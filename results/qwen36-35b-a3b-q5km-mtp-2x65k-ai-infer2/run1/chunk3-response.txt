T1 — `tofu plan` performs a dry-run: it reads state, queries providers, and outputs a diff of what will be created/updated/destroyed without making changes. `tofu apply` executes the proposed changes, updates state, and provisions resources.

T2 — State is a JSON file mapping OpenTofu resources to real-world infrastructure IDs and attributes. Remote state is crucial for team collaboration, security (storing secrets out of VCS), state locking to prevent concurrent modifications, and enabling modules/workspaces.

T3 — `count` uses integer indices (0, 1, 2) and recreates all resources if the list length changes. `for_each` uses maps or sets with stable keys. `for_each` is preferred when resources have unique identifiers, as it only creates/destroys changed items and avoids unnecessary recreation on list modifications.

T4 — OpenTofu detects drift during `tofu plan` via state refresh (reads current cloud state). It plans to reconcile drift by applying the desired configuration. If drift is intentional, use `lifecycle { ignore_changes = [...] }`. If critical, `tofu apply` will overwrite it; use `-refresh-only` to update state without changes.

T5:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `terraform_remote_state` reads the entire state file, which can expose sensitive data and cause performance issues. Output values expose only explicitly declared data. Recommended alternative: Use `data "terraform_remote_state"` with explicit `outputs` mapping to fetch only needed values, or use `terraform_remote_state` with `workspace` filtering. This improves security, reduces state payload, and enforces explicit contracts.

T7 — Provisioners (`remote-exec`) run during apply but do not update state attributes. Outputs depend on state, so they return empty on first apply. Fix: Use a `local_file` resource to write the kubeconfig, or use `remote-exec` to write to a known path, then use `local_file` to read it. Alternatively, generate kubeconfig via `local-exec` in a `null_resource` with `triggers` and output the file content directly.

T8 — `tofu import` is a CLI command that manually maps existing infrastructure to state, requiring manual config scaffolding and error-prone ID mapping. The `import` block (1.5+) is declarative, supports multiple resources, validates config before import, and integrates with `tofu plan` for safer, auditable migrations.

T9 — A `variable` block defines inputs passed into a module/root. An `output` block exposes computed values from a module/root to consumers. Variables flow in; outputs flow out.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a platform (AWS, K8s, etc.). Running `tofu plan` without `tofu init` fails because provider plugins aren't downloaded, the `.terraform` directory isn't initialized, and dependency locking isn't resolved.

T11 — `.terraform.lock.hcl` pins exact provider versions and checksums. Commit it to VCS to ensure reproducible builds, prevent supply-chain attacks, and guarantee all team members/CI use identical provider versions.

T12 — `tofu destroy` deletes all resources tracked in state. Target a single resource: `tofu destroy -target=module.name.resource_name`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to find the latest Ubuntu AMI, or `data "aws_vpc" "existing"` to reference a VPC created outside OpenTofu.

T14 — `locals` compute values within a module without exposing them externally. `variables` accept external inputs. Use `locals` for derived values, transformations, or to avoid repetition (e.g., `name = "${var.prefix}-${var.env}"`).

T15 — `lifecycle` controls resource behavior:
- `create_before_destroy = true`: Creates new instance before destroying old (zero-downtime for stateful resources).
- `prevent_destroy = true`: Blocks `tofu destroy` (safety for critical data).
- `ignore_changes = [...]`: Ignores drift on specific attributes (e.g., `user_data` updated by external scripts).

T16 — `moved` block maps old resource/module addresses to new ones in state. It updates internal references without destroying/recreating resources, enabling safe refactoring of module structure or resource naming.

T17 — OpenTofu builds a dependency graph from resource references. Implicit dependencies are inferred automatically. Explicit `depends_on` forces ordering but disables parallelism for those resources. Use sparingly to avoid bottlenecks; prefer implicit references for optimal concurrency.

T18 — Strategies & tradeoffs:
1. **Split into multiple modules/workspaces**: Reduces graph size. Tradeoff: Increased management overhead and cross-module data sharing complexity.
2. **Use `data` sources sparingly & cache results**: Fewer API calls. Tradeoff: Stale data if not refreshed properly.
3. **Optimize providers** (e.g., `skip_metadata_api_check`, `max_retries`): Faster provider initialization. Tradeoff: May bypass security checks or mask transient errors.
4. **Use `terraform plan -target` for targeted changes**: Skips unrelated resources. Tradeoff: Misses cross-resource impacts; not suitable for full-state audits.

T19 — State locking uses backend-specific mechanisms (DynamoDB, Consul, etc.) to prevent concurrent writes. If a lock isn't released: `tofu force-unlock <LOCK_ID>`. Risks: Data corruption or race conditions if another apply is actively running; always verify no other process holds the lock.

T20 — Steps:
1. Add new backend config (`backend "s3" { bucket = "...", key = "...", region = "...", dynamodb_table = "..." }`).
2. Run `tofu init -migrate-state`. OpenTofu copies state to S3, verifies integrity, and deletes local state.
3. Verify: `tofu state list`, check S3 bucket contents, run `tofu plan` to confirm no drift.
4. Test: `tofu apply` in a non-prod environment to validate locking and state reads.

A1 — A **playbook** is an ordered list of plays (host/target + tasks). A **role** is a reusable directory structure (`tasks/`, `vars/`, `templates/`) for modularization. A **task** is a single unit of work (module + arguments).

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_facts['os_family'] }}` or `{{ ansible_os_family }}`.

A3 — `command`: runs without shell features (safest). `shell`: runs via `/bin/sh`, supports pipes/redirects. `raw`: executes without Python, ideal for bootstrapping or unpatched hosts.

A4 — Idempotency means running a task multiple times yields the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "log" >> /var/log/app.log` (appends every run; use `lineinfile` or `copy` with `content` instead).

A5:
```yaml
- name: Install htop based on OS family
  package:
    name: htop
  when: ansible_os_family == "Debian"

- name: Install epel-release and htop on RedHat
  yum:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (lowest to highest): inventory vars → group_vars → host_vars → role defaults → play vars → role vars → task vars → block vars → extra_vars. Extra_vars always win.

A7 — Use `serial: 3` for the first batch, then `serial: "100%"` for the rest. Group nodes in inventory (`[rke2_masters]`, `[rke2_agents]`). Add `pause: seconds=30` or `wait_for` on a readiness endpoint after the first batch to ensure stability before scaling.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'my_secret' --name 'db_password'`, then paste the output into a vars file. The rest of the file remains plaintext.

A9 — Inventory defines hosts/groups. **Static**: YAML/INI file maintained manually. **Dynamic**: Script/API that returns JSON/YAML at runtime, ideal for cloud environments with auto-scaling.

A10 — `ansible webservers -m shell -a "df -h"` or `ansible webservers -a "df -h"` (uses `command` module by default).

A11 — A **handler** is a task triggered by `notify`, executed only if notified, and runs once at the end of the play. Differs from regular tasks (run immediately). Trigger: `notify: restart_service`.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `roles_path`, `vault_password_file`.

A13 — `register` saves task output to a variable. Use in subsequent tasks: `when: my_var.stdout_lines | length > 0` or `debug: msg="{{ my_var.stdout }}"`.

A14 — `import_tasks` is static (evaluated at parse time, faster). `include_tasks` is dynamic (evaluated at runtime, supports conditionals/loops). Use `include_tasks` for runtime decisions; `import_tasks` for performance and static inclusion.

A15 — Ansible Galaxy is a community repository for roles/collections. `requirements.yml` lists dependencies with versions. Install: `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible communicates with targets. `ssh`: default for Linux/Unix. `local`: runs on control node. `network_cli`: uses telnet/SSH for network devices (Cisco, Juniper). Choose based on target OS/architecture.

A17 — `delegate_to` runs a task on a specific host. `run_once` runs a task once across all hosts. Example: Gather disk metrics from all hosts, then write a consolidated report to localhost once:
```yaml
- name: Collect disk info
  command: df -h
  register: disk_info

- name: Write summary to localhost
  copy:
    content: "{{ disk_info.results | map(attribute='stdout') | join('\n') }}"
    dest: /tmp/disk_report.txt
  delegate_to: localhost
  run_once: true
```

A18 — Strategies & tradeoffs:
1. **Increase `forks`**: Parallelizes tasks. Tradeoff: Higher memory/CPU on control node.
2. **Enable `pipelining`**: Reduces SSH connections per task. Tradeoff: Requires `requiretty` disabled on targets.
3. **Fact caching** (Redis/Memcached): Avoids repeated fact gathering. Tradeoff: Stale facts if infrastructure changes rapidly.
4. **Mitogen**: Replaces SSH with persistent connections. Tradeoff: Requires installation, may conflict with some modules.

A19 — `{{ }}` evaluates expressions, `{% %}` controls flow (loops/conditionals), `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
    # Health check: {{ server }}:{{ server_port }}
    server {{ server }}:{{ server_port }};
{% endfor %}
}
```

A20 — Implementation:
- `serial: 1` or `20%` for rolling batches.
- **Pre-task**: `uri` to deregister from LB (set weight=0 or health=draining).
- **Deploy**: Update app, restart service.
- **Post-task**: `uri` health check loop (`until: response.status == 200`, `retries: 5`).
- **Rollback**: `block/rescue` catches failures; rescue task re-registers node, reverts deployment, and notifies LB. Use `pause` for manual verification if needed.
