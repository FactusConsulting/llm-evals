K1 — A **Deployment** manages stateless workloads with interchangeable, randomly named pods and supports rolling updates. A **StatefulSet** manages stateful workloads with stable, predictable network IDs, ordered deployment/scaling, and persistent storage tied to each pod.

K2 — `kube-proxy` creates iptables or IPVS rules that map the Service's ClusterIP:Port to the backend pod IPs. When traffic hits the ClusterIP, kube-proxy performs DNAT to randomly select one healthy pod IP, routing the request directly to it.

K3 — A **PersistentVolume (PV)** is a cluster-provisioned storage resource. A **PersistentVolumeClaim (PVC)** is a user's request for storage. A **StorageClass** defines a template for dynamic PV provisioning. A PVC binds to a PV (static) or triggers a StorageClass to provision one dynamically.

K4 — 1. `kubectl logs <pod> --previous` to check crash exit codes/stack traces. 2. `kubectl describe pod` to inspect Events, OOMKilled status, or probe failures. 3. Verify resource requests/limits and node capacity. 4. Check external dependencies (DB, env vars, configmaps) and app startup commands.

K5 — CoreDNS provides internal DNS resolution for `Service` and `Pod` names. If CoreDNS pods are down, internal service discovery fails (pods can't resolve cluster DNS names), but direct IP communication and external DNS resolution remain unaffected.

K6 — The scheduler **filters** nodes that don't meet requirements (resources, taints, affinity, node selectors), then **scores** remaining nodes based on priorities. Factors: 1) Resource utilization (LeastRequested/BalancedResourceAllocation), 2) Node affinity/anti-affinity rules, 3) Taints/tolerations, 4) Pod topology spread constraints.

K8 — Client → External LB (routes to Ingress Controller IP) → Ingress Controller (NGINX) reads Ingress/Service resources → NGINX forwards to Service ClusterIP → kube-proxy/iptables/IPVS DNATs to pod IP → Application pod handles request.

K9 — A **NetworkPolicy** restricts pod ingress/egress traffic. Default behavior (no policies): all traffic allowed. When applied: only traffic matching the policy is permitted; all other ingress/egress is explicitly denied.

K10 — **RollingUpdate** gradually replaces old pods with new ones (zero downtime). **Recreate** terminates all old pods before starting new ones (downtime). Choose Recreate for stateful apps, database migrations, or when old/new versions are incompatible.

K11 — A **namespace** provides virtual cluster isolation for resources. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get pod`, it reveals: 1) Events (scheduling, pull, probe failures), 2) Resource requests/limits & node affinity, 3) Mounted volumes/secrets/configmaps, 4) Pod conditions & container last states.

K13 — A **ConfigMap** stores non-confidential configuration data. Pods consume it via: 1) Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`), 2) Volume mounts (files appear in the container filesystem).

K14 — **ClusterIP**: internal cluster-only access. **NodePort**: exposes the service on a static port on each node's IP. **LoadBalancer**: provisions a cloud provider LB that routes to the NodePort/ClusterIP.

K15 — A **DaemonSet** ensures a pod runs on every node (or subset via selector). Use it for node-level agents: logging (Fluentd), monitoring (node-exporter), CNI plugins, or storage daemons.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Use taints/tolerations for dedicated/maintenance nodes; use node affinity to co-locate related workloads (e.g., app + cache).

K17 — An **Operator** is a custom controller that manages complex stateful apps using CRDs and domain-specific reconciliation logic. Unlike standard controllers (which just match desired state), Operators encode operational knowledge (backups, upgrades, failover), automating manual DB/app lifecycle tasks.

K18 — etcd uses **Raft** for linearizable consistency. If quorum is lost, the cluster becomes read-only/unwritable. Recovery from 2/3 loss: restore the remaining node from a recent snapshot (`etcdctl snapshot restore`), reconfigure the cluster membership, and restart etcd.

K19 — **Role/ClusterRole** define permissions (verbs/resources). **RoleBinding/ClusterRoleBinding** bind roles to users/groups/serviceaccounts.
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` causes Kubernetes to append cluster suffixes (e.g., `.svc.cluster.local`) to queries with <5 dots, generating 5 DNS lookups before falling back to external DNS. Fix: set `dnsConfig: { options: [{ name: "ndots", value: "2" }] }` in the pod spec, or use FQDNs (trailing dot).

D1 — **Merge** preserves commit history with a merge commit. **Rebase** rewrites history into a linear timeline. Avoid rebasing on shared/public branches or after pushing to remote to prevent history conflicts.

D2 — **TCP** is connection-oriented, reliable, ordered, and flow-controlled. **UDP** is connectionless, unreliable, fast, and unordered. TCP: HTTP, SSH, FTP. UDP: DNS, DHCP, VoIP, video streaming.

D3 — A **race condition** occurs when concurrent threads/processes access shared state without synchronization, causing unpredictable results. Example: two threads incrementing a shared counter without a mutex, resulting in lost updates.

D4 — **Symmetric** encryption uses one key for encrypt/decrypt (fast). **Asymmetric** uses a public/private key pair (secure key exchange). TLS uses asymmetric encryption for the handshake/key exchange, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates an immutable **image layer**. Layer caching speeds up builds by reusing unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., copy dependency manifests first, install deps, then copy source code).

D6 — 1. Check app logs for errors/timeouts. 2. Verify upstream dependencies (DB, cache) health and connection pools. 3. Check resource limits (CPU throttling, OOM). 4. Inspect load balancer/ingress health checks, connection limits, and rate limiting.

D7 — **CAP theorem** states a distributed system can only guarantee two of: Consistency, Availability, Partition tolerance. **CP**: Distributed SQL (CockroachDB, HBase) prioritizes data accuracy over availability during partitions. **AP**: Cassandra, DynamoDB prioritize availability, allowing stale reads.

D8 — **Horizontal scaling** adds more nodes/instances; **vertical scaling** increases CPU/RAM of existing nodes. Horizontal scaling requires: stateless services, distributed databases, message queues, consistent hashing, and container orchestration.

D9 — An **environment variable** is a dynamic value that configures process behavior. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON** is strict, machine-friendly, and universally supported in web APIs. **YAML** is human-readable, indentation-based, and supports comments. JSON advantage: strict parsing/universal API support. YAML advantage: readability/less boilerplate for configs.

D11 — A **REST API** is an architectural style using HTTP methods on resources. **GET**: retrieve data. **POST**: create a resource. **PUT**: update/replace a resource. **DELETE**: remove a resource.

D12 — **Version pinning** locks dependencies to exact versions (e.g., `package-lock.json`, `Pipfile.lock`). It ensures reproducible builds, prevents unexpected breaking changes, and guarantees consistent environments across deployments.

D13 — **Compiled** languages translate source to machine code before execution (C, Rust). **Interpreted** languages execute source line-by-line at runtime (Python, JavaScript). (Note: many modern languages use hybrid JIT/AOT compilation.)

D14 — A **forward proxy** sits on the client side, routing outbound traffic (e.g., corporate internet proxy). A **reverse proxy** sits on the server side, routing inbound traffic. Examples: Nginx (load balancing/SSL termination), HAProxy (high-availability routing).

D15 — A **deadlock** occurs when two+ processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait.

D16 — **Eventual consistency** guarantees all replicas will converge to the same state without further updates. Cassandra handles read-after-write via tunable consistency: use `QUORUM` for both reads and writes, or `SERIALIZABLE`/`LINEARIZABLE` for strong consistency.

D17 — **mTLS** requires both client and server to present valid certificates. Handshake: ClientHello → ServerHello+Cert → ServerKeyExchange → ClientKeyExchange+Cert → CertificateVerify → Finished. Used in: service meshes (Istio/Linkerd), zero-trust architectures, internal microservices.

D18 — A **hash table** maps keys to values via a hash function. Collision resolution: **chaining** (linked lists per bucket) or **open addressing** (probing: linear/quadratic/double hashing). Time complexity: average O(1) for insert/lookup/delete; worst O(n) with severe collisions.

D19 — A **circuit breaker** prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal), **Open** (fail fast, trip after error threshold), **Half-open** (test with limited requests). Works with retries/backoff: circuit breaker should throttle requests while retries with exponential backoff allow the downstream service to recover.

D20 — **Optimistic** concurrency assumes no conflicts, checking at commit (e.g., row versioning/timestamps). **Pessimistic** locks resources during transactions (e.g., `SELECT FOR UPDATE`). Choose optimistic for high-read/low-write contention; pessimistic for high-write contention or critical financial data.
