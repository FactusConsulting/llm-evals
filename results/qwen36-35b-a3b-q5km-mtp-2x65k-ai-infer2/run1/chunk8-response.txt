CL1 — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, runtime, data, and apps. Example: AWS EC2. PaaS provides runtime, middleware, and OS; you manage apps and data. Example: Google App Engine. SaaS provides fully managed applications; you only manage user access and data. Example: AWS WorkSpaces.

CL2 — The Shared Responsibility Model divides security: provider secures the cloud infrastructure; customer secures what's in it. IaaS VM: Provider = physical, hypervisor, host OS. Customer = guest OS, patches, network config, data, IAM. Managed K8s: Provider = control plane, node OS, API server, etcd. Customer = workloads, network policies, RBAC, secrets, data. SaaS (M365): Provider = app, infra, compliance, patches. Customer = identities, data, access policies, MFA, device compliance.

CL3 — VPC: Isolated virtual network. Subnet: IP range within a VPC, tied to an AZ. Security Group (SG): Stateful firewall at the instance/pod level; only allow rules, evaluated before routing. NACL: Stateless firewall at the subnet level; allow/deny rules, evaluated after routing. Layering: Traffic enters VPC → hits NACL (subnet boundary) → routed to subnet → hits SG (resource boundary). Stateful = tracks connection state, automatically allows return traffic. Stateless = evaluates each packet direction independently.

CL4 — Landing zone: Pre-configured, secure multi-account foundation with baseline networking, IAM, logging, and guardrails. OUs: Group accounts by function/environment (e.g., Corp, Sandbox, Prod, Security). Guardrails: SCPs/Policy Frameworks enforcing compliance, budget caps, region restrictions. Shared Networking: Transit Gateway (AWS) / Hub-and-Spoke (Azure) for centralized inter-VPC/VNet routing and on-prem connectivity. Centralized Logging: Dedicated security account aggregates CloudTrail, VPC Flow Logs, GuardDuty. Single-account problems: Massive blast radius, permission sprawl, billing opacity, compliance violations, operational bottlenecks, lack of isolation.

CL5 — IaC: Managing infrastructure via version-controlled, machine-readable definitions. Terraform/OpenTofu: Declarative HCL, provider-agnostic, massive ecosystem. Best for multi-cloud, complex state, team collaboration. Pulumi: Imperative/Declarative, general-purpose languages (TS, Python, Go). Best for devs, complex logic, dynamic provisioning. CloudFormation/Bicep: AWS-native declarative. Bicep improves readability. Best for AWS-only shops. Crossplane: K8s-native IaC; manages cloud resources as CRDs. Best for GitOps/K8s-centric teams.

CL6 — HPA: Scales pods based on CPU/memory/custom metrics. Reactive. VPA: Adjusts pod resource requests/limits; requires restart. Best for right-sizing, not real-time scaling. Cluster Autoscaler: Adds/removes nodes based on pending pods. KEDA: Event-driven scaling based on external triggers (queues, Kafka, HTTP). Use KEDA over HPA when scaling must respond to event backlog or external metrics rather than static resource utilization.

CL7 — RPO/RTO: Define by business impact. Active-Active: Both regions serve traffic; lowest RPO/RTO, highest cost/complexity. Active-Passive: One serves, one standby; higher RPO/RTO, lower cost. DB Replication: Sync = strong consistency, higher latency, limits region distance. Async = eventual consistency, lower latency, higher RPO. DNS Failover: Route53/Traffic Manager health checks route to healthy region. State Management: Externalize to managed services (RDS, DynamoDB, Redis); avoid local state. Cost: Active-active doubles infra + data transfer; active-passive cheaper but needs warm/cold standby. Pilot Light: Core infra running, scaled up on failover. Warm Standby: Scaled-down prod running. Multi-site Active-Active: Full prod in both regions.

CL8 — GitOps: Git as single source of truth; declarative desired state pushed to cluster; operators reconcile live state to desired state. ArgoCD: UI-first, push/pull, strong visualization. FluxCD: Git-native, pull-only, tightly integrated with GitHub/GitLab, CLI/automation focused. Secrets: SealedSecrets (encrypt in Git, decrypt in cluster), External Secrets Operator (syncs from AWS Secrets Manager/Vault), HashiCorp Vault (dynamic secrets, mTLS). Drift: Controllers detect manual changes, auto-revert to Git state on sync. Prevents drift but requires strict change control.

CL9 — StatefulSet: Provides stable pod identity, ordered deployment/termination, stable DNS. PV/PVC + Local Storage: Use `local` storageClass with `volumeBindingMode: WaitForFirstConsumer` to bind PV to the node where the pod schedules, ensuring low latency. Headless Service: `clusterIP: None` enables StatefulSet DNS discovery. Init Containers: Run before main app to fetch config, validate deps, or prepare filesystem. ConfigMaps as Volume Mounts: Mount config files directly into specific paths; use `subPath` if needed. PDB: `minAvailable` or `maxUnavailable` ensures minimum healthy pods during disruptions. Note: Local storage lacks replication; accept data loss risk or implement app-level replication.

CL10 — Service Account: K8s native pod identity; no cloud permissions by default. Workload Identity (GCP/Azure): Maps K8s SA to cloud IAM identity without long-lived credentials. IRSA (AWS): Maps K8s SA to AWS IAM Role via OIDC provider. Mounting credentials in pods is bad practice: long-lived, hard to rotate, risk of leakage, violates least privilege, breaks audit trails. Workload identity federation solves this via OIDC token exchange: pods get short-lived, scoped credentials from cloud IAM with auto-rotation, least privilege, and full auditability.

CL11 — Object (S3/Blob): Scalable, HTTP API, flat namespace, metadata-rich. Durability: 99.999999999%. Availability: 99.99%. Use for: unstructured data, backups, static web, data lakes. Block (EBS/Managed Disk): Low-latency, fixed size, mounted as drive. Durability: 99.999%. Availability: 99.99%. Use for: databases, VM OS, apps requiring POSIX. File (EFS/Azure Files): NFS/SMB, shared, hierarchical. Durability: 99.999999999%. Availability: 99.99%. Use for: shared configs, home dirs, legacy file shares. Trade-offs: Block = performance, File = sharing, Object = scale/cost.

CL12 — Network Policies: Default deny, allow only required pod-to-pod/service traffic. Service Mesh (mTLS): Istio/Linkerd for encrypted service-to-service comms, policy enforcement, observability. Pod Identity: Workload identity/IRSA for cloud access. Admission Controllers: OPA/Kyverno enforce policies (no privileged pods, required labels, resource limits). Image Signing/Verification: Cosign/Notary + admission controller blocks unsigned images. Runtime Security: Falco monitors syscalls, detects anomalies. Secrets: External Secrets Operator/Vault, never in env vars/plain ConfigMaps. vs Perimeter: Zero-trust assumes breach, verifies every request, micro-segments, identity-centric. Perimeter trusts internal traffic and relies on network boundaries.

CL13 — CDN: Distributed network of edge servers caching content closer to users. Works by DNS routing to nearest edge, caching static assets, serving requests, fetching from origin on cache miss. Services: CloudFront (AWS), Azure CDN, Cloudflare. Use CDN for static/dynamic content delivery, DDoS mitigation, global latency reduction. Direct origin causes high latency, high bandwidth costs, and single point of failure.

CL14 — Region: Geographic area with multiple AZs. AZ: One or more discrete data centers with independent power/cooling/networking, connected via low-latency links. Deploy across multiple AZs to protect against single data center failure and meet HA SLAs. Zonal resources: Tied to one AZ (EBS, EC2). Regional resources: Span multiple AZs (S3, RDS Multi-AZ, ALB).

CL15 — Managed DB: Cloud provider handles provisioning, patching, backups, replication, monitoring, scaling. Provider handles: OS/db engine updates, HA setup, automated backups, point-in-time recovery, storage scaling, monitoring. You handle: schema, queries, IAM access, data modeling, connection pooling. Benefits: Reduced ops overhead, faster recovery, built-in HA/DR.

CL16 — IAM Users: Human/service identities. Groups: Collections of users. Roles: Temporary credentials for entities (users, services, external). Policies: JSON documents defining permissions. Least Privilege: Grant only necessary permissions for required actions/resources. Apply: Use roles over long-lived keys, attach policies to groups, use condition keys (IP, MFA, time), audit with IAM Access Analyzer, enforce SCPs.

CL17 — Serverless: Managed compute where provider handles infra scaling/patching; pay per execution. Compare: Lambda (AWS), Azure Functions, GCP Cloud Functions. Similar models, differ in runtime support, cold start behavior, integration ecosystems. Cold starts: Delay when container initializes for first request. Matters for latency-sensitive apps. Mitigate with provisioned concurrency, keep-warm, lighter runtimes. Poor fit: Long-running processes, sustained high CPU/memory, strict latency requirements, complex stateful workloads, vendor lock-in concerns.

CL18 — Ingress Resource: Standard K8s API, relies on controller (NGINX, ALB). TLS termination at controller. Gateway API: Newer, standardized, separates routing (Gateway) from backend (HTTPRoute). Better RBAC, multi-tenant, explicit TLS management. Cloud LB Annotations: Directly provision cloud LB (ALB/ILB). TLS termination at LB. Simpler but less portable. Service Mesh Ingress: Istio/Linkerd gateway. mTLS, advanced traffic splitting, observability. TLS termination at mesh gateway. Use Gateway API over Ingress for multi-tenant isolation, standardized routing, explicit TLS/cert management, or complex traffic policies.

CL19 — RI vs SP vs Spot: RIs (1-3yr commitment, predictable, high discount). SPs (flexible commitment, pay-as-you-go discount). Spot/Preemptible (up to 90% off, interruptible, fault-tolerant workloads). Right-sizing: Use monitoring to match instance types to actual CPU/memory; downsize over-provisioned, upsize bottlenecks. Storage Tiering: S3 Intelligent-Tiering, Archive for cold data. Delete unattached EBS, optimize snapshots. Idle Detection: Find unattached volumes, idle LBs, unused IPs, dormant instances; automate cleanup. FinOps: Cross-functional culture (Eng, Fin, Ops). Tagging strategy, showback/chargeback dashboards, budget alerts, monthly reviews. Tools: Cost Explorer, Azure Cost Management, Kubecost, CloudHealth, OpenCost. Processes: Tag enforcement, automated rightsizing, spot adoption pipelines, cost ownership mapping.

CL20 — Abstraction: Kubernetes, Terraform, service mesh, API gateways. K8s as runtime: EKS/AKS/GKE, GitOps, Helm/Kustomize. Terraform: Provider-agnostic IaC, modular design, per-cloud state. Networking: Cloud VPN, Interconnect/ExpressRoute, global LB, DNS routing. Identity: OIDC federation, centralized IdP, cross-cloud SSO. Trade-offs: Increased complexity, higher costs, operational overhead, data egress fees, inconsistent feature parity. Justified: Regulatory/data residency, avoiding single-vendor risk, best-of-breed services, M&A integration. Unnecessary: Startups, homogeneous workloads, limited engineering bandwidth, where cloud-native features outweigh lock-in risk.

OT1 — Purdue Model (ISA-95): Hierarchical enterprise-control integration. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, DCS controllers). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations/MES (production scheduling, batch management). Level 4: Business/Enterprise (ERP, finance, supply chain). Level 5: Enterprise/Cloud (analytics, AI, external partners).

OT2 — IT networks prioritize confidentiality/integrity/availability, use standardized OS, and support rapid automated patching. OT networks prioritize availability/safety/process continuity, run legacy/proprietary systems, have real-time constraints, and long lifecycles. IT patching fails in OT because updates require vendor validation, maintenance windows, and can cause downtime, safety risks, or protocol incompatibilities.

OT3 — IDMZ: Segmented network between IT and OT, firewalled. Traffic: Strictly controlled bidirectional or one-way OT→IT (process data, alarms). IT→OT (commands, updates) only via IDMZ with strict filtering. Direct L4→L1 is dangerous because it bypasses security controls, exposes critical control systems to IT threats, violates Purdue isolation, and risks catastrophic process disruption.

OT4 — Modbus TCP: L1/L2, simple request/response, legacy/SCADA. OPC UA: L2/L3, secure, platform-independent, modern SCADA/MES. EtherNet/IP (CIP): L1/L2, industrial Ethernet, real-time control, manufacturing. PROFINET: L1/L2, deterministic real-time Ethernet, process/manufacturing. MQTT: L3/L4, lightweight publish/subscribe, IoT/cloud telemetry, edge-to-cloud.

OT5 — Data Diode: Hardware-enforced unidirectional flow. Physically prevents reverse traffic. Use when strict one-way data flow is required (OT→IT telemetry, secure updates). Firewall: Software/hardware, bidirectional, stateful inspection, allows/denies based on rules. Limitation: Diodes cannot allow any return traffic (acknowledgments, commands, status), whereas firewalls allow bidirectional but are vulnerable to sophisticated exploits.

OT6 — Flow: PLCs/RTUs → OPC UA Server (historian/edge) → MQTT Broker (edge gateway) → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security Boundaries: 1) OT Network (L1/L2): Segmented, no internet. 2) Edge Gateway/DMZ: Protocol translation, data filtering, TLS/mTLS, local caching. 3) Cloud Boundary: WAF, DDoS protection, IAM, encryption. 4) OT-Edge boundary: Data diode or strict firewall rules.

OT7 — Zone: Logical grouping of assets with similar security requirements, risk tolerance, and blast radius. Conduit: Communication path between zones with defined security controls. Model: Zone 1 (Corporate/IT L4) → Conduit 1-2 (Firewall/DMZ) → Zone 2 (Engineering/SCADA L3) → Conduit 2-3 (Firewall) → Zone 3 (Control/PLCs/HMIs L1-2) → Conduit 3-4 (Data diode/firewall) → Zone 4 (SIS, air-gapped/isolated). Each zone enforces specific security levels (SL-T), access controls, and monitoring.

OT8 — VLAN Design: Segment by function/process (e.g., VLAN 10: Line 1 PLCs, 20: Line 2, 30: HMIs, 40: SCADA, 50: Engineering). Firewall Placement: Core firewall IT/OT, edge firewalls between VLANs, DMZ for external access. Switch Architecture: Managed L3 switches, port security, 802.1X (if supported), disable unused ports. Remote Access: Jump host in DMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, monitor latency/alarms.

OT9 — SIS: Independent system to bring process to safe state on hazardous conditions. BPCS: Normal process control. IEC 61511: Safety lifecycle standard for SIS; defines SIL requirements. Isolation: SIS must be independent to prevent common-cause failures (cyber attacks, power loss). Air-gapped or strictly isolated. Ransomware on SIS: Could disable safety functions, causing catastrophic failure, environmental damage, or loss of life. SIS design assumes physical/logical independence to mitigate this.

OT10 — PLC: Discrete control, fast, rugged, machine/line-level. DCS: Centralized control, integrated I/O, continuous/process industries. SCADA: Supervisory system, HMI, data acquisition, remote monitoring, aggregates PLC/DCS data. Coexist: Yes. PLCs/DCS handle control, SCADA provides oversight, HMIs for operators, historians for data. Common in modern plants.

OT11 — Jump Hosts: Isolated bastion in DMZ, no direct OT access. MFA: Required for all remote access. Session Recording: Audit trail. Vendor Access: Time-limited, role-based, approved requests, break-glass. RDP to HMI unacceptable: Exposes OT directly to corporate network, bypasses segmentation, high lateral movement risk, violates Purdue model.

OT12 — Detection: Network IDS/IPS at OT boundary, anomaly detection (unusual PLC commands, traffic spikes), asset inventory validation. Inventory: Real-time OT asset map, baseline behavior, configuration management. IR Steps: Contain (isolate VLANs, block vendor IP), Investigate (forensics, logs), Eradicate (patch, revoke creds), Recover (restore clean backups, validate). Coordination: Notify control room, switch to manual/local control if needed, prioritize safety. Operator Role: Monitor process, execute manual overrides, report anomalies, follow emergency procedures, avoid compromised IT systems. Safe Operations: Maintain SIS independence, use local HMIs, fallback comms, ensure power/cooling unaffected.

OT13 — HMI: Interface for operators to monitor/control processes (displays, buttons, alarms). Role: Real-time visualization, manual overrides, alarm management. vs Engineering Workstation: HMI is for operators (run-time). Engineering workstation is for programmers/configurers (offline/online programming, logic editing, parameter tuning).

OT14 — Historian: Time-series database optimized for high-volume, continuous process data logging. Importance: Trend analysis, compliance, troubleshooting, performance optimization. Plant Historian (L3): Real-time/near-real-time, local, process-focused, high write throughput. Enterprise Historian (L4): Aggregated, long-term retention, business analytics, integrated with ERP/MES, lower write frequency.

OT15 — Ladder Logic: Graphical programming language mimicking relay circuits. Executed by: PLCs. Dominance: Familiar to electricians, easy to troubleshoot, deterministic, widely supported, low learning curve, decades of proven reliability in industrial settings.

OT16 — RTU: Remote Terminal Unit, designed for harsh environments, long-distance communication (serial, cellular, satellite), simple I/O, SCADA telemetry. PLC: Faster, complex logic, local control, wired networks. RTU deployment: Pipelines, utilities, remote sites, harsh conditions, wide geographic dispersion.

OT17 — Analog: Continuous voltage/current (4-20mA, 0-10V). Digital: Discrete on/off (24VDC). 4-20mA preferred over 0-20mA: 4mA "live zero" indicates wire break/failure (0mA = fault), allows powering 2-wire transmitters, less susceptible to noise over long distances.

OT18 — Asset Inventory: Comprehensive list of hardware, firmware, network configs, communication patterns. Foundation: Cannot secure what you don't know; enables vulnerability management, segmentation, compliance. Tools: Passive monitoring (packet capture, protocol analyzers), active scanning (limited, targeted). Active scanning dangerous: Can crash legacy devices, cause process disruption, trigger safety systems, generate unexpected network traffic. Passive is preferred.

OT19 — MITRE ATT&CK for ICS: Maps adversary tactics/techniques specific to ICS/OT. Tactics & Examples: 1) Reconnaissance: Gather network topology (T1580). 2) Resource Development: Acquire ICS malware (T1587). 3) Initial Access: Phishing for credentials (T1566). 4) Execution: Run malicious commands on PLC (T1059). 5) Impact: Manipulate process values to cause physical damage (T1496). vs Enterprise ATT&CK: ICS focuses on safety, availability, physical process impact, legacy protocols, operational constraints. Enterprise focuses on IT confidentiality/integrity. Assessment: Map defenses to techniques, identify gaps (e.g., no PLC command monitoring), prioritize controls, simulate attacks, update detection rules.

OT20 — Log Collection: Passive network taps, OPC UA/MQTT log forwarders, SIEM agents on non-critical OT servers. Avoid active polling. SIEM Integration: Normalize OT logs (Syslog, CEF), correlate with IT logs, use OT-specific parsers. Detection Rules: Baseline normal traffic, alert on unauthorized PLC writes, unusual protocol usage, after-hours access, known malicious IPs. Triage: IT analysts filter noise, OT engineers validate process impact. Escalation to plant manager/safety officer. Staffing: IT analysts (threat intel, log analysis), OT engineers (protocol/process expertise), shared SOC manager. False Positives: High due to maintenance/batch jobs. Mitigate with whitelisting, baseline tuning, OT-specific correlation. Unauthorized Firmware Change: Immediate isolation of affected PLC/network segment, verify safety impact, restore from known-good backup, investigate root cause, update change management, patch vulnerability.
