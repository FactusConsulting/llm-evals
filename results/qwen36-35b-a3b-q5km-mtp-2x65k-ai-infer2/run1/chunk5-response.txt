DN1 — **class vs struct**: `class` is a reference type (heap-allocated, supports inheritance, nullable, GC-managed). `struct` is a value type (stack/inline-allocated, copied on assignment, no inheritance, typically immutable). Use `struct` for small, short-lived, immutable data that doesn't require polymorphism (e.g., coordinates, IDs, math vectors). Avoid if large or frequently boxed.

DN2 — **IEnumerable<T> vs IQueryable<T>**: `IEnumerable<T>` enumerates in-memory (LINQ-to-Objects), filtering/mapping happens in application memory. `IQueryable<T>` builds expression trees that translate to provider-specific queries (e.g., SQL), executing filtering/aggregation on the database. The distinction matters because `IQueryable` reduces memory/network overhead by pushing computation to the data source.

DN3 — **async/await, Task vs ValueTask**: `async/await` compiles to a state machine that captures context, yields control during I/O-bound waits, and resumes when complete. `Task` is a reference type representing async operations, always heap-allocated. `ValueTask` is a struct that can represent synchronous or asynchronous results, avoiding heap allocation when already completed. Use `ValueTask` when an async method frequently completes synchronously (e.g., cache hits, cached results) to reduce GC pressure.

DN4 — **DI lifetimes & Scoped-in-Singleton bug**: DI provides dependencies externally. `Transient`: new instance per resolution. `Scoped`: one instance per request/context. `Singleton`: one instance per app lifetime. Injecting a `Scoped` service into a `Singleton` captures it for the Singleton's lifetime, breaking request isolation, causing thread-safety issues, and leaking state/memory.

DN5 — **string vs ReadOnlySpan<char>, Span<T>**: `string` is immutable, heap-allocated, and copies on manipulation. `ReadOnlySpan<char>` is a stack-allocated, zero-copy view over contiguous memory (strings, arrays, unmanaged buffers). `Span<T>` is the mutable counterpart. Use `Span<T>`/`ReadOnlySpan<char>` for high-performance parsing, slicing, and string processing to avoid allocations and enable buffer reuse.

DN6 — **GC, Generations, LOH, IDisposable**: GC traces live objects and reclaims unreachable memory. Generations: `Gen 0` (short-lived, frequent collections), `Gen 1` (buffer), `Gen 2` (long-lived, infrequent). Objects survive collections and promote. `LOH` (Large Object Heap) holds objects >85KB, collected only during Gen 2, not compacted by default (can fragment). `IDisposable` enables deterministic cleanup of unmanaged resources (handles, native memory). GC is non-deterministic; `using`/disposal ensures timely release.

DN7 — **ConfigureAwait(false), SynchronizationContext**: Default `await` captures the current `SynchronizationContext` (UI thread, ASP.NET request context) and resumes there. `ConfigureAwait(false)` skips context capture, resuming on any thread pool thread. Use in libraries/shared code to avoid deadlocks and improve performance. Do NOT use in UI apps or code requiring thread-affine resources. It relates to `SynchronizationContext` by bypassing the thread-switching mechanism that causes deadlocks during synchronous waits.

DN8 — **.NET 8/9 features**: 
- **Primary constructors**: `public class MyService(IOptions<Config> config, ILogger<MyService> logger) { ... }` (compiler auto-generates backing fields).
- **Collection expressions**: `[1, 2, 3]`, `[.. array]`, `[.. list, 4]` for concise array/list creation.
- **FrozenDictionary**: Immutable, perfect-hashing optimized for static lookups (config, routing).
Example:
```csharp
public class MyService(IOptions<Config> config, ILogger<MyService> logger) : IDisposable {
    public void DoWork() => logger.LogInformation(config.Value.Key);
}
```

DN9 — **ObjectDisposedException on DbContext under high concurrency**: Likely cause: `DbContext` is registered as `Transient` or `Singleton`, or resolved outside the HTTP request scope. EF Core's `DbContext` is thread-unsafe and tracks state per request. Fix: Register as `services.AddScoped<MyDbContext>()` and ensure it's resolved within the request pipeline. EF Core relies on DI scoping to isolate change tracking and connection management per request.

DN10 — **record vs class, record struct**: `record` is a reference type with value-based equality, immutable by default, positional syntax. `class` is mutable, reference-equality, supports inheritance. `record struct` is a value type with value equality, immutable, no inheritance. Choose `record` for DTOs/domain events, `class` for mutable entities/inheritance-heavy designs, `record struct` for small, performance-critical immutable data.

DN11 — **ref, out, in**: `ref`: pass by reference, requires initialization, read/write. `out`: pass by reference, must be assigned in method, caller doesn't need init. `in`: pass by reference, read-only, prevents copying large structs. Use `ref` for modifying existing values, `out` for multiple returns/parsing, `in` for performance with large structs.

DN12 — **Nullable reference types vs value types**: NRT (`string?`) is a compile-time warning system for reference types to prevent null reference exceptions. `#nullable enable` activates it. Nullable value types (`int?`) are actual CLR `Nullable<T>` types with runtime null support. NRT is erased at runtime; value types retain null capability.

DN13 — **LINQ, method vs query syntax, deferred execution**: LINQ unifies querying across data sources. Method syntax (`list.Where(...).Select(...)`) is fluent and preferred for complex chains. Query syntax (`from x in list where ... select ...`) is SQL-like and compiles to method syntax. Deferred execution means the query isn't executed until enumerated (e.g., `foreach`, `.ToList()`), enabling composition and lazy evaluation.

DN14 — **Generic constraints**: `where T : class` (reference type), `where T : struct` (non-nullable value type), `where T : new()` (parameterless constructor), `where T : IComparable<T>` (implements comparison). Combine when you need multiple capabilities (e.g., `where T : class, IComparable<T>, new()`). Use to enable type-safe algorithms, collections, or serialization without boxing/casting.

DN15 — **abstract class vs interface, default methods**: Abstract classes can hold state, constructors, and non-virtual methods; support single inheritance. Interfaces define contracts; support multiple inheritance. C# 8+ default interface methods allow interfaces to contain implementations, bridging the gap by enabling backward-compatible API additions. Interfaces still cannot hold instance state.

DN16 — **Middleware pipeline, Use/Map/Run, ordering, exception handling**: Middleware processes requests sequentially. `app.Use()` adds middleware to the pipeline. `app.Map()` branches based on path prefix. `app.Run()` is terminal (no `next`). Ordering matters: auth before routing, error handling early, static files before MVC. `app.UseExceptionHandler()` catches unhandled exceptions, logs, and returns error responses; place it early to catch downstream failures.

DN17 — **Channel<T> vs BlockingCollection<T>**: `Channel<T>` is modern, async-first, supports bounded/unbounded modes, built-in backpressure, and high performance. `BlockingCollection<T>` is synchronous, wraps concurrent collections, less flexible for async. Example (bounded channel):
```csharp
var channel = Channel.CreateBounded<int>(new BoundedChannelOptions(10) { FullMode = BoundedChannelFullMode.Wait });
// Producer: await channel.Writer.WriteAsync(value);
// Consumer: await foreach (var item in channel.Reader.ReadAllAsync()) { ... }
```
Backpressure: Writer blocks when buffer is full, preventing memory exhaustion.

DN18 — **Source Generators, Incremental vs ISourceGenerator**: Source generators compile-time code generation using Roslyn, outputting C# source. Faster/safer than reflection (runtime) and IL weaving (modifies compiled IL). `ISourceGenerator` regenerates on every build. Incremental generators (`ISourceGenerator` replacement) support caching, incremental compilation, and MSBuild integration. Preferred for large projects due to faster rebuilds and better IDE support.

DN19 — **TPL Dataflow vs Channels**: TPL Dataflow builds message-passing pipelines. `BufferBlock<T>` stores messages manually. `TransformBlock<TIn,TOut>` processes and outputs. `ActionBlock<T>` processes without output. Compared to `Channels`, Dataflow offers richer composition (fan-out/in, completion propagation, backpressure policies), better for complex pipelines. Channels are simpler, async-first, and better for straightforward producer-consumer patterns.

DN20 — **Minimal APIs vs Controllers**: Minimal APIs are lightweight, inline routing/handlers, less boilerplate, faster startup. Controllers use attributes, constructor DI, better for complex apps, easier to test/mock, richer OpenAPI/Swagger support. Trade-offs: Minimal APIs sacrifice some testability/middleware flexibility for speed. Route groups (`app.MapGroup("/api")`) share metadata. Endpoint filters (`builder.AddFilter(...)`) handle cross-cutting concerns (auth, validation) at the endpoint level.

P1 — **list vs tuple, set vs frozenset**: Lists are mutable, ordered, indexed, allow duplicates. Tuples are immutable, ordered, fixed-size, heterogeneous, unpackable. Sets are mutable, unordered, unique elements. Frozensets are immutable sets, hashable, usable as dict keys or set members.

P2 — **GIL**: Global Interpreter Lock allows only one thread to execute Python bytecode at a time. Affects CPU-bound multithreading (no true parallelism). I/O-bound workloads benefit (threads release GIL during I/O). Workarounds: Multiprocessing, C extensions (release GIL), `asyncio`, `concurrent.futures.ProcessPoolExecutor`, or alternative interpreters (PyPy, Jython).

P3 — **deepcopy vs copy**: `copy.copy()` creates a shallow copy (new container, same nested objects). `copy.deepcopy()` recursively copies all nested objects. Shallow copy causes unexpected behavior when nested mutable objects are modified: `a = [[1]]; b = copy.copy(a); b[0].append(2); print(a)` → `[[1, 2]]`.

P4 — **Decorators, execution time**: Decorators wrap functions to extend behavior. Example:
```python
import time, functools
def log_time(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — **Generators, yield, yield from**: Generators use `yield` to produce values lazily, maintaining state and using constant memory. Unlike lists, they don't store all values in memory. `yield from` delegates to another generator, replacing nested loops with cleaner syntax: `yield from subgen()`.

P6 — **asyncio event loop, run/gather/create_task, time.sleep**: Event loop manages async tasks and I/O. `asyncio.run()` creates loop, runs coroutine, closes loop. `asyncio.gather()` runs multiple coroutines concurrently, returns results. `asyncio.create_task()` schedules background execution. `time.sleep()` blocks the entire thread/event loop; use `await asyncio.sleep()` to yield control.

P7 — **MRO, C3 linearization, diamond inheritance**: MRO defines method lookup order. Python 3 uses C3 linearization. Diamond inheritance (`D(B, C)` where `B,C` inherit `A`) resolves to `D -> B -> C -> A`. `B` doesn't override `who`, `C` does. `D().who()` calls `C.who()`, printing `"C"`.

P8 — **Metaclass vs __init_subclass__**: Metaclass controls class creation (`__new__`, `__init__`), powerful but complex. `__init_subclass__` is a class method called when a subclass is created, simpler for instance-level customization. Use metaclass for framework-level registration/validation. Use `__init_subclass__` for plugin registration or automatic method wrapping without metaclass complexity.

P9 — **multiprocessing vs threading vs concurrent.futures**: Threading: I/O-bound, shares memory, GIL limits CPU parallelism. Multiprocessing: CPU-bound, separate processes, bypasses GIL, higher overhead. `concurrent.futures`: High-level API wrapping both via `ThreadPoolExecutor`/`ProcessPoolExecutor`. Multiprocessing uses `pickle` for serialization; objects must be picklable. Lambdas, open handles, and some C extensions fail pickling.

P10 — **__slots__**: Declares fixed attributes, prevents `__dict__` creation. Use for memory-critical apps with many instances. Prevents dynamic attribute addition and `__dict__`/`__weakref__` (unless explicitly included). Memory impact: Significant per-instance reduction (no dict overhead), but adds class-level overhead.

P11 — **Virtual environments, venv vs virtualenv vs conda**: Virtual envs isolate Python packages/interpreter per project. Prevents dependency conflicts and ensures reproducibility. `venv`: Standard library, lightweight, Python 3.3+. `virtualenv`: Third-party, older, cross-platform. `conda`: Package + environment manager, handles non-Python dependencies, data-science focused.

P12 — **Comprehensions vs map/filter**: Comprehensions (`[x for x in lst if x > 0]`, `{k:v for k,v in d}`, `{x for x in lst}`) are concise, Pythonic, and often faster. `map()`/`filter()` return iterators, can be slower due to function call overhead. Prefer comprehensions for readability/performance. Use `map`/`filter` for lazy evaluation chains or when working with existing functions.

P13 — **== vs is, object interning**: `==` checks value equality (`__eq__`). `is` checks identity (same memory address). Python interns small integers (-5 to 256) and some strings for performance. `a is b` returns `True` for small ints because they reference the same cached object. Not guaranteed for larger integers.

P14 — **\*args, \*\*kwargs, /, \***: `*args` collects extra positional args into a tuple. `**kwargs` collects extra keyword args into a dict. `/` marks positional-only parameters. `*` marks keyword-only parameters. Use for flexible APIs, function wrappers, and enforcing calling conventions.

P15 — **Context managers**: Ensure setup/teardown via `with`. Class-based: implement `__enter__`/`__exit__`. Generator-based: use `@contextmanager`. Example (DB session):
```python
from contextlib import contextmanager
@contextmanager
def db_session():
    conn = get_connection()
    try: yield conn
    finally: conn.close()
```

P16 — **Type hinting, Union, Optional, Literal, TypeVar, Protocol**: Static annotations for tooling, not runtime-enforced. `Union[A, B]`: either type. `Optional[T]` = `Union[T, None]`. `Literal["x"]`: exact value match. `TypeVar`: constrained generic variable. `Protocol`: structural subtyping (duck typing). `mypy`/`pyright` parse annotations, check types statically, catch bugs pre-runtime.

P17 — **Data model (dunder methods)**: `__repr__`: unambiguous, dev-focused. `__str__`: readable, user-focused. `__eq__`: equality. `__hash__`: hash value. `__getattr__`: fallback for missing attrs. `__getattribute__`: intercepts all attr access. Defining `__eq__` without `__hash__` sets `__hash__ = None`, making instances unhashable (can't be dict keys/set members).

P18 — **Descriptors**: Objects implementing `__get__`, `__set__`, `__delete__` that control attribute access. `property` uses descriptors for getters/setters. `classmethod`/`staticmethod` are descriptors that modify `self`/`cls` binding. Under the hood, `__getattribute__` checks for descriptors on the class; if found, descriptor protocol takes precedence over instance `__dict__`.

P19 — **Import system**: Relative imports (`from . import mod`) resolve relative to package. Absolute imports (`from pkg import mod`) resolve from `sys.path`. `PYTHONPATH` prepends to `sys.path`. `__init__.py` marks packages and runs on import. Namespace packages lack `__init__.py`, allowing split packages. Finders locate modules in `sys.path`; loaders execute module code. `importlib` standardizes this.

P20 — **dataclasses vs attrs vs Pydantic**: `dataclasses` (built-in) generates `__init__`, `__repr__`, `__eq__`, `__hash__`. Simple, fast. `attrs` (third-party) adds validators, converters, slots, faster in some cases. `Pydantic` adds validation, serialization, type coercion, integrates with FastAPI. `__post_init__` runs after init. `field(default_factory=list)` avoids mutable default bug. `frozen=True` enables immutability. Inheritance works but requires careful `__post_init__` handling. Choose Pydantic for validation/API integration; dataclasses for simple, fast DTOs.
