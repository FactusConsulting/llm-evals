SC1-A
The pods fail because the Restricted Pod Security Standard (PSS) explicitly forbids running containers as root (`runAsUser: 0`). `runAsNonRoot: true` without an explicit `runAsUser` instructs the kubelet to assign a random non-zero UID at runtime. However, the new base image (`cgr.dev/chainguard/static:latest`) sets `USER root` in the Dockerfile. When the container runtime attempts to start, it either: (1) the image's `USER root` overrides the random UID, causing PSS admission/runtime rejection, or (2) the random UID lacks filesystem permissions expected by the app, causing immediate crashes. Baseline PSS only forbids privileged containers and host namespaces; it allows root. Restricted PSS enforces `runAsUser: >0`, `runAsNonRoot: true`, and drops all capabilities. The upgrade shifted the namespace policy from Baseline to Restricted, exposing the mismatch between the image's default user and the policy.

SC1-C
**Immediate Fix:** Update images to include `RUN adduser -D appuser` and `USER appuser`. Add `runAsUser: 1000` to pod/container `securityContext`.
**Manifest Changes:** Enforce `runAsUser` and `runAsNonRoot` in deployment specs. Add `securityContext.fsGroup` if needed for volume permissions.
**CI Gate:** Add a PSS admission controller (Kyverno/OPA) that rejects deployments missing `runAsUser: >0`. Add a Trivy/Grype scan that fails if base image defaults to root or lacks a non-root user. Pin base images by digest.
**Rollout:** Use a rolling update with `maxSurge=25%` and `maxUnavailable=0`. Deploy updated images to a canary namespace first, validate with synthetic checks, then promote. Monitor `kubectl get pods -w` and alert on `CrashLoopBackOff` or `OOMKilled`.

SC2-A
Promoting a cross-region async replica causes data loss equal to the replication lag at promotion time. PostgreSQL ships WAL asynchronously; the replica replays WAL at its own pace. During the outage, WAL shipping paused or lagged, so unshipped transactions are permanently lost. To quantify: query `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica, check `pg_stat_replication` for `lag` columns, and review application logs for replication delay metrics. The data loss window = time between last committed transaction on primary and last replayed WAL on replica.

SC2-B
1. Import the promoted replica into state: `terraform import aws_db_instance.promoted_replica <new-arn>`
2. Rename the old resource in state to avoid conflicts: `terraform state mv aws_db_instance.old aws_db_instance.promoted_replica_old`
3. Update Terraform code: replace hardcoded ARNs with `aws_db_instance.promoted_replica.arn` or data sources.
4. Detach old instance: `terraform state rm aws_db_instance.promoted_replica_old`
5. Verify no destroy/create: `terraform plan` (should show only attribute updates or no changes).
6. Apply: `terraform apply` to update dependent resources (security groups, Route53, parameter groups) to reference the new ARN.

SC2-C
**Connection Management:** Use RDS Proxy instead of PgBouncer. RDS Proxy handles connection pooling, failover transparency, and automatic reconnection without app changes.
**DNS Failover:** Route53 failover routing policy with health checks on the RDS endpoint. Update app config to use the Route53 alias.
**Retry Logic:** Implement exponential backoff with jitter in the app driver. Use circuit breakers to fail fast during prolonged outages.
**RPO < 1s:** Standard RDS async replication cannot guarantee this. Use PostgreSQL synchronous replication (`synchronous_commit = on`, `synchronous_standby_names = 'standby1'`) or Aurora Global Database. Aurora Global DB is recommended: it uses a single primary cluster with up to 5 secondary clusters, optimized cross-region replication, sub-second RPO, and automated failover with <1 min RTO. It abstracts WAL shipping and reduces operational complexity.

```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid,
       blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS current_statement_in_blocking_process
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC6-C
**Direct Connect:** Dedicated 10Gbps+ link. Low latency, high throughput, predictable cost. Requires on-prem router upgrade. Fits ZT if combined with IPsec/TLS overlay. Routing: BGP peering, static routes to TGW.
**Second VPN + ECMP:** Cheap, scales bandwidth linearly. Encryption overhead (~20-30%). Failover via BGP/ECMP. Routing: dual tunnels, equal-cost multipath, health checks.
**Tailscale/Netbird:** WireGuard mesh, zero-config, ZT-native. Low cost, bandwidth depends on DERP/relay or direct P2P. Routing: subnet routers, tailnet DNS, automatic service discovery. Best for rapid deployment, but may not meet strict compliance/throughput needs without enterprise features.
**Recommendation:** Direct Connect for primary backbone, Tailscale/Netbird for management/DR overlay. ECMP VPN as fallback.

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks (ping, TCP, app heartbeat) across sites. Site down = 3 consecutive failures + etcd quorum loss.
2. **DNS Failover:** GSLB (Route53/Azure DNS) switches traffic to Dallas. TTL <60s.
3. **Patroni Promotion:** etcd triggers synchronous standby promotion. `synchronous_commit` ensures zero loss.
4. **Redis Sentinel:** Sentinel detects master down, promotes replica.
5. **RabbitMQ:** Federation/shovel catches up, quorum queues elect new leader.
