AA1: A monolith is a single codebase deployed as one unit with shared memory/process. Microservices are independently deployable, loosely coupled services communicating over a network. Microservices introduce: (1) network latency & failure handling, (2) distributed data consistency challenges, (3) operational complexity (orchestration, CI/CD, observability, debugging).

AA2: Synchronous communication blocks the caller until a response is received (tight coupling, immediate feedback). Example: REST/gRPC. Asynchronous communication decouples sender/receiver; messages are processed later (eventual processing, burst handling). Example: RabbitMQ/Kafka.

AA3: A reverse proxy routes traffic, handles TLS termination, load balancing, and basic caching. An API gateway adds API-specific logic: rate limiting, auth, versioning, request transformation, and developer portal features. An API gateway can replace a reverse proxy functionally, but they’re often layered: a lightweight reverse proxy (nginx/envoy) at the edge for TLS/SSL, with an API gateway handling business routing. Replacing entirely is possible but sacrifices edge-optimized performance.

AA4: The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a step fails. Choreography uses events to trigger the next step (decentralized, simpler for linear flows, harder to trace). Orchestration uses a central coordinator directing steps (better for complex/conditional flows, easier debugging, introduces a control dependency). Use choreography for simple, loosely coupled workflows; orchestration for complex, multi-step, conditional business processes.

AA5: CQRS separates read and write operations into different models. Event Sourcing stores state as an immutable sequence of events. They’re paired because events naturally drive read-model projections, providing a single source of truth. This solves CRUD’s limitations: independent read/write scaling, full auditability, temporal queries, and handling complex concurrency/domain logic where direct state mutation fails.

AA6: The Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (threshold breached, fail fast), Half-Open (tests recovery). Differs from retry: retry attempts immediate recovery; circuit breaker halts requests to prevent overload. Use both: retry with exponential backoff for transient failures within the Closed state; circuit breaker when failures persist to avoid hammering a down service.

AA7: 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, easiest ops.
2. Shared DB, separate schema: Moderate cost, better isolation, easier per-tenant backup/restore, moderate ops.
3. Separate DB per tenant: Highest cost, best security/isolation, simplest backup/restore/migration, highest ops complexity.
Trade-offs scale linearly: cost & ops complexity increase, while security & noisy-neighbor risk decrease.

AA8: Eventual consistency allows stale reads during propagation; strong consistency guarantees immediate visibility. For inventory oversell prevention: use strong consistency (or linearizable reads/writes). Architecture: dedicated inventory service with a strongly consistent store (CockroachDB, Spanner, or PostgreSQL with row-level locking). Patterns: optimistic concurrency control with version numbers, short-lived reservation/hold queues, and idempotent checkout transactions. Partition by SKU to limit lock contention at scale.

AA9: A sidecar proxy co-locates with a service, intercepting all traffic. In Istio, Envoy acts as the data plane proxy handling routing, load balancing, mTLS, and observability. The control plane (Istiod) pushes config and rotates certs. mTLS solves: transparent east-west security without app code changes, automatic cert rotation, service identity verification, and protection against MITM in untrusted networks. App TLS requires manual cert management and doesn’t secure internal traffic automatically.

AA10: The Strangler Fig pattern incrementally replaces monolith functionality by routing traffic to new services until the old system is decommissioned. Strategy: deploy .NET 8 microservices alongside the legacy app. Use an API gateway/reverse proxy to route specific endpoints/URLs to new services. Start with low-risk, independent modules (e.g., notifications, user profiles). Implement dual-write or CDC for data migration. Gradually shift traffic, validate, and decommission legacy routes. Shut down monolith once all functionality is migrated.

AA11: 12-Factor App methodology ensures cloud-native portability and scalability. Six factors: (1) Codebase (one repo, many deploys), (2) Dependencies (explicitly declared/isolated), (3) Config (env vars, never in code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strictly separate stages), (6) Processes (stateless, execute in containers). They matter because they prevent config drift, enable horizontal scaling, simplify CI/CD, and ensure environment parity.

AA12: 
- Coupling: Event-driven = loose (producers/consumers unaware); Request-driven = tight (caller knows endpoint).
- Scalability: Event-driven = highly scalable, handles bursts, async processing; Request-driven = scales linearly, synchronous bottlenecks.
- Debugging: Event-driven = complex (distributed traces, replay needed); Request-driven = straightforward (request/response logs).
- Ordering: Event-driven = partition-level guaranteed, global not always; Request-driven = naturally ordered per request.
- Failure: Event-driven = retry, dead-letter queues, idempotency; Request-driven = timeouts, retries, circuit breakers.
Choose event-driven for async workflows, high throughput, decoupled systems, event sourcing. Choose request-driven for real-time APIs, simple CRUD, strict latency requirements.

AA13: A load balancer distributes traffic across multiple servers. Layer 4 balances by IP/port (fast, no content inspection). Layer 7 balances by content (URL, headers, cookies, SSL). Layer 7 is required for content-based routing (e.g., routing `/api/v1` vs `/api/v2` to different backends) or SNI-based TLS termination.

AA14: A message queue (RabbitMQ) uses point-to-point/pub-sub, consumes/deletes messages, and supports complex routing. A log-based broker (Kafka) appends messages to immutable logs, persists them, and allows multiple consumers to read at their own pace. Pick RabbitMQ for task distribution, complex routing, low latency. Pick Kafka for event streaming, replayability, high throughput, and decoupled data pipelines.

AA15: Containers share the host OS kernel, isolate processes/filesystems, and start instantly. VMs run a full guest OS under a hypervisor, are heavier, and slower. Containers are popular for microservices due to fast deployment, consistent environments, efficient resource usage, and native orchestration support (Kubernetes).

AA16: Stateless services hold no local session data; any instance can handle any request. Stateful services maintain local state/session and require pinning. Stateless services scale horizontally easily because no session affinity is needed, allowing dynamic add/remove and even load distribution. Examples: Stateless = web API, Redis; Stateful = PostgreSQL, Kafka.

AA17: An ORM maps database tables to application objects, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORM = faster development, type safety, DB portability, but can generate inefficient queries and complicate complex optimizations. Raw SQL = full performance control, easier optimization, but more boilerplate, DB-specific, and harder to maintain.

AA18: The Bulkhead pattern isolates resources so a failure in one component doesn’t exhaust resources for others. It prevents cascading failures in microservices by partitioning thread pools, connections, or deployments. Implementation: allocate separate thread pools/connection pools per downstream service call. Alternatively, deploy critical vs non-critical services on separate node pools/availability zones with independent resource quotas.

AA19: OT requires a central server to transform conflicting operations; strong consistency, low online latency, complex server logic, poor offline support. CRDTs are mathematical structures that converge automatically; eventual consistency, higher message size/latency, simpler client logic, excellent offline support. Choose CRDTs for offline editing: they allow concurrent local edits without server sync, merge automatically on reconnect, and avoid complex transformation logic.

AA20: Challenges include polyglot instrumentation, network hops, async boundaries, and overhead. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject/extract trace IDs across HTTP/gRPC. Sampling: head-based (random, simple, loses context) vs tail-based (collects all, samples after, accurate but high storage). Storage/querying: Jaeger (OpenTelemetry) or Tempo (Grafana, S3-backed) index spans for trace ID/service queries. For Kafka: producers inject trace context into message headers, consumers extract and continue the trace. Use tail-based sampling with consumer groups and ensure idempotent context propagation to maintain continuity across async boundaries.

OP1: Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and low overhead. Examples: VMware ESXi, Proxmox VE, KVM, Hyper-V. Type 2 (hosted) hypervisors run as applications on a host OS, offering ease of use but higher overhead. Examples: VirtualBox, VMware Workstation, Parallels.

OP2: SAN provides block storage, presenting disks directly to servers for high performance/low latency. Protocols: Fibre Channel, iSCSI. NAS provides file storage over a network, enabling easy sharing. Protocols: NFS, SMB/CIFS. Use SAN for databases, VMs, and performance-critical workloads. Use NAS for file shares, backups, and home directories.

OP3: 3-tier architecture uses Core (high-speed backbone), Distribution (policy/routing), and Access (edge/ports). Leaf-spine replaces this with a full mesh between leaf (access) and spine (core) layers. It solves 3-tier bottlenecks by providing predictable low latency, eliminating oversubscription, and scaling horizontally by adding spines/leaves without redesign.

OP4: Use 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing (STONITH via IPMI/iLO) powers off failed nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. On node failure: HA manager detects failure, fences the node, and restarts VMs on healthy nodes using shared storage.

OP5: VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, `ip link set eth0.10 up`, assign IP. Alternatively, use Netplan/NetworkManager with VLAN interfaces.

OP6: RAID 1: mirror, 50% capacity, 2-drive fault tolerance. RAID 5: stripe+parity, 1-drive fault, read fast, write penalty. RAID 6: double parity, 2-drive fault, higher write penalty. RAID 10: mirror+stripe, 50% capacity, 2-drive fault (different mirrors), best perf. Z2 (ZFS): double parity, self-healing, snapshots, similar to RAID 6 but with data integrity features. Choice: RAID 10 for raw DB write performance, or Z2 if leveraging ZFS for snapshots, compression, and self-healing.

OP7: Recursive resolvers: internal DNS servers (Windows DNS/Bind) for clients. Authoritative: internal zone for AD, external zone for public. Forwarders: point to ISP/Cloudflare for external resolution. Conditional forwarding: routes internal AD zones to internal DNS, external to forwarders. Split-horizon: internal DNS returns private IPs, external returns public. DNSSEC: signs external zone, chains to root. Laptop roaming: DHCP assigns internal DNS. VPN uses split tunneling/conditional forwarding to route internal queries to HQ DNS. Roaming clients rely on cached records or dynamic updates.

OP8: PKI chain: Root CA (offline, self-signed, long-lived) -> Subordinate CA (online, issues certs, shorter life) -> End-entity cert. Trust anchored in root. CRL = downloaded revocation list; OCSP = real-time status check. Templates define cert properties (key usage, EKU, auto-enrollment). Auto-enrollment lets Windows clients request/renew certs automatically. Compromised subordinate: issue fake certs, but root can revoke it. Compromised root: catastrophic, requires rebuilding entire PKI and updating all trust stores.

OP9: MPLS: high reliability, low latency, expensive, carrier-managed. IPsec VPN: cheap, internet-based, variable latency, manual config. SD-WAN: app-aware routing, QoS, centralized management, cost-effective over internet/MPLS. WireGuard mesh: modern crypto, fast, simple, lacks enterprise QoS/SLA/centralized mgmt. Recommendation: SD-WAN. Best balance of cost, reliability, VoIP QoS, centralized management, and security for 50-user sites.

OP10: iDRAC (Dell), iLO (HPE), IPMI: out-of-band management interfaces for remote server control. Critical for accessing servers when OS/network is down, power cycling, console access, and firmware updates. Internet exposure: high risk of brute force, credential theft, remote compromise, ransomware, and server hijacking. Should be isolated on a dedicated management network.

OP11: LVM: traditional volume manager, fixed-size volumes, snapshots consume space. LVM-Thin: overprovisions storage, space-efficient snapshots, but performance degrades if thin pool fills. ZFS: integrated FS+volume manager, copy-on-write, self-healing, instant/zero-space snapshots, clones. Use LVM for simple Linux setups, LVM-Thin for flexible overprovisioning, ZFS for data integrity and advanced enterprise features.

OP12: Ceph CRUSH rules distribute OSDs across failure domains (host, rack, site). Monitor placement: odd number, geographically distributed, low latency within site. Network latency: <10ms within site, <100ms between sites. Split-brain: both sites write independently, causing data corruption. 2-site Ceph without a tiebreaker is bad because neither site holds quorum; both can become primary, diverging data. A 3rd site or disk witness breaks ties and enforces quorum.

OP13: DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable: client uses APIPA (169.254.x.x) or retries. Windows lease expiry: attempts renewal at 50% (T1) and 87.5% (T2). If failed, reverts to APIPA or requests a new lease.

OP14: Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP, ACLs, and link aggregation. Enterprise importance: network segmentation, traffic prioritization, loop prevention, monitoring, and security enforcement.

OP15: NTP synchronizes clocks over a network. Critical for log correlation, Kerberos auth, distributed transactions, cluster health, and forensics. Clock drift consequences: Kerberos auth failures, split-brain in clusters, log timeline corruption, database replication lag, false monitoring alerts.

OP16: Physical servers run directly on hardware (max performance, no virtualization overhead). VMs provide full OS isolation (heavier, good for legacy/OS-level isolation). Containers isolate processes (lightweight, fast, shared kernel). Run bare metal for databases, HPC, low-latency trading, GPU/NIC passthrough, or compliance requirements.

OP17: UPS provides battery backup for short outages, conditions power, and bridges to generators. Generators provide long-term power via fuel. Both are needed: UPS covers immediate gap and protects sensitive gear; generator sustains operations. ATS (Automatic Transfer Switch) automatically switches load from utility to generator during outages and back when utility returns.

OP18: Active-passive: one node handles traffic, standby takes over on failure. Active-active: both handle traffic, require sync and split-brain prevention. PostgreSQL HA with Pacemaker/Corosync: STONITH fencing kills failed nodes. Virtual IP (VIP) floats to active node. Patroni/repmgr handles replication. On failure: Pacemaker fences node, promotes standby, moves VIP, starts DB.

OP19: 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO define acceptable data loss and downtime. Backup types: full (baseline), incremental (changes since last), differential (changes since last full). Deduplication reduces storage and backup windows. Media: disk (fast restore), tape (cheap long-term), cloud (offsite/scalable). Immutable backups: WORM storage prevents ransomware deletion. Testing: regular restore drills, verify integrity, measure RTO/RPO. Backup = data protection; DR = full recovery process (infrastructure, data, procedures) to resume operations.

OP20: 802.1X is port-based NAC. Roles: Supplicant (client), Authenticator (switch/AP), Auth Server (RADIUS). EAP-TLS: cert-based, mutual auth, highly secure. PEAP: username/password, tunneled, easier deployment. RADIUS handles auth/authorization/accounting. Dynamic VLAN: auth server returns VLAN ID, switch assigns port. Failure: port stays unauthorized, traffic blocked, falls back to guest VLAN/MAB. MAB: uses MAC address as credential, assigns to default VLAN, bypasses 802.1X for non-compliant devices.
