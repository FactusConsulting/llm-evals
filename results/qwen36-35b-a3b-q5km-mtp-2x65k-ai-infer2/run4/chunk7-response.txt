AA1 — Monoliths are single, unified codebases deployed as one unit with shared memory/process. Microservices are independently deployable, loosely coupled services with separate codebases, databases, and processes. Three concrete problems microservices introduce: (1) Distributed system complexity (network latency, partial failures, distributed tracing), (2) Operational overhead (CI/CD pipelines, service discovery, monitoring, config management for dozens/hundreds of services), (3) Data consistency challenges (no ACID across services, requiring eventual consistency, sagas, or compensating transactions).

AA2 — Synchronous communication blocks the caller until a response is received, creating tight coupling and latency dependency. Example: REST/HTTP or gRPC. Asynchronous communication decouples producer and consumer; messages are queued and processed later without blocking. Example: RabbitMQ or Kafka. Async improves fault tolerance and scalability but introduces eventual consistency and message ordering/delivery guarantees to manage.

AA3 — A reverse proxy routes traffic to backend servers, handling TLS termination, load balancing, and caching at the network/transport layer. An API gateway adds API-specific logic: rate limiting, authentication, request/response transformation, versioning, and developer portal integration. An API gateway can replace a reverse proxy in many modern stacks, but reverse proxies (Nginx, Traefik) are still preferred at the edge for high-performance static content, DDoS mitigation, or when API gateway overhead is unnecessary. They often work together (reverse proxy at edge → API gateway at app layer).

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a later step fails. Choreography-based sagas use events to trigger the next step; services are decentralized and loosely coupled, making them ideal for simple, stable workflows but hard to monitor/debug. Orchestration-based sagas use a central coordinator that sends commands to participants; better for complex, stateful, or regulated flows, easier to monitor, rollback, and version.

AA5 — CQRS separates read and write operations into distinct models: commands modify state, queries read optimized views. Event Sourcing stores state as an immutable sequence of domain events. Combined, they solve: (1) Read/write scaling divergence (independent scaling), (2) Complete auditability and temporal queries (replay events to any point in time), (3) Complex domain modeling without CRUD impedance mismatch. Traditional CRUD struggles with high-throughput reads/writes, historical state reconstruction, and audit trails.

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. Three states: Closed (normal, requests pass), Open (failure threshold met, requests fail fast), Half-Open (tests recovery with limited traffic). Differs from retry/backoff: retry assumes transient failure and attempts recovery; circuit breaker assumes persistent failure and halts requests to avoid resource exhaustion. Use both together: retry/backoff handles transient network glitches within the closed state; circuit breaker engages when failures persist to protect system stability.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, easiest ops.
2. Shared DB, separate schema: Moderate cost, better isolation/backups, moderate ops complexity, reduced noisy-neighbor impact.
3. Separate DB per tenant: Highest cost, best security/isolation, easiest per-tenant backup/restore, highest ops complexity.
Trade-offs: Cost scales inversely with isolation. Security and noisy-neighbor risk improve with separation. Operational complexity and cost increase with tenant isolation.

AA8 — Eventual consistency allows stale reads during propagation; strong consistency guarantees immediate visibility of writes. For inventory oversell prevention: use strong consistency (or linearizable reads/writes). Data store: Relational DB (PostgreSQL) or strongly consistent distributed DB (CockroachDB). Patterns: Optimistic concurrency (version columns), distributed locks (Redlock), or reservation/hold pattern with TTL. At scale: partition inventory by SKU/warehouse, enforce strong consistency per partition, and use async replication only for non-critical reads.

AA9 — A sidecar proxy is a co-located container that intercepts all inbound/outbound traffic for the main app. In Istio, Envoy handles L7 routing, mTLS, retries, circuit breaking, and observability. Data plane = Envoy proxies forwarding traffic. Control plane = Istiod managing config, pushing updates to proxies. mTLS between sidecars solves: transparent service-to-service authentication without code changes, automatic cert rotation, uniform security policy enforcement, and protection against internal eavesdropping that application-level TLS misses (since app TLS only secures external endpoints).

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality with new services, routing traffic gradually until the legacy system is decommissioned. Strategy: Place an API gateway in front of the .NET Framework monolith. Identify a bounded context (e.g., user management). Build a .NET 8 microservice. Configure gateway to route `/users/**` to the new service. Update monolith to delegate or remove the endpoint. Repeat per context. Use feature flags for safe rollout. Monitor metrics, then decommission monolith routes until only the new architecture remains.

AA11 — 12-Factor App is a methodology for building SaaS/cloud-native apps. Six factors: (1) Codebase (one code, many deploys), (2) Dependencies (explicitly declare, no implicit system deps), (3) Config (store in env vars, never in code), (4) Backing services (treat as attached resources, replaceable), (5) Build/release/deploy (strictly separate stages), (6) Processes (stateless, concurrent, disposable). They matter because they ensure portability, predictable deployments, horizontal scalability, and resilience in cloud environments.

AA12 — 
- Coupling: Event-driven = loose (producers/consumers unaware); Request-driven = tight (direct dependency).
- Scalability: Event-driven = high (async, backpressure, replay); Request-driven = moderate (sync bottlenecks, connection limits).
- Debugging: Event-driven = complex (distributed state, ordering, replay); Request-driven = simpler (request/response tracing).
- Ordering: Event-driven = partition-level guaranteed; Request-driven = per-request only.
- Failure: Event-driven = durable, retry/replay, eventual consistency; Request-driven = immediate failure, requires retries/circuit breakers.
Choose event-driven for async workflows, high throughput, decoupled systems. Choose request-driven for real-time APIs, synchronous CRUD, and simple integrations.

AA13 — A load balancer distributes incoming traffic across multiple backend servers. Layer 4 routes by IP/port (TCP/UDP), stateless and fast. Layer 7 routes by HTTP headers, URLs, cookies, stateful and slower. Layer 7 is required for content-based routing (e.g., `/api/v1` → service A, `/static` → CDN), SSL termination, WAF integration, or A/B testing.

AA14 — A message queue (RabbitMQ) uses point-to-point or pub/sub with exchanges, consumes/deletes messages after processing, and excels at task routing and reliable delivery. A log-based broker (Kafka) is an append-only log, persists messages, allows multiple consumers to read at their own pace, and supports replay. Pick RabbitMQ for task queues, command routing, and strict delivery. Pick Kafka for event streaming, log aggregation, real-time analytics, and replayability.

AA15 — Containers share the host OS kernel, package binaries/libs, and are lightweight/fast to start. VMs virtualize hardware, run full guest OSes, and are heavier/slower. Containers are popular for microservices because they provide consistent environments, efficient resource utilization, rapid scaling, and native orchestration support (Kubernetes), aligning with cloud-native deployment models.

AA16 — Stateless services store no session data locally; any instance can handle any request. Easier to scale horizontally because adding/removing instances requires no data migration or sticky sessions. Example: REST API, Nginx. Stateful services maintain local session/data. Harder to scale due to replication, partitioning, or affinity requirements. Example: PostgreSQL, Redis, WebSocket server.

AA17 — An ORM maps objects to database tables, abstracting SQL generation. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORM accelerates development, ensures type safety, and improves portability, but can generate inefficient queries, obscure performance bottlenecks, and complicate complex joins/aggregations. Raw SQL offers full control, optimal performance, and DB-specific features, but requires more boilerplate, manual mapping, and is harder to maintain across DB migrations.

AA18 — The Bulkhead pattern isolates resources so a failure in one component doesn't exhaust resources for others. In microservices, it prevents cascading failures and improves resilience. Implementation: Use separate thread pools or connection pools per downstream service (e.g., Spring `@Bulkhead`), deploy critical vs non-critical services in separate K8s namespaces with distinct resource limits/requests, or route traffic through separate message queues. This ensures a slow payment service doesn't starve the inventory service of threads/connections.

AA19 — OT requires a central server to transform concurrent operations, ensuring consistency but introducing latency, complexity, and weak offline support. CRDTs are mathematical structures that converge automatically without coordination, offering strong consistency guarantees, lower latency, and excellent offline support at the cost of higher memory/compute overhead. For offline editing, choose CRDTs: they allow disconnected devices to edit independently and merge seamlessly upon sync without requiring a central server for conflict resolution.

AA20 — Challenges: polyglot instrumentation, overhead, data volume, and context loss across async boundaries. Context propagation: W3C Trace Context (industry standard) or B3 (Zipkin) inject trace/span IDs into headers. Sampling: head-based (random, cheap, loses context), tail-based (collects all, samples post-facto, accurate, high overhead). Storage/querying: Jaeger (OpenTelemetry, indexed), Tempo (Grafana, label-based, object storage). Async/Kafka: trace context must be serialized into message headers. Producers inject via SDK interceptors; consumers extract and continue spans. Continuity requires explicit propagation in all SDKs; without it, traces break across topics.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, managing VMs with minimal overhead. Examples: VMware ESXi, KVM, Proxmox VE. Type 2 (hosted) hypervisors run as applications on a host OS, adding overhead. Examples: VMware Workstation, Oracle VirtualBox. Type 1 is for production/enterprise; Type 2 is for development/testing.

OP2 — SAN provides block-level storage presented as local disks, optimized for databases/VMs. Protocols: Fibre Channel, iSCSI. NAS provides file-level storage over network, optimized for file shares/backups. Protocols: NFS, SMB/CIFS. Use SAN for low-latency, high-IOPS workloads. Use NAS for collaborative file access, backups, and scalable capacity.

OP3 — 3-tier architecture (core/distribution/access) is hierarchical, predictable, but creates core bottlenecks and poor east-west scaling. Leaf-spine is a Clos network where every leaf connects to every spine, providing non-blocking, equal-latency paths. It solves the core bottleneck, supports massive east-west traffic, simplifies cabling, and scales horizontally by adding spines/leaves.

OP4 — Architecture: 3+ nodes (odd for quorum), shared storage (Ceph recommended), Corosync for clustering. Quorum: majority of nodes must agree to prevent split-brain. Fencing: STONITH via IPMI/iDRAC powers off unresponsive nodes. Shared storage: Ceph (distributed, HA) or iSCSI/NFS (centralized, needs HA controller). Node failure: Corosync detects failure, triggers fencing, and VMs restart on surviving nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte tag to Ethernet frames containing the VLAN ID. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, `ip link add link eth0 name eth0.20 type vlan id 20`, assign IPs, enable `net.ipv4.ip_forward=1`, and configure switch port as trunk (802.1Q).

OP6 — RAID 1: mirror, 50% capacity, 1 drive fault. RAID 5: striping+parity, N-1 capacity, 1 drive fault, write penalty. RAID 6: double parity, N-2 capacity, 2 drive fault, higher write penalty. RAID 10: mirror+stripe, 50% capacity, 2 drive fault (different mirrors), high perf. RAID Z2: ZFS double parity, N-2 capacity, self-healing, safe rebuilds. Choice: RAID Z2 for 6 drives. Best balance of capacity, fault tolerance, and database safety due to checksums, no RAID controller dependency, and reliable scrubbing.

OP7 — Recursive resolvers: internal DNS servers for clients. Authoritative: internal zone for AD, external zone for public. Forwarders: point to ISP/Cloudflare for external resolution. Conditional forwarding: routes internal AD zones to internal DNS, external to forwarders. Split-horizon: internal DNS returns private IPs, external returns public IPs for same FQDN. DNSSEC: signs external zone, validates chain to root. Laptop moves: DHCP assigns internal DNS. On VPN, split tunneling/conditional forwarding routes internal queries to HQ DNS. Roaming clients use cached records or DDNS for AD updates.

OP8 — Chain: Root CA (offline, self-signed) → Subordinate/Issuing CA (online, signed by root) → End-entity certs. Root CA: air-gapped, long validity. Subordinate CA: issues certs, shorter validity. CRL: downloaded revocation list. OCSP: real-time status check. Templates: define key usage, validity, auto-enrollment policies. Auto-enrollment: AD CS pushes certs via GPO. Compromise: Subordinate CA = revoke issuing CA, reissue certs, limited blast radius. Root CA = entire PKI trust broken, requires rebuilding chain, massive disruption.

OP9 — MPLS: private, predictable latency, high cost, carrier-managed. IPsec VPN: cheap, internet-based, variable latency, manual config. SD-WAN: orchestrates multiple links, app-aware routing, centralized management, moderate cost. WireGuard mesh: modern crypto, low overhead, requires internet, manual orchestration. Recommendation: SD-WAN. Best balance of cost, reliability, latency optimization (QoS for VoIP), centralized management, and security for 50 users/site.

OP10 — iDRAC (Dell), iLO (HPE), IPMI (standard) are out-of-band management interfaces for remote power, console, and hardware monitoring. Critical for recovery from OS crashes, remote installs, and diagnostics without physical access. Internet exposure: high risk. Attackers can exploit vulnerabilities to gain root, reset passwords, or brick hardware. Should be on isolated management network, behind firewall, with strong auth/2FA.

OP11 — LVM: traditional, fixed-size volumes, snapshots consume space quickly. LVM-Thin: overprovisions storage, cheap/fast snapshots, but risks thin pool exhaustion. ZFS: integrated FS+volume manager, copy-on-write, instant/cheap snapshots, self-healing, checksums. Use LVM for legacy/simple setups. LVM-Thin for VM storage with overprovisioning. ZFS for data integrity, advanced snapshots, and modern Linux storage.

OP12 — Design: 2 sites (primary/secondary), 3 nodes total (2 primary, 1 secondary as tiebreaker/witness). CRUSH rules: place OSDs across sites, ensure replicas span sites. Monitors: 3 monitors (1 per site) for quorum. Latency: <10ms ideal, <15ms acceptable. Split-brain: prevented by odd monitors + tiebreaker. 2-site Ceph without tiebreaker risks split-brain if network partitions, as both sites think they have quorum. Tiebreaker breaks deadlock and ensures single-writer consistency.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable and lease expires: client falls back to APIPA (169.254.x.x), loses network connectivity, and periodically retries DHCP.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, ACLs, and monitoring. Enterprise importance: segmentation, traffic prioritization, loop prevention, security enforcement, and troubleshooting.

OP15 — NTP synchronizes clocks over network. Critical for authentication (Kerberos), logging, distributed transactions, clustering, and certificate validation. Clock drift consequences: cluster split-brain, failed auth, corrupted logs, transaction failures, certificate rejections.

OP16 — Physical: bare hardware, full control. VM: OS virtualization, isolation, overhead. Container: process virtualization, lightweight, shares kernel. Bare metal use: HPC, low-latency trading, databases requiring direct hardware access, GPU passthrough, or regulatory compliance.

OP17 — UPS: short-term battery-backed power, handles outages/transients, runs generators. Generator: long-term fuel-based power, takes minutes to start. Need both: UPS bridges gap until generator starts. ATS: automatically switches load from utility to generator on failure, and back when restored.

OP18 — Active-passive: one node handles traffic, standby takes over on failure. Simple, no split-brain. Active-active: both handle traffic, sync data. Complex, requires distributed DB/app sync. PostgreSQL HA: Pacemaker/Corosync cluster, 2 nodes. STONITH via IPMI fences failed node. Virtual IP floats to active node. Patroni/repmgr handles replication. On failure, STONITH triggers, VIP moves, standby promotes to primary.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO: define by criticality (e.g., RPO 1h, RTO 4h). Backup types: full (baseline), incremental (changes since last), differential (changes since last full). Deduplication: reduces storage, improves backup window. Media: disk for fast restores, tape/cloud for cheap offsite. Immutable backups: WORM/air-gapped, ransomware protection. Test restores: regular drills, automated verification, documented procedures. Backup = data protection. DR = full recovery process (infrastructure, data, procedures, failover).

OP20 — 802.1X roles: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP methods: EAP-TLS (certificate-based, mutual auth, secure), PEAP (username/password, tunneled, common). RADIUS: central auth server, stores credentials, returns access-accept/reject. Dynamic VLAN: switch assigns VLAN based on RADIUS attributes. Failure: port stays unauthorized, blocked traffic, optionally guest VLAN. MAB: switch uses device MAC as username/password for RADIUS auth. Fallback for printers/IoT without 802.1X supplicant.
