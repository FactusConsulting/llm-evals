CL1 — **IaaS, PaaS, SaaS**
- **IaaS (Infrastructure as a Service):** Provider delivers virtualized compute, storage, and networking. Customer manages OS, middleware, runtime, data, and applications. *Example:* AWS EC2.
- **PaaS (Platform as a Service):** Provider manages OS, runtime, and middleware. Customer manages application code and data. *Example:* Google App Engine.
- **SaaS (Software as a Service):** Provider manages everything. Customer consumes the application via browser/client. *Example:* AWS WorkSpaces or Google Workspace.

CL2 — **Shared Responsibility Model**
- **Provider:** Secures the global infrastructure (hardware, facilities, physical security, hypervisor, managed service underlying components).
- **Customer:** Secures data, IAM, OS/network configuration, application code, and encryption keys.
- **IaaS VM:** Provider = physical host, hypervisor, network fabric. Customer = guest OS, patches, firewall, app, data.
- **Managed Kubernetes (EKS/AKS):** Provider = control plane, etcd, node OS/patches, API server. Customer = worker node apps, network policies, RBAC, secrets, data.
- **SaaS (M365):** Provider = app, infra, compliance, patches. Customer = user accounts, data classification, sharing policies, MFA, conditional access.

CL3 — **VPC, Subnet, SG, NACL, Stateful vs Stateless**
- **VPC:** Isolated virtual network with custom IP ranges.
- **Subnet:** IP range within a VPC, confined to one Availability Zone.
- **Security Group (SG):** Instance-level, stateful firewall. Only allow rules. Evaluates return traffic automatically.
- **Network ACL (NACL):** Subnet-level, stateless firewall. Allow/deny rules. Requires explicit rules for both inbound and outbound traffic.
- **Layering:** Traffic enters VPC → hits NACL (subnet boundary) → routed to instance → hits SG (instance boundary). NACLs provide coarse perimeter filtering; SGs provide fine-grained, stateful instance filtering.

CL4 — **Multi-Account Strategy**
- **Landing Zone:** Pre-configured, secure baseline environment with networking, IAM, logging, and guardrails.
- **Organizational Units (OUs):** Group accounts by function/environment (e.g., Sandbox, Dev, Prod, Shared Services, Security).
- **Guardrails:** SCPs/Policy Frameworks enforcing compliance, budget caps, region restrictions, and mandatory controls.
- **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) for centralized inter-VPC/VNet routing and on-prem connectivity.
- **Centralized Logging:** Dedicated security account aggregates CloudTrail, VPC Flow, GuardDuty, and audit logs.
- **Single-Account Problems:** Massive blast radius, permission sprawl, billing opacity, compliance violations, deployment bottlenecks, and lack of environment isolation.

CL5 — **Infrastructure as Code Tools**
- **IaC:** Declarative/programmatic management of infrastructure.
- **Terraform/OpenTofu:** Declarative HCL, state-driven, massive provider ecosystem, vendor-neutral. *Choose:* Multi-cloud, large teams, established workflows.
- **Pulumi:** Imperative/Declarative using general-purpose languages (TS, Python, Go). *Choose:* Complex logic, existing dev teams, dynamic provisioning.
- **CloudFormation/Bicep:** AWS-native, declarative JSON/YAML/Bicep. *Choose:* AWS-only shops, tight AWS integration, simplified CI/CD.
- **Crossplane:** Kubernetes-native IaC (XRs/Providers). *Choose:* GitOps/K8s-centric orgs, unifying cloud resources under K8s API.

CL6 — **Cloud-Native Autoscaling**
- **HPA:** Scales pods based on CPU/memory/custom metrics. Reactive, steady-state.
- **VPA:** Adjusts pod resource requests/limits based on usage. Requires pod restart.
- **Cluster Autoscaler:** Adds/removes nodes based on pending pods/resource pressure.
- **KEDA:** Event-driven scaling. Scales pods based on external event queues (Kafka, SQS, RabbitMQ).
- **KEDA vs HPA:** Use KEDA when scaling must be driven by event backlog/throughput rather than static resource metrics. HPA is better for predictable, resource-bound workloads.

CL7 — **Disaster Recovery Strategy**
- **RPO/RTO:** Define by business impact. RPO = max tolerable data loss; RTO = max tolerable downtime.
- **Active-Active vs Active-Passive:** Active-active serves traffic in both regions (lower RPO/RTO, higher cost/complexity). Active-passive uses one region live, one standby (higher RPO/RTO, lower cost).
- **DB Replication:** Sync = strong consistency, higher latency, limits region distance. Async = lower latency, potential data loss, standard for cross-region.
- **DNS Failover:** Route53/Traffic Manager uses health checks to route traffic to healthy region.
- **State Management:** Externalize state (Redis, S3, managed DB). Never rely on local disk state.
- **Cost & DR Types:** Pilot light = minimal infra, DB replicas, spin up on failover (low cost, moderate RTO). Warm standby = scaled-down prod, faster recovery. Multi-site active-active = full prod in both (highest cost, lowest RPO/RTO).

CL8 — **GitOps Model**
- **GitOps:** Git is the single source of truth. Desired state is declarative. Operators continuously sync cluster to Git.
- **ArgoCD vs FluxCD:** ArgoCD is push-based (polls Git, syncs to cluster), UI-heavy, beginner-friendly. FluxCD is pull-based (runs in cluster, watches Git, pushes changes), Git-native, CI-integrated.
- **Secrets Management:** Sealed Secrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from AWS SM/Vault), Vault (dynamic secrets, auth).
- **Drift Handling:** Manual changes are overwritten on next sync. Operators reconcile state. Drift can trigger alerts or be blocked via sync windows. Enforces consistency.

CL9 — **Stateful Legacy App to Kubernetes**
- **StatefulSet:** Provides stable network IDs, ordered deployment/termination, and stable storage bindings.
- **PV/PVC + Local Storage:** Use `local` storageClass with `volumeBindingMode: WaitForFirstConsumer` to bind PVC to the node with the local disk.
- **Headless Service:** `clusterIP: None` enables stable DNS (`<pod-name>.<service>.<namespace>`) for StatefulSet pods.
- **Init Containers:** Pre-load config, check dependencies, set permissions before the main app starts.
- **ConfigMaps as Volume Mounts:** Mount config files at required filesystem paths using `subPath` if needed.
- **Pod Disruption Budget (PDB):** Set `minAvailable` or `maxUnavailable` to ensure minimum replicas during voluntary disruptions (upgrades, node drains).

CL10 — **Service Account vs Workload Identity vs IRSA**
- **K8s Service Account:** Native identity for pods. No cloud IAM binding by default.
- **Workload Identity (GCP/Azure):** Securely maps K8s SA to cloud IAM identity.
- **IRSA (AWS):** Maps K8s SA to AWS IAM Role via OIDC provider. Pods assume role via STS.
- **Mounting Creds:** Bad practice. Hardcoded, long-lived, violates least privilege, high blast radius if leaked.
- **Federation Solves:** Short-lived credentials, OIDC-based trust, scoped IAM policies, automatic rotation, no static keys in pods/images.

CL11 — **Object vs Block vs File Storage**
- **Object (S3/Blob):** Scalable, HTTP API, flat namespace. Durability: 99.999999999%. Availability: 99.99%. *Use:* Unstructured data, backups, static hosting, data lakes.
- **Block (EBS/Managed Disk):** Low-latency, fixed size, mounted as disk. Durability: 99.999% (multi-AZ). Availability: High but AZ-tied. *Use:* OS disks, databases, high-IOPS apps.
- **File (EFS/Azure Files):** NFS/SMB, POSIX/Windows compatible, shared across instances. Durability: 99.999999999%. Availability: High. *Use:* Shared configs, home dirs, legacy apps needing file shares.

CL12 — **Zero-Trust Kubernetes Architecture**
- **Network Policies:** Default deny, allow only required pod-to-pod/service traffic.
- **Service Mesh (mTLS):** Istio/Linkerd for encrypted service-to-service comms, traffic control, observability.
- **Pod Identity:** Workload identity/IRSA for cloud resource access.
- **Admission Controllers:** OPA/Kyverno to enforce policies (no privileged pods, enforce registries, require resource limits).
- **Image Signing/Verification:** Cosign/Notary + admission controller to reject unsigned images.
- **Runtime Security:** Falco/Sysdig for anomaly detection (shell exec, unexpected network).
- **Secrets:** External Secrets Operator + Vault/KMS. Never in env vars or plain ConfigMaps.
- **vs Perimeter:** Zero-trust assumes breach, verifies every request, micro-segments, identity-centric, continuous validation vs static firewall boundaries.

CL13 — **CDN**
- **CDN:** Distributed edge cache network that proxies content closer to users.
- **How it works:** Caches static/dynamic content at edge PoPs. First request hits origin, subsequent requests hit cache.
- **Services:** CloudFront, Azure CDN, Fastly.
- **CDN vs Origin:** Use CDN for static assets, video, global users, DDoS mitigation, offloading origin. Direct origin for real-time, highly dynamic, or low-latency internal apps.

CL14 — **AZs and Regions**
- **Region:** Geographic area with multiple AZs.
- **AZ:** One or more discrete data centers with independent power/cooling/networking, connected via low-latency links.
- **Multi-AZ:** Protects against single data center failure. Ensures high availability.
- **Zonal vs Regional:** Zonal resources (EBS, NAT GW) tied to one AZ. Regional resources (ALB, RDS Multi-AZ, S3) span multiple AZs or are globally distributed.

CL15 — **Managed Database**
- **Managed DB (RDS/Cloud SQL):** Provider handles provisioning, patching, backups, replication, monitoring, failover.
- **vs Self-hosted on VM:** User manages OS, DB software, config, backups, scaling, HA.
- **Benefits:** Reduced ops overhead, built-in HA/DR, automated backups, easier scaling.

CL16 — **Cloud IAM & Least Privilege**
- **IAM Users:** Human/service identities. **Groups:** Collections of users. **Roles:** Temporary credentials for entities (users, services, external). **Policies:** JSON documents defining permissions.
- **Least Privilege:** Grant only necessary permissions. Apply via scoped policies, avoid `*:*`, use conditions, regular access reviews, just-in-time access.

CL17 — **Serverless Computing**
- **Serverless:** Managed compute where provider handles infra scaling/patching. Pay per execution.
- **Compare:** Lambda (AWS), Functions (Azure), GCF (GCP). Similar concepts, different ecosystems/tooling.
- **Cold Starts:** First invocation after idle period requires container provisioning. Matters for latency-sensitive apps. Mitigated by provisioned concurrency, smaller packages, lighter runtimes.
- **Poor Fit:** Long-running processes, stateful apps, high predictable throughput (reserved instances cheaper), strict compliance/network constraints.

CL18 — **Kubernetes Ingress Options**
- **Ingress Resource:** Standard K8s API, relies on controller (NGINX, ALB). TLS termination at controller.
- **Gateway API:** Newer, more structured, separates traffic routing (Gateway) from backend routing (HTTPRoute). Better RBAC, multi-tenant.
- **Cloud LB Annotations:** Directly provision cloud LB (ALB/ILB). TLS termination at LB.
- **Service Mesh Ingress:** Mesh gateway handles mTLS, traffic splitting, observability.
- **TLS:** Terminates at controller/LB/mesh. Can pass through or re-encrypt.
- **Gateway API over Ingress:** When needing fine-grained RBAC, multi-tenant routing, standardized API, or complex traffic splitting.

CL19 — **Cost Optimization Strategy ($80k/mo)**
- **RI/SP/Spot:** Commit to 1-3yr for predictable workloads (RI/SP). Spot/Preemptible for fault-tolerant, batch, dev/test (up to 90% savings).
- **Right-sizing:** Use monitoring to match instance size to actual CPU/mem/disk I/O.
- **Storage Tiering:** S3 Intelligent-Tiering, lifecycle policies to Glacier/Archive for infrequent access.
- **Idle Detection:** Find unattached volumes, idle LBs, unused IPs, zombie VMs. Automate cleanup.
- **FinOps:** Cross-functional culture (Eng, Fin, Ops). Set budgets, track showback/chargeback, regular optimization reviews.
- **Tools/Processes:** CloudHealth, Kubecost, native cost explorer. Tagging strategy, automated alerts, monthly cost reviews, accountability per team.

CL20 — **Multi-Cloud Strategy**
- **Abstraction:** Terraform, Crossplane, K8s for runtime. Avoid vendor-specific managed services where possible.
- **Networking:** Cloud VPN, Direct Connect/ExpressRoute, or partner interconnects. Complex routing, latency, cost.
- **Identity:** OIDC federation, centralized IdP (Okta/Azure AD), map to cloud IAM roles.
- **Trade-offs:** Multi-cloud increases complexity, cost, skill fragmentation, data egress fees. Benefits: Avoid lock-in, leverage best-of-breed, regulatory compliance, resilience.
- **Justified vs Unnecessary:** Justified for regulatory/data sovereignty, specific vendor capabilities, extreme resilience. Unnecessary for most startups/SMBs, when cloud-native services are core to value, or when team size can't manage complexity.

OT1 — **Purdue Model (ISA-95)**
- Hierarchical model for industrial automation.
- **Level 0:** Physical process (sensors, actuators).
- **Level 1:** Direct control (PLCs, RTUs, DCS).
- **Level 2:** Supervisory control (SCADA, HMIs, historians).
- **Level 3:** Operations/Manufacturing execution (MES, production scheduling).
- **Level 4:** Enterprise/business (ERP, finance, supply chain).
- **Level 5:** Strategic/external (partners, cloud analytics).

OT2 — **IT vs OT Networks**
- **IT:** Focus on confidentiality, data integrity, availability. Fast patching, frequent updates, standardized OS.
- **OT:** Focus on safety, availability, process continuity. Legacy systems, real-time constraints, proprietary protocols, cannot tolerate downtime/patching.
- **Why different patching:** OT systems run 24/7, unpatched firmware/OS is often safety-certified, patching can break process logic or require vendor validation, downtime costs millions/safety risks.

OT3 — **DMZ (IDMZ)**
- **IDMZ:** Segmented network between IT and OT. Acts as buffer.
- **Traffic:** One-way or strictly controlled bidirectional. Typically, IT pulls data from OT via DMZ (OPC UA, MQTT). OT does not initiate connections to IT.
- **Direct L4 to L1 dangerous:** Bypasses security controls, exposes real-time control network to internet/IT threats, risk of malicious commands to PLCs causing physical damage/safety incidents.

OT4 — **OT Protocols & Purdue Levels**
- **Modbus TCP:** L1/L2, simple request/response, widely used in legacy PLCs.
- **OPC UA:** L2/L3, secure, platform-independent, information modeling, modern standard.
- **EtherNet/IP (CIP):** L1/L2, industrial Ethernet, uses CIP for control, common in Rockwell.
- **PROFINET:** L1/L2, real-time Ethernet, deterministic, Siemens/dominant in Europe.
- **MQTT:** L2/L3/L4, lightweight publish/subscribe, ideal for edge-to-cloud telemetry.

OT5 — **Data Diode vs Firewall**
- **Data Diode:** Hardware-enforced unidirectional communication. Only allows data flow one way.
- **Firewall:** Bidirectional, inspects traffic, allows/denies based on rules.
- **Use diode when:** Strict data exfiltration prevention needed, high-security OT zones, regulatory requirements.
- **Limitation:** Cannot allow any return traffic (e.g., ACKs, commands, status updates). Less flexible than firewalls.

OT6 — **SCADA to Cloud Data Flow**
- **Flow:** PLCs/RTUs → Historian (L2) → OPC UA Server → Edge Gateway (protocol translation, buffering, security) → MQTT Broker (on-prem/cloud) → Cloud Ingestion (IoT Core/Event Hubs) → Analytics.
- **Security Boundaries:** IDMZ between OT and edge/cloud. TLS/mTLS for all comms. Edge gateway handles authentication, data filtering, offline buffering. Cloud uses IAM, VPC endpoints, WAF. Network segmentation isolates historian/SCADA.

OT7 — **IEC 62443 Zones & Conduits**
- **Zone:** Logical/physical boundary with common security requirements. Defined by asset function, risk, and access needs.
- **Conduit:** Communication path between zones with defined security controls.
- **Plant Model:**
  - Zone 1: Corporate/IT (L4)
  - Zone 2: Engineering Workstations (L3)
  - Zone 3: SCADA Servers & Historian (L2)
  - Zone 4: PLCs & Control Network (L1)
  - Zone 5: SIS (Safety, isolated)
  - Conduits: Z1→Z2 (firewall, jump host), Z2→Z3 (firewall, one-way data pull), Z3→Z4 (firewall/data diode, strict allow rules), Z4↔Z5 (physical/logical isolation, no direct conduit).

OT8 — **Network Segmentation Strategy**
- **VLAN Design:** Segment by function/process (e.g., VLAN 10: Line 1 PLCs, VLAN 20: Line 2, VLAN 30: HMIs, VLAN 40: SCADA/History, VLAN 50: Engineering).
- **Firewall Placement:** Core firewall between IT/OT, edge firewalls between VLANs, DMZ for external access.
- **Switch Architecture:** Managed Layer 3 switches, port security, 802.1X (if supported), disable unused ports.
- **Remote Access:** Jump host in DMZ, MFA, session recording, time-limited vendor accounts, no direct OT access.
- **Transition:** Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, vendor coordination, test in staging first.

OT9 — **SIS vs BPCS & IEC 61511**
- **SIS:** Independent system designed to bring process to safe state on hazardous conditions. **BPCS:** Normal process control.
- **IEC 61511:** Safety lifecycle standard for SIS. Defines SIL (Safety Integrity Level) requirements.
- **Isolation:** Prevents cyber attacks from compromising safety functions. SIS must operate independently to guarantee safety during IT/OT compromise.
- **Ransomware on SIS:** If compromised, safety functions may fail to activate, leading to catastrophic physical damage, environmental release, or loss of life. Hence, air-gap/isolation is critical.

OT10 — **PLC vs DCS vs SCADA**
- **PLC:** Discrete control, fast, rugged, handles I/O, used for machine/line control.
- **DCS:** Centralized control architecture, integrated I/O, better for continuous processes (chemical, oil/gas), built-in redundancy.
- **SCADA:** Supervisory system, aggregates data from multiple PLCs/RTUs, provides HMI, trending, alarms.
- **Coexist:** Yes. DCS often uses PLCs/RTUs as field controllers. SCADA supervises both. Common in large plants.

OT11 — **Remote Access Architecture**
- **Jump Host:** Isolated bastion in DMZ, no direct OT access.
- **MFA:** Required for all remote access.
- **Session Recording:** Audit trail for compliance.
- **Vendor Access:** Time-limited, scoped permissions, break-glass accounts, approved requests.
- **Why RDP to HMI unacceptable:** Exposes OT directly to corporate network, bypasses segmentation, increases attack surface, violates Purdue model, risk of lateral movement to control layer.

OT12 — **SOC for Water Treatment (Nation-State Compromise)**
- **Detection:** Network monitoring (IDS/Zeek, anomaly detection on PLC traffic), asset inventory (passive discovery), SIEM correlation, EDR on IT/DMZ.
- **Response Steps:** Isolate compromised segment (VLAN/firewall rules), preserve forensics, engage incident response team, notify regulators/stakeholders, verify SIS/BPCS integrity.
- **Coordination:** Control room prioritizes safety, manual overrides if needed, maintain process stability, communicate with OT engineers.
- **Safe Operations:** Never disrupt critical process without safety validation. Use manual controls if automated systems are suspect. Verify SIS is unaffected.
- **Plant Operator Role:** Monitor physical parameters, execute manual safety procedures, report anomalies, follow cyber incident playbook, do not attempt IT-style troubleshooting.

OT13 — **HMI**
- **HMI:** Interface for operators to monitor/control processes (screens, buttons, alarms).
- **Role:** Real-time visualization, manual overrides, alarm management.
- **vs Engineering Workstation:** HMI is for operations (run-time). Engineering workstation is for programming, configuration, diagnostics, firmware updates (Level 3).

OT14 — **Historian**
- **Historian:** Time-series database optimized for high-volume process data logging.
- **Importance:** Trend analysis, compliance, troubleshooting, performance optimization.
- **Plant (L2/L3) vs Enterprise (L4):** Plant stores high-frequency, raw process data for operational use. Enterprise stores aggregated, filtered data for business analytics, ERP integration, long-term archival.

OT15 — **Ladder Logic**
- **Ladder Logic:** Graphical programming language mimicking relay circuits.
- **Executes on:** PLCs.
- **Dominant:** Familiar to electricians/technicians, deterministic, easy to troubleshoot, widely supported, legacy codebase, safety-certified.

OT16 — **RTU vs PLC**
- **RTU:** Remote Terminal Unit. Designed for harsh environments, long-distance communication (cellular, satellite), typically fewer I/O, optimized for telemetry.
- **PLC:** Programmable Logic Controller. Local control, faster scan times, more I/O, industrial Ethernet/fieldbus.
- **RTU use:** Pipelines, water distribution, wind farms, remote sites where connectivity is limited and environmental ruggedness is key.

OT17 — **Analog vs Digital Signals**
- **Analog:** Continuous voltage/current (4-20mA, 0-10V). Digital: Discrete on/off or pulse.
- **4-20mA preferred:** 4mA live zero indicates wire break/failure (0mA = fault). 0-20mA cannot distinguish between no signal and broken wire. Better noise immunity, loop-powered.

OT18 — **OT Asset Inventory**
- **Inventory:** Comprehensive list of hardware, firmware, network configs, connections. Foundation for risk assessment, patching, segmentation.
- **Tools:** Passive monitoring (Zeek, NetBox, OT-specific scanners like Nozomi, Claroty). Active scanning (port scans, protocol probes).
- **Active scanning dangerous:** Can crash legacy PLCs/RTUs, cause process disruption, trigger safety systems, or be detected as attack. Passive is safer.

OT19 — **MITRE ATT&CK for ICS**
- **Framework:** Maps adversary tactics/techniques specific to industrial environments.
- **Tactics & Examples:**
  1. Reconnaissance: Gather network topology (T1580)
  2. Resource Development: Acquire exploit tools (T1583)
  3. Initial Access: Spearphishing attachment (T1566)
  4. Execution: Command and Scripting Interpreter (T1059)
  5. Impact: Damage to Physical Systems (T1499)
- **Differs from Enterprise:** Focuses on physical process impact, legacy protocols, safety systems, deterministic timing.
- **Assessment:** Map current defenses to techniques, identify gaps (e.g., no firmware integrity monitoring), prioritize controls, simulate attacks.

OT20 — **Converged IT/OT SOC**
- **Log Collection:** Passive network taps, OPC UA/MQTT log forwarders, SIEM agents on DMZ/jump hosts. Avoid active polling on OT.
- **SIEM Integration:** Normalize OT logs (Syslog, CEF), correlate with IT logs, use OT-specific parsers.
- **Detection Rules:** Baseline normal traffic, alert on protocol anomalies, unauthorized PLC writes, after-hours access, known malicious IPs.
- **Triage:** IT analysts handle low-risk IT alerts. OT engineers validate process impact. Escalation matrix defined.
- **Staffing:** IT analysts (threat intel, phishing, malware), OT engineers (protocol expertise, process safety, PLC diagnostics). Joint training.
- **False Positives:** OT environments have predictable, repetitive traffic. Tune rules to baseline, use allowlists, validate with OT team before alerting.
- **Unauthorized Firmware Change:** Immediate isolation of affected PLC/network segment, verify SIS/BPCS integrity, restore from known-good backup, forensic analysis, patch/validate new firmware, update change management, notify regulators if safety impacted.
