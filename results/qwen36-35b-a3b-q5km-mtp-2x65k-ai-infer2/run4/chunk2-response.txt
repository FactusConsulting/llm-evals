## Kubernetes

**K1** — A **Deployment** manages stateless workloads: pods are interchangeable, have random names, and are replaced on updates. A **StatefulSet** manages stateful workloads: pods have stable, unique network IDs, are deployed/terminated in order, and retain stable storage bindings across restarts.

**K2** — The Endpoint Controller populates the Service's `Endpoints` object with pod IPs. `kube-proxy` watches Services/Endpoints and programs kernel networking (iptables or IPVS) to map the Service's ClusterIP:Port to the backend pod IPs:Ports. Traffic hitting the ClusterIP is load-balanced by the kernel to healthy pods.

**K3** — A **PersistentVolume (PV)** is a cluster-wide storage resource (statically provisioned or dynamically created). A **PersistentVolumeClaim (PVC)** is a user's request for storage. A **StorageClass (SC)** defines a template for dynamic PV provisioning. Relation: A PVC binds to a PV (or triggers an SC to provision one). Once bound, the PVC acts as a mountable volume for pods.

**K4** — 1. `kubectl logs <pod> --previous` to check crash exit codes/stack traces. 2. `kubectl describe pod` to inspect Events, OOMKilled status, and probe failures. 3. Verify resource requests/limits and node capacity. 4. Check environment variables, mounted configs/secrets, and external dependency connectivity.

**K5** — CoreDNS provides internal DNS resolution for `svc.cluster.local` and pod FQDNs. If CoreDNS pods are down, internal service discovery and DNS-based routing fail, but direct IP communication, external DNS, and node-level networking remain unaffected.

**K6** — The scheduler uses **filtering** (predicate functions) to eliminate unsuitable nodes, then **scoring** (priority functions) to rank remaining nodes. Filtering checks: taints/tolerations, node selectors, resource availability, pod affinity/anti-affinity, topology spread constraints. Scoring factors: 1) Resource balance (CPU/memory requests), 2) Node affinity/anti-affinity weights, 3) Taint toleration costs, 4) Topology spread skew.

**K7** — Yes, it will schedule: 3.5GB requested + 256Mi request ≈ 3.75GB < 4GB node capacity. At runtime, if it uses 600Mi (exceeds 512Mi limit), the cgroup enforces the limit, triggers an OOMKilled event, and the pod restarts (entering CrashLoopBackOff if the leak persists).

**K8** — 1. Client request hits External LB. 2. LB forwards to Ingress Controller (NGINX) pod. 3. NGINX parses the Ingress resource, matches host/path rules. 4. Routes to a Kubernetes Service. 5. Service selects pods via the Endpoints object. 6. `kube-proxy` (iptables/IPVS) programs kernel rules to route traffic to pod IPs. 7. Traffic reaches the application container.

**K9** — A `NetworkPolicy` restricts pod-to-pod and pod-to-external traffic using selectors and rules. Default behavior (no policies): all pods can communicate freely. When a policy is applied to a namespace, it only affects pods matching its `podSelector`; unmatched pods are unaffected, but matched pods deny all traffic except what explicitly matches the policy rules.

**K10** — **RollingUpdate** gradually replaces old pods with new ones (zero downtime, supports health checks). **Recreate** terminates all existing pods before starting new ones (causes downtime). Choose Recreate for stateful apps, database migrations, or workloads requiring exclusive access to shared resources/locks.

**K11** — A namespace provides logical isolation and scope for resources. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

**K12** — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it displays: 1) Pod Events (scheduling, pull, probe failures), 2) Container statuses (restart counts, last state, exit codes), 3) Resource usage & limits, 4) Mount details (volumes, configmaps, secrets), 5) Conditions & node affinity/taint status.

**K13** — A ConfigMap stores non-sensitive configuration data. Pods consume it via: 1) Environment variables (key-value pairs injected into container env), 2) Volume mounts (files projected into the container filesystem).

**K14** — **ClusterIP**: internal-only virtual IP, accessible only within the cluster. **NodePort**: exposes the service on a static port on each node's IP, accessible externally via `<NodeIP>:<NodePort>`. **LoadBalancer**: provisions a cloud provider's external LB, assigns a public IP, and routes traffic to the Service.

**K15** — A DaemonSet ensures a copy of a pod runs on every node (or subset via nodeSelector). Use it for cluster-level daemons: logging agents (Fluentd), monitoring (Prometheus node-exporter), network plugins (CNI), or storage daemons (CSI). Deployments manage application replicas, not node-level daemons.

**K16** — **Taints/Tolerations** are node-level "repel" rules: nodes repel pods unless the pod explicitly tolerates the taint. **Node Affinity** is pod-level "attract" rules: pods prefer nodes matching labels. Use case: Taints for dedicated GPU nodes (prevent general workloads); Affinity for zone-aware scheduling (prefer nodes in same AZ).

**K17** — An Operator is a custom Kubernetes controller that manages complex, stateful applications using Custom Resource Definitions (CRDs) and custom reconciliation logic. Unlike standard controllers (which only watch built-in resources), Operators encode operational knowledge (backups, upgrades, failover, scaling). Solves manual intervention for stateful workloads by automating lifecycle management.

**K18** — etcd uses a **linearizable** consistency model (via Raft). If quorum is lost, the cluster becomes read-only/unwritable to prevent split-brain. If 2/3 etcd nodes are permanently lost, quorum cannot be restored; recovery requires restoring from a recent snapshot + watch prefix, or rebuilding the cluster and migrating data.

**K19** — RBAC controls access via Roles/ClusterRoles (permissions) and RoleBindings/ClusterRoleBindings (assignments). 
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev-namespace
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev-namespace
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — Default `ndots:5` in `/etc/resolv.conf` causes the resolver to append multiple search domains before querying external DNS. For `api.example.com`, it tries `api.example.com.svc.cluster.local`, `.cluster.local`, `.local`, etc., causing 5+ queries. Fix: set `ndots:2` in pod `dnsConfig`:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "2"
```

## Development

**D1** — `git merge` creates a merge commit, preserving full branch history. `git rebase` rewrites commit history by replaying branches onto a new base, creating a linear history. Avoid rebasing on shared/public branches or branches others are actively working on.

**D2** — **TCP**: connection-oriented, reliable, ordered delivery, flow/congestion control. **UDP**: connectionless, unreliable, low-latency, no ordering. TCP examples: HTTP/HTTPS, SSH, SMTP. UDP examples: DNS, VoIP, DHCP.

**D3** — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to non-deterministic results. Example: Two threads incrementing a shared counter without a mutex; final value may be less than expected due to lost updates.

**D4** — **Symmetric**: single shared key for encryption/decryption (fast, scalable for bulk data). **Asymmetric**: public/private key pair (secure key exchange, digital signatures). TLS uses asymmetric encryption during handshake to authenticate and exchange a session key, then switches to symmetric encryption for data transfer.

**D5** — Each Dockerfile instruction creates a read-only image layer. Layer caching reuses unchanged layers on rebuild. Best practice: order instructions from least to most frequently changing (e.g., install dependencies before copying source code) to maximize cache hits.

**D6** — 1. Check upstream service logs/metrics for errors, timeouts, or dependency failures. 2. Verify resource limits (OOMKilled or CPU throttling). 3. Inspect liveness/readiness probe configurations and recent probe failures. 4. Check load balancer/backend pool health and connection limits.

**D7** — CAP theorem states a distributed system can only guarantee two of three: Consistency, Availability, Partition tolerance. **CP example**: CockroachDB, HBase (prioritize data correctness; reject requests during network partitions). **AP example**: Cassandra, DynamoDB (prioritize availability; serve stale data during partitions, reconcile later).

**D8** — **Horizontal scaling**: add more nodes/instances. **Vertical scaling**: increase CPU/RAM of existing node. Horizontal scaling requires: stateless application design, external session/state storage (Redis, DB), sharding/partitioning, service discovery, and load balancing.

**D9** — An environment variable is a dynamic named value passed to processes at runtime. Persist across sessions: add `export VAR_NAME="value"` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

**D10** — **JSON**: strict syntax, key-value pairs, arrays. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: universal parsing, strict schema validation. YAML advantage: readability, less boilerplate, easier for configuration files.

**D11** — A REST API is an architectural style using HTTP methods to interact with resources. **GET**: retrieve data (idempotent). **POST**: create new resource. **PUT**: update/replace entire resource (idempotent). **DELETE**: remove resource.

**D12** — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3` or `package-lock.json`). Ensures reproducible builds, prevents unexpected breaking changes from minor/patch updates, and guarantees consistent environments across dev/staging/prod.

**D13** — **Compiled**: source code is translated to machine code before execution (C, Rust). **Interpreted**: source code is executed line-by-line at runtime by an interpreter (Python, JavaScript). Note: many modern languages use hybrid/JIT compilation.

**D14** — A **reverse proxy** sits in front of backend servers, routing client requests to appropriate backends. A **forward proxy** sits in front of clients, routing outbound requests to the internet. Reverse proxy examples: Nginx (SSL termination, load balancing), HAProxy (high-performance TCP/HTTP routing).

**D15** — A deadlock occurs when two or more processes wait indefinitely for resources held by each other. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait. Breaking any one prevents deadlock.

**D16** — Eventual consistency guarantees that if no new updates occur, all replicas will eventually converge. Cassandra handles read-after-write via vector clocks/Lamport timestamps. Tunable consistency levels: `ONE`, `TWO`, `THREE`, `QUORUM`, `LOCAL_QUORUM`, `ALL`, `SERIAL`, `LOCAL_SERIAL`. For strong read-after-write, use `CL=ALL` or `SERIALIZABLE`.

**D17** — mTLS requires both client and server to present valid certificates. Handshake: 1. ClientHello, 2. ServerHello + ServerCert, 3. ServerKeyExchange, 4. ClientKeyExchange + ClientCert, 5. CertificateVerify (both sides), 6. Finished. Used in service meshes (Istio/Linkerd), microservices, zero-trust networks, and database replication.

**D18** — A hash table maps keys to values via a hash function. Collision resolution: **chaining** (linked lists/arrays at each bucket), **open addressing** (linear/quadratic probing, double hashing). Average time complexity: O(1) for insert/lookup/delete. Worst case: O(n) when all keys hash to the same bucket.

**D19** — A circuit breaker monitors downstream health and fails fast when failures exceed a threshold. States: **Closed** (normal traffic), **Open** (fail fast, trip after threshold), **Half-open** (allow limited test requests). Relates to retries: circuit breakers prevent retry storms during outages; retries should be bounded and paired with circuit breakers to avoid amplifying load.

**D20** — **Optimistic**: assumes no conflicts, validates on commit using row versioning/ETags. Fails if version changed. **Pessimistic**: locks rows during transaction using `SELECT FOR UPDATE`. Choose optimistic for high read/low write contention (web apps). Choose pessimistic for high write contention or critical financial transactions where data integrity is paramount.
