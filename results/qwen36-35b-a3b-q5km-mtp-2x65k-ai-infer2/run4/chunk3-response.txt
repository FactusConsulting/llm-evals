T1 — `tofu plan` performs a dry-run: it reads config + state, queries providers, and outputs a diff of proposed changes without modifying infrastructure. `tofu apply` executes those changes, creating/updating/deleting resources and updating state.

T2 — State is a JSON file mapping configuration resources to real-world API objects. Remote state is critical for team collaboration, prevents state file corruption, enables state locking, and allows state to survive local machine changes.

T3 — `count` uses integer indices (0, 1, 2...); `for_each` uses maps or sets of strings. `for_each` is preferred when resources have unique identifiers or attributes, as changing a list element with `count` forces recreation of all subsequent resources, while `for_each` only affects the changed key.

T4 — OpenTofu detects drift during `tofu plan` by comparing the remote state to live API calls. If a resource is modified externally, the plan shows it as a diff. On `apply`, OpenTofu overwrites the change to match config, or errors if `prevent_destroy` or lifecycle rules block it.

T5 —
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.key
  }
}
```

T6 — `terraform_remote_state` reads raw state from another configuration, which can expose sensitive data and lacks type safety. The recommended alternative is using **module output values**, which are explicit, type-checked, versioned, and decouple consumers from state file structure.

T7 — Provisioners run after resource creation but don't update state outputs reliably; if the kubeconfig isn't captured by a resource, the output evaluates as empty. Fix: Use a `local_file` resource to write the kubeconfig during the provisioner, or switch to a proper Kubernetes provider/data source that polls for cluster readiness before exposing the kubeconfig.

T8 — `tofu import` manually maps existing infrastructure to state, requiring manual config writing and offering no attribute auto-discovery. The `import` block (1.5+) allows declarative mapping directly in config, supports multiple resources, provides better error messages, and integrates with `tofu plan` for validation.

T9 — A `variable` block defines input parameters consumed by modules. An `output` block exposes values from state/config to calling modules or CLI. Variables flow in; outputs flow out.

T10 — A provider is a plugin that translates OpenTofu config into API calls for a platform. Without `tofu init`, providers aren't downloaded or initialized, causing `tofu plan` to fail with "provider not installed" errors.

T11 — `.terraform.lock.hcl` pins provider versions, checksums, and source hashes. Commit it to ensure reproducible builds, prevent supply-chain attacks, and guarantee all team members/CI use identical provider binaries.

T12 — `tofu destroy` removes all resources tracked in state. Target a single resource: `tofu destroy -target=module.name.resource[0]`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to fetch the latest Ubuntu AMI ID instead of creating a new one each run.

T14 — `locals` compute values within a module scope; `variable` blocks accept external inputs. Use `locals` for intermediate calculations, string manipulation, or conditional logic to keep config DRY and avoid cluttering input variables.

T15 — `lifecycle` controls resource behavior: `create_before_destroy` creates new before deleting old (zero-downtime). `prevent_destroy` blocks accidental deletion (safety). `ignore_changes` skips drift detection for specific attributes (e.g., auto-scaling tags).

T16 — The `moved` block tracks resource address changes during refactoring. It tells OpenTofu to remap state entries to new addresses without destroying/recreating resources, preserving infrastructure during module restructuring.

T17 — OpenTofu builds a DAG of dependencies. Implicit dependencies are inferred from references; explicit uses `depends_on`. `depends_on` forces sequential execution, reducing parallelism and blocking the graph, so it should only be used when implicit references fail.

T18 — 1. `tofu plan -refresh=false`: skips API calls (faster, but risks stale state). 2. Split state into multiple workspaces/modules: reduces graph size (adds complexity). 3. Use `data` sources with `lifecycle { ignore_changes = [last_updated] }` or defer evaluation: reduces plan noise (less real-time data). 4. Optimize providers (exact versions, disable metadata calls): cuts API latency (may miss upstream updates).

T19 — State locking uses a backend-specific mechanism (e.g., DynamoDB) to prevent concurrent writes. If a lock isn't released, run `tofu force-unlock <LOCK_ID>`. Risks include data corruption, lost changes, or race conditions if another process is actively modifying state.

T20 — 1. Add remote backend config (S3 + DynamoDB). 2. Run `tofu init -migrate-state`. 3. OpenTofu uploads local state to S3 and creates the lock table. 4. Verify with `tofu state list` and `tofu plan`. Existing state is atomically migrated; verify by checking S3 object versioning and DynamoDB lock entries.

A1 — A playbook is a YAML file defining automation steps. A role is a reusable collection of tasks, handlers, vars, and templates. A task is a single unit of work (module execution) within a playbook or role.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_os_family }}`.

A3 — `command` runs without shell features (safest). `shell` runs via `/bin/sh`, supporting pipes/redirects. `raw` executes over SSH without Python, used for bootstrapping unmanaged hosts. Use `command` for safety, `shell` for complex commands, `raw` for initial setup.

A4 — Idempotency means a task produces the same result if run multiple times. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run).

A5 —
```yaml
- name: Install htop based on OS
  package:
    name:
      - htop
      - "{{ 'epel-release' if ansible_os_family == 'RedHat' else omit }}"
    state: present
```

A6 — Precedence (high to low): extra_vars > command line > play vars > host_vars > group_vars > role vars > role defaults > inventory vars. Higher precedence overrides lower.

A7 — Use `serial: 3` in the playbook to deploy first 3 nodes. Group remaining in `[rke2_rest]`. Add `wait_for: port=6443 delay=10 timeout=300` to ensure readiness before scaling. Use `strategy: free` if nodes don't need strict ordering, or keep `linear` with `serial`.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'my_secret' --name 'db_password'` and paste the `!vault` block into the vars file.

A9 — Inventory lists hosts/groups for Ansible. Static inventory is a hardcoded file. Dynamic inventory is a script/API that generates host data on-the-fly (e.g., cloud metadata, CMDB).

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task that runs only when explicitly notified. Differs from regular tasks (which run unconditionally). Trigger with `notify: handler_name` in a task.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `log_path`.

A13 — `register` captures task output into a variable. Use in subsequent tasks: `when: my_var.stdout == "success"` or `debug: msg="{{ my_var.stdout_lines }}"`.

A14 — `include_tasks` is dynamic (evaluated at runtime, supports `when`). `import_tasks` is static (evaluated at parse time, faster, no conditionals). Use `include` for conditional logic, `import` for performance/static includes.

A15 — Ansible Galaxy is a repository for roles/collections. `requirements.yml` lists them with versions. Install: `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins manage host communication. `ssh`: standard SSH. `local`: runs on control node. `network_cli`: CLI over SSH/Telnet for network devices. Choose based on target OS/device type.

A17 — `delegate_to` runs a task on a specified host. `run_once` runs it once across all hosts. Example: gather remote facts, then write a consolidated report to localhost: `delegate_to: localhost` + `run_once: true`.

A18 — 1. Increase `forks` (tradeoff: higher control node CPU/memory). 2. Enable `pipelining` (tradeoff: requires SSH config changes, minor security consideration). 3. Fact caching (Redis/Memcached) (tradeoff: stale facts, cache invalidation overhead). 4. Use Mitogen or `strategy: free` (tradeoff: Mitogen needs Python env, `free` breaks task ordering).

A19 — `{{ }}` outputs values, `{% %}` controls flow, `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check: {{ server }}
  server {{ server }};
{% endfor %}
}
```

A20 — Use `serial: 1` or `20%`. Pre-task: `uri` module to set LB weight=0 or disable health check. Post-task: re-enable LB. Health check: `uri` module polling `http://{{ inventory_hostname }}/healthz`. Rollback: wrap in `block/rescue`; on failure, `rescue` re-enables LB, reverts config, and notifies next batch.
