SC1-A
The pods fail because the namespace Pod Security Standard (PSS) was upgraded from `Baseline` to `Restricted`. `Restricted` enforces `runAsNonRoot: true`, `runAsUser: >0`, and `allowPrivilegeEscalation: false`. The container images were rebuilt with `cgr.dev/chainguard/static:latest`, which sets `USER root` (UID 0) in the Dockerfile. When `runAsNonRoot: true` is set without an explicit `runAsUser`, Kubernetes attempts to run the container as a random non-zero UID, but the image's `USER root` directive overrides it, causing the container runtime to reject the pod or the security context to conflict with the image's filesystem permissions. The `Restricted` policy explicitly forbids UID 0, triggering `CrashLoopBackOff` due to failed container startup or permission denied errors.

SC1-C
**Immediate Fix:** Update container images to explicitly set a non-root user (`RUN addgroup -S appgroup && adduser -S appuser -G appgroup && USER appuser`) and pin the base image digest. Update manifests to include `securityContext.runAsUser: 1000` and `runAsGroup: 1000`.
**CI Gate:** Add `kube-score` or `kubeconform` with PSS validation in CI. Integrate `trivy` with `--exit-code 1` for image scanning. Add a policy-as-code step (e.g., `checkov` or `kyverno` CLI) to reject images not signed or running as root.
**Rollout:** Use Helm or Kustomize to roll out the updated image with `strategy: rollingUpdate` (`maxSurge: 25%`, `maxUnavailable: 0`). Monitor `kubectl rollout status` and pod readiness probes. If error rate spikes, trigger `helm rollback` or revert the image tag. This ensures zero downtime via rolling updates and instant rollback capability.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped from the primary to the replica with network latency. When the primary fails, the replica is promoted, but any transactions committed on the primary after the last shipped WAL are permanently lost. The data loss window equals the replication lag at failover time. To quantify: query `pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()` on the replica, check `pg_stat_replication` for `replay_lag`, and cross-reference with application commit logs or WAL position timestamps.

```sql
SELECT blocked_locks.pid AS blocked_pid, blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid, blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement, blocking_activity.query AS blocking_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC6-C
**Comparison:**
- **Direct Connect:** Dedicated 10Gbps+, low latency, high cost ($5k/mo + data transfer). Fits ZT if combined with encryption (MACsec/IPsec). Routing: BGP over TGW attachment.
- **Second VPN + ECMP:** Scales to 2Gbps, medium cost, IPsec encryption. Routing: Multiple VPN attachments + BGP ECMP. ZT-compatible but management overhead.
- **Tailscale/Netbird:** WireGuard mesh, unlimited bandwidth (limited by endpoints), low cost, built-in encryption & ACLs. Routing: Overlay network, simplifies routing. Best fits ZT model with least friction.
**Routing Changes:** DX requires BGP/TGW attachment. ECMP requires multiple VPN attachments + BGP. Mesh uses overlay routing, eliminating complex BGP/VPN routing tables.

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks (Patroni, Redis Sentinel, RabbitMQ federation) monitor site heartbeat. Site down = 3 consecutive failures + etcd quorum loss.
2. **DNS Failover:** GSLB (Route53/Azure Traffic Manager) switches traffic to Dallas endpoint.
3. **Patroni Promotion:** Standby promoted via etcd DCS, synchronous commit ensures zero data loss.
4. **Redis/RabbitMQ:** Sentinel promotes master, federation catches up queues.
5. **MinIO:** Site replication catches up, read/write switches to Dallas.
6. **State Update:** OpenTofu drift detection applies state changes, updates infrastructure config.
**Split-Brain:** Quorum-based DCS (etcd/Patroni) prevents dual promotion. Fencing scripts disable primary node network.
**Failback:** Reverse replication sync, verify data consistency, switch DNS back to Chicago, update OpenTofu state, decommission Dallas as primary.
