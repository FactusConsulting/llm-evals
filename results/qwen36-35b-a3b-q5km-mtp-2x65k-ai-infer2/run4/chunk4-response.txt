G1 — A slice is a dynamic, reference-like view over an underlying array (header: pointer, length, capacity), while an array is a fixed-size value type with compile-time known length. Appending to a slice at capacity triggers reallocation: the runtime allocates a new backing array (typically doubling capacity), copies existing elements, and returns a new slice pointing to it.

G2 — `var x int` declares a variable with explicit type and zero value; `x := 0` is a short variable declaration that infers type and requires at least one new variable on the left. You cannot use `:=` at package level, when redeclaring an existing variable without introducing a new one, or when explicit type annotation is required (e.g., `var x int = 0` vs `x := 0` where type inference might not match intent).

G3 — A goroutine is a lightweight, multiplexed execution context managed by the Go runtime (~2KB initial stack vs MBs for OS threads). The GMP scheduler maps G (goroutines) to M (OS threads) via P (processors/context objects). P limits concurrent OS threads, manages run queues, and enables work-stealing, allowing efficient M:N scheduling without OS thread overhead.

G4 — Channels are typed conduits for safe goroutine communication. Unbuffered channels block both sender and receiver until both are ready. Buffered channels have a capacity; send blocks only when full, recv blocks only when empty. Sending to a full buffered channel blocks until a receiver consumes an element or the channel is closed.

G5 — `context` carries deadlines, cancellation signals, and request-scoped values across API boundaries. Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
resp, err := client.Do(req) // cancels automatically on timeout
```

G6 — Go uses implicit interface satisfaction: a type satisfies an interface if it implements the method set, with no `implements` keyword. Unlike Java/C#, interfaces are decoupled from type declarations. `interface{}` (or `any` since 1.18) accepts any type, enabling generics/JSON handling, but is dangerous because unchecked type assertions panic and bypass compile-time safety.

G7 — The code violates Go's memory model: no synchronization guarantees visibility or ordering, allowing compiler/CPU reordering and cache coherency issues. Fix with `sync/atomic`:
```go
var ready atomic.Bool
var data atomic.String
go func() { data.Store("hello"); ready.Store(true) }()
for !ready.Load() {}
fmt.Println(data.Load())
```
Alternatively, use a channel or mutex.

G8 — `sync.Mutex` provides exclusive access; `sync.RWMutex` allows concurrent reads or a single write. `sync.Map` optimizes for read-heavy, write-sparse, or disjoint-key workloads by avoiding mutex contention, but has higher per-operation overhead, worse cache locality, and slower iteration. Use a regular `map` + `Mutex` for general-purpose hot paths.

G9 — Go modules manage dependencies via `go.mod` (module path, Go version, direct deps) and `go.sum` (cryptographic hashes for integrity). `go mod tidy` removes unused deps, adds missing ones, and updates `go.sum`. MVS (Minimum Version Selection) resolves the dependency tree to the lowest compatible versions, preventing version bloat and conflicts.

G10 — `defer` schedules a function call until the surrounding function returns, executing in LIFO order. Common loop gotcha: variables captured by deferred closures are evaluated at defer time, not declaration time. Fix by passing as arguments: `defer func(v int) { fmt.Println(v) }(i)`.

G11 — A pointer stores a memory address. Zero value is `nil`. Create a pointer to a struct literal with `&MyStruct{Field: val}`. Pointers are value types; `nil` indicates no valid address.

G12 — `init()` runs after package-level variable initialization and before `main()`. A package can have multiple `init()` functions; their execution order is undefined within the package but deterministic across packages (dependencies initialize first). Avoid side effects; use for setup only.

G13 — `new(T)` allocates zeroed memory for any type and returns a pointer `*T`. `make(T, args)` initializes only built-in reference types (slice, map, channel) and returns the initialized value (not a pointer). `make` sets capacity/length; `new` does not.

G14 — Go uses explicit error handling via the `error` interface (`Error() string`). Idiomatic: `if err != nil { return err }`. `errors.Is(err, target)` checks if the error or any wrapped error matches `target`. `errors.As(err, &target)` extracts a typed error from the chain. `==` only checks direct equality, ignoring wrapping.

G15 — Zero values: `map` → `nil` (use `make`), `slice` → `nil` (len=0, cap=0), `channel` → `nil`, `struct` → zero values of each field. `nil` slices/maps/channels are safe to read/close but panic on write.

G16 — A race occurs when concurrent goroutines access shared data without synchronization, with at least one write. `-race` injects runtime instrumentation to detect conflicting accesses. Fix with `sync.Mutex` (lock around shared access) or channels (communicate by sharing memory). Example fix: `var mu sync.Mutex; mu.Lock(); counter++; mu.Unlock()`.

G17 — `select` waits on multiple channel operations, evaluating ready cases in random order. Unlike `switch`, it blocks if no case is ready and never falls through. Timeout: `case <-time.After(d):`. If multiple cases are ready, one is chosen pseudo-randomly.

G18 — Escape analysis determines stack vs heap allocation. Variables escape if: address taken, size unknown at compile time, outlives function scope, or returned. Inspect with `go build -gcflags="-m"`. Heap allocations trigger GC; stack is zero-cost. Minimizing escapes improves latency and throughput.

G19 — `reflect.Type` holds type metadata; `reflect.Value` holds the actual value/data. Reflection bypasses compile-time checks, is slow, and allocates. Justified for serialization, ORMs, or generic utilities. Prefer code generation (`go generate`, `stringer`) for performance-critical paths to retain type safety and zero-cost dispatch.

G20 — `//go:embed` compiles files/directories into the binary at compile time. Supports single files, directories (`...`), and entire FS via `embed.FS`. Limitations: compile-time only, no runtime modification, pattern restrictions. `embed.FS` implements `io/fs.FS`, enabling seamless use with `http.FS`, `os.DirFS`, and standard library FS consumers.

R1 — Ownership is Rust's core memory safety mechanism without GC. Rules: 1) Each value has exactly one owner. 2) Only one owner exists at a time. 3) When the owner goes out of scope, the value is dropped. This prevents leaks, double-frees, and use-after-free.

R2 — `String` is a heap-allocated, mutable, owned UTF-8 string. `&str` is an immutable string slice (borrowed reference to UTF-8 bytes). Use `String` when ownership/modification is needed; use `&str` in function signatures to accept both `String` and `&str` via coercion, avoiding unnecessary allocations.

R3 — Borrowing allows temporary access without transferring ownership. Rules: 1) Either one `&mut T` or multiple `&T` references, never both. 2) References must always be valid. 3) No dangling references. The borrow checker enforces these at compile time to guarantee memory safety.

R4 — `Result<T, E>` represents success/failure; `Option<T>` represents `Some(T)` or `None`. The `?` operator propagates errors/unwrap values, returning early on `Err`/`None`. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```

R5 — `Box<T>`: heap-allocates, single owner, moves data. `Rc<T>`: reference-counted, single-threaded shared ownership. `Arc<T>`: atomic reference-counted, thread-safe shared ownership. Use `Box` for large/recursive types, `Rc` for shared read-only single-threaded, `Arc` for concurrent sharing.

R6 — Traits define behavior; unlike Go's implicit satisfaction, Rust requires explicit `impl Trait for Type`. `dyn Trait` creates a trait object with dynamic dispatch (vtable), enabling heterogeneous collections. `T: Trait` uses static dispatch/monomorphization, generating type-specific code with zero runtime overhead.

R7 — The function fails because the compiler cannot determine which input lifetime applies to the output. Fix by tying both inputs to the same lifetime:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This guarantees the returned reference lives as long as both inputs.

R8 — `Send`: types safe to transfer ownership across threads. `Sync`: types safe to share references across threads. `Rc<T>` isn't `Send`/`Sync` due to non-atomic reference counting. `Arc<T>` uses atomic ref counting, making it `Send`+`Sync` (if `T` is), enabling safe concurrent shared ownership.

R9 — `async/await` compiles to a state machine implementing `Future::poll()`. A `Future` is lazy; it does nothing until polled. An executor (e.g., Tokio) drives futures, handles I/O, and schedules tasks. Differs from Go: Rust futures are explicit, lazy, and executor-driven; Go goroutines are eagerly scheduled by a runtime M:N scheduler with implicit threading.

R10 — `unsafe` bypasses compiler safety checks. Three capabilities: 1) Dereference raw pointers. 2) Call `unsafe` functions. 3) Access/modify `static mut` or implement `unsafe` traits. Justified for FFI, low-level hardware access, performance-critical code, or building safe abstractions over unsafe foundations.

R11 — Pattern matching exhaustively evaluates values. `match` requires covering all variants (compiler enforces exhaustiveness); `if let` is shorthand for `match` + one arm. `if let` doesn't require exhaustiveness. The compiler warns on unreachable arms or missing variants in `match`.

R12 — `Vec<T>` is a dynamically sized heap array; `[T; N]` is a fixed-size, usually stack-allocated array. When `Vec` exceeds capacity, it allocates a new larger buffer, moves/copy-constructs elements, drops the old buffer, and updates the pointer. Capacity grows geometrically (typically ×2).

R13 — Rust enums are algebraic data types: each variant can hold data, be generic, and support pattern matching. Unlike C/Java, they're first-class and exhaustive. `Option<T>` = `Some(T)` | `None`. Rust has no `null`; `Option` forces explicit handling, eliminating null pointer exceptions.

R14 — `impl` blocks define methods. `&self`: borrows immutably, `&mut self`: borrows mutably, `self`: takes ownership (consumes). Associated functions (e.g., `String::new()`) don't take `self`, acting like static constructors or utility functions.

R15 — `#[derive]` auto-implements traits. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive if: fields lack the trait (e.g., `Fn`), custom logic is required, or the trait demands specific implementation (e.g., `Drop`, `Default` with complex logic).

R16 — `Cow<'a, T>` (Clone-on-Write) holds either `&'a T` (borrowed) or `T` (owned). Useful when a function might return borrowed or owned data. Example: `fn normalize(s: &str) -> Cow<str> { if s.is_ascii() { Cow::Borrowed(s) } else { Cow::Owned(s.to_ascii_uppercase()) } }`. Avoids allocation when input already matches desired format.

R17 — `mod` declares a module, `use` imports paths, `pub` exposes visibility. File system: `mod_name.rs` or `mod_name/mod.rs` maps to a module. 2015 edition required `mod.rs` and `use` paths relative to crate root. 2018 edition allows `mod_name.rs`, resolves `use` paths relative to crate root by default, and introduces `self`, `super`, `crate` keywords.

R18 — `Pin<T>` guarantees a value's memory location won't move. Required for self-referential structs and async/await (futures may hold references to their own fields). `Unpin` is a marker trait indicating a type can be safely moved; most types are `Unpin`, but async futures are `!Unpin` to prevent invalidation.

R19 — Declarative macros (`macro_rules!`) use pattern matching on token trees and are hygienic (generated identifiers don't leak/collide). Procedural macros (`derive`, `attribute`, `function-like`) run as Rust code, generating tokens at compile time. Hygiene ensures macro-generated names don't interfere with surrounding scope, preventing accidental captures.

R20 — Zero-cost abstractions compile to efficient machine code. Iterators are lazy and optimized by LLVM (no intermediate allocations). Generics use monomorphization, generating type-specific code without vtable overhead. Trait static dispatch resolves at compile time, enabling inlining. Together, they provide high-level ergonomics with C-like performance.
