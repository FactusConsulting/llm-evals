T1 — `tofu plan` evaluates configuration against current state and live infrastructure to generate an execution plan (showing creates, updates, destroys) without making changes. `tofu apply` executes that plan, making actual API calls to provision/modify resources.

T2 — State is a JSON file mapping real-world resources to your configuration. Remote state stores this file in a shared backend (e.g., S3, GCS, Terraform Cloud), enabling team collaboration, state locking, and secure access control.

T3 — `count` uses integer indices (0, 1, 2), while `for_each` uses maps or sets of strings. `for_each` is preferred when resources have unique identifiers (e.g., names, IDs) because adding/removing items only affects that specific resource, avoiding destructive recreation of the entire set.

T4 — OpenTofu detects drift during `tofu plan` by comparing the remote state against live infrastructure. On `tofu apply`, it attempts to reconcile drift to match your config. Use `lifecycle { ignore_changes = [...] }` to explicitly allow drift on specific attributes.

T5 —
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = { name = each.key }
}
```

T6 — `terraform_remote_state` reads the entire state file, posing security risks (exposing sensitive outputs) and performance overhead. Output values are explicit and scoped. Recommended alternative: Pass outputs directly via module calls. If cross-module state is unavoidable, use `data "terraform_remote_state"` with an explicit `outputs` filter to minimize exposure.

T7 — Outputs are evaluated during the plan phase, but `remote-exec` provisioners run during apply. The kubeconfig file doesn’t exist yet, so the output is empty. Fix: Use `depends_on` on downstream resources that consume the kubeconfig, generate the config via `local-exec` during apply, or run `tofu apply` twice.

T8 — `tofu import` CLI creates a state entry but requires manual config writing. The `import` block (1.5+) generates both state and config, supports multiple resources in one block, and provides better error handling and developer experience.

T9 — A `variable` block defines input parameters passed into a module/root. An `output` block exposes computed values from a module/root to consumers.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a specific platform. Without `tofu init`, providers aren’t downloaded or initialized, causing `tofu plan` to fail with missing provider errors.

T11 — `.terraform.lock.hcl` pins exact provider versions and checksums. Committing it ensures reproducible builds, prevents supply-chain attacks, and guarantees CI/CD environments match local dev.

T12 — `tofu destroy` removes all managed resources in the current state. Target a single resource: `tofu destroy -target=module.name.resource.type.name`.

T13 — A data source reads existing infrastructure or external data without managing it. Example: `data "aws_ami" "ubuntu"` to dynamically fetch the latest Ubuntu image instead of hardcoding an AMI ID.

T14 — `variable` blocks accept external inputs. `locals` compute derived values within the configuration. Use `locals` for complex expressions, default transformations, or repeated calculations to keep code DRY and readable.

T15 — `lifecycle` controls resource behavior. `create_before_destroy` = destroy old, create new (zero-downtime). `prevent_destroy` = error on destroy (protects critical data). `ignore_changes` = skip drift on specific attributes (e.g., auto-generated tags).

T16 — `moved` block maps old resource addresses to new ones in state. It tells OpenTofu to update state references during refactoring without destroying/recreating resources.

T17 — OpenTofu builds a DAG of dependencies. Implicit = attribute references (e.g., `aws_instance.id`). Explicit = `depends_on`. `depends_on` forces sequential execution, breaking parallelism. Use sparingly to avoid bottlenecks.

T18 — 1. Split into multiple modules/workspaces (tradeoff: increased state management complexity). 2. Use `terraform plan -target` in CI (tradeoff: hides drift, requires careful scoping). 3. Cache/async data sources (tradeoff: potential stale reads). 4. Optimize backend (S3+DynamoDB, state locking) (tradeoff: minimal, but requires infra setup).

T19 — State locking uses a backend mechanism (e.g., DynamoDB) to prevent concurrent writes. If a lock persists, run `tofu force-unlock <lock-id>`. Risks: Data corruption, lost changes, or overwriting concurrent modifications.

T20 — 1. Add remote backend config (S3+DynamoDB). 2. Run `tofu init -migrate-state`. 3. State file uploads to S3, lock table created. 4. Verify with `tofu state list`. 5. Test with `tofu plan`. Existing state is safely migrated; no resources are recreated.

A1 — A playbook is a YAML file orchestrating plays. A role is a reusable collection of tasks, files, templates, and variables. A task is a single module execution within a play.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `ansible_facts['os_family']` or `ansible_os_family`.

A3 — `command` runs without shell features (safest). `shell` runs via `/bin/sh`, supports pipes/vars. `raw` runs via SSH without Python, used for bootstrapping or unmanaged hosts.

A4 — Idempotency = running a task multiple times yields the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "data" > /tmp/file.txt` (overwrites every run).

A5 —
```yaml
- name: Install htop on Debian
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel and htop on RedHat
  package:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (lowest to highest): inventory vars < group_vars < host_vars < role defaults < play vars < block vars < task vars < role vars < extra_vars. Extra_vars always win.

A7 — Use `serial: 3` in the play. Group nodes in inventory (`[rke2_control]`, `[rke2_worker]`). Use `wait_for` to check node readiness (e.g., port 6443 or kubelet health) before proceeding to the next batch.

A8 — `ansible-vault` encrypts secrets. To encrypt a single variable in a file: run `ansible-vault encrypt_string 'mysecret' --name 'db_pass'`, then paste the resulting `!vault` block into the YAML file without encrypting the whole file.

A9 — Inventory defines hosts/groups. Static = hardcoded file (INI/YAML). Dynamic = script/API that generates inventory on-demand (e.g., cloud metadata).

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task triggered by `notify`. It runs only if notified, at the end of the play. Differs from regular tasks (always run). Trigger: `notify: restart nginx`.

A12 — `ansible.cfg` sets global defaults. Common settings: `forks`, `remote_user`, `host_key_checking`, `inventory`, `roles_path`, `log_path`.

A13 — `register` saves task output to a variable. Example: `register: disk_info` then `debug: var=disk_info.stdout_lines`.

A14 — `include_tasks` = dynamic (evaluated at runtime, supports `when`). `import_tasks` = static (evaluated at parse time, faster, no conditionals). Use `include` for conditionals, `import` for performance.

A15 — Ansible Galaxy is the community hub for roles/collections. `requirements.yml` lists dependencies. Install: `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible connects. `ssh` = standard SSH. `local` = runs on control node. `network_cli` = CLI over SSH/Telnet for network devices. Use `network_cli` for routers/switches.

A17 — `delegate_to` runs a task on a different host. `run_once` runs it once across all hosts. Example: Gather remote host facts, then `delegate_to: localhost` with `run_once: true` to write a consolidated config file.

A18 — 1. Increase `forks` (tradeoff: higher memory/CPU on control node). 2. Enable `pipelining` (tradeoff: requires SSH config changes, reduces overhead). 3. Fact caching (Redis/Memcached) (tradeoff: stale facts if infra changes rapidly). 4. Use Mitogen (tradeoff: adds complexity, requires testing, but cuts runtime by 50-80%).

A19 — `{{ }}` = output/expression. `{% %}` = control flow/loops. `{# #}` = comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
    # Health check: {{ server }}
    server {{ server }};
{% endfor %}
}
```

A20 — Use `serial: 1` (or 20%). Pre-task: `uri` to deregister from LB. Deploy tasks. Post-task: `uri` health check. Wrap in `block/rescue`: if health check fails, `rescue` re-registers the failed host and aborts. Ensures zero-downtime and automatic rollback.
