DN1 — **class vs struct**: `class` is a reference type (heap-allocated, supports inheritance, null-capable, GC-managed). `struct` is a value type (stack/inline-allocated, copy-on-assign, no inheritance, non-null by default). Use `struct` for small, immutable, short-lived data that doesn't require inheritance (e.g., coordinates, IDs, math vectors). Avoid if large or frequently mutated due to copy overhead.

DN2 — **IEnumerable<T> vs IQueryable<T>**: `IEnumerable<T>` enumerates in-memory (LINQ-to-Objects). `IQueryable<T>` holds an expression tree that providers (like EF Core) translate to remote queries (LINQ-to-Entities/SQL). Distinction matters because `IQueryable` pushes filtering/sorting to the database, reducing memory/network overhead. `IEnumerable` pulls all rows first, then filters in memory.

DN3 — **async/await, Task vs ValueTask**: `async/await` compiles to a state machine, enabling non-blocking I/O while preserving logical flow. `Task` is a reference type representing async operations. `ValueTask` is a struct that avoids heap allocation when the operation completes synchronously. Use `ValueTask` for high-frequency async methods that often complete synchronously (e.g., cache hits, in-memory lookups). Avoid if the async path is common, as it adds branching overhead.

DN4 — **DI lifetimes & Scoped-in-Singleton bug**: DI injects dependencies via a container. `Transient`: new instance each resolution. `Scoped`: new per request/context. `Singleton`: one per container lifetime. **Bug**: Injecting a `Scoped` service into a `Singleton` captures the first scope's instance for the singleton's entire lifetime, causing stale state, memory leaks, or thread-safety violations. Fix: Use `IServiceScopeFactory` to create a scope manually when needed.

DN5 — **string vs ReadOnlySpan<char>, Span<T>**: `string` is heap-allocated, immutable, and copies on slicing. `ReadOnlySpan<char>` is a stack-only, zero-allocation view over memory (strings, arrays, buffers). `Span<T>` is the mutable counterpart. Use `Span<T>`/`ReadOnlySpan<char>` for high-performance parsing, string manipulation, or buffer processing to eliminate allocations and enable slicing without copying.

DN6 — **GC, Generations, LOH, IDisposable**: GC traces live objects and reclaims unreachable memory. **Generations**: Gen 0 (short-lived, frequent GC), Gen 1 (buffer), Gen 2 (long-lived, expensive GC). **LOH**: Objects >85KB, not compacted (causes fragmentation), collected only on Gen 2. `IDisposable` enables deterministic cleanup of unmanaged resources (handles, native memory). GC finalizers are non-deterministic and expensive; `Dispose` avoids relying on them.

DN7 — **ConfigureAwait(false) & SynchronizationContext**: By default, `await` captures the current `SynchronizationContext` (e.g., UI thread, ASP.NET request context) to resume on it. `ConfigureAwait(false)` skips context capture, resuming on any thread pool thread. **Use**: Library code, background tasks, non-UI/server contexts to prevent deadlocks. **Don't use**: UI apps (WPF/WinForms) or code that must resume on a specific context. `SynchronizationContext` dictates thread affinity for continuations; `false` breaks it.

DN8 — **.NET 8/9 features**: 
- **Primary constructors**: `public class Service(IOptions<Config> cfg) { ... }` injects/assigns parameters automatically.
- **Collection expressions**: `[1, 2, 3]`, `[.. array]`, `[.. list, 4]` for concise array/span creation.
- **FrozenDictionary**: Immutable, highly optimized for lookup-heavy scenarios, lower memory than `Dictionary`.
- **Example**: `public class MyService(IOptions<AppSettings> settings) { _cfg = settings.Value; }`

DN9 — **ObjectDisposedException on DbContext under high concurrency**: Likely cause: `DbContext` registered as `Transient` or manually disposed in a long-lived service, causing it to be shared across requests or disposed prematurely. EF Core's `DbContext` is thread-unsafe. **Fix**: Register as `Scoped` (`services.AddScoped<MyDbContext>()`). DI resolves one instance per HTTP request and disposes it at scope end. High concurrency exposes race conditions if shared or manually managed incorrectly.

DN10 — **record vs class, record struct**: `record` is a reference type with value-based equality, immutability by default, positional syntax, and `with` expression. `class` is mutable with reference equality. `record struct` is a value type with value equality and zero allocation. **Choose**: `record` for immutable DTOs/domain events. `record struct` for performance-critical, small, immutable data. `class` for mutable/stateful objects.

DN11 — **ref, out, in**: `ref`: Pass by reference, must be initialized before call, read/write. `out`: Pass by reference, must be assigned inside method, can be uninitialized before call. `in`: Pass by reference, read-only, prevents copying large structs. **Use**: `ref` for modifying existing values, `out` for multiple return values/parsing, `in` for performance with large structs.

DN12 — **Nullable reference types vs value types**: NRT (`string?`) is a compile-time warning system to prevent null reference exceptions; it doesn't change runtime behavior. Nullable value types (`int?`) are runtime types (`Nullable<T>`) that actually hold null. **Difference**: NRT is static analysis; `int?` is a runtime struct with `HasValue`/`Value`.

DN13 — **LINQ, method vs query syntax, deferred execution**: LINQ unifies querying across collections, DBs, XML. **Method syntax**: Fluent, chainable, preferred for complex queries. **Query syntax**: SQL-like, compiles to method syntax, better for readability. **Deferred execution**: Query isn't executed until enumerated (e.g., `foreach`, `.ToList()`), enabling composition and lazy evaluation.

DN14 — **Generic constraints**: `where T : class` (reference type), `where T : struct` (value type, non-nullable), `where T : new()` (parameterless constructor), `where T : IComparable<T>` (implements comparison). **Combine**: `where T : class, IComparable<T>, new()` for flexible, type-safe algorithms/collections requiring specific capabilities.

DN15 — **abstract class vs interface, default methods**: Abstract classes can have state, constructors, and non-virtual methods; single inheritance. Interfaces define contracts; multiple inheritance. **Default interface methods (C# 8+)**: Allow interfaces to contain implementations, enabling backward-compatible API evolution without breaking implementers. Doesn't replace abstract classes for shared state/implementation.

DN16 — **Middleware pipeline, Use/Map/Run, ordering, exception handling**: Sequential request processing. `Use()` adds middleware. `Map()` branches by path prefix. `Run()` is terminal (no `next()`). **Ordering**: Critical. Auth/error handling early, static files before MVC, routing last. **Exception handling**: `UseExceptionHandler` catches unhandled exceptions, logs, and returns error responses. Should be early to catch downstream failures.

DN17 — **Channel<T> vs BlockingCollection<T>**: `Channel<T>` is modern, async-native, supports bounded/unbounded, built-in backpressure. `BlockingCollection<T>` is older, sync/blocking, wraps `ConcurrentQueue`, less efficient for async. **Example**: `var ch = Channel.CreateBounded<int>(100);` Producer `WriteAsync` blocks when full; consumer `ReadAsync` blocks when empty. Enables backpressure without manual signaling.

DN18 — **Source Generators**: Compile-time code generation via Roslyn APIs, outputs C# source. **vs Reflection**: Reflection is runtime, slow, breaks obfuscation. SG is compile-time, zero runtime overhead. **vs IL weaving**: IL weaving modifies compiled assemblies (harder to debug, breaks tools). SG is cleaner, IDE-friendly. **Incremental generator**: Replaces `ISourceGenerator`, supports incremental compilation, caches results, integrates with MSBuild. Preferred for performance and large projects.

DN19 — **TPL Dataflow**: Message-passing pipeline/actor model. `BufferBlock<T>`: Stores messages, manual post/receive. `TransformBlock<TIn, TOut>`: Async processing with output. `ActionBlock<T>`: Async processing, no output. **vs Channels**: Dataflow is declarative, built-in backpressure, linking, completion propagation. Channels are lower-level, more flexible. Dataflow for complex workflows; Channels for simple producer-consumer.

DN20 — **Minimal APIs**: Lightweight framework using `WebApplication` builder, no controllers. **vs Controllers**: Less boilerplate, faster startup, simpler routing, but less structured for large apps. **Trade-offs**: Testability: Easy to unit test handlers, harder to mock full pipeline. Middleware: Same capabilities, configured differently. OpenAPI: Requires `Swashbuckle`/`Scalar`, less automatic. **Route groups**: `app.MapGroup("/api").WithTags("Users")`. **Endpoint filters**: Inline or registered filters for auth, validation, logging, applied per endpoint.

P1 — **list vs tuple, set vs frozenset**: `list`: mutable, ordered, indexed, allows duplicates. `tuple`: immutable, ordered, fixed size, heterogeneous, supports unpacking. `set`: mutable, unordered, unique elements, requires hashable items. `frozenset`: immutable set, hashable, can be dict key or set member.

P2 — **GIL**: Mutex allowing only one thread to execute Python bytecode at a time. **Affects**: CPU-bound multithreading (no true parallelism). **Workarounds**: Multiprocessing, C extensions releasing GIL, `asyncio` (I/O bound), external processes.

P3 — **deepcopy vs copy**: `copy` (shallow) copies container but references nested objects. `deepcopy` recursively copies nested objects. **Example**: `a = [[1,2]]; b = copy(a); b[0][0] = 99; print(a[0][0])` → `99`. Shallow copy shares inner lists, causing unexpected mutations.

P4 — **Decorators & timing example**: Functions that wrap/modify other functions. 
```python
import time, functools
def log_time(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — **Generators, yield, yield from**: Functions using `yield` to produce iterators lazily, preserving state. **vs list**: Memory efficient, infinite sequences, single-pass. `yield from`: Delegates to another generator/iterable, cleaner syntax for nesting without manual iteration.

P6 — **asyncio, run/gather/create_task, time.sleep**: Single-threaded scheduler for coroutines. `asyncio.run()`: Entry point, creates loop, runs coroutine. `asyncio.gather()`: Runs multiple concurrently, returns results. `asyncio.create_task()`: Schedules coroutine for later, returns Task. `time.sleep()` blocks the entire thread/event loop; use `await asyncio.sleep()` instead.

P7 — **MRO & diamond inheritance**: MRO is the method search order. Python 3 uses **C3 linearization**. For `D(B, C)`, MRO is `D → B → C → A → object`. `D().who()` finds `who` in `C` (since `B` doesn't override it). Prints `"C"`. C3 ensures monotonicity and left-to-right resolution, preventing diamond ambiguity.

P8 — **Metaclass vs __init_subclass__**: Metaclass controls class creation (`__new__`/`__init__`), powerful but complex. `__init_subclass__` is a hook called when a class is subclassed, simpler and instance-level. **Metaclass use**: Framework-level registration, automatic method wrapping, strict schema enforcement. **`__init_subclass__` use**: Plugin systems, automatic subclass registration, custom base behavior without metaclass complexity.

P9 — **multiprocessing vs threading vs concurrent.futures**: Threading: I/O bound, shares memory, GIL limits CPU parallelism. Multiprocessing: CPU bound, separate processes, bypasses GIL, higher overhead. `concurrent.futures`: High-level unified API (`Executor`) wrapping both. **Serialization**: `multiprocessing` uses `pickle` to send data between processes. Unpicklable objects (file handles, locks, lambdas) fail. Use `spawn`/`forkserver` for cross-platform safety.

P10 — **__slots__**: Declares fixed attributes, prevents `__dict__` creation. **Use**: Memory optimization, performance, preventing accidental attribute assignment. **Impact**: Eliminates per-instance `__dict__` overhead, significantly reducing memory. Prevents dynamic attribute addition.

P11 — **Virtual environments**: Isolated Python environment with its own packages/interpreter. **Why**: Dependency isolation, reproducibility, avoids system conflicts. `venv`: Standard library, lightweight. `virtualenv`: Third-party, older, more features. `conda`: Data science focused, manages non-Python dependencies, cross-platform.

P12 — **Comprehensions vs map/filter**: Comprehensions (`[x for x in lst if x > 0]`) are readable, Pythonic, often faster. `map`/`filter` are functional, lazy in Python 3, useful with C-implemented functions. **Prefer**: Comprehensions for readability/simple logic. `map`/`filter` for performance with built-ins or functional chaining.

P13 — **== vs is, interning**: `==` checks value equality. `is` checks object identity. **Interning**: CPython caches small integers (-5 to 256) and some strings for memory/performance. `a is b` returns `True` for small ints because they reference the same cached object.

P14 — **\*args, \*\*kwargs, /, \***: `*args`: Variable positional arguments (tuple). `**kwargs`: Variable keyword arguments (dict). `/`: Positional-only parameters (before `/`). `*`: Keyword-only parameters (after `*`). **Use**: Flexible APIs, configuration, argument forwarding.

P15 — **Context managers**: `with` ensures cleanup (`__exit__`) even on exceptions. **Class-based**: `__enter__`/`__exit__`. **Generator-based**: `@contextmanager` simplifies function implementation. **Example**: Database connection pooling, lock acquisition, temporary directory creation.

P16 — **Type hinting**: `Union`/`Optional`: Multiple types, `Optional[T]` = `Union[T, None]`. `Literal`: Restricts to specific values. `TypeVar`: Generic type variables with constraints. `Protocol`: Structural subtyping (duck typing). `mypy`/`pyright`: Static analyzers check types at compile time, catch mismatches, improve IDE support.

P17 — **Data model (dunder methods)**: `__repr__`: Unambiguous, developer-focused. `__str__`: Readable, user-focused. `__eq__`: Value equality. `__hash__`: Hashability (must be consistent with `__eq__`). `__getattr__`: Called when attribute not found. `__getattribute__`: Called for every access (dangerous). Define `__eq__` without `__hash__`: Sets `__hash__ = None`, making instances unhashable (can't be dict keys/set members).

P18 — **Descriptors**: Protocol: `__get__`, `__set__`, `__delete__`. **Used by**: `property` (get/set), `classmethod` (binds to class), `staticmethod` (no binding). **Under the hood**: `__getattribute__` checks for descriptors and calls them. Enables reusable attribute logic across instances/classes.

P19 — **Import system**: Relative: `from . import mod` (relative to package). Absolute: `from pkg import mod`. `sys.path`: Directories searched. `PYTHONPATH`: Env var adding to `sys.path`. `__init__.py`: Marks directory as package, runs on import. Namespace packages: `__init__.py` absent, allows split packages. **Finder**: Locates modules in `sys.path`. **Loader**: Loads/executes module. `importlib` standardizes this.

P20 — **dataclasses vs attrs/Pydantic**: `dataclasses`: Built-in, generates `__init__`/`__repr__`/`__eq__`. `__post_init__` for validation. `field()` for defaults/factories. `frozen=True` for immutability. `attrs`: Older, more flexible, better inheritance. `Pydantic`: Runtime validation, type coercion, serialization, FastAPI integration. **Choose Pydantic** for API boundaries/validation/serialization. **Choose dataclasses** for simple data containers/performance/built-in convenience.
