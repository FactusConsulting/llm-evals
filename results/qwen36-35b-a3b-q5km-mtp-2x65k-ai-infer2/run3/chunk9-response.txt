SC1-A
The pods fail because Kubernetes Pod Security Standards (PSS) `Restricted` enforces `runAsNonRoot: true` at the pod level, which implicitly requires an explicit `runAsUser` set to a non-zero UID (typically ≥1000). The `Baseline` profile allowed containers to run as root (UID 0) if `runAsNonRoot` wasn't explicitly set to false. The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`. When the namespace policy shifted to `Restricted`, the kubelet rejects the pod spec because `runAsNonRoot: true` is present but `runAsUser` is missing/zero, causing the container runtime to refuse startup and Kubernetes to cycle the pod into `CrashLoopBackOff`.

*(Requires `jq`. Filters all namespaces for `CrashLoopBackOff`, extracts namespace, pod name, and pod-level securityContext as JSON.)*

SC1-C
**Immediate Fix:** Update deployments to add `securityContext.runAsUser: 1000` (or the app's expected UID) at the container or pod level. Alternatively, rebuild images with `USER 1000` in the Dockerfile.
**Manifest Changes:** Add `securityContext.runAsUser: 1000` and `runAsNonRoot: true` to all pod specs. Use a Helm/Kustomize patch to apply globally.
**CI Gate:** Add a policy check (e.g., `kubeval` + `opa`/`kyverno` or `trivy config`) that fails builds if `runAsNonRoot: true` exists without `runAsUser` set to a non-zero value. Enforce base image pinning by digest.
**Rollout:** Use a rolling update with `maxSurge: 0` and `maxUnavailable: 1` per deployment, or blue/green via Ingress routing. Update image tags, let the rollout controller handle pod replacement, and verify health checks before proceeding.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous. WAL segments are shipped over the network and replayed on the replica. During an outage, promoting the replica cuts off replication immediately. Any WAL not yet shipped or replayed is permanently lost. The data loss window equals the replication lag at promotion time. To quantify: check `pg_stat_replication` for `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn` differences, or query `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()`. Also check `pg_stat_replication.application_name` lag metrics and network throughput to the replica.

SC2-C
**Connection Management:** Use RDS Proxy instead of PgBouncer. RDS Proxy handles connection pooling, failover transparently, and reduces login retry storms during promotion.
**DNS Failover:** Route53 failover routing policy with health checks on the RDS endpoint. Applications should use the Route53 endpoint, not hardcoded IPs.
**Retry Logic:** Implement exponential backoff with jitter in the application driver.
**RPO < 1s:** True synchronous cross-region replication is impossible due to latency. Recommend Aurora Global Database, which uses a dedicated, optimized async replication layer achieving ~1s RPO. Alternatively, accept async RDS replication with strict lag monitoring and automated promotion triggers. Aurora Global DB is recommended for regulated workloads requiring predictable cross-region RPO.

5. **JVM Memory/Performance:** Bare-metal vs container resource limits. *Fix:* Set precise `requests/limits`, use `CGroup v2`, tune JVM heap (`-Xms/-Xmx`), and use node affinity for high-memory nodes.

**SQL Lock Diagnostic:**
```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid,
       blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS current_statement_in_blocking_process
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC6-C
- **Direct Connect:** Dedicated 10Gbps+ link, lower latency, predictable cost. Fits ZT: traffic still encrypted (MACsec/IPsec), routing via BGP. Requires physical circuit provisioning.
- **ECMP VPN:** Add second tunnel, configure BGP ECMP. Scales bandwidth, uses existing IPsec. Cost: low. Routing: BGP multipath. ZT compatible but encryption overhead remains.
- **Tailscale/Netbird:** WireGuard-based mesh, zero-config routing, automatic key rotation. Cost: subscription/per-device. Bandwidth: limited by WireGuard overhead but sufficient for most workloads. Routing: subnet routers + tailnet control. ZT native: identity-based, encrypted, least-privilege.
**Recommendation:** Netbird/Tailscale for rapid ZT deployment + Direct Connect for high-throughput data sync. ECMP VPN is a stopgap.

SC10-C
**Failover Sequence:**
1. **Detection:** Prometheus/Grafana monitors site health (ping, DB heartbeat, K8s API). Site down = 3 consecutive failures + etcd quorum loss.
2. **DNS Failover:** GSLB (Route53/Cloudflare) switches traffic to Dallas. TTL < 60s.
3. **Patroni Promotion:** etcd triggers async promotion. Synchronous standby demoted.
4. **Redis/RabbitMQ/MinIO:** Sentinel promotes master. RabbitMQ federation syncs. MinIO site replication catches up.
5. **State Update:** Ansible/Terraform updates OpenTofu state to reflect new primary.
**Split-Brain Prevention:** etcd quorum, fencing (STONITH), Patroni `failover_threshold`, MinIO erasure coding quorum.
**Failback:** Once Chicago recovers, rejoin as standby. Patroni async replication resumes. MinIO replication syncs delta. DNS switches back during maintenance window. Verify data consistency before cutover.
