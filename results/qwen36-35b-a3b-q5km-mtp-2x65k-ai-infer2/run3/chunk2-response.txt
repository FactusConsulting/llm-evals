K1 — A **Deployment** manages stateless workloads with interchangeable pods, random names, and no guaranteed startup order. A **StatefulSet** manages stateful workloads with stable, unique network IDs, ordered deployment/scaling, and stable persistent storage per pod.

K2 — A `ClusterIP` Service creates an internal virtual IP. `kube-proxy` watches the API server and programs `iptables` or `IPVS` rules on each node to load-balance traffic hitting that IP:Port to the healthy backend pod IPs.

K3 — **PersistentVolume (PV)**: cluster-provisioned storage resource (static or dynamic). **PersistentVolumeClaim (PVC)**: user request for storage. **StorageClass (SC)**: template for dynamic PV provisioning. Relation: A PVC binds to a PV (or triggers an SC to create one). Once bound, the PVC claims the PV's capacity.

K4 — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` for OOMKilled, exit codes, or probe failures. 3. Verify resource limits/requests match actual usage. 4. Check app dependencies (DB connectivity, missing config files, invalid env vars). 5. Inspect liveness/readiness probe configurations.

K5 — CoreDNS provides internal DNS resolution for `svc.cluster.local` domains. If CoreDNS pods are down, internal service discovery fails (pods can't resolve service names), but direct IP communication and external DNS resolution remain unaffected.

K6 — The scheduler uses **filtering** (removes nodes failing constraints) then **scoring** (ranks remaining nodes). Factors: 1. Resource requests vs node capacity (balance CPU/memory). 2. Taints/tolerations & node selectors. 3. Node/pod affinity & anti-affinity rules. 4. Topology spread constraints. 5. Resource pressure (disk, memory pressure).

K7 — Yes, it will schedule: 3.5GB + 256Mi ≈ 3.75GB < 4GB. At runtime, if it uses 600Mi, it exceeds the `limits.memory: 512Mi` hard cap. The kernel OOM killer will terminate the container (`OOMKilled`), and Kubernetes will restart it.

K8 — 1. External LB routes traffic to the Ingress Controller's exposed port. 2. Ingress Controller reads the Ingress resource and configures NGINX routes. 3. NGINX matches host/path and forwards to the Kubernetes Service. 4. Service resolves to backend pod IPs via Endpoints. 5. `kube-proxy`/`iptables` on the node performs the final DNAT to the pod's network namespace.

K9 — A `NetworkPolicy` restricts pod-to-pod and pod-to-external traffic. Default behavior (no policies): all traffic allowed. When a policy is applied: only traffic explicitly allowed by the policy is permitted; all other traffic is denied.

K10 — **RollingUpdate** gradually replaces old pods with new ones (zero downtime). **Recreate** terminates all old pods before starting new ones (downtime). Choose Recreate for stateful apps that cannot run concurrent versions or require strict sequential updates.

K11 — A namespace provides virtual cluster isolation within a physical cluster. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it reveals: 1. Pod events (scheduling, pull, probe failures). 2. Container states & exit codes. 3. Resource usage & limits. 4. Volume mounts & config references. 5. Conditions & node affinity status.

K13 — A `ConfigMap` stores non-sensitive configuration data. Pods consume it via: 1. Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`). 2. Volume mounts (files appear in the container filesystem).

K14 — **ClusterIP**: internal-only virtual IP. **NodePort**: exposes the service on a static port on each node's IP. **LoadBalancer**: provisions a cloud provider external load balancer with a public IP.

K15 — A `DaemonSet` ensures one pod runs on every node (or subset via selector). Use it for node-level daemons: logging agents, metrics collectors, CNI plugins, or storage drivers. Deployments run a fixed replica count, not node-bound.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Use case: Taints for dedicated GPU nodes (repel general workloads); Affinity for zone-aware scheduling (attract pods to specific AZs).

K17 — An Operator is a custom controller that manages complex stateful applications using CRDs and reconciliation loops. Unlike standard controllers, it encapsulates domain-specific operational knowledge (backups, upgrades, failover). It solves manual ops overhead for stateful workloads.

K18 — etcd uses Raft consensus with linearizable reads/writes. Quorum loss makes the cluster read-only/unwritable to prevent split-brain. If 2/3 nodes are lost, quorum cannot be formed. Recovery requires restoring from a backup or adding a 4th node to form a new quorum, then restoring data.

K19 — RBAC controls access via Roles/ClusterRoles (permissions) and RoleBindings/ClusterRoleBindings (assignments). Manifest for read-only pod/log access in a namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev-ns
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev-ns
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` means queries with <5 dots are tried against multiple suffixes (`<name>.<ns>.svc.cluster.local`, `.svc.cluster.local`, `.cluster.local`, then external), causing excessive DNS queries. Fix: set `dnsConfig: { ndots: 1 }` in the pod spec, or use fully qualified domain names (FQDNs) in the application config.

D1 — `git merge` preserves history with a merge commit. `git rebase` rewrites history by replaying commits linearly. Avoid rebasing on shared/public branches to prevent forcing others to reconcile divergent histories.

D2 — **TCP**: connection-oriented, reliable, ordered, flow/congestion control. **UDP**: connectionless, unreliable, low-latency. TCP: HTTP, SMTP. UDP: DNS, VoIP, live video streaming.

D3 — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to unpredictable results. Example: two threads incrementing a shared counter without a mutex, resulting in lost updates.

D4 — **Symmetric**: single key for encryption/decryption (fast). **Asymmetric**: public/private key pair (secure key exchange). TLS uses asymmetric encryption during the handshake to securely exchange a session key, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates a read-only image layer. Layer caching reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., install dependencies before copying source code) to maximize cache hits and speed up builds.

D6 — 1. Check upstream service logs/metrics for errors or timeouts. 2. Verify rate limiting/throttling configurations. 3. Check resource exhaustion (CPU/memory/CPU throttling). 4. Inspect circuit breakers or retry storms causing cascading failures. 5. Validate load balancer health checks.

D7 — CAP theorem: a distributed system can only guarantee two of Consistency, Availability, Partition tolerance. **CP**: CockroachDB/HBase (prioritizes data accuracy; blocks requests during partitions). **AP**: DynamoDB/Cassandra (prioritizes availability; serves potentially stale data during partitions).

D8 — **Horizontal**: add more nodes/instances. **Vertical**: increase CPU/RAM of existing node. Horizontal scaling requires: stateless application design, external session/state storage, database sharding/partitioning, and load balancing.

D9 — An environment variable is a dynamic value passed to processes. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict syntax, key-value pairs, arrays. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: universal parsing, strict validation. YAML advantage: readability, less verbose, easier for config files.

D11 — A REST API is an architectural style using HTTP methods. **GET**: retrieve resource. **POST**: create new resource. **PUT**: replace/update entire resource. **DELETE**: remove resource.

D12 — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes from upstream updates, and simplifies debugging.

D13 — **Compiled**: source code is translated to machine code before execution (C, Rust). **Interpreted**: source code is executed line-by-line at runtime by an interpreter (Python, JavaScript). (Note: modern languages often use JIT/AOT compilation, but this is the foundational distinction.)

D14 — A **reverse proxy** sits in front of servers, routing client requests to backends. **Forward proxy** sits in front of clients, routing outbound requests. Reverse proxy use cases: Nginx (load balancing/SSL termination), HAProxy (high-performance TCP/HTTP routing).

D15 — A deadlock occurs when two+ processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait.

D16 — Eventual consistency guarantees all replicas will converge if no new updates occur. Cassandra uses tunable consistency levels (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`, `SERIALIZABLE`). For read-after-write consistency, use `SERIALIZABLE` or `QUORUM` for both reads and writes, or use Lightweight Transactions (`IF` clauses) for strict ordering.

D17 — mTLS authenticates both client and server using X.509 certificates. Handshake: ClientHello → ServerHello+Cert → ServerKeyExchange → ClientKeyExchange+Cert → certificate verification → symmetric session establishment. Commonly used in: service meshes (Istio/Linkerd), zero-trust architectures, and internal microservice communication.

D18 — A hash table maps keys to values via a hash function → array index. Collision resolution: **chaining** (linked lists at each bucket), **open addressing** (probing: linear, quadratic, double hashing). Time complexity: average O(1) for insert/lookup/delete; worst-case O(n) when all keys collide.

D19 — A circuit breaker prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal traffic), **Open** (fail fast after error threshold), **Half-open** (allow limited test requests). It complements retries: use circuit breakers alongside exponential backoff to avoid overwhelming recovering services.

D20 — **Optimistic**: assumes no conflict, validates at commit (e.g., row versioning, `SELECT ... FOR UPDATE NO WAIT`, or `UPDATE ... WHERE version = X`). **Pessimistic**: locks resources upfront (`SELECT ... FOR UPDATE`). Choose optimistic for high read/low write contention; pessimistic for high write contention or critical financial transactions requiring strict isolation.
