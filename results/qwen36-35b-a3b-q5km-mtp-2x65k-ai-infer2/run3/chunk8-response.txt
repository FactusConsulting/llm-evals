CL1 — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, runtime, data, and apps. Example: AWS EC2. PaaS provides a managed runtime/environment; you manage apps and data, provider handles OS, middleware, and infra. Example: Google App Engine. SaaS delivers a fully managed application; you only use it, provider manages everything. Example: AWS WorkSpaces or Salesforce.

CL2 — The Shared Responsibility Model divides security: provider secures the cloud (physical, global infra, hypervisor, managed service components); you secure what you put in it (data, IAM, OS/network config, apps). IaaS VM: Provider = infra/hypervisor; You = OS patching, network config, apps, data. Managed K8s: Provider = control plane, node OS patching, infra; You = K8s RBAC, network policies, app images, secrets, data. SaaS (M365): Provider = app, infra, compliance defaults; You = user accounts, data, access policies, MFA, device compliance.

CL3 — VPC is an isolated virtual network. Subnet is an IP range within a VPC, tied to an AZ. Security Group (SG) is instance-level, stateful, allow-only. NACL is subnet-level, stateless, allow/deny. Traffic flows VPC → Subnet (NACL) → Instance (SG). Stateful (SG) automatically allows return traffic. Stateless (NACL) requires explicit allow rules for both inbound and outbound.

CL4 — A landing zone is a pre-configured, secure multi-account baseline with networking, logging, IAM, and guardrails. OUs group accounts by function/environment (Sandbox, Dev, Prod, Shared). Guardrails (SCPs/policies) enforce compliance, budget limits, and region restrictions. Shared networking (Transit Gateway/Azure Hub-and-Spoke) centralizes inter-VPC/VNet routing and on-prem connectivity. Centralized logging aggregates security/audit logs in a dedicated account. Single-account causes blast radius, permission sprawl, billing opacity, compliance risk, and deployment bottlenecks.

CL5 — IaC manages infrastructure via version-controlled, automated definitions. Terraform/OpenTofu: Declarative HCL, multi-cloud, mature ecosystem. Best for complex, multi-cloud, or vendor-agnostic infra. Pulumi: Imperative/Declarative using general-purpose languages. Best for dev-heavy teams needing dynamic logic. CloudFormation/Bicep: AWS-native declarative. Best for AWS-only, tight CI/CD integration. Crossplane: K8s-native IaC using CRDs. Best for GitOps workflows and teams already on K8s.

CL6 — HPA scales pods based on CPU/memory/custom metrics. VPA adjusts pod resource requests/limits (doesn't change replica count). Cluster Autoscaler adds/removes nodes when pods can't schedule. KEDA scales based on external event queues (Kafka, RabbitMQ, HTTP). Use KEDA over HPA when scaling should be driven by event backlog/throughput rather than static resource utilization.

CL7 — Define RPO/RTO based on business impact. Active-active: both regions serve traffic, lowest RPO/RTO, highest cost/complexity. Active-passive: one serves, one standby, higher RPO/RTO, lower cost. DB replication: sync (strong consistency, latency-bound) vs async (eventual consistency, distance-tolerant). DNS failover (Route53/Traffic Manager) uses health checks to route to healthy region. Externalize state to managed services. Pilot light: minimal DR infra, scales up on failover. Warm standby: reduced but running prod-like env. Multi-site active-active: full dual-region capacity. Cost scales with active capacity and data transfer.

CL8 — GitOps uses Git as single source of truth; controllers continuously reconcile cluster state with manifests. ArgoCD: UI-first, push/pull, app-of-apps, visual tracking. Flux: Git-native, pull-only, tightly integrated with GitHub/GitLab, CLI-focused. Secrets: Sealed Secrets (encrypted in Git), External Secrets Operator (syncs from cloud/Vault), Vault (dynamic secrets). Manual drift is overwritten on next reconciliation, enforcing consistency and providing audit trails via Git history.

CL9 — Use a StatefulSet for stable IDs and ordered lifecycle. PV/PVC with `local` storageClass and `volumeBindingMode: WaitForFirstConsumer` binds to the node with local disk. Headless service (`clusterIP: None`) enables direct pod DNS resolution. Init containers handle pre-start setup and volume checks. ConfigMaps mount as volumes at specific filesystem paths via `subPath`. PDB (`minAvailable`) prevents simultaneous pod eviction. Architecture: 1:N StatefulSet, local PVs, headless svc, init containers, configMap volumes, PDB for disruption tolerance.

CL10 — K8s Service Account is native pod identity with no cloud auth. Workload Identity (GCP/Azure) and IRSA (AWS) map K8s SAs to cloud IAM identities via OIDC. Mounting static credentials is bad practice: leaks, rotation issues, violates least privilege, and pod compromise equals cloud compromise. Workload identity federation solves this with short-lived, OIDC-issued tokens, scoped permissions, automatic rotation, and no static keys in pods/images.

CL11 — Object storage (S3/Blob): key-value, HTTP API, scalable, unstructured data. Durability: 11 9s. Availability: 99.99%+. Block storage (EBS/Managed Disk): raw volumes, low latency, random I/O, attached to VMs. Durability: 99.999%. Availability: AZ-bound unless replicated. File storage (EFS/Azure Files): NFS/SMB, shared POSIX/SMB filesystem. Durability: 11 9s. Availability: Regional, concurrent access. Use object for backups/static assets, block for OS/databases, file for shared configs/legacy apps.

CL12 — Zero-trust K8s: default-deny Network Policies, service mesh (Istio/Linkerd) for mTLS and identity-based routing, pod identity (IRSA/Workload Identity), admission controllers (OPA/Kyverno) to enforce policies, image signing (Cosign) verified at admission, runtime security (Falco) for syscall monitoring, secrets via External Secrets/Vault. Differs from perimeter security by assuming breach, micro-segmenting traffic, verifying every request, and using identity/context rather than network boundaries.

CL13 — CDN is a distributed edge cache network that proxies content closer to users. Origin fetches first, caches at PoPs, serves subsequent requests locally. Services: CloudFront, Azure CDN, Fastly. Use CDN for static/dynamic delivery, DDoS mitigation, SSL termination, and global latency reduction. Direct origin causes high latency, single point of failure, higher origin load, and no edge caching.

CL14 — Region: geographic area with multiple AZs. AZ: discrete data centers with independent power/cooling/network, low-latency interconnects. Multi-AZ deployment protects against data center failure and ensures high availability. Zonal resources (EBS, most VMs) are tied to a single AZ. Regional resources (S3, Route53, ALB) span multiple AZs and provide higher availability.

CL15 — Managed DB (RDS/Cloud SQL/Azure SQL) offloads provisioning, patching, backups, replication, monitoring, and automated failover. Running on a VM requires manual OS/DB management, backup scripting, HA setup, scaling, and security patching. Managed services improve reliability and reduce operational overhead but cost more and limit low-level access.

CL16 — IAM Users: human/service identities. Groups: collections of users. Roles: temporary credentials for entities (users, services, external). Policies: JSON documents defining permissions. Least privilege: grant only necessary permissions. Apply via scoped roles/policies, avoid `*:*`, use conditions, enforce MFA, and conduct regular access reviews.

CL17 — Serverless: managed compute where provider handles scaling/patching; pay per execution. Lambda/Functions/GCF differ in runtime support, cold start behavior, and ecosystem integration. Cold starts: container initialization delay on first/infrequent invocation; matters for latency-sensitive apps. Poor fit: long-running processes, stateful apps, predictable high-throughput (reserved instances cheaper), strict compliance/network constraints, heavy CPU/GPU workloads.

CL18 — Ingress Resource: standard K8s API, relies on controller (nginx/ALB), TLS termination at controller. Gateway API: newer, multi-protocol, separates Gateway vs HTTPRoute, vendor-neutral, TLS at Gateway. Cloud LB Annotations: direct cloud LB provisioning, TLS at cloud LB. Service Mesh Ingress: mesh gateway handles traffic/mTLS, TLS at mesh. Use Gateway API over Ingress for multi-protocol support, fine-grained traffic splitting, vendor neutrality, and complex routing policies.

CL19 — RI/SP: commit 1-3yr for predictable workloads (30-70% savings). Spot/Preemptible: fault-tolerant/batch/dev (up to 90% savings). Right-size via utilization monitoring and auto-scaling. Storage tiering: lifecycle policies to Glacier/Archive. Idle detection: unattached volumes, idle LBs, unused IPs. FinOps: cross-functional culture, tagging, budget alerts. Showback/chargeback: tag-based allocation, dashboards (Cost Explorer/Kubecost), monthly team reports. Tools: native + third-party (CloudHealth, Datadog). Processes: tagging standards, monthly optimization reviews, automated cleanup.

CL20 — Multi-cloud: abstract via Terraform/Crossplane/K8s, avoid vendor-specific managed services. Networking: Cloud VPN/ExpressRoute/Direct Connect, complex routing/latency/cost. Identity: OIDC federation, centralized IdP mapped to cloud roles. Trade-offs: higher complexity, skill fragmentation, data transfer costs, inconsistent tooling, operational lock-in increases. Justified: regulatory/data residency, catastrophic vendor risk, best-of-breed needs, M&A. Unnecessary: most startups/SMBs, when vendor maturity is high, when complexity outweighs risk mitigation.

OT1 — Purdue Model (ISA-95) industrial automation hierarchy. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, DCS). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations management (MES, production planning). Level 4: Business planning (ERP, finance). Level 5: Enterprise/Cloud (external partners, analytics).

OT2 — IT focuses on confidentiality/integrity/availability, fast patching, frequent updates, user-centric. OT focuses on availability/safety/integrity, real-time constraints, legacy systems, proprietary protocols. OT patching requires maintenance windows, vendor validation, and can cause downtime/safety risks; IT patching is routine, automated, and low-risk.

OT3 — IDMZ is a segmented buffer between IT and OT. Traffic: strictly controlled bidirectional or one-way. IT→OT: commands/updates via IDMZ. OT→IT: process data/alarms via IDMZ. Direct L4→L1 bypasses security controls, exposes critical systems to IT threats, enables lateral movement, and risks safety incidents.

OT4 — Modbus TCP: L1/L2, PLC communication, simple, unencrypted. OPC UA: L2/L3, secure, platform-independent, metadata-rich. EtherNet/IP (CIP): L1/L2, industrial Ethernet, real-time, Allen-Bradley dominant. PROFINET: L1/L2, real-time Ethernet, deterministic, Siemens dominant. MQTT: L3/L4, lightweight publish/subscribe, cloud/edge analytics, not real-time control.

OT5 — Data diode: hardware-enforced one-way communication, physically prevents return traffic. Firewall: software/hardware, inspects traffic, allows/denies bidirectionally. Use diode for strict OT→IT monitoring where return traffic is unnecessary. Limitation: cannot allow acknowledgments/commands back, less flexible than firewalls.

OT6 — Flow: PLCs → Historian (L2) → OPC UA Server → Edge Gateway (protocol translation/buffering) → MQTT Broker → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: IDMZ between IT/OT, edge gateway in DMZ/OT edge, OPC UA over TLS, MQTT with mTLS/SAS tokens, cloud WAF/Zero Trust, network segmentation at each hop.

OT7 — IEC 62443 zones: logical groups of assets with similar security requirements. Conduits: communication paths between zones. Define zones by function, risk, and security level. Model: Zone 1 (Corporate L4), Zone 2 (Engineering L3), Zone 3 (SCADA/Historian L2), Zone 4 (PLCs/SIS L1/0). Conduits: strictly controlled firewalls/data diodes between zones. SIS isolated zone with physical/logical separation.

OT8 — VLANs: segment by function/line (e.g., VLAN 10: Line 1 PLCs, 20: Line 2, 30: HMIs, 40: SCADA). Firewalls: at VLAN boundaries and IT/OT edge, enforce strict ACLs. Switches: managed industrial switches, port security, disable unused ports. Remote access: jump host in DMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: phased rollout, parallel run, maintenance windows, backup configs, rollback plan, test in staging.

OT9 — BPCS: basic process control (PLCs/DCS) for normal operation. SIS: safety instrumented system for emergency shutdown, independent of BPCS. IEC 61511: functional safety standard for SIS, defines SIL ratings. SIS must be isolated/air-gapped to prevent cyber attacks from compromising safety functions. Ransomware on SIS could disable shutdowns, causing catastrophic failure, environmental damage, or loss of life.

OT10 — PLC: programmable logic controller, discrete control, fast, rugged, machine/line-level. DCS: distributed control system, centralized architecture, integrated I/O, continuous processes (chemical/oil). SCADA: supervisory software/hardware for monitoring, data collection, HMI, remote control over wide areas. Coexist: yes; PLCs/DCS handle control, SCADA provides supervisory layer.

OT11 — Remote access: isolated jump hosts in DMZ, MFA required, session recording for audit, time-limited/scoped vendor access, no direct OT access. Direct RDP to HMI from corporate is unacceptable: exposes OT to IT threats, bypasses segmentation, violates least privilege, and enables lateral movement.

OT12 — Detection: network IDS/IPS, OT protocol anomaly detection, asset inventory baseline, EDR on IT/DMZ. Inventory: passive monitoring, tag assets, map to Purdue levels. IR: contain (isolate VLANs/switches), eradicate (patch/remove), recover (clean backups), post-incident review. Coordination: notify control room, switch to manual/local control if needed, ensure safe process state before isolation. Operator role: monitor process, execute manual overrides, verify safety, communicate status, avoid compromised systems.

OT13 — HMI: Human-Machine Interface, graphical display for operators to monitor/control processes in real-time, manage alarms, perform manual overrides. Differs from engineering workstation: HMI is for runtime operations; EWS is for programming, configuration, diagnostics, and offline engineering tasks.

OT14 — Historian: time-series database for process data (temperatures, pressures, flows). Important for trend analysis, compliance, optimization, troubleshooting. Plant historian (L3): high-frequency, raw process data for operations. Enterprise historian (L4): aggregated, business-relevant data for ERP/finance, lower frequency, longer retention.

OT15 — Ladder logic: graphical programming language mimicking relay circuits. Executes on PLCs. Dominant because it's familiar to electricians, easy to troubleshoot, deterministic, standards-based (IEC 61131-3), supports legacy codebases, and has robust safety certification.

OT16 — RTU: Remote Terminal Unit, designed for harsh environments, long-distance communication, telemetry, SCADA integration. Differs from PLC: PLCs for local, fast, discrete control; RTUs for remote, distributed, analog/telemetry, often battery/solar powered. Deploy RTUs in pipelines, water distribution, wind farms, remote monitoring stations.

OT17 — Analog: continuous signals (4-20mA, 0-10V). Digital: discrete signals (on/off, pulses). 4-20mA preferred over 0-20mA because 4mA "live zero" indicates wire break/failure (0mA = fault), whereas 0-20mA cannot distinguish between zero process value and broken wire.

OT18 — OT asset inventory: complete list of hardware, software, firmware, network connections. Foundation of security: enables risk assessment, patching, compliance. Tools: passive monitoring (packet capture, protocol analysis), active scanning (ping, SNMP, Modbus scan). Active scanning dangerous: can crash legacy devices, cause process disruption, trigger safety systems, generate unexpected network traffic.

OT19 — MITRE ATT&CK for ICS: tactics/techniques specific to industrial control systems. 5 tactics/examples: Reconnaissance (SCADA-101), Initial Access (SCADA-103), Execution (SCADA-104), Lateral Movement (SCADA-110), Impact (SCADA-113). Differs from Enterprise ATT&CK: focuses on safety, availability, physical processes, legacy protocols, real-time constraints. Use to map defenses, identify gaps, prioritize controls, simulate attacks, align with IEC 62443.

OT20 — Log collection: passive taps, OPC UA/MQTT brokers, SIEM agents on DMZ, avoid direct OT polling. SIEM integration: normalize OT logs (Syslog/CEF), correlate with IT logs. OT rules: protocol anomalies (unexpected Modbus writes, HMI config changes, SIS bypass). Triage: OT engineers validate process impact, IT analysts handle threat intel. Staffing: IT analysts (threat hunting), OT engineers (process safety, protocol expertise). False positives: predictable OT cycles/maintenance; tune rules, baseline behavior. Unauthorized PLC firmware: isolate segment, verify with engineering, check change management, restore signed backup, investigate source, update patch management.
