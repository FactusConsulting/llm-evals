G1 — A slice is a lightweight descriptor containing a pointer to an underlying array, length, and capacity. An array is a fixed-size value type. When appending to a slice that has reached capacity, Go allocates a new backing array (typically doubling capacity), copies existing elements, updates the slice header, and returns the new slice.

G2 — `var x int` declares a variable with explicit type and zero value. `x := 0` is a short variable declaration that infers type and requires at least one new variable on the left side. You cannot use `:=` at package level, when redeclaring all variables on the LHS, or when explicit type annotation is required (e.g., `var x int = 0` vs `x := 0` where type inference might differ).

G3 — A goroutine is a lightweight, user-space thread managed by the Go runtime. Unlike OS threads (1:1 mapping, fixed stacks, expensive context switches), goroutines use M:N scheduling, have dynamically growing stacks, and cheap context switches. The GMP model: G=goreoutine, M=OS thread, P=processor/context. The scheduler multiplexes Gs onto Ms using Ps to maintain parallelism and handle blocking syscalls.

G4 — Channels are typed conduits for communication and synchronization. Unbuffered channels block both sender and receiver until both are ready. Buffered channels have a capacity; send blocks only when full, recv blocks only when empty. Sending to a full buffered channel blocks until space is available or the channel is closed.

G5 — The `context` package propagates cancellation, deadlines, timeouts, and request-scoped values across API boundaries. Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
client.Do(req) // cancels automatically on timeout
```

G6 — Go uses implicit interface satisfaction (duck typing): any type implementing the methods automatically satisfies the interface. Unlike Java/C#, no `implements` keyword is needed. `interface{}` (Go <1.18) or `any` (Go 1.18+) matches any type. Powerful for generic abstraction, but dangerous because type assertions can panic at runtime and bypass compile-time safety.

G7 — Go's memory model guarantees visibility only through synchronization (channels, `sync` primitives). The code is unsafe due to a data race: `ready` and `data` are read/written concurrently without synchronization, and `for !ready {}` is a busy-wait spinlock that may never see the update due to CPU caching/compiler reordering. Fix: use `sync.Once`, `atomic.Bool`/`atomic.String`, or a channel to signal readiness.

G8 — `sync.Mutex` provides exclusive access. `sync.RWMutex` allows multiple concurrent readers or one writer. `sync.Map` is optimized for read-heavy workloads or disjoint key sets (different keys rarely accessed by same goroutine). Trade-offs: `sync.Map` has higher per-operation overhead and worse cache locality; a regular `map` + `Mutex` is generally faster for mixed workloads.

G9 — Go modules manage dependencies. `go.mod` declares module path, Go version, and direct dependencies. `go.sum` stores cryptographic hashes of dependency versions for integrity verification. `go mod tidy` removes unused dependencies, adds missing ones, and updates `go.sum`. MVS (Minimum Version Selection) picks the lowest version of each dependency that satisfies all direct/indirect constraints, preventing version skew.

G10 — `defer` schedules a function call to run after the surrounding function returns. Multiple defers execute in LIFO order. Common loop gotcha: variables captured by deferred closures are evaluated at defer time, not declaration time. Fix: pass as arguments `defer func(v int) { fmt.Println(v) }(i)`.

G11 — A pointer holds a memory address. Zero value is `nil`. Create a pointer to a struct literal with `&MyStruct{Field: value}` or `new(MyStruct)` (zero-initialized).

G12 — `init()` runs automatically before `main()` starts, once per package. A package can have multiple `init()` functions; they execute in declaration order. Used for setup, but complex logic should be avoided to prevent hidden dependencies.

G13 — `make(T, args)` initializes slice, map, or channel and returns the initialized value (not a pointer). `new(T)` allocates zeroed memory and returns `*T`. Use `make` for reference types, `new` for value types.

G14 — Errors implement `error` interface (`Error() string`). Idiomatic pattern: `if err != nil { return err }`. `errors.Is(err, target)` checks if `err` wraps `target`. `errors.As(err, &target)` extracts typed error from the chain. `==` only checks exact equality and doesn't unwrap wrapped errors.

G15 — Zero values: `map` → `nil`, `slice` → `nil` (len=0, cap=0), `channel` → `nil` (blocks forever), `struct` → zero values of each field.

G16 — A race condition occurs when concurrent goroutines access shared data without synchronization, causing undefined behavior. `-race` flag instruments the runtime to detect conflicting accesses at runtime. Example: `var c int; go func(){c++}(); c++`. Fix: `sync.Mutex` or channel-based communication.

G17 — `select` waits on multiple channel operations, like `switch` but for channels. If multiple cases are ready, one is chosen pseudo-randomly. Timeout: `case <-time.After(d):`. Blocks until at least one case is ready or default executes.

G18 — Escape analysis determines if a variable lives on stack or heap. Heap allocation occurs if the value escapes the function (returned, captured by closure, stored in heap-allocated struct). Inspect with `go build -gcflags="-m"`. Matters because heap allocs trigger GC overhead; stack allocs are faster and zero-cost.

G19 — `reflect.Type` holds type metadata; `reflect.Value` holds the actual value/data. Costs: slow, bypasses compile-time checks, creates GC roots. Justified in frameworks, ORMs, JSON parsers. Prefer code generation (`go generate`, `stringer`) for performance-critical paths to avoid reflection overhead.

G20 — `go:embed` embeds static files/directories into the binary at compile time. `//go:embed file.txt` or `//go:embed dir/`. Works with `embed.FS` which implements `io/fs.FS`, enabling virtual filesystem traversal. Limitations: only static files, no runtime paths, size constraints, must be in the same package.

R1 — Ownership ensures memory safety without GC. Rules: 1) Each value has exactly one owner. 2) Only one owner at a time. 3) Owner drops value when out of scope. Prevents double-free, use-after-free, and data races.

R2 — `String` is heap-allocated, growable, and owned. `&str` is a borrowed, immutable slice of UTF-8 bytes. Use `String` when you need ownership/modification; use `&str` in function signatures to accept any string-like type efficiently.

R3 — Borrowing allows temporary access without transferring ownership. Rules: 1) Either one `&mut T` or multiple `&T` (not both). 2) References must always be valid. The borrow checker enforces these at compile time, preventing data races and dangling pointers.

R4 — `Result<T, E>` represents success (`Ok(T)`) or error (`Err(E)`). `Option<T>` represents `Some(T)` or `None`. The `?` operator propagates errors/returns early. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```

R5 — `Box<T>`: heap allocation, single owner, moves data. `Rc<T>`: reference counting, single-threaded shared ownership. `Arc<T>`: atomic reference counting, thread-safe shared ownership. Use `Box` for large data/ownership, `Rc` for shared read-only, `Arc` for shared across threads.

R6 — Traits are Rust's interface mechanism. Unlike Go's implicit duck-typing, Rust requires explicit `impl Trait for Type`. Trait object (`dyn Trait`) enables dynamic dispatch (vtable, heap-allocated, allows heterogeneous collections). Generic (`T: Trait`) enables static dispatch (monomorphization, zero-cost, type-specific).

R7 — The function fails because the compiler cannot infer which input lifetime applies to the output. Fix with explicit lifetime: `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str { if x.len() > y.len() { x } else { y } }`. (Note: Rust's lifetime elision rules actually allow this signature in modern Rust, but explicit lifetimes clarify intent and are required in older editions or complex cases.)

R8 — `Send`: types safe to transfer ownership across threads. `Sync`: types safe to share references across threads. `Rc<T>` isn't `Send`/`Sync` due to non-atomic reference counting. `Arc<T>` uses atomic ref counting, making it `Send`+`Sync` (if `T` is).

R9 — `async fn` returns a `Future` (a state machine). `await` yields control when the future is blocked. An executor (e.g., Tokio) polls futures, manages I/O, and schedules them on threads. Differs from Go: Go uses eager, runtime-managed M:N goroutines; Rust uses lazy, explicit futures + external executors with zero hidden allocations.

R10 — `unsafe` bypasses compile-time safety checks. Three things: 1) Dereference raw pointers. 2) Call `unsafe` functions. 3) Implement `unsafe` traits or access/modify `static mut`. Justified for FFI, low-level syscalls, performance-critical code, or building safe abstractions over unsafe foundations.

R11 — Pattern matching exhaustively handles enum variants. `match` binds values and requires exhaustiveness; `if let` is concise for single cases. The compiler enforces exhaustiveness in `match`, preventing unhandled variants and reducing runtime panics.

R12 — `Vec<T>` is heap-allocated, dynamically sized, and growable. `[T; N]` is stack-allocated (usually), fixed size, known at compile time. When `Vec` exceeds capacity, it reallocates (typically 2x), copies elements, and drops old allocation.

R13 — Rust enums are algebraic data types; variants can hold data. C/Java enums are integer constants or fixed sets. `Option<T>` = `Some(T)` or `None`. Rust has no `null` to prevent null pointer exceptions and force explicit handling of absent values.

R14 — `impl` blocks define methods. `&self`: immutable borrow (most common). `&mut self`: mutable borrow. `self`: takes ownership (consumes `self`). Associated functions (e.g., `String::new()`) don't take `self` and act like static methods.

R15 — `#[derive]` auto-implements traits. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive if trait requires custom logic, or if struct contains non-derivable types (e.g., `Fn` closures, raw pointers for `Clone`, or types without `Clone`/`Debug`).

R16 — `Cow<'a, T>` (Clone-on-Write) holds either borrowed `&'a T` or owned `T`. Useful when a function might return borrowed or owned data. Avoids allocation if input matches expected output; clones only when mutation is needed, saving memory in read-heavy paths.

R17 — `mod` declares a module, `use` brings items into scope, `pub` exposes items. File system: `mod.rs` or `mod_name.rs` in a directory. Rust 2018 changed path resolution (`crate::`, `super::`, `self::`), removed `extern crate`, and allowed modules to be declared in the crate root or separate files.

R18 — `Pin<T>` guarantees a value's memory location doesn't change. Needed for self-referential structs and async/await (futures may contain references to their own fields). `Unpin` is the default marker trait for types that can be safely moved. `Pin` prevents invalidation of self-references during moves.

R19 — Declarative macros (`macro_rules!`) use pattern matching and repetition to generate code. Procedural macros (derive, attribute, function-like) operate on Rust ASTs. Hygiene rules prevent macro-expanded code from accidentally capturing or rebinding variables from the caller's scope, ensuring predictable behavior.

R20 — Zero-cost abstractions compile high-level features to efficient machine code. Iterators use loop unrolling and eliminate bounds checks. Generics use monomorphization (type-specific code generation). Trait static dispatch inlines calls. Together, they achieve C-like performance while providing safety, ergonomics, and composability.
