AA1 — Monoliths are single codebases deployed as one unit with shared memory/processes. Microservices are independently deployable, loosely coupled services with separate databases/processes. Microservices introduce: (1) network latency/failure handling, (2) distributed tracing/debugging complexity, (3) data consistency challenges across service boundaries.

AA2 — Synchronous communication blocks the caller until a response is received (e.g., REST/HTTP, gRPC). Asynchronous communication decouples producer and consumer; messages are stored and processed later (e.g., RabbitMQ, Kafka). Async improves resilience and throughput but complicates flow control.

AA3 — A reverse proxy routes traffic, handles SSL termination, load balancing, and basic caching (Nginx, HAProxy). An API Gateway adds business-layer features: rate limiting, auth, request transformation, versioning, and analytics (Kong, Apigee). An API Gateway can technically replace a reverse proxy, but is often heavier; many architectures use a lightweight reverse proxy at the edge for performance, with the API Gateway handling application logic.

AA4 — The Saga pattern breaks distributed transactions into local transactions, each with a compensating action for rollback. Choreography uses events to trigger next steps (decentralized, simple, hard to monitor). Orchestration uses a central coordinator sending commands (centralized, easier to track/rollback, better for complex flows). Use choreography for simple, loosely coupled workflows; orchestration for stateful, complex, or compliance-heavy processes.

AA5 — CQRS separates read and write models: commands modify state, queries read from optimized read models. Event Sourcing stores state changes as immutable events. Combined, they solve auditability, temporal queries, complex domain modeling, and independent scaling of reads/writes. Traditional CRUD struggles with historical state reconstruction, immutable audit trails, and high write/read throughput separation.

AA6 — The Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failures threshold met, fail fast), Half-Open (tests recovery). Unlike retry/backoff (which assumes transient failure and retries), the circuit breaker halts traffic to prevent overload. Use both: retry/backoff for transient errors in Closed state; circuit breaker opens when errors persist, preventing system collapse.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, easiest ops.
2. Shared DB, separate schema: Moderate cost, better isolation/noisy-neighbor mitigation, moderate ops complexity, per-schema backup/restore.
3. Separate DB per tenant: Highest cost, best isolation/security, lowest noisy-neighbor risk, highest ops complexity (backup, migration, connection pooling). Trade-off: cost/security vs operational overhead and performance isolation.

AA8 — Eventual consistency allows stale reads during propagation; strong consistency guarantees reads reflect the latest write. For inventory oversell prevention: use strong consistency (or linearizable reads). Data store: relational DB (PostgreSQL) or distributed SQL (CockroachDB) with row-level locking. Patterns: optimistic concurrency (version columns), distributed locks (Redlock), or short-TTL reservations. Partition inventory by SKU/warehouse to maintain strong consistency per partition while scaling reads async.

AA9 — A sidecar proxy co-locates with an app container to handle traffic, security, and observability. In Istio, Envoy is the data plane proxy intercepting ingress/egress, enforcing policies, metrics, and tracing. The control plane (Istiod) pushes config to Envoy. mTLS between sidecars solves transparent service-to-service authentication, automatic cert rotation, and network-layer enforcement without application code changes, unlike app-level TLS which requires manual cert management and lacks mesh-aware routing/auth.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is removed. Strategy: Place an API gateway in front of the .NET Framework monolith. Identify a bounded context (e.g., user auth). Build a .NET 8 microservice. Route specific URLs/paths to the new service via the gateway. Implement dual-write or CDC for DB migration. Repeat per feature, use feature flags for gradual rollout, and decommission monolith endpoints as traffic shifts.

AA11 — 12-Factor App is a methodology for cloud-native SaaS best practices. Six factors: (1) Codebase (1 codebase, many deploys), (2) Dependencies (explicitly declare), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strictly separate stages), (6) Processes (stateless, ephemeral). They matter for portability, zero-downtime deploys, secure config management, horizontal scaling, and cloud resilience.

AA12 — 
- Coupling: Event-driven = loose; Request-driven = tight.
- Scalability: Event-driven = high throughput, async scaling, backpressure; Request-driven = synchronous scaling, potential bottlenecks.
- Debugging: Event-driven = harder (distributed state, replay needed); Request-driven = easier (request/response trace).
- Ordering: Event-driven = partition-level guaranteed, global not; Request-driven = per-request ordering.
- Failure: Event-driven = durable storage, retry/replay, eventual consistency; Request-driven = immediate failure, requires retries/circuit breakers.
Choose event-driven for async workflows, high throughput, decoupled systems, analytics. Choose request-driven for real-time APIs, simple CRUD, strict consistency needs.

AA13 — A load balancer distributes traffic across servers. Layer 4 routes by IP/port (TCP/UDP), fast and stateless. Layer 7 routes by HTTP headers, URLs, cookies, stateful. Layer 7 is required for content-based routing (e.g., `/api/v1` → backend A, `/static` → CDN), SSL termination, or cookie-based session affinity.

AA14 — Message queues (RabbitMQ) consume and delete messages, support complex routing/exchanges, ideal for task queues and reliable delivery. Log-based brokers (Kafka) append messages, persist them, allow multiple consumers to read at their own pace, and support replay. Pick RabbitMQ for task processing, strict delivery, lower volume. Pick Kafka for event streaming, log aggregation, real-time analytics, replayability, high throughput.

AA15 — Containers share the host OS kernel, are lightweight, fast-starting, and isolate processes/filesystems. VMs run full guest OSes with hardware virtualization, are heavier, and slower. Containers are popular for microservices due to fast deployment, consistent environments, efficient resource usage, immutable infrastructure, and native orchestration support (Kubernetes).

AA16 — Stateless services store no session data locally; each request is independent. They scale horizontally easily (add/remove nodes without data migration). Example: Web API, CDN. Stateful services maintain local session/data. Scaling requires replication/sharding/sticky sessions. Example: Database, Redis, WebSocket server.

AA17 — An ORM maps database tables to objects, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python), Prisma (Node). Trade-offs: ORM = faster dev, DB abstraction, but risks N+1 queries, less performance control, harder optimization. Raw SQL = full control, optimal performance, DB-specific, more boilerplate, harder to migrate.

AA18 — The Bulkhead pattern isolates components/resources to prevent failure cascades. In microservices, it stops one failing service from exhausting threads/connections/memory of another. Implementation: Use separate thread pools per service (e.g., Java `ThreadPoolExecutor`), distinct connection pools, separate deployment namespaces/nodes, or isolated queues. Example: Reserve 70% threads for critical auth, 30% for non-critical analytics.

AA19 — OT requires a central server to transform operations, ensuring strong consistency but complex implementation and weak offline support. CRDTs are mathematical data structures that merge concurrently edited states deterministically without a central server, offering excellent offline support and eventual consistency at higher memory/compute cost. Choose CRDTs for offline editing: they allow disconnected devices to merge edits safely without server coordination, critical for real-time collaboration during network drops.

AA20 — Challenges: polyglot instrumentation, overhead, data volume. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject trace/span IDs into headers. Sampling: head-based (random, cheap, loses context) vs tail-based (sample after processing, accurate, high overhead). Storage: Jaeger (OpenTelemetry) or Tempo (Grafana, object storage) index metadata for querying. Async/Kafka: trace context must be serialized into message headers. Producers inject, consumers extract. Continuity requires explicit header propagation via OpenTelemetry propagators; otherwise, spans break across the queue.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering better performance and data center use. Examples: VMware ESXi, Proxmox VE, KVM. Type 2 (hosted) run on a host OS, easier setup, lower performance. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block-level storage, presents as local disk, high performance/low latency, used for databases/VMs. Protocols: Fibre Channel, iSCSI. NAS provides file-level storage, mounted over network, easier sharing, used for backups/home dirs/media. Protocols: NFS, SMB/CIFS.

OP3 — 3-tier architecture (core/distribution/access) is hierarchical, prone to bottlenecks, asymmetric routing, and high east-west latency. Leaf-spine is fully meshed, enables equal-cost multipath (ECMP), low latency, predictable bandwidth, and scale-out. It solves tier bottlenecks and supports modern data center east-west traffic patterns.

OP4 — Use 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing uses STONITH (e.g., IPMI/fence_node) to power off failed nodes. Shared storage: Ceph (recommended for redundancy/performance), iSCSI, or NFS. On node failure: HA manager detects failure, fences node, restarts VMs on healthy nodes using shared storage. No data loss if storage is replicated.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte tag to Ethernet frames with a VLAN ID. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, repeat for VLANs 20/30, assign IPs, enable forwarding. Alternatively, use `netplan` or `NetworkManager` with VLAN interfaces.

OP6 — RAID 1: mirror, 50% capacity, 1 drive fault tolerance. RAID 5: stripe+parity, (N-1) capacity, 1 drive fault tolerance, write penalty. RAID 6: double parity, (N-2) capacity, 2 drive fault tolerance, higher write penalty. RAID 10: mirror+stripe, 50% capacity, 2 drive fault tolerance (different mirrors), best IOPS. RAID Z2: ZFS double parity, (N-2) capacity, 2 drive fault tolerance, superior integrity/scrubbing. For 6 drives + DB: RAID 10 for max performance, or RAID Z2/RAID 6 for capacity/integrity balance.

OP7 — Recursive resolvers: internal DNS servers (Windows DNS/BIND) for clients. Authoritative: internal zone for AD, external zone for public. Forwarders: point to ISP/Cloudflare for external resolution. Conditional forwarding: routes internal AD queries to DCs, external to forwarders. Split-horizon: internal DNS returns private IPs, external returns public IPs for same FQDN. DNSSEC: sign external zone, publish DS at registrar; internal zone can be unsigned or AD-integrated. Laptop roaming: DHCP assigns internal DNS; VPN uses split tunneling to route internal queries to corporate resolvers; cached records handle brief offline periods.

OP8 — Chain: Root CA (offline, self-signed) → Subordinate/Issuing CA (online, signed by root) → End-entity certs. Deployment: Root CA air-gapped. Subordinate CA handles issuance. CRL/OCSP for revocation. Certificate templates + auto-enrollment (Windows AD CS) streamline issuance. Compromise consequences: Subordinate CA → revoke issuing CA, reissue certs, limited blast radius. Root CA → catastrophic, must trust new root, revoke all, massive re-issuance, trust store updates.

OP9 — MPLS: high reliability, low latency, expensive, managed, secure. IPsec VPN: cheap, internet-based, variable latency, manual management. SD-WAN: orchestrates MPLS/IPsec/WireGuard, app-aware routing, centralized management, cost-effective. WireGuard mesh: modern, fast, simple, lacks enterprise policy/monitoring without overlay. Recommendation: SD-WAN. Handles 50 users/site, supports VoIP QoS/prioritization, cost-effective, resilient, centralized management.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: out-of-band management interfaces for remote server control (power, console, hardware monitoring). Critical for recovery from OS crashes, remote installs, diagnostics without physical access. Internet exposure: high risk. Attackers can brute-force, exploit vulnerabilities, gain full server control, bypass OS security. Must be isolated on management network, use strong auth/MFA, and firewall rules.

OP11 — LVM: traditional, fixed-size volumes, snapshots consume space quickly. LVM-Thin: overprovisions storage, cheap/fast snapshots, performance degrades if pool fills, no data integrity. ZFS: filesystem+volume manager, copy-on-write, instant/zero-space snapshots, continuous integrity checking, compression, RAID-Z. Use LVM for legacy/simple setups, LVM-Thin for VM overprovisioning, ZFS for data integrity, snapshots, self-healing.

OP12 — Design: 2 sites (primary/secondary), 3 nodes total (2 primary, 1 secondary as tiebreaker/witness). CRUSH rules: place replicas across sites (e.g., `step chooseleaf firstn 0 type host step chooseleaf firstn 1 type site`). Monitors: 3 monitors, ideally 1 per site + 1 tiebreaker. Latency: <10ms ideal, <15ms acceptable. Split-brain: without tiebreaker, both sites form quorum, causing data corruption. Tiebreaker (quorum disk/external monitor) breaks deadlock. 2-site Ceph without tiebreaker is bad because neither site holds majority, leading to split-brain risk.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. Server unavailable: client retries, eventually falls back to APIPA (169.254.x.x). Lease expiry: client tries renewal at T1 (50%) and T2 (87.5%). If server unavailable, lease expires, client loses IP, must restart DORA or use APIPA.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP monitoring, ACLs, link aggregation. Enterprise importance: segmentation, traffic prioritization, loop prevention, security, troubleshooting, and compliance.

OP15 — NTP synchronizes clocks over networks. Critical for authentication, logging, clustering, distributed transactions, certificate validation, Kerberos. Clock drift consequences: cluster split-brain, failed auth, log correlation issues, data corruption, certificate errors, replication failures.

OP16 — Physical servers: direct hardware access, max performance, no virtualization overhead. VMs: full OS isolation, hardware abstraction, moderate overhead. Containers: process isolation, share kernel, minimal overhead, fast startup. Bare metal use: HPC, databases with strict I/O needs, latency-sensitive apps, hardware passthrough (GPUs/NICs), compliance requirements.

OP17 — UPS: battery backup, provides immediate power, conditions electricity, bridges to generator. Generator: long-term power, fuel-based, takes seconds/minutes to start. Need both: UPS handles instantaneous transition and short outages; generator handles extended outages. ATS: automatically switches load from utility to generator during outages, and back when restored.

OP18 — Active-passive: one node handles traffic, standby takes over on failure. Simple, no split-brain. Active-active: both handle traffic, sync data. Complex, requires distributed DB or app-level sync. PostgreSQL HA with Pacemaker/Corosync: primary runs PostgreSQL, standby replicates via WAL. Virtual IP floats. STONITH fencing ensures failed node is powered off. On failure, Pacemaker promotes standby, moves VIP, starts services. (Modern alternative: Patroni/pg_auto_failover.)

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO: define acceptable data loss and downtime. Backup types: full (baseline), incremental (changes since last), differential (changes since last full). Deduplication: reduces storage, improves backup window. Media: disk (fast restores), tape (cheap long-term), cloud (offsite/scalability). Immutable: WORM storage, ransomware protection. Testing: regular restore drills, verify integrity, measure RTO/RPO. Backup vs DR: backup = data protection/restoration; DR = comprehensive strategy (infrastructure, processes, failover) to resume operations after disaster.

OP20 — 802.1X: port-based NAC. Roles: supplicant (client), authenticator (switch), authentication server (RADIUS). EAP: EAP-TLS (cert-based, mutual auth, secure), PEAP (username/password, tunneled, common). RADIUS: handles AAA. Dynamic VLAN: switch assigns VLAN via RADIUS attributes (Tunnel-Private-Group-ID). Failure: port stays unauthorized, no traffic. MAB: uses MAC address as credential when supplicant lacks 802.1X support. RADIUS validates MAC against database. Less secure, fallback for IoT/printers.
