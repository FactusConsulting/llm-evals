SC1-A
The pods fail because Kubernetes Pod Security Standards (PSS) `Restricted` explicitly forbids running containers as UID 0 (root). While `runAsNonRoot: true` is set, it only validates that the container *wants* to run non-root; it does not enforce a specific UID. The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`. When the runtime starts the container, it runs as UID 0, violating the `Restricted` PSS requirement of `runAsUser: >0`. Between `Baseline` and `Restricted`, the latter enforces `runAsNonRoot: true`, `runAsUser: >0`, `allowPrivilegeEscalation: false`, and drops all capabilities. The cluster upgrade switched namespace enforcement to `Restricted`, triggering immediate admission/runtime failures for pods that previously ran as root under `Baseline`.

SC1-C
**Immediate Fix:** Update deployments to add `runAsUser: 1000` (or matching non-root UID) to both pod and container `securityContext`. Rebuild images with `USER 1000` in Dockerfile and pin base image digest.
**CI Gate:** Add a Kyverno policy or OPA Gatekeeper constraint that enforces `runAsUser > 0`, `allowPrivilegeEscalation: false`, and PSS `Restricted` compliance. Integrate `trivy` or `checkov` in CI to fail on non-root base images or missing securityContext.
**Rollout:** Use `kubectl rollout restart` with `maxSurge=25%` and `maxUnavailable=0`. Monitor `kubectl get events` and pod readiness probes. Switch traffic via Ingress/Service if using blue-green, or rely on rolling update for zero downtime.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped over the network and replayed on the replica. During promotion, any WAL not yet shipped or replayed is permanently lost. The data loss window equals the replication lag at promotion time. To quantify: check `pg_stat_replication` on the primary for `replay_lag` and `sent_lag`, and compare `pg_last_wal_receive_lsn()` on the replica vs `pg_current_wal_lsn()` on the primary. Asynchronous replication guarantees no data loss only if you manually verify lag is zero before promotion, which is impractical across regions.

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks (ping, TCP, DB heartbeat) across sites. Threshold: 3 consecutive failures over 30s = site down.
2. **Isolation:** Disable Chicago load balancers, trigger fencing (STONITH) if split-brain suspected.
3. **Promotion:** Patroni promotes Dallas standby (sync commit ensures RPO=0). Redis Sentinel promotes master. RabbitMQ federation catches up. MinIO site replication syncs delta.
4. **Routing:** GSLB/DNS updates to Dallas VIP. TTL < 60s.
5. **State Update:** Ansible/Terraform updates state file to reflect Dallas as primary.
**Split-Brain:** Quorum-based DCS (etcd/Patroni) prevents dual promotion. Manual override required if quorum lost.
**Failback:** Reverse replication, sync data, update DNS back to Chicago, cutover traffic, update state, decommission Dallas primary. Test quarterly with game days.
