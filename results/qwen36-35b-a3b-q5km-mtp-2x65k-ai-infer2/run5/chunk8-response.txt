CL1 — IaaS provides virtualized compute, network, and storage where you manage the OS, middleware, runtime, and applications (e.g., AWS EC2). PaaS provides a managed runtime and middleware where you only manage applications and data (e.g., Google App Engine). SaaS delivers a fully managed application where you only manage user access and configuration (e.g., AWS WorkSpaces).

CL2 — The Shared Responsibility Model divides security: the provider secures the global infrastructure, hypervisor, and managed service components; you secure data, identity, OS/network config, and applications. IaaS VM: Provider = physical/hypervisor; You = OS patching, network, data, app. Managed K8s: Provider = control plane, etcd, node OS patching; You = worker config, pod security, network policies, secrets, app. SaaS (M365): Provider = app, infra, patching, compliance framework; You = identity, access management, data classification, user config.

CL3 — A VPC is an isolated virtual network; subnets are IP ranges within it. Security Groups (SGs) are stateful, instance/pod-level, allow-only rules evaluated before routing. Network ACLs (NACLs) are stateless, subnet-level, allow/deny rules evaluated after routing. They layer as VPC → Subnet → SG/NACL. Stateful filtering automatically tracks and allows return traffic; stateless requires explicit rules for both directions.

CL4 — A landing zone is a pre-configured, secure multi-account foundation. OUs logically group accounts (dev, prod, security). Guardrails (SCPs/policies) enforce encryption, MFA, region restrictions, and budget caps. Shared networking uses Transit Gateway/Azure Hub-and-Spoke for centralized inter-VPC/VNet peering and on-prem connectivity. Centralized logging aggregates CloudTrail/VPC Flow Logs to a dedicated security account. Single-account approaches cause massive blast radius, permission sprawl, billing opacity, compliance isolation failures, and accidental deletion risks.

CL5 — IaC manages infrastructure via version-controlled, machine-readable definitions. Terraform/OpenTofu: Declarative HCL, multi-cloud, mature ecosystem; best for multi-cloud or large teams. Pulumi: Imperative/Declarative (TS/Python/Go), native cloud SDKs; best for dev-heavy teams needing complex logic. CloudFormation/Bicep: AWS-native, declarative, tightly integrated; best for AWS-only shops. Crossplane: Kubernetes-native IaC using CRDs; best for K8s-centric teams wanting a unified control plane.

CL6 — HPA scales pods based on CPU/memory/custom metrics. VPA adjusts pod resource requests/limits based on usage. Cluster Autoscaler adds/removes nodes based on pending pods/resource pressure. KEDA scales to/from zero based on external event triggers (queues, streams). Use KEDA over HPA when scaling must be event-driven, scale to zero, or based on non-standard metrics (e.g., Kafka lag, queue depth).

CL7 — Define RPO/RTO by business impact. Active-active: RPO~0, RTO~0, high cost/complexity. Active-passive: RPO>0 (async replication), RTO>0, lower cost. DB replication: Sync ensures strong consistency but limits cross-region latency; async enables cross-region but accepts eventual consistency. DNS failover uses Route53/Traffic Manager health checks with low TTLs for rapid routing. State must be externalized (DB, object storage, distributed cache). Cost: Active-active doubles infra + data transfer; active-passive saves cost but requires regular failover testing. Pilot light: Core infra runs, scaled up on failover. Warm standby: Scaled-down prod ready. Multi-site active-active: Full prod in both regions, load-balanced.

CL8 — GitOps uses Git as the single source of truth; controllers continuously reconcile cluster state with Git manifests. ArgoCD: UI-first, app-of-apps, push/pull, strong visualization. Flux: Git-native, pull-only, Kustomize/Helm, operator pattern, CLI-first. Secrets: SealedSecrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from cloud/Vault), Vault (dynamic secrets, auth). Drift: Manual changes are overwritten on next sync; GitOps enforces declarative state and auto-corrects drift.

CL9 — Use a StatefulSet for stable network IDs and ordered deployment. PV/PVC with `local` storageClass and `volumeBindingMode: WaitForFirstConsumer` ensures node affinity. Headless service (`clusterIP: None`) enables direct pod DNS resolution. Init containers pre-load config, check dependencies, and set permissions. ConfigMaps mount as volumes at specific filesystem paths via `subPath`. Pod Disruption Budgets (`minAvailable`) ensure quorum during node drains/upgrades. Note: K8s is suboptimal for legacy stateful apps, but this architecture meets the stated constraints.

CL10 — K8s Service Accounts are native identities with no cloud permissions. Workload Identity (GCP/Azure) and IRSA (AWS) map K8s SAs to cloud IAM identities without static keys. Mounting cloud credentials in pods leaks secrets, prevents rotation, violates least privilege, and enables full cloud compromise if the pod is breached. Workload identity federation uses OIDC to exchange short-lived, scoped tokens automatically, eliminating static keys and enabling automatic rotation.

CL11 — Object storage (S3/Blob) is HTTP-based, unstructured, highly scalable; use for backups, media, data lakes. Durability: 99.999999999%. Block storage (EBS/Disk) is low-latency, mounted to a single VM; use for OS, databases, high-IOPS apps. Durability: 99.999%. File storage (EFS/Azure Files) is NFS/SMB, shared across multiple VMs; use for shared configs, home dirs, legacy apps. Durability: 99.999999999%. Object/Block are typically zone-redundant; File spans AZs natively.

CL12 — Zero-trust K8s: Default-deny Network Policies restrict pod-to-pod traffic. Service mesh (Istio/Linkerd) enforces mTLS and identity-based routing. Pod identity uses workload identity/IRSA for cloud access. Admission controllers (OPA/Kyverno) enforce policies (no privileged pods, resource limits). Image signing (Cosign/Notary) verifies signatures at admission. Runtime security (Falco) monitors syscalls for anomalies. Secrets use External Secrets Operator/Vault, never in env vars. Differs from perimeter security by verifying every request, assuming breach, micro-segmenting, and enforcing least privilege internally.

CL13 — A CDN is a distributed edge cache network that proxies content closer to users, reducing origin load and latency. Cloud-native examples: AWS CloudFront, Azure CDN. Use a CDN for static/cached content, high global traffic, DDoS mitigation, and edge computing. Serve directly from origin for dynamic, personalized, or low-traffic content where caching adds complexity or stale data risk.

CL14 — A region is a geographic area containing multiple Availability Zones (AZs). AZs are discrete data centers with independent power/cooling/networking, connected via low-latency links. Deploy across multiple AZs to survive data center failures and ensure high availability. Zonal resources are tied to a single AZ (e.g., EBS, some LBs). Regional resources span multiple AZs (e.g., ALB, Route53, S3).

CL15 — Managed databases (RDS, Cloud SQL, Azure SQL) abstract infrastructure management. The provider handles provisioning, OS patching, backups, replication, monitoring, failover, and storage scaling. Self-hosting on a VM requires you to manage the OS, database software, patching, backups, replication, tuning, and HA setup. Trade-off: Managed = faster ops, less control; Self-hosted = full control, higher operational burden.

CL16 — IAM Users are human/service identities. Groups organize users. Roles provide temporary credentials for services/users. Policies are JSON rules defining permissions. Least privilege grants only necessary permissions. Apply via scoped policies, avoid `*:*`, use IAM Access Analyzer, enforce MFA, prefer roles over long-term keys, and conduct regular access reviews.

CL17 — Serverless is managed, event-driven compute with pay-per-use pricing and auto-scaling (Lambda, Azure Functions, GCF). Cold starts are initial invocation latencies when containers are provisioned; they matter for latency-sensitive apps. Mitigate with provisioned concurrency, smaller packages, and lighter runtimes. Poor fit: Long-running processes, stateful apps, predictable high-throughput (reserved instances cheaper), strict compliance/network constraints, or vendor lock-in concerns.

CL18 — Ingress Resource: Standard K8s CRD, relies on a controller (NGINX/ALB), TLS terminates at the controller. Gateway API: Next-gen, separates gateway (infra) from routes (app), better RBAC/multi-tenancy, TLS terminates at the gateway. Cloud LB annotations: Provision cloud LBs directly, TLS terminates at the cloud LB. Service Mesh Ingress: Mesh-level gateway, mTLS termination, advanced traffic management. Use Gateway API over Ingress for multi-tenancy, clearer separation of duties, standardized TLS/routing, and future-proofing.

CL19 — RI/SP: Commit 1–3 years for predictable workloads (30–70% savings). Spot/Preemptible: Interruptible, 60–90% savings for fault-tolerant/stateless workloads. Right-sizing: Monitor utilization, downsize overprovisioned, enforce auto-scaling. Storage tiering: Lifecycle policies, S3 Intelligent-Tiering, Glacier for archives. Idle detection: CloudHealth, Cost Explorer, Azure Advisor, tag-based alerts. FinOps: Cross-functional culture, showback/chargeback via tags/cost allocation, budget alerts, monthly optimization reviews. Tools: Native (Cost Explorer, Azure Cost Mgmt), third-party (CloudHealth, Kubecost). Processes: Strict tagging strategy, accountability per team, regular cost reviews.

CL20 — Abstraction: Terraform, Kubernetes, service mesh, API gateways. K8s runtime: EKS/AKS/GKE with GitOps and consistent CI/CD. IaC: Terraform modules, provider-agnostic design, avoid cloud-specific features. Networking: Cloud VPN, Direct Connect/ExpressRoute, global load balancing, DNS routing. Identity: OIDC federation, centralized IdP (Okta/Azure AD), cross-cloud trust. Trade-offs: Complexity, data egress costs, inconsistent features, operational overhead vs resilience, negotiation leverage, regulatory compliance. Justified: Regulatory/data residency, catastrophic vendor risk, specific service needs. Unnecessary: Most startups/SMBs; adds cost/complexity without proportional benefit.

OT1 — The Purdue Model (ISA-95) is a hierarchical framework for industrial automation. Level 0: Physical process (sensors/actuators). Level 1: Direct control (PLCs/RTUs). Level 2: Local control (HMI/SCADA). Level 3: Site operations (MES/historian). Level 4: Enterprise (ERP/business). Level 5: Cloud/remote.

OT2 — IT networks prioritize confidentiality/integrity, use TCP/IP, frequent patching, and are user-centric. OT networks prioritize availability/safety, use deterministic/legacy protocols, run 24/7, and require strict change control. IT patching doesn't apply to OT because legacy OS/hardware often can't be patched, patching requires maintenance windows, and unpatched vulnerabilities are accepted to avoid process disruption or safety risks.

OT3 — An IDMZ buffers IT and OT, enforcing controlled data exchange. Traffic allowed: Primarily OT→IT (process data, alarms). IT→OT is highly restricted (rare commands, via DMZ). Direct L4→L1 connectivity is dangerous because it bypasses security controls, exposes critical control networks to IT threats, enables lateral movement, and violates Purdue segmentation principles.

OT4 — Modbus TCP: L1/L2, PLC communication, master/slave. OPC UA: L2/L3, secure, platform-independent, SCADA/historian/IT data exchange. EtherNet/IP (CIP): L1/L2, industrial Ethernet, Allen-Bradley dominant. PROFINET: L1/L2, real-time Ethernet, Siemens dominant. MQTT: L3/L4, lightweight publish/subscribe, edge-to-cloud telemetry.

OT5 — A data diode is hardware-enforced unidirectional communication (optical/electrical) guaranteeing no return traffic. A firewall is bidirectional, stateful, and allows/denies based on rules. Use a data diode when strict data exfiltration prevention is required (e.g., safety systems, high-security zones). Limitation: No bidirectional communication, no stateful inspection, protocol restrictions, and harder management compared to firewalls.

OT6 — Flow: PLCs → Historian (L3) → OPC UA Server → Edge Gateway (protocol translation, buffering) → MQTT Broker (secure, TLS) → Cloud Ingestion (IoT Core/Kafka) → Analytics. Security boundaries: DMZ between OT and edge, mutual TLS between edge and cloud, network segmentation, encrypted storage, zero-trust access for cloud services. The edge gateway acts as the primary security choke point.

OT7 — IEC 62443 zones are logical groupings of assets with similar security requirements; conduits are controlled communication paths between zones. Model: Zone 1: Corporate (L4). Zone 2: Engineering/SCADA (L3). Zone 3: Control/PLCs (L2). Zone 4: SIS (L1, isolated). Conduits: Zone 1→2 (firewall), 2→3 (firewall/data diode for safety), 3→4 (strict isolation). Engineering workstations in Zone 2 with jump hosts. SIS in dedicated Zone 4, air-gapped or hardened conduit.

OT8 — VLANs: Segment by function/process (e.g., VLAN 10: Line 1 PLCs, VLAN 20: Line 2, VLAN 30: HMIs, VLAN 40: SCADA, VLAN 50: Engineering). Firewalls: Core firewall between IT/OT, edge firewalls per VLAN/zone. Switches: Managed L3 switches, port security, disable unused ports. Remote access: Jump host in DMZ, MFA, session recording, time-bound vendor accounts, no direct OT access. Transition: Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, test in staging, communicate with operations.

OT9 — BPCS maintains normal process operations. SIS is an independent safety system that triggers a safe state on hazardous conditions. IEC 61511 is the safety lifecycle standard defining SIL requirements for process industry SIS. SIS must be isolated to prevent common-cause failures; IT/BPCS compromise could disable safety functions. Ransomware on SIS could bypass interlocks, causing catastrophic failure, environmental damage, or loss of life.

OT10 — PLC: Discrete control, fast, localized, handles I/O, runs ladder logic; used for machine/line control. DCS: Centralized control, integrated I/O, suited for continuous processes (chemical, oil/gas), built-in redundancy. SCADA: Supervisory, remote monitoring/control, aggregates data from PLCs/RTUs, HMI-driven. They coexist commonly: PLCs/RTUs at field, DCS for process control, SCADA for site-wide supervision.

OT11 — Remote access: Isolated jump hosts in DMZ, MFA required, session recording for audit, time-limited scoped vendor access, no direct OT access. RDP directly to an HMI from corporate is unacceptable because it exposes OT directly to the corporate network, bypasses segmentation, increases attack surface, and violates least privilege.

OT12 — Detection: Passive IDS (Zeek/Suricata), network anomaly detection, asset inventory baseline, EDR on OT workstations. Inventory: Continuous passive discovery, tag assets, map dependencies. IR Steps: Contain (isolate compromised segment, don't shut down critical processes), investigate, eradicate, recover, post-incident. Coordination: Notify control room, maintain manual operations if needed, prioritize safety over data. Operator role: Monitor physical process, execute manual overrides, report anomalies, follow emergency procedures, do not interact with compromised systems.

OT13 — An HMI is an operator interface for monitoring/control, displaying process data and allowing manual overrides. It provides situational awareness and alarm management. Differs from an engineering workstation: HMIs are for operators (runtime, limited read/write). EWS are for engineers (programming, configuration, diagnostics, full access).

OT14 — A historian is a time-series database for process data (temperatures, pressures, flows). It's critical for trend analysis, compliance, troubleshooting, and optimization. Plant historian (L3) stores high-frequency, raw process data for operations. Enterprise historian (L4) stores aggregated, filtered data for business analytics and ERP integration at lower frequency.

OT15 — Ladder logic is a graphical programming language mimicking relay circuits, executed by PLCs. It remains dominant because it's familiar to electricians, deterministic, easy to troubleshoot, integrates with legacy systems, is safety-certified, and has a low learning curve for the industrial workforce.

OT16 — An RTU (Remote Terminal Unit) is designed for harsh environments, long-distance communication (serial/SCADA), modular I/O, and often battery/solar power. Differs from a PLC: PLCs are for factory automation, faster scan times, local I/O, rack-based. RTUs are deployed in remote field sites (pipelines, utilities) for SCADA telemetry and low-bandwidth links.

OT17 — Analog signals (4-20mA, 0-10V) are continuous and represent physical variables proportionally. Digital signals are discrete (0/1) representing binary states. 4-20mA is preferred over 0-20mA because 4mA is a "live zero," indicating wire break/failure at 0mA, improving diagnostics and noise immunity over long distances.

OT18 — OT asset inventory is a comprehensive list of hardware, software, firmware, network connections, and dependencies. It's the foundation for risk assessment, patching, segmentation, compliance, and incident response. Tools: Passive monitoring (packet capture, protocol analysis), cautious active scanning. Active scanning is dangerous because it can crash legacy devices, cause network congestion, trigger alarms, disrupt processes, or be detected as an attack.

OT19 — MITRE ATT&CK for ICS maps tactics/techniques specific to industrial control systems. Tactics & examples: Reconnaissance (Gather Victim Host Information), Resource Development (Acquire Infrastructure), Initial Access (Supply Chain Compromise), Execution (Scheduled Task/Job), Impact (Inhibit Response Function/Disrupt Process Control). Differs from enterprise ATT&CK by focusing on physical process impact, safety, legacy protocols, and OT-specific tools. Use it to map current defenses, identify gaps, prioritize mitigations, and test detection capabilities.

OT20 — Log collection: Passive taps, OT-friendly lightweight agents, OPC UA/MQTT telemetry, SIEM via secure gateways. No active polling. SIEM integration: Normalize OT logs (Syslog, CEF, OT schemas), correlate with IT logs. Detection rules: OT-specific (unusual PLC writes, protocol anomalies, after-hours access, firmware changes, unexpected HMI interactions). Triage: OT engineers + IT analysts, playbooks for process safety impact, prioritize by physical risk. Staffing: IT analysts for network/cloud, OT engineers for process/PLC expertise, joint shift model. False positives: OT has predictable cycles; tune rules to baseline, use passive data, involve operators. Unauthorized firmware change: Isolate affected PLC/network, verify safety impact, revert to known good image, investigate source, update change management, patch vulnerability, review access controls.
