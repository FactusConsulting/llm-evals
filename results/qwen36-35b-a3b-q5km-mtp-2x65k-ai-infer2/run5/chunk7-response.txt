AA1 — A monolith is a single codebase deployed as one unit with shared memory/process. Microservices are independently deployable, loosely coupled services with separate databases/processes. Three problems microservices introduce: (1) Distributed debugging/tracing complexity, (2) Network latency and partial failure handling, (3) Data consistency across services (no ACID transactions, requiring sagas/eventual consistency).

AA2 — Synchronous communication blocks the caller until a response is received (e.g., REST/HTTP, gRPC). Asynchronous communication decouples producer and consumer; messages are queued and processed later without blocking (e.g., RabbitMQ, Kafka, AWS SQS).

AA3 — A reverse proxy routes traffic, terminates TLS, and provides basic load balancing/caching (Nginx, HAProxy). An API Gateway adds API-specific capabilities: rate limiting, auth, request/response transformation, versioning, and analytics. An API Gateway can technically replace a reverse proxy, but it’s heavier, more expensive, and often overkill for simple routing. Reverse proxies remain preferred for pure traffic distribution.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to rollback if a step fails. Choreography-based sagas use events; services react to each other without a central coordinator. Best for simple, decoupled flows. Orchestration-based sagas use a central coordinator service that directs steps. Best for complex flows, easier monitoring/rollback, but introduces a single point of control.

AA5 — CQRS separates read and write models: commands modify state, queries read from optimized read models. Event Sourcing stores state as an immutable sequence of events. They’re paired because events naturally drive read-model updates. This combination solves: auditability, temporal queries, independent read/write scaling, and avoids ORM mapping bottlenecks in complex domains.

AA6 — The Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failure threshold met, fail fast), Half-Open (allows test requests). Differs from retry: retry attempts recovery immediately; circuit breaker halts requests to prevent overload. Use both: retry with exponential backoff for transient errors, circuit breaker opens if errors persist to protect the system.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, requires row-level security, simplest ops.
2. Shared DB, separate schema: Moderate cost, better isolation, moderate noisy-neighbor risk, easier per-tenant backups.
3. Separate DB per tenant: Highest cost, best security/isolation, zero noisy-neighbor, high ops complexity (backup/migration per tenant).

AA8 — Eventual consistency: updates propagate asynchronously; consistency achieved after delay. Strong consistency: updates visible immediately to all readers. For inventory oversell prevention: use strong consistency. Architecture: single authoritative inventory service with pessimistic row-level locking (PostgreSQL) or atomic Redis Lua scripts. Partition inventory by SKU/warehouse to scale. Avoid eventual consistency for stock deduction; use idempotent commands and distributed locks (etcd/ZooKeeper) if cross-region.

AA9 — A sidecar proxy is a co-located container handling network traffic for the main app. In Istio, Envoy handles L7 routing, mTLS, retries, and observability. Data plane = Envoy proxies forwarding traffic. Control plane = Istiod managing config and pushing to proxies. mTLS solves east-west encryption and mutual authentication without app code changes; application-level TLS only secures external/client traffic.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality with new services, routing traffic via a gateway until the legacy system is decommissioned. Strategy: Deploy API Gateway. Identify a bounded context (e.g., billing). Build .NET 8 microservice. Route `/billing/*` to new service. Implement dual-write or CDC for DB migration. Use feature flags. Gradually migrate endpoints. Decommission legacy routes once traffic is fully shifted.

AA11 — 12-Factor App is a methodology for cloud-native SaaS best practices. Six factors: (1) Codebase (1 codebase, many deploys), (2) Dependencies (explicitly declare), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/run (strictly separate stages), (6) Processes (stateless, concurrent). They matter for portability, scalable deployments, secure config management, and predictable cloud operations.

AA12 — 
- Coupling: Event-driven = loose (producers/consumers unaware); Request-driven = tight (direct calls).
- Scalability: Event-driven = highly scalable, async, handles bursts; Request-driven = synchronous limits, harder to scale spikes.
- Debugging: Event-driven = complex (traces, replay needed); Request-driven = straightforward (request/response logs).
- Ordering: Event-driven = partition-level guaranteed, global not always; Request-driven = strict per-request.
- Failure: Event-driven = durable storage, retry/replay, eventual consistency; Request-driven = immediate failure, requires retries/circuit breakers.
Choose event-driven for async workflows, high throughput, decoupled systems. Choose request-driven for real-time, strict consistency, simple CRUD.

AA13 — A load balancer distributes traffic across multiple servers. Layer 4 routes by IP/port (fast, no content inspection). Layer 7 routes by content (URL, headers, cookies, SSL). Layer 7 is required for SNI-based SSL termination, path-based routing (`/api` vs `/static`), or cookie-based session affinity.

AA14 — Message queues (RabbitMQ) consume and delete messages, support complex routing, ideal for task queues. Log-based brokers (Kafka) append-only, persist messages, support multiple consumers reading the same stream, ideal for event streaming and replay. Pick RabbitMQ for task processing/strict delivery. Pick Kafka for event sourcing, analytics, log aggregation, replayability.

AA15 — Containers share the host OS kernel, isolate processes/filesystems, and start instantly. VMs run full guest OSes with hardware virtualization, heavier and slower. Containers are popular for microservices due to density, fast deployment, consistent environments, and native orchestration (Kubernetes) without VM overhead.

AA16 — Stateless services hold no local session data; any instance can handle any request, making horizontal scaling trivial (add/remove freely). Example: REST API, Nginx. Stateful services maintain local state/session; scaling requires sticky sessions or shared state. Example: PostgreSQL, Redis, WebSocket server.

AA17 — An ORM maps objects to database tables, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORM = faster dev, portability, safety, but can generate inefficient queries and struggles with complex SQL. Raw SQL = full control, optimal performance, complex queries, but more code, DB-specific, slower dev.

AA18 — The Bulkhead pattern isolates resources so failure in one component doesn’t cascade. In microservices, it prevents thread/connection pool exhaustion from one service taking down others. Implementation: separate thread pools per downstream service, distinct connection pools, or deploy critical vs non-critical services on separate K8s namespaces/node pools with resource quotas.

AA19 — OT requires a central server to transform concurrent operations, ensuring strong consistency but adding latency and complexity. CRDTs are mathematical structures that guarantee convergence without coordination, supporting decentralized offline edits. Choice: CRDTs. They automatically resolve conflicts when devices reconnect, require no server mediation, and provide superior offline-first UX.

AA20 — Challenges: polyglot libraries, overhead, high data volume. Context propagation: W3C Trace Context (standard) or B3; inject/extract trace IDs across HTTP/gRPC. Sampling: head-based (random, simple, loses context), tail-based (sample after processing, accurate, high overhead). Storage: Jaeger/Tempo use columnar/object storage optimized for trace queries. Async/Kafka: inject trace context into message headers; consumer extracts and continues trace. Ensures continuity across async boundaries.

OP1 — Type 1 (bare-metal) runs directly on hardware, high performance, low overhead. Examples: VMware ESXi, Proxmox VE, KVM. Type 2 (hosted) runs as an app on a host OS, lower performance. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block-level storage, presents disks to servers, high IOPS/low latency. Protocols: Fibre Channel, iSCSI. NAS provides file-level storage, mounted as shares, easier management. Protocols: NFS, SMB/CIFS. Use SAN for databases/VMs. Use NAS for file shares/backups/media.

OP3 — 3-tier: Core (backbone), Distribution (policy/routing), Access (edge). Hierarchical, prone to bottlenecks and asymmetric routing. Leaf-spine: all-to-all mesh, equal latency, non-blocking, scalable. Solves spine bottleneck, east-west traffic scaling, and predictable latency in modern data centers.

OP4 — Architecture: 3+ nodes (odd for quorum), shared storage (Ceph recommended), fencing (STONITH via IPMI/iDRAC), quorum daemon. Node failure: Corosync detects failure, fencing isolates node, VMs restart on remaining nodes. Ceph replicates data. Odd nodes + fencing prevent split-brain.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte tag with VLAN ID to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, assign IPs, enable `vlan` module, configure switch port as trunk.

OP6 — RAID 1: mirror, 50% cap, 1 fault. RAID 5: stripe+parity, N-1 cap, 1 fault. RAID 6: stripe+double parity, N-2 cap, 2 faults. RAID 10: mirror+stripe, 50% cap, 2 faults (different mirrors). RAID Z2: double parity, N-2 cap, better rebuild/scrubbing. Choice: RAID Z2 or RAID 6. For 6 drives, Z2 gives 4 usable, survives 2 failures, superior data integrity for DBs.

OP7 — Recursive resolvers: internal DNS servers for clients. Authoritative: internal zone for AD, external for public. Forwarders: point to ISP/Cloudflare for external queries. Conditional forwarding: routes internal AD domains to internal DNS, external to forwarders. Split-horizon: internal DNS returns private IPs, external returns public IPs. DNSSEC: signs external zone, validates externally. Laptop roaming: DHCP assigns internal DNS; VPN uses split tunneling/conditional forwarding; cached records + DNS suffix search handle transitions.

OP8 — Chain: Root CA (offline, self-signed) → Subordinate CA (issues certs) → End-entity. Root CA: air-gapped, long-lived. Subordinate CA: online, shorter lifetime. CRL: downloaded revocation list. OCSP: real-time status check. Templates: define key usage, validity, auto-enrollment. Auto-enrollment: AD CS pushes certs to domain devices. Compromise: Subordinate = issue fake certs, but root can revoke it. Root = catastrophic, requires full PKI rebuild and trust redistribution.

OP9 — MPLS: high reliability, low latency, expensive, managed. IPsec VPN: cheap, internet-based, variable latency, manual. SD-WAN: orchestrates multiple links, app-aware routing, centralized mgmt, cost-effective. WireGuard mesh: modern crypto, fast, simple, lacks enterprise features. Recommendation: SD-WAN. Handles VoIP QoS, optimizes internet/MPLS mix, centralized management, reliable for latency-sensitive traffic.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: out-of-band hardware management interfaces for power/console/diagnostics independent of OS. Critical for recovery from OS crashes, remote installs, hardware monitoring. Internet exposure: high risk (password resets, console access, crypto mining, hardware bricking). Should be on isolated management network.

OP11 — LVM: fixed-size volumes, COW snapshots consume space. LVM-Thin: overprovisions storage, instant snapshots, pool can exhaust. ZFS: CoW filesystem+volume manager, instant read-only snapshots, shares unchanged blocks, highly reliable. Use LVM for legacy/simple needs. LVM-Thin for overprovisioning (monitor pool). ZFS for data integrity, snapshots, compression, modern storage.

OP12 — Design: 2 sites (primary/secondary), 3 monitors (2 primary, 1 arbiter/tiebreaker in secondary), OSDs distributed. CRUSH rules: map primary site as crush rule, secondary as replica, arbiter as tiebreaker. Latency: <5ms ideal, <10ms max. Split-brain: prevented by odd monitors + arbiter. Arbiter breaks ties during network partition. 2-site Ceph without tiebreaker = even monitors = split-brain, no quorum, data corruption risk.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. Server unavailable: client uses APIPA (169.254.x.x) or retains old IP if lease valid. Lease expiry: client unicasts renewal; if fails, broadcasts. If still fails, IP released, must restart DORA.

OP14 — Unmanaged: plug-and-play, no config. Managed: configurable, supports VLANs, QoS, STP, port security, SNMP, ACLs, LAG. Important for traffic segmentation, security, performance tuning, troubleshooting, and redundancy in enterprises.

OP15 — NTP synchronizes clocks across networks. Critical for log correlation, Kerberos/AD auth, distributed DB consistency, certificate validation, debugging. Clock drift causes: Kerberos auth failures, cluster split-brain, incorrect log/DB timestamps, certificate validation errors, time-sensitive data corruption.

OP16 — Physical: bare hardware, full control, highest performance. VM: OS virtualization, isolation, hardware abstraction. Container: process isolation, shares kernel, lightweight. Bare metal use: HPC, low-latency trading, databases with direct storage, GPU/NIC passthrough, compliance requirements.

OP17 — UPS: battery backup, immediate power during outages, bridges to generator startup. Generator: long-term power, fuel-based, minutes to start. Need both: UPS handles instant transition/short outages; generator handles extended outages. ATS: detects outage, switches load to generator, switches back when utility restored.

OP18 — Active-passive: one node handles traffic, standby takes over on failure. Simple, no split-brain. Active-active: both handle traffic, sync data. Complex, requires distributed DB/app sync. PostgreSQL HA: Pacemaker/Corosync cluster, 2 nodes. STONITH (fencing) via IPMI kills failed node. Virtual IP floats to active node. Patroni/repmgr handles replication. Failover: Pacemaker detects failure, fences node, promotes standby, moves VIP, starts DB.

OP19 — 3-2-1: 3 copies, 2 media types, 1 offsite. RPO/RTO: define by business impact (e.g., RPO 1h, RTO 4h). Backup types: Full (baseline), Incremental (changes since last), Differential (changes since last full). Deduplication: reduces storage, improves backup window. Media: disk for fast restore, tape/cloud for cheap offsite. Immutable: WORM/air-gapped, protects against ransomware. Test restores: regular drills, verify integrity, measure RTO/RPO. Backup = data protection. DR = full recovery process (infrastructure, data, procedures) to resume operations.

OP20 — 802.1X: port-based NAC. Roles: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP: EAP-TLS (cert-based, mutual auth, secure), PEAP (username/password, tunneled, common). RADIUS: handles AAA. Dynamic VLAN: RADIUS returns VLAN ID in Access-Accept, switch assigns port. Failure: port stays unauthorized, no traffic. MAB: uses MAC address as credential, fallback for printers/IoT, less secure, assigned to guest VLAN.
