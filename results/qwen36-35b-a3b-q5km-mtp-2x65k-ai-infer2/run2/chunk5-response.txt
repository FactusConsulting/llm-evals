DN1 — **class vs struct**: `class` is a reference type (heap-allocated, supports inheritance/polymorphism, null-capable). `struct` is a value type (stack/inline-allocated, copy-on-assignment, no inheritance). Use `struct` for small, immutable, short-lived data with value semantics (e.g., coordinates, IDs, math vectors). Avoid for large objects or when reference identity is required.

DN2 — **IEnumerable<T> vs IQueryable<T>**: `IEnumerable<T>` executes LINQ-to-Objects in memory. `IQueryable<T>` builds expression trees that providers (e.g., EF Core) translate to SQL, pushing filtering/joins to the database. The distinction matters because using `IEnumerable<T>` on a DB context loads entire tables into memory before applying in-memory LINQ, causing severe performance/memory issues.

DN3 — **async/await, Task vs ValueTask**: `async/await` compiles to a state machine that captures context, yields control on I/O-bound awaits, and resumes when completed. `Task` is a heap-allocated reference type. `ValueTask` is a struct that avoids allocation when the async operation completes synchronously. Use `ValueTask` in hot paths where synchronous completion is common or allocation overhead is unacceptable.

DN4 — **DI lifetimes & Scoped-in-Singleton bug**: DI injects dependencies instead of creating them. `Transient`: new per usage. `Scoped`: one per request scope. `Singleton`: one per container lifetime. Injecting a `Scoped` service into a `Singleton` captures it for the container's lifetime, breaking per-request semantics (state leakage, thread safety, memory leaks). Fix: resolve via `IServiceScopeFactory.CreateAsync()` to create a proper scope.

DN5 — **string vs ReadOnlySpan<char>, Span<T> usage**: `string` is immutable, heap-allocated, and GC-managed. `ReadOnlySpan<char>` is a stack/inline value type enabling zero-copy, bounds-checked slicing without allocations. `Span<T>` is the mutable counterpart. Use `Span<T>`/`ReadOnlySpan<T>` for high-performance parsing, formatting, or buffer manipulation where avoiding copies and GC pressure is critical.

DN6 — **GC, Generations, LOH, IDisposable**: GC tracks object references, reclaims unreachable memory, and compacts heaps. `Gen 0`: short-lived, frequent collection. `Gen 1`: buffer. `Gen 2`: long-lived, infrequent. Objects promote when they survive collections. `LOH`: heap for objects >85KB, not compacted by default (causes fragmentation), collected only with Gen 2. `IDisposable` provides deterministic cleanup for unmanaged resources (handles, native memory); GC only manages managed memory.

DN7 — **ConfigureAwait(false), SynchronizationContext**: Default `await` captures the current `SynchronizationContext` (or `TaskScheduler`) and resumes on it. `ConfigureAwait(false)` skips context capture, resuming on any thread pool thread. Use in libraries/shared code to avoid deadlocks and improve throughput. Do NOT use in UI/framework code where context-specific operations (e.g., UI updates) are required post-await. Relates to `SynchronizationContext` because capturing it marshals execution back to the original context, which can deadlock if that context is blocked waiting for the task.

DN8 — **.NET 8/9 features**: Primary constructors declare parameters directly in the type signature, auto-injecting into fields/properties. Collection expressions (`[1, 2, 3]`, `[..arr]`) simplify collection creation. `FrozenDictionary` is an immutable, lookup-optimized dictionary using perfect hashing for lower memory/CPU overhead. Example with DI:
```csharp
public record MyService([FromKeyedServices("db")] IDbConnection conn);
```

DN9 — **ObjectDisposedException on DbContext under high concurrency**: Likely cause: DbContext is registered as `Transient` or manually disposed (`using`) in a background task, or shared across requests. EF Core's `DbContext` is `Scoped` by default in ASP.NET Core, tied to the HTTP request. Sharing it breaks the unit-of-work pattern and causes disposal/concurrency conflicts. Fix: keep it `Scoped`, never manually dispose in web apps, and use `IServiceScopeFactory` to create a scope for background work.

DN10 — **record vs class, record struct**: `record` is a reference type with value-based equality, immutable by default, and positional syntax. `class` uses reference equality and is mutable. `record struct` is a value type with value equality and zero allocation. Choose `record` for domain models/DTOs needing value semantics, `record struct` for performance-critical short-lived data, and `class` for mutable/stateful objects.

DN11 — **ref, out, in**: `ref` passes a reference by reference; caller must initialize, callee can read/write. `out` passes by reference; caller need not initialize, callee must assign before return. `in` passes by reference, read-only; prevents modification while avoiding copies of large structs. Use `ref` for bidirectional parameters, `out` for multiple returns/parsing, `in` for large structs where immutability is guaranteed.

DN12 — **Nullable reference types vs value types**: NRTs (`string?`) are compile-time annotations that warn about potential null reference exceptions; they don't affect runtime behavior. `#nullable enable` activates them. Nullable value types (`int?`) are runtime wrappers (`Nullable<T>`) that actually hold null. NRTs enforce compile-time safety for reference types; `T?` for value types enables runtime nullability.

DN13 — **LINQ, method vs query syntax, deferred execution**: LINQ unifies querying across collections, DBs, XML, etc. Method syntax (`list.Where(...).Select(...)`) is fluent and preferred for complex queries. Query syntax (`from x in list where ...`) compiles to method syntax and reads like SQL. Deferred execution means the query isn't executed until enumerated (e.g., `foreach`, `.ToList()`), enabling composition and lazy evaluation.

DN14 — **Generic constraints**: `where T : class` (reference type), `where T : struct` (non-nullable value type), `where T : new()` (parameterless constructor), `where T : IComparable<T>` (implements comparison). Combine for type safety: e.g., `where T : class, IComparable<T>, new()` ensures T is a reference type, comparable, and instantiable. Used in collections, serializers, and factories.

DN15 — **abstract class vs interface, default interface methods**: Abstract classes can have state, constructors, and partial implementation; single inheritance. Interfaces define contracts; multiple inheritance. C# 8+ default interface methods allow interfaces to provide implementations, enabling backward-compatible API evolution and multiple behavioral contracts. Conflicts are resolved via explicit implementation.

DN16 — **Middleware pipeline, Use/Map/Run, ordering, exception handling**: Middleware processes requests/responses sequentially. `app.Use()` adds middleware that can call `await next()`. `app.Map()` branches for specific paths. `app.Run()` is terminal (no `next()`). Ordering matters: auth before routing, error handling early, static files before MVC. `UseExceptionHandler` catches unhandled exceptions, logs, and returns error responses; place it early to catch downstream failures.

DN17 — **Channel<T> vs BlockingCollection<T>, backpressure**: `Channel<T>` is modern, async-native, supports bounded/unbounded, and natively applies backpressure. `BlockingCollection<T>` is older, sync/blocking, and less efficient for async. Bounded example: `var ch = Channel.CreateBounded<int>(100);` Producers `WriteAsync` block when full; consumers `ReadAsync` process at their pace, naturally throttling producers without manual signaling.

DN18 — **Source Generators, incremental generators**: Source generators compile-time code generation via Roslyn APIs, injecting C# into the compilation. Faster and more debuggable than reflection (runtime) and IL weaving (post-compile assembly modification). Incremental generators (`IncrementalGenerator`) use `IncrementalGeneratorInitializationContext`, support caching, incremental compilation, and better performance. Preferred over legacy `ISourceGenerator` for modern .NET.

DN19 — **TPL Dataflow vs Channels**: TPL Dataflow provides message-passing blocks: `ActionBlock` (processes, no output), `TransformBlock` (maps input to output), `BufferBlock` (stores without processing). Supports fan-out/in, branching, and completion propagation. `System.Threading.Channels` is simpler, async-native, and better for straightforward producer-consumer pipelines. Use Dataflow for complex workflows; Channels for simple, high-throughput pipelines.

DN20 — **Minimal APIs vs Controllers, trade-offs, route groups, filters**: Minimal APIs are lightweight, inline handlers with less boilerplate and faster startup. Controllers offer structured routing, model binding, filters, and easier testing/mocking. Trade-offs: Minimal APIs sacrifice some testability/middleware flexibility but gain simplicity/performance. OpenAPI support is now robust in .NET 8+ via `MapOpenApi`. Route groups (`app.MapGroup("/api")`) prefix routes and apply tags. Endpoint filters (`builder.AddFilter(...)`) handle cross-cutting concerns (auth, validation) at the endpoint level.

P1 — **list vs tuple, set vs frozenset**: Lists are mutable, ordered, indexed, allow duplicates. Tuples are immutable, ordered, fixed-size, heterogeneous, and unpackable. Sets are mutable, unordered, unique elements, hash-based. Frozensets are immutable sets, hashable, usable as dict keys or in other sets.

P2 — **GIL**: Global Interpreter Lock is a mutex allowing only one thread to execute Python bytecode at a time. It severely limits CPU-bound multithreaded workloads (no true parallelism). Workarounds: multiprocessing, C extensions that release the GIL, `asyncio` for I/O-bound concurrency, or alternative runtimes (though not mainstream).

P3 — **deepcopy vs copy**: `copy.copy()` creates a shallow copy: new container, but nested objects are shared. `copy.deepcopy()` recursively copies all nested objects. Example: `a = [[1,2]]; b = copy.copy(a); b[0].append(99); print(a)` → `[[1, 2, 99]]` because inner lists reference the same object.

P4 — **Decorators, execution time**: Decorators wrap functions to extend behavior without modifying source.
```python
import time, functools
def log_time(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — **Generators, yield, yield from**: Generators use `yield` to produce lazy iterators, pausing/resuming state without loading everything into memory. Unlike lists, they use O(1) memory and support infinite sequences. `yield from` delegates to another generator/iterable, simplifying nesting and forwarding.

P6 — **asyncio, run/gather/create_task, time.sleep**: The event loop is a single-threaded scheduler managing coroutines. `asyncio.run()` creates the loop, runs a coroutine, and closes it. `asyncio.gather()` runs multiple coroutines concurrently, returning results. `asyncio.create_task()` schedules a coroutine for background execution. `time.sleep()` blocks the entire event loop; use `await asyncio.sleep()` to yield control.

P7 — **MRO, C3 linearization, diamond inheritance**: MRO defines the method lookup order. Python 3 uses C3 linearization (ensures monotonicity, left-to-right precedence). For `D(B, C)` where `B(A)` and `C(A)`, MRO is `D → B → C → A`. `D().who()` skips D and B (no override), finds `C.who()`, and prints `"C"`. C3 resolves the diamond by linearizing left-to-right, skipping already-visited classes.

P8 — **Metaclass vs __init_subclass__**: Metaclasses control class creation (`__new__`, `__init__`), enabling global class modification. `__init_subclass__` is a class method called when a subclass is created, offering simpler per-subclass hooks. Use metaclasses for global transformations (ORM field registration, singleton enforcement). Use `__init_subclass__` for per-subclass customization (auto-registration, default injection).

P9 — **multiprocessing vs threading vs concurrent.futures**: Threading shares memory, ideal for I/O-bound work, but GIL limits CPU parallelism. Multiprocessing spawns separate processes, bypasses GIL, ideal for CPU-bound work, but has higher overhead. `concurrent.futures` provides a high-level API (`ThreadPoolExecutor`, `ProcessPoolExecutor`) unifying both. Multiprocessing uses pickle for serialization; unpicklable objects (locks, DB connections, lambdas) fail. Use `multiprocessing.shared_memory` or `pathos` for complex objects.

P10 — **__slots__**: Declares a fixed set of attributes, preventing `__dict__` creation. Use for memory optimization, performance, and preventing accidental attribute assignment. Reduces per-instance memory significantly (no dict overhead). Breaks inheritance if subclasses don't declare their own `__slots__`.

P11 — **Virtual environments, venv vs virtualenv vs conda**: A virtual environment isolates Python packages/interpreter per project. Prevents dependency conflicts and ensures reproducibility. `venv`: standard library, lightweight, pure Python. `virtualenv`: third-party, more features, pre-venv standard. `conda`: package + env manager, handles non-Python binaries, data-science focused.

P12 — **Comprehensions vs map/filter**: Comprehensions (`[x for x in lst if x > 0]`, `{k: v for ...}`) are Pythonic, readable, and often faster. `map()`/`filter()` return lazy iterators, functional in style. Prefer comprehensions for readability; `map`/`filter` for performance with built-ins or functional pipelines.

P13 — **== vs is, object interning**: `==` checks value equality (`__eq__`). `is` checks identity (same memory address). CPython interns small integers (-5 to 256) and some strings for performance. `a is b` returns `True` for interned objects because they reference the same cached instance.

P14 — **\*args, \*\*kwargs, /, \***: `*args` collects extra positional args into a tuple. `**kwargs` collects extra keyword args into a dict. `/` marks parameters as positional-only (before it). `*` marks parameters as keyword-only (after it). Use for flexible APIs, argument forwarding, and enforcing calling conventions.

P15 — **Context managers**: `with` ensures cleanup (`__exit__`) even on exceptions. Implement via `__enter__`/`__exit__` (class-based) or `@contextmanager` (generator-based, simpler). Example beyond files: database transaction management, acquiring/releasing locks, or creating/temporarily modifying environment variables.

P16 — **Type hinting, Union, Optional, Literal, TypeVar, Protocol**: Type hints are static annotations for IDE/tooling, not enforced at runtime. `Union[A, B]`/`Optional[T]` (Union[T, None]) allow multiple types. `Literal["a", "b"]` enforces exact values. `TypeVar` enables generics with constraints/bounds. `Protocol` enables structural subtyping (duck typing). `mypy`/`pyright` parse hints to catch type mismatches and enforce contracts.

P17 — **Data model (dunder methods)**: `__repr__` is unambiguous/developer-focused; `__str__` is readable/user-focused. `__eq__` defines value equality; `__hash__` defines hash for dict/set membership. `__getattr__` is a fallback when attribute isn't found; `__getattribute__` intercepts every access (dangerous, can cause recursion). Defining `__eq__` without `__hash__` sets `__hash__ = None`, making instances unhashable.

P18 — **Descriptors**: Descriptors are objects implementing `__get__`, `__set__`, `__delete__` that control attribute access on owner classes. `property` is a data descriptor with getter/setter. `classmethod`/`staticmethod` are non-data descriptors that modify `__get__` behavior based on class/instance. Under the hood, attribute lookup checks the descriptor protocol before checking the instance `__dict__`.

P19 — **Import system**: Relative imports (`from . import mod`) resolve relative to the package; absolute imports (`from pkg import mod`) resolve from the root. `sys.path` lists search directories; `PYTHONPATH` prepends to it. `__init__.py` marks directories as packages and runs on import. Namespace packages allow splitting packages across paths without `__init__.py`. Finders locate modules in `sys.path`; loaders compile them into code objects. `importlib` standardizes this.

P20 — **dataclasses vs attrs vs Pydantic**: `dataclasses` (built-in) generates `__init__`, `__repr__`, `__eq__`, `__hash__`; simple and fast. `attrs` adds validation, converters, frozen, and better inheritance. `Pydantic` provides runtime validation, type coercion, serialization, and nested models; ideal for APIs/DBs. `__post_init__` runs after `__init__` for custom logic. `field(default_factory=list)` avoids mutable default argument bugs. Frozen dataclasses are immutable. Inheritance works but `__init__` merging requires care. Choose Pydantic for validation/API boundaries; dataclasses/attrs for internal domain models.
