T1 — `tofu plan` performs a dry-run: it reads config, refreshes state (optional), and generates an execution plan showing what will be created, updated, or destroyed without making changes. `tofu apply` executes that plan, making the actual API calls to provision/modify infrastructure.

T2 — State is a JSON file mapping configuration resources to real-world infrastructure attributes. Remote state is critical for team collaboration, prevents state file corruption, enables state locking, and allows state to survive local machine changes or CI/CD pipeline resets.

T3 — `count` uses integer indices (0, 1, 2) and is suitable for homogeneous resources. `for_each` uses maps or sets of strings, preserving unique keys. `for_each` is preferred when resources have distinct identifiers or when list changes should only affect modified items, avoiding full recreation on index shifts.

T4 — OpenTofu detects drift during `tofu plan` by comparing the remote state to live infrastructure. On `tofu apply`, it overwrites the external change to match the configuration (unless `ignore_changes` is set). This ensures configuration-driven consistency but can overwrite manual tweaks.

T5:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.key
  }
}
```

T6 — `terraform_remote_state` reads the entire state file, which is slow and exposes sensitive data. Output values expose only specific, intentional data. Recommended alternative: Use `terraform_remote_state` but explicitly reference only required outputs, or refactor to a single root module and pass outputs via variables. For cross-root sharing, consider a dedicated state backend with a query API or Terraform Cloud/Enterprise workspaces.

T7 — Provisioners run during resource creation, but outputs are evaluated after resource creation and before provisioners finish, causing a race condition where the output is empty. Fix: Add `depends_on = [null_resource.kubeconfig]` to the dependent resource, or better, generate the kubeconfig via a `local-exec` provisioner or a provider-specific data source that waits for the cluster to be ready.

T8 — `tofu import` manually maps existing infrastructure to state, requiring manual config writing and offering no validation. The `import` block (1.5+) is declarative, supports multiple resources, validates against config during plan, provides better error messages, and integrates with CI/CD workflows.

T9 — A `variable` block defines external input parameters for configuration. An `output` block exposes resource attributes or computed values from the module/root. Variables are inputs; outputs are outputs.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a specific platform. Without `tofu init`, providers aren't downloaded or initialized, causing `tofu plan/apply` to fail with "provider not found" errors.

T11 — `.terraform.lock.hcl` pins provider versions, checksums, and signatures. Commit it to version control to ensure reproducible builds, prevent supply-chain attacks, and guarantee all team members/CI use identical provider binaries.

T12 — `tofu destroy` removes all managed resources in the current state. Target a single resource: `tofu destroy -target=module.name.resource_type.resource_name`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to fetch the latest Ubuntu AMI ID instead of managing an AMI resource.

T14 — `locals` compute derived values within the configuration scope and aren't exposed as inputs. `variables` accept external input. Use `locals` for transformations, conditional logic, or avoiding repetition of complex expressions.

T15 — `lifecycle` controls resource creation/deletion behavior:
- `create_before_destroy`: Creates new instance before destroying old (zero-downtime for load balancers/DBs).
- `prevent_destroy`: Blocks `destroy` to prevent accidental data loss (use cautiously).
- `ignore_changes`: Skips drift detection for specific attributes (e.g., auto-scaling tags, instance metadata).

T16 — The `moved` block tracks resource address changes during refactoring. It tells OpenTofu to remap existing state to the new address without destroying/recreating resources, preserving infrastructure while updating configuration structure.

T17 — OpenTofu builds a DAG of dependencies. Implicit dependencies are inferred from variable/resource references. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, breaking parallelism. Use sparingly to avoid blocking the entire graph when only a subset needs ordering.

T18 — Strategies to reduce plan time:
1. `-refresh=false`: Skips state refresh (tradeoff: stale state, potential drift).
2. Split into multiple state files/modules: Reduces graph size (tradeoff: cross-module references become complex).
3. Defer/cache data sources: Use `data` sources sparingly or cache results (tradeoff: less dynamic info, cache management overhead).
4. Use workspaces/targeting: Scope plans to specific environments (tradeoff: doesn't reduce full-state plan time, requires workflow changes).

T19 — State locking uses a backend-specific mechanism (e.g., DynamoDB, Consul) to prevent concurrent writes. If a pipeline crashes, the lock remains. Break it with `tofu force-unlock <LOCK_ID>`. Risk: Data corruption if another process is actively running.

T20 — Steps:
1. Add backend config to `main.tf` (S3 + DynamoDB).
2. Run `tofu init -migrate-state`. OpenTofu uploads local state to S3 and creates a lock in DynamoDB.
3. Verify: `tofu state list` should match, S3 bucket contains state files, and `tofu plan` shows no drift.
4. Existing state file is safely migrated; local file can be deleted after verification.

A1 — A playbook is a YAML file defining automation steps. A role is a reusable collection of tasks, files, templates, and variables. A task is a single unit of work (module execution) within a playbook or role.

A2 — `ansible_facts` are auto-discovered system attributes. Access OS family via `{{ ansible_os_family }}`.

A3 — `command`: runs commands safely (no shell features). `shell`: runs via shell, supports pipes/redirects. `raw`: runs via SSH without Python, for bootstrapping unmanaged hosts. Use `command` for safety, `shell` for complex commands, `raw` for initial setup.

A4 — Idempotency means a task produces the same result regardless of how many times it runs. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites each run).

A5:
```yaml
- name: Install htop (and epel-release on RHEL)
  package:
    name: "{{ (ansible_os_family == 'Debian') | ternary('htop', 'epel-release htop') }}"
```

A6 — Precedence (highest to lowest): Extra vars > Command line > Play vars > Host vars > Group vars > Role vars > Role defaults > Inventory vars.

A7 — Use `serial: 3` to process 3 nodes at a time. Group first 3 in `rke2_first`, rest in `rke2_rest`. Add `max_fail_percentage: 0` to halt on failure. Use `wait_for` or `pause` if explicit synchronization is needed, but `serial` inherently batches execution.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'my_secret' --name 'db_password'` and paste the `!vault` block into the vars file.

A9 — Inventory lists hosts/groups. Static: hardcoded file (INI/YAML). Dynamic: script/API that generates inventory on-demand (e.g., cloud metadata, CMDB).

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task that runs only when explicitly notified. Differs from regular tasks (run unconditionally). Trigger with `notify: handler_name` in a task.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `log_path`.

A13 — `register` saves task output to a variable. Use in subsequent tasks: `when: my_var.stdout == "success"` or `debug: msg="{{ my_var.stdout_lines }}"`.

A14 — `include_tasks` is dynamic (evaluated at runtime, supports `when`). `import_tasks` is static (evaluated at parse time, faster, but no conditionals). Use `include_tasks` for conditional logic, `import_tasks` for performance.

A15 — Ansible Galaxy is a hub for community roles/collections. `requirements.yml` lists dependencies. Install with `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins manage host communication. `ssh`: standard Linux/Unix. `local`: runs on control node. `network_cli`: network devices (IOS, Junos). Use `ssh` for servers, `local` for control tasks, `network_cli` for routers/switches.

A17 — `delegate_to` runs a task on a specified host. `run_once` runs a task once across all hosts. Example: Gather facts from one host, then write aggregated config to `localhost` once using `delegate_to: localhost` and `run_once: true`.

A18 — Performance strategies:
1. Increase `forks`: Parallelizes tasks (tradeoff: higher control node CPU/memory).
2. Enable `pipelining`: Reduces SSH overhead (tradeoff: requires SSH config changes, minor security consideration).
3. Fact caching: Avoids repeated fact gathering (tradeoff: stale facts, requires cache backend setup).
4. Mitogen: Replaces SSH with persistent connections (tradeoff: third-party, requires compatibility testing).

A19 — Jinja2 uses `{{ }}` for output, `{% %}` for control flow, `{# #}` for comments.
Template snippet:
```jinja2
upstream backend {
{% for server in backend_servers %}
    # Health check: {{ server }}
    server {{ server }};
{% endfor %}
}
```

A20 — Rolling deploy structure:
- `serial: 1` (or `20%`)
- `block`: 
  - Pre-task: `uri` module to set LB maintenance mode
  - Deploy tasks
  - Post-task: `uri` health check loop
- `rescue`: Rollback tasks (re-enable LB, revert config)
- `always`: Cleanup/logging
Ensures zero-downtime by draining traffic, verifying health, and rolling back on failure.
