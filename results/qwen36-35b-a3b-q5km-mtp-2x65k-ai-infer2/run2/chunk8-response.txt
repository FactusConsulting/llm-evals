CL1 — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, runtime, data, and apps. Example: AWS EC2. PaaS provides runtime, middleware, and OS; you manage apps and data. Example: Google App Engine. SaaS provides fully managed applications; you only manage user access and data. Example: AWS WorkSpaces.

CL2 — The Shared Responsibility Model divides security: provider secures the cloud infrastructure; customer secures what they put in it. IaaS VM: Provider = physical hardware, hypervisor, host OS. Customer = guest OS, patches, network config, data, IAM. Managed K8s: Provider = control plane, node OS, API server, etcd. Customer = worker apps, network policies, RBAC, secrets, data. SaaS (M365): Provider = app, infra, compliance, patches. Customer = user accounts, data, access policies, MFA, device compliance.

CL3 — VPC: Isolated virtual network. Subnet: IP range within a VPC, confined to one AZ. Security Group (SG): Stateful, instance/pod-level, allow-only rules, evaluated before routing. NACL: Stateless, subnet-level, allow/deny rules, evaluated after routing. Layering: Traffic enters VPC → routed to subnet → NACL checks → SG checks → instance. Stateful = automatically allows return traffic; Stateless = requires explicit rules for both directions.

CL4 — Landing zone: Pre-configured, secure multi-account foundation with networking, logging, and guardrails. OUs: Group accounts by function/environment (dev, prod, shared services). Guardrails: SCPs, IAM boundaries, config rules, mandatory tagging. Shared networking: Transit Gateway/Azure Hub-and-Spoke for centralized inter-VPC/VNet routing and on-prem connectivity. Centralized logging: Single account aggregates CloudTrail/Activity Log, VPC flow logs, threat detection. Single-account problems: Massive blast radius, permission sprawl, opaque billing, compliance isolation failures, deployment bottlenecks.

CL5 — IaC: Managing infrastructure via declarative/programmatic code. Terraform/OpenTofu: Declarative HCL, state-based, vendor-neutral, massive provider ecosystem. Best for multi-cloud, large teams, established workflows. Pulumi: Programmatic (TS/Python/Go), state-based, native cloud SDKs. Best for complex logic, dev-heavy teams. CloudFormation/Bicep: AWS-native, declarative, tightly integrated, faster AWS deploys. Best for AWS-only shops. Crossplane: K8s-native IaC, manages cloud resources via CRDs. Best for GitOps/K8s-centric teams wanting a unified control plane.

CL6 — HPA: Scales pods based on CPU/memory/custom metrics. VPA: Recommends/sets pod resource requests/limits based on historical usage. Cluster Autoscaler: Adds/removes nodes when pods can't schedule. KEDA: Event-driven scaling, scales to/from zero, supports Kafka, SQS, Prometheus, etc. Use KEDA over HPA for event-driven workloads, scaling to zero, or non-CPU metrics. HPA is better for steady-state, metric-driven scaling.

CL7 — RPO/RTO dictate DR design. Active-active: RPO≈0, RTO≈0, high cost/complexity. Active-passive: RPO>0, RTO>0, lower cost. DB replication: Sync (strong consistency, higher latency, active-active) vs Async (eventual consistency, lower latency, active-passive). DNS failover: Route53/Traffic Manager health checks, weighted routing, low TTLs. State management: Externalize state (DB, object storage, distributed cache), use distributed locks/queues. DR models: Pilot light (core infra running, scale up on failover), Warm standby (scaled-down prod ready), Multi-site active-active (full prod in both, sync traffic). Cost: Active-active doubles infra + data transfer; pilot light cheapest but higher RTO.

CL8 — GitOps: Git is the single source of truth. Controllers continuously reconcile cluster state with Git. ArgoCD: Push-based (cluster polls Git), UI-heavy, app-of-apps. Flux: Pull-based (cluster watches Git), Git-native, CLI-focused. Both excellent; choose based on team preference. Secrets: SealedSecrets (encrypted in Git), External Secrets Operator (syncs from AWS Secrets Manager/Vault), Vault Agent Injector. Never commit plaintext. Drift: Controllers detect drift, auto-revert to Git state, or flag for review. Manual changes are overwritten on next sync unless explicitly excluded.

CL9 — StatefulSet: Stable network ID, ordered deployment/termination, stable storage. PV/PVC + local storage: `local` storageClass, `volumeBindingMode: WaitForFirstConsumer` to bind to node with local disk. Headless service: `clusterIP: None`, enables direct pod DNS resolution. Init containers: Pre-load config, migrate data, or set permissions before main app starts. ConfigMaps as volume mounts: Mount config files at required paths; use `subPath` if needed. PDB: `minAvailable` or `maxUnavailable` to ensure quorum during node drains/upgrades. Note: Local storage lacks built-in replication; pair with backup strategy.

CL10 — SA: K8s-native identity, no cloud permissions by default. Workload Identity (GCP/Azure): Maps K8s SA to cloud IAM identity without keys. IRSA (AWS): Maps K8s SA to IAM Role via OIDC provider. Mounting creds: Bad practice (leaks, rotation issues, violates least privilege, pod compromise = full cloud access). Federation solves: OIDC-based token exchange, short-lived credentials, automatic rotation, scoped IAM policies.

CL11 — Object (S3/Blob): Scalable, HTTP API, metadata-rich, eventual/strong consistency. Durability: 99.999999999%. Use for backups, media, data lakes. Block (EBS/Managed Disk): Low-latency, mounted as filesystem, attached to single VM. Durability: 99.99%+. Use for OS, databases, apps needing POSIX. File (EFS/Azure Files): NFS/SMB, shared across multiple VMs. Durability: 99.99%+. Use for shared configs, home dirs, legacy apps. Availability: Object = multi-AZ by default; Block = AZ-bound; File = AZ-bound or regional depending on tier.

CL12 — Network Policies: Default deny, allow only required pod-to-pod/service traffic. Service Mesh (mTLS): Istio/Linkerd for encrypted service-to-service, identity-based routing. Pod Identity: Workload identity/IRSA for cloud resource access. Admission Controllers: OPA/Kyverno enforce policies (no privileged pods, signed images, resource limits). Image signing: Cosign/Notary, verify signatures at admission. Runtime security: Falco monitors syscalls, detects anomalies. Secrets: External Secrets Operator/Vault, never in env vars or etcd plaintext. vs Perimeter: Zero-trust assumes breach, verifies every request, micro-segmentation, identity-centric. Perimeter relies on network boundaries, trusts internal traffic.

CL13 — CDN: Distributed edge cache network. Caches static/dynamic content closer to users. How: User request → DNS to nearest edge → cache hit/miss → fetch origin → cache & serve. Services: CloudFront, Azure CDN, Fastly. CDN vs Origin: Use CDN for static assets, video, global users, DDoS mitigation, offloading origin. Direct origin for dynamic, low-latency internal, or cache-busting needs.

CL14 — Region: Geographic area with multiple AZs. AZ: One or more discrete data centers with independent power/network/cooling, connected via low-latency links. Multi-AZ: Fault tolerance against AZ failure, higher availability. Zonal: Tied to one AZ (EBS, most VMs). Regional: Span multiple AZs (ELB, Route53, EFS).

CL15 — Managed DB: RDS/Cloud SQL/Azure SQL. Provider handles provisioning, patching, backups, replication, monitoring, failover. vs VM: You manage OS, DB software, config, backups, scaling, HA. Managed saves ops overhead, improves reliability, but costs more and limits low-level access.

CL16 — IAM: Users (human/service), Groups (collections), Roles (assumable identities with policies), Policies (JSON permissions). Least Privilege: Grant only necessary permissions. Apply via scoped policies, avoid `*:*`, use conditions, regular access reviews, temporary credentials, role assumption.

CL17 — Serverless: Managed compute, pay-per-use, auto-scaling, no infra management. Compare: Lambda (AWS), Functions (Azure), GCF (GCP). Similar models, slight differences in runtime support, cold start behavior, limits. Cold starts: Container initialization delay on first/infrequent invocation. Matters for latency-sensitive apps. Mitigate with provisioned concurrency, smaller images, keep warm. Poor fit: Long-running processes, stateful apps, predictable high throughput (reserved VMs cheaper), strict compliance/air-gapped needs.

CL18 — Ingress Resource: Standard K8s CRD, relies on controller (nginx, ALB), TLS termination at controller. Gateway API: Next-gen, separates routing (Gateway) from backend (HTTPRoute), better RBAC, multi-tenant, TLS termination at gateway. Cloud LB annotations: Directly provision cloud LB (ALB/ILB), TLS termination at LB. Service Mesh Ingress: Istio/Linkerd ingress gateway, mTLS, advanced traffic mgmt, TLS termination at mesh. Gateway API vs Ingress: Use Gateway API for multi-tenant, fine-grained RBAC, standardized routing, future-proofing. Ingress is simpler for single-team, single-controller setups.

CL19 — RI/SP: Commit to 1-3yr for predictable workloads (30-70% discount). Spot/Preemptible: 60-90% off for fault-tolerant/batch workloads. Right-sizing: Monitor utilization, downsize overprovisioned, use auto-scaling. Storage tiering: S3 Intelligent-Tiering, lifecycle policies to Glacier/Archive, delete orphaned snapshots/EBS. Idle detection: CloudHealth, AWS Cost Explorer, Azure Advisor, tag-based idle resource alerts. FinOps: Cross-functional team, showback/chargeback via tags, monthly reviews, budget alerts, cost allocation reports. Tools/Processes: Native (Cost Explorer, Azure Cost Mgmt), third-party (CloudHealth, Kubecost, Datadog), processes: tagging strategy, approval workflows, quarterly RI/SP reviews, spot fleet integration.

CL20 — Abstraction: Terraform/OpenTofu, Kubernetes, service mesh, API gateways. K8s runtime: EKS/AKS/GKE, GitOps, uniform deployment. IaC: Terraform modules, provider-agnostic design, avoid cloud-specific services where possible. Networking: Cloud VPN, Direct Connect/ExpressRoute, global load balancers, DNS routing. Identity: OIDC federation, centralized IdP (Okta/Azure AD), cross-cloud SSO. Trade-offs: Higher complexity, data egress costs, inconsistent SLAs, operational overhead vs theoretical resilience/flexibility. Justified: Regulatory/data sovereignty, avoiding single-vendor risk, leveraging best-of-breed, M&A integration. Unnecessary: Small/mid teams, cost-sensitive, simple workloads, where cloud-native services provide better value than abstraction overhead.

OT1 — Purdue Model (ISA-95): Hierarchy for industrial automation. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, DCS). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations/Manufacturing execution (MES, production scheduling). Level 4: Business/Enterprise (ERP, finance, supply chain). Level 5: Enterprise cloud/corporate IT.

OT2 — IT: Focus on confidentiality, data integrity, availability. Fast patching, frequent updates, user-centric. OT: Focus on safety, availability, process continuity. Legacy systems, real-time constraints, proprietary protocols, cannot tolerate downtime/patching. Why not IT patching: OT systems run 24/7, unpatched firmware/OS is often certified/validated, rebooting can cause physical damage or safety hazards, vendor support may require specific versions.

OT3 — IDMZ: Segmented network between IT (L4) and OT (L0-L2). Acts as buffer. Traffic: Unidirectional or strictly controlled bidirectional. Typically, IT pulls data from IDMZ (OPC UA, MQTT, SQL). OT pushes to IDMZ via data diodes or firewalls. Direct L4->L1 dangerous: Exposes control systems to internet threats, bypasses OT security controls, risk of malicious commands, ransomware, or protocol exploitation directly to PLCs.

OT4 — Modbus TCP: L1/L2, simple request/response, widely used in legacy PLCs. OPC UA: L2/L3, secure, platform-independent, information modeling, modern standard. EtherNet/IP (CIP): L1/L2, industrial Ethernet, Allen-Bradley dominant, real-time. PROFINET: L1/L2, Siemens ecosystem, deterministic, real-time. MQTT: L2/L3/L4, lightweight publish/subscribe, IoT/cloud bridge, not real-time.

OT5 — Data diode: Hardware-enforced unidirectional data flow. Physically prevents return traffic. Firewall: Software/hardware, bidirectional, inspects/controls traffic based on rules. Use diode: When strict unidirectional data flow is required (e.g., OT to IT reporting, high-security zones). Limitation: Cannot inspect return traffic, no bidirectional control, less flexible for complex protocols, higher cost/complexity for bidirectional needs.

OT6 — Flow: PLCs/RTUs → OPC UA Server (L1/L2) → Edge Gateway (protocol translation, buffering, security) → MQTT Broker (L3) → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: IDMZ at edge, TLS/mTLS for all links, mutual auth, firewall between OT and edge, cloud IAM for ingestion, data validation at edge, encrypted storage. Place boundaries: OT network (L1/L2) isolated, edge gateway in IDMZ, cloud ingestion secured with WAF/IAM, zero-trust for data pipeline.

OT7 — Zone: Logical/physical grouping of assets with similar security requirements. Conduit: Communication path between zones, controlled by security controls (firewalls, diodes). Model: Zone 1: Corporate/IT (L4) → Conduit 1: Firewall/IDMZ → Zone 2: Engineering/SCADA (L3) → Conduit 2: Strict firewall, unidirectional where possible → Zone 3: Control/PLC/HMI (L1/L2) → Conduit 3: Data diode or strict firewall, SIS isolated → Zone 4: SIS (Safety) - physically/logically isolated, independent power/network. Apply SRs per zone, enforce least privilege, monitor conduits.

OT8 — VLAN design: Segment by function/process (e.g., VLAN 10: Line 1 PLCs, VLAN 20: Line 2, VLAN 30: HMIs, VLAN 40: SCADA, VLAN 50: Engineering). Firewall placement: Core firewall between IT/OT, edge firewalls between VLANs, DMZ for cloud/remote access. Switch architecture: Managed Layer 3 switches, port security, 802.1X (if supported), disable unused ports. Remote access: Jump host in IDMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, test in staging, monitor closely.

OT9 — BPCS: Basic Process Control System (PLC/DCS) for normal operation. SIS: Safety Instrumented System for emergency shutdown, independent of BPCS. IEC 61511: Standard for functional safety of SIS in process industry. Defines SIL (Safety Integrity Level) requirements. Isolation: Prevents cyber attacks from compromising safety functions. SIS must operate independently to guarantee safety during IT/OT breaches. Ransomware on SIS: If compromised, safety functions may fail to activate, leading to catastrophic physical damage, environmental release, or loss of life. Hence, air-gap/isolation is critical.

OT10 — PLC: Programmable Logic Controller, discrete control, fast, rugged, used for machine/line control. DCS: Distributed Control System, centralized architecture, integrated I/O, used for continuous processes (chemical, oil/gas). SCADA: Supervisory Control and Data Acquisition, software layer for monitoring/control, aggregates data from PLCs/RTUs, HMI-based. Coexist: Yes, common in large plants. PLCs/DCS handle control, SCADA provides supervisory view, historians store data.

OT11 — Jump hosts: Isolated bastion in IDMZ, no direct OT access. MFA: Mandatory for all remote access. Session recording: Audit trail, compliance. Vendor access: Time-limited, role-based, approved tickets, break-glass procedures. Why RDP to HMI unacceptable: Exposes HMI to corporate network threats, bypasses OT segmentation, RDP vulnerabilities can lead to full OT compromise, violates least privilege.

OT12 — Detection: Network monitoring (IDS/NTA), asset inventory (CMDB), anomaly detection (baseline deviations), EDR on IT/edge, passive OT monitoring. IR steps: Contain (isolate affected segments, disable compromised VPN), eradicate (patch, rotate creds), recover (restore from clean backups), lessons learned. Coordination: Notify control room, switch to manual/local control if needed, ensure safety systems unaffected. Safe operations: Maintain SIS/BPCS isolation, monitor process parameters, fallback procedures, communication protocols. Plant operator role: Monitor physical process, execute manual overrides if automated systems compromised, report anomalies, follow emergency procedures, do not interact with compromised IT/OT systems.

OT13 — HMI: Human-Machine Interface, graphical display for operators to monitor/control processes. Role: Real-time visualization, alarms, manual overrides, trend analysis. vs Engineering Workstation: HMI is for operators (runtime), EWS is for engineers (programming, configuration, diagnostics, firmware updates).

OT14 — Historian: Time-series database for process data (temperatures, pressures, flows). Importance: Trend analysis, compliance, optimization, troubleshooting, predictive maintenance. Plant (L3) vs Enterprise (L4): Plant historian stores high-frequency, detailed process data for operations. Enterprise historian aggregates, summarizes, integrates with ERP/MES for business analytics, lower frequency.

OT15 — Ladder logic: Graphical programming language mimicking relay circuits, used for PLCs. Execution: PLCs scan inputs, execute logic, update outputs cyclically. Dominance: Familiar to electricians, easy to troubleshoot, deterministic, widely supported, legacy integration, low learning curve for industrial workforce.

OT16 — RTU: Remote Terminal Unit, designed for harsh environments, long-distance communication (SCADA), serial/telecom protocols, modular I/O. vs PLC: PLCs are for local, fast, discrete control. RTUs are for remote, telemetry, wide-area monitoring. Deploy RTUs: Pipelines, water distribution, wind farms, oil/gas fields, remote sites with cellular/satellite comms.

OT17 — Analog: Continuous voltage/current (4-20mA, 0-10V), represents physical variable proportionally. Digital: Discrete on/off or binary, used for alarms, status, communication. 4-20mA vs 0-20mA: 4mA "live zero" indicates wire break/failure (0mA = fault), improves diagnostics, less susceptible to noise, standard in industry.

OT18 — Inventory: Complete list of hardware, firmware, software, network connections, and dependencies. Foundation: Cannot secure what you don't know, enables risk assessment, patch management, compliance, incident response. Tools: Passive monitoring (packet capture, protocol analysis), active scanning (ping, SNMP, Modbus scan). Active scanning danger: Can crash legacy devices, cause process disruption, trigger alarms, or be detected as attack. Passive is safer.

OT19 — Framework: Maps adversary tactics/techniques specific to ICS/OT. Tactics & examples: 1. Reconnaissance: Gather network topology (T1580). 2. Resource Development: Acquire ICS-specific malware (T1587). 3. Initial Access: Compromise vendor remote access (T1190). 4. Execution: Run malicious commands on PLC (T1059). 5. Impact: Sabotage process, trigger shutdown (T1499). vs Enterprise ATT&CK: ICS focuses on safety, availability, physical processes, legacy protocols, real-time constraints. Enterprise focuses on confidentiality, data, modern OS/networks. Assessment: Map current defenses to ICS tactics, identify gaps (e.g., no passive monitoring, weak segmentation), prioritize controls, simulate attacks, update IR plans.

OT20 — Log collection: Passive network taps, OPC UA/MQTT log forwarders, SIEM agents on IT/edge, avoid active polling on OT. SIEM integration: Normalize OT logs (Syslog, CEF, OT-specific schemas), correlate with IT logs. OT detection rules: Protocol anomalies, unauthorized PLC writes, HMI config changes, unusual SCADA commands, firmware updates. Triage: OT-specific playbooks, involve OT engineers early, verify against maintenance windows, prioritize safety impact. Staffing: IT analysts (threat intel, malware, network), OT engineers (process knowledge, protocol expertise, safety), joint SOC manager. False positives: OT has predictable cycles, maintenance windows, legacy quirks. Tune rules, baseline behavior, use allowlists, correlate with change management. Unauthorized firmware on PLC: Isolate segment, verify against approved baseline, check change management, rollback if unauthorized, investigate source, update detection rules, notify safety/engineering.
