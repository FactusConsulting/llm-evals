AA1 — Monoliths are single, unified codebases deployed as one unit with shared memory/processes. Microservices are independently deployable, loosely coupled services communicating over a network. Microservices introduce: (1) network latency and failure handling, (2) distributed data consistency challenges, and (3) significantly higher operational complexity (orchestration, CI/CD pipelines, observability).

AA2 — Synchronous communication blocks the caller until a response is received (e.g., REST/HTTP, gRPC). Asynchronous communication decouples sender and receiver; messages are queued and processed later (e.g., RabbitMQ, Kafka, AWS SQS).

AA3 — A reverse proxy routes traffic, terminates TLS, and provides basic load balancing/caching (e.g., Nginx, HAProxy). An API gateway adds API-specific capabilities: rate limiting, auth, request/response transformation, versioning, and analytics. An API gateway can replace a reverse proxy functionally, but is heavier, more complex, and often cloud-managed; reverse proxies remain preferable for non-API traffic or lightweight edge routing.

AA4 — The Saga pattern breaks distributed transactions into local transactions, each with a compensating action for rollback. Choreography uses events to trigger the next step (decentralized, simple but hard to monitor/debug). Orchestration uses a central coordinator sending commands (better for complex/conditional flows, easier to track, but introduces a coordination bottleneck). Use choreography for simple, loosely coupled flows; orchestration for complex, multi-step workflows.

AA5 — CQRS separates read and write models: commands modify state, queries read from optimized read models. Event Sourcing stores state as an immutable sequence of events. They pair naturally because CQRS needs a durable, replayable source of truth for writes. Together they solve auditability, temporal queries, independent read/write scaling, and complex domain logic that traditional CRUD struggles with.

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping traffic to a failing service. States: Closed (normal), Open (failures threshold met, fail fast), Half-Open (tests recovery). Unlike retry+backoff (assumes transient failure and retries), the circuit breaker halts traffic entirely to allow downstream recovery. Use both: retry for transient blips, circuit breaker for sustained failures; apply retry with backoff inside the half-open state or for idempotent calls.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, requires row-level security, low operational complexity.
2. Shared DB, separate schema: Moderate cost, better isolation, easier per-tenant backup/restore, moderate complexity.
3. Separate DB per tenant: Highest cost, maximum isolation/security, trivial backup/migration, high operational complexity (connection pooling, schema migrations at scale).

AA8 — Eventual consistency allows temporary stale reads; strong consistency guarantees all reads see the latest write. For zero-oversell inventory: use strong consistency with a relational DB (PostgreSQL) and `SELECT ... FOR UPDATE` row locking or optimistic versioning. At scale: partition by SKU/warehouse, use a dedicated inventory service with distributed locks or Redis Lua scripts for atomic decrements, and run reconciliation jobs to catch edge cases.

AA9 — A sidecar proxy is a companion container that intercepts all inbound/outbound traffic. In Istio, Envoy handles the data plane (routing, mTLS, metrics, retries), while the Istio control plane (Pilot, Citadel) pushes config and manages certificates. mTLS between sidecars provides transparent, zero-trust service-to-service authentication without application code changes, unlike app-level TLS which requires manual cert management per service.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is decommissioned. Strategy: Place an API gateway in front of the .NET Framework monolith. Identify a bounded context (e.g., user auth), build the .NET 8 microservice, route its endpoints via the gateway, implement dual-write or CDC for data sync, and repeat per feature. Use feature flags for gradual rollout and decommission monolith routes as traffic shifts.

AA11 — 12-Factor App methodology ensures cloud-native readiness. Six factors: (1) Codebase (one repo, many deploys), (2) Dependencies (explicitly declared/locked), (3) Config (env vars, not code), (4) Backing services (treated as attached resources), (5) Build/release/run (strictly separated stages), (6) Processes (stateless, ephemeral). They matter because they guarantee portability, horizontal scalability, secure config management, and reliable, repeatable deployments.

AA12 — 
- Coupling: Event-driven = loose; Request-driven = tight.
- Scalability: Event-driven = highly scalable, decoupled consumers; Request-driven = scales per endpoint, caller-bound.
- Debugging: Event-driven = harder (async, needs tracing); Request-driven = easier (synchronous, direct logs).
- Ordering: Event-driven = partition-level guarantees; Request-driven = per-request atomic, no global order.
- Failure: Event-driven = durable queues, DLQs, retry later; Request-driven = immediate failure, requires retry/circuit breaker.
Choose event-driven for async workflows, high throughput, and decoupled systems. Choose request-driven for real-time APIs, strict latency, and simple CRUD.

AA13 — A load balancer distributes traffic across multiple backend servers. Layer 4 operates at the transport layer (IP + port), routing based on network info. Layer 7 operates at the application layer (HTTP headers, URLs, cookies), enabling content-aware routing. Layer 7 is required when routing `/api/v1` vs `/api/v2`, terminating SSL, or enforcing cookie/session affinity.

AA14 — Message queues (RabbitMQ) consume and delete messages, support complex routing/exchanges, and excel at task/work queues. Log-based brokers (Kafka) append messages to immutable logs, allow multiple consumers to read at different speeds, and support replayability. Pick RabbitMQ for reliable task processing and strict delivery. Pick Kafka for event streaming, log aggregation, and high-throughput replay.

AA15 — Containers share the host OS kernel, are lightweight, and isolate processes/filesystems. VMs run a full guest OS under a hypervisor, are heavier, and provide hardware-level isolation. Containers are popular for microservices due to fast startup, consistent environments, efficient resource utilization, and native orchestration support (Kubernetes).

AA16 — Stateless services hold no local session data; any instance can handle any request. Stateful services maintain local state. Stateless services scale horizontally easily because load balancers can route freely without affinity, and instances can be added/removed dynamically. Examples: Stateless = web API; Stateful = relational database, message broker.

AA17 — An ORM maps database tables to application objects, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: Pro = developer productivity, DB abstraction, safety, maintainability. Con = N+1 query risks, performance overhead, complex queries hard to optimize, less control over execution plans.

AA18 — The Bulkhead pattern isolates resources to prevent failure in one component from exhausting shared resources elsewhere. In microservices, it prevents thread/connection pool exhaustion. Implementation: Assign separate thread pools and connection pools per downstream service call. Alternatively, deploy critical vs non-critical services on separate node pools or availability zones to isolate resource contention.

AA19 — OT requires a central server to transform concurrent operations to maintain consistency. CRDTs are data structures that mathematically guarantee convergence without coordination. Consistency: OT = strong (server-mediated); CRDTs = eventual (convergent). Latency: OT = higher (server round-trip); CRDTs = lower (peer/local). Complexity: OT = high server logic; CRDTs = high data structure design but simpler deployment. Choice: CRDTs for offline-first editing, as they allow local edits and guaranteed convergence upon sync, whereas OT breaks without server coordination.

AA20 — Challenges include polyglot instrumentation, overhead, and async correlation. Context propagation uses W3C Trace Context or B3 headers to pass trace IDs across services. Sampling: head-based is cheap but loses rare traces; tail-based collects all, samples post-facto, and is accurate but network-heavy. Storage: Jaeger (OTel-native, indexed), Tempo (S3-backed, metadata-only, cost-effective). Async/Kafka: trace context must be serialized into message headers. Continuity: use OpenTelemetry SDKs, propagate `traceparent`/`tracestate` headers, configure Kafka producer/consumer interceptors, and align sampling strategies across the stack.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and data-center use. Examples: VMware ESXi, Proxmox VE, KVM. Type 2 (hosted) hypervisors run as applications on a host OS, offering convenience but lower performance. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block-level storage presented as local disks, ideal for databases/VMs. Uses Fibre Channel or iSCSI. NAS provides file-level storage mounted over a network, ideal for file shares/backups. Uses NFS or SMB/CIFS. Choose SAN for low-latency, high-IOPS workloads; NAS for shared file access and simpler management.

OP3 — 3-tier architecture uses Core (backbone), Distribution (policy/routing), and Access (edge) layers. It suffers from hierarchical bottlenecks and non-deterministic latency. Leaf-spine replaces this with an all-to-all mesh where every leaf connects to every spine. It solves oversubscription and spine bottlenecks, providing deterministic, non-blocking latency and equal-cost multipath routing for east-west traffic.

OP4 — Use 3+ nodes for quorum. Quorum requires a majority to form the cluster. Fencing (STONITH via IPMI/iLO) powers off failed nodes to prevent split-brain. Shared storage: Ceph (distributed, recommended) or HA iSCSI/NFS. On node failure: HA manager detects it, fences the node, and restarts VMs on remaining nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte tag to Ethernet frames containing the VLAN ID. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, assign IPs, and enable `ip_forward` if routing. Alternatively, use `netplan` or `NetworkManager` with VLAN interfaces.

OP6 — RAID 1: mirror, 50% capacity, 1-fault tolerance. RAID 5: striping+parity, 1-fault, write penalty. RAID 6: double parity, 2-fault, higher write penalty. RAID 10: mirror+stripe, 50% capacity, 2-fault (if different mirrors), high perf. RAID Z2: ZFS double parity, flexible capacity, checksums, safe rebuilds. Choice: RAID Z2 for modern DBs due to data integrity and safe rebuilds, or RAID 10 if raw IOPS are critical and budget allows 3 mirror pairs.

OP7 — Recursive resolvers: internal DNS servers for clients. Authoritative: AD-integrated DNS for internal zones, external DNS for public. Forwarders: internal DNS forwards external queries to ISP/Cloudflare. Conditional forwarding: routes internal AD queries to AD DNS, external to forwarders. Split-horizon: internal DNS returns private IPs, external returns public. DNSSEC: sign external zone, publish DS at registrar. Laptop move: DHCP assigns internal DNS; VPN uses split-tunneling/conditional forwarding to route internal queries to corporate DNS.

OP8 — PKI chain: Root CA (offline, air-gapped) -> Subordinate/Issuing CA (online, issues certs) -> End-entity. CRL/OCSP handle revocation. Certificate templates + AD auto-enrollment streamline deployment. Compromised subordinate: revoke certs, issue new subordinate, minimal impact. Compromised root: catastrophic; requires rebuilding entire PKI, redistributing root certs, and causes massive downtime.

OP9 — MPLS: high reliability/low latency, expensive, managed. IPsec VPN: cheap, internet-dependent, variable latency. SD-WAN: intelligent routing, cost-effective, cloud-optimized, centralized management. WireGuard mesh: lightweight/fast, lacks enterprise routing/policy/management. Recommendation: SD-WAN. It optimizes latency/QoS for VoIP, balances cost/reliability, and centralizes policy/security.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: out-of-band management interfaces for remote console, power control, and hardware monitoring. Critical because they provide access when the OS/network is down. Internet exposure: high risk of credential stuffing, known CVE exploitation, ransomware, and full hardware compromise. Should reside on an isolated management network.

OP11 — LVM: traditional, fixed volumes, snapshots consume space quickly. LVM-Thin: overprovisions storage, cheap/fast snapshots, but can exhaust pool space. ZFS: integrated FS+volume manager, copy-on-write, checksums, self-healing, instantaneous space-efficient snapshots. Use LVM for legacy/simple setups, LVM-Thin for VM pools, ZFS for data integrity and modern Linux.

OP12 — Stretch cluster: 2 sites with 2 nodes each + 1 arbiter node. Ceph CRUSH rules split by site. Monitors distributed (2/site + arbiter). Network latency: <5ms ideal, <10ms max. Split-brain prevented by arbiter quorum. 2-site without tiebreaker fails because neither side achieves majority, causing both to act as primary and corrupt data. DR strategy: async replication (DRBD/ZFS send) or Ceph stretch with arbiter.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable: client retries, eventually falls back to APIPA (169.254.x.x). On lease expiry: client tries renewal at T1 (50%) and T2 (87.5%). If failed, releases IP, falls back to APIPA, and loses network connectivity.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP, ACLs, and link aggregation. These features enable network segmentation, traffic prioritization, loop prevention, monitoring, and security in enterprise environments.

OP15 — NTP synchronizes clocks over a network. Critical for log correlation, auth tokens (Kerberos/JWT), distributed consensus, backup scheduling, and replication. Clock drift causes Kerberos auth failures, cluster split-brain, corrupted log timelines, replication lag, and data inconsistency.

OP16 — Physical servers run directly on hardware. VMs add a hypervisor and guest OS. Containers isolate processes sharing the host OS. Run bare metal for maximum I/O performance, GPU passthrough, ultra-low latency networking, compliance requirements, or when hosting hypervisors themselves.

OP17 — UPS provides short-term battery backup and power conditioning, bridging to generator startup. Generators provide long-term power but take seconds to start. Both are needed: UPS covers transition and protects against surges/brownouts. ATS (Automatic Transfer Switch) detects outages, switches load to generator, and switches back when utility returns.

OP18 — Active-passive: one node handles traffic, standby waits. Active-active: both handle traffic, requiring complex sync. PostgreSQL HA with Pacemaker/Corosync: Corosync handles quorum/heartbeat. Pacemaker manages resources (VIP, PG service, STONITH). STONITH ensures failed node is powered off. VIP floats to active node. On failure: Pacemaker detects it, runs STONITH, promotes standby, moves VIP, and starts PG.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. Define RPO (data loss tolerance) and RTO (downtime tolerance). Use full (baseline), incremental (changes since last), or differential (changes since last full). Deduplication reduces storage and backup windows. Disk for fast restore, tape/cloud for cheap offsite. Immutable (WORM) storage prevents ransomware deletion. Test restores regularly via drills. Backup = data preservation; DR = full recovery process (infrastructure, data, procedures) to resume operations.

OP20 — 802.1X is port-based NAC. Roles: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP-TLS uses certificates for mutual auth (secure). PEAP uses username/password in a TLS tunnel (common). RADIUS handles AAA. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: port stays unauthorized, no traffic. MAB: fallback for IoT/printers; switch sends MAC to RADIUS, which matches MAC to policy and grants access (less secure, no cert validation).
