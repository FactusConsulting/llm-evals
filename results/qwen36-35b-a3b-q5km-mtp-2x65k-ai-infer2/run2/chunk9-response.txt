SC1-A
The pods fail because Kubernetes Pod Security Standards (PSS) enforce different constraints than container image defaults. `runAsNonRoot: true` tells the kubelet to reject containers running as UID 0, but without an explicit `runAsUser`, the kubelet defaults to UID 0. The new base image (`cgr.dev/chainguard/static:latest`) also defaults to `USER root`. Under the **Baseline** PSS, running as root was permitted. Under **Restricted** PSS, UID 0 is explicitly forbidden, and the pod spec must either set `runAsUser: <non-zero>` or the container image must declare a non-root `USER`. The kubelet rejects the pod, and the container restart loop triggers `CrashLoopBackOff`.

SC1-C
- **Image fix:** Add `USER appuser` (or `RUN adduser -D appuser && USER appuser`) to the Dockerfile. Pin the base image digest (`cgr.dev/chainguard/static@sha256:...`).
- **Manifest fix:** Add `securityContext.runAsUser: 1000` (or match the image UID) to deployments. Add `securityContext.runAsNonRoot: true` explicitly.
- **CI gate:** Integrate `kube-score` or `kubeval` with PSS checks, plus an admission controller (Kyverno/OPA) that rejects images without a non-root `USER` or missing `runAsUser` when `runAsNonRoot: true` is set. Enforce digest-pinned base images via Trivy/Grype.
- **Rollout:** Use `kubectl rollout restart deployment/<name> --record` with `maxSurge=25%` and `maxUnavailable=25%` to ensure zero downtime. Monitor `kubectl rollout status` before proceeding to the next namespace.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped from the primary to the replica, but network latency and disk I/O create a replication lag. When the replica is promoted, any WAL not yet shipped or replayed is permanently lost. The stale data issue occurs because the application reads from the replica before WAL catch-up completes, or because the promotion cut off in-flight transactions. To quantify the loss window: check `pg_stat_replication` for `write_lag`, `flush_lag`, and `replay_lag`; compare `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()`; and review `pg_stat_replication`'s `sent_lsn` vs `flush_lsn`. The data loss window equals the replication lag at promotion time plus any uncommitted in-flight transactions.

SC2-C
- **Connection management:** Use **RDS Proxy** over PgBouncer. RDS Proxy handles connection pooling, failover transparency, and automatic retry logic natively with AWS, reducing connection churn during failover.
- **Route53:** Configure failover routing with health checks targeting the RDS endpoint. Use `EvaluateTargetHealth` to route to the promoted replica automatically.
- **App retry:** Implement exponential backoff with jitter and idempotent write guards. Use connection poolers with `max_lifetime` and `idle_timeout` tuned to avoid stale connections.
- **RPO < 1s:** Standard RDS cross-region async replication cannot guarantee RPO < 1s. **Aurora Global Database** is recommended: it uses a primary region and up to 5 secondary regions with optimized cross-region replication, automatic failover in < 1 minute, and near-zero RPO for most workloads. For strict RPO < 1s, use synchronous multi-AZ in the primary region and accept cross-region async with monitoring, or use Aurora Global DB with cross-region read replicas and application-level write forwarding.

       blocking_locks.pid AS blocking_pid, blocking_activity.usename AS blocking_user,

SC6-C
- **AWS Direct Connect:** High cost ($5k+ setup + port fees), high bandwidth (10Gbps+), low latency, IPsec/BGP encryption. Requires colocation. Routing: BGP route propagation to TGW. Fits zero-trust poorly (IP-based trust remains).
- **Dual VPN + ECMP:** Low cost, limited bandwidth (2x1Gbps), IPsec encryption, automatic failover. Routing: Equal-cost route tables. Fits zero-trust moderately (still IP-based, but encrypted).
- **Hybrid Mesh (Tailscale/Netbird):** Low cost, software-defined, end-to-end encryption, identity-based access. Routing: Overlay network, no IP trust. Fits zero-trust best (access controlled by identity, not network location).
- **Recommendation:** Use Direct Connect for core data plane (performance), but enforce zero-trust at the application layer via SPIFFE/mTLS. Mesh is ideal for management/auxiliary traffic.

SC10-A
- **Active-passive (Velero):** Backups to S3, restore on failover. RPO = backup interval (min 15m), RTO = restore time (often >1h for 200TB). **Fails RPO/RTO.**
- **Active-active (Istio/Cilium):** Traffic split across sites. Stateful components need cross-site replication. 12ms latency allows async replication with acceptable lag. **Meets RPO/RTO** if replication is optimized.
- **Replication strategy:**
  - **PostgreSQL:** Patroni async replication with `synchronous_commit = off` for cross-site, or use `synchronous_standby_names` for zero-loss within 12ms.
  - **Redis:** Sentinel with cross-site replication or Redis Enterprise multi-site.
  - **RabbitMQ:** Mirror queues or federation with `ha-mode: all`.
  - **MinIO:** Site replication (async, eventual consistency). 200TB sync takes time; accept RPO ~15m with replication lag monitoring.
- **Recommendation:** Active-active with Istio/Cilium + async replication. Monitor lag; if >15m, throttle writes or switch to active-passive for critical stateful workloads.
