AA1 — Monoliths consist of a single codebase and database, deployed as one unit. Microservices decompose the application into independent services with their own data stores. Three concrete problems microservices introduce: 1) Distributed transaction complexity (no ACID across services), 2) Network latency and failure points (inter-service communication), 3) Operational overhead (deploying, monitoring, and debugging many services vs one).

AA2 — Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST, gRPC). Asynchronous communication involves fire-and-forget or callback patterns where the caller does not wait (e.g., Message Queues like RabbitMQ, Event Bus like Kafka).

AA3 — An API Gateway handles business logic (auth, rate limiting, aggregation), while a reverse proxy handles traffic routing and SSL termination. An API Gateway cannot replace a reverse proxy entirely because reverse proxies often handle Layer 4 (TCP/UDP) routing and load balancing at a lower level than the application logic handled by a gateway.

AA4 — The Saga pattern manages long-running transactions across services by breaking them into local transactions. Choreography-based sagas rely on services publishing events that other services react to (decoupled but hard to debug). Orchestration-based sagas use a central coordinator to tell services what to do (easier to manage but introduces a single point of failure). Choreography is appropriate for loosely coupled systems; orchestration for tightly coupled or complex workflows.

AA5 — CQRS separates read and write operations into different models. It is paired with Event Sourcing, which stores state as a sequence of events. This combination solves the problem of read/write performance mismatch and complex query requirements that a traditional CRUD model cannot handle efficiently (e.g., optimizing read queries without impacting write performance).

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. The three states are Closed (normal), Open (failures detected, calls blocked), and Half-Open (testing if service recovered). It differs from simple retry because it stops retrying when failure is persistent. You use both together: retry for transient errors, but trip the circuit breaker if failures persist.

AA7 — 1. Shared DB/Schema: Lowest cost, highest noisy-neighbor risk, lowest security (row-level isolation). 2. Shared DB/Separate Schema: Medium cost, better isolation, harder to manage migrations. 3. Separate DB per tenant: Highest cost, best security/performance, highest operational complexity. For high-security SaaS, Option 3 is preferred; for cost-sensitive, Option 1.

AA8 — Strong consistency guarantees immediate visibility of updates; eventual consistency allows temporary divergence. For an inventory system that must never oversell, strong consistency is required. At scale, use a distributed database with strong consistency guarantees (e.g., CockroachDB, DynamoDB with strong reads) or implement a centralized locking mechanism (e.g., Redis with Lua scripts) to coordinate writes across services.

AA9 — A sidecar proxy is a lightweight process running alongside a service to handle networking. In Istio, Envoy is the sidecar (data plane) handling traffic, while Istiod is the control plane managing configuration. mTLS between sidecars solves service-to-service authentication without requiring application-level TLS changes, simplifying certificate management and enforcing security policies automatically.

AA10 — The Strangler Fig pattern involves incrementally migrating functionality from a legacy system to a new one. For a .NET Framework monolith to .NET 8: Identify a module, extract it as a microservice, wrap it in an API, route traffic to the new service, and gradually retire the old code until the monolith is fully replaced.

AA11 — The 12-Factor App methodology defines best practices for cloud-native apps. Six factors: 1) Codebase (versioned), 2) Dependencies (explicit), 3) Config (environment variables), 4) Services (treat as resources), 5) Build/Release/Run (separation), 6) Processes (stateless). They matter for portability, scalability, and security in cloud environments.

AA12 — Event-driven (Kafka) offers high scalability and decoupling but has higher debugging complexity and eventual consistency. Request-driven (REST/gRPC) offers synchronous guarantees and easier debugging but tighter coupling. Choose Event-driven for pipelines and high throughput; Request-driven for user-facing APIs requiring immediate responses.

AA13 — A load balancer distributes incoming traffic across servers. Layer 4 (TCP/UDP) balances based on IP/Port. Layer 7 (HTTP/HTTPS) balances based on content (URL, headers). Layer 7 is required when routing traffic based on specific paths (e.g., `/api` vs `/static`) or SSL termination.

AA14 — A message queue (RabbitMQ) supports point-to-point and pub/sub with guaranteed delivery. A log-based broker (Kafka) is append-only, high-throughput, and supports replay. Pick RabbitMQ for task queues where message delivery is critical; pick Kafka for event streaming and analytics where replayability and throughput are key.

AA15 — A container packages code and dependencies with a lightweight OS layer (shared kernel). A VM includes a full guest OS. Containers are popular for microservices because they are lightweight, start faster, and allow higher density on the same hardware compared to VMs.

AA16 — Stateless services do not store data in memory (e.g., web servers), making them easy to scale horizontally by adding more instances. Stateful services store data (e.g., databases, caches) and are harder to scale. Stateless example: API Gateway; Stateful example: PostgreSQL.

AA17 — An ORM maps database tables to object classes. Examples: Entity Framework (.NET), Hibernate (Java). Trade-offs: ORMs simplify development but can lead to performance issues (N+1 queries) and reduced flexibility compared to raw SQL for complex queries.

AA18 — The Bulkhead pattern isolates resources (threads, CPU, memory) to prevent a failure in one part of the system from affecting others. Example: Implement separate thread pools for database connections and HTTP client calls. If the HTTP pool is exhausted, the DB pool remains available.

AA19 — Operational Transformation (OT) transforms operations to maintain consistency (e.g., Google Docs). CRDTs use mathematical data types to converge without server intervention. CRDTs are better for offline editing because they allow local merges without immediate server synchronization, whereas OT requires a central server to resolve conflicts.

AA20 — Distributed tracing requires propagating context (TraceID/ParentID) via headers (W3C Trace Context). Sampling reduces storage load (head-based vs tail-based). Storage uses tools like Jaeger or Tempo. For async messaging (Kafka), ensure trace headers are passed from producer to consumer headers to maintain continuity across the message boundary.

OP1 — Type 1 (Bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) run on top of an OS (e.g., VMware Workstation, VirtualBox). Type 1 is used for production servers; Type 2 for development.

OP2 — SAN (Storage Area Network) provides block storage (e.g., iSCSI, Fibre Channel) for high-performance databases. NAS (Network Attached Storage) provides file storage (e.g., NFS, SMB) for general file sharing. Use SAN for DBs requiring low latency; NAS for file servers.

OP3 — A 3-tier architecture has Core, Distribution, and Access layers. Leaf-Spine is preferred in modern data centers because it provides a flat topology with equal latency between any two leaf switches, solving the latency and scalability bottlenecks of hierarchical 3-tier designs.

OP4 — A Proxmox HA cluster needs an odd number of nodes (e.g., 3) for quorum. Use Ceph for shared storage to avoid single points of failure. Implement STONITH (fencing) to prevent split-brain. If a node fails, the cluster detects the loss of quorum/fencing and fails over the resources to the remaining nodes.

OP5 — VLAN trunking allows multiple VLANs over a single link using 802.1Q tags. On Linux with a single NIC, create virtual interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`, `ip link add link eth0 name eth0.20 type vlan id 20`, etc.

OP6 — RAID 1 (Mirror), 5 (Striping+Parity), 6 (Double Parity), 10 (Stripe+Mirror), Z2 (ZFS Mirror+Parity). For 6 drives balancing performance and fault tolerance for a DB: RAID 10 offers best performance but lower capacity. ZFS RAID-Z2 offers better capacity efficiency with similar fault tolerance. Z2 is often preferred for modern drives.

OP7 — DNS architecture uses Recursive resolvers (ISP), Authoritative servers (AD), and Forwarders. Split-horizon DNS directs internal vs external queries. DNSSEC signs zones. When a laptop moves, DHCP updates the DNS suffix or the split-horizon logic routes the query to the correct zone based on the client's IP or domain.

OP8 — PKI chain: Root CA (offline) -> Subordinate CA -> End Entity. CRL (Certificate Revocation List) is a list of revoked certs; OCSP checks status in real-time. Compromised Subordinate CA: revoke certs issued by that subordinate. Compromised Root CA: revoke all certs in the hierarchy, causing massive disruption.

OP9 — MPLS is expensive and reliable. IPsec is cheap but relies on public internet. SD-WAN balances cost and performance with dynamic routing. WireGuard is simple mesh. For 50 users per site with latency-sensitive VoIP, SD-WAN is recommended for its QoS capabilities and cost-effectiveness compared to MPLS.

OP10 — iDRAC/iLO/IPMI are out-of-band management interfaces (BMC). Critical for remote reboot/console access when OS is unresponsive. Exposing IPMI to the internet is a severe security risk (brute force attacks, unauthorized hardware access).

OP11 — LVM manages block devices; LVM-Thin provides space efficiency (thin provisioning). ZFS is a file system with built-in compression and snapshots. LVM-Thin snapshots are fast (copy-on-write pointers). ZFS snapshots are also fast and include data integrity checks. Use ZFS for file storage; LVM for block storage.

OP12 — A stretch cluster spans two sites. 2-site Ceph is risky because a network partition can cause a split-brain (quorum loss). Without a tiebreaker (3rd site), the cluster may stop writing. CRUSH rules ensure data placement across sites. Generally, avoid 2-site Ceph without a tiebreaker mechanism.

OP13 — DHCP DORA: Discover, Offer, Request, Ack. If the server is unavailable, the client uses APIPA (169.254.x.x). If a lease expires and the server is unavailable, the client cannot renew and loses network connectivity.

OP14 — Managed switches allow VLANs, QoS, and ACLs. Unmanaged switches are plug-and-play. Managed switches are required in enterprises for traffic segmentation, security, and prioritizing critical traffic (VoIP).

OP15 — NTP synchronizes system clocks. Accurate time is critical for authentication (Kerberos), log correlation, and cluster consensus. Clock drift can cause authentication failures, incorrect log analysis, and split-brain in distributed systems.

OP16 — Physical servers are bare metal. VMs run a guest OS. Containers share the host OS. Run workloads on bare metal for maximum performance and lowest latency (e.g., high-frequency trading, specific DB requirements) where virtualization overhead is unacceptable.

OP17 — UPS provides immediate backup power (minutes) during outages. Generators provide long-term power (hours/days). ATS (Automatic Transfer Switch) switches the load from grid to generator automatically. You need both to bridge the gap until the generator starts.

OP18 — Active-Passive has one active node; Active-Active has both active. For PostgreSQL HA with Pacemaker/Corosync: Configure shared resources (Virtual IP). Use STONITH (fencing) to ensure only one node holds the resource. On failure, the cluster moves the VIP to the healthy node.

OP19 — Backup strategy follows 3-2-1 rule (3 copies, 2 media types, 1 offsite). RPO (max data loss) and RTO (max downtime) define requirements. Use Full/Incremental/Differential backups. Immutable backups prevent ransomware encryption. Backup is data copy; DR is system recovery (restoring services).

OP20 — 802.1X uses Supplicant (client), Authenticator (switch), and Authentication Server (RADIUS). EAP-TLS uses certificates; PEAP uses passwords. Failed auth blocks the port. MAB (MAC Authentication Bypass) allows devices without supplicants (printers) to authenticate based on their MAC address.
