**G1**
In Go, an **array** is a fixed-size, value type (e.g., `[3]int`), while a **slice** is a reference type (a descriptor pointing to an underlying array with length and capacity). When appending to a slice that has reached its capacity, Go allocates a new underlying array (typically 1.25x the old capacity), copies the old data, and updates the slice header to point to the new array.

**G2**
`var x int` declares a variable `x` of type `int` and initializes it to the zero value (0). `x := 0` is a short declaration that initializes `x` to 0. You **cannot** use `:=` in package-level scope (outside functions) or if the left-hand side is already declared. `:=` is only allowed within functions for new variables.

**G3**
A **goroutine** is a lightweight thread of execution managed by the Go runtime. It differs from an OS thread in that it is much smaller (stack grows dynamically) and the runtime multiplexes thousands of goroutines onto a smaller pool of OS threads. The **GMP model** (Goroutine, Machine, Processor) manages this: Gs are the tasks, Ms are OS threads, and Ps are schedulers that assign Gs to Ms.

**G4**
Channels allow goroutines to communicate. An **unbuffered channel** blocks the sender until a receiver is ready. A **buffered channel** holds up to `N` values; sending blocks only if the buffer is full. If you send to a full buffered channel, the sender blocks until a receiver removes a value.

**G5**
The `context` package manages request-scoped values (cancelation, deadlines, values).
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
// Use ctx in HTTP request: http.Get(ctx, url)
```
This ensures the request is canceled if it exceeds the timeout.

**G6**
Go interfaces are **implicit**; a type satisfies an interface if it implements the required methods. Java/C# require explicit implementation. `interface{}` (or `any`) is the empty interface, requiring no methods. It is powerful for generic-like behavior but dangerous because it disables compile-time type safety, leading to runtime panics on type assertions.

**G7**
This code is unsafe due to a **data race**. `ready` and `data` are not atomic or protected by synchronization. The compiler may reorder writes, or the main goroutine may read `data` before the worker writes it. Correct alternatives: use a channel (`done <- true`), `sync.WaitGroup`, or `sync/atomic` for simple flags.

**G8**
`sync.Mutex` allows only one writer. `sync.RWMutex` allows multiple concurrent readers but exclusive writers. `sync.Map` is optimized for concurrent read-heavy workloads with sparse keys (uses a hash table with sharded locks). A regular map with a mutex is better for dense data or when you need complex logic (e.g., nested maps) that `sync.Map` cannot handle efficiently.

**G9**
Go modules manage dependencies. `go.mod` declares the module path and dependencies. `go.sum` stores checksums for security. `go mod tidy` cleans up unused dependencies and ensures versions match `go.mod`. The **Minimum Version Selection (MVS)** algorithm picks the lowest version of a dependency that satisfies all constraints to maximize compatibility.

**G10**
`defer` schedules a function call to run when the surrounding function returns. Multiple defers execute in **LIFO** (Last-In, First-Out) order. A common gotcha is capturing loop variables: `defer fmt.Println(i)` inside a loop prints the final value of `i` for all defers, not the value at the time of the loop iteration.

**G11**
A pointer is a variable that holds the memory address of another variable. The zero value is `nil`. To create a pointer to a struct literal: `var p *MyStruct = &MyStruct{Field: "value"}`.

**G12**
`init()` runs automatically before `main()`. A package can have multiple `init()` functions (e.g., in different files). They execute in alphabetical order of the file names.

**G13**
`make` allocates and initializes slices, maps, and channels (e.g., `make(map[string]int)`). `new` allocates a zero value on the heap and returns a pointer (e.g., `new(int)` returns `*int`). `make` is required for slices/maps/channels; `new` works for any type.

**G14**
Go uses an `error` interface (`type error interface { Error() string }`). The idiomatic check is `if err != nil`. `errors.Is` checks if an error wraps a specific target error (using `errors.Unwrap`). `errors.As` type-asserts an error to a specific type, handling wrapping. `==` only checks identity, not wrapping.

**G15**
Composite types: `map[K]V` (zero: `nil`), `[]T` (slice) (zero: `nil`), `chan T` (zero: `nil`), `struct` (zero: fields set to their zero values).

**G16**
A race condition occurs when two goroutines access shared memory concurrently without synchronization. The `-race` flag enables the Thread Sanitizer to detect this.
*Race:*
```go
var x int
go func() { x = 1 }()
go func() { x = 2 }()
```
*Fix:* Use `sync.Mutex` to lock access to `x` or use a channel to coordinate updates.

**G17**
`select` chooses a case based on channel readiness. It differs from `switch` by handling channel operations. If multiple cases are ready, one is chosen randomly. To implement a timeout, use `select` with a `time.After` case alongside the channel operations.

**G18**
Escape analysis determines if a variable lives on the stack or heap. If a variable is used outside the current function (e.g., stored in a global or returned), it escapes to the heap. You can inspect this with `go build -gcflags="-m"`. It matters because heap allocation incurs GC overhead; keeping variables on the stack improves performance.

**G19**
The `reflect` package allows runtime introspection. `reflect.Type` describes a type; `reflect.Value` holds the value. Reflection is slow (dynamic dispatch). It is justified for configuration, serialization, or generic-like behavior where generics aren't available, but should be avoided in performance-critical paths.

**G20**
`go:embed` embeds files at compile time. It supports single files (`//go:embed "file.txt"`), directories (`//go:embed "dir/*"`), and file systems (`//go:embed "fs:dir"`). It requires Go 1.16+. It interacts with `io/fs.FS` to provide the embedded content as a virtual filesystem.

**R1**
Ownership means each value has a single owner responsible for its memory. The three rules: 1. Each value has one owner. 2. When the owner goes out of scope, the value is dropped. 3. When a value is assigned or passed, ownership is transferred (moved).

**R2**
`String` is an owned, heap-allocated UTF-8 string. `&str` is a borrowed slice of UTF-8 bytes. Use `String` when you need to own the data (e.g., return value). Use `&str` for function arguments to avoid unnecessary copies.

**R3**
Borrowing allows accessing data without ownership. Immutable references (`&T`) allow reading. Mutable references (`&mut T`) allow writing. Rules: 1. Only one mutable reference at a time. 2. No mutable and immutable references simultaneously. 3. References must not outlive the data they point to.

**R4**
`Result<T, E>` holds `Ok(T)` or `Err(E)`. `Option<T>` holds `Some(T)` or `None`. The `?` operator propagates errors (returns early on `Err`).
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)?
}
```

**R5**
`Box<T>` is a heap-allocated pointer (single owner). `Rc<T>` is a reference-counted pointer (single thread). `Arc<T>` is an atomic reference-counted pointer (multiple threads). Use `Box` for tree structures, `Rc` for single-threaded shared ownership, `Arc` for multi-threaded shared ownership.

**R6**
Traits define behavior. Go interfaces are implicit; Rust traits are explicit. `dyn Trait` (trait objects) use vtables for dynamic dispatch (like Go interfaces). Generics with trait bounds (`T: Trait`) use monomorphization (static dispatch), which is faster and more type-safe than trait objects.

**R7**
This fails because the compiler cannot guarantee that `x` or `y` live long enough to return a reference to them. Fix: Add a lifetime annotation `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str` or return an owned `String`.

**R8**
`Send` means a type can be sent across threads. `Sync` means it can be shared between threads. `Rc<T>` is not `Send` because its reference count is not atomic. `Arc<T>` is `Send` and `Sync` because it uses atomic operations for reference counting.

**R9**
Rust's async/await compiles to state machines (Futures). A `Future` is a type that can be polled for completion. An executor (like Tokio) drives these Futures. Unlike Go's M:N scheduler, Rust's async is cooperative and relies on the executor to yield control, avoiding OS thread overhead but requiring manual task scheduling.

**R10**
`unsafe` blocks allow bypassing safety checks. 3 things: 1. Dereferate raw pointers. 2. Call FFI functions. 3. Inline assembly. It is justified for FFI, low-level memory manipulation, or when the compiler cannot optimize a safe abstraction.

**R11**
Pattern matching uses `match` to exhaustively match a value against patterns. `if let` is a shorthand for a single match arm. The compiler enforces exhaustiveness: all cases must be covered (e.g., `Option` must handle `Some` and `None`).

**R12**
`Vec<T>` is a growable heap array. `[T; N]` is a fixed-size stack array. When a `Vec` pushes beyond capacity, it allocates a larger buffer (usually 1.5x or 2x) and copies elements. Arrays have fixed capacity and no reallocation.

**R13**
Rust enums are tagged unions (data + tag). C/Java enums are typically just integer constants. `Option<T>` is an enum with `Some(T)` and `None`. Rust has no null; `Option<T>` replaces null to prevent null pointer dereferences.

**R14**
`impl` defines methods for a type. `&self` borrows the instance (read). `&mut self` borrows mutably (write). `self` consumes the instance (move). Associated functions (e.g., `String::new`) take `&Self` or no self and are called on the type itself.

**R15**
`derive` generates implementations automatically. Common traits: `Debug`, `Clone`, `PartialEq`, `Serialize`. You cannot derive if the struct contains types that don't implement the trait (e.g., `Clone` on a struct with a non-Clone field) or if the struct has private fields (for `Clone`/`PartialEq` in some contexts).

**R16**
`Cow<'a, T>` (Clone on Write) holds a reference if the data is immutable, but clones it if it needs to be mutated. It avoids allocation when the data is read-only. Example: `Cow::Borrowed("literal")` vs `Cow::Owned("owned".to_string())`.

**R17**
`mod` declares a module. `use` imports items. `pub` makes items public. The file system maps to modules (e.g., `src/lib.rs` is the root). Rust 2018 edition changed path resolution to be more explicit (e.g., `mod foo` in `src/lib.rs` looks for `src/foo.rs` or `src/foo/mod.rs`).

**R18**
`Pin<P>` prevents a type from being moved in memory. It is needed for self-referential structs (pointers to self) and async tasks (Futures) which rely on stable memory addresses. `Unpin` is a marker trait that allows a `Pin` to be moved.

**R19**
Declarative macros (`macro_rules!`) are text substitution. Procedural macros (derive, attribute, function-like) are Rust functions that generate code. Hygiene rules ensure macros don't accidentally capture variables from the caller's scope (e.g., `!` in `macro_rules!` is distinct from `!` in code).

**R20**
Zero-cost abstractions mean high-level code compiles to code as efficient as hand-written C. Iterators avoid heap allocation by using stack-based state. Generics use monomorphization (code generation per type). Traits use static dispatch (resolved at compile time), avoiding vtable overhead.
