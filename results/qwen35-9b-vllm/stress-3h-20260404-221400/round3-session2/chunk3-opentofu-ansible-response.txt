T1 — Easy: `tofu plan` calculates the execution plan and shows what changes would be made without applying them. `tofu apply` executes the plan and makes the actual changes to the infrastructure.

T2 — Easy: State is a JSON file that tracks the real-world resources managed by OpenTofu. Remote state is important for team collaboration (multiple users), safety (state locking), and portability (CI/CD pipelines).

T3 — Medium: `count` uses an index (0, 1, 2...) and creates resources in a list. `for_each` uses a map/set key and creates resources with unique identifiers. `for_each` is preferred when resource names matter (e.g., `aws_instance.web1`) or when you need to iterate over a collection of unique items.

T4 — Medium: OpenTofu detects this as "Drift" during `tofu plan`. It compares the state file against the actual cloud resources. It handles it by proposing a plan to update the state to match the cloud (or ignoring changes if configured).

T5 — Medium:
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-12345678"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

T6 — Hard: `terraform_remote_state` reads the *state file* of another project, coupling the project to the lifecycle of the other. Output values read *computed values* from another project. The recommended alternative is to use a shared module or a dedicated data source that computes the value, avoiding state dependency to prevent coupling and accidental data loss if the source project is destroyed.

T7 — Hard: The `remote-exec` provisioner runs during resource creation. If the dependent resource tries to read the output immediately, the provisioner hasn't finished writing the kubeconfig yet. Fix: Use `local-exec` to write the kubeconfig to a file, then use a `file` data source or `template` resource in the dependent module to read the file content.

T8 — Medium: `tofu import` maps an existing cloud resource to the OpenTofu state. Limitations: Schema mismatches or missing attributes can cause import to fail. The `import` block (1.5+) allows declarative import configuration, making it easier to manage multiple imports and handle attributes without CLI flags.

T9 — Easy: A variable is an input value provided by the user or environment. An input variable is defined in a `variable` block and passed in. An output variable is defined in an `output` block and computed by the module.

T10 — Easy: A provider is a plugin that interacts with a cloud API. If you run `tofu plan` without `tofu init`, OpenTofu cannot download the provider binaries, and the plan will fail.

T11 — Easy: `.terraform.lock.hcl` locks provider versions to ensure consistency across environments. It should be committed to version control to prevent "dependency drift" where different environments use different provider versions.

T12 — Easy: `tofu destroy` removes all resources defined in the state. Use `tofu destroy -target=resource_type.name` to target a single resource.

T13 — Easy: A data source reads existing resources (e.g., `aws_ami`). Use it when the resource exists but is not managed by OpenTofu, or when you need to reference an external resource (e.g., an existing VPC ID).

T14 — Medium: `locals` are computed values within a module (derived from variables). `variables` are inputs. Use `locals` for derived values (e.g., `var.env == "prod" ? "production" : "dev"`) to avoid repeating logic or passing complex values as inputs.

T15 — Medium: `lifecycle` block controls resource behavior. `create_before_destroy` ensures zero downtime during updates (use for load balancers). `prevent_destroy` protects resources from accidental deletion (use for DBs). `ignore_changes` prevents drift on specific attributes (use for immutable tags).

T16 — Medium: A `moved` block tells OpenTofu that a resource has been renamed or moved to a new path. It helps by updating the state reference without destroying and recreating the resource, preserving the resource ID.

T17 — Hard: The dependency graph orders tasks based on references. Implicit dependencies are inferred from resource references (e.g., `aws_instance` referencing `aws_vpc`). Explicit dependencies use `depends_on`. `depends_on` forces order and reduces parallelism; use sparingly because it can break the graph if the dependency is not actually needed.

T18 — Hard: Strategies: 1. `tofu plan -refresh=false` (skip cloud API calls). 2. `tofu plan -target` (plan specific resources). 3. Split state (multiple workspaces or state files). 4. Remove unused resources (`tofu state rm`). Tradeoffs: `refresh=false` risks missing drift; `target` requires manual selection; splitting state increases complexity.

T19 — Hard: OpenTofu uses a backend (e.g., S3) to lock state. If a lock is not released (crash), the state is locked. Manual break: Delete the lock file in the backend (e.g., DynamoDB item or S3 lock file). Risk: Concurrent state corruption if another process tries to apply simultaneously.

T20 — Hard: 1. `tofu state pull` (backup local state). 2. Update `backend` block in config. 3. `tofu init` (re-initialize with new backend). 4. `tofu state push` (upload state to new backend). 5. Verify with `tofu state list`.
