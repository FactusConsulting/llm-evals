K1 — Easy: What is the difference between a Deployment and a StatefulSet?
A Deployment manages stateless applications. Pods are interchangeable, and updates happen in parallel without guaranteed ordering. A StatefulSet manages stateful applications. Pods have stable, unique network identities (hostname), stable storage (persistent volumes), and ordered deployment/termination.

K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?
The Service creates a virtual IP (ClusterIP) within the cluster. kube-proxy (running on nodes) creates iptables or IPVS rules that DNAT traffic destined for the Service IP to the IP of the backend pods listed in the Service's Endpoints.

K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?
A PersistentVolume (PV) is a piece of storage provisioned by the admin (or dynamically). A PersistentVolumeClaim (PVC) is a request for storage resources made by a user. A StorageClass defines the provisioner and parameters for dynamically creating PVs. Relationship: StorageClass -> creates PV -> PVC binds to PV -> Pod mounts PV.

K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).
1. Check container logs (`kubectl logs <pod>`) for application errors.
2. Check container health probes (`kubectl describe pod`) to see if liveness/readiness is failing.
3. Check for OOMKilled events in events/logs indicating memory limits exceeded.
4. Verify image pull errors or missing ConfigMap/Secret references.

K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?
CoreDNS provides DNS resolution for services, pods, and nodes within the cluster. If CoreDNS pods are down, internal service discovery fails (pods cannot reach services by name), and external access to cluster services via DNS breaks.

K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.
The scheduler first **filters** nodes that satisfy hard constraints (taints/tolerations, node selectors, resource availability). Then it **scores** the remaining nodes to pick the best fit. Factors include: Node affinity/anti-affinity, resource utilization (CPU/Memory), and topology spread constraints.

K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?
The node has 0.5GB (512Mi) free. The pod requests 256Mi, which is less than 512Mi, so it **will be scheduled**. If the runtime usage exceeds the limit (600Mi > 512Mi), the kubelet will **OOMKill** the container.

K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.
1. Client request hits **External LB** (e.g., AWS ALB).
2. LB routes to **Ingress Controller** (NGINX Pod).
3. NGINX matches rules and forwards to the backend **Service** (ClusterIP).
4. Service resolves to **Endpoints** (Pod IPs).
5. **kube-proxy** on the node intercepts traffic via iptables rules and DNATs to the specific **Pod**.
6. Pod receives request and processes it.

K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?
A NetworkPolicy controls ingress/egress traffic to/from pods. By default, **all traffic is allowed**. When a policy is applied, it restricts traffic to/from the selected pods based on rules (ports, namespaces, pod selectors).

K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?
RollingUpdate updates pods gradually (old -> new) with no downtime. Recreate kills all old pods before starting new ones (downtime). Choose Recreate for stateful applications (e.g., databases) where concurrent access during updates is unsafe.

K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?
A namespace is a logical partition for resources. Default namespaces are: `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.
It shows detailed status and metadata. 3 examples: **Events** (restart reasons), **Conditions** (Ready, Running), and **Container details** (image, restart count, resource limits).

K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.
A ConfigMap stores non-confidential configuration data as key-value pairs. Methods: 1. Inject as **Environment Variables**. 2. Mount as a **Volume** (files or directories).

K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?
ClusterIP: Internal cluster access only. NodePort: Exposes service on a static port on every node. LoadBalancer: Provisions an external cloud load balancer to expose the service externally.

K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?
A DaemonSet ensures a copy of a Pod runs on all (or a subset of) nodes. Use it for node-level tasks like logging agents (Fluentd), monitoring (Prometheus Node Exporter), or network plugins (Calico).

K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?
Taints prevent scheduling of regular pods; tolerations allow specific pods to ignore taints. Node affinity is a positive match (pod wants specific node labels). Use case: Taints for GPU nodes (prevent CPU pods); Affinity for placing DBs on specific hardware.

K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?
An Operator is a custom controller that manages the lifecycle of a specific application type. Standard controllers manage generic resources (Pods, Deployments). Operators solve complex stateful problems (backups, upgrades, scaling) that standard controllers cannot handle.

K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?
etcd uses Raft consensus (strong consistency). If quorum is lost (e.g., 2/3 nodes down), the cluster becomes **unavailable**. Recovery: You cannot recover data from the lost nodes. You must restore etcd from a backup or rejoin a new node to form a new quorum (requires data backup).

K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.
Role = permissions in a namespace. ClusterRole = permissions cluster-wide. Binding links Role/ClusterRole to a User/Group.
Manifests:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.
High `ndots` value causes the resolver to try resolving the domain as a single label first before splitting, causing multiple queries for external domains. Fix: Set `ndots: 1` (or lower) in `dnsConfig` under `spec.dnsConfig` in the Pod spec.

D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?
Rebase rewrites history to make it linear; Merge preserves history with a merge commit. Avoid rebasing on public/shared branches or commits that others have based their work on.

D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.
TCP is reliable, ordered, connection-oriented. UDP is unreliable, fast, connectionless. TCP: HTTP, SSH. UDP: DNS, VoIP.

D3 — Medium: What is a race condition? Give a concrete example in any language.
A race condition occurs when the outcome depends on the timing of concurrent events. Example: Two threads incrementing a shared counter `count++` without locks; one thread reads, increments, writes while another does the same, resulting in lost updates.

D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?
Symmetric uses one key for encryption/decryption (fast). Asymmetric uses public/private key pairs (secure key exchange). TLS uses Asymmetric to exchange a session key, then Symmetric to encrypt the actual data transfer.

D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?
Layers are read-only filesystem stacks. Caching speeds up builds if layers don't change. Best practice: Combine `RUN` commands to reduce layers and place `COPY`/`ADD` of changing files at the end of the Dockerfile.

D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.
1. Check application logs for errors.
2. Check health check endpoints (liveness/readiness).
3. Check upstream dependencies (database connectivity).
4. Check infrastructure resources (CPU/Memory saturation).

D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.
CAP theorem: A distributed system can only guarantee 2 of 3: Consistency, Availability, Partition Tolerance. CP: ZooKeeper (strong consistency). AP: Cassandra/DynamoDB (eventual consistency).

D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?
Horizontal adds more instances; Vertical adds more resources to existing instances. Horizontal scaling requires stateless applications and a load balancer.

D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?
An environment variable is a dynamic name-value pair. To persist across sessions, add `export VAR=value` to `~/.bashrc` or `~/.profile`.

D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.
JSON is strict, machine-readable text. YAML is human-readable, indentation-based. Advantage JSON: Strict validation. Advantage YAML: Readability.

D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.
REST is a stateless architectural style using HTTP. GET: Retrieve data. POST: Create data. PUT: Replace/Update data. DELETE: Remove data.

D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?
Version pinning locks specific versions of dependencies. It ensures builds are reproducible and prevents unexpected breaking changes from upstream updates.

D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.
Compiled languages translate source to binary before execution (faster). Interpreted languages translate source to machine code at runtime (slower). Compiled: C, Go. Interpreted: Python, Ruby.

D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.
Reverse proxy sits between client and server (terminates SSL, load balances). Forward proxy sits between client and internet (hides client identity). Reverse: Nginx (web server). Forward: Squid (user access).

D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?
Deadlock is when threads wait for each other indefinitely. Conditions: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait.

D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?
Eventually consistent means data converges over time without immediate consistency. Cassandra uses tunable consistency levels: ONE (1 node), QUORUM (majority), ALL (all nodes).

D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?
mTLS requires both client and server to present certificates. Handshake: Client sends cert -> Server verifies -> Server sends cert -> Client verifies. Used in Service Meshes (Istio) and secure internal APIs.

D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?
Hash table uses an array and hash function. Chaining: Linked lists at indices. Open Addressing: Probing for empty slots. Average: O(1). Worst: O(n) (all collisions).

D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?
Circuit breaker stops calls to failing services. Closed: Normal. Open: Fail fast (no calls). Half-Open: Test calls. Prevents cascade by stopping load. Retry policies use exponential backoff to retry in Half-Open state.

D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).
Optimistic: Check version on commit (no locks). Pessimistic: Lock rows immediately. Choose Optimistic for high read/low write. Choose Pessimistic for critical writes. Example: Optimistic uses `version` column; Pessimistic uses `SELECT ... FOR UPDATE`.
