## Application Architecture

AA1 — **Monolith vs. Microservices:** A monolith is a single unified unit where the entire application logic resides in one codebase and shares resources. Microservices break this into small, independent services that communicate over a network.
**3 Problems introduced by microservices:**
1.  **Distributed System Complexity:** Managing partial failures, network latency, and distributed transactions.
2.  **Data Consistency:** Maintaining consistency across multiple isolated databases (lack of ACID across boundaries).
3.  **Operational Overhead:** Increased complexity in monitoring, deployment pipelines, and service discovery.

AA2 — **Synchronous vs. Asynchronous:** Synchronous communication requires the requester to wait for a response before proceeding (e.g., REST/HTTP). Asynchronous communication allows the requester to continue immediately after sending a message; the response is handled later or via a callback (e.g., RabbitMQ/Kafka).
*   **Sync Example:** REST API call.
*   **Async Example:** Message Queue (RabbitMQ) publication.

AA3 — **API Gateway vs. Reverse Proxy:** A reverse proxy sits in front of a server to forward requests (basic load balancing/SSL termination). An API Gateway adds application-layer features like authentication, rate limiting, request transformation, and protocol translation. 
**Can it replace a reverse proxy?** Yes, an API Gateway performs all functions of a reverse proxy plus more. However, you wouldn't use a full API Gateway if you only need simple load balancing because the gateway introduces unnecessary overhead.

AA4 — **Saga Pattern:** Manages distributed transactions by executing a sequence of local transactions. Each local transaction updates its own database and publishes an event to trigger the next step.
*   **Choreography:** Services exchange events without a central coordinator (decentralized). Best for simple workflows with few services.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows where visibility into the state of the entire process is required.

AA5 — **CQRS & Event Sourcing:** CQRS separates Read models from Write models. It is paired with Event Sourcing because Event Sourcing stores every change as a sequence of immutable events. This combination solves the problem of high contention on a single database schema; it allows scaling reads independently of writes and provides a perfect audit log for reconstructing state at any point in time.

AA6 — **Circuit Breaker:** Prevents a failing service from causing cascading failures by "tripping" after a threshold of errors. 
**States:** Closed (normal), Open (requests fail fast/don't hit backend), Half-Open (testing if the backend has recovered).
**Difference:** Retry with backoff handles transient network blips; Circuit Breakers handle systemic outages or slow responses that would otherwise exhaust thread pools. You use both together: retry for minor hiccups, circuit breaker for major system failure.

AA7 — **Multi-tenant Isolation Models:**
1.  **Shared DB, Shared Schema:** Lowest cost, highest risk of noisy neighbor/data leakage. High operational simplicity but hard to scale horizontally per tenant.
2.  **Shared DB, Separate Schema:** Good balance. Provides logical isolation while sharing resources. Easier to manage than separate DBs but still shares some hardware limits.
3.  **Separate DB per Tenant:** Highest security and strongest isolation. Noisy neighbor is minimized because each tenant has its own resource pool. Very high operational complexity and cost as you scale.

AA8 — **Consistency Models:** Strong consistency ensures all reads see the latest write immediately. Eventual consistency allows temporary divergence where data will eventually sync.
**Inventory System Architecture:** To never oversell, I would use **Strong Consistency**. I would choose a distributed SQL database (e.g., CockroachDB) or an RDBMS with strict ACID properties. At scale, I'd implement a "Reservation" pattern using a distributed lock or a transaction on a specific row representing inventory count before confirming the order.

AA9 — **Service Mesh & Envoy:** A sidecar proxy runs alongside every service instance to intercept all inbound/outbound traffic. 
*   **Envoy:** Handles load balancing, health checks, and telemetry.
*   **Data Plane:** The actual proxies handling the packets.
*   **Control Plane:** Manages configuration for the proxies (e.g., Istio).
*   **mTLS Benefit:** It provides identity-based authentication between services automatically without changing application code; it ensures that even if a network segment is breached, only authorized services can talk to each other.

AA10 — **Strangler Fig Pattern:** You wrap the legacy monolith in a facade (API Gateway). New features are built as microservices. Slowly, you migrate existing functionality by routing specific endpoints from the old system to new services until the old system has no remaining logic left and can be decommissioned.

AA11 — **12-Factor App Methodology:** Key factors include: Codebase, Dependencies, Config, Backing Services, Build, Runshots, Port binding, Concurrency, Disposability, Dev/Prod Parity, Statelessness, and Logs. These matter because they ensure applications are portable, scalable, and easily managed in containerized environments like Kubernetes or AWS.

AA12 — **Event-driven vs. Request-driven:**
*   **Coupling:** Event-driven is loosely coupled (producer doesn't know consumer); Request-driven is more tightly coupled.
*   **Scalability:** Event-driven scales better for high-throughput spikes via buffering.
*   **Debugging:** Request-driven is easier to trace linearly; Event-driven requires distributed tracing tools.
*   **Ordering:** Kafka provides strict ordering per partition; REST guarantees order of execution on one thread.
*   **Choice:** Use Request-driven for user-facing actions (UI feedback); use Event-driven for background processing (emails, analytics).

AA13 — **Load Balancer:** Distributes incoming traffic across multiple servers. 
*   **Layer 4:** Operates at the Transport layer (TCP/UDP), looking only at IP/Port. Faster but less "intelligent."
*   **Layer 7:** Operates at the Application layer (HTTP/HTTPS). It can route based on URL paths, cookies, or headers.
*   **L7 Requirement:** Required when you need to route `example.com/api` to Service A and `example.com/web` to Service B.

AA14 — **Message Queue vs. Log Broker:**
*   **MQ (RabbitMQ):** Messages are deleted once consumed by a worker. Good for complex routing logic (headers, exchanges) and task queues.
*   **Log Broker (Kafka):** Messages stay in an ordered log until they expire or are deleted. Best for high throughput, stream processing, and replaying data.
*   **Pick MQ** for discrete tasks like sending emails; **pick Kafka** for real-time telemetry or clickstream analysis.

AA15 — **Container vs. VM:** A VM virtualizes hardware (has its own OS kernel); a container virtualizes the OS (shares the host's kernel). Containers are popular because they have much lower overhead, start faster, and allow higher density of services per server.

AA16 — **Stateless vs. Stateful:** Stateless services do not store client context between requests (e.g., a web server that just serves HTML). Stateful services maintain session state (e.g., a database or a gaming server). 
**Scaling:** Stateless is easier to scale horizontally because any instance can handle any request at any time. Example: Nginx (stateless), PostgreSQL (stateful).

AA17 — **ORM:** An Object-Relational Mapper maps code objects to DB tables. Examples: Hibernate (Java), SQLAlchemy (Python).
**Trade-offs:** ORMs increase developer productivity and safety but can produce inefficient SQL queries ("N+1 problem"). Raw SQL offers maximum performance and control but is harder to maintain and prone to injection vulnerabilities if handled poorly.

AA18 — **Bulkhead Pattern:** Named after ship hulls, it isolates resources so that a failure in one part doesn't sink the whole system. In microservices, this means isolating thread pools for different service calls; if Service A hangs, it shouldn't consume all threads available for Service B. Implementation: Use separate thread pools for external API clients or deploy critical services on physically separate hardware/clusters.

AA19 — **OT vs. CRDTs:** OT requires a central server to sequence operations (Google Docs style); CRDTs allow peers to update data independently and merge results mathematically without a coordinator.
*   **Consistency:** Both provide strong eventual consistency.
*   **Latency:** CRDTs have lower latency as they don't wait for a "lock."
*   **Offline Support:** CRDTs are superior for offline editing because they don't require an active connection to resolve conflicts upon reconnection. I would choose **CRDTs**.

AA20 — **Distributed Tracing Challenges:** 
Challenges include maintaining context across asynchronous boundaries (Kafka) and handling high-volume sampling. Context propagation uses headers like W3C Trace Context. Sampling strategies use Head-based (decide at start) or Tail-based (decide based on trace duration/errors). To ensure continuity through Kafka, you must inject trace IDs into the message headers so the consumer can pick up where the producer left off.

## On-Premise Infrastructure Architecture

OP1 — **Hypervisor Type 1 vs. Type 2:** Type 1 runs directly on bare metal (e.g., VMware ESXi, Xen). Type 2 runs on top of an existing OS (e.g., Oracle VirtualBox, VMware Workstation).

OP2 — **SAN vs. NAS:** SAN provides block-level storage over Fiber Channel or iSCSI; used for databases requiring low latency. NAS provides file-level storage over NFS or SMB; used for shared files/folders.

OP3 — **Network Topology:** Core handles high-speed switching; Distribution aggregates access switches; Access connects end devices. Leaf-Spine is preferred because it provides a "flat" architecture where every leaf is exactly two hops from any other leaf, providing predictable latency and massive horizontal scalability compared to the bottlenecked core of 3-tier designs.

OP4 — **Proxmox Cluster Design:**
*   **Nodes:** Minimum 3 nodes for quorum.
*   **Quorum:** Ensures enough votes exist to make decisions.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) ensures a failed node doesn't write data while trying to reboot.
*   **Storage:** Ceph (distributed block), iSCSI (centralized block), or NFS (file).
*   **Failure:** If a node fails, Proxmox detects loss of heartbeat, fences the dead node, and restarts VMs on remaining healthy nodes.

OP5 — **VLAN Trunking & Linux Config:** VLAN trunking carries multiple VLAN tags over one physical link using 802.1Q. To configure a single NIC on 3 VLANs in Linux: Create sub-interfaces (e.g., `eth0.10`, `eth0.20`) using the `ip` command or bridge-utils, assigning each a unique IP within their respective VLANs.

OP6 — **RAID Levels:** RAID 1 (Mirroring), RAID 5 (Parity - 1 disk failure), RAID 6 (Double Parity - 2 disks), RAID 10 (Mirror + Stripe), RAID Z2 (ZFS parity). For a 6-drive DB server needing performance/fault tolerance, I choose **RAID 10**. It provides the best balance of high IOPS and fast rebuild times compared to RAID 6/Z2.

OP7 — **DNS Architecture:** Use internal recursive resolvers for employees; authoritative servers for public zones. Split-horizon DNS ensures internal IPs aren't leaked. Conditional forwarding sends requests for specific domains (like `internal.corp`) to AD controllers. When moving from office to VPN, the client switches its primary DNS suffix to point to the VPN's internal resolver.

OP8 — **PKI Chain:** Root CA signs Subordinate CA, which signs End Entity certs. Keep Root CA offline to prevent total compromise. CRL checks if a cert is revoked; OCSP does this in real-time. A compromised subordinate allows an attacker to issue fake certificates for your domain; a compromised root allows them to forge any certificate globally.

OP9 — **WAN Comparison:** MPLS is reliable but expensive. IPsec over Internet is cheap but variable latency. SD-WAN manages multiple paths intelligently. WireGuard offers high-performance mesh encryption. Recommendation: **SD-WAN** because it combines cost efficiency with path steering for VoIP quality across remote sites.

OP10 — **Out-of-Band Management:** iDRAC/iLO provide access via a dedicated management chip even when the server OS is crashed or powered off. If exposed to the internet, attackers can gain full hardware control of the server, potentially installing persistent firmware-level malware.

OP11 — **LVM vs. LVM-Thin vs. ZFS:** 
*   **LVM:** Standard block volume management.
*   **LVM-Thin:** Allows "thin provisioning" (overprovisioning space).
*   **ZFS:** File system + Volume manager with built-in snapshots and RAID-Z.
Snapshots are metadata-based in LVM-Thin; ZFS uses Copy-on-Write (CoW) semantics.

OP12 — **Stretch Cluster & Ceph:** To survive site failure, use a stretch cluster where nodes in Site A see storage in Site B. Use CRUSH rules to ensure data replicas are distributed correctly. Network latency must be <5ms for synchronous replication. Why 2-site without tiebreaker? Without a third location (or witness), if the link between sites breaks, both sides might think they are the only survivors ("split-brain"), leading to data corruption.

OP13 — **DHCP DORA:** Discover (Client), Offer (Server), Request (Client), Acknowledge (Server). If the DHCP server is down, a Windows client will keep its current lease until it expires, then attempt to renew; if it fails, it may assign itself an APIPA address (169.254.x.x).

OP14 — **Managed vs. Unmanaged Switch:** Managed switches allow VLANs, Quality of Service (QoS) prioritization, SNMP monitoring, and Spanning Tree Protocol (STP) to prevent loops. These are essential in enterprises to isolate departments (VLANs) and prioritize VoIP traffic over standard web traffic.

OP15 — **NTP Importance:** NTP keeps clocks synchronized across servers. Drift causes failures in Kerberos authentication (time skew errors), database log synchronization issues, and prevents accurate timestamping of logs/transactions in distributed systems.

OP16 — **Physical vs. VM vs. Container:**
*   **Physical:** Direct hardware access. Use for high-performance DBs or heavy compute.
*   **VM:** Isolated OS environment. Good for legacy apps requiring specific kernels.
*   **Container:** Shared kernel. Best for microservices and rapid scaling.

OP17 — **UPS vs. Generator:** UPS provides immediate battery power during a blackout to allow graceful shutdown or bridge time until the generator starts. The generator provides long-term power. ATS automatically detects power loss and triggers the switch from utility to generator power.

OP18 — **Active-Active HA:** All nodes handle live traffic simultaneously. In an Active-Passive setup with Pacemaker/Corosync: Corosync handles cluster heartbeat; Pacemaker manages failover logic. STONITH ensures that if Node A fails, it is physically "fenced" off so it cannot write to shared storage while Node B takes over the Virtual IP (VIP).

OP19 — **Backup & DR Strategy:** 3-2-1 Rule: 3 copies, 2 different media types, 1 offsite. RPO = max data loss allowed; RTO = max downtime allowed. Use Incremental backups for daily efficiency and Full backups weekly. Use immutable cloud buckets for ransomware protection. Difference: Backup is copying data; Disaster Recovery is the entire plan (people, processes, hardware) to restore service after a catastrophe.

OP20 — **802.1X & MAB:** Supplicant (Device), Authenticator (Switch), Auth Server (RADIUS). EAP-TLS uses certificates for mutual auth. RADIUS checks credentials and tells the switch which VLAN to assign dynamically. MAB (MAC Authentication Bypass) allows devices like printers or IoT sensors—which don't support 802.1X—to be authenticated based on their MAC address against a whitelist.
