## Kubernetes

K1 — Easy: A **Deployment** is used for stateless applications where pods are interchangeable; it manages replica counts and rolling updates. A **StatefulSet** is used for stateful applications (e.g., databases) that require stable, unique network identifiers, ordered deployment/scaling, and dedicated persistent storage mapping to specific pod instances.

K2 — Easy: A ClusterIP Service acts as a virtual IP. The `kube-proxy` component on each node manages rules (via iptables or IPVS) that intercept traffic sent to the ClusterIP and redirect it to the actual IP addresses of the healthy Pods associated with that Service's endpoints.

K3 — Medium: 
- **PersistentVolume (PV):** A piece of storage provisioned by an admin (the "physical" resource).
- **PersistentVolumeClaim (PVC):** A request for storage by a user (the "ticket").
- **StorageClass:** A definition of different types of storage (the "template").
Relationship: A user creates a PVC requesting a certain size/type defined in a StorageClass; the controller then provisions a PV to satisfy that claim.

K4 — Medium: 
1. Check logs (`kubectl logs <pod>`) to see application stack traces or errors.
2. Check events (`kubectl describe pod <pod>`) to look for OOMKills, ImagePullBackOff, or failed Liveness Probes.
3. Check Resource Limits vs Usage (check if memory limits are too low causing OOMKill).
4. Check internal dependencies (e.g., is the DB connection failing during startup?).

K5 — Medium: CoreDNS provides internal name resolution for services within the cluster (e.g., `my-svc.default.svc.cluster.local`). If CoreDNS pods are down, pods can no longer resolve internal service names or external domains via the cluster's DNS system, leading to connection failures between microservices.

K6 — Hard: The scheduler uses two main phases:
1. **Filtering:** It eliminates nodes that don't meet requirements (e.g., insufficient CPU/Memory, Taints without matching Tolerations, NodeSelector mismatches).
2. **Scoring:** It ranks remaining nodes based on factors like:
   - **LeastRequested:** Preferring nodes with more free resources.
   - **ImageLocality:** Preferring nodes where the container image is already cached.
   - **InterPodAffinity:** Placing pods near others they are "affinity" grouped with.

K7 — Hard: 
**Scheduling:** Yes, it will be scheduled because its *request* (256Mi) fits in the remaining available capacity (512Mi). 
**Runtime:** If it tries to use 600Mi at runtime, it exceeds its defined *limit* of 512Mi. Kubernetes will trigger an OOMKill (Out Of Memory Kill), and the pod will restart, potentially entering a CrashLoopBackOff.

K8 — Hard: 
External Request $\rightarrow$ External Load Balancer $\rightarrow$ Ingress Controller Pod (NGINX) $\rightarrow$ Service (via internal logic) $\rightarrow$ Endpoints list $\rightarrow$ kube-proxy (iptables rules redirecting traffic) $\rightarrow$ Target Application Pod.

K9 — Medium: A NetworkPolicy is a firewall for Pods that controls ingress/egress traffic. By default, if no policy exists, all traffic is allowed (**Allow All**). When you apply one, only the pods selected by the label selector receive those specific restrictions; other pods remain unaffected unless explicitly included.

K10 — Medium: **RollingUpdate** replaces pods one by one, ensuring zero downtime but allowing two versions to run simultaneously. **Recreate** kills all existing pods before starting new ones. Choose Recreate when the application has non-backward-compatible changes or requires exclusive access to a singleton resource (like a database migration).

K11 — Easy: A Namespace is a virtual cluster inside a physical cluster used to partition resources and provide isolation. Default namespaces are `default`, `kube-system`, and `kube-public`.

K12 — Easy: It shows detailed status information about a pod's lifecycle. Three pieces of info not in `get` include: 
1. **Events** (e.g., "BackOff", "Pulled").
2. **Container Status** (Restart counts, exit codes).
3. **Node Name** where it is running.

K13 — Easy: A ConfigMap stores non-confidential data as key-value pairs. Pods consume them via:
1. **Environment Variables:** Injected into the container environment.
2. **Volume Mounts:** Mounted as files/directories within the container filesystem.

K14 — Easy: 
- **ClusterIP:** Internal only; provides a stable internal IP.
- **NodePort:** Exposes the service on a specific port on every Node's IP.
- **LoadBalancer:** Provisions an external load balancer from the cloud provider to route traffic to the Service.

K15 — Easy: A DaemonSet ensures that one copy of a pod runs on every node (or a subset of nodes). Use this for infrastructure tasks like log collection (Fluentd), monitoring agents (Prometheus Node Exporter), or networking plugins.

K16 — Medium: 
- **Taints:** Applied to Nodes to repel pods (unless they have a matching Toleration). Example: Tainting a GPU node so only "GPU-workload" pods can run there.
- **Node Affinity:** Rules applied to Pods to attract them to certain nodes. Example: Ensuring a web server always runs in a specific Availability Zone.

K17 — Medium: An Operator is a custom controller thates the "human operational knowledge" of a complex application (like Postgres) into software. It uses Custom Resource Definitions (CRDs) to automate complex logic like automated backups, failovers, and scaling that standard controllers cannot handle alone.

K18 — Hard: etcd uses the Raft consensus algorithm to ensure consistency across a quorum ($n/2 + 1$). If quorum is lost, the cluster stops accepting writes. To recover from losing 2 out of 3 nodes, you must restore an etcd snapshot to a new cluster and reconfigure the membership to include new healthy nodes.

K19 — Hard: Role = Namespace scope; ClusterRole = Cluster wide; Binding connects identity to role.
**Manifest for read-only access to pods/logs in namespace `dev`:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: read-only-binding
subjects:
- kind: User
  name: developer-user
  username: dev-user
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Hard: The `ndots` setting (default is usually 5) causes DNS lookups to try multiple search paths before failing, leading to excessive queries for every internal lookup. Fix this by setting `dnsConfig` with `ndots: 1` in the Pod spec's `dns_config` section or via a global configuration.

## Development

D1 — Easy: **Merge** combines two branches into one while preserving history; **Rebase** moves your entire branch's commits to the tip of another branch, rewriting history. Avoid rebasing on public/shared branches as it breaks others' local copies.

D2 — Easy: **TCP** is connection-oriented and reliable (e.g., HTTP, SSH). **UDP** is connectionless and faster but unreliable (e.g., DNS, VoIP).

D3 — Medium: A race condition occurs when two threads access shared data simultaneously where the final result depends on the timing of execution. Example: Two threads trying to increment a counter variable without a mutex lock at the same time.

D4 — Medium: Symmetric uses one key for both encryption/decryption; Asymmetric uses a Public Key (encryption) and Private Key (decryption). In TLS, asymmetric keys are used during the handshake to securely exchange a symmetric "session key," which then encrypts the actual data stream.

D5 — Medium: Each line in a Dockerfile creates a layer. Layer caching means if a command hasn't changed since the last build, Docker reuses the previous layer. Best practice: Put stable commands (like `apt-get install`) at the top and frequently changing code at the bottom.

D6 — Medium: 
1. Check application logs for errors.
2. Monitor resource metrics (CPU/Memory spikes).
3. Verify upstream service health/availability.
4. Check Load Balancer / Ingress limits or timeout settings.

D7 — Hard: CAP Theorem states you can only have two out of three: Consistency, Availability, Partition Tolerance. **CP** example: Etcd (Consistency + Partition Tolerance). **AP** example: Cassandra (Availability + Partition Tolerance).

D8 — Medium: **Horizontal Scaling** adds more machines (scaling out); **Vertical Scaling** adds more power (CPU/RAM) to an existing machine (scaling up). Patterns enabling horizontal scaling include Load Balancing, Sharding, and Microservices architecture.

D9 — Easy: An environment variable is a dynamic value stored by the OS/shell. On Linux, set it persistently by adding `export VAR_NAME=value` to your `.bashrc` or `.zshrc` file.

D10 — Easy: JSON is a lightweight data-interchange format; YAML is a human-friendly data serialization language. Advantage: JSON is faster for machines to parse; YAML supports comments and multi-line strings better for humans.

D11 — Easy: REST is an architectural style using HTTP methods. GET = fetch data; POST = create resource; PUT = update entire resource; DELETE = remove resource.

D12 — Easy: Version pinning specifies exact versions of dependencies (e.g., `requests==2.31.0`). It ensures that builds are reproducible across different environments and prevents "breaking changes" from automatic updates.

D13 — Easy: Compiled languages are converted to machine code before execution (C++, Rust). Interpreted languages are executed line-by-line by an interpreter (Python, Ruby).

D14 — Medium: A **Reverse Proxy** sits in front of web servers (e.g., NGINX) to handle load balancing/SSL. A **Forward Proxy** sits in front of clients to hide client IPs/filter traffic. Use cases: NGINX (Load Balancing), HAProxy (High Availability).

D15 — Medium: Deadlock occurs when two processes wait forever for each other to release resources. Coffman conditions: 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

D16 — Hard: Eventual consistency means the system will eventually be consistent but may return stale data temporarily. Cassandra uses tunable consistency levels like `ONE` (fastest, low consistency) or `QUORUM` (slower, higher consistency) to balance speed vs accuracy based on use case requirements.

D17 — Hard: mTLS requires both client and server to present certificates. Handshake: Client Hello $\rightarrow$ Server Certificate $\rightarrow$ Client Certificate $\rightarrow$ Key Exchange $\rightarrow$ Encrypted Channel. Used commonly in Service Meshes (Istio/Linkerd) to secure pod-to-pod communication.

D18 — Hard: Hash tables map keys to indices via a hash function. Collision resolution: Chaining (linked list at index) or Open Addressing (probing next empty slot). Time Complexity: Average $O(1)$, Worst $O(n)$ if many collisions occur.

D19 — Hard: A Circuit Breaker stops requests to a failing service to prevent "cascading failures." States: **Closed** (normal), **Open** (fail fast immediately), **Half-Open** (test if service is back). It works with retries + exponential backoff by ensuring we don't hammer a struggling service while it tries to recover.

D20 — Hard: **Optimistic:** Assumes no conflict; checks for changes only at commit time (e.g., row versioning). Best for low contention web apps. **Pessimistic:** Locks the record during the transaction (e.g., `SELECT FOR UPDATE`). Best for high-contention, critical transactions like banking transfers.
