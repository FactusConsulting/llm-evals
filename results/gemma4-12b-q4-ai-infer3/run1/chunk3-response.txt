As a senior infrastructure engineer, I have provided the requested answers below. Each answer is designed to be technically accurate while remaining concise enough for quick reference.

## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` creates an execution plan, showing what changes will occur (create, modify, destroy) without actually making them. It compares the current configuration against the existing state. `tofu apply` executes those actions to reach the desired state defined in your code.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file mapping your configuration resources to real-world identifiers. It tracks metadata about every managed resource. Remote state is critical for team collaboration; it ensures multiple engineers can work on the same infrastructure simultaneously by providing a centralized "source of truth" with locking mechanisms to prevent concurrent modification conflicts.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an index (0, 1, 2...) to replicate resources. `for_each` uses a map or set of keys. `for_each` is preferred whenever you need specific naming conventions or non-sequential logic because changing a middle element in a `count` list can cause unexpected reordering/recreation of subsequent items.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This creates "Configuration Drift." During the next `plan`, OpenTofu compares the actual cloud environment against the stored state file. If they differ, OpenTofu will propose a plan to revert the manual changes back to the configuration defined in your code.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
variable "vm_names" {
  type    = set(string)
  default = ["web1", "web2", "web3"]
}

resource "cloud_vm" "instances" {
  for_each = toset(var.vm_names)
  name     = each.key
  # ... other config
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads from an existing state file produced by another project. While useful, it couples two projects together via their state files. The recommended alternative is passing variables directly into child modules or using a shared "Global/Common" module approach where inputs are passed as parameters; this keeps dependencies explicit and makes testing easier.

**T7 — Hard: You have a module that provisions an RKE2 cluster... [null_resource issue]. Explain why and how to fix it.**
The `remote-exec` provisioner does not automatically capture stdout/stderr into OpenTofu outputs. On the first apply, the resource exists but has no value assigned to the output variable because the script finished without a mechanism to "save" its result. **Fix:** Use a `script` provisioner (if available for the provider) or use a `local_file` resource to write the kubeconfig to a local path, then use a `data "local_file"` block to read that content into a variable.

**T8 — Medium: What is tofu import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
Import brings existing infrastructure under management. Limitations include manual mapping of IDs and potential configuration mismatches. The `import` block allows you to declare the import inside your code, making it version-controlled, repeatable, and allowing the plan phase to validate the import before execution.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a placeholder for dynamic values. A **variable** is an input provided *to* the module/configuration (like a user's name). An **output** is a return value produced *by* the module/configuration (like a Load Balancer IP) used by other modules or humans.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates HCL into API calls for specific platforms (AWS, Azure, etc.). If you run `plan` without `init`, the process will fail because the necessary binaries/plugins haven't been downloaded or initialized in the `.terraform` directory.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It locks the exact versions of providers and modules used during the last successful `init`. Committing it ensures every team member and CI/CD pipeline uses identical provider versions, preventing "it works on my machine" bugs caused by minor provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`destroy` removes all resources managed by the configuration. To target a single resource, use the `-target` flag: `tofu destroy -target=aws_instance.example`.

**T13 — Easy: What is a data source in OpenTofu? Give an example.**
A data source allows you to fetch information about existing infrastructure *without* managing it. **Example:** Fetching the ID of an existing VPC created by another team so you can place your VM inside that specific VPC.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are inputs from outside; Locals are internal calculations. Use `locals` to simplify complex logic (e.g., concatenating strings or performing math) within a module to keep the main code clean and avoid repeating the same calculation multiple times.

**T15 — Medium: What is the lifecycle block in a resource? Explain create_before_destroy, prevent_destroy, and ignore_changes with a use case for each.**
It controls resource behavior during updates/deletion. 
- `create_before_destroy`: Ensures a new instance exists before deleting the old one (useful for zero-downtime DB migrations).
- `prevent_destroy`: Prevents accidental deletion of critical resources (like production databases).
- `ignore_changes`: Tells Tofu to ignore manual changes to specific attributes (e.g., ignoring tags modified manually via the console).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has changed its address in the configuration but remains the same physical object. It allows you to rename modules or move resources into sub-modules without triggering a "delete then recreate" cycle on live infrastructure.

**T17 — Hard: Explain how OpenTofu's dependency graph works... How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG) based on implicit dependencies (references like `aws_instance.web.id`). Explicit `depends_on` forces an order even if no reference exists. It reduces parallelism because it blocks the engine from starting independent tasks; use it sparingly as it can hide architectural flaws and slow down execution unnecessarily.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies.**
1. **State Splitting:** Break one giant state file into multiple smaller ones (e.g., network, db, app). *Tradeoff:* Complexity of cross-state references.
2. **Reduce Module Depth:** Flatten nested module structures. *Tradeoff:* Less modularity/reusability.
3. **Use Data Sources:** Fetch data instead of managing every small component. *Tradeoff:* Slightly slower lookups during plan.
4. **Parallelism Tuning:** Increase provider concurrency limits or use specialized providers. *Tradeoff:* Risk of hitting API rate limits.

**T19 — Hard: Explain the OpenTofu state locking mechanism... How do you manually break a lock?**
Locking prevents two users from modifying the same state simultaneously. If a CI pipeline crashes, the lock remains "stuck." To fix, use `tofu force-unlock <LOCK_ID>`. **Risk:** Manually breaking a lock is dangerous; if another process actually had a write operation in progress, it can lead to state corruption.

**T20 — Hard: You need to migrate an existing OpenTofu project from local to S3+DynamoDB. Describe the step-by-step process.**
1. Define the `backend` block with S3 and DynamoDB details.
2. Run `tofu init` (this creates the remote backend).
3. Use `tofu state rm` / `tofu import` or copy the local `.tfstate` file into the bucket. 
4. Verify by running `tofu plan`; it should show "No changes" (or only minor metadata updates) confirming the new state matches the current infrastructure.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
Task: A single action (e.g., install Nginx). Role: A reusable bundle of tasks, variables, and files for a specific purpose (e.g., a "webserver" role). Playbook: The top-level file that maps hosts to roles/tasks.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
Ansible Facts are system information gathered during setup. Access the OS family using the variable `ansible_os_family`.

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
`command`: Basic execution (no shell features like pipes/redirects). `shell`: Executes via a shell (supports pipes/wildcards). `raw`: Used when the Python interpreter is missing on the target; it executes directly via SSH. Use `command` whenever possible for predictability.

**A4 — Medium: How does Ansible handle idempotency? Give an example.**
Idempotency means running a task multiple times results in no change if the desired state is already met. 
*Idempotent:* `apt: name=nginx state=present` (won't reinstall if nginx exists).
*NOT Idempotent:* `shell: echo "data" >> /file` (appends every time run).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems.**
```yaml
- name: Install software based on OS
  apt:
    name: ["htop", "epel-release"]
    state: present
  when: ansible_os_family == "Debian"

- name: Install software for RedHat
  yum:
    name: ["htop", "epel-release"]
    state: present
  when: ansible_os_family == "RedHat"
```

**A6 — Hard: Explain Ansible's variable precedence order...**
Precedence is complex, but generally: Extra vars (`-e`) > Host vars > Group vars > Role defaults. Specifically, `extra_vars` has the highest priority, while role defaults have very low priority.

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this?**
Use `serial: 3`. This ensures Ansible processes exactly 3 hosts at a time; it will not move to the next batch until the current 3 are finished. To ensure they finish completely (including post-tasks), use `run_once: true` or `wait_for` if checking external health.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
Ansible Vault encrypts data. To encrypt only one variable in a file, run `ansible-vault encrypt --pretty <filename>`. It will prompt for which lines/variables to encrypt, allowing other parts of the file to remain plain text.

**A9 — Easy: What is an Ansible inventory file? Difference between static and dynamic?**
An inventory lists managed hosts. **Static:** A manual list of IPs/hostnames. **Dynamic:** Generated via API from cloud providers (AWS/GCP) where instances scale up/down automatically.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible... How do you trigger a handler?**
A handler is a task that runs only when "notified" by another task (e.g., restarting a service after a config change). Triggered using the `notify` keyword in a task.

**A12 — Easy: What is the ansible.cfg file used for? Name 3 settings.**
It configures Ansible's behavior. Common settings: `forks` (parallelism), `remote_interpreter`, and `pipelining`.

**A13 — Easy: What is the register keyword in Ansible, and how do you use it?**
`register` saves the output of a task into a variable. Example: Use `register: result` then access it in the next task with `{{ result.stdout }}`.

**A14 — Medium: Explain the difference between include_tasks and import_tasks.**
`import_tasks` is static; it is parsed at the start of the play. `include_tasks` is dynamic; it is parsed only when the execution reaches that line, allowing for conditional inclusion (`when`).

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles/collections?**
Galaxy is a public repository for Ansible roles. You list desired roles in `requirements.yml` and run `ansible-galaxy install -i requirements.yml` to download them.

**A16 — Medium: Explain how Ansible connection plugins work... ssh, local, network_cli.**
Connection plugins define *how* Ansible talks to the host. `ssh`: standard remote shell via SSH. `local`: runs on the control node itself. `network_cli`: sends commands directly over a CLI (like Telnet/Netconf) to networking gear.

**A17 — Hard: Explain how delegate_to and run_once work. Give an example.**
`delegate_to` runs a task on a specific host (e.g., localhost), while `run_once` ensures it only happens once regardless of the inventory size. **Example:** Updating a Load Balancer's config using data gathered from one web server: `delegate_to: localhost`, `run_once: true`.

**A18 — Hard: Strategies to improve performance for 500 hosts.**
1. **Forks:** Increase `-f` to allow more concurrent connections.
2. **Pipelining:** Enable `pipelining = True` in `ansible.cfg` to reduce SSH overhead.
3. **Fact Caching:** Use Redis or Memcached to store facts so they aren't re-gathered every time.
4. **Mitogen:** Replace the Ansible execution engine with Mitogen for significantly faster execution.

**A19 — Hard: Explain Jinja2 templating... Write a template snippet.**
`{{ }}` is for expressions, `{% %}` is for logic (loops/ifs), `{# #}` is for comments.
```jinja2
# Upstream block
upstream backend_servers {
{% for server in servers %}
  server {{ server.ip }}; {# Health check comment #}
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment across 20 servers.**
Use `serial: 1` (or small batches) to update one host at a time. Use a `block`/`rescue` structure: In the `block`, run the update and use the `uri` module to perform a health check. If it fails, the `rescue` block triggers a rollback task (e.g., reverting the config). Only move to the next batch if the health check passes.
