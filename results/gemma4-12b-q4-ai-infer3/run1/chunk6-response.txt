## JavaScript / TypeScript

JS1 — **var, let, const & Hoisting**: `var` is function-scoped and can be re-declared; `let` and `const` are block-scoped and cannot be re-declared in the same scope. `const` creates a constant binding (the value itself can change if it's an object/array, but the identifier cannot be reassigned). **Hoisting** is the JS engine's behavior of moving declarations to the top of their scope during the creation phase. `var` variables are initialized as `undefined`, while `let`/`const` are hoisted but remain in a "Temporal Dead Zone" (TDZ) until reached by execution.

JS2 — **Event Loop**: A mechanism that allows JS to perform non-blocking I/O despite being single-threaded. It processes the Call Stack first. Once empty, it checks the **Microtask Queue** (Promises, MutationObserver), then the **Macrotask Queue** (setTimeout, setInterval, setImmediate). Each macrotask completes one cycle before the next microtask queue is processed again.

JS3 — **Closure**: A function that remembers its lexical environment even when executed outside that scope. *Example*: A counter function where the count variable is private. **Classic bug**: Using `for (let i = 0...)` with a closure inside often captures the final value of `i`. Fix: Use `let` (block scoping) or wrap the inner logic in an IIFE.

JS4 — **Promise & Async/Await**: Promises represent eventual completion; `async/await` provides syntactic sugar for promises. Error handling uses `.catch()` for promises and `try/catch` for async functions. **Promise.all** rejects if any promise fails; **Promise.allSettled** waits for all promises to complete regardless of success/failure.

JS5 — **Interface vs Type**: Interfaces are primarily for defining shapes of objects/functions and support declaration merging. Types can define primitives, unions, and aliases. Use `interface` for public APIs/objects; use `type` for complex types like Unions or Intersections. **Discriminated Unions** use a common literal property (e.g., `type: 'success'`) to allow TS to narrow down types via type guards.

JS6 — **Prototypal Inheritance**: Every JS object has a prototype from which it inherits methods/properties. `Object.create(proto)` creates a new object with a specific prototype. ES6 classes are "syntactic sugar" over prototypes; they don't change the underlying prototypal nature but provide a cleaner way to manage inheritance.

JS7 — **The `this` keyword**: Binding rules (priority): 1. New (constructor), 2. Explicit (bind/call/apply), 3. Implicit (method call), 4. Default (global). `bind()` returns a *new* function with a fixed `this` context; you cannot re-bind a bound function because its `this` is already locked.

JS8 — **WeakRef & FinalizationRegistry**: `WeakRef` allows holding a reference to an object without preventing garbage collection. `FinalizationRegistry` notifies you when that object is collected. Used for memory management in high-performance apps (like caches). **WeakMap keys** must be objects because WeakMaps do not prevent GC of their keys, ensuring no memory leaks occur by keeping keys alive indefinitely.

JS9 — **V8 Optimization**: V8 uses **Hidden Classes** (shapes) to track property layouts and **Inline Caching** to store results of previous lookups at specific call sites. **Deoptimization** occurs when code changes types unexpectedly (e.g., adding properties in different orders or changing a variable from integer to string), forcing the engine to drop back to slower interpreted execution.

JS10 — **Tree-shaking**: A dead-code elimination technique where unused exports are removed during bundling. It works best with ES Modules (`import`/`export`) because they are statically analyzable. CommonJS (`require`) is dynamic, making it difficult for bundlers to know which parts will actually be used.

JS11 — **null vs undefined**: `null` is an intentional absence of value; `undefined` means a variable has been declared but not assigned. `==` performs type coercion (true); `===` checks strict equality (false). **Nullish coalescing (`??`)** returns right side if left is null/undefined; **Optional chaining (`?.`)** allows accessing nested properties only if the parent exists.

JS12 — **Array Methods**: `map()` transforms each element into a new array; `filter()` creates a subset based on a predicate; `reduce()` accumulates values into a single result. Initial value in `reduce()` defines the starting point. `flatMap()` maps then flattens one level deep—useful for returning arrays of results that need to be merged.

JS13 — **Template Literals & Tagged Templates**: Template literals use `` `...` `` and `${}` interpolation. **Tagged templates** allow a function to process the template string as pieces (strings + expressions). *Example*: A SQL query tagger: `sql` tagged template handles escaping variables automatically before sending them to the DB.

JS14 — **Destructuring**: Extracting data from objects or arrays into variables. Object destructuring supports renaming `{ name: userName }`. Array destructuring can include default values `[a, b = 1]`. The **Rest operator (...)** collects remaining elements into an array (e.g., `const [first, ...rest] = arr`).

JS15 — **for...in vs for...of**: `for...in` iterates over enumerable property keys (names); `for...of` iterates over values. You should avoid `for...in` on arrays because it includes inherited properties and non-numeric indices, leading to unexpected behavior.

JS16 — **TS Generics**: Allow creating reusable components with types. **Constraints (`extends`)** limit what type `T` can be; **Conditional Types** act like ternary operators at the type level; **infer** allows TS to "guess" a type from context. *Example*: `type GetLength<T> = { length: number } & { len: number }`.

JS17 — **Module Systems**: CommonJS is synchronous/dynamic (`require`); ESM is asynchronous/static (`import`). Node.js handles both but requires `"type": "module"` in `package.json` to treat `.js` files as ES Modules. This enables native ESM features like top-level await.

JS18 — **Structural Typing**: TS checks if a type matches the shape of another. **Excess Property Checks** only apply when assigning an object literal directly to a variable; they don't apply to variables already typed. **Extends** defines inheritance; **Satisfies** ensures a value meets a type without changing its own type. **Variance** (in/out) controls how subtypes are allowed in generic parameters.

JS19 — **Proxy & Reflect**: Proxy intercepts operations on an object (get, set, etc.); Reflect provides methods to perform those same actions. Example: A Proxy can intercept `set` to validate that a price property is always positive before updating it.

JS20 — **SharedArrayBuffer & Atomics**: Allows multiple threads (Web Workers) to share memory. `Atomics` provide thread-safe operations (add, wait, notify). They prevent race conditions by ensuring operations happen atomically across shared buffers. `Atomics.wait`/`notify` allow for synchronization between workers.

## Bash

B1 — **$@ vs $* **: `$*` expands all arguments into a single string (separated by spaces); `$@` expands each argument as a separate quoted string. Use `"$@"` to preserve individual spacing and quotes from command line inputs.

B2 — **set -euo pipefail**: `-e`: Exit immediately on error. `-u`: Error if using uninitialized variables. `-o pipefail`: Ensure the entire pipeline fails if any command within it fails (otherwise only the last command's exit code matters).

B3 — **$(...) vs `...`**: Both are command substitution; backticks are legacy/deprecated syntax. **$((...))** is used for arithmetic expansion (integer math), while `expr` is an external utility for similar tasks but slower and less portable in modern scripts.

B4 — **Process Substitution**: `<(command)` creates a temporary file descriptor that acts like a file path. *Example*: `diff <(ls dir1) <(ls dir2)` compares the output of two commands directly without creating temp files.

B5 — **Safe Iteration**: Using `for f in $(ls)` breaks if filenames have spaces. The safe way is `while read -r line; do ... done < <(ls -1)`; or use `find . -type f -print0 | while read -d '\0'`.

B6 — **Here Doc vs Here String**: `<<EOF` (doc) allows multi-line input until a delimiter. `<<< "string"` (string) takes a single string as input. `<<-EOF` removes leading tabs from each line, useful for indented blocks.

B7 — **Redirections**:
1. `cmd > file 2>&1`: Redirects stdout to file, then redirects stderr to where stdout was sent.
2. `cmd 2>&1 > file`: Redirection order matters! This sends stderr to stdout (which goes nowhere), then tries to redirect stdout to file. Result: Stdout goes to file, Stderr disappears/goes to original terminal.
3. `cmd &> file`: Shorthand for both stdout and stderr into one file.

B8 — **Locking Script**: Use `mkdir /tmp/lock` because `mkdir` is atomic at the OS level—if it exists, it fails instantly. A script would check `mkdir`, if successful proceed, else wait. Cleanup uses `trap 'rmdir /tmp/lock; exit' SIGTERM SIGINT`.

B9 — **Quotes**: `'...'` preserves literal content; `"..."` allows variable expansion (`$VAR`); no quotes treats everything as literal space-separated words. *Example*: `echo "Hello $USER"` vs `echo 'Hello $USER'`.

B10 — **File Checks**: `-f` (file), `-d` (directory), `-r` (readable). `[ ]` is a standard test; `[[ ]]` is a bash keyword that handles word splitting and globbing more safely (preferred in Bash).

B11 — **Variables**: `$?` Exit code of last command. `$$` PID of current shell. `$!` PID of last background process. `$#` Number of arguments passed to the script.

B12 — **Functions**: `foo() {}` is standard. `function foo {}` is also valid but not strictly necessary unless using specific keywords. Return values are handled by capturing output: `result=$(func)`. Bash doesn't have a native return value for data other than status codes.

B13 — **PATH & Builtins**: PATH is the list of directories searched for executables. A builtin (e.g., `cd`, `echo`) runs inside the shell; an external command (e.g., `/bin/ls`) starts a new process. Use `type <command>` to check which one it is.

B14 — **Trap**: Captures signals like `SIGINT` (Ctrl+C) or `TERM`. `trap 'cleanup_func' EXIT INT TERM ERR`. The order depends on signal arrival, but usually, they execute sequentially as caught.

B15 — **xargs vs Substitution**: Command substitution handles single outputs; `xargs` handles lists and can handle large inputs via pipes. For spaces/newlines, use `find ... -print0 | xargs -0`. `-P` enables parallel execution (e.g., `xargs -P 4`).

B16 — **Arrays**: Declare with `arr=()`. Append: `arr+=("val")`. Iterate: `for i in "${arr[@]}"; do...`. Length: `${#arr[@]}`. Associative arrays need `declare -A arr` and are accessed by keys (`arr[key]=val`).

B17 — **Subshell vs Grouping**: `(...)` creates a subshell (new PID); `{ ...; }` executes in current shell context. Variables changed inside `(...)` don't persist outside. Piping into a while loop `cmd | while read` runs the loop in a subshell because of the pipe.

B18 — **Signals & Job Control**: SIGINT (Interrupt), SIGTERM (Terminate), SIGHUP (Hangup), SIGKILL (Kill). To handle graceful shutdown, trap `SIGTERM`, then send signals to background PIDs or wait for them to finish before exiting.

B19 — **Parallel Processing Script**:
```bash
process_log() {
  grep "ERROR" "$1" > "out_$1"
}
export -f process_log
split -l 1000 large_log.log part_
ls part_* | xargs -P 4 -I {} bash -c 'process_log {}'
cat out_* > final_results.txt
```
Trade-off: Parallelism speeds up processing but makes error ordering/merging difficult. Use unique output files per chunk.

B20 — **Exec and Coprocesses**: `exec` replaces the current shell process with a new command. `exec 3>file` opens file descriptor 3. A coprocess is a background process whose stdin/stdout are connected to the script; use it for asynchronous communication where you need to read/write back and forth.

## PowerShell

PS1 — **Write-Output vs Write-Host**: `Write-Output` sends data into the pipeline (objects); `Write-Host` writes directly to the console buffer. Using `Write-Host` inside a function breaks pipelines because the result isn't passed forward.

PS2 — **Pipeline & ForEach**: The PS pipeline passes objects one by one. `ForEach-Object` processes items in the pipeline; `foreach` statement iterates over an existing collection variable. Use `ForEach-Object` for streaming, `foreach` for local collections.

PS3 — **PSCustomObject vs Hashtable**: `Hashtable` is a key-value dictionary; `[PSCustomObject]` behaves like a .NET object with properties. Convert via `[PSCustomObject]$hash`. Use PSCustomObject when property order or dot-notation access matters.

PS4 — **Error Handling**: Terminating errors stop execution; non-terminating continue. `$ErrorActionPreference = 'Stop'` turns all errors into terminating ones. `try/catch` only catches *terminating* errors.

PS5 — **Splatting**: Passing a hashtable as parameters using `@params`. Example:
`$p = @{Path="C:\Temp"; -Force} Function-Name @p`. It makes code much more readable than long lists of arguments.

PS6 — **Remoting**: `Invoke-Command` runs commands on remote machines (WinRM/SSH). `Enter-PSSession` creates an interactive session. WinRM uses SOAP/HTTP; SSH is used primarily in Linux environments.

PS7 — **Type System & Implicit Behavior**: The result of the provided snippet's `.GetType().Name` would be "Object" because PowerShell treats empty arrays and null results differently depending on how they are returned. To fix, ensure the function returns a consistent type (e.g., always an array) by initializing `$result = @()`.

PS8 — **ScriptBlock vs Function**: A ScriptBlock is a block of code that can be passed as data; a function is a named command. Use ScriptBlocks for `Invoke-Command`. Double-hop occurs when trying to access a third machine from a second machine via rem; solved with CredSSP or passing credentials explicitly.

PS9 — **@() vs [array]**: `@()` ensures a single item becomes an array; `[array]` casts a variable to an array type but doesn't change its count. Indexing into `$null` usually throws an error unless handled specifically.

PS10 — **Comparison Operators**: `-eq`/`-like` are standard; `-ceq`/`-clike` are case-sensitive. `-contains` checks if a collection contains a value; `-in` checks if a value exists within a collection.

PS11 — **Modules**: `.psm1` is the script module; `.psd1` is the manifest (metadata). Binary modules are compiled .dlls. `Import-Module` loads these into the session.

PS12 — **String Interpolation**: `"..."` allows interpolation (`$var`); `'...'` is literal. Expressions like `$(Get-Date)` work inside double quotes. Here-strings: `@"`...`"@` allow multi-line strings without escaping.

PS13 — **Get-Member & Pipeline**: `Get-Member` shows members of an object. Properties are attributes, Methods are actions. NoteProperties are properties added via hash tables. `Select-Object` filters properties/objects; `Where-Object` filters based on conditions.

PS14 — **PowerShell Classes**: Introduced in v5 to provide strongly typed objects. They differ from C# because they have limited inheritance and cannot use some advanced features like complex constructors or certain types of interfaces. Use functions for logic; classes for data structure consistency.

PS15 — **CmdletBinding**: Enables standard cmdlet behavior (e.g., `-Verbose`, `-WhatIf`). `SupportsShouldProcess` enables `-WhatIf`. `ValueFromPipeline` allows accepting input from the pipeline. Begin/Process/End blocks handle different stages of the pipeline stream.

PS16 — **Providers**: Providers abstract storage systems. `FileSystem` handles files; `Registry` treats registry keys as folders/files. You can access registry via `Get-Item HKCU:\Software\...`. This abstraction allows consistent commands across different backends.

PS17 — **Runspaces**: Runspaces are isolated execution environments. A `[runspacepool]` manages multiple runspaces. `ForEach-Object -Parallel` is a high-level wrapper that manages these automatically in PS 7+. Manual management is needed for long-running, stateful background tasks.

PS18 — **PSScriptAnalyzer**: An analyzer tool that checks code against best practices. It uses rules with severity levels (Warning, Error). Rules can be suppressed using `#PS_Suppress_RuleName`. Integrated into CI/CD to fail builds on "Error" level violations.

PS19 — **$using: Scope & Serialization**: `$using:` allows passing variables into remote sessions or parallel jobs. Variables must be serializable. Complex objects might exceed CLIXML depth limits during serialization when passed to remote sessions.

PS20 — **Desired State Configuration (DSC)**: DSC defines the *state* of a system (e.g., "Service X should be running"). LCM (Local Configuration Manager) enforces this state. In modern infra, it has been largely superseded by cross-platform tools like Ansible and Terraform.
