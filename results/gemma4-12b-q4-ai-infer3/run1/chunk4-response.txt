## Go Questions

G1 — An **array** has a fixed size; its length is part of its type. A **slice** is a descriptor (header) containing a pointer to an underlying array, a length, and a capacity. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array, copies the existing elements over, and returns a new slice header pointing to this new memory.

G2 — `var x int` declares a variable with a zero value (`0`). `x := 0` is a short variable declaration that infers the type from the right side. You cannot use `:=` inside a function if the variable is already declared in the same scope or at the package level (e.g., global variables must be declared with `var`).

G3 — A **goroutine** is a lightweight thread managed by the Go runtime, not the OS. It starts with a small stack (growing as needed), whereas OS threads have fixed sizes. The **GMP model** uses: **G**oroutines, **M**achines (OS threads), and **P**rocessors (logical contexts/resources). The scheduler maps Gs onto Ms via Ps to balance load across CPU cores.

G4 — Channels are typed conduits for communication between goroutines. An **unbuffered channel** blocks the sender until there is a receiver (synchronous). A **buffered channel** allows sending up to $N$ items without blocking. If a buffered channel is full, the send operation blocks until space becomes available.

G5 — The `context` package manages request-scoped values, cancellation signals, and deadlines.
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
```

G6 — Go interfaces use **implicit satisfaction**: any type that implements the required methods satisfies the interface automatically. Java/C# require explicit implementation (`implements`). `interface{}` (any) can hold any value but loses type safety; it requires type assertion or reflection to access specific fields, making it prone to runtime panics if not handled carefully.

G7 — This code has a **data race**. Even though `ready` is set to true, the compiler/CPU might reorder instructions or cache the `data` string in a register, causing the loop to see an old version of `data`. To fix this, you must use `sync.Mutex` or `atomic.Bool` to ensure memory visibility across goroutines.

G8 — `sync.Mutex` allows only one holder at a time. `sync.RWMutex` allows multiple concurrent readers OR one writer. Use `sync.Map` for high-concurrency scenarios with many reads and few writes on different keys; otherwise, a regular map with a `sync.Mutex` is often faster due to lower overhead.

G9 — `go.mod` defines module requirements; `go.sum` stores cryptographic hashes of dependencies. `go mod tidy` cleans up unused modules and adds missing ones. **MVS** ensures that if two modules require different versions of a third dependency, Go selects the *minimum* version that satisfies all constraints.

G10 — `defer` schedules a function call to run immediately before the surrounding function returns. They execute in **LIFO (Last-In, First-Out)** order. A common gotcha: using `defer` inside a loop (like a timer) can cause the deferred functions to stack up until the loop finishes, rather than running each iteration.

G11 — A pointer is a variable holding the memory address of another value. The zero value of a pointer is `nil`. To create a pointer to a struct literal, use the address-of operator: `x := &MyStruct{Field: 1}`.

G12 — `init()` runs automatically before `main()`. It runs after package variables are initialized but before `main`. A package can have multiple `init()` functions; they execute in lexical order (the order they appear in the source file).

G13 — `new(T)` allocates memory for a type and returns a pointer (`*T`). `make(T)` initializes the internal data structures of complex types like slices, maps, or channels. `new` works with any type; `make` only works with slices, maps, and channels.

G14 — Go treats errors as values. The `error` interface has an `Error() string` method. Idiomatic pattern: `if err != nil { return err }`. `errors.Is` checks if an error wraps a specific target; `errors.As` extracts a custom error type from a wrapped chain. They differ from `==` because they account for wrapped errors.

G15 — Built-in composite types: **Map** (zero value: `nil`), **Slice** (zero value: `nil`), **Channel** (zero value: `nil`), **Struct** (zero value: all fields at their zero values).

G16 — A race condition occurs when two goroutines access shared memory concurrently where at least one is a write. `-race` uses instrumentation to detect unsynchronized access during testing. Fix: Wrap the shared variable in a `sync.Mutex` or pass the data through a channel.

G17 — `select` lets a goroutine wait on multiple communication operations. Unlike `switch`, which evaluates expressions immediately, `select` blocks until one case can proceed. If multiple cases are ready, one is chosen pseudo-randomly. Timeout: Use `case <-time.After(duration):`.

G18 — Escape analysis determines if a variable lives on the stack or heap based on its lifetime and size. Variables that "escape" (e.g., returned from a function) go to the heap. Inspect via `go build -gcflags="-m"`. It matters because stack allocation is significantly faster than heap allocation/GC pressure.

G19 — Reflection allows inspecting/modifying types at runtime. `reflect.Type` describes the type; `reflect.Value` holds the actual data. Performance cost is high due to dynamic dispatch and lack of compiler optimization. Use code generation (like `protoc`) instead of reflection for performance-critical paths.

G20 — `go:embed` allows including static files into the binary at compile time. For directories, it includes all files recursively. It interacts with `io/fs.FS` by providing an `fs.FS` implementation of the embedded content, allowing standard file system access patterns.

## Rust Questions

R1 — Ownership means every value has a single owner. Rules: 1. Each value has exactly one owner. 2. When the owner goes out of scope, the value is dropped. 3. You can move ownership but cannot have two owners of the same memory simultaneously.

R2 — `String` is owned, heap-allocated, and growable. `&str` is a "string slice"—a view into existing memory. In function signatures, use `&str` if you only need to read the data; use `String` if the function needs to own or modify the string's buffer.

R3 — Borrowing lets you access data without taking ownership. **Rules**: You can have either many immutable references (`&T`) OR exactly one mutable reference (`&mut T`) at a time. You cannot have both simultaneously (the "aliasing XOR mutability" rule).

R4 — `Result<T, E>` handles errors; `Option<T>` handles presence/absence. The `?` operator returns early from a function if a result is `Err`.
```rust
use std::fs;
fn read_file(path: &str) -> Result<String, std::io::Error> {
    fs::read_to_string(path) // Returns Result automatically via ?
}
```

R5 — `Box<T>` provides heap allocation for single ownership. `Rc<T>` allows multiple owners (reference counting) but is not thread-safe. `Arc<T>` is an atomic version of `Rc`, allowing shared ownership across threads. Use `Box` for simple owned data, `Rc` for local multi-ownership, and `Arc` for cross-thread sharing.

R6 — Traits define shared behavior. They are similar to Go interfaces but require explicit implementation. A **trait object** (`dyn Trait`) uses dynamic dispatch (vtable), while a generic with a trait bound (`T: Trait`) uses monomorphization (static dispatch), which is faster as the compiler generates specific code for each type.

R7 — This fails because the compiler cannot guarantee that the returned reference lives as long as the caller expects (the "lifetime" of the return value). Fix by adding lifetime annotations: `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str`.

R8 — `Send` means a type can be sent to another thread; `Sync` means it's safe to share between threads. `Rc<T>` isn't `Send` because its internal counter isn't atomic. `Arc<T>` makes this safe by using atomic operations for the reference count, ensuring thread-safe incrementing/decrementing.

R9 — Rust async is "lazy"—nothing happens until polled. A `Future` is a state machine representing an eventual value. An executor (like Tokio) polls these futures. Unlike Go’s preemptive goroutines, Rust’s async is cooperative and requires an external runtime to drive progress.

R10 — `unsafe` allows bypassing some compiler guarantees. 3 examples: dereferencing raw pointers, calling FFI functions, or accessing mutable static variables. It is justified when interfacing with C libraries or writing low-level data structures where the overhead of safety checks is prohibitive.

R11 — Pattern matching checks values against patterns. `match` must be **exhaustive** (all possible cases covered), while `if let` handles only one specific case. The compiler enforces exhaustiveness at compile time, forcing you to handle every possibility (or use a wildcard `_`).

R12 — `Vec<T>` is a growable array on the heap; `[T; N]` is a fixed-size array (stack or heap). When a `Vec` exceeds capacity, it reallocates a larger block of memory (usually doubling) and moves elements there. Arrays have no growth mechanism.

R13 — Enums in Rust can hold data (sum types/algebraic data types), unlike standard C enums. `Option<T>` represents "some value" or "none." Rust doesn't have `null`; instead, it uses `Option` to force developers to explicitly handle the "nothing" case, preventing null pointer exceptions.

R14 — `impl` defines methods for a type. `&self` takes an immutable reference, `&mut self` takes a mutable reference, and `self` consumes the instance (moves ownership). Associated functions are functions defined within an `impl` block that don't take a `self` parameter (like `String::new()`).

R15 — The `derive` macro automatically implements traits like `Debug`, `Clone`, `PartialEq`. You cannot derive traits that require manual implementation logic or those involving complex lifetime requirements without extra configuration.

R16 — `Cow<'a, T>` stands for "Clone on Write." It allows you to return either a borrowed value (`&T`) or an owned value (`T`). This avoids allocating a new string if only a borrow is needed but provides an owned version if modification occurs.

R17 — Modules organize code. `mod` declares a module; `use` brings items into scope; `pub` makes them accessible outside the current module. In 2018 edition, the file system mapping became more flexible: any file in a directory can be a module, and nested modules can be declared via `mod sub_module;` even if they aren't in a subdirectory named `sub_module`.

R18 — `Pin<P>` ensures that a value's memory address won't change. This is required for types containing self-referential pointers (common in async futures). If a future moves in memory while it's being polled, internal pointers would break. `Unpin` indicates a type that *can* be moved safely.

R19 — **Declarative macros** (`macro_rules!`) are pattern-matching based. **Procedural macros** act like functions that take a token stream as input and output a token stream (e.g., `#[derive]`). Hygiene rules ensure that macro expansion doesn't accidentally capture variables from the surrounding scope.

R20 — Zero-cost abstractions mean you don't pay a performance penalty for using high-level features. **Monomorphization** generates specific machine code for every generic type used (static dispatch), and iterators/traits use compiler optimizations to produce assembly nearly identical to manual loops or C-style pointer arithmetic.
