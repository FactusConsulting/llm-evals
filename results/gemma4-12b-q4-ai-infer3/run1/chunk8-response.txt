## Cloud Infrastructure Architecture

CL1 — **IaaS** provides raw computing resources (VMs, storage, networking); you manage the OS and middleware. **PaaS** provides a platform (runtime, middleware) where you only manage code/data; the provider manages the underlying infra. **SaaS** is a finished software product managed entirely by the provider. Examples: AWS EC2 (IaaS), Google App Engine (PaaS), Microsoft 365 (SaaS).

CL2 — The **Shared Responsibility Model** dictates that the provider secures the "Cloud," while the customer secures "in the Cloud."
*   **IaaS VMs:** Provider secures hardware/hypervisor; You secure OS, patching, apps, data.
*   **Managed Kubernetes:** Provider secures control plane; You secure worker nodes (if not serverless), container images, and app logic.
*   **M365 (SaaS):** Provider secures almost everything except your data, identity management, and endpoint security.

CL3 — A **VPC** is an isolated private network. A **Subnet** is a logical partition of that VPC. A **Security Group** is a stateful firewall at the instance level (allow-list). A **NACL** is a stateless firewall at the subnet level. They layer as: VPC $\rightarrow$ Subnet (NACL) $\rightarrow$ Instance (Security Group). **Stateful** filtering remembers connection states (if inbound is allowed, return traffic is automatically allowed); **Stateless** requires explicit rules for both directions.

CL4 — A **Landing Zone** is a pre-configured multi-account environment with baseline security. **Organizational Units (OUs)** group accounts by function (Prod, Dev, Shared Services). **Guardrails** are automated policies (e.g., SCPs) to prevent non-compliant actions. **Transit Gateway / Hub-and-Spoke** centralizes networking so all spokes connect through a hub. **Centralized Logging** aggregates logs into a dedicated "Log Archive" account. A **single-account approach** leads to blast radius risks, lack of isolation between environments, and complex permission "spaghetti."

CL5 — **Terraform/OpenTofu:** Declarative, provider-agnostic, excellent for general infra. **Pulumi:** Imperative (use real code like Python/TS), great for complex logic. **CloudFormation/Bicep:** Native to AWS/Azure; best if staying within one ecosystem. **Crossplane:** Kubernetes-native IaC; treats cloud resources as K8s objects. Choose Terraform for standard infra, Pulumi for complex app logic, Bicep for native Azure depth, or Crossplane for GitOps-driven K8s infrastructure.

CL6 — **HPA:** Scales pods based on CPU/RAM. **VPA:** Scales pod size (CPU/RAM limits). **Cluster Autoscaler:** Adds/removes physical nodes from the cluster. **KEDA:** Event-driven scaling (scales to zero). Use **KEDA over HPA** when scaling based on external metrics (e.g., RabbitMQ queue length, Kafka lag) rather than just internal resource usage.

CL7 — **DR Strategy:**
*   **RPO/RTO:** Recovery Point Objective (data loss limit); Recovery Time Objective (downtime limit).
*   **Active-Active:** Traffic hits both regions simultaneously (lowest RTO/RPO).
*   **Active-Passive:** One region is standby.
*   **Replication:** Sync (Zero data loss, high latency) vs Async (Lower latency, potential minor data loss).
*   **DNS Failover:** Route53 Health Checks trigger DNS record updates to point to healthy region.
*   **Pilot Light:** Minimal resources running (DB only). **Warm Standby:** Scaled-down version of production ready to scale up. **Multi-site Active-Active:** Full capacity in two locations.

CL8 — **GitOps** ensures the "Source of Truth" is a Git repo; any change must be committed to Git first. **ArgoCD** uses a pull model (controller inside K8s pulls from Git); **FluxCD** does similar but focuses heavily on the "set and forget" controller logic. **Secrets:** Use **External Secrets Operator** or **Vault** to inject secrets into pods without storing them in Git. If someone makes a manual change (**Drift**), ArgoCD/Flux will automatically overwrite it with the Git state (Self-healing).

CL9 — Architecture: 1. **StatefulSet** for stable identity. 2. **Local Persistent Volume (LPV)** via StorageClass for low-latency disk access. 3. **Headless Service** to provide fixed network IDs per pod. 4. **Init Containers** to handle pre-startup scripts. 5. **ConfigMaps** mounted as volumes for config files. 6. **Pod Disruption Budgets (PDB)** to ensure minimum availability during maintenance.

CL10 — A **Service Account** is an identity for a K8s pod. **Workload Identity** is a cloud provider's identity mapped to that service account. **IRSA** is specifically AWS’s implementation of this. Mounting credentials (JSON keys) in a pod is bad because they can be stolen; **Workload Identity Federation** solves this by allowing the K8s pod to exchange its token for a short-lived cloud IAM token, eliminating long-lived static keys.

CL11 — **Object:** Unstructured data (S3); high durability, infinite scale. **Block:** Raw storage (EBS); used for DBs and OS disks. **File:** Shared filesystem (EFS/Azure Files); multiple pods mounting one share. Durability: Object usually offers "eleven nines" (99.999999999%); Block/File focus on IOPS and throughput performance.

CL12 — **Zero Trust Architecture:**
*   **Network Policies:** Isolate namespaces/pods.
*   **Service Mesh (Istio/Linkerd):** Enforce mTLS between all services.
*   **Pod Identity:** Assign unique identities to every workload.
*   **OPA/Kyverno:** Policy as Code (e.g., "No root containers").
*   **Falco:** Runtime threat detection.
Difference: Traditional security relies on a "hard shell" (Firewall). Zero Trust assumes the network is already breached and verifies every single request at every layer.

CL13 — A **CDN** caches content geographically closer to users to reduce latency and origin load. It works by caching "edges." Examples: CloudFront, Akamai. Use a CDN when serving static assets or global traffic; serve directly from origin only if you have low-latency requirements with very small user base or highly dynamic data that cannot be cached.

CL14 — **Regions** are physical locations; **Availability Zones (AZs)** are isolated data centers within a region. Deploying across AZs protects against local hardware/power failures. **Zonal resources** (like an EC2 instance) live in one AZ; **Regional resources** (like a Load Balancer or Global DB) span multiple AZs for high availability.

CL15 — Managed Databases handle automated patching, backups, multi-AZ failover, and scaling. Running on a VM requires you to manage OS updates, manual replication setup, and manual vertical/horizontal scaling of the underlying instances.

CL16 — **IAM Users** (People); **Groups** (Collections of users); **Roles** (Identities for services/apps); **Policies** (JSON permissions). **Least Privilege** means giving a user/service *only* the minimum permissions required to perform their job. Apply it by creating granular roles rather than using `AdministratorAccess`.

CL17 — Serverless is code execution where the provider manages all infra. AWS Lambda / Azure Functions / GCF. **Cold Starts** occur when a function hasn't been called recently, causing latency during "spin up." Poor fit: Long-running processes (>15 mins), constant heavy CPU tasks, or apps requiring specific low-level kernel tuning.

CL18 — **Ingress:** Standard K8s entry point. **Gateway API:** The next generation of Ingress providing more expressive configuration (traffic splitting, etc.). **Service Mesh Gateways:** Handle mTLS and complex routing. Gateway API allows for better separation of concerns between infrastructure (Gateway) and routing rules (HTTPRoute). Use Gateway API over Ingress when you need advanced traffic management without managing separate Load Balancer annotations.

CL19 — Strategy: 1. **Reserved Instances/Savings Plans** for baseline steady-state load. 2. **Spot Instances** for non-critical batch processing. 3. **Right-sizing** via monitoring tools (CloudWatch/Prometheus). 4. **S3 Intelligent-Tiering** for automated storage cost optimization. 5. **FinOps:** Establish a "Showback" model to show teams their costs; "Chargeback" actually bills them from the budget. Tools: CloudHealth, Kubecost, or native Cost Explorer.

CL20 — Multi-cloud strategy uses **Kubernetes** as an abstraction layer so containers run identically on AWS/Azure. **Terraform** manages both providers. Networking is handled via **VPN/DirectConnect/ExpressRoute**. Identity federation ensures one identity works across clouds. Trade-offs: High complexity and egress costs often outweigh benefits unless required by regulatory compliance or extreme high availability requirements. It's justified only if avoiding lock-in is a legal requirement or if specific features are unique to one provider.

## OT Infrastructure Architecture

OT1 — The **Purdue Model** segments industrial networks into levels based on function.
*   Level 0: Physical Process (Sensors/Actuators)
*   Level 1: Basic Control (PLCs/RTUs)
*   Level 2: Area Supervisory Control (HMIs/SCADA)
*   Level 3: Site Operations (Historians/MES)
*   Level 4: Enterprise Zone (Corporate IT)

OT2 — **IT** focuses on data confidentiality/integrity; **OT** focuses on safety/availability. You can't apply standard patching because OT systems have "uptime" requirements where rebooting a controller could stop a production line or cause physical danger. Many legacy PLCs lack modern OS support for frequent updates.

OT3 — An **IDMZ** acts as a buffer between Corporate (L4) and Production (L3). Only proxied, inspected traffic should cross. Direct L4 $\rightarrow$ L1 connectivity is dangerous because it allows an internet-facing breach to reach the controllers that move physical machinery, potentially causing kinetic damage.

OT4 — 1. Modbus TCP (L1/L2); 2. OPC UA (L2/L3 - Standard for machine-to-machine); 3. EtherNet/IP (L1); 4. PROFINET (L1); 5. MQTT (L3+ - used for cloud telemetry).

OT5 — A **Data Diode** is a hardware device allowing data to flow in only one direction physically. Use it when you need absolute certainty that no signal can enter from the outside (e.g., pushing sensor data out of a nuclear plant). Limitation: It prevents any two-way communication (no handshake), making some protocols impossible without specialized proxies.

OT6 — Flow: Sensors $\rightarrow$ PLC $\rightarrow$ Local Historian $\rightarrow$ Edge Gateway (MQTT Broker) $\rightarrow$ Cloud Ingestion Point. Security boundaries are placed at the IDMZ (Firewall) and the Edge Gateway (where encryption starts before hitting the public internet).

OT7 — **Zones** are logical groupings of assets with similar security requirements; **Conduits** are the secure paths between zones.
*   Design: Zone 1 (Corporate), Zone 2 (Engineering Workstations), Zone 3 (SCADA/Historian), Zone 4 (PLCs), Zone 5 (SIS). Conduits connect them via firewalls or diodes, ensuring SIS remains isolated even if SCADA is compromised.

OT8 — Strategy: Segment by production line using VLANs. Place industrial firewalls between lines. Remote access must go through a Jump Host in the IDMZ with MFA. Transition: Build the new network "parallel" to the old one, then migrate PLCs one by one during scheduled maintenance windows to avoid downtime.

OT9 — **SIS** handles emergency shutdown/safety; **BPCS** handles normal process control. IEC 61511 defines safety standards. They must be air-gapped because an attack on BPCS could cause a plant trip; an attack on SIS could disable safety systems entirely, leading to catastrophic failure. Ransomware on SIS would prevent the system from triggering an emergency stop during a pressure spike or leak.

OT10 — **PLC:** Localized logic for small machines. **DCS:** Distributed Control System for large, complex processes (refineries). **SCADA:** Supervisory system for wide-area monitoring. They coexist: A refinery uses DCS for the core process and SCADA to monitor multiple sites across different locations.

OT11 — Architecture: User $\rightarrow$ Corporate VPN $\rightarrow$ IDMZ Firewall $\rightarrow$ Jump Host (MFA) $\rightarrow$ Session Recording $\rightarrow$ HMI. RDP directly is unacceptable because it bypasses all security layers and provides a direct path into the control zone.

OT12 — Detection: Deploy passive IDS (e.g., Dragos, Claroty) to detect anomalous traffic in L3. IR Steps: 1. Isolate compromised segment. 2. Verify PLC integrity via hash checks. 3. Coordinate with operators to ensure "Safe State." The Plant Operator's role is critical—they provide context on whether a "malfunction" is a cyber event or a mechanical failure and authorize manual overrides.

OT13 — An **HMI** is the visual interface for an operator to see status/input commands. It differs from an Engineering Workstation (EWS) because EWS has tools to change logic/code; HMIs are primarily for viewing and setpoint adjustments.

OT14 — A **Historian** stores time-series data for analysis. **Plant Historian (L3)** serves local production needs (high frequency). **Enterprise Historian (L4)** aggregates filtered data for long-term business analytics and reporting.

OT15 — **Ladder Logic** mimics electrical relay diagrams. Executed by **PLCs**. It remains dominant because its visual representation allows electricians and engineers to troubleshoot easily using familiar concepts of physical wiring.

OT16 — An **RTU** is designed for remote telemetry over low-bandwidth links (radio/cellular); a **PLC** is for high-speed, localized control. RTUs are used in water pumping stations or oil wells where communication is distant and intermittent.

OT17 — Analog signals represent continuous values (pressure, temp). 4-20mA is preferred over 0-20mA because if a wire breaks (0mA), the system knows there's a "wire break" error rather than just reading a zero value.

OT18 — Asset Inventory: You can't protect what you don't know exists. Passive monitoring listens to traffic without injecting packets. Active scanning (like Nmap) can crash older PLCs by overwhelming their network stacks; hence it is often avoided in OT.

OT19 — Tactics include: 1. Impair Process Control (Technique: Modify PLC logic); 2. Inhibit Response Function (Technique: Disable alarms); 3. Loss of Control (Technique: Change setpoints); 4. Denial of Service (Technique: Flood network); 5. Persistence (Technique: Firmware modification). Difference: It focuses on *physical* impact (Safety/Process) vs IT's focus on Data/Confidentiality. Use it to map out how an attacker could stop production.

OT20 — SOC Design: Collect logs from IDMZ firewalls and Historians (not directly from PLCs to avoid jitter). SIEM must have OT-specific rules (e.g., "New Modbus function code"). Staffing requires both IT analysts for log correlation and OT engineers to validate if a "PLC firmware change" alert is a legitimate maintenance task or a cyber attack.
