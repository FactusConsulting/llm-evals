## Go

**G1 — Slice vs array; append at capacity**  
An array has a fixed length that is part of its type (`[3]int` and `[4]int` are different types) and is copied by value. A slice is a descriptor containing a pointer, length, and capacity, referencing a backing array; slices are reference-like. When `append` exceeds capacity, Go allocates a new larger backing array, copies existing elements, and returns a new slice header. If no reallocation occurs, other slices sharing the backing array may observe the change; if reallocation occurs, the original slice is unaffected.

**G2 — `var x int` vs `x := 0`**  
`var x int` declares a variable with an explicit type and zero value; it can be used at package or function scope. `x := 0` is short variable declaration: it infers the type and initializes the variable. You cannot use `:=` at package level, cannot use it to redeclare an existing variable in the same scope unless at least one variable is new, and cannot explicitly specify the type with `:=`.

**G3 — Goroutine vs OS thread; GMP scheduler**  
A goroutine is a lightweight function execution managed by the Go runtime, typically starting with a small stack that grows/shrinks. An OS thread is scheduled by the kernel and has larger fixed overhead. Go uses the GMP model: `G` = goroutine, `M` = OS thread, `P` = logical processor with a local run queue. The scheduler multiplexes many goroutines onto OS threads, uses work stealing, and can preempt long-running goroutines.

**G4 — Channels; buffered vs unbuffered; full buffered send**  
Channels are typed communication pipes that synchronize goroutines. An unbuffered channel requires a receiver to be ready before a send completes. A buffered channel has a queue of capacity `n`; sends complete until the buffer is full. Sending to a full buffered channel blocks until space becomes available or the channel is closed; sending on a closed channel panics.

**G5 — `context` package; `context.WithTimeout` example**  
`context` carries deadlines, cancellation signals, and request-scoped values across API boundaries and goroutines.

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

req, err := http.NewRequestWithContext(ctx, http.MethodGet, "https://example.com", nil)
if err != nil {
    return err
}

resp, err := http.DefaultClient.Do(req)
if err != nil {
    if errors.Is(err, context.DeadlineExceeded) {
        // handle timeout
    }
    return err
}
defer resp.Body.Close()
```

**G6 — Interface satisfaction; empty interface**  
Go interfaces are satisfied implicitly: a type implements an interface if it has the required methods, without an `implements` keyword. Java/C# interfaces are nominal: types explicitly declare implementation. `interface{}` / `any` has no methods, so every type satisfies it. It is powerful for heterogeneous collections and reflection, but dangerous because it erases static type safety and pushes failures to runtime type assertions.

**G7 — Memory model; unsafe ready/data example**  
The example is unsafe because there is no happens-before relationship between the goroutine writing `data`/`ready` and the main goroutine reading them. The compiler or CPU may reorder writes, and the main goroutine may see `ready == true` before `data` is visible, or may never observe the update. Correct alternatives include a channel, mutex, or atomic synchronization:

```go
done := make(chan struct{})
go func() {
    data = "hello"
    close(done)
}()
<-done
fmt.Println(data)
```

**G8 — `sync.Mutex` vs `sync.RWMutex`; `sync.Map` trade-offs**  
`sync.Mutex` allows one holder at a time. `sync.RWMutex` allows multiple concurrent readers or one writer, useful when reads greatly outnumber writes. `sync.Map` is optimized for read-mostly maps with stable keys and disjoint key access; it avoids a global lock but has higher memory overhead, weakly consistent `Range`, no `len`, and is not a general replacement for `map + Mutex`. For frequent writes or predictable iteration, a regular map with a mutex is usually better.

**G9 — Go modules; `go.mod`, `go.sum`, `go mod tidy`, MVS**  
`go.mod` declares the module path, Go version, dependencies, and replacements. `go.sum` stores cryptographic checksums for module zips and `go.mod` files to verify integrity. `go mod tidy` adds missing dependencies, removes unused ones, and updates `go.sum`. Minimum Version Selection chooses the minimum version that satisfies all requirements, effectively the maximum of required versions, not the latest available version.

**G10 — `defer`; order; loop gotcha**  
`defer` schedules a function call to run when the surrounding function returns. Multiple defers execute in LIFO order. Arguments to the deferred function are evaluated at the `defer` statement. A common gotcha is deferring inside a loop: resources are not released until the function exits, which can exhaust file descriptors or memory. Also, closures may capture loop variables unexpectedly, especially before Go 1.22.

**G11 — Pointers; zero value; pointer to struct literal**  
A pointer stores the memory address of a value. The zero value of a pointer is `nil`. You can create a pointer to a struct literal with `&`:

```go
p := &Point{X: 1, Y: 2}
```

**G12 — `init()` function**  
`init()` is a special function with no arguments or return values that runs automatically before `main`. Package-level variables are initialized before `init()` functions. Imported packages are initialized before the importing package. A package can have multiple `init()` functions; within a file they run in source order, and across files the order depends on compiler/build file order, so cross-file ordering should not be relied upon.

**G13 — `make` vs `new`**  
`new(T)` allocates zeroed memory for `T` and returns a `*T`; it works for any type. `make(T, ...)` initializes and returns a ready-to-use slice, map, or channel, not a pointer. `make` only works with slices, maps, and channels.

**G14 — Error handling; `errors.Is` vs `errors.As`**  
Go handles errors as values. The `error` interface is:

```go
type error interface {
    Error() string
}
```

Idiomatic code checks `if err != nil` and returns or wraps the error. `errors.Is` checks whether an error in the chain matches a sentinel error. `errors.As` finds a concrete error type in the chain. `==` only compares direct equality and fails for wrapped errors.

**G15 — Composite types and zero values**  
- `map`: zero value is `nil`; reads return zero values, writes panic.  
- `slice`: zero value is `nil`; length and capacity are 0; `append` works.  
- `channel`: zero value is `nil`; sends and receives block forever.  
- `struct`: zero value has each field set to its zero value.

**G16 — Race condition; `-race`; example and fix**  
A data race occurs when goroutines access shared memory concurrently, at least one access is a write, and there is no synchronization. The `-race` flag compiles with instrumentation that detects races at runtime and reports stack traces.

Race example:

```go
var counter int
var wg sync.WaitGroup

for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counter++ // data race
    }()
}
wg.Wait()
```

Fix with mutex:

```go
var mu sync.Mutex
var counter int

for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        mu.Lock()
        counter++
        mu.Unlock()
    }()
}
wg.Wait()
```

**G17 — `select`; timeout**  
`select` waits on multiple channel operations, like a switch but with channel cases. It blocks until one case can proceed. If multiple cases are ready, Go chooses one pseudo-randomly to avoid starvation.

Timeout example:

```go
select {
case v := <-ch:
    fmt.Println(v)
case <-time.After(time.Second):
    fmt.Println("timeout")
}
```

**G18 — Escape analysis**  
Escape analysis determines whether a variable can live on the stack or must be allocated on the heap. If a pointer escapes the function—by being returned, stored in a heap object, captured by a goroutine, or converted to an interface—the compiler heap-allocates it. Inspect with:

```bash
go build -gcflags="-m -m"
```

This matters because heap allocations increase GC pressure and can reduce cache locality.

**G19 — `reflect`; `reflect.Type` vs `reflect.Value`**  
`reflect.Type` describes a type: kind, fields, methods, interfaces. `reflect.Value` represents a concrete value and can inspect or modify it if addressable and exported. Reflection is slower than direct code because it uses runtime type information, boxing, allocations, and dynamic dispatch. It is justified for serialization, ORMs, dependency injection, and generic tooling; code generation is often better for performance-critical paths.

**G20 — `go:embed`**  
`go:embed` embeds files or directories into the binary at compile time.

```go
//go:embed config.json
var config string

//go:embed assets/*
var assets embed.FS
```

Single files can be embedded into `string`, `[]byte`, or `embed.FS`. Directories can only be embedded into `embed.FS`. Limitations: patterns cannot use `..` or absolute paths, hidden files beginning with `.` or `_` are excluded unless explicitly named, and files must be within the package/module directory. `embed.FS` implements `io/fs.FS`, enabling `fs.Sub`, `fs.ReadFile`, and HTTP file serving.

## Rust

**R1 — Ownership rules**  
Ownership is Rust’s memory management model. The three rules are: each value has exactly one owner; ownership can be moved; when the owner goes out of scope, the value is dropped. Moves transfer responsibility instead of copying, unless the type implements `Copy`.

**R2 — `String` vs `&str`**  
`String` is an owned, growable, heap-allocated UTF-8 string. `&str` is a borrowed view into UTF-8 data, which may be static or borrowed from a `String`. Use `&str` in function signatures when you only need to read text; use `String` when the function needs to own, mutate, or return owned text.

**R3 — Borrowing and borrow checker**  
Borrowing lets code access data without taking ownership. Shared references `&T` are immutable and can have many simultaneous borrows. Mutable references `&mut T` are exclusive: you cannot have `&mut T` and `&T` at the same time. References must also not outlive the data they borrow.

**R4 — `Result<T, E>`, `Option<T>`, `?` operator**  
`Result<T, E>` represents success `Ok(T)` or failure `Err(E)`. `Option<T>` represents presence `Some(T)` or absence `None`. The `?` operator returns early with the error or `None`, converting the error type if `From` is implemented.

```rust
use std::fs;
use std::io;

fn read_contents(path: &str) -> io::Result<String> {
    let contents = fs::read_to_string(path)?;
    Ok(contents)
}
```

**R5 — `Box<T>`, `Rc<T>`, `Arc<T>`**  
`Box<T>` allocates a value on the heap with single ownership. `Rc<T>` provides shared ownership with non-atomic reference counting, for single-threaded use. `Arc<T>` provides shared ownership with atomic reference counting, safe across threads. Use `Box` for heap ownership, `Rc` for shared single-threaded ownership, and `Arc` for shared multithreaded ownership.

**R6 — Traits; trait objects vs generics**  
Traits define shared behavior, similar to interfaces. Unlike Go interfaces, Rust trait implementations are explicit. `dyn Trait` is a trait object using dynamic dispatch through a vtable, allowing heterogeneous collections but with runtime cost. A generic bound `T: Trait` uses static dispatch and monomorphization, usually yielding faster code and compile-time specialization.

**R7 — Lifetimes; `longest` example**  
The function fails because the compiler cannot know whether the returned reference is tied to `x` or `y`. Lifetimes describe how long references are valid. Fix by tying both inputs and output to one lifetime:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Alternatively, return an owned `String`.

**R8 — `Send` and `Sync`; `Rc` vs `Arc`**  
`Send` means a type can be moved to another thread. `Sync` means `&T` can be shared across threads. `Rc<T>` is not `Send` or `Sync` because its reference count is non-atomic. `Arc<T>` uses atomic reference counting, making it safe for concurrent use when `T` itself is `Send + Sync`.

**R9 — Rust async/await; Future; executor**  
`async fn` returns a `Future`, which the compiler transforms into a state machine. A `Future` is polled by an executor; when it is not ready, it returns `Poll::Pending` and registers a waker. Tokio provides the executor and thread pool that polls tasks. Unlike Go goroutines, Rust futures are lazy and cooperative; they require an executor and can block the executor if they perform synchronous blocking work.

**R10 — `unsafe`**  
`unsafe` is an opt-in escape hatch for operations the compiler cannot prove safe. In an `unsafe` block you can dereference raw pointers, call `unsafe` functions, access or mutate `static mut`, implement `unsafe` traits, and access union fields. It is justified for FFI, low-level systems code, custom data structures, and performance-critical code where the programmer manually maintains safety invariants.

**R11 — Pattern matching; `match` vs `if let`**  
Pattern matching destructures enums, structs, tuples, and other values. `match` can bind values, use guards, and must be exhaustive unless a wildcard `_` is used. `if let` is sugar for matching a single pattern and ignoring all others. The compiler enforces that `match` covers all possible enum variants.

**R12 — `Vec<T>` vs `[T; N]`**  
`Vec<T>` is a growable heap-allocated dynamic array. `[T; N]` is a fixed-size array whose length is known at compile time and is often stack-allocated. When `Vec` pushes beyond capacity, it allocates a larger buffer, moves or copies existing elements, and deallocates the old buffer. Growth is amortized O(1).

**R13 — Rust enums; `Option<T>`; no null**  
Rust enums are algebraic data types: variants can carry data. C enums are mostly integer constants; Java enums are objects but not full sum types. `Option<T>` is:

```rust
enum Option<T> {
    Some(T),
    None,
}
```

Rust has no null because absence is represented in the type system, forcing explicit handling of missing values.

**R14 — `impl` block; `&self`, `&mut self`, `self`**  
An `impl` block defines methods and associated functions for a type. `&self` borrows the receiver immutably. `&mut self` borrows it mutably. `self` consumes or moves the receiver. Associated functions have no receiver, such as `String::new()`.

**R15 — `derive` macro**  
`#[derive(...)]` generates trait implementations automatically. Common examples include `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, `Hash`, `Default`, and external derives like `Serialize`/`Deserialize` from Serde. You cannot derive a trait if the trait does not support derivation, if the type contains fields that do not satisfy required bounds, or if the type is foreign and the trait cannot be implemented for it.

**R16 — `Cow<'a, T>`**  
`Cow` stands for clone-on-write. It can hold either a borrowed value or an owned value, cloning only when modification is needed. It avoids allocations when the input already satisfies the required form.

```rust
use std::borrow::Cow;

fn normalize(s: Cow<'_, str>) -> Cow<'_, str> {
    if s.contains(' ') {
        Cow::Owned(s.replace(' ', "_"))
    } else {
        s
    }
}
```

If the input has no spaces, no allocation occurs.

**R17 — Rust module system; `mod`, `use`, `pub`**  
`mod` declares a module. `use` imports names into the current scope. `pub` controls visibility outside the module. The file system maps to modules: `src/lib.rs` or `src/main.rs` is the crate root, and `mod foo;` looks for `foo.rs` or `foo/mod.rs`. In Rust 2018, paths in `use` can start with `crate::`, `::`, or external crate names directly; Rust 2015 required `extern crate` and more relative path rules.

**R18 — `Pin<T>`; self-referential structs; `Unpin`**  
`Pin<T>` guarantees that the value behind a pointer will not be moved. This is needed for self-referential structs because moving them would invalidate internal pointers. Async/await compiles to state machines that may hold references across `await` points, so futures often require pinning. `Unpin` is an auto trait indicating a type is safe to move; most types are `Unpin`, while self-referential or async state machines may be `!Unpin`.

**R19 — Macros; `macro_rules!` vs procedural macros**  
`macro_rules!` defines declarative macros using pattern matching over token trees. They are expanded at the use site and are hygienic. Procedural macros operate on token streams and include derive macros, attribute macros, and function-like macros. They can inspect and generate arbitrary code. Hygiene prevents macro-generated identifiers from accidentally capturing or being captured by local identifiers, though spans and `$crate` can influence resolution.

**R20 — Zero-cost abstractions**  
Zero-cost abstractions mean high-level code compiles to efficient machine code without runtime overhead beyond what hand-written code would have. Iterators compile down to loops, often with bounds checks optimized away. Generics are monomorphized into specialized code per concrete type, enabling static dispatch and inlining. Trait static dispatch via generics avoids vtable overhead, while still providing abstraction. This allows Rust to offer safe, ergonomic code with performance comparable to C.
