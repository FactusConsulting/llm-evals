## Cloud Infrastructure Architecture

**CL1 — Easy**  
- **IaaS (Infrastructure as a Service):** You rent compute, storage, and networking; you manage OS, middleware, apps, and data. Example: **AWS EC2**.  
- **PaaS (Platform as a Service):** Provider manages runtime/platform; you deploy code and data. Example: **Azure App Service**.  
- **SaaS (Software as a Service):** Provider manages the application; you use it. Example: **Microsoft 365**.

**CL2 — Easy**  
Shared Responsibility Model: provider secures the cloud; customer secures what they put in the cloud.  
- **IaaS VMs:** Provider handles physical hardware, hypervisor, host networking. You handle guest OS, patches, apps, data, firewall/security group config, IAM.  
- **Managed Kubernetes:** Provider handles control plane, master nodes, platform patching, and often node images. You handle cluster config, RBAC, network policies, workloads, secrets, data, and node scaling policy.  
- **SaaS like M365:** Provider handles app availability, infrastructure, and platform security. You handle identity/access, data classification, retention, user behavior, conditional access, and tenant configuration.

**CL3 — Medium**  
- **VPC:** Isolated virtual network in a cloud region.  
- **Subnet:** Segment of a VPC, usually tied to one availability zone.  
- **Security Group:** Instance-level firewall; **stateful** — return traffic is automatically allowed.  
- **NACL:** Subnet-level firewall; **stateless** — inbound and outbound rules must both allow traffic.  
Layering: VPC → subnet → NACL → security group → instance.  
Stateful means one rule can allow a connection and return traffic; stateless requires explicit rules in both directions.

**CL4 — Medium**  
A multi-account strategy uses:  
- **Landing zone:** Baseline accounts for security, logging, networking, shared services, and workloads.  
- **Organizational Units:** Group accounts by environment, business unit, or compliance domain.  
- **Guardrails:** SCPs/Azure policy to enforce regions, tagging, encryption, logging, and prohibited actions.  
- **Shared networking:** AWS Transit Gateway or Azure Hub-and-Spoke provides controlled connectivity between accounts/VNETs.  
- **Centralized logging:** Send logs to a dedicated security/logging account for audit and threat detection.  
Single-account is problematic because it creates a large blast radius, noisy neighbors, quota contention, weak cost allocation, and harder compliance isolation.

**CL5 — Medium**  
Infrastructure as Code defines infrastructure in version-controlled, repeatable code.  
- **Terraform/OpenTofu:** Multi-cloud, declarative, strong ecosystem; good for mixed clouds.  
- **Pulumi:** Uses general-purpose languages; good for software teams wanting logic, testing, and reuse.  
- **CloudFormation/Bicep:** Native AWS/Azure; tightly integrated, managed state, good for single-cloud teams.  
- **Crossplane:** Kubernetes-native control plane; good when platform teams want to manage cloud resources through Kubernetes APIs.  
Choose Terraform for multi-cloud, Pulumi for developer-centric teams, CloudFormation/Bicep for native single-cloud, Crossplane for Kubernetes platform engineering.

**CL6 — Medium**  
- **HPA:** Scales number of pod replicas based on CPU, memory, or custom metrics.  
- **VPA:** Adjusts pod CPU/memory requests and limits.  
- **Cluster Autoscaler:** Adds/removes nodes when pods cannot schedule or nodes are underutilized.  
- **KEDA:** Event-driven autoscaling from external sources like queues, Kafka lag, CloudWatch metrics, or custom events.  
Use **KEDA over HPA** when scaling should be driven by external event sources, queue depth, or when you need scale-to-zero.

**CL7 — Hard**  
DR design across two regions:  
- **RPO/RTO:** Define acceptable data loss and recovery time; drive architecture.  
- **Active-passive:** Primary region serves traffic; standby region is ready but not serving. Lower cost, higher RTO.  
- **Active-active:** Both regions serve traffic; lower RTO, higher cost and complexity.  
- **Database replication:** Synchronous gives low RPO but adds latency and cross-region coupling; asynchronous gives lower latency but higher RPO.  
- **DNS failover:** Route 53 or Azure Traffic Manager redirects traffic to healthy region.  
- **State management:** Externalize sessions, use idempotent APIs, global load balancing, and consistent data replication.  
- **Cost:** Active-active is most expensive; pilot light is cheapest; warm standby is middle ground.  
DR patterns:  
- **Pilot light:** Minimal core services running; scale up during DR.  
- **Warm standby:** Scaled-down but running environment.  
- **Multi-site active-active:** Full production capacity in both regions.

**CL8 — Hard**  
GitOps uses Git as the source of truth for desired state. A controller continuously reconciles live clusters to match Git.  
- **ArgoCD:** UI-driven, application-centric, strong for app delivery.  
- **FluxCD:** Kubernetes-native, modular, good for GitOps pipelines and infrastructure.  
Secrets:  
- **Sealed Secrets:** Encrypt secrets so only the cluster can decrypt.  
- **External Secrets Operator:** Pulls secrets from Vault/AWS Secrets Manager/Azure Key Vault.  
- **Vault:** Dynamic secrets, rotation, and centralized secret management.  
Manual drift: GitOps controllers detect drift and either revert automatically or alert, depending on policy. Manual changes are treated as temporary and auditable.

**CL9 — Hard**  
Design for a stateful legacy app on Kubernetes:  
- **StatefulSet:** Provides stable pod names, ordered deployment/scaling, and stable storage identity.  
- **PV/PVC with local storage class:** Use local persistent volumes for low latency; bind PVCs to specific nodes.  
- **Headless Service:** Gives stable DNS names for each pod, e.g., `pod-0.statefulset.namespace.svc`.  
- **Init containers:** Prepare config files, wait for dependencies, and enforce ordered startup.  
- **ConfigMaps as volume mounts:** Mount config files into required filesystem paths.  
- **Pod Disruption Budget:** Limits voluntary disruptions during maintenance.  
For sticky sessions, use ingress cookie affinity or service session affinity. Local storage reduces portability, so use anti-affinity, node affinity, backups, and application-level replication.

**CL10 — Medium**  
- **Service account:** Kubernetes identity for pods.  
- **Workload identity:** Cloud provider mechanism that maps Kubernetes workload identity to cloud IAM.  
- **IRSA:** AWS IAM Roles for Service Accounts; maps a Kubernetes service account to an AWS IAM role via OIDC.  
Mounting static cloud credentials in pods is bad because they can leak, are hard to rotate, often overprivileged, and lack workload-specific audit. Workload identity federation solves this by issuing short-lived, scoped tokens tied to the workload identity.

**CL11 — Medium**  
- **Object storage:** S3/Blob; accessed via HTTP APIs; good for unstructured data, backups, media, logs.  
- **Block storage:** EBS/Managed Disk; attached to a VM; good for databases, VM disks, low-latency workloads.  
- **File storage:** EFS/Azure Files; shared file system; good for shared home directories, CMS, lift-and-shift apps.  
Durability/availability:  
- Object storage is highly durable, often 11 nines, and regional.  
- Block storage is durable within an AZ but usually zonal; snapshots provide cross-AZ durability.  
- File storage is regional and highly available, with multi-AZ options.

**CL12 — Hard**  
Zero-trust Kubernetes architecture:  
- **Network policies:** Default deny, allow only required pod-to-pod traffic.  
- **Service mesh mTLS:** Encrypt and authenticate service-to-service traffic.  
- **Pod identity:** Use workload identity/IRSA instead of static credentials.  
- **Admission controllers:** OPA Gatekeeper or Kyverno enforce policies like image source, resource limits, and security contexts.  
- **Image signing/verification:** Use Cosign/Notary and verify signatures before deployment.  
- **Runtime security:** Falco detects anomalous process, file, or network behavior.  
- **Secrets management:** External secrets, Vault, short-lived credentials, encryption at rest.  
This differs from perimeter security because trust is not granted by network location; every request is authenticated, authorized, encrypted, and continuously verified.

**CL13 — Easy**  
A CDN is a distributed network of edge servers that caches content closer to users. It works by routing users to the nearest edge, serving cached content, and fetching from origin when needed.  
Examples: **AWS CloudFront**, **Azure Front Door/CDN**.  
Use a CDN for static assets, media, global web traffic, and reducing origin load. Serve directly from origin when content is highly dynamic, personalized, uncached, or latency-sensitive to origin logic.

**CL14 — Easy**  
- **Availability Zone:** Isolated data center within a region.  
- **Region:** Geographic area containing multiple availability zones.  
Deploy across multiple AZs to survive data center failure.  
- **Zonal resources:** Exist in one AZ, e.g., EBS volume.  
- **Regional resources:** Span multiple AZs, e.g., S3, Azure SQL managed instance options, regional load balancers.

**CL15 — Easy**  
A managed database service, such as RDS, Cloud SQL, or Azure SQL, provides a database platform managed by the cloud provider.  
Provider handles: provisioning, OS/database patching, backups, failover, monitoring, scaling, and infrastructure maintenance.  
You handle: schema design, queries, application integration, access control, data classification, and performance tuning.

**CL16 — Easy**  
- **IAM user:** Identity for a person or application.  
- **Group:** Collection of users with shared permissions.  
- **Role:** Temporary identity assumed by users, services, or workloads.  
- **Policy:** Defines allowed or denied actions.  
Principle of least privilege means granting only the minimum permissions needed. Apply it by using roles instead of users, scoped policies, temporary credentials, regular access reviews, and deny-by-default.

**CL17 — Easy**  
Serverless is event-driven compute where the provider manages servers, scaling, and runtime.  
- **AWS Lambda:** Deep AWS integration, many triggers.  
- **Azure Functions:** Strong Azure integration, supports many languages.  
- **Google Cloud Functions:** Simple event-driven functions, strong GCP integration.  
Cold starts are startup delays when a function instance is created; they matter for latency-sensitive APIs. Serverless is a poor fit for long-running processes, heavy state, predictable sustained high load, very low latency requirements, or large dependency bundles.

**CL18 — Medium**  
- **Ingress resource:** Kubernetes API for HTTP routing; simple but limited.  
- **Gateway API:** Modern Kubernetes API for traffic management with richer routing and role separation.  
- **Cloud load balancer annotations:** Provider-specific way to configure LB behavior.  
- **Service mesh ingress gateway:** Mesh-controlled entry point with mTLS, observability, and traffic policies.  
TLS termination can occur at cloud LB, ingress controller, or mesh gateway. Use Gateway API over traditional Ingress when you need advanced routing, multi-team ownership, extensibility, and clearer separation between platform and application teams.

**CL19 — Hard**  
Cost optimization for $80k/month:  
- **Reserved Instances/Savings Plans:** Commit to usage for predictable workloads.  
- **Spot/Preemptible:** Use for fault-tolerant, interruptible workloads.  
- **Right-sizing:** Reduce overprovisioned VMs, databases, and Kubernetes requests.  
- **Storage tiering:** Use S3 Intelligent-Tiering, Archive, or lifecycle policies.  
- **Idle resource detection:** Find unattached disks, idle VMs, orphaned IPs, unused load balancers.  
- **FinOps:** Shared accountability, tagging, budgets, alerts, monthly reviews.  
- **Showback/chargeback:** Attribute costs to teams/projects.  
Tools: AWS Cost Explorer, Azure Cost Management, Kubecost, CloudHealth, custom tagging policies, budget alerts, and automated governance.

**CL20 — Hard**  
Multi-cloud strategy:  
- **Abstraction layers:** Use Kubernetes, Terraform, and portable APIs to reduce provider-specific coupling.  
- **Kubernetes as common runtime:** Run workloads consistently across AWS and Azure.  
- **Terraform for IaC portability:** Define infrastructure declaratively across clouds.  
- **Networking:** Use VPN or interconnects for controlled cross-cloud traffic.  
- **Identity federation:** Use OIDC/SAML to federate identities and avoid duplicate credential sprawl.  
Trade-offs: multi-cloud adds complexity, cost, skill requirements, and operational overhead. It is justified for regulatory needs, resilience, acquisitions, best-of-breed services, or avoiding strategic vendor risk. It is unnecessary if one cloud meets requirements and the added complexity does not create real business value.

## OT Infrastructure Architecture

**OT1 — Easy**  
The Purdue Model/ISA-95 is a layered reference model for industrial systems.  
- **Level 0:** Physical process — sensors, actuators, motors, valves.  
- **Level 1:** Basic control — PLCs, RTUs, I/O.  
- **Level 2:** Supervisory control — HMIs, SCADA, local control.  
- **Level 3:** Site operations — MES, historians, plant data.  
- **Level 4:** Enterprise IT — ERP, email, business systems.  
- **Level 5:** External network — internet, partners, vendors.

**OT2 — Easy**  
IT networks prioritize confidentiality, patching, and rapid change. OT networks prioritize availability, safety, determinism, and long-lived equipment.  
Standard IT patching can break OT because devices may be untested, vendor-certified, real-time, or unable to tolerate downtime. Patching must be risk-based, tested, and scheduled around production windows.

**OT3 — Medium**  
An Industrial DMZ sits between IT and OT to control and monitor traffic.  
Allowed traffic is typically limited: OT-to-IT data uploads, historian replication, approved management traffic, and vendor access through controlled jump hosts.  
Direct connectivity from Level 4 to Level 1 is dangerous because it bypasses segmentation, allows malware or unauthorized commands to reach control devices, and removes visibility and approval controls.

**OT4 — Medium**  
- **Modbus TCP:** Simple industrial protocol; typically Level 1/2.  
- **OPC UA:** Secure, structured industrial data exchange; typically Level 2/3.  
- **EtherNet/IP:** CIP-based industrial Ethernet; typically Level 1/2.  
- **PROFINET:** Industrial Ethernet for automation; typically Level 1/2.  
- **MQTT:** Lightweight pub/sub messaging; typically Level 2/3, edge, or cloud data flows.

**OT5 — Medium**  
A **data diode** is a hardware-enforced one-way communication device. A firewall filters bidirectional traffic based on rules.  
Use a data diode when data must only leave a secure OT zone and no inbound traffic is allowed, such as sending historian data to IT/cloud.  
Limitation: it cannot support normal bidirectional protocols or remote control, so it is unsuitable where two-way communication is required.

**OT6 — Medium**  
Data flow:  
1. PLCs/SCADA publish process data.  
2. Plant historian collects and stores time-series data.  
3. OPC UA server exposes data securely.  
4. Edge gateway normalizes and buffers data.  
5. MQTT broker publishes data to cloud ingestion.  
Security boundaries:  
- OT-to-IDMZ boundary.  
- Edge gateway with authentication, TLS, and allowlists.  
- MQTT broker in IDMZ or controlled DMZ.  
- Cloud connector with least-privilege credentials and monitoring.  
Direct OT-to-cloud connections should be avoided.

**OT7 — Hard**  
IEC 62443 defines security zones and conduits.  
- **Zone:** Logical group of assets with similar security requirements.  
- **Conduit:** Controlled communication path between zones.  
Example plant model:  
- Corporate IT zone.  
- Industrial DMZ.  
- Engineering workstation zone.  
- SCADA/HMI zone.  
- PLC/control zone.  
- SIS/safety zone.  
Conduits are controlled by firewalls, jump hosts, and monitoring. SIS should have the strictest isolation, possibly one-way data flow or highly restricted managed conduits.

**OT8 — Hard**  
Segmentation strategy:  
- Create VLANs by function and production line: PLC VLAN, HMI VLAN, historian VLAN, engineering VLAN, vendor VLAN.  
- Place firewalls between L2/L3 zones and between OT and IDMZ.  
- Use managed switches with access VLANs, trunking, and port security.  
- Vendor access goes through a jump host/VDI with MFA, session recording, and time-limited credentials.  
Transition without stopping production:  
- Use passive monitoring first.  
- Build parallel VLANs/firewall rules.  
- Deploy in monitor mode.  
- Cut over during maintenance windows.  
- Keep rollback plans.  
- Coordinate with operations and vendors.

**OT9 — Hard**  
- **BPCS:** Basic process control system for normal production control.  
- **SIS:** Safety Instrumented System for independent safety shutdowns.  
- **IEC 61511:** Functional safety standard for process industry SIS.  
SIS must be isolated or air-gapped because compromise could disable safety functions or force unsafe manual operation.  
If ransomware reaches SIS, it could prevent safe shutdown, corrupt safety logic, or force operators into degraded manual mode, creating physical safety risk.

**OT10 — Medium**  
- **PLC:** Discrete, fast control for machines and processes.  
- **DCS:** Integrated control for continuous processes, often large plants.  
- **SCADA:** Supervisory control and data acquisition across distributed sites.  
Use PLCs for machine control, DCS for continuous process plants, SCADA for remote/distributed monitoring. They can coexist: SCADA supervises PLCs/DCS, and DCS may include PLC-like control elements.

**OT11 — Medium**  
Remote OT access should use:  
- Jump hosts or VDI in a controlled zone.  
- MFA.  
- Session recording and monitoring.  
- Vendor-specific, time-limited accounts.  
- Just-in-time access and approval workflows.  
Direct RDP from corporate to an HMI is unacceptable because it bypasses segmentation, lacks audit, exposes OT to IT malware, and allows uncontrolled changes.

**OT12 — Hard**  
Detection and response plan:  
- Activate OT incident response and notify control room leadership.  
- Use network monitoring/IDS to identify lateral movement, unusual PLC traffic, and vendor VPN abuse.  
- Validate asset inventory to identify affected L3 systems.  
- Disable compromised vendor VPN access and rotate credentials.  
- Isolate affected L3 systems while preserving process visibility.  
- Coordinate with operators to maintain safe operation; shift to manual or safe mode if needed.  
- Preserve logs and forensic evidence.  
- Restore from known-good backups and validate PLC logic.  
- Hunt for persistence and re-test safety functions.  
Plant operator role: maintain safe process conditions, follow emergency procedures, communicate status, and avoid unauthorized changes while IT/OT teams contain the threat.

**OT13 — Easy**  
An HMI is the operator interface to an industrial control system. It displays process status, alarms, and allows operator actions.  
An engineering workstation is used by engineers to configure, program, and maintain control systems. HMI is for operations; EWS is for engineering.

**OT14 — Easy**  
A historian stores time-series process data for analysis, reporting, and troubleshooting.  
- **Plant historian:** Level 3, collects data from SCADA/PLCs for plant operations.  
- **Enterprise historian:** Level 4, aggregates plant data for business analytics, KPIs, and enterprise reporting.

**OT15 — Easy**  
Ladder logic is a graphical programming language resembling electrical relay logic. It is executed by PLCs.  
It remains dominant because it is intuitive for electricians and technicians, standardized, reliable, and deeply embedded in legacy industrial automation.

**OT16 — Easy**  
An RTU is a ruggedized controller used in remote, distributed environments.  
A PLC is typically used in factory/industrial control panels.  
RTUs are common in utilities, oil and gas, water/wastewater, pipelines, and remote substations where communication, harsh environments, and distributed sites are key.

**OT17 — Easy**  
- **Analog signals:** Continuous values, e.g., 4-20mA or 0-10V.  
- **Digital signals:** Discrete on/off states.  
4-20mA is preferred over 0-20mA because 4mA represents live zero, allowing wire break detection, better noise immunity, and loop-powered devices.

**OT18 — Medium**  
OT asset inventory is the foundation of OT security because you cannot protect what you do not know exists.  
Tools/techniques:  
- Passive network monitoring.  
- Protocol-aware OT monitoring.  
- CMDB integration.  
- Maintenance records.  
- Careful active scanning only in approved windows.  
Active scanning is dangerous because legacy OT devices may crash, timeout, or behave unpredictably when probed.

**OT19 — Hard**  
MITRE ATT&CK for ICS describes adversary behaviors in industrial environments.  
Example tactics and techniques:  
- **Initial Access:** Valid accounts via compromised vendor VPN.  
- **Execution:** Command and scripting interpreter on engineering workstation.  
- **Persistence:** Scheduled task or service on HMI.  
- **Discovery:** Network service scanning of PLCs.  
- **Impact:** Modify controller logic or firmware.  
It differs from enterprise ATT&CK by focusing on OT protocols, safety impact, and physical process effects. Use it to map detections, identify gaps, and prioritize OT-specific monitoring and controls.

**OT20 — Hard**  
Converged IT/OT SOC design:  
- Collect logs passively where possible: syslog, NetFlow, historian events, IDS alerts, jump host logs.  
- Avoid active agents on critical OT devices unless vendor-approved.  
- Integrate OT data into SIEM with normalized schemas.  
- Build OT-specific rules: PLC program changes, unauthorized firmware, unusual Modbus writes, vendor access anomalies.  
- Triage workflow: IT analyst triages, OT engineer validates operational impact.  
- Staffing: combine SOC analysts with OT engineers and plant liaisons.  
- False positives: tune rules with OT context and maintain known-good baselines.  
For unauthorized PLC firmware change:  
1. Verify against change management.  
2. Notify OT engineer and control room.  
3. Assess process safety.  
4. Isolate affected PLC if safe.  
5. Compare firmware/checksums.  
6. Roll back or restore from approved backup.  
7. Preserve evidence and investigate root cause.
