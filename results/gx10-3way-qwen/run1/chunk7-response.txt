## Application Architecture

**AA1 — Monolith vs microservices**  
A monolith is a single deployable application with one codebase, process, and usually one database. Microservices split functionality into independently deployable services, each with its own process, API, and often its own data store.  
Concrete problems microservices introduce that monoliths usually do not:
1. **Distributed transactions/data consistency** — updates span multiple services and databases.
2. **Network failure and partial failure** — calls can time out, fail, or return stale data.
3. **Operational complexity** — service discovery, versioning, deployment pipelines, observability, and security become distributed concerns.

---

**AA2 — Synchronous vs asynchronous communication**  
Synchronous communication means the caller sends a request and waits for a response before continuing. Example: **REST over HTTP** or **gRPC**.  
Asynchronous communication means the caller sends a message/event and continues without waiting for the consumer to process it. Example: **Kafka**, **RabbitMQ**, or **AWS SQS**.

---

**AA3 — API Gateway vs reverse proxy**  
A reverse proxy forwards client requests to backend servers, often handling TLS termination, load balancing, caching, and basic routing.  
An API Gateway is typically a reverse proxy plus API management: authentication, rate limiting, quotas, request/response transformation, versioning, analytics, service discovery, and policy enforcement.  
Can an API Gateway replace a reverse proxy entirely? **Often for API traffic, yes**, but not always. It may be overkill for simple internal proxying, may not handle arbitrary TCP protocols, non-HTTP traffic, or very low-latency L4 proxying, and can become a centralized bottleneck if not designed carefully.

---

**AA4 — Saga pattern**  
A Saga is a sequence of local transactions where each service updates its own data and publishes an event or command to trigger the next step. If a later step fails, compensating transactions undo earlier changes.  
- **Choreography-based Saga**: services react to events from other services. No central coordinator. Good for simple, loosely coupled workflows.  
- **Orchestration-based Saga**: a central coordinator tells services what to do. Good for complex workflows needing visibility, retries, timeouts, and explicit compensation logic.

---

**AA5 — CQRS and Event Sourcing**  
CQRS separates the write model from the read model. Commands modify state; queries read from optimized read models.  
It is often paired with Event Sourcing because events are the immutable source of truth, and read models can be built as projections from those events.  
This combination solves problems traditional CRUD struggles with: auditability, temporal queries, complex domain rules, read/write scaling asymmetry, and rebuilding read models without losing history.

---

**AA6 — Circuit Breaker pattern**  
A Circuit Breaker prevents repeated calls to a failing dependency.  
States:
1. **Closed** — calls proceed normally; failures are counted.
2. **Open** — calls fail fast without hitting the dependency.
3. **Half-open** — a limited number of test calls are allowed to see if the dependency recovered.  
It differs from retry with backoff because retry keeps attempting calls, which can amplify load during failure. Use both together: retry transient errors while the circuit is closed, but open the circuit after a failure threshold to stop retry storms.

---

**AA7 — Multi-tenant isolation models**

| Model | Cost | Security | Operational complexity | Noisy-neighbor risk |
|---|---:|---:|---:|---:|
| Shared DB, shared schema | Lowest | Weakest; relies on row-level tenant ID and strict query isolation | Lowest | Highest |
| Shared DB, separate schema | Medium | Better; schema isolation reduces accidental cross-tenant access | Medium/high; migrations and connection management scale poorly | Medium |
| Separate DB per tenant | Highest | Strongest; easier compliance and blast-radius control | Highest; provisioning, backup, patching, monitoring multiply | Lowest |

---

**AA8 — Eventual vs strong consistency; inventory never oversells**  
Eventual consistency means replicas converge over time after updates. Strong consistency means reads see the latest committed write immediately, often via linearizability or serializable transactions.  
For inventory that must never oversell, use **strong consistency for the authoritative stock update**.  
At scale:
- Use a transactional store with atomic conditional updates, e.g. PostgreSQL, CockroachDB, Spanner, or DynamoDB conditional writes.
- Decrement stock with a condition: `UPDATE inventory SET qty = qty - N WHERE sku = ? AND qty >= N`.
- Use idempotency keys to prevent duplicate orders.
- Partition by SKU/product to reduce contention.
- Use reservation patterns with TTL for cart holds.
- Use eventual consistency only for caches, analytics, or reporting, not for the authoritative inventory decision.

---

**AA9 — Sidecar proxy, Envoy/Istio, data plane vs control plane**  
A sidecar proxy runs alongside an application container and intercepts inbound/outbound traffic.  
In Istio, Envoy is injected as a sidecar. iptables redirect traffic through Envoy. Envoy receives configuration from **istiod** via xDS APIs.  
- **Data plane**: Envoy proxies handling traffic.
- **Control plane**: istiod generating and distributing configuration, certificates, and policies.  
mTLS between sidecars solves service-to-service identity and zero-trust encryption. Application-level TLS often only authenticates the server, not the client service, and makes uniform policy, certificate rotation, and identity enforcement much harder.

---

**AA10 — Strangler Fig pattern for .NET Framework to .NET 8**  
Strangler Fig incrementally replaces legacy functionality by routing traffic through a facade until the legacy system can be decommissioned.  
Concrete strategy:
1. Put a reverse proxy/API Gateway in front of the .NET Framework monolith, e.g. YARP, NGINX, or HAProxy.
2. Identify bounded contexts or endpoints to extract first, such as reporting, auth, or a low-risk API.
3. Build the replacement as a .NET 8 service.
4. Route selected paths or headers to the new service while the rest go to the monolith.
5. Use an anti-corruption layer if the new service needs legacy data.
6. Use dual-write or read-through migration if data ownership changes.
7. Monitor, roll back if needed, then decommission the legacy module.

---

**AA11 — 12-Factor App methodology**  
The 12-Factor App is a set of principles for building portable, scalable, cloud-native applications. Important factors include:
1. **Codebase** — one tracked codebase per service.
2. **Dependencies** — explicitly declared and isolated.
3. **Config** — stored in environment variables, not code.
4. **Backing services** — databases, queues, APIs treated as replaceable resources.
5. **Build, release, run** — strict separation of stages.
6. **Stateless processes** — state stored externally.
7. **Port binding** — services expose themselves via ports.
8. **Concurrency** — scale by adding processes.
9. **Disposability** — fast startup and graceful shutdown.
10. **Dev/prod parity** — keep environments similar.
11. **Logs** — treat logs as event streams.
12. **Admin processes** — run management tasks as one-off processes.  
They matter for cloud-native deployments because they enable automation, horizontal scaling, immutable infrastructure, and reliable orchestration.

---

**AA12 — Event-driven Kafka vs request-driven REST/gRPC**

| Dimension | Event-driven with Kafka | Request-driven REST/gRPC |
|---|---|---|
| Coupling | Low; producers and consumers do not need to know each other | Higher; caller must know endpoint and availability |
| Scalability | High; buffering, fan-out, replay | Limited by synchronous request load |
| Debugging | Harder; async flows, eventual outcomes | Easier; request/response correlation |
| Ordering | Per-partition ordering only | No global ordering unless enforced by app |
| Failure handling | Retries, DLQs, idempotent consumers, eventual consistency | Timeouts, retries, circuit breakers, fallbacks |

Choose Kafka/event-driven for high-throughput integration, async workflows, audit logs, and fan-out. Choose REST/gRPC for synchronous user-facing operations, simple CRUD, and low-latency request/response.

---

**AA13 — Load balancer; L4 vs L7**  
A load balancer distributes traffic across multiple backend servers.  
- **Layer 4** load balancing routes based on IP address and TCP/UDP port. It does not inspect application content.
- **Layer 7** load balancing routes based on HTTP attributes such as URL path, headers, cookies, or host.  
Layer 7 is required for path-based routing, e.g. sending `/api` to one service and `/web` to another, or for WAF, authentication, and HTTP header manipulation.

---

**AA14 — Message queue vs log-based broker**  
A message queue stores messages until consumers process them, often deleting them after acknowledgment. RabbitMQ is a classic queue with point-to-point, pub/sub, priority, and complex routing.  
A log-based broker like Kafka stores an append-only log. Consumers track offsets and can replay messages.  
Pick RabbitMQ for task queues, low-latency work distribution, and complex routing. Pick Kafka for event streaming, replay, high throughput, and multiple independent consumers.

---

**AA15 — Container vs VM**  
A container is an isolated process using OS-level namespaces and cgroups. It shares the host kernel.  
A VM runs a full guest OS on a hypervisor.  
Containers are popular for microservices because they start quickly, are lightweight, package dependencies consistently, and fit well with orchestration platforms like Kubernetes.

---

**AA16 — Stateless vs stateful services**  
A stateless service does not store client session state locally; any instance can handle any request. A stateful service stores state locally or requires affinity.  
Stateless services scale horizontally easily because you can add or remove instances without moving session data.  
Example stateless: REST API using JWT and external database.  
Example stateful: local file cache, in-memory session store, or database primary.

---

**AA17 — ORM**  
An ORM maps objects in code to relational database tables, reducing boilerplate SQL.  
Examples: **Entity Framework Core** in .NET, **Hibernate** in Java, **SQLAlchemy** in Python.  
Trade-offs: ORMs improve productivity, maintainability, and safety, but can generate inefficient SQL, cause N+1 queries, and make complex performance tuning harder than raw SQL.

---

**AA18 — Bulkhead pattern**  
The Bulkhead pattern isolates resources so failure in one part of the system does not consume all capacity.  
In microservices, this can mean separate thread pools, connection pools, queues, or deployment groups.  
Example: a payment service and a search service share a gateway. Give payments a dedicated thread pool or separate deployment group so slow search requests cannot exhaust threads needed for payments.

---

**AA19 — OT vs CRDTs for collaborative editing**

| Dimension | Operational Transformation | CRDTs |
|---|---|---|
| Consistency | Often strong with central server | Eventual convergence without central authority |
| Latency | Can require server round-trips | Local edits apply immediately |
| Complexity | Complex transform algorithms, server coordination | Complex data structures and metadata overhead |
| Offline support | Harder; needs server or complex local OT | Native strength |

For a system that must support offline editing, choose **CRDTs** because they converge without requiring a central server to be online.

---

**AA20 — Distributed tracing in polyglot microservices**  
Challenges include propagating trace context across languages, frameworks, protocols, and asynchronous boundaries.  
- **Context propagation**: use W3C Trace Context headers (`traceparent`, `tracestate`) or legacy B3 headers.
- **Sampling**: head-based sampling decides at request entry; tail-based sampling decides after seeing the full trace, preserving errors or slow traces but requiring buffering.
- **Storage/querying**: Jaeger and Tempo store traces in backends like Cassandra, Elasticsearch, or object storage, enabling lookup by trace ID, service, tags, and latency.
- **Async messaging**: trace context must be injected into message headers. For Kafka, the producer injects `traceparent` into Kafka headers, and the consumer extracts it to continue the same trace. Without this, the trace breaks at the queue boundary.

## On-Premise Infrastructure Architecture

**OP1 — Type 1 vs Type 2 hypervisor**  
Type 1 hypervisors run directly on bare metal. Examples: **VMware ESXi**, **Proxmox VE/KVM**, **Xen**, **Microsoft Hyper-V Server**.  
Type 2 hypervisors run on top of a host OS. Examples: **VirtualBox**, **VMware Workstation**, **Parallels Desktop**.

---

**OP2 — SAN vs NAS**  
A SAN provides block-level storage, typically over **Fibre Channel** or **iSCSI**. Use it for databases, VMs, and workloads needing raw block devices.  
A NAS provides file-level storage, typically over **NFS** or **SMB**. Use it for shared files, home directories, backups, and collaborative file access.

---

**OP3 — 3-tier vs leaf-spine networking**  
3-tier architecture uses:
- **Core**: high-speed backbone.
- **Distribution**: aggregation, routing, policy.
- **Access**: edge ports for servers and users.  
Leaf-spine is preferred in modern data centers because east-west server-to-server traffic dominates. Leaf-spine provides predictable latency, non-blocking bandwidth, ECMP, and avoids many Spanning Tree limitations of 3-tier designs.

---

**OP4 — Highly available Proxmox cluster with shared storage**  
Use at least **3 nodes** for Proxmox HA quorum. With 2 nodes, use a quorum device such as `qdevice-net`.  
Enable fencing/STONITH, usually via IPMI, iDRAC, or iLO, so a failed node is powered off before resources restart elsewhere.  
Shared storage options:
- **Ceph**: replicated, self-healing, good for HA VMs.
- **iSCSI**: block storage, needs multipath and HA storage array.
- **NFS**: file-based, needs highly available NFS server.  
During node failure, Corosync detects the failure, fencing isolates the node, and HA manager restarts affected VMs on surviving nodes. If shared storage is unavailable, HA cannot start VMs.

---

**OP5 — VLAN trunking and 802.1Q**  
VLAN trunking carries multiple VLANs over one physical link. 802.1Q inserts a 4-byte tag containing the VLAN ID.  
On Linux, create VLAN subinterfaces:

```bash
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip link add link eth0 name eth0.30 type vlan id 30
ip addr add 10.0.10.10/24 dev eth0.10
ip link set eth0.10 up
```

The switch port must be configured as a trunk allowing VLANs 10, 20, and 30.

---

**OP6 — RAID levels and choice for a database server**

| RAID | Fault tolerance | Capacity | Notes |
|---|---:|---:|---|
| RAID 1 | 1 disk | 50% | Simple mirror, good read performance |
| RAID 5 | 1 disk | n-1 | Write penalty, risky with large disks |
| RAID 6 | 2 disks | n-2 | Better fault tolerance, write penalty |
| RAID 10 | 1 disk per mirror | 50% | High performance, good for databases |
| RAID Z2 | 2 disks | n-2 | ZFS double parity, checksums, good capacity |

For a 6-drive database server balancing performance and fault tolerance, choose **RAID 10** if write latency and random I/O matter. Choose RAID Z2 or RAID 6 only if capacity is more important than database write performance.

**OP7 — DNS architecture for enterprise with AD, DMZ, split-horizon, DNSSEC**  
Internal architecture:
- Active Directory DNS servers are authoritative for internal zones and recursive resolvers for internal clients.
- Use forwarders to external DNS or root hints.
- Use conditional forwarding for DMZ, partner, or special internal zones.

DMZ/public architecture:
- Public authoritative DNS servers host public zones.
- External zone is DNSSEC-signed with DS records in the parent zone.
- Internal clients may use split-horizon DNS to resolve public names to internal IPs.

Laptop behavior:
- In the office, DHCP gives internal DNS servers.
- On VPN, the VPN profile should push internal DNS servers or route DNS to internal resolvers.
- If the laptop uses external DNS, conditional forwarding from internal resolvers to AD zones is needed.  
Avoid exposing AD DNS directly to the internet. DNSSEC validation works for external signed zones; internal split-horizon answers must either use separate internal names or be signed consistently to avoid validation issues.

---

**OP8 — PKI chain of trust and internal PKI deployment**  
Chain: **Root CA → Subordinate/Issuing CA → End-entity certificate**.  
Best practice:
- Keep the **root CA offline** and store its private key securely.
- Use an online **subordinate/issuing CA** to issue certificates.
- Use **certificate templates** to define key usage, extended key usage, validity, and enrollment rules.
- Use **auto-enrollment** via Active Directory Group Policy for domain-joined machines.
- Use **CRL** for published revocation lists and **OCSP** for online status checks; OCSP stapling improves performance.

Compromise consequences:
- **Compromised subordinate CA**: revoke the subordinate CA certificate, publish CRL/OCSP, reissue certificates. Damage is significant but limited to that CA’s issued certificates.
- **Compromised root CA**: catastrophic. All certificates chaining to that root may become untrusted, requiring replacement of the root trust anchor across all clients and systems.

**OP9 — WAN options for 5 remote offices**

| Option | Cost | Reliability | Latency | Management complexity | Security |
|---|---:|---:|---:|---:|---|
| MPLS | High | High | Predictable | Low/medium, provider-managed | Private, strong |
| IPsec over internet | Low | Variable | Variable | Medium | Strong encryption, depends on internet |
| SD-WAN | Medium | High with multiple links | Improved with path selection | Medium/high | Strong, policy-driven |
| WireGuard mesh | Low | Depends on underlay | Depends on underlay | Low/medium | Strong, simple |

For 50 users per site with latency-sensitive VoIP, recommend **SD-WAN with business-grade internet links and QoS**. If strict SLAs are required, add MPLS or a dedicated link for voice. WireGuard is secure and simple but lacks enterprise-grade QoS and traffic engineering out of the box.

---

**OP10 — iDRAC/iLO/IPMI**  
iDRAC, iLO, and IPMI are out-of-band management interfaces on server BMCs. They allow remote power control, console access, firmware updates, and hardware monitoring even if the OS is down.  
Out-of-band management is critical for recovery when servers are unresponsive.  
If IPMI is exposed to the internet, attackers can brute-force credentials, exploit BMC vulnerabilities, and gain full server control. Management interfaces should be isolated on a dedicated management VLAN, firewalled, patched, and protected with MFA where possible.

---

**OP11 — LVM, LVM-Thin, ZFS**  
- **LVM**: traditional logical volumes over block devices. Snapshots are copy-on-write and require reserved space.
- **LVM-Thin**: thin-provisioned logical volumes with overcommit and snapshots. Snapshots are also copy-on-write but can grow dynamically.
- **ZFS**: integrated filesystem and volume manager with pools, RAID-Z, checksums, compression, and snapshots. ZFS snapshots are read-only, metadata-based, and support rollback and clones.

Use LVM for simple volume management, LVM-Thin for overcommit and flexible provisioning, and ZFS when data integrity, snapshots, RAID, and compression are important.

---

**OP12 — Stretch cluster or DR for 3-node Proxmox/Ceph**  
A 3-node cluster split across two sites is fragile for synchronous site failure.  
For a stretch cluster:
- Proxmox HA needs quorum. A 2+1 node split loses quorum if the 2-node site fails unless a quorum witness/qdevice exists.
- Ceph monitors need quorum. Use monitors across sites plus a tiebreaker/witness, often at a third site or cloud.
- CRUSH rules should use `failure_domain=datacenter` and ensure replicas are distributed.
- Synchronous Ceph replication requires low latency, often under ~10 ms RTT, and high bandwidth.
- Split-brain can occur during network partition if both sites think they are healthy. A tiebreaker prevents the minority site from forming quorum.

2-site Ceph without a tiebreaker is generally a bad idea because quorum can be lost or split-brain can occur. For many environments, asynchronous DR using Ceph RBD mirroring, backups, or restore-based DR is safer than synchronous 2-site stretch.

---

**OP13 — DHCP and DORA**  
DHCP dynamically assigns IP addresses. DORA is:
1. **Discover** — client broadcasts for DHCP servers.
2. **Offer** — server offers an address.
3. **Request** — client requests the offered address.
4. **Acknowledge** — server confirms the lease.  
If the DHCP server is unavailable and a Windows client’s lease expires, the client assigns itself an APIPA address in the `169.254.0.0/16` range. It usually loses default gateway and DNS configuration, so it cannot reach normal network resources.

---

**OP14 — Managed vs unmanaged switch**  
An unmanaged switch is plug-and-play with no configuration.  
A managed switch allows configuration and enterprise features such as VLANs, trunking, QoS, Spanning Tree, port mirroring, SNMP monitoring, ACLs, LACP, port security, and 802.1X. These are important for segmentation, reliability, troubleshooting, and security.

---

**OP15 — NTP and clock drift**  
NTP synchronizes system clocks across servers. Accurate time is critical for authentication, logging, clustering, replication, certificate validation, and distributed consensus.  
Clock drift can cause Kerberos failures, log correlation problems, database replication issues, cluster quorum problems, and certificate validation errors.

---

**OP16 — Physical server, VM, container**  
A physical server runs directly on hardware.  
A VM runs a full guest OS on a hypervisor.  
A container runs isolated processes sharing the host kernel.  
Run workloads on bare metal when you need maximum performance, low latency, direct GPU/NVMe access, strict licensing, hardware encryption, or predictable I/O without virtualization overhead.

---

**OP17 — UPS, generator, ATS**  
A UPS provides short-term battery power and power conditioning during outages.  
A generator provides long-term power after the UPS battery is exhausted.  
An ATS automatically transfers electrical load from utility power to generator power. You need both because the UPS bridges the gap while the generator starts and stabilizes.

---

**OP18 — Active-passive vs active-active HA with PostgreSQL**  
Active-passive has one node serving traffic while the standby waits to take over. Active-active has multiple nodes serving traffic simultaneously.  
For two Linux PostgreSQL servers using Pacemaker/Corosync:
- Corosync provides cluster messaging.
- Pacemaker manages resources.
- A virtual IP resource moves to the active node.
- STONITH fencing powers off the failed node to prevent split-brain.
- On failure, Pacemaker fences the failed node, moves the VIP, and starts PostgreSQL on the surviving node.

For PostgreSQL, active-passive is simpler. True active-active PostgreSQL is complex and usually requires multi-master replication, sharding, or application-level coordination.

---

**OP19 — Backup and recovery strategy for 50 servers**  
Use the **3-2-1 rule**: 3 copies of data, on 2 media types, with 1 offsite.  
Define **RPO** — maximum acceptable data loss — and **RTO** — maximum acceptable downtime.  
Backup types:
- **Full**: complete copy.
- **Incremental**: changes since last backup.
- **Differential**: changes since last full backup.  
Use deduplication to reduce storage. Disk gives fast restores, tape gives cheap long-term retention, and cloud provides offsite durability. Use immutable backups, such as object-lock or air-gapped copies, for ransomware protection.  
Test restores regularly, including full DR drills.  
Backup is data protection. Disaster recovery is the broader process of restoring infrastructure, applications, and operations.

---

**OP20 — 802.1X and MAB**  
802.1X provides port-based network access control.  
Roles:
- **Supplicant**: client device requesting access.
- **Authenticator**: switch or wireless controller enforcing access.
- **Authentication server**: usually RADIUS, validating credentials or certificates.

EAP methods:
- **EAP-TLS**: mutual certificate-based authentication; strong.
- **PEAP**: server certificate plus inner username/password; common but weaker than EAP-TLS.

RADIUS carries EAP messages and can return dynamic VLAN assignment attributes.  
If a device fails authentication, it can be blocked or placed in a guest VLAN.  
MAB, MAC Authentication Bypass, is used for devices that cannot run 802.1X, such as printers or phones. The switch sends the device’s MAC address to RADIUS as a credential, and RADIUS decides whether to allow access and assign a VLAN.
