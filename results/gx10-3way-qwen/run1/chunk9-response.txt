## SC1 — Broken Deployments After Cluster Upgrade

### SC1-A
The pods fail because the namespace now enforces the **Restricted Pod Security Standard (PSS)**, which is stricter than **Baseline**.

- **Baseline** blocks privileged containers, host namespaces, hostPath volumes, etc., but does **not** require containers to run as non-root.
- **Restricted** additionally requires:
  - `securityContext.runAsNonRoot: true`
  - `allowPrivilegeEscalation: false`
  - `capabilities.drop: ["ALL"]`
  - `seccompProfile.type: RuntimeDefault`
  - no host namespaces, restricted volume types, etc.

In your pods:

```yaml
securityContext:
  runAsNonRoot: true
```

but no `runAsUser` is set. Kubernetes then uses the container image’s `USER` directive. The new Chainguard base image defaults to `USER root`, i.e. UID 0.

The PodSecurity admission controller may accept the pod because it cannot always inspect the image’s effective user at admission time. At runtime, kubelet sees:

- `runAsNonRoot: true`
- effective image user: root

and refuses to start the container, producing errors like:

```text
container has runAsNonRoot and image will run as root
```

That causes `CrashLoopBackOff`.

```bash
kubectl get pods -A -o json | jq -c '[.items[] | select(any(.status.containerStatuses[]?; .state.waiting.reason == "CrashLoopBackOff")) | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: {pod: .spec.securityContext, containers: [.spec.containers[] | {name, securityContext}]}}]'
```

### SC1-C
**Immediate fix**

Option 1: Override the image user in the pod spec:

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 65532
    runAsGroup: 65532
    fsGroup: 65532
  containers:
    - name: app
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
        seccompProfile:
          type: RuntimeDefault
```

Option 2, preferred: rebuild the image with a non-root user:

```dockerfile
USER 65532
```

or use a nonroot Chainguard/Distroless image.

**Manifest changes**

Add to all affected Deployments:

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 65532
  runAsGroup: 65532
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
```

**CI gate**

Add pipeline checks:

1. Fail if Dockerfile uses `USER root` or omits `USER`.
2. Use Trivy or Hadolint to detect root-user images.
3. Require base images pinned by digest.
4. Use Kyverno/OPA Gatekeeper to reject pods where:
   - `runAsNonRoot` is false, or
   - `runAsUser` is `0`.

Example Kyverno rule concept:

```yaml
validate:
  message: "runAsUser must not be 0"
  pattern:
    spec:
      containers:
        - securityContext:
            =(runAsUser): "!0"
```

**Zero-downtime rollout**

Use rolling updates:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

Roll out one namespace or one service first, monitor CrashLoopBackOff, then proceed. If failures continue, rollback with:

```bash
kubectl rollout undo deployment/<name> -n <namespace>
```

## SC2 — Cross-Region Database Failover Gone Wrong

### SC2-A
The stale data is caused by **asynchronous cross-region replication lag**.

PostgreSQL streaming replication works by shipping WAL records from the primary to the replica. The replica replays WAL and applies changes. With asynchronous replication:

1. Primary commits transaction locally.
2. Primary returns success to client.
3. WAL is shipped to replica later.
4. Replica replays WAL.

If the primary fails before WAL is shipped/replayed, those transactions are lost.

When you promoted the eu-west-1 replica, it only contained data up to its last replayed WAL position. Any writes committed in us-east-1 after that point were lost.

Possible causes of “stale data” after promotion:

- Replica promotion lag.
- Application caches still holding old data.
- PgBouncer holding connections to old endpoints.
- Read replicas still being queried.
- DNS caching pointing to old primary.

**Quantify the data loss window**

Check on the replica before promotion, if available:

```sql
SELECT
  pg_last_wal_receive_lsn(),
  pg_last_wal_replay_lsn(),
  pg_last_xact_replay_timestamp();
```

Also check:

```sql
SELECT
  client_addr,
  state,
  sent_lsn,
  write_lsn,
  flush_lsn,
  replay_lsn,
  replay_lag
FROM pg_stat_replication;
```

For RDS, check CloudWatch metrics:

- `ReplicaLag`
- `ReplicaLagMilliseconds`
- `FreeableMemory`
- `CPUUtilization`

Also compare application transaction logs or audit logs against the replica’s `pg_last_xact_replay_timestamp()`.

### SC2-C
**Recommended architecture**

Use:

- Aurora Global Database or RDS Multi-AZ + cross-region read replica, depending on RPO requirements.
- RDS Proxy in each region.
- Route53 health checks with DNS failover.
- Application-level retry, circuit breaker, and connection pool reset.
- Secrets Manager or IAM authentication for DB credentials.

**RDS Proxy vs PgBouncer**

RDS Proxy is preferable for AWS-managed failover:

- Managed connection pooling.
- Faster failover.
- IAM authentication.
- Secrets Manager integration.
- Connection draining.
- Less operational burden.

PgBouncer is useful when:

- You need cross-region or self-managed pooling.
- You need query-mode pooling.
- You want more control over server lifetime and DNS behavior.

For this failure class, RDS Proxy reduces connection storms and login retry errors during promotion.

**Route53 health checks**

Use a failover routing policy:

- Primary: us-east-1 DB endpoint or RDS Proxy.
- Secondary: eu-west-1 DB endpoint or RDS Proxy.
- Health check: TCP/HTTP check against proxy or application health endpoint.
- Low TTL, e.g. 30 seconds.
- Health check should validate DB reachability, not just TCP connect.

**Application retry logic**

Applications should:

- Use short connect timeouts.
- Retry with exponential backoff and jitter.
- Reset connection pools after failover.
- Use idempotent writes where possible.
- Use circuit breakers.
- Avoid long-lived cached DB endpoints.

**RPO < 1 second**

Standard RDS cross-region read replicas are asynchronous and cannot guarantee RPO < 1 second.

For RPO < 1 second, use **Aurora Global Database**.

Aurora Global Database provides:

- Cross-region physical replication.
- Low replication lag.
- Managed failover.
- Better RPO/RTO than standard RDS cross-region replicas.

If strict zero data loss is required, synchronous replication is needed, but cross-region synchronous replication increases commit latency and reduces availability. Aurora Global Database is the best balance for RPO < 1 second across regions.

```bash
API_LAYERS=$(skopeo inspect --raw docker://"$API_IMAGE" | jq -r '.layers[].digest')

if [[ ! -f "$KNOWN_GOOD_LAYERS" ]]; then

echo "Comparing layers against known-good build..."

while IFS= read -r layer; do
  if ! grep -qxF "$layer" "$KNOWN_GOOD_LAYERS"; then
    echo "UNEXPECTED LAYER: $layer"
    UNEXPECTED=1
```

- Image signed by trusted key.
- SBOM attestation present.

```yaml

  name: verify-images
```

## SC4 — Migrating a Stateful Monolith to Kubernetes

### SC4-A
**Top 5 blockers**

1. **In-memory sessions with F5 sticky sessions**

   Problem: Kubernetes pods are ephemeral. Restarts, scaling, and rescheduling lose session state.

   Solution: externalize sessions to Redis or Memcached, or use stateless JWTs. Sticky sessions can be a temporary migration aid but should not be the final design.

2. **Local file uploads on `/data/uploads`**

   Problem: local filesystem paths are not portable across pods and nodes.

   Solution: migrate uploads to object storage such as S3/MinIO, or use an NFS CSI driver with `ReadWriteMany` PVC. Object storage is preferred for scalability.

3. **On-prem Oracle 19c database**

   Problem: Oracle is stateful, licensed, and not trivially containerized. Latency and HA must be preserved.

   Solution: keep Oracle on-prem initially, connect Kubernetes pods over secure network, use connection pooling, and migrate later to RDS/Aurora or Oracle Cloud if desired.

4. **IBM MQ mainframe integration**

   Problem: MQ is stateful, transactional, and network-sensitive.

   Solution: keep MQ on-prem initially. Use MQ client libraries in pods, secure network connectivity, idempotent consumers, and possibly bridge MQ to Kafka later.

5. **Java 11 monolith resource and lifecycle behavior**

   Problem: JVM startup time, memory footprint, health checks, graceful shutdown, and load balancer integration may not match Kubernetes expectations.

   Solution: containerize with JVM tuning, readiness/liveness probes, graceful shutdown, HPA, and blue-green/canary deployment.

### SC4-C
**Phased Strangler Fig migration**

**Phase 0: Foundation**

- Build Kubernetes cluster.
- Set up CI/CD, observability, secrets, networking.
- Establish connectivity to Oracle and IBM MQ.
- Deploy non-critical read-only endpoints to Kubernetes.

**Phase 1: Stateless/read-only traffic**

Move:

- Static content.
- Read-only APIs.
- Health/status endpoints.
- Non-session endpoints.

Traffic split:

- F5 sends a small percentage to Kubernetes Ingress.
- Use weighted DNS or F5 pool weights.
- Keep Oracle and MQ unchanged.

Go/no-go metrics:

- Error rate < 0.1%.
- p99 latency < 2 seconds.
- No increase in Oracle connection errors.
- No upload failures.

**Phase 2: Session and upload migration**

Move:

- Application tier.
- Session store to Redis.
- Uploads to object storage or NFS CSI.

Traffic split:

- Gradually shift authenticated traffic.
- Use feature flags.
- Maintain dual-write or compatibility layer for uploads if needed.

Go/no-go metrics:

- Session loss rate near zero.
- Upload success rate > 99.9%.
- Login success rate unchanged.
- p99 latency within SLA.

**Phase 3: MQ and async workers**

Move:

- MQ consumers/producers.
- Background jobs.
- Mainframe integration adapters.

Approach:

- Keep MQ on-prem.
- Use idempotent consumers.
- Drain queues before cutover.
- Use dual consumers only if safe.

Go/no-go metrics:

- MQ backlog stable.
- Duplicate message rate acceptable.
- Mainframe transaction success rate unchanged.
- End-to-end business transaction latency within SLA.

**Zero-downtime cutover**

- Keep legacy and Kubernetes running in parallel.
- Use DNS/F5 weighted routing.
- Use feature flags.
- Use database-compatible schema changes.
- Avoid destructive changes during migration.

**Rollback**

- Shift F5/DNS weights back to legacy.
- Disable feature flags.
- Keep legacy app warm.
- Restore previous Helm release or Kubernetes deployment.
- For MQ, resume legacy consumers and pause Kubernetes consumers.

## SC5 — Mysterious Latency Spike in Microservices

### SC5-A
**Systematic debugging approach**

1. Correlate spike with CronJobs, deployments, batch jobs, and database maintenance.
2. Check distributed traces for checkout-service → inventory-service.
3. Compare:
   - checkout-service client span duration.
   - Istio sidecar span duration.
   - inventory-service server span duration.
   - database query duration.
4. Check Kubernetes events around 14:00 UTC.
5. Check database lock waits and connection pool saturation.

**Istio metrics**

Check:

```promql
istio_request_duration_milliseconds_bucket
istio_requests_total
istio_tcp_connections_opened_total
istio_tcp_pending_bytes
```

Filter by:

```promql
destination_service="inventory-service"
```

**Envoy metrics distinguishing proxy queueing vs upstream latency**

Proxy/connection-pool queueing:

- `upstream_cx_overflow`
- `upstream_rq_pending_overflow`
- `upstream_cx_pool_overflow`
- `upstream_cx_connect_timeout`
- `downstream_cx_overflow`

Upstream application latency:

- High `upstream_service_time` or `upstream_rq_time`.
- High server-side span duration in Jaeger.
- High database query duration.

Response flags:

- `UF`: upstream failure.
- `URX`: upstream reset.
- `DC`: downstream connection termination.
- `UT`: upstream request timeout.

If `upstream_service_time` is high, inventory-service is slow. If pending/overflow metrics are high, the sidecar or connection pool is queueing.

### SC5-B
**PostgreSQL lock diagnostic query**

```sql
SELECT
  blocked_locks.pid AS blocked_pid,
  blocked_activity.query AS blocked_query,
  blocked_activity.query_start AS blocked_query_start,
  blocked_activity.state AS blocked_state,
  blocking_locks.pid AS blocking_pid,
  blocking_activity.query AS blocking_query,
  blocking_activity.query_start AS blocking_query_start,
  blocking_activity.state AS blocking_state,
  blocked_locks.locktype,
  blocked_locks.mode AS blocked_lock_mode,
  blocking_locks.mode AS blocking_lock_mode,
  blocked_locks.granted AS blocked_granted
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity
  ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks
  ON blocking_locks.locktype = blocked_locks.locktype
 AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
 AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
 AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
 AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
 AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
 AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
 AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
 AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
 AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
 AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity
  ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

Simpler version using `pg_blocking_pids`:

```sql
SELECT
  blocked.pid AS blocked_pid,
  blocked.query AS blocked_query,
  blocked.query_start AS blocked_query_start,
  blocking.pid AS blocking_pid,
  blocking.query AS blocking_query,
  blocking.query_start AS blocking_query_start,
  blocking.state AS blocking_state
FROM pg_stat_activity blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) AS blocking_pid(pid) ON true
JOIN pg_stat_activity blocking ON blocking.pid = blocking_pid.pid
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;
```

```go
	ReadyToTrip: func(counts gobreaker.Counts) bool {
		if counts.ConsecutiveFailures > 5 {
			return true
		}
		if counts.Requests > 100 {
			failureRatio := float64(counts.TotalFailures) / float64(counts.Requests)
			return failureRatio > 0.10
		}
		return false
	},
})

func CallInventory(ctx context.Context, req *InventoryRequest) (*InventoryResponse, error) {
	resp, err := inventoryBreaker.Execute(func() (interface{}, error) {
		callCtx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
		defer cancel()

		return inventoryClient.GetInventory(callCtx, req)
	})

	if err != nil {
		return nil, err
	}

	return resp.(*InventoryResponse), nil
}
```

### SC5-C
**Architectural solution**

1. **CQRS / read-write separation**

   - Serving path reads from a read model, cache, or read replica.
   - Reconciliation writes to a separate batch path.
   - Checkout-service should not depend on the same hot table used by batch reconciliation.

2. **Read replica for reconciliation**

   Run the CronJob against a PostgreSQL read replica or analytics database.

3. **Bulkhead isolation**

   Use separate connection pools:

   - Serving pool: low latency, small max connections.
   - Batch pool: limited concurrency, longer timeouts.

   Use PgBouncer pools per workload.

4. **CronJob scheduling**

   - Move off peak.
   - Use `concurrencyPolicy: Forbid`.
   - Add `activeDeadlineSeconds`.
   - Add `backoffLimit`.
   - Use smaller transactions.
   - Add `lock_timeout` and `idle_in_transaction_session_timeout`.

5. **Kubernetes protections**

Use lower priority for batch:

```yaml
priorityClassName: batch-low
```

Use ResourceQuota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: batch-quota
  namespace: batch
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 4Gi
    limits.cpu: "4"
    limits.memory: 8Gi
```

Use LimitRange to cap batch pods.

PodDisruptionBudgets protect serving pods during voluntary disruptions, but they do not prevent resource starvation. Use PriorityClass and quotas to prevent CronJobs from starving serving pods.

## SC6 — Zero-Trust Network Overhaul for a Hybrid Environment

### SC6-A
**Identity and access layer**

Use a federated workload identity model based on SPIFFE/SPIRE.

**SPIFFE/SPIRE**

- Each environment runs a SPIRE server or federated trust domain.
- Each node runs a SPIRE agent.
- Workloads receive short-lived SVIDs:
  - X.509 SVIDs for mTLS.
  - JWT-SVIDs for API authentication.

Workload identity examples:

```text
spiffe://prod.example.com/ns/checkout/sa/api
spiffe://aws/prod/ec2/i-0123456789abcdef0
spiffe://azure/prod/vm/checkout-vm
spiffe://onprem/vsphere/vm/legacy-service
```

**AWS integration**

- EKS workloads use IRSA: Kubernetes service account → AWS IAM role.
- EC2 workloads use instance identity attestation.
- SPIRE can issue SPIFFE IDs that map to IAM roles.

**Azure integration**

- Azure VMs use Managed Identities.
- AKS workloads use Azure Workload Identity.
- SPIRE can attest Azure VMs using platform identity.

**On-prem integration**

- Use vSphere VM identity, TPM, or join tokens.
- Use internal PKI for bootstrap.
- SPIRE issues workload SVIDs.

**Federation**

Use SPIRE federation so trust bundles are exchanged across environments.

Example flow:

1. AWS workload obtains SPIFFE JWT-SVID.
2. AWS workload calls on-prem service over mTLS or bearer JWT.
3. On-prem service validates JWT-SVID using federated SPIRE bundle.
4. On-prem service maps SPIFFE ID to least-privilege authorization policy.

No shared secrets are required.

### SC6-C
**Option comparison**

| Option | Cost | Bandwidth | Encryption | Failover | Zero-trust fit | Routing changes |
|---|---:|---:|---|---|---|---|
| AWS Direct Connect | Higher: port, cross-connect, data transfer | 1/10/100 Gbps, predictable | IPsec or MACsec | Excellent with redundant DX + TGW | Good transport layer; still needs workload identity | TGW route tables, BGP, private prefixes |
| Second VPN tunnel / ECMP | Low | Up to ~1.25 Gbps aggregate, internet-dependent | IPsec | Good, but internet variability | Transport encryption only | TGW ECMP or BGP AS prepend, health checks |
| Tailscale/Netbird mesh | Per-device/user licensing | Variable, often relay-limited | WireGuard | Good for admin access, not ideal for bulk DR | Strong identity/ACL model | Agent routes, advertised subnets, policy routing |

**Recommendation**

- Use **Direct Connect** for production inter-site traffic.
- Keep **Site-to-Site VPN** as backup.
- Use **Tailscale/Netbird** for administrative access or developer zero-trust access, not primary data replication.

For Direct Connect:

- Create redundant DX connections.
- Attach to Transit Gateway.
- Use separate TGW route tables for production/staging.
- Use BGP with health checks.
- Keep VPCs private.
- Use PrivateLink for AWS services.

For second VPN:

- Use TGW with two VPN connections or dual tunnels.
- Use BGP AS prepend for active/passive.
- Use health checks.
- Do not rely on it for high-throughput DR.

For mesh:

- Install agents on gateway VMs.
- Advertise on-prem and cloud CIDRs.
- Use ACLs based on identity.
- Avoid using it for 200TB replication or latency-sensitive DB traffic.

## SC7 — CI/CD Pipeline Causing Production Drift

### SC7-A
**Drift sources**

1. **Manual `tofu apply` from laptops**

   Developers changed live infrastructure without Git changes. Git no longer represents reality.

   Dangers:

   - No review.
   - No audit trail.
   - No rollback artifact.
   - State may be updated locally but not shared.
   - Security controls bypassed.

2. **Helm values divergence**

   Staging/production values changed outside Git.

   Dangers:

   - Different environments behave differently.
   - Rollbacks may revert unknown changes.
   - Security settings may drift.
   - Reproducibility is lost.

3. **Direct `kubectl edit` on ConfigMaps**

   Live Kubernetes objects changed without Git/Helm/OpenTofu.

   Dangers:

   - Next deployment may overwrite or conflict.
   - Secrets/config may be inconsistent.
   - No provenance.
   - Compliance violation.

**State locking danger**

Without state locking, two engineers can run `tofu apply` simultaneously.

Sequence:

1. Engineer A reads state.
2. Engineer B reads same state.
3. A applies changes and writes state.
4. B applies changes and overwrites A’s state.

Consequences:

- Last write wins.
- Resources may be orphaned.
- Resources may be duplicated.
- State may become inconsistent with cloud.
- Terraform/OpenTofu may plan destructive changes later.
- Partial applies can leave infrastructure broken.

## SC9 — Securing a Public-Facing API After a Breach

### SC9-A
**1. BOLA**

OWASP API Top 10: **API1: Broken Object Level Authorization**.

Blast radius:

- Users access other users’ records.
- Mass data exposure.
- Account takeover if sensitive records are exposed.

Fix: enforce object-level authorization.

Django REST Framework example:

```python
from rest_framework.views import APIView
from rest_framework.permissions import IsAuthenticated
from rest_framework.exceptions import PermissionDenied
from django.shortcuts import get_object_or_404

class OrderDetailView(APIView):
    permission_classes = [IsAuthenticated]

    def get_object(self):
        order = get_object_or_404(Order, pk=self.kwargs["pk"])

        if order.user_id != self.request.user.id and not self.request.user.is_staff:
            raise PermissionDenied("You do not have access to this object.")

        self.check_object_permissions(self.request, order)
        return order

    def get(self, request, pk):
        order = self.get_object()
        serializer = OrderSerializer(order)
        return Response(serializer.data)
```

**2. Full database objects returned**

OWASP API Top 10: **API3: Broken Object Property Level Authorization**, which includes excessive data exposure.

Blast radius:

- Internal fields leak.
- Business logic exposure.
- Privilege escalation clues.

Fix: use explicit serializers/DTOs.

```python
class OrderSerializer(serializers.ModelSerializer):
    class Meta:
        model = Order
        fields = [
            "id",
            "status",
            "total",
            "created_at",
        ]
```

Never use:

```python
fields = "__all__"
```

for public APIs.

**3. No rate limiting**

OWASP API Top 10: **API4: Unrestricted Resource Consumption**.

Blast radius:

- Mass scraping.
- Data exfiltration.
- DoS.

Fix:

- WAF rate limiting.
- DRF throttling.
- API gateway rate limits.
- Per-user and per-IP limits.
- Anomaly detection.

**4. API keys in query parameters**

OWASP API Top 10: **API2: Broken Authentication**, and also credential leakage.

Blast radius:

- Keys logged in ALB, CloudWatch, proxies, browser history.
- Credential reuse.
- Account takeover.

Fix:

- Move keys to `Authorization` header.
- Rotate all compromised keys.
- Scrub logs.
- Move to OAuth2/JWT.

### SC9-C
**Defense-in-depth architecture**

1. **Move API keys to headers**

Use:

```http
Authorization: Bearer <token>
```

or:

```http
X-API-Key: <key>
```

Prefer `Authorization`.

2. **Rotate compromised keys**

- Generate new keys.
- Disable old keys.
- Force consumers to update.
- Audit usage of old keys.
- Scrub logs containing query-string keys.

3. **OAuth2 with short-lived JWTs**

Use:

- Client credentials flow for machine-to-machine.
- Authorization code flow for users.
- Short-lived access tokens, e.g. 5–15 minutes.
- Refresh tokens where needed.
- JWKS endpoint for validation.
- Scopes for least privilege.

4. **API gateway**

Put Kong or AWS API Gateway in front of ALB.

Centralize:

- Authentication.
- Authorization.
- Rate limiting.
- Request transformation.
- API key removal.
- JWT validation.
- Logging.
- WAF integration.

5. **CloudTrail and audit logging**

Enable:

- CloudTrail data events for relevant AWS resources.
- ALB access logs.
- WAF logs.
- API Gateway access logs.
- Application audit logs.

Do not log secrets.

6. **Field-level encryption for PII**

Use:

- AWS KMS envelope encryption.
- Django field encryption.
- Deterministic encryption only where search is required.
- Separate encryption keys per data class.
- Key rotation.

**Migration from API keys to OAuth2**

Use a dual-auth period:

1. API gateway accepts both:
   - Legacy API key in header.
   - OAuth2 JWT.
2. Rate-limit legacy keys aggressively.
3. Notify consumers.
4. Require OAuth2 for new consumers.
5. Disable legacy keys after sunset date.

This avoids breaking existing consumers while enforcing a secure end state.

## SC10 — Multi-Cluster Disaster Recovery Platform

### SC10-A
**Active-passive with Velero**

Velero backs up Kubernetes resources and persistent volumes.

Pros:

- Simple.
- Good for stateless or small-state workloads.

Cons:

- RPO depends on backup frequency.
- RTO depends on restore time.
- Restoring 200TB MinIO data in 1 hour is unrealistic.
- Velero is not ideal for large object storage DR.

RPO/RTO:

- RPO: likely > 15 minutes unless backups run every few minutes.
- RTO: likely > 1 hour for 200TB unless data is already replicated.

**Active-active with service mesh**

Use Istio multi-cluster or Cilium Cluster Mesh.

Pros:

- Stateless services can run in both sites.
- DNS/GSLB can fail over in minutes.
- RTO can meet 1 hour.
- RPO depends on stateful replication.

Cons:

- More complex.
- Stateful components still need replication.
- Cross-site latency affects consensus systems.

With 12ms latency:

- PostgreSQL synchronous replication adds ~12ms commit latency, acceptable.
- Redis Sentinel async replication may have seconds of RPO.
- RabbitMQ WAN clustering is risky; use federation/shovel or carefully designed quorum queues.
- MinIO site replication can meet RPO 15 minutes if replication lag stays below 15 minutes.

**Stateful replication strategy**

PostgreSQL:

- Patroni streaming replication.
- Synchronous standby for zero data loss, or async with lag monitoring for RPO 15 minutes.

Redis:

- Redis Sentinel or Redis Cluster with cross-site replicas.
- Accept small RPO unless synchronous replication is used.

RabbitMQ:

- Prefer independent clusters with federation/shovel.
- Use idempotent consumers.
- Monitor queue lag.

MinIO:

- Active-active site replication.
- Versioning enabled.
- Monitor replication lag.
- Initial 200TB seeding over 10Gbps takes roughly 44 hours theoretical; ongoing replication must keep lag < 15 minutes.

**Conclusion**

Active-active with replicated state is the only realistic way to meet RPO 15 minutes and RTO 1 hour for 200TB object storage.

### SC10-C
**Automated failover sequence**

1. **Failure detection**

   Monitors:

   - Prometheus blackbox probes.
   - Patroni health API.
   - etcd quorum.
   - Redis Sentinel status.
   - RabbitMQ health.
   - MinIO replication lag.
   - DNS/GSLB health checks.
   - Application synthetic transactions.

   “Site down” should require:

   - Multiple independent probes.
   - Quorum agreement.
   - Sustained failure, e.g. 2–3 minutes.
   - No false positive from single network path.

2. **DNS/GSLB failover**

   - GSLB health checks mark Chicago unhealthy.
   - DNS TTL is low, e.g. 30 seconds.
   - Traffic shifts to Dallas.
   - Application clients reconnect.

3. **PostgreSQL failover**

   - Patroni detects primary loss.
   - If etcd quorum exists in Dallas, Dallas standby promotes.
   - Synchronous mode ensures no committed transaction is lost.
   - Applications reconnect via DNS or connection pooler.

4. **Redis failover**

   - Sentinel detects master down.
   - Replica promoted.
   - Clients update topology via Sentinel.
   - Monitor replication lag and possible lost writes.

5. **RabbitMQ failover**

   - If using federation/shovel, Dallas queues continue accepting messages.
   - Consumers switch to Dallas.
   - Chicago queues are drained when site recovers.
   - Consumers must be idempotent.

6. **MinIO failover**

   - Dallas site becomes writable.
   - Chicago becomes read-only or paused.
   - Site replication catches up when Chicago returns.
   - Monitor object version conflicts.

7. **OpenTofu state update**

   - CI pipeline updates variables:
     - `primary_region = dallas`
     - `dns_primary = dallas`
   - Apply changes to DNS, security groups, load balancers.
   - Do not manually edit state.

**Split-brain handling**

- Require etcd quorum for Patroni promotion.
- Use `synchronous_mode_strict: true`.
- Use STONITH/fencing where possible.
- DNS/GSLB should only point to one writable site.
- MinIO site replication must resolve conflicts deterministically.
- RabbitMQ must avoid dual active consumers writing conflicting state.
- Applications should use idempotency keys.

**Failback to Chicago**

1. Verify Chicago infrastructure is healthy.
2. Attach Chicago PostgreSQL as standby.
3. Catch up WAL.
4. Verify replication lag is zero.
5. Attach Redis replica and catch up.
6. Reconnect RabbitMQ federation/shovel.
7. Resume MinIO replication from Dallas to Chicago.
8. Run read-only validation in Chicago.
9. Drain Dallas writes.
10. Promote Chicago PostgreSQL.
11. Switch DNS/GSLB back to Chicago.
12. Update OpenTofu state.
13. Monitor error rate, latency, replication lag, and business transactions.
