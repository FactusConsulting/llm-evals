## OpenTofu / Terraform

**T1 — Easy: What is the difference between `tofu plan` and `tofu apply`?**  
`tofu plan` previews the changes OpenTofu will make by comparing configuration, state, and real infrastructure. It does not create, update, or delete resources unless you use special modes. `tofu apply` executes the planned changes, creates/updates/deletes resources, and writes the resulting state.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**  
State is OpenTofu’s mapping between configuration resources and real infrastructure, including IDs, attributes, dependencies, and metadata. Remote state is important for team collaboration, consistency, locking, backup, and avoiding conflicting local state files.

**T3 — Medium: Explain the difference between `count` and `for_each`. When is `for_each` preferred?**  
`count` creates resources by numeric index, e.g. `count.index`. `for_each` creates resources from a map or set using `each.key` and `each.value`. `for_each` is preferred when resources have stable names/keys because adding or removing items does not shift indices and cause unintended replacements.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**  
This causes drift. During `plan` or `apply`, OpenTofu refreshes state by reading the real resource from the provider and compares it to state and configuration. The plan then shows changes needed to reconcile the resource, such as update, replace, or recreate.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using `for_each` over `toset(["web1", "web2", "web3"])`.**  
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])

  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"

  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between `terraform_remote_state` data source and output values when sharing data between root modules. What is the recommended alternative and why?**  
`output` values are explicit module interfaces used within a single root module or between parent/child modules. `terraform_remote_state` reads outputs from another root module’s remote state. For sharing between separate root modules, the recommended mechanism is usually `terraform_remote_state` or CI/CD-passed outputs because root modules have separate state files. If possible, consolidating into one root module with child modules and explicit outputs reduces coupling and avoids reading remote state.

**T7 — Hard: RKE2 module kubeconfig output depends on `null_resource` with `remote-exec`. Dependent resources fail because output is empty on first apply. Explain why and how to fix it.**  
`null_resource` provisioners are side effects; they do not expose command output or files as computed attributes. `remote-exec` runs on the remote host and cannot directly populate a local kubeconfig output. If consumers need the kubeconfig during the same apply, they may see empty/unknown values. Fix by modeling kubeconfig as a real value/resource: use a provider/resource that exports kubeconfig, use `local-exec` to fetch it to the control node, output a path or computed attribute, and sequence consumers with `depends_on` or split into two applies.

**T8 — Medium: What is `tofu import`, and what are its limitations? How does the import block improve on the CLI command?**  
`tofu import` brings an existing resource into state so OpenTofu can manage it. Limitations: it does not automatically generate full configuration, requires a matching resource block, may not import all attributes, cannot import data sources, and does not run provisioners. The `import` block improves this by making imports declarative, version-controlled, planable, and able to generate configuration with `-generate-config-out`.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between `variable` and `output`?**  
A variable is an input value to a module or root configuration. `variable` declares inputs; `output` exposes values from a module or root configuration to users, parent modules, or other automation.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run `tofu plan` without `tofu init` first?**  
A provider is a plugin that manages resources and data sources for a platform, such as AWS, Kubernetes, or Cloudflare. Without `tofu init`, providers and backend configuration may not be installed or initialized, so `tofu plan` can fail with provider or backend errors.

**T11 — Easy: What is the `.terraform.lock.hcl` file, and why should it be committed to version control?**  
`.terraform.lock.hcl` records provider versions and checksums. It should be committed to ensure reproducible, secure, consistent provider versions across developers and CI.

**T12 — Easy: What does `tofu destroy` do, and how do you target a single resource for destruction?**  
`tofu destroy` removes managed resources and updates state. To destroy one resource, use:  
```bash
tofu destroy -target=aws_instance.web
```

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**  
A data source reads existing external information without managing its lifecycle. Example: look up an existing VPC ID, AMI, subnet, or DNS zone instead of creating it.

**T14 — Medium: Explain the difference between `locals` and `variable` blocks. When should you use `locals` instead of input variables?**  
`variable` blocks define inputs from outside the module. `locals` define computed or derived values inside the module. Use `locals` for transformations, constants, or intermediate values that should not be configurable inputs.

**T15 — Medium: What is the `lifecycle` block in a resource? Explain `create_before_destroy`, `prevent_destroy`, and `ignore_changes` with a use case for each.**  
`lifecycle` customizes resource behavior.  
- `create_before_destroy`: create replacement before deleting old resource; useful for zero-downtime replacement.  
- `prevent_destroy`: fail if plan would destroy the resource; useful for critical databases or stateful resources.  
- `ignore_changes`: ignore specified attributes in config vs state; useful for externally managed tags or labels.

**T16 — Medium: What is a `moved` block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**  
A `moved` block tells OpenTofu that a resource or module address has changed. During plan/apply, OpenTofu updates state to the new address instead of destroying and recreating the real resource. Example:  
```hcl
moved {
  from = aws_instance.old
  to   = aws_instance.new
}
```

**T17 — Hard: Explain how OpenTofu’s dependency graph works. What is the difference between implicit and explicit dependencies? How does `depends_on` affect parallelism, and why should it be used sparingly?**  
OpenTofu builds a graph from references between resources, data sources, and modules. Implicit dependencies come from expressions, e.g. `subnet_id = aws_subnet.main.id`. Explicit dependencies use `depends_on`. `depends_on` adds artificial ordering edges, which can reduce parallelism and hide real dependency problems. Use it only when ordering is required but no data reference exists.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and `tofu plan` takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain tradeoffs.**  
1. Split into smaller root modules/state per domain or lifecycle. Tradeoff: more coordination and cross-module dependencies.  
2. Use `-refresh=false` for fast plans and refresh periodically. Tradeoff: may miss drift.  
3. Use `-target` for narrow changes. Tradeoff: incomplete validation and possible missed dependencies.  
4. Reduce provider/data source calls by replacing dynamic lookups with variables/locals where safe. Tradeoff: less automatic discovery.  
5. Increase parallelism with `-parallelism=N`. Tradeoff: provider API rate limits and control-node load.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released? How do you manually break a lock, and what are the risks?**  
Supported backends, such as S3 + DynamoDB, acquire a lock before operations to prevent concurrent state changes. If a CI pipeline crashes, the lock may remain and subsequent operations fail with “Error acquiring the state lock.” You can manually release it with:  
```bash
tofu force-unlock <LOCK_ID>
```  
Risk: if another operation is still running, forcing unlock can corrupt state or cause conflicting infrastructure changes.

**T20 — Hard: Migrate local state to an S3-compatible remote backend with DynamoDB locking. Describe the process and verification.**  
1. Back up local state: `tofu state pull > backup.tfstate` or copy `terraform.tfstate`.  
2. Add backend config, e.g.:  
```hcl
terraform {
  backend "s3" {
    endpoint         = "https://minio.example.com"
    bucket           = "tofu-state"
    key              = "project/terraform.tfstate"
    region           = "us-east-1"
    dynamodb_table   = "tofu-locks"
    encrypt          = true
    skip_credentials_validation = true
    skip_metadata_api_check     = true
    skip_region_validation      = true
    force_path_style            = true
  }
}
```  
3. Run `tofu init -migrate-state` and confirm migration.  
4. Verify with `tofu state list`, `tofu plan` showing no unexpected changes, and confirm the state object exists in S3 and lock table in DynamoDB. The local state is copied to remote and is no longer authoritative.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**  
A task is a single module invocation. A role is a reusable bundle of tasks, variables, templates, files, and handlers. A playbook is a YAML file that runs one or more plays against hosts, often using roles and tasks.

**A2 — Easy: What is `ansible_facts` and how do you access the OS family of a target host?**  
`ansible_facts` contains gathered information about a host, such as OS, IP, disks, and packages. Access OS family with:  
```yaml
{{ ansible_facts['os_family'] }}
```
or legacy: `{{ ansible_os_family }}`.

**A3 — Medium: Explain the difference between `command`, `shell`, and `raw` modules. When would you use each?**  
`command` runs a command without a shell; no pipes, redirection, or globs. `shell` runs through `/bin/sh` and supports shell features. `raw` runs a raw command over the connection without requiring Python on the target; useful for bootstrapping Python or network devices.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**  
Idempotent tasks make the system match desired state without unnecessary changes. Idempotent example:  
```yaml
- ansible.builtin.apt:
    name: htop
    state: present
```
Not idempotent example:  
```yaml
- ansible.builtin.command: date > /tmp/time.txt
```
This changes the file every run.

**A5 — Medium: Write an Ansible task that installs `htop` only on Debian-based systems and `epel-release` + `htop` on RedHat-based systems using a single task file.**  
```yaml
- name: Install htop on Debian
  ansible.builtin.apt:
    name: htop
    state: present
  become: true
  when: ansible_facts['os_family'] == 'Debian'

- name: Install EPEL on RedHat
  ansible.builtin.yum:
    name: epel-release
    state: present
  become: true
  when: ansible_facts['os_family'] == 'RedHat'

- name: Install htop on RedHat
  ansible.builtin.yum:
    name: htop
    state: present
  become: true
  when: ansible_facts['os_family'] == 'RedHat'
```

**A6 — Hard: Explain Ansible’s variable precedence order. Where do `group_vars`, `host_vars`, `extra_vars`, role defaults, and `set_fact` land in priority?**  
From lower to higher priority, relevant items are roughly:  
`role defaults` → `group_vars` → `host_vars` → play/role vars → `set_fact`/registered vars → `extra_vars`.  
`extra_vars` are highest and override almost everything. `host_vars` override `group_vars`. `set_fact` is high but still below `extra_vars`.

**A7 — Hard: Deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this? Cover `serial`, inventory groups, and `wait_for`.**  
Use separate inventory groups and separate plays:  
```yaml
- hosts: rke2_servers
  serial: 1
  roles:
    - rke2_server

- hosts: rke2_agents
  serial: 10
  pre_tasks:
    - name: Wait for RKE2 API
      ansible.builtin.wait_for:
        host: "{{ groups['rke2_servers'][0] }}"
        port: 6443
        state: started
        timeout: 300
  roles:
    - rke2_agent
```
Separate plays guarantee servers finish before agents start. `serial` controls batch size. `wait_for` ensures agents only proceed when the server API is reachable.

**A8 — Medium: What is `ansible-vault`? How do you encrypt a single variable inside a vars file without encrypting the entire file?**  
`ansible-vault` encrypts sensitive data. To encrypt one variable, use:  
```bash
ansible-vault encrypt_string 'mysecret' --name 'db_password'
```
Paste the output into the vars file:  
```yaml
db_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  ...
```

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**  
An inventory lists managed hosts and groups. Static inventory is a fixed INI/YAML file. Dynamic inventory is generated by a script or plugin from cloud providers, CMDBs, or other sources.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the `webservers` group?**  
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```
or shorter:  
```bash
ansible webservers -a "df -h"
```

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**  
A handler is a task that runs only when notified and usually runs at the end of a play. Regular tasks run in order. Trigger a handler with `notify` from a task that reports `changed`.

**A12 — Easy: What is the `ansible.cfg` file used for? Name at least 3 settings commonly configured there.**  
`ansible.cfg` configures Ansible behavior. Common settings: `inventory`, `remote_user`, `private_key_file`, `host_key_checking`, `forks`, `roles_path`, `stdout_callback`.

**A13 — Easy: What is the `register` keyword in Ansible, and how do you use the registered variable in a subsequent task?**  
`register` stores a task result in a variable. Example:  
```yaml
- command: hostname
  register: host_result

- debug:
    msg: "{{ host_result.stdout }}"
```

**A14 — Medium: Explain the difference between `include_tasks` and `import_tasks`. When would you use one over the other, and how does this affect conditional evaluation?**  
`import_tasks` is static and parsed at playbook load time; it cannot use variables in the filename. `include_tasks` is dynamic and parsed at runtime; it can use variables in the filename. A `when` on `import_tasks` is applied to each imported task, while a `when` on `include_tasks` is evaluated when the include task runs.

**A15 — Medium: What is Ansible Galaxy, and how do you use a `requirements.yml` file to install roles and collections from it?**  
Ansible Galaxy is a repository of roles and collections. Example `requirements.yml`:  
```yaml
roles:
  - name: geerlingguy.docker
    version: 6.0.0

collections:
  - name: community.general
    version: 8.0.0
```
Install with:  
```bash
ansible-galaxy install -r requirements.yml
ansible-galaxy collection install -r requirements.yml
```

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between `ssh`, `local`, and `network_cli` connection types? When would you use each?**  
Connection plugins define how Ansible connects to and executes on targets. `ssh` is default for Linux/Unix hosts. `local` runs tasks on the control node. `network_cli` connects to network devices using CLI protocols and persistent connections, useful for switches/routers without Python.

**A17 — Hard: Explain how Ansible’s `delegate_to` and `run_once` work. Give a practical example where you need to run a task on the control node once, using data gathered from a remote host.**  
`delegate_to` runs a task on a different host than the current play host. `run_once` runs a task only once for the play/host group. Example: gather hostnames from web servers, then update DNS once from the control node:  
```yaml
- hosts: web
  tasks:
    - command: hostname -f
      register: fqdn

    - name: Add hosts to DNS once from control node
      ansible.builtin.uri:
        url: https://dns.example/api/records
        method: POST
        body_format: json
        body:
          name: "{{ hostvars[item].fqdn.stdout }}"
      loop: "{{ ansible_play_hosts }}"
      delegate_to: localhost
      run_once: true
```

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain tradeoffs.**  
1. Increase `forks` to run more hosts in parallel. Tradeoff: more control-node CPU/network and possible API rate limits.  
2. Enable pipelining to reduce SSH round trips. Tradeoff: some modules or environments may not support it and debugging can be harder.  
3. Use fact caching or disable fact gathering when facts are stable. Tradeoff: stale facts can cause incorrect decisions.  
4. Use Mitogen or similar strategy plugins to speed Python execution over SSH. Tradeoff: not core Ansible, compatibility risk, and possible licensing/support concerns.  
5. Use `serial` carefully; it can improve safety but usually reduces parallelism.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between `{{ }}`, `{% %}`, and `{# #}`? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**  
`{{ }}` outputs values. `{% %}` contains control logic such as `if` and `for`. `{# #}` are comments. Example:  
```jinja2
upstream {{ upstream_name }} {
{% for server in backend_servers %}
    server {{ server.host }}:{{ server.port }} {{ server.params | default('') }}; # health_check: {{ server.health_check | default('enabled') }}
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover serial batches, pre/post tasks for load balancer registration, health checks with `uri`, and rollback strategy on failure using `block/rescue`.**  
Use a play with `serial: 2` or `serial: 25%` and `max_fail_percentage: 0`. For each host: remove from load balancer, wait for drain, deploy, restart, health check, then re-add to load balancer. Use `block/rescue` to rollback if deployment or health check fails.

Example:  
```yaml
- hosts: web
  serial: 2
  max_fail_percentage: 0
  vars:
    lb_api: https://lb.example/api/backends
    upstream: web_backend
  tasks:
    - block:
        - name: Remove from load balancer
          ansible.builtin.uri:
            url: "{{ lb_api }}/{{ upstream }}/{{ inventory_hostname }}"
            method: DELETE

        - name: Wait for connections to drain
          ansible.builtin.wait_for:
            timeout: 30

        - name: Deploy new release
          ansible.builtin.git:
            repo: https://git.example/app.git
            dest: /srv/webapp
            version: "{{ release }}"

        - name: Restart app
          ansible.builtin.systemd:
            name: webapp
            state: restarted

        - name: Health check
          ansible.builtin.uri:
            url: http://{{ inventory_hostname }}/healthz
            status_code: 200
          register: health
          until: health.status == 200
          retries: 10
          delay: 5

        - name: Add back to load balancer
          ansible.builtin.uri:
            url: "{{ lb_api }}/{{ upstream }}/{{ inventory_hostname }}"
            method: POST

      rescue:
        - name: Rollback to previous release
          ansible.builtin.git:
            repo: https://git.example/app.git
            dest: /srv/webapp
            version: "{{ previous_release }}"

        - name: Restart app after rollback
          ansible.builtin.systemd:
            name: webapp
            state: restarted

        - name: Health check after rollback
          ansible.builtin.uri:
            url: http://{{ inventory_hostname }}/healthz
            status_code: 200
          register: rollback_health
          until: rollback_health.status == 200
          retries: 10
          delay: 5

        - name: Add back to load balancer after rollback
          ansible.builtin.uri:
            url: "{{ lb_api }}/{{ upstream }}/{{ inventory_hostname }}"
            method: POST

        - name: Fail deployment
          ansible.builtin.fail:
            msg: "Deployment failed on {{ inventory_hostname }}; rolled back."
```
