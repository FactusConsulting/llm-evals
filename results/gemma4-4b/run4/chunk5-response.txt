## .NET / C#

**DN1** — **Class vs Struct:** A `class` is a reference type, allocated on the heap, and supports inheritance. A `struct` is a value type, allocated on the stack (or inline within a containing type), and is designed for small, immutable data structures. Use a `struct` when the type represents a small, lightweight value (e.g., a point, color, or coordinate) and copying it is cheap; avoid structs for large objects or those requiring inheritance.

**DN2** — **IEnumerable<T> vs IQueryable<T>:** `IEnumerable<T>` represents a sequence that can be iterated over in memory. Operations are executed locally on the collection after it has been loaded. `IQueryable<T>` represents an expression tree that describes a query. Operations are translated into an executable query (e.g., SQL) and executed remotely (e.g., against a database) before the results are materialized into memory. This distinction matters because `IQueryable<T>` allows filtering and projection to happen *on the server*, minimizing data transfer and memory usage, whereas `IEnumerable<T>` forces the entire dataset to be pulled into the application memory first.

**DN3** — **Async/Await, Task vs ValueTask:** `async/await` allows asynchronous code to be written in a synchronous-looking style by pausing execution until an awaited operation completes, without blocking the thread. A `Task` represents an asynchronous operation that might return a value or throw an exception. A `ValueTask<T>` is a struct optimized for scenarios where the operation might complete synchronously (i.e., without needing heap allocation for the state machine). Use `ValueTask<T>` when you expect the operation to complete synchronously often, as it avoids the heap allocation overhead associated with `Task<T>`.

**DN4** — **Dependency Injection (DI):** DI is a design pattern where components receive their dependencies from an external source (the DI container) rather than creating them internally. This promotes loose coupling and testability.
*   **Transient:** A new instance is created every time it is requested.
*   **Scoped:** A single instance is created per scope (e.g., per HTTP request in ASP.NET Core).
*   **Singleton:** A single instance is created for the entire application lifetime.
A common bug is injecting a Scoped service (like `DbContext`) into a Singleton service. Since the Singleton lives for the entire application lifetime, it holds a reference to the Scoped service, causing that service to be instantiated only once at application startup, effectively making it a Singleton, which violates the intended request-specific scope and can lead to concurrency issues or incorrect state management.

**DN5** — **string vs ReadOnlySpan<char>:** `string` is an immutable, heap-allocated sequence of characters, optimized for Unicode text handling. `ReadOnlySpan<char>` is a stack-allocated, lightweight, non-allocating view over a contiguous block of memory (which could be a string, a character array, or a buffer). Use `Span<T>` when you need to perform high-performance, low-allocation string or buffer manipulation (e.g., parsing, slicing, or searching) without creating new string objects for every operation.

**DN6** — **Garbage Collector (GC):** The .NET GC is a generational, tracing collector that automatically manages memory by identifying and reclaiming unreachable objects.
*   **Generations:** Objects are allocated in Gen 0. If they survive a collection, they are promoted to Gen 1, and then potentially to Gen 2. Gen 0 collections are frequent and fast, targeting short-lived objects. Gen 2 collections are rare and target long-lived objects.
*   **Large Object Heap (LOH):** A dedicated area for objects larger than a threshold (typically 85KB). LOH collections are less frequent and can cause fragmentation because the GC cannot easily move large objects.
`IDisposable` is required for resources that manage unmanaged resources (like file handles, network sockets, or database connections). Even with a GC, the GC only manages *managed* memory; it cannot automatically release external, unmanaged resources, so `IDisposable` allows deterministic cleanup via the `using` statement.

**DN7** — **ConfigureAwait(false):** When `ConfigureAwait(false)` is used, it tells the runtime that the continuation of the asynchronous method does not need to resume on the original `SynchronizationContext`.
*   **When to use:** In library code or background services where you do not need to interact with UI elements or specific context state. This prevents deadlocks and improves performance by avoiding the overhead of capturing and restoring the context.
*   **When NOT to use:** In UI applications (WPF, WinForms, MAUI) where the continuation *must* resume on the UI thread to safely update the UI.
This relates to `SynchronizationContext`: the context captures the execution environment (e.g., the UI thread context). If you don't care about that context, you tell the runtime to skip capturing it.

**DN8** — **.NET 8/9 Features:**
*   **Primary Constructors:** Allow defining constructor parameters directly in the class signature, which are automatically available as read-only properties.
*   **Collection Expressions:** Provide a concise syntax for initializing collections (e.g., `[1, 2, 3]`).
*   **FrozenDictionary:** A dictionary whose contents cannot be changed after creation, providing thread-safe, immutable lookups.
*   **Example (Primary Constructor with DI):**
    ```csharp
    public class UserService(ILogger<UserService> logger) 
    {
        private readonly ILogger<UserService> _logger = logger;
        public void DoWork() => _logger.LogInformation("Service running.");
    }
    // In Program.cs:
    builder.Services.AddScoped<UserService>();
    ```

**DN9** — **ObjectDisposedException with DbContext:** The likely cause is that the `DbContext` instance is being reused across multiple concurrent requests or threads without proper scoping. EF Core's `DbContext` is **not thread-safe** and should be scoped to a single unit of work (typically one HTTP request).
**Fix:** Ensure that the `DbContext` is registered with the DI container using `AddDbContext<TContext>(...)` and that the consuming service (the API controller/handler) is registered as `Scoped`. The DI container will then provide a fresh, isolated instance of the `DbContext` for each incoming request.

**DN10** — **Record vs Class:**
*   **Class:** A traditional reference type, mutable by default, designed for complex object behavior and inheritance.
*   **Record:** A reference type optimized for holding data. It automatically provides value-based equality (equality is based on the *content* of the properties, not the memory address) and supports non-destructive mutation (`with` expressions).
*   **Record Struct:** A value type that benefits from record semantics (value equality).
Choose a **Class** when you need complex behavior, inheritance, or mutable state. Choose a **Record** when you are modeling immutable data transfer objects (DTOs) or entities where content equality is paramount.

**DN11** — **ref, out, in:**
*   **`ref`:** The variable must be initialized before being passed to the method. The method modifies the original variable. Used when you need to pass an existing variable by reference for modification.
*   **`out`:** The variable does not need to be initialized before being passed. The method is responsible for assigning a value to it. Used when the method needs to return multiple values via parameters.
*   **`in`:** The variable must be initialized, but the method receives it as a read-only reference. Used for performance optimization when passing large structs to avoid copying the entire value, but you do not intend to modify it.

**DN12** — **Nullable Reference Types (NRTs):** NRTs (enabled via `#nullable enable`) allow the compiler to track whether a reference type variable might be `null`.
*   **`string?` (Nullable Reference Type):** Indicates that the reference variable *might* hold `null`. The compiler forces you to handle the null case (e.g., using null checks or the null-forgiving operator `!`).
*   **`int?` (Nullable Value Type):** Indicates that a value type (like `int`) can hold `null`. This is a distinct concept from NRTs and is used when the absence of a value is a valid state for a primitive type.

**DN13** — **LINQ:** LINQ (Language Integrated Query) is a set of features in C# that allows developers to write queries against various data sources (collections, databases, XML) using a unified syntax.
*   **Method Syntax:** Uses extension methods on the collection (`list.Where(x => x.Age > 30)`). This is generally preferred for complex logic as it is more fluent.
*   **Query Syntax:** Uses SQL-like syntax (`from x in list where x.Age > 30 select x`). This is often more readable for developers familiar with SQL.
**Deferred Execution:** Queries are not executed immediately when written. The query expression is built and stored. Execution only occurs when the results are iterated over (e.g., in a `foreach` loop or by calling `.ToList()`). This allows the query provider (like EF Core) to optimize the entire query before sending it to the database.

**DN14** — **Generic Constraints:** Constraints restrict the types that can be used as type arguments for a generic type, ensuring that the generic code can safely call methods or access members specific to those types.
*   `where T : class`: T must be a reference type.
*   `where T : struct`: T must be a value type.
*   `where T : new()`: T must have a public parameterless constructor.
*   `where T : IComparable<T>`: T must implement the `IComparable<T>` interface, allowing comparisons between instances of T.
You combine constraints (e.g., `where T : class, new()`) when the generic type needs to satisfy multiple requirements simultaneously (e.g., it must be a reference type *and* must be instantiable).

**DN15** — **Abstract Class vs Interface:**
*   **Abstract Class:** Can contain both implemented methods and abstract methods. It defines a base structure and can share common implementation logic among derived classes. A class can only inherit from one abstract class.
*   **Interface:** Defines a contract—a set of methods/properties that implementing classes *must* adhere to. It historically contained no implementation.
**Default Interface Methods (C# 8+):** This feature allows interfaces to include method implementations. This blurs the line, as an interface can now provide default behavior, making it easier to evolve contracts without breaking existing implementations. However, the core distinction remains: Abstract classes define *is-a* relationships with shared state/implementation, while interfaces define *can-do* capabilities.

**DN16** — **ASP.NET Core Middleware Pipeline:** The pipeline is a series of software components that process HTTP requests sequentially. Each middleware component inspects the request, performs an action (e.g., authentication, logging, routing), and then either passes the request to the next component or terminates the request/response cycle.
*   **`app.Use()`:** Registers middleware that processes the request/response flow (e.g., `UseAuthentication()`, `UseRouting()`).
*   **`app.Map()`:** Maps a specific route or set of routes to a handler, effectively short-circuiting the pipeline for that route.
*   **`app.Run()`:** Terminates the pipeline, usually used as the final endpoint handler.
**Ordering Matters:** Middleware executes in the order it is registered. If authentication middleware is placed *after* routing, the request might reach the endpoint before authentication has run.
**Exception Handling:** Exception handling middleware (e.g., `UseExceptionHandler`) must be placed *early* in the pipeline (usually near the beginning) so that it can catch exceptions thrown by subsequent middleware or endpoint handlers before they result in a generic server error response.

**DN17** — **Channel<T> vs BlockingCollection<T>:**
*   **`Channel<T>`:** A modern, asynchronous, producer-consumer mechanism introduced in .NET Core. It is designed to work seamlessly with `async/await` and is highly flexible (bounded or unbounded).
*   **`BlockingCollection<T>`:** A legacy, thread-safe collection designed for synchronous producer-consumer scenarios, often used with `Task.Run()` or manual threads. It blocks threads when the collection is empty or full.
**Bounded Channel Example (Backpressure):** A bounded channel limits the number of items that can be buffered. If the producer tries to write to a full bounded channel, the `await channel.Writer.WriteAsync(item)` call will asynchronously pause (backpressure) until a consumer reads an item, freeing up space.

**DN18** — **Source Generators:** Source Generators are compile-time code generators. They analyze the syntax tree of the source code during compilation and generate new C# source files that are then compiled alongside the original code.
*   **Difference from Reflection:** Reflection inspects types and members *at runtime*. Source Generators generate code *at compile time*, eliminating runtime overhead and allowing for compile-time validation.
*   **Difference from IL Weaving:** IL Weaving modifies the Intermediate Language (IL) of compiled assemblies *after* compilation. Source Generators modify the source code *before* compilation.
**Incremental Generator:** An incremental generator only re-runs when the specific source files it depends on have changed, rather than re-running the entire generator logic on every build. This significantly speeds up the build process, especially in large projects.

**DN19** — **TPL Dataflow:** TPL Dataflow provides a library of building blocks (blocks) that allow developers to construct complex, asynchronous data processing pipelines.
*   **`ActionBlock`:** Executes an action (a delegate) asynchronously for each item received. It is a sink/processor.
*   **`TransformBlock`:** Executes a transformation function (takes an input, returns a transformed output) asynchronously.
*   **`BufferBlock`:** Acts as a queue, buffering incoming messages until a consumer processes them.
**Comparison to Channels:** Channels are a simpler, lower-level mechanism for point-to-point or producer-consumer communication. TPL Dataflow is a higher-level framework for building complex, multi-stage, flow-controlled pipelines where you need specific processing semantics (transforming, filtering, aggregating) between stages.

**DN20** — **Minimal APIs:** Minimal APIs are a streamlined, modern way to build HTTP endpoints in ASP.NET Core using top-level statements and lambda expressions, bypassing the traditional controller/action pattern.
*   **Differences from Controllers:** Controllers use classes, methods, and attributes (`[HttpGet]`). Minimal APIs use direct function signatures (`app.MapGet("/weatherforecast", ...)`).
*   **Trade-offs:**
    *   **Testability:** Slightly harder to unit test in isolation compared to controllers, as they are tightly coupled to the `WebApplication` builder.
    *   **Middleware:** Middleware integration is very direct and simple.
    *   **OpenAPI Support:** Requires explicit configuration (e.g., using Swashbuckle) to generate OpenAPI documentation, whereas controllers often integrate more naturally with standard scaffolding.
*   **Route Groups/Endpoint Filters:** Route groups allow applying common middleware or route prefixes to a set of related endpoints. Endpoint filters allow executing logic (like authorization checks or logging) before or after the endpoint handler runs, regardless of the specific route definition.

## Python

**P1** — **List vs Tuple, Set vs Frozenset:**
*   **List:** Mutable, ordered sequence of items (defined with `[]`). Allows duplicate elements.
*   **Tuple:** Immutable, ordered sequence of items (defined with `()`). Does not allow modification after creation.
*   **Set:** Mutable, unordered collection of unique items (defined with `{}`). Does not allow duplicates.
*   **Frozenset:** Immutable version of a set. Because it is immutable, it can be used as an element within another set or as a dictionary key.

**P2** — **Global Interpreter Lock (GIL):** The GIL is a mutex that protects access to Python objects, ensuring that only one thread executes Python bytecode at any given time, even on multi-core processors.
*   **Workloads Affected:** CPU-bound workloads (heavy computation, mathematical processing) are limited by the GIL, as threads cannot execute Python code truly in parallel.
*   **Workarounds:**
    1.  **Multiprocessing:** Using separate processes bypasses the GIL because each process has its own Python interpreter and memory space.
    2.  **C Extensions:** Using libraries written in C/C++ (like NumPy) that release the GIL during heavy computation.
    3.  **Asyncio:** Using cooperative multitasking (I/O-bound tasks) where threads yield control voluntarily while waiting for I/O, allowing other tasks to run.

**P3** — **Deepcopy vs Copy (Shallow Copy):**
*   **Shallow Copy (`.copy()` or `copy.copy()`):** Creates a new container object, but populates it with *references* to the objects found in the original. If the original contains mutable objects (like lists), modifying those nested objects in the copy will also modify them in the original.
*   **Deep Copy (`copy.deepcopy()`):** Creates a completely independent copy of the original object and recursively copies all nested objects. Changes to the copy do not affect the original.
**Example of Shallow Copy Issue:**
```python
original = [{'a': 1}]
shallow = original.copy()
shallow['a'] = 99  # Modifies the nested dict in both
print(original) # Output: [{'a': 99}]
```

**P4** — **Decorators:** Decorators are syntactic sugar in Python that allow you to wrap a function or class method to modify or enhance its behavior without permanently altering its source code. They are essentially functions that take another function as an argument and return a new, wrapped function.
**Logging Decorator Example:**
```python
import time
from functools import wraps

def timing_decorator(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start_time = time.time()
        result = func(*args, **kwargs)
        end_time = time.time()
        print(f"Function {func.__name__} executed in {end_time - start_time:.4f} seconds.")
        return result
    return wrapper

@timing_decorator
def heavy_computation(n):
    sum(i*i for i in range(n))

heavy_computation(1000000)
```

**P5** — **Generators and Yield:**
*   **Generators:** Functions that return an iterator. Instead of calculating and returning all results at once (like a list), they use the `yield` keyword to pause execution, return a value, and save their internal state. When `next()` is called, execution resumes from where it left off.
*   **Difference from Returning a List:** Returning a list calculates and stores *all* results in memory immediately. Generators calculate results *lazily* (on demand), which is highly memory efficient for large datasets.
*   **`yield from`:** Used to delegate control to a sub-generator. It allows one generator to seamlessly delegate iteration to another generator, effectively chaining them together.

**P6** — **Asyncio Event Loop:** The event loop is the core mechanism of `asyncio`. It is a single-threaded scheduler that manages and runs asynchronous tasks. When an `await` call is encountered, the task yields control back to the event loop, allowing the loop to switch context and run other ready tasks until the awaited operation completes.
*   **`asyncio.run(coro)`:** Runs the top-level coroutine and manages the event loop lifecycle (starts, runs, and closes the loop).
*   **`asyncio.gather(*coros)`:** Runs multiple awaitables concurrently and waits for all of them to complete, returning a list of their results.
*   **`asyncio.create_task(coro)`:** Schedules a coroutine to run concurrently on the event loop immediately, returning a `Task` object that can be awaited later.
**Why `time.sleep()` fails:** `time.sleep()` is a *blocking* call. When called inside an `async` function, it blocks the entire thread, which means it blocks the single-threaded event loop, preventing *all* other concurrent tasks from running until the sleep duration is over. You must use `await asyncio.sleep(delay)` to yield control back to the loop.

**P7** — **MRO (Method Resolution Order):** MRO is the algorithm Python uses to determine the order in which base classes are searched when looking up a method or attribute in a class hierarchy.
*   **Algorithm:** Python 3 uses the C3 Linearization algorithm. This algorithm ensures that the inheritance order is consistent, respects the local precedence order (classes listed earlier are checked first), and avoids infinite loops in complex inheritance structures.
*   **Diamond Inheritance:** When a class inherits from two classes that share a common ancestor (the diamond shape), C3 ensures that the common ancestor is visited only once, following the order specified in the inheritance list.
*   **Output Explanation:** `D` inherits from `B` and `C`. `B` inherits from `A`. `C` inherits from `A`. The MRO for `D` is `(D, B, C, A, object)`. When `D().who()` is called, Python checks `D` (no `who`), then `B` (no `who`), then `C` (has `who`), and executes `C`'s implementation, returning "C".

**P8** — **Metaclass:** A metaclass is the "class of a class." It controls how a class itself is created. When you define a class, Python calls its metaclass to construct the class object.
*   **`__init_subclass__`:** A class method available since Python 3.6. It is called *after* a subclass has been created but *before* it is fully initialized. It is ideal for modifying or reacting to the structure of a subclass *after* it has been defined.
*   **Metaclass:** Controls the *creation* process itself. It intercepts the creation of the class object.
*   **Use Cases:**
    *   **`__init_subclass__`:** Implementing automatic logging or validation hooks for all subclasses of a base class (e.g., ensuring all subclasses implement a specific method).
    *   **Metaclass:** Implementing complex structural changes, such as automatically registering all subclasses into a central registry or enforcing specific API patterns across an entire module.

**P9** — **Multiprocessing, Threading, Concurrent.futures:**
*   **Threading:** Uses threads within the same process. Best for **I/O-bound** tasks (waiting for network/disk) because the GIL allows context switching during waits. Limited by the GIL for CPU-bound tasks.
*   **Multiprocessing:** Uses separate processes. Bypasses the GIL, allowing true parallel execution on multiple CPU cores. Best for **CPU-bound** tasks.
*   **`concurrent.futures`:** A high-level interface that abstracts both threading (`ThreadPoolExecutor`) and multiprocessing (`ProcessPoolExecutor`), allowing the developer to use a unified API (`.submit()`, `.as_completed()`) regardless of the underlying execution model.
**Serialization Implications:** Multiprocessing requires data to be passed between separate memory spaces (processes). This necessitates **pickling** (serialization) of the data. Pickling can be slow and fails if the objects contain non-serializable resources (like open file handles or database connections).

**P10** — **`__slots__`:** `__slots__` is a class attribute that explicitly declares the attributes an instance of the class will have.
*   **What it prevents:** It prevents the creation of the instance dictionary (`__dict__`) for each instance.
*   **When to use:** When creating classes that are instantiated millions of times (e.g., data points, nodes in a graph) and memory efficiency is critical.
*   **Memory Impact:** It significantly reduces memory footprint because Python no longer needs to allocate and maintain the dynamic `__dict__` for every object instance. However, it also prevents the addition of new attributes to instances dynamically after creation.

**P11** — **Virtual Environment:** A virtual environment is an isolated Python environment that contains a specific version of the Python interpreter and its own set of installed packages.
*   **Why use one:** It prevents dependency conflicts between different projects. Project A might require Django 2.0, while Project B requires Django 4.0. A virtual environment ensures that each project has its required, isolated dependencies.
*   **Differences:**
    *   **`venv`:** The standard, built-in module in Python 3.3+ for creating lightweight virtual environments.
    *   **`virtualenv`:** An older, more feature-rich third-party tool that predates `venv` and offers more customization.
    *   **`conda`:** A comprehensive package and environment manager (often used in data science) that manages not just Python packages but also non-Python dependencies (like specific C libraries).

**P12** — **Comprehensions:** Comprehensions provide a concise, readable way to create new collections based on existing iterables.
*   **List Comprehension:** `[expression for item in iterable if condition]` (Creates a list).
*   **Dict Comprehension:** `{key: value for item in iterable if condition}` (Creates a dictionary).
*   **Set Comprehension:** `{expression for item in iterable if condition}` (Creates a set).
**Relation to map()/filter():** Comprehensions are generally preferred over `map()` and `filter()` because they are more Pythonic and often more readable.
*   `map()` applies a function to every item (like a list comprehension without the `if`).
*   `filter()` selects items based on a predicate (like a list comprehension without the expression).
**Preference:** Use comprehensions when you are building a new collection based on an existing one, as they combine the iteration, transformation, and filtering steps into one clean line.

**P13** — **== vs is:**
*   **`==` (Equality Operator):** Compares the *values* of two objects. It calls the object's `__eq__()` method.
*   **`is` (Identity Operator):** Compares the *identity* of two objects. It checks if both variables point to the exact same object in memory (i.e., if they have the same `id()`).
**Object Interning:** Interning is an optimization where Python pre-allocates and reuses immutable objects (like small integers, short strings) in memory.
**Small Integers:** Python automatically interns integers in the range of -5 to 256. When you write `a = 10` and `b = 10`, Python often points both `a` and `b` to the same cached object in memory, causing `a is b` to return `True`. This is an optimization, not a guarantee for all integers.

**P14** — **\*args and \*\*kwargs:**
*   **`*args`:** Collects any number of positional arguments into a tuple.
*   **`**kwargs`:** Collects any number of keyword arguments into a dictionary.
**Parameter Markers:**
*   **Positional-Only (`/`):** Arguments placed before `/` must be passed by position and cannot be passed using a keyword argument name.
*   **Keyword-Only (`*`):** Arguments placed after `*` must be passed using their keyword name; positional arguments are not allowed for them.
**Example:** `def func(a, b, /, c, *, d):`
*   `a` and `b` must be positional.
*   `c` can be positional or keyword.
*   `d` must be keyword.

**P15** — **Context Managers (`with` statement):** Context managers ensure that setup and teardown actions are executed reliably, even if errors occur within the block. They guarantee resource cleanup.
*   **`__enter__` / `__exit__`:** The standard way. `__enter__` runs upon entering the `with` block and returns the resource. `__exit__` runs upon exiting (success or failure) and handles cleanup.
*   **`@contextmanager`:** A simpler decorator from the `contextlib` module. It uses `yield` to define the resource setup (before `yield`) and the cleanup (after `yield`).
**Example Beyond File Handling (Database Connection):**
```python
from contextlib import contextmanager
import sqlite3

@contextmanager
def get_db_connection(db_name):
    conn = sqlite3.connect(db_name)
    try:
        yield conn  # Resource is yielded here
    finally:
        conn.close() # Cleanup happens here
```

**P16** — **Type Hinting:** Type hinting allows developers to annotate variables, function parameters, and return values with expected types. This does not enforce types at runtime but enables static analysis tools like Mypy or Pyright to catch type errors *before* execution.
*   **`typing.Union[A, B]`:** Specifies that a variable can be of type A OR type B.
*   **`typing.Optional[T]`:** A shorthand for `Union[T, None]`, indicating the variable can be T or None.
*   **`typing.Literal[A, B]`:** Restricts a variable to only accept one of a specific set of literal values (e.g., `Literal["red", "green"]`).
*   **`typing.TypeVar`:** A placeholder for types that will be specified later, crucial for writing generic functions that maintain type safety across different types.
*   **`typing.Protocol`:** Defines a structural type. Instead of inheriting from a class, a class conforms to a Protocol if it implements the required methods/attributes, enabling duck typing with static type checking.

**P17** — **Data Model (Dunder Methods):** Dunder methods (double underscore methods) are special methods that Python calls internally to implement core language features.
*   **`__repr__` vs `__str__`:**
    *   `__repr__`: The "official" string representation, intended for developers. It should ideally be unambiguous and allow recreation of the object (e.g., `ClassName(arg1=value1)`).
    *   `__str__`: The "informal" string representation, intended for end-users (should be readable).
*   **`__eq__` vs `__hash__`:**
    *   `__eq__`: Defines how two objects are compared for equality (`a == b`).
    *   `__hash__`: Returns an integer hash value for the object.
**If `__eq__` is defined but not `__hash__`:** If you define custom equality (`__eq__`), you are telling Python that two objects can be considered equal. If you do not define `__hash__`, Python cannot reliably place that object into hash-based collections (like `set` or as a dictionary key), as it doesn't know how to calculate a consistent hash for equal items. You must define both, or explicitly set `__hash__ = None`.

**P18** — **Descriptors:** A descriptor is an object attribute that defines how attribute access (getting, setting, or deleting) should behave. It implements one or more of the descriptor protocol methods: `__get__`, `__set__`, and `__delete__`.
*   **Descriptor Protocol:**
    *   `__get__(self, instance, owner)`: Called when the attribute is accessed.
    *   `__set__(self, instance, value)`: Called when the attribute is assigned a value.
    *   `__delete__(self, instance)`: Called when the attribute is deleted.
*   **Usage:**
    *   **`property`:** A built-in descriptor that allows methods to be accessed like attributes (e.g., `@property`).
    *   **`classmethod` / `staticmethod`:** These are specialized descriptors that alter how the method is bound to the class or instance.
Descriptors are the fundamental mechanism that allows Python to implement features like properties, slots, and method binding.

**P19** — **Import System:** Python's import system manages how modules (code files) are located and loaded.
*   **Relative vs Absolute Imports:**
    *   **Absolute:** Imports start from the root of the package structure (e.g., `from my_package import module`).
    *   **Relative:** Imports reference modules relative to the current package (e.g., `from . import sibling_module`).
*   **Mechanisms:**
    *   **`sys.path`:** A list of directories Python searches when an `import` statement is encountered.
    *   **`PYTHONPATH`:** An environment variable that adds directories to `sys.path` before the script runs.
    *   **`__init__.py`:** Historically, this file marked a directory as a Python package. While less strictly required in modern Python (namespace packages), it still defines package-level initialization code.
    *   **Namespace Packages:** Packages that do not require an `__init__.py` and allow multiple, independent packages to contribute to the same namespace.
*   **Finder and Loader:** When an import is requested, Python uses **Finders** (e.g., `PathFinder`) to locate the module file based on the path in `sys.path`. Once found, the **Loader** (e.g., `SourceFileLoader`) reads the file content and executes the code to create the module object.

**P20** — **Dataclasses vs attrs vs Pydantic:**
*   **Dataclasses:** A standard library feature (Python 3.7+) that automatically generates boilerplate methods (`__init__`, `__repr__`, `__eq__`) for classes primarily used to hold data. They are simple and lightweight.
*   **`attrs`:** A third-party library that provides similar functionality to dataclasses but offers more flexibility and customization hooks.
*   **Pydantic:** A data validation and settings management library. It uses type hints to define schemas and performs rigorous runtime data validation, coercion, and serialization/deserialization (e.g., converting a string "123" to an integer 123).
**Features:**
*   **`__post_init__`:** A method in dataclasses/attrs called immediately after `__init__` completes, allowing for post-initialization logic (e.g., calculating a derived field).
*   **Field Factories:** Used to provide default values that are computed dynamically rather than being static constants (e.g., `field(default_factory=list)`).
*   **Frozen Dataclasses:** Setting `frozen=True` makes the instance immutable, preventing attribute assignment after creation.
*   **Inheritance:** Dataclasses support inheritance, but careful use of `__post_init__` and field definitions is required to manage inherited state correctly.
**When to choose Pydantic:** Choose Pydantic when data integrity and validation are critical. If you are receiving data from an external source (API request body, JSON file) and must guarantee that the data conforms to a specific structure and type *before* your business logic runs, Pydantic is superior to dataclasses.
