**T1** — Easy: What is the difference between tofu plan and tofu apply?
`tofu plan` calculates the difference (the execution plan) between the desired state defined in the configuration files and the actual current state recorded in the state file. It shows exactly what resources will be created, updated, or destroyed without making any changes. `tofu apply` executes the changes detailed in the plan, provisioning or modifying the infrastructure in the cloud provider.

**T2** — Easy: What is state in OpenTofu, and why is remote state important?
State is a mapping file that records the real-world infrastructure resources managed by OpenTofu, including their attributes (IDs, IPs, ARNs, etc.). Remote state (e.g., S3, Azure Storage) is crucial because it provides a centralized, durable, and accessible source of truth for the state file, enabling collaboration across teams and ensuring state persistence even if the local machine fails.

**T3** — Medium: Explain the difference between count and for_each. When is for_each preferred?
`count` creates a specified number of identical instances, using an integer index (e.g., `count.index`). `for_each` creates instances based on the keys of a map or the elements of a set, providing a stable, unique identifier (the key) for each instance. `for_each` is preferred when the identity of the resource matters, as it ensures that if you change the input set, the existing resources are updated or destroyed predictably based on their unique key, rather than being re-indexed by `count`.

**T4** — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
This is known as configuration drift. When you run `tofu plan`, OpenTofu performs a refresh operation, querying the cloud provider to fetch the current, actual state of the resource. It then compares this actual state against the desired state recorded in its state file. If a discrepancy is found, OpenTofu detects the drift and includes the necessary actions (e.g., an update or replacement) in the plan to reconcile the actual state with the desired state.

**T5** — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).

```hcl
locals {

    Name = each.key
  }
}
```

**T6** — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
**Output Values:** An output value is a value *produced* by a resource or module and is intended to be consumed by consumers *after* the resource has been created. It is a direct result of the current state.
**Data Source:** A data source is used to *read* information about existing infrastructure that is *not* managed by the current configuration.
**Difference:** Outputs provide data *from* the current configuration; Data Sources provide data *about* external or existing infrastructure.
**Recommended Alternative:** For sharing data between root modules, the recommended approach is to use **module outputs** combined with **module inputs**. The child module outputs the necessary data, and the parent module consumes it as an input variable. This maintains clear dependency boundaries and prevents the parent module from needing to know the internal implementation details of the child module.

**T7** — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
**Explanation:** The dependency graph resolves the `null_resource` first, which executes the `remote-exec` provisioner. However, provisioners run *after* the resource is created, and the output value is only populated *after* the provisioner successfully completes and the resource state is updated. If dependent resources try to read this output immediately, the value is not yet available, leading to an empty or null result.
**Fix:** Use the `depends_on` meta-argument on the dependent resource, explicitly telling OpenTofu that it must wait for the `null_resource` to finish its provisioning phase before attempting to read the output.

**T8** — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
`tofu import` allows you to bring existing, manually provisioned infrastructure resources under the management of OpenTofu without having to write the configuration code for them first.
**Limitations:** It only imports the resource ID; it does not automatically populate all necessary configuration attributes, requiring manual configuration updates afterward.
**Improvement (Import Block):** The import block allows you to specify the resource type, name, and the ID to import *within* the configuration file itself. This makes the process declarative, self-documenting, and allows OpenTofu to attempt to populate more attributes during the import process, reducing the manual cleanup required post-import.

**T9** — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
A **variable** is a placeholder for configuration values that are passed *into* the configuration (input). They allow the code to be reusable and parameterized.
An **output** is a value that is *produced* by the configuration (output). It exposes data derived from the resources (e.g., an IP address, a DNS name) so that other parts of the infrastructure or external systems can consume it.

**T10** — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
A provider is a plugin that enables OpenTofu to interact with a specific API or service (e.g., AWS, Azure, Kubernetes). It contains the logic for CRUD operations against that service. If you run `tofu plan` without `tofu init`, OpenTofu will fail because it has not downloaded or initialized the necessary provider plugins specified in the configuration, meaning it has no mechanism to communicate with the target cloud API.

**T11** — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
The `.terraform.lock.hcl` file records the exact versions and checksums of every provider and module dependency used in the configuration. It should be committed to version control to ensure that every developer and every CI/CD pipeline uses the exact same, tested versions of dependencies, preventing unexpected behavior caused by upstream provider updates.

**T12** — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
`tofu destroy` tears down all infrastructure resources managed by the current state file. To target a single resource, you must use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web_server`).

**T13** — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
A data source is a mechanism to fetch information about existing infrastructure that is outside the scope of the current configuration.
**Example:** You would use a data source to look up the latest Amazon Machine Image (AMI) ID for a specific region. Instead of managing the AMI itself (which is external), you query the AWS API using a data source to get the current, valid ID, which you then use as an input for your managed `aws_instance` resource.

**T14** — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
**Variable Blocks:** Define external inputs that are passed into the configuration from the outside (e.g., via CLI flags or environment variables). They define the *interface* of the configuration.
**Locals:** Define internal, computed values within the configuration itself. They are used for complex logic, string manipulation, or deriving values based on other variables or resources *after* the inputs have been received.
**When to use locals:** Use locals when you need to perform transformations, calculations, or create complex maps/sets based on existing inputs, rather than simply accepting a raw value from the user.

**T15** — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
The lifecycle block controls how OpenTofu manages the resource during updates and destruction.
*   **`create_before_destroy`:** Creates the new version of the resource *before* destroying the old one. **Use Case:** Database migrations or critical services where downtime must be avoided during an update.
*   **`prevent_destroy`:** Prevents the resource from being destroyed by OpenTofu, even if the configuration dictates its removal. **Use Case:** Protecting critical, manually configured resources (like a primary load balancer) from accidental deletion.
*   **`ignore_changes`:** Tells OpenTofu to ignore specific attributes when calculating drift or planning updates. **Use Case:** When an attribute (like a `last_modified_date` or a tag added manually by an external process) must be allowed to change outside of OpenTofu without triggering an unnecessary update or replacement.

**T16** — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
A `moved` block is used during configuration refactoring (e.g., renaming a resource, moving it to a different module, or changing its address). It explicitly tells OpenTofu: "The resource previously known as `old_address` is now known as `new_address`." This allows OpenTofu to maintain the state association between the physical resource in the cloud and its new logical address in the code, preventing the resource from being incorrectly destroyed and recreated during the refactoring process.

**T17** — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
The dependency graph maps out the execution order of all resources.
**Implicit Dependency:** Occurs when one resource references an attribute of another resource (e.g., `resource_b.id` is used in `resource_a`). OpenTofu automatically infers that `resource_b` must be created before `resource_a`.
**Explicit Dependency:** Defined using `depends_on = [resource_b]`. This forces an execution order regardless of whether an attribute reference exists.
**Impact of `depends_on`:** It forces serialization. If you explicitly depend on Resource B, OpenTofu must wait for B to finish before starting A, even if A could theoretically run in parallel with other resources. This reduces parallelism and increases plan time. It should be used sparingly, only when implicit dependencies are insufficient to guarantee the correct order.

**T18** — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
1.  **Modularization:** Break the monolithic configuration into smaller, focused modules. **Tradeoff:** Increased complexity in managing module dependencies and inputs/outputs.
2.  **State Splitting:** Separate related but independent resources into different state files (e.g., networking state vs. compute state). **Tradeoff:** Requires careful management of cross-state references and increases the number of state files to manage.
3.  **Provider Optimization/Filtering:** Use provider configuration to limit the scope of API calls (e.g., only query specific regions or resource types). **Tradeoff:** Requires deep knowledge of the provider API and may limit future flexibility.
4.  **Parallelism Tuning:** Ensure the backend and provider configuration allow for maximum parallel execution (e.g., setting appropriate concurrency limits). **Tradeoff:** If resources have hidden dependencies, increasing parallelism can lead to race conditions or failed plans.

**T19** — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
**Mechanism:** State locking ensures that only one operation (plan or apply) can modify the state file at any given time. This is typically implemented via a backend feature (e.g., DynamoDB table lock in S3). When an operation starts, it acquires the lock; when it finishes, it releases it.
**Failure to Release:** If a process crashes mid-apply, the lock remains held indefinitely. Subsequent operations will hang, waiting for a lock that will never be released, effectively halting infrastructure changes.
**Manual Break:** You can manually force the release of a lock using the backend provider's specific CLI command (e.g., `aws s3api delete-object` or a specific DynamoDB API call).
**Risks:** Manually breaking a lock bypasses safety checks. If another process is actively running or if the state file is in an inconsistent state, forcing the lock release can lead to state corruption, data loss, or resource duplication.

**T20** — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
1.  **Configure Remote Backend:** Update the `backend` block in the configuration to point to the S3 bucket and DynamoDB table.
2.  **Initialize with Migration:** Run `tofu init`. OpenTofu detects the existing local state and prompts the user to migrate it to the new remote backend.
3.  **Migration Execution:** OpenTofu uploads the contents of the local state file to the S3 bucket and registers the necessary metadata in DynamoDB. The local state file is effectively replaced by the remote state.
4.  **Verification:** Run `tofu plan`. If the migration was successful, OpenTofu will successfully connect to the remote backend, download the state, and generate a plan based on the remote state. If the migration failed, it will report an error connecting to the backend or state file.

**A1** — Easy: What is the difference between an Ansible playbook, a role, and a task?
**Task:** The smallest unit of work in Ansible. It defines a specific action to be performed (e.g., `apt: name=nginx state=present`).
**Playbook:** A YAML file that defines a set of plays. A play is a collection of tasks that are executed against a specific group of hosts, defining the desired state of those hosts.
**Role:** A standardized, reusable structure that groups related tasks, handlers, variables, and templates into a cohesive unit (e.g., a `webserver` role containing all tasks for installing Nginx, configuring firewall, etc.).

**A2** — Easy: What is ansible_facts and how do you access the OS family of a target host?
`ansible_facts` is a dictionary object populated by Ansible during the initial fact-gathering phase, containing extensive information about the target host (OS version, memory, network configuration, etc.). To access the OS family, you would use: `{{ ansible_facts['distribution']['family'] }}`.

**A3** — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
*   **`command`:** Executes a command directly without invoking a shell. It is safer and preferred for simple, non-shell-dependent commands (e.g., `ls -l`).
*   **`shell`:** Executes commands through the system's shell (e.g., `/bin/sh`). It is necessary when you need shell features like pipes (`|`), redirection (`>`), or environment variable expansion.
*   **`raw`:** Executes a command directly on the remote host using the underlying connection mechanism (often used for low-level interaction). It is generally used when you need to execute a command that is not a standard shell command, but it is less common than `command` or `shell`.

**A4** — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
Idempotency means that running the same task multiple times will result in the same system state without causing unintended side effects after the first successful run. Ansible achieves this by using modules that check the current state before making changes.
**Idempotent Example:** `ansible.builtin.file` module. If the directory already exists, the module reports "ok" and makes no changes.
**Non-Idempotent Example:** `ansible.builtin.command: name="echo hello"`. Running this command multiple times will append "hello" to the output or log, changing the state each time.

**A5** — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.

```yaml
- name: Install htop based on OS family
```

**A6** — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
Ansible resolves variables based on a strict precedence order, where variables defined later in the list override those defined earlier. The general order (highest priority first) is:
1.  **`extra_vars`** (Passed via CLI: `-e`)
2.  **`host_vars`** (Host-specific variables)
3.  **`group_vars`** (Group-specific variables)
4.  **Role Defaults** (Variables defined in `defaults/main.yml` within a role)
5.  **Inventory Variables** (Variables defined directly in the inventory file)

**A7** — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
1.  **Inventory Grouping:** Define two groups: `initial_batch` (3 nodes) and `remaining_nodes` (47 nodes).
2.  **Serial Execution:** Use the `serial` keyword in the play to control batch size.
3.  **Workflow:**
    *   Run the play targeting `initial_batch` with `serial: 1` (or 3) to ensure they complete first.
    *   Use `wait_for` in the initial batch tasks to confirm the service is running and reachable.
    *   Run a second play targeting `remaining_nodes` with `serial: 5` (or another batch size) to start the deployment in waves.

**A8** — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
`ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible files.
To encrypt a single variable without encrypting the entire file, you must use the `ansible-vault encrypt` command and specify the exact path to the variable definition, or use a dedicated encrypted variable file structure. For instance, you can place the sensitive variable in a separate file (e.g., `secrets.yml`) and encrypt only that file using `ansible-vault encrypt secrets.yml`.

**A9** — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
An inventory file defines the hosts (servers) that Ansible will manage, along with associated metadata (groups, variables).
**Static Inventory:** A simple text file (INI or YAML format) where hosts and groups are manually listed by the user.
**Dynamic Inventory:** A script or plugin that connects to an external source (e.g., AWS API, Kubernetes cluster) at runtime to automatically discover and populate the list of hosts and their metadata.

**A11** — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
A handler is a special task that is only executed when explicitly notified by another task.
**Difference:** A regular task runs sequentially as part of the play flow. A handler is asynchronous; it waits until all tasks in the play have completed before running, ensuring that services are only restarted *after* configuration changes are complete.
**Triggering:** A task triggers a handler by using the `notify:` keyword, which references the handler's name.

**A12** — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
`ansible.cfg` is a configuration file that controls the behavior of Ansible. It allows users to override default settings globally or per project.
**Common Settings:**
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Defines the default SSH user to connect as.
3.  `roles_path`: Specifies the directory where Ansible should look for roles.

**A13** — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
The `register` keyword captures the output of a task (including stdout, stderr, and return codes) into a variable.
**Usage:**
```yaml
- name: Check service status
  ansible.builtin.service_facts:
    register: service_status

- name: Report status if service is running
  ansible.builtin.debug:
    msg: "Service is running"
  when: service_status.ansible_facts.services['nginx.service'].state == 'running'
```

**A14** — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
**`import_tasks`:** Reads the tasks file as a static YAML file during the parsing phase (compile time). It is faster and is used for including static, non-conditional task lists.
**`include_tasks`:** Reads the tasks file dynamically at runtime. It is used when you need to conditionally include tasks based on runtime variables or facts.
**Conditional Evaluation:** `include_tasks` allows for conditional logic (e.g., `when: some_variable`) to determine which tasks are executed, whereas `import_tasks` is generally static.

**A16** — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
Connection plugins define how Ansible connects to and executes commands on the target host.
*   **`ssh`:** The default. Used for standard Linux/Unix hosts, leveraging SSH for remote command execution.
*   **`local`:** Executes tasks directly on the Ansible control node itself, without connecting remotely. Used for tasks like running local scripts or managing the control machine.
*   **`network_cli`:** Used for managing network devices (routers, switches). It communicates using protocols like Telnet or SSH but is specialized for interacting with device CLIs, not general OS commands.

**A17** — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
**`delegate_to`:** Allows a task to be executed on a host *other than* the host defined in the play. You can delegate to a specific host, a group, or `localhost`.
**`run_once`:** Ensures that a task is executed only once across *all* hosts in the current play, regardless of how many hosts are targeted.
**Practical Example:** Gathering the total number of servers from a remote group and then logging that count on the control node.
```yaml
- name: Get total host count
  ansible.builtin.setup:
    gather_subset: [min]
  delegate_to: localhost
  run_once: true
  register: host_count
```

**A18** — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
1.  **Increase Forks:** Increase the `forks` setting in `ansible.cfg` (e.g., from 5 to 50). This allows Ansible to run multiple hosts in parallel. **Tradeoff:** Increased load on the control node and the target hosts; potential for network saturation.
2.  **Fact Caching:** Use the `ansible_facts_cache` module or configuration to cache gathered facts. This prevents Ansible from re-running the expensive fact-gathering process on every run. **Tradeoff:** Requires a persistent, accessible cache server; the cache might become stale if the host state changes outside of Ansible.
3.  **Pipelining:** Use pipelining (if supported by the connection plugin) to send multiple commands to a single remote host in one SSH session, reducing connection overhead. **Tradeoff:** Can complicate error handling if one command in the pipeline fails.
4.  **Mitogen/Parallel Execution:** Use tools like Mitogen or custom parallel execution frameworks to manage large-scale, complex deployments, allowing for more sophisticated job scheduling than standard Ansible forks. **Tradeoff:** Adds external complexity and dependency management to the automation stack.

**A19** — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
Jinja2 is the templating engine used by Ansible.
*   **`{{ variable }}`:** Used for *printing* or *outputting* the value of a variable.
*   **`{% statement %}`:** Used for *control flow* logic, such as loops (`for`), conditionals (`if/else`), and assignments.
*   **`{# comment #}`:** Used for *comments* within the template that are completely stripped out of the final rendered output.
**Snippet:**
```nginx
upstream backend_servers {
{% for server in backend_list %}
    server {{ server.ip }}:{{ server.port }}; # Health check target
{% endfor %}
}
```

**A20** — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
1.  **Serial Batches:** Use `serial: 4` in the play to deploy to 4 servers at a time, ensuring only a small subset is down at any moment.
2.  **Pre-Task (Deregister):** Before updating the application on a batch, use a task to deregister the batch from the load balancer (LB).
3.  **Deployment Task:** Update the application code/configuration on the batch.
4.  **Health Check:** Use the `uri` module to perform a health check against the newly deployed servers. If the check fails, the deployment fails immediately.
5.  **Post-Task (Register):** If the health check passes, use a task to register the batch back into the LB.
6.  **Rollback Strategy:** Wrap the entire deployment sequence in a `block`/`rescue` structure. If the health check fails (or any task within the block fails), the `rescue` block executes, which runs a task to revert the application code on the affected servers and deregister them from the LB, ensuring the system remains stable.
