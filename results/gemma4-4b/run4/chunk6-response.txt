**JS1**
The difference is scope and reassignment. `var` is function-scoped and hoisted (initialized as `undefined`). `let` is block-scoped and hoisted but uninitialized (Temporal Dead Zone). `const` is block-scoped and must be initialized upon declaration; its binding cannot be reassigned (though object/array contents can be mutated). Hoisting is JavaScript's behavior of moving declarations to the top of their scope during compilation, but not the initialization.

**JS2**
The Event Loop is the mechanism that manages the execution of asynchronous code in JavaScript. It continuously checks the Call Stack and the queues. The Call Stack holds synchronous function calls. When an async operation (like `setTimeout` or network request) completes, its callback is placed in the appropriate queue. The Event Loop moves tasks from the queues to the Call Stack when the stack is empty. The Microtask Queue (e.g., Promises, `queueMicrotask`) has higher priority and is emptied completely before the Event Loop checks the Macrotask Queue (e.g., `setTimeout`, I/O).

**JS3**
A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). It allows an inner function to access variables from its outer function's scope even after the outer function has finished executing.
*Example:* A counter factory: `function createCounter() { let count = 0; return function() { count++; return count; }; }`
*Bug:* The classic `for` loop closure bug occurs when using `var` in a loop, causing all loop iterations to reference the *same* final variable binding.
*Fix:* Use `let` in the loop declaration, as `let` creates a new binding for each iteration, or use an Immediately Invoked Function Expression (IIFE) to create a new scope for each iteration.

**JS4**
A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. `async/await` is syntactic sugar built on top of Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()` or `try...catch` blocks around `await` calls.
* `Promise.all()`: Waits for *all* promises to resolve. If *any* promise rejects, `Promise.all()` immediately rejects with the reason of the first promise that rejected.
* `Promise.allSettled()`: Waits for *all* promises to either resolve or reject. It returns an array of objects describing the outcome of each promise (status: 'fulfilled' or 'rejected').

**JS5**
*Interface:* A contract that defines the *shape* of an object. It describes what properties and methods an object *must* have. Interfaces are purely structural and are used for compile-time type checking.
*Type:* A more general construct that can describe primitive types, unions, intersections, tuples, and object shapes. Types can represent more complex data structures than interfaces.
*Usage:* Use `interface` when defining clear, reusable contracts for object shapes (e.g., API responses). Use `type` when defining unions, aliases for primitives, or complex mapped types.
*Discriminated Unions:* A union type where each member has a unique, literal property (the "discriminant"). This allows TypeScript to narrow the type safely using a `switch` statement or `if` checks on that property.

**JS6**
Prototypal inheritance means that objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. When you access a property on an object, JavaScript looks on the object itself; if not found, it traverses up the prototype chain until it finds it or reaches `null`.
`Object.create(proto)` creates a new object whose internal `[[Prototype]]` is set to the object passed as the first argument (`proto`). This establishes the prototype link directly.
ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance model. They provide a cleaner, more familiar syntax (like classical inheritance) but fundamentally operate using prototypes under the hood.

**JS7**
The `this` keyword refers to the object that is currently executing the function. Its value is determined dynamically based on *how* the function is called, not where it is defined.
The 4 binding rules (in priority order):
1. **New Binding:** When a function is called with `new`, `this` refers to the newly created instance.
2. **Explicit Binding:** When `call()`, `apply()`, or `bind()` are used, `this` is set to the object passed as the first argument.
3. **Implicit Binding:** When a function is called as a method of an object (e.g., `obj.method()`), `this` refers to `obj`.
4. **Default Binding:** If none of the above apply (e.g., a standalone function call), `this` defaults to the global object (`window` in browsers, `global` in Node.js).
`bind()` returns a *new* function with the specified `this` context permanently bound. Yes, you can re-bind the returned function, but the original function's context remains unchanged.

**JS8**
*WeakRef:* A reference to a JavaScript object that does not prevent the object from being garbage collected. It holds a weak reference, meaning if no other strong references exist, the object can be collected, and the `WeakRef` will become invalid.
*FinalizationRegistry:* Allows you to register a callback function that will be executed *after* the associated target object has been garbage collected.
*Usage:* Use `WeakRef` and `FinalizationRegistry` to manage memory and perform cleanup operations on objects without creating memory leaks (e.g., caching metadata about objects that are about to be destroyed).
*WeakMap Keys:* Keys must be objects because the garbage collector needs to track whether the key object is still reachable. If a key were a primitive (like a string), the GC would treat it as a value, and the `WeakMap` would lose track of the association when the key was no longer strongly referenced elsewhere.

**JS9**
V8 optimizes JavaScript by compiling code into highly efficient machine code.
*Hidden Classes (Maps):* V8 tracks the shape (the sequence of properties and their types) of objects. When objects of the same shape are created, V8 assigns them the same "hidden class," allowing it to optimize property access by knowing exactly where the property resides in memory without needing a full hash lookup.
*Inline Caching (IC):* V8 caches the results of recent operations (like property lookups or function calls) directly in the machine code. If the next call matches the cached type/shape, the operation executes extremely fast without re-checking.
*Deoptimization:* If the assumptions V8 made during optimization (e.g., "this object will always have property X as a number") are violated at runtime (e.g., property X suddenly becomes a string), V8 must discard the optimized machine code and revert to a slower, safer interpretation or compilation path.
*Deoptimization Triggers:* Changing the shape of an object (adding/deleting properties), or using dynamic features like `eval()` or complex metaprogramming that break the expected type flow.

**JS10**
Tree-shaking is a form of dead code elimination performed by bundlers (like Webpack or Rollup). It analyzes the static `import`/`export` statements to determine which parts of the dependency graph are actually being used by the application. Unused exports are then omitted from the final bundled output, significantly reducing bundle size.
*ES Modules (ESM):* ESM uses static `import` and `export` syntax, which allows bundlers to perform static analysis reliably, making tree-shaking highly effective.
*CommonJS (CJS):* CJS uses dynamic `require()` calls. Since `require()` can be called conditionally or based on runtime variables, bundlers cannot statically determine which modules are used, making effective tree-shaking impossible without runtime analysis, which defeats the purpose.

**JS11**
*Null vs Undefined:* `undefined` means a variable has been declared but has not yet been assigned a value. `null` is an assignment value, explicitly meaning "no value" or "empty."
*Comparison:* `==` performs type coercion before comparison (e.g., `null == undefined` is `true`). `===` checks for strict equality, requiring both value and type to match (e.g., `null === undefined` is `false`).
*Nullish Coalescing (`??`):* Returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. It differs from `||` because `||` triggers if the left operand is *any* falsy value (like `0` or `""`).
*Optional Chaining (`?.`):* Allows you to safely access deeply nested properties without explicitly checking if each intermediate property exists. If any part of the chain is `null` or `undefined`, the expression short-circuits and returns `undefined`.

**JS12**
*`map()`:* Creates a new array populated with the results of calling a provided function on every element in the calling array. It transforms elements.
*`filter()`:* Creates a new array with all elements that pass the test implemented by the provided function. It selects elements.
*`reduce()`:* Executes a reducer function on each element of the array, resulting in a single output value.
*Reduce with Initial Value:* Providing an initial value (e.g., `0` for summing) sets the accumulator's starting point. The reducer function is called with `(accumulator, currentValue, currentIndex, array)` starting with the initial value as the accumulator.
*`flatMap()`:* First maps each element using a mapping function, and then flattens the result into a new array. It is useful when your mapping function returns an array, and you want the final result to be a single, flat array, rather than an array of arrays.

**JS13**
Template literals (backticks ``) allow for string interpolation and multi-line strings. They allow embedding expressions directly into strings using `${expression}`.
*Tagged Templates:* A function that is executed before the template literal is converted to a string. It receives the literal's static strings and the interpolated values as separate arguments.
*Example (HTML Escaping):*
```javascript
const escapeHtml = (strings, ...values) => {
  let result = strings[0];
  values.forEach((value, i) => {
    const escaped = String(value).replace(/[&<>"']/g, function(match) {
      return { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' }[match];
    });
    result += escaped + strings[i + 1];
  });
  return result;
};
const html = escapeHtml`<h1>Hello ${userInput}</h1>`;
```

**JS14**
Destructuring is a syntax that allows you to unpack values from arrays or properties from objects into distinct variables.
*Object Destructuring:* Extracts properties from an object into variables based on the property name. `const { name, age } = user;`
*Array Destructuring:* Extracts values from an array based on position. `const [first, second] = myArray;`
*Default Values:* Allows you to assign a fallback value if a property/element is missing during destructuring. `const { age = 30 } = user;`
*Renaming:* Allows you to assign the extracted value to a different variable name. `const { name: fullName } = user;`
*Rest Operator (`...`):* When used in destructuring, it collects all remaining, un-destructured properties/elements into a new array or object. `const { id, ...rest } = user;`

**JS15**
*`for...in`:* Iterates over the *enumerable properties* of an object, including inherited enumerable properties (unless filtered). It iterates over keys (property names).
*`for...of`:* Iterates over the *values* of an iterable object (like Arrays, Maps, Sets, Strings).
*Avoid `for...in` on Arrays:* Arrays are objects, and `for...in` iterates over their enumerable properties, which includes custom properties added to the array object, not just the indices. This can lead to unpredictable iteration order and processing of non-index properties. Use `for...of` or `Array.prototype.forEach()` for arrays.

**JS16**
Generics allow you to write reusable components that can work over a variety of types while maintaining type safety.
*Generic Constraints (`extends`):* Restricts the types that can be used with a generic type parameter. `function identity<T extends { length: number }>(arg: T): T { return arg; }` ensures `T` must have a `length` property.
*Conditional Types:* Allows defining types based on a condition. `type IsString<T> = T extends string ? true : false;`
*Infer Keyword:* Used to infer the type of a variable or function parameter based on its usage, often used in utility types. `type MyType = infer T;`
*Practical Example:* A generic function that accepts any object but guarantees it has an `id` property: `function findById<T extends { id: number }>(items: T[]): T | undefined { ... }`

**JS17**
The module system defines how code dependencies are managed.
*CommonJS (CJS):* Synchronous, file-based system used primarily by Node.js. Uses `require()` to import and `module.exports` to export.
*ES Modules (ESM):* Standardized, static system (`import`/`export`). It is asynchronous and designed for static analysis.
*Node.js Handling:* Node.js supports both. By default, `.js` files are CJS. If a file uses `import`/`export` syntax, Node.js treats it as ESM, especially if `"type": "module"` is set in `package.json`.
*`"type": "module"`:* When present in `package.json`, it tells Node.js to treat all `.js` files in that project as ES Modules, enabling native ESM syntax (`import`/`export`) without needing `.mjs` extensions.

**JS18**
TypeScript uses a structural type system, meaning that two types are considered compatible if they have the same structure (the same members with compatible types), regardless of whether they share a common ancestor or explicitly declare an interface relationship.
*Excess Property Checks:* This feature ensures that an object being assigned to a type does not contain properties that are *not* defined in that type. If the object has extra properties, TypeScript throws a compile-time error. This is useful for strict API contracts.
*`extends` vs `satisfies`:*
* `extends`: Used for inheritance. The derived type *is* a subtype of the base type.
* `satisfies`: Used for type checking only. It asserts that the object conforms to the shape of the type, but it does not change the object's actual type.
*Variance (`in`, `out`):* Defines how subtyping works for generic types. `in` (contravariant) means the type can be used as an input (e.g., a function parameter). `out` (covariant) means the type can be used as an output (e.g., a function return type). This allows for safe substitution in generic containers.

**JS19**
*Proxy:* An object that wraps another object (the target) and allows you to intercept fundamental operations performed on that target, such as property lookups, assignments, function calls, and deletions.
*Reflect:* An API that provides methods to perform operations on objects, which Proxies then call. It acts as the underlying mechanism for the Proxy traps.
*Interception:* You define "traps" (e.g., `get`, `set`, `apply`) within the Proxy handler object. When an operation occurs on the proxy, the corresponding trap is triggered, allowing custom logic to run before or instead of the default behavior.
*Example (Validation):* A `set` trap can check if the incoming value meets validation rules before allowing the assignment to the target object.
```javascript
const handler = {
  set(target, property, value) {
    if (property === 'age' && typeof value !== 'number' || value < 0) {
      throw new Error("Invalid age provided.");
    }
    target[property] = value;
    return true;
  }
};
const user = new Proxy({ age: 25 }, handler);
// user.age = "twenty"; // Throws error
```

**JS20**
*SharedArrayBuffer (SAB):* A low-level JavaScript object that allows multiple threads (Web Workers) to share the same block of raw binary memory. This avoids the overhead of message passing.
*Atomics:* A set of methods that operate on `SharedArrayBuffer` data. They guarantee that operations (like incrementing a counter) are performed atomically—meaning they complete entirely without interruption from other threads, preventing race conditions.
*Communication:* Workers share the SAB, and use `Atomics` methods to coordinate access to the shared memory.
*Ordering Guarantees:* Atomics operations provide memory ordering guarantees, ensuring that memory writes performed before an atomic operation are visible to other threads before the atomic operation completes.
*`Atomics.wait/notify`:* These functions allow threads to pause execution (`wait`) until another thread signals them (`notify`) on a specific memory location, enabling efficient, low-overhead synchronization instead of busy-waiting.

**B1**
*`$@`:* Expands to all positional parameters as separate, quoted arguments. It preserves the individual arguments, even if they contain spaces.
*`$*`:* Expands to all positional parameters as a single string, separated by the first character of the `$IFS` (Internal Field Separator) variable (usually space).
*`"$@"` vs `"$*"`:* When quoted, both expand to separate arguments, but `$@` is the standard, safer way to handle arguments containing spaces, as it respects the original argument boundaries. `"$*"` treats the entire set of arguments as one single string argument.

**B2**
`set -euo pipefail` is a robust shell configuration designed to make scripts fail fast and predictably.
* `-e` (errexit): Causes the script to exit immediately if any command exits with a non-zero status (i.e., fails).
* `-u` (nounset): Causes the script to exit immediately if it tries to use an uninitialized variable.
* `-o pipefail`: Causes a pipeline to return a non-zero exit status if *any* command in the pipeline fails, not just the last one.

**B3**
*`$(command)` (Command Substitution):* Executes the `command` and substitutes its standard output into the current command line. This output is treated as a string or argument list.
*`command` (Direct Execution):* Executes the command directly.
*`$((expression))` (Arithmetic Expansion):* Evaluates a mathematical expression within the shell.
*`expr` (External Command):* Executes the external `expr` utility to perform arithmetic.
*Difference:* `$((...))` is native shell arithmetic, faster and cleaner than calling the external `expr` command.

**B4**
Process substitution (`<(command)`) runs a command in a subshell and makes the *output* of that command appear as a temporary file path that the current shell can read from.
*Use Case:* It allows commands that expect a file path as input (like `diff` or `grep`) to operate on the output of another command without needing to pipe the output to a temporary file first.
*Example:*
```bash
diff <(ls -l /etc/passwd) <(ls -l /etc/shadow)
```
This compares the output of `ls -l /etc/passwd` against the output of `ls -l /etc/shadow` as if they were two separate files.

**B5**
The safest way is to use `find` combined with `while read -r` loop and null termination (`-print0` and `read -d ''`).
*Dangerous:* `for f in $(ls)` is dangerous because `$(ls)` splits the output based on the `$IFS` variable (usually space, tab, newline). If a filename contains a space (e.g., `My Document.txt`), it will be split into two separate tokens (`My` and `Document.txt`), causing the loop to process two incorrect items.
*Safe Method:*
```bash
find . -type f -print0 | while IFS= read -r -d $'\0' f; do
    echo "Processing: $f"
done
```

**B6**
*Here Document (`<<EOF`):* Reads input from standard input until it encounters a line containing only the delimiter (`EOF`). The content is treated as literal text, preserving newlines and whitespace.
*Here String (`<<<`):* Passes a single string as standard input to a command. It is used for short, single-line inputs.
*`<<-EOF` (Here Document with Tab Expansion):* This variant treats leading tabs in the input lines as whitespace characters, rather than expanding them as tabs. This is useful for writing configuration files where indentation must be preserved literally.

**B7**
The key difference lies in *when* the redirection happens relative to the command execution.
1. `cmd > file 2>&1`: First, stdout (`> file`) is redirected to `file`. Then, stderr (`2`) is redirected to the current location of stdout (`&1`), which is `file`. **Result: Both stdout and stderr go to `file`.**
2. `cmd 2>&1 > file`: First, stderr (`2`) is redirected to stdout (`&1`). Then, stdout (`> file`) is redirected to `file`. **Result: Both stdout and stderr go to `file`.** (In modern shells, these often behave identically, but the order matters conceptually.)
3. `cmd &> file`: This is a shorthand (Bash 4+) that redirects both stdout and stderr to `file` simultaneously.
*Why the difference (conceptually):* In older or stricter shells, if you redirect stdout first, the subsequent `2>&1` points to the *original* stdout location, not the new file. The order dictates the target of the redirection.

**B8**
A robust locking function uses `mkdir` because it is an atomic operation at the filesystem level.
```bash
LOCK_DIR="/tmp/mylockdir"
LOCK_FILE="$LOCK_DIR/lock"

acquire_lock() {
    if mkdir "$LOCK_DIR" 2>/dev/null; then
        echo "Lock acquired."
        trap "rmdir $LOCK_DIR" EXIT TERM INT
        return 0
    else
        echo "Lock already held."
        return 1
    fi
}

release_lock() {
    # Cleanup is handled by the trap, but explicit release is good practice
    rmdir "$LOCK_DIR" 2>/dev/null
}

# Usage:
acquire_lock || exit 1
# ... main script logic ...
```
*Why `mkdir` is preferred:* `mkdir` is an atomic operation. If two processes try to create the same directory simultaneously, only one will succeed. File creation (`touch`) is not guaranteed to be atomic across all filesystems and can lead to race conditions where both processes believe they successfully created the file.

**B9**
*Single Quotes (`'...'`):* Literal interpretation. No variable expansion, no command substitution. Everything inside is treated as a literal character.
*Double Quotes (`"..."`):* Variable expansion and command substitution are performed. `$VAR` expands to the variable's value, and `` `command` `` executes the command.
*No Quotes:* Word splitting and pathname expansion (globbing) occur based on the `$IFS` variable.
*Example:*
```bash
VAR="hello world"
echo 'The value is $VAR'  # Output: The value is $VAR
echo "The value is $VAR" # Output: The value is hello world
echo $VAR              # Output: hello world (if IFS is space)
```

**B10**
*File Exists:* `[ -e file ]` or `[[ -e file ]]`
*Is Directory:* `[ -d file ]` or `[[ -d file ]]`
*Is Readable:* `[ -r file ]` or `[[ -r file ]]`
*Difference between `[ ]` (test) and `[[ ]]` (Bash keyword):*
`[ ]` is an alias for the `test` command. It is older, less feature-rich, and requires careful quoting of variables.
`[[ ]]` is a Bash keyword (a conditional expression). It supports regex matching (`=~`), logical operators (`&&`, `||`), and is generally safer and more powerful.

**B11**
*`$?`:* The exit status of the most recently executed foreground command (0 means success, non-zero means failure).
*`$$`:* The Process ID (PID) of the current shell script.
*`$!`:* The PID of the most recently executed background command (a command run with `&`).
*`$#`:* The number of positional arguments passed to the current script or function.
*Use Case:* `$?` is used immediately after a command to check for errors. `$$` is used for logging or PID tracking. `$!` is used to monitor background jobs. `$#` is used to validate required inputs.

**B12**
*Definition:* Functions are defined using `function name { ... }` or the shorthand `name() { ... }`.
*Difference:* `function foo {}` is the traditional syntax. `foo() {}` is the modern, preferred shorthand. Functionally, they are nearly identical in modern Bash, but the shorthand is cleaner.
*Returning Values:* Bash functions do not return values in the traditional sense. They return an exit status (0-255) via `$?`. To pass data back, you must use global variables, pass variables as arguments, or use `echo` and capture the output via command substitution: `result=$(my_function arg1)`.

**B13**
*PATH:* An environment variable that contains a colon-separated list of directories where the shell searches for executable commands.
*Command Resolution:* When you type a command, the shell searches through the directories listed in `$PATH` sequentially until it finds an executable file matching the command name.
*Builtin vs External:*
*Builtin:* Commands that are part of the shell itself (e.g., `cd`, `echo`, `read`). They execute internally within the shell process, making them very fast.
*External:* Separate executable programs located in the directories specified by `$PATH` (e.g., `ls`, `grep`).
*Checking:* You can check if a command is built-in using `type -a command_name`. If it shows `builtin`, it's built-in.

**B14**
`trap` is a shell built-in command used to catch and handle signals sent to the shell or script. It allows you to execute specific commands when a signal is received.
*Setup:* `trap 'command_to_run' SIGNAL_NAME`
*Handlers:*
* `EXIT`: Runs when the script exits, regardless of success or failure. Ideal for cleanup.
* `ERR`: Runs when a command exits with a non-zero status (requires `set -e`).
* `INT`: Interrupt signal (usually Ctrl+C).
* `TERM`: Termination signal (graceful shutdown request).
*Execution Order:* Signals are generally processed in the order they are trapped, but the shell handles signal delivery based on OS rules. If multiple signals arrive rapidly, the shell processes them sequentially based on its internal signal handling queue.

**B15**
*`xargs` vs Command Substitution:* Command substitution (`$(cmd)`) runs the command and captures its output as a single string/argument list. `xargs` takes input from stdin and builds and executes command lines from that input.
*Handling Spaces/Newlines:* `find . -print0` outputs filenames separated by the null character (`\0`). `xargs -0` tells `xargs` to expect null-terminated input, correctly treating filenames containing spaces or newlines as single arguments.
*Parallel Execution (`xargs -P`):* The `-P N` flag tells `xargs` to run up to $N$ processes in parallel. This is crucial for speeding up I/O-bound or CPU-bound tasks on large datasets.

**B16**
*Bash Arrays (Indexed):* Ordered lists accessed by integer indices starting from 0.
*Declaration:* `my_array=(item1 item2 item3)`
*Append:* `my_array+=("new_item")`
*Iterate:* `for item in "${my_array[@]}"; do ... done`
*Length:* `${#my_array[@]}`
*Associative Arrays (Keyed):* Maps that associate string keys with values.
*Declaration:* `declare -A my_assoc_array`
*Append/Set:* `my_assoc_array["key_name"]="value"`
*Iterate:* `for key in "${!my_assoc_array[@]}"; do echo "$key: ${my_assoc_array[$key]}"; done`
*Length:* `${#my_assoc_array[@]}`
*Difference:* Indexed arrays rely on numerical order; associative arrays rely on arbitrary string keys, providing O(1) lookup time by key.

**B17**
*Subshell (`(...)`):* Executes commands in a separate, isolated process. Any variables modified inside the subshell are lost when it exits, and its exit code is returned to the parent.
*Group Command (`{ ...; }`):* Executes commands in the *current* shell process group. Variables modified inside persist in the parent shell.
*Variable Scope:* Subshells create a new environment; group commands share the environment.
*Exit Codes:* The exit code of the subshell is the exit code of the last command executed within it. The exit code of the group command is the exit code of the last command executed within it.
*Piping into `while` loop:* When you pipe output into a `while` loop (`while read line; do ... done < <(command)`), the loop runs in a subshell. Any variable modifications made inside the loop are confined to that subshell and are lost when the loop finishes, meaning the parent shell's variables remain unchanged.

**B18**
*Signals:* Notifications sent to a process to request or inform it of an event.
*SIGINT (Interrupt):* Sent by Ctrl+C. Requests the process to stop gracefully.
*SIGTERM (Terminate):* The standard, polite request for a process to shut down. Allows the process to clean up resources before exiting.
*SIGHUP (Hangup):* Sent when a controlling terminal is closed. Often used to signal daemons to reload configuration files without stopping.
*SIGKILL (Kill):* A non-catchable, immediate termination signal. The kernel forces the process to stop instantly; no cleanup is performed.
*Graceful Shutdown:* To handle background processes, the main script must trap `SIGTERM` and `SIGINT`. The trap handler should iterate over all background jobs (`jobs -p`) and send them a `SIGTERM` signal, waiting for them to confirm shutdown before the main script exits.

**B19**
This script uses parallel processing for speed, but requires careful error handling.
```bash
# 1. Define the processing function
process_file() {
    local input_file="$1"
    # Simulate work and potential failure
    if [[ "$input_file" == *"error"* ]]; then
        echo "ERROR processing $input_file" >&2
        return 1 # Signal failure
    fi
    # Actual processing logic here
    echo "Processed: $input_file"
}

# 2. Split and process in parallel
find /path/to/logs -name "*.log" -print0 | xargs -0 -P 4 -I {} bash -c 'process_file "$@"' _ {}

# 3. Error Propagation (Crucial Step)
# Since xargs runs in a subshell, its exit code might mask individual job failures.
# A more robust method involves checking the return status of the function call
# or using a job control mechanism to track individual PIDs.
# For simple logging, we rely on stderr output from the function.
```
*Performance Trade-offs:* Parallel processing drastically reduces wall-clock time for I/O-bound tasks (like reading many files). However, it increases CPU overhead due to context switching and resource contention.
*Error Propagation:* Standard `xargs` does not reliably propagate the failure status of individual parallel jobs back to the parent script. To handle this robustly, you must wrap the job execution in a function that explicitly captures the exit code (`$?`) for each job, or use job control features to monitor PIDs.

**B20**
*`exec` vs Normal Command:*
*Normal Command:* Runs the command in a new child process. The parent shell continues execution after the child finishes.
*`exec`:* Replaces the current shell process image with the new command. The shell itself is replaced; it does not continue execution afterward.
*File Descriptor Manipulation:* `exec 3>file` opens a file and assigns it to file descriptor 3. `exec 3>&-` closes file descriptor 3. This is used to manage persistent file handles within the shell environment.
*Bash Coprocess:* A coprocess allows the parent shell to communicate with a child process using named pipes (FIFOs) for bidirectional communication, without the child process needing to be a background job.
*When to use:* Use a coprocess when you need continuous, interactive, or structured communication between the parent and child processes, rather than a single input/output exchange (like piping).

**PS1**
*`Write-Output`:* Sends objects down the pipeline. This is the standard, idiomatic way to output data in PowerShell, allowing subsequent cmdlets to process the object.
*`Write-Host`:* Writes directly to the console/host buffer. It bypasses the pipeline and is used for displaying formatted messages, status updates, or simple text that should not be processed by other cmdlets.
*Pipeline Matter:* If you use `Write-Host`, the object is not passed to the next cmdlet. If you use `Write-Output`, the object is correctly formatted and passed down the pipeline for further processing.

**PS2**
The PowerShell pipeline passes objects, not just strings, from one cmdlet to the next.
*`ForEach-Object` (Pipeline Cmdlet):* This cmdlet processes objects as they flow through the pipeline. It is designed to be used *after* a source cmdlet.
*`foreach` (Script Block):* This is a standard PowerShell language construct used to iterate over a collection (array, list, etc.) that is already loaded into memory.
*Appropriate Use:* Use `ForEach-Object` when you are chaining cmdlets (e.g., `Get-Service | ForEach-Object { ... }`). Use `foreach` when you have a pre-existing collection variable (e.g., `$servers = Get-Content servers.txt; foreach ($s in $servers) { ... }`).

**PS3**
*`[PSCustomObject]`:* A lightweight, dynamic object created at runtime that allows you to define properties and values on the fly. It is ideal for creating structured data from disparate sources.
*`[hashtable]`:* A collection of key-value pairs, similar to a dictionary or map. It is optimized for lookups by key.
*Usage:* Use `[PSCustomObject]` when you need a fixed, named structure (like a record). Use `[hashtable]` when you need a flexible map where keys might change or when you are implementing dictionary-like behavior.
*Conversion:*
* Hashtable to PSCustomObject: `[PSCustomObject]@{Name = $ht.Name; Age = $ht.Age}`
* PSCustomObject to Hashtable: `$obj | Select-Object * | ConvertTo-Hashtable` (though this is often complex; direct iteration is usually better).

**PS4**
PowerShell distinguishes between two error types:
*Terminating Errors:* Errors that stop the execution of the current script block or function immediately (e.g., file not found when using `-ErrorAction Stop`).
*Non-Terminating Errors:* Errors that are logged but allow the script to continue execution.
*Interaction:*
* `-ErrorAction`: Modifies how a specific command handles errors (e.g., `Stop`, `Continue`, `SilentlyContinue`).
* `$ErrorActionPreference`: Sets the default behavior for *all* cmdlets in the current scope (e.g., setting it to `Stop` makes most cmdlets throw terminating errors).
* `try/catch`: Allows you to explicitly wrap code. If a terminating error occurs within the `try` block, execution jumps immediately to the `catch` block, allowing you to handle it gracefully without stopping the script.

**PS5**
Splatting (`@params`) is a technique used to pass a hashtable as a set of named parameters to a cmdlet. It allows you to define all parameters in a single, readable data structure, making code cleaner and easier to reuse.
*Example:*
```powershell
$serverParams = @{
    ComputerName = "Server01"
    Credential   = $cred
    Port         = 3389
}
Invoke-Command @serverParams
```
*Difference from passing a hashtable as a single parameter:* If you pass a hashtable as a single parameter, the cmdlet must be explicitly designed to accept that hashtable as a parameter type. Splatting automatically unpacks the key/value pairs of the hashtable and maps them to the named parameters of the target cmdlet.

**PS6**
PowerShell Remoting allows management of remote computers.
*`Invoke-Command -ComputerName`:* Executes a script block or command on a remote machine *once* or multiple times, returning the results immediately. It is best for quick, non-interactive tasks.
*`Enter-PSSession`:* Establishes an interactive, persistent connection (a session) to the remote machine. You are dropped into a remote PowerShell prompt and can run multiple commands sequentially as if you were logged in.
*Protocol:* PowerShell Remoting primarily uses **WinRM (Windows Remote Management)** over HTTP/HTTPS. While SSH can be used for Linux/Unix remoting, WinRM is the native protocol for Windows management.

**PS7**
The pipeline in PowerShell passes *objects*. When you use `return $result` where `$result` is an array, PowerShell implicitly wraps that array into a single object that represents the collection, but the type system can be tricky.
*The Issue:* When a function returns an array, the calling context often treats the return value as a single object containing the array, or the array itself is treated as a single item in the pipeline. If the function returns nothing (or an empty array), the pipeline receives nothing.
*Type:* In the example, `$x.GetType().Name` would likely be `System.Object` or `System.Array` depending on how the return value is captured, but the key is that the pipeline expects objects.
*Correct Pattern:* To ensure the function behaves correctly in the pipeline, it should explicitly output the items one by one using `Write-Output` inside the function, or ensure the return value is explicitly cast to an array of objects if you intend to treat it as a collection.

**PS8**
*`[scriptblock]`:* A block of code that can be passed around and executed later. It is essentially a compiled unit of code.
*Function:* A named, reusable block of code that accepts parameters and returns results.
*Passing to Remote Session:* You pass a scriptblock using the `-ScriptBlock` parameter of `Invoke-Command`.
*Double-Hop Problem:* This occurs when you try to use a variable defined in the *local* session (the session initiating the remote call) inside a scriptblock running on the *remote* session. The variable is not automatically serialized across the hop.
*Solution:* Use `Invoke-Command -ArgumentList` to explicitly pass the local variable into the remote scriptblock, or use `Get-PSSession | Set-PSSession -Name ...` to establish a persistent session where variables can be managed more easily.

**PS9**
*`@()`:* An empty array literal. It is a collection object.
*`[array]`:* The type accelerator used to explicitly declare a variable as an array type.
*Forcing Single Result:* To force a single result into an array, you must wrap it: `$myArray = @($singleItem)`.
*Indexing:* Indexing `$null` throws a terminating error because `$null` is not an object with properties. Indexing an empty array (`@()`) returns `$null` without error, as it is a valid, empty collection.

**PS10**
*`-eq` (Equal):* Case-insensitive equality comparison.
*`-ne` (Not Equal):* Case-insensitive inequality comparison.
*`-like` (Wildcard):* Pattern matching using wildcards (`*`, `?`). Case-insensitive by default.
*`-match` (Regex):* Pattern matching using regular expressions. Case-insensitive by default.
*`-contains`:* Checks if a specific *value* exists within an array or collection.
*`-in`:* Checks if a specific *value* exists within a list of possible values (e.g., `$value -in @('A', 'B')`).
*Case-Sensitive Variants:* `-ceq`, `-clike`, `-cmatch` perform the same operations but require an exact case match.
*Difference between `-contains` and `-in`:* `-contains` checks if an element is present in a collection. `-in` checks if a value matches one of several possibilities provided in a list.

**PS11**
*Module:* A container for reusable PowerShell code (cmdlets, functions, variables, aliases).
*Script Module (`.psm1`):* A file containing functions and definitions that are loaded into the current session's scope when imported.
*Manifest Module (`.psd1`):* A metadata file that describes the module (version, dependencies, required parameters) but does not contain the code itself. It points to the `.psm1` files.
*Binary Module:* A compiled module, often used for performance or distribution, which is loaded directly.
*`Import-Module`:* Loads the module's definitions (functions, cmdlets) into the current PowerShell session's scope, making them available for use.

**PS12**
*String Interpolation:* Allows embedding variables and expressions directly into a string using double quotes.
*`"..."` (Double Quotes):* Enables variable expansion and expression evaluation.
*`'...'` (Single Quotes):* Literal string. No expansion occurs; variables are treated as literal text.
*Expressions:* Expressions are enclosed in curly braces: `"The result is $($variable * 2)"`.
*Here-String (`@"...@"@`):* A multi-line string literal that supports interpolation and preserves formatting, similar to template literals in JavaScript. It is delimited by the start and end markers.

**PS13**
*`Get-Member`:* Returns a list of properties and methods available on an object, providing introspection into its structure.
*Exploring Objects:* You pipe an object to `Get-Member` to see what capabilities it has.
*Properties:* Data fields associated with the object (e.g., `$user.Name`).
*Methods:* Functions that can be called on the object (e.g., `$user.CalculateTotal()`).
*NoteProperties:* Properties that are not directly accessible but are stored internally (less common for general use).
*`Select-Object` vs `Where-Object`:*
*`Select-Object`:* Used to *choose* which properties to display or to *rename* properties. It shapes the output.
*`Where-Object` (or `?`):* Used to *filter* objects based on a condition. It determines which objects pass through the pipeline.

**PS14**
*PowerShell Classes:* Introduced in v5, these allow object-oriented programming paradigms (inheritance, encapsulation) within PowerShell. They are implemented using classes and methods.
*Difference from C# Classes:* PowerShell classes are generally less strict than C# classes. They are designed to integrate seamlessly with the dynamic nature of PowerShell. While they support inheritance, they often rely on PowerShell's dynamic nature rather than strict compile-time enforcement.
*Limitations:* Inheritance and interfaces are supported, but the ecosystem is less rigid than a pure C# environment. Constructors are used, but the dynamic nature means runtime behavior is highly flexible.
*When to use:* Use a class when you need to model a complex, persistent entity with defined state and behavior (e.g., a `DatabaseConnection` object or a `UserAccount` object) that needs to be passed around and maintained across multiple operations. Use a function for simple, stateless operations.

**PS15**
*`CmdletBinding()`:* An attribute that allows a function to behave like a full-fledged cmdlet. It automatically grants the function standard cmdlet features like parameter validation, pipeline support, and error handling.
*Enables:* It enables advanced features like parameter sets, pipeline input, and automatic support for common parameters (`-Verbose`, `-Debug`).
*`SupportsShouldProcess`:* When set to `$true`, the cmdlet will prompt the user with a confirmation message (e.g., "Are you sure you want to delete X?") before executing destructive actions, unless the `-Force` parameter is used.
*`DefaultParameterSetName`:* Specifies which parameter set should be used if the user does not explicitly specify one.
*`ValueFromPipeline`:* Allows the cmdlet to accept input objects from the pipeline and assign those objects to a specific parameter.
*Blocks:*
* `Begin`: Runs once before any input is processed (setup).
* `Process`: Runs for every object received from the pipeline (the main work).
* `End`: Runs once after all input has been processed (cleanup).

**PS16**
*Providers System:* PowerShell uses providers to abstract the underlying data source. Instead of having separate cmdlets for every type of data, a single cmdlet (`Get-ChildItem`) uses a provider to determine *where* to look.
*How `Get-ChildItem` Works:* When you run `Get-ChildItem`, PowerShell checks the drive/path prefix. If it's `C:\`, it uses the `FileSystem` provider. If it's `HKLM:`, it uses the `Registry` provider.
*Accessing Registry:* You access the registry using the `Registry` provider syntax, treating registry keys like file paths: `Get-ChildItem -Path "Registry::HKEY_LOCAL_MACHINE\SOFTWARE"`.

**PS17**
*Runspaces:* An isolated execution environment where PowerShell commands run. They manage the state, environment, and execution context.
*`[runspace]`:* A basic execution context.
*`[runspacepool]`:* A managed pool of runspaces. Instead of creating a new runspace for every task, the pool reuses existing ones, significantly reducing overhead for high-volume parallel tasks.
*Parallel Execution:*
* `ForEach-Object -Parallel` (v7+): This cmdlet handles the creation, management, and cleanup of the necessary runspaces internally, providing a simple, high-level abstraction for parallel loops.
* Manual Management: In older versions or complex scenarios, you manually create and manage `[runspacepool]` objects, submitting jobs to them, and waiting for results.
*Thread Safety:* Runspaces provide isolation, but shared resources (like external files or network connections) must be managed carefully to avoid race conditions.

**PS18**
*PSScriptAnalyzer:* A static code analysis tool that checks PowerShell scripts against a defined set of best practices, style guides, and security standards.
*Enforcement:* It scans code for potential bugs, performance anti-patterns, and adherence to conventions.
*Rules:* Specific checks (e.g., "Do not use `Invoke-Expression`").
*Severity Levels:* Rules are assigned levels (e.g., `Warning`, `Error`, `Information`) to indicate the potential impact of the violation.
*Custom Rules:* Users can write their own analyzer rules to enforce organization-specific standards.
*CI/CD Integration:* PSScriptAnalyzer is typically integrated into CI/CD pipelines (e.g., Azure DevOps, GitHub Actions) as a mandatory build step. If the analyzer finds rules above a certain severity threshold, the build fails, preventing non-compliant code from being merged.

**PS19**
*`$using:` Scope:* Used when passing variables into parallel jobs (`ForEach-Object -Parallel`) or background jobs. It creates a read-only copy of the variable from the parent scope, allowing the remote job to access the value without serialization issues.
*`$args/-ArgumentList`:* Used when passing variables to remote sessions (`Invoke-Command`). These arguments are serialized (often using CLIXML) and passed to the remote session.
*Serialization Limits:* CLIXML (the serialization format for remoting) has depth and size limits. Complex, deeply nested objects, or objects containing large binary data, can exceed these limits, causing the remote execution to fail with serialization errors.
*Impact:* If an object is too complex, it cannot be reliably passed across the remoting boundary, forcing the developer to pass only primitive types or simple, flat structures.

**PS20**
*Desired State Configuration (DSC):* A management framework that allows administrators to define the desired state of a system (e.g., "IIS must be installed," "Registry key X must equal Y") and ensures the system remains in that state, automatically remediating drift.
*Configurations:* The high-level blueprint defining the desired state (e.g., "Web Server Configuration").
*Resources:* The atomic components within a configuration that perform the actual work (e.g., the `WindowsFeature` resource ensures IIS is installed).
*Local Configuration Manager (LCM):* The engine on the target node that reads the configuration, determines the current state, and executes the resources to enforce the desired state.
*DSC Differences:*
*Windows PowerShell:* DSC was tightly integrated into Windows Server roles.
*PowerShell 7+:* DSC functionality has been modernized and made more cross-platform, moving towards a more standardized, modular approach.
*Modern Replacement:* While DSC is still used, modern Infrastructure-as-Code (IaC) tools like **Terraform** (for provisioning) and **Ansible** (for configuration management) have largely superseded DSC for broad, multi-platform infrastructure automation.
