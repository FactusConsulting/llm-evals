**AA1**
The monolith is a single, tightly coupled application where all business logic resides in one codebase. Microservices are a suite of small, independently deployable services, each running its own process and communicating via lightweight mechanisms.
Problems microservices introduce:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication.
2. **Operational Overhead:** Increased complexity in deployment, monitoring, and logging across dozens of services.
3. **Data Consistency:** Managing transactions across multiple, independent databases (distributed transactions).

**AA2**
**Synchronous communication** requires the calling service to wait for an immediate response from the called service. Example: REST/HTTP (e.g., a client making a GET request to an API).
**Asynchronous communication** involves sending a message or event without waiting for an immediate response; the sender continues processing. Example: Kafka or RabbitMQ.

**AA3**
A **Reverse Proxy** sits in front of one or more servers, routing incoming client requests to the appropriate backend server based on rules (e.g., path, host header). It primarily handles traffic distribution, SSL termination, and caching.
An **API Gateway** sits in front of microservices, acting as a single entry point for clients. It handles routing, but also adds cross-cutting concerns like authentication, rate limiting, request transformation, and protocol translation.
No, an API Gateway cannot entirely replace a reverse proxy. A reverse proxy is a fundamental network component for load balancing and traffic routing at the infrastructure level. An API Gateway is an *application-level* abstraction layer built *on top* of routing capabilities, adding business logic and security enforcement.

**AA4**
The Saga pattern manages distributed transactions by breaking a large transaction into a sequence of local transactions. If any local transaction fails, the Saga executes compensating transactions to undo the preceding successful transactions, maintaining data consistency.
**Choreography-based:** Services communicate by producing and consuming events. There is no central coordinator; each service knows what to do based on the events it receives. Appropriate when services are highly decoupled and the workflow is simple.
**Orchestration-based:** A dedicated service (the Orchestrator) manages the workflow, telling each participant service what local transaction to execute. Appropriate when the workflow is complex, requires centralized visibility, or needs strict control over the sequence of steps.

**AA5**
**CQRS** separates the model used for updating data (Commands) from the model used for reading data (Queries). This allows optimization of read and write paths independently.
It is often paired with **Event Sourcing (ES)** because ES stores the state of the application as a sequence of immutable events. The write model (Command side) persists these events. The read model (Query side) then projects these events into optimized, denormalized views (e.g., a relational table or document store) for fast querying.
This combination solves the problem of complex, evolving read requirements in a traditional CRUD model. In CRUD, the write model must support all read needs, leading to complex, slow joins. With CQRS/ES, the read model can be tailored perfectly for specific query patterns without affecting the transactional integrity of the write model.

**AA6**
The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service).
The three states are:
1. **Closed:** Requests pass through normally. If failures exceed a threshold, the breaker trips to Open.
2. **Open:** Requests are immediately rejected without attempting the call, failing fast, allowing the downstream service time to recover.
3. **Half-Open:** After a timeout, a limited number of test requests are allowed through. If they succeed, the breaker returns to Closed; if they fail, it returns to Open.
It differs from simple retry with backoff because retry attempts continue hammering a failing service, potentially exacerbating the failure (cascading failure). You use both together: the Circuit Breaker prevents the flood of requests, and the retry mechanism handles transient, expected failures *within* the Closed state.

**AA8**
**Strong Consistency** guarantees that once a write operation is acknowledged, all subsequent read operations will immediately see that write.
**Eventual Consistency** guarantees that if no new updates are made to a data item, eventually all accesses to that item will return the last updated value, but there is a period where reads may return stale data.
To prevent overselling inventory (a critical business invariant), you must enforce **Strong Consistency** for the inventory count.
*   **Data Store:** A transactional relational database (e.g., PostgreSQL, MySQL) or a strongly consistent distributed ledger/database (e.g., CockroachDB, Spanner).
*   **Patterns:** Use pessimistic locking or atomic database transactions (e.g., `UPDATE inventory SET stock = stock - 1 WHERE item_id = X AND stock > 0 RETURNING stock;`). The transaction must succeed entirely before the order is confirmed.

**AA9**
A **sidecar proxy** is a small, dedicated proxy container deployed alongside every instance of a service container within the same deployment unit (e.g., a Kubernetes Pod). It intercepts all inbound and outbound network traffic for the main application container.
In an Istio deployment, **Envoy** is the high-performance L7 proxy that runs as the sidecar. It handles service discovery, traffic routing, metrics collection, and policy enforcement for the application.
**Data Plane:** The set of proxies (Envoy sidecars) that actually handle the network traffic (forwarding, routing, encryption).
**Control Plane:** The management layer (e.g., Istiod) that configures and manages the proxies in the data plane, pushing routing rules, security policies, and configuration updates.
mTLS between sidecars solves the problem of *service-to-service* encryption and authentication without requiring the application code itself to manage certificates, key rotation, or TLS handshake logic. The sidecar handles the cryptographic negotiation transparently, ensuring that only authenticated, authorized services can communicate.

**AA10**
The **Strangler Fig pattern** involves gradually replacing specific functionalities of a legacy system by building new services around it. The new services intercept calls intended for the monolith, and over time, the monolith is "strangled" until it can be decommissioned.
**Migration Strategy:**
1. **Identify Seams:** Identify a low-risk, bounded context in the monolith (e.g., User Profile Management).
2. **Implement Facade/Proxy:** Place an API Gateway in front of the monolith.
3. **Build New Service:** Reimplement the User Profile functionality as a new, independent .NET 8 microservice.
4. **Reroute Traffic:** Configure the API Gateway to route all `/api/user/*` requests to the new .NET 8 service, while all other requests still go to the monolith.
5. **Iterate:** Repeat this process for other bounded contexts until the monolith is reduced to a minimal core or retired.

**AA11**
The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable, and resilient software-as-a-service applications.
Six factors and their importance:
1. **Codebase:** One codebase tracked in revision control, many deploys. (Enables CI/CD).
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures environment consistency).
3. **Config:** Store configuration in the environment. (Decouples code from environment, crucial for cloud portability).
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. (Allows swapping providers easily).
5. **Build, Release, Run:** Strictly separate build, release, and run stages. (Enables immutable deployments).
6. **Processes:** Execute the app as one or more stateless processes. (Essential for horizontal scaling).

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Temporal and spatial decoupling) | Tight (Synchronous dependency) |
| **Scalability** | High (Consumers scale independently) | Moderate (Limited by synchronous request/response chain) |
| **Debugging Complexity** | High (Tracing event flow across many consumers is hard) | Low (Clear request/response path) |
| **Ordering Guarantees** | Guaranteed within a partition/topic | Guaranteed by the request sequence |
| **Failure Handling** | Built-in (Consumers can replay events; dead-letter queues) | Requires explicit retry logic and circuit breakers |

**Choice:** Choose **Event-Driven** when high throughput, decoupling, and asynchronous processing are paramount (e.g., logging, notifications, order fulfillment pipelines). Choose **Request-Driven** when an immediate, synchronous response is required for the user interaction (e.g., login validation, fetching a specific resource).

**AA13**
A **Load Balancer** distributes incoming network traffic across a group of backend servers to ensure no single server is overwhelmed, maximizing throughput and availability.
**Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It routes traffic based on IP addresses and port numbers. It is fast but unaware of the content of the request.
**Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the content of the request (headers, URL path, cookies) to make intelligent routing decisions.
**Use Case for L7:** Routing traffic based on the URL path (e.g., routing `/api/v1/users` to Service A and `/api/v2/products` to Service B, even if they share the same IP/port).

**AA14**
A **Message Queue** (e.g., RabbitMQ) is a buffer that holds messages until a consumer is ready to process them. It is designed for point-to-point or publish/subscribe messaging, often ensuring a message is consumed and acknowledged exactly once.
A **Log-Based Message Broker** (e.g., Kafka) treats messages as an immutable, ordered log appended to topics. Consumers read from specific offsets in this log.
**When to pick one over the other:** Pick a **Message Queue** when you need guaranteed, transactional delivery of a message and the message should be consumed and removed (e.g., processing a payment request). Pick a **Log-Based Broker** when you need stream processing, replayability, and multiple independent consumers to read the same data stream (e.g., capturing all user activity logs).

**AA15**
A **Container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and configuration. It shares the host OS kernel.
A **Virtual Machine (VM)** virtualizes the entire hardware stack, including the kernel, running a full guest OS on top of a hypervisor.
Containers are popular because they offer high density, fast startup times (seconds vs. minutes for VMs), and strong environmental consistency ("it runs the same everywhere") without the overhead of a full OS per instance.

**AA16**
**Stateless Service:** A service that does not retain any client session data or state between requests. Every request from the client contains all the necessary information for the service to fulfill it. Example: A REST API endpoint that validates a token and returns data.
**Stateful Service:** A service that retains data or context from previous interactions. This state must be managed, often in local memory or attached persistent storage. Example: A session manager, a database server, or a shopping cart service.
Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance, as no instance holds unique session data that would need to be maintained or synchronized across the cluster.

**AA17**
An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using object-oriented paradigms (objects, classes) instead of writing raw SQL queries. It maps database tables to classes and rows to objects.
Popular ORMs: **Hibernate** (Java), **Entity Framework Core** (.NET).
**Trade-offs:**
*   **ORM Pros:** Increased developer productivity, abstraction from specific SQL dialects, improved type safety.
*   **ORM Cons:** Performance overhead (the "N+1 query problem"), impedance mismatch (mapping object graphs to relational tables is inherently complex), and difficulty optimizing complex, highly specific queries.

**AA18**
The **Bulkhead pattern** isolates components of an application so that the failure or resource exhaustion in one component does not cascade and bring down the entire system. It partitions resources (like thread pools, connection pools, or memory) into isolated compartments (bulkheads).
It relates to resource isolation by ensuring that if one service or function becomes overloaded or hangs, it only consumes the resources allocated to its specific bulkhead, leaving resources available for other, healthy services.
**Implementation Example:** Using thread pools. If Service A calls Service B, instead of using the main application thread pool, Service A uses a dedicated, limited thread pool (Bulkhead A) specifically for calls to Service B. If Service B slows down, only the threads in Bulkhead A become saturated, while the main application threads remain free to handle other requests.

**AA19**
**Operational Transformation (OT):** A mathematical algorithm that transforms operations (like insertions or deletions) based on the operations that have occurred concurrently on the same document. It requires a central server to sequence and transform operations before broadcasting them to clients.
**CRDTs (Conflict-free Replicated Data Types):** Data structures designed so that concurrent updates can be merged mathematically without requiring a central coordinator. They are inherently commutative and associative.
| Feature | OT | CRDTs |
| :--- | :--- | :--- |
| **Consistency** | Strong (Requires server coordination) | Eventual (Converges mathematically) |
| **Latency** | Higher (Requires round-trip to server for transformation) | Lower (Local operations are immediate) |
| **Complexity** | High (Complex transformation logic) | Medium (Requires specialized data structures) |
| **Offline Support** | Poor (Requires synchronization upon reconnection) | Excellent (Updates are applied locally and merged later) |

I would choose **CRDTs**. For a system that *must* support offline editing, CRDTs are superior because they allow the client to apply changes locally immediately, and the mathematical properties guarantee that when connectivity is restored, the changes will merge correctly without data loss or complex server-side transformation logic.

**AA20**
**Challenges:** Maintaining a coherent view of a single request's journey across multiple services, especially when asynchronous messaging is involved.
**Context Propagation:** This is the mechanism of passing a unique identifier (Trace ID) and span information across service boundaries. Standards like **W3C Trace Context** or **B3** headers are used to inject this context into HTTP headers or message metadata.
**Sampling Strategies:**
*   **Head-based:** A decision is made at the entry point (head) whether to sample the entire trace (e.g., sample 1% of all requests). Simple, but might miss critical errors in unsampled traces.
*   **Tail-based:** The decision to sample is made after the entire trace is complete, often based on criteria like error status or latency. More accurate for debugging but requires buffering all traces before deciding.
**Trace Storage/Querying:** Tools like **Jaeger** or **Tempo** ingest the trace data (spans) and provide a UI for visualizing the request flow, latency, and dependencies.
**Asynchronous Messaging:** When a request passes through Kafka, the trace context must be explicitly injected into the Kafka message headers *before* publishing. The consuming service must then extract this context from the message headers and continue the trace span, linking the consumer's work back to the original producer's span.

**OP1**
**Type 1 (Bare-Metal) Hypervisor:** Runs directly on the host hardware, managing the hardware resources and allocating them to VMs. It has the highest performance and lowest overhead. Examples: VMware ESXi, Microsoft Hyper-V (when run directly).
**Type 2 (Hosted) Hypervisor:** Runs as an application *on top* of a conventional host operating system (like Windows or Linux). It introduces overhead due to the host OS layer. Examples: VMware Workstation, Oracle VirtualBox.

**OP2**
**SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. The storage appears to the server as a local disk drive. Protocols: Fibre Channel (FC), iSCSI. Used when servers need raw, high-performance disk access (e.g., databases).
**NAS (Network Attached Storage):** A dedicated file storage device accessible over the standard network (LAN). It presents storage as shared files/folders. Protocols: NFS, SMB/CIFS. Used for file sharing, backups, and general data storage.

**OP3**
**3-Tier Architecture:**
1. **Access Layer:** Connects end-user devices (switches, endpoints).
2. **Distribution Layer:** Aggregates traffic from the Access layer, enforces policies, and handles routing between VLANs.
3. **Core Layer:** The high-speed backbone responsible for fast, reliable transport between distribution layers.
**Leaf-Spine:** This modern architecture replaces the rigid hierarchy. All servers connect to a "Leaf" switch, and all Leaf switches connect to a "Spine" switch.
**Problem Solved:** The 3-tier model creates bottlenecks at the Distribution layer and limits east-west traffic flow (server-to-server communication). Leaf-Spine provides predictable, low-latency, non-blocking paths between any two endpoints, allowing for massive horizontal scaling and predictable bandwidth.

**OP4**
**Architecture:**
*   **Node Count:** Minimum 3 nodes for quorum.
*   **Quorum:** Achieved via the Corosync/Ceph monitor cluster, ensuring a majority of nodes must agree on the cluster state.
*   **Fencing (STONITH):** Critical mechanism to ensure a failed node is truly offline before another node takes over its resources, preventing split-brain. This is usually done via IPMI/iDRAC commands to power cycle or isolate the node.
*   **Shared Storage:** Ceph is the preferred choice as it is software-defined storage that runs *on* the cluster nodes, providing distributed block/file storage.
*   **Node Failure:** If a node fails, the remaining nodes maintain quorum. Ceph automatically rebalances the data (replicas) onto the surviving nodes, and the cluster remains operational, though performance may degrade until the failed node is restored.

**OP5**
**VLAN Trunking:** The process of allowing traffic from multiple VLANs to traverse a single physical link (trunk port).
**802.1Q Tagging:** The standard protocol used for VLAN trunking. It inserts a 4-byte tag into the Ethernet frame header, specifying the VLAN ID (VID) to which the frame belongs.
**Linux Configuration:** You configure the physical NIC to be in a "promiscuous" or "trunking" mode (depending on the switch/driver support). Then, you create multiple virtual interfaces (sub-interfaces) on that single physical NIC, each assigned a specific VLAN ID and IP address.
Example: `eth0.10` (for VLAN 10) and `eth0.20` (for VLAN 20) are created, and IP addresses are assigned to these sub-interfaces.

**OP6**
*   **RAID 1:** Mirroring. Duplicates data across two drives. Excellent read performance, 50% capacity loss, high fault tolerance (can lose one drive).
*   **RAID 5:** Striping with parity. Distributes data and parity across drives. Good balance, can lose one drive.
*   **RAID 6:** Striping with double parity. Distributes data and two parity blocks. Excellent fault tolerance (can lose two drives).
*   **RAID 10:** Striping of mirrors. Combines RAID 1 and RAID 0. Excellent performance and fault tolerance, but high capacity loss.
*   **RAID Z2 (ZFS):** Similar to RAID 6, using distributed parity across multiple drives.
**Choice:** For a database server needing to balance performance, capacity, and fault tolerance, **RAID 10** is often the best choice. It offers superior read/write performance (due to striping) while maintaining high fault tolerance (due to mirroring), which is critical for transactional database workloads.

**OP7**
**Architecture Components:**
1.  **Internal Recursive Resolvers:** Located inside the corporate network, these servers receive DNS queries from clients. They forward external queries to public DNS servers and handle internal queries.
2.  **Authoritative Servers:** These hold the actual zone files for the domains (e.g., the internal AD DNS servers are authoritative for `corp.local`).
3.  **Forwarders:** The internal resolvers use forwarders to send external queries to trusted public DNS servers (e.g., Google DNS).
4.  **Conditional Forwarding:** Configured on the internal resolvers to direct queries for specific domains (e.g., `partner.com`) to a specific, known external DNS server, bypassing the general forwarders.
5.  **Split-Horizon DNS:** The internal DNS servers host two different records for the same hostname: one internal (pointing to private IPs) and one external (pointing to public IPs), based on the client's network location.
6.  **DNSSEC:** Applied to the external zone to cryptographically sign records, ensuring data integrity and preventing cache poisoning.
**Laptop Movement:** When the laptop is on the office LAN, it queries the internal recursive resolver, which uses the internal records (Split-Horizon). When it connects via VPN, the VPN tunnel routes traffic through the corporate DNS infrastructure, ensuring it still queries the internal resolvers, which then serve the correct internal records.

**OP8**
**PKI Chain of Trust:** The trust flows from the **Root CA** (the ultimate trust anchor, kept offline and highly secured) $\rightarrow$ to a **Subordinate/Issuing CA** (which performs the day-to-day signing) $\rightarrow$ to the **End-Entity Certificate** (the certificate issued to the server/user).
**CRL vs OCSP:**
*   **CRL (Certificate Revocation List):** A list published periodically by the CA containing serial numbers of revoked certificates. Clients must download and check this list.
*   **OCSP (Online Certificate Status Protocol):** A real-time query mechanism where the client asks the CA if a specific certificate is valid.
**Certificate Templates:** Define the rules for what can be issued (e.g., server certificate, client certificate, key usage restrictions).
**Auto-Enrollment:** A process where clients automatically request and receive certificates from the Issuing CA without manual intervention, typically using protocols like SCEP or EST.
**Consequences of Compromise:**
*   **Compromised Subordinate CA:** High risk. An attacker can issue fraudulent certificates that appear valid until the CA is revoked. The damage is contained to the certificates issued by that CA.
*   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, its compromise invalidates *every* certificate issued under its authority, requiring a complete, costly PKI infrastructure rebuild.

**OP10**
**iDRAC/iLO/IPMI:** These are management interfaces built into server hardware that allow administrators to remotely manage the server's hardware components (power cycling, viewing logs, accessing the console) independent of the operating system.
**Out-of-Band Management Criticality:** It is critical because if the OS or the primary network stack fails, you still need a way to access the server to diagnose or recover it. IPMI provides this lifeline.
**Exposure Risk:** If the IPMI interface is exposed to the internet, it becomes a massive attack vector. An attacker could gain full physical control over the server (e.g., forcing a reboot, accessing the BIOS, or installing malicious firmware) without needing OS-level credentials. It must be strictly firewalled and accessed only via secure, internal networks.

**OP11**
**LVM (Logical Volume Manager):** A software layer that abstracts physical disks into flexible logical volumes. It allows for resizing and snapshotting of volumes dynamically. It manages block-level storage.
**LVM-Thin:** An extension of LVM that allows for thin provisioning, meaning you can allocate more logical space than you physically have, and only consume physical space as data is written.
**ZFS:** A comprehensive file system and volume manager that integrates storage management, data integrity checks (checksumming), and volume management into one system.
**Use Cases & Snapshots:**
*   **LVM:** Use when you need simple, flexible block device management on a standard Linux setup. Snapshots are block-level copies.
*   **LVM-Thin:** Use for environments where storage efficiency is key and you need to provision space ahead of time without consuming physical disk space immediately. Snapshots are block-level.
*   **ZFS:** Use when data integrity, advanced features (like compression, deduplication), and robust snapshots are paramount (e.g., critical file servers). Snapshots are transactional, capturing the state of the file system at a specific point in time.

**OP12**
**Strategy:** A **Stretch Cluster** configuration is required for true site failure survival. This involves deploying the Ceph monitors and OSDs across two geographically separated data centers (Site A and Site B).
**CRUSH Rules:** Must be configured to ensure that data replicas are spread across different failure domains (racks, power zones, and crucially, different physical sites).
**Monitor Placement:** Monitors must be placed in both sites, but the cluster must be configured to tolerate the loss of one entire site.
**Network Latency:** Low latency is required, but high latency is manageable if the cluster is configured for asynchronous replication between sites.
**Split-Brain Problem:** This occurs when network partitioning causes both sites to believe they are the sole authority. To prevent this, a **tiebreaker** (e.g., a third, small, highly available witness node located in a neutral third location, or a quorum mechanism) must be used. This witness node ensures that only one side of the partition can achieve a majority quorum and continue operating.

**OP13**
**DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses, subnet masks, default gateways, and DNS server information to devices on a network.
**DORA Process:**
1.  **Discover:** Client broadcasts a DHCP Discover message to find available servers.
2.  **Offer:** Server responds with a DHCP Offer, proposing an IP address and lease terms.
3.  **Request:** Client broadcasts a DHCP Request, formally accepting the offered IP address.
4.  **Acknowledge:** Server sends a DHCP ACK, finalizing the lease assignment.
**Server Unavailable:** If the server is unavailable and the lease expires, the client will attempt to renew the lease (DHCP Request) periodically. If renewal fails, the client will eventually transition to an APIPA (Automatic Private IP Addressing) address (169.254.x.x) to allow local communication, but it will not have external network access.

**OP14**
**Unmanaged Switch:** A plug-and-play switch that operates at Layer 2. It simply forwards frames based on MAC addresses without any configuration options. It is suitable for small, simple networks.
**Managed Switch:** A switch that offers extensive configuration capabilities via CLI or GUI.
**Enterprise Features:** Managed switches provide:
1.  **VLAN Tagging/Trunking:** Segmenting broadcast domains for security and traffic isolation.
2.  **QoS (Quality of Service):** Prioritizing latency-sensitive traffic (like VoIP) over bulk data transfers.
3.  **Port Mirroring/SPAN:** Copying traffic from one port to another for monitoring/troubleshooting.
4.  **Security Features:** Port security (limiting MAC addresses per port) and 802.1X support.

**OP15**
**NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.
**Criticality:** Accurate time synchronization is vital for:
1.  **Log Correlation:** Correlating events across distributed services (essential for debugging).
2.  **Security:** Kerberos authentication and certificate validation rely heavily on synchronized time.
3.  **Clustering:** Ensuring that state changes and failover events are processed in the correct chronological order.
**Clock Drift Consequences:** If clocks drift, services can fail authentication checks (e.g., JWT expiration validation), database replication can fail due to timestamp mismatches, and cluster quorum decisions can become unreliable, leading to data corruption or service outages.

**OP16**
**Physical Server:** A dedicated, physical piece of hardware running a full operating system.
**Virtual Machine (VM):** A software emulation of a physical computer, running a full guest OS, managed by a hypervisor.
**Container:** A lightweight, isolated process environment that shares the host OS kernel.
**Bare Metal Use Case:** You would run a workload directly on bare metal when the workload has extremely low latency requirements, requires direct hardware access (e.g., specialized GPU computing, high-frequency trading), or when the overhead introduced by the hypervisor/container runtime is unacceptable.

**OP17**
**UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power when utility power fails. Its role is to bridge the gap between power loss and generator startup, allowing graceful shutdown or continuous operation for a limited time.
**Generator:** Provides long-term, sustained power during extended utility outages.
**Why both are needed:** The UPS handles the immediate, sudden failure (seconds), while the generator handles the prolonged outage (hours/days).
**ATS (Automatic Transfer Switch):** This hardware device automatically detects the loss of utility power and switches the electrical load from the utility source to the generator source, and back again, ensuring seamless power transition.

**OP18**
**Active-Passive Clustering:** One server (Active) handles all the workload, while the second server (Passive/Standby) is running but idle, constantly monitoring the Active node. If the Active node fails, the Passive node takes over the workload.
**Active-Active Clustering:** Both servers actively handle portions of the workload simultaneously. This provides higher utilization and better load distribution but is significantly more complex to manage state synchronization.
**HA Implementation (Pacemaker/Corosync):**
1.  **Corosync:** Provides the cluster communication and membership service, ensuring all nodes agree on the cluster state.
2.  **Pacemaker:** The resource manager that monitors the health of services (e.g., PostgreSQL).
3.  **Fencing (STONITH):** Pacemaker uses STONITH (Shoot The Other Node In The Head) to ensure that if a node appears "alive" but is actually partitioned (split-brain), it can be forcibly powered off or isolated by an external mechanism (e.g., IPMI call) before the surviving node takes over the resource.
4.  **Virtual IPs (VIP):** The database service is bound to a floating VIP. Pacemaker manages this VIP, moving it to the newly active node upon failover.
**Failover Behavior:** If the Active node fails, Corosync detects the failure, Pacemaker initiates the failover, STONITH ensures the failed node is truly down, and the VIP is moved to the Passive node, which then starts the PostgreSQL service.

**OP19**
**3-2-1 Rule:** Maintain at least **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.
**RPO (Recovery Point Objective):** The maximum acceptable amount of data loss measured in time (e.g., 1 hour). Determines backup frequency.
**RTO (Recovery Time Objective):** The maximum acceptable downtime measured in time (e.g., 4 hours). Determines recovery speed and infrastructure readiness.
**Backup Types:**
*   **Full:** Copies all selected data. Slowest, largest backup.
*   **Incremental:** Copies only data that has changed since the *last* backup of any type. Fastest, smallest backup.
*   **Differential:** Copies all data that has changed since the *last full* backup. Faster than full, but grows larger than incremental.
**Deduplication:** Reduces storage footprint by identifying and storing only unique blocks of data, regardless of how many times they appear across different files.
**Storage:** Use disk for fast local recovery, tape/cloud for long-term, immutable, offsite archival.
**Immutable Backups:** Backups that cannot be modified, deleted, or encrypted by an attacker for a set retention period. This is the primary defense against ransomware encrypting your backups.
**Testing Restores:** Crucial. Backups are useless if they cannot be restored. Regular, scheduled, full-scale restore drills must be performed to validate RTO/RPO compliance.
**Backup vs. DR:** **Backup** is the process of creating copies of data. **Disaster Recovery (DR)** is the comprehensive plan and infrastructure required to restore *all* business functions (data, applications, network, processes) following a catastrophic event.

**OP20**
**802.1X (Port-Based Network Access Control):** A standard that controls which devices are allowed to connect to a wired network port.
**Roles:**
*   **Supplicant:** The client device (laptop, server) requesting access.
*   **Authenticator:** The network switch/port that enforces the policy and mediates the connection.
*   **Authentication Server:** The central server (usually RADIUS) that verifies the supplicant's credentials.
**EAP Methods:**
*   **EAP-TLS:** Uses digital certificates for mutual authentication (client proves identity to server, server proves identity to client). Highly secure.
*   **PEAP (Protected EAP):** Encapsulates authentication within a TLS tunnel, often using username/password credentials inside the tunnel. Less secure than EAP-TLS but easier to deploy.
**RADIUS:** The protocol used by the Authenticator to communicate authentication requests and receive authorization decisions from the Authentication Server.
**Dynamic VLAN Assignment:** Upon successful authentication, the RADIUS server instructs the switch (Authenticator) to place the supplicant into a specific VLAN, segmenting the network based on user role (e.g., "Finance" VLAN vs. "Guest" VLAN).
**Failed Authentication:** The switch (Authenticator) denies the port access, typically placing the device into a restricted, quarantined VLAN with no access to production resources, or simply shutting down the port entirely.
**MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., printers, IP phones). The switch sends the device's MAC address to the RADIUS server, which authenticates the MAC address against a pre-approved list, allowing the device onto the network without a full EAP exchange.
