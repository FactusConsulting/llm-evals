**Kubernetes Questions**

K1 — The primary difference is their use case. A **Deployment** manages stateless applications, ensuring a specified number of identical replicas are running and handling updates via rolling updates. A **StatefulSet** manages stateful applications (e.g., databases) that require stable, unique network identifiers, persistent storage, and ordered deployment/scaling.

K2 — A ClusterIP Service exposes the Service internally within the cluster using a stable virtual IP (ClusterIP). When a pod sends traffic to this ClusterIP, `kube-proxy` (running on each node) intercepts the traffic and uses iptables or IPVS rules to randomly select and forward the packet to one of the healthy backend pod IPs associated with that Service.

K3 — **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator or dynamically. It represents the actual storage resource (e.g., an AWS EBS volume). **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a request object that binds to an available PV that meets its requirements (size, access mode). **StorageClass:** A class that defines "how" the PV should be provisioned (e.g., fast SSD, standard HDD). It allows for dynamic provisioning, meaning a PVC can automatically request a PV of a specific type without manual intervention.

K4 — 1. **Check Pod Events:** Use `kubectl describe pod <name>` to check the `Events` section for specific failure reasons (e.g., ImagePullBackOff, CrashLoopBackOff reason). 2. **Check Logs:** Use `kubectl logs <name>` to see the application's output leading up to the crash. 3. **Check Container Image:** Verify the image exists, is correct, and can be pulled by the node (check image registry access/credentials). 4. **Check Resource Limits/Requests:** Verify the pod's resource requests/limits are reasonable and that the node has sufficient allocatable resources.

K5 — CoreDNS acts as the cluster's internal DNS service, translating service names (e.g., `my-service.my-namespace.svc.cluster.local`) and pod names into cluster IP addresses. If CoreDNS pods are down, DNS resolution fails entirely within the cluster. Pods cannot resolve service names or other internal endpoints, leading to connection timeouts and application failures.

K6 — The scheduler uses a two-phase process: **Filtering** and **Scoring**.
1. **Filtering (Predicates):** The scheduler first filters out nodes that *cannot* run the pod based on hard constraints (e.g., resource availability, node selector matching, taints/tolerations).
2. **Scoring (Priorities):** For the remaining viable nodes, it scores them based on various factors to determine the "best" fit.
Specific factors include:
1. **Resource Utilization:** Preferring nodes that are less utilized to balance load.
2. **Node Affinity/Anti-Affinity:** Matching the pod's desired placement rules to the node's characteristics.
3. **Pod Topology Spread Constraints:** Spreading pods across different failure domains (e.g., different availability zones) to maximize resilience.

K7 — **Scheduling:** Yes, the pod *will* be scheduled. Kubernetes scheduling considers *requests*, not limits, for initial placement decisions. The node has 4GB total, 3.5GB requested, leaving 0.5GB available. The pod requests 256Mi, which fits within the remaining 0.5GB.
**Runtime Behavior:** If the pod uses 600Mi, it will exceed its limit (512Mi). The Kubelet on the node will enforce the limit, and the container runtime will terminate the process, resulting in the pod being restarted (likely entering CrashLoopBackOff) due to an Out-Of-Memory (OOM) kill.

K8 — 1. **External LB:** The external load balancer (e.g., AWS ELB) receives traffic and forwards it to the Ingress Controller's external IP/NodePort. 2. **Ingress Controller:** The NGINX controller (running as a pod) receives the request, inspects the Ingress resource rules (host/path matching), and determines the target Service. 3. **Service:** The Ingress Controller forwards the request to the ClusterIP of the target Service. 4. **Endpoints:** The Service object references the Endpoints object, which maintains a list of the actual IP addresses of the healthy backend pods. 5. **kube-proxy/iptables:** `kube-proxy` programs iptables rules on the node. When the Service IP is hit, iptables randomly selects a backend pod IP from the Endpoints list and redirects the traffic to that pod's network interface.

K9 — A **NetworkPolicy** defines rules that specify how groups of pods are allowed to communicate with each other and with external network endpoints. If no NetworkPolicy exists in a namespace, the default behavior is "allow all" ingress and egress traffic. When you apply a policy that selects certain pods, the default behavior changes to "deny all" ingress/egress traffic for those selected pods, unless explicitly allowed by a rule in the applied policy.

K10 — **RollingUpdate:** Gradually replaces old versions of pods with new versions. It maintains availability by ensuring a minimum number of old and new pods are running concurrently during the transition. **Recreate:** Terminates all existing pods of the deployment, and then creates all new pods.
You would choose **Recreate** when the application state is entirely ephemeral, or when the change is so fundamental (e.g., changing the underlying OS base image) that a gradual transition is impossible or undesirable, accepting a brief period of downtime.

K11 — A **namespace** is a mechanism for partitioning cluster resources, providing scope for names and isolation for resources (like Pods, Services, ConfigMaps) within a single physical cluster. Default namespaces include: `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

K12 — `kubectl describe pod <name>` provides a detailed status report of the pod, including metadata, current state, resource requests/limits, container images, volume mounts, and, critically, the **Events** log. Information it shows that `kubectl get pod` does not include: detailed resource requests/limits, the full list of container statuses (including restart counts), and the chronological sequence of events (e.g., scheduling, pulling image, failing health checks).

K13 — A **ConfigMap** is an API object used to store non-confidential configuration data in key-value pairs, allowing configuration to be injected into pods without rebuilding the image.
Two methods to consume it:
1. **Environment Variables:** Mounting the ConfigMap as environment variables in the pod spec.
2. **Volume Mounts:** Mounting the ConfigMap as a file volume inside the container filesystem.

K14 — **ClusterIP:** Exposes the Service only internally within the cluster using a stable virtual IP. Only reachable from other pods inside the cluster. **NodePort:** Exposes the Service on a specific port on *every* node in the cluster. This allows external traffic to reach the service via `<NodeIP>:<NodePort>`. **LoadBalancer:** Provisions an external cloud load balancer (e.g., AWS ELB, GCP Load Balancer) that routes external traffic to the Service's nodes.

K15 — A **DaemonSet** ensures that a copy of a pod runs on *every* (or a specified subset of) node in the cluster. You use it when you need a system-level agent or service running on every node, such as a log collector (Fluentd), monitoring agent (Prometheus Node Exporter), or network policy enforcement agent.

K16 — **Taints** are properties applied to a node that repel pods. They tell the scheduler, "Do not place pods here unless they explicitly tolerate this taint." **Tolerations** are properties applied to a pod that allow it to be scheduled onto a tainted node.
**Node Affinity** is a scheduling constraint that *attracts* or *repels* pods based on node labels (e.g., "only schedule on nodes labeled `disk=ssd`").
**Practical Use Case:**
*   **Taint/Toleration:** Isolating a high-security database workload onto a dedicated, hardened node pool by tainting those nodes.
*   **Node Affinity:** Ensuring a specific application pod is always scheduled onto a node that has a specific GPU attached.

K17 — A **Kubernetes Operator** is a method of packaging, deploying, and managing a complex application (like a database cluster) using custom controllers. It differs from a standard controller because it encapsulates *domain-specific knowledge* (e.g., backup procedures, failover logic, scaling rules specific to Cassandra). The Operator pattern solves the problem of managing complex, stateful applications that require human-like operational knowledge, automating complex lifecycle management beyond simple declarative state changes.

K18 — Kubernetes uses **Raft** (a consensus algorithm) for etcd consistency. Raft ensures that all members of the cluster agree on the sequence of operations (the log). If the etcd quorum (majority, typically $N/2 + 1$) is lost, the cluster cannot achieve consensus, and the control plane (API Server, Scheduler) becomes read-only or completely unavailable, as it cannot guarantee data integrity. If 2 out of 3 nodes are permanently lost, the quorum is lost, and the cluster is effectively dead until a replacement node is added and bootstrapped to restore the majority.

K19 — **RBAC (Role-Based Access Control)** defines permissions based on roles.
*   **Role:** Defines a set of permissions (verbs like `get`, `list`, `create`) scoped to a specific resource (e.g., Pods) *within a single namespace*.
*   **ClusterRole:** Defines a set of permissions scoped across *all namespaces* in the cluster.
*   **RoleBinding:** Binds a specific Role to a user or ServiceAccount *within a namespace*.
*   **ClusterRoleBinding:** Binds a specific ClusterRole to a user or ServiceAccount across the *entire cluster*.

**RBAC Manifests (Read-only access to pods and logs in `my-namespace`):**
```yaml
# 1. Define the Role (Permissions within the namespace)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"] # Accessing logs
  verbs: ["get"]

---
# 2. Bind the Role to a User/Group (Assuming user 'developer')
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-pod-binding
  namespace: my-namespace
subjects:
- kind: User
  name: developer # Replace with actual user name
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — **ndots** specifies the number of DNS dots (periods) that the resolver should follow when resolving a hostname. If `ndots` is set to 1, the resolver will only attempt to resolve a fully qualified domain name (FQDN) if the name contains at least one dot *after* the first dot. If the pod is querying external domains (e.g., `google.com`), and `ndots` is set too high (e.g., 5), the resolver might incorrectly assume the domain is local or internal, leading to excessive, unnecessary queries to internal DNS servers before failing or timing out.
**Fix:** Use `dnsConfig` in the pod spec to explicitly set `options: { nameServers: [...] }` or, more precisely, set `ndots: 1` within the `dnsPolicy` to ensure it correctly queries external resolvers for external domains.

**Development Questions**

D1 — **git merge** integrates changes by creating a new "merge commit" that combines the histories of two branches. **git rebase** rewrites history by moving the entire feature branch to start *after* the target branch's latest commit, creating a linear history.
You should avoid rebasing commits that have already been pushed to a shared, public repository, as rewriting history on shared branches forces collaborators to perform complex recovery operations.

D2 — **TCP (Transmission Control Protocol):** Connection-oriented, reliable, ordered delivery. It uses a three-way handshake to establish a connection and guarantees packet delivery via acknowledgments and retransmissions. (Protocols: HTTP/1.1, FTP). **UDP (User Datagram Protocol):** Connectionless, unreliable, best-effort delivery. It sends packets without establishing a formal connection or guaranteeing order/delivery. (Protocols: DNS, VoIP/SIP).

D3 — A **race condition** occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data.
**Example:** Two threads simultaneously check a bank account balance ($100) and both decide they can withdraw $100 because the balance is $>100$. Both threads execute the withdrawal logic, resulting in a final balance of -$100, even though only $100 was available.

D4 — **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is fast and efficient. **Asymmetric Encryption:** Uses a pair of mathematically linked keys: a public key (shared widely for encryption) and a private key (kept secret for decryption) (e.g., RSA).
**TLS Usage:** Asymmetric encryption is used during the initial **handshake** to securely exchange a temporary, symmetric session key. Once the session key is established, symmetric encryption is used for the bulk data transfer because it is much faster.

D5 — A **container image layer** is a read-only, immutable filesystem layer created from each instruction in a Dockerfile. Each instruction (e.g., `RUN`, `COPY`) creates a new layer on top of the previous one.
**Layer Caching:** Docker caches these layers. If an instruction and its context have not changed since the last build, Docker reuses the cached layer, significantly speeding up subsequent builds. Best practice dictates placing instructions that change infrequently (like installing base dependencies) near the top of the Dockerfile, and placing frequently changing instructions (like copying source code) near the bottom.

D6 — 1. **Check Application Logs:** Look for specific exceptions, database connection errors, or resource exhaustion messages. 2. **Check Resource Utilization (CPU/Memory):** Use monitoring tools (Prometheus/Grafana) to see if the pod is hitting CPU throttling limits or running out of memory. 3. **Check Dependencies/Downstream Services:** Verify if the API relies on external services (DB, cache) that might be slow or unavailable. 4. **Check Ingress/Service Health:** Verify the Service Endpoints are correctly populated and the ingress controller is healthy and routing traffic correctly.

D7 — The **CAP Theorem** states that a distributed data store can only simultaneously guarantee two out of three properties: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest data), and **Partition Tolerance** (the system continues to operate despite arbitrary message loss or failure of part of the network).
*   **CP System (Consistency over Availability):** Systems like traditional relational databases (e.g., PostgreSQL cluster) or ZooKeeper. If a network partition occurs, the system sacrifices availability (stops accepting writes/reads) to ensure data consistency.
*   **AP System (Availability over Consistency):** Systems like Cassandra or DynamoDB. If a network partition occurs, the system remains available, accepting writes on both sides, and resolves conflicts later (eventual consistency).

D8 — **Vertical Scaling (Scaling Up/Down):** Increasing or decreasing the resources (CPU, RAM) allocated to an *existing* instance. This is limited by the maximum capacity of the underlying machine. **Horizontal Scaling (Scaling Out/In):** Increasing or decreasing the number of instances (replicas) running the application. This is generally preferred in cloud environments as it offers near-limitless scalability.
Architectural patterns enabling horizontal scaling include: **Statelessness** (ensuring no session data is tied to a single instance), **Load Balancing** (distributing traffic evenly across replicas), and **Microservices** (breaking the application into independent, scalable services).

D9 — An **environment variable** is a dynamic named value that can affect the way running processes behave on a computer. It allows configuration to be passed to an application at runtime without modifying the code.
To set one that persists across shell sessions on Linux, you must add the export command (e.g., `export MY_VAR="value"`) to your shell's startup file, such as `~/.bashrc` or `~/.zshrc`, and then source the file (`source ~/.bashrc`).

D10 — **JSON (JavaScript Object Notation):** A lightweight data-interchange format using key-value pairs and arrays. It is language-independent and is the standard for modern web APIs. Advantage: Extremely easy for JavaScript/web clients to parse. **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that uses indentation to denote structure. Advantage: Highly readable and concise for configuration files (like Kubernetes manifests).

D11 — A **REST API (Representational State Transfer)** is an architectural style for designing networked applications. It uses standard HTTP methods to perform operations on resources identified by unique URLs (endpoints).
*   **GET:** Retrieves a representation of a resource (safe and idempotent).
*   **POST:** Submits data to a specified resource, often causing a change in state (non-idempotent).
*   **PUT:** Replaces an entire resource at a specific URI (idempotent).
*   **DELETE:** Removes the specified resource (idempotent).

D12 — **Version pinning** is the practice of explicitly specifying the exact version of a dependency (e.g., `library==1.2.3`) rather than using a broad range (e.g., `library>=1.0`). It is crucial for reproducible builds because it guarantees that the build environment will always use the exact same code dependencies, preventing unexpected runtime bugs caused by upstream library changes.

D13 — **Compiled Language:** Source code is translated directly into machine code (binary executable) by a compiler *before* execution. Examples: C++, Go, Rust. **Interpreted Language:** Source code is executed line-by-line by an interpreter program at runtime. Examples: Python, JavaScript.

D14 — A **Reverse Proxy** sits in front of one or more web servers and forwards client requests to them. It acts as an intermediary, hiding the backend structure from the client. It is used for load balancing, SSL termination, and caching.
A **Forward Proxy** sits in front of clients and forwards requests *from* the clients to the internet, often used to enforce corporate security policies or anonymity.
**Servers & Use Cases:**
*   **NGINX:** Used as a high-performance reverse proxy for load balancing and serving static assets.
*   **HAProxy:** Used for sophisticated, high-availability load balancing across multiple backend servers.

D15 — A **deadlock** is a situation where two or more competing actions are each waiting for the other to finish, resulting in a permanent standstill.
The four necessary **Coffman conditions** are:
1. **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2. **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3. **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily.
4. **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

D16 — **Eventual Consistency** is a consistency model where, if no new updates are made to a given data item, all reads will eventually return the last written value, though there may be a period where different replicas return different values.
Cassandra handles read-after-write consistency using **Tunable Consistency Levels**. When writing, you specify a consistency level (e.g., `QUORUM`), meaning the write must succeed on a majority of replicas. When reading, you specify a read consistency level. To guarantee read-after-write consistency, the read level must overlap with the write level (e.g., Read Quorum + Write Quorum > Total Replicas).

D17 — **mTLS (Mutual TLS)** requires *both* the client and the server to authenticate each other using digital certificates during the TLS handshake.
**Handshake Process:**
1. Client initiates connection and sends its certificate to the server.
2. Server verifies the client's certificate against its trusted Certificate Authority (CA) list.
3. Server sends its certificate to the client.
4. Client verifies the server's certificate against its trusted CA list.
5. If both validations pass, they proceed to exchange and agree upon a symmetric session key.
**Use Case:** Highly secure, service-to-service communication within a microservices mesh (e.g., using Istio or Linkerd) where identity verification for both parties is mandatory.

D18 — A **hash table** stores key-value pairs using a hash function that maps the key to an index (bucket) in an array.
**Collision Resolution:**
*   **Chaining:** Each bucket holds a pointer to a linked list (or other structure) containing all key-value pairs that hash to that index.
*   **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing).
**Time Complexity:**
*   **Average Case (Good Hash Function):** Insertion, Lookup, Deletion are $O(1)$.
*   **Worst Case (All keys hash to the same bucket):** Insertion, Lookup, Deletion are $O(N)$.

D19 — The **Circuit Breaker Pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing microservice), thereby preventing resource exhaustion and cascading failures across the entire system.
**States:**
1. **Closed:** Requests pass through normally. If failures exceed a threshold, the breaker trips to Open.
2. **Open:** Requests are immediately rejected without attempting the external call, failing fast. After a timeout period, the breaker moves to Half-Open.
3. **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker closes; if they fail, it returns to Open.
**Relation to Retry/Backoff:** The circuit breaker acts as a high-level gatekeeper. Retry policies and exponential backoff are used *within* the closed state or during the half-open state to handle transient errors gracefully, preventing immediate overwhelming of a struggling service.

D20 — **Optimistic Concurrency Control (OCC):** Assumes conflicts are rare. Transactions read data, perform operations locally, and only check for conflicts (usually via version numbers or timestamps) just before committing. If a conflict is detected, the transaction is rolled back and retried. (Example: Using a `version` column; if the version read doesn't match the version in the database upon update, the update fails).
**Pessimistic Concurrency Control (PCC):** Assumes conflicts are likely. Transactions acquire locks on the data they intend to modify *before* reading it, preventing any other transaction from accessing or modifying that data until the lock is released. (Example: Using `SELECT FOR UPDATE` in SQL, which locks the selected rows immediately).
**Choice:** Choose **OCC** for high-read, low-write systems where contention is low. Choose **PCC** for low-read, high-write systems where data integrity during the transaction window is paramount.
