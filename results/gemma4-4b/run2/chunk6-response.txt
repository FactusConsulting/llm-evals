**JS1**
The difference is scope and reassignment. `var` is function-scoped and hoisted (can lead to unexpected behavior). `let` is block-scoped and can be reassigned. `const` is block-scoped and must be initialized; it cannot be reassigned (though object/array contents can be mutated). Hoisting is JavaScript's behavior of moving declarations (but not initializations) to the top of their scope during compilation.

**JS2**
The Event Loop is the mechanism that monitors the Call Stack and the various queues (Microtask and Macrotask) to determine what code to execute next. The Call Stack holds synchronous function calls. When the stack is empty, the Event Loop checks the queues. Microtasks (e.g., Promises, `queueMicrotask`) are processed entirely before the next macrotask. Macrotasks (e.g., `setTimeout`, I/O) are processed one at a time.

**JS3**
A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). It allows an inner function to access variables from its outer function even after the outer function has finished executing.
*Example:* `function makeCounter() { let count = 0; return function() { count++; return count; }; }`
*Bug:* In a classic `for` loop closure bug (`var i; for (var i = 0; i < 3; i++) { setTimeout(() => console.log(i), 100); }`), the closure captures the *variable* `i`, not the value at that iteration. By the time the timeouts fire, `i` is 3.
*Fix:* Use `let` in the loop (`for (let i = 0; i < 3; i++)`) or pass `i` as an argument to the callback to create a new scope for each iteration.

**JS4**
A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. `async/await` is syntactic sugar built on Promises, allowing asynchronous code to be written in a synchronous-looking style using `await` to pause execution until a Promise resolves.
*Error Handling:* With Promises, errors are caught using `.catch()` or a `try...catch` block around `await`.
*`Promise.allSettled` vs `Promise.all`*: `Promise.all` rejects immediately if *any* input promise rejects. `Promise.allSettled` waits for *all* input promises to either fulfill or reject, returning an array of status objects describing the outcome of each.

**JS5**
*Interface:* Defines a contract—a set of properties and methods that an object must implement. It describes *what* an object looks like. Interfaces are purely structural and cannot contain implementation logic.
*Type:* Describes the shape of data, including primitive types, unions, and intersections. It can describe implementation details or constraints.
*Usage:* Use `interface` for defining public APIs or object shapes that need to be implemented by classes. Use `type` for aliasing complex types, unions, or primitives.
*Discriminated Unions:* A union type where one member has a literal property (the "discriminant"). This allows TypeScript to narrow the type safely using a `switch` statement based on that literal property.

**JS6**
Prototypal inheritance means objects inherit properties and methods directly from other objects (prototypes) rather than from classes. Every object in JS has an internal `[[Prototype]]` link pointing to another object.
`Object.create(proto)` creates a new object whose internal `[[Prototype]]` is set to the provided `proto` object, effectively linking it to the prototype chain.
ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance mechanism. When you define a class, the JS engine still creates and manages prototype chains behind the scenes.

**JS7**
The `this` keyword refers to the object that is currently executing the function. Its value is determined dynamically based on *how* the function is called.
*Binding Rules (Priority Order):* 1. `new` binding (Constructor call). 2. Explicit binding (`.call()`, `.apply()`, `.bind()`). 3. `implicit` binding (Method call on an object). 4. `default` binding (Global object/undefined in strict mode).
`bind()` returns a *new* function with the specified `this` context permanently bound. Yes, you can re-bind the returned function, but the original function's context remains unchanged.

**JS8**
`WeakRef` allows you to create a weak reference to an object. If the object is garbage collected, the `WeakRef` automatically becomes null. `FinalizationRegistry` allows you to register a callback function that will be executed *after* the associated object has been garbage collected.
*Usage:* Use `WeakRef` when you need to hold a reference to an object without preventing its garbage collection (e.g., caching metadata). Use `FinalizationRegistry` for cleanup tasks (e.g., closing file handles, unsubscribing from events) when the object is destroyed.
*WeakMap Keys:* WeakMap keys must be objects because the garbage collector needs to track object references. If a key were a primitive (like a string), the GC would treat it as a constant value, and the map would never know when the associated object was truly unreachable, leading to memory leaks or incorrect behavior.

**JS9**
V8 optimizes JS using several techniques:
1. **Hidden Classes (Maps):** V8 tracks the shape (structure) of objects. When an object is created with the same sequence of properties, V8 assigns it a "Hidden Class." This allows V8 to treat objects of the same shape as having a fixed layout in memory, enabling fast property access.
2. **Inline Caching (IC):** V8 caches the expected type and location of properties/methods used in hot code paths. Subsequent accesses can use this cached information directly, avoiding full lookups.
3. **Deoptimization:** If the assumptions made by the JIT compiler (e.g., "this object will always have property X") are violated at runtime (e.g., a new property is added), V8 discards the optimized machine code and reverts to slower, safer interpretation/compilation until a new optimization can be performed.
*Deoptimization Causes:* Adding properties dynamically, changing object shapes, or using complex type coercion.

**JS10**
Tree-shaking is a dead code elimination technique used by bundlers (like Webpack/Rollup) to eliminate unused exports from modules during the build process, reducing final bundle size.
*ES Modules (ESM):* ESM uses static `import`/`export` syntax, which allows the bundler to statically analyze the dependency graph and determine exactly which exports are referenced, making tree-shaking highly effective.
*CommonJS (CJS):* CJS uses dynamic `require()`. Since `require()` can be called conditionally or based on runtime values, the bundler cannot statically determine which parts of the module are actually used, making effective tree-shaking nearly impossible.

**JS11**
`null` represents the intentional absence of any object value (a deliberate empty value). `undefined` means a variable has been declared but has not yet been assigned a value, or a function returned nothing.
*Comparison:* `==` performs type coercion before comparison (e.g., `null == undefined` is true). `===` checks both value and type strictly (e.g., `null === undefined` is false).
*Nullish Coalescing (`??`):* Returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. It differs from `||` because `||` triggers if the left side is *any* falsy value (like `0` or `""`).
*Optional Chaining (`?.`):* Allows safe navigation through nested object properties. If any part of the chain is `null` or `undefined`, the expression short-circuits and returns `undefined` instead of throwing a TypeError.

**JS12**
*`map()`:* Creates a new array populated with the results of calling a provided function on every element in the calling array. (Transformation)
*`filter()`:* Creates a new array with all elements that pass the test implemented by the provided function. (Selection)
*`reduce()`:* Executes a reducer function on each element of the array, resulting in a single output value.
*Reduce with Initial Value:* The initial value acts as the starting accumulator. If provided, it is used as the first argument to the reducer function, and iteration starts from the first element. If omitted, the first element is used as the initial accumulator, and iteration starts from the second element.
*`flatMap()`:* First maps each element using a mapping function, and then flattens the result into a new array (equivalent to `map()` followed by `flat(1)`). It is useful when your mapping function might return an array, and you want the final result to be a single, flattened array.

**JS13**
Template literals (backticks ``) allow embedding expressions directly into strings using `${expression}`. They also support multi-line strings without special characters.
*Tagged Templates:* A function that is called with the template literal. The function receives two arguments: the `strings` array (containing the static parts) and the `...values` array (containing the interpolated expressions).
*Example (HTML Escaping):*
```javascript
function htmlEscape(strings, ...values) {
  let result = strings[0];
  values.forEach((value, i) => {
    const escapedValue = String(value).replace(/[&<>"']/g, function(match) {
      return { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' }[match];
    });
    result += escapedValue + strings[i + 1];
  });
  return result;
}
const safeHtml = htmlEscape`<div>Hello, ${userInput}</div>`;
```

**JS14**
Destructuring is a syntax that allows you to unpack values from arrays or properties from objects into distinct variables.
*Object Destructuring:* `const { name, age } = user;` extracts `name` and `age` from the `user` object.
*Array Destructuring:* `const [first, second] = myArray;` extracts the first two elements.
*Default Values:* `const { age = 30 } = user;` assigns 30 to `age` if it is missing in the object.
*Renaming:* `const { name: fullName } = user;` extracts `name` but assigns it to a new variable `fullName`.
*Rest Operator (`...`):* When used in destructuring, it collects all remaining, un-destructured properties/elements into a new array or object. E.g., `const { id, ...rest } = user;` puts all other properties into `rest`.

**JS15**
*`for...in`:* Iterates over the *enumerable properties* of an object, including inherited enumerable properties (though usually only own properties are desired). It iterates over keys (strings).
*`for...of`:* Iterates over the *values* of an iterable object (like Arrays, Maps, Sets, Strings).
*Difference:* `for...in` is for object keys; `for...of` is for iterable values.
*Avoid `for...in` on Arrays:* Arrays are iterable, but `for...in` iterates over the array's *indices* as strings, which can include non-index properties added to the array object, leading to unpredictable iteration order and missing elements.

**JS16**
Generics allow you to write reusable components that can work over a variety of types while maintaining type safety.
*Generic Constraints (`extends`):* Restricts the types that can be used with a generic parameter. Example: `function identity<T extends { length: number }>(arg: T): T { return arg; }` ensures `T` must have a `length` property.
*Conditional Types:* Allows defining types based on a condition. Example: `type IsString<T> = T extends string ? true : false;`
*Infer Keyword:* Used to infer the type of a variable or function parameter based on its usage. Example: `function getLength<T>(arg: T): number { return arg.length; }` (T is inferred as the type of `arg`).

**JS17**
The module system defines how code dependencies are managed.
*CommonJS (CJS):* Synchronous, file-based system used primarily by Node.js. Uses `require()` to import and `module.exports` to export.
*ES Modules (ESM):* Standardized, static system (`import`/`export`). It is asynchronous and designed for static analysis.
*Node.js Handling:* Node.js supports both. By default, `.js` files use CJS. If a file uses `import`/`export` syntax, or if the project specifies `"type": "module"` in `package.json`, Node treats it as ESM.
*`"type": "module"`:* This field in `package.json` tells Node.js to treat all `.js` files in that project as ES Modules by default, enabling native ESM syntax.

**JS18**
TypeScript uses a structural type system, meaning that two types are considered compatible if they have the same structure (shape), regardless of whether they explicitly declare the same name or inherit from the same class.
*Excess Property Checks:* This check ensures that an object passed to a function or assigned to a type does not contain properties that are *not* defined in that type. It helps prevent accidental data pollution.
*`extends` vs `satisfies`:* `extends` is used for inheritance (the derived type *is* the base type). `satisfies` is used for type checking; it asserts that the object *conforms* to the type without changing the object's actual type.
*Variance (in/out):* Variance describes how subtyping relationships behave when used as function arguments. `in` (contravariant) means the type can be used as an input parameter (e.g., `(T)`). `out` (covariant) means the type can be used as a return value (e.g., `(T)`).

**JS19**
*Proxy:* Allows you to wrap an object and intercept fundamental operations (get, set, apply, construct, etc.) before they execute on the target object.
*Reflect:* Provides methods that mirror the built-in operations that Proxies intercept (e.g., `Reflect.get(target, property)`). It is the standard way to perform the operation that the Proxy handler intercepts.
*Example (Validation/Logging):* A Proxy can intercept a `set` operation. If the property being set is `age`, the handler can check if the new value is positive before allowing the assignment to proceed.
```javascript
const handler = {
  set: (target, property, value) => {
    if (property === 'age' && value < 0) {
      console.error("Age cannot be negative!");
      return false; // Prevent assignment
    }
    return Reflect.set(target, property, value);
  }
};
const user = new Proxy({ age: 25 }, handler);
user.age = -5; // Logs error, assignment fails
```

**JS20**
*SharedArrayBuffer (SAB):* A low-level memory buffer that can be shared directly between multiple threads (like Web Workers). This allows threads to read and write to the same memory location without copying data.
*Atomics:* A set of functions that operate on `SharedArrayBuffer` data in a thread-safe manner. They guarantee that operations (like incrementing a counter) are indivisible, preventing race conditions.
*Communication:* Web Workers communicate by sharing the SAB. Workers access the shared memory view (e.g., `Int32Array` view over the SAB).
*Ordering Guarantees:* Atomics operations provide memory ordering guarantees, ensuring that writes performed by one thread are visible to another thread in a predictable sequence.
*`Atomics.wait/notify`:* These functions allow threads to sleep (wait) until another thread signals them (notifies) that a specific condition in the shared memory has changed, enabling efficient synchronization without constant polling.

**B1**
`$@` expands to all positional parameters as separate, separate arguments to the command. `*` treats them as a single string argument.
`$*` expands to all positional parameters as a single string, separated by the first character of `$IFS` (Internal Field Separator).
`"$@"` (quoted) expands to each argument as a separate, quoted word, preserving spaces within arguments. This is the safest way to iterate over arguments.
`"$*"` (quoted) expands to a single string, preserving the `$IFS` separation.

**B2**
`set -euo pipefail` sets strict error handling for the script:
* `-e` (errexit): Causes the script to exit immediately if any command exits with a non-zero status code.
* `-u` (nounset): Causes the script to exit immediately if an unset variable is used.
* `-o pipefail`: Causes a pipeline to return a non-zero status if *any* command in the pipeline fails, not just the last one.

**B3**
*`$(command)` (Command Substitution):* Executes the `command` and substitutes its standard output into the current command line. This is the modern, preferred method.
*`command` (Direct Execution):* Executes the command directly.
*`$((expression))` (Arithmetic Expansion):* Performs integer arithmetic calculations.
*`expr` (External Command):* An external utility used to evaluate mathematical expressions.
*Difference:* `$((...))` is native shell arithmetic; `expr` is a separate program call.

**B4**
Process substitution (`<(command)`) runs a command in a subshell and makes its standard output appear as a temporary file path that the current shell can read from.
*Use Case:* It is essential when a command needs to be treated as a file argument by another command (like `diff` or `sort`), but the command's output is dynamic.
*Example:* `diff <(ls -t | head -n 5) <(ls -t | tail -n 5)` compares the five newest files against the five oldest files, treating both lists as temporary files.

**B5**
The safest way is to use a `while read` loop combined with `find` and `find -print0` (or `find ... -print0 | xargs -0`).
*Example:* `find . -type f -print0 | while IFS= read -r -d $'\0' file; do echo "Processing $file"; done`
*Danger of `for f in $(ls)`:* If a filename contains a space (e.g., "My File.txt"), `$(ls)` splits it into two separate tokens ("My" and "File.txt"), causing the loop to process two incorrect items.

**B6**
*Here Document (`<<EOF`):* Reads multiple lines of input until it encounters the delimiter (`EOF`) on a line by itself. It preserves newlines and allows variable expansion.
*Here String (`<<<`):* Passes a single string as standard input to a command. It is concise for short strings.
*`<<-EOF` (Indented Here Document):* Allows the content of the here document to be indented in the script without those leading spaces being interpreted as part of the content. The shell strips the common leading whitespace.

**B7**
*`cmd > file 2>&1`*: Redirects standard output (`1`) to `file`. Then, it redirects standard error (`2`) to the *same location* as standard output (`&1`), which is `file`. Both stdout and stderr go to `file`.
*`cmd 2>&1 > file`*: First, it redirects standard error (`2`) to standard output (`&1`). Then, it redirects standard output (`1`) to `file`. Since the redirection of `2` happened *before* the redirection of `1`, `2` points to the original stdout, which is then redirected to `file`. Both stdout and stderr go to `file`.
*`cmd &> file`*: (Bash shorthand) Redirects both stdout and stderr to `file` simultaneously.
*Difference:* The order matters in the second example. `2>&1` must happen before `> file` for the redirection to work correctly.

**B8**
```bash
LOCK_FILE="/tmp/my_script.lock"
function cleanup {
    rm -f "$LOCK_FILE"
    echo "Lock released."
}
trap cleanup EXIT INT TERM

# Attempt to create the lock directory/file atomically
if mkdir "$LOCK_FILE" 2>/dev/null; then
    echo "Lock acquired."
    # --- CRITICAL SECTION ---
    # Script logic here
    # --- END CRITICAL SECTION ---
    # Cleanup trap handles removal on exit
else
    echo "Could not acquire lock. Another process is running."
    exit 1
fi
```
*Why `mkdir` is preferred:* Using `mkdir` (or `ln -s` for advisory locks) is preferred over creating an empty file (`touch`) because `mkdir` can be used with the `-p` flag or, more importantly, the atomic nature of directory creation (if the directory already exists, it fails, indicating contention) provides a more robust, atomic locking mechanism against race conditions than checking for file existence followed by creation.

**B9**
*Single Quotes (`'...'`):* Literal interpretation. No variable expansion, no command substitution. Everything inside is treated as a literal character.
*Double Quotes (`"..."`):* Allows variable expansion (`$VAR`) and command substitution (`$(cmd)`).
*No Quotes:* Word splitting and pathname expansion (globbing) occur.
*Example:*
`echo 'Hello $USER'` -> Prints "Hello $USER" (literal)
`echo "Hello $USER"` -> Prints "Hello [username]" (expanded)
`echo $USER` -> Prints "[username]" (expanded, no surrounding text)

**B10**
*File Existence:* `[ -f file ]` (is a regular file), `[ -d file ]` (is a directory), `[ -r file ]` (is readable).
*Difference between `[ ]` and `[[ ]]`:*
* `[ ]` (test): An external command. It requires careful quoting of variables to prevent word splitting.
* `[[ ]]` (bash keyword): A built-in keyword. It supports advanced features like regex matching (`=~`), logical operators (`&&`, `||`), and does not require variables to be quoted for basic string comparison.

**B11**
*`$?`*: The exit status of the most recently executed foreground command (0 for success, non-zero for failure).
*`$$`*: The Process ID (PID) of the current shell.
*`$!`*: The PID of the most recently executed background job.
*`$#`*: The number of positional arguments passed to the current script/function.
*Use Case:* `$?` is used immediately after a command to check for success/failure. `$$` is used for logging or PID tracking. `$!` is used to wait for a background job to finish.

**B12**
*Definition:* `function foo { echo "Hello"; }` or `foo() { echo "Hello"; }`. Both are valid.
*Difference:* `function foo {}` is the traditional syntax; `foo() {}` is the modern, preferred syntax. They are functionally equivalent in most modern shells.
*Returning Values:* Bash functions do not return values like C/Java. They return an *exit code* (0-255) via `$?`. To return data, you must `echo` the data to standard output, and the caller must capture it using command substitution: `result=$(foo)`.

**B13**
*PATH:* An environment variable that specifies a list of directories the shell searches sequentially when a command is executed.
*Command Resolution:* When you type `ls`, bash searches the directories listed in `$PATH` (e.g., `/bin`, `/usr/bin`) for an executable file named `ls`.
*Builtin vs External:* A builtin command is a command implemented directly within the shell itself (e.g., `cd`, `echo`). An external command is a separate executable file located in a directory listed in `$PATH` (e.g., `grep`, `awk`).
*Checking:* Use the `type` command: `type cd` (will show `cd is a shell builtin`) vs `type grep` (will show `/bin/grep is /bin/grep`).

**B14**
*`trap`:* A shell built-in command used to catch and handle signals sent to the shell or script.
*Cleanup Handlers:*
* `trap 'cleanup_func' EXIT`: Runs `cleanup_func` when the script exits normally.
* `trap 'cleanup_func' ERR`: Runs when a command exits with a non-zero status (if `set -e` is active).
* `trap 'cleanup_func' INT`: Catches Ctrl+C (SIGINT).
* `trap 'cleanup_func' TERM`: Catches termination signals (SIGTERM).
* *Execution Order:* Signals are generally handled in the order they are received, but `EXIT` traps are guaranteed to run upon normal termination, regardless of other signals. If multiple signals arrive rapidly, the shell processes them sequentially based on its internal signal handling queue.

**B15**
*`xargs` vs Command Substitution:* Command substitution runs the command and captures its output as a string. `xargs` takes input from standard input and builds and executes command lines from that input.
*Handling Spaces/Newlines:* `find . -name "*.log" -print0 | xargs -0 -I {} your_command {}`
* `-print0` (find): Outputs results separated by null characters (`\0`).
* `-0` (xargs): Reads input separated by null characters. This correctly handles filenames containing spaces, newlines, or other special characters.
* `-P`: Specifies the number of parallel processes to run concurrently, significantly speeding up I/O-bound tasks.

**B16**
*Bash Arrays (Indexed):* Ordered lists accessed by integer indices starting at 0.
*Declaration:* `my_array=(apple banana cherry)`
*Append:* `my_array+=("date")`
*Iterate:* `for item in "${my_array[@]}"; do ... done`
*Check Length:* `${#my_array[@]}`
*Associative Arrays (Keyed):* Maps keys (strings) to values. Requires `declare -A`.
*Declaration:* `declare -A my_map`
*Set/Append:* `my_map["key"]=value`
*Iterate:* `for key in "${!my_map[@]}"; do echo "$key: ${my_map[$key]}"; done`
*Differences:* Indexed arrays are ordered and accessed numerically; associative arrays are unordered and accessed by arbitrary string keys.

**B17**
*Subshell (`(...)`):* Executes commands in a separate, isolated process. Any variables modified inside the subshell are lost when the subshell exits.
*Group Command (`{ ...; }`):* Executes commands in the *current* shell process group. Variables modified inside are visible outside.
*Exit Codes:* Both return an exit code, but the subshell's exit code is captured by the parent shell's `$?` only if the subshell is the last command executed.
*Piping into `while` loop:* When you pipe output into a `while` loop (`while read line; do ... done < <(command)`), the loop runs in a subshell created by the pipe. Any variable changes made inside the loop are local to that subshell and are lost when the loop finishes, meaning the parent shell's variables remain unchanged.

**B18**
*Signal Handling:* Signals are notifications sent to a process to request an action.
*SIGINT (2):* Interrupt signal (usually Ctrl+C). Used to request graceful termination.
*SIGTERM (15):* Termination signal. The standard, polite request for a process to shut down, allowing it to clean up resources.
*SIGHUP (1):* Hangup signal. Often used to tell a daemon process to reload its configuration files without stopping.
*SIGKILL (9):* Immediate, non-catchable termination. The kernel kills the process instantly; no cleanup is possible.
*Graceful Shutdown:* Use `trap` to catch `SIGINT` and `SIGTERM`. In the trap handler, you should signal background processes to stop, wait for them to finish (e.g., using `wait`), and then exit cleanly.

**B19**
```bash
# 1. Define the processing function
process_log() {
    LOG_FILE=$1
    echo "Processing $LOG_FILE..."
    # Simulate work and potential failure
    if [[ "$LOG_FILE" == *"error"* ]]; then
        echo "ERROR processing $LOG_FILE" >&2
        return 1
    fi
    echo "SUCCESS: Processed $LOG_FILE"
}

# 2. Split the large file into chunks (e.g., 100 lines each)
split -l 100 large_log.txt chunk_

# 3. Process chunks in parallel
# Use 'set -o pipefail' to ensure xargs reports failure if any job fails
find . -maxdepth 1 -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c 'process_log "$@"' _ {}

# 4. Merge results (assuming processing outputs to stdout/a temporary file)
# If processing writes to a specific output file, use cat to merge them.
# Example: cat chunk_*.output > merged_results.txt
```
*Performance Trade-offs:* Parallel processing (using `-P`) drastically reduces wall-clock time for I/O-bound tasks (like reading/writing many small files). However, it increases CPU overhead due to context switching and resource contention (I/O saturation).
*Error Propagation:* By using `set -o pipefail` in the calling script and ensuring the processing function returns a non-zero exit code on failure, `xargs` will propagate that failure status back to the main script, allowing the script to detect that one or more parallel jobs failed.

**B20**
*`exec` vs Normal Command:* Running a command normally forks a new process. `exec` replaces the current shell process image with the new command. The shell itself is overwritten; it does not spawn a child process.
*File Descriptor Manipulation:* `exec 3>file` opens a file and assigns it to file descriptor 3. `exec 3>&-` closes file descriptor 3. This is crucial for redirecting I/O streams within a running shell process.
*Bash Coprocess:* A coprocess allows a shell to run a command in a separate, managed process that can communicate back to the parent shell via standard streams (stdin/stdout/stderr).
*Use Case:* Coprocesses are used when you need a long-running background task that must communicate results or status updates back to the main script in real-time, without relying on complex file polling or background job management.

**PS1**
*`Write-Output`:* Sends objects down the pipeline. This is the standard, idiomatic way to output data in PowerShell, allowing subsequent cmdlets to process the object.
*`Write-Host`:* Writes output directly to the console/host window. It bypasses the pipeline, meaning the output cannot be captured by variables or piped to other cmdlets.
*Pipeline Importance:* The distinction matters because the pipeline relies on objects flowing through cmdlets. If you use `Write-Host`, the object is lost to the pipeline flow.

**PS2**
The PowerShell pipeline passes objects from one cmdlet to the next. Cmdlets receive objects, process them, and output new objects.
*`ForEach-Object` (Pipeline Cmdlet):* This cmdlet (`%`) is designed to receive objects from the pipeline and process them one by one. It is the standard way to iterate over pipeline input.
*`foreach` (Script Block):* This is a standard PowerShell control flow structure. It is typically used to iterate over a collection (like an array or list) that is already loaded into memory, not necessarily from the pipeline stream.
*Appropriateness:* Use `ForEach-Object` when processing objects flowing through the pipeline. Use `foreach` when iterating over a pre-existing collection variable.

**PS3**
*`[PSCustomObject]`:* A dynamic object created at runtime that allows you to define custom properties and types on the fly. It is the standard way to structure data returned by a function or cmdlet.
*`[hashtable]`:* A collection of key-value pairs, similar to a dictionary or map. It is optimized for lookups by key but lacks the formal structure of a custom object.
*Usage:* Use `[PSCustomObject]` when you need a structured, strongly typed return object (best practice for cmdlets). Use `[hashtable]` when you need a flexible, dynamic map structure for quick lookups.
*Conversion:*
* `[PSCustomObject]` to `[hashtable]`: Use `[hashtable]@{$_}` on the object's properties.
* `[hashtable]` to `[PSCustomObject]`: Use `[PSCustomObject]@{}` and populate its properties using the hashtable keys/values.

**PS4**
PowerShell uses a robust error handling system based on error records.
*Terminating Errors:* Errors that stop the execution flow immediately (e.g., trying to access a non-existent registry key when strict mode is on). These halt the script unless explicitly handled.
*Non-Terminating Errors:* Errors that are logged but allow the script to continue execution (e.g., a file not found when using `-ErrorAction SilentlyContinue`).
*Interaction:*
* `-ErrorAction`: Modifies how a specific command handles errors (e.g., `Stop`, `Continue`, `SilentlyContinue`).
* `$ErrorActionPreference`: Sets the default behavior for *all* commands in the current scope (e.g., setting it to `Stop` makes most errors terminating).
* `try/catch`: Allows you to wrap code blocks. The `catch` block executes only when a terminating error occurs within the `try` block, allowing you to handle the error record gracefully.

**PS5**
Splatting (`@params`) is a technique used to pass a hashtable of parameters to a cmdlet, effectively "splatting" the contents of the hashtable into the command's parameter list.
*Example:*
```powershell
$Params = @{
    Path = "C:\Logs"
    Recurse = $true
    Force = $true
}
Get-ChildItem @Params
```
*Difference:* Passing a hashtable as a single parameter means the cmdlet must be explicitly designed to accept a hashtable for that parameter. Splatting allows you to dynamically construct the parameter set using a hashtable and pass it to *any* cmdlet that accepts parameters, making code highly reusable and cleaner.

**PS6**
PowerShell Remoting allows management of remote computers.
*`Invoke-Command -ComputerName`*: Executes a script block or command on a remote machine *without* establishing a persistent session. It runs the command and returns the results immediately.
*`Enter-PSSession`*: Establishes an interactive, persistent connection (a session) to the remote machine, allowing you to run multiple commands as if you were logged in locally.
*Protocol:* It primarily uses **WinRM (Windows Remote Management)**, which is Microsoft's implementation of WS-Management. While SSH can be used for Linux/Unix remoting, WinRM is the native protocol for Windows PowerShell remoting.

**PS7**
*Type System/Pipeline Behavior:* PowerShell is object-oriented. When you return an object, it flows through the pipeline. If a function returns an empty array (`@()`), the pipeline receives zero objects, and the subsequent cmdlet sees nothing.
*The Issue:* In the example, `$result += "one"` appends a *string* to an array initialized as an empty array. The resulting object type is an array of strings. When you call `$x.GetType().Name`, it returns `System.Object[]` (or similar, depending on context), indicating an array type.
*Zero Items:* If the function returns nothing (implicitly returns `$null`), the pipeline receives `$null`. If it returns an empty array (`@()`), the pipeline receives zero objects.
*Correct Pattern:* Always explicitly return the collection you intend to pass down the pipeline. If you intend to return an array, ensure the return statement is `return @("one")` or `return $result`.

**PS8**
*`[scriptblock]`:* A block of code that can be passed as a parameter to a function or cmdlet. It is essentially a compiled, executable unit of code.
*Function:* A named, reusable block of code that accepts parameters and returns results.
*Passing to Remote Session:* You pass the scriptblock directly to `Invoke-Command` or `Enter-PSSession`.
*Double-Hop Problem:* This occurs when you try to use a variable defined in the *local* scope (the calling machine) inside a scriptblock being executed remotely. The remote session cannot see the local variable.
*Solution:* Use `Invoke-Command -ArgumentList` to explicitly pass the variable values to the remote scriptblock, or use `CredSSP` for more complex credential/context sharing.

**PS9**
*`@()`:* An empty array. It is a collection object.
*`[array]`:* A type accelerator used to explicitly declare a variable as an array type.
*Forcing Single Result:* To force a single result into an array, wrap it: `@[my_value]`.
*Indexing:* Indexing `$null` results in an error (or `$null` depending on context). Indexing an empty array (`@()`) results in `$null` because the index does not exist.

**PS10**
*Comparison Operators:*
* `-eq`: Equal to (case-insensitive by default).
* `-ne`: Not equal to (case-insensitive).
* `-like`: Wildcard matching using `*` and `?` (case-insensitive).
* `-match`: Regular expression matching (case-insensitive by default).
* `-contains`: Checks if a specific *value* exists within a collection.
* `-in`: Checks if a specific *value* exists within a list of values (e.g., `$value -in @('A', 'B')`).
* *Case-Sensitive Variants:* `-ceq`, `-clike`, `-cmatch` enforce case sensitivity.
* *Difference between `-contains` and `-in`*: `-contains` checks if an element is present in a collection. `-in` checks if a value matches any element in a list of values.

**PS11**
*PowerShell Module:* A collection of cmdlets, functions, variables, and data that can be imported into a PowerShell session to extend functionality.
*Script Module (`.psm1`):* A file containing PowerShell code (functions, aliases, etc.) that is loaded into the current session.
*Manifest Module (`.psd1`):* A metadata file that describes the module (version, required dependencies, author, etc.). It is often used to define the module structure and capabilities.
*Binary Module:* A compiled module, often used for performance, containing compiled code (like C# assemblies).
*`Import-Module`:* Loads the module definition (usually from the `.psd1` or `.psm1`) into the current session, making its exported functions and cmdlets available.

**PS12**
*String Interpolation:* Allows embedding expressions directly inside a string using double quotes.
*`"..."` (Double Quotes):* Enables variable expansion (`$VAR`) and expression evaluation (`$VAR + 1`).
*`'...'` (Single Quotes):* Literal string. No expansion occurs.
*Expression Inclusion:* Use `$()` to execute a command or expression and insert its result: `"The result is $(Get-Date)"`.
*Here-String (`@"...@"@`):* A multi-line string literal that preserves all formatting, including newlines, without needing to escape them. It is similar to a here document but contained within the string itself.

**PS13**
*`Get-Member`:* A cmdlet used to inspect the properties and methods available on an object. It is essential for understanding what an object can do.
*Exploring Objects:* You pipe objects into `Get-Member` to see their structure.
*Properties:* Data fields associated with the object (e.g., `Name`, `Count`).
*Methods:* Functions that can be called on the object (e.g., `.ToString()`, `.Calculate()`).
*NoteProperties:* Properties that are not part of the object's core structure but are metadata about it (less common).
*`Select-Object` vs `Where-Object`:*
* `Select-Object`: Used to *choose* which properties/columns to display or to *create* new calculated properties.
* `Where-Object`: Used to *filter* objects based on a condition (i.e., selecting only objects that meet a criteria).

**PS14**
*PowerShell Classes:* Introduced in v5, they allow object-oriented programming paradigms in PowerShell. They are defined using the `class` keyword.
*Difference from C# Classes:* While they support OOP concepts, PowerShell classes are generally more flexible and dynamic than strict C# classes. They are often used to model data structures or complex entities within a script.
*Limitations:* Inheritance and interfaces are supported, but the ecosystem is less rigid than pure C#. Constructors are used, but the dynamic nature allows for runtime modification.
*Usage:* Use a class when you need to model a complex entity with defined state (properties) and behavior (methods) that needs to be instantiated multiple times. Use a function when you need a reusable block of logic that operates on input data.

**PS15**
*`CmdletBinding()`:* An attribute used to turn a standard function into an Advanced Function (Cmdlet). It automatically grants the function standard cmdlet features like parameter validation, common parameters (`-Verbose`, `-Debug`), and pipeline support.
*`SupportsShouldProcess`:* When set to `$true`, it enables the `-WhatIf` parameter. This allows the cmdlet to simulate actions without actually executing them, which is crucial for safety.
*`DefaultParameterSetName`:* Defines which parameter set is used if the user does not specify one, helping to guide users toward the intended usage pattern.
*`ValueFromPipeline`:* When set to `$true`, it tells the cmdlet to accept input objects from the pipeline and process them, rather than requiring them to be passed as explicit parameters.
*Blocks:*
* `Begin`: Executes once before any input is processed (setup).
* `Process`: Executes for each object received from the pipeline (the main work).
* `End`: Executes once after all input has been processed (cleanup).

**PS16**
*Providers System:* PowerShell uses providers to abstract the underlying data source. Instead of hardcoding file system calls, cmdlets interact with a provider interface, allowing the same cmdlet (`Get-ChildItem`) to work across different storage types.
*How `Get-ChildItem` Works:* When you run `Get-ChildItem C:\`, it uses the `FileSystem` provider. When you run `Get-ChildItem Cert:\CurrentUser\My`, it uses the `Certificate` provider.
*Accessing Registry:* You access the registry by using the `Registry` provider: `Get-ChildItem -Path "Registry::HKEY_LOCAL_MACHINE\SOFTWARE"`. The provider handles the necessary Win32 API calls to interact with the registry structure as if it were a directory tree.

**PS17**
*Runspaces:* A runspace is an isolated execution environment where PowerShell commands are executed. It manages the state, environment, and execution context for a set of commands.
*`[runspace]`:* A single, isolated execution context.
*`[runspacepool]`:* A pool of runspaces that can be reused, optimizing resource usage for concurrent tasks.
*`[powershell]`:* The object representing the PowerShell engine itself, which manages the runspaces.
*Parallel Execution:*
* `ForEach-Object -Parallel` (v7+): This is the modern, high-level approach. It automatically manages the creation and pooling of runspaces in the background to execute the script block concurrently, handling thread safety internally.
* Manual Management: In older versions or complex scenarios, you manually create `[runspace]` objects, start them, and use `Invoke-Command` or `Start-Job` to manage the execution and collect results, requiring manual synchronization.

**PS18**
*PSScriptAnalyzer:* A static code analysis tool for PowerShell. It scans scripts against a predefined set of rules to enforce best practices, identify potential bugs, and ensure code quality.
*Enforcing Standards:* It checks for things like unused variables, inconsistent naming conventions, missing error handling, and deprecated syntax.
*Rules/Severity:* Rules are specific checks (e.g., "Do not use global variables"). Severity levels (e.g., `Error`, `Warning`, `Information`) dictate how critical the finding is.
*Custom Rules:* Users can write their own rules to enforce organizational-specific standards.
*Suppression:* Rules can be suppressed using `#Requires -ErrorAction SilentlyContinue` or by adding specific comments (`# PSScriptAnalyzer: Suppress RuleName`).
*CI/CD Integration:* PSScriptAnalyzer is typically integrated into CI/CD pipelines (e.g., Azure DevOps, GitHub Actions) as a mandatory build step. If the analysis finds rules above a certain severity threshold, the build fails, preventing non-compliant code from merging.

**PS19**
*`$using:` Scope:* Used when passing variables into parallel jobs (`ForEach-Object -Parallel`) or background jobs. It creates a read-only copy of the variable's value *at the time the job starts* and makes it available inside the parallel job's scope. This prevents race conditions where the variable might change in the parent scope while the job is running.
*`$args/-ArgumentList`:* Used when passing variables to remote sessions (`Invoke-Command`). These variables are serialized and passed to the remote session's execution context.
*Serialization Limits (CLIXML):* When passing complex objects (like large custom objects or nested structures) across the pipeline or remoting boundaries, PowerShell serializes them using CLIXML. This serialization has depth and size limits. If an object is too complex or too deep, the serialization fails, resulting in an error indicating the object could not be transmitted.

**PS20**
*Desired State Configuration (DSC):* A management framework that allows administrators to define the desired state of a system (e.g., "IIS must be installed," "Registry key X must have value Y") and ensures the system remains in that state, automatically remediating drift.
*Configurations:* The high-level blueprint defining the desired state (e.g., "Web Server Configuration").
*Resources:* The specific components that implement the desired state (e.g., `WindowsFeature`, `Registry`, `Service`). A configuration is composed of multiple resources.
*Local Configuration Manager (LCM):* The engine on the target node responsible for reading the configuration, checking the current state, and applying necessary changes to reach the desired state.
*DSC Difference (WinPS vs PS7+):* In Windows PowerShell, DSC was tightly integrated with Windows features. In PowerShell 7+, DSC functionality has been modernized, often relying on more standardized, cross-platform resource providers, and the framework is more modular.
*Modern Replacement:* While DSC is still used, modern Infrastructure-as-Code (IaC) tools like **Terraform** (for provisioning infrastructure) and **Ansible** (for configuration management) have largely superseded DSC in many cloud-native environments due to their broader scope and declarative nature.
