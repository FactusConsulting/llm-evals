**AA1**
The monolith is a single, tightly coupled application where all components (UI, business logic, data access) reside in one codebase and deploy as one unit. Microservices are a collection of small, independent services, each running its own process and communicating via lightweight mechanisms (like HTTP/REST or message queues).

Problems microservices introduce:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication overhead.
2. **Operational Overhead:** Increased complexity in deployment, monitoring, and logging across dozens of independent services.
3. **Distributed Transactions:** Handling data consistency across multiple independent databases (requiring patterns like Saga).

**AA2**
**Synchronous communication** requires the calling service to wait for an immediate response from the called service before proceeding. Example: RESTful HTTP request/response.
**Asynchronous communication** involves sending a message or event to a broker/queue and immediately continuing execution without waiting for a response. Example: Kafka or RabbitMQ.

**AA3**
A **Reverse Proxy** sits in front of one or more servers, routing external client requests to the appropriate internal service based on rules (e.g., path, host header). Its primary function is traffic routing, load balancing, and SSL termination.
An **API Gateway** is a specialized reverse proxy that adds business logic and cross-cutting concerns on top of routing. It handles authentication, rate limiting, request transformation, protocol translation, and service composition.

No, an API Gateway cannot entirely replace a reverse proxy. A reverse proxy is a foundational network component for traffic distribution and security termination. An API Gateway *is* a specialized reverse proxy, but it adds the layer of application-level governance and business logic that a basic reverse proxy lacks.

**AA4**
The **Saga pattern** is a sequence of local transactions where each transaction updates the database within a single service. If one local transaction fails, the Saga executes a series of compensating transactions to undo the changes made by the preceding successful transactions, maintaining eventual consistency.

*   **Choreography-based:** Services communicate by producing and consuming events. There is no central coordinator; each service knows what to do based on the events it receives. Appropriate when services are highly decoupled and the workflow is simple.
*   **Orchestration-based:** A dedicated service (the Orchestrator) manages the workflow, telling each participant service what local transaction to execute via commands. Appropriate when the workflow is complex, long-running, or requires centralized visibility and control.

**AA5**
**CQRS (Command Query Responsibility Segregation)** separates the model used for updating data (Commands) from the model used for reading data (Queries). Commands modify state; Queries retrieve state.

It is often paired with **Event Sourcing (ES)** because ES stores the state of the application as a sequence of immutable events. The Command side writes these events to the event store. The Query side then builds optimized, denormalized read models (projections) by consuming these events.

This combination solves the problem of needing highly optimized read paths without compromising transactional integrity on the write path. A traditional CRUD model forces the read and write models to share the same schema, leading to complex joins and performance bottlenecks when read requirements diverge significantly from write requirements.

**AA6**
The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service). It monitors calls and, if failures exceed a threshold, it "trips" the circuit, immediately failing subsequent calls without attempting the network request, allowing the failing service time to recover.

The three states are:
1. **Closed:** Normal operation; requests pass through.
2. **Open:** Failures threshold reached; requests are immediately rejected (fail-fast).
3. **Half-Open:** After a timeout, a few test requests are allowed through to see if the service has recovered. If they succeed, the circuit closes; if they fail, it opens again.

It differs from a simple retry with backoff because retry/backoff *continues* hammering the failing service, potentially exacerbating its overload. The Circuit Breaker *stops* the traffic entirely, giving the service breathing room. They are used together: the Circuit Breaker prevents cascading failures, and retries/backoff are used *within* the closed state or during the half-open state for transient errors.

**AA8**
**Strong Consistency** guarantees that once a write operation is acknowledged, all subsequent read operations will immediately see that updated value. (e.g., ACID transactions in a single database).
**Eventual Consistency** guarantees that if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value, but there is a window where reads might return stale data.

To prevent overselling inventory (a critical business invariant), you must enforce **Strong Consistency** at the point of transaction.

*   **Consistency Model:** Strong Consistency (or Linearizability).
*   **Data Store:** A transactional relational database (e.g., PostgreSQL, MySQL) or a strongly consistent distributed ledger/database (e.g., CockroachDB, Spanner).
*   **Patterns:** Use pessimistic locking or atomic database transactions (e.g., `SELECT ... FOR UPDATE`) during the checkout/inventory deduction process. If scaling requires distributed writes, use a consensus algorithm (like Raft or Paxos) provided by the chosen data store to ensure all nodes agree on the inventory count before confirming the sale.

**AA9**
A **sidecar proxy** is a small, dedicated network proxy container deployed alongside every instance of a service container within the same deployment unit (e.g., Kubernetes Pod). It intercepts all inbound and outbound network traffic for the application container.

In an Istio deployment, **Envoy** is the high-performance L7 proxy that runs as the sidecar. It handles service discovery, traffic routing, load balancing, metrics collection, and policy enforcement for the application container.

*   **Data Plane:** The set of proxies (Envoy sidecars) that handle the actual traffic forwarding, routing, and policy enforcement.
*   **Control Plane:** The management layer (e.g., Istiod) that configures and manages the data plane proxies, pushing routing rules, security policies, and configuration updates to all the sidecars.

mTLS between sidecars solves the problem of *untrusted network hops*. Application-level TLS requires the application code to manage certificates, key rotation, and handshake logic. Sidecar mTLS offloads this entirely to the proxy, ensuring that all service-to-service communication is automatically encrypted and mutually authenticated *at the network layer*, regardless of the application language.

**AA10**
The **Strangler Fig pattern** is an incremental migration strategy where a new system (the "vine") is built around a legacy system (the "fig"). New functionality is built in the microservices architecture, and traffic is gradually rerouted from the monolith to the new services until the monolith can be safely decommissioned.

**Migration Strategy (Monolith to Microservices):**
1. **Identify Seams:** Identify bounded contexts within the monolith (e.g., User Profile, Order Processing, Inventory).
2. **Implement Facade/Proxy:** Place an API Gateway in front of the monolith.
3. **Extract First Service:** Select a low-risk, self-contained context (e.g., User Profile). Build the new microservice for this context.
4. **Reroute Traffic:** Configure the API Gateway to route all `/users/*` requests to the new microservice, while all other requests still go to the monolith.
5. **Data Synchronization:** Implement a mechanism (e.g., Change Data Capture or dual writes) to keep the new service's data synchronized with the monolith's database during the transition.
6. **Iterate:** Repeat steps 3-5 for the next bounded context until the monolith is "strangled."

**AA11**
The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable, and resilient software-as-a-service applications.

Six factors and their importance:
1. **Codebase:** One codebase tracked in revision control, many deploys. (Ensures consistency across environments).
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures reproducibility).
3. **Config:** Store configuration in the environment. (Decouples code from deployment environment, crucial for cloud elasticity).
4. **Backing Services:** Treat backing services (databases, queues) as attached resources. (Allows easy swapping of infrastructure providers).
5. **Build, Release, Run:** Strictly separate these stages. (Enables CI/CD pipelines and immutable deployments).
6. **Processes:** Execute the application as one or more stateless processes. (Essential for horizontal scaling; statelessness allows any instance to handle any request).

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Services only know the event contract) | Tight (Caller must know the callee's endpoint/interface) |
| **Scalability** | Excellent (Decoupled producers/consumers scale independently) | Good (Vertical/Horizontal scaling of services) |
| **Debugging Complexity** | High (Tracing flow across asynchronous boundaries is hard) | Low (Synchronous stack trace is clear) |
| **Ordering Guarantees** | Guaranteed within a partition/topic. | Guaranteed by the request/response sequence. |
| **Failure Handling** | Built-in resilience via message retention/replay. | Requires explicit retry logic and circuit breakers. |

**Choose Event-Driven when:** The system requires high throughput, needs to react to state changes across many services (e.g., order fulfillment), or when services must remain highly decoupled.
**Choose Request-Driven when:** The interaction requires an immediate response (e.g., user login validation, fetching a specific resource), or when the workflow is simple and synchronous.

**AA13**
A **Load Balancer** distributes incoming network traffic across a group of backend servers (a server farm) to ensure no single server is overwhelmed, maximizing throughput and availability.

*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It distributes traffic based on network information like IP address and port number. It is fast because it does not inspect the payload.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (headers, URL path, cookies) to make intelligent routing decisions.

Use Case for Layer 7: Routing traffic based on the requested URL path (e.g., routing `/api/v1/users` to the User Service and `/api/v2/orders` to the Order Service, even if they share the same IP/port).

**AA14**
A **Message Queue** (e.g., RabbitMQ) is a point-to-point or publish/subscribe system designed for reliable message delivery. Messages are consumed and *removed* from the queue by a single consumer. It focuses on task execution and guaranteed delivery.

A **Log-based Message Broker** (e.g., Kafka) is a distributed commit log. Messages are appended to topics and are *retained* for a configurable period. Consumers read from the log at their own pace, and multiple consumers can read the same message stream independently.

**Pick RabbitMQ (Queue) when:** You need guaranteed, single consumption of a task (e.g., processing a payment request) and the task is ephemeral.
**Pick Kafka (Log Broker) when:** You need stream processing, historical replayability, high-volume data ingestion, or multiple independent consumers to react to the same event stream.

**AA15**
A **Container** is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and settings. It shares the host OS kernel.

A **Virtual Machine (VM)** virtualizes the entire hardware stack, including the CPU, memory, disk, and network interface, running a full guest OS on top of a hypervisor.

Containers are popular because they offer high density (many containers run efficiently on one host) and fast startup times, while providing strong process isolation and portability (the container runs the same way on a developer's laptop as it does in production).

**AA16**
**Stateless Services** do not retain any session-specific data or client context between requests. Every request from a client must contain all the necessary information for the service to process it.
**Stateful Services** retain data or context across multiple requests (e.g., user session data, in-memory caches, database connections).

Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance of the service, as no instance holds unique session data that would need to be maintained or synchronized across the cluster.

*   **Stateless Example:** A REST API endpoint that validates a JWT token provided in the header.
*   **Stateful Example:** A Redis cache server or a database instance.

**AA17**
An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using object-oriented paradigms (classes and objects) instead of writing raw SQL queries. It maps database tables to application objects.

Popular ORMs:
*   **Python:** SQLAlchemy
*   **Java:** Hibernate

**Trade-offs:**
*   **Pros of ORM:** Increased developer productivity, abstraction from specific SQL dialects, type safety, and easier refactoring.
*   **Cons of ORM:** Performance overhead (the ORM might generate inefficient SQL), the "impedance mismatch" (mapping complex object graphs to flat relational tables can be awkward), and difficulty in optimizing complex, highly specific queries.

**AA18**
The **Bulkhead pattern** isolates components or resources so that the failure or exhaustion of resources in one area does not cascade and bring down the entire system. It partitions resources into isolated pools, much like watertight compartments in a ship.

It relates to resource isolation by ensuring that if one dependency or service becomes slow or fails, it only consumes its allocated pool of resources, leaving the resources for other services untouched and available.

**Implementation Example (Thread Pools):** If Service A calls Service B and Service C, you would assign Service B its own dedicated thread pool (e.g., 10 threads) and Service C its own pool (e.g., 5 threads). If Service B becomes slow and exhausts its 10 threads, Service C's 5 threads remain available to handle its requests, preventing the failure of B from blocking C.

**AA19**
| Feature | Operational Transformation (OT) | CRDTs (Conflict-free Replicated Data Types) |
| :--- | :--- | :--- |
| **Consistency** | Strong (Requires centralized coordination/transformation logic) | Eventual (Guaranteed convergence mathematically) |
| **Latency** | Higher (Requires server intervention to transform operations) | Lower (Operations can be applied locally immediately) |
| **Complexity** | High (Complex transformation algorithms, difficult to implement correctly) | Medium (Requires understanding specific data structure properties) |
| **Offline Support** | Difficult (Requires complex state synchronization upon reconnection) | Excellent (Operations are commutative and associative; can be applied in any order) |

I would choose **CRDTs**. For a system that *must* support offline editing, CRDTs are superior because they are designed to handle concurrent, unordered operations that arrive at different replicas. They guarantee that regardless of the order in which operations are received, all replicas will eventually converge to the same correct state without needing a central server to mediate and transform every change.

**AA20**
**Challenges of Distributed Tracing:**
1. **Context Propagation:** Ensuring that the unique trace ID and span ID are passed correctly across service boundaries. This requires standardized headers (e.g., W3C Trace Context or B3 headers) to be injected into every request/message.
2. **Sampling:** Since tracing every request is too expensive, sampling is needed.
    *   **Head-based:** A decision (e.g., sample 1% of requests) is made at the entry point of the trace. Simple, but might miss critical errors in unsampled traces.
    *   **Tail-based:** The decision is made after the entire trace is complete, based on the trace's content (e.g., sample all traces that resulted in an HTTP 5xx error). More accurate but requires buffering all traces before analysis.
3. **Storage/Querying:** Tools like Jaeger or Tempo are used to ingest, index, and visualize the trace data, allowing engineers to reconstruct the entire request path.
4. **Asynchronous Messaging:** This is the hardest part. When a request passes through Kafka, the trace context must be serialized and injected into the Kafka message headers *before* publishing. The consuming service must then extract these headers upon receipt to resume the existing trace span, linking the producer span to the consumer span.

**OP1**
A **Type 1 (Bare-Metal) Hypervisor** runs directly on the host hardware, managing the hardware resources and hosting the Guest OSs. It has minimal overhead. Examples: VMware ESXi, Microsoft Hyper-V (when run natively).
A **Type 2 (Hosted) Hypervisor** runs as an application *within* a conventional operating system (the host OS). It relies on the host OS for hardware access. Examples: VMware Workstation, Oracle VirtualBox.

**OP2**
**SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. The server sees the storage as a raw disk volume. Protocols: Fibre Channel (FC), iSCSI. Used when high I/O performance and low latency are critical (e.g., large databases).
**NAS (Network Attached Storage):** A file-level storage device accessible over the standard network (LAN). The storage device manages the file system. Protocols: NFS, SMB/CIFS. Used for file sharing, backups, and general file storage.

**OP3**
**3-Tier Architecture:**
1. **Access Layer:** Connects end-user devices (switches, endpoints).
2. **Distribution Layer:** Aggregates traffic from the Access layer, enforces policies, and acts as the boundary between the access and core.
3. **Core Layer:** High-speed backbone responsible only for fast packet switching between distribution blocks.

**Leaf-Spine** is preferred because it creates a non-blocking, predictable, low-latency fabric. In 3-tier, traffic often has to traverse up to the Distribution layer and back down, creating bottlenecks and unpredictable hop counts. Leaf-Spine connects every leaf (access) switch to every spine switch, ensuring that any two endpoints are separated by a maximum of two hops (Leaf $\rightarrow$ Spine $\rightarrow$ Leaf), providing predictable latency and massive horizontal scalability.

**OP4**
**Architecture:**
*   **Node Count:** Minimum 3 nodes for quorum and high availability.
*   **Quorum:** Ceph requires a majority of monitors (MONs) to be available to maintain cluster state. With 3 nodes, 2 must be up.
*   **Fencing (STONITH):** Essential. If a node fails, the cluster must ensure that the failed node cannot write data simultaneously (split-brain). Fencing mechanisms (e.g., IPMI power cycling, network isolation) must be in place to forcibly shut down the suspected node.
*   **Shared Storage:** Ceph is the preferred choice as it is software-defined storage (SDS) and integrates natively with the cluster.
*   **Failure Scenario:** If one node fails, the remaining nodes maintain quorum. The cluster continues operating, and the failed node's workloads are rescheduled onto the healthy nodes. The cluster monitors the failed node and attempts to recover its services once it returns.

**OP5**
**VLAN Trunking** is the process of allowing traffic from multiple VLANs to traverse a single physical link (a trunk port).
**802.1Q Tagging** is the standard mechanism used to identify which VLAN a specific frame belongs to. It inserts a 4-byte tag into the Ethernet frame header, containing a VLAN ID (VID).

**Linux Configuration:** You configure the physical NIC to be in promiscuous mode (or simply use the interface as a bridge). Then, you create multiple virtual interfaces (VLAN sub-interfaces) on top of the physical NIC, each assigned a specific VLAN ID.
Example: `eth0.10` (for VLAN 10) and `eth0.20` (for VLAN 20) are created, and IP addresses are assigned to these sub-interfaces.

**OP6**
*   **RAID 1 (Mirroring):** Duplicates data across two or more drives. Excellent read performance, 50% capacity loss. Fault tolerance: 1 drive failure.
*   **RAID 5 (Striping with Parity):** Stripes data across drives and distributes parity information. Good balance. Fault tolerance: 1 drive failure.
*   **RAID 6 (Striping with Dual Parity):** Stripes data and uses two independent parity blocks. Higher fault tolerance. Fault tolerance: 2 drive failures.
*   **RAID 10 (Mirroring + Striping):** Stripes data across mirrored pairs. Excellent performance and fault tolerance. Capacity loss: 50%.
*   **RAID Z2 (ZFS):** Similar to RAID 6, using multiple parity blocks across multiple disks. Highly resilient and integrates ZFS features.

**Choice for Database Server (6 drives):** **RAID 10** or **RAID Z2**.
*   **RAID 10:** Offers the best combination of high read/write performance (due to striping) and excellent fault tolerance (can lose multiple drives as long as they aren't in the same mirrored pair). This is often preferred for high-transaction databases.
*   **RAID Z2:** Offers better capacity utilization than RAID 10 while providing robust protection against two simultaneous drive failures.

**OP7**
**Architecture Components:**
1. **Internal Recursive Resolvers:** Located inside the private network, these servers receive DNS queries from internal clients (laptops, servers). They forward external queries to the DMZ resolvers and internal queries to the AD DNS servers.
2. **Internal Authoritative Servers:** These are the DNS servers hosting the internal zones (e.g., `corp.local`), typically integrated with Active Directory.
3. **DMZ Authoritative Servers:** These servers host the public-facing zones (e.g., `company.com`). They are hardened and only accept external queries.
4. **Forwarders:** The internal resolvers use forwarders to send external queries to trusted public DNS providers (e.g., Google 8.8.8.8).
5. **Conditional Forwarding:** The internal resolvers are configured to forward queries for `corp.local` directly to the internal AD servers, bypassing the public forwarders.
6. **DNSSEC:** Applied only to the external (public) zone to cryptographically sign records, ensuring data integrity during external lookups.

**Laptop Movement:** When a laptop moves from the office (on the internal network) to the VPN, its DNS requests are routed through the VPN tunnel to the internal recursive resolvers. The resolvers then use conditional forwarding to correctly resolve internal names (`server.corp.local`) while using standard forwarding for external names.

**OP8**
The **PKI Chain of Trust** establishes trust from the highest authority down to the individual certificate.
1. **Root CA:** The self-signed, highest authority. It is kept offline (air-gapped) and highly secured. It signs the subordinate CA certificate.
2. **Subordinate/Issuing CA:** This CA is online and performs the day-to-day signing of end-entity certificates (servers, users). It is signed by the Root CA.
3. **End-Entity Certificate:** The certificate issued to the actual resource (e.g., a web server). It is signed by the Subordinate CA.

**CRL (Certificate Revocation List) vs OCSP (Online Certificate Status Protocol):**
*   **CRL:** A list published periodically by the CA containing the serial numbers of all revoked certificates. Clients must download and check this list.
*   **OCSP:** A real-time query service where a client asks the CA, "Is this specific certificate valid?" This is faster and more immediate than checking a large CRL.

**Consequences of Compromise:**
*   **Compromised Subordinate CA:** High risk. An attacker can issue fraudulent certificates for any service under that CA's scope. The damage is contained to the scope of that subordinate CA, and it can be revoked/replaced without affecting the Root CA's trust anchor.
*   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, if it is compromised, *every* certificate issued under its chain is untrustworthy, requiring a complete, organization-wide PKI rebuild and trust re-establishment.

It leverages the low cost of the public internet (unlike MPLS), offers centralized management, and uses intelligent path steering to prioritize latency-sensitive traffic (like VoIP) over the best available link, providing reliability superior to a simple IPsec VPN.

**OP10**
**iDRAC (Dell), iLO (HP), IPMI (Intelligent Platform Management Interface):** These are dedicated, embedded management processors on server hardware that allow administrators to manage the server's hardware components (power, fans, BIOS, remote console access) independently of the main operating system.

**Out-of-Band Management Criticality:** It is critical because if the main OS or network stack fails, you still need a way to access the server to diagnose the failure, reboot it, or attach storage. It provides a separate, resilient management channel.

**Exposure Risk:** If the IPMI interface is exposed to the internet, it becomes a high-value target. An attacker could use it to remotely power cycle, access the console, or potentially exploit vulnerabilities in the management firmware to gain root access to the physical hardware, bypassing all OS-level security controls.

**OP11**
**LVM (Logical Volume Manager):** A software layer that abstracts physical disks into flexible logical volumes. It allows resizing and snapshotting of volumes dynamically. Snapshot semantics are typically *crash-consistent* (the state at the moment of the snapshot, but not necessarily application-consistent).
**LVM-Thin:** An extension of LVM that allows for thin provisioning, meaning you can allocate more logical space than physically exists on the underlying storage pool. It is highly efficient for space utilization. Snapshot semantics are similar to standard LVM.
**ZFS:** A complete file system and volume manager. It manages storage pools, volumes, and snapshots natively. It is known for its data integrity features (checksumming) and advanced snapshot capabilities. Snapshot semantics are generally *application-consistent* if used correctly with volume management tools.

**Usage:**
*   **LVM:** When you need flexible volume management on standard block storage without the overhead of a full file system overhaul.
*   **LVM-Thin:** When you need to over-provision storage capacity efficiently on top of existing block devices.
*   **ZFS:** When data integrity, advanced features (like replication, compression, and integrated volume management), and robust snapshots are paramount (e.g., archival or critical database storage).

**OP12**
**Strategy:** A **Stretch Cluster** is the most direct way to survive a complete site failure, but it is extremely complex. A more practical approach is a **Disaster Recovery (DR) setup** using asynchronous replication.

**Stretch Cluster Design (High Risk):**
*   **Ceph CRUSH Rules:** Must be configured to span both sites, ensuring that data replicas are placed across the two geographically separated data centers.
*   **Monitor Placement:** Monitors must be distributed across both sites, ensuring quorum can be maintained even if one site loses connectivity.
*   **Network Latency:** Extremely low latency is required (ideally <10ms round trip) to prevent the cluster from constantly timing out and triggering split-brain scenarios.
*   **Split-Brain Problem:** This occurs when network partitioning causes both sides of the cluster to believe the other side is down, leading both sides to assume they hold the quorum and begin accepting writes independently, resulting in irreconcilable data divergence.

**Why 2-site Ceph is generally bad without a tiebreaker:** Without a tiebreaker (like a quorum witness or fencing mechanism), if the link between Site A and Site B fails, both sites might see themselves as having a majority of monitors, leading to a split-brain scenario where both sites become writable, corrupting the data.

**OP13**
**DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses and other network configuration parameters (subnet mask, gateway, DNS servers) to devices on a network.

**DORA Process:**
1. **Discover:** Client broadcasts a DHCP Discover message to find available servers.
2. **Offer:** DHCP servers respond with a DHCP Offer, proposing an IP address and lease terms.
3. **Request:** The client sends a DHCP Request, formally accepting the offered IP address.
4. **Acknowledge:** The server sends a DHCP ACK, finalizing the lease agreement.

**Server Unavailability:** When a Windows client's lease expires and the DHCP server is unavailable, the client will continue using its current IP address until the lease time is fully exhausted. Once the lease expires, the client will attempt to renew the lease (sending a DHCP Request). If the server is down, the client will eventually fail to communicate on the network until it is manually configured or the network is restored.

**OP14**
**Unmanaged Switch:** A plug-and-play device that operates purely at Layer 2 (MAC address forwarding). It simply forwards frames based on MAC addresses without any configuration options. It is suitable for small, simple networks.
**Managed Switch:** A configurable device that allows administrators to control traffic flow, security, and performance.

**Enterprise Features:** Managed switches provide:
*   **VLAN Support:** Segmenting broadcast domains for security and traffic isolation.
*   **QoS (Quality of Service):** Prioritizing critical traffic (like VoIP) over bulk data transfers.
*   **Port Security:** Limiting the number of MAC addresses allowed on a port to prevent unauthorized devices.
*   **Link Aggregation (LAG/LACP):** Bundling multiple physical links into one logical link for increased bandwidth and redundancy.

**OP15**
**NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.

**Criticality:** Accurate time synchronization is critical because many distributed systems rely on timestamps for ordering events, logging, and security.

**Consequences of Clock Drift:**
1. **Transaction Failures:** Distributed databases and microservices rely on timestamps for causality. Drift can cause transactions to fail or be processed out of order.
2. **Security Issues:** Kerberos authentication and certificate validation rely on time validity windows. Drift can cause authentication failures or allow expired credentials to be accepted.
3. **Log Analysis:** Correlating events across multiple servers (e.g., debugging a failure) becomes impossible if the logs are not time-aligned.

**OP16**
**Physical Server:** The actual hardware machine (CPU, RAM, Motherboard, NICs).
**Virtual Machine (VM):** A software emulation of a physical computer, running a full Guest OS, managed by a hypervisor.
**Container:** A lightweight, isolated process environment that shares the host OS kernel, containing only the application and its dependencies.

**Bare Metal Use Case:** You would run a workload directly on bare metal when the workload requires absolute maximum hardware performance, minimal latency, or when the overhead introduced by virtualization (even Type 1) is unacceptable. Examples include high-frequency trading platforms, specialized hardware acceleration tasks (e.g., GPU compute), or specialized network appliances.

**OP17**
**UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power when utility power fails. Its role is to bridge the gap between the power failure and the generator startup time, allowing graceful shutdown or continuous operation.
**Generator:** Provides long-term, sustained power during extended utility outages.

**Why both are needed:** The UPS handles the immediate, transient power dips and the critical few seconds/minutes required for the generator to spin up and stabilize. The generator provides the sustained power needed for hours or days.

**ATS (Automatic Transfer Switch):** This device monitors the utility power source. When utility power fails, the ATS automatically switches the load from the utility source to the generator source. When utility power returns, the ATS switches the load back to the utility source.

**OP18**
**Active-Passive Clustering:** One server (Active) handles all the workload, while the second server (Passive) remains idle, constantly monitoring the active node. If the active node fails, the passive node takes over the workload (failover). This is simpler and uses less overhead but sacrifices potential capacity.
**Active-Active Clustering:** Both servers actively handle portions of the workload simultaneously. This provides higher resource utilization and better scaling but is significantly more complex, requiring sophisticated mechanisms to prevent data corruption (e.g., distributed locking).

**HA Implementation (PostgreSQL):**
1. **Pacemaker/Corosync:** Used for cluster resource management and communication. Corosync handles cluster membership and messaging.
2. **Fencing (STONITH - Shoot The Other Node In The Head):** Essential. If the cluster suspects a node is hung (not just slow), STONITH uses an external mechanism (e.g., IPMI command) to forcibly power off the suspected node to prevent it from corrupting the shared resource (the database).
3. **Virtual IPs (VIP):** A single, floating IP address is assigned to the cluster resource. Pacemaker ensures this VIP is only active on the node currently running the PostgreSQL service.
4. **Failover Behavior:** If the active node fails, Corosync detects the failure, Pacemaker initiates the failover sequence, STONITH ensures the failed node is isolated, and the passive node assumes ownership of the VIP and starts the PostgreSQL service, redirecting traffic.

**OP19**
**3-2-1 Rule:** Maintain at least **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.

**RPO (Recovery Point Objective):** The maximum acceptable amount of data loss measured in time (e.g., 1 hour). Dictates backup frequency.
**RTO (Recovery Time Objective):** The maximum acceptable downtime measured in time (e.g., 4 hours). Dictates recovery speed and infrastructure readiness.

**Backup Types:**
*   **Full:** Copies all selected data. Slowest, largest backup.
*   **Incremental:** Copies only data that has changed since the *last* backup of any type. Fastest, smallest backup, but longest restore time.
*   **Differential:** Copies all data that has changed since the *last full backup*. Faster restore than incremental, but larger than incremental.

**Deduplication:** Reduces storage footprint by identifying and eliminating redundant data blocks across backups.
**Offsite Storage:** Tape (air-gapped, slow retrieval), Disk (fast retrieval, requires physical offsite location), Cloud (flexible, scalable, good for DR).
**Immutable Backups:** Backups that cannot be altered, encrypted, or deleted for a set period. This is the primary defense against ransomware, as the attacker cannot encrypt or delete the recovery point.

**Backup vs. Disaster Recovery (DR):**
*   **Backup:** The process of creating copies of data for recovery from localized failures (hardware failure, accidental deletion).
*   **Disaster Recovery:** The comprehensive plan and infrastructure to restore *all* business functions (applications, network, data) following a catastrophic event (fire, flood, regional outage). DR relies on backups but encompasses the entire operational recovery process.

**OP20**
**802.1X (Port-Based Network Access Control):** A standard that controls which devices are allowed to connect to a wired network port.
*   **Supplicant:** The client device (laptop, server) requesting access.
*   **Authenticator:** The network switch port that enforces the policy and communicates with the server.
*   **Authentication Server:** The central authority (usually RADIUS) that verifies the supplicant's credentials.

**EAP Methods:**
*   **EAP-TLS:** Uses digital certificates for mutual authentication (both client and server must present valid certificates). Highest security.
*   **PEAP (Protected EAP):** Encapsulates an inner authentication method (like MS-CHAPv2) within a TLS tunnel. Easier to deploy than EAP-TLS but relies on password credentials inside the tunnel.

**RADIUS:** The protocol used by the Authenticator (switch) to communicate authentication requests, authorization decisions, and accounting data to the Authentication Server.

**Dynamic VLAN Assignment:** Upon successful authentication, the RADIUS server sends an Access-Accept message back to the switch, which includes vendor-specific attributes instructing the switch to place the supplicant into a specific VLAN (e.g., VLAN 10 for corporate users, VLAN 50 for guests).

**Failed Authentication:** If a device fails authentication, the switch port is placed into an unauthorized state (often a quarantine VLAN or completely shut down), preventing any traffic from passing until credentials are provided or the port is manually reset.

**MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., printers, IP phones). The switch sends the device's MAC address to the RADIUS server, which checks a pre-configured database mapping that MAC address to an authorized user/VLAN, bypassing the full EAP handshake.
