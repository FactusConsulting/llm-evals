**Kubernetes Answers**

K1 — A Deployment manages stateless applications, ensuring a specified number of identical replicas are running and handling updates via rolling updates. A StatefulSet manages stateful applications, providing stable, unique network identifiers and persistent storage for each pod (e.g., databases).

K2 — A ClusterIP Service exposes the Service internally within the cluster using a stable virtual IP (ClusterIP). When traffic hits this IP, `kube-proxy` (running on every node) intercepts the traffic and uses iptables or IPVS rules to load balance the request across the healthy backend pods associated with that Service.

K3 — A **PersistentVolume (PV)** is a piece of storage in the cluster provisioned by an administrator or dynamically. It is the actual storage resource. A **PersistentVolumeClaim (PVC)** is a request for storage made by a user/application. It is a request object that binds to an available PV that meets its requirements (size, access mode). A **StorageClass** defines the "class" of storage (e.g., fast SSD, slow HDD) and dictates the dynamic provisioning mechanism (the provisioner) used to create the PV when a PVC requests it. They relate as: PVC $\rightarrow$ requests $\rightarrow$ StorageClass $\rightarrow$ provisions $\rightarrow$ PV $\rightarrow$ mounts to Pod.

K4 —
1. **Check Pod Events:** Use `kubectl describe pod <name>` to examine the `Events` section for specific error messages (e.g., ImagePullBackOff, CrashLoopBackOff reason).
2. **Check Logs:** Use `kubectl logs <name>` to see the application's output leading up to the crash. This often reveals application-level exceptions or configuration errors.
3. **Check Container Image:** Verify the image tag and registry access. Use `kubectl describe pod` to check for `ImagePullBackOff` errors, indicating network or authentication issues.
4. **Check Resource Limits/Requests:** Review the pod spec against the node capacity. If the pod is crashing due to OOMKilled, the memory limit is too low.

K5 — CoreDNS acts as the cluster's internal DNS service, translating service names (e.g., `my-service.mynamespace.svc.cluster.local`) and pod names into cluster IP addresses. If CoreDNS pods are down, DNS resolution fails entirely. Pods cannot resolve service names, and external DNS lookups (if relying on CoreDNS forwarding) will fail, leading to application connectivity failures across the cluster.

K6 — The scheduler uses a two-phase process:
1. **Filtering (Predicates):** The scheduler first filters out nodes that *cannot* run the pod based on hard constraints. Examples include: resource availability (does the node have enough CPU/Memory?), node selector matching, and volume attachment availability.
2. **Scoring (Priorities):** From the remaining eligible nodes, the scheduler scores them based on various preferences. The node with the highest score is chosen.
Specific factors considered include:
1. **Resource Utilization:** Preferring nodes that are less utilized to balance the load.
2. **Node Affinity/Anti-Affinity:** Respecting rules that dictate where the pod should or should not run relative to other pods.
3. **Taints and Tolerations:** Ensuring the pod is allowed to run on nodes that have specific taints applied.

K7 — **Scheduling:** Yes, the pod *will* be scheduled, provided the node has enough *available* capacity. The scheduler primarily checks against the *requests* (256Mi). Since 3.5GB is requested and 4GB is available, there is 0.5GB free. 256Mi fits easily.
**Runtime Behavior:** If the pod uses 600Mi, it will exceed its `limits.memory` (512Mi). Kubernetes will enforce the limit, and the container runtime (e.g., containerd) will terminate the container, resulting in an **OOMKilled** status, causing the Deployment controller to restart the pod.

K8 — 1. **External LB:** The external Load Balancer (L4/L7) receives the external traffic and forwards it to the Ingress Controller node(s) based on the configured host/path rules.
2. **Ingress Controller:** The NGINX controller receives the request, inspects the Ingress resource rules, and determines the target Service based on the host/path match.
3. **Service:** The Ingress Controller forwards the request to the ClusterIP Service associated with the application.
4. **Endpoints:** The Service object uses the Endpoints object (which tracks the IP:Port of all healthy backing pods) to select a specific target pod IP.
5. **kube-proxy/iptables:** `kube-proxy` maintains iptables rules on the node. These rules intercept the traffic destined for the Service ClusterIP and rewrite the destination IP/port to the actual IP and port of the selected backend pod, completing the delivery.

K9 — A NetworkPolicy defines rules that specify how groups of pods are allowed to communicate with each other and with external network endpoints. If no NetworkPolicy exists in a namespace, the default behavior is **"allow all"** ingress and egress traffic. When you apply a NetworkPolicy that selects certain pods, the default behavior changes to **"deny all"** ingress/egress traffic for those selected pods, unless explicitly allowed by another policy.

K10 — **RollingUpdate:** Gradually replaces old pod versions with new ones, maintaining service availability by running both old and new versions concurrently during the transition. **Recreate:** Terminates all existing pods of the old version before creating any new pods of the new version.
You would choose **Recreate** when the application requires a clean state or when the change is fundamental (e.g., changing the underlying OS image or configuration that cannot be gracefully handled by the application), and downtime is acceptable.

K11 — A namespace is a mechanism to partition cluster resources (like pods, services, etc.) into logical groups. It provides scope isolation, preventing naming collisions. Default namespaces include: `default` (where resources land if no namespace is specified), `kube-system` (for cluster components like CoreDNS, kube-proxy), `kube-public`, and `kube-node-lease`.

K12 — `kubectl describe pod <name>` provides a detailed status report, including:
1. **Events:** A chronological log of actions taken on the pod (scheduling, pulling images, starting containers, errors).
2. **Container Status Details:** Detailed exit codes, restart counts, and specific reasons for termination.
3. **Resource Requests/Limits:** Explicitly shows the requested and limited CPU/Memory for each container.

K13 — A ConfigMap is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) in key-value pairs.
Methods to consume it:
1. **Environment Variables:** Mounting the ConfigMap as environment variables in the Pod spec.
2. **Volume Mounts:** Mounting the ConfigMap as a file volume inside the container filesystem.

K14 — **ClusterIP:** Exposes the Service only internally within the cluster using a virtual IP. Only reachable from within the cluster.
**NodePort:** Exposes the Service on a specific port on *every* node in the cluster. This allows external access via `<NodeIP>:<NodePort>`.
**LoadBalancer:** Exposes the Service externally by provisioning an external cloud load balancer (e.g., AWS ELB, GCP Load Balancer) that routes traffic to the cluster nodes.

K15 — A DaemonSet ensures that a copy of a pod runs on *every* (or a specified subset of) eligible node in the cluster. You use it when you need a service that must run locally on every node, such as a log collector (Fluentd), a node monitoring agent (Prometheus Node Exporter), or a network plugin component. A Deployment manages a fixed set of replicas across the cluster, regardless of the node count.

K16 — **Taints** are properties applied to a Node that repel pods. A pod must have a matching **Toleration** to be scheduled onto a tainted node.
**Node Affinity** is a scheduling preference that dictates where a pod *should* or *must* run based on node labels (e.g., `requiredDuringSchedulingIgnoredDuringExecution`).
**Difference:** Taints/Tolerations are about *repelling* pods; Affinity is about *attracting* pods.
**Use Case (Taint):** Preventing general workloads from running on a dedicated GPU node by tainting it with `dedicated=gpu:NoSchedule`.
**Use Case (Affinity):** Ensuring a database pod always runs on nodes labeled `disktype=ssd`.

K17 — A Kubernetes Operator is a method of packaging, deploying, and managing a complex application (like a database cluster) using custom controllers. It extends the Kubernetes API to manage the application's operational lifecycle (e.g., backups, scaling, failover) using domain-specific knowledge. It differs from a standard controller because it implements complex, human-like operational logic (e.g., "if replication factor drops below 3, initiate failover to node X"), solving the problem of managing stateful, complex applications that standard controllers cannot handle gracefully.

K18 — Kubernetes uses **Raft** for etcd consistency, which is a consensus algorithm that ensures strong consistency. It requires a strict majority (quorum) of nodes to agree on a write operation before it is committed. If the quorum is lost (e.g., 2 out of 3 nodes fail), the cluster enters a read-only or unavailable state because no new writes can be safely committed. To recover from 2 out of 3 nodes being permanently lost, the cluster cannot be recovered using the existing quorum. A new, functional quorum (at least 3 nodes) must be established, and the cluster state must be manually bootstrapped or restored from a backup.

K19 — RBAC controls authorization—what users/service accounts can do to cluster resources.
*   **Role:** Defines a set of permissions (verbs like get, list, create) scoped to a specific **Namespace**.
*   **ClusterRole:** Defines a set of permissions scoped across the **entire cluster**.
*   **RoleBinding:** Binds a **Role** to a subject (User/Group/ServiceAccount) within a specific **Namespace**.
*   **ClusterRoleBinding:** Binds a **ClusterRole** to a subject across the **entire cluster**.

**Manifests for Read-Only Access to Pods/Logs in `my-namespace`:**
```yaml
# 1. Define the permissions (Role)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# 2. Bind the permissions to the user/service account (RoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: my-namespace
subjects:
- kind: User # Or ServiceAccount
  name: developer-user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` specifies the number of dots to append to a hostname when performing DNS lookups. If `ndots` is set too low (e.g., 1), and the pod tries to resolve an external domain like `api.external.com`, the resolver might first try to resolve it as `api.external.com.cluster.local` or `api.external.com.namespace.svc.cluster.local` before trying the bare domain. This results in many unnecessary, slow internal DNS queries.
To fix this, you use `dnsConfig` in the Pod spec and explicitly set `options` to override the default `ndots` value, typically setting it to 0 or a value appropriate for external lookups.

**Development Answers**

D1 — **git merge** integrates changes by creating a new "merge commit" that combines the histories of two branches. **git rebase** rewrites history by moving the entire feature branch's commits onto the tip of the target branch, creating a linear history.
You should avoid rebasing commits that have already been pushed to a shared, public repository, as rewriting shared history forces collaborators to perform complex recovery steps.

D2 — **TCP (Transmission Control Protocol)** is a connection-oriented protocol that guarantees reliable, ordered, and error-checked delivery of a stream of bytes. It uses a three-way handshake. **UDP (User Datagram Protocol)** is a connectionless protocol that sends packets without guaranteeing delivery, order, or error checking; it is faster but less reliable.
Protocols using TCP: HTTP, FTP, SSH.
Protocols using UDP: DNS, NTP, VoIP.

D3 — A race condition occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data.
**Example:** Two threads simultaneously read a bank account balance ($1000). Both threads calculate a withdrawal of $100. Both threads write back the new balance ($900). The correct final balance should be $800, but because the reads happened before the writes, one withdrawal was effectively lost.

D4 — **Symmetric Encryption** uses a single, shared secret key for both encryption and decryption (e.g., AES). **Asymmetric Encryption** uses a pair of keys: a public key (for encryption, shared widely) and a private key (for decryption, kept secret).
**TLS Usage:** Asymmetric encryption is used during the initial handshake to securely exchange a temporary symmetric session key. Once the symmetric key is established, the bulk data transfer is encrypted using the much faster symmetric algorithm.

D5 — A container image layer is a read-only, immutable filesystem layer representing the changes made at a specific stage of the build process (e.g., installing packages, copying files). Layer caching allows the container runtime to reuse previously built layers if the instructions in the Dockerfile haven't changed, drastically speeding up subsequent builds.
**Best Practice:** Place instructions that change infrequently (like installing base OS dependencies) near the top of the Dockerfile, and place instructions that change frequently (like copying application code) near the bottom to maximize cache hits.

D6 — 1. **Check Application Logs:** Look for specific exceptions, database connection timeouts, or high error rates (the root cause).
2. **Check Resource Utilization:** Monitor CPU/Memory usage on the application pods. High saturation can cause throttling or timeouts leading to 503s.
3. **Check Dependencies/Downstream Services:** Verify if the API relies on other services (DB, cache) and if those dependencies are healthy and responsive.
4. **Check Load Balancer/Ingress Metrics:** Verify if the load balancer is correctly routing traffic and if the ingress controller itself is healthy and not overloaded.

D7 — The **CAP Theorem** states that a distributed data store can only provide two out of three guarantees simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest write), and **Partition Tolerance** (the system continues to operate despite network failures between nodes).
**CP Example:** Traditional relational databases (e.g., PostgreSQL cluster). If a network partition occurs, the system sacrifices availability to ensure that the nodes that remain operational maintain strict data consistency.
**AP Example:** Cassandra or DynamoDB. If a network partition occurs, the system remains available to accept reads/writes on both sides of the partition, accepting that data might temporarily diverge (eventual consistency).

D8 — **Vertical Scaling** (Scaling Up) involves increasing the resources (CPU, RAM) of an existing machine or instance. **Horizontal Scaling** (Scaling Out) involves adding more machines or instances to distribute the load.
Architectural patterns enabling horizontal scaling include: **Stateless Services** (where any instance can handle any request), **Load Balancing** (distributing traffic across instances), and **Sharding/Partitioning** (dividing the data set across multiple database instances).

D9 — An environment variable is a dynamic named value that can affect the way running processes behave on a computer.
On Linux, to set a variable that persists across shell sessions, you must add the export command (e.g., `export MY_VAR="value"`) to your shell's startup file, such as `~/.bashrc` or `~/.zshrc`, and then run `source ~/.bashrc`.

D10 — **JSON (JavaScript Object Notation)** is a lightweight data-interchange format using key-value pairs and arrays. **YAML (YAML Ain't Markup Language)** is a human-readable data serialization standard that uses indentation to denote structure.
**JSON Advantage:** Universally supported by nearly all programming languages and is excellent for machine parsing.
**YAML Advantage:** Highly readable and concise, making it ideal for configuration files (like Kubernetes manifests).

D11 — A REST (Representational State Transfer) API is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources.
*   **GET:** Retrieves a representation of a resource (Read). Should be idempotent and safe.
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource (Create).
*   **PUT:** Replaces an entire resource at a known URI (Update/Replace). Should be idempotent.
*   **DELETE:** Removes the specified resource (Delete). Should be idempotent.

D12 — Version pinning is the practice of explicitly specifying the exact version of a dependency (e.g., `library@1.2.3` instead of `library@^1.2.0`) in a project's manifest file. It is crucial for reproducible builds because it guarantees that the build environment will use the exact same code dependencies every time, preventing unexpected runtime failures caused by upstream library changes.

D13 — **Compiled Language:** Source code is translated directly into machine code (binary) by a compiler *before* execution. Examples: C++, Go, Rust.
**Interpreted Language:** Source code is read and executed line-by-line at runtime by an interpreter. Examples: Python, JavaScript.

D14 — A **Reverse Proxy** sits in front of one or more web servers and forwards client requests to them. It acts as an intermediary, hiding the backend structure from the client. A **Forward Proxy** sits in front of a client and forwards requests on behalf of the client to the internet.
**Reverse Proxy Servers:**
1. **NGINX:** Used for load balancing, SSL termination, and caching.
2. **HAProxy:** Specialized for high-performance TCP/HTTP load balancing.
**Use Case (NGINX):** Serving as the entry point for a microservices architecture, routing `/api/users` to the User Service and `/api/orders` to the Order Service.

D15 — A deadlock is a situation where two or more competing actions are each waiting for the other to finish, resulting in a permanent standstill.
The four Coffman conditions required for a deadlock are:
1. **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2. **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3. **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily.
4. **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

D16 — **Eventual Consistency** is a consistency model where, if no new updates are made to a given data item, all reads will eventually return the last updated value, but there is no guarantee about *when* that convergence will happen.
Cassandra handles read-after-write consistency using **Quorum Reads/Writes**. A write operation must succeed on $W$ replicas, and a read operation must query $R$ replicas. If $W + R > N$ (where $N$ is the replication factor), strong consistency is achieved.
**Tunable Consistency Levels:** `ONE` (fastest, least consistent), `QUORUM` (majority consensus), `ALL` (slowest, strongest consistency).

D17 — **mTLS (Mutual TLS)** requires *both* the client and the server to authenticate each other using digital certificates during the TLS handshake.
**Handshake Process:**
1. Client initiates connection and sends its certificate.
2. Server verifies the client's certificate against its trusted CA list.
3. Server sends its certificate to the client.
4. Client verifies the server's certificate against its trusted CA list.
5. If both validations pass, a symmetric session key is established.
**Use Case:** Service-to-service communication in a zero-trust microservices mesh (e.g., using Istio or Linkerd) to ensure only authorized services can communicate.

D18 — A hash table maps keys to values using a hash function. The hash function converts the key into an index (bucket) in an array.
**Collision Resolution:**
1. **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hash to that index.
2. **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing).
**Time Complexity:**
*   Average Case (Good Hash Function): Insertion, Lookup, Deletion $\rightarrow O(1)$.
*   Worst Case (All keys hash to the same bucket): Insertion, Lookup, Deletion $\rightarrow O(N)$.

D19 — The Circuit Breaker pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing microservice), thereby preventing resource exhaustion and cascading failures.
**States:**
1. **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the breaker trips to Open.
2. **Open:** Requests are immediately rejected without attempting the call, failing fast. After a timeout, the breaker moves to Half-Open.
3. **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker returns to Closed; if they fail, it returns to Open.
**Relation to Retry/Backoff:** The circuit breaker acts as a high-level gatekeeper. Retry policies and exponential backoff are used *within* the Closed state or during the Half-Open state to manage transient failures gracefully, but the circuit breaker prevents the system from hammering a known-down dependency.

D20 — **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data record *before* the transaction reads or modifies it, preventing other transactions from accessing it until the lock is released. (Example: `SELECT * FROM accounts WHERE id=1 FOR UPDATE;`).
**Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read (often using a version number or timestamp). If the version has changed, the transaction fails and must be retried.
**Choice:** Choose **Pessimistic** for high-contention data (e.g., inventory decrementing). Choose **Optimistic** for low-contention data (e.g., user profile updates).
