## OpenTofu / Terraform (20 questions)

**T1** — Easy: What is the difference between tofu plan and tofu apply?
T1: `tofu plan` calculates the necessary changes (additions, modifications, deletions) required to transition the current infrastructure state to the desired state defined in the configuration files, displaying these changes without executing them. `tofu apply` executes the changes detailed in the plan, making the actual modifications to the cloud infrastructure.

**T2** — Easy: What is state in OpenTofu, and why is remote state important?
T2: State is a file that maps the real-world infrastructure resources managed by OpenTofu to the configuration code. It tracks the attributes, IDs, and current status of every resource. Remote state is crucial because it centralizes this state file, allowing multiple team members or CI/CD pipelines to safely collaborate on the same infrastructure without overwriting each other's work, and it enables state locking to prevent concurrent modifications.

**T3** — Medium: Explain the difference between count and for_each. When is for_each preferred?
T3: `count` creates a list of identical instances based on an integer value. It is best for simple, homogenous replication (e.g., 3 identical VMs). `for_each` creates instances based on a map or a set of strings/objects, allowing each instance to be uniquely identified by a key. `for_each` is preferred when instances need unique identifiers or when the configuration logic depends on the specific key/value of the instance (e.g., creating a load balancer target group for each specific service name).

**T4** — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
T4: OpenTofu detects this drift during the `tofu plan` phase. It compares the current state recorded in the state file against the actual configuration retrieved from the cloud provider API. If a discrepancy is found, OpenTofu flags the resource as "drifted" and proposes a change to reconcile the state with the configuration, often suggesting reverting the manual change or updating the configuration to match the manual change.

**T5** — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
T5:
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-0abcdef1234567890"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

**T6** — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
T6: An **output value** is a value explicitly defined and exported by a module or resource, which can be consumed by other modules *within the same configuration*. A `terraform_remote_state` **data source** is used to read the state file of an *entirely separate* infrastructure deployment (often another root module or workspace). The recommended alternative for sharing specific, non-state-dependent data is to use **module outputs** combined with passing those outputs as input variables to the consuming module. This keeps dependencies explicit and avoids coupling modules to the state file structure.

**T7** — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
T7: The failure occurs because OpenTofu's dependency graph executes provisioners *before* the resource output is fully available or populated, especially if the provisioner runs asynchronously or relies on a remote command that hasn't completed its output capture. The fix is to use an **explicit dependency** via `depends_on`. The resource that consumes the kubeconfig must explicitly list the `null_resource` (or the resource generating the output) in its `depends_on` block, forcing OpenTofu to wait until the provisioner has successfully completed and populated the output before proceeding.

**T8** — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
T8: `tofu import` allows you to bring existing, manually provisioned infrastructure resources under OpenTofu management by mapping the resource ID from the cloud provider to a resource block in the configuration. Limitations include the need to manually write the configuration block *after* the import, and the fact that it only imports the current state, not the history or configuration logic. The import block (1.5+) improves this by allowing the configuration and the import ID to be defined in a single block, automating the state population process and making the configuration more self-contained.

**T9** — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
T9: A variable is a placeholder used to parameterize configuration, allowing the same code to be reused with different values. An **input variable** accepts values from the user or environment during `tofu apply` (e.g., `var.instance_type`). An **output** is a value exported by a resource or module that is made available to other parts of the configuration or to the user after deployment (e.g., `output.public_ip`).

**T10** — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
T10: A provider is a plugin that enables OpenTofu to interact with a specific API (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without `tofu init`, OpenTofu will fail because it has not downloaded or initialized the necessary provider plugins defined in the configuration. `tofu init` downloads the required providers and sets up the backend configuration.

**T11** — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
T11: The `.terraform.lock.hcl` file records the exact versions and checksums of every provider and module dependency used in the configuration. It should be committed to version control to ensure deterministic builds. This guarantees that every developer and every CI/CD pipeline uses the exact same, tested versions of dependencies, preventing unexpected behavior caused by upstream provider updates.

**T12** — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
T12: `tofu destroy` tears down all infrastructure resources managed by the current state file. To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web["web1"]`).

**T13** — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
T13: A data source is a mechanism that allows OpenTofu to fetch information about existing infrastructure or external data that is *not* managed by the current configuration. Example: Using a `aws_ami` data source to look up the latest Amazon Machine Image ID for a specific region. You use it instead of a managed resource when you need to reference an existing resource (e.g., an existing VPC ID) without OpenTofu being responsible for creating or managing it.

**T14** — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
T14: **Variables** are inputs defined externally (via CLI, environment, or `.tfvars`) and are intended to be configurable by the user. **Locals** are internal, computed values defined within a configuration file that derive from inputs or other locals. You should use locals when you need to perform complex transformations, calculations, or create reusable, derived values (like constructing a complex map or calculating a subnet CIDR block) based on the input variables, without exposing that derived value as a configurable input.

**T15** — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
T15: The lifecycle block controls how OpenTofu manages the resource during updates and destruction.
*   `create_before_destroy`: Ensures a new resource is created *before* the old one is destroyed. Use case: Blue/Green deployments where service interruption must be avoided during replacement.
*   `prevent_destroy`: Prevents the resource from being deleted via `tofu destroy`. Use case: Critical infrastructure components (e.g., production databases) that should never be accidentally removed.
*   `ignore_changes`: Tells OpenTofu to ignore specific attributes that might be manually changed outside of OpenTofu. Use case: When an external monitoring system updates a tag or metadata field that OpenTofu should not attempt to manage or revert.

**T16** — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
T16: A `moved` block is a directive used during configuration refactoring. It explicitly tells OpenTofu how to map the old resource address to the new resource address. When you rename a resource or move it between modules, the `moved` block ensures that OpenTofu understands the relationship, allowing it to safely update the state file by changing the resource's address without performing a destructive replacement (i.e., without destroying and recreating the underlying cloud resource).

**T17** — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
T17: OpenTofu builds a Directed Acyclic Graph (DAG) based on resource references. **Implicit dependencies** are automatically inferred when one resource references an attribute of another (e.g., `aws_instance.a.id` used in `aws_security_group.b`). **Explicit dependencies** are manually declared using `depends_on`. Implicit dependencies allow OpenTofu to maximize parallelism by running independent resources concurrently. Using `depends_on` forces sequential execution, which reduces parallelism and increases plan time. It should be used sparingly, only when implicit dependencies are insufficient (e.g., when a resource needs to wait for a side effect of another resource, not just its output).

**T18** — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
T18:
1.  **Modularization:** Break large configurations into smaller, focused modules. *Tradeoff:* Increases complexity in managing module dependencies and state references.
2.  **Targeted Operations:** Use `tofu plan -target=...` to only plan changes for specific components. *Tradeoff:* Reduces safety; if the target is incorrect, you might miss necessary changes elsewhere.
3.  **State Splitting/Workspaces:** Separate large infrastructure components (e.g., networking vs. compute) into different state files/workspaces. *Tradeoff:* Increases operational overhead; cross-component dependencies become harder to manage.
4.  **Provider Optimization/Caching:** Ensure providers are configured efficiently and leverage local/remote caching mechanisms. *Tradeoff:* Requires careful configuration of provider settings; may not solve deep dependency bottlenecks.

**T19** — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
T19: State locking ensures that only one operation (plan or apply) can modify the state file at any given time, preventing race conditions. When a lock is acquired (usually via the backend, e.g., DynamoDB), subsequent operations wait. If a lock is not released (e.g., a crash), the state remains locked indefinitely. To manually break a lock, you use the backend-specific unlock command (e.g., `terraform force-unlock`). The risk is that if the lock is broken while another process is actively modifying the state, the state file can become corrupted, leading to infrastructure drift or catastrophic failure on the next run.

**T20** — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
T20:
1.  **Configure Remote Backend:** Update the `backend` block in the configuration to point to the S3 bucket and DynamoDB table.
2.  **Initialize with Migration:** Run `tofu init -migrate`. OpenTofu will prompt you to confirm the migration. It reads the local state, uploads it to S3, and creates the necessary lock mechanism in DynamoDB.
3.  **Verify:** Run `tofu plan`. If successful, the plan should show "No changes. Your infrastructure matches the configuration." This confirms that the remote state is correctly loaded and synchronized with the configuration.
4.  **Cleanup:** Once verified, the local state file can be safely deleted.

## Ansible (20 questions)

**A1** — Easy: What is the difference between an Ansible playbook, a role, and a task?
A1: A **Playbook** is a YAML file that defines a set of plays, which dictate the overall execution flow, targeting specific hosts or groups. A **Role** is a standardized, reusable structure (a directory hierarchy) that encapsulates related tasks, handlers, variables, and templates for a specific function (e.g., `webserver`). A **Task** is a single, atomic unit of work within a play or role, defining a specific action to be performed (e.g., "install nginx").

**A2** — Easy: What is ansible_facts and how do you access the OS family of a target host?
A2: `ansible_facts` is a dictionary containing gathered information about the target host (OS version, memory, network interfaces, etc.), collected by the `setup` module. To access the OS family, you would use `ansible_facts['os_family']`.

**A3** — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
A3:
*   **`command`:** Executes a command directly. It does not process shell features (like pipes `|` or redirection `>`). Use this for simple, non-shell-dependent commands.
*   **`shell`:** Executes a command through the host's shell (e.g., `/bin/sh`). It supports shell features. Use this when piping, redirection, or environment variables are required.
*   **`raw`:** Executes a command directly on the remote host without invoking the shell interpreter. Use this when you need maximum control over the execution environment and want to avoid shell interpretation overhead.

**A4** — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
A4: Idempotency means that running the same task multiple times will result in the same system state without causing unintended side effects after the first successful run. Ansible achieves this by using modules that check the current state before making changes.
*   **Idempotent Example:** `ansible.builtin.package` (e.g., `name: httpd`, `state: present`). If httpd is installed, Ansible does nothing; if not, it installs it.
*   **Non-Idempotent Example:** `ansible.builtin.command: echo "Hello" >> /tmp/log.txt`. Running this repeatedly appends a new line every time, changing the state each time.

**A5** — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.
A5:
```yaml
- name: Install htop based on OS family
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```

**A6** — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
A6: Ansible resolves variables based on a strict precedence order, where later definitions override earlier ones. The general order (highest priority listed last) is:
1.  Role Defaults (`defaults/main.yml`)
2.  Inventory Variables (Group/Host Vars)
3.  Extra Variables (`-e` or `extra_vars`)
4.  Playbook Variables (defined in the play itself)
5.  Facts (`ansible_facts`)

**A7** — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
A7: This requires using the `serial` keyword in the play definition, targeting a specific group, and potentially using `wait_for` if the deployment requires external readiness checks.
```yaml
- name: Deploy RKE2 Agents
  hosts: rke2_nodes
  serial: 3  # Only 3 hosts run at a time
  tasks:
    - name: Wait for initial network readiness (optional)
      ansible.builtin.wait_for:
        port: 80
        host: "{{ inventory_hostname }}"
        timeout: 30
    - name: Install RKE2 agent
      ansible.builtin.shell: |
        # RKE2 installation commands here
        ...
```

**A8** — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
A8: `ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible files. To encrypt a single variable without encrypting the entire file, you must use the `ansible-vault encrypt` command specifically on the variable definition line or use a dedicated encrypted variable file that is only loaded for that specific variable. For instance, you can use the `ansible.builtin.include_vars` module with a vaulted file, or define the variable in a separate, vaulted file that is only referenced where needed.

**A9** — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
A9: An inventory file defines the hosts (servers) that Ansible will manage and groups them logically. A **static inventory** is a manually maintained file (INI or YAML format) listing hostnames or IP addresses. A **dynamic inventory** is a script or plugin that queries an external source (like AWS, Azure, or a CMDB) in real-time to generate the host list and group membership before the playbook runs.

**A10** — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?
A10:
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

**A11** — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
A11: A handler is a special task that is only executed when explicitly notified by another task. Unlike a regular task, handlers are not run sequentially during the main playbook flow; they are queued and run only once at the end of the play, even if multiple tasks notify the same handler. You trigger a handler using the `notify` keyword in a task.

**A12** — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
A12: The `ansible.cfg` file configures the behavior of Ansible itself, overriding default settings. Common settings include:
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Defines the default SSH user to connect as.
3.  `host_key_checking`: Controls whether Ansible verifies the host keys (often set to `False` in testing environments).

**A13** — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
A13: The `register` keyword captures the output of a task (including return codes, stdout, and stderr) and stores it in a variable. You use this registered variable in a subsequent task by referencing it using dot notation (e.g., `{{ result.stdout }}`).
Example: `register: check_disk` followed by `debug: var: "{{ check_disk.stdout }}"`.

**A14** — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
A14:
*   **`import_tasks`:** Reads the tasks file as a static file *before* the play starts. It is used for including static, non-conditional task lists.
*   **`include_tasks`:** Reads the tasks file dynamically *during* the play execution. It is used when you need to conditionally include tasks based on runtime variables (e.g., `when:` conditions).
*   **Conditional Evaluation:** `include_tasks` allows the `when` condition to be evaluated at runtime, whereas `import_tasks` evaluates conditions statically during parsing.

**A15** — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
A15: Ansible Galaxy is a community repository where users share reusable Ansible roles and collections. You use a `requirements.yml` file to declare dependencies. The file lists the required roles/collections and their sources (e.g., GitHub, Ansible Galaxy). You then run `ansible-galaxy install -r requirements.yml` to download and install them into your local Ansible environment.

**A16** — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
A16: Connection plugins define how Ansible establishes and maintains a connection to the target host.
*   **`ssh`:** The default. Used to connect to remote Linux/Unix hosts via SSH.
*   **`local`:** Used when the target host is the Ansible control machine itself.
*   **`network_cli`:** Used to manage network devices (routers, switches) via CLI protocols (like Telnet or SSH CLI), often requiring specialized modules.

**A17** — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
A17:
*   **`delegate_to`:** Allows a task to be executed on a host *other* than the one specified in the `hosts:` line of the play. You can delegate to a specific remote host, a group, or `localhost`.
*   **`run_once`:** When combined with `delegate_to: localhost`, it ensures that the task runs only one time across the entire execution, regardless of how many hosts are targeted.
*   **Example:** Gathering the IP addresses of all web servers (`register: web_ips`) and then using `delegate_to: localhost` and `run_once: true` to write a summary file to the control node:
    ```yaml
    - name: Write summary to control node
      ansible.builtin.copy:
        content: "Web IPs: {{ web_ips.results | map(attribute='ansible_facts.ansible_default_ipv4.address') | list }}"
        dest: /tmp/summary.txt
      delegate_to: localhost
      run_once: true
    ```

**A18** — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
A18:
1.  **Increase Forks:** Increase the `forks` setting in `ansible.cfg` (e.g., from 5 to 50). *Tradeoff:* Increases load on the control node and the network; too high can overwhelm the target hosts.
2.  **Pipelining:** Use pipelining (running multiple tasks concurrently on the same host). *Tradeoff:* Can increase complexity and might not be suitable for tasks that require sequential state changes.
3.  **Fact Caching:** Use the `fact_caching` mechanism to store gathered facts locally or remotely. *Tradeoff:* Requires persistent storage; adds initial setup overhead but drastically speeds up subsequent runs.
4.  **Mitogen/Parallel Execution:** Use tools like Mitogen or Ansible Tower/AWX to manage parallel job execution across multiple control nodes. *Tradeoff:* Significant infrastructure overhead (requires managing a cluster of control nodes).

**A19** — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
A19: Jinja2 is the templating engine used by Ansible.
*   **`{{ variable }}`:** Used for *printing* the value of a variable (output).
*   **`{% statement %}`:** Used for *logic* control flow (loops, conditionals, assignments).
*   **`{# comment #}`:** Used for comments that are completely stripped from the final rendered output.
**Snippet:**
```nginx
upstream backend_servers {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; # Health Check: {{ server.name }}
{% endfor %}
}
```

**A20** — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
A20:
1.  **Serial Batches:** Use `serial: 4` (or similar) to ensure only a small batch of servers (e.g., 4 out of 20) is updated at any time.
2.  **Pre-Task (LB Registration):** Before updating a batch, use a task to register the current batch of servers with the load balancer (e.g., using the `uri` module to call the LB API).
3.  **Deployment Task:** Run the application update tasks.
4.  **Health Check:** After deployment, use `ansible.builtin.uri` or `wait_for` to confirm the new application version is responding correctly on the updated servers.
5.  **Post-Task (LB Health Check):** If the health check passes, the batch is considered healthy.
6.  **Rollback Strategy:** Wrap the deployment and health check logic in a `block/rescue` structure. If the health check fails (the `rescue` block is triggered), the `rescue` block executes a task to immediately revert the application to the previous stable version on that batch of servers, and then potentially deregister them from the LB.
