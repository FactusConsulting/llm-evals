### Go (20 questions)

---

**G1** — Arrays in Go are fixed-size, contiguous memory allocations of a single type, declared with a length (e.g., `[3]int`). Slices are dynamically-sized views into arrays, declared without a length (e.g., `[]int`). When you append to a slice that has reached its capacity, Go allocates a new underlying array (typically doubling the capacity), copies the existing elements, and returns a new slice pointing to the new array.

---

**G2** — `var x int` declares a variable `x` of type `int` with its zero value (`0`). `x := 0` declares and initializes `x` with type inference. You **cannot** use `:=` outside a function (e.g., at package level) or if the variable was already declared in the same scope.

---

**G3** — A goroutine is a lightweight, user-space thread managed by the Go runtime. Unlike OS threads, goroutines are multiplexed onto a smaller number of OS threads (M:N threading) and have minimal overhead (a few KB vs. ~1-2MB for OS threads). The Go scheduler (GMP model) uses **G** (goroutines), **M** (OS threads), and **P** (logical processors) to efficiently schedule goroutines across CPU cores, handling blocking syscalls and workload balancing.

---

**G4** — Channels are typed conduits for communication between goroutines. An **unbuffered channel** blocks the sender until a receiver is ready (synchronous). A **buffered channel** (e.g., `make(chan int, 3)`) allows the sender to enqueue up to `N` values without blocking. Sending to a full buffered channel blocks until a receiver frees space. Receiving from an empty channel (buffered or unbuffered) blocks until a value is available.

---
**G5** — The `context` package manages cancellation, timeouts, and request-scoped values across goroutines. Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
resp, err := http.DefaultClient.Do(req)
if err != nil {
    if ctx.Err() == context.DeadlineExceeded {
        fmt.Println("Request timed out")
    }
    return err
}
defer resp.Body.Close()
```

---
**G6** — Go interfaces are **implicitly satisfied**: a type implements an interface if it has all the interface’s methods (duck typing). This differs from Java/C#, where types explicitly declare interface implementations. The empty interface `interface{}` (or `any` in Go 1.18+) can hold any type, making it powerful for generic code (e.g., `fmt.Println`). However, it’s dangerous because it bypasses type safety, requiring type assertions or reflection to use the underlying value.

---
**G7** — Go’s memory model guarantees that **happens-before** relationships (e.g., via channel ops or `sync` primitives) ensure visibility across goroutines. The example is unsafe because there’s no happens-before edge between the write to `data` and the read in the main goroutine. The compiler or CPU may reorder or cache `ready` and `data`, leading to stale reads or infinite loops.
**Fixes**:
1. Use a channel:
   ```go
   ch := make(chan string)
   go func() { ch <- "hello" }()
   fmt.Println(<-ch)
   ```
2. Use `sync.Mutex`:
   ```go
   var mu sync.Mutex
   var data string
   go func() {
       mu.Lock()
       data = "hello"
       mu.Unlock()
   }()
   mu.Lock()
   fmt.Println(data)
   mu.Unlock()
   ```

---
**G8** —
- `sync.Mutex`: Provides exclusive access (only one goroutine can hold the lock).
- `sync.RWMutex`: Allows multiple readers (`RLock`) or one writer (`Lock`). Use when reads vastly outnumber writes.
- `sync.Map`: A concurrent map optimized for read-heavy, write-light workloads with disjoint keys. It uses fine-grained locking internally. For most cases, a `map` + `RWMutex` is simpler and faster unless you have extreme contention or disjoint access patterns.
**Trade-offs**: `sync.Map` has higher overhead for small maps or sequential access. Benchmark for your use case.

---
**G9** — Go modules are the dependency management system (introduced in Go 1.11). `go.mod` defines the module’s path, Go version, and dependencies. `go.sum` records cryptographic hashes of dependencies for reproducibility. `go mod tidy` adds missing dependencies and removes unused ones, updating `go.mod` and `go.sum`.
**Minimum Version Selection (MVS)**: When resolving dependencies, Go picks the **highest version** that satisfies all constraints (from `go.mod` and indirect dependencies) and is **>= the minimum version** required by any other dependency. This avoids "dependency hell" by preferring newer, compatible versions.

---
**G10** — `defer` schedules a function call to run when the surrounding function returns. Multiple defers execute in **LIFO** (last-in-first-out) order. A common gotcha in loops:
```go
for i := 0; i < 3; i++ {
    defer fmt.Println(i) // Prints 2, 1, 0 (not 0, 1, 2)
}
```
**Fix**: Pass `i` as an argument to the deferred function:
```go
for i := 0; i < 3; i++ {
    defer func(i int) { fmt.Println(i) }(i) // Prints 0, 1, 2
}
```

---
**G11** — A pointer holds the memory address of a value. The zero value of a pointer is `nil`. Create a pointer to a struct literal:
```go
p := &struct{ X, Y int }{1, 2} // p is *struct{ X, Y int }
```

---
**G12** — `init()` is a special function that runs **automatically** when a package is initialized, before `main()`. A package can have **multiple `init()` functions**, which execute in the order they are declared (file order). Initialization order: variables → `init()` functions → `main()`.

---
**G13** —
- `new(T)`: Allocates zeroed memory for type `T` and returns `*T`. Works for **any type** (including `int`, `struct`).
- `make(T, args...)`: Allocates and initializes **slices, maps, and channels** (only these types). For example:
  ```go
  make([]int, 0, 10) // slice with len=0, cap=10
  make(map[string]int)
  make(chan int, 5)
  ```

---
**G14** — Errors are values of type `error` (an interface with `Error() string`). Idiomatic pattern:
```go
resp, err := http.Get(url)
if err != nil {
    log.Fatal(err)
}
```
- `errors.Is(err, targetErr)`: Checks if `err` or any error in its chain matches `targetErr` (using `==` or `Is` method).
- `errors.As(err, &target)`: Checks if `err` or any error in its chain can be assigned to `target` (e.g., extracting a custom error type).
- `==` only compares the exact error value (not wrapped errors).

---
**G15** — Built-in composite types:
- `map[K]V`: Zero value is `nil` (not usable; must initialize with `make`).
- `[]T`: Zero value is `nil` (len=0, cap=0).
- `chan T`: Zero value is `nil` (blocking sends/receives).
- `struct{...}`: Zero value has all fields set to their zero values.

---
**G16** — A race condition occurs when multiple goroutines access shared data concurrently without synchronization, leading to undefined behavior. The `-race` flag instruments your code to detect data races at runtime (using ThreadSanitizer).
**Example race**:
```go
var counter int
go func() { counter++ }()
go func() { counter++ }()
```
**Fix with `sync.Mutex`**:
```go
var mu sync.Mutex
var counter int
go func() {
    mu.Lock()
    counter++
    mu.Unlock()
}()
```
**Fix with channel**:
```go
ch := make(chan int, 1)
ch <- 1
go func() { ch <- counter + 1 }()
counter = <-ch
```

---
**G17** — `select` allows a goroutine to wait on multiple channel operations. Unlike `switch`, it randomly picks a ready case if multiple are ready. Example timeout:
```go
select {
case msg := <-ch:
    fmt.Println(msg)
case <-time.After(1 * time.Second):
    fmt.Println("Timeout")
}
```

---
**G18** — Escape analysis determines whether a variable can be allocated on the **stack** (faster, no GC overhead) or must escape to the **heap** (e.g., if it’s referenced after the function returns or passed to another goroutine). The compiler decides based on:
- Pointers to the variable escaping the function.
- Variable size (large structs may heap-allocate).
- Dynamic types (e.g., slices/maps with unknown size at compile time).
**Inspect decisions**: Run with `go build -gcflags="-m"` to see escape analysis logs.
**Why it matters**: Stack allocation reduces GC pressure and improves performance.

---
**G19** — The `reflect` package provides runtime type introspection. `reflect.Type` represents a type (e.g., `reflect.TypeOf(x)`), while `reflect.Value` holds a value (e.g., `reflect.ValueOf(x)`). You can inspect types, modify values (if `CanSet` is true), and call methods dynamically.
**Performance costs**: Reflection is **slow** (100x+ slower than static code) and unsafe (no compile-time checks). Use sparingly.
**Justified when**: Writing generic libraries (e.g., JSON marshaling, ORMs) or working with unknown types (e.g., plugins). Prefer **code generation** (e.g., `go generate`) for performance-critical paths.

---
**G20** — `go:embed` (Go 1.16+) embeds files/directories into the binary at compile time. Works for:
- Single files: `//go:embed file.txt` → `var content string`
- Directories: `//go:embed dir/*` → `var content embed.FS`
- File systems: `embed.FS` implements `io/fs.FS` for nested access.
**Limitations**:
- Only works with static files (not dynamic paths).
- Embedded files are read-only.
- Large files increase binary size.
**Interaction with `io/fs.FS`**: `embed.FS` is a read-only `io/fs.FS`, so you can use standard `fs` functions (e.g., `fs.WalkDir`).

### Rust (20 questions)

---
**R1** — Ownership is Rust’s system for managing memory safely without a GC. The three rules:
1. Each value has a single **owner**.
2. When the owner goes out of scope, the value is **dropped** (memory freed).
3. Ownership can be **moved** (not copied) to another variable.

---
**R2** —
- `String`: A growable, heap-allocated UTF-8 string (owned).
- `&str`: An immutable **slice** (view) into a string (borrowed). Prefer `&str` for function parameters to accept both `String` and string literals. Use `String` when you need to own or modify the string.

---
**R3** — Borrowing allows references to data without taking ownership. The borrow checker enforces:
- **Shared references (`&T`)**: Multiple immutable references allowed, but no mutable references can exist simultaneously.
- **Mutable references (`&mut T`)**: Only one mutable reference allowed, and no shared references can exist simultaneously.
- References must always be **valid** (no dangling pointers).

---
**R4** —
- `Result<T, E>`: Represents success (`Ok(T)`) or failure (`Err(E)`).
- `Option<T>`: Represents some value (`Some(T)`) or none (`None`).
- `?` operator: Propagates errors/none values up the call stack (early return).
**Example**:
```rust
use std::fs;
fn read_file(path: &str) -> Result<String, std::io::Error> {
    let contents = fs::read_to_string(path)?;
    Ok(contents)
}
```

---
**R5** —
- `Box<T>`: A heap-allocated pointer to `T` (single ownership).
- `Rc<T>`: Reference-counted pointer for **shared ownership** (single-threaded).
- `Arc<T>`: Atomic reference-counted pointer for **shared ownership across threads**.
**Use cases**:
- `Box`: Large data, recursive types (e.g., trees), or trait objects.
- `Rc`: Shared data in single-threaded contexts (e.g., graphs).
- `Arc`: Shared data in multi-threaded contexts.

---
**R6** — Traits are Rust’s interface-like abstractions for shared behavior. Unlike Go interfaces (implicit), Rust traits are **explicit** and can include default implementations. Key differences:
- **Trait objects (`dyn Trait`)**: Dynamic dispatch (runtime polymorphism) via pointers (`Box<dyn Trait>`, `&dyn Trait`). Requires the trait to be **object-safe** (no generic methods, `Self` types, etc.).
- **Generics with trait bounds (`T: Trait`)**: Static dispatch (compile-time monomorphization). More efficient but can cause code bloat.

---
**R7** — Lifetimes annotate how long references are valid. The example fails because the returned reference (`&str`) could outlive the input references (`x` or `y`). Fix by adding a lifetime parameter:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
The lifetime `'a` ensures the output lives at least as long as the inputs.

---
**R8** —
- `Send`: A type is `Send` if it can be **safely transferred across threads** (ownership moved).
- `Sync`: A type is `Sync` if it can be **safely shared across threads** (immutable references are `Send`).
- `Rc<T>` is **not `Send` or `Sync`** because its reference count is not thread-safe (non-atomic increments/decrements).
- `Arc<T>` uses atomic operations for reference counting, making it `Send` and `Sync`.

---
**R9** — Rust’s `async/await` is built on **state machines** and **Futures**. A `Future` is a pollable computation that resolves to a value. The `async` keyword desugars a function into a state machine implementing `Future`. The **executor** (e.g., Tokio) drives the Future to completion by polling it (e.g., `tokio::spawn`).
**Key differences from Go**:
- Rust Futures are **lazy** (do nothing until polled).
- Go goroutines are **eager** (start running immediately).
- Rust async uses **cooperative multitasking** (Futures yield control when awaiting), while Go uses **preemptive scheduling**.

---
**R10** — `unsafe` bypasses Rust’s safety checks. In `unsafe` blocks, you can:
1. Dereference raw pointers (`*const T`, `*mut T`).
2. Call `unsafe` functions (e.g., `std::mem::transmute`).
3. Access or modify mutable static variables.
4. Implement `unsafe` traits (e.g., `Send`, `Sync`).
**Justified when**: Interfacing with C, writing low-level systems code, or implementing safe abstractions (e.g., `Vec<T>` uses `unsafe` internally but exposes a safe API).

---
**R11** — Pattern matching in Rust uses `match` to destructure and handle values. `match` is **exhaustive** (must cover all possible cases). `if let` is a shorthand for single-pattern matches.
**Example**:
```rust
match some_option {
    Some(x) => println!("{}", x),
    None => println!("None"),
}
```
The compiler enforces exhaustiveness (e.g., missing `None` would cause an error).

---
**R12** —
- `Vec<T>`: A growable heap-allocated array. When capacity is exceeded, it reallocates (typically doubling capacity), copies elements, and frees the old memory.
- `[T; N]`: A fixed-size stack-allocated array. Size is part of the type (e.g., `[i32; 3]`).

---
**R13** — Rust enums are **algebraic data types** (ADTs) that can represent multiple variants, each with its own data. Unlike C enums (just integers), Rust enums can hold data:
```rust
enum Option<T> {
    Some(T),
    None,
}
```
`Option<T>` replaces `null` by explicitly handling absence of a value, avoiding null pointer errors.

---
**R14** — `impl` blocks define methods and associated functions for a type.
- `&self`: Immutable borrow (read-only).
- `&mut self`: Mutable borrow (can modify).
- `self`: Takes ownership (consumes the value).
**Associated functions** (e.g., `String::new()`) are called on the type itself, not an instance.

---
**R15** — The `#[derive]` macro automatically implements traits for a type. Common derived traits:
- `Debug`: Printable with `{:?}`.
- `Clone`: Creates a deep copy.
- `PartialEq`: Equality comparison (`==`).
- `Serialize`/`Deserialize`: For `serde` (JSON, etc.).
**Cannot derive** traits that require custom logic (e.g., `Add`, `Mul`) or have supertrait bounds not satisfied by the type.

---
**R16** — `Cow<'a, T>` (Clone-on-Write) is a smart pointer that either **borrows** (`&'a T`) or **owns** (`T`) data. It clones the data only when mutation is needed.
**Example**:
```rust
use std::borrow::Cow;
fn capitalize(s: &str) -> Cow<str> {
    if s.chars().all(|c| c.is_ascii_lowercase()) {
        Cow::Owned(s.to_uppercase())
    } else {
        Cow::Borrowed(s)
    }
}
```
Useful for avoiding allocations when the borrowed data doesn’t need modification.

---
**R17** — Rust’s module system organizes code into logical units. Key concepts:
- `mod`: Declares a module (maps to a file/directory).
- `use`: Brings paths into scope.
- `pub`: Makes items accessible outside the module.
**File system mapping**:
- `mod.rs` (Rust 2015) or `lib.rs`/`main.rs` (Rust 2018) defines the root module.
- Submodules are files/directories under the parent module’s directory.
**Rust 2018 edition**: Simplified paths (e.g., `use crate::foo` instead of `use foo`).

---
**R18** — `Pin<T>` ensures a value **cannot be moved in memory**, which is critical for **self-referential structs** (e.g., a struct containing a pointer to its own field). This is essential for `async/await` because the state machine for an async block may contain references to its own fields (e.g., local variables captured by the Future).
- **`Unpin`**: A marker trait for types that can be safely moved (most types implement `Unpin`).
- **Why it matters**: Without `Pin`, moving a Future could invalidate its internal references, leading to undefined behavior.

---
**R19** — Rust’s macro system allows metaprogramming:
- **Declarative macros (`macro_rules!`)**: Pattern-matching macros (like `println!`). Hygienic (scopes are isolated).
- **Procedural macros**: More powerful, written as functions. Types:
  - `derive`: Auto-implement traits (e.g., `#[derive(Debug)]`).
  - `attribute`: Transform items (e.g., `#[tokio::main]`).
  - `function-like`: Custom syntax (e.g., `sql!`).
**Hygiene rules**: Macros preserve lexical scopes (e.g., variables in a macro expansion refer to the macro’s scope, not the caller’s).

---
**R20** — Zero-cost abstractions in Rust provide high-level ergonomics without runtime overhead. Examples:
- **Iterators**: Compile to tight loops (same as hand-written `for` loops). Methods like `map`, `filter` are fused and optimized.
- **Generics (monomorphization)**: Compiles generic code into specialized versions for each type, avoiding runtime dispatch overhead.
- **Trait static dispatch**: Trait bounds (`T: Trait`) are resolved at compile time, inlining method calls.
**Result**: Rust achieves C-like performance while offering safety and expressiveness.
