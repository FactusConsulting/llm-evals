### **Application Architecture (20 questions)**

---

**AA1**
- **Monolith vs. Microservices**: A monolith is a single, self-contained application with tightly coupled components, while microservices break the application into loosely coupled, independently deployable services.
- **3 Problems Microservices Introduce**:
  1. **Distributed Complexity**: Network latency, retries, and partial failures (e.g., handling timeouts between services).
  2. **Operational Overhead**: Managing multiple services (deployment, monitoring, logging) is harder than a single monolith.
  3. **Data Consistency**: Distributed transactions require patterns like Saga or eventual consistency, which are harder to implement than ACID in a monolith.

---

**AA2**
- **Synchronous Communication**: The caller waits for a response (blocking). Example: REST/HTTP (e.g., a client calling an API and waiting for JSON).
- **Asynchronous Communication**: The caller sends a request and continues without waiting. Example: Kafka (publish-subscribe) or RabbitMQ (message queues).

---

**AA3**
- **API Gateway**: A reverse proxy that also provides request routing, rate limiting, authentication, and protocol translation (e.g., gRPC ↔ HTTP). Often includes request/response transformation.
- **Reverse Proxy**: Forwards requests to backend servers (e.g., Nginx, HAProxy) but lacks advanced features like request transformation or API-specific routing.
- **Can an API Gateway replace a reverse proxy?**
  - **Yes, but not entirely**: An API Gateway can act as a reverse proxy, but a reverse proxy alone cannot replace an API Gateway’s advanced features (e.g., JWT validation, request aggregation). Use both if you need load balancing (reverse proxy) + API management (gateway).

---

**AA4**
- **Saga Pattern**: Manages distributed transactions by breaking them into local transactions with compensating actions (rollbacks) if a step fails.
  - **Choreography-Based**: Services emit events (e.g., "OrderCreated") and react to them (e.g., "ReserveInventory"). No central coordinator.
    - *Use when*: Services are loosely coupled, and event-driven workflows are natural (e.g., e-commerce).
  - **Orchestration-Based**: A central orchestrator (e.g., a workflow engine) tells services what to do (e.g., "ReserveInventory → ChargePayment → ShipOrder").
    - *Use when*: Complex workflows require strict ordering or compensating logic (e.g., banking).
- **Trade-off**: Choreography is simpler but harder to debug; orchestration adds complexity but provides better control.

---

**AA5**
- **CQRS**: Separates reads (queries) and writes (commands) into different models. Reads use optimized data stores (e.g., Elasticsearch), writes use a transactional store (e.g., PostgreSQL).
- **Event Sourcing**: Stores state changes as an immutable sequence of events (e.g., "OrderCreated," "PaymentReceived"). The current state is derived by replaying events.
- **Why Pair Them?**
  - **Problem Solved**: Traditional CRUD struggles with auditability, temporal queries (e.g., "What was the order state at time X?"), and scaling reads/writes independently.
  - **Benefit**: Event Sourcing provides a natural audit log, and CQRS allows scaling reads (e.g., materialized views) without impacting writes.

---

**AA6**
- **Circuit Breaker Pattern**: Prevents cascading failures by "tripping" (failing fast) after a threshold of failures, giving the downstream service time to recover.
  - **States**:
    1. **Closed**: Normal operation (requests pass through).
    2. **Open**: Fails fast (returns errors immediately).
    3. **Half-Open**: Tests if the service has recovered (allows a few requests).
  - **vs. Retry with Backoff**: Retries assume transient failures; circuit breakers assume the service is *unavailable* and avoid hammering it. Use both: retry for transient errors (e.g., network blips), circuit breaker for prolonged outages.

---

**AA7**
| **Model**                     | **Cost** | **Security** | **Operational Complexity** | **Noisy-Neighbor Risk** | **Use Case**                     |
|-------------------------------|----------|--------------|----------------------------|--------------------------|----------------------------------|
| Shared DB, Shared Schema      | Low      | Low          | Low                        | High                     | Simple SaaS, low isolation needs |
| Shared DB, Separate Schema    | Medium   | Medium       | Medium                     | Medium                   | Multi-tenant with some isolation |
| Separate DB per Tenant        | High     | High         | High                       | Low                      | High-security, compliance needs  |

- **Trade-offs**:
  - **Shared Schema**: Cheapest but risk of data leakage (e.g., misconfigured tenant ID filters).
  - **Separate Schema**: Better isolation but harder to manage (schema migrations across tenants).
  - **Separate DB**: Best isolation but highest cost (provisioning, backups).

---

**AA8**
- **Eventual Consistency**: Guarantees that, if no new updates are made, all nodes will eventually reflect the same state (e.g., DNS, Kafka).
- **Strong Consistency**: All reads return the most recent write (e.g., PostgreSQL with `READ COMMITTED`).
- **Inventory System (No Overselling)**:
  - **Consistency Model**: Strong consistency (e.g., serializable isolation).
  - **Data Store**: SQL database (PostgreSQL) with row-level locking (`SELECT ... FOR UPDATE`).
  - **Patterns**:
    - **Pessimistic Locking**: Lock inventory rows during checkout.
    - **Optimistic Locking**: Use version numbers to detect conflicts.
    - **At Scale**: Shard by product ID + use distributed locks (e.g., Redis Redlock) or a dedicated inventory service with atomic operations.

---

**AA9**
- **Sidecar Proxy**: A proxy deployed alongside each service instance (e.g., Envoy in Istio) to handle cross-cutting concerns (mTLS, retries, metrics).
- **Envoy in Istio**:
  - **Data Plane**: Envoy sidecars handle traffic (L4/L7 routing, load balancing).
  - **Control Plane**: Istiod (Istio’s control plane) configures Envoy via xDS (e.g., routes, certificates).
- **mTLS vs. Application-Level TLS**:
  - **mTLS (Sidecar)**: Transparent to the app; managed by the service mesh. Solves *service-to-service* auth (no code changes).
  - **App-Level TLS**: Requires app code to handle certs/keys; harder to rotate or enforce uniformly.

---

**AA10**
- **Strangler Fig Pattern**: Incrementally replace a legacy system by routing traffic to new services while keeping the old system running.
- **Migration Strategy for .NET Framework → .NET 8 Microservices**:
  1. **Identify Seams**: Break the monolith into domains (e.g., Orders, Inventory).
  2. **API Gateway**: Route requests to new services (e.g., `/orders` → new .NET 8 service) or legacy (fallback).
  3. **Database**: Use the **Database View** or **Anti-Corruption Layer** to avoid coupling to the legacy schema.
  4. **Incremental Rollout**: Deploy new services behind a feature flag, then gradually shift traffic.
  5. **Decommission**: Once a domain is fully migrated, retire the legacy code.

---

**AA11**
- **12-Factor App**: Methodology for building cloud-native, scalable apps. Key factors:
  1. **Codebase**: One codebase per app (multiple deploys).
  2. **Dependencies**: Explicitly declare and isolate (e.g., `requirements.txt`, `package.json`).
  3. **Config**: Store config in environment variables (not code).
  4. **Backing Services**: Treat databases/queues as attached resources (e.g., `DATABASE_URL`).
  5. **Build, Release, Run**: Strict separation of stages (e.g., Docker images are built once, deployed many times).
  6. **Processes**: Run as stateless processes (no local storage).
  - **Why It Matters**: Enables portability (e.g., Docker/K8s), scalability, and CI/CD.

---

**AA12**
| **Aspect**            | **Event-Driven (Kafka)**               | **Request-Driven (REST/gRPC)**       |
|-----------------------|---------------------------------------|--------------------------------------|
| **Coupling**          | Loose (producers/consumers decoupled) | Tight (client knows server API)      |
| **Scalability**       | High (horizontal scaling of brokers)  | Limited by server capacity           |
| **Debugging**         | Hard (distributed traces, event logs) | Easier (request/response logs)       |
| **Ordering**          | Per-partition (Kafka)                 | Per-request (no inherent ordering)   |
| **Failure Handling**  | Retries + dead-letter queues          | Retries + circuit breakers           |
- **Choose Event-Driven**: For async workflows (e.g., order processing), high throughput, or fan-out (multiple consumers).
- **Choose Request-Driven**: For simple, synchronous interactions (e.g., user profile updates).

---

**AA13**
- **Load Balancer**: Distributes traffic across servers to improve availability and performance.
  - **Layer 4 (Transport)**: Operates at TCP/UDP level (e.g., HAProxy, NLB). Routes based on IP/port. *Use case*: High-performance, low-latency (e.g., gaming).
  - **Layer 7 (Application)**: Operates at HTTP/HTTPS level (e.g., Nginx, ALB). Routes based on URL, headers, cookies. *Use case*: Hosting multiple websites on one IP (SNI).

---

**AA14**
- **Message Queue**: Temporary storage for messages until consumed (e.g., RabbitMQ). Messages are *removed* after consumption.
- **Log-Based Broker (Kafka)**: Immutable, ordered log of events. Consumers read *offsets* and can replay.
- **When to Use**:
  - **Queue (RabbitMQ)**: Simple workflows, competing consumers (e.g., task queues).
  - **Kafka**: Event sourcing, stream processing, or replayability (e.g., analytics).

---

**AA15**
- **Container**: Lightweight, shares host OS kernel, isolated via namespaces/cgroups (e.g., Docker).
- **VM**: Full OS virtualization (e.g., KVM, VMware), higher overhead but stronger isolation.
- **Why Containers for Microservices**:
  - Faster startup, lower resource usage, and better portability (e.g., Kubernetes).

---

**AA16**
- **Stateless Service**: No local data; state is stored externally (e.g., Redis, DB). *Example*: API gateway.
- **Stateful Service**: Maintains local state (e.g., session data). *Example*: WebSocket server.
- **Why Stateless Scales Easier**: Any instance can handle any request (no affinity), enabling horizontal scaling.

---
**AA17**
- **ORM**: Maps objects to database tables (e.g., SQLAlchemy for Python, Entity Framework for .NET).
- **Trade-offs**:
  - **Pros**: Faster development, database-agnostic, reduces SQL injection risk.
  - **Cons**: Performance overhead (N+1 queries), limited control over complex queries, schema changes can be painful.

---
**AA18**
- **Bulkhead Pattern**: Isolates resources (e.g., thread pools, connection pools) to prevent one service from starving others.
  - **Example**: Separate thread pools for DB calls and external API calls. If the API is slow, DB threads remain available.
- **Implementation**:
  - **Thread Pools**: Dedicate pools per service.
  - **Deployment Groups**: Deploy critical services on separate nodes.

---
**AA19**
| **Aspect**            | **Operational Transformation (OT)**       | **CRDTs**                              |
|-----------------------|------------------------------------------|----------------------------------------|
| **Consistency**       | Strong (linearizable)                    | Eventual                               |
| **Latency**           | Higher (requires central authority)      | Lower (peer-to-peer)                   |
| **Complexity**        | High (transform functions for each op)   | Medium (predefined data types)         |
| **Offline Support**   | Limited (needs sync on reconnect)        | Native (merges automatically)          |
- **Choice for Offline Editing**: **CRDTs** (e.g., Google Docs uses OT, but CRDTs are better for offline-first apps like mobile note-taking).

---
**AA20**
- **Challenges in Polyglot Tracing**:
  - **Context Propagation**: Use W3C Trace Context or B3 headers to pass `trace-id` and `span-id` across services.
  - **Sampling**: Head-based (decide at the start) vs. tail-based (decide at the end). Head-based is more common (e.g., Jaeger).
  - **Storage/Querying**: Jaeger (open-source), Tempo (Grafana), or commercial (Datadog).
  - **Async Messaging (Kafka)**: Inject trace headers into message metadata. Consumers extract and continue the trace.
- **Ensuring Continuity**:
  - Use **Kafka headers** to store `trace-id` and `span-id`.
  - Libraries like OpenTelemetry auto-instrument Kafka producers/consumers.

### **On-Premise Infrastructure Architecture (20 questions)**

---
**OP1**
- **Type 1 Hypervisor (Bare-Metal)**: Runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V).
- **Type 2 Hypervisor (Hosted)**: Runs on top of a host OS (e.g., VirtualBox, VMware Workstation).

---
**OP2**
- **SAN (Storage Area Network)**: Block-level storage (appears as local disk). *Protocols*: Fibre Channel (FC), iSCSI.
  - *Use case*: High-performance databases (e.g., Oracle RAC).
- **NAS (Network-Attached Storage)**: File-level storage (e.g., NFS, SMB).
  - *Use case*: Shared files (e.g., home directories, backups).

---
**OP3**
- **3-Tier Architecture**:
  - **Core**: High-speed backbone (e.g., 10Gbps switches).
  - **Distribution**: Aggregates access layer traffic (e.g., VLAN routing, ACLs).
  - **Access**: Connects end devices (e.g., switches in server racks).
- **Leaf-Spine**:
  - **Why Preferred**: Non-blocking, lower latency, and simpler scaling (add leaves/spines as needed).
  - **Problem Solved**: 3-tier has oversubscription (e.g., core can become a bottleneck). Leaf-spine provides full bisectional bandwidth.

---
**OP4**
- **Proxmox Cluster Architecture**:
  - **Node Count**: Minimum 3 (quorum requires majority).
  - **Quorum**: Uses Corosync. If quorum is lost, the cluster stops to prevent split-brain.
  - **Fencing (STONITH)**: Power off a failed node (e.g., via IPMI) to prevent data corruption.
  - **Shared Storage Options**:
    - **Ceph**: Distributed, highly available, but complex (requires monitor nodes).
    - **iSCSI/NFS**: Simpler but single point of failure (unless using HA storage).
  - **Node Failure**: If a node fails, Proxmox migrates VMs to other nodes (if shared storage is available). If the node is fenced, its VMs are restarted elsewhere.

---
**OP5**
- **VLAN Trunking**: Carries multiple VLANs over a single link (802.1Q tagging adds a 4-byte tag to Ethernet frames).
- **Linux Configuration**:
  ```bash
  # Create a trunk interface (e.g., eth0)
  ip link add link eth0 name eth0.100 type vlan id 100
  ip link add link eth0 name eth0.200 type vlan id 200
  ip link set eth0.100 up
  ip link set eth0.200 up
  ```
  - Assign IPs to `eth0.100`, `eth0.200`, etc.

---
**OP6**
| **RAID**  | **Description**                          | **Fault Tolerance** | **Capacity (6x1TB)** | **Performance**       |
|-----------|------------------------------------------|---------------------|----------------------|-----------------------|
| RAID 1    | Mirroring (2 drives)                     | 1 drive             | 1TB                  | High read, low write  |
| RAID 5    | Striping + parity (1 parity drive)       | 1 drive             | 5TB                  | Medium                |
| RAID 6    | Striping + dual parity                   | 2 drives            | 4TB                  | Lower write           |
| RAID 10   | Mirroring + striping (min 4 drives)      | 1 drive per mirror  | 3TB                  | High                  |
| RAID Z2   | ZFS equivalent of RAID 6                | 2 drives            | 4TB                  | Variable (COW)        |
- **Choice for Database**: **RAID 10** (best balance of performance and fault tolerance for 6 drives).

---
**OP7**
- **DNS Architecture**:
  - **Internal AD**: Active Directory-integrated DNS (authoritative for `internal.example.com`).
  - **DMZ**: Public DNS servers (authoritative for `example.com`).
  - **Split-Horizon**: Internal clients resolve `app.example.com` to private IPs; external clients resolve to public IPs.
  - **DNSSEC**: Enable on external zone (signs records to prevent spoofing).
  - **Recursive Resolvers**: Forward internal queries to AD DNS; external queries to ISP or public DNS (e.g., 8.8.8.8).
  - **Conditional Forwarding**: Internal DNS forwards `external.example.com` to DMZ DNS.
  - **Laptop Behavior**: On VPN, use internal DNS (via DHCP or VPN config); in office, use local DNS.

---
**OP8**
- **PKI Chain of Trust**:
  - Root CA (offline) → Subordinate CA (issuing) → End-Entity Certificate.
- **Internal PKI Deployment**:
  - **Root CA**: Offline, stored in a HSM. Only used to sign subordinate CAs.
  - **Subordinate CA**: Online, issues certs to servers/users. Uses CRL (Certificate Revocation List) or OCSP (Online Certificate Status Protocol) for revocation.
  - **Certificate Templates**: Define for users, servers, code-signing, etc.
  - **Auto-Enrollment**: Group Policy (Windows) or SCEP (Simple Certificate Enrollment Protocol).
- **Compromise Impact**:
  - **Subordinate CA**: Revoke and reissue all certs from it. Less severe.
  - **Root CA**: Catastrophic; requires rebuilding the entire PKI.

---
**OP9**
| **Option**          | **Cost** | **Reliability** | **Latency** | **Management** | **Security**       | **Recommendation**          |
|---------------------|----------|-----------------|-------------|----------------|--------------------|-----------------------------|
| MPLS                | High     | High            | Low         | Low            | High (private)     | Best for VoIP if budget allows |
| IPsec VPN           | Medium   | Medium          | Medium      | Medium         | High               | Good balance                |
| SD-WAN              | Medium   | High            | Low         | High           | High               | Best for dynamic routing    |
| WireGuard Mesh      | Low      | Medium          | Low         | High           | High               | Simple but complex to manage at scale |
- **Recommendation**: **SD-WAN** (e.g., Cisco Viptela) for VoIP (low latency, high reliability) or **IPsec VPN** if cost is a concern.

---
**OP10**
- **iDRAC/iLO/IPMI**: Out-of-band management (OOB) for remote server control (power, BIOS, KVM) independent of the OS.
- **Why Critical**: Allows recovery if the OS crashes (e.g., reinstall OS via virtual media).
- **Risk if Exposed**: Attackers can power off servers, access BIOS, or install malware. **Mitigation**: Restrict IPMI to a management VLAN, use strong passwords, and disable if unused.

---
**OP11**
| **Feature**       | **LVM**               | **LVM-Thin**          | **ZFS**                     |
|-------------------|-----------------------|-----------------------|-----------------------------|
| **Snapshot**      | COW (Copy-on-Write)   | COW                   | COW + writable clones       |
| **Thin Provisioning** | No (unless thin pools) | Yes                  | Yes                         |
| **Use Case**      | Simple volume management | Space-efficient snapshots | Advanced features (compression, checksums) |
- **When to Use**:
  - **LVM**: Basic volume management (e.g., extending disks).
  - **LVM-Thin**: Snapshots with space efficiency.
  - **ZFS**: Data integrity (checksums), compression, and snapshots (e.g., for databases).

---
**OP12**
- **Stretch Cluster/DR Strategy**:
  - **Ceph CRUSH Rules**: Configure to replicate data across sites (e.g., `osd` placement groups across `site1` and `site2`).
  - **Monitor Placement**: Deploy monitors in a 3rd site or use a tiebreaker (e.g., cloud-based arbitrator).
  - **Network Latency**: Ceph requires <10ms latency for synchronous replication (use async if higher).
  - **Split-Brain Problem**: Without a tiebreaker, a 2-site cluster may split into two active partitions, causing data corruption.
  - **Why 2-Site is Bad**: No way to break ties; use a 3rd site or a cloud-based witness.

---
**OP13**
- **DHCP DORA Process**:
  1. **Discover**: Client broadcasts `DHCPDISCOVER`.
  2. **Offer**: Server responds with `DHCPOFFER` (IP, subnet, lease time).
  3. **Request**: Client requests the offered IP (`DHCPREQUEST`).
  4. **Acknowledge**: Server confirms (`DHCPACK`).
- **Lease Expiry**: Windows clients enter a **rebinding state** (retry current server), then **renewing state** (broadcast for any server). If no server responds, the client keeps the IP until the lease expires (then stops using it).

---
**OP14**
- **Managed Switch**: Configurable (VLANs, QoS, SNMP, port mirroring).
- **Unmanaged Switch**: Plug-and-play, no configuration.
- **Enterprise Features**:
  - VLANs (traffic isolation).
  - Link aggregation (LACP).
  - QoS (prioritize VoIP traffic).
  - Port security (MAC filtering).

---
**OP15**
- **NTP**: Synchronizes clocks across servers (e.g., `ntpd` or `chronyd`).
- **Why Critical**:
  - Kerberos (AD) requires time sync within 5 minutes.
  - Logs are useless if timestamps are inconsistent.
  - Distributed systems (e.g., Ceph, databases) rely on synchronized clocks.
- **Drift Issues**: Can cause authentication failures, split-brain in clusters, or incorrect event ordering.

---
**OP16**
| **Type**          | **Description**                          | **Use Case**                          |
|-------------------|------------------------------------------|---------------------------------------|
| Physical Server   | Bare metal, no virtualization            | High-performance (e.g., HPC, databases) |
| Virtual Machine   | Full OS virtualization                   | General-purpose workloads             |
| Container         | Lightweight, shares host OS kernel       | Microservices, stateless apps         |
- **Bare Metal When**:
  - Extreme performance (e.g., latency-sensitive trading).
  - Hardware passthrough (e.g., GPU, FPGA).
  - Licensing restrictions (e.g., Oracle DB).

---
**OP17**
- **UPS**: Provides short-term power (minutes to hours) during outages. *Types*: Standby, line-interactive, online (double-conversion).
- **Generator**: Long-term power (hours/days) but takes time to start (seconds to minutes).
- **Why Both**:
  - UPS bridges the gap until the generator starts.
  - UPS protects against power spikes/sags.
- **ATS (Automatic Transfer Switch)**: Switches load from utility to generator automatically.

---
**OP18**
- **Active-Passive**: One node is active; the other is standby. *Failover*: Promote standby to active.
- **Active-Active**: Both nodes handle traffic (e.g., load-balanced).
- **PostgreSQL HA with Pacemaker/Corosync**:
  - **Resources**: Virtual IP (VIP), PostgreSQL service, and storage (e.g., DRBD or shared SAN).
  - **Fencing (STONITH)**: Use IPMI to power off a failed node.
  - **Failover**: If the active node fails, Corosync promotes the standby, assigns the VIP, and starts PostgreSQL.

---
**OP19**
- **Backup Strategy**:
  - **3-2-1 Rule**: 3 copies, 2 media types, 1 offsite.
  - **RPO/RTO**:
    - **RPO (Recovery Point Objective)**: Max data loss (e.g., 1 hour for backups).
    - **RTO (Recovery Time Objective)**: Max downtime (e.g., 4 hours for critical systems).
  - **Backup Types**:
    - **Full**: Complete backup (weekly).
    - **Incremental**: Changes since last backup (daily).
    - **Differential**: Changes since last full backup (daily).
  - **Storage**:
    - **Disk**: Fast, but vulnerable to ransomware.
    - **Tape**: Slow, but air-gapped (ransomware-proof).
    - **Cloud**: Offsite, but egress costs can be high.
  - **Immutable Backups**: WORM (Write Once, Read Many) storage (e.g., AWS S3 Object Lock) to prevent tampering.
  - **Testing**: Regularly restore backups to a test environment.
- **Backup vs. Disaster Recovery**:
  - **Backup**: Copying data for restoration.
  - **DR**: Full process to restore *services* (e.g., failover to a secondary site).

---
**OP20**
- **802.1X Roles**:
  - **Supplicant**: Client device (e.g., laptop).
  - **Authenticator**: Switch/port (relays messages).
  - **Authentication Server**: RADIUS server (validates credentials).
- **EAP Methods**:
  - **EAP-TLS**: Certificate-based (most secure).
  - **PEAP**: Password-based (uses TLS tunnel for MS-CHAPv2).
- **Dynamic VLAN Assignment**: RADIUS returns a VLAN ID based on user/group (e.g., HR users → VLAN 10).
- **Failed Authentication**: Port is placed in an **unauthorized VLAN** (e.g., a quarantine VLAN with limited access).
- **MAB (MAC Authentication Bypass)**: For devices without 802.1X (e.g., printers). The switch sends the device’s MAC to RADIUS for validation. If allowed, the port is authorized.
