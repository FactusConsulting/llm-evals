### **Kubernetes (20 questions)**

---

**K1** — A **Deployment** is for stateless applications, managing a set of identical pods with rolling updates and rollbacks. A **StatefulSet** is for stateful applications, providing stable, unique network identities and persistent storage for each pod (e.g., ordered pod names, stable hostnames).

---

**K2** — A **ClusterIP Service** creates a virtual IP (ClusterIP) in the cluster. `kube-proxy` (via iptables/IPVS) routes traffic to the ClusterIP, which load-balances requests to the **Endpoints** (pod IPs) associated with the Service. Traffic is distributed to all pods labeled by the Service’s selector.

---

**K3** —
- **PersistentVolume (PV)**: A provisioned storage resource in the cluster (e.g., NFS, AWS EBS).
- **PersistentVolumeClaim (PVC)**: A request for storage by a user, binding to a PV that meets its requirements (size, access mode).
- **StorageClass**: Defines dynamic provisioning (e.g., "fast" SSD vs. "slow" HDD). PVs can be dynamically created based on a PVC’s StorageClass.
**Relationship**: PVCs consume PVs; StorageClass enables dynamic PV creation.

---

**K4** — Troubleshooting **CrashLoopBackOff**:
1. **Logs**: `kubectl logs <pod> --previous` (check crash logs from the previous container instance).
2. **Events**: `kubectl describe pod <pod>` (look for OOMKilled, ImagePullBackOff, or other errors).
3. **Resource Limits**: Check if the pod exceeds `limits.memory` (OOMKilled) or `limits.cpu` (throttling).
4. **Liveness/Readiness Probes**: Verify if probes are failing (e.g., misconfigured endpoints or slow startup).
5. **Application Errors**: Check if the app crashes due to missing configs (e.g., ConfigMap/Secret not mounted).

---

**K5** — **CoreDNS** provides DNS resolution in Kubernetes, translating service names (e.g., `my-service.namespace.svc.cluster.local`) to ClusterIPs. If CoreDNS pods are down:
- Pods cannot resolve service names, breaking inter-pod communication.
- External DNS (e.g., `google.com`) may also fail if CoreDNS is the upstream resolver.
- Workaround: Use static IPs or hostnames in `/etc/hosts` (not scalable).

---

**K6** — The scheduler uses a **two-phase process**:
1. **Filtering (Predicates)**: Eliminates nodes that don’t meet requirements (e.g., insufficient CPU/memory, node selector mismatch, taints without tolerations).
2. **Scoring (Priorities)**: Ranks remaining nodes using factors like:
   - **Resource Availability**: Nodes with more free CPU/memory score higher.
   - **Node Affinity/Anti-Affinity**: Prefer nodes matching affinity rules or avoiding anti-affinity.
   - **Topology Spread Constraints**: Distribute pods across zones/nodes for high availability.
   - **Inter-Pod Affinity**: Place pods near/away from other pods (e.g., co-locate frontend/backend).
   - **Taints/Tolerations**: Nodes with taints are avoided unless pods tolerate them.

---

**K7** —
- **Scheduling**: The pod’s `requests.memory: 256Mi` is added to the node’s requested memory (3.5GB + 0.25GB = 3.75GB ≤ 4GB). **The pod will be scheduled**.
- **Runtime**: If the pod uses **600Mi**, it exceeds its `limits.memory: 512Mi`. The kernel **OOM-kills** the pod (Kubernetes restarts it, leading to CrashLoopBackOff).

---

**K8** — Request flow for **NGINX Ingress**:
1. **External Load Balancer**: Routes traffic to the Ingress controller’s NodePort/LoadBalancer Service.
2. **Ingress Controller (NGINX)**: Evaluates Ingress rules (host/path) and routes to the appropriate **Service**.
3. **Service (ClusterIP)**: `kube-proxy` (iptables/IPVS) forwards traffic to the **Endpoints** (pod IPs).
4. **Endpoints**: The Service’s selector matches pod labels; traffic is load-balanced to a pod.
5. **Pod**: The application (e.g., Nginx/Apache) processes the request.

---
**K9** — A **NetworkPolicy** controls pod-to-pod traffic (like a firewall). Default behavior:
- **No NetworkPolicy**: All traffic is allowed (open by default).
- **With NetworkPolicy**: Only traffic matching the policy’s `ingress`/`egress` rules is allowed; all else is **denied**.
Example: A policy selecting `app=backend` pods may only allow traffic from `app=frontend` pods on port 80.

---
**K10** —
- **RollingUpdate**: Gradually replaces pods (default). Ensures availability during updates (e.g., 25% unavailable at a time).
- **Recreate**: **Deletes all old pods before creating new ones**. Use when:
  - The app cannot handle concurrent old/new versions (e.g., database schema changes).
  - You need to free resources before starting new pods.

---
**K11** — A **namespace** is a virtual cluster for isolating resources (e.g., `dev`, `prod`). Default namespaces:
- `default`: Default for objects with no namespace specified.
- `kube-system`: Kubernetes system components (e.g., CoreDNS, kube-proxy).
- `kube-public`: Publicly readable data (e.g., cluster info).
- `kube-node-lease`: Node heartbeats for lease-based node health.

---
**K12** — `kubectl describe pod <name>` provides detailed pod info, including:
1. **Events**: Timeline of pod lifecycle (e.g., FailedScheduling, PullImageError).
2. **Conditions**: Pod status (e.g., `Ready: False`, `CrashLoopBackOff`).
3. **Container State**: Exit codes, restart count, last termination reason.
4. **Node/IP**: The node the pod is running on and its IP.
5. **Mounts/Volumes**: ConfigMap/Secret/PV mounts and their status.

---
**K13** — A **ConfigMap** stores non-confidential configuration data (e.g., env vars, config files). Pod consumption methods:
1. **Environment Variables**: Inject as env vars via `envFrom` or `valueFrom`.
2. **Volume Mounts**: Mount as files in a pod (e.g., `configMap` volume).
3. **Command-Line Args**: Use in `command`/`args` (e.g., `args: ["--config", "/etc/config/my-config"]`).

---
**K14** —
- **ClusterIP**: Internal-only virtual IP. Accessible only within the cluster.
- **NodePort**: Exposes the Service on a static port on **every node’s IP** (e.g., `NodeIP:30007`). Routes to ClusterIP.
- **LoadBalancer**: Provisions an external cloud LB (e.g., AWS ELB) that routes to NodePort.

---
**K15** — A **DaemonSet** ensures **one pod per node** (or subset of nodes). Use cases:
- **Logging agents** (e.g., Fluentd, Logstash).
- **Monitoring agents** (e.g., Prometheus Node Exporter).
- **Network plugins** (e.g., Calico, kube-proxy).
- **Storage daemons** (e.g., Ceph, GlusterFS).
Prefer over Deployment when you need **one pod per node** (not scalable replicas).

---
**K16** —
- **Taints/Tolerations**: Nodes **repel** pods unless they **tolerate** the taint.
  - *Use Case*: Reserve nodes for specific workloads (e.g., `node-role.kubernetes.io/master:NoSchedule` for control plane nodes).
- **Node Affinity**: Pods **prefer** or **require** nodes with specific labels.
  - *Use Case*: Schedule pods on nodes with GPUs (`kubernetes.io/arch: amd64`).
**Difference**: Taints/tolerations are **exclusionary** (pods are blocked unless they tolerate), while affinity is **inclusionary** (pods are attracted to nodes).

---
**K17** — A **Kubernetes Operator** is a **custom controller** that extends Kubernetes with domain-specific logic (e.g., managing databases, Kafka clusters). Differences from standard controllers:
- **Standard Controller**: Manages built-in resources (e.g., Deployment, StatefulSet).
- **Operator**: Uses **Custom Resource Definitions (CRDs)** to manage complex, stateful applications (e.g., `MySQLCluster` CRD).
**Problems Solved**:
- Automates **Day 2 operations** (backups, upgrades, failover).
- Encapsulates **domain knowledge** (e.g., how to scale a Cassandra ring).
- Enables **declarative management** of complex systems.

---
**K18** — **etcd** uses **Raft consensus** (strong consistency, linearizable reads). Key properties:
- **Quorum**: Requires majority of nodes (e.g., 2/3 for a 3-node cluster) to agree on writes.
- **If quorum is lost** (e.g., 2/3 nodes down):
  - The cluster **becomes read-only** (no writes accepted).
  - Existing pods may continue running, but **no new pods can be scheduled** (scheduler/apiserver depend on etcd).
- **Recovery from 2/3 node loss**:
  - **Not recoverable** if the lost nodes are permanently down (Raft requires majority to elect a leader).
  - **Solution**: Restore from a **backup** (etcd snapshots) and rebuild the cluster.

---
**K19** — **RBAC** (Role-Based Access Control) in Kubernetes:
- **Role**: Defines permissions **within a namespace** (e.g., `pods:read`).
- **ClusterRole**: Defines **cluster-wide** permissions (e.g., `nodes:list`).
- **RoleBinding**: Grants a Role to users/groups **in a namespace**.
- **ClusterRoleBinding**: Grants a ClusterRole **cluster-wide**.
**Example**: Developer needs read-only access to pods/logs in `dev` namespace:
```yaml
# Role (namespace-scoped)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

# RoleBinding (binds Role to user)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: "dev-user"
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — **Slow DNS resolution due to `ndots`**:
- **Problem**: `/etc/resolv.conf` in pods inherits `ndots:5` from the node. For a query like `my-service`, CoreDNS tries:
  `my-service`, `my-service.dev`, `my-service.dev.svc`, `my-service.dev.svc.cluster`, `my-service.dev.svc.cluster.local` (5 queries).
  If the domain doesn’t exist, each query times out (~5s total).
- **Fix**: Use `dnsConfig` in the pod spec to override `ndots`:
  ```yaml
  dnsConfig:
    options:
      - name: ndots
        value: "2"  # Reduces to 2 queries (e.g., my-service, my-service.dev)
  ```

### **Development (20 questions)**

---
**D1** —
- **`git rebase`**: Moves the current branch’s commits to the tip of another branch, **rewriting history** (linear, clean commits).
- **`git merge`**: Creates a **merge commit**, preserving history (non-linear).
**Avoid rebasing**:
- On **public/shared branches** (rewriting history breaks others’ work).
- If commits are already pushed to a remote.

---
**D2** —
- **TCP**: Connection-oriented, reliable, ordered, error-checked. Uses **handshakes** (SYN, SYN-ACK, ACK).
  - *Protocols*: HTTP, FTP, SSH.
- **UDP**: Connectionless, unreliable, low-latency. No handshakes.
  - *Protocols*: DNS, DHCP, QUIC (HTTP/3).

---
**D3** — A **race condition** occurs when the outcome depends on the **timing/order of concurrent operations**.
**Example (Python)**:
```python
counter = 0

def increment():
    global counter
    temp = counter  # Read
    temp += 1       # Modify
    counter = temp  # Write

# Thread 1 and 2 run increment() concurrently:
# Thread 1: Reads counter=0
# Thread 2: Reads counter=0
# Thread 1: Writes counter=1
# Thread 2: Writes counter=1 (should be 2!)
```
**Fix**: Use locks (`threading.Lock`).

---
**D4** —
- **Symmetric Encryption**: Same key for encryption/decryption (e.g., AES, ChaCha20). Fast, but key distribution is hard.
- **Asymmetric Encryption**: Public/private key pairs (e.g., RSA, ECC). Slow, but solves key distribution.
**In TLS**:
1. **Asymmetric**: Client and server exchange keys via **RSA/ECDHE** (key exchange).
2. **Symmetric**: A **session key** is generated and encrypted with the server’s public key. The client decrypts it with the private key, then uses the session key for **AES** (symmetric) encryption of all data.

---
**D5** — A **container image layer** is a read-only filesystem layer (e.g., from a `Dockerfile` instruction like `RUN`, `COPY`). Layers are:
- **Stacked**: Each layer depends on the previous one.
- **Cached**: Docker caches layers; if a layer changes, all subsequent layers are rebuilt.
**Best Practices**:
- **Order commands**: Place **least-changing** layers first (e.g., `FROM`, `RUN apt-get update`) to maximize cache hits.
- **Multi-stage builds**: Reduce final image size by discarding build-time layers.

---
**D6** — Troubleshooting **intermittent HTTP 503** (Service Unavailable):
1. **Check Server Logs**: Look for crashes, OOM errors, or timeouts.
2. **Load Balancer/Proxy**: Verify if the LB (e.g., Nginx, ALB) is healthy and not dropping requests (e.g., `503` from Nginx if upstream is down).
3. **Resource Limits**: Check CPU/memory usage (e.g., `docker stats`, `kubectl top pods`). Throttling or OOM can cause 503s.
4. **Dependency Failures**: Test external dependencies (DB, cache, APIs). Use `curl` or `tcptraceroute` to check connectivity.
5. **Rate Limiting**: Check if the API is rate-limited (e.g., `429` responses upstream).
6. **Health Checks**: Verify if liveness/readiness probes are failing (e.g., `/health` endpoint returns 5xx).

---
**D7** — **CAP Theorem**: A distributed system can only guarantee **2 out of 3** properties:
- **Consistency (C)**: All nodes see the same data at the same time.
- **Availability (A)**: Every request receives a response (even if stale).
- **Partition Tolerance (P)**: System works despite network partitions.
**Examples**:
- **CP (Consistency + Partition Tolerance)**: MongoDB (with `writeConcern: majority`), etcd, ZooKeeper.
- **AP (Availability + Partition Tolerance)**: Cassandra (with `QUORUM` reads/writes relaxed), DynamoDB.

---
**D8** —
- **Vertical Scaling**: Increase **resources** (CPU, RAM) of a single machine.
- **Horizontal Scaling**: Add **more machines** (instances/nodes).
**Patterns for Horizontal Scaling**:
- **Stateless Services**: Scale by adding more replicas (e.g., web servers).
- **Load Balancing**: Distribute traffic (e.g., Nginx, ALB).
- **Sharding**: Split data across nodes (e.g., MongoDB shards).
- **Microservices**: Decompose monoliths into independently scalable services.

---
**D9** — An **environment variable** is a dynamic value that affects processes (e.g., `PATH`, `DATABASE_URL`).
**Set Persistent Env Var on Linux**:
1. Add to shell config (e.g., `~/.bashrc`, `~/.zshrc`):
   ```bash
   export MY_VAR="value"
   ```
2. Source the file:
   ```bash
   source ~/.bashrc
   ```
3. For system-wide vars, add to `/etc/environment` (no `export`):
   ```bash
   MY_VAR="value"
   ```

**D11** — A **REST API** is an architectural style for networked applications using HTTP methods:
- **GET**: Retrieve a resource (idempotent, safe).
- **POST**: Create a resource (non-idempotent).
- **PUT**: Replace a resource (idempotent; full update).
- **DELETE**: Remove a resource (idempotent).

**D12** — **Version Pinning** is specifying exact versions of dependencies (e.g., `package@1.2.3`) in `package.json`, `requirements.txt`, or `go.mod`.
**Why It Matters**:
- **Reproducible Builds**: Ensures all developers/testers use the same versions.
- **Avoids Breaking Changes**: Prevents accidental upgrades to incompatible versions.

**D13** —
- **Compiled Language**: Code is translated to machine code **before execution** (e.g., C, Go, Rust).
  - *Pros*: Faster execution, optimized.
- **Interpreted Language**: Code is executed line-by-line at runtime (e.g., Python, JavaScript).
  - *Pros*: Portable, easier debugging.

**D14** —
- **Reverse Proxy**: Accepts requests from clients and forwards them to **backend servers** (e.g., Nginx, Traefik).
  - *Use Cases*:
    - **Load Balancing**: Distribute traffic to multiple app servers.
    - **SSL Termination**: Decrypt HTTPS at the proxy (offload from apps).
    - **Caching**: Serve static content (e.g., Nginx caching).
- **Forward Proxy**: Clients route requests **through the proxy** to external servers (e.g., Squid, corporate proxies).
  - *Use Cases*: Anonymity, bypassing restrictions, caching.

---
**D15** — A **deadlock** occurs when two+ processes are **blocked forever**, each waiting for the other’s resources.
**Coffman Conditions** (all must hold):
1. **Mutual Exclusion**: Only one process can use a resource at a time.
2. **Hold and Wait**: A process holds a resource while waiting for another.
3. **No Preemption**: Resources cannot be forcibly taken from a process.
4. **Circular Wait**: A cycle of processes exists (A waits for B, B waits for A).
**Example**: Thread 1 locks `A` and waits for `B`; Thread 2 locks `B` and waits for `A`.

---
**D16** — **Eventual Consistency**: Guarantees that, if no new updates are made, all nodes will **eventually** converge to the same value.
**Cassandra’s Approach**:
- **Read-After-Write Consistency**: Achieved via **tunable consistency levels**:
  - **ONE**: Fastest, but may return stale data.
  - **QUORUM**: Majority of replicas must respond (stronger consistency).
  - **ALL**: All replicas must respond (strongest, but slowest).
- **Hinted Handoff**: If a replica is down, Cassandra stores hints and replays them when the node recovers.
- **Read Repair**: Fixes inconsistencies during reads by comparing replicas.

---
**D17** — **mTLS (Mutual TLS)**: Both client and server authenticate each other using TLS certificates.
**Handshake Process**:
1. **Client Hello**: Client sends supported cipher suites and a **client certificate**.
2. **Server Hello**: Server sends its certificate and requests the client’s certificate.
3. **Server Verification**: Client verifies the server’s certificate (CA-signed).
4. **Client Verification**: Server verifies the client’s certificate (CA-signed).
5. **Key Exchange**: Both parties generate a **session key** (e.g., via ECDHE).
6. **Encrypted Communication**: All traffic is encrypted with the session key.
**Use Cases**:
- **Service-to-Service Auth**: Microservices in a zero-trust network (e.g., Istio, Linkerd).
- **Database Connections**: PostgreSQL, MongoDB with mTLS.
- **Kubernetes**: API server to kubelet communication.

---
**D18** — **Hash Table** is a data structure that maps keys to values using a **hash function**.
**Internal Workings**:
- **Hash Function**: Converts a key to an index (e.g., `hash(key) % array_size`).
- **Collision Resolution**:
  - **Chaining**: Each bucket is a linked list of entries (collisions are appended).
  - **Open Addressing**: If a collision occurs, probe the next slot (e.g., linear probing, quadratic probing).
**Time Complexity**:
| Operation | Average Case | Worst Case (All Collisions) |
|-----------|--------------|-----------------------------|
| Insert    | O(1)         | O(n)                        |
| Lookup    | O(1)         | O(n)                        |
| Delete    | O(1)         | O(n)                        |

**D19** — **Circuit Breaker Pattern**: Prevents cascade failures by **failing fast** when a service is unhealthy.
**States**:
1. **Closed**: Normal operation. Requests pass through; failures are counted.
2. **Open**: If failures exceed a **threshold** (e.g., 50% of requests fail), the circuit **trips**. All requests **fail immediately** (no retries).
3. **Half-Open**: After a **timeout** (e.g., 30s), a few requests are allowed through. If they succeed, the circuit **closes**; if they fail, it **reopens**.
**Relation to Retries/Backoff**:
- **Avoids Retries**: In the **Open** state, no retries are attempted (prevents hammering a dead service).
- **Exponential Backoff**: Used in **Half-Open** state to gradually test service recovery.

**D20** —
- **Optimistic Concurrency Control (OCC)**:
  - **Assumption**: Conflicts are rare. Reads are **not locked**.
  - **Mechanism**: Uses **row versioning** (e.g., `version` column). On update, check if the version matches; if not, **retry**.
  - *Example*:
    ```sql
    UPDATE accounts SET balance = 100, version = version + 1
    WHERE id = 123 AND version = 5;
    ```
  - **When to Use**: High-read, low-write scenarios (e.g., Wikipedia edits).

- **Pessimistic Concurrency Control (PCC)**:
  - **Assumption**: Conflicts are likely. **Locks** resources during reads/writes.
  - **Mechanism**: Uses `SELECT FOR UPDATE` (exclusive lock) to block other transactions.
  - *Example*:
    ```sql
    BEGIN;
    SELECT * FROM accounts WHERE id = 123 FOR UPDATE;
    UPDATE accounts SET balance = 100 WHERE id = 123;
    COMMIT;
    ```
  - **When to Use**: High-contention scenarios (e.g., banking transactions).
