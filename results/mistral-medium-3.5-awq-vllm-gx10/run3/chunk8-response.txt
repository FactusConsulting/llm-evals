### **Cloud Infrastructure Architecture**

---

**CL1** – **IaaS (Infrastructure as a Service)**: Provides virtualized computing resources (VMs, storage, networking). Example: AWS EC2.
**PaaS (Platform as a Service)**: Provides a managed platform for developing, testing, and deploying applications. Example: AWS Elastic Beanstalk.
**SaaS (Software as a Service)**: Delivers fully managed software applications. Example: Microsoft 365.

---

**CL2** – **Shared Responsibility Model**:
- **IaaS VMs**: Provider manages physical infrastructure (host, network, hypervisor). Customer manages OS, middleware, apps, and data.
- **Managed Kubernetes (e.g., EKS, AKS)**: Provider manages control plane (API server, etcd). Customer manages worker nodes, pods, and applications.
- **SaaS (e.g., M365)**: Provider manages everything (infrastructure, app, data). Customer manages user access, data classification, and compliance.

---

**CL3** –
- **VPC**: Isolated virtual network in the cloud.
- **Subnet**: Segment of a VPC with a CIDR block (public/private).
- **Security Group**: Stateful firewall for instances (allow/deny rules based on source/destination).
- **NACL**: Stateless firewall for subnets (explicit allow/deny rules, no state tracking).
**Layering**: VPC → Subnets → NACLs (subnet-level) → Security Groups (instance-level).
**Stateful vs Stateless**: Security Groups track connection state (e.g., allow return traffic). NACLs do not (must explicitly allow return traffic).

---

**CL4** – **Multi-Account Strategy**:
- **Landing Zone**: Pre-configured baseline (guardrails, networking, IAM) for new accounts.
- **Organizational Units (OUs)**: Group accounts (e.g., Dev, Prod, Security) for policy inheritance.
- **Guardrails**: SCPs (Service Control Policies) to enforce compliance (e.g., no public S3 buckets).
- **Shared Networking**: AWS Transit Gateway / Azure Hub-and-Spoke for centralized connectivity.
- **Centralized Logging**: Aggregate logs (CloudTrail, Azure Monitor) to a security account.
**Single-Account Problems**: No isolation, blast radius for breaches, harder to enforce least privilege, and difficult to manage costs/access.

---

**CL5** – **Infrastructure as Code (IaC)**:
- **Terraform/OpenTofu**: Declarative, multi-cloud, stateful (manages state file).
- **Pulumi**: Imperative (code in Python/Go), multi-cloud, supports existing IaC.
- **CloudFormation/Bicep**: AWS/Azure-native, declarative, tightly integrated.
- **Crossplane**: Extends Kubernetes API to manage cloud resources (K8s-style declarative).
**Choices**:
- Terraform: Multi-cloud, modular.
- Pulumi: Need programmatic logic.
- CloudFormation: AWS-only, deep integration.
- Crossplane: Kubernetes-centric environments.

---

**CL6** –
- **HPA (Horizontal Pod Autoscaler)**: Scales pods based on CPU/memory or custom metrics.
- **VPA (Vertical Pod Autoscaler)**: Adjusts CPU/memory requests/limits for pods.
- **Cluster Autoscaler**: Adds/removes nodes based on pod demand.
- **KEDA (Kubernetes Event-Driven Autoscaling)**: Scales based on external events (e.g., Kafka, RabbitMQ).
**Use KEDA over HPA**: When scaling is driven by event queues or external triggers (e.g., message backlog).

---

**CL7** – **Disaster Recovery (DR) Strategy**:
- **RPO (Recovery Point Objective)**: Max acceptable data loss (e.g., 5 minutes).
- **RTO (Recovery Time Objective)**: Max acceptable downtime (e.g., 1 hour).
- **Active-Active**: Both regions serve traffic (synchronous DB replication, global load balancing).
- **Active-Passive**: Primary region active; secondary on standby (asynchronous DB replication).
- **Database Replication**:
  - Sync: Zero RPO but latency/performance impact.
  - Async: Lower performance impact but potential data loss.
- **DNS Failover**: Route53/Traffic Manager health checks redirect traffic.
- **State Management**: Stateless apps in both regions; stateful apps use shared storage (e.g., S3, DynamoDB Global Tables).
- **Cost Implications**: Active-active is expensive (2x resources); pilot light is cheapest (minimal standby).
**DR Models**:
- **Pilot Light**: Minimal infrastructure in DR region (scale up on failure).
- **Warm Standby**: Partial capacity in DR region (faster recovery).
- **Multi-Site Active-Active**: Full redundancy (highest cost, zero downtime).

---

**CL8** – **GitOps**:
- **Model**: Declarative infrastructure/app definitions in Git. Tools (ArgoCD/FluxCD) sync Git state to cluster.
- **ArgoCD vs FluxCD**:
  - ArgoCD: UI, RBAC, app-of-apps pattern.
  - FluxCD: Simpler, Git-native, supports Kustomize/Helm.
- **Secrets Management**:
  - Sealed Secrets: Encrypt secrets in Git (decrypted by controller).
  - External Secrets Operator: Fetches secrets from Vault/AWS Secrets Manager.
  - Vault: Dynamic secrets, lease management.
- **Drift Handling**: Tools detect manual changes and revert to Git state (or alert).

---

**CL9** – **Stateful Legacy App on Kubernetes**:
- **StatefulSet**: Manages ordered pod creation/deletion with stable hostnames.
- **PV/PVC with Local Storage Class**: Persistent volumes tied to nodes (low latency).
- **Headless Service**: Direct pod DNS resolution (no load balancing).
- **Init Containers**: Prep filesystem (e.g., bake config files into paths).
- **ConfigMaps as Volume Mounts**: Inject configs into specific paths.
- **Pod Disruption Budget (PDB)**: Ensures minimum available pods during disruptions.

---
**CL10** –
- **Service Account**: Kubernetes identity for pods (used for in-cluster auth).
- **Workload Identity (Azure)**: Maps Kubernetes service accounts to Azure AD identities (no static credentials).
- **IRSA (IAM Roles for Service Accounts, AWS)**: Assigns IAM roles to Kubernetes service accounts via OIDC.
- **Bad Practice**: Mounting cloud credentials in pods risks exposure (e.g., via logs, container escapes).
- **Workload Identity Federation**: Uses OIDC to dynamically fetch short-lived credentials (e.g., AWS STS, Azure AD).

---
**CL11** –
- **Object Storage (S3/Blob)**: Scalable, unstructured data (files, backups). Durability: 11 9’s (S3). Availability: 99.99% (S3 Standard).
- **Block Storage (EBS/Managed Disk)**: Low-latency volumes for VMs/DBs. Durability: 99.999% (EBS).
- **File Storage (EFS/Azure Files)**: Shared file systems (NFS/SMB). Use for lift-and-shift apps needing shared access.
**When to Use**:
- Object: Static assets, backups.
- Block: Databases, VM disks.
- File: Shared folders, legacy apps.

---
**CL12** – **Zero-Trust Kubernetes Architecture**:
- **Network Policies**: Restrict pod-to-pod traffic (Calico/Cilium).
- **Service Mesh (mTLS)**: Istio/Linkerd for encrypted pod communication.
- **Pod Identity**: Assign identities to pods (e.g., Azure Workload Identity, AWS IRSA).
- **Admission Controllers**: OPA/Kyverno to enforce policies (e.g., no privileged pods).
- **Image Signing**: Cosign/Notary to verify container images.
- **Runtime Security**: Falco for anomaly detection (e.g., shell in container).
- **Secrets Management**: Vault or Kubernetes Secrets (encrypted at rest).
**vs Perimeter Model**: Zero-trust assumes breach; verifies every request. Perimeter model trusts internal traffic.

---
**CL13** –
- **CDN**: Distributes content via edge servers to reduce latency.
- **How It Works**: Users fetch content from nearest edge location; cache misses fetch from origin.
- **Cloud-Native CDNs**: AWS CloudFront, Azure CDN.
- **Use CDN**: Static assets, global users, high traffic.
- **Use Origin**: Dynamic content, real-time data, low-latency requirements.

---
**CL14** –
- **Region**: Geographical area with multiple isolated locations (e.g., us-east-1).
- **Availability Zone (AZ)**: Physically separate data centers within a region.
- **Zonal Resources**: Deployed in a single AZ (e.g., EC2 instance).
- **Regional Resources**: Deployed across AZs (e.g., S3, RDS Multi-AZ).
**Multi-AZ Deployment**: Improves availability (survives AZ outages).

---
**CL15** –
- **Managed Database Service**: Provider handles provisioning, patching, backups, and scaling.
- **Examples**: AWS RDS, Azure SQL, Cloud SQL.
- **Provider Tasks**: Hardware, OS, DB engine, backups, HA.
- **Self-Managed on VM**: Customer handles all of the above.

---
**CL16** –
- **IAM Users**: Individual accounts (e.g., `alice@company`).
- **Groups**: Collection of users (e.g., `Developers`).
- **Roles**: Temporary credentials for services/users (e.g., EC2 instance role).
- **Policies**: JSON documents defining permissions (e.g., `s3:GetObject`).
- **Least Privilege**: Grant only necessary permissions. Use roles over long-term credentials; audit with IAM Access Analyzer.

---
**CL17** –
- **Serverless**: Event-driven, auto-scaling, pay-per-use (e.g., Lambda, Azure Functions).
- **Cold Starts**: Delay when a function is invoked after inactivity (mitigate with provisioned concurrency).
- **Poor Fit**: Long-running processes, high-performance computing, stateful apps.

---
**CL18** –
- **Ingress Resource**: L7 HTTP routing (host/path-based) with annotations for cloud LB.
- **Gateway API**: Next-gen Ingress (more expressive, role-based, supports gRPC/WebSockets).
- **Cloud LB Annotations**: Directly configure cloud LB (e.g., AWS ALB annotations).
- **Service Mesh Ingress Gateway**: Istio/Linkerd gateway for mTLS, advanced routing.
- **TLS Termination**:
  - Ingress: Terminate at LB (simpler, but no end-to-end encryption).
  - Gateway API: Terminate at gateway or passthrough.
  - Service Mesh: Terminate at ingress gateway (mTLS to pods).
**Use Gateway API**: For advanced routing (e.g., weighted traffic splitting, header matching).

---
**CL19** – **Cost Optimization Strategy**:
- **Reserved Instances**: 1-3 year commitments (up to 75% discount).
- **Savings Plans**: Flexible commitments (e.g., $/hour spend).
- **Spot/Preemptible**: Up to 90% discount for fault-tolerant workloads.
- **Right-Sizing**: Use tools (AWS Compute Optimizer) to match instance types to workloads.
- **Storage Tiering**: S3 Intelligent-Tiering (auto-moves data), Glacier for archives.
- **Idle Resource Detection**: AWS Trusted Advisor, Azure Advisor.
- **FinOps Practices**: Tagging, budget alerts, cost allocation.
- **Showback/Chargeback**: Attribute costs to teams (showback = report; chargeback = bill).
**Tools**: AWS Cost Explorer, Azure Cost Management, Kubecost (K8s).

---
**CL20** – **Multi-Cloud Strategy**:
- **Abstraction Layers**: Terraform for IaC, Kubernetes for workloads.
- **Common Runtime**: Kubernetes (EKS, AKS, GKE) for portability.
- **IaC Portability**: Terraform modules for AWS/Azure resources.
- **Networking**: VPN or dedicated interconnect (AWS Direct Connect, Azure ExpressRoute) between clouds.
- **Identity Federation**: SAML/OIDC (e.g., Azure AD + AWS SSO).
**Trade-offs**:
- **Benefits**: Avoid lock-in, resilience, best-of-breed services.
- **Complexity**: Operational overhead, networking latency, inconsistent APIs.
**When Justified**: Regulatory requirements, critical workload redundancy.
**When Unnecessary**: Most workloads can use a single cloud with proper DR.

### **OT Infrastructure Architecture**

---
**OT1** – **Purdue Model (ISA-95)**:
- **Level 0**: Physical process (sensors, actuators).
- **Level 1**: Intelligent devices (PLCs, RTUs).
- **Level 2**: Supervisory control (SCADA, HMIs).
- **Level 3**: Site operations (historian, MES).
- **Level 4**: Site business systems (ERP, scheduling).
- **Level 5**: Enterprise network (corporate IT).

---
**OT2** –
- **IT Networks**: Designed for confidentiality/integrity (CIA triad), frequent patching, high bandwidth.
- **OT Networks**: Designed for availability/reliability, real-time performance, and safety. Patching is risky (downtime, untested updates).
**Why No Standard IT Patching**:
- OT systems often run 24/7; patches may break legacy systems.
- Vendors test patches on specific schedules (e.g., quarterly).

---
**OT3** – **Industrial DMZ (IDMZ)**:
- **Role**: Buffer zone between IT (Level 4) and OT (Levels 0-3).
- **Allowed Traffic**:
  - **IT → OT**: Read-only (e.g., historian data to ERP).
  - **OT → IT**: Alerts, logs, process data.
- **Danger of Direct IT→Level 1**: Malware from IT could disrupt control systems (e.g., Stuxnet). IDMZ enforces strict filtering.

---
**OT4** –
1. **Modbus TCP**: Level 1-2 (PLC ↔ SCADA). Simple, unencrypted.
2. **OPC UA**: Level 2-3 (SCADA ↔ MES). Secure, platform-independent.
3. **EtherNet/IP (CIP)**: Level 1-2 (PLC ↔ HMI). Industrial Ethernet protocol.
4. **PROFINET**: Level 1-2 (PLC ↔ Devices). Real-time Ethernet for automation.
5. **MQTT**: Level 2-3 (Edge ↔ Cloud). Lightweight pub/sub for telemetry.

---
**OT5** –
- **Data Diode**: Hardware device allowing one-way data flow (e.g., OT → IT). No return path.
- **Firewall**: Stateful filtering (allows bidirectional traffic if rules permit).
- **Use Data Diode**: For critical systems where even a misconfigured firewall is too risky (e.g., nuclear plants).
- **Limitation**: No feedback or acknowledgment (e.g., cannot confirm data receipt).

---
**OT6** – **SCADA to Cloud Data Flow**:
1. **Historian (Level 3)**: Stores process data (e.g., OSIsoft PI).
2. **OPC UA Server**: Exposes historian data to edge.
3. **MQTT Broker (Edge Gateway)**: Publishes data to cloud (e.g., AWS IoT Core).
4. **Edge Gateway**: Filters/aggregates data, adds security (TLS, auth).
5. **Cloud Ingestion**: AWS Kinesis/Azure Event Hubs → Analytics (e.g., Time Series DB).
**Security Boundaries**:
- Firewall between historian and edge.
- TLS for MQTT/OPC UA.
- IAM for cloud access.

---
**OT7** – **IEC 62443 Zones and Conduits**:
- **Zone**: Group of assets with similar security requirements (e.g., "PLC Zone").
- **Conduit**: Secure channel between zones (e.g., firewall rule, VPN).
**Manufacturing Plant Model**:
- **Zone 1**: Corporate Network (IT).
- **Zone 2**: Engineering Workstations (Level 3).
- **Zone 3**: SCADA Servers (Level 2).
- **Zone 4**: PLCs (Level 1).
- **Zone 5**: Safety Instrumented Systems (SIS) (Isolated).
**Conduits**:
- Firewall between Zone 1 and Zone 2 (allow only approved protocols).
- Data diode from Zone 4 to Zone 3 (for monitoring).

---
**OT8** – **Network Segmentation Strategy**:
- **VLAN Design**:
  - VLAN 10: PLCs (Level 1).
  - VLAN 20: HMIs (Level 2).
  - VLAN 30: SCADA/Historian (Level 3).
  - VLAN 40: Engineering Workstations.
- **Firewall Placement**:
  - Between VLANs (e.g., allow Modbus TCP only between PLCs and SCADA).
  - North-South: Between OT and IT (IDMZ).
- **Switch Architecture**: Industrial-grade managed switches (e.g., Cisco IE-4000) with ACLs.
- **Remote Vendor Access**:
  - Jump host in IDMZ with MFA.
  - Time-limited VPN to specific VLANs.
- **Transition Plan**:
  - Phase 1: Deploy firewalls in "monitor-only" mode.
  - Phase 2: Enforce policies during maintenance windows.

---
**OT9** –
- **SIS (Safety Instrumented System)**: Independent system to prevent hazards (e.g., emergency shutdown).
- **BPCS (Basic Process Control System)**: Normal process control (e.g., PLCs).
- **IEC 61511**: Standard for SIS design and management.
- **Isolation Requirement**: SIS must be air-gapped or strictly isolated from BPCS/IT to prevent cyber attacks from disabling safety functions.
- **Ransomware Impact**: Could disable SIS, leading to unsafe conditions (e.g., explosions, environmental damage).

---
**OT10** –
- **PLC (Programmable Logic Controller)**: Ruggedized computer for real-time control (e.g., ladder logic). Used for discrete/process control.
- **DCS (Distributed Control System)**: Centralized system for large-scale process control (e.g., refineries). Integrates PLCs, HMIs, and historians.
- **SCADA (Supervisory Control and Data Acquisition)**: Monitors/controls large-scale systems (e.g., water treatment). Uses HMIs, alarms, and reporting.
**Coexistence**: Yes. DCS for process control, PLCs for local logic, SCADA for supervision.

---
**OT11** – **Remote Access Architecture**:
- **Jump Host**: Bastion server in IDMZ; only accessible via MFA.
- **Vendor Access**:
  - Time-limited credentials (e.g., 2-hour sessions).
  - Session recording (e.g., CyberArk, BeyondTrust).
  - Restrict to specific VLANs/IPs.
- **Why No Direct RDP to HMI**:
  - Exposes OT to IT threats (e.g., malware).
  - No audit trail or control.

---
**OT12** – **Detection and Response Plan (Water Treatment Facility)**:
- **Network Monitoring**:
  - IDS (e.g., Nozomi, Dragos) for OT-specific threats.
  - Anomaly detection (e.g., unexpected Modbus writes).
- **Asset Inventory**: Passive monitoring (e.g., Tenable.ot) to track all devices.
- **Incident Response**:
  1. Isolate compromised segment (Level 3).
  2. Verify SIS/BPCS integrity (air-gapped?).
  3. Coordinate with control room to switch to manual mode if needed.
  4. Forensic analysis on vendor VPN appliance.
- **Plant Operator Role**:
  - Follow safety procedures (e.g., manual overrides).
  - Report unusual HMI behavior (e.g., alarms, unauthorized changes).

---
**OT13** –
- **HMI (Human-Machine Interface)**: Graphical interface for operators to monitor/control processes (e.g., touchscreens in control room).
- **Engineering Workstation**: Used by engineers to program PLCs/SCADA (e.g., Studio 5000, TIA Portal).

---
**OT14** –
- **Historian**: Database storing time-series process data (e.g., temperature, pressure).
- **Plant Historian (Level 3)**: Local storage for real-time operations.
- **Enterprise Historian (Level 4)**: Aggregates data from multiple plants for analytics/ERP.

---
**OT15** –
- **Ladder Logic**: Graphical programming language for PLCs (resembles relay logic diagrams).
- **Executed by**: PLCs.
- **Why Still Dominant**: Intuitive for electricians/engineers, standardized (IEC 61131-3), and reliable for discrete control.

---
**OT16** –
- **RTU (Remote Terminal Unit)**: Ruggedized device for remote monitoring/control (e.g., oil pipelines, water systems).
- **vs PLC**: RTUs are designed for harsh environments and telemetry; PLCs are for local control.
- **Typical Use**: Wide-area systems (e.g., utilities, transportation).

---
**OT17** –
- **Analog Signals (4-20mA, 0-10V)**: Continuous range for sensors (e.g., temperature, pressure).
- **Digital Signals**: Discrete (on/off) or binary (e.g., switch, relay).
- **4-20mA Preferred**: 4mA allows for fault detection (0mA = broken wire). More noise-resistant than 0-20mA.

---
**OT18** –
- **OT Asset Inventory**: Foundation for security (can’t protect what you don’t know).
- **Discovery Tools**:
  - **Passive Monitoring**: Sniff network traffic (e.g., Nozomi, Claroty).
  - **Active Scanning**: Risky (can disrupt OT devices); use only in maintenance windows.
- **Why Active Scanning is Dangerous**: Can crash PLCs, cause downtime, or trigger safety systems.

---
**OT19** – **MITRE ATT&CK for ICS**:
- **Tactics/Techniques**:
  1. **Initial Access**: Spearphishing (e.g., malicious USB to engineering workstation).
  2. **Lateral Movement**: Modbus writes to PLCs.
  3. **Execution**: Upload malicious ladder logic.
  4. **Impact**: Stop process (e.g., open breakers in power grid).
  5. **Persistence**: Backdoor in HMI software.
- **vs Enterprise ATT&CK**: ICS matrix includes OT-specific techniques (e.g., protocol manipulation).
- **Use Case**: Identify gaps (e.g., no monitoring for unauthorized Modbus writes).

---
**OT20** – **Converged IT/OT SOC**:
- **Log Collection**:
  - Passive OT traffic monitoring (e.g., Nozomi).
  - Forward logs to SIEM (e.g., Splunk, QRadar) via IDMZ.
- **OT-Specific Detection Rules**:
  - Unauthorized PLC stops.
  - Unexpected OPC UA connections.
- **Alert Triage**:
  - IT Analysts: Handle IT alerts.
  - OT Engineers: Validate OT alerts (e.g., false positives from maintenance).
- **False Positives**: Common in OT (e.g., normal process changes flagged as anomalies). Use whitelisting and OT context.
- **Unauthorized PLC Firmware Alert**:
  1. Isolate PLC network segment.
  2. Verify firmware hash against baseline.
  3. Coordinate with control room to fail-safe if needed.
  4. Forensic analysis on engineering workstation.
