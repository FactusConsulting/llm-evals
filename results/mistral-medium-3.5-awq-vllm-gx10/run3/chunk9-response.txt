### **SC1 — Broken Deployments After Cluster Upgrade**

#### **SC1-A**
The pods fail because the **Restricted Pod Security Standard** (enforced post-upgrade) requires `runAsNonRoot: true` **and** an explicit `runAsUser` (non-zero). The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`, but the `securityContext` only sets `runAsNonRoot: true` without specifying a user. Kubernetes rejects these pods because:
1. **Baseline** (pre-upgrade) allowed `runAsNonRoot: true` without `runAsUser` (defaulting to a non-root user if the image didn’t specify one).
2. **Restricted** requires **both** `runAsNonRoot: true` **and** an explicit `runAsUser` (e.g., `1000`). The image’s `USER root` conflicts with `runAsNonRoot`, causing admission failure.
**Fix**: Set `runAsUser: 1000` (or another non-root UID) in the pod’s `securityContext`.

---

#### **SC1-B**
```bash
kubectl get pods --all-namespaces --field-selector=status.phase=CrashLoopBackOff -o json | jq -r '.items[] | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.securityContext}'
```

---

#### **SC1-C**
**Remediation Strategy**:
1. **Image Fix**: Rebuild images with a non-root `USER` (e.g., `USER 1000`) in the Dockerfile.
2. **Manifest Fix**: Add `runAsUser: 1000` to all pod `securityContext` sections.
3. **CI Gate**: Add a **Kyverno** or **OPA Gatekeeper** policy to block pods with `runAsNonRoot: true` but no `runAsUser`.
4. **Rollout**:
   - Deploy fixes to a **canary namespace** with `Restricted` enforcement.
   - Use `kubectl rollout restart` for affected deployments.
   - Monitor with `kubectl get pods -w` and roll back if failures persist.

### **SC2 — Cross-Region Database Failover Gone Wrong**

#### **SC2-A**
**Stale Data Issue**:
- **Replication Lag**: Cross-region RDS read replicas use **asynchronous replication**, meaning the EU replica may lag behind the US primary by seconds to minutes. Promoting it risks **data loss** for transactions not yet replicated.
- **WAL Shipping**: PostgreSQL streams WAL (Write-Ahead Log) to the replica, but network latency (85ms) and bandwidth constraints can delay apply.
- **Data Loss Window**: Check `pg_stat_replication` on the old primary (if still up) or `pg_last_wal_receive_lsn` vs. `pg_last_wal_replay_lsn` on the promoted replica to quantify lag.

---

#### **SC2-B**
**Terraform Operations**:
1. **Import the Promoted Replica**:
   ```bash
   terraform import aws_db_instance.eu_primary <REPLICA_ARN>
   ```
2. **Update State**:
   - Replace hardcoded ARNs with references (e.g., `aws_db_instance.eu_primary.arn`).
   - Use `terraform state mv` to rename resources if needed.
3. **Detach Old Instance**:
   ```bash
   terraform state rm aws_db_instance.us_primary
   ```
4. **Apply Changes**:
   ```bash
   terraform plan -target=aws_db_instance.eu_primary
   terraform apply -target=aws_db_instance.eu_primary
   ```

---

#### **SC2-C**
**Architecture Design**:
1. **RDS Proxy**: Replace PgBouncer to manage connections and reduce retry errors.
2. **Route53 Failover**: Use **latency-based routing** with health checks to switch DNS to the EU primary.
3. **Retry Logic**: Implement **exponential backoff** in the app for transient failures.
4. **RPO < 1s**: Use **Aurora Global Database** (synchronous replication across regions) instead of standard RDS.
5. **Multi-AZ**: Deploy Aurora with **Multi-AZ** in both regions for faster failover.

### **SC4 — Migrating a Stateful Monolith to Kubernetes**

#### **SC4-A**
**Top 5 Blockers & Solutions**:
1. **Sticky Sessions**:
   - **Problem**: Kubernetes doesn’t natively support sticky sessions.
   - **Solution**: Use **Redis** for shared session storage.
2. **Local NFS Mounts**:
   - **Problem**: Pods are ephemeral; local NFS mounts won’t persist.
   - **Solution**: Use a **ReadWriteMany** PVC with an NFS CSI driver.
3. **Oracle 19c**:
   - **Problem**: Oracle isn’t container-friendly.
   - **Solution**: Run Oracle in a **StatefulSet** with a PVC or use **Amazon RDS for Oracle**.
4. **IBM MQ**:
   - **Problem**: MQ client libraries may not be Kubernetes-aware.
   - **Solution**: Use **IBM MQ Kubernetes Operator** or a sidecar container.
5. **F5 BIG-IP**:
   - **Problem**: BIG-IP is external to Kubernetes.
   - **Solution**: Replace with **Kubernetes Ingress (NGINX/Traefik)** + **Service Mesh (Istio)**.

---

#### **SC4-B**
**OpenTofu Module**:

#### **SC4-C**
**Phased Migration Plan**:
1. **Phase 1: Stateless Services**:
   - Move non-stateful endpoints (e.g., `/health`, `/metrics`) to Kubernetes.
   - Use **Ingress** to route 10% of traffic to Kubernetes.

   - Deploy Oracle in a **StatefulSet** or migrate to RDS.
   - Use **IBM MQ Operator** for MQ integration.
   - **Cutover**: 100% traffic to Kubernetes.
   - **Rollback**: Fail back to F5 if p99 latency > 2s.

- p99 latency < 2s.

- Redis/NFS latency < 10ms.

```sql

  blocked_locks.pid AS blocked_pid,
  blocking_locks.pid AS blocking_pid,
  blocked_activity.query AS blocked_statement,
  blocking_activity.query AS blocking_statement,
  blocked_activity.query_start,
  age(now(), blocked_activity.query_start) AS blocking_duration
FROM
  pg_catalog.pg_locks blocked_locks
JOIN
  pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid

  pg_catalog.pg_locks blocking_locks

  AND blocking_locks.DATABASE IS NOT DISTINCT FROM blocked_locks.DATABASE
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
  AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
  AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
  AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
  AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
  AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
  AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
  AND blocking_locks.pid != blocked_locks.pid
JOIN
  pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
```

  - Replace VPN/Direct Connect with **Tailscale** as the overlay network.

### **SC9 — Securing a Public-Facing API After a Breach**

#### **SC9-A**
**Vulnerabilities & Fixes**:
1. **BOLA (Broken Object Level Authorization)**:
   - **OWASP Category**: **API1:2023 - Broken Object Level Authorization**.
   - **Blast Radius**: Attackers can access **all user records** (e.g., PII, financial data).
   - **Fix**: Implement **object-level permissions** in Django REST Framework:
     ```python
     from rest_framework.permissions import BasePermission

     class IsOwner(BasePermission):
         def has_object_permission(self, request, view, obj):
             return obj.user == request.user

     class UserRecordViewSet(viewsets.ModelViewSet):
         permission_classes = [IsAuthenticated, IsOwner]
         def get_object(self):
             obj = super().get_object()
             self.check_object_permissions(self.request, obj)
             return obj
     ```
2. **Exposed Internal Fields**:
   - **OWASP Category**: **API3:2023 - Excessive Data Exposure**.
   - **Blast Radius**: Leaks **internal IDs, employee data, or sensitive notes**.
   - **Fix**: Use **Django REST Framework serializers** to exclude fields:
     ```python
     class UserSerializer(serializers.ModelSerializer):
         class Meta:
             model = User
             exclude = ['created_by_employee_id', 'internal_notes']
     ```
3. **No Rate Limiting**:
   - **OWASP Category**: **API4:2023 - Lack of Resources & Rate Limiting**.
   - **Blast Radius**: **DoS attacks** or **data exfiltration** (e.g., 100K records in 10 mins).
   - **Fix**: Use **Django Ratelimit**:
     ```python
     from django_ratelimit.decorators import ratelimit

     @ratelimit(key='ip', rate='100/5m')
     def my_view(request):
         ...
     ```
4. **API Keys in URLs**:
   - **OWASP Category**: **API2:2023 - Broken Authentication**.
   - **Blast Radius**: Keys are **logged in CloudWatch/ALB**, enabling **replay attacks**.
   - **Fix**: Move keys to **headers** (e.g., `Authorization: Bearer <key>`) and **rotate all keys**.

#### **SC9-C**
**Defense-in-Depth Architecture**:
1. **Authentication**:
   - **Short-Term**: Rotate all API keys and move them to **headers**.
   - **Long-Term**: Replace API keys with **OAuth2** (e.g., **Auth0** or **AWS Cognito**).
     - Use **JWTs** with short expiration (e.g., 15 minutes).
     - Validate tokens in Django using `django-oauth-toolkit`.
2. **API Gateway**:
   - Deploy **Kong** or **AWS API Gateway** in front of ALB for:
     - **Centralized auth** (OAuth2/JWT validation).
     - **Rate limiting** (per-client).
     - **Request transformation** (e.g., strip internal fields).
3. **Field-Level Encryption**:
   - Use **AWS KMS** or **Django Fernet Fields** to encrypt PII in the database.
4. **Audit Logging**:
   - Enable **CloudTrail Data Events** for API Gateway/ALB.
   - Log all requests to **S3** (with **KMS encryption**).
5. **Migration Plan**:
   - **Phase 1**: Deploy API Gateway with **dual auth** (API keys + OAuth2).
   - **Phase 2**: Gradually migrate clients to OAuth2.
   - **Phase 3**: Deprecate API keys.

### **SC10 — Designing a Multi-Cluster Disaster Recovery Platform**

#### **SC10-A**
**Kubernetes Multi-Cluster Architecture**:
| **Approach**               | **RPO** | **RTO** | **Feasibility with 12ms Latency** | **Stateful Component Strategy** |
|----------------------------|---------|---------|-----------------------------------|----------------------------------|
| **Active-Passive (Velero)** | 15m     | <1h     | ✅ (Velero backups to S3) | **PostgreSQL**: WAL archiving to S3 + Velero snapshots. **Redis**: RDB snapshots. **RabbitMQ**: Mirrored queues to DR. **MinIO**: Cross-site replication. |
| **Active-Active (Istio/Cilium)** | <1s     | <1m     | ❌ (12ms is acceptable, but **conflict resolution** is complex for PostgreSQL/Redis) | **PostgreSQL**: Aurora Global Database (synchronous). **Redis**: Redis Enterprise with **Active-Active Geo-Distribution**. **RabbitMQ**: **Shovel plugin** for cross-site mirroring. **MinIO**: **Multi-site replication**. |

**Recommendation**:
- **Active-Passive with Velero** is **simpler** and meets RPO/RTO requirements.
- **Active-Active** is **risky** for PostgreSQL/Redis due to **split-brain** risks.

#### **SC10-C**
**Automated Failover Orchestration**:
1. **Failure Detection**:
   - **Monitoring**: Use **Prometheus + Alertmanager** to detect:
     - **Site Down**: All nodes in Chicago are unreachable (e.g., `up{site="chicago"} == 0` for 5 minutes).
     - **False Positive Prevention**: Require **multiple signals** (e.g., Prometheus + Pingdom).
   - **DNS Failover**: Use **Route53 Health Checks** with **DNS Failover**:
     ```hcl
     resource "aws_route53_health_check" "chicago" {
       fqdn              = "chicago-postgres.internal"
       port              = 5432
       type              = "TCP"
       failure_threshold = 3
     }
     resource "aws_route53_record" "postgres" {
       zone_id = aws_route53_zone.internal.zone_id
       name    = "postgres.internal"
       type    = "A"
       ttl     = 60
       records = [aws_instance.chicago_postgres.private_ip]
       health_check_id = aws_route53_health_check.chicago.id
       set_identifier = "chicago"
       failover_routing_policy {
         type = "PRIMARY"
       }
     }
     ```
2. **Failover Sequence**:
   - **Step 1**: **Promote Dallas PostgreSQL** (Patroni auto-promotes standby if primary fails).
   - **Step 2**: **Update DNS** (Route53 fails over to Dallas).
   - **Step 3**: **Redis Sentinel Failover**:
     - Sentinel detects primary failure and promotes Dallas Redis.
   - **Step 4**: **RabbitMQ**:
     - **Mirrored queues** in Dallas take over (configured via `rabbitmq-shovel`).
   - **Step 5**: **MinIO**:
     - **Site replication** catches up (MinIO’s `mc admin replicate`).
   - **Step 6**: **Update OpenTofu State**:
     - Run `tofu apply` in DR to update references (e.g., PostgreSQL endpoint).
3. **Split-Brain Handling**:
   - **PostgreSQL**: Use **synchronous_commit = remote_apply** to ensure no data loss.
   - **Redis**: Use **Sentinel with quorum** (e.g., 3/5 nodes must agree).
   - **RabbitMQ**: Use **federation** (not mirroring) to avoid conflicts.
4. **Failback Procedure**:
   - **Step 1**: Restore Chicago site.
   - **Step 2**: **Re-sync PostgreSQL** (Patroni will rejoin as standby).
   - **Step 3**: **Re-sync Redis** (Sentinel will re-add Chicago as replica).
   - **Step 4**: **Re-sync RabbitMQ** (re-enable mirroring).
   - **Step 5**: **Update DNS** back to Chicago (manual step to avoid flapping).
   - **Step 6**: **Verify Data Consistency** (run checksums on PostgreSQL/MinIO).
