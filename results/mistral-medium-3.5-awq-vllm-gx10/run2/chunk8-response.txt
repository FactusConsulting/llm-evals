### **Cloud Infrastructure Architecture**

---

**CL1** – **IaaS (Infrastructure as a Service)**: Provides virtualized computing resources (VMs, storage, networking). Example: AWS EC2.
**PaaS (Platform as a Service)**: Provides a managed platform for developing, testing, and deploying applications. Example: AWS Elastic Beanstalk.
**SaaS (Software as a Service)**: Delivers fully managed software applications. Example: Microsoft 365.

---

**CL2** – **Shared Responsibility Model**:
- **IaaS VMs**: Provider manages physical infrastructure (host, network, hypervisor). Customer manages OS, middleware, apps, and data.
- **Managed Kubernetes (e.g., EKS, AKS)**: Provider manages control plane (API server, etcd). Customer manages worker nodes, pods, and applications.
- **SaaS (e.g., M365)**: Provider manages everything (infrastructure, app, data). Customer manages user access and data classification.

---

**CL3** –
- **VPC**: Isolated virtual network in the cloud.
- **Subnet**: Segment of a VPC with a CIDR range (public/private).
- **Security Group**: Stateful firewall for instances (allow/deny rules based on source/destination).
- **NACL**: Stateless firewall for subnets (explicit deny rules, no state tracking).
**Layering**: VPC → Subnets → NACLs (subnet-level) → Security Groups (instance-level).
**Stateful vs Stateless**: Security Groups track connection state (e.g., allow return traffic). NACLs do not (require explicit inbound/outbound rules).

---

**CL4** – **Multi-Account Strategy**:
- **Landing Zone**: Pre-configured baseline (guardrails, networking, IAM) for new accounts.
- **Organizational Units (OUs)**: Group accounts by function (e.g., Dev, Prod, Security).
- **Guardrails**: SCPs (Service Control Policies) to enforce compliance (e.g., no public S3 buckets).
- **Shared Networking**: AWS Transit Gateway / Azure Hub-and-Spoke for centralized connectivity.
- **Centralized Logging**: Aggregate logs (CloudTrail, Azure Monitor) to a security account.
**Single-Account Problems**: No isolation, blast radius for breaches, harder to manage permissions, and lack of cost allocation.

---

**CL5** – **Infrastructure as Code (IaC)**:
- **Terraform/OpenTofu**: Declarative, multi-cloud, stateful (manages state file).
- **Pulumi**: Imperative (code in Python/Go), multi-cloud, supports existing IaC.
- **CloudFormation/Bicep**: AWS/Azure-native, declarative, tightly integrated.
- **Crossplane**: Extends Kubernetes to manage cloud resources via CRDs.
**Choices**:
- Terraform: Multi-cloud, modular.
- Pulumi: Need programmatic logic.
- CloudFormation: AWS-only, deep integration.
- Crossplane: Kubernetes-centric control plane.

---

**CL6** –
- **HPA (Horizontal Pod Autoscaler)**: Scales pods based on CPU/memory or custom metrics.
- **VPA (Vertical Pod Autoscaler)**: Adjusts CPU/memory requests/limits for pods.
- **Cluster Autoscaler**: Adds/removes nodes based on pod demand.
- **KEDA (Kubernetes Event-Driven Autoscaling)**: Scales based on external events (e.g., Kafka, RabbitMQ).
**Use KEDA over HPA**: When scaling is driven by event queues or external triggers (e.g., message backlog).

---

**CL7** – **Disaster Recovery (DR) Strategy**:
- **RPO (Recovery Point Objective)**: Max acceptable data loss (e.g., 5 minutes).
- **RTO (Recovery Time Objective)**: Max acceptable downtime (e.g., 1 hour).
- **Active-Active**: Both regions serve traffic (synchronous DB replication, global load balancing).
- **Active-Passive**: Primary region active; secondary on standby (asynchronous DB replication).
- **Database Replication**: Sync (strong consistency, higher cost) vs Async (eventual consistency, lower cost).
- **DNS Failover**: Route53/Traffic Manager redirects traffic to healthy region.
- **State Management**: Stateless apps in both regions; stateful apps use shared storage (e.g., S3, DynamoDB Global Tables).
- **Cost Implications**: Active-active is expensive (2x resources); pilot light is cheapest (minimal standby).
**DR Models**:
- **Pilot Light**: Minimal infrastructure in DR region (e.g., DB snapshots, scaled-down services).
- **Warm Standby**: Partial capacity in DR region (e.g., reduced-scale app, async DB).
- **Multi-Site Active-Active**: Full redundancy in both regions.

---

**CL8** – **GitOps**:
- **Model**: Declarative infrastructure/app definitions in Git. Tools (ArgoCD/FluxCD) sync Git state to cluster.
- **ArgoCD vs FluxCD**:
  - ArgoCD: UI, RBAC, app health monitoring.
  - FluxCD: Simpler, Git-native, no UI.
- **Secrets Management**:
  - **Sealed Secrets**: Encrypt secrets in Git (decrypted by controller).
  - **External Secrets Operator**: Fetches secrets from Vault/AWS Secrets Manager.
  - **Vault**: Dynamic secrets, lease management.
- **Drift Handling**: Tools detect manual changes and revert to Git state (or alert).

---

**CL9** – **Stateful Legacy App on Kubernetes**:
- **StatefulSet**: Manages ordered, stable pod identities (e.g., `pod-0`, `pod-1`).
- **PV/PVC with Local Storage Class**: Persistent volumes with local SSDs (low latency).
- **Headless Service**: Direct pod DNS resolution (e.g., `pod-0.statefulset.default.svc.cluster.local`).
- **Init Containers**: Prep filesystem (e.g., copy config files to `/etc/app`).
- **ConfigMaps as Volume Mounts**: Inject configs into specific paths (e.g., `/etc/app/config.ini`).
- **Pod Disruption Budget (PDB)**: Ensures minimum available pods during disruptions (e.g., `minAvailable: 2`).

---

**CL10** –
- **Service Account**: Kubernetes identity for pods (used for in-cluster API access).
- **Workload Identity (Azure)**: Maps Kubernetes service accounts to Azure AD identities (no static credentials).
- **IRSA (IAM Roles for Service Accounts, AWS)**: Assigns IAM roles to Kubernetes service accounts via OIDC.
- **Bad Practice**: Mounting cloud credentials (e.g., AWS keys) in pods risks exposure (use IRSA/Workload Identity instead).
- **Workload Identity Federation**: Short-lived tokens (OIDC) for cross-cloud identity (e.g., Azure AD → AWS IAM).

---

**CL11** –
- **Object Storage (S3/Blob)**: Unstructured data (files, backups), high durability (11 9s), eventual consistency.
- **Block Storage (EBS/Managed Disk)**: Low-latency volumes for VMs/DBs (e.g., EC2, RDS), high availability (AZ-bound).
- **File Storage (EFS/Azure Files)**: Shared file systems (NFS/SMB), multi-AZ access.
**Use Cases**:
- Object: Static assets, backups.
- Block: Databases, boot volumes.
- File: Shared home directories, lift-and-shift apps.

---

**CL12** – **Zero-Trust Kubernetes Architecture**:
- **Network Policies**: Restrict pod-to-pod traffic (e.g., only allow `frontend → backend`).
- **Service Mesh (mTLS)**: Istio/Linkerd for encrypted pod-to-pod communication.
- **Pod Identity**: Assign identities to pods (e.g., Azure Workload Identity, AWS IAM Roles for Service Accounts).
- **Admission Controllers**: OPA/Kyverno to enforce policies (e.g., "no privileged pods").
- **Image Signing**: Cosign/Notary to verify container images.
- **Runtime Security**: Falco for anomaly detection (e.g., shell in a container).
- **Secrets Management**: Vault or Kubernetes Secrets (encrypted at rest).
**vs Perimeter Model**: Zero-trust assumes breach; every request is authenticated/authorized (no implicit trust).

---

**CL13** –
- **CDN**: Distributes content via edge servers (reduces latency, offloads origin).
- **How it Works**: Users request content → CDN edge server (cache hit) or fetches from origin (cache miss).
- **Cloud-Native CDNs**: AWS CloudFront, Azure Front Door.
- **Use CDN**: Static assets, global users, high traffic.
- **Use Origin**: Dynamic content, real-time data, low-latency requirements.

---
---
**CL14** –
- **Availability Zone (AZ)**: Isolated data center within a region (e.g., `us-east-1a`).
- **Region**: Geographic area with multiple AZs (e.g., `us-east-1`).
- **Multi-AZ Deployment**: High availability (e.g., RDS Multi-AZ, ALB across AZs).
- **Zonal vs Regional Resources**:
  - Zonal: Bound to one AZ (e.g., EC2 instance).
  - Regional: Span multiple AZs (e.g., S3, IAM).

---
---
**CL15** –
- **Managed Database Service**: Provider handles provisioning, patching, backups, scaling (e.g., RDS, Cloud SQL).
- **vs Self-Managed on VM**:
  - Provider: Automated backups, failover, monitoring.
  - Self-Managed: Full control but operational overhead.

---
---
**CL16** –
- **IAM Users**: Individual accounts (e.g., `alice@company.com`).
- **Groups**: Collection of users (e.g., `Developers`).
- **Roles**: Temporary permissions (e.g., `EC2-Admin-Role`).
- **Policies**: JSON documents defining permissions (e.g., `s3:GetObject`).
- **Principle of Least Privilege**: Grant minimal permissions required (e.g., deny `*` by default).

---
---
**CL17** –
- **Serverless**: Event-driven, auto-scaling, pay-per-use (e.g., Lambda, Azure Functions).
- **Cold Starts**: Delay when a function is invoked after inactivity (mitigate with provisioned concurrency).
- **Poor Fit**: Long-running processes, high-performance computing, stateful apps.

---
---
**CL18** –
- **Ingress Resource**: L7 HTTP routing (e.g., `/api → backend-service`).
- **Gateway API**: Next-gen Ingress (better for multi-team, extensible).
- **Cloud Load Balancer Annotations**: L4/L7 load balancing (e.g., AWS ALB annotations).
- **Service Mesh Ingress Gateway**: mTLS, advanced traffic management (e.g., Istio Ingress Gateway).
- **TLS Termination**:
  - Ingress: Terminate at ingress controller (simpler).
  - Gateway API: Terminate at gateway or backend.
  - Service Mesh: Terminate at ingress gateway (end-to-end mTLS).
- **Use Gateway API**: Multi-team environments, advanced routing (e.g., header-based).

---
---
**CL19** – **Cost Optimization Strategy**:
- **Reserved Instances**: 1- or 3-year commitments (up to 75% discount).
- **Savings Plans**: Flexible commitments (e.g., $10/hour for 1 year).
- **Spot/Preemptible Instances**: Up to 90% discount (for fault-tolerant workloads).
- **Right-Sizing**: Match instance types to workload (e.g., use `t3.medium` instead of `m5.xlarge`).
- **Storage Tiering**: S3 Intelligent-Tiering (auto-move to cheaper tiers), Archive for cold data.
- **Idle Resource Detection**: Tools like AWS Trusted Advisor, Azure Advisor.
- **FinOps Practices**: Tagging, budget alerts, cost allocation.
- **Showback/Chargeback**: Allocate costs to teams (showback = visibility; chargeback = billing).
- **Tools**: AWS Cost Explorer, Azure Cost Management, Kubecost (Kubernetes).

---
---
**CL20** – **Multi-Cloud Strategy**:
- **Abstraction Layers**: Terraform (IaC), Kubernetes (container orchestration).
- **Kubernetes as Common Runtime**: Run workloads on EKS (AWS) and AKS (Azure) with same manifests.
- **Terraform for IaC**: Write once, deploy to both clouds (use cloud-agnostic modules).
- **Networking Between Clouds**: VPN (site-to-site) or dedicated interconnect (AWS Direct Connect + Azure ExpressRoute).
- **Identity Federation**: SAML/OIDC (e.g., Azure AD → AWS IAM).
- **Trade-Offs**:
  - **Pros**: Avoid lock-in, resilience, best-of-breed services.
  - **Cons**: Complexity, operational overhead, networking latency.
- **When Justified**: Regulatory requirements, critical workload redundancy.
- **When Unnecessary**: Most workloads can run in a single cloud with proper DR.

### **OT Infrastructure Architecture**

---

**OT1** – **Purdue Model (ISA-95)**:
- **Level 0**: Physical process (sensors, actuators).
- **Level 1**: Intelligent devices (PLCs, RTUs).
- **Level 2**: Supervisory control (SCADA, HMIs).
- **Level 3**: Site operations (historian, MES).
- **Level 4**: Site business systems (ERP, scheduling).
- **Level 5**: Enterprise (corporate IT, cloud).

---
---
**OT2** – **IT vs OT Networks**:
- **IT**: General-purpose, frequent patching, high bandwidth, tolerance for downtime.
- **OT**: Real-time, deterministic, high availability, patching risks downtime (prioritize uptime over security).
- **Why No Standard Patching**: OT systems often run 24/7; patches may break legacy systems or require downtime.

---
---
**OT3** – **IDMZ (Industrial DMZ)**:
- **Role**: Buffer zone between IT (Level 4) and OT (Levels 0-3).
- **Allowed Traffic**:
  - **IT → OT**: Read-only (e.g., historian data to ERP).
  - **OT → IT**: Alerts, logs, non-critical data.
- **Danger of Direct IT → Level 1**: Malware/ransomware could disrupt control systems (e.g., PLCs).

---
---
**OT4** – **OT Protocols & Purdue Levels**:
1. **Modbus TCP**: Level 1-2 (PLC ↔ SCADA).
2. **OPC UA**: Level 2-3 (secure, platform-independent data exchange).
3. **EtherNet/IP (CIP)**: Level 1-2 (industrial Ethernet for automation).
4. **PROFINET**: Level 1-2 (Siemens industrial Ethernet).
5. **MQTT**: Level 3+ (lightweight pub/sub for telemetry).

---
---
**OT5** – **Data Diode vs Firewall**:
- **Data Diode**: One-way hardware device (physically prevents reverse traffic). Used for high-security OT (e.g., nuclear plants).
- **Firewall**: Stateful filtering (allows bidirectional traffic if rules permit).
- **Limitation of Data Diode**: No return path (e.g., cannot acknowledge receipt).

---
---
**OT6** – **SCADA to Cloud Data Flow**:
1. **Historian (Level 3)**: Stores process data (e.g., OSIsoft PI).
2. **OPC UA Server**: Exposes historian data.
3. **MQTT Broker (Edge Gateway)**: Publishes data to cloud (e.g., AWS IoT Core).
4. **Edge Gateway**: Filters/aggregates data, applies security (TLS, auth).
5. **Cloud Ingestion**: AWS Kinesis/Azure Event Hubs → analytics (e.g., Databricks).
**Security Boundaries**:
- Firewall between OT and edge gateway.
- TLS for MQTT/OPC UA.
- IAM for cloud access.

---
---
**OT7** – **IEC 62443 Zones & Conduits**:
- **Zone**: Group of assets with similar security requirements (e.g., "PLC Zone").
- **Conduit**: Secure channel between zones (e.g., firewall rule allowing OPC UA traffic).
**Manufacturing Plant Model**:
- **Zone 1**: Corporate Network (IT).
- **Zone 2**: Engineering Workstations (Level 4).
- **Zone 3**: SCADA Servers (Level 3).
- **Zone 4**: PLCs (Level 1-2).
- **Zone 5**: Safety Instrumented Systems (SIS) (isolated).
**Conduits**:
- Firewall between Zone 1 (IT) and Zone 2 (read-only access).
- Data diode between Zone 3 (SCADA) and Zone 1 (IT).

---
---
**OT8** – **Network Segmentation Strategy**:
- **VLAN Design**:
  - VLAN 10: PLCs (Level 1).
  - VLAN 20: HMIs (Level 2).
  - VLAN 30: SCADA (Level 3).
  - VLAN 40: Historian.
- **Firewall Placement**: Between VLANs (e.g., allow OPC UA from HMI to SCADA, block all else).
- **Switch Architecture**: Layer 3 switches for inter-VLAN routing (with ACLs).
- **Remote Vendor Access**: Jump host in DMZ with MFA + session recording.
- **Transition Plan**:
  1. Audit current traffic flows.
  2. Deploy firewalls in "monitor-only" mode.
  3. Gradually enforce rules during maintenance windows.

---
---
**OT9** – **SIS vs BPCS**:
- **BPCS (Basic Process Control System)**: Normal operation (e.g., temperature control).
- **SIS (Safety Instrumented System)**: Emergency shutdown (e.g., pressure relief).
- **IEC 61511**: Standard for SIS design and management.
- **Isolation Requirement**: SIS must be air-gapped or strictly isolated to prevent cyber attacks from disabling safety functions.
- **Ransomware Impact**: Could disable SIS → catastrophic physical harm (e.g., explosions, chemical leaks).

---
---
**OT10** –
- **PLC (Programmable Logic Controller)**: Ruggedized computer for real-time control (e.g., ladder logic).
- **DCS (Distributed Control System)**: Centralized control for large processes (e.g., oil refinery).
- **SCADA (Supervisory Control and Data Acquisition)**: Monitoring/control for geographically dispersed assets (e.g., water treatment).
- **Coexistence**: Yes (e.g., DCS for process control + SCADA for monitoring + PLCs for local control).

---
---
**OT11** – **Remote Access Architecture**:
- **Jump Host**: Bastion server in DMZ (no direct access to OT).
- **MFA**: Required for all remote sessions.
- **Session Recording**: Log all vendor/employee actions (e.g., Splunk).
- **Vendor Access**: Time-limited, just-in-time (JIT) access via VPN + jump host.
- **Why No Direct RDP to HMI**: Exposes OT to IT threats (e.g., malware, brute force).

---
---
**OT12** – **Detection & Response Plan (Water Treatment Facility)**:
- **Network Monitoring**:
  - IDS (e.g., Nozomi, Dragos) for OT-specific threats.
  - Anomaly detection (e.g., unexpected Modbus writes).
- **Asset Inventory**: Passive monitoring (e.g., Tenable.ot) to track all devices.
- **Incident Response**:
  1. Isolate compromised segment (Level 3).
  2. Verify SIS integrity (air-gapped?).
  3. Coordinate with control room to switch to manual operation if needed.
  4. Forensic analysis on vendor VPN appliance.
- **Plant Operator Role**: Follow emergency procedures, confirm physical safety, avoid digital actions (e.g., no rebooting PLCs).

---
---
**OT13** –
- **HMI (Human-Machine Interface)**: Graphical interface for operators to monitor/control processes (e.g., touchscreen in a control room).
- **Engineering Workstation**: Used by engineers to program PLCs/SCADA (e.g., Studio 5000, TIA Portal).

---
---
**OT14** –
- **Historian**: Database for time-series process data (e.g., temperature, pressure).
- **Plant Historian (Level 3)**: Local, high-resolution data (e.g., 1-second intervals).
- **Enterprise Historian (Level 4)**: Aggregated, long-term data for analytics (e.g., daily averages).

---
---
**OT15** –
- **Ladder Logic**: Graphical programming language for PLCs (resembles relay logic diagrams).
- **Device**: PLCs (e.g., Allen-Bradley, Siemens).
- **Why Still Dominant**: Intuitive for electricians, standardized (IEC 61131-3), real-time execution.

---
---
**OT16** –
- **RTU (Remote Terminal Unit)**: Ruggedized device for remote monitoring/control (e.g., oil pipelines, water systems).
- **vs PLC**: RTUs are simpler, designed for harsh environments, and often have built-in I/O for telemetry.
- **Typical Use**: Wide-area, low-bandwidth, or extreme environments (e.g., offshore rigs).

---
---
**OT17** –
- **Analog Signals (4-20mA, 0-10V)**: Continuous range (e.g., temperature, pressure).
- **Digital Signals**: Discrete (on/off) (e.g., valve open/closed).
- **4-20mA vs 0-20mA**: 4mA allows detection of broken wires (0mA = fault).

---
---
**OT18** – **OT Asset Inventory**:
- **Foundation**: Critical for security (can’t protect what you don’t know exists).
- **Discovery Tools**:
  - **Passive Monitoring**: Nozomi, Claroty (listen to network traffic).
  - **Active Scanning**: Risky (can disrupt OT devices); use cautiously (e.g., during maintenance).
- **Why Active Scanning is Dangerous**: Can crash PLCs, cause downtime, or trigger safety systems.

---
---
**OT19** – **MITRE ATT&CK for ICS**:
- **Tactics & Techniques**:
  1. **Initial Access**: Spearphishing (e.g., malicious USB to engineering workstation).
  2. **Lateral Movement**: Modbus writes to PLCs.
  3. **Execution**: Upload malicious ladder logic.
  4. **Impact**: Stop process (e.g., SIS disable).
  5. **Persistence**: Backdoor in HMI software.
- **vs Enterprise ATT&CK**: ICS focuses on physical impacts (e.g., safety, production).
- **Use Case**: Identify gaps (e.g., "Can an attacker move from IT to OT via OPC UA?").

---
---
**OT20** – **Converged IT/OT SOC**:
- **Log Collection**:
  - OT: Passive monitoring (e.g., Nozomi) → SIEM (e.g., Splunk, QRadar).
  - Avoid active polling (risk of disruption).
- **SIEM Integration**: Normalize OT logs (e.g., Modbus, OPC UA) with IT logs.
- **OT-Specific Detection Rules**:
  - Unauthorized PLC firmware changes.
  - Unexpected Modbus function codes (e.g., write to read-only registers).
- **Alert Triage**:
  - **IT Analysts**: Handle IT alerts (e.g., brute force on jump host).
  - **OT Engineers**: Validate OT alerts (e.g., "Is this a real process anomaly?").
- **False Positives**: High in OT (e.g., normal process fluctuations). Use whitelisting and OT-specific baselines.
- **Unauthorized Firmware Change Alert**:
  1. Isolate affected PLC (via firewall/NACL).
  2. Verify firmware hash against known-good baseline.
  3. Coordinate with control room to failover to backup PLC if available.
  4. Forensic analysis on engineering workstation used for upload.
