### **Kubernetes (20 questions)**

**K1** – **Deployment vs. StatefulSet**:
- **Deployment**: Stateless, pods are interchangeable, scaling is dynamic, and updates are rolling. No stable identity (e.g., pod names change).
- **StatefulSet**: Stateful, pods have stable identities (e.g., `pod-0`, `pod-1`), ordered scaling/updates, and persistent storage (e.g., databases like MySQL, Kafka).

**K2** – **ClusterIP Service Routing**:
- A `ClusterIP` Service creates a virtual IP inside the cluster. `kube-proxy` (using `iptables`/`ipvs`) forwards traffic to the Service IP, which load-balances to pod IPs (via `Endpoints` object). Traffic is distributed to all pods labeled by the Service’s selector.

**K3** – **PV, PVC, StorageClass**:
- **PersistentVolume (PV)**: Cluster-wide storage resource (e.g., NFS, AWS EBS) provisioned by an admin.
- **PersistentVolumeClaim (PVC)**: User request for storage (e.g., "I need 10Gi"). Binds to a PV that meets its requirements.
- **StorageClass**: Defines dynamic provisioning (e.g., "fast" SSD vs. "slow" HDD). PVCs can reference a StorageClass to auto-create PVs.
- **Relationship**: PVCs consume PVs; StorageClass enables dynamic PV creation.

**K4** – **Troubleshooting CrashLoopBackOff**:
1. **Logs**: `kubectl logs <pod> --previous` (check crash reason).
2. **Events**: `kubectl describe pod <pod>` (look for OOMKilled, ImagePullBackOff, etc.).
3. **Resource Limits**: Check if the pod exceeds `limits.memory` (OOM) or `limits.cpu` (throttling).
4. **Liveness/Readiness Probes**: Verify probes aren’t failing (e.g., misconfigured endpoints).
5. **Image/Command**: Confirm the container image exists and the entrypoint/command is correct.

**K5** – **CoreDNS Role**:
- CoreDNS provides DNS resolution for cluster services (e.g., `my-service.namespace.svc.cluster.local` → ClusterIP → Pod IPs).
- **If CoreDNS is down**: Pods cannot resolve service names, breaking inter-pod communication. External DNS (e.g., `google.com`) may also fail unless fallback resolvers are configured.

**K6** – **Kubernetes Scheduler**:
1. **Filtering (Predicates)**: Nodes are filtered based on:
   - Resource availability (CPU/memory requests ≤ node capacity).
   - Node affinity/anti-affinity rules.
   - Taints/tolerations (pod must tolerate node taints).
2. **Scoring (Priorities)**: Remaining nodes are ranked by:
   - **Resource utilization**: Prefer nodes with more free resources.
   - **Node affinity**: Higher score if pod matches `preferredDuringSchedulingIgnoredDuringExecution`.
   - **Inter-pod affinity**: Co-locate pods from the same app.
   - **Topology spread**: Distribute pods across zones/nodes.
- The highest-scoring node wins.

**K7** – **Scheduling and Runtime**:
- **Scheduling**: Yes, the pod will be scheduled. The node has 3.5GB requested + 256Mi (new pod) = 3.75GB ≤ 4GB capacity.
- **Runtime**: If the pod uses 600Mi (>512Mi limit), it will be **OOMKilled** and restart (CrashLoopBackOff).

**K8** – **Ingress Request Lifecycle**:
1. **External LB**: Routes traffic to the Ingress Controller (e.g., NGINX) Service (type `LoadBalancer` or `NodePort`).
2. **Ingress Controller**: NGINX evaluates Ingress rules (host/path) and routes to the correct **Service**.
3. **Service**: `ClusterIP` Service load-balances to **Endpoints** (pod IPs).
4. **kube-proxy**: Uses `iptables`/`ipvs` to forward traffic from the Service IP to pod IPs.
5. **Pod**: The application container processes the request.

**K9** – **NetworkPolicy**:
- **Definition**: Controls pod-to-pod traffic (L3/L4 firewall rules).
- **Default Behavior**: If no NetworkPolicy exists, **all traffic is allowed** (open by default).
- **After Applying**: Only traffic matching the policy’s `ingress`/`egress` rules is allowed. Unmatched traffic is **blocked**.

**K10** – **Deployment Strategies**:
- **RollingUpdate**: Gradually replaces old pods with new ones (default). Zero downtime, but old/new versions coexist.
- **Recreate**: **Deletes all old pods before creating new ones**. Use when:
  - The app cannot handle concurrent versions (e.g., database schema changes).
  - You need a clean slate (e.g., config changes requiring full restart).

**K11** – **Namespaces**:
- **Purpose**: Virtual clusters for isolation (e.g., `dev`, `prod`).
- **Default Namespaces**:
  - `default`: Default for objects with no namespace specified.
  - `kube-system`: Kubernetes system components (e.g., CoreDNS, kube-proxy).
  - `kube-public`: Publicly readable config (e.g., cluster info).
  - `kube-node-lease`: Node heartbeats.

**K12** – **`kubectl describe pod`**:
- Shows **detailed info** not in `kubectl get pod`:
  1. **Events**: Errors (e.g., `FailedScheduling`, `OOMKilled`).
  2. **Conditions**: `Ready`, `ContainersReady`, `PodScheduled`.
  3. **Resource Limits/Requests**: CPU/memory allocations.
  4. **Environment Variables**: From ConfigMaps/Secrets.
  5. **Volumes**: Mounted storage.

**K13** – **ConfigMap**:
- **Purpose**: Store non-sensitive configuration (e.g., env vars, config files).
- **Consumption Methods**:
  1. **Environment Variables**: Inject via `envFrom` or `valueFrom`.
  2. **Volume Mounts**: Mount as files in a pod (e.g., `configMapKeyRef`).

**K14** – **Service Types**:
- **ClusterIP**: Internal-only. Accessible within the cluster via the ClusterIP.
- **NodePort**: Exposes the Service on a static port on **every node** (e.g., `30000-32767`). Accessible via `<NodeIP>:<NodePort>`.
- **LoadBalancer**: Creates an external LB (e.g., AWS ELB) that routes to NodePort. Assigns a public IP.

**K15** – **DaemonSet**:
- **Definition**: Ensures **one pod per node** (or subset of nodes via selectors).
- **Use Case**: Node-specific tasks like:
  - Logging agents (e.g., Fluentd).
  - Monitoring agents (e.g., Prometheus Node Exporter).
  - Network plugins (e.g., Calico, kube-proxy).

**K16** – **Taints/Tolerations vs. Node Affinity**:
- **Taints/Tolerations**:
  - **Taint**: Marks a node to repel pods unless they **tolerate** it (e.g., `node-role.kubernetes.io/master:NoSchedule`).
  - **Use Case**: Reserve nodes for specific workloads (e.g., GPU nodes).
- **Node Affinity**:
  - **Required**: Pod **must** run on nodes matching the rule (e.g., `kubernetes.io/arch: amd64`).
  - **Preferred**: Pod **prefers** nodes matching the rule but can run elsewhere.
  - **Use Case**: Schedule pods on nodes with SSDs (`disk: ssd`).

**K17** – **Kubernetes Operator**:
- **Definition**: Custom controller that extends Kubernetes with domain-specific logic (e.g., managing databases, Kafka clusters).
- **Difference from Controller**: Standard controllers (e.g., Deployment) manage Kubernetes-native objects. Operators manage **custom resources** (CRDs) and encode human operational knowledge (e.g., backup, scaling, upgrades).
- **Problems Solved**:
  - Automates complex workflows (e.g., etcd cluster resizing).
  - Handles stateful apps (e.g., MySQL failover).
- **Example**: `etcd-operator` manages etcd clusters (backups, restores, scaling).

**K18** – **etcd Consistency**:
- **Model**: etcd uses **Raft consensus** (strong consistency, linearizable reads).
- **Quorum Loss**: If quorum is lost (e.g., 2/3 nodes down), the cluster **becomes read-only**. Writes fail.
- **Recovery from 2/3 Loss**:
  - **Permanent Loss**: If 2/3 nodes are **permanently** lost, the cluster is **irrecoverable** (Raft requires majority to elect a leader).
  - **Mitigation**: Regular backups (`etcdctl snapshot save`). Restore from snapshot and rebuild the cluster.

**K19** – **RBAC**:
- **Components**:
  - **Role**: Defines permissions **within a namespace** (e.g., `get pods`).
  - **ClusterRole**: Cluster-wide permissions (e.g., `get nodes`).
  - **RoleBinding**: Grants a Role to users/groups **in a namespace**.
  - **ClusterRoleBinding**: Grants a ClusterRole **cluster-wide**.
- **Example Manifests** (read-only access to pods/logs in `dev` namespace):
  ```yaml
  # Role
  apiVersion: rbac.authorization.k8s.io/v1
  kind: Role
  metadata:
    namespace: dev
    name: pod-reader
  rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
  ---
  # RoleBinding
  apiVersion: rbac.authorization.k8s.io/v1
  kind: RoleBinding
  metadata:
    name: dev-pod-reader
    namespace: dev
  subjects:
  - kind: User
    name: "developer"
    apiGroup: rbac.authorization.k8s.io
  roleRef:
    kind: Role
    name: pod-reader
    apiGroup: rbac.authorization.k8s.io
  ```

**K20** – **Slow DNS (ndots)**:
- **Problem**: `/etc/resolv.conf` in pods inherits `ndots:5` from the node. For a query like `myapp`, CoreDNS tries:
  `myapp`, `myapp.dev`, `myapp.dev.svc`, `myapp.dev.svc.cluster`, `myapp.dev.svc.cluster.local` (5 queries).
  If `myapp` is external (e.g., `myapp.com`), all 5 queries fail before trying `myapp.com`, causing delays.
- **Fix**: Set `dnsConfig` in the pod spec to override `ndots`:
  ```yaml
  dnsConfig:
    options:
      - name: ndots
        value: "2"
  ```

### **Development (20 questions)**

**D1** – **git rebase vs. merge**:
- **Rebase**: Rewrites commit history by moving the feature branch’s commits to the tip of `main`. Results in a linear history.
  - **Avoid when**: Rebasing **shared branches** (rewrites history for others).
- **Merge**: Creates a merge commit, preserving branch history (non-linear).
  - **Use when**: Collaborating on a shared branch.

**D2** – **TCP vs. UDP**:
- **TCP**: Connection-oriented, reliable, ordered, error-checked (e.g., HTTP, SSH).
- **UDP**: Connectionless, unreliable, no ordering (e.g., DNS, VoIP).
- **Protocols**:
  - TCP: HTTP, FTP.
  - UDP: DNS, DHCP.

**D3** – **Race Condition**:
- **Definition**: Outcome depends on the **timing/order** of concurrent operations.
- **Example (Python)**:
  ```python
  counter = 0
  def increment():
      global counter
      temp = counter  # Read
      temp += 1       # Modify
      counter = temp  # Write
  ```
  If two threads run `increment()` simultaneously, both may read `counter=0`, then write `1` (expected: `2`).

**D4** – **Symmetric vs. Asymmetric Encryption**:
- **Symmetric**: Same key for encryption/decryption (e.g., AES). Fast but requires secure key exchange.
- **Asymmetric**: Public key (encrypt) + private key (decrypt) (e.g., RSA). Slow but solves key distribution.
- **TLS Usage**:
  - Asymmetric: Exchange a symmetric key (e.g., RSA for key exchange).
  - Symmetric: Encrypt actual data (e.g., AES for bulk encryption).

**D5** – **Container Image Layers**:
- **Layer**: Each `Dockerfile` instruction (e.g., `RUN`, `COPY`) creates a read-only layer. Layers are stacked to form the final image.
- **Caching**: Docker caches layers. If a layer changes (e.g., `COPY . /app`), all subsequent layers are rebuilt.
- **Best Practices**:
  - Order instructions by **least frequently changed** (e.g., `apt-get update` before `COPY`).
  - Use multi-stage builds to reduce final image size.

**D6** – **HTTP 503 Troubleshooting**:
1. **Load Balancer/Proxy**: Check if the LB (e.g., NGINX, ALB) is healthy and not rate-limiting.
2. **Service Health**: Verify backend pods are `Ready` (`kubectl get pods`).
3. **Resource Limits**: Check for OOMKilled pods or CPU throttling (`kubectl describe pod`).
4. **Dependencies**: Are downstream services (DB, cache) available? Check their logs.
5. **Autoscaling**: If using HPA, check if pods are scaling down due to low traffic.

**D7** – **CAP Theorem**:
- **CAP**: In distributed systems, you can only guarantee **2 out of 3**:
  - **Consistency**: All nodes see the same data at the same time.
  - **Availability**: Every request receives a response (even if stale).
  - **Partition Tolerance**: System works despite network partitions.
- **Examples**:
  - **CP (Consistency + Partition Tolerance)**: etcd, MongoDB (with `w:majority`).
  - **AP (Availability + Partition Tolerance)**: Cassandra (with `QUORUM` reads/writes), DynamoDB.

**D8** – **Scaling**:
- **Vertical Scaling**: Increase resources (CPU/RAM) of a single machine.
- **Horizontal Scaling**: Add more machines (nodes/pods).
- **Patterns for Horizontal Scaling**:
  - **Stateless Apps**: Scale pods behind a load balancer.
  - **Microservices**: Decompose into independent services.
  - **Sharding**: Split data across nodes (e.g., by user ID).

**D9** – **Environment Variables**:
- **Definition**: Dynamic values (e.g., `DB_HOST`) that affect process behavior.
- **Persistent Setup (Linux)**:
  - Add to `~/.bashrc` or `/etc/environment`:
    ```bash
    echo 'export MY_VAR="value"' >> ~/.bashrc
    source ~/.bashrc
    ```

**D10** – **JSON vs. YAML**:
- **JSON**: Lightweight, machine-readable, strict syntax (e.g., `{"key": "value"}`).
  - **Advantage**: Universal support (e.g., APIs, web).
- **YAML**: Human-readable, supports comments, indentation-based.
  - **Advantage**: Easier to write/read (e.g., Kubernetes manifests).

**D11** – **REST API**:
- **Definition**: API using HTTP methods to perform CRUD operations on resources (e.g., `/users`).
- **HTTP Methods**:
  - **GET**: Retrieve a resource (idempotent, safe).
  - **POST**: Create a resource (non-idempotent).
  - **PUT**: Replace a resource (idempotent).
  - **DELETE**: Remove a resource (idempotent).

**D12** – **Version Pinning**:
- **Definition**: Specifying exact dependency versions (e.g., `package@1.2.3`) in `package.json`, `requirements.txt`, etc.
- **Importance**: Ensures **reproducible builds** (avoids breaking changes from updates).

**D13** – **Compiled vs. Interpreted**:
- **Compiled**: Code is translated to machine code **before execution** (e.g., C, Go).
- **Interpreted**: Code is executed line-by-line at runtime (e.g., Python, JavaScript).

**D14** – **Reverse Proxy vs. Forward Proxy**:
- **Reverse Proxy**: Sits **in front of servers**, routes client requests to backend services (e.g., NGINX, Traefik).
  - **Use Cases**:
    - Load balancing (NGINX).
    - SSL termination (Traefik).
- **Forward Proxy**: Sits **in front of clients**, forwards requests to external servers (e.g., Squid).
  - **Use Case**: Caching, anonymizing client IPs.

**D15** – **Deadlock**:
- **Definition**: Two+ processes are blocked forever, each waiting for the other’s resource.
- **Coffman Conditions**:
  1. **Mutual Exclusion**: Only one process can use a resource at a time.
  2. **Hold and Wait**: A process holds a resource while waiting for another.
  3. **No Preemption**: Resources cannot be forcibly taken.
  4. **Circular Wait**: A → B → C → A.

**D16** – **Eventual Consistency**:
- **Definition**: If no new updates are made, all nodes will **eventually** converge to the same state.
- **Cassandra Read-After-Write**:
  - **Tunable Consistency**:
    - `ONE`: Fast but may return stale data.
    - `QUORUM`: Majority of replicas must respond (stronger consistency).
    - `ALL`: All replicas must respond (strongest, but slow).
  - **Trade-off**: Higher consistency → higher latency.

**D17** – **mTLS (Mutual TLS)**:
- **Definition**: Both client and server authenticate each other using TLS certificates.
- **Handshake Process**:
  1. Client sends a **ClientHello** (with client cert).
  2. Server validates client cert (against CA) and sends **ServerHello** (with server cert).
  3. Client validates server cert.
  4. Symmetric key exchange (e.g., via RSA or ECDHE).
  5. Encrypted communication begins.
- **Use Cases**:
  - Service-to-service auth in microservices (e.g., Istio, Linkerd).
  - Internal APIs (e.g., database connections).

**D18** – **Hash Table**:
- **Internal Workings**:
  - Uses a **hash function** to map keys to array indices (buckets).
  - **Collision Resolution**:
    - **Chaining**: Each bucket is a linked list of entries.
    - **Open Addressing**: If collision, probe next bucket (e.g., linear probing).
- **Time Complexity**:
  - **Average Case**: O(1) for insert/lookup/delete (good hash function).
  - **Worst Case**: O(n) (all keys hash to the same bucket).

**D19** – **Circuit Breaker**:
- **States**:
  1. **Closed**: Normal operation. Requests pass through.
  2. **Open**: After `N` failures, the breaker **trips**. All requests fail fast (no calls to downstream).
  3. **Half-Open**: After a timeout, a few requests are allowed to test if the service is healthy.
- **Purpose**: Prevents cascade failures by stopping requests to unhealthy services.
- **Relation to Retries**:
  - **Retry Policies**: Retry failed requests (with backoff).
  - **Exponential Backoff**: Wait longer between retries (e.g., 1s, 2s, 4s).
  - **Circuit Breaker**: Stops retries entirely if failures exceed a threshold.

**D20** – **Optimistic vs. Pessimistic Concurrency Control**:
- **Optimistic**:
  - **Approach**: Assume no conflicts. Check for conflicts **at commit time** (e.g., via row versioning).
  - **Example**: PostgreSQL `REPEATABLE READ` with `UPDATE ... WHERE version = old_version`.
  - **Use When**: Low contention (e.g., read-heavy workloads).
- **Pessimistic**:
  - **Approach**: Lock rows **before** modifying (e.g., `SELECT FOR UPDATE`).
  - **Example**: `BEGIN; SELECT * FROM accounts WHERE id=1 FOR UPDATE; UPDATE accounts SET balance=balance-100 WHERE id=1; COMMIT;`
  - **Use When**: High contention (e.g., financial transactions).
