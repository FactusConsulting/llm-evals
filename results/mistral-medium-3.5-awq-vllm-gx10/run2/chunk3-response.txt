### **OpenTofu / Terraform (20 questions)**

---

**T1** – `tofu plan` generates an execution plan (dry run) showing what changes will be made, while `tofu apply` executes the plan to create/update resources. `plan` is read-only; `apply` modifies infrastructure.

---

**T2** – **State** in OpenTofu is a file (e.g., `terraform.tfstate`) that tracks the current state of managed resources. **Remote state** (e.g., S3, DynamoDB) is critical for team collaboration, locking, and disaster recovery, as it centralizes state storage and prevents conflicts.

---

**T3** – `count` creates multiple identical instances of a resource (indexed numerically), while `for_each` iterates over a map/set, assigning a unique key to each instance. **Prefer `for_each`** when:
- You need stable, predictable resource addresses (avoids churn on list reordering).
- You want to reference instances by name (e.g., `each.key`).

---
**T4** – OpenTofu detects **drift** (manual changes) during `plan`/`apply` by comparing the state file with real-world resources. If detected:
- It flags differences and attempts to reconcile them (e.g., revert or update).
- Use `tofu import` to bring unmanaged resources under control.

---
**T5** – Minimal snippet:
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-123456"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

---
**T6** – **`terraform_remote_state`** fetches outputs from another state backend (e.g., S3), while **output values** are for exposing data within the same root module.
- **Recommended alternative**: Use **`data` sources** (e.g., `terraform_data`) or **explicit outputs** with `depends_on` for intra-module sharing.
- **Why?** `terraform_remote_state` is for cross-stack dependencies; outputs are simpler for same-stack use.

---
**T7** – **Problem**: The `null_resource` with `remote-exec` may not complete before the output is read, causing empty `kubeconfig`.
- **Fix**: Use `depends_on` to ensure the `null_resource` finishes first, or add a `local-exec` provisioner to write the output to a file and read it back.

---
**T8** – **`tofu import`** (CLI) imports existing resources into state but **does not generate configuration** (manual effort required).
- **Limitations**: No automatic code generation; complex resources may need manual adjustments.
- **`import` block (1.5+)** improves this by allowing **declarative imports** in HCL, making it repeatable and version-controlled.

---
**T9** – A **variable** (`variable` block) is an input parameter for a module (e.g., `ami_id`). An **output** (`output` block) exposes data (e.g., a VM’s IP) for other modules to use.
- **Difference**: Variables are inputs; outputs are exports.

---
**T10** – A **provider** (e.g., `aws`, `google`) is a plugin that interacts with APIs to manage resources.
- Running `tofu plan` without `tofu init` fails because providers and modules are not downloaded/initialized.

---
**T11** – `.terraform.lock.hcl` records the exact provider versions and checksums used. **Commit it** to ensure reproducibility and avoid version conflicts.

---
**T12** – `tofu destroy` deletes all resources in the state file.
- **Target a single resource**: `tofu destroy -target=aws_instance.web[0]`.

---
**T13** – A **data source** fetches read-only information (e.g., an existing VPC’s ID) without managing it.
- **Example**: Use `aws_vpc` data source to reference an existing VPC instead of creating a new one with `aws_vpc` resource.

---
**T14** – **`locals`** are internal variables for calculations (e.g., `local.prefix = "prod"`), while **`variable`** blocks define inputs.
- **Use `locals`** for derived values (e.g., `local.full_name = "${var.prefix}-${var.name}"`).

---
**T15** – **`lifecycle`** block controls resource behavior:
- **`create_before_destroy`**: Creates a new resource before destroying the old (e.g., blue-green deployments).
- **`prevent_destroy`**: Blocks deletion (e.g., critical databases).
- **`ignore_changes`**: Prevents OpenTofu from modifying certain attributes (e.g., `ignore_changes = [tags]`).

---
**T16** – **`moved`** block refactors resource addresses (e.g., moving `aws_instance.web` to a module) **without recreating resources**.
- Example:
  ```hcl
  moved {
    from = aws_instance.web
    to   = module.web.aws_instance.web
  }
  ```

---
**T17** – OpenTofu builds a **dependency graph** to determine execution order.
- **Implicit dependencies**: Inferred from references (e.g., `aws_instance.web` depends on `aws_vpc.main` if referenced).
- **Explicit dependencies**: Defined via `depends_on`.
- **Tradeoff**: `depends_on` reduces parallelism (slower applies) and should be avoided unless necessary.

---
**T18** – Strategies to reduce `plan` time:
1. **State splitting**: Split into smaller states (e.g., by environment). *Tradeoff*: More complex dependency management.
2. **Remote state caching**: Use a backend with caching (e.g., Terraform Cloud). *Tradeoff*: Cost for cloud services.
3. **`-refresh=false`**: Skip refreshing state (use cached data). *Tradeoff*: Risk of drift.
4. **Module isolation**: Use `terraform_remote_state` for cross-module data. *Tradeoff*: Added complexity.

---
**T19** – **State locking** prevents concurrent modifications (e.g., via DynamoDB for S3 backend).
- **If lock is stuck**: Manually delete the lock entry (e.g., DynamoDB item or `terraform.tflock` file).
- **Risks**: Deleting a lock may cause corruption if another process is active.

---
**T20** – **Migration steps**:
1. **Backup** the local state file (`terraform.tfstate`).
2. **Configure remote backend** in `backend` block (S3 + DynamoDB).
3. Run `tofu init` to migrate state to S3.
4. **Verify**: Check S3 bucket for the state file and DynamoDB for the lock table.
5. **Test**: Run `tofu plan` to confirm no changes are detected.

### **Ansible (20 questions)**

---
**A1** –
- **Playbook**: YAML file containing a series of **plays** (e.g., `site.yml`).
- **Role**: Reusable collection of plays, tasks, vars, etc. (e.g., `roles/nginx`).
- **Task**: A single action (e.g., `apt: name=nginx`).

---
**A2** – `ansible_facts` are system information gathered by the `setup` module (e.g., OS, IP).
- Access OS family: `{{ ansible_facts['os_family'] }}` or `{{ ansible_os_family }}`.

---
**A3** –
- **`command`**: Runs a command **without shell features** (e.g., pipes, `&&`). Safer but limited.
- **`shell`**: Runs in a shell (supports pipes, variables). *Use when*: Need shell features (e.g., `grep`, `&&`).
- **`raw`**: Sends raw commands **without Ansible’s module system** (e.g., for non-Python targets like network devices).

---
**A4** – **Idempotency** means a task can be run repeatedly without changing the system after the first successful run.
- **Idempotent**: `apt: name=nginx state=present` (installs only if missing).
- **Not idempotent**: `command: echo "hello" >> /tmp/file` (appends on every run).

---
**A5** –
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_facts['os_family'] == "Debian"

- name: Install epel-release and htop (RedHat)
  package:
    name: "{{ item }}"
    state: present
  loop: [epel-release, htop]
  when: ansible_facts['os_family'] == "RedHat"
```

---
**A6** – **Variable precedence** (highest to lowest):
1. `extra_vars` (CLI: `-e` or `--extra-vars`).
2. `set_fact` (runtime facts).
3. `host_vars` (host-specific).
4. `group_vars` (group-specific).
5. Role defaults (`roles/<role>/defaults/main.yml`).

---
**A7** – **Structure**:
1. **Inventory groups**: Split nodes into `rke2_first3` and `rke2_rest`.
2. **Playbook**:
   ```yaml
   - hosts: rke2_first3
     serial: 3  # Run on all 3 first
     tasks:
       - name: Install RKE2 agent
         # ...
   - hosts: rke2_rest
     tasks:
       - name: Wait for first 3 nodes
         wait_for:
           host: "{{ item }}"
           port: 6443
           timeout: 300
         loop: "{{ groups['rke2_first3'] | map('extract', hostvars) | map(attribute='ansible_host') | list }}"
       - name: Install RKE2 agent
         # ...
   ```

---
**A8** – **`ansible-vault`** encrypts sensitive data (e.g., passwords).
- **Encrypt a single variable** in a vars file:
  ```yaml
  db_password: !vault |
    $ANSIBLE_VAULT;1.1;AES256
    66386439653636353834643566386335...
  ```
  Use `ansible-vault encrypt_string` to generate the encrypted value.

---
**A9** – **Inventory file** defines target hosts (e.g., `inventory.ini`).
- **Static inventory**: Manually maintained (e.g., INI or YAML).
- **Dynamic inventory**: Generated at runtime (e.g., from AWS, Kubernetes).

---
**A10** – Ad-hoc command:
```bash
ansible webservers -a "df -h"
```

---
**A11** – A **handler** is a task triggered by another task (e.g., restarting a service).
- **Difference**: Handlers run **only once** at the end of the playbook, even if notified multiple times.
- **Trigger**: Use `notify` in a task:
  ```yaml
  - name: Update nginx config
    copy:
      src: nginx.conf
      dest: /etc/nginx/nginx.conf
    notify: Restart nginx

  handlers:
    - name: Restart nginx
      service:
        name: nginx
        state: restarted
  ```

---
**A12** – **`ansible.cfg`** is the configuration file for Ansible defaults.
- **Common settings**:
  - `inventory`: Default inventory file path.
  - `remote_user`: Default SSH user.
  - `forks`: Number of parallel connections (default: 5).

---
**A13** – **`register`** captures a task’s output into a variable.
- **Usage**:
  ```yaml
  - name: Check file exists
    stat:
      path: /tmp/file
    register: file_stat

  - name: Print file size
    debug:
      msg: "File size is {{ file_stat.stat.size }}"
  ```

---
**A14** –
- **`include_tasks`**: Dynamically includes tasks **at runtime** (evaluates conditionals when included).
- **`import_tasks`**: Statically imports tasks **at parse time** (faster, but conditionals are evaluated when the playbook is parsed).
- **Use `include_tasks`** when tasks are conditionally included (e.g., based on a variable).

---
**A15** – **Ansible Galaxy** is a repository for sharing roles/collections.
- **`requirements.yml`** example:
  ```yaml
  roles:
    - name: geerlingguy.nginx
  collections:
    - name: community.general
  ```
  Install with: `ansible-galaxy install -r requirements.yml`.

---
**A16** – **Connection plugins** define how Ansible communicates with hosts:
- **`ssh`**: Default for Linux (uses SSH).
- **`local`**: Runs tasks on the control node (e.g., for local provisioning).
- **`network_cli`**: For network devices (e.g., Cisco, Juniper) via CLI.
- **Use cases**:
  - `ssh`: Most Linux/Unix hosts.
  - `local`: Local tasks (e.g., file operations on the control node).
  - `network_cli`: Network switches/routers.

---
**A17** –
- **`delegate_to`**: Runs a task on a **specific host** (e.g., a database server).
- **`run_once`**: Ensures the task runs **only once** (on the first host in the batch).
- **Example**: Run a task on `localhost` using data from a remote host:
  ```yaml
  - name: Gather remote host data
    command: hostname
    register: remote_hostname
    delegate_to: remote_host

  - name: Process data on control node
    debug:
      msg: "Remote host is {{ remote_hostname.stdout }}"
    run_once: true
    delegate_to: localhost
  ```

---
**A18** – **Performance strategies**:
1. **Forks**: Increase parallelism (e.g., `forks: 50` in `ansible.cfg`). *Tradeoff*: Higher CPU/memory usage.
2. **Pipelining**: Reduces SSH connections (enable in `ansible.cfg`). *Tradeoff*: Requires `requiretty` disabled on targets.
3. **Fact caching**: Cache `ansible_facts` (e.g., Redis, JSON files). *Tradeoff*: Stale data if hosts change.
4. **Mitogen**: Uses Python for faster execution. *Tradeoff*: Complex setup; not all modules supported.

---
**A19** – **Jinja2 templating**:
- `{{ }}`: **Variable interpolation** (e.g., `{{ nginx_port }}`).
- `{% %}`: **Control structures** (e.g., `{% for server in servers %}`).
- `{# #}`: **Comments**.
- **Example template** (`nginx_upstream.conf.j2`):
  ```jinja2
  upstream backend {
    {% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }};  # Health check: {{ server.health_check }}
    {% endfor %}
  }
  ```

---
**A20** – **Zero-downtime rolling deployment**:
```yaml
- hosts: webservers
  serial: 4  # 4 servers at a time (20 servers / 5 batches)
  pre_tasks:
    - name: Remove server from load balancer
      uri:
        url: "http://lb/api/remove/{{ ansible_host }}"
        method: POST
      delegate_to: localhost
      run_once: true

  tasks:
    - name: Deploy new app version
      copy:
        src: app_v2.tar.gz
        dest: /opt/app/
      notify: Restart app

    - name: Health check
      uri:
        url: "http://{{ ansible_host }}:8080/health"
        return_content: yes
      register: health_check
      until: health_check.status == 200
      retries: 5
      delay: 10

  post_tasks:
    - name: Add server back to load balancer
      uri:
        url: "http://lb/api/add/{{ ansible_host }}"
        method: POST
      delegate_to: localhost
      run_once: true

  handlers:
    - name: Restart app
      service:
        name: app
        state: restarted

  # Rollback on failure
  block:
    - name: Deploy tasks (from above)
      # ...
  rescue:
    - name: Revert to old version
      copy:
        src: app_v1.tar.gz
        dest: /opt/app/
      notify: Restart app
    - name: Re-add to load balancer
      uri:
        url: "http://lb/api/add/{{ ansible_host }}"
        method: POST
      delegate_to: localhost
      run_once: true
```
