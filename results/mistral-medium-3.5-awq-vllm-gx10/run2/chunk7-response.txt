### **Application Architecture (20 questions)**

---

**AA1**
- **Monolith vs. Microservices**: A monolith is a single, self-contained application with tightly coupled components, while microservices break the application into loosely coupled, independently deployable services.
- **3 Problems Microservices Introduce**:
  1. **Distributed Complexity**: Network latency, retries, and partial failures (e.g., handling timeouts between services).
  2. **Operational Overhead**: Managing deployments, monitoring, and debugging across many services (e.g., tracing requests across 10+ services).
  3. **Data Consistency**: Distributed transactions require patterns like Saga or eventual consistency (e.g., inventory and order services may desync).

---

**AA2**
- **Synchronous**: The caller waits for a response (blocking). Example: REST/HTTP (e.g., a frontend calling a backend API).
- **Asynchronous**: The caller sends a request and continues processing; the response arrives later (non-blocking). Example: Kafka (event-driven) or RabbitMQ (message queues).

---

**AA3**
- **API Gateway**: A reverse proxy that also handles request routing, rate limiting, authentication, and protocol translation (e.g., gRPC ↔ HTTP). Often includes request/response transformation.
- **Reverse Proxy**: Forwards requests to backend servers (e.g., Nginx, HAProxy) but lacks advanced features like request transformation or API-specific routing.
- **Can an API Gateway replace a reverse proxy?** No, because reverse proxies are simpler and more performant for basic load balancing. API Gateways add overhead for advanced features.

---

**AA4**
- **Saga Pattern**: Manages distributed transactions by breaking them into local transactions coordinated via events or commands.
  - **Choreography**: Services emit events and react to them (e.g., Order Service emits "OrderCreated," Payment Service reacts by processing payment). Decentralized but harder to debug.
  - **Orchestration**: A central orchestrator (e.g., a workflow engine) tells services what to do (e.g., "Reserve Inventory," then "Process Payment"). Easier to debug but introduces a single point of failure.
- **When to use**:
  - Choreography: Simple workflows, low coupling.
  - Orchestration: Complex workflows, need for compensation logic (rollbacks).

---

**AA5**
- **CQRS**: Separates reads (queries) and writes (commands) into different models. Reads use optimized data stores (e.g., Redis), writes use a transactional store (e.g., PostgreSQL).
- **Event Sourcing**: Stores state changes as a sequence of immutable events (e.g., "OrderCreated," "PaymentProcessed"). The current state is derived by replaying events.
- **Why pair them?**
  - CQRS + Event Sourcing enables:
    - **Auditability**: Full history of changes.
    - **Scalability**: Read/Write paths scale independently.
    - **Flexibility**: Rebuild projections (read models) from events.
  - **Problem solved**: Traditional CRUD struggles with complex domain logic (e.g., undoing actions, temporal queries) and scaling reads/writes differently.

---

**AA6**
- **Circuit Breaker**: Prevents cascading failures by stopping requests to a failing service after a threshold of failures.
  - **States**:
    1. **Closed**: Normal operation (requests pass through).
    2. **Open**: Fails fast (returns errors immediately).
    3. **Half-Open**: Tests if the service has recovered (allows limited requests).
  - **vs. Retry with Backoff**: Retries assume transient failures; Circuit Breaker assumes prolonged failure. Use both: Retry for transient issues (e.g., network blips), Circuit Breaker for prolonged outages (e.g., service down).

---

**AA7**
| **Model**                     | **Cost** | **Security**       | **Operational Complexity** | **Noisy-Neighbor Risk** | **Use Case**                     |
|-------------------------------|----------|--------------------|----------------------------|-------------------------|----------------------------------|
| Shared DB, Shared Schema      | Low      | Low (row-level leaks) | Low                        | High                    | Simple SaaS, low isolation needs |
| Shared DB, Separate Schema    | Medium   | Medium (schema leaks) | Medium (schema management) | Medium                  | Multi-tenant with moderate isolation |
| Separate DB per Tenant        | High     | High (full isolation) | High (DB sprawl)          | Low                     | High-security (e.g., healthcare) |

- **Trade-offs**:
  - Shared schema: Cheapest but risk of data leaks (e.g., misconfigured tenant ID).
  - Separate schema: Better isolation but harder to manage (e.g., schema migrations).
  - Separate DB: Best isolation but expensive (e.g., 1000 tenants = 1000 DBs).

---

**AA8**
- **Eventual vs. Strong Consistency**:
  - **Eventual**: Replicas converge over time (e.g., DynamoDB, Cassandra).
  - **Strong**: All replicas are consistent at all times (e.g., PostgreSQL with synchronous replication).
- **Inventory System (No Overselling)**:
  - **Consistency Model**: Strong consistency (linearizability).
  - **Data Store**: PostgreSQL (ACID) or etcd (distributed lock for inventory counts).
  - **Patterns**:
    - **Pessimistic Locking**: Lock inventory rows during checkout (e.g., `SELECT FOR UPDATE`).
    - **Distributed Locks**: Use Redis Redlock or ZooKeeper for cross-service coordination.
    - **Idempotency**: Ensure retries don’t double-count (e.g., idempotency keys).
  - **At Scale**: Shard inventory by product ID + use a distributed lock manager (e.g., Redis Cluster).

---

**AA9**
- **Sidecar Proxy**: A proxy deployed alongside each service (e.g., Envoy in Istio) to handle cross-cutting concerns (e.g., mTLS, retries, metrics).
- **Envoy in Istio**:
  - **Data Plane**: Envoy sidecars handle traffic (L4/L7 proxying, load balancing).
  - **Control Plane**: Istiod (Istio’s control plane) configures Envoy via xDS (e.g., routes, certificates).
- **mTLS vs. App-Level TLS**:
  - **mTLS (Sidecar)**: Transparent to the app; managed by the mesh. Solves:
    - **Service Identity**: Certificates tied to service accounts (not IPs).
    - **Fine-Grained Control**: Per-service policies (e.g., "only allow A→B").
  - **App-Level TLS**: Requires app code to manage certs/keys; harder to rotate or enforce policies.

---

**AA10**
- **Strangler Fig Pattern**: Incrementally replace a monolith by routing traffic to new services while keeping the old system running.
- **Migration Strategy for .NET Framework → .NET 8 Microservices**:
  1. **Identify Boundaries**: Split monolith into domains (e.g., Orders, Inventory).
  2. **API Gateway**: Deploy a gateway (e.g., Ocelot, YARP) to route requests to old/new services.
  3. **Extract Services**:
     - Start with a non-critical module (e.g., Notifications).
     - Deploy as a .NET 8 service behind the gateway.
  4. **Data Isolation**:
     - Use the **Database per Service** pattern (new services get their own DB).
     - For shared data, use **Anti-Corruption Layer** (translate old/new models).
  5. **Traffic Shift**:
     - Use feature flags to route % of traffic to new services.
     - Monitor for errors/latency.
  6. **Decommission**: Once a module is fully migrated, retire its monolith code.

---

**AA11**
- **12-Factor App**: Methodology for cloud-native apps. Key factors:
  1. **Codebase**: One codebase per app (multiple deploys).
  2. **Dependencies**: Explicitly declare (e.g., `nuget`, `npm`).
  3. **Config**: Store in environment variables (not code).
  4. **Backing Services**: Treat databases as attached resources (e.g., connection strings in env vars).
  5. **Build, Release, Run**: Separate stages (e.g., CI/CD pipelines).
  6. **Processes**: Stateless, share-nothing (e.g., no local sessions).
  7. **Port Binding**: Export services via ports (e.g., `http://0.0.0.0:8080`).
  - **Why it matters**: Enables scalability, portability, and resilience in cloud environments (e.g., Kubernetes).

---

**AA12**
| **Aspect**            | **Event-Driven (Kafka)**               | **Request-Driven (REST/gRPC)**       |
|-----------------------|---------------------------------------|--------------------------------------|
| **Coupling**          | Loose (producers/consumers decoupled) | Tight (client knows server API)      |
| **Scalability**       | High (async, backpressure)            | Limited by server capacity           |
| **Debugging**         | Hard (distributed traces, event logs) | Easier (request/response logs)       |
| **Ordering**          | Per-partition (Kafka)                 | Per-request (no global ordering)     |
| **Failure Handling**  | Retries, dead-letter queues           | Retries, circuit breakers            |
- **Choose Event-Driven**:
  - High throughput (e.g., clickstream analytics).
  - Decoupled services (e.g., order processing → notification).
- **Choose Request-Driven**:
  - Simple, synchronous workflows (e.g., user login).
  - Low-latency needs (e.g., API gateways).

---

**AA13**
- **Load Balancer**: Distributes traffic across servers to improve availability and performance.
- **Layer 4 (Transport)**: Routes based on IP/port (e.g., TCP/UDP). Example: HAProxy (L4 mode).
- **Layer 7 (Application)**: Routes based on HTTP headers, paths, or cookies (e.g., Nginx, ALB). Example: Host-based routing (`example.com/api` → Service A).
- **L7 Required**: When you need content-based routing (e.g., `/images` → CDN, `/api` → backend).

---

**AA14**
- **Message Queue (RabbitMQ)**: Temporary storage for messages; consumers pull messages (e.g., task queues). **Pull-based**.
- **Log-Based Broker (Kafka)**: Immutable, ordered log; consumers subscribe to streams. **Push-based**.
- **When to Pick**:
  - **RabbitMQ**: Simple workloads, competing consumers (e.g., background jobs).
  - **Kafka**: High-throughput, replayable streams (e.g., event sourcing, analytics).

---

**AA15**
- **Container**: Lightweight, shares host OS kernel (e.g., Docker). Uses namespaces/cgroups for isolation.
- **VM**: Full OS virtualization (e.g., KVM, VMware). Higher overhead but stronger isolation.
- **Why Containers for Microservices**:
  - Faster startup, lower resource usage.
  - Consistent environments (dev/prod parity).
  - Easy orchestration (Kubernetes).

---

**AA16**
- **Stateless**: No local session data (e.g., REST API). Scales horizontally by adding more instances.
- **Stateful**: Maintains local state (e.g., WebSocket server, session-affinity load balancing).
- **Example**:
  - Stateless: API Gateway.
  - Stateful: WebSocket chat server.

---

**AA17**
- **ORM**: Maps objects to database tables (e.g., SQLAlchemy for Python, Entity Framework for .NET).
- **Trade-offs**:
  - **Pros**: Faster development, database-agnostic, reduces SQL injection risk.
  - **Cons**: Performance overhead (e.g., N+1 queries), limited control over complex queries.

---

**AA18**
- **Bulkhead Pattern**: Isolates critical resources (e.g., thread pools, DB connections) to prevent one service from starving others.
- **Example**:
  - **Thread Pools**: Reserve a pool for Service A and another for Service B.
  - **Deployment Groups**: Deploy Service A on Node Group 1, Service B on Node Group 2.
- **Relation to Microservices**: Prevents cascading failures (e.g., a slow DB query in Service A won’t block Service B).

---

**AA19**
| **Aspect**            | **Operational Transformation (OT)**       | **CRDTs**                              |
|-----------------------|------------------------------------------|----------------------------------------|
| **Consistency**       | Strong (linearizable)                    | Eventual (conflict-free)               |
| **Latency**           | Higher (requires central authority)      | Lower (peer-to-peer)                   |
| **Complexity**        | High (transform functions)               | Medium (predefined data types)         |
| **Offline Support**   | Limited (needs sync on reconnect)        | Full (merges changes automatically)    |
- **Choice for Offline Editing**: **CRDTs** (e.g., Google Docs uses OT, but CRDTs are better for offline-first apps like mobile note-taking).

---

**AA20**
- **Challenges of Distributed Tracing in Polyglot Systems**:
  - **Context Propagation**: Use W3C Trace Context (standard headers: `traceparent`, `tracestate`) or B3 (Zipkin’s format).
  - **Sampling**:
    - **Head-Based**: Decide at the start of a request (e.g., sample 1% of traces).
    - **Tail-Based**: Decide at the end (e.g., only keep traces with errors).
  - **Storage/Querying**: Jaeger (open-source), Tempo (Grafana), or cloud (AWS X-Ray).
  - **Async Messaging (Kafka)**:
    - **Problem**: Trace context is lost when a message is published.
    - **Solution**: Inject trace headers into Kafka message headers (e.g., `traceparent: 00-...`).

### **On-Premise Infrastructure Architecture (20 questions)**

---

**OP1**
- **Type 1 (Bare-Metal)**: Runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V).
- **Type 2 (Hosted)**: Runs on top of a host OS (e.g., VirtualBox, VMware Workstation).
- **Examples**:
  - Type 1: ESXi, KVM.
  - Type 2: VirtualBox, Parallels.

---

**OP2**
- **SAN (Storage Area Network)**:
  - **Use Case**: Block-level storage for high-performance apps (e.g., databases).
  - **Protocols**: Fibre Channel (FC), iSCSI.
- **NAS (Network-Attached Storage)**:
  - **Use Case**: File-level storage (e.g., shared documents).
  - **Protocols**: NFS, SMB/CIFS.

---

**OP3**
- **3-Tier Architecture**:
  - **Core**: High-speed backbone (e.g., 10Gbps switches).
  - **Distribution**: Aggregates access layer traffic (e.g., L3 routing, ACLs).
  - **Access**: Connects end devices (e.g., 1Gbps switches).
- **Leaf-Spine**:
  - **Why Preferred**: Non-blocking, lower latency, and higher scalability.
  - **Problem Solved**: 3-tier has oversubscription (e.g., 10Gbps core → 1Gbps access = bottleneck). Leaf-spine provides full bisectional bandwidth.

---

**OP4**
- **Proxmox Cluster with Shared Storage**:
  - **Node Count**: 3+ (quorum requires odd number; 3 for HA).
  - **Quorum**: Uses Corosync. If quorum is lost, the cluster stops to prevent split-brain.
  - **Fencing (STONITH)**: Power off a failed node (e.g., via IPMI) to prevent data corruption.
  - **Shared Storage Options**:
    - **Ceph**: Distributed, scalable, but complex (requires monitor nodes).
    - **iSCSI**: Simple, but single point of failure (unless multi-path).
    - **NFS**: Easy to set up, but performance may lag for VMs.
  - **Node Failure**:
    - VMs on the failed node are migrated to healthy nodes (if shared storage is available).
    - If storage is local, VMs on the failed node are down until recovery.

---

**OP5**
- **VLAN Trunking**: Allows a single physical link to carry traffic for multiple VLANs.
- **802.1Q Tagging**: Adds a VLAN ID (tag) to Ethernet frames.
- **Linux Configuration (Single NIC, 3 VLANs)**:
  ```bash
  # Create a trunk interface (e.g., eth0)
  ip link add link eth0 name eth0.10 type vlan id 10
  ip link add link eth0 name eth0.20 type vlan id 20
  ip link add link eth0 name eth0.30 type vlan id 30
  # Assign IPs (or use DHCP)
  ip addr add 192.168.10.1/24 dev eth0.10
  ip addr add 192.168.20.1/24 dev eth0.20
  ip addr add 192.168.30.1/24 dev eth0.30
  # Bring up interfaces
  ip link set eth0.10 up
  ip link set eth0.20 up
  ip link set eth0.30 up
  ```

**OP7**
- **DNS Architecture for 500-Person Enterprise**:
  - **Internal AD**:
    - **Authoritative Servers**: 2x Windows DNS servers (AD-integrated) for `internal.example.com`.
    - **Recursive Resolvers**: 2x internal DNS servers (forwarders to external).
  - **DMZ**:
    - **Authoritative Servers**: 2x external DNS servers (e.g., BIND) for `public.example.com` (DNSSEC-signed).
    - **Split-Horizon**: Internal clients resolve `app.example.com` to private IPs; external resolves to public IPs.
  - **Forwarders**: Internal DNS forwards external queries to ISP or public DNS (e.g., 8.8.8.8).
  - **Conditional Forwarding**: For internal zones, forward to AD DNS.
  - **Laptop Behavior**:
    - **Office**: Uses internal DNS (via DHCP).
    - **VPN**: Uses VPN-provided DNS (split-tunnel or full-tunnel).

**OP8**
- **PKI Chain of Trust**:
  - Root CA (offline) → Subordinate CA (issuing) → End-Entity Certificate.
- **Internal PKI Deployment**:
  - **Root CA**: Offline, stored in a HSM (e.g., YubiHSM).
  - **Subordinate CA**: Online, issues certs (e.g., Windows AD CS).
  - **CRL vs. OCSP**:
    - **CRL**: Static list of revoked certs (downloadable).
    - **OCSP**: Real-time revocation checks (faster but requires online responder).
  - **Certificate Templates**: Predefined for servers, users, etc.
  - **Auto-Enrollment**: GPO for domain-joined machines.
- **Compromise Impact**:
  - **Subordinate CA**: Revoke and reissue all certs from it.
  - **Root CA**: Rebuild entire PKI (catastrophic).

**OP10**
- **iDRAC/iLO/IPMI**: Out-of-band (OOB) management interfaces for remote server control (power, BIOS, KVM).
- **Why Critical**:
  - Reboot servers without physical access.
  - Monitor hardware health (e.g., temperature, PSU status).
- **Risk of Internet Exposure**:
  - Attackers can gain full control (e.g., power off servers, change BIOS settings).
  - **Mitigation**: Restrict IPMI to a dedicated management VLAN; use strong passwords or certificates.

**OP11**
| **Feature**       | **LVM**               | **LVM-Thin**          | **ZFS**               |
|-------------------|-----------------------|-----------------------|-----------------------|
| **Snapshots**     | COW (Copy-on-Write)   | COW, space-efficient  | COW, writable         |
| **Thin Provisioning** | No (unless thin LV) | Yes                   | Yes                   |
| **Data Integrity** | No (relies on FS)     | No                    | Yes (checksums)       |
| **Use Case**      | Simple volume mgmt    | Dynamic allocation    | Data integrity, NAS   |
- **When to Use**:
  - **LVM**: Basic volume management (e.g., extending partitions).
  - **LVM-Thin**: Overcommit storage (e.g., VMs with varying usage).
  - **ZFS**: High reliability (e.g., backup server with checksums).

**OP12**
- **Stretch Cluster/DR for Proxmox + Ceph**:
  - **Ceph CRUSH Rules**: Configure to replicate data across sites (e.g., `osd` placement groups across Site A and Site B).
  - **Monitor Placement**: Deploy monitors in both sites (odd number, e.g., 3: 2 in Site A, 1 in Site B).
  - **Network Latency**: Ceph requires <10ms latency for synchronous replication (use **async** for >10ms).
  - **Split-Brain Problem**: If sites lose connectivity, Ceph may stop writing to avoid divergence. **Solution**: Use a **tiebreaker** (e.g., a 3rd site or cloud-based monitor).
  - **Why 2-Site Ceph is Bad**: Without a tiebreaker, a network partition can cause both sites to go read-only.

**OP13**
- **DHCP DORA Process**:
  1. **Discover**: Client broadcasts `DHCPDISCOVER`.
  2. **Offer**: Server responds with `DHCPOFFER` (IP, subnet, lease time).
  3. **Request**: Client requests the offered IP (`DHCPREQUEST`).
  4. **Acknowledge**: Server confirms (`DHCPACK`).
- **Lease Expiry (No DHCP Server)**:
  - Windows client continues using the IP until:
    - **50% of lease time**: Tries to renew.
    - **87.5% of lease time**: Rebroadcasts `DHCPDISCOVER`.
    - **100%**: Releases IP and stops using it (falls back to APIPA: 169.254.x.x).

**OP14**
- **Managed vs. Unmanaged Switch**:
  - **Unmanaged**: Plug-and-play, no configuration (e.g., home switches).
  - **Managed**: Supports VLANs, QoS, STP, monitoring (e.g., Cisco Catalyst).
- **Enterprise Features**:
  - VLANs (traffic isolation).
  - STP (prevents loops).
  - QoS (prioritizes VoIP traffic).
  - Mirroring (for packet capture).

---

**OP15**
- **NTP**: Synchronizes clocks across devices (e.g., `ntpd`, `chronyd`).
- **Why Critical**:
  - **Kerberos**: Requires time sync within 5 minutes.
  - **Logs**: Correlate events across servers.
  - **Clustering**: Prevents split-brain (e.g., Ceph, Pacemaker).
- **Drift Issues**:
  - **Ceph**: Clock skew can cause MONs to reject each other.
  - **AD**: Kerberos tickets fail if time is out of sync.

**OP16**
| **Type**          | **Isolation** | **Performance** | **Use Case**                     |
|-------------------|---------------|-----------------|----------------------------------|
| Physical Server   | High          | Highest         | High-security (e.g., PCI DSS)   |
| VM                | Medium        | Medium          | General workloads                |
| Container         | Low           | High            | Microservices, stateless apps    |
- **Bare Metal When**:
  - **Performance**: Low-latency (e.g., HFT trading).
  - **Licensing**: Software tied to physical hardware.
  - **Security**: Air-gapped systems.

**OP17**
- **UPS**: Short-term power (minutes to hours) for graceful shutdowns.
- **Generator**: Long-term power (days) for extended outages.
- **ATS (Automatic Transfer Switch)**: Switches load from UPS to generator when UPS battery is low.
- **Why Both**:
  - UPS bridges the gap until the generator starts (generators take ~10-30 seconds to kick in).

**OP18**
- **Active-Passive**: One node active, others standby (e.g., PostgreSQL with hot standby).
- **Active-Active**: Both nodes handle traffic (e.g., PostgreSQL with BDR or CockroachDB).
- **PostgreSQL HA with Pacemaker/Corosync**:
  - **Resources**:
    - **Virtual IP (VIP)**: Floats between nodes.
    - **PostgreSQL**: Managed as a resource (start/stop scripts).
  - **Fencing (STONITH)**: IPMI or PDU to power off failed nodes.
  - **Failover**:
    1. Primary fails → Corosync detects via heartbeat.
    2. STONITH fences the failed node.
    3. VIP moves to standby node.
    4. PostgreSQL promotes standby to primary.

**OP19**
- **Backup Strategy for 50-Server Environment**:
  - **3-2-1 Rule**: 3 copies, 2 media types, 1 offsite.
  - **RPO/RTO**:
    - **RPO**: 1 hour (hourly incrementals).
    - **RTO**: 4 hours (tested restores).
  - **Backup Types**:
    - **Full**: Weekly.
    - **Incremental**: Hourly (back up changes since last full/incremental).
    - **Differential**: Daily (back up changes since last full).
  - **Storage**:
    - **Disk**: Fast, for recent backups (e.g., NAS).
    - **Tape**: Cheap, long-term (e.g., LTO-8).
    - **Cloud**: Offsite (e.g., AWS S3 Glacier).
  - **Immutable Backups**: WORM (Write Once, Read Many) storage (e.g., tape, S3 Object Lock) to prevent ransomware tampering.
  - **Testing**: Monthly restore tests (e.g., spin up a VM from backup).
  - **Backup vs. DR**:
    - **Backup**: Restore individual files/servers.
    - **DR**: Full environment recovery (e.g., new site after fire).

**OP20**
- **802.1X (Port-Based NAC)**:
  - **Roles**:
    - **Supplicant**: Client device (e.g., laptop).
    - **Authenticator**: Switch (enforces access).
    - **Authentication Server**: RADIUS (e.g., FreeRADIUS, Windows NPS).
  - **EAP Methods**:
    - **EAP-TLS**: Certificate-based (most secure).
    - **PEAP**: Password-based (uses TLS tunnel for MS-CHAPv2).
  - **Dynamic VLAN Assignment**: RADIUS returns a VLAN ID based on user/group (e.g., HR users → VLAN 10).
  - **Failed Authentication**: Port is placed in a **quarantine VLAN** (e.g., no internet access) or disabled.
  - **MAB (MAC Authentication Bypass)**:
    - For devices without 802.1X (e.g., printers, IoT).
    - Switch sends the device’s MAC address to RADIUS for authentication.
    - **Risk**: MAC spoofing (mitigate with port security).
