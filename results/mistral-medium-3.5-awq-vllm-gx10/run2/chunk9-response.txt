### **SC1 — Broken Deployments After Cluster Upgrade**

#### **SC1-A**
The pods fail because the **Restricted Pod Security Standard** (enforced post-upgrade) requires explicit `runAsUser` when `runAsNonRoot: true` is set. The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`, but Kubernetes blocks this under Restricted mode if no non-root user is specified.
- **Baseline vs. Restricted**: Baseline allows root users if no `securityContext` is set, but Restricted enforces non-root execution and requires explicit UID/GID.
- **Interaction**: The container’s `USER root` conflicts with `runAsNonRoot: true` (which expects a non-root user). Without `runAsUser`, the pod violates Restricted and is rejected.

#### **SC1-B**
```bash
kubectl get pods --all-namespaces --field-selector=status.phase=CrashLoopBackOff -o json | jq -r '.items[] | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.securityContext}'
```

#### **SC1-C**
**Immediate Fix**:
- Rebuild images with `USER 1000` (non-root) or add `runAsUser: 1000` to `securityContext`.
**Manifest Changes**:
- Explicitly set `runAsUser` and `fsGroup` in all deployments.
**CI Gate**:
- Add a policy check (e.g., OPA Gatekeeper) to block manifests with `runAsNonRoot: true` but no `runAsUser`.
**Rollout**:
- Use `kubectl rollout restart` with a canary deployment to avoid downtime.

### **SC2 — Cross-Region Database Failover Gone Wrong**

#### **SC2-A**
- **Stale Data**: Promoting an async replica risks replication lag. PostgreSQL’s WAL shipping is asynchronous across regions, so the replica may be seconds/minutes behind. Data loss window = time between last WAL send and promotion.
- **Check**: Query `pg_stat_replication` for `replay_lag` and `last_activity` on the replica.

#### **SC2-B**
```bash
# Import the promoted replica into Terraform state
terraform import aws_db_instance.new_primary <REPLICA_ARN>
# Update references in other resources (e.g., Route53)
terraform state mv aws_db_instance.old_primary aws_db_instance.old_primary_backup
# Apply changes without recreation
terraform apply -target=aws_db_instance.new_primary
```

#### **SC2-C**
- **Architecture**:
  - Use **Aurora Global Database** (sync replication, RPO <1s).
  - Replace PgBouncer with **RDS Proxy** (handles failover transparently).
  - Route53 health checks + DNS failover (TTL=30s).
  - Application retries with exponential backoff.
- **Why Aurora**: Built-in cross-region sync replication and automated failover.

### **SC4 — Migrating a Stateful Monolith to Kubernetes**

#### **SC4-A**
| **Blocker**               | **Problem**                          | **Solution**                          |
|---------------------------|--------------------------------------|---------------------------------------|
| Sticky sessions           | F5 affinity breaks in K8s            | Use Redis for shared sessions.        |
| Local NFS mounts          | Stateful pods need persistent storage | Use `ReadWriteMany` NFS CSI driver.   |
| Oracle 19c dependency     | Not cloud-native                     | Migrate to RDS/Aurora PostgreSQL.     |
| IBM MQ integration        | Legacy protocol                      | Use MQ Kubernetes Operator.           |
| Java 11 monolith          | Hard to scale                        | Decompose into microservices.         |

#### **SC4-B**
```hcl
variable "nfs_server" { type = string }
variable "nfs_path" { type = string }
variable "storage_size" { type = string }

resource "kubernetes_storage_class" "nfs" {
  metadata { name = "nfs-csi" }
  storage_provisioner = "nfs.csi.k8s.io"
  parameters = { server = var.nfs_server, path = var.nfs_path }
}

resource "kubernetes_persistent_volume" "nfs_pv" {
  metadata { name = "nfs-pv" }
  spec {
    capacity = { storage = var.storage_size }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source { nfs { server = var.nfs_server, path = var.nfs_path } }
  }
}

resource "kubernetes_persistent_volume_claim" "nfs_pvc" {
  metadata { name = "nfs-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    resources { requests = { storage = var.storage_size } }
    storage_class_name = kubernetes_storage_class.nfs.metadata[0].name
  }
}
```
**Why `ReadWriteMany`**: Multiple pods (e.g., NFS clients) need concurrent write access.

#### **SC4-C**
**Phased Migration**:
1. **Phase 1**: Deploy new K8s ingress alongside F5 (traffic split 10% to K8s).
   - Use **Strangler Fig**: Route `/api/*` to K8s, legacy paths to F5.
2. **Phase 2**: Migrate IBM MQ to K8s Operator (test with 50% traffic).
3. **Phase 3**: Cutover sessions to Redis, NFS to CSI, and decommission F5.
**Rollback**: Revert DNS to F5 if p99 latency >2s.
**Metrics**: Track error rates, latency, and MQ queue depth.

**SQL Diagnostic Query**:
```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocking_locks.pid AS blocking_pid,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS blocking_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks
  ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.DATABASE IS NOT DISTINCT FROM blocked_locks.DATABASE
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
  AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
  AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
  AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
  AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
  AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
  AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.GRANTED;
```

### **SC7 — CI/CD Pipeline Causing Production Drift**

#### **SC7-A**
1. **Manual `tofu apply`**:
   - **Risk**: State file corruption if concurrent applies; drift from Git.
   - **Scenario**: Two engineers apply changes simultaneously → state lock conflict → one apply overwrites the other.
2. **Diverged Helm Values**:
   - **Risk**: Untracked config changes (e.g., staging vs. prod).
3. **`kubectl edit`**:
   - **Risk**: ConfigMaps revert on `helm upgrade` (if not in Git).

#### **SC7-B**
```yaml
stages:
  - validate
  - plan
  - apply

validate:
  stage: validate
  script:
    - tofu fmt -check
    - tofu validate

plan:
  stage: plan
  script:
    - tofu plan -out=tfplan
    - terraform show -json tfplan | jq -r '.planned_values' > plan.json
  artifacts:
    paths: [tfplan, plan.json]

apply_prod:
  stage: apply
  script:
    - tofu apply -lock=true -lock-address=dynamodb://terraform-lock -auto-approve
  when: manual
  environment: production
```

#### **SC7-C**
- **Drift Detection**:
  - Schedule `tofu plan` in CI (nightly) and alert on changes.
- **Admission Control**:
  - **OPA Gatekeeper**: Block `kubectl edit` on ConfigMaps with `deny-edit` policy.
- **Helm Values**:
  - Use **Helmfile** with `environments/` overrides (e.g., `values-prod.yaml`).
- **RBAC**:
  - Kubernetes: Restrict `edit`/`apply` to CI service account.
  - AWS: IAM policy allowing only `s3:GetObject`/`s3:PutObject` on state bucket.

### **SC9 — Securing a Public-Facing API After a Breach**

#### **SC9-A**
| **Vulnerability**         | **OWASP Category**       | **Blast Radius**               | **Fix**                                  |
|---------------------------|--------------------------|--------------------------------|------------------------------------------|
| BOLA                      | API1:2019 (Broken Auth)  | Data leakage (all user records) | Django object-level permissions:         |

**Django BOLA Fix**:
```python
from rest_framework import permissions

class IsOwnerOrReadOnly(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.owner == request.user or request.method in permissions.SAFE_METHODS

class UserRecordViewSet(viewsets.ModelViewSet):
    permission_classes = [IsOwnerOrReadOnly]
    def get_object(self):
        obj = super().get_object()
        self.check_object_permissions(self.request, obj)
        return obj
```

### **SC10 — Designing a Multi-Cluster Disaster Recovery Platform**

#### **SC10-A**
| **Approach**               | **RPO/RTO Met?** | **PostgreSQL**               | **Redis**               | **RabbitMQ**            | **MinIO**                     |
|----------------------------|------------------|------------------------------|-------------------------|-------------------------|-------------------------------|
| **Active-Passive (Velero)** | RPO: 15m (yes)   | Async WAL shipping (RPO <15m) | Redis Sentinel (async)  | Federation (async)      | MinIO bucket replication (RPO ~1m) |
|                            | RTO: 1h (yes)    | Velero restore + Patroni     | Manual failover         | Manual failover         | `mc admin replicate`           |
| **Active-Active (Istio)**  | RPO: <1s (yes)   | Aurora Global DB (sync)      | Redis Cluster (multi-region) | Shovel plugin (sync) | MinIO multi-site replication   |
|                            | RTO: <1h (yes)   | Automatic                    | Automatic               | Automatic               | Automatic                     |

**Recommendation**: **Active-Active with Istio** (meets RPO/RTO; 12ms latency is acceptable for sync replication).

#### **SC10-C**
**Failover Sequence**:
1. **Detection**:
   - **Site Down**: Use **BGP health checks** (Chicago → Dallas) + **Prometheus Blackbox Exporter** (ping `kube-apiserver`).
   - **False Positive Avoidance**: Require 3/5 probes to fail over 30s.
2. **Order of Operations**:
   - **Step 1**: Promote Dallas PostgreSQL (Patroni auto-failover).
   - **Step 2**: Failover Redis Sentinel (`SENTINEL failover`).
   - **Step 3**: Failover RabbitMQ (promote Dallas node to master).
   - **Step 4**: Update MinIO replication (Dallas becomes primary).
   - **Step 5**: DNS failover (Route53 GSLB with health checks).
   - **Step 6**: Update OpenTofu state (import Dallas resources).
3. **Split-Brain Handling**:
   - **STONITH**: Use **fencing** (e.g., AWS API to power off Chicago nodes).
   - **Quorum**: Patroni/etcd requires 3/5 nodes to agree on primary.
4. **Failback**:
   - **Step 1**: Restore Chicago site.
   - **Step 2**: Sync data (PostgreSQL: `pg_basebackup`; MinIO: `mc replicate`).
   - **Step 3**: Rejoin Chicago as standby (Patroni: `patronictl reinit`).
   - **Step 4**: DNS failback (Route53 health checks auto-revert).
