### **Cloud Infrastructure Architecture**

---

**CL1** – **IaaS (Infrastructure as a Service)**: Provides virtualized computing resources (VMs, storage, networking). Example: AWS EC2.
**PaaS (Platform as a Service)**: Provides a managed platform for deploying applications (OS, middleware, runtime). Example: AWS Elastic Beanstalk.
**SaaS (Software as a Service)**: Delivers fully managed applications. Example: Microsoft 365.

---

**CL2** – **Shared Responsibility Model**:
- **IaaS VMs**: Provider manages hardware, hypervisor, and physical security. Customer manages OS, apps, data, and network config.
- **Managed Kubernetes (EKS/AKS)**: Provider manages control plane (API server, etcd). Customer manages worker nodes, pods, and app security.
- **SaaS (M365)**: Provider manages everything (app, data, OS, infrastructure). Customer manages user access, data classification, and compliance.

---

**CL3** –
- **VPC**: Isolated virtual network in the cloud.
- **Subnet**: Segment of a VPC with a CIDR range (public/private).
- **Security Group**: Stateful firewall for instances (allow/deny rules based on source/destination).
- **NACL**: Stateless firewall for subnets (explicit deny rules, no return traffic tracking).
**Layering**: VPC → Subnets → NACLs (subnet-level) → Security Groups (instance-level).
**Stateful vs Stateless**: Security Groups track connection state (e.g., allow return traffic). NACLs do not.

---

**CL4** – **Multi-Account Strategy**:
- **Landing Zone**: Pre-configured baseline (guardrails, networking, IAM) for new accounts.
- **Organizational Units (OUs)**: Group accounts by function (e.g., Dev, Prod, Security).
- **Guardrails**: SCPs (Service Control Policies) to enforce compliance (e.g., no public S3 buckets).
- **Shared Networking**: AWS Transit Gateway (hub-and-spoke) or Azure Virtual WAN for cross-account connectivity.
- **Centralized Logging**: Aggregate logs (CloudTrail, Azure Monitor) to a security account.
**Single-Account Problems**: No isolation, blast radius for breaches, harder to enforce least privilege, and difficult cost allocation.

---

**CL5** – **Infrastructure as Code (IaC)**:
- **Terraform/OpenTofu**: Declarative, multi-cloud, stateful (manages state file).
- **Pulumi**: Imperative (code in Python/Go), multi-cloud, supports custom logic.
- **CloudFormation/Bicep**: AWS/Azure-native, declarative, tightly integrated with provider services.
- **Crossplane**: Extends Kubernetes API to manage cloud resources (control plane for IaC).
**When to Use**:
- Terraform: Multi-cloud, complex dependencies.
- Pulumi: Need programmatic logic.
- CloudFormation: AWS-only, deep integration.
- Crossplane: Kubernetes-centric IaC.

---

**CL6** –
- **HPA (Horizontal Pod Autoscaler)**: Scales pods based on CPU/memory or custom metrics.
- **VPA (Vertical Pod Autoscaler)**: Adjusts CPU/memory requests/limits for pods.
- **Cluster Autoscaler**: Adds/removes nodes based on pod demand.
- **KEDA (Kubernetes Event-Driven Autoscaling)**: Scales based on external events (e.g., RabbitMQ queue length).
**Use KEDA over HPA**: When scaling is driven by event sources (e.g., messages in a queue) rather than resource utilization.

---

**CL7** – **Disaster Recovery (DR) Strategy**:
- **RPO (Recovery Point Objective)**: Max acceptable data loss (e.g., 5 minutes).
- **RTO (Recovery Time Objective)**: Max acceptable downtime (e.g., 1 hour).
- **Active-Active**: Both regions serve traffic (synchronous DB replication, global load balancing).
- **Active-Passive**: Primary region active; secondary on standby (asynchronous DB replication).
- **Database Replication**:
  - Sync: No data loss (e.g., AWS Aurora Global Database).
  - Async: Potential data loss (e.g., DynamoDB Global Tables).
- **DNS Failover**: Route53 (AWS) or Traffic Manager (Azure) with health checks.
- **State Management**: Stateless apps in both regions; stateful apps use shared storage (e.g., S3, DynamoDB).
- **Cost Implications**: Active-active is expensive (2x resources); pilot light is cheapest (minimal standby).
**DR Strategies**:
- **Pilot Light**: Minimal infrastructure in DR region (scale up on failure).
- **Warm Standby**: Partial capacity in DR region (faster recovery).
- **Multi-Site Active-Active**: Full redundancy (highest cost, lowest RTO/RPO).

---

**CL8** – **GitOps**:
- **Model**: Declarative infrastructure/app definitions in Git. Tools (ArgoCD/FluxCD) sync Git state to cluster.
- **ArgoCD vs FluxCD**:
  - ArgoCD: UI, RBAC, app-of-apps pattern.
  - FluxCD: Simpler, Git-native, supports Kustomize/Helm.
- **Secrets Management**:
  - Sealed Secrets: Encrypt secrets in Git (decrypted by controller).
  - External Secrets Operator: Fetches secrets from Vault/AWS Secrets Manager.
  - Vault: Dynamic secrets, lease management.
- **Drift Handling**: Tools detect manual changes and revert to Git state (or alert).

---

**CL9** – **Stateful Legacy App on Kubernetes**:
- **StatefulSet**: Manages pod identities (stable hostnames, ordered startup).
- **PV/PVC with Local Storage Class**: Persistent volumes tied to nodes (low latency).
- **Headless Service**: Direct pod DNS resolution (no load balancing).
- **Init Containers**: Prep filesystem (e.g., copy config files to paths).
- **ConfigMaps as Volume Mounts**: Inject configs into specific paths.
- **Pod Disruption Budget (PDB)**: Ensures minimum pods available during disruptions.

---
**CL10** –
- **Service Account**: Kubernetes identity for pods (used for in-cluster auth).
- **Workload Identity (Azure)**: Maps Kubernetes service accounts to Azure AD identities (no static credentials).
- **IRSA (IAM Roles for Service Accounts, AWS)**: Assigns IAM roles to service accounts (OIDC-based).
**Why Not Mount Credentials**: Static credentials risk exposure; workload identity federation (OIDC) provides short-lived tokens.
**Workload Identity Federation**: Uses OIDC to dynamically fetch cloud provider credentials (e.g., AWS STS, Azure AD).

---
**CL11** –
- **Object Storage (S3/Blob)**: Unstructured data (files, backups), high durability (11 9s), eventual consistency.
- **Block Storage (EBS/Managed Disk)**: Low-latency volumes for VMs/DBs (e.g., EBS gp3).
- **File Storage (EFS/Azure Files)**: Shared file systems (NFS/SMB), multi-node access.
**When to Use**:
- Object: Static assets, backups.
- Block: Databases, VM disks.
- File: Shared configs, home directories.

---
**CL12** – **Zero-Trust Kubernetes Architecture**:
- **Network Policies**: Restrict pod-to-pod traffic (Calico/Cilium).
- **Service Mesh (mTLS)**: Istio/Linkerd for encrypted pod communication.
- **Pod Identity**: Assign identities to pods (e.g., Azure Workload Identity).
- **Admission Controllers**: OPA/Kyverno to enforce policies (e.g., no privileged pods).
- **Image Signing**: Cosign/Notary to verify container images.
- **Runtime Security**: Falco for anomaly detection (e.g., shell in container).
- **Secrets Management**: Vault or Kubernetes Secrets (encrypted at rest).
**vs Perimeter Model**: Zero-trust assumes breach; verifies every request (no implicit trust).

---
**CL13** – **CDN (Content Delivery Network)**:
- **How It Works**: Distributes content to edge locations (POPs) closer to users, reducing latency.
- **Cloud-Native CDNs**: AWS CloudFront, Azure Front Door.
- **When to Use CDN**: Static assets (images, JS), global audiences, high traffic.
- **When Not to Use**: Dynamic content, real-time data (use origin server).

---
**CL14** –
- **Availability Zone (AZ)**: Isolated data center within a region (e.g., us-east-1a).
- **Region**: Geographic area with multiple AZs (e.g., us-east-1).
- **Multi-AZ Deployment**: High availability (e.g., RDS Multi-AZ).
- **Zonal vs Regional Resources**:
  - Zonal: Tied to one AZ (e.g., EBS volume).
  - Regional: Span multiple AZs (e.g., S3, DynamoDB).

---
**CL15** – **Managed Database Service (RDS/Cloud SQL/Azure SQL)**:
- **Provider Handles**: Patching, backups, HA (Multi-AZ), scaling, monitoring.
- **Self-Managed on VM**: Customer handles OS, DB software, backups, and failover.

---
**CL16** –
- **IAM Users**: Individual accounts (e.g., `alice@company`).
- **Groups**: Collection of users (e.g., `Developers`).
- **Roles**: Temporary permissions (e.g., `EC2-ReadOnly`).
- **Policies**: JSON documents defining permissions (e.g., `s3:GetObject`).
**Principle of Least Privilege**: Grant minimal permissions required; audit regularly.

---
**CL17** – **Serverless Computing**:
- **AWS Lambda/Azure Functions/GCP Functions**: Event-driven, ephemeral execution.
- **Cold Starts**: Delay when function initializes (mitigate with provisioned concurrency).
- **Poor Fit**: Long-running tasks, high-performance computing, stateful apps.

---
**CL18** – **Kubernetes Ingress Options**:
- **Ingress Resource**: L7 HTTP routing (host/path-based).
- **Gateway API**: Extended Ingress (multi-protocol, advanced routing).
- **Cloud Load Balancer Annotations**: Directly configure ALB/NLB (e.g., AWS ALB Ingress Controller).
- **Service Mesh Ingress Gateway**: Istio/Linkerd for L7 traffic with mTLS.
**TLS Termination**:
- Ingress: Terminate at ingress controller (simpler).
- Gateway API: Terminate at gateway or backend.
- Service Mesh: Terminate at ingress gateway (end-to-end encryption).
**Use Gateway API**: For advanced use cases (e.g., gRPC, WebSockets, multi-team ownership).

---
**CL19** – **Cost Optimization Strategy ($80K/month)**:
- **Reserved Instances/Savings Plans**: Commit to 1- or 3-year terms for predictable workloads (e.g., 40% savings).
- **Spot/Preemptible Instances**: For fault-tolerant workloads (e.g., batch jobs).
- **Right-Sizing**: Use tools (AWS Compute Optimizer) to match instance types to usage.
- **Storage Tiering**: Move infrequent data to S3 IA/Glacier; use Intelligent-Tiering.
- **Idle Resource Detection**: Shut down unused VMs (e.g., AWS Instance Scheduler).
- **FinOps Practices**: Tag resources, allocate costs to teams, set budgets.
- **Showback/Chargeback**: Report costs to teams (showback) or bill them (chargeback).
**Tools**: AWS Cost Explorer, Azure Cost Management, Kubecost (Kubernetes).

---
**CL20** – **Multi-Cloud Strategy (AWS + Azure)**:
- **Abstraction Layers**: Use Terraform for IaC, Kubernetes (EKS/AKS) for workloads.
- **Networking**: VPN or direct interconnect (AWS Direct Connect + Azure ExpressRoute).
- **Identity Federation**: SAML/OIDC (e.g., Azure AD + AWS IAM).
- **Trade-Offs**:
  - **Benefits**: Avoid lock-in, leverage best-of-breed services.
  - **Challenges**: Complexity, networking latency, inconsistent APIs, higher costs.
**When Justified**: Regulatory requirements, critical workload redundancy.
**When Unnecessary**: Most workloads can run in a single cloud with proper DR.

### **OT Infrastructure Architecture**

---
**OT1** – **Purdue Model (ISA-95)**:
- **Level 0 (Physical Process)**: Sensors, actuators (e.g., temperature probes).
- **Level 1 (Basic Control)**: PLCs, RTUs (direct control of physical processes).
- **Level 2 (Supervisory Control)**: HMIs, SCADA (monitor/control Level 1).
- **Level 3 (Site Operations)**: Historian, MES (manufacturing execution systems).
- **Level 4 (Site Business)**: ERP, scheduling (business systems).
- **Level 5 (Enterprise)**: Corporate IT (finance, HR).

---
**OT2** – **IT vs OT Networks**:
- **IT**: General-purpose, frequent patching, high bandwidth, tolerance for downtime.
- **OT**: Real-time, deterministic, high availability (99.999%), legacy systems, patching risks downtime.
**Why No Standard IT Patching**: OT systems often run 24/7; patches may break compatibility or cause unplanned downtime.

---
**OT3** – **IDMZ (Industrial DMZ)**:
- **Role**: Buffer zone between IT (Level 4) and OT (Levels 0-3).
- **Allowed Traffic**:
  - **IT → OT**: Read-only (e.g., historian data to ERP).
  - **OT → IT**: Alerts, logs, process data (e.g., SCADA to MES).
- **Danger of Direct IT→Level 1**: Malware/ransomware could disrupt control systems (e.g., Stuxnet).

---
**OT4** – **OT Protocols & Purdue Levels**:
1. **Modbus TCP**: Level 1-2 (PLC communication).
2. **OPC UA**: Level 2-3 (secure, platform-independent data exchange).
3. **EtherNet/IP (CIP)**: Level 1-2 (industrial Ethernet for automation).
4. **PROFINET**: Level 1-2 (Siemens industrial Ethernet).
5. **MQTT**: Level 3-4 (lightweight pub/sub for telemetry).

---
**OT5** – **Data Diode vs Firewall**:
- **Data Diode**: Hardware-enforced one-way communication (e.g., OT → IT for logs).
  - **Use Case**: High-security environments (e.g., nuclear plants).
  - **Limitation**: No bidirectional traffic (e.g., cannot send commands back).
- **Firewall**: Bidirectional, but requires strict rules (risk of misconfiguration).

---
**OT6** – **SCADA to Cloud Data Flow**:
1. **Historian (Level 3)**: Stores process data (e.g., OSIsoft PI).
2. **OPC UA Server**: Exposes historian data.
3. **MQTT Broker (Edge Gateway)**: Publishes data to cloud (e.g., AWS IoT Core).
4. **Edge Gateway**: Filters/aggregates data, applies security (TLS, auth).
5. **Cloud Ingestion**: AWS Kinesis/Azure Event Hubs → analytics (e.g., Time Series DB).
**Security Boundaries**:
- Firewall between SCADA and edge gateway.
- TLS for MQTT/OPC UA.
- IAM for cloud access.

---
**OT7** – **IEC 62443 Zones & Conduits**:
- **Zone**: Group of assets with similar security requirements (e.g., "PLC Zone").
- **Conduit**: Secure channel between zones (e.g., firewall rule allowing OPC UA traffic).
**Manufacturing Plant Model**:
- **Zone 1**: Corporate Network (IT).
- **Zone 2**: Engineering Workstations (Level 3).
- **Zone 3**: SCADA Servers (Level 2).
- **Zone 4**: PLCs (Level 1).
- **Zone 5**: Safety Instrumented Systems (SIS) (isolated).
**Conduits**:
- Firewall between Zone 1 and Zone 2 (allow HTTPs for MES).
- Data diode from Zone 3 to Zone 1 (logs only).

---
**OT8** – **Network Segmentation for Flat L2 Plant**:
- **VLAN Design**:
  - VLAN 10: PLCs (Level 1).
  - VLAN 20: HMIs (Level 2).
  - VLAN 30: SCADA/Historian (Level 3).
  - VLAN 40: Engineering Workstations.
- **Firewall Placement**: Between VLANs (e.g., Palo Alto/NGFW).
- **Switch Architecture**: Layer 3 switches for inter-VLAN routing (no L2 flooding).
- **Vendor Access**: Jump host in DMZ with MFA; no direct RDP to HMIs.
- **Transition Plan**:
  1. Inventory all devices (passive monitoring).
  2. Deploy firewalls in "monitor-only" mode.
  3. Gradually enforce policies (e.g., block inter-VLAN traffic by default).
  4. Test during maintenance windows.

---
**OT9** – **SIS vs BPCS**:
- **BPCS (Basic Process Control System)**: Normal operation (e.g., PLCs controlling valves).
- **SIS (Safety Instrumented System)**: Emergency shutdown (e.g., failsafe valves).
- **IEC 61511**: Standard for SIS design/operation.
- **Why Air-Gap SIS**: SIS must operate independently to avoid common-mode failures (e.g., ransomware disabling both BPCS and SIS).
- **Ransomware Impact on SIS**: Could disable safety mechanisms → catastrophic failure (e.g., chemical release).

---
**OT10** – **PLC vs DCS vs SCADA**:
- **PLC (Programmable Logic Controller)**: Ruggedized, real-time control for discrete processes (e.g., assembly line).
- **DCS (Distributed Control System)**: Centralized control for continuous processes (e.g., oil refinery).
- **SCADA (Supervisory Control and Data Acquisition)**: Monitoring/control for large-scale, geographically dispersed systems (e.g., water treatment).
**Coexistence**: Yes; e.g., DCS for process control + SCADA for monitoring + PLCs for local logic.

---
**OT11** – **Remote Access Architecture**:
- **Jump Host**: Bastion server in DMZ (no direct access to OT).
- **MFA**: Required for all remote sessions.
- **Session Recording**: Log all vendor/engineer actions (e.g., CyberArk).
- **Vendor Access**: Time-limited, just-in-time (JIT) access via VPN + jump host.
- **Why No Direct RDP to HMI**: Exposes OT to corporate network threats (e.g., malware).

---
**OT12** – **Detection & Response Plan (Water Treatment Compromise)**:
- **Network Monitoring**:
  - IDS (e.g., Nozomi, Dragos) for OT-specific threats.
  - Anomaly detection (e.g., unexpected Modbus writes).
- **Asset Inventory**: Passive monitoring (e.g., Tenable.ot) to identify all devices.
- **Incident Response**:
  1. Isolate Level 3 network (disconnect from Level 4).
  2. Verify SIS integrity (air-gapped?).
  3. Coordinate with control room to switch to manual operation if needed.
  4. Forensic analysis on compromised systems.
- **Plant Operator Role**: Follow emergency procedures, confirm physical safety, report anomalies.

---
**OT13** – **HMI (Human-Machine Interface)**:
- **Role**: Graphical interface for operators to monitor/control processes (e.g., touchscreen in control room).
- **vs Engineering Workstation**: HMI is for operators; engineering workstation is for programming/configuring PLCs/SCADA.

---
**OT14** – **Historian**:
- **Role**: Time-series database for process data (e.g., temperature, pressure).
- **Plant Historian (Level 3)**: Local, high-resolution data for operations.
- **Enterprise Historian (Level 4)**: Aggregated data for analytics/ERP.

---
**OT15** – **Ladder Logic**:
- **Definition**: Graphical programming language for PLCs (resembles relay logic).
- **Device**: Executed by PLCs.
- **Why Still Dominant**: Intuitive for electricians, standardized (IEC 61131-3), real-time execution.

---
**OT16** – **RTU (Remote Terminal Unit)**:
- **Definition**: Ruggedized device for remote monitoring/control (e.g., oil pipelines).
- **vs PLC**: RTUs are simpler, designed for harsh environments, and often use serial/modem comms.
- **Typical Use**: Utilities (water, gas), telemetry in remote locations.

---
**OT17** – **Analog vs Digital Signals**:
- **Analog (4-20mA, 0-10V)**: Continuous signals (e.g., temperature sensors).
- **Digital**: Discrete (on/off) or binary (e.g., relay status).
- **Why 4-20mA**: 4mA = live zero (detects wire breaks); immune to electrical noise.

---
**OT18** – **OT Asset Inventory**:
- **Foundation**: Critical for security (can’t protect what you don’t know).
- **Discovery Tools**:
  - **Passive Monitoring**: Nozomi, Claroty (listen to network traffic).
  - **Active Scanning**: Risky (can crash PLCs); only during maintenance windows.
- **Why Active Scanning is Dangerous**: May disrupt real-time operations (e.g., Modbus scans can stop a conveyor belt).

---
**OT19** – **MITRE ATT&CK for ICS**:
- **Tactics & Techniques**:
  1. **Initial Access**: Spear-phishing (e.g., malicious USB to engineering workstation).
  2. **Lateral Movement**: Exploit weak passwords on HMIs.
  3. **Execution**: Upload malicious ladder logic to PLC.
  4. **Impact**: Stop process (e.g., open/close valves erratically).
  5. **Persistence**: Backdoor in firmware.
- **vs Enterprise ATT&CK**: ICS focuses on physical impacts (safety, availability).
- **Use Case**: Identify gaps (e.g., no network segmentation between Levels 1-2).

---
**OT20** – **Converged IT/OT SOC**:
- **Log Collection**:
  - OT: Passive monitoring (no agents on PLCs); forward logs via edge gateways.
  - IT: Traditional agents (e.g., Splunk Universal Forwarder).
- **SIEM Integration**: Correlate IT/OT logs (e.g., failed login on HMI + unusual Modbus traffic).
- **OT-Specific Detection Rules**:
  - Unauthorized firmware changes.
  - Unexpected process value changes (e.g., pressure spike).
- **Alert Triage**:
  - **IT Analysts**: Handle IT alerts (e.g., malware on engineering workstation).
  - **OT Engineers**: Validate OT alerts (e.g., "Is this a real process anomaly?").
- **False Positives**: High in OT (e.g., normal maintenance may trigger alerts); tune rules with OT team input.
- **Unauthorized PLC Firmware Change**:
  1. Isolate affected PLC (via firewall/NACL).
  2. Verify firmware hash against known-good baseline.
  3. Coordinate with control room to failover to backup PLC.
  4. Forensic analysis on the device.
