### **Application Architecture (20 questions)**

---

**AA1**
- **Monolith vs. Microservices**: A monolith is a single, self-contained application with tightly coupled components, while microservices break the application into loosely coupled, independently deployable services.
- **3 Problems Microservices Introduce**:
  1. **Distributed Complexity**: Network latency, retries, and partial failures (e.g., handling timeouts between services).
  2. **Operational Overhead**: Managing deployments, monitoring, and debugging across many services (e.g., tracing requests across 10+ services).
  3. **Data Consistency**: Distributed transactions require patterns like Saga or eventual consistency (e.g., inventory and order services may desync).

---

**AA2**
- **Synchronous Communication**: The caller waits for a response (blocking). Example: REST/HTTP (e.g., a frontend calling a backend API).
- **Asynchronous Communication**: The caller sends a request and continues without waiting. Example: Kafka (publish-subscribe) or RabbitMQ (message queues).

---

**AA3**
- **API Gateway**: A reverse proxy that also handles request routing, rate limiting, authentication, and protocol translation (e.g., gRPC ↔ HTTP). Often includes features like request/response transformation.
- **Reverse Proxy**: Forwards requests to backend servers (e.g., Nginx, HAProxy) but lacks advanced API-specific features.
- **Can an API Gateway replace a reverse proxy?** No, because reverse proxies are simpler and more performant for basic load balancing. API Gateways add overhead for advanced features. Use both: reverse proxy for L7 load balancing, API Gateway for API management.

---

**AA4**
- **Saga Pattern**: Manages distributed transactions by breaking them into local transactions coordinated via events or commands.
  - **Choreography**: Services emit events (e.g., "OrderCreated") and react to them (e.g., "ReserveInventory"). Decentralized but harder to debug.
  - **Orchestration**: A central orchestrator (e.g., a workflow engine) tells services what to do. Easier to debug but introduces a single point of failure.
- **When to Use**:
  - Choreography: Simple workflows, low coupling.
  - Orchestration: Complex workflows, need for compensation logic (e.g., rollbacks).

---

**AA5**
- **CQRS**: Separates reads (queries) and writes (commands) into different models. Reads use optimized data stores (e.g., Redis), writes use a transactional store (e.g., PostgreSQL).
- **Event Sourcing**: Stores state changes as a sequence of events (e.g., "InventoryDecreased"). CQRS + Event Sourcing allows rebuilding state from events and provides an audit log.
- **Problem Solved**: Traditional CRUD struggles with complex domain logic (e.g., auditing, temporal queries). CQRS + Event Sourcing enables scalability (read/write separation) and historical analysis.

---

**AA6**
- **Circuit Breaker**: Prevents cascading failures by stopping requests to a failing service after a threshold of failures.
  - **States**:
    1. **Closed**: Normal operation.
    2. **Open**: Fails fast (returns errors immediately).
    3. **Half-Open**: Tests if the service has recovered.
- **vs. Retry with Backoff**: Retries assume transient failures; Circuit Breaker assumes prolonged failure. Use both: retry for transient issues (e.g., network blips), Circuit Breaker for prolonged outages.

---

**AA7**
| **Model**                     | **Cost** | **Security**       | **Operational Complexity** | **Noisy-Neighbor Risk** |
|-------------------------------|----------|--------------------|----------------------------|-------------------------|
| Shared DB, Shared Schema      | Low      | Low (row-level leaks) | Low                        | High (shared resources) |
| Shared DB, Separate Schema    | Medium   | Medium (schema isolation) | Medium (schema management) | Medium (DB-level contention) |
| Separate DB per Tenant        | High     | High (full isolation) | High (DB sprawl)          | Low (dedicated resources) |

- **Trade-offs**:
  - Shared schema: Cheapest but riskiest (e.g., a misconfigured query could expose cross-tenant data).
  - Separate DB: Most secure but expensive (e.g., 10,000 tenants = 10,000 DBs).

---

**AA8**
- **Eventual Consistency**: Data will eventually sync (e.g., Kafka consumers).
- **Strong Consistency**: All nodes see the same data at the same time (e.g., PostgreSQL with `SERIALIZABLE`).
- **Inventory System Design**:
  - **Consistency Model**: Strong consistency (to prevent overselling).
  - **Data Store**: PostgreSQL (ACID transactions) or etcd (distributed lock for inventory counts).
  - **Patterns**:
    - **Pessimistic Locking**: Lock inventory rows during checkout.
    - **Optimistic Locking**: Use version numbers to detect conflicts.
    - **Distributed Lock**: Redis Redlock or PostgreSQL advisory locks.
  - **At Scale**: Shard by product ID + use a distributed lock manager (e.g., Apache ZooKeeper).

---

**AA9**
- **Sidecar Proxy**: A proxy deployed alongside each service (e.g., Envoy in Istio) to handle cross-cutting concerns (e.g., mTLS, retries, metrics).
- **Envoy in Istio**:
  - **Data Plane**: Envoy sidecars handle traffic (L4/L7).
  - **Control Plane**: Istiod manages Envoy configs (e.g., routing rules, certificates).
- **mTLS vs. App-Level TLS**:
  - **mTLS (Sidecar)**: Transparent to the app; enforces service-to-service encryption without code changes.
  - **App-Level TLS**: Requires app code to manage certs; harder to enforce uniformly.

---

**AA10**
- **Strangler Fig Pattern**: Incrementally replace a monolith by routing traffic to new services while keeping the old system running.
- **Migration Strategy**:
  1. **Edge Routing**: Deploy an API Gateway (e.g., Nginx) to route requests to either the monolith or new services.
  2. **Extract Services**: Start with a non-critical feature (e.g., user authentication). Deploy it as a .NET 8 service.
  3. **Database**: Use the monolith’s DB initially (shared schema with tenant ID). Later, migrate to a separate DB for the new service.
  4. **Dual Write**: Temporarily write to both old and new systems during transition.
  5. **Sunset**: Once all features are migrated, decommission the monolith.

---

**AA11**
- **12-Factor App**: Methodology for cloud-native apps. Key factors:
  1. **Codebase**: One codebase, multiple deploys.
  2. **Dependencies**: Explicitly declare and isolate dependencies.
  3. **Config**: Store config in environment variables.
  4. **Backing Services**: Treat databases as attached resources.
  5. **Build, Release, Run**: Separate stages.
  6. **Processes**: Stateless processes.
  7. **Port Binding**: Export services via port binding.
  - **Why It Matters**: Enables scalability, portability, and CI/CD (e.g., config via env vars allows dynamic scaling).

---

**AA12**
| **Aspect**            | **Event-Driven (Kafka)**               | **Request-Driven (REST/gRPC)**       |
|-----------------------|---------------------------------------|--------------------------------------|
| **Coupling**          | Loose (producers/consumers decoupled) | Tight (client-server dependency)     |
| **Scalability**       | High (horizontal scaling for brokers) | Limited by server capacity           |
| **Debugging**         | Hard (distributed logs, event flows)  | Easier (request/response logs)       |
| **Ordering**          | Guaranteed per partition              | Not guaranteed (unless sequential)   |
| **Failure Handling**  | Retries, dead-letter queues           | Retries, circuit breakers            |
- **Choose Event-Driven**: For async workflows (e.g., order processing), high throughput, or fan-out (e.g., notifications).
- **Choose Request-Driven**: For simple, synchronous interactions (e.g., user profile updates).

---

**AA13**
- **Load Balancer**: Distributes traffic across servers.
  - **Layer 4 (Transport)**: Routes based on IP/port (e.g., TCP/UDP). Example: HAProxy in TCP mode.
  - **Layer 7 (Application)**: Routes based on HTTP headers, paths, or cookies. Example: Nginx.
- **L7 Use Case**: Hosting multiple websites on one IP (e.g., `example.com/api` vs `example.com/static`).

---

**AA14**
- **Message Queue (RabbitMQ)**: Buffers messages for point-to-point or pub/sub. Messages are consumed once.
- **Log-Based Broker (Kafka)**: Append-only log; consumers can replay messages. Supports high-throughput, ordered streams.
- **When to Pick**:
  - **RabbitMQ**: Simple task queues (e.g., background jobs).
  - **Kafka**: Event streaming (e.g., clickstream analytics), replayability.

---

**AA15**
- **Container**: Lightweight, shares host OS kernel, isolated via namespaces/cgroups. Example: Docker.
- **VM**: Full OS virtualization, heavier (includes guest OS). Example: KVM.
- **Why Containers for Microservices**: Faster startup, lower overhead, portable (same image runs anywhere).

---
**AA16**
- **Stateless Service**: No local state (e.g., API gateway). Easy to scale horizontally (add more instances).
- **Stateful Service**: Maintains local state (e.g., session data in memory). Harder to scale (requires sticky sessions or shared storage).
- **Examples**:
  - Stateless: REST API.
  - Stateful: WebSocket server.

---
**AA17**
- **ORM**: Maps objects to database tables (e.g., SQLAlchemy for Python, Entity Framework for .NET).
- **Trade-offs**:
  - **Pros**: Faster development, database-agnostic.
  - **Cons**: Performance overhead (e.g., N+1 queries), limited control over SQL.

---
**AA18**
- **Bulkhead Pattern**: Isolates failures by partitioning resources (e.g., thread pools, connection pools) so one failure doesn’t affect others.
- **Example**: Deploy Service A on 3 nodes and Service B on 3 separate nodes. If Service A crashes, Service B remains unaffected.
- **Implementation**: Use separate thread pools for different services in a microservices app.

---
**AA19**
| **Aspect**            | **Operational Transformation (OT)** | **CRDTs**                          |
|-----------------------|-------------------------------------|------------------------------------|
| **Consistency**       | Strong (central authority)          | Eventual (conflict-free merges)    |
| **Latency**           | Higher (requires coordination)      | Lower (local operations)           |
| **Complexity**        | High (transform functions)          | Medium (predefined data types)     |
| **Offline Support**   | Limited (needs sync)                | Full (merges changes later)        |
- **Choice for Offline Editing**: **CRDTs** (e.g., Google Docs uses CRDT-like structures). OT requires a central server to resolve conflicts, while CRDTs allow offline edits and merge later.

---
**AA20**
- **Challenges of Distributed Tracing in Polyglot Systems**:
  - **Context Propagation**: Use W3C Trace Context or B3 headers to pass trace IDs across services (e.g., HTTP headers, Kafka message headers).
  - **Sampling**: Head-based (decide at the start) vs. tail-based (decide at the end). Head-based is more common (e.g., Jaeger).
  - **Storage/Querying**: Use Jaeger (open-source) or Tempo (Grafana) for trace storage. Query with tags (e.g., `service=checkout`).
  - **Async Messaging (Kafka)**: Inject trace context into message headers. Consumers extract and continue the trace.
  - **Trace Continuity**: Ensure every service propagates the trace context (e.g., in Kafka, include `traceparent` header in messages).

### **On-Premise Infrastructure Architecture (20 questions)**

---
**OP1**
- **Type 1 Hypervisor (Bare-Metal)**: Runs directly on hardware. Examples: VMware ESXi, Microsoft Hyper-V.
- **Type 2 Hypervisor (Hosted)**: Runs on top of a host OS. Examples: VirtualBox, VMware Workstation.

---
**OP2**
- **SAN (Storage Area Network)**: Block-level storage, appears as local disks. Uses Fibre Channel (FC) or iSCSI. Best for high-performance (e.g., databases).
- **NAS (Network-Attached Storage)**: File-level storage (e.g., NFS, SMB). Best for shared files (e.g., user home directories).

---
**OP3**
- **3-Tier Architecture**:
  - **Core**: High-speed backbone (e.g., 10Gbps switches).
  - **Distribution**: Aggregates access layer traffic (e.g., VLAN routing).
  - **Access**: Connects end devices (e.g., 1Gbps switches).
- **Leaf-Spine**:
  - **Why Preferred**: Non-blocking, lower latency, and higher scalability. Every leaf connects to every spine, eliminating bottlenecks.
  - **Problem Solved**: 3-tier has oversubscription (e.g., core can become a bottleneck). Leaf-spine provides full bisectional bandwidth.

---
**OP4**
- **Proxmox Cluster Design**:
  - **Node Count**: 3 nodes (minimum for HA; quorum requires odd numbers).
  - **Quorum**: Uses Corosync. If quorum is lost (e.g., 2 nodes down), the cluster stops to prevent split-brain.
  - **Fencing (STONITH)**: Power off a failed node (e.g., via IPMI) to prevent data corruption.
  - **Shared Storage**:
    - **Ceph**: Distributed, highly available, but complex. Recommended for production.
    - **iSCSI/NFS**: Simpler but single point of failure (unless using HA iSCSI targets).
  - **Node Failure**: If a node fails, Proxmox migrates VMs to other nodes (if shared storage is available). If the node is fenced, its VMs are restarted elsewhere.

---
**OP5**
- **VLAN Trunking (802.1Q)**: Allows a single physical NIC to carry traffic for multiple VLANs by tagging frames with VLAN IDs.
- **Linux Configuration**:
  ```bash
  # Create a trunk interface (e.g., eth0)
  ip link add link eth0 name eth0.100 type vlan id 100
  ip link add link eth0 name eth0.200 type vlan id 200
  ip link add link eth0 name eth0.300 type vlan id 300
  # Assign IPs or use DHCP
  ip addr add 192.168.1.100/24 dev eth0.100
  ```

---
**OP6**
| **RAID**  | **Fault Tolerance** | **Capacity (6x1TB)** | **Performance**       | **Use Case**               |
|-----------|---------------------|----------------------|-----------------------|----------------------------|
| RAID 1    | 1 drive             | 1TB                  | High (read), Low (write) | OS drives                  |
| RAID 5    | 1 drive             | 5TB                  | Medium                | General-purpose storage    |
| RAID 6    | 2 drives            | 4TB                  | Medium (slower writes)| Archive storage            |
| RAID 10   | 1 drive per mirror  | 3TB                  | Very High             | Databases (high IOPS)      |
| RAID Z2   | 2 drives            | 4TB                  | High (ZFS optimized)  | ZFS-based NAS/SAN          |
- **Choice for Database**: **RAID 10** (best balance of performance and fault tolerance for 6 drives).

---
**OP7**
- **DNS Architecture**:
  - **Internal AD**: Active Directory-integrated DNS (authoritative for `internal.example.com`). Uses Windows DNS servers.
  - **DMZ**: Public DNS (authoritative for `example.com`) on separate servers (e.g., BIND).
  - **Split-Horizon**: Internal clients resolve `example.com` to private IPs; external clients resolve to public IPs.
  - **DNSSEC**: Enable on external zone (e.g., using BIND + DNSSEC signing).
  - **Recursive Resolvers**: Deploy internal resolvers (e.g., Windows DNS) with forwarders to ISP or public DNS (e.g., 8.8.8.8).
  - **Conditional Forwarding**: Internal DNS forwards `internal.example.com` to AD DNS; external queries go to public resolvers.
  - **Laptop Behavior**: On VPN, laptop uses internal DNS (via DHCP or VPN config). Off VPN, uses public DNS.

---
**OP8**
- **PKI Chain of Trust**: Root CA → Subordinate CA → End-Entity Certificate.
- **Internal PKI Deployment**:
  - **Root CA**: Offline, stored in a secure vault. Issues certificates to subordinate CAs.
  - **Subordinate CA**: Online, issues end-entity certs (e.g., for servers, users).
  - **CRL vs. OCSP**:
    - **CRL**: Static list of revoked certs (downloadable).
    - **OCSP**: Real-time revocation checks (faster but requires network access).
  - **Certificate Templates**: Define in AD CS (e.g., "Web Server" template for HTTPS).
  - **Auto-Enrollment**: Use Group Policy to auto-enroll machines/users.
- **Compromise Impact**:
  - **Subordinate CA**: Revoke its cert and issue new ones from the root. Less damage (only certs it issued are affected).
  - **Root CA**: Catastrophic; requires rebuilding the entire PKI.

---
**OP9**
| **Option**          | **Cost** | **Reliability** | **Latency** | **Management** | **Security**       |
|---------------------|----------|-----------------|-------------|----------------|--------------------|
| MPLS                | High     | High            | Low         | Low (carrier)  | High (private)     |
| IPsec VPN           | Low      | Medium          | Medium      | Medium         | High (encrypted)   |
| SD-WAN              | Medium   | High            | Low         | High           | High (encrypted)   |
| WireGuard Mesh      | Low      | Medium          | Low         | Medium         | High (modern crypto)|
- **Recommendation**: **SD-WAN** (e.g., Cisco Viptela) for VoIP. Balances cost, reliability, and low latency. MPLS is too expensive; IPsec VPN may have higher latency.

---
**OP10**
- **iDRAC/iLO/IPMI**: Out-of-band management interfaces for remote server control (power, BIOS, KVM).
- **Why Critical**: Allows recovery if the OS crashes (e.g., reboot a hung server).
- **Risk of Internet Exposure**: Attackers can gain full control (e.g., power off servers, change BIOS settings). **Mitigation**: Restrict IPMI access to a management VLAN or use a VPN.

---
**OP11**
| **Feature**       | **LVM**               | **LVM-Thin**          | **ZFS**                |
|-------------------|-----------------------|-----------------------|-------------------------|
| **Snapshots**     | Copy-on-write (COW)   | COW, space-efficient  | COW, writable clones    |
| **Pooling**       | Yes (VG)              | Yes (thin pools)      | Yes (zpools)            |
| **Deduplication** | No                    | No                    | Yes                     |
| **Use Case**      | General-purpose       | Thin provisioning     | NAS, high reliability   |
- **When to Use**:
  - **LVM**: Simple volume management (e.g., extending a filesystem).
  - **LVM-Thin**: Overcommit storage (e.g., VMs with thin disks).
  - **ZFS**: Data integrity (checksums), snapshots, and deduplication (e.g., backup server).

---
**OP12**
- **Stretch Cluster/DR Strategy**:
  - **Ceph CRUSH Rules**: Configure to replicate data across sites (e.g., `osd` placement groups span Site A and Site B).
  - **Monitor Placement**: Deploy Ceph monitors in both sites (odd number, e.g., 3: 2 in Site A, 1 in Site B).
  - **Network Latency**: Ceph requires <10ms latency for synchronous replication. Use **asynchronous replication** for >10ms (but risk data loss).
  - **Split-Brain Problem**: If sites lose connectivity, Ceph may stop writing to prevent divergence. **Solution**: Use a tiebreaker (e.g., a 3rd site or quorum witness).
  - **Why 2-Site Ceph is Bad**: Without a tiebreaker, split-brain can cause both sites to go read-only.

---
**OP13**
- **DHCP DORA Process**:
  1. **Discover**: Client broadcasts `DHCPDISCOVER`.
  2. **Offer**: Server responds with `DHCPOFFER` (IP, subnet, lease time).
  3. **Request**: Client requests the offered IP (`DHCPREQUEST`).
  4. **Acknowledge**: Server confirms (`DHCPACK`).
- **Lease Expiry**: Windows clients enter a **rebinding state** (try to renew with the original server). If no server responds, they use an **APIPA address** (169.254.x.x).

---
**OP14**
- **Managed Switch**: Configurable (VLANs, QoS, monitoring). Example: Cisco Catalyst.
- **Unmanaged Switch**: Plug-and-play, no configuration.
- **Enterprise Features**:
  - VLANs (traffic isolation).
  - STP (prevents loops).
  - Port mirroring (for monitoring).
  - QoS (prioritizes VoIP traffic).

---
**OP15**
- **NTP**: Synchronizes clocks across servers.
- **Why Critical**: Kerberos (AD) requires time sync within 5 minutes. Clocks drifting can break authentication, logs, and distributed systems (e.g., Ceph).
- **Issues with Drift**:
  - Failed logins (Kerberos).
  - Inconsistent timestamps in logs.
  - Split-brain in clusters (e.g., Proxmox).

---
**OP16**
| **Type**          | **Description**                          | **When to Use**                     |
|-------------------|------------------------------------------|-------------------------------------|
| Physical Server   | Bare metal, no virtualization.           | High-performance (e.g., databases). |
| Virtual Machine   | Runs on a hypervisor (e.g., VMware).     | General-purpose workloads.          |
| Container         | Lightweight, shares host OS.             | Microservices, stateless apps.      |
- **Bare Metal Use Case**: Low-latency trading systems, high-I/O databases.

---
**OP17**
- **UPS**: Provides short-term power (minutes to hours) during outages. Protects against power surges/sags.
- **Generator**: Long-term power (days). Kicks in after UPS battery depletes.
- **ATS (Automatic Transfer Switch)**: Switches load from UPS to generator automatically.
- **Why Both**: UPS bridges the gap until the generator starts (generators take ~10-30 seconds to come online).

---
**OP18**
- **Active-Passive**: One node is active; the other is standby. Failover occurs on failure.
- **Active-Active**: Both nodes handle traffic (e.g., load-balanced).
- **PostgreSQL HA with Pacemaker/Corosync**:
  - **Resources**: PostgreSQL (master/slave), Virtual IP (VIP), and a health check script.
  - **Fencing (STONITH)**: Use IPMI to power off a failed node.
  - **Failover**: If the master fails, Corosync promotes the slave to master and moves the VIP to it.
  - **Replication**: Use PostgreSQL streaming replication (async or sync).

---
**OP19**
- **Backup Strategy**:
  - **3-2-1 Rule**: 3 copies, 2 media types, 1 offsite.
  - **RPO/RTO**:
    - **RPO (Recovery Point Objective)**: Max data loss (e.g., 1 hour for databases).
    - **RTO (Recovery Time Objective)**: Max downtime (e.g., 4 hours for critical systems).
  - **Backup Types**:
    - **Full**: Complete backup (weekly).
    - **Incremental**: Backs up changes since last backup (daily).
    - **Differential**: Backs up changes since last full (daily).
  - **Storage**:
    - **Disk**: Fast, but vulnerable to ransomware.
    - **Tape**: Slow, but air-gapped (ransomware-proof).
    - **Cloud**: Offsite (e.g., AWS S3 with versioning).
  - **Immutable Backups**: Use WORM (Write Once, Read Many) storage (e.g., tape, cloud object lock).
  - **Testing**: Restore backups to a test environment quarterly.
  - **Backup vs. DR**:
    - **Backup**: Restores data.
    - **DR**: Restores entire systems (e.g., VMs, configs) to a secondary site.

---
**OP20**
- **802.1X Workflow**:
  1. **Supplicant** (client device) requests network access.
  2. **Authenticator** (switch) blocks the port and requests credentials.
  3. **Authentication Server** (RADIUS) validates credentials (e.g., via AD).
  4. If successful, the switch opens the port and assigns a VLAN (dynamic VLAN assignment).
- **EAP Methods**:
  - **EAP-TLS**: Uses client certificates (most secure).
  - **PEAP**: Uses server-side certs + password (easier to deploy).
- **Failed Authentication**: Port remains blocked (or assigned to a quarantine VLAN).
- **MAB (MAC Authentication Bypass)**: For devices without 802.1X (e.g., printers). The switch authenticates using the device’s MAC address (pre-registered in RADIUS).
