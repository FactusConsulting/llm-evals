### **Kubernetes (20 questions)**

---

**K1** — A **Deployment** is for stateless applications, managing a set of identical pods with rolling updates and scaling. A **StatefulSet** is for stateful applications, providing stable, unique network identities and persistent storage for each pod (e.g., ordered pod names, stable hostnames).

---

**K2** — A **ClusterIP Service** creates a virtual IP (ClusterIP) in the cluster. **kube-proxy** (using iptables/IPVS) routes traffic to the ClusterIP, which load-balances requests to the **Endpoints** (pod IPs) associated with the Service. Traffic is distributed to all healthy pods matching the Service’s selector.

---

**K3** —
- **PersistentVolume (PV)**: A provisioned storage resource in the cluster (e.g., NFS, AWS EBS).
- **PersistentVolumeClaim (PVC)**: A request for storage by a user, binding to a PV that meets its requirements.
- **StorageClass**: Defines dynamic provisioning (e.g., "fast" SSD vs. "slow" HDD). PVs can be dynamically created based on StorageClass when a PVC is made.
**Relationship**: PVCs consume PVs; StorageClass enables dynamic PV creation.

---

**K4** — Troubleshooting **CrashLoopBackOff**:
1. **Logs**: `kubectl logs <pod> --previous` (check crash logs from the previous container instance).
2. **Describe**: `kubectl describe pod <pod>` (look for OOMKilled, exit codes, or failed liveness probes).
3. **Events**: `kubectl get events --sort-by=.metadata.creationTimestamp` (check for scheduling failures or image pull errors).
4. **Resource Limits**: Verify if the pod exceeds `limits.memory` (OOMKilled) or `limits.cpu` (throttling).
5. **Application Errors**: Check if the app crashes due to misconfigurations (e.g., missing ConfigMaps/Secrets).

---

**K5** — **CoreDNS** provides DNS resolution in Kubernetes, translating service names (e.g., `my-service.namespace.svc.cluster.local`) to ClusterIPs. If CoreDNS pods are down:
- Pods cannot resolve service names, breaking inter-pod communication.
- External DNS (e.g., `google.com`) may also fail unless fallback DNS is configured.
- New pods may fail to start if they rely on DNS-based service discovery.

---

**K6** — The scheduler uses a **two-phase process**:
1. **Filtering (Predicates)**: Eliminates nodes that don’t meet requirements (e.g., insufficient CPU/memory, taints without tolerations, node affinity/anti-affinity).
2. **Scoring (Priorities)**: Ranks remaining nodes using factors like:
   - **Resource Availability**: Nodes with more free CPU/memory score higher.
   - **Node Affinity**: Prefer nodes matching `preferredDuringSchedulingIgnoredDuringExecution`.
   - **Inter-Pod Affinity/Anti-Affinity**: Co-locate or separate pods based on rules.
   - **Topology Spread Constraints**: Distribute pods across zones/nodes for high availability.
The highest-scoring node is selected.

---

**K7** —
- **Scheduling**: The pod’s **requests.memory (256Mi)** is added to the node’s total requested memory (3.5GB + 0.25GB = 3.75GB ≤ 4GB). **The pod will be scheduled**.
- **Runtime**: If the pod uses **600Mi**, it exceeds its **limit (512Mi)**. The kernel’s OOM killer will **terminate the pod** (with `OOMKilled` status), and it will restart (if part of a Deployment).

---

**K8** — Request flow for **NGINX Ingress**:
1. **External Load Balancer**: Routes traffic to the **Ingress Controller** (NGINX pod) based on the Ingress’s host/path rules.
2. **Ingress Controller**: NGINX evaluates the Ingress rules and routes the request to the appropriate **Service** (ClusterIP).
3. **Service**: The Service (e.g., `my-service:80`) load-balances traffic to its **Endpoints** (pod IPs).
4. **kube-proxy**: Uses **iptables/IPVS** to forward traffic from the Service’s ClusterIP to the pod IPs.
5. **Pod**: The application pod processes the request.

---

**K9** — A **NetworkPolicy** controls pod-to-pod traffic (like a firewall). Default behavior:
- **No NetworkPolicy**: All traffic is **allowed** (open by default).
- **With NetworkPolicy**: Only traffic matching the policy’s `ingress`/`egress` rules is allowed; all else is **denied**.
Example: A policy selecting pods with `app: backend` may only allow traffic from pods with `app: frontend`.

---

**K10** —
- **RollingUpdate**: Gradually replaces pods (default). Ensures availability during updates (e.g., 25% unavailable at a time).
- **Recreate**: **Deletes all old pods before creating new ones**. Use when:
  - The app cannot handle concurrent old/new versions (e.g., database schema changes).
  - You need to avoid resource contention during updates.

---

**K11** — A **namespace** is a virtual cluster for isolating resources (e.g., `dev`, `prod`). Default namespaces:
- `default`: For objects with no namespace specified.
- `kube-system`: For Kubernetes system components (e.g., CoreDNS, kube-proxy).
- `kube-public`: For public cluster info (e.g., `cluster-info` ConfigMap).
- `kube-node-lease`: For node heartbeats.

---

**K12** — `kubectl describe pod <name>` provides detailed pod info, including:
1. **Events**: Timeline of pod lifecycle events (e.g., scheduling, pulling images).
2. **Conditions**: Pod status (e.g., `Ready`, `ContainersReady`).
3. **Container State**: Exit codes, restart count, and last termination reason.
4. **Node/IP**: The node the pod is running on and its IP.
5. **Volumes/Mounts**: ConfigMap/Secret mounts and their paths.

---

**K13** — A **ConfigMap** stores configuration data (e.g., env vars, config files). Pods consume it via:
1. **Environment Variables**: Inject keys as env vars using `envFrom` or `valueFrom`.
2. **Volume Mounts**: Mount as files in a pod (e.g., `configMap` volume type).
3. **Command Arguments**: Use ConfigMap values in `command` or `args`.

---
**K14** —
- **ClusterIP**: Internal-only virtual IP. Accessible only within the cluster.
- **NodePort**: Exposes the Service on a static port on **every node’s IP** (e.g., `NodeIP:30007`). Routes to ClusterIP internally.
- **LoadBalancer**: Provisions an **external cloud LB** (e.g., AWS ELB) that routes to NodePort, which routes to ClusterIP.

---
**K15** — A **DaemonSet** ensures **one pod per node** (or subset of nodes). Use instead of a Deployment when:
- Running node-specific workloads (e.g., logging agents like Fluentd, monitoring agents like Prometheus Node Exporter).
- Requiring a pod on every node (e.g., kube-proxy, CNI plugins).

---
**K16** —
- **Taints and Tolerations**: Nodes can **repel** pods unless the pod **tolerates** the taint.
  - *Use Case*: Reserve nodes for specific workloads (e.g., `node-role.kubernetes.io/master:NoSchedule` taint on control plane nodes).
- **Node Affinity**: Pods **prefer** or **require** nodes with specific labels.
  - *Use Case*: Schedule pods on nodes with SSDs (`disk: ssd` label).
**Difference**: Taints/tolerations are **exclusionary** (pods are blocked unless they tolerate), while affinity is **inclusionary** (pods are attracted to nodes).

---
**K17** — A **Kubernetes Operator** is a **custom controller** that extends Kubernetes’ functionality using **Custom Resource Definitions (CRDs)**. Unlike standard controllers (which manage built-in resources like Deployments), Operators encode **domain-specific knowledge** (e.g., managing databases, Kafka clusters).
- **Problems Solved**:
  - Automates complex, stateful workflows (e.g., backups, upgrades, failover).
  - Reduces manual intervention for day-2 operations.
- Example: The **Etcd Operator** manages etcd clusters (scaling, backups, restores).

---
**K18** — Kubernetes uses **etcd**, which employs the **Raft consensus algorithm** (strong consistency, linearizability). etcd’s consistency model:
- **Linearizable reads/writes**: All operations appear to occur instantaneously at a single point in time.
- **Quorum-based**: Requires a majority of nodes (e.g., 2/3 for a 3-node cluster) to agree on writes.
**If quorum is lost**:
- The cluster becomes **read-only** (no writes allowed).
- API server cannot persist changes (e.g., pod schedules, ConfigMap updates).
**Recovery from 2/3 etcd nodes lost**:
- **Not recoverable** without manual intervention. You must:
  1. Restore etcd from a **snapshot** (if available).
  2. Rebuild the cluster if no snapshot exists (data loss).

---
**K19** — **RBAC** (Role-Based Access Control) in Kubernetes:
- **Role**: Defines permissions **within a namespace** (e.g., `pods:read`).
- **ClusterRole**: Defines **cluster-wide** permissions (e.g., `nodes:list`).
- **RoleBinding**: Grants a Role to users/groups **in a namespace**.
- **ClusterRoleBinding**: Grants a ClusterRole **cluster-wide**.
**Example RBAC for read-only pod/log access in `dev` namespace**:
```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: "developer"
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — **Slow DNS resolution due to `ndots`**:
- **Problem**: The `ndots` option in `/etc/resolv.conf` (inside pods) specifies how many dots a hostname must have before DNS queries are sent directly (without appending search domains). For example, if `ndots:5` and the query is `my-service`, CoreDNS will try:
  `my-service.namespace.svc.cluster.local`, `my-service.svc.cluster.local`, `my-service.cluster.local`, `my-service.local`, `my-service` (5 queries).
- **Fix**: Use `dnsConfig` in the pod spec to override `ndots` (e.g., set `ndots: 2`):
  ```yaml
  dnsConfig:
    options:
      - name: ndots
        value: "2"
  ```

### **Development (20 questions)**

---
**D1** —
- **git rebase**: Rewrites commit history by moving the feature branch’s commits to the tip of the main branch, creating new commits. Results in a linear history.
- **git merge**: Creates a new "merge commit" that ties two branches together, preserving history.
**Avoid rebasing**:
- On **public/shared branches** (rewriting history breaks others’ work).
- If the team prefers explicit merge commits for traceability.

---
**D2** —
- **TCP**: Connection-oriented, reliable, ordered, error-checked. Uses **handshakes** (SYN, SYN-ACK, ACK). Protocols: **HTTP, FTP**.
- **UDP**: Connectionless, unreliable, low-latency. No handshakes. Protocols: **DNS, DHCP**.

---
**D3** — A **race condition** occurs when the outcome of a program depends on the **timing/order of uncontrollable events** (e.g., thread scheduling).
**Example (Python)**:
```python
counter = 0

def increment():
    global counter
    temp = counter  # Read
    temp += 1       # Modify
    counter = temp  # Write

# Thread 1 and Thread 2 call increment() simultaneously.
# Possible outcome: counter = 1 (instead of 2) if both threads read `counter=0` before writing.
```
**Fix**: Use locks (`threading.Lock`).

---
**D4** —
- **Symmetric Encryption**: Same key for encryption/decryption (e.g., AES). Fast, but key distribution is hard.
- **Asymmetric Encryption**: Public key (encrypt) + private key (decrypt) (e.g., RSA). Slow, but solves key distribution.
**In TLS**:
1. Asymmetric encryption (RSA/ECDHE) is used for the **key exchange** (to securely share a symmetric key).
2. Symmetric encryption (AES) is used for **bulk data encryption** (faster).

---
**D5** — A **container image layer** is a read-only filesystem layer (e.g., a `RUN` command in a Dockerfile creates a new layer). Layers are stacked to form the final image.
- **Layer Caching**: Docker caches layers to avoid rebuilding unchanged steps. **Best Practices**:
  - Order Dockerfile commands by **least frequently changed** (e.g., `FROM`, `RUN apt-get update`) to **maximize cache hits**.
  - Avoid `RUN apt-get update && apt-get install -y package` in separate layers (cache invalidation).

---
**D6** — Troubleshooting **intermittent HTTP 503** (Service Unavailable):
1. **Check Server Logs**: Look for crashes, timeouts, or resource exhaustion (CPU/memory).
2. **Load Balancer/Proxy**: Verify if the LB (e.g., NGINX, ALB) is dropping requests due to:
   - Backend health check failures.
   - Connection pool exhaustion.
3. **Database**: Check for slow queries, deadlocks, or connection limits.
4. **Dependencies**: Verify third-party APIs or microservices are available (use `curl` or monitoring tools).
5. **Resource Limits**: Check if the app is hitting `ulimit` (file descriptors) or container `limits.cpu/memory`.

---
**D7** — **CAP Theorem**: A distributed system can only guarantee **2 out of 3** properties:
- **Consistency (C)**: All nodes see the same data at the same time.
- **Availability (A)**: Every request receives a response (even if stale).
- **Partition Tolerance (P)**: The system works despite network partitions.
**Examples**:
- **CP (Consistency + Partition Tolerance)**: **etcd**, **MongoDB (with strong consistency)**. Sacrifices availability during partitions.
- **AP (Availability + Partition Tolerance)**: **Cassandra**, **DynamoDB**. Sacrifices consistency (eventual consistency).

---
**D8** —
- **Vertical Scaling**: Adding more resources (CPU, RAM) to a single machine.
- **Horizontal Scaling**: Adding more machines (nodes) to distribute load.
**Patterns for Horizontal Scaling**:
- **Load Balancing**: Distribute traffic across instances (e.g., NGINX, ALB).
- **Stateless Services**: Store session data in a shared cache (e.g., Redis) or database.
- **Microservices**: Decompose monoliths into independent services.
- **Sharding**: Split data across multiple databases (e.g., by user ID).

---
**D9** — An **environment variable** is a dynamic value that affects processes’ behavior (e.g., `PATH`, `DATABASE_URL`).
**Set Persistent Env Var on Linux**:
1. Add to shell config file (e.g., `~/.bashrc`, `~/.zshrc`):
   ```bash
   export MY_VAR="value"
   ```
2. Source the file or restart the shell:
   ```bash
   source ~/.bashrc
   ```
For system-wide vars, use `/etc/environment` or `/etc/profile.d/`.

---
**D10** —
- **JSON**: Lightweight data format using key-value pairs (e.g., `{"key": "value"}`). **Advantage**: Native support in browsers (JavaScript).
- **YAML**: Superset of JSON with human-readable syntax (e.g., indentation, comments). **Advantage**: Easier to read/write for configs (e.g., Kubernetes manifests).

---
**D11** — A **REST API** is an architectural style for networked applications using HTTP methods to perform CRUD operations on resources.
- **GET**: Retrieve a resource (idempotent, safe).
- **POST**: Create a resource (non-idempotent).
- **PUT**: Replace a resource entirely (idempotent).
- **DELETE**: Remove a resource (idempotent).

---
**D12** — **Version Pinning** is specifying exact versions of dependencies (e.g., `package@1.2.3`) in `package.json`, `requirements.txt`, or `go.mod`.
**Importance**:
- Ensures **reproducible builds** (same dependencies every time).
- Avoids breaking changes from automatic updates (e.g., `package@^1.2.3` may pull `1.3.0` with breaking changes).

---
**D13** —
- **Compiled Language**: Code is translated to machine code before execution (e.g., **C, Go**). Faster execution, but requires recompilation for different platforms.
- **Interpreted Language**: Code is executed line-by-line by an interpreter (e.g., **Python, JavaScript**). Portable, but slower.

---
**D14** —
- **Reverse Proxy**: Accepts requests from clients and forwards them to backend servers. **Use Cases**:
  - **NGINX**: Load balancing, SSL termination, caching.
  - **Apache HTTP Server**: URL rewriting, A/B testing.
- **Forward Proxy**: Acts on behalf of clients to fetch resources from external servers (e.g., corporate proxy to access the internet).
**Difference**: Reverse proxy hides **servers**, forward proxy hides **clients**.

---
**D15** — A **deadlock** occurs when two or more processes are blocked forever, each waiting for the other to release a resource.
**Coffman Conditions**:
1. **Mutual Exclusion**: Only one process can use a resource at a time.
2. **Hold and Wait**: A process holds a resource while waiting for another.
3. **No Preemption**: Resources cannot be forcibly taken from a process.
4. **Circular Wait**: A cycle of processes exists where each waits for a resource held by the next.
**Example**: Process A holds Resource 1 and waits for Resource 2, while Process B holds Resource 2 and waits for Resource 1.

---
**D16** — **Eventual Consistency**: A system guarantees that, if no new updates are made, all nodes will **eventually** converge to the same value.
**Cassandra’s Approach**:
- Uses **gossip protocol** for node communication and **hinted handoff** for temporary failures.
- **Tunable Consistency Levels** (per read/write):
  - `ONE`: Acknowledge from 1 replica.
  - `QUORUM`: Acknowledge from a majority of replicas (strong consistency).
  - `ALL`: Acknowledge from all replicas (strongest consistency).
- **Read-After-Write Consistency**: Achieved by using `QUORUM` for both reads and writes (or `LOCAL_QUORUM` for multi-DC setups).

---
**D17** — **mTLS (Mutual TLS)**: Both client and server authenticate each other using X.509 certificates.
**Handshake Process**:
1. **Client Hello**: Client sends supported cipher suites and a **client certificate**.
2. **Server Hello**: Server sends its certificate and requests the client’s certificate.
3. **Server Verification**: Client verifies the server’s certificate (CA, expiry, hostname).
4. **Client Verification**: Server verifies the client’s certificate.
5. **Key Exchange**: Both parties generate a **pre-master secret**, encrypted with the other’s public key.
6. **Session Keys**: Both derive symmetric session keys for encrypted communication.
**Use Cases**:
- **Service-to-Service Auth**: In microservices (e.g., Istio, Linkerd).
- **Database Connections**: PostgreSQL, MongoDB with mTLS.
- **Kubernetes**: API server to kubelet communication.

---
**D18** — A **hash table** stores key-value pairs using a **hash function** to compute an index (bucket).
- **Collision Resolution**:
  - **Chaining**: Each bucket is a linked list of entries. **Time Complexity**:
    - Average: **O(1)** (good hash function).
    - Worst: **O(n)** (all keys hash to the same bucket).
  - **Open Addressing**: If a collision occurs, probe for the next available slot (e.g., linear probing, quadratic probing). **Time Complexity**:
    - Average: **O(1)**.
    - Worst: **O(n)** (if many collisions).
- **Operations**:
  - Insertion: Average **O(1)**, Worst **O(n)**.
  - Lookup: Average **O(1)**, Worst **O(n)**.
  - Deletion: Average **O(1)**, Worst **O(n)**.

---
**D19** — **Circuit Breaker Pattern**: Prevents cascade failures by stopping requests to a failing service.
**States**:
1. **Closed**: Normal operation. Requests pass through; failures are counted.
2. **Open**: If failures exceed a threshold (e.g., 50% of requests fail), the circuit **trips**. All requests **fail fast** (return an error without calling the service).
3. **Half-Open**: After a timeout, a few requests are allowed through to test if the service has recovered. If they succeed, the circuit **closes**; if they fail, it **reopens**.
**Relation to Retries/Backoff**:
- **Retry Policies**: Retry failed requests (with exponential backoff to avoid thundering herds).
- **Circuit Breaker**: Stops retries entirely if the service is down, preventing resource exhaustion.
**Example**: In a microservice calling a payment API, the circuit breaker trips after 10 failures, fails fast for 30 seconds, then tests with 1 request.

**D20** —
- **Pessimistic Concurrency Control**: Locks records during transactions to prevent conflicts. **Example**:
  ```sql
  BEGIN;
  SELECT * FROM accounts WHERE id = 1 FOR UPDATE; -- Locks the row
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  COMMIT;
  ```
  **Use When**: High contention, strong consistency required (e.g., banking systems).
- **Optimistic Concurrency Control**: Assumes conflicts are rare; checks for conflicts at commit time. **Example**:
  ```sql
  UPDATE accounts SET balance = balance - 100, version = version + 1
  WHERE id = 1 AND version = 5; -- Fails if version changed
  ```
  **Use When**: Low contention, high read throughput (e.g., wiki edits).
**Database Features**:
- **Pessimistic**: `SELECT FOR UPDATE` (row-level locks).
- **Optimistic**: **Row versioning** (e.g., `version` column in PostgreSQL) or **timestamp-based** checks.
