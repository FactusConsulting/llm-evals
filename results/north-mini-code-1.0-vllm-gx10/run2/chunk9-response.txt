**SC2 – Hard – Cross‑Region Database Failover Gone Wrong**

---

### SC2‑A – Stale data after promotion  

1. **Replication lag at promotion time** – The EU‑west‑1 read replica was a *standby* for us‑east‑1. When us‑east‑1 went down, the replica was promoted **as‑is**, but any ongoing transactions in the primary that had not yet been shipped to the replica are lost. PostgreSQL streaming replication is **asynchronous** across regions; the primary can acknowledge a commit before the replica has written the WAL.  

2. **WAL shipping across regions** – The primary streams WAL via `pg_receivewal` (or the RDS replication mechanism). Network latency (≈ 80‑100 ms) and disk I/O cause a **replication lag** that can be seconds to minutes. When the replica is promoted, the lag becomes the **data‑loss window**.  

3. **Data‑loss scenarios** –  
   * **Transaction not yet received** – a commit on the primary that never reached the replica is lost.  
   * **Replication slot not used** – without a slot, the primary may recycle WAL, discarding un‑shipped data.  
   * **Network partition** – if the replica was temporarily disconnected, the lag could be larger.  

4. **Quantifying the loss window** –  
   ```sql
   SELECT EXTRACT(EPOCH FROM now() - pg_last_xact_replay_timestamp()) AS replication_lag_sec;
   ```  
   Also check `pg_stat_replication` for `sent_lsn` vs `write_lsn` and `flush_lsn`. The difference between `pg_last_committed_xact_id()` on the primary and the replica (via `pg_replication_slots`) gives a concrete lag in bytes/transactions.  

**Bottom line:** The stale data is the replication lag that existed at the moment of promotion. The lag can be measured in seconds (or minutes) and directly translates to the amount of data that may be missing.

### SC2‑B – Terraform import & state update without destroy/recreate  

Assume the promoted replica’s ARN is `arn:aws:rds:us-west-2:123456789012:db:promoted-replica`. The old primary is `aws_db_instance.primary`.

```bash
# 1. Import the replica into Terraform state (keep the same resource name)
terraform import aws_db_instance.replica arn:aws:rds:us-west-2:123456789012:db:promoted-replica

# 2. Refresh its attributes (so Terraform knows the current config)
terraform refresh -resource aws_db_instance.replica

# 3. Detach the old primary from dependent resources (no destroy)
#    a) Update security‑group references to point to the replica
terraform state mv aws_security_group.primary_rule aws_security_group.replica_rule
#    b) Update Route53 A record
terraform state mv aws_route53_record.primary_dns aws_route53_record.replica_dns

# 4. Remove the old primary from state (so it won't be destroyed)
terraform state rm aws_db_instance.primary

# 5. Update any other resources that still reference the old ARN (parameter groups, option groups, etc.)
#    Example: replace the parameter group reference
terraform state mv aws_db_parameter_group.primary_pg aws_db_parameter_group.replica_pg

# 6. Run a plan to see what changes are required (should be only updates to the new resources)
terraform plan

# 7. Apply – this will update the replica, security groups, Route53 records, etc. without destroying anything.
terraform apply
```

**Key points**

* `terraform import` brings the existing resource into state, allowing Terraform to manage it.  
* `terraform state mv` (or `terraform state mv -state=...`) renames resources so that the configuration references the new names.  
* `terraform state rm` removes the old primary from state, preventing a `destroy` action.  
* After the moves, `terraform apply` will **update** the replica and dependent resources, never destroying the old instance (which can be kept as a backup or manually deleted later).

### SC3‑B – Script to compare base‑image digests & list layers  

```bash
#!/usr/bin/env bash
set -euo pipefail

# ---- Configuration ----
ECR_REPO="123456789012.dkr.ecr.us-east-1.amazonaws.com/api-gateway"
IMAGE_TAG="v2.4.1"
KNOWN_GOOD_LAYERS_FILE="/tmp/known_good_layers.txt"   # pre‑populated list of layer digests

# ---- Helper: get digest of a Docker image from ECR ----
get_ecr_digest() {
  local repo=$1 tag=$2
  # Use AWS CLI to fetch manifest
  local manifest=$(aws ecr batch-get-image \
    --repository-name "$repo" \
    --image-ids imageTag="$tag" \
    --query 'images[0].imageManifest' \
    --output text \
    --region us-east-1)
  echo "$manifest" | jq -r '.layers[].digest'   # list of layer digests
}

# ---- Helper: get upstream digest of node:20-slim from Docker Hub ----
get_upstream_digest() {
  # Docker Hub API (public, no auth needed)
  curl -s "https://hub.docker.com/v2/repositories/library/node/images/latest/" |
    jq -r '.results[0].digest'   # returns something like "sha256:..."
}

# ---- Main ----
echo "=== Base‑image digest comparison ==="
EC_LAYER_DIGESTS=$(get_ecr_digest "$ECR_REPO" "$IMAGE_TAG")
UPSTREAM_DIGEST=$(get_upstream_digest)

echo "ECR image layers (api-gateway:$IMAGE_TAG):"
printf "%s\n" "$EC_LAYER_DIGESTS"

echo "Upstream node:20-slim digest: $UPSTREAM_DIGEST"

# Check if the upstream digest appears among the layers (should be the first layer)
if echo "$EC_LAYER_DIGESTS" | grep -Fxq "$UPSTREAM_DIGEST"; then
  echo "✓ Base image matches upstream digest."
else
  echo "✗ WARNING: Base image digest mismatch – possible compromise!"
fi

# ---- List all layers and flag unknown ones ----
echo -e "\n=== Layer analysis ==="
# Get full manifest (including config) to see all layers
aws ecr batch-get-image \
  --repository-name "$ECR_REPO" \
  --image-ids imageTag="$IMAGE_TAG" \
  --query 'images[0].imageManifest' \
  --output json \
  --region us-east-1 > /tmp/manifest.json

jq -r '.layers[] | "\(.digest) \(.size) \(.mediaType)"' /tmp/manifest.json |
  while read -r digest size media; do
    if [[ "$digest" == "$UPSTREAM_DIGEST" ]]; then
      echo "KNOWN   $digest  ($size)"
    else
      echo "UNKNOWN $digest  ($size)  ← flag for investigation"
    fi
  done > /tmp/layer_report.txt

echo "Layer report written to /tmp/layer_report.txt"
```

*What the script does*  

* Pulls the ECR manifest for `api-gateway:v2.4.1`.  
* Fetches the **upstream** `node:20-slim` digest from Docker Hub.  
* Compares the two – if the upstream digest is missing, the base image may have been tampered with.  
* Enumerates every layer in the built image and flags any layer not present in the known‑good list (`KNOWN_GOOD_LAYERS_FILE`).  

You can pre‑populate `KNOWN_GOOD_LAYERS_FILE` with the layer digests from a trusted build (e.g., the last clean CI run).

### SC3‑C – Hardened CI/CD pipeline to stop supply‑chain attacks  

1. **Image signing** – Use **Cosign** (or **Sigstore**) to sign every container image at build time:  
   ```bash
   cosign sign --key signing.key ${ECR_REPO}:${IMAGE_TAG}
   ```  
   Store the signatures in the registry (as `cosign` attaches them as annotations) and in a transparency log.

2. **Admission control** – Deploy a **Kyverno** policy that rejects any pod whose image is **not signed** or whose `cosign` verification fails:  
   ```yaml
   apiVersion: kyverno.io/v1
   kind: ClusterPolicy
   metadata:
     name: require-cosign-signature
   spec:
     validationFailureAction: enforce
     rules:
     - name: verify-signature
       match:
         any:
         - resources:
             kinds:
             - Pod
       verifyImages:
         - imageRegistry:
             ociRepository: ${ECR_REPO}
           cosign:
             publicKey: "https://fulcio.sigstore.dev/api/v1/rootCertificate"
   ```

3. **Base‑image pinning** – In the Dockerfile, replace `node:20-slim` with its **digest**:  
   ```dockerfile
   FROM node@sha256:<upstream‑digest> AS base
   ```  
   This prevents accidental tag substitution.

4. **SBOM generation** – Run **Syft** (or **grype**) on the built image to produce an SBOM; enforce a policy that **no critical CVEs** are present before merging.

5. **Notary v2 integration** – Use **Notary v2** (or **Notation**) as an additional signing layer for the registry. The registry can be configured to require a **signed manifest** before pushing. Cosign can push the signature to Notary, providing a **transparent, cryptographic attestation** that can be audited independently of the CI system.

**Result:** An attacker would need to compromise both the build pipeline *and* the signing keys to produce a malicious image, and the admission controller will block deployment unless the image is verified.

### SC4‑A – Top 5 technical blockers & solutions  

| # | Blocker | Why it hurts K8s | Solution |
|---|---------|------------------|----------|
| 1 | **Sticky sessions / session state in memory** | K8s pods are ephemeral; load balancers (F5) rely on cookie‑based persistence, which breaks on pod restart. | Move sessions to an external store (Redis Cluster or Memcached). Use **session affinity** only as a fallback, or switch to **sticky‑free** design with token‑based auth. |
| 2 | **Local NFS mount (`/data/uploads`)** | NFS is not a native K8s PV; it lacks atomic leases, leading to “stale file handles” and performance issues. | Deploy an **NFS‑CSI driver** (e.g., `nfs.csi.k8s.io`) with a **ReadWriteMany** PV, or migrate uploads to **object storage** (S3/MinIO) and use a sidecar sync‑container. |
| 3 | **On‑prem Oracle 19c DB** | Oracle needs special storage, networking, and licensing; K8s cannot directly manage Oracle instances. | Use a **database‑as‑a‑service** (e.g., Amazon RDS for Oracle, or a managed Oracle operator). If staying on‑prem, run Oracle in a VM and expose via **Kubernetes Service** using **IPVS** or **MetalLB**. |
| 4 | **IBM MQ integration** | MQ is a heavyweight messaging system; K8s pods need stable network endpoints and durable queues. | Deploy MQ using the **IBM MQ Operator** (or a Helm chart) as a **StatefulSet**. Use **Kubernetes Secrets** for credentials, and expose a **ClusterIP** service for the monolith. |
| 5 | **Monolithic Java app not container‑ready** | No health checks, no resource limits, monolithic deployment makes scaling hard. | Refactor incrementally: add **Liveness/Readiness probes**, **resource requests/limits**, and **horizontal pod autoscaler** (HPA). Containerize with a **fat JAR** and a **distroless** base image. |

### SC5‑B – SQL diagnostic query & Go circuit‑breaker  

**SQL diagnostic (PostgreSQL 16)** – shows lock holders, waiters, and the query text:

```sql
-- 1. Find the blocking PID(s)
WITH blocking AS (
  SELECT pid
  FROM pg_locks l
  JOIN pg_stat_activity a ON a.pid = l.pid
  WHERE NOT l.granted AND l.locktype = 'relation'
    AND a.query LIKE '%stock_levels%'

), waiters AS (
  SELECT DISTINCT pid
  FROM pg_locks w
  JOIN blocking b ON w.locktype = 'relation' AND w.database = current_database()
    AND w.relation = (SELECT relation FROM pg_locks WHERE pid = b.pid)
    AND w.granted = false
)
SELECT
  wa.pid,
  wa.query,
  wa.state,
  bl.pid AS blocking_pid,
  bl.query AS blocking_query
FROM pg_stat_activity wa
JOIN waiters w ON wa.pid = w.pid
LEFT JOIN pg_stat_activity bl ON bl.pid = (
  SELECT pid FROM pg_locks l
  WHERE l.granted = false
    AND l.relation = (SELECT relation FROM pg_locks WHERE pid = w.pid)
    AND l.pid != w.pid
  LIMIT 1
)
WHERE wa.query LIKE '%stock_levels%';
```

*Explanation*: The CTE `blocking` finds the session holding the lock; `waiters` finds sessions waiting on that same relation. The final SELECT joins back to `pg_stat_activity` to show the waiting queries and the blocking query.

**Go circuit‑breaker snippet (sony/gobreaker)**  

```go
package checkout

import (
    "context"
    "time"

    "github.com/sony/gobreaker"
)

type InventoryClient struct {
    cb *gobreaker.CircuitBreaker
    // HTTP client, base URL, etc.
}

func NewInventoryClient() *InventoryClient {
    settings := gobreaker.Settings{
        Name:        "inventory",
        MaxRequests: 5,
        Interval:    60 * time.Second,
        Timeout:     30 * time.Second,
        ReadyToTrip: func(counts gobreaker.Counts) bool {
            // Trip if 80% failures in the last interval
            failureRatio := float64(counts.TotalFailures) / float64(counts.Requests)
            return counts.Requests >= 5 && failureRatio >= 0.8
        },
        // OnStateChange: log state changes
        OnStateChange: func(name string, from gobreaker.State, to gobreaker.State) {
            logger.Infof("circuit %s state changed: %s -> %s", name, from, to)
        },
    }
    return &InventoryClient{
        cb: gobreaker.NewCircuitBreaker(settings),
    }
}

// CallInventory performs a GET with circuit‑breaker protection.
func (c *InventoryClient) CallInventory(ctx context.Context, sku string) ([]byte, error) {
    // Wrap the actual HTTP call
    resp, err := c.doGet(ctx, "/inventory?sku="+url.QueryEscape(sku))
    if err != nil {
        return nil, err
    }
    return resp, nil
}

// doGet is the underlying HTTP call (simplified)
func (c *InventoryClient) doGet(ctx context.Context, path string) ([]byte, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, "http://inventory-service:8080"+path, nil)
    if err != nil {
        return nil, err
    }
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        return nil, fmt.Errorf("inventory returned %d", resp.StatusCode)
    }
    return io.ReadAll(resp.Body)
}
```

The circuit breaker will **open** after 5 requests with ≥ 80 % failure, preventing further calls to the blocked inventory service during the reconciliation window.

### SC5‑C – Architectural solution to eliminate the problem  

| Concern | Solution |
|---------|----------|
| **CronJob contention** | • **Separate read/write models** – use **CQRS**: keep a read‑only replica (or materialized view) for inventory queries; the reconciliation job writes to the write DB. <br>• **Read replica** – point inventory‑service to a PostgreSQL read replica (RDS read replica or Aurora Secondary). <br>• **Bulkload window** – schedule the reconciliation job during off‑peak hours (e.g., 02:00‑04:00 UTC) and use **pg_replication_slots** to limit impact. |
| **Connection‑pool exhaustion** | • Use **connection pooling** (PgBouncer) with **max_client_conn** sized for serving traffic, and a **separate pool** for the reconciliation job. <br>• Apply ** bulkhead** via separate Kubernetes `ResourceQuota`s or `PodDisruptionBudgets` to guarantee serving pods retain resources. |
| **CronJob starving serving pods** | • Deploy the CronJob as a **separate namespace** (`batch-jobs`) with its own **ResourceQuota** limiting CPU/memory. <br>• Use **PodDisruptionBudget** on the serving deployment to keep at least 1 replica alive even if the CronJob pod hogs nodes. <br>• Leverage **Kubernetes Scheduler** `PodPriority` – give serving pods higher priority. |
| **Zero‑downtime** | • Keep the read replica in sync via **logical replication** (or Aurora Global). <br>• Use **Istio** traffic splitting to route inventory calls to the read replica while the write replica runs the reconciliation. |

**Result:** The checkout service never contends for the same DB connections as the reconciliation job, eliminating the latency spikes.

### SC6‑A – Identity & access layer design  

| Environment | Machine‑identity mechanism | Integration points |
|-------------|---------------------------|--------------------|

### SC6‑C – Comparing connectivity options for the 1 Gbps bottleneck  

| Option | Cost (approx.) | Bandwidth | Encryption | Failover | Fit in Zero‑Trust |
|--------|----------------|-----------|------------|----------|-------------------|
| **AWS Direct Connect (DX)** | $2,000‑$5,000 setup + $0.05‑$0.10/GB data transfer | 10 Gbps (or 1 Gbps) | Layer‑2 VLAN; can run IPsec or use AWS‑managed encryption | Requires a second DX circuit for HA; can use BGP ECMP | Provides a **private, dedicated** connection – aligns with ZT; can be segmented with VPC endpoints. |
| **Second VPN tunnel with ECMP** | $0.05‑$0.10/GB + $0.00 for extra tunnel | 1 Gbps per tunnel (aggregate 2 Gbps with ECMP) | IPsec (TLS‑wrapped) – managed by AWS | Automatic failover via BGP; both tunnels active | Still traverses the internet (though encrypted); can be hardened with **TLS** and **IPsec**; fits ZT but adds a public‑internet hop. |
| **Hybrid mesh (Tailscale/Netbird)** | Free‑tier + $10‑$20/user for enterprise | Up to 10 Gbps per link (depends on underlying NIC) | WireGuard‑based encryption (TLS underneath) | Built‑in mesh failover; if one node fails, traffic reroutes | Provides **zero‑trust mesh** across on‑prem, AWS, Azure; simplifies policy enforcement via a central control plane. |

**Recommendation** – For a **strict zero‑trust** posture, the **Hybrid mesh (Tailscale/Netbird)** is attractive because it enforces mutual TLS, provides a unified identity‑based mesh, and eliminates the need for separate VPN tunnels. However, if you need **guaranteed bandwidth** and **compliance** that mandates a direct physical connection, **Direct Connect** is the safest. A **dual‑tunnel VPN** is a quick intermediate step but still relies on the public internet.

**Routing changes needed**  

* **DX** – Add a new VPC attachment to the Transit Gateway, advertise routes via BGP, configure VRFs on the DX gateway.  
* **Second VPN** – Add a second tunnel to the existing Customer Gateway, enable BGP ECMP on the VGW, update route tables.  
* **Mesh (Tailscale)** – Deploy Tailscale nodes on each environment; configure **Subnet routes** in the Tailscale admin console; no changes to existing VPC routing needed (traffic goes through the mesh).

total_metrics=$(echo "$metric_names" | wc -l)

# 3. Top 20 metrics by series count
top_series=$(for m in $metric_names; do
  series=$(curl -s "${PROMETHEUS_URL}/api/v1/series?match[]=${m}" | jq '.data[].length? // 0')
  echo "$m $series"
done | sort -k2,2nr | head -20)

# 4. For the highest‑cardinality metric, get label with most unique values
# Determine the metric with max series
highest_metric=$(echo "$top_series" | head -1 | awk '{print $1}')
# Query label values for each label of that metric
label_counts=$(curl -s "${PROMETHEUS_URL}/api/v1/label/${highest_metric}/values" | jq -r '.data[]')
# For each label, count distinct values in the metric
declare -A label_max
for lbl in $label_counts; do
  # Use PromQL to count distinct label values for the metric
  count=$(curl -s "${PROMETHEUS_URL}/api/v1/query?query=count%20by%20(%22${lbl}%22)%20${highest_metric}" |
    jq -r '.data.result[0].value[1] // "0"')
  label_max["$lbl"]=$count
done

# Find label with max count
max_label=$(printf "%s\n" "${!label_max[@]}" | sort -t= -k2,2nr | head -1)
max_count=${label_max[$max_label]}

# Output formatted report
cat <<EOF
=== Prometheus Cardinality Report ===
Generated: $(date -u +"%Y-%m-%d %H:%M:%S UTC")
Total unique metric names: $total_metrics

--- Top 20 metrics by series count ---
$(echo "$top_series" | awk '{printf "%s: %s series\n", $1, $2}')

--- Highest‑cardinality metric: $highest_metric ---
Label with most unique values: $max_label ($max_count distinct values)

--- Sample of high‑cardinality label combinations (first 5) ---
$(curl -s "${PROMETHEUS_URL}/api/v1/query?query=topk(5,%20count%20by%20(pod,%20namespace)%20${highest_metric})" |
  jq -r '.data.result[] | "\(.metric.pod)/\(.metric.namespace): \(.value[1]) series"')
EOF
```

*Explanation*  

* Pulls metric names from `/label/__name__/values`.  
* Counts series per metric via the `/api/v1/series` endpoint.  
* Determines the metric with the most series, then queries each of its label names for distinct values using a simple `count by` query.  
* Prints a Slack‑friendly table with totals, top offenders, and the worst label for the top metric.  

Save the script as `scripts/prometheus_cardinality_report.sh`, make it executable, and schedule it via a CronJob or GitLab CI job.

### SC9‑A – Vulnerability analysis & fixes  

| # | Vulnerability | OWASP API category | Blast radius | Fix (code / infra) |
|---|---------------|--------------------|--------------|--------------------|
| 1 | **BOLA** – users can view other users’ records by ID | **Broken Access Control** (A1) | Unauthorized data disclosure, PII leakage, compliance violations. | Implement **object‑level permission** in DRF viewset: <br>```python
class UserResource(viewsets.ModelViewSet):
    queryset = User.objects.all()
    serializer_class = UserSerializer
    permission_classes = [IsOwnerOrReadOnly]

    def get_object(self):
        obj = get_object(queryset=self.get_queryset(), pk=self.kwargs['pk'])
        # Additional check: user must own the object or be admin
        if self.request.user != obj.owner and not self.request.user.is_staff:
            raise PermissionDenied("You do not own this resource.")
        return obj
``` |
| 2 | **Internal fields exposed** (created_by_employee_id, internal_notes) | **Information Exposure** (A2) | Leakage of sensitive business data, audit trails. | Use **nested serializers** with `read_only=True` for internal fields, or conditionally exclude them based on user role. <br>```python
class UserSerializer(serializers.ModelSerializer):

        model = User
        fields = ['id','public_field','internal_notes']
        read_only_fields = ['internal_notes']
``` |
| 3 | **No rate limiting** – 100k records extracted in 10 min | **Abuse** (A6) | DoS, data exfiltration, resource exhaustion. | Deploy **AWS WAF rate‑based rule** (100 req/5 min per IP) and/or **API Gateway throttling** (`rateLimit`/`burstLimit`). |
| 4 | **API keys in query string** – logged in CloudWatch/ALB | **Sensitive Data Exposure** (A2) | Keys can be leaked in logs, enabling unauthorized access. | Move keys to **Authorization header** (`Authorization: ApiKey <key>`). Rotate keys regularly and purge old logs. |

### SC9‑C – Defense‑in‑depth architecture & migration plan  

1. **Authentication shift**  
   * Move API keys to **`Authorization: ApiKey <key>`** header.  
   * Rotate all keys immediately; delete old keys from the system and from CloudWatch logs (use `aws logs filter`).  

2. **Adopt OAuth2**  
   * Deploy **AWS API Gateway** (or Kong) in front of the ALB.  
   * Configure **OAuth2 authorizer** (JWT validation) using a **Cognito User Pool** or custom JWT issuer.  
   * Issue **short‑lived JWTs** (e.g., 15 min) signed with RS256.  

3. **API gateway benefits**  
   * Centralized **rate limiting** (e.g., 100 req/5 min per authenticated user).  
   * Request **transformation** (strip query‑string keys, enforce header‑based auth).  
   * **Logging** to CloudTrail (data events) for audit.  

4. **CloudTrail data events** – Enable **read/write** events for the API Gateway and the underlying Lambda functions.  

5. **Field‑level encryption** – Use **AWS KMS** with ** envelope encryption** for PII columns in the RDS database. Apply a **dynamic data masking** policy for internal fields (`created_by_employee_id`, `internal_notes`).  

6. **Migration without breaking existing consumers**  
   * **Dual‑stack**: Keep the old API key authentication on a **different base path** (`/v1/`) while the new OAuth2‑protected API runs on `/v2/`.  
   * **Feature flag** in the application to switch behavior based on `Authorization` header presence.  
   * **Gradual rollout**: Use **Canary deployment** (e.g., 5 % traffic to `/v2/`) and monitor error rates. Once stable, switch DNS/CNAME records to point `/api/` to the new gateway.  

**Result:** The API is protected by multiple layers (network, auth, rate limiting, encryption), and the transition is backward‑compatible.

### SC10‑A – Multi‑cluster architecture & replication strategies  

| Approach | Description | RPO / RTO feasibility (12 ms latency, 200 TB MinIO) | Replication per component |
|----------|-------------|------------------------------------------------------|---------------------------|
| **Active‑passive (Velero backup/restore)** | Primary cluster (Chicago) is active; DR cluster (Dallas) holds snapshots taken periodically (e.g., every 5 min). On failure, restore the latest snapshot and promote to primary. | **RPO** ≈ 5 min (snapshot interval) → **exceeds** 15 s requirement. **RTO** depends on restore time (could be > 1 h). Not acceptable. | *Kubernetes workloads*: Velero snapshots (CSI snapshots). <br>*PostgreSQL*: Automated daily backups + point‑in‑time recovery (PITR) via WAL‑shipping to a standby (Dallas) – lag may be minutes. <br>*Redis*: Redis Sentinel with replica sync – lag < 1 s. <br>*RabbitMQ*: Mirror queues across clusters – near‑real‑time. <br>*MinIO*: Cross‑site replication (CSR) – ~ seconds per object. |
| **Active‑active (Istio multi‑cluster or Cilium Cluster Mesh)** | Both clusters run workloads; traffic is load‑balanced across them using **global traffic management** (e.g., **Istio GlobalTrafficPolicy** or **Cilium ClusterMesh**). Writes are **synchronously replicated** across regions (e.g., PostgreSQL logical replication, Redis Sentinel with `sync` mode, RabbitMQ federation, MinIO CSR). | **RPO** < 1 s (continuous replication). **RTO** < 1 h (failover via DNS/GSLB). Meets requirements. | *PostgreSQL*: **Logical replication** (pg_logical) with `synchronous_standby_names` set to Dallas standby → zero‑loss. <br>*Redis*: **Redis Sentinel** with `sentinel monitor` across regions; enable **replica-only** writes? Use **Redis Enterprise** for cross‑region replication (sub‑second). <br>*RabbitMQ*: **Queue mirroring** + **federation** (upstream/downstream) – near‑real‑time. <br>*MinIO*: **Site Replication** (MinIO CSR) – continuous sync. <br>*Kubernetes*: **Istio service mesh** provides traffic splitting; no need for backup. |

**Recommendation:** **Active‑active** with a service mesh. It satisfies the strict RPO/RTO, leverages the low 12 ms inter‑site latency, and provides seamless failover without restoring snapshots.

### SC10‑C – Automated failover orchestration  

**Sequence on Chicago site failure**

1. **Failure detection**  
   * **Health checks** – Deploy **Prometheus** alerts: `pg_up` on Chicago primary, `patroni_member_status` (primary role), `node_cpu_usage` > 95 % for > 5 min.  
   * **Site‑down monitor** – A **Kubernetes Deployment** (`site-monitor`) runs `curl` to a health endpoint on Chicago services every 10 s; if 3 consecutive failures, mark `site_chicago_unhealthy = true`.  

2. **DNS / GSLB failover**  
   * Use **AWS Route53 Failover** hosted zone with **health‑checked** records pointing to Dallas ALB.  
   * Triggered automatically when `site_chicago_unhealthy` becomes true (via Route53 API or external DNS controller).  

3. **Patroni automatic promotion**  
   * Dallas standby detects loss of `etcd` leader heartbeat from Chicago (Patroni watches etcd).  
   * Patroni promotes itself to **primary** (`SET /service/postgresql/leader` points to Dallas).  
   * Updates `postgresql.conf` `synchronous_standby_names` (empty) and restarts.  

4. **Redis Sentinel failover**  
   * Sentinel monitors Redis instances in both regions; when Chicago master goes down, Sentinel elects Dallas replica as new master.  

5. **RabbitMQ queue mirroring & federation**  
   * Enable **queue mirroring** to Dallas node (`policy: all`).  
   * Set up **federation links** (`rabbitmq-federation`) so that Dallas can act as upstream for any remaining Chicago consumers.  

6. **MinIO site replication catch‑up**  
   * MinIO **Cross‑Site Replication (CSR)** continuously syncs objects; after Chicago outage, Dallas will have the latest objects (lag < seconds).  

7. **Update OpenTofu state**  
   * A **Terraform Cloud workspace** runs a **post‑failover script** that imports the new primary (`aws_db_instance.primary`) into state, removes the old primary, and updates dependent resources (security groups, Route53 records).  
   * Use `terraform state mv` and `terraform import` as shown earlier.  

8. **Split‑brain handling**  
   * If both Chicago and Dallas think they are primary (e.g., network partition), **etcd** (or a separate **Consul** cluster) will have a leader election; the side with the majority of etcd nodes wins.  
   * Deploy a **conflict resolution service** that monitors `etcd` leader changes and forcibly demotes the “wrong” primary (using Patroni `DELETE /service/postgresql/leader`).  

9. **Fail‑back procedure**  
   * Once Chicago is back online, **Patroni** will detect the restored primary (via etcd).  
   * **Route53** health checks become healthy; DNS failover reverts automatically (or via a manual `aws route53 change-resource-record-sets`).  
   * **Data sync** – Use **logical replication** to bring Dallas up‑to‑date (Patroni will re‑establish replication slots).  
   * **Application traffic** – Gradual cut‑over: enable **traffic splitting** (Istio VirtualService weight 100 % to Chicago) after confirming replication lag < 1 s.  

**Metrics for go/no‑go**  

* **Replication lag** (`pg_last_xact_replay_timestamp`) < 1 s.  
* **Application error rate** < 0.1 % during failover window.  
* **Latency** to Dallas primary < 100 ms (acceptable).  
* **All services** (`/health` endpoints) report `200 OK`.  

If any metric breaches thresholds, abort the failover, revert DNS, and alert SREs for manual intervention.
