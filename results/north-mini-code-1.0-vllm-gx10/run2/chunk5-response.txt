- **Class**: reference type, allocated on the managed heap, default value `null`, can be `null` reference, supports inheritance, finalizer (`~T`), can be `null`‑able (`class?`).  
- **Struct**: value type, allocated on the stack (or inline in containing object), default value is the CLR default for each field, cannot be `null` (except `struct?` nullable), does **not** support inheritance (cannot be base of another class/struct), cannot have a finalizer.  

**When to use a struct?**  
- Small, immutable value objects that are frequently passed by value (e.g., `Point`, `DateTime`, `Guid`).  
- When you want to avoid the overhead of heap allocation and reference indirection.  
- When the type logically represents a “value” rather than an “object” (e.g., a currency amount, a 2‑D coordinate).

**DN2** – *IEnumerable<T> vs IQueryable<T>*  
- **IEnumerable<T>**: represents a collection that can be enumerated. The query expression is evaluated **immediately** (client‑side) in C#; the provider is the `IEnumerable` itself.  
- **IQueryable<T>**: represents a **queryable** collection that can be translated to the underlying data source (SQL, LINQ to Objects, etc.). The expression tree is **deferred** and can be translated by a provider (`IQueryProvider`).  

**Why it matters for DB queries**  
- Using `IQueryable<T>` lets you push filtering, ordering, grouping, etc., to the database engine, resulting in far fewer rows transferred and optimized execution.  
- Using `IEnumerable<T>` forces the filtering to happen in C# after the whole table is fetched, which is inefficient for large data sets.

**DN3** – *Async/await, Task vs ValueTask*  
- **Async/await** works by returning a `Task`/`ValueTask` from an async method. The compiler generates state‑machine code that suspends at `await` points, preserving the method’s locals.  
- **Task**: represents an asynchronous operation that may produce a result (`Task<TResult>`) or simply signal completion (`Task`). It is a reference‑type, allocated on the heap, and includes fields for result, exception, etc.  
- **ValueTask<TResult>` (or `ValueTask`)**: a value‑type wrapper that can hold either a result or a `Task`. It avoids allocating a `Task` when the operation completes synchronously (e.g., fast I/O).  

**When to use `ValueTask`**  
- In hot paths where many async calls are made and most complete quickly (e.g., reading from a socket, file, or in‑memory cache).  
- When you want to reduce allocation pressure; `ValueTask` reuses the stack slot for the result.

**DN4** – *Dependency Injection (DI) in .NET*  
- **Registration**: services are registered with an `IServiceProvider` (or `IServiceCollection`).  
- **Lifetimes**:  
  1. **Transient** – a new instance each time the service is resolved.  
  2. **Scoped** – same instance for the duration of a single request (e.g., HTTP scope). Created once per scope and disposed with the scope.  
  3. **Singleton** – a single instance for the lifetime of the application.  

- **Common bug**: injecting a **Scoped** service into a **Singleton** (or vice‑versa). The singleton holds a reference to a scoped instance that may be disposed or replaced, leading to `ObjectDisposedException` or stale data. The fix is to resolve the scoped service inside the singleton’s method (e.g., via `IHttpContextAccessor` or explicit `IServiceScope`).

**DN5** – *String vs ReadOnlySpan<char> vs Span<T>*  
- **`string`**: immutable, UTF‑16, reference‑type. Operations create new strings (e.g., `Substring`, `Replace`).  
- **`ReadOnlySpan<char>`**: read‑only view over a `string`, `char[]`, `Memory`, etc. Allows zero‑copy slicing and efficient `IndexOf`, `Contains`, `AsSpan`, etc., without copying.  
- **`Span<T>`** (or `Memory<T>`): mutable view over a `char[]`, `ArrayPool<char>`, native memory, etc. Enables in‑place operations (`.Slice()`, `.CopyTo()`, `MemoryMarshal.AsBytes`).  

**When to use `Span<T>`**  
- When you need to mutate data (e.g., parsing, formatting) and want to avoid extra allocations.  
- For high‑performance scenarios (e.g., parsing binary data, text processing) where you can work directly on the underlying buffer.

**DN6** – *.NET GC, generations, LOH, IDisposable*  
- **GC** compacts memory to reclaim unreachable objects. It uses **generation-based** collection:  
  - **Gen 0** – short‑lived objects (most allocations). Collected frequently.  
  - **Gen 1** – medium‑lived objects promoted from Gen 0.  
  - **Gen 2** – long‑lived objects (e.g., static caches). Collected less often.  
- **Large Object Heap (LOH)**: holds objects ≥ 85 KB. Collected only in Gen 2, can cause fragmentation; historically not compacted (now partially compacted in .NET Core/5+).  
- **IDisposable**: for **unmanaged resources** (file handles, sockets, GDI objects). The GC cannot know when to release them, so `Dispose` must be called explicitly (or via `using`). Even with GC, unmanaged resources must be freed deterministically to avoid leaks.

**DN7** – *ConfigureAwait(false)*  
- **Default (`ConfigureAwait(true)`)**: after an `await`, the continuation resumes on the **capturing synchronization context** (e.g., UI thread in ASP.NET, synchronization context of the caller).  
- **`ConfigureAwait(false)`**: tells the awaiter **not to capture** the current `SynchronizationContext`. The continuation resumes on the thread pool.  

**When to use `false`**  
- In library code where you don’t want to inadvertently block UI threads or cause deadlocks (e.g., ASP.NET Core middleware, background services).  
- When you know you’ll continue on a thread‑pool thread and want to avoid context‑switch overhead.  

**When **not** to use `false`**  
- In UI or ASP.NET apps where you need to update UI controls or rely on the captured context for thread‑safety.  

**Relation to `SynchronizationContext`**: `ConfigureAwait(false)` prevents the awaiter from calling `SynchronizationContext.Post`/`Send`. If you need the context, keep the default.

**DN9** – *ObjectDisposedException on DbContext under high concurrency*  

**Likely cause**: **DbContext lifetime mismatch**. In ASP.NET Core, the default DI registration for `DbContext` is **Scoped**. If a **Singleton** (or **Transient**) service holds a reference to a `DbContext` and re‑uses it across requests, the underlying `DbContext` may be disposed after the request while the singleton still tries to use it.  

**Fix**:  
- Register `DbContext` as **Scoped** (the default).  
- Ensure any service that needs the context resolves it **within the same scope** (e.g., via constructor injection).  
- If you need a longer‑lived service that uses the context, resolve the context **lazily** inside methods using `IHttpContextAccessor` or create a new scope (`using var scope = _sp.CreateScope()`).  

**EF Core interaction**: EF Core expects the `DbContext` to be used within a single logical operation (usually a request). The `DbContext` tracks changes; disposing it clears that tracking, causing `ObjectDisposedException` if you try to use a disposed context.

**DN10** – *Record vs class, record struct*  

- **Class**: reference type, mutable by default, supports inheritance, can have a finalizer.  
- **Record**: reference type with **positional** and **named** members, **structural equality** (`Equals` compares field values), **with` expression` for immutability, **generated `ToString`, `GetHashCode`, `Deconstruct`**. Records are **inheritable** but equality is defined by the base’s fields.  
- **Record struct**: value type version of a record. Behaves like a struct (stack‑allocated, `Equals` compares values) but retains record features (`with` expression, positional syntax). Use when you need value semantics and structural equality but want the syntax of records.  

**When to choose each**:  
- **Class** – when you need reference semantics, inheritance hierarchy, mutability, or a large object.  
- **Record** – when you want immutable data carriers with value‑based equality (DTOs, domain entities).  
- **Record struct** – for small, frequently passed value objects where you want record syntax but value semantics (e.g., `Point`, `Guid`).

**DN11** – *ref, out, in parameter modifiers*  

| Modifier | Purpose | Usage |
|----------|---------|-------|
| **`ref`** | Passes a parameter **by reference**; caller must provide a variable that already exists. The method can read **and** write the argument. | `void Swap(ref int a, ref int b) { (a,b) = (b,a); }` |
| **`out`** | Passes a parameter **by reference**; caller may not have a variable. The method **must** assign a value to the `out` parameter before returning. | `bool TryParse(string s, out int result) { … result = …; return true; }` |
| **`in`** | Prevents the parameter from being modified inside the method (read‑only reference). Useful for large structs to avoid copying. | `void Print(in string s) { Console.WriteLine(s); }` |

**DN12** – *Nullable reference types (NRT)*  

- **`?` annotation** (`string?`) indicates the variable may be **null** at runtime, but the compiler treats it as **non‑null** by default unless `#nullable enable` is present.  
- **`#nullable enable`** turns on NRT analysis for the project, causing warnings when a non‑nullable reference is assigned `null` or when a nullable reference is dereferenced without null‑check.  

**Difference from nullable value types (`int?`)**:  
- `int?` is a **value type** that can hold either a boxed `int` or `null`. It’s a single variable that can be `null`.  
- `string?` is a **reference type** that can be `null`. NRTs are **compile‑time** annotations; they do **not** change runtime behavior (the CLR still sees `null`).

**DN13** – *LINQ*  

- **LINQ** (Language Integrated Query) provides a uniform way to query collections, databases, XML, etc., using a functional style.  
- **Method syntax** (`list.Where(x => x > 5).Select(x => x.ToString())`) – each operation is a separate method call.  
- **Query syntax** (`from x in list where x > 5 select x.ToString()`) – reads like SQL; it is **syntactic sugar** that the compiler translates to method syntax.  
- **Deferred execution**: LINQ queries are **lazy**; the actual iteration occurs when you enumerate the result (e.g., `foreach`, `ToList`, `First`). This allows building pipelines without materializing intermediate collections.

**DN16** – *ASP.NET Core middleware pipeline*  

- **`app.Use()`**: adds a middleware component that receives `RequestDelegate` and returns a new delegate. Runs **in order**; each middleware can modify request/response or short‑circuit.  
- **`app.Map()`**: conditionally adds a branch based on the request path (or other predicate). Useful for mounting separate pipelines (e.g., `/admin/*`).  
- **`app.Run()`**: final endpoint that writes the response directly; no further middleware runs after it.  

**Ordering**: middleware is executed **top‑down** as it’s added; `Use` adds to the left of the pipeline (closest to the request). Exception handling middleware is usually added **early** (e.g., `app.UseExceptionHandler()`) so it can catch exceptions from later middleware.  

**Exception handling**: `UseExceptionHandler` registers a middleware that catches unhandled exceptions, logs them, and either renders a custom error page or re‑throws. It runs **after** other middleware but **before** the final `Run`.

**DN17** – *Channel<T> vs BlockingCollection<T>*  

- **`Channel<T>`** (from `System.Channels` / `System.Threading.Channels`): a **unbounded** or **bounded** channel that supports async `Writer`/`Reader` with backpressure. It’s built on `Memory<T>` and can be used across thread boundaries efficiently.  
- **`BlockingCollection<T>`**: a thread‑safe collection with `Add`/`Take` that internally uses a `BlockingCollection` + `ConcurrentQueue`. It provides **blocking** and **TakeWhen`** APIs but does not expose a separate writer/reader abstraction.  

**Example – bounded channel for producer‑consumer backpressure**  

```csharp
var options = new BoundedChannelOptions(10) { FullMode = BoundedChannelFullMode.Wait };
var channel = new Channel<int>(options);
var writer = channel.Writer;
var reader = channel.Reader;

// Producer
Task.Run(async () =>
{
    for (int i = 0; i < 100; i++)
    {
        await writer.WriteAsync(i); // blocks if buffer full
    }
    writer.Complete();
});

// Consumer
await foreach (var item in reader.ReadAllAsync())
{
    Console.WriteLine(item);
}
```

If the channel fills, `WriteAsync` blocks (or can be configured to drop/signal), providing backpressure.

**DN19** – *TPL Dataflow (System.Threading.Tasks.Dataflow)*  

- **ActionBlock<T>`**: a **synchronous** or **asynchronous** action block that executes a user‑provided `Action<T>` or `Func<T, Task>` on each received item. Supports `Completion` and `Faulting`.  
- **TransformBlock<TInput, TOutput>`**: applies a transformation function to each input, producing an output item. Can be synchronous or async.  
- **BufferBlock<T>`**: a simple buffer that can hold items; supports `Post`, `TryReceive`, `TryComplete`.  

**Comparison with `System.Threading.Channels`**:  
- **Dataflow** is higher‑level, provides built‑in **scheduling**, **error handling**, **completion**, and **linking** between blocks.  
- **Channels** are lower‑level, focus on **zero‑copy** `Memory<T>` and are ideal for high‑throughput scenarios (e.g., networking). Channels require manual coordination for backpressure, while Dataflow blocks manage it internally.

**P2** – *GIL*  

- The **Global Interpreter Lock** is a mutex in CPython that ensures only **one thread executes Python bytecode at a time**.  
- **Affected workloads**: CPU‑bound tasks (e.g., heavy numeric loops) and any code that holds the GIL for long periods; they cannot benefit from multiple cores.  
- **Workarounds**:  
  - Use **multiprocessing** (spawn separate interpreter processes) for CPU‑bound work.  
  - Use **asyncio** with async I/O for I/O‑bound tasks (releases GIL during waits).  
  - Use **Cython**, **Numba**, or **extension modules** that release the GIL.  
  - Use **threading** for I/O‑bound parallelism (e.g., network requests) where the GIL is released during I/O operations.

**P3** – *deepcopy vs copy*  

- **`copy`** (shallow copy): creates a new container but references the **same** objects inside. For mutable containers, changes to nested objects affect both.  
- **`copy.deepcopy`**: recursively creates new objects for nested structures, so modifications are independent.  

**Example where shallow copy fails**  

```python
import copy

a = {'items': [1, 2, 3]}
b = copy.copy(a)      # b['items'] is the same list as a['items']
b['items'].append(4)
print(a)   # {'items': [1, 2, 3, 4]}  <-- unexpected!
c = copy.deepcopy(a) # c has its own copy of the list
c['items'].append(5)
print(a)   # {'items': [1, 2, 3, 4]}  <-- unchanged
```

**P4** – *Decorators*  

A decorator is a **callable** that wraps a function, returning a new function that typically adds behavior before/after the original call.  

**Decorator that logs execution time**  

```python
import time
from functools import wraps

def log_execution_time(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

@log_execution_time
def compute():
    time.sleep(0.5)
    return 42

print(compute())  # prints "compute took 0.5002s", then 42
```

**P5** – *Generators and yield*  

- **Generator function**: contains `yield` statements; when called it returns a **generator iterator** that produces values lazily.  
- **Difference from returning a list**: a generator yields values one‑at‑a‑time, preserving state between yields; a list materializes all items upfront.  
- **`yield from`**: delegates to another iterable, flattening nested generators (e.g., `yield from child_gen`).  

**Example**  

```python
def count_up_to(n):
    for i in range(1, n+1):
        yield i

def flatten(gen):
    yield from gen

print(list(count_up_to(3)))          # [1, 2, 3]
print(list(flatten(count_up_to(2)))) # [1, 2]
```

**P6** – *Asyncio event loop*  

- **Event loop**: core of asyncio; drives I/O operations, schedules callbacks, and manages tasks.  
- **`asyncio.run()`**: high‑level entry point that creates a new event loop, runs the given coroutine, and cleans up. Use for **top‑level** scripts.  
- **`asyncio.gather()`**: schedules multiple coroutines concurrently and waits for all to complete; returns a list of results.  
- **`asyncio.create_task()`**: schedules a coroutine as a **Task** (a future) to run soon on the loop; returns a `Task` you can await or combine with `gather`.  

**Why not `time.sleep()` inside async**: `time.sleep()` blocks the thread, holding the GIL and preventing the event loop from switching to other tasks. Use `asyncio.sleep()` for asynchronous waiting.

**P7** – *Method Resolution Order (MRO)*  

- Python 3 uses **C3 linearization** to produce a deterministic order that respects both inheritance hierarchy and the order of base classes.  
- **Diamond inheritance** example:

```python
class A:
    def who(self): return "A"
class B(A):
    pass
class C(A):
    def who(self): return "C"
class D(B, C):
    pass

print(D().who())   # prints "C"
```

**Explanation**:  
- MRO for `D` is `[D, B, C, A, object]`.  
- `B` does not override `who`, so Python continues to `C`, which **does** override `who` with `"C"`.  
- Hence `D().who()` returns `"C"`.

**P8** – *Metaclass*

**P9** – *Multiprocessing vs Threading vs concurrent.futures*  

| Approach | Mechanism | Best for | Serialization |
|----------|-----------|----------|---------------|
| **Threading** | OS threads sharing memory (GIL limits CPU parallelism) | I/O‑bound tasks, leveraging GIL release during I/O | No serialization needed |
| **Multiprocessing** | Separate processes, each with its own interpreter and memory space | CPU‑bound tasks, bypass GIL | Objects must be **picklable** to pass between processes |
| **concurrent.futures** | High‑level API over threads (`ThreadPoolExecutor`) or processes (`ProcessPoolExecutor`) | General parallelism; choose executor type per need | Same serialization rules as underlying mechanism (threads = none, processes = pickling) |

**Pickling implications**: When using `ProcessPoolExecutor`, arguments and return values are pickled (serialized) to the worker process and unpickled back. Large objects or non‑picklable resources (e.g., open files, sockets) need special handling (e.g., `multiprocessing.Manager`, `shared memory`).

**P10** – *__slots__*  

- **`__slots__`** defines a fixed set of attributes for a class, preventing the creation of a `__dict__` (and `__weakref__` unless added).  
- **When to use**:  
  - Large numbers of instances where memory overhead matters (e.g., game entities).

- **What it prevents**: Dynamic attribute assignment (`obj.newAttr = …`) and the per‑instance `__dict__` overhead.  
- **Memory impact**: Each instance stores attributes directly in a compact array, reducing memory per object (often ~50% less). However, you lose the ability to add attributes at runtime.

**P13** – *`==` vs `is`*

- **`is`**: compares **identity** (same object in memory).

**P15** – *Context managers*

from contextlib import contextmanager

        session.rollback()

**P16** – *Type hinting*  

- **`typing.Union[X, Y]`** – `X | Y` (Python 3.10+).  
- **`Optional[T]`** – `Union[T, None]`.  
- **`Literal[value]`** – restricts to a specific literal value(s).  
- **`TypeVar`** – generic placeholder (`T = TypeVar('T')`).  
- **`Protocol`** – structural typing; defines interface-like contracts.  

**Mypy / pyright** use these to perform static checks: detect mismatched argument types, uncover potential `None` dereferences, enforce return types, and validate generic usage.  

---

**P17** – *Data model dunder methods*  

- **`__repr__`** – unambiguous, developer‑friendly representation (ideally `ClassName(attr=value)`).  
- **`__str__`** – human‑readable string (often defaults to `__repr__` if `__str__` not defined).  
- **`__eq__`** – defines value equality; if defined, Python **automatically** makes the object **unhashable** unless `__hash__` is also defined (sets `__hash__ = None`).  
- **`__getattr__`** – called when attribute lookup fails; **`__getattribute__`** is called for **all** attribute accesses (including existing ones). Overriding `__getattribute__` can cause infinite recursion if not careful.  

---

**P18** – *Descriptors*  

- **Descriptor protocol**: objects implementing `__get__`, `__set__`, `__delete__`. When accessed as a class or instance attribute, the descriptor’s `__get__` is invoked.  
- **`property`**, **`classmethod`**, **`staticmethod`** are built‑in descriptors:  
  - `property` – computes value on get, optionally validates on set.  
  - `classmethod` – binds the method to the class, passing the class as first argument.  
  - `staticmethod` – binds the method to the class without automatic argument.  

---

**P19** – *Python import system*  

- **Absolute import**: `import module.submodule`. Resolves relative to `sys.path`.  
- **Relative import**: `from . import submodule` or `from ..parent import sibling`. Used inside packages.  

- **`sys.path`** – list of directories searched for modules; includes script directory, `PYTHONPATH`, installed packages.  
- **`__init__.py`** – marks a directory as a Python package (can contain package‑level code).  
- **Namespace packages** – directories without `__init__.py` that contribute to a package (PEP 420).  

- **Finder** – locates a module spec (`importlib.abc.MetaPathFinder`).  
- **Loader** – loads the module code (`importlib.abc.Loader`).  

---

**P20** – *Dataclasses*  

- **Definition**: class decorator that automatically adds generated `__init__`, `__repr__`, `__eq__`, `__hash__`, `__lt__`, etc., based on annotated fields.  
- **Comparison with `attrs` and `pydantic`**:  
  - `attrs` is more concise, uses `attr.s` decorator, supports `__init__` generation, validators, converters.  
  - `pydantic` focuses on **validation**, **serialization** (JSON), and **type‑based** defaults; provides rich error messages and OpenAPI generation.  

- **`__post_init__`** – a user‑defined method called after auto‑generated `__init__`; used for extra initialization, validation, or computed fields.  
- **Field factories** – `field(default_factory=list)` creates a new mutable default per instance.  
- **Frozen dataclasses** – `frozen=True` makes instances immutable (raises `FrozenInstanceError` on assignment).  
- **Inheritance** – fields are combined; `__init__` includes parent fields; `__post_init__` can call `super().__post_init__()`.  

**When to choose Pydantic over dataclasses**:  
- Need **runtime validation** (e.g., email format, range checks).  
- Want **automatic serialization/deserialization** to/from JSON, ORM models, or config files.  
- Require **rich error messages** and **OpenAPI/Swagger** generation for APIs.  
- Prefer **type‑based defaults** and **extra** configuration (e.g., `extra='forbid'`).  

Dataclasses are ideal for simple data carriers, immutable value objects, or when you want minimal boilerplate without validation or serialization concerns.<|END_TEXT|>
