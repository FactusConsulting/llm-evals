**K2** – A **ClusterIP** Service creates a virtual IP (`10.x.y.z`) that, via `kube-proxy`/`iptables`, maps incoming traffic to a set of pod endpoints using the endpoints object. `kube-proxy` maintains a NAT table that rewrites destination addresses to the selected pod’s IP and port.

**K3** –  
- **PersistentVolume (PV)**: a cluster‑level storage resource (disk, SSD, NFS) that is provisioned by a storage class and lives independently of pods.  
- **PersistentVolumeClaim (PVC)**: a namespaced request for storage attributes (size, access modes) that binds to a matching PV.  
- **StorageClass**: a definition that describes how PVs are provisioned (e.g., `aws-ebs`, `nfs`), including reclaim policy and volumeBindingMode.  
They relate as: **StorageClass** → **PV** (created on demand) ← **PVC** (binds to PV). Pods claim storage via a PVC, which resolves to a PV that was provisioned using the referenced StorageClass.

**K4** – Troubleshooting a pod in **CrashLoopBackOff**:  
1. **Check pod logs** (`kubectl logs <pod>`) for error messages or stack traces.  
2. **Inspect the container’s exit code** (`kubectl get pod -o wide`) and any `TerminationMessage`.  
3. **Review resource limits** (`requests` vs `limits`) to ensure OOMKilled or throttling.  
4. **Validate configuration and dependencies** (environment variables, ConfigMaps, image pull secrets, network connectivity, DNS).  
5. **Run the container manually** (`docker run <image>`) to see if it works outside Kubernetes.  
6. **Check node health** (disk pressure, pressure, etc.) that could cause restarts.

**K5** – **CoreDNS** is the default DNS server in a Kubernetes cluster; it provides service discovery and cluster‑internal name resolution (e.g., `myservice.namespace.svc.cluster.local`). If CoreDNS pods are down, pods lose the ability to resolve internal names and external domains, causing DNS queries to fall back to the upstream resolver (often the node’s `/etc/resolv.conf`), which may be slower or unavailable.

**K6** – The scheduler follows a **filter → score → select** pipeline:  
- **Filtering (predicates)** discards nodes that cannot run the pod (e.g., insufficient CPU/memory, nodeSelector mismatches, taints without tolerations, pod affinity violations).  
- **Scoring (priorities)** ranks remaining nodes; higher scores get placed first.  
- **Selection** picks the highest‑scoring node.  
Key factors considered:  
1. **Resource availability** (CPU, memory, allocatable).  
2. **Node affinity/anti‑affinity** rules.  
3. **Taint/toleration** compatibility.  
4. **Inter‑pod affinity/anti‑affinity** constraints.  
5. **Topology spread constraints** (distance, zones).  
6. **Custom priority functions** (e.g., based on labels, resource usage).

**K8** – Full Ingress request flow (NGINX Ingress Controller):  
1. **External Load Balancer** (AWS ALB, GCE LB, etc.) receives the external IP and port, performs health checks, and forwards the TCP/HTTP request to the Ingress Controller’s Service (type `LoadBalancer`/`NodePort`).  
2. **Ingress Controller Service** (ClusterIP/NodePort) routes traffic to the NGINX pods.  
3. **NGINX Ingress Controller** reads the Ingress spec, determines the backend Service, and rewrites the host/path, then forwards the request to the **backend Service** (type `ClusterIP`).  
4. **Backend Service** selects a set of **Endpoints** (pod IPs) via Endpoints object.  
5. **kube-proxy** on the node maintains iptables rules that NAT the request’s destination to the chosen pod IP and port.  
6. The pod receives the request, processes it, and returns a response that follows the same reverse path through iptables, Service, Ingress Controller, and external LB back to the client.

**K9** – A **NetworkPolicy** defines inbound/outbound pod‑level network rules (allow/deny). With **no NetworkPolicy** in a namespace, the default is “allow all traffic” (the namespace is wide open). Applying a NetworkPolicy that selects certain pods **replaces** the default for those pods, allowing only traffic that matches the policy rules; other pods remain unrestricted unless also selected.

**K10** – **RollingUpdate**: incrementally replace pods in a Deployment; new replicas are created while old ones are terminated, maintaining availability. **Recreate**: deletes all existing replicas before creating new ones, causing a brief downtime. Choose **Recreate** when the new version cannot coexist with the old (e.g., configuration changes that require a full restart, or when the pod’s lifecycle cannot be safely upgraded incrementally).

**K11** – A **namespace** is a logical partition for Kubernetes resources (pods, services, etc.) that enables multi‑tenant isolation. Default namespaces created in a fresh cluster: `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

**K12** – `kubectl describe pod <name>` shows detailed runtime state:  
- **Pod conditions** (Ready, ContainersReady, etc.) – not in `get`.  
- **Container statuses** (waiting reasons, terminated exit codes, restarts) – not in `get`.  
- **Events** (reason for restarts, OOMKilled, image pull errors) – not in `get`.  
- **IP address**, **QoS class**, **node name**, **resource requests/limits** (more granular than `get`).

**K13** – A **ConfigMap** is an API object that holds key‑value data (strings, JSON/YAML) to inject configuration into pods without images. Consumption methods:  
1. **Environment variables** – `envFrom` or `env` referencing the ConfigMap keys.  
2. **Projected volume** – mount the ConfigMap as a file in a volume (single mount point).  
3. **Subpath volume** – mount individual keys as separate files (via `items`).

**K14** –  
- **ClusterIP**: internal service, reachable only inside the cluster; no external exposure.  
- **NodePort**: adds a static port (30000‑32767) on each node; external clients can hit `<node-ip>:<nodeport>` and traffic is forwarded to the ClusterIP.  
- **LoadBalancer**: creates an external load balancer (cloud provider) with a provisioned external IP; traffic is load‑balanced to the ClusterIP, providing high availability and cloud‑native integration.

**K15** – A **DaemonSet** ensures a copy of a pod runs on all (or some) nodes, typically for node‑level services (e.g., log collectors, node exporters). Use a DaemonSet instead of a Deployment when the workload must be present on every node and should not be scaled via replicas; Deployments manage replica counts independent of node count.

**K16** – **Taints** are node‑level repulsions (`node.spec.taints`) that prevent pods from scheduling onto a node unless they have a matching **toleration**. **Node affinity** is a soft/hard requirement expressed in pod spec that selects nodes based on labels.  
- **Taint/Toleration use case**: schedule exclusive GPU nodes only for GPU workloads (`taint: key=gpu, effect=NoSchedule`; pod tolerates `gpu`).  
- **Node affinity use case**: place pods only on nodes with label `environment=prod` (`affinity.nodePreferences.matchExpressions`).

**K17** – A **Kubernetes Operator** is a controller that extends Kubernetes API to manage complex applications’ lifecycle (install, update, backup). It differs from a standard controller by **encoding application‑specific logic** into custom resources (CRs) and **self‑healing** using Kubernetes primitives. Operators solve problems like **declarative configuration**, **version‑aware upgrades**, and **multi‑cluster management** without manual intervention.

**K18** – **etcd consistency model**: linearizable (strong) consistency for reads/writes; all operations go through a quorum (majority) of etcd members. If the quorum is lost (e.g., <2 of 3 nodes reachable), the cluster **cannot commit new states**; APIs become unavailable and the control plane is considered unhealthy. Recovery after permanent loss of 2/3 nodes:  
1. Install a new etcd member on a fresh node, seed it with the remaining node’s data (`etcd --initial-cluster` with `--initial-advertise-peer-urls`).  
2. Remove the lost members from the cluster (`etcdctl del` or `etcdctl member remove`).  
3. Restore the full cluster to a healthy quorum (now 2 nodes).  
4. Restore the lost data from snapshots/backups (if needed) and rejoin any recovered nodes.

**K19** – **RBAC components**:  
- **Role** – namespaced permissions (e.g., `get`, `list`, `watch` pods).  
- **ClusterRole** – cluster‑wide permissions.  
- **RoleBinding** – binds a Role to subjects (User, Group, ServiceAccount) within a namespace.  
- **ClusterRoleBinding** – binds a ClusterRole to subjects cluster‑wide.  

Manifest for read‑only access to pods and logs in a single namespace (`myns`):  

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: myns
rules:
- apiGroups: [""]
  resources: ["pods","pods/log"]
  verbs: ["get","list","watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: myns
subjects:
- kind: User
  name: "developer@example.com"   # or a ServiceAccount
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```
If cluster‑wide needed, replace `Role`/`RoleBinding` with `ClusterRole`/`ClusterRoleBinding`.

**K20** – Inside a pod, `/etc/resolv.conf` often contains many nameservers and `options ndots:5`. The `ndots` option tells the DNS resolver to query external DNS only after trying local domains; a high `ndots` (e.g., 5) causes the resolver to perform many iterative queries before falling back, leading to >5 s latency. Fix with `dnsConfig`:  

```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "2"   # lower threshold for faster resolution
```
or explicitly set `nameservers` if using an internal DNS. This reduces the number of queries and speeds up external domain resolution.

**D1** – `git rebase` rewrites commit history by moving a branch onto another, creating a linear timeline; `git merge` combines histories, preserving the original commits and creating a merge commit. Avoid rebasing when working on **public/shared branches** (e.g., main) because it rewrites history and can cause conflicts for collaborators.

**D2** – **TCP** is connection‑oriented, reliable, with flow control and ordered delivery (e.g., HTTP, SMTP). **UDP** is connectionless, unreliable, no ordering (e.g., DNS, DHCP, VoIP).

**D3** – A **race condition** occurs when two or more threads/processes access shared data concurrently and the final outcome depends on timing. Example (C++): two threads increment a global counter `int counter = 0;` without a lock:

```cpp
void increment() { counter++; }
```
If both threads read `counter` (0) simultaneously, each writes back 1, resulting in final value 1 instead of 2.

**D4** – **Symmetric encryption** uses a single secret key for both encryption and decryption (e.g., AES). **Asymmetric encryption** uses a public/private key pair (e.g., RSA). In **TLS**, the client generates a premaster secret, encrypts it with the server’s public key (asymmetric), and both derive the same symmetric session key to encrypt application data (symmetric) for performance.

**D5** – A **container image layer** is an immutable filesystem change (diff) added on top of the previous layer; Docker builds images as a stack of layers. **Layer caching** encourages reusing unchanged layers (e.g., `FROM` base, install dependencies) to speed builds and reduce image size. Best practice: combine related commands (e.g., `RUN apt-get install ... && rm -rf ...`) to create fewer layers and improve cache hits.

**D6** – For intermittent HTTP 503s:  
1. **Check application logs** for errors, timeouts, or health‑check failures.  
2. **Inspect the underlying service/health checks** (database connectivity, external API calls).  
3. **Review resource utilization** (CPU, memory, network) on the pod/node for throttling or OOM risks.  
4. **Examine deployment/rollout status** (e.g., pending updates, pod disruptions) and any recent configuration changes.  
5. **Validate external dependencies** (load balancer, CDN, downstream services) for outages.

**D7** – **CAP theorem**: a distributed system can provide at most two of **Consistency**, **Availability**, **Partition tolerance**.  
- **CP example**: a banking transaction system that must be consistent and tolerate network partitions (e.g., Cassandra with `QUORUM` reads/writes).  
- **AP example**: a social media feed that eventually converges; it prioritizes availability and partition tolerance (e.g., DynamoDB with eventual consistency).

**D8** – **Horizontal scaling** adds more instances of the same service (scale‑out). **Vertical scaling** increases resources (CPU/RAM) of existing instances (scale‑up). Architectural patterns enabling horizontal scaling: **Microservices**, **Stateless design**, **Load balancing**, **Container orchestration** (Kubernetes), **Auto‑scaling** based on metrics.

**D9** – An **environment variable** is a name‑value pair passed to processes, used for configuration. To persist across shell sessions on Linux:  

```bash
echo 'export MYVAR="value"' >> ~/.bashrc   # or ~/.profile
source ~/.bashrc
```
or use `export` in `~/.profile` for login shells.

**D10** – **JSON** is a language‑independent text format using `key: value` pairs with strict syntax (no comments). **YAML** is a human‑readable superset of JSON, using indentation and anchors.  
- JSON advantage: easy parsing, native support in many languages.  
- YAML advantage: readability, support for complex data structures and comments.

**D11** – A **REST API** follows **Representational State Transfer** principles: stateless, client‑server, uniform interface (resource URIs, standard HTTP methods).  
- **GET** – retrieve a representation.  
- **POST** – create a new resource (or trigger an action).  
- **PUT** – replace an existing resource entirely.  
- **DELETE** – remove a resource.

**D12** – **Version pinning** fixes exact versions of dependencies (e.g., `package@1.2.3`) to ensure reproducible builds. It prevents unexpected updates that could break the application or cause drift across environments.

**D13** – **Compiled languages** translate source code to machine code before execution (e.g., C, C++). **Interpreted languages** execute source code via an interpreter at runtime (e.g., Python, JavaScript). Compiled languages typically run faster; interpreted languages offer easier rapid prototyping.

**D14** – A **reverse proxy** sits in front of servers, forwarding client requests to the appropriate backend and returning responses. A **forward proxy** acts on behalf of clients to reach external resources.  
- **NGINX** – high‑performance web server/reverse proxy; use case: load balancing HTTP(S) traffic.  
- **HAProxy** – lightweight TCP/HTTP proxy; use case: layer‑4 load balancing for high‑throughput services.  
- **Envoy** – service mesh proxy; use case: fine‑grained traffic management in microservices.

**D15** – A **deadlock** is a situation where two or more processes are each waiting for a resource held by another, causing all to stall. **Coffman conditions** (all must hold):  
1. **Mutual exclusion** – resources not shareable.  
2. **Hold and wait** – processes hold resources while waiting for others.  
3. **No preemption** – resources cannot be forcibly taken.  
4. **Circular wait** – a cycle of processes waiting for each other’s resources.

**D16** – **Eventual consistency** means that, after no further updates, all replicas will converge to the same value, but reads may see stale data temporarily. **Cassandra** handles read‑after‑write via tunable consistency levels: `ONE`, `QUORUM`, `ALL`, etc. For a write, you set `writeConsistency` (e.g., `QUORUM`); for a read, you set `readConsistency`. Choosing `QUORUM` gives stronger consistency while still allowing availability during partitions.

**D17** – **mTLS (mutual TLS)** requires both client and server to present X.509 certificates for authentication, in addition to verifying each other’s identity. Handshake steps:  
1. **ClientHello** – offers TLS versions, ciphers.  
2. **ServerHello** – selects parameters, sends server certificate.  
3. **ClientCertificate** – client sends its certificate (if requested).  
4. **Certificate verification** – both sides validate peer certificates against trusted CAs.  
5. **Key exchange** (e.g., ECDHE) to derive a shared secret.  
6. **Finished** messages confirm handshake integrity.  
Common uses: **service‑to‑service communication** in service meshes (Istio, Linkerd), **API gateways**, **database access**, **Kubernetes API server** authentication.

**D18** – A **hash table** maps keys to values via a hash function that computes an index into an array of buckets. **Collision resolution**:  
- **Chaining** – each bucket holds a linked list (or tree) of entries.  
- **Open addressing** – probe sequence (linear, quadratic, double hashing) finds next free slot.  
Average‑case time complexity: **O(1)** for insert, lookup, delete. Worst‑case (all keys collide) → **O(n)** for each operation.

**D19** – The **circuit breaker** pattern monitors service calls; it trips to an **open** state when failures exceed a threshold, preventing further requests and allowing the system to degrade gracefully. After a timeout, it moves to **half‑open** to test a single request; success closes the circuit (back to **closed**), failure re‑opens it. It works with **retry policies** and **exponential backoff** by limiting retries while open and backing off between attempts while closed.

**D20** – **Optimistic concurrency control (OCC)** assumes conflicts are rare; it reads a version/timestamp, performs work, and writes only if the version matches, otherwise aborts and retries. **Pessimistic concurrency control** locks resources (e.g., row locks) before accessing them to prevent conflicts.  
- Choose **OCC** for low‑contention workloads (e.g., analytics).  
- Choose **pessimistic** for high‑contention scenarios (e.g., financial transactions).  
Example (SQL): `SELECT * FROM accounts WHERE id=1 FOR UPDATE` (pessimistic) vs. `UPDATE accounts SET balance=balance-100 WHERE id=1 AND version=5` (optimistic, using a version column).<|END_TEXT|>
