<|END_THINKING|><|START_TEXT|>**JS1** – **var, let, const & hoisting**  
- **`var`** – function‑scoped, hoisted to the top of the *function* (initialized with `undefined`). Re‑declaration and reassignment allowed.  
- **`let`** – block‑scoped (scopes to `{}`), **not** hoisted (appears in the “Temporal Dead Zone”). Cannot be re‑declared, but can be reassigned.  
- **`const`** – block‑scoped, not hoisted, must be initialized at declaration, and its identifier cannot be reassigned (the value itself can be mutable for objects/arrays).  
- **Hoisting** – the compiler/interpreter moves declarations to the top of the enclosing scope **only for `var`**. `let`/`const` declarations are still hoisted but remain in the TDZ until the line is executed, so they behave as if they weren’t hoisted for practical purposes.

**JS2** – **Event loop, call stack, micro‑/macro‑task queues**  
- The **event loop** continuously checks three queues:  
  1. **Call Stack** – where synchronous code runs.  
  2. **Macrotask queue** – tasks scheduled by `setTimeout`, `setInterval`, `setImmediate`, I/O callbacks, UI events, etc.  
  3. **Microtask queue** – tasks scheduled by `Promise` callbacks (`.then`, `.catch`, async `await` resolution) and `queueMicrotask`.  
- **Order of execution**: The stack is emptied first. While empty, the loop picks a **macrotask**, runs it, then repeats. **After each macrotask**, the loop exhausts the **entire microtask queue** before picking the next macrotask. This guarantees that all pending promises resolve before the next scheduled timer runs.

**JS3** – **Closures, classic for‑loop bug & fix**  
- A **closure** is a function that retains references to variables from its *enclosing* lexical scope even after that scope has finished executing. The retained variables form a “closure” over the environment.  
- **Practical example** – a counter factory:  

```js
function makeCounter() {
  let n = 0;
  return () => ++n;
}
const inc = makeCounter();
inc(); // 1
inc(); // 2
```  

- **Classic for‑loop bug** (ES5 / older browsers):  

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```  

All three callbacks log `3` because `i` is function‑scoped and shared; by the time the timeouts fire, the loop has completed and `i` is `3`.  

- **Fix** – use `let` (block‑scoped) or an IIFE to capture the value:  

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```  

or  

```js
for (var i = 0; i < 3; i++) {
  (function(i) {
    setTimeout(() => console.log(i), 0);
  })(i);
}
```

**JS4** – **Promises, async/await, error handling, `Promise.allSettled` vs `Promise.all`**  
- **Promise** – an asynchronous operation that either resolves (success) or rejects (failure). Use `.then`/`catch` or `async/await`.  
- **`async/await`** – syntactic sugar over Promises. `async` functions always return a Promise; `await` pauses execution until the awaited Promise settles, automatically unwrapping the value (or throwing the rejection).  
- **Error handling** –  
  - With Promises: `.catch` (or `Promise.prototype.finally`) catches rejections.  
  - With `async/await`: a thrown error/rejected Promise propagates as an uncaught rejection; wrap in `try/catch` to handle it.  
- **`Promise.all`** – returns a single Promise that fulfills with an array of results **only if all input promises fulfill**. If any input rejects, the returned Promise rejects immediately (no further processing).  
- **`Promise.allSettled`** – returns a Promise that fulfills with an array of objects `{status: 'fulfilled'/'rejected', value:/reason}` for **every** input promise, regardless of outcomes. Useful when you need to know which succeeded/failed without aborting on the first failure.

**JS5** – **TypeScript `interface` vs `type`, discriminated unions**  
- **`interface`** – designed for *structural* object shapes. You can extend interfaces (`interface Animal { … }`, `interface Dog extends Animal { … }`). Open‑ended; you can re‑open and add properties.  
- **`type`** – more flexible; can describe intersection types, primitive unions, mapped types, conditional types, and can be used for **alias** of any type (including primitives). You cannot “extend” a `type` with `interface` (but you can merge an `interface` into a `type`).  
- **When to use**:  
  - Use `interface` for object literals, class definitions, and when you expect to extend or merge later.  
  - Use `type` for primitive unions, mapped/conditional types, or when you need intersection/union syntax.  
- **Discriminated unions** – a union where each member has a common discriminant property (usually a literal). The type guard infers the member based on that property, enabling precise `switch`/`if` narrowing.  

```ts
type Shape = Circle | Square;
interface Circle { kind: "circle"; radius: number; }
interface Square { kind: "square"; side: number; }

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.radius ** 2;
    case "square": return s.side ** 2;
    default: throw new Error("Unknown shape");
  }
}
```

**JS6** – **Prototypal inheritance, `Object.create`, ES6 classes**  
- **Prototypal inheritance** – objects inherit directly from other objects via the `[[Prototype]]` chain (aka `__proto__`). Property lookup walks up the chain until found.  
- **`Object.create(proto, props?)`** – creates a new object with `proto` as its prototype and optionally defines properties on that new object. It does **not** copy own properties from `proto`; it only sets the prototype link.  
- **ES6 `class`** – syntactic sugar over prototypes. `class C { … }` creates a constructor function with `[[Construct]]` that sets `this` and automatically creates an internal prototype (`C.prototype`). `extends` sets the subclass’s prototype to an object created from the superclass’s prototype. Under the hood, classes still use prototype chains; they just provide a cleaner syntax and guarantee `super()` usage.

**JS7** – **`this` binding rules (priority order)**  
1. **Explicit binding** – `call`, `apply`, `bind` (highest).  
2. **Implicit binding** – the object before the dot (`obj.method()` → `this = obj`).  
3. **New binding** – when a function is invoked with `new` (`this` becomes the newly created object).  
4. **Default binding** – global object (or `undefined` in strict mode).  

- **`bind()`** returns a **new function** with `this` permanently set to the supplied value (or first argument). The returned function can be called later; it does **not** invoke the original immediately.  
- **Re‑binding** – you can call `bind` on an already bound function, creating a new bound function that overrides the previous binding (the original remains unchanged). Example:  

```js
const fn = () => console.log(this);
const bound1 = fn.bind({a:1});
const bound2 = bound1.bind({b:2}); // bound2 now points to {b:2}
```

**JS8** – **`WeakRef`, `FinalizationRegistry`, `WeakMap` keys & GC**  
- **`WeakRef`** – holds a *weak* reference to an object; the object can be garbage‑collected without the WeakRef keeping it alive. Use `WeakRef.deref()` to get the object (returns `undefined` if collected).  
- **`FinalizationRegistry`** – registers a *callback* that runs when a target object (or an array of targets) is about to be garbage‑collected. Useful for cleanup of auxiliary resources (e.g., revoking revocable promises).  
- **When to use** –  
  - `WeakRef` when you need to observe an object without preventing its collection (e.g., caching, memoization with eviction).  
  - `FinalizationRegistry` when you need deterministic cleanup of side‑effects tied to object lifecycle (e.g., releasing native resources, removing event listeners).  
- **`WeakMap` keys must be objects** because the map stores *weak* references to those keys. Primitive keys cannot be weakly referenced; using an object allows the map to be garbage‑collected when the key itself is no longer reachable, keeping memory usage low.

**JS9** – **V8 optimizations: hidden classes, inline caching, deoptimization**  
- **Hidden classes** – also called “maps”. V8 creates a hidden class for each distinct object shape (set of properties in a specific order). When objects share the same hidden class, property access can be optimized (fast dictionary lookups).  
- **Inline caching** – caches the result of property accesses or function calls on the hidden class. If the same property is accessed repeatedly on objects of the same shape, the cache avoids dictionary lookups, turning them into direct pointer dereferences.  
- **Deoptimization** – occurs when the assumptions underlying the hidden class or inline cache break (e.g., adding a new property to an object that previously had a stable shape, or assigning a different type to a property). V8 must fall back to slower generic property access.  
- **Patterns that cause deoptimization**:  
  - Adding properties dynamically to objects that were previously “stable”.  
  - Changing property types (e.g., `obj.x = 5` then later `obj.x = "hello"`).  
  - Using `eval`, `with`, or `delete` on optimized objects.  
  - Frequent object literal creation with varying property order.

**JS10** – **Tree‑shaking**  
- **Definition** – a dead‑code elimination technique where unused exports are removed from the final bundle.  
- **ES modules** – static analysis: `import`/`export` statements are resolved at compile time, so tools can see which names are referenced and drop unreferenced modules.  
- **CommonJS** – dynamic: `require` is a runtime function; the module is always executed, and the export object is not statically analyzable. Consequently, the whole module is included in the bundle, making tree‑shaking ineffective unless the module is wrapped in an ES module or a tool like `webpack`’s `sideEffects: false` is used.

**JS11** – **`null` vs `undefined`, `==` vs `===`, nullish coalescing & optional chaining**  
- **`null`** – intentional absence of any object value.  
- **`undefined`** – variable declared but not assigned, or missing property.  
- **`==`** performs *type coercion*: `null == undefined` → `true`. `===` does not coerce: `null === undefined` → `false`.  
- **Nullish coalescing (`??`)** – returns the right‑hand operand if the left is `null` or `undefined`. Useful for providing defaults without ignoring `0`, `false`, `""`.  
- **Optional chaining (`?.`)** – safely accesses nested properties; if any intermediate value is `null`/`undefined`, the whole expression short‑circuits to `undefined` instead of throwing.

**JS12** – **Array methods: `map`, `filter`, `reduce`, `flatMap`**  
- **`map`** – creates a new array of the same length; each element transformed by the callback (`callback(item, idx, arr)`).  
- **`filter`** – creates a new array containing only elements where the callback returns a truthy value.  
- **`reduce`** – accumulates values into a single result. With an **initial value** (`reduce((acc, cur) => acc + cur, 0)`) the accumulator starts as that value; without it, the first array element becomes the initial accumulator and iteration starts at index 1.  
- **`flatMap`** – combines `map` and `flat` (depth 1). Useful for transforming each element into an array and flattening the result in one step (e.g., splitting strings into words).

**JS14** – **Destructuring & rest operator**  
- **Object destructuring** – `const {a, b} = obj;` extracts named properties.  
- **Array destructuring** – `const [x, y] = arr;` extracts by index.  
- **Default values** – `const {a = 1} = obj;` provides a fallback when `a` is missing/undefined.

**JS15** – **`for...in` vs `for...of`**  
- **`for...in`** iterates over **enumerable own and inherited** properties of an object (including non‑string keys). Best for object keys.  
- **`for...of`** iterates over **iterable** collections (arrays, strings, Maps, Sets, NodeLists). It yields values, not keys.  
- **Avoid `for...in` on arrays** because arrays have numeric indices but also inherited properties (e.g., `toString`, `length`). It can produce unexpected results and is slower. Use `for...of` or `forEach`.

**JS16** – **TypeScript generics, constraints, conditional types, infer**  
- **Generics** – allow a function/class to work with many types while preserving type safety.  

```ts
function identity<T>(arg: T): T { return arg; }
```  

- **Generic constraints** – limit `T` to a subset of types:  

```ts
function max<T extends number | string>(a: T, b: T): T {
  return a > b ? a : b;
}
```  

- **Conditional types** – `T extends U ? X : Y`. Example:  

```ts
type Expected<T> = T extends string ? string : T extends number ? number : never;
```  

- **Infer** – extracts a type variable from a generic parameter:  

```ts
type ReturnType<T extends (...args: any[]) => any> = T extends (...args: infer R) => infer Ret ? Ret : any;
```  

- **Practical examples**:  
  - **Constraint**: `function merge<T extends object>(a: T, b: Partial<T>): T` ensures `b` can be assigned to `Partial<T>`.  
  - **Conditional**: `type NonNullable<T> = T extends null | undefined ? never : T;`  
  - **Infer**: `type Params<T> = T extends ( ...args: infer P ) => any ? P : never;`

**JS17** – **Module systems in JavaScript**  
- **CommonJS** – `require('mod')` at runtime, `module.exports` (or `exports`) to expose. Synchronous, file‑based, used by Node before ES modules.  
- **ES Modules** – `import { … } from 'mod'` and `export { … }`. Static analysis, can be hoisted, supported natively in modern Node (`"type":"module"`).  
- **Node handling** – Node supports both: files ending in `.js` are CommonJS unless `package.json` sets `"type":"module"` or the file has `.mjs` extension. Mixing requires careful naming (`.cjs`, `.mjs`).  
- **`"type": "module"`** – tells Node to treat `.js` files as ES modules, enabling `import`/`export` syntax and static tree‑shaking.

**JS18** – **Structural type system, excess property checks, `extends` vs `satisfies`, variance**  
- **Structural typing** – types are compatible based on shape, not name. `interface A { x: number }` is assignable to `interface B { x: number; y?: number }` because `B` has all required members of `A`.  
- **Excess property checks** – when assigning an object literal to a variable of a type, TypeScript checks that **no extra properties** exist that aren’t allowed by the target type (unless `allowExcessPropertyAccess` is true). This prevents accidental typos.  
- **`extends` vs `satisfies`** – `extends` is used for type guards (`T extends U ? …`). `satisfies` (`v satisfies T`) asserts that a value conforms to a type at runtime (type‑only check). Example:  

```ts
const obj = { a: 1 } satisfies { a: number; b: never };
```  

- **Variance (TS 4.7+)** –  
  - **`in`** – covariant type parameter (used only as input). `function foo<T>(reader: (t: T) => void): void` → `T` is `in`.  
  - **`out`** – contravariant (used only as output). `function bar<T>(provider: () => T): void` → `T` is `out`.  
  - **`both`** – invariant (default).

**JS19** – **Proxy & Reflect**  
- **Proxy** – wraps an object to intercept fundamental operations (`get`, `set`, `has`, `deleteProperty`, `apply`, etc.). `Reflect` provides the same operations as functions (`Reflect.get(target, prop)`, `Reflect.set(...)`).  
- **Intercepting**:  

```ts
const handler = {
  get(target, prop, receiver) {
    console.log(`Getting ${String(prop)}`);
    return Reflect.get(target, prop, receiver);
  },
  set(target, prop, value, receiver) {
    if (typeof value === 'string') {
      console.log(`Setting ${String(prop)} to "${value}"`);
      return Reflect.set(target, prop, value, receiver);
    }
    throw new TypeError('Only strings allowed');
  }
};
const p = new Proxy({}, handler);
p.name = 'Alice'; // logs & sets
console.log(p.name); // logs & returns
```  

- **Practical use** – validation, logging, reactive data binding (e.g., Vue’s observed objects), or revocable promises.

**JS20** – **SharedArrayBuffer & Atomics**  
- **SharedArrayBuffer** – an ArrayBuffer that can be shared across multiple threads (e.g., within a `Worker` or between main thread and a worker). It does **not** allow direct mutation from multiple threads without synchronization.  
- **Atomics** – atomic operations on shared memory (e.g., `Atomics.add`, `Atomics.load`, `Atomics.store`, `Atomics.wait`, `Atomics.notify`). They guarantee indivisible reads/writes, preventing race conditions.  
- **Web Workers communication** – workers can post messages (`postMessage`) or share a `SharedArrayBuffer` via `transferable` transfer. The main thread and worker can read/write the same underlying ArrayBuffer; changes are visible to all.  
- **Ordering guarantees** – operations on shared memory are **sequentially consistent** when using Atomics; however, regular reads/writes without atomics are not ordered, leading to data races.  
- **`Atomics.wait` / `notify`** – low‑level blocking primitives. `Atomics.wait` blocks the calling thread until the value at a location changes or a timeout expires (returns `'not‑equal'`, `'timed‑out'`, etc.). `Atomics.notify` wakes up a waiting thread (or multiple threads) on the same location. Useful for implementing locks or condition variables in shared memory.

**B1** – **`$@` vs `$*` and quoting**  
- `$@` – expands to all positional parameters as separate words, preserving spaces and special characters. Example: `echo "$@"` → `arg1 arg2`.  
- `$*` – expands to all positional parameters as a single word, with spaces separating them. Example: `echo "$*"` → `arg1 arg2` (but treated as one argument to subsequent commands).  
- `"$@"` vs `"$*"` – same quoting, but `$@` yields each param as a distinct argument; `"$*"` yields them concatenated.

- `-u` – treat unset variables as an error (prevent accidental referencing).  
- `-o pipefail` – cause pipeline to fail if any component fails (not just the last).

**B3** – **`$(cmd)` vs `` `cmd` `` vs `$((expr))` vs `expr`**  
- `$(cmd)` and `` `cmd` `` are equivalent; both perform **command substitution** (execute `cmd` and replace with its stdout). `` ` `` is the original shell syntax; `$()` is preferred for readability.  
- `$((expr))` performs **arithmetic expansion** (evaluated by the shell’s arithmetic interpreter). `expr` is an external utility that also evaluates expressions but returns an exit status and prints result to stdout; `$((expr))` is faster and integrates with shell variables.

Both `grep` outputs are treated as temporary files, enabling direct comparison without intermediate files.

**B5** – **Iterating safely over files with spaces**  
- `for f in $(ls)` is dangerous because command substitution splits on whitespace, so filenames containing spaces or newlines are broken into separate variables, and wildcards are expanded before substitution.  
- Safer approaches:  

```bash
shopt -s nullglob
for f in *; do
  # handle $f safely
done
```  

or using `find`:  

```bash
find . -type f -print0 | IFS= read -d '' -r f && while [ -n "$f" ]; do
  # process $f
  IFS= read -d '' -r f
done
```  

or `for f in * ./*` with quoting and using `printf '%s\n' *`.

**B6** – **Here‑document vs here‑string vs `<<-EOF`**  
- **Here‑document (`<<EOF`)** – reads literal lines from the script until a delimiter line (`EOF`) is encountered; the content becomes a word (or multiple words) passed to a command.  
- **Here‑string (`<<<`)** – treats its argument as a single‑line string, similar to `echo -e` but without a newline unless supplied. Example: `sort <<< "banana\napple"`.  
- **`<<-EOF`** – same as `<<EOF` but strips **leading tabs** from each line (useful for indenting heredocs in scripts while keeping content clean).  

---

**B7** – **Redirection differences**  

```bash
cmd > file 2>&1   # stdout → file, stderr merged into same file (order: stdout first, then stderr)
cmd 2>&1 > file   # stderr → stdout, then both → file (stderr appears before stdout in file)
cmd &> file        # same as `cmd 2>&1 > file` (POSIX syntax)
```  

- The first form writes stdout then stderr sequentially; the second merges stderr into stdout **before** redirection, so the file contains stderr **before** stdout. The difference matters when the command writes to both streams and you care about order.  

---

**B8** – **Safe lock‑file function with SIGTERM handling**  
```bash
#!/usr/bin/env bash
set -euo pipefail

LOCK_DIR="/var/run/myapp"
LOCK_FILE="$LOCK_DIR/$(basename "$0").lock"
MAX_WAIT=30
WAIT_INTERVAL=1

acquire_lock() {
  local start end
  start=$(date +%s)
  end=$((start + MAX_WAIT))

  while [ $(date +%s) -lt $end ]; do
    if mkdir "$LOCK_DIR" 2>/dev/null; then
      # Lock acquired – create a marker file for cleanup
      echo "$$" > "$LOCK_FILE"
      trap 'cleanup_lock' EXIT INT TERM
      return 0
    fi
    sleep $WAIT_INTERVAL
  done
  echo "Failed to acquire lock" >&2
  exit 1
}

cleanup_lock() {
  # Remove lock file only if we own it
  if [ -f "$LOCK_FILE" ] && [ "$(cat "$LOCK_FILE")" = "$$" ]; then
    rm -f "$LOCK_FILE"
    rmdir "$LOCK_DIR" 2>/dev/null || :
  fi
}

acquire_lock
# ---- main script ----
# ... your work ...

# cleanup will run on EXIT, INT, TERM
```  

- **Why `mkdir`?** – `mkdir` is atomic; if two processes attempt it simultaneously, only one succeeds. A plain lock file requires extra checks (`flock`, `O_EXCL` open) and is prone to race conditions. `mkdir` also cleans up automatically when empty, providing a natural cleanup.  

---

**B9** – **Quote differences**  
- **No quotes** – word splitting and globbing occur; `ls *.txt` expands to matching filenames.  
- **Single quotes** – literal; no variable expansion, no escape sequences. `'hello world'` stays exactly `hello world`.  
- **Double quotes** – partial expansion; variables and backslash escapes are processed, but spaces are preserved. `"hello $USER"` → `hello alice`.  

---

**B10** – **Testing file existence & type**  
- `[ -e "$file" ]` – exists (file or dir). `[ -f "$file" ]` – regular file. `[ -d "$file" ]` – directory. `[ -r "$file" ]` – readable.  
- `[` is the **test** builtin (single brackets). `[[` is **compound test** (double brackets) with extended keywords (`==`, `=~`, `||`, `&&`). `[[ ]]` also supports pattern matching and doesn't need spaces around operators.  

---

**B11** – **`$?`, `$$`, `$!`, `$#`**  
- `$?` – exit status of the last command.  
- `$$` – process ID of the current shell.  
- `$!` – PID of the most recent background command.  
- `$#` – number of positional parameters (arguments) passed to the script.  

---

**B12** – **Bash functions**  
- Syntax: `function name { ... }` or `name() { ... }`. Both are equivalent; `function` is more explicit.  
- Functions return a **status code** via `return N` (or implicit `N` of last command). They cannot return arbitrary values; use global variables or stdout.  

---

**B13** – **PATH, command resolution, builtins vs externals**  
- **PATH** – colon‑separated list of directories the shell searches for executables.  
- **Resolution** – for a command `cmd`, shell first checks if it’s a builtin (hash table), then looks in each PATH directory for an executable file with that name.  
- **Builtin** – integrated into the shell, no separate process (e.g., `cd`, `echo`). **External** – separate process (e.g., `ls`).  
- **Check** – `type -a cmd` shows all definitions (builtin, hashed, alias, function). `declare -f cmd` shows function definition.  

---

**B14** – **`trap`**  
- `trap` sets signal handlers. Syntax: `trap 'cleanup' EXIT INT TERM`.  
- **Handlers**:  
  - `EXIT` – executed when the script exits (normal or via `return`).  
  - `ERR` – on command failure (if `-e` is set).  
  - `INT` – SIGINT (Ctrl‑C).  
  - `TERM` – SIGTERM (kill).  
- **Execution order** – when multiple signals arrive, the most recent pending signal is processed first; if a handler itself triggers another signal, it will be queued. Multiple traps for the same signal are cumulative (later overrides earlier unless using `trap - SIGINT`).  

---

**B15** – **`xargs` vs command substitution**  
- **`xargs`** builds argument lists from stdin (or find output) and executes a command, handling argument length limits and quoting safely.  
- **Command substitution** (`$(cmd)`) runs the command directly in the shell, which can break with spaces/newlines.  
- **Handling spaces/newlines**: `find . -type f -print0 | xargs -0 cmd` (or `xargs -0` with `-I`). `-0` reads NUL‑terminated names, preserving any characters.  
- **`xargs -P N`** runs up to `N` jobs in parallel, useful for CPU‑intensive processing.  

---

**B16** – **Bash arrays & associative arrays**  
- **Regular array** – indexed numerically, declared `arr=(a b c)`. Append: `arr+=("d")`. Iterate: `for e in "${arr[@]}"; do … done`. Length: `${#arr[@]}`.  
- **Associative array** – key/value pairs, declared `declare -A assoc`. Insert: `assoc[key]=value`. Iterate: `for k in "${!assoc[@]}"; do v=${assoc[$k]}; … done`. Length: `${#assoc[@]}`.  
- **Syntax differences** – associative arrays require `declare -A` and keys are strings, not numeric indices.  

---

**B17** – **Subshell vs group command**  
- **Subshell** `(...)` creates a new process; variable changes inside do **not** affect the parent. Exit status is that of the last command in the subshell.  
- **Group command** `{ ...; }` runs commands in the current shell; variables and exit status propagate.  
- **Piping into a `while read`** – `cmd | while ...` runs the loop in a subshell (because of the pipe), so variable modifications are lost after the loop. Use process substitution or `cmd | while ...; do ...; done` with `while ...; do ...; done < <(cmd)` to keep scope.  

---

**B18** – **Bash signals & job control**  
- **SIGINT** – interrupt (Ctrl‑C).  
- **SIGTERM** – termination request (kill).  
- **SIGHUP** – hang‑up (often terminates interactive jobs).  
- **SIGKILL** – forced kill (cannot be caught/ignored).  
- **Graceful shutdown** – trap `INT TERM` to clean up background jobs, wait for them, then exit. Example:  

```bash
cleanup() {
  # kill background jobs gracefully
  jobs -p | xargs kill -TERM
  wait
}
trap cleanup INT TERM
# start background work
sleep 1000 &
```  

---

**B19** – **Parallel log processing script**  
```bash
#!/usr/bin/env bash
set -euo pipefail

LOG_FILE="app.log"
PROCESSED_DIR="processed"
mkdir -p "$PROCESSED_DIR"

# Split into chunks (e.g., 10 MB each)
split -b 10M "$LOG_FILE" "$PROCESSED_DIR/chunk_"

# Process chunks in parallel (max 4 jobs)
export PROCESSED_DIR
xargs -0 -I {} -P 4 bash -c '
  chunk="$1"
  base=$(basename "$chunk")
  # Example processing: count lines, write result
  lines=$(wc -l < "$chunk")
  echo "$base:$lines" > "$PROCESSED_DIR/${base}.cnt"
' _ find "$PROCESSED_DIR" -type f -print0

# Merge results
{
  for f in "$PROCESSED_DIR"/*.cnt; do
    cat "$f"
  done
} | sort -t: -k2,2nr > "$PROCESSED_DIR/summary.txt"

# Cleanup chunk files
rm -f "$PROCESSED_DIR/chunk_"*
```  

- **Performance trade‑offs** – `split` creates many small files; too many can cause overhead. `xargs -P` controls parallelism; too high may overload CPU/memory.  
- **Error propagation** – `set -e` will abort on first failing command; using `|| true` or explicit error checking can allow partial results.  

---

**B20** – **`exec` vs normal command & coprocess**  
- **`exec`** replaces the current shell process with the given command, closing the original fd unless redirected. `exec cmd args` runs `cmd` in the current shell environment (no subshell).  
- **File descriptor manipulation** – `exec 3>file` opens `file` for writing on descriptor 3; `exec 3>&-` closes descriptor 3.  
- **Coprocess** – a bidirectional pipe pair used for background communication. Example:  

```bash
exec 3<> <(cat /dev/null)   # open a read/write pipe on fd 3
coproc READER { cat; }      # READER reads from fd 3, writes to fd 4
```  

- Use coprocess for pipelines where you need to feed input and capture output concurrently without subshell overhead (e.g., building a client that reads/writes to a remote service).  

---

**PS1** – **`Write-Output` vs `Write-Host`**  
- **`Write-Host`** writes directly to the console (bypasses pipeline). Useful for progress messages, warnings.  
- **`Write-Output`** (or `Write-O`) streams objects into the pipeline; other cmdlets can process them. In pipelines, `Write-Host` output is lost unless explicitly captured.  

---

**PS2** – **PowerShell pipeline & `ForEach-Object` vs `foreach` statement**  
- **Pipeline** – objects flow from one cmdlet to the next via `|` using `Write-Output` (or automatic output).  
- **`ForEach-Object`** – script block runs **per object** in the pipeline (supports `Process`, `Begin`, `End` blocks).  
- **`foreach` statement** – traditional C‑style loop over a collection (e.g., `foreach ($item in $collection) { … }`). Use `ForEach-Object` for pipeline scenarios; use `foreach` for simple array loops.  

---

**PS3** – **`[PSCustomObject]` vs hashtable**  
- **`[PSCustomObject]`** – a .NET `PSObject` with structured properties; appears as an object in the pipeline, supports `PSStandardMembers`.  
- **Hashtable** – a plain `System.Collections.Hashtable`; used for splatting, hash tables, but not pipeline‑friendly (appears as a `Hashtable` type).  
- **Conversion** – `[PSCustomObject]$hash = $hashtable` creates a custom object; `$hashtable = @{} + $psobject` can convert back (copy properties).  

---

**PS4** – **Error handling**  
- **Terminating errors** – fatal, stop pipeline, require `try/catch`. Example: `throw "error"`.  
- **Non‑terminating errors** – reported but pipeline continues; controlled by `-ErrorAction` (`Stop`, `Continue`, `SilentlyContinue`, `Inquire`). `$ErrorActionPreference` is the session default.  
- Interaction: `try { ... } catch { ... }` only catches terminating errors; non‑terminating errors can be suppressed with `-ErrorAction SilentlyContinue`.  

---

**PS5** – **Splatting (`@params`)**  
- Splatting passes a hash table as named parameters, improving readability and reducing errors.  

```powershell
$common = @{ Path = 'C:\log'; Recurse = $true }
Get-ChildItem @common
```  

- Differs from passing a hashtable as a single parameter (e.g., `Get-ChildItem $common`) which would treat the hashtable as a single argument (the cmdlet would try to interpret it as a path).  

---

**PS6** – **PowerShell remoting**  
- **`Invoke-Command -ComputerName`** runs a script block on a remote machine, returning output to the local session.  
- **`Enter-PSSession`** creates an interactive session; subsequent commands run remotely until `Exit-PSSession`.  
- Protocol: **WS‑Man** (Windows Remote Management) or **SSH** (when using `-Transport SSH`). Relies on WinRM service (or SSH daemon).  

---

**PS7** – **Pipeline type behavior & correct pattern**  
```powershell
function Get-Items {
    $result = @()
    $result += "one"
    return $result
}
$x = Get-Items
$x.GetType().Name   # 'Object[]' (array)
```  

- Returning a single object (e.g., `"one"`) yields a **single‑element array** because functions that `return` a value are automatically wrapped in an array when used in a pipeline.  
- If the function returns **0 items** (empty array), `$x` is still an array (`Object[]`).  
- **Correct pattern** – use `process` block in a *function‑based* cmdlet or explicitly `return $input` to preserve pipeline streaming. For simple functions, avoid `return` and just `$_` or `$input`. Example:  

```powershell
function Get-Items {
    "one","two"
}
```  

Now `$x` is a **string[]** (array of strings) and pipeline works as expected.  

---

**PS8** – **`[scriptblock]` vs function, double‑hop, CredSSP**  
- **ScriptBlock** – a compiled block of PowerShell code (`[scriptblock]::Create('...')`). Functions are also scriptblocks but have metadata (name, parameters).  
- Passing a scriptblock to a remote session: `Invoke-Command -ComputerName $computer -ScriptBlock $scriptBlock`.  
- **Double‑hop problem** – when you delegate credentials through an intermediate server (e.g., `Invoke-Command` → `Enter-PSSession`), the intermediate server cannot forward the original credentials to the target. Solutions:  
  - Use **CredSSP** (`-Authentication Credssp`).  
  - Use `Invoke-Command -ArgumentList` to pass needed variables, avoiding nested `Enter-PSSession`.  

---

**PS9** – **`@()` vs `[array]`**  
- `@()` creates an empty **array** (`System.Object[]`). `[array]` is a **type accelerator** that can be used to cast a collection into an array: `[array]"a","b"` → `a b`.  
- To force a single result into an array: `@(value)` or `[value]`.  
- Indexing `$null` throws an error; indexing an empty array `$arr[0]` returns `$null` (or throws if you use `-ErrorAction Stop`).  

---

**PS10** – **Comparison operators**  
- `-eq`, `-ne`, `-like`, `-match`, `-contains`, `-in` are **string/numeric** comparisons (case‑insensitive).  
- Case‑sensitive variants: `-ceq`, `-cne`, `-clike`, `-cmatch`.  
- `-contains` checks if a **collection** contains a specific value (order matters). `-in` checks if a value exists in a collection (order irrelevant).  

---

**PS11** – **PowerShell modules**  
- **Script module (`.psm1`)** – contains functions/cmdlets, loaded via `Import-Module`.  
- **Manifest module (`.psd1`)** – metadata file (nested modules, required assemblies, variables).  
- **Binary module** – compiled DLL with a `psd1` manifest describing exported cmdlets.  
- `Import-Module` loads the module into the session, making its functions available.  

---

**PS12** – **String interpolation**  
- `"Hello $name"` – **double‑quoted** string with variable expansion.  
- `'Hello $name'` – single‑quoted, literal `$name`.  
- Interpolated strings: `$"Hello $name"` (or `$"Hello $(Get-Date)"`).  
- Here‑string: `@"
Line1
Line2
"@` preserves newlines and quotes.  

---

**PS13** – **`Get-Member` & pipeline exploration**  
- `Get-Member` shows **Properties**, **Methods**, **NoteProperties** (custom PS notes).  
- `Select-Object` chooses properties; `Where-Object` filters objects based on scriptblocks.  

---

**PS14** – **PowerShell classes (v5)**  
- Similar to C# but limited: no multiple inheritance, no static constructors, no operator overloading.  
- Can define **constructors**, **methods**, **properties**, **static methods**.  
- Inheritance allowed but limited (no generic variance).  
- Use classes for complex data structures, validation, or when you need true encapsulation; functions are preferred for simple scripts.  

---

**PS15** – **CmdletBinding & advanced functions**  
- `[CmdletBinding()]` enables common parameters (`-Verbose`, `-WhatIf`, `-ErrorAction`).  
- `SupportsShouldProcess` – allows `-WhatIf`/`-Confirm`.  
- `DefaultParameterSetName` – which parameter set is used by default.  
- `ValueFromPipeline` – allows input from pipeline (type must match).  
- **Begin/Process/End** blocks – `Begin` runs once before any input, `Process` per object, `End` after all input.  

---

**PS16** – **Providers**  
- Providers abstract namespaces as filesystems (`Get-ChildItem`, `Set-Item`, etc.).  
- `FileSystem`, `Registry`, `Certificate`, `Environment` are built‑in.  
- Access registry: `Get-ChildItem HKLM:\Software` or `PSDrive` `HKLM`.  

---

**PS17** – **Runspaces & parallel execution**  
- **Runspace** – isolated execution environment (thread).  
- **RunspacePool** – collection of runspaces for reuse.  
- **PowerShell** object – represents a remoting session.  
- `ForEach-Object -Parallel` (v7+) uses the underlying runspace pool automatically; manual runspace management gives finer control over thread safety and resource limits.  

---

**PS18** – **PSScriptAnalyzer**  
- Static analysis engine that enforces coding standards via **rules** (e.g., `PSUseConsistentIndentation`).  
- **Severity** – Error, Warning, Information.  
- Custom rules can be added via PSModule.  
- Suppress with `# PSScriptAnalyzer: enable DisableRuleName` or `Disable -Name RuleName`.  
- Integrates with CI (e.g., Azure DevOps, GitHub Actions) via `Invoke-ScriptAnalyzer` task.  

---

**PS19** – **$using: scope vs $args/-ArgumentList**  
- `$using:` creates a **reference** to a variable that is serialized and sent to a remote session (limited depth – CLIXML).  
- `$args` / `-ArgumentList` passes arguments as positional parameters; they are serialized similarly but can hold more data (still limited by CLIXML depth).  
- Use `$using:` for simple variables; for complex objects, flatten or pass by reference if possible.  

---

**PS20** – **Desired State Configuration (DSC)**  
- **Configurations** – declarative blocks defining the desired state of nodes.  
- **Resources** – built‑in (File, Package, Service) or custom, representing system aspects.  
- **Local Configuration Manager (LCM)** – on each node, holds configuration mode (`ApplyOnly`, `ApplyOnce`), refresh frequency, etc.
