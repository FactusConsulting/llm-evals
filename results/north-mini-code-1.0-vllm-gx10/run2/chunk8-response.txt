**CL3** – **VPC, Subnet, Security Group, NACL**  
- **VPC** – Isolated logical network (RFC‑1918 address space) that acts as the boundary for all resources in a region.  
- **Subnet** – Portion of a VPC’s IP space (e.g., /24) that defines where VMs/ELBs are placed; subnets are placed in AZs for high availability.  
- **Security Group** – **Stateful** firewall attached to individual instances (VM, container). Rules are applied at the instance level; inbound rule automatically permits outbound response (stateful).  
- **Network ACL (NACL)** – **Stateless** subnet‑level firewall; rules are evaluated in order, inbound and outbound must be defined explicitly.  

**Layering:** VPC (outermost) → Subnets (segmented IP ranges) → NACLs (subnet‑wide stateless filter) → Security Groups (instance‑level stateful filter). Traffic passes through NACL first, then SG, then the host’s OS firewall if any.  

**Stateful vs Stateless:**  
- *Stateful* (SG): Tracks TCP/UDP sessions; allows return traffic without explicit rule.  
- *Stateless* (NACL): Each packet evaluated independently; must allow both directions if needed.

- **Operational scaling** – IAM, networking, and logging become unwieldy.

**CL7** – **Disaster‑Recovery (DR) design for a cloud‑native app (two regions)**  

1. **RPO / RTO** – Define acceptable data loss (RPO) and downtime (RTO). Example: RPO ≤ 5 min, RTO ≤ 30 min → active‑active with synchronous replication for critical data, async for less‑critical.  
2. **Active‑Active vs Active‑Passive** –  
   *Active‑Active*: Both regions serve traffic; DNS round‑robin or geo‑routing; requires multi‑master DB replication, state synchronization (e.g., Redis Cluster, Cassandra).  
   *Active‑Passive*: Primary region handles traffic; secondary stands by; DNS points to secondary only after failover; lower complexity, higher RTO.  
3. **Database replication** –  
   *Sync* (e.g., PostgreSQL logical replication, MySQL Group Replication) for strong consistency but higher latency & cost.  
   *Async* (e.g., DynamoDB global tables, Kafka CDC) for lower latency & cost, acceptable for eventual consistency.  
4. **DNS failover** – Use AWS Route 53 health‑checked aliases or Azure Traffic Manager. Health checks on critical services; fail‑over to secondary region when primary fails.  
5. **State management** – Use distributed stores that support multi‑region (e.g., DynamoDB Global Tables, Spanner, Redis Cluster). Session state can be stored in a shared cache; consider eventual‑consistency patterns for non‑critical UI state.  
6. **Cost implications** – Active‑active doubles compute, networking, and storage costs; need to rightsize, use spot instances where permissible, and apply data tiering (cold storage).  

**DR patterns:**  
- **Pilot Light** – Minimal infrastructure (e.g., a single VM) in secondary region; spin up full stack on demand (RTO ≈ hours).  
- **Warm Standby** – Pre‑provisioned services (databases, caches) but not full application; faster recovery (RTO ≈ minutes).  
- **Multi‑site Active‑Active** – Full production stack in both regions; near‑zero RTO, continuous replication; highest cost.

**CL8** – **GitOps model**  

- **GitOps definition** – All infrastructure and application state declared as Git repositories (YAML/JSON). Continuous reconciliation performed by an operator (ArgoCD, FluxCD) that watches Git and applies changes to the cluster.  

- **ArgoCD vs FluxCD**  
  *ArgoCD*: Server‑side diff, focuses on applications, rich UI, built‑in health checks, supports Kustomize/Helm natively.  
  *FluxCD*: Agent‑based (Helm Operator, Kustomize Controller), uses Kubernetes resources (HelmRelease, Kustomization) for declarative management, lighter weight, integrates tightly with Kubernetes RBAC.  

- **Secrets handling**  
  *Sealed Secrets*: Encrypt secrets in Git, decrypt at runtime by the cluster (kubectl‑seal).  
  *External Secrets Operator*: Pulls secrets from external vaults (HashiCorp Vault, AWS Secrets Manager) into Kubernetes Secret objects.  
  *Vault*: Can be used via TLS/CLI or API; operators fetch credentials at pod start‑up, rotating automatically.  

- **Drift handling** – If a manual change is made on a cluster (e.g., pod annotation), the GitOps controller detects the divergence, reports it as “OutOfSync,” and can either:  
  1. **Auto‑correct** (reapply the Git state, potentially overwriting manual changes).  
  2. **Alert** the team and require a PR to Git to incorporate the change.  
  Most setups choose auto‑correct to enforce desired state, but they also log drift events for audit.

**CL9** – **Stateful legacy app → Kubernetes architecture**  

1. **StatefulSet** – Manages pod identities, stable network IDs (`pod-0`, `pod-1`), ordered deployment (`ordinal` ordering).  
2. **Headless Service** (`clusterIP: None`) – Provides DNS entries for each pod (`myapp-0.myapp.default.svc.cluster.local`) enabling direct TCP connections and sticky sessions.  
3. **PersistentVolumeClaim (PVC) with local storage class** – Use `aws-ebs` (e.g., `gp3`) or `azure-disk` with `local` storage class to give each pod a dedicated block device for low‑latency local storage.  
4. **Init Containers** – Ensure startup order: e.g., wait for config‑map volume mount, create required directories, set permissions.  
5. **ConfigMaps as volume mounts** – Deploy configuration files into a predictable path (`/opt/app/config/`) using `subPath` mapping so the app reads from a known location.  
6. **PodDisruptionBudgets (PDB)** – Set `minAvailable` or `maxUnavailable` to keep at least N pods alive during maintenance (e.g., `minAvailable: 2`).  
7. **Sticky sessions** – Use the headless service + `sessionAffinity: ClientIP` or application‑level session store (e.g., Redis) to maintain user state across pods.  
8. **Scaling** – Use `StatefulSet` rolling updates with `maxUnavailable` to control batch upgrades.  

Result: each replica has its own low‑latency block device, ordered startup, deterministic config location, and the ability to survive node failures while preserving session affinity.

**CL10** – **Service Account vs Workload Identity vs IRSA**  

| Concept | Scope | Credential form | Typical use |
|---------|-------|----------------|-------------|
| **Service Account** (Kubernetes) | Cluster‑local identity for pods; tokens stored in API server. | Service‑account token (mounted as file or env var). | Generic pod‑level access (e.g., read a ConfigMap). |
| **Workload Identity** (GCP) | Identity federation between Kubernetes and cloud IAM; pods assume a Google‑based IAM role. | No long‑lived credentials in the pod; OIDC token exchanged for GCP access token via GCP IAM Workload Identity. |
| **IRSA (IAM Roles for Service Accounts)** (AWS) | Similar to workload identity but for AWS; maps a Kubernetes Service Account to an IAM Role. | OIDC token from EKS, exchanged via AWS STS for temporary credentials (no keys in pod). |

**Why mounting cloud provider credentials is bad:**  
- Credentials become part of the container image or pod spec, potentially leaked in logs, images, or Git repos.  
- Long‑lived static keys increase blast radius if a pod is compromised.  
- No automatic rotation.  

**Workload identity federation solves this** by:  
- Using the cluster’s OIDC provider to obtain a short‑lived token.  
- Exchanging that token for cloud‑specific temporary credentials via STS (AWS) or GCP IAM.  
- No static keys ever reside in the pod; rotation is handled by the cloud provider (e.g., IAM role session expiration).

**CL12** – **Zero‑Trust Network Architecture for Kubernetes**  

1. **Network Policies** – Define ingress/egress per namespace/pod; default deny all, allow explicit connections.  
2. **Service Mesh (e.g., Istio, Linkerd)** – Enforce mTLS between all services, provide traffic management, observability, and fine‑grained routing.  
3. **Pod Identity** – Use IRSA/Workload Identity to give pods least‑privilege cloud IAM roles; avoid embedding credentials.  
4. **Admission Controllers** – OPA Gatekeeper / Kyverno enforce policies at creation (resource quotas, labels, image trust).  
5. **Image Signing & Verification** – Cosign, Notary, or Sigstore; enforce that only signed images run (policy‑enforced via admission controller).  
6. **Runtime Security** – Falco monitors container syscalls; alerts on anomalous behavior (e.g., unexpected binaries, network connections).  
7. **Secrets Management** – External Secrets Operator or HashiCorp Vault; secrets never stored in etcd or images.  

**Difference from perimeter‑based security:**  
- **Perimeter** assumes trust inside the network; firewall rules protect the boundary.  
- **Zero‑trust** assumes no implicit trust; every request is authenticated, authorized, and encrypted, regardless of source.  
- Controls are enforced at the workload level (pod, service) rather than just at the network edge.

**CL13** – **CDN basics**  

- **What it is:** A globally distributed edge cache that stores copies of static content (HTML, CSS, JS, images, video) close to end users.  
- **How it works:** Origin pulls content to edge nodes via HTTP/HTTPS; edge nodes serve cached responses, performing origin pull on cache miss or stale content. DNS (anycast or DNS‑based routing) directs users to the nearest edge.  
- **Cloud‑native CDN services:**  
  * AWS CloudFront  
  * Azure Front Door (includes CDN)  
  * Google Cloud CDN (via Cloud Load Balancing)  
- **When to use CDN vs origin:** Use CDN for any static or semi‑dynamic content that is requested by many users (images, CSS/JS bundles, videos, API documentation). Serve directly from origin when content is highly dynamic, personalized per request, or when you need to avoid cache‑stale issues.

**CL14** – **Regions & Availability Zones**  

- **Region:** Geographic area with independent infrastructure (data centers, power, networking). Example: `us-east-1` (N. Virginia).  
- **Availability Zone (AZ):** Physically separate data center within a region, low‑latency network, independent power/utility. Example: `us-east-1a`, `us-east-1b`.  
- **Why deploy across AZs:** Provides fault tolerance; if one AZ fails, other AZs continue serving traffic; improves performance (proximity to users).  
- **Zonal vs Regional resources:**  
  *Zonal* – Tied to a single AZ (e.g., EC2 instance, EBS volume). If AZ goes down, the resource is unavailable.  
  *Regional* – Replicated across AZs (e.g., S3, DynamoDB, Azure SQL Database). High availability is built‑in; data is automatically replicated.

**CL16** – **Cloud identity services**  

- **IAM Users:** Individual accounts with credentials (password, MFA).  
- **Groups:** Collections of users for policy assignment; simplify permissions.  
- **Roles:** Scoped permissions (often temporary, assume‑role) that can be attached to users, groups, or resources.  
- **Policies:** JSON definitions that specify allowed/denied actions and resources.  

**Principle of Least Privilege:** Grant only the permissions required to perform a job. Apply by:  
- Using role‑based access (RBAC) with narrowly scoped policies.  
- Leveraging temporary credentials (assume‑role) rather than long‑lived keys.  
- Regularly reviewing and pruning permissions (IAM Access Analyzer, AWS IAM Access Advisor).

**CL17** – **Serverless computing**  

- **Definition:** Execute code on‑demand in response to events; no provisioned servers to manage.  
- **Providers:**  
  * AWS Lambda (Node.js, Python, Java, Go) – triggers: S3, DynamoDB, API Gateway, CloudWatch, etc.  
  * Azure Functions (C#, Python, JavaScript) – triggers: Blob storage, Queue, HTTP, Timer.  
  * Google Cloud Functions (Node.js, Python, Go) – triggers: Cloud Storage, Pub/Sub, HTTP.  
- **Cold starts:** When a function is invoked after idle period, the runtime may spin up a new container, causing latency (seconds). Critical for latency‑sensitive APIs.  
- **When serverless is a poor fit:**  
  * Long‑running processes (hours).  
  * Workloads with sustained high CPU/memory (costly).  
  * Need for persistent state or shared memory.  
  * Strict low‑latency requirements (e.g., real‑time trading).

**CL19** – **Cost‑optimization strategy for $80k/month**  

1. **Reserved Instances vs Savings Plans vs Spot/Preemptible**

   * **Savings Plans** – Flexible compute‑hour commitment across instance families/regions; better utilization than RI.  
   * **Spot / Preemptible** – Unused capacity at steep discounts; suitable for fault‑tolerant, batch, or stateless jobs.  

2. **Right‑sizing** – Use CloudWatch/Cost Explorer + AWS Compute Optimizer or Azure Advisor to down‑size over‑provisioned VMs, containers, or functions.  

3. **Storage tiering** –  
   * Hot data → Standard SSD.  
   * Warm data → Standard HDD or S3 Standard.  
   * Cold/Archive → S3 Intelligent‑Tiering, Glacier, or Azure Cold Blob.  

4. **Idle resource detection** – Deploy tools like **AWS Compute Optimizer**, **Azure Monitor for VMs**, or **Datadog** to identify idle VMs, containers, and functions; schedule auto‑scaling or shut them down.  

5. **FinOps practices** –  
   * Define cost‑allocation tags.  
   * Set budgets & alerts (AWS Budgets, Azure Cost Management).  
   * Implement “pay‑as‑you‑go” tagging policies.  
   * Regular cost reviews & governance.  

6. **Showback / Chargeback** –  
   * Use **AWS Cost and Usage Report** + **Snowflake** or **Azure Cost Management + FinOps** to produce reports per business unit.  
   * Integrate with ticketing/billing systems for internal invoicing.  

**Tools & processes for visibility:**  
- **AWS:** Cost Explorer, Budgets, Cost and Usage Report, Trusted Advisor, Compute Optimizer, CloudWatch Alarms.  
- **Azure:** Cost Management + Billing, Azure Advisor, Monitor, Log Analytics Workspace, Azure Policy for tagging.  
- **Cross‑cloud:** **CloudHealth**, **Cloudability**, or **Cloudability** for unified dashboards.  
- **Processes:** Weekly cost review meetings, automated tagging enforcement, governance via Service Catalog/Policy, FinOps champion role.

**CL20** – **Multi‑cloud strategy (AWS + Azure) to avoid lock‑in**  

1. **Abstraction layers** – Use container images + Kubernetes manifests; abstract infra‑specific services behind custom operators or façade libraries.  
2. **Kubernetes as common runtime** – Deploy clusters on both clouds (EKS, AKS, GKE) and use the same workloads (Helm charts, Kustomize) across them.  
3. **IaC portability** – Terraform (or OpenTofu) with provider blocks for both AWS and Azure; use `terraform.workspace` or environment variables to switch.  
4. **Networking between clouds** –  
   * **VPN** (AWS‑Azure) via CloudHub, ExpressRoute Connect, or Azure ExpressRoute + AWS Direct Connect.  
   * **Interconnect** – Use a third‑party service (e.g., Google Cloud Interconnect) or a dedicated circuit.  
5. **Identity federation** – Deploy a central IdP (Okta, Azure AD, Auth0) and configure SAML/OIDC trusts to both clouds; use AWS IAM Identity Center and Azure AD Conditional Access.  
6. **Trade‑offs** –  
   * **Benefits:** Reduced vendor dependence, ability to choose best‑of‑breed services, negotiate better pricing.  
   * **Costs:** Increased operational complexity, duplicated expertise, networking overhead, potential data‑gravity issues, compliance across jurisdictions.  

**When multi‑cloud is justified:**  
- Business continuity across regions with different regulatory regimes.  
- Need for services not available on a single provider (e.g., a specific database engine only on Azure).  
- Competitive sourcing or cost‑optimization across providers.  

**When it’s unnecessary complexity:**  
- All required services are available on a single provider.  
- Team lacks expertise to manage multiple platforms.  
- Simple lift‑and‑shift with minimal integration requirements.

**OT1** – **Purdue Model (ISA‑95) – Levels 0‑5**  

| Level | Description |
|-------|-------------|
| **Level 0 – Production Floor (Physical Process)** | Sensors, actuators, PLCs, RTUs directly controlling equipment (e.g., motors, valves). |
| **Level 1 – Control (Supervisory Control)** | PLCs/RTUs execute control logic; HMI/SCADA displays real‑time data; basic data acquisition. |
| **Level 2 – Operations (Manufacturing Execution)** | MES systems coordinate production scheduling, batch control, quality, and material tracking; interfaces with Level 3. |
| **Level 3 – Site/Plant Management** | Plant-wide monitoring, historical data archiving, performance KPI dashboards, maintenance planning. |
| **Level 4 – Enterprise Integration** | ERP, logistics, supply‑chain, financial systems; integrates plant data for enterprise planning. |
| **Level 5 – Business Management** | Strategic planning, sales, market analysis; uses aggregated data from Level 4. |

---

**OT2** – **IT vs OT networks & patching**  

- **IT network:** Focus on data, user productivity, external connectivity; uses TCP/IP, Ethernet, often VLAN‑segmented, supports diverse OSes, patching is routine.  
- **OT network:** Focus on real‑time control of physical processes; uses deterministic protocols (Modbus, EtherNet/IP), often Ethernet/IP, PROFINET; devices are embedded, limited computing, may run legacy OSes.  

**Why standard IT patching doesn’t work:**  
- OT devices have limited resources; a patch can cause reboot, downtime, or break deterministic timing.  
- Many OT devices lack patch management agents or support.  
- Patching windows are tightly constrained by production schedules; unplanned reboots can halt manufacturing.  

---

**OT3** – **Industrial DMZ (IDMZ) role**  

- **Purpose:** Acts as a buffer zone between corporate IT (Level 4) and OT (Level 1‑3) to limit exposure while allowing necessary data flow.  
- **Allowed traffic:**  
  * **Inbound to OT:** Limited, specific protocols (e.g., OPC UA, MQTT) from the DMZ to SCADA/PLC servers, usually via a hardened gateway.  
  * **Outbound from OT:** Process data (historical, metrics) pushed to the DMZ (e.g., via OPC UA or MQTT) for analytics; typically only outbound.  
- **Direction:** Generally **unidirectional** (OT → DMZ) for data collection; occasional **controlled inbound** (e.g., engineering tools) through strict firewall rules.  
- **Why direct Level 4 → Level 1 is dangerous:** It bypasses segmentation, exposing critical control devices to malware, unauthorized access, and network storms that could disrupt production.  

---

**OT4** – **OT protocols & typical Purdue level**  

| Protocol | Typical Purdue level |
|----------|---------------------|
| **Modbus TCP** | Level 1 (PLC/IO) – direct device communication. |
| **OPC UA** | Level 2‑3 – used for higher‑level data collection (SCADA, MES). |
| **EtherNet/IP (CIP)** | Level 1 – industrial control (PLC, motor drives). |
| **PROFINET** | Level 1 – real‑time fieldbus for motion control. |
| **MQTT** | Level 3‑4 – lightweight publish/subscribe for telemetry and cloud integration. |

---

**OT5** – **Data diode vs firewall**  

- **Data diode:** Hardware device that allows **unidirectional** data flow (usually read‑only from secure to less‑secure zone). No processing, no bidirectional communication.  
- **Firewall:** Software/appliance that filters **bidirectional** traffic based on rules; can block, allow, inspect payloads.  

**When to use hardware data diode:**  
- When you need a guaranteed one‑way flow (e.g., sending process data from a secure control network to a DMZ/analytics server) with zero risk of inbound attacks.  

**Limitation:** Cannot enforce complex policies, cannot inspect or modify traffic, and cannot support interactive protocols (e.g., VNC, RDP). Firewalls provide richer control but are vulnerable to compromise.  

---

**OT6** – **SCADA → Cloud analytics data flow**  

1. **SCADA system** (Level 2) collects real‑time data from PLCs.  
2. **Historian** (Level 3) stores raw/time‑series data locally.  
3. **OPC UA Server** (on edge or plant) publishes data via OPC UA Pub/Sub or HTTP.  
4. **MQTT broker** (edge‑deployed, e.g., Mosquitto) receives OPC UA‑converted telemetry (QoS 1/2).  
5. **Edge gateway** (e.g., Azure IoT Edge, AWS Greengrass) filters, enriches, and forwards to cloud.  
6. **Cloud ingestion** (e.g., AWS IoT Core, Azure IoT Hub) validates, stores in time‑series DB (InfluxDB, TimescaleDB) or data lake.  

**Security boundaries:**  
- **OT network (Level 1‑2)** – isolated VLAN, strict firewall.  
- **DMZ/Edge** – separate VLAN with only allowed outbound to cloud.  
- **Cloud** – separate VPC/Subnet with least‑privilege IAM, encryption, and logging.  

---

**OT7** – **IEC 62443 security zones & conduits**  

- **Zone:** Logical grouping of assets with similar security requirements (e.g., “Corporate Network”, “Engineering Workstation Zone”, “SCADA Server Zone”, “PLC Zone”, “SIS Zone”).  
- **Conduit:** Controlled pathway (usually a firewall or router) that permits specific, authorized communication between zones (e.g., data from PLC Zone to SCADA Server Zone).  

**Proposed zone‑and‑conduit model:**  

| Zone | Assets | Security level (high → low) | Conduits |
|------|--------|----------------------------|----------|
| **Zone 1 – Corporate** | End‑user PCs, domain controllers, internet gateway. | Low | Conduit to Zone 2 only for email/web. |
| **Zone 2 – Engineering** | Engineer workstations, CAD servers. | Medium | Conduit to Zone 3 for software updates; restricted inbound. |
| **Zone 3 – SCADA/ Historian** | SCADA server, historian DB. | High | Conduit to Zone 4 (PLC) for control commands; read‑only from Zone 5 (SIS) if needed. |
| **Zone 4 – PLC / IOP** | PLCs, RTUs, HMIs. | Very High | Conduit to Zone 5 (SIS) for safety interlocks; no direct conduit to corporate. |
| **Zone 5 – SIS** | Safety Instrumented System controllers. | Critical | Conduit only to Zone 4 (bidirectional for safety); isolated from all others. |

Each conduit is enforced by a firewall with strict ACLs, often using **deep packet inspection** and **application‑layer filtering**.

**OT8** – **Network segmentation for 200 PLCs, 30 HMIs, SCADA, historian (flat Layer 2)**  

1. **VLAN design**  
   - **VLAN 10 – PLCs** (tagged, isolated, VLAN‑10).  
   - **VLAN 20 – HMIs / Operator stations**.  
   - **VLAN 30 – SCADA server & historian**.  
   - **VLAN 40 – Management (Routers, switches, admin PCs)**.  
   - **VLAN 50 – Guest / vendor access** (isolated, limited).  

2. **Firewall placement**  
   - **Core firewall** between VLAN 40 (management) and VLAN 10/20/30.  
   - **Layer‑2 switch ACLs** or **next‑gen firewalls** at each VLAN boundary for fine‑grained control.  

3. **Switch architecture**  
   - Use **managed Gigabit switches** with **Port‑based VLAN tagging**.  
   - Enable **Spanning Tree Protocol (RSTP)** for redundancy.  
   - Configure **Port Security** to limit MAC addresses per port.  

4. **Remote vendor access**  
   - **Jump hosts** in VLAN 40, accessed via MFA and Bastion host.  
   - **VPN** (IPsec or SSL) terminating at a dedicated **vendor gateway** in VLAN 40.  
   - **Session recording** (e.g., Fortinet FortiRecorder) for all admin sessions.  

5. **Transition without production stop**  
   - **Phased VLAN rollout**: enable VLAN tagging on switches, keep existing ports in native VLAN, gradually move devices.  
   - Use **virtual stacking** or **switch firmware** that supports VLAN reconfiguration without rebooting.  
   - Perform **maintenance windows** for critical lines; use **hot‑standby** PLCs where possible.  
   - Validate connectivity with **ping/traceroute** and **port mirroring** before cutting links.  

---

**OT9** – **SIS vs BPCS & IEC 61511**  

- **BPCS (Basic Process Control System)** – Handles routine control (temperature, pressure, flow). It is **non‑safety**; failures may affect product quality but not immediate safety.  
- **SIS (Safety Instrumented System)** – Provides independent protection layers to bring a process into a safe state when hazardous conditions occur (e.g., emergency shutdown). It is **safety‑critical** and must meet IEC 61511.  

**IEC 61511** – International standard for functional safety of SIS; defines requirements for risk assessment, safety requirements specification, hardware/software safety functions, validation, and lifecycle management.  

**Why SIS network must be air‑gapped/isolated:**  
- Prevents accidental or malicious interference that could disable safety functions.  
- Reduces attack surface; ensures SIS operates independently of IT/BPCS networks.  

**Impact of ransomware on SIS:**  
- Ransomware could encrypt SIS control logic or disable safety functions, leading to uncontrolled releases, explosions, or environmental harm.  
- Recovery may require manual safe‑shutdown, potentially causing plant shutdown, costly downtime, and safety incidents.  

---

**OT10** – **PLC, DCS, SCADA differences**  

| System | Primary purpose | Typical scale | Example use |
|--------|----------------|---------------|-------------|
| **PLC** | Low‑level, deterministic control of discrete/continuous I/O. | Single machine or small cell. | Motor control, batch valve sequencing. |
| **DCS** | Distributed control across an entire plant; integrates multiple loops, historical trending, alarm management. | Medium‑large plant (multiple units). | Chemical plant process control, refinery units. |
| **SCADA** | Supervisory data acquisition & visualization; aggregates data from PLCs/DCS for operator monitoring. | Plant‑wide or enterprise‑wide. | HMI for water treatment plant, monitoring across sites. |

**Can they coexist?** Yes. PLCs feed data to DCS/SCADA; DCS may coordinate multiple PLCs; SCADA presents the overall picture to operators.

**OT11** – **Remote OT access architecture**  

1. **Jump hosts / Bastion servers** placed in a demilitarized zone (DMZ) with strict firewall rules.  
2. **MFA** (TOTP, hardware token) required for bastion login.  
3. **Session recording** (e.g., BeyondTrust, JumpBox) to audit all actions.  
4. **Vendor access** – time‑limited, role‑based accounts; credentials rotated automatically.  
5. **RDP directly to HMI from corporate network** is unacceptable because:  
   - Exposes HMI (Level 1/2) to internet‑facing threats.  
   - Bypasses network segmentation and audit controls.  
   - Increases risk of lateral movement into OT.

**OT12** – **Detection & response for water treatment facility (Level 3 compromise)**  

1. **Network monitoring**  
   - Deploy **IDS/IPS** (Snort, Suricata) on internal segmentation firewalls.  
   - Use **anomaly detection** (NetFlow, Zeek) to spot unusual traffic patterns (e.g., unexpected protocols, large data bursts).  

2. **Asset inventory**  
   - Maintain a **CMDB** with PLC/HMI/SIS serial numbers, firmware versions, and network addresses.  
   - Perform **passive fingerprinting** (SNMP, ARP) to discover devices.  

3. **Incident response steps**  
   - **Contain**: Isolate compromised VLAN (e.g., block traffic at firewall).  
   - **Eradicate**: Reimage affected devices, apply patches, update credentials.  
   - **Recover**: Restore from clean backups; verify safety interlocks.  
   - **Post‑incident**: Review logs, update detection rules, improve segmentation.  

4. **Coordination with control room**  
   - **Control room operators** verify that safety functions (SIS) remain operational.  
   - Provide **real‑time status** of network isolation and any manual overrides needed.  

5. **Ensuring safe operations**  
   - Keep **SIS** and **BPCS** on separate networks; maintain **air‑gap** for safety.  
   - Use **redundant** communication paths; have **manual emergency shutdown** procedures.  

**Role of plant operator during cyber incident:**  
- Monitor HMI for anomalies, confirm safety system status.  
- Execute **pre‑defined safe‑state procedures** (e.g., emergency shutdown) if automated safety functions are compromised.  
- Document actions, communicate with security team, and assist in forensic analysis.

**OT13** – **HMI definition & role**  

- **HMI (Human‑Machine Interface)** – The graphical client that allows operators to view real‑time process data, interact with control systems, and initiate commands. It sits at Level 2 (SCADA) or Level 3 (plant).  

- **Difference from engineering workstation:**  
  - **Engineering workstation** is used for configuration, programming, and maintenance of control logic (e.g., PLC programming, SCADA configuration).  
  - **HMI** is for **operational** viewing/control, typically with limited access rights and optimized for real‑time visualization.  

---

**OT14** – **Historian in OT**  

- **Definition:** A time‑series database that continuously records process variables (tags) with high fidelity and retention.  

- **Why important:** Enables trend analysis, performance optimization, compliance reporting, and root‑cause analysis.  

- **Plant historian (Level 3) vs Enterprise historian (Level 4):**  
  - **Plant historian** stores raw, high‑frequency data locally; used for immediate process optimization and safety analysis.  
  - **Enterprise historian** aggregates/leans data from multiple plant historians, integrates with ERP/MES, and supports longer‑term business analytics.  

---

**OT15** – **Ladder logic**  

- **What it is:** A graphical programming language resembling electrical ladder diagrams; represents relay‑logic sequences.  
- **Device:** Executed on **PLC** (Programmable Logic Controller) using a CPU that scans the ladder diagram.  
- **Why still dominant:**  
  - **Maturity & familiarity** for control engineers.  
  - **Deterministic execution** and real‑time performance.  
  - **Robustness** in harsh industrial environments; many legacy systems rely on it.  

---

**OT16** – **RTU vs PLC**  

- **RTU (Remote Terminal Unit):** Typically a ruggedized device for **remote** telemetry; limited processing, often used in SCADA for data collection (e.g., oil fields, water pipelines).  
- **PLC:** More powerful, designed for **local control** with advanced logic, motion control, and networking capabilities.  

**When to use RTU:**  
- Large geographically dispersed sites where bandwidth is limited and you need to send aggregated data back to a central SCADA.  
- Harsh environments where low power consumption and simple I/O are preferred.  

**When to use PLC:**  
- Complex control loops, high-speed motion, or integrated HMI/SCADA within a plant.  

---

**OT17** – **Analog vs digital signals**  

- **Analog signals** (4‑20 mA, 0‑10 V) represent continuous physical quantities (e.g., temperature, pressure).  
- **Digital signals** are discrete (0/1, high/low) representing on/off states.  

**Why 4‑20 mA preferred over 0‑20 mA:**  
- **Live zero**: 4 mA indicates a valid “zero” reading, allowing detection of a broken wire (0 mA = fault).  
- Better noise immunity and longer cable runs.  

---

**OT18** – **OT asset inventory**  

- **Concept:** Comprehensive list of all hardware, software, firmware, and connections in the OT environment.  
- **Foundation:** Enables risk assessment, patch management, compliance, and incident response.  

**Discovery tools/techniques:**  
- **Passive network monitoring** (NetFlow, packet captures) to see devices and protocols.  
- **Active scanning** (SNMP, SSH, Telnet) to query device properties.  

**Why active scanning is dangerous:**  
- Can trigger resets or crashes on legacy PLCs/RTUs, leading to unplanned downtime.  
- May interfere with real‑time control loops.

**OT19** – **MITRE ATT&CK for ICS**  

- **Framework:** Maps adversary tactics and techniques specific to industrial control systems, extending enterprise ATT&CK with ICS‑specific behaviors.  

**Five tactics (examples):**  
1. **Initial Access** – *Supply Chain Compromise* (e.g., malicious firmware uploaded to a PLC).  
2. **Execution** – *Command and Scripting Interpreter* (e.g., PowerShell on a workstation that reaches PLC).  
3. **Persistence** – *Modify Existing Service* (e.g., malicious service on HMI).  
4. **Impact** – *Data Manipulation* (e.g., altering setpoints in a PLC).  
5. **Lateral Movement** – *Remote Services* (e.g., exploiting VNC on engineering workstation to reach PLC).  

**Difference from enterprise ATT&CK:**  
- Includes **ICS‑specific techniques** (e.g., *Manipulate Process Control Logic*, *Exploit PLC*).  
- Emphasizes **safety and availability** impacts rather than confidentiality alone.  

**Using it for defensive gaps:**  
- Map existing controls to each technique; identify missing mitigations (e.g., lack of network segmentation for *Lateral Movement*).  
- Prioritize remediation based on likelihood and impact on safety.

**OT20** – **Converged IT/OT SOC design (3 sites)**  

1. **Log collection**  
   - Deploy **OT‑optimized agents** (e.g., Syslog, NetFlow collectors) on edge gateways; use **remote collectors** (Splunk, Elastic) with **high‑frequency batching** to avoid impacting real‑time control.  
   - Implement **network taps** or **port mirroring** from OT switches to avoid injecting traffic.  

2. **SIEM integration**  
   - Central SIEM (Splunk, Azure Sentinel, QRadar) ingests OT logs, network flows, and alerts.  
   - Create **OT data models** (e.g., PLC events, HMI sessions).  

3. **OT‑specific detection rules**  
   - Rules for *unauthorized firmware changes*, *unexpected protocol usage*, *access to engineering workstations from external IPs*, *SCADA configuration changes*.  

4. **Alert triage workflow**  
   - **Tier 1** (IT analysts) handle generic network alerts.  
   - **Tier 2** (OT engineers) investigate OT‑specific alerts, verify impact on control loops, coordinate with plant operators.  

5. **Staffing**  
   - Mix of **IT SOC analysts** (network, endpoint) and **OT engineers** (PLC/HMI expertise).  
   - Cross‑training to ensure both understand each other’s tools and terminology.  

6. **False positives challenge**  
   - OT environments have **periodic spikes** (e.g., batch runs) that can look like anomalies.  
   - Use **context‑aware correlation** (time, production schedule) and **whitelist** known good patterns.  

**Handling “unauthorized firmware changes on a PLC” alert:**  
- **Immediate**: Isolate the PLC’s VLAN at the firewall, disable remote access.  
- **Verification**: OT engineer confirms the change, checks if safety interlocks still functional.  
- **Remediation**: Roll back to known‑good firmware image, apply signed update, verify integrity.  
- **Documentation**: Record incident, update asset inventory, adjust detection rules to reduce noise.
