**Monolith vs. Microservices**  
- **Monolith:** All components are tightly coupled, run in a single process, and share the same database and runtime.  
- **Microservices:** The application is split into small, independently deployable services, each with its own data store and runtime.  

**Three concrete problems introduced by microservices (not present in a monolith):**  
1. **Network latency & reliability** – Service‑to‑service calls add extra round‑trips and possible failures that a monolith avoids.  
2. **Operational complexity** – You must manage service discovery, configuration, logging, monitoring, and deployments for many services.  
3. **Data consistency & transaction management** – Distributed transactions, eventual consistency, and saga patterns are required, making data integrity harder to guarantee.

**AA3 – Medium**  
**API Gateway vs. Reverse Proxy**  
- **Reverse Proxy** – L4/L7 traffic router that forwards client requests to backend servers, typically for load balancing, SSL termination, or session stickiness. It is generic and unaware of API‑specific concerns.  
- **API Gateway** – An API‑centric reverse proxy that adds value‑added services: request routing, composition, protocol translation, rate limiting, authentication, caching, and monitoring. It understands the API contract (OpenAPI, Swagger).  

**Can an API Gateway replace a reverse proxy entirely?**  
- **Partially, but not always.** An API Gateway can handle the routing and SSL termination that a reverse proxy does, but many architectures still keep a reverse proxy (or load balancer) in front of the gateway for raw traffic distribution, health checks, and to offload TLS termination at scale. Using both gives you separation of concerns: the reverse proxy handles generic load balancing, the gateway adds API‑specific logic.

**AA4 – Medium**  
**Saga Pattern** – a sequence of local transactions that implement a distributed business transaction. If a step fails, the saga executes compensating transactions to undo previous steps.  

- **Choreography‑based saga:** Each service publishes events that trigger the next step. No central coordinator; services react to events.  
- **Orchestration‑based saga:** A central orchestrator (typically a saga coordinator) tracks the state and sends commands to services, reacting to outcomes.  

**When to use each:**  
- **Choreography** – Simpler to scale, no single point of failure, suitable when services are loosely coupled and the saga flow is relatively static.  
- **Orchestration** – Better for complex flows, conditional logic, or when you need explicit compensation ordering and observability.

**AA5 – Medium**  
**CQRS (Command Query Responsibility Segregation)**  
- **Definition:** Separate read‑only operations (queries) from write‑only operations (commands). The model is split into a **Command Side** (handles writes, updates domain) and a **Query Side** (optimised for reads, may use different data structures).  

**Why paired with Event Sourcing?**  
- Event Sourcing stores all state‑changing events, providing an immutable audit trail. CQRS can project those events into separate read models (denormalisations) that are optimised for query patterns, while the command side works directly with the event stream.  

**Problem solved vs. traditional CRUD:**  
- **Scalability & performance:** Reads can be heavily optimised (materialised views, caching) without impacting writes.  
- **Audit & replay:** Full history of changes enables debugging, replay, and compliance that CRUD tables lack.

**AA6 – Medium**  
**Circuit Breaker Pattern**  
- **Purpose:** Prevents a service from repeatedly attempting an operation that is likely to fail, allowing the system to degrade gracefully.  

**Three states:**  
1. **Closed** – Normal operation; requests flow, failures counted.  
2. **Open** – Failure threshold exceeded; further requests short‑circuit to a fallback (e.g., cached response, error) without invoking the downstream.  
3. **Half‑Open** – After a timeout, a limited number of requests are allowed to test if the downstream recovered.  

**Difference from simple retry with backoff:**  
- **Retry with backoff** still attempts the call each time, potentially overwhelming a failing dependency.  
- **Circuit breaker** stops calling altogether once failure thresholds are met, protecting resources.  

**When to use both together:**  
- Use retries with exponential backoff for transient, short‑lived glitches.  
- Add a circuit breaker to protect against prolonged outages or cascading failures. The breaker can open after repeated retries fail, and half‑open allows recovery testing.

**AA8 – Hard**  
**Eventual vs. Strong Consistency**  
- **Strong consistency:** All nodes see the same data at the same time; reads return the latest write.  
- **Eventual consistency:** Updates propagate asynchronously; after no further writes, all replicas converge to the same value.  

**Inventory system that must never oversell**  
- **Consistency model:** **Strong consistency** (or at least **linearizable** for the “reserve” operation).  
- **Data store:** A **distributed transaction‑capable** store such as **Spanner**, **CockroachDB**, or a **single‑region relational DB** with row‑level locking. If scale requires sharding, use **two‑phase commit** or **sagas** with compensation to guarantee atomic reservation.  
- **Patterns:**  
  - **Optimistic locking** on inventory rows to detect concurrent updates.  
  - **Versioned records** or **MVCC** to avoid lost updates.  
  - **Idempotent reservation service** that can be retried safely.  
  - **Read‑through/write‑through caching** with cache invalidation to keep reads consistent.  
- **At scale:** Deploy a **distributed lock service** (e.g., etcd) for critical sections, or use a **dedicated inventory service** that owns the inventory rows and runs on a **single‑writer** per shard, ensuring atomic decrements.

**AA9 – Hard**  
**Sidecar Proxy in a Service Mesh**  
- **Definition:** A proxy (e.g., Envoy) deployed alongside each application container, handling cross‑cutting concerns (traffic management, security, observability) while the app focuses on business logic.  

**Envoy in Istio**  
- **Data Plane:** All sidecar proxies (Envoy) intercept inbound/outbound traffic, enforce mTLS, implement load balancing, retries, timeouts, and collect telemetry.  
- **Control Plane:** Istio Pilot, Citadel, Galley, etc., run as separate pods, continuously push configuration to each Envoy (via SDS, XDS).  

**mTLS between sidecars vs. application‑level TLS**  
- **Application‑level TLS** encrypts only the app‑to‑app communication; the proxy sees plaintext headers and can be compromised if the app is compromised.  
- **mTLS between sidecars** ensures **service‑to‑service** encryption end‑to‑end, with mutual authentication of identities, protecting against compromised containers and enabling zero‑trust network.

**Strangler Fig Pattern**  
- **Concept:** Gradually replace a monolith with new services, routing requests through the monolith until its functionality is fully delegated.  

**Concrete migration from .NET Framework monolith to .NET 8 microservices:**  
1. **Identify a bounded context** (e.g., Order Management) that can be extracted.  
2. **Create a new .NET 8 microservice** with its own DB (or via DB migration).  
3. **Deploy the service** behind an API Gateway; configure the gateway to route `/api/orders/*` to the new service while `/api/orders/*` still calls the monolith for legacy endpoints.  
4. **Implement adapters**: Use a façade or wrapper that calls the monolith’s internal APIs where needed.  
5. **Gradually migrate data** (using change‑data‑capture) and move functionality (e.g., business logic, UI) to the new service.  
6. **Deprecate monolith endpoints** one by one, finally removing the monolith after all traffic is routed to microservices.

| Aspect | Operational Transformation (OT) | Conflict‑Free Replicated Data Types (CRDT) |
|--------|--------------------------------|-------------------------------------------|

**Recommendation for offline editing:** Use **CRDTs** because they allow local edits without waiting for remote transformations and automatically resolve conflicts when the connection is restored.

**AA20 – Hard**  
**Distributed Tracing Challenges in Polyglot Microservices**  

- **Context propagation:** Different languages/frameworks use different header formats (W3C Trace Context `traceparent`, B3 single/double header). Need a uniform injector/extractor or a proxy that translates between them.  
- **Sampling strategies:**  
  - **Head‑based sampling** – decide at request start; may miss short‑lived traces.  
  - **Tail‑based sampling** – record after the request finishes; requires storage for all spans, higher cost.  
- **Trace storage & querying:**  
  - **Jaeger** – open‑source, spans stored in Cassandra/ES, good for moderate scale.  
  - **Tempo (Grafana)** – uses chunked OTLP, stores traces in object storage, scales to high volume.  
- **Interaction with async messaging:** When a request passes through Kafka, the span context must be injected into message headers (e.g., using `MessageHeaders` with traceparent) and extracted by the consuming service. Ensure the producer adds the context, and the consumer propagates it further.  

**Ensuring trace continuity across Kafka:**  
1. **Instrument producers** to inject the active span’s trace ID and span ID into Kafka message headers (using a library like `opentracing-kafka-client` or `java-kafka-clients` with `Tracer`).  
2. **Configure consumers** to extract the headers and continue the span (or start a new child span).  
3. **Use a tracing interceptor** that automatically propagates context for both send and receive operations.  
4. **Validate** by checking that spans appear as a chain: HTTP → Kafka producer → Kafka consumer → downstream service.

**VLAN Trunking & 802.1Q**  

- **VLAN trunking** allows a single physical NIC to carry traffic for multiple VLANs.  
- **802.1Q tagging** inserts a 4‑byte VLAN identifier into Ethernet frames.  

**Linux configuration for a single NIC on 3 VLANs:**  
```bash
# Create bridge for each VLAN (or one bridge with multiple ports)
ip link add dev bond0 type bond mode active-backup
ip link set dev bond0 master br0

# Add NIC to bond
ip link set dev eth0 master bond0

# Create VLANs as sub‑interfaces (802.1Q)

ip link add link bond0 name bond0.20 type vlan id 20
ip link add link bond0 name bond0.30 type vlan id 30

ip link set bond0 up
ip link set bond0.10 up
ip link set bond0.20 up
ip link set bond0.30 up
```  

**OP6 – Medium**  
**RAID Levels Overview**  

| RAID | Description | Pros | Cons |
|------|-------------|------|------|
| **RAID 1** | Mirror; data duplicated on each drive. | Simple, fast reads, good fault tolerance (1 drive loss). | 50 % capacity overhead. |
| **RAID 5** | Block‑level striping with distributed parity. | Good read performance, tolerates 1 drive loss, efficient capacity. | Write penalty, slower rebuild, vulnerable during rebuild. |
| **RAID 6** | Striping with double parity. | Tolerates 2 drive failures, good for large arrays. | Higher write penalty, more complex. |
| **RAID 10** | Mirror of stripes (RAID 1+0). | Excellent performance, tolerates multiple failures as long as mirrored pairs survive. | 50 % capacity overhead, complex to build. |
| **RAID Z2 (ZFS)** | Striped with two parity disks (similar to RAID 6). | ZFS features (snapshots, self‑healing), good performance, easy management. | Similar to RAID 6. |

**Choice for 6 drives, DB server (balance performance, capacity, fault tolerance):**  
- **RAID 10** is often preferred for databases because it offers **high read/write performance** and tolerates a single drive failure (mirrored pairs). With 6 drives you can create three mirrored pairs (2‑disk mirrors) and stripe across them, giving you 3 TB usable (if each drive 1 TB) and fast I/O.  
- If you need more capacity and can accept write penalty, **RAID 5** (5 drives) + 1 hot spare could be used, but RAID 10 gives better performance for random I/O typical of DB workloads.

**OP7 – Hard**  
**DNS Architecture for 500‑person Enterprise**  

- **Internal AD DNS:** Primary authoritative zone for `corp.example.com`. Runs on domain controllers, provides **dynamic updates**, **split‑horizon** (internal vs external views).  
- **DMZ authoritative servers:** Separate DNS servers for public zones (`example.com`, `mail.example.com`). Configured with **forwarders** to external ISPs for recursion.  
- **Recursive resolvers:** Internal clients use a **forwarder** (e.g., corporate DNS server) that forwards external queries to Internet root hints; DMZ servers act as **authoritative** for external zones.  
- **Conditional forwarding:** From internal DNS to external forwarders; from DMZ DNS to internal DNS for internal lookups (to avoid leaking internal records).  
- **DNSSEC on external zone:** Sign the public zone with a **KSK** (signing key) and **ZSK** (zone signing key). Publish DS records at the parent registry.  
- **Laptop moving between office and VPN:**  
  - **Office network:** DHCP assigns a **site‑local** DNS suffix; laptop registers its hostname via AD dynamic updates.  
  - **VPN connection:** VPN client adds the corporate DNS servers (internal AD DNS) to the client; laptop continues to use them, so name resolution remains consistent.  
  - **Split‑horizon:** Internal queries resolve to internal IPs; external queries go to DMZ authoritative servers.

**OP8 – Hard**  
**PKI Chain of Trust**  

1. **Root CA** – Offline, highly protected, signs **subordinate CA certificates**.  
2. **Subordinate/Issuing CA** – Online, signs **end‑entity certificates** (server, client, user).  
3. **End‑entity certificate** – Issued to user/host; contains public key, subject, validity, CA signature.  

**Certificate lifecycle management:**  
- **CRL (Certificate Revocation List)** – periodically published list of revoked certificates.  
- **OCSP (Online Certificate Status Protocol)** – real‑time checking via an OCSP responder.  

**Auto‑enrollment (Windows)** – Domain controllers issue templates; computers/users automatically request and receive certificates based on template policies.  

**Consequences of compromise:**  
- **Subordinate CA compromised:** Attacker can issue arbitrary certificates for any domain, effectively breaking trust for all certificates issued by that CA. Requires immediate revocation of the CA certificate and re‑issuance.  
- **Root CA compromised:** Catastrophic – the entire trust chain is broken; all certificates signed by that root become untrustworthy. Requires offline root key replacement and re‑signing of all subordinate certificates (a massive operation).

**OP9 – Hard**  
**Hub‑and‑Spoke WAN Options (5 remote offices, 50 users/site, latency‑sensitive VoIP)**  

| Technology | Cost | Reliability | Latency | Management Complexity | Security Posture |
|------------|------|-------------|---------|-----------------------|-------------------|
| **MPLS** | High (circuit‑based) | Very high (QoS built‑in) | Low (dedicated paths) | Moderate (carrier‑managed) | Strong (private network) |
| **IPsec VPN over Internet** | Low (uses existing internet) | Good (depends on ISP) | Variable (depends on path) | Low‑moderate | Requires strong encryption, key management |
| **SD‑WAN** | Medium‑high (appliances + licensing) | Good (multiple transport paths, failover) | Low‑moderate (optimizes paths) | Moderate (centralized orchestration) | Can integrate IPsec, TLS; policy‑driven |
| **WireGuard Mesh** | Very low (open‑source, lightweight) | Good (if underlying internet stable) | Low (direct tunnels) | Low (simple config) | Strong (modern cryptography) but requires careful key management |

**Recommendation for latency‑sensitive VoIP with 50 users per site:**  
- **SD‑WAN** is the best fit: it provides **QoS prioritization** for voice traffic, **automatic failover** between internet links, centralized policy management, and can combine multiple transport types (broadband + cellular). It balances cost and performance better than pure MPLS while offering more reliability and control than a basic IPsec VPN.

**OP10 – Medium**  
**iDRAC / iLO / IPMI** – **Out‑of‑Band Management** firmware that provides remote server monitoring and control (CPU stats, temperature, power, console).  

- **Why critical:** Allows administrators to troubleshoot, patch, reboot, or collect logs even when the OS is down, supporting rapid incident response and reducing downtime.  

**If IPMI interface is exposed to the internet:**  
- Attackers can gain **administrative access** to servers, potentially executing arbitrary commands, changing BIOS settings, or powering off machines. It becomes a **high‑value attack surface**; immediate remediation includes disabling external access, using VPN‑based IPMI, and enforcing strong authentication.

**OP11 – Medium**  
**LVM vs. LVM‑Thin vs. ZFS**  

| Feature | LVM | LVM‑Thin | ZFS |
|---------|-----|----------|-----|
| **Underlying FS** | Usually ext4/xfs; logical volumes are thin‑provisioned at LVM level. | Same as LVM but volumes are **thin‑provisioned** (no pre‑allocation). | Integrated filesystem with its own storage management. |
| **Snapshot semantics** | Snapshots are read‑only copies of the logical volume at a point in time; changes to the original volume are not reflected in the snapshot (copy‑on‑write). | Same as LVM snapshots; thin provisioning reduces space usage. | Snapshots are lightweight, copy‑on‑write; can be cloned efficiently; supports snapshot deletion without affecting original. |
| **When to use** | Simple volume management, legacy systems. | When you need flexible provisioning (e.g., many VMs with varying sizes). | When you need advanced features: snapshots, deduplication, self‑healing, quotas, and integrated RAID. |

**OP12 – Hard**  
**Stretch Cluster / DR for 3‑node Proxmox + Ceph**  

- **Goal:** Survive a **complete site failure** (e.g., rack or data‑center outage).  
- **Design options:**  
  1. **Stretch Ceph cluster** – add a fourth node in a remote site, configure **CRUSH** rules to place OSDs across sites, use **monitors** ( Ceph monitors ) placed one per site with a **tiebreaker** (a fifth node or external KVM) to avoid split‑brain.  
  2. **Active‑passive DR** – replicate Ceph snapshots to a secondary site (e.g., using **Ceph Snapshots → RadosGW → object store** or **CephFS mirroring**) and fail over Proxmox VMs using **Pacemaker** with remote resources.  

- **Ceph CRUSH rules:** Define **replicated** or **erasure** coding placement; for stretch clusters, use **“rack”** or **“region”** CRUSH buckets to ensure OSDs are spread across sites.  

- **Monitor placement:** At least **2 monitors** in each site (total 4) with a **tiebreaker** (a fifth monitor or external KVM) to guarantee quorum when one site is down.  

- **Network latency requirements:** Keep inter‑site latency < 50 ms for Ceph replication; otherwise performance degrades.  

- **Split‑brain problem:** Without a tiebreaker, a network partition can cause two sites each believing they have a majority of monitors, leading to inconsistent data. The tiebreaker (a fifth monitor or external KVM) provides a decisive vote to break the tie.  

- **Why 2‑site Ceph is generally a bad idea without a tiebreaker:** Ceph’s monitor quorum logic can deadlock in a two‑site configuration if both sites lose connectivity to each other; a tiebreaker ensures a deterministic winner.

**OP13 – Easy**  
**DHCP & DORA**  

- **DHCP (Dynamic Host Configuration Protocol)** automatically assigns IP addresses and network parameters to clients.  

- **DORA (Discover, Offer, Request, Acknowledge):**  
  1. **Discover** – Client broadcasts “I need an IP.”  
  2. **Offer** – DHCP server replies with a proposed address.  
  3. **Request** – Client requests the offered address.  
  4. **Acknowledge** – Server confirms assignment.  

**If DHCP server is unavailable and lease expires:**  
- The client will **fail to obtain a new lease**, fall back to **APIPA** (IPv4) or **link‑local** addressing (169.254.0.0/16), and may display a warning that it is operating with limited connectivity.

**OP14 – Easy**  
**Managed vs. Unmanaged Switch**  

- **Unmanaged Switch:** Plug‑and‑play, no configuration, basic forwarding.  
- **Managed Switch:** Full CLI/web UI, supports VLANs, QoS, ACLs, SNMP, spanning‑tree, stacking, etc.  

**Enterprise‑relevant managed features:**  
- **VLAN tagging (802.1Q)**, **Port security**, **Link aggregation (LAG)**, **QoS (DSCP)**, **SNMP monitoring**, **RSTP**, **Port mirroring** for troubleshooting, **IP‑based access control**.

**OP15 – Easy**  
**NTP (Network Time Protocol)** – synchronizes system clocks over a network to a common time source.  

- **Why critical:** Consistent timestamps are essential for security logs, authentication (Kerberos), audit trails, distributed transaction ordering, and coordinated backups.  

- **What can go wrong with clock drift:**  
  - **Kerberos** tickets may be rejected if client/server clocks differ beyond the allowed skew.  
  - **Log correlation** across services becomes unreliable.  
  - **Distributed consensus** (e.g., Paxos/Raft) may cause nodes to disagree on leadership.

**Physical Server vs. VM vs. Container**  

| Type | Description | Typical Use Cases |
|------|-------------|-------------------|
| **Physical Server** | Bare‑metal hardware running an OS directly. | High‑performance workloads, databases, heavy I/O, licensing constraints. |
| **Virtual Machine** | Hypervisor abstracts hardware; guest OS runs as a VM. | Multi‑tenant hosting, legacy apps, isolation, rapid provisioning. |

**When to run workload directly on bare metal:**  
- When you need **direct hardware access** (e.g., high‑throughput networking, GPU acceleration, low‑latency storage) or when licensing prohibits virtualization.

**OP17 – Easy**  
**UPS vs. Generator**  

- **UPS (Uninterruptible Power Supply):** Provides **instantaneous** battery power during outages, allowing graceful shutdown or short‑term operation.  
- **Generator:** Supplies **continuous** power after the UPS battery depletes, typically diesel or natural gas.  

**Why need both:** UPS handles the **transition period** and provides clean, regulated power; generator handles **long‑duration** outages.  

**ATS (Automatic Transfer Switch):** Automatically switches electrical loads from utility power to generator (or UPS) and back, ensuring **zero‑downtime** for critical loads.

**OP18 – Medium**  
**Active‑Passive vs. Active‑Active Clustering**  

- **Active‑Passive:** One node is primary (active), the other is idle (standby). Failover is manual or automatic but the passive node must be kept in sync.  
- **Active‑Active:** Both nodes serve traffic simultaneously, using **resource groups** and **distributed lock managers** to keep data consistent (e.g., PostgreSQL streaming replication with logical replication).  

**Implementing HA for PostgreSQL with Pacemaker/Corosync:**  

1. **Configure PostgreSQL** with **streaming replication** (primary → standby).  
2. **Set up Pacemaker resources:**  
   - **Primitive** for the virtual IP (`ocf:heartbeat:IPaddr2`).  
   - **Primitive** for PostgreSQL service (`ocf:linbit:drbd` + `ocf:heartbeat:postgres`).  
3. **STONITH (fencing):** Configure IPMI/DRAC power‑off for any node that loses heartbeat.  
4. **Resource ordering:** Ensure IP is moved before PostgreSQL, and PostgreSQL promotion follows.  
5. **Failover behavior:** If primary node fails, STONITH fences it, Pacemaker promotes the standby as new primary, virtual IP moves to the new node, and PostgreSQL starts serving reads/writes.

**OP19 – Hard**  
**Backup & Recovery Strategy for 50‑server On‑Prem Environment**  

- **3‑2‑1 Rule:** 3 copies of data, on 2 different media, 1 copy off‑site.  
- **RPO/RTO requirements:** Define acceptable data loss (RPO) and downtime (RTO) per workload (e.g., RPO ≤ 15 min for databases, RTO ≤ 4 h for file servers).  
- **Backup types:**  
  - **Full** – baseline, used for quick restores.  
  - **Incremental** – captures changes since last backup; low storage, longer restore.  
  - **Differential** – captures changes since last full; faster restore than incremental but more storage.  
- **Deduplication:** Reduce storage footprint, especially for virtual machine images and file servers.  
- **Storage media:**  
  - **Disk (NAS/SAN)** – fast restores, used for short‑term (daily) backups.  
  - **Tape** – cheap, high capacity, suitable for long‑term archival (off‑site).  
  - **Cloud** – off‑site replication (e.g., AWS S3, Azure Blob) for disaster recovery.  
- **Immutable backups:** Use write‑once storage (e.g., WORM S3 buckets, tape) to protect against ransomware deletion.  
- **Testing restores:** Perform quarterly **full restore drills** for critical systems; document results and adjust RTO/RPO as needed.  

**Difference between backup and disaster recovery:**  
- **Backup** = copying data for restoration after accidental loss, corruption, or deletion.  
- **Disaster Recovery (DR)** = holistic plan (infrastructure, processes, failover) to restore **services** after a major outage (site loss, hardware failure, cyber‑attack), often involving replicated systems, failover networks, and documented runbooks.

**OP20 – Hard**  
**802.1X Port‑Based Network Access Control**  

- **Supplicant:** Client device (e.g., workstation, IoT) that initiates authentication.  
- **Authenticator:** Managed switch port that controls access; enforces authentication before allowing data traffic.  
- **Authentication Server:** Typically a RADIUS server (e.g., FreeRADIUS, Cisco ACS) that validates credentials and issues attributes.  

**EAP methods:**  
- **EAP‑TLS:** Mutual TLS certificates; strong mutual authentication.  
- **PEAP (EAP‑MSCHAPv2):** Tunneled authentication; password‑based, widely supported.  

**RADIUS:** Centralized AAA; receives authentication requests from authenticator, contacts directory (AD) or external identity provider, returns acceptance/rejection and attributes (e.g., VLAN assignment).  

**Dynamic VLAN assignment:** After successful auth, RADIUS returns a **VLAN attribute**; the authenticator moves the port to that VLAN, isolating traffic per user/group.  

**Device that fails authentication:** Port is placed in an **unauthorized** or **guest** VLAN, typically blocked from internal network resources; only limited access (e.g., limited DHCP, DNS) is allowed until auth succeeds.  

**MAB (MAC Authentication Bypass):** For non‑802.1X devices ( Printers, IP phones ), the switch uses the device’s MAC address as a “username” and matches it against a RADIUS database (static MAC‑based entries).
