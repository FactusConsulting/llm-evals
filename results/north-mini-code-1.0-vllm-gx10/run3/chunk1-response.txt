**N1** – *Layer 2 vs. Layer 3 switch*  
- **Layer 2 (switch)** – Operates at the Data Link layer (OSI 2). It forwards frames based on MAC addresses, learns a MAC‑to‑port table, and isolates collision domains. No routing logic; all traffic on a VLAN stays within that VLAN.  
- **Layer 3 (router/switch)** – Adds network‑layer intelligence (OSI 3). It can route IP packets, maintain an IP routing table, and perform inter‑VLAN routing. It still switches frames on a per‑MAC basis but can also forward based on destination IP addresses and perform NAT, ACLs, etc.

**N2** – *Network and broadcast addresses for 10.0.5.37/20*  
- Prefix length **/20** → mask **255.255.240.0** (third octet increments by 16).  
- **Network address:** **10.0.0.0** (the first address in the /20 block).  
- **Broadcast address:** **10.0.15.255** (the last address in the block).

**N3** – *TCP three‑way handshake & lost final ACK*  
1. **SYN** – Client → Server (synchronize).  
2. **SYN‑ACK** – Server → Client (acknowledge and synchronize).  
3. **ACK** – Client → Server (acknowledge server’s SYN).  

If the **final ACK** never reaches the server, the server remains in **SYN‑RECEIVED** state, waiting for that ACK. The client assumes the connection succeeded (it has already sent data after step 3). The server will eventually time‑out and abort the half‑open connection, causing a connection failure on the server side. Retransmission timers and TCP’s persistence detection eventually close the dangling connection.

**N4** – *SNAT vs. DNAT*  
- **Source NAT (SNAT)** – Translates the **source** IP/port of a packet, usually on a firewall/NAT gateway.  
  *Example:* Internal host `192.168.1.10` accesses the Internet. The firewall replaces `192.168.1.10:1234` with its public IP `203.0.113.5:xxxx`. The remote server sees the public IP.  
- **Destination NAT (DNAT)** – Translates the **destination** IP/port, allowing external clients to reach internal hosts behind a public IP.  
  *Example:* Web server `10.0.0.20:80` is hidden behind public IP `203.0.113.5`. An external client connects to `203.0.113.5` (port 80) and the firewall rewrites it to `10.0.0.20:80`. The internal server sees the external client’s IP.

**N5** – *Three common causes of “certificate subject name does not match target host name”*  
1. **Wrong Common Name (CN) or Subject Alternative Name (SAN).** The cert is issued for `api.example.org` but you’re connecting to `www.example.org`.  
2. **Using an IP address or hostname that isn’t listed in the cert.** Some certs only cover domain names; an IP address isn’t a match.  
3. **Certificate mis‑configuration (e.g., wildcard mismatch, missing SANs, or a cert issued for a different domain).** A wildcard `*.example.com` won’t match `mail.example.com` if the SAN list is missing.

**N6** – *VLAN vs. VxLAN*  
- **VLAN (802.1Q)** – Tagging at the data‑link layer, limited to ~4,000 VLANs per physical switch. Works within a single broadcast domain and requires switches to support the VLAN space.  
- **VxLAN (RFC 7348)** – Encapsulates Ethernet frames inside UDP, providing up to 16 million logical networks. Enables multi‑tenant overlays across existing L3 fabrics (e.g., in cloud environments).  

**When to choose VxLAN:**  
- Large‑scale data‑center/multi‑tenant environments where the number of required isolated networks exceeds the VLAN limit.  
- When you need VMs to move across physical servers while preserving their VLAN IDs (VM mobility).  
- When you have an existing L3 fabric and want an overlay network without redesigning the underlying switching infrastructure.

**N7** – *Why traffic on eth1 replies via eth0 & policy‑based routing fix*  
- **Why:** The host’s default route (`0.0.0.0/0`) points out **eth0** (`10.0.0.1`). When a packet arrives on **eth1** (source `192.168.1.5`) and the destination is outside the `192.168.1.0/24` subnet, the kernel selects the default route on eth0 for the reply, even though the inbound interface is eth1.  
- **Fix with policy‑based routing:**  
  ```bash
  # Prefer eth1 for traffic sourced from 192.168.1.0/24
  ip rule add from 192.168.1.0/24 table 100
  ip route add default via 192.168.1.1 dev eth1 table 100
  ```  
  The `ip rule` forces packets with that source to be looked up in table 100, which has a gateway on eth1. All other traffic continues to use the main routing table (eth0).

**N9** – *MTU impact of VxLAN over IPsec*  
- **Physical MTU:** 1500 bytes  
- **VxLAN overhead:** Outer IP (20) + UDP (8) + VXLAN (8) = **36 bytes**  
- **IPsec ESP overhead:** ESP header (8) + ESP trailer (8) + possible padding (up to 8) ≈ **24 bytes** (average)  

**Maximum inner payload** = 1500 – (VxLAN + IPsec) = 1500 – (36 + 24) = **1440 bytes**.  
If the inner payload exceeds 1440 B, the packet fragments on the tunnel endpoint. In practice many deployments lower the outer MTU (e.g., 1450) to accommodate the combined overhead.

**N10** – *ARP purpose & Gratuitous ARP*  
- **ARP (Address Resolution Protocol):** Resolves an IPv4 address to a MAC address on a local link‑layer network. A host broadcasts “Who has X.X.X.X?” and the owner replies with its MAC.  
- **Gratuitous ARP:** A host sends an ARP reply (or request) for its own IP address, usually after IP change or failover. It **detects IP conflicts** (if another host replies) and **updates neighboring devices’ ARP caches**, ensuring traffic is forwarded to the correct interface (e.g., after a failover).

**N11** – *Public vs. private IP & RFC 1918 ranges*  
- **Public IP:** Globally unique, routable on the Internet. Assigned by IANA/Regional registries.  
- **Private IP:** Reserved for internal networks, not routable on the public Internet; internal hosts use NAT to communicate externally.  

**RFC 1918 private IPv4 ranges:**  
1. **10.0.0.0/8** (10.0.0.0 – 10.255.255.255)  
2. **172.16.0.0/12** (172.16.0.0 – 172.31.255.255)  
3. **192.168.0.0/16** (192.168.0.0 – 192.168.255.255)

**N12** – *DNS records*  
- **A record:** Maps a hostname to an **IPv4** address (e.g., `www.example.com  A 93.184.216.34`).  
- **CNAME record:** Canonical name; an alias that points one hostname to another (e.g., `mail  CNAME  www.example.com`).  
- **AAAA record:** Maps a hostname to an **IPv6** address (e.g., `www.example.com  AAAA  2001:0db8::1`).

**N13** – *DHCP DORA process*  
1. **Discover** – Client broadcasts DHCPDISCOVER.  
2. **Offer** – DHCP servers reply with DHCPOFFER (proposed IP, lease time).  
3. **Request** – Client selects an offer and broadcasts DHCPREQUEST.  
4. **Acknowledge** – Server replies with DHCPACK, confirming the lease.

**N14** – *Hub, Switch, Router*  
| Device | Primary OSI Layer | Function | Typical Behavior |
|--------|-------------------|----------|------------------|
| **Hub** | 1 (Physical) | Repeats incoming bits to all ports; no addressing. | Broadcasts everything; shared collision domain. |
| **Switch** | 2 (Data Link) | Learns MAC addresses, forwards frames only to the port associated with the destination MAC. | Isolates collision domains, reduces broadcast scope. |
| **Router** | 3 (Network) | Routes IP packets based on destination IP addresses; maintains routing tables. | Inter‑connects different networks, performs NAT, firewalling. |

**N15** – *Half‑duplex vs. Full‑duplex*  
- **Half‑duplex:** Only one direction can transmit at a time (e.g., early Ethernet hubs). Collisions possible; uses CSMA/CD.  
- **Full‑duplex:** Simultaneous two‑way communication (e.g., modern twisted‑pair Ethernet). No collisions; uses separate transmit/receive channels.  

**Modern Ethernet links use full‑duplex** by default.

**N16** – *TTL field & traceroute*  
- **TTL (Time‑to‑Live):** Decremented by each hop; when it reaches zero the packet is discarded and an ICMP “Time Exceeded” message is sent back.  
- **Traceroute:** Sends a series of packets with incrementally increasing TTL values (starting at 1). The first ICMP Time Exceeded reveals hop 1, the second hop 2, etc., until the destination replies with an ICMP Port Unreachable (or other) message, mapping the path.

**N17** – *NAT gateway & types*  
- **NAT gateway:** Translates private‑address traffic to a public address, often with stateful tracking of connections.  
- **Static NAT:** One‑to‑one mapping of a single internal IP to a single external IP (no port changes). Used for servers reachable from the Internet.  
- **Dynamic NAT:** Pool of external IPs; internal hosts are allocated an unused external IP from the pool for the duration of a session.  
- **PAT (Port Address Translation):** Same external IP for all internal hosts, but each connection is distinguished by source/destination ports (e.g., `203.0.113.5:5060`). Provides many‑to‑one mapping.

**N18** – *ECMP routing, hashing, and firewall issues*  
- **ECMP:** When multiple routes to the same destination have equal cost, the router load‑balances traffic across them using a hash of packet fields. All packets of a flow typically stay on the same path because the hash is consistent.  
- **Common hash keys:**  
  - **2‑tuple:** Source IP, Destination IP.  
  - **4‑tuple:** Source IP, Source Port, Destination IP, Destination Port.  
  - Vendor‑specific may include protocol and VLAN ID.  
- **Problems with stateful firewalls:**  
  - **Asymmetric routing:** If hash splits return traffic onto a different ECMP path, the firewall may see the return packet on a different interface, causing rule mismatches (e.g., “allow” only on the forward path).  
  - **Session synchronization:** Firewalls must synchronize connection state across multiple paths or use “flow‑based” forwarding (e.g., FRR’s `hash-policy` or `ecmp` load‑balance with `persist`).  
  - **Packet loss/reordering:** Different paths can have different latencies, leading to out‑of‑order packets that break TCP’s reordering tolerance.

**N19** – *High latency, BDP 10 MB, window 64 KB*  
- **Problem:** The TCP receive window (64 KB) is far smaller than the bandwidth‑delay product (10 MB). The sender cannot keep the pipe full; each ACK returns only a small amount of data, causing under‑utilization despite low packet loss.  
- **Solution – TCP Window Scaling (RFC 1323):** Allows the advertised window to be multiplied by a scaling factor (up to 1000×). With scaling, the effective window can be enlarged to >10 MB, enabling the sender to transmit enough data to fill the pipe and achieve higher throughput.

**N20** – *802.1Q trunk ports & Linux sub‑interfaces*  
- **802.1Q trunk:** Carries multiple VLAN tags on a single physical link. The Ethernet frame format on the wire is:  
  `Dst MAC | Src MAC | EtherType=0x8100 | 802.1Q Tag (VLAN ID, priority, CFI) | Payload (IP, etc.)`  
- **Linux sub‑interfaces:** Create virtual interfaces for each VLAN:  
  ```bash
  ip link add link eth0 name eth0.10 type vlan id 10
  ip link add link eth0 name eth0.20 type vlan id 20
  ip link add link eth0 name eth0.30 type vlan id 30
  ip link set eth0.10 up
  ip link set eth0.20 up
  ip link set eth0.30 up
  ```  
  Each sub‑interface belongs to its VLAN and can have its own IP address. Traffic sent from the server to, say, VLAN 10 will be tagged with the 802.1Q header containing VLAN ID 10 before leaving the NIC.

**Linux**

**L1** – *Hard link vs. symbolic link*  
- **Hard link:** A directory entry that points directly to the same inode as the original file. Deleting a hard link does not free space; the file persists until all hard links are removed. Links can span filesystems (if same inode) but cannot point to directories.  
- **Symbolic link (symlink):** A special file containing a path string to the target file. It is a separate inode; deleting the symlink does not affect the target, but deleting the target breaks the link. Symlinks can point across filesystems and to directories.

**L2** – *Find files >100 MB under /var/log*  
```bash
find /var/log -type f -size +100M -print
```
(Use `-size +100M` for “greater than 100 MiB”. Add `-maxdepth 1` if you only want immediate children.)

**L3** – *Process state D (uninterruptible sleep)*  
- **Meaning:** The process is blocked waiting for a hardware or kernel operation that cannot be interrupted (e.g., I/O on a disk, network device, or a lock). The state is “D” because the wait is uninterruptible by normal signals.  
- **Can you kill it with `kill -9`?** `SIGKILL` (`-9`) can be sent, but the kernel will not actually terminate the process until the underlying I/O completes; the process remains in D until the operation finishes, after which it will exit or respond to the signal.

**L4** – *cgroups v1 vs. v2*  
- **cgroups v1:** Uses a hierarchical “controller” model; each controller (cpu, memory, etc.) has its own subsystem directory. Complex mounting, multiple “cgroup" hierarchies possible.  
- **cgroup v2:** Unified hierarchy – a single “cgroup2” mount with unified interface; simpler, consistent interface, better integration with systemd.  
- **systemd preference:** Systemd uses **cgroup v2** because it provides a single, predictable view of resource limits, easier delegation, and better support for features like `MemoryPressure` and `CPUPressure`.

**L5** – *nftables vs. iptables*  
- **iptables:** Legacy userspace utility that manipulates legacy “iptables” chain tables (filter, nat, mangle). Operates on netfilter hooks.  
- **nftables:** Modern, unified framework that replaces iptables/arp tables. Uses a simpler syntax and can replace iptables, ip6tables, arptables, ebtables in a single tool.  
- **Kernel handling:** The kernel’s netfilter subsystem implements both; nftables can be configured to emulate iptables behavior, and iptables can be run as a compatibility layer that translates its rules to nftables internally (via `iptables-legacy` vs `iptables-nft`). Both ultimately program the same kernel hooks.

**L6** – *Filesystem 100 % but `du` shows little usage*  
Most likely cause: **inode exhaustion**. The filesystem can fill its inode table (metadata) while actual file data occupies little space (e.g., many small files, sparse files, or a large number of deleted files whose inodes remain). `df` reports usage based on blocks; `du` reports used data blocks. Check `df -i` and `ls -la` to see inode saturation.

**L7** – *Linux boot process (UEFI → systemd)*  
1. **UEFI firmware** loads the **bootloader** (e.g., GRUB) from EFI system partition.  
2. **Bootloader** reads kernel image and optional initramfs (ramdisk) and passes boot parameters.  
3. **Kernel** initializes hardware, mounts the initramfs at `/rom` (or `/initramfs`), and begins early drivers.  
4. **initramfs** (usually cpio archive) contains scripts (`/scripts/*`) and essential tools to prepare the system: detect hardware, mount root filesystem (often via NFS, LVM, or crypto), run `pivot_root`.  
5. **Root filesystem** is now accessible; the kernel execs `/sbin/init` (or the `init` specified by the bootloader).  
6. **systemd** takes over, becoming PID 1, parsing unit files, starting services, and managing the system.

**L8** – *Why `available` can be low with high buff/cache & OOM killer*  
- `free -h` reports **available** as `free + buffers/cache` (the amount of memory that can be reclaimed without swapping). However, the kernel may **not reclaim** all of that memory immediately because some buffers/cache are **reclaimable** but still held by processes (e.g., page cache for dirty pages).  
- If a process allocates memory faster than the reclaim rate, the ** watermark** thresholds (`low`, `high`) are crossed, triggering the OOM killer even though `available` appears large.  
- **Kernel tunables affecting this:**  
  - `vm.overcommit_memory` (0 = heuristic, 1 = always overcommit, 2 = never)  
  - `vm.swappiness` (controls tendency to swap)  
  - `vm.vfs_cache_pressure` (how aggressively the kernel reclaims inode & dentry cache)  
  - `vm.min_free_kbytes` (minimum free memory to avoid OOM)  

**L9** – *`ip netns` and container runtimes*  
- `ip netns` creates and manages **network namespaces**, providing isolated L3‑L4 stacks (different IP addresses, interfaces, routing tables).  
- **Container runtimes** (Docker, containerd, Podman) use network namespaces to give each container its own virtual network interface (`eth0`), enabling isolation, custom IP schemes, and network policies. The host may also expose ports via `iptables` NAT or `nftables` bridging.

**L10** – *SIGTERM, SIGKILL, SIGQUIT*  
- **SIGTERM:** Termination signal; process can catch it, perform cleanup, and exit gracefully. Default action is termination.  
- **SIGKILL:** Forceful kill; cannot be caught or ignored; process is immediately terminated.  
- **SIGQUIT:** Usually generated by `Ctrl+\`; causes core dump and termination. Can be caught (if handler installed) but default action is core dump + termination.  

**L11** – *stdout, stderr, stdin & redirect*  
- **stdin (0):** Standard input.  
- **stdout (1):** Standard output.  
- **stderr (2):** Standard error.  

Redirect `stderr` while keeping `stdout` on terminal:  
```bash
command >stdout.log 2>stderr.log   # both redirected
command 2>&1                         # merge both to stdout
command 2>/dev/null                  # discard stderr
# To keep stdout on terminal but send stderr to file:
{ command; } 2>stderr.log
```
Or using a shell builtin: `command 2>stderr.log`.

**L12** – *`chmod 755` meaning*  
- **755** in octal = **rwxr-xr-x**:  
  - **Owner:** `rwx` (read, write, execute)  
  - **Group:** `r-x` (read, execute)  
  - **Others:** `r-x` (read, execute)  
- Allows owner to modify, everyone can read and traverse (execute) the file/directory.

**L13** – *Root user vs. sudo user*  
- **Root:** Full privileged account; can do anything without restriction, logged in directly.  
- **Sudo user:** Regular user who can execute commands with root‑level privileges for specific commands (or all) after authenticating. Provides audit trail and limits exposure compared to a permanent root login.

**L14** – *Package manager*  
- **Debian/Ubuntu:** `apt` (Advanced Package Tool) – `apt-get`, `apt`.  
- **RHEL/Fedora:** `dnf` (Dandified Yum) – successor to `yum`.  

**L15** – *`/etc/fstab` purpose*  
- Contains static filesystem mount information. Used by `mount -a` (system boot) and `df`.  
- **Misconfiguration consequences:** System may fail to mount required filesystems at boot, leading to rescue mode or inability to start services that depend on those mounts.

**L16** – *LVM overview & extending a logical volume*  
- **Physical Volume (PV):** Raw disk partition or LVM physical volume (`pvcreate`).  
- **Volume Group (VG):** Pool of PVs (`vgcreate`). Holds free space.  
- **Logical Volume (LV):** Virtual block device within a VG (`lvcreate`). Mounted like a regular filesystem.  

**Extending a LV on a running system:**  
```bash
# Add free space to VG (e.g., new PV)
pvcreate /dev/sdb1
vgextend myvg /dev/sdb1

# Increase LV size
lvextend -L +2G /dev/myvg/data
# Resize filesystem
resize2fs /dev/myvg/data
mount -o remount /mnt/data
```
(Use `lvextend -l +100%FREE /dev/vg/name` for percentage growth.)

**L17** – *Linux I/O scheduler basics*  
- **I/O scheduler:** Decides the order and grouping of I/O requests for block devices, aiming to balance latency, throughput, and fairness.  
- **mq‑deadline:** Deadline‑oriented; guarantees per‑request service time and read/write latency; good for latency‑sensitive workloads (databases).  
- **BFQ (Budget Fair Queueing):** Fair‑share allocator; gives each process a “budget” of I/O; excels for interactive workloads and many concurrent tasks.  
- **none:** No scheduling; requests go straight to the hardware queue; useful for SSDs where hardware queue already handles ordering.  

**Choosing a scheduler:**  
- **mq‑deadline** for low‑latency storage (NVMe, databases).  
- **BFQ** for general‑purpose servers with many mixed workloads.  
- **none** for SSDs with low queue depth or when you want the device’s own scheduler.  

**Changing at runtime:**  
```bash
# Identify block device, e.g., /dev/sda
echo mq-deadline > /sys/block/sda/queue/scheduler
# Verify
cat /sys/block/sda/queue/scheduler
```
(Use `systemctl restart systemd-block-device` if needed.)

**L18** – *Load average, I/O wait, diagnosing bottlenecks*  
- **Load average** reflects the number of processes (or threads) that are ready or running. It does **not** directly measure CPU utilization; high load can be due to I/O‑bound processes waiting for disk/network.  
- **I/O wait** appears in `top`/`htop` as `iow` or in `vmstat`/`sar` as `wa`. When `wa` is high, load rises even if CPU usage is low.  
- **Diagnosis tools:**  
  - `top`/`htop` – see CPU, iow, load.  
  - `iostat` – disk throughput, wait times.  
  - `sar -n DEV` – network interface utilization.  
  - `vmstat 1 5` – see `wa`, `id` (idle).  
  - `pidstat` – per‑process CPU/I/O.  
  - `ss -s` or `netstat` – socket states for network stalls.  

If `wa` dominates, suspect storage (disk, filesystem, LVM). If network `ifstat` shows low utilization but load high, suspect CPU throttling or context switches.

**L19** – *SELinux enforcement*  
- **Enforcing:** SELinux policies are applied strictly; violations are denied and logged (audit).  
- **Permissive:** Policies are not enforced; violations are logged but allowed, useful for debugging.  
- **Disabled:** SELinux is off; no MAC enforcement.  

**Troubleshooting a daemon that cannot bind a non‑standard port:**  
1. Check `audit.log` (`auditctl -e 1` if needed) for `AVC` denials.  
2. Use `semanage port -l` to see allowed ports; add with `semanage port -a -t http_port_t -p tcp 1234`.  
3. Verify `getenforce` and temporarily set to `Permissive` (`setenforce 0`) to confirm the port works.  
4. If needed, adjust the daemon’s context: `chcon -t http_port_t /path/to/binary` or define a new SELinux type.

**L20** – *Linux virtual memory, page faults, THP*  
- **Page fault:** When a process accesses a virtual address not currently mapped to physical memory.  
  - **Minor page fault:** Page is already in physical memory (e.g., file cache) but not mapped; cheap, just updates page tables.  
  - **Major page fault:** Page is not in memory; must be loaded from disk (swap or backing file); expensive.  
- **Transparent Huge Pages (THP):** Automatically groups 2 MB (or larger) pages to reduce TLB misses and overhead of small‑page allocations. Improves performance for workloads with large sequential memory accesses (e.g., databases, scientific apps).  
- **When to disable THP:**  
  - Real‑time or latency‑critical applications where THP’s unpredictable page‑size changes can cause latency spikes.  
  - Workloads with many small allocations where THP may cause internal fragmentation.  
  Disable via kernel boot parameter `transparent_hugepage=never` or runtime: `echo never > /sys/kernel/mm/transparent_hugepage/enabled`.<|END_TEXT|>
