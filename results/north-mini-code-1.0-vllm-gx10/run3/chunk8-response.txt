**CL3 – VPC, Subnet, Security Group, NACL**  
- **VPC** – Isolated logical network space (your own private address space). Acts as the top‑level container.  
- **Subnet** – Division of a VPC into smaller IP ranges; used to place resources for routing and scaling (e.g., public vs private subnets).  
- **Security Group** – **Stateful** firewall attached to individual instances (VM/Pod). Allows inbound rule to open outbound automatically; enforced at the instance level.  
- **Network ACL (NACL)** – **Stateless** subnet‑level firewall; rules evaluated in order, must allow both inbound and outbound.  

**Layering:** VPC → Subnets (IP allocation) → NACLs (subnet‑wide stateless filtering) → Security Groups (instance/pod‑level stateful filtering).  

**Stateful vs Stateless:**  
- *Stateful* (SG) tracks TCP/UDP sessions; a return packet is allowed without a rule.  
- *Stateless* (NACL) treats each packet independently; you must allow both directions explicitly.

**CL7 – Disaster‑Recovery (DR) Design for a Cloud‑Native App (Two Regions)**  

- **RPO / RTO** – Define acceptable data loss (RPO) and downtime (RTO). Example: RPO ≤ 5 min, RTO ≤ 30 min → active‑active with synchronous replication for critical data, async for less‑critical.  
- **Active‑Active vs Active‑Passive** –  
  *Active‑Active*: Both regions serve traffic; DNS round‑robin or geo‑RTD; requires state synchronization (e.g., distributed databases with multi‑master).  
  *Active‑Passive*: Primary region handles traffic; secondary stands by; fail‑over is a cut‑over; lower cost, higher RTO.  
- **Database Replication** –  
  *Sync*: Guarantees zero loss but adds latency; used for transactional DBs (e.g., PostgreSQL with logical replication).  
  *Async*: Higher performance, tolerates network partitions; used for analytics or caching layers.  
- **DNS Failover** – Use AWS Route 53 Health Checks or Azure Traffic Manager; health‑check monitors primary region; switch to secondary when unhealthy.  
- **State Management** – Deploy a distributed state store (e.g., Redis Cluster, DynamoDB Global Tables) that can operate across regions; consider eventual‑consistency patterns for non‑critical state.  
- **Cost Implications** – Active‑active doubles compute and network costs; need to rightsize, use spot instances where permissible, and apply storage tiering.  

**DR Patterns**  
- **Pilot Light**: Minimal copy of production (few VMs/containers) that can be spun up quickly; used for testing fail‑over procedures; low cost.  
- **Warm Standby**: Core services running in secondary region with periodic data replication (e.g., every 5‑15 min). Faster recovery than pilot light, higher cost.  
- **Multi‑Site Active‑Active**: Both regions run full production; users are routed based on latency or geographic proximity; highest availability but highest cost and complexity.

**CL8 – GitOps Model**

**CL9 – Migrating a Stateful Legacy App to Kubernetes**  

1. **StatefulSet** – Manages ordered pod deployment, stable network identifiers (`pod-0`, `pod-1`).  
2. **PV/PVC with Local Storage Class** – Use `awsElasticBlockStore`/`azureDisk` or a custom `local` storage class for low‑latency block storage attached to each node.

**CL12 – Zero‑Trust Network Architecture for a Kubernetes Cluster**  

1. **Network Policies** – Deny‑all by default; allow only required pod‑to‑pod traffic using labels/selectors.  
2. **Service Mesh (e.g., Istio, Linkerd)** – Enforces mTLS between services, provides traffic management, observability, and fine‑grained routing.  
3. **Pod Identity** – Use IRSA/Workload Identity; pods assume least‑privilege IAM roles; avoid embedding credentials.  
4. **Admission Controllers** – OPA Gatekeeper or Kyverno enforce policies at creation time (resource quotas, image policies, network policies).  
5. **Image Signing & Verification** – Cosign, Notary, or Sigstore; enforce that only signed images run (policy‑enforced via admission controllers).  
6. **Runtime Security** – Falco monitors container activity; alerts on anomalous syscalls, file access, network connections.  
7. **Secrets Management** – External Secrets Operator or Vault CSI driver; secrets never stored in etcd or images.  

**Difference from Traditional Perimeter Security:**  
- Traditional model trusts everything inside the network boundary; zero‑trust trusts **nothing** and verifies every request.  
- Controls are applied at workload/pod level, not just at firewall edges.  
- Identity is the primary security factor (pod service accounts, IAM roles) rather than IP address.

**CL13 – CDN (Content Delivery Network)**  

- **Definition:** Distributed edge cache that stores copies of static content (HTML, CSS, JS, images, video) close to end users.  
- **How it works:** Request is routed to the nearest edge node; if cache hit, content is served locally; otherwise edge fetches from origin, caches, and returns. DNS (or anycast) directs users to the optimal edge.  
- **Cloud‑native CDN services:**  
  * AWS CloudFront  
  * Azure Front Door / CDN (Microsoft)  
  * Google Cloud CDN (via Cloud Load Balancing)  
- **When to use a CDN vs origin:** Use a CDN for static assets, large media files, global user base, or to reduce latency and offload origin bandwidth. Serve directly from origin for dynamic, personalized content or when you need real‑time data.

**CL14 – Regions, Availability Zones, Zonal vs Regional Resources**  

- **Region:** Geographically isolated data center cluster (e.g., us‑east‑1). Independent power, networking, governance.  
- **Availability Zone (AZ):** Within a region, isolated power/network sub‑domain (AZ‑a, AZ‑b, …). Designed for high fault tolerance.  
- **Why deploy across AZs:** Provides resilience against AZ‑level failures (hardware, outage). Improves availability and reduces impact of a single point of failure.  
- **Zonal resources:** Tied to a single AZ (e.g., EC2 instance, EBS volume). If that AZ fails, the resource is unavailable.  
- **Regional resources:** Replicated across AZs (e.g., S3, DynamoDB global tables). Survive AZ failures; higher availability.

**CL16 – Cloud Identity Services & Least Privilege**  

- **IAM Users:** Human accounts with credentials (password, MFA).  
- **Groups:** Collections of users for policy assignment.  
- **Roles:** Permissions assigned to entities (users, groups, or services) often with assumed‑role semantics (e.g., STS).  
- **Policies:** JSON documents that define allowed/denied actions and resources.  

**Principle of Least Privilege:** Grant only the permissions needed to perform a specific job. Apply by:  
- Using role‑based access (RBAC) with narrowly scoped policies.  
- Leveraging service‑specific roles (e.g., `AmazonS3ReadOnlyAccess`).  
- Regularly reviewing and pruning permissions (IAM Access Analyzer).  
- Enforcing MFA for privileged users and using temporary credentials (assume‑role) for automated workloads.

**CL17 – Serverless Computing**  

- **Definition:** Execute code on‑demand in response to events; no server management.  
- **Providers:**  
  * **AWS Lambda** – runs on AWS infrastructure, integrated with many AWS services.  
  * **Azure Functions** – uses triggers (HTTP, timers, storage queues) and runs on Azure App Service Plan or Consumption Plan.  
  * **Google Cloud Functions (2nd gen)** – runs on Cloud Run (Kubernetes‑based) with VPC access.  
- **Cold Starts:** Time between trigger and first execution of a new instance; matters for latency‑sensitive workloads and for languages/runtimes with heavy initialization (Java, Go).  
- **When serverless is a poor fit:**  
  * Long‑running processes (minutes to hours).  
  * Workloads requiring persistent connections or stateful computation.  
  * High‑throughput, latency‑critical workloads where cold‑start latency dominates.  
  * Complex runtime dependencies that increase package size beyond 50 MB/250 MB limits.

**CL18 – Kubernetes Ingress Options**  

| Option | Description | TLS termination | When to prefer |
|--------|-------------|----------------|----------------|
| **Ingress (resource)** | Standard Kubernetes Ingress API; uses Ingress Controller (NGINX, HAProxy) to route HTTP/HTTPS. | TLS terminated at the Ingress Controller (certificate stored there). | Simple HTTP/HTTPS routing, existing deployments. |

**Gateway API vs Ingress:** Choose Gateway API for richer routing, multiple listener support, and clearer separation of concerns; Ingress is fine for basic HTTP/HTTPS routing.

**CL19 – Cost‑Optimization Strategy for $80k/month Spend**  

1. **Reserved Instances vs Savings Plans vs Spot/Preemptible**  
   * **Reserved Instances** – 1‑3 yr term, up to ~60 % discount for predictable workloads.

   * **Spot / Preemptible** – Up to ~90 % discount; suitable for fault‑tolerant, batch, or stateless jobs; use Auto Scaling with interruption handling.  

2. **Right‑sizing** – Use CloudHealth, AWS Compute Optimizer, Azure Advisor to down‑size over‑provisioned VMs, containers, or databases.  

3. **Storage Tiering** –  
   * Hot data → Standard SSD.  
   * Warm data → Standard HDD or S3 Intelligent‑Tiering.  
   * Cold/Archive → Glacier or Deep Archive; lifecycle policies automate transition.  

4. **Idle Resource Detection** – Deploy tools like **CloudIdle**, **Azure Monitor for VMs**, or **Kubernetes cost metrics** to identify unused instances, stop/start schedules, or scale to zero.  

5. **FinOps Practices** –  
   * Tagging policies (environment, owner, costcenter).  
   * Budget alerts & SLA‑based spending limits.  
   * Regular cost reviews, chargeback models for business units.  

6. **Showback/Chargeback** – Use **Cost Explorer**, **Azure Cost Management**, or third‑party tools (Cloudability, CloudHealth) to allocate costs to teams via tags or custom dimensions.  

**Tools & Processes for Visibility**  
- **Centralized Cost Management Dashboard** (AWS Cost Explorer, Azure Cost Management + Billing).  
- **Automated Reporting** (AWS Budgets, Azure Consumption API, scheduled CSV/JSON exports).  
- **FinOps Platform** (Snowflake + custom queries, or CloudHealth, Cloudability).  
- **Policy Enforcement** (Service Catalog, Terraform Cloud with cost‑estimation).  
- **Governance** – Require cost‑center tags on resource creation; integrate with CI/CD (e.g., checkov, Terraform Cloud’s cost estimation).

**CL20 – Multi‑Cloud Strategy (AWS + Azure) to Avoid Vendor Lock‑In**  

1. **Abstraction Layers** – Use container images + Kubernetes manifests; abstract infra as code via **Terraform** (or OpenTofu) with provider blocks for each cloud.  

2. **Kubernetes as Common Runtime** – Deploy **EKS**, **AKS**, or **GKE** in each cloud; use **Kubernetes Federation** or **Anthos/GKE Multi‑Cloud** for cross‑cloud service mesh.  

3. **IaC Portability** – Terraform modules define networking, storage, IAM; reuse across clouds; avoid native‑only services.  

4. **Cross‑Cloud Networking** –  
   * **AWS‑Azure VPN/ExpressRoute** via third‑party providers or Direct Connect/ExpressRoute Direct.  
   * **Transit Gateway / Azure VNET Peering** for hub‑spoke connectivity.  

5. **Identity Federation** – Use **Azure AD** + **AWS IAM Identity Center** or **Okta** to provide single sign‑on; map corporate identities to cloud roles.  

6. **Trade‑offs** –  
   * **Benefits:** Reduced lock‑in, ability to choose best‑of‑breed services, disaster recovery across clouds, cost arbitrage.  
   * **Complexity:** Increased operational overhead, duplicated tooling, cross‑cloud compliance, networking complexity, skill gaps.  

**When multi‑cloud is justified:**  
- Regulatory requirements (data residency) forcing presence in specific clouds.  
- Need for distinct services not available in a single provider (e.g., AWS Lambda + Azure SQL).  
- Business continuity across clouds for DR.  

**When it’s unnecessary complexity:**  
- All workloads fit within a single provider’s service catalog.  
- Team lacks expertise to manage multiple platforms.  
- Cost of duplicated infrastructure outweighs benefits.

**OT2 – IT vs OT Networks**  
- **IT:** Focus on data, confidentiality, integrity, availability; uses TCP/IP, Windows/Linux, frequent patching, dynamic addressing.  
- **OT:** Focus on real‑time control, safety, reliability; uses deterministic protocols (Modbus, EtherNet/IP), specialized hardware (PLC, RTU), minimal patching (updates can affect control stability).  

**Why standard IT patching isn’t suitable:**  
- Patching can introduce downtime or cause device malfunction.  
- OT devices often have long lifecycles and limited vendor support.  
- Changes may affect safety‑instrumented functions; need rigorous change‑management and validation.

**OT3 – DMZ (Industrial DMZ) Role**  
- **Purpose:** Isolate IT from OT while allowing controlled data exchange (e.g., historian, MES).  
- **Allowed traffic:**  
  * **Inbound to OT:** Limited, authenticated connections from DMZ (e.g., remote monitoring, firmware updates).  
  * **Outbound from OT:** Process data pushed to DMZ (e.g., OPC UA, MQTT) for analytics.  
- **Direction:** Typically **unidirectional** from OT → DMZ (data export) with optional bidirectional for maintenance.  
- **Why direct Level 4 ↔ Level 1 is dangerous:** Direct connectivity bypasses segmentation, exposing control devices to malware, unauthorized access, and potential disruption of safety functions.

**OT4 – OT Protocols & Typical Purdue Levels**  

| Protocol | Typical Purdue Level |
|----------|----------------------|
| **Modbus TCP** | Level 3 (Control) – PLCs to SCADA/HMI. |
| **OPC UA** | Level 2‑3 – Used for data collection between control devices and SCADA/MES. |
| **EtherNet/IP (CIP)** | Level 3 – Allen‑Bradley PLCs, motion controllers. |
| **PROFINET** | Level 3 – Siemens industrial Ethernet, PLCs. |
| **MQTT** | Level 2‑3 – Publish/subscribe messaging for telemetry (often via edge gateway). |

**OT5 – Data Diode vs Firewall**  
- **Data Diode:** One‑way hardware device; allows only outbound (or inbound) flow; cannot be bypassed; provides physical isolation.  
- **Firewall:** Software/appliance that filters based on rules; can be configured bi‑directionally; susceptible to mis‑configuration or compromise.  

**When to use hardware data diode:**  
- When you need absolute guarantee of unidirectional data flow (e.g., sending process data to a secure external archive while preventing any external command injection).  

**Limitation:** Cannot enforce complex policies, inspect payload content, or adapt to dynamic requirements; must be paired with other security measures for full protection.

**OT6 – SCADA → Cloud Analytics Data Flow**  

1. **SCADA system** (Level 1/2) collects process data.  
2. **Historian** (Level 3) stores raw/time‑series data locally.  
3. **OPC UA Server** (on edge) publishes data via OPC UA.  
4. **MQTT Broker** (edge) receives OPC UA data, re‑publishes as MQTT topics.  
5. **Edge Gateway** (OT‑IT boundary) ingests MQTT, applies transformation, and forwards to cloud.  
6. **Cloud Ingestion** (e.g., AWS IoT Core, Azure IoT Hub) receives data, stores in data lake, feeds analytics.  

**Security boundaries:**  
- **OT network** (Levels 0‑3) is isolated from IT.  
- **Edge gateway** sits in the **Industrial DMZ**; only allowed outbound to cloud via encrypted tunnels (VPN/IPsec, TLS).  
- **Cloud** is the final trust zone; data is encrypted in transit and at rest.

**OT7 – IEC 62443 Security Zones & Conduits**  

- **Zone:** Logical grouping of assets with similar security requirements (e.g., “Corporate Network”, “Engineering Workstation Zone”, “SCADA Server Zone”, “PLC Zone”, “SIS Zone”).  
- **Conduit:** Controlled pathway (firewalls, routers, VLANs) that permits only authorized, monitored traffic between zones.  

**Proposed zone‑and‑conduit model:**  

| Zone | Assets | Security Level | Conduits |
|------|--------|----------------|----------|
| **Zone 1 – Corporate** | ERP, office workstations, DNS/DHCP | Low | Conduit to Zone 2 (firewall with strict inbound allow). |
| **Zone 2 – Engineering** | Engineer workstations, CAD servers | Medium | Conduit to Zone 3 (bidirectional, limited to engineering tools). |
| **Zone 3 – SCADA** | SCADA server, HMI, historian | High | Conduit to Zone 4 (read‑only, OPC UA) and Zone 5 (SIS) (no write). |
| **Zone 4 – PLCs** | PLCs, RTUs, field devices | Very High | Conduit to Zone 5 (SIS) (unidirectional, only safety data). |
| **Zone 5 – SIS** | Safety Instrumented System controllers | Critical | Isolated; only inbound from Zone 4 (unidirectional), no external connectivity. |

**OT8 – Network Segmentation for 200 PLCs, 30 HMIs, SCADA, Historian**  

1. **VLAN Design**  
   * **VLAN 10 – PLCs** (tagged, isolated, VLAN‑based ACLs).  
   * **VLAN 20 – HMIs** (connected to PLC VLAN, with limited access).  
   * **VLAN 30 – SCADA Server** (trusted, allowed to communicate with PLC & HMI VLANs).  
   * **VLAN 40 – Historian** (read‑only access to SCADA, write from SCADA).  
   * **VLAN 50 – Management** (admin workstations, separate from production).  

2. **Firewall Placement**  
   * **Core firewall** between Management VLAN and Production VLANs.  
   * **Layer‑2 switches** with VLAN tagging; **access‑control lists** on switch ports (restrict to VLAN).  
   * **Industrial firewalls** (e.g., Cisco Industrial Security Appliance) placed between PLC and HMI zones for fine‑grained protocol filtering.  

3. **Switch Architecture**  
   * **Catalyst/Industrial Ethernet switches** with **port isolation**, **VLAN trunking**, **PoE** for HMIs/PLC I/O.  
   * Enable **Spanning Tree Protocol** for redundancy; consider **MSTP** for rapid convergence.  

4. **Remote Vendor Access**  
   * Use **jump hosts** in Management VLAN; require **MFA** and **Bastion host** with audit logging.  
   * Vendor VPN tunnels terminate at the jump host; only necessary ports/protocols allowed.  

5. **Transition Without Production Stop**  
   * Perform **phased VLAN implementation**: start with a copy of production traffic (port mirroring) to validate segmentation.  
   * Use **virtualization** (e.g., logical switches) to test policies before applying to physical infrastructure.  
   * Schedule **maintenance windows** for critical lines; keep a **fallback** to original flat network until validation complete.  

**OT9 – SIS vs BPCS, IEC 61511, Isolation, Ransomware Impact**  

- **Safety Instrumented System (SIS):** Dedicated safety control system that takes independent actions to bring a process to a safe state when hazardous conditions are detected.  
- **Basic Process Control System (BPCS):** Core control system managing normal production (temperature, pressure, flow).  

**IEC 61511** – Standard for functional safety of SIS; defines requirements for SIS design, verification, validation, and lifecycle.  

**Why SIS must be air‑gapped/isolated:**  
- Prevents safety controllers from being compromised by malware targeting BPCS or IT.  
- Ensures deterministic behavior; any interference could jeopardize personnel, environment, or equipment.  

**If ransomware reaches SIS:**  
- Attackers could block safety trips, manipulate setpoints, or lock operators out → catastrophic process upset, potential loss of life, environmental damage.  
- Recovery requires safe‑state verification, re‑commissioning of safety loops, and often a plant shutdown for extensive forensic analysis.

**OT10 – PLC, DCS, SCADA Differences**  

| System | Primary Function | Typical Scale | Example Use |
|--------|------------------|---------------|-------------|
| **PLC** | Low‑level, real‑time control of discrete/continuous signals; deterministic I/O. | Single machine/cell. | Motor control, batch valve sequencing. |
| **DCS** | Integrated control of multiple processes across a plant; hierarchical alarm management, historical trending. | Large plant (multiple units). | Chemical plant process control, temperature/pressure loops. |
| **SCADA** | Supervisory data acquisition & visualization; aggregates data from PLCs/DCS, provides HMI, alarms, logging. | Enterprise‑wide monitoring. | Water treatment plant monitoring, remote site oversight.  

**Can they coexist?** Yes; PLCs feed data to DCS, which is monitored by SCADA; they form a layered architecture.

**OT11 – Remote Access Architecture**  

1. **Jump Hosts / Bastion Hosts** – Placed in Management VLAN; only reachable via VPN/MFA.  
2. **MFA** – Require second factor for any privileged access.  
3. **Session Recording** – Tools like **CyberArk**, **BeyondTrust**, or **Splunk** record all sessions for audit.  
4. **Vendor Access** – Limited‑privilege accounts, time‑boxed sessions, monitored.  
5. **Time‑Limited Access** – Use **Just-In-Time (JIT)** IAM or **AWS STS**‑based temporary credentials.  

**Why RDP directly to an HMI is unacceptable:**  
- Exposes control interfaces directly to the internet, bypassing segmentation.  
- Increases attack surface; any compromise can directly affect PLCs.  
- Lacks audit trail and MFA, violating OT security policies.

**OT12 – Detection & Response for Water Treatment Facility (Level 3 Compromise)**  

1. **Network Monitoring**  
   * Deploy **IDS/IPS** (Snort, Suricata) on the industrial DMZ.  
   * Use **anomaly detection** (NetFlow, Zeek) to spot unusual traffic patterns.  

2. **Asset Inventory**  
   * Maintain a **CMDB** of all PLCs, HMIs, SCADA servers, vendor devices.  
   * Tag each device with firmware version, vendor, and support contact.  

3. **Incident Response Steps**  
   * **Contain**: Isolate compromised segment (disconnect from network, place in quarantine VLAN).  
   * **Eradicate**: Remove malicious artifacts, reset credentials, apply patches.  
   * **Recover**: Restore from clean backups, verify safety interlocks.  
   * **Post‑Incident**: Conduct lessons‑learned, update detection rules.  

4. **Coordination with Control Room**  
   * Keep **operations staff** informed of containment actions; they may need to switch to **manual safe‑state procedures**.  
   * Ensure **safety interlocks** remain functional; verify SIS status.  

5. **Ensuring Safe Operations**  
   * Use **redundant** control paths; keep a **stand‑by** HMI for critical functions.  
   * Perform **safe‑shutdown** procedures if necessary, following IEC 61511.  

**Role of Plant Operator during a cyber incident:**  
- Monitor system status, confirm safe‑state actions, execute manual overrides if automated controls are unavailable.  
- Document observations, report anomalies to security team, and follow established **operator emergency procedures**.  

**OT13 – HMI Definition & Role**  
- **HMI (Human‑Machine Interface):** Client application that visualizes process data, allows operators to interact with control systems (alarms, setpoints, trends).  
- **Difference from Engineering Workstation:** Engineering workstation is used for configuration, programming, and maintenance of PLC/DCS; HMI is for **operational** interaction, not for system changes.  

**OT14 – Historian in OT Context**  
- **Purpose:** Stores time‑stamped process variables for trend analysis, compliance, and performance optimization.  
- **Plant Historian (Level 3):** Located on‑premises, tightly coupled with SCADA, stores raw/high‑frequency data.  
- **Enterprise Historian (Level 4):** Centralized data warehouse (e.g., OSIsoft PI, Wonderware) that aggregates, normalizes, and correlates data from multiple sites for business analytics.  

**OT15 – Ladder Logic**  
- **Definition:** Graphical programming language resembling electrical relay logic; used to program PLCs.  
- **Device:** Executed by the PLC’s CPU; scan cycle reads inputs, executes ladder rungs, updates outputs.  
- **Why still dominant:**  
  * Mature, well‑understood by automation engineers.  
  * Deterministic execution, robust in harsh environments.  
  * Extensive tooling, long vendor support, and low learning curve for field technicians.  

**OT16 – RTU vs PLC**  
- **RTU (Remote Terminal Unit):** Typically embedded, limited processing, focuses on telemetry and simple control; often used in remote/field locations with limited power/communication.  
- **PLC:** More powerful, modular, designed for complex control logic, deterministic I/O, and local processing.  

**When to deploy RTUs:**  
* Remote telemetry for SCADA in dispersed assets (e.g., water wells, remote pumps).  
* Environments where power and space are constrained, and control logic is simple.  

**OT17 – Analog vs Digital Signals**  
- **Analog signals:** Continuous voltage/current (e.g., 4‑20 mA, 0‑10 V) representing measured values.  
- **Digital signals:** Discrete on/off (0/1) used for discrete I/O.  

**Why 4‑20 mA preferred over 0‑20 mA:**  
* 4 mA “live zero” allows detection of a broken wire (0 mA indicates fault).  
* Improves noise immunity and enables loop power supply for sensors.  

**OT18 – OT Asset Inventory**  
- **Concept:** Comprehensive list of all hardware, software, firmware, and configurations in the OT environment.  
- **Foundation:** Enables risk assessment, patch management, compliance, and rapid incident response.  

**Discovery Tools/Techniques:**  
* **Passive network monitoring** (NetFlow, packet captures) to see devices and protocols.  
* **Active scanning** (e.g., Nmap, SNMP polling) – but can be intrusive; may affect real‑time control loops.  

**Why active scanning is dangerous:**  
* Can generate traffic that interferes with control loops.  
* May cause PLCs to reboot or change state, leading to production impact.  

**OT19 – MITRE ATT&CK for ICS**  

| Tactics | Example Technique |
|--------|-------------------|
| **Initial Access** | **T1195 – Supply Chain Compromise** (compromised firmware). |
| **Execution** | **T1199 – Component Injection** (malicious DLL loaded by HMI). |
| **Persistence** | **T1543 – Server Software Component: Native Image** (rootkit in PLC firmware). |
| **Privilege Escalation** | **T1068 – Exploitation for Privilege Escalation** (vulnerability in controller OS). |
| **Defense Evasion** | **T1070 – Indicator Removal on Host** (deleting logs from historian). |
| **Credential Access** | **T1555 – Credentials from Password Stores** (extract PLC admin passwords). |
| **Discovery** | **T1482 – System Time Discovery** (checking timestamps for forensic analysis). |
| **Impact** | **T1496 – Resource Manipulation** (flooding network causing denial of control). |

**Differences from Enterprise ATT&CK:**  
- Focus on **ICS‑specific protocols**, **safety‑instrumented functions**, and **physical process impact**.  
- Includes tactics like **“Manipulate Process”** and **“Cause Physical Damage.”**  

**Using the framework:**  
- Map existing controls to each technique; identify gaps (e.g., missing network segmentation for Modbus).  
- Prioritize mitigations based on likelihood and potential impact on safety.  

**OT20 – Converged IT/OT SOC Design**  

1. **Log Collection (OT‑friendly)**  
   * Deploy ** lightweight agents** (e.g., Sysdig, Fluent Bit) on edge gateways and historians; use **network taps** to capture switch traffic.  
   * Ensure collection does **not** compete for CPU/IO on PLCs; use **packet brokers** for passive capture.  

2. **SIEM Integration**  
   * Forward logs to a **SIEM** (Splunk, Elastic, Azure Sentinel) with OT‑specific parsers.  
   * Tag logs with **asset identifiers**, **process context**, and **severity levels**.  

3. **OT‑Specific Detection Rules**  
   * Monitor for **unauthorized firmware changes**, **unexpected protocol usage** (e.g., Modbus over HTTP), **access to PLC web interfaces**.  
   * Correlate **network anomalies** with **process variable spikes**.  

4. **Alert Triage Workflows**  
   * **Tier 1** – Automated enrichment (asset inventory, historical baselines).  
   * **Tier 2** – OT engineers validate alerts (check HMI, confirm safe‑state).  
   * **Tier 3** – IT analysts investigate network/endpoint evidence.  

5. **Staffing**  
   * **IT analysts** for network/endpoint logs, SIEM management.  
   * **OT engineers** for protocol knowledge, safety impact assessment.  

6. **False Positives**  
   * Use **baseline modeling** of normal process behavior.  
   * Implement **tuning** based on historical false‑positive rates.  

**Handling an alert of unauthorized firmware changes on a PLC:**  

1. **Immediate containment** – Isolate the PLC’s VLAN, block traffic to/from the device.  
2. **Evidence collection** – Capture firmware hash, change logs, and network flow.  
3. **Impact assessment** – Verify if safety functions are affected; consult SIS status.  
4. **Recovery** – Restore from known‑good backup, apply vendor‑approved firmware, verify functionality.  
5. **Post‑incident** – Update change‑management policies, enforce signed firmware images, and adjust detection rules.
