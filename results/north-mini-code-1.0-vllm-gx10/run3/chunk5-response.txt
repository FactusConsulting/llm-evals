*Class* (`class`) is a reference type: variables hold a reference (null possible), they are allocated on the **managed heap**, have default values (`null` for reference types, `0` for value types), and are subject to heap‑allocation, garbage collection, and can be `null`.  
*Struct* (`struct`) is a **value type**: variables hold the actual data, are allocated on the stack (or inline in a containing object), cannot be `null`, and are copied when assigned or passed.  

**When to use a struct** – When you have small, immutable, frequently‑created objects that logically represent a simple value (e.g., `Point`, `Color`, `Guid`). Use a struct to avoid the overhead of heap allocation and GC pressure. Avoid structs that are large, mutable, or intended to be boxed frequently.

**DN2** – **IEnumerable<T> vs IQueryable<T>**  
* `IEnumerable<T>` represents a **collection** that can be enumerated. Its queries are **evaluated locally** (in‑memory) and support `foreach`, `Where`, `Select`, etc., but cannot translate to SQL.  
* `IQueryable<T>` represents a **queryable source** (often an `IEnumerable` wrapped by an `IQueryProvider`). Its expression tree can be **translated** (e.g., to SQL) by the provider before execution, enabling server‑side filtering, ordering, paging, etc.  

**Why it matters** – Using `IQueryable` lets you push filtering, projection, and aggregation to the database, reducing data transfer and leveraging DB optimizations. Using `IEnumerable` forces all processing in‑memory, which can be inefficient for large result sets.

**DN3** – **Async/await, Task vs ValueTask**  
* `Task` – represents an asynchronous operation that may produce a result (`Task<T>`), may have multiple continuations, and is allocated on the heap. It’s the default return type for `async` methods.  
* `ValueTask` – a **value‑type** wrapper that can hold either a result or an underlying `Task`. It avoids allocating a `Task` when the operation completes synchronously (e.g., fast I/O).  

**When to use `ValueTask`** – In hot paths where many async calls complete quickly (e.g., `ValueTask<string> ReadAsync`, `ValueTask<int> GetHashCodeAsync`). Use `Task` for operations that are likely to be awaited asynchronously or when you need to chain multiple awaits.

**DN4** – **Dependency Injection (DI) in .NET**  
DI registers services so they can be **injected** rather than created manually. The container manages lifetimes:

| Lifetime | Scope | Typical Use |
|----------|-------|-------------|
| **Transient** | New instance each time requested | Services with no state (e.g., `ILogger<T>`) |
| **Scoped** | Same instance per **scope** (usually a request) | Request‑scoped services (e.g., `DbContext`, `HttpContext`) |
| **Singleton** | Single instance for the lifetime of the application | Global, immutable services (e.g., configuration) |

**Common bug** – Injecting a **Scoped** service into a **Singleton** (or vice‑versa) can cause unexpected behavior. If a Singleton holds a Scoped service (e.g., `DbContext`), the Scoped instance may be disposed or replaced when the request ends, leading to `ObjectDisposedException` or stale data. The fix is to request the Scoped service at the point of use (e.g., via constructor injection) or use a factory (`Func<IScoped>`) if a Singleton truly needs it.

**DN5** – **String vs ReadOnlySpan<char> vs Span<T>**  
* `string` – immutable, UTF‑16, reference type. Operations create new strings (e.g., `Substring`, `Replace`).  
* `ReadOnlySpan<char>` – a **read‑only view** over a `string` or `char[]`. It’s a **value type** that references the original data without copying, enabling zero‑allocation operations (`Contains`, `SequenceEqual`). It’s immutable.  
* `Span<T>` – mutable view over a `char[]`, `Memory<T>`, or native memory. Allows in‑place modifications and zero‑copy operations (`AsSpan`, `CopyTo`).  

**When to use `Span<T>`** – When you need to **mutate** a buffer, perform high‑performance parsing, or work with native memory (e.g., `MemoryMarshal.AsBytes`). Use `ReadOnlySpan` for read‑only operations (search, split) without copying. Prefer `string` for typical text handling and interop where immutability is required.

**DN6** – **Garbage Collector (GC) & IDisposable**  
* **Generations** – The GC organizes objects by lifetime estimate:  
  * **Gen 0** – short‑lived objects (most allocations). Collected frequently.  
  * **Gen 1** – medium‑lived objects promoted from Gen 0.  
  * **Gen 2** – long‑lived objects (e.g., static fields, large objects). Collected less often.  
* **Large Object Heap (LOH)** – Holds objects ≥ 85 KB. They are allocated on a separate heap and collected only in Gen 2, causing larger pauses.  
* **IDisposable** – Provides deterministic release of **unmanaged resources** (file handles, sockets, database connections). The GC cannot know when those resources are no longer needed, so `Dispose` must be called explicitly (or via `using`). It also allows the pattern of **finalizable + disposable** where the finalizer calls `Dispose` if the user forgot.

**DN7** – **ConfigureAwait(false)**  
`ConfigureAwait(false)` tells an async method **not to capture the current `SynchronizationContext`** (e.g., ASP.NET Core’s UI context) when resuming execution.  

* **Use it** – In library code that will be awaited by many callers, especially in long‑running background tasks, to avoid unnecessary context switches and potential deadlocks.  
* **Do NOT use it** – In UI or ASP.NET request‑handling code where you want the continuation to run in the captured context (e.g., to update UI controls or call ASP.NET Core’s request services).  

`SynchronizationContext` is used by frameworks like WPF, WinForms, and ASP.NET Core to marshal async continuations back to the thread that started the operation. `ConfigureAwait(false)` bypasses that marshaling.

**DN9** – **ObjectDisposedException on DbContext under high concurrency**  

*Likely cause*: **DbContext is registered as Scoped** (default in ASP.NET Core). Each HTTP request (or scope) gets its own instance. If a **Singleton** or **Transient** service holds a reference to the DbContext and the request ends, the DbContext may be disposed while other code still expects it to be alive (e.g., background tasks, async continuations).  

*Fix*: Ensure DbContext is **scoped** and never stored outside its scope. Use a **factory** (`IDbContextFactory<YourContext>`) if you need to create contexts outside a request (e.g., in background services). In controllers/services, request the DbContext via constructor injection; do not cache it in a static field.  

*EF Core interaction*: EF Core expects DbContext to be short‑lived. It manages its own connection pool internally, but the context itself is not thread‑safe. Scoped lifetime guarantees a fresh context per request, preventing cross‑request contamination and disposal issues.

**DN10** – **Record vs class vs record struct**  

* **Class** – reference type, mutable (unless sealed), no special equality semantics.  
* **Record** – reference type with **structural equality** (members compared), **positional syntax**, **with‑expression** for immutability, and automatically generated `ToString`, `Equals`, `GetHashCode`. Immutable by default (fields are `readonly`).  
* **Record struct** – value type (struct) with the same features as record (structural equality, positional syntax) but stored on the stack/heap as a value type. Useful when you need value‑type semantics (e.g., lightweight, comparable) and structural equality.  

**When to choose**:  
* Use **class** for large, hierarchical objects where reference semantics matter.  
* Use **record** for DTOs, data carriers, or immutable objects where equality is based on field values.  
* Use **record struct** for small, frequently‑created value objects (e.g., `Point`, `Money`) where you want value semantics and structural equality without heap allocation.

**DN11** – **ref, out, in parameter modifiers**  

| Modifier | Purpose | Example |
|----------|---------|---------|
| **`ref`** | Passes a parameter **by reference**; caller must provide a variable that already exists. The method can read **and** write the argument. | `void Swap(ref int a, ref int b) { (a,b) = (b,a); }` |
| **`out`** | Passes a parameter **by reference**; caller may not have a variable. The method **must assign** the parameter before returning. | `bool TryParse(string s, out int result) { … result = …; return true; }` |
| **`in`** | **Read‑only reference**; prevents the method from assigning to the parameter, useful for large structs to avoid copying. | `void Print(in StringBuilder sb) { … }` |

Use `ref` for bidirectional sharing, `out` for return‑by-reference where the caller doesn’t have a variable, `in` for large structs passed to avoid copy while guaranteeing immutability.

**DN12** – **Nullable reference types (NRT) vs nullable value types**  

* **Nullable reference type** (`string?` or `global::System.Nullable<T>` in C# 8+) indicates that a **reference** may be `null` at runtime. It’s a **compile‑time** annotation; the type itself is `string` but the nullability is tracked.  
* **Nullable value type** (`int?`) is a **value type** that can hold either a value of `int` or `null`. It’s a distinct type (`System.Nullable<int>`).  

NRTs help avoid `NullReferenceException` in reference types; nullable value types are used when you need a field that can be absent but still be a value type (e.g., optional numeric data). They are orthogonal: you can have `int?` that is `null` or `string?` that is `null`.

**DN13** – **LINQ, method vs query syntax, deferred execution**  

* **LINQ** (Language Integrated Query) provides a uniform way to query collections, databases, XML, etc., using C# syntax.  
* **Method syntax** (`collection.Where(...).Select(...)`) is just ordinary method calls; easier to compose dynamically.  
* **Query syntax** (`from x in collection where x > 0 select x`) reads like SQL; it’s syntactic sugar that the compiler translates to method syntax.  
* **Deferred execution** – LINQ queries are **not executed** when they are built; they are evaluated **when the results are enumerated** (e.g., `foreach` or `ToList`). This allows chaining and lazy evaluation, but also means changes to the source after query creation affect the results.

**DN14** – **Generic constraints**  

```csharp
where T : class      // T must be a reference type (object, string, etc.)
where T : struct     // T must be a value type (int, DateTime, etc.)
where T : new()      // T must have a parameterless constructor
where T : IComparable<T> // T must implement the interface
```

**Combining constraints** – You can stack them, e.g., `where T : class, IComparable<T>, new()`. The order is `class/struct`, then interfaces, then `new()`. Multiple constraints allow you to use features that require both a base type and an interface (e.g., sorting and creating instances).

**DN15** – **Abstract class vs interface, default interface methods**  

* **Abstract class** – can contain **fields**, **constructors**, **partial methods**, and **implemented members**. A class can inherit from **only one** abstract class.  
* **Interface** – can contain **only** members (methods, properties, events) and **static** members; no fields or constructors. A class can implement **multiple** interfaces.  

**Default interface methods (C# 8+)** – Interfaces can now have **implemented** members (e.g., `interface IFoo { void Bar() => Console.WriteLine("default"); }`). This blurs the line: interfaces can provide non‑trivial behavior, and abstract classes can be replaced by interfaces with default implementations when you need multiple inheritance of behavior.

**DN16** – **ASP.NET Core middleware pipeline**  

* `app.UseMiddleware` / `app.Use(...)` – **short‑circuit** middleware that receives `RequestDelegate next` and calls it to pass the request downstream.  
* `app.Map` – **branches** the pipeline based on a path predicate; requests matching the path go to the branch, others continue.  
* `app.Run` – **terminal** middleware; no `next` delegate, ends the pipeline.  

**Ordering** – Middleware is executed **in the order it’s added** (first added = first executed). Exception handling middleware (e.g., `UseExceptionHandler`) should be placed **near the end** so it can catch exceptions from earlier middleware.  

**Exception handling** – When an exception bubbles up, the **exception middleware** can capture it, log, and return a custom response, then the pipeline stops (unless re‑thrown). The `IExceptionHandlerFeature` provides access to the exception.

**DN17** – **Channel<T> vs BlockingCollection<T>**  

* `Channel<T>` (from `System.Threading.Channels`) is a **producer‑consumer** channel with **unbounded** or **bounded** capacity, supporting async `Writer`/`Reader` APIs. It integrates with `await` and `ReadAsync/WriteAsync`.  
* `BlockingCollection<T>` is a **thread‑safe collection** that provides `Add`/`Take` with optional blocking and `CompleteAdding`. It’s built on `BlockingCollection` which uses `Monitor` synchronization.  

**Bounded channel example (producer‑consumer backpressure):**

```csharp
var channel = new Channel<int>(new BoundedChannelOptions(10) { SingleWriter = true, SingleReader = true });

// Producer
async Task ProduceAsync()
{
    for (int i = 0; i < 100; i++)
    {
        await channel.Writer.WriteAsync(i);
        await Task.Delay(10);
    }
    channel.Writer.Complete();
}

// Consumer
async Task ConsumeAsync()
{
    await foreach (var item in channel.Reader.ReadAllAsync())
    {
        Console.WriteLine(item);
    }
}
```

If the channel fills, `WriteAsync` will **wait** (backpressure) until space is available, preventing unbounded memory growth.

**DN18** – **Source Generators**  

* **Source generators** are **compile‑time** Roslyn analyzers that **emit** C# source files, which are then compiled together with the original code. They differ from **reflection** (runtime inspection) and **IL weaving** (post‑compile modification) by generating code **before** the IL is produced.  

* **Incremental generators** – A newer model that **tracks dependencies** (e.g., changed source files) and **re‑generates only affected parts**, improving incremental build performance. They implement `IIncrementalGenerator` instead of `ISourceGenerator`.  

* **Why incremental?** – Traditional `ISourceGenerator` re‑generates all output on any change, causing unnecessary recompilation. Incremental generators allow fine‑grained tracking, reducing build times for large projects.

**DN19** – **TPL Dataflow (System.Threading.Tasks.Dataflow)**  

| Block | Purpose | Typical use |
|-------|---------|-------------|
| **ActionBlock<T>** | Executes an `Action<T>` (or `Func<T, Task>`) on each received item. | Simple processing pipelines, parallel work. |
| **TransformBlock<TInput, TOutput>** | Applies a transformation function, producing output items. | Data conversion, mapping. |
| **BufferBlock<T>** | Stores items in memory; can be linked to other blocks. | Temporary buffering, decoupling producers and consumers. |

**Comparison with `System.Threading.Channels`** – Dataflow provides **higher‑level abstractions** (e.g., `ITargetBlock`, `ISourceBlock`) with built‑in error handling, completion, and linking. Channels are **lower‑level**, focusing on async `Writer/Reader` APIs and are more flexible for custom scenarios. Choose Dataflow for **complex pipelines** with built‑in backpressure and linking; choose Channels for **fine‑grained control** and integration with async/await patterns.

**DN20** – **Minimal APIs in .NET**  

* **Definition** – Endpoint‑oriented APIs defined as **plain methods** (no controllers) using `MapGet`, `MapPost`, etc., directly in `Program` class.  
* **Differences from controller‑based APIs** – No MVC pipeline overhead, less boilerplate, tighter coupling to the request pipeline, and direct access to `HttpContext` and services.  
* **Trade‑offs**  
  * *Testability*: Easier to unit‑test endpoint logic (no controller lifecycle), but integration tests may need to spin up the host.  
  * *Middleware*: Minimal APIs can still use **middleware** via `app.UseMiddleware` or **endpoint filters**, but they bypass many MVC‑specific features (e.g., model binding, filters).  
  * *OpenAPI*: Tools like **Swashbuckle** or **Microsoft.OpenApi** can generate docs automatically, but support is newer than for controllers.  

* **Route groups** – `var group = app.MapGroup("/api/v1"); group.MapGet(...);` – groups common prefixes, enabling versioning and repeated middleware.  

* **Endpoint filters** – Attributes or classes implementing `IEndpointFilter` that can **short‑circuit** request processing, modify arguments, or handle exceptions, providing reusable cross‑cutting logic without middleware.

**P1** – **List vs tuple vs set vs frozenset**  

| Type | Mutability | Ordering | Syntax | Typical use |
|------|------------|----------|--------|-------------|
| `list` | Mutable | Ordered | `[]` | Dynamic sequences, stacks, queues |
| `tuple` | Immutable | Ordered | `()` | Fixed collections, dictionary keys, record‑like data |
| `set` | Mutable | Unordered | `{}` | Membership testing, mathematical set ops |

**P2** – **GIL (Global Interpreter Lock)**  

The GIL is a mutex that **only one thread executes Python bytecode at a time**. It protects CPython’s internal memory management.  

* **Affected workloads** – CPU‑bound pure Python code (e.g., heavy loops, numeric calculations) cannot benefit from multiple cores.  
* **I/O‑bound workloads** – Threads can still run concurrently because I/O releases the GIL (e.g., file reads, network sockets).  
* **Workarounds** – Use **multiprocessing** (spawn separate processes), **asyncio** with async I/O, or **Cython/Numba** extensions that release the GIL, or third‑party libraries like `concurrent.futures.ProcessPoolExecutor`.

**P3** – **Shallow copy vs deep copy**  

* `copy.copy(obj)` creates a **shallow copy**: new container, but elements are **references** to the same objects.  
* `copy.deepcopy(obj)` recursively copies **all** objects, creating new nested objects.  

**Example where shallow copy fails:**

```python
import copy

a = {'items': [1, 2, 3]}
b = copy.copy(a)      # b['items'] is the same list object
b['items'].append(99)
print(a)              # {'items': [1, 2, 3, 99]}  <-- unexpected!
```

Here modifying `b`'s list also changes `a`. `deepcopy` would create an independent list.

**P4** – **Decorators**  

A decorator is a **callable** that wraps a function, returning a new function that typically adds behavior before/after the original call.  

```python
import time
from functools import wraps

def log_execution_time(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

@log_execution_time
def compute():
    time.sleep(0.5)
    return 42

compute()
```

**P5** – **Generators and yield**  

* A **generator function** contains `yield` statements; each `yield` pauses the function, returning a value to the caller, and resumes on the next iteration.  
* Generators produce an **iterator** that yields values lazily, unlike returning a list which materializes all items upfront.  
* `yield from` delegates to another iterable, flattening nested generators.  

```python
def count_up_to(n):
    for i in range(1, n+1):
        yield i

def flatten(gen):
    yield from gen

print(list(count_up_to(3)))          # [1, 2, 3]
print(list(flatten(count_up_to(2)))) # [1, 2]
```

**P6** – **asyncio event loop**  

* `asyncio.run(coro)` – Creates a **new event loop**, runs the coroutine, and **closes** the loop afterwards. Use for top‑level async entry points.  
* `asyncio.gather(*coros, return_exceptions=False)` – Schedules multiple coroutines **concurrently** and waits for all to complete; returns a list of results.  
* `asyncio.create_task(coro)` – Schedules a coroutine as a **Task** (a future) to run soon; returns a `Task` object that can be awaited or monitored.  

`time.sleep()` blocks the thread; inside an async function you should use `asyncio.sleep(delay)` which yields control to the event loop.

**P7** – **Method Resolution Order (MRO)**  

Python 3 uses **C3 linearization** to produce a consistent order that respects both inheritance hierarchy and the order of base classes.  

For the given classes:

```python
class A:
    def who(self): return "A"
class B(A):
    pass
class C(A):
    def who(self): return "C"
class D(B, C):
    pass
```

MRO of `D` → `D -> B -> C -> A -> object`.  
`D().who()` looks for `who` in `D` (none), then `B` (none), then `C` (found) → returns `"C"`.  

Thus `print(D().who())` prints `C`. Diamond inheritance is resolved by the linear order, preventing ambiguous multiple paths.

**P8** – **Metaclass vs `__init_subclass__`**  

* **Metaclass** – A class that defines how **other classes** are created (`type` is the default). Use when you need to **inject behavior into every class** (e.g., adding attributes, enforcing interfaces).  
* **`__init_subclass__`** – A **class method** invoked when a subclass is created. It’s simpler and scoped to a particular base class; useful for **registration**, **validation**, or **custom initialization** without a custom metaclass.  

**Practical use cases**:  
* **Metaclass** – Implementing a **ORM** where each model class needs a `__tablename__` derived from its name.  
* **`__init_subclass__`** – Registering all UI components in a plugin system: `class PluginBase: ...; class MyPlugin(PluginBase): ...` automatically adds `MyPlugin` to a global registry inside `PluginBase.__init_subclass__`.

**P9** – **Multiprocessing vs threading vs concurrent.futures**  

| Approach | Mechanism | When to use | Serialization |
|----------|-----------|-------------|---------------|
| **Threading** | OS threads sharing memory (GIL limits CPU parallelism) | I/O‑bound tasks, CPU‑light Python code | No pickling needed |
| **Multiprocessing** | Separate **processes** with independent memory | CPU‑bound tasks, leverage multiple cores | Objects must be **picklable** to be passed between processes |
| **concurrent.futures** | High‑level API over threads (`ThreadPoolExecutor`) or processes (`ProcessPoolExecutor`) | Need a uniform interface for either thread or process pools | Same serialization rules as underlying executor |

**P10** – **`__slots__`**  

`__slots__` defines a **fixed set of attributes** for a class, preventing the creation of `__dict__` and `__weakref__` per instance.  

* **Benefits** – Reduced memory per instance (no dict overhead), faster attribute access, and fewer accidental attribute creation.  
* **Prevents** – Dynamic addition of new attributes (`obj.newAttr = …`) and weak referencing unless `__weakref__` is included.  

**Memory impact** – For a class with many instances, each instance can save tens of bytes, which is significant for large numbers of objects (e.g., game entities).

**P11** – **Virtual environment**  

A **virtual environment** isolates Python dependencies for a project, preventing conflicts with system‑wide packages.  

* **`venv`** – Built‑in module (`python -m venv env`) that creates a lightweight isolated environment.  
* **`virtualenv`** – Third‑party tool (now largely superseded by `venv`) that also supports multiple Python versions and more customization.  
* **`conda`** – Package manager and environment tool that includes its own interpreter and binary packages; useful for scientific Python stacks and binary dependencies.  

**P12** – **Comprehensions vs map/filter**  

* **List comprehension** `[x for x in seq if cond]` – Pythonic, readable, creates a list directly.  
* **Dict comprehension** `{k: v for k, v in seq.items() if cond}` – Similar for dicts.  
* **Set comprehension** `{x for x in seq if cond}` – Similar for sets.  

`map(func, seq)` and `filter(pred, seq)` return **iterators** (lazy) and are functional in style. Comprehensions are often **faster** and more readable for simple transformations; use `map`/`filter` when you need to pass functions as arguments or chain multiple operations.

**P13** – **`==` vs `is`**  

* `==` compares **values** (calls `__eq__`).  
* `is` compares **identity** (same object in memory).  

**Object interning** – Small integers (`-5` to `256`) and some strings are cached; `a is b` may be `True` for those literals because they refer to the same object. For larger integers or dynamically created strings, `is` usually returns `False`.

**P14** – **`*args` and `**kwargs`**  

* `*args` collects **extra positional arguments** into a tuple.  
* `**kwargs` collects **extra keyword arguments** into a dict.  

**Positional‑only (`/`)** and **keyword‑only (`*`)** markers (Python 3.8+):  

```python
def func(a, b, /, c, *, d):
    print(a, b, c, d)
func(1, 2, 3, d=4)   # OK
func(1, 2, c=3, d=4) # Error: c is positional‑only
```

`/` forces preceding parameters to be passed positionally; `*` forces following parameters to be keyword‑only.

**P15** – **Context managers**  

A context manager implements `__enter__` (called on entry) and `__exit__` (called on exit, even on exceptions).  

```python
from contextlib import contextmanager

class Database:
    def __enter__(self):
        self.conn = sqlite3.connect('test.db')
        return self
    def __exit__(self, *exc):
        self.conn.close()

# Using __enter__/__exit__
with Database() as db:
    db.conn.execute("SELECT 1")

# Using @contextmanager
@contextmanager
def temporary_file():
    f = open('tmp.txt', 'w')
    try:
        yield f
    finally:
        f.close()

with temporary_file() as f:
    f.write('hello')
```

**P16** – **Type hinting**  

* `Union[X, Y]` – value can be `X` or `Y`.  
* `Optional[T]` – shorthand for `Union[T, None]`.  
* `Literal[value1, value2]` – restricts to specific literal values.  
* `TypeVar` – defines generic type parameters (`T = TypeVar('T')`).  
* `Protocol` – defines structural interfaces (duck‑typing) for static checking.  

Tools like **mypy** or **pyright** read these annotations, infer types, and report mismatches, enabling early detection of type errors.

**P17** – **Data model dunder methods**  

* `__repr__` – unambiguous, developer‑friendly representation (ideally `ClassName(attr=value)`).  
* `__str__` – human‑readable string (often defaults to `__repr__`).  
* `__eq__` – defines value equality; if defined, Python **does not automatically create `__hash__`**, making instances unhashable (cannot be used in sets/dicts) unless `__hash__` is also defined or the class is marked `@frozen`/`@dataclass(frozen=True)`.  
* `__getattr__` – called when attribute lookup fails; `__getattribute__` is called for **all** attribute accesses (including existing ones). Overriding `__getattribute__` can break attribute access if not careful.  

**P18** – **Descriptors**  

Descriptor protocol: objects with `__get__`, `__set__`, `__delete__`.  

* `property` – implements `__get__` and `__set__` (and `__delete__` if `@x.deleter`).  
* `classmethod` – descriptor that binds the underlying function to the class, passing the class as first argument.  
* `staticmethod` – descriptor that returns the raw function without binding.  

Descriptors enable **controlled attribute access**, computed properties, and class‑level data storage.

**P19** – **Python import system**  

* **Absolute import** – `import sys` (search `sys.path`).  
* **Relative import** – `from . import module` (relative to current package).  

`sys.path` holds directories searched for modules; `PYTHONPATH` extends it. `__init__.py` marks a directory as a package (though **namespace packages** can exist without it). **Finders** locate modules; **loaders** actually load them (e.g., `SourceFileLoader`). The import machinery (`importlib`) uses these to resolve imports dynamically.

**P20** – **Dataclasses vs attrs vs Pydantic**  

* **Dataclasses** – simple, generated `__init__`, `__repr__`, `eq`, `order`, etc. via `@dataclass`. Support `field()` for default factories, `frozen=True` for immutability. Inheritance works but fields are merged.  
* **attrs** – similar to dataclasses but more concise (`@attr.s` or `@attr.define`), flexible default factories, and explicit `attr.ib()` definitions.  
* **Pydantic** – data‑validation library; creates dataclasses‑like classes with **type‑based validation**, serialization (JSON), and OpenAPI generation. Supports `__post_init__`‑like validation via field validators, `field_validator`, `model_validator`.  

**`__post_init__`** runs after generated `__init__` in dataclasses; `field` factories (`default_factory`) create mutable defaults safely.  

**Frozen dataclasses** prevent assignment after creation.  

**When to choose Pydantic** – When you need **rich validation**, **serialization/deserialization** (e.g., JSON, ORM mapping), and **OpenAPI/Swagger** generation for APIs. Dataclasses/attrs are preferable for simple data containers where validation is minimal.<|END_TEXT|>
