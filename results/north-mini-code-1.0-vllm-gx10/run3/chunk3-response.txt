**T1** – **tofu plan** creates an execution plan that shows what actions OpenTofu will take (creates, updates, or deletes resources) without making any changes. It validates the configuration, resolves dependencies, and can estimate costs or output diffs. **tofu apply** actually carries out the plan, modifying the real infrastructure and updating the state file. `plan` is a read‑only “dry‑run”; `apply` is the mutating step.

**T2** – **State** is OpenTofu’s inventory of the real‑world resources it manages (IDs, attributes, etc.). It lives in a state file (local or remote). **Remote state** is essential for team collaboration, locking, and consistency across workspaces; without it each user would have a separate copy and could overwrite each other’s changes.

**T3** – `count` creates N identical resources with auto‑generated names (`resource.0`, `resource.1`, …). It only knows “how many”. `for_each` iterates over a map or list, using each element’s key (or value) as the resource name and allowing per‑item attributes. Use `for_each` when resources need distinct names, tags, or configuration that varies per item.

**T4** – If you edit a resource manually (e.g., via the cloud console), OpenTofu detects **drift** on the next `plan`/`apply`. It will flag the resource as “drifted” and, by default, will attempt to reconcile it (often by recreating or updating). You can refresh the state (`tofu refresh`) to update OpenTofu’s view, or use `lifecycle { ignore_changes = [...] }` to deliberately ignore certain drift.

Use module outputs; reserve `data "terraform_remote_state"` only for read‑only cross‑workspace queries where outputs aren’t feasible.

**T8** – `tofu import` adds an existing infrastructure object to OpenTofu’s state, allowing it to be managed. Limitations: only one resource at a time, the resource must already exist, you must have the exact resource type defined, and you can’t import resources that have dependencies not yet in the config. The **import block** (1.5+) lets you declare imports declaratively inside `.tf` files, enabling version‑controlled imports, parallel imports, and better error handling without manual CLI steps.

**T9** – A **variable** (`variable "region" {}`) is an input placeholder that can be supplied from CLI, environment, or `.tfvars`. An **output** (`output "public_ip" {}`) is a value exported from a module so callers can retrieve it. Variables are for configuration; outputs are for results.

**T10** – A **provider** is a plugin that knows how to create, read, update, or delete resources in a specific SaaS (e.g., AWS, GCP). Running `tofu plan` without `tofu init` will fail (or attempt an auto‑download) because the required provider plugin isn’t present locally. `init` downloads, authenticates, and configures providers.

**T11** – `.terraform.lock.hcl` records the exact provider binary versions (and plugin checksums) that were downloaded. It guarantees reproducible builds across environments. Commit it so every CI/runner uses the same provider versions.

**T12** – `tofu destroy` removes **all** resources managed by the current state, prompts for confirmation, and then deletes the state file (or leaves it for re‑use). **T13** – A **data source** (`data "aws_ami"` etc.) provides read‑only access to external information without managing a resource. Use it when you need to reference existing data (e.g., the latest AMI) rather than creating a new resource.

**T14** – **locals** are computed values defined with `locals { ... }`. **T15** – `lifecycle { ... }` block controls resource behavior.

**T17** – OpenTofu builds a **dependency graph** where nodes are resources and edges represent required order. **Implicit dependencies** arise from attribute references (e.g., `subnet_id = aws_subnet.foo.id`). **Explicit dependencies** are declared with `depends_on`. `depends_on` forces a resource to wait for another, reducing parallelism (the dependent resource won’t start until the prerequisite finishes). **T18** – Strategies to shrink a 10‑minute plan for a 200‑resource stack (trade‑offs noted):

1. **`-refresh=false`** – Skip API calls to cloud providers. *Trade‑off:* you lose drift detection; you may apply changes to resources that have already been modified outside Terraform.  
2. **`-target=`** – Limit the plan to a subset of resources (e.g., only the ones you’re actively changing). *Trade‑off:* you must re‑run plan for other subsets, and you need to know which resources are safe to plan in isolation.  
3. **`-parallelism=n`** – Reduce the number of concurrent operations OpenTofu attempts during plan (default is 10). Lower values can reduce memory pressure and make plans more predictable. *Trade‑off:* longer plan time if parallelism is too low.

**T19** – OpenTofu’s state locking works via the backend (e.g., S3 + DynamoDB). When a operation starts, OpenTofu writes a lock ID and a “lock info” record to DynamoDB (or a local file for local backend). Subsequent operations see the lock and wait up to a timeout (default 5 min) before failing with “state lock denied”.  

If a lock is not released (e.g., CI crash), you can manually break it: delete the lock record from DynamoDB (`aws dynamodb delete-item`) or remove the `.terraform/lock.info` file for a local backend. Risks: concurrent modifications can corrupt the state, leading to inconsistent infrastructure or “orphaned” resources.

**T20** – Migration from a local state to an S3‑compatible remote backend with DynamoDB locking:

1. **Backup** the existing local `terraform.tfstate` (copy to safe location).  
2. Create a **backend configuration** (`backend "s3" { bucket = "my-tfstate" key = "prod.tfstate" region = "us‑east‑1" dynamodb_table = "tf-state-lock"}`) in a new `terraform.tf` (or update existing).  
3. Run `tofu init -backend=true -reconfigure`. This creates the S3 bucket (if missing) and the DynamoDB lock table, and initializes the remote state with the current state (OpenTofu will automatically copy the local state into the remote backend).  
4. Verify the remote state exists (`tofu show -json`).  
5. Optionally switch workspaces (`tofu workspace new <new>`), then **delete** the local state file (`rm terraform.tfstate`) to force all future operations to use the remote backend.  
6. Run `tofu plan` and `tofu apply` to confirm everything works against the remote state.  

The old local state is now superseded; OpenTofu will read/write exclusively to S3/DynamoDB, and locking is enforced via DynamoDB.

**A9** – An **inventory file** lists hosts and optional variables (e.g., `webservers ansible_host=10.0.0.1`).  

*Static inventory* – plain text (`hosts.ini`) or INI/YAML format, read directly by Ansible.  
*Dynamic inventory* – a script or plugin (e.g., AWS, Azure, OpenStack) that queries cloud APIs and outputs an inventory JSON/YAML on the fly, allowing host lists to change automatically.

**A10** – Ad‑hoc command to check disk space on all webservers:

```bash
ansible webservers -m shell -a "df -h"
```

**A11** – A **handler** is a task that runs only when notified and at the end of a play, used for services that need to be restarted after configuration changes. Regular tasks run immediately. Handlers are triggered with the `notify:` keyword.

**A12** – `ansible.cfg` controls global Ansible behavior. Common settings:

* `defaults` – default module options.  
* `remote_tmp` – temporary directory on remote hosts.  
* `forks` – number of parallel connections.  
* `timeout` – connection timeout.  
* `ssh_args` – extra SSH options.  
* `roles_path` – additional role directories.  
* `library` – custom module paths.

**A13** – `register` captures the result of a module into a variable. Example:

```yaml
- name: Get system info
  setup:
    filter: ansible_distribution*
  register: distro_info

- name: Show distribution
  debug:
    var: distro_info.ansible_facts.ansible_distribution
```

**A14** – `include_tasks` is **dynamic** – evaluated at runtime, can be conditionally included with `when`. `import_tasks` is **static** – parsed when the playbook is loaded, cannot be conditionally included. Use `include_tasks` when you need conditional inclusion or want to avoid re‑parsing the whole playbook; use `import_tasks` for reusable task blocks that should be part of the playbook’s static structure.

**A16** – **Connection plugins** define how Ansible talks to targets.  

* `ssh` – default for Unix/Linux/macOS hosts, uses SSH.  
* `local` – runs tasks directly on the control node (useful for admin tasks).  
* `network_cli` – for network devices (Cisco, Juniper) using CLI over SSH/Telnet.  

Choose based on target OS/type.

**A17** – `delegate_to` runs a task on a specified host; `run_once` ensures a task runs once on the first host of a group and then delegates the result to other hosts (or uses `delegate_to`).  

*Example:* gather facts from a remote host, then run a control‑node script that uses those facts:

```yaml
- hosts: all
  tasks:
    - name: Gather OS version on remote host
      setup:
        filter: ansible_distribution_version
      register: os_info
      delegate_to: "{{ inventory_hostname }}"

    - name: Run local cleanup using gathered version
      command: /usr/local/bin/cleanup --version {{ os_info.ansible_facts.ansible_distribution_version }}
      delegate_to: localhost
      run_once: true   # ensures only the control node runs it
```

**A18** – Performance boosters for a 500‑host fleet (trade‑offs):

1. **Increase `forks`** (e.g., `forks: 50`). More parallel connections → faster runs, but higher memory/CPU usage and possible SSH throttling.  
2. **Enable pipelining** (`pipelining = True`). Reduces per‑task overhead by streaming output, improving throughput on high‑latency links, at the cost of more complex debugging.  
3. **Fact caching** (`fact_path` or external cache like Memcached). Avoid re‑gathering facts each run, saving CPU/time, but you must keep cached facts up‑to‑date.  
4. **Mitogen or similar SSH acceleration** (e.g., `strategy: mitogen_linear`). Drastically cuts SSH handshake time and connection overhead, but adds a dependency and requires careful key management.

**A19** – Jinja2 templating in Ansible:  

* `{{ expression }}` – evaluates an expression and inserts the result.  
* `{% ... %}` – control structures (loops, conditionals, includes).  
* `{# ... #}` – comments (ignored by Jinja).  

Snippet generating an nginx upstream block:

```yaml
- name: Render nginx upstream config
  template:
    src: nginx_upstream.j2
    dest: /etc/nginx/upstream.conf
  vars:
    backends:
      - host: web1.example.com
        port: 80
      - host: web2.example.com
        port: 80
```

`nginx_upstream.j2`:

```nginx
upstream myapp {
    # backends
{% for b in backends %}
    server {{ b.host }}:{{ b.port }};  # health check via default nginx health checks
{% endfor %}
}
```

**A20** – Zero‑downtime rolling deployment across 20 servers:

```yaml
- hosts: app_servers
  strategy: linear
  serial: 5          # deploy 5 servers at a time (20/5 = 4 waves)

  pre_tasks:
    - name: Drain load balancer for this batch
      uri:
        url: "https://lb.example.com/api/drain?batch={{ group_names[0] }}"
        method: POST
        status_code: 200

  tasks:
    - name: Deploy new version (block)
      block:
        - name: Stop old service
          service:
            name: myapp
            state: stopped
        - name: Copy new code
          copy:
            src: /src/myapp.tar.gz
            dest: /opt/
        - name: Unarchive and set permissions
          shell: |
            tar -xzf /opt/myapp.tar.gz -C /opt/myapp
            chown -R myapp:myapp /opt/myapp
        - name: Start new service
          service:
            name: myapp
            state: started
            enabled: yes
      rescue:
        - name: Rollback on failure
          command: /opt/myapp/rollback.sh
          notify: trigger_service_restart

  post_tasks:
    - name: Re‑enable load balancer for this batch
      uri:
        url: "https://lb.example.com/api/reenable?batch={{ group_names[0] }}"
        method: POST
        status_code: 200

  handlers:
    - name: trigger_service_restart
      service:
        name: myapp
        state: restarted
```

*Explanation*:  
- `serial: 5` creates 4 waves of 5 servers each.  
- `pre_tasks` notify the LB to stop sending traffic to the batch.  
- The `block` runs deployment steps; `rescue` executes a rollback script if any step fails.  
- `post_tasks` re‑enables LB traffic after successful deployment.  
- Handlers ensure the service is restarted if a rollback is needed.  

This pattern keeps the application available (only a subset of servers is down at any time) and provides an automated rollback path.<|END_TEXT|>
