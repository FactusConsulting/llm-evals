*Array*: ` [N]T ` – fixed length `N` known at compile time, value type includes the underlying array.  
*Slice*: ` []T ` – a lightweight descriptor (`struct { ptr *T; len, cap int }`) that references a **segment** of an underlying array. Slices can grow (via `append`) because they have a `cap`.  

*Append behavior*: When you `append` to a slice, if the current length < capacity, the element is stored in‑place and the slice’s length is incremented. If the slice has **reached capacity**, `append` allocates a **new underlying array** (usually 2× the old capacity), copies the existing elements, stores the new element, and returns a new slice header pointing to the new array. The original slice’s underlying array is no longer used.

**G2** – **`var x int` vs `x := 0`**  
* `var x int` – declares a **top‑level** (package‑scope) variable, initializes it to the zero value of `int` (`0`). The syntax can also be used inside a block to give an explicit type.  
* `x := 0` – **short‑variable declaration**; the type is inferred from the right‑hand side (`int`). It can only be used **inside a function** (or other lexical block) where there is no existing identifier `x`.  

*When you cannot use `:=`*:  
1. At package level (global variable declarations).  
2. Inside a function where the name already appears on the left‑hand side of a `:=` (you must use `=` or `var`).  
3. In a `for`‑loop initializers that already have a `var` or `:=` (you must use `=`).

**G3** – **Goroutine, OS thread, and the Go scheduler (GMP model)**  
*Goroutine*: a lightweight thread managed by Go runtime; it has no direct OS thread until the scheduler maps it.  
*OS thread*: a kernel‑level thread; switching is expensive.  

*GMP model*:  
- **G** – goroutine.  
- **M** – OS thread (executed by the kernel).  
- **P** – processor (a set of OS threads + work queues).  

The scheduler multiplexes many Gs onto a smaller number of Ms, which are bound to Ps. When a G blocks (e.g., I/O), the M is parked and can be reused for another G. The scheduler’s goal is to keep Ms busy with runnable Gs, achieving high concurrency with low overhead.

**G4** – **Channels**  
A channel `chan T` is a communication conduit.  
*Unbuffered*: each send must have a corresponding receive at the same moment; the operation blocks until the other side is ready.  
*Buffered*: created with a capacity, e.g., `make(chan T, 5)`. Up to 5 values can be sent without a receiver; once full, a send blocks.  

*Sending to a full buffered channel*: the sender **blocks** until a receiver removes an element, freeing space. This provides back‑pressure without requiring a separate goroutine for each producer/consumer pair.

**G5** – **Context package (minimal `WithTimeout` example)**  

```go
package main

import (
    "context"
    "fmt"
    "net/http"
    "time"
)

func main() {
    // Create a context that times out after 1 second.
    ctx, cancel := context.WithTimeout(context.Background(), time.Second)
    defer cancel() // ensure resources are released

    // Build a request with the context.
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, "https://example.com", nil)
    if err != nil {
        fmt.Println("request error:", err)
        return
    }

    // Perform the HTTP request.
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        // err may be a timeout from the context.
        fmt.Println("request error:", err)
        return
    }
    defer resp.Body.Close()
    fmt.Println("status:", resp.Status)
}
```

The `context.WithTimeout` creates a `Context` that automatically cancels the underlying request when the deadline expires, causing the HTTP client to return an error (e.g., `context.DeadlineExceeded`).

**G6** – **Interface satisfaction & the empty interface**  

*Interface satisfaction*: In Go, a type **automatically satisfies** an interface if it implements all the required methods. No explicit `implements` keyword; the compiler checks this at compile time.  

*Difference from Java/C#*: Java/C# require an explicit `implements` or `:` syntax, and interfaces can contain fields. Go interfaces are **empty** (no fields) and are satisfied implicitly.  

*Empty interface (`interface{}` or `any`)*: Holds **any** value because every type implements zero methods.  
- **Powerful**: you can store heterogeneous data in a slice (`[]any`), write generic functions that accept anything, and use `type switches`.  
- **Dangerous**: type safety is lost; you must perform explicit type assertions, which can panic if the underlying type is unexpected.

**G7** – **Memory model & visibility**  

The snippet suffers from a **data race** and **visibility** issue:

```go
var ready bool
var data string

go func() {
    data = "hello"
    ready = true
}()

for !ready {} // busy‑wait
fmt.Println(data)
```

*Why unsafe*:  
1. No synchronization between the goroutine and the main goroutine. The write to `ready` may not be visible to the main goroutine (compiler/CPU may reorder or cache‑keep the variable).  
2. The `bool` and `string` writes are not atomic; concurrent unsynchronized accesses cause data races (undefined behavior).

*Correct alternatives*:  

- Use `atomic.Bool` / `atomic.Value` or a `sync.Mutex` to protect the flag.  
- Or use a channel to signal completion:

```go
var data string
ready := make(chan struct{})

go func() {
    data = "hello"
    close(ready) // signal
}()

<-ready // wait
fmt.Println(data)
```

The channel provides a happens‑before relationship, guaranteeing visibility.

**G8** – **Mutex vs. RWMutex & `sync.Map`**  

*`sync.Mutex`*: exclusive lock; only one goroutine can hold it.  
*`sync.RWMutex`*: allows **many** concurrent readers (`RLock`/`RUnlock`) but exclusive writer (`Lock`/`Unlock`). Useful when reads dominate.  

*`sync.Map` vs. `map + mutex`*:  

- `sync.Map` is optimized for **concurrent reads/writes** with low contention; it uses sharding and atomic operations. It is **not** a replacement for `map` when you need iteration or deterministic ordering.  
- A regular `map` with a `Mutex` gives you full control, iteration, and the ability to use `range`. It may have higher contention but is simpler and can be tuned (e.g., using a reader‑writer mutex).  

*Performance trade‑offs*: `sync.Map` avoids the global lock contention of a single mutex, but each operation incurs overhead of hash‑table sharding and atomic updates. For low‑contention workloads, a `map+Mutex` is often faster and more memory‑efficient.

**G9** – **Go modules**  

- **`go.mod`**: Module manifest. Contains module path, required version, replacements, excludes, etc. It tells the tool which module we are in and which dependencies are needed.  
- **`go.sum`**: Checksum file. Stores cryptographic hashes of downloaded module files to guarantee reproducibility and protect against tampering.  

- **`go mod tidy`**: Removes unused requirements, adds needed ones, and cleans up the `go.mod` file. It ensures the module’s dependency graph is minimal and consistent.  

- **Minimum Version Selection (MVS)**: Algorithm used by `go mod` to pick the lowest compatible version of each dependency that satisfies all transitive requirements, avoiding unnecessary upgrades and keeping builds deterministic.

**G10** – **`defer`**  

`defer` schedules a function call to run **when the surrounding function returns** (either via normal return, panic, or multiple returns).  

*Order*: Defers are executed **LIFO** (last‑in, first‑out). The most recently deferred call runs first.  

*Gotcha in a loop*:

```go
for i := 0; i < 3; i++ {
    defer fmt.Println(i)
}
```

All three `defer`s capture the **same variable `i`** (the loop variable). By the time they run, `i` has the final value `2`, so you see `2` three times. Fix by using a local copy:

```go
for i := 0; i < 3; i++ {
    iLocal := i
    defer fmt.Println(iLocal)
}
```

**G11** – **Pointer**  

A pointer holds the **memory address** of a variable. Zero value is `nil`.  

Create a pointer to a struct literal:

```go
p := &struct{ name string }{name: "Alice"}
```

`p` points to a newly allocated struct on the heap (or stack if escape analysis decides it can stay on stack).

**G12** – **`init()`**  

- `init()` is a special function that the Go compiler automatically creates an entry point for each package.  
- It runs **automatically** after all global variable initializations and before the program’s `main()` (or any other top‑level function) begins.  
- Multiple `init()` functions are allowed in a package; they are executed in the order they appear in the source file(s).

**G13** – **`make` vs. `new`**  

- `new(T)`: returns a pointer `*T` (`new(int) -> *int`). The returned pointer is **zero‑initialized**. Used for any type.  
- `make(T)`: only works for **channel, slice, and map** (and a few other built‑ins). It returns an **initialized zero‑value** of that type (e.g., `make([]int, 0)`). It does **not** allocate a pointer.

**G14** – **Error handling**  

- The `error` interface: `type error interface { Error() string }`.  
- Idiomatic pattern:

```go
if err := someFunc(); err != nil {
    // log, wrap, or return
    return fmt.Errorf("wrapped: %w", err)
}
```

- `errors.Is(err, target)` checks if `err` **is** `target` or wraps it (using `Is` method). `errors.As(err, &target)` attempts to **cast** `err` to a specific type implementing `error`. Both are safer than `==` because they respect error wrapping (`fmt.Errorf` with `%w`).

**G16** – **Race condition & `-race` flag**  

A race occurs when two goroutines concurrently read/write the same memory without synchronization, leading to data corruption or inconsistent state.  

`-race` instrument Go code to detect data races at runtime; it adds bookkeeping and will panic if a race is found.  

*Example race*:

```go
var cnt int

go func() {
    for i := 0; i < 1000; i++ {
        cnt++ // write
    }
}()
for i := 0; i < 1000; i++ {
    _ = cnt // read
}
```

Two goroutines may interleave reads/writes, causing lost increments.  

*Fix with `sync.Mutex`*:

```go
var cnt int
var mu sync.Mutex

go func() {
    for i := 0; i < 1000; i++ {
        mu.Lock()
        cnt++
        mu.Unlock()
    }
}()
mu.Lock()
for i := 0; i < 1000; i++ {
    _ = cnt
}
mu.Unlock()
```

Or use a channel to serialize increments.

**G17** – **`select`**  

`select` is like a **switch** over **communication operations** (`send`, `receive`, default). It chooses **one** ready case **randomly** when multiple are ready.  

- If none are ready, it blocks until at least one becomes ready.  
- A `default` case executes immediately if the channel operation would block.  

*Timeout with `select`*:

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

select {
case <-time.After(2 * time.Second):
    fmt.Println("timeout")
case msg := <-ch:
    fmt.Println("received:", msg)
}
```

Or using a `chan struct{}` with a timer.

**G18** – **Escape analysis**  

Escape analysis determines whether a variable’s value can be allocated on the **stack** (no pointers escape the function) or must go to the **heap** (e.g., referenced by a closure, returned, or stored in a global).  

The compiler decides at compile time; you cannot directly control it, but you can influence it by:  

- Returning pointers to local variables → forces heap allocation.  
- Using `new(T)` or `&T{}` inside a function that returns the pointer → heap.  
- Passing a pointer to a function that stores it in a closure → heap.  

*Inspecting*: compile with `-m` flag (`go build -gcflags="-m"`). Output shows “ escapes to heap” or “does not escape”.  

*Why it matters*: Stack allocation is cheap (no GC pressure), while heap allocation incurs GC overhead and possible pauses.

**G19** – **Reflection (`reflect` package)**  

- `reflect.Type`: describes **type information** (kind, methods, fields, etc.). Obtained via `reflect.TypeOf(x)`.  
- `reflect.Value`: holds a **value** (including methods) and allows reading/writing fields, calling functions, etc. Obtained via `reflect.ValueOf(x)`.  

*Performance costs*: Reflection is **dynamic**; each operation incurs overhead of type checks, bounds checks, and often indirect calls. It also prevents many compiler optimizations.  

*When justified*:  
- Generic code that must operate on arbitrary types (e.g., serialization frameworks, testing utilities).  
- Situations where the set of types is not known at compile time (e.g., plugin systems).  

*When to prefer code generation*: If you need high‑throughput serialization or heavy numeric work, generating type‑specific code (e.g., via `reflect`-based code generators) eliminates per‑call reflection overhead.

**G20** – **`go:embed` directive**  

`go:embed` embeds **files or directories** into the program at compile time, producing a `[]byte` or `string` (depending on the type of the variable) that holds the file contents.  

- **Single file**: `embed "config.txt"` → variable of type `string` or `[]byte`.  
- **Directory**: `embed "static/..."` → variable of type `embed.FS` (an `io/fs.FS` implementation) that can be used with `os.ReadFile`, `embed.Open`, etc.  

*Limitations*:  
- Only works with **plain files** (no symlinks).  
- Cannot embed files larger than the maximum executable size (practical limits).  
- The embedded data is read‑only; you cannot modify it at runtime.  

*Interaction with `io/fs.FS`*: The generated `embed.FS` satisfies the `io/fs.FS` interface, so you can use standard `fs` utilities (`fs.ReadFile`, `fs.Stat`, `fs.Sub`) without extra conversion.

**R1** – **Ownership & three rules**  

Ownership: each value has **exactly one owner** at a time; the owner is responsible for dropping the value when done (freeing memory).  

Three rules:  
1. **Each value has a single owner** (cannot have multiple owners simultaneously).  
2. **When the owner goes out of scope or is reassigned, the value is dropped** (memory freed).  
3. **You can borrow (`&`) a value immutably or mutably, but borrows cannot outlive the owner** and there can be at most one mutable borrow or any number of immutable borrows at a time.

**R2** – **`String` vs `&str`**  

- `String`: owned, heap‑allocated, mutable (`String` implements `Deref<Target=str>`).  
- `&str`: borrowed, slice of UTF‑8 bytes, immutable, no allocation.  

*Function signatures*: Use `&str` for read‑only text (e.g., `fn process(s &str)`). Use `String` when you need to own and possibly modify the text (e.g., `fn make_upper(s String) String`).

---

**R3** – **Borrowing & the borrow checker**  

Borrowing creates a reference (`&T` or `&mut T`). The borrow checker enforces:  

- **Immutability**: any number of `&T` borrows allowed, but they must be read‑only; the data cannot be mutated through any of them.  
- **Mutability**: at most **one** `&mut T` borrow at a time; it grants exclusive access for mutation.  
- **Lifetime**: borrows cannot outlive the original value; they must not be used after the owner is dropped.  

---

**R4** – **`Result` & `Option` & `?` operator**  

- `Result<T, E>`: `Ok(v)` for success, `Err(e)` for failure.  
- `Option<T>`: `Some(v)` or `None`.  

`?` propagates errors: `expr?` returns the inner value on `Ok`, or returns `Err(expr)` on `Err`.  

*File‑reading example*:

```rust
use std::fs;

fn read_file(path: &str) -> Result<String, std::io::Error> {
    let contents = fs::read_to_string(path)?; // propagates IO error
    Ok(contents)
}
```

---

**R5** – **`Box`, `Rc`, `Arc`**  

- `Box<T>`: **owned** heap allocation; moves the value onto the heap, allowing recursive types or large values on the stack without size limit.  
- `Rc<T>`: **reference‑counted** for single‑threaded scenarios; each clone increments the count, the data is dropped when the last `Rc` is dropped.  
- `Arc<T>`: **atomic reference‑counted** for multi‑threaded use; atomic increments/decrements ensure safe sharing across threads.  

*Use*: `Box` for owned heap data, `Rc` for interior‑mutability within a thread, `Arc` for shared data across threads.

---

**R6** – **Traits & trait objects vs. generics**  

- **Trait**: a collection of method signatures a type can implement.  
- **Go interfaces** are similar but **do not support** associated types, default implementations, or higher‑ranked traits.  

*Trait object (`dyn Trait`)*: a **fat pointer** (`data pointer`, `vtable pointer`) that can hold any type implementing `Trait`. Dynamic dispatch (runtime lookup).  

*Generic with trait bound (`T: Trait`)`: static dispatch; the compiler monomorphizes the code for each concrete type at compile time, eliminating vtable overhead.

---

**R7** – **Lifetimes**  

The function:

```rust
fn longest(x: &str, y: &str) -> &str { … }
```

fails because the returned slice borrows from one of the inputs, but the compiler cannot guarantee that the returned reference lives as long as both `x` and `y`.  

*Fix*: introduce explicit lifetimes:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

The lifetime `'a` ties the output to the inputs.

---

**R8** – **`Send` & `Sync`**  

- `Send`: a type can be transferred safely across thread boundaries (owns data).  
- `Sync`: a type can be referenced safely from multiple threads (`&T` is `Send`).  

`Rc<T>` does **not** implement `Send` because its internal reference count is not atomic; sharing across threads could cause data races. `Arc<T>` implements both `Send` and `Sync` because it uses atomic reference counting, making concurrent updates safe.

---

**R9** – **Async/await under the hood**  

- **Future**: a trait representing a computation that may not be complete; it returns `Poll<Output>`.  
- **Executor (e.g., Tokio)**: drives futures by polling them, switching tasks when a future yields (`Pending`).  

*Difference from Go goroutines*: Go’s goroutines are **pre‑emptive** (scheduled by the Go runtime) and communicate via channels. Rust async is **cooperative**; a future runs until it awaits something, then yields control to the executor. Both achieve concurrency, but Rust’s model is based on explicit `await` points and a task scheduler.

---

**R10** – **`unsafe` block**  

Three things you can do in `unsafe`:  

1. **Dereference raw pointers** (`*mut T`) without ownership guarantees.  
2. **Call functions from C** (`extern "C" { fn foo(); }`) and invoke them.  
3. **Access or modify `static mut`** variables.  

`unsafe` is justified when interfacing with OS APIs, implementing low‑level data structures, or working with foreign code where safe Rust cannot express the required semantics.

---

**R11** – **Pattern matching**  

`match` examines an expression against patterns, optionally binding variables. `if let` is syntactic sugar for a `match` with a single `Some(pattern)`‑like arm.  

The compiler enforces **exhaustiveness**: every possible value of the matched type must be covered, otherwise a warning (or error in some lint configurations) appears.

---

**R12** – **`Vec<T>` vs. `[T; N]`**  

- `[T; N]` is a **fixed‑size array** stored on the stack (or in the location where it appears). Length is part of the type.  
- `Vec<T>` is a **growable, heap‑allocated** slice with its own length and capacity.  

When `push` exceeds capacity, `Vec` allocates a **new underlying array** (typically 1.5×–2× growth), copies existing elements, and deallocates the old array.

---

**R13** – **Enums**  

Rust enums can carry data (variant fields), unlike C enums which are just integral constants.  

`Option<T>` (`Some`/`None`) eliminates the need for `null`; the compiler forces handling of both cases, preventing null‑pointer dereferences.

---

**R14** – **`impl` block**  

- `&self`: immutable borrow, can read fields.  
- `&mut self`: mutable borrow, can modify fields.  
- `self`: takes ownership, used for methods that consume `self` (e.g., `String::into_bytes`).  

Associated functions (`String::new()`) are called on the type without an implicit `self` (`Self`).

---

**R15** – **Derive macro**  

`#[derive(Debug, Clone, PartialEq, Serialize)]` automatically implements those traits.  

You **cannot** derive traits that are not defined in the standard library or that have generic parameters not supported by `#[derive]`. Also, you cannot derive traits that require custom logic (e.g., `Ord` unless you also implement it manually).

---

**R16** – **`Cow<'a, T>` (Clone‑on‑Write)**  

`Cow` is either `Borrow<'a, T>` (view into existing data) or `Owned(T)` (owned data).  

*Use case*: reading a file that may be small enough to keep in memory, but large otherwise:

```rust
fn read_file(path: &str) -> Cow<str> {
    if let Ok(small) = std::fs::read_to_string(path) {
        Cow::Borrowed(&small) // cheap if already owned
    } else {
        Cow::Owned(std::fs::read_to_string(path).unwrap()) // fallback
    }
}
```

If the file is small, we borrow; if it’s large, we own, avoiding an extra clone.

---

**R17** – **Module system (2015 vs 2018 editions)**  

- `mod foo;` declares a module in `foo.rs` (or `foo/mod.rs`).  
- `use foo::bar;` brings an item into scope.  
- `pub` controls visibility.  

**2015 edition**: files were `foo.rs` or `foo/mod.rs`; `mod foo { … }` could be inline.  

**2018 edition**: introduced **module paths** and **edition‑agnostic** file layout; you can use `pub mod foo;` with `foo/` directory containing `mod.rs`. Also added **crate root** (`lib.rs`) and **binary** (`main.rs`) separation, and support for `use` statements with `as`.

---

**R18** – **`Pin<T>`**  

`Pin` ensures a value’s location in memory never changes after being pinned, enabling safe self‑referential structs (e.g., a struct that holds a reference to one of its own fields).  

It is needed for async functions because the returned future may be stored somewhere and must not be moved while it’s being polled.  

`Unpin` is a marker trait; types that implement `Unpin` can be safely moved. `Pin` automatically implements `Unpin` for types that are `Unpin`, allowing `pin_mut!` macros.

---

**R19** – **Macro system**  

- **Declarative macros** (`macro_rules!`): text substitution at compile time, hygienic (cannot capture outer variables).  
- **Procedural macros**:  
  - `derive`: custom attribute that generates implementations.  
  - `attribute`: custom `#[proc_macro]` that transforms items.  
  - `function‑like`: `proc_macro` that looks like a macro call.  

Hygiene ensures that identifiers inside macros do not accidentally capture or pollute the surrounding namespace.

---

**R20** – **Zero‑cost abstractions**  

Zero‑cost abstractions mean the high‑level Rust code compiles to **exactly** the same performance as hand‑written low‑level code (no runtime overhead).  

- **Iterators**: implemented via `Next` trait; compiler often optimizes loops into direct indexing.  
- **Generics (monomorphization)**: each concrete type gets its own version of generic code, eliminating virtual dispatch.  
- **Trait static dispatch**: if a trait is used without `dyn`, the compiler resolves method calls at compile time (static dispatch), avoiding vtable overhead.  

Together they let you write expressive, safe code while achieving C‑level performance.<|END_TEXT|>
