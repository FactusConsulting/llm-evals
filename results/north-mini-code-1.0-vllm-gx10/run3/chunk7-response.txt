A monolith is a single, tightly‑coupled codebase where all components run in one process and share the same database and runtime.  
Microservices decompose the application into small, independently deployable services, each with its own data store and business logic.  

**Three concrete problems introduced by microservices (not present in a monolith):**  
1. **Network latency & reliability** – inter‑service calls add hop‑by‑hop latency and possible failures; a monolith’s in‑process calls are essentially local.  
2. **Operational complexity** – you must manage service discovery, configuration, logging, monitoring, and deployments for many services (often using CI/CD pipelines per service).  
3. **Distributed data consistency** – maintaining data integrity across multiple databases requires Saga patterns, eventual consistency, or complex locking, whereas a monolith can use a single transactional DB.

- **Asynchronous communication:** The caller sends a message and continues processing; the recipient processes it later. Example: RabbitMQ (message queue) or Apache Kafka (event broker).

**AA3 – Medium**  
- **API Gateway:** Acts as a single entry point for clients, providing request routing, protocol translation, composition, security (auth, rate‑limiting, TLS termination), caching, and monitoring. It understands application‑level concerns.  
- **Reverse Proxy:** Primarily forwards traffic at Layer 4/7, load‑balances, terminates TLS, and can do basic path‑based routing, but does not typically enforce business‑level policies.

Often you still need a reverse proxy (or a load balancer) in front of the API Gateway for raw TCP/SSL termination, health‑checking, and high‑availability. An API Gateway can incorporate many reverse‑proxy features, but a dedicated reverse proxy provides lower‑level, high‑performance routing that is easier to scale and maintain separately.

**AA4 – Medium**  
**Saga pattern:** A sequence of local transactions, each belonging to a single service, that must be coordinated to achieve a global transaction. If a step fails, compensating transactions are invoked to undo earlier steps.  

- **Choreography‑based saga:** Each service publishes an event when it completes its step; the next service reacts to that event. No central coordinator; services are loosely coupled but coordination logic is spread across them.  
- **Orchestration‑based saga:** A central orchestrator (typically a service) tracks the saga state, publishes “start/next/compensate” commands, and decides the next step. Provides explicit control, easier debugging, and can handle complex business logic.  

**When to use each:**  
- **Choreography** for simple, loosely‑coupled workflows where eventual consistency is acceptable and you want minimal central point of failure.  
- **Orchestration** for complex, critical, or regulatory‑driven workflows where you need explicit compensation, auditability, and the ability to pause or retry steps.

**AA5 – Medium**  
**CQRS (Command Query Responsibility Segregation):** Separates “write” operations (Commands) from “read” operations (Queries). The command side updates a write‑model (often an ORM or raw DB), while the query side uses a read‑model (denormalized view, projection, or cache) optimized for fast reads.  

**Why paired with Event Sourcing?**  
Event Sourcing stores an immutable log of state‑changing events. CQRS can project those events into multiple read‑models (different queries) without touching the write model, enabling independent scaling of reads and writes, audit trails, and replayability.  

**Problem solved vs. traditional CRUD:**  
- **Scalability:** Reads and writes can be scaled independently.  
- **Complex queries:** Read‑models can be tailored for UI needs, avoiding expensive joins on the write store.  
- **Audit & replay:** Event log provides a full history for debugging, rollback, or rebuilding state.

**AA6 – Medium**  
**Circuit Breaker pattern:** Monitors for failures; if a threshold is exceeded, it “opens” the circuit so subsequent calls short‑circuit without invoking the remote service, allowing the system to degrade gracefully.  

**Three states:**  
1. **Closed** – Normal operation; requests flow and failures are counted.  
2. **Open** – Failure threshold reached; all requests immediately fail (or return a fallback).  
3. **Half‑Open** – After a timeout, a limited number of test requests are allowed; if they succeed, the circuit returns to Closed; if they fail, it re‑opens.  

**Difference from simple retry with backoff:**  
- **Retry** repeatedly attempts the same call with exponential backoff, assuming the failure is transient.  
- **Circuit Breaker** stops calling altogether after a failure threshold, preventing cascade failures.  

**When to use both:**  
- Use retries for occasional transient glitches (e.g., network blip).  
- Use a circuit breaker when a service is prone to sustained outages or when calling it repeatedly would overwhelm it or downstream resources.

| Model | Cost | Security | Operational Complexity | Noisy‑Neighbor Risk |
|-------|------|----------|-----------------------|---------------------|
| **Shared DB, shared schema (row‑level tenant ID)** | Lowest – single DB instance, one set of licenses, maintenance. | Moderate – tenant isolation via column; risk of accidental cross‑tenant queries or privilege escalation. | Low – one schema, one set of backups. | High – a noisy tenant can consume CPU, IO, and lock resources affecting all tenants. |

**AA8 – Hard**  
**Eventual vs. Strong Consistency**  
- **Strong consistency** guarantees that any read sees the most recent write; changes are atomic across all replicas.  
- **Eventual consistency** allows temporary divergence; replicas converge after a period of no updates.  

**Inventory “never oversell” design**  
- **Consistency model:** Strong (or at least **serializable**) consistency is required to guarantee that inventory counts cannot be double‑booked.  
- **Data store:** A transactional relational DB (PostgreSQL, MySQL) with row‑level locking, or a NoSQL store that supports ACID transactions (e.g., CockroachDB, Spanner). For scale, consider a sharded DB with distributed locking (e.g., Redis + DB).  
- **Patterns:**  
  - **Optimistic concurrency control** with version fields (`UPDATE ... WHERE version = ?`).  
  - **Saga with compensation** for inventory deduction across services, ensuring atomic “reserve‑then‑commit”.  
  - **Idempotent consumers** to safely retry messages without double‑deduction.  
  - **Read‑through/write‑through caching** with proper invalidation to keep inventory UI up‑to‑date while preserving DB consistency.  

**Result:** The system can safely handle high concurrency, prevent oversell, and still scale by sharding or using read replicas for reporting.

**AA9 – Hard**  
**Sidecar proxy:** A lightweight process that runs alongside each application container, handling networking, observability, and security for that service. It isolates cross‑cutting concerns from business logic.  

**Envoy in Istio:**  
- **Data plane:** Each workload’s sidecar (Envoy) intercepts all inbound/outbound traffic, performing mTLS, load balancing, circuit breaking, and telemetry.  
- **Control plane:** Istio components (Pilot for service discovery & routing config, Citadel for CA & mTLS certificates, Galley/istiod for validation) push configuration to all sidecars via SDS (Secret Discovery Service).  

**mTLS between sidecars vs. app‑level TLS:**  
- **App‑level TLS** encrypts only the application’s own traffic (e.g., service‑to‑service gRPC). It can be disabled per service, and keys are often embedded in code.  
- **Sidecar mTLS** provides **service‑to‑service** encryption automatically, with mutual authentication based on the service identity (SPIFFE). It prevents lateral movement even if a compromised container can read its own TLS keys, because traffic never leaves the sidecar unencrypted.

6. **Repeat** for other domains (Orders, Inventory, etc.), building a mesh of .NET 8 services while the monolith shrinks to a legacy “shadow” system.

- **Layer 4 (Transport) load balancing:** Works at the TCP/IP level, routing based on IP address and port (e.g., round‑robin).  
- **Layer 7 (Application) load balancing:** Inspects the full HTTP request (headers, URI, host) and can route based on path, host, or custom logic (e.g., NGINX, HAProxy).  

**Use case for Layer 7:** Routing `/api/v1/` to one service and `/api/v2/` to another, or performing header‑based routing, content‑based routing, or TLS SNI inspection.

**AA14 – Easy**  
A **message queue** (e.g., RabbitMQ) is a durable, first‑in‑first‑out (FIFO) store where producers push messages and consumers pull them, supporting acknowledgments and routing keys.  

- **RabbitMQ vs. Kafka:**  
  - **RabbitMQ** – traditional queue, low latency, complex routing (headers, topics), guaranteed delivery, suitable for point‑to‑point or pub/sub with small‑to‑medium throughput.  
  - **Kafka** – log‑structured, high‑throughput, partitioned commit log; provides consumer groups and retention policies; better for streaming pipelines and back‑filling.  

**When to pick each:**  
- Choose **RabbitMQ** for request‑reply patterns, RPC, or when you need sophisticated routing and guaranteed message delivery with lower latency.  
- Choose **Kafka** for high‑volume event streaming, audit trails, and scenarios where you need to replay historical data or have many consumers.

**AA15 – Easy**  
A **container** packages an application with its runtime, system tools, libraries, and configuration into an isolated unit that shares the host OS kernel.  

- **Difference from a VM:** VMs emulate a full OS and hardware, incurring higher overhead and slower startup. Containers are lightweight, start in seconds, and pack more density.  

**Why containers are popular for microservices:**  
- **Portability** – “write once, run anywhere.”

**AA18 – Medium**  
**Bulkhead pattern:** Isolates critical resources so that failures in one component do not affect others, akin to naval bulkheads that prevent a flooded compartment from sinking the whole ship.  

**Relation to resource isolation:** In microservices, bulkheads prevent a noisy or failing service from consuming CPU, memory, or I/O that would starve other services.  

**Concrete implementation example:**  
- **Thread‑pool bulkheads:** Create separate `ExecutorService` pools for “high‑priority” (e.g., payment processing) and “best‑effort” (e.g., logging) tasks, each with its own max‑size limits.  
- **Separate deployment groups:** Run critical services on dedicated VM/host clusters, while non‑critical services share a lower‑tier pool, ensuring resource guarantees.

**AA19 – Hard**  
**Operational Transformation (OT) vs. CRDTs**  

| Aspect | Operational Transformation (OT) | Conflict‑Free Replicated Data Types (CRDT) |
|--------|--------------------------------|-------------------------------------------|
| **Consistency guarantees** | Strong eventual consistency; requires central coordination to transform concurrent edits. | Strong eventual consistency; mathematically guaranteed convergence without coordination. |
| **Latency** | Requires real‑time communication between replicas to apply transformations; can be higher under network partitions. | Low latency; each replica can apply local operations independently. |
| **Complexity** | Complex algorithm, especially for nested structures; needs careful design of transformation functions. | Simpler data structures (e.g., RGA, G-Set, OR‑Set) but limited to certain data shapes. |
| **Offline support** | Poor; OT relies on real‑time sync to resolve conflicts. | Excellent; offline edits are applied locally and merged later. |

**Choice for offline editing:** Use **CRDTs** because they allow each client to edit independently and converge later without a central server, providing true offline capability and simpler conflict resolution.

**AA20 – Hard**  
**Distributed tracing challenges in a polyglot ecosystem:**  

- **Context propagation:** Different languages/frameworks use different header formats (W3C Trace Context, B3). Need a unified injector/extractor or a proxy that translates between them.  
- **Sampling strategies:**  
  - **Head‑based sampling:** Decision made at the entry point; may miss rare errors deep in the graph.  
  - **Tail‑based sampling:** Record all traces and later sample; requires storage for massive data.  
- **Trace storage & querying:**  
  - **Jaeger:** Open‑source, spans stored in Cassandra/ES, good for moderate scale.  
  - **Tempo (Grafana):** Uses compressed OTLP, stores in object storage, scales to high trace volumes.  
- **Asynchronous messaging interaction:** When a request passes through Kafka, the trace context must be injected into message headers (e.g., using W3C Trace Context) and extracted by the consuming service.  

**Ensuring trace continuity through Kafka:**  
1. **Inject** the current trace context into Kafka message headers (using a producer interceptor).  
2. **Configure** consumer applications to extract the headers and continue the span.  
3. **Use** a tracing‑aware Kafka client library (e.g., `kafka-python` with OpenTelemetry) or a sidecar proxy that intercepts produce/consume.  
4. **Validate** that the span ID is preserved across partitions (header injection is partition‑agnostic).

**OP3 – Medium**  
**3‑tier network architecture:**  
- **Core layer:** High‑speed backbone, responsible for routing between distribution switches.  
- **Distribution (aggregation) layer:** Policy enforcement, VLAN aggregation, and uplinks to core.  
- **Access layer:** End‑hosts (servers, workstations) connect here; provides PoE, port security.  

**Why leaf‑spine is preferred:**  
- **Reduced latency:** Two‑hop topology (leaf ↔ spine) vs. three‑hop (core‑distribution‑access).  
- **Scalability:** Adding new leaf switches does not require redesigning the core.  
- **Redundancy & resilience:** Multiple equal‑cost paths, eliminating single‑point failures.  
- **Simplified spanning‑tree:** Fewer hops reduce broadcast domains and STP convergence time.  

**Problem solved:** Traditional 3‑tier suffers from bottleneck at the core and long convergence times; leaf‑spine eliminates these by providing a non‑blocking, mesh‑like fabric.

**OP4 – Medium**  
**Highly available Proxmox cluster with shared storage:**  

- **Node count:** Minimum 3 nodes for quorum (odd number).  
- **Quorum:** Use `corosync` with `two‑out‑of‑three` voting; enable `quorum` with `expected votes`.  
- **Fencing (STONITH):** Configure IPMI/DRAC power‑off fencing; enable `fence` agents for each node.  
- **Shared storage options:**  
  - **Ceph:** Deploy Ceph OSDs on cluster nodes; use `ceph` as a storage backend for VMs (Proxmox integrates via `ceph` storage plugin). Provides replication, erasure coding, and scaling.  
  - **iSCSI:** Use an iSCSI target (e.g., Open-iSCSI) to present LUNs; Proxmox can attach iSCSI disks. Simpler but less granular than Ceph.  
  - **NFS:** Export a directory via NFS; Proxmox can mount NFS shares as storage. Good for small environments, but NFS is a single point of failure unless HA NFS is used.  

- **During node failure:**  
  1. **Detection:** Corosync detects loss of heartbeat.  
  2. **Quorum check:** If enough nodes remain, the cluster stays active.  
  3. **Fencing:** The surviving nodes issue a STONITH command to power‑off the failed node, preventing split‑brain.  
  4. **Failover:** VM resources on the failed node are restarted on remaining nodes (if HA is enabled).  
  5. **Storage:** Ceph maintains data replication; iSCSI/NFS LUNs may be re‑mounted if the storage backend itself is HA.

**OP5 – Medium**  
**VLAN trunking & 802.1Q:**  
- **VLAN trunking** allows a single physical link to carry traffic for multiple VLANs.  
- **802.1Q** adds a 4‑byte tag to Ethernet frames containing VLAN ID (VID) and priority.  

**Single NIC on 3 VLANs (Linux):**  
1. **Create a bridge** (e.g., `br0`) and attach the NIC to it.  
2. **Add VLAN interfaces** using `ip link add link eth0 name eth0.100 type vlan id 100` (repeat for 200, 300).  
3. **Assign each VLAN interface to the bridge**: `bridge fdb add ...` (or simply `bridge link set dev eth0.100 master br0`).  
4. **Configure IP addresses** on each VLAN interface (`ip addr add 192.168.100.10/24 dev eth0.100`).  
5. **Enable VLAN filtering** on the bridge: `bridge vlan add dev eth0 vid 100 pvid untagged` (repeat for each VID).  

Result: The single NIC can now carry traffic for VLAN 100, 200, 300 simultaneously.

**OP6 – Medium**  
**RAID levels overview:**  

| RAID | Data protection | Parity | Write penalty | Typical use |
|------|----------------|--------|---------------|-------------|
| **RAID 1** | Mirror (2 copies) | – | 2× writes | Small, critical data |
| **RAID 5** | Striped + distributed parity | 1 disk worth | 2× writes | Good balance, up to 1 disk failure |
| **RAID 6** | Striped + double parity | 2 disks worth | 4× writes | Tolerates 2 disk failures |
| **RAID 10** | Mirror + stripe | – | 2× writes | Best performance, tolerates up to N/2 failures |
| **RAID Z2 (ZFS)** | Striped + double parity (similar to RAID 6) | 2 disks worth | 4× writes | ZFS features (snapshots, self‑healing) |

**Scenario:** 6 drives, need performance, capacity, fault tolerance for a database server.  

**Recommendation:** **RAID 10** (3 mirrored pairs striped).  
- **Performance:** Excellent read/write (parallel reads/writes across mirrors).  
- **Capacity:** 3 TB usable out of 6 TB (50 % overhead).  
- **Fault tolerance:** Can survive up to 3 drive failures (any one from each mirror pair).  
- **Database workloads** benefit from low write latency and high IOPS.

**OP7 – Hard**  
**DNS architecture for 500‑person enterprise:**  

- **Internal AD DNS:** Serves as authoritative zone for `corp.example.com`. Provides dynamic updates for AD objects, SRV records, and split‑horizon data.  
- **DMZ authoritative servers:** Separate DNS servers (e.g., BIND or Windows DNS) for public zones (`example.com`, `mail.example.com`). Configured with **split‑horizon** – internal queries get internal A/AAAA records, external queries get public records.  
- **Recursive resolvers:**  
  - **Internal:** Forwarders to external root hints (e.g., 8.8.8.8) for external lookups.  
  - **DMZ:** May act as forwarders to upstream public DNS for external queries.  
- **Forwarders & conditional forwarding:**  
  - Internal DNS forwards `*.example.com` to the DMZ authoritative servers (conditional forwarding).  
  - DMZ DNS forwards external zones to upstream public resolvers.  
- **DNSSEC on external zone:** Sign the public zone with a DNSSEC chain (KSK/ZSK). Use DS records in the parent zone (e.g., .com).  
- **Laptop moving between office and VPN:**  
  - **Office:** Laptop queries internal AD DNS (via local DNS server). Receives internal records (e.g., `fileserver.corp.example.com`).  
  - **VPN:** VPN client adds its own DNS (often the corporate DNS) to the routing table; laptop queries the same internal DNS via the VPN tunnel, preserving split‑horizon behavior.  
  - **Fallback:** If internal DNS unreachable, VPN may push upstream DNS (e.g., Google DNS) for external resolution.  

**Result:** Internal users get fast, secure name resolution with AD integration; external clients receive only public records, protected by DNSSEC.

**OP8 – Hard**  
**PKI chain of trust:**  

1. **Root CA (offline):** Holds the most trusted private key; signs certificates for subordinate CAs only. Kept offline to minimize exposure.  
2. **Subordinate/issuing CA:** Online, signs end‑entity certificates (servers, users). Its certificate is signed by the root.  
3. **End‑entity certificates:** Issued to resources (e.g., web servers, AD objects).  

**CRL vs. OCSP:**  
- **CRL (Certificate Revocation List):** Periodic list of revoked serial numbers; simple but can be stale.  
- **OCSP (Online Certificate Status Protocol):** Real‑time query per certificate; more up‑to‑date but adds latency and depends on OCSP responder availability.  

**Certificate templates & auto‑enrollment:**  
- Define usage (e.g., Server Authentication, Client Authentication), key length, validity, enrollment rights via Group Policy (Windows) or SCEP (Cisco).  
- Enable **auto‑enrollment** so domain‑joined machines automatically request/renew certificates based on template policies.  

**Compromised CA impact:**  
- **Subordinate CA compromise:** Revoke its certificate, issue a new subordinate CA, and re‑issue all certificates signed by the old one. Impact limited to certificates issued by that CA.  
- **Root CA compromise:** Catastrophic; all certificates anchored by that root become untrustworthy. Must replace the root, publish a new trust anchor, and revoke/re‑issue every certificate issued by it (often impractical).

**WAN options comparison (5 remote offices, 50 users each, latency‑sensitive VoIP):**

| **MPLS** | High (circuit‑based) | Very high (guaranteed QoS) | Low (dedicated paths) | Moderate‑high (carrier‑managed) | Strong (encrypted optional) |

**OP11 – Medium**  
**LVM vs. LVM‑Thin vs. ZFS:**  

- **LVM (Logical Volume Manager):** Creates physical volumes → volume groups → logical volumes. Fixed provisioning; you must allocate space upfront.  
- **LVM‑Thin:** Thin provisioning on top of LVM; you create a thin pool and logical volumes that consume space on demand, allowing over‑subscription.  
- **ZFS:** Combined file system and volume manager; uses copy‑on‑write, snapshots, clones, and built‑in data integrity (checksums, RAID‑Z).  

**When to use each:**  
- **LVM** for simple resizing of partitions, moderate workloads.  
- **LVM‑Thin** when you need flexible allocation (e.g., many small VMs with uncertain storage needs).  
- **ZFS** for data‑intensive workloads requiring snapshots, replication, and high reliability (e.g., backups, media servers).  

**Snapshot semantics:**  
- **LVM:** Snapshots are read‑only views of the logical volume at creation time; modifications go to the original volume; snapshot size is small but can consume space as the original changes.  
- **LVM‑Thin:** Same snapshot behavior, but thin provisioning can lead to space exhaustion if many snapshots are taken.  
- **ZFS:** Snapshots are essentially pointers; they consume minimal space initially and can be cloned; they are immutable and can be taken frequently.

**OP12 – Hard**  
**Stretch cluster / DR for 3‑node Proxmox with Ceph:**  

- **Design:** Deploy a fourth “tiebreaker” node in a third site (or cloud) to break ties during split‑brain. Use **Ceph CRUSH rules** to place OSDs across sites (e.g., `crush rule` with `bucket` types: rack → row → site).  
- **Monitor placement:** Ensure the **monitor (mon)** quorum includes at least two nodes; place one mon in each site, with the tiebreaker as a third.  
- **Network latency:** Keep inter‑site latency < 5 ms for Ceph OSD replication to avoid performance degradation; use dedicated low‑latency links (e.g., 10 GbE or 40 GbE).  
- **Split‑brain prevention:** The tiebreaker node provides a decisive vote; Ceph’s `mon` quorum requires a majority (e.g., 2 of 3). If a site loses connectivity, the remaining two nodes can still form a quorum, but the tiebreaker ensures a consistent view.  

**Why 2‑site Ceph is generally a bad idea without a tiebreaker:**  
- With only two sites, a network partition can leave each side with a single monitor; both think they have a quorum, leading to split‑brain and data inconsistency. A third “tiebreaker” (or a cloud-based monitor) is needed to break the tie and maintain a single source of truth.

**OP18 – Medium**  
**Active‑passive vs. active‑active clustering:**  

- **Active‑passive:** Only the primary node serves requests; the secondary is idle, ready to take over on failure. Simpler, but underutilizes resources.  
- **Active‑active:** Both nodes serve traffic, often using data replication; provides higher utilization and reduced failover time.  

**Implementing HA for PostgreSQL using Pacemaker/Corosync:**  

1. **Resources:** Define a `postgresql` service resource with `op` primitives (start, stop, monitor).  
2. **Fencing (STONITH):** Configure IPMI/DRAC fence agents for each node; enable `stonith` in `pacemaker`.  
3. **Virtual IP:** Create a floating IP resource (`ipaddr2`) that moves with the active node.  
4. **Data replication:** Use `pg_rewind` or `repmgr` for synchronous replication; Pacemaker can monitor replication status via a custom script.  
5. **Failover behavior:** On node failure, Pacemaker demotes the failed node, issues STONITH, promotes the standby node, and moves the virtual IP to the new active node.  

Result: Seamless fail‑over with minimal downtime and data consistency.

**OP19 – Hard**  
**Backup & recovery strategy for 50‑server on‑prem environment:**  

- **3‑2‑1 rule:** 3 copies of data, on 2 different media types, 1 copy off‑site.  
- **RPO/RTO requirements:** Define acceptable data loss (RPO) and downtime (RTO) per workload (e.g., RPO ≤ 15 min, RTO ≤ 2 h for critical apps).  
- **Backup types:**  
  - **Full:** Baseline, used for quick restores.  
  - **Incremental:** Backs up changes since last backup.  
  - **Differential:** Backs up changes since last full; faster restore than incremental.  
- **Deduplication:** Apply at source or target to reduce storage footprint, especially for virtual machine images and file servers.  
- **Storage media:**  
  - **Disk (NAS/SAN)** for short‑term, fast restores.  
  - **Tape or cloud** for long‑term, off‑site copies.  
- **Immutable backups:** Use write‑once storage (e.g., WORM S3 buckets, tape) to protect against ransomware deletion.  
- **Testing restores:** Perform quarterly restore drills for critical systems; document procedures and success criteria.  

**Backup vs. Disaster Recovery (DR):**  
- **Backup** = copying data for restoration after accidental loss, corruption, or ransomware.  
- **DR** = holistic plan (infrastructure, applications, sites, processes) to restore entire services after a major outage (e.g., site failure), often involving failover, replication, and coordinated communication.

**OP20 – Hard**  
**802.1X (Port‑Based Network Access Control) workflow:**  

1. **Supplicant:** Client device (e.g., Windows laptop, IP‑phone) that initiates authentication.  
2. **Authenticator:** Managed switch port that blocks traffic until authentication passes.  
3. **Authentication Server:** RADIUS server (e.g., FreeRADIUS, Windows NPS) that validates credentials.  

**EAP methods:**  
- **EAP‑TLS:** Mutual TLS certificates; strong mutual authentication.  
- **PEAP (EAP‑MSCHAPv2):** Tunneled authentication; password‑based, widely supported.  

**RADIUS:** Handles authentication, authorization, and accounting (AAA). The switch forwards EAP packets to the RADIUS server.  

**Dynamic VLAN assignment:** After successful auth, the switch can tag the port’s traffic with a VLAN ID (e.g., `vlan‑user123`) to isolate user traffic.  

**Device fails authentication:** The authenticator places the port in a “guest” or “unauthorized” state, allowing only limited traffic (e.g., DHCP, DNS) to reach the RADIUS server for re‑attempt.  

**MAB (MAC Authentication Bypass):** For devices lacking 802.1X support (e.g., printers), the switch uses the device’s MAC address as a “username” and maps it in RADIUS (or local) database to authorize access, bypassing EAP.
