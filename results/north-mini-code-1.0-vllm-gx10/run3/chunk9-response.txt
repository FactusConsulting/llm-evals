## SC1 – Broken Deployments After Cluster Upgrade  

### SC1‑A – Why the pods crash after the upgrade  

| Factor | Explanation |
|--------|-------------|
| **PodSecurity Standard change** | The cluster moved from **Baseline** to **Restricted** at the namespace level. `Restricted` enforces: <br>• `runAsNonRoot: true` **and** a non‑root `runAsUser` must be set.<br>• No privileged containers, no hostPath, no allowPrivilegeEscalation, etc. |
| **securityContext.runAsNonRoot: true** | The pod spec says the container **must not run as root**. |
| **Missing explicit `runAsUser`** | No `runAsUser` is defined, so Kubernetes falls back to the **image’s `USER`** (or the default root user). |
| **Image USER defaults to root** | The new base image `cgr.dev/chainguard/static:latest` declares `USER root`. Because `runAsUser` is absent, the runtime runs as root → violates the `runAsNonRoot` requirement. |
| **Admission controller rejection** | The `PodSecurity` admission controller rejects the pod (or evicts it) because the pod does **not** satisfy the `Restricted` policy. The pod is repeatedly created → `CrashLoopBackOff`. |
| **Why it worked before** | With `Baseline` the controller only checked `runAsNonRoot: true` (no `runAsUser` required). The root‑user image was allowed, so pods ran fine. |

**Bottom line:** The upgrade tightened the PodSecurity policy, and the combination of `runAsNonRoot:true` **without** an explicit non‑root `runAsUser` makes the pod non‑compliant when the image’s `USER` is root.

## SC2 – Cross‑Region Database Failover Gone Wrong  

### SC2‑A – Stale data after promotion  

* **Replication lag implication** – When a read replica in `eu-west-1` is promoted, any writes that occurred **after** the last successful WAL ship from `us-east-1` are lost. Cross‑region streaming replication is **asynchronous**, so there is a non‑zero lag (network RTT + apply time).  
* **PostgreSQL streaming replication across regions** – The primary continuously ships WAL segments to the replica via `pg_receivewal`. The replica applies them locally. Because of latency (≈ 85 ms one‑way), the replica can be **seconds to minutes** behind.  
* **Data‑loss scenarios** – <br>1. **Network partition** – WAL may be buffered on the primary and never reach the replica. <br>2. **Replica overload** – Slow WAL apply (disk I/O, CPU) increases lag. <br>3. **Promotion while lag > 0** – Any unapplied transactions are discarded.  
* **Quantifying the loss window** – ```sql
SELECT EXTRACT(EPOCH FROM now() - pg_last_xact_replay_timestamp()) AS replication_lag_seconds;
``` <br>Also query `pg_stat_replication` for `replay_lag` and `write_lag`. <br>Check `pg_replication_slots` for slot lag (`confirmed_flush_lsn`). <br>Monitor `pg_walreceiver_status` for `receive_start_lsn` vs `replay_end_lsn`.  

The observed **stale data** is the direct result of this lag window.

### SC2‑B – Terraform state import & detach workflow  

Assume the old instance is `aws_db_instance.primary` and the promoted replica is `aws_db_instance.dr`.

```bash
# 1. Export the replica's ARN (or use the resource address)

    --db-instance-identifier <dr-instance-id> \
    --query "DBInstances[0].DBInstanceArn" --output text)

# 2. Import the replica into Terraform state (replace <resource-address> with the exact address in your .tf)

# 3. Remove the old primary from state (so Terraform no longer manages it)

# 5. Run plan/apply to sync the new state (no destroy/recreate should happen)

terraform apply
```

*Key points*  

* `terraform import` **does not** create a new resource; it just adds the existing DB to state.  
* `terraform state rm` **detaches** the old resource, preventing Terraform from trying to delete/recreate it.  
* After updating references, `terraform apply` will only modify the new resource’s attributes (e.g., endpoint, tags) – no infrastructure churn.

### SC3‑B – Script to compare base‑image digests & list layers  

```bash
#!/usr/bin/env bash
set -euo pipefail

# ---- Configuration ----
ECR_REPO="123456789.dkr.ecr.us-east-1.amazonaws.com/api-gateway"
IMAGE_TAG="v2.4.1"
KNOWN_GOOD_LAYERS_FILE="/tmp/known_good_layers.txt"   # pre‑populated list of good layer digests

# ---- 1. Fetch current image manifest & layers ----
MANIFEST=$(aws ecr batch-get-image \
    --repository-name "${ECR_REPO}" \
    --image-ids imageTag="${IMAGE_TAG}" \
    --query 'images[0].imageManifest' \
    --output text)

# Extract layer digests (Docker Image Manifest V2, Schema 2)
LAYER_DIGESTS=$(echo "$MANIFEST" | jq -r '.layers[].digest')

# ---- 2. Get upstream node:20-slim digest from Docker Hub API ----
UPSTREAM_DIGEST=$(curl -s "https://hub.docker.com/v2/repositories/library/node/tags/20-slim/" |
    jq -r '.images[0].digest')

# ---- 3. Get the digest used in the CI build log (example: stored in a file) ----
CI_BASE_DIGEST=$(grep "node:20-slim@" /path/to/ci/build.log | head -1 | cut -d'@' -f2)

# ---- 4. Compare ----
echo "=== Base Image Comparison ==="
echo "CI build used digest : $CI_BASE_DIGEST"
echo "Current upstream digest: $UPSTREAM_DIGEST"
if [[ "$CI_BASE_DIGEST" == "$UPSTREAM_DIGEST" ]]; then
    echo "✓ Base image digest matches upstream."
else
    echo "✗ BASE IMAGE MISMATCH – possible compromise!"
fi

# ---- 5. List layers and flag unknown ones ----
echo -e "\n=== Layer Analysis ==="
echo "Total layers: $(echo "$MANIFEST" | jq '.layers | length')"
echo "Layer digests:"
echo "$LAYER_DIGESTS" | while IFS= read -r layer; do
    if [[ " $layer " == *" $CI_BASE_DIGEST "* ]]; then
        echo "  $layer (expected)"
    else
        echo "  $layer (UNEXPECTED)"
    fi
done > /tmp/current_layers.txt

# ---- 6. Flag any layer not in known‑good list ----
echo -e "\n=== Unexpected layers (not in known‑good) ==="
comm -23 <(sort /tmp/current_layers.txt | cut -d' ' -f2) \
         <(sort "$KNOWN_GOOD_LAYERS_FILE") || true
```

**What the script does**

* Pulls the current image manifest from ECR.  
* Queries Docker Hub for the **official** `node:20-slim` digest.  
* Reads the digest recorded in the CI build log (or a stored file).  
* Compares the two – a mismatch signals a possible base‑image substitution.  
* Lists all layers of `api-gateway:v2.4.1` and marks any that differ from the known‑good list.  

Run the script in a secure CI environment (e.g., a dedicated runner) and store its output in your incident‑response bucket.

  metadata {
    name      = "uploads-pvc"
    namespace = "default"   # adjust as needed
  }
  spec {
    access_modes = ["ReadWriteMany"]
    resources {
      requests = {
        storage = var.storage_capacity
      }
    }
    storage_class_name = nfs_csi_storage_class.uploads.metadata[0].name
    volume_name = kubernetes_persistent_volume.uploads_pv.metadata[0].name

```

**Why `ReadWriteMany`?**  
The monolith writes uploaded files to `/data/uploads`. Multiple pods (e.g., multiple replicas for scaling) may need to read/write the same files simultaneously. `ReadWriteMany` satisfies that requirement, allowing the shared NFS export to be accessed concurrently.

### SC4‑C – Phased migration using the Strangler Fig pattern  

| Phase | Goal | Actions | Traffic handling | IBM MQ handling | Rollback |
|-------|------|---------|------------------|----------------|----------|
| **Phase 1 – Lift‑and‑Shift** | Get the monolith running on K8s with minimal changes. | • Deploy the existing Docker image to K8s (same JVM opts). <br>• Expose service via **Ingress** (port 8080). <br>• Keep F5 as the **frontend** (still routing to old pods). <br>• Mount the NFS PVC for uploads. | Traffic stays **entirely** on F5 → old servers (no change). | MQ sidecar runs in K8s; update connection string to point to MQ service (same host). | If pods fail, revert to old deployment (`kubectl delete deployment monolith-k8s`). |

| **Phase 3 – Full cutover** | Shut down legacy bare‑metal fleet. | • Disable F5 pool for old servers (remove from pool). <br>• Update DNS/Route53 to point to K8s Ingress. <br>• Run **canary** with auto‑scaling; monitor latency, error rates. | All traffic goes to K8s Ingress → monolith (still monolithic) + any migrated services. | All MQ clients now use the K8s sidecar (if monolith still uses MQ, keep same connection). | If metrics breach thresholds (latency > 2 s, error > 1 %), re‑enable old pool and roll back. |

* **Latency** – p99 < 2 s (target).  
* **Error rate** – < 0.1 % (5‑minute window).  
* **CPU/Memory** – < 80 % of limits.  
* **Availability** – > 99.9 % (SLO).  
* **Throughput** – ≥ 3 000 req/s (current load).

## SC5 – Mysterious Latency Spike in Microservices  

### SC5‑A – Systematic debugging approach  

1. **Istio telemetry** – Pull `istio-requests-total`, `istio_request_duration_seconds`, `istio_tcp_sent_bytes_total`. Look for spikes in `destination_service` `inventory-service`.  
2. **Kubernetes metrics** – `kube-state-metrics`, `node-exporter` metrics for CPU, memory, disk I/O on nodes hosting `inventory-service`.  
3. **Application logs** – Check `inventory-service` logs for long‑running queries, stack traces.  
4. **Distributed tracing** – Use **Jaeger** or **Zipkin**. Enable **B3** propagation. Query traces for the 14:00‑14:30 window, filter by `checkout-service → inventory-service`.  
5. **Envoy sidecar metrics** – `envoy_cluster_upstream_rq_time` (latency distribution), `envoy_cluster_upstream_rq_active` (queue length), `envoy_listener_manager_listener_stats` for listener drops.  

**Distinguishing proxy vs upstream**  

* **Proxy‑level queueing** → high `envoy_cluster_upstream_rq_active` and a **bimodal** latency distribution (many fast requests, many delayed). The `istio_request_duration_seconds` histogram shows a spike at the **proxy** level (the “outbound” side).  
* **Upstream service latency** → `inventory-service` application metrics (`jvm_memory_used`, `db_connection_count`) show high CPU or lock wait; the trace shows the span inside `inventory-service` (not just the proxy).  

**Queries**  

```bash
# Envoy proxy queue length
curl -s http://prometheus:9090/api/v1/query?query=envoy_cluster_upstream_rq_active
# Inventory service DB wait
curl -s http://prometheus:9090/api/v1/query?query=db_wait_seconds_total
```

### SC5‑B – SQL diagnostic & Go circuit‑breaker  

**SQL diagnostic (PostgreSQL)** – Shows lock holders, waiters, and the blocking query:

```sql
-- 1. Identify the blocking PID
SELECT
    l.blocking_pid,
    l.pid,
    l.query,
    l.state,
    l.wait_event_type,
    l.wait_event,
    l.lock_type,
    l.mode,
    l.granted
FROM pg_locks l
JOIN pg_stat_activity a ON a.pid = l.pid
WHERE l.blocking_pid IS NOT NULL;

-- 2. Get the exact query text of the holder
SELECT pid, query FROM pg_stat_activity
WHERE pid = <blocking_pid>;

-- 3. List waiters (processes waiting on the same relation)
SELECT
    a.pid,
    a.query,
    a.state,
    a.wait_event_type,
    a.wait_event
FROM pg_stat_activity a
JOIN pg_locks l ON a.pid = l.pid
WHERE l.granted = FALSE
  AND l.relation = <relation_oid>;  -- e.g., stock_levels
```

*Replace `<blocking_pid>` and `<relation_oid>` with values from the first query.*

**Go circuit‑breaker snippet (sony/gobreaker)**  

```go
package checkout

import (
    "context"
    "time"

    "github.com/sony/gobreaker"
)

type InventoryClient struct {
    cb *gobreaker.CircuitBreaker
    // HTTP client, etc.
}

func NewInventoryClient() *InventoryClient {
    settings := gobreaker.Settings{
        Name:        "InventoryService",
        Timeout:     5 * time.Minute,
        // Trip after 5 failures in 10 seconds
        Interval:    10 * time.Second,
        MaxRequests: 5,
        ReadyToTrip: func(counts gobreaker.Counts) bool {
            return counts.ConsecutiveFailures > 5
        },
        OnStateChange: func(name string, from gobreaker.State, to gobreaker.State) {
            // log state changes
        },
    }
    return &InventoryClient{cb: gobreaker.NewCircuitBreaker(settings)}
}

func (c *InventoryClient) GetInventory(ctx context.Context, itemID string) (*InventoryResponse, error) {
    // Wrap the actual HTTP call with the circuit breaker
    resp, err := c.cb.Execute(func() (interface{}, error) {
        // actual HTTP request (e.g., using http.Client)
        req, _ := http.NewRequestWithContext(ctx, http.MethodGet,
            fmt.Sprintf("http://inventory-service/v1/inventory/%s", itemID), nil)
        resp, err := http.DefaultClient.Do(req)
        if err != nil {
            return nil, err
        }
        defer resp.Body.Close()
        if resp.StatusCode != http.StatusOK {
            return nil, fmt.Errorf("inventory service returned %d", resp.StatusCode)
        }
        var inv InventoryResponse
        if err := json.NewDecoder(resp.Body).Decode(&inv); err != nil {
            return nil, err
        }
        return &inv, nil
    })

    if err != nil {
        return nil, err
    }
    return resp.(*InventoryResponse), nil
}
```

The circuit breaker will **open** after 5 consecutive failures, preventing further calls while the inventory reconciliation is holding locks.

### SC5‑C – Architectural solution to eliminate the problem  

| Aspect | Solution |
|--------|----------|
| **Separate read/write paths** | Deploy a **CQRS** pattern: <br>• **Command side** (writes, reconciliation) uses a dedicated DB instance / read‑replica. <br>• **Query side** (checkout) reads from a **read‑replica** that is never written by the reconciliation job. |
| **Read replica for reconciliation** | Create a PostgreSQL **hot standby** (or Aurora Replica) that the CronJob writes to, while the serving pods read from a **different replica**. This isolates lock contention. |
| **Bulkhead isolation** | Use **connection pooling** with separate pools: <br>• `HikariCP` pool for serving pods (size = concurrent pods). <br>• Separate pool for the reconciliation CronJob (size = 1‑2). <br>Implement **DataSource** per pool. |
| **CronJob scheduling** | Move the reconciliation to a **low‑traffic window** (e.g., 02:00‑03:00 UTC) or run it **continuously** with incremental updates (e.g., delta sync) to avoid a 30‑second lock. |
| **Kubernetes safeguards** | • **PodDisruptionBudget** for serving pods to prevent eviction during CronJob spikes. <br>• **ResourceQuota** in the namespace to limit CPU/memory for the CronJob, ensuring it cannot starve serving pods. |
| **Monitoring** | Add alerts for `pg_locks` growth, `inventory-service` latency > 500 ms, and `CronJob` runtime > 60 s. |

These changes make the latency spike a non‑issue because the serving path no longer contends for the same DB connections or locks.

## SC6 – Zero‑Trust Network Overhaul for a Hybrid Environment  

### SC6‑A – Identity & access layer design  

| Component | Implementation |
|-----------|----------------|
| **Workload identity** | Use **SPIFFE/SPIRE**: <br>• Deploy a **SPIRE server** in each environment (on‑prem, AWS, Azure). <br>• Agents inject **SPIFFE IDs** (`spiffe://example.org/ns/<ns>/sa/<sa>`) into pods via CSI or kubelet plugins. |
| **AWS integration** | Configure **IAM Roles for Service Accounts (IRSA)** for pods in EKS. The OIDC provider trusts the SPIRE trust domain; a pod’s `assume_role` is mapped via IAM policy. |
| **Azure integration** | Use **Azure AD Pod Identity** (or **Azure Managed Identity** with **Azure AD Pod Identity addon**) to assign managed identities to pods. The SPIRE agent signs a JWT that Azure AD validates. |
| **On‑prem PKI** | Run a **HashiCorp Vault** or **OpenVPN** PKI that issues **X.509 certificates** for service-to-service mutual TLS. SPIRE can also sign certificates for workloads. |
| **Cross‑environment federation** | Establish a **trust federation** via **JWT/OIDC**: <br>• SPIRE issues a **JWT** signed with its private key. <br>• Each cloud provider’s identity provider (AWS IAM, Azure AD) trusts the same SPIRE root CA. <br>• A workload in AWS can present its SPIFFE JWT to an on‑prem service; the service validates the JWT against the SPIRE public key (stored in a public KMS). No shared secrets. |
| **Policy enforcement** | Use **OPA Gatekeeper** or **Kyverno** to enforce that all inbound/outbound traffic is authenticated (`spiffe://` source) and authorized via **RBAC** (service accounts). |

### SC6‑C – Comparing connectivity options for the 1 Gbps VPN bottleneck  

| Option | Cost (approx.) | Bandwidth | Encryption | Failover | Fit in Zero‑Trust |
|--------|----------------|-----------|------------|----------|-------------------|
| **AWS Direct Connect (DX)** | $0.05‑$0.10/GB + $2‑$4k setup | 10 Gbps (or higher) | Layer 1 dedicated fiber (no encryption needed, but you can add IPSec) | Manual failover via DX gateway; can configure redundant circuits | Provides a **private, direct** path to AWS, simplifying trust boundaries. Requires on‑prem DX gateway and possibly a **CloudHub** or **Transit Gateway** for inter‑region mesh. |
| **Second VPN tunnel with ECMP** | $0.02‑$0.04/GB (per tunnel) | 1 Gbps per tunnel → 2 Gbps total (still < 10 Gbps) | IPSec (standard) | Automatic ECMP load‑balancing; if one tunnel fails, traffic shifts to the other. | Still relies on **public internet**; encryption is built‑in. Zero‑trust can be enforced at the workload level (mTLS) but the transport is less private. |
| **Hybrid mesh (Tailscale/Netbird)** | Free tier + $10‑$20/user (enterprise) | Up to 10 Gbps per link (depends on underlying NIC) | WireGuard (cryptography) + optional TLS | Built‑in mesh; if a node goes down, the mesh re‑routes automatically. | Provides **application‑level zero‑trust** (each node authenticated). Network is abstracted; you can still attach to AWS via **tailscale‑aws** integration (VPC‑endpoint). No need for separate VPN. |

**Recommendation**  

* **Short‑term**: Add a second VPN tunnel with ECMP to double bandwidth (2 Gbps) and gain simple failover.  
* **Medium‑term**: Deploy **AWS Direct Connect** for the production site (Chicago) to get 10 Gbps and reduce cost per GB.  
* **Long‑term**: Migrate to a **Tailscale/Netbird mesh** for the entire hybrid environment. It enforces zero‑trust at the host level, simplifies credential management, and can be integrated with AWS via VPC‑endpoint or Transit Gateway.  

**Routing changes per option**  

* **DX** – Add a new **DX gateway** and route on‑prem CIDR via the Transit Gateway attachment. Update BGP sessions.  
* **Second VPN** – Create a second **customer gateway** and IPSec tunnel; enable `bgp` with ECMP on the Transit Gateway.  
* **Mesh** – Install the mesh client on each on‑prem host and each cloud VM. The mesh creates overlay routes; you then advertise on‑prem CIDRs via the mesh’s own routing (no separate VPN).

## SC7 – CI/CD Pipeline Causing Production Drift  

### SC7‑A – How drift occurred & dangers  

| Drift source | How it happened | Why dangerous |
|--------------|----------------|---------------|
| **Manual `tofu apply`** | Developers ran `tofu apply` locally, bypassing CI. No state locking → concurrent runs could corrupt the S3 state file. | Corrupted state leads to **unpredictable infrastructure**, possible resource leaks, or accidental deletions. |
| **Diverged Helm values** | Staging/production values files were edited directly (`kubectl edit ConfigMap`, `helm upgrade --set ...`) without updating Git. | Drift means **Git is no longer the source of truth**, making audits impossible and causing “works in prod but not in repo” scenarios. |
| **Direct `kubectl edit` on ConfigMaps** | Three ConfigMaps edited via `kubectl edit` (bypassing Helm). | ConfigMap changes are **not versioned**, leading to inconsistent deployments and inability to roll back. |
| **Missing state locking** | OpenTofu state stored in S3 without versioning or locking. | Two engineers running `tofu apply` simultaneously can **overwrite each other’s changes**, leaving the state file in an inconsistent state. |

**Potential outage scenarios**  

* **Race condition** on state file → Terraform thinks a resource is already created and skips it, leaving a missing dependency → service fails to start.  
* **Stale ConfigMap** → application reads outdated config → functional regression.  
* **Missing security controls** → drift away from compliance (e.g., missing network policies).

## SC8 – Observability Stack Scaling Failure  

### SC8‑A – Diagnose each symptom  

| Symptom | Likely root cause | Confirmation metrics / queries |

### SC8‑B – Bash script for Prometheus cardinality report

promql() {
  curl -s "${PROMETHEUS_URL}/api/v1/query?query=$1" | jq -r '.data.result[]?.metric'
}

# 1. Total unique metric names
echo "=== Total unique metric names ==="
curl -s "${PROMETHEUS_URL}/api/v1/label/__name__/values" | jq -r '.data | length' > "$OUTPUT_FILE"

echo

  jq -r '.data[]' |

    series=$(curl -s "${PROMETHEUS_URL}/api/v1/series?match[]=${metric}" | jq '.data | length')

  done |
  sort -k2,2nr |
  head -20 |
  awk '{print $1, "(", $2, "series)"}' >> "$OUTPUT_FILE"

**Chargeback implementation steps**

4. **Exporters** – each service emits `tenant_id` label; ensure consistency.

## SC9 – Securing a Public‑Facing API After a Breach  

### SC9‑A – Vulnerability analysis & fixes  

| # | Vulnerability | OWASP API category | Blast radius | Fix (code / infra) |
|---|---------------|--------------------|--------------|--------------------|
| 1 | **BOLA** – users can access other users’ records by ID | **Broken Access Control** (A1) | Unauthorized read/write/delete of any user’s data → data breach, compliance violations. | Implement **object‑level permissions**: <br>```python
from rest_framework import generics, permissions
class UserResource(generics.RetrieveUpdateDestroyAPIView):
    queryset = User.objects.all()
    permission_classes = [IsOwnerOrAdmin]

    def get_object(self):
        obj = super().get_object()
        # Ensure the requesting user owns the object or is staff
        if self.request.user != obj and not self.request.user.is_staff:
            raise PermissionDenied("You do not own this resource.")
        return obj
``` |
| 2 | **Internal fields exposed** (created_by_employee_id, internal_notes) | **Information Exposure** (A2) | Leakage of sensitive business data, potential insider threats. | Use **serializers** with `read_only_fields` and **exclude** internal fields from public endpoints. <br>```python
class UserSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = ['id', 'username', 'email', 'public_profile']
        read_only_fields = ['created_by_employee_id', 'internal_notes']
``` |
| 3 | **No rate limiting** – 100k records extracted in 10 min | **Denial of Service** (A4) | Exhaust database, degrade service, possible data exfiltration. | Deploy **AWS WAF** rate‑limit rules (100 req/5 min per IP). <br>Application‑level: use **Django‑RL** or **django-ratelimit** decorators. |
| 4 | **API keys in query string & logged** | **Sensitive Data Exposure** (A2) | Keys can be captured in logs, enabling unauthorized access. | Move keys to **Authorization header** (`Authorization: ApiKey <key>`). <br>Remove query‑string param from code; configure ALB to **strip** query parameters before logging. <br>Rotate keys regularly and invalidate old ones. |

### SC9‑C – Defense‑in‑depth architecture & migration plan  

| Layer | Controls & Tools | Details |
|-------|------------------|---------|
| **Authentication** | Move API keys to **Authorization: ApiKey** header; rotate keys via **AWS Secrets Manager**; enforce **HTTPS** only. |
| **Authorization** | Implement **OAuth2** with **short‑lived JWTs** (access + refresh). Use **AWS Cognito** or **Keycloak** as OIDC provider. |
| **API Gateway** | Deploy **AWS API Gateway REST API** (or **Kong**) in front of the ALB. <br>• Centralized auth (OAuth2), rate‑limiting, request validation. <br>• Request transformation (strip query param, add header). |
| **Audit** | Enable **CloudTrail data events** for API Gateway calls; store logs in **S3** with **Object Lock**. |
| **Data protection** | **Field‑level encryption** for PII using **AWS KMS** with ** envelope encryption**; encrypt columns in the DB (e.g., via **pgcrypto** or application‑level encryption). |
| **Network** | **Security Groups** restrict ALB to only the API Gateway SG; **Network ACLs** deny inbound from internet. |
| **Monitoring** | **WAF logs** → **OpenSearch** for anomaly detection; **CloudWatch** alerts on failed auth attempts. |

**Migration from API keys to OAuth2 (zero‑downtime)**  

1. **Dual‑support phase** – Keep API key auth working while also accepting JWTs. The API gateway can have two authorizers: one for API keys (legacy) and one for OAuth2 (new).  
2. **Gradual client migration** – Provide documentation and a **migration guide** to existing consumers; offer a **transition period** (e.g., 30 days) where both auth methods are accepted.  
3. **Key rotation** – As soon as API key usage drops below a threshold (e.g., < 5 % of total requests), rotate all remaining keys, invalidate them, and delete from logs.  
4. **Fallback** – If OAuth2 validation fails, fall back to API key (only for legacy clients) but log the event for audit.  
5. **Deprecation** – After the transition window, remove the API key authorizer and enforce OAuth2 only.

## SC10 – Designing a Multi‑Cluster Disaster Recovery Platform  

### SC10‑A – Kubernetes multi‑cluster architecture  

| Approach | Description | RPO / RTO feasibility (12 ms latency, 200 TB MinIO) |
|----------|-------------|---------------------------------------------------|
| **Active‑passive with Velero backup/restore** | Primary cluster (Chicago) is active; DR cluster (Dallas) receives **Velero** backups (volume snapshots + Kubernetes resources). On failover, restore snapshots and spin up workloads. | **RPO** ≈ backup interval (e.g., every 5 min) → 5 min. **RTO** ≈ restore time (snapshot mount + pod startup) could be > 30 min for 200 TB. **Not meeting** 15 min RPO / 1 h RTO. |
| **Active‑active with service mesh (Istio multi‑cluster or Cilium Cluster Mesh)** | Both clusters run workloads; traffic is split via **global traffic policy**. State replication is continuous: <br>• **PostgreSQL** – logical replication (streaming) across regions. <br>• **Redis** – Redis Sentinel with cross‑region replication (Redis Enterprise or Twemproxy). <br>• **RabbitMQ** – mirrored queues/federation. <br>• **MinIO** – **Site Replication** (MinIO SR) with incremental sync. | **RPO** ≈ network latency + replication lag (≈ 100 ms). <br>**RTO** ≈ fail‑over via DNS/GSLB (seconds). <br>Meets 15 min RPO / 1 h RTO easily. |

**Replication strategies**

* **PostgreSQL** – Use **Patroni** with `synchronous_mode = true` and `synchronous_standby_names = 'dr-standby'`. Enable **streaming replication** with `wal_level = logical` and `max_replication_slots = 10`.  
* **Redis** – Deploy **Redis Sentinel** in each region; configure **cross‑region replication** using `replicaof` to the opposite region’s primary (or use **Redis Enterprise Global Data Replication**).  
* **RabbitMQ** – Enable **queue mirroring** (`policy: all`) and **federation** (upstream/downstream) between clusters for topics.  
* **MinIO** – Use **MinIO Site Replication** (SR) – a lightweight, asynchronous replication that syncs objects incrementally; configure **sync interval** to < 1 min for near‑real‑time consistency.  

**Recommendation** – **Active‑active with service mesh** is the only approach that satisfies the strict RPO/RTO while keeping latency low and providing seamless failover.

### SC10‑C – Automated failover orchestration  

**Sequence of events (Chicago → Dallas)**  

1. **Failure detection**  
   * **Health checks** – Deploy **Kubernetes DNS‑based** readiness probes on critical workloads (`checkout-service`, `inventory-service`).  
   * **Cluster health monitor** – Use **Prometheus** + **Alertmanager** to fire `ClusterDown` alert if > 30 % of nodes in Chicago are unreachable for > 30 s.  
   * **Site‑down criteria** – Combine node health, etcd quorum loss, and network connectivity to the Transit Gateway.  

2. **DNS / GSLB failover**  
   * Configure **AWS Route53** **Geolocation** or **AWS Global Accelerator** with health‑check monitors pointing to the Dallas Ingress (`*.k8s.prod.dallas.example.com`).  
   * When health check fails, Route53 returns the Dallas IP; external clients see instant traffic shift.  

3. **Patroni automatic promotion**  
   * Patroni’s DCS (`etcd`) detects loss of primary’s `postgresql` endpoint.  
   * Patroni promotes the **Dallas standby** to primary (sets `role: master`).  
   * Updates `postgresql` service endpoint in Kubernetes (`Endpoint` object) via a **Patroni‑Kubernetes** sync (Patroni can write to a ConfigMap that a Kubernetes controller updates).  

4. **Redis Sentinel failover**  
   * Sentinel monitors Dallas Redis instances; when Chicago master is unreachable, Sentinel promotes Dallas replica to master and updates Redis service DNS.  

5. **RabbitMQ queue mirroring & federation**  
   * Use **RabbitMQ policy** `ha-mode: all` for queues; ensure both clusters have mirrored copies.  
   * Configure **federation** (upstream Dallas → Chicago, downstream Chicago → Dallas) so messages are replicated even before failover.  

6. **MinIO site replication catch‑up**  
   * MinIO SR is continuous; after Chicago outage, Dallas replica will have the latest objects (replication lag < 1 min).  
   * Verify via `mc admin info` that object count matches.  

7. **Update OpenTofu state**  
   * Run a **GitLab CI job** that detects the new primary (`aws_db_instance.dr` is now active).  
   * Use `terraform state mv aws_db_instance.primary aws_db_instance.primary_dr` and `terraform state rm aws_db_instance.primary` (or import the new ARN).  
   * Commit the updated `terraform.tfstate` to S3 (with versioning) and push to Git.  

8. **Application re‑configuration**  
   * Deploy **deployment patches** (e.g., `kubectl set image deployment/checkout-service=...`) to ensure pods pick up the new DB endpoint (via environment variable `DB_HOST`).  
   * Use **rolling update** to avoid traffic spikes.  

**Split‑brain handling**  

* **Quorum check** – Both sites cannot simultaneously think they are primary. Use **etcd** with **Raft** across regions (or **Consul** with session TTL). The site that holds the lock (`/failover/lock`) proceeds; the other waits.  
* **Network isolation** – If the inter‑site link fails, each site’s health checks will fail; the **GSLB** will route traffic to the healthy site (Dallas) because Chicago health checks will be down.  

**Fail‑back procedure**  

1. **Health restoration** – Chicago nodes recover; Patroni detects a healthy primary again.  
2. **Drain Dallas** – Update Route53/Accelerator health checks to prefer Chicago; stop traffic to Dallas.  
3. **Promote Chicago** – Patroni on Chicago promotes back to master (synchronizes from Dallas replica).  
4. **Resync replication slots** – Ensure Dallas standby slots are recreated.  
5. **MinIO sync** – Run `mc mirror` from Dallas to Chicago (or rely on SR to keep parity).  
6. **Update Terraform state** – Move the primary back to Chicago and commit.  

**Metrics for go/no‑go**  

* **RPO** – Replication lag < 15 s (checked via `pg_last_xact_replay_timestamp`).  
* **RTO** – Total failover time < 45 min (including DNS, DB promotion, pod restarts).  
* **Application health** – < 0.1 % error rate for 5 min post‑failover.  
* **Data consistency** – Verified object count parity between MinIO sites.  

If any metric breaches, trigger an **automated rollback** (re‑point DNS to Chicago, revert Patroni config) and open an incident.
