Hoisting means the declaration is processed before the code runs, but only `var` is initialized with `undefined`. `let`/`const` are hoisted as “undeclared” (they throw a ReferenceError if accessed before the declaration).

**JS2** – The event loop coordinates three queues: the **call stack** (currently executing code), the **macrotask queue** (e.g., `setTimeout`, `setInterval`, I/O callbacks, UI events), and the **microtask queue** (Promise callbacks, `queueMicrotask`). When the stack is empty, the loop picks a macrotask, runs it, then checks the microtask queue and exhausts it before picking the next macrotask. This guarantees that Promise‑chain resolutions run before any scheduled macrotasks.

**JS3** – A closure is a function that retains access to its lexical environment even after that environment has exited. Example:
```js

  return function(y) { return x + y; };
}
const add5 = makeAdder(5);
```
The classic `for`‑loop closure bug:
```js

  setTimeout(() => console.log(i), 100);
}
```
All logs `3` because the timeout callbacks close over the same `i`, which by the time they fire has the final value `3`. Fix by creating a new scope:
```js
for (var i = 0; i < 3; i++) {
  (function(i) {
    setTimeout(() => console.log(i), 100);
  })(i);
}
```
or use `let` (block‑scoped) instead of `var`.

**JS4** – A `Promise` represents an eventual value or error, with `.then`/`catch`/`finally` for handling outcomes. `async/await` is syntactic sugar over Promises: an `async` function returns a Promise, and `await` pauses until the awaited Promise resolves, automatically unwrapping it. Errors are propagated like any Promise; `await` throws the rejected value, and `try/catch` works around it. `Promise.all` rejects if **any** input rejects, returning the first rejection reason. `Promise.allSettled` waits for **all** inputs to either resolve or reject, returning an array of `{status:'fulfilled',value:...}` or `{status:'rejected',reason:...}` objects.

**JS6** – JavaScript uses prototypal inheritance: objects inherit directly from other objects via `__proto__` or `Object.getPrototypeOf`. `Object.create(proto)` creates a new object whose prototype is `proto`. **JS7** – `this` is the **execution context** receiver. The four binding rules (in priority order):
1. **Explicit binding** (`.call`, `.apply`, `.bind`) – you set `this` directly.
2. **Implicit binding** – the object before the dot invoking the function.
3. **New binding** – when the function is called with `new`, `this` becomes the newly created instance.
4. **Default binding** – if none of the above, `this` is the global object (or `undefined` in strict mode).

`bind()` returns a **new function** with `this` permanently set; you can call it later and it will retain the bound `this`. You can re‑bind by calling `bind` again on the bound function (or using `Function.prototype.bind` with new arguments).

**JS8** – `WeakRef` holds a weak reference to an object, allowing the object to be garbage‑collected without keeping it alive. `FinalizationRegistry` lets you register a callback that runs when a target object is about to be collected. **JS9** – V8 optimizes JavaScript via **hidden classes** (shapes) that track property order and type, enabling fast property access. **Inline caching** records which class of object a property access sees and generates specialized code for that class. **Deoptimization** occurs when the hidden class changes (e.g., adding a property to an object that previously had a stable shape) or when the code encounters operations that cannot be optimized (e.g., `eval`, `with`, `typeof` on dynamic property names). Patterns that cause deoptimization: adding properties dynamically to objects that were previously “stable”, using `eval`, `with`, `Function` constructor, or relying on `this` with varying types.

**JS10** – **Tree‑shaking** is static dead‑code elimination of unused exports. - `-u`: treat unset variables as an error.
- `-o pipefail`: cause pipeline exit status to be that of the last (rightmost) command to exit with a non‑zero status, not the first failing one.

**B6** – `<<EOF` (here‑document) feeds the following lines as stdin to a command; `<<<` (here‑string) creates a single‑string stdin. `<<-EOF` strips leading tabs from the lines (useful for indentation in scripts).

**B7** –  
- `cmd > file 2>&1` redirects stdout to `file` **and** merges stderr into that same file **after** stdout redirection (stderr follows stdout).  
- `cmd 2>&1 > file` first redirects stderr to stdout, then both go to `file`. The order matters when `cmd` writes to both descriptors concurrently; the first form can interleave stdout/stderr in the file, while the second form may buffer them differently, potentially losing ordering.

**B8** – ```bash
lock() {
  local lockfile="$1".lock
  local dir="$(dirname "$lockfile")"
  # Ensure the lock directory exists
  mkdir -p "$dir" || return 1
  # Try to create the directory as the lock
  if mkdir "$lockfile" 2>/dev/null; then
    # Lock acquired – register cleanup
    trap 'rmdir "$lockfile"' EXIT INT TERM
    return 0
  else
    return 1
  fi
}
```
`mkdir` is preferred because it is atomic; a race condition cannot create a stale lock file. Removing the directory cleans up even if the script is killed with `SIGTERM` (trap handles it). The lock directory can be checked for existence to test lock status.

**B15** – `xargs` builds argument lists from stdin; `command substitution` runs a command and substitutes its output. Use `find -print0 | xargs -0` to safely handle spaces/newlines. `-P` runs `xargs` with N parallel jobs.

**B18** – Signals: `SIGINT` (Ctrl‑C), `SIGTERM` (terminate), `SIGHUP` (hangup), `SIGKILL` (cannot be caught). Graceful shutdown: trap signals, wait for background jobs, send termination signals, and clean up resources.

**B19** – Script sketch:

process_log() {

or simply `return @('one','two')` and handle `$null` downstream.

**PS8** – `[scriptblock]` is a block of code that can be stored and invoked; a function is a named scriptblock with metadata. Pass a scriptblock to a remote session via `-ScriptBlock` or `-ArgumentList` with `$using:` variables. The **double‑hop problem** occurs when a remote session uses delegated credentials that cannot be re‑used in a second hop; solve with `CredSSP` (`-AuthenticationMechanism Credssp`) or store credentials in a `PSCredential` passed via `-Credential`.

**PS9** – `@()` creates a empty array; `[array]` is a type accelerator that also creates an empty array. To force a single result into an array: `@(value)` or `[value]`. Indexing `$null` throws; indexing an empty array returns `$null`.

**PS10** – `-eq`/`-ne` perform case‑insensitive comparison; `-ceq`/`-clike` are case‑sensitive. `-like` uses wildcards, `-match` uses regex. `-contains` checks if a collection contains a specific value; `-in` checks if a value exists in a collection.

**PS11** – A **module** groups functions, cmdlets, providers. Script module (`.psm1`) contains procedural code; manifest module (`.psd1`) defines metadata (functionsToExport, rootModule, requiredAssemblies); binary module (`.dll`) is a compiled .NET assembly exposing cmdlets via `[CmdletBinding]`. `Import-Module` loads the module into the session, making its commands available.

**PS12** – Interpolation: `"$var"` or `@"$var"` (here‑string). Single quotes `'...'` do not interpolate. Use `@'` for verbatim strings. Here‑string (`@"..."@`) preserves newlines and allows multi‑line strings.

**PS13** – `Get-Member` shows properties, methods, note properties of an object. `Select-Object` chooses columns; `Where-Object` filters objects. `Get-Member` is for introspection; `Select-Object`/`Where-Object` are for transformation/filtering.

**PS14** – PowerShell classes (v5+) are .NET‑backed, similar to C# but limited: no multiple inheritance, no static constructors, no operator overloading. Constructors are defined with `function __Constructor__`. Use classes for complex data with validation; functions are simpler for ad‑hoc scripts.

**PS15** – `[CmdletBinding()]` enables common parameters (`-Verbose`, `-WhatIf`). `SupportsShouldProcess` enables `-WhatIf`/`-Confirm`. `DefaultParameterSetName` selects which parameter set is used by default. `ValueFromPipeline` allows pipeline input. `Begin/Process/End` blocks are used in advanced functions to separate initialization, per‑object processing, and finalization.

**PS16** – Providers abstract different data stores. `Get-ChildItem` works across `FileSystem`, `Registry`, `Certificate`, `Environment`. Access registry like a file system: `Get-ChildItem -Path 'HKLM:\Software'`.

**PS17** – Runspaces are isolated .NET execution contexts. `[runspace]` represents a single pipeline execution; `[runspacepool]` manages a pool of runspaces; `[powershell]` is the object representing a PowerShell command. `ForEach-Object -Parallel` (v7+) uses internal runspace pools; manual runspace management gives finer control over thread safety and resource limits.

**PS18** – `PSScriptAnalyzer` is a static analysis tool that enforces coding standards via rules (e.g., `PSUseConsistentIndentation`). Severity levels: `Error`, `Warning`, `Information`. Custom rules can be added. Suppress with `# PSScriptAnalyzer: enable DisableRuleName`. Integration: add to CI pipelines (e.g., Azure DevOps, GitHub Actions) to fail builds on violations.

**PS19** – `$using:` scope allows a variable from the current runspace to be referenced in a remote session without passing it as an argument; `$args`/`-ArgumentList` pass data as positional arguments. Serialization limits (`CLIXML`) cap depth (~1000) and can truncate complex objects. Use `$using:` for simple variables; for complex objects, pass via `-ArgumentList` and be aware of truncation.

**PS20** – **DSC** defines configurations as declarative MOF documents; **resources** (e.g., `File`, `Package`) describe desired state; **LCM** (Local Configuration Manager) enforces configurations on nodes. Windows PowerShell uses `.ps1` MOF; PowerShell 7+ supports `PSDesiredStateConfiguration` with JSON/PS1 configurations. Modern IaC often replaces DSC with tools like **Azure Automation**, **Terraform**, **Ansible**, or **Puppet**, which provide broader ecosystem support.<|END_TEXT|>
