- **Deployment**: Stateless, rolling updates, pod names are generated (`pod‑123‑abc`). No guaranteed ordering or stable network identity. Scaling is generic; updates use rolling replacements.  
- **StatefulSet**: Stateful, ordered pods (`pod‑0`, `pod‑1`, …) with stable DNS and headless Service (`<statefulset‑name>.<namespace>.svc.cluster.local`). **K2** – **ClusterIP Service routing**  
1. A `ClusterIP` Service creates an IP (or virtual IP) and a kube‑proxy endpoint in each node’s iptables.  
2. DNS resolves the Service name to that IP.  
3. When a pod sends traffic to the Service IP, kube‑proxy rewrites the destination to one of the Service’s Endpoints (pods) using iptables/NAT rules.  
4. The pod’s traffic reaches the selected pod; kube‑proxy also load‑balances across multiple endpoints (round‑robin by default).

**K3** – **PV, PVC, StorageClass**  
- **PersistentVolume (PV)**: A cluster‑wide storage resource (block or NFS) that has been provisioned by an external provider (AWS EBS, GCE PD, NFS server). It is independent of any pod.  
- **PersistentVolumeClaim (PVC)**: A request for storage (`apiVersion: v1; kind: PersistentVolumeClaim`). A pod mounts a PVC, and the scheduler matches the PVC to a suitable PV based on resources and labels.  
- **StorageClass**: A definition (`storage.k8s.io/v1; kind: StorageClass`) that describes how PVs are provisioned (e.g., `aws-ebs`, `standard`). It is referenced by PVCs to influence the class of PV that will be bound.  
- **Relation**: PVC → StorageClass → PV (binding). The PVC requests storage; the StorageClass tells the provisioner which driver to use; the provisioner creates a PV, which the PVC then binds to. The pod mounts the PVC, gaining access to the underlying PV.

**K5** – **CoreDNS role & impact of its failure**

**K6** – **Scheduler decision process**  
1. **Filtering (predicates)** – Nodes that do **not** satisfy constraints are removed. Typical predicates:  
   - **Resource availability** (CPU, memory, storage).  
   - **NodeSelector/Tolerations** (taints, pod tolerations).  
   - **Affinity/Anti‑affinity** (pod affinity/anti‑affinity rules).  
   - **Topology Spread Constraints** (distance, zone).  
2. **Scoring (priorities)** – Remaining nodes are ranked. Common priority factors:  
   - **Resource usage** (prefer less‑loaded nodes).  
   - **Node affinity/anti‑affinity weight**.  
   - **Taint/toleration priority**.  
   - **Custom metrics** (e.g., GPU availability, custom schedulers).  
3. The scheduler picks the highest‑scoring node; if multiple nodes tie, a deterministic tie‑breaker (e.g., name) is used.

**K8** – **Ingress request lifecycle (NGINX Ingress)**  
1. **External LB** (cloud provider) receives a client request on the Ingress’s external IP/port (80/443).  
2. LB forwards to the **NGINX Ingress Controller** (running as a Deployment) listening on port 80/443.  
3. NGINX evaluates the Ingress rules (host/path) and forwards the request to the **Service** defined in the Ingress (`kubernetes.io/ingress.backends`).  
4. The Service is of type `ClusterIP`. NGINX contacts the Service’s IP; **kube‑proxy** on the node rewrites the destination to one of the Service’s **Endpoints** (pods) using iptables/NAT.  
5. The request reaches the target application pod. Responses travel back through the same path (pod → kube‑proxy → Service → NGINX → LB → client).

**K9** – **NetworkPolicy**  
- **Purpose**: Define inbound/outbound pod communication rules (allow/deny).  
- **Default behavior**: If no NetworkPolicy exists in a namespace, the default is **allow all traffic** (both inbound and outbound).  
- **Applying a policy**: A NetworkPolicy that selects a subset of pods (e.g., via `spec.podSelector`) restricts **only** those pods. Other pods in the namespace continue to follow the default allow‑all unless they are also selected. Inbound traffic to selected pods is denied unless explicitly allowed; outbound traffic is allowed unless the policy also restricts it.

**K10** – **RollingUpdate vs Recreate**  
- **RollingUpdate**: Gradually replaces pods. Old pods are terminated while new ones are created, maintaining a configurable `maxUnavailable`/`maxSurge`. Zero‑downtime for stateless services.  
- **Recreate**: Deletes all replicas at once, then creates the new replicas. Guarantees a clean state but causes total service interruption.  
- **When to choose Recreate**: When the new version cannot coexist with the old (e.g., configuration changes that require a full restart, or when the application cannot tolerate a mixed‑version state). Also useful for small, non‑critical services where a brief outage is acceptable.

**K11** – **Namespace & default namespaces**  
- **Namespace**: A logical partition that groups resources (pods, services, deployments, etc.) and provides isolation at the API/server level. Namespaced resources are scoped to a namespace; cluster‑scoped resources (Node, PersistentVolume) are global.  
- **Default namespaces in a fresh cluster**:  
  - `default` – for untagged resources.  
  - `kube-system` – core cluster components (kube‑proxy, DNS, controller‑manager).  
  - `kube-public` – publicly readable (used for cluster DNS).  
  - `kube-node-lease` – lease objects for node heartbeats.

**K14** – **Service types**  
- **ClusterIP**: Internal-only service, accessible only from within the cluster. No external IP.  
- **NodePort**: Adds a static port (30000‑32767) on every node; external clients can reach the service via `<nodeIP>:<nodePort>`.  
- **LoadBalancer**: Creates a cloud‑provider‑specific load balancer (e.g., AWS ELB, GCP LB) with an external IP, automatically provisioning health‑checking and forwarding.

**K15** – **DaemonSet**  
- **Definition**: Ensures a copy of a pod runs on all (or a subset of) nodes that match a label selector.  
- **When to use**: For node‑level agents such as node exporters, log collectors, sidecar containers, or network plugins that must be present on every worker.

**K16** – **Taints/Tolerations vs Node Affinity**  
- **Taints** (applied to nodes) repel pods that don’t tolerate them. **Tolerations** (applied to pods) allow a pod to schedule onto tainted nodes.  
  *Use case*: Control‑plane pods tolerate `node-role.kubernetes.io/master` taint.  
- **Node affinity** selects nodes based on node labels (e.g., `node-type=high-cpu`). It does **not** use taints.  
  *Use case*: Place a GPU‑intensive workload on nodes labeled `accelerator=nvidia`.  
- **Difference**: Taints/Tolerations are “hard” exclusions; affinity is “soft” preference (required/preferred). Both achieve placement control but with different semantics.

**K17** – **Kubernetes Operator**  
- **Definition**: A controller that extends the Kubernetes API to manage complex applications (e.g., databases, monitoring). It watches custom resources (CRDs) and performs reconciliation logic.  
- **Difference from a standard controller**: Operators are **application‑specific**, encode operational knowledge, and expose **domain‑level APIs** (CRDs) rather than low‑level pod/statefulset manipulations.  
- **Problems solved**: Reduces manual lifecycle management, ensures consistent updates, handles scaling, backup, recovery, and configuration in a declarative way.

**K18** – **etcd consistency model & recovery**  
- **Model**: etcd uses the **Raft consensus algorithm**, providing **linearizable (strong) consistency**. All reads/writes go through a quorum (majority) of etcd members; a write is committed only after a majority acknowledges.  
- **If quorum is lost**: The cluster becomes **unavailable** for writes and reads; no leader can be elected, causing API server failures.  
- **Recovery from permanent loss of 2/3 nodes**:  
  1. Restore a fresh etcd from the remaining node’s snapshot (`etcdctl snapshot restore`).  
  2. Start the new node with `--initial-cluster` containing the restored member plus any new members you plan to add.  
  3. Add the other lost members back as new nodes (if data can be salvaged) or decommission them.  
  4. Verify quorum (`etcdctl endpoint status`).

- **ClusterRole**: Permissions cluster‑wide.  
- **RoleBinding**: Binds a Role (or ClusterRole) to **subjects** (users, groups, service accounts) within a namespace.  
- **ClusterRoleBinding**: Binds a ClusterRole to subjects **cluster‑wide**.

**K20** – **ndots and DNS slowdown**  
- **Problem**: `ndots` (default 5) tells `resolv.conf` how many dots a hostname must contain before trying search domains. A low `ndots` (e.g., 1) causes the resolver to try each search domain for external names, generating many queries and latency.  
- **Fix with `dnsConfig`**:  

```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "3"   # increase to reduce search attempts
```

or explicitly set `nameservers` to external DNS (e.g., Google 8.8.8.8) to bypass search domains. This reduces the number of iterative queries and restores external DNS performance.

**D1** – **git rebase vs merge**  
- **Rebase**: Rewrites the commit history of the current branch onto the target branch, creating a linear history.  
- **Merge**: Creates a new merge commit that combines histories, preserving the original branch structure.  
- **Avoid rebasing** when the branch is **public/shared** (e.g., main, feature branches already pushed) because rewriting history forces collaborators to re‑base/pull‑request, causing confusion and lost work.

**D2** – **TCP vs UDP**  
- **TCP**: Connection‑oriented, reliable, ordered byte stream; uses handshake, ACKs, flow control. Protocols: HTTP, SMTP, FTP.  
- **UDP**: Connectionless, datagram‑based, no reliability or ordering. Protocols: DNS (often), DHCP, VoIP.

**D3** – **Race condition**  
- **Definition**: Concurrent modifications to shared state without proper synchronization, leading to unpredictable outcomes.  
- **Example (C++):**  

```cpp
int counter = 0;
void increment() {
    int tmp = counter; // read
    tmp++;             // increment
    counter = tmp;     // write
}
```

Two threads can read the same `counter` value, increment locally, and write back, resulting in a lost update (final value < expected).

**D4** – **Symmetric vs asymmetric encryption & TLS**  
- **Symmetric**: Same secret key for encryption/decryption; fast, used for bulk data.  
- **Asymmetric**: Public/private key pair; slower, used for key exchange and authentication.  
- **TLS usage**: Client and server perform an asymmetric handshake (e.g., RSA/ECDHE) to agree on a shared secret and authenticate. The secret key derived is then used for symmetric encryption of the application data.

**D5** – **Container image layer & Dockerfile best practices**  
- **Layer**: Each `RUN`, `COPY`, `ADD` creates a read‑only filesystem layer; subsequent layers build on the previous ones.  
- **Layer caching**: Docker reuses cached layers if the preceding instructions haven’t changed.  
- **Best practices**:  
  1. Combine multiple `RUN` statements into one `RUN` to reduce layers.  
  2. Use multi‑stage builds to keep final image small.  
  3. Order `COPY` after `FROM` and group related files to maximize cache hits.

**D6** – **Intermittent HTTP 503 – 4 checks (in order)**  
1. **Application logs** – Look for exceptions, database connection failures, or health‑check failures.  
2. **Health‑check endpoint** – Verify `/health` or `/ready` returns 200; if not, diagnose upstream services.  
3. **External dependencies** – Check database, message queue, third‑party APIs for connectivity or latency issues.  
4. **Infrastructure** – Inspect load balancer health, pod resource limits (OOM), network policies, and node conditions (DiskPressure, NetworkUnavailable).

**D7** – **CAP theorem**  
- **Definition**: A distributed system can provide at most **two** of **Consistency**, **Availability**, and **Partition tolerance**.  
- **CP example**: **etcd** or **ZooKeeper** – they prioritize strong consistency and partition tolerance, sacrificing availability during network partitions.  
- **AP example**: **DynamoDB** (or Cassandra) – they favor availability and partition tolerance, offering eventual consistency.

**D8** – **Horizontal vs vertical scaling**  
- **Horizontal scaling**: Add more **instances** of a service; each instance runs the same code. Enables fault tolerance and linear throughput growth. Architectural patterns: **Load balancing**, ** sharding**, **microservices**, **container orchestration** (K8s).  
- **Vertical scaling**: Increase **resources** (CPU, memory) of a single instance. Limited by the maximum size of a VM/container; can improve latency but may hit diminishing returns.

**D9** – **Environment variable & persistence**  
- **Definition**: A name‑value pair passed to processes, used for configuration.  
- **Persist across sessions on Linux**:  

```bash
echo 'export MYVAR="value"' >> ~/.bashrc
source ~/.bashrc   # or open a new shell
```

**D10** – **JSON vs YAML**  
- **JSON**: JavaScript Object Notation; strict syntax, no comments, human‑readable for machines. Advantage: **Fast parsing**, native support in many languages.  
- **YAML**: YAML Ain’t Markup Language; human‑friendly, supports comments, indentation. Advantage: **Readability** and ease of authoring complex structures.

**D11** – **REST API & HTTP methods**  
- **REST API**: Architectural style using HTTP resources, stateless, uniform interface (resource identification, representation, self‑descriptive messages).  
- **GET** – Retrieve a representation of a resource.  
- **POST** – Create a new resource (or trigger an action).  
- **PUT** – Replace/update a resource entirely (idempotent).  
- **DELETE** – Remove a resource (idempotent).

**D12** – **Version pinning**  
- **Definition**: Explicitly specifying exact versions of dependencies (e.g., `package@1.2.3`).  
- **Importance**: Guarantees **reproducible builds**, prevents unexpected breaking changes, and ensures the same binary across environments.

**D13** – **Compiled vs interpreted languages**  
- **Compiled**: Source code translated to machine code before execution. Examples: **C**, **Go**.  
- **Interpreted**: Source code executed by an interpreter at runtime. Examples: **Python**, **JavaScript** (via V8).

**D14** – **Reverse proxy vs forward proxy**  
- **Reverse proxy**: sits in front of **servers**, accepting client requests and forwarding them to the appropriate backend. Use cases: load balancing (`Nginx`), SSL termination (`HAProxy`).  
- **Forward proxy**: sits in front of **clients**, forwarding their outbound requests to the internet, often for caching or filtering.  
- **Common reverse proxies**: `Nginx` (web serving, load balancing), `HAProxy` (high‑availability load balancing).  

**D15** – **Deadlock & Coffman conditions**  
- **Deadlock**: Two or more processes wait indefinitely for resources held by each other.  
- **Coffman conditions** (must all hold):  
  1. **Mutual exclusion** – resources not shareable.  
  2. **Hold‑and‑wait** – processes hold resources while waiting for others.  
  3. **No preemption** – resources cannot be forcibly taken.  
  4. **Circular wait** – a cycle of processes waiting for each other’s resources.

**D16** – **Eventual consistency & Cassandra tunable levels**  
- **Eventual consistency**: Updates propagate asynchronously; after some time, all replicas converge to the same value. Reads may see stale data temporarily.  
- **Cassandra read‑after‑write**: Use `QUORUM` or `LOCAL_QUORUM` consistency level for writes and reads to guarantee that a majority has applied the write before acknowledging.  
- **Tunable levels**: `ONE`, `QUORUM`, `ALL`, `LOCAL_ONE`, `SERIAL`, etc., allowing trade‑offs between latency and consistency.

**D17** – **mTLS (mutual TLS)**  
- **Handshake**:  
  1. Client sends **ClientHello** with supported TLS versions/ciphers.  
  2. Server replies **ServerHello**, presents its certificate chain.  
  3. Client verifies server cert against trusted CA.  
  4. Client sends **Certificate** (client cert) and **CertificateVerify**.  
  5. Server verifies client cert against CA.  
  6. Both derive a pre‑master secret (via RSA/ECDHE) and compute session keys.  
- **Authentication**: Both sides prove identity via X.509 certificates.  
- **Common uses**: Service mesh (Istio, Linkerd), API gateways, internal microservices communication, and secure database access.

**D18** – **Hash table internals**  
- **Structure**: Array of buckets; each bucket holds entries (chaining) or uses open addressing (linear probing, quadratic).  
- **Collision resolution**:  
  - **Chaining**: Each bucket points to a linked list of entries.  
  - **Open addressing**: Colliding entries are placed in subsequent slots (probe sequence).  
- **Time complexity**:  
  - **Average**: Insertion O(1), lookup O(1), deletion O(1).  
  - **Worst‑case** (all keys hash to same bucket): O(n) for all operations.

**D19** – **Circuit breaker pattern**  
- **Closed**: Normal operation; requests go through.  
- **Open**: Failure threshold exceeded; requests short‑circuit to a fallback (e.g., error response) without invoking the service.  
- **Half‑open**: After a timeout, a limited number of test requests are allowed; if they succeed, the circuit resets to closed; if they fail, it returns to open.  
- **Prevents cascade**: By stopping repeated calls to a failing service, it protects downstream systems and allows the failing service time to recover.  
- **Relation to retry & backoff**: Circuit breaker works **above** retry logic; after a failure count reaches the threshold, retries are suppressed. Exponential backoff can be used within the closed/half‑open states to avoid overwhelming the service during recovery.

**D20** – **Optimistic vs pessimistic concurrency control**  
- **Pessimistic**: Locks resources (e.g., `SELECT FOR UPDATE`, row locks) before performing updates, assuming conflicts are likely. Guarantees serializability.  
- **Optimistic**: Allows concurrent updates, checking for conflicts at commit time (e.g., version/column `VERSION` increments). Assumes conflicts are rare.  
- **When to choose**:  
  - **Pessimistic** for high‑contention scenarios (e.g., financial transactions).  
  - **Optimistic** for low‑contention, high‑throughput workloads (e.g., social media feeds).  
- **Concrete example**:  
  - **Pessimistic**: `BEGIN; SELECT * FROM accounts WHERE id=1 FOR UPDATE; UPDATE accounts SET balance=balance-100 WHERE id=1; COMMIT;`
