<|END_THINKING|><|START_TEXT|>**T1** – `tofu plan` creates an execution plan that shows what actions OpenTofu will take **without** making any changes. It validates configuration, refreshes the state (by default), and outputs a JSON plan that can be inspected or saved (`tofu plan -out=plan`). `tofu apply` (or just `tofu apply <plan>`) actually carries out the actions described in the plan, creating, updating, or deleting resources, and then updates the state file with the new resource IDs and attributes. `plan` is safe to run multiple times; `apply` is the irreversible step.

**T2** – The **state** is OpenTofu’s internal record of the real‑world resources it manages (IDs, IPs, tags, etc.). It lives in a state file (local or remote) and is required for OpenTofu to know what it has already created, to compute dependencies, and to detect drift. **Remote state** (e.g., S3 + DynamoDB) is essential for team collaboration because it provides a single source of truth accessible to all team members, enables locking to prevent concurrent modifications, and survives CI runners or machine changes. Without remote state, each developer works on a separate copy, leading to conflicts and “state drift”.

**T3** – `count` creates a fixed number of identical resources with auto‑generated names (`resource.foo.0`, `resource.foo.1`, …). It only supports an integer count and cannot reference dynamic keys. `for_each` iterates over a **map** or **list** and uses the iteration key (or value) as the resource address (`resource.foo["web1"]`). `for_each` is preferred when you need:
* Non‑integer identifiers (e.g., server names, zone codes).  
* Different configurations per item (you can reference the key/value inside the resource).  
* Conditional creation based on the collection contents.

**T4** – If you edit a resource manually (e.g., delete a VM in the cloud console), OpenTofu detects **drift** on the next `plan`. The resource will appear as “needs to be recreated” or “needs to be updated”. OpenTofu will either:
* **Refresh** the state automatically (default) to reflect the real state, then propose a corrective action.  
* Or, if you run `apply` with `-refresh=false`, it will ignore the drift and keep its recorded state, potentially leading to inconsistency.

You can also force a refresh (`tofu refresh`) or manually adjust the state (`tofu state mv`, `tofu state rm`) to bring the state back in sync.

**T6** – `terraform_remote_state` (or `data "terraform_remote_state"` in OpenTofu) **reads the raw state** of another OpenTofu configuration as a data source. It is opaque: you get the exact keys/values that were output, but you cannot enforce schema or versioning. It creates a tight coupling because any change in the remote state’s structure can break the consumer.

**Outputs** (`output` blocks) are **explicit, versioned interfaces** that a module publishes. The consumer references them via `module.<mod_name>.output_name`. Outputs are part of the module’s contract, are validated by OpenTofu, and can be documented.

**Recommended alternative:** Use **module outputs** (or `terraform_remote_state` only when you truly need to read a remote state that isn’t expressed as an output). Outputs give you:
* Clear dependency tracking (`depends_on` works naturally).  
* Ability to reuse the same data across multiple callers.  
* Better IDE/autocomplete support and documentation.

Thus, share data between root modules by exposing needed values as outputs from the provider module and consuming them as `module.<mod>.output_name`.

**T7** – The `null_resource` with a `remote-exec` provisioner runs **after** the RKE2 cluster resource creates the kubeconfig, but the `output` that references the kubeconfig is defined **inside** the same `null_resource`. On the first `apply`, the `null_resource` runs **before** the cluster resource finishes, so the output variable is still empty. Dependent resources that need the kubeconfig therefore fail because they receive an empty value.

**Fix options:**
1. **Move the output definition** to a separate resource (or a `local` variable) that is created **after** the cluster resource, e.g.:

```hcl
resource "aws_s3_bucket_object" "kubeconfig" {
  bucket = var.bucket_name
  key    = "${var.cluster_name}/kubeconfig"
  content = module.rke2.kubeconfig_path   # assume module.rke2 writes the file locally
}

output "cluster_kubeconfig" {
  value = aws_s3_bucket_object.kubeconfig.id
}
```

2. Use `depends_on` on the `null_resource` to ensure it runs after the cluster resource, then reference the output:

```hcl
null_resource.wait_for_kubeconfig {
  depends_on = [module.rke2.cluster]

  provisioner "remote-exec" {
    # ... copy kubeconfig ...
  }
}

output "kubeconfig" {
  value = null_resource.wait_for_kubeconfig.id   # or read from file
}
```

3. Use a **local-exec** provisioner that writes the kubeconfig to a local file, then read that file via a `local` variable and expose it as an output. This avoids the circular dependency.

**T8** – `tofu import` (or `terraform import`) brings an **existing, already‑managed resource** into OpenTofu’s state without creating it. Limitations:
* You must know the resource’s Terraform **resource address** (`type.name`) and its **ID**.  
* The resource must already exist in the target backend; OpenTofu cannot import resources that it cannot read.  
* Importing can leave the configuration out of sync with reality; you usually need to adjust the Terraform config afterward.  
* Some providers do not support import (or only support partial attributes).

The **import block** (available from OpenTofu 1.5+ as a first‑class construct) improves on the CLI command by:
* Declaring imports **inside the configuration** (`import { from = ... }`), making them version‑controlled and reproducible.  
* Allowing **multiple imports** in a single block, with optional `to` and `id` overrides.  
* Enabling **`terraform plan`** to show import actions, so you can review them before applying.  
* Supporting **`terraform refresh`** after import to reconcile any drift.

**T9** – A **variable** (`variable "region" {}`) is an **input** that can be passed into a Terraform configuration (via CLI, env, or TF files). It defines a parameter that modules or the root module accept from the user.

An **output** (`output "public_ip" {}`) is an **explicit return value** that makes data computed by Terraform available to the user, other modules, or external systems (e.g., CI). Variables are **inputs**; outputs are **outputs**.

**T10** – A **provider** (e.g., `aws`, `google`) defines the plugin that OpenTofu uses to interact with a cloud API. It determines which resource types and arguments are available.

If you run `tofu plan` without a prior `tofu init`, OpenTofu will fail because it cannot locate the provider plugins, download required versions, or initialize the backend. The error typically says “Provider not found” and will abort the plan.

**T11** – `.terraform.lock.hcl` records the **exact provider version** and **download location** that were selected during `tofu init`. It pins the provider to a specific version to ensure reproducible runs across machines and CI. **Commit it** so that every team member uses the same provider versions, avoiding “provider version drift” and unexpected changes in behavior.

**T12** – `tofu destroy` deletes all resources managed by the current state file (after prompting for confirmation). To target a **single resource**, use the `-target` flag:

```
tofu destroy -target=aws_instance.example
```

Only the specified resource will be destroyed; other resources remain untouched.

**T13** – A **data source** (`data "aws_ami"` for example) reads **external data** that is not managed by OpenTofu (e.g., an existing AMI ID, a DNS record, a secret from a cloud provider). It is **read‑only** and does not create or modify resources.

*Use case:* You need to reference a pre‑existing AMI ID for an EC2 instance, but you don’t want to manage that AMI with Terraform. You query it with a data source and use its ID in a managed resource.

**T14** – **Variable blocks** (`variable "region" {}`) define **external inputs** that can be set from the CLI, environment, or `.tfvars`. They are part of the module’s public interface.

**Locals** (`locals { region = var.region }`) are **internal, computed values** that stay within a module and are not exposed as inputs/outputs. Use locals when:
* You need to compute a value from other variables (e.g., `combined = "${var.env}-${var.project}"`).  
* You want to avoid repeating complex expressions.  
* You need a value only for a subset of resources inside the same module.

**T15** – The **lifecycle block** (`lifecycle {}`) allows fine‑grained control over resource creation, update, and deletion.

| Option | Effect | Typical Use‑Case |
|--------|--------|------------------|
| `create_before_destroy = true` | OpenTofu creates the new resource **before** destroying the old one, keeping the resource available during updates. | Updating a server configuration where downtime must be minimized. |
| `prevent_destroy = true` | Blocks any plan that would destroy the resource. | Protecting critical infrastructure (e.g., a database subnet) from accidental deletion. |
| `ignore_changes = [attribute]` | Tells OpenTofu to ignore manual changes to specified attributes, leaving them as‑is after apply. | When external services (e.g., a load‑balancer health check) modify tags that you don’t want Terraform to manage. |

**T16** – A **moved block** (`moved { from = aws_instance.old id = ... to = aws_instance.new }`) tells OpenTofu that a resource’s logical address has changed **without** deleting and recreating it. It helps during refactoring (renaming resources, moving them between modules) while preserving the existing state, avoiding unnecessary destruction/recreation and associated costs or downtime.

**T17** – OpenTofu builds a **dependency graph** where each node is a resource (or data source). **Implicit dependencies** arise automatically from references (e.g., a resource referencing another’s attribute). **Explicit dependencies** are declared via `depends_on` or `lifecycle.create_before_destroy`.

`depends_on` forces an ordering: the dependent resource will not be created until the referenced resource(s) are created. It also **reduces parallelism** because OpenTofu must wait for the dependency to reach a “created” state before proceeding with the dependent resource. Use it sparingly—over‑using it can increase apply time and hide true dependency relationships that could be expressed more cleanly.

**T18** – Strategies to cut a 10‑minute plan for a 200‑resource codebase:

1. **Skip state refresh** – `tofu plan -refresh=false`.  
   *Trade‑off:* You lose detection of drift against the real cloud, but plan time drops dramatically.

2. **Reduce parallelism** – `tofu plan -parallelism=1` (or a low number).  
   *Trade‑off:* Slower plan/apply but can surface errors earlier and reduce API rate‑limit hits.

3. **Disable input prompts** – `tofu plan -input=false`.  
   *Trade‑off:* No interactive variable prompts; you must supply all variables via files or env, but plan runs faster.

4. **Compact output & disable colors** – `tofu plan -compact-warnings -no-color`.  
   *Trade‑off:* Less human‑readable output, but parsing is faster and console I/O is reduced.

5. **Split modules** – Move unrelated resources into separate modules and run `plan` on each module individually.  
   *Trade‑off:* More granular planning, but adds complexity to orchestration.

6. **Use `-detailed-exitcode`** – Allows CI to skip a second plan if no changes are detected, avoiding repeated long plans.  
   *Trade‑off:* Requires CI logic to interpret exit codes.

**T19** – OpenTofu’s **state locking** works by acquiring an **exclusive lock** on the state file (or remote backend) before any operation (`plan`, `apply`, `refresh`, `import`). For remote backends (S3+DynamoDB), DynamoDB provides the lock; for local state, OpenTofu uses file‑system locks (`.terraform/terraform.lock`).

If a lock is not released (e.g., a CI runner crashes mid‑apply), subsequent operations will **wait** for the lock timeout (default 5‑10 minutes) and then **fail** with a “state lock denied” error. The state may be left in an **inconsistent** or **half‑applied** state, risking resource drift.

**Manual lock break** (for remote backends):
```
aws dynamodb delete-item --table-name <state-table> --key '{"LockID":{"S":"terraform"}}'
```
or use `tofu force-unlock <lock-id>` after identifying the lock ID from the error.

**Risks** of breaking a lock:
* You can overwrite an ongoing apply, causing **resource deletions** or **corruption**.  
* The broken lock may leave the state file in a partially written condition, leading to **drift** or **inconsistent** resource management.  
* It bypasses safety mechanisms that protect against concurrent modifications.

**T20** – Migration from a local state to an S3‑compatible remote backend with DynamoDB locking:

1. **Create the remote backend resources** (S3 bucket, DynamoDB table) if not already present. Enable versioning on the S3 bucket.

2. **Backup the existing local state** (`cp terraform.tfstate backup.tfstate`).

3. **Add a new backend block** to your root module (`terraform { backend "s3" { ... } }`). Commit this change **without** running `tofu init` yet.

4. **Run `tofu init -backend-reinitialize`** (or `tofu init -backend=true`). This will prompt you to migrate the existing state:
   * Choose “Migrate existing state”.
   * OpenTofu will read the local `terraform.tfstate`, upload it to the S3 bucket under the specified key, and create a lock table entry.

5. **Verify the migration**:
   * `tofu workspace list` should show the default workspace.
   * `aws s3 ls s3://<bucket>/<key>` should display the new state file.
   * `tofu show -json` should reflect the same resources as before.

6. **Remove the old local state file** (`rm terraform.tfstate`) to enforce using the remote backend.

7. **Test** by running `tofu plan` and `tofu apply` (if any changes are pending). Ensure lock behavior works (e.g., run two concurrent plans; one should be denied).

**What happens to the existing state file?**  
OpenTofu copies its contents to the remote backend and then **renames** the local file to `terraform.tfstate.backup`. The local file is no longer used, but you keep the backup for rollback.

**Verification** includes checking the remote state’s checksum, confirming that `tofu workspace select` works, and ensuring that subsequent team members can run `tofu init` without errors.

**A1** – **Playbook**: A YAML file that defines a **sequence of plays** to accomplish a task (e.g., `site.yml`). It can contain multiple plays, each targeting different hosts or roles.

**Role**: A reusable collection of **tasks**, variables, defaults, library files, and templates organized in a directory structure (`tasks/`, `vars/`, `defaults/`, etc.). Roles encapsulate common functionality (e.g., `nginx` role) and can be called from any playbook.

**Task**: The smallest unit of work in Ansible, describing **what to do** (module, action) and **how** (parameters). A playbook is composed of tasks (or groups of tasks via roles).

**A2** – `ansible_facts` is a built‑in fact gathering mechanism. To access the OS family of a host:

```yaml
- name: Gather facts
  ansible.builtin.setup:
    gather_subset:
      - "!all"
      - "distribution"

- debug:
    var: ansible_facts['distribution']
```

or simply after a `setup` task, `{{ ansible_facts.distribution }}` (or `ansible_facts['os_family']`).

**A3** – **command**: Executes a **raw shell command** directly, without any module parsing. No idempotent guarantees; you must manage idempotency yourself.

**shell**: Similar to `command` but **interprets a shell** (supports pipes, redirections, environment variables). Still non‑idempotent.

**raw**: The lowest‑level module; passes arguments directly to the remote shell **without** any module overhead. Used for very low‑level operations where `command`/`shell` aren’t suitable (e.g., custom scripts). All three are **non‑idempotent**; use `command`/`shell`/`raw` only when you need exact control and will handle idempotency manually.

**A4** – Ansible ensures idempotency by **comparing the desired state** (defined in the task) with the **actual state** (gathered via modules or facts) and skipping changes if they match.

*Idempotent task example* (using `user` module):
```yaml
- name: Ensure user alice exists
  ansible.builtin.user:
    name: alice
    state: present
    uid: 1050
```

Running this task multiple times will create the user only on the first run; subsequent runs will report “changed=0”.

*Non‑idempotent task example* (using `command`):
```yaml
- name: Run a one‑off script
  ansible.builtin.command: "echo 'Hello' >> /tmp/hello.txt"
```

Each execution appends another line, so repeated runs change the system.

  when: ansible_facts['os_family'] is defined
```  

Explanation:
* `ansible_facts['os_family']` determines the OS type.
* On Debian‑based hosts, only `htop` is installed and `update_cache` runs.
* On RedHat‑based hosts, `epel-release` is installed first (required for `htop`), then `htop`.

**A6** – Ansible variable precedence (highest to lowest):

1. **CLI extra vars** (`-e` or `--extra-vars`).  
2. **Role defaults** (`defaults/main.yml` inside a role).  
3. **Host vars** (`host_vars/<hostname>.yml`).  
4. **Group vars** (`group_vars/*.yml`).  
5. **Inventory source vars** (e.g., `inventory.yml` variables).  
6. **Play variables** (`vars:` in a play).  
7. **Task keywords** (`set_fact`, `include_vars`, `include_tasks`).  
8. **Fact cache** (`ansible_facts`).  
9. **Built‑in variables** (e.g., `ansible_facts`, `ansible_hostname`).  
10. **Parameter defaults** defined in modules.

`set_fact` sets a variable that lives **after** role defaults but **before** host/group vars? Actually `set_fact` at task level has **lower priority** than host/group vars but **higher** than inventory source vars. The exact order is documented in Ansible’s variable precedence guide.

**A7** – To roll out an RKE2 agent on 50 nodes where the first 3 must finish before the rest start:

```yaml
# inventory.yml (or group in hosts file)
all:
  hosts:
    node1: { ansible_host: ... }
    node2: { ansible_host: ... }
    node3: { ansible_host: ... }
    node4: { ansible_host: ... }
    # ... up to node50
  children:
    early_nodes:
      hosts:
        node1: {}
        node2: {}
        node3: {}
    later_nodes:
      hosts:
        node4: {}
        # ... node5‑node50
```

Playbook snippet:

```yaml
- name: Deploy RKE2 agents
  hosts: all
  serial: 3          # first play: only early_nodes
  tasks:
    - name: Install agent on early nodes
      include_tasks: tasks/install-agent.yml
      when: inventory_hostname in groups['early_nodes']

- name: Deploy remaining agents
  hosts: all
  serial: 1          # one node at a time (or a batch size)
  tasks:
    - name: Install agent on later nodes
      include_tasks: tasks/install-agent.yml
      when: inventory_hostname in groups['later_nodes']
```

Alternatively, use a **single play** with `serial: 3` and then `wait_for` on a custom fact:

```yaml
- name: Rolling install
  hosts: all
  serial: 3
  tasks:
    - name: Install agent
      ansible.builtin.shell: "curl -sfL ... | sh -"
      register: install_result

    - name: Wait for node to join cluster
      ansible.builtin.wait_for:
        host: "{{ ansible_host }}"
        port: 9345
        delay: 5
        timeout: 300
      when: inventory_hostname in groups['later_nodes']
```

The `serial` directive limits concurrent hosts; `wait_for` ensures each node is ready before the next batch proceeds.

**A8** – `ansible-vault` encrypts data using AES‑256‑CBC. To encrypt a **single variable** without encrypting the whole file:

1. Create a plain vars file (`vars.yml`):

```yaml
db_password: plain
api_key: plain
```

2. Extract the variable you want to protect:

```bash
ANSIBLE_VAULT_PASSWORD_FILE=/.vault_pass.txt ansible-vault view vars.yml > plain_vars.yml
```

3. Encrypt only that variable into a new vault file:

```bash
ansible-vault create vars_encrypted.yml <<EOF
db_password: "{{ lookup('ansible.builtin.file', 'plain_vars.yml') | to_yaml }}"
EOF
```

Or more practically, use `ansible-vault encrypt_string`:

```bash
ansible-vault encrypt_string --vault-id .vault_key 'db_password: secret' > vars_encrypted.yml
```

Now `vars_encrypted.yml` contains only the encrypted variable; other vars stay plaintext.

*Dynamic inventory*: Pulls host data from APIs (AWS, Azure, OpenStack) or scripts (`script.py`). It can provide real‑time inventory, auto‑discovery, and variable enrichment.

**A11** – A **handler** is a special task that **runs only at the end of a play**, used for actions like restarting services, where you want to avoid repeated executions during the play. Handlers differ from regular tasks in that they are **not** executed immediately; they are queued and run after all other tasks in the play complete (unless `flush_handlers` is called). You trigger a handler by referencing its name in a `notify:` line within a task.

**A14** – `include_tasks` **evaluates its YAML** at **runtime** (when the task runs). `import_tasks` **evaluates** at **parse time** (when the playbook is loaded). **A16** – **Connection plugins** define how Ansible reaches a target host.

* `ssh` – Uses SSH to execute commands, copy files, etc. Works for Unix/Linux/Windows (via `ssh`).  
* `local` – Runs tasks directly on the control node (no remote connection). Useful for tasks that manipulate the controller’s filesystem or run scripts only on the Ansible server.  
* `network_cli` – Specialized for network devices (Cisco, Arista, etc.) using SSH/Telnet, handling network‑specific command modes and enable passwords.

Choose `ssh` for generic Linux/Unix hosts, `local` for host‑less tasks, `network_cli` for network infrastructure.

**A17** – `delegate_to` sends a task to a **different host** than the one defined in `hosts`. `run_once` ensures a task runs **once** on the **first** host in the group, then delegates the result to all hosts (or uses `delegate_to`). Example: gather data from a remote host and run a setup script on the control node:

```yaml
- name: Gather kernel version from web01
  ansible.builtin.shell: "uname -r"
  delegate_to: web01
  register: kernel_info

- name: Run local cleanup on controller using gathered data
  ansible.builtin.shell: "echo '{{ kernel_info.stdout }}' > /tmp/kernel_version.txt"
  run_once: true
```

`delegate_to: web01` runs the first task only on `web01`. `run_once: true` on the second task ensures it runs once on the controller (the first host in the inventory) and uses the gathered `kernel_info` to write a file locally.

**A18** – Performance improvements for a 500‑host fleet taking >30 min:

1. **Increase forks** – `ansible-playbook -f 50` (or higher).  
   *Trade‑off:* More processes consume CPU/memory and may hit connection limits; too many forks can cause throttling.

2. **Enable pipelining** – `pipelining = yes` in `ansible.cfg`.  
   *Trade‑off:* Reduces temporary file overhead, speeding up short tasks, but may increase memory usage and can cause issues with some modules.

3. **Fact caching** – Use `fact_caching` (e.g., `jsonfile` or `memcached`).  
   *Trade‑off:* Reduces repeated `setup` runs, but adds complexity and requires cache maintenance.

4. **Mitogen or similar connection acceleration** – Install `mitogen` for faster SSH connections and reduced latency.  
   *Trade‑off:* Requires extra installation, may need privileged access, and can change connection behavior (e.g., persistent connections).

Additional tactics: split playbooks into smaller plays, use `serial` for batches, and prune inventory to only needed hosts.

**A19** – Jinja2 templating in Ansible uses three delimiter types:

* `{{ variable }}` – **expression** that outputs the evaluated value.  
* `{% statement %}` – **control structures** (loops, conditionals, includes).  
* `{# comment #}` – **comments** that are stripped out during rendering.

Example snippet generating an nginx upstream block:

```yaml
- name: Render nginx upstream config
  ansible.builtin.template:
    src: nginx_upstream.j2
    dest: /etc/nginx/conf.d/upstream.conf
  vars:
    backends:
      - host: "10.0.0.1"
        port: 80
      - host: "10.0.0.2"
        port: 80
```

`nginx_upstream.j2`:

```nginx
upstream backend {
    # Health check comments
{% for host in backends %}
    server {{ host.host }}:{{ host.port }} max_fails=3 fail_timeout=30s;  # {{ host.host }}:{{ host.port }}
{% endfor %}
}
```

The template loops over `backends`, writes each server line with an inline comment.

**A20** – Zero‑downtime rolling deployment across 20 servers:

```yaml
- name: Rolling deploy of web app
  hosts: webservers
  serial: 5          # deploy in batches of 5
  pre_tasks:
    - name: Drain old instance from load balancer
      ansible.builtin.uri:
        url: "https://lb.example.com/api/drain/{{ inventory_hostname }}"
        method: POST
        status_code: 200
      delegate_to: localhost   # run on control node

  tasks:
    - name: Stop old service
      ansible.builtin.service:
        name: webapp
        state: stopped
      notify: Start new service

    - name: Deploy new code
      ansible.builtin.git:
        repo: https://github.com/example/webapp.git
        dest: /opt/webapp
        version: main

    - name: Restart service
      ansible.builtin.service:
        name: webapp
        state: started

  post_tasks:
    - name: Verify health
      ansible.builtin.uri:
        url: "https://webapp.example.com/health"
        status_code: 200
      register: health_check
      until: health_check.status_code == 200
      retries: 5
      delay: 10

    - name: Re‑enable instance in load balancer
      ansible.builtin.uri:
        url: "https://lb.example.com/api/enable/{{ inventory_hostname }}"
        method: POST
        status_code: 200
      delegate_to: localhost

  handlers:
    - name: Start new service
      ansible.builtin.service:
        name: webapp
        state: started

  rescue:
    - name: Rollback on failure
      block:
        - name: Revert to previous release
          ansible.builtin.shell:
            cmd: "cd /opt/webapp && git checkout {{ rollback_tag }}"
          args:
            chdir: /opt/webapp

        - name: Restart service
          ansible.builtin.service:
            name: webapp
            state: restarted

        - name: Notify ops
          ansible.builtin.debug:
            msg: "Rollback completed for {{ inventory_hostname }}"
      when: rollback_tag is defined
```

Explanation:
* `serial: 5` limits concurrent hosts, creating 4 batches.  
* `pre_tasks` drain the host from the LB before stopping the service.  
* `post_tasks` health‑check the new version and re‑enable the host.  
* `rescue` block runs if any task in the play fails, performing a rollback to a known good tag and restarting the service.  
* Handlers ensure the service starts cleanly after a stop.

This approach maintains availability (old version still serving until the new one passes health checks) and provides an automated rollback path.<|END_TEXT|>
