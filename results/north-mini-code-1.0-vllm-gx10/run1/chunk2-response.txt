<|END_THINKING|><|START_TEXT|>**K1** – *Difference between a Deployment and a StatefulSet*  
- **Deployment**: Manages stateless, replica‑based workloads. Pods are created with unique names (`pod‑template‑xxxx`) but are interchangeable; scaling, rolling updates, and rollbacks work on the whole set. No guaranteed stable network identifiers or ordered deployment.  
- **StatefulSet**: For stateful applications that need stable, unique pod identities (`pod‑0`, `pod‑1`, …) and ordered deployment/termination. Maintains a headless Service, persistent volume claims, and sticky identities. Supports rolling updates that respect pod names and ordinal ordering.

**K2** – *How a ClusterIP Service routes traffic to pods*  
1. Client (usually another pod) contacts the Service’s cluster‑wide IP.  
2. kube‑proxy (IPTables or IPVS) intercepts the destination IP, looks up the Service’s endpoints in its data plane, and rewrites the packet to one of the backing pod IPs (chosen by round‑robin or other externalTrafficPolicy).  
3. The pod receives the request.  
If the Service selects multiple endpoints, kube‑proxy load‑balances across them; if a single endpoint exists, traffic goes directly.

**K3** – *PersistentVolume, PersistentVolumeClaim, and StorageClass*  
- **PersistentVolume (PV)**: A storage resource in the cluster (block or NFS) that has been provisioned by an external provider (e.g., AWS EBS, GCE PD). It is abstract and not directly usable by pods.  
- **PersistentVolumeClaim (PVC)**: A request for storage made by a workload. A pod mounts a PVC, and the kube‑let binds it to an existing PV that matches the PVC’s size and access modes.  
- **StorageClass**: A definition that describes the “class” of storage (e.g., `standard`, `gp2`, `ssd`). It includes provisioning parameters (reclaim policy, volumeBindingMode, allowed topologies). When a PVC does not specify a StorageClass, the default is used; the PV is provisioned on demand based on that class.  
*Relation*: StorageClass → (dynamic) PV creation → PVC binds to PV → pod mounts PVC.

**K4** – *Troubleshooting a pod in CrashLoopBackOff (4+ distinct checks)*  
1. **Container logs** – `kubectl logs <pod>` (or `kubectl logs -p` for previous instance) to see error messages, OOM kills, or startup failures.  
2. **Resource limits** – Verify `requests` vs `limits` (especially memory/CPU). If the pod exceeds limits, the kube‑let may kill it, causing restarts.  
3. **Image/pull issues** – Check `kubectl describe pod`; look for `ImagePullBackOff` or `ErrImagePull`. Ensure registry credentials, network connectivity, and image tags exist.  
4. **Configuration / health‑check failures** – Examine readiness/liveness probe definitions; a failing probe can cause the pod to be restarted if `restartPolicy: Always`. Also inspect ConfigMaps/Secrets mounts, environment variables, and command/args.  
5. **Node/system state** – Review node events (`kubectl describe node`) for pressure (disk, memory, PID) or taints that could affect scheduling. Also check if the pod’s `terminationGracePeriodSeconds` is too short.

**K5** – *Role of CoreDNS and impact of its failure*  
- **CoreDNS**: The cluster’s DNS service, running as a Deployment. It resolves cluster‑local names (e.g., `myservice.namespace.svc.cluster.local`) and forwards external queries to upstream DNS (e.g., Google DNS, Cloudflare). It also provides additional scoped plugins (metrics, health‑checking, etc.).  
- **If CoreDNS pods are down**: Pod DNS resolution fails for internal names; pods may only resolve external domains if an alternative DNS (e.g., node‑level `/etc/resolv.conf`) is used. The kube‑let will stop updating its internal DNS cache, causing `NXDOMAIN` or long timeouts for cluster services. The cluster may become partially unusable until CoreDNS is restored.

**K6** – *Kubernetes scheduler decision process (filtering, scoring, ≥3 factors)*  
1. **Filtering (predicates)** – Nodes that do **not** meet requirements are removed. Common predicates:  
   - *GeneralPredicate*: enough CPU, memory, ports, etc.  
   - *NodeAffinity*: node selector/taint/toleration mismatch.  
   - *PodAffinity/PodAntiAffinity*: placement constraints.  
   - *VolumeZone*: PV zone compatibility.  
2. **Scoring (priorities)** – Remaining nodes are ranked. Key factors:  
   - *ResourceAllocation*: remaining CPU/memory (higher score for more free resources).  
   - *NodeAffinity*: weight of affinity rules.  
   - *InterPodAffinity*: penalty for violating anti‑affinity.  
   - *NodePrefered* (e.g., `node.kubernetes.io/instance-type` weight).  
   - *Taint/Toleration*: nodes with tolerations get higher priority.  
3. **Selection** – The node with the highest aggregated score is chosen; ties are broken by lexicographic order of node names.

**K7** – *Scheduling with memory requests/limits and runtime usage*  
- **Scheduling**: The scheduler checks **requests** (256 Mi) against node allocatable memory. The node has 4 GB total, 3.5 GB already requested → 0.5 GB free. Since 256 Mi < 0.5 GB, the pod **will be scheduled**. Limits are not considered for admission.  
- **Runtime usage**: If the pod actually consumes 600 Mi, it exceeds its limit (512 Mi). The kube‑let’s OOM killer will terminate the container that exceeds the limit (usually the one with highest memory usage). The pod may restart (if `restartPolicy: Always`) and could be evicted again, leading to CrashLoopBackOff.

**K8** – *Full lifecycle of a request hitting an Ingress (NGINX) → pod*  
1. **External LB** (AWS ELB, GCE LB, etc.) receives the external IP:port, load‑balances to the Ingress Controller’s Service (type LoadBalancer/NodePort).  
2. **Ingress Controller Service** (ClusterIP/NodePort) routes to the NGINX pods (via Endpoints).  
3. **NGINX Ingress** parses the request path/host against Ingress rules, determines the backend Service (e.g., `myapp-svc`).  
4. **Backend Service** (ClusterIP) receives the request. kube‑proxy (IPTables/IPVS) rewrites the destination to one of the Service’s Endpoints (pod IPs).  
5. **Endpoints** (pod IPs) receive the traffic directly; pod network stack delivers it to the application container.  
6. **kube‑proxy** maintains iptables rules for each Service; NGINX runs as a pod and may also use iptables for its own SNAT/DNAT if needed.

**K9** – *NetworkPolicy*  
- **Purpose**: Defines inbound/outbound allowed traffic for pods in a namespace/cluster.  
- **Default behavior**: If no NetworkPolicy exists, all pods are allowed to communicate with each other (the default “allow all” policy).  
- **Applying a selector‑based policy**: Pods matching the selector inherit the rules; other pods continue to follow the default allow. The policy is additive – it does not block traffic unless explicitly denied.

**K10** – *RollingUpdate vs Recreate*  
- **RollingUpdate**: Gradually replace pods; new replicas are created while old ones are terminated, maintaining the desired replica count throughout. Ideal for stateless apps where downtime must be minimized.  
- **Recreate**: Deletes all existing replicas before creating new ones; brief period where the service is unavailable. Chosen for applications that cannot tolerate concurrent old/new versions (e.g., configuration changes that require a clean restart) or when the deployment strategy must guarantee a clean state.

**K11** – *Namespace and default namespaces*  
- **Namespace**: Logical isolation container for Kubernetes resources (pods, services, deployments, etc.). Provides scoping for names, quotas, RBAC, and network policies.  
- **Default namespaces**: `default` (for untagged resources) and `kube-system` (core cluster components). Additional namespaces may exist (`kube-public`, `kube-node-lease`).

**K12** – *`kubectl describe pod <name>` vs `kubectl get pod`*  
`describe` shows detailed, human‑readable fields that `get` omits, e.g.:  
1. **Pod conditions** (Ready, ContainersReady, PodScheduled).  
2. **Events** (reason codes, timestamps for failures).  
3. **Container resource requests/limits**, environment variables, volume mounts.  
4. **IP addresses** (podIP, hostIP).  
5. **Restart policy** and termination grace period.

**K13** – *ConfigMap and consumption methods*  
- **ConfigMap**: Stores configuration data as key‑value strings, allowing decoupling of config from container images.  
- **Consumption methods**:  
  1. **EnvVar** – mount as environment variables (`env:` in pod spec).  
  2. **Projected volume** – combine multiple ConfigMaps/Secrets into a single volume.  
  3. **File mount** – mount as a directory where each key becomes a file (`volumes:` with `configMap`).

**K14** – *ClusterIP, NodePort, LoadBalancer*  
- **ClusterIP**: Internal-only service, reachable only from within the cluster. No external IP.  
- **NodePort**: Exposes the service on a static port (30000‑32767) on each node’s IP; external clients can hit `<node-ip>:<nodeport>`.  
- **LoadBalancer**: Creates an external load balancer (cloud provider specific) that proxies traffic to the service, providing a stable external IP and load‑balancing at the cloud level.

**K15** – *DaemonSet*  
- **Definition**: Ensures a copy of a pod runs on all (or a subset of) nodes, typically for node‑level services (e.g., log collectors, node exporters).  
- **When to use vs Deployment**: Use DaemonSet when the workload is node‑specific and must run on every node (or a label‑selected subset). Use Deployment for workload that should run as a set of replicas across the cluster, independent of node count.

**K16** – *Taints & tolerations vs node affinity*  
- **Taints**: Applied to nodes to repel pods that don’t tolerate them (`node.spec.taints`).  
- **Tolerations**: Applied to pods to allow them to schedule onto tainted nodes.  
- **Node affinity**: Declarative “soft” or “hard” rules that schedule pods to nodes matching label selectors (e.g., `nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution`).  
- **Practical use**:  
  - *Taint/Toleration*: “NoSchedule” a GPU node for general workloads, but tolerate GPU‑specific pods.  
  - *Node affinity*: Prefer scheduling database pods on larger‑memory nodes (`nodeAffinity.preferredDuringSchedulingIgnoredDuringExecution`).

**K17** – *Kubernetes Operator*  
- **Definition**: A controller that extends Kubernetes API to manage complex applications. Operators are packaged as Go/Python/Helm charts that encode operational knowledge (install, update, backup).  
- **Difference from standard controller**: Standard controllers are built‑in (e.g., Deployment controller) and manage a single resource type; Operators are **custom** controllers that watch custom resources (CRDs) and perform reconciliation logic.  
- **Problems solved**: Reduces manual ops, ensures consistent lifecycle, handles versioning, scaling, and disaster recovery for domain‑specific applications (e.g., databases, monitoring).

**K18** – *etcd consistency model and quorum loss*  
- **Consistency model**: etcd provides **linearizable (strong) consistency** via a Raft protocol. All writes go through a quorum (majority) of etcd members; reads can be served from a quorum or from a leader‑cached store.  
- **If quorum is lost**: The cluster cannot commit new writes; the remaining minority nodes become **read‑only** (if configured) or become unavailable. Kubernetes API server may become unresponsive for writes, causing controller manager failures.  
- **Recovery from loss of 2/3 nodes**:  
  1. **Restore from snapshot**: Use the latest snapshot (`etcd-snapshot`) from the surviving node (if any) or from a backup.  
  2. **Reconstruct data directory** on new nodes, copy snapshot, and start etcd with `--initial-cluster` reflecting the original member list (including lost nodes).  
  3. **Add new members** and remove the lost ones once the cluster reaches a new quorum.  
  4. **Recover Kubernetes state** via `kube-apiserver --etcd-prefix` restoration or `kubeadm init --experimental-control-plane` with `--etcd-member` options.

**K20** – *ndots causing slow DNS and fixing with dnsConfig*  
- **ndots**: In `/etc/resolv.conf`, `options ndots:3` tells glibc to query external DNS only after trying search domains that have ≥3 dots. Pods often have a default search domain (`svc.cluster.local`), causing glibc to try that first; if it fails, it queries external DNS, but the extra search attempts add latency, leading to >5 s resolution.  
- **Fix**: Use `dnsConfig` in the pod spec to override `ndots`:  

```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "1"   # try external DNS immediately
```

Alternatively, set `dnsPolicy: Default` and add `dnsConfig` with `nameservers` to use a faster upstream resolver.

**D1** – *git rebase vs git merge*  
- **Rebase**: Rewrites history by moving the current branch onto the target branch’s tip, creating a linear timeline. Useful for cleaning up feature branches.  
- **Merge**: Creates a merge commit that combines histories, preserving the original branch structure.  
- **When to avoid rebasing**: When the branch has already been pushed to a shared repository (e.g., main branch) and other collaborators have based work on it. Rebasing would rewrite public history, causing conflicts.

**D2** – *TCP vs UDP*  
- **TCP**: Connection‑oriented, reliable, ordered byte stream; uses three‑way handshake, acknowledgments, retransmissions. Protocols: HTTP, SMTP, FTP.  
- **UDP**: Connectionless, unordered, no reliability guarantees; low‑overhead, suitable for time‑sensitive traffic. Protocols: DNS, DHCP, VoIP.

**D3** – *Race condition*  
- **Definition**: When two or more threads/processes access shared data concurrently, and the final outcome depends on the order of execution.  
- **Concrete example (Python)**:  

```python
counter = 0

def increment():
    global counter
    counter += 1   # not atomic: read, increment, write

# Two threads call increment() simultaneously → counter may end up 1 instead of 2.
```

**D4** – *Symmetric vs asymmetric encryption & TLS*  
- **Symmetric encryption**: Same key for encrypt/decrypt; fast, used for bulk data (e.g., AES).  
- **Asymmetric encryption**: Public/private key pair; slower, used for key exchange and signatures (e.g., RSA, ECC).  
- **TLS usage**: Client and server perform an asymmetric handshake to exchange/agree on a pre‑shared symmetric key (e.g., via ECDHE). Subsequent application data is encrypted symmetrically for performance.

**D5** – *Container image layer*  
- **Definition**: Each instruction in a Dockerfile creates a new read‑only layer; layers are cached and reused on subsequent builds if preceding instructions unchanged.  
- **Layer caching impact**: Place frequently changing instructions (e.g., `COPY` of source code) later in the Dockerfile so they don’t invalidate earlier cached layers (like `RUN pip install`). Use multi‑stage builds to keep final image small.

**D6** – *Investigating intermittent HTTP 503* (order)  
1. **Application logs** – Look for errors, crashes, or resource exhaustion in the service that returns 503.  
2. **Health‑check configuration** – Verify liveness/readiness probes; mis‑configured probes can cause premature restarts.  
3. **External dependencies** – Check database, cache, message queue connectivity; transient failures often surface as 503.  
4. **Infrastructure** – Review pod/container metrics (CPU, memory, network), node conditions, and any recent deployments or config changes.  
5. **Load balancer / proxy** – Inspect upstream health checks, circuit‑breaker states, or rate‑limiting rules in ingress controllers.

**D7** – *CAP theorem*  
- **Definition**: A distributed system can provide at most two of **Consistency**, **Availability**, **Partition tolerance**.  
- **CP example**: A relational database like **PostgreSQL** with synchronous replication – guarantees consistency and partition tolerance (availability sacrificed during network partitions).  
- **AP example**: **Cassandra** – prioritizes availability and partition tolerance; reads may return slightly stale data to stay available.

**D8** – *Horizontal vs vertical scaling*  
- **Horizontal scaling**: Add more instances of a service; each instance handles a subset of load. Enabled by stateless design, load balancers, and orchestration (Kubernetes Deployments, service mesh).  
- **Vertical scaling**: Increase resources (CPU, memory) of a single instance. Limited by the maximum size of a VM/container and can cause contention.  
- **Architectural patterns for horizontal scaling**: Microservices, sharding, load‑balanced clusters, auto‑scaling based on metrics, and using a service mesh for traffic distribution.

**D9** – *Environment variable*  
- **Definition**: A variable passed to a process at runtime, providing configuration (e.g., `PORT`, `DB_URL`).  
- **Persist across shell sessions on Linux**: Add to `~/.bashrc` or `~/.profile` (e.g., `export MY_VAR=value`). Then source the file (`source ~/.bashrc`) or open a new terminal.

**D10** – *JSON vs YAML*  
- **JSON**: JavaScript‑centric, strict syntax, no comments, always quoted keys, human‑readable but verbose. Advantage: native parsing in many languages, easy to generate programmatically.  
- **YAML**: Human‑friendly, supports comments, indentation‑based syntax, can represent complex hierarchies succinctly. Advantage: readability for configuration files, easy to write by humans.

**D11** – *REST API*  
- **Definition**: Architectural style for networked applications using HTTP methods to perform standard operations on resources.  
- **HTTP methods**:  
  - **GET** – retrieve a resource (idempotent).  
  - **POST** – create a new resource (non‑idempotent).  
  - **PUT** – replace an existing resource entirely (idempotent).  
  - **DELETE** – remove a resource (idempotent).

**D12** – *Version pinning*  
- **Definition**: Explicitly specifying exact versions of dependencies (e.g., `package@1.2.3`).  
- **Importance**: Guarantees reproducible builds, prevents unexpected breaking changes, and ensures consistent behavior across environments.

**D13** – *Compiled vs interpreted languages*  
- **Compiled**: Source code translated to machine code before execution. Examples: C, C++.  
- **Interpreted**: Source code executed directly by an interpreter at runtime. Examples: Python, JavaScript.

**D14** – *Reverse proxy vs forward proxy*  
- **Reverse proxy**: sits in front of servers, distributes client requests to backend services; hides internal topology (e.g., NGINX, HAProxy). Use case: load balancing HTTP traffic.  
- **Forward proxy**: sits on client side, forwards client requests to external servers; often used for caching, filtering, or anonymity. Use case: corporate internet access control.  
- **Common reverse proxies**: NGINX, HAProxy, Envoy.

**D15** – *Deadlock & Coffman conditions*  
- **Deadlock**: Two or more processes wait indefinitely for resources held by each other.  
- **Coffman conditions** (must all hold):  
  1. **Mutual exclusion** – resources not shareable.  
  2. **Hold and wait** – process holds resources while requesting others.  
  3. **No preemption** – resources cannot be forcibly taken.  
  4. **Circular wait** – chain of processes each waiting for resource held by next.

**D16** – *Eventual consistency*  
- **Concept**: In a distributed system, updates propagate asynchronously; reads may see stale data for a period, but eventually converge to the latest value.  
- **Cassandra read‑after‑write**: Uses `WRITE` replication and `READ` quorum settings. By default, a write is considered successful after a write‑quorum of nodes acknowledge; subsequent reads with a quorum will see the latest data.  
- **Tunable consistency levels**: `ONE`, `QUORUM`, `ALL`, `LOCAL_ONE`, `SERIAL`, etc., allowing trade‑offs between latency and consistency.

**D17** – *mTLS (mutual TLS)*  
- **Definition**: TLS where both client and server present X.509 certificates for authentication.  
- **Handshake**:  
  1. Client sends **ClientHello** with supported ciphers and a **CertificateRequest** (if server needs client cert).  
  2. Server replies with **ServerHello**, **ServerCertificate**, and optionally **CertificateRequest** for client.  
  3. Client sends **ClientCertificate**, **ClientKeyExchange**, and **CertificateVerify** (proves possession of private key).  
  4. Both derive a pre‑master secret, compute master secret, and generate session keys.  
  5. Server may request client authentication via **CertificateVerify**; if missing or invalid, handshake aborts.  
- **Common uses**: Service‑to‑service communication in service meshes (Istio, Linkerd), API gateways, and internal APIs where mutual authentication is required.

**D18** – *Hash table internals*  
- **Structure**: Array of buckets; each bucket holds either a single key‑value pair (open addressing) or a linked list/chain of entries (chaining).  
- **Collision resolution**:  
  - *Chaining*: Colliding keys stored in a linked list; bucket size grows with collisions.  
  - *Open addressing*: Probe sequence (linear, quadratic, double hashing) to find next free slot.  
- **Time complexity**:  
  - **Average**: O(1) for insert, lookup, delete (assuming good hash function, load factor < 0.7).  
  - **Worst**: O(n) when many collisions (e.g., all keys hash to same bucket) or table is full in open addressing.

**D19** – *Circuit breaker pattern*  
- **Purpose**: Detects failures and temporarily blocks requests to a failing service to prevent cascade failures.  
- **States**:  
  1. **Closed** – Normal operation; requests flow, failures counted.  
  2. **Open** – Failure threshold exceeded; further requests short‑circuit immediately (e.g., exception) without invoking the remote service.  
  3. **Half‑open** – After a timeout, a single test request is allowed; if succeeds, re‑close; if fails, reopen.  
- **Relation to retry & backoff**: Circuit breaker works alongside retry policies; retries are attempted while closed, but when open, retries are suppressed. Exponential backoff can be used within the half‑open test to avoid overwhelming a recovering service.

**D20** – *Optimistic vs pessimistic concurrency control*  
- **Optimistic concurrency control (OCC)**: Assume conflicts are rare; transactions proceed without locking, validate at commit time (e.g., using version numbers or timestamps). If validation fails, transaction is rolled back and retried.  
- **Pessimistic concurrency control (PCC)**: Lock resources upfront (e.g., `SELECT FOR UPDATE`, row locks) to prevent others from modifying the same data.  
- **When to choose each**:  
  - *OCC*: High read/write contention with low conflict rates (e.g., social media feeds).  
  - *PCC*: High contention on same rows (e.g., financial transactions) where consistency is critical.  
- **Concrete example**:  
  - *OCC*: Update a product inventory using a version field; `UPDATE products SET qty = qty - 1, version = version + 1 WHERE id = ? AND version = ?`. If the version mismatch, retry.
