**JS2** – The **event loop** continuously checks whether the call stack is empty. If it is, it processes the **macrotask queue** (e.g., setTimeout, setImmediate, I/O callbacks). After the macrotask queue is empty, it processes the **microtask queue** (e.g., Promise `.then` callbacks, queueMicrotask). Microtasks are completed before the next macrotask, ensuring that asynchronous operations resolve before the next scheduled task runs.

**JS6** – JavaScript uses **prototypal inheritance**: objects inherit directly from other objects via `__proto__` or `Object.getPrototypeOf`. `Object.create(proto)` creates a new object with `proto` as its prototype, without invoking a constructor. **JS7** – `this` refers to the **object** that is executing the current function. The four binding rules in priority order:
1. **Explicit binding** (`.call`, `.apply`, `.bind`) – you set `this` directly.
2. **Implicit binding** – `this` is the object preceding the dot (or undefined in strict mode for plain functions).
3. **New binding** – when a function is called with `new`, `this` becomes the newly created instance.
4. **Default binding** – `this` is the global object (or `undefined` in strict mode) if none of the above apply.

`bind()` returns a **new function** with `this` permanently set; you can call it later and it will retain the bound `this`. You can re‑bind by calling `bind` again on the bound function (or using `Function.prototype.bind` with new arguments).

**JS8** – `WeakRef` holds a **weak reference** to an object; the referent can be garbage‑collected and the `WeakRef` will become dead (`.deref()` returns `null`). `FinalizationRegistry` lets you register a callback that runs when a target object is about to be collected. **JS9** – V8 optimizes JavaScript via **hidden classes** (shapes) that track property order and type; **inline caching** records which class of object a property access sees and generates specialized code. **Deoptimization** occurs when the hidden class changes (e.g., adding a property to an existing object) or when code fails assumptions (e.g., typeof checks, instanceof). Patterns that cause deoptimization: adding properties to objects after they’ve been accessed, using `delete`, mixing property types, relying on `instanceof` with non‑native constructors, or using `eval`/`with`.

**JS10** – **Tree‑shaking** is static dead‑code elimination of unused exports. **B7** – Redirection differences:
```bash
cmd > file 2>&1   # stdout → file, stderr → stdout (which is now redirected to file)
cmd 2>&1 > file   # stderr → stdout, then both → file (order of redirection matters)
cmd &> file        # POSIX shorthand, same as `cmd 2>&1 > file`
```
The first two produce different results because in `cmd > file 2>&1`, `2>&1` redirects stderr to the **original** stdout (which is already redirected to `file`), so both go to `file`. In `cmd 2>&1 > file`, `2>&1` redirects stderr to the **original** stdout (still the terminal), then `> file` redirects that combined stdout/stderr to `file`. The net effect is the same on most shells, but subtle differences appear with scripts that rely on exit status or with `set -e`.

**B8** – ```bash

  # Remove pid file

**B14** – `trap` sets signal handlers:

**B17** – Subshell `(...)` creates a new process; variables assigned inside do **not** affect the parent. Group command `{ ...; }` runs in the current shell; variables persist. **B18** – Bash handles signals via `trap`. `SIGINT` (Ctrl‑C) and `SIGTERM` (kill) terminate; `SIGHUP` (hangup) also terminates unless the process is a login shell; `SIGKILL` cannot be caught. Graceful shutdown: trap signals, kill background jobs, wait for them, then exit.

**PS2** – The pipeline passes objects from left to right; `ForEach-Object` (`%`) processes each object via a script block; `foreach` statement iterates over a collection (array, range, etc.) and is faster for large static collections. Use `ForEach-Object` for pipeline scenarios; `foreach` for simple loops over known collections.

**PS3** – `[PSCustomObject]` creates a custom object with dynamic properties; `[hashtable]` is a dictionary (`@{}`). Use a hashtable for hash‑table operations; use PSCustomObject for pipeline objects that need `.PSObject.Properties`. Conversion: `[PSCustomObject]$ht` or `$ht | ForEach-Object { [PSCustomObject]$_ }`.

**PS4** – Terminating errors stop the pipeline immediately (e.g., `Throw`); non‑terminating errors (e.g., `Write-Error`) continue. `-ErrorAction` (`-EA`) sets behavior per command; `$ErrorActionPreference` is the session default; `try/{...}catch{...}` catches terminating errors only. Interaction: `-EA Stop` behaves like an uncaught terminating error; `try` can also catch non‑terminating errors if `$PSDebugContext` is set.

**PS5** – Splatting: `@params` unpacks a hashtable into named parameters:
```powershell
$params = @{ComputerName='srv01'; Credential=$cred}
Invoke-Command @params -ScriptBlock { ... }
```
Differs from passing a single hashtable because the latter would bind the hashtable as a positional argument, not as named parameters.

**PS6** – `Invoke-Command -ComputerName` runs a script block on a remote machine without interactive session; `Enter-PSSession` creates an interactive session (persistent). Both use **WinRM** (Windows) or **SSH** (when using `Enter-PSSession -HostName`). `Invoke-Command` is fire‑and‑forget; `Enter-PSSession` maintains state.

**PS7** – The function returns an **array** (`@()`), so `$x` is an array object. `$x.GetType().Name` yields `"Object"` because PowerShell treats arrays as `object`. With zero items, `$x` is still an array (`@()`). Correct pattern: `return $result` (already) or use `Write-Output` inside the function for pipeline‑friendly output; avoid returning `$result` directly if you want each item streamed.

**PS8** – `[scriptblock]` is a compiled block of code; a function is a scriptblock with metadata (name, parameters). Pass a scriptblock to a remote session via `-ScriptBlock` parameter. Double‑hop problem: credentials used for first hop cannot be forwarded automatically; solve with `CredSSP` (`-Authentication Credssp`) or `Invoke-Command -ArgumentList` to pass variables explicitly.

**PS9** – `@()` creates an empty array; `[array]` is a type accelerator for `[object[]]`. To force a single result into an array: `@(value)` or `[value]`. Indexing `$null` throws; indexing an empty array returns `$null` (or throws if out of bounds depending on `$ErrorActionPreference`).

**PS10** – `-eq`/`-ne` case‑sensitive equality; `-ceq`/`-clike` case‑insensitive. `-like` uses wildcards; `-match` uses regex. `-contains` checks if a collection contains a specific value; `-in` checks if a value is in a collection. Example: `'abc' -like 'a*'` true; `'abc' -match '^a'` true.

**PS11** – A **module** groups functions, cmdlets, variables. Script module (`.psm1`) contains procedural code; manifest module (`.psd1`) defines metadata and can import script modules; binary module (`.dll`) is a compiled .NET assembly providing cmdlets. `Import-Module` loads the module into the session, making its commands available.

**PS12** – Interpolation: `"$var"` or `"{0}"` style. Double quotes allow `$` expansion; single quotes are literal. Include expressions: `"$($obj.Property)"`. Here‑string (`@"..."@`) preserves newlines and backslashes, useful for multi‑line strings.

**PS13** – `Get-Member` shows properties, methods, note properties of an object. Properties are defined on the class; Methods are callable; NoteProperties are added at runtime via `-Property`. `Select-Object` projects properties; `Where-Object` filters based on scriptblock.

**PS14** – PowerShell classes (v5+) are .NET‑backed; they support properties, methods, constructors, but inheritance is limited to single class and cannot inherit from arbitrary .NET types without `[System.Object]`. Interfaces can be implemented. Use classes for complex data with validation; functions are preferred for simple scripts.

**PS15** – `[CmdletBinding()]` enables common parameters (`-Verbose`, `-WhatIf`). `SupportsShouldProcess` enables `-WhatIf`/`-Confirm`. `DefaultParameterSetName` selects which parameter set is used. `ValueFromPipeline` allows input from pipeline. `Begin/Process/End` blocks in advanced functions separate initialization, per‑object processing, and finalization.

**PS16** – Providers abstract namespaces as filesystems. `Get-ChildItem` works across `FileSystem`, `Registry`, `Certificate`, `Environment`. Access registry: `Get-ChildItem -Path 'Registry::HKCU:\Software'`.

**PS17** – Runspaces are isolated .NET execution contexts. `[runspace]` represents a single pipeline execution; `[runspacepool]` manages a pool of runspaces; `[powershell]` object holds script and arguments. `ForEach-Object -Parallel` (v7+) uses internal runspace pools; manual management gives finer control over thread safety and resource limits.

**PS18** – `PSScriptAnalyzer` is a static analysis tool that enforces coding standards via rules (e.g., `PSUseConsistentIndentation`). Severity levels: Error, Warning, Information. Custom rules can be added. Suppress with `# PSScriptAnalyzer: enable Disable`. Integration: add to CI pipelines (e.g., Azure DevOps, GitHub Actions) to fail builds on violations.

**PS19** – `$using:` scope allows passing variables to remote sessions without serialization (direct reference). `$args`/`-ArgumentList` serialize arguments for background jobs and remote sessions. Serialization depth (`CLIXML`) limits nested object graphs; exceeding it throws `SerializationException`. Use `$using:` for simple variables; for complex objects, flatten or pass references.

**PS20** – DSC defines **configurations** (desired state) using **resources** (e.g., `File`, `Package`). The **Local Configuration Manager (LCM)** on each node enforces the configuration. Windows PowerShell DSC uses `powershell.exe` and `LCM` service; PowerShell 7+ uses `dsc` cmdlets and integrates with `PSDesiredStateConfiguration`. Modern IaC (e.g., **Terraform**, **Ansible**, **Pulumi**) has largely superseded DSC, offering agent‑based, cross‑platform provisioning.<|END_TEXT|>
