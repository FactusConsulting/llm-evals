**CL3 – Medium**  
| Concept | What it is | Typical scope |
|---------|------------|---------------|
| **VPC** | Isolated logical network in the cloud (e.g., AWS VPC, Azure VNet). | Whole tenant‑level network. |
| **Subnet** | Portion of a VPC divided by IP range; used to place resources. | Within a VPC, defines address space for a set of VMs/containers. |
| **Security Group** (SG) | Stateful, host‑level firewall attached to individual instances (VM, container). Rules are applied per‑instance. | Works at the instance level; rules are stateful (allow response automatically). |
| **Network ACL** (NACL) | Stateless, subnet‑level firewall (layer‑3). Rules are evaluated in order, allow/deny inbound/outbound. | Operates at the subnet level; must be explicitly allow both directions. |

**Layering:** VPC → Subnet → NACL (subnet‑wide) + Security Groups (instance‑wide). Traffic passes through the NACL first, then the instance’s SG.  

**Stateful vs Stateless:**  
*Stateful* (SG) automatically permits return traffic that matches an established connection, simplifying rule sets.  
*Stateless* (NACL) requires explicit rules for both inbound and outbound; you must allow the response separately.

**CL4 – Medium**  
**Landing‑zone concept** – A hardened, baseline environment (network, IAM, logging, guardrails) that serves as the “entry point” for all workloads across multiple accounts.  

**Organizational Units (OUs)** – Logical containers (AWS Organizations / Azure Enterprise Cloud Management) that group accounts by business unit, environment (dev/test/prod), or project, enabling centralized policy enforcement.  

**Guardrails** – Baseline security controls (IAM policies, tagging, encryption defaults, service quotas) applied via Service Control Policies (SCPs) or Azure Policy to prevent mis‑configurations.  

**Shared networking** –  
*AWS:* Transit Gateway interconnects VPCs across accounts/regions; each account’s VPC attaches, creating a hub‑and‑spoke topology.  
*Azure:* Hub‑and‑Spoke using Virtual WAN or Azure Firewall/DNS‑Forwarding. Spoke VNet’s connect to the hub, enabling cross‑account traffic while keeping isolation.  

**Centralized logging** – CloudTrail/AuditLogs, FlowLogs, and OS logs forwarded to a central SIEM or log analytics (e.g., AWS CloudWatch Logs Insights, Azure Monitor) with retention and alerting.  

**Why single‑account is problematic** –  
* Limited isolation → accidental cross‑environment contamination.  
* Harder to apply least‑privilege per project.  
* No natural boundary for cost allocation.  
* Increased blast radius for compromises.

**CL7 – Hard**  
**RPO / RTO considerations** – Define acceptable data loss (RPO) and downtime (RTO). Example: RPO ≤ 5 min, RTO ≤ 30 min → active‑active design.  

**Active‑active vs Active‑passive** –  
*Active‑active*: Both regions serve traffic; writes are replicated (sync/async) and DNS routes based on health/latency. Provides highest availability but higher complexity and cost.  
*Active‑passive*: Primary region handles all traffic; secondary is idle (warm or cold). Simpler, lower cost, longer RTO.  

**Database replication** –  
*Sync* (synchronous) → strong consistency, higher latency, suitable for financial data.  
*Async* → lower latency, eventual consistency, acceptable for many apps.  

**DNS failover** – Use Route 53 health checks or Azure Traffic Manager; TTL set low (e.g., 30 s) to quickly switch.  

**State management** – Use distributed caches (Redis Cluster), shared object stores (S3/Blob), or CRDTs; consider eventual consistency patterns.  

**Cost implications** – Active‑active doubles compute, networking, and storage costs; need to rightsize, use spot where possible, and apply data tiering.  

**DR patterns** –  
*Pilot Light*: Minimal core (e.g., a single VM) that can be spun up quickly; RTO ≈ hours‑days.  
*Warm Standby*: Core services plus data snapshots; RTO ≈ minutes‑hours.  
*Multi‑site Active‑Active*: Full production in both regions; RTO ≈ seconds‑minutes, highest cost.

**CL8 – Hard**  
**GitOps model** – All infrastructure and application state is stored as declarative manifests in Git. A Git‑focused controller (ArgoCD, Flux) continuously reconciles the cluster state to the Git state, triggering automated rollouts.  

**ArgoCD vs FluxCD**  
*ArgoCD*: Event‑driven, uses a declarative “application” resource, offers rich UI, automated sync, and built‑in health checks.  
*FluxCD*: Uses Helm charts and Kustomize, focuses on “Git‑ops with progressive delivery”, supports image automation and cross‑cluster sync.  

**Secrets handling** –  
*Sealed Secrets*: Encrypt secrets in Git, decrypt at runtime by the cluster (kubectl‑sealed‑secrets).  
*External Secrets Operator*: Pulls secrets from external vaults (HashiCorp Vault, AWS Secrets Manager) into Kubernetes Secret objects.  
*Vault*: Can be used via TLS/CLI or via the External Secrets Operator; supports dynamic secrets and lease management.  

**Drift handling** – If a manual change diverges from Git, the controller detects a drift and will automatically revert (or raise an alert) to enforce desired state, ensuring compliance and auditability.

**CL9 – Hard**  
**Architecture for a stateful legacy app on K8s**  

1. **StatefulSet** – Provides stable pod identifiers (`$(metadata.name)`), ordered deployment, and sticky storage.  
2. **PV/PVC with local storage class** – Use a `local-path` or `ebs` storage class that maps to host directories; ensures low‑latency local storage.  
3. **Headless Service** (`clusterIP: None`) – Enables DNS resolution to stable pod names (`pod-0`, `pod-1`) for stateful communication.  
4. **Init Containers** –  
   * Copy config files from ConfigMap/Secret into the persistent volume.  
   * Perform health checks, database migrations, or version‑specific setup before the app container starts.  
5. **ConfigMaps as volume mounts** – Mount ConfigMaps as read‑only volumes; the app reads configuration from known paths (e.g., `/etc/config/app.conf`).  
6. **Pod Disruption Budgets (PDB)** – Set `minAvailable` or `maxUnavailable` to guarantee a minimum number of pods stay available during maintenance (e.g., `minAvailable: 2`).  
7. **Anti‑affinity rules** – Spread pods across nodes/zones to avoid a single point of failure.  
8. **Lifecycle hooks** – Pre/stop hooks for graceful shutdown, ensuring data flush.  

Result: Ordered startup, persistent low‑latency storage, config baked into known paths, and resilience against disruptions.

**CL10 – Medium**  
* **Service Account** – A Kubernetes object that provides an identity for pods to access the API server (e.g., `default`, custom).  
* **Workload Identity** – The broader concept of associating a workload’s identity (pod) with cloud‑provider permissions, often via OIDC.  
* **IRSA (IAM Roles for Service Accounts)** – AWS implementation: a service account is annotated with an IAM role ARN; the pod assumes that role via OIDC, no long‑term credentials in the pod.  

**Why mounting cloud provider credentials is bad** – Credentials in containers are long‑lived, can be leaked, are hard to rotate, and violate the principle of least privilege.  

**Workload identity federation** – Uses OIDC tokens from the cloud provider (e.g., EKS, GKE) that are exchanged for short‑lived cloud credentials (or directly assumed IAM roles) without storing static keys in the pod. This provides ephemeral, auditable, and least‑privilege access.

**CL12 – Hard**  
**Zero‑Trust Network for a Cloud K8s Cluster**  

1. **Network Policies** – Define ingress/egress at pod/namespace level; deny‑by‑default, allow only required traffic.  
2. **Service Mesh (e.g., Istio, Linkerd) with mTLS** – Enforce mutual TLS between all services, provide telemetry, traffic management, and automatic authentication.  
3. **Pod Identity** – Use IRSA/Workload Identity to give pods only the IAM roles they need; avoid static service accounts.  
4. **Admission Controllers** – OPA Gatekeeper / Kyverno enforce policies (resource limits, image trust, namespace labels) at creation time.  
5. **Image Signing & Verification** – Cosign, Notary, or Azure Key Vault; enforce that only signed images run (policy‑enforced via admission controllers).  
6. **Runtime Security (Falco)** – Monitor system calls, container runtime events; generate alerts on anomalous behavior (e.g., unexpected binaries).  
7. **Secrets Management** – External Secrets Operator pulling from Vault/HSM; never store secrets in ConfigMaps or image layers.  

**Difference from perimeter‑based security** – Traditional models trust everything inside the network boundary. Zero‑trust assumes no implicit trust; every request is authenticated, authorized, and encrypted, regardless of source. It also enforces least‑privilege at the micro‑service level, provides continuous verification, and reduces blast radius of compromises.

**CL20 – Hard**  
**Multi‑cloud strategy (AWS + Azure) to avoid lock‑in**  

1. **Abstraction layers** – Use container images and Kubernetes API as the portable substrate; abstract storage, networking, and databases behind Kubernetes‑native APIs (e.g., CSI drivers, external secrets).  

2. **Kubernetes as common runtime** – Deploy a managed K8s service on each cloud (EKS, AKS) or use a managed Kubernetes service that supports multi‑cloud (e.g., Rancher, Anthos, Azure Arc).  

3. **IaC portability** – Terraform (or OpenTofu) with provider blocks for both AWS and Azure; store state in an object store (e.g., S3 with cross‑region replication) and use workspaces per cloud.  

4. **Networking between clouds** – Use a VPN or Direct Connect/ExpressRoute between on‑prem and each cloud; for inter‑cloud traffic, employ a hub‑spoke topology (AWS Transit Gateway ↔ Azure Virtual WAN) or a third‑party SD‑WAN.  

5. **Identity federation** – Deploy a central IdP (Okta, Azure AD, Auth0) and configure OIDC trusts with both clouds (EKS, AKS) so users/ workloads assume cloud‑specific IAM roles via `sts:AssumeRoleWithWebIdentity`.  

**Trade‑offs** –  
* **Benefits**: Reduced vendor dependence, ability to choose best‑of‑breed services, improved negotiation leverage.  
* **Costs**: Increased operational complexity, need for cross‑cloud tooling, potential performance overhead for inter‑cloud traffic, duplicated expertise.  

**When multi‑cloud is justified** –  
* Geographic compliance (data residency) requiring specific cloud regions.  
* Need for unique services not available on a single provider (e.g., a service only on AWS and another only on Azure).  
* Risk mitigation for a single vendor failure.  

**When it’s unnecessary complexity** –  
* All workloads fit within one provider’s service portfolio.  
* Team lacks expertise to manage multiple environments.  
* Cost savings from a single‑vendor commitment outweigh the benefits of diversification.

**OT1 – Easy**  
The **Purdue Model (ISA‑95)** maps the hierarchy of manufacturing systems:  

| Level | Description |
|-------|-------------|
| **Level 0 – Operations Management** | Business planning, ERP, MES; integrates production scheduling, inventory, and financial data. |
| **Level 1 – Site Management** | Supervision of multiple cells/processes; HMI/SCADA, data collection, basic control. |
| **Level 2 – Control** | PLCs/RTUs executing real‑time control loops; raw data acquisition. |
| **Level 3 – Execution** | Manufacturing execution; data historian, batch control, quality systems. |
| **Level 4 – Enterprise** | Corporate IT systems, ERP, logistics, supply‑chain. |
| **Level 5 – Strategic Planning** | Long‑term planning, production planning, sustainability. |

(Only four levels are required; the above includes five for completeness.)  

---

**OT2 – Easy**  
**IT vs OT networks** – IT networks prioritize data, connectivity, and flexibility; OT networks prioritize real‑time control, deterministic timing, and device reliability.  

**Why standard IT patching doesn’t work for OT** – OT devices often run legacy firmware/OS that cannot tolerate reboots, may have vendor‑supported support windows, and require strict uptime. Patching can disrupt control loops, cause unexpected behavior, or break compatibility with proprietary protocols.  

---

**OT3 – Medium**  
**Industrial DMZ (IDMZ) role** – Acts as a buffer zone between corporate IT (Level 4) and OT control networks (Levels 0‑3).  

**Allowed traffic** –  
* **Inbound**: Authenticated remote access (VPN, jump hosts), software updates, monitoring data from SIEM/OT‑specific tools.  
* **Outbound**: OT data (process values, alarms) to enterprise systems, historian queries, firmware updates from vendor.  

**Direction** – Typically **allow outbound** from OT to DMZ for data export, and **controlled inbound** from DMZ to OT for maintenance.  

**Why direct Level 4 → Level 1 is dangerous** – It exposes critical control devices (PLCs, RTUs) to the broader internet, enabling attackers to issue commands, disrupt processes, or move laterally into the control network.

**OT4 – Medium**  
| Protocol | Typical Purdue level | Notes |
|----------|--------------------|-------|
| **Modbus TCP** | Level 2 (Control) | Simple request/response, widely used for PLCs. |
| **OPC UA** | Level 3 (Execution) | Service‑oriented, secure, can span multiple levels. |
| **EtherNet/IP (CIP)** | Level 2‑3 | Real‑time industrial Ethernet, used by Allen‑Bradley devices. |
| **PROFINET** | Level 2 | Real‑time Ethernet, Siemens automation. |
| **MQTT** | Level 3 (or higher) | Publish/subscribe messaging, often used for telemetry to the cloud. |

---

**OT5 – Medium**  
**Data diode vs firewall** –  
*Data diode*: Unidirectional hardware device allowing only outbound (or inbound) data flow; cannot be manipulated to allow reverse traffic.  
*Firewall*: Bidirectional, policy‑based filtering, can be configured both ways.  

**When to use hardware data diode** – For air‑gapped environments where you must guarantee that sensitive OT data can only flow outward (e.g., to a DMZ) while preventing any inbound commands.  

**Limitation** – Cannot enforce complex policies, inspect payload content, or adapt to dynamic requirements; only provides a hard unidirectional pipe.  

---

**OT6 – Medium**  
**Data flow design**  

1. **SCADA system** → **OPC UA server** (Level 3) publishes process data.  
2. **OPC UA server** → **MQTT broker** (edge) for lightweight telemetry.  
3. **Edge gateway** (e.g., Azure IoT Edge) receives MQTT messages, applies filtering, enriches metadata, and forwards to cloud.  
4. **Cloud ingestion** (e.g., AWS IoT Core, Azure IoT Hub) stores data in a time‑series database or data lake.  

**Security boundaries** –  
* **OT network** (Levels 0‑3) is isolated from corporate IT.  
* **Edge gateway** sits in the DMZ/IDMZ, acting as the only allowed outbound point.  
* **Cloud** is a separate network segment; only the edge gateway has outbound internet access.

**OT7 – Hard**  
**IEC 62443 security zones & conduits**  

* **Zone** – A logical grouping of assets with similar security requirements (e.g., “Corporate Network”, “Engineering Workstation Zone”, “SCADA Server Zone”, “PLC Zone”, “SIS Zone”).  
* **Conduit** – Controlled pathway (usually a firewall or router ACL) that defines allowed traffic between zones, specifying protocols, ports, and direction.  

**Proposed zone‑and‑conduit model**  

| Zone | Assets | Security level | Conduits (example) |
|------|--------|----------------|--------------------|
| **Zone 1 – Corporate IT** | ERP, office workstations, DNS/DHCP | Low (perimeter) | Conduit to Zone 2 (allow HTTPS, DNS) |
| **Zone 2 – Engineering Workstation** | Engineer laptops, CAD servers | Medium | Conduit to Zone 3 (allow OPC UA, VNC) |
| **Zone 3 – SCADA Server** | SCADA HMI, historian, alarm server | High | Conduit to Zone 4 (allow Modbus/TCP, OPC UA) |
| **Zone 4 – PLCs / BPCS** | PLCs, RTUs, I/O modules | Very High | Conduit to Zone 5 (allow only specific PLC protocols) |
| **Zone 5 – SIS (Safety Instrumented System)** | SIS controllers, safety relays | Critical | Air‑gapped (no conduit) or only read‑only conduit to Zone 4 for status. |

Each conduit is enforced by firewalls with strict ACLs, IDS/IPS, and logging.

**OT8 – Hard**  
**Network segmentation for 200 PLCs, 4 lines, 30 HMIs, SCADA, historian**  

1. **VLAN design** –  
   * **VLAN 10** – PLCs per production line (VLAN 10‑13).  
   * **VLAN 20** – HMIs (shared across lines).  
   * **VLAN 30** – SCADA server & historian.  
   * **VLAN 40** – Management (jump hosts, admin workstations).  

2. **Firewall placement** – Layer‑3 firewalls (or next‑gen) between each VLAN pair (e.g., PLC‑to‑HMI, HMI‑to‑SCADA, SCADA‑to‑Corporate). Use access policies that allow only required protocols (Modbus/TCP, OPC UA, VNC).  

3. **Switch architecture** –  
   * **Core switches** (redundant) in a ring for high availability.  
   * **Distribution switches** per line, each connected to core.  
   * **Access switches** directly to PLCs/HMIs; enable port security, MAC limiting, and VLAN assignment.  

4. **Remote vendor access** –  
   * Use a **jump host** in VLAN 40, MFA‑protected.  
   * Vendor VPN tunnels terminate on the jump host; traffic is NATed to the required VLANs.  
   * Session recording and time‑limited credentials.  

5. **Transition without production stop** –  
   * Perform VLAN re‑tagging during a planned maintenance window (short, coordinated).  
   * Use **virtual stacking** or **software‑defined access** to apply new VLAN policies while keeping physical links up.  
   * Validate connectivity with ping/traceroute from each HMI to PLC before and after changes.  

---

**OT9 – Hard**  
**SIS vs BPCS**  

* **BPCS (Basic Process Control System)** – Handles routine control (temperature, pressure, flow). It is the “primary” control loop but not safety‑critical.  
* **SIS (Safety Instrumented System)** – Provides independent protection layers to bring a process into a safe state when hazardous conditions occur; governed by IEC 61511.  

**IEC 61511** – Defines requirements for design, installation, validation, and maintenance of SIS (functional safety lifecycle).  

**Why SIS must be air‑gapped/isolated** – To prevent malicious actors from compromising safety functions that could cause catastrophic events (explosions, toxic releases). Isolation ensures that IT/ BPCS compromises cannot affect SIS logic.  

**Impact of ransomware on SIS** – An attacker could disable safety interlocks, cause false trips, or prevent safe shutdown, leading to equipment damage, injuries, or fatalities. Recovery may require manual safe‑shutdown procedures and could necessitate plant shutdown for investigation.  

---

**OT10 – Medium**  
* **PLC (Programmable Logic Controller)** – Embedded industrial computer executing ladder logic or function block diagrams; directly controls hardware.  
* **DCS (Distributed Control System)** – Larger‑scale, multi‑loop control for complex processes (e.g., chemical plants); often uses proprietary OS and provides extensive HMI/SCADA integration.  
* **SCADA (Supervisory Control and Data Acquisition)** – Higher‑level supervisory system that monitors and records data from multiple PLCs/DCSs; typically runs on IT servers.  

**When to use each** –  
* **PLC** – Simple machine control, single‑machine automation.  
* **DCS** – Process plants with many interconnected loops, need redundancy and advanced control algorithms.  
* **SCADA** – Enterprise‑wide monitoring, data collection, and historical logging across many subsystems.  

**Coexistence** – Yes; a plant can have PLCs for individual machines, a DCS for process control, and a SCADA system for overall supervision and data aggregation.  

---

**OT11 – Medium**  
**Remote OT access architecture**  

1. **Jump hosts** – Bastion servers placed in a demilitarized zone (DMZ/IDMZ) with strict firewall rules.  
2. **MFA** – Require multi‑factor authentication for jump host login.  
3. **Session recording** – Tools like SafeNet, BeyondTrust, or open‑source `recordmydesktop` to capture all interactions.  
4. **Vendor access** – Vendor credentials are time‑limited, scoped to specific assets, and logged.  
5. **Why RDP directly to HMI is unacceptable** – HMIs often run on Windows with legacy software; exposing them directly to the corporate network bypasses segmentation, allows lateral movement, and lacks auditability.  

---

**OT12 – Hard**  
**Detection & response for compromised vendor VPN (Level 3 access)**  

1. **Network monitoring** – Deploy IDS/IPS (Snort, Suricata) and anomaly detection (NetFlow, Zeek) on the IDMZ and Level 3 segments; look for unusual traffic patterns, unknown IPs, or protocol deviations.  
2. **Asset inventory** – Maintain a live CMDB of PLCs, HMIs, SCADA servers; tag each with model, firmware version, and support status.  
3. **Incident response steps** –  
   * Isolate the affected segment (block VLAN traffic).  
   * Disconnect the vendor VPN tunnel.  
   * Preserve logs and capture network forensics.  
   * Initiate safe‑shutdown procedures for critical processes if needed.  
   * Coordinate with control room operators to verify plant status.  
4. **Coordination with control room** – Provide operators with real‑time visibility of network status, alerts, and any required manual interventions; keep them informed of containment actions.  
5. **Ensuring safe operations** –  
   * Use **redundant** control loops where possible.  
   * Keep **manual override** capabilities functional.  
   * Run a **fallback** (e.g., backup HMI) on an isolated machine.  
6. **Role of plant operator** – The operator is the final authority for safe plant state; they must acknowledge alerts, confirm that safety interlocks are functional, and execute any required manual safe‑shutdown or isolation actions.

**OT13 – Easy**  
**HMI (Human‑Machine Interface)** – The graphical client that allows operators to monitor and interact with PLCs, DCS, or SCADA in real time. It presents process data, alarms, and control panels.  

**Difference from engineering workstation** – An engineering workstation is used for configuration, programming, and maintenance of control systems (e.g., creating PLC programs, tuning controllers). An HMI is for **operational** viewing/control, not for engineering tasks.  

---

**OT14 – Easy**  
**Historian in OT** – A time‑series database that records process variables (tags) at high frequency for trend analysis, compliance, and performance reporting.  

* **Plant historian (Level 3)** – Stores data directly from the control system (e.g., OSIsoft PI, Wonderware).  
* **Enterprise historian (Level 4)** – Aggregates plant data into the ERP/MES layer, often using data warehousing or cloud analytics.  

---

**OT15 – Easy**  
**Ladder logic** – A graphical programming language resembling electrical relay diagrams; used to program PLCs.  

**Device** – Executed by the PLC’s CPU (often a ruggedized industrial PC).  

**Why still dominant** – It maps directly to existing electrical schematics, is vendor‑agnostic, easy to troubleshoot, and supported by decades of engineering expertise and training.  

---

**OT16 – Easy**  
**RTU (Remote Terminal Unit)** – A remote device that receives commands and returns data for field devices; typically used in telemetry and remote sites.  

**Difference from PLC** – RTUs are generally simpler, focused on data acquisition and communication (often using serial protocols), while PLCs have more robust processing and control capabilities.  

**Typical deployment** – Oil & gas wellheads, water treatment stations, remote pumping stations where power and space are limited, and maintenance windows are large.  

---

**OT17 – Easy**  
**Analog signals** – Continuous voltage/current (e.g., 4‑20 mA, 0‑10 V). **Digital signals** – Discrete on/off (e.g., TTL, Ethernet).  

**Why 4‑20 mA preferred over 0‑20 mA** – 4 mA provides a “live zero” that distinguishes a broken wire (0 mA) from a valid low reading (4 mA), improving fault detection.  

---

**OT18 – Medium**  
**OT asset inventory** – A comprehensive list of all devices (PLCs, HMIs, servers, switches) with attributes (IP, firmware, vendor, location). It underpins security because you cannot protect what you don’t know.  

**Discovery tools** –  
* **Passive monitoring** – Network taps, SPAN, or flow collectors (NetFlow, sFlow) to see devices and protocols.  
* **Active scanning** – Tools like Nmap, Nessus, or vendor‑specific scanners to query devices for OS/firmware.  

**Why active scanning is dangerous** – Sending probes can destabilize legacy OT equipment, cause unexpected reboots, or disrupt control loops, leading to production downtime.

**OT19 – Hard**  
**MITRE ATT&CK for ICS** – Extends the enterprise ATT&CK matrix to industrial control systems, covering tactics such as “Initial Access”, “Execution”, “Persistence”, “Lateral Movement”, “Impact”, etc., with techniques specific to PLCs, SCADA, and HMI.  

**Five tactics & example techniques**  
1. **Initial Access** – “Supply Chain Compromise” (e.g., malicious firmware uploaded to a vendor).  
2. **Execution** – “Native API” (e.g., using PLC programming languages to run malicious code).  
3. **Persistence** – “Modify Existing Service” (e.g., install a malicious DLL in a PLC’s firmware).  
4. **Lateral Movement** – “Remote Services” (e.g., exploiting VNC or OPC UA to move from HMI to PLC).  
5. **Impact** – “Data Destruction” (e.g., overwriting historian databases) or “Manipulate Control Loops” (e.g., altering setpoints).  

**Difference from enterprise ATT&CK** – Focuses on industrial protocols, PLC/HMI behavior, and safety‑critical impacts rather than typical IT malware.  

**Using the framework** – Conduct a gap analysis: map existing controls to each technique, identify missing defenses (e.g., no network segmentation for Modbus), and prioritize mitigations (e.g., implement firewall rules, host‑based intrusion detection on PLCs).

**OT20 – Hard**  
**Converged IT/OT SOC for 3 manufacturing sites**  

1. **Log collection** – Deploy lightweight agents on OT devices (e.g., Syslog, OPC UA historical data) that forward to a central SIEM via secure channels (TLS, VPN). Ensure agents are low‑impact and can operate offline with buffered forwarding.  

2. **SIEM integration** – Use a SIEM with OT‑aware correlation rules (e.g., Splunk with OT add‑ons, Azure Sentinel OT content). Ingest logs from IT (Windows, Linux) and OT (PLC, HMI, network devices).  

3. **OT‑specific detection rules** –  
   * Unexpected PLC program changes.  
   * Unauthorized firmware updates.  
   * Anomalous Modbus traffic (e.g., sudden burst of writes).  
   * Access to HMI from unknown IPs.  

4. **Alert triage workflow** –  
   * **Triage** – Auto‑assign based on severity and asset criticality.  
   * **Investigation** – OT engineers verify with HMI screenshots, PLC logs.  
   * **Escalation** – If impact on safety, involve control‑room operators.  

5. **Staffing** –  
   * **IT analysts** – Handle network, endpoint, and SIEM management.  
   * **OT engineers** – Understand PLCs, HMI, process logic, and safety standards.  

6. **False positives** – OT environments have legitimate spikes (e.g., batch runs). Use baselining, context (production schedule), and involve OT staff to validate before escalation.  

**Handling an alert of unauthorized firmware changes on a PLC**  
* Immediately isolate the PLC’s network segment (VLAN quarantine).  
* Verify the change’s scope (which parameter, impact on control loops).  
* Roll back to known‑good firmware if possible, using signed images.  
* Update the vendor’s support ticket, document the event, and initiate a post‑incident review.
