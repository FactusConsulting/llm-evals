**N3** – *TCP three‑way handshake & lost final ACK*  
1. **SYN** – Client → Server (synchronize).  
2. **SYN‑ACK** – Server → Client (acknowledge and synchronize).  
3. **ACK** – Client → Server (acknowledge server’s SYN).  

If the final **ACK** never reaches the server, the server retains the connection in **SYN‑RECEIVED** state (or **ESTABLISHED** if it already sent the ACK). The client assumes the connection is established and may start sending data, while the server will retransmit the SYN‑ACK (retransmit timer) until it finally receives the ACK or gives up after several retries. The connection never becomes fully established on the server side, causing data loss or connection failure on the client.

**N10** – *ARP purpose & Gratuitous ARP*

  2. **Updating neighboring devices’ ARP caches** (e.g., after failover or IP change) so traffic is correctly forwarded.

**N15** – *Half‑duplex vs. Full‑duplex*  
- **Half‑duplex** – Only one direction can transmit at a time; collisions possible (e.g., early Ethernet hubs).  
- **Full‑duplex** – Simultaneous two‑way communication; no collisions (e.g., modern twisted‑pair Ethernet with separate transmit/receive pairs).  
- **Modern Ethernet** uses **full‑duplex** exclusively (e.g., 100 Mbps, 1 Gbps, 10 Gbps).  

**N16** – *TTL field & traceroute*  
- **TTL (Time‑To‑Live)** – Decremented by each router; when it reaches zero, the packet is discarded and an ICMP “Time exceeded” message is sent back.  
- **Traceroute** exploits this: it sends packets with incrementally increasing TTL values (starting at 1). The first router discards the packet (TTL = 1) and returns ICMP Time exceeded, revealing hop 1. The next packet (TTL = 2) is dropped by hop 2, etc., until the destination responds with ICMP Port unreachable (or other).  

**N17** – *NAT gateway & types*  
- **NAT gateway** translates private‑address packets to a public address (or vice‑versa) to enable routing between networks with limited address space.  
- **Static NAT** – One‑to‑one mapping that never changes (e.g., `192.168.1.10 → 203.0.113.5`). Used for servers requiring a consistent external address.  
- **Dynamic NAT** – Pool of public addresses; a private host gets an address from the pool for the duration of the session (e.g., `192.168.1.10 → 203.0.113.100` while connected).  
- **PAT (Port Address Translation)** – Same public IP for many hosts, but each connection is distinguished by source/destination port numbers (e.g., `192.168.1.10:5000 → 203.0.113.5:XXXXX`). Also called “overload.”  

**N18** – *ECMP routing, hashing, and stateful firewall issues*  
- **ECMP** – When multiple routes to a destination have the same cost, the router load‑balances traffic across them using a hash of packet fields. All packets of a flow typically stay on the same path because the hash is consistent.  
- **Common hash keys** (Linux `ip rule`/`tc`):  
  1. **Source IP**  
  2. **Destination IP**  
  3. **Source port**  
  4. **Destination port**  
  5. **Protocol** (TCP/UDP/ICMP)  
- **Problems with asymmetric flows & stateful firewalls:**  
  - If hash parameters change (e.g., due to NAT, load balancer, or different source IPs), return traffic may take a different ECMP path. A stateful firewall that tracks only the original flow may drop the return packet because it appears on a different interface or with different source/destination addresses, causing connection drops.  
  - Mitigation: ensure symmetric hashing (include both source and destination addresses/ports), use consistent hash seeds, or disable ECMP for traffic that must stay symmetric.  

**N19** – *High latency, BDP 10 MB, window 64 KB*  
- **Problem:** The **bandwidth‑delay product** (BDP) = bandwidth × RTT ≈ 10 MB. TCP can only have at most 64 KB of unacknowledged data in flight, so the pipe is far from full. The connection’s throughput is limited to roughly `cwnd / RTT` ≈ 64 KB / RTT, far below the possible capacity, causing under‑utilization despite low packet loss.  
- **Solution – TCP Window Scaling (RFC 1323):**  
  - Allows the `cwnd` field (16 bits) to be shifted left by a scaling factor (0‑14).  
  - The receiver advertises a larger `window` size (e.g., 10 MB) using the `WS` option.  
  - The sender can then transmit up to the scaled window, filling the pipe and achieving the available bandwidth.  

**N20** – *802.1Q trunk & Linux sub‑interfaces for VLANs 10, 20, 30*

**L1** – *Hard link vs. symbolic link*  
- **Hard link:** A directory entry that points directly to an inode. Deleting a filename (unlinking) does not affect the file data as long as at least one hard link remains. All hard links share the same inode, size, timestamps, and storage. Cannot cross filesystem boundaries.  
- **Symbolic link (symlink):** A special file containing a path string to the target file. It is a separate inode; breaking the link (deleting the symlink) does not affect the target. Symlinks can span filesystems and can point to non‑existent files (dangling).

**L3** – *Process state D (uninterruptible sleep)*  
- **Meaning:** The process is blocked waiting for a system resource that cannot be satisfied immediately (e.g., I/O from storage, network device, or a lock). It is “uninterruptible” because signals like `SIGINT` or `SIGKILL` are not delivered until the operation completes.  
- **Can you kill it with `kill -9`?** `SIGKILL` (`-9`) **cannot** be used to wake a D‑state process; the kernel will ignore it. You must wait for the underlying I/O to complete, troubleshoot the device, or reboot if necessary.  

**L4** – *cgroups v1 vs. v2*  
- **cgroups v1:** Uses a hierarchical “controller” model; each controller (cpu, memory, blkio, etc.) has its own subsystem directory. Complex mounting, multiple “cgroupfs” instances.  
- **cgroup v2:** Unified hierarchy with a single “cgroup2” mount; controllers are combined under one set of files, simplifying management and providing better atomic operations.  
- **Systemd preference:** Systemd uses **cgroup v2** because it offers a cleaner API, consistent interface for all controllers, and better support for features like unified memory pressure notifications.  

**L5** – *nftables vs. iptables*  
- **iptables** – Legacy framework using separate tables (filter, nat, mangle, raw) and chains. Rules are stored in kernel and user‑space tools (`iptables`, `iptables-save/restore`).  
- **nftables** – Modern, unified framework that replaces iptables/arp tables. Rules are expressed as a single netfilter object language; it can replace iptables, ip6tables, arptables, ebtables.  
- **Kernel handling:** The kernel exposes both rule sets; iptables can be configured to use the nftables backend via the `iptables-nft` compatibility layer, but they are separate code paths. Running both simultaneously is possible but not recommended due to rule conflicts.  

**L6** – *df shows 100 % but du totals far less*  
- **Most likely cause:** **Reserved space for the superuser** (typically 5 % of the filesystem) plus **metadata overhead** (inodes, journal, etc.) that `df` counts as used, while `du` only measures data in directory trees. Additionally, many deleted files may still occupy blocks (e.g., in ext4 with delayed allocation) that `df` reports but `du` does not see because they are no longer referenced.  

**L7** – *Linux boot process (UEFI → systemd)*  
1. **UEFI Firmware** – Performs hardware POST, loads the **EFI boot loader** (e.g., `bootx64.efi`).  
2. **Bootloader** – Reads the kernel image (`vmlinuz`) and optional initramfs (`initramfs`), passes boot parameters to the kernel.  
3. **Kernel** – Initializes hardware, runs the **kernel entry point** (`start_kernel`), mounts the **initramfs** (if needed) as the initial RAM disk.  
4. **Initramfs** – Contains scripts and binaries to set up essential filesystems (e.g., LVM, RAID, network) before the real root filesystem is available.  
5. **Root filesystem** – After initramfs determines the true root (e.g., `/dev/vg0/lvroot`), the kernel **unmounts** the initramfs and **mounts** the root FS.  
6. **Init** – Historically `init` (sysvinit) or `systemd` (PID 1). Modern systems use **systemd** as the final stage, which spawns all services, sets up mounts, and brings the system to the target (e.g., `multi-user.target`).  

**L8** – *OOM killer, low “available” despite buff/cache*  
- **Why “available” can be low:** `free -h` reports **available** as `MemAvailable = Free + (Buffers + Cached) - (some overhead)`. When `Buffers+Cached` is large (15 GB), the kernel may consider that memory “used” for page cache, but it can be reclaimed instantly. However, if the system is under heavy pressure (e.g., many processes allocating anonymous memory), the **free** portion may be small, making `available` appear low even though reclaimable cache exists.  
- **Kernel tunables influencing this:**  
  - `vm.overcommit_memory` (0 = heuristic, 1 = always overcommit, 2 = never)  
  - `vm.swappiness` (controls how aggressively the kernel swaps)  
  - `vm.vfs_cache_pressure` (affects reclaim of dentries/inodes)  
  - `vm.min_free_kbytes` (sets minimum free memory)  
  - `vm.max_map_count` (limits mmap entries)  

**L9** – *`ip netns` and container runtimes*  
- **`ip netns`** creates, lists, and deletes network namespaces—isolated virtual network stacks that have their own interfaces, IP addresses, routing tables, and firewalls.  
- **Use by container runtimes:** Docker, Podman, containerd, etc., use network namespaces to give each container its own virtual NIC (e.g., `eth0`). The host can attach a veth pair: one end stays in the host namespace, the other in the container’s netns, enabling isolated networking and optional bridging to the host.

- **SIGKILL** – Forceful kill; cannot be caught or ignored; process is terminated immediately.  
- **SIGQUIT** – Usually generates a core dump and terminates; can be caught (default action is to dump core).

**L13** – *Root user vs. sudo user*

- **Sudo user** – Regular account that can execute specific commands (or all) with elevated privileges of another user (usually root). Requires authentication, and actions are logged. Provides least‑privilege principle.  

**L14** – *Package manager*  
- **Debian/Ubuntu:** `apt` (Advanced Package Tool) – `apt-get`, `apt`.  
- **RHEL/Fedora:** `dnf` (Dandified Yum) – successor to `yum`.  

**L15** – *`/etc/fstab` purpose*  
- Defines how filesystems (disk partitions, LVM, network filesystems, swap) should be mounted at boot, including mount options and dump/pass numbers.  
- **Misconfiguration consequences:** System may fail to mount critical filesystems (boot failures), attempt to mount non‑existent devices (hangs), or mount with wrong options (security/performance issues).  

**L16** – *LVM basics*  
- **Physical Volume (PV):** Raw disk partition or LVM physical volume (`pvcreate`).  
- **Volume Group (VG):** Collection of PVs (`vgcreate`). Represents pooled storage.  
- **Logical Volume (LV):** Virtual block device created from a VG (`lvcreate`). Mounted like a regular filesystem.  
- **Extend LV on running system:**  
  ```bash
  # Increase size of existing LV
  lvextend -L +2G /dev/vg0/lvdata
  # Resize filesystem (e.g., ext4)
  resize2fs /dev/vg0/lvdata
  ```  

**L17** – *Linux I/O scheduler*  
- **I/O scheduler** decides the order and grouping of I/O requests for block devices, balancing latency, throughput, fairness.  
- **mq‑deadline:** Deadline‑oriented; guarantees per‑request service time and FIFO ordering; good for latency‑sensitive workloads (databases).  
- **BFQ (Budget Fair Queueing):** Fair‑share allocator; gives each process a “budget” of I/O; excels for interactive/desktop systems with many mixed workloads.  
- **none:** No scheduling; requests go straight to the device (e.g., for SSDs where hardware queue handles ordering).  
- **Choosing:**  
  - **mq‑deadline** for low‑latency storage (NVMe) with strict deadlines.  
  - **BFQ** for general‑purpose servers with many concurrent processes.  
  - **none** for SSDs with hardware queuing or for testing.  
- **Change scheduler at runtime:**  
  ```bash
  sudo tee /sys/block/sda/queue/scheduler <<< "bfq"
  # Verify
  cat /sys/block/sda/queue/scheduler
  ```  
  (Replace `sda` with the target block device.)  

**L18** – *High load average with low CPU*  
- **Load average** counts the number of processes that are runnable **or** in uninterruptible sleep (D state). It does **not** measure CPU utilization.  
- **I/O wait** (e.g., disk stalls) can keep processes in D state, inflating load average even if CPU usage is low.  
- **Diagnosing bottleneck:**  
  - `top` / `htop` – view `%CPU` and `load`.  
  - `iostat 1` – check disk utilization (`await`, `util%`).  
  - `vmstat 1` – see `wa` (I/O wait) column.  
  - `netstat -s` or `ss -s` – inspect network queue lengths.  
  - Compare `wa` (I/O wait) vs. CPU steal; high `wa` indicates storage bottleneck.  

**L19** – *SELinux enforcement*  
- **Enforcing:** SELinux policies are enforced; violations are denied and logged (audit).  
- **Permissive:** Policies are loaded and checked, but violations are allowed (logged only). Good for debugging.  
- **Disabled:** SELinux is off; no MAC enforcement.  
- **Troubleshooting a daemon binding a non‑standard port:**  
  1. Check audit logs: `auditctl -r /var/log/audit/audit.log` or `grep denied_bind`.  
  2. Identify the port (e.g., 8080) and the daemon’s context (`ps -Z`).  
  3. Use `semanage port -l` to see if the port is defined; add if missing: `semanage port -a -t http_port_t -p tcp 8080`.  
  4. Verify the daemon’s file context: `semanage fcontext -l | grep <daemon_path>`.  
  5. Apply changes: `semodule -s reload` or `load_policy`.  
  6. Test again; if still denied, check `audit.log` for specific denial messages and adjust the SELinux boolean or policy accordingly.  

**L20** – *Linux VM subsystem, page faults, THP*  
- **Page fault handling:** When a process accesses a virtual address:  
  1. **Minor page fault** – Page is in memory (e.g., file cache) but not mapped; kernel loads it from swap or file.  
  2. **Major page fault** – Page is not in memory and must be read from disk (or swap).  
- **Transparent Huge Pages (THP):** Automatically groups 2 MB (or 1 GB) pages to reduce TLB misses and overhead of small‑page allocations. Improves performance for large sequential workloads (e.g., databases, scientific computing).  
- **When to disable THP:**  
  - Applications that are latency‑sensitive and suffer from THP “thundering herd” page faults.  
  - Workloads with many small, random allocations where THP fragmentation hurts.  
  - Disable via kernel boot parameter `transparent_hugepage=never` or runtime: `echo never > /sys/kernel/mm/transparent_hugepage/enabled`.
