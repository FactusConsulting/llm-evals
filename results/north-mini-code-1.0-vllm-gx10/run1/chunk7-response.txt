- **Monolith:** All application logic, data access, UI, and configuration reside in a single executable unit. Deployment, scaling, and testing affect the whole system.

**AA3** – **API Gateway vs. Reverse Proxy**  
- **Reverse Proxy:** Generic layer that forwards any TCP/HTTP traffic, performs load balancing, SSL termination, health checks, and basic routing. It operates at Layer 3‑4 (or Layer 7 for simple host/path rewriting).  
- **API Gateway:** Specialized reverse proxy for **APIs**. It adds API‑specific concerns: request/response transformation, authentication/authorization (OAuth, JWT), rate limiting, caching, service discovery, monitoring, and protocol translation (REST ↔ gRPC).  

**Can an API Gateway replace a reverse proxy entirely?**  
Often **yes**, because a modern API gateway already performs the core functions of a reverse proxy (load balancing, TLS, routing). However, a dedicated reverse proxy may still be useful for non‑API traffic (e.g., static file serving, health‑check endpoints, or legacy services that don’t go through the gateway). Keeping both gives you flexibility and separation of concerns.

**AA4** – **Saga Pattern**  
- **Saga:** A sequence of local transactions where each step is executed, and if a step fails, the saga executes compensating actions to undo previous steps, preserving consistency across services.  

**Choreography‑based vs. Orchestration‑based**  
| Aspect | Choreography | Orchestration |
|--------|--------------|---------------|
| **Control** | Each service publishes events that trigger the next service’s action. No central coordinator. | A central orchestrator (orchestrator service) explicitly manages the saga state and decides next steps. |
| **Complexity** | Decoupled, but hard to debug and monitor; “distributed conversation” problem. | Easier to monitor, replay, and reason about; introduces a single point of failure (mitigated with redundancy). |
| **When appropriate** | Small, stable set of services; low transaction depth; you want true decoupling. | Complex business processes, need for compensation logic, auditability, or when you must support partial failures and rollbacks. |

**AA5** – **CQRS & Event Sourcing**  
- **CQRS (Command Query Responsibility Segregation):** Separate read and write models. Commands (writes) update a **Command Model**; queries read from a **Query Model** that may be optimized for read patterns.  
- **Event Sourcing:** Store an immutable log of state‑changing events for each entity. The current state can be reconstructed by replaying events.  

**Why pair them?**  
- Event sourcing provides the **event stream** that CQRS can project into multiple read models.  
- The event log gives auditability, replayability, and the ability to build derived views without complex joins.  

**Problem solved vs. CRUD:**  
- CRUD assumes a single, mutable data store; you cannot easily query historical states or build multiple read‑optimized schemas. CQRS + Event Sourcing lets you:  
  1. **Query multiple, denormalized views** without heavy joins.  
  2. **Reconstruct past states** (e.g., for compliance or UI “undo”).  
  3. **Scale reads and writes independently** (different databases, caching strategies).

**AA6** – **Circuit Breaker Pattern**  
- **Purpose:** Prevent a service from repeatedly attempting an operation that is likely to fail, allowing the system to degrade gracefully.  

**Three states:**  
1. **Closed** – Normal operation; requests go through, and failures are recorded.  
2. **Open** – Failure threshold exceeded; further requests short‑circuit to a fallback (e.g., cached response, error) without invoking the downstream service.  
3. **Half‑Open** – After a timeout, a limited number of test requests are allowed; if they succeed, the circuit returns to **Closed**, otherwise it stays **Open**.  

**Difference from simple retry with backoff:**  
- **Retry with backoff** still attempts the call each time, potentially overwhelming a failing dependency.  
- **Circuit breaker** stops calls altogether once failure rate exceeds a threshold, protecting resources.  

**When to use both together:**  
- Use **retry with backoff** for transient, expected failures (e.g., network glitches).  
- Add a **circuit breaker** to protect against prolonged outages or systemic errors. The breaker can open after repeated retries fail, and the system can fall back to a degraded mode.

**AA8** – **Consistency for an Inventory System**  
- **Strong Consistency** guarantees that any read sees the most recent write.  
- **Eventual Consistency** allows temporary divergence, reconciling later.  

**Goal:** *Never oversell* → must enforce that inventory cannot be decremented beyond available stock.  

**Architecture recommendation:**  
1. **Consistency Model:** **Strong consistency** for the inventory count (or at least **linearizable** for the decrement operation).  
2. **Data Store:**  
   - **Primary:** A **distributed, ACID‑compliant database** (e.g., PostgreSQL with `READ COMMITTED` isolation, or a NewSQL store like CockroachDB/TiDB) that can handle high‑throughput concurrent updates.  
   - **Secondary (for scaling reads):** A **read‑replicas** or **in‑memory cache** (Redis) that is kept **eventually consistent** but only used for non‑critical reads after a **synchronous replication** step.  
3. **Patterns:**  
   - **Optimistic locking** or **pessimistic locking** on the inventory rows (e.g., `SELECT ... FOR UPDATE`).  
   - **Idempotent decrement** with **retry logic** to avoid double‑deduction.  
   - **Saga/Compensating transaction** if the order‑reservation spans multiple services (e.g., reservation → payment).  
   - **Versioned rows** or **compare‑and‑set** to ensure the stock count hasn’t changed since read.  
4. **Scale considerations:**  
   - Use **sharding** by product or warehouse to distribute load.  
   - Employ **read‑through/write‑through caching** with a **cache lock** (e.g., Redlock) to keep the hot inventory data low‑latency while preserving consistency.  

Result: any order‑creation will block or fail if insufficient stock, guaranteeing no oversell even under high concurrency.

**AA9** – **Sidecar Proxy & Istio**  
- **Sidecar Proxy:** A lightweight proxy (e.g., Envoy) that runs alongside each application container, handling inbound/outbound traffic, service discovery, TLS, routing, and telemetry.  

**Envoy in Istio:**  
- **Data Plane:** All sidecar proxies (Envoy instances) that intercept service‑to‑service traffic, enforce policies, and collect metrics/logs.  
- **Control Plane:** Istio components (Pilot, Citadel, Galley/istiod) that compute networking configurations, issue certificates, and push policies to sidecars via the **XDS** API.  

**mTLS between sidecars vs. application‑level TLS:**  
- **Application‑level TLS** encrypts only the workload‑to‑workload traffic; the proxy itself may terminate TLS, exposing plaintext inside the pod.  
- **mTLS between sidecars** ensures **end‑to‑end encryption** from client pod to server pod, with the proxy acting as a trusted peer. This prevents lateral movement, protects against compromised containers, and provides **automatic, centrally managed** certificate rotation.

**AA12** – **Event‑Driven (Kafka) vs. Request‑Driven (REST/gRPC)**  

| Dimension | Event‑Driven (Kafka) | Request‑Driven (REST/gRPC) |
|-----------|----------------------|---------------------------|

**AA13** – **Load Balancer**  
- **Definition:** Distributes incoming client connections across multiple backend servers to achieve scalability, redundancy, and performance.  

**Layer 4 vs. Layer 7**  
- **Layer 4 (Transport):** Operates on TCP/UDP, load‑balances based on IP address and port (e.g., round‑robin). No inspection of HTTP headers.  
- **Layer 7 (Application):** Inspects full HTTP(S) request (host, path, headers) and can route based on those attributes, perform content‑aware routing, caching, and TLS termination.  

**Use case requiring Layer 7:**  
- **Path‑based routing** for multiple web applications on the same IP/port (e.g., `example.com/app1`, `example.com/app2`). A Layer 4 balancer would send all traffic to the same backend, while a Layer 7 balancer can direct each path to the appropriate service.

**AA14** – **Message Queue vs. Log‑Based Broker**  
- **Message Queue (RabbitMQ, SQS):** Point‑to‑point or pub/sub model; messages are **consumed** and removed (or acknowledged) from the queue. Guarantees at‑most‑once or at‑least‑once delivery per consumer.  
- **Log‑Based Broker (Kafka):** Append‑only log; messages are **never removed** unless compacted; consumers can replay from any offset. Provides **durability** and **replayability**.  

**When to pick each:**  
- **RabbitMQ:** Work‑queue patterns, task distribution, RPC‑style request/reply, when you need strict QoS (prefetch limits) and need to guarantee that a message is processed exactly once per consumer.  
- **Kafka:** Event streaming, audit trails, real‑time analytics, when you need high throughput, replayability, and multiple downstream consumers (e.g., analytics, alerts, archiving).

**AA15** – **Container vs. Virtual Machine**  
- **VM:** Emulates a full hardware stack; runs a complete OS; higher overhead, slower start‑up, but provides strong isolation.  
- **Container:** Shares the host OS kernel; lightweight, fast start‑up, higher density, but isolation is at the process level.  

**Why containers are popular for microservices:**  
- **Rapid scaling** – can spin up/have down containers in seconds.  
- **Resource efficiency** – many more containers per host, reducing cost.  
- **Portability** – “write once, run anywhere” via Docker/OCI images.  
- **Integration with orchestration** (Kubernetes, Docker Swarm) for auto‑scaling, service discovery, and rolling updates.

**AA16** – **Stateless vs. Stateful Services**  
- **Stateless Service:** No persistent local state; each request can be handled by any instance.  
- **Stateful Service:** Maintains session or in‑memory state across requests (e.g., user session, game state).  

**Why stateless is easier to scale horizontally:**  
- Load balancers can route any request to any instance; no need to track “owner” of a session, eliminating sticky sessions and simplifying failover.  

**Examples:**  
- **Stateless:** REST API that reads from a database and returns JSON.  
- **Stateful:** A game server that tracks player position, score, or lobby state.

**AA18** – **Bulkhead Pattern**  
- **Purpose:** Isolate critical resources (e.g., thread pools, DB connections) so that a failure or overload in one component does not affect others.  

**Relation to resource isolation in microservices:**  
- Bulkheads enforce **resource quotas** per service or per tenant, preventing a noisy microservice from starving others of CPU, memory, or I/O.  

**Concrete implementation example:**  
- **Thread‑pool bulkhead:** In a .NET service, create two `ThreadPool`‑based queues: one for high‑priority requests (e.g., payment processing) with 10 threads, another for low‑priority (e.g., logging) with 2 threads. Use a semaphore or `BlockingCollection<T>` to enforce the limits.  
- **Separate deployment groups:** Run the payment service on a dedicated node or Kubernetes pod group with guaranteed CPU/memory limits, while the analytics service shares the remaining nodes.  

Result: a surge in logging traffic cannot starve the payment service of threads, preserving SLA.

**AA19** – **Operational Transformation (OT) vs. CRDTs for Collaborative Editing**  

| Aspect | Operational Transformation (OT) | Conflict‑Free Replicated Data Types (CRDT) |
|--------|--------------------------------|-------------------------------------------|
| **Consistency guarantees** | Requires a central sequencer or deterministic transformation rules; strong eventual consistency if all transformations applied in same order. | Guarantees convergence regardless of delivery order; no need for a sequencer. |
| **Latency** | Typically lower latency for each operation if a sequencer exists; otherwise need to wait for remote transformations. | Higher latency for each operation (needs to propagate to all replicas) but can be processed locally. |
| **Complexity** | Complex to implement correct transformation logic for arbitrary editors; error‑prone. | Simpler data‑type implementations (e.g., LWW‑set, OR‑set) but may require careful design for rich text. |
| **Offline support** | Hard – offline edits cannot be transformed without a sequencer; must buffer and sync later. | Excellent – CRDTs can be applied locally offline; they converge automatically when reconnected. |
| **Typical use‑case** | Real‑time collaborative editors where low latency and strong ordering are critical (e.g., Google Docs historically used OT). | Systems that need eventual consistency and offline capability (e.g., collaborative canvases, counters). |

**Choice for offline editing:**  
- **CRDTs** are preferred because they allow the client to apply edits locally without waiting for a central authority, and they converge automatically when connectivity resumes.

**AA20** – **Distributed Tracing Challenges in Polyglot Microservices**  

1. **Context Propagation**  
   - **W3C Trace Context** (`traceparent` header) is the emerging standard; **B3** (single or multi‑header) is still widely used.  
   - Need instrumentation libraries for each language (OpenTelemetry agents, Jaeger client, etc.) to inject/extract the headers correctly.  

2. **Sampling Strategies**  
   - **Head‑based sampling:** Decision made at the entry point; simple but may miss rare errors deep in the graph.  
   - **Tail‑based sampling:** Continuous recording of traces, then post‑hoc selection; requires storage for all traces (e.g., Tempo’s ingestion model).  

3. **Trace Storage & Querying**  
   - **Jaeger:** Stores spans in a Cassandra/MariaDB back‑end; good for long‑term retention, but query UI can be slower.  
   - **Tempo (Grafana):** Uses chunked OTLP‑compatible storage (object storage); scales to millions of traces, faster queries for high‑throughput services.  

4. **Asynchronous Messaging (Kafka) Continuity**  
   - When a request is processed via Kafka, the trace context must be **carried in message headers** (e.g., using the `traceparent` header).  
   - Instrumentation libraries (e.g., `kafka-python` with OpenTelemetry) automatically propagate the active span.  
   - Ensure **sampling decisions** are preserved across the bridge; otherwise a sampled trace may be lost.  

5. **Ensuring Trace Continuity**  
   - Use a **single trace ID** across services; generate a new span for each logical step (e.g., “publish to Kafka”, “consume from Kafka”).  
   - Implement **span linking** (OpenTelemetry `Link`) to connect the producer span to the consumer span.  
   - Deploy **consistent sampling policies** across all services (e.g., sample 1 % of traces, but tail‑based for error paths).  

Result: end‑to‑end visibility even when requests hop through message brokers, enabling root‑cause analysis across language boundaries.

**OP2** – **SAN vs. NAS**

- **SAN:** High‑performance, low‑latency workloads needing direct block access (databases, virtualization).  
- **NAS:** File sharing, backup, media distribution, where file semantics are sufficient.

**OP3** – **3‑Tier Network Architecture & Leaf‑Spine Preference**  
- **3‑Tier (Core/Distribution/Access):** Core switches aggregate traffic, distribution switches enforce policies, access switches connect end‑hosts. Simple but can create bottlenecks at the core and long east‑west paths.  

- **Leaf‑Spine:** Leaf switches act as access points, spine switches interconnect leaves. Provides **non‑blocking** bandwidth (any leaf can talk to any spine directly) and **shorter hop counts**, reducing latency and improving fault isolation.  

- **Problem solved:** Eliminates “traffic jam” at a single core switch and reduces broadcast domains, improving scalability for data‑center workloads.

**OP4** – **Highly Available Proxmox Cluster with Shared Storage**  

1. **Node Count:** Minimum **3 nodes** for quorum; recommend **5 nodes** for resilience and load distribution.  
2. **Quorum:** Use **Corosync/Pacemaker** with **quorum** based on node votes; enable **two‑node** split‑brain protection via **STONITH** (e.g., fencing scripts).  
3. **Fencing:**  
   - **STONITH** devices (IPMI, DRAC, or dedicated fencing agents).  
   - Automatic power‑off or network isolation of a node that loses its lock.  
4. **Shared Storage Options:**  
   - **Ceph:** Scalable, object/block storage; integrates with Proxmox via `pve-storage` plugin. Provides replication and erasure coding.  
   - **iSCSI:** Target (e.g., Open-iSCSI) on a dedicated storage server; Proxmox iSCSI initiator mounts LUNs.  
   - **NFS:** Simple, but less performant; use NFSv4 with security considerations.  
5. **Node Failure Scenario:**  
   - If a node fails, its VMs are **migrated** (if HA is enabled) to other nodes using **QM migrate**.  
   - The storage cluster (e.g., Ceph) continues to serve the VM disks; the failed node’s storage is marked **down** but data remains available.  
   - Quorum remains intact (if ≥ majority nodes alive); Pacemaker moves resources to healthy nodes.

**OP5** – **VLAN Trunking & 802.1Q**  
- **VLAN Trunking:** Allows a single physical NIC to carry traffic for multiple VLANs.  
- **802.1Q:** Ethernet frame tag adds a 4‑byte VLAN identifier (VLAN ID) and a priority field.  

**Linux configuration for a single NIC on 3 VLANs:**  
```bash
# Create a bridge for each VLAN (or one bridge with multiple ports)
ip link add name bond0 type bond mode balance_rr
ip link set dev bond0 address 00:11:22:33:44:55

# Add physical NIC to bond
ip link set dev eth0 master bond0

# Add VLAN interfaces (802.1Q)
ip link add link bond0 name bond0.10 type vlan id 10
ip link add link bond0 name bond0.20 type vlan id 20
ip link add link bond0 name bond0.30 type vlan id 30

# Bring up
ip link set dev bond0 up
ip link set dev bond0.10 up
ip link set dev bond0.20 up
ip link set dev bond0.30 up

# Assign IP addresses
ip addr add 192.168.10.10/24 dev bond0.10
ip addr add 192.168.20.10/24 dev bond0.20
ip addr add 192.168.30.10/24 dev bond0.30
```
- Alternatively, use **ifcfg** or **NetworkManager** with `VLAN` definitions.

**OP6** – **RAID Levels Comparison & Choice for 6 Drives**  

| RAID | Description | Parity | Spare | Write Penalty | Typical Use |
|------|-------------|--------|-------|---------------|-------------|
| **RAID 1** | Mirror pairs; 3 mirrors for 6 drives. | N/A | N/A | 1 read, 2 writes | Small, critical data |
| **RAID 5** | Block‑level striping + distributed parity; 5 drives data, 1 parity. | 1 parity drive | Yes (optional) | 1 read, 4 writes | Good balance, moderate capacity |
| **RAID 6** | RAID 5 + extra parity (double parity); 4 drives data, 2 parity. | 2 parity drives | Yes | 1 read, 6 writes | Higher protection, larger arrays |
| **RAID 10** | Mirror + stripe; 3 mirrors of 2 drives each. | N/A | N/A | 2 reads, 2 writes | High performance, good protection |
| **RAID Z2 (ZFS)** | Similar to RAID 6; uses parity and copy‑on‑write. | 2 parity | Yes | 2 writes (copy‑on‑write) | ZFS features (snapshots, self‑healing) |

**For a database server on 6 drives:**  
- **Goal:** Good performance (read/write), decent capacity, fault tolerance for up to 2 drive failures.  
- **Recommendation:** **RAID 10** – provides **high IOPS**, fast reads/writes, and can survive a single drive failure per mirrored pair (up to 3 drives). It also avoids parity calculation overhead, which benefits write‑intensive workloads.  
- **Alternative:** If you need higher capacity and can tolerate parity overhead, **RAID 6** or **RAID Z2** give protection against two drive failures and better usable capacity (≈ 4/6 drives). Choose RAID 10 if performance is the primary driver; choose RAID 6/Z2 if capacity and extra redundancy are more important.

**OP7** – **DNS Architecture for 500‑Person Enterprise**  

1. **Recursive Resolvers**  
   - **Internal DNS servers** (e.g., Windows DNS or BIND) for employees; forward external queries to internet root hints or upstream ISPs.  
   - **External DNS** (e.g., Cloudflare DNS) for public‑facing services.  

2. **Authoritative Servers**  
   - **Internal zone:** Windows DNS server(s) hosting `corp.example.com` (AD integrated).  
   - **External zone:** BIND server(s) in the DMZ hosting `example.com` (public).  

3. **Split‑Horizon DNS**  
   - Configure each authoritative server to answer queries based on source IP:  
     - **Internal queries** (RFC 5732) return internal IPs (e.g., `file-server.corp.example.com` → `192.168.1.10`).  
     - **External queries** return public IPs (e.g., `example.com` → `203.0.113.5`).  

4. **Forwarders & Conditional Forwarding**  
   - Internal DNS forward **external** queries to a forwarder (e.g., ISP DNS or internal forwarder to internet root).  
   - Conditional forwarder on external DNS to forward **internal** queries (for reverse lookups) to internal DNS.  

5. **DNSSEC on External Zone**  
   - Generate a key pair (KSK/ZSK) on the external BIND server.  
   - Sign the zone (`dnssec-signzone`).  
   - Publish the DS record in the parent zone (e.g., at IANA).  

6. **Laptop Movement (Office ↔ VPN)**  
   - When a laptop connects via VPN, its DNS server points to internal DNS (or corporate DHCP).  
   - Internal DNS resolves internal names using AD integration; external names are forwarded.  
   - If the laptop roams to a remote office with a different DNS, DHCP updates the DNS suffix search list; split‑horizon logic still applies.  

Result: Employees get fast internal name resolution, external users reach public services, and DNSSEC protects against cache poisoning for public zones.

**OP8** – **PKI Chain of Trust & Internal PKI**  

1. **Chain of Trust**  
   - **Root CA:** Offline, highly protected, signs **subordinate CA certificates**.  
   - **Subordinate/Issuing CA:** Online, signs **end‑entity certificates** (servers, users).  
   - **End‑Entity Certificate:** Issued to a device/user; trusted because its issuer is signed by a subordinate CA, which is trusted via the root.  

2. **Internal PKI Components**  
   - **Root CA:** Offline, uses hardware security module (HSM).  
   - **Subordinate CA:** May be **offline** for issuance (policy) or **online** for signing certificates; often placed in a DMZ or internal network.  
   - **CRL vs. OCSP:**  
     - **CRL (Certificate Revocation List):** Periodic batch revocation list; simple but can be stale.  
     - **OCSP (Online Certificate Status Protocol):** Real‑time status check; requires an OCSP responder service.  
   - **Certificate Templates:** Define fields (e.g., key usage, extended key usage, validity periods) for server, client, and code‑signing certificates.  
   - **Auto‑enrollment:** Windows Server Certificate Services (or third‑party CA) automatically issues/renews certificates based on templates when a machine/user requests one.  

3. **Compromised CA Impact**  
   - **Compromised Subordinate CA:** Allows issuance of fraudulent certificates for any domain within its trust chain; revocation must be rapid, and the CA certificate may need to be revoked/re‑issued.  
   - **Compromised Root CA:** Catastrophic – any certificate signed by that root is untrusted; must be immediately revoked, a new root key generated, and all dependent certificates re‑issued.

**OP9** – **Hub‑and‑Spoke WAN Options**  

| Technology | Cost | Reliability | Latency | Management Complexity | Security Posture |
|------------|------|-------------|---------|----------------------|-------------------|
| **MPLS** | Higher (service fees) | Very reliable (QoS, SLA) | Low (direct circuits) | Low (provider managed) | Provider‑controlled; limited encryption (can add IPsec) |
| **IPsec VPN over Internet** | Low (uses existing internet) | Dependent on ISP; can have outages | Variable (depends on path) | Moderate (need to manage tunnels) | Strong encryption; endpoint authentication |
| **SD‑WAN** | Moderate (hardware + software licenses) | High (multiple transport paths, failover) | Low‑to‑moderate (optimizes paths) | Moderate‑high (central orchestration) | Supports IPsec, TLS; centralized policy |
| **WireGuard Mesh** | Very low (open‑source, lightweight) | Depends on underlying internet; mesh provides redundancy | Low (direct tunnels) | Low‑moderate (simple config) | Strong encryption (Noise protocol); key‑based auth |

**Recommendation for 50 users/site, latency‑sensitive VoIP:**  
- **Primary:** **SD‑WAN** – provides built‑in QoS, path selection (prefer MPLS or broadband), and easy failover, ensuring VoIP quality.  
- **Backup/Fallback:** Add **IPsec VPN** tunnels to a secondary ISP for redundancy.  
- **Optional:** For very small sites, **WireGuard mesh** could be used, but SD‑WAN gives better QoS and centralized management for VoIP policies.

**OP10** – **iDRAC/iLO/IPMI**  
- **Definition:** Manufacturer‑specific **Out‑of‑Band (OOB)** management interfaces (Dell iDRAC, HP iLO, generic IPMI). Provide remote server monitoring, power control, and console access independent of the host OS.  

**Why OOB is critical:**  
- Enables **remote troubleshooting**, **patch deployment**, **health monitoring**, and **power management** even when the operating system is down or compromised.  

**Risk of internet exposure:**  
- Exposes management credentials and APIs to the public internet, making the host vulnerable to brute‑force attacks, unauthorized power actions, and potential escalation to the internal network (if management VLAN is not isolated). Mitigation: use **strong authentication**, **VPN**, **network segmentation**, and **disable unnecessary services**.

**OP11** – **LVM vs. LVM‑Thin vs. ZFS**  

| Feature | LVM | LVM‑Thin | ZFS |
|---------|-----|----------|-----|
| **Underlying FS** | Usually ext4/xfs; logical volumes are thin‑provisioned only with LVM‑Thin. | Same as LVM but with **thin provisioning** (logical volumes consume space on demand). | Integrated filesystem + volume manager; uses copy‑on‑write. |
| **Snapshot semantics** | Snapshots are read‑only copies of the logical volume mapping; space‑efficient (copy‑on‑write). | Same as LVM snapshots; thin provisioning can cause snapshot growth if source writes. | Snapshots are lightweight, copy‑on‑write; can be cloned efficiently. |
| **Data integrity** | No built‑in checksums; relies on FS. | Same as LVM. | End‑to‑end checksums, self‑healing (via RAID‑Z). |
| **When to use** | Simple partitioning, legacy systems. | When you need **thin provisioning** (e.g., many VMs with variable usage). | Modern systems needing **snapshots, deduplication, snapshots, pools**, and data integrity (e.g., storage servers). |

**OP12** – **Stretch Cluster / DR for 3‑Node Proxmox + Ceph**  

1. **Stretch Cluster Design**  
   - **Nodes:** Deploy **3 nodes** in Site A and **3 nodes** in Site B (total 6).  
   - **Quorum:** Use **network‑based quorum** (e.g., **Corosync** with **two‑node** split‑brain protection) to avoid split‑brain when one site loses connectivity.  
   - **Ceph CRUSH Rules:** Define **site‑aware** CRUSH hierarchy (`root -> rack -> host -> osd`). Place OSDs on both sites to achieve **replication across sites** (e.g., `replicated` with `size=3`).  
   - **Monitor Placement:** Run **Ceph monitors** on both sites (e.g., 1 monitor per site) to keep them reachable; use **quorum** of monitors (requires odd number, e.g., 3 total).  
   - **Network Latency:** Keep inter‑site latency < 50 ms for Ceph replication; use **dedicated low‑latency links** (10 GbE or higher).  

2. **Split‑Brain Problem**  
   - Without a **tiebreaker** (e.g., a fourth node or external IP‑based quorum), each site may think it’s the majority, leading to both accepting writes → data divergence.  
   - **Solution:** Deploy a **fourth “tiebreaker” node** (could be a lightweight VM) that only votes in quorum decisions, or use **external IPMI** fencing to automatically power‑off the losing site.  

3. **Why 2‑Site Ceph is Generally a Bad Idea Without Tiebreaker**  
   - With only two sites, any network partition results in a 50/50 split; Ceph cannot decide which side is primary, leading to split‑brain. A tiebreaker provides a clear decision point.

**OP13** – **DHCP & DORA**  

- **DHCP (Dynamic Host Configuration Protocol)** automatically assigns IP addresses and network parameters to clients.  

**DORA Process**  
1. **Discover:** Client broadcasts `DHCPDISCOVER` to locate a DHCP server.  
2. **Offer:** Server replies with `DHCPOFFER` (proposed address, lease time).  
3. **Request:** Client sends `DHCPREQUEST` (accepts an offered address or renews).  
4. **Acknowledge:** Server replies with `DHCPACK` (confirms lease).  

**When DHCP server is unavailable and lease expires:**  
- The client will **re‑initiate DORA** after the lease expires (or earlier if configured). If the server remains down, the client will eventually fall back to **APIPA** (link‑local 169.254.0.0/16) on Windows, obtaining an automatic private IP address.

**OP14** – **Managed vs. Unmanaged Switch**  

- **Unmanaged Switch:** Plug‑and‑play; basic forwarding; no configuration options.  
- **Managed Switch:** Full configuration capabilities (VLANs, STP, QoS, SNMP, ACLs, PoE control, etc.).  

**Enterprise‑important features:**  
- **VLAN tagging (802.1Q)** for segmentation.  
- **Spanning Tree Protocol (RSTP/MST)** to prevent loops.  
- **QoS (DSCP)** for traffic prioritization.  
- **Port security & ACLs** for access control.  
- **SNMP/NetConf** for monitoring and automation.  
- **Power over Ethernet (PoE) management** for APs, IP phones.

**OP15** – **NTP & Time Synchronization**  

- **NTP (Network Time Protocol)** synchronizes clocks across a network to a common reference (NTP server or stratum).  

**Why accurate time matters:**  
- Essential for **logging correlation**, **security (TLS handshakes)**, **distributed transaction ordering**, **scheduling**, and **cluster coordination** (e.g., Pacemaker).  

**Problems with clock drift:**  
- **Misordered logs** make debugging difficult.  
- **Authentication failures** (certificate expiration checks).  
- **Cluster split‑brain** (Pacemaker may think a node is stale and fence it).  
- **Inconsistent timestamps** in databases (e.g., audit trails).  

Mitigation: Use **NTP with hardware timestamps**, **chrony** for faster convergence, and **regular monitoring** of clock skew.

**OP16** – **Physical Server, VM, Container**  

- **Physical Server:** Direct hardware usage; full OS; highest performance, no virtualization overhead.  
- **Virtual Machine:** Emulated hardware via hypervisor; isolated OS instances; can run multiple VMs per host.  
- **Container:** OS‑level virtualization; shares kernel; lightweight; runs isolated processes.  

**When to run workload directly on bare metal:**  
- **High‑performance requirements** (e.g., high‑frequency trading, large‑scale databases).  
- **Low‑latency needs** (e.g., real‑time processing).  
- **Regulatory constraints** that forbid virtualization.  
- **Workloads that need direct hardware access** (e.g., GPU passthrough, storage controllers).

**OP17** – **UPS vs. Generator**  

- **UPS (Uninterruptible Power Supply):** Provides **instantaneous** battery power during outages, typically for minutes; smooths power quality (voltage regulation, surge protection).  
- **Generator:** Supplies **longer‑duration** power (minutes to hours) but has a start‑up delay.  

**Why need both:**  
- **UPS** handles brief outages and power quality issues, allowing graceful shutdown or short‑term operation.  
- **Generator** provides sustained power for extended outages.  

**ATS (Automatic Transfer Switch):**  
- Automatically switches electrical load from utility power to generator (or vice‑versa) without manual intervention, ensuring continuous power to critical loads.

**OP18** – **Active‑Passive vs. Active‑Active Clustering for PostgreSQL**  

| Aspect | Active‑Passive | Active‑Active |
|--------|----------------|---------------|
| **Configuration** | One node is primary (master), the other is standby (replica). | Both nodes can accept reads/writes; data is synchronized (e.g., streaming replication). |
| **Failover** | Failover triggers promotion of standby; brief downtime. | No single point of failure; traffic can be re‑routed instantly. |
| **Complexity** | Simpler, lower resource usage. | More complex (conflict avoidance, synchronous replication). |

**Implementing HA with Pacemaker/Corosync (Active‑Passive)**  

1. **Resources**  
   - **IPaddr2** resource for virtual IP.  
   - **systemd** resource for PostgreSQL service (`postgresql`).  
   - ** stonith** (e.g., `fence_ipmi`) for fencing.  

2. **Pacemaker Configuration**  
   ```xml
   <resource_set id="rs1">
     <resource id="vip"/>
     <resource id="postgresql"/>
   </resource_set>
   ```  
   - Define **master/slave** relationship: `postgresql` as a master/slave pair (using `postgresql` resource agent).  

3. **STONITH**  
   - Configure `fence_ipmi` with node credentials; Pacemaker will power‑off a node that loses its lock.  

4. **Virtual IP**  
   - VIP moves to the surviving node after failover, ensuring clients reconnect to the new primary.  

5. **Failover Behavior**  
   - If the primary node fails, Pacemaker detects failure, promotes the standby, updates VIP, and restarts PostgreSQL on the promoted node.

**OP19** – **Backup & Recovery Strategy for 50‑Server On‑Prem**  

1. **3‑2‑1 Rule**  
   - **3** copies of data.  
   - **2** different storage media (e.g., disk + tape or cloud).  
   - **1** copy off‑site.  

2. **RPO / RTO Requirements**  
   - Define **RPO** (max data loss tolerated, e.g., 15 min) → use **continuous replication** or frequent snapshots.  
   - Define **RTO** (max downtime, e.g., 2 h) → design backup windows, replication targets, and failover procedures.  

3. **Backup Types**  
   - **Full backup** (weekly) – baseline.  
   - **Incremental** (daily) – only changed blocks.  
   - **Differential** (optional) – easier restore than incremental but more storage.  

4. **Deduplication**  
   - Apply **block‑level dedupe** on backup storage (e.g., NetBackup, Veeam, or hardware‑based dedupe appliances) to reduce storage footprint.  

5. **Storage Media**  
   - **Disk (NAS/SAN)** for short‑term, fast RTO (e.g., daily backups, snapshots).  
   - **Tape or Cloud** for long‑term, off‑site retention (3‑2‑1).  

6. **Immutable Backups for Ransomware**  
   - Use **write‑once, read‑many** storage (e.g., WORM tapes, cloud “object lock” features) to prevent deletion/modification.  

7. **Testing Restores**  
   - Perform **quarterly full restore drills** on a staging environment; verify application functionality, data integrity, and RTO compliance.  

**Difference between Backup and Disaster Recovery (DR):**  
- **Backup** = copying data for restoration after accidental loss, corruption, or ransomware.  
- **DR** = holistic strategy (including failover infrastructure, site replication, network, applications, and processes) to resume operations after a major outage (e.g., site loss). DR encompasses backups but also includes **failover testing**, **replication**, **communication plans**, and **recovery procedures**.

**OP20** – **802.1X Port‑Based Network Access Control**  

1. **Roles**  
   - **Supplicant:** Client device (e.g., workstation, IP‑phone) that initiates authentication.  
   - **Authenticator:** Managed switch port that controls access; enforces 802.1X.  
   - **Authentication Server:** Typically RADIUS (e.g., Windows NPS, FreeRADIUS) that validates credentials.  

2. **EAP Methods**  
   - **EAP‑TLS:** Mutual TLS certificates; strong mutual authentication.  
   - **PEAP (EAP‑MSCHAPv2):** Tunneled authentication; password‑based, widely used.  

3. **RADIUS**  
   - Centralized authentication, authorization, and accounting (AAA).  
   - Switch forwards EAP packets to RADIUS; RADIUS returns accept/reject.  

4. **Dynamic VLAN Assignment**  
   - After successful auth, switch can tag the port with a VLAN ID based on user/group (e.g., `radius‑attr‑filter`).  

5. **Device Failure to Authenticate**  
   - Port remains in **unauthorized** state; traffic is blocked (except 802.1X discovery packets).  
   - Optionally, **MAB (MAC Authentication Bypass)** can be enabled for non‑802.1X devices (e.g., printers).  

6. **MAB Operation**  
   - Switch uses the device’s MAC address as a “username” and looks it up in RADIUS.  
   - If MAC is pre‑configured in RADIUS, the port is authorized; otherwise, access is denied.  

Result: only authenticated devices gain network access, reducing unauthorized device risk and enabling policy‑based segmentation.<|END_TEXT|>
