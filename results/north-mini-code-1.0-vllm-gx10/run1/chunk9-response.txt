**SC2 – Hard – Cross‑Region Database Failover Gone Wrong**

**SC2-A – Stale data explanation**

* **Replication lag**: When a read replica in `eu-west-1` is promoted, any writes that occurred in `us-east-1` after the replica was created are **not** captured because the replica was a read‑only copy that streams WALs asynchronously. The lag equals the time between the last successful WAL shipment and the moment of promotion.
* **PostgreSQL streaming replication across regions** works by the primary shipping WAL to the replica via `pg_receivewal`. The replica applies WALs locally. Because network latency (≈ 100 ms) and replication is **asynchronous**, there is a non‑zero “gap” where writes may not yet be replicated.
* **Data‑loss scenarios**: <br>1. **Write‑ahead log not yet shipped** – a transaction committed on the primary but not yet received by the replica. <br>2. **Replication slot not used** – without a slot, the primary may recycle WAL segments, discarding un‑replicated data. <br>3. **Network partition** – if the replica falls behind and the primary is lost, the promoted replica may miss a batch of transactions.
* **Quantifying the loss window**: <br>```sql\nSELECT EXTRACT(EPOCH FROM now() - pg_last_xact_replay_timestamp()) AS replication_lag_seconds;\n```<br>Also check `SELECT * FROM pg_stat_replication;` and `SELECT * FROM pg_replication_slots;`. The `pg_last_xact_replay_timestamp()` reflects the latest transaction applied on the replica. The difference between `pg_current_wal_lsn()` on the primary (if still reachable) and `pg_last_received_lsn()` on the replica gives the exact WAL gap.


|-----------|----------------|-----------|

**SC3-B – Script to compare base‑image digests & list layers**

```bash
#!/usr/bin/env bash
set -euo pipefail

# ---- Configuration ----
ECR_REPO="123456789012.dkr.ecr.us-east-1.amazonaws.com/api-gateway"
IMAGE_TAG="v2.4.1"
KNOWN_GOOD_LAYERS_FILE="/tmp/known_good_layers.txt"   # pre‑populated list of layer digests

# ---- Helper: get digest of a Docker Hub image tag ----
get_hub_digest() {
  local repo=$1 tag=$2
  # Docker Hub API (public, no auth)
  curl -sSL "https://hub.docker.com/v2/repositories/library/${repo}/tags/${tag}/" |
    jq -r '.images[0].digest // empty'
}

# ---- Get node:20-slim digest from Docker Hub ----
NODE_DIGEST=$(get_hub_digest "node" "20-slim")
echo "node:20-slim digest (Docker Hub) = $NODE_DIGEST"

# ---- Get api-gateway:v2.4.1 manifest from ECR ----
# Use AWS SDK (aws ecr batch-get-image) – assumes AWS CLI configured
MANIFEST_JSON=$(aws ecr batch-get-image \
  --repository-name $(basename $ECR_REPO) \
  --image-ids imageTag=$IMAGE_TAG \
  --query 'images[0].imageManifest' \
  --output text)

# Extract layer digests
LAYER_DIGESTS=$(echo "$MANIFEST_JSON" | jq -r '.layers[].digest')

# ---- Compare base image ----
# The first layer of the manifest is usually the base image; we can check its digest
BASE_LAYER_DIGEST=$(echo "$MANIFEST_JSON" | jq -r '.rootfs.diff_ids[0] // empty')
if [[ "$BASE_LAYER_DIGEST" == "$NODE_DIGEST" ]]; then
  echo "✓ Base image matches expected digest."
else
  echo "✗ BASE IMAGE MISMATCH!"
  echo "  Expected: $NODE_DIGEST"
  echo "  Found:    $BASE_LAYER_DIGEST"
fi

# ---- List all layers and flag unknown ones ----
echo "All layer digests:"
echo "$LAYER_DIGESTS" | while IFS= read -r layer; do
  echo "  $layer"
  if ! grep -qx "$layer" "$KNOWN_GOOD_LAYERS_FILE" 2>/dev/null; then
    echo "  *** UNKNOWN LAYER ***"
  fi
done > /tmp/layer_report.txt

echo "Report written to /tmp/layer_report.txt"
```

*Explanation*  
* `get_hub_digest` queries Docker Hub’s public API for the exact digest of `node:20-slim`.  
* `aws ecr batch-get-image` pulls the manifest for `api-gateway:v2.4.1`.  
* The script compares the **rootfs diff_id** (the base image) against the Hub digest.  
* It then enumerates every layer and flags any that are not present in a pre‑populated `known_good_layers.txt` (generated from a trusted build).

**SC3-C – Hardened CI/CD pipeline**

1. **Base‑image pinning** – Store the exact digest of `node:20-slim` in a file (`base-images.yaml`). CI reads this file and fails if the built image’s first layer diff does not match.  
2. **Image signing** – Use **Cosign**: <br>`cosign sign --key cosign.key ${ECR_REPO}:${IMAGE_TAG}` <br>Store the signature in the container image’s OCI annotations.  
3. **Admission control** – Deploy a **Kyverno** policy that validates: <br>```yaml\napiVersion: kyverno.io/v1\nkind: ClusterPolicy\nmetadata:\n  name: require-image-signature\n spec:\n  validation:\n    imageRegistry:\n      reference: \"*\"\n      mutateDigest: true\n    rules:\n    - name: require-cosign\n      match:\n        any:\n          resources:\n            kinds:\n              - Pod\n      verifyImages:\n        - image: \"*\"\n          ofKind: \"*\"\n          cosign:\n            publicKey: \"https://cosign.example.com/fulcio.pub\"\n``` <br>Reject pods whose images lack a valid Cosign signature.

**SC5 – Medium – Mysterious Latency Spike in Microservices**

**SC5-A – Systematic debugging approach**

1. **Istio telemetry** – Query `istio_requests_total` and `istio_request_duration_seconds` for the `checkout-service` → `inventory-service` edge. Look for spikes in `5xx` or `timeout` counts.  
2. **Kubernetes metrics** – `kube_pod_container_resource_requests` vs `usage` to confirm pods aren’t throttled.

4. **Distributed tracing** – Use **Jaeger** or **Zipkin**. Enable `b3` or `w3c` propagation. Export traces for requests that hit the latency spike.  
   * In Jaeger UI, filter by `checkout-service` and examine the span graph.  
   * If the span for `inventory-service` is the longest, the problem is upstream of that service.  
   * If the span for the **proxy** (sidecar) is long, look at Envoy’s `upstream_rq_time` vs `request_time`.  
5. **Envoy metrics** – `envoy_cluster_manager_cluster_stats` (e.g., `upstream_rq_time`) and `envoy_listener_stats` (e.g., `downstream_rq_time`).  
   * `downstream_rq_time` ≈ total request time seen by the proxy.  
   * `upstream_rq_time` ≈ time spent talking to the upstream service.  
   * Large gap indicates proxy queueing (e.g., CPU pressure, connection pool exhaustion).  

**SC5-B – SQL diagnostic & Go circuit‑breaker**

*SQL diagnostic (PostgreSQL 16)* – shows lock holders, waiters, and the blocking query:

```sql
-- 1. Current long‑running queries (including the reconciliation job)
SELECT pid,
       usename,
       state,
       query_start,
       now() - query_start AS duration,
       query
FROM   pg_stat_activity
WHERE  state <> 'idle'
  AND  query NOT LIKE '%pg_stat_activity%'
ORDER BY duration DESC;

-- 2. Locks that are *waiting* (not granted)
SELECT l.pid AS locker_pid,
       a.usename AS locker_user,
       l.blocking_pid,
       a2.usename AS blocker_user,
       l.locktype,
       l.relation::regclass AS relation,
       l.mode,
       a.query AS locker_query,
       a2.query AS blocker_query
FROM   pg_locks l
JOIN   pg_stat_activity a  ON a.pid = l.pid
LEFT JOIN pg_locks lb ON lb.pid = l.blocking_pid AND lb.granted = true
LEFT JOIN pg_stat_activity a2 ON a2.pid = lb.pid
WHERE  NOT l.granted
ORDER BY l.pid;
```

*Go circuit‑breaker snippet (sony/gobreaker)*:

```go
package checkout

import (
    "context"
    "time"

    "github.com/sony/gobreaker"
)

type InventoryClient struct {
    cb *gobreaker.CircuitBreaker
    // HTTP client, base URL, etc.
}

func NewInventoryClient() *InventoryClient {
    settings := gobreaker.Settings{
        Name:        "inventoryService",
        Timeout:     5 * time.Minute, // how long to wait before trying again
        Interval:    0,                // reset statistics after each call
        Concurrency: 100,
        ReadyToTrip: func(count int64, consecutiveFailures int64) bool {
            // Trip if 5 consecutive failures
            return consecutiveFailures >= 5
        },
        OnStateChange: func(name string, from gobreaker.State, to gobreaker.State) {
            // optional logging
        },
    }
    return &InventoryClient{cb: gobreaker.NewCircuitBreaker(settings)}
}

func (c *InventoryClient) GetInventory(ctx context.Context, itemID string) (*InventoryResponse, error) {
    // Wrap the actual HTTP call with the circuit breaker
    resp, err := c.cb.Execute(func() (interface{}, error) {
        // actual HTTP request (e.g., using http.Client)
        req, _ := http.NewRequestWithContext(ctx, http.MethodGet,
            fmt.Sprintf("http://inventory-service/v1/inventory/%s", itemID), nil)
        out, err := http.DefaultClient.Do(req)
        if err != nil {
            return nil, err
        }
        defer out.Body.Close()
        if out.StatusCode != http.StatusOK {
            return nil, fmt.Errorf("inventory service returned %d", out.StatusCode)
        }
        var inv InventoryResponse
        json.NewDecoder(out.Body).Decode(&inv)
        return &inv, nil
    })
    if err != nil {
        return nil, err
    }
    return resp.(*InventoryResponse), nil
}
```

**SC5-C – Architectural solution to eliminate the problem**

| Concern | Solution |
|---------|----------|
| **CronJob contention** | **CQRS** – Move the heavy reconciliation job to a **read‑replica** (or a separate analytics DB). The serving DB only handles writes. |
| **Connection pool exhaustion** | Use ** bulkhead isolation**: create a dedicated JDBC DataSource with a small pool (`maxPoolSize=5`) for the reconciliation job, while the application uses a larger pool. |
| **Scheduling** | Shift the reconciliation to off‑peak hours (e.g., 02:00‑04:00) or run it **continuously** as a low‑priority workload. |
| **Prevent starvation** | • **PodDisruptionBudget (PDB)** – set `minAvailable: 80%` on the inventory-service Deployment to guarantee capacity. <br>• **ResourceQuotas** – enforce a limit on CPU/memory for the `reconciliation` namespace, preventing it from consuming all cluster resources. |
| **Overall** | Deploy the reconciliation job as a **CronJob** in its own namespace with its own **PriorityClass** (`low-priority`). Use **HorizontalPodAutoscaler** only for the serving pods, not for the CronJob. |

**SC6 – Hard – Zero‑Trust Network Overhaul for a Hybrid Environment**

**SC6-A – Identity & access layer design**

1. **Workload Identity (SPIFFE/SPIRE)**  
   * Deploy **SPIRE server** in each environment (on‑prem, AWS, Azure).  
   * Agents (SPIRE agent) run on each VM, EKS pod, AKS pod, installing a **SPIFFE ID** (`spiffe://example.org/ns/<ns>/sa/<sa>`).  
   * The agent issues **X.509 SVIDs** (short‑lived) to workloads.  

2. **Federated trust to cloud providers**  
   * **AWS** – Use **IAM Roles for Service Accounts (IRSA)**: map a Kubernetes ServiceAccount to an IAM role that trusts the SPIRE server’s X.509 certificate (via `aws-sigv4` authentication).  
   * **Azure** – Use **Azure AD Pod Identity** (or **Azure AD Workload Identity**) where the ServiceAccount references an Azure AD app registration that is trusted to the SPIRE server.  
   * **On‑prem** – Use existing PKI (e.g., Active Directory Certificate Services) to issue SVIDs that are trusted by the SPIRE server.  

3. **Cross‑environment federation**  
   * Establish a **trust domain** (`example.org`) across all three environments.  
   * SPIRE servers exchange **X.509 certificates** via **SPIFFE Federation** (using `spiffe://` trust bundles).  
   * A workload in **AWS** presenting an SVID signed by the SPIRE root can call a service on **on‑prem**; the on‑prem SPIRE validates the SVID against the federated bundle and authorizes the request. No shared secrets are exchanged.  

4. **Human identity**  
   * Use **Okta/ Azure AD** with **SSO** and **just‑in‑time (JIT)** access via **HashiCorp Vault** or **AWS IAM Access Analyzer**.  
   * Machine‑to‑machine communication uses the workload SVIDs; humans use short‑lived tokens.

**SC9 – Medium – Securing a Public‑Facing API After a Breach**

**SC9-A – Vulnerability analysis & fixes**

| # | Vulnerability | OWASP API category | Blast radius | Fix (code / infra) |
|---|---------------|--------------------|--------------|--------------------|
| 1 | BOLA (Broken Object Level Authorization) | **API3 – Broken Object Level Authorization** | Attacker can read/modify any user’s data → data breach, privilege escalation. | Implement **object‑level permission checks** in DRF viewset. Example: <br>```python\nfrom rest_framework import viewsets\nfrom .models import UserProfile\nfrom .serializers import UserProfileSerializer\nfrom rest_framework.permissions import BasePermission\n\nclass IsOwnerOrAdmin(BasePermission):\n    def has_object_permission(self, request, view, obj):\n        return request.user.is_staff or obj.user == request.user\n\nclass UserProfileViewSet(viewsets.ModelViewSet):\n    queryset = UserProfile.objects.all()\n    serializer_class = UserProfileSerializer\n    permission_classes = [IsOwnerOrAdmin]\n    def get_queryset(self):\n        # Only return records the user is allowed to see\n        if self.request.user.is_staff:\n            return UserProfile.objects.all()\n        return UserProfile.objects.filter(user=self.request.user)\n``` |
| 2 | Returning internal fields in API response | **API4 – Insecure Data Exposure** | Leakage of internal IDs, notes → compliance violations, reconnaissance for further attacks. | Use **serializers** that exclude internal fields for public endpoints, or apply **field‑level permissions**. <br>```python\nclass UserProfileSerializer(serializers.ModelSerializer):\n    class Meta:\n        model = UserProfile\n        fields = ['id','public_name','email','created_at']  # omit internal fields\n``` |
| 3 | No rate limiting → DoS / data scraping | **API5 – Broken Rate Limiting** | Attacker can exfiltrate 100k records, causing DB load, bandwidth cost, and potential DoS. | Deploy **AWS WAF** rate‑based rules (100 req/5 min per IP). <br>Or use **Django‑REST‑Framework throttling** (`AnonRateThrottle`, `UserRateThrottle`). |
| 4 | API keys in query string → logged | **API6 – Security Misconfiguration** | Keys exposed in CloudWatch/ALB logs → credential leakage, compromise of API. | Move keys to **Authorization: ApiKey** header. <br>Update ALB listener to strip query parameters from logs (`alb.log_format` config). <br>Rotate keys immediately. |

**SC9-C – Defense‑in‑depth architecture**

1. **API key hygiene** – Move keys to `Authorization: ApiKey` header, store keys **encrypted** in AWS Secrets Manager, rotate automatically (e.g., every 30 days).  
2. **OAuth2 migration** – Deploy **AWS API Gateway** (or Kong) in front of the ALB. <br> * Use **OAuth2.0** with **AWS Cognito** as authorization server. <br> * Issue short‑lived JWTs (e.g., 15 min). <br> * Existing API keys become **client credentials** for backward compatibility; migrate consumers gradually via **dual‑support** phase.  
3. **API gateway benefits** – Centralized auth, rate limiting, request validation, request‑transformation (strip query params), logging to CloudTrail.  
4. **Audit** – Enable **CloudTrail data events** for the ALB and API Gateway, forward to **CloudWatch Logs** and **Athena** for forensic queries.  
5. **Field‑level encryption** – Use **AWS KMS** with ** envelope encryption** for PII columns in the RDS database (e.g., `pgcrypto` functions). Apply at the application layer (encrypt before insert, decrypt after select).  

*Migration plan*  

| Phase | Action | Rollout |
|-------|--------|---------|
| **A – Preparation** | Deploy API Gateway, configure Cognito user pool, create JWT authorizer, start secret rotation. | No traffic change; only health‑check endpoints. |
| **B – Dual auth** | Keep existing API key support (header) while also accepting JWT via gateway. Use **request validator** to route based on `Authorization` header type. | Traffic split via **weighted target groups** (e.g., 70% old ALB, 30% gateway). |
| **C – Cutover** | Disable API key authentication in ALB, update client SDKs to use OAuth2, switch traffic 100% to gateway. | Perform after all consumers have been updated (communication 30 days lead time). |
| **D – Cleanup** | Remove old ALB, delete API key secrets, decommission key‑management overhead. | Post‑cutover validation (metrics, error rates). |

**SC10 – Hard – Designing a Multi‑Cluster Disaster Recovery Platform**

**SC10-A – Multi‑cluster architecture comparison**

| Approach | Description | RPO / RTO feasibility (12 ms latency, 200 TB MinIO) | Replication strategy |
|----------|-------------|---------------------------------------------------|----------------------|
| **Active‑Passive (Velero backup/restore)** | Primary cluster (Chicago) runs workloads; DR cluster (Dallas) idle. On failure, run Velero backup restore to Dallas. | **RPO** ≈ backup interval (e.g., every 15 min) → 15 min data loss. <br>**RTO** ≈ restore time (200 TB → several hours). **Not meeting** 1 h RTO. | - **Kubernetes**: Velero snapshots of PVcs (CSI snapshots). <br>- **PostgreSQL**: logical replication to standby (Patroni) – continuous. <br>- **Redis**: Redis Sentinel with replication. <br>- **RabbitMQ**: mirrored queues. <br>- **MinIO**: cross‑cluster replication (MinIO CR) – continuous. |
| **Active‑Active (Istio multi‑cluster or Cilium Cluster Mesh)** | Both clusters run workloads, traffic routed via service mesh with **global traffic policy**. Reads can go to nearest region; writes go to primary with **distributed consensus** (e.g., PostgreSQL synchronous replication). | **RPO** ≈ replication lag (≈ < 1 s) – achievable with synchronous replication within a region and asynchronous across regions. <br>**RTO** ≈ fail‑over via DNS/GSLB (< 5 min). **Meets** requirements. | - **PostgreSQL**: Patroni with `synchronous_standby_names` to Dallas standby (zero‑loss). <br>- **Redis**: Sentinel with automatic failover; enable **replication** to Dallas. <br>- **RabbitMQ**: Federation upstream/downstream between clusters. <br>- **MinIO**: Site replication (continuous). <br>- **Kubernetes**: Service mesh handles traffic split; no need for full cluster state sync. |

*Recommendation*: **Active‑Active with Istio multi‑cluster** (or Cilium Cluster Mesh) because it meets the tight RPO/RTO, leverages the low 12 ms inter‑site latency, and provides seamless fail‑over without large restore windows.

**SC10-C – Automated failover orchestration**

1. **Failure detection**  
   * **Health probes**: <br> - **Kubernetes**: `kube-state-metrics` + **Prometheus** alerts on pod readiness (`pod_ready_seconds`). <br> - **Database**: Patroni `pg_is_in_recovery` + `pg_last_xact_replay_timestamp` lag > 5 s triggers alert. <br> - **Site‑level**: AWS CloudWatch `Route53` health check for `us-east-1` resources; Azure Monitor for on‑prem.  
   * **“Site down”** defined as **simultaneous** failure of: <br> - All control plane nodes in Chicago (API server unreachable). <br> - Primary PostgreSQL instance not reachable. <br> - At least 2 of 3 Redis Sentinel nodes down.  

2. **DNS failover**  
   * Use **AWS Route53 GSLB** (or **Azure Front Door**) with health checks pointing to `us-east-1` A record. <br> * When health check fails, Route53 returns the Dallas IP.  

3. **Patroni automatic promotion**  
   * Patroni’s DCS (`etcd`) holds a `master` endpoint. When the primary node reports `unreachable` for > 30 s, Patroni’s `sync` logic promotes the standby (Dallas) to master. <br> * Ensure `synchronous_mode: asynchronous` on standby to avoid blocking.  

4. **Redis Sentinel failover**  
   * Sentinel monitors both clusters; when master down, Sentinel promotes a replica (Dallas) automatically.  

5. **RabbitMQ queue mirroring & federation**  
   * Configure **mirror queues** (`policy: {"ha-mode":"all","ha-sync-mode":"automatic"}`) so each cluster holds a copy. <br> * Set up **federation links** (Chicago → Dallas and Dallas → Chicago) for cross‑cluster message flow.  

6. **MinIO site replication catch‑up**  
   * MinIO **Site Replication** (SR) already replicates objects continuously. After failover, the Dallas site will have the latest objects; any writes that occurred during the brief window will be replayed via **replication lag** detection.  

7. **Update OpenTofu state**  
   * Use a **Terraform Cloud/Enterprise workspace** with **remote state** in S3. <br> * Trigger a **plan/apply** via **GitHub Actions** (or **GitLab CI**) that runs `terraform import` for the new primary resources (e.g., RDS instance) and `terraform state mv` to reflect the new primary/DR roles. <br> * Example command: <br>`terraform import aws_db_instance.primary <new-primary-arn>` <br>`terraform state mv aws_db_instance.replica aws_db_instance.primary`  

8. **Split‑brain handling**  
   * Deploy a **lease mechanism** (e.g., **etcd** TTL lock) during failover. The first cluster to acquire the lock proceeds; the other aborts and stays read‑only. <br> * Use **Istio** `VirtualService` weight `0` for the losing cluster.  

9. **Fail‑back procedure**  
   * Once Chicago is healthy, perform a **planned promotion**: <br> - Promote Chicago standby (if any) to primary. <br> - Update Route53 health checks and GSLB weights back to Chicago. <br> - Run Patroni `sync` to re‑establish replication from Chicago to Dallas (as standby). <br> - Verify data consistency (compare `pg_last_xact_replay_timestamp`). <br> - Clean up any temporary resources (e.g., extra RDS read replicas).  

10. **Monitoring & alerting**  
    * Alerts for: <br> - `SiteDown` (multiple health checks) <br> - `DatabaseReplicationLag` > 5 s <br> - `MinIOReplicationLag` > 30 s <br> - `RabbitMQMirrorSync` failure <br> * Use **PagerDuty** or **Slack** integration.  

Result: Automated, sub‑minute detection, < 1 s RPO (thanks to synchronous PostgreSQL replication), < 5 min RTO (DNS + Patroni promotion), and clear rollback path.
