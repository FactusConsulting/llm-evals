

K1 — **Deployment vs. StatefulSet**
A **Deployment** manages stateless pods with interchangeable identities, random names, and parallel scaling. A **StatefulSet** manages stateful applications with stable, unique network identifiers (e.g., `pod-0`, `pod-1`), ordered deployment/scaling, and stable persistent storage per pod. Use StatefulSet for databases (e.g., Cassandra, MySQL) requiring stable network IDs and storage.

K2 — **ClusterIP Routing**
A ClusterIP Service exposes a virtual IP (VIP) internal to the cluster. `kube-proxy` runs on each node and configures `iptables` or `IPVS` rules. When traffic hits the VIP, these rules randomly select an endpoint (Pod IP) from the Service’s Endpoints list and DNAT (Destination NAT) the packet to that Pod IP.

K3 — **PV, PVC, StorageClass**
*   **PersistentVolume (PV):** A cluster-wide storage resource provisioned by an admin or dynamically.
*   **PersistentVolumeClaim (PVC):** A request for storage by a user (Pod). It binds to a PV.
*   **StorageClass:** Defines the "type" of storage (e.g., SSD, HDD) and provisioner.
*   **Relation:** PVC requests storage -> StorageClass provisions a PV -> PV binds to PVC -> Pod mounts PVC.

K4 — **CrashLoopBackOff Troubleshooting**
1.  **Check Logs:** `kubectl logs <pod> --previous` to see why the process exited.
2.  **Check Events:** `kubectl describe pod <pod>` for OOMKilled, Liveness probe failures, or scheduling issues.
3.  **Check Config:** Verify ConfigMaps/Secrets are mounted correctly and environment variables are valid.
4.  **Check Resources:** Ensure memory/CPU limits aren't too low causing OOMKilled or throttling.

K5 — **CoreDNS Role**
CoreDNS provides service discovery and DNS resolution within the cluster. It maps Service names and Pod IPs to DNS records. If CoreDNS pods are down, internal DNS resolution fails, causing pods to be unable to communicate via Service names (e.g., `my-service.default.svc.cluster.local`), though direct IP communication may still work.

K6 — **Kubernetes Scheduler Logic**
The scheduler uses a **Filter** phase (Predicate) to remove nodes that cannot satisfy constraints (resources, taints, affinity). Then a **Score** phase (Priority) ranks remaining nodes.
*   **Factors:** 1. Resource availability (CPU/RAM), 2. Node Affinity/Selector, 3. Taints/Tolerations, 4. Pod Inter-Affinity (spread across nodes).

K7 — **Scheduling and Runtime Limits**
*   **Scheduling:** Yes, it will be scheduled. The node has 512MB free (4GB - 3.5GB requested). The pod requests 256Mi, which fits.
*   **Runtime:** If the pod uses 600Mi, it exceeds its `limits.memory` (512Mi). The Linux OOM Killer will terminate the container, resulting in an `OOMKilled` exit code.

K8 — **Ingress Request Lifecycle**
1.  **External LB:** Routes traffic to the Ingress Controller Pod IP.
2.  **Ingress Controller:** Reads Ingress resources, matches host/path rules, and forwards traffic to the target Service.
3.  **Service:** Acts as a virtual IP; `kube-proxy` (iptables/IPVS) selects a backend Pod from Endpoints.
4.  **Endpoints:** The actual Pod IP receives the request.
5.  **App Pod:** The application container processes the request.

K9 — **NetworkPolicy**
A NetworkPolicy defines rules for traffic allowed to/from pods.
*   **Default (No Policy):** All traffic is allowed (allow-all).
*   **With Policy:** If a policy selects a pod, it becomes **default-deny** for the traffic types specified (ingress/egress). Only explicitly allowed traffic flows.

K10 — **RollingUpdate vs. Recreate**
*   **RollingUpdate:** Gradually replaces pods (new version comes up before old goes down). Zero downtime.
*   **Recreate:** Terminates all existing pods before creating new ones. Downtime occurs.
*   **Use Recreate:** When the application cannot run two versions simultaneously (e.g., database schema migration requiring exclusive access).

K11 — **Namespace**
A Namespace is a virtual cluster within a physical cluster used for resource isolation and organization.
*   **Defaults:** `default` (user workloads), `kube-system` (system components), `kube-public` (public config), `kube-node-lease` (node heartbeats).

K12 — **kubectl describe pod**
Used for detailed debugging. Unlike `get`, it shows:
1.  **Events:** Recent warnings or status changes (e.g., Pulling image, Scheduled).
2.  **Conditions:** Detailed status of readiness/liveness probes.
3.  **Volumes/Containers:** Specific mount paths, resource limits, and environment variables.

K13 — **ConfigMap**
A ConfigMap stores non-confidential configuration data as key-value pairs.
*   **Methods:** 1. **Environment Variables:** Inject keys as env vars in the container spec. 2. **Volume Mount:** Mount the ConfigMap as a file in the container filesystem.

K14 — **Service Types**
*   **ClusterIP:** Exposes service on an internal IP (default). Accessible only within the cluster.
*   **NodePort:** Exposes service on a static port on each Node's IP. Accessible externally via `<NodeIP>:<Port>`.
*   **LoadBalancer:** Provisions an external cloud load balancer that routes traffic to the Service.

K15 — **DaemonSet**
A DaemonSet ensures a copy of a pod runs on **all** (or selected) nodes.
*   **Use Case:** Use instead of Deployment for node-level agents like log collectors (Fluentd), monitoring agents (Node Exporter), or storage drivers (CNI plugins).

K16 — **Taints/Tolerations vs. Affinity**
*   **Taints/Tolerations:** "Push" mechanism. Taints repel pods; tolerations allow pods to schedule on tainted nodes. *Use Case:* Dedicated GPU nodes (taint GPU, tolerate only GPU pods).
*   **Node Affinity:** "Pull" mechanism. Pod specifies preferred/required node labels. *Use Case:* Schedule web pods on nodes with SSDs.

K17 — **Kubernetes Operator**
An Operator is a custom controller that manages complex applications using Custom Resource Definitions (CRDs).
*   **Difference:** Standard controllers manage built-in resources (Pods, Deployments). Operators manage domain-specific resources (e.g., `PostgresCluster`).
*   **Solves:** Automates complex lifecycle tasks (backups, upgrades, failover) that `kubectl` cannot handle alone.

K18 — **etcd Consistency & Recovery**
*   **Model:** etcd uses the **Raft** consensus algorithm for strong consistency.
*   **Quorum Loss:** If quorum (majority) is lost (e.g., 2 of 3 nodes down), the cluster becomes read-only/unavailable to prevent split-brain.
*   **Recovery:** You cannot recover a 2-of-3 loss without data loss unless you have a snapshot. Restore the snapshot to a new etcd member and rejoin the cluster, or reinitialize the cluster from backup.

K19 — **RBAC & Manifests**
*   **Role/ClusterRole:** Define permissions (verbs on resources). Role is namespace-scoped; ClusterRole is cluster-wide.
*   **RoleBinding/ClusterRoleBinding:** Grants the permissions to a user/group/service account.
*   **Manifest:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — **DNS ndots Issue**
*   **Cause:** `ndots` (default 5) triggers search domain expansion. If a domain has fewer dots than `ndots`, the resolver appends search domains (e.g., `svc.cluster.local`), causing multiple DNS queries before failing.
*   **Fix:** Set `dnsConfig.options.ndots: 1` in the Pod spec to reduce search attempts, or use Fully Qualified Domain Names (FQDN) in the application.

D1 — **git rebase vs. merge**
*   **Merge:** Creates a new commit combining histories (preserves history structure).
*   **Rebase:** Rewrites history by moving commits to the tip of the target branch (linear history).
*   **Avoid Rebasing:** On shared/public branches (e.g., `main`), as it rewrites history and causes conflicts for other collaborators.

D2 — **TCP vs. UDP**
*   **TCP:** Connection-oriented, reliable, ordered delivery. (Protocols: HTTP, SSH).
*   **UDP:** Connectionless, unreliable, faster, no ordering. (Protocols: DNS, VoIP/Video Streaming).

D3 — **Race Condition**
A race condition occurs when multiple threads access shared data concurrently, and the outcome depends on the timing of execution.
*   **Example:** Two threads increment a counter `x = x + 1`. If both read `x=0` before writing, the result is `1` instead of `2`.

D4 — **Symmetric vs. Asymmetric Encryption**
*   **Symmetric:** Same key for encryption/decryption (fast).
*   **Asymmetric:** Public key encrypts, private key decrypts (secure key exchange).
*   **TLS:** Asymmetric is used during the handshake to exchange a session key. Symmetric is used for the actual data transfer (faster).

D5 — **Container Image Layers**
Images are built as stacked read-only layers.
*   **Layer Caching:** Docker caches layers based on the Dockerfile instructions.
*   **Best Practice:** Order instructions from least to most frequently changing (e.g., install deps before copying source code) to maximize cache hits and reduce build time.

D6 — **HTTP 503 Troubleshooting**
1.  **App Logs:** Check for application errors or unhandled exceptions.
2.  **Health Checks:** Verify Liveness/Readiness probes are failing (K8s).
3.  **Upstream Services:** Check if the 503 is coming from a dependency (e.g., DB, API Gateway).
4.  **Resources:** Check for CPU throttling or memory pressure causing timeouts.

D7 — **CAP Theorem**
A distributed system can only guarantee two of three: **C**onsistency, **A**vailability, **P**artition Tolerance.
*   **CP Example:** Banking system (Consistency > Availability). If partitioned, reject writes to prevent double-spending.
*   **AP Example:** Social Media Feed (Availability > Consistency). If partitioned, show old data rather than erroring.

D8 — **Horizontal vs. Vertical Scaling**
*   **Vertical:** Adding more resources (CPU/RAM) to a single node. Limited by hardware.
*   **Horizontal:** Adding more nodes/instances.
*   **Patterns:** Stateless architecture, Load Balancing, Database Sharding, Caching layers.

D9 — **Environment Variable**
A dynamic value available to processes at runtime.
*   **Persistence:** Add `export VAR=value` to `~/.bashrc` or `~/.profile` to persist across shell sessions.

D10 — **JSON vs. YAML**
*   **JSON:** Data interchange format. Strict syntax. *Advantage:* Easy for machines to parse.
*   **YAML:** Human-readable data serialization. *Advantage:* Supports comments and indentation for readability (common in K8s configs).

D11 — **REST API**
An API using HTTP protocols for communication.
*   **GET:** Retrieve data (Safe, Idempotent).
*   **POST:** Create new resource (Not idempotent).
*   **PUT:** Update/Replace resource (Idempotent).
*   **DELETE:** Remove resource (Idempotent).

D12 — **Version Pinning**
Locking dependencies to specific versions (e.g., `package.json` lockfile, `requirements.txt`).
*   **Importance:** Ensures reproducible builds across environments and prevents breaking changes from upstream updates.

D13 — **Compiled vs. Interpreted**
*   **Compiled:** Source code translated to machine code before execution (e.g., C++, Go). Faster runtime.
*   **Interpreted:** Source code executed line-by-line by a runtime (e.g., Python, JavaScript). Faster development iteration.

D14 — **Reverse vs. Forward Proxy**
*   **Reverse Proxy:** Sits in front of servers, routes client requests to backend services (e.g., Nginx for load balancing, SSL termination).
*   **Forward Proxy:** Sits in front of clients, routes client requests to the internet (e.g., Squid for corporate filtering/anonymity).

D15 — **Deadlock**
A situation where processes wait indefinitely for resources held by each other.
*   **Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

D16 — **Eventual Consistency**
Data updates propagate asynchronously; all nodes will eventually agree.
*   **Cassandra:** Uses tunable consistency levels (ONE, QUORUM, ALL). Read-after-write consistency is not guaranteed at `ONE` but is at `QUORUM`/`ALL`.

D17 — **mTLS (Mutual TLS)**
Both client and server authenticate each other using certificates.
*   **Handshake:** Server sends cert -> Client verifies -> Client sends cert -> Server verifies.
*   **Use Case:** Service-to-service communication in Service Meshes (e.g., Istio) to ensure zero-trust security.

D18 — **Hash Table Internals**
Stores key-value pairs in an array using a hash function to compute an index.
*   **Collisions:** 1. **Chaining:** Store a linked list at the index. 2. **Open Addressing:** Find next available slot (probing).
*   **Complexity:** Average O(1) for insert/lookup/delete. Worst case O(n) if all keys collide.

D19 — **Circuit Breaker Pattern**
Prevents cascading failures by stopping requests to a failing service.
*   **States:** **Closed** (Normal), **Open** (Fail fast, no requests), **Half-Open** (Test if service recovered).
*   **Relation:** Works with retries; if circuit is open, retries are skipped immediately to save resources.

D20 — **Optimistic vs. Pessimistic Concurrency**
*   **Optimistic:** Assumes no conflict; checks version on commit. *Example:* `UPDATE table SET val=1 WHERE id=1 AND version=5`.
*   **Pessimistic:** Assumes conflict; locks resource on read. *Example:* `SELECT ... FOR UPDATE`.
*   **Choice:** Optimistic for high read/low write contention. Pessimistic for high write contention or critical financial data.
