

CL1 — **IaaS vs PaaS vs SaaS:**
*   **IaaS (Infrastructure as a Service):** Provides virtualized computing resources (VMs, storage, networking). You manage OS, middleware, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a managed environment for developing and running apps. You manage code and data; provider manages OS/runtime. *Example: AWS RDS or Azure App Service.*
*   **SaaS (Software as a Service):** Delivers fully managed software over the internet. You manage only user access and data. *Example: Salesforce or Microsoft 365.*

CL2 — **Shared Responsibility Model:**
*   **Concept:** Security is a joint effort. Provider secures the cloud (hardware, physical); Customer secures what is in the cloud (data, config).
*   **IaaS VMs:** Provider secures physical host/network. Customer secures Guest OS, patches, firewall rules, data.
*   **Managed Kubernetes:** Provider secures control plane, nodes (sometimes). Customer secures pod security, network policies, app config, secrets.
*   **SaaS (M365):** Provider secures everything (app, infra, data at rest). Customer secures user access (MFA), data classification, device compliance.

CL3 — **VPC, Subnet, SG, NACL:**
*   **VPC:** Virtual network boundary (IP range).
*   **Subnet:** Segment of VPC IP range, tied to an Availability Zone.
*   **Security Group (SG):** Instance-level firewall. **Stateful** (returns allowed automatically).
*   **NACL:** Subnet-level firewall. **Stateless** (must allow inbound and outbound explicitly).
*   **Layering:** Traffic flows VPC → Subnet (NACL) → Instance (SG). NACL acts as a perimeter for the subnet; SG acts as a perimeter for the instance.

CL4 — **Multi-Account Strategy:**
*   **Landing Zone:** Pre-configured, secure multi-account environment (networking, identity, logging).
*   **OUs:** Organizational Units group accounts by function (Prod, Dev, Security).
*   **Guardrails:** SCPs (Service Control Policies) enforce limits (e.g., no us-east-1).
*   **Shared Networking:** AWS Transit Gateway or Azure Hub-Spoke connects accounts securely without VPC peering sprawl.
*   **Centralized Logging:** CloudTrail/CloudWatch logs aggregated to a Security account.
*   **Single Account Risk:** High blast radius, billing confusion, difficulty isolating workloads, harder to enforce least privilege.

CL5 — **Infrastructure as Code (IaC):**
*   **Concept:** Managing infrastructure via declarative code files.
*   **Terraform/OpenTofu:** Multi-cloud, stateful, large ecosystem. Choose for portability.
*   **Pulumi:** Uses general-purpose languages (Python/TS). Choose for complex logic/Dev teams.
*   **CloudFormation/Bicep:** Native to AWS/Azure. Choose for deep native integration/support.
*   **Crossplane:** Kubernetes-native IaC. Choose if managing infra via K8s API.

CL6 — **Kubernetes Autoscaling:**
*   **HPA:** Scales pods based on CPU/Memory or custom metrics.
*   **VPA:** Adjusts pod resource requests/limits (requires restart).
*   **Cluster Autoscaler:** Adds/removes nodes based on pending pods.
*   **KEDA:** Event-driven autoscaling (e.g., queue depth, cron).
*   **KEDA vs HPA:** Use KEDA when scaling based on external events (e.g., SQS queue length) rather than resource utilization.

CL7 — **Disaster Recovery (DR) Strategy:**
*   **RPO/RTO:** Define max data loss (RPO) and max downtime (RTO).
*   **Active-Active:** Traffic routed to both regions. High cost, zero RTO.
*   **Active-Passive:** Primary handles traffic; secondary standby. Lower cost, higher RTO.
*   **DB Replication:** Sync (strong consistency, latency) vs Async (performance, potential data loss).
*   **DNS Failover:** Route53 Health Checks/Traffic Manager route traffic on failure.
*   **State:** Use global storage (S3) or replicated DBs.
*   **DR Types:**
    *   *Pilot Light:* Minimal core running (DB), scale up on failover.
    *   *Warm Standby:* Scaled-down version running, ready to scale.
    *   *Multi-site Active-Active:* Full capacity in both regions.

CL8 — **GitOps:**
*   **Model:** Git repository is the single source of truth. Controller syncs cluster state to Git state.
*   **ArgoCD vs Flux:** ArgoCD has a UI and App of Apps; Flux is CLI/CRD focused, lighter.
*   **Secrets:** Use Sealed Secrets (encrypted in Git) or External Secrets Operator (fetch from Vault/AWS Secrets Manager).
*   **Drift:** If manual change occurs, GitOps controller detects drift and reverts to Git state automatically.

CL9 — **Stateful K8s Migration:**
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC:** Use `local` storage class for low latency (node-attached).
*   **Headless Service:** `clusterIP: None` for stable DNS names per pod.
*   **Init Containers:** Run before app to prepare filesystem/config.
*   **ConfigMap:** Mount as volume to specific paths.
*   **PDB:** Ensure minimum pods available during voluntary disruptions.

CL10 — **Identity in K8s:**
*   **Service Account:** K8s identity for pods.
*   **Workload Identity:** Cloud identity mapped to K8s SA (e.g., GCP Workload Identity).
*   **IRSA:** AWS specific (IAM Role for Service Account).
*   **Bad Practice:** Mounting static keys/secrets in pods exposes them to theft/leakage.
*   **Solution:** Workload Identity Federation uses OIDC to exchange K8s SA token for short-lived cloud credentials.

CL11 — **Storage Types:**
*   **Object (S3/Blob):** Unstructured data (files, backups). High durability (11 9s).
*   **Block (EBS/Disk):** Raw volume for VMs/DBs. Low latency, high IOPS.
*   **File (EFS/Azure Files):** Shared filesystem (NFS/SMB). Multi-attach.
*   **Guarantees:** Object (11 9s durability), Block (99.99%+ availability), File (Regional availability).

CL12 — **Zero Trust K8s:**
*   **Network Policies:** Default deny all traffic; allow only explicit paths.
*   **Service Mesh:** mTLS for service-to-service encryption (Istio/Linkerd).
*   **Pod Identity:** No cloud creds in pods (see CL10).
*   **Admission:** OPA/Kyverno enforce policies (e.g., no root user).
*   **Image Signing:** Cosign/Notary verify image integrity.
*   **Runtime:** Falco detects anomalous behavior.
*   **Diff:** Traditional = Perimeter trust. Zero Trust = Verify every request, assume breach.

CL13 — **CDN:**
*   **Concept:** Distributed edge servers caching content closer to users.
*   **Mechanism:** DNS resolves to nearest edge; edge serves cached content or fetches from origin.
*   **Services:** AWS CloudFront, Azure CDN.
*   **Use Case:** Static assets (images, JS), global latency reduction.
*   **Direct Origin:** Dynamic content, private data, or low-traffic sites.

CL14 — **Regions & AZs:**
*   **Region:** Geographic area (e.g., us-east-1).
*   **AZ:** Isolated data center within a region.
*   **Multi-AZ:** Protects against data center failure (HA).
*   **Zonal Resource:** Tied to one AZ (e.g., specific VM).
*   **Regional Resource:** Spans AZs (e.g., S3 bucket, Load Balancer).

CL15 — **Managed Database:**
*   **Service:** RDS, Cloud SQL, Azure SQL.
*   **Provider Handles:** Hardware, OS patching, DB engine patching, backups, replication, failover.
*   **Customer Handles:** Schema design, user management, query optimization, data security.

CL16 — **IAM & Least Privilege:**
*   **Users:** Human identities.
*   **Groups:** Collections of users.
*   **Roles:** Identities assumed by services/users (temporary creds).
*   **Policies:** JSON rules defining permissions.
*   **Least Privilege:** Grant only permissions necessary for the task. Apply via specific resource ARNs and actions, avoiding wildcards (`*`).

CL17 — **Serverless:**
*   **Concept:** Event-driven compute without server management.
*   **Comparison:** AWS Lambda (broad ecosystem), Azure Functions (Microsoft stack), GCP Functions (Google stack).
*   **Cold Start:** Latency when initializing a new container instance. Matters for latency-sensitive apps.
*   **Poor Fit:** Long-running processes (>15 mins), stateful apps, consistent high load (often cheaper on VMs).

CL18 — **K8s Ingress:**
*   **Ingress Resource:** L7 routing, controller-dependent.
*   **Gateway API:** Standardized L4/L7, more extensible.
*   **Cloud LB:** Direct cloud load balancer (e.g., AWS NLB).
*   **Mesh Ingress:** Sidecar-based (e.g., Istio Ingress Gateway).
*   **TLS:** Terminate at LB (offload) or Ingress (end-to-end encryption).
*   **Gateway API:** Use for complex routing, multi-cluster, or when Ingress limitations are hit.

CL19 — **Cost Optimization ($80k/mo):**
*   **Commitments:** Reserved Instances/Savings Plans for steady state.
*   **Spot/Preemptible:** For fault-tolerant batch workloads (70-90% savings).
*   **Right-sizing:** Analyze CPU/Mem usage, downsize over-provisioned resources.
*   **Storage:** S3 Intelligent-Tiering, Archive for old logs.
*   **Idle Detection:** Remove unattached EBS, idle LBs.
*   **FinOps:** Tagging strategy, showback/chargeback to teams.
*   **Tools:** AWS Cost Explorer, Kubecost, CloudHealth.

CL20 — **Multi-Cloud Strategy:**
*   **Abstraction:** Terraform (IaC), K8s (Runtime), CNCF tools (CNI, CSI).
*   **Networking:** Interconnect/Peering between clouds (expensive/complex).
*   **Identity:** Central IdP (Okta/Azure AD) federated to both clouds.
*   **Trade-offs:** Avoids lock-in, resilience vs. increased complexity, skill requirements, data egress costs.
*   **Justification:** Compliance (data residency), M&A integration, specific service needs.
*   **Unnecessary:** If one cloud meets 95%+ needs, multi-cloud adds cost/complexity without proportional benefit.

OT1 — **Purdue Model (ISA-95):**
*   **Level 0:** Physical Process (Sensors/Actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Supervisory (HMI, SCADA).
*   **Level 3:** Manufacturing Operations (MES, Historian).
*   **Level 4:** Enterprise (ERP, Business Planning).
*   **Level 5:** Internet/External.

OT2 — **IT vs OT:**
*   **IT:** Prioritizes Confidentiality, Integrity, Availability (CIA).
*   **OT:** Prioritizes Safety, Availability, Integrity (CIA).
*   **Patching:** OT systems often run legacy OS (Win XP/7), proprietary hardware, and cannot tolerate downtime. Patching can break deterministic timing or crash controllers.

OT3 — **IDMZ (Industrial DMZ):**
*   **Role:** Buffer zone between IT (L4) and OT (L1-L3).
*   **Traffic:** Read-only data (L3→L4), Config updates (L4→L3, strictly controlled).
*   **Danger:** Direct L4-L1 allows lateral movement from corporate network to critical control systems, risking physical safety.

OT4 — **OT Protocols:**
*   **Modbus TCP:** L1/L2 (Simple, legacy).
*   **OPC UA:** L2/L3 (Secure, cross-platform, modern).
*   **EtherNet/IP (CIP):** L1 (Industrial Ethernet).
*   **PROFINET:** L1 (Real-time, Siemens).
*   **MQTT:** L3/L4 (Pub/Sub, IoT/Cloud).

OT5 — **Data Diode vs Firewall:**
*   **Data Diode:** Hardware-enforced one-way data flow (physical).
*   **Firewall:** Software/Logic-based bi-directional filtering.
*   **Use Diode:** When data must leave OT but never enter (e.g., sending telemetry to cloud).
*   **Limitation:** Cannot receive commands or updates through the diode.

OT6 — **Data Flow Design:**
*   **Flow:** PLC (L1) → Historian (L3) → OPC UA Server → Edge Gateway → MQTT Broker → Cloud.
*   **Security:** IDMZ between Edge and Cloud. Firewall between Historian and Edge. Encryption (TLS) on all hops.

OT7 — **IEC 62443 Zones & Conduits:**
*   **Zone:** Group of assets with same security requirements (e.g., "Safety Zone").
*   **Conduit:** Communication path between zones.
*   **Design:**
    *   Zone 1: PLCs/SIS (High Security).
    *   Zone 2: SCADA/HMI.
    *   Zone 3: Engineering Workstations.
    *   Zone 4: Corporate.
    *   Conduits: Firewalls between each zone.

OT8 — **Segmentation Strategy:**
*   **VLANs:** Separate VLAN per production line.
*   **Firewalls:** Between lines and IT.
*   **Switches:** Managed switches with port security (MAC binding).
*   **Vendor Access:** Jump host in DMZ, time-limited, MFA.
*   **Transition:** Implement in phases (e.g., one line at a time), test during maintenance windows, rollback plan ready.

OT9 — **SIS vs BPCS:**
*   **BPCS:** Controls normal process (PLC/DCS).
*   **SIS:** Safety system (Emergency Shutdown). Independent.
*   **IEC 61511:** Functional Safety standard.
*   **Isolation:** SIS must be isolated to prevent IT malware from disabling safety trips.
*   **Ransomware on SIS:** Could prevent shutdown during emergency, causing physical damage or injury.

OT10 — **PLC vs DCS vs SCADA:**
*   **PLC:** Discrete control, fast, localized.
*   **DCS:** Continuous process control, integrated, centralized.
*   **SCADA:** Supervisory control, wide area, data collection.
*   **Coexistence:** Yes. PLCs control machines, DCS manages process, SCADA monitors plant-wide.

OT11 — **Remote Access:**
*   **Architecture:** Jump Host (Bastion) in IDMZ.
*   **Controls:** MFA, Session Recording, Time-limited access, Vendor approval.
*   **RDP Direct:** Unacceptable. Bypasses security controls, no audit trail, exposes HMI directly to internet/corporate.

OT12 — **Incident Response (Nation-State):**
*   **Detection:** IDS/IPS on L3/L2, Anomaly detection on traffic.
*   **Response:** Isolate compromised VLANs (Firewall block), disconnect vendor VPN.
*   **Coordination:** Work with Control Room to ensure manual overrides are ready.
*   **Operator Role:** Maintain physical safety, monitor critical parameters, execute manual shutdown if cyber controls fail.
*   **Safety First:** Do not shut down safety systems even if compromised.

OT13 — **HMI:**
*   **Role:** Interface for operators to view process and issue commands.
*   **Diff:** HMI = Runtime (Operator view). Engineering Workstation = Development (Logic/Config creation).

OT14 — **Historian:**
*   **Role:** Time-series database for process data.
*   **Importance:** Trend analysis, compliance, troubleshooting.
*   **Plant Historian (L3):** Local, high frequency, short retention.
*   **Enterprise Historian (L4):** Aggregated, long retention, business analytics.

OT15 — **Ladder Logic:**
*   **Device:** PLC.
*   **Concept:** Visual programming resembling electrical relay circuits.
*   **Dominance:** Legacy investment, electrician familiarity, deterministic execution, ease of troubleshooting for hardware engineers.

OT16 — **RTU vs PLC:**
*   **RTU:** Remote Terminal Unit. Focus on telemetry, comms (radio/satellite), wide temp range.
*   **PLC:** Focus on local logic control.
*   **Environment:** RTUs for remote sites (pipelines, wells, substations) where connectivity is limited.

OT17 — **Analog vs Digital:**
*   **Analog:** Continuous signal (4-20mA, 0-10V).
*   **Digital:** Discrete (On/Off, 0/1).
*   **4-20mA:** "Live zero" (4mA = 0% signal). Distinguishes between 0% signal and broken wire (0mA). Noise immunity.

OT18 — **Asset Inventory:**
*   **Foundation:** Cannot secure what you don't know exists.
*   **Tools:** Passive monitoring (Packet capture), Active scanning (Nmap - risky).
*   **Active Scanning Risk:** Can crash legacy devices, trigger alarms, or disrupt real-time traffic. Prefer passive discovery.

OT19 — **MITRE ATT&CK for ICS:**
*   **Framework:** Tactics/Techniques specific to ICS.
*   **Tactics:** Reconnaissance, Initial Access, Execution, Persistence, Impact.
*   **Example:** Tactic: Impact. Technique: Manipulation of Control Logic.
*   **Diff:** Enterprise focuses on data theft; ICS focuses on physical process disruption/safety.
*   **Use:** Map controls to techniques to find gaps (e.g., do we detect logic manipulation?).

OT20 — **Converged SOC:**
*   **Log Collection:** Syslog/Agentless (to avoid load on OT).
*   **SIEM:** OT-specific parsers (Modbus, DNP3).
*   **Workflow:** IT Analyst triage → Escalate to OT Engineer for validation.
*   **False Positives:** Tune rules based on baseline OT traffic.
*   **Firmware Alert:** Verify signature, isolate device, contact vendor, check safety impact before patching. Never patch without OT approval.
