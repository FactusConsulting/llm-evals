

AA1 — **Monolith vs. Microservices:** A monolith is a single deployable unit where all components are tightly coupled. Microservices decompose the application into loosely coupled, independently deployable services.
**3 Microservice Problems:**
1.  **Distributed Transactions:** Maintaining data consistency across services requires complex patterns (Saga) unlike local ACID transactions.
2.  **Network Latency & Reliability:** Inter-service communication introduces network failure modes and latency not present in in-process calls.
3.  **Operational Complexity:** Requires orchestration (Kubernetes), service discovery, and centralized logging/tracing infrastructure.

AA2 — **Sync vs. Async:** Synchronous communication blocks the caller until a response is received (Request/Response). Asynchronous communication allows the caller to continue without waiting (Fire-and-forget or Pub/Sub).
**Examples:**
*   **Sync:** HTTP/REST, gRPC.
*   **Async:** RabbitMQ (AMQP), Apache Kafka.

AA3 — **API Gateway vs. Reverse Proxy:** A reverse proxy routes traffic based on IP/Port/Path. An API Gateway adds application-level logic: authentication, rate limiting, request transformation, and aggregation.
**Replacement:** An API Gateway can replace a reverse proxy functionally, but a dedicated reverse proxy (e.g., Nginx) is often lighter and more performant for simple routing. Use a Gateway for business logic offloading; use a Proxy for pure traffic management.

AA4 — **Saga Pattern:** A sequence of local transactions where each updates data within a single service. If a step fails, compensating transactions undo previous changes.
**Choreography:** Services emit events to trigger the next step (decentralized). Good for simple flows.
**Orchestration:** A central coordinator tells services what to do (centralized). Better for complex flows requiring visibility and control.

AA5 — **CQRS:** Separates read (Query) and write (Command) models.
**Pairing with Event Sourcing:** Event Sourcing stores state changes as an immutable log of events. CQRS uses this log to build optimized read projections.
**Problem Solved:** Traditional CRUD struggles with high read/write contention and complex reporting. CQRS+ES allows scaling reads independently and provides a full audit trail of state changes.

AA6 — **Circuit Breaker:** Prevents cascading failures by stopping requests to a failing service.
**States:** Closed (normal), Open (fail fast), Half-Open (test recovery).
**Differs from Retry:** Retry assumes the failure is transient and retries immediately. Circuit Breaker assumes the service is down and stops traffic to allow recovery.
**Together:** Use Circuit Breaker to stop traffic, then Retry with backoff for transient errors within the Closed state.

AA7 — **Multi-Tenant Isolation:**
1.  **Shared DB, Shared Schema:** Low cost, high noisy-neighbor risk, complex row-level security.
2.  **Shared DB, Separate Schema:** Medium cost, better isolation, schema management overhead.
3.  **Separate DB:** High cost, maximum security/isolation, easiest backup/restore per tenant.
**Trade-off:** Choose Separate DB for regulated/enterprise tenants; Shared Schema for SaaS volume/cost efficiency.

AA8 — **Consistency:** Eventual consistency guarantees data will match eventually; Strong consistency guarantees all nodes see the same data at the same time.
**Inventory Architecture:** Use **Strong Consistency**.
**Store:** Relational DB (PostgreSQL) with row-level locking or a distributed lock manager (Redis Redlock).
**Pattern:** Pessimistic locking on the SKU row during checkout to prevent overselling. At scale, use sharding by SKU to reduce lock contention.

AA9 — **Sidecar Proxy:** A helper process deployed alongside the application container (e.g., Envoy in Istio).
**Envoy/Istio:** Envoy handles traffic (Data Plane); Istio Control Plane configures Envoy via xDS API.
**Data Plane:** Handles actual traffic flow. **Control Plane:** Manages policies and configuration.
**mTLS:** Encrypts traffic between services automatically. Solves the problem of managing certificates in every application codebase and ensures zero-trust identity verification between services.

AA10 — **Strangler Fig:** Incrementally migrate functionality from a legacy system to a new system by routing traffic to the new system over time.
**Strategy:**
1.  Place a reverse proxy in front of the .NET Framework monolith.
2.  Build new features as .NET 8 microservices.
3.  Configure the proxy to route specific API paths to the new services.
4.  Gradually move more paths until the monolith is "strangled" and can be decommissioned.

AA11 — **12-Factor App:** Methodology for building SaaS apps.
**6 Factors:**
1.  **Codebase:** One codebase tracked in VCS.
2.  **Dependencies:** Explicitly declare and isolate dependencies.
3.  **Config:** Store config in environment variables.
4.  **Backing Services:** Treat services (DB, Queue) as attached resources.
5.  **Build, Release, Run:** Strictly separate build and run stages.
6.  **Processes:** Run the app as one or more stateless processes.
**Why:** Ensures portability, scalability, and parity between dev/prod.

AA12 — **Event-Driven (Kafka) vs. Request-Driven (REST/gRPC):**
*   **Coupling:** Kafka (loose, async); REST (tight, sync).
*   **Scalability:** Kafka (high throughput, buffering); REST (limited by request latency).
*   **Debugging:** Kafka (harder, replay logs); REST (easier, request/response logs).
*   **Ordering:** Kafka (partition-level); REST (none).
*   **Failure:** Kafka (retry via consumer lag); REST (retry logic in client).
**Choose Kafka:** For audit trails, high throughput, decoupling. **Choose REST:** For immediate user feedback, simple CRUD.

AA13 — **Load Balancer:** Distributes network traffic across multiple servers.
**Layer 4:** Works at Transport Layer (TCP/UDP). Routes based on IP/Port. Fast, unaware of content.
**Layer 7:** Works at Application Layer (HTTP). Routes based on URL, Headers, Cookies.
**Use Case:** Layer 7 is required for path-based routing (e.g., `/api` to backend, `/static` to CDN) or SSL termination.

AA14 — **Message Queue:** Buffers messages between producers and consumers.
**Queue (RabbitMQ):** Messages are deleted after consumption. Competing consumers. Good for task distribution.
**Log (Kafka):** Messages are persisted and replayable. Multiple consumer groups. Good for event streaming.
**Pick:** RabbitMQ for task queues (emails, jobs). Kafka for event sourcing, analytics, or replay requirements.

AA15 — **Container vs. VM:** A VM virtualizes hardware (Hypervisor + Guest OS). A Container virtualizes the OS kernel (Namespaces + Cgroups).
**Difference:** Containers share the host kernel; VMs have full OS isolation.
**Popularity:** Containers are lighter, start faster, and use fewer resources, making them ideal for high-density microservice deployments.

AA16 — **Stateless vs. Stateful:** Stateless services hold no session data between requests (e.g., API Gateway). Stateful services store data locally (e.g., Database).
**Scaling:** Stateless services can be scaled horizontally by simply adding nodes behind a load balancer. Stateful services require data sharding or replication logic.
**Example:** Stateless: Web Server. Stateful: Redis Cache.

AA17 — **ORM:** Maps objects in code to database tables.
**Examples:** Hibernate (Java), Entity Framework (.NET).
**Trade-offs:**
*   **ORM:** Faster development, type safety, abstraction.
*   **Raw SQL:** Better performance, fine-grained control, complex query optimization.
**Risk:** ORMs can generate inefficient queries (N+1 problem).

AA18 — **Bulkhead Pattern:** Isolates resources (thread pools, connections) for different services to prevent a failure in one from exhausting resources for all.
**Relation:** Prevents cascade failures in microservices.
**Implementation:** Assign a dedicated thread pool to each downstream service call. If Service A hangs, its thread pool fills up, but Service B's pool remains available.

AA19 — **OT vs. CRDT:**
*   **OT:** Centralized server resolves conflicts. Complex logic, requires server coordination.
*   **CRDT:** Decentralized, mathematically guaranteed convergence.
**Comparison:** CRDTs handle offline support better (merge locally). OT has lower latency for real-time but requires connectivity.
**Choice:** **CRDTs** for offline editing support. They allow local edits to merge automatically upon reconnection without server-side conflict resolution logic.

AA20 — **Distributed Tracing:**
*   **Context Propagation:** Inject trace IDs (W3C Trace Context) into HTTP headers and Kafka message headers.
*   **Sampling:** Head-based (decide at start) vs. Tail-based (decide after seeing errors). Tail-based is better for debugging.
*   **Storage:** Jaeger/Tempo store traces for querying.
*   **Async Continuity:** Ensure the Kafka producer injects the trace context into the message header, and the consumer extracts it to continue the span.

OP1 — **Hypervisor Type 1 vs. 2:**
*   **Type 1 (Bare-metal):** Runs directly on hardware. Examples: VMware ESXi, Microsoft Hyper-V.
*   **Type 2 (Hosted):** Runs on top of an OS. Examples: Oracle VirtualBox, VMware Workstation.
**Use:** Type 1 for production servers; Type 2 for development/testing.

OP2 — **SAN vs. NAS:**
*   **SAN (Storage Area Network):** Block-level storage. Protocols: Fibre Channel, iSCSI. Used for databases/VMs requiring low latency.
*   **NAS (Network Attached Storage):** File-level storage. Protocols: NFS, SMB/CIFS. Used for file sharing.
**Use:** SAN for high-performance app storage; NAS for shared documents.

OP3 — **3-Tier vs. Leaf-Spine:**
*   **3-Tier:** Core, Distribution, Access. Can create bottlenecks at the core.
*   **Leaf-Spine:** Every leaf connects to every spine. Provides predictable low latency and non-blocking bandwidth.
**Problem Solved:** Leaf-spine eliminates oversubscription bottlenecks common in 3-tier East-West traffic (server-to-server).

OP4 — **Proxmox HA:**
*   **Architecture:** 3 nodes minimum for quorum.
*   **Storage:** Ceph (integrated) or iSCSI/NFS.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) to prevent split-brain.
*   **Failure:** If a node fails, HA manager restarts VMs on remaining nodes. Quorum requires 2/3 nodes to vote.

OP5 — **VLAN Trunking:** Carries multiple VLANs over a single link using 802.1Q tags.
**802.1Q:** Inserts a 4-byte tag into the Ethernet frame with VLAN ID.
**Linux Config:** Create sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`. Assign IPs to `eth0.10`, `eth0.20`, etc.

OP6 — **RAID Levels:**
*   **RAID 1:** Mirror (50% capacity).
*   **RAID 5:** Parity (N-1 capacity).
*   **RAID 6:** Double Parity (N-2 capacity).
*   **RAID 10:** Mirror + Stripe (50% capacity, high perf).
*   **RAID Z2:** ZFS equivalent of RAID 6.
**Choice:** **RAID 10** for 6 drives DB. Better write performance and rebuild times than RAID 6, which is critical for database I/O.

OP7 — **DNS Architecture:**
*   **Internal:** AD-integrated DNS for internal resolution.
*   **DMZ:** Separate authoritative servers for public zones.
*   **Split-Horizon:** Internal clients resolve internal IPs; external resolve public IPs.
*   **Security:** DNSSEC on external zone. Forwarders to ISP/Cloud for external queries.
*   **Laptop:** Uses conditional forwarding or DHCP options to switch DNS servers based on network (Office vs. VPN).

OP8 — **PKI Chain:** Root CA (offline) signs Subordinate CA. Subordinate signs End-Entity (Server/Client).
*   **Validation:** CRL (list of revoked) vs. OCSP (real-time check).
*   **Compromise:** Compromised Subordinate = Revoke Subordinate cert (Root safe). Compromised Root = Revoke Root (All trust broken, massive revocation).
*   **Deployment:** Auto-enrollment via GPO for internal devices.

OP9 — **WAN Comparison:**
*   **MPLS:** High cost, high reliability, low latency.
*   **IPsec:** Secure, variable latency (internet dependent).
*   **SD-WAN:** Intelligent path selection, cost-effective, manages multiple links.
*   **WireGuard:** Simple, fast, but less enterprise management features.
**Recommendation:** **SD-WAN**. It optimizes VoIP traffic over multiple links (MPLS + Internet) for cost and reliability.

OP10 — **OOB Management:** iDRAC (Dell), iLO (HPE), IPMI (Generic).
**Critical:** Allows management when OS is down or network is unreachable.
**Risk:** If exposed to internet, attackers can gain full hardware control (firmware, power, console). Must be on a dedicated management network.

OP11 — **LVM vs. ZFS:**
*   **LVM:** Logical Volume Manager on Linux. Flexible resizing. Snapshots are copy-on-write but depend on underlying FS.
*   **ZFS:** Combined FS and Volume Manager. Snapshots are instant, atomic, and space-efficient.
**Use:** LVM for general Linux flexibility. ZFS for data integrity, compression, and advanced snapshot management.

OP12 — **Stretch Cluster/DR:**
*   **Design:** 2 sites + 1 Witness node (tiebreaker).
*   **Ceph:** CRUSH rules to replicate across sites.
*   **Latency:** < 5ms RTT recommended for synchronous replication.
*   **Split-Brain:** Without a witness, 2-site Ceph risks split-brain if link fails. Witness ensures quorum.
**Recommendation:** Use Active-Passive DR (backup/restore) rather than Stretch Cluster for high latency sites to avoid performance penalties.

OP13 — **DHCP:** Dynamic Host Configuration Protocol.
**DORA:** Discover (Client broadcasts), Offer (Server proposes), Request (Client accepts), Acknowledge (Server confirms).
**Unavailable:** Client uses APIPA (169.254.x.x) and cannot reach external networks until lease renews or server returns.

OP14 — **Managed vs. Unmanaged Switch:**
*   **Unmanaged:** Plug-and-play, no config.
*   **Managed:** Configurable via CLI/Web.
**Features:** VLANs, QoS (prioritize VoIP), Port Security, SNMP Monitoring, STP (loop prevention). Essential for enterprise segmentation and troubleshooting.

OP15 — **NTP:** Network Time Protocol.
**Critical:** Kerberos authentication fails if clock skew > 5 mins. Log correlation and DB consistency rely on accurate time.
**Drift:** Causes authentication failures, certificate validation errors, and data inconsistency in distributed systems.

OP16 — **Physical vs. VM vs. Container:**
*   **Physical:** Bare metal hardware.
*   **VM:** Virtualized OS.
*   **Container:** Virtualized App.
**Bare Metal:** For high-performance computing, low-latency trading, or heavy I/O workloads where virtualization overhead is unacceptable.

OP17 — **UPS vs. Generator:**
*   **UPS:** Battery backup for instant power (seconds/minutes).
*   **Generator:** Fuel-powered for long-term power (hours/days).
**ATS:** Automatic Transfer Switch switches load from Utility to Generator when power fails.
**Need Both:** UPS bridges the gap between outage and generator startup.

OP18 — **Active-Passive vs. Active-Active:**
*   **Active-Passive:** One node handles traffic; other waits.
*   **Active-Active:** Both handle traffic.
**PostgreSQL HA:** Pacemaker/Corosync.
*   **Fencing:** STONITH to ensure failed node is powered off before failover.
*   **VIP:** Virtual IP floats to active node.
*   **Failover:** Automatic promotion of standby to primary upon detection of failure.

OP19 — **Backup Strategy:**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Define max data loss and max downtime.
*   **Types:** Full (baseline), Incremental (changes since last), Differential (changes since full).
*   **Security:** Immutable backups (WORM) prevent ransomware encryption.
*   **Test:** Regular restore drills.
*   **Backup vs. DR:** Backup is data recovery; DR is full system failover to another site.

OP20 — **802.1X:**
*   **Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
*   **EAP:** EAP-TLS (certificates, most secure) vs. PEAP (passwords).
*   **Dynamic VLAN:** RADIUS assigns VLAN based on user identity.
*   **Fail:** Port blocked or assigned to Guest VLAN.
*   **MAB:** MAC Authentication Bypass. Switch sends MAC address to RADIUS for devices without 802.1X (printers, IoT).
