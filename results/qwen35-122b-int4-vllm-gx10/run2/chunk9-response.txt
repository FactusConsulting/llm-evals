

SC1-A
**Root Cause:** The failure is caused by a conflict between the **Pod Security Standard (PSS) Restricted** profile and the container image's default user.
1.  **PSS Restricted:** Enforces `runAsNonRoot: true`. This requires the container to run as a non-root user (UID != 0).
2.  **Image Configuration:** The new base image (`cgr.dev/chainguard/static:latest`) defaults `USER` to `root` (UID 0).
3.  **Manifest Configuration:** The pod spec sets `securityContext.runAsNonRoot: true` but does **not** set `securityContext.runAsUser`.
4.  **Interaction:** Kubernetes attempts to run the container. The image specifies `root`. The PSS policy forbids `root`. Since `runAsUser` is not explicitly set to a non-root UID in the manifest, the admission controller or kubelet rejects the pod (or the container runtime fails to start it), resulting in `CrashLoopBackOff`.
5.  **Upgrade Impact:** The cluster upgrade enforced **Restricted** PSS where **Baseline** was previously used. Baseline allows `runAsNonRoot: true` without strictly enforcing a non-root UID if the image defaults to root, whereas Restricted strictly enforces non-root execution.

SC1-C
**Remediation Strategy:**
1.  **Immediate Fix:** Update the Kubernetes manifests to explicitly set `securityContext.runAsUser: 65534` (nobody) or a specific non-root UID matching the image. If the image must run as root, update the image Dockerfile to `USER 65534`.
2.  **Image Fix:** Modify the Dockerfile to include `USER 65534` (or specific UID) before the final stage. Rebuild and push.
3.  **CI Pipeline Gate:** Add a step in the CI pipeline using **OPA Gatekeeper** or **Kyverno** to scan manifests before merge. Policy: `deny if runAsNonRoot is true AND runAsUser is null`. Also, scan images for `USER root` using Trivy or similar.
4.  **Rollout:** Use a **Rolling Update** strategy. Update the image tag in the deployment manifest. Kubernetes will replace pods one by one. Since the fix is in the manifest/image, no downtime occurs if the new pods pass the PSS check. Monitor `kubectl rollout status` to ensure success.

SC2-A
**Stale Data & Replication:**
1.  **Replication Lag:** Cross-region read replicas use **asynchronous streaming replication**. WAL (Write-Ahead Log) shipping occurs over the network. During an outage, the primary stops sending WAL. The replica has only received WAL up to the last successful transmission.
2.  **Data Loss:** Promoting the replica means any transactions committed on the primary but not yet shipped to the replica are **lost**.
3.  **Quantification:** Check `pg_stat_replication` on the primary (before outage) for `sent_lsn`, `write_lsn`, `flush_lsn`, and `replay_lsn`. The difference between `sent_lsn` and `replay_lsn` indicates the lag in bytes/transactions.
4.  **Check:** Query `pg_current_wal_lsn()` on the new primary and compare it to the last known `sent_lsn` from the old primary logs to estimate the data loss window.

SC2-C
**Architecture Design:**
1.  **Connection Management:** Use **RDS Proxy** instead of PgBouncer. RDS Proxy handles failover automatically, manages connection pooling, and reduces latency spikes during failover.
2.  **DNS Failover:** Configure **Route53 Health Checks** on the primary endpoint. Set up a Failover Routing Policy. When primary fails, Route53 updates DNS TTL to point to the replica endpoint.
3.  **Application Logic:** Implement **retry logic with exponential backoff** and circuit breakers in the application to handle transient connection errors during DNS propagation.
4.  **RPO < 1s:** Standard RDS cross-region async replication cannot guarantee RPO < 1s consistently. **Recommend Aurora Global Database**. It uses storage-based replication with < 1s RPO and allows faster failover (1-2 mins) compared to RDS read replicas.
5.  **Why Aurora:** Aurora decouples compute from storage, allowing storage to replicate across regions independently of the compute instance, ensuring lower RPO and faster promotion.

SC3-A

1.  **Containment:** Do not delete the pod immediately. Scale the deployment to 0 to stop new pods, but keep the compromised pod running for forensics (or snapshot it).

3.  **Kill:** Once evidence is captured, delete the pod to stop the attacker.

SC4-A
**Top 5 Blockers:**
1.  **Sticky Sessions (F5):** K8s pods are ephemeral. Local memory sessions are lost on pod restart. **Solution:** Move session state to an external store (Redis) and disable sticky sessions.
2.  **Local NFS Mount:** Pods are stateless; local mounts don't persist across nodes. **Solution:** Use **ReadWriteMany (RWX)** Persistent Volumes (NFS CSI or EFS).
3.  **Oracle 19c:** On-prem DB is hard to migrate. **Solution:** Keep Oracle on-prem initially (via Service) or migrate to RDS/Aurora Oracle.
4.  **IBM MQ:** Mainframe integration requires specific network access. **Solution:** Use **IBM MQ Operator** on K8s or maintain a dedicated VM for MQ gateway with secure tunneling.
5.  **Stateful Monolith:** Hard to scale horizontally. **Solution:** Containerize as a **StatefulSet** with resource limits, but plan for microservices extraction (Strangler Fig).

SC4-C

SC5-C
**Architectural Solution:**
1.  **CQRS:** Separate the **Write Path** (Checkout) from the **Read/Reconciliation Path**.
2.  **Read Replica:** Run the CronJob against a **PostgreSQL Read Replica** to avoid locking the primary.
3.  **Bulkhead:** Use **Helm values** to set separate `resources.limits` for the CronJob vs. Deployment. Use **Kubernetes ResourceQuotas** to limit CronJob CPU/Memory.
4.  **Scheduling:** Move CronJob to off-peak hours (e.g., 03:00 UTC).
5.  **PDB:** Ensure `PodDisruptionBudget` on `inventory-service` prevents the CronJob from evicting serving pods during node pressure.

SC6-A
**Identity Layer:**
1.  **Machine Identity:** Deploy **SPIRE** (SPIFFE Runtime Environment) on all clusters (VMware, AWS, Azure).
2.  **Workload Identity:** SPIRE issues **SPIFFE IDs** (SVIDs) to workloads.
3.  **Federation:** Configure SPIRE **Trust Domains**. AWS workloads use **IAM Roles for Service Accounts (IRSA)** mapped to SPIFFE IDs. Azure uses **Managed Identities** mapped to SPIFFE IDs. On-prem uses **PKI** certificates signed by SPIRE.

SC6-C
**Connectivity Comparison:**
1.  **Direct Connect (DX):**
    *   **Pros:** High bandwidth (10G+), low latency, dedicated, cost-effective at scale.
    *   **Cons:** High setup cost, long lead time.
    *   **Zero Trust:** Fits well; private connection reduces attack surface.
    *   **Routing:** Requires BGP configuration on TGW.
2.  **VPN ECMP:**
    *   **Pros:** Faster setup, redundant tunnels.
    *   **Cons:** Limited bandwidth (1.25G per tunnel), CPU overhead on gateways.
    *   **Zero Trust:** IPsec encrypts traffic, but relies on public internet.
3.  **Tailscale/Netbird:**
    *   **Pros:** Easy mesh, NAT traversal, zero-config.
    *   **Cons:** Control plane dependency, bandwidth limits on free tiers.
    *   **Zero Trust:** Built on WireGuard, excellent identity integration.
    *   **Recommendation:** **Direct Connect** for production backbone (cost/performance), **Tailscale** for dev/admin access.

SC10-C
**Failover Orchestration:**
1.  **Detection:** **Prometheus Alertmanager** monitors site health (heartbeat). If > 30s no heartbeat, trigger failover.
2.  **DNS:** **GSLB** (Global Server Load Balancer) updates DNS TTL to point to Dallas VIP.
3.  **Patroni:** **Patroni** detects primary loss, promotes Dallas standby to primary automatically.
4.  **Redis:** **Sentinel** promotes new master.
5.  **RabbitMQ:** **Federation** links re-route queues to Dallas.
6.  **MinIO:** **Site Replication** ensures data catch-up.
7.  **ToFu:** Update state file to reflect Dallas as primary (manual or automated via CI).
8.  **Split-Brain:** Use **Quorum** (etcd) to ensure only one primary exists. If Chicago recovers, it becomes a **Standby** automatically.
9.  **Failback:** Once Chicago is stable, re-sync data (Patroni sync), then switch DNS back.
