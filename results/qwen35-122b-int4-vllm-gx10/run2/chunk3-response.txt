

T1 — **Difference between `tofu plan` and `tofu apply`**
`tofu plan` generates an execution plan, showing what actions OpenTofu will take (create, update, destroy) without making changes. It is used for validation and review. `tofu apply` executes the plan, making the actual changes to the infrastructure to match the configuration. `apply` requires confirmation unless `-auto-approve` is used.

T2 — **State in OpenTofu and importance of remote state**
State is a JSON file (`terraform.tfstate`) that maps real-world resources to your configuration, tracks metadata, and stores outputs. It is the source of truth for OpenTofu. **Remote state** is critical for collaboration (preventing concurrent edits), security (storing secrets in backend storage, not local files), and enabling module composition (sharing outputs between teams/projects).

T3 — **Difference between `count` and `for_each`**
`count` creates resources based on an integer index (0, 1, 2...). `for_each` creates resources based on a map or set of strings (key-value pairs). **`for_each` is preferred** when resources need stable identities (keys) that don't shift if an item is removed from the middle of a list. It prevents unintended recreation of resources when the collection size changes.

T4 — **Manual changes outside OpenTofu (Drift)**
If you modify a resource manually (e.g., in the cloud console), OpenTofu detects this as **drift** during the next `tofu plan`. It will show the resource as "needs update" to match the configuration. To handle this, run `tofu apply` to revert the change to match code, or run `tofu import`/`refresh` if the manual change should be adopted into the state.

T5 — **Snippet: 3 VMs using `for_each`**
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  
  triggers = {
    name = each.key
  }
}
```

T6 — **`terraform_remote_state` vs. Outputs between root modules**
`terraform_remote_state` is a data source used to read outputs from a *different* state file (different root module). Direct outputs only work within the same module. **Recommended alternative:** Structure code so one root module calls the other as a child module. This keeps state in one place, simplifies dependency management, and avoids the complexity of managing multiple state files and remote state data sources.

T7 — **RKE2 Cluster Output Dependency Issue**
**Why:** Outputs are evaluated after resources are created. If a `null_resource` uses a provisioner (like `remote-exec`) to generate a kubeconfig, the output is only available *after* the provisioner runs. If another resource tries to read this output in the same apply, it may fail if dependencies aren't explicit.
**Fix:** Ensure the dependent resource has an explicit `depends_on` referencing the `null_resource`. Alternatively, avoid provisioners for critical data; use cloud-init or cloud APIs to generate the config directly as a resource attribute.

T8 — **`tofu import` vs. Import Block (1.5+)**
`tofu import` is a CLI command to map existing infrastructure to state. **Limitations:** It requires manual ID entry and doesn't generate code. The **`import` block** (HCL) allows defining imports directly in configuration. **Improvement:** It makes imports reproducible, version-controlled, and allows OpenTofu to automatically generate the resource configuration block during import (with `-generate-config-out`).

T9 — **Variable vs. Output**
A **variable** (`variable`) is an input parameter passed into a module or root configuration to customize behavior. An **output** (`output`) is a value exposed from a module or root configuration for use by other modules or to display to the user. Variables configure; outputs report.

T10 — **Provider and `tofu init`**
A **provider** is a plugin that interacts with an API (e.g., AWS, Azure). It translates HCL into API calls. If you run `tofu plan` without `tofu init`, it fails because the provider plugins are not downloaded and the backend is not configured. `init` initializes the working directory, downloads providers, and configures the backend.

T11 — **`.terraform.lock.hcl`**
This file records the exact versions of providers and modules used. **Committing it** ensures all team members and CI/CD pipelines use identical provider versions, preventing unexpected behavior or breaking changes due to automatic provider upgrades.

T12 — **`tofu destroy` and Targeting**
`tofu destroy` removes all resources managed by the current state. To target a single resource for destruction, use the `-target` flag: `tofu destroy -target=aws_instance.web`. **Warning:** This leaves orphaned resources if dependencies exist; use with caution.

T13 — **Data Source**
A **data source** (`data`) reads information from existing infrastructure without managing it. **Example:** Use `data "aws_ami" "latest"` to fetch the latest Ubuntu AMI ID instead of creating a new AMI resource. Use data sources for read-only lookups; use managed resources for creation/modification.

T14 — **Locals vs. Variables**
**Variables** are inputs passed from outside the module. **Locals** are internal variables calculated within the module. Use **locals** for derived values, complex expressions, or constants that don't need to be configurable by the caller. Use variables when the value must be customizable by the user.

T15 — **Lifecycle Block Options**
*   `create_before_destroy`: Creates a new resource before destroying the old one (useful for immutable infrastructure like load balancers).
*   `prevent_destroy`: Prevents the resource from being destroyed (useful for critical data stores).
*   `ignore_changes`: Ignores specific attribute changes in the plan (useful for attributes managed externally, like `tags` updated by a script).

T16 — **`moved` Block**
A `moved` block tells OpenTofu that a resource has changed address (e.g., moved from one module to another) without changing its identity. It updates the state file to point to the new address, preventing OpenTofu from destroying the old resource and creating a new one during refactoring.

T17 — **Dependency Graph & `depends_on`**
OpenTofu builds a graph based on references (implicit dependencies). **Explicit dependencies** use `depends_on`. `depends_on` forces ordering but reduces parallelism because it serializes resource creation. Use it sparingly only when implicit references are insufficient (e.g., external dependencies not tracked in state).

T18 — **Reducing Plan Time (200+ resources)**
1.  **State Isolation:** Split state into smaller backends/modules (reduces state size).
2.  **Parallelism:** Increase `-parallelism` flag (utilizes more CPU, but risks API rate limits).
3.  **Backend Optimization:** Use a high-performance backend (e.g., S3 + DynamoDB) with caching.
4.  **Targeted Planning:** Use `-target` to plan only changed sections (skips full graph evaluation).
*Tradeoffs:* Splitting state increases complexity; higher parallelism risks throttling; targeting can leave orphaned resources if dependencies aren't managed.

T19 — **State Locking & Breaking Locks**
OpenTofu locks state during operations to prevent corruption. If a CI pipeline crashes, the lock persists. **Manual Break:** Use the backend's CLI (e.g., `aws dynamodb delete-item` for DynamoDB) or `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually writing, breaking the lock can corrupt the state file. Verify no other process is running first.

T20 — **Migrate Local to S3 Backend**
1.  Configure the new S3 backend in `backend` block.
2.  Run `tofu init -migrate-state`.
3.  OpenTofu prompts to migrate; confirm.
4.  It copies local state to S3 and updates the local `.terraform` directory.
5.  **Verify:** Run `tofu plan` to ensure state is read correctly from S3. Check S3 bucket for the state file.

A1 — **Playbook, Role, Task**
*   **Task:** A single action (e.g., install package).
*   **Playbook:** A YAML file containing a list of plays (tasks executed on hosts).
*   **Role:** A reusable collection of tasks, variables, and handlers organized in a directory structure. Roles promote modularity; playbooks orchestrate roles.

A2 — **`ansible_facts` and OS Family**
`ansible_facts` is a dictionary of system information gathered by the `setup` module. Access OS family via `ansible_os_family`. Example: `{{ ansible_os_family }}` returns "RedHat" or "Debian".

A3 — **`command`, `shell`, `raw`**
*   **`command`:** Runs a command without shell features (no pipes, variables). Safest, idempotent-friendly.
*   **`shell`:** Runs through a shell (supports pipes, variables). Use when shell features are needed.
*   **`raw`:** Executes commands without Python on the target. Use for bootstrapping or when Python is unavailable.

A4 — **Idempotency**
Idempotency means running a task multiple times yields the same result without side effects.
*   **Idempotent:** `apt: name=htop state=present` (Installs if missing, does nothing if present).
*   **Not Idempotent:** `shell: echo "log" >> /var/log/app.log` (Appends every time, changing state).

A5 — **Task: Install htop (Debian/RHEL)**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```

A6 — **Variable Precedence (Low to High)**
1.  Role defaults
2.  Inventory file vars
3.  Play vars
4.  `host_vars`
5.  `group_vars`
6.  Role vars
7.  `extra_vars` (command line `-e`)
*Note:* `set_fact` overrides most but is lower than `extra_vars`.

A7 — **RKE2 Agent Deployment (Serial)**
Use `serial` in the play to limit concurrency.
```yaml
- hosts: rke2_nodes
  serial: 3
  tasks:
    - name: Wait for previous nodes
      wait_for: ... # Custom logic or use a lock file
    - name: Install RKE2
      ...
```
Group the first 3 nodes in inventory (e.g., `[rke2_first]`) and run a separate play with `serial: 3` targeting that group first, then the rest.

A8 — **`ansible-vault` Single Variable**
`ansible-vault` encrypts entire files. To encrypt a single variable, use `ansible-vault encrypt_string "secret_value"`. Copy the output (ciphertext) into the vars file as the value. The file remains plaintext, but the specific value is encrypted.

A9 — **Inventory File**
A list of hosts and groups.
*   **Static:** A text file (INI or YAML) manually maintained.
*   **Dynamic:** A script that queries an API (e.g., AWS EC2, VMware) to generate the inventory at runtime.

A10 — **Ad-hoc Disk Space Command**
```bash
ansible webservers -m shell -a "df -h"
```

A11 — **Handlers**
Handlers are tasks that run only if notified (changed state). They differ from regular tasks because they execute at the end of the play, not immediately. Triggered via `notify: handler_name` in a task.

A12 — **`ansible.cfg` Settings**
Used to configure Ansible behavior. Common settings:
1.  `inventory`: Path to inventory file.
2.  `remote_user`: Default SSH user.
3.  `host_key_checking`: Disable SSH host key checking for automation.

A13 — **`register` Keyword**
Captures the output of a task into a variable.
```yaml
- name: Check status
  command: /bin/true
  register: result
- name: Print output
  debug: msg="{{ result.stdout }}"
```

A14 — **`include_tasks` vs `import_tasks`**
*   **`import_tasks`:** Static import. Processed at parse time. Conditions apply to the import itself.
*   **`include_tasks`:** Dynamic import. Processed at runtime. Conditions apply to the execution of the included tasks.
*   **Use:** `import` for static structure; `include` for conditional logic or loops.

A15 — **Ansible Galaxy & `requirements.yml`**
Galaxy is a repository for roles and collections. `requirements.yml` lists dependencies.
```yaml
collections:
  - name: community.general
roles:
  - name: geerlingguy.nginx
```
Install via `ansible-galaxy install -r requirements.yml`.

A16 — **Connection Plugins**
*   **`ssh`:** Standard SSH connection (default).
*   **`local`:** Runs tasks on the control node itself.
*   **`network_cli`:** Used for network devices (Cisco, Juniper) via SSH/Telnet with specific CLI parsing.

A17 — **`delegate_to` and `run_once`**
*   **`delegate_to`:** Runs a task on a different host (e.g., localhost) while iterating over others.
*   **`run_once`:** Runs a task only once on the first host.
*   **Example:** Gather facts on all hosts, then run a task on `localhost` to aggregate data.
```yaml
- name: Aggregate
  delegate_to: localhost
  run_once: true
  command: ./aggregate.sh
```

A18 — **Performance (500 hosts)**
1.  **Forks:** Increase `forks` (default 5) to 50+ in `ansible.cfg`.
2.  **Pipelining:** Enable `pipelining = True` to reduce SSH connections.
3.  **Fact Caching:** Use `fact_caching = jsonfile` to avoid re-gathering facts.
4.  **Mitogen:** Use the `ansible-mitogen` plugin to optimize SSH multiplexing.
*Tradeoffs:* Higher forks consume more control node RAM; Mitogen requires installation and compatibility checks.

A19 — **Jinja2 Templating**
*   `{{ }}`: Print variables/expressions.
*   `{% %}`: Control structures (loops, if).
*   `{# #}`: Comments.
**Snippet:**
```jinja2
upstream backend {
{% for server in servers %}
  server {{ server.ip }}:{{ server.port }}; {# Health check comment #}
{% endfor %}
}
```

A20 — **Zero-Downtime Rolling Deployment**
1.  **Serial:** Set `serial: 20%` to update batches.
2.  **Pre-task:** Notify Load Balancer to remove host from pool (`uri` module).
3.  **Deploy:** Update app code.
4.  **Health Check:** `uri` module to check `/health` endpoint.
5.  **Post-task:** Notify Load Balancer to add host back.
6.  **Rollback:** Use `block/rescue`. If health check fails in `block`, `rescue` reverts the deployment and notifies LB to keep host out.
