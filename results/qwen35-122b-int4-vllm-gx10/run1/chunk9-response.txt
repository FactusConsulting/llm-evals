

SC1-A
**Root Cause:** The failure is caused by a conflict between the **Pod Security Standard (PSS) Restricted** profile and the container image's default user.
1.  **PSS Restricted:** Enforces `runAsNonRoot: true`. This requires the container to run as a non-root user (UID != 0).
2.  **Image Configuration:** The new base image (`cgr.dev/chainguard/static:latest`) sets `USER root` (UID 0) in the Dockerfile.
3.  **Pod Spec:** The pod spec sets `securityContext.runAsNonRoot: true` but does **not** set `securityContext.runAsUser`.
4.  **Kubernetes Behavior:** When `runAsNonRoot: true` is set without `runAsUser`, Kubernetes attempts to run the container as the user defined in the image (`root`). Since `root` violates `runAsNonRoot`, the kubelet rejects the pod or the container runtime fails to start it, resulting in `CrashLoopBackOff`.
5.  **Upgrade Impact:** The cluster upgrade enforced **Restricted** PSS where **Baseline** was previously used. Baseline allows running as root (mostly), whereas Restricted strictly forbids it.

SC1-C
**Remediation Strategy:**
1.  **Immediate Fix:** Update the Kubernetes manifests to explicitly set `securityContext.runAsUser: 1000` (or a non-root UID) and `runAsGroup: 1000`.
2.  **Image Fix:** Modify the Dockerfile to include `USER 1000` before the final stage. Rebuild and push the image.
3.  **CI Pipeline Gate:** Add a step in the CI pipeline using `checkov` or `kube-score` to scan manifests for `runAsNonRoot: true` without `runAsUser`. Add a Trivy scan to verify the image does not run as root.
4.  **Rollout:** Use a **Blue/Green** deployment strategy. Deploy the fixed manifests to a new deployment (Green) with the same service selector. Verify health checks pass. Switch the Service selector to the Green deployment. Delete the old deployment (Blue). This ensures zero downtime.

SC2-A
**Stale Data & Replication Lag:**
1.  **Cause:** Cross-region read replicas in RDS use **asynchronous streaming replication**. There is inherent network latency (85ms) and potential network congestion.
2.  **Implication:** When the primary fails, the replica promotes. Any transactions committed on the primary but not yet shipped/applied to the replica are lost. This is the **Recovery Point Objective (RPO)** gap.
3.  **WAL Shipping:** WAL segments are shipped via TCP. If the primary crashes before shipping the last segment, that data is unrecoverable from the replica.
4.  **Quantification:** Check `pg_stat_replication` on the primary before failure. Look at `sent_lsn`, `write_lsn`, and `replay_lsn`. The difference between `sent_lsn` and `replay_lsn` indicates the lag in bytes/transactions.

SC2-B
**Terraform Operations:**
1.  **Import:** Import the promoted replica into state using its new ARN.
    ```bash
    terraform import aws_db_instance.new_primary <new-replica-arn>
    ```
2.  **Update Config:** Update the Terraform code to reference the new ARN in dependent resources (Security Groups, Route53).
3.  **Detach Old:** Modify the old instance resource in Terraform to `deletion_policy = "Retain"` or remove it from state without destroying.
    ```bash
    terraform state rm aws_db_instance.old_primary
    ```
4.  **Apply:** Run `terraform apply`. Terraform will update dependent resources to point to the new primary without destroying the new primary (since it's now in state) or the old one (since it's removed from state).

SC2-C
**Architecture Design:**
1.  **Connection Management:** Use **RDS Proxy** instead of PgBouncer. RDS Proxy handles failover transparently, reducing connection storms and managing pooling centrally.
2.  **DNS Failover:** Configure **Route53 Health Checks** on the primary endpoint. Set up a Failover Routing Policy. When primary health check fails, Route53 updates DNS to point to the replica's endpoint.
3.  **Application Logic:** Implement **retry logic with exponential backoff** in the application to handle transient connection errors during failover.
4.  **RPO < 1s:** Use **Aurora Global Database**. It replicates storage across regions with < 1s latency and supports planned/unplanned failover with minimal data loss. Standard RDS cross-region replication is asynchronous and cannot guarantee < 1s RPO consistently.
5.  **Recommendation:** **Aurora Global Database** is recommended over standard RDS for this requirement due to storage-level replication and faster failover times.

SC3-A
**Incident Response:**
1.  **Containment:** Do not delete pods immediately. Scale the deployment to 0 replicas to stop new traffic, but keep the compromised pod running for forensics.
2.  **Forensics Commands:**

    *   **Memory Dump:** `kubectl exec -it <pod> -- gdb -p <pid>` (if debug symbols available)
3.  **Kill:** After evidence capture, delete the pod to stop the attacker.

SC3-C
**Hardened CI/CD:**
1.  **Image Signing:** Use **Cosign** to sign images in CI. `cosign sign --key cosign.key <image>`.
2.  **Admission Control:** Deploy **Kyverno** or **OPA Gatekeeper** in the cluster. Create a policy that rejects any pod image not signed by the trusted key.
3.  **Pinning:** Pin base images by **digest** (e.g., `node@sha256:...`) in Dockerfiles, not tags.
4.  **SBOM:** Generate Software Bill of Materials using **Syft** in CI and attach to the image.
5.  **Notary v2:** Use Notary v2 for OCI artifact signing and verification, integrating with container registries to enforce trust boundaries.

SC4-A
**Top 5 Blockers:**
1.  **Sticky Sessions:** F5 sticky sessions rely on IP/Session ID. K8s pods are ephemeral. **Solution:** Use K8s `sessionAffinity: ClientIP` or externalize session state to Redis.
2.  **Local NFS Mount:** `/data/uploads` is local to bare metal. **Solution:** Use a **ReadWriteMany (RWX)** PersistentVolume (e.g., EFS or NFS CSI).
3.  **Oracle 19c:** On-prem DB is hard to migrate. **Solution:** Keep Oracle on-prem initially (external service) or migrate to RDS Oracle/Aurora.
4.  **IBM MQ:** Mainframe integration is network-bound. **Solution:** Use **IBM MQ Cloud** or expose MQ via a secure tunnel/Service Mesh.
5.  **Stateful Monolith:** Hard to scale horizontally. **Solution:** Refactor into microservices (Strangler Fig) or use StatefulSets with careful resource management.

SC4-C
**Migration Plan (Strangler Fig):**
1.  **Phase 1 (Read-Only):** Deploy read-only replicas of the monolith to K8s. Route 10% of read traffic via F5 to K8s. **Metric:** Error rate < 0.1%.
2.  **Phase 2 (Write Traffic):** Migrate write traffic for non-critical features (e.g., profile updates). Use F5 to split traffic. **Metric:** Transaction success rate > 99.9%.
3.  **Phase 3 (Cutover):** Route 100% traffic to K8s. Decommission F5 rules. **Rollback:** Revert F5 routing to legacy servers immediately.
4.  **IBM MQ:** Use a sidecar or dedicated pod to handle MQ connections, ensuring the K8s app doesn't need direct mainframe access.
5.  **Zero Downtime:** Use F5 to manage traffic splitting. Database changes are backward compatible (add columns, don't drop).

SC5-C
**Architectural Solution:**
1.  **CQRS:** Separate the reconciliation job (Write path) from the checkout API (Read path).
2.  **Read Replica:** Point the reconciliation CronJob to a **Read Replica** of the database to avoid locking the primary.
3.  **Bulkhead:** Use separate database connection pools for the API and the CronJob.
4.  **Scheduling:** Move CronJob to off-peak hours (e.g., 02:00 UTC).
5.  **K8s Controls:** Set `resources.limits` on the CronJob to prevent CPU starvation. Use `PodDisruptionBudget` on the serving pods to ensure they are not evicted during node maintenance.

SC6-C
**Connectivity Comparison:**
1.  **Direct Connect (DX):**
    *   *Pros:* High bandwidth (10G+), low latency, dedicated.
    *   *Cons:* High cost, long setup time.
    *   *Zero Trust:* Fits well; private connection reduces attack surface.
2.  **VPN ECMP:**
    *   *Pros:* Lower cost, faster setup.
    *   *Cons:* Limited bandwidth (1.25G per tunnel), encryption overhead.
    *   *Zero Trust:* Acceptable, but shared internet path.
3.  **Tailscale/Netbird:**
    *   *Pros:* Easy mesh, NAT traversal, built-in identity.
    *   *Cons:* Dependent on relay servers (unless DERP), bandwidth limits.
    *   *Zero Trust:* Excellent identity integration, but adds a third party.
4.  **Recommendation:** Upgrade to **Direct Connect** for production traffic due to bandwidth needs. Use Tailscale for management/ops access.

SC10-C
**Failover Orchestration:**
1.  **Detection:** **Prometheus Alertmanager** monitors site health (ping, DB lag). If > 5 mins down, trigger failover.
2.  **DNS:** **Route53 Health Checks** detect failure. Update DNS TTL to low (60s) prior to failover. Switch record to Dallas IP.
3.  **Patroni:** Patroni DCS (etcd) detects primary loss. **Standby in Dallas** promotes automatically (if `synchronous_mode` is off or quorum lost).
4.  **Redis:** **Sentinel** detects master down. Promotes slave in Dallas.
5.  **RabbitMQ:** **Federation** links queues. Dallas node takes over publishing.
6.  **MinIO:** **Site Replication** ensures Dallas has latest data.
7.  **Terraform:** Update state file to reflect Dallas as primary (manual or automated via CI).
8.  **Split-Brain:** Use **Quorum** in etcd/Patroni. Only one node can be leader. If network partition, the minority partition becomes read-only.
9.  **Failback:** Once Chicago recovers, sync data from Dallas to Chicago. Switch DNS back. Re-establish replication.
