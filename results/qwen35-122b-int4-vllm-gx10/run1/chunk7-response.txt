

AA1 — **Monolith vs. Microservices:** A monolith is a single deployable unit where all components are tightly coupled. Microservices decompose the application into loosely coupled, independently deployable services.
**3 Microservice Problems:**
1.  **Distributed Transactions:** Maintaining data consistency across services requires complex patterns (Saga) instead of local ACID transactions.
2.  **Network Latency & Reliability:** Inter-service communication introduces network overhead and failure modes (timeouts, partial failures) not present in in-process calls.
3.  **Operational Complexity:** Requires orchestration (Kubernetes), service discovery, centralized logging, and distributed tracing infrastructure.

AA2 — **Sync vs. Async:** Synchronous communication blocks the caller until a response is received (e.g., HTTP/REST, gRPC). Asynchronous communication allows the caller to continue without waiting for a response (e.g., AMQP/RabbitMQ, Kafka).
**Examples:** Sync: REST API. Async: RabbitMQ.

AA3 — **API Gateway vs. Reverse Proxy:** A reverse proxy routes traffic based on IP/Port/Path. An API Gateway adds application-layer logic: authentication, rate limiting, request transformation, and aggregation.
**Replacement:** An API Gateway can replace a reverse proxy functionally, but it introduces more overhead. For simple internal routing, a lightweight proxy (Nginx) is often preferred over a heavy gateway (Kong/Apigee).

AA4 — **Saga Pattern:** A sequence of local transactions where each updates data within a single service. If a step fails, compensating transactions undo previous changes.
**Choreography:** Services emit events to trigger the next step (decentralized). Good for simple flows.
**Orchestration:** A central coordinator tells services what to do (centralized). Good for complex flows requiring visibility and control.

AA5 — **CQRS:** Separates read (Query) and write (Command) models. Writes update a write model; reads query an optimized read model.
**Event Sourcing Pairing:** Events store state changes as a log. CQRS + ES allows rebuilding read models from events.
**Problem Solved:** Traditional CRUD struggles when read and write scaling requirements differ or when complex audit trails/history are needed.

AA6 — **Circuit Breaker:** Prevents cascading failures by stopping requests to a failing service.
**States:** Closed (normal), Open (failing, fail fast), Half-Open (testing recovery).
**Differs from Retry:** Retry assumes transient failure; Circuit Breaker assumes persistent failure.
**Together:** Use retry for transient errors within the Closed state; use Circuit Breaker to stop retrying when the error rate is too high.

AA7 — **Multi-Tenant Isolation:**
1.  **Shared DB, Shared Schema:** Lowest cost, highest risk. Noisy neighbors affect all. Hard to isolate data.
2.  **Shared DB, Separate Schema:** Balanced. Easier backup/restore per tenant. Moderate noisy-neighbor risk.
3.  **Separate DB:** Highest security/isolation. Highest cost/ops complexity. Best for enterprise compliance.
**Trade-off:** Choose #1 for SaaS startups, #3 for regulated industries (HIPAA/Finance).

AA8 — **Eventual vs. Strong Consistency:** Eventual means data converges over time. Strong means all nodes see the same data immediately.
**Inventory Architecture:** Requires **Strong Consistency**.
**Stack:** Relational DB (PostgreSQL) with row-level locking or Optimistic Concurrency Control.
**Pattern:** Use a distributed lock manager (Redis Redlock) or database transactions to reserve inventory before payment. Avoid eventual consistency for stock counts to prevent overselling.

AA9 — **Sidecar Proxy:** A helper process deployed alongside an application container (e.g., Envoy in Istio).
**Envoy/Istio:** Envoy handles traffic (Data Plane); Istiod manages configuration/policies (Control Plane).
**mTLS:** Encrypts traffic between services automatically. Solves the problem of managing certificates and auth in every application codebase; ensures zero-trust network security.

AA10 — **Strangler Fig:** Incrementally migrate functionality from a legacy system to a new system by routing traffic to the new system over time.
**Strategy:** Place a reverse proxy (Nginx/API Gateway) in front of the .NET Monolith. Route specific paths (e.g., `/api/v2/*`) to new .NET 8 microservices. Gradually move more paths until the monolith is "strangled" and can be decommissioned.

AA11 — **12-Factor App:** Methodology for building SaaS apps.
**6 Factors:**
1.  **Codebase:** One codebase tracked in VCS.
2.  **Dependencies:** Explicitly declare and isolate dependencies.
3.  **Config:** Store config in environment variables.
4.  **Backing Services:** Treat services (DB, Queue) as attached resources.
5.  **Build/Release/Run:** Strictly separate build and run stages.
6.  **Processes:** Run app as one or more stateless processes.
**Why:** Ensures portability, scalability, and parity between dev/prod.

AA12 — **Event-Driven (Kafka) vs. Request-Driven (REST):**
*   **Coupling:** Kafka (Loose), REST (Tight).
*   **Scalability:** Kafka (High throughput, async), REST (Limited by request/response).
*   **Debugging:** Kafka (Harder, need log replay), REST (Easier, request logs).
*   **Ordering:** Kafka (Partition-level), REST (None).
*   **Failure:** Kafka (Retry/Dead Letter), REST (Immediate error).
**Choice:** Use REST for user-facing APIs requiring immediate feedback. Use Kafka for background processing, audit trails, and decoupling heavy workloads.

AA13 — **Load Balancer:** Distributes network traffic across servers.
**L4 (Transport):** Routes based on IP/Port (TCP/UDP). Fast, unaware of content.
**L7 (Application):** Routes based on HTTP headers/URL. Slower, content-aware.
**Use Case:** L7 required for path-based routing (e.g., `/api` to backend, `/static` to CDN) or SSL termination.

AA14 — **Message Queue vs. Log Broker:**
*   **Queue (RabbitMQ):** Message deleted after consumption. Point-to-point. Good for task distribution.
*   **Log (Kafka):** Message persisted for retention period. Pub/Sub. Good for event streaming and replay.
**Pick:** Queue for work queues (emails, jobs). Log for event sourcing, analytics, or when multiple consumers need the same data.

AA15 — **Container vs. VM:** A VM virtualizes hardware (includes OS kernel). A Container virtualizes the OS (shares host kernel).
**Difference:** Containers are lighter, faster to start, and use fewer resources.
**Popularity:** Ideal for microservices due to rapid scaling, portability, and density.

AA16 — **Stateless vs. Stateful:**
*   **Stateless:** No client data stored on server (e.g., Web Server).
*   **Stateful:** Stores session/data on server (e.g., Database).
**Scaling:** Stateless services can be scaled horizontally by adding nodes behind a load balancer without session affinity. Stateful services require complex data replication/sharding.

AA17 — **ORM:** Maps objects to database tables (e.g., Hibernate/Java, Entity Framework/.NET).
**Trade-offs:**
*   **Pros:** Productivity, type safety, abstraction.
*   **Cons:** Performance overhead, N+1 query problems, difficulty optimizing complex SQL.
**Decision:** Use ORM for CRUD; use raw SQL for complex reporting or high-performance critical paths.

AA18 — **Bulkhead Pattern:** Isolates resources (thread pools, connections) for different services.
**Relation:** Prevents a failure in one service from exhausting resources for others (cascading failure).
**Implementation:** Assign separate thread pools per downstream service call. If Service A's pool is exhausted, Service B's calls still succeed.

AA19 — **OT vs. CRDT:**
*   **OT:** Server-centric, transforms operations to maintain consistency. Complex to implement.
*   **CRDT:** Math-based data structures that converge automatically without coordination.
**Choice:** **CRDTs**. They support offline editing naturally (merge on reconnect) and provide strong eventual consistency without a central server bottleneck.

AA20 — **Distributed Tracing Challenges:**
*   **Context Propagation:** Use W3C Trace Context headers (`traceparent`) across HTTP/gRPC.
*   **Sampling:** Head-based (decide at entry) vs. Tail-based (decide after seeing errors). Tail-based is better for debugging.
*   **Async Messaging:** Inject trace context into Kafka message headers. Consumers must extract and continue the span.
*   **Storage:** Use Jaeger/Tempo. Ensure high cardinality tags are avoided to prevent storage explosion.

OP1 — **Hypervisor Type 1 vs. 2:**
*   **Type 1 (Bare-metal):** Runs directly on hardware. Examples: VMware ESXi, Microsoft Hyper-V.
*   **Type 2 (Hosted):** Runs on top of an OS. Examples: Oracle VirtualBox, VMware Workstation.
**Use:** Type 1 for production servers; Type 2 for development/testing.

OP2 — **SAN vs. NAS:**
*   **SAN (Storage Area Network):** Block-level storage. Protocols: Fibre Channel, iSCSI. Use for databases requiring low latency.
*   **NAS (Network Attached Storage):** File-level storage. Protocols: NFS, SMB/CIFS. Use for file shares and backups.

OP3 — **3-Tier vs. Leaf-Spine:**
*   **3-Tier:** Core, Distribution, Access. High latency for East-West traffic (server-to-server).
*   **Leaf-Spine:** Every leaf connects to every spine. Constant 2-hop latency.
**Why Leaf-Spine:** Preferred in modern DCs for cloud-native workloads requiring high East-West bandwidth and predictable latency.

OP4 — **Proxmox HA Architecture:**
*   **Nodes:** Minimum 3 for quorum (avoid split-brain).
*   **Storage:** Ceph (integrated) or iSCSI/NFS.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) to prevent data corruption.
*   **Failure:** If a node fails, HA manager restarts VMs on remaining nodes after verifying the failed node is down.

OP5 — **VLAN Trunking:** Carries multiple VLANs over a single link.
**802.1Q:** Adds a 4-byte tag to Ethernet frames with VLAN ID.
**Linux Config:** Create sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`. Assign IPs to `eth0.10`, `eth0.20`, etc.

OP6 — **RAID Levels:**
*   **RAID 1:** Mirror (50% capacity).
*   **RAID 5:** Parity (N-1 capacity).
*   **RAID 6:** Double Parity (N-2 capacity).
*   **RAID 10:** Mirror + Stripe (50% capacity, high perf).
*   **RAID Z2:** ZFS equivalent of RAID 6.
**Choice:** **RAID 10** for 6 drives DB server. Better write performance and rebuild times than RAID 5/6, despite lower capacity.

OP7 — **DNS Architecture:**
*   **Internal:** AD-integrated DNS for internal resolution.
*   **External:** Authoritative servers in DMZ (e.g., Route53, Bind).
*   **Split-Horizon:** Internal clients resolve `corp.com` to private IPs; external to public.
*   **Forwarders:** Internal DNS forwards external queries to ISP/Google.
*   **Laptop Move:** DHCP updates DNS records (DDNS). VPN clients use internal DNS forwarders via split-tunnel.

OP8 — **PKI Chain:** Root CA (Offline) -> Subordinate CA (Issuing) -> End Entity.
*   **Revocation:** CRL (list) vs. OCSP (real-time check).
*   **Templates:** Define cert usage (Server Auth, Client Auth).
*   **Compromise:** Sub CA compromised = Revoke Sub CA cert, reissue end-entity certs. Root CA compromised = Revoke Root, rebuild entire PKI infrastructure.

OP9 — **WAN Consolidation:**
*   **MPLS:** Reliable, expensive, rigid.
*   **IPsec:** Secure, cheap, variable latency.
*   **SD-WAN:** Intelligent path selection, cost-effective, manages multiple links.
*   **WireGuard:** Simple, fast, but lacks enterprise management features.
**Recommendation:** **SD-WAN**. Balances cost, manages VoIP prioritization (QoS), and provides reliability over internet links.

OP10 — **iDRAC/iLO/IPMI:** Out-of-band (OOB) management interfaces for hardware control (power, console) independent of OS.
**Criticality:** Allows recovery when OS is crashed or network is down.
**Risk:** Exposed to internet = Remote Code Execution (RCE) risk. Must be isolated on management VLAN.

OP11 — **LVM vs. ZFS:**
*   **LVM:** Logical Volume Manager (Linux). Thin provisioning allows overcommit. Snapshots are copy-on-write (thin).
*   **ZFS:** Filesystem + Volume Manager. Native snapshots (instant, space-efficient).
**Use:** LVM for general Linux VMs. ZFS for data integrity, compression, and advanced snapshot management.

OP12 — **Stretch Cluster/DR:**
*   **Design:** 2 sites + 3rd witness (tiebreaker).
*   **Ceph:** CRUSH rules to prefer local data.
*   **Latency:** <5ms RTT required for synchronous replication.
*   **Split-Brain:** Without a tiebreaker, both sites may think they are primary, causing data corruption.
**Verdict:** 2-site Ceph is risky without a witness. Prefer async replication for DR over stretch clusters for long distances.

OP13 — **DHCP DORA:** Discover, Offer, Request, Acknowledge.
**Unavailable Server:** Client uses APIPA (169.254.x.x) if lease expires and no server responds. Connectivity limited to local subnet.

OP14 — **Managed vs. Unmanaged Switch:**
*   **Unmanaged:** Plug-and-play, no config.
*   **Managed:** Configurable VLANs, QoS, SNMP monitoring, Port Security.
**Enterprise:** Managed required for segmentation, troubleshooting, and traffic prioritization.

OP15 — **NTP:** Network Time Protocol.
**Criticality:** Logs correlation, Kerberos auth (5 min skew limit), DB consistency, certificate validation.
**Drift:** Causes authentication failures, data ordering issues, and security vulnerabilities.

OP16 — **Physical vs. VM vs. Container:**
*   **Physical:** Bare metal hardware.
*   **VM:** Virtualized OS.
*   **Container:** Virtualized App.
**Bare Metal:** High-performance DBs, HPC, or workloads requiring direct hardware access (GPU passthrough) where virtualization overhead is unacceptable.

OP17 — **UPS vs. Generator:**
*   **UPS:** Battery backup for immediate power loss (seconds/minutes).
*   **Generator:** Fuel-powered for long-term outage (hours/days).
**ATS:** Automatically switches load from utility to generator when power fails.
**Need Both:** UPS bridges the gap until generator starts.

OP18 — **Active-Passive vs. Active-Active:**
*   **Active-Passive:** One node handles traffic; other waits.
*   **Active-Active:** Both handle traffic.
**PostgreSQL HA:** Pacemaker/Corosync.
*   **Fencing:** STONITH to ensure failed node is powered off before failover.
*   **VIP:** Virtual IP floats to active node.
*   **Failover:** Automatic promotion of standby to primary upon detection of failure.

OP19 — **Backup Strategy:**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Define max data loss and max downtime.
*   **Types:** Full (baseline), Incremental (changes since last).
*   **Immutable:** WORM storage to prevent ransomware encryption of backups.
*   **Backup vs. DR:** Backup restores files; DR restores entire infrastructure/service availability.
*   **Testing:** Regular restore drills are mandatory.

OP20 — **802.1X:**
*   **Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
*   **EAP:** EAP-TLS (certs, most secure) vs. PEAP (passwords).
*   **Dynamic VLAN:** RADIUS assigns VLAN based on user identity.
*   **Fail:** Port blocked or assigned to Guest VLAN.
*   **MAB:** Falls back to MAC address authentication for devices without 802.1X (printers, IoT).
