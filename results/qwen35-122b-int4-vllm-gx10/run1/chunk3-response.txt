

T1 — **Plan vs. Apply**
`tofu plan` performs a dry run: it analyzes the configuration and state to generate an execution plan (what will change) without making any changes. `tofu apply` executes the plan: it provisions, updates, or destroys resources to match the configuration. Plan is for review; Apply is for execution.

T2 — **State and Remote State**
State is a JSON file mapping configuration resources to real-world infrastructure IDs. It tracks metadata and dependencies. Remote state is crucial for team collaboration (prevents local state conflicts), enables state locking (prevents concurrent writes), and allows modules to share data via `terraform_remote_state`.

T3 — **count vs. for_each**
`count` creates resources based on an integer index (0, 1, 2). `for_each` creates resources based on a map or set of strings (keys). `for_each` is preferred when resources have unique identifiers (keys) because adding/removing items in `count` can shift indices and cause unintended recreation of resources.

T4 — **Manual Changes (Drift)**
If you change a resource manually, OpenTofu detects this "drift" during the next `tofu plan`. It will show the resource as "out of sync" (e.g., `~` for update). Running `tofu apply` will reconcile the state by either reverting the manual change to match the config or updating the config to match the change (if using `import` or specific lifecycle settings).

T5 — **Snippet: 3 VMs with for_each**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-123456"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

T6 — **remote_state vs. Outputs**
`terraform_remote_state` reads state from another stack, creating tight coupling and potential locking issues. The recommended alternative is **Module Composition** (calling one module from another within the same root) or passing outputs via **CI/CD pipelines** as variables. This avoids direct state dependencies between independent root modules.

T7 — **Output Dependency Issue**
The output is likely defined on the cluster resource, but the kubeconfig is generated by a `null_resource` provisioner that runs *after* the cluster resource is created. OpenTofu evaluates outputs after the apply phase, but if the output references the `null_resource` which hasn't finished, it may be empty. **Fix:** Move the output definition to the `null_resource` or ensure the consuming resource depends on the `null_resource` using `depends_on`.

T8 — **Import (CLI vs. Block)**
`tofu import` (CLI) is imperative: you run a command to link a real resource to a config block. The `import` block (1.5+) is declarative: you define the import in HCL, and `tofu plan`/`apply` handles the linking. The block improves reproducibility and version control of the import process.

T9 — **Variable vs. Output**
A `variable` is an input parameter passed into a module or root configuration (e.g., region, instance type). An `output` is a value exported from a module or root configuration for use by other modules or to display to the user after apply.

T10 — **Provider and Init**
A provider is a plugin that interacts with an API (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, it fails because the provider plugins are not downloaded or configured in the `.terraform` directory. `init` initializes the working directory and downloads providers.

T11 — **.terraform.lock.hcl**
This file locks the specific versions of providers and modules used in the project. It should be committed to version control to ensure all team members and CI/CD pipelines use identical provider versions, preventing unexpected breaking changes.

T12 — **Destroy and Target**
`tofu destroy` removes all resources managed by the state. To target a single resource for destruction, use the `-target` flag: `tofu destroy -target=aws_instance.example`. Note: This leaves orphaned resources if dependencies exist.

T13 — **Data Source**
A data source reads existing data from the infrastructure provider without managing it (read-only). **Example:** Using `aws_ami` data source to find the latest Ubuntu AMI ID instead of hardcoding it or creating a new AMI resource.

T14 — **Locals vs. Variables**
`variable` blocks define inputs that users must provide (or have defaults). `locals` define internal variables calculated within the module that are not exposed as inputs. Use `locals` for computed values, formatting, or reducing repetition within a module.

T15 — **Lifecycle Block**
*   `create_before_destroy`: Replaces resources by creating the new one before destroying the old (prevents downtime).
*   `prevent_destroy`: Prevents the resource from being destroyed (safety for critical data).
*   `ignore_changes`: Ignores specific attribute changes during updates (e.g., ignore tags updated externally).

T16 — **Moved Block**
A `moved` block tells OpenTofu that a resource has changed its address (e.g., moved to a different module) without changing its identity. It updates the state file to point to the new address, preventing the resource from being destroyed and recreated during refactoring.

T17 — **Dependency Graph**
OpenTofu builds a graph of resources based on references. **Implicit dependencies** are created automatically when one resource references another (e.g., `aws_instance` referencing `aws_vpc.id`). **Explicit dependencies** use `depends_on`. `depends_on` forces serialization, reducing parallelism; use sparingly to avoid slowing down execution.

T18 — **Plan Performance Strategies**
1.  **Split State:** Break large state files into smaller modules/backends. (Tradeoff: Increased complexity).
2.  **Refresh False:** Use `-refresh=false` if state is trusted. (Tradeoff: Risk of drift).
3.  **Parallelism:** Increase `-parallelism` flag. (Tradeoff: Higher API load).
4.  **Targeting:** Use `-target` for specific changes. (Tradeoff: Risk of orphaned resources).

T19 — **State Locking**
Locking prevents concurrent writes to the state file (e.g., via DynamoDB). If a CI pipeline crashes, the lock remains. **Fix:** Use `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually writing, forcing unlock can corrupt the state file.

T20 — **Migrate to S3 Backend**
1.  Backup local state.
2.  Configure new S3 backend in `backend` block.
3.  Run `tofu init -migrate-state`.
4.  Confirm migration when prompted.
5.  Verify by running `tofu plan` and checking the state backend in the UI/logs.

A1 — **Playbook, Role, Task**
A **Playbook** is a YAML file containing one or more plays. A **Role** is a structured collection of tasks, vars, and files for reuse. A **Task** is a single unit of work (e.g., install a package) executed within a play.

A2 — **ansible_facts**
`ansible_facts` is a dictionary of system information gathered automatically (e.g., OS, IP). Access OS family via `{{ ansible_os_family }}`.

A3 — **command, shell, raw**
`command`: Runs commands without shell features (safe, idempotent). `shell`: Runs via shell (supports pipes, variables). `raw`: Executes without Python on the remote node (used for bootstrapping). Use `command` by default; `shell` for pipes; `raw` for minimal environments.

A4 — **Idempotency**
Idempotency means running a task multiple times yields the same result. **Idempotent:** `apt: name=nginx state=present` (installs only if missing). **Not Idempotent:** `shell: echo "hello"` (appends "hello" every time).

A5 — **Install htop Task**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```

A6 — **Variable Precedence**
Order (Low to High): Role defaults < Inventory file vars < Group vars < Host vars < Role vars < Play vars < `extra_vars` (CLI). `set_fact` acts like host vars but can be overridden by higher precedence.

A7 — **RKE2 Agent Deployment**
Use `serial: 3` in the play to limit concurrency. Use `wait_for` or a custom task to ensure the first 3 nodes are ready before proceeding. Group the first 3 nodes in a specific inventory group if strict ordering is required, or rely on `serial` with a handler checking node status.

A8 — **ansible-vault**
`ansible-vault` encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'secret_value' --name 'my_var'` and paste the output into the vars file. The file itself remains unencrypted, but the variable value is ciphertext.

A9 — **Inventory File**
An inventory file lists target hosts. **Static:** A simple INI or YAML file. **Dynamic:** A script or plugin that queries an API (e.g., AWS EC2) to generate the host list at runtime.

A10 — **Ad-hoc Command**
`ansible webservers -m shell -a "df -h"`

A11 — **Handler**
A handler is a task that runs only if notified (e.g., service restart). It differs from a regular task because it runs once at the end of the play, even if notified multiple times. Trigger with `notify: handler_name`.

A12 — **ansible.cfg**
Configuration file for Ansible settings. Common settings: `inventory` (path), `remote_user` (SSH user), `forks` (parallel processes).

A13 — **register Keyword**
`register` saves the output of a task to a variable. Use it in subsequent tasks for conditionals (e.g., `when: my_var.rc == 0`) or debugging (`debug: var=my_var`).

A14 — **include_tasks vs. import_tasks**
`import_tasks` is static (parsed at playbook start); conditionals apply to the import itself. `include_tasks` is dynamic (parsed at runtime); conditionals apply to the execution of the included tasks. Use `include_tasks` for runtime logic.

A15 — **Ansible Galaxy**
Galaxy is a repository for sharing roles and collections. Use `requirements.yml` to list dependencies and run `ansible-galaxy install -r requirements.yml` to install them.

A16 — **Connection Plugins**
Defines how Ansible connects. `ssh`: Standard SSH for Linux. `local`: Runs on the control node. `network_cli`: For network devices (Cisco, Juniper). Use `local` for control tasks, `ssh` for servers, `network_cli` for routers.

A17 — **delegate_to and run_once**
`delegate_to` runs a task on a different host (e.g., localhost). `run_once` ensures the task runs only once per play. **Example:** Run a database backup script on the primary DB host (`delegate_to: primary_db`) while iterating over app servers, using `run_once: true`.

A18 — **Performance Strategies**
1.  **Forks:** Increase `-f` (default 5) to parallelize more hosts. (Tradeoff: Network load).
2.  **Pipelining:** Enable `pipelining = True` in `ansible.cfg` to reduce SSH connections. (Tradeoff: Requires sudo config).
3.  **Fact Caching:** Enable `fact_caching` to avoid re-gathering facts. (Tradeoff: Stale data).
4.  **Mitogen:** Use the Mitogen plugin for faster execution. (Tradeoff: Security/Compatibility risks).

A19 — **Jinja2 Templating**
`{{ }}` for variables, `{% %}` for logic (loops/if), `{# #}` for comments.
**Snippet:**
```jinja2
upstream backend {
{% for server in servers %}
    server {{ server.ip }}:{{ server.port }}; # {{ server.name }}
{% endfor %}
}
```

A20 — **Zero-Downtime Rolling Deployment**
1.  **Serial:** Set `serial: 20%` to update batches.
2.  **Pre-tasks:** Remove host from Load Balancer (LB).
3.  **Tasks:** Deploy app, run health checks (`uri` module).
4.  **Post-tasks:** Add host back to LB.
5.  **Rollback:** Use `block/rescue`. If health check fails in `block`, `rescue` reverts the deployment and re-adds to LB.
