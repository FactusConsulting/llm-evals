

CL1 — **IaaS vs PaaS vs SaaS:**
*   **IaaS (Infrastructure as a Service):** Provides virtualized computing resources (VMs, storage, networking). You manage OS, runtime, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a managed environment for developing and running apps. You manage code and data; provider manages OS/runtime. *Example: AWS RDS or Azure App Service.*
*   **SaaS (Software as a Service):** Delivers fully managed software applications over the internet. You manage only user access and data. *Example: Salesforce or Microsoft 365.*

CL2 — **Shared Responsibility Model:**
*   **IaaS VMs:** Provider secures physical hardware, hypervisor, and network infrastructure. You secure the OS, applications, data, and firewall rules.
*   **Managed Kubernetes:** Provider manages control plane, nodes, and underlying infrastructure. You manage the OS on worker nodes (if self-managed), workloads, and network policies.
*   **SaaS (M365):** Provider secures everything (infrastructure, app, data at rest). You manage user access, data classification, and device compliance.

CL3 — **VPC, Subnet, SG, NACL:**
*   **VPC:** Virtual network boundary (IP range).
*   **Subnet:** Segment of VPC IP range (public/private).
*   **Security Group (SG):** Instance-level firewall, **stateful** (tracks connections, allows return traffic automatically).
*   **NACL:** Subnet-level firewall, **stateless** (must explicitly allow return traffic).
*   **Layering:** Traffic flows VPC → Subnet (NACL) → Instance (SG).

CL4 — **Multi-Account Strategy:**
*   **Landing Zone:** Pre-configured baseline environment (networking, logging, security).
*   **OUs:** Organizational Units group accounts by function (Prod, Dev, Security).
*   **Guardrails:** SCPs (Service Control Policies) enforce limits across accounts.
*   **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) centralizes connectivity.
*   **Centralized Logging:** All CloudTrail/VPC logs aggregate to a Security account.
*   **Single Account Risk:** High blast radius, billing complexity, noisy security alerts, difficult permission management.

CL5 — **Infrastructure as Code (IaC):**
*   **Terraform/OpenTofu:** Declarative, multi-cloud, stateful. Choose for multi-cloud or complex provisioning.
*   **Pulumi:** Imperative, uses general-purpose languages (Python/TS). Choose for teams strong in coding over HCL.
*   **CloudFormation/Bicep:** Native to AWS/Azure. Choose for deep integration with specific provider features.
*   **Crossplane:** Kubernetes-native IaC. Choose if managing cloud resources via K8s API.

CL6 — **Autoscaling Patterns:**
*   **HPA:** Scales pods based on CPU/Memory.
*   **VPA:** Adjusts pod resource requests/limits (requires restart).
*   **Cluster Autoscaler:** Adds/removes nodes based on pending pods.
*   **KEDA:** Event-driven scaling (e.g., queue depth, custom metrics).
*   **KEDA vs HPA:** Use KEDA when scaling based on external events (e.g., Kafka lag) rather than resource utilization.

CL7 — **Disaster Recovery (DR) Strategy:**
*   **RPO/RTO:** Define max data loss (RPO) and max downtime (RTO).
*   **Active-Active:** Traffic routed to both regions. High cost, lowest RTO.
*   **Active-Passive:** Primary handles traffic; secondary standby. Lower cost, higher RTO.
*   **DB Replication:** Sync (low RPO, latency sensitive) vs Async (higher RPO, better performance).
*   **DNS Failover:** Route53 Health Checks/Traffic Manager route traffic on failure.
*   **DR Types:**
    *   *Pilot Light:* Minimal core running (DB), scale up on failover.
    *   *Warm Standby:* Scaled-down version running, ready to scale.
    *   *Multi-site:* Full capacity in both regions.

CL8 — **GitOps:**
*   **Model:** Git repository is the single source of truth. Controllers sync cluster state to match Git.
*   **ArgoCD vs Flux:** ArgoCD has a UI and App-of-Apps pattern; Flux is lightweight, CLI-driven, and CNCF native.
*   **Secrets:** Use Sealed Secrets (encrypted in Git) or External Secrets Operator (fetch from Vault/AWS Secrets Manager).
*   **Drift:** GitOps controller detects manual changes and automatically reverts them to match the Git state.

CL9 — **Stateful K8s Migration:**
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC:** Use `local` storage class for low latency (node-affinity required).
*   **Headless Service:** `clusterIP: None` for stable DNS names (pod-0.service).
*   **Init Containers:** Run before main container (e.g., file setup).
*   **ConfigMaps:** Mount as volumes to specific paths.
*   **PDB:** Prevents voluntary disruptions from taking down all pods simultaneously.

CL10 — **Identity & Credentials:**
*   **Service Account:** K8s identity for pods.
*   **Workload Identity:** Maps K8s SA to Cloud IAM role (Azure/GCP).
*   **IRSA:** AWS-specific mapping of K8s SA to IAM Role.
*   **Bad Practice:** Mounting static keys/secrets in pods risks leakage if pod is compromised.
*   **Federation:** Uses OIDC to exchange short-lived tokens, eliminating long-lived credentials.

CL11 — **Storage Types:**
*   **Object (S3/Blob):** Unstructured data, HTTP access, high durability (11x9s). Use for backups, media.
*   **Block (EBS/Disk):** Raw volume attached to VM, low latency. Use for databases, OS disks.
*   **File (EFS/Azure Files):** Shared file system (NFS/SMB). Use for shared configs, home directories.
*   **Guarantees:** Object storage offers highest durability; Block offers highest IOPS/latency.

CL12 — **Zero Trust K8s:**
*   **Network Policies:** Default deny all traffic; allow only specific pods.
*   **Service Mesh:** Enforces mTLS between services.
*   **Pod Identity:** No cloud credentials in pods.
*   **Admission:** OPA/Kyverno enforce policies (e.g., no root user).
*   **Image Signing:** Cosign/Notary verify image integrity.
*   **Runtime:** Falco detects anomalous behavior.
*   **Diff:** Traditional relies on perimeter firewall; Zero Trust assumes breach and verifies every request.

CL13 — **CDN:**
*   **Definition:** Distributed network of edge servers caching content closer to users.
*   **Mechanism:** DNS resolves to nearest edge; edge serves cached content or fetches from origin.
*   **Services:** AWS CloudFront, Azure CDN.
*   **Use Case:** CDN for static assets (images, JS) to reduce latency/cost. Direct origin for dynamic/private data.

CL14 — **AZs and Regions:**
*   **Region:** Geographic area (e.g., us-east-1).
*   **AZ:** Isolated data center within a region.
*   **Multi-AZ:** Protects against data center failure (HA).
*   **Zonal Resource:** Tied to one AZ (e.g., specific VM).
*   **Regional Resource:** Spans AZs (e.g., S3 bucket, Load Balancer).

CL15 — **Managed Database:**
*   **Definition:** Cloud provider manages the database engine (e.g., RDS, Cloud SQL).
*   **Provider Tasks:** Patching, backups, replication, failover, scaling infrastructure.
*   **User Tasks:** Schema design, query optimization, access control, data management.

CL16 — **IAM & Least Privilege:**
*   **Users:** Individual identities.
*   **Groups:** Collections of users.
*   **Roles:** Identities assumed by services/users (temporary credentials).
*   **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Grant only permissions necessary for the specific task. Apply via granular policies and regular access reviews.

CL17 — **Serverless:**
*   **Definition:** Event-driven compute without managing servers (Lambda, Functions).
*   **Comparison:** AWS Lambda (ecosystem), Azure Functions (Microsoft stack), GCP Functions (Google stack).
*   **Cold Starts:** Latency incurred when initializing a new container instance. Matters for latency-sensitive apps.
*   **Poor Fit:** Long-running processes (>15 mins), consistent high load (often cheaper on VMs), stateful apps.

CL18 — **K8s Ingress:**
*   **Ingress Resource:** L7 routing, simple, controller-dependent.
*   **Gateway API:** L4/L7, extensible, standardizing replacement for Ingress.
*   **CLB Annotations:** Cloud Load Balancer directly attached to Service.
*   **Mesh Ingress:** Traffic enters mesh via Gateway.
*   **TLS:** Terminate at LB (easier) or Ingress Controller (end-to-end encryption).
*   **Gateway API:** Use for complex routing, multi-tenant, and future-proofing.

CL19 — **Cost Optimization ($80k/mo):**
*   **Commitments:** Reserved Instances/Savings Plans for steady state.
*   **Spot/Preemptible:** For fault-tolerant batch workloads (up to 90% savings).
*   **Right-sizing:** Downsize over-provisioned resources.
*   **Storage:** Move old data to Archive/Intelligent-Tiering.
*   **FinOps:** Tagging strategy, showback/chargeback to teams.
*   **Tools:** AWS Cost Explorer, Kubecost, CloudHealth. Process: Monthly review meetings, automated anomaly alerts.

CL20 — **Multi-Cloud Strategy:**
*   **Abstraction:** Use K8s as common runtime, Terraform for IaC.
*   **Networking:** Interconnect (Direct Connect/ExpressRoute) or SD-WAN.
*   **Identity:** Federated SSO across providers.
*   **Trade-offs:** Avoids lock-in, improves resilience vs. increased complexity, cost, and skill requirements.
*   **Justification:** Regulatory requirements, negotiation leverage, specific service needs.
*   **Unnecessary:** If one provider meets 95% of needs, multi-cloud adds operational overhead without proportional benefit.

OT1 — **Purdue Model (ISA-95):**
*   **Level 0:** Physical Process (Sensors/Actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Supervisory Control (HMI, SCADA).
*   **Level 3:** Manufacturing Operations (MES, Historian).
*   **Level 4:** Enterprise (ERP, Business Planning).
*   **Level 5:** Internet/External.

OT2 — **IT vs OT:**
*   **IT:** Prioritizes Confidentiality, then Integrity, then Availability.
*   **OT:** Prioritizes Safety, then Availability, then Integrity/Confidentiality.
*   **Patching:** OT systems often run legacy OS (WinXP/7), require vendor validation, and cannot tolerate downtime. Standard patching risks safety and production.

OT3 — **IDMZ (Industrial DMZ):**
*   **Role:** Buffer zone between IT (L4) and OT (L1-L3).
*   **Traffic:** IT→DMZ (Data collection), DMZ→OT (Read-only). No direct IT→OT.
*   **Risk:** Direct L4→L1 bypasses security controls, allowing malware to reach critical control systems.

OT4 — **OT Protocols:**
*   **Modbus TCP:** L1/L2 (Device to Controller).
*   **OPC UA:** L2/L3 (Secure data exchange).
*   **EtherNet/IP (CIP):** L1 (Industrial Ethernet).
*   **PROFINET:** L1 (Real-time control).
*   **MQTT:** L3/L4 (Lightweight messaging to cloud).

OT5 — **Data Diode vs Firewall:**
*   **Data Diode:** Hardware-enforced one-way data flow (OT→IT).
*   **Firewall:** Bi-directional rule-based filtering.
*   **Use Case:** High-security environments where OT data must leave but nothing can enter.
*   **Limitation:** Cannot support return traffic (e.g., acknowledgments, remote config).

OT6 — **Data Flow Design:**
*   **Flow:** PLC → Historian (L3) → OPC UA Server → Edge Gateway → MQTT Broker → Cloud.
*   **Security:** IDMZ between OT and Cloud. Edge Gateway performs protocol translation and filtering.
*   **Boundaries:** Firewall between Historian and Edge; Firewall between Edge and Cloud.

OT7 — **IEC 62443 Zones & Conduits:**
*   **Zone:** Logical grouping of assets with same security requirements.
*   **Conduit:** Communication path between zones.
*   **Design:**
    *   Zone 1: PLCs/SIS (High Security).
    *   Zone 2: SCADA/HMI (Medium Security).
    *   Zone 3: Engineering Workstations (Medium Security).
    *   Zone 4: Corporate Network (Low Security).
    *   Conduits: Firewalls/DMZ between zones.

OT8 — **Segmentation Strategy:**
*   **VLANs:** Separate VLAN per production line.
*   **Firewalls:** Between VLANs and at network edge.
*   **Switches:** Managed switches with port security (MAC binding).
*   **Vendor Access:** Jump host in DMZ, time-limited, monitored.
*   **Transition:** Build parallel network, migrate line-by-line during maintenance windows.

OT9 — **SIS vs BPCS:**
*   **BPCS:** Controls normal process operations.
*   **SIS:** Independent safety system (trips process on danger).
*   **IEC 61511:** Functional Safety standard.
*   **Isolation:** SIS must be isolated to prevent IT malware from disabling safety trips.
*   **Ransomware Impact:** If SIS is compromised, safety is lost, risking physical damage or injury.

OT10 — **PLC vs DCS vs SCADA:**
*   **PLC:** Discrete control, localized, fast response.
*   **DCS:** Process control, integrated, centralized (chemical/petrochemical).
*   **SCADA:** Supervisory control over wide areas (pipelines, utilities).
*   **Coexistence:** Yes. PLCs often feed data to DCS/SCADA systems.

OT11 — **Remote Access:**
*   **Architecture:** Jump Host (Bastion) in DMZ.
*   **Controls:** MFA, PAM (Privileged Access Management), Session Recording, Time-limited access.
*   **RDP Direct:** Unacceptable due to lack of audit trail, credential exposure, and direct network path to critical assets.

OT12 — **Incident Response (Water Treatment):**
*   **Detection:** IDS/IPS on network segments, anomaly detection on PLC traffic.
*   **Response:** Isolate compromised VLANs immediately.
*   **Coordination:** IT secures network; OT ensures physical safety (manual override).
*   **Operator Role:** Monitor physical process, execute manual safety procedures, do not trust compromised HMIs.
*   **Safety First:** Security actions must not trigger unsafe physical states.

OT13 — **HMI:**
*   **Role:** Interface for operators to monitor and control the process.
*   **Diff:** Engineering Workstation is for programming logic/configuring the system. HMI is for runtime operation.

OT14 — **Historian:**
*   **Role:** Time-series database storing process data.
*   **Importance:** Enables trend analysis, compliance, and troubleshooting.
*   **Plant Historian (L3):** High resolution, real-time data.
*   **Enterprise Historian (L4):** Aggregated data for business reporting.

OT15 — **Ladder Logic:**
*   **Device:** Executed by PLCs.
*   **Dominance:** Visual representation mimics electrical relay logic, easy for electricians to understand, massive legacy codebase.

OT16 — **RTU:**
*   **Definition:** Remote Terminal Unit, focuses on telemetry and communication.
*   **Diff:** PLC is for local control logic; RTU is for remote data collection/control.
*   **Environment:** Remote sites (oil wells, pipelines) where connectivity is limited.

OT17 — **Analog vs Digital:**
*   **Analog:** Continuous signal (4-20mA, 0-10V).
*   **Digital:** Discrete On/Off.
*   **4-20mA vs 0-20mA:** 4mA "live zero" allows detection of wire breaks (0mA = broken wire, 4mA = 0% signal).

OT18 — **Asset Inventory:**
*   **Foundation:** You cannot secure what you don't know exists.
*   **Tools:** Passive monitoring (packet sniffing) vs Active Scanning.
*   **Active Scanning Risk:** Can crash legacy OT devices due to unexpected traffic or protocol queries. Prefer passive discovery.

OT19 — **MITRE ATT&CK for ICS:**
*   **Tactics:** Reconnaissance, Initial Access, Execution, Persistence, Impact.
*   **Example:** Impact → Manipulation of Control Logic.
*   **Diff:** Focuses on physical consequences and ICS-specific protocols.
*   **Use:** Map existing controls to techniques to identify gaps (e.g., lack of firmware integrity monitoring).

OT20 — **Converged SOC:**
*   **Log Collection:** Agentless or lightweight agents to avoid performance impact.
*   **SIEM:** Ingest OT logs, correlate with IT logs.
*   **Rules:** OT-specific (e.g., PLC write attempts, unauthorized config changes).
*   **Staffing:** IT analysts handle network; OT engineers validate physical impact.
*   **False Positives:** Tune aggressively; OT tolerates downtime less than IT.
*   **Firmware Alert:** Isolate device, verify signature, coordinate rollback with vendor, do not reboot without safety check.
