

K1 — **Deployment vs. StatefulSet**
A **Deployment** manages stateless pods with interchangeable identities (random names), supports rolling updates, and scales pods in parallel. A **StatefulSet** manages stateful applications with stable, unique network identifiers (e.g., `pod-0`, `pod-1`), ordered deployment/scaling, and stable persistent storage (each pod gets its own PVC). Use StatefulSet for databases or clusters requiring stable identity.

K2 — **ClusterIP Routing**
A ClusterIP Service exposes a virtual IP (VIP) internal to the cluster. `kube-proxy` runs on each node and configures `iptables` or `IPVS` rules. When traffic hits the VIP, these rules randomly select an endpoint (Pod IP) from the Service’s Endpoints list and DNAT (Destination NAT) the traffic to that Pod.

K3 — **PV, PVC, and StorageClass**
*   **StorageClass:** Defines the "type" of storage (provisioner, parameters). It enables dynamic provisioning.
*   **PersistentVolume (PV):** A piece of storage in the cluster (claimable resource).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user/pod.
*   **Relation:** A PVC requests storage; Kubernetes matches it to a PV (either pre-existing or dynamically provisioned via a StorageClass). The Pod mounts the PVC.

K4 — **CrashLoopBackOff Troubleshooting**
1.  **Check Logs:** `kubectl logs <pod> --previous` to see why the app exited.
2.  **Check Events:** `kubectl describe pod <pod>` for OOMKilled, Liveness probe failures, or scheduling issues.
3.  **Check Resources:** Verify memory/CPU limits aren't too low causing OOM.
4.  **Check Config:** Verify ConfigMaps/Secrets are mounted correctly and environment variables are valid.

K5 — **CoreDNS Role**
CoreDNS provides DNS-based service discovery within the cluster. It resolves service names (e.g., `my-service.default.svc.cluster.local`) to Pod IPs. If CoreDNS pods are down, internal service discovery fails, and pods cannot resolve external domains unless they use external DNS directly (bypassing CoreDNS), breaking most cluster communication.

K6 — **Kubernetes Scheduler Logic**
The scheduler uses a **Filter** (Predicate) phase to remove unschedulable nodes (e.g., insufficient resources, taints), then a **Score** (Priority) phase to rank remaining nodes.
*   **Factors:** 1. Resource availability (CPU/RAM), 2. Node Affinity/Anti-Affinity rules, 3. Taints/Tolerations, 4. Pod topology spread constraints.
The node with the highest score is selected.

K7 — **Memory Scheduling and Runtime**
*   **Scheduling:** Yes, it will be scheduled. The node has 0.5GB (512Mi) free (4GB - 3.5GB). The pod requests 256Mi, which fits within the free capacity.
*   **Runtime:** If the pod uses 600Mi, it exceeds its `limits.memory` (512Mi). The Linux OOM Killer will terminate the container, resulting in an `OOMKilled` exit code.

K8 — **Ingress Request Lifecycle**
1.  **External LB:** Cloud load balancer forwards traffic to the Ingress Controller Pod IP.
2.  **Ingress Controller:** NGINX controller reads Ingress Resources to determine routing rules (host/path).
3.  **Service:** Controller forwards traffic to the target Kubernetes Service (ClusterIP).
4.  **Endpoints:** Service resolves to a list of Pod IPs.
5.  **kube-proxy:** Node-level `iptables`/IPVS rules DNAT traffic from Service IP to the specific Pod IP.
6.  **Pod:** Traffic reaches the application container.

K9 — **NetworkPolicy**
A NetworkPolicy defines how pods are allowed to communicate.
*   **Default:** If no policy exists, all traffic is allowed (default allow).
*   **With Policy:** If a policy selects a pod, it defaults to **deny all** for the specified direction (ingress/egress) unless explicitly allowed by rules. It acts as a firewall.

K10 — **RollingUpdate vs. Recreate**
*   **RollingUpdate:** Gradually replaces pods (new version comes up before old goes down). Zero downtime.
*   **Recreate:** Terminates all existing pods before creating new ones. Causes downtime.
*   **Choose Recreate:** When the application cannot run two versions simultaneously (e.g., database schema changes incompatible with old version) or for stateful sets where parallel updates are unsafe.

K11 — **Namespace**
A Namespace is a virtual cluster within a physical cluster, providing logical isolation for resources (RBAC, quotas).
*   **Default Namespaces:** `default`, `kube-system` (system components), `kube-public` (readable by all), `kube-node-lease` (node heartbeats).

K12 — **kubectl describe pod**
Used for detailed debugging. Unlike `get`, it shows:
1.  **Events:** Recent warnings or state changes (e.g., Pulling image, OOMKilled).
2.  **Conditions:** Detailed status of readiness/liveness probes.
3.  **Mounts/Env:** Specific ConfigMap/Secret mounts and environment variables injected.

K13 — **ConfigMap**
A ConfigMap stores non-confidential configuration data as key-value pairs.
*   **Methods:** 1. Inject as **Environment Variables** (`envFrom` or `env`). 2. Mount as **Files** in a Volume (`volumeMounts`).

K14 — **Service Types**
*   **ClusterIP:** Exposes service on an internal IP (default). Accessible only within the cluster.
*   **NodePort:** Exposes service on a static port on each Node's IP. Accessible externally via `<NodeIP>:<Port>`.
*   **LoadBalancer:** Provisions an external cloud load balancer. Accessible via a public IP.

K15 — **DaemonSet**
A DaemonSet ensures a copy of a pod runs on **all** (or selected) nodes.
*   **Use Case:** Use instead of Deployment for node-level agents like log collectors (Fluentd), monitoring agents (Node Exporter), or storage drivers (Ceph) that must run on every node.

K16 — **Taints/Tolerations vs. Affinity**
*   **Taints/Tolerations:** Taints "repel" pods from a node; Tolerations allow pods to "tolerate" the taint. Use case: Dedicate GPU nodes (Taint) to GPU workloads (Toleration).
*   **Node Affinity:** "Attracts" pods to nodes based on labels. Use case: Schedule web pods on nodes with `disktype=ssd`.
*   **Difference:** Taints control node eligibility; Affinity controls pod preference.

K17 — **Kubernetes Operator**
An Operator is a method of packaging, deploying, and managing a Kubernetes application using Custom Resources (CRDs) and a Custom Controller.
*   **Difference:** Standard controllers manage built-in resources (Pods, Deployments). Operators manage custom resources specific to an application (e.g., `PostgresCluster`).
*   **Solves:** Automates complex stateful application lifecycle tasks (backups, upgrades, scaling) that Helm/Deployments cannot handle alone.

K18 — **etcd Consistency and Recovery**
*   **Model:** etcd uses the **Raft** consensus algorithm for strong consistency.
*   **Quorum Loss:** If quorum (majority) is lost (e.g., 2 of 3 nodes down), the cluster becomes read-only/unavailable to prevent split-brain.
*   **Recovery:** You cannot recover the cluster state from the remaining node alone. You must restore from a **snapshot backup** to a new node and reconfigure the cluster members, accepting potential data loss since the last snapshot.

K19 — **RBAC and Manifests**
RBAC uses **Roles/ClusterRoles** (permissions) and **RoleBindings/ClusterRoleBindings** (who gets permissions).
*   **Role:** Namespace-scoped permissions.
*   **ClusterRole:** Cluster-wide permissions.
*   **Binding:** Links a Role/ClusterRole to a User/Group/ServiceAccount.

**Manifests (Read-only access to pods/logs in `dev` namespace):**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — **DNS ndots Issue**
*   **Cause:** Default `ndots:5` means if a domain has fewer than 5 dots (e.g., `google.com`), the resolver appends search domains (e.g., `default.svc.cluster.local.google.com`), causing multiple DNS queries before resolving the external IP.
*   **Fix:** Set `dnsConfig` in the Pod spec to reduce `ndots` to 1 or use absolute FQDNs (ending in `.`).
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "1"
```

D1 — **git rebase vs. merge**
*   **Merge:** Creates a new commit combining branches, preserving history structure.
*   **Rebase:** Rewrites history by moving the current branch to the tip of the target branch, creating a linear history.
*   **Avoid Rebasing:** Never rebase **public/shared branches** (e.g., `main`, `develop`) as it rewrites commit hashes, causing conflicts for other collaborators.

D2 — **TCP vs. UDP**
*   **TCP:** Connection-oriented, reliable, ordered delivery, flow control. Protocols: HTTP, SSH.
*   **UDP:** Connectionless, unreliable, no ordering, low overhead. Protocols: DNS, VoIP (RTP).

D3 — **Race Condition**
A race condition occurs when multiple threads/processes access shared data concurrently, and the outcome depends on the timing of execution.
*   **Example:** Two threads increment a counter `x = x + 1`. Both read `x=0`, both write `x=1`. Result is 1 instead of 2.

D4 — **Symmetric vs. Asymmetric Encryption**
*   **Symmetric:** Same key for encryption/decryption (fast).
*   **Asymmetric:** Public key encrypts, Private key decrypts (slow, secure key exchange).
*   **TLS:** Asymmetric encryption is used during the **handshake** to securely exchange a symmetric session key. Symmetric encryption is used for the **data transfer** for performance.

D5 — **Container Image Layers**
An image is a stack of read-only filesystem layers. Each instruction in a Dockerfile creates a layer.
*   **Layer Caching:** Docker caches layers. If a layer changes, all subsequent layers are rebuilt.
*   **Best Practice:** Order commands to maximize cache hits (e.g., copy `package.json` and install dependencies *before* copying application code).

D6 — **HTTP 503 Troubleshooting**
1.  **Check Upstream Health:** Are backend pods healthy? (Readiness probes).
2.  **Check Load Balancer:** Is the LB routing to healthy endpoints?
3.  **Check App Logs:** Are there connection timeouts or resource exhaustion?
4.  **Check Resources:** Is the pod OOMKilled or CPU throttled causing latency?

D7 — **CAP Theorem**
A distributed system can only guarantee two of three: **Consistency** (all nodes see same data), **Availability** (every request gets a response), **Partition Tolerance** (system works despite network splits).
*   **CP Example:** Banking system (Consistency > Availability). If partitioned, it rejects writes to prevent bad data.
*   **AP Example:** Social media feed (Availability > Consistency). If partitioned, it shows potentially stale data rather than failing.

D8 — **Horizontal vs. Vertical Scaling**
*   **Vertical:** Adding more resources (CPU/RAM) to an existing node. Limited by hardware.
*   **Horizontal:** Adding more nodes/instances.
*   **Patterns for Horizontal:** Stateless application design, Load Balancing, Database Sharding, Caching layers.

D9 — **Environment Variable**
A dynamic value available to processes in an OS.
*   **Persistence:** Add `export VAR=value` to `~/.bashrc` or `~/.profile` for user sessions, or `/etc/environment` for system-wide.

D10 — **JSON vs. YAML**
*   **JSON:** Data interchange format. Strict syntax. Advantage: Easy to parse programmatically.
*   **YAML:** Human-readable data serialization. Advantage: Supports comments and indentation-based structure (less verbose).

D11 — **REST API**
An architectural style for APIs using HTTP methods to manipulate resources.
*   **GET:** Retrieve resource (safe, idempotent).
*   **POST:** Create resource (not idempotent).
*   **PUT:** Replace resource entirely (idempotent).
*   **DELETE:** Remove resource (idempotent).

D12 — **Version Pinning**
Locking dependencies to specific versions (e.g., `package-lock.json`, `requirements.txt`).
*   **Importance:** Ensures reproducible builds. Prevents "it works on my machine" issues caused by upstream dependency updates breaking the build.

D13 — **Compiled vs. Interpreted**
*   **Compiled:** Source code translated to machine code before execution (faster runtime). Examples: C, Go, Rust.
*   **Interpreted:** Source code executed line-by-line by a runtime engine (slower, flexible). Examples: Python, JavaScript, Ruby.

D14 — **Reverse vs. Forward Proxy**
*   **Reverse Proxy:** Sits in front of servers, forwards client requests to backend servers. Use case: Nginx (Load Balancing, SSL termination).
*   **Forward Proxy:** Sits in front of clients, forwards client requests to the internet. Use case: Corporate firewall (filtering, anonymity).

D15 — **Deadlock**
A situation where processes are blocked because each is holding a resource and waiting for another resource held by another process.
*   **Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

D16 — **Eventual Consistency**
Data updates propagate asynchronously; all replicas will eventually agree.
*   **Cassandra:** Uses tunable consistency.
*   **Levels:** `ONE` (fastest, least consistent), `QUORUM` (balance), `ALL` (slowest, most consistent). Read-after-write consistency is not guaranteed at `ONE`.

D17 — **mTLS (Mutual TLS)**
Both client and server authenticate each other using certificates.
*   **Handshake:** Server sends cert (standard TLS). Client sends cert. Server verifies client cert against a CA.
*   **Use Case:** Service Mesh (Istio/Linkerd) for zero-trust internal service-to-service communication.

D18 — **Hash Table Internals**
Stores key-value pairs. Key is hashed to an index.
*   **Collision Resolution:**
    *   **Chaining:** Index points to a linked list of entries.
    *   **Open Addressing:** Find next available slot (probing).
*   **Complexity:** Average O(1) for insert/lookup/delete. Worst case O(n) if all keys collide.

D19 — **Circuit Breaker Pattern**
Prevents cascading failures by stopping calls to a failing service.
*   **States:**
    1.  **Closed:** Requests pass through normally.
    2.  **Open:** Requests fail immediately (timeout) without calling the service.
    3.  **Half-Open:** Limited requests allowed to test if service recovered.
*   **Relation:** Works with retry policies; if circuit is open, retries are skipped to save resources. Exponential backoff is used during the "Open" timeout period.

D20 — **Optimistic vs. Pessimistic Concurrency**
*   **Optimistic:** Assumes no conflict. Checks version/timestamp on commit. If changed, aborts. (e.g., `UPDATE ... WHERE version = old_version`).
*   **Pessimistic:** Assumes conflict. Locks row on read. (e.g., `SELECT ... FOR UPDATE`).
*   **Choice:** Optimistic for low contention (web apps). Pessimistic for high contention (banking transfers).
