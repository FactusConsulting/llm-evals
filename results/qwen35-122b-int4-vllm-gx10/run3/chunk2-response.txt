

K1 — **Deployment vs. StatefulSet**
A **Deployment** manages stateless pods with interchangeable identities (random names), supports rolling updates, and scales pods in parallel. A **StatefulSet** manages stateful applications with stable, unique network identifiers (e.g., `web-0`, `web-1`), ordered deployment/scaling, and stable persistent storage (one PV per pod). Use StatefulSet for databases or apps requiring stable network IDs and ordered startup/shutdown.

K2 — **ClusterIP Routing**
A ClusterIP Service exposes a virtual IP (VIP) internal to the cluster. `kube-proxy` runs on each node and configures `iptables` or `IPVS` rules. When traffic hits the VIP, these rules randomly select an endpoint (Pod IP) from the Service’s `Endpoints` object and DNAT (Destination NAT) the traffic to that Pod.

K3 — **PV, PVC, and StorageClass**
*   **PersistentVolume (PV):** A cluster-wide storage resource provisioned by an admin or dynamically.
*   **PersistentVolumeClaim (PVC):** A request for storage by a user (Pod). It binds to a matching PV.
*   **StorageClass:** Defines the "type" of storage (e.g., SSD, HDD) and the provisioner.
*   **Relation:** PVC requests storage -> StorageClass provisions a PV -> PVC binds to PV -> Pod mounts PVC.

K4 — **CrashLoopBackOff Troubleshooting**
1.  **Check Logs:** `kubectl logs <pod> --previous` to see why the process exited.
2.  **Check Events:** `kubectl describe pod <pod>` for OOMKilled, Liveness Probe failures, or scheduling issues.
3.  **Check Resources:** Verify memory/CPU limits aren't too low causing OOM.
4.  **Check Config:** Verify ConfigMaps/Secrets exist and environment variables are correct.

K5 — **CoreDNS Role**
CoreDNS provides DNS-based service discovery within the cluster. It resolves service names (e.g., `my-service.default.svc.cluster.local`) to Pod IPs. If CoreDNS pods are down, internal service discovery fails, and pods cannot resolve external domains unless they use external DNS directly (bypassing CoreDNS), breaking most cluster communication.

K6 — **Kubernetes Scheduler Logic**
The scheduler uses a **Filter** (Predicate) phase to remove unschedulable nodes (e.g., insufficient resources, taints), then a **Score** (Priority) phase to rank remaining nodes.
*   **Factors:** 1. Resource Requests (CPU/Mem), 2. Node Affinity/Anti-Affinity rules, 3. Taints/Tolerations, 4. Pod Topology Spread Constraints.

K7 — **Memory Scheduling & Runtime**
*   **Scheduling:** Yes, it will be scheduled. The scheduler checks **Requests** (256Mi). Node has 4GB total - 3.5GB requested = 500MB free. 256Mi < 500MB.
*   **Runtime:** If it uses 600Mi, it exceeds the **Limit** (512Mi). The kubelet will trigger an OOMKill, and the pod will restart (potentially causing CrashLoopBackOff).

K8 — **Ingress Request Lifecycle**
1.  **External LB:** Cloud provider routes traffic to the Ingress Controller Pod IP.
2.  **Ingress Controller:** NGINX pod reads Ingress Resources, matches host/path rules.
3.  **Service:** Controller forwards traffic to the target Kubernetes Service (ClusterIP).
4.  **Endpoints:** Service resolves to a list of Pod IPs.
5.  **kube-proxy:** Node-level `iptables`/`IPVS` rules DNAT traffic to the specific Pod IP.
6.  **Pod:** Traffic reaches the application container.

K9 — **NetworkPolicy**
A NetworkPolicy defines allowed ingress/egress traffic for selected pods.
*   **Default:** If no policy exists, all traffic is allowed (default allow).
*   **With Policy:** If a policy selects a pod, it becomes **default deny** for that traffic type (ingress/egress) unless explicitly allowed by rules in the policy.

K10 — **RollingUpdate vs. Recreate**
*   **RollingUpdate:** Gradually replaces pods (new version comes up before old goes down). Zero downtime.
*   **Recreate:** Terminates all existing pods before creating new ones. Downtime occurs.
*   **Choose Recreate:** When the app cannot run two versions simultaneously (e.g., incompatible database schema changes) or for stateful apps without readiness probes.

K11 — **Namespace**
A logical cluster partition for resource isolation (RBAC, quotas).
*   **Default Namespaces:** `default`, `kube-system` (control plane), `kube-public` (readable by all), `kube-node-lease` (node heartbeats).

K12 — **kubectl describe pod**
Shows detailed spec and status not in `get`.
1.  **Events:** Recent warnings/info (e.g., scheduling failures, OOM).
2.  **Conditions:** Pod status details (Ready, Initialized, ContainersReady).
3.  **Volumes/Mounts:** Which ConfigMaps/Secrets are mounted and where.

K13 — **ConfigMap**
A key-value store for non-confidential configuration data.
*   **Methods:** 1. **Environment Variables** (`envFrom` or `env`), 2. **Volume Mounts** (mount as files in the container filesystem).

K14 — **Service Types**
*   **ClusterIP:** Exposes service on an internal IP (default). Accessible only within cluster.
*   **NodePort:** Exposes service on a static port on each Node's IP. Accessible externally via `<NodeIP>:<Port>`.
*   **LoadBalancer:** Provisions an external cloud Load Balancer that routes to the NodePort.

K15 — **DaemonSet**
Ensures a copy of a Pod runs on **all** (or selected) nodes.
*   **Use Case:** Instead of Deployment, use DaemonSet for node-level agents like log collectors (Fluentd), monitoring (Node Exporter), or storage drivers (Ceph) that must run on every node.

K16 — **Taints/Tolerations vs. Affinity**
*   **Taints/Tolerations:** Taints "repel" pods; Tolerations allow pods to "tolerate" the taint. Used to dedicate nodes (e.g., GPU nodes).
*   **Node Affinity:** "Attracts" pods to nodes based on labels.
*   **Use Case:** Taint a node with `dedicated=gpu:NoSchedule`; Pod tolerates it. Use Affinity to ensure pods land on nodes with `disktype=ssd`.

K17 — **Kubernetes Operator**
An Operator is a custom controller + Custom Resource Definition (CRD) that automates the lifecycle management of complex applications.
*   **Difference:** Standard controllers manage built-in resources (Pods, Deployments). Operators manage custom resources (e.g., `PostgresCluster`).
*   **Solves:** Complex stateful logic (backups, failover, upgrades) that declarative YAML cannot express alone.

K18 — **etcd Consistency & Recovery**
*   **Model:** Strong consistency using the Raft consensus algorithm.
*   **Quorum Loss:** If quorum (majority) is lost (e.g., 2 of 3 nodes down), the cluster becomes read-only/unavailable to prevent split-brain.
*   **Recovery:** You cannot recover data from the lost nodes. You must restore the remaining node(s) from a **snapshot backup** or rebuild the cluster and restore data from backup.

K19 — **RBAC & Manifests**
*   **Role/ClusterRole:** Define permissions (verbs on resources). Role is namespace-scoped; ClusterRole is cluster-wide.
*   **RoleBinding/ClusterRoleBinding:** Bind a Role/ClusterRole to a User/Group/ServiceAccount.
*   **Manifests:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — **DNS ndots Issue**
*   **Cause:** Default `ndots:5` means if a domain has fewer than 5 dots, the resolver tries appending all search domains (e.g., `svc.cluster.local`, `cluster.local`). This causes 5+ queries for a single lookup.
*   **Fix:** Set `dnsConfig` in Pod spec: `options: [{name: ndots, value: "1"}]`. This forces immediate resolution for absolute domains or reduces search attempts.

D1 — **git rebase vs. merge**
*   **Merge:** Creates a new commit combining histories. Preserves chronological order.
*   **Rebase:** Rewrites history by moving commits to the tip of the target branch. Linear history.
*   **Avoid Rebasing:** On shared/public branches (e.g., `main`), as it rewrites history and causes conflicts for other collaborators.

D2 — **TCP vs. UDP**
*   **TCP:** Connection-oriented, reliable, ordered delivery. (Protocols: HTTP, SSH).
*   **UDP:** Connectionless, unreliable, faster, no ordering. (Protocols: DNS, VoIP/Streaming).

D3 — **Race Condition**
A bug where system behavior depends on the sequence/timing of uncontrollable events.
*   **Example:** Two threads increment a shared counter `x = x + 1` without locking. Both read `x=0`, both write `x=1`. Result is 1 instead of 2.

D4 — **Symmetric vs. Asymmetric Encryption**
*   **Symmetric:** Same key for encrypt/decrypt. Fast.
*   **Asymmetric:** Public key encrypts, Private key decrypts. Slow, used for key exchange.
*   **TLS:** Asymmetric (RSA/ECC) establishes the session and exchanges a symmetric key. Symmetric (AES) encrypts the actual data payload.

D5 — **Container Image Layers**
Images are stacked read-only filesystem layers.
*   **Layer Caching:** Docker caches layers based on instructions.
*   **Best Practice:** Order Dockerfile commands to maximize cache hits. Install dependencies (slow) before copying application code (frequent change). If code changes, dependency layer is reused.

D6 — **HTTP 503 Troubleshooting**
1.  **Check Upstream Health:** Are backend pods healthy? (Readiness probes).
2.  **Check Load Balancer:** Is the LB routing to healthy endpoints?
3.  **Check Resources:** Is the app OOMKilled or CPU throttled?
4.  **Check Logs:** Application logs for connection timeouts or dependency failures (DB down).

D7 — **CAP Theorem**
Distributed systems can only guarantee 2 of 3: **C**onsistency, **A**vailability, **P**artition Tolerance.
*   **CP Example:** Banking system (Consistency > Availability). If partitioned, reject writes to prevent double-spending.
*   **AP Example:** Social Media Feed (Availability > Consistency). If partitioned, show old posts rather than failing.

D8 — **Horizontal vs. Vertical Scaling**
*   **Vertical:** Add more resources (CPU/RAM) to a single node. Limited by hardware.
*   **Horizontal:** Add more nodes/instances.
*   **Patterns:** Stateless application design, Load Balancing, Database Sharding, Caching layers.

D9 — **Environment Variable**
A dynamic value accessible to processes.
*   **Persist:** Add `export MY_VAR=value` to `~/.bashrc` or `~/.profile` and reload shell.

D10 — **JSON vs. YAML**
*   **JSON:** Data interchange format. Strict syntax. Advantage: Easy to parse programmatically.
*   **YAML:** Human-readable data serialization. Advantage: Supports comments and indentation for readability (common in K8s).

D11 — **REST API**
Architectural style using HTTP methods to manipulate resources.
*   **GET:** Retrieve resource (Safe, Idempotent).
*   **POST:** Create resource (Not Idempotent).
*   **PUT:** Replace resource entirely (Idempotent).
*   **DELETE:** Remove resource (Idempotent).

D12 — **Version Pinning**
Locking dependencies to specific versions (e.g., `package.json` lockfile, `requirements.txt`).
*   **Importance:** Ensures reproducible builds. Prevents "it works on my machine" issues caused by upstream library updates breaking code.

D13 — **Compiled vs. Interpreted**
*   **Compiled:** Source code translated to machine code before execution. (Examples: C++, Go). Faster runtime.
*   **Interpreted:** Source code executed line-by-line by a runtime. (Examples: Python, JavaScript). Faster development iteration.

D14 — **Reverse vs. Forward Proxy**
*   **Forward Proxy:** Client -> Proxy -> Internet. Hides client identity.
*   **Reverse Proxy:** Client -> Proxy -> Server. Hides server identity, handles SSL, Load Balancing.
*   **Servers:** Nginx (Web Server/LB), HAProxy (High-performance TCP/HTTP LB).

D15 — **Deadlock**
A situation where processes wait indefinitely for resources held by each other.
*   **Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait. All must hold simultaneously.

D16 — **Eventual Consistency**
Data updates propagate asynchronously; all replicas will converge to the same value eventually.
*   **Cassandra:** Uses tunable consistency.
*   **Levels:** `ONE` (fastest, least consistent), `QUORUM` (balance), `ALL` (slowest, strongest). Read-after-write consistency is achieved by setting read consistency >= write consistency.

D17 — **mTLS (Mutual TLS)**
Both client and server authenticate each other using certificates.
*   **Handshake:** 1. Server sends cert. 2. Client verifies server. 3. Client sends cert. 4. Server verifies client. 5. Secure channel established.
*   **Use Case:** Service-to-service communication in Service Meshes (Istio), API Gateways requiring client auth.

D18 — **Hash Table Internals**
*   **Mechanism:** Key is hashed to an index in an array.
*   **Collision Resolution:**
    *   **Chaining:** Array slots point to linked lists of entries.
    *   **Open Addressing:** Find next available slot via probing (linear/quadratic).
*   **Complexity:** Average O(1) for insert/lookup/delete. Worst Case O(n) (all keys collide).

D19 — **Circuit Breaker Pattern**
Prevents cascading failures by stopping calls to a failing service.
*   **States:**
    1.  **Closed:** Normal operation.
    2.  **Open:** Fail fast immediately (no calls sent) after threshold errors.
    3.  **Half-Open:** Allow limited test requests. If success -> Close; If fail -> Open.
*   **Relation:** Works with Retry policies. Circuit breaker prevents retries from overwhelming a failing service (Retry Storm).

D20 — **Optimistic vs. Pessimistic Concurrency**
*   **Optimistic:** Assume no conflict. Check version/timestamp at commit. If changed, rollback/retry. (Feature: Row Versioning).
*   **Pessimistic:** Assume conflict. Lock row on read. (Feature: `SELECT FOR UPDATE`).
*   **Choice:** Optimistic for high read/low write (web apps). Pessimistic for high contention (banking transfers).
