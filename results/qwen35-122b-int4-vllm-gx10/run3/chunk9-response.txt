

SC1-A
**Root Cause:** The failure stems from a conflict between the **Restricted Pod Security Standard (PSS)** and the container image's default user.
1.  **PSS Interaction:** The `Restricted` profile enforces `runAsNonRoot: true`. This means the container *must* run as a non-root user (UID != 0).
2.  **Image Directive:** The new base image (`cgr.dev/chainguard/static:latest`) sets `USER root` in its Dockerfile.
3.  **Manifest Deficit:** The pod spec sets `securityContext.runAsNonRoot: true` but does not explicitly set `securityContext.runAsUser`.
4.  **The Conflict:** When Kubernetes attempts to start the pod, it sees `runAsNonRoot: true`. However, because `runAsUser` is unset, the kubelet defaults to the image's `USER` directive (root/UID 0). This violates the `runAsNonRoot` constraint enforced by the PSS admission controller (or the kubelet enforcement in newer versions), causing the pod to fail admission or crash immediately upon startup.
5.  **Upgrade Impact:** The cluster upgrade likely enforced the `Restricted` PSS more strictly or changed the default behavior of the admission controller compared to the previous `Baseline` level, which allowed root execution.

SC1-C
**Remediation Strategy:**
1.  **Immediate Fix:** Update the pod manifests to explicitly set `securityContext.runAsUser: 1000` (or a non-root UID) and `runAsGroup: 1000`. Ensure the container image is rebuilt with `USER 1000` in the Dockerfile.
2.  **CI Pipeline Gate:** Add a step in the CI pipeline to scan the Dockerfile for `USER root` and reject the build. Integrate a PSS validator (e.g., `kube-score` or `checkov`) to validate manifests against the target PSS profile before merging.
3.  **Rollout:** Use a **Canary Deployment** strategy. Deploy the fixed manifests to a subset of namespaces first. Monitor for CrashLoopBackOff reduction. Once stable, roll out to all namespaces using a rolling update strategy (`kubectl rollout restart`) to ensure zero downtime.
4.  **Prevention:** Enforce PSS at the namespace level via `PodSecurity` admission controller labels (`pod-security.kubernetes.io/enforce: restricted`) to prevent future regressions.

SC2-A
**Stale Data & Replication Lag:**
1.  **Implication:** Cross-region read replicas typically use **asynchronous replication**. When the primary (us-east-1) fails, the replica (eu-west-1) may not have received the latest Write-Ahead Log (WAL) records. Promoting it results in data loss for transactions committed on the primary but not yet shipped to the replica.
2.  **WAL Shipping:** PostgreSQL ships WAL segments via streaming replication. In cross-region setups, network latency (85ms) and bandwidth constraints cause lag.
3.  **Data Loss:** Any transaction committed on the primary after the last WAL segment received by the replica is lost.
4.  **Quantification:** Check `pg_stat_replication` on the primary (before failure) for `sent_lsn`, `write_lsn`, and `flush_lsn`. On the replica, check `pg_last_wal_receive_lsn` and `pg_last_wal_replay_lsn`. The difference between the primary's `current_wal_lsn` and the replica's `pg_last_wal_replay_lsn` at the time of failure quantifies the data loss window.

SC2-C
**Future Architecture:**
1.  **Connection Management:** Use **RDS Proxy** instead of PgBouncer. RDS Proxy handles connection pooling, failover transparency, and IAM authentication, reducing the load on the DB during failover.
2.  **DNS Failover:** Configure **Route53 Health Checks** on the primary endpoint. Use Failover Routing Policy to automatically switch DNS records to the replica endpoint upon primary failure.
3.  **Application Logic:** Implement **retry logic with exponential backoff** in the application to handle transient connection errors during the failover window.

5.  **Recommendation:** **Aurora Global Database** is recommended. It decouples compute from storage, allows faster failover (typically < 1 minute), and maintains lower replication lag, directly addressing the RPO requirement.

SC4-A
**Top 5 Blockers & Solutions:**
1.  **Sticky Sessions (F5):** K8s pods are ephemeral; sticky sessions break state. **Solution:** Move session state to an external Redis cluster and use K8s Service `sessionAffinity: ClientIP` only as a fallback.
2.  **Local NFS Mount:** Pods are stateless; local mounts don't persist across restarts. **Solution:** Use a **ReadWriteMany (RWX)** PersistentVolume (e.g., EFS or NFS CSI) mounted at `/data/uploads`.
3.  **Oracle 19c On-Prem:** Network latency and licensing. **Solution:** Migrate to **Amazon RDS for Oracle** or **Aurora Oracle-compatible** to decouple from on-prem hardware.
4.  **IBM MQ:** Legacy protocol integration. **Solution:** Use **Amazon MQ for IBM MQ** or a Kubernetes Operator for IBM MQ to maintain compatibility without on-prem dependencies.
5.  **Stateful Sessions:** App stores sessions in memory. **Solution:** Refactor to use **externalized session storage** (Redis) to allow horizontal scaling and pod replacement.

SC6-C
**VPN Upgrade Comparison:**
1.  **AWS Direct Connect:**
    *   **Pros:** High bandwidth (10Gbps+), low latency, dedicated connection.
    *   **Cons:** High cost, long lead time.
    *   **Zero-Trust:** Fits well; traffic stays on private backbone.
    *   **Routing:** Requires BGP configuration on TGW.
2.  **ECMP (2 VPN Tunnels):**
    *   **Pros:** Cost-effective, immediate.
    *   **Cons:** Still limited by IPsec overhead, potential jitter.
    *   **Zero-Trust:** Same encryption, but shared public internet path.
    *   **Routing:** Requires BGP on both tunnels.
3.  **Tailscale/Netbird:**
    *   **Pros:** Easy setup, mesh networking, NAT traversal.
    *   **Cons:** Overlay network overhead, dependency on control plane.
    *   **Zero-Trust:** Excellent (mTLS, identity-based).
    *   **Routing:** No BGP needed; uses virtual interfaces.
**Recommendation:** **Direct Connect** for production stability and bandwidth, combined with **Tailscale** for management plane access (Zero-Trust admin access).

SC10-C
**Failover Orchestration:**
1.  **Detection:** **Prometheus Alertmanager** monitors site health (heartbeat). If Chicago > 30s down, trigger failover.
2.  **DNS:** **GSLB** (Global Server Load Balancing) switches DNS TTL to Dallas.
3.  **Patroni:** **Patroni** detects leader loss, promotes Dallas standby (sync mode ensures no data loss).
4.  **Redis:** **Sentinel** promotes new master in Dallas.
5.  **RabbitMQ:** **Federation** links ensure queues are mirrored; Dallas takes over.
6.  **MinIO:** **Site Replication** catches up asynchronously.
7.  **ToFu:** Update state file to reflect Dallas as primary (manual or automated via API).
8.  **Split-Brain:** Use **Quorum** (etcd) to prevent two primaries. If Chicago recovers, it becomes a **Standby** automatically.
9.  **Failback:** Once Chicago is stable, re-sync data, then switch DNS back. Run `tofu apply` to restore Chicago as primary.
