

AA1 — **Monolith vs. Microservices:** A monolith is a single deployable unit where all components are tightly coupled. Microservices decompose the application into loosely coupled, independently deployable services.
**3 Microservice Problems:**
1.  **Distributed Transactions:** Maintaining data consistency across services requires complex patterns (Saga) instead of local ACID transactions.
2.  **Network Latency & Reliability:** Inter-service communication introduces network overhead and failure modes (timeouts, partial failures) not present in in-process calls.
3.  **Operational Complexity:** Requires orchestration (Kubernetes), centralized logging, tracing, and service discovery infrastructure.

AA2 — **Sync vs. Async:**
*   **Synchronous:** The caller waits for a response before proceeding. Example: **HTTP/REST** or **gRPC**.
*   **Asynchronous:** The caller sends a request and continues without waiting; the response is handled later via callback or polling. Example: **RabbitMQ** (AMQP) or **Kafka**.

AA3 — **API Gateway vs. Reverse Proxy:**
*   **Reverse Proxy:** Routes traffic based on IP/Port/Path, handles SSL termination, and load balancing (e.g., Nginx).
*   **API Gateway:** Adds business logic layer: authentication, rate limiting, request transformation, and API versioning (e.g., Kong, Apigee).
*   **Replacement:** An API Gateway can replace a reverse proxy functionally, but it adds overhead. For simple internal routing, a lightweight reverse proxy is often preferred for performance.

AA4 — **Saga Pattern:** A sequence of local transactions where each updates data within a single service. If a step fails, compensating transactions undo previous changes.
*   **Choreography:** Services emit events; others react. Good for simple workflows; hard to trace.
*   **Orchestration:** A central coordinator tells services what to do. Good for complex workflows; easier to manage state.
*   **Appropriateness:** Use Choreography for decoupled, simple flows. Use Orchestration for critical business processes requiring visibility and control.

AA5 — **CQRS:** Separates read (Query) and write (Command) models.
*   **Pairing with Event Sourcing:** Event Sourcing stores state changes as a log of events. CQRS uses this log to build optimized read projections.
*   **Problem Solved:** Traditional CRUD couples read/write schemas, causing contention and scaling limits. CQRS/ES allows independent scaling of reads and writes and provides a full audit trail.

AA6 — **Circuit Breaker:** Prevents cascading failures by stopping requests to a failing service.
*   **States:** **Closed** (normal), **Open** (fail fast), **Half-Open** (test recovery).
*   **Differs from Retry:** Retry attempts to fix transient errors; Circuit Breaker stops traffic to allow the downstream service to recover.
*   **Usage:** Use both. Retry for transient network glitches; Circuit Breaker for persistent downstream failures.

AA7 — **Multi-Tenant Isolation:**
1.  **Shared DB, Shared Schema:** *Cost:* Low. *Security:* Low (row-level security bugs). *Ops:* Easy. *Noisy Neighbor:* High.
2.  **Shared DB, Separate Schema:** *Cost:* Medium. *Security:* Medium (schema isolation). *Ops:* Medium (migration complexity). *Noisy Neighbor:* Medium.
3.  **Separate DB:** *Cost:* High. *Security:* High (physical isolation). *Ops:* High (provisioning). *Noisy Neighbor:* None.
*   **Recommendation:** Start with Shared Schema for cost; move to Separate DB for enterprise/regulated tenants.

AA8 — **Consistency Models:**
*   **Eventual:** Data converges over time (high availability).
*   **Strong:** All nodes see the same data at the same time (high consistency).
*   **Inventory Architecture:** Requires **Strong Consistency**. Use a relational database (PostgreSQL) with **Optimistic Locking** or **Pessimistic Locking** on stock rows. At scale, use **Sharding** by product ID or a distributed lock manager (e.g., Redis Redlock) to prevent overselling during concurrent updates.

AA9 — **Sidecar Proxy:** A helper container deployed alongside the application container to handle network traffic.
*   **Envoy/Istio:** Envoy handles the data plane (traffic); Istio Pilot/Control Plane configures Envoy.
*   **Data Plane:** Proxies handling actual traffic. **Control Plane:** Manages configuration and policies.
*   **mTLS:** Encrypts traffic between services automatically. Solves the problem of managing certificates and auth in every application codebase; ensures zero-trust network security.

AA10 — **Strangler Fig:** Incrementally migrate functionality by routing traffic to new services while keeping the legacy system running.
*   **Strategy:** Place a reverse proxy (e.g., Nginx) in front of the .NET Framework monolith. Route specific paths (e.g., `/api/v2/*`) to new .NET 8 microservices. Gradually move more paths until the monolith is "strangled" and can be decommissioned.

AA11 — **12-Factor App:** Methodology for building SaaS apps.
1.  **Codebase:** One codebase tracked in VCS.
2.  **Dependencies:** Explicitly declare dependencies.
3.  **Config:** Store config in environment variables.
4.  **Backing Services:** Treat services (DB, Queue) as attached resources.
5.  **Build/Release/Run:** Strict separation of stages.
6.  **Processes:** Execute app as one or more stateless processes.
*   **Importance:** Ensures portability, scalability, and reproducibility in cloud environments.

AA12 — **Event-Driven (Kafka) vs. Request-Driven (REST/gRPC):**
*   **Coupling:** Kafka (Loose), REST (Tight).
*   **Scalability:** Kafka (High, async buffering), REST (Limited by request latency).
*   **Debugging:** Kafka (Hard, replay logs), REST (Easy, request/response logs).
*   **Ordering:** Kafka (Partition-level), REST (None).
*   **Failure:** Kafka (Retry/Dead Letter), REST (Immediate error).
*   **Choice:** Use REST for synchronous user-facing APIs. Use Kafka for background processing, audit trails, and decoupling complex workflows.

AA13 — **Load Balancer:** Distributes network traffic across servers.
*   **Layer 4:** Transports (TCP/UDP). Fast, unaware of content.
*   **Layer 7:** Application (HTTP). Can route based on URL, headers, cookies.
*   **Use Case:** Layer 7 is required for **path-based routing** (e.g., `/api` to backend, `/static` to CDN) or **SSL Termination**.

AA14 — **Message Queue vs. Log Broker:**
*   **Queue (RabbitMQ):** Messages are deleted after consumption. Competing consumers. Good for task distribution.
*   **Log (Kafka):** Messages are persisted and replayable. Multiple independent consumers. Good for event sourcing/streaming.
*   **Pick:** Queue for work distribution (emails, jobs). Log for data pipelines and state reconstruction.

AA15 — **Container vs. VM:**
*   **Container:** Shares the host OS kernel; isolates user space. Lightweight, fast startup.
*   **VM:** Virtualizes hardware; runs a full guest OS. Heavy, slower startup.
*   **Popularity:** Containers are preferred for microservices due to density, portability, and CI/CD integration.

AA16 — **Stateless vs. Stateful:**
*   **Stateless:** No client data stored on the server (e.g., API Gateway).
*   **Stateful:** Server retains client session/state (e.g., Database).
*   **Scaling:** Stateless services can be scaled horizontally by simply adding instances behind a load balancer. Stateful services require complex data replication/sharding.

AA17 — **ORM:** Maps objects to database tables.
*   **Examples:** **Hibernate** (Java), **Entity Framework** (.NET).
*   **Trade-offs:** ORM speeds development and abstracts SQL dialects. Raw SQL offers better performance, fine-grained control, and easier debugging of complex queries.

AA18 — **Bulkhead Pattern:** Isolates resources to prevent a failure in one part of the system from affecting others.
*   **Relation:** Like ship bulkheads; if one compartment floods, the ship stays afloat.
*   **Implementation:** Assign separate **thread pools** per service dependency. If one dependency hangs, its thread pool exhausts, but others remain available. Alternatively, deploy critical services in separate Kubernetes namespaces/instances.

AA19 — **OT vs. CRDT:**
*   **OT:** Server-centric. Operations are transformed against server state. Requires constant connectivity.
*   **CRDT:** Mathematically guaranteed convergence. Works peer-to-peer.
*   **Comparison:** OT has lower latency for real-time but requires server mediation. CRDT supports offline editing naturally but has higher complexity and memory overhead.
*   **Choice:** **CRDTs** for offline support. They allow local edits to merge automatically upon reconnection without server conflict resolution logic.

AA20 — **Distributed Tracing:**
*   **Challenges:** Polyglot languages, async boundaries, high volume.
*   **Context:** Propagate via **W3C Trace Context** headers.
*   **Sampling:** **Head-based** (decide at start) vs. **Tail-based** (decide after seeing errors). Tail-based is better for debugging.
*   **Storage:** Jaeger/Tempo (Hot/Warm/Cold tiers).
*   **Kafka:** Inject Trace ID into message headers. Consumers extract headers to continue the trace span, ensuring continuity across async boundaries.

OP1 — **Hypervisors:**
*   **Type 1 (Bare-metal):** Runs directly on hardware. Examples: **VMware ESXi, Microsoft Hyper-V**.
*   **Type 2 (Hosted):** Runs on top of an OS. Examples: **Oracle VirtualBox, VMware Workstation**.
*   **Use:** Type 1 for production servers; Type 2 for development/testing.

OP2 — **SAN vs. NAS:**
*   **SAN:** Block-level storage. Protocol: **Fibre Channel, iSCSI**. Use for databases requiring low latency.
*   **NAS:** File-level storage. Protocol: **NFS, SMB/CIFS**. Use for file sharing and backups.

OP3 — **3-Tier vs. Leaf-Spine:**
*   **3-Tier:** Core, Distribution, Access. High latency for East-West traffic (server-to-server).
*   **Leaf-Spine:** Every leaf connects to every spine. Constant latency (2 hops).
*   **Problem Solved:** Leaf-spine eliminates bottlenecks in modern data centers where server-to-server traffic (East-West) exceeds client-to-server (North-South).

OP4 — **Proxmox HA:**
*   **Architecture:** 3 nodes minimum for quorum.
*   **Storage:** Ceph (integrated) or iSCSI/NFS.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) to prevent split-brain.
*   **Failure:** If a node fails, the cluster detects loss of quorum (if >1 fails) or restarts VMs on remaining nodes via HA manager.

OP5 — **VLAN Trunking:**
*   **Concept:** Carrying multiple VLANs over a single link.
*   **802.1Q:** Adds a 4-byte tag to Ethernet frames with VLAN ID.
*   **Linux Config:** Create sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`. Assign IPs to `eth0.10`, `eth0.20`, etc.

OP6 — **RAID Levels:**
*   **RAID 1:** Mirror (50% capacity).
*   **RAID 5:** Striping + Parity (N-1 capacity).
*   **RAID 6:** Double Parity (N-2 capacity).
*   **RAID 10:** Mirror + Stripe (50% capacity, high perf).
*   **RAID Z2:** ZFS equivalent of RAID 6.
*   **Choice:** **RAID 10** for 6 drives DB. Better write performance than RAID 5/6, survives 1 drive failure per mirror pair (potentially 2), and rebuilds faster.

OP7 — **DNS Architecture:**
*   **Internal:** AD-integrated DNS for internal resolution.
*   **External:** Authoritative servers in DMZ (e.g., Route53, Bind).
*   **Split-Horizon:** Internal clients resolve `corp.com` to private IPs; external resolve to public.
*   **Security:** DNSSEC on external zone. Forwarders for internet queries.
*   **Laptop Move:** DHCP updates DNS records (DDNS). If on VPN, DNS suffix search list changes to route queries correctly.

OP8 — **PKI Chain:**
*   **Chain:** Root CA (Offline) -> Subordinate CA (Issuing) -> End Entity (Server/User).
*   **Validation:** CRL (List of revoked certs) vs. OCSP (Real-time check).
*   **Templates:** Define key usage/validity for different roles.
*   **Compromise:** Sub CA compromised = Revoke Sub CA cert, reissue end-entity certs. Root CA compromised = Revoke Root, rebuild entire PKI infrastructure (catastrophic).

OP9 — **WAN Consolidation:**
*   **MPLS:** High cost, high reliability, low latency.
*   **IPsec:** Low cost, variable latency (internet dependent).
*   **SD-WAN:** Intelligent path selection, cost-effective, manages multiple links.
*   **WireGuard:** Simple, fast, but lacks enterprise management features.
*   **Recommendation:** **SD-WAN**. Balances cost and performance, prioritizes VoIP traffic dynamically over internet links, and simplifies management for 5 sites.

OP10 — **iDRAC/iLO/IPMI:**
*   **Definition:** Out-of-band (OOB) management interfaces for hardware control (power, BIOS, console).
*   **Criticality:** Allows management when OS is down or network is unreachable.
*   **Risk:** Exposed to internet = attackers gain root access to hardware. Must be on isolated management network with strict firewall rules.

OP11 — **LVM vs. ZFS:**
*   **LVM:** Logical Volume Manager (Linux). Block level. Snapshots are copy-on-write but require space.
*   **LVM-Thin:** Allows over-provisioning of volumes.
*   **ZFS:** Combined filesystem and volume manager. Copy-on-write, built-in checksums, compression.
*   **Snapshots:** LVM (instant, space efficient with thin). ZFS (instant, space efficient, recursive).
*   **Use:** LVM for general Linux VMs. ZFS for storage pools requiring data integrity and advanced features.

OP12 — **Stretch Cluster/DR:**
*   **Design:** 2 sites + 1 Witness node (quorum).
*   **Ceph:** CRUSH rules must prevent data placement on the same site for redundancy.
*   **Latency:** < 5ms RTT required for synchronous replication.
*   **Split-Brain:** If link fails, sites may both think they are primary.
*   **Tiebreaker:** Witness node decides quorum.
*   **Warning:** 2-site Ceph without witness risks split-brain. Generally, asynchronous replication to a DR site is safer than stretch clusters for high latency.

OP13 — **DHCP:**
*   **Process:** **D**iscover (Client), **O**ffer (Server), **R**equest (Client), **A**ck (Server).
*   **Unavailable:** Client uses **APIPA** (169.254.x.x) if lease expires and no server is found. Connectivity limited to local subnet.

OP14 — **Managed vs. Unmanaged Switch:**
*   **Unmanaged:** Plug-and-play, no configuration.
*   **Managed:** Configurable via CLI/Web.
*   **Features:** VLANs, QoS, SNMP monitoring, Port Security, STP. Essential for enterprise segmentation and troubleshooting.

OP15 — **NTP:**
*   **Definition:** Network Time Protocol.
*   **Criticality:** Logs correlation, Kerberos authentication (5 min drift limit), Database consistency.
*   **Drift:** Causes auth failures, data corruption in distributed DBs, and broken security certificates.

OP16 — **Physical vs. VM vs. Container:**
*   **Physical:** Bare metal hardware.
*   **VM:** Virtualized OS.
*   **Container:** Virtualized User Space.
*   **Bare Metal:** High-performance workloads (HPC, High-frequency trading, large DBs) where virtualization overhead is unacceptable.

OP17 — **UPS vs. Generator:**
*   **UPS:** Battery backup for immediate power loss (seconds/minutes).
*   **Generator:** Fuel-powered for long-term outages (hours/days).
*   **ATS:** Automatically switches power source from Utility to Generator when utility fails.
*   **Need Both:** UPS bridges the gap between utility failure and generator startup.

OP18 — **Active-Passive vs. Active-Active:**
*   **Active-Passive:** One node serves, one waits.
*   **Active-Active:** Both nodes serve traffic.
*   **PostgreSQL HA:** Use **Pacemaker/Corosync**.
*   **Fencing:** STONITH device to power off failed node to prevent data corruption.
*   **VIP:** Virtual IP floats to the active node.
*   **Failover:** Automatic promotion of standby to primary upon detection of failure.

OP19 — **Backup Strategy:**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Define max data loss and max downtime.
*   **Types:** Full (baseline), Incremental (changes since last), Differential (changes since full).
*   **Protection:** Immutable backups (WORM) prevent ransomware encryption.
*   **Test:** Regular restore drills.
*   **Backup vs. DR:** Backup restores data; DR restores the entire service environment (infrastructure + data).

OP20 — **802.1X:**
*   **Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
*   **EAP:** EAP-TLS (Cert-based, secure) vs. PEAP (Password-based).
*   **Dynamic VLAN:** RADIUS assigns VLAN ID upon success.
*   **Fail:** Port blocked or assigned to Guest VLAN.
*   **MAB:** Falls back to MAC address authentication for devices without 802.1X supplicants (printers, IoT).
