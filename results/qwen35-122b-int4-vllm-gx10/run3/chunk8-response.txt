

CL1 — **IaaS vs PaaS vs SaaS:**
*   **IaaS (Infrastructure as a Service):** Provides virtualized computing resources (VMs, storage, networking). You manage OS, middleware, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a managed environment for developing, running, and managing applications. You manage code and data; provider manages runtime/OS. *Example: AWS RDS or Azure App Service.*
*   **SaaS (Software as a Service):** Delivers fully managed software applications over the internet. You manage user access and data; provider manages everything else. *Example: Microsoft 365 or Salesforce.*

CL2 — **Shared Responsibility Model:**
*   **Concept:** Security "of" the cloud (Provider) vs. Security "in" the cloud (Customer).
*   **IaaS VMs:** Provider secures physical hardware, hypervisor, and network infrastructure. Customer secures Guest OS, patches, firewall rules, and data.
*   **Managed Kubernetes:** Provider secures control plane, worker node infrastructure, and API server. Customer secures worker node OS (if self-managed), pod security, network policies, and application code.
*   **SaaS (M365):** Provider secures the application, infrastructure, and compliance. Customer secures user identities, access management, and data classification.

CL3 — **VPC, Subnet, SG, NACL:**
*   **VPC:** Virtual network boundary (IP range).
*   **Subnet:** Segment of VPC IP range, tied to an Availability Zone.
*   **Security Group (SG):** Virtual firewall at the *instance* level. **Stateful** (returns traffic allowed automatically).
*   **NACL:** Virtual firewall at the *subnet* level. **Stateless** (must explicitly allow return traffic).
*   **Layering:** Traffic flows VPC → Subnet (NACL Inbound) → Instance (SG Inbound) → App. Return path reverses through SG (allowed) → NACL (explicitly allowed).

CL4 — **Multi-Account Strategy:**
*   **Landing Zone:** Pre-configured, secure multi-account environment (networking, identity, logging).
*   **OUs:** Organizational Units group accounts by function (Prod, Dev, Security).
*   **Guardrails:** SCPs (Service Control Policies) enforce limits (e.g., no root access, specific regions).
*   **Shared Networking:** AWS Transit Gateway or Azure Hub-and-Spoke connects VPCs/VNets centrally.
*   **Centralized Logging:** All accounts ship logs to a dedicated Security/Logging account (S3/CloudWatch).
*   **Single Account Risk:** High blast radius, billing complexity, difficulty isolating environments, security policy conflicts.

CL5 — **Infrastructure as Code (IaC):**
*   **Concept:** Managing infrastructure via declarative code files rather than manual UI.
*   **Terraform/OpenTofu:** Multi-cloud, stateful, large ecosystem. Choose for portability.
*   **Pulumi:** Uses general-purpose languages (Python, Go). Choose for complex logic/teams with dev skills.
*   **CloudFormation/Bicep:** Native to AWS/Azure. Choose for deep native integration and cost (no extra tooling).
*   **Crossplane:** Kubernetes-native IaC. Choose if managing cloud resources via K8s API.

CL6 — **Kubernetes Autoscaling:**
*   **HPA:** Scales pods based on CPU/Memory or custom metrics.
*   **VPA:** Adjusts pod resource requests/limits (requires restart).
*   **Cluster Autoscaler:** Adds/removes nodes based on pending pods.
*   **KEDA:** Event-driven autoscaling (e.g., queue depth, cron).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external events (e.g., SQS queue length) rather than pod resource utilization.

CL7 — **Disaster Recovery (DR) Strategy:**
*   **RPO/RTO:** Define max data loss (RPO) and max downtime (RTO).
*   **Active-Active:** Traffic routed to both regions. High cost, lowest RTO.
*   **Active-Passive:** Primary region active, secondary standby. Lower cost, higher RTO.
*   **DB Replication:** Sync (strong consistency, latency impact) vs Async (performance, potential data loss).
*   **DNS Failover:** Route53 Health Checks/Traffic Manager route traffic on failure.
*   **State:** Use stateless app design; store state in replicated DB/Object Store.
*   **DR Types:**
    *   *Pilot Light:* Minimal core (DB) running; scale up on failover.
    *   *Warm Standby:* Scaled-down version running; scale up on failover.
    *   *Multi-site:* Full capacity in both; load balanced.

CL8 — **GitOps:**
*   **Model:** Git repository is the single source of truth. Controller syncs cluster state to Git state.
*   **ArgoCD vs Flux:** ArgoCD (UI-focused, App of Apps, easier for teams). Flux (CLI-focused, lightweight, CNCF standard).
*   **Secrets:** Never store plain text. Use Sealed Secrets (encrypted in Git), External Secrets Operator (fetch from Vault/AWS Secrets Manager), or Vault Agent Injector.
*   **Drift:** GitOps controller detects manual changes and automatically reconciles (overwrites) them to match Git state.

CL9 — **Stateful K8s Migration:**
*   **StatefulSet:** Ensures stable network IDs and ordered deployment/scaling.
*   **PV/PVC:** Use `local` storage class for low latency (node-attached disks).
*   **Headless Service:** `clusterIP: None` for stable DNS names (pod-0.service).
*   **Init Containers:** Run before main app to prepare filesystem/config.
*   **ConfigMap:** Mount as volume to specific paths (read-only).
*   **PDB:** Prevents voluntary disruptions from taking down all pods simultaneously.
*   **Sticky Sessions:** Use `sessionAffinity: ClientIP` on Service if app requires it (though app-level session is preferred).

CL10 — **Identity in K8s:**
*   **Service Account (SA):** K8s identity for pods.
*   **Workload Identity:** Cloud IAM identity bound to K8s SA (e.g., Azure Workload Identity).
*   **IRSA:** AWS specific (IAM Roles for Service Accounts).
*   **Bad Practice:** Mounting long-lived cloud credentials (Access Keys) in pods risks leakage if pod is compromised.
*   **Solution:** Workload Identity Federation exchanges K8s SA token for short-lived cloud tokens via OIDC.

CL11 — **Storage Types:**
*   **Object (S3/Blob):** Unstructured data (images, logs). High durability (11x9s). Use for backups, static assets.
*   **Block (EBS/Managed Disk):** Raw volume for VMs/DBs. Low latency. Use for OS disks, databases.
*   **File (EFS/Azure Files):** Shared filesystem (NFS/SMB). Use for shared config, content management.
*   **Guarantees:** Object storage typically offers 99.999999999% durability; Block/File depends on replication config (Multi-AZ).

CL12 — **Zero Trust K8s:**
*   **Network Policies:** Default deny all ingress/egress; allow only specific paths.
*   **Service Mesh:** Enforce mTLS between services (Istio/Linkerd).
*   **Pod Identity:** Use Workload Identity (no secrets in env vars).
*   **Admission Controllers:** OPA/Kyverno to enforce policies (e.g., no root containers).
*   **Image Signing:** Cosign/Notary to verify image provenance.
*   **Runtime Security:** Falco to detect anomalous behavior (e.g., shell in container).
*   **Diff:** Traditional relies on perimeter firewall; Zero Trust assumes breach and verifies every request/identity.

CL13 — **CDN:**
*   **Concept:** Distributed network of edge servers caching content closer to users.
*   **Mechanism:** User requests DNS → CDN resolves to nearest edge → Edge serves cache or fetches from Origin.
*   **Services:** AWS CloudFront, Azure CDN.
*   **Use Case:** Static assets (JS, CSS, Images), global latency reduction.
*   **Direct Origin:** Dynamic content, private data, or low-traffic internal apps.

CL14 — **Regions and AZs:**
*   **Region:** Geographic area (e.g., us-east-1).
*   **AZ:** Isolated data center within a region (power/network independent).
*   **Multi-AZ:** Deploy across AZs for High Availability (HA) against data center failure.
*   **Zonal Resource:** Tied to one AZ (e.g., specific VM, Local PV).
*   **Regional Resource:** Available across all AZs in region (e.g., S3, IAM, Route53).

CL15 — **Managed Database:**
*   **Service:** RDS, Cloud SQL, Azure SQL.
*   **Provider Handles:** Hardware provisioning, OS patching, DB engine patching, backups, replication, failover.
*   **Customer Handles:** Database schema, data management, user access, parameter tuning, connection security.

CL16 — **Cloud Identity:**
*   **Users:** Individual identities.
*   **Groups:** Collections of users for easier policy assignment.
*   **Roles:** Identities assumed by users/services (temporary credentials).
*   **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Grant only permissions necessary for the specific task. Apply by attaching minimal policies to Roles/Groups, avoiding `*` wildcards.

CL17 — **Serverless:**
*   **Concept:** Event-driven compute without managing servers.
*   **Comparison:** AWS Lambda (broad ecosystem), Azure Functions (Microsoft stack), GCP Functions (Google stack).
*   **Cold Start:** Latency incurred when initializing a new container instance. Matters for latency-sensitive apps.
*   **Poor Fit:** Long-running processes (>15 mins), stateful apps, consistent high load (can be more expensive than VMs), strict compliance requiring specific OS control.

CL18 — **Kubernetes Ingress:**
*   **Ingress Resource:** L7 routing, requires Ingress Controller (Nginx). TLS termination at Controller.
*   **Gateway API:** Standardized L4/L7 API, more flexible. TLS termination at Gateway.
*   **CLB Annotations:** Cloud Load Balancer directly exposes Service. TLS at LB.
*   **Service Mesh:** Ingress Gateway (Envoy). TLS at Mesh Gateway.
*   **Gateway API vs Ingress:** Use Gateway API for future-proofing, multi-cluster, and advanced traffic splitting (canary).

CL19 — **Cost Optimization ($80k/mo):**
*   **Compute:** Reserved Instances/Savings Plans (commit 1-3 yrs) for baseline; Spot Instances for fault-tolerant batch.
*   **Right-sizing:** Analyze CPU/Mem usage; downsize over-provisioned resources.
*   **Storage:** S3 Intelligent-Tiering (auto-move to Archive); delete unattached EBS volumes.
*   **Idle Detection:** Tagging strategy; alert on unused IPs/Load Balancers.
*   **FinOps:** Culture of accountability. Showback (reporting) vs Chargeback (billing).
*   **Tools:** AWS Cost Explorer, Kubecost (K8s), CloudHealth. Process: Monthly review meetings with team leads.

CL20 — **Multi-Cloud Strategy:**
*   **Abstraction:** Use Kubernetes (EKS/AKS/GKE) as common runtime.
*   **IaC:** Terraform for portability (avoid CloudFormation/Bicep lock-in).
*   **Networking:** Cloud Interconnect/VPN for hybrid connectivity.
*   **Identity:** Centralized IdP (Okta/Azure AD) federated to all clouds.
*   **Trade-offs:** Complexity increases (2x tooling, 2x skills).
*   **Justified:** Regulatory requirements, geo-redundancy, negotiating leverage.
*   **Unnecessary:** If one cloud meets 95% needs; multi-cloud often adds cost/complexity without proportional benefit.

OT1 — **Purdue Model (ISA-95):**
*   **Level 0:** Physical Process (Sensors/Actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Supervisory (HMI, SCADA).
*   **Level 3:** Operations Management (MES, Historian).
*   **Level 4:** Business Planning (ERP, IT).
*   **Level 5:** Enterprise Network (External).

OT2 — **IT vs OT:**
*   **IT:** Prioritizes Confidentiality > Integrity > Availability.
*   **OT:** Prioritizes Safety > Availability > Integrity > Confidentiality.
*   **Patching:** OT systems often run legacy OS (WinXP/7) or proprietary firmware. Patching can cause downtime or incompatibility, risking safety/production.

OT3 — **IDMZ (Industrial DMZ):**
*   **Role:** Buffer zone between IT (Level 4) and OT (Level 1-3).
*   **Traffic:** Allowed: OT → IT (Read-only data push). Blocked: IT → OT (No direct access).
*   **Danger:** Direct L4-L1 allows lateral movement from corporate network to critical control systems, risking safety shutdowns.

OT4 — **OT Protocols:**
*   **Modbus TCP:** L1/L2 (Simple, legacy).
*   **OPC UA:** L2/L3 (Secure, platform-independent).
*   **EtherNet/IP (CIP):** L1 (Industrial Ethernet).
*   **PROFINET:** L1 (Real-time Ethernet).
*   **MQTT:** L3/L4 (Lightweight publish-subscribe for telemetry).

OT5 — **Data Diode vs Firewall:**
*   **Data Diode:** Hardware-enforced one-way data flow (Optical).
*   **Firewall:** Software/Logic-based bi-directional filtering.
*   **Use Diode:** When data must leave OT but *never* enter (e.g., sending logs to cloud).
*   **Limitation:** Cannot receive commands or updates through the diode.

OT6 — **Data Flow Design:**
*   **Flow:** PLC (L1) → Historian (L3) → OPC UA Server → Edge Gateway → MQTT Broker → Cloud.
*   **Security:** IDMZ between Edge Gateway and Cloud. Firewall between Historian and Edge.
*   **Boundaries:** OT Network (L1-L3) is air-gapped from IT. Edge Gateway acts as the secure bridge.

OT7 — **IEC 62443 Zones & Conduits:**
*   **Zone:** Group of assets with same security requirements (e.g., "Safety Zone", "Control Zone").
*   **Conduit:** Communication path between zones.
*   **Design:**
    *   Zone 1: PLCs/SIS (High Security).
    *   Zone 2: SCADA/HMI (Medium Security).
    *   Zone 3: Engineering Workstations (Medium Security).
    *   Zone 4: Corporate IT (Lower Security).
    *   Conduits: Firewalls between each Zone.

OT8 — **Segmentation Strategy:**
*   **VLANs:** One VLAN per production line + separate VLANs for HMI, Engineering, IT.
*   **Firewalls:** Between VLANs and at the IT/OT boundary.
*   **Switches:** Managed L2/L3 switches with port security.
*   **Remote Access:** Jump host in IDMZ; MFA required.
*   **Transition:** Implement in phases (e.g., per line) during maintenance windows; monitor traffic before enforcing policies.

OT9 — **SIS vs BPCS:**
*   **BPCS:** Controls normal process operations.
*   **SIS:** Independent safety system (Emergency Shutdown).
*   **IEC 61511:** Functional Safety standard for SIS.
*   **Isolation:** SIS must be isolated to ensure it functions during a cyber incident affecting BPCS/IT.
*   **Ransomware on SIS:** Could prevent emergency shutdown, leading to physical damage or injury.

OT10 — **PLC vs DCS vs SCADA:**
*   **PLC:** Discrete control, localized, fast response.
*   **DCS:** Process control, centralized, redundant, high availability.
*   **SCADA:** Wide area monitoring/control (pipelines, grids).
*   **Coexistence:** Yes. PLCs control machines; DCS manages process; SCADA monitors multiple sites.

OT11 — **Remote Access:**
*   **Architecture:** Bastion/Jump Host in IDMZ.
*   **Controls:** MFA, Session Recording, Time-limited access (Just-in-Time).
*   **Vendor Access:** Dedicated accounts, audited, no persistent access.
*   **RDP Direct:** Unacceptable due to lack of audit trail, credential exposure, and direct network path to critical assets.

OT12 — **Incident Response (Water Treatment):**
*   **Detection:** IDS on Level 3, Anomaly detection on PLC traffic.
*   **Inventory:** Know all assets to identify compromise scope.
*   **Response:** Isolate compromised segment (VLAN/Firewall) without shutting down safety systems.
*   **Coordination:** SOC informs Plant Manager; Operator maintains physical safety manually.
*   **Operator Role:** Monitor physical parameters, execute manual overrides if automation is compromised. Safety > Security.

OT13 — **HMI:**
*   **Role:** Interface for operators to view process data and issue commands.
*   **Diff:** HMI is runtime (Level 2). Engineering Workstation is for configuration/logic development (Level 3). HMI should not be used for programming.

OT14 — **Historian:**
*   **Role:** Time-series database for process data.
*   **Importance:** Enables trend analysis, compliance reporting, and troubleshooting.
*   **Plant Historian (L3):** High resolution, local process data.
*   **Enterprise Historian (L4):** Aggregated data, lower resolution, business analytics.

OT15 — **Ladder Logic:**
*   **Device:** PLC.
*   **Definition:** Visual programming language resembling electrical relay logic.
*   **Dominance:** Legacy investment, ease of use for electricians, deterministic execution, reliability.

OT16 — **RTU vs PLC:**
*   **RTU:** Remote Terminal Unit. Low power, wide temp range, telemetry focus.
*   **PLC:** Programmable Logic Controller. Local control, high logic capability.
*   **Environment:** RTUs for remote sites (oil wells, pipelines) with limited connectivity/power. PLCs for factory floors.

OT17 — **Analog vs Digital:**
*   **Analog:** Continuous signal (4-20mA, 0-10V).
*   **Digital:** Discrete On/Off (24V).
*   **4-20mA vs 0-20mA:** 4mA "Live Zero" allows detection of wire breaks (0mA = fault). 0-20mA cannot distinguish between 0 signal and broken wire.

OT18 — **Asset Inventory:**
*   **Foundation:** You cannot secure what you don't know exists.
*   **Tools:** Passive monitoring (Packet capture/NetFlow), Active scanning (Nmap - *use with caution*).
*   **Active Scanning Risk:** Can crash legacy PLCs/RTUs due to unexpected traffic or malformed packets. Prefer passive discovery.

OT19 — **MITRE ATT&CK for ICS:**
*   **Framework:** Tactics/Techniques specific to Industrial Control Systems.
*   **Tactics:** Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion.
*   **Example:** Initial Access (Phishing), Execution (Command and Scripting Interpreter).
*   **Diff:** Focuses on ICS protocols and physical effects (e.g., "Modify Control Logic").
*   **Use:** Map current controls against techniques to find gaps (e.g., "Do we detect PLC logic modification?").

OT20 — **Converged SOC:**
*   **Log Collection:** Agentless or passive mirroring to avoid impacting real-time control.
*   **SIEM:** Ingest OT logs; use OT-specific parsers (Modbus, DNP3).
*   **Rules:** Detect protocol anomalies, unauthorized config changes.
*   **Workflow:** IT Analyst triages; OT Engineer validates safety impact.
*   **Staffing:** Hybrid team (IT Security + OT Engineers).
*   **False Positives:** Tune rules aggressively; OT traffic is noisy.
*   **Firmware Alert:** Isolate device immediately. Verify integrity. Do not auto-patch. Manual update by OT engineer after testing.
