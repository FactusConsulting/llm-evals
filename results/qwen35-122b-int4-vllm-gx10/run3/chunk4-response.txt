

G1 — **Slice vs. Array & Append:**
An array has a fixed size and is a value type (copying copies the whole array). A slice is a dynamic view over an array, consisting of a pointer, length, and capacity (reference type). When appending to a slice that exceeds capacity, Go allocates a new, larger underlying array, copies existing data, and updates the slice header to point to the new array.

G2 — **`var` vs `:=` & Limitations:**
`var x int` explicitly declares a variable with a type. `x := 0` infers the type from the value. You cannot use `:=` at the package level (global scope) or if the variable already exists in the current scope (unless you are redeclaring at least one new variable in the same statement).

G3 — **Goroutine vs. Thread & GMP:**
A goroutine is a lightweight thread managed by the Go runtime (KB stack vs. MB OS stack). The GMP model schedules goroutines (G) onto OS threads (M) via logical processors (P). The scheduler multiplexes many Gs onto fewer Ms, handling blocking syscalls and work-stealing for load balancing.

G4 — **Channels & Buffering:**
Channels are typed conduits for communication between goroutines. Unbuffered channels block on send/receive until the other side is ready (synchronization). Buffered channels queue messages up to capacity. Sending to a full buffered channel blocks until space opens; receiving from an empty one blocks until data arrives.

G5 — **Context & Timeout:**
Context manages cancellation signals, deadlines, and request-scoped values across API boundaries.
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
client.Do(req) // Cancels if >5s
```

G6 — **Interfaces & `interface{}`:**
Go interfaces are satisfied implicitly (duck typing); no `implements` keyword. Java/C# require explicit declaration. `interface{}` (or `any`) accepts any type. It is powerful for generic containers but dangerous because it loses type safety, requiring runtime type assertions which can panic if incorrect.

G7 — **Memory Model & Visibility:**
This is unsafe due to lack of synchronization. The compiler/CPU may reorder writes (`ready = true` before `data = "hello"`), or the reading goroutine may see `ready = true` before `data` is updated. Fix: Use `sync/atomic` for `ready`, `sync.Mutex`, or channels to establish a "happens-before" relationship.

G8 — **Mutex vs. RWMutex & sync.Map:**
`Mutex` allows exclusive access. `RWMutex` allows multiple readers OR one writer. `sync.Map` is optimized for high-contention read-heavy maps where keys are static. For most cases, a regular `map` + `Mutex` is faster due to lower overhead; `sync.Map` trades memory for lock contention reduction.

G9 — **Modules & MVS:**
Modules manage dependencies. `go.mod` lists requirements; `go.sum` stores cryptographic checksums for verification. `go mod tidy` adds missing and removes unused dependencies. Minimum Version Selection (MVS) chooses the lowest version satisfying all requirements to ensure reproducibility.

G10 — **Defer & Gotchas:**
`defer` schedules a function call to run when the surrounding function returns. Multiple defers execute in Last-In-First-Out (LIFO) order. Common gotcha: capturing the loop variable in a deferred closure (captures the variable reference, not value), causing all defers to use the final loop value.

G11 — **Pointers:**
A pointer holds a memory address. The zero value is `nil`. To create a pointer to a struct literal: `p := &MyStruct{Field: value}`.

G12 — **`init()` Function:**
`init()` is a special function called automatically before `main()` to initialize package state. A package can have multiple `init()` functions; they execute in declaration order within the package. Across packages, execution order follows import dependency graph.

G13 — **`make` vs `new`:**
`new(T)` allocates zeroed memory for type T and returns `*T`. `make(T, ...)` initializes slices, maps, and channels and returns the initialized type `T` (not a pointer). `new` works for all types; `make` only for reference types.

G14 — **Error Handling:**
Errors are values implementing the `error` interface (`Error() string`). Idiomatic pattern: `if err != nil { return err }`. `errors.Is` checks if an error matches a target (handles wrapping). `errors.As` extracts the underlying error type. `==` only checks exact equality.

G15 — **Composite Types & Zero Values:**
Map: `nil`. Slice: `nil`. Channel: `nil`. Struct: zero value of each field (e.g., 0, false, nil).

G16 — **Race Conditions:**
A race occurs when multiple goroutines access shared memory concurrently, and at least one writes. `-race` uses shadow memory to detect conflicts at runtime. Fix: Protect access with `sync.Mutex` or serialize access via channels.

G17 — **Select Statement:**
`select` waits on multiple channel operations. Unlike `switch`, it chooses a ready case randomly if multiple are ready. If none are ready, it blocks. Timeout: `case <-time.After(d):`.

G18 — **Escape Analysis:**
The compiler decides stack vs. heap allocation. If a variable's address escapes the function scope (e.g., returned or stored globally), it moves to the heap. Inspect with `go build -gcflags="-m"`. Heap allocation increases GC pressure; stack is faster.

G19 — **Reflection:**
`reflect.Type` describes type info; `reflect.Value` holds the data. Reflection is slow (runtime overhead) and prevents compiler optimizations. Justified for generic libraries (e.g., ORM, JSON) where code generation isn't feasible. Prefer code gen for performance.

G20 — **`go:embed`:**
Embeds files into the binary at compile time. Supports single files, directories, and patterns. Returns `embed.FS` (implements `io/fs.FS`). Limitations: Files cannot change at runtime; increases binary size.

R1 — **Ownership Rules:**
1. Each value has exactly one owner. 2. When the owner goes out of scope, the value is dropped. 3. Ownership can be transferred (moved), but not copied (unless `Copy` trait).

R2 — **`String` vs `&str`:**
`String` is an owned, growable, heap-allocated string. `&str` is a borrowed string slice (view). Use `&str` for function inputs (flexible), `String` for outputs or when ownership is required.

R3 — **Borrowing & Rules:**
Borrowing creates references. Rules: You can have either one mutable reference (`&mut T`) OR any number of immutable references (`&T`), but not both simultaneously. The borrow checker enforces this at compile time to prevent data races.

R4 — **`Result`, `Option` & `?`:**
`Result<T, E>` handles success/failure. `Option<T>` handles some/none. `?` propagates errors/none up the call stack.
```rust
fn read_file(path: &str) -> Result<String, io::Error> {
    fs::read_to_string(path)
}
```

R5 — **`Box`, `Rc`, `Arc`:**
`Box<T>`: Heap allocation, single owner. `Rc<T>`: Reference counting, single-threaded shared ownership. `Arc<T>`: Atomic reference counting, thread-safe shared ownership. Use `Arc` for concurrent data sharing.

R6 — **Traits:**
Traits define shared behavior (like interfaces). Go is implicit; Rust requires `impl Trait for Type`. `dyn Trait` (trait object) uses dynamic dispatch (vtable). `T: Trait` uses static dispatch (monomorphization), usually faster.

R7 — **Lifetimes:**
Fails because the compiler doesn't know if the return reference lives as long as `x` or `y`. Fix: Explicitly tie the return lifetime to the inputs.
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str { ... }
```

R8 — **`Send` & `Sync`:**
`Send`: Type can be transferred across threads. `Sync`: Type can be referenced across threads (`&T` is `Send`). `Rc` is not `Send` (not thread-safe). `Arc` uses atomics for ref counting, making it `Send` and `Sync`.

R9 — **Async/Await:**
Async functions return a `Future` (state machine). An executor (e.g., Tokio) polls futures to completion. Unlike Go's preemptive scheduler (OS threads), Rust's async is cooperative (yield control explicitly).

R10 — **`unsafe`:**
Bypasses borrow checker and type safety. 3 things: Dereference raw pointers, call unsafe functions, access union fields. Justified for FFI, low-level OS interaction, or performance-critical code where safety is manually verified.

R11 — **Pattern Matching:**
`match` deconstructs values and must be exhaustive (cover all cases). `if let` handles a single pattern. Compiler enforces exhaustiveness to prevent runtime panics on unhandled cases.

R12 — **`Vec` vs Array:**
Array `[T; N]` is fixed size, stack-allocated. `Vec<T>` is dynamic, heap-allocated. When capacity is exceeded, `Vec` allocates a new larger buffer (usually 2x), copies/moves elements, and frees the old buffer.

R13 — **Enums:**
Rust enums are tagged unions (can hold data). C/Java enums are integers or classes. `Option<T>` is an enum (`Some(T) | None`) replacing null, forcing explicit handling of absence.

R14 — **`impl` Block:**
Defines methods. `&self` borrows immutably, `&mut self` borrows mutably, `self` consumes ownership. Associated functions (no `self`) are called via `Type::func()`, used for constructors.

R15 — **Derive Macro:**
Automatically implements traits. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive for types containing fields that don't implement the trait (e.g., raw pointers for `Debug` sometimes).

R16 — **`Cow` (Clone on Write):**
`Cow<'a, T>` holds either a borrowed reference or an owned clone. Useful when data might not change (avoid clone) but might need mutation (clone on demand).

R17 — **Module System:**
`mod` declares a module. `use` brings items into scope. `pub` exports visibility. 2018 edition: `mod.rs` is optional; paths resolve relative to crate root or module file.

R18 — **`Pin<T>`:**
Prevents moving a value in memory. Needed for self-referential structs (common in async `Future`s) where pointers inside the struct point to the struct itself. `Unpin` indicates a type is safe to move.

R19 — **Macros:**
Declarative (`macro_rules!`) for pattern matching code. Procedural (derive, attribute) for generating code at compile time. Hygiene ensures macro variables don't clash with surrounding scope.

R20 — **Zero-Cost Abstractions:**
High-level features compile to efficient machine code. Iterators are inlined. Generics are monomorphized (specialized code per type). Traits use static dispatch where possible. No runtime overhead compared to C.
