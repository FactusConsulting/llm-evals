## .NET / C#

**DN1** — **Class vs Struct**: A `class` is a reference type (heap-allocated, copied by reference, supports inheritance, nullable). A `struct` is a value type (stack/inline-allocated, copied by value, sealed, non-nullable unless `Nullable<T>`). Use a struct for small (≤16 bytes), logically single-value, immutable data types (e.g., `Point`, `Complex`, `Guid`-like values) where copying is cheaper than heap allocation. Avoid structs for large or frequently-boxed types.

**DN2** — **IEnumerable<T> vs IQueryable<T>**: `IEnumerable<T>` represents in-memory iteration; LINQ methods execute client-side (LINQ to Objects). `IQueryable<T>` represents a queryable data source (e.g., EF Core); LINQ methods build an expression tree that is translated to SQL and executed server-side. Distinction matters because `IQueryable` defers execution and pushes filtering to the database (reduces memory/network), while `IEnumerable` pulls all data into memory first. Using `IEnumerable` on a DbSet forces client-side evaluation.

**DN3** — **async/await, Task vs ValueTask**: `async`/`await` compiles into a state machine; `await` returns control to the caller and resumes on the captured `SynchronizationContext`/`TaskScheduler` when the awaited task completes. `Task` is a heap-allocated reference type; `ValueTask` is a struct that avoids allocation when the result is already available (e.g., cached or synchronous completion). Use `ValueTask` for hot paths where the result is often immediately available (e.g., `IAsyncEnumerable`-style APIs), but note it can only be awaited once and cannot be cached.

**DN4** — **DI lifetimes & common bug**: 
- **Transient**: new instance per resolution (cheap, stateless services).
- **Scoped**: one instance per scope/request (e.g., `DbContext`).
- **Singleton**: one instance for app lifetime (caches, config).
Common bug: injecting a Scoped service into a Singleton captures the scoped instance for the Singleton's lifetime, causing it to be shared across requests (e.g., a `DbContext` used concurrently → `ObjectDisposedException` or stale data). Fix: never inject scoped services into singletons; use `IServiceScopeFactory` to create scopes inside the singleton.

**DN5** — **string vs ReadOnlySpan<char>**: `string` is immutable, heap-allocated, UTF-16, and supports interning. `ReadOnlySpan<char>` is a stack-allocated view over arbitrary memory (string, array, native buffer) that supports slicing without allocation. Use `Span<T>`/`ReadOnlySpan<T>` for performance-critical parsing, slicing, or processing where avoiding allocations matters (e.g., `string.Split` alternatives, JSON parsing). `Span<T>` is ref struct, so it cannot be captured in async methods or stored in fields.

**DN6** — **GC, generations, LOH, IDisposable**: The GC is a generational, non-deterministic collector. **Gen 0**: short-lived, small objects (survive ~1 collection). **Gen 1**: survivors from Gen 0. **Gen 2**: long-lived survivors. **Large Object Heap (LOH)**: objects > 85KB, not compacted by default (fragmentation risk). `IDisposable` is needed for unmanaged resources (file handles, sockets, DB connections) because the GC only tracks managed memory; deterministic cleanup via `using`/`Dispose` is required. The GC does not call `Dispose`; finalizers are a safety net.

**DN7** — **ConfigureAwait(false)**: By default, `await` captures the current `SynchronizationContext` (or `TaskScheduler`) and resumes on it (e.g., UI thread, ASP.NET request context). `ConfigureAwait(false)` skips capture, resuming on the thread pool. Use it in library code to avoid deadlocks (e.g., blocking on async in UI) and improve performance. Do NOT use it in UI/ASP.NET Core code that must update UI or access request-scoped state after the await. In ASP.NET Core, the default `SynchronizationContext` is null, so `ConfigureAwait(false)` is often unnecessary.

**DN8** — **.NET 8/9 features**:
- **Primary constructors**: `public class MyService(ILogger<MyService> logger)` — parameters are in scope for the class body; can be captured as fields.
- **Collection expressions**: `int[] arr = [1, 2, 3];` or `List<int> list = [.. existing];` (spread operator).
- **FrozenDictionary**: immutable, optimized for read-only access (created via `ToFrozenDictionary()`), faster lookup than `Dictionary` for read-heavy scenarios.
Example with DI:
```csharp
public class OrderService(ILogger<OrderService> logger, IOrderRepository repo)
{
    public async Task<Order> GetAsync(int id) 
    {
        logger.LogInformation("Fetching order {Id}", id);
        return await repo.GetByIdAsync(id);
    }
}
```

**DN9** — **DbContext ObjectDisposedException under concurrency**: Likely cause: a Singleton service holds a scoped `DbContext` (or captures it via DI), causing it to be shared across requests. When one request disposes the context (end of scope), another request tries to use it → `ObjectDisposedException`. Fix: ensure `DbContext` is injected only into scoped services; if a singleton needs data access, use `IServiceScopeFactory` to create a scope per operation. EF Core's `DbContext` is registered as Scoped by default, so its lifetime matches the request scope.

**DN10** — **record vs class vs record struct**: `record` is a reference type with value equality, `with` expressions, and synthesized `ToString`/`GetHashCode`/`Equals`. `record struct` is a value type with value equality (C# 10+). `class` is a reference type with reference equality by default. Choose `record` for immutable data models, DTOs, and domain events where equality is value-based. Choose `class` for behavior-heavy objects with identity. `record struct` for small, immutable value data (e.g., coordinates).

**DN11** — **ref, out, in**: 
- `ref`: variable must be initialized before passing; method can read/write it.
- `out`: variable need not be initialized; method must assign it before returning.
- `in`: read-only reference; avoids copying for large structs; method cannot modify it.
Use `ref` for modifying caller's variable, `out` for returning multiple values (e.g., `TryParse`), `in` for passing large structs by reference without mutation.

**DN12** — **Nullable reference types (NRT) vs nullable value types**: NRT (`string?`) is a compile-time-only annotation; the runtime type is still `string`. `#nullable enable` enables compiler flow analysis to warn about potential nulls. Nullable value types (`int?`) are `Nullable<T>` structs that can be `null` at runtime. NRT does not change runtime behavior; `int?` is a value type wrapper.

**DN13** — **LINQ, method vs query syntax, deferred execution**: LINQ is a set of extension methods for querying collections. Method syntax: `list.Where(x => x > 5).Select(x => x * 2)`. Query syntax: `from x in list where x > 5 select x * 2` (compiles to method syntax). Deferred execution: the query is not executed until enumerated (e.g., `foreach` or `.ToList()`), allowing composition and avoiding multiple enumerations.

**DN14** — **Generic constraints**: 
- `where T : class` — reference type only.
- `where T : struct` — value type only.
- `where T : new()` — must have a parameterless constructor.
- `where T : IComparable<T>` — must implement the interface.
Combine multiple: `where T : class, IComparable<T>, new()` — all constraints must be satisfied. Use for generic algorithms that need specific capabilities (e.g., sorting, comparison).

**DN15** — **abstract class vs interface**: `abstract class` can have implementation, fields, constructors, and access modifiers; supports "is-a" relationships. `interface` is a pure contract (no state). Default interface methods (C# 8+) allow interfaces to have implementations, blurring the line. Use abstract class for shared base behavior; interface for "can-do" capabilities (e.g., `IDisposable`, `IEnumerable`).

**DN16** — **Middleware pipeline**: `app.Use()` adds middleware that can call `next` or short-circuit. `app.Map()` branches the pipeline (e.g., `MapGet`, `MapPost`, `Map("/path")`). `app.Run()` is terminal middleware (does not call `next`). Ordering matters: exception handling, static files, authentication, then business logic. Exception middleware (`UseExceptionHandler`) should be early to catch downstream exceptions.

**DN17** — **Channel<T> vs BlockingCollection<T>**: `Channel<T>` is async-first, supports bounded channels for backpressure, and is allocation-efficient. `BlockingCollection<T>` is synchronous, uses blocking operations, and is older. Bounded channel example:
```csharp
var channel = Channel.CreateBounded<T>(capacity: 100);
// Producer:
await channel.Writer.WriteAsync(item);
// Consumer:
await foreach (var item in channel.Reader.ReadAllAsync()) { ... }
```
Bounded channels block producers when full, providing natural backpressure.

**DN18** — **Source Generators**: Generate C# code at compile time by analyzing source (e.g., attributes, syntax trees). Differ from reflection (runtime, slower) and IL weaving (post-compilation, modifies IL). **Incremental generators** (`IIncrementalGenerator`) cache intermediate results and only re-run when inputs change, making them faster and more memory-efficient than `ISourceGenerator`. Preferred for build performance.

**DN19** — **TPL Dataflow vs Channels**: TPL Dataflow (`System.Threading.Tasks.Dataflow`) provides `ActionBlock` (processes items), `TransformBlock` (transforms input to output), `BufferBlock` (buffers items). It supports declarative pipelines, bounded capacity, and complex linking. Channels are simpler, async-first, and more lightweight. Use Dataflow for complex pipelines with branching/joining; Channels for simple producer-consumer with backpressure.

**DN20** — **Minimal APIs vs Controllers**: Minimal APIs use top-level statements and lambda handlers (`app.MapGet("/", () => "Hello")`), reducing boilerplate. Controllers use classes with attributes, supporting per-action filters, model binding, and testability via `WebApplicationFactory`. Trade-offs: Minimal APIs are lighter but less structured; controllers are more testable and feature-rich. OpenAPI support via `AddEndpointsApiExplorer`. Route groups (`MapGroup`) organize endpoints; endpoint filters (`AddFilter`) run before/after handlers.

## Python

**P1** — **list vs tuple**: `list` is mutable, `tuple` is immutable (but can contain mutable objects). `set` is mutable, unordered, and unhashable; `frozenset` is immutable and hashable (usable as dict key). Use tuples for fixed data, lists for dynamic data, frozensets for hashable sets.

**P2** — **GIL**: The Global Interpreter Lock ensures only one thread executes Python bytecode at a time. It affects CPU-bound workloads (e.g., heavy computation) by preventing parallel execution across threads. I/O-bound workloads (network, disk) are unaffected because the lock is released during I/O. Workarounds: `multiprocessing` (separate processes), using C extensions (e.g., NumPy), or `asyncio` for I/O concurrency.

**P3** — **deepcopy vs copy**: `copy.copy()` is shallow — copies the object but not nested objects. `copy.deepcopy()` recursively copies all nested objects. Example of shallow-copy bug:
```python
a = [[1, 2], [3, 4]]
b = copy.copy(a)
b[0].append(99)  # a[0] also becomes [1, 2, 99]
```
Use deepcopy for nested mutable structures.

**P4** — **Decorators**: Functions that wrap other functions. Example timing decorator:
```python
import time
def timer(func):
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.time() - start:.2f}s")
        return result
    return wrapper

@timer
def slow_func():
    time.sleep(1)
```

**P5** — **Generators & yield**: Generators are functions that use `yield` to produce values lazily, one at a time, without storing the entire sequence in memory. `yield from` delegates to another generator (e.g., `yield from gen2()`). Unlike returning a list, generators are memory-efficient for large datasets and support streaming.

**P6** — **asyncio**: `asyncio.run()` runs a single coroutine as the entry point. `asyncio.gather()` runs multiple coroutines concurrently and waits for all. `asyncio.create_task()` schedules a coroutine as a task without blocking. `time.sleep()` blocks the event loop (synchronous), so use `await asyncio.sleep()` instead to allow other tasks to run.

**P7** — **MRO & diamond inheritance**: Python 3 uses the **C3 linearization** algorithm. For `D(B, C)` where `B` and `C` inherit from `A`, the MRO is `D → B → C → A → object`. The output is `"C"` because `C` overrides `who()` and appears before `A` in the MRO. C3 ensures monotonicity and consistent method resolution.

**P8** — **Metaclass vs __init_subclass__**: A metaclass is a class that creates classes (e.g., `type`). `__init_subclass__` is a hook called when a subclass is created. Use a metaclass for complex class-level customization (e.g., registering classes, modifying class creation). Use `__init_subclass__` for simpler subclass hooks (e.g., validating subclass attributes). Practical use case: a metaclass that auto-registers subclasses in a registry; `__init_subclass__` for enforcing a required method.

**P9** — **multiprocessing vs threading vs concurrent.futures**: 
- `multiprocessing`: separate processes, bypasses GIL, ideal for CPU-bound tasks. Requires pickling of arguments/return values (serialization overhead).
- `threading`: threads within one process, GIL limits CPU-bound, good for I/O-bound tasks.
- `concurrent.futures`: high-level API for thread/process pools (`ThreadPoolExecutor`, `ProcessPoolExecutor`).
Use multiprocessing for CPU-heavy, threading for I/O-heavy, concurrent.futures for simple parallelism.

**P10** — **__slots__**: Class attribute that prevents `__dict__` creation, saving memory and improving attribute access speed. Use for classes with many instances and fixed attributes (e.g., data records). It prevents adding new attributes dynamically and requires `__slots__` in subclasses.

**P11** — **Virtual environments**: Isolated Python environments for dependency management. `venv` is built-in (standard library), `virtualenv` is third-party (more features, faster), `conda` is a package manager + environment manager (handles non-Python dependencies). Use to avoid dependency conflicts.

**P12** — **Comprehensions vs map/filter**: 
- List: `[x for x in range(10) if x % 2 == 0]`
- Dict: `{k: v for k, v in items}`
- Set: `{x for x in range(10)}`
Comprehensions are more readable and Pythonic than `map()`/`filter()` (which require lambdas). Prefer comprehensions for clarity; use `map`/`filter` for pre-existing functions or very simple transformations.

**P13** — **== vs is**: `==` checks value equality (calls `__eq__`), `is` checks identity (memory address). Object interning: small integers (-5 to 256) and some strings are cached, so `a is b` may return `True` for these. Use `is` for `None` and singletons; `==` for value comparison.

**P14** — **\*args, \*\*kwargs, positional-only, keyword-only**: `*args` collects extra positional arguments as a tuple; `**kwargs` collects extra keyword arguments as a dict. Positional-only parameters (before `/`) cannot be passed by keyword. Keyword-only parameters (after `*`) must be passed by keyword. Example: `def f(a, /, b, *, c): ...` — `a` positional-only, `b` positional-or-keyword, `c` keyword-only.

**P15** — **Context managers**: `with` statement ensures setup/cleanup. Write via `__enter__`/`__exit__`:
```python
class Timer:
    def __enter__(self): self.start = time.time()
    def __exit__(self, *args): print(f"Elapsed: {time.time() - self.start}")
```
Or via `@contextmanager`:
```python
from contextlib import contextmanager
@contextmanager
def timer():
    start = time.time()
    yield
    print(f"Elapsed: {time.time() - start}")
```
Example beyond files: timing code, database transactions, thread locks.

**P16** — **Type hinting**: `typing.Union` (`Union[int, str]`), `Optional` (`Optional[int]` = `Union[int, None]`), `Literal` (`Literal["a", "b"]`), `TypeVar` (generic `T`), `Protocol` (structural typing). Mypy/pyright use these to statically check types, catch errors, and infer types. `Protocol` enables duck typing with static checks.

**P17** — **Data model (dunder methods)**: `__repr__` (unambiguous, for debugging), `__str__` (human-readable, for `print()`). `__eq__` defines equality; if defined without `__hash__`, `__hash__` is set to `None` (unhashable). `__getattr__` is called only when attribute is not found; `__getattribute__` is called for every attribute access. Define `__eq__` and `__hash__` together for hashable objects.

**P18** — **Descriptors**: Objects implementing `__get__`, `__set__`, `__delete__` control attribute access. `property` uses `__get__`/`__set__` to compute values. `classmethod` uses `__get__` to bind the class as first argument. `staticmethod` uses `__get__` to return the function unchanged. Descriptors enable reusable attribute behavior (e.g., validation, caching).

**P19** — **Import system**: The import system uses **finders** (locate modules) and **loaders** (load them). `sys.path` is the search path; `PYTHONPATH` adds directories. `__init__.py` marks a directory as a package; namespace packages (PEP 420) don't need it. Relative imports use `.` (current) and `..` (parent); absolute imports use the full module path. Finders/loaders are part of `importlib` and can be customized.

**P20** — **dataclasses vs attrs vs Pydantic**: `dataclasses` generates `__init__`, `__repr__`, `__eq__`, etc. `attrs` is more feature-rich (validators, converters, slots). `Pydantic` adds runtime validation, serialization, and JSON schema. `__post_init__` runs after `__init__` for custom logic. `field(default_factory=list)` for mutable defaults. `frozen=True` makes instances immutable. Dataclasses support inheritance but require `kw_only` or careful field ordering. Choose Pydantic for validated, serialized data (e.g., API requests); dataclasses for simple internal data containers.
