# Cloud Infrastructure Architecture

**CL1 — IaaS vs PaaS vs SaaS**
- **IaaS** (Infrastructure as a Service): Provides virtualized computing resources — VMs, storage, networking. You manage OS, runtime, apps. *Example: AWS EC2*
- **PaaS** (Platform as a Service): Provides a platform for developing and deploying applications — runtime, middleware, databases. You manage only your app code. *Example: Azure App Service*
- **SaaS** (Software as a Service): Provides ready-to-use software applications. You manage only user data and settings. *Example: Microsoft 365*

---

**CL2 — Shared Responsibility Model**
- **IaaS VMs (EC2/Azure VM)**: Provider handles physical infrastructure, hypervisor, host networking, and facility security. **Your responsibility**: OS patching, runtime, application, data, VM-level firewall, IAM credentials.
- **Managed Kubernetes (EKS/AKS)**: Provider handles control plane, worker node patching, cluster networking, and managed add-ons. **Your responsibility**: Pod workloads, RBAC, secrets, container images, cluster policies, and application data.
- **SaaS (M365)**: Provider handles everything — infrastructure, platform, application, and most security features. **Your responsibility**: User access management, data classification, compliance, and client devices.

---

**CL3 — VPC, Subnet, Security Group, NACL**
- **VPC**: Isolated virtual network in the cloud — defines IP address space, routing, and connectivity.
- **Subnet**: A segmented IP range within the VPC, typically tied to an availability zone.
- **Security Group (SG)**: A **stateful** virtual firewall attached to instances — allows/denies traffic based on rules. Stateful means return traffic is automatically allowed.
- **NACL**: A **stateless** firewall at the subnet level — evaluates traffic entering/exiting the subnet. Stateless means both inbound and outbound rules must be explicitly defined.
- **Layering**: NACL (subnet-level) → Security Group (instance-level) → Instance. NACL filters first, then SG filters.
- **Stateful vs stateless**: SG tracks connection state (return traffic auto-allowed); NACL requires explicit rules for both directions.

---

**CL4 — Multi-Account AWS/Azure Strategy**
- **Landing zone**: A pre-configured baseline environment with accounts, policies, and guardrails (e.g., AWS Control Tower, Azure Landing Zones).
- **Organizational Units (OUs)**: Hierarchical grouping of accounts (e.g., Dev, Prod, Security, Network) for policy inheritance.
- **Guardrails**: Preventive (SCPs, Azure Policy) and detective (CloudWatch alarms, Security Hub) controls enforced across accounts.
- **Shared networking**: AWS Transit Gateway or Azure Hub-and-Spoke — central hub for VPC/VNet connectivity, with shared services (DNS, AD, firewalls).
- **Centralized logging**: Aggregated CloudTrail/Activity Logs, VPC Flow Logs, and security findings into a central S3/Log Analytics workspace.
- **Why single-account is problematic**: No blast-radius isolation, no compliance boundary separation, no cost allocation, and shared IAM creates excessive privilege.

---

**CL5 — Infrastructure as Code Comparison**
- **Terraform/OpenTofu**: Declarative HCL, multi-cloud, mature ecosystem, state-based drift detection. Best for multi-cloud or cloud-agnostic teams.
- **Pulumi**: Supports Python/TypeScript/Go — imperative logic with declarative intent. Best for software engineers who want programming-language expressiveness.
- **CloudFormation/Bicep**: Native AWS/Azure — deep integration, no state file, but vendor-locked. Best for single-cloud shops.
- **Crossplane**: Kubernetes-native control plane that provisions cloud resources via CRDs. Best for teams already running K8s who want GitOps-style cloud provisioning.
- **Choose based on**: cloud strategy (single vs multi), team skill set, and desired abstraction level.

---

**CL6 — Autoscaling Patterns**
- **HPA (Horizontal Pod Autoscaler)**: Scales pod count based on CPU/memory/custom metrics. Reactive, metric-driven.
- **VPA (Vertical Pod Autoscaler)**: Adjusts CPU/memory requests/limits for existing pods. Good for bursty workloads but requires pod restart.
- **Cluster Autoscaler**: Scales the underlying node pool based on pending pods. Works with HPA/VPA.
- **KEDA (Kubernetes Event-Driven Autoscaling)**: Scales pods based on external event sources — queue length (SQS, Kafka), message counts, custom metrics.
- **Use KEDA over HPA** when: scaling is driven by external events (e.g., queue depth) rather than CPU/memory, or when you need scale-to-zero for event-driven workloads.

---

**CL7 — Disaster Recovery Design**
- **RPO/RTO**: RPO = acceptable data loss (e.g., 15 min); RTO = acceptable downtime (e.g., 1 hour).
- **Active-active vs active-passive**: Active-active serves traffic from both regions; active-passive has one standby region.
- **Database replication**: Sync replication (lower RPO, higher latency) for active-active; async replication (higher RPO, lower latency) for active-passive.
- **DNS failover**: Route53 (health checks, failover policies) or Azure Traffic Manager (priority, weighted routing).
- **State management**: Distributed sessions (Redis), database as source of truth, stateless services.
- **DR patterns**: 
  - **Pilot light**: Minimal standby — core services running, scale up on failover.
  - **Warm standby**: Pre-provisioned but not serving traffic — faster failover.
  - **Multi-site active-active**: Both regions serve traffic — zero RTO, highest cost.
- **Cost implications**: Active-active doubles infrastructure cost; pilot light minimizes standby cost.

---

**CL8 — GitOps Model**
- **GitOps**: Git is the single source of truth for both infrastructure and application state. A controller reconciles the cluster to match Git.
- **ArgoCD vs FluxCD**: ArgoCD has a rich UI, multi-cluster management, and sync policies; FluxCD is more flexible with multi-tenancy, supports Kustomize/Helm natively, and has a smaller footprint.
- **Secrets handling**: 
  - **Sealed Secrets**: Encrypts secrets in Git, decrypts in cluster.
  - **External Secrets Operator**: Syncs secrets from cloud providers (AWS Secrets Manager, Vault).
  - **Vault**: Dynamic secrets, rotation, audit logging.
- **Manual drift**: GitOps controller detects drift and **reverts** manual changes — or you configure auto-sync to enforce Git state. Manual changes are overwritten unless you use `ignoreDifferences`.

---

**CL9 — Stateful Legacy App on Kubernetes**
- **StatefulSet**: Provides stable network identity (pod-N), ordered deployment/termination, and stable storage binding.
- **PV/PVC with local storage class**: Use local SSDs (e.g., AWS EBS Local, GCE Local SSD) for low-latency persistent storage. PVC binds to a specific node.
- **Headless service**: Provides stable DNS names for each pod (pod-0.service, pod-1.service) — needed for sticky sessions and peer discovery.
- **Init containers**: Run ordered startup scripts — wait for dependencies, initialize config files, pre-create directories.
- **ConfigMaps as volume mounts**: Mount config files at exact filesystem paths (e.g., `/opt/app/config/app.ini`) — no need to bake into image.
- **Pod Disruption Budgets (PDB)**: Protect against voluntary evictions — ensure minimum available replicas during node maintenance.

---

**CL10 — Service Accounts vs Workload Identity vs IRSA**
- **Service Account**: Kubernetes identity for pods — used for K8s API auth.
- **Workload Identity**: Cloud identity for workloads (e.g., Azure AD Workload Identity, GCP Workload Identity) — maps K8s SA to cloud IAM.
- **IRSA (IAM Roles for Service Accounts)**: AWS-specific — associates a K8s SA with an IAM role via OIDC federation.
- **Why mounting cloud credentials is bad**: Static credentials in pods are a security risk — they can be exfiltrated, rotated manually, and violate least privilege.
- **Workload identity federation**: Uses OIDC to exchange K8s SA tokens for cloud IAM credentials — no static secrets, automatic rotation, scoped permissions.

---

**CL11 — Object vs Block vs File Storage**
- **Object storage (S3/Blob)**: Unstructured data, HTTP API, 11 nines durability, eventual consistency. Use for static content, backups, data lakes.
- **Block storage (EBS/Managed Disk)**: Raw disk attached to a VM, low latency, single-writer. Use for databases, OS disks, applications.
- **File storage (EFS/Azure Files)**: Shared file system over NFS/SMB, multi-writer. Use for shared application data, home directories, legacy apps.
- **Durability/availability**: Object = 11 nines durability, 99.99% availability; Block = 99.9% availability (AZ-specific); File = 99.9% availability, multi-AZ.

---

**CL12 — Zero-Trust Network Architecture for Kubernetes**
- **Network policies**: Micro-segmentation — allow only specific pod-to-pod traffic (e.g., app → DB).
- **Service mesh with mTLS**: Istio/Linkerd encrypts service-to-service traffic, provides identity-based auth (SPIFFE).
- **Pod identity**: Workload identity federation — each pod gets a scoped cloud identity.
- **Admission controllers (OPA/Kyverno)**: Enforce policies — no privileged containers, no root, required labels, image allowlists.
- **Image signing and verification**: Sign images (Cosign), verify signatures at admission time.
- **Runtime security (Falco)**: Detect anomalous behavior — unexpected syscalls, file access, network connections.
- **Secrets management**: Vault/External Secrets — no secrets in Git or images.
- **Difference from perimeter model**: Zero-trust assumes no implicit trust — every request is authenticated and authorized, regardless of network location.

---

**CL13 — CDN**
- **CDN**: A distributed network of edge servers that caches content closer to users.
- **How it works**: User requests content → DNS routes to nearest edge → edge serves cached copy or fetches from origin.
- **Examples**: AWS CloudFront, Azure CDN (Verizon/Edgio).
- **When to use CDN**: Static content (images, CSS, JS), global distribution, DDoS protection, video streaming.
- **When not**: Dynamic personalized content, low-latency internal APIs, or when origin is already geographically close.

---

**CL14 — Regions and Availability Zones**
- **Regions**: Geographic areas (e.g., us-east-1) containing multiple AZs.
- **Availability Zones (AZs)**: Isolated data centers within a region — independent power, cooling, networking.
- **Why deploy across AZs**: High availability — if one AZ fails, traffic shifts to another.
- **Zonal vs regional resources**: Zonal (EBS volume, EC2 instance) tied to one AZ; Regional (S3, ELB, Lambda) span all AZs in a region.

---

**CL15 — Managed Database Services**
- **Examples**: AWS RDS, Google Cloud SQL, Azure SQL Database.
- **Provider handles**: Patching, backups, replication, failover, monitoring, scaling, and hardware maintenance.
- **vs VM**: On a VM, you handle OS patching, DB software installation, backup scripts, replication, and monitoring yourself — significantly more operational overhead.

---

**CL16 — Cloud Identity Services (IAM)**
- **Users**: Individual identities (human or service).
- **Groups**: Collections of users — policies applied at group level.
- **Roles**: Assume-able identities with permission policies — used for services or federated users.
- **Policies**: JSON documents defining allowed/denied actions on resources.
- **Principle of least privilege**: Grant only the minimum permissions required for a task. Apply via: scoped policies (resource-level), conditional access, regular access reviews, and avoiding wildcard permissions.

---

**CL17 — Serverless Computing**
- **AWS Lambda / Azure Functions / Google Cloud Functions**: Event-driven, auto-scaling, pay-per-execution compute.
- **Cold starts**: Delay when a function is first invoked after being idle — container spin-up, runtime initialization. Matters for latency-sensitive workloads.
- **When serverless is a poor fit**: Long-running processes, stateful workloads, predictable high-throughput workloads, or applications requiring persistent connections (WebSockets).

---

**CL18 — Kubernetes Ingress Options**
- **Ingress resource**: Traditional — path/host-based routing to services. TLS termination at the ingress controller.
- **Gateway API**: Newer, more expressive — separates routing, policy, and infrastructure. Supports HTTP, TLS, TCP/UDP, and multi-tenancy.
- **Cloud LB annotations**: Provider-specific (e.g., AWS ALB annotations) — configure load balancer directly.
- **Service mesh ingress gateways**: Istio/Linkerd ingress — mTLS, traffic policies, observability at the edge.
- **TLS termination**: At cloud LB (external), at ingress controller (internal), or at mesh gateway (mTLS).
- **Gateway API over Ingress**: When you need multi-tenancy, protocol support beyond HTTP, or policy attachment (e.g., rate limiting, auth).

---

**CL19 — Cost Optimization Strategy ($80k/month)**
- **Reserved instances vs savings plans vs spot**: RIs (1-3 yr commitment, up to 72% savings), Savings Plans (flexible, 1-3 yr), Spot/Preemptible (up to 90% savings, interruptible).
- **Right-sizing**: Match instance types to actual utilization — use CloudWatch/Compute Optimizer recommendations.
- **Storage tiering**: S3 Intelligent-Tiering (auto-tiering), Archive/Glacier for cold data, lifecycle policies.
- **Idle resource detection**: Identify unattached EBS volumes, idle RDS, over-provisioned clusters.
- **FinOps practices**: Budgets, alerts, cost anomaly detection, tagging, and regular reviews.
- **Showback/chargeback**: Tag resources by team/project; allocate costs via Cost Explorer/Cloud FinOps tools.
- **Tools**: AWS Cost Explorer, Budgets, Trusted Advisor, Azure Cost Management, third-party (CloudHealth, FinOps platforms).

---

**CL20 — Multi-Cloud Strategy**
- **Abstraction layers**: Kubernetes as common runtime, Terraform for IaC portability, cloud-agnostic APIs.
- **Networking**: VPN/interconnect between clouds — private, encrypted links.
- **Identity federation**: SSO (Okta/Azure AD) across both clouds, OIDC federation.
- **Real-world trade-offs**: Increased complexity, cross-cloud latency, higher operational overhead, duplicated tooling, and cost inefficiency.
- **When justified**: Regulatory requirements (data residency), vendor risk mitigation, best-of-breed services, or M&A scenarios.
- **When unnecessary**: Small/medium orgs, single-cloud workloads, or when the complexity outweighs benefits — often a single cloud with good architecture is simpler and cheaper.

# OT Infrastructure Architecture

**OT1 — Purdue Model (ISA-95)**
- **Level 0**: Physical processes — sensors, actuators, pumps, valves.
- **Level 1**: Basic control — PLCs, DCS controllers, intelligent devices.
- **Level 2**: Supervision — HMIs, SCADA servers, alarm management.
- **Level 3**: Operations management — historians, batch management, shift logs.
- **Level 4**: Business planning — ERP, MES, asset management.
- **Level 5**: Enterprise network — corporate IT, internet access.

---

**OT2 — IT vs OT Networks**
- **IT**: Data-centric, high bandwidth, frequent updates, availability measured in seconds.
- **OT**: Process-centric, real-time control, availability measured in milliseconds, safety-critical.
- **Why standard IT patching fails**: OT systems require scheduled downtime, vendor validation, compatibility testing, and cannot tolerate reboots — a patch that causes a PLC to fail could halt production or cause safety incidents.

---

**OT3 — DMZ/IDMZ**
- **Industrial DMZ (IDMZ)**: A security zone between IT (Level 4) and OT (Level 3) networks — isolates untrusted IT traffic from control systems.
- **Allowed traffic**: Only specific protocols (e.g., historian data replication, remote access via jump hosts) — typically from IT to DMZ, and DMZ to OT, with no direct IT-to-OT traffic.
- **Why direct L4→L1 is dangerous**: No security controls, unvalidated protocols, and direct access to control devices bypasses monitoring — a compromise in IT can directly manipulate or disrupt physical processes.

---

**OT4 — OT Protocols**
- **Modbus TCP**: Level 1-2 — industrial control protocol for reading/writing registers on PLCs/RTUs.
- **OPC UA**: Level 2-3 — interoperability standard for data exchange between SCADA, historians, and controllers.
- **EtherNet/IP (CIP)**: Level 1-2 — industrial Ethernet protocol for I/O control and messaging.
- **PROFINET**: Level 1-2 — industrial Ethernet for real-time control and diagnostics.
- **MQTT**: Level 3-4 — lightweight publish/subscribe for IoT/cloud data streaming.

---

**OT5 — Data Diode vs Firewall**
- **Data diode**: Hardware device that physically allows data flow in only one direction — unidirectional, no return traffic.
- **Firewall**: Stateful filtering device that allows bidirectional traffic based on rules.
- **When to use data diode**: High-security environments (e.g., nuclear, critical infrastructure) where data must flow one-way (OT→IT) with zero possibility of reverse access.
- **Limitation**: No interactive protocols (no remote access, no acknowledgments), requires application-level data transfer (e.g., file transfer, database replication).

---

**OT6 — SCADA Data to Cloud**
- **Data flow**: Historian (Level 3) → OPC UA server → MQTT broker → edge gateway → cloud ingestion.
- **Security boundaries**: 
  - Between historian and OPC UA: authenticate, restrict to read-only.
  - Between OPC UA and MQTT: TLS, client certificates.
  - Edge gateway: protocol conversion, data validation, buffering.
  - Cloud ingestion: API gateway, authentication, data encryption.
- **Placement**: DMZ between OT and cloud; edge gateway in DMZ; cloud ingestion behind cloud firewall.

---

**OT7 — IEC 62443 Zones and Conduits**
- **Zone**: Logical grouping of assets with similar security requirements (e.g., control zone, safety zone).
- **Conduit**: A communication path between zones — controlled, monitored, and encrypted.
- **Design for manufacturing plant**:
  - **Corporate zone**: IT network, ERP, email.
  - **Engineering zone**: Workstations for PLC programming.
  - **SCADA zone**: SCADA servers, historians.
  - **Control zone**: PLCs, HMIs, I/O.
  - **SIS zone**: Safety instrumented systems — isolated, minimal connectivity.
- **Conduits**: Between zones — firewalls, IPS, and access control lists; only specific protocols allowed.

---

**OT8 — Network Segmentation for 200 PLCs**
- **VLAN design**: Per production line (Line 1-4), per function (SCADA, engineering, safety), and per zone (control, supervision).
- **Firewall placement**: Between each zone — industrial firewalls (e.g., Tofino, MGuard) with protocol-aware filtering.
- **Switch architecture**: Managed Layer 2/3 switches with VLAN trunking, STP, and port security.
- **Remote access for vendors**: Jump hosts in DMZ, VPN with MFA, session recording, time-limited access.
- **Transition without stopping production**: Phased approach — segment one line at a time, schedule during planned shutdowns, use temporary monitoring, and validate no production impact.

---

**OT9 — SIS vs BPCS**
- **SIS (Safety Instrumented Systems)**: Independent safety systems that detect dangerous conditions and initiate protective actions (e.g., emergency shutdown).
- **BPCS (Basic Process Control System)**: The primary control system that maintains normal process operations.
- **IEC 61511**: Functional safety standard for SIS — requires independent, reliable, and fail-safe design.
- **Why SIS must be isolated**: A compromise could disable safety functions — leading to catastrophic incidents (explosions, toxic releases).
- **Ransomware on SIS**: Could prevent emergency shutdowns, cause unsafe conditions, or mask dangerous states — potentially causing loss of life and environmental damage.

---

**OT10 — PLC vs DCS vs SCADA**
- **PLC**: Programmable Logic Controller — discrete control (on/off, sequencing). Used for individual machines or small processes.
- **DCS**: Distributed Control System — continuous process control (chemical plants, refineries) with centralized supervision and distributed controllers.
- **SCADA**: Supervisory Control and Data Acquisition — monitors and controls geographically distributed assets (pipelines, power grids).
- **Can coexist**: Yes — a plant may use PLCs for machine control, DCS for process control, and SCADA for enterprise-wide monitoring.

---

**OT11 — Remote Access to OT**
- **Jump hosts**: Dedicated hardened servers in DMZ — users connect to jump host, then to OT assets.
- **MFA**: Multi-factor authentication for all remote access.
- **Session recording**: Audit trail of all remote sessions.
- **Vendor access**: Time-limited, monitored, and restricted to specific assets.
- **Why direct RDP to HMI is unacceptable**: No audit trail, no access control, potential for malware propagation, and no way to enforce least privilege.

---

**OT12 — OT Security Incident Response (Water Treatment Facility)**
- **Detection**: Deploy passive IDS (e.g., Nozomi, Dragos) on Level 3 network — monitor for anomalous traffic, protocol anomalies, and known IOC indicators.
- **Asset inventory**: Maintain up-to-date inventory of all devices, IPs, and protocols.
- **Response steps**: 
  1. Isolate compromised VPN appliance from network.
  2. Monitor for lateral movement — block suspicious traffic.
  3. Engage incident response team.
  4. Preserve evidence (logs, packet captures).
  5. Coordinate with control room — maintain safe operations.
- **Safe operations**: Operators may need to switch to manual control — ensure safety systems (SIS) are unaffected.
- **Operator role**: Plant operators are the first line of defense — they notice anomalies, maintain process safety, and execute manual fallback procedures.

---

**OT13 — HMI**
- **HMI (Human-Machine Interface)**: Graphical interface that allows operators to monitor and control industrial processes — displays process data, alarms, and control buttons.
- **Role**: Real-time monitoring, alarm management, manual control.
- **vs engineering workstation**: HMI is for operations (view/control); engineering workstation is for configuration, programming, and maintenance (PLC logic, device settings).

---

**OT14 — Historian**
- **Historian**: Time-series database that stores process data (temperatures, pressures, flow rates) for historical analysis.
- **Importance**: Enables trend analysis, troubleshooting, compliance reporting, and process optimization.
- **Plant historian (Level 3)**: Local, real-time data collection from control systems — high resolution, short retention.
- **Enterprise historian (Level 4)**: Aggregates data from multiple plants — lower resolution, longer retention, business intelligence.

---

**OT15 — Ladder Logic**
- **Ladder logic**: Graphical programming language for PLCs — resembles electrical relay diagrams.
- **Executes on**: PLCs (Programmable Logic Controllers).
- **Why dominant**: Proven reliability, easy for electricians/engineers to understand, deterministic execution, real-time performance, and massive installed base.

---

**OT16 — RTU vs PLC**
- **RTU (Remote Terminal Unit)**: Telemetry device for remote monitoring and control — communicates over long distances (radio, satellite, cellular).
- **PLC**: Local control device — executes logic at the machine/process level.
- **RTU environments**: Remote, harsh environments (pipelines, wellheads, substations) where power and connectivity are limited.
- **PLC environments**: Local, controlled environments (factory floors, process plants).

---

**OT17 — Analog vs Digital Signals**
- **Analog**: Continuous signals — 4-20mA current, 0-10V voltage — represent variable process values (temperature, pressure).
- **Digital**: Discrete signals — on/off, open/closed — represent binary states.
- **Why 4-20mA over 0-20mA**: 4mA provides a "live zero" — a broken wire or fault results in 0mA, which is distinguishable from a valid 4mA signal. Also, the 4mA baseline powers the transmitter.

---

**OT18 — OT Asset Inventory**
- **Foundation**: You cannot protect what you don't know — asset inventory is the basis for risk assessment, monitoring, and incident response.
- **Passive monitoring**: SPAN ports, network taps — observe traffic without sending packets. Safe, no impact.
- **Active scanning**: Send probes (nmap, Nessus) — can disrupt real-time control systems, cause PLCs to fault, or trigger safety shutdowns.
- **Why active scanning is dangerous**: Control protocols are sensitive to unexpected traffic — a single malformed packet can cause a device to stop, reset, or fail.

---

**OT19 — MITRE ATT&CK for ICS**
- **Tactics and techniques**:
  1. **Initial Access** — Phishing (spear-phishing email to engineer).
  2. **Execution** — Malicious OPC UA client (execute code via OPC UA).
  3. **Persistence** — Firmware modification (plant backdoor in PLC firmware).
  4. **Privilege Escalation** — Valid accounts (use compromised engineering workstation).
  5. **Evasion** — Modify alarms (disable alarm notifications).
  6. **Discovery** — Network scanning (identify control devices).
  7. **Lateral Movement** — Remote service exploitation (exploit HMI vulnerability).
  8. **Collection** — Process data exfiltration (steal process recipes).
  9. **Command & Control** — Standard protocols (use Modbus for C2).
  10. **Impact** — DoS (flood PLC with traffic), Safety compromise (disable SIS).
- **Difference from enterprise ATT&CK**: ICS framework focuses on physical/safety impact, control system protocols, and operational technology constraints.
- **Use**: Map your environment to tactics, identify gaps in detection/response, prioritize defenses based on ICS-specific risks.

---

**OT20 — Converged IT/OT SOC**
- **Log collection**: Passive collection via SPAN ports, industrial protocol analyzers, and OT-specific collectors (Nozomi, Dragos) — no active polling.
- **SIEM integration**: Forward OT logs to central SIEM (Splunk, Sentinel) via secure connectors — correlate with IT events.
- **OT-specific detection rules**: Protocol anomalies (invalid Modbus function codes), unauthorized firmware changes, unexpected device communication, alarm suppression.
- **Alert triage workflows**: IT analysts triage initial alerts, escalate to OT engineers for domain-specific validation — joint playbooks.
- **False positives**: OT environments generate many false positives due to legacy protocols and non-standard traffic — need context-rich rules and baseline learning.
- **Firmware change alert**: Verify via asset inventory (was change authorized?), isolate the device if unauthorized, preserve logs, investigate the source (engineering workstation?), and coordinate with plant operations for safe remediation.
