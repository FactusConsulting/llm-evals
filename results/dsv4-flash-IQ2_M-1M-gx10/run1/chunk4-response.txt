## Go (20 questions)

### G1 — Easy: Slice vs Array
An array has a fixed length (`[N]T`) determined at compile time; a slice (`[]T`) is a dynamic view into an underlying array with length and capacity. When you append to a slice at capacity, Go allocates a new larger backing array (typically doubling capacity), copies existing elements, and updates the slice header. The old array becomes garbage.

### G2 — Easy: `var x int` vs `x := 0`
`var x int` declares `x` with zero value (0) and explicit type. `x := 0` uses type inference, declaring and assigning in one step. You **cannot** use `:=` at package level (only inside functions), nor can you use it when the variable is already declared (use `=` instead), or when the left-hand side has no new variables.

### G3 — Medium: Goroutines & GMP
A goroutine is a lightweight user-space thread managed by the Go runtime, starting with ~2KB stack (grows dynamically) vs OS threads with ~1MB fixed stack. The GMP model: **G**oroutine (task), **M**achine (OS thread), **P**rocessor (logical CPU). The scheduler multiplexes goroutines onto a pool of OS threads (M), with each P holding a run queue of Gs. It uses work-stealing, preemption, and handles blocking syscalls by detaching the M.

### G4 — Medium: Channels
Channels are typed conduits for goroutine communication. An **unbuffered** channel blocks the sender until a receiver is ready (synchronous handshake). A **buffered** channel has capacity; sends succeed if buffer has room, otherwise block until space frees. Sending to a full buffered channel blocks indefinitely (unless `select` with default). Closing a channel signals no more sends; receivers get zero values after close.

### G5 — Medium: context package
`context` propagates cancellation, deadlines, and request-scoped values across API boundaries. Minimal example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
req, err := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
if err != nil { /* handle */ }
resp, err := http.DefaultClient.Do(req)
if err != nil { /* handle timeout/cancel */ }
```

### G6 — Medium: Interface satisfaction
Go uses **implicit structural typing**: a type satisfies an interface if it implements all methods, with no explicit `implements` declaration. Unlike Java/C# (nominal, explicit), Go interfaces are small and composable. The empty interface `interface{}` (or `any`) accepts any type because every type has zero methods. It's powerful for generic containers but dangerous because it bypasses type safety, requiring type assertions and causing runtime panics if mismatched.

### G7 — Hard: Memory model & goroutine visibility
The code is unsafe because there's no **happens-before** relationship between the goroutine's writes and the main goroutine's reads. The compiler/CPU may reorder or cache `ready` and `data`, so the loop may never see `ready=true` or see stale `data`. Correct alternatives: use a channel (`done := make(chan struct{})`), `sync.Mutex`, `sync.WaitGroup`, or `atomic` operations. The Go memory model guarantees visibility only through synchronization primitives.

### G8 — Hard: Mutex vs RWMutex, sync.Map
`sync.Mutex` gives exclusive access; `sync.RWMutex` allows multiple readers or one writer. Use `RWMutex` for read-heavy workloads to reduce contention. `sync.Map` is optimized for read-heavy, write-once scenarios (e.g., config caches) using copy-on-write and sharded maps; it avoids lock contention but has higher overhead for typical read-write workloads. Trade-offs: `sync.Map` has amortized O(1) reads but slower writes; a regular map + `RWMutex` is simpler and faster for write-heavy or balanced workloads.

### G9 — Hard: Go modules
`go.mod` defines module path, Go version, and dependencies with versions. `go.sum` contains cryptographic checksums of module contents for integrity verification. `go mod tidy` adds missing dependencies, removes unused ones, and updates `go.sum`. **MVS (Minimum Version Selection)**: for each module, choose the minimum version that satisfies all constraints from the dependency graph, ensuring reproducibility and avoiding "dependency hell".

### G10 — Medium: defer
`defer` schedules a function call to run when the enclosing function returns. Multiple defers execute in **LIFO order** (last deferred runs first). Common gotcha: deferring in a loop accumulates calls until function exit, not per-iteration; wrap in a helper function or use `defer` inside a closure to scope it.

### G11 — Easy: Pointers
A pointer holds the memory address of a value. Zero value is `nil`. Create a pointer to a struct literal with `&MyStruct{...}` or `new(MyStruct)`. Example: `p := &Person{Name: "Alice"}`.

### G12 — Easy: init() function
`init()` runs automatically before `main()`, after package-level variable initialization. A package can have **multiple** `init()` functions; they execute in file order (by filename) within a package, and package dependencies are initialized first. Used for setup that can't be done in variable declarations.

### G13 — Easy: make vs new
`make` creates initialized values for slices, maps, and channels (returns the value, not a pointer). `new` allocates zeroed memory and returns a pointer to it, works with any type. Example: `make([]int, 5)` vs `p := new(int)`.

### G14 — Easy: Error handling
Errors are values implementing `error` interface (`Error() string`). Idiomatic pattern: check `if err != nil` immediately, handle or return. `errors.Is(err, target)` checks if err wraps target (for sentinel errors); `errors.As(err, &target)` finds a specific error type in the chain. `==` only works for direct comparison without wrapping.

### G15 — Easy: Composite types & zero values
- **map**: `nil` (read-only, write panics)
- **slice**: `nil` (len=0, append works)
- **channel**: `nil` (blocks forever on send/receive)
- **struct**: zero value of all fields (e.g., `0`, `""`, `false`)

### G16 — Medium: Race conditions
A data race occurs when multiple goroutines access the same variable concurrently, at least one writes, without synchronization. `-race` flag instruments code to detect races at runtime (using happens-before analysis). Example:
```go
var counter int
go func() { counter++ }()
go func() { counter++ }()
// race!
```
Fix with `sync.Mutex`:
```go
var mu sync.Mutex
go func() { mu.Lock(); counter++; mu.Unlock() }()
```
Or channel:
```go
ch := make(chan int, 1)
go func() { ch <- 1 }()
counter += <-ch
```

### G17 — Medium: select statement
`select` waits on multiple channel operations; it's for channels only, unlike `switch` which handles values. If multiple cases are ready, it picks one **randomly** (to prevent starvation). Timeout pattern:
```go
select {
case <-ch:
    // received
case <-time.After(2 * time.Second):
    // timeout
}
```

### G18 — Hard: Escape analysis
The compiler determines whether a variable escapes to the heap by analyzing whether its address escapes the function scope (e.g., returned, stored in global, passed to function that may store it). If it escapes, allocate on heap; otherwise stack. Inspect with `go build -gcflags=-m` (or `-m=2` for more detail). It matters because heap allocation incurs GC overhead and memory fragmentation; stack allocation is cheap and cache-friendly.

### G19 — Hard: Reflection
`reflect.Type` describes the type (kind, methods, fields); `reflect.Value` holds the runtime value and allows inspection/modification. Performance costs: reflection bypasses compiler optimizations, incurs runtime type checks, and prevents inlining; can be 10-100x slower than static dispatch. Justified for generic serialization (JSON), ORMs, testing frameworks, or when types are unknown at compile time. For performance-critical paths, prefer code generation (e.g., `go generate`) or generics.

### G20 — Hard: go:embed
`//go:embed` embeds files into the binary at compile time. Syntax:
```go
//go:embed static
var staticFS embed.FS

//go:embed file.txt
var fileContent string

//go:embed *.txt
var files embed.FS
```
Limitations: files must be in the module (no `..`), patterns can't match directories recursively (use `all:` prefix), and embedded files are read-only. It implements `io/fs.FS`, so you can use `fs.ReadFile`, `fs.WalkDir`, etc.

## Rust (20 questions)

### R1 — Easy: Ownership
Three rules:
1. Each value has a single **owner**.
2. When the owner goes out of scope, the value is **dropped**.
3. Ownership can be transferred (moved) but not borrowed implicitly.

### R2 — Easy: String vs &str
`String` owns a heap-allocated UTF-8 buffer (mutable, growable). `&str` is a borrowed reference to a string slice (immutable, fixed). In function signatures, use `&str` for read-only parameters (accepts both `&String` and `&str` via deref coercion); use `String` when you need to own or modify the data.

### R3 — Medium: Borrowing & borrow checker
Borrowing allows using a value without transferring ownership. Rules:
- You can have **many** `&T` (shared) references simultaneously.
- You can have **one** `&mut T` (mutable) reference at a time.
- Shared and mutable references cannot coexist.
The borrow checker enforces these at compile time, preventing data races and dangling references.

### R4 — Medium: Result/Option & `?`
`Result<T, E>` represents success (`Ok`) or failure (`Err`); `Option<T>` represents presence (`Some`) or absence (`None`). The `?` operator unwraps `Ok`/`Some` or returns `Err`/`None` early from the function. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    let mut file = std::fs::File::open(path)?;
    let mut contents = String::new();
    file.read_to_string(&mut contents)?;
    Ok(contents)
}
```

### R5 — Medium: Box, Rc, Arc
- `Box<T>`: single ownership, heap-allocated, for recursive types or large data.
- `Rc<T>`: single-threaded shared ownership with non-atomic reference counting (clone increments count).
- `Arc<T>`: multi-threaded shared ownership with atomic reference counting.
Use `Box` for ownership transfer, `Rc` for shared immutable data in one thread, `Arc` for shared data across threads.

### R6 — Medium: Traits vs Go interfaces
Traits are like Go interfaces but more powerful: they can have associated types, generic parameters, and default methods. Go interfaces are structural (implicit); Rust traits require explicit `impl`. **Trait objects** (`dyn Trait`) use dynamic dispatch (vtable, like Go interfaces) and have size limits. **Generics with trait bounds** (`T: Trait`) use static dispatch (monomorphization) — faster, no runtime overhead, but larger binary.

### R7 — Hard: Lifetimes
The code fails because the return type `&str` has no lifetime parameter — the compiler can't determine how long the returned reference lives. Fix by adding a lifetime parameter:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This says the returned reference lives as long as the shorter of `x` and `y`.

### R8 — Hard: Send & Sync
- `Send`: type can be transferred across threads safely.
- `Sync`: type can be shared across threads safely (references).
`Rc<T>` is not `Send` because its reference count is non-atomic; concurrent clones could race. `Arc<T>` uses atomic operations for the count, making it `Send` and `Sync` (if `T` is). `Mutex<T>` makes `T` `Sync` by providing exclusive access.

### R9 — Hard: async/await
Rust's async is **poll-based**: a `Future` is a state machine that returns `Poll::Pending` or `Poll::Ready`. An **executor** (e.g., Tokio) polls futures, schedules them on threads, and handles I/O events. Unlike Go's goroutines (preemptively scheduled, stackful), Rust futures are **stackless** — they don't allocate stacks, are composable, and can be zero-cost. Go's scheduler multiplexes goroutines onto threads; Rust's executor does similar but with explicit `Future` objects.

### R10 — Medium: unsafe
Three things you can do in `unsafe`:
1. Dereference raw pointers (`*const T`, `*mut T`).
2. Call unsafe functions (e.g., FFI to C).
3. Access or modify mutable static variables.
Unsafe is justified for FFI, implementing safe abstractions over raw memory, or performance-critical code where the compiler can't prove safety. It must be encapsulated and documented.

### R11 — Easy: Pattern matching
`match` is exhaustive — the compiler requires all possible patterns to be covered. `if let` is a shorthand for matching a single pattern (ignores others). Example:
```rust
match x {
    1 => println!("one"),
    _ => println!("other"),
}
if let Some(v) = opt { println!("{}", v); }
```

### R12 — Easy: Vec vs array
`Vec<T>` is a heap-allocated, growable sequence; `[T; N]` is a fixed-size array on the stack. When pushing beyond capacity, `Vec` allocates a new larger buffer (typically doubles), copies elements, and deallocates the old one. This is amortized O(1) per push.

### R13 — Easy: Enums & Option
Rust enums are **algebraic data types** — they can hold data (like tagged unions), unlike C/Java enums which are just named constants. `Option<T>` is `Some(T)` or `None`, replacing null. Rust has no null because it eliminates null pointer errors at compile time — absence is explicit via `Option`.

### R14 — Easy: impl blocks
`impl` defines methods and associated functions. Methods take `&self` (immutable borrow), `&mut self` (mutable borrow), or `self` (consumes the value). Associated functions (e.g., `String::new()`) don't take `self` and are called with `::`.

### R15 — Easy: derive macro
`#[derive(Debug, Clone, PartialEq)]` auto-implements traits by generating code based on the struct's fields. You **cannot** derive traits that require manual logic (e.g., `Display` with custom formatting, `From` with conversion rules, or traits with associated types like `Iterator`).

### R16 — Medium: Cow
`Cow<'a, T>` (clone-on-write) is an enum: `Borrowed(&'a T)` or `Owned(T)`. It starts borrowed and only clones when mutation is needed. Useful for read-mostly data where you might need to modify. Example:
```rust
fn process(input: &str) -> Cow<'_, str> {
    if input.contains("bad") {
        Cow::Owned(input.replace("bad", "good"))
    } else {
        Cow::Borrowed(input)
    }
}
```
Avoids allocation when no change is needed.

### R17 — Medium: Module system
`mod` declares a module (inline or from file), `use` brings items into scope, `pub` makes items public. In Rust 2015, modules map to files: `mod foo;` loads `foo.rs` or `foo/mod.rs`. In Rust 2018, `mod foo;` loads `foo.rs` or `foo/mod.rs` (same), but `use` paths are more uniform, and `crate::` refers to the current crate root.

### R18 — Hard: Pin & self-referential structs
`Pin<T>` prevents moving the value out of its memory location. Needed for self-referential structs (e.g., a struct holding a pointer to its own field) because moving would invalidate the pointer. In async/await, futures may be self-referential (e.g., borrowing across await points), so they must be `Pin`ned before polling. `Unpin` is a marker trait for types that can be moved freely (most types); `Pin<Box<dyn Future>>` is common for async tasks.

### R19 — Hard: Macros
- **Declarative** (`macro_rules!`): pattern-matching on tokens, generates code. Hygienic — local variables are scoped to the macro.
- **Procedural** (`#[derive]`, attribute, function-like): Rust code that processes token streams and generates code. More powerful but must be in a separate crate.
Hygiene rules: declarative macros prevent name collisions by scoping; procedural macros have full control but must be careful.

### R20 — Hard: Zero-cost abstractions
Rust achieves C-level performance via:
- **Iterators**: compile to direct loops with no allocation (e.g., `iter().map().filter().sum()` is as fast as a hand-written loop).
- **Generics (monomorphization)**: each instantiation generates specialized code, no virtual dispatch overhead.
- **Static dispatch**: trait bounds on generics resolve at compile time, unlike `dyn Trait` (vtable).
- **Ownership/lifetimes**: eliminate garbage collection and runtime checks, enabling predictable memory layout and inlining.
