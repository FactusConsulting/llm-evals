**K1 — Easy:** A Deployment manages stateless applications, ensuring a desired number of identical pods run at all times. A StatefulSet manages stateful applications, providing stable network identities (stable hostnames), stable persistent storage (via PVCs), and ordered deployment/scaling/termination. Deployments use interchangeable pods; StatefulSets require stable identity and storage.

**K2 — Easy:** A ClusterIP Service acts as a virtual IP (VIP) in the cluster. kube-proxy (or a proxy mode like IPVS) watches the Service and its Endpoints (the pod IPs matching the selector). It programs iptables/IPVS rules on nodes to intercept traffic destined for the ClusterIP and randomly forward it to one of the backend pod IPs, performing load balancing and NAT.

**K3 — Medium:** A PersistentVolume (PV) is a cluster-level storage resource, provisioned by an admin or dynamically via a StorageClass. A PersistentVolumeClaim (PVC) is a request for storage by a user/pod, binding to a PV that meets its size/access mode requirements. A StorageClass defines the provisioner and parameters (e.g., type, IOPS) for dynamically provisioning PVs when a PVC requests it. They relate as: PVC → StorageClass → dynamically creates PV → PVC binds to PV → Pod mounts PVC.

**K4 — Medium:** Troubleshooting CrashLoopBackOff:
1. **Check pod logs:** `kubectl logs <pod> --previous` to see why the last container exited (e.g., panic, error).
2. **Check events:** `kubectl describe pod <pod>` for OOMKill, liveness probe failures, or image pull errors.
3. **Check resource limits:** Verify if the container is exceeding memory limits (OOMKilled) or CPU throttling.
4. **Check startup/liveness probes:** Verify probe paths, ports, and timeouts; a failing liveness probe restarts the container.
5. **Check dependencies:** Verify the pod can reach required services (DB, API) and that ConfigMaps/Secrets are correctly mounted.

**K5 — Medium:** CoreDNS is the cluster's DNS server. It serves DNS records for Services and Pods (e.g., `service.namespace.svc.cluster.local`). If CoreDNS is down, internal DNS resolution fails, breaking service discovery. External DNS resolution may still work if pods have external DNS servers configured in `/etc/resolv.conf`, but internal service names will fail to resolve, causing application errors.

**K6 — Hard:** The scheduler uses a two-phase process: **Filtering** (feasibility) and **Scoring** (preference). Filtering removes nodes that don't meet hard constraints (e.g., insufficient resources, failing affinity/anti-affinity, taints not tolerated, node conditions like `DiskPressure`). Scoring ranks remaining nodes based on soft constraints (e.g., spreading across zones, packing, least-requested resources). Specific factors: (1) **Resource requests** (CPU/memory) vs. node allocatable; (2) **Node affinity/anti-affinity** rules; (3) **Pod affinity/anti-affinity**; (4) **Taints and tolerations**; (5) **Data locality** (if using volume zone constraints); (6) **Node selectors** and labels.

**K7 — Hard:** **Scheduling:** The pod requests 256Mi. The node has 4GB total, 3.5GB already requested, leaving 500Mi allocatable. Since 256Mi < 500Mi, the pod **will be scheduled** (assuming no other constraints). **Runtime:** If it uses 600Mi, it exceeds its limit (512Mi). The kernel will likely OOMKill the container (or the runtime will enforce the limit via cgroups). If it only exceeds requests but stays under limits, it's fine but may be evicted under pressure.

**K8 — Hard:** 1. **External LB** (e.g., cloud LB) forwards traffic to the Ingress Controller's NodePort or LoadBalancer service. 2. **Ingress Controller** (NGINX) receives the request, parses the Ingress resource for routing rules (host/path). 3. It resolves the backend Service name to a ClusterIP. 4. It forwards the request to the Service's ClusterIP. 5. **kube-proxy** intercepts the ClusterIP traffic via iptables/IPVS rules. 6. It selects a backend pod IP from the Service's **Endpoints** (the list of pod IPs matching the selector). 7. It NATs and forwards the request to the pod's IP. 8. The application pod receives the request.

**K9 — Medium:** A NetworkPolicy is a rule that controls traffic between pods, namespaces, or external IPs (ingress/egress). **Default behavior:** If no NetworkPolicy exists, all traffic is allowed (no isolation). **When you apply one:** It selects pods via labels and applies the rules. It also **isolates** the selected pods, meaning all traffic not explicitly allowed by the policy is denied (unless a default-allow rule is added).

**K10 — Medium:** **RollingUpdate:** Updates pods incrementally, keeping some old pods running while new ones start, ensuring zero downtime. **Recreate:** Terminates all old pods before creating new ones, causing downtime. **Choose Recreate** when: the application cannot tolerate multiple versions running simultaneously (e.g., schema changes that break old versions), or when a rolling update would cause conflicts (e.g., single-writer databases).

**K11 — Easy:** A namespace is a virtual cluster partition that isolates resources (pods, services, etc.) and provides a scope for names. Default namespaces: `default` (for user resources), `kube-system` (for system components), `kube-public` (publicly readable), `kube-node-lease` (for node heartbeats).

**K12 — Easy:** `kubectl describe pod` shows detailed metadata and status. Three pieces it shows that `get` does not: (1) **Events** (e.g., pulling image, failed scheduling, OOMKill); (2) **Detailed container status** (e.g., last state, exit code, reason, restart count); (3) **Resource limits/requests** and **liveness/readiness probe configurations**.

**K13 — Easy:** A ConfigMap stores configuration data as key-value pairs. Pods consume it via: (1) **Environment variables** (e.g., `valueFrom: configMapKeyRef`); (2) **Volume mount** (mounted as files in a directory); (3) **Command-line arguments** (using env vars in the command).

**K14 — Easy:** **ClusterIP:** Internal-only virtual IP, accessible only within the cluster. **NodePort:** Exposes the Service on a static port on each node's IP, allowing external access via `nodeIP:nodePort`. **LoadBalancer:** Uses the cloud provider's LB to expose the Service externally, routing to the NodePorts or directly to pods.

**K15 — Easy:** A DaemonSet ensures a copy of a pod runs on every node (or a subset). Use it for cluster-level agents like log collectors (Fluentd), monitoring agents (Prometheus Node Exporter), or networking plugins (CNI). Deployments are for stateless apps that scale; DaemonSets are for node-level infrastructure.

**K16 — Medium:** **Taints and tolerations** are applied to nodes and pods, respectively. A taint on a node repels pods that don't tolerate it. **Node affinity** attracts pods to nodes based on labels. Taints are a hard "do not schedule here" (unless tolerated), while affinity is a soft/hard preference. Use cases: Taints for dedicated nodes (e.g., GPU-only nodes), tolerations for special pods (e.g., master nodes). Affinity for co-locating pods (e.g., same zone) or preferring specific hardware.

**K17 — Medium:** A Kubernetes Operator is a pattern that extends Kubernetes to manage a specific application or service (e.g., databases, message queues). It uses custom resources (CRDs) and a controller that watches the resource's desired state and reconciles the actual state. It differs from a standard controller (like a Deployment controller) because it is application-specific and encodes domain knowledge (e.g., backup, scaling, upgrades). It solves the problem of managing complex stateful applications that require operational knowledge beyond simple pod management.

**K18 — Hard:** etcd uses the **Raft consensus algorithm**. It requires a quorum (majority) of nodes to agree on writes. If quorum is lost (e.g., 2 of 3 nodes down), the cluster becomes **read-only** for writes (to avoid split-brain). **Recovery:** If 2 of 3 are permanently lost, you must restore from a backup. You would stop etcd on the surviving node, restore the data directory from a snapshot, and then start a new single-node cluster (or rebuild the cluster with new members). You cannot simply add new members without restoring data, as the surviving node's data is stale.

**K19 — Hard:** RBAC uses four objects: **Role** (namespace-scoped permissions), **ClusterRole** (cluster-wide permissions), **RoleBinding** (binds a Role to a user/group/SA in a namespace), **ClusterRoleBinding** (binds a ClusterRole cluster-wide). Manifests for read-only pods/logs in `dev` namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: dev, name: pod-reader }
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: dev, name: dev-pod-reader }
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:** Pods have `ndots:5` by default, meaning DNS queries for names with fewer than 5 dots are tried as fully qualified names first (e.g., `service.namespace.svc.cluster.local`). For external domains like `example.com`, the resolver tries `example.com.<search-domain>` (e.g., `example.com.default.svc.cluster.local`) first, causing multiple failed queries before falling back to the real domain. This adds latency. **Fix:** Set `dnsConfig: { options: [ { name: ndots, value: "1" } ] }` in the pod spec, so external queries are attempted directly first, reducing search domain lookups.

**D1 — Easy:** `git rebase` rewrites history by replaying commits onto a new base, creating a linear history. `git merge` creates a merge commit, preserving the branching history. Avoid rebasing when: the branch is shared/public (rewriting history breaks other developers' clones), or when you want to preserve the exact commit history for auditing.

**D2 — Easy:** TCP is connection-oriented, reliable, ordered, and provides flow control (e.g., HTTP, FTP). UDP is connectionless, unreliable, unordered, and low-latency (e.g., DNS, video streaming, VoIP).

**D3 — Medium:** A race condition occurs when multiple threads/processes access shared data concurrently, and the outcome depends on the timing of their execution. Example (Python):
```python
balance = 100
def withdraw(amount):
    global balance
    if balance >= amount:
        time.sleep(0.1)  # context switch
        balance -= amount
# Two threads call withdraw(80) concurrently -> both pass the check, balance becomes -60.
```

**D4 — Medium:** Symmetric encryption uses the same key for encryption/decryption (fast, e.g., AES). Asymmetric uses a public/private key pair (slow, e.g., RSA). In TLS: the client verifies the server's certificate using asymmetric encryption (public key), then they exchange a symmetric session key (e.g., via Diffie-Hellman) for fast bulk data encryption.

**D5 — Medium:** A container image layer is a filesystem diff, created by each instruction in a Dockerfile. Layers are cached; if a layer is unchanged, it's reused. Best practices: order instructions from least to most frequently changing (e.g., install dependencies before copying source code), combine `RUN` commands to reduce layers, and use `.dockerignore` to avoid invalidating the cache.

**D6 — Medium:** Troubleshooting 503 (Service Unavailable):
1. **Check application health:** Is the app actually up? (e.g., `/healthz` endpoint).
2. **Check load balancer/ingress config:** Is the service defined correctly? Are there unhealthy backends?
3. **Check backend service/pods:** Are pods running? Are they ready? (e.g., `kubectl get pods`, `kubectl describe`).
4. **Check dependencies:** Is the database/redis reachable? Are there connection pool exhaustion issues?
5. **Check logs and metrics:** Look for errors, high latency, or rate limiting.

**D7 — Hard:** CAP theorem states a distributed system can only guarantee two of: Consistency (all nodes see the same data), Availability (every request gets a response), Partition tolerance (system works despite network partitions). **CP example:** etcd (sacrifices availability during partition to maintain consistency). **AP example:** Cassandra (sacrifices consistency, allows stale reads, but remains available during partitions).

**D8 — Medium:** Horizontal scaling adds more machines/nodes (scale out), increasing parallelism. Vertical scaling adds more resources (CPU/RAM) to a single machine (scale up). Patterns enabling horizontal: stateless services (no session state), distributed databases (sharding), message queues, and load balancers.

**D9 — Easy:** An environment variable is a key-value pair in the shell environment. To persist across sessions on Linux, add `export VAR=value` to `~/.bashrc` (or `~/.profile`) and source it (`source ~/.bashrc`).

**D10 — Easy:** JSON is a text-based data format using key-value pairs and arrays. YAML is a human-readable serialization format using indentation. JSON advantage: widely supported, strict, good for APIs. YAML advantage: more readable, supports comments, better for config files.

**D11 — Easy:** REST API is an architectural style for building web services using HTTP. **GET:** Retrieve a resource (idempotent). **POST:** Create a resource (non-idempotent). **PUT:** Update/replace a resource (idempotent). **DELETE:** Remove a resource.

**D12 — Easy:** Version pinning means specifying exact versions for dependencies (e.g., `package.json` with `exact` versions, `requirements.txt` with `==`). It ensures reproducible builds by preventing unexpected changes from dependency updates.

**D13 — Easy:** Compiled languages are translated to machine code before execution (e.g., C, Go). Interpreted languages are executed line-by-line by an interpreter at runtime (e.g., Python, JavaScript).

**D14 — Medium:** A reverse proxy sits in front of backend servers, forwarding client requests to them (e.g., Nginx, HAProxy). A forward proxy sits in front of clients, forwarding their requests to the internet (e.g., corporate proxy). Use cases: Reverse proxy for load balancing, TLS termination, caching; forward proxy for content filtering, anonymity, bypassing geo-restrictions.

**D15 — Medium:** A deadlock is a state where two or more processes are blocked, each waiting for the other to release a resource. Coffman conditions: (1) **Mutual exclusion** (resource is non-shareable), (2) **Hold and wait** (process holds a resource while waiting for another), (3) **No preemption** (resources cannot be forcibly taken), (4) **Circular wait** (a cycle of processes waiting for each other).

**D16 — Hard:** Eventual consistency means that if no new updates occur, all replicas will eventually converge to the same value. Cassandra handles read-after-write consistency via tunable consistency levels (e.g., `ONE`, `QUORUM`, `ALL`). For read-after-write, you can use `QUORUM` for both reads and writes to ensure the latest value is read. Other levels: `LOCAL_QUORUM`, `EACH_QUORUM`, `ANY`.

**D17 — Hard:** mTLS (mutual TLS) is TLS where both client and server authenticate each other. Handshake: 1. Client sends `ClientHello`. 2. Server responds with `ServerHello`, its certificate, and requests client certificate. 3. Client verifies server cert, sends its own certificate and a signed `CertificateVerify` message. 4. Server verifies client cert. 5. Both derive a session key via key exchange (e.g., ECDHE). 6. Finished messages confirm the handshake. Used in service meshes (Istio), zero-trust networks, and internal API gateways.

**D18 — Hard:** A hash table uses a hash function to map keys to indices in an array. **Collision resolution:** Chaining (each bucket is a linked list; insert at head) vs. Open addressing (probing: linear, quadratic, double hashing; find next empty slot). **Time complexity:** Average: O(1) for insert/lookup/delete. Worst case (all keys collide): O(n) for all operations.

**D19 — Hard:** Circuit breaker pattern prevents cascading failures by failing fast when a downstream service is unhealthy. **States:** Closed (normal, requests pass), Open (fail fast, no requests pass), Half-open (allow a few test requests to see if the service recovered). It relates to retry policies by preventing infinite retries during an outage; exponential backoff (increasing wait time between retries) is used in the half-open state to probe recovery.

**D20 — Hard:** Optimistic concurrency control assumes conflicts are rare; it checks for conflicts at commit time (e.g., using a version column or timestamp). Pessimistic concurrency control locks resources upfront (e.g., `SELECT FOR UPDATE`) to prevent conflicts. Choose optimistic for read-heavy workloads with low contention; pessimistic for write-heavy workloads where conflicts are likely and data integrity is critical. Example: Optimistic uses `UPDATE ... WHERE version = ?`; Pessimistic uses `SELECT * FROM accounts WHERE id = ? FOR UPDATE` before updating.
