## Application Architecture

**AA1 — Monolith vs. Microservices**
A monolith is a single deployable unit containing all application logic, while microservices decompose the application into independently deployable services, each with its own data store and API. Three concrete problems microservices introduce that monoliths don't: (1) **Distributed network complexity** — services communicate over the network, introducing latency, partial failures, and serialization overhead; (2) **Distributed data consistency** — each service owns its database, making cross-service transactions difficult and requiring patterns like Sagas; (3) **Operational overhead** — multiple services require CI/CD pipelines, monitoring, tracing, and orchestration (Kubernetes) that a single monolith doesn't need.

**AA2 — Synchronous vs. Asynchronous Communication**
Synchronous communication blocks the caller until the receiver responds — the caller waits for a reply. Example: REST over HTTP (client sends request, waits for 200/201 response). Asynchronous communication allows the caller to continue without waiting — the message is sent and processed later. Example: message queues like RabbitMQ or Kafka (producer publishes, consumer processes independently). Synchronous is simpler for request-response flows; asynchronous decouples services, improves resilience, and handles bursts.

**AA3 — API Gateway vs. Reverse Proxy**
A reverse proxy forwards client requests to backend servers, typically handling TLS termination, load balancing, and simple routing. An API Gateway is a specialized reverse proxy that adds API-specific features: authentication/authorization, rate limiting, request/response transformation, API versioning, circuit breaking, and analytics. An API Gateway **cannot** fully replace a reverse proxy — a reverse proxy operates at the network/L7 level for any traffic (including WebSockets, static files, gRPC), while an API Gateway is API-focused. In practice, you often run both: a reverse proxy (Nginx/HAProxy) in front of an API Gateway.

**AA4 — Saga Pattern**
The Saga pattern manages distributed transactions across multiple services by breaking them into a series of local transactions, each with a compensating action to undo it if a later step fails. **Choreography-based sagas** use events — each service listens for events, performs its local transaction, and publishes the next event. No central coordinator; services are loosely coupled but the flow is harder to trace. **Orchestration-based sagas** use a central coordinator (orchestrator) that commands each service and handles compensation logic. Choreography is appropriate for simple flows with few services and where eventual consistency is acceptable; orchestration is better for complex flows requiring clear control, error handling, and auditability.

**AA5 — CQRS and Event Sourcing**
CQRS separates the command model (writes) from the query model (reads), using different data stores or schemas optimized for each. Event Sourcing stores state as an immutable sequence of events, where the current state is derived by replaying events. They're paired because CQRS's write model naturally uses events as the source of truth, and the read model can be projected from those events. This combination solves the problem of traditional CRUD where a single model must serve both write-heavy and read-heavy workloads, leading to contention, poor scalability, and difficulty auditing changes. Event sourcing provides a complete audit trail, temporal queries, and easy replay/rebuild of read models.

**AA6 — Circuit Breaker Pattern**
The Circuit Breaker pattern prevents a service from repeatedly calling a failing dependency. Three states: **Closed** (normal operation, requests pass), **Open** (fail fast — requests fail immediately without hitting the dependency), **Half-Open** (allows a few test requests to see if the dependency recovered). It differs from simple retry with backoff because it fails fast at the client level, preventing resource exhaustion and cascading failures. Use both together: circuit breaker for coarse-grained failure detection (stop hammering a down service), retry with backoff for transient failures (e.g., 503s) within the closed state. Circuit breaker also needs a retry mechanism in half-open state to test recovery.

**AA7 — Multi-Tenant Isolation Models**
1. **Shared DB, shared schema (row-level tenant ID)**: Lowest cost (one database, minimal overhead), simplest operations, but weakest security (risk of SQL injection or bug exposing cross-tenant data), highest noisy-neighbor risk (one tenant's heavy query impacts all), and hardest to scale per-tenant. 2. **Shared DB, separate schema per tenant**: Moderate cost (one DB, multiple schemas), better isolation (schema-level security), easier to migrate/backup per tenant, but still shares compute resources — noisy neighbor remains. 3. **Separate DB per tenant**: Highest cost (per-tenant infrastructure), strongest security and isolation, no noisy neighbor, but operational complexity scales with tenant count (backups, monitoring, migrations). Trade-off: cost vs. security vs. operational complexity vs. noisy-neighbor risk — choose based on tenant trust level and regulatory requirements.

**AA8 — Eventual vs. Strong Consistency for Inventory**
Eventual consistency means reads may return stale data but will converge over time; strong consistency guarantees every read returns the latest committed write. For a never-oversell inventory system, you need **strong consistency** on the inventory count. Architecture: use a single-node database (e.g., PostgreSQL with `SELECT ... FOR UPDATE` or Redis with atomic operations) as the source of truth for inventory. At scale, use sharding by product ID with a strongly consistent store per shard, or use a distributed transaction coordinator. Patterns: optimistic locking with version numbers, atomic decrement operations (`UPDATE inventory SET quantity = quantity - 1 WHERE id = ? AND quantity >= 1`), and a reservation system with timeouts. For high throughput, use Redis with Lua scripts for atomicity, then asynchronously persist to a durable store.

**AA9 — Sidecar Proxy and Service Mesh**
A sidecar proxy is a lightweight proxy deployed alongside each service instance, handling network communication (routing, retries, TLS, observability) on behalf of the service. In Istio, **Envoy** is the sidecar proxy that intercepts all traffic in/out of the pod. The **data plane** consists of all Envoy proxies that handle actual traffic; the **control plane** (Istiod) manages configuration, certificate distribution, and policy. mTLS between sidecars solves the problem of **service-to-service authentication and encryption at the network layer** — application-level TLS only protects specific endpoints and requires application code changes; sidecar mTLS provides uniform, transparent encryption and identity verification for all traffic, including legacy services that don't support TLS.

**AA10 — Strangler Fig Pattern**
The Strangler Fig pattern incrementally replaces parts of a legacy system with new services while keeping the overall system functional. For a .NET Framework monolith migrating to .NET 8 microservices: (1) Start by identifying seams — extract bounded contexts (e.g., billing, user management) into separate modules. (2) Create a facade (API Gateway or reverse proxy) that routes requests to either the legacy monolith or new microservices. (3) Incrementally extract one service at a time — e.g., move the "invoicing" module to a .NET 8 microservice with its own database, and have the monolith call it via HTTP or message queue. (4) Use strangler routes — gradually shift traffic from monolith to new service. (5) Once all modules are extracted, decommission the monolith. This minimizes risk by keeping the system running during migration.

**AA11 — 12-Factor App**
The 12-Factor methodology defines best practices for building cloud-native applications. Six key factors: (1) **Codebase** — one codebase, multiple deploys (no code duplication). (2) **Dependencies** — explicitly declare and isolate dependencies (no implicit system packages). (3) **Config** — store configuration in environment variables, not code. (4) **Backing services** — treat databases, caches, etc. as attached resources, swappable via config. (5) **Stateless processes** — processes are stateless and share nothing; state goes in external stores. (6) **Port binding** — the app exports services via HTTP, not embedded in a web server. These matter for cloud-native because they enable portability, horizontal scaling, and continuous deployment.

**AA12 — Event-Driven vs. Request-Driven**
**Event-driven (Kafka)**: Services communicate via events; producers publish, consumers subscribe. Coupling is loose (services don't know each other). Scalability is high (partitioning, replay). Debugging is harder (no direct request-response, need tracing). Ordering is per-partition (guaranteed within a partition). Failure handling: events are durable, can be replayed; consumers must handle retries. **Request-driven (REST/gRPC)**: Direct synchronous calls. Coupling is tight (client knows server). Scalability is limited by request latency and server capacity. Debugging is easier (request-response traceable). Ordering is natural (caller waits). Failure handling: retries, timeouts, circuit breakers. Choose event-driven for decoupling, async workflows, and high-throughput pipelines; choose request-driven for simple CRUD, low-latency interactive requests, and when you need immediate responses.

**AA13 — Load Balancer, L4 vs. L7**
A load balancer distributes incoming traffic across multiple backend servers. **Layer 4** (transport) balances based on IP address and TCP/UDP port — it forwards raw packets without inspecting content. **Layer 7** (application) inspects HTTP headers, URLs, cookies, and can route based on content (e.g., `/api` to one service, `/static` to another). Layer 7 is required for: content-based routing, SSL termination, sticky sessions based on cookies, and HTTP-level health checks.

**AA14 — Message Queue vs. Log-Based Broker**
A message queue (RabbitMQ) delivers messages to consumers and removes them after consumption — each message is consumed once. A log-based broker (Kafka) stores messages in an append-only log; consumers maintain offsets and can replay messages. RabbitMQ is better for task distribution (each message processed once) and complex routing (topics, headers). Kafka is better for event streaming, replayability, and high-throughput pub/sub where consumers need independent progress. Choose RabbitMQ for simple job queues; choose Kafka for event sourcing, stream processing, and when you need message replay.

**AA15 — Container vs. VM**
A container shares the host OS kernel and packages the application with its dependencies (libraries, binaries) as isolated processes. A VM includes a full guest OS with its own kernel, running on a hypervisor. Containers are lighter (MBs vs GBs), start faster (seconds vs minutes), and have lower overhead. They're popular for microservices because they provide consistent environments, efficient resource utilization, and fast scaling — you can run hundreds of containers on one host.

**AA16 — Stateless vs. Stateful Services**
Stateless services don't store any session or user data — each request is independent and can be handled by any instance. Stateful services maintain state (e.g., user sessions, database data) that must be preserved across requests. Stateless services are easier to scale horizontally because any instance can handle any request — you just add more instances behind a load balancer; no need to sync state or route requests to the same instance. Example: a stateless REST API that reads from a shared database; a stateful example: a WebSocket chat server that maintains connection state per user.

**AA17 — ORM**
An ORM maps database tables to objects in code, abstracting SQL. Two popular ORMs: Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs increase developer productivity (no SQL boilerplate), provide type safety, and handle relationships. But they add overhead (lazy loading, N+1 queries), can generate inefficient SQL, and obscure database-specific features. Raw SQL gives full control, better performance for complex queries, and easier optimization, but requires more code and is error-prone.

**AA18 — Bulkhead Pattern**
The Bulkhead pattern isolates failures by partitioning resources (thread pools, connections, deployment groups) so that a failure in one part doesn't exhaust resources for others. In microservices, it prevents one slow service from consuming all threads/connections and blocking others. Example: in a Java app, use separate thread pools for different downstream services — if Service A is slow, its pool fills up but Service B's pool remains available. At the deployment level, run critical services in separate Kubernetes namespaces or separate nodes so a noisy neighbor doesn't impact them.

**AA19 — OT vs. CRDTs for Collaborative Editing**
**OT** transforms operations to account for concurrent edits, ensuring convergence. It requires a central server or deterministic ordering, has low latency for small groups, but is complex to implement (transformation functions for every operation type) and has poor offline support (requires server for conflict resolution). **CRDTs** use commutative/associative/idempotent operations that converge without a central coordinator. They support offline editing naturally (each replica merges on sync), are simpler in some ways, but have higher memory overhead and can be less efficient for large documents. For a system that must support offline editing, **CRDTs** are the better choice — they allow any replica to merge changes without a central server, providing true offline-first support. (e.g., Yjs uses CRDTs).

**AA20 — Distributed Tracing Challenges**
Distributed tracing across polyglot microservices requires: (1) **Context propagation** — trace IDs must be passed via headers (W3C Trace Context `traceparent`, B3 `X-B3-TraceId`) through every service call. (2) **Sampling** — head-based sampling (decide at the first service) is simple but can miss critical traces; tail-based sampling (decide after collecting all spans) is more accurate but requires a central collector. (3) **Storage/querying** — Jaeger/Tempo store traces in object stores or databases; querying requires indexing by trace ID and service. (4) **Async messaging** — Kafka messages must carry trace context in message headers; the producer injects the trace ID, and the consumer extracts it to continue the trace. To ensure continuity through Kafka: set the trace context as a Kafka message header (e.g., `traceparent`), and have the consumer use that header to create a child span. This requires consistent instrumentation across all languages (OpenTelemetry SDKs).

## On-Premise Infrastructure Architecture

**OP1 — Hypervisor Type 1 vs. Type 2**
Type 1 (bare-metal) hypervisor runs directly on hardware, providing high performance and low overhead. Examples: VMware ESXi, Microsoft Hyper-V (with Hyper-V server), KVM (as a kernel module). Type 2 (hosted) hypervisor runs on top of an existing OS, adding overhead. Examples: Oracle VirtualBox, VMware Workstation/Fusion. Type 1 is used in production data centers; Type 2 for development/testing.

**OP2 — SAN vs. NAS**
SAN (Storage Area Network) provides block-level storage accessed as raw disks (LUNs) over Fibre Channel or iSCSI. NAS (Network Attached Storage) provides file-level storage accessed as shared folders over NFS or SMB/CIFS. Use SAN for databases, virtual machine disks, and applications requiring low-latency block access; use NAS for file sharing, home directories, and shared documents. SAN protocols: Fibre Channel, iSCSI, FCoE. NAS protocols: NFS, SMB.

**OP3 — 3-Tier vs. Leaf-Spine**
3-tier architecture: Core (routing/backbone), Distribution (policy, aggregation), Access (end-user connectivity). It's hierarchical but has bottlenecks at the core and limited east-west bandwidth. Leaf-spine: every leaf switch connects to every spine switch (full mesh), providing predictable low-latency east-west traffic and easy scaling (add spines or leaves). Leaf-spine solves the problem of **oversubscription and bottlenecks** — in 3-tier, traffic between servers on different access switches must traverse the distribution and core, creating latency and congestion; leaf-spine provides uniform any-to-any connectivity with consistent latency.

**OP4 — Highly Available Proxmox Cluster**
Architecture: 3+ nodes (odd number for quorum). Use **Corosync** for cluster communication and **QDevice** as a quorum tiebreaker (or a fourth node). Shared storage: **Ceph** (preferred — provides distributed storage with replication), iSCSI (central SAN), or NFS (simplest but single point of failure). Configure fencing (STONITH) to power off unresponsive nodes. On node failure: the cluster detects loss of quorum, fences the failed node, and VMs are migrated to surviving nodes (HA agent restarts them). Ceph handles storage redundancy automatically via replication (e.g., 3 replicas). For 2-node clusters, add a QDevice (external arbiter) to avoid split-brain.

**OP5 — VLAN Trunking and 802.1Q**
VLAN trunking carries multiple VLANs over a single link by tagging frames with 802.1Q headers (adds a 4-byte tag with VLAN ID). On Linux, configure a trunk on a single NIC using `ip link add link eth0 name eth0.10 type vlan id 10` for each VLAN, then assign IPs to each VLAN interface. Example: `ip link add link eth0 name eth0.10 type vlan id 10; ip link add link eth0 name eth0.20 type vlan id 20; ip addr add 192.168.10.1/24 dev eth0.10; ip addr add 192.168.20.1/24 dev eth0.20`. The switch port must be configured as a trunk port.

**OP6 — RAID Levels**
RAID 1: mirroring — 2 drives, 1 disk failure tolerance, 50% capacity. RAID 5: striping with parity — 3+ drives, 1 disk failure, capacity = (N-1)/N. RAID 6: striping with double parity — 4+ drives, 2 disk failures, capacity = (N-2)/N. RAID 10: striped mirrors — 4+ drives, 1 disk failure per mirror pair, 50% capacity, high performance. RAID Z2 (ZFS): similar to RAID 6 but with variable block sizes and checksums — 2 disk failures, capacity = (N-2)/N. For a database server with 6 drives: **RAID 10** — best performance (mirror + stripe), good fault tolerance (can lose 1 disk per pair), but only 3 TB usable from 6 TB. If capacity is critical, RAID 6 (4 TB usable) but slower for random writes. For databases, performance and fault tolerance outweigh capacity — choose RAID 10.

**OP7 — Enterprise DNS Architecture**
Design: (1) **Internal DNS** — Active Directory-integrated DNS on domain controllers, serving internal zones (e.g., `internal.corp.com`). (2) **DMZ DNS** — separate authoritative servers for public zones (`corp.com`) in the DMZ, with DNSSEC signing. (3) **Split-horizon** — internal and external views of the same zone; internal resolvers return internal IPs, external resolvers return public IPs. (4) **Recursive resolvers** — internal DNS servers forward external queries to ISP or public resolvers (e.g., 8.8.8.8) or use root hints. (5) **Conditional forwarding** — internal servers forward queries for `corp.com` to AD DNS, and for `dmz.corp.com` to DMZ servers. When a laptop moves between office and VPN: the DNS client uses the DHCP-assigned DNS server (office) or VPN-assigned DNS (VPN). The VPN DNS server must resolve internal names; the laptop's DNS suffix search list must include `corp.com`. DNSSEC on the external zone ensures clients can validate public records; internal zones may skip DNSSEC for simplicity.

**OP8 — PKI Chain of Trust**
Chain: Root CA (offline, self-signed) → Subordinate/Issuing CA (online, signed by root) → End-entity certificates (signed by issuing CA). For internal PKI: (1) Stand up an **offline root CA** (air-gapped, stored securely) — it issues only the subordinate CA certificate. (2) Deploy **issuing CAs** (online) for different purposes (e.g., user certs, server certs, code signing). (3) Use **certificate templates** to define enrollment policies (key usage, validity, auto-enrollment). (4) **Auto-enrollment** via Group Policy for domain-joined machines/users. **CRL vs. OCSP**: CRL is a list of revoked certs (can be large, stale); OCSP is a real-time check (online responder). Use OCSP for fast validation. Consequences: a compromised **subordinate CA** can be revoked (via CRL/OCSP) and replaced — limited damage; a compromised **root CA** invalidates the entire PKI — you must rebuild the whole chain, reissue all certificates, and trust is broken.

**OP9 — Hub-and-Spoke WAN Comparison**
- **MPLS**: Carrier-managed, high reliability, QoS for VoIP, but expensive, long deployment, less flexible.
- **IPsec VPN over internet**: Cheap, uses existing internet, but best-effort (no QoS), latency/jitter varies, management complexity for many sites.
- **SD-WAN**: Overlay on internet/MPLS, central management, application-aware routing, can prioritize VoIP, cost-effective, but requires SD-WAN devices and a controller.
- **WireGuard mesh**: Simple, fast, modern crypto, but no QoS, no central management, best for small sites.
For 50 users/site with latency-sensitive VoIP: **SD-WAN** — it provides application-aware routing (prioritize VoIP), uses cost-effective internet links, central management, and can failover to secondary links. If budget allows, hybrid SD-WAN with MPLS for critical traffic.

**OP10 — iDRAC/iLO/IPMI**
iDRAC (Dell), iLO (HPE), IPMI (standard) are out-of-band management interfaces on servers that allow remote monitoring, power control, console access, and hardware health checks even when the OS is down. Critical because they provide **lights-out management** — you can reboot, view POST, and diagnose hardware failures remotely. If exposed to the internet: attackers can gain full control of the server (power off, boot from ISO, access BIOS), leading to complete compromise. Mitigate: restrict to management VLAN, use strong auth, disable default accounts, and never expose directly to the internet.

**OP11 — LVM vs. LVM-Thin vs. ZFS**
- **LVM**: Traditional volume manager — creates logical volumes from physical volumes, supports snapshots (copy-on-write but can be slow with large volumes), resizing, and LVM mirroring.
- **LVM-Thin**: Thin provisioning — allocates blocks on demand, supports efficient snapshots (fast, space-efficient), and better for virtual machine storage (e.g., Proxmox).
- **ZFS**: Full filesystem + volume manager — provides checksums, snapshots (instant, space-efficient), compression, RAID-Z, and data integrity. Use LVM for simple partitioning; LVM-Thin for VM storage with snapshots; ZFS for data integrity, compression, and advanced snapshotting. Snapshot semantics: LVM snapshots are COW (copy-on-write) and can degrade performance; LVM-Thin snapshots are efficient but require thin pool; ZFS snapshots are instant, read-only, and space-efficient.

**OP12 — Proxmox/Ceph Stretch Cluster**
Design: 2 sites (e.g., 3 nodes each) with a **tiebreaker** (third site or monitor). Ceph CRUSH rules: create a rule that distributes data across both sites (e.g., `min_size = 2` with replicas in different sites). Monitors: place 2 in site A, 2 in site B, 1 tiebreaker (or 1 in each site + 1 tiebreaker). Network latency: must be < 10ms RTT for Ceph to maintain consistency; higher latency causes performance issues. Split-brain: if sites lose connectivity, Ceph monitors must maintain quorum — without a tiebreaker, both sites may think they're primary, causing data corruption. With a tiebreaker, one site wins quorum and continues. 2-site Ceph is bad without a tiebreaker because a network partition creates a 2-2 split (no majority), causing both sites to stop or split-brain. Use a tiebreaker (third site or a monitor on a separate network) to ensure quorum.

**OP13 — DHCP and DORA**
DHCP (Dynamic Host Configuration Protocol) uses the DORA process: **Discover** (client broadcasts for DHCP servers), **Offer** (server offers an IP lease), **Request** (client requests the offered IP), **Acknowledge** (server confirms). If the DHCP server is unavailable and a Windows client's lease expires: the client continues using the IP (if it was previously assigned) but at some point (e.g., after lease expiry and multiple retries), it falls back to **APIPA** (169.254.x.x) — an automatic private address that allows local communication but no internet access. The client keeps retrying DHCP periodically.

**OP14 — Managed vs. Unmanaged Switch**
An unmanaged switch is plug-and-play with no configuration. A managed switch provides: VLAN configuration, port mirroring, SNMP monitoring, link aggregation (LACP), QoS, spanning tree protocol (STP) for loop prevention, access control lists (ACLs), and remote management (SSH/web). Enterprise environments need managed switches for network segmentation, monitoring, redundancy, and security.

**OP15 — NTP and Time Synchronization**
NTP (Network Time Protocol) synchronizes clocks across servers. Critical because: distributed systems rely on timestamps for ordering, log correlation, and transaction consistency. Clock drift between servers causes: (1) **Incorrect ordering** — events appear out of sequence; (2) **Failed authentication** — Kerberos tickets have time windows; (3) **Database conflicts** — last-write-wins may pick the wrong write; (4) **Broken replication** — replication lag calculations are wrong. Use a local NTP server (e.g., `chrony` or `ntpd`) synced to GPS or upstream, and configure all servers to use it.

**OP16 — Physical Server vs. VM vs. Container**
Physical server: bare metal — full hardware access, no virtualization overhead. VM: full OS with virtualized hardware, isolated, high overhead. Container: shares host OS kernel, lightweight, fast start. Run on bare metal when: you need maximum performance (HPC, GPU workloads), hardware-specific drivers, or legacy applications that don't virtualize well. Otherwise, VMs provide isolation and management; containers provide density and speed.

**OP17 — UPS vs. Generator vs. ATS**
UPS (Uninterruptible Power Supply) provides immediate battery power during outages — covers the gap between utility failure and generator startup. Generator provides long-term power (fuel-based) for extended outages. You need both: UPS handles the transition (seconds), generator handles the duration (hours/days). ATS (Automatic Transfer Switch) automatically switches the load between utility power and generator power — it monitors utility, starts the generator, and transfers the load when utility fails, then transfers back when restored.

**OP18 — Active-Passive vs. Active-Active Clustering**
Active-passive: one node handles traffic, the other is standby (hot or cold). Failover is fast but the standby is idle. Active-active: both nodes handle traffic simultaneously, providing load balancing and redundancy. For PostgreSQL HA with Pacemaker/Corosync: use **active-passive** (PostgreSQL doesn't support multi-master easily). Configure: Corosync for cluster membership, Pacemaker for resource management. Use **STONITH** (fencing) — a watchdog or IPMI-based power control to power off a failed node. Define a **virtual IP** (VIP) resource that floats between nodes. On failover: Pacemaker detects node failure, fences the failed node, promotes the standby (via `pg_ctl promote` or repmgr), and moves the VIP to the new primary. Clients connect to the VIP, so they don't need to change configuration.

**OP19 — Backup and Recovery Strategy**
3-2-1 rule: 3 copies of data, on 2 different media, 1 offsite. Define RPO (Recovery Point Objective — max data loss) and RTO (Recovery Time Objective — max downtime). Backup types: full (all data), incremental (changes since last full/incremental), differential (changes since last full). Use **deduplication** to reduce storage (e.g., dedupe across backups). Storage: disk (fast, for recent backups), tape (cheap, long-term archive), cloud offsite (for disaster recovery). **Immutable backups** (WORM — write once, read many) protect against ransomware by preventing deletion/modification. Test restores regularly — verify backups are restorable. **Backup vs. DR**: backup is copying data; disaster recovery is the process of restoring full IT services (including infrastructure, applications, and data) at a recovery site. Backup is a component of DR.

**OP20 — 802.1X and MAB**
802.1X provides port-based network access control. Roles: **Supplicant** (client device), **Authenticator** (switch/AP), **Authentication server** (RADIUS). The supplicant sends EAP credentials (e.g., EAP-TLS with client certs, PEAP with username/password) to the authenticator, which forwards to RADIUS. RADIUS validates and can assign a **dynamic VLAN** based on the user/device. If authentication fails: the port is blocked (no traffic) or placed in a guest VLAN. **MAB (MAC Authentication Bypass)**: for devices that don't support 802.1X (printers, IoT), the switch sends the device's MAC address to RADIUS as the username/password. If the MAC is known, RADIUS grants access and assigns a VLAN. MAB is a fallback — it's less secure (MAC spoofing) but provides connectivity for legacy devices.
