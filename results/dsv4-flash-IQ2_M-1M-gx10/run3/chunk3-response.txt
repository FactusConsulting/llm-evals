## OpenTofu / Terraform

**T1 — Easy:**  
`tofu plan` reads configuration and state, computes the changes needed to reach the desired state, and displays a plan without applying it. `tofu apply` executes the plan (or a saved plan file) and makes the actual changes to infrastructure. `plan` is a dry-run; `apply` is the action.

**T2 — Easy:**  
State is OpenTofu’s record of the real-world infrastructure it manages, mapping resources to their current attributes. Remote state stores this file in a shared backend (e.g., S3, Azure Storage) so multiple team members/CI can access it, enabling locking, consistency, and preventing conflicts. It also avoids storing sensitive data locally and supports team workflows.

**T3 — Medium:**  
`count` creates a fixed number of instances from a list/count value; `for_each` iterates over a map or set of strings, giving each instance a unique key. `for_each` is preferred when resources have distinct identifiers or when you need to reference each instance by key, and it handles unordered/duplicate-safe collections better. `count` is simpler for numeric ranges but less flexible for keyed access.

**T4 — Medium:**  
OpenTofu detects drift by comparing the state file to the actual cloud provider’s API during `plan`. If a resource was manually changed, `plan` will show a diff and propose to revert it to the configuration-defined state. OpenTofu does not automatically fix drift; it requires an `apply` to reconcile. If the change is intentional, you must import it or update state.

**T5 — Medium:**  
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-123"
  instance_type = "t2.micro"
  tags = { Name = each.key }
}
```

**T6 — Hard:**  
`terraform_remote_state` data source retrieves the entire output of another root module’s state, creating a hard dependency and exposing all outputs (including sensitive ones) to the consuming module. Direct output values (e.g., module outputs) are only available within the same configuration. The recommended alternative is to use a shared data store (e.g., a database, object storage, or a dedicated outputs module) or to pass values explicitly via variables. This reduces coupling, avoids state exposure, and improves modularity.

**T7 — Hard:**  
The `null_resource` with a `remote-exec` provisioner runs during apply, but its output (e.g., kubeconfig) is only available after the provisioner completes. Dependent resources that reference that output may be evaluated during plan time, before the provisioner runs, so they see an empty value. Fix: use a `depends_on` on the dependent resources to force them to wait for the `null_resource`, and ensure the output is computed as a `depends_on` attribute (e.g., via `triggers` or a `local` that reads the file after creation). Alternatively, use a data source that reads the kubeconfig after the cluster is created, or use a provisioner that writes to a known location and read it with a `file` data source.

**T8 — Medium:**  
`tofu import` imports existing infrastructure into state so OpenTofu can manage it. Limitations: it only imports the resource into state; the configuration must be written separately, and some resources may not support import or require manual state editing. The `import` block (introduced in Terraform 1.5, also in OpenTofu) allows declarative import during `plan`/`apply`, generating configuration and handling dependencies more gracefully, reducing manual steps and errors.

**T9 — Easy:**  
A variable (input variable) is a parameter that lets you customize configuration without hardcoding values. An output is a value that a module or root configuration exposes to the caller or user. Input variables are inputs; outputs are results.

**T10 — Easy:**  
A provider is a plugin that translates OpenTofu’s resource definitions into API calls for a specific infrastructure platform (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, OpenTofu will error because providers are not installed and the provider schema is missing. `init` downloads providers and modules.

**T11 — Easy:**  
`.terraform.lock.hcl` records provider and module version checksums and dependencies. It should be committed to version control to ensure reproducible builds—everyone uses the same provider versions and hashes, preventing unexpected changes and supply-chain issues.

**T12 — Easy:**  
`tofu destroy` removes all resources managed by the configuration (or a saved plan). To target a single resource, use `tofu destroy -target=resource_type.name` (e.g., `-target=aws_instance.web[0]`). This destroys only that resource and its dependents.

**T13 — Easy:**  
A data source reads information from the provider (or external system) without creating or managing a resource. Example: `data "aws_ami" "ubuntu"` fetches the latest AMI ID; you use it in a resource instead of hardcoding an AMI. Data sources are read-only and used for lookups, while managed resources create/modify infrastructure.

**T14 — Medium:**  
`locals` are internal, computed values within a module; they are not user-configurable and are used to simplify expressions. `variable` blocks are inputs that users can set from outside. Use `locals` for derived values (e.g., concatenating names, transforming lists) that don’t need external input; use `variable` for values that vary per environment or user.

**T15 — Medium:**  
The `lifecycle` block controls resource lifecycle behavior.  
- `create_before_destroy`: creates a new resource before destroying the old one (e.g., for zero-downtime replacements).  
- `prevent_destroy`: prevents accidental destruction (e.g., for a database that must not be deleted).  
- `ignore_changes`: ignores specified attribute changes (e.g., auto-scaling updates) to avoid drift detection on those fields.  
Use cases: `create_before_destroy` for load balancers, `prevent_destroy` for production databases, `ignore_changes` for tags managed externally.

**T16 — Medium:**  
A `moved` block tells OpenTofu to treat a resource as having been moved from one address to another in the configuration. When refactoring modules (e.g., splitting a module), `moved` blocks update the state mapping so resources are not destroyed/recreated. Example: `moved { from = aws_instance.old to = aws_instance.new }` inside the module.

**T17 — Hard:**  
OpenTofu builds a dependency graph from resource references (implicit dependencies) and `depends_on` (explicit dependencies). Implicit dependencies are derived from attribute references (e.g., `aws_instance.web.id`). Explicit dependencies are declared via `depends_on`. The graph determines the order of operations: independent resources can run in parallel, dependent ones wait. `depends_on` forces ordering and reduces parallelism, so it should be used only when implicit dependencies are insufficient, to avoid slowing down applies.

**T18 — Hard:**  
Strategies to reduce plan time:  
1. **Use `refresh=false`** (or `-refresh=false`) to skip refreshing state from providers, but this risks stale state.  
2. **Limit `refresh` scope** with `-target` or `-refresh-only` for specific resources, but may miss drift.  
3. **Use `-parallelism`** to increase concurrency, but may hit API rate limits.  
4. **Use `-no-color` and `-input=false`** to reduce output processing, but minor gains.  
5. **Use `-compact-warnings`** to reduce log noise, but not plan time.  
6. **Use `-json`** for machine-readable output, but not faster.  
7. **Use `-state`** with a remote backend that caches state, but not plan time.  
8. **Refactor configuration** to reduce resource count or use `ignore_changes` to skip refreshing certain attributes.  
Tradeoffs: skipping refresh can miss drift; targeting reduces coverage; higher parallelism can cause throttling; refactoring is time-consuming.

**T19 — Hard:**  
OpenTofu uses state locking (e.g., DynamoDB, Consul) to prevent concurrent applies. If a lock is not released (e.g., CI crash), subsequent operations fail with a lock error. To break a lock, you can use `tofu force-unlock <lock_id>` (or manually delete the lock entry). Risks: breaking a lock can lead to concurrent modifications if another process is actually running; you must ensure no other apply is in progress before forcing unlock.

**T20 — Hard:**  
Steps to migrate from local to S3-compatible backend with DynamoDB locking:  
1. Create the S3 bucket and DynamoDB table (with `LockID` as primary key).  
2. Add backend configuration in `terraform.tf` (or `backend.tf`):  
   ```hcl
   terraform {
     backend "s3" {
       bucket         = "my-bucket"
       key            = "state.tfstate"
       region         = "us-east-1"
       dynamodb_table = "lock-table"
       encrypt        = true
     }
   }
   ```  
3. Run `tofu init -migrate-state` (or `-backend-config` for remote). OpenTofu will prompt to copy the existing local state to the remote backend.  
4. Verify by running `tofu plan` and checking that state is stored remotely (e.g., `tofu state list`).  
5. Confirm locking works by running `tofu apply` and checking DynamoDB lock entry.  
6. Remove local `terraform.tfstate` backup if desired (it may be kept as backup).  
7. Ensure team members update their backend config and run `init` again.

## Ansible

**A1 — Easy:**  
A playbook is a YAML file containing one or more plays (hosts + tasks). A role is a reusable, organized structure (tasks, handlers, vars, files) that can be included in playbooks. A task is a single action (e.g., install a package) executed on a host.

**A2 — Easy:**  
`ansible_facts` (or `ansible_facts` variable) contains system information gathered by the `setup` module. To access OS family: `ansible_facts['os_family']` or `ansible_os_family` (deprecated but still works). Example: `debug: var=ansible_facts['os_family']`.

**A3 — Medium:**  
- `command`: executes a command on the remote host using the shell’s default (no shell features like pipes, redirection).  
- `shell`: uses the shell to run commands, supporting pipes, variables, etc.  
- `raw`: runs a raw command without any module wrapper, useful for bootstrapping or when Python is unavailable.  
Use `command` for simple, safe commands; `shell` for complex shell syntax; `raw` for minimal environments (e.g., routers, containers without Python).

**A4 — Medium:**  
Ansible modules are designed to be idempotent—they check current state and only make changes if needed. Example of idempotent: `apt: name=htop state=present` (installs only if missing). Non-idempotent: `command: echo "hello" >> /tmp/file` (appends every run). Use modules that support state, or write conditionals to check results.

**A5 — Medium:**  
```yaml
- name: Install htop on Debian/RedHat
  package:
    name: "{{ item }}"
    state: present
  loop: "{{ packages }}"
  vars:
    packages: "{{ 'htop' if ansible_facts['os_family'] == 'Debian' else ['epel-release', 'htop'] }}"
```
Or use `when`:
```yaml
- name: Install htop on Debian
  apt: name=htop state=present
  when: ansible_facts['os_family'] == 'Debian'

- name: Install epel-release and htop on RedHat
  yum: name={{ item }} state=present
  loop: [epel-release, htop]
  when: ansible_facts['os_family'] == 'RedHat'
```

**A6 — Hard:**  
Ansible variable precedence (highest to lowest):  
1. extra vars (`-e`)  
2. `set_fact` (runtime)  
3. host facts (gathered)  
4. play vars  
5. host_vars  
6. group_vars  
7. role defaults (lowest for roles)  
8. inventory variables  
9. defaults in `defaults/main.yml`  
`extra_vars` override everything; `set_fact` overrides facts; `group_vars` override inventory; role defaults are lowest.

**A7 — Hard:**  
Structure:  
- Inventory: create a group `rke2_agents` with all 50 nodes, and a subgroup `first3` for the first 3.  
- Play 1: target `first3` with `serial=1` (or `serial=3`) to ensure they complete sequentially.  
- Play 2: target `rke2_agents` with `serial=10` (or any batch) and use `wait_for` to check that the first 3 are ready before proceeding.  
Example:
```yaml
- hosts: first3
  serial: 1
  tasks:
    - name: Deploy RKE2 agent
      ...
- hosts: rke2_agents
  serial: 10
  tasks:
    - name: Wait for first3 to be ready
      wait_for:
        host: "{{ item }}"
        port: 6443
        delay: 10
      loop: "{{ groups['first3'] }}"
      run_once: true
    - name: Deploy RKE2 agent
      ...
```

**A8 — Medium:**  
`ansible-vault` encrypts sensitive data (passwords, keys). To encrypt a single variable inside a vars file, you can use `ansible-vault encrypt_string` to generate an encrypted string and place it in the file. Example: `ansible-vault encrypt_string 'secret' --name 'db_password'` outputs `db_password: !vault | ...`. You can then paste that into the vars file; the rest of the file remains plaintext.

**A9 — Easy:**  
An inventory file defines hosts and groups. Static inventory is a plain text file (INI/YAML) with hostnames/IPs. Dynamic inventory is a script or program that queries external sources (e.g., cloud APIs) to generate the inventory on the fly. Static is simple; dynamic is scalable and always up-to-date.

**A10 — Easy:**  
```bash
ansible webservers -m command -a "df -h"
```
Or use the `shell` module: `ansible webservers -m shell -a "df -h"`.

**A11 — Easy:**  
A handler is a task that runs only when notified by another task (via `notify`). It is typically used for restarting services after configuration changes. Handlers run once at the end of the play, even if notified multiple times. Trigger: `notify: restart nginx` in a task; the handler is defined in `handlers` section.

**A12 — Easy:**  
`ansible.cfg` is the configuration file for Ansible settings. Common settings: `inventory` (path to inventory), `remote_user` (default SSH user), `become` (whether to use sudo), `forks` (parallelism), `host_key_checking` (disable SSH host key verification), `timeout` (SSH timeout), `roles_path` (location of roles).

**A13 — Easy:**  
`register` captures the result of a task into a variable. Example:
```yaml
- name: Check file exists
  command: ls /tmp/file
  register: file_check
  ignore_errors: yes
- name: Show result
  debug: msg="File exists"
  when: file_check.rc == 0
```
The registered variable contains `rc`, `stdout`, `stderr`, etc.

**A14 — Medium:**  
`include_tasks` dynamically includes tasks at runtime; it is evaluated when the play reaches that point, so conditionals can be applied to the include itself. `import_tasks` is statically parsed at playbook load time; all tasks are pre-processed, so conditionals on the import are not evaluated per-host. Use `include_tasks` for dynamic loops/conditionals; `import_tasks` for static inclusion (e.g., roles) where you want compile-time checks.

**A15 — Medium:**  
Ansible Galaxy is a community hub for roles and collections. `requirements.yml` lists roles/collections to install. Example:
```yaml
roles:
  - name: geerlingguy.nginx
collections:
  - name: community.docker
```
Install with `ansible-galaxy install -r requirements.yml`. It downloads roles/collections to the configured roles path.

**A16 — Medium:**  
Connection plugins define how Ansible communicates with hosts. `ssh` is the default, using SSH to remote hosts. `local` runs tasks on the control node without SSH (e.g., for localhost). `network_cli` is for network devices (e.g., Cisco, Juniper) using CLI over SSH/HTTPS. Use `ssh` for most Linux/Unix hosts; `local` for local actions; `network_cli` for network appliances.

**A17 — Hard:**  
`delegate_to` runs a task on a different host than the target. `run_once` ensures a task runs only once per play (or batch). Example: gather facts from a remote host, then run a task on localhost to update a central database:
```yaml
- hosts: webservers
  tasks:
    - name: Gather facts
      setup:
    - name: Update central DB
      delegate_to: localhost
      run_once: true
      command: "curl -X POST -d '{{ inventory_hostname }}' http://db.example.com/register"
```
Here, the task runs once on localhost using facts from all hosts (via `run_once` and `delegate_to`).

**A18 — Hard:**  
Performance strategies:  
1. **Increase `forks`** (e.g., `-f 50`) to run more hosts in parallel, but may overwhelm network/API.  
2. **Enable SSH pipelining** (`pipelining=True`) to reduce SSH connections, but requires sudo compatibility.  
3. **Use fact caching** (e.g., `fact_caching=jsonfile`) to avoid gathering facts on every run, but facts may become stale.  
4. **Use Mitogen** (or similar) to speed up execution via faster process spawning, but adds dependency and may have compatibility issues.  
5. **Use `serial`** to batch hosts, but increases total time.  
6. **Use `async` and `poll`** for long-running tasks, but adds complexity.  
Tradeoffs: higher forks can cause resource exhaustion; pipelining may break with some sudo configs; caching reduces accuracy; Mitogen is extra code.

**A19 — Hard:**  
Jinja2 templating:  
- `{{ }}` outputs a variable/expression (e.g., `{{ ansible_hostname }}`).  
- `{% %}` contains control logic (e.g., `{% for server in servers %}`).  
- `{# #}` is a comment (ignored).  
Example template for nginx upstream:
```nginx
upstream backend {
{% for server in backend_servers %}
    server {{ server }}:8080;
    # health check for {{ server }}
{% endfor %}
}
```
This generates a server line per backend with a comment.

**A20 — Hard:**  
Zero-downtime rolling deployment:  
- Use `serial` to batch servers (e.g., `serial=2`).  
- Pre-task: remove server from load balancer (e.g., via `uri` module to LB API).  
- Deploy app (e.g., `git` + `service`).  
- Post-task: run health check with `uri` module (e.g., `uri: url=http://localhost/health status_code=200`).  
- If health check fails, use `block`/`rescue` to rollback (e.g., revert to previous version) and re-register server.  
- After each batch, move to next.  
Example structure:
```yaml
- hosts: webservers
  serial: 2
  tasks:
    - block:
        - name: Remove from LB
          uri: url=http://lb.example.com/remove/{{ inventory_hostname }}
        - name: Deploy new version
          git: repo=... dest=/var/www version=release
        - name: Restart service
          service: name=webapp state=restarted
        - name: Health check
          uri: url=http://localhost/health status_code=200
      rescue:
        - name: Rollback
          git: repo=... dest=/var/www version=previous
        - name: Restart service
          service: name=webapp state=restarted
      always:
        - name: Add back to LB
          uri: url=http://lb.example.com/add/{{ inventory_hostname }}
```
