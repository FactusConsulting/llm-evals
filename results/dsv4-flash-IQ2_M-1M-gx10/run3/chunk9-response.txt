## SC1 — Medium — Broken Deployments After Cluster Upgrade

### SC1-A
The failure is caused by a conflict between the container image's default user and the `securityContext.runAsNonRoot: true` setting. The new Chainguard base image defaults `USER` to `root`. When `runAsNonRoot: true` is set, Kubernetes requires the container to run as a non-root user. If the image's `USER` is `root` and no explicit `runAsUser` is provided, the kubelet refuses to start the container, resulting in `CrashLoopBackOff`.

Pod Security Standards (PSS) are admission controls that enforce security policies at the namespace level. `Baseline` allows containers to run as root (it only restricts privileged, host namespaces, etc.). `Restricted` adds stricter requirements, including `runAsNonRoot: true` and disallowing root users. After the upgrade, the namespace enforcement changed from `Baseline` to `Restricted`. Even though the pod spec already had `runAsNonRoot: true`, the image's `USER root` violates the runtime check, so the container fails to start. The healthy pods likely use images with a non-root `USER` or have an explicit `runAsUser` set.

### SC1-B
```bash
kubectl get pods -A -o json | jq -c '
  .items[] | 
  select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") | 
  {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.containers[0].securityContext}
'
```
This outputs a JSON object per failing pod with namespace, name, and securityContext.

### SC1-C
**Immediate fix:** Rebuild the affected images with a non-root `USER` (e.g., `USER 65532`) or add `securityContext.runAsUser: 1000` to the pod specs. Then perform a rolling update (`kubectl rollout restart deployment -n <ns>`).

**Prevention:**
- **Image-level:** Use a CI gate that inspects the image's `USER` directive (e.g., `docker inspect` or `skopeo inspect`) and fails if it is `root`.
- **Manifest-level:** Add an admission policy (Kyverno/OPA) that requires `runAsNonRoot: true` and `runAsUser` to be set, or rejects images with `USER root`.
- **CI pipeline:** Add a step that runs `kubectl dry-run` or a policy check against the cluster's PSS before deployment.

**Rollout without downtime:** Use a rolling update with `maxUnavailable: 0` and `maxSurge: 1`. First patch the deployment with the corrected image, then `kubectl rollout status`. Monitor health checks before proceeding.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

### SC2-A
The stale data issue stems from asynchronous replication lag. The eu-west-1 replica was promoted before it had received all WAL data from us-east-1. PostgreSQL streaming replication ships WAL asynchronously across regions; any transactions committed on the primary after the last replayed LSN on the replica are lost. After promotion, the new primary starts with a lagged dataset, so queries return data that is missing recent writes. To quantify the loss window, check:
- `pg_stat_replication` on the old primary for `replay_lag` or `write_lag`.
- On the promoted replica, compare the last replayed LSN with the old primary's last write LSN (if accessible).
- Use `pg_last_xact_replay_timestamp()` on the replica before promotion.

### SC2-B
Terraform operations:
1. **Import the promoted replica** into state:
   ```bash
   terraform import aws_db_instance.new_primary <replica_id>
   ```
2. **Remove the old instance** from state:
   ```bash
   terraform state rm aws_db_instance.old_primary
   ```
3. **Update references** in Terraform code (security groups, Route53, parameter groups) to point to the new resource name. Run `terraform plan` to ensure no destructive changes (only updates to dependencies). Apply with `terraform apply`.

### SC2-C
**Architecture improvements:**
- **RDS Proxy** over PgBouncer: RDS Proxy handles connection pooling and automatically fails over to the new primary, reducing connection retry errors.
- **Route53 health checks** with DNS failover: Use a failover policy that points to the active primary based on health checks.
- **Application retry logic:** Implement exponential backoff and retry for transient connection failures.
- **RPO < 1 second:** Use **Aurora Global Database** with synchronous replication across regions. It provides a global cluster with failover capability and minimal data loss. Standard RDS only supports asynchronous cross-region replication, so it cannot meet RPO < 1s. Aurora Global Database is recommended for this requirement.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

### SC4-A
1. **Sticky sessions:** Local memory sessions break in Kubernetes because pods are ephemeral and replicas scale. Solution: externalize sessions to Redis or use a distributed cache.
2. **NFS mount:** Local NFS mount `/data/uploads` must be replaced with a CSI-backed NFS storage class that supports ReadWriteMany.
3. **Oracle DB:** The monolith expects a direct JDBC connection; Kubernetes needs network access to the DB. Solution: keep Oracle external or use a sidecar proxy.
4. **IBM MQ:** The app uses MQ for mainframe communication; Kubernetes needs MQ client libraries and network access. Solution: use a message queue bridge or sidecar.
5. **F5 load balancer:** F5 sticky sessions and L7 routing must be replaced by Kubernetes Ingress/Service mesh.

### SC4-B
```hcl
variable "nfs_server" { type = string }
variable "nfs_export" { type = string }
variable "storage_capacity" { default = "100Gi" }

resource "kubernetes_storage_class_v1" "nfs" {
  metadata { name = "nfs-csi" }
  storage_class {
    provisioner = "nfs.csi.k8s.io"
    parameters = {
      server = var.nfs_server
      share  = var.nfs_export
    }
    mount_options = ["hard", "nfsvers=4.1"]
  }
}

resource "kubernetes_persistent_volume_v1" "uploads" {
  metadata { name = "uploads-pv" }
  spec {
    capacity = { storage = var.storage_capacity }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source {
      nfs {
        server = var.nfs_server
        path   = var.nfs_export
      }
    }
  }
}

resource "kubernetes_persistent_volume_claim_v1" "uploads" {
  metadata { name = "uploads-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    resources = { requests = { storage = var.storage_capacity } }
    storage_class_name = kubernetes_storage_class_v1.nfs.metadata[0].name
  }
}
```
ReadWriteMany is necessary because multiple replicas of the monolith need concurrent read/write access to uploaded files.

### SC4-C
**Phased Strangler Fig Migration:**
- **Phase 1:** Move static file uploads to NFS CSI and externalize sessions to Redis. Keep F5 for routing, but add an ingress for new services.
- **Phase 2:** Extract a subset of functionality (e.g., file upload API) into a Kubernetes service. Use F5 to route traffic based on path to either legacy or new service.
- **Phase 3:** Migrate the database to a managed service or containerized PostgreSQL with replication. Move IBM MQ integration to a sidecar or message broker.

**Zero-downtime:** Use blue-green deployment with traffic splitting via F5 or ingress. Rollback by reverting routing rules.

**Metrics for go/no-go:** Error rate < 0.1%, p99 latency < 2s, no data loss, successful session migration.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

### SC6-A
**Identity layer:**
- **SPIFFE/SPIRE:** Deploy SPIRE in each environment to issue workload identities (SVIDs) to pods/containers.
- **AWS IAM Roles:** Use IAM roles for service accounts (IRSA) or EKS Pod Identity to map Kubernetes service accounts to IAM roles.
- **Azure Managed Identities:** Use Azure AD workload identity for Azure workloads.
- **On-prem PKI:** Use SPIRE as the on-prem identity provider, issuing SVIDs to VMs/containers.
- **Federation:** Use SPIFFE federation to establish trust between SPIRE domains. A workload in AWS can authenticate to an on-prem service by presenting its SVID, which the on-prem SPIRE verifies via federation.

### SC6-C
- **Direct Connect:** Higher bandwidth (up to 100 Gbps), lower latency, but higher cost. Encryption via IPsec or MACsec. Fits zero-trust by providing dedicated private path.
- **Second VPN with ECMP:** Adds bandwidth (2 Gbps) but still IPsec overhead. Cost lower than Direct Connect. Failover improved.
- **Hybrid mesh (Tailscale/Netbird):** Uses WireGuard-based overlay, encrypted, identity-aware, and can route over existing internet. Cost-effective, but bandwidth depends on internet. Fits zero-trust by providing identity-based access.

Routing changes: For Direct Connect, add BGP over private virtual interfaces; for ECMP, configure equal-cost routes; for mesh, deploy agents on all workloads.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

### SC7-A
1. **Manual tofu apply:** Developers bypassed CI, so changes were not reviewed or recorded. This can cause unexpected resource changes, state conflicts, and missing dependencies.
2. **Diverged Helm values:** Staging and production values files were not tracked, so deployments used different configurations, leading to environment drift.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

### SC10-A
**Active-passive with Velero:** Backup/restore of Kubernetes resources and PVCs. RPO is limited by backup frequency (e.g., hourly), not 15 min. Restore of 200TB MinIO would take >1 hour, so fails RTO.

**Active-active with service mesh (Istio/Cilium):** Both clusters serve traffic, with data replicated synchronously. For PostgreSQL, use synchronous replication (Patroni with `synchronous_standby_names`). Redis Sentinel can failover. RabbitMQ uses queue mirroring/federation. MinIO uses site replication. This can meet RPO < 15 min if synchronous replication is used, but 12ms latency may impact performance. RTO can be < 1 hour with automatic failover.

**Replication strategies:**
- PostgreSQL: Patroni with synchronous commit.
- Redis: Sentinel with replication.
- RabbitMQ: Queue mirroring across sites.
- MinIO: Site-to-site replication (active-active).

### SC10-B
```yaml
- hosts: database_servers
  tasks:
    - name: Install Patroni
      apt:
        name: patroni
        state: present
    - name: Template patroni.yml
      template:
```

### SC10-C
**Failover sequence:**
1. **Detection:** Monitoring (e.g., Prometheus) detects Chicago site down via health checks and network probes. Confirm with secondary monitor to avoid false positives.
2. **DNS failover:** GSLB updates DNS to point to Dallas.
3. **Patroni:** Automatically promotes Dallas standby to primary (if synchronous replication is configured, no data loss).
4. **Redis Sentinel:** Promotes Dallas replica to master.
5. **RabbitMQ:** Mirrored queues failover to Dallas.
6. **MinIO:** Site replication catches up; if Chicago is down, Dallas serves reads/writes.
7. **OpenTofu:** Update state to reflect Dallas as primary (import new resources, remove old).

**Split-brain:** Use a majority-based DCS (etcd) to prevent multiple primaries. Patroni uses etcd quorum; if Chicago loses quorum, it demotes.

**Failback:** Once Chicago recovers, reverse replication, promote Chicago back during a maintenance window, and update DNS/state.
