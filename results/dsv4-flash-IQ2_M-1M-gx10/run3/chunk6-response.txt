# JavaScript / TypeScript

**JS1 — var, let, const & Hoisting**
- `var`: function-scoped, hoisted and initialized as `undefined`, can be redeclared. `let`/`const`: block-scoped, hoisted but in temporal dead zone (TDZ) until declaration. `const` cannot be reassigned (but objects are mutable). Hoisting: declarations are moved to top of scope at compile time; `var` initializes to `undefined`, `let`/`const` remain uninitialized until execution reaches them.

**JS2 — Event Loop**
The event loop coordinates the call stack (synchronous execution), microtask queue (Promises, `queueMicrotask`, `MutationObserver`), and macrotask queue (setTimeout, setInterval, I/O). Each loop iteration: run all microtasks until empty, then run one macrotask. Microtasks have priority over macrotasks. This enables non-blocking async behavior despite single-threaded JS.

**JS3 — Closures**
A closure is a function that retains access to its lexical scope even when executed outside that scope. Example:
```js
function counter() {
  let count = 0;
  return () => ++count;
}
const c = counter(); c(); // 1
```
Classic for-loop bug: `var` in loop creates shared variable; callbacks capture the same variable. Fix: use `let` (block-scoped) or wrap in IIFE/closure:
```js
for (var i = 0; i < 3; i++) {
  (function(j) { setTimeout(() => console.log(j), 100); })(i);
}
```

**JS4 — Promises, async/await, error handling**
Promises use `.then()`/`.catch()`; async/await uses `try/catch` (syntactic sugar over Promises). `Promise.all` rejects on first rejection; `Promise.allSettled` waits for all and returns `{status, value/reason}` for each, never rejecting. `Promise.race` resolves/rejects on first settled; `Promise.any` resolves on first fulfilled.

**JS5 — TypeScript interface vs type**
`interface` is for object shapes, supports declaration merging, can be extended. `type` is more flexible (unions, tuples, primitives, mapped types). Use `interface` for public APIs/object contracts; `type` for unions, intersections, computed types. Discriminated unions: a union of types with a common discriminant property (e.g., `type` field) enabling type narrowing:
```ts
type Shape = { kind: 'circle'; radius: number } | { kind: 'square'; side: number };
function area(s: Shape) { if (s.kind === 'circle') return Math.PI * s.radius ** 2; }
```

**JS6 — Prototypal inheritance**
Every object has a `[[Prototype]]` (accessed via `Object.getPrototypeOf`). `Object.create(proto)` creates a new object with `proto` as its prototype. ES6 classes are syntactic sugar over prototypes: `class Foo extends Bar` creates `Foo.prototype` with `[[Prototype]]` pointing to `Bar.prototype`. Methods are on the prototype; constructor initializes instances.

**JS7 — `this` binding rules (priority order)**
1. **New binding**: `new` creates a new object and binds `this` to it.
2. **Explicit binding**: `call`, `apply`, `bind` override `this`.
3. **Implicit binding**: object method call (`obj.method()` binds to `obj`).
4. **Default binding**: global object (or `undefined` in strict mode).
`bind()` returns a new function with permanently bound `this`; you cannot re-bind a bound function (even with `call`/`apply`), but you can create a new bound function from it.

**JS8 — WeakRef & FinalizationRegistry**
`WeakRef` holds a weak reference to an object; `deref()` returns the object or `undefined` if GC'd. `FinalizationRegistry` registers callbacks when objects are GC'd. Use for caching large objects, tracking resources, or memory-sensitive maps. WeakMap keys must be objects because they are held weakly; primitive keys can't be weak (no identity for GC tracking). This allows keys to be collected when no other references exist.

**JS9 — V8 optimization**
V8 uses **hidden classes** (maps) to track object shapes for fast property access, **inline caching** to cache property lookup results, and **JIT compilation** (TurboFan) with type feedback. **Deoptimization** occurs when assumptions break (e.g., adding new properties to objects, changing types, polymorphism). Patterns that cause deopt: inconsistent object shapes, changing prototype, using `delete`, mixing types in functions, or exceeding inline cache limits.

**JS10 — Tree-shaking**
Tree-shaking removes unused exports. ES modules are statically analyzable (imports/exports are top-level), enabling dead-code elimination. CommonJS is dynamic (`require` can be conditional), so bundlers can't reliably determine unused exports. ES modules also support `sideEffects` field in package.json to mark modules with side effects.

**JS11 — null vs undefined**
`undefined` means variable declared but not assigned; `null` is an explicit empty value. `==` treats them as equal (`null == undefined` → true); `===` distinguishes them. Nullish coalescing `??` returns right side only for `null`/`undefined` (not falsy values). Optional chaining `?.` short-circuits if the operand is `null`/`undefined`.

**JS12 — Array methods**
- `map()`: transforms each element, returns new array.
- `filter()`: returns elements passing a predicate.
- `reduce()`: accumulates values; initial value is optional but recommended (avoids edge cases with empty arrays).
- `flatMap()`: maps then flattens one level; useful for one-to-many transformations (e.g., splitting strings, nested arrays).

**JS13 — Template literals & tagged templates**
Template literals use backticks, support `${}` interpolation and multi-line strings. Tagged templates call a function with the template's string parts and interpolated values:
```js
function escapeHtml(strings, ...values) {
  return strings.reduce((acc, s, i) => acc + s + (i < values.length ? String(values[i]).replace(/[&<>"']/g, m => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[m])) : ''), '');
}
const user = '<script>';
escapeHtml`<p>${user}</p>`; // escapes HTML
```

**JS14 — Destructuring**
Object: `const { a, b: renamed, c = 1 } = obj;` Array: `const [x, y, ...rest] = arr;` Default values apply when value is `undefined`. Rest operator `...` collects remaining elements/properties. Useful for extracting props, swapping variables, and handling function parameters.

**JS15 — for...in vs for...of**
`for...in` iterates enumerable string keys (including inherited ones); `for...of` iterates iterable values (arrays, strings, maps). Avoid `for...in` on arrays because it includes inherited properties, order is not guaranteed, and it iterates indices as strings.

**JS16 — TypeScript generics**
Generics parameterize types: `function identity<T>(x: T): T`. Constraints: `T extends Lengthwise` restricts to types with `length`. Conditional types: `type IsArray<T> = T extends any[] ? true : false`. `infer` extracts types: `type ElementType<T> = T extends (infer U)[] ? U : never`. Practical: generic API response wrapper, type-safe event handlers.

**JS17 — Module systems**
CommonJS (`require`/`module.exports`) is synchronous, dynamic, used by Node.js by default. ES Modules (`import`/`export`) are static, asynchronous, standardized. Node supports both: `.mjs` or `"type": "module"` for ESM; `.cjs` for CommonJS. ESM enables tree-shaking, top-level await, and better static analysis.

**JS18 — TypeScript structural typing**
Types are compatible if their members are compatible (duck typing). Excess property checks apply only to object literals assigned to typed variables (catch typos/extra props). `extends` is for type constraints/inheritance; `satisfies` (TS 4.9) checks a value against a type without changing its inferred type. Variance: `in` (contravariant) for inputs, `out` (covariant) for outputs; TS 4.7+ allows explicit variance annotations for better type safety.

**JS19 — Proxy & Reflect**
`Proxy` wraps an object to intercept operations via handler traps (`get`, `set`, `apply`, `has`, `deleteProperty`). `Reflect` provides default behavior for traps. Example — validation:
```js
const user = new Proxy({}, {
  set(target, prop, value) {
    if (prop === 'age' && (typeof value !== 'number' || value < 0)) throw new Error('Invalid age');
    return Reflect.set(target, prop, value);
  }
});
```
Also used for logging, reactive data binding (Vue 3), and access control.

**JS20 — SharedArrayBuffer & Atomics**
`SharedArrayBuffer` allows multiple threads (Web Workers) to share memory. `Atomics` provides atomic operations (`add`, `load`, `store`, `compareExchange`) with memory ordering guarantees. `Atomics.wait` blocks a thread until notified; `Atomics.notify` wakes waiting threads. Example: worker synchronization via shared counter. Requires cross-origin isolation (COOP/COEP headers) for security.

# Bash

**B1 — $@ vs $***
`$@` and `$*` both expand to positional parameters. Unquoted, they're identical (all args as separate words). Quoted: `"$@"` preserves each argument as a separate word (handles spaces correctly); `"$*"` joins all args into a single string (using IFS). Use `"$@"` for safe argument passing.

**B2 — set -euo pipefail**
- `-e`: exit on any command failure (non-zero exit).
- `-u`: error on unset variables.
- `-o pipefail`: pipeline returns the rightmost non-zero exit code.
- `-o` with `pipefail` ensures pipelines fail if any component fails. Together, they make scripts fail fast and catch bugs early.

**B3 — $(command) vs `command`**
Both are command substitution. `$(...)` is preferred: supports nesting, escaping, and is more readable. Backticks have legacy escaping issues. `$((expression))` is arithmetic expansion (integer math); `expr` is an external command (slower, requires escaping).

**B4 — Process substitution**
`<(command)` creates a file descriptor (e.g., `/dev/fd/N`) that acts as a FIFO. Used when a command expects a file argument but you want to pipe data. Example:
```bash
diff <(sort file1) <(sort file2)
```
Also `>(command)` for output redirection. Avoids creating temp files.

**B5 — Safe file iteration**
Use `find` with `-print0` and `while IFS= read -r -d ''`:
```bash
find . -type f -print0 | while IFS= read -r -d '' file; do
  echo "$file"
done
```
`for f in $(ls)` is dangerous because it splits on whitespace (spaces, newlines, glob chars). Use `find -exec` or `while read` with null delimiter.

**B6 — Here documents vs here strings**
Here document `<<EOF` feeds multiple lines as stdin; `<<-EOF` strips leading tabs (allows indentation). Here string `<<<` feeds a single string with trailing newline. Example:
```bash
cat <<EOF
line1
line2
EOF
cat <<< "hello"
```

**B7 — Redirection order**
- `cmd > file 2>&1`: stdout to file, then stderr to same file (both go to file).
- `cmd 2>&1 > file`: stderr to current stdout (terminal), then stdout to file — stderr still goes to terminal.
- `cmd &> file`: both to file (bash-specific shorthand).
Order matters because redirections are processed left-to-right; `2>&1` captures the current stdout target.

**B8 — Lock file function**
```bash
lock() {
  local lockdir="${1:-/tmp/lock.$$}"
  while ! mkdir "$lockdir" 2>/dev/null; do
    sleep 0.1
  done
  trap 'rmdir "$lockdir"' EXIT INT TERM
}
```
`mkdir` is atomic (unlike file creation with `touch` + check, which has TOCTOU races). Trap ensures cleanup on EXIT, SIGINT, SIGTERM. For SIGKILL (uncatchable), use `flock` or stale lock detection with PID.

**B9 — Quote types**
- Single quotes: literal, no expansion.
- Double quotes: expansion but no word splitting/globbing.
- No quotes: expansion + word splitting + globbing.
Example:
```bash
x="hello world"
echo '$x'   # $x
echo "$x"   # hello world
echo $x     # hello world (but splits if multiple words)
```

**B10 — File checks & test**
`[ -e file ]` exists, `[ -d dir ]` directory, `[ -r file ]` readable. `[[ ]]` is bash-specific, supports `&&`/`||`, regex `=~`, and no word splitting. `[ ]` is POSIX `test` command. Prefer `[[ ]]` in bash scripts.

**B11 — Special variables**
- `$?`: exit status of last command.
- `$$`: PID of current shell.
- `$!`: PID of last background job.
- `$#`: number of positional parameters.
Use cases: `$?` for error checking, `$$` for temp file names, `$!` to wait/kill background jobs, `$#` to validate argument count.

**B12 — Bash functions**
```bash
foo() { echo "Hello $1"; }
function foo { echo "Hello $1"; }  # equivalent
```
Return values: `return` for exit status (0-255), `echo` for data (capture via `$(foo)`). Functions are like commands; use `local` for scoped variables.

**B13 — PATH & builtins**
`PATH` is a colon-separated list of directories. Bash resolves commands by searching PATH (hash table for speed). Builtins are shell-internal (e.g., `cd`, `echo`, `read`); external commands are separate executables (e.g., `ls`, `grep`). Check with `type -a cmd` or `which`.

**B14 — trap**
```bash
trap 'cleanup' EXIT
trap 'echo "Interrupted"; exit 1' INT TERM
```
EXIT runs on normal exit, ERR on command failure (with `set -e`), INT/TERM for signals. Multiple signals: traps run in order received; EXIT trap runs last. Use `trap -` to reset.

**B15 — xargs**
`xargs` reads stdin and builds commands; command substitution runs in subshell. For filenames with spaces/newlines:
```bash
find . -type f -print0 | xargs -0 -P 4 -I {} process_file {}
```
`-0` handles null-delimited input, `-P` runs parallel jobs. `-I {}` replaces `{}` with each input.

**B16 — Bash arrays**
```bash
arr=(a b c)          # indexed
arr+=(d)             # append
echo "${arr[@]}"     # all elements
echo "${#arr[@]}"    # length
declare -A assoc     # associative
assoc[key]=value
echo "${assoc[@]}"   # values
echo "${!assoc[@]}"  # keys
```
Indexed arrays use integers; associative arrays use strings. Syntax: `${arr[i]}` vs `${assoc[key]}`.

**B17 — Subshell vs group**
`(...)` runs in subshell (variable changes don't propagate); `{ ...; }` runs in current shell (changes persist). Exit codes: subshell returns last command's status; group returns last command's status. Piping into `while` creates a subshell, so variable changes are lost — fix with `while ... done < <(cmd)` (process substitution) or `shopt -s lastpipe`.

**B18 — Signals & job control**
- SIGINT (2): interrupt (Ctrl+C), catchable.
- SIGTERM (15): terminate, catchable (graceful shutdown).
- SIGHUP (1): hangup (terminal closed), catchable.
- SIGKILL (9): kill, uncatchable.
Graceful shutdown: trap SIGTERM, forward to background jobs, wait for them:
```bash
trap 'kill $pid1 $pid2; wait; exit 0' TERM INT
```

**B19 — Parallel log processing**
```bash
split -n 4 -d log.txt part-
process() { grep -c "error" "$1" > "$1.count"; }
export -f process
find . -name "part-*" -print0 | xargs -0 -P 4 -I {} bash -c 'process {}'
cat part-*.count | awk '{s+=$1} END {print s}'
```
Trade-offs: split overhead, CPU/memory balance, error propagation (use `xargs` exit status, `set -e` per job, or collect status files).

**B20 — exec & coprocess**
`exec` replaces the current shell process (no return). For FD manipulation:
```bash
exec 3>file   # open FD 3 for writing
exec 3>&-     # close FD 3
```
Coprocess: `coproc name { command; }` creates bidirectional pipe. Use for interactive processes (e.g., `coproc bc` then `echo "1+1" >&"${bc[1]}"` and read from `"${bc[0]}"`).

# PowerShell

**PS1 — Write-Output vs Write-Host**
`Write-Output` sends objects to the pipeline (can be captured/processed). `Write-Host` writes directly to the console (host), bypassing the pipeline — output is lost unless using `6+` with `-NoNewline` or redirect. Use `Write-Output` for data, `Write-Host` for user-facing messages (or `Write-Information`).

**PS2 — Pipeline & ForEach**
Pipeline passes objects from one command to another (`|`). `ForEach-Object` is a cmdlet that processes pipeline input (streaming, memory-efficient). `foreach` statement iterates a collection in memory (faster for small collections, but loads all). Use `ForEach-Object` for large streams, `foreach` for known collections.

**PS3 — PSCustomObject vs hashtable**
`[hashtable]` is a key-value dictionary (unordered, case-insensitive by default). `[PSCustomObject]` is a structured object with properties (ordered, supports methods, better for output). Convert: `[PSCustomObject]$hashtable` or `$obj | ConvertTo-Hashtable` (PS7+). Use hashtable for lookups, PSCustomObject for output/objects.

**PS4 — Error handling**
Terminating errors stop execution (can be caught with `try/catch`); non-terminating errors continue (use `-ErrorAction Stop` to make them terminating). `$ErrorActionPreference` sets default behavior (`Stop`, `Continue`, `SilentlyContinue`). `try/catch/finally` catches terminating errors; `-ErrorAction` overrides preference per command.

**PS5 — Splatting**
Splatting passes parameters as a hashtable or array:
```powershell
$params = @{ Path = "C:\temp"; Recurse = $true }
Get-ChildItem @params
```
It's cleaner than long parameter lists and allows conditional parameters. Passing a hashtable as a single parameter (e.g., `-Hashtable $hash`) passes it as one value, not expanded.

**PS6 — PowerShell remoting**
`Invoke-Command -ComputerName` runs commands on remote machines (one-off). `Enter-PSSession` creates an interactive session. Uses WinRM (WS-Man) by default, SSH in PS7+ (cross-platform). WinRM requires HTTP/HTTPS (5985/5986), authentication, and firewall config. SSH remoting uses SSH transport.

**PS7 — Type system & pipeline behavior**
Functions that output multiple objects return an array; a single object returns a scalar. The bug: `return $result` where `$result` is an array — PowerShell unrolls arrays. If 0 items, returns `$null` (or `@()` if forced). Correct pattern:
```powershell
function Get-Items {
    [OutputType([string[]])]
    param()
    $result = @()
    $result += "one"
    return ,$result  # comma prevents unrolling
}
```
Or use `Write-Output -NoEnumerate`.

**PS8 — Scriptblock vs function**
A scriptblock `{ ... }` is a reusable code block (not named); a function is a named scriptblock with parameters. Pass scriptblocks to remote sessions via `Invoke-Command -ScriptBlock`. Double-hop problem: credentials don't cross multiple machines. Solutions: CredSSP (delegates credentials), `Invoke-Command -ArgumentList` (passes values, not credentials), or Kerberos with constrained delegation.

**PS9 — @() vs [array]**
`@()` creates an array (empty if no items). `[array]` is a type accelerator for casting. Force single result into array: `@($result)` or `Write-Output -NoEnumerate`. Indexing `$null` returns `$null`; indexing empty array returns `$null` (or error in strict mode). `@($null)` creates an array with one `$null` element.

**PS10 — Comparison operators**
`-eq` (equal), `-ne` (not equal), `-like` (wildcard), `-match` (regex), `-contains` (collection contains value), `-in` (value in collection). Case-sensitive variants: `-ceq`, `-clike`, etc. `-contains` tests if a collection contains an item; `-in` tests if an item is in a collection (PS3+). Both are case-insensitive by default.

**PS11 — Modules**
A module is a package of functions/cmdlets. Script module (`.psm1`) contains PowerShell code; manifest module (`.psd1`) describes metadata (version, dependencies); binary module (`.dll`) is compiled C#. `Import-Module` loads the module; `Get-Module` lists loaded modules. Modules can be auto-loaded from `$env:PSModulePath`.

**PS12 — String interpolation**
Double quotes `"..."` interpolate variables and expressions (`"$var"`, `"$(1+2)"`). Single quotes `'...'` are literal. Here-strings: `@"..."@` (double) interpolates, `@'...'@` (single) is literal. Multi-line strings for large text blocks.

**PS13 — Get-Member**
`Get-Member` reveals object properties, methods, and note properties (added properties). `Select-Object` selects properties (projection); `Where-Object` filters objects (predicate). Use `Get-Member` to explore pipeline objects, `Select-Object` to shape output, `Where-Object` to filter.

**PS14 — PowerShell classes (v5+)**
Classes (`class Foo { ... }`) support constructors, properties, methods, inheritance, but not interfaces (use `interface` in C# or abstract classes). Limitations: no multiple inheritance, no operator overloading, no generics (use `[type]` casts). Use classes for complex stateful objects; functions for simple operations.

**PS15 — CmdletBinding & advanced functions**
`[CmdletBinding()]` adds cmdlet features: `-Verbose`, `-Debug`, `-ErrorAction`, `-WhatIf`. `SupportsShouldProcess` enables `-WhatIf`/`-Confirm`. `DefaultParameterSetName` selects a parameter set. `ValueFromPipeline` accepts pipeline input. `Begin` (setup), `Process` (per-input), `End` (cleanup) blocks control streaming.

**PS16 — Providers**
Providers expose data stores as drives. `Get-ChildItem` works across providers: `FileSystem` (C:), `Registry` (HKCU:), `Certificate` (Cert:), `Environment` (Env:). Access registry like filesystem: `Get-ChildItem HKCU:\Software`, `Set-ItemProperty HKCU:\... -Name value`. Providers enable unified navigation via `cd`, `Get-ChildItem`, `Set-Location`.

**PS17 — Runspaces & parallelism**
A `[runspace]` is a thread; `[runspacepool]` manages multiple threads; `[powershell]` object executes commands in a runspace. `ForEach-Object -Parallel` (PS7+) simplifies parallel execution (each scriptblock runs in a runspace). Manual runspace management gives more control (state, reuse). Thread safety: use `[hashtable]` with locks or `[ConcurrentDictionary]` for shared state.

**PS18 — PSScriptAnalyzer**
PSScriptAnalyzer is a static analysis tool for PowerShell. It enforces rules (e.g., `PSUseShouldProcessForStateChangingFunctions`, `PSAvoidUsingWriteHost`). Severity levels: Error, Warning, Information. Custom rules via `-CustomRulePath`. Suppress with `[Diagnostics.CodeAnalysis.SuppressMessageAttribute]` or `-ExcludeRule`. Integrate with CI/CD via `Invoke-ScriptAnalyzer` in build pipelines.

**PS19 — $using: scope & serialization**
`$using:` passes variables to remote sessions, background jobs, and `ForEach-Object -Parallel` (read-only). `-ArgumentList` passes values (copies). Serialization limits: CLIXML depth (default 2) — complex objects (e.g., custom objects with deep nesting) may lose fidelity. Use `[xml]` or `ConvertTo-Json` for complex data. `$using:` is read-only; modify via `-ArgumentList` or return values.

**PS20 — Desired State Configuration (DSC)**
DSC is a declarative configuration management system. **Configurations** are scripts that define desired state; **resources** implement the logic (e.g., `File`, `Service`, `Registry`); **LCM** (Local Configuration Manager) applies and enforces configurations. Windows PowerShell DSC uses WMI/CIM; PS7+ uses `PSDscResources` (cross-platform). Modern IaC: replaced by **Azure Arc**, **Terraform**, **Ansible**, or **Bicep** for cloud-native config management.
