## Cloud Infrastructure Architecture

**CL1 — IaaS, PaaS, SaaS**
- **IaaS**: Provider offers raw compute, storage, and networking. You manage OS, runtime, apps. Example: AWS EC2.
- **PaaS**: Provider manages OS, runtime, middleware; you deploy apps. Example: Azure App Service.
- **SaaS**: Provider delivers fully managed software. Example: Microsoft 365.

**CL2 — Shared Responsibility Model**
- **IaaS VMs**: Provider responsible for physical host, hypervisor, network, storage infrastructure. You're responsible for guest OS, patches, applications, data, IAM, network config within VM.
- **Managed Kubernetes**: Provider handles control plane, nodes, OS patching, cluster upgrades. You're responsible for workloads, RBAC, pod security, secrets, application data.
- **SaaS (M365)**: Provider handles everything except your data, user identities, and client devices. You manage user accounts, data classification, compliance, and endpoint security.

**CL3 — VPC, Subnet, Security Group, NACL**
- **VPC**: Virtual network boundary isolating your cloud resources.
- **Subnet**: IP range within VPC, segmented by AZ or function.
- **Security Group**: Stateful virtual firewall attached to resources (e.g., EC2). Allows return traffic automatically.
- **NACL**: Stateless firewall at subnet level. Rules evaluated in order; return traffic must be explicitly allowed.
- **Layering**: NACL filters traffic at subnet boundary → Security Group filters at instance level. NACL is stateless (both inbound/outbound rules needed), SG is stateful (return traffic auto-allowed).

**CL4 — Multi-account AWS/Azure Strategy**
- **Landing zone**: Pre-configured baseline with accounts, IAM, networking, logging, guardrails.
- **Organizational units (OUs)**: Group accounts by function (dev, prod, security, shared services).
- **Guardrails**: Preventive (SCP/Policy) and detective (Config/Policy) controls enforced centrally.
- **Shared networking**: Transit Gateway (AWS) or Hub-and-Spoke (Azure) for centralized connectivity, inspection, and egress.
- **Centralized logging**: Aggregated CloudTrail/Activity Logs, Config, and security findings into a central log archive.
- **Single-account problems**: No blast radius isolation, no clear ownership, hard to enforce guardrails, cost attribution difficult, compliance risk.

**CL5 — Infrastructure as Code**
- **Terraform/OpenTofu**: Declarative, state-based, multi-cloud. Best for broad cloud-agnostic provisioning.
- **Pulumi**: Declarative with imperative languages (Python, Go, TS). Good for complex logic and code reuse.
- **CloudFormation/Bicep**: Native to AWS/Azure, deeply integrated, but vendor-locked.
- **Crossplane**: Control-plane approach, Kubernetes-native, enables platform teams to offer APIs for infra.
- **Choice**: Terraform for multi-cloud/legacy; Pulumi for code-heavy teams; CloudFormation/Bicep for single-cloud deep integration; Crossplane for platform engineering/self-service.

**CL6 — Autoscaling Patterns**
- **HPA**: Scales pods based on CPU/memory/custom metrics. Good for stateless workloads.
- **VPA**: Adjusts pod resource requests/limits based on usage. Good for stateful or hard-to-scale apps.
- **Cluster Autoscaler**: Adds/removes nodes when pods can't be scheduled. Handles capacity.
- **KEDA**: Event-driven scaling based on queue length, Kafka lag, custom metrics. Use KEDA over HPA when scaling on non-Kubernetes metrics (e.g., SQS depth, DB connections) or when you need scale-to-zero.

**CL7 — Disaster Recovery**
- **RPO/RTO**: Define acceptable data loss (RPO) and recovery time (RTO). E.g., RPO=15min, RTO=1hr.
- **Active-active**: Both regions serve traffic; DB multi-writer or read replicas. Complex but fast failover.
- **Active-passive**: Primary serves; standby has minimal resources. Failover via DNS.
- **Database replication**: Sync (low RPO, latency penalty) vs async (higher RPO, better performance).
- **DNS failover**: Route53 health checks / Traffic Manager policies for automatic or manual failover.
- **State management**: Use managed services (S3, DynamoDB, Cosmos DB) with cross-region replication; avoid local state.
- **Cost**: Active-active doubles infra cost; warm standby ~50%; pilot light ~20%.
- **DR types**: Pilot light (minimal core running, scale up on failover), warm standby (full stack running but idle), multi-site active-active (both serving traffic).

**CL8 — GitOps Model**
- **GitOps**: Git is the single source of truth for desired state; controllers reconcile cluster to match.
- **ArgoCD vs FluxCD**: Both reconcile Git→cluster. ArgoCD has richer UI, multi-cluster management, sync policies. Flux is more lightweight, integrates with Git providers, supports multi-tenancy via Kustomize/Helm.
- **Secrets**: Sealed Secrets (encrypt in Git), External Secrets Operator (pull from Vault/AWS Secrets Manager), or Vault agent injection.
- **Drift**: Controllers detect drift and either auto-revert or alert. Manual changes are overwritten unless you use `ignoreDifferences` or disable auto-sync.

**CL9 — Stateful Legacy App on Kubernetes**
- **StatefulSet**: Stable network identity, ordered startup/shutdown, stable storage.
- **PV/PVC with local storage class**: Use local SSDs via CSI driver for low latency; PVC binds to specific node.
- **Headless service**: Provides stable DNS names for each pod (e.g., `pod-0.service`).
- **Init containers**: Handle ordered dependencies, config validation, or pre-start setup.
- **ConfigMaps as volume mounts**: Mount config files at exact paths (e.g., `/etc/app/config.ini`).
- **Pod Disruption Budgets**: Ensure minimum availability during voluntary disruptions (e.g., `minAvailable: 2`).

**CL10 — Service Account vs Workload Identity vs IRSA**
- **Service account**: Kubernetes identity for pods to access API server.
- **Workload identity**: Cloud identity mapped to a K8s service account (e.g., GCP Workload Identity, Azure Workload Identity).
- **IRSA**: AWS-specific — IAM role associated with a K8s service account via OIDC federation.
- **Bad practice**: Mounting cloud credentials in pods — long-lived, hard to rotate, risk of exfiltration.
- **Workload identity federation**: Uses OIDC to exchange K8s service account tokens for cloud credentials, short-lived, scoped, no secrets stored.

**CL11 — Storage Types**
- **Object storage (S3/Blob)**: For unstructured data, static content, backups. 11 nines durability (S3), 99.99% availability. HTTP-based.
- **Block storage (EBS/Managed Disk)**: For VM disks, databases. Attached to one VM, low latency, 99.9% availability, durability via snapshots.
- **File storage (EFS/Azure Files)**: Shared file system for multiple VMs, NFS/SMB. Good for shared app data, home directories. 99.9% availability, regional durability.
- **Use cases**: Object for static/media/backups; block for DB/OS disks; file for shared workloads.

**CL12 — Zero-Trust Kubernetes**
- **Network policies**: Micro-segmentation at pod level (e.g., only allow app→DB).
- **Service mesh (Istio/Linkerd)**: mTLS between pods, identity-based auth, fine-grained policies.
- **Pod identity**: Workload identity federation for cloud access.
- **Admission controllers (OPA/Kyverno)**: Enforce policies (e.g., no privileged containers, required labels).
- **Image signing/verification**: Use cosign/Notary to sign images; verify before admission.
- **Runtime security (Falco)**: Detect anomalous syscalls, file access, network behavior.
- **Secrets management**: External Secrets Operator, Vault, or CSI driver for dynamic secrets.
- **Difference from perimeter**: No implicit trust inside network; every request authenticated/authorized; identity-based, not IP-based.

**CL13 — CDN**
- **CDN**: Distributed edge servers that cache content closer to users.
- **How it works**: User requests → edge PoP → cache hit or origin fetch → cached for TTL.
- **Services**: AWS CloudFront, Azure CDN (Front Door).
- **When to use**: Static content, media streaming, global distribution, DDoS mitigation. Use CDN for latency-sensitive/global content; origin for dynamic, personalized, or low-traffic content.

**CL14 — Regions and Availability Zones**
- **Region**: Geographic area with multiple AZs (e.g., us-east-1).
- **AZ**: Isolated data center within region; independent power/cooling/network.
- **Multi-AZ deployment**: High availability — if one AZ fails, others continue.
- **Zonal vs regional resources**: Zonal (e.g., EBS volume, EC2 in one AZ) vs regional (e.g., S3, ELB, RDS multi-AZ) — regional resources survive AZ failures.

**CL15 — Managed Databases**
- **Examples**: RDS, Cloud SQL, Azure SQL.
- **Provider handles**: Hardware, OS, patching, backups, replication, failover, monitoring, scaling.
- **You handle**: Schema, queries, data modeling, access control, application tuning.
- **Vs VM**: No patching/backup/admin overhead; but less control over OS-level tuning.

**CL16 — Cloud Identity Services**
- **IAM users**: Individual accounts for people/services.
- **Groups**: Collections of users for shared permissions.
- **Roles**: Identity with permissions that can be assumed (no long-term credentials).
- **Policies**: JSON documents defining permissions (allow/deny).
- **Least privilege**: Grant only required permissions. Apply via: scoped policies, role separation, regular audits, use conditions (e.g., IP, time).

**CL17 — Serverless**
- **Serverless**: Run code without managing servers; pay per invocation.
- **Lambda/Functions/Cloud Functions**: Event-driven, auto-scaling, ephemeral.
- **Cold starts**: Delay when a new instance spins up; affects latency-sensitive apps.
- **When poor fit**: Long-running processes, stateful apps, low-latency critical paths, heavy compute (ML training), or high sustained load (cost).

**CL18 — Kubernetes Ingress**
- **Ingress resource**: Defines routing rules; controller (e.g., NGINX) implements them.
- **Gateway API**: Newer, more expressive; supports HTTP, TLS, TCP; multi-tenant; better for service mesh integration.
- **Cloud LB annotations**: Direct cloud LB (ALB/NLB) with annotations; simpler but less flexible.
- **Service mesh ingress gateways**: Istio/Envoy gateways for advanced routing, mTLS, traffic management.
- **TLS termination**: At LB (cloud), at ingress controller, or at mesh gateway. Gateway API allows per-route TLS config.
- **When Gateway API**: For complex routing, multi-team clusters, or when you need protocol support beyond HTTP.

**CL19 — Cost Optimization**
- **Reserved instances/Savings plans**: Commit for 1-3 years for 40-60% savings.
- **Spot/preemptible**: Up to 90% off for fault-tolerant workloads.
- **Right-sizing**: Match instance size to actual utilization; use rightsizing recommendations.
- **Storage tiering**: S3 Intelligent-Tiering, Archive for cold data; lifecycle policies.
- **Idle detection**: Find unused resources (e.g., unattached EBS, idle LB) via tools like AWS Trusted Advisor, Azure Advisor.
- **FinOps**: Cloud Center of Excellence, tagging, budget alerts, showback/chargeback.
- **Tools**: Cost Explorer, Budgets, Terraform cost estimation, Kubecost for K8s.
- **Processes**: Monthly reviews, tagging standards, automated shutdown of non-prod, reserved capacity planning.

**CL20 — Multi-Cloud Strategy**
- **Abstraction layers**: Use Terraform for IaC, Kubernetes for runtime, cloud-agnostic services (e.g., S3-compatible storage).
- **Kubernetes**: Common runtime; but cloud-specific integrations (LB, storage, IAM) still differ.
- **Networking**: VPN/Interconnect between clouds for private connectivity.
- **Identity federation**: Use OIDC/SAML to federate identities across clouds.
- **Trade-offs**: Multi-cloud adds complexity, latency, skill requirements, and cost. Benefits: avoid lock-in, best-of-breed, resilience.
- **When justified**: Regulatory requirements, vendor risk, or specific service needs. **When unnecessary**: Small orgs, single-region workloads, or when cost/complexity outweighs benefits.

## OT Infrastructure Architecture

**OT1 — Purdue Model (ISA-95)**
- **Level 0**: Physical process (sensors, actuators).
- **Level 1**: Basic control (PLCs, RTUs, DCS controllers).
- **Level 2**: Supervision (HMI, SCADA servers, alarm management).
- **Level 3**: Operations management (historian, batch management, scheduling).
- **Level 4**: Business planning (ERP, MES, corporate IT).
- **Level 5**: Enterprise network (internet, cloud, corporate services).

**OT2 — IT vs OT Networks**
- **IT**: Data-centric, high bandwidth, frequent patching, dynamic IPs, standard protocols (HTTP, SQL).
- **OT**: Process-centric, real-time deterministic, low tolerance for downtime, legacy protocols (Modbus, OPC), long device lifecycles, safety-critical.
- **Why IT patching fails in OT**: Patches can disrupt real-time control, cause unexpected reboots, or break compatibility with legacy hardware/software. OT systems require change windows and extensive testing.

**OT3 — DMZ/IDMZ**
- **IDMZ**: Industrial DMZ sits between IT (Level 4) and OT (Level 3) networks.
- **Allowed traffic**: Only specific protocols (e.g., HTTPS for web services, OPC UA over TLS) from IT to DMZ, and from DMZ to OT. No direct IT→OT traffic.
- **Direction**: IT→DMZ (limited), DMZ→OT (limited), OT→DMZ (historians, data push), OT→IT (rarely).
- **Why direct IT→Level 1 is dangerous**: IT networks are less controlled, more exposed to threats; direct access bypasses security zones, allowing malware/lateral movement to control systems.

**OT4 — OT Protocols**
- **Modbus TCP**: Level 1/2 — industrial protocol for PLC communication; simple, unencrypted.
- **OPC UA**: Level 2/3 — standardized data exchange between controllers and SCADA/historian; supports encryption.
- **EtherNet/IP (CIP)**: Level 1/2 — industrial Ethernet protocol for real-time control and I/O.
- **PROFINET**: Level 1/2 — industrial Ethernet for real-time control, diagnostics.
- **MQTT**: Level 3/4 — lightweight pub/sub for IoT/cloud data; often used for edge-to-cloud telemetry.

**OT5 — Data Diode vs Firewall**
- **Data diode**: Hardware device that allows one-way data transfer (physically prevents reverse traffic). Used for high-security environments (e.g., nuclear, critical infrastructure).
- **Firewall**: Two-way filtering; can be bypassed if misconfigured.
- **When to use data diode**: When you need absolute assurance that no external traffic can reach the OT network (e.g., sending data from classified to unclassified network).
- **Limitation**: No return traffic, no remote access, no interactive protocols; only suitable for one-way data flows.

**OT6 — SCADA Data Flow to Cloud**
- **Flow**: PLCs → OPC UA server (Level 2) → historian (Level 3) → edge gateway → MQTT broker → cloud ingestion.
- **Security boundaries**: 
  - Between Level 2/3 and edge gateway: firewall/IDMZ.
  - Edge gateway: protocol translation, data filtering, TLS encryption.
  - MQTT broker: TLS, authentication, topic-level access control.
  - Cloud: API gateway, IAM, data encryption at rest.
- **Placement**: Edge gateway in DMZ or Level 3; MQTT broker in cloud or DMZ; never expose OT directly to internet.

**OT7 — IEC 62443 Zones and Conduits**
- **Zone**: Group of assets with similar security requirements (e.g., control zone, safety zone).
- **Conduit**: Communication path between zones with defined security controls (e.g., firewall rules, encryption).
- **Design for manufacturing plant**:
  - **Zone 1**: Corporate IT (Level 4) — low security requirements.
  - **Zone 2**: Engineering workstations (Level 3) — moderate.
  - **Zone 3**: SCADA servers (Level 2) — high.
  - **Zone 4**: PLCs (Level 1) — critical.
  - **Zone 5**: SIS (safety) — highest, isolated.
  - **Conduits**: Between zones, with firewalls, allow only required protocols (e.g., OPC UA from SCADA to PLCs, HTTPS from IT to DMZ).

**OT8 — Network Segmentation for Plant**
- **VLAN design**: Separate VLANs per line (Line 1-4), HMI VLAN, SCADA VLAN, engineering VLAN, safety VLAN.
- **Firewall placement**: Between each VLAN and central core; between OT and IT (IDMZ).
- **Switch architecture**: Use managed switches with VLAN support; segment at access layer; core switch for inter-VLAN routing.
- **Remote access**: Vendor access via jump host in DMZ with MFA, session recording, time-limited access.
- **Transition without stopping production**: Phased approach — start with passive monitoring, then segment one line at a time during planned outages, test thoroughly, rollback plan.

**OT9 — SIS vs BPCS**
- **BPCS**: Basic Process Control System — handles normal operations (setpoints, regulation).
- **SIS**: Safety Instrumented System — independent protection layer for critical safety functions (emergency shutdown, pressure relief).
- **IEC 61511**: Functional safety standard for SIS in process industries; requires SIL-rated components, lifecycle management.
- **Why SIS must be isolated**: SIS is safety-critical; a cyber attack could disable safety functions, leading to catastrophic incidents. Air-gapping or strict isolation ensures no external influence.
- **Ransomware on SIS**: Could prevent safety shutdowns, cause equipment damage, or endanger personnel. Recovery requires manual intervention and potentially physical inspection.

**OT10 — PLC vs DCS vs SCADA**
- **PLC**: Programmable Logic Controller — discrete control, fast I/O, used for individual machines or small processes.
- **DCS**: Distributed Control System — integrated control for large continuous processes (chemical plants, refineries); redundant, scalable.
- **SCADA**: Supervisory Control and Data Acquisition — monitors and controls geographically distributed assets (pipelines, power grids); focuses on data acquisition and operator supervision.
- **Coexistence**: Yes — many plants use PLCs for local control, DCS for process-wide control, and SCADA for remote monitoring.

**OT11 — Remote Access to OT**
- **Architecture**: Jump host in DMZ → MFA → session recording → time-limited access → vendor-specific credentials.
- **Why RDP directly to HMI is unacceptable**: Exposes HMI to internet/corporate network, no audit trail, no MFA, risk of lateral movement, and violates segmentation.
- **Best practices**: Use a bastion host with MFA, record sessions, restrict access to specific IPs, use vendor-specific accounts with least privilege, terminate sessions after use.

**OT12 — OT Incident Response (Water Treatment)**
- **Detection**: Deploy IDS/NDR on Level 3 network; monitor for anomalous traffic (e.g., unexpected Modbus writes, VPN anomalies); use asset inventory to detect new devices.
- **Response steps**: 
  1. Isolate compromised VPN appliance from network.
  2. Monitor for lateral movement; block suspicious IPs.
  3. Engage incident response team; preserve evidence.
  4. Coordinate with control room to maintain safe operations (manual override if needed).
  5. Scan for other compromised assets; contain and remediate.
- **Operator role**: Operators are the first line of defense — they notice anomalies (e.g., unexpected setpoint changes, alarms). They must be trained to report incidents and can execute manual shutdowns if needed.
- **Safe operations**: Ensure SIS remains functional; if uncertain, switch to manual control; prioritize physical safety over cyber containment.

**OT13 — HMI**
- **HMI**: Human-Machine Interface — graphical screens for operators to monitor and control processes (e.g., tank levels, valve positions).
- **Role**: Provides real-time visualization, alarms, and control inputs.
- **Vs engineering workstation**: HMI is for operators (runtime); engineering workstation is for engineers to program/configure controllers (development). Engineering workstations have more privileged access and are higher risk.

**OT14 — Historian**
- **Historian**: Time-series database for process data (temperatures, pressures, flows).
- **Importance**: Provides historical context for troubleshooting, optimization, compliance, and reporting.
- **Plant historian (Level 3)**: Collects data from control systems at high frequency; local to plant.
- **Enterprise historian (Level 4)**: Aggregates data from multiple plants for enterprise-wide analytics; lower frequency, longer retention.

**OT15 — Ladder Logic**
- **Ladder logic**: Graphical programming language for PLCs, resembling relay logic diagrams.
- **Executed by**: PLCs (and some DCS controllers).
- **Why dominant**: Familiar to electricians/engineers, easy to debug visually, deterministic execution, well-suited for discrete control, and legacy expertise.

**OT16 — RTU vs PLC**
- **RTU**: Remote Terminal Unit — designed for remote/outdoor environments, low power, wide temperature range, telemetry over radio/satellite.
- **PLC**: Programmable Logic Controller — designed for local control, faster I/O, more processing power.
- **When to use RTU**: Remote sites (pipelines, wellheads, power distribution) where environmental conditions are harsh and communication is limited.

**OT17 — Analog vs Digital Signals**
- **Analog**: Continuous signal (4-20mA, 0-10V) representing a variable (e.g., temperature, pressure).
- **Digital**: Discrete signal (0 or 1) representing a state (e.g., valve open/closed, motor running).
- **Why 4-20mA over 0-20mA**: 4mA represents zero; a broken wire results in 0mA, which is detectable as a fault. Also, 4-20mA is less affected by voltage drops and provides better noise immunity.

**OT18 — OT Asset Inventory**
- **Why foundation**: You can't protect what you don't know. Asset inventory enables risk assessment, vulnerability management, and incident response.
- **Passive monitoring**: Use network taps/SPAN ports to observe traffic and identify devices (e.g., via MAC addresses, protocols). Safe, no impact.
- **Active scanning**: Send probes to devices (e.g., Nmap) — dangerous because legacy devices may crash or behave unpredictably.
- **Why active scanning is dangerous**: OT devices are often fragile, real-time, and not designed for scanning; a scan can cause communication failures, process disruptions, or device reboots.

**OT19 — MITRE ATT&CK for ICS**
- **Framework**: Maps adversary tactics/techniques specific to industrial control systems.
- **Tactics (5 examples)**:
  1. **Initial Access** — technique: Exploit public-facing application (e.g., VPN vulnerability).
  2. **Execution** — technique: Command-line interface on engineering workstation.
  3. **Persistence** — technique: Modify controller logic (e.g., change PLC program).
  4. **Lateral Movement** — technique: Remote Services (e.g., RDP to HMI).
  5. **Impact** — technique: Damage to physical asset (e.g., overpressure valve).
- **Difference from enterprise ATT&CK**: ICS framework includes physical impact, controller-specific techniques, and safety implications.
- **Use**: Map your OT environment to the framework to identify gaps (e.g., no detection for controller logic changes), prioritize defenses, and build detection rules.

**OT20 — Converged IT/OT SOC**
- **Log collection**: Use passive collectors (e.g., network taps) or OT-native logging (e.g., syslog from PLCs/HMIs) without disrupting real-time operations. Avoid agents on critical controllers.
- **SIEM integration**: Forward OT logs to central SIEM (e.g., Splunk/Elastic) via secure channels; correlate with IT logs.
- **OT-specific detection rules**: Monitor for unauthorized firmware changes, unexpected Modbus writes, new devices, protocol anomalies, and login failures on HMIs.
- **Alert triage**: IT analysts handle IT alerts; OT engineers handle OT alerts. Use a tiered approach — Tier 1 triage, Tier 2 OT-specific analysis.
- **False positives**: OT environments have low tolerance for false positives; use context-aware rules, baseline behavior, and validate alerts with OT engineers.
- **Handling firmware change alert**: Verify with asset inventory, check change management records, isolate the device if unauthorized, and coordinate with plant operations for safe remediation.
