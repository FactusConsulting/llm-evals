## Application Architecture

**AA1 — Monolith vs Microservices**
A monolith is a single deployable unit where all application components (UI, business logic, data access) run in one process. Microservices decompose the application into independently deployable services, each with its own data store and API.
Three concrete problems microservices introduce that monoliths don't:
1. **Network latency** — every service call incurs network overhead (serialization, round-trip), whereas monoliths use in-process calls.
2. **Distributed transaction complexity** — no single ACID transaction spans services; you need sagas, compensation, or eventual consistency.
3. **Operational overhead** — more services means more deployment pipelines, monitoring, configuration, and infrastructure to manage.

**AA2 — Synchronous vs Asynchronous Communication**
- **Synchronous**: The caller sends a request and blocks until a response is received. Example technology: REST/HTTP (client waits for HTTP response).
- **Asynchronous**: The caller sends a message and continues processing; the receiver processes it later. Example technology: RabbitMQ or Kafka (producer publishes, consumer consumes independently).

**AA3 — API Gateway vs Reverse Proxy**
A reverse proxy routes incoming traffic to backend servers, handling load balancing, SSL termination, and basic routing. An API Gateway does all that plus API-specific concerns: rate limiting, authentication/authorization, API versioning, request/response transformation, and analytics.
Can an API Gateway replace a reverse proxy entirely? **Yes, in most cases** — an API Gateway includes reverse proxy functionality. However, for simple use cases (e.g., static content serving, TCP-level routing), a lightweight reverse proxy (like Nginx) is more efficient and simpler to configure. An API Gateway is overkill if you don't need API-specific features.

**AA4 — Saga Pattern**
The Saga pattern manages distributed transactions by breaking them into a sequence of local transactions, each with a compensating action to undo it if a later step fails.
- **Choreography-based**: Each service publishes events; other services react and trigger the next step. No central coordinator. Good for simple workflows with few services, as it reduces coupling but makes the flow harder to track.
- **Orchestration-based**: A central orchestrator (e.g., a saga coordinator) commands each service step-by-step and handles compensation. Good for complex workflows where you need centralized control and easier debugging.
Choose choreography for simple, loosely coupled flows; orchestration for complex flows requiring visibility and control.

**AA5 — CQRS**
CQRS separates the read model (queries) from the write model (commands), often using different data stores or schemas. Event Sourcing stores state as an ordered sequence of events, rather than just the current state.
Why paired: Event Sourcing provides a natural audit log and enables rebuilding the read model at any point in time. The combination solves problems traditional CRUD struggles with: complex read queries that don't match the write model, high write contention, and the need for complete auditability/replayability. It also improves scalability by allowing read and write models to scale independently.

**AA6 — Circuit Breaker Pattern**
Circuit Breaker prevents a service from repeatedly calling a failing dependency. Three states:
1. **Closed** — requests pass through normally.
2. **Open** — requests fail fast without hitting the dependency (after a failure threshold).
3. **Half-Open** — a few trial requests are allowed through to test recovery; if successful, the circuit closes; if not, it reopens.
Difference from retry with backoff: retry assumes transient failures and retries with delays; circuit breaker stops all traffic to a failing service to prevent resource exhaustion. Use both together: retry for transient failures (e.g., network blips) and circuit breaker for sustained failures (e.g., service down). The circuit breaker can also be combined with retries inside the closed state.

**AA7 — Multi-Tenant Isolation Models**
1. **Shared database, shared schema (row-level tenant ID)**: Cheapest (one DB, one schema), highest operational simplicity, but weakest security isolation (risk of SQL injection or bug exposing other tenants' data) and highest noisy-neighbor risk (one tenant's heavy query impacts all).
2. **Shared database, separate schema per tenant**: Moderate cost (one DB, many schemas), better security isolation (schema-level permissions), moderate operational complexity (schema management), and reduced noisy-neighbor risk (still shared DB resources).
3. **Separate database per tenant**: Most expensive (many DBs), best security isolation, highest operational complexity (backup, monitoring per DB), and lowest noisy-neighbor risk (full resource isolation).
Trade-off summary: cost decreases and noisy-neighbor risk increases as you move from separate DB → separate schema → shared schema. Security follows the same direction.

**AA8 — Eventual vs Strong Consistency**
- **Strong consistency**: Every read returns the most recent write; requires coordination (e.g., single-writer, quorum).
- **Eventual consistency**: Reads may return stale data but converge over time; common in distributed systems (e.g., DynamoDB).
For an inventory system that must never oversell: use **strong consistency** with a single-writer database (e.g., PostgreSQL with row-level locks) or a distributed system with linearizable transactions (e.g., Spanner). At scale, use:
- A relational DB with `SELECT ... FOR UPDATE` on inventory rows to serialize writes.
- Or a Redis with Lua scripts for atomic decrement operations.
- Or a distributed lock service (e.g., ZooKeeper) combined with conditional updates (`UPDATE inventory SET quantity = quantity - 1 WHERE id = ? AND quantity >= 1`).

**AA9 — Sidecar Proxy in Service Mesh**
A sidecar proxy is a lightweight proxy (e.g., Envoy) deployed alongside each service instance, handling all network traffic in and out of the service. In Istio:
- **Data plane**: Envoy proxies that handle traffic between services, enforcing policies (routing, retries, mTLS).
- **Control plane**: Istio components (Pilot, Mixer, Citadel) that configure and manage the data plane, distributing certificates and routing rules.
mTLS between sidecars solves **service-to-service authentication and encryption at the network layer**, independent of application-level TLS. This ensures that even if an application doesn't implement TLS, the service mesh provides secure communication, and it also provides identity-based authorization (e.g., only certain services can talk to others).

**AA10 — Strangler Fig Pattern**
The Strangler Fig pattern incrementally replaces parts of a legacy monolith with new services, leaving the old system in place until fully replaced.
Concrete migration strategy for .NET Framework monolith → .NET 8 microservices:
1. **Identify bounded contexts** (e.g., orders, billing, users) and extract one at a time.
2. **Create a facade/API gateway** that routes traffic to either the legacy monolith or the new microservice based on the endpoint.
3. **Extract the first service** (e.g., orders) into a .NET 8 microservice with its own database; the monolith continues to serve other functions.
4. **Redirect traffic** for orders to the new service via the gateway; keep the monolith's order code as a fallback during transition.
5. **Repeat** for each bounded context until the monolith is fully replaced, then decommission it.

**AA11 — 12-Factor App**
The 12-Factor methodology defines best practices for building cloud-native applications. Six key factors:
1. **Codebase** — one codebase, multiple deploys (no code duplication).
2. **Dependencies** — explicitly declare and isolate dependencies (no implicit system packages).
3. **Config** — store configuration in environment variables, not code.
4. **Backing services** — treat services (DB, cache) as attached resources, easily swapped.
5. **Build/release/run** — strict separation between build, release, and run stages.
6. **Processes** — stateless processes, no session state stored in the app.
Why they matter: they ensure portability across environments, scalability (statelessness), maintainability, and consistency between dev and production.

**AA12 — Event-Driven vs Request-Driven**
- **Event-driven (Kafka)**: Loose coupling (services don't know about each other), high scalability (can add consumers), but harder debugging (no direct request-response), no natural ordering guarantees (unless partitioned), and failure handling is complex (need replay/retry logic).
- **Request-driven (REST/gRPC)**: Tight coupling (caller knows the callee), easier debugging (direct trace), natural ordering (request-response), but limited scalability (caller blocks) and failure handling is simpler (timeouts/retries).
Choose event-driven for decoupling, scalability, and asynchronous workflows (e.g., order processing). Choose request-driven for simplicity, low-latency interactions, and when you need immediate feedback (e.g., CRUD APIs).

**AA13 — Load Balancer**
A load balancer distributes incoming traffic across multiple backend servers.
- **Layer 4 (L4)**: Operates at the transport layer (TCP/UDP), routes based on IP address and port. Fast, but no awareness of application content.
- **Layer 7 (L7)**: Operates at the application layer (HTTP), routes based on URLs, headers, cookies, or hostnames. Slower but more intelligent.
Layer 7 is required for: **path-based routing** (e.g., `/api/*` → service A, `/web/*` → service B), sticky sessions based on cookies, or SSL termination.

**AA14 — Message Queue vs Log-Based Broker**
- **Message queue (RabbitMQ)**: Messages are consumed and removed after delivery; supports complex routing (topics, headers) and immediate acknowledgment. Good for task distribution and RPC-like patterns.
- **Log-based broker (Kafka)**: Messages are retained for a configurable period and can be replayed; supports consumer groups for parallel processing. Good for event streaming, audit logs, and replayable data.
Pick RabbitMQ for **task queues** (e.g., sending emails) where messages are transient. Pick Kafka for **event sourcing, stream processing, and data pipelines** where you need replayability and high throughput.

**AA15 — Container vs Virtual Machine**
- **Container**: Shares the host OS kernel, packages the application and its dependencies (e.g., Docker image). Lightweight, starts in milliseconds, uses fewer resources.
- **Virtual Machine**: Includes a full guest OS, runs on a hypervisor. Heavier, slower to start, but provides stronger isolation.
Containers are popular for microservices because they are **portable, lightweight, and efficient** — you can run many containers on one host, scale them independently, and deploy consistently across environments.

**AA16 — Stateless vs Stateful Services**
- **Stateless**: No persistent state between requests; each request is independent. Easy to scale horizontally because any instance can handle any request (just add more instances behind a load balancer).
- **Stateful**: Maintains state (e.g., session data, database state); requires sticky sessions or shared storage. Harder to scale because state must be replicated or partitioned.
Examples: stateless — a REST API that reads from a database; stateful — a database server or a WebSocket chat server that tracks connections.

**AA17 — ORM**
An ORM maps database tables to objects in code, allowing developers to work with data using language-native constructs instead of SQL.
Two popular ORMs: **Hibernate** (Java), **SQLAlchemy** (Python).
Trade-offs:
- **Pros**: Reduces boilerplate, improves productivity, handles relationships and migrations, provides type safety.
- **Cons**: Can be slower (N+1 queries, lazy loading), less flexible for complex queries, hides SQL optimization, and can lead to performance issues if not tuned.

**AA18 — Bulkhead Pattern**
The Bulkhead pattern isolates resources (e.g., thread pools, connections, deployment groups) so that a failure in one part of the system doesn't cascade to others.
In microservices, it relates to **resource isolation** — e.g., a slow downstream service shouldn't exhaust the thread pool for all requests.
Concrete example: Use separate thread pools for different dependencies (e.g., one pool for database calls, one for external API calls). If the external API is slow, it only exhausts its own pool, not the database pool. Alternatively, deploy critical services in separate Kubernetes namespaces or separate clusters to isolate failures.

**AA19 — OT vs CRDTs**
- **Operational Transformation (OT)**: Maintains a consistent document by transforming operations against concurrent edits. Requires a central server to order operations; complex to implement (especially for arbitrary data types); low latency but poor offline support (needs server coordination).
- **CRDTs (Conflict-free Replicated Data Types)**: Data types that converge to the same state on all replicas, regardless of operation order. Support decentralized merging; simpler for some data types (e.g., text, counters); good offline support (each device edits locally and merges later).
For a system that must support offline editing, **CRDTs are the better choice** — they allow each device to edit independently and merge changes later without a central server, providing true offline-first behavior. OT requires a central server for ordering, making offline editing difficult.

**AA20 — Distributed Tracing**
Challenges in a polyglot microservices ecosystem:
- **Context propagation**: Use W3C Trace Context (`traceparent` header) or B3 headers to propagate trace/span IDs across service calls.
- **Sampling**: Head-based sampling (decide at the start of a trace) vs tail-based sampling (decide at the end, preserving complete traces). Tail-based is better for capturing rare but important traces.
- **Trace storage/querying**: Use Jaeger or Tempo for storing and querying traces; they support indexing by service, operation, and tags.
- **Async messaging**: For Kafka, propagate trace context in message headers. Use a Kafka interceptor or producer/consumer hooks to extract and inject trace context, ensuring the trace continues across the message boundary. Without this, traces break at the queue.

## On-Premise Infrastructure Architecture

**OP1 — Hypervisor Type 1 vs Type 2**
- **Type 1 (bare-metal)**: Runs directly on hardware, no host OS. Examples: VMware ESXi, KVM (Linux kernel module).
- **Type 2 (hosted)**: Runs on top of an existing OS. Examples: VirtualBox, VMware Workstation.
Type 1 is used in production for better performance and stability; Type 2 is for development/testing.

**OP2 — SAN vs NAS**
- **SAN (Storage Area Network)**: Block-level storage, presented as raw disks to servers. Uses Fibre Channel or iSCSI. Used for databases, virtual machine disks, and high-performance workloads.
- **NAS (Network Attached Storage)**: File-level storage, presented as shared file systems. Uses NFS or SMB. Used for file sharing, home directories, and backup storage.
Use SAN for block-level access (e.g., VMware datastores), NAS for file-level access (e.g., shared documents).

**OP3 — 3-Tier vs Leaf-Spine**
- **3-Tier**: Core (routing), distribution (policy), access (connectivity). Hierarchical, with north-south traffic dominating. Problems: east-west traffic (server-to-server) traverses multiple hops, causing latency and bottlenecks.
- **Leaf-Spine**: Flat topology where every leaf switch connects to every spine switch. All traffic takes at most 2 hops (leaf → spine → leaf). Solves east-west traffic bottleneck, improves scalability (add more spines/leaves), and reduces latency. Preferred in modern data centers for high-bandwidth, low-latency workloads.

**OP4 — Proxmox HA Cluster**
- **Node count**: Minimum 3 nodes for quorum (majority voting). With 2 nodes, you need a tiebreaker (e.g., QDevice).
- **Quorum**: Prevents split-brain; a node must have majority to remain active.
- **Fencing**: STONITH (Shoot The Other Node In The Head) — a failed node is forcibly rebooted/powered off to prevent it from accessing shared storage.
- **Shared storage**: Options include Ceph (distributed, self-managing), iSCSI (central SAN), or NFS (simplest but less HA). Ceph is recommended for Proxmox HA.
- **Node failure**: The HA agent detects the failure, fences the node, and migrates VMs to healthy nodes. The VM restarts on a new node with minimal downtime.

**OP5 — VLAN Trunking**
VLAN trunking allows a single physical link to carry traffic for multiple VLANs by tagging frames with VLAN IDs.
- **802.1Q tagging**: Adds a 4-byte tag to Ethernet frames, including a VLAN ID (12 bits, up to 4096 VLANs).
- **Single NIC on 3 VLANs (Linux)**: Create VLAN interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`, then assign IPs to each (e.g., `ip addr add 192.168.10.1/24 dev eth0.10`). The switch port must be configured as a trunk port.

**OP6 — RAID Levels**
- **RAID 1**: Mirroring — 2 drives, 1 disk failure tolerance, 50% capacity.
- **RAID 5**: Striping with single parity — 3+ drives, 1 disk failure tolerance, good read performance.
- **RAID 6**: Striping with double parity — 4+ drives, 2 disk failure tolerance.
- **RAID 10**: Striped mirrors — 4+ drives, high performance, 1 disk failure per mirror set.
- **RAID Z2 (ZFS)**: Double parity, similar to RAID 6 but with ZFS features (checksums, snapshots).
For a database server with 6 drives: **RAID 10** — it offers the best performance (striping + mirroring) and fault tolerance (can lose 1 disk per mirror pair), which is critical for database I/O. RAID 5/6 have write penalty (parity calculation) and slower rebuild times.

**OP7 — DNS Architecture for 500-Person Enterprise**
- **Internal AD**: DNS integrated with Active Directory (AD-integrated zones) for dynamic updates and secure resolution.
- **DMZ**: Separate DNS zone for public-facing services (e.g., `dmz.example.com`), hosted on DMZ DNS servers.
- **Split-horizon DNS**: The same domain (`example.com`) resolves differently internally vs externally. Internal DNS returns private IPs; external DNS returns public IPs.
- **DNSSEC**: Sign the external zone to prevent spoofing; internal zones may skip DNSSEC for simplicity.
- **Recursive resolvers**: Internal DNS servers (e.g., Windows DNS) resolve internal names and forward external queries to forwarders (e.g., ISP DNS or 8.8.8.8).
- **Conditional forwarding**: Forward queries for specific domains (e.g., `partner.com`) to specific DNS servers.
- **Laptop moving between office and VPN**: When on VPN, the laptop uses the internal DNS server (via VPN DNS settings); when in the office, it uses the local DNS server. The laptop's DNS suffix and search list change based on the network connection, ensuring it resolves internal names correctly.

**OP8 — PKI Chain of Trust**
- **Root CA → Subordinate/Issuing CA → End-entity certificate**: The root CA is offline and highly protected; it signs the subordinate CA. The subordinate CA issues end-entity certificates (e.g., for servers, users).
- **CRL vs OCSP**: CRL (Certificate Revocation List) is a periodically published list of revoked certificates; OCSP (Online Certificate Status Protocol) provides real-time revocation status via a responder.
- **Certificate templates**: Define properties (e.g., key usage, validity period) for different certificate types (e.g., server auth, client auth).
- **Auto-enrollment**: Group Policy (Windows) automatically requests and renews certificates from the issuing CA.
- **Compromised subordinate CA**: You can revoke its certificate and reissue a new one; the root CA remains trusted, but you must reissue all certificates from that subordinate.
- **Compromised root CA**: Catastrophic — the entire PKI is untrusted; you must rebuild the root CA, reissue all subordinate CAs, and reissue all end-entity certificates.

**OP9 — Hub-and-Spoke WAN Options**
- **MPLS**: Managed service, reliable, low latency, but expensive and rigid (requires carrier).
- **IPsec VPN over internet**: Cheap, but relies on internet quality; can be unreliable for VoIP.
- **SD-WAN**: Overlay on internet or MPLS, provides application-aware routing, cost-effective, good for VoIP (can prioritize voice traffic), and centralized management.
- **WireGuard mesh**: Simple, secure, fast, but lacks enterprise features (centralized management, QoS).
For a company with 50 users per site and latency-sensitive VoIP: **SD-WAN** — it provides cost-effective connectivity, prioritizes VoIP traffic, and offers centralized management. It can also use multiple links (e.g., internet + MPLS) for redundancy.

**OP10 — iDRAC/iLO/IPMI**
- **iDRAC (Dell), iLO (HPE), IPMI (generic)**: Out-of-band management interfaces that allow remote server management (power on/off, console access, hardware monitoring) even when the OS is down.
- **Critical**: Enables remote troubleshooting, firmware updates, and recovery without physical access.
- **Exposed to internet**: Security risk — attackers can gain full control of the server (power cycle, boot from media, access console). Must be isolated on a management VLAN and protected with strong authentication.

**OP11 — LVM vs LVM-Thin vs ZFS**
- **LVM**: Traditional logical volume manager; snapshots are copy-on-write but can be slow and require space allocation.
- **LVM-Thin**: Thin provisioning — allocates space on demand; snapshots are efficient and fast.
- **ZFS**: Advanced filesystem with built-in checksums, snapshots, compression, and RAID-Z. Snapshots are instantaneous and space-efficient.
Use LVM for simple volume management, LVM-Thin for thin provisioning and efficient snapshots, ZFS for data integrity, compression, and advanced snapshot features.

**OP12 — Ceph Stretch Cluster / DR**
- **CRUSH rules**: Define data placement (e.g., `replicated_rule` with 3 replicas across 2 sites).
- **Monitor placement**: Place 3 monitors — one in site A, one in site B, and one tiebreaker (e.g., a third site or a monitor on a separate network).
- **Network latency**: Must be <10ms between sites for synchronous replication; higher latency causes performance issues.
- **Split-brain problem**: Without a tiebreaker, both sites may think they're primary and accept writes, causing data divergence.
- **2-site Ceph is bad**: Without a tiebreaker, you can't achieve quorum (2 monitors can't form majority). A tiebreaker (third site or a dedicated monitor) is required to avoid split-brain. Even with a tiebreaker, synchronous replication over WAN is slow; consider asynchronous replication or active-passive DR.

**OP13 — DHCP DORA**
- **DORA**: Discover (client broadcasts for DHCP servers), Offer (server offers an IP), Request (client requests the offered IP), Acknowledge (server acknowledges and provides lease).
- **If DHCP unavailable and lease expires**: Windows client uses **APIPA** (Automatic Private IP Addressing) — assigns itself an IP in the 169.254.x.x range, which doesn't work on the network. The client continues to retry DHCP periodically.

**OP14 — Managed vs Unmanaged Switch**
- **Unmanaged**: Plug-and-play, no configuration, no monitoring. Suitable for small/home networks.
- **Managed**: Provides VLANs, QoS, SNMP monitoring, port security, spanning tree protocol, link aggregation, and remote management (CLI/Web).
Enterprise environments need managed switches for **network segmentation (VLANs), traffic prioritization (QoS), monitoring (SNMP), and security (port security, 802.1X)**.

**OP15 — NTP**
NTP (Network Time Protocol) synchronizes clocks across servers.
- **Critical**: Accurate time is essential for Kerberos authentication (ticket validity), database replication (timestamps), log correlation, and distributed systems (ordering).
- **Clock drift**: If servers drift apart, Kerberos fails (tickets rejected), database replication conflicts occur, and logs are out of order, making troubleshooting impossible.

**OP16 — Physical vs VM vs Container**
- **Physical server**: Bare metal, full hardware resources, no virtualization overhead.
- **Virtual machine**: Full OS on a hypervisor, isolated, portable.
- **Container**: Shares host OS, lightweight, fast.
Run workloads on bare metal when: you need maximum performance (HPC), specialized hardware (GPU, FPGA), or legacy applications that don't virtualize well.

**OP17 — UPS vs Generator**
- **UPS (Uninterruptible Power Supply)**: Provides immediate battery backup for short-term power loss (minutes), bridging the gap until generators start.
- **Generator**: Provides long-term power (hours/days) using fuel, but takes time to start (seconds to minutes).
- **ATS (Automatic Transfer Switch)**: Automatically switches between utility power, UPS, and generator. When utility fails, ATS switches to UPS; if outage persists, it starts the generator and switches to it.
You need both: UPS for seamless failover (no downtime), generator for extended outages (UPS batteries can't last long).

**OP18 — Active-Passive vs Active-Active Clustering**
- **Active-Passive**: One node handles all traffic, the other is standby. Failover is simple but the standby is idle.
- **Active-Active**: Both nodes handle traffic, providing load balancing and redundancy. More complex but better resource utilization.
For PostgreSQL HA with Pacemaker/Corosync:
- Use **active-passive** (primary + standby) for PostgreSQL, as it's a stateful database.
- Configure **STONITH** (fencing) to power off a failed node.
- Use a **virtual IP** (VIP) that floats between nodes; clients connect to the VIP.
- On failure, Pacemaker promotes the standby to primary and moves the VIP.

**OP19 — Backup and Recovery Strategy**
- **3-2-1 rule**: 3 copies of data, on 2 different media, 1 offsite.
- **RPO/RTO**: Define recovery point objective (max data loss) and recovery time objective (max downtime).
- **Backup types**: Full (all data), incremental (changes since last full/incremental), differential (changes since last full).
- **Deduplication**: Reduces storage by eliminating redundant data.
- **Tape vs disk vs cloud**: Tape is cheap but slow; disk is fast but expensive; cloud is offsite but requires bandwidth.
- **Immutable backups**: Store backups in a write-once-read-many (WORM) format to protect against ransomware.
- **Test restores**: Regularly verify backups by restoring to a test environment.
- **Backup vs DR**: Backup is copying data; disaster recovery is the full process of restoring services (including infrastructure, networking, and procedures) after an outage.

**OP20 — 802.1X**
- **Supplicant**: The client device (e.g., laptop) that requests network access.
- **Authenticator**: The switch or access point that enforces access control.
- **Authentication server**: RADIUS server that validates credentials.
- **EAP methods**: EAP-TLS (uses certificates for mutual authentication), PEAP (uses passwords with TLS tunnel).
- **RADIUS**: Central authentication server that communicates with the authenticator.
- **Dynamic VLAN assignment**: After successful authentication, RADIUS can assign the device to a specific VLAN based on its identity.
- **Failed authentication**: The device is denied access (port is blocked or placed in a guest VLAN).
- **MAB (MAC Authentication Bypass)**: For devices that don't support 802.1X (e.g., printers, IoT), the switch uses the device's MAC address to authenticate with RADIUS. If the MAC is known, the device is granted access; otherwise, it's denied or placed in a restricted VLAN.
