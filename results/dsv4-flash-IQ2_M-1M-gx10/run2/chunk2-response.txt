## Kubernetes (20 questions)

### K1 — Easy: What is the difference between a Deployment and a StatefulSet?

A **Deployment** is for stateless applications. Pods are interchangeable, have random names, no stable network identity, and typically share volumes (if any). Scaling, rolling updates, and rollbacks are straightforward.

A **StatefulSet** is for stateful applications. Pods have stable, unique network identities (stable hostname), stable persistent storage (each pod gets its own PVC), and are deployed in order (scale up/down in order). Used for databases, Kafka, etc.

### K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?

A ClusterIP Service has a stable virtual IP. It uses a selector to match pods. `kube-proxy` watches the Service and Endpoints, and programs iptables/IPVS rules on each node. When a request comes to the ClusterIP, it's DNAT'd to one of the matching pod IPs (via round-robin or other load balancing algorithm).

### K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?

- **PersistentVolume (PV)**: A cluster-level resource representing a piece of storage (e.g., NFS share, cloud disk). Provisioned by an admin or dynamically.
- **PersistentVolumeClaim (PVC)**: A request for storage by a user. It binds to a PV that satisfies its requirements (size, access mode).
- **StorageClass**: Defines how storage is provisioned dynamically. Specifies the provisioner (e.g., AWS EBS, GCE PD) and parameters (e.g., type, IOPS).

**Relationship**: PVC → binds to PV → PV uses StorageClass to be provisioned dynamically. PVC is the user's request, PV is the actual storage, StorageClass is the template for creating PVs.

### K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).

1. **Check pod logs**: `kubectl logs <pod>` — look for application errors, panics, etc.
2. **Check pod events**: `kubectl describe pod <pod>` — look for image pull failures, OOMKilled, etc.
3. **Check container status**: `kubectl get pod <pod> -o yaml` — look at container state, restart count, exit codes.
4. **Check resource limits**: If the container is being OOMKilled, check memory limits vs usage.
5. **Check configuration**: Verify ConfigMaps, Secrets, environment variables are correct.
6. **Check dependencies**: Is the app trying to connect to a database or service that isn't ready?

### K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?

CoreDNS provides DNS resolution for services and pods within the cluster. It implements the cluster DNS service (e.g., `service.namespace.svc.cluster.local`). It also handles external DNS resolution (forwarding to upstream DNS servers).

If CoreDNS is down:
- Pod-to-pod DNS resolution fails (services won't resolve by name)
- External DNS resolution may still work if pods have fallback DNS servers configured (but typically fails)
- Existing connections may continue, but new connections requiring DNS will fail
- The cluster's internal services become unreachable by name

### K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.

The scheduler uses a two-phase process:

1. **Filtering (Predicates)**: Eliminates nodes that can't run the pod. Checks:
   - Resource availability (CPU, memory, GPU) vs pod requests
   - Node affinity/anti-affinity rules
   - Taints and tolerations
   - Node conditions (e.g., out of disk, memory pressure)
   - Port conflicts (if pod needs a host port)
   - Volume zone conflicts

2. **Scoring (Priorities)**: Ranks remaining nodes based on weighted criteria:
   - Least requested resources (spreads pods across nodes)
   - Most requested resources (bin-packing)
   - Node affinity weights
   - Inter-pod affinity/anti-affinity
   - Node locality (data locality for volumes)

**Specific factors**:
- **Resource requests**: CPU, memory, ephemeral storage
- **Node affinity**: Required and preferred rules
- **Taints/tolerations**: Whether pod tolerates node taints
- **Pod anti-affinity**: Avoid co-locating with other pods
- **Topology spread**: Spread across zones
- **Node selectors**: Match labels

### K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?

**Scheduling**: The node has 4GB total, 3.5GB already requested, leaving 0.5GB (512Mi) available. The pod requests 256Mi, which is less than 512Mi available, so it will be scheduled (assuming no other constraints).

**Runtime**: The pod's limit is 512Mi. If it uses 600Mi, it will be OOMKilled (the kernel will kill the process). The container will be terminated and restarted (if restart policy allows). The pod may enter CrashLoopBackOff.

### K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.

1. **External LB**: The cloud load balancer (or service of type LoadBalancer) receives the request and forwards it to the NGINX ingress controller pod (typically via a NodePort or LoadBalancer service).

2. **Ingress Controller**: NGINX pod receives the request. It looks at the Ingress resource to determine the routing rules (host, path → service). It then forwards the request to the Service's ClusterIP.

3. **Service**: The Service (ClusterIP) has a selector that matches the application pods. The Service's virtual IP is backed by Endpoints (list of pod IPs).

4. **kube-proxy/iptables**: On the node where the NGINX pod runs, kube-proxy has programmed iptables rules. When NGINX sends to the Service ClusterIP, iptables DNATs the packet to one of the Endpoint pod IPs (using random or round-robin selection).

5. **Application Pod**: The pod receives the request on its container port. The container processes it and returns the response, which flows back through the same path.

### K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?

**NetworkPolicy**: A resource that controls network traffic between pods, namespaces, and external endpoints. It uses labels to select pods and defines ingress/egress rules.

**Default behavior**: If no NetworkPolicy exists, all pods can communicate with each other freely (allow-all).

**When you apply one that selects certain pods**: The selected pods become "isolated" — only traffic that matches the policy rules is allowed. Unselected pods remain allow-all. The policy acts as a firewall for the selected pods.

### K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?

- **RollingUpdate**: Gradually replaces old pods with new ones. Ensures zero downtime. Can be configured with maxSurge and maxUnavailable. Default strategy.
- **Recreate**: Terminates all old pods before creating new ones. Causes downtime. Simpler and useful when the application can't have multiple instances running simultaneously (e.g., due to database schema migrations).

**Choose Recreate when**:
- The application requires exclusive access to a resource (e.g., a database that can't have multiple writers)
- You need to ensure no old version is running during the update
- The application is not designed for concurrent versions

### K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?

**Namespace**: A virtual cluster within a Kubernetes cluster that isolates resources (pods, services, etc.). Used for environment separation (dev, prod), team separation, or multi-tenancy.

**Default namespaces**:
- `default`: For resources that don't specify a namespace
- `kube-system`: For system components (kube-proxy, CoreDNS, etc.)
- `kube-public`: Publicly accessible resources
- `kube-node-lease`: For node lease objects (heartbeat)

### K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.

`kubectl describe pod` shows detailed information about a pod, including:
1. **Events**: Recent events (e.g., image pull failures, OOMKilled, scheduling decisions)
2. **Container details**: Image, command, args, environment variables, resource requests/limits, liveness/readiness probe config
3. **Volume mounts**: Which volumes are mounted and where
4. **Node information**: Which node the pod is on, node conditions
5. **Tolerations**: Taints the pod tolerates
6. **Status details**: Detailed container states (waiting reasons, terminated exit codes)

`kubectl get pod` only shows basic info: name, ready status, restart count, age, IP, node.

### K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.

**ConfigMap**: A Kubernetes resource that stores configuration data as key-value pairs. It decouples configuration from container images.

**Methods to consume**:
1. **Environment variables**: `envFrom` or `env` with `valueFrom: configMapKeyRef`
2. **Volume mount**: Mount the ConfigMap as a file or directory (e.g., `/etc/config/`)
3. **Command-line arguments**: Use ConfigMap values in the container's command

### K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?

- **ClusterIP**: Internal virtual IP, only accessible within the cluster. Default type.
- **NodePort**: Exposes the service on a static port on each node's IP (e.g., `nodeIP:30000`). Accessible from outside the cluster via any node.
- **LoadBalancer**: Uses cloud provider's load balancer to expose the service externally. It creates a NodePort and ClusterIP underneath, and the cloud LB routes traffic to the nodes.

### K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?

**DaemonSet**: Ensures that a copy of a pod runs on every node (or a subset). Used for node-level infrastructure.

**Use cases**:
- Logging agents (e.g., Fluentd, Filebeat)
- Monitoring agents (e.g., Prometheus node exporter)
- Network plugins (e.g., Calico, Cilium)
- kube-proxy itself

Use DaemonSet instead of Deployment when you need a pod on every node, not just a certain number of replicas.

### K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?

- **Taints**: Applied to nodes to repel pods that don't tolerate them. Taints have key, value, and effect (NoSchedule, PreferNoSchedule, NoExecute).
- **Tolerations**: Applied to pods to allow them to schedule on nodes with matching taints.

**Difference from node affinity**:
- Taints/tolerations: "Repel" pods from nodes (negative selection). Pods must explicitly tolerate taints.
- Node affinity: "Attract" pods to nodes (positive selection). Pods express preference for nodes.

**Use cases**:
- Taints/tolerations: Dedicate nodes to specific workloads (e.g., GPU nodes tainted so only GPU workloads schedule there). Also used for control plane nodes (taint to prevent workloads).
- Node affinity: Prefer to schedule on nodes with SSD storage, or in a specific zone.

### K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?

**Operator**: A pattern that extends Kubernetes with custom resources and controllers that automate the management of a specific application (e.g., databases, message queues). It encodes domain knowledge about how to deploy, scale, backup, and recover the application.

**Difference from standard controller**:
- Standard controllers (e.g., Deployment controller) manage built-in resources (Deployments, Services).
- Operators manage custom resources (CRDs) and implement application-specific logic (e.g., failover, backup, scaling).

**Problems solved**:
- Automates complex operational tasks (backup, recovery, scaling)
- Encapsulates human operational knowledge into code
- Provides self-healing for stateful applications
- Enables declarative management of complex systems

### K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?

etcd uses **Raft consensus algorithm**. It requires a quorum (majority) of nodes to agree on writes. For a 3-node cluster, quorum is 2 nodes.

**If quorum is lost** (e.g., 2 of 3 nodes are down):
- The cluster cannot accept writes (all API server writes fail)
- Reads may still work if the remaining node can serve them (but in strict Raft, reads also require quorum)
- The cluster becomes read-only or completely unavailable
- Kubernetes control plane becomes unavailable for changes

**Recovery from 2/3 nodes permanently lost**:
- The remaining node has the data but cannot form quorum alone
- You must restore from a backup or use the remaining node's data
- Options:
  1. Restore from etcd backup (snapshot) on a new cluster
  2. If the remaining node has the latest data, you can start a new 3-node cluster from that node's data (but this is risky)
  3. Use `etcdctl` to recover: create a new cluster with the remaining node as the seed, then add new members
- The standard approach is to restore from a recent snapshot to avoid data loss

### K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.

RBAC (Role-Based Access Control) uses four resources:
- **Role**: Defines permissions within a namespace (e.g., get pods, list services)
- **ClusterRole**: Defines permissions cluster-wide (can also be used for namespaced resources)
- **RoleBinding**: Binds a Role to a user/group/service account within a namespace
- **ClusterRoleBinding**: Binds a ClusterRole cluster-wide

**Relationship**: Roles define "what" (permissions), Bindings define "who" (subjects) and "where" (namespace or cluster).

**Manifests for developer read-only access to pods and logs in namespace `dev`**:

```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: dev-pod-reader
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.

The `ndots` setting in `/etc/resolv.conf` controls how many dots a domain name must have before it's treated as a fully qualified domain name. Default in Kubernetes is `ndots:5`. This means for a domain like `example.com` (1 dot), the resolver tries:
1. `example.com.<namespace>.svc.cluster.local`
2. `example.com.svc.cluster.local`
3. `example.com.cluster.local`
4. `example.com.<node>.local` (or similar)
5. `example.com` (the actual external domain)

Each attempt is a DNS query, and the resolver waits for a timeout (or negative response) before trying the next. This causes 4-5 queries per resolution, leading to slow resolution.

**Fix**: Use `dnsConfig` in the pod spec to set `ndots: 1`:

```yaml
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "1"
  dnsPolicy: None  # or keep ClusterFirst
```

This makes the resolver try `example.com` first, avoiding the extra search domain queries.

## Development (20 questions)

### D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?

- **Merge**: Creates a new merge commit that combines branches. Preserves history as a DAG. Non-destructive.
- **Rebase**: Replays commits from one branch onto another, creating a linear history. Rewrites commit history.

**Avoid rebasing**:
- When the branch is shared/public (already pushed to remote) — rebasing rewrites history and can cause conflicts for others
- When you want to preserve the exact commit history (e.g., for auditing)
- When the commits have been used as a base for other branches

### D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.

- **TCP**: Connection-oriented, reliable, ordered, flow-controlled. Has handshake (SYN/SYN-ACK/ACK), retransmission, error checking. Used for: HTTP/HTTPS, FTP, SMTP.
- **UDP**: Connectionless, unreliable, unordered, no flow control. No handshake, no retransmission. Used for: DNS, DHCP, VoIP, video streaming, gaming.

### D3 — Medium: What is a race condition? Give a concrete example in any language.

A race condition occurs when multiple threads/processes access shared resources concurrently, and the outcome depends on the timing of their execution. The result is non-deterministic.

**Example in Python**:

```python
import threading

counter = 0

def increment():
    global counter
    for _ in range(1000):
        temp = counter
        # Simulate context switch
        counter = temp + 1

threads = [threading.Thread(target=increment) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)  # Not 10000, but some random value
```

The race condition occurs because `counter = temp + 1` is not atomic — multiple threads read the same value and write back, losing increments.

### D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?

- **Symmetric encryption**: Same key for encryption and decryption. Fast, efficient. Used for bulk data. Examples: AES, DES.
- **Asymmetric encryption**: Different keys (public/private). Public key encrypts, private key decrypts. Slower, used for key exchange and authentication. Examples: RSA, ECC.

**In TLS**:
1. Client and server use asymmetric encryption to exchange a session key (e.g., RSA key exchange or ECDHE).
2. Once the session key is established, they switch to symmetric encryption (AES) for the actual data transfer.
3. Asymmetric encryption is also used for digital signatures (server authentication via certificate).

### D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?

A container image layer is a filesystem change set. Each instruction in a Dockerfile creates a new layer (e.g., `RUN`, `COPY`, `ADD`). Layers are stacked, and each layer is immutable. When pulling an image, layers are downloaded separately and cached.

**Layer caching affects best practices**:
- Order instructions from least to most frequently changing (put `COPY` of source code last)
- Combine `RUN` commands (e.g., `apt-get install` + `cleanup`) to reduce layers
- Use multi-stage builds to keep final image small
- Leverage cache by keeping base images stable
- Avoid invalidating cache with unnecessary changes (e.g., `COPY . .` before installing dependencies)

### D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.

1. **Check server logs**: Look for errors, stack traces, or resource exhaustion (e.g., OOM, too many open files).
2. **Check load balancer / proxy logs**: Is the 503 coming from the LB or the app? Check for upstream timeouts.
3. **Check application health**: Is the app healthy? Check health endpoints, memory usage, CPU, connection pools.
4. **Check database / dependencies**: Is the DB or external service slow or down? Check connection pool exhaustion.
5. **Check network**: Are there network issues between components? Check latency, packet loss.
6. **Check configuration**: Are there misconfigurations (e.g., wrong timeouts, retry settings)?

**Order**: Start with logs (fastest), then check the source of the 503 (LB vs app), then check app health, then dependencies, then network, then config.

### D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.

**CAP theorem**: In a distributed system, you can only guarantee two of three: Consistency (all nodes see the same data at the same time), Availability (every request gets a response), Partition tolerance (system continues to operate despite network partitions).

- **CP system**: Chooses consistency over availability during partitions. Example: **etcd** (used by Kubernetes) — during a partition, it sacrifices availability to maintain consistency (quorum required).
- **AP system**: Chooses availability over consistency during partitions. Example: **Cassandra** — during a partition, it continues to accept writes and serves reads, but may return stale data (eventual consistency).

### D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?

- **Vertical scaling**: Add more resources (CPU, RAM) to a single machine. Limited by hardware capacity. Simpler but has a ceiling.
- **Horizontal scaling**: Add more machines/nodes to distribute load. Unlimited in theory, but requires the application to be designed for it.

**Architectural patterns for horizontal scaling**:
- Stateless application design (no session state on server)
- Distributed databases (sharding, replication)
- Load balancing (distribute traffic across instances)
- Message queues (decouple producers/consumers)
- Microservices (independent scaling of services)
- Auto-scaling (based on load metrics)

### D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.

- **Compiled**: Source code is translated to machine code before execution. Faster runtime, but slower development cycle. Examples: C, Rust, Go.
- **Interpreted**: Source code is executed line-by-line by an interpreter at runtime. Slower runtime, but faster development cycle. Examples: Python, JavaScript, Ruby.

### D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.

- **Forward proxy**: Sits between client and internet. Acts on behalf of the client (e.g., to bypass geo-blocking, filter content, anonymize). The server sees the proxy, not the client.
- **Reverse proxy**: Sits between internet and backend servers. Acts on behalf of the servers (e.g., load balancing, caching, SSL termination). The client sees the proxy, not the backend.

**Common reverse proxies**:
- **NGINX**: Load balancing, caching, SSL termination, serving static files
- **HAProxy**: High-availability load balancing, TCP/HTTP proxying

### D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?

**Deadlock**: A situation where two or more processes/threads are blocked, each waiting for the other to release a resource, causing all to stall.

**Coffman conditions**:
1. **Mutual exclusion**: At least one resource is held exclusively (non-shareable)
2. **Hold and wait**: A process holds a resource while waiting for another
3. **No preemption**: Resources cannot be forcibly taken away
4. **Circular wait**: A cycle of processes waiting for each other's resources

### D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?

**Eventual consistency**: A consistency model where if no new updates are made, all replicas will eventually converge to the same value. During the interim, reads may return stale data.

**Cassandra** handles read-after-write consistency via tunable consistency levels:
- **ONE**: Read/write to one replica. Fastest, but may return stale data.
- **QUORUM**: Read/write to a quorum (majority) of replicas. Ensures read-after-write consistency if write quorum + read quorum > N/2.
- **ALL**: Read/write to all replicas. Slowest, but strongest consistency.
- **LOCAL_QUORUM**: Quorum within a local data center (for multi-DC).
- **EACH_QUORUM**: Quorum in each DC.

To ensure read-after-write consistency, use `QUORUM` for both reads and writes (or `LOCAL_QUORUM` in single DC).

### D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?

**mTLS** (mutual TLS): A TLS variant where both client and server authenticate each other using certificates.

**Handshake process**:
1. Client sends `ClientHello` (supported ciphers, TLS version).
2. Server responds with `ServerHello`, its certificate, and requests client certificate.
3. Client verifies server's certificate (against CA).
4. Client sends its certificate and a `CertificateVerify` message (signature proving possession of private key).
5. Server verifies client's certificate.
6. Client and server exchange key material (e.g., via ECDHE) to derive session keys.
7. Both send `Finished` messages to confirm handshake.

**Common uses**:
- Service-to-service communication in microservices (e.g., Istio service mesh)
- Kubernetes API server authentication (client certificates)
- Database connections (e.g., PostgreSQL with client certs)
- Zero-trust security models

### D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?

**Hash table**: A data structure that maps keys to values using a hash function. The hash function computes an index into an array.

**Collision resolution**:
- **Chaining**: Each bucket is a linked list (or tree). Collisions are stored in the same bucket. Average O(1), worst O(n) if all keys hash to same bucket.
- **Open addressing**: On collision, probe for next empty slot (linear probing, quadratic probing, double hashing). Average O(1), worst O(n) when table is full or clustering occurs.

**Time complexity**:
- Average: O(1) for insertion, lookup, deletion
- Worst: O(n) for all operations (when many collisions)

### D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?

**Circuit breaker**: A pattern that prevents a service from repeatedly calling a failing dependency, avoiding resource exhaustion and cascade failures.

**Three states**:
- **Closed**: Normal operation. Requests pass through. If failures exceed a threshold, circuit opens.
- **Open**: Requests fail fast (without calling the dependency). After a timeout, circuit moves to half-open.
- **Half-open**: Allows a few test requests. If they succeed, circuit closes. If they fail, circuit reopens.

**Prevents cascade failures by**:
- Stopping the "retry storm" that can overwhelm a failing service
- Giving the failing service time to recover
- Reducing load on the caller (fail fast)

**Relation to retry policies**:
- Circuit breaker is a "stop retrying" mechanism, while retry policies are "keep trying" mechanisms.
- Exponential backoff (increasing delay between retries) can be used in the closed state, but the circuit breaker overrides it when the circuit opens.

### D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).

- **Pessimistic concurrency**: Locks resources before accessing them, preventing conflicts. Uses `SELECT FOR UPDATE`, `LOCK TABLE`. Ensures no conflicts but can cause deadlocks and reduces concurrency.
- **Optimistic concurrency**: Allows concurrent access, but checks for conflicts at commit time. Uses version numbers or timestamps. If conflict detected, the transaction fails and must be retried.

**When to choose**:
- **Pessimistic**: When conflicts are frequent, or when the cost of retrying is high (e.g., financial transactions). Good for short transactions.
- **Optimistic**: When conflicts are rare, or when read-heavy workloads. Good for long transactions where holding locks would be problematic.

**Example**:
- Pessimistic: `SELECT * FROM accounts WHERE id = 1 FOR UPDATE;` — locks the row until the transaction commits.
- Optimistic: `UPDATE accounts SET balance = balance - 100, version = version + 1 WHERE id = 1 AND version = 5;` — if version doesn't match, no rows updated, indicating a conflict.
