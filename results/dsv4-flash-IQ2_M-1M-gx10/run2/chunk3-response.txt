## OpenTofu / Terraform (20 questions)

### T1 — Easy: What is the difference between tofu plan and tofu apply?
`tofu plan` performs a dry-run: it compares the current state against the desired configuration and shows what will be added, changed, or destroyed—without making any actual changes. `tofu apply` executes the changes proposed by the plan (or generates a new plan interactively if run without a plan file) and modifies the real infrastructure. Plan is safe for review; apply is the action that mutates resources.

### T2 — Easy: What is state in OpenTofu, and why is remote state important?
State is a JSON file that stores the mapping between resources defined in configuration and their real-world counterparts, including metadata, attributes, and dependencies. Remote state is important because it enables team collaboration (shared state), provides locking to prevent concurrent modifications, protects against local disk loss, and supports CI/CD pipelines by making state accessible from any environment.

### T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?
`count` creates a fixed number of resources indexed by integers (0, 1, 2...). It works with a number or a list, but each resource must have identical configuration except for the index. `for_each` creates resources from a map or set, keyed by the map key or set element, allowing each resource to have distinct configuration (e.g., different names, tags, or settings). `for_each` is preferred when resources need meaningful keys, when iterating over existing data (like a map of objects), or when you need to reference each resource by a stable identifier rather than a numeric index.

### T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
OpenTofu detects drift during `tofu plan` by refreshing the state against the actual cloud resource (via the provider). It compares the real attributes to the state and configuration, showing the drift as a diff. On `tofu apply`, it will attempt to revert the resource back to the desired configuration. If the manual change is intentional, you can use `tofu plan -refresh-only` to update the state to match reality, or add `ignore_changes` in the resource's `lifecycle` block to prevent OpenTofu from reverting specific attributes.

### T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
```hcl
resource "aws_instance" "web" {
  for_each      = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

### T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
`terraform_remote_state` reads the entire state file of another root module, exposing all outputs (and sometimes sensitive data). It creates a hard dependency on the other module's state, can cause performance issues (large state reads), and risks exposing unintended data. Output values are explicit, but still require remote state access. The recommended alternative is to use a dedicated data store—such as a database, object storage (S3), or a service like Consul/etcd—to share only the necessary data. This decouples modules, reduces dependencies, improves security (only shares what's needed), and avoids state-locking conflicts.

### T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
**Why**: The `null_resource` with a `remote-exec` provisioner runs during apply, but output values are computed at plan time. On the first apply, the output is empty because the provisioner hasn't executed yet (or the output references a value that only exists after the provisioner completes). Dependent resources that reference this output get an empty value and fail.

**Fix**: Add an explicit `depends_on` in the dependent resources to ensure they wait for the `null_resource` to finish. Additionally, restructure the output to be computed correctly: use a `local-exec` provisioner to fetch the kubeconfig after the cluster is up, or use a `file` data source to read the kubeconfig file after the provisioner creates it. Example:
```hcl
resource "null_resource" "rke2" {
  provisioner "remote-exec" {
    # fetch kubeconfig
  }
}
data "file" "kubeconfig" {
  depends_on = [null_resource.rke2]
  path       = "/path/to/kubeconfig"
}
output "kubeconfig" {
  value = data.file.kubeconfig.content
}
```

### T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
`tofu import` is a CLI command that imports existing infrastructure into OpenTofu state so it can be managed by configuration. Limitations: it imports only one resource at a time, requires manual mapping of resource addresses, and does not generate configuration (only state). The import block (introduced in 1.5) is a declarative way to import resources within configuration. It allows importing multiple resources at once, can generate configuration with `-generate-config`, and is reproducible because it's part of the codebase. It also supports `for_each` and `count` for bulk imports.

### T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
Input variables are parameters that allow users to customize configuration without modifying the code. They are defined in `variable` blocks and can have defaults, types, and validation. Output values are return values from a module or root configuration that can be used by other modules or displayed to the user. They are defined in `output` blocks and expose computed or static data.

### T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
A provider is a plugin that manages resources for a specific infrastructure platform (e.g., AWS, Azure, GCP). It translates OpenTofu configuration into API calls. Without `tofu init`, `tofu plan` will fail because the provider plugins are not installed. You'll get an error like "provider not found" or "missing plugin".

### T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
The `.terraform.lock.hcl` file is a dependency lock file that records the exact provider versions and their checksums. It ensures reproducibility by pinning versions so that all team members and CI pipelines use the same provider versions. It should be committed to version control to prevent unexpected changes from newer provider versions and to maintain consistency across environments.

### T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
`tofu destroy` removes all resources managed by the configuration (or those in the state). It's the inverse of apply and will prompt for confirmation unless `-auto-approve` is used. To target a single resource, use `-target`:
```bash
tofu destroy -target=aws_instance.web
```

### T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
A data source reads information from the provider without creating or managing resources. It's used to fetch existing data, such as AMI IDs, existing VPC IDs, or current IP addresses. Example: Use the `aws_ami` data source to get the latest Ubuntu AMI ID instead of hardcoding it, or `aws_vpc` to get an existing VPC's ID for use in new resources.

### T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
`locals` are computed values within a module/configuration. They are derived from other values (e.g., combining strings, transforming lists) and cannot be set externally. `variable` blocks are input parameters that can be set by the user or caller. Use locals when you need to compute intermediate values that shouldn't be exposed as inputs (e.g., building a name from a prefix and environment). Use variables when you need external input or customization.

### T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
The `lifecycle` block controls resource lifecycle behavior:
- `create_before_destroy`: Creates a new resource before destroying the old one. Use case: zero-downtime deployment of a VM or service (e.g., replacing an instance in an autoscaling group).
- `prevent_destroy`: Prevents a resource from being destroyed. Use case: protecting a database or critical resource from accidental deletion.
- `ignore_changes`: Ignores specific attribute changes (e.g., tags, auto-scaling group size). Use case: when external systems modify attributes (like auto-scaling group size) and you don't want OpenTofu to revert them.

### T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
A `moved` block tells OpenTofu to treat a resource as if it was moved from one address to another in the configuration. It updates the state to reflect the new address without destroying/recreating the resource. This helps during refactoring (e.g., renaming resources, moving them into modules) by preserving resource identity and avoiding downtime.

### T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
OpenTofu builds a dependency graph based on resource references (implicit dependencies) and `depends_on` (explicit dependencies). Implicit dependencies occur when one resource references another (e.g., `aws_instance.web` uses `aws_subnet.subnet.id`). Explicit dependencies are declared with `depends_on` when there's no direct reference but ordering matters. `depends_on` reduces parallelism because it forces resources to wait for others, creating bottlenecks. It should be used sparingly because it can slow down applies and mask missing implicit dependencies (which are more efficient and maintainable).

### T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
1. **Use `-refresh=false` or `-refresh-only` selectively**: Skip refreshing state for resources that don't change often. Tradeoff: may miss drift.
2. **Use `target` for focused planning**: Plan only specific resources. Tradeoff: doesn't catch all changes.
3. **Increase `-parallelism`**: More parallel operations. Tradeoff: may hit API rate limits.
4. **Use `-compact-warnings` and `-no-color`**: Reduce output processing. Tradeoff: minimal.
5. **Use `-check-variable-constraints=false`**: Skip variable validation. Tradeoff: may miss errors.
6. **Use `-refresh-only` for drift detection**: Only refresh state, not plan. Tradeoff: doesn't show full plan.

### T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
State locking prevents concurrent modifications to state. Backends like S3+DynamoDB, Azure, or GCP support locking. If a lock isn't released (e.g., CI crash), subsequent operations will fail with a lock error. To manually break a lock, use `tofu force-unlock <lock_id>`. Risks: if the original process is still running, it could cause state corruption or conflicts (e.g., two processes writing simultaneously).

### T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
1. Configure the backend in `terraform.tf`:
   ```hcl
   terraform {
     backend "s3" {
       bucket       = "my-bucket"
       key          = "path/to/state.tfstate"
       region       = "us-east-1"
       dynamodb_table = "terraform-locks"
       encrypt      = true
     }
   }
   ```
2. Run `tofu init -migrate-state`. This will copy the local state to the remote backend and prompt for confirmation.
3. Confirm the migration. The local state file is moved (or backed up) to the remote backend.
4. Verify: Run `tofu plan` and check that it uses the remote state. Also check the S3 bucket for the state file and DynamoDB for lock records.
5. Optionally, keep a backup of the local state file for rollback.

## Ansible (20 questions)

### A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?
- **Task**: A single unit of work (e.g., install a package, copy a file).
- **Playbook**: A YAML file containing one or more plays, each with tasks, hosts, and variables.
- **Role**: A reusable, organized structure for tasks, handlers, variables, files, and templates. Roles are modular and can be shared via Galaxy.

### A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?
`ansible_facts` (or the `ansible_facts` variable) contains system information gathered by the `setup` module (e.g., OS, IP, memory). Access OS family via `ansible_facts['os_family']` or the shortcut `ansible_os_family`.

### A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
- **`command`**: Executes a command directly without shell interpretation (no pipes, redirects). Safe and idempotent-friendly.
- **`shell`**: Executes via a shell, supports pipes, redirects, and shell features. More flexible but less safe.
- **`raw`**: Executes raw commands over SSH without any module wrapper. Used when modules aren't available (e.g., bootstrapping, minimal systems).
Use `command` for simple commands, `shell` for complex shell operations, `raw` for emergency or minimal environments.

### A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
Ansible modules are designed to be idempotent by checking current state before making changes. Idempotent example: `apt: name=htop state=present` — if htop is already installed, no change. Non-idempotent example: `command: echo "hello" >> /tmp/file.txt` — appends every run, causing duplicates.

### A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.
```yaml
- name: Install htop on Debian-based systems
  apt:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel-release and htop on RedHat-based systems
  yum:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
```

### A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
Variable precedence (lowest to highest):
1. Role defaults (`defaults/main.yml`)
2. Inventory file variables (host/group vars in inventory)
3. Host facts
4. Playbook variables (`vars` in play)
5. Host_vars (`inventory/host_vars`)
6. Group_vars (`inventory/group_vars`)
7. Playbook vars (`vars_files`)
8. Registered variables (`set_fact`)
9. Extra vars (command line `-e`)
So: role defaults < inventory vars < host facts < play vars < host_vars < group_vars < set_fact < extra_vars.

### A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
```yaml
- name: Deploy RKE2 agents - first batch
  hosts: rke2_agents
  serial: 3
  tasks:
    - name: Install RKE2 agent
      ...
    - name: Wait for agent to be ready
      wait_for:
        path: /var/lib/rancher/rke2/agent/...
        state: present
      when: inventory_hostname in groups['rke2_agents'][:3]

- name: Deploy RKE2 agents - rest
  hosts: rke2_agents
  serial: 10
  tasks:
    - name: Install RKE2 agent
      ...
    - name: Wait for first 3 to be ready
      wait_for:
        host: "{{ groups['rke2_agents'][0] }}"
        port: 6443
        delay: 10
        state: started
      when: inventory_hostname not in groups['rke2_agents'][:3]
```

### A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
`ansible-vault` encrypts sensitive data (passwords, keys) in files or variables. To encrypt a single variable, create a separate vault file for that variable, or use `ansible-vault encrypt_string` to generate an encrypted string and place it in a vars file. Example:
```bash
ansible-vault encrypt_string 'secret_password' --name 'db_password'
```
Then include the encrypted string in a vars file.

### A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
An inventory file defines hosts and groups for Ansible to manage. A static inventory is a file (INI, YAML) with hosts and groups. A dynamic inventory is a script or program that generates inventory dynamically from external sources (e.g., cloud APIs, CMDB).

### A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?
```bash
ansible webservers -m command -a "df -h"
```

### A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
A handler is a task that runs only when notified by another task (usually at the end of the play). It differs from a regular task because regular tasks always run, while handlers run only when notified. Trigger a handler using `notify` in a task:
```yaml
- name: Restart service
  service:
    name: nginx
    state: restarted
  notify: restart nginx
```

### A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
`ansible.cfg` configures Ansible behavior (inventory location, SSH settings, forks, etc.). Common settings: `inventory`, `forks`, `remote_user`, `host_key_checking`, `timeout`, `become`.

### A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
`register` captures the output of a task into a variable. Use it in subsequent tasks by referencing `{{ var_name.stdout }}`, `{{ var_name.rc }}`, etc. Example:
```yaml
- name: Check file exists
  command: ls /tmp/file
  register: file_check

- name: Show output
  debug:
    msg: "File exists: {{ file_check.stdout }}"
```

### A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
`include_tasks` dynamically includes tasks at runtime. It can be used with `when` conditions evaluated at runtime and supports loops. `import_tasks` statically imports tasks at parse time; conditions are evaluated at parse time, so `when` on the import is evaluated before the tasks are loaded. Use `include_tasks` for dynamic conditions (e.g., based on facts), `import_tasks` for static structure.

### A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
Ansible Galaxy is a community hub for sharing roles and collections. `requirements.yml` lists roles/collections to install. Use `ansible-galaxy install -r requirements.yml`. Example:
```yaml
roles:
  - name: geerlingguy.nginx
collections:
  - name: community.docker
```

### A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
Connection plugins define how Ansible connects to hosts. `ssh` is the default, connecting via SSH to remote hosts. `local` runs tasks on the control node (localhost) without SSH. `network_cli` is used for network devices (routers/switches) via CLI over SSH. Use `ssh` for servers, `local` for local operations, `network_cli` for network devices.

### A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
`delegate_to` runs a task on a specific host (e.g., localhost) instead of the target host. `run_once` runs a task only once per play (even with multiple hosts). Example: Gather facts from all hosts, then generate a config file on localhost once:
```yaml
- name: Gather facts
  setup:
  delegate_to: localhost
  run_once: true
  ...
```

### A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
1. **Increase `forks`**: More parallel SSH connections. Tradeoff: higher CPU/memory on control node, may hit SSH limits.
2. **Enable pipelining**: Reduces SSH connections by using a single connection for multiple tasks. Tradeoff: requires sudo privileges and compatible SSH.
3. **Fact caching**: Cache facts to avoid gathering them every run. Tradeoff: stale facts if not refreshed.
4. **Use Mitogen (or similar)**: Faster connection and execution. Tradeoff: requires installation, may have compatibility issues.

### A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
Jinja2 templating in Ansible uses:
- `{{ }}`: Outputs a variable/expression (e.g., `{{ ansible_hostname }}`).
- `{% %}`: Control flow (e.g., `{% for server in servers %}`).
- `{# #}`: Comments (ignored in output).

Template snippet:
```
upstream backend {
{% for server in backend_servers %}
    server {{ server }};  # health check: /health
{% endfor %}
}
```

### A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
```yaml
- name: Rolling deployment
  hosts: web_servers
  serial: 5
  tasks:
    - name: Pre-deploy - remove from LB
      ...
    - name: Deploy application
      ...
    - name: Post-deploy - health check
      uri:
        url: http://localhost/health
        status_code: 200
      register: health
    - name: Add back to LB
      ...
    - block:
        - name: Deploy app
          ...
      rescue:
        - name: Rollback
          ...
```
This uses `serial: 5` to deploy in batches of 5, pre-deploy tasks remove servers from the load balancer, post-deploy tasks run health checks with `uri` module, and `block/rescue` handles rollback on failure.
