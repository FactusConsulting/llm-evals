## Cloud Infrastructure Architecture (20 questions)

### CL1 — Easy
**IaaS** provides virtualized infrastructure (compute, storage, networking) that you manage. Example: AWS EC2.
**PaaS** provides a platform for application development without managing underlying infrastructure. Example: Azure App Service.
**SaaS** provides fully managed software applications. Example: Microsoft 365.
Key difference: level of control vs. level of management. IaaS gives you maximum control but requires most management; SaaS gives you least control but requires least management; PaaS sits in between.

---

### CL2 — Easy
The Shared Responsibility Model defines who is responsible for security of different layers:
- **IaaS VMs (EC2)**: Provider secures physical hosts, hypervisor, network infrastructure. You secure the guest OS, applications, data, access (IAM), and network configuration (security groups).
- **Managed Kubernetes (EKS/AKS)**: Provider secures control plane, worker node OS, and underlying infrastructure. You secure pods, containers, images, RBAC, network policies, and application-level secrets.
- **SaaS (M365)**: Provider secures the entire service, including application, OS, and physical infrastructure. You secure your data, user identities, access policies, and compliance requirements.

---

### CL3 — Medium
- **VPC**: Virtual private network boundary within a cloud region. Isolates your resources from other tenants.
- **Subnet**: A CIDR block within a VPC, typically segmented by availability zone or function (public/private).
- **Security Group**: Instance-level virtual firewall. **Stateful** — return traffic automatically allowed. Supports allow rules only.
- **NACL**: Subnet-level firewall. **Stateless** — return traffic must be explicitly allowed. Supports both allow and deny rules.

Layering: NACLs filter traffic at the subnet boundary first, then security groups filter at the instance level. Security groups are evaluated after NACLs. Stateful filtering (security groups) remembers connection state; stateless (NACLs) treats each packet independently.

---

### CL4 — Medium
**Landing zone**: A well-architected multi-account baseline with pre-configured security, identity, and networking.
**Organizational units (OUs)**: Hierarchical grouping of accounts (e.g., Dev, Prod, Finance) for policy inheritance.
**Guardrails**: Preventive/detective controls (SCPs, Azure Policy) enforced across accounts.
**Shared networking**: Transit Gateway (AWS) or Hub-and-Spoke (Azure) centralizes connectivity between accounts/VPCs.
**Centralized logging**: Aggregates CloudTrail/Activity Logs into a central account for monitoring and compliance.

**Single-account problems**: No blast radius isolation, no separation of duties, no environment isolation, compliance violations, and difficulty scaling. A single compromise affects everything.

---

### CL5 — Medium
**IaC** is managing infrastructure through code, enabling versioning, review, and reproducibility.
- **Terraform/OpenTofu**: Declarative, multi-cloud, mature ecosystem. Best for multi-cloud or cloud-agnostic teams.
- **Pulumi**: Declarative with imperative languages (Python, TypeScript). Best for teams wanting programming logic and testing.
- **CloudFormation/Bicep**: Native to AWS/Azure. Best for single-cloud teams wanting deep integration and provider-native features.
- **Crossplane**: Kubernetes-native control plane for infrastructure. Best for platform teams wanting GitOps-style infrastructure delivery.

Choose Terraform for multi-cloud portability; CloudFormation/Bicep for deep single-cloud; Pulumi for complex logic; Crossplane for Kubernetes-centric platforms.

---

### CL6 — Medium
- **HPA**: Scales pod replicas based on CPU/memory/custom metrics. Horizontal scaling.
- **VPA**: Adjusts pod CPU/memory requests based on usage. Vertical scaling.
- **Cluster Autoscaler**: Adds/removes worker nodes when pods can't be scheduled.
- **KEDA**: Event-driven autoscaler for Kubernetes. Scales based on queue depth, message counts, custom events (e.g., Kafka lag, SQS queue length).

Use **KEDA** over HPA when scaling is driven by external events (message queues, streaming) rather than CPU/memory, or when you need scale-to-zero for batch workloads.

---

### CL7 — Hard
**DR Design for cloud-native app across two regions:**
- **RPO/RTO**: Define acceptable data loss (RPO) and recovery time (RTO). Typically RPO ≤ 15 min, RTO ≤ 1 hour for critical apps.
- **Active-active vs active-passive**: Active-active serves traffic from both regions with data replication; active-passive has one standby region that only takes over on failover.
- **Database replication**: Sync replication (lower RPO, higher latency) vs async (higher RPO, lower latency). Use sync for critical data, async for less critical.
- **DNS failover**: Route53 health checks + failover policies, or Azure Traffic Manager with priority/weighted routing.
- **State management**: Use distributed caches (Redis) with cross-region replication, or stateless services with externalized state.
- **Cost implications**: Active-active doubles infrastructure cost; warm standby reduces cost but increases RTO; pilot light minimizes cost but has highest RTO.

**DR patterns**: 
- **Pilot light**: Minimal standby (database only), scale up on failover. Lowest cost, highest RTO.
- **Warm standby**: Pre-provisioned but idle infrastructure. Moderate cost/RTO.
- **Multi-site active-active**: Both regions serve traffic. Highest cost, lowest RTO.

---

### CL8 — Hard
**GitOps model**: Git is the single source of truth for both infrastructure and application state. Changes are made via pull requests; controllers reconcile actual state to desired state.
- **ArgoCD**: Application-centric, supports multi-cluster, has rich UI, uses Kustomize/Helm.
- **FluxCD**: More flexible, supports Git, S3, and OCI registries as sources; has a larger ecosystem of controllers.

**Secrets handling**: 
- **Sealed Secrets**: Encrypt secrets into Kubernetes objects stored in Git.
- **External Secrets Operator**: Syncs secrets from cloud providers (Vault, AWS Secrets Manager) into Kubernetes.
- **Vault**: Dynamic secrets, rotation, and audit logging.

**Drift handling**: GitOps controllers continuously reconcile. If someone makes a manual change, the controller detects drift and reverts to the Git state. You can configure auto-sync or manual approval for drift correction.

---

### CL9 — Hard
**Kubernetes architecture for stateful legacy app:**
- **StatefulSet**: Provides stable network identity, ordered deployment/termination, and stable storage.
- **PV/PVC with local storage class**: Use local SSDs for low latency. Local storage class binds PVCs to specific nodes.
- **Headless service**: Provides stable DNS names for each pod (e.g., pod-0.service). Enables direct pod-to-pod communication.
- **Init containers**: Handle ordered startup dependencies (e.g., wait for database, initialize config).
- **ConfigMaps as volume mounts**: Mount config files at specific paths (e.g., /opt/app/config) without rebuilding images.
- **Pod Disruption Budgets**: Ensure minimum availability during voluntary disruptions (e.g., node maintenance).

---

### CL10 — Medium
- **Service account**: Kubernetes identity for pods to access Kubernetes API.
- **Workload identity**: Cloud identity for a workload (e.g., Azure AD workload identity).
- **IRSA**: AWS IAM roles for service accounts — maps Kubernetes service accounts to IAM roles.

**Bad practice**: Mounting cloud credentials in pods — credentials can be stolen, rotated poorly, and grant broad access.

**Workload identity federation**: Uses OIDC to let pods assume cloud roles without storing credentials. Pods get short-lived tokens that map to cloud IAM roles, eliminating static credential management.

---

### CL11 — Medium
- **Object storage (S3/Blob)**: For unstructured data (files, images, backups). Highly durable (11 nines), scalable, HTTP-based access. Best for static content, data lakes, backups.
- **Block storage (EBS/Managed Disk)**: For VM-attached disks. Low latency, high IOPS. Best for databases, OS disks, applications needing direct disk access.
- **File storage (EFS/Azure Files)**: Shared file system over NFS/SMB. Best for shared application data, home directories, legacy apps.

**Durability**: Object storage 99.999999999% (11 nines); block/file storage typically 99.999% (multi-AZ). **Availability**: Object storage 99.99%; block/file storage 99.95% (multi-AZ).

---

### CL12 — Hard
**Zero-trust Kubernetes architecture:**
- **Network policies**: Micro-segmentation at the pod level — define which pods can communicate.
- **Service mesh with mTLS**: Encrypts all pod-to-pod traffic, provides identity-based auth (e.g., Istio, Linkerd).
- **Pod identity**: Each pod gets a unique identity via workload identity federation.
- **Admission controllers (OPA/Kyverno)**: Enforce policies at deploy time (e.g., no privileged containers, require labels).
- **Image signing and verification**: Sign images with cosign; verify signatures before admission.
- **Runtime security (Falco)**: Detects anomalous runtime behavior (e.g., unexpected system calls, file access).
- **Secrets management**: Use Vault/External Secrets Operator; never store secrets in Git or env vars.

**Difference from perimeter security**: Zero-trust assumes no implicit trust — every request is authenticated, authorized, and encrypted. Perimeter security trusts everything inside the network boundary.

---

### CL13 — Easy
A **CDN** is a distributed network of edge servers that caches content closer to users, reducing latency and origin load. It works by serving cached copies of static content (images, videos, JS/CSS) from edge locations.

**Examples**: AWS CloudFront, Azure CDN.

**When to use**: For globally distributed users, static content, media streaming, or to absorb DDoS attacks. Use origin server directly for dynamic, personalized, or frequently changing content that can't be cached.

---

### CL14 — Easy
**Regions**: Geographic areas with multiple availability zones (e.g., us-east-1). **Availability zones**: Isolated data centers within a region with independent power, cooling, and networking.

**Why multi-AZ**: High availability — if one AZ fails, resources in other AZs continue serving. Deploying across AZs protects against single-point failures.

**Zonal vs regional resources**: Zonal resources are tied to one AZ (e.g., EBS volume, zonal EC2). Regional resources span multiple AZs (e.g., ELB, S3, RDS multi-AZ).

---

### CL15 — Easy
A **managed database service** (RDS, Cloud SQL, Azure SQL) provides automated backups, patching, replication, failover, and monitoring. The provider handles hardware, OS, database engine maintenance, and high availability.

Compared to running a database on a VM, you avoid: manual patching, backup management, replication setup, and failover configuration. You gain: automated scaling, built-in monitoring, and reduced operational burden — but lose some control over the underlying OS and configuration.

---

### CL16 — Easy
- **IAM users**: Individual identities for people or services.
- **Groups**: Collections of users with shared permissions.
- **Roles**: Identities that can be assumed by users, services, or federated identities. Grant temporary credentials.
- **Policies**: JSON documents defining permissions (allow/deny).

**Principle of least privilege**: Grant only the minimum permissions needed. Apply by: using roles instead of users, scoping policies to specific resources, using conditions (e.g., IP, time), and regularly auditing permissions.

---

### CL17 — Easy
**Serverless computing**: Run code without provisioning or managing servers. You pay only for execution time.

- **AWS Lambda**: Event-driven, supports many languages, integrates with AWS services.
- **Azure Functions**: Similar, integrates with Azure services, supports durable functions.
- **Google Cloud Functions**: Lightweight, integrates with GCP services.

**Cold starts**: Delay when a function is first invoked after being idle — the platform must allocate resources and load the runtime. Matters for latency-sensitive applications.

**Poor fit for**: Long-running processes, stateful applications, workloads with predictable high utilization, or applications requiring persistent connections.

---

### CL18 — Medium
- **Ingress resource**: Kubernetes-native API for HTTP routing. Uses an ingress controller (e.g., NGINX) that implements the rules.
- **Gateway API**: Newer, more expressive API with GatewayClass, Gateway, and Route resources. Supports HTTP, TCP, TLS, and cross-namespace routing.
- **Cloud LB annotations**: Provider-specific annotations on Service resources (e.g., AWS NLB annotations) for L4/L7 load balancing.
- **Service mesh ingress gateways**: Dedicated ingress gateways (e.g., Istio IngressGateway) that handle mTLS, routing, and policy at the mesh edge.

**TLS termination**: At the ingress controller (Ingress), at the Gateway API implementation, at the cloud LB (annotations), or at the mesh gateway. Each layer can terminate TLS and re-encrypt internally.

**Gateway API over Ingress**: Use Gateway API for multi-protocol support (TCP/UDP), cross-namespace routing, richer policy, and better extensibility. Choose Ingress for simple HTTP routing.

### CL19 — Hard
**Cost optimization strategy for $80K/month:**
- **Reserved instances/savings plans**: Commit to 1-3 years for predictable workloads — save 30-60%.
- **Spot/preemptible instances**: Use for fault-tolerant, stateless workloads — save 60-90%.
- **Right-sizing**: Analyze utilization and downsize over-provisioned resources.
- **Storage tiering**: Use S3 Intelligent-Tiering for auto-tiering; archive cold data to Glacier/Cool Blob.
- **Idle resource detection**: Identify and terminate unused resources (e.g., idle EC2, unattached EBS).
- **FinOps practices**: Establish cost ownership, budgeting, and regular reviews.
- **Showback/chargeback**: Tag resources by team/project; allocate costs to business units.

**Tools**: AWS Cost Explorer, Azure Cost Management, Terraform cost estimation, CloudHealth, or OpenCost for Kubernetes. **Processes**: Monthly cost reviews, tagging standards, budget alerts, and automated shutdown of non-prod environments.

### CL20 — Hard
**Multi-cloud strategy design:**
- **Abstraction layers**: Use Kubernetes as a common runtime, Terraform for IaC, and cloud-agnostic APIs (e.g., CNCF projects).
- **Kubernetes as common runtime**: Run workloads on EKS and AKS with identical deployment patterns.
- **Terraform for portability**: Write modules that abstract provider-specific resources.
- **Networking**: Connect clouds via VPN or dedicated interconnect (e.g., AWS Direct Connect + Azure ExpressRoute).
- **Identity federation**: Use OIDC/SAML to federate identities across clouds (e.g., SSO via Okta).

**Real-world trade-offs**: Multi-cloud increases complexity, latency, and cost. You lose native features, have inconsistent tooling, and need specialized expertise. **When justified**: Regulatory requirements (data residency), vendor risk mitigation, or leveraging best-of-breed services. **When unnecessary**: Most organizations — single-cloud with good architecture provides sufficient resilience and cost efficiency.

## OT Infrastructure Architecture (20 questions)

### OT1 — Easy
The **Purdue Model (ISA-95)** is a reference architecture for industrial control systems, dividing operations into levels:
- **Level 0**: Physical processes (sensors, actuators).
- **Level 1**: Basic control (PLCs, RTUs, DCS controllers).
- **Level 2**: Supervision (HMIs, SCADA servers, alarm systems).
- **Level 3**: Operations management (historians, batch management, scheduling).
- **Level 4**: Business logistics (ERP, MES, plant-level systems).
- **Level 5**: Enterprise network (corporate IT, internet).

---

### OT2 — Easy
**IT networks** prioritize confidentiality and integrity; **OT networks** prioritize availability and safety. OT systems run 24/7, have long lifecycles, and often use proprietary protocols. Standard IT patching can disrupt production, cause unexpected behavior, or violate vendor support agreements. OT systems require testing in staging environments, scheduled maintenance windows, and careful change management.

---

### OT3 — Medium
The **IDMZ (Industrial DMZ)** sits between IT (Level 4) and OT (Level 3) networks. It hosts services that need to cross boundaries (e.g., web servers, file transfer, remote access gateways). Traffic should be limited to specific protocols (HTTPS, SFTP) and only from the DMZ to OT, never direct IT-to-OT. Direct Level 4-to-Level 1 connectivity is dangerous because it bypasses security controls, exposes control systems to IT-based threats, and violates the Purdue Model's segmentation principles.

---

### OT4 — Medium
1. **Modbus TCP**: Simple master/slave protocol for reading/writing registers. Operates at Level 1-2 (PLC/HMI communication).
2. **OPC UA**: Service-oriented protocol for data exchange between controllers, HMIs, and historians. Operates at Level 2-3 (supervision and operations).
3. **EtherNet/IP (CIP)**: Industrial Ethernet protocol for real-time control and I/O. Operates at Level 1-2.
4. **PROFINET**: Industrial Ethernet for real-time control, diagnostics, and safety. Operates at Level 1-2.
5. **MQTT**: Lightweight publish/subscribe protocol for IoT/telemetry. Operates at Level 3-4 (edge to cloud).

---

### OT5 — Medium
A **data diode** is a hardware device that physically allows data to flow in only one direction. It's used when you need to guarantee no inbound traffic can reach the OT network — e.g., sending process data to the cloud while ensuring no external entity can send commands back. A **firewall** allows bidirectional traffic with rule-based filtering. Data diodes are more secure but limited — you can't send acknowledgments or commands back. Use data diodes for high-security environments (critical infrastructure, nuclear) where even a single inbound packet is unacceptable.

---

### OT6 — Medium
**Data flow design:**
1. **Historian** (Level 3) collects process data from PLCs/DCS.
2. **OPC UA server** exposes historian data in a standardized format.
3. **Edge gateway** (in IDMZ) subscribes to OPC UA, converts to MQTT, and publishes to a broker.
4. **MQTT broker** (in DMZ or cloud) receives telemetry.
5. **Cloud ingestion** (e.g., AWS IoT Core, Azure IoT Hub) stores data for analytics.

**Security boundaries**: Place the OPC UA server in the OT network, the MQTT broker in the DMZ, and the cloud ingestion behind cloud security. Use a data diode or unidirectional gateway between OT and DMZ if possible. Authenticate MQTT with certificates, encrypt with TLS, and restrict topics.

---

### OT7 — Hard
**IEC 62443 zones and conduits**: A **zone** is a grouping of assets with similar security requirements (e.g., control zone, safety zone). A **conduit** is a communication path between zones with defined security controls.

**Zone-and-conduit model for a manufacturing plant:**
- **Zone 1 — Corporate Network (Level 4)**: IT systems, ERP, email.
- **Zone 2 — Engineering Workstations (Level 3)**: Engineering tools, configuration software.
- **Zone 3 — SCADA Servers (Level 3)**: Historian, SCADA applications.
- **Zone 4 — Control Network (Level 2)**: HMIs, supervisory systems.
- **Zone 5 — PLCs (Level 1)**: Controllers, I/O.
- **Zone 6 — SIS (Safety)**: Safety instrumented systems — isolated from all other zones.

**Conduits**: Between zones, define allowed protocols (e.g., OPC UA from SCADA to PLCs, HTTPS from corporate to engineering). Each conduit has firewall rules, authentication, and monitoring.

---

### OT8 — Hard
**Network segmentation for 200 PLCs, 30 HMIs, SCADA, historian:**
- **VLAN design**: Create VLANs per production line (VLAN 10-13), per function (SCADA VLAN, HMI VLAN, historian VLAN), and a management VLAN for engineering access.
- **Firewall placement**: Deploy firewalls between each production line, between OT and DMZ, and between DMZ and IT. Use industrial firewalls (e.g., MGuard, Tofino) for protocol-aware filtering.
- **Switch architecture**: Use managed industrial switches with VLAN support, spanning tree, and port security. Deploy redundant switches for critical lines.
- **Remote access for vendors**: Use a jump host in the DMZ with MFA, session recording, and time-limited access. Never allow direct VPN to OT.
- **Transition without stopping production**: Implement in phases — start with passive monitoring (SPAN ports), then segment one line at a time during scheduled maintenance windows. Use temporary ACLs to test before enforcing.

---

### OT9 — Hard
**SIS vs BPCS**: The **BPCS** (basic process control system) handles normal process control (regulating temperature, pressure). The **SIS** (safety instrumented system) provides independent protection — it detects dangerous conditions and initiates shutdowns or mitigation. **IEC 61511** is the functional safety standard for SIS, covering the full lifecycle from design to decommissioning.

**Why SIS must be isolated**: A compromised SIS could prevent safety shutdowns, leading to catastrophic failures (explosions, toxic releases). Ransomware reaching the SIS could disable safety functions or cause spurious shutdowns. The SIS must be air-gapped or isolated with unidirectional communication to ensure its integrity.

**If ransomware reaches the SIS**: The plant must initiate emergency shutdown procedures, physically isolate the SIS, and follow manual safety protocols. The SIS may need to be reset/revalidated per IEC 61511 before restart.

---

### OT10 — Medium
- **PLC**: A single controller for discrete control (e.g., one machine). Fast, deterministic, handles I/O and logic.
- **DCS**: Distributed control system for continuous processes (e.g., chemical plant). Multiple controllers coordinated across a plant, with centralized supervision.
- **SCADA**: Supervisory system that monitors and controls geographically distributed assets (e.g., pipelines, power grids). Focuses on data acquisition and operator supervision.

**When to use**: PLC for small/discrete automation; DCS for large continuous processes; SCADA for remote monitoring/control. They can coexist — e.g., a DCS plant may use PLCs for specific machines, and SCADA can overlay both.

---

### OT11 — Medium
**Remote access architecture:**
- **Jump hosts**: A hardened bastion in the DMZ that provides the only entry point to OT.
- **MFA**: Require multi-factor authentication for all remote access.
- **Session recording**: Record all remote sessions for audit and forensic purposes.
- **Vendor access**: Use time-limited, per-session credentials; restrict to specific systems; require approval.
- **Time-limited access**: Auto-expire access after a defined window (e.g., 4 hours).

**Why RDP directly to HMI is unacceptable**: It exposes the HMI to the corporate network, bypasses security controls, lacks audit trails, and creates a direct attack path from IT to OT. It also violates the Purdue Model and IEC 62443 segmentation.

---

### OT12 — Hard
**Detection and response for compromised vendor VPN:**
1. **Network monitoring**: Deploy IDS (e.g., Zeek, Suricata) on OT network SPAN ports. Monitor for anomalous traffic patterns, unexpected connections, or protocol anomalies.
2. **Asset inventory**: Maintain a complete inventory of all OT assets, their IPs, and expected behavior.
3. **Incident response steps**: 
   - Isolate the compromised VPN appliance from the internet.
   - Revoke all vendor credentials and VPN sessions.
   - Analyze logs to determine scope of compromise.
   - Monitor for lateral movement into Level 3/2 networks.
   - If control systems are affected, initiate manual shutdown procedures.
4. **Coordination with control room**: Operators must maintain situational awareness and be prepared for manual operation. They should report any anomalies (e.g., unexpected setpoint changes, valve movements).
5. **Safe operations**: If the threat actor could affect control systems, switch to manual operation or controlled shutdown. Never risk safety for security.

**Role of plant operator**: Operators are the eyes and ears — they detect physical anomalies, execute manual overrides, and communicate with the response team. They must be trained on cyber incident procedures and have authority to shut down if safety is at risk.

---

### OT13 — Easy
An **HMI** (Human-Machine Interface) is a graphical interface that lets operators monitor and control industrial processes — displaying process values, alarms, and allowing setpoint changes. An **engineering workstation** is used by engineers to configure, program, and maintain control systems (e.g., PLC programming, DCS configuration). HMIs are operator-facing; engineering workstations are engineering-facing and typically have more privileged access.

---

### OT14 — Easy
A **historian** is a time-series database that records process data (temperatures, pressures, flow rates) over time. It's critical for process optimization, troubleshooting, and compliance reporting.

**Plant historian (Level 3)**: Collects high-resolution data from control systems at the plant level. Used for operational analysis and troubleshooting.
**Enterprise historian (Level 4)**: Aggregates data from multiple plants for enterprise-wide analytics, reporting, and business intelligence. Lower resolution, longer retention.

---

### OT15 — Easy
**Ladder logic** is a graphical programming language for PLCs that mimics electrical relay circuits. It's executed by PLCs (and some DCS controllers). It remains dominant because: it's intuitive for electricians and engineers, it's standardized (IEC 61131-3), it's proven and reliable, and it's deeply embedded in existing systems and training. Modern PLCs also support structured text, function blocks, and sequential function charts.

---

### OT16 — Easy
An **RTU** (Remote Terminal Unit) is a field device that collects data from sensors and sends it to a SCADA master, and can execute remote commands. It's designed for remote, harsh environments with low power consumption and wide temperature tolerance. A **PLC** is designed for local control with high-speed I/O and deterministic logic. Use RTUs for geographically distributed sites (pipelines, power grids, water systems) where remote monitoring is primary; use PLCs for local control applications.

---

### OT17 — Easy
**Analog signals** represent continuous values (e.g., 4-20mA current, 0-10V voltage) for process variables like temperature or pressure. **Digital signals** represent discrete states (on/off, open/closed) for status or control.

**Why 4-20mA over 0-20mA**: The 4mA baseline provides a live-zero — you can detect a broken wire or failed transmitter (current drops to 0), and the signal is less affected by voltage drops over long cable runs. It also allows the transmitter to be powered from the loop (2-wire configuration).

---

### OT18 — Medium
**OT asset inventory** is the foundation of OT security because you can't protect what you don't know. It provides visibility into what devices exist, their firmware, protocols, and vulnerabilities.

**Discovery tools**: 
- **Passive monitoring**: Capture traffic on SPAN ports to identify devices and protocols without sending packets. Safe, non-intrusive.
- **Active scanning**: Send probes (e.g., Nmap) to identify devices and open ports. **Dangerous** because legacy devices may crash or behave unexpectedly when scanned — many PLCs and RTUs are not designed to handle unexpected traffic.

Use passive monitoring as the primary method; active scanning only on known-safe devices during maintenance windows.

---

### OT19 — Hard
**MITRE ATT&CK for ICS** is a knowledge base of adversary tactics and techniques specific to industrial control systems. It includes 14 tactics (vs. 14 in enterprise, but with ICS-specific techniques).

**Five tactics with example techniques:**
1. **Initial Access**: "Exploit Public-Facing Application" — attacking a remote access VPN or web server.
2. **Execution**: "Modify Controller Logic" — uploading malicious ladder logic to a PLC.
3. **Persistence**: "Project File Infection" — embedding malware in engineering project files.
4. **Lateral Movement**: "Remote Services" — using RDP or VNC to move between HMIs and servers.
5. **Impact**: "Loss of Safety" — disabling safety functions or causing unsafe process conditions.

**Difference from enterprise ATT&CK**: ICS framework includes physical/process impact, controller-specific techniques, and emphasizes safety consequences. **Use it to assess gaps**: Map your defenses to each tactic, identify missing detections, and prioritize mitigations based on risk to safety and production.

---

### OT20 — Hard
**Converged IT/OT SOC design:**
- **Log collection**: Deploy passive collectors (e.g., industrial protocol sensors) on SPAN ports. Use OPC UA or syslog where supported. Avoid active agents on critical controllers. Collect from firewalls, HMIs, and engineering workstations.
- **SIEM integration**: Forward OT logs to a central SIEM (e.g., Splunk, Sentinel) with OT-specific parsers for Modbus, OPC UA, and proprietary protocols.
- **OT-specific detection rules**: Monitor for unauthorized firmware changes, unexpected protocol usage, new devices on the network, and abnormal Modbus function codes.
- **Alert triage workflows**: Create a tiered workflow — Tier 1 (IT analysts) triage, escalate to Tier 2 (OT engineers) for OT-specific alerts. OT engineers have context on process impact.
- **Staffing**: Blend IT security analysts with OT engineers. Cross-train both — IT analysts learn OT protocols; OT engineers learn security fundamentals.
- **False positives**: OT environments have limited tolerance for false positives — a false alarm can cause unnecessary shutdowns. Use context-aware rules, baseline behavior, and validate alerts against process state.

**Handling unauthorized firmware change alert**: 
1. Verify the alert with the OT engineer — confirm if a change was scheduled.
2. If unauthorized, isolate the PLC from the network (physically or via firewall rule).
3. Capture forensic evidence (firmware image, logs).
4. Determine if the change was malicious or accidental.
5. Restore from known-good backup and revalidate per safety procedures.
6. Investigate the source — check engineering workstations, remote access logs, and network connections.
