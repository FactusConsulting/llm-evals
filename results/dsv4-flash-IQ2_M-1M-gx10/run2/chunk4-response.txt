## Go (20 questions)

### G1 — Easy
**Slice vs Array**: Arrays have a fixed length determined at compile time (`[5]int`). Slices are dynamic views into an underlying array (`[]int`), with length and capacity. Slices are more common and flexible.

**Appending at capacity**: When `append` exceeds a slice's capacity, Go allocates a new, larger backing array (typically doubling capacity), copies all existing elements, then appends the new element. The old array becomes eligible for garbage collection. This is O(n) due to copying.

### G2 — Easy
- `var x int` declares `x` as `int` with zero value `0`.
- `x := 0` uses type inference and is shorthand for declaration + assignment.

**Cannot use `:=`**:
- At package level (outside functions) — only inside functions.
- When declaring without initializing (e.g., `var x int`).
- When one variable already exists and you want to redeclare without `var` (though `:=` can redeclare if at least one variable on the left is new).

### G3 — Medium
**Goroutine**: A lightweight, cooperatively scheduled thread managed by the Go runtime. Created with `go func()`. Starts with a small stack (2KB) that grows dynamically.

**vs OS thread**: OS threads have large fixed stacks (1-8MB), are scheduled by the OS kernel, and have high creation/context-switch overhead. Goroutines are multiplexed onto OS threads (M:N scheduling), with much lower creation cost and faster context switches.

**GMP model**: 
- **G** = Goroutine (task)
- **M** = Machine (OS thread)
- **P** = Processor (logical CPU, holds run queue)
The scheduler assigns Gs to Ps, and Ps to Ms. When a G blocks (e.g., on I/O), the M can be released to run other Gs. This enables efficient concurrency with few OS threads.

### G4 — Medium
**Channels**: Typed conduits for communication between goroutines. Created with `make(chan T)`.

**Buffered vs unbuffered**:
- **Unbuffered** (`make(chan T)`): Send blocks until a receiver is ready; receive blocks until a sender is ready. Provides synchronization (happens-before).
- **Buffered** (`make(chan T, n)`): Send blocks only when buffer is full; receive blocks only when buffer is empty. Decouples sender/receiver timing.

**Sending to full buffered channel**: The sender blocks until another goroutine receives from the channel, freeing space. This is a fundamental backpressure mechanism.

### G5 — Medium
**context package**: Provides cancellation, deadlines, and request-scoped values. Used to propagate cancellation signals across API boundaries (e.g., HTTP servers, database calls).

**Example**:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

req, err := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
if err != nil { /* handle */ }

resp, err := http.DefaultClient.Do(req)
if err != nil {
    // err could be context.DeadlineExceeded or context.Canceled
    log.Fatal(err)
}
defer resp.Body.Close()
```

### G6 — Medium
**Interface satisfaction**: Go uses **implicit** satisfaction — a type satisfies an interface if it implements all methods, with no explicit `implements` declaration. This differs from Java/C# where classes must explicitly declare they implement an interface.

**Empty interface** (`interface{}` or `any`): Accepts any type. Powerful for generic containers (e.g., `fmt.Println`), but dangerous because it bypasses type safety — you must type-assert to use the value, risking runtime panics if the type is wrong.

### G7 — Hard
**Memory model**: Go guarantees happens-before only through synchronization primitives (channels, mutexes, atomics). Without them, goroutine visibility is **not guaranteed** — the compiler/CPU may reorder operations.

**Why unsafe**: The `for !ready {}` loop has no synchronization. The compiler may cache `ready` in a register, or the CPU may reorder `data = "hello"` and `ready = true`. The main goroutine may never see `ready = true`, or may see it before `data` is written.

**Correct alternatives**:
```go
// 1. Channel
done := make(chan struct{})
go func() {
    data = "hello"
    close(done)
}()
<-done
fmt.Println(data)

// 2. Mutex
var mu sync.Mutex
go func() {
    mu.Lock()
    data = "hello"
    ready = true
    mu.Unlock()
}()
mu.Lock()
for !ready { mu.Unlock(); runtime.Gosched(); mu.Lock() }
mu.Unlock()
fmt.Println(data)

// 3. Atomic
var ready atomic.Bool
go func() {
    data = "hello"
    ready.Store(true)
}()
for !ready.Load() {}
fmt.Println(data)
```

### G8 — Hard
**sync.Mutex vs sync.RWMutex**:
- `Mutex`: Exclusive lock — one goroutine at a time (read or write).
- `RWMutex`: Allows multiple readers OR one writer. Readers use `RLock()/RUnlock()`, writers use `Lock()/Unlock()`. Better for read-heavy workloads.

**sync.Map vs map + mutex**:
- `sync.Map` is optimized for:
  - Read-heavy workloads with distinct keys (e.g., cache).
  - Avoiding lock contention via atomic operations and per-shard locking.
  - Cases where you'd otherwise need separate locks for reads/writes.
- Regular map + mutex is simpler and faster for write-heavy or single-key workloads.

**Performance trade-offs**: `sync.Map` has higher overhead for writes and simple access patterns. A mutex-protected map is more predictable and often faster for small maps or write-heavy scenarios. `sync.Map` shines when reads dominate and keys are spread out.

### G9 — Hard
**Go modules**: Introduced in Go 1.11, replaced GOPATH. A module is a collection of packages with a `go.mod` file defining module path, Go version, and dependencies.

**go.mod vs go.sum**:
- `go.mod`: Declares module path, Go version, and direct dependencies with versions (e.g., `require github.com/foo/bar v1.2.3`).
- `go.sum`: Contains cryptographic checksums (SHA-256) of dependency module files. Ensures reproducible builds and detects tampering.

**go mod tidy**: Adds missing dependencies, removes unused ones, and updates `go.mod`/`go.sum` to match the source code.

**MVS (Minimum Version Selection)**: When multiple modules depend on different versions of the same module, MVS selects the **minimum version that satisfies all constraints**. This ensures reproducibility — the build uses the same versions regardless of build order.

### G10 — Medium
**defer**: Schedules a function call to run when the enclosing function returns. Used for cleanup (closing files, unlocking mutexes).

**Order**: Multiple defers execute in **LIFO** (last-in, first-out) order — the last deferred call runs first.

**Gotcha in loop**: `defer` in a loop accumulates calls that run at the **end of the function**, not at the end of each iteration. This can cause resource leaks (e.g., open files) or unexpected behavior. Fix by wrapping the loop body in a helper function or using explicit cleanup.

### G11 — Easy
**Pointer**: A variable that stores the memory address of another variable. Declared with `*T`, dereferenced with `*`.

**Zero value**: `nil` — no memory address.

**Creating pointer to struct literal**:
```go
p := &Person{Name: "Alice"}  // p is *Person
// or
p := new(Person)  // returns *Person with zero values
```

### G12 — Easy
**init()**: A special function that runs automatically when a package is initialized. Used for setup that can't be done in variable declarations.

**When**: Runs after variable declarations are evaluated, before `main()` runs. Package initialization order is determined by dependency order (imports first).

**Multiple init()**: Yes, a package can have multiple `init()` functions. They execute in **file order** (as determined by the compiler, typically lexical file name order). Within a file, they execute in declaration order.

### G13 — Easy
**make vs new**:
- `make(T, args)` — allocates and initializes **slices, maps, channels**. Returns a non-zero value (e.g., empty slice, empty map).
- `new(T)` — allocates memory for a type and returns a **pointer** to zeroed memory (`*T`). Works with any type.

**Types**: `make` only works with slice, map, channel. `new` works with any type.

### G14 — Easy
**Error handling**: Go uses explicit error returns. The `error` interface is:
```go
type error interface {
    Error() string
}
```

**Idiomatic pattern**: Check `if err != nil` immediately after a call, handle or return early.

**errors.Is vs errors.As vs ==**:
- `==` — direct comparison, only works if the error is the exact same value (not wrapped).
- `errors.Is(err, target)` — checks if `err` matches `target` in the error chain (works with `%w` wrapping).
- `errors.As(err, &target)` — finds the first error in the chain that matches the target type and assigns it.

### G15 — Easy
**Composite types and zero values**:
- **map**: `nil` — reading from nil map returns zero value, writing panics.
- **slice**: `nil` — `len`/`cap` are 0, append works.
- **channel**: `nil` — sending/receiving blocks forever.
- **struct**: All fields set to their zero values (e.g., `0`, `""`, `nil`).

### G16 — Medium
**Race condition**: When multiple goroutines access shared data without synchronization, and at least one writes. Results are unpredictable.

**-race flag**: The `go run -race` / `go test -race` flag instruments the binary to detect data races at runtime. It uses the ThreadSanitizer algorithm to track memory accesses and reports races with stack traces.

**Example**:
```go
var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }()  // race!
}
```

**Fix with mutex**:
```go
var mu sync.Mutex
var counter int
for i := 0; i < 1000; i++ {
    go func() {
        mu.Lock()
        counter++
        mu.Unlock()
    }()
}
```

**Fix with channel**:
```go
ch := make(chan int, 1000)
for i := 0; i < 1000; i++ {
    go func() { ch <- 1 }()
}
counter := 0
for i := 0; i < 1000; i++ { counter += <-ch }
```

### G17 — Medium
**select**: A control structure for waiting on multiple channel operations. It blocks until one of its cases can proceed.

**vs switch**: `switch` compares values; `select` waits on channel operations. `select` has no default case unless explicitly added.

**Multiple ready cases**: If multiple cases are ready, Go picks one **uniformly at random** (to prevent starvation).

**Timeout with select**:
```go
select {
case msg := <-ch:
    fmt.Println(msg)
case <-time.After(5 * time.Second):
    fmt.Println("timeout")
}
```

### G18 — Hard
**Escape analysis**: The compiler determines whether a variable can be allocated on the stack or must be moved to the heap. If a variable's address escapes the function (e.g., returned, stored in a global, passed to a function that keeps it), it's heap-allocated.

**Inspection**: Use `go build -gcflags=-m` (or `-m=2` for more detail). Output shows decisions like `moved to heap`.

**Why it matters**: Heap allocations increase GC pressure and memory overhead. Stack allocations are nearly free (just stack pointer adjustment). Optimizing hot paths to avoid escapes (e.g., using value receivers, avoiding returning pointers) can significantly improve performance.

### G19 — Hard
**reflect package**: Provides runtime introspection of types and values.

- `reflect.Type` — describes the type (e.g., name, kind, methods).
- `reflect.Value` — represents a runtime value, allows reading/writing.

**Performance costs**: Reflection is slow — involves runtime type checks, interface boxing, and often allocations. It can be 10-100x slower than static dispatch.

**When justified**: 
- Generic serialization (e.g., JSON encoding).
- Building ORMs or validation libraries.
- Implementing dependency injection.

**vs code generation**: Code generation (e.g., `go generate`) produces static, type-safe code at compile time — faster and safer. Use reflection when the type set is unknown at compile time; use code generation when types are known but repetitive.

### G20 — Hard
**go:embed**: A compiler directive that embeds files into the Go binary at compile time.

```go
//go:embed static/*
var staticFS embed.FS
```

**Single files**: `//go:embed file.txt` — embeds as `[]byte` or `string`.
**Directories**: `//go:embed dir/*` — embeds as `embed.FS` (implements `fs.FS`).
**File systems**: `embed.FS` implements `io/fs.FS`, so it works with `fs.ReadFile`, `http.FileServer`, etc.

**Limitations**:
- Files must be in the module directory (no `..`).
- Patterns must match at least one file.
- Cannot embed files with names starting with `_` or `.` unless explicitly matched.
- Embedded files are read-only.

**Interaction with io/fs.FS**: `embed.FS` implements `fs.FS`, `fs.ReadDirFile`, etc., so it can be used anywhere an `fs.FS` is expected (e.g., `http.FileServer`, `fs.WalkDir`).

## Rust (20 questions)

### R1 — Easy
**Ownership**: Rust's memory management system — each value has a single owner.

**Three rules**:
1. Each value has an owner (a variable).
2. Only one owner at a time.
3. When the owner goes out of scope, the value is dropped (freed).

This ensures memory safety without garbage collection.

### R2 — Easy
**String vs &str**:
- `String` — owned, heap-allocated, mutable, can grow/shrink.
- `&str` — borrowed reference to a string slice, immutable, points to a `String` or string literal.

**Function signatures**: Use `&str` for parameters (borrowing) — it's more flexible and avoids allocation. Use `String` when you need to own or modify the string. Return `String` when creating new strings.

### R3 — Medium
**Borrowing**: Allows using a value without taking ownership. The borrow checker enforces rules at compile time.

**Rules**:
1. You can have **many** shared references (`&T`) — immutable.
2. You can have **one** mutable reference (`&mut T`) — exclusive.
3. You cannot have a shared reference and a mutable reference to the same value simultaneously.

These rules prevent data races and dangling references at compile time.

### R4 — Medium
**Result<T, E>**: Represents success (`Ok(T)`) or failure (`Err(E)`). Used for recoverable errors.
**Option<T>**: Represents presence (`Some(T)`) or absence (`None`). Used for nullable values.

**? operator**: Unwraps `Ok`/`Some` or returns `Err`/`None` early from the function. Requires the function to return a compatible `Result`/`Option` type.

**Example**:
```rust
use std::fs;
use std::io::Error;

fn read_file(path: &str) -> Result<String, Error> {
    let contents = fs::read_to_string(path)?;  // returns Err early if failed
    Ok(contents)
}
```

### R5 — Medium
- **Box<T>**: Single ownership, heap-allocated. Used for recursive types, large data, or trait objects. No reference counting.
- **Rc<T>**: Single-threaded reference counting. Multiple owners share the value. Not thread-safe.
- **Arc<T>**: Atomic reference counting. Thread-safe version of `Rc`. Used for shared ownership across threads.

**When to use**: `Box` for single ownership, `Rc` for shared single-threaded, `Arc` for shared multi-threaded.

### R6 — Medium
**Traits**: Define shared behavior. Similar to Go interfaces but **explicit** — types must implement the trait.

**vs Go interfaces**: Go interfaces are implicit (structural), Rust traits are explicit (nominal). Rust traits can have default methods, associated types, and generic parameters.

**Trait objects (`dyn Trait`)**: Dynamic dispatch — the concrete type is unknown at compile time. Used with `Box<dyn Trait>`. Has runtime overhead (vtable lookup).

**Generic with trait bound (`T: Trait`)**: Static dispatch — the compiler generates a separate function for each concrete type. No runtime overhead, but code bloat.

### R7 — Hard
**Lifetimes**: Rust's way of ensuring references are valid as long as they're used. The compiler tracks how long references live.

**Why fails**: The function returns `&str` but the compiler can't determine which input's lifetime the return value borrows from. Without an explicit lifetime, the compiler can't verify the return value outlives the caller's usage.

**Fix**:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This says: the return value has the same lifetime as both inputs (the smaller of the two).

### R8 — Hard
**Send**: A type is `Send` if it's safe to move to another thread. Most types are `Send` (e.g., `Vec`, `String`).
**Sync**: A type is `Sync` if it's safe to share references across threads. `&T` is `Send` if `T` is `Sync`.

**Why Rc<T> is not Send**: `Rc` uses non-atomic reference counting. If moved to another thread, concurrent `clone`/`drop` could cause data races on the counter.

**Why Arc<T> is safe**: `Arc` uses atomic reference counting (`fetch_add`/`fetch_sub`), which is thread-safe. However, `Arc<T>` is only `Send`/`Sync` if `T` is `Send`/`Sync`.

### R9 — Hard
**async/await under the hood**: `async fn` creates a **Future** — a state machine that can be polled. When you `await`, the future yields control back to the executor. The compiler transforms the async function into a state machine that stores local variables across await points.

**Future**: A trait with `poll` method. When polled, it either returns `Pending` (not ready) or `Ready(value)`.

**Executor (e.g., Tokio)**: Polls futures, manages I/O events, and schedules tasks. It uses a work-stealing thread pool.

**vs Go goroutines**: 
- Go goroutines are **stackful** — each has its own stack, scheduled by the Go runtime.
- Rust futures are **stackless** — they don't have their own stack; they're state machines that can be polled. This makes them more memory-efficient but requires an executor to drive them.

### R10 — Medium
**unsafe**: A block that allows operations the compiler can't verify. It's not "dangerous" per se, but requires the programmer to uphold safety invariants.

**3 things you can do**:
1. Dereference raw pointers (`*const T`, `*mut T`).
2. Call unsafe functions (e.g., FFI to C).
3. Access or modify mutable static variables.

**When justified**: FFI (calling C code), implementing safe abstractions over raw memory, performance-critical code where the compiler can't optimize. Should be minimal and well-documented.

### R11 — Easy
**Pattern matching**: `match` allows destructuring and matching against patterns. It's exhaustive — the compiler requires all possible cases to be handled.

**match vs if let**: `match` handles multiple patterns and is exhaustive. `if let` is for a single pattern — it's syntactic sugar for `match` with one arm.

**Exhaustiveness**: The compiler enforces that `match` covers all possible values. For enums, you must handle all variants or use `_` (wildcard). This prevents runtime panics from unhandled cases.

### R12 — Easy
**Vec<T> vs array [T; N]**:
- `Vec<T>` — heap-allocated, dynamic size, can grow/shrink.
- `[T; N]` — stack-allocated (unless boxed), fixed size known at compile time.

**Vec memory management**: When pushing beyond capacity, `Vec` allocates a new larger buffer (typically 2x), copies elements, and deallocates the old buffer. This is amortized O(1) per push.

### R13 — Easy
**Enums in Rust**: Unlike C/Java enums (which are just integers), Rust enums can hold data (algebraic data types). Each variant can have associated values.

**Option<T>**:
```rust
enum Option<T> {
    Some(T),
    None,
}
```

**Why no null**: Rust doesn't have null pointers. Instead, absence is represented by `Option<T>` — the compiler forces you to handle the `None` case. This eliminates null pointer dereference bugs.

### R14 — Easy
**impl block**: Defines methods and associated functions for a type.

- **&self** — immutable borrow, can read but not modify.
- **&mut self** — mutable borrow, can modify.
- **self** — takes ownership, consumes the value.

**Associated functions**: Functions that don't take `self` — called with `Type::function()`. Example: `String::new()` creates a new empty `String`.

### R15 — Easy
**derive macro**: Automatically implements traits for a type. Used with `#[derive(Trait)]`.

**Common examples**:
- `Debug` — formatting with `{:?}`.
- `Clone` — deep copy.
- `PartialEq` — equality comparison.
- `Serialize`/`Deserialize` — from serde.

**Cannot derive**: When the trait requires behavior that can't be automatically generated. For example, `PartialEq` can't be derived if the type contains floats (NaN != NaN), or `Serialize` if the type has non-serializable fields. You must implement manually.

### R16 — Medium
**Cow<'a, T>** (Clone on Write): An enum that either borrows (`Borrowed`) or owns (`Owned`) data. When you need a value that might be borrowed or owned, `Cow` avoids unnecessary allocations.

**Useful when**: You have a function that may return either a borrowed reference or a newly created value. Example:

```rust
use std::borrow::Cow;

fn process(input: &str) -> Cow<'_, str> {
    if input.starts_with("hello") {
        Cow::Borrowed(input)  // no allocation
    } else {
        Cow::Owned(format!("hello {}", input))  // allocation
    }
}
```

This avoids cloning when the input already matches the desired format.

### R17 — Medium
**Module system**:
- `mod` — declares a module (inline or in a file).
- `use` — brings items into scope.
- `pub` — makes items public (visible outside the module).

**File system mapping**: 
- `mod foo` looks for `foo.rs` or `foo/mod.rs`.
- In Rust 2018, `foo.rs` can have a `foo/` directory for submodules (no `mod.rs` needed).

**2015 vs 2018 changes**: 
- 2018 edition removed the need for `mod.rs` files (can use `foo.rs` + `foo/` directory).
- `use` paths are more uniform (e.g., `use crate::foo::bar` vs `use foo::bar`).
- `extern crate` is no longer needed for dependencies.

### R18 — Hard
**Pin<T>**: A wrapper that prevents the value from being moved. It's needed for **self-referential structs** — structs that contain pointers to their own fields. If moved, the pointers become dangling.

**Why needed for async/await**: Async futures are state machines that may contain self-referential data (e.g., a buffer that holds a reference to itself). When a future is polled, it must not be moved, so it's pinned.

**Unpin**: A marker trait. Types that implement `Unpin` can be moved freely even when pinned. Most types are `Unpin`. `Pin<Box<T>>` is used for `!Unpin` types.

### R19 — Hard
**Macro system**:
- **Declarative macros** (`macro_rules!`): Pattern-matching macros that generate code. They match tokens and expand to code.
- **Procedural macros**: More powerful — they take tokens, process them, and produce new tokens. Three types:
  - **Derive** — `#[derive(MyTrait)]`.
  - **Attribute** — `#[my_attribute]`.
  - **Function-like** — `my_macro!()`.

**Hygiene rules**: Declarative macros are hygienic — they don't accidentally capture variables from the caller's scope. Procedural macros are less hygienic — they can introduce new identifiers that may conflict. This requires careful naming.

### R20 — Hard
**Zero-cost abstractions**: Rust's abstractions compile to the same machine code as hand-written C, with no runtime overhead.

**Iterators**: Chain operations (`map`, `filter`, `fold`) that are optimized away by the compiler — they become direct loops with no allocation or virtual dispatch.

**Generics (monomorphization)**: The compiler generates a separate function for each concrete type. No runtime dispatch — the function is specialized for the type.

**Trait static dispatch**: When using `T: Trait` generics, the compiler knows the concrete type at compile time and generates direct calls. No vtable lookup.

**Result**: Performance comparable to C because the compiler optimizes away all abstraction layers — iterators become raw loops, generics become specialized code, and trait bounds become direct calls.
