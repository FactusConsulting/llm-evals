# Answers to All 60 Questions

## JavaScript / TypeScript

### JS1: var, let, const, and hoisting

| | Scope | Redeclare | Reassign | Before declaration |
|---|---|---|---|---|
| `var` | Function (or global) | Yes | Yes | `undefined` |
| `let` | Block | No | Yes | `ReferenceError` (TDZ) |
| `const` | Block | No | No (binding only) | `ReferenceError` (TDZ) |

- **`const` freezes the binding, not the value.** `const o = {}; o.x = 1` is fine.
- **Hoisting:** declarations are registered when their scope is created, before any code runs.
  - `var` is initialized to `undefined`.
  - `let`, `const` and `class` stay uninitialized until their line executes. That window is the Temporal Dead Zone (TDZ).
  - Function declarations are hoisted with their body, so you can call them before they appear.
- **Global `var`** also creates a property on `globalThis`. `let` and `const` do not.

### JS2: The event loop

- **Call stack:** synchronous execution frames.
- **Macrotask (task) queue:** `setTimeout`, `setInterval`, I/O, UI events, `MessageChannel`, `setImmediate` in Node.
- **Microtask queue:** Promise reactions, `queueMicrotask`, `MutationObserver`. Node's `process.nextTick` runs even earlier.

**One loop iteration:**
1. Run one macrotask to completion.
2. Drain the entire microtask queue, including microtasks that other microtasks enqueue.
3. The browser may render.
4. Repeat.

```js
setTimeout(() => console.log('timeout'));
Promise.resolve().then(() => console.log('micro'));
console.log('sync');
// sync, micro, timeout
```

A microtask that keeps scheduling microtasks starves rendering and all macrotasks.

### JS3: Closures and the for-loop bug

A **closure** is a function plus the lexical environment it captured. It keeps access to outer variables after the outer function has returned.

```js
function counter() { let n = 0; return { inc: () => ++n, get: () => n }; }
const c = counter(); c.inc(); c.get(); // 1  (n is private state)
```

Closures are commonly used for memoization, partial application, private state, and event handlers.

**The classic bug:**
```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 3 3 3
```
There is a single function-scoped `i`, and every callback shares it.

**Fixes:**
- Use `let`, which creates a fresh binding per iteration: prints `0 1 2`.
- Use an IIFE: `(j => setTimeout(() => console.log(j)))(i)`.
- Pass the value as an argument: `setTimeout(console.log, 0, i)`.

### JS4: Promises, async/await, error handling

- **A Promise** is a placeholder for a future value, in one of three states: pending, fulfilled, or rejected.
- **`.then`** returns a new promise, which is what makes chaining work.
- **Errors in chains:** a thrown error or a rejection skips forward to the next `.catch`. `.finally` runs either way.
- **`async` functions** always return a promise. `await` unwraps a fulfilled value or throws the rejection reason, so ordinary `try/catch/finally` works.

```js
async function load() {
  try { const r = await fetch(url); return await r.json(); }
  catch (e) { log(e); throw e; }
}
```

**Gotchas:**
- `return promise` inside `try` without `await` means the `catch` will not see its rejection.
- Unhandled rejections crash Node (≥15).
- `forEach(async …)` does not wait for anything.

**Combinators:**
- **`Promise.all`** fails fast: it rejects on the first rejection and otherwise resolves to an array of values. The other operations keep running; they are not cancelled.
- **`Promise.allSettled`** never rejects. It resolves to `[{status:'fulfilled', value} | {status:'rejected', reason}]`. Use it when you want every result regardless of individual failures.
- **Also:** `Promise.race` settles with the first settled promise. `Promise.any` resolves with the first fulfilled one, or rejects with an `AggregateError` if all fail.

### JS5: interface vs type; discriminated unions

- **`interface`:**
  - Describes object shapes only.
  - Supports declaration merging, so the same interface can be declared twice.
  - Uses `extends`, which gives better error messages and cached relationship checks. It is slightly faster for the compiler on large hierarchies.
- **`type`:**
  - Can alias anything: unions, intersections, primitives, tuples, mapped and conditional types, template literal types.
  - Cannot be merged.
- **Rule of thumb:**
  - Use `interface` for public object contracts and class shapes, especially when you want augmentation (for example extending library types).
  - Use `type` for unions and computed types.

**Discriminated union:** a union whose members share a literal "tag" property. TypeScript narrows on it.

```ts
type Shape = { kind: 'circle'; r: number } | { kind: 'rect'; w: number; h: number };
function area(s: Shape) {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'rect': return s.w * s.h;
    default: const _x: never = s; return _x; // exhaustiveness check
  }
}
```

### JS6: Prototypal inheritance

- **The prototype chain:** every object has an internal `[[Prototype]]` link (`Object.getPrototypeOf`, `__proto__`). Property lookup walks the chain until it finds the key or reaches `null`.
- **Where writes go:** writes always create or modify an *own* property, unless the chain has a setter or a non-writable property.
- **`Object.create(proto, descriptors?)`** creates a new object whose `[[Prototype]]` is `proto`. `Object.create(null)` gives a dictionary with no prototype at all.

```js
const animal = { speak() { return `${this.name} speaks`; } };
const dog = Object.create(animal); dog.name = 'Rex'; dog.speak();
```

**ES6 classes are mostly syntax over the same mechanism:**
- Methods live on `C.prototype`.
- `new C()` creates an object whose prototype is `C.prototype`.
- `extends` sets `Child.prototype.__proto__ = Parent.prototype`, and also `Child.__proto__ = Parent` so static members are inherited.

**Real differences from constructor functions:**
- Class bodies are strict mode.
- Classes are not callable without `new`.
- Methods are non-enumerable.
- `super` uses `[[HomeObject]]`.
- Derived constructors must call `super()` before using `this`.
- `#private` fields are not prototype-based at all.

### JS7: `this` binding

`this` is determined by **how a function is called**, not where it is defined. The exception is arrow functions, which take `this` lexically from the enclosing scope and ignore all the rules below.

**Priority, highest first:**
1. **`new` binding:** `new Foo()` makes `this` the freshly created object.
2. **Explicit binding:** `fn.call(obj)`, `fn.apply(obj)`, `fn.bind(obj)`.
3. **Implicit binding:** `obj.fn()` makes `this` equal `obj`. This is lost when you detach the method: `const f = obj.fn; f()`.
4. **Default binding:** `undefined` in strict mode or modules; `globalThis` in sloppy mode.

**`bind()`:**
- Returns a new *bound function exotic object* with a fixed `this` and optionally pre-filled arguments.
- Re-binding does not change `this`: `f.bind(a).bind(b)` still uses `a`. The second `bind` can only add more partial arguments.
- `new` overrides a bound `this`. The bound `this` is ignored and the prepended arguments are still applied.
- `call`/`apply` on a bound function cannot override `this` either.

### JS8: WeakRef, FinalizationRegistry, WeakMap

- **`WeakRef(obj)`:**
  - Holds a reference that does not keep `obj` alive.
  - `ref.deref()` returns the object, or `undefined` once it has been collected.
- **`FinalizationRegistry(cb)`:**
  - `registry.register(obj, heldValue, unregisterToken)` calls `cb(heldValue)` at some point after `obj` is collected.
  - Timing is not guaranteed, and the callback may never run.
- **When to use them:**
  - Caches of expensive, re-creatable objects, such as decoded images or large parsed data.
  - Releasing external resources (for example Wasm memory or native handles) as a *backup* to explicit cleanup.
- **When not to use them:** never for program correctness, since GC is nondeterministic. The spec explicitly advises avoiding them where possible.

```js
const cache = new Map();
const reg = new FinalizationRegistry(k => { if (!cache.get(k)?.deref()) cache.delete(k); });
function get(k) {
  let v = cache.get(k)?.deref();
  if (!v) { v = compute(k); cache.set(k, new WeakRef(v)); reg.register(v, k); }
  return v;
}
```

**Why WeakMap/WeakSet keys must be objects:**
- A weak entry lives only as long as its key is reachable by identity.
- Primitives have no identity. `"a"` or `42` can be recreated at any time, so "is this key still reachable?" is meaningless and the entry could never be safely collected.
- Since ES2023, non-registered symbols are also allowed, because they are unique and unforgeable.
- WeakMaps are not enumerable and have no `size`. Otherwise they would expose GC timing.
- **Typical uses:** private per-object metadata, and DOM-node → data maps that disappear with the node.

### JS9: V8 optimizations

**Pipeline:**
- Ignition interprets bytecode and collects type feedback.
- Sparkplug is a baseline compiler.
- Maglev is a mid-tier optimizer.
- TurboFan is the top-tier optimizing compiler.

**Hidden classes (Maps/Shapes):**
- Objects with the same properties added in the same order share a hidden class, which records each property's offset.
- Adding a property creates a transition to a new hidden class.
- This turns property lookup into a fixed-offset load.

**Inline caching:**
- Each property-access site caches the hidden class(es) it has seen, together with the offset.
- Monomorphic (1 shape) is fastest. Polymorphic (2–4 shapes) is still good. Megamorphic (more) falls back to a slow generic lookup.

**Deoptimization:**
- Optimized code relies on speculative assumptions, such as "x is always a Smi" or "obj always has shape M".
- When an assumption breaks, V8 bails out to the interpreter, discards the optimized code, and may re-optimize later.
- Repeated deopt cycles are expensive.

**Patterns that cause deopt or slowdowns:**
- Initializing properties in different orders, or conditionally adding them outside the constructor.
- `delete obj.prop`, which drops the object into slow dictionary mode.
- Mixing types at one site: numbers and strings, or ints and doubles in the same array.
- Holey arrays (`new Array(n)`, `arr[1000] = x`) and out-of-bounds reads.
- Megamorphic call sites, for example a generic function fed many object shapes.
- `arguments` misuse in sloppy mode, `eval`, and `with`.
- Changing the prototype after creation (`Object.setPrototypeOf`).
- Functions whose argument types keep changing.

**Diagnosis:** `node --trace-deopt --trace-opt`, or `%OptimizeFunctionOnNextCall` together with `--allow-natives-syntax`.

### JS10: Tree-shaking

Tree-shaking is dead-code elimination at the module-export level, done by bundlers such as Rollup, esbuild, webpack and Vite. The bundler marks which exports are actually imported and drops the rest. A minifier (Terser) then removes the unreachable code.

**Why ES modules work:**
- `import`/`export` are static. They appear at the top level, use literal specifiers and fixed names, and are live read-only bindings.
- The dependency graph and the set of used exports are therefore known at build time.

**Why CommonJS does not:**
- `require()` is an ordinary runtime function call. Specifiers can be computed (`require(name)`), and it can be called conditionally.
- `module.exports` is a mutable object that can be reassigned or have keys added dynamically (`exports[key] = …`).
- Consumers can access exports dynamically (`const lib = require('x'); lib[fn]()`).
- The bundler cannot prove an export is unused, so it keeps everything.
- Some tools, such as webpack and `@rollup/plugin-commonjs`, handle simple static patterns, but only partially.

**Helping it along:**
- Set `"sideEffects": false` in `package.json`.
- Add `/*#__PURE__*/` annotations.
- Avoid barrel files that re-export modules with side effects.

### JS11: null vs undefined, ??, ?.

- **`undefined`** means "not assigned or absent": uninitialized variables, missing properties and arguments, and functions with no return value.
- **`null`** is an intentional "no value" set by the programmer.
- **`typeof`:** `typeof null === 'object'` (a historical bug). `typeof undefined === 'undefined'`.
- **Equality:**
  - `null == undefined` is `true`. Loose equality treats them as equal to each other and to nothing else, so `null == 0` is `false`.
  - `null === undefined` is `false`.
  - The idiom `x == null` checks for both.
- **`a ?? b`** returns `b` only if `a` is `null` or `undefined`. Unlike `||`, it keeps `0`, `''` and `false`: `count ?? 10`.
  - It cannot be mixed with `||`/`&&` without parentheses.
  - The assignment form is `a ??= b`.
- **`a?.b`, `a?.[k]`, `fn?.()`** short-circuit to `undefined` if the left side is nullish: `user?.address?.city ?? 'N/A'`.

### JS12: map, filter, reduce, flatMap

```js
[1,2,3].map(x => x * 2);          // [2,4,6]   same length, transformed
[1,2,3].filter(x => x % 2);       // [1,3]     subset
[1,2,3].reduce((acc, x) => acc + x, 0); // 6 folds into one value
```

**`reduce(cb, init)`:**
- `acc` starts at `init`, and the callback runs for every element.
- Without `init`, `acc` starts as `arr[0]` and iteration begins at index 1. An empty array with no `init` throws a `TypeError`.
- Always pass an initial value, especially when building objects: `arr.reduce((m, u) => (m[u.id] = u, m), {})`.

**`flatMap(fn)`:**
- Equivalent to `map(fn).flat(1)`, done in one pass.
- Useful for one-to-many mappings: `sentences.flatMap(s => s.split(' '))`.
- Also works as map-and-filter together: `arr.flatMap(x => x.valid ? [x.val] : [])`.

### JS13: Template literals and tagged templates

**Template literals** use backticks and support:
- Interpolation: `` `Hi ${name}, ${a + b}` ``
- Multi-line strings
- `String.raw` for raw strings

**A tagged template** calls a function with `(stringsArray, ...values)`. `strings.raw` holds the uninterpreted text.

```js
const esc = s => String(s).replace(/[&<>"']/g,
  c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]));
function html(strings, ...vals) {
  return strings.reduce((out, s, i) => out + s + (i < vals.length ? esc(vals[i]) : ''), '');
}
html`<p>${userInput}</p>`; // values escaped, literal parts trusted

// SQL: build a parameterized query instead of concatenating
function sql(strings, ...values) {
  return { text: strings.reduce((a, s, i) => a + '$' + i + s), values };
}
sql`SELECT * FROM users WHERE id = ${id} AND org = ${org}`;
// { text: 'SELECT * FROM users WHERE id = $1 AND org = $2', values: [id, org] }
```

Libraries such as `postgres`, `slonik`, `lit-html` and `styled-components` use this pattern.

### JS14: Destructuring

```js
const { a, b: renamed, c = 5, d: { e } = {}, ...rest } = obj; // rename, default, nested, rest
const [x, , y = 0, ...tail] = arr;                              // skip, default, rest
[a, b] = [b, a];                                                 // swap
function f({ host = 'localhost', port = 80 } = {}) {}            // parameter destructuring
```

- **Defaults** apply only when the value is `undefined`, not when it is `null`.
- **Rest (`...`)** must come last.
  - In objects it collects the remaining own enumerable properties into a new object. This is a shallow copy, handy for omitting keys: `const { password, ...safe } = user`.
  - In arrays it collects the remaining elements into an array.
- **Array destructuring** uses the iterator protocol, so it works on any iterable (Map entries, Sets, strings).

### JS15: for...in vs for...of

- **`for...in`** iterates over **enumerable string keys**, including *inherited* ones from the prototype chain. Order is mostly defined, with integer keys first.
- **`for...of`** iterates over the **values** of an **iterable** (`Symbol.iterator`): arrays, strings, Map, Set, generators, NodeLists. Plain objects are not iterable.

**Avoid `for...in` on arrays because:**
- Keys come back as strings (`"0"`, `"1"`).
- It picks up inherited or added enumerable properties, such as polyfilled `Array.prototype` methods or `arr.foo = 1`.
- It skips holes.
- It is slower and signals the wrong intent.

**Better choices:**
- For arrays: `for...of`, `for (const [i, v] of arr.entries())`, or `forEach`.
- For objects: `for (const [k, v] of Object.entries(obj))`.

### JS16: Generics, constraints, conditional types, infer

```ts
// Generic: type parameter preserves relationships
function first<T>(arr: T[]): T | undefined { return arr[0]; }

// Constraint
function prop<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
function longest<T extends { length: number }>(a: T, b: T) { return a.length >= b.length ? a : b; }

// Conditional type (distributes over unions when T is a naked type parameter)
type NonNullable2<T> = T extends null | undefined ? never : T;
type ApiResult<T> = T extends Error ? { ok: false; error: T } : { ok: true; data: T };

// infer: capture a type inside a conditional
type Unwrap<T> = T extends Promise<infer U> ? Unwrap<U> : T;         // like Awaited
type ReturnOf<F> = F extends (...args: any[]) => infer R ? R : never;
type ElementOf<T> = T extends readonly (infer E)[] ? E : never;
type Route<S> = S extends `/${infer Head}/${infer Rest}` ? Head | Route<`/${Rest}`> : S extends `/${infer L}` ? L : never;
```

**Practical example:** an API client where `get<T>(url): Promise<T>` combined with `Unwrap<ReturnType<typeof get>>` gives callers typed data without writing the types twice.

### JS17: Module systems

**CommonJS (CJS):**
- Uses `require()` and `module.exports`.
- Loads synchronously at runtime, with dynamic specifiers allowed.
- Exports are a copied value of the `exports` object.
- Provides `__dirname`, `__filename` and `require.cache`.
- It is Node's original system.

**ES Modules (ESM):**
- Uses `import`/`export`, which are static and parsed before execution.
- Exports are live bindings.
- The graph is loaded asynchronously, and top-level `await` is supported.
- Strict mode by default. Browsers support it natively.
- Uses `import.meta.url`, `import.meta.dirname` and `import.meta.filename`. Dynamic loading goes through `import()`.

**How Node decides which system a file uses:**
- `.mjs` is always ESM. `.cjs` is always CJS.
- `.js` follows the nearest `package.json` `"type"`: `"module"` means ESM, while `"commonjs"` (or no field) means CJS.
- Recent Node versions also auto-detect ESM syntax in ambiguous files.

**Interop:**
- ESM can `import` CJS. You get `module.exports` as the default export, plus named exports detected by static analysis (cjs-module-lexer).
- CJS can load ESM through `await import()`.
- Since Node 22.12/20.19, `require(esm)` works for ESM graphs without top-level `await`.

**Package entry points:** `"exports"` in `package.json` defines entry points and conditional exports (`"import"`, `"require"`, `"types"`, `"default"`). This is how packages ship both formats.

**Hazards:**
- Dual-package hazard: two instances of the same module get loaded, one per format.
- ESM requires file extensions in relative imports.

### JS18: Structural typing, excess property checks, satisfies, variance

**Structural typing:**
- Compatibility is based on shape, not on declared names.
- Any value with at least the required members is assignable. A `Point3D` works where a `{x, y}` is expected.

**Excess property checks:**
- An extra strictness check that applies only when a **fresh object literal** is assigned directly to a typed target or passed as an argument.
- `const p: Point = { x: 1, y: 2, z: 3 }` is an error.
- Assigning through an intermediate variable skips the check, as do type assertions and targets with index signatures.
- Its purpose is catching typos in option objects.
- For unions it checks against the union as a whole, and discriminated unions check the matched member.

**`extends` vs `satisfies`:**
- `extends` declares relationships:
  - `interface A extends B` means inheritance.
  - `<T extends U>` is a generic constraint.
  - `T extends U ? :` is a conditional test.
- `expr satisfies Type` (TypeScript 4.9) checks that an expression conforms to `Type`, including excess property checks, **without changing its inferred type**:

```ts
const routes = { home: '/', user: '/u/:id' } satisfies Record<string, string>;
routes.home; // still known key, type string; typo'd keys error
// vs `const routes: Record<string,string>` which loses the specific keys
```

**Variance annotations (TypeScript 4.7):**
- `out T` means covariant: T appears only in output positions. `Producer<Dog>` is assignable to `Producer<Animal>`.
- `in T` means contravariant: T appears only in input positions. `Consumer<Animal>` is assignable to `Consumer<Dog>`.
- `in out T` means invariant.

```ts
interface Getter<out T> { get(): T }
interface Setter<in T> { set(v: T): void }
```

- Normally TypeScript infers variance by structural measurement, which can be expensive or imprecise for recursive types.
- Annotations document intent, speed up checking, and are verified against the actual usage.
- Caveat: method parameters are bivariant, unlike function-typed properties under `strictFunctionTypes`.

### JS19: Proxy and Reflect

- **`new Proxy(target, handler)`** intercepts fundamental operations through traps: `get`, `set`, `has`, `deleteProperty`, `apply` (function call), `construct` (`new`), `ownKeys`, `getOwnPropertyDescriptor`, `defineProperty`, `getPrototypeOf`, and others.
- **`Reflect`** provides the default behavior for each trap, with matching signatures.
  - Forwarding with `Reflect.get(t, k, receiver)` keeps getters and inheritance correct.
  - `Reflect.set` returns a boolean instead of throwing.
- **Invariants are enforced.** For example, a proxy cannot report a non-configurable property differently from the target.

```js
// Validation + logging
const validated = obj => new Proxy(obj, {
  get(t, k, r) { console.log(`get ${String(k)}`); return Reflect.get(t, k, r); },
  set(t, k, v, r) {
    if (k === 'age' && (!Number.isInteger(v) || v < 0)) throw new TypeError('bad age');
    return Reflect.set(t, k, v, r);
  },
});

// Function call interception (timing)
const timed = fn => new Proxy(fn, {
  apply(t, thisArg, args) { const s = performance.now();
    try { return Reflect.apply(t, thisArg, args); }
    finally { console.log(`${t.name}: ${performance.now() - s}ms`); } },
});

// Minimal reactivity (Vue 3 style)
function reactive(o, onChange) {
  return new Proxy(o, {
    get(t, k, r) { const v = Reflect.get(t, k, r); return typeof v === 'object' && v ? reactive(v, onChange) : v; },
    set(t, k, v, r) { const ok = Reflect.set(t, k, v, r); onChange(k, v); return ok; },
  });
}
```

**Caveats:**
- Proxies have overhead.
- `===` identity differs between the proxy and its target.
- Objects with internal slots (Map, Date, `#private` fields) break unless you bind their methods to the target.

### JS20: SharedArrayBuffer and Atomics

**Shared memory:**
- A `SharedArrayBuffer` posted to a Worker is **shared**, not copied. Both threads view the same memory through TypedArrays.
- An ordinary `ArrayBuffer` is copied, or transferred with its ownership moved.
- In browsers this requires cross-origin isolation (`COOP: same-origin` + `COEP: require-corp`), because of Spectre and high-resolution timers.

```js
// main
const sab = new SharedArrayBuffer(1024);
const ia = new Int32Array(sab);
worker.postMessage(sab);
// worker
onmessage = ({ data }) => { const ia = new Int32Array(data); Atomics.add(ia, 0, 1); Atomics.notify(ia, 0); };
```

**Ordering guarantees:**
- Plain reads and writes on shared memory are unordered and may tear or be reordered by the compiler or CPU.
  - A data race gives you an unspecified value, not undefined behavior as in C.
- `Atomics.*` operations (`load`, `store`, `add`, `sub`, `and`, `or`, `xor`, `exchange`, `compareExchange`) are indivisible and **sequentially consistent**.
- An atomic store followed by another thread's atomic load of the same location establishes happens-before. That makes non-atomic data written before the store visible after the load, which is the classic "publish flag" pattern.

**Wait and notify (a futex model):**
- `Atomics.wait(int32OrBigInt64Array, index, expectedValue, timeoutMs)` blocks only if `ia[index] === expected`.
  - It returns `"ok"`, `"not-equal"` or `"timed-out"`.
  - It is not allowed on the browser main thread.
- `Atomics.waitAsync` is the non-blocking, promise-based variant, and is usable on the main thread.
- `Atomics.notify(ia, index, count = Infinity)` wakes waiters on that index and returns the number woken.

A mutex built from `compareExchange` with `wait`/`notify` is the standard pattern:

```js
function lock(ia, i) { while (Atomics.compareExchange(ia, i, 0, 1) !== 0) Atomics.wait(ia, i, 1); }
function unlock(ia, i) { Atomics.store(ia, i, 0); Atomics.notify(ia, i, 1); }
```

## Bash

### B1: $@ vs $*

- **Unquoted `$@` and `$*`** behave the same: all positional parameters, each subjected to word splitting and globbing.
- **`"$@"`** expands to each parameter as a **separate word**, preserving spaces exactly. It is almost always what you want, for example when forwarding arguments: `exec cmd "$@"`.
- **`"$*"`** expands to **one word**, with the parameters joined by the first character of `IFS` (a space by default).

```bash
set -- "a b" c
printf '[%s]\n' "$@"   # [a b] [c]
printf '[%s]\n' "$*"   # [a b c]
printf '[%s]\n' $@     # [a] [b] [c]
```

### B2: set -euo pipefail

- **`-e` (errexit):** exit when a command fails with a non-zero status.
  - Failures are not caught inside `if`/`while` conditions, in commands joined by `&&`/`||` (except the last), or in commands negated with `!`.
  - It has surprising edge cases: it is disabled inside functions called from an `if`, and `local x=$(fail)` masks the failure.
- **`-u` (nounset):** referencing an unset variable is an error. Use `${var:-default}` for optional variables.
- **`-o pipefail`:** a pipeline's exit status becomes the status of the rightmost failing command, instead of only the last command's.
  - Without it, `false | true` succeeds.
  - Watch out for `SIGPIPE`: `cmd | head` can return 141.

Many scripts also add `IFS=$'\n\t'` and `shopt -s inherit_errexit` (bash 4.4+).

### B3: $(...) vs backticks; $((...)) vs expr

- **`$(cmd)` and `` `cmd` ``** both capture stdout, with trailing newlines stripped.
  - `$()` nests cleanly: `$(dirname $(readlink -f x))`.
  - Inside `$()` quoting and backslashes behave normally. Backticks need escaped inner backticks and treat `\` specially.
  - `$()` is POSIX, so prefer it.
- **`$((expr))`** is shell-builtin integer arithmetic. It is fast (no fork), variables do not need `$`, and it supports C operators (`**`, `<<`, ternary, `++`).
- **`expr`** is an external process. It is slow, awkward (`*` must be escaped: `expr 3 \* 4`), and legacy.
- Neither handles floating point. Use `bc` or `awk` for that.
- `(( ))` is the arithmetic command form, which yields an exit status: `if (( n > 5 ))`.

### B4: Process substitution

`<(cmd)` runs `cmd` asynchronously and substitutes a filename (`/dev/fd/63` or a FIFO) that reads its output. `>(cmd)` gives a filename that writes into `cmd`.

Use it when a command expects **file arguments** but you have command output, or to avoid temporary files and the subshell problem of pipes.

```bash
diff <(sort a.txt) <(sort b.txt)
diff <(ssh host1 cat /etc/hosts) <(ssh host2 cat /etc/hosts)
comm -13 <(sort old) <(sort new)
while read -r l; do n=$((n+1)); done < <(grep x f)   # n survives (no pipe subshell)
tee >(gzip > out.gz) >(sha256sum > out.sha) < data > /dev/null
```

It is bash, zsh and ksh only, not POSIX `sh`. The exit status of the substituted process is not directly checked; bash ≥4.4 exposes its PID via `$!`.

### B5: Safe file iteration

**Why `for f in $(ls)` is dangerous:**
- The output of `ls` is word-split on IFS (spaces, tabs, newlines).
- Each word is then glob-expanded, so a file named `*` expands to everything.
- `ls` may also mangle non-printable characters.
- Result: `my file.txt` becomes two iterations.

**Safe patterns:**

```bash
for f in ./*; do [ -e "$f" ] || continue; printf '%s\n' "$f"; done   # glob; quote "$f"
shopt -s nullglob globstar; for f in **/*.log; do ...; done

find . -type f -print0 | while IFS= read -r -d '' f; do ...; done
while IFS= read -r -d '' f; do ...; done < <(find . -name '*.txt' -print0)  # keeps vars
find . -name '*.tmp' -exec rm -- {} +
mapfile -d '' files < <(find . -print0)
```

- Always quote `"$f"`.
- Use `--` or a `./` prefix so names starting with `-` are not treated as options.
- `IFS= read -r` keeps leading whitespace and backslashes.

### B6: Here document vs here string

```bash
cat <<EOF          # heredoc: multi-line stdin; $vars and $(cmds) expanded
Hello $USER
EOF
cat <<'EOF'        # quoted delimiter: no expansion (literal)
$HOME stays literal
EOF
grep foo <<< "$var"   # here-string: single string (+ trailing newline) as stdin
read -r a b <<< "1 2"
```

- **`<<-EOF`** strips **leading tab characters** (not spaces) from the body lines and from the closing delimiter, so you can indent heredocs inside functions or blocks.
- Here-strings are a bash/zsh/ksh feature. Bash implements them with a temporary file or a pipe.

### B7: Redirection order

Redirections are processed **left to right**. `2>&1` means "make fd 2 a copy of whatever fd 1 points to **right now**."

- **`cmd > file 2>&1`:** fd1 goes to `file`, then fd2 is copied from fd1, so it also goes to `file`. **Both** end up in the file.
- **`cmd 2>&1 > file`:** fd2 is copied from fd1, which is still the **terminal**; then fd1 is moved to `file`. Stdout goes to the file and stderr goes to the terminal.
  - This ordering is useful for piping only stderr: `cmd 2>&1 >/dev/null | grep err`.
- **`cmd &> file`:** bash shorthand for `> file 2>&1`. It is not POSIX. The append form is `&>>`.

### B8: Lock with mkdir and cleanup

```bash
LOCKDIR=/var/lock/myjob.lock

acquire_lock() {
  if mkdir "$LOCKDIR" 2>/dev/null; then
    echo $$ > "$LOCKDIR/pid"
    trap 'release_lock' EXIT
    trap 'exit 130' INT        # EXIT trap still fires
    trap 'exit 143' TERM HUP
    return 0
  fi
  # Stale lock detection
  local pid; pid=$(cat "$LOCKDIR/pid" 2>/dev/null)
  if [[ -n $pid ]] && ! kill -0 "$pid" 2>/dev/null; then
    echo "Removing stale lock from PID $pid" >&2
    rm -rf -- "$LOCKDIR"
    acquire_lock; return   # retry once; mkdir arbitrates any race again
  fi
  echo "Locked by PID ${pid:-unknown}" >&2
  return 1
}

release_lock() {
  [[ $(cat "$LOCKDIR/pid" 2>/dev/null) == "$$" ]] && rm -rf -- "$LOCKDIR"
}

acquire_lock || exit 1
# ... work ...
```

**Why `mkdir`:**
- `mkdir` is **atomic**: the existence check and the creation happen in one syscall, and it either succeeds or fails with `EEXIST`.
- `[ -e lock ] || touch lock` is check-then-act, a TOCTOU race where two processes both pass the check.
- `touch` and `>` succeed even if the file already exists.
- `set -o noclobber; > lock` is also atomic on local filesystems, but `mkdir` is portable and atomic even on NFS.

**Signals and traps:**
- `SIGKILL` cannot be trapped, so stale-lock detection by PID is needed.
- The stale-lock recovery itself has a small race. Staleness checks based on `flock` are more robust.

**Alternative:** `flock` (util-linux). The kernel releases the lock automatically when the process dies:

```bash
exec 9>/var/lock/myjob.lock
flock -n 9 || { echo "already running"; exit 1; }
```

### B9: Quoting

- **Single quotes `'...'`:** fully literal. No expansion at all, and a single quote cannot appear inside.
- **Double quotes `"..."`:** expand `$var`, `$(cmd)`, `$((..))` and `` `..` ``. They prevent word splitting and globbing. `\` escapes only `$`, `` ` ``, `"`, `\` and newline.
- **No quotes:** expansion, then **word splitting** on IFS, then **globbing**.

```bash
v="a   *.txt"
echo '$v'   # $v
echo "$v"   # a   *.txt
echo $v     # a file1.txt file2.txt  (spaces collapsed, glob expanded)
```

`$'...'` is ANSI-C quoting and interprets escapes: `$'tab\there'`.

### B10: File tests; [ ] vs [[ ]]

**File tests:**
- `-e` exists; `-f` regular file; `-d` directory; `-L` symlink.
- `-r`, `-w`, `-x`: readable, writable, executable by the current user.
- `-s` non-empty; `f1 -nt f2` newer than.

```bash
if [[ -d $dir && -r $dir/config ]]; then ...; fi
```

**`[ ]`** is the POSIX `test` command (a builtin, with `/usr/bin/[` as the external version):
- Arguments are normal words, so you must quote variables: `[ -n "$x" ]`. Unquoted empty variables cause syntax errors.
- Combine conditions with `-a`/`-o`, or better `[ ] && [ ]`.
- `<` and `>` are redirections and must be escaped.

**`[[ ]]`** is a bash keyword:
- No word splitting or globbing on variables.
- Supports `&&`, `||` and `()` inside.
- Supports `<`/`>` string comparison.
- Supports `==` glob patterns (`[[ $f == *.log ]]`) and `=~` regex, with captures in `BASH_REMATCH`.
- Safer, but not portable to `sh`.

### B11: Special parameters

- **`$?`:** exit status of the last command.
  ```bash
  grep -q x f; rc=$?; (( rc == 0 )) && echo found
  ```
- **`$$`:** PID of the current shell. It does not change in subshells; use `$BASHPID` for that. Used for unique temp names (prefer `mktemp`) and for PID files.
- **`$!`:** PID of the most recent background job.
  ```bash
  server & pid=$!; ...; kill "$pid"; wait "$pid"
  ```
- **`$#`:** number of positional parameters.
  ```bash
  (( $# >= 1 )) || { echo "usage: $0 file" >&2; exit 2; }
  ```

### B12: Functions

```bash
greet() { local name=${1:?name required}; echo "Hello $name"; }
greet "Lars"
msg=$(greet "Lars")     # "return" data via stdout
```

**Syntax:**
- `foo() { ...; }` is POSIX and portable.
- `function foo { ...; }` is ksh/bash syntax. In bash they are equivalent. In ksh, the `function` form gives local scoping for traps and `typeset`.
- `function foo() {}` is also accepted by bash.

**Returning values:**
- `return N` sets the exit status only (0–255). Use it for success or failure.
- Echo data to stdout and capture it with `$(...)`. This runs in a subshell and strips trailing newlines.
- Use a nameref (bash 4.3+), which avoids the subshell:
  ```bash
  get() { local -n out=$1; out="value"; }; get res; echo "$res"
  ```
- A global variable also works, but is less clean.

**Scope:** variables are global unless declared `local`. Scoping is dynamic, so called functions can see the caller's locals.

### B13: PATH and command resolution

`PATH` is a colon-separated list of directories that are searched in order for external executables.

**Resolution order for a command name without a `/`:**
1. Aliases (interactive shells)
2. Keywords (`if`, `[[`)
3. Functions
4. Builtins
5. Hash table / `PATH` search

- A name containing `/` is executed directly.
- Bash caches `PATH` lookups; `hash -r` resets the cache.

**Builtins vs external commands:**
- Builtins run inside the shell process: `cd`, `read`, `export`, `echo`, `printf`, `test`.
- They are needed for anything that changes shell state, and they are faster because there is no fork/exec.
- External commands are separate executables started with fork+exec.

**Checking which one runs:**

```bash
type -a echo      # echo is a shell builtin / echo is /usr/bin/echo
type -t ls        # alias|keyword|function|builtin|file
command -v foo    # portable; path or name
which foo         # external tool, only searches PATH (can lie about builtins/aliases)
command ls        # bypass functions/aliases; builtin cd forces builtin
```

**Security:** never put `.` or writable directories early in `PATH`.

### B14: trap

```bash
cleanup() { rm -rf -- "$TMP"; }
trap cleanup EXIT                               # runs on any exit (normal, exit N, set -e)
trap 'echo "error on line $LINENO: $BASH_COMMAND" >&2' ERR
set -E                                           # ERR trap inherited by functions/subshells
trap 'echo interrupted; exit 130' INT
trap 'exit 143' TERM
trap - INT                                       # reset to default; trap '' INT = ignore
```

**Behavior:**
- **`EXIT`** is a pseudo-signal and the best single place for cleanup. When an INT or TERM handler calls `exit`, the EXIT trap then runs, so cleanup happens once.
- **`ERR`** fires when a command fails under the same rules as `set -e`, whether or not `-e` is set.
- **`ERR` and `set -E`:** without `set -E` (errtrace), functions and subshells do not inherit the ERR trap. (`set -T` is the separate option that makes functions inherit DEBUG and RETURN traps.)

**Execution order and timing:**
- Bash runs trap handlers **between commands**. If bash is waiting on a *foreground* child, the trap runs only after that child exits.
  - To handle signals promptly, run the work in the background and `wait`. The `wait` builtin returns immediately with a status >128 when a trapped signal arrives.
- When several signals arrive, pending traps run **sequentially**, one handler at a time; handlers are not interrupted by one another.
- Standard (non-realtime) signals do not queue. Multiple instances of the same signal can coalesce into one.
- `EXIT` runs last, after any signal handler that calls `exit`.
- If a handler does not call `exit`, the script continues where it was interrupted.

### B15: xargs vs command substitution; -0; -P

**Command substitution (`cmd $(find ...)`):**
- Builds a single command line in memory.
- Subject to word splitting and globbing.
- Can hit `ARG_MAX` ("Argument list too long").
- Waits for the whole list before starting.

**`xargs`:**
- Reads items from stdin and runs the command in **batches** that fit `ARG_MAX`.
- Streams: it starts before input ends.
- Supports parallelism.
- By default it splits on whitespace and interprets quotes and backslashes, which is dangerous.

**NUL-delimited handling:** NUL is the only byte that cannot appear in a path, so names with spaces or newlines survive intact.

```bash
find . -name '*.log' -print0 | xargs -0 -r gzip           # -r: don't run if empty (GNU)
find . -type f -print0 | xargs -0 -n 1 -P "$(nproc)" -I{} sh -c 'convert "$1" "${1%.*}.webp"' _ {}
```

**Useful options:**
- `-P N` runs up to N processes in parallel. Combine it with `-n` (items per call) or `-I{}`.
- `xargs` exits with **123** if any invocation failed (status 1–125), and with 124, 126, 127 or 255 for special cases.
- Output from parallel jobs can interleave.

**Alternatives:** `find -exec cmd {} +` gives batching without xargs. GNU `parallel` offers ordered output and better handling of job failures.

### B16: Indexed and associative arrays

```bash
# Indexed
arr=(one "two words" three)     # or declare -a arr
arr+=(four)                     # append
arr[10]=x                       # sparse allowed
echo "${arr[1]}" "${#arr[@]}"   # element, length
for v in "${arr[@]}"; do echo "$v"; done
for i in "${!arr[@]}"; do echo "$i=${arr[i]}"; done
echo "${arr[@]:1:2}"            # slice; unset 'arr[1]' removes element
mapfile -t lines < file

# Associative (bash 4+), MUST declare
declare -A cfg=([host]=localhost [port]=80)
cfg[user]=lars; cfg+=([tls]=on)
[[ -v cfg[host] ]] && echo "has host"     # bash 4.3+
for k in "${!cfg[@]}"; do echo "$k=${cfg[$k]}"; done
echo "${#cfg[@]}"
```

**Differences:**

| | Indexed | Associative |
|---|---|---|
| Keys | Integers; subscripts are evaluated arithmetically | Arbitrary strings |
| Declaration | Implicit | Requires `declare -A` (otherwise keys evaluate as arithmetic, to 0) |
| Order | Ordered by index | Iteration order unspecified |
| Slicing | Yes | No |
| Negative index | `${arr[-1]}` (bash 4.3+) | N/A |

**Limitations of both:** one dimension only, cannot be exported to child processes, and cannot be returned from functions except via namerefs. macOS ships bash 3.2, which has no associative arrays.

### B17: Subshell vs group command

- **`( cmds )`** runs in a **subshell**, a forked child process.
  - Changes to variables, `cd`, `set` options, traps and `umask` do not affect the parent.
  - `exit` leaves only the subshell. Its exit status is the last command's status.
- **`{ cmds; }`** runs in the **current shell**.
  - It needs spaces and a trailing `;` or newline.
  - Variable changes and `cd` persist, and `exit` exits the whole script.
  - It is used to group redirections: `{ echo a; echo b; } > out`.

**Why piping into `while` loses variables:** each part of a pipeline runs in its own subshell. Bash runs the last element in a subshell too, unlike ksh and zsh.

```bash
count=0
cat f | while read -r l; do ((count++)); done
echo $count   # 0

# Fixes:
while read -r l; do ((count++)); done < f
while read -r l; do ((count++)); done < <(cmd)
shopt -s lastpipe   # runs last pipeline element in current shell (only when job control off, i.e. scripts)
cmd | { while read -r l; do ((count++)); done; echo "$count"; }  # use value inside group
```

### B18: Signals and job control

| Signal | # | Default | Meaning |
|---|---|---|---|
| SIGINT | 2 | Terminate | Ctrl-C; sent to the foreground process group |
| SIGTERM | 15 | Terminate | Polite "please exit" (default for `kill`, systemd, Docker stop). Catchable |
| SIGHUP | 1 | Terminate | Terminal hung up. Daemons often treat it as "reload config" |
| SIGKILL | 9 | Kill | Cannot be caught, blocked or ignored. No cleanup happens |

**Job control (interactive shells):**
- `&`, `jobs`, `fg`, `bg`, Ctrl-Z (SIGTSTP), `disown`, and `nohup` (ignore SIGHUP).
- Each job gets its own process group.
- In scripts, job control is off (`set -m` turns it on). Background jobs started with `&` in a non-interactive shell ignore SIGINT and SIGQUIT.
- When an interactive shell exits, it sends SIGHUP to its jobs.

**Graceful shutdown with background workers:**

```bash
#!/usr/bin/env bash
set -uo pipefail
pids=()
shutdown() {
  echo "stopping..." >&2
  kill -TERM "${pids[@]}" 2>/dev/null
  # grace period, then force
  for _ in {1..10}; do
    local alive=0; for p in "${pids[@]}"; do kill -0 "$p" 2>/dev/null && alive=1; done
    (( alive )) || break; sleep 1
  done
  kill -KILL "${pids[@]}" 2>/dev/null
  wait
  exit 143
}
trap shutdown TERM INT HUP

worker 1 & pids+=($!)
worker 2 & pids+=($!)
wait      # interruptible: trap runs as soon as signal arrives
```

- Use `wait` rather than a foreground `sleep`, so the trap runs promptly.
- In containers, a bash PID 1 gets no default signal handling. Use `exec` for single processes, or `tini`.

### B19: Parallel log processing

```bash
#!/usr/bin/env bash
set -euo pipefail

LOG=${1:?usage: $0 logfile}
JOBS=${JOBS:-$(nproc)}
WORK=$(mktemp -d)
trap 'rm -rf -- "$WORK"' EXIT

process_chunk() {
  local chunk=$1 out="$1.out"
  # example: count HTTP status codes per chunk
  awk '{c[$9]++} END {for (k in c) print k, c[k]}' "$chunk" > "$out.tmp" \
    && mv "$out.tmp" "$out"          # atomic: only complete results count
}
export -f process_chunk

# Split by lines (never mid-line) into ~JOBS*4 chunks for load balancing
split -n "l/$((JOBS * 4))" -d -a 4 -- "$LOG" "$WORK/chunk."

# Run in parallel; xargs returns 123 if any job failed
if ! find "$WORK" -name 'chunk.*' ! -name '*.out*' -print0 \
     | xargs -0 -n 1 -P "$JOBS" bash -c 'process_chunk "$1"' _; then
  echo "one or more chunks failed" >&2
  exit 1
fi

# Verify all outputs exist, then merge (reduce step)
n_in=$(find "$WORK" -name 'chunk.????' | wc -l)
n_out=$(find "$WORK" -name '*.out' | wc -l)
(( n_in == n_out )) || { echo "missing results" >&2; exit 1; }

cat "$WORK"/*.out | awk '{s[$1]+=$2} END {for (k in s) print k, s[k]}' | sort -k2,2nr
```

**Performance trade-offs:**
- **Splitting cost:**
  - `split` rewrites the whole file to disk, which is expensive for I/O-bound work.
  - Alternatives: pass byte offsets per worker (`tail -c +N | head -c M`, aligned to newlines), or `parallel --pipepart`, which avoids copies.
- **Where parallelism pays off:**
  - Mainly for CPU-heavy processing (regex, parsing, compression).
  - For simple `grep` on a spinning disk, a single stream may be as fast.
- **Chunk count:**
  - More chunks than cores gives better load balancing.
  - Too many chunks means process-spawn overhead and many small files.
- **Merge requirements:**
  - The merge must be associative (counts, sums, sets).
  - Order-sensitive output needs ordered chunk names (`-d`) and an ordered merge.
- **Memory and I/O limits:**
  - Watch memory per worker and page-cache pressure.
  - Consider `LC_ALL=C` for faster `sort`/`grep`.
- **Compressed logs:** `split` needs plain input. Decompression itself is usually serial, unless you use `pigz`/`zstd -T0`.

**Error propagation:**
- `xargs` exits with 123 if any child exits with 1–125, and with 124 if a child exits 255, which also stops xargs.
- Write output atomically (`.tmp` + `mv`) so partial results are never merged, then verify the chunk and output counts.
- To collect per-job failures, have each job write a status file. Alternatively, use GNU `parallel --halt now,fail=1 --joblog`, which records exit codes and kills the siblings.
- `pipefail` together with checking xargs' exit status ensures that `find` failures also surface.

### B20: exec, file descriptors, coprocesses

**`exec cmd`:**
- Replaces the current shell process with `cmd`: same PID, and nothing after it runs.
- **Uses:**
  - Wrapper scripts and container entrypoints (`exec "$@"`), so the program is PID 1 and receives signals directly.
  - Saving memory.
- A normal command forks a child, waits for it, then continues.

**`exec` with only redirections** changes the **current shell's** file descriptors permanently:

```bash
exec 3> out.log          # open fd 3 for writing
echo "msg" >&3
exec 4< input.txt; read -r line <&4
exec 5<> /dev/tcp/example.com/80     # bash network redirection
exec 3>&-                # close fd 3 (4<&- for input)
exec > >(tee -a script.log) 2>&1     # log all subsequent output
exec {fd}> file; echo hi >&"$fd"; exec {fd}>&-   # auto-allocated fd (bash 4.1+)
exec 6>&1 >/dev/null; ...; exec 1>&6 6>&-        # save/restore stdout
```

**Coprocess (bash 4+):** starts an async process with two-way pipes to its stdin and stdout.

```bash
coproc BC { bc -l; }
echo "scale=5; 4*a(1)" >&"${BC[1]}"
read -r pi <&"${BC[0]}"
echo "$pi"        # 3.14156
exec {BC[1]}>&-   # close its stdin -> it exits
wait "$BC_PID"
```

- `NAME[0]` reads from the coprocess's stdout, `NAME[1]` writes to its stdin, and `NAME_PID` holds its PID.

**When to use a coprocess:**
- You need an interactive dialogue with a long-running helper, such as `bc`, a DB CLI, `ssh`, or a line-oriented protocol server.
- It avoids spawning a new process per request.

**Caveats:**
- Deadlocks from buffering: use `stdbuf -oL` or line-buffered programs, and read exactly as much as you expect.
- Only one active coproc is well supported.
- Named FIFOs (`mkfifo`) are the portable alternative.

## PowerShell

### PS1: Write-Output vs Write-Host

- **`Write-Output`** writes objects to the **success output stream (1)**, which is the pipeline.
  - The objects can be captured (`$x = ...`), piped, redirected, or returned from functions.
  - Implicit output, meaning a bare expression like `"text"`, is the same thing.
- **`Write-Host`** writes directly to the host UI as formatted text, with options such as `-ForegroundColor`.
  - Since PowerShell 5 it goes to the **Information stream (6)**, so it can be captured with `6>` or `-InformationVariable`.
  - It is **not** in the pipeline.

**Why it matters in pipelines:**
- A function that uses `Write-Output` for status messages pollutes its return value. Callers get the messages mixed in with the data.
- Anything emitted with `Write-Host` cannot be piped to the next command.

**Rule of thumb:**
- Data goes to output.
- User-facing messages go to `Write-Verbose`, `Write-Information`, `Write-Warning`, or `Write-Host` for pure UI.

### PS2: Pipeline; ForEach-Object vs foreach

**The pipeline** passes **.NET objects**, not text, one at a time as they are produced (streaming). Parameter binding happens `ByValue` (by type) or `ByPropertyName`.

- **`ForEach-Object`** (aliases `%`, `foreach` in pipeline position) is a cmdlet.
  - It processes items **as they stream**, with low memory use.
  - It supports `-Begin`/`-Process`/`-End`, and `-Parallel` in v7.
  - Its per-item scriptblock invocation adds overhead.
- **The `foreach ($x in $coll)` statement** is a language keyword.
  - It needs the **whole collection in memory** first.
  - It is much faster, often 5–10×.
  - It supports `break` and `continue` normally. In `ForEach-Object`, `break` exits the enclosing loop or script, which is surprising.
  - Its output cannot be piped directly; wrap it in `$(...)` or assign it.

**When to use which:**
- `ForEach-Object` for large or streaming data, such as `Get-Content` of big files or `Get-ChildItem -Recurse`, and for one-liners.
- `foreach` for in-memory collections in scripts where speed matters.
- There is also the `.ForEach({})` method on collections.

### PS3: [PSCustomObject] vs [hashtable]

- **`[hashtable]`:**
  - A key/value dictionary.
  - Keys are unordered unless you use `[ordered]`, and case-insensitive.
  - Fast lookup: `$h['k']` or `$h.k`.
  - Mutable, and keys can be of any type.
  - Its properties are not enumerated in the pipeline: `Format-Table` shows Name/Value rows.
  - `Export-Csv` does not export its keys as columns.
- **`[PSCustomObject]`:**
  - A real object with NoteProperties and a fixed property order (the declaration order).
  - Formats as a table with one column per property.
  - Works properly with `Select-Object`, `Sort-Object`, `Export-Csv`, `ConvertTo-Json`, and pipeline binding by property name.
  - Can have methods added (`Add-Member ScriptMethod`) and a custom type name (`PSTypeName`).

**When to use which:**
- Hashtables for lookups, caches, splatting and configuration.
- PSCustomObjects for **output records** emitted by functions.

**Conversion:**

```powershell
$h   = [ordered]@{ Name = 'srv1'; CPU = 4 }
$obj = [PSCustomObject]$h                       # hashtable -> object (literal cast)
$h2  = @{}; $obj.PSObject.Properties | ForEach-Object { $h2[$_.Name] = $_.Value }  # object -> hashtable
$h3  = $json | ConvertFrom-Json -AsHashtable    # PS 7
```

### PS4: Error handling

**Non-terminating errors** (for example one bad path in `Get-Item a,b,c`):
- Written to the error stream and to `$Error`.
- Execution continues.
- **`try/catch` does NOT catch them** by default.

**Terminating errors** come from `throw`, from .NET exceptions, from `$PSCmdlet.ThrowTerminatingError()`, and from parse errors:
- They stop the statement or pipeline.
- They are caught by `try/catch` (or `trap`).

**How the controls interact:**
- `$ErrorActionPreference` is the scope-wide default: `Continue` (default), `Stop`, `SilentlyContinue`, `Ignore`, `Inquire`.
- `-ErrorAction` is a per-call common parameter that overrides the preference for that cmdlet.
- `-ErrorAction Stop`, or `$ErrorActionPreference = 'Stop'`, **promotes non-terminating errors to terminating** so that `try/catch` works.

```powershell
try {
    Get-Item C:\nope -ErrorAction Stop
} catch [System.Management.Automation.ItemNotFoundException] {
    Write-Warning "Missing: $($_.TargetObject)"
} catch {
    Write-Error $_; throw
} finally { <# cleanup #> }
```

**Details:**
- `$_` in a `catch` block is the `ErrorRecord`. `$_.Exception` holds the .NET exception.
- `-ErrorVariable ev` collects errors. `$?` reports whether the last command succeeded.
- `-ErrorAction` does not affect errors thrown by `throw` or .NET methods. Those are always terminating.
- Native executables do not throw. Check `$LASTEXITCODE`, or in PS 7.4+ set `$PSNativeCommandUseErrorActionPreference = $true`.
- In advanced functions, prefer `Write-Error` for non-terminating errors and `$PSCmdlet.ThrowTerminatingError()` for terminating ones.

### PS5: Splatting

Splatting passes a hashtable (named parameters) or an array (positional parameters) as parameters by using `@` instead of `$`.

```powershell
$params = @{
    Path        = 'C:\logs'
    Filter      = '*.log'
    Recurse     = $true
    ErrorAction = 'SilentlyContinue'
}
Get-ChildItem @params
Get-ChildItem @params -File           # combine with explicit params

$args2 = 'C:\src', 'C:\dst'; Copy-Item @args2   # array splat = positional
function Wrapper { param($Path) Inner @PSBoundParameters }  # forward params
```

**Difference from `$params`:** `Get-ChildItem $params` passes **one argument**, the hashtable object itself, which gets bound positionally to the first parameter (`-Path`) and fails or behaves oddly. `@params` expands each key into `-Key Value`.

**Benefits:** readability, conditional parameters (`if ($x) { $params.Credential = $cred }`), and reuse.

### PS6: Remoting

- **`Invoke-Command -ComputerName a,b,c -ScriptBlock {...}`:**
  - Runs a scriptblock non-interactively, **fanning out in parallel** (`-ThrottleLimit` defaults to 32).
  - Returns **deserialized** objects, tagged with a `PSComputerName` property.
  - Suited to automation. It can use persistent sessions via `-Session` (`New-PSSession`), and `-AsJob`.
- **`Enter-PSSession`:**
  - An **interactive** 1:1 remote prompt (`[server]: PS>`), like SSH.
  - For humans, not scripts.

**Protocols:**
- **WinRM / WS-Management:**
  - Windows' default, over HTTP 5985 or HTTPS 5986.
  - Messages are SOAP carrying PSRP (the PowerShell Remoting Protocol).
  - Authentication is Kerberos (domain), NTLM, CredSSP or certificates. The traffic is encrypted even over HTTP with Kerberos/NTLM.
  - Set up with `Enable-PSRemoting`. Outside a domain, `TrustedHosts` or HTTPS is required.
  - Endpoints are session configurations, such as JEA endpoints.
- **SSH (PowerShell 6+):**
  - PSRP is tunneled over SSH using the `powershell` subsystem.
  - Use `-HostName`/`-UserName`/`-KeyFilePath` (or `-SSHTransport`).
  - Cross-platform (Linux and macOS) with key-based authentication, and no WinRM configuration needed.
- **Both** carry the same PSRP protocol and serialization. Only the transport differs.

### PS7: Pipeline unrolling of returns

```powershell
$x = Get-Items
$x.GetType().Name   # String   (not Object[])
```

**Why:**
- `return $result` does not return "the array". It writes `$result` to the output stream, and **the pipeline enumerates collections**, so each element is emitted individually.
- The caller captures what was emitted.
  - One item gives the scalar itself (`String`).
  - Two or more items are re-collected into a new `Object[]`, which loses the original type, such as `List[T]` or `string[]`.
- **Zero items:** nothing is emitted, so `$x` is `$null`. It is actually `AutomationNull.Value`, which behaves as `$null` and piped into anything yields nothing.
  - Consequences: `$x.Count` works in PS3+ (returns 0/1 via intrinsic members), but `$x[0]` on `$null` errors, and `$x.GetType()` throws.

**Correct patterns:**

```powershell
# Callee: prevent enumeration
return ,$result                         # unary comma wraps in 1-element array; pipeline unwraps outer
Write-Output -NoEnumerate $result

# Caller: always force array (usually preferred - robust to any callee)
$x = @(Get-Items)                       # 0 -> empty array, 1 -> array of 1
[string[]]$x = Get-Items

# Also: avoid $arr += in loops (copies array each time: O(n^2))
$list = [System.Collections.Generic.List[string]]::new(); $list.Add('one')
# or just emit items and let the pipeline collect:
$x = foreach ($i in 1..3) { "item$i" }
```

### PS8: Scriptblocks vs functions; remote scriptblocks; double hop

**Scriptblock vs function:**
- A `[scriptblock]` (`{ ... }`) is an anonymous, first-class chunk of code. It can be stored in a variable, passed as a parameter, and invoked with `&` (child scope) or `.` (current scope). It can have `param()` and `begin`/`process`/`end` blocks.
- A **function** is a named scriptblock registered in the `Function:` drive. It is discoverable, supports `CmdletBinding`, help and aliases, and is callable by name.
- **Closures:** scriptblocks are *dynamically scoped* by default. They capture variables only via `.GetNewClosure()`.

**Passing a scriptblock to a remote session:**
- The scriptblock is **sent as text** and recreated remotely. Local variables and functions do not exist there.

```powershell
$svc = 'Spooler'
Invoke-Command -ComputerName srv1 -ScriptBlock { param($name) Get-Service $name } -ArgumentList $svc
Invoke-Command -ComputerName srv1 -ScriptBlock { Get-Service $using:svc }
# Ship a local function:
Invoke-Command -ComputerName srv1 -ScriptBlock ${function:Get-Thing} -ArgumentList 42
Invoke-Command -Session $s -ScriptBlock { param($def) . ([scriptblock]::Create($def)) } -ArgumentList ${function:Helper}.Ast.Extent.Text
```

**The double-hop problem:**
- You connect A → B with Kerberos or NTLM.
- B gets a network logon token without delegable credentials.
- When B then accesses C (a file share, SQL, or another `Invoke-Command`), authentication fails ("Access denied", anonymous).

**Solutions:**

1. **Explicit credentials to the second hop, via `-ArgumentList` or `$using:`.** This is simple and scoped.
   ```powershell
   $cred = Get-Credential
   Invoke-Command -ComputerName B -ScriptBlock {
       param($c) Get-ChildItem \\C\share -Credential $c   # or New-PSDrive -Credential, Invoke-Command -ComputerName C -Credential $c
   } -ArgumentList $cred
   ```
   The `PSCredential` is serialized with DPAPI/session encryption for the transfer.

2. **CredSSP.** Credentials are delegated fully to B.
   ```powershell
   Enable-WSManCredSSP -Role Client -DelegateComputer B   # on A
   Enable-WSManCredSSP -Role Server                       # on B
   Invoke-Command -ComputerName B -Authentication CredSSP -Credential $cred -ScriptBlock { dir \\C\share }
   ```
   **Security risk:** your plaintext-equivalent credentials are cached on B, so a compromised B exposes them. Microsoft discourages it.

3. **Resource-based Kerberos constrained delegation (preferred in domains):**
   ```powershell
   Set-ADComputer C -PrincipalsAllowedToDelegateToAccount (Get-ADComputer B)
   ```
   No credentials are stored. It does not work for WinRM → WinRM hops without extra configuration.

4. **Other options:**
   - JEA endpoints with a RunAs or gMSA virtual account.
   - A `RunAsCredential` on a session configuration.
   - SSH remoting with key-based authentication on each hop.

### PS9: @() vs [array]; indexing $null

- **`@(...)`** is the *array subexpression operator*. It evaluates its contents and **always** returns an `Object[]`:
  - `@(nothing)` gives an empty array.
  - `@(1)` gives a 1-element array.
  - An existing array is not nested; it is re-collected into a new `Object[]`.
- **`[array]`** is a *cast* (to `System.Array`).
  - It wraps a scalar into an array and passes existing arrays through (keeping `string[]` and similar).
  - `[array]$null` is still `$null`, **not** an empty array.
- **Forcing an array:**
  - `$r = @(Get-Thing)` works even for zero results.
  - Type-constrain the variable: `[object[]]$r = Get-Thing`.
- **Indexing:**
  - `$null[0]` gives the error "Cannot index into a null array."
  - `@()[0]` quietly returns `$null` (out-of-range is silent), unless you use `Set-StrictMode -Version 3+`, which makes it throw.
  - `$null.Count` is 0 (PS3+ intrinsic), and `@().Count` is 0.
  - Negative indexes work: `$a[-1]` is the last element.

### PS10: Comparison operators

**Operators:**
- `-eq`/`-ne`/`-gt`/`-lt`/`-ge`/`-le`: equality and ordering. The right side is **converted to the left side's type**, so `'10' -eq 10` compares as strings, while `10 -eq '10'` compares as numbers.
- `-like`/`-notlike`: wildcard matching (`*`, `?`, `[a-z]`), for example `$n -like 'srv*'`.
- `-match`/`-notmatch`: regex matching. With a scalar on the left, it sets the automatic `$Matches` hashtable (`$Matches[0]`, named groups).
- `-contains`/`-notcontains`: **collection -contains item**. It tests exact membership (with `-eq` semantics), not substrings. `'abc' -contains 'a'` is `$false`.
- `-in`/`-notin` (PS3+): **item -in collection**. The operands are swapped, which reads better in `Where-Object`: `Where-Object Status -in 'Running','Starting'`.

**Case sensitivity:**
- The defaults are **case-insensitive** (effectively the `-i*` variants).
- The `c`-prefixed forms are case-sensitive: `-ceq`, `-clike`, `-cmatch`, `-ccontains`, `-cin`, and so on.
- `-i` forms such as `-ieq` make case-insensitivity explicit.

**With an array on the left side**, the comparison operators **filter**:
- `1,2,3,2 -eq 2` returns `2,2`.
- `if ($arr -eq $null)` is therefore a bug. Write `$null -eq $arr`, with `$null` on the left, which is also a PSScriptAnalyzer rule.

### PS11: Modules

A **module** is a reusable, versioned package of commands (functions and cmdlets), variables, aliases and types, with its own scope. Only exported members are visible.

**Types:**
- **Script module (`.psm1`):** PowerShell code. It exports functions via `Export-ModuleMember`, or through the manifest.
- **Manifest (`.psd1`):** a data hashtable describing the module. It is not a module "type" by itself; it describes one:
  - `ModuleVersion`, `GUID`, `Author`
  - `RootModule`, `NestedModules`, `RequiredModules`
  - `FunctionsToExport` (list them explicitly for fast auto-loading, not `*`)
  - `CompatiblePSEditions`, `PowerShellVersion`, `PrivateData` (PSGallery tags)
  - Created with `New-ModuleManifest`.
- **Binary module (`.dll`):** compiled C# cmdlets, deriving from `PSCmdlet`. It gives better performance and is loaded into the AppDomain, where it cannot be unloaded.
- **Dynamic modules** (`New-Module`) exist only in memory.

**How `Import-Module` works:**
- It resolves the name via `$env:PSModulePath` (user, then system, then `$PSHOME\Modules`), using the folder `Name\<version>\Name.psd1`.
- It loads the manifest, processes `RequiredModules`, `NestedModules`, `TypesToProcess` and `FormatsToProcess`, then imports the `RootModule` into a module scope.
- Exported commands are added to the caller's session state.
- **Autoloading** (PS3+) imports modules automatically the first time one of their commands is used.
- Useful options: `-Force` (reload, but not binary modules or classes), `-RequiredVersion`, `-Prefix`, and `using module` (needed to import PowerShell classes).
- Modules are installed with `Install-PSResource` (PSResourceGet) or `Install-Module`.

### PS12: String interpolation

- **`"..."`** (expandable): variables are expanded.
  - Simple variables expand directly: `"$name"`.
  - Property access and expressions need the subexpression operator `$()`: `"Name: $($user.Name), sum: $(1+2), date: $(Get-Date -f yyyy)"`. Without it, `"$user.Name"` expands `$user` followed by the literal `.Name`.
  - `${var}` delimits names: `"${env:ProgramFiles}"`, `"${prefix}_x"`.
  - The escape character is the backtick: `` `n ``, `` `t ``, `` `$ ``, `` `" ``.
  - A quote can be doubled to escape it: `""`.
- **`'...'`** (literal): no expansion. Double a single quote to include one: `'it''s'`.

**Here-strings:**

```powershell
$html = @"
<h1>$($site.Title)</h1>
Generated $(Get-Date)
"@            # closing "@ must be at line start (col 0) in Windows PS; PS7.x allows no indentation either
$raw = @'
No $expansion here
'@
```

**Alternatives:**
- The `-f` format operator: `'{0} has {1:N2} GB' -f $name, $size`.
- `[string]::Format`.
- `$ExecutionContext.InvokeCommand.ExpandString()` for deferred expansion.

### PS13: Get-Member, members, Select vs Where

- **`Get-Member` (`gm`)** shows the .NET type (`TypeName`) and members of the objects piped to it. It reports distinct types once each:
  ```powershell
  Get-Process | Get-Member -MemberType Property
  ```
  - `gm -Static` shows static members.
  - `-Force` shows hidden and intrinsic members.
  - `$obj.PSObject.Properties` gives programmatic access.
  - `Get-Member -InputObject $arr` inspects the array itself rather than its elements.

**Member types:**
- **Property:** a real .NET property of the underlying type (`Process.Id`).
- **Method:** a .NET method (`$p.Kill()`). `gm` shows its signature.
- **NoteProperty:** a static value attached by PowerShell's extended type system (ETS). Found on PSCustomObjects, `Import-Csv` rows, and `Add-Member` additions.
- **Also:**
  - AliasProperty (`Process.Name` → `ProcessName`)
  - ScriptProperty (computed, for example `Process.CPU`)
  - CodeProperty
  - PropertySet (for example `PSConfiguration`)
  - ScriptMethod

**`Select-Object` vs `Where-Object`:**
- **`Select-Object`** chooses **properties** (columns) or a subset of **items by position**.
  - `-Property`, calculated properties (`@{n='MB'; e={$_.WS/1MB}}`), `-ExpandProperty`.
  - `-First`/`-Last`/`-Skip`/`-Unique`.
  - It creates new `Selected.*` PSCustomObjects.
- **`Where-Object`** filters **items** (rows) by a condition: `Where-Object { $_.CPU -gt 100 }` or `Where-Object CPU -gt 100`.
  - It returns the original objects unchanged.
  - Filter left: use the cmdlet's own `-Filter` when possible.

### PS14: PowerShell classes

Classes were introduced in v5 with the `class` and `enum` keywords.

```powershell
class Server {
    [string]$Name
    hidden [int]$Port = 443
    static [int]$Count = 0
    Server([string]$name) { $this.Name = $name; [Server]::Count++ }
    [string] Url() { return "https://$($this.Name):$($this.Port)" }
}
class WebServer : Server, System.IComparable {
    WebServer([string]$n) : base($n) {}
    [int] CompareTo([object]$o) { return $this.Name.CompareTo($o.Name) }
}
```

**Differences from and limitations compared with C#:**
- **Visibility:** no `private`/`protected`/`internal`. Everything is public; `hidden` only hides a member from `gm` and tab completion.
- **Properties:** no property accessors (get/set). Workarounds are `Add-Member ScriptProperty` in the constructor, or validation attributes.
- **Constructors:** no chaining to another constructor of the *same* class (`: this()`). Only `: base()` is available; use a shared `hidden Init()` method instead.
- **Inheritance:**
  - Single inheritance.
  - You can implement existing .NET interfaces, but not **declare** new interfaces, abstract classes, or generic classes.
  - Methods can be overridden (everything is effectively virtual).
- **Output:** methods require explicit `return` and a declared return type. Implicit output is discarded, unlike in functions.
- **Variables:** class methods cannot use variables from the enclosing scope unless they are qualified with `$script:` or `$global:`.
- **Parse-time definition:**
  - Types are defined at **parse time**. Classes used in a script must be defined in it or imported via `using module`; `Import-Module` does not export them.
  - Types referenced in class signatures must already be loaded before the script is parsed (`using assembly`).
  - You **cannot redefine or reload** a class in the same session. Changes require a new session, which is painful during development.
- **Threads:** classes have runspace affinity issues across threads (methods run in the runspace where they were defined).
- **No namespaces**, no events or delegates declared inline, and no operator overloading.

**When to use a class vs a function:**
- **Classes:** structured data types with behavior and validation; DSC class-based resources; implementing .NET interfaces (`IComparable`, `IValidateSetValuesGenerator`, argument completers, transformation attributes); strongly typed internal models.
- **Functions:** the public interface of a module, since they have pipeline support, help, parameter sets and discoverability. Keep classes internal and expose functions.

### PS15: Advanced functions

**`[CmdletBinding()]`** makes a function behave like a compiled cmdlet:
- Common parameters: `-Verbose`, `-Debug`, `-ErrorAction`, `-WarningAction`, `-InformationAction`, `-ErrorVariable`, `-OutVariable`, `-OutBuffer`, `-PipelineVariable`.
- The `$PSCmdlet` object: `ShouldProcess`, `ThrowTerminatingError`, `WriteError`, `ParameterSetName`, `MyInvocation`.
- Strict parameter binding: unknown parameters raise errors, and `$args` is no longer populated.

**Key settings:**
- **`SupportsShouldProcess`** adds `-WhatIf` and `-Confirm`. Guard destructive actions with `if ($PSCmdlet.ShouldProcess(target, action))`. Pair it with `ConfirmImpact='High'` for prompts by default.
- **`DefaultParameterSetName`** chooses the parameter set when the supplied parameters are ambiguous. Parameters are assigned to sets with `[Parameter(ParameterSetName='ByName')]`.
- **`ValueFromPipeline`** binds whole pipeline objects to a parameter by type. **`ValueFromPipelineByPropertyName`** binds from a matching property name or alias.

**Blocks:**
- **`begin`** runs once before the first pipeline input. Pipeline parameters are not yet bound. Use it to set up connections and lists.
- **`process`** runs **once per pipeline item**, with `$InputObject`/`$_` bound to the current item. If there is no pipeline input, it runs once with the parameter values.
- **`end`** runs once after all input. Use it to aggregate and clean up. A function with no named blocks puts all its code in `end`.
- **`clean`** (PS 7.3+) always runs, even on Ctrl-C or errors, like `finally`.

```powershell
function Remove-OldLog {
    [CmdletBinding(SupportsShouldProcess, ConfirmImpact = 'Medium', DefaultParameterSetName = 'ByPath')]
    param(
        [Parameter(Mandatory, ValueFromPipeline, ValueFromPipelineByPropertyName, ParameterSetName = 'ByPath')]
        [Alias('FullName')][string[]]$Path,
        [ValidateRange(1, 3650)][int]$Days = 30
    )
    begin   { $cutoff = (Get-Date).AddDays(-$Days); $n = 0 }
    process {
        foreach ($p in $Path) {
            $f = Get-Item -LiteralPath $p
            if ($f.LastWriteTime -lt $cutoff -and $PSCmdlet.ShouldProcess($p, 'Delete')) {
                Remove-Item -LiteralPath $p; $n++
            }
        }
    }
    end     { Write-Verbose "Removed $n files" }
}
Get-ChildItem C:\logs *.log | Remove-OldLog -Days 7 -WhatIf
```

### PS16: Providers

**Providers** expose different data stores through a common filesystem-like model of **drives**, items, child items, properties and content. The same core cmdlets work everywhere: `Get-ChildItem`, `Get-Item`, `New-Item`, `Set-Item`, `Remove-Item`, `Get-ItemProperty`, `Get-Content`, `Test-Path`, `Set-Location`.

- List them with `Get-PSProvider` and `Get-PSDrive`.
- Built-in providers:
  - FileSystem, Registry (`HKLM:`, `HKCU:`), Certificate (`Cert:`), Environment (`Env:`)
  - Variable, Function, Alias
  - WSMan
- Modules add more, such as ActiveDirectory (`AD:`) and SqlServer.

```powershell
Get-ChildItem C:\Windows -Filter *.log                     # files
Get-ChildItem Env: | Where-Object Name -like 'PS*'         # env vars; $env:PATH shortcut
Get-ChildItem Cert:\LocalMachine\My | Where-Object NotAfter -lt (Get-Date).AddDays(30)
Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert        # dynamic parameter from provider

# Registry as a file system: keys = items/containers, values = item *properties*
Set-Location HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion
Get-ChildItem                                               # subkeys
Get-ItemProperty . -Name ProgramFilesDir                    # value
Get-ItemPropertyValue 'HKLM:\SOFTWARE\...\CurrentVersion' ProductName
New-Item HKCU:\Software\Factus -Force
New-ItemProperty HKCU:\Software\Factus -Name Enabled -Value 1 -PropertyType DWord
Set-ItemProperty HKCU:\Software\Factus -Name Enabled -Value 0
Remove-Item HKCU:\Software\Factus -Recurse
New-PSDrive -Name HKCR -PSProvider Registry -Root HKEY_CLASSES_ROOT
Get-ChildItem Registry::HKEY_USERS                          # provider-qualified path
```

- Providers add **dynamic parameters**, such as `-File`/`-Directory` for FileSystem or `-ExpiringInDays` for certificates.
- Capabilities differ by provider. The Registry provider does not support `Get-Content`, and `-Filter` support varies.
- Use `-LiteralPath` to avoid wildcard interpretation of `[` and `]`.

### PS17: Runspaces and parallelism

**The building blocks:**
- **Runspace:** an execution environment with its own session state (variables, functions, modules) running on a thread. Each PowerShell host has at least one.
  - Runspaces are *not* thread-safe to share.
  - Objects passed between them are live references, so shared .NET objects need synchronization.
- **RunspacePool:** a pool of N runspaces reused for many invocations, which limits concurrency.
- **`[powershell]`:** a pipeline object you build (`AddScript`, `AddCommand`, `AddParameter`/`AddArgument`) and run synchronously (`Invoke()`) or asynchronously (`BeginInvoke()`/`EndInvoke()`), inside a runspace or pool.

**Manual pool:**

```powershell
$iss  = [initialsessionstate]::CreateDefault()
$pool = [runspacefactory]::CreateRunspacePool(1, 8, $iss, $Host); $pool.Open()
$results = [System.Collections.Concurrent.ConcurrentBag[object]]::new()
$jobs = foreach ($h in $hosts) {
    $ps = [powershell]::Create().AddScript({
        param($h, $bag) $bag.Add([pscustomobject]@{ Host = $h; Up = Test-Connection $h -Count 1 -Quiet })
    }).AddArgument($h).AddArgument($results)
    $ps.RunspacePool = $pool
    [pscustomobject]@{ PS = $ps; Handle = $ps.BeginInvoke() }
}
foreach ($j in $jobs) { $j.PS.EndInvoke($j.Handle); if ($j.PS.HadErrors) { $j.PS.Streams.Error }; $j.PS.Dispose() }
$pool.Close(); $pool.Dispose()
```

**`ForEach-Object -Parallel` (PS 7+):**

```powershell
$bag = [System.Collections.Concurrent.ConcurrentDictionary[string,bool]]::new()
$hosts | ForEach-Object -Parallel {
    $d = $using:bag
    $d[$_] = Test-Connection $_ -Count 1 -Quiet
} -ThrottleLimit 16      # default 5; -AsJob, -TimeoutSeconds available
```

**Comparing the two approaches:**
- **`-Parallel`:**
  - Simple, with pooled runspaces reused since 7.1.
  - Streams and errors are forwarded automatically.
  - Each iteration gets a fresh runspace context, so no local functions or variables are available except through `$using:`. Module imports happen per runspace.
  - Startup overhead per item. Good for I/O-bound batches.
- **Manual runspaces:**
  - More control: a shared `InitialSessionState` with preloaded modules, functions and variables.
  - Custom scheduling and lower overhead for many tiny tasks.
  - Works in Windows PowerShell 5.1.
  - More boilerplate. Wrappers: `Start-ThreadJob` (ThreadJob module), PoshRSJob.

**Thread safety:**
- Use `ConcurrentBag`/`ConcurrentDictionary`, `[hashtable]::Synchronized(@{})`, or `[System.Threading.Monitor]`/`lock`-style locking.
- Never do `$using:list.Add()` on a plain `List` or `ArrayList`, and never `+=` on a shared variable.
- Prefer returning output from each iteration and collecting it: `$r = $items | ForEach-Object -Parallel {...}`.

### PS18: PSScriptAnalyzer

PSScriptAnalyzer is a static code checker (linter) for PowerShell. It parses scripts into an AST and runs rules over them. It powers the diagnostics in the VS Code extension.

```powershell
Install-PSResource PSScriptAnalyzer
Invoke-ScriptAnalyzer -Path .\src -Recurse -Settings .\PSScriptAnalyzerSettings.psd1
Invoke-ScriptAnalyzer -Path x.ps1 -Fix                     # auto-fix where supported
Invoke-Formatter -ScriptDefinition $code -Settings CodeFormattingOTBS
```

**Rules:**
- Built-in examples:
  - `PSAvoidUsingCmdletAliases`, `PSAvoidUsingWriteHost`, `PSUseShouldProcessForStateChangingFunctions`
  - `PSAvoidUsingPlainTextForPassword`, `PSAvoidUsingConvertToSecureStringWithPlainText`, `PSAvoidUsingInvokeExpression`
  - `PSPossibleIncorrectComparisonWithNull`, `PSUseApprovedVerbs`, `PSUseDeclaredVarsMoreThanAssignments`
  - `PSUseCompatibleCommands`/`Syntax` (cross-version checks)
  - Formatting rules: `PSPlaceOpenBrace`, `PSUseConsistentIndentation`
- List them with `Get-ScriptAnalyzerRule`.

**Severity levels:**
- `Information`, `Warning`, `Error`, and `ParseError`.
- Filter with `-Severity`. The level indicates impact, and CI can gate on specific levels.

**Settings file (`.psd1`):**

```powershell
@{
  Severity = @('Error','Warning')
  ExcludeRules = @('PSAvoidUsingWriteHost')
  IncludeDefaultRules = $true
  CustomRulePath = @('.\build\rules\MyRules.psm1')
  Rules = @{ PSUseCompatibleSyntax = @{ Enable = $true; TargetVersions = @('5.1','7.4') }
             PSPlaceOpenBrace = @{ Enable = $true; OnSameLine = $true } }
}
```

**Custom rules:**
- Write a module with functions named `Measure-*`.
- Each takes a `[System.Management.Automation.Language.ScriptBlockAst]` (or `Token[]`) parameter and returns `[Microsoft.Windows.PowerShell.ScriptAnalyzer.Generic.DiagnosticRecord]` objects.
- You can also write them in C# against `IScriptRule`.
- Load them via `-CustomRulePath`.

**Suppression:**

```powershell
function Show-Banner {
    [Diagnostics.CodeAnalysis.SuppressMessageAttribute('PSAvoidUsingWriteHost', '', Justification = 'Interactive UI')]
    param() Write-Host 'Hi'
}
# Scope/Target params allow suppressing for Function scope or specific parameter; or ExcludeRules in settings.
```

**CI/CD integration:**
- Run it as a pipeline step and fail the build on findings:
  ```powershell
  $r = Invoke-ScriptAnalyzer -Path . -Recurse -Settings ./PSScriptAnalyzerSettings.psd1
  $r | Format-Table -AutoSize
  if ($r | Where-Object Severity -in 'Error','Warning') { throw "$($r.Count) analyzer findings" }
  ```
- Alternatives: wrap it in Pester tests (one test per rule/file, with NUnit/JUnit output for test reporting), or convert the results to SARIF for GitHub code scanning.
- Commit the settings file so editor and CI apply identical rules, and use it in pre-commit hooks.

### PS19: $using: vs -ArgumentList; serialization

**`-ArgumentList` / `$args` / `param()`:**
- Values are passed **positionally** to the scriptblock's `param()` block, or to `$args`.
- Available on `Invoke-Command`, `Start-Job`, `Start-ThreadJob`, and `[powershell].AddArgument`.
- **Not** available on `ForEach-Object -Parallel`, which binds `$_` from the pipeline.
- It is explicit and makes the scriptblock reusable and testable.

**`$using:var`:**
- Reads a variable from the **caller's** scope. The value is captured when the command starts.
- Works with `Invoke-Command` (remote, PS3+), `Start-Job`, `Start-ThreadJob`, `ForEach-Object -Parallel`, and DSC and workflow scripts.
- More readable than positional arguments.
- It is **read-only**: you cannot assign to `$using:x`.
- Expressions such as `$using:h['k']` or `$using:obj.Prop` are limited. Assign to a local variable first.
- Remotely it requires PS3+ on the target.

**Serialization by context:**

| Context | Mechanism | Effect |
|---|---|---|
| Remoting (`Invoke-Command -ComputerName`/`-Session`), `Start-Job` (a separate process) | Values are **serialized to CLIXML** both ways | Arguments in and results out |
| `ForEach-Object -Parallel`, `Start-ThreadJob`, runspaces | Same process | **Live references**, no serialization; thread-safety concerns apply |

- In ThreadJob and `-Parallel`, `$using:` of a scriptblock is disallowed or fails. Pass the scriptblock as a string and rebuild it with `[scriptblock]::Create()`.

**CLIXML serialization limits:**
- **Primitive and known types** round-trip with full fidelity: strings, numbers, DateTime, GUID, arrays, hashtables, `PSCredential`/`SecureString` (encrypted), enums as values.
- **Other types** become **deserialized property bags**:
  - The type name is prefixed `Deserialized.` (for example `Deserialized.System.Diagnostics.Process`).
  - **Methods are gone** (except `ToString`), and ScriptProperties are frozen to values.
  - It is a snapshot, not live.
- **Depth:**
  - Remoting and jobs serialize nested objects to a **default depth of 1**, unless the type specifies `SerializationDepth` in `types.ps1xml`.
  - Deeper nested objects are flattened to their `ToString()` string, so `$r.Parent.Child.Name` may be just a string.
  - `Export-Clixml` defaults to depth 2 (`-Depth` configurable). `ConvertTo-Json` also defaults to depth 2 and warns when it truncates (since 7.1).
- **Size:** remoting limits apply (`MaximumReceivedObjectSizeMB`, 200 MB by default in PS 7; `MaximumReceivedDataSizePerCommandMB`).
- **Workarounds:**
  - Select exactly the needed properties remotely and return `[pscustomobject]`s. This is also faster.
  - Do the work that needs methods **on the remote side**.
  - Serialize explicitly: `[System.Management.Automation.PSSerializer]::Serialize($obj, 5)` or `ConvertTo-Json -Depth 10`, then pass the string and deserialize on the other side.

### PS20: Desired State Configuration

**DSC** is Microsoft's declarative configuration-management platform. You describe the *desired* state, and the engine makes it so and keeps it that way (idempotent, with drift detection).

**Core pieces:**
- **Configuration:** a PowerShell `configuration` keyword block. Compiling it produces a **MOF** document per node, with `ConfigurationData` separating environment data from structure.
  ```powershell
  Configuration WebServer {
      Import-DscResource -ModuleName PSDesiredStateConfiguration
      Node 'web01' {
          WindowsFeature IIS { Name = 'Web-Server'; Ensure = 'Present' }
          File Site { DestinationPath = 'C:\inetpub\site\index.html'; Contents = 'hi'; DependsOn = '[WindowsFeature]IIS' }
      }
  }
  WebServer -OutputPath .\mof; Start-DscConfiguration .\mof -Wait -Verbose
  ```
- **Resources:** units implementing **`Get` / `Test` / `Set`**.
  - `Test` returns a bool (compliant or not). `Set` is called only if `Test` returns false.
  - Implemented as MOF schema + script module, as class-based resources (PS5+), or as composite resources.
  - Distributed as modules, for example `ComputerManagementDsc`, `SqlServerDsc`, `NetworkingDsc`.
- **Local Configuration Manager (LCM):** the engine on each Windows node. It is itself configured by a meta-configuration (`[DscLocalConfigurationManager()]`). It:
  - applies MOFs and handles `DependsOn` ordering and reboots,
  - supports **push** (`Start-DscConfiguration`) or **pull** (an HTTP/SMB pull server or Azure Automation State Configuration),
  - runs consistency checks on a schedule (`ConfigurationModeFrequencyMins`),
  - applies a `ConfigurationMode`: `ApplyOnly`, `ApplyAndMonitor`, or `ApplyAndAutoCorrect`,
  - reports compliance.

**Windows PowerShell vs PowerShell 7+:**

| | Version | Platform | LCM | How it runs |
|---|---|---|---|---|
| Windows PowerShell 5.1 | DSC 1.1 | Windows only | Built-in, runs as a WMI service | MOF documents, full push/pull via LCM |
| PowerShell 7 | PSDesiredStateConfiguration 2.x | Cross-platform | **None** | Resources invoked directly with `Invoke-DscResource`, or used by Azure Machine Configuration (Guest Configuration); class-based resources preferred |
| DSC v3 | Standalone (GA 2025) | Cross-platform | **None** | `dsc` CLI; resources in any language |

- **About DSC v3:**
  - The `dsc` CLI is written in Rust and does not depend on PowerShell.
  - Configuration documents are **JSON/YAML**, not MOF.
  - Resources can be written in any language via JSON manifests. PowerShell resources are supported through adapters, and WMI through another adapter.
  - It is designed to be called by other tools (Azure Machine Configuration, WinGet configuration, Ansible/Chef-style orchestrators) rather than to run a background agent.

**What replaced classic DSC in modern IaC:**
- **Azure Machine Configuration** (Azure Policy guest configuration) for Azure and Arc-enabled servers, the successor to Azure Automation State Configuration, which is being retired.
- **Configuration-management tools:** Ansible (very common for Windows as well, via WinRM or SSH), Chef, Puppet and Salt, some of which can wrap DSC resources.
- **Provisioning, images and policy:**
  - Terraform, OpenTofu, Bicep and ARM for infrastructure provisioning.
  - Immutable images built with Packer.
  - Intune or Group Policy for endpoint configuration.
  - WinGet configuration files (which use DSC v3) for developer machines.
- **Containers:** Kubernetes and GitOps (Flux, Argo CD) for declarative workload state.

The overall trend: immutable infrastructure plus cloud policy engines, with DSC v3 as a pluggable resource engine rather than a standalone agent-based platform.
