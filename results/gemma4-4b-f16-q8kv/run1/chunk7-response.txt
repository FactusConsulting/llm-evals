**JavaScript / TypeScript**

JS1 — `var` is function-scoped and hoisted (initialized to `undefined`). `let` and `const` are block-scoped and are hoisted but remain in the Temporal Dead Zone (TDZ) until declaration. Hoisting is JavaScript's behavior of moving declarations to the top of their scope during compilation, but only the declaration, not the assignment.
JS2 — The Event Loop is the mechanism that monitors the Call Stack and queues (Microtask/Macrotask) to ensure non-blocking I/O. The Call Stack executes synchronous code. When the stack is empty, the Event Loop checks the Microtask Queue (e.g., Promises, `queueMicrotask`) and drains it completely before checking the Macrotask Queue (e.g., `setTimeout`, I/O events).
JS3 — A closure is the ability of a function to remember and access variables from its lexical scope even after that outer scope has finished executing. Example: `function outer() { let count = 0; return function() { count++; return count; }; }`. The classic bug occurs in `for` loops where the inner function references the *same* final `i` value in the outer scope. Fix: Use `let` in the `for` loop declaration (`for (let i = 0; ...)`), as `let` creates a new binding for `i` in each iteration.
JS4 — A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. `async/await` is syntactic sugar built on Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()`. With `async/await`, errors are caught using standard `try...catch` blocks. `Promise.all` waits for *all* promises to resolve, failing immediately if *any* one rejects (fail-fast). `Promise.allSettled` waits for *all* promises to either resolve or reject, returning an array describing the outcome of each.
JS5 — An `interface` defines a structural contract—it describes *what* an object must look like at compile time. It is purely a design-time construct and is erased during compilation. A `type` alias can describe any shape, including primitives, unions, tuples, and intersections. Use `interface` for defining object shapes/contracts. Use `type` for complex unions, primitives, or utility types. Discriminated unions are unions of types that share a common, literal property (the "discriminant"), allowing TypeScript to narrow the type safely using a `switch` statement on that property.
JS6 — Prototypal inheritance means objects inherit properties and methods directly from other objects (their prototypes) rather than from classes. `Object.create(proto)` creates a new object whose internal `[[Prototype]]` link points directly to the provided `proto` object. ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance model; they provide a cleaner, more familiar syntax for defining constructor functions and prototype chains.
JS7 — `this` refers to the object that is currently executing the function. The 4 binding rules in priority order are: 1. **New Binding** (when using `new`). 2. **Explicit Binding** (using `.call()`, `.apply()`, or `.bind()`). 3. **Implicit Binding** (when a method is called on an object). 4. **Default Binding** (when called globally/outside any context, `this` defaults to the global object in non-strict mode). `bind()` returns a *new* function with the context permanently set; this new function can then be bound again or called normally.
JS8 — `WeakRef` provides a weak reference to an object, meaning the garbage collector (GC) is free to reclaim the object even if a `WeakRef` exists. `FinalizationRegistry` allows you to register a callback function that will be executed *after* the associated object has been garbage collected. They are used for non-blocking cleanup or metadata tracking without preventing GC. WeakMap keys must be objects because primitives (strings, numbers) are immutable; if they were used as keys, the map would only track the value, not the object identity, defeating the purpose of weak referencing based on object lifecycle.
JS9 — V8 optimizes JS by assuming code paths are stable. **Hidden Classes** (or Maps) allow V8 to represent objects with the same structure (same property order/names) using a single internal representation, speeding up property lookups. **Inline Caching** caches the result of property lookups for frequently accessed objects. **Deoptimization** occurs when V8's assumptions about an object's shape or type are violated (e.g., adding a new property to an object that V8 had optimized for). Coding patterns causing deoptimization include dynamic property addition/deletion, or frequent type switching on the same variable.
JS10 — Tree-shaking is the process of eliminating unused code from a final bundle. It works effectively with ES Modules because `import` and `export` are static syntax constructs that bundlers (like Webpack) can analyze before runtime to determine which exports are actually imported. CommonJS uses dynamic `require()` calls, which are resolved at runtime, making it impossible for static analysis tools to reliably determine which modules are truly unused.
JS11 — `null` represents the intentional absence of any object value. `undefined` means a variable has been declared but has not yet been assigned a value. `==` performs type coercion before comparison (e.g., `0 == false` is true). `===` performs strict comparison, checking both value and type without coercion. `??` (nullish coalescing) returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. `?.` (optional chaining) allows safe navigation through nested objects, returning `undefined` if any part of the chain is null or undefined, preventing runtime errors.
JS12 — `map()` creates a new array by applying a function to every element. `filter()` creates a new array containing only elements that pass a test (return `true`). `reduce()` executes a reducer function on each element, resulting in a single output value. With an initial value, `reduce` starts the accumulation process with that value. `flatMap()` first maps each element using a function, and then flattens the resulting array by one level, useful when mapping might return arrays itself (e.g., flattening nested results).
JS13 — Template literals use backticks (``) to allow embedded expressions (`${expression}`) and multi-line strings. Tagged templates allow a function to be called before the template literal is converted to a string. The function receives the string parts and the evaluated expressions as arguments. Example (SQL escaping): `const sql = escapeSql`${user.name}, ${user.id}`;` where `escapeSql` processes the inputs before concatenation.
JS14 — Destructuring is a syntax that allows unpacking values from arrays or properties from objects into distinct variables. Object destructuring: `const { name, age } = user;`. Array destructuring: `const [first, second] = arr;`. Default values: `const { age = 30 } = user;`. Renaming: `const { name: fullName } = user;`. The rest operator (`...`) collects the remaining properties (object rest) or elements (array rest) into a new array/object.
JS15 — `for...in` iterates over the *enumerable properties* (keys) of an object, including inherited ones. `for...of` iterates over the *values* of an iterable object (like Arrays, Maps, Sets). You should avoid `for...in` on arrays because it iterates over indices as strings and may include non-index properties added to the array object, leading to unpredictable iteration.
JS16 — Generics allow writing components that can work over a variety of types while maintaining type safety. **Generic Constraints** (`extends`) restrict the types that can be used with a generic parameter (e.g., `function identity<T extends { length: number }>(arg: T)`). **Conditional Types** (`T extends U ? X : Y`) perform type-level branching based on whether type `T` satisfies type `U`. **Infer** extracts a type from a complex type structure, often used in utility types (e.g., `type T = infer R`).
JS17 — The module system defines how code is organized and shared. CommonJS uses synchronous loading via `require()` and `module.exports` (runtime resolution). ES Modules use static `import`/`export` (static analysis). Node.js supports both; using `"type": "module"` in `package.json` forces `.js` files to be treated as ES Modules.
JS18 — TypeScript uses a structural type system: two types are compatible if they have the same structure (shape), regardless of their declared names. **Excess property checks** ensure that an object passed to a function does not contain properties that are *not* defined in the function's parameter type. They apply when strict checks are enabled. `extends` requires the implementing type to fulfill the contract. `satisfies` checks that the type conforms to the structure without requiring the type to *be* that structure (useful for narrowing types without changing the original type). Variance (`in`/`out`) defines how subtyping works for generic parameters: `in` (contravariant) means the type can accept a wider range of inputs; `out` (covariant) means the type can safely produce a wider range of outputs.
JS19 — A `Proxy` wraps a target object, allowing interception of fundamental operations (like `get`, `set`, `apply`). `Reflect` provides the standard, low-level API for these operations. You use a Proxy handler to define custom logic for these traps. Example: For validation, you can intercept a `set` operation (`set(target, prop, value)`) and throw an error if the `value` violates business rules before it reaches the target object.
JS20 — `SharedArrayBuffer` (SAB) is a block of memory that can be shared between multiple threads (Web Workers). `Atomics` provides methods to perform atomic operations (read, write, compare-and-swap) on the data within the SAB, ensuring that operations are indivisible and preventing race conditions. Workers communicate by reading/writing to this shared memory. `Atomics.wait()` pauses a thread until a specific value changes, and `Atomics.notify()` wakes up waiting threads.

**Bash**

B1 — `$@` expands to all positional parameters, with each parameter quoted separately (e.g., `"$1" "$2"`). This is the safest way to handle arguments containing spaces. `$*` expands to all positional parameters as a single string, separated by the first character of the `IFS` variable. `"$@"` vs `"$*"`: `"$@"` preserves argument boundaries; `"$*"` treats them as one block.
B2 — `set -e`: Exit immediately if a command exits with a non-zero status. `set -u`: Treat unset variables as an error and exit. `set -o pipefail`: Causes a pipeline to return a non-zero status if any command in the pipeline fails, not just the last one.
B3 — `$(command)`: Command substitution. The shell executes `command` and replaces the substitution with the command's standard output. `command`: Executes the command directly. `$((expression))`: Arithmetic evaluation performed by the shell. `expr`: An external utility used to evaluate mathematical expressions.
B4 — Process substitution (`<(command)`) allows the output of a command to be treated as a temporary file path that the shell can pass to another command. Example: `diff <(ls -t) <(ls -r)` compares the output of two separate `ls` commands as if they were two different files.
B5 — Use `find . -print0 | while IFS= read -r -d $'\0' f; do ... done`. This uses `find` to locate files and prints them separated by null characters (`\0`). The `while` loop reads these null-separated items safely, preventing word splitting and globbing issues associated with spaces or special characters. `for f in $(ls)` is dangerous because `$(ls)` outputs a space-separated string, causing word splitting to break filenames containing spaces.
B6 — A here document (`<<EOF`) allows multi-line input to be fed into a command until the delimiter (`EOF`) is encountered. A here string (`<<<`) passes a single line of input to standard input. `<<-EOF` is a variation of the here document where any leading tabs on subsequent lines are stripped before being passed to the command.
B7 — `cmd > file 2>&1`: Redirects standard output (1) to `file`. Then, it redirects standard error (2) to the same location as standard output (which is `file`). Result: Both stdout and stderr go to `file`. `cmd 2>&1 > file`: First, it redirects standard error (2) to standard output (1). Then, it redirects standard output (1) to `file`. Result: Both stdout and stderr go to `file`. The difference is the order of operations; the first command establishes the destination before redirecting stderr to it. `cmd &> file` is a shorthand for the first case.
B8 — Use `mkdir /tmp/lockdir` (atomic creation). If successful, the lock is held. Use `trap 'rmdir /tmp/lockdir' EXIT TERM INT` to ensure cleanup runs on normal exit or signal interruption. `mkdir` is preferred because the operation is atomic; it either succeeds completely or fails completely, preventing race conditions where one process checks for existence, and another creates the file before the first process can lock it.
B9 — Single quotes (`'...'`) treat everything literally; no expansion occurs. Double quotes (`"..."`) allow variable expansion (`$VAR`) and command substitution (`$(cmd)`). No quotes allow word splitting (splitting by IFS) and pathname expansion (globbing). Example: `echo 'hello $VAR'` (prints literal `$VAR`) vs `echo "hello $VAR"` (substitutes value) vs `echo hello world` (splits into two arguments).
B10 — File existence: `[ -f file ]` (regular file), `[ -d dir ]` (directory). Readability: `[ -r file ]`. `[ ]` is an alias for the `test` command, which uses POSIX syntax. `[[ ]]` is a Bash keyword that offers extended features, including regex matching (`=~`), and is generally safer and more powerful than `[ ]`.
B11 — `$?`: The exit status (0-255) of the most recently executed foreground command. Use case: Checking if a previous command succeeded. `$$`: The Process ID (PID) of the current shell. Use case: Logging the script's PID. `$!`: The PID of the most recently executed background job. Use case: Monitoring a background process. `$#`: The number of positional arguments passed to the script. Use case: Validating required inputs.
B12 — Functions are defined using `name() { ... }` or `function name { ... }`. They are functionally equivalent in modern Bash. Values are typically returned by printing them to standard output, which the caller captures using command substitution: `result=$(my_function)`.
B13 — The PATH environment variable is a colon-separated list of directories that the shell searches sequentially when a command is invoked. Bash resolves commands by checking if the command name matches a builtin first; if not, it searches the directories listed in PATH for an executable file. A builtin is part of the shell itself (e.g., `cd`, `echo`). An external command is a separate binary executable found in PATH. Use `type command` to determine if it's a builtin, alias, or external file.
B14 — `trap` allows you to specify commands to run when the shell receives a specific signal. `trap 'cleanup_script' EXIT` runs on normal script termination. `trap 'cleanup_script' ERR` runs if a command fails (if `set -e` is active). `trap 'cleanup_script' INT` handles Ctrl+C. `trap 'cleanup_script' TERM` handles termination signals. Execution order is generally sequential, but signals can interrupt execution at any point.
B15 — Command substitution (`$(cmd)`) runs the command and substitutes its output into the current command line. `xargs` takes standard input and builds and executes command lines from it. `xargs` is superior for large inputs because it batches arguments efficiently. To handle spaces/newlines safely: `find . -print0 | xargs -0 ...`. `-P N` specifies that `xargs` should run up to $N$ processes in parallel.
B16 — Standard arrays are indexed numerically (0, 1, 2...). Associative arrays (maps) use string keys. Declaration: `declare -A map_name`. Appending: `map_name[key]=value`. Iterating: `for key in "${!map_name[@]}"; do echo "$key"; done`. Length: `${#map_name[@]}`. Associative arrays are used when the key's meaning is more important than its numerical position.
B17 — A subshell `(...)` executes commands in a completely new, isolated process; any variables set or modified inside are lost when the subshell exits. A group command `{ ...; }` executes commands in the *current* shell context; variables persist. Piping into a `while` loop (`cmd | while read line; do ... done`) runs the loop in a subshell, meaning any variables modified inside the loop are lost when the loop finishes, as the subshell exits.
B18 — SIGINT (Interrupt, Ctrl+C): Asks the process to stop gracefully. SIGTERM (Terminate): A standard request for graceful shutdown. SIGHUP (Hangup): Often used by daemons to signal a configuration reload. SIGKILL (Kill): The kernel forces immediate termination; it cannot be caught or ignored. Graceful shutdown requires trapping SIGTERM/SIGINT and explicitly killing or waiting for background jobs (`kill %123`).
B19 — Use `find /path/to/logs -type f -print0 | xargs -0 -P 4 -I {} bash -c 'process_log "$@"' _ {}`. The `-P 4` runs 4 jobs in parallel. Error propagation is difficult; the script must check the exit code of the wrapper function (`process_log`) or use a shared status file/queue to aggregate failures from the parallel jobs.
B20 — `exec command` replaces the current shell process entirely with the new command; it does not return. It's used for resource management, like redirecting file descriptors: `exec 3>log.txt` opens file descriptor 3 to `log.txt`. `exec 3>&-` closes descriptor 3. A coprocess allows the shell to manage two related, communicating processes (parent/child) via pipes, useful for complex, long-running parallel tasks where you need the shell to manage the communication channels explicitly.

**PowerShell**

PS1 — `Write-Output` sends objects down the pipeline, allowing subsequent cmdlets to process them. `Write-Host` writes directly to the console buffer, bypassing the pipeline entirely. This distinction is crucial because pipeline processing relies on objects being passed, whereas `Write-Host` is purely for visual display.
PS2 — The pipeline passes objects sequentially from one cmdlet to the next. `ForEach-Object` (or `%`) is the cmdlet that *consumes* the input objects from the pipeline and executes a script block on each one. The `foreach` statement is a loop structure used to iterate over a collection (like an array or list) that is already loaded into memory.
PS3 — A `Hashtable` is a dictionary structure mapping string keys to values. A `PSCustomObject` is a structured object with named properties, behaving like a lightweight class instance. Use `PSCustomObject` when you need structured, predictable output that flows well through the pipeline. Use `Hashtable` when you need dynamic key/value storage, often for parameter passing (splatting). Conversion: `[PSCustomObject]@{...}` or `[hashtable]@{...}`.
PS4 — Terminating errors halt the current operation or script flow. Non-terminating errors are logged but execution continues. `-ErrorAction` dictates the response to an error (e.g., `Stop` terminates, `Continue` ignores). `$ErrorActionPreference` sets the default behavior for the session. `try/catch` is used specifically to trap and handle terminating errors.
PS5 — Splatting (`@params`) is the practice of passing a hashtable to a cmdlet where the hashtable keys match the cmdlet's parameter names and values match the desired parameter values. Example: `Get-Service @params` where `@params = @{Name="Spooler"; Status="Running"}`. It differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named parameters.
PS6 — `Invoke-Command -ComputerName` executes a script block on a remote machine, returning the results to the local session. `Enter-PSSession` establishes an interactive, persistent session on the remote machine, allowing you to run commands as if you were logged in. Both primarily use WinRM (Windows Remote Management) over HTTP/HTTPS.
PS7 — The function returns an array (`$result`), but because it is not explicitly typed, PowerShell treats the return value as a generic collection of objects. When the function returns 0 items, the pipeline receives nothing, which is the correct behavior. The correct pattern is to use `Write-Output` inside the function to explicitly push objects into the pipeline, rather than relying on the function's return value to populate the pipeline.
PS8 — A `[scriptblock]` is a block of code that can be passed as a parameter to a cmdlet. A function is a named, reusable block of code. To pass a scriptblock remotely, you must serialize it. The double-hop problem occurs when variables are passed to a remote session; they are serialized and copied, meaning the remote session gets a snapshot, not a live reference. This is solved by using `Invoke-Command -ArgumentList` to pass values explicitly, or by using CredSSP for deeper credential delegation.
PS9 — `@()` creates an empty array object. `[array]` is a type accelerator used to cast a variable to an array type. To force a single result into an array, wrap it: `@[single_item]`. Indexing `$null` throws a terminating error. Indexing an empty array (`$emptyArray[0]`) returns `$null`.
PS10 — `-eq` (case-insensitive equality). `-ceq` (case-sensitive equality). `-like` (wildcard matching, case-insensitive). `-match` (regex matching, case-insensitive). `-contains` checks if a specific *value* exists within an array. `-in` checks if a value matches any item in a provided list of possible values.
PS11 — A module is a container for related cmdlets, functions, and types. A `.psm1` is a script module containing executable code. A `.psd1` is a manifest module containing metadata (version, dependencies). A binary module is a compiled assembly. `Import-Module` loads the module's definitions into the current PowerShell session, making its contents available.
PS12 — String interpolation uses double quotes (`"..."`) and allows embedding expressions via `$()` or `${}`. Single quotes (`'...'`) treat all content literally. Here-strings (`@"..."@`) allow multi-line strings and support interpolation within the delimiters.
PS13 — `Get-Member` returns the properties, methods, and events of an object. Properties are data fields. Methods are executable functions. NoteProperties are properties that lack explicit getter/setter definitions. `Select-Object` chooses which properties to display from the input objects. `Where-Object` filters the input objects based on a specified condition applied to their properties.
PS14 — PowerShell classes are object-oriented constructs that support inheritance and interfaces, but they are dynamically typed and less strictly enforced than C# classes. Limitations include dynamic nature and reliance on runtime checks. Use a class when you need to model complex, stateful entities with encapsulated behavior; use a function for simple, stateless procedural logic.
PS15 — `[CmdletBinding()]` enables advanced features like `-Verbose`, `-Debug`, and parameter validation. `SupportsShouldProcess` allows the cmdlet to check if the user wants to proceed with a potentially destructive action (e.g., "Are you sure you want to delete X?"). `DefaultParameterSetName` sets the default behavior when parameters are omitted. `ValueFromPipeline` allows the cmdlet to accept input objects from the pipeline. Begin, Process, and End blocks define the execution lifecycle: setup, main work, and cleanup.
PS16 — Providers are interfaces that allow cmdlets (like `Get-ChildItem`) to interact with diverse data sources using a unified syntax. The FileSystem provider accesses local drives. The Registry provider accesses the Windows Registry structure. The Certificate provider accesses stored certificates. You access the registry like a file system by using the `Registry:` provider prefix, e.g., `Get-ChildItem Registry:\HKLM\Software`.
PS17 — A `[runspace]` is an isolated execution environment. A `[runspacepool]` manages a collection of runspaces to handle concurrent requests efficiently. `ForEach-Object -Parallel` (v7+) abstracts this by managing the runspace pool internally for parallel iteration. Manual runspace management is necessary for fine-grained control over execution context and resource allocation in complex parallel workflows.
PS18 — PSScriptAnalyzer is a static code analysis tool that enforces coding standards by checking scripts against predefined rules. Rules define specific checks (e.g., "Do not use global variables"). Severity levels (Error, Warning, Information) indicate the impact of the violation. Rules can be suppressed using specific analyzer directives or by setting error actions. It integrates into CI/CD pipelines as a mandatory linting step before deployment.
PS19 — `$using:` scope allows variables from the parent scope to be safely accessed by child jobs or parallel processes after they have been serialized. `$args` (or `-ArgumentList`) explicitly passes arguments to the child process. Serialization limits (CLIXML depth) restrict the complexity and size of objects that can be passed across process boundaries, preventing infinite recursion or excessively large data transfers.
PS20 — DSC (Desired State Configuration) is a system for ensuring that infrastructure components maintain a defined, desired state. Configurations define the target state; Resources are the specific components (e.g., ensuring a service is running). The Local Configuration Manager (LCM) is the agent on the target node that enforces the configuration. In modern IaC, DSC is often complemented or replaced by tools like Terraform (for provisioning) or Ansible (for configuration management) due to their broader orchestration capabilities.
