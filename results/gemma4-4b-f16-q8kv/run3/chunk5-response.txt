**Go Answers**

G1 — An array has a fixed size known at compile time (`[5]int`), while a slice is a dynamically sized, flexible view into an underlying array. When appending to a slice that reaches capacity, Go allocates a new, larger underlying array (usually doubling the capacity), copies the existing elements, and then appends the new element.

G2 — `var x int` declares a variable `x` and initializes it to its zero value (0 for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when redeclaring a variable within the same scope, or when declaring a variable outside of a function body (at the package level).

G3 — A goroutine is a lightweight, independently executing function managed by the Go runtime. It is much cheaper than an OS thread because it requires very little stack space (starting small and growing as needed). The Go scheduler (GMP model) maps many goroutines (G) onto a smaller number of OS threads (M), managed by a set of logical processors (P). This allows Go to efficiently utilize multi-core CPUs while minimizing context switching overhead compared to OS threads.

G4 — Channels are typed conduits through which you can send and receive values between goroutines, enabling safe communication. An **unbuffered channel** requires both the sender and receiver to be ready simultaneously for the communication to proceed (synchronous). A **buffered channel** can hold a specified number of values without blocking the sender until the buffer is full. When sending to a full buffered channel, the sender goroutine blocks until another goroutine receives a value, freeing up space.

G5 — The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. It allows functions to gracefully stop work when a parent operation is canceled or times out.
*Example:*
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // Always call cancel to release resources

req, err := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
// ... proceed with client.Do(req)
```

G6 — Go uses **implicit interface satisfaction**. A type satisfies an interface simply by implementing all the methods defined in that interface; there is no explicit `implements` keyword. This differs from Java/C# where explicit declaration is often required. The empty interface `interface{}` (or `any`) can hold a value of *any* type. It is powerful because it allows for maximum flexibility (e.g., generic storage), but dangerous because the compiler loses all type information, requiring type assertions or reflection at runtime, which can panic if the assertion is wrong.

G7 — This is unsafe due to **data races**. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading them without synchronization. The Go memory model guarantees that writes are visible across goroutines only if synchronization primitives (like channels or mutexes) are used. The main goroutine might read the initial zero values (`false` and `""`) indefinitely, leading to a deadlock or incorrect output.
*Correct Alternatives:* Use a channel to signal completion:
```go
ready := make(chan bool)
go func() {
    data = "hello"
    ready <- true
}()
<-ready // Wait for the signal
fmt.Println(data)
```

G8 — `sync.Mutex` provides exclusive locking (only one goroutine can hold the lock at a time). `sync.RWMutex` allows multiple readers to hold the lock simultaneously (`RLock`) but requires exclusive access for writers (`Lock`). Use `sync.Map` when you have a high volume of concurrent reads and writes where the keys are unpredictable, as it is optimized for concurrent access without requiring external locking around the entire map structure. A regular map with a mutex is better when writes are infrequent or when you need complex transactional logic over the entire map state. Performance-wise, `RWMutex` is faster than `Mutex` under read-heavy loads.

G9 — Go modules manage dependencies. `go.mod` lists the required modules and their version constraints (e.g., `require github.com/pkg/errors v0.9.1`). `go.sum` contains cryptographic checksums for the exact content of every dependency listed in `go.mod`, ensuring that the downloaded code hasn't been tampered with. `go mod tidy` cleans up the `go.mod` and `go.sum` files by adding missing dependencies and removing unused ones. MVS (Minimum Version Selection) is an algorithm that selects the highest possible version of a dependency that still satisfies all version constraints specified in the module graph.

G10 — A `defer` statement schedules a function call to be executed just before the surrounding function returns. Multiple defers execute in **Last-In, First-Out (LIFO)** order. A common gotcha in a loop is that if you defer a call that captures a loop variable (e.g., `i`), the deferred function will execute *after* the loop finishes, and all deferred calls will reference the final value of `i`.

G11 — A pointer in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

G12 — The `init()` function is a special function that runs automatically before the `main` function (or before any other code in the package) is executed. It runs exactly once per package initialization. A package *can* have multiple `init()` functions; they execute sequentially in the order they appear in the source code.

G13 — `make` is used to initialize built-in reference types (slices, maps, channels). It allocates and initializes the underlying data structure. `new` allocates memory for a value of a specified type and returns a pointer to the zero value of that type. `make` works with slices, maps, and channels; `new` works with any type.

G14 — Error handling in Go is explicit and idiomatic: functions return an `error` type as their last return value. The error interface is satisfied by any type that implements the `Error() string` method. The idiomatic pattern is `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain contains a specific sentinel error value. `errors.As(err, &target)` checks if the error chain contains a value that matches a specific type, allowing you to extract structured error data.

G15 — **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be written to until initialized). **Slice:** `[]Type`. Zero value: `nil` (a nil slice, length 0, capacity 0). **Channel:** `chan Type`. Zero value: `nil` (a nil channel). **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.

G16 — A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization mechanism. The `-race` flag instruments the Go runtime to detect these unsynchronized concurrent memory accesses.
*Example Fix (Mutex):*
```go
var mu sync.Mutex
var counter int
mu.Lock()
counter++
mu.Unlock()
```

G17 — The `select` statement waits on multiple communication operations (channel receives/sends). It differs from `switch` because `select` is specifically designed for concurrency and channel operations. When multiple cases are ready, `select` chooses one **randomly** to ensure fairness. A timeout is implemented by using `select` with a `time.After` channel:
```go
select {
case msg := <-ch:
    // Handle message
case <-time.After(5 * time.Second):
    // Handle timeout
}
```

G18 — Escape analysis is the compiler's process of determining whether a variable's data should be allocated on the stack (fast, automatic cleanup) or the heap (slower, managed by the garbage collector). The compiler decides based on how long the variable needs to live and whether it needs to outlive the function call stack frame. You can inspect this using the `-gcflags="-m"` flag. It matters because heap allocation involves pointer chasing and GC overhead, which is significantly slower than stack allocation.

G19 — Reflection allows a program to examine and manipulate its own structure (types, fields, methods) at runtime. `reflect.Type` describes the structure of a value (metadata), while `reflect.Value` holds the actual runtime value. Reflection incurs significant performance costs because the compiler cannot optimize calls involving reflection statically. It is justified for serialization/deserialization libraries, ORMs, or dynamic plugin systems, but should be avoided in performance-critical paths where code generation is possible.

G20 — `go:embed` is a directive that allows embedding files or directories directly into a Go binary as assets. It works by instructing the compiler to read the specified path and make its contents available as a string, byte slice, or `fs.FS` object. For directories, it embeds the entire file system structure. Limitations include the size of the embedded data and the need to use the `embed` package. It interacts with `io/fs.FS` by providing an implementation of that interface for the embedded content.

**Rust Answers**

R1 — Ownership is Rust's system for managing memory without a garbage collector. It ensures that every piece of data has a single, clear owner at any given time. The three rules are: 1) Each value in Rust has a variable that’s called its owner. 2) There can only be one owner at a time. 3) When the owner goes out of scope, the value is dropped (memory is freed).

R2 — `String` is a heap-allocated, growable, mutable UTF-8 string type (owned data). `&str` is a string slice, which is a borrowed reference to a sequence of UTF-8 bytes, usually stored in the binary or on the stack. Use `String` when you need to own and modify the string data (e.g., building a string in a loop). Use `&str` in function signatures when you only need to read the string data, as it avoids unnecessary heap allocations.

R3 — Borrowing allows you to refer to data without taking ownership of it. The borrow checker enforces rules to prevent data races at compile time. **Shared references (`&T`)** allow multiple immutable references to the same data simultaneously. **Mutable references (`&mut T`)** allow only one mutable reference to the data at any given time. The core rule is: you can have *either* one mutable reference *or* any number of immutable references, but not both simultaneously.

R4 — `Result<T, E>` is an enum representing a computation that might succeed (`Ok(T)`) or fail (`Err(E)`). `Option<T>` is an enum representing a value that might be present (`Some(T)`) or absent (`None`). The `?` operator is syntactic sugar for propagating errors or unwrapping `Option`s. If the expression evaluates to `Ok(T)`, it unwraps `T` and continues. If it evaluates to `Err(E)`, it immediately returns `Err(E)` from the current function.
*Example:*
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> io::Result<String> {
    let mut file = File::open(path)?; // Propagates error if file cannot be opened
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates error if reading fails
    Ok(contents)
}
```

R5 — **`Box<T>`:** A smart pointer that allocates data on the heap, giving the compiler a fixed size at compile time. Used for recursive types or when you need to put a trait object on the stack. **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data on the heap. It uses atomic reference counting. **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>` but uses atomic operations, making it safe to share ownership across multiple threads.

R6 — Traits define shared behavior (a set of methods) that types can implement. They are conceptually similar to Go interfaces, but Rust traits are often used for *static dispatch* (compile-time polymorphism), whereas Go interfaces are inherently dynamic. A **trait object (`dyn Trait`)** uses dynamic dispatch (like an interface pointer) and incurs a small runtime cost. A **generic with a trait bound (`T: Trait`)** uses static dispatch, allowing the compiler to inline the calls, resulting in zero runtime overhead.

R7 — This fails because the compiler cannot guarantee that the returned reference (`&str`) will remain valid as long as the caller uses it. The reference must live at least as long as the *shortest* input reference. The fix requires introducing a lifetime annotation:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
The `'a` lifetime ensures that the returned reference is valid for the scope of the shortest input lifetime.

R8 — **`Send`** means a type can be safely transferred (sent) to another thread. **`Sync`** means a type can be safely referenced across threads (i.e., `&T` where `T: Sync` is safe to share). You cannot send an `Rc<T>` across threads because its internal reference count is not atomic, leading to race conditions during counting. `Arc<T>` is safe for concurrent use because its reference counting mechanism uses atomic CPU instructions, guaranteeing thread safety.

R9 — Rust's async/await is built on the concept of a **Future**. A `Future` is a trait representing a value that *might* be available at some point in the future. It is essentially a state machine that knows how to poll itself until it completes. The **executor** (like Tokio or async-std) is the runtime environment responsible for driving these futures—it polls them repeatedly, switching between tasks when one is waiting on I/O, thus achieving concurrency without blocking OS threads. This differs from Go's goroutines because Rust futures are *cooperative* (they must explicitly yield control via polling), whereas Go goroutines are *preemptive* (the scheduler interrupts them).

R10 — `unsafe` allows the programmer to bypass Rust's compile-time safety guarantees. Three things you can do are: 1) Dereference raw pointers (`*const T`, `*mut T`). 2) Call `unsafe` functions or methods. 3) Access or modify mutable static variables. Unsafe code is justified only when interfacing with C libraries (FFI), implementing highly optimized data structures, or when the programmer can mathematically prove the safety invariants that the compiler cannot verify.

R11 — Pattern matching uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches. `if let` is syntactic sugar used for matching a single, specific pattern and immediately executing a block if it matches. The compiler enforces **exhaustiveness**, meaning you must cover every possible variant of the enum or pattern, or explicitly use a wildcard (`_`) to signal that the remaining cases are acceptable.

R12 — `Vec<T>` is a dynamically sized, heap-allocated, growable array. An array `[T; N]` has a fixed size `N` known at compile time and is typically stored on the stack. When `Vec` pushes elements beyond its current capacity, it allocates a new, larger contiguous block of memory (usually doubling the capacity), copies all existing elements to the new block, and then deallocates the old block.

R13 — Rust enums are powerful algebraic data types that can hold different types of data for each variant (unlike C/Java enums which are often just integer constants). `Option<T>` is an enum with two variants: `Some(T)` (contains a value) and `None` (contains no value). Rust avoids null by using `Option<T>`, forcing the programmer to explicitly handle the absence of a value at compile time, thus eliminating null pointer dereference errors.

R14 — The `impl` block defines methods and associated functions for a specific type. **`&self`** means the method borrows the instance immutably (read-only access). **`&mut self`** means the method borrows the instance mutably (allows modification). **`self`** means the method takes ownership of the instance, consuming it. Associated functions (like `String::new()`) are functions associated with the type but do not operate on a specific instance; they are called using the type name.

R15 — A derive macro is a procedural macro that automatically implements standard traits for a struct or enum based on its definition. Examples include `#[derive(Debug)]` (allows printing via `{:#?}`), `#[derive(Clone)]` (implements deep copying), `#[derive(PartialEq)]` (implements equality checks), and `#[derive(Serialize)]` (used by Serde for serialization). You cannot derive a trait if the type contains fields that do not implement the required trait (e.g., you cannot derive `Clone` if one of your fields is a raw pointer).

R16 — `Cow<'a, T>` (Clone On Write) is a smart pointer that can hold either an owned value (`T`) or a borrowed reference (`&'a T`). It is useful when you frequently receive data that might be immutable, but sometimes you need to modify it. If you only read the data, `Cow` acts as a cheap reference. If you attempt to mutate it, `Cow` automatically clones the data into an owned `T` *only at that moment*, avoiding unnecessary allocations if the data remains immutable.

R17 — Rust's module system organizes code using `mod` declarations. `mod` declares a module (which can map to a file or a submodule). `use` brings items from a module into the current scope for easier access. `pub` makes items accessible outside the current module. The file system maps to modules: a file named `foo.rs` typically defines the `foo` module. The major change in Rust 2018 was the introduction of **path-based modules**, allowing modules to be defined by directory structure rather than strictly by file names.

R18 — `Pin<T>` is a wrapper type that guarantees that a value `T` will not be moved in memory after it has been pinned. This is crucial for types that contain self-references (where a part of the struct points back to another part of the same struct) or for async/await futures, which must maintain their internal state across `.await` points without being moved. **`Unpin`** is a marker trait indicating that a type *can* be safely moved in memory.

R19 — **Declarative macros (`macro_rules!`)** are pattern-matching macros that operate on tokens (like a sophisticated `switch` statement). They are simple and compile-time safe. **Procedural macros** (like `#[derive(...)]` or `#[attribute(...)]`) are complex functions that take Rust code as input, manipulate the Abstract Syntax Tree (AST), and output new Rust code. **Hygiene rules** prevent macro expansions from accidentally capturing or interfering with identifiers defined inside the macro call site, ensuring local scope integrity.

R20 — Zero-cost abstractions mean that high-level language features (like generics or iterators) compile down to machine code that is as fast as if the programmer had written the equivalent low-level code manually. **Generics** achieve this via **monomorphization**, where the compiler generates a specific version of the code for every concrete type used. **Trait static dispatch** (using generics) allows the compiler to resolve method calls at compile time, enabling inlining and avoiding the runtime overhead associated with dynamic dispatch (like virtual function tables). Iterators provide ergonomic chaining while maintaining this low-level performance.
