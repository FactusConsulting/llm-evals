K1 — A Deployment manages stateless applications by providing declarative updates for Pods and ReplicaSets. It ensures a desired number of replicas are running and handles rolling updates/rollbacks. A StatefulSet manages stateful applications (like databases) by providing stable, unique network identifiers and persistent storage for each pod, ensuring ordered deployment and scaling.

K2 — A ClusterIP Service exposes the Service on an internal IP address within the cluster. Traffic hitting this ClusterIP is routed by `kube-proxy` (which typically uses iptables or IPVS) to one of the healthy backing Pods selected via the Service's selector.

K3 — **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator or dynamically. It is a cluster resource representing actual storage capacity. **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a namespace resource that binds to an available PV that meets its requirements (size, access mode). **StorageClass:** A definition that dictates *how* dynamic provisioning should happen (e.g., which cloud provider/CSI driver to use, and what performance tier to offer). They relate because a PVC requests storage, the StorageClass defines the mechanism to create the PV, and the PV is the actual storage resource.

K4 — 1. **Check Pod Logs:** Use `kubectl logs <pod-name>` to see the application's startup errors or exceptions causing the crash. 2. **Check Events:** Use `kubectl describe pod <pod-name>` to check the 'Events' section for scheduling failures, image pull errors, or OOMKilled messages. 3. **Check Resource Limits:** Verify the Pod's resource requests/limits against the Node's capacity to rule out resource starvation. 4. **Check Container Image:** Ensure the container image is correct, accessible, and doesn't have immediate startup bugs.

K5 — CoreDNS acts as the cluster's internal DNS service, translating service names (e.g., `my-service.my-namespace.svc.cluster.local`) and pod IP addresses into resolvable names. If CoreDNS pods are down, internal DNS resolution fails entirely. Pods cannot resolve other services or pods within the cluster by name, leading to connection timeouts and application failures.

K6 — The scheduler uses a two-phase process: **Filtering** and **Scoring**.
1. **Filtering (Predicates):** The scheduler first filters out nodes that *cannot* run the pod based on hard constraints (e.g., insufficient CPU/Memory, node taints that the pod doesn't tolerate, required node selectors).
2. **Scoring (Priorities):** From the remaining viable nodes, the scheduler scores them based on various factors to determine the "best" fit.
*   **Factors:** 1. Resource utilization (preferring nodes with available capacity). 2. Node affinity/anti-affinity rules. 3. Topology spread constraints (spreading pods across different failure domains like zones). 4. QoS class requirements.

K7 — **Scheduling:** Yes, the pod *will* be scheduled initially. The scheduler only checks *requested* resources against *available* resources. Since 3.5GB is requested and 4GB is available, there is 0.5GB free. The pod requests 0.25GB (256Mi), so it fits. **Runtime:** If it uses 600Mi, it will exceed its limit (512Mi). The Kubelet on the node will enforce the limit, and the container runtime will terminate the process, resulting in an OOMKilled event and the pod entering CrashLoopBackOff.

K8 — 1. **External LB:** The external load balancer (e.g., AWS ELB, GCP LB) receives external traffic and forwards it to the Ingress Controller's external IP/NodePort. 2. **Ingress Controller:** The NGINX controller receives the request, inspects the Ingress resource rules (host/path matching), and determines the target Service. 3. **Service:** The Ingress Controller forwards the request to the ClusterIP of the target Service. 4. **Endpoints:** The Service object uses its selector to look up the corresponding Pod IPs in the Endpoints object. 5. **kube-proxy/iptables:** `kube-proxy` maintains iptables rules on the node. These rules intercept traffic destined for the Service ClusterIP and rewrite/forward it directly to one of the healthy Pod IPs listed in the Endpoints object.

K9 — A NetworkPolicy defines rules about how groups of pods are allowed to communicate with each other and with external network endpoints. If no NetworkPolicy exists in a namespace, the default behavior is "allow all" ingress and egress traffic. When a policy is applied, the default behavior changes to "deny all" ingress/egress for the selected pods, and only traffic explicitly permitted by the policy is allowed.

K10 — **RollingUpdate:** Gradually replaces old Pods with new ones, maintaining service availability throughout the update by ensuring a minimum number of replicas are always running. **Recreate:** Terminates all existing Pods before creating any new ones. **Choose Recreate:** When the application is not designed for zero-downtime updates, or when the change is fundamental (e.g., changing the underlying OS image or configuration that requires a clean slate).

K11 — A namespace is a mechanism to partition cluster resources, providing scope isolation for names (e.g., preventing naming collisions between different teams). Default namespaces include `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

K12 — `kubectl describe pod <name>` provides detailed metadata and state information. It shows: 1. **Events:** A chronological log of actions taken on the pod (scheduling, pulling images, readiness checks). 2. **Container Status Details:** Specific exit codes, restart counts, and detailed resource usage metrics. 3. **IP Address and Node Assignment:** Explicitly shows which node the pod is running on and its assigned internal IP.

K13 — A ConfigMap is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) external to the container image.
Methods to consume it: 1. **As Environment Variables:** Injecting keys/values directly into the Pod spec's `env` section. 2. **As Mounted Files:** Mounting the ConfigMap as a volume inside the container, where each key becomes a file in the specified directory.

K14 — **ClusterIP:** Exposes the Service internally within the cluster using a stable virtual IP. Only reachable from within the cluster. **NodePort:** Exposes the Service on a specific port on *every* Node's IP address. This allows external access via `<NodeIP>:<NodePort>`. **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes traffic to the Service's nodes.

K15 — A DaemonSet ensures that a copy of a Pod runs on *every* (or a specified subset of) eligible nodes in the cluster. You use it when you need a cluster-level service that must run locally on every node, such as log collectors (Fluentd), node monitoring agents (Prometheus Node Exporter), or network plugins.

K16 — **Taints:** A property applied to a Node that repels (prevents) Pods from being scheduled onto it unless the Pod explicitly tolerates the taint. **Tolerations:** A property applied to a Pod that allows it to be scheduled onto a Node that has a matching taint. **Node Affinity:** A scheduling rule that *attracts* or *repels* a Pod based on labels present on the Node (e.g., "only schedule on nodes labeled `disktype=ssd`"). **Difference:** Taints/Tolerations are about *repulsion* (a hard gate), while Affinity is about *preference* (a soft scoring mechanism). **Use Case:** Taint/Toleration: Dedicating a set of nodes for GPU workloads. Affinity: Ensuring a database pod is scheduled on a node with high local storage capacity.

K17 — A Kubernetes Operator is a method of packaging, deploying, and managing a complex application. It extends the Kubernetes API to create custom controllers that encode human operational knowledge (runbooks) into software. It differs from a standard controller because it understands the *application's state* and lifecycle, not just the desired resource state. It solves the problem of managing complex, stateful applications (like Kafka or Cassandra) that require custom operational logic beyond simple replica management.

K18 — Kubernetes uses **etcd's Raft consensus algorithm**, which ensures strong consistency. Raft requires a strict majority (quorum) of nodes to agree on any write operation before it is committed. If the quorum is lost (e.g., 2 out of 3 nodes fail), the cluster cannot achieve consensus, and the API server becomes unavailable for writes, effectively halting cluster state changes. If 2 out of 3 nodes are permanently lost, the cluster loses its quorum and cannot function until a replacement node is added and bootstrapped to restore the majority.

K19 — **RBAC (Role-Based Access Control):** Defines permissions based on the identity of the user/service account.
*   **Role:** Defines a set of permissions (verbs like `get`, `list`, `create`) scoped to a specific **Namespace**.
*   **ClusterRole:** Defines a set of permissions scoped across the **entire cluster**.
*   **RoleBinding:** Binds a **Role** to a specific user/group/service account *within a specific Namespace*.
*   **ClusterRoleBinding:** Binds a **ClusterRole** to a specific user/group/service account *cluster-wide*.

**Manifests for Read-Only Pod/Log Access in one namespace:**
```yaml
# 1. Define the Role (Permissions within the namespace)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

---
# 2. Bind the Role to a user/service account
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: my-namespace
subjects:
- kind: User # Or ServiceAccount
  name: developer-user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` specifies the number of DNS dots that the pod's resolver should follow before querying the upstream DNS server. If `ndots` is set too low (e.g., 1), and the pod tries to resolve an external domain (e.g., `api.external.com`), the resolver might first try to resolve it as a short name within the cluster (e.g., `api.external.com.svc.cluster.local`), leading to many unnecessary internal lookups before finally hitting the external server, causing slow resolution. To fix this, you can use `dnsConfig` in the pod spec and set `options` to explicitly control the search path or increase `ndots` to ensure external queries are attempted immediately.

D1 — **Git Merge:** Combines two or more divergent branches by creating a new "merge commit" that has two or more parents. It preserves the exact history of both branches. **Git Rebase:** Rewrites history by moving or combining a sequence of commits to a new base commit. It makes the history linear and cleaner. **Avoid Rebasing:** When working on shared, public branches (like `main` or `develop`), as rebasing rewrites history, which causes significant synchronization issues for collaborators who have already pulled the original commits.

D2 — **TCP (Transmission Control Protocol):** Connection-oriented, reliable, ordered delivery. It uses a three-way handshake to establish a connection and guarantees packet delivery/ordering. Protocols: HTTP/1.1, FTP. **UDP (User Datagram Protocol):** Connectionless, unreliable, best-effort delivery. It sends packets without prior setup and offers no guarantees of delivery or order. Protocols: DNS, VoIP.

D3 — A race condition occurs when the outcome of a program depends on the sequence or timing of uncontrollable events (like thread scheduling or network latency). **Example:** Two threads simultaneously check if a bank account balance is greater than $100. Both threads see $150. Both threads proceed to withdraw $100. Both succeed, resulting in a final balance of -$50, even though only one withdrawal should have been allowed.

D4 — **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is fast. **Asymmetric Encryption:** Uses a pair of keys: a public key (for encryption, shared widely) and a private key (for decryption, kept secret). It is computationally intensive. **TLS Usage:** Asymmetric encryption (RSA/ECC) is used during the initial handshake to securely exchange a temporary, random **symmetric session key**. Once the session key is established, all subsequent bulk data transfer is encrypted using the much faster symmetric algorithm.

D5 — A container image layer is a read-only, immutable filesystem layer created by each instruction in a Dockerfile (e.g., `RUN`, `COPY`). Each layer stores only the changes made by that instruction. **Layer Caching:** Docker caches the result of each layer. If an instruction and its context (files) haven't changed since the last build, Docker reuses the cached layer, drastically speeding up subsequent builds. **Best Practice:** Place instructions that change infrequently (like `FROM` or installing OS dependencies) near the top, and place instructions that change often (like `COPY . .`) near the bottom to maximize cache hits.

D6 — 1. **Check Application Logs:** Look for specific exceptions, database connection timeouts, or high error rates in the application logs. 2. **Check Resource Utilization:** Monitor CPU/Memory usage on the application pods and the underlying nodes to check for throttling or saturation. 3. **Check Dependencies:** Verify the health and latency of external services the API relies on (e.g., database, cache). 4. **Check Service Mesh/Network:** Inspect ingress/service logs and network policies to rule out routing issues or timeouts introduced by the infrastructure layer.

D7 — **CAP Theorem:** States that a distributed data store can only provide two out of three guarantees simultaneously: **Consistency** (every read receives the most recent write), **Availability** (every request receives a response, without guarantee that it is the most recent write), and **Partition Tolerance** (the system continues to operate despite arbitrary message loss or failure of part of the system).
*   **CP Example:** Traditional relational databases (e.g., PostgreSQL cluster, MongoDB replica set configured for strong consistency). If the network partitions, they prioritize consistency by refusing writes/reads on the minority side.
*   **AP Example:** Cassandra or DynamoDB. If the network partitions, they prioritize availability by allowing writes on both sides, resolving conflicts later (eventual consistency).

D8 — **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) allocated to an *existing* instance or pod. It is limited by the maximum capacity of the underlying hardware. **Horizontal Scaling (Scaling Out):** Increasing the number of instances (replicas) running the application. It is generally preferred in microservices as it offers near-limitless scalability. **Patterns:** Load Balancing, Stateless Architecture, Microservices.

D9 — An environment variable is a dynamic named value that can affect the way running processes will behave on a computer. On Linux, to set a variable that persists across shell sessions, you must add the definition (e.g., `export MY_VAR="value"`) to your shell's startup file, such as `~/.bashrc` or `~/.zshrc`, and then source the file (`source ~/.bashrc`).

D10 — **JSON (JavaScript Object Notation):** A lightweight data-interchange format that uses key-value pairs and array structures. Advantage: Highly native to JavaScript and easily parsed by most modern programming languages. **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard often used for configuration files. Advantage: Extremely clean syntax, minimal boilerplate, making it ideal for configuration management (like Kubernetes manifests).

D11 — A REST (Representational State Transfer) API is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources.
*   **GET:** Retrieves a representation of a resource (Read). Should be idempotent and safe (no side effects).
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource (Create).
*   **PUT:** Replaces an entire resource at a known URI (Update/Replace). Should be idempotent.
*   **DELETE:** Removes the specified resource (Delete). Should be idempotent.

D12 — Version pinning is the practice of explicitly specifying the exact version number of a dependency (e.g., `library==1.2.3`) rather than using a range (e.g., `library>=1.0`). It is crucial for reproducible builds because it guarantees that the build environment will use the exact same code dependencies every time, preventing unexpected runtime failures caused by upstream library changes.

D13 — **Compiled Language:** Source code is translated directly into machine code (binary executable) by a compiler *before* execution. Examples: C++, Go. **Interpreted Language:** Source code is read and executed line-by-line at runtime by an interpreter. Examples: Python, JavaScript.

D14 — **Reverse Proxy:** Sits in front of one or more web servers, intercepting client requests and forwarding them to the appropriate backend server. It shields the backend servers from direct client exposure. **Forward Proxy:** Sits in front of a client, acting as an intermediary to forward requests *on behalf of* the client (often used for anonymity or filtering).
*   **Nginx:** Common reverse proxy. Use Case: Load balancing traffic across multiple application servers.
*   **HAProxy:** Common reverse proxy. Use Case: High-performance TCP/HTTP load balancing, especially for complex routing rules.

D15 — A deadlock is a situation where two or more competing actions are waiting for the other to finish, resulting in a permanent standstill. The four necessary conditions (Coffman conditions) are: 1. **Mutual Exclusion:** At least one resource must be held in a non-sharable mode. 2. **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes. 3. **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily. 4. **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

D16 — **Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, all reads will eventually return the last updated value, but there is no guarantee about *when* that convergence will happen. **Cassandra Handling:** Cassandra uses mechanisms like vector clocks and read repair. When a client reads data, Cassandra checks the timestamps/versions of the replicas. If they differ, it returns the most recent version and asynchronously updates the stale replicas (read repair). **Tunable Consistency Levels:** Clients specify the required consistency level per operation (e.g., `ONE` - read from the fastest replica; `QUORUM` - read from a majority of replicas; `ALL` - read from every replica).

D17 — **mTLS (Mutual TLS):** An extension of standard TLS where *both* the client and the server authenticate each other using digital certificates, rather than just the server authenticating to the client. **Handshake Process:** 1. Client initiates connection. 2. Server sends its certificate. 3. Client verifies the server certificate against its trusted CAs. 4. Server requests the client's certificate. 5. Client sends its certificate. 6. Server verifies the client certificate against its trusted CAs. 7. Both parties exchange and verify session keys. **Use Case:** Service-to-service communication in a zero-trust microservices architecture (e.g., using a service mesh like Istio).

D18 — A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an array. **Collision Resolution:** 1. **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hash to that index. 2. **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing). **Time Complexity:**
*   **Average Case (Good Hash Function):** Insertion, Lookup, Deletion are $O(1)$.
*   **Worst Case (All keys collide):** Insertion, Lookup, Deletion degrade to $O(n)$ (similar to traversing a linked list).

D19 — The Circuit Breaker pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing microservice), thereby preventing resource exhaustion and cascading failures. **States:** 1. **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the breaker trips to Open. 2. **Open:** Requests are immediately rejected without attempting the call (fail-fast). After a timeout, the breaker moves to Half-Open. 3. **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker closes; if they fail, it returns to Open. **Relation to Retries:** Circuit breakers act as a high-level guardrail. Retries and exponential backoff are low-level strategies used *within* the Closed state to handle transient errors, but the circuit breaker prevents retries when the downstream service is fundamentally broken.

D20 — **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data resource *before* the transaction reads or modifies it, preventing other transactions from accessing it until the lock is released. (Example: `SELECT * FROM accounts WHERE id=1 FOR UPDATE`). **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read (often using version numbers or timestamps). If a conflict is detected, the transaction is rolled back and must be retried. **Choice:** Choose **Pessimistic** for high-contention, short transactions (e.g., inventory decrement). Choose **Optimistic** for low-contention, long transactions (e.g., user profile updates).
