# Kubernetes (20 questions)

**K1** — A **Deployment** manages stateless applications with identical, interchangeable pods. It provides rolling updates, rollbacks, and scaling. A **StatefulSet** manages stateful applications where each pod has a unique, stable identity (hostname like `web-0`, `web-1`), stable network identity, and ordered deployment/termination. StatefulSets are used for databases, message queues, and other stateful workloads.

**K2** — A **ClusterIP** Service creates an internal virtual IP (VIP) within the cluster. kube-proxy programs iptables (or IPVS) rules on each node that redirect traffic to the Service IP to one of the backing pod IPs. The routing uses random selection by default, with options for session affinity.

**K3** — A **PersistentVolume (PV)** is a cluster-wide storage resource provisioned by an admin or dynamically. A **PersistentVolumeClaim (PVC)** is a user's request for storage that binds to a PV. A **StorageClass** defines storage provisioner parameters (type, reclaim policy, provisioner) enabling dynamic provisioning. When a PVC references a StorageClass, Kubernetes automatically creates a matching PV.

**K4** — Troubleshooting CrashLoopBackOff:
1. `kubectl logs <pod> --previous` — check previous container logs for crash reason
2. `kubectl describe pod <pod>` — check Events for OOMKilled, liveness probe failures, or mount errors
3. Verify environment variables and ConfigMaps/Secrets are correctly mounted
4. Check resource limits — OOMKilled pods restart immediately
5. Test the container image locally to verify it runs
6. Check liveness/readiness probe configurations for overly strict timeouts

**K5** — **CoreDNS** is the DNS server for Kubernetes, resolving pod and service names to IPs. It reads Service endpoints from the Kubernetes API and answers queries like `myservice.default.svc.cluster.local`. If CoreDNS pods are down, internal DNS resolution fails — pods cannot resolve service names, breaking service discovery. External DNS may still work via `/etc/resolv.conf` nameservers.

**K6** — The scheduler uses a **predictor** (optional), then **filtering** (hard predicates), then **scoring** (priority functions). Filtering eliminates nodes that can't run the pod (insufficient resources, taints without tolerations, node selectors not matching, PodAntiAffinity violations). Scoring ranks remaining nodes using factors like: (1) resource utilization balance, (2) image locality (prefers nodes with cached images), (3) inter-pod affinity/anti-affinity preferences, (4) topology spread constraints.

**K7** — **No, the pod will NOT be scheduled.** The node has 4GB total, 3.5GB requested, leaving only 512Mi available. The pod requests 256Mi, which fits, but Kubernetes also reserves ~10-15% for system daemons, so effective available is less. Even if scheduled, when the pod uses 600Mi (exceeding its 512Mi limit), it will be **OOMKilled** — the OOM killer terminates the container to protect the node.

**K8** — Request lifecycle:
1. External traffic hits **External Load Balancer** (cloud LB or MetalLB)
2. LB forwards to **NGINX Ingress Controller** pod(s) on port 80/443
3. NGINX parses Host header and path, matches Ingress rules
4. NGINX forwards to **Service** VIP (ClusterIP)
5. **kube-proxy** iptables/IPVS rules redirect to a healthy **Endpoint** (pod IP)
6. Request reaches the **application pod**
7. Response follows reverse path back to client

**K9** — A **NetworkPolicy** controls pod-to-pod and pod-to-external traffic using labels. **Default behavior with no NetworkPolicy**: all traffic is allowed (permissive). When you apply a NetworkPolicy selecting certain pods, those pods become **isolated** — only explicitly allowed traffic flows. Unselected pods remain permissive.

**K10** — **RollingUpdate** replaces pods incrementally, maintaining availability during updates. **Recreate** terminates all old pods before creating new ones, causing brief downtime. Choose Recreate for: database migrations requiring exclusive access, schema changes incompatible with mixed versions, or when rolling updates cause issues (e.g., connection pool exhaustion).

**K11** — A **namespace** provides isolation boundaries for resources within a cluster. Default namespaces: `default` (user workloads), `kube-system` (cluster components), `kube-public` (public cluster info), `kube-node-lease` (node lease objects).

**K12** — `kubectl describe pod` shows detailed pod information including: (1) **Events** (scheduling, probe failures, OOMKilled), (2) **Container state and restart count**, (3) **Volume mounts and PVC bindings**, (4) **Resource requests/limits**, (5) **Node assignment and IP**, (6) **Conditions** (Ready, Initialized, PodScheduled).

**K13** — A **ConfigMap** stores non-sensitive configuration data as key-value pairs. Pods consume ConfigMaps via: (1) **Environment variables** (`envFrom` or `valueFrom`), (2) **Volume mounts** (as files in `/etc/config/`), (3) **Command-line arguments** via `valueFrom`.

**K14** — **ClusterIP**: internal-only virtual IP, default type. **NodePort**: exposes service on each node's IP at a static port (30000-32767), accessible externally. **LoadBalancer**: provisions an external cloud load balancer routing to NodePort or directly to pods.

**K15** — A **DaemonSet** ensures exactly one pod runs on each (or selected) node. Use DaemonSets for: node-level agents (Fluentd, Prometheus node exporter), network plugins (Calico, Cilium), monitoring agents, or log collectors that need access to node resources.

**K16** — **Taints** repel pods from nodes (node says "I'm special, don't schedule here unless..."). **Tolerations** allow pods to be scheduled on tainted nodes. **Node affinity** attracts pods to nodes with matching labels. Use case: taint GPU nodes with `gpu=true:NoSchedule`, add toleration to GPU workloads. Use node affinity to schedule database pods on SSD-backed nodes.

**K17** — A **Kubernetes Operator** is a controller that manages complex applications using Custom Resources (CRDs). Unlike standard controllers managing built-in resources, Operators encode operational knowledge for stateful applications (databases, caches). They handle provisioning, upgrades, backups, and failover. The pattern solves the problem of automating complex application lifecycle management that requires domain expertise.

**K18** — etcd uses **Raft consensus** for strong consistency. If quorum is lost (2+ nodes down in 3-node cluster), the cluster becomes **unavailable** — no reads or writes possible. Recovery from 2/3 lost: (1) Identify surviving node, (2) Backup its data, (3) Delete data directories of dead nodes, (4) Reinitialize cluster with surviving node as seed, (5) Add new nodes. Data from dead nodes is lost.

**K19** — **RBAC** grants permissions via Roles/ClusterRoles bound to subjects. **Role** is namespace-scoped, **ClusterRole** is cluster-wide. **RoleBinding** binds a Role to subjects in a namespace. **ClusterRoleBinding** binds a ClusterRole cluster-wide.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: development
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-pod-reader
  namespace: development
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — **ndots** in `/etc/resolv.conf` determines how many dots must be in a name before it's treated as fully-qualified. Default ndots=5 means `example.com` (1 dot) triggers searching all search domains first, causing timeouts. Fix: set `ndots: 1` in pod `dnsConfig`:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "1"
```

# Development (20 questions)

**D1** — **Merge** creates a merge commit preserving branch history. **Rebase** rewrites history by moving commits onto another branch's tip. Avoid rebasing: (1) public/shared branches, (2) branches with multiple collaborators, (3) branches with tags/releases — rebasing rewrites commit hashes, confusing others.

**D2** — **TCP** is connection-oriented, reliable, ordered, with flow control. **UDP** is connectionless, unreliable, unordered, lower overhead. TCP protocols: HTTP, HTTPS, SSH, SMTP. UDP protocols: DNS, DHCP, VoIP (RTP), streaming media.

**D3** — A **race condition** occurs when program behavior depends on timing of uncontrollable events. Example:
```python
counter = 0
def increment():
    global counter
    temp = counter  # Read
    temp = temp + 1  # Modify
    counter = temp  # Write
# Two threads calling increment() may both read 0, both write 1
```

**D4** — **Symmetric encryption** uses one key for encrypt/decrypt (fast, e.g., AES). **Asymmetric encryption** uses public/private key pairs (slower, e.g., RSA). In TLS: asymmetric encryption establishes a secure channel and exchanges a symmetric session key; symmetric encryption then secures the actual data transfer.

**D5** — A **container image layer** is a read-only filesystem snapshot. Layers are cached — if a layer's content hasn't changed, Docker reuses it. Best practice: order Dockerfile commands so frequently-changing commands (like `COPY .`) come last, maximizing cache hits.

**D6** — HTTP 503 troubleshooting order:
1. Check application logs for errors or resource exhaustion
2. Verify upstream dependencies (database, cache, external APIs) are healthy
3. Check resource utilization (CPU, memory, connections) — possible throttling
4. Review circuit breaker status or rate limiting configurations
5. Check load balancer health checks and endpoint status
6. Review recent deployments or configuration changes

**D7** — **CAP theorem**: distributed systems can only guarantee 2 of 3: Consistency, Availability, Partition tolerance. **CP example**: etcd, ZooKeeper — sacrifice availability during network partitions to maintain consistency. **AP example**: Cassandra (default), DynamoDB — sacrifice consistency for availability, providing eventual consistency.

**D8** — **Horizontal scaling** adds more instances (scale out). **Vertical scaling** adds resources to existing instance (scale up). Horizontal scaling patterns: stateless services, shared-nothing architecture, load balancers, distributed databases, message queues for decoupling.

**D9** — An **environment variable** is a key-value pair available to processes. To persist across sessions on Linux: add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `/etc/environment`.

**D10** — **JSON** is a data interchange format using key-value pairs with strict typing. **YAML** is human-readable configuration format supporting anchors, references, and multi-line strings. JSON advantage: universal parsing, strict validation. YAML advantage: readability, comments, anchors for reuse.

**D11** — A **REST API** uses HTTP methods to perform CRUD operations on resources. **GET** retrieves resources (safe, idempotent). **POST** creates resources (not idempotent). **PUT** replaces a resource entirely (idempotent). **DELETE** removes a resource (idempotent).

**D12** — **Version pinning** specifies exact dependency versions (e.g., `package==1.2.3`). It ensures reproducible builds by preventing unexpected breaking changes from dependency updates. Without pinning, `pip install` might pull newer versions with incompatible changes.

**D13** — **Compiled languages** translate to machine code before execution (faster runtime, e.g., C, Go, Rust). **Interpreted languages** execute source code directly via an interpreter (slower, more flexible, e.g., Python, JavaScript, Ruby).

**D14** — A **reverse proxy** sits in front of servers, forwarding client requests to backend servers (clients don't know about backends). A **forward proxy** sits in front of clients, forwarding requests to any server (servers don't know about clients). Reverse proxies: **NGINX** (web serving, load balancing), **HAProxy** (TCP/HTTP load balancing).

**D15** — A **deadlock** occurs when processes wait indefinitely for each other's resources. **Coffman conditions**: (1) Mutual exclusion — resources can't be shared, (2) Hold and wait — process holds resources while waiting for others, (3) No preemption — resources can't be forcibly taken, (4) Circular wait — circular chain of processes waiting.

**D16** — **Eventual consistency** guarantees that if no new updates, all accesses will eventually return the last updated value. Cassandra handles read-after-write via **tunable consistency levels**: ONE, QUORUM, ALL, LOCAL_QUORUM, etc. For strong read-after-write, use QUORUM for both reads and writes, or use **read repair** and **anti-entropy** mechanisms.

**D17** — **mTLS** requires both client and server to present certificates. Handshake: (1) ClientHello with client cert, (2) Server responds with server cert, (3) Client verifies server cert against CA, (4) Server verifies client cert against CA, (5) Both derive session keys. Used in: service mesh (Istio), internal microservices communication, database connections, API gateways.

**D18** — A **hash table** uses a hash function to map keys to array indices. **Collision resolution**: (1) **Chaining** — linked list at each bucket, (2) **Open addressing** — probe for next available slot (linear, quadratic, double hashing). Time complexity: Average O(1) for insert/lookup/delete. Worst case O(n) when all keys hash to same bucket (poor hash function or adversarial input).

**D19** — A **circuit breaker** prevents cascade failures by stopping calls to failing services. **States**: (1) **Closed** — normal operation, calls pass through, (2) **Open** — failures exceed threshold, calls fail fast, (3) **Half-open** — after timeout, allow test calls to check recovery. Relates to retries: circuit breakers reduce unnecessary retries to failing services; exponential backoff spreads retry load over time.

**D20** — **Optimistic concurrency** assumes conflicts are rare; validates at commit time (e.g., row versioning, CAS). **Pessimistic concurrency** assumes conflicts are common; locks resources upfront (e.g., `SELECT FOR UPDATE`). Choose optimistic for read-heavy workloads with rare updates. Choose pessimistic for write-heavy workloads or when conflicts must be prevented. Example:
```sql
-- Optimistic: version column checked at UPDATE
UPDATE accounts SET balance = balance - 100, version = version + 1 
WHERE id = 1 AND version = 5;

-- Pessimistic: lock row for exclusive access
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```
