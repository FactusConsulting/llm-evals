# Kubernetes (20 questions)

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**

A Deployment manages stateless applications with identical, interchangeable pods that can be scheduled on any node. A StatefulSet manages stateful applications where each pod has a unique, stable identity (hostname like `web-0`, `web-1`), stable network identity, and ordered deployment/termination. StatefulSets guarantee that pods are created/terminated in order and maintain persistent storage tied to specific pod identities.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**

A ClusterIP Service creates an internal virtual IP (VIP) within the cluster. kube-proxy on each node programs iptables (or IPVS) rules that redirect traffic to the Service's ClusterIP to one of the backend pod IPs. The rules implement round-robin or random selection among healthy endpoints discovered via the Endpoints object.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**

- **PersistentVolume (PV)**: A cluster-wide storage resource provisioned by an administrator or dynamically. It represents actual storage (e.g., NFS share, cloud disk).
- **PersistentVolumeClaim (PVC)**: A user's request for storage within a namespace. It specifies size, access mode, and optionally a StorageClass.
- **StorageClass**: Defines storage provisioner and parameters for dynamic PV creation.

Relationship: A PVC references a StorageClass → Kubernetes dynamically creates a PV → PVC binds to PV → Pod mounts PVC → Pod gets storage.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**

1. **Check container logs**: `kubectl logs <pod> --previous` to see the last crash output.
2. **Describe the pod**: `kubectl describe pod <pod>` to see events, exit codes, and resource issues.
3. **Verify application configuration**: Check ConfigMaps, Secrets, and environment variables for missing/incorrect values.
4. **Check resource limits**: Verify the container isn't being OOMKilled or hitting CPU limits.
5. **Test locally**: Run the container image locally with same config to isolate cluster vs. app issues.
6. **Check dependencies**: Verify databases, external services, or other pods the app depends on are reachable.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**

CoreDNS provides internal DNS resolution for the cluster. It resolves:
- Service names (e.g., `my-service.default.svc.cluster.local`)
- Pod names (via headless services)
- External domains (via upstream DNS)

If CoreDNS pods are down, internal DNS resolution fails. Pods cannot resolve service names, breaking service discovery. External DNS may still work if pods have fallback upstream resolvers configured.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**

**Filtering (Predicate phase)**: Eliminates nodes that cannot run the pod:
- Resource availability (CPU/memory requests fit)
- Node selectors match
- Taints/tolerations compatible
- Node affinity rules satisfied
- Pod topology spread constraints met
- Volume zone constraints

**Scoring (Priority phase)**: Ranks remaining nodes:
- Least allocated resources (prefers nodes with more free capacity)
- Balanced resource distribution
- Inter-pod affinity/anti-affinity preferences
- Topology hints for local storage

**Factors considered**: Resource requests, taints/tolerations, node affinity, pod affinity, topology spread, volume zone constraints, priority/preemption.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**

**Will it be scheduled?** Yes. The scheduler checks if `requested + pod_requests <= node_capacity`. Here: 3.5GB + 256Mi = 3.75GB < 4GB. The pod fits.

**If it uses 600Mi at runtime**: The container exceeds its 512Mi limit. The OOM killer will terminate the container with OOMKilled exit code. The pod will restart (if restartPolicy allows), potentially entering CrashLoopBackOff.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod.**

1. **External Load Balancer**: Cloud LB or metal LB receives request, forwards to NodePort of ingress controller.
2. **Ingress Controller (NGINX)**: Reads Ingress resources, matches host/path rules, determines target Service.
3. **Service Discovery**: NGINX queries Kubernetes API (or watches) for Service endpoints.
4. **kube-proxy/iptables**: Service ClusterIP is translated via iptables DNAT to a specific pod IP (round-robin).
5. **Pod**: Request reaches application container on the target port.
6. **Response**: Travels back through same path in reverse.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**

A NetworkPolicy controls pod-to-pod and pod-to-external traffic using labels.

**Default behavior**: If no NetworkPolicy exists in a namespace, all traffic is allowed (permissive).

**When you apply one**: The namespace becomes restrictive. Only traffic matching the NetworkPolicy rules is allowed. Pods not selected by any NetworkPolicy are isolated (no ingress/egress unless explicitly allowed).

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**

**RollingUpdate**: Gradually replaces old pods with new ones. Maintains availability during update. Configurable via `maxUnavailable` and `maxSurge`.

**Recreate**: Terminates all old pods before creating new ones. Causes brief downtime.

**Choose Recreate when**:
- Application requires exclusive access to resources during update
- Database schema migrations that can't run concurrently
- Testing/development environments where downtime is acceptable
- Stateful applications that can't handle multiple versions running simultaneously

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**

A namespace provides a scope for names, enabling isolation and organization of resources. Resources in different namespaces are isolated by default.

**Default namespaces**:
- `default`: For user workloads
- `kube-system`: For Kubernetes system components
- `kube-public`: Publicly accessible read-only data
- `kube-node-lease`: Node lease objects (for node heartbeats)

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**

`kubectl describe` shows detailed pod information including events and status details.

**Three pieces not in `kubectl get`**:
1. **Events**: Recent events related to the pod (scheduling, image pull, probe failures)
2. **Container state details**: Exit codes, reason for termination, restart count details
3. **Volume mounts**: Detailed volume information including PVC bindings and mount paths

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**

A ConfigMap stores non-sensitive configuration data as key-value pairs.

**Two consumption methods**:
1. **Environment variables**: Inject keys as env vars via `envFrom` or `env.valueFrom.configMapKeyRef`
2. **Volume mount**: Mount as files in `/etc/config/` directory via `volumes` with `configMap` type

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**

- **ClusterIP**: Internal-only virtual IP. Accessible only within the cluster. Default type.
- **NodePort**: Exposes service on each node's IP at a static port (30000-32767). Accessible externally via `<NodeIP>:<NodePort>`.
- **LoadBalancer**: Provisions an external load balancer (cloud provider) with an external IP. Routes traffic to NodePort or directly to pods.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**

A DaemonSet ensures exactly one pod runs on each (or selected) node. Automatically adds pods to new nodes.

**Use DaemonSet instead of Deployment when**:
- Running node-level agents (log collectors like Fluentd, monitoring agents like Node Exporter)
- Running network plugins (Calico, Flannel)
- Running storage daemons (GlusterFS, Ceph)
- Any workload that must run on every node

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**

**Taints/Tolerations**:
- **Taint**: Applied to nodes, "taints" them so pods won't schedule unless they have matching toleration
- **Toleration**: Applied to pods, allows scheduling on tainted nodes
- **Use case**: Dedicate GPU nodes with taint `gpu=true:NoSchedule`, only GPU pods tolerate it

**Node Affinity**:
- Expresses preference or requirement for pod to run on nodes with certain labels
- **Use case**: Schedule database pods only on SSD-backed nodes with label `storage=ssd`

**Difference**: Taints/tolerations push pods away from nodes; affinity pulls pods toward nodes.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**

An Operator is a controller that manages complex stateful applications using Custom Resources (CRDs). It encodes human operational knowledge into software.

**Difference from standard controller**: Standard controllers manage built-in resources (Pods, Deployments). Operators manage custom resources representing complex applications (databases, message queues).

**Problems solved**:
- Automates complex lifecycle operations (backup, restore, scaling, upgrades)
- Encodes operational expertise into automation
- Enables GitOps for stateful applications
- Provides self-healing for complex applications

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**

**Consistency model**: etcd uses Raft consensus, providing strong consistency (linearizability). All reads see the most recent committed write.

**If quorum is lost**: The cluster becomes unavailable. No reads or writes can proceed. The control plane stops functioning.

**Recovery from 2/3 nodes lost**:
1. **Cannot recover** - 2/3 loss means quorum is permanently lost
2. **Must restore from snapshot**: Use `etcdctl snapshot restore` from the latest backup
3. **Rebuild cluster**: Start new etcd cluster from snapshot, point control plane to it
4. **Prevention**: Use 5 or 7 nodes for production (tolerates 2 or 3 failures)

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**

**RBAC components**:
- **Role**: Namespaced permissions (verbs + resources)
- **ClusterRole**: Cluster-wide permissions
- **RoleBinding**: Binds Role to subjects in a namespace
- **ClusterRoleBinding**: Binds ClusterRole to subjects cluster-wide

**Manifests for developer read-only access**:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: development
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: development
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**

**Problem**: Default `ndots: 5` means for a name with fewer than 5 dots (like `google.com`), CoreDNS tries each search domain first before querying the name directly. With search domains like `default.svc.cluster.local`, `svc.cluster.local`, `cluster.local`, this causes multiple failed queries before reaching the external resolver.

**Fix using dnsConfig**:

```yaml
spec:
  containers:
  - name: app
    image: myapp
  dnsConfig:
    options:
    - name: ndots
      value: "1"
    - name: timeout
      value: "2"
    - name: attempts
      value: "2"
    searches:
    - svc.cluster.local
    - cluster.local
    nameservers:
    - 10.96.0.10  # CoreDNS
```

Setting `ndots: 1` makes single-label names go directly to nameservers, reducing query count.

# Development (20 questions)

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**

**Merge**: Creates a new merge commit preserving history. Both branches' commits remain intact.

**Rebase**: Moves commits to appear as if they were made after the target branch. Rewrites history.

**Avoid rebasing when**:
- Branch is shared with others (rewriting history breaks their work)
- Branch has been pushed to remote and others may have based work on it
- Working on a public/main branch
- History preservation is important for audit trails

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**

**TCP**: Connection-oriented, reliable, ordered delivery, flow control, congestion control. Slower but guarantees delivery.

**UDP**: Connectionless, unreliable, no ordering guarantees, no flow control. Faster, lower overhead.

**TCP protocols**: HTTP, HTTPS, SSH, SMTP, FTP

**UDP protocols**: DNS, DHCP, VoIP (RTP), QUIC, TFTP

**D3 — Medium: What is a race condition? Give a concrete example in any language.**

A race condition occurs when program behavior depends on the relative timing of events, leading to unpredictable results.

**Example (Python)**:

```python
counter = 0

def increment():
    global counter
    temp = counter  # Read
    temp = temp + 1  # Modify
    counter = temp   # Write

# Two threads calling increment() simultaneously
# Both read counter=0, both write counter=1
# Expected: 2, Actual: 1
```

The read-modify-write sequence isn't atomic, so interleaving causes lost updates.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**

**Symmetric encryption**: Same key for encryption and decryption. Fast, efficient. Examples: AES, ChaCha20.

**Asymmetric encryption**: Public key encrypts, private key decrypts (or vice versa for signing). Slower, enables key exchange. Examples: RSA, ECC.

**In TLS**:
1. **Asymmetric**: Client and server exchange keys using RSA or ECDHE (key exchange)
2. **Symmetric**: Session keys derived from key exchange are used for bulk data encryption (AES-GCM)

This combines asymmetric's secure key exchange with symmetric's speed.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**

A layer is a read-only filesystem snapshot created by each Dockerfile instruction. Layers are stacked and cached.

**Layer caching best practices**:
1. **Order instructions by change frequency**: Put rarely-changing instructions first (base image, dependencies)
2. **Combine related commands**: Use single RUN with `&&` to reduce layers
3. **Use .dockerignore**: Exclude unnecessary files from context
4. **Copy dependency files first**: Copy `requirements.txt` before source code so dependency layer caches

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**

1. **Application logs**: Check for errors, exceptions, or resource exhaustion messages
2. **Resource metrics**: CPU, memory, disk I/O, network saturation on application servers
3. **Downstream dependencies**: Database connections, external API availability, cache status
4. **Load balancer/ingress**: Check for connection limits, timeout settings, health check failures
5. **Database**: Connection pool exhaustion, slow queries, lock contention
6. **Rate limiting**: Check if requests are being throttled

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**

**CAP Theorem**: A distributed system can only guarantee two of three properties:
- **C**onsistency: All nodes see same data at same time
- **A**vailability: Every request gets a response
- **P**artition tolerance: System works despite network partitions

**CP example (Consistency + Partition Tolerance)**: **etcd**, **ZooKeeper**, **Google Spanner**. During partition, system becomes unavailable rather than serving stale data.

**AP example (Availability + Partition Tolerance)**: **Cassandra**, **DynamoDB**, **CouchDB**. During partition, both sides continue serving, potentially with stale data, reconciling later.

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**

**Vertical scaling**: Adding resources (CPU, RAM) to existing servers. Limited by hardware max.

**Horizontal scaling**: Adding more servers/nodes. Theoretically unlimited.

**Architectural patterns enabling horizontal scaling**:
- **Stateless services**: No session state on server
- **Shared-nothing architecture**: Each node independent
- **Load balancing**: Distribute traffic across instances
- **Distributed caching**: Redis Cluster, Memcached
- **Database sharding/partitioning**: Split data across databases
- **Message queues**: Decouple producers/consumers

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**

An environment variable is a key-value pair available to processes. Used for configuration without code changes.

**Set persistently**:
```bash
# For current user, bash
echo 'export MY_VAR=value' >> ~/.bashrc
source ~/.bashrc

# For all users, system-wide
echo 'export MY_VAR=value' >> /etc/environment
# or
echo 'export MY_VAR=value' >> /etc/profile.d/myvars.sh
```

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**

**JSON**: JavaScript Object Notation. Strict syntax, requires quotes, commas, braces.

**YAML**: YAML Ain't Markup Language. Human-friendly, uses indentation, no quotes needed for strings.

**JSON advantage**: Universally supported, strict parsing, faster to parse

**YAML advantage**: More readable, supports anchors/aliases, comments, less verbose

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**

**REST API**: Architectural style using HTTP for stateless client-server communication with resources identified by URIs.

**HTTP methods**:
- **GET**: Retrieve resource. Safe, idempotent.
- **POST**: Create resource or trigger action. Not idempotent.
- **PUT**: Replace resource entirely. Idempotent.
- **DELETE**: Remove resource. Idempotent.

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**

**Version pinning**: Specifying exact dependency versions (e.g., `package==1.2.3`) rather than ranges (e.g., `package>=1.0`).

**Importance for reproducible builds**:
- Ensures identical dependencies across builds
- Prevents breaking changes from upstream updates
- Enables debugging by reproducing exact environment
- Critical for security (knowing exact vulnerable versions)

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**

**Compiled language**: Source code translated to machine code before execution. Faster runtime, longer build time.

**Interpreted language**: Source code executed line-by-line by interpreter. Slower runtime, faster development cycle.

**Compiled examples**: C, C++, Rust, Go

**Interpreted examples**: Python, JavaScript, Ruby, PHP

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**

**Reverse proxy**: Sits in front of servers, receives client requests, forwards to backend servers. Client thinks it's talking directly to server.

**Forward proxy**: Sits in front of clients, receives client requests, forwards to external servers. Server thinks it's talking to client.

**Common reverse proxies**:
- **NGINX**: High-performance web server, load balancing, SSL termination
- **HAProxy**: Specialized load balancer, advanced traffic management

**Use cases**: Load balancing, SSL termination, caching, compression, security (hiding backend topology)

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**

**Deadlock**: Two or more processes blocked forever, each waiting for resources held by others.

**Four Coffman conditions**:
1. **Mutual Exclusion**: Resources cannot be shared; only one process can use at a time
2. **Hold and Wait**: Process holds at least one resource while waiting for another
3. **No Preemption**: Resources cannot be forcibly taken from processes
4. **Circular Wait**: Circular chain of processes, each waiting for resource held by next

All four must hold simultaneously for deadlock.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**

**Eventual consistency**: After updates stop, all replicas will eventually converge to same value. No guarantee of immediate consistency.

**Cassandra read-after-write**:
- Uses **read repair** and **anti-entropy** to reconcile replicas
- Client can specify consistency level per operation
- **Tunable consistency levels**:
  - **ONE**: Fastest, least consistent (1 replica)
  - **QUORUM**: Balanced (majority of replicas)
  - **ALL**: Most consistent, slowest (all replicas)
  - **LOCAL_QUORUM**, **EACH_QUORUM**: Datacenter-aware variants

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**

**mTLS**: Both client and server present certificates and authenticate each other.

**Handshake process**:
1. Client sends ClientHello with supported ciphers
2. Server responds with ServerHello, certificate, ServerKeyExchange
3. Server sends CertificateRequest (asks for client cert)
4. Client sends certificate, ClientKeyExchange
5. Server verifies client certificate against trusted CA
6. Client verifies server certificate
7. Both derive session keys, send Finished messages

**Infrastructure use cases**:
- Service mesh (Istio, Linkerd) for service-to-service authentication
- Database connections
- Internal API communication
- Zero-trust network architectures

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**

**Hash table**: Array + hash function mapping keys to indices.

**Collision resolution**:
- **Chaining**: Each bucket holds a linked list of entries. Collisions append to list.
- **Open addressing**: On collision, probe for next available slot (linear, quadratic, or double hashing).

**Time complexity**:
| Operation | Average | Worst Case |
|-----------|---------|------------|
| Insertion | O(1) | O(n) |
| Lookup | O(1) | O(n) |
| Deletion | O(1) | O(n) |

Worst case occurs when all keys hash to same index (poor hash function or adversarial input).

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**

**Circuit breaker**: Prevents cascade failures by stopping calls to failing services.

**Three states**:
1. **Closed**: Normal operation. Requests pass through. Track failures.
2. **Open**: Failure threshold exceeded. Requests fail fast without calling service.
3. **Half-open**: After timeout, allow limited requests. If successful, close circuit; if failed, reopen.

**Prevents cascade failures**: Stops failing requests from consuming resources and propagating failures.

**Relation to retry/backoff**:
- Circuit breaker should be **outside** retry logic
- Retries with exponential backoff attempt recovery; circuit breaker gives up after threshold
- Together: Retry with backoff for transient failures, circuit breaker for persistent failures

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**

**Pessimistic concurrency control**: Lock resources before access. Assumes conflicts are likely.

**Optimistic concurrency control**: Allow concurrent access, detect conflicts at commit time. Assumes conflicts are rare.

**When to choose**:
- **Pessimistic**: High contention, critical data, short transactions
- **Optimistic**: Low contention, read-heavy workloads, long transactions

**Examples**:

**Pessimistic (SELECT FOR UPDATE)**:
```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- Lock held until commit
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**Optimistic (row versioning)**:
```sql
-- Read with version
SELECT balance, version FROM accounts WHERE id = 1;
-- Update with version check
UPDATE accounts SET balance = balance - 100, version = version + 1 
WHERE id = 1 AND version = <original_version>;
-- Returns 0 rows if version changed (conflict)
```
