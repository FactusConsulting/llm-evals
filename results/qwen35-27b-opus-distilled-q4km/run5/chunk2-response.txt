# Kubernetes (20 questions)

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**

A Deployment manages stateless applications with identical, interchangeable pods that can be scheduled on any node. A StatefulSet manages stateful applications where each pod has a unique, stable identity (hostname like `web-0`, `web-1`), stable network identity, and ordered deployment/termination. StatefulSets guarantee that pods are created/terminated in order and maintain persistent storage tied to specific pod identities.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**

A ClusterIP Service creates an internal virtual IP (VIP) within the cluster. kube-proxy on each node programs iptables (or IPVS) rules that intercept traffic to the Service IP and load-balance it to the backing pod IPs listed in the Endpoints object. Traffic is routed via the node's network stack to the target pod's IP.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**

- **PersistentVolume (PV)**: A cluster-wide storage resource provisioned by an administrator or dynamically. It represents actual storage (e.g., NFS share, cloud disk).
- **PersistentVolumeClaim (PVC)**: A user's request for storage within a namespace. It specifies size, access mode, and optionally a StorageClass.
- **StorageClass**: Defines storage provisioner parameters (e.g., `gp2` for AWS EBS) enabling dynamic provisioning.

Relationship: A PVC references a StorageClass → Kubernetes dynamically creates a PV → PVC binds to PV → Pod mounts PVC.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**

1. `kubectl logs <pod>` and `kubectl logs <pod> --previous` to see application errors.
2. `kubectl describe pod <pod>` to check Events for OOMKilled, liveness probe failures, or mount errors.
3. Verify environment variables, ConfigMaps, and Secrets are correctly mounted and contain expected values.
4. Check resource limits — pod may be OOMKilled if memory limit is too low.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**

CoreDNS provides internal DNS resolution for services (e.g., `my-service.default.svc.cluster.local`) and external DNS forwarding. If CoreDNS pods are down, internal service discovery fails — pods cannot resolve service names, causing connection failures to other services. External DNS may still work via fallback to node's `/etc/resolv.conf`.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**

**Filtering (Predicate phase)**: Eliminates nodes that cannot run the pod based on:
- Resource availability (CPU/memory requests)
- Node selectors, affinity rules, taints/tolerations
- Pod topology spread constraints

**Scoring (Priority phase)**: Ranks remaining nodes using:
- Least allocated resources (prefer nodes with more free capacity)
- Node affinity preferences (weighted scores)
- Inter-pod affinity/anti-affinity preferences
- Topology spread constraints

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**

**Will it be scheduled?** Yes. The scheduler checks requested resources: 3.5GB + 256Mi = 3.756GB < 4GB available. The pod fits.

**If it uses 600Mi at runtime:** The pod exceeds its 512Mi limit. The OOM killer will terminate the container, causing the pod to restart (CrashLoopBackOff if it keeps exceeding).

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod.**

1. **External Load Balancer**: Routes traffic from internet to the Ingress Controller's NodePort or directly to its pod IP.
2. **NGINX Ingress Controller**: Reads Ingress resources, matches host/path rules, applies SSL termination if configured.
3. **Service**: NGINX forwards to the backend Service's ClusterIP.
4. **kube-proxy/iptables**: Intercepts traffic to Service IP, load-balances to pod IPs in the Endpoints object.
5. **Application Pod**: Receives the request on its container port.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**

A NetworkPolicy controls ingress/egress traffic to/from pods using labels. **Default behavior**: If no NetworkPolicy exists, all traffic is allowed (permissive). **When applied**: Only pods selected by the policy's `podSelector` are affected; unselected pods remain unrestricted. The policy defines allowed traffic patterns for selected pods.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**

**RollingUpdate**: Gradually replaces old pods with new ones, maintaining availability. Configurable via `maxSurge` and `maxUnavailable`.

**Recreate**: Terminates all old pods before creating new ones — causes downtime.

**Choose Recreate when**: Database schema migrations require exclusive access, or when the application cannot handle multiple versions running simultaneously.

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**

A namespace provides logical isolation for resources within a cluster. Default namespaces:
- `default`: For user workloads
- `kube-system`: For Kubernetes system components
- `kube-public`: Publicly accessible resources
- `kube-node-lease`: Node lease objects (for heartbeat)

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**

Shows detailed pod information including:
1. **Events** — scheduling, probe failures, OOM kills
2. **Container state details** — exit codes, restart counts, reason
3. **Volume mounts and their status**
4. Resource requests/limits per container
5. Node assignment and QoS class

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**

A ConfigMap stores non-sensitive configuration data as key-value pairs. Consumption methods:
1. **Environment variables**: Via `envFrom` or `env.valueFrom.configMapKeyRef`
2. **Volume mount**: Mounted as files in `/etc/config/` or similar path

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**

- **ClusterIP**: Internal-only virtual IP, accessible within cluster
- **NodePort**: Exposes service on each node's IP at a static port (30000-32767)
- **LoadBalancer**: Provisions external cloud load balancer, routes to NodePort

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**

A DaemonSet ensures exactly one pod runs on each (or selected) node. Use for:
- Node monitoring agents (Prometheus node exporter)
- Log collectors (Fluentd)
- Network plugins (Calico, Cilium)
- Storage daemons

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**

**Taints/Tolerations**: Taints repel pods from nodes; tolerations allow pods to "tolerate" taints. Use case: Taint GPU nodes with `gpu=true:NoSchedule`, only GPU pods tolerate it.

**Node Affinity**: Attracts pods to nodes with matching labels. Use case: Schedule database pods to nodes with `ssd=true` label.

**Difference**: Taints push pods away; affinity pulls pods toward nodes.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**

An Operator is a controller that manages complex stateful applications using Custom Resource Definitions (CRDs). Unlike standard controllers that manage built-in resources (Pods, Services), Operators manage application-specific resources (e.g., `PostgreSQL`, `Redis`).

**Problems solved**: Automates complex lifecycle operations like backups, failover, scaling, upgrades that require domain-specific logic.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**

**Consistency model**: etcd uses Raft consensus, providing strong consistency (linearizability). All reads/writes go through the leader.

**Quorum lost**: Cluster becomes unavailable — no reads or writes possible. Control plane stops functioning.

**Recovery from 2/3 lost**: 
1. Start a new etcd cluster with fresh data
2. Restore from latest snapshot if available
3. Rebuild Kubernetes control plane components pointing to new etcd
4. This is a destructive recovery — data after last snapshot is lost

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**

**RBAC components**:
- **Role**: Namespaced permissions (verbs + resources)
- **ClusterRole**: Cluster-wide permissions
- **RoleBinding**: Binds Role to subjects in a namespace
- **ClusterRoleBinding**: Binds ClusterRole to subjects cluster-wide

**Manifests**:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev-team
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev-team
  name: dev-pod-reader
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**

**Problem**: Default `ndots: 5` means for domain `example.com`, the resolver tries:
1. `example.com` (no dot, treated as local)
2. `example.com.<search-domain>`
3. `example.com.<search-domain-2>`
... up to 5 attempts before trying `example.com.` (with trailing dot)

Each failed attempt adds ~1-2s delay.

**Fix**:
```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "1"
    - name: timeout
      value: "2"
    - name: attempts
      value: "2"
```

# Development (20 questions)

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**

**Merge**: Creates a merge commit preserving history as-is. **Rebase**: Rewrites history by moving commits to a new base.

**Avoid rebasing**: On shared/public branches, as it rewrites history and causes conflicts for collaborators.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**

**TCP**: Connection-oriented, reliable, ordered delivery, flow control. Protocols: HTTP, SSH.

**UDP**: Connectionless, unreliable, no ordering guarantees, lower overhead. Protocols: DNS, VoIP.

**D3 — Medium: What is a race condition? Give a concrete example in any language.**

A race condition occurs when program behavior depends on non-deterministic timing of events.

**Example (Python)**:
```python
counter = 0
def increment():
    global counter
    temp = counter
    counter = temp + 1  # Another thread could modify counter here
```
Two threads reading `counter=0`, both writing `1` → final value is `1` instead of `2`.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**

**Symmetric**: Same key for encrypt/decrypt. Fast, used for bulk data. Example: AES.

**Asymmetric**: Public/private key pair. Slower, used for key exchange/signing. Example: RSA, ECC.

**In TLS**: Asymmetric (RSA/ECDHE) establishes session and exchanges symmetric session key → Symmetric (AES) encrypts all subsequent traffic.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**

Each `RUN`, `COPY`, `ADD` instruction creates a layer. Layers are cached and reused if unchanged.

**Best practices**:
- Put rarely-changing commands first (base image, dependencies)
- Put frequently-changing commands last (source code)
- Combine related commands to reduce layers
- Use `.dockerignore` to avoid unnecessary files in layers

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**

1. **Application logs** — Look for errors, timeouts, connection refused
2. **Resource utilization** — CPU, memory, disk I/O, network saturation
3. **Downstream dependencies** — Database connections, external API availability
4. **Load balancer/ingress** — Circuit breakers, rate limits, health check failures

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**

**CAP theorem**: A distributed system can only guarantee 2 of 3: Consistency, Availability, Partition tolerance.

**CP (Consistency + Partition tolerance)**: etcd, ZooKeeper, MongoDB (with strong consistency). Sacrifices availability during network partitions.

**AP (Availability + Partition tolerance)**: Cassandra (default), DynamoDB (eventual consistency). Sacrifices strong consistency — reads may return stale data.

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**

**Vertical**: Add resources to existing instance (more CPU/RAM). Limited by hardware max.

**Horizontal**: Add more instances. Requires:
- Stateless application design
- Load balancer
- Shared state externalization (database, cache)
- Service discovery

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**

Environment variables are key-value pairs passed to processes. To persist:

```bash
echo 'export MY_VAR=value' >> ~/.bashrc  # or ~/.profile, ~/.zshrc
source ~/.bashrc
```

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**

**JSON**: JavaScript Object Notation — strict, machine-friendly format.

**Differences**: YAML supports comments, anchors, more flexible syntax; JSON is stricter.

**Advantages**:
- JSON: Universal parsing support, strict validation
- YAML: Human-readable, supports comments, anchors for reuse

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**

REST API uses HTTP methods to perform CRUD operations on resources.

- **GET**: Retrieve resource (safe, idempotent)
- **POST**: Create new resource (not idempotent)
- **PUT**: Replace entire resource (idempotent)
- **DELETE**: Remove resource (idempotent)

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**

Version pinning fixes dependencies to exact versions (e.g., `requests==2.28.0`). Ensures reproducible builds — same code + same dependencies = same behavior, preventing "works on my machine" issues.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**

**Compiled**: Source → machine code via compiler before execution. Examples: C, Go.

**Interpreted**: Source executed line-by-line by interpreter. Examples: Python, JavaScript.

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**

**Reverse proxy**: Sits in front of servers, forwards client requests to backend servers. Client thinks it's talking directly to the server.

**Forward proxy**: Sits in front of clients, forwards client requests to internet. Server sees proxy's IP.

**Reverse proxy servers**:
- **NGINX**: Load balancing, SSL termination
- **HAProxy**: High-performance TCP/HTTP load balancing

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**

A deadlock is when two or more processes are blocked forever, each waiting for the other.

**Coffman conditions**:
1. **Mutual exclusion**: Resources cannot be shared
2. **Hold and wait**: Process holds resources while waiting for others
3. **No preemption**: Resources cannot be forcibly taken
4. **Circular wait**: Circular chain of processes waiting for each other

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**

**Eventual consistency**: If no new updates, all replicas will eventually converge to same value.

**Cassandra read-after-write**: Client can use `CONSISTENCY LEVEL` per operation:
- **WRITE**: ONE, QUORUM, ALL, LOCAL_QUORUM
- **READ**: ONE, QUORUM, ALL, LOCAL_QUORUM

For read-after-write: Write with QUORUM, read with QUORUM guarantees consistency (majority overlap).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**

**mTLS**: Both client and server present certificates for mutual authentication.

**Handshake**:
1. ClientHello → ServerHello + Server Certificate
2. Client verifies server cert, sends Client Certificate
3. Server verifies client cert
4. Both derive shared session key
5. Encrypted communication begins

**Use cases**: Service mesh (Istio), internal microservice communication, database connections.

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**

**Hash table**: Maps keys to indices via hash function `h(key) % table_size`.

**Collision resolution**:
- **Chaining**: Each bucket holds a linked list of entries
- **Open addressing**: Find next available slot (linear/quadratic probing, double hashing)

**Time complexity**:
- **Average**: O(1) for all operations
- **Worst**: O(n) — all keys hash to same bucket

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**

**Circuit breaker**: Prevents cascading failures by stopping calls to failing services.

**States**:
- **Closed**: Normal operation, requests pass through
- **Open**: Failing, requests fail fast without calling service
- **Half-open**: Testing if service recovered, limited requests allowed

**Prevents cascade**: Stops retry storms, allows failing service to recover.

**Relation to retries**: Circuit breaker should be combined with retries + exponential backoff. Retries handle transient failures; circuit breaker handles persistent failures.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**

**Pessimistic**: Lock resources before access. Assumes conflicts are likely.
```sql
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- Modify
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**Optimistic**: No locks, check for conflicts at commit time. Assumes conflicts are rare.
```sql
-- Read with version
SELECT balance, version FROM accounts WHERE id = 1;
-- Update with version check
UPDATE accounts SET balance = balance - 100, version = version + 1 
WHERE id = 1 AND version = <original_version>;
-- Check affected rows = 1
```

**Choose pessimistic**: High contention, financial transactions.
**Choose optimistic**: Low contention, read-heavy workloads.
