# Kubernetes (20 questions)

**K1:** A **Deployment** manages stateless applications with identical, interchangeable pods, providing rolling updates and rollbacks. A **StatefulSet** manages stateful applications where each pod has a unique, stable identity (hostname, network ID), stable storage, and ordered deployment/termination. Use Deployments for web servers; use StatefulSets for databases like MySQL or Kafka.

**K2:** A **ClusterIP** Service exposes a service on an internal IP address within the cluster. It routes traffic to pods via **kube-proxy**, which sets up **iptables** (or IPVS) rules on each node. When a request hits the Service IP, iptables rules redirect the packet to one of the healthy pod IPs listed in the Service's **Endpoints** object, typically using round-robin load balancing.

**K3:**
- **PersistentVolume (PV):** A cluster-level resource representing a piece of storage (e.g., NFS share, cloud disk).
- **PersistentVolumeClaim (PVC):** A namespace-level request for storage by a user/pod. It binds to a PV.
- **StorageClass:** Defines storage provisioner and parameters (e.g., SSD vs HDD). Enables dynamic provisioning of PVs when a PVC is created.
**Relation:** A PVC references a StorageClass → Kubernetes dynamically creates a PV → Pod mounts the PVC → PV provides the actual storage.

**K4:**
1. **Check pod logs:** `kubectl logs <pod> --previous` to see error output before crash.
2. **Inspect events:** `kubectl describe pod <pod>` to see OOMKilled, liveness probe failures, or image pull errors.
3. **Verify resource limits:** Check if the pod is being OOMKilled due to memory limits.
4. **Test locally:** Run the container image locally with `docker run` to reproduce the crash outside the cluster.

**K5:** **CoreDNS** provides internal DNS resolution for Kubernetes services and pods. It resolves service names (e.g., `my-service.default.svc.cluster.local`) to ClusterIP addresses. If CoreDNS pods are down, DNS resolution fails entirely—pods cannot resolve service names, causing connectivity failures between services.

**K6:** The scheduler uses a two-phase process:
1. **Filtering (Predicate):** Eliminates nodes that can't run the pod based on:
   - Resource availability (CPU/memory requests)
   - Node selectors and affinity rules
   - Taints/tolerations
   - Pod topology spread constraints
2. **Scoring (Priority):** Ranks remaining nodes by:
   - Least allocated resources (balance load)
   - Image locality (prefer nodes with cached images)
   - Inter-pod affinity/anti-affinity preferences
   - Topology spread constraints

**K7:**
- **Will it schedule?** Yes. The node has 4GB total, 3.5GB requested, leaving 512Mi available. The pod requests 256Mi, which fits.
- **If it uses 600Mi at runtime:** The pod exceeds its 512Mi limit and will be **OOMKilled** (terminated by the kubelet).

**K8:**
1. **External Load Balancer** (cloud provider) receives the request and forwards it to the **NGINX Ingress Controller** pod.
2. **NGINX Ingress Controller** reads Ingress rules, matches the host/path, and determines the target Service.
3. NGINX performs server-side load balancing to a pod IP from the Service's **Endpoints**.
4. **kube-proxy** on the node has set up **iptables** rules that redirect traffic to the target pod's IP:port.
5. The pod receives the request and responds back through the same path.

**K9:** A **NetworkPolicy** is a Kubernetes resource that controls ingress/egress traffic to/from pods using labels. **Default behavior:** If no NetworkPolicy exists in a namespace, all traffic is allowed (permissive). When you apply a NetworkPolicy that selects certain pods, those pods become restricted—only traffic matching the policy rules is allowed; all other traffic is denied.

**K10:**
- **RollingUpdate:** Gradually replaces old pods with new ones, maintaining availability during updates.
- **Recreate:** Terminates all old pods before creating new ones, causing brief downtime.
**Choose Recreate** when: The application cannot handle mixed versions running simultaneously (e.g., database schema migrations), or when you need a clean slate (e.g., clearing all in-memory state).

**K11:** A **namespace** provides a scope for names within a cluster, enabling resource isolation. **Default namespaces:** `default`, `kube-system` (system components), `kube-public` (public cluster info), and `kube-node-lease` (node heartbeats).

**K12:** `kubectl describe pod <name>` shows detailed pod information including:
1. **Events** (scheduling, probe failures, OOMKilled)
2. **Container state** and restart count
3. **Volume mounts** and resource requests/limits
4. **Node assignment** and QoS class
5. **Conditions** (Ready, Initialized, PodScheduled)

**K13:** A **ConfigMap** stores non-confidential configuration data as key-value pairs. A pod can consume it via:
1. **Environment variables:** `envFrom` or `env.valueFrom.configMapKeyRef`
2. **Volume mount:** Mounted as files in `/etc/config/`
3. **Command-line arguments** via `args`

**K14:**
- **ClusterIP:** Internal cluster access only (default).
- **NodePort:** Exposes service on each node's IP at a static port (30000-32767).
- **LoadBalancer:** Provisions an external load balancer (cloud provider) with a public IP.

**K15:** A **DaemonSet** ensures a copy of a pod runs on all (or selected) nodes. Use it instead of a Deployment for node-level agents: log collectors (Fluentd), monitoring agents (Node Exporter), or network plugins (Calico).

**K16:**
- **Taints/Tolerations:** Taints repel pods from nodes; tolerations allow pods to "tolerate" taints. Use case: Dedicate GPU nodes by tainting them and only allowing GPU pods to tolerate.
- **Node Affinity:** Attracts pods to nodes based on labels. Use case: Schedule pods only on nodes with specific hardware or zone labels.
**Difference:** Taints push pods away; affinity pulls pods toward nodes.

**K17:** A **Kubernetes Operator** is a controller that manages complex applications using **Custom Resource Definitions (CRDs)**. Unlike standard controllers that manage built-in resources (Pods, Services), Operators manage application-specific resources (e.g., `PostgreSQL`, `Redis`). They solve problems like automated backups, scaling, failover, and upgrades for stateful applications.

**K18:**
- **Consistency model:** etcd uses **Raft consensus**, providing strong consistency (linearizability). All reads see the most recent committed write.
- **Quorum lost:** If quorum is lost (e.g., 2 of 3 nodes down), the cluster becomes unavailable for writes and may become unavailable for reads depending on configuration.
- **Recovery from 2/3 lost:** This is catastrophic. You must restore from the last available snapshot of the surviving node, then rebuild the cluster with new nodes. Data from the lost nodes is unrecoverable.

**K19:**
- **Role:** Namespace-scoped permissions.
- **ClusterRole:** Cluster-scoped permissions.
- **RoleBinding:** Binds a Role to users/groups in a namespace.
- **ClusterRoleBinding:** Binds a ClusterRole to users/groups cluster-wide.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev-team
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev-team
  name: dev-pod-reader
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20:** The `ndots` setting in `/etc/resolv.conf` determines how many dots must be in a name before it's treated as fully qualified. Default is 5. For a domain like `api.google.com` (2 dots), the resolver tries: `api.google.com.<search-domain>` first, then falls back after timeout. This causes multiple DNS queries per lookup. **Fix:** Set `ndots: 1` in `dnsConfig`:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "1"
```

# Development (20 questions)

**D1:**
- **Merge:** Creates a new merge commit preserving branch history. Non-destructive.
- **Rebase:** Rewrites commit history by replaying commits on top of another branch. Creates linear history.
**Avoid rebasing:** On shared/public branches, as it rewrites history and causes conflicts for collaborators.

**D2:**
- **TCP:** Connection-oriented, reliable, ordered delivery. Protocols: HTTP, HTTPS, SSH.
- **UDP:** Connectionless, unreliable, unordered. Protocols: DNS, VoIP, streaming.

**D3:** A **race condition** occurs when multiple threads/processes access shared data concurrently, and the outcome depends on the timing of execution. **Example** (Python):
```python
counter = 0
def increment():
    global counter
    temp = counter
    temp += 1
    counter = temp  # Race: another thread may modify counter between read and write
```

**D4:**
- **Symmetric:** Same key for encryption/decryption. Fast, used for bulk data.
- **Asymmetric:** Public/private key pair. Slower, used for key exchange and signatures.
**In TLS:** Asymmetric encryption (RSA/ECDHE) establishes a session key during handshake; symmetric encryption (AES) encrypts the actual data transfer.

**D5:** A **container image layer** is a read-only filesystem snapshot created by each Dockerfile instruction. Layers are cached and reused. **Best practices:** Order instructions from least to most frequently changing (e.g., `COPY requirements.txt` before `COPY .`) to maximize cache hits.

**D6:**
1. **Check application logs** for errors (stack traces, exceptions).
2. **Verify upstream dependencies** (database, cache, external APIs) are healthy.
3. **Check resource utilization** (CPU, memory, connections) for throttling.
4. **Review recent deployments** or configuration changes.

**D7:** **CAP theorem** states a distributed system can only guarantee two of: Consistency, Availability, Partition tolerance.
- **CP example:** ZooKeeper, etcd (prioritize consistency; become unavailable during partition).
- **AP example:** Cassandra, DynamoDB (prioritize availability; may return stale data during partition).

**D8:**
- **Horizontal scaling:** Adding more instances (scale out).
- **Vertical scaling:** Adding resources to existing instance (scale up).
**Patterns enabling horizontal scaling:** Stateless services, load balancers, distributed databases, message queues, shared storage.

**D9:** An **environment variable** is a key-value pair available to processes. To persist across sessions on Linux, add to `~/.bashrc`, `~/.profile`, or `/etc/environment`:
```bash
export MY_VAR=value
```

**D10:**
- **JSON:** JavaScript Object Notation, strict syntax, widely supported.
- **YAML:** Human-readable, supports anchors/aliases, no quotes for simple strings.
**Advantage JSON:** Strict parsing, fewer ambiguities. **Advantage YAML:** More readable, supports comments.

**D11:**
- **REST API:** Architectural style using HTTP for stateless client-server communication.
- **GET:** Retrieve resource.
- **POST:** Create resource.
- **PUT:** Update/replace resource.
- **DELETE:** Remove resource.

**D12:** **Version pinning** fixes dependency versions to exact values (e.g., `requests==2.28.0`). Important for reproducible builds—ensures identical dependencies across environments and over time.

**D13:**
- **Compiled:** Source → machine code before execution. Examples: C, Go, Rust.
- **Interpreted:** Source executed line-by-line by interpreter. Examples: Python, JavaScript.

**D14:**
- **Reverse proxy:** Sits in front of servers, forwards client requests to backend servers.
- **Forward proxy:** Sits in front of clients, forwards requests to any server.
**Examples:**
- **Nginx:** Load balancing, SSL termination.
- **HAProxy:** High-performance TCP/HTTP proxying.

**D15:** A **deadlock** occurs when two or more processes are blocked forever, each waiting for the other to release a resource. **Coffman conditions:**
1. Mutual exclusion
2. Hold and wait
3. No preemption
4. Circular wait

**D16:** **Eventual consistency** means if no new updates, all replicas will eventually converge to the same value. **Cassandra** handles read-after-write via:
- **Tunable consistency levels:** ONE, QUORUM, ALL, LOCAL_QUORUM, etc.
- **Read repair** and anti-entropy processes reconcile differences.
- Clients can use `CAS` (Compare-And-Set) for strong consistency when needed.

**D17:** **mTLS** requires both client and server to present certificates. **Handshake:**
1. ClientHello → ServerHello + Server Certificate
2. Client verifies server cert, sends Client Certificate
3. Server verifies client cert
4. Both derive session keys
**Used in:** Service mesh (Istio), internal microservice communication, zero-trust architectures.

**D18:**
- **Hash table:** Maps keys to indices via hash function.
- **Collision resolution:**
  - **Chaining:** Linked list at each bucket.
  - **Open addressing:** Probe for next available slot.
- **Time complexity:**
  - Average: O(1) for insert, lookup, delete
  - Worst: O(n) when all keys hash to same bucket

**D19:** **Circuit breaker** prevents cascade failures by stopping calls to failing services. **States:**
- **Closed:** Normal operation, requests pass through.
- **Open:** Failing, requests fail fast without calling service.
- **Half-open:** Testing if service recovered, allow limited requests.
**Relates to retry/backoff:** Retries should respect circuit breaker state; exponential backoff reduces load during failures.

**D20:**
- **Optimistic:** Assume conflicts rare; validate at commit time. Use row versioning or checksums. Example: `SELECT * FROM table FOR UPDATE` not needed; check version column on update.
- **Pessimistic:** Lock resources upfront. Example: `SELECT * FROM table FOR UPDATE` locks rows until transaction ends.
**Choose optimistic** for read-heavy workloads with rare conflicts; **pessimistic** for write-heavy or when conflicts are expensive.
