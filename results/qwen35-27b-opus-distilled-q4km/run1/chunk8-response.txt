# Cloud Infrastructure Architecture (20 questions)

## CL1 — IaaS, PaaS, and SaaS

| Layer | IaaS | PaaS | SaaS |
|-------|------|------|------|
| **Your Control** | Compute, Storage, Network, OS, Runtime, App, Data | Runtime, App, Data | App, Data |
| **Provider Manages** | Physical hardware, virtualization | Everything except your app/data | Everything |

**Examples:**
- **IaaS:** AWS EC2, Azure VMs, GCP Compute Engine
- **PaaS:** AWS Elastic Beanstalk, Azure App Service, Google App Engine
- **SaaS:** Microsoft 365, Salesforce, Slack

## CL3 — VPC, Subnet, Security Group, NACL

**Layering (coarse to fine):**
1. **VPC** — Isolated virtual network (e.g., 10.0.0.0/16)
2. **Subnet** — CIDR within VPC (e.g., 10.0.1.0/24), tied to one AZ
3. **NACL** — Stateless subnet-level firewall (evaluated first, inbound/outbound rules)
4. **Security Group** — Stateful instance-level firewall (evaluated second, allows/egress rules)

**Stateful vs Stateless:**
- **Security Group (stateful):** Return traffic automatically allowed; tracks connection state
- **NACL (stateless):** Must explicitly allow return traffic; no connection tracking

## CL4 — Multi-Account Strategy

**Landing Zone:** Pre-configured account structure with guardrails, networking, logging, and IAM foundations.

**Organizational Units (OUs):** Group accounts by function (prod, dev, shared-services, security).

**Guardrails:** SCPs (AWS) / Policy-based restrictions (Azure) to prevent non-compliant actions.

**Shared Networking:**
- AWS: Transit Gateway connects VPCs across accounts
- Azure: Hub-and-Spoke with VNet peering

**Centralized Logging:** Dedicated logging account with CloudTrail/Activity Logs forwarded via S3 Event Notifications / Event Hubs.

**Why Single Account is Problematic:**
- No blast radius containment
- No separation of duties
- Difficult cost allocation
- Security policy conflicts
- No environment isolation

## CL6 — Kubernetes Autoscaling Patterns

| Autoscaler | Scales | Metric Source | Use Case |
|------------|--------|---------------|----------|
| **HPA** | Pod count (horizontal) | CPU, memory, custom metrics | Variable request load |
| **VPA** | Pod resource requests (vertical) | Actual pod usage | Memory-heavy workloads, unpredictable per-pod needs |
| **Cluster Autoscaler** | Node count | Pending pods, resource pressure | Scale underlying infrastructure |
| **KEDA** | Pod count (horizontal) | 20+ external sources (queues, DBs, etc.) | Event-driven, queue-based workloads |

**KEDA over HPA when:**
- Scaling based on queue depth (RabbitMQ, Kafka, SQS)
- Database connection pool metrics
- HTTP request rate from external sources
- Need sub-minute scaling decisions

## CL7 — Disaster Recovery Strategy

**RPO/RTO Definitions:**
- **RPO (Recovery Point Objective):** Max acceptable data loss (time)
- **RTO (Recovery Time Objective):** Max acceptable downtime (time)

**DR Strategies:**

| Strategy | RTO | RPO | Cost | Description |
|----------|-----|-----|------|-------------|
| **Pilot Light** | Hours | Hours | Low | Minimal infrastructure running; scale up on failure |
| **Warm Standby** | Minutes | Minutes | Medium | Scaled-down production in secondary region |
| **Multi-Site Active-Active** | Seconds | Seconds | High | Full production in both regions simultaneously |

**Architecture Components:**
- **Database:** Async replication (lower latency, eventual consistency) vs sync (strong consistency, higher latency)
- **DNS Failover:** Route53 health checks + failover routing policy / Azure Traffic Manager
- **State Management:** Externalize state to replicated storage (S3 Cross-Region, DynamoDB Global Tables)
- **Active-Active Complexity:** Session affinity, bidirectional replication conflicts, split-brain scenarios

**Cost Implications:**
- Pilot Light: ~10-20% of production cost
- Warm Standby: ~30-50% of production cost
- Active-Active: 100%+ (double infrastructure + data transfer)

## CL8 — GitOps Model

**GitOps Principles:**
1. Infrastructure and applications defined declaratively in Git
2. Git is the single source of truth
3. Automated reconciliation brings reality to desired state
4. Pull-based deployment (cluster pulls from Git, not push)

**ArgoCD vs FluxCD:**
- **ArgoCD:** UI-first, application-centric, supports multiple Git repos per app, stronger ecosystem
- **FluxCD:** Kubernetes-native, Helm-focused, simpler model, better for Helm-heavy workflows

**Secrets Handling:**
- **Sealed Secrets (Bitnami):** Encrypt secrets with public key, store encrypted in Git
- **External Secrets Operator:** Fetch from Vault/AWS Secrets Manager/Azure Key Vault at runtime
- **Vault Agent Injector:** Mount secrets from HashiCorp Vault as volumes/env vars

**Drift Detection:**
- GitOps controllers continuously compare live state to Git
- Manual changes are detected as "drift"
- Options: Auto-revert (enforce Git), Alert-only (notify), or Ignore (for specific resources)

## CL10 — Service Account vs Workload Identity vs IRSA

| Concept | Description | Cloud |
|---------|-------------|-------|
| **Service Account** | Kubernetes identity for pods to authenticate to API server | All |
| **IRSA (IAM Roles for SA)** | AWS: Map K8s SA to IAM role via OIDC trust relationship | AWS |
| **Workload Identity** | GCP: Bind K8s SA to GCP SA via token exchange | GCP |
| **Azure Workload Identity** | Azure: Similar OIDC-based federation | Azure |

**Why Mounting Credentials is Bad:**
- Static credentials can be stolen from filesystem
- No automatic rotation
- Difficult to audit/track usage
- Violates principle of least privilege

**Workload Identity Federation Solution:**
- Pod requests short-lived JWT from K8s SA token endpoint
- Pod exchanges JWT for cloud credentials via OIDC federation
- Credentials are short-lived, scoped, and auditable
- No long-term secrets stored anywhere

## CL11 — Object vs Block vs File Storage

| Type | Interface | Use Case | Durability | Availability |
|------|-----------|----------|------------|--------------|
| **Object (S3/Blob)** | REST API, key-value | Static assets, backups, data lakes | 99.999999999% (11 9s) | 99.99% |
| **Block (EBS/Managed Disk)** | Block device (iSCSI) | Database data files, boot volumes | 99.999% | 99.9% (per AZ) |
| **File (EFS/Azure Files)** | NFS/SMB | Shared config, home dirs, media processing | 99.999999999% | 99.99% |

**When to Use Each:**
- **Object:** Immutable data, large files, distributed access, archival
- **Block:** Low-latency random I/O, database storage, boot volumes
- **File:** Shared access across multiple instances, legacy app compatibility

## CL12 — Zero-Trust Kubernetes Architecture

**Components:**
1. **Network Policies:** Restrict pod-to-pod communication (default-deny + explicit allow)
2. **Service Mesh (Istio/Linkerd):** mTLS between services, fine-grained traffic policies
3. **Pod Identity:** Workload identity for cloud resource access (no mounted credentials)
4. **Admission Controllers:**
   - OPA/Gatekeeper: Policy enforcement (e.g., no privileged containers)
   - Kyverno: Native K8s policy engine
5. **Image Security:**
   - Cosign/Notary: Sign images
   - Admission webhook: Verify signatures before deployment
6. **Runtime Security:** Falco for anomaly detection (e.g., unexpected processes, network connections)
7. **Secrets Management:** External Secrets Operator + Vault/AWS Secrets Manager

**vs Traditional Perimeter Model:**
- **Perimeter:** Trust inside, verify at edge
- **Zero-Trust:** Verify everything, never trust, least privilege everywhere
- **Zero-Trust assumes breach; perimeter assumes protection**

## CL13 — CDN (Content Delivery Network)

**How CDN Works:**
1. User requests content
2. DNS resolves to nearest edge location
3. Edge cache serves content if hit, otherwise fetches from origin
4. Content cached at edge for subsequent requests

**Cloud-Native CDN Services:**
- AWS CloudFront
- Azure CDN
- Google Cloud CDN

**When to Use CDN:**
- Static assets (images, CSS, JS)
- Global user base with latency sensitivity
- High traffic spikes (DDoS mitigation, viral content)
- Video streaming

**When NOT to Use CDN:**
- Dynamic, personalized content
- Low-traffic internal applications
- Real-time data that can't be cached

## CL14 — Availability Zones and Regions

**Regions:** Geographically separate areas (e.g., us-east-1, eu-west-1). Each region has multiple AZs.

**Availability Zones:** Isolated datacenter locations within a region. Each AZ has independent power, cooling, networking.

**Why Deploy Across Multiple AZs:**
- Fault tolerance (single AZ failure doesn't take down application)
- Lower latency for users in different locations within region
- Compliance requirements

**Zonal vs Regional Resources:**
- **Zonal:** Exist in one AZ only (e.g., EC2 instance, EBS volume)
- **Regional:** Span multiple AZs (e.g., RDS Multi-AZ, ELB, S3 bucket)

## CL16 — Cloud Identity Services

| Concept | Description |
|---------|-------------|
| **User** | Human identity with permanent credentials |
| **Group** | Collection of users for policy assignment |
| **Role** | Temporary, assumable identity with specific permissions |

- Grant minimum permissions necessary for a task
- Apply via:
  - Role-based access control (RBAC)
  - Just-in-time access (temporary elevation)
  - Resource-level permissions (not wildcard *)
  - Regular permission audits
  - Separate prod/dev environments with different access levels

## CL17 — Serverless Computing

**Comparison:**
- **AWS Lambda:** Most mature, largest ecosystem, 15 min timeout
- **Azure Functions:** Strong .NET integration, Durable Functions for stateful workflows
- **Google Cloud Functions:** Tight GCP integration, simpler pricing model

**Cold Starts:**
- **Definition:** Delay when function scales from zero; includes container spin-up + code initialization
- **Why They Matter:** Impact latency-sensitive applications (APIs, real-time processing)
- **Mitigation:** Provisioned concurrency, keep-alive pings, smaller deployment packages

**When Serverless is a Poor Fit:**
- Long-running processes (>15 min)
- Consistent high traffic (VMs may be cheaper)
- Applications requiring specific OS libraries
- Stateful applications needing persistent connections
- ML model inference with large model files

## CL18 — Kubernetes Ingress Options

| Option | Description | TLS Termination |
|--------|-------------|-----------------|
| **Ingress Resource** | K8s native, HTTP routing, annotations for LB | Ingress controller (edge) |
| **Gateway API** | Next-gen, more expressive, supports TCP/UDP | Gateway (edge) or Route (per-route) |
| **Cloud LB Annotations** | Direct cloud LB provisioning via annotations | Cloud LB (edge) |
| **Service Mesh Ingress** | Istio IngressGateway, etc. | Mesh (edge or per-service) |

**TLS Termination Layers:**
- **Edge:** At ingress point (most common, efficient)
- **Per-Route:** Different certs per route
- **Per-Service:** mTLS through service mesh

**Gateway API over Ingress When:**
- Need TCP/UDP routing (not just HTTP)
- Require more complex routing rules
- Want standardized API across implementations
- Need observability and policy features built-in

## CL19 — Cost Optimization Strategy ($80K/month)

**Compute Optimization:**
- **Reserved Instances/Savings Plans:** 1-3 year commitments, 30-72% savings for baseline workloads
- **Spot/Preemptible:** Up to 90% savings for fault-tolerant, stateless workloads
- **Right-Sizing:** Use CloudWatch/Azure Monitor recommendations; downsize over-provisioned instances

**Storage Optimization:**
- **S3 Intelligent-Tiering:** Automatic tiering based on access patterns

**Process Implementation:**
1. **Tagging Strategy:** Required tags for Cost Center, Environment, Owner
2. **Cost Allocation Tags:** Enable showback reports per team
3. **Budgets & Alerts:** Set monthly budgets with 80%/100% alerts
4. **FinOps Review:** Monthly cross-team cost review meeting
5. **Automated Reports:** AWS Cost Explorer / Azure Cost Management dashboards

**Tools:**
- Native: AWS Cost Explorer, Azure Cost Management, GCP Billing Reports
- Third-party: CloudHealth, Cloudability, Kubecost (for K8s)

**Showback vs Chargeback:**
- **Showback:** Report costs to teams (awareness)
- **Chargeback:** Bill teams actual costs (accountability)

## CL20 — Multi-Cloud Strategy

**Abstraction Layers:**
- **Kubernetes:** Common runtime (EKS, AKS, GKE)
- **Terraform:** Infrastructure as Code (multi-cloud providers)
- **Helm:** Package management for applications
- **Crossplane:** Cloud resources as K8s objects

**Networking Between Clouds:**
- AWS Direct Connect + Azure ExpressRoute
- Third-party interconnect providers (Megaport, Equinix Fabric)
- Site-to-site VPN (simpler, less performant)

**Identity Federation:**
- Central IdP (Okta, Azure AD) federates to both clouds
- SAML/OIDC for single sign-on

**Real-World Trade-Offs:**
- **Complexity:** 2x operations teams, 2x tooling, 2x learning curves
- **Cost:** No bulk discounts, data transfer costs between clouds
- **Skills:** Need expertise in both platforms
- **Limited Benefits:** Most "avoid lock-in" benefits are theoretical

**When Multi-Cloud is Justified:**
- Regulatory requirements (data residency)
- Disaster recovery across providers
- Specific service advantages (e.g., AWS AI/ML + Azure enterprise integration)
- Acquisition scenarios with existing investments

**When It's Unnecessary:**
- Small to medium organizations
- No specific compliance requirements
- Team lacks multi-cloud expertise
- Cost of complexity exceeds benefits

## OT2 — IT vs OT Networks

| Aspect | IT | OT |
|--------|----|----|
| **Priority** | Confidentiality, Integrity | Availability, Safety |
| **Patching** | Regular, automated | Scheduled during maintenance windows |
| **Uptime Expectation** | 99.9% acceptable | 99.999% required |
| **Lifecycle** | 3-5 years | 15-20+ years |
| **Protocols** | TCP/IP, HTTP, SQL | Modbus, OPC, Profinet |

**Why Standard IT Patching Fails in OT:**
- Reboots may cause production stoppages
- Legacy systems may not support modern patches
- Vendor patches may not be tested for safety impact
- Patching windows are limited to planned maintenance

## OT3 — DMZ (IDMZ) Between IT and OT

**Purpose:** Security boundary allowing controlled data flow while preventing direct IT-to-OT connectivity.

**Traffic Allowed (OT → IT direction):**
- Historian data exports (batch, not real-time)
- Alarms and events (filtered, aggregated)
- Asset inventory data
- Time synchronization (NTP, one-way)

**Traffic NOT Allowed:**
- Direct IT → OT control commands
- IT-initiated connections to Level 1-2
- Unfiltered file transfers

**Why Direct L4 → L1 is Dangerous:**
- Malware from IT can reach control systems
- No visibility or filtering of traffic
- Violates defense-in-depth principle
- Single point of failure for security

| **EtherNet/IP (CIP)** | 1-2 | Rockwell Automation, implicit/explicit messaging |
| **PROFINET** | 1-2 | Siemens, real-time Ethernet for automation |
| **MQTT** | 3-4 | Publish-subscribe, lightweight, IoT/analytics |

## OT5 — Data Diode vs Firewall

**Data Diode:**
- Hardware device allowing one-way data flow only
- Uses physical separation (optical isolator)
- Cannot be configured to allow reverse traffic
- Used when absolute one-way guarantee is required

**Firewall:**
- Software/hardware filtering bidirectional traffic
- Can be misconfigured or compromised
- Allows return traffic by design

**When to Use Data Diode:**
- SCADA to IT data export (never reverse)
- Safety-critical systems
- Regulatory requirements for one-way flow

**Limitation vs Firewall:**
- No bidirectional communication possible
- Cannot support queries from IT side
- More expensive
- No filtering capabilities (all or nothing)

## OT7 — IEC 62443 Zones and Conduits

**Zone:** Collection of assets with common security requirements (e.g., same safety level, same function).

**Conduit:** Communication path between zones with defined security controls.

**Zone-and-Conduit Design:**

```
Zone 0 (Corporate): ERP, email, general IT
    ↓ Conduit A (Firewall, strict rules)
Zone 1 (Engineering): Engineering workstations, configuration tools
    ↓ Conduit B (Firewall, vendor access only)
Zone 2 (SCADA): SCADA servers, HMIs, historian
    ↓ Conduit C (Firewall, protocol filtering)
Zone 3 (Control): PLCs, controllers
    ↓ Conduit D (Firewall, minimal rules)
Zone 4 (Safety): SIS network (air-gapped or separate VLAN)
```

**Zone Definition Criteria:**
- Safety integrity level (SIL)
- Business criticality
- Asset type and age
- Network connectivity requirements

## OT8 — Network Segmentation Strategy for Flat OT Network

**Current State:** Flat Layer 2, 200 PLCs, 30 HMIs, SCADA, historian

**Segmentation Design:**
```
VLAN 10: Engineering Workstations (Level 3.5)
VLAN 20: SCADA Servers & HMIs (Level 3)
VLAN 30: Historian (Level 3)
```

## OT9 — SIS vs BPCS

**BPCS (Basic Process Control System):**
- Normal process control
- Maintains process within operating parameters
- IEC 61131 standards

**SIS (Safety Instrumented System):**
- Safety-critical shutdown system
- Activates when process goes unsafe
- IEC 61511 standards
- SIL (Safety Integrity Level) rated

**Why SIS Must Be Isolated:**
- Ransomware on BPCS could disable safety shutdowns
- SIS failure could lead to catastrophic incidents
- Different lifecycle and maintenance requirements
- Regulatory requirements (OSHA, functional safety standards)

**If Ransomware Reaches SIS:**
- Safety shutdowns may not activate
- Could lead to equipment damage, environmental release, or人员伤亡
- Plant must be manually shut down (emergency procedure)
- Recovery requires complete SIS rebuild and validation

## OT12 — Incident Response for Water Treatment Facility

**Detection:**
- Network monitoring: Nozomi, Claroty, or Dragos for OT-specific IDS
- Anomaly detection: Baseline normal traffic, alert on deviations
- Asset inventory: Know what's connected and what's normal

**Response Plan:**
1. **Confirm:** Verify alert is not false positive
2. **Contain:** Isolate affected segment (don't power off!)
3. **Assess:** Determine scope with control room operator
4. **Coordinate:** Plant operator decides operational impact
5. **Eradicate:** Remove threat during planned maintenance
6. **Recover:** Restore from clean backups, validate

**Plant Operator Role:**
- Decides if isolation impacts safe operations
- Authorizes any actions affecting production
- Communicates with management and regulators
- May need to manually override automated controls

**Critical Consideration:** Never reboot or disconnect OT systems without operator approval — could cause unsafe conditions.

## OT17 — Analog vs Digital Signals

**Analog Signals:**
- **4-20mA:** Current loop, most common for process instrumentation
- **0-10V:** Voltage signal, shorter distances

**Digital Signals:**
- Discrete on/off (0V/24V)
- Communication protocols (Modbus, Profibus)

**Why 4-20mA Preferred Over 0-20mA:**
- 4mA "live zero" allows wire break detection (0mA = broken wire)
- Can power the transmitter (loop-powered devices)
- Less susceptible to voltage drop over distance
- Industry standard for process instrumentation

## OT18 — OT Asset Inventory

**Why Foundation of OT Security:**
- Can't protect what you don't know exists
- Baseline for anomaly detection
- Patch management requires knowing what needs patching
- Incident response needs asset context

**Discovery Techniques:**
- **Passive Network Monitoring:** Nozomi, Claroty, Dragos (safe, no impact)
- **Active Scanning:** Nmap, Lansweeper (DANGEROUS in OT)

**Why Active Scanning is Dangerous:**
- Can crash legacy devices
- May trigger unintended actions
- Can disrupt real-time communications
- Some devices don't handle unexpected traffic well

## OT19 — MITRE ATT&CK for ICS

**Five Tactics with Examples:**

1. **Reconnaissance (TA0043):**
   - T1488: External Remote Services — Scanning for exposed HMIs

2. **Resource Development (TA0042):**
   - T1584: Compromise Account — Purchasing vendor credentials

3. **Initial Access (TA0001):**
   - T1190: Exploit Public-Facing Application — Vulnerable web server

4. **Execution (TA0002):**
   - T1059: Command and Scripting Interpreter — PowerShell on engineering workstation

5. **Collection (TA0009):**
   - T1005: Data from Local System — Stealing PLC configuration files

**vs Enterprise ATT&CK:**
- ICS-specific techniques (e.g., modify PLC logic, inject HMI commands)
- Different impact considerations (safety vs data loss)
- Industry-specific protocols and systems

**Using for Gap Assessment:**
- Map current controls to each technique
- Identify gaps where no detection/prevention exists
- Prioritize based on likelihood and impact
- Test with purple team exercises

## OT20 — Converged IT/OT SOC Design

**Log Collection from OT:**
- Passive network taps (no impact on operations)
- OT-specific agents (lightweight, read-only)
- Avoid active polling of control systems

**SIEM Integration:**
- Separate OT index/stream initially
- OT-specific parsers for protocols (Modbus, OPC)
- Correlation rules spanning IT and OT data

**OT-Specific Detection Rules:**
- Unauthorized PLC program changes
- Unusual HMI access patterns
- Protocol anomalies (e.g., Modbus write to read-only register)
- Off-hours engineering workstation activity

**Alert Triage Workflow:**
1. IT analyst initial triage
2. Escalate to OT engineer for validation
3. Plant operator consulted for operational impact
4. Joint response decision

**Staffing:**
- IT analysts: Initial triage, IT-side investigations
- OT engineers: Validation, OT-specific response
- Joint training programs

**False Positive Challenge:**
- OT processes have legitimate unusual patterns
- Baseline during normal operations first
- Tune rules with OT engineer input
- Start with high-confidence rules only

**Unauthorized Firmware Change Alert:**
1. **Verify:** Check if change was authorized (maintenance window?)
2. **Contain:** Isolate affected PLC if change is malicious
3. **Assess:** Compare firmware hash with known good version
4. **Respond:** Restore from backup, investigate source
5. **Learn:** Update detection rules, review access controls

**Key Principle:** OT security decisions must consider operational safety first — a false positive that shuts down production is as bad as a missed detection.
