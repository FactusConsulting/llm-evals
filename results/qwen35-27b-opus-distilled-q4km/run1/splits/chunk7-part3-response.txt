Here are the detailed answers to the infrastructure and software engineering questions.

**OP1 — Easy: Explain the difference between a hypervisor Type 1 (bare-metal) and Type 2 (hosted). Give 2 examples of each.**

*   **Type 1 (Bare-Metal):** The hypervisor installs directly on the physical hardware. It manages the hardware resources and allocates them to virtual machines (VMs). It has no underlying operating system, resulting in lower overhead and higher performance.
    *   *Examples:* VMware ESXi, Microsoft Hyper-V, Citrix Hypervisor (XenServer), Proxmox VE.
*   **Type 2 (Hosted):** The hypervisor is installed as an application on top of an existing host operating system (like Windows or Linux). The host OS manages the hardware, and the hypervisor requests resources from the OS. This introduces more overhead but is easier to set up for desktop virtualization.
    *   *Examples:* VMware Workstation, Oracle VirtualBox, Parallels Desktop.

**OP2 — Easy: What is a SAN vs NAS? When would you use each? What protocols does each typically use?**

*   **SAN (Storage Area Network):** A dedicated high-speed network that provides block-level storage access. The server sees the storage as a raw local disk (LUN).
    *   *Use Case:* High-performance databases (SQL), virtualization clusters requiring low latency, and applications needing raw block access.
    *   *Protocols:* Fibre Channel (FC), iSCSI, FCoE.
*   **NAS (Network Attached Storage):** A file-level storage device connected to a network. Clients access files over the network using file-sharing protocols.
    *   *Use Case:* File sharing, home directories, backups, and general-purpose file storage.
    *   *Protocols:* NFS (Linux/Unix), SMB/CIFS (Windows).

**OP3 — Medium: Explain a 3-tier network architecture (core/distribution/access). Why is leaf-spine preferred in modern data centers? What problem does it solve that 3-tier doesn't?**

*   **3-Tier Architecture:**
    *   **Access Layer:** Connects end devices (servers, PCs) to the network.
    *   **Distribution Layer:** Aggregates access switches, handles routing, filtering, and QoS.
    *   **Core Layer:** High-speed backbone connecting distribution layers; focuses purely on speed and availability.
*   **Leaf-Spine Preference:** Modern data centers prefer leaf-spine because it is a flat, two-tier topology. Every leaf switch connects to every spine switch.
*   **Problem Solved:** 3-tier architectures suffer from **oversubscription** and **latency** when traffic moves between access switches (East-West traffic), as it must traverse multiple hops (Access -> Distribution -> Core -> Distribution -> Access). Leaf-spine guarantees **non-blocking, equal-cost multi-path (ECMP)** routing with only two hops between any two servers, optimizing for the high East-West traffic patterns of virtualization and cloud computing.

**OP4 — Medium: You need to design a highly available Proxmox cluster with shared storage. Describe the architecture covering: node count, quorum, fencing, shared storage options (Ceph, iSCSI, NFS), and what happens during a node failure.**

*   **Architecture:**
    *   **Node Count:** Minimum of 3 nodes to ensure quorum is maintained if one fails.
    *   **Quorum:** Uses Corosync/Pacemaker. A majority (N/2 + 1) of nodes must be online to prevent split-brain scenarios.
    *   **Fencing:** STONITH (Shoot The Other Node In The Head) is mandatory. If a node hangs, the cluster must physically cut power or reboot it to prevent data corruption on shared storage.
*   **Shared Storage Options:**
    *   **Ceph:** Best for Proxmox. Distributed object/block store running on the cluster nodes themselves. No external hardware required.
    *   **iSCSI:** Good for dedicated hardware SANs. Lower latency than NFS but requires external hardware.
    *   **NFS:** Easiest to set up but generally lower performance and higher risk of data corruption if the network drops compared to block storage.
*   **Node Failure:** If a node fails, the cluster detects the loss of heartbeat. If fencing is configured, the failed node is powered off. VMs running on that node are automatically restarted on surviving nodes (HA feature) using the shared storage.

**OP5 — Medium: What is VLAN trunking? Explain 802.1Q tagging. A server has a single NIC but needs to be on 3 VLANs — how do you configure this on Linux?**

*   **VLAN Trunking:** A method of carrying traffic for multiple VLANs over a single physical link (usually between switches or a switch and a server).
*   **802.1Q Tagging:** An Ethernet frame modification standard. It inserts a 4-byte tag into the Ethernet header containing a 12-bit VLAN ID (VID). This allows the receiving switch to identify which VLAN the frame belongs to.
*   **Linux Configuration:** You create virtual sub-interfaces for each VLAN.
    *   *Command:* `ip link add link eth0 name eth0.10 type vlan id 10` (Repeat for VLANs 20 and 30).
    *   *IP Assignment:* Assign IP addresses to `eth0.10`, `eth0.20`, and `eth0.30` respectively. The switch port connected to the server must be configured as a **Trunk** allowing those specific VLANs.

**OP6 — Medium: Explain the difference between RAID 1, RAID 5, RAID 6, RAID 10, and RAID Z2 (ZFS). You have 6 drives and need to balance performance, capacity, and fault tolerance for a database server — which do you choose and why?**

*   **RAID 1:** Mirroring. 50% capacity. Fast reads, slow writes. Tolerates 1 drive failure per pair.
*   **RAID 5:** Striping with distributed parity. (N-1) capacity. Tolerates 1 drive failure. Write penalty is high due to parity calculation.
*   **RAID 6:** Striping with double distributed parity. (N-2) capacity. Tolerates 2 drive failures. High write penalty.
*   **RAID 10:** Mirror of stripes. 50% capacity. Tolerates multiple failures (depending on which drives fail). Excellent performance (reads/writes).
*   **RAID Z2 (ZFS):** Similar to RAID 6 but with copy-on-write and checksumming. Tolerates 2 drive failures.
*   **Selection:** **RAID 10**.
    *   *Reasoning:* For a database, **performance** (especially random writes) and **reliability** are paramount. RAID 5/6/Z2 have significant write penalties and long rebuild times that risk a second drive failing during reconstruction. RAID 10 offers the best read/write performance and faster rebuilds. With 6 drives, you get 3 drives worth of usable space, which is acceptable for a database workload.

**OP7 — Hard: Design a DNS architecture for a 500-person enterprise with: internal Active Directory, a DMZ with public-facing services, split-horizon DNS, and DNSSEC on the external zone. Cover: recursive resolvers, authoritative servers, forwarders, conditional forwarding, and what happens when a laptop moves between office and VPN.**

*   **Architecture:**
    *   **Internal:** Two Windows Server DNS instances (AD-integrated) acting as Recursive Resolvers and Authoritative for internal zones (e.g., `corp.local`).
    *   **DMZ:** Two Linux/Windows DNS servers acting as Authoritative for public zones (e.g., `example.com`).
    *   **Split-Horizon:** The internal DNS servers host `example.com` as an internal zone (pointing to internal IPs) and forward external queries to upstream resolvers. The DMZ servers host `example.com` pointing to public IPs.
    *   **DNSSEC:** Enabled on the DMZ authoritative servers. The internal recursive resolvers validate DNSSEC signatures for external queries.
*   **Forwarding:** Internal resolvers forward unknown queries to ISP DNS or public resolvers (e.g., 1.1.1.1).
*   **Conditional Forwarding:** Internal DNS forwards queries for specific partner domains directly to partner DNS IPs.
*   **Laptop Mobility:**
    *   *Office:* Laptop gets internal DNS via DHCP. Queries `mail.example.com` -> Internal DNS -> Internal IP.
    *   *VPN:* Laptop connects via VPN, receives internal DNS via DHCP override. Same behavior as office.
    *   *Remote (No VPN):* Laptop uses public DNS. Queries `mail.example.com` -> Public DNS -> DMZ Authoritative -> Public IP (Load Balancer).

**OP8 — Hard: Explain the PKI chain of trust from root CA to end-entity certificate. You need to deploy an internal PKI for your organization. Cover: root CA (offline), subordinate/issuing CA, CRL vs OCSP, certificate templates, and auto-enrollment. What are the consequences of a compromised subordinate CA vs a compromised root CA?**

*   **Chain of Trust:** Root CA (Self-Signed) -> Subordinate CA (Signed by Root) -> End-Entity Certificate (Signed by Subordinate). Clients trust the Root; they verify the chain up to the Root.
*   **Deployment:**
    *   **Root CA:** Installed on an air-gapped machine. Used *only* to sign the Subordinate CA. Never issues end-entity certs.
    *   **Subordinate CA:** Online, connected to the network. Issues certificates to users/devices.
    *   **Revocation:** Use **OCSP** (Online Certificate Status Protocol) for real-time checking, backed by **CRL** (Certificate Revocation List) as a fallback.
    *   **Templates:** Define key usage, validity periods, and SANs (e.g., "Web Server," "User Authentication").
    *   **Auto-Enrollment:** Group Policy Objects (GPO) push settings to domain-joined machines to automatically request/renew certs based on templates.
*   **Compromise Consequences:**
    *   **Subordinate CA:** You revoke the Subordinate CA certificate on the Root. All certs issued by that Subordinate become invalid immediately. You generate a new Subordinate CA. Minimal impact on the Root's trust.
    *   **Root CA:** Catastrophic. The Root must be retired. A new Root CA must be generated and distributed to every device/browser in the organization (and potentially partners). All existing certificates become untrusted.

**OP9 — Hard: You're consolidating 5 remote offices into a hub-and-spoke WAN. Compare: MPLS, IPsec VPN over internet, SD-WAN, and WireGuard mesh. Cover: cost, reliability, latency, management complexity, and security posture. Which would you recommend for a company with 50 users per site and latency-sensitive VoIP?**

*   **Comparison:**
    *   **MPLS:** High cost, high reliability (SLA), low latency, complex management, secure by design (private network).
    *   **IPsec VPN:** Low cost, variable reliability (internet dependent), variable latency, moderate complexity, secure (encrypted).
    *   **SD-WAN:** Moderate cost, high reliability (path selection), optimized latency, low management complexity (centralized), secure (encrypted).
    *   **WireGuard Mesh:** Low cost, variable reliability, low latency (efficient protocol), low complexity (config files), secure.
*   **Recommendation:** **SD-WAN**.
    *   *Reasoning:* For VoIP, latency and jitter are critical. SD-WAN allows you to use cheaper broadband links but intelligently routes traffic. It can detect packet loss on one link and switch to another instantly. It supports QoS prioritization for VoIP traffic better than standard IPsec. It is more cost-effective than MPLS while offering better reliability than a simple IPsec tunnel.

**OP10 — Medium: What is iDRAC/iLO/IPMI? Why is out-of-band management critical? What happens if your IPMI interface is exposed to the internet?**

*   **Definitions:**
    *   **IPMI (Intelligent Platform Management Interface):** The standard protocol for out-of-band management.
    *   **iDRAC:** Dell's implementation of IPMI.
    *   **iLO:** HPE's implementation of IPMI.
*   **Criticality:** Out-of-band (OOB) management allows administrators to control a server (power cycle, view console, install OS) even if the operating system is crashed, frozen, or the network cable is unplugged. It operates on a separate network interface.
*   **Exposure Risk:** If the IPMI interface is exposed to the internet without strict firewalling/MFA:
    *   Attackers can brute-force default credentials (often weak).
    *   They can gain full control of the hardware, including the ability to **mount ISO images** to install malware, **reboot the server** (DoS), or **exfiltrate data** via the virtual console. It is a high-value target for ransomware groups.
