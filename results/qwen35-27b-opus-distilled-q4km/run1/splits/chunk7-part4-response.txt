**OP11 — Medium: Explain the difference between LVM, LVM-Thin, and ZFS. When would you use each? What are the snapshot semantics for each?**

*   **LVM (Logical Volume Manager):** A standard Linux subsystem that abstracts physical storage devices into logical volumes. It allows for resizing volumes, moving data between physical disks, and creating snapshots.
    *   *Use Case:* Standard Linux deployments requiring flexible volume management without the overhead of a full filesystem stack like ZFS.
    *   *Snapshot Semantics:* **Copy-on-Write (CoW).** When a snapshot is taken, the original data blocks are preserved. When the original volume is modified, the old data is copied to the snapshot volume before being overwritten. This requires free space in the snapshot volume equal to the amount of data changed.
*   **LVM-Thin:** An extension of LVM that provides thin provisioning. It allows you to allocate more logical space than physically exists, assuming not all space will be used simultaneously.
    *   *Use Case:* Virtualization environments (like KVM) where you want to overcommit storage and avoid wasting space on empty files.
    *   *Snapshot Semantics:* **Copy-on-Write (CoW).** Similar to standard LVM, but snapshots are extremely lightweight (near-zero space initially) because they share the same underlying data blocks until modified.
*   **ZFS (Zettabyte File System):** A combined filesystem and logical volume manager. It manages data integrity (checksums), compression, deduplication, and snapshots natively.
    *   *Use Case:* High-integrity storage, databases, and environments requiring advanced features like self-healing, compression, and easy replication.
    *   *Snapshot Semantics:* **Copy-on-Write (CoW).** ZFS never modifies data in place. When data is written, it is written to a new location, and the pointer is updated. Snapshots are simply immutable pointers to the old data blocks. They are space-efficient and instantaneous.

**OP12 — Hard: You have a 3-node Proxmox cluster with Ceph storage and need to survive a complete site failure. Design a stretch cluster or DR strategy. Cover: Ceph CRUSH rules, monitor placement, network latency requirements, and the split-brain problem. Why is 2-site Ceph generally a bad idea without a tiebreaker?**

*   **Design Strategy:** A true "Stretch Cluster" in Ceph requires a minimum of 3 failure domains (sites) to maintain quorum if one site fails completely. With only 2 sites, you risk split-brain.
*   **Architecture:**
    *   **Site A:** 2 Ceph Nodes.
    *   **Site B:** 2 Ceph Nodes.
    *   **Tiebreaker (Site C):** A lightweight "Quorum Node" (or a third physical site with 1 node) that holds no data but participates in the monitor quorum.
*   **Ceph CRUSH Rules:** Configure a custom CRUSH map with a `host` type and a `site` type. Set the `replica_size` to 3 and `min_size` to 2. Configure the rule to place replicas across different `site` types (e.g., `type site`). This ensures one replica is in Site A, one in Site B, and one in Site C (or distributed across the 4 data nodes if using a specific stretch topology, but 3 sites is safer for quorum).
*   **Monitor Placement:** Ceph monitors (MONs) must be placed to ensure quorum. With 2 sites, you cannot have a majority in one site if the other fails. You need an odd number of monitors (e.g., 3). Place 1 in Site A, 1 in Site B, and 1 in the Tiebreaker site.
*   **Network Latency:** Ceph is sensitive to latency. For synchronous replication (stretch), latency between sites should ideally be **< 5ms** (preferably < 2ms) to avoid performance degradation and timeout issues.
*   **Split-Brain & The 2-Site Problem:**
    *   **Split-Brain:** Occurs when the network partitions, and both sides believe they are the active cluster. Both might try to write data, leading to corruption.
    *   **Why 2-Site is Bad:** Ceph uses a quorum mechanism (majority rule). If you have 2 sites with equal weight (e.g., 2 nodes each), and the link between them fails, neither side has a majority (2 vs 2). The cluster goes down on both sides to prevent split-brain. To survive a site failure, you need a **tiebreaker** (a third site or node) to tip the scale (2+1 vs 2), allowing the majority site to stay online.

**OP13 — Easy: What is DHCP and how does the DORA process work? What happens when a DHCP server is unavailable and a Windows client's lease expires?**

*   **DHCP (Dynamic Host Configuration Protocol):** A network management protocol used to automatically assign IP addresses and other communication parameters to devices on a network.
*   **DORA Process:**
    1.  **Discover:** Client broadcasts a DHCPDISCOVER message ("I need an IP").
    2.  **Offer:** DHCP server responds with a DHCPOFFER (proposing an IP).
    3.  **Request:** Client broadcasts a DHCPREQUEST (accepting the offer).
    4.  **Acknowledge:** Server sends a DHCPACK, finalizing the lease.
*   **Lease Expiry & Unavailable Server:** If the lease expires and the server is unreachable, the Windows client enters **APIPA (Automatic Private IP Addressing)** mode. It assigns itself a link-local IP address in the range **169.254.0.0/16**. The client will have no gateway and cannot communicate outside its local subnet.

**OP14 — Easy: Explain the difference between a managed switch and an unmanaged switch. What features does a managed switch provide that are important in an enterprise environment?**

*   **Unmanaged Switch:** A "plug-and-play" device. It forwards traffic based on MAC addresses automatically. No configuration interface.
*   **Managed Switch:** Allows network administrators to monitor and configure the device.
*   **Enterprise Features:**
    *   **VLANs (Virtual LANs):** Segments traffic logically for security and broadcast control.
    *   **QoS (Quality of Service):** Prioritizes critical traffic (e.g., VoIP) over bulk data.
    *   **Port Mirroring (SPAN):** Copies traffic from one port to another for monitoring/sniffing.
    *   **STP (Spanning Tree Protocol):** Prevents network loops in redundant topologies.
    *   **Link Aggregation (LACP):** Combines multiple physical ports into one logical high-bandwidth link.
    *   **SNMP Monitoring:** Allows centralized monitoring of health and traffic stats.

**OP15 — Easy: What is NTP and why is accurate time synchronization critical in an on-premise environment? What can go wrong when clocks drift between servers in a cluster?**

*   **NTP (Network Time Protocol):** The standard protocol for synchronizing clock times of computer systems over packet-switched, variable-latency data networks.
*   **Criticality:**
    *   **Logging & Forensics:** Logs rely on timestamps to reconstruct events. Drifted clocks make troubleshooting impossible.
    *   **Authentication:** Kerberos and SSL/TLS certificates rely on accurate time. If clocks drift too far, authentication fails.
    *   **Distributed Systems:** Databases (like PostgreSQL or Ceph) and message queues rely on time for ordering events and consistency.
*   **Consequences of Drift:**
    *   **Replication Failures:** Database replicas may reject updates.
    *   **Certificate Errors:** "Certificate not yet valid" or "Certificate expired" errors.
    *   **Data Corruption:** In distributed ledgers or file systems, out-of-order writes can corrupt data integrity.

**OP16 — Easy: What is the difference between a physical server, a virtual machine, and a container? When would you run a workload directly on bare metal instead of virtualizing it?**

*   **Physical Server (Bare Metal):** A single operating system running directly on the hardware. Full access to CPU, RAM, and I/O.
*   **Virtual Machine (VM):** An emulated computer system that runs an OS on top of a Hypervisor. It virtualizes hardware resources. Heavyweight (includes full OS kernel).
*   **Container:** A lightweight, standalone executable package that includes everything needed to run a piece of software (code, runtime, system tools, libraries). Containers share the host OS kernel but isolate processes.
*   **When to use Bare Metal:**
    *   **High Performance/Low Latency:** Database clusters (e.g., Oracle RAC, high-frequency trading) where virtualization overhead is unacceptable.
    *   **GPU Passthrough:** Machine Learning workloads requiring direct access to specific GPU hardware without virtualization tax.
    *   **Licensing:** Some software licenses are cheaper or required on bare metal.
    *   **Legacy Hardware Dependencies:** Applications requiring specific hardware interrupts or drivers not supported by hypervisors.

**OP17 — Easy: Explain the difference between a UPS (Uninterruptible Power Supply) and a generator in a data center context. Why do you need both? What is the role of an ATS (Automatic Transfer Switch)?**

*   **UPS:** Provides immediate, short-term backup power (battery) to bridge the gap between utility failure and generator startup. It also conditions power (filters surges/spikes). Runtime: Minutes.
*   **Generator:** Provides long-term backup power using fuel (diesel/natural gas). Runtime: Hours/Days (limited by fuel).
*   **Why Both:** The UPS handles the instant outage (0ms transfer) and protects against power quality issues. The generator handles prolonged outages. The UPS buys time for the generator to start (which takes 10-30 seconds).
*   **ATS (Automatic Transfer Switch):** A device that automatically transfers an electrical load from a primary power source (utility) to an emergency source (generator) when the primary fails. It ensures the generator is not back-fed into the utility grid (islanding).

**OP18 — Medium: Explain the difference between active-passive and active-active clustering for high availability. You have a pair of Linux servers running a PostgreSQL database — describe how you would implement HA using Pacemaker/Corosync, covering fencing (STONITH), virtual IPs, and failover behavior.**

*   **Active-Passive:** One node handles all traffic (Active); the other sits idle (Passive) ready to take over. Simple, no data sync complexity during operation.
*   **Active-Active:** Both nodes handle traffic simultaneously. Requires load balancing and complex data synchronization (e.g., replication).
*   **PostgreSQL HA Implementation (Pacemaker/Corosync):**
    *   **Resources:** Define a `pgsql` resource (the database service) and an `IPaddr2` resource (Virtual IP).
    *   **Colocation:** Configure a constraint to ensure the DB and VIP run on the same node.
    *   **Ordering:** Configure the VIP to start *after* the DB starts and stop *before* the DB stops.
    *   **Fencing (STONITH):** Essential to prevent split-brain. If Node A fails, Pacemaker must physically cut power or isolate Node A (via iLO/iDRAC or a dedicated fence device) so it cannot corrupt the database while Node B takes over.
    *   **Failover:** If Node A (Active) fails, Corosync detects the loss of heartbeat. Pacemaker triggers STONITH on Node A, then migrates the `pgsql` and `IPaddr2` resources to Node B. Clients reconnect to the VIP, which is now on Node B.

**OP19 — Hard: You are designing the backup and recovery strategy for a 50-server on-premise environment. Cover: the 3-2-1 rule, RPO/RTO requirements, backup types (full/incremental/differential), deduplication, tape vs disk vs cloud offsite, immutable backups for ransomware protection, and how you test restores. What is the difference between backup and disaster recovery?**

*   **3-2-1 Rule:** Keep **3** copies of data, on **2** different media types, with **1** copy offsite.
*   **RPO/RTO:**
    *   **RPO (Recovery Point Objective):** Max acceptable data loss (e.g., 1 hour). Determines backup frequency.
    *   **RTO (Recovery Time Objective):** Max acceptable downtime (e.g., 4 hours). Determines recovery speed (instant VM recovery vs. tape restore).
*   **Backup Types:**
    *   **Full:** Backs up everything. Slow, high storage.
    *   **Incremental:** Backs up changes since last backup (any type). Fastest backup, slowest restore (needs chain).
    *   **Differential:** Backs up changes since last *Full*. Faster restore than incremental, grows over time.
*   **Deduplication:** Reduces storage by storing only unique data blocks. Critical for disk-based backups to save space and bandwidth.
*   **Media:**
    *   **Disk:** Fast, good for local backups and instant restores.
    *   **Tape:** Cheap, air-gapped (offline), good for long-term archival and ransomware protection.
    *   **Cloud:** Offsite by default, scalable, good for the "1 copy offsite" requirement.
*   **Immutable Backups:** Backups that cannot be modified or deleted for a set period (WORM - Write Once Read Many). Essential for ransomware; even if the attacker compromises the backup server, they cannot encrypt or delete the backups.
*   **Testing Restores:** A backup is useless if it doesn't restore. Schedule quarterly "fire drills" where a random server is restored to a sandbox environment to verify integrity and speed.
*   **Backup vs. DR:**
    *   **Backup:** Copying data for recovery of files or systems.
    *   **Disaster Recovery (DR):** The broader strategy and infrastructure to recover *operations* after a catastrophic event (e.g., site fire). DR includes backups, but also redundant sites, failover procedures, and communication plans.

**OP20 — Hard: Explain how 802.1X (port-based network access control) works in an enterprise wired network. Cover: the supplicant, authenticator, and authentication server roles; EAP methods (EAP-TLS vs PEAP); RADIUS; dynamic VLAN assignment; and what happens to a device that fails authentication. How does MAB (MAC Authentication Bypass) work for devices that don't support 802.1X?**

*   **Roles:**
    *   **Supplicant:** The client device (laptop, phone) requesting access.
    *   **Authenticator:** The network device (switch/AP) controlling physical access to the network.
    *   **Authentication Server:** Usually a RADIUS server that verifies credentials.
*   **Process:**
    1.  Supplicant connects to Authenticator.
    2.  Authenticator blocks traffic and requests authentication.
    3.  Supplicant sends credentials (via EAP) to Authenticator, which forwards them to the RADIUS server.
    4.  RADIUS validates and sends Accept/Reject to Authenticator.
    5.  Authenticator opens/closes the port.
*   **EAP Methods:**
    *   **EAP-TLS:** Uses mutual certificates (client and server). Most secure, requires PKI management on clients.
    *   **PEAP (Protected EAP):** Creates an encrypted TLS tunnel first, then authenticates the user (usually username/password) inside the tunnel. Easier to deploy than EAP-TLS.
*   **Dynamic VLAN Assignment:** Upon successful auth, the RADIUS server can send a VLAN ID attribute (e.g., `Tunnel-Private-Group-ID`). The switch places the port into that specific VLAN (e.g., "Guest" vs "Corp").
*   **Failed Authentication:** The port is placed into a "Guest" or "Quarantine" VLAN with restricted access (e.g., only to a splash page or patch server).
*   **MAB (MAC Authentication Bypass):** Used for "dumb" devices (printers, IoT) that don't support 802.1X. The switch reads the device's MAC address and sends it to the RADIUS server as the username/password. The RADIUS server checks if the MAC is allowed and assigns a VLAN. Less secure than 802.1X (MACs can be spoofed) but necessary for legacy hardware.
