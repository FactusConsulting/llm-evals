# AA11 — 12-Factor App Methodology

The 12-Factor App is a methodology for building software-as-a-service applications, originally defined by Heroku. It provides a set of best practices for building scalable, maintainable applications that run in cloud environments.

**Six Key Factors:**

1. **Codebase**: One codebase tracked in version control, many deploys. *Why it matters*: Ensures consistency across environments and enables reproducible deployments.

2. **Dependencies**: Explicitly declare and isolate dependencies. *Why it matters*: Prevents "works on my machine" problems and ensures reproducible builds.

3. **Config**: Store config in the environment. *Why it matters*: Separates code from configuration, enabling the same codebase to run in different environments (dev, staging, prod) without modification.

4. **Backing Services**: Treat backing services (databases, queues, caches) as attached resources. *Why it matters*: Enables easy swapping of services and supports the "12-factor" principle of treating infrastructure as disposable.

5. **Build, Release, Run**: Strictly separate build, release, and run stages. *Why it matters*: Ensures deterministic deployments and enables rollback capabilities.

6. **Stateless Processes**: Run app processes as stateless, share nothing. *Why it matters*: Enables horizontal scaling and rapid failover since any instance can handle any request.

# AA12 — Event-Driven vs Request-Driven Architecture

| Aspect | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
|--------|---------------------|---------------------------|
| **Coupling** | Loose coupling; producers don't know consumers | Tighter coupling; caller knows callee |
| **Scalability** | Excellent; consumers scale independently | Good; but synchronous bottlenecks possible |
| **Debugging** | Complex; distributed, asynchronous traces | Simpler; synchronous call stacks |
| **Ordering** | Per-partition ordering only | Request-response ordering guaranteed |
| **Failure Handling** | Retry with backoff, dead-letter queues | Immediate failure, retries by client |

**When to Choose Each:**

- **Event-Driven**: Real-time analytics, event sourcing, decoupled microservices, high-throughput data pipelines, systems requiring replayability.

- **Request-Driven**: Simple CRUD operations, synchronous user-facing APIs, systems requiring strong consistency, low-latency request-response patterns.

# AA13 — Load Balancers

A **load balancer** distributes incoming network traffic across multiple servers to ensure no single server becomes overwhelmed.

**Layer 4 (Transport Layer) Load Balancing:**
- Operates on IP addresses and ports
- Uses TCP/UDP information only
- Faster, lower overhead
- Cannot inspect HTTP headers or content

**Layer 7 (Application Layer) Load Balancing:**
- Operates on HTTP/HTTPS content
- Can inspect headers, cookies, URLs
- Enables content-based routing
- Higher overhead but more intelligent routing

**Layer 7 Required Use Case:**
API routing where `/api/v1/*` goes to service A and `/api/v2/*` goes to service B, or routing based on `Host` header for multi-tenant applications.

# AA14 — Message Queue vs Log-Based Broker

A **message queue** is a middleware component that enables asynchronous communication between services by storing messages until consumers are ready to process them.

**Message Queue (RabbitMQ):**
- Point-to-point or publish-subscribe patterns
- Messages are consumed and deleted
- Supports complex routing (exchanges, bindings)
- Better for task distribution and work queues

**Log-Based Broker (Kafka):**
- Append-only log with partitions
- Messages persist for retention period
- Multiple consumers can read same messages
- Better for event streaming, replay, and analytics

**When to Pick Each:**
- **RabbitMQ**: Task queues, complex routing requirements, message acknowledgment patterns
- **Kafka**: Event streaming, log aggregation, systems needing message replay, high-throughput scenarios

# AA15 — Containers vs Virtual Machines

A **container** is a lightweight, standalone package containing code, runtime, libraries, and system tools needed to run an application.

**Key Differences:**

| Aspect | Container | Virtual Machine |
|--------|-----------|-----------------|
| **Virtualization** | OS-level (shares host kernel) | Hardware-level (full OS) |
| **Size** | MBs | GBs |
| **Startup Time** | Seconds | Minutes |
| **Isolation** | Process-level | Hardware-level |
| **Overhead** | Minimal | Significant |

**Why Containers for Microservices:**
- Fast startup enables rapid scaling
- Small size allows high density
- Consistent environments across deployment stages
- Easy orchestration with Kubernetes
- Efficient resource utilization

# AA16 — Stateless vs Stateful Services

**Stateless Service**: Each request contains all information needed to process it; no client state stored server-side between requests.

**Stateful Service**: Maintains client state between requests (sessions, cached data, etc.)

**Why Stateless Scales Better:**
- Any instance can handle any request
- No session affinity required
- Easy to add/remove instances
- Simpler failure recovery

**Examples:**
- **Stateless**: REST API endpoint returning user profile (auth via JWT)
- **Stateful**: Shopping cart service storing cart items in memory

# AA17 — Object-Relational Mapper (ORM)

An **ORM** is a programming technique that maps object-oriented programming concepts to relational database operations, allowing developers to interact with databases using objects instead of SQL.

**Popular ORMs:**
- **Python**: SQLAlchemy, Django ORM
- **Java**: Hibernate, JPA
- **JavaScript**: TypeORM, Prisma
- **Go**: GORM

**Trade-offs:**

| ORM | Raw SQL |
|-----|---------|
| Faster development | More control |
| Type safety | Better performance |
| Portability across databases | Complex queries easier |
| Less boilerplate | No abstraction leaks |
| Potential N+1 queries | Explicit optimization |

# AA18 — Bulkhead Pattern

The **Bulkhead pattern** isolates resources so that failure in one component doesn't cascade to others, inspired by ship design where bulkheads prevent flooding from sinking the entire vessel.

**Relation to Resource Isolation:**
In microservices, bulkheads prevent a slow or failing service from exhausting all threads/connections, protecting the entire system.

**Implementation Examples:**

**Thread Pool Bulkhead:**
```python
# Separate thread pools per service
payment_pool = ThreadPool(max_workers=10)
inventory_pool = ThreadPool(max_workers=5)

def process_payment():
    return payment_pool.submit(payment_service.call)
```

**Separate Deployment Groups:**
```yaml
# Kubernetes - separate deployments with resource limits
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: payment
        resources:
          limits:
            memory: "256Mi"
            cpu: "500m"
```

# AA19 — OT vs CRDTs for Collaborative Editing

| Aspect | Operational Transformation (OT) | CRDTs |
|--------|--------------------------------|-------|
| **Consistency** | Eventual, requires central server | Strong eventual, decentralized |
| **Latency** | Lower (transform operations) | Higher (merge on sync) |
| **Complexity** | High (transform functions) | Medium (data structure design) |
| **Offline Support** | Poor (needs server for transforms) | Excellent (merge anytime) |

**Recommendation for Offline-First System:**

**Choose CRDTs** because:
1. **True offline editing**: Users can edit completely disconnected; changes merge automatically on reconnect
2. **No central coordination**: No server needed to transform operations
3. **Simpler conflict resolution**: Mathematical guarantees ensure convergence
4. **Peer-to-peer friendly**: Works well with WebRTC, P2P networks

**Trade-off**: Slightly higher memory usage and merge complexity, but worth it for offline-first requirements.

# AA20 — Distributed Tracing Challenges

**Context Propagation:**
- **W3C Trace Context**: Standardized headers (`traceparent`, `tracestate`) for cross-vendor compatibility
- **B3**: Zipkin's format (`X-B3-TraceId`, `X-B3-SpanId`)
- Challenge: Polyglot systems need libraries supporting these standards in each language

**Sampling Strategies:**
- **Head-based**: Decide at trace start; lower storage but may miss important traces
- **Tail-based**: Store all, filter later; higher storage but captures rare errors

**Trace Storage & Querying:**
- **Jaeger**: All-in-one solution, good for smaller deployments
- **Tempo**: Prometheus-native, uses object storage, better for large-scale

**Asynchronous Messaging Challenge:**
Traces break at message boundaries since there's no direct request-response relationship.

**Ensuring Trace Continuity Through Kafka:**

```python
# Producer side
trace_context = tracer.extract_current()
message = {
    "data": payload,
    "headers": {
        "traceparent": trace_context.traceparent,
        "tracestate": trace_context.tracestate
    }
}
kafka_producer.send("topic", message)

# Consumer side
headers = message.headers()
trace_context = tracer.inject(headers)
with tracer.start_span("process-message", context=trace_context):
    process(message.data)
```

**Key considerations:**
- Propagate trace context in message headers
- Use correlation IDs linking parent-child traces
- Implement tail-based sampling to capture async failures
- Ensure all services use compatible tracing libraries
