# OT Security Interview Questions - Detailed Answers

---

## OT1 — Easy: What is the Purdue Model (ISA-95)? Name and describe at least 4 of the levels (0-5).

**Answer:**

The Purdue Model (ISA-95) is a hierarchical framework for industrial automation and control systems (IACS) that defines 6 levels (0-5) from physical processes to enterprise systems. It provides a common language for integrating IT and OT systems and is foundational for IEC 62443 security standards.

**The 6 Levels:**

| Level | Name | Description |
|-------|------|-------------|
| **Level 0** | Physical Process | The actual physical process — sensors, actuators, motors, valves, pumps. No computing here, just physics. |
| **Level 1** | Basic Control | PLCs, RTUs, DCS controllers that directly control Level 0 devices. Real-time deterministic control (milliseconds). |
| **Level 2** | Area Supervisory Control | HMIs, local supervisory systems, data historians. Operators monitor and intervene. Near real-time (seconds). |
| **Level 3** | Site Operations | SCADA servers, MES (Manufacturing Execution Systems), production scheduling. Batch tracking, quality data. |
| **Level 4** | Site Business Planning | ERP, supply chain, inventory management. Business-level systems with no real-time requirements. |
| **Level 5** | Enterprise | Corporate network, external connections, internet, cloud services. |

**Key Concept:** The model creates a "pyramid" where real-time requirements decrease and business relevance increases as you move up. Security boundaries are typically placed at Level 3.5 (between OT and IT).

## OT2 — Easy: What is the difference between IT and OT networks? Why can't you apply standard IT patching practices to OT systems?

**Answer:**

**Key Differences Between IT and OT Networks:**

| Aspect | IT Networks | OT Networks |
|--------|-------------|-------------|
| **Primary Goal** | Confidentiality, Integrity, Availability (CIA) | **Availability**, Safety, Integrity |
| **Downtime Cost** | Minutes/hours acceptable | Seconds can cost millions or cause safety incidents |
| **Lifecycle** | 3-5 years | 15-30+ years |
| **Patching** | Regular, automated | Rare, planned, tested extensively |
| **Protocols** | TCP/IP, HTTP, SQL | Modbus, Profinet, EtherNet/IP, proprietary |
| **Visibility** | Full asset discovery possible | Often unknown assets, legacy systems |
| **Security Tools** | EDR, SIEM, firewalls everywhere | Limited, non-intrusive monitoring only |

**Why Standard IT Patching Fails in OT:**

1. **Availability First:** A failed patch can stop production for days. IT patches for security; OT patches for functionality.

2. **Legacy Systems:** Many OT systems run Windows XP, Windows 7, or even Windows NT — unsupported by vendors, no patches available.

3. **Vendor Lock-in:** Only equipment vendors can patch their systems. You can't just download a patch from Microsoft.

4. **Testing Requirements:** Every patch must be tested in a staging environment that mirrors production — expensive and time-consuming.

5. **Scheduled Maintenance Windows:** Patching only happens during planned shutdowns (quarterly, annually), not continuously.

6. **Firmware vs. Software:** Many OT devices have firmware that requires physical access or special procedures to update.

7. **Safety Critical:** A bad patch could cause unsafe conditions, not just downtime.

## OT3 — Medium: Explain the role of a DMZ (IDMZ — Industrial DMZ) between IT and OT networks. What traffic should be allowed to cross, and in which direction? Why is direct connectivity from Level 4 (IT) to Level 1 (control) dangerous?

**Answer:**

**Role of the IDMZ:**

The Industrial DMZ (IDMZ) is a security buffer zone between IT (Level 4/5) and OT (Level 0-3) networks. It allows controlled data exchange while preventing direct connectivity that could compromise safety or availability.

**Architecture:**
```
Internet → Corporate Firewall → IT Network (Level 4) → IDMZ → OT Firewall → OT Network (Level 3)
```

**Traffic Rules:**

| Direction | Allowed Traffic | Purpose |
|-----------|----------------|---------|
| **OT → IDMZ** | Process data exports, alarms, historian data | Data collection for analytics |
| **IDMZ → IT** | Aggregated reports, KPIs, alerts | Business intelligence |
| **IT → IDMZ** | Configuration updates (scheduled), time sync | Limited management |
| **IT ↔ OT** | **BLOCKED** | Never direct |

**What Goes in the IDMZ:**
- Data collectors/gateways
- Protocol converters
- Historian interfaces
- Time synchronization servers
- Antivirus scanning for outbound files

**Why Direct Level 4 to Level 1 Connectivity is Dangerous:**

1. **No Security Boundary:** Malware from corporate email could directly reach PLCs controlling physical processes.

2. **No Logging/Monitoring:** Direct connections bypass security monitoring, making attacks invisible.

3. **Lateral Movement:** Compromised IT systems can pivot directly to critical control systems.

4. **No Rate Limiting:** IT traffic patterns don't match OT requirements — could overwhelm control networks.

5. **Protocol Mismatch:** IT protocols (HTTP, SMB) aren't designed for deterministic control — could cause unpredictable behavior.

6. **Safety Risk:** A ransomware infection could lock out operators from emergency controls.

## OT4 — Medium: What are the following OT protocols, and where in the Purdue Model does each typically operate?

**Answer:**

| Protocol | Description | Purdue Level | Notes |
|----------|-------------|--------------|-------|
| **1. Modbus TCP** | Simple master-slave protocol for reading/writing registers. Unencrypted, no authentication. | Level 1-2 | Most common legacy protocol. Runs over Ethernet. Ports 502. |
| **2. OPC UA** | Modern, secure, platform-independent protocol with built-in encryption and authentication. | Level 2-3 | Replaces classic OPC. Supports pub/sub and request/response. |
| **3. EtherNet/IP (CIP)** | Rockwell/Automation Alliance protocol. Uses standard Ethernet with CIP messaging. | Level 1-2 | Common in North America. Uses ports 44818, 2222. |
| **4. PROFINET** | Siemens-led real-time Ethernet protocol. Deterministic, supports IRT (Isochronous Real-Time). | Level 1-2 | Dominant in Europe. Sub-millisecond cycles possible. |
| **5. MQTT** | Lightweight publish-subscribe messaging protocol. Not originally OT but widely adopted. | Level 2-3+ | Used for IIoT, cloud connectivity. Runs on port 1883 (or 8883 TLS). |

**Key Observations:**
- **Level 1-2 protocols** (Modbus, EtherNet/IP, PROFINET) are deterministic, real-time, often proprietary
- **Level 2-3+ protocols** (OPC UA, MQTT) are more IT-friendly, support encryption, designed for data aggregation
- **Modbus** is the "HTTP of OT" — ubiquitous but insecure
- **OPC UA** is the modern replacement with security built-in
- **MQTT** bridges OT to cloud/IIoT applications

## OT5 — Medium: Explain the concept of a data diode vs a firewall in OT security. When would you use a hardware data diode? What is the limitation compared to a firewall?

**Answer:**

**Data Diode vs. Firewall:**

| Feature | Firewall | Hardware Data Diode |
|---------|----------|---------------------|
| **Direction** | Bidirectional (configurable) | **Unidirectional only** (physical enforcement) |
| **Enforcement** | Software/Logic-based | **Physical/optical** (LED transmitter, photodiode receiver) |
| **Fail State** | Could fail open | **Fails closed** by physics |
| **Insider Threat** | Vulnerable to misconfiguration | Immune — cannot send back |
| **Performance** | Can be bottleneck | High throughput, low latency |
| **Cost** | Lower | Higher ($10k-$50k+) |

**How a Data Diode Works:**
```
OT Network → [Transmitter LED] → [Optical Fiber] → [Photodiode Receiver] → IT Network
              ↑                                                        ↑
         (Can only send light)                                (Can only receive light)
```

**When to Use a Hardware Data Diode:**

1. **High-Security Environments:** Power grids, nuclear facilities, military SCADA
2. **Regulatory Requirements:** NERC CIP, critical infrastructure mandates
3. **Maximum Assurance Needed:** When you absolutely cannot risk bidirectional communication
4. **Data Exfiltration Prevention:** Ensuring OT data can only flow outward, never inward

**Limitations Compared to Firewall:**

1. **No Bidirectional Communication:** Cannot receive commands, updates, or queries from IT side
2. **No Active Defense:** Cannot block malicious packets — only allows one direction
3. **Higher Cost:** Significantly more expensive than firewalls
4. **Less Flexible:** Cannot implement complex rules, deep packet inspection
5. **Single Purpose:** Only for data export, not for general network segmentation

**Best Practice:** Use data diodes for critical data export paths, firewalls for general segmentation. They complement each other.

**Data Flow Steps:**

1. **PLCs/Sensors (Level 1)** → SCADA Server reads process values
2. **SCADA Server (Level 3)** → OPC UA Server exposes data points
3. **OPC UA Server** → MQTT Broker publishes to topics (e.g., `plant/line1/temp`)
4. **Historian** (optional) → Archives data for compliance, can also publish to MQTT
5. **MQTT Broker** → Edge Gateway subscribes, buffers, transforms data
6. **Edge Gateway** → Applies protocol conversion, compression, TLS encryption
7. **OT/IT Firewall** → Allows only outbound MQTT/TLS traffic (ports 8883, 443)
8. **Cloud Endpoint** → Receives data via HTTPS/MQTT over TLS
9. **Message Queue** → Kafka/RabbitMQ for buffering
10. **Stream Processing** → Real-time analytics, aggregation
11. **Analytics Platform** → Storage, visualization, ML models

**Security Boundaries:**

| Boundary | Control |
|----------|---------|
| **OT Network Internal** | VLAN segmentation, port security, NAC |
| **OT → IDMZ** | Firewall: Allow only MQTT publish OUT (port 8883) |
| **IDMZ → IT** | Firewall: Allow only HTTPS OUT (port 443) |
| **Edge Gateway** | TLS 1.2+, certificate authentication, data signing |
| **Cloud** | IAM roles, VPC isolation, encryption at rest |

**Key Security Principles:**
- **Pull, don't push:** IT should never initiate connections to OT
- **Least privilege:** Only required data points exported
- **Encryption:** TLS everywhere, certificates for authentication
- **Buffering:** Edge gateway buffers for network resilience
- **Monitoring:** Log all data transfers for audit

## OT7 — Hard: Explain IEC 62443 (ISA/IEC 62443) security zones and conduits. How do you define a zone? What is a conduit? Design a zone-and-conduit model for a manufacturing plant with: corporate network, engineering workstations, SCADA servers, PLCs, and safety instrumented systems (SIS).

**Answer:**

**IEC 62443 Zones and Conduits Explained:**

**Zone:** A grouping of assets with common security requirements based on:
- Business criticality
- Safety impact
- Process function
- Trust level
- Risk tolerance

**Conduit:** A communication path between zones with defined security requirements:
- Allowed protocols
- Traffic direction
- Security controls (firewall, encryption)
- Monitoring requirements

**How to Define a Zone:**
1. Identify assets with similar security requirements
2. Assess business impact and safety criticality
3. Group by process function or location
4. Assign security level (SL 0-4)
5. Document zone boundaries and assets

**Zone-and-Conduit Model Design:**

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           ENTERPRISE NETWORK (Zone E)                          │
│  Security Level: SL-2  │  Corporate IT, ERP, Email, Internet                   │
├─────────────────────────────────────────────────────────────────────────────────┤
│                              CONDUIT C1                                        │
│  ┌─────────────────────────────────────────────────────────────────────────────┐│
│  │  Firewall + IDS/IPS + Proxy + DLP                                          ││
│  │  Allow: HTTPS(443), SMTP(587) OUT only                                     ││
│  └─────────────────────────────────────────────────────────────────────────────┘│
├─────────────────────────────────────────────────────────────────────────────────┤
│                              IDMZ (Zone I)                                     │
│  Security Level: SL-2  │  Data collectors, protocol converters, time sync      │
├─────────────────────────────────────────────────────────────────────────────────┤
│                              CONDUIT C2                                        │
│  ┌─────────────────────────────────────────────────────────────────────────────┐│
│  │  Industrial Firewall                                                      ││

┌─────────────────────────────────────────────────────────────────────────────────┐

│  │  Jump Host / Bastion with MFA                                              ││

│  │  Time-limited access, session recording                                    ││
│  └─────────────────────────────────────────────────────────────────────────────┘│
│                                                                 │
│  ┌─────────────────────────────────────────────────────────────────────────────┐│
│  │  Conduit to Zone O1 (SCADA): Allow programming protocols                   ││

│  └─────────────────────────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────────────────────────┘
```

**Zone Summary Table:**

| Zone | Name | Assets | Security Level | Notes |
|------|------|--------|----------------|-------|
| **E** | Enterprise | Corporate IT, ERP | SL-2 | IT security practices |
| **I** | IDMZ | Data collectors, converters | SL-2 | Buffer zone |
| **O1** | OT Level 3 | SCADA, Historian, MES | SL-2 | Operations management |
| **O2** | OT Level 1-2 | PLCs, HMIs, RTUs | SL-2 | Control systems |
| **O3** | OT Level 0 | Sensors, actuators | SL-1 | Physical layer |
| **S** | Safety | SIS, safety sensors | SL-3 | **Isolated**, highest priority |
| **ENG** | Engineering | Programming workstations | SL-2 | Controlled access only |

**Conduit Security Requirements:**

| Conduit | From | To | Controls |
|---------|------|-----|----------|
| C1 | E | I | Firewall, IDS, proxy, DLP |
| C2 | I | O1 | Industrial firewall, protocol filter |
| C3 | O1 | O2 | Industrial firewall, VLAN separation |
| C4 | O2 | O3 | Switch port security, no routing |
| C5 | ENG | O1/O2 | Jump host, MFA, session recording |
| C6 | S | Any | **Data diode only** (monitoring) |

**Key Principles:**
- **Safety network (Zone S) is always isolated** — never directly connected to BPCS or IT
- **Engineering access is through a bastion** with MFA and logging
- **Each conduit has specific protocol and direction restrictions**
- **Security levels increase toward safety-critical systems**
