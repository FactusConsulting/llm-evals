# OpenTofu / Terraform Answers

**T1:** `tofu plan` performs a dry-run that calculates the execution plan—showing what changes OpenTofu will make—without actually modifying any infrastructure. `tofu apply` executes that plan, creating, updating, or destroying resources as specified.

**T2:** State is a JSON file that tracks the current real-world state of managed resources, mapping OpenTofu configuration to actual infrastructure. Remote state is important because it enables: (1) collaboration (multiple users/CI pipelines access the same state), (2) state locking (prevents concurrent modifications), (3) persistence (state survives local machine failures), and (4) security (can be encrypted and access-controlled).

**T3:** `count` creates resources indexed by integer (0 to n-1), while `for_each` creates resources keyed by map keys or set elements. `for_each` is preferred because: (1) it provides stable resource identities (changing order doesn't cause unnecessary recreation), (2) it allows referencing resources by meaningful keys rather than indices, and (3) it avoids the "index shifting" problem where removing an item causes all subsequent resources to be recreated.

**T4:** When you manually change a resource outside OpenTofu, the next `tofu plan` detects a "drift" by comparing the actual resource state (fetched from the API) against the recorded state. OpenTofu shows this as a change that would be made to reconcile the difference. By default, it will modify the resource to match the configuration. You can use `ignore_changes` in the lifecycle block to prevent OpenTofu from managing specific attributes.

**T5:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  
  ami           = "ami-12345678"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

**T6:** `terraform_remote_state` data source reads another state file's outputs directly, while output values pass data through the current module's outputs. The recommended alternative is using a shared state backend with outputs, accessed via `terraform_remote_state` data source in consuming modules. This is preferred because it's explicit, doesn't require restructuring modules, and allows fine-grained access control. However, for complex sharing, consider using a dedicated "state module" that outputs all shared data, or use external data sources (e.g., reading from a database or API).

**T7:** The issue is that `null_resource` with `provisioner` runs during apply, but its output (if any) isn't available until after the resource is created. On first apply, dependent resources try to read the output before the provisioner completes. Fix: (1) Use `triggers` on the null_resource to ensure it runs when needed, (2) Use `depends_on` to explicitly order resources, (3) Better yet, avoid provisioners—use a separate module or external tool to generate kubeconfig, or use the cloud provider's native kubeconfig output if available.

**T8:** `tofu import` brings existing infrastructure under OpenTofu management by reading the real resource and writing it to state without modifying the resource. Limitations: (1) You must know the exact resource address and ID, (2) It doesn't generate configuration—you must write matching config manually, (3) Complex resources may not import cleanly. The `import` block (1.5+) improves this by allowing you to declare import intent in configuration, making it version-controllable and enabling `tofu plan` to show what will be imported before running `tofu apply`.

**T9:** A variable is an input parameter that allows configuration customization. Input variables (`variable` block) accept values from outside (CLI, env vars, files), while outputs (`output` block) expose values from the module to be used by other modules or consumed externally.

**T10:** A provider is a plugin that enables OpenTofu to interact with APIs (cloud providers, services, etc.). Without `tofu init`, providers aren't downloaded, so `tofu plan` fails with an error like "provider not installed" or "no providers found."

**T11:** `.terraform.lock.hcl` is a lock file that pins exact provider versions, ensuring reproducible builds. It should be committed to version control to guarantee that all team members and CI pipelines use identical provider versions, preventing unexpected behavior from provider updates.

**T12:** `tofu destroy` removes all managed resources. To target a single resource: `tofu destroy -target=aws_instance.example` or `tofu destroy -target=module.name.resource.type.name`.

**T13:** A data source reads existing infrastructure or external data without managing it. Example: Use `data "aws_ami"` to find the latest Amazon Linux AMI ID instead of hardcoding it, or `data "http"` to fetch external configuration—unlike managed resources, data sources don't create/update/destroy anything.

**T14:** `variable` blocks define input parameters from outside the module; `locals` define internal computed values. Use `locals` for: (1) complex expressions reused multiple times, (2) derived values not meant as inputs, (3) avoiding repetition of long expressions, (4) organizing logic without exposing internals as inputs.

**T15:** The `lifecycle` block controls resource creation/deletion behavior:
- `create_before_destroy`: Creates new resource before destroying old one (use for zero-downtime deployments, e.g., replacing a load balancer target).
- `prevent_destroy = true`: Prevents accidental deletion (use for critical resources like production databases).
- `ignore_changes = [attr]`: Ignores changes to specific attributes (use when external systems manage certain fields, e.g., auto-scaling groups modifying instance counts).

**T16:** A `moved` block tells OpenTofu that a resource has been relocated (renamed, moved between modules, etc.) without being destroyed and recreated. It preserves state associations during refactoring, preventing unnecessary resource recreation and potential downtime.

**T17:** OpenTofu builds a dependency graph where nodes are resources and edges represent dependencies. Implicit dependencies are inferred from references (e.g., `${aws_instance.a.id}` creates a dependency). Explicit dependencies use `depends_on`. `depends_on` forces ordering, reducing parallelism—use sparingly because it can slow down applies. Prefer implicit dependencies via references when possible.

**T18:** Strategies to reduce plan time:
1. **Modularize**: Split into smaller modules; tradeoff is increased complexity in orchestration.
2. **Use `tofu plan -target`**: Plan only changed sections; tradeoff is you might miss cross-resource impacts.
3. **Optimize data sources**: Cache or reduce API calls; tradeoff is potential staleness.
4. **Upgrade hardware/parallelism**: More CPU/RAM helps; tradeoff is cost.
5. **Review provider configurations**: Some providers are slow; consider caching or mocking in CI.
6. **Use `refresh_only` selectively**: Avoid full refresh if state is trusted.

**T19:** State locking prevents concurrent modifications. Backends like S3+DynamoDB or Terraform Cloud implement locks. If a lock isn't released (CI crash), subsequent runs fail. Manually break with backend-specific commands (e.g., delete DynamoDB lock item, or `terraform force-unlock` for some backends). Risks: potential state corruption if two processes modified state simultaneously.

**T20:** Migration steps:
1. Configure new backend in `terraform.tfbackend` block (S3 bucket, DynamoDB table for locking).
2. Run `tofu init -migrate-state` to move state from local to S3.
3. Verify state exists in S3 bucket and DynamoDB table.
4. Run `tofu plan` to confirm no unexpected changes.
5. Test with a small apply to ensure locking works.
The existing state file is copied to S3; local state becomes stale (can be deleted after verification).

# Ansible Answers

**A1:** A **task** is a single unit of work (e.g., install a package). A **playbook** is a YAML file containing one or more plays, each targeting hosts with a list of tasks. A **role** is a structured directory containing tasks, handlers, templates, etc., promoting reusability.

**A2:** `ansible_facts` is a dictionary of system information gathered automatically. Access OS family via `{{ ansible_os_family }}` (e.g., "Debian", "RedHat").

**A3:** 
- `command`: Executes commands without a shell (no pipes, redirection); safest, fastest.
- `shell`: Executes via `/bin/sh`; supports shell features but slower and less portable.
- `raw`: Sends commands directly over connection without becoming a module; useful when modules aren't available.
Use `command` by default, `shell` only when needed, `raw` for special cases (e.g., Windows without WinRM modules).

**A4:** Ansible achieves idempotency by checking current state before making changes. Idempotent example: `apt: name=nginx state=present` (only installs if missing). Non-idempotent: `shell: echo "hello" >> /tmp/log.txt` (appends every run).

**A5:**
```yaml
- name: Install htop based on OS family
  package:
    name: "{{ htop_packages }}"
    state: present
  vars:
    htop_packages: >-
      {% if ansible_os_family == 'Debian' %}
      htop
      {% elif ansible_os_family == 'RedHat' %}
      epel-release,htop
      {% endif %}
```

**A6:** Variable precedence (lowest to highest):
1. Role defaults (`defaults/main.yml`)
2. Inventory file variables (group_vars, host_vars)
3. Host facts
4. Role vars (`vars/main.yml`)
5. Include vars
6. Set_fact / registered vars
7. Extra vars (`-e` or `--extra-vars`)
`set_fact` has higher priority than role vars but lower than extra_vars.

**A7:**
```yaml
- hosts: rke2_agents
  tasks:
    - name: Deploy RKE2 agent
      ansible.builtin.shell: /usr/local/install.sh
      delegate_to: "{{ item }}"
      loop: "{{ groups['rke2_agents'] }}"
      serial: "3"  # First batch of 3
    - name: Wait for first batch
      ansible.builtin.wait_for:
        port: 6443
        host: "{{ item }}"
      loop: "{{ groups['rke2_agents'][:3] }}"
      delegate_to: localhost
  post_tasks:
    - name: Deploy remaining agents
      ansible.builtin.shell: /usr/local/install.sh
      delegate_to: "{{ item }}"
      loop: "{{ groups['rke2_agents'][3:] }}"
      serial: 10
```
Alternatively, use separate plays with `when: inventory_hostname in groups['first_batch']`.

**A8:** `ansible-vault` encrypts sensitive data. To encrypt a single variable:
```bash
ansible-vault encrypt_string 'secret_value' --name=my_var --vault-password-file=vault_pass.txt
```
This outputs encrypted YAML that can be inserted into a vars file without encrypting the whole file.

**A9:** An inventory file lists target hosts and groups. Static inventory is a YAML/INI file you maintain manually. Dynamic inventory is generated by a script/plugin (e.g., AWS EC2 inventory) that queries external systems at runtime.

**A10:** `ansible webservers -m shell -a "df -h"` or `ansible webservers -a "df -h"`

**A11:** A handler is a task that runs only when notified (triggered) by another task. Unlike regular tasks that run in order, handlers run once at the end of a play if notified. Trigger with `notify: handler_name` in a task.

**A12:** `ansible.cfg` configures Ansible behavior. Common settings: `forks` (parallelism), `host_key_checking` (SSH security), `remote_user` (default SSH user), `log_path`, `inventory`, `roles_path`.

**A13:** `register` captures task output into a variable. Example:
```yaml
- name: Get disk info
  shell: df -h
  register: disk_output
- name: Show result
  debug: msg="{{ disk_output.stdout }}"
```

**A14:** `import_tasks` is statically included at parse time (all tasks visible, conditionals evaluated immediately). `include_tasks` is dynamically included at runtime (conditionals evaluated when included). Use `import_tasks` for static structure, `include_tasks` for dynamic/conditional inclusion.

**A15:** Ansible Galaxy is a repository of roles and collections. Use `requirements.yml`:
```yaml
roles:
  - name: geerlingguy.mysql
collections:
  - name: community.general
```
Install with `ansible-galaxy install -r requirements.yml`.

**A16:** Connection plugins define how Ansible reaches targets. `ssh` (default) uses SSH; `local` runs tasks on control node; `network_cli` is for network devices (Cisco, Juniper). Use `ssh` for Linux/Windows, `local` for localhost tasks, `network_cli` for network gear.

**A17:** `delegate_to` runs a task on a different host than the target. `run_once` runs a task once per play (on first host). Example:
```yaml
- name: Gather remote data
  shell: hostname
  register: remote_hostname
  
- name: Process on control node once
  shell: echo "{{ remote_hostname.stdout }}" > /tmp/processed.txt
  delegate_to: localhost
  run_once: true
```

**A18:** Performance strategies:
1. **Increase forks**: `forks=50` in ansible.cfg; tradeoff is memory/CPU usage.
2. **Pipelining**: `pipelining=true` reduces SSH connections; tradeoff is SSH config requirements.
3. **Fact caching**: `fact_caching=jsonfile` avoids regathering facts; tradeoff is cache staleness.
4. **Mitogen**: Alternative transport that's faster; tradeoff is complexity and compatibility.
5. **Optimize playbooks**: Reduce tasks, use `async/polling`, limit hosts with patterns.

**A19:** Jinja2 in Ansible: `{{ }}` for expressions/variables, `{% %}` for control structures (if, for), `{# #}` for comments. Template example:
```jinja2
upstream backend {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }} weight={{ server.weight }};
    # Health check: {{ server.health_endpoint }}
{% endfor %}
}
```

**A20:** Zero-downtime rolling deployment:
```yaml
- hosts: webservers
  serial: "20%"  # 4 servers at a time
  
  pre_tasks:
    - name: Remove from load balancer
      uri:
        url: "http://lb/api/deregister/{{ inventory_hostname }}"
        method: POST
  
  tasks:
    - name: Deploy new version
      git:
        repo: "{{ app_repo }}"
        dest: "{{ app_dir }}"
        version: "{{ new_version }}"
    
    - name: Restart application
      systemd:
        name: "{{ app_name }}"
        state: restarted
    
    - name: Health check
      uri:
        url: "http://localhost/health"
        status_code: 200
      retries: 5
      delay: 10
  
  post_tasks:
    - name: Add back to load balancer
      uri:
        url: "http://lb/api/register/{{ inventory_hostname }}"
        method: POST
  
  rescue:
    - name: Rollback on failure
      git:
        repo: "{{ app_repo }}"
        dest: "{{ app_dir }}"
        version: "{{ previous_version }}"
      notify: Restart application
```
