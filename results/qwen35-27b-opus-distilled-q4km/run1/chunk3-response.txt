# OpenTofu / Terraform Answers

## T1 — Easy: What is the difference between tofu plan and tofu apply?

**tofu plan**: Creates an execution plan showing what actions OpenTofu will take. It's a read-only operation that compares your configuration against the current state and outputs a preview of changes (add, modify, destroy) without making any actual changes.

**tofu apply**: Executes the plan and makes the actual changes to infrastructure. It reads the state, computes the diff, and performs the API calls to create/update/delete resources.

---

## T2 — Easy: What is state in OpenTofu, and why is remote state important?

**State**: A JSON file that maps real-world resources to your configuration. It tracks resource IDs, attributes, and metadata.

**Remote state is important because it enables**:
- Team collaboration (shared state)
- State locking (prevents concurrent modifications)
- Persistence (survives local machine failures)
- Security (can be encrypted at rest)

---

## T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?

**count**: Creates resources by index (0, 1, 2...). Resources are identified by numeric index.

**for_each**: Creates resources by unique key from a map or set. Resources are identified by the key.

**for_each is preferred because**:
- Resources are identified by key, not index (reordering doesn't cause unnecessary recreation)
- More flexible (can use maps for different configurations per resource)
- Better for dynamic resource sets

---

## T4 — Medium: What happens if you manually change a resource outside of OpenTofu?

OpenTofu detects drift during `tofu plan` by comparing the actual resource state (fetched from the API) against the recorded state. It will show the resource as needing update to match the configuration. If the manual change isn't in your config, OpenTofu will try to revert it on next apply.

---

## T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).

```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  
  ami           = "ami-12345678"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

---

## T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules.

**terraform_remote_state**: Reads another state file directly. Creates tight coupling between modules and can cause circular dependencies.

**Output values**: Pass data through module outputs/inputs.

**Recommended alternative**: Use module outputs/inputs with a shared state backend. **Why**: Better encapsulation, explicit dependencies, easier to refactor, and follows single responsibility principle.

---

## T7 — Hard: RKE2 cluster module with null_resource provisioner issue.

**Problem**: The null_resource runs provisioners during apply, but the output is only available after the provisioner completes. On first apply, dependent resources try to read the output before the provisioner finishes, getting an empty value.

**Fix**: Use a `trigger` to force the null_resource to run before dependents, or use a data source that waits for the cluster to be ready. Better approach: Use the actual Kubernetes provider with proper resource dependencies instead of null_resource.

---

## T8 — Medium: What is terraform import, and what are its limitations?

**terraform import**: Brings existing infrastructure under OpenTofu management by reading the current state and creating a state entry.

**Limitations**:
- Requires knowing the exact resource address and ID
- Doesn't create configuration (you must write it manually)
- Can fail if resource attributes don't match config
- No dry-run capability

**Import block (1.5+)**: Declares imports in configuration. **Improvements**: Can run `tofu plan` to preview imports, imports happen as part of normal apply, better error handling and rollback.

---

## T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?

**Variable (input)**: External input to your configuration, defined with `variable` blocks.

**Output**: Values exported from your configuration, defined with `output` blocks.

**Difference**: Inputs come in; outputs go out.

---

## T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?

**Provider**: A plugin that interacts with APIs (AWS, Azure, Kubernetes, etc.).

**Without tofu init**: OpenTofu will fail with an error saying providers are not installed. Init downloads providers, initializes backends, and sets up the working directory.

---

## T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?

**Lock file**: Records exact provider versions and their checksums.

**Commit it to ensure**:
- Reproducible builds across environments
- Team consistency
- Security (prevents unexpected version upgrades)

---

## T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?

**tofu destroy**: Removes all resources managed by the configuration.

**Target single resource**: `tofu destroy -target=aws_instance.web`

---

## T13 — Easy: What is a data source in OpenTofu?

**Data source**: Reads existing infrastructure without managing it.

**Example**: Using `aws_ami` data source to find the latest Amazon Linux AMI instead of hardcoding an AMI ID.

**Use when**: You need information about existing resources but don't want OpenTofu to manage their lifecycle.

---

## T14 — Medium: Explain the difference between locals and variable blocks.

**Variable**: External input, can be overridden via CLI/env/TF_VAR_ prefix.

**Locals**: Internal computed values, cannot be overridden externally.

**Use locals for**:
- Derived values (e.g., `local "region" { value = var.aws_region }`)
- Complex expressions reused multiple times
- Default values that shouldn't be exposed as inputs

---

## T15 — Medium: What is the lifecycle block in a resource?

**create_before_destroy**: Creates new resource before destroying old one (zero-downtime updates).

**prevent_destroy**: Prevents resource deletion (safety mechanism).

**ignore_changes**: Ignores specific attribute changes (e.g., auto-managed tags).

**Use case examples**:
- create_before_destroy: Database instances, load balancers
- prevent_destroy: Production databases with critical data
- ignore_changes: Auto-scaling group desired capacity, security group rules managed elsewhere

---

## T16 — Medium: What is a moved block in OpenTofu?

**Moved block**: Tells OpenTofu that a resource was renamed or reorganized. Helps during refactoring by preserving state associations without destroying/recreating resources.

**Example**: Moving a resource from one module to another, or renaming a resource address.

---

## T17 — Hard: Explain how OpenTofu's dependency graph works.

**Implicit dependencies**: Automatically detected when one resource references another (e.g., `aws_instance.web.ami = aws_ami.amazon_linux.id`).

**Explicit dependencies**: Declared with `depends_on` meta-argument.

**depends_on affects parallelism**: Resources with explicit dependencies must wait, reducing parallelism.

**Use sparingly because**:
- Implicit dependencies are usually sufficient
- Overuse creates unnecessary serialization
- Can hide design problems (should resources really be coupled?)

---

## T18 — Hard: Strategies to reduce plan time for 200+ resources.

1. **Use -target flag**: Only plan specific resources. Tradeoff: May miss related changes.
2. **Split into smaller modules**: Plan independently. Tradeoff: More complex orchestration.
3. **Use -refresh-only selectively**: Don't refresh all resources every plan. Tradeoff: State may drift.
4. **Optimize data sources**: Cache results, reduce API calls. Tradeoff: May use stale data.
5. **Use -parallelism flag**: Limit concurrent operations. Tradeoff: Slower but more predictable.
6. **Upgrade providers**: Newer versions often have performance improvements. Tradeoff: Breaking changes possible.

---

## T19 — Hard: OpenTofu state locking mechanism.

**Locking**: Prevents concurrent modifications to state. Backend-specific (S3+DynamoDB, Consul, etc.).

**If lock not released**:
- Other operations block indefinitely
- Can manually break with `tofu force-unlock <lock-id>`
- **Risk**: Concurrent modifications could corrupt state

---

## T20 — Hard: Migrate from local to S3+DynamoDB backend.

**Step-by-step**:
1. Configure new backend in config (commented out or in separate file)
2. Run `tofu init -migrate-state` to move state to S3
3. Verify state file exists in S3 bucket
4. Verify DynamoDB table has lock entry
5. Run `tofu plan` to confirm state is readable
6. Test with a small change and apply
7. Verify state updates correctly in S3

**Existing state**: Copied to S3, local state becomes stale (should delete after verification).

# Ansible Answers

## A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?

**Task**: Single unit of work (e.g., install a package).

**Playbook**: Ordered list of plays, each targeting hosts with tasks.

**Role**: Reusable, organized collection of tasks, templates, files, and variables in a standard directory structure.

---

## A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?

**ansible_facts**: Automatically gathered information about target hosts (IP, OS, memory, etc.).

**Access OS family**: `{{ ansible_os_family }}` or `{{ ansible_facts.os_family }}`

---

## A3 — Medium: Explain the difference between command, shell, and raw modules.

**command**: Executes commands without shell (no pipes, redirects). Most secure, fastest.

**shell**: Executes through /bin/sh (supports pipes, redirects, variables). More flexible but slower.

**raw**: Sends command directly over connection without shell. Lowest level, no module support.

**Use**: command for simple commands, shell for complex ones, raw for troubleshooting or when modules aren't available.

---

## A4 — Medium: How does Ansible handle idempotency?

**Idempotency**: Running a task multiple times produces the same result as running it once. Ansible modules are designed to be idempotent by checking current state before making changes.

**Idempotent example**:
```yaml
- name: Ensure nginx is installed
  apt:
    name: nginx
    state: present
```

**Not idempotent example**:
```yaml
- name: Append to file (not idempotent)
  shell: echo "line" >> /tmp/file
```

---

## A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.

```yaml
- name: Install htop and dependencies
  package:
    name: "{{ item }}"
    state: present
  loop: "{{ htop_packages }}"
  vars:
    htop_packages: >-
      {% if ansible_os_family == 'Debian' %}
        htop
      {% elif ansible_os_family == 'RedHat' %}
        epel-release,htop
      {% endif %}
```

---

## A6 — Hard: Explain Ansible's variable precedence order.

**From lowest to highest priority**:
1. Role defaults (defaults/main.yml)
2. Inventory file variables (group_vars, host_vars)
3. Host facts (ansible_facts)
4. Role variables (vars/main.yml)
5. Include variables
6. Set_fact / registered variables
7. Extra vars (-e flag, ansible.cfg)
8. Command line extra vars (highest)

---

## A7 — Hard: Deploy RKE2 agent on 50 nodes, first 3 must complete before rest.

```yaml
- name: Deploy RKE2 on control nodes first
  hosts: rke2_control
  become: yes
  tasks:
    - include_role:
        name: rke2_agent

- name: Wait for control nodes to be ready
  hosts: rke2_control
  tasks:
    - name: Wait for rke2 to be ready
      wait_for:
        port: 6443
        timeout: 300

- name: Deploy RKE2 on worker nodes
  hosts: rke2_workers
  become: yes
  serial: 5  # Process 5 at a time
  tasks:
    - include_role:
        name: rke2_agent
```

## A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?

**ansible-vault**: Encrypts sensitive data (passwords, keys, tokens).

**Encrypt single variable**:
```bash
ansible-vault encrypt_string 'secret_value' --name=my_var --vault-password-file=vault_pass.txt
```
This outputs YAML with the encrypted variable that you can paste into your vars file.

---

## A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?

**Inventory**: List of target hosts and their organization.

**Static inventory**: Manual INI or YAML file.

**Dynamic inventory**: Script or plugin that generates inventory from external sources (cloud APIs, CMDB, etc.).

---

## A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?

```bash
ansible webservers -m shell -a "df -h"
```

Or using the setup module for facts:
```bash
ansible webservers -m setup -a "filter=ansible_mounts"
```

---

## A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task?

**Handler**: Special task that only runs when notified by another task.

**Difference**: Regular tasks run in order; handlers run once at the end of a play if notified.

**Trigger with notify**:
```yaml
- name: Update nginx config
  template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  notify: Restart nginx

handlers:
  - name: Restart nginx
    service:
      name: nginx
      state: restarted
```

---

## A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.

**ansible.cfg**: Configuration file for Ansible behavior.

**Common settings**:
- `host_key_checking = False` (disable SSH host key verification)
- `forks = 10` (parallel connections)
- `retry_files_enabled = False` (disable retry files)
- `log_path` (logging location)
- `remote_user` (default SSH user)

---

## A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?

**Register**: Captures task output into a variable.

```yaml
- name: Get disk usage
  shell: df -h /
  register: disk_output

- name: Show disk usage
  debug:
    msg: "{{ disk_output.stdout }}"
```

---

## A14 — Medium: Explain the difference between include_tasks and import_tasks.

**import_tasks**: Static inclusion at parse time. Always executed, cannot be conditional.

**include_tasks**: Dynamic inclusion at runtime. Can be conditional, looped, and skipped.

**Use import_tasks** for performance (parsed once), **include_tasks** for flexibility (conditional execution).

---

## A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?

**Ansible Galaxy**: Repository for sharing Ansible roles and collections.

**requirements.yml**:
```yaml
roles:
  - name: geerlingguy.mysql
    version: 3.0.1
collections:
  - name: community.general
    version: 6.0.0
```

**Install with**: `ansible-galaxy install -r requirements.yml`

---

## A16 — Medium: Explain how Ansible connection plugins work.

**Connection plugins**: Handle how Ansible connects to target hosts.

**ssh**: Default, uses SSH protocol. Most common for Linux servers.

**local**: Runs tasks on control node. For localhost operations.

**network_cli**: For network devices (Cisco, Juniper). Uses CLI over SSH.

**Use**: ssh for servers, local for control node tasks, network_cli for network equipment.

---

## A17 — Hard: Explain how Ansible's delegate_to and run_once work.

**delegate_to**: Run task on a different host than the target.

**run_once**: Run task once per play, not per host.

**Example**:
```yaml
- name: Gather facts from remote hosts
  hosts: webservers
  tasks:
    - name: Get IP addresses
      debug:
        msg: "{{ ansible_default_ipv4.address }}"
      delegate_to: "{{ item }}"
      loop: "{{ groups['webservers'] }}"

    - name: Create DNS records on control node
      command: nsupdate -l dns_records.txt
      delegate_to: localhost
      run_once: yes
```

## A18 — Hard: Strategies to improve Ansible performance for 500 hosts.

1. **Increase forks**: `forks = 50` in ansible.cfg. Tradeoff: More memory/CPU usage.
2. **Enable pipelining**: `pipelining = True`. Reduces SSH round trips. Tradeoff: May not work with all SSH configurations.
3. **Fact caching**: Use `fact_caching = jsonfile` or `redis`. Tradeoff: Facts may become stale.
4. **Use mitogen**: Drop-in replacement for Ansible transport. 10-100x faster. Tradeoff: Additional dependency, different behavior in edge cases.
5. **Reduce fact gathering**: `gather_facts: no` when not needed.
6. **Use serial** with smaller batches for large deployments.

## A19 — Hard: Explain how Ansible Jinja2 templating works.

**{{ }}**: Variables and expressions (output to template).

**{% %}**: Control structures (if, for, etc.).

**{# #}**: Comments (not output).

**Nginx upstream template**:
```jinja2
upstream backend {
{% for server in backend_servers %}
    # Health check: {{ server.name }} - {{ server.health_endpoint }}
    server {{ server.ip }}:{{ server.port }} weight={{ server.weight }};
{% endfor %}
}
```

## A20 — Hard: Zero-downtime rolling deployment across 20 servers.

```yaml
- name: Rolling deployment with health checks
  hosts: webservers
  serial: 2  # Deploy to 2 servers at a time
  become: yes
  
  tasks:
    - name: Remove from load balancer
      uri:
        url: "http://lb-api/remove/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost
      ignore_errors: yes

    - name: Deploy application
      block:
        - name: Stop service
          service:
            name: myapp
            state: stopped

        - name: Deploy new version
          git:
            repo: "{{ app_repo }}"
            dest: /opt/myapp
            version: "{{ app_version }}"

        - name: Start service
          service:
            name: myapp
            state: started

        - name: Wait for health check
          uri:
            url: "http://localhost:8080/health"
            status_code: 200
          retries: 30
          delay: 2

      rescue:
        - name: Rollback on failure
          git:
            repo: "{{ app_repo }}"
            dest: /opt/myapp
            version: "{{ previous_version }}"
          
          - name: Restart service after rollback
            service:
              name: myapp
              state: restarted

    - name: Add back to load balancer
      uri:
        url: "http://lb-api/add/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost
```
