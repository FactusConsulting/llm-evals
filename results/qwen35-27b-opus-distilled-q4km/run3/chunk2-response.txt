# Kubernetes (20 questions)

## K1: Deployment vs StatefulSet

**Deployment**: Manages stateless applications with identical, interchangeable pods. Pods have random names (e.g., `myapp-7d9f8b6c5-x2k9m`) and no guaranteed identity or ordering. Ideal for web servers, APIs, and microservices.

**StatefulSet**: Manages stateful applications requiring stable network identities and persistent storage. Each pod has a predictable name (`myapp-0`, `myapp-1`, `myapp-2`), stable hostname, and ordered deployment/termination. Each pod gets its own PersistentVolume. Ideal for databases, message queues, and distributed systems.

---

## K2: ClusterIP Service Traffic Routing

A ClusterIP Service creates an internal virtual IP (VIP) within the cluster. Traffic routing works via:

1. **kube-proxy** runs on each node and watches for Service/Endpoint changes
2. It programs **iptables** (or IPVS) rules that redirect traffic to the Service's ClusterIP
3. When a pod sends traffic to the ClusterIP, iptables performs DNAT to one of the backing pod IPs
4. kube-proxy uses **round-robin** load balancing across healthy endpoints
5. Health checks ensure only ready pods receive traffic

---

## K3: PersistentVolume, PersistentVolumeClaim, StorageClass

**PersistentVolume (PV)**: Cluster-wide storage resource provisioned by an administrator or dynamically. Defines actual storage (e.g., NFS path, AWS EBS volume ID).

**PersistentVolumeClaim (PVC)**: User's request for storage. Specifies capacity and access mode. Binds to a PV.

**StorageClass**: Defines storage provisioner and parameters for **dynamic provisioning**. When a PVC references a StorageClass, Kubernetes automatically creates a PV.

**Relationship**: StorageClass → (dynamic provisioning) → PV ← (binding) → PVC → (mount) → Pod

---

## K4: CrashLoopBackOff Troubleshooting

1. **Check container logs**: `kubectl logs <pod> --previous` to see why the container exited
2. **Inspect events**: `kubectl describe pod <pod>` to see Liveness/Readiness probe failures, OOMKilled, or scheduling issues
3. **Verify application configuration**: Check ConfigMaps, Secrets, and environment variables for missing/incorrect values
4. **Test locally**: Run the container image locally with `docker run` to reproduce the issue outside the cluster

Additional checks: resource limits, network connectivity, database availability, application dependencies.

---

## K5: CoreDNS Role and Failure Impact

**Role**: CoreDNS is the default DNS server in Kubernetes. It resolves:
- Internal service names (`myservice.default.svc.cluster.local`)
- Pod hostnames
- External domain names (via upstream DNS)

**If CoreDNS pods are down**: Internal DNS resolution fails completely. Pods cannot resolve service names, breaking service discovery. External DNS may still work if pods have fallback upstream resolvers configured, but internal communication breaks.

---

## K6: Kubernetes Scheduler Decision Process

**Phase 1: Filtering (Predicate)**
Eliminates nodes that cannot run the pod:
- Insufficient CPU/memory (based on requests)
- Node taints without matching tolerations
- Node selectors not matching
- Pod affinity/anti-affinity violations
- Volume zone constraints

**Phase 2: Scoring (Priority)**
Ranks remaining nodes (0-100):
- **Least allocated**: Prefers nodes with more available resources
- **Balanced allocation**: Spreads pods evenly across nodes
- **Image locality**: Prefers nodes with cached images
- **Inter-pod affinity**: Prefers nodes near related pods

**Phase 3: Selection**
Picks highest-scoring node and binds the pod.

---

## K7: Memory Scheduling and OOM

**Will it schedule?** Yes. The node has 4GB total, 3.5GB requested, leaving 512Mi available. The pod requests 256Mi, which fits.

**If it uses 600Mi at runtime**: The pod exceeds its 512Mi limit. The kernel's OOM killer terminates the container with an **OOMKilled** exit code. The pod enters CrashLoopBackOff.

Note: Requests are for scheduling; limits are enforced at runtime.

---

## K8: Ingress Request Lifecycle

1. **External Load Balancer**: Routes HTTPS traffic (port 443) to the Ingress Controller pod
2. **NGINX Ingress Controller**: Terminates TLS, matches host/path against Ingress rules, selects target Service
3. **Service (ClusterIP)**: NGINX forwards to the Service's virtual IP
4. **kube-proxy/iptables**: DNAT redirects to a specific pod IP from the Endpoints list
5. **Application Pod**: Receives the request on its container port

The Endpoints object is automatically updated by the Endpoint Controller when pods scale or fail.

---

## K9: NetworkPolicy Default Behavior

**NetworkPolicy**: Declares how pods communicate using labels to select pods and define allowed traffic.

**Default behavior (no policies)**: All traffic is allowed (permissive).

**When a policy is applied**: The namespace becomes **denied by default**. Only traffic explicitly allowed by policies is permitted. Pods not selected by any policy are completely isolated.

---

## K10: RollingUpdate vs Recreate

**RollingUpdate**: Gradually replaces old pods with new ones. Maintains availability during updates. Configurable via `maxSurge` and `maxUnavailable`.

**Recreate**: Kills all old pods before creating new ones. Causes brief downtime.

**Choose Recreate when**:
- Application cannot handle mixed versions running simultaneously
- Database schema migrations requiring exclusive access
- Testing/development environments where downtime is acceptable
- Stateful applications that can't tolerate parallel instances

---

## K11: Namespaces and Defaults

**Namespace**: Logical isolation boundary for resources within a cluster. Provides scope for names, RBAC, and NetworkPolicies.

**Default namespaces**:
- `default`: General-purpose namespace for user workloads
- `kube-system`: Kubernetes system components (CoreDNS, kube-proxy, etc.)
- `kube-public`: Publicly accessible cluster information
- `kube-node-lease`: Node lease objects for heartbeat

---

## K12: kubectl describe pod

**Purpose**: Shows detailed pod information including events, conditions, and resource usage.

**Information not in `kubectl get pod`**:
1. **Events**: Scheduling events, probe failures, image pull errors
2. **Container state details**: Exit codes, restart counts, reason for termination
3. **Resource requests/limits**: CPU and memory allocations per container
4. **Volume mounts**: Detailed mount paths and volume types
5. **Node assignment**: Which node the pod is running on

---

## K13: ConfigMap and Consumption

**ConfigMap**: Stores non-confidential configuration data as key-value pairs.

**Consumption methods**:
1. **Environment variables**: `envFrom` or `env.valueFrom.configMapKeyRef`
2. **Volume mount**: Mounted as files at a specified path
3. **Command arguments**: Passed via `args` using `valueFrom`

---

## K14: Service Types

| Type | Description | Use Case |
|------|-------------|----------|
| **ClusterIP** | Internal VIP, accessible only within cluster | Default, internal services |
| **NodePort** | Opens port on each node (30000-32767), routes to ClusterIP | Simple external access without LB |
| **LoadBalancer** | Provisions cloud LB, forwards to ClusterIP | Production external access |

---

## K15: DaemonSet

**DaemonSet**: Ensures all (or selected) nodes run a copy of a pod. Automatically adds pods to new nodes.

**Use DaemonSet instead of Deployment when**:
- Running node-level agents (log collectors like Fluentd)
- Running network plugins (Calico, Cilium)
- Running monitoring agents (Node Exporter)
- Any workload that must run on every node

---

## K16: Taints/Tolerations vs Node Affinity

**Taints/Tolerations**:
- **Taint**: Applied to node, "repels" pods (e.g., `gpu=true:NoSchedule`)
- **Toleration**: Applied to pod, allows scheduling on tainted nodes
- **Use case**: Dedicated GPU nodes, master node protection

**Node Affinity**:
- **NodeSelector/Affinity**: Applied to pod, "attracts" to matching nodes
- Uses label matching with operators (In, NotIn, Exists)
- **Use case**: Schedule pods on specific zones, instance types

**Key difference**: Taints push pods away; affinity pulls pods toward nodes.

---

## K17: Kubernetes Operators

**Operator**: Custom controller that manages complex applications using Custom Resources (CRDs). Implements the reconciliation loop pattern.

**Difference from standard controller**:
- Standard controllers manage built-in resources (Pods, Services)
- Operators manage custom resources representing complex applications

**Problems solved**:
- Automating complex lifecycle operations (backups, upgrades, failover)
- Encoding operational knowledge into code
- Managing stateful applications (databases, message queues)
- Example: Prometheus Operator manages Prometheus instances, Alertmanagers, and ServiceMonitors

---

## K18: etcd Consistency and Recovery

**Consistency model**: etcd uses **Raft consensus** providing strong consistency. All reads see the latest committed value.

**Quorum lost**: With 3 nodes, quorum = 2. If 2 nodes are permanently lost, the cluster cannot form quorum and becomes **unavailable**. The remaining node cannot make progress.

**Recovery from 2/3 lost**:
1. **Cannot recover** the lost data — it's permanently gone
2. Must **rebuild the cluster** from scratch
3. If you have snapshots: restore from latest snapshot to new cluster
4. If no snapshots: accept data loss, rebuild cluster, restore application state from backups

---

## K19: RBAC and Manifests

**RBAC Components**:
- **Role**: Permissions within a namespace
- **ClusterRole**: Permissions cluster-wide or namespace-wide
- **RoleBinding**: Binds Role to subjects in a namespace
- **ClusterRoleBinding**: Binds ClusterRole to subjects cluster-wide

**Manifests for read-only pod access in namespace**:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: my-namespace
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: my-namespace
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

## K20: DNS Resolution and ndots

**Problem**: Default `ndots: 5` means if a domain has fewer than 5 dots, the resolver tries the search path first. For `google.com` (2 dots), it tries:
1. `google.com.<search-domain-1>`
2. `google.com.<search-domain-2>`
...each with 5s timeout before falling back to `google.com`

**Fix using dnsConfig**:

```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "1"
    - name: timeout
      value: "2"
    - name: attempts
      value: "2"
```

This reduces unnecessary search path queries and lowers timeouts.

# Development (20 questions)

## D1: git rebase vs git merge

**git merge**: Creates a merge commit preserving history. Non-destructive. Shows branching structure.

**git rebase**: Replays commits on top of another branch. Rewrites history. Creates linear history.

**Avoid rebasing when**:
- Branch is shared with others (rewrites public history)
- Branch has been pushed and others may have based work on it
- You need to preserve the exact commit history for auditing

---

## D2: TCP vs UDP

| TCP | UDP |
|-----|-----|
| Connection-oriented | Connectionless |
| Reliable, ordered delivery | Best-effort, unordered |
| Retransmits lost packets | Drops lost packets |
| Slower, more overhead | Faster, less overhead |

**TCP protocols**: HTTP, HTTPS, SSH, FTP, SMTP

**UDP protocols**: DNS, DHCP, VoIP (RTP), QUIC, TFTP

---

## D3: Race Condition

**Race condition**: When program behavior depends on the relative timing of events, leading to unpredictable results.

**Example (Python)**:
```python
counter = 0

def increment():
    global counter
    temp = counter  # Read
    temp = temp + 1  # Modify
    counter = temp   # Write

# Two threads calling increment() simultaneously
# Both read counter=0, both write counter=1
# Expected: 2, Actual: 1
```

The read-modify-write sequence is not atomic.

---

## D4: Symmetric vs Asymmetric Encryption

**Symmetric**: Same key for encryption and decryption. Fast. Examples: AES, ChaCha20.

**Asymmetric**: Public key encrypts, private key decrypts. Slower. Examples: RSA, ECC.

**In TLS**:
1. **Asymmetric**: Client and server exchange keys using RSA/ECDHE (key exchange)
2. **Asymmetric**: Server authenticates with certificate signed by CA
3. **Symmetric**: All subsequent data encrypted with negotiated session key (AES)

TLS uses asymmetric for authentication/key exchange, symmetric for data transfer.

---

## D5: Container Image Layers

**Layer**: Each Dockerfile instruction creates a read-only layer. Layers are stacked and cached.

**Layer caching impact on best practices**:
- **Order instructions by change frequency**: Put rarely-changing instructions first
- **Combine related commands**: Use `&&` to reduce layers
- **Example**:
```dockerfile
# Good: Dependencies cached if unchanged
FROM python:3.11
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

# Bad: Source copy invalidates dependency cache
FROM python:3.11
COPY . .
RUN pip install -r requirements.txt
```

---

## D6: HTTP 503 Troubleshooting

**Check in order**:

1. **Application logs**: Look for errors, exceptions, connection refused
2. **Resource utilization**: CPU, memory, disk I/O, network saturation
3. **Upstream dependencies**: Database connections, external API availability, cache status
4. **Load balancer/ingress**: Connection limits, timeout settings, health check failures

Additional: Check for rate limiting, circuit breakers tripped, thread pool exhaustion.

---

## D7: CAP Theorem

**CAP**: A distributed system can only guarantee 2 of 3:
- **C**onsistency: All nodes see same data at same time
- **A**vailability: Every request gets a response
- **P**artition tolerance: System works despite network partitions

**CP example**: etcd, ZooKeeper, Google Spanner. Sacrifice availability during partitions to maintain consistency.

**AP example**: Cassandra (default), DynamoDB (eventual mode). Sacrifice consistency for availability during partitions.

---

## D8: Horizontal vs Vertical Scaling

**Vertical scaling**: Add resources to existing instance (more CPU, RAM). Limited by hardware max.

**Horizontal scaling**: Add more instances. Theoretically unlimited.

**Architectural patterns enabling horizontal scaling**:
- Stateless application design
- Externalized sessions (Redis, database)
- Load balancers
- Message queues for async processing
- Database read replicas and sharding
- Caching layers (CDN, Redis)

---

## D9: Environment Variables

**Environment variable**: Key-value pair available to processes in the environment.

**Persist across shell sessions on Linux**:
```bash
# For current user, add to ~/.bashrc or ~/.profile
export MY_VAR="value"

# For all users, add to /etc/environment or /etc/profile.d/*.sh
```

## D10: JSON vs YAML

**JSON**: JavaScript Object Notation. Strict syntax, requires quotes and commas.

**YAML**: Human-readable data serialization. Supports comments, less punctuation.

**Advantages**:
- **JSON**: Universally supported, strict parsing, faster to parse
- **YAML**: More readable, supports anchors/aliases, allows comments

---

## D11: REST API and HTTP Methods

**REST API**: Architectural style using HTTP for stateless client-server communication with resources identified by URIs.

**HTTP Methods**:
- **GET**: Retrieve resource (safe, idempotent)
- **POST**: Create resource or trigger action (not idempotent)
- **PUT**: Replace resource entirely (idempotent)
- **DELETE**: Remove resource (idempotent)

---

## D12: Version Pinning

**Version pinning**: Specifying exact dependency versions (e.g., `requests==2.28.1` instead of `requests>=2.0`).

**Importance for reproducible builds**:
- Ensures identical dependencies across environments
- Prevents breaking changes from upstream updates
- Enables debugging by reproducing exact build conditions
- Critical for CI/CD consistency

---

## D13: Compiled vs Interpreted Languages

**Compiled**: Source → machine code before execution. Faster runtime, longer build time.
- Examples: C, C++, Rust, Go

**Interpreted**: Source executed line-by-line by interpreter. Slower runtime, faster iteration.
- Examples: Python, JavaScript, Ruby, PHP

Note: Many languages blur the line (Java compiles to bytecode, Python uses bytecode caching).

---

## D14: Reverse Proxy

**Reverse proxy**: Sits in front of servers, forwards client requests to backend servers. Clients think they're talking directly to the server.

**Forward proxy**: Sits in front of clients, forwards requests to any server. Used for anonymity/circumventing restrictions.

**Common reverse proxies**:
- **NGINX**: High-performance web server, load balancing, caching
- **HAProxy**: Specialized load balancer, TCP/HTTP layer 4-7

**Use cases**: Load balancing, SSL termination, caching, compression, security.

---

## D15: Deadlock and Coffman Conditions

**Deadlock**: Two or more processes blocked forever, each waiting for resources held by others.

**Four Coffman conditions** (all must hold):
1. **Mutual exclusion**: Resources cannot be shared
2. **Hold and wait**: Process holds resources while waiting for others
3. **No preemption**: Resources cannot be forcibly taken
4. **Circular wait**: Circular chain of processes waiting for each other

---

## D16: Eventual Consistency

**Eventual consistency**: If no new updates, all replicas will eventually converge to the same value.

**Cassandra read-after-write**:
- Writes go to multiple replicas (based on consistency level)
- Reads may see stale data if reading from different replicas
- **Tunable consistency levels**:
  - **ONE**: Fastest, least consistent
  - **QUORUM**: Balanced (default)
  - **ALL**: Most consistent, slowest
  - **LOCAL_QUORUM**, **EACH_QUORUM**: Datacenter-aware

---

## D17: mTLS (Mutual TLS)

**mTLS**: Both client and server authenticate each other with certificates.

**Handshake process**:
1. Client sends ClientHello
2. Server sends ServerHello + server certificate
3. **Client verifies server certificate**
4. Server requests client certificate (CertificateRequest)
5. **Client sends client certificate**
6. **Server verifies client certificate**
7. Both generate shared secret, encrypt traffic

**Infrastructure use cases**:
- Service mesh (Istio, Linkerd) for service-to-service auth
- Database connections
- Internal API authentication
- Zero-trust network architectures

---

## D18: Hash Table Internals

**How it works**:
- Key → hash function → bucket index
- Store value at bucket

**Collision resolution**:
- **Chaining**: Each bucket holds a linked list of entries
- **Open addressing**: Find next available slot (linear/quadratic probing, double hashing)

**Time complexity**:
| Operation | Average | Worst Case |
|-----------|---------|------------|
| Insertion | O(1) | O(n) |
| Lookup | O(1) | O(n) |
| Deletion | O(1) | O(n) |

Worst case occurs when all keys hash to same bucket (poor hash function or adversarial input).

---

## D19: Circuit Breaker Pattern

**Circuit breaker**: Prevents cascade failures by stopping calls to failing services.

**Three states**:
1. **Closed**: Normal operation, requests pass through
2. **Open**: Failing, requests fail fast without calling service
3. **Half-open**: Testing recovery, allow limited requests through

**Prevents cascade failures**: By failing fast when a service is down, preventing thread/connection pool exhaustion in calling services.

**Relation to retry/backoff**:
- Retries can help with transient failures but worsen cascades
- Exponential backoff spreads retry load over time
- Circuit breaker should be combined with retries (retry before opening circuit)

## D20: Optimistic vs Pessimistic Concurrency Control

**Pessimistic**: Lock resources before access. Assumes conflicts are likely.
- **Example**: `SELECT ... FOR UPDATE` locks rows
- **Choose when**: High contention, financial transactions, data integrity critical

**Optimistic**: Allow concurrent access, detect conflicts at commit time. Assumes conflicts are rare.
- **Example**: Row versioning with `SELECT ... FOR UPDATE` or `SELECT ... SKIP LOCKED`
- **Choose when**: Read-heavy workloads, low contention, better performance needed

**Concrete example**:
```sql
-- Pessimistic
BEGIN;
SELECT balance FROM accounts WHERE id=1 FOR UPDATE;
-- Update balance
UPDATE accounts SET balance = balance - 100 WHERE id=1;
COMMIT;

-- Optimistic (using version column)
SELECT balance, version FROM accounts WHERE id=1;
-- Application checks version hasn't changed
UPDATE accounts SET balance = balance - 100, version = version + 1 
WHERE id=1 AND version = <original_version>;
-- Check affected rows = 1 for conflict detection
```
