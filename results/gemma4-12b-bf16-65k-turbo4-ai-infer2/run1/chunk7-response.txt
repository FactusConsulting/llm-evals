## Application Architecture

**AA1 — Easy: What is the difference between a monolith and a microservices architecture? Name 3 concrete problems that microservices introduce that monoliths don't have.**
A **Monolith** is a single unified unit where all components (UI, business logic, data access) share the same memory space and database. A **Microservices** architecture decomposes this into small, independent services communicating over a network.
Three problems introduced by microservices:
1.  **Network Latency:** Every inter-service call adds overhead compared to in-memory calls.
2.  **Distributed Data Consistency:** Maintaining ACID properties across multiple databases requires complex patterns like Sagas.
3.  **Operational Complexity:** Monitoring, deploying, and debugging a distributed system is significantly harder than a single application.

**AA2 — Easy: Explain the difference between synchronous and asynchronous communication between services. Give an example technology for each.**
**Synchronous:** The client sends a request and waits (blocks) for a response before proceeding. Example: **REST/gRPC**.
**Asynchronous:** The client sends a message/request and continues its work without waiting for an immediate response; the result is handled later via a callback or polling. Example: **RabbitMQ / Apache Kafka**.

**AA3 — Medium: What is the difference between an API Gateway and a reverse proxy? Can an API Gateway replace a reverse proxy entirely? Why or why not?**
A **Reverse Proxy** primarily handles request routing, load balancing, and SSL termination. An **API Gateway** does all of that plus "edge" logic like authentication, rate limiting, request transformation, and protocol translation. 
An API Gateway *can* replace a reverse proxy because it encompasses its functionality, but in very high-traffic scenarios where only simple proxying is needed, using a dedicated reverse proxy (like Nginx) might be preferred to avoid the overhead of gateway logic.

**AA4 — Medium: Explain the Saga pattern for distributed transactions. What is the difference between choreography-based and orchestration-based sagas? When is each appropriate?**
The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. If one fails, the system executes "compensating transactions" to undo previous steps.
*   **Choreography:** Each service produces/consumes events; there is no central coordinator. Best for simple workflows with few participants.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows with many steps to avoid "spaghetti" event flows.

**AA5 — Medium: What is CQRS (Command Query Responsibility Segregation)? Why is it often paired with Event Sourcing? What problem does this combination solve that a traditional CRUD model doesn't?**
**CQRS** separates read operations (Queries) from write operations (Commands), allowing independent scaling of reads vs writes. It is paired with **Event Sourcing**, which stores all changes as a sequence of immutable events rather than just current state. 
This solves the problem of handling high-concurrency updates while simultaneously providing complex, performant query views that are difficult to maintain in a standard CRUD model where the schema must satisfy both requirements at once.

**AA6 — Medium: Explain the Circuit Breaker pattern. What are the three states? How does it differ from a simple retry with backoff, and when would you use both together?**
The **Circuit Breaker** prevents a failing service from causing cascading failures by "tripping" when error thresholds are met. States: **Closed** (normal operation), **Open** (failing fast without calling the remote service), and **Half-Open** (testing if the service has recovered).
*   **Difference:** Retries handle transient blips; Circuit Breakers handle systemic outages/slowdowns.
*   **Together:** Use retries for short network hiccups; use Circuit Breakers to stop hitting a dead service so the system can recover.

**AA7 — Hard: You're designing a multi-tenant SaaS platform. Compare the following tenant isolation models and their trade-offs across cost, security, operational complexity, and noisy-neighbor risk:**
1.  **Shared DB, Shared Schema (Row-level ID):** Lowest cost, highest scalability, lowest security isolation, high noisy-neighbor risk.
2.  **Shared DB, Separate Schema per Tenant:** Moderate cost, moderate complexity, better logical separation, medium noisy-neighbor risk.
3.  **Separate Database per Tenant:** Highest cost, highest security/isolation, highest operational complexity, lowest noisy-neighbor risk.

**AA8 — Hard: Explain the difference between eventual consistency and strong consistency. A product team wants their inventory system to never oversell. How would you architect this — what consistency model, what data store, and what patterns would you use at scale?**
**Strong Consistency** ensures all reads return the most recent write immediately. **Eventual Consistency** guarantees that if no new updates are made, eventually all accesses will return the last updated value.
To prevent overselling: I would use **Strong Consistency**. At scale, I’d use a distributed SQL database like **Google Spanner** or **CockroachDB**, utilizing **Distributed Locking** or **Atomic Increments** on an "inventory" table with a unique constraint on stock levels.

**AA9 — Medium: What is a sidecar proxy in a service mesh? Explain how Envoy works in an Istio deployment. What is the data plane vs control plane? What problem does mTLS between sidecars solve that application-level TLS doesn't?**
A **Sidecar Proxy** (like Envoy) runs alongside every service instance to handle networking logic. In **Istio**, Envoy acts as the **Data Plane** (handling actual traffic), while Istio's management server acts as the **Control Plane** (configuring policies/routing). 
**mTLS** between sidecars provides identity-based encryption without requiring developers to manage certificates inside their code; it secures the *transport* layer automatically across polyglot services.

**AA10 — Medium: Explain the Strangler Fig pattern. You have a legacy .NET Framework monolith and need to incrementally migrate to .NET 8 microservices. Describe a concrete migration strategy using this pattern.**
The **Strangler Fig** involves building new functionality in microservices around the edges of the old system until the old system is eventually replaced.
Strategy: Place an API Gateway/Proxy in front of the monolith. Identify one bounded context (e.g., "Billing"). Build the Billing microservice in .NET 8. Route all "/billing" traffic to the new service via the proxy, leaving other routes pointing to the monolith. Repeat for other modules until the monolith is empty.

**AA11 — Medium: What is the 12-Factor App methodology? Name at least 6 factors and explain why they matter for cloud-native deployments.**
A set of best practices for building scalable, portable apps. Factors include:
1. Codebase (one repo), 2. Dependencies (explicitly declared), 3. Config (env vars), 4. Backing Services (treat DBs as attached resources), 5. Build, Release, Run (separation), 6. Portability (dev/prod parity). These ensure the app can run anywhere consistently and scale horizontally easily.

**AA12 — Hard: Compare event-driven architecture using an event broker (Kafka) vs request-driven architecture using REST/gRPC. Cover: coupling, scalability, debugging complexity, ordering guarantees, and failure handling. When would you choose each?**
*   **Coupling:** Event-driven is loosely coupled; Request-driven is tightly coupled.
*   **Scalability:** Kafka scales better for high throughput; gRPC is faster for low-latency point-to-point.
*   **Debugging:** Event-driven is harder due to "hidden" flows; REST/gRPC is easier to trace linearly.
*   **Ordering:** Kafka guarantees order within a partition; gRPC relies on application logic.
*   **Failure Handling:** Kafka uses offsets/retries; gRPC requires manual retry logic.
*   **Choice:** Use **REST/gRPC** for synchronous user actions (Login); use **Kafka** for background processing or data pipelines.

**AA13 — Easy: What is a load balancer? Explain the difference between Layer 4 and Layer 7 load balancing. Give one use case where Layer 7 is required.**
A **Load Balancer** distributes incoming traffic across multiple servers.
*   **Layer 4:** Routes based on IP/TCP port (fast).
*   **Layer 7:** Routes based on HTTP headers, cookies, or URL paths (smarter).
*   **L7 Case:** Routing requests to different microservices based on path (e.g., `/api/v1/users` vs `/api/v1/orders`).

**AA14 — Easy: What is a message queue? Explain the difference between a message queue (e.g., RabbitMQ) and a log-based message broker (e.g., Kafka). When would you pick one over the other?**
A **Message Queue** stores messages until they are consumed and then deletes them. A **Log-based Broker** appends messages to an immutable log; consumers track their own position (offset).
Pick **RabbitMQ** if you need complex routing logic and "work queues." Pick **Kafka** if you need high throughput, replayability of data, or stream processing.

**AA15 — Easy: What is a container and how does it differ from a virtual machine? Why are containers popular for deploying microservices?**
A **VM** virtualizes hardware (includes a full Guest OS); a **Container** virtualizes the OS kernel (shares the host OS). Containers are lighter, start faster, and allow for higher density, making them ideal for packing many small microservices onto a single host.

**AA16 — Easy: Explain the difference between stateless and stateful services. Why are stateless services easier to scale horizontally? Give an example of each.**
**Stateless** services do not store client context between requests (each request contains all info needed). They are easy to scale because any instance can handle any request. 
**Stateful** services maintain session/data (e.g., a Database). Scaling these requires complex synchronization.
*   Example Stateless: Web Server / Auth Service.
*   Example Stateful: PostgreSQL / Redis.

**AA17 — Easy: What is an ORM (Object-Relational Mapper)? Name two popular ORMs in different languages. What are the trade-offs of using an ORM vs writing raw SQL?**
An **ORM** maps database tables to objects in code. Examples: **Hibernate** (Java), **SQLAlchemy** (Python).
*   **Pros:** Faster development, cleaner code, handles boilerplate.
*   **Cons:** Can produce inefficient queries ("N+1 problem"), less control over optimization compared to raw SQL.

**AA18 — Medium: Explain the Bulkhead pattern. How does it relate to resource isolation in a microservices architecture? Give a concrete example of how you would implement bulkheads using thread pools or separate deployment groups.**
The **Bulkhead** pattern isolates resources so that if one component fails, others continue to function (like compartments in a ship).
In microservices, this prevents one slow service from consuming all available threads on a shared server. Implementation: Use dedicated **thread pools** for different external API calls (so a slow "Payment" call doesn't exhaust threads needed for "Search") or deploy services into isolated **deployment groups/clusters**.

**AA19 — Hard: You are designing a real-time collaborative editing system (like Google Docs). Compare Operational Transformation (OT) and CRDTs as conflict resolution strategies. Cover: consistency guarantees, latency, complexity, and offline support. Which would you choose for a system that must support offline editing and why?**
*   **OT:** Centralized authority; requires complex transformation logic but is very mature (Google Docs uses OT). High complexity for many users.
*   **CRDTs:** Mathematically designed to merge automatically without a central coordinator. Lower complexity for merging, higher memory overhead.
*   **Choice:** I would choose **CRDTs** because they naturally support **offline editing**, as the data structures can be merged locally and synced whenever connectivity returns without needing a constant connection to a central sequencer.

**AA20 — Hard: Explain the challenges of distributed tracing across a polyglot microservices ecosystem. Cover: context propagation (W3C Trace Context, B3), sampling strategies (head-based vs tail-based), trace storage and querying (Jaeger, Tempo), and how tracing interacts with asynchronous messaging. How do you ensure trace continuity when a request passes through Kafka?**
Challenges include maintaining a unique `trace_id` across different languages/frameworks (**Context Propagation**) using standards like W3C Trace Context. 
**Sampling:** Head-based samples at the start (high volume); Tail-based keeps traces only if an error occurs or latency is high.
**Kafka Continuity:** You must inject the trace headers into the message metadata (e.g., Kafka Headers) so the consumer can extract them and continue the span. Tracing in async systems requires "linking" spans rather than just nesting them.

## On-Premise Infrastructure Architecture

**OP1 — Easy: Explain the difference between a hypervisor Type 1 (bare-metal) and Type 2 (hosted). Give 2 examples of each.**
*   **Type 1:** Runs directly on hardware. Examples: **ESXi, KVM**.
*   **Type 2:** Runs as an application on an OS. Examples: **VirtualBox, VMware Workstation**.

**OP2 — Easy: What is a SAN vs NAS? When would you use each? What protocols does each typically use?**
*   **SAN (Storage Area Network):** Block-level storage. Used for high-performance DBs where low latency is key. Protocols: **Fibre Channel, iSCSI**.
*   **NAS (Network Attached Storage):** File-level storage. Used for shared files/folders. Protocols: **NFS, SMB**.

**OP3 — Medium: Explain a 3-tier network architecture (core/distribution/access). Why is leaf-spine preferred in modern data centers? What problem does it solve that 3-tier doesn't?**
The 3-tier model creates bottlenecks at the core during East-West traffic. **Leaf-Spine** provides a non-blocking fabric where every Leaf connects to every Spine. This ensures predictable, low-latency "East-West" traffic (server-to-server), which dominates modern microservice environments compared to traditional North-South user traffic.

**OP4 — Medium: You need to design a highly available Proxmox cluster with shared storage. Describe the architecture covering: node count, quorum, fencing, shared storage options (Ceph, iSCSI, NFS), and what happens during a node failure.**
Architecture: Minimum **3 nodes** (for odd number quorum). Use **Corosync/Pacemaker** for clustering. Fencing (**STONITH**) is mandatory to power off failed nodes. Shared storage: **Ceph** is preferred for native integration. On failure, Corosync detects loss of heartbeat, STONITH kills the dead node, and the remaining nodes mount the shared volume and restart VMs.

**OP5 — Medium: What is VLAN trunking? Explain 802.1Q tagging. A server has a single NIC but needs to be on 3 VLANs — how do you configure this on Linux?**
VLAN trunking allows multiple VLANs to travel over one physical link. **802.1Q** adds a tag to the Ethernet frame identifying its VLAN ID. To configure 3 VLANs on one NIC in Linux, create sub-interfaces using `ip link` or `bridge` commands (e.g., `eth0.10`, `eth0.20`, `eth0.30`) and assign them to respective bridge interfaces.

**OP6 — Medium: Explain the difference between RAID 1, RAID 5, RAID 6, RAID 10, and RAID Z2 (ZFS). You have 6 drives and need to balance performance, capacity, and fault tolerance for a database server — which do you choose and why?**
*   RAID 1: Mirroring.
*   RAID 5: Parity (1 drive failure allowed).
*   RAID 6: Double parity (2 failures).
*   RAID 10: Striped Mirrors (Fastest/Safe).
*   RAID Z2: ZFS dual parity.
**Choice:** **RAID 10**. It provides the best balance of high IOPS (needed for DB) and redundancy by striping across mirrored pairs.

**OP7 — Hard: Design a DNS architecture for a 500-person enterprise with: internal Active Directory, a DMZ with public-facing services, split-horizon DNS, and DNSSEC on the external zone. Cover: recursive resolvers, authoritative servers, forwarders, conditional forwarding, and what happens when a laptop moves between office and VPN.**
Architecture: Internal clients use **Recursive Resolvers** that point to **Authoritative Servers**. Use **Split-Horizon**: External queries see only public IPs; internal queries see private IPs. Use **Conditional Forwarding** to send AD queries to Domain Controllers. For VPN users, the VPN gateway must provide a DNS proxy or push the internal DNS server IP to the client so they can resolve local resources via the tunnel. Apply **DNSSEC** to the public zones to prevent cache poisoning.

**OP8 — Hard: Explain the PKI chain of trust from root CA to end-entity certificate. You need to deploy an internal PKI for your organization. Cover: root CA (offline), subordinate/issuing CA, CRL vs OCSP, certificate templates, and auto-enrollment. What are the consequences of a compromised subordinate CA vs a compromised root CA?**
Chain: Root CA signs Subordinate CA -> Subordinate CA signs End-Entity certificates. Keep the **Root CA offline** to protect it. Use **CRL** (list of revoked certs) or **OCSP** (real-time check). Use **Certificate Templates** to define permissions. 
*   Compromised Subordinate: Only those specific certs are at risk; you revoke the sub's cert.
*   Compromised Root: The entire PKI is dead; every certificate issued by that root is untrusted.

**OP9 — Hard: You're consolidating 5 remote offices into a hub-and-spoke WAN. Compare: MPLS, IPsec VPN over internet, SD-WAN, and WireGuard mesh. Cover: cost, reliability, latency, management complexity, and security posture. Which would you recommend for a company with 50 users per site and latency-sensitive VoIP?**
*   MPLS: Reliable but expensive.
*   IPsec: Cheap but unpredictable.
*   SD-WAN: Best balance (manages multiple paths/prioritizes traffic).
*   WireGuard Mesh: Fast, modern encryption, but harder to manage at scale without an overlay manager.
**Recommendation:** **SD-WAN**. It allows for "Application Aware Routing" to prioritize VoIP packets over standard web traffic while using cheaper internet links where possible.

**OP10 — Medium: What is iDRAC/iLO/IPMI? Why is out-of-band management critical? What happens if your IPMI interface is exposed to the internet?**
These are hardware controllers providing access to power, BIOS, and KVM even when the OS is crashed or off. Out-of-band (OOB) is critical because it allows recovery from a dead server. If exposed to the internet, attackers can gain full remote control of the physical hardware, allowing them to reinstall the OS, steal data, or run miners.

**OP11 — Medium: Explain the difference between LVM, LVM-Thin, and ZFS. When would you use each? What are the snapshot semantics for each?**
*   **LVM:** Logical volumes; traditional block management. Snapshots are "Copy-on-Write" (COW), which degrades performance as they age.
*   **LVM-Thin:** Allows thin provisioning (overprovisioning). Better for many small VMs.
*   **ZFS:** A combined filesystem + volume manager. Native COW snapshots that do not degrade performance significantly and include compression/deduplication. Use ZFS for high-reliability storage needs.

**OP12 — Hard: You have a 3-node Proxmox cluster with Ceph storage and need to survive a complete site failure. Design a stretch cluster or DR strategy. Cover: Ceph CRUSH rules, monitor placement, network latency requirements, and the split-brain problem. Why is 2-site Ceph generally a bad idea without a tiebreaker?**
To survive a site failure, you need at least **3 sites** (or a 3rd location) to maintain quorum. If Site A fails in a 2-site setup, both remaining nodes might think they are the leader (**Split-Brain**). To solve this, place a lightweight "Witness" node in a 3rd physical location. For Ceph, ensure `failure_domain=host` or `rack`. Latency between sites must be low enough (<10ms ideally) to avoid slow writes.

**OP13 — Easy: What is DHCP and how does the DORA process work? What happens when a DHCP server is unavailable and a Windows client's lease expires?**
DHCP assigns IPs automatically. **DORA**: Discover (Client), Offer (Server), Request (Client), Acknowledge (Server). If the server is down during renewal, the client continues using its current IP until the lease time expires, then it will attempt to renew/request again but fail, eventually losing connectivity.

**OP14 — Easy: Explain the difference between a managed switch and an unmanaged switch. What features does the managed switch provide that are important in an enterprise environment?**
Unmanaged switches are "plug and play." Managed switches allow for configuration of **VLANs**, **Quality of Service (QoS)** for prioritizing voice traffic, **SNMP** for monitoring, and **Port Mirroring** for security analysis. These are essential for segmenting networks and ensuring performance.

**OP15 — Easy: What is NTP and why is accurate time synchronization critical in an on-premise environment? What can go wrong when clocks drift between servers in a cluster?**
NTP synchronizes clocks across the network. It is critical for log correlation, authentication (Kerberos requires tight time sync), and database replication. Clock drift causes logs to be out of order, prevents logins from working, and can cause high-availability clusters to trigger false failovers or split-brain scenarios.

**OP16 — Easy: What is the difference between a physical server, a virtual machine, and a container? When would you run a workload directly on bare metal instead of virtualizing it?**
*   Physical Server: Hardware only.
*   VM: Virtualized hardware (Hypervisor).
*   Container: Virtualized OS (Kernel sharing).
Run on **Bare Metal** for workloads requiring maximum raw performance/low latency (e.g., heavy GPU processing, large databases) or if there is no overhead tolerance.

**OP17 — Easy: Explain the difference between a UPS (Uninterruptible Power Supply) and a generator in a data center context. Why do you need both? What is the role of an ATS (Automatic Transfer Switch)?**
A **UPS** provides immediate battery power during a flick/outage (seconds/minutes); a **Generator** provides long-term power (hours/days). You need both because generators take time to start up. An **ATS** automatically switches the load from the UPS/Grid to the Generator once it's running.

**OP18 — Medium: Explain the difference between active-passive and active-active clustering for high availability. You have a pair of Linux servers running a PostgreSQL database — describe how you would implement HA using Pacemaker/Corosync, covering fencing (STONITH), virtual IPs, and failover behavior.**
*   **Active-Passive:** One node handles traffic; other sits idle.
*   **Active-Active:** Both nodes handle traffic simultaneously.
For Postgres: Use **Pacemaker/Corosync**. Configure a **Virtual IP (VIP)** that moves between nodes. Use **STONITH** to ensure only one node can own the VIP at a time. If Node A fails, Corosync detects loss of heartbeat, Pacemaker triggers STONITH to kill Node A, and then promotes Node B as primary, moving the VIP to Node B.

**OP19 — Hard: You are designing the backup and recovery strategy for a 50-server on-premise environment. Cover: the 3-2-1 rule, RPO/RTO requirements, backup types (full/incremental/differential), deduplication, tape vs disk vs cloud offsite, immutable backups for ransomware protection, and how you test restores. What is the difference between backup and disaster recovery?**
Strategy: Follow **3-2-1 Rule** (3 copies, 2 media, 1 offsite). Define **RPO** (max data loss) and **RTO** (max downtime). Use **Incremental** backups daily with weekly **Fulls**, using **Deduplication** to save space. Store on local **Disk** + Cloud/Tape. Implement **Immutable Backups** (WORM storage) to prevent ransomware from deleting backups. Test by performing monthly "Restore Drills."
*   **Backup:** Copying data.
*   **Disaster Recovery:** The process/plan to restore operations after a catastrophe.

**OP20 — Hard: Explain how 802.1X (port-based network access control) works in an enterprise wired network. Cover: the supplicant, authenticator, and authentication server roles; EAP methods (EAP-TLS vs PEAP); RADIUS; dynamic VLAN assignment; and what happens to a device that fails authentication. How does MAB (MAC Authentication Bypass) work for devices that don't support 802.1X?**
In 802.1X: The **Supplicant** is the client software; the **Authenticator** is the switch; the **Auth Server** is a RADIUS server. It uses **EAP-TLS** (Certificates) or **PEAP** (Username/Pass). Upon success, the RADIUS server sends a **Dynamic VLAN ID** to put the user in their specific segment. If auth fails, the port is blocked or moved to a restricted "Guest" VLAN. **MAB** bypasses this by checking the MAC address against a whitelist—used for printers/IoT devices that can't run 802.1X clients.
