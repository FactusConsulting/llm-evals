## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` is a dry run that compares the current state with the configuration files to generate an execution plan (what will change). `tofu apply` executes those changes to reach the desired state defined in the configuration.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file mapping real-world resources to your configuration code. Remote state is critical for team collaboration; it provides a single source of truth, enables state locking to prevent concurrent modifications, and allows multiple users/CI systems to work on the same infrastructure safely.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an integer index (e.g., 0, 1, 2) to replicate resources. `for_each` uses a map or set of strings as keys. `for_each` is preferred because it prevents "index shifting"—if you delete the second item in a `count=3` list, OpenTofu might try to rename/recreate items at indices 1 and 2. `for_each` keeps resource identities tied to specific keys regardless of order.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This is called "Configuration Drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the cloud provider's API. It compares the actual live attributes against the desired configuration. If they differ, OpenTofu will propose a plan to revert the manual changes back to the configuration's defined state.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
variable "vm_names" {
  type    = set(string)
  default = ["web1", "web2", "web3"]
}

resource "null_resource" "vms" {
  for_each = toset(var.vm_names)
  provisioner "local-exec" {
    command = "echo Creating VM ${each.key}"
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads the state file of another workspace/module. This creates tight coupling; if the remote module changes its outputs, the consuming module breaks. The recommended alternative is passing variables into child modules from a parent orchestrator or using a shared "data" module. This keeps modules decoupled and makes dependencies explicit in the code rather than hidden in the state file.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
This happens because `tofu plan` cannot predict the result of a `remote-exec` script (it doesn't know what the script will return). On the first apply, the resource exists but the output hasn't been populated yet for downstream consumers. **Fix:** Use a local variable to capture the output within the same module, or use a `null_resource` with a `triggers` argument so OpenTofu knows the resource must be recreated/updated before the next step. Better yet, avoid `remote-exec` for outputs; use native provider resources where possible.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
Import brings existing infrastructure into management without destroying it. Limitations include manual effort (you must write the HCL manually) and potential errors in mapping attributes. The `import` block allows you to declare the import in code, allowing OpenTofu to handle the state generation during the plan phase, making it more declarative and easier to review via PRs.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a parameter for your configuration. An input variable (`variable`) is a value provided by the user at runtime (like an environment variable). An output (`output`) is a value returned by the module after execution (like a Load Balancer IP address).

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates OpenTofu's configuration into API calls for specific platforms (AWS, Azure, etc.). If you run `plan` before `init`, it will fail because the binary plugins haven't been downloaded or initialized in the `.terraform` directory.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It is a dependency lock file. It records the exact versions of providers used. Committing it ensures that every team member and CI/CD runner uses the identical provider versions, preventing "it works on my machine" issues caused by automatic provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the current state file. To target a single resource, use the `-target` flag: `tofu destroy -target=aws_instance.web_server`.

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source allows you to fetch information about existing infrastructure without managing its lifecycle. Example: Fetching the AMI ID of the latest Ubuntu image from AWS; you want to *use* the ID (data), but you don't want OpenTofu to *manage* the creation of the AMI itself.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are inputs provided by users (external). Locals are internal constants derived within the module. Use `locals` for values calculated from other variables or repeated logic (e.g., constructing a complex naming convention string) that shouldn't be changed by the user.

**T15 — Medium: What is the lifecycle block in a resource? Explain create_before_destroy, prevent_destroy, and ignore_changes with a use case for each.**
The `lifecycle` block modifies how OpenTofu handles resource changes.
- `create_before_destroy`: Ensures a new instance is up before deleting the old one (Use Case: High availability web servers).
- `prevent_destroy`: Prevents accidental deletion (Use Case: Production databases).
- `ignore_changes`: Tells OpenTofu to ignore specific attribute updates (Use Case: Ignoring tags added by an external automated system like AWS Auto Scaling).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has been renamed or relocated in the code. It allows you to move a resource into a module or rename its address in the HCL without triggering a "Destroy/Create" cycle; OpenTofu simply updates the state mapping to the new name.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG) of all resources. **Implicit:** Dependencies created automatically because Resource B references an attribute of Resource A. **Explicit:** Defined via `depends_on`. `depends_on` forces a sequence but can hinder parallelism by creating unnecessary bottlenecks; use it only when there are no direct attribute links between resources.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs.**
1.  **State Splitting:** Break one large state file into multiple smaller states (e.g., network, db, app). *Tradeoff:* More complex cross-state referencing.
2.  **Targeted Plans:** Use `-target` for specific changes. *Tradeoff:* Risk of missing side effects in unrelated components.
3.  **Reduce Provider Refresh:** Optimize provider configurations or limit refresh frequency. *Tradeoff:* Might miss minor drift.
4.  **Use Workspaces/Modules:** Modularize code so plans only run on changed modules. *Tradeoff:* Requires more architectural planning upfront.

**T19 — Hard: Explain how OpenTofu's state locking mechanism works. What happens if a lock is not released? How do you manually break a lock, and what are the risks?**
Locking prevents two people from running `apply` simultaneously. If a CI pipeline crashes, the lock remains in the backend (e.g., DynamoDB). To fix it, use `tofu force-unlock <LOCK_ID>`. **Risk:** You might cause state corruption if another process actually did make partial changes while you forced the unlock.

**T20 — Hard: You need to migrate an existing OpenTofu project from local state to S3 with DynamoDB locking. Describe the step-by-step process.**
1. Create the S3 bucket and DynamoDB table.
2. Add the `backend "s3"` block to your configuration.
3. Run `tofu init`. It will detect the change and ask to migrate.
4. Confirm migration; OpenTofu copies the local `.tfstate` to S3.
5. Verify by checking the S3 bucket for the new state file and ensuring the DynamoDB table shows a lock entry during a subsequent `plan`.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
Task: A single action (e.g., install a package). Role: A reusable bundle of tasks, variables, and files organized into a directory structure. Playbook: A YAML file that maps hosts to roles/tasks to be executed.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
Ansible Facts are system information gathered by Ansible at runtime. Access the OS family via `ansible_os_family` (e.g., `RedHat`, `Debian`).

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
- `command`: Default module; does not support pipes or redirects (`|`, `>`). Use for simple commands.
- `shell`: Runs through the shell (sh/bash); supports pipes and redirects. Use when complex logic is needed.
- `raw`: Bypasses Python; sends the string directly to the OS. Use only if the target node has no Python installed.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means running a task multiple times results in the same state without extra changes. 
*Idempotent:* `apt: name=nginx state=present` (checks if nginx exists first).
*Non-idempotent:* `shell: echo "data" >> /tmp/file` (appends every time it runs). To make it idempotent, check if the file contains the data first.

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS family
  apt:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install EPEL and htop on RedHat
  yum:
    name: ["epel-release", "htop"]
    state: present
  when: ansible_os_family == "RedHat"
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
Precedence (Highest to Lowest):
1. Extra vars (`-e`)
2. Host vars
3. Group vars
4. Role defaults
5. Inventory variables
*Note:* `set_fact` is high but generally lower than `extra_vars`.

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this?**
Use `serial: 3` at the play level to process hosts in batches of 3. Use `wait_for` if a specific service port needs to be open before proceeding. Organize into groups if different configurations are needed for subsets.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
Ansible Vault encrypts sensitive data. To encrypt only one variable, use `ansible-vault encrypt_string` to generate the encrypted string, then paste that string into your standard YAML file as the value for that specific key.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory lists the managed hosts. Static inventory is a manual list (INI/YAML). Dynamic inventory pulls host lists from cloud providers (AWS/GCP) via plugins, updating automatically as instances scale.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
Handlers are tasks triggered by a change in another task (e.g., restarting Nginx after a config change). Unlike regular tasks which run every time, handlers only run once at the end of a play unless notified multiple times. Triggered using `notify`.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
It configures Ansible's behavior. Common settings: `remote_interpreter`, `forks` (parallelism), and `host_key_checking`.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
`register` saves the output of a task into a variable. Use it like this:
Task 1: `name: run cmd; register: my_result`
Task 2: `debug: msg="{{ my_result.stdout }}"`

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
- `import_tasks`: Static. Included at the start of parsing. Conditions (`when`) on the *parent* playbook apply to all tasks inside.
- `include_tasks`: Dynamic. Included during execution. Allows conditions to be evaluated based on variables gathered during the run.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Galaxy is a hub for sharing community-maintained roles/collections. Create a `requirements.yml` listing names/versions, then run `ansible-galaxy -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins define how Ansible communicates with targets.
- `ssh`: Standard remote execution via SSH (default).
- `local`: Runs commands on the control node itself.
- `network_cli`: Uses APIs (like `netconf` or `rest_conf`) instead of SSH; used for networking gear like Cisco switches.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
- `delegate_to`: Executes a task on a specific host (e.g., localhost).
- `run_once`: Ensures a task runs only one time across the whole batch.
*Example:* Gather facts from all web servers, then use `delegate_to: localhost` and `run_once: true` to send an aggregate summary email from the control node.

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance.**
1. **Forks:** Increase `-f` (max parallel processes). *Tradeoff:* Higher CPU/Memory usage on control node.
2. **Pipelining:** Reduces the number of SSH connections by multiplexing. *Tradeoff:* Requires specific OS support.
3. **Fact Caching:** Cache results in Redis/JSON files so facts aren't re-gathered every run. *Tradeoff:* Risk of stale data if infrastructure changes rapidly.
4. **Mitogen:** A plugin that replaces the standard SSH transport with a faster protocol. *Tradeoff:* Third-party dependency management.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
- `{{ }}`: Expressions (outputting values).
- `{% %}`: Statements (logic like loops, ifs).
- `{# #}`: Comments (ignored during execution).
*Snippet:*
```jinja2
upstream my_backend {
{% for server in backend_servers %}
  server {{ server.ip }} max_fails=3; {# Health Check Node: {{ server.name }} #}
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible.**
1. Set `serial: 2` or `serial: 1` to update hosts in small batches.
2. Use a `pre_tasks` block to add the node's IP to a "maintenance" group/LB pool if needed.
3. Deploy code/config changes.
4. Run a task using the `uri` module to perform a local health check (`GET /health`).
5. If healthy, proceed; else, use a `block/rescue` structure to trigger a rollback (revert symlinks) and stop the play.
6. Update LB status to "active".
