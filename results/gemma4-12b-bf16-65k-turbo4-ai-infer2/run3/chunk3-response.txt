## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` is a dry-run operation that creates an execution plan. It compares the current state against the configuration files to show what changes will occur without actually making them. `tofu apply` executes those planned actions to reach the desired state defined in the code.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file that maps real-world resources to your configuration. It tracks metadata, dependencies, and resource attributes. Remote state is critical because it allows teams to collaborate on the same infrastructure; it provides a single source of truth, prevents concurrent modification conflicts via locking, and ensures consistency across different environments.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an integer index to create multiple instances. `for_each` uses a map or set of strings/objects. `for_each` is preferred when creating complex objects where order doesn't matter (e.g., naming web servers) because changing one item in a `count` list can cause "index shifting," leading to unnecessary resource recreation.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This is known as "Configuration Drift." During the next `tofu plan`, OpenTofu performs a "refresh" by querying the cloud provider API. It compares the actual live state with the local state file and the code. If they differ, OpenTofu will propose a plan to revert the manual changes back to the desired state defined in the code.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
variable "vm_names" {
  type    = set(string)
  default = ["web1", "web2", "web3"]
}

resource "null_resource" "vms" {
  for_each = toset(var.vm_names)
  
  provisioner "local-exec" {
    command = "echo Creating VM ${each.key}"
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads the entire state of another workspace (which can be heavy). Using `outputs` from one module into variables of another is cleaner but requires tight coupling. The recommended modern approach is **Module Composition**: pass outputs as inputs directly into child modules within the same configuration, or use a dedicated "Shared Services" state file/module if cross-team boundaries exist.

**T7 — Hard: You have a module that provisions an RKE2 cluster... [output empty on first apply]. Explain why and how to fix it.**
The issue occurs because OpenTofu evaluates outputs during the plan phase before the `remote-exec` provisioner has actually executed. Since the provisioner runs during the *apply* phase, the value isn't available for the plan. 
**Fix:** Use a specialized provider (like the Kubernetes/Helm provider) instead of `null_resource`. If you must stay with `remote-exec`, ensure the dependent resources are not strictly required until after the apply completes by using a separate workflow or a multi-step pipeline.

**T8 — Medium: What is tofu import, and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
The CLI `tofu import` manually maps existing infrastructure to code via a terminal command. Its limitation is that it’s manual and easy to forget in documentation. The `import` block allows you to declare the resource in your code; OpenTofu then handles the mapping automatically during the next plan/apply, making migrations reproducible and version-controllable.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A **variable** is an input parameter used to make configurations dynamic (e.g., instance size). An **output** is a return value produced by a module or resource (e.g., a public IP address) that can be used by other modules or displayed in the CLI.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates OpenTofu's generic configuration into API calls for specific platforms (AWS, Azure, etc.). If you run `plan` without `init`, OpenTofu will fail because it hasn't downloaded the necessary binary plugins or initialized the backend configuration.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
This is the Dependency Lock File. It records the exact versions of providers used. Committing it ensures that every team member and CI/CD runner uses the identical provider versions, preventing "it works on my machine" errors caused by automatic minor-version updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the current state file. To target only one specific resource, use the `-target` flag: `tofu destroy -target=aws_instance.web_server`.

**T13 — Easy: What is a data source in OpenTofu? Give an example.**
A data source allows you to fetch information about existing infrastructure that was *not* created by your current configuration. 
**Example:** Fetching the ID of an existing VPC created by a different team so you can place your subnet inside it.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are inputs provided by the user (external). Locals are internal logic—derived values or repeated expressions within a module. Use **locals** when you need to perform complex string manipulation, math, or combine multiple variables into a single object used across several resources within the same module.

**T15 — Medium: What is the lifecycle block in a resource? Explain create_before_destroy, prevent_destroy, and ignore_changes with a use case for each.**
The `lifecycle` block controls how OpenTofu handles resource updates/deletions.
- `create_before_destroy`: Used for high-availability DBs where the new instance must be up before the old one is removed.
- `prevent_destroy`: A safety guard; prevents any action from deleting a critical production database.
- `ignore_changes`: Prevents OpenTofu from reverting manual changes made via the cloud console (e.g., ignoring tags added manually).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has changed its name or location in the code but still refers to the same physical resource in the real world. It allows you to rename a resource in your `.tf` files without triggering a "Destroy -> Create" cycle, which would cause downtime.

**T17 — Hard: Explain how OpenTofu's dependency graph works... How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG) based on resource references (implicit dependencies). If Resource B uses an attribute of Resource A, B waits for A. **Explicit** dependencies use `depends_on`. These force a strict order even if no data link exists. They reduce parallelism because they create bottlenecks where OpenTofu cannot run tasks concurrently, potentially slowing down deployments significantly.

**T18 — Hard: You have 200+ resources and plan takes over 10 minutes. Identify at least 4 strategies.**
1.  **State Splitting:** Break one giant state file into multiple smaller states (e.g., Network, DB, App). *Tradeoff:* Complexity in managing cross-state dependencies.
2.  **Module Decomposition:** Smaller modules allow for more granular updates. *Tradeoff:* More boilerplate code.
3.  **Targeted Plans:** Use `-target` to only update specific components during rapid iterations. *Tradeoff:* Risk of missing side effects.
4.  **Provider Caching/Parallelism:** Increase the number of concurrent operations or optimize provider configurations. *Tradeoff:* Can hit API rate limits.

**T19 — Hard: Explain the OpenTofu state locking mechanism... How do you manually break a lock?**
Locking prevents two people from running `apply` simultaneously, which would corrupt the state file. If a CI pipeline crashes, the lock remains "stuck." To fix it, use `tofu force-unlock <LOCK_ID>`. The risk is that if another process actually started writing to the state while the crash happened, manual unlocking could lead to state corruption or duplicate resource creation.

**T20 — Hard: You need to migrate an existing project from local state to S3 with DynamoDB locking. Describe the step-by-step.**
1. Create the S3 bucket and DynamoDB table (manually or via separate Tofu).
2. Update the backend configuration block in your code to point to the new S3/DynamoDB details.
3. Run `tofu init -reconfigure` (or `migrate`). This copies the current local `.tfstate` into the remote bucket.
4. Verify by running `tofu plan`; ensure there are zero changes planned for existing resources.
5. Confirm the state content matches using `tofu state list`.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
A **task** is a single action (e.g., install Nginx). A **role** is a way to group tasks, variables, and files into a reusable component. A **playbook** is a collection of plays that define how roles/tasks are applied to specific hosts.

**A2 — Easy: What is ansible_facts and how do you access the OS family?**
Ansible "Facts" are system variables gathered at the start of a run. You can check the OS family using the variable `ansible_os_family` (e.g., `RedHat`, `Debian`).

**A3 — Medium: Explain the difference between command, shell, and raw modules.**
- `command`: Runs the command directly; no shell features (no pipes, redirects). Fastest/Safest.
- `shell`: Runs through `/bin/sh`. Supports pipes and environment variables. Use when complex logic is needed.
- `raw`: Bypasses Python execution on the target host. Used only for bootstrapping or fixing broken systems where Python isn't installed.

**A4 — Medium: How does Ansible handle idempotency? Give an example.**
Idempotency means running a playbook multiple times results in the same state without making changes if already correct. 
*Idempotent:* `apt: name=nginx state=present` (checks if Nginx exists first).
*NOT Idempotent:* `shell: echo "hello" >> /file` (appends every time it runs). To make this idempotent, use the `lineinfile` module.

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS family
  hosts: all
  tasks:
    - name: Install requirements
      become: yes
      package:
        name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
        state: present
      when: ansible_os_family in ['Debian', 'RedHat']
```

**A6 — Hard: Explain Ansible's variable precedence order.**
Precedence is complex, but generally: **Extra Vars** > **Host Vars** > **Group Vars** > **Role Defaults**. Variables defined in `extra_vars` (passed via CLI) always win over everything else. `set_fact` also has very high priority during runtime.

**A7 — Hard: You need to deploy RKE2 agent on 50 nodes... first 3 must complete before rest start.**
Use the `serial` keyword at the play level: `serial: 3`. This ensures Ansible processes hosts in batches of 3. To ensure they finish completely before moving to the next batch, use `serial: 3` combined with any necessary `wait_for` tasks for port availability or health checks.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
Ansible Vault encrypts files/variables at rest. To encrypt just one variable, use `ansible-vault encrypt --pretty <filename>` and only wrap the specific line/value in the vault block if using certain versions, though typically it encrypts the whole file unless you split secrets into a separate `.vaulted_secrets.yml` file.

**A9 — Easy: What is an Ansible inventory file? Static vs Dynamic?**
An inventory file lists the hosts managed by Ansible. A **static** inventory is a manual list (INI/YAML). A **dynamic** inventory is a script or plugin that queries a cloud provider API (like AWS) to generate the host list in real-time based on tags.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger it?**
Handlers are tasks triggered by a change in another task via the `notify` keyword. Unlike regular tasks which run immediately, handlers run once at the end of the play (unless notified again). Example: Restarting Nginx only if the config file changed.

**A12 — Easy: What is the ansible.cfg file used for? Name 3 settings.**
It is the configuration file for Ansible behavior. Common settings: `remote_user`, `forks` (concurrency), and `host_key_checking`.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable?**
`register` saves the output of a task into a variable. You access it in the next task using that variable name (e.g., `result.stdout`).

**A14 — Medium: Explain include_tasks vs import_tasks.**
`import_tasks` is static; it's processed when the playbook is parsed (faster). `include_tasks` is dynamic; it's processed during execution (allows loops/conditionals). Use `import` for structure, `include` for logic.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file?**
Galaxy is a community hub for roles and collections. A `requirements.yml` file lists these dependencies; you install them via `ansible-galaxy install -r requirements.yml`.

**A16 — Medium: Explain connection plugins... ssh, local, network_cli.**
Connection plugins define *how* Ansible connects to the target. 
- **ssh**: Standard remote execution over SSH.
- **local**: Runs tasks on the control node itself (no network overhead).
- **network_cli**: Used to run commands through an intermediate device (like a proxy or switch CLI) without direct SSH.

**A17 — Hard: Explain delegate_to and run_once. Give a practical example.**
`delegate_to` runs a task on a different host than the current one in the play. `run_once` ensures a task only runs once per play regardless of inventory size.
**Example:** Run a task on `localhost` that triggers a Slack notification using data gathered from a remote server's IP address (`delegate_to: localhost`).

**A18 — Hard: You need to manage 500 hosts and playbook runs take >30 mins. Strategies?**
1.  **Forks:** Increase `-f` (e.g., `forks=50`) to increase parallel executions.
2.  **Pipelining:** Enable `pipelining = True` in `ansible.cfg` to reduce the number of SSH connections required for each task.
3.  **Fact Caching:** Use Redis/Memcached to store facts so they aren't re-gathered every time.
4.  **Mitogen:** Replace the standard Ansible execution engine with Mitogen, which uses persistent connections to significantly speed up execution. *Tradeoff:* Compatibility issues with some complex modules.

**A19 — Hard: Explain Jinja2 templating... {{ }}, {% %}, {# #}. Write an nginx upstream snippet.**
- `{{ }}`: Expression evaluation (output).
- `{% %}`: Control flow (if, for, set).
- `{# #}`: Comments (not rendered).
```nginx
upstream backend {
  {% for server in servers %}
  server {{ server.ip }};
  {# Health check comment for this node #}
  {% endfor %}
}
```

**A20 — Hard: Describe a zero-downtime rolling deployment across 20 servers.**
1. Set `serial: 2` or `serial: 5` to update small batches at once.
2. **Pre-tasks**: Use `uri` module to verify LB health and remove the target host from rotation.
3. **Tasks**: Run the application update tasks.
4. **Post-tasks/Rescue**: Use `uri` module to perform a health check on the new version. If it fails, use a `rescue` block to roll back the app version and re-add the old version to the LB.
