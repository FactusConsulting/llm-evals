## Go (20 questions)

### G1 — Easy
**Slice vs Array**: An array has a fixed size (`[5]int`), is a value type, and cannot be resized. A slice (`[]int`) is a dynamic view into an underlying array with three parts: pointer, length, capacity. When appending to a slice at capacity, Go allocates a new larger array (typically doubling), copies existing elements, appends the new element, and returns a new slice header. The old array becomes garbage.

### G2 — Easy
`var x int` declares `x` as `int` with zero value 0. `x := 0` is short declaration, inferring type from literal, usable only inside functions. You cannot use `:=` at package level, when you need explicit type (e.g., `var x int64 = 0`), or when redeclaring without at least one new variable in the same scope.

### G3 — Medium
A goroutine is a lightweight, user-space thread managed by the Go runtime, starting with ~2KB stack (grows as needed). OS threads are kernel-managed with ~1MB stacks and expensive to create/switch. The GMP model: G = goroutine, M = OS thread, P = logical processor. The scheduler multiplexes goroutines onto threads; when a goroutine blocks, the scheduler moves it off the thread and runs another, enabling efficient concurrency with far fewer OS threads.

### G4 — Medium
Channels are typed communication mechanisms for goroutines. Unbuffered (`make(chan T)`) blocks send until a receiver is ready and blocks receive until a sender is ready, providing synchronization. Buffered (`make(chan T, n)`) allows sends if buffer has space; sends block when full. Sending to a full buffered channel blocks the sender until another goroutine receives, freeing space.

### G5 — Medium
The `context` package carries deadlines, cancellation signals, and request-scoped values across API boundaries. Minimal example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, err := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
if err != nil { log.Fatal(err) }
resp, err := http.DefaultClient.Do(req)
if err != nil { log.Fatal(err) } // context.DeadlineExceeded on timeout
defer resp.Body.Close()
```

### G6 — Medium
Go interfaces are structural/implicit: a type satisfies an interface if it implements all methods, no explicit `implements` keyword. Java/C# require nominal declaration. The empty interface `interface{}`/`any` accepts any type—powerful for duck typing and generic-like behavior, but dangerous because it lacks compile-time type safety, requires type assertions, can cause runtime panics, and increases cognitive load.

### G7 — Hard
The code is unsafe because Go's memory model doesn't guarantee visibility of writes across goroutines without synchronization. The compiler/CPU can reorder operations; the main goroutine may see `ready = true` but not the updated `data`. Correct alternatives: use a channel (`ch <- "hello"` / `<-ch`), `sync.Mutex` to protect both writes and reads, or `sync.WaitGroup`/`sync.Once` for synchronization.

### G8 — Hard
`sync.Mutex` is an exclusive lock; only one goroutine can hold it. `sync.RWMutex` allows multiple readers (`RLock`) but exclusive writers (`Lock`), ideal for read-heavy workloads. `sync.Map` is optimized for specific patterns: keys written once/read many, read-heavy with occasional writes, or multiple writers. Trade-offs: RWMutex reduces read contention; sync.Map uses copy-on-write (amortized O(1) reads, expensive writes); regular map + mutex is simpler and better for write-heavy workloads.

### G9 — Hard
`go.mod` defines module name, Go version, and dependencies. `go.sum` contains cryptographic checksums for dependency integrity/reproducibility. `go mod tidy` adds missing dependencies, removes unused ones, and updates both files. MVS (Minimum Version Selection) picks the minimum version of each dependency satisfying all constraints, ensuring reproducibility and avoiding unnecessary upgrades.

### G10 — Medium
`defer` schedules a function call to run when the surrounding function returns, used for cleanup. Multiple defers execute LIFO (last deferred runs first). Gotcha in loops: deferred calls don't run per iteration—they accumulate until the function returns, causing resource leaks (e.g., deferring `f.Close()` in a loop keeps files open). Fix: close explicitly inside the loop.

### G11 — Easy
A pointer stores the memory address of another variable, declared with `*T`. Zero value is `nil`. Create a pointer to a struct literal with `&Person{Name: "Alice"}` or `new(Person)` (returns `*Person` with zero values).

### G12 — Easy
`init()` is a special function for package initialization, running when the package is initialized before `main()`. A package can have multiple `init()` functions; they run in source order (top to bottom), and across files in file name order. Dependencies initialize before the package itself.

### G13 — Easy
`make` allocates and initializes slices, maps, and channels, returning a non-zero value (not a pointer). `new` allocates memory for any type, returning a pointer to zeroed memory. `make` works only with slices/maps/channels; `new` works with any type but is typically used for structs or scalars.

### G14 — Easy
Go uses explicit error returns: functions return `(value, error)`. The `error` interface is `type error interface { Error() string }`. Idiomatic pattern: `if err != nil { /* handle */ return err }`. `errors.Is(err, target)` checks if `err` wraps `target` (handles wrapped errors), while `==` checks exact equality. `errors.As(err, &target)` checks if `err` can be cast to a specific error type.

### G15 — Easy
Zero values: map → `nil` (must be initialized with `make`), slice → `nil` (usable with `append`), channel → `nil` (must be initialized with `make`), struct → all fields zero-valued.

### G16 — Medium
A race condition occurs when multiple goroutines access shared data without synchronization, with at least one writing. The `-race` flag instruments code to detect data races at runtime by tracking memory accesses and reporting conflicting unsynchronized accesses. Example: `counter++` from two goroutines. Fix with `sync.Mutex` (lock/unlock around increment) or a channel (send increments through a buffered channel and sum them).

### G17 — Medium
`select` waits on multiple channel operations, blocking until one case can proceed. Unlike `switch` (which evaluates values), `select` waits on channel ops. If multiple cases are ready, it picks one uniformly at random. Timeout example:
```go
select {
case msg := <-ch:
    fmt.Println(msg)
case <-time.After(5 * time.Second):
    fmt.Println("timeout")
}
```

### G18 — Hard
Escape analysis determines whether a variable can be allocated on the stack or must escape to the heap. If a variable's address escapes the function (returned, stored in a global, passed to a function that might store it), it's heap-allocated; otherwise stack-allocated. Inspect with `go build -gcflags="-m"` or `go tool compile -m`. Stack allocation is faster (no GC pressure); heap allocation requires garbage collection, so escape analysis minimizes heap allocations for performance.

### G19 — Hard
`reflect.Type` represents a value's type for introspection; `reflect.Value` represents the runtime value for dynamic reads/writes. Reflection is slow (runtime type checks, interface conversions, heap allocations; often 10-100x slower than static dispatch). Justified for dynamic type handling (serialization, ORM), pre-generics code, or when flexibility outweighs performance. Code generation is better for performance-critical paths.

### G20 — Hard
`go:embed` embeds files into the Go binary at compile time. Single files can be embedded into `[]byte`, `string`, or `embed.FS`; directories use `embed.FS`; `embed.FS` implements `fs.FS`, so it works with `io/fs` functions. Limitations: files must be in the module (no `..` or absolute paths), certain file names are excluded, and pattern matching lacks `**`.

## Rust (20 questions)

### R1 — Easy
Ownership is Rust's memory management system. Three rules: (1) each value has exactly one owner, (2) when the owner goes out of scope, the value is dropped, (3) values can be moved, borrowed, or copied.

### R2 — Easy
`String` is an owned, heap-allocated, mutable UTF-8 string that can grow/shrink. `&str` is a borrowed string slice, immutable. In function signatures, use `&str` for read-only access (most common), `String` when you need to own/modify, and `&mut String` when you need to modify in place.

### R3 — Medium
Borrowing uses references to access a value without taking ownership. Borrow checker rules: many `&T` (shared) references allowed simultaneously; only one `&mut T` (mutable) reference at a time; cannot have `&T` and `&mut T` to the same value simultaneously; references must be valid (lifetime rules).

### R4 — Medium
`Result<T, E>` represents success (`Ok`) or failure (`Err`). `Option<T>` represents presence (`Some`) or absence (`None`). The `?` operator unwraps `Ok`/`Some` or returns `Err`/`None` from the function early. Example:
```rust
use std::fs::File;
use std::io::Read;

fn read_file(path: &str) -> Result<String, std::io::Error> {
    let mut file = File::open(path)?;
    let mut contents = String::new();
    file.read_to_string(&mut contents)?;
    Ok(contents)
}
```

### R5 — Medium
`Box<T>`: single owner, heap-allocated; used for recursive types, trait objects, or large data. `Rc<T>`: single-threaded reference counting, multiple owners but not thread-safe. `Arc<T>`: atomic reference counting, thread-safe, multiple owners across threads. Use `Box` for single ownership/heap allocation, `Rc` for single-threaded shared ownership (e.g., graphs), `Arc` for multi-threaded shared ownership.

### R6 — Medium
Traits define shared behavior, similar to interfaces but more powerful: they can have associated types, generic parameters, and default implementations. Rust traits are explicit (must be implemented), Go interfaces are implicit. Trait objects (`dyn Trait`) use dynamic dispatch, allowing heterogeneous types with runtime overhead. Generics with trait bounds (`T: Trait`) use static dispatch, monomorphized at compile time—faster but each type gets its own code.

### R7 — Hard
The code fails because the compiler can't determine the lifetime of the returned reference—it doesn't know if it's tied to `x` or `y`. Fix with lifetime parameters:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This states the returned reference lives as long as both inputs.

### R8 — Hard
`Send` means a type can be transferred across threads safely. `Sync` means a type can be shared across threads safely (references can be sent). `Rc<T>` is not `Send` because it uses non-atomic reference counting; concurrent increments/decrements would cause data races. `Arc<T>` uses atomic reference counting, making it thread-safe for concurrent use.

### R9 — Hard
`Future` is a state machine representing an asynchronous computation; when polled, it returns `Pending` or `Ready`. `async/await` transforms async functions into state machines implementing `Future`. An executor (e.g., Tokio) polls futures, manages scheduling, and handles I/O events; when a future is `Pending`, the executor moves on. Difference from Go goroutines: Go goroutines are preemptively scheduled with their own stacks; Rust futures are cooperative with no per-future stack (state machine). Go's runtime manages goroutines; Rust's executor manages futures in user space.

### R10 — Medium
`unsafe` blocks allow operations that could violate memory safety. Three things you can do: (1) dereference raw pointers, (2) call unsafe functions (e.g., FFI), (3) access mutable static variables. Unsafe is justified for FFI, performance-critical code where safe alternatives are too slow, implementing safe abstractions requiring low-level control, or when you can prove safety through invariants.

### R11 — Easy
Pattern matching uses `match` to destructure and match values. `match` is exhaustive (must handle all cases); `if let` is convenient for a single pattern and doesn't require exhaustiveness. The compiler enforces exhaustiveness—if `match` doesn't cover all possible values, it's a compile error.

### R12 — Easy
`Vec<T>` is a dynamic, heap-allocated array that can grow/shrink. `[T; N]` is a fixed-size, stack-allocated array with size known at compile time. When pushing beyond capacity, `Vec` allocates a new larger buffer (typically doubling), copies elements, and deallocates the old buffer.

### R13 — Easy
Rust enums are algebraic data types with variants that can carry data, unlike C/Java enums which are simple constants. `Option<T>` is an enum with `Some(T)` or `None`, used instead of null. Rust avoids null pointer errors by using `Option`; the compiler forces handling the `None` case.

### R14 — Easy
`impl` blocks define methods and associated functions for a type. `&self` is an immutable borrow (can read), `&mut self` is a mutable borrow (can modify), `self` takes ownership (consumes the value). Associated functions don't take `self` and are called with `Type::function()` (e.g., `String::new()`).

### R15 — Easy
`derive` automatically implements traits for a type. Common derives: `Debug` (format with `{:?}`), `Clone` (create copies), `PartialEq` (equality), `Serialize`/`Deserialize` (Serde). You cannot derive a trait when the trait requires manual implementation (custom behavior), when fields don't implement the trait, or when the trait has associated types/complex logic.

### R16 — Medium
`Cow<'a, T>` is clone-on-write: it borrows data when possible and clones only when mutation is needed. Useful when data is usually borrowed but occasionally needs to be owned/modified. Example:
```rust
use std::borrow::Cow;

fn process(input: &str) -> Cow<'_, str> {
    if input.starts_with("hello") {
        Cow::Borrowed(input)  // no allocation
    } else {
        Cow::Owned(format!("hello {}", input))  // allocates
    }
}
```

### R17 — Medium
`mod` declares a module (inline or from file), `use` brings items into scope, `pub` makes items public. File system mapping: `mod foo` looks for `foo.rs` or `foo/mod.rs`. In 2018 edition, `foo.rs` can have `mod bar` looking for `foo/bar.rs`. 2015 edition used `mod.rs` files for hierarchies; 2018 allows `foo.rs` with submodules in `foo/` directory.

### R18 — Hard
`Pin<T>` prevents moving a value out of its memory location, ensuring it stays at the same address. Needed for self-referential structs (where a field points to another field) and async futures, which can be self-referential. `Unpin` is a marker trait; types implementing `Unpin` can be moved freely (most types are `Unpin`). `Pin<T>` is only restrictive for `!Unpin` types. In async/await, `Pin` ensures the future isn't moved while being polled.

### R19 — Hard
Declarative macros (`macro_rules!`) match patterns and generate code. Procedural macros are functions that transform code: derive macros (`#[derive(Serialize)]`), attribute macros (`#[test]`), function-like macros (`println!()`). Hygiene rules: declarative macros are hygienic—they don't accidentally capture variables from the caller's scope; procedural macros are less hygienic—they can introduce items into the caller's scope.

### R20 — Hard
Zero-cost abstractions mean high-level constructs compile to efficient machine code with no runtime overhead. Iterators compile to efficient loops (e.g., `.map().filter().collect()` becomes a single loop without intermediate allocations). Generics use monomorphization—each instantiation gets specialized code, no runtime dispatch. Trait static dispatch generates specialized code for each type, avoiding vtable lookups. Result: Rust code can match hand-written C performance while providing safety and ergonomics; the compiler optimizes away abstractions.
