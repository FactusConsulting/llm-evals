## Application Architecture

**AA1 — Monolith vs. Microservices**  
A monolith is a single deployable unit where all components run in one process. Microservices split functionality into independently deployed services. Three concrete problems microservices introduce that monoliths don't:  
1. **Network latency** – every call between services incurs serialization/deserialization and network overhead.  
2. **Distributed data consistency** – transactions span services, requiring patterns like Sagas instead of ACID.  
3. **Operational complexity** – service discovery, configuration, monitoring, and deployment orchestration become first-class concerns.

**AA2 — Synchronous vs. Asynchronous Communication**  
Synchronous: the caller blocks until the receiver responds. Example: REST/HTTP or gRPC.  
Asynchronous: the caller sends a message and continues; the receiver processes later. Example: RabbitMQ, Kafka, or Amazon SQS.  
Synchronous is simpler for request-response; asynchronous decouples services and handles bursts.

**AA3 — API Gateway vs. Reverse Proxy**  
A reverse proxy forwards traffic to backend servers, often performing TLS termination, load balancing, and header manipulation. An API Gateway adds API-specific features: authentication, rate limiting, request routing, aggregation, and API lifecycle management.  
An API Gateway can replace a reverse proxy for API traffic, but not entirely: reverse proxies are still needed for non-API traffic (static files, WebSockets, legacy protocols), and many gateways are themselves built on top of reverse proxies.

**AA4 — Saga Pattern**  
A Saga is a sequence of local transactions where each step has a compensating action to undo previous steps if one fails.  
- **Choreography-based**: services exchange events; each service decides next step. No central coordinator. Good for simple workflows, low coupling.  
- **Orchestration-based**: a central coordinator commands each service. Easier to manage complex workflows, but introduces a single point of coordination.  
Use choreography for simple, event-driven flows; orchestration for complex, long-running processes with clear control.

**AA5 — CQRS and Event Sourcing**  
CQRS separates read models (queries) from write models (commands). Event Sourcing stores state as an immutable sequence of events, with the current state derived by replaying events.  
The combination solves problems of traditional CRUD:  
- **Scalability** – reads and writes can be scaled independently.  
- **Auditability** – every change is recorded, enabling full history and replay.  
- **Temporal queries** – reconstruct state at any point in time.  
It also avoids the object-relational impedance mismatch by using events as the source of truth.

**AA6 — Circuit Breaker Pattern**  
States: **Closed** (normal operation), **Open** (fail fast, no calls), **Half-Open** (allow a few trial calls to test recovery).  
A simple retry with backoff keeps sending requests, risking resource exhaustion. A circuit breaker fails fast and prevents cascading failures.  
Use both together: circuit breaker with internal retries for transient failures (e.g., network blips) while still tripping open on sustained failures.

**AA7 — Multi-Tenant Isolation Models**  
1. **Shared database, shared schema** – lowest cost, simplest ops, but poor isolation; noisy neighbor risk high; security relies on row-level tenant ID.  
2. **Shared database, separate schema** – moderate cost; better isolation (schema-level), but still shared DB resources; noisy neighbor risk medium; ops more complex (schema management).  
3. **Separate database per tenant** – highest cost, best security and performance isolation; noisy neighbor risk low; ops complexity high (many DBs to manage).  
Trade-off: cost vs. isolation. For high-security tenants, separate DBs; for cost-sensitive, shared schema.

**AA8 — Eventual vs. Strong Consistency for Inventory**  
Eventual consistency: updates propagate asynchronously; reads may be stale. Strong consistency: every read sees the latest write.  
To never oversell, you need **strong consistency** on stock decrements. Architecture:  
- Use a single relational database (e.g., PostgreSQL) with `UPDATE inventory SET quantity = quantity - 1 WHERE id = ? AND quantity >= 1` (atomic conditional update).  
- At scale, partition by product ID and use a single writer per partition, or use Redis with Lua scripts for atomic operations.  
- Use optimistic locking (version numbers) or distributed locks (e.g., ZooKeeper) to serialize writes.  
- For high throughput, use a queue to serialize decrements per product.

**AA9 — Sidecar Proxy and Service Mesh**  
A sidecar proxy is a lightweight proxy co-located with each service instance, handling network traffic. In Istio, Envoy sidecars intercept all inbound/outbound traffic.  
- **Data plane**: the sidecars (Envoy) that enforce policies, route traffic, and report telemetry.  
- **Control plane**: Istio components (Pilot, Mixer, Citadel) that configure and manage the data plane, distribute certificates, and collect telemetry.  
mTLS between sidecars provides service-to-service authentication and encryption at the network layer, independent of application-level TLS. This protects all traffic, even if apps don't implement TLS, and enables identity-based policies.

**AA10 — Strangler Fig Pattern**  
Incrementally replace parts of a legacy monolith with new services. For a .NET Framework monolith migrating to .NET 8:  
1. Identify seams (modules, APIs, data boundaries).  
2. Extract one module into a .NET 8 microservice, exposing it via an API.  
3. Use a facade (API Gateway or reverse proxy) to route traffic to the new service.  
4. Gradually move data and logic, keeping the monolith running until the new service is proven.  
5. Repeat until the monolith is fully replaced, then decommission it.

**AA11 — 12-Factor App Methodology**  
Six factors and why they matter:  
1. **Codebase** – one codebase, multiple deploys; ensures consistency.  
2. **Dependencies** – explicit dependency declaration; avoids hidden conflicts.  
3. **Config** – config in environment variables; enables portability across environments.  
4. **Backing services** – treat services as attached resources; allows swapping without code changes.  
5. **Build/release/run** – strict separation; enables reproducible releases.  
6. **Processes** – stateless processes; enables horizontal scaling and resilience.  
Others: port binding, concurrency, disposability, dev/prod parity, logs, admin processes.

**AA12 — Event-Driven vs. Request-Driven**  
- **Coupling**: events are loosely coupled (producer doesn't know consumers); REST/gRPC are tightly coupled (client knows server).  
- **Scalability**: event brokers allow independent scaling of consumers; REST requires load balancing and can bottleneck.  
- **Debugging**: REST is easier to trace (request-response); events require distributed tracing and replay.  
- **Ordering**: Kafka partitions preserve order per key; REST has no inherent ordering.  
- **Failure handling**: events use retries, dead-letter queues, and outbox patterns; REST uses retries and timeouts.  
Choose event-driven for decoupled, asynchronous, high-throughput workflows; request-driven for low-latency, simple request-response interactions.

**AA13 — Load Balancer**  
A load balancer distributes traffic across servers.  
- **Layer 4** (transport): routes based on IP/port, e.g., TCP/UDP. Fast, but no awareness of application content.  
- **Layer 7** (application): routes based on HTTP headers, URLs, cookies. Required for path-based routing, sticky sessions, SSL termination, and content-aware decisions.

**AA14 — Message Queue vs. Log-Based Broker**  
- **RabbitMQ**: a traditional queue; messages are removed after acknowledgment. Good for task distribution, point-to-point.  
- **Kafka**: a log-based broker; messages are retained and replayable, supporting multiple consumer groups. Good for event streaming, pub-sub, and replay.  
Pick RabbitMQ for simple task queues; Kafka for event sourcing, stream processing, and long-term retention.

**AA15 — Container vs. Virtual Machine**  
A container shares the host OS kernel and isolates processes via namespaces/cgroups; it is lightweight and starts in seconds. A VM includes a full guest OS and runs on a hypervisor; it is heavier and more isolated.  
Containers are popular for microservices because they are portable, resource-efficient, and fit orchestration (Kubernetes) for scaling and deployment.

**AA16 — Stateless vs. Stateful Services**  
Stateless services don't store session data; any instance can handle any request, so scaling horizontally is trivial (just add instances). Stateful services store data (e.g., databases) and require careful scaling (sharding, replication).  
Example: a stateless web server (REST API) vs. a stateful database (PostgreSQL).

**AA17 — ORM**  
An ORM maps objects to relational tables. Examples: Hibernate (Java), Entity Framework (.NET), SQLAlchemy (Python).  
Trade-offs: ORMs increase productivity and reduce boilerplate, but can cause performance issues (N+1 queries, lazy loading) and obscure SQL. Raw SQL gives full control and optimization but is more verbose and error-prone.

**AA18 — Bulkhead Pattern**  
Bulkhead isolates failures by partitioning resources so one failure doesn't exhaust all resources. In microservices, use separate thread pools or connection pools for different dependencies.  
Example: a service calls a database and an external API. Use two thread pools: if the API is slow, it only exhausts its own pool, leaving DB threads available. Alternatively, deploy critical services in separate deployment groups (e.g., separate Kubernetes namespaces) to limit blast radius.

**AA19 — OT vs. CRDTs for Collaborative Editing**  
- **OT**: requires a central server to transform operations; provides strong consistency, low latency, but complex to implement and offline support is hard.  
- **CRDTs**: replicate state and merge automatically; provide eventual consistency, excellent offline support, but may require more storage and have higher memory overhead.  
For a system that must support offline editing, choose **CRDTs** because they allow each device to edit locally and merge later without a central coordinator.

**AA20 — Distributed Tracing Challenges**  
- **Context propagation**: use W3C Trace Context (`traceparent` header) or B3 headers to propagate trace/span IDs.  
- **Sampling**: head-based sampling decides at the entry point; tail-based sampling decides after the trace is complete (e.g., using Jaeger or Tempo).  
- **Storage/querying**: Jaeger or Grafana Tempo store traces and provide query APIs.  
- **Async messaging**: propagate trace context in message headers (e.g., Kafka record headers). Producers inject the trace context; consumers read it and continue the trace. Ensure the message broker doesn't strip headers.  
For Kafka, use the `OpenTelemetry` instrumentation to automatically inject/read trace context from Kafka headers.

## On-Premise Infrastructure Architecture

**OP1 — Hypervisor Types**  
- **Type 1 (bare-metal)**: runs directly on hardware. Examples: VMware ESXi, Microsoft Hyper-V, KVM.  
- **Type 2 (hosted)**: runs on an operating system. Examples: Oracle VirtualBox, VMware Workstation.  
Type 1 is more efficient and used in data centers; Type 2 is for desktop virtualization.

**OP2 — SAN vs. NAS**  
- **SAN** (Storage Area Network): block-level storage, accessed as raw disks. Protocols: Fibre Channel, iSCSI. Used for databases, virtualization, high-performance workloads.  
- **NAS** (Network Attached Storage): file-level storage, accessed as shared files. Protocols: NFS, SMB/CIFS. Used for file sharing, home directories, media.  
SAN provides lower latency and more control; NAS is simpler and more portable.

**OP3 — 3-Tier vs. Leaf-Spine**  
3-tier: core (routing), distribution (policy), access (endpoints). Traffic between servers in different access switches must traverse core, causing bottlenecks and oversubscription.  
Leaf-spine: every leaf switch connects to every spine switch; any leaf-to-leaf path has equal latency (one hop). It solves east-west traffic bottlenecks and scales horizontally by adding spines/leaves. Preferred for modern data centers with high east-west traffic (e.g., microservices).

**OP4 — Proxmox HA Cluster**  
- **Nodes**: at least 3 (odd number) for quorum.  
- **Quorum**: majority of votes; use a QDevice (arbitrator) for even-numbered clusters.  
- **Fencing**: use hardware watchdog (IPMI) or STONITH to power off failed nodes.  
- **Shared storage**: Ceph (preferred for Proxmox), iSCSI, or NFS. Ceph provides distributed, self-healing storage.  
- **Node failure**: HA manager detects loss of quorum, fences the node, and migrates VMs to surviving nodes. Storage remains accessible via shared storage.

**OP5 — VLAN Trunking and Linux Configuration**  
VLAN trunking carries multiple VLANs over one link using 802.1Q tags. Each frame gets a VLAN ID.  
On Linux with a single NIC (e.g., eth0), create VLAN interfaces:  
```bash
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip link add link eth0 name eth0.30 type vlan id 30
ip link set eth0 up
ip addr add 192.168.10.1/24 dev eth0.10
# repeat for each VLAN
```
The switch port must be configured as a trunk.

**OP6 — RAID Levels**  
- **RAID 1**: mirroring, 1 disk fault tolerance, 50% capacity.  
- **RAID 5**: block-level striping with parity, 1 disk fault tolerance, good read performance.  
- **RAID 6**: dual parity, 2 disk fault tolerance, lower write performance.  
- **RAID 10**: mirrored and striped, high performance, fault tolerance up to 1 disk per mirror pair.  
- **RAID Z2 (ZFS)**: double parity, similar to RAID 6, but with ZFS features (checksums, snapshots).  
For a database with 6 drives, choose **RAID 10** for best performance and fault tolerance (4 data + 2 parity equivalent, but faster).

**OP7 — Enterprise DNS Architecture**  
- **Internal AD DNS**: authoritative for internal zones (e.g., `corp.local`), integrated with AD.  
- **DMZ**: separate DNS servers for public-facing services, split-horizon (internal vs. external views).  
- **Recursive resolvers**: internal DNS servers resolve external names; forwarders send queries to ISP or public DNS.  
- **Conditional forwarding**: for AD domains, forward to other domain controllers.  
- **DNSSEC**: sign external zone to prevent spoofing.  
- **Laptop mobility**: when on office, uses internal DNS; on VPN, uses VPN-assigned DNS (internal). DNS resolution changes based on network interface.

**OP8 — PKI Chain and Internal PKI**  
Chain: Root CA (offline) → Subordinate/Issuing CA → End-entity certificates.  
- **Root CA**: kept offline, signs subordinate CAs.  
- **Subordinate CA**: online, issues end-entity certs.  
- **CRL vs. OCSP**: CRL is a list of revoked certs; OCSP is a real-time check.  
- **Certificate templates**: define attributes (e.g., server auth, client auth).  
- **Auto-enrollment**: via GPO or Intune, clients automatically request certs.  
Consequences: compromised subordinate CA → revoke and reissue, but root still trusted; compromised root CA → entire trust chain compromised, must rebuild and distribute new root.

**OP9 — Hub-and-Spoke WAN Options**  
- **MPLS**: reliable, QoS, low latency, but expensive.  
- **IPsec VPN over internet**: cheap, but latency/jitter variable, no QoS.  
- **SD-WAN**: overlay on internet, central control, can prioritize VoIP, cost-effective.  
- **WireGuard mesh**: simple, secure, but no QoS and requires full mesh.  
For 50 users per site with latency-sensitive VoIP, recommend **SD-WAN** for cost and reliability, or MPLS if budget allows.

**OP10 — Out-of-Band Management**  
iDRAC (Dell), iLO (HPE), IPMI are out-of-band management interfaces. They allow remote console, power control, and hardware monitoring even if the OS is down. Critical for troubleshooting and remote data center operations.  
If exposed to the internet, they are vulnerable to brute-force attacks, unauthorized access, and can compromise the entire server.

**OP11 — LVM, LVM-Thin, ZFS**  
- **LVM**: traditional volume manager; snapshots are space-consuming and slow.  
- **LVM-Thin**: thin provisioning; efficient snapshots (copy-on-write), good for virtualization.  
- **ZFS**: filesystem + volume manager; snapshots are fast, space-efficient, with checksums and compression.  
Use LVM for simple setups, LVM-Thin for VM storage, ZFS for data integrity and advanced features.

**OP12 — Ceph Stretch Cluster / DR**  
For a 3-node Proxmox cluster with Ceph, to survive a site failure:  
- **CRUSH rules**: define failure domains (e.g., site) so data replicas are distributed across sites.  
- **Monitors**: place at least one monitor per site, plus a tiebreaker (third site or external).  
- **Network latency**: Ceph requires <5ms RTT between sites for synchronous replication.  
- **Split-brain**: without a tiebreaker, two sites can't form quorum; a tiebreaker (e.g., a small VM in a third location) provides majority.  
2-site Ceph is bad without a tiebreaker because neither site can achieve quorum alone, causing cluster outage.

**OP13 — DHCP and DORA**  
DORA: Discover (client broadcasts), Offer (server offers IP), Request (client requests), Ack (server acknowledges).  
If a DHCP server is unavailable and a Windows client's lease expires, the client uses APIPA (169.254.x.x) and loses network connectivity (no DNS, no gateway).

**OP14 — Managed vs. Unmanaged Switch**  
Unmanaged switches are plug-and-play, no configuration. Managed switches provide: VLANs, QoS, SNMP monitoring, spanning tree (loop prevention), port security, port mirroring, and remote management. Enterprise environments require managed switches for segmentation, monitoring, and resilience.

**OP15 — NTP and Time Sync**  
NTP synchronizes clocks across servers. Critical for:  
- Log correlation (timestamps must match).  
- Kerberos authentication (tickets have time limits).  
- Distributed databases (replication ordering).  
Clock drift causes auth failures, inconsistent logs, and replication conflicts.

**OP16 — Physical Server, VM, Container**  
- **Physical server**: bare metal, full hardware access.  
- **VM**: virtualized hardware, isolated OS.  
- **Container**: shares host OS, lightweight.  
Run on bare metal when you need maximum performance, specialized hardware (GPU, FPGA), or when virtualization overhead is unacceptable (e.g., HPC, real-time systems).

**OP17 — UPS vs. Generator**  
UPS provides immediate, short-term battery power to bridge outages. Generator provides long-term fuel-based power. Both are needed: UPS covers the gap until the generator starts and stabilizes. An ATS (Automatic Transfer Switch) automatically switches between utility, UPS, and generator power.

**OP18 — Active-Passive vs. Active-Active Clustering**  
- **Active-passive**: one node active, others standby. Failover is simple but idle resources.  
- **Active-active**: all nodes serve traffic; higher utilization but more complex.  
For PostgreSQL with Pacemaker/Corosync:  
- Use active-passive with a virtual IP (VIP) that moves to the active node.  
- STONITH (fencing) ensures the failed node is powered off to prevent split-brain.  
- Failover: Pacemaker detects node failure, fences it, promotes the standby, and moves the VIP.

**OP19 — Backup and Recovery Strategy**  
- **3-2-1 rule**: 3 copies, 2 different media, 1 offsite.  
- **RPO/RTO**: define acceptable data loss and recovery time.  
- **Backup types**: full, incremental (since last full), differential (since last full).  
- **Deduplication**: reduce storage.  
- **Media**: disk (fast), tape (long-term), cloud (offsite).  
- **Immutable backups**: prevent ransomware by making backups unchangeable (e.g., WORM).  
- **Test restores**: regularly verify backups.  
Backup is copying data; disaster recovery is restoring entire infrastructure (servers, network, applications).

**OP20 — 802.1X and MAB**  
802.1X roles:  
- **Supplicant**: client device (e.g., laptop).  
- **Authenticator**: network switch (or AP).  
- **Authentication server**: RADIUS server.  
EAP methods: EAP-TLS (certificate-based, strong), PEAP (password-based with TLS tunnel).  
RADIUS authenticates the supplicant and can assign a dynamic VLAN based on policy.  
If authentication fails, the switch blocks the port (no network access).  
MAB (MAC Authentication Bypass) allows devices without 802.1X support (e.g., printers) to authenticate by MAC address; the switch sends the MAC to RADIUS, which can grant access or assign a VLAN.
