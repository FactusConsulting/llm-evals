## Kubernetes (20 questions)

**K1 — Easy:** A **Deployment** is for stateless applications. It manages a set of identical pods, supports rolling updates, scaling, and self-healing. A **StatefulSet** is for stateful applications. It gives each pod a stable network identity (e.g., `pod-0`, `pod-1`), stable persistent storage (via PVCs), and ordered deployment/scaling/termination. Use StatefulSet for databases, message queues, or any app requiring stable identity and storage.

**K2 — Easy:** A `ClusterIP` Service uses a label selector to find matching pods. The Kubernetes control plane creates an **Endpoints** object listing the IPs of those pods. On each node, **kube-proxy** watches the Service and Endpoints and programs **iptables** (or IPVS) rules. Traffic sent to the Service's virtual IP is DNAT'd to one of the pod IPs, typically using random or round-robin load balancing.

**K3 — Medium:** A **PersistentVolume (PV)** is cluster-level storage provisioned by an admin or dynamically via a StorageClass. A **PersistentVolumeClaim (PVC)** is a request for storage by a user/pod; it binds to a matching PV. A **StorageClass** defines how storage is provisioned dynamically (e.g., AWS EBS, GCE PD) and its parameters (reclaim policy, type). Relationship: Pod → PVC → PV → StorageClass (if dynamic).

**K4 — Medium:** Troubleshooting `CrashLoopBackOff`:
1. **Check pod logs**: `kubectl logs <pod> --previous` to see why the last container exited.
2. **Check events**: `kubectl describe pod <pod>` for OOMKilled, failed liveness probe, or image pull errors.
3. **Check resource limits**: If `OOMKilled`, increase memory limits or reduce usage.
4. **Check probes**: Verify liveness/readiness probe paths and ports are correct.
5. **Check dependencies**: Ensure the app can reach its DB, ConfigMap, or Secret (e.g., wrong env var).
6. **Check image/command**: Verify the container image exists and the `command`/`args` are correct.

**K5 — Medium:** **CoreDNS** is the cluster's DNS server. It resolves service names (e.g., `my-svc.my-ns.svc.cluster.local`) to IPs and handles external DNS lookups. If CoreDNS is down, pods cannot resolve cluster services or external domains (unless they have cached entries or use external DNS). New DNS queries fail, breaking service discovery and external connectivity.

**K6 — Hard:** The scheduler uses a two-phase process:
- **Filtering**: Removes nodes that don't meet hard constraints (e.g., insufficient resources, node selector, taints/tolerations, volume zone conflicts, node affinity).
- **Scoring**: Ranks remaining nodes based on soft constraints (e.g., spreading across zones, bin-packing, node affinity weights, anti-affinity).
Specific factors: CPU/memory requests, pod affinity/anti-affinity, node affinity, taints/tolerations, topology spread, and local storage availability.

**K7 — Hard:** **Scheduling**: The node has 4GB RAM, 3.5GB requested. The pod requests 256Mi. 3.5GB + 256Mi = 3.75GB < 4GB, so it **will be scheduled**. Limits are not used for scheduling, only requests. **Runtime**: If the pod uses 600Mi, it exceeds its 512Mi limit. The kernel will **OOMKill** the container (memory is not throttled, unlike CPU).

**K8 — Hard:** Lifecycle:
1. **External LB** (e.g., cloud LB) forwards traffic to the Ingress Controller's NodePort or LoadBalancer service.
2. **NGINX Ingress Controller** (running as a pod) receives the request, parses the `Ingress` resource for routing rules (host/path).
3. It forwards to the **Service** (ClusterIP) based on the backend specified in the Ingress.
4. The Service's **Endpoints** object lists the pod IPs.
5. **kube-proxy** (via iptables) DNATs the Service IP to a pod IP.
6. The request reaches the **application pod**.

**K9 — Medium:** A **NetworkPolicy** controls traffic between pods, namespaces, and external endpoints. **Default behavior**: If no NetworkPolicy exists, all traffic is allowed (no isolation). When you apply one that selects certain pods, those pods become isolated, and only traffic matching the policy's ingress/egress rules is allowed. Unselected pods remain fully open.

**K10 — Medium:** **RollingUpdate** gradually replaces old pods with new ones, ensuring zero downtime (e.g., maxSurge/maxUnavailable). **Recreate** kills all old pods before creating new ones, causing downtime. Choose **Recreate** for breaking changes, or when the app requires exclusive access to a resource (e.g., a database migration that can't run concurrently).

**K11 — Easy:** A **namespace** is a virtual cluster within a physical cluster, used to isolate resources (e.g., dev vs. prod). Default namespaces: `default` (for user workloads), `kube-system` (for system components), `kube-public` (publicly readable), and `kube-node-lease` (for node heartbeats).

**K12 — Easy:** `kubectl describe pod` shows detailed info not in `kubectl get pod`:
1. **Events** (e.g., scheduling failures, image pulls, probe failures).
2. **Labels and Annotations**.
3. **Resource requests/limits** per container.
4. **Tolerations** and **node affinity**.
5. **Last state** (exit code, reason, restart count).

**K13 — Easy:** A **ConfigMap** stores configuration data (key-value pairs). Pods consume it via:
1. **Environment variables** (e.g., `valueFrom: configMapKeyRef`).
2. **Volume mount** (files in `/etc/config/`).
3. **Command-line arguments** (using `$(VAR)` syntax).

**K14 — Easy:** **ClusterIP**: Internal-only virtual IP, accessible within the cluster. **NodePort**: Exposes the Service on a static port on each node's IP (accessible externally). **LoadBalancer**: Uses the cloud provider's LB to route external traffic to the NodePort, then to the ClusterIP.

**K15 — Easy:** A **DaemonSet** ensures a copy of a pod runs on every node (or a subset). Use it for cluster-level agents like logging (Fluentd), monitoring (Prometheus node-exporter), or networking (CNI plugins). A **Deployment** runs a variable number of replicas, suitable for stateless apps.

**K16 — Medium:** **Taints/Tolerations** repel pods from nodes (taint on node, toleration on pod). **Node affinity** attracts pods to nodes (e.g., prefer SSD). Taints are for "do not schedule here unless tolerated" (e.g., dedicated GPU nodes). Affinity is for "prefer/require this node" (e.g., place near other pods or in a specific zone).

**K17 — Medium:** An **Operator** is a custom controller that extends the Kubernetes API to manage a specific application (e.g., a database). A standard controller watches built-in resources (e.g., Deployments) and reconciles state. The Operator pattern solves operational tasks (backup, scaling, upgrades) by encoding domain knowledge into code, using CRDs and controllers.

**K18 — Hard:** etcd uses **Raft consensus**. It requires a **quorum** (majority) of nodes to accept writes. If quorum is lost (e.g., 2 of 3 nodes down), the cluster becomes **read-only** (or rejects writes) to prevent split-brain. Recovery: If 2 of 3 are permanently lost, you must restore from a snapshot or rebuild the cluster. You can use `etcdctl` to remove dead members and promote the surviving node, but data loss is possible.

**K19 — Hard:** RBAC uses **Roles** (namespace-scoped) and **ClusterRoles** (cluster-scoped) to define permissions. **RoleBindings** bind a Role to a user/SA within a namespace; **ClusterRoleBindings** bind a ClusterRole cluster-wide. Manifests for a developer with read-only access to pods and logs in `dev` namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: dev, name: pod-reader }
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: dev, name: dev-pod-reader }
subjects:
- kind: User, name: dev-user, apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:** Pods have `ndots:5` by default. For `example.com`, the resolver tries `example.com.` (1 dot), then `example.com.default.svc.cluster.local.`, `example.com.svc.cluster.local.`, `example.com.cluster.local.`, and `example.com.` again — up to 5 queries. For external domains, this causes many unnecessary queries and latency. Fix: set `dnsConfig` in the pod spec:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "1"
```
This makes the resolver try the FQDN first, reducing queries.

## Development (20 questions)

**D1 — Easy:** **git merge** creates a new merge commit, preserving the history of both branches. **git rebase** rewrites the history of one branch onto another, creating a linear history. Avoid rebasing **shared/public branches** because it rewrites commits, causing confusion for other developers.

**D2 — Easy:** **TCP** is reliable, ordered, and connection-oriented (e.g., HTTP, FTP). **UDP** is fast, unreliable, and connectionless (e.g., DNS, DHCP, VoIP).

**D3 — Medium:** A **race condition** occurs when multiple threads access shared data without synchronization, and the outcome depends on the timing. Example (Go):
```go
var counter int
func increment() {
    for i := 0; i < 1000; i++ {
        counter++ // not atomic
    }
}
// Two goroutines calling increment() may lose updates.
```

**D4 — Medium:** **Symmetric encryption** uses the same key for encryption/decryption (e.g., AES). **Asymmetric encryption** uses a public/private key pair (e.g., RSA). In TLS: asymmetric is used for key exchange (e.g., ECDHE) to securely share a session key, then symmetric encryption (AES) is used for bulk data transfer.

**D5 — Medium:** A **container image layer** is a filesystem change created by each Dockerfile instruction (e.g., `RUN`, `COPY`). Layers are cached; if a layer is unchanged, it's reused. Best practices: order instructions from least to most frequently changing (base image → dependencies → app code), combine `RUN` commands to reduce layers, and use specific base image tags.

**D6 — Medium:** Troubleshooting intermittent 503s (in order):
1. **Check application logs** for errors (e.g., stack traces, DB connection failures).
2. **Check load balancer/ingress logs** for 503 patterns (e.g., backend down).
3. **Check health endpoints** (`/healthz`) and readiness probes.
4. **Check backend dependencies** (database, cache, external API) for latency or failures.
5. **Check resource usage** (CPU, memory) for throttling or OOM.
6. **Check recent deployments/config changes** that might have introduced instability.

**D7 — Hard:** The **CAP theorem** states a distributed system can only guarantee two of: Consistency, Availability, and Partition tolerance. **CP** (e.g., etcd, MongoDB) chooses consistency over availability during a partition — it may reject requests. **AP** (e.g., Cassandra, DynamoDB) chooses availability — it accepts writes but may serve stale data.

**D8 — Medium:** **Horizontal scaling** adds more machines/nodes (e.g., more pods). **Vertical scaling** adds more resources to an existing machine (e.g., more CPU/RAM). Patterns enabling horizontal scaling: stateless services, load balancing, distributed databases, microservices, and event-driven architectures.

**D9 — Easy:** An **environment variable** is a key-value pair in the shell environment. To persist across sessions on Linux, add `export VAR=value` to `~/.bashrc` or `~/.profile`, then `source ~/.bashrc`.

**D10 — Easy:** **JSON** is a strict, machine-friendly data interchange format (no comments, double quotes). **YAML** is human-readable, supports comments, and uses indentation. JSON advantage: universally supported and machine-parseable. YAML advantage: readability and suitability for configuration files.

**D11 — Easy:** A **REST API** uses HTTP methods to perform operations on resources. **GET** retrieves a resource. **POST** creates a new resource. **PUT** updates/replaces an existing resource. **DELETE** removes a resource.

**D12 — Easy:** **Version pinning** specifies exact versions of dependencies (e.g., `package.json` with `1.2.3` instead of `^1.2.3`). It ensures reproducible builds, avoids unexpected breaking changes, and makes debugging easier.

**D13 — Easy:** A **compiled language** is translated to machine code before execution (e.g., C, Go). An **interpreted language** is executed line by line by an interpreter at runtime (e.g., Python, JavaScript).

**D14 — Medium:** A **reverse proxy** sits in front of backend servers and forwards client requests to them (e.g., Nginx, HAProxy). A **forward proxy** sits in front of clients and forwards their requests to the internet. Use cases: Nginx for load balancing and TLS termination; HAProxy for high-availability load balancing and health checks.

**D15 — Medium:** A **deadlock** occurs when two or more processes wait indefinitely for each other's resources. The four Coffman conditions: **Mutual exclusion** (resource is non-shareable), **Hold and wait** (process holds a resource while waiting for another), **No preemption** (resources cannot be forcibly taken), and **Circular wait** (a cycle of waiting).

**D16 — Hard:** **Eventual consistency** means updates propagate asynchronously; reads may return stale data. Cassandra uses tunable consistency levels: `ONE` (fast, may be stale), `QUORUM` (majority, strong), `ALL` (strongest, slow). For read-after-write consistency, use `QUORUM` for both reads and writes, or use read repair to fix stale replicas.

**D17 — Hard:** **mTLS** (mutual TLS) requires both client and server to authenticate each other. Handshake: Client sends `ClientHello` → Server sends `ServerHello` + certificate → Client verifies server cert → Client sends its own certificate → Server verifies client cert → Key exchange (e.g., ECDHE) → Finished. mTLS is used in service meshes (Istio), zero-trust networks, and internal API gateways.

**D18 — Hard:** A **hash table** uses a hash function to map keys to an array index. **Collision resolution**: **Chaining** uses a linked list per bucket; **open addressing** probes for the next empty slot (e.g., linear/quadratic probing). Time complexity: Average O(1) for insertion, lookup, deletion; worst case O(n) if all keys collide (e.g., poor hash function).

**D19 — Hard:** The **circuit breaker** pattern prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal, requests pass), **Open** (fail fast, no requests), **Half-open** (allow a few test requests; if successful, close; if failed, reopen). It relates to retry policies: retries are for transient failures, but circuit breakers stop retries when the service is down. Exponential backoff is used for retries to avoid overwhelming the service.

**D20 — Hard:** **Optimistic concurrency** assumes conflicts are rare; it uses a version number or timestamp to check if data changed before updating (e.g., `UPDATE ... WHERE version = ?`). **Pessimistic concurrency** locks the row to prevent conflicts (e.g., `SELECT FOR UPDATE`). Choose optimistic for low contention (e.g., web apps), pessimistic for high contention or critical data (e.g., inventory systems).
