## JavaScript / TypeScript

**JS1 — var, let, const & hoisting**  
`var` is function-scoped, hoisted and initialized to `undefined`, and can be redeclared. `let` and `const` are block-scoped, hoisted but in a temporal dead zone (TDZ) until the declaration executes, and cannot be redeclared. `const` also forbids reassignment (though object properties remain mutable). Hoisting means declarations are moved to the top of their scope at compile time; `var` gets initialized, `let`/`const` stay uninitialized until the declaration line.

**JS2 — Event loop**  
The call stack executes synchronous code (LIFO). When it empties, the event loop drains the **microtask queue** (Promise callbacks, `queueMicrotask`, `MutationObserver`) completely, then processes **one** macrotask (setTimeout, setInterval, I/O events) from the macrotask queue, then repeats. This guarantees microtasks run before the next macrotask, enabling predictable async ordering.

**JS3 — Closures**  
A closure is a function that retains access to its lexical scope even when invoked outside that scope. Example:  
```js
function makeCounter() {
  let count = 0;
  return () => ++count;
}
```
The classic for-loop bug: with `var`, the loop variable is shared across all closures, so each callback sees the final value. Fix with `let` (block-scoped per iteration) or an IIFE: `for (var i=0; i<3; i++) (j => setTimeout(()=>console.log(j), 0))(i)`.

**JS4 — Promise, async/await, error handling**  
A Promise represents eventual completion/failure; `async/await` is syntactic sugar over promises. For promises, errors are caught via `.catch()`; for async/await, use `try/catch`. `Promise.all` rejects immediately on the first rejection (fail-fast). `Promise.allSettled` waits for all promises to settle and returns an array of `{status, value/reason}` objects, never rejecting — useful when you need all results regardless of failures.

**JS5 — TypeScript interface vs type**  
`interface` supports declaration merging and is best for object shapes that may be extended. `type` is more flexible: unions, intersections, mapped types, tuples, and computed properties. Use `interface` for public APIs/object contracts; use `type` for everything else. A **discriminated union** is a union of object types sharing a common discriminant property (e.g., `type: 'circle' | 'square'`), enabling exhaustive type narrowing with `switch`.

**JS6 — Prototypal inheritance**  
Every object has a prototype chain; property lookup walks up until found or `null`. `Object.create(obj)` creates a new object whose prototype is `obj` — useful for delegation without constructors. ES6 classes are syntactic sugar: `class Foo {}` creates a constructor function, `extends` sets `Foo.prototype`'s prototype, and `super` calls the parent constructor. Under the hood, instances still use the prototype chain.

**JS7 — The `this` keyword**  
Binding rules in priority order:  
1. **New binding** — `new` creates a new object and sets `this` to it.  
2. **Explicit binding** — `call`, `apply`, `bind` override `this`.  
3. **Implicit binding** — method call: `obj.method()` sets `this` to `obj`.  
4. **Default binding** — standalone function: `this` is global (or `undefined` in strict mode).  
`bind()` returns a new function with permanently bound `this`; you cannot re-bind a bound function (even with `call`/`apply`).

**JS8 — WeakRef, FinalizationRegistry, WeakMap**  
`WeakRef` holds a weak reference to an object; `.deref()` returns the object or `undefined` if GC'd. `FinalizationRegistry` registers a callback that runs when a target object is garbage-collected — useful for cleanup of external resources. WeakMap keys must be objects because they are held weakly; if keys were primitives, the engine couldn't track their identity for GC (primitives are immutable and can't be weakly referenced). This enables memory-safe caches and private data.

**JS9 — V8 optimization**  
V8 uses **hidden classes** (maps) to track object shapes; adding properties creates new hidden classes. **Inline caching** caches property access based on the hidden class, speeding up repeated lookups. **Deoptimization** occurs when the hidden class changes unexpectedly or a call site becomes polymorphic (multiple shapes). Patterns that cause deoptimization: adding properties after object creation, changing object shape dynamically, using `delete`, or mixing types in arrays. Avoid these by initializing all properties upfront and keeping object shapes stable.

**JS10 — Tree-shaking**  
Tree-shaking removes unused exports from the final bundle. ES modules are statically analyzable — imports/exports are fixed at parse time — so bundlers can safely drop unused exports. CommonJS is dynamic (`require` can be conditional, `module.exports` can be reassigned), making static analysis impossible; bundlers often cannot determine what's used, so tree-shaking is ineffective or requires complex heuristics.

**JS11 — null vs undefined, == vs ===, ?? and ?.**  
`null` is an intentional absence of value; `undefined` means a variable hasn't been assigned. `null == undefined` is `true` (abstract equality), but `null === undefined` is `false`. The **nullish coalescing** operator `??` returns the right side only when the left is `null` or `undefined` (unlike `||` which also skips falsy values). **Optional chaining** `?.` short-circuits property access if the object is `null`/`undefined`, e.g., `obj?.a?.b`.

**JS12 — map, filter, reduce, flatMap**  
`map` transforms each element; `filter` keeps elements passing a predicate; `reduce` accumulates with an initial value (second argument) — e.g., `arr.reduce((sum, x) => sum + x, 0)`. `flatMap` maps then flattens one level, useful for nested arrays: `[1,2].flatMap(x => [x, x*2])` → `[1,2,2,4]`. It avoids intermediate arrays and is ideal for one-to-many transformations.

**JS13 — Template literals & tagged templates**  
Template literals use backticks and `${}` for interpolation. Tagged templates call a function with the string parts array and substitution values:  
```js
function sql(strings, ...values) {
  return strings.reduce((acc, s, i) => acc + s + (values[i] ?? ''), '');
}
sql`SELECT * FROM users WHERE id = ${id}`;
```
This enables safe escaping (e.g., HTML escaping, SQL parameterization) by processing raw strings and values separately.

**JS14 — Destructuring**  
Object: `const { a, b } = obj`; array: `const [x, y] = arr`. Defaults: `const { a = 1 } = obj`; renaming: `const { a: newName } = obj`. Rest: `const { a, ...rest } = obj` collects remaining properties; `const [first, ...rest] = arr` collects remaining elements. Rest must be last. Works in function parameters too: `function f({ name = 'anon' } = {}) {}`.

**JS15 — for...in vs for...of**  
`for...in` iterates enumerable string keys, including inherited ones — designed for objects. `for...of` iterates iterable values (arrays, strings, maps). Avoid `for...in` on arrays because it includes inherited properties, returns indices as strings, and can include non-index enumerable properties. Use `for...of` or `forEach` for arrays.

**JS16 — TypeScript generics**  
Generics: `function identity<T>(arg: T): T { return arg; }`. Constraints: `T extends Lengthwise` restricts to types with `length`. Conditional types: `type IsArray<T> = T extends any[] ? true : false;`. `infer` extracts types: `type Element<T> = T extends (infer U)[] ? U : never;` — used in utility types like `ReturnType` and `PromiseType`.

**JS17 — Module system**  
CommonJS uses `require`/`module.exports`, is synchronous, and was designed for Node. ES Modules use `import`/`export`, are asynchronous and statically analyzable. Node supports both: `.cjs` forces CommonJS, `.mjs` forces ESM, and `"type": "module"` in `package.json` makes `.js` files ESM. Node can `require()` ESM (with limitations) and `import` CJS (default export interop).

**JS18 — Structural typing, excess checks, extends vs satisfies, variance**  
TypeScript is structurally typed: types are compatible if their shapes match. **Excess property checks** apply only to object literals assigned to a typed variable — extra properties error, preventing typos. `extends` constrains a generic or type; `satisfies` (TS 4.9+) checks a value against a type without changing its inferred type (e.g., `const x = { a: 1 } satisfies Record<string, number>`). Variance: `in` marks contravariant positions (function parameters), `out` marks covariant positions (return types) — TS 4.7+ uses these for safer type checking.

**JS19 — Proxy and Reflect**  
`Proxy` wraps an object and intercepts operations via handler traps (`get`, `set`, `apply`, `has`, etc.). `Reflect` provides default behavior for each trap. Example — validation:  
```js
const user = new Proxy({}, {
  set(target, prop, value) {
    if (prop === 'age' && value < 0) throw new Error('Invalid age');
    target[prop] = value;
    return true;
  }
});
```
Also used for logging, reactive data binding (Vue 3), and access control.

**JS20 — SharedArrayBuffer & Atomics**  
`SharedArrayBuffer` is a fixed-length shared memory region accessible by multiple Web Workers. Workers transfer it via `postMessage`. `Atomics` provides atomic operations (`add`, `load`, `store`, `exchange`, `wait`, `notify`) that guarantee ordering and prevent data races. `Atomics.wait` blocks the thread until `Atomics.notify` wakes it — enabling synchronization primitives like mutexes. Ordering guarantees: operations are sequentially consistent on the shared buffer; `Atomics.wait`/`notify` provide a way to coordinate workers without message-passing overhead.

## Bash

**B1 — $@ vs $*, "$@" vs "$*"**  
Unquoted, `$@` and `$*` behave identically: each positional parameter is subject to word splitting. Quoted, `"$@"` passes each parameter as a separate quoted argument (preserving spaces), while `"$*"` joins all parameters into a single string using the first character of `IFS` as separator. `"$@"` is almost always the correct choice for safe argument forwarding.

**B2 — set -euo pipefail**  
`-e` (errexit): exit immediately if any command returns non-zero. `-u` (nounset): treat unset variables as an error. `-o pipefail`: a pipeline returns the rightmost non-zero exit status (not just the last command). Together they create a "strict mode" that catches errors early, but `-e` requires careful handling of expected failures (e.g., `cmd || true`).

**B3 — $(command) vs `command`; $((expression)) vs expr**  
`$(command)` is the modern command substitution syntax; backticks are legacy and have escaping quirks (e.g., nested backticks need `\``). `$((expression))` is arithmetic expansion — pure shell, fast, no external process. `expr` is an external command, slower, and requires escaping operators (`expr 1 + 1`). Always prefer `$(...)` and `$((...))`.

**B4 — Process substitution**  
`<(command)` creates a file descriptor (e.g., `/dev/fd/63`) that reads from the command's output. Used when a command expects a file path instead of stdin. Example:  
```bash
diff <(sort file1) <(sort file2)
```
This avoids temp files and works with `while read` loops: `while read line; do ...; done < <(cmd)`.

**B5 — Safe file iteration**  
Use `find ... -print0 | while IFS= read -r -d '' file` to handle spaces, newlines, and special characters. Or use globbing: `for f in *.txt` (safe for spaces, but not for newlines). `for f in $(ls)` is dangerous because `$(ls)` splits on spaces, tabs, and newlines, and glob expansion can occur — filenames with spaces break into multiple words.

**B6 — Here document vs here string**  
Here document: `cmd <<EOF` feeds multi-line input to stdin. Here string: `cmd <<< "string"` feeds a single string with a trailing newline. `<<-EOF` strips leading tabs from the here-doc body, allowing indented content without breaking the delimiter — useful for readability inside functions.

**B7 — Redirection order**  
`cmd > file 2>&1`: stdout is redirected to `file` first, then stderr is redirected to the current stdout (which is `file`) — both go to `file`.  
`cmd 2>&1 > file`: stderr is redirected to the current stdout (the terminal) first, then stdout is redirected to `file` — stderr goes to the terminal, stdout to `file`.  
`cmd &> file` is bash shorthand for both to `file`. The order matters because redirections are evaluated left-to-right, each referring to the current state.

**B8 — Lock file with cleanup**  
```bash
acquire_lock() {
    local lockdir="/tmp/mylock.$$"
    while ! mkdir "$lockdir" 2>/dev/null; do
        # stale lock detection
        if [ -f "$lockdir/pid" ] && ! kill -0 "$(cat "$lockdir/pid")" 2>/dev/null; then
            rm -rf "$lockdir"
            continue
        fi
        sleep 0.1
    done
    echo $$ > "$lockdir/pid"
    trap 'rm -rf "$lockdir"' EXIT TERM INT
}
```
`mkdir` is preferred because it's atomic — only one process can succeed. File creation with `>` can race (both check then both create). The trap ensures cleanup on normal exit, SIGTERM, and SIGINT; stale detection handles crashes.

**B9 — Quotes**  
Single quotes `'...'`: literal, no expansion. Double quotes `"..."`: expansion (`$var`, `$(cmd)`) but no word splitting or globbing. No quotes: expansion + word splitting + globbing. Example:  
```bash
var="a b"
echo '$var'   # $var
echo "$var"   # a b
echo $var     # a b (but splits into two args if used unquoted)
```

**B10 — File checks; [ ] vs [[ ]]**  
`-e file` exists, `-d` directory, `-r` readable, `-w` writable, `-x` executable. `[ ]` is the `test` command (POSIX); `[[ ]]` is a bash keyword with more features: pattern matching (`[[ $str == *.txt ]]`), `&&`/`||` without quoting, regex with `=~`, and no word splitting. Prefer `[[ ]]` in bash scripts for robustness.

**B11 — $?, $$, $!, $#**  
`$?` — exit status of the last command (check success/failure). `$$` — PID of the current shell (for temp files, logging). `$!` — PID of the last background job (to `kill` or `wait` it). `$#` — number of positional parameters (validate argument count).

**B12 — Functions**  
Define with `foo() { ... }` or `function foo { ... }` (bash-specific; `function` is not POSIX). Return values: `return` sets the exit status (0–255); `echo` outputs data captured via command substitution: `result=$(foo)`. Example:  
```bash
add() { echo $(($1 + $2)); }
sum=$(add 3 4)
```

**B13 — PATH, builtins vs external**  
`PATH` is a colon-separated list of directories for command lookup. Bash resolves commands by checking builtins first, then `PATH` (hash table for speed). Builtins are shell-internal (`cd`, `echo`, `read`); external commands are separate binaries (`ls`, `grep`). Check with `type -t cmd` (returns `builtin`, `alias`, `file`, etc.) or `which`.

**B14 — trap**  
`trap 'cmd' SIGNAL` runs `cmd` when the signal is received. Common: `trap 'cleanup' EXIT` (always runs on exit), `trap '...' ERR` (on non-zero exit), `trap '...' INT TERM` (for graceful shutdown). When multiple signals arrive, traps run in the order received; the `EXIT` trap runs last after all other traps. Use `trap - SIG` to reset.

**B15 — xargs vs command substitution; -0; -P**  
`xargs` reads stdin and builds/runs commands, handling large inputs efficiently; command substitution `$(...)` collects output into memory and splits on spaces. `find -print0 | xargs -0` uses null separators to safely handle spaces/newlines. `xargs -P 4` runs up to 4 processes in parallel — useful for CPU-bound tasks. Example: `find . -name '*.log' -print0 | xargs -0 -P 4 gzip`.

**B16 — Arrays & associative arrays**  
Indexed: `arr=(a b c)`, append `arr+=(d)`, iterate `for i in "${arr[@]}"`, length `${#arr[@]}`, index `${arr[1]}`. Associative: `declare -A map`, assign `map[key]=value`, iterate keys `for k in "${!map[@]}"`, values `for v in "${map[@]}"`, length `${#map[@]}`. Associative arrays require bash 4+ and support arbitrary string keys.

**B17 — Subshell vs group; pipe while loop**  
`(...)` runs in a subshell — variable changes don't propagate to the parent. `{ ...; }` runs in the current shell — variables persist. Piping into a `while` loop creates a subshell, so variable changes are lost:  
```bash
echo -e "a\nb" | while read line; do count=$((count+1)); done
echo $count  # 0
```
Fix with process substitution: `while read line; do ...; done < <(echo -e "a\nb")` or `<<<` for a single string.

**B18 — Signals & job control**  
SIGINT (Ctrl+C) interrupts; SIGTERM requests termination (catchable); SIGHUP is sent on terminal hangup; SIGKILL kills immediately (uncatchable). Graceful shutdown: trap TERM/INT, then kill background jobs and `wait`:  
```bash
trap 'kill $pid1 $pid2; wait; exit 0' TERM INT
cmd1 & pid1=$!
cmd2 & pid2=$!
wait
```

**B19 — Parallel log processing**  
```bash
process_chunk() {
    local file="$1"
    awk '{ count[$1]++ } END { for (k in count) print k, count[k] }' "$file"
}
export -f process_chunk

split -n 4 -d logfile chunk_
find . -name 'chunk_*' -print0 | xargs -0 -P 4 -I {} bash -c 'process_chunk "$1"' _ {}
# merge results
cat chunk_* | sort | uniq > final_results
rm chunk_*
```
Trade-offs: `split` creates files (I/O overhead); `xargs -P` spawns processes (memory); merging requires sorting. Error propagation: use `xargs` with `-P` and check exit codes via `xargs`'s return status, or collect per-chunk exit codes in files.

**B20 — exec, file descriptors, coprocess**  
`exec` replaces the current shell with a command (no return) or manipulates file descriptors: `exec 3>file` opens fd 3 for writing; `exec 3>&-` closes it; `exec 3<&0` duplicates stdin. A coprocess: `coproc myproc { cmd; }` creates a bidirectional pipe — `myproc` has `myproc_IN`/`myproc_OUT` fds. Useful for interactive communication with a long-running process (e.g., a server or REPL).

## PowerShell

**PS1 — Write-Output vs Write-Host**  
`Write-Output` writes to the output stream (pipeline), so it can be captured, piped, or assigned. `Write-Host` writes directly to the host console and does **not** go to the pipeline — it's for user display only. This matters because functions should return data via the output stream; `Write-Host` breaks composability (e.g., `Get-Item | Write-Host` doesn't pass data).

**PS2 — Pipeline; ForEach-Object vs foreach**  
The pipeline passes objects between commands, enabling streaming and composability. `ForEach-Object` is a cmdlet that processes items one-by-one as they arrive (streaming, memory-efficient). The `foreach` statement is a language construct that collects all input first (faster for small collections, but uses more memory). Use `ForEach-Object` for large/streaming data; use `foreach` for small in-memory collections where speed matters.

**PS3 — PSCustomObject vs hashtable**  
`[hashtable]` is a key-value dictionary with `[hashtable]` semantics (keys, `Add()`, `ContainsKey()`). `[PSCustomObject]` is a structured object with fixed properties, suitable for output. Convert: `[PSCustomObject]@{ Name='John'; Age=30 }` creates an object; `$obj.PSObject.Properties` accesses properties. Use hashtables for lookups/configuration; use PSCustomObject for pipeline output.

**PS4 — Error handling**  
Terminating errors stop execution; non-terminating errors continue (e.g., `Get-ChildItem` on a missing file). `-ErrorAction Stop` converts non-terminating to terminating; `$ErrorActionPreference` sets the default (e.g., `'Stop'`). `try/catch` catches terminating errors; `catch` can inspect `$_` for the error record. `$Error` is the error history list. `throw` creates terminating errors.

**PS5 — Splatting**  
Splatting passes a collection of parameters using `@`:  
```powershell
$params = @{ Path='C:\temp'; Recurse=$true; Verbose=$true }
Get-ChildItem @params
```
It improves readability and avoids long command lines. Difference: splatting expands the hashtable into named parameters; passing a hashtable as a single parameter requires the function to accept a hashtable parameter (e.g., `-Properties $hash`).

**PS6 — Remoting**  
`Invoke-Command -ComputerName` runs a scriptblock on a remote machine and returns results (one-shot). `Enter-PSSession` opens an interactive session. Both use WinRM (WS-Management protocol) by default; PowerShell 7+ also supports SSH-based remoting. WinRM requires proper configuration (listeners, firewall, authentication). `Invoke-Command` is for automation; `Enter-PSSession` is for interactive troubleshooting.

**PS7 — Type system & pipeline unrolling**  
PowerShell unrolls single-item collections: a function returning a one-element array yields a scalar. In the example, `$result` is an array, but `return $result` unrolls it — `$x` becomes a string `"one"` (so `$x.GetType().Name` is `String`). If the function returns 0 items, `$x` is `$null` (or empty array if `@()` is used). Correct pattern: `return ,$result` (comma prevents unrolling) or `Write-Output -NoEnumerate $result`.

**PS8 — Scriptblock vs function; double-hop**  
A scriptblock `{ ... }` is a reusable code block; a function is a named scriptblock with parameters. Scriptblocks can be passed to remote sessions: `Invoke-Command -ScriptBlock { ... }`. The **double-hop problem**: credentials don't propagate from the remote session to a second hop (e.g., accessing a file share from the remote machine). Solutions: CredSSP (delegates credentials, but less secure), or pass explicit credentials via `-ArgumentList` and `New-Credential`.

**PS9 — @() vs [array]; indexing null**  
`@()` is the array subexpression operator — wraps results in an array (even a single item). `[array]` is a type accelerator for casting. Force a single result into an array: `@($result)` or `Write-Output -NoEnumerate`. Indexing `$null` returns `$null`; indexing an empty array also returns `$null` (no error). To distinguish, check `$null -eq $x` vs `$x.Count -eq 0`.

**PS10 — Comparison operators**  
`-eq`/`-ne` (equality), `-like` (wildcard), `-match` (regex), `-contains` (collection contains value), `-in` (value in collection). Case-sensitive variants: `-ceq`, `-clike`, `-cmatch`, etc. `-contains` and `-in` are inverses: `$collection -contains $value` vs `$value -in $collection`. `-like` uses `*`/`?`; `-match` uses regex and sets `$matches`.

**PS11 — Modules**  
A script module (`.psm1`) contains PowerShell functions; a manifest module (`.psd1`) is metadata (version, author, dependencies); a binary module (`.dll`) is compiled C#. `Import-Module` loads a module by name or path, making its exported functions available. Modules can have `Export-ModuleMember` to control exports. `Get-Module` lists loaded modules.

**PS12 — String interpolation**  
Double quotes `"..."` interpolate: `$var`, `${var}`, or `$(expression)`. Single quotes `'...'` are literal. Here-strings: `@"..."@` (double-quoted, interpolates) and `@'...'@` (single-quoted, literal) for multi-line strings. Example: `"Result: $(2 + 2)"` → `Result: 4`.

**PS13 — Get-Member; Select vs Where**  
`Get-Member` shows an object's properties, methods, and note properties. Properties are data fields; Methods are callable actions; NoteProperties are added properties (e.g., from `Add-Member`). `Select-Object` chooses/transforms properties; `Where-Object` filters objects by criteria. Use `Get-Member` to discover what's available, then `Select-Object` to shape output.

**PS14 — PowerShell classes**  
PowerShell classes (v5+) use `class` keyword:  
```powershell
class Person {
    [string]$Name
    [int]$Age
    [void]Greet() { "Hi, $($this.Name)" }
}
```
They differ from C#: no multiple inheritance, limited interface support (no explicit `interface` keyword), constructors are simpler, and methods can use PowerShell syntax. Use classes for complex domain logic; use functions for simple operations and pipeline-friendly code.

**PS15 — CmdletBinding & advanced functions**  
`[CmdletBinding()]` adds cmdlet features: `-Verbose`, `-Debug`, `-WhatIf`, `-Confirm`, parameter validation, and automatic `$PSCmdlet`. `SupportsShouldProcess` enables `-WhatIf`/`-Confirm`. `DefaultParameterSetName` selects a parameter set. `ValueFromPipeline` accepts pipeline input. Begin (init), Process (per-item), End (cleanup) blocks control streaming — Process runs once per pipeline input.

**PS16 — Providers**  
Providers expose data stores as a file system. `Get-ChildItem` works across providers: FileSystem (`C:\`), Registry (`HKLM:\`, `HKCU:\`), Certificate (`Cert:\`), Environment (`Env:\`). You can `cd HKLM:\Software` and use `Get-ChildItem`/`Set-Item` to manipulate registry keys like files. Providers enable a unified navigation model.

**PS17 — Runspaces & parallelism**  
A `[runspace]` is an isolated PowerShell environment; `[runspacepool]` manages multiple runspaces; `[powershell]` object runs commands in a runspace. Manual runspace management gives fine control but is complex. `ForEach-Object -Parallel` (v7+) simplifies parallelism: `1..10 | ForEach-Object -Parallel { $_ * 2 } -ThrottleLimit 5`. Runspaces are thread-safe only if you avoid shared state; use `$using:` for input.

**PS18 — PSScriptAnalyzer**  
PSScriptAnalyzer is a static analysis tool for PowerShell. Rules enforce coding standards (e.g., `PSUseShouldProcessForStateChangingCommands`, `PSAvoidUsingWriteHost`). Severity levels: Error, Warning, Information. Custom rules implement `IDynamicScriptRule` or `IScriptRule`. Suppress with `#PSScriptAnalyzer -Suppress` comments or `-ExcludeRule`. Integrate with CI/CD via `Invoke-ScriptAnalyzer` in Azure DevOps, GitHub Actions, or Pester tests.

**PS19 — $using: scope & serialization**  
`$using:` passes variables to remote sessions, background jobs, and `ForEach-Object -Parallel` (e.g., `$using:var`). `-ArgumentList` passes arguments to scriptblocks. CLIXML serialization has a depth limit (default 2) — complex objects (e.g., custom classes, large hashtables) may lose fidelity or become deserialized as `PSObject`. Use `[xml]` or JSON for complex data, or increase depth with `-Depth` (remoting).

**PS20 — Desired State Configuration (DSC)**  
DSC is declarative configuration management. **Configurations** are declarative scripts (`Configuration MyConfig { ... }`); **Resources** are modules that implement `Get/Set/Test-TargetResource`; the **Local Configuration Manager (LCM)** applies configurations. Windows PowerShell DSC (v1) uses the LCM service; PowerShell 7+ has DSC v2 with a different engine (no WMI dependency). Modern infrastructure-as-code has largely replaced DSC with Terraform, Ansible, Azure Policy, and Pulumi, though DSC still exists for Windows-specific state management.
