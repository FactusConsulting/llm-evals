## Cloud Infrastructure Architecture (20 questions)

### CL1 — Easy: IaaS vs PaaS vs SaaS

**IaaS (Infrastructure as a Service):** Provides virtualized computing resources—servers, storage, networking. You manage OS, middleware, runtime, and applications. *Example: AWS EC2, Azure VMs.*

**PaaS (Platform as a Service):** Provides a managed platform for application development—runtime, middleware, databases, deployment tools. You manage only your application code and data. *Example: AWS Elastic Beanstalk, Azure App Service.*

**SaaS (Software as a Service):** Provides fully managed software applications. You only manage user settings and data. *Example: Microsoft 365, Salesforce.*

**Key difference:** The level of control vs. the level of abstraction. IaaS gives maximum control, SaaS gives maximum convenience, PaaS sits in between.

---

### CL2 — Easy: Shared Responsibility Model

The cloud provider is responsible for security **of** the cloud (physical infrastructure, host OS, network, hypervisor), while you are responsible for security **in** the cloud (data, application, access, configuration).

- **IaaS VMs:** Provider secures physical hosts, hypervisor, and network. You secure the guest OS, applications, data, firewall rules, and access keys.
- **Managed Kubernetes (EKS/AKS/GKE):** Provider secures control plane, worker node OS, and underlying infrastructure. You secure pods, containers, RBAC, secrets, network policies, and application code.
- **SaaS (M365):** Provider secures the service, physical infrastructure, and platform. You secure user accounts, MFA, data classification, and compliance settings.

---

### CL3 — Medium: VPC, Subnet, Security Group, NACL

- **VPC:** A logically isolated virtual network in the cloud. Defines the IP address space (e.g., 10.0.0.0/16).
- **Subnet:** A segment of the VPC's IP range, typically tied to an availability zone. Subnets can be public (with internet gateway) or private.
- **Security Group (SG):** A virtual firewall attached to resources (e.g., EC2 instances). It's **stateful**—return traffic is automatically allowed. SG rules are allow-only.
- **NACL:** A stateless firewall at the subnet level. It filters traffic entering/exiting the subnet. Both allow and deny rules are possible. Return traffic must be explicitly allowed.

**Layering:** NACLs filter traffic at the subnet boundary first, then SGs filter at the instance level. NACLs are stateless (you must define both inbound and outbound rules), while SGs are stateful (return traffic is automatic).

### CL4 — Medium: Multi-Account AWS/Azure Strategy

**Landing Zone:** A well-architected, multi-account baseline environment with pre-configured security, identity, and networking controls. In AWS: AWS Control Tower. In Azure: Azure Landing Zones.

**Organizational Units (OUs):** Hierarchical grouping of accounts for governance. E.g., "Prod," "Non-Prod," "Sandbox," "Security," "Logging."

**Guardrails:** Preventive and detective controls enforced via Service Control Policies (AWS) or Azure Policy. E.g., block public S3 buckets, enforce MFA, restrict regions.

**Shared Networking:** A central "hub" account hosts Transit Gateway (AWS) or Virtual WAN hub (Azure). Spoke accounts connect via peering/attachments. Centralized egress, VPN, and inspection appliances live in the hub.

**Centralized Logging:** All accounts send CloudTrail/Flow Logs/Activity Logs to a central logging account with a secure S3 bucket + KMS key + log archive.

**Why single-account is problematic:** No blast radius isolation, no clear ownership boundaries, no environment separation, difficult cost allocation, and a single misconfiguration can compromise everything.

### CL5 — Medium: Infrastructure as Code (IaC)

**Terraform/OpenTofu:** Declarative, HCL-based, multi-cloud, stateful. Best for broad multi-cloud provisioning and lifecycle management. OpenTofu is the open-source fork.

**Pulumi:** Declarative but uses general-purpose languages (Python, TypeScript, Go). Better for complex logic, testing, and reuse of code patterns.

**CloudFormation/Bicep:** Native to AWS/Azure. Deep integration with provider-specific features. Bicep is a simpler DSL for Azure. Best when you're all-in on one cloud.

**Crossplane:** Control-plane-based IaC that runs inside Kubernetes. Treats cloud resources as Kubernetes objects. Best for teams that want GitOps-style management of cloud infrastructure from within K8s.

**When to choose:** Terraform for multi-cloud or vendor-neutral; Pulumi for complex logic; CloudFormation/Bicep for single-cloud depth; Crossplane for K8s-centric organizations.

### CL6 — Medium: Kubernetes Autoscaling Patterns

- **HPA (Horizontal Pod Autoscaler):** Scales the number of pod replicas based on CPU/memory/custom metrics. Good for stateless workloads.
- **VPA (Vertical Pod Autoscaler):** Adjusts CPU/memory requests of existing pods. Good for stateful or single-instance workloads that can't scale horizontally.
- **Cluster Autoscaler:** Adds/removes worker nodes to the cluster based on pending pods. Handles the "where do pods go" question.
- **KEDA (Kubernetes Event-Driven Autoscaling):** Scales based on external event sources—queue length (Kafka, RabbitMQ), HTTP traffic, custom metrics, scheduled times. It's an event-driven HPA.

**Use KEDA over HPA when:** Your scaling signal is not CPU/memory but an external event (e.g., SQS queue depth, Kafka lag, Prometheus custom metric). KEDA allows scaling to zero and scales based on business-relevant signals.

### CL7 — Hard: Disaster Recovery Design

**RPO/RTO:** RPO = acceptable data loss (e.g., 15 min). RTO = acceptable downtime (e.g., 1 hour). These drive architecture choices.

**Active-Active vs Active-Passive:**
- **Active-Active:** Both regions serve traffic. Requires synchronous replication or near-sync, global DNS routing, and conflict resolution. Higher cost but near-zero RTO.
- **Active-Passive:** One region is live, the other is standby. Failover requires DNS switch and database promotion. Lower cost, higher RTO (minutes).

**Database Replication:** Sync replication (same region) for zero data loss; async replication (cross-region) for lower latency but potential data loss. Use managed services (RDS Multi-AZ + cross-region read replica, Aurora Global Database, Azure SQL Geo-replication).

**DNS Failover:** Route53 (AWS) or Traffic Manager (Azure) with health checks. Use failover routing policy or priority-based routing. TTL should be low (30-60s).

**State Management:** Stateless apps are easy. Stateful apps need replicated storage (S3/Blob), distributed caches (Redis), and database failover. Use session affinity or externalize state.

**DR Patterns:**
- **Pilot Light:** Core services (database, messaging) are always on; compute is off and scaled up on failover.
- **Warm Standby:** A minimal version of the full stack is always running; scale up on failover.
- **Multi-site Active-Active:** Both sites serve traffic; failover is automatic via DNS and load balancing.

**Cost:** Active-active is 2x cost. Pilot light is cheapest. Warm standby is moderate. Choose based on RTO/RPO.

### CL8 — Hard: GitOps Model

**GitOps:** Git is the single source of truth for both infrastructure and application state. A controller (ArgoCD/Flux) continuously reconciles the cluster to match the desired state in Git.

**ArgoCD vs FluxCD:**
- **ArgoCD:** Strong UI, multi-cluster management, Application CRD, sync policies, and SSO integration. Better for teams that want a visual dashboard.
- **FluxCD:** More flexible, uses Kustomize/Helm natively, has a smaller footprint, and integrates well with Git providers. Better for automation-first teams.

**Secrets Handling:**
- **Sealed Secrets:** Encrypt secrets into a SealedSecret CRD; only the controller can decrypt.
- **External Secrets Operator:** Fetches secrets from external stores (Vault, AWS Secrets Manager, Azure Key Vault) and syncs them into K8s.
- **Vault:** Use Vault agent injector or CSI driver to mount secrets dynamically.

**Drift:** If someone manually changes the cluster (e.g., `kubectl edit deployment`), the GitOps controller detects drift and reverts the change to match Git. You can configure auto-sync or manual sync with approval. Manual changes are effectively "rejected" unless committed to Git.

### CL9 — Hard: Stateful Legacy App on Kubernetes

**StatefulSet:** Provides stable network identity (pod-0, pod-1), ordered startup/shutdown, and stable storage binding.

**PV/PVC with Local Storage Class:** Use a local storage class (e.g., Rook/Ceph, local SSDs) for low-latency, high-throughput storage. PVCs bind to specific nodes; use node affinity to ensure pods land on the right node.

**Headless Service:** Use a headless service (clusterIP: None) so each pod gets a stable DNS name (e.g., `pod-0.app.svc.cluster.local`). This supports sticky sessions and ordered access.

**Init Containers:** Use init containers to wait for dependencies (e.g., wait for database, wait for pod-0 to be ready) before starting the main container. This handles ordered startup.

**ConfigMaps as Volume Mounts:** Mount config files as ConfigMap volumes at the exact filesystem paths the app expects (e.g., `/etc/app/config.ini`). Use subPath for individual files.

**Pod Disruption Budgets:** Define PDBs to ensure a minimum number of pods are available during voluntary disruptions (e.g., node drain). For stateful apps, set `minAvailable: 1` or `maxUnavailable: 0`.

### CL10 — Medium: Service Accounts, Workload Identity, IRSA

**Service Account (K8s):** A Kubernetes identity for pods. Used for API server authentication and RBAC.

**Workload Identity (Azure/GCP):** A cloud identity assigned to a workload (pod/VM) that can authenticate to cloud APIs without static credentials.

**IRSA (IAM Roles for Service Accounts):** AWS-specific. Associates a K8s service account with an IAM role. Pods get temporary credentials via OIDC federation.

**Why mounting cloud credentials in a pod is bad:** Credentials are static, long-lived, and can be exfiltrated. They don't rotate, are hard to revoke per-pod, and violate least privilege.

**Workload Identity Federation:** Uses OIDC to exchange a K8s service account token for a cloud IAM token. Credentials are short-lived, scoped, and automatically rotated. No secrets are stored in the cluster.

### CL11 — Medium: Object vs Block vs File Storage

- **Object Storage (S3/Blob):** Stores data as objects with metadata and unique keys. Best for static files, backups, media, data lakes. Highly durable (11 nines), scalable, and cost-effective. Not for low-latency random access.
- **Block Storage (EBS/Managed Disk):** Raw disk volumes attached to a single VM. Best for databases, OS disks, and applications requiring low-latency reads/writes. Durability: 3-4 nines (depending on replication).
- **File Storage (EFS/Azure Files):** Network-attached file system shared across multiple VMs. Best for shared application files, home directories, and legacy apps. Durability: 4-5 nines.

**Availability:** Object storage is regionally redundant (11 nines durability, 99.99% availability). Block storage is zone-redundant (99.99% availability). File storage is regionally redundant (99.9% availability).

### CL12 — Hard: Zero-Trust Kubernetes Architecture

**Network Policies:** Define micro-segmentation at the pod level (e.g., only allow pods in namespace A to talk to pods in namespace B on port 443). Use a CNI that supports network policies (Calico, Cilium).

**Service Mesh with mTLS:** Use Istio/Linkerd to encrypt all pod-to-pod traffic with mTLS. Enforce identity-based authorization (e.g., only service account X can call service Y).

**Pod Identity:** Use workload identity (IRSA/Workload Identity) so each pod has a unique, scoped identity. No shared credentials.

**Admission Controllers (OPA/Kyverno):** Enforce policies at deploy time—e.g., block privileged containers, require image signatures, enforce resource limits, validate labels.

**Image Signing & Verification:** Use cosign/Notary to sign images. Admission controller verifies signatures before allowing pods to run.

**Runtime Security (Falco):** Detect anomalous behavior at runtime—e.g., unexpected system calls, file access, network connections. Falco rules trigger alerts.

**Secrets Management:** Use External Secrets Operator or Vault CSI to inject secrets dynamically. Never store secrets in Git or env vars.

**Difference from perimeter security:** Zero-trust assumes no implicit trust. Every request is authenticated, authorized, and encrypted, regardless of source. There's no "trusted internal network."

### CL13 — Easy: CDN

**CDN (Content Delivery Network):** A distributed network of edge servers that cache and serve content closer to users. It reduces latency, offloads origin traffic, and provides DDoS protection.

**How it works:** User requests content → DNS routes to nearest edge PoP → edge serves cached copy or fetches from origin → caches for future requests.

**Cloud-native CDNs:** AWS CloudFront, Azure CDN (Front Door), Google Cloud CDN.

**When to use CDN vs origin:** Use CDN for static content (images, videos, JS/CSS), API acceleration, and global distribution. Use origin directly for dynamic, personalized, or real-time data that can't be cached.

---

### CL14 — Easy: Regions and Availability Zones

**Region:** A geographic area with multiple isolated data centers (e.g., us-east-1, west-europe).

**Availability Zone (AZ):** One or more data centers within a region, with independent power, cooling, and networking. AZs are physically separate but connected via low-latency links.

**Why deploy across AZs:** High availability. If one AZ fails, your application continues in another. Use multi-AZ for databases, load balancers, and stateless compute.

**Zonal vs Regional resources:**
- **Zonal:** Tied to a single AZ (e.g., EBS volume, EC2 instance, single-AZ RDS).
- **Regional:** Replicated across AZs (e.g., S3, ELB, Aurora, Lambda).

### CL15 — Easy: Managed Database Services

**Managed DB (RDS, Cloud SQL, Azure SQL):** The cloud provider handles:
- Hardware provisioning, OS patching, backups, replication, failover, monitoring, and scaling.

**You handle:** Schema design, queries, application connections, and data optimization.

**Compared to running on a VM:** On a VM, you handle everything—OS updates, database software, backups, replication, failover, and monitoring. Managed DBs reduce operational burden but may have less control over the underlying OS.

### CL16 — Easy: Cloud Identity Services

- **IAM Users:** A permanent identity for a person or service. Has credentials (password/access keys).
- **Groups:** A collection of users. Policies attached to groups apply to all members.
- **Roles:** An identity that can be assumed temporarily. No long-term credentials. Used for services, federated users, or cross-account access.
- **Policies:** JSON documents that define permissions (allow/deny actions on resources).

**Principle of Least Privilege:** Grant only the minimum permissions required for a task. Apply by:
- Using roles instead of shared accounts.
- Scoping policies to specific resources.
- Regularly auditing and removing unused permissions.
- Using conditions (e.g., IP range, MFA, time).

---

### CL17 — Easy: Serverless Computing

**Serverless:** You write code, the cloud provider runs it. No server management, auto-scaling, pay-per-execution.

**AWS Lambda:** Event-driven, supports many languages, integrates with AWS services.
**Azure Functions:** Similar, integrates with Azure services, supports durable functions.
**Google Cloud Functions:** Lightweight, integrates with GCP services.

**Cold Starts:** The delay when a function is invoked after being idle. The provider must spin up the runtime. Cold starts can be 100ms-1s+ depending on language/runtime.

**Why cold starts matter:** For latency-sensitive APIs, cold starts cause slow responses. Mitigate with provisioned concurrency (Lambda) or keep functions warm.

**When serverless is a poor fit:** Long-running processes, stateful workloads, low-latency requirements, heavy compute (ML training), or applications with predictable high traffic that would be cheaper on reserved instances.

---

### CL18 — Medium: Kubernetes Ingress Options

**Ingress Resource:** A K8s API object that defines routing rules (host/path → service). Requires an ingress controller (NGINX, Traefik, ALB). TLS termination happens at the controller.

**Gateway API:** The next-generation ingress API. More expressive, supports HTTP, TCP, TLS, and cross-namespace routing. Controllers: Istio, Envoy Gateway, NGINX. TLS termination at the gateway.

**Cloud Load Balancer Annotations:** Use cloud-specific annotations on a Service (e.g., AWS ALB Ingress Controller, Azure Application Gateway). TLS termination at the cloud LB.

**Service Mesh Ingress Gateways:** Istio/Gateway API or Linkerd. TLS termination at the mesh edge, with mTLS inside the mesh.

**When to use Gateway API over Ingress:** When you need cross-namespace routing, TCP/UDP routing, richer traffic management (weighted, header-based), or multi-cluster routing. Gateway API is the future standard.

### CL19 — Hard: Cost Optimization Strategy ($80k/month)

**Reserved Instances vs Savings Plans vs Spot:**
- **Reserved Instances:** 1-3 year commitment, up to 72% savings. Best for steady-state workloads.
- **Savings Plans:** Flexible commitment (compute usage), up to 72% savings. Best for mixed workloads.
- **Spot/Preemptible:** Up to 90% savings, but can be terminated. Best for stateless, fault-tolerant, batch workloads.

**Right-sizing:** Analyze utilization (CPU, memory, network) and downsize over-provisioned instances. Use CloudWatch/Cloud Advisor.

**Storage Tiering:** Use S3 Intelligent-Tiering for unknown access patterns, S3 Glacier/Archive for cold data. Move unused EBS volumes to snapshot storage.

**Idle Resource Detection:** Find unattached EBS volumes, idle load balancers, unused IP addresses, and orphaned resources. Automate termination.

**FinOps Practices:** Establish a FinOps team, use tagging for cost allocation, implement budget alerts, and review costs weekly.

**Showback/Chargeback:** Tag resources by team/project. Use cost allocation reports to show each team their spend. Chargeback: deduct from team budgets.

**Tools:** AWS Cost Explorer, Azure Cost Management, Terraform Cloud cost estimation, CloudHealth, or OpenCost.

### CL20 — Hard: Multi-Cloud Strategy

**Abstraction Layers:**
- **Kubernetes as common runtime:** Run workloads on EKS/AKS/GKE with the same manifests.
- **Terraform for IaC:** Write provider-agnostic modules for AWS/Azure.
- **Service abstraction:** Use managed services (S3 vs Blob, RDS vs SQL) behind a common interface.

**Networking:** Connect clouds via VPN or dedicated interconnect (AWS Direct Connect + Azure ExpressRoute). Use a central hub for inter-cloud traffic.

**Identity Federation:** Use OIDC/SAML to federate identities across clouds. Use a single IdP (Okta/Azure AD) for both clouds.

**Real-world trade-offs:**
- **Benefits:** Avoid lock-in, best-of-breed services, resilience.
- **Costs:** Higher complexity, duplicated tooling, cross-cloud latency, harder compliance, and higher operational overhead.

**When multi-cloud is justified:** Regulatory requirements (data residency), avoiding single-vendor risk, or specific service needs (e.g., AWS for ML, Azure for M365).

**When it's unnecessary complexity:** If you don't have a specific driver, single-cloud is simpler, cheaper, and more reliable. Multi-cloud for the sake of it increases risk.

## OT Infrastructure Architecture (20 questions)

### OT1 — Easy: Purdue Model (ISA-95)

The Purdue Model (ISA-95) is a reference architecture for industrial control systems, dividing the enterprise into levels:

- **Level 0 — Physical Process:** Sensors, actuators, and physical equipment (valves, motors, pumps).
- **Level 1 — Basic Control:** PLCs, RTUs, and DCS controllers that directly control Level 0 devices.
- **Level 2 — Supervision:** HMIs, SCADA servers, and historian systems that monitor and control Level 1.
- **Level 3 — Operations Management:** Plant-wide systems like MES, batch management, and plant historians. This is the last level before IT.
- **Level 4 — Enterprise:** ERP, CRM, and business systems. This is the IT domain.
- **Level 5 — Internet/External:** Cloud, remote access, and external partners.

---

### OT2 — Easy: IT vs OT Networks

**IT Networks:** Prioritize confidentiality and integrity. Use standard protocols (TCP/IP, HTTP), frequent patching, and modern security tools.

**OT Networks:** Prioritize availability and safety. Use proprietary protocols (Modbus, OPC UA), legacy devices, and real-time control loops. Patching is risky because it can disrupt production.

**Why standard IT patching fails in OT:**
- **Uptime requirements:** Rebooting a PLC or HMI can stop production.
- **Legacy systems:** Many OT devices are old and unsupported.
- **Vendor validation:** Patches must be tested by the vendor for safety.
- **Real-time constraints:** Patching can introduce latency or instability.
- **No central management:** Many OT devices lack remote management.

---

### OT3 — Medium: DMZ (IDMZ) Between IT and OT

**Role of the IDMZ:** A secure buffer zone between the IT network (Level 4) and the OT network (Level 3). It hosts services that need to be accessed from both sides, such as:
- Remote access gateways (jump hosts)
- Patch management servers
- Data historians (for IT access)
- Web servers for reporting

**Traffic allowed:**
- **IT → IDMZ:** HTTPS, RDP (to jump hosts), file transfer (SFTP).
- **IDMZ → OT:** Only specific protocols (e.g., OPC UA, SQL to historian) via controlled paths.
- **OT → IDMZ:** Historian data push, syslog, SNMP.
- **IT → OT (direct):** **Never allowed.**

**Why direct IT-to-Level 1 is dangerous:** A compromised IT system can directly send commands to PLCs, bypassing all safety and control logic. This can cause physical damage, safety incidents, or production loss.

---

### OT4 — Medium: OT Protocols

1. **Modbus TCP:** A simple, open protocol for reading/writing registers. Operates at Level 1 (PLC-to-PLC) and Level 2 (HMI-to-PLC). No authentication or encryption.
2. **OPC UA:** A service-oriented protocol for data exchange between controllers, HMIs, and historians. Operates at Level 2-3. Supports encryption and authentication.
3. **EtherNet/IP (CIP):** An industrial Ethernet protocol for real-time control and I/O. Operates at Level 1-2. Uses TCP/UDP, no native security.
4. **PROFINET:** An industrial Ethernet standard for real-time control. Operates at Level 1-2. Supports security features but often not enabled.
5. **MQTT:** A lightweight publish/subscribe protocol for IoT and telemetry. Operates at Level 3-4 (edge to cloud). Supports TLS and authentication.

---

### OT5 — Medium: Data Diode vs Firewall

**Data Diode:** A hardware device that physically allows data to flow in only one direction. It's unidirectional by design—no return traffic possible.

**Firewall:** A software/hardware device that filters traffic in both directions based on rules.

**When to use a data diode:** When you need absolute one-way data transfer—e.g., sending process data from OT to IT/cloud, but never allowing any traffic back into OT. Used in high-security environments (critical infrastructure, nuclear, defense).

**Limitation:** You cannot send commands or acknowledgments back. You can't remotely manage or patch devices behind a diode. It's for data exfiltration only.

---

### OT6 — Medium: SCADA to Cloud Data Flow

**Data Flow Design:**
1. **Historian (Level 3):** Collects process data from PLCs via OPC UA.
2. **OPC UA Server:** Exposes data to the edge gateway.
3. **Edge Gateway (IDMZ):** Converts OPC UA to MQTT, adds local buffering, and forwards to the cloud.
4. **MQTT Broker (Cloud):** Receives telemetry, stores in time-series DB (e.g., InfluxDB, Azure Time Series Insights).
5. **Cloud Analytics:** Processes data for dashboards, ML, and reporting.

**Security Boundaries:**
- **Boundary 1 (OT ↔ IDMZ):** Firewall with allow-only rules for OPC UA from historian to edge gateway.
- **Boundary 2 (IDMZ ↔ Cloud):** Use a data diode or one-way TLS connection. Edge gateway authenticates to cloud via client certificates.
- **Boundary 3 (Cloud):** Use managed identity, encrypt data at rest, and restrict access.

---

### OT7 — Hard: IEC 62443 Zones and Conduits

**IEC 62443** defines security zones and conduits for OT segmentation.

**Zone:** A logical grouping of assets with similar security requirements. Zones share trust levels and risk profiles. E.g., "Control Zone" (PLCs, HMIs) vs "Corporate Zone."

**Conduit:** A communication path between zones. Conduits are controlled by firewalls/routers and allow only specific protocols.

**Zone-and-Conduit Model for a Manufacturing Plant:**
- **Zone 1 — Corporate Network (Level 4):** IT systems, ERP, email.
- **Zone 2 — Operations Management (Level 3):** SCADA servers, historians, MES.
- **Zone 3 — Control Zone (Level 2):** HMIs, engineering workstations.
- **Zone 4 — Field Zone (Level 1):** PLCs, RTUs, DCS controllers.
- **Zone 5 — Safety Zone (SIS):** Safety instrumented systems (air-gapped or highly isolated).

**Conduits:**
- **Corporate ↔ Operations:** Firewall with HTTPS, SQL, and remote access via jump host.
- **Operations ↔ Control:** Firewall with OPC UA, Modbus TCP, and engineering protocols.
- **Control ↔ Field:** Firewall with I/O protocols (EtherNet/IP, PROFINET).
- **Safety Zone:** No conduits or only a one-way data diode for monitoring.

---

### OT8 — Hard: Network Segmentation for 200 PLCs

**VLAN Design:**
- **VLAN 10 — Corporate IT:** Level 4 systems.
- **VLAN 20 — Operations (Level 3):** SCADA, historian, MES.
- **VLAN 30 — Line 1 Control (Level 2):** HMIs, engineering workstations for Line 1.
- **VLAN 31 — Line 2 Control:** Same for Line 2.
- **VLAN 32 — Line 3 Control:** Same for Line 3.
- **VLAN 33 — Line 4 Control:** Same for Line 4.
- **VLAN 40 — Field Devices (Level 1):** PLCs, RTUs (could be per-line or shared).
- **VLAN 50 — Safety (SIS):** Air-gapped or isolated.

**Firewall Placement:**
- **Core Firewall:** Between IT (VLAN 10) and OT (VLAN 20+). Enforces IDMZ.
- **Line Firewalls:** Between Operations (VLAN 20) and each Line VLAN (30-33). Allow only specific protocols (OPC UA, Modbus).
- **Field Firewalls:** Between Line VLANs and Field VLAN (40). Allow only I/O protocols.

**Switch Architecture:**
- Use a **core switch** for the OT backbone, with **distribution switches** per line.
- Use **managed switches** with VLAN support and port security.
- Enable **STP (Spanning Tree)** or use **ring topology** for redundancy.

**Remote Access for Vendors:**
- Use a **jump host** in the IDMZ with MFA and session recording.
- Vendors get **time-limited access** via VPN to the jump host only.
- Never allow direct VPN to PLCs or HMIs.

**Transition Without Stopping Production:**
- **Phased approach:** Segment one line at a time during scheduled maintenance windows.
- **Use temporary firewalls** (e.g., Palo Alto/Check Point) in "monitor mode" to learn traffic patterns.
- **Validate traffic** before enforcing rules.
- **Rollback plan:** If a rule breaks production, revert immediately.

---

### OT9 — Hard: SIS vs BPCS, IEC 61511

**BPCS (Basic Process Control System):** The standard control system (PLCs, DCS) that keeps the process running within normal operating parameters.

**SIS (Safety Instrumented System):** An independent, highly reliable system that detects dangerous conditions and initiates safety actions (e.g., emergency shutdown, pressure relief). It's designed to prevent or mitigate catastrophic events.

**IEC 61511:** The functional safety standard for SIS. It defines safety integrity levels (SIL 1-4), lifecycle requirements, and proof testing.

**Why SIS must be isolated:** A ransomware attack on the SIS could disable safety functions, leading to explosions, toxic releases, or loss of life. The SIS must remain operational even if the BPCS is compromised.

**If ransomware reaches the SIS:** The plant loses its last line of defense. Operators may not receive alarms, and safety shutdowns may not trigger. This can result in catastrophic physical damage and loss of life. The SIS must be air-gapped or protected by a data diode.

---

### OT10 — Medium: PLC vs DCS vs SCADA

**PLC (Programmable Logic Controller):** A ruggedized industrial computer for discrete control (on/off, sequencing). Used for small to medium automation tasks (e.g., a single machine).

**DCS (Distributed Control System):** A centralized control architecture for large, continuous processes (e.g., chemical plants, refineries). It integrates controllers, HMIs, and historians into a single system.

**SCADA (Supervisory Control and Data Acquisition):** A software system that monitors and controls geographically distributed assets (e.g., pipelines, power grids). It gathers data from remote RTUs/PLCs and provides operator dashboards.

**When to use each:**
- **PLC:** Small, discrete, standalone machines.
- **DCS:** Large, continuous, complex processes with many I/O points.
- **SCADA:** Distributed assets over a wide area (e.g., water distribution, oil pipelines).

**Can they coexist?** Yes. A plant can have a DCS for the main process, PLCs for auxiliary equipment, and a SCADA system for remote monitoring.

---

### OT11 — Medium: Remote Access to OT

**Architecture:**
- **Jump Host (Bastion):** A hardened server in the IDMZ. All remote access goes through this host.
- **MFA:** Require multi-factor authentication for all remote sessions.
- **Session Recording:** Record all remote sessions for audit and forensic purposes.
- **Vendor Access:** Vendors get a dedicated, time-limited account with access only to their specific devices.
- **Time-Limited Access:** Use temporary credentials or scheduled access windows (e.g., 9am-5pm, 2 hours).

**Why direct RDP to HMI is unacceptable:**
- No audit trail, no MFA, no session recording.
- Exposes the HMI directly to the internet/corporate network.
- A compromised HMI can be used to send commands to PLCs.
- No way to enforce time limits or vendor-specific access.

---

### OT12 — Hard: Water Treatment Facility Incident Response

**Detection:**
- **Network Monitoring:** Deploy passive IDS (e.g., Zeek/Suricata) at Level 3/2 to detect anomalous traffic (e.g., unexpected Modbus commands, VPN traffic).
- **Anomaly Detection:** Use behavioral baselines—e.g., a PLC that normally sends 10 packets/min suddenly sends 1000.
- **Asset Inventory:** Maintain a complete inventory of all OT assets (PLCs, HMIs, servers) with their expected behavior.

**Incident Response Steps:**
1. **Triage:** Confirm the alert, assess severity, and determine if it's a false positive.
2. **Isolate:** Disconnect the compromised VPN appliance and any affected systems from the network.
3. **Contain:** Block the threat actor's known IOCs (IPs, domains) at the firewall.
4. **Eradicate:** Reimage the compromised VPN appliance and any infected hosts.
5. **Recover:** Restore from backups, verify integrity, and monitor for re-infection.
6. **Lessons Learned:** Update security policies, improve monitoring, and conduct a post-incident review.

**Coordination with Control Room:**
- The control room operator is the **primary decision-maker** for safety. They can issue manual overrides or shutdowns if needed.
- The IR team must **not** disrupt control operations without operator approval.
- Use a **unified communication channel** (e.g., a dedicated hotline) between IR and control room.

**Role of the Plant Operator:**
- Monitor process alarms and ensure safe operation.
- Execute manual shutdowns or overrides if the cyber incident affects control.
- Provide situational awareness to the IR team.
- **Never** take actions that could compromise safety (e.g., disconnecting a safety system).

### OT13 — Easy: HMI vs Engineering Workstation

**HMI (Human-Machine Interface):** A graphical interface that allows operators to monitor and control the process. It displays real-time data (temperatures, pressures, alarms) and allows operators to send commands (start/stop pumps, change setpoints).

**Engineering Workstation:** A PC used by engineers to program, configure, and maintain controllers (PLCs, RTUs). It runs engineering software (e.g., Studio 5000, TIA Portal) and can download logic to controllers.

**Difference:** HMI is for operators (runtime use), engineering workstation is for engineers (development/maintenance). Engineering workstations are higher-risk because they can modify control logic.

### OT14 — Easy: Historian

**Historian:** A time-series database that collects and stores process data (temperatures, pressures, flow rates, alarms) from controllers and HMIs.

**Why it's important:** It provides historical context for troubleshooting, optimization, compliance reporting, and predictive maintenance.

**Plant Historian (Level 3):** Collects data from the control system (PLCs, DCS) at high frequency (e.g., 1-second intervals). Used for process analysis and troubleshooting.

**Enterprise Historian (Level 4):** Aggregates data from multiple plant historians for enterprise-wide reporting, KPIs, and analytics. Lower frequency (e.g., 1-minute intervals).

### OT15 — Easy: Ladder Logic

**Ladder Logic:** A graphical programming language for PLCs that resembles electrical relay logic diagrams. It uses contacts (inputs) and coils (outputs) arranged in rungs.

**Device that executes it:** PLCs (Programmable Logic Controllers).

**Why it's still dominant:**
- **Familiarity:** Electricians and engineers already know relay logic.
- **Simplicity:** Easy to visualize and debug.
- **Deterministic:** Executes in a predictable scan cycle.
- **Legacy:** Millions of existing programs and trained engineers.
- **Safety:** Well-understood behavior for safety-critical applications.

---

### OT16 — Easy: RTU vs PLC

**RTU (Remote Terminal Unit):** A ruggedized controller designed for remote, unattended locations. It communicates over long distances (e.g., radio, satellite, cellular) and is optimized for telemetry and remote control.

**PLC:** A controller designed for local, high-speed control in industrial environments. It's typically installed near the process.

**When to use RTU instead of PLC:**
- **Remote locations:** Pipelines, power substations, water wells.
- **Wide-area telemetry:** SCADA systems that monitor distributed assets.
- **Low-power environments:** Solar/battery-powered sites.
- **Harsh environments:** Extreme temperatures, vibration, no local power.

### OT17 — Easy: Analog vs Digital Signals, 4-20mA

**Digital Signals:** Discrete on/off states (0 or 1). Used for limit switches, relays, and proximity sensors.

**Analog Signals:** Continuous variable values. Used for process measurements (temperature, pressure, level, flow).

**Common analog ranges:** 4-20mA (current loop), 0-10V (voltage).

**Why 4-20mA is preferred over 0-20mA:**
- **Live zero:** 4mA indicates a live signal. If the signal drops to 0mA, it indicates a wire break or device failure.
- **No offset error:** The 4mA baseline avoids the non-linearity near 0mA.
- **Better noise immunity:** Current loops are less susceptible to voltage drops and EMI.
- **Intrinsic safety:** 4-20mA is easier to implement in hazardous areas.

### OT18 — Medium: OT Asset Inventory

**Why it's the foundation:** You can't protect what you don't know. Asset inventory provides:
- Visibility into what's connected (PLCs, HMIs, servers, switches).
- Baseline for anomaly detection.
- Input for risk assessment and segmentation.
- Compliance evidence.

**Discovery Tools:**
- **Passive Network Monitoring:** Use SPAN ports or TAPs to observe traffic without sending packets. Tools: Zeek, Nozomi, Dragos, Claroty. Safe—no impact on OT.
- **Active Scanning:** Use Nmap or vulnerability scanners to send probes to devices. **Dangerous** because:
  - Legacy devices may crash or reboot when scanned.
  - Protocols like Modbus don't respond well to unexpected packets.
  - Scanning can disrupt real-time control loops.

**Best practice:** Use passive monitoring first, then selectively active-scan only known-safe devices (e.g., Windows servers) during maintenance windows.

### OT19 — Hard: MITRE ATT&CK for ICS

**MITRE ATT&CK for ICS** is a knowledge base of adversary tactics and techniques specific to industrial control systems.

**5 Tactics and Example Techniques:**
1. **Initial Access:** *Exploit Public-Facing Application* (e.g., hacking a vendor's web portal).
2. **Execution:** *Command & Scripting Interpreter* (e.g., running PowerShell on a Windows engineering workstation).
3. **Persistence:** *Modify Controller Logic* (e.g., changing ladder logic in a PLC).
4. **Lateral Movement:** *Remote Services* (e.g., using RDP to move from IT to OT).
5. **Impact:** *Damage to Process* (e.g., opening a safety valve to cause a leak).

**Difference from Enterprise ATT&CK:** ICS framework includes techniques specific to controllers, HMIs, historians, and safety systems. It accounts for physical impact and safety consequences.

**How to use it:** Map your OT environment to the framework to identify gaps. For example, if you have no detection for "Modify Controller Logic," you need to add monitoring for firmware changes and logic uploads.

### OT20 — Hard: Converged IT/OT SOC

**Log Collection from OT Assets:**
- Use **passive collectors** (SPAN ports, network TAPs) to capture traffic without impacting real-time operations.
- Use **OPC UA** or **Syslog** from HMIs and servers where possible.
- Use **industrial protocol parsers** (e.g., Modbus, EtherNet/IP) to extract metadata.
- Avoid installing agents on PLCs or RTUs—they may disrupt control.

**SIEM Integration:**
- Forward OT logs to a central SIEM (e.g., Splunk, Sentinel, Elastic) via a one-way data diode or secure forwarding.
- Correlate OT events with IT events (e.g., a VPN login from a vendor followed by a PLC logic change).

**OT-Specific Detection Rules:**
- **Firmware change on a PLC** (unauthorized).
- **Unexpected Modbus write** to a coil/register.
- **New device** appearing on the OT network.
- **High-volume traffic** from a single asset (anomaly).
- **Login from a vendor account** outside approved hours.

**Alert Triage Workflows:**
- **IT Analyst:** Handles IT-related alerts (VPN, malware, phishing).
- **OT Engineer:** Handles OT-specific alerts (PLC logic changes, protocol anomalies).
- **Escalation:** If an alert indicates a safety impact, escalate immediately to the control room.

**Challenge of False Positives:**
- OT environments have **noisy** traffic (e.g., broadcast storms, vendor maintenance).
- False positives cause **alert fatigue** and can lead to missed real threats.
- Mitigation: Use **baseline profiling** (learn normal behavior), tune rules per asset, and validate alerts with OT engineers.

**Handling a PLC Firmware Change Alert:**
1. **Verify** the alert with the OT engineer—was it a scheduled maintenance?
2. **Check** the asset inventory—is the PLC known and authorized?
3. **Isolate** the PLC from the network if unauthorized.
4. **Forensic analysis:** Compare the current firmware hash to the known-good hash.
5. **Recover:** Restore the original firmware from backup.
6. **Report** to the plant manager and security leadership.
