## OpenTofu / Terraform (20 questions)

**T1 — Easy: What is the difference between tofu plan and tofu apply?**  
`tofu plan` performs a dry-run: it compares the current state against the configuration and shows what will be created, modified, or destroyed, without making any changes. `tofu apply` executes the changes described in the plan (or generates a new plan and applies it), and can be run with `-auto-approve` to skip interactive confirmation.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**  
State is a JSON file that maps your configuration to real-world resources, storing resource IDs, attributes, and metadata. Remote state stores this file in a shared backend (e.g., S3, GCS, Terraform Cloud) so that multiple team members and CI pipelines can access it, prevents conflicts, enables state locking, and survives local machine failures.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**  
`count` creates a list of resources indexed by numbers (e.g., `aws_instance.web[0]`), while `for_each` creates a map keyed by unique strings (e.g., `aws_instance.web["web1"]`). `for_each` is preferred when resources have distinct keys, you need to reference specific instances, or when you want to delete/insert individual instances without affecting others (e.g., removing `web2` from a `toset` only destroys that instance).

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?**  
OpenTofu detects drift during `tofu plan` by refreshing the state against the actual cloud resource. It will show the difference as a change. If the configuration still matches the desired state, OpenTofu will plan to revert the manual change (or update it if the configuration also changed). It does not automatically fix drift; you must run `tofu apply` to reconcile.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**  
```hcl
resource "aws_instance" "web" {
  for_each      = toset(["web1", "web2", "web3"])
  ami           = "ami-123456"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**  
`terraform_remote_state` reads the state of another root module from its backend, extracting outputs. It creates a hard dependency on that module's state, which can cause issues with locking, versioning, and cross-team coordination. Output values are the standard way to expose data from a module, but they only work within the same root module. The recommended alternative is to use a shared data store (e.g., AWS SSM Parameter Store, Consul, or a database) or a dedicated data source (e.g., `http` or `aws_ssm_parameter`) to fetch data, avoiding direct state coupling.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**  
The issue occurs because the output is evaluated before the `remote-exec` provisioner completes, or the provisioner hasn't written the kubeconfig file yet. Fixes: (1) Add an explicit `depends_on` on the `null_resource` in the dependent resources; (2) Use a `local-exec` provisioner to write the kubeconfig to a local file, then read it with a `file` data source; (3) Add a `time_sleep` resource to wait for the cluster to be ready before reading the output.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**  
`tofu import` imports existing infrastructure into state so it can be managed by OpenTofu. Limitations: it requires manual mapping of resource addresses, does not generate configuration, and is error-prone. The import block (1.5+) allows declarative import in configuration, making it reproducible and easier to manage, and supports generating configuration with `-generate-config-out`.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**  
Input variables are parameters that can be passed to a module or root configuration, making it configurable. Output values are return values that expose data to the caller or to the CLI (e.g., IP addresses, kubeconfigs).

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**  
A provider is a plugin that manages resources for a specific cloud/API (e.g., AWS, Azure, Kubernetes). Without `tofu init`, the provider plugins are not downloaded, and `tofu plan` will fail with an error about missing providers.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**  
It locks provider and module versions to ensure reproducible runs. Committing it ensures all team members and CI use the same versions, preventing unexpected changes from newer releases.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**  
`tofu destroy` removes all resources managed by the configuration. To target a single resource, use `tofu destroy -target=resource_type.name` (e.g., `-target=aws_instance.web`).

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**  
A data source reads information from the provider without creating/managing a resource. Example: `aws_ami` data source to fetch the latest AMI ID instead of hardcoding it, or `aws_vpc` to get an existing VPC ID.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**  
`locals` are internal values computed within a module (e.g., derived strings, tags); `variable` blocks are inputs from the caller. Use locals for values that don't need to be exposed to the caller, such as combining names or computing common tags.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**  
- `create_before_destroy`: Creates new resource before destroying old (e.g., zero-downtime updates of a VM).  
- `prevent_destroy`: Prevents accidental destruction (e.g., a production database that must never be deleted).  
- `ignore_changes`: Ignores specific attribute changes (e.g., auto-scaling changes to tags or user-data).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**  
A `moved` block tells OpenTofu to move a resource from one address to another in state, preserving the resource. It helps when renaming resources or moving them into modules without recreating them, reducing downtime and avoiding data loss.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**  
OpenTofu builds a dependency graph from resource references (implicit dependencies) and `depends_on` (explicit dependencies). Implicit dependencies are automatic (e.g., `aws_instance.web` depends on `aws_vpc.main` if referenced); explicit dependencies are manual. `depends_on` creates strict ordering, reducing parallelism because dependent resources must wait. Use it sparingly because it can slow down applies and create unnecessary dependencies that mask missing references.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**  
1. Use `-refresh=false` to skip refreshing state — faster but may miss drift.  
2. Use `-target` to plan only specific resources — faster but incomplete.  
3. Use remote state with caching (e.g., S3 with `-backend-config`) — reduces refresh time but adds complexity.  
4. Increase `-parallelism` — faster but may hit API rate limits.  
5. Use `-no-color` and `-input=false` — minor overhead reduction.  
6. Use `-compact-warnings` — reduces output processing.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**  
State locking uses a backend (e.g., DynamoDB) to prevent concurrent modifications. If a lock is not released, subsequent operations fail with a lock error. To manually break a lock, run `tofu force-unlock <lock-id>` (you must know the lock ID). Risks: breaking a lock can cause concurrent applies and state corruption if another process is still running.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.**  
1. Configure the backend in `terraform.tf` (e.g., `backend "s3"` with bucket, key, region, and `dynamodb_table`).  
2. Run `tofu init -migrate-state` — this copies the local state to the remote backend.  
3. Verify the state is in S3 and locking works (e.g., run `tofu plan` and check the lock).  
4. Check that `tofu state list` shows the same resources as before.  
5. Optionally, remove the local state file after verification.

## Ansible (20 questions)

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**  
A playbook is a YAML file that defines a set of plays (hosts + tasks). A role is a reusable, organized structure of tasks, handlers, variables, and files. A task is a single action (e.g., install a package, copy a file).

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**  
`ansible_facts` is a dictionary of system information gathered by the `setup` module. Access the OS family via `ansible_facts['os_family']` or the shortcut `ansible_os_family`.

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**  
- `command`: Executes a command without shell features (no pipes, redirects). Safe and recommended for simple commands.  
- `shell`: Executes with shell features (pipes, redirects). More flexible but risky (e.g., injection).  
- `raw`: Executes without any module wrapper, useful for rebooting or when Python is unavailable on the target.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**  
Idempotency means running the same task multiple times yields the same result. Idempotent example: `apt: name=htop state=present` (installs if missing, no-op if present). Not idempotent: `command: echo "hello" >> /tmp/file` (appends every time).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**  
```yaml
- name: Install htop on Debian
  apt:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel-release and htop on RedHat
  yum:
    name: "{{ item }}"
    state: present
  loop:
    - epel-release
    - htop
  when: ansible_os_family == "RedHat"
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**  
Precedence (lowest to highest): role defaults → inventory vars → host_vars → group_vars → set_fact → extra_vars (highest). `extra_vars` override everything; `set_fact` overrides most but not `extra_vars`.

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**  
Use `serial: 3` on the play to process 3 nodes at a time. Inventory groups: `[rke2_agents]` for all nodes, `[rke2_first]` for the first 3. Play 1: Run on `rke2_first` with `serial: 3`. Play 2: Run on `rke2_agents` with `serial: 10` and use `wait_for` to ensure the first 3 are ready before proceeding (e.g., wait for a port or a file).

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**  
`ansible-vault` encrypts sensitive data (files or strings). To encrypt a single variable, use `ansible-vault encrypt_string` to generate an encrypted string, then place it in the vars file (e.g., `password: !vault | ...`).

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**  
An inventory file defines hosts and groups. A static inventory is a file (INI/YAML) with hosts listed manually. A dynamic inventory is a script or plugin that fetches hosts from a cloud/API (e.g., AWS EC2, GCP).

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**  
```bash
ansible webservers -m command -a "df -h"
```

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**  
A handler is a task that runs only when notified by another task (e.g., restart a service). It differs from a regular task because it runs at the end of the play, not in order. Trigger it via `notify` in a task (e.g., `notify: restart nginx`).

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**  
`ansible.cfg` is the configuration file for Ansible settings. Common settings: `inventory` (path to inventory file), `forks` (parallelism), `remote_user` (default SSH user), `become` (privilege escalation), `timeout` (SSH timeout), `host_key_checking` (disable host key verification).

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**  
`register` captures the output of a task into a variable. Use it in subsequent tasks via `{{ var.stdout }}`, `{{ var.rc }}`, `{{ var.stderr }}`, etc.

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**  
`include_tasks` is dynamic: evaluated at runtime, supports conditionals and loops. `import_tasks` is static: evaluated at parse time, cannot be conditional. Use `include_tasks` for dynamic/conditional inclusion; `import_tasks` for static structure (e.g., always include a common set of tasks).

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**  
Ansible Galaxy is a community hub for roles and collections. A `requirements.yml` file lists roles/collections (e.g., `- src: geerlingguy.nginx`), and you install them with `ansible-galaxy install -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**  
- `ssh`: Default, connects via SSH to remote hosts. Used for Linux/Unix servers.  
- `local`: Runs on the control node (localhost), no SSH. Used for local actions or when the target is the control node.  
- `network_cli`: For network devices (routers/switches) using CLI over SSH. Used for network automation (e.g., Cisco, Juniper).

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**  
`delegate_to` runs a task on a specific host (e.g., `localhost`) instead of the target. `run_once` runs a task only once per play, even with multiple hosts. Example: Gather facts from a remote host, then use `delegate_to: localhost` and `run_once: true` to update a central database with the host's IP address.

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).**  
1. Increase `forks` (more parallel) — faster but may overwhelm network/API.  
2. Enable `pipelining` — reduces SSH connections, faster but requires sudo.  
3. Use fact caching (e.g., redis) — avoids gathering facts every run, but facts may be stale.  
4. Use Mitogen — faster execution via persistent connections, but adds complexity and may not be compatible with all modules.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**  
`{{ }}` outputs a variable/expression; `{% %}` is control flow (if, for, etc.); `{# #}` is a comment (not rendered). Template snippet:
```jinja2
upstream backend {
{% for server in backend_servers %}
    server {{ server }};  # health check: {{ server }}:80
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.**  
Use `serial: 2` (2 servers at a time) to minimize impact. Pre-task: Remove server from load balancer (e.g., `delegate_to: lb`). Deploy the app. Post-task: Add server back to LB. Health check: use `uri` module to check `/health` endpoint. Rollback: use `block`/`rescue` to revert to the previous version if the health check fails (e.g., `rescue` restores the old artifact and re-registers the server).
