## OpenTofu / Terraform (20 questions)

T1 — Easy: What is the difference between tofu plan and tofu apply?
- tofu plan: Shows what changes will be made to infrastructure without making any changes. It generates an execution plan.
- tofu apply: Executes the changes shown in the plan, actually creating/updating/deleting resources.

T2 — Easy: What is state in OpenTofu, and why is remote state important?
- State: A JSON file that tracks the current state of your infrastructure (resource IDs, attributes, etc.).
- Remote state: Storing state in a remote backend (e.g., S3) instead of locally. Important for collaboration, locking, and durability.

T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?
- count: Creates multiple identical resources by counting. Uses index-based keys.
- for_each: Creates multiple resources by iterating over a map or set. Uses user-defined keys.
- for_each preferred when resources need unique keys or metadata, or when working with dynamic data.

T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
- OpenTofu detects changes via its state file. If a resource is modified externally, OpenTofu will show a diff during plan and attempt to reconcile the state.
- It may try to update the resource to match the external change or mark it as tainted if it can't reconcile.

T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-abc123"
  instance_type = "t2.micro"
  tags = {
    Name = each.value
  }
}
```

T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
- terraform_remote_state: Fetches state from a remote backend. Can be slow and complex.
- output values: Share data via outputs from child modules. More efficient and idiomatic.
- Recommended alternative: Use output values. They are faster, more reliable, and better integrated with OpenTofu's workflow.

T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
- Why: null_resource outputs are empty on first apply because the remote-exec provisioner runs after the resource is created.
- Fix: Use a local-exec provisioner instead, or use a data source to fetch the kubeconfig after the cluster is created.

T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
- terraform import: CLI command to import existing infrastructure into OpenTofu state.
- Limitations: Can be error-prone, doesn't handle complex dependencies, and may require manual adjustments.
- import block: Allows importing resources declaratively in code, making it more reliable and easier to manage.

T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
- Variable: Input parameter that can be set via CLI, environment variables, or files.
- Output: Value that can be accessed by other modules or exported for use outside OpenTofu.

T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
- Provider: Plugin that manages resources for a specific cloud or service (e.g., AWS, Azure).
- If you run tofu plan without tofu init, OpenTofu will prompt you to initialize the working directory to download providers.

T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
- .terraform.lock.hcl: Lock file that pins provider versions to ensure consistent builds.
- Should be committed to version control to maintain reproducibility across environments.

T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
- tofu destroy: Destroys all resources managed by OpenTofu.
- Target a single resource: Use the -target flag (e.g., tofu destroy -target=aws_instance.example).

T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
- Data source: Fetches existing data from a provider (e.g., existing VMs, DNS records).
- Example: Use a data source to get the ID of an existing VM to attach a disk to it.

T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
- locals: Define local variables within a module. Computed at plan time.
- variable blocks: Input variables that can be set externally.
- Use locals for computed values, defaults, or to simplify complex expressions.

T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
- lifecycle block: Controls resource behavior during updates.
- create_before_destroy: Creates a new resource before destroying the old one (e.g., for zero-downtime updates).
- prevent_destroy: Prevents a resource from being destroyed (e.g., for critical infrastructure).
- ignore_changes: Ignores specific attribute changes (e.g., for immutable attributes).

T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
- moved block: Tracks resource moves between modules or configurations.
- Helps: Allows refactoring module structure without destroying and recreating resources, preserving state.

T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
- Dependency graph: OpenTofu builds a graph of resource dependencies to determine execution order.
- Implicit dependencies: Automatically inferred from resource attributes (e.g., referencing a resource ID).
- Explicit dependencies: Defined using depends_on to force a specific order.
- depends_on: Can break parallelism and should be used sparingly, as it can lead to slower plans.

T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
1. Use tofu plan -out to generate a plan file and apply it later.
2. Use tofu plan -refresh=false to skip state refresh.
3. Use tofu plan -target to target specific resources.
4. Use tofu plan -parallelism to limit concurrent operations.
Tradeoffs: Each strategy may reduce plan time but can also reduce visibility or flexibility.

T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
- State locking: Prevents concurrent operations on the same state file.
- If a lock is not released: Other operations will be blocked until the lock is released.
- Manually break a lock: Use tofu force-unlock with caution.
- Risks: Breaking a lock can lead to state corruption or conflicts.

T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
1. Configure the remote backend in OpenTofu.
2. Run tofu init to initialize the backend.
3. Run tofu plan to migrate the state.
4. Verify the state is in the remote backend.
5. Test the migration by making a small change and applying it.
6. Remove the local state file.
Risks: Migration can fail if the state is large or complex. Always test in a non-production environment first.

## Ansible (20 questions)

A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?
- Playbook: YAML file that defines a set of plays to run on hosts.
- Role: Reusable set of tasks, handlers, templates, etc., organized in a directory structure.
- Task: Single unit of work performed by Ansible (e.g., installing a package).

A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?
- ansible_facts: Dictionary of facts gathered about the target host.
- Access OS family: {{ ansible_facts['os_family'] }} or {{ ansible_os_family }}.

A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
- command: Runs a command without shell (e.g., /bin/command).
- shell: Runs a command through the shell (e.g., /bin/sh).
- raw: Runs a command directly on the target host (e.g., for unmanaged hosts).
- Use command for simple commands, shell for complex commands, and raw for unmanaged hosts.

A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
- Idempotency: Ensures a task can be run multiple times without changing the result.
- Idempotent task: apt: name=htop state=present
- Non-idempotent task: command: echo "Hello World" > /tmp/test.txt

A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_facts['os_family'] == 'Debian' else 'epel-release,htop' }}"
    state: present
```

A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
- Variable precedence order (from lowest to highest):
  1. Role defaults
  2. Inventory vars (group_vars, host_vars)
  3. Playbook vars
  4. Role vars
  5. Task vars
  6. set_fact
  7. extra_vars
- group_vars and host_vars: Inventory vars defined in group_vars and host_vars files.
- extra_vars: Variables passed via the command line or playbook.
- role defaults: Default variables defined in a role's defaults/main.yml file.
- set_fact: Variables set during playbook execution.
- Tradeoffs: Higher precedence variables override lower precedence ones.

A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
1. Create an inventory group for the first 3 nodes.
2. Create an inventory group for the remaining 47 nodes.
3. Use serial: 3 in the play for the first 3 nodes.
4. Use wait_for: until: "rke2_agent_status == 'ready'" in the play for the first 3 nodes.
5. Use serial: 47 in the play for the remaining 47 nodes.
6. Use wait_for: until: "rke2_agent_status == 'ready'" in the play for the remaining 47 nodes.

A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
- ansible-vault: Tool for encrypting sensitive data in Ansible playbooks and variables.
- Encrypt a single variable: Use the ansible-vault encrypt_string command and include the encrypted value in the vars file.

A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
- Inventory file: Defines the hosts and groups that Ansible manages.
- Static inventory: Inventory file that is manually maintained.
- Dynamic inventory: Inventory file that is generated by a script or plugin.

A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?
- ansible webservers -m command -a "df -h"

A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
- Handler: Task that is run only when notified by another task.
- Difference: Handlers are run after all tasks have completed.
- Trigger a handler: Use the notify keyword in a task.

A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
- ansible.cfg: Configuration file for Ansible.
- Common settings: inventory, remote_user, forks, timeout.

A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
- register: Stores the result of a task in a variable.
- Use the registered variable: Use the variable in a subsequent task (e.g., debug: var=result).

A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
- include_tasks: Includes tasks from a file at runtime.
- import_tasks: Imports tasks from a file at parse time.
- Use include_tasks for dynamic task inclusion and import_tasks for static task inclusion.
- Conditional evaluation: include_tasks evaluates conditions at runtime, while import_tasks evaluates conditions at parse time.

A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
- Ansible Galaxy: Repository for sharing Ansible roles and collections.
- Use a requirements.yml file: Specify roles and collections to install from Galaxy.
- Install roles and collections: Use the ansible-galaxy install command with the requirements.yml file.

A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
- Connection plugins: Define how Ansible connects to target hosts.
- ssh: Connects to remote hosts via SSH.
- local: Connects to the local host.
- network_cli: Connects to network devices via a network CLI.
- Use ssh for remote hosts, local for the local host, and network_cli for network devices.

A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
- delegate_to: Runs a task on a different host than the target host.
- run_once: Runs a task only once, even if it's applied to multiple hosts.
- Example: Gather facts from a remote host and use them to configure a file on the control node.

A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
1. Increase forks: Run more tasks in parallel.
2. Enable pipelining: Reduce the number of SSH connections.
3. Use fact caching: Cache facts to avoid gathering them repeatedly.
4. Use mitogen: Optimize SSH connections and reduce overhead.
Tradeoffs: Each strategy can improve performance but may also increase resource usage or complexity.

A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
- Jinja2 templating: Allows dynamic generation of content using variables and expressions.
- {{ }}: Output a variable or expression.
- {% %}: Execute a Jinja2 statement.
- {# #}: Comment out a block of text.
- Template snippet:
```jinja2
upstream my_upstream {
{% for server in backend_servers %}
  server {{ server.ip }}:{{ server.port }}{% if server.health_check %} check{% endif %};
  # {{ server.comment }}
{% endfor %}
}
```

A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
1. Use serial: 5 in the play to deploy in batches of 5 servers.
2. Use pre_tasks to register servers with the load balancer.
3. Use post_tasks to remove servers from the load balancer.
4. Use the uri module to check the health of the application.
5. Use block/rescue to implement a rollback strategy on failure.
6. Use notify to trigger handlers for restarting the application.
7. Use wait_for to wait for the application to become healthy before proceeding.
8. Use loop_control to control the loop behavior.
9. Use when to conditionally execute tasks.
10. Use tags to group related tasks.
