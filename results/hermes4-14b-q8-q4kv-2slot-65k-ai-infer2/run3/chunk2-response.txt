K1 — Easy: What is the difference between a Deployment and a StatefulSet?
A Deployment manages stateless pods with automatic rollouts/rollbacks, while a StatefulSet manages stateful pods with stable network identities, persistent storage, and ordered deployment/termination.

K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?
A ClusterIP Service creates a virtual IP (VIP) that is only reachable within the cluster. kube-proxy uses iptables or IPVS rules to forward traffic from the VIP to the pods' IPs, based on the Service's selector.

K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?
- PersistentVolume (PV): A piece of storage in the cluster, provisioned by an administrator or dynamically.
- PersistentVolumeClaim (PVC): A request for storage by a user, which binds to a PV.
- StorageClass: Defines storage "profiles" that can be used to dynamically provision PVs.
Relationship: PVCs request storage, which is fulfilled by PVs. StorageClasses define how PVs are dynamically provisioned when a PVC is created without a pre-existing PV.

K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).
1. Check pod logs with `kubectl logs <pod-name> -c <container-name>` to see error messages.
2. Inspect pod events with `kubectl describe pod <pod-name>` to see scheduling issues or container startup failures.
3. Verify resource requests/limits in the pod spec to ensure they are not too restrictive.
4. Check if the container image is correct and accessible (e.g., image pull secrets, registry availability).
5. Examine the container's health checks (liveness/readiness probes) if defined.

K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?
CoreDNS provides DNS resolution for services and pods within the cluster. If CoreDNS pods are down, DNS resolution will fail, causing pods to be unable to communicate with each other by name, leading to connectivity issues.

K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.
The scheduler first filters nodes that can run the pod (node affinity, taints/tolerations, resource availability). Then it scores the remaining nodes based on factors like:
1. Resource utilization (CPU/memory)
2. Anti-affinity rules (avoiding co-location with certain pods)
3. Node labels (e.g., topology spread constraints)
4. Pod priority and preemption
The highest-scoring node is selected for scheduling.

K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?
The pod will not be scheduled because the node has only 0.5GB available (4GB - 3.5GB), which is less than the pod's requested 256Mi. If the pod were scheduled and used 600Mi, it would exceed its limit, causing the container to be killed by OOM killer.

K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.
1. External request hits the cloud provider's Load Balancer (external LB).
2. The LB forwards the request to the NGINX ingress controller pods.
3. The ingress controller parses the request, matches it to an Ingress resource, and routes it to the appropriate Service.
4. The Service's Endpoints (managed by kube-proxy) point to the pod IPs.
5. kube-proxy uses iptables rules to forward traffic from the Service IP to the pod IPs.
6. The request reaches the application pod.

K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?
A NetworkPolicy defines how pods can communicate with each other and with external network endpoints. By default, all ingress and egress traffic is allowed if no NetworkPolicy exists. When a NetworkPolicy is applied, it restricts traffic to only what is explicitly allowed, blocking all other traffic.

K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?
- RollingUpdate: Updates pods incrementally, maintaining availability.
- Recreate: Terminates all old pods before creating new ones, causing downtime.
Choose Recreate for stateless applications where downtime is acceptable, or when you need to ensure all pods are updated simultaneously.

K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?
A namespace is a virtual cluster that provides resource isolation. Default namespaces: `default`, `kube-system`, `kube-public`.

K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.
`kubectl describe pod` shows detailed pod information, including:
1. Events (scheduling, startup, errors)
2. Container status (running, waiting, terminated)
3. Resource requests/limits
4. Environment variables
5. Volume mounts

K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.
A ConfigMap stores non-confidential data in key-value pairs. A pod can consume it via:
1. Environment variables
2. Volume mounts (as files in a directory)

K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?
- ClusterIP: Internal cluster-only service.
- NodePort: Exposes the service on a static port on each node's IP.
- LoadBalancer: Creates an external load balancer (cloud provider-specific) to route traffic to the service.

K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?
A DaemonSet ensures a pod runs on every node (or subset of nodes) in the cluster. Use it for system daemons like log collectors or monitoring agents, instead of Deployments which manage stateless applications.

K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?
- Taints: Node attributes that repel pods unless they have matching tolerations.
- Tolerations: Pod attributes that allow them to be scheduled on tainted nodes.
- Node Affinity: Attracts pods to nodes based on node labels.
Use case for taints/tolerations: Reserving nodes for critical system pods. Use case for node affinity: Ensuring pods run on nodes with specific hardware (e.g., GPUs).

K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?
An Operator is a custom controller that extends Kubernetes with domain-specific knowledge. It differs from standard controllers by managing complex applications with custom logic. Operators solve problems like automated application lifecycle management, configuration, and self-healing.

K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?
etcd uses a Raft consensus algorithm for strong consistency. If the quorum is lost (e.g., 2 out of 3 nodes), the cluster becomes unavailable. To recover from 2 out of 3 nodes lost, you must restore from a backup and rejoin the remaining node, then rebuild the cluster.

K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.
RBAC uses Roles (namespace-scoped) and ClusterRoles (cluster-scoped) to define permissions. RoleBindings and ClusterRoleBindings grant these permissions to users/groups. For read-only access to pods and logs in a namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: <namespace>
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: <namespace>
subjects:
- kind: User
  name: <developer-username>
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.
The `ndots` value in /etc/resolv.conf determines how many dots in a name before querying external DNS. A low value (default 1) causes excessive queries for external domains. Fix by setting `ndots: 5` in the pod's `dnsConfig`:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "5"
```

D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.
- TCP: Reliable, connection-oriented, ordered delivery (HTTP, FTP).
- UDP: Unreliable, connectionless, unordered delivery (DNS, VoIP).

D3 — Medium: What is a race condition? Give a concrete example in any language.
A race condition occurs when the outcome depends on the timing of uncontrollable events. Example in Python:
```python
counter = 0
def increment():
    global counter
    counter += 1
# Multiple threads calling increment() simultaneously
```

D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?
- Symmetric: Single key for encryption/decryption (AES).
- Asymmetric: Public/private key pair (RSA).
TLS uses asymmetric encryption for key exchange and symmetric for bulk data encryption.

D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?
A container image layer is a read-only filesystem layer. Layer caching allows Docker to reuse layers, speeding up builds. Best practices: Order instructions to maximize layer reuse, avoid unnecessary layers.

1. Check application logs for errors.
2. Verify service health (CPU/memory, disk I/O).

D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.
CAP theorem states a distributed system can only guarantee two of: Consistency, Availability, Partition tolerance. Example CP: ZooKeeper (prioritizes consistency). Example AP: Cassandra (prioritizes availability).

D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?
A deadlock is a situation where processes are waiting for resources held by others. Coffman conditions:
1. Mutual exclusion
2. Hold and wait
3. No preemption
4. Circular wait

D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?
Eventual consistency means data will eventually be consistent across replicas. Cassandra uses tunable consistency levels (e.g., QUORUM, ONE) to balance consistency and availability.

D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?
mTLS is TLS where both client and server authenticate each other. Handshake:
1. Client sends ClientHello.
2. Server sends ServerHello and certificate.
3. Client verifies server certificate and sends ClientCertificate.
4. Server verifies client certificate.
5. Keys are exchanged.
Common use: Service-to-service authentication in microservices.

D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?
A hash table maps keys to values using a hash function. Collision resolution:
- Chaining: Each bucket is a linked list.
- Open addressing: Collisions are resolved by probing.
Time complexity:
- Average: O(1) for insertion, lookup, deletion.
- Worst: O(n) for chaining, O(1) for open addressing.

D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?
A circuit breaker prevents cascading failures by monitoring service calls. States:
- Closed: Normal operation.
- Open: Service is unavailable; calls fail fast.
- Half-open: Limited calls to test recovery.
Relates to retries by preventing excessive retries during failures.

D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).
- Optimistic: Assumes no conflicts; checks at commit (e.g., row versioning).
- Pessimistic: Locks resources during transaction (e.g., SELECT FOR UPDATE).
Choose optimistic for low conflict scenarios (e.g., e-commerce inventory), pessimistic for high conflict scenarios (e.g., banking transactions).
