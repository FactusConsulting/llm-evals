CL1 — Easy: IaaS (Infrastructure as a Service) provides virtualized computing resources (e.g., AWS EC2, Azure VMs). PaaS (Platform as a Service) offers a platform for developing, running, and managing apps (e.g., AWS Elastic Beanstalk, Azure App Service). SaaS (Software as a Service) delivers software applications over the internet (e.g., Microsoft 365, Google Workspace).

CL2 — Easy: The Shared Responsibility Model defines which security tasks are handled by the cloud provider and which by the customer. For IaaS VMs, the provider secures the underlying hardware and hypervisor, while you manage the OS, apps, and data. For managed Kubernetes, the provider secures the control plane and underlying infrastructure, while you manage the cluster configuration, node security, and workloads. For a SaaS product like M365, the provider secures the entire stack, and you manage user access, data, and compliance.

CL3 — Medium: A VPC (Virtual Private Cloud) is a logically isolated network in the cloud. A subnet is a segment of the VPC's IP address range. A security group acts as a stateful firewall at the instance level, allowing/denying traffic based on rules. A NACL (Network ACL) is a stateless firewall at the subnet level, filtering traffic in both directions. They layer together: traffic flows through NACLs (subnet level) then security groups (instance level). Stateful filtering (security groups) tracks connection state, while stateless filtering (NACLs) does not.

CL4 — Medium: A multi-account AWS/Azure strategy involves: a landing zone (initial setup with core services), organizational units (OU) for grouping accounts, guardrails (policies to enforce security/compliance), shared networking (e.g., AWS Transit Gateway or Azure Hub-and-Spoke for inter-account connectivity), and centralized logging (e.g., AWS CloudTrail to a central S3 bucket). A single-account approach is problematic due to lack of isolation, increased blast radius, and difficulty in managing permissions and costs.

CL5 — Medium: Infrastructure as Code (IaC) automates infrastructure provisioning. Terraform/OpenTofu is declarative and multi-cloud. Pulumi uses general-purpose programming languages (Python, Go, etc.). CloudFormation/Bicep is AWS/Azure-specific. Crossplane extends Kubernetes for multi-cloud. Choose Terraform for multi-cloud, Pulumi for complex logic, CloudFormation/Bicep for native cloud, and Crossplane for Kubernetes-native multi-cloud.

CL6 — Medium: Cloud-native autoscaling patterns: HPA (Horizontal Pod Autoscaler) scales pods based on metrics like CPU/memory. VPA (Vertical Pod Autoscaler) adjusts pod resource requests/limits. Cluster autoscaler scales the node pool. KEDA (Kubernetes Event-driven Autoscaling) scales based on external events (e.g., queue length). Use KEDA over HPA when scaling based on external triggers (e.g., message queues, Kafka topics).

CL7 — Hard: Disaster recovery strategy: Define RPO (Recovery Point Objective) and RTO (Recovery Time Objective). Active-active (both regions live) vs active-passive (one region live, other standby). Database replication: sync (zero RPO) vs async (trade-off between RPO and performance). DNS failover (e.g., AWS Route53 health checks). State management (e.g., replicated stateful services). Cost implications (active-active is more expensive). Pilot light (minimal resources running, scaled up on failover), warm standby (scaled-down resources), and multi-site active-active (both regions fully operational).

CL8 — Hard: GitOps uses Git as the single source of truth for infrastructure and app configurations. ArgoCD and FluxCD are popular tools. Secrets can be managed via sealed secrets (GitOps-compatible), external secrets operator (integrates with cloud providers), or Vault. Manual changes that drift from Git state are detected and can be automatically reverted or flagged for review.

CL9 — Hard: For a stateful legacy app on Kubernetes: Use a StatefulSet for ordered, sticky pods. PV/PVC with a local storage class for low-latency storage. Headless service for DNS-based discovery. Init containers for pre-start tasks. ConfigMaps as volume mounts for config files. Pod disruption budgets to control voluntary disruptions.

CL10 — Medium: A service account is a Kubernetes identity for pods. Workload identity (e.g., Azure AD Workload Identity) federates Kubernetes identities with cloud IAM. IRSA (IAM Roles for Service Accounts) allows AWS IAM roles to be assumed by pods. Mounting cloud provider credentials in pods is a bad practice due to security risks. Workload identity federation solves this by securely mapping Kubernetes identities to cloud IAM roles.

CL11 — Medium: Cloud object storage (S3/Blob) is for unstructured data, highly durable, and scalable. Block storage (EBS/Managed Disk) is for VMs, offering low-latency block-level access. File storage (EFS/Azure Files) provides shared file systems. Durability and availability vary: object storage is highest, block storage is high, file storage is moderate.

CL12 — Hard: Zero-trust for Kubernetes: Network policies for micro-segmentation. Service mesh (e.g., Istio) with mTLS for encrypted service-to-service communication. Pod identity for fine-grained access control. Admission controllers (OPA/Kyverno) for policy enforcement. Image signing/verification for trusted images. Runtime security (Falco) for anomaly detection. Secrets management (e.g., HashiCorp Vault). This differs from perimeter-based security by assuming no implicit trust.

CL13 — Easy: A CDN (Content Delivery Network) caches content at edge locations closer to users, reducing latency. Cloud-native CDNs: AWS CloudFront, Azure CDN. Use a CDN for static content, high-traffic sites, or global reach; serve directly from origin for dynamic, low-traffic, or sensitive content.

CL14 — Easy: Availability zones (AZs) are isolated data centers within a region. Regions are geographic areas with multiple AZs. Deploy resources across AZs for high availability. Zonal resources are in a single AZ; regional resources span multiple AZs.

CL15 — Easy: A managed database service (e.g., AWS RDS, Azure SQL) handles provisioning, patching, backups, and scaling. The cloud provider manages the underlying infrastructure, while you manage the database itself.

CL16 — Easy: Cloud identity services: IAM users (human accounts), groups (collections of users), roles (temporary permissions), and policies (rules defining permissions). Principle of least privilege: grant only necessary permissions. Apply by using roles, least-privilege policies, and regular audits.

CL17 — Easy: Serverless computing (e.g., AWS Lambda, Azure Functions) runs code in response to events without managing servers. Cold starts are the initial delay when a function is invoked after being idle. Serverless is poor for long-running tasks, high latency, or needing persistent state.

CL18 — Medium: Kubernetes ingress options: Ingress resource (standard, but limited); Gateway API (modern, extensible); cloud load balancer annotations (provider-specific); service mesh ingress gateways (advanced, with mTLS). TLS termination varies: Ingress/Gateway API at the ingress layer; cloud load balancers at the load balancer layer; service mesh at the service layer. Use Gateway API for complex routing and observability.

CL19 — Hard: Cost optimization: Use reserved instances/savings plans for steady workloads; spot/preemptible instances for fault-tolerant workloads; right-size resources; tier storage (e.g., S3 Intelligent-Tiering); detect idle resources; implement FinOps practices (cost visibility, accountability); use showback/chargeback models. Tools: cloud provider cost management tools, third-party tools (e.g., CloudHealth, Flexera). Processes: regular cost reviews, tagging, budget alerts.

CL20 — Hard: Multi-cloud strategy: Use abstraction layers (e.g., Kubernetes, Terraform) for portability; Kubernetes as a common runtime; Terraform for IaC portability; VPN/interconnect for networking; identity federation (e.g., SAML, OIDC). Trade-offs: complexity, increased management overhead, potential for vendor lock-in at the abstraction layer. Multi-cloud is justified for avoiding single points of failure, regulatory requirements, or competitive pricing; unnecessary complexity otherwise.

OT1 — Easy: The Purdue Model (ISA-95) defines five levels: Level 0 (field devices), Level 1 (control), Level 2 (supervisory), Level 3 (plant/process), Level 4 (enterprise).

OT2 — Easy: IT networks handle data, while OT networks control physical processes. Standard IT patching can disrupt OT operations due to real-time requirements and lack of redundancy.

OT3 — Medium: An IDMZ (Industrial DMZ) isolates IT and OT networks. Allow traffic from IT to OT only for specific, necessary services (e.g., historian data). Direct connectivity from Level 4 (IT) to Level 1 (control) is dangerous due to high risk of disruption.

OT4 — Medium: Modbus TCP (Level 1), OPC UA (Levels 1-3), EtherNet/IP (CIP) (Levels 1-3), PROFINET (Levels 1-3), MQTT (Levels 2-4).

OT5 — Medium: A data diode allows one-way data transfer, while a firewall filters traffic in both directions. Use a hardware data diode for critical one-way data flows (e.g., from OT to IT). Limitation: no bidirectional communication.

OT6 — Medium: Data flow: SCADA system -> historian -> OPC UA server -> MQTT broker -> edge gateway -> cloud ingestion. Security boundaries: historian, OPC UA server, MQTT broker, edge gateway.

OT7 — Hard: IEC 62443 defines security zones (group of assets with similar security requirements) and conduits (secure communication paths). Design: Corporate network (Zone 4), Engineering workstations (Zone 3), SCADA servers (Zone 2), PLCs (Zone 1), SIS (Zone 0). Conduits between zones.

OT8 — Hard: Network segmentation: VLANs for each zone; firewalls between zones; switch architecture with segmentation; remote access via jump hosts; transition without stopping production using phased cutover.

OT9 — Hard: SIS (Safety Instrumented System) ensures safety; BPCS (Basic Process Control System) controls process. IEC 61511 defines SIS safety lifecycle. SIS must be isolated from BPCS/IT to prevent disruption. Ransomware reaching SIS can cause safety failures.

OT10 — Medium: PLC (Programmable Logic Controller) for discrete control; DCS (Distributed Control System) for continuous processes; SCADA (Supervisory Control and Data Acquisition) for monitoring/controlling. They can coexist in the same plant.

OT11 — Medium: Remote access: jump hosts, MFA, session recording, vendor access, time-limited access. RDP directly to HMI from corporate network is unacceptable due to security risks.

OT12 — Hard: Detection and response: Network monitoring (IDS/anomaly detection), asset inventory, incident response steps, coordination with control room, safe operations during isolation. Plant operator role: monitor process, execute manual controls if needed.

OT13 — Easy: HMI (Human-Machine Interface) allows operators to interact with industrial systems. Differs from engineering workstation by focusing on monitoring/control rather than configuration.

OT14 — Easy: Historian stores process data. Plant historian (Level 3) stores real-time data; enterprise historian (Level 4) aggregates data for business use.

OT15 — Easy: Ladder logic is a programming language for PLCs, using symbols resembling relay logic. Dominant due to familiarity, simplicity, and suitability for discrete control.

OT16 — Easy: RTU (Remote Terminal Unit) collects/transmits data from remote locations. Differs from PLC by typically being less powerful and used in remote areas. Deploy RTUs where PLCs are impractical.

OT17 — Easy: Analog signals (4-20mA, 0-10V) represent continuous values; digital signals represent discrete states. 4-20mA preferred over 0-20mA for process instrumentation due to ability to detect open circuits.

OT18 — Medium: OT asset inventory is the foundation of OT security. Tools: passive network monitoring, active scanning. Active scanning is dangerous in OT networks due to potential disruption.

OT19 — Hard: MITRE ATT&CK for ICS framework: Tactics: Initial Access (e.g., Spearphishing Attachments), Execution (e.g., PowerShell), Persistence (e.g., Registry Run Keys), Credential Access (e.g., Brute Force), Impact (e.g., Data Encrypted for Impact). Differs from enterprise ATT&CK by focusing on ICS-specific techniques. Use to assess defensive gaps.

OT20 — Hard: Converged IT/OT SOC: Log collection (e.g., passive monitoring, OT-specific agents), SIEM integration, OT-specific detection rules, alert triage workflows, staffing (IT analysts + OT engineers), handling false positives. Unauthorized firmware changes on a PLC: isolate the PLC, investigate, restore from backup if necessary, update firmware securely.
