## SC1 — Medium — Broken Deployments After Cluster Upgrade

Part A:  
The pods are failing because the Restricted Pod Security Standard (PSS) enforces `runAsNonRoot: true` and `runAsUser` must be explicitly set. The new base image (cgr.dev/chainguard/static:latest) defaults to `USER root`, but the container image does not override this. With PSS enforcement, Kubernetes rejects the pod because it cannot run as root.  
**Interaction**:  
- PSS `Restricted` requires `runAsNonRoot: true` and `runAsUser` to be set.  
- The container image’s `USER` directive is ignored if `runAsUser` is not explicitly set in the pod spec.  
**Change from Baseline**:  
- Baseline allows `runAsNonRoot: false` (root by default) and does not enforce `runAsUser`.  
- Restricted forces non-root execution and requires explicit `runAsUser` to avoid ambiguity.  

Part B:  
```bash
kubectl get pods --all-namespaces --field-selector=status.phase=Failed --output=jsonpath='{range .items[?(@.status.containerStatuses[*].restartCount > 0)]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.spec.securityContext.runAsNonRoot}{"\t"}{.spec.securityContext.runAsUser}{"\n"}{end}'
```  

Part C:  
**Immediate Fix**:  
1. **Image-Level**: Rebuild the base image with `USER` explicitly set to a non-root UID (e.g., `1001`).  
2. **Manifest**: Add `securityContext: { runAsUser: 1001 }` to the pod spec.  
3. **Rollout**: Use `kubectl rollout restart deployment <deployment-name>` to trigger a rolling update.  

**Prevention**:  
- **CI Pipeline Gate**: Add a step to validate `runAsUser` is set in the pod spec and the base image’s `USER` matches.  
- **Admission Controller**: Deploy Kyverno or OPA Gatekeeper to enforce `runAsUser` and PSS compliance.  

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

Part A:  
**Stale Data Issue**:  
- Promoting a cross-region replica breaks replication. Writes to the new primary (eu-west-1) are not replicated back to the old primary (us-east-1).  
- **Replication Lag**: Asynchronous replication introduces a lag window (e.g., seconds to minutes). During promotion, any data written to the old primary after the last WAL shipped is lost.  
- **Data Loss Scenarios**:  
  - **Asynchronous**: Data written after the last WAL shipped is lost.  
  - **Synchronous**: Zero data loss but higher latency.  
- **Quantify Data Loss**: Check `pg_stat_replication` for `write_lag` and `flush_lag` on the old primary.  

Part B:  
```bash
# Import the promoted replica into Terraform state
terraform import aws_db_instance.dr_replica eu-west-1:replica-instance-id

# Update references to the old instance
terraform state mv aws_db_instance.old_primary eu-west-1:replica-instance-id
terraform state mv aws_db_instance.dr_replica eu-west-1:replica-instance-id

# Update dependent resources (e.g., Route53, security groups)
terraform apply
```  

Part C:  
**Architecture**:  
- **RDS Proxy vs PgBouncer**: Use RDS Proxy for connection pooling and automatic failover.  
- **Route53**: Health checks with DNS failover to the new primary.  
- **Application Retry Logic**: Implement exponential backoff for transient errors.  
- **RPO < 1s**: Use Aurora Global Database (synchronous replication) instead of standard RDS.  
- **Recommendation**: Aurora Global Database is better due to built-in cross-region replication and failover.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

Part A:  
**Top 5 Blockers**:  
1. **Sticky Sessions**: F5 BIG-IP uses local session affinity.  
   - **Solution**: Use Kubernetes Ingress with session affinity or a service mesh.  
2. **Local NFS Mount**: `/data/uploads` is tied to bare-metal.  
   - **Solution**: Provision a PersistentVolume (PV) with NFS CSI driver.  
3. **Oracle Database**: On-prem Oracle 19c.  
   - **Solution**: Containerize Oracle or use a managed service.  
4. **IBM MQ**: Mainframe integration.  
   - **Solution**: Use MQ containerized or a managed MQ service.  
5. **Memory-Backed Sessions**: Local session storage.  
   - **Solution**: Use Redis or Hazelcast for distributed sessions.  

Part B:  
```hcl
variable "nfs_server" { type = string }
variable "nfs_path" { type = string }
variable "storage_capacity" { type = string }

resource "kubernetes_storage_class" "nfs" {
  metadata { name = "nfs-sc" }
  provisioner = "kubernetes.io/no-provisioner"
  volume_binding_mode = "WaitForFirstConsumer"
  reclaim_policy = "Delete"
}

resource "kubernetes_persistent_volume" "nfs_pv" {
  metadata { name = "nfs-pv" }
  spec {
    capacity { storage = var.storage_capacity }
    access_modes = ["ReadWriteMany"]
    nfs {
      path = var.nfs_path
      server = var.nfs_server
    }
  }
}

resource "kubernetes_persistent_volume_claim" "nfs_pvc" {
  metadata { name = "nfs-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    storage_class_name = "nfs-sc"
    resources { requests = { storage = var.storage_capacity } }
  }
}
```  
**ReadWriteMany**: Required for multiple pods to access the same NFS share.  

Part C:  
**Phased Migration (Strangler Fig)**:  
- **Phase 1**: Deploy new microservices alongside the monolith. Use a service mesh to route traffic.  
- **Phase 2**: Gradually migrate functionality (e.g., inventory, pricing) to new services.  
- **Phase 3**: Decommission the monolith after all functionality is migrated.  
**Zero-Downtime**: Use blue/green deployments and canary releases.  
**Rollback**: Revert traffic routing if issues arise.  
**Metrics**: Monitor error rates, latency, and resource usage.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

Part A:  
**Drift Sources**:  
1. **Manual `tofu apply`**: Developers bypass CI, risking untracked changes.  
2. **Diverged Helm Values**: Manual edits in staging/production.  
3. **Direct `kubectl edit`**: Untracked ConfigMap changes.  
**Risks**:  
- Data loss from uncoordinated state changes.  
- Outages from conflicting changes.  

Part B:  
```yaml
stages:
  - validate
  - plan
  - apply

validate:
  stage: validate
  script:
    - tofu fmt -check
    - tofu validate

plan:
  stage: plan
  script:
    - tofu plan -out=tfplan
  artifacts:
    paths: [tfplan]

apply:
  stage: apply
  script:
    - tofu apply -auto-approve tfplan
  environment: production
  when: manual
  lock_timeout: 60
  lock_method: dynamodb
```  

Part C:  
**Drift Detection**:  
- **Scheduled `tofu plan`**: Run in CI to detect drift.  
- **Admission Webhook**: Block direct `kubectl edit` on critical resources.  
- **Helm Values**: Use Helmfile/Kustomize for base/override separation.  
**RBAC**:  
- Restrict `kubectl` access to CI service account.  
- Use IAM roles for AWS resources.

## SC9 — Medium — Securing a Public-Facing API After a Breach

Part A:  
**Vulnerabilities**:  
1. **BOLA**: Violates OWASP API Top 10 (Broken Object Level Authorization).  
   - **Fix**: Implement object-level permissions in Django.  
   ```python
   class UserRecordViewSet(viewsets.ModelViewSet):
     def get_object(self):
       obj = super().get_object()
       if obj.user != self.request.user:
         raise PermissionDenied("Not your record")
       return obj
   ```  
2. **Full Database Objects**: Exposes internal fields.  
   - **Fix**: Return only necessary fields in serializers.  
3. **No Rate Limiting**: Allows data scraping.  
   - **Fix**: Implement rate limiting (e.g., Django Ratelimit).  
4. **API Keys in URL**: Logged in plaintext.  
   - **Fix**: Move API keys to headers.  

Part B:  

Part C:  
**Defense-in-Depth**:  
- **API Key Migration**: Rotate keys and move to headers.  
- **OAuth2**: Implement short-lived JWTs.  
- **API Gateway**: Use Kong/AWS API Gateway for auth/rate-limiting.  
- **CloudTrail**: Enable data events for auditing.  
- **Field-Level Encryption**: Encrypt PII in the database.  
**Migration**: Use a phased approach with dual authentication methods.  

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

Part A:  
**Kubernetes Multi-Cluster Architecture**:  
- **Active-Passive (Velero)**:  
  - **Pros**: Simpler, lower cost.  
  - **Cons**: RPO/RTO may not meet requirements.  
- **Active-Active (Service Mesh)**:  
  - **Pros**: Better RPO/RTO.  
  - **Cons**: Higher complexity.  
**Replication Strategy**:  
- **PostgreSQL**: Patroni with synchronous replication.  
- **Redis**: Sentinel with replication.  
- **RabbitMQ**: Queue mirroring.  
- **MinIO**: Erasure coding with cross-cluster replication.  

Part B:  
```yaml
# Ansible playbook for PostgreSQL replication
- name: Configure PostgreSQL replication
  hosts: postgres_servers
  become: yes

  vars:
    patroni_config: |
      name: postgres
      scope: postgres
      namespace: patroni
      restapi:
        listen: 0.0.0.0:8008
        connect_address: {{ ansible_host }}:8008
      bootstrap:
        dcs:
          etcd:
            hosts:
              - {{ etcd_host }}:2379
      postgresql:
        use_pg_rewind: true
        use_slots: true
        parameters:
          wal_level: replica
          max_wal_senders: 10
          hot_standby: on
        synchronous_commit: on
        synchronous_standby_names: 'ANY 1 (standby1, standby2)'

  tasks:
    - name: Install Patroni
      apt: name=patroni state=present

    - name: Template patroni.yml
      template:
        src: patroni.yml.j2
        dest: /etc/patroni.yml

    - name: Start Patroni
      service: name=patroni state=started

  handlers:
    - name: Restart Patroni
      service: name=patroni state=restarted
```  

Part C:  
**Automated Failover Orchestration**:  
1. **Failure Detection**: Use monitoring tools (e.g., Prometheus) to detect site outage.  
2. **DNS Failover**: Update Route53 to point to DR site.  
3. **Patroni Promotion**: Automatically promote standby to primary.  
4. **Redis Sentinel**: Failover to replica.  
5. **RabbitMQ**: Mirror queues to DR.  
6. **MinIO**: Replicate data to DR.  
7. **OpenTofu State**: Update state to reflect new primary.  
**Split-Brain**: Use quorum-based decisions (e.g., etcd).  
**Failback**: Reverse the process after Chicago recovers.
