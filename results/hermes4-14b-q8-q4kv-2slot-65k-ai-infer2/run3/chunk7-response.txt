AA1 — Easy: A monolith is a single, unified application, while microservices are a collection of small, independently deployable services. Microservices introduce: 1) Distributed system complexity (e.g., network latency, partial failures), 2) Data consistency challenges (e.g., eventual consistency), 3) Operational overhead (e.g., monitoring, deployment).

AA2 — Easy: Synchronous communication (e.g., REST/gRPC) requires immediate response, while asynchronous (e.g., message queues) decouples sender/receiver. Example tech: Synchronous - gRPC; Asynchronous - RabbitMQ.

AA3 — Medium: An API Gateway handles routing, auth, rate limiting, while a reverse proxy focuses on load balancing and SSL termination. An API Gateway can replace a reverse proxy for API-specific needs but not for general SSL termination or load balancing across all services.

AA4 — Medium: The Saga pattern manages distributed transactions via local transactions and compensating actions. Choreography-based sagas use event-driven coordination (services react to events), while orchestration-based sagas use a central coordinator. Choreography is better for decoupled services; orchestration is better for complex, coordinated workflows.

AA5 — Medium: CQRS separates read/write operations. It pairs with Event Sourcing (persisting state changes as events) to solve issues like complex read/write conflicts and scalability in traditional CRUD models.

AA6 — Medium: The Circuit Breaker pattern prevents cascading failures by tripping after repeated failures. States: Closed (normal), Open (failures), Half-Open (testing recovery). It differs from retries by preventing further calls during failures. Use both for transient errors with retries and persistent failures with circuit breakers.

AA7 — Hard: 
1. Shared DB/Schema: Low cost, high operational complexity, noisy neighbors.
2. Shared DB/Separate Schema: Moderate cost, moderate complexity, reduced noise.
3. Separate DB: High cost, low complexity, no noise. Choose based on tenant density, isolation needs, and budget.

AA8 — Hard: Use strong consistency (e.g., with a distributed database like CockroachDB) to prevent overselling. Patterns: Optimistic concurrency, distributed locks, or a reservation system with compensating transactions.

AA9 — Hard: A sidecar proxy (e.g., Envoy in Istio) handles traffic management, security, and observability for a service. Envoy's data plane processes traffic; the control plane (Istio) configures it. mTLS between sidecars solves mutual authentication and encryption at the service mesh level, unlike application-level TLS.

AA10 — Medium: The Strangler Fig pattern replaces parts of a monolith incrementally. Strategy: Identify a bounded context, build a new microservice, route traffic to it, and gradually migrate functionality.

AA11 — Medium: The 12-Factor App methodology includes: Codebase, Dependencies, Config, Backing Services, Build, Release, Run, Processes, Port Binding, Stateless, Admin Processes, and Logs. These ensure scalability, portability, and maintainability.

AA12 — Hard: Event-driven (Kafka) offers loose coupling, high scalability, but complex debugging and ordering. Request-driven (REST/gRPC) is simpler but less scalable. Choose event-driven for high-throughput, decoupled systems; request-driven for low-latency, synchronous interactions.

AA13 — Easy: A load balancer distributes traffic. Layer 4 (e.g., LVS) balances at TCP/UDP; Layer 7 (e.g., Nginx) balances at HTTP. Use Layer 7 for content-based routing.

AA14 — Easy: A message queue (e.g., RabbitMQ) ensures ordered delivery; a log-based broker (e.g., Kafka) supports high throughput and persistence. Use queues for ordered tasks; Kafka for high-volume, persistent logs.

AA15 — Easy: A container (e.g., Docker) packages an app with dependencies; a VM virtualizes hardware. Containers are popular for microservices due to lightweight, fast startup, and portability.

AA16 — Easy: Stateless services (e.g., web servers) don't store session data; stateful services (e.g., databases) do. Stateless services are easier to scale horizontally as any instance can handle requests.

AA17 — Easy: An ORM (e.g., Hibernate, Entity Framework) maps objects to databases. Trade-offs: ORMs simplify development but may introduce performance overhead vs raw SQL.

AA18 — Medium: The Bulkhead pattern isolates resources (e.g., thread pools) to prevent cascading failures. Implement using separate thread pools or deployment groups for critical services.

AA19 — Hard: OT ensures consistency but has high latency; CRDTs offer eventual consistency with lower latency and better offline support. Choose CRDTs for offline editing due to their resilience and lower latency.

AA20 — Hard: Distributed tracing challenges include context propagation (W3C Trace Context), sampling strategies (head-based vs tail-based), trace storage (Jaeger, Tempo), and handling async messaging. Ensure trace continuity via message headers or Kafka headers.

OP1 — Easy: Type 1 (bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Xen); Type 2 (hosted) run on OS (e.g., VirtualBox, VMware Workstation).

OP2 — Easy: SAN provides block-level storage (e.g., iSCSI, Fibre Channel); NAS provides file-level storage (e.g., NFS, SMB). Use SAN for databases; NAS for file sharing.

OP3 — Medium: 3-tier architecture (core/distribution/access) is hierarchical; leaf-spine is flat. Leaf-spine solves scalability and latency issues in modern data centers.

OP4 — Medium: Design a Proxmox cluster with 3+ nodes, shared storage (Ceph), and fencing. During node failure, remaining nodes take over via quorum.

OP5 — Medium: VLAN trunking (802.1Q) allows multiple VLANs on a single NIC. Configure on Linux using VLAN interfaces (e.g., veth0.10).

OP6 — Medium: RAID 1 (mirroring), RAID 5 (striping + parity), RAID 6 (dual parity), RAID 10 (mirroring + striping), RAID Z2 (ZFS with double parity). For a database, RAID 10 offers best performance and fault tolerance.

OP7 — Hard: Design a DNS architecture with internal AD, DMZ services, split-horizon DNS, and DNSSEC. Use recursive resolvers, authoritative servers, forwarders, and conditional forwarding. Ensure seamless transitions for laptops.

OP8 — Hard: PKI chain: Root CA (offline), Subordinate CA, end-entity certificates. Deploy internal PKI with root CA offline, subordinate CAs, CRL/OCSP, and auto-enrollment. Compromised root CA is catastrophic; subordinate CA compromise is manageable.

OP9 — Hard: Compare MPLS, IPsec VPN, SD-WAN, and WireGuard. For latency-sensitive VoIP, SD-WAN offers cost-effective, reliable, and manageable solution.

OP10 — Medium: iDRAC/iLO/IPMI provide out-of-band management. Critical for remote server control. Exposing IPMI to the internet risks security breaches.

OP11 — Medium: LVM (logical volumes), LVM-Thin (thin provisioning), ZFS (copy-on-write). Use LVM for flexibility, LVM-Thin for space efficiency, ZFS for snapshots and data integrity.

OP12 — Hard: Design a stretch cluster with Ceph, CRUSH rules, monitor placement, and tiebreaker. 2-site Ceph without a tiebreaker risks split-brain.

OP13 — Easy: DHCP assigns IP addresses via DORA (Discover, Offer, Request, Acknowledge). If a DHCP server is unavailable, clients use APIPA addresses.

OP14 — Easy: Managed switches offer VLANs, QoS, and security; unmanaged switches are plug-and-play. Managed switches are essential for enterprise networks.

OP15 — Easy: NTP synchronizes clocks. Clock drift in clusters can cause authentication failures and data inconsistencies.

OP16 — Easy: Physical server runs directly on hardware; VM runs on hypervisor; container runs on OS. Use bare metal for performance-critical workloads.

OP17 — Easy: UPS provides short-term power; generator provides long-term power. Both are needed for data center resilience. ATS switches between power sources.

OP18 — Medium: Active-passive clustering (e.g., Pacemaker/Corosync) uses STONITH, virtual IPs, and failover for HA. Active-active requires load balancing and shared storage.

OP19 — Hard: Backup strategy: 3-2-1 rule, RPO/RTO, backup types, deduplication, offsite storage, immutable backups, and restore testing. Backup is data protection; disaster recovery is system restoration.

OP20 — Hard: 802.1X uses supplicant, authenticator, and RADIUS server. EAP methods (EAP-TLS, PEAP) authenticate devices. MAB allows non-802.1X devices to authenticate via MAC address.
