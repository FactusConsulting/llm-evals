AA1 — Easy: A monolith is a single, unified application, while microservices are a collection of small, independently deployable services. Microservices introduce: 1) Distributed system complexity (network latency, partial failures), 2) Increased operational overhead (monitoring, logging, deployment), 3) Data consistency challenges (distributed transactions).

AA2 — Easy: Synchronous communication (e.g., REST/gRPC) requires the caller to wait for a response. Asynchronous communication (e.g., message queues) allows the caller to continue without waiting. Example sync: REST API call. Example async: RabbitMQ message.

AA3 — Medium: An API Gateway handles routing, authentication, rate limiting, and request/response transformation for APIs. A reverse proxy routes traffic to backend servers. An API Gateway can replace a reverse proxy for API-specific needs but not for general load balancing or SSL termination.

AA4 — Medium: The Saga pattern manages distributed transactions by breaking them into local transactions. Choreography-based sagas use events to trigger actions in other services (loosely coupled). Orchestration-based sagas use a central coordinator (Saga orchestrator) to manage steps (tightly coupled). Choreography is better for decoupled systems; orchestration is better for complex, coordinated workflows.

AA5 — Medium: CQRS separates read and write operations into different models. It is often paired with Event Sourcing, which stores state changes as a sequence of events. This combination solves the problem of scaling reads and writes independently and provides a full audit trail, which a traditional CRUD model cannot.

AA6 — Medium: The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service after a threshold is reached. States: Closed (normal operation), Open (failing, calls are blocked), Half-Open (testing if service is back). It differs from retries by preventing repeated calls to a failing service. Use both together for resilience.

AA7 — Hard: 
1. Shared DB, shared schema: Low cost, high operational complexity, high noisy-neighbor risk.
2. Shared DB, separate schema: Moderate cost, moderate complexity, moderate risk.
3. Separate DB: High cost, low complexity, low risk.
Trade-offs: Cost vs isolation vs operational overhead.

AA8 — Hard: Eventual consistency allows temporary inconsistencies for scalability. For inventory, use strong consistency with a distributed database (e.g., CockroachDB) and patterns like Saga or two-phase commit to prevent overselling.

AA9 — Hard: A sidecar proxy (e.g., Envoy) runs alongside a service, handling cross-cutting concerns like mTLS, load balancing, and observability. In Istio, Envoy is the data plane (handling traffic) and Istio control plane (managing Envoy config). mTLS between sidecars provides end-to-end encryption and mutual authentication, which application-level TLS cannot.

AA10 — Medium: The Strangler Fig pattern gradually replaces a monolith by building new services around it. For .NET Framework to .NET 8 migration: 1) Identify a feature to migrate, 2) Build a new microservice, 3) Route traffic to the new service, 4) Gradually decommission the old code.

AA11 — Medium: The 12-Factor App methodology includes: 1) Codebase (single code repo), 2) Dependencies (explicit declarations), 3) Config (externalized), 4) Backing services (treat as attached resources), 5) Build, release, run (separate stages), 6) Processes (stateless, concurrent). These factors ensure apps are scalable, maintainable, and cloud-native.

AA12 — Hard: Event-driven (Kafka) vs request-driven (REST/gRPC): Event-driven has loose coupling, better scalability, complex debugging, eventual consistency, and requires handling failures. Request-driven has tight coupling, simpler debugging, strong consistency, and easier failure handling. Choose event-driven for high-throughput, decoupled systems; request-driven for low-latency, synchronous interactions.

AA13 — Easy: A load balancer distributes traffic across servers. Layer 4 (TCP/UDP) balances based on IP/port. Layer 7 (HTTP) balances based on content. Use Layer 7 for SSL termination or content-based routing.

AA14 — Easy: A message queue (RabbitMQ) is for point-to-point messaging. A log-based broker (Kafka) is for high-throughput, persistent logs. Use RabbitMQ for reliable messaging; Kafka for streaming and high-volume data.

AA15 — Easy: A container (e.g., Docker) is a lightweight, isolated environment. A VM (e.g., VirtualBox) is a full OS virtualization. Containers are popular for microservices due to their speed, resource efficiency, and portability.

AA16 — Easy: Stateless services (e.g., web servers) don't store session data; stateful services (e.g., databases) do. Stateless services are easier to scale horizontally because any instance can handle any request.

AA17 — Easy: An ORM (e.g., Hibernate, Entity Framework) maps objects to database tables. Trade-offs: ORMs simplify development but may introduce performance overhead and reduce control over SQL.

AA18 — Medium: The Bulkhead pattern isolates resources to prevent cascading failures. In microservices, implement bulkheads using separate thread pools or deployment groups. Example: Isolate database connections per service.

AA19 — Hard: OT and CRDTs for real-time collaboration: OT ensures consistency through transformations; CRDTs use commutative operations. OT has lower latency but higher complexity; CRDTs handle offline editing better. Choose CRDTs for offline support.

AA20 — Hard: Distributed tracing challenges: Context propagation (W3C Trace Context), sampling strategies (head-based vs tail-based), trace storage (Jaeger, Tempo), and asynchronous messaging. Ensure trace continuity with Kafka by propagating trace IDs in messages.

OP1 — Easy: Type 1 (bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Xen). Type 2 (hosted) run on an OS (e.g., VirtualBox, VMware Workstation).

OP2 — Easy: SAN (Storage Area Network) provides block-level storage over a network (e.g., iSCSI). NAS (Network Attached Storage) provides file-level storage (e.g., SMB/NFS). Use SAN for databases; NAS for file sharing.

OP3 — Medium: 3-tier (core/distribution/access) is hierarchical. Leaf-spine is non-blocking, low-latency, and preferred for modern data centers. It solves the problem of bottlenecks in 3-tier.

OP4 — Medium: Proxmox cluster: 3+ nodes, quorum (odd number), fencing (STONITH), shared storage (Ceph, iSCSI, NFS). During node failure, remaining nodes take over with shared storage.

OP5 — Medium: VLAN trunking allows multiple VLANs over a single link. 802.1Q tagging adds VLAN IDs to frames. Configure Linux with VLAN interfaces (e.g., veth0.10, veth0.20, veth0.30).

OP6 — Medium: RAID 1 (mirroring), RAID 5 (striping with parity), RAID 6 (dual parity), RAID 10 (mirroring + striping), RAID Z2 (ZFS, dual parity). For 6 drives, RAID 10 balances performance, capacity, and fault tolerance.

OP7 — Hard: Enterprise DNS: Internal AD, DMZ services, split-horizon DNS, DNSSEC. Recursive resolvers, authoritative servers, forwarders, conditional forwarding. When a laptop moves, it uses the appropriate DNS server.

OP8 — Hard: PKI chain: Root CA (offline), subordinate CA, end-entity certificates. Consequences: Compromised subordinate CA affects issued certs; compromised root CA affects all certs.

OP9 — Hard: WAN options: MPLS (reliable, expensive), IPsec VPN (cost-effective, variable latency), SD-WAN (flexible, complex), WireGuard (simple, secure). Recommend SD-WAN for 50 users per site with VoIP.

OP10 — Medium: iDRAC/iLO/IPMI are out-of-band management interfaces. Critical for remote server control. Exposing IPMI to the internet is a security risk.

OP11 — Medium: LVM (flexible volumes), LVM-Thin (efficient storage), ZFS (snapshotting, checksums). Use LVM for flexibility, LVM-Thin for efficiency, ZFS for snapshots.

OP12 — Hard: Stretch cluster: Ceph CRUSH rules, monitor placement, network latency, split-brain prevention. 2-site Ceph is risky without a tiebreaker.

OP13 — Easy: DHCP assigns IP addresses via DORA (Discover, Offer, Request, Ack). If a DHCP server is unavailable, a Windows client uses APIPA (169.254.x.x).

OP14 — Easy: Managed switches (configurable, QoS, VLANs) vs unmanaged switches (plug-and-play). Managed switches are essential for enterprise networks.

OP15 — Easy: NTP synchronizes clocks. Drift causes issues in clusters (e.g., Kerberos failures).

OP16 — Easy: Physical server (bare metal), VM (virtualized), container (lightweight). Run bare metal for performance-critical workloads.

OP17 — Easy: UPS (short-term power), generator (long-term power). Both needed for redundancy. ATS switches between power sources.

OP18 — Medium: Active-passive (one active, one standby) vs active-active (both active). Implement HA for PostgreSQL with Pacemaker/Corosync, fencing (STONITH), virtual IPs.

OP19 — Hard: Backup strategy: 3-2-1 rule, RPO/RTO, backup types, deduplication, offsite storage, immutable backups, restore testing. Backup is data protection; disaster recovery is business continuity.

OP20 — Hard: 802.1X uses supplicant, authenticator, authentication server (RADIUS). EAP methods (EAP-TLS, PEAP). MAB allows non-802.1X devices to authenticate via MAC address.
