## SC1 — Medium — Broken Deployments After Cluster Upgrade

Part A: The pods are failing because the combination of the new Restricted Pod Security Standard (PSS) and the container image's USER directive is causing a conflict. The Restricted PSS requires `runAsNonRoot: true` and `runAsUser` to be set to a non-zero value. The container image (cgr.dev/chainguard/static:latest) defaults to `USER root` (UID 0), but the pod spec does not explicitly set `runAsUser`. This results in the container running as root, which violates the Restricted PSS. Kubernetes enforces PSS at admission time, so the pod fails to start. The change from Baseline (which allows root) to Restricted (which enforces non-root) is the key factor.

Part B: One-liner to identify failing pods and their securityContext:
```bash
kubectl get pods --all-namespaces --field-selector=status.phase=Running --field-selector=status.phase=Pending --field-selector=status.phase=Failed --field-selector=status.phase=CrashLoopBackOff --field-selector=status.phase=ImagePullBackOff --field-selector=status.phase=ErrImagePull --field-selector=status.phase=Unknown --field-selector=status.phase=CrashLoopBackOff -o jsonpath='{range .items[?(@.status.containerStatuses[*].restartCount > 0)]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.spec.containers[*].securityContext}{"\n"}{end}'
```
Note: This command is complex and might need adjustment. A more robust approach would use `kubectl get pods -A -o json | jq '.items[] | select(.status.containerStatuses[].restartCount > 0) | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.containers[].securityContext}'`.

Part C: Remediation strategy:
1. **Image-Level Fix**: Rebuild the container images with a base image that defaults to a non-root user (e.g., cgr.dev/chainguard/static:latest with a non-root user) or explicitly set `USER` in the Dockerfile to a non-root UID.
2. **Kubernetes Manifest Changes**: Update the pod specifications to explicitly set `securityContext.runAsUser` to a non-zero value (e.g., 65532 for Chainguard images) and ensure `runAsNonRoot: true` is set. This should be done for all affected pods.
3. **CI Pipeline Gate**: Implement a CI pipeline gate that:
    * Scans container images for the `USER` directive and verifies it's non-root.
    * Validates that Kubernetes manifests explicitly set `runAsUser` and `runAsNonRoot` correctly.
    * Runs a local PSS validation tool (e.g., `kubectl apply --dry-run=server` or a custom script) against the manifests.
4. **Rollout Without Downtime**: Use a rolling update strategy with a small batch size and a short interval. Monitor the rollout closely. If issues arise, roll back to the previous version. Consider using a canary deployment for critical services.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

Part A: The stale data issue arises because promoting a cross-region read replica means you are now serving writes to a database that was previously only receiving asynchronous replication of writes from the primary. The replication lag (the time it takes for WAL records to be shipped from the primary to the replica and applied) means that any writes made to the old primary after the last successful WAL shipment are lost. PostgreSQL streaming replication is asynchronous by default for cross-region setups. Data loss scenarios include:
    * **Network Partition**: If the network between primary and replica is down, the replica cannot receive WALs, leading to data loss when it's promoted.
    * **Replication Lag**: The replica is always slightly behind the primary. Promoting it means accepting that data written in the last few seconds (or minutes, depending on lag) is lost.
To quantify data loss, check the replica's `pg_last_wal_receive_lsn` and `pg_last_wal_replay_lsn` against the primary's `pg_current_wal_lsn()`. The difference indicates the amount of WAL not yet applied.

Part B: Terraform operations:
1. **Import the promoted replica**: `terraform import aws_db_instance.my_db_replica <replica_arn>`
2. **Update the resource definition**: Change the `replica_source_db_instance_identifier` to `null` (or remove it) and set `engine_mode` to `provisioned` (if needed) and `promotion_tier` to `primary`.
3. **Update dependent resources**:
    * **Security Groups**: Update rules to allow traffic to the new primary's endpoint.
    * **Route53 Records**: Update the CNAME or Alias record to point to the new primary's endpoint.
    * **Parameter Groups**: Ensure the new primary uses the correct parameter group.
    * **Other resources**: Update any resources that reference the old instance's ARN or endpoint.
4. **Apply changes**: `terraform apply`. Terraform will update the state to reflect the new primary and modify dependent resources without destroying the instance.

Part C: Future-proof architecture:
1. **RDS Proxy vs PgBouncer**: Use RDS Proxy for connection management. It handles connection pooling, throttling, and failover more robustly than PgBouncer, especially in a multi-AZ or cross-region setup. RDS Proxy also integrates with IAM for authentication.
2. **Route53 Health Checks & DNS Failover**: Implement Route53 health checks on the RDS instances. Use DNS failover (e.g., latency-based routing or failover routing) to automatically redirect traffic to the healthy region.
3. **Application-Level Retry Logic**: Implement retries with exponential backoff in the application for database operations to handle transient errors during failover.
4. **RPO < 1 second**: Use Aurora Global Database. It provides low RPO (typically seconds) by replicating data to a secondary region with a lag of a few seconds. It also supports fast failover.
5. **Recommendation**: Yes, Aurora Global Database is highly recommended. It natively addresses the issues of replication lag, data loss, and failover speed, and integrates well with AWS services.

4. **Kill**: Once evidence is captured, kill the compromised pods and rebuild them with a known-good image.

            return None

            return manifest.get('layers', [])
        else:
            print(f"Error: Image {image_uri} not found for layers.")
            return []

        print(f"Error getting image layers for {image_uri}: {e}")
        return []

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

Part A: Top 5 technical blockers and solutions:
1. **Sticky Sessions (Local Memory)**:
    * Problem: Kubernetes pods are ephemeral and not sticky. Local memory in pods will not survive pod restarts or rescheduling.
    * Solution: Implement a distributed session store (e.g., Redis, Hazelcast) or use Kubernetes StatefulSets with persistent volumes for session data.
2. **Local NFS Mount (/data/uploads)**:
    * Problem: Local NFS mounts are tied to specific nodes and not portable.
    * Solution: Use a Kubernetes PersistentVolume (PV) backed by a network-attached storage (NAS) or a cloud storage solution (e.g., AWS EFS, Azure Files, GCP Filestore) that can be mounted by any pod.
3. **On-Prem Oracle 19c Database**:
    * Problem: The monolith is tightly coupled to the on-prem database. Migrating the database is a separate, complex task.
    * Solution: Containerize the Oracle database using a suitable image (e.g., Oracle's official image or a community image) and run it in Kubernetes. Alternatively, use a managed database service (e.g., Oracle Cloud Database, AWS RDS for Oracle) and update the application connection string.
4. **IBM MQ Integration**:
    * Problem: The monolith communicates with a mainframe via IBM MQ. Ensuring reliable messaging in a containerized environment requires careful configuration.
    * Solution: Use a containerized IBM MQ instance (e.g., IBM MQ Advanced for Developers) or a managed MQ service (e.g., IBM Cloud MQ, AWS MQ). Ensure the Kubernetes application has network access to the MQ instance.
5. **F5 BIG-IP Load Balancer**:
    * Problem: F5 is a physical load balancer. Replacing it with Kubernetes-native Ingress controllers (e.g., NGINX Ingress, Traefik) requires configuration changes and testing.
    * Solution: Implement an Ingress controller in Kubernetes. Configure it to handle SSL termination, routing, and health checks. Gradually shift traffic from F5 to the Ingress controller.

Part A: Systematic debugging approach:

    * Examine Envoy proxy metrics: `envoy_cluster_upstream_rq_pending_overflow`, `envoy_cluster_upstream_rq_pending_active`, `envoy_cluster_upstream_rq_retry`, `envoy_cluster_upstream_rq_timeout` for the inventory-service cluster. These can indicate proxy-level issues like queueing or timeouts.

2. **Kubernetes Metrics**:
    * Check CPU and memory utilization of inventory-service pods during the spike (already confirmed low).
    * Check network I/O and disk I/O for inventory-service pods.
    * Check the number of active connections to the inventory-service pods.
3. **Application-Level Metrics**:
    * Inventory-service: Monitor its own application metrics (e.g., request processing time, database query times, lock contention metrics if available).
    * Checkout-service: Monitor its own metrics for the call to inventory-service (e.g., time spent waiting for a response).
4. **Distributed Tracing (Jaeger/Zipkin)**:
    * Capture traces during the spike. Look for:
        * Increased latency in the span representing the call from checkout-service to inventory-service.
        * If the latency is in the network: The span duration will be high, and network-related metrics (e.g., TCP connect time, TLS handshake time) will be high.
        * If the latency is in the sidecar proxy: The span duration will be high, and Envoy proxy metrics (as listed above) will show issues.
        * If the latency is in the inventory-service application: The span duration will be high, and application-level metrics for inventory-service will show high processing times.
5. **Specific Envoy Metrics**:
    * `envoy_cluster_upstream_rq_pending_active`: Number of active requests pending in the proxy's queue. High values indicate the proxy is overwhelmed.
    * `envoy_cluster_upstream_rq_pending_overflow`: Number of requests that were dropped due to queue overflow. High values indicate severe proxy overload.
    * `envoy_cluster_upstream_rq_retry`: Number of requests that were retried. High values might indicate transient issues with the upstream service.
    * `envoy_cluster_upstream_rq_timeout`: Number of requests that timed out. High values indicate the upstream service is slow or unresponsive.

Part C: Architectural solution to eliminate this class of problem:
1. **CQRS (Command Query Responsibility Segregation)**:
    * Separate the read path (queries) from the write path (commands). The reconciliation job should only write to the database, not read from it in a way that blocks other operations.
2. **Read Replica for Reconciliation**:
    * Run the inventory reconciliation job against a dedicated read replica of the database. This isolates the read load from the primary database, preventing lock contention on the primary.
3. **Bulkhead Isolation for Database Connection Pool**:
    * Implement separate connection pools for the serving application (checkout-service) and the reconciliation job. This prevents the reconciliation job from exhausting the connection pool used by the serving application.
4. **Adjust CronJob Scheduling**:
    * Schedule the reconciliation job during off-peak hours to minimize impact on serving applications.
    * Consider breaking the reconciliation job into smaller, more frequent batches to reduce the duration of locks.
5. **Kubernetes PodDisruptionBudgets (PDBs) and Resource Quotas**:
    * **PDBs**: Define PDBs for the inventory-service pods to ensure a minimum number of replicas are always available during voluntary disruptions (e.g., node maintenance). This prevents the reconciliation job from being scheduled on the last available node if it's resource-intensive.
    * **Resource Quotas**: Set resource quotas for namespaces or specific pods to limit the CPU and memory consumption of the reconciliation job, preventing it from starving the serving pods.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

Part A: Identity and access layer design:
1. **Machine Identity**:
    * **SPIFFE/SPIRE**: Implement SPIFFE (Secure Production Identity Framework For Everyone) for workload identity. SPIRE (SPIFFE Runtime Environment) will issue and manage short-lived X.509 certificates for workloads.
    * **AWS IAM Roles**: For AWS workloads, use IAM Roles for Service Accounts (IRSA) to associate IAM roles with Kubernetes service accounts. SPIRE can integrate with IRSA to issue SPIFFE IDs that map to IAM roles.
    * **Azure Managed Identities**: For Azure workloads, use Azure Managed Identities. SPIRE can integrate with Azure to issue SPIFFE IDs that map to Managed Identities.
    * **On-Prem PKI**: For on-prem workloads, integrate SPIRE with the existing on-prem PKI. SPIRE can issue SPIFFE IDs that are signed by the on-prem CA.
2. **Federating Identity**:
    * Use a federated identity provider (IdP) like Keycloak, Dex, or an enterprise IdP (e.g., Okta, Azure AD) that can integrate with SPIRE.
    * Workloads in AWS can authenticate to the IdP using their IAM roles (via OIDC federation).
    * Workloads in Azure can authenticate using their Managed Identities (via OIDC federation).
    * On-prem workloads can authenticate using their on-prem PKI certificates.
    * The IdP will issue short-lived JWTs or SAML assertions that are then used by SPIRE to issue SPIFFE X.509 certificates. This allows a workload in AWS to authenticate to a service on-prem without shared secrets, as both use certificates issued by a trusted CA (the IdP's CA or a CA trusted by the IdP).

Part C: VPN upgrade comparison:
1. **Upgrade to AWS Direct Connect**:
    * **Cost**: Higher upfront and monthly costs for ports and cross-connects. More expensive than VPN.
    * **Bandwidth**: Higher bandwidth options (up to 100 Gbps) available. Better for high-throughput needs.
    * **Encryption**: AWS handles encryption over the public internet for Direct Connect. For private connections, MACsec can be used.
    * **Failover**: Can be configured with redundant ports and connections for high availability.
    * **Zero-Trust Fit**: Fits well as it provides a dedicated, high-bandwidth connection. However, it still relies on IPsec for the last mile to the on-prem network. It needs to be integrated with the overall zero-trust architecture (e.g., using Transit Gateway).
    * **Routing Changes**: Requires configuring BGP on the on-prem router and AWS side. Routes need to be propagated through the Transit Gateway.
2. **Adding a Second VPN Tunnel with ECMP**:
    * **Cost**: Lower cost compared to Direct Connect. Only requires additional VPN tunnels.
    * **Bandwidth**: Aggregates bandwidth of multiple tunnels. Can achieve higher throughput than a single VPN.
    * **Encryption**: Each tunnel is encrypted separately.
    * **Failover**: ECMP provides load balancing and failover between tunnels.
    * **Zero-Trust Fit**: Fits well as it's a standard AWS service. Can be used with Transit Gateway. Still relies on IPsec.
    * **Routing Changes**: Requires configuring BGP on the on-prem router and AWS side. ECMP needs to be configured on the on-prem router.
3. **Hybrid Mesh (Tailscale/Netbird)**:
    * **Cost**: Tailscale has a free tier and paid plans. Netbird is open-source. Generally lower cost than Direct Connect or multiple VPN tunnels.
    * **Bandwidth**: Depends on the underlying internet connection. May not be suitable for very high bandwidth needs.
    * **Encryption**: Provides end-to-end encryption for all traffic between nodes in the mesh.
    * **Failover**: Can be resilient if nodes have multiple internet connections.
    * **Zero-Trust Fit**: Excellent fit for zero-trust. Provides a secure overlay network that bypasses traditional network segmentation. Workloads can communicate securely regardless of their location (on-prem, AWS, Azure). Integrates well with SPIFFE/SPIRE for workload identity.
    * **Routing Changes**: Requires installing the mesh agent on all nodes. Routing is handled by the mesh overlay. No need for complex BGP configurations on the on-prem router for inter-site traffic.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

Part A: Explanation of drift sources and dangers:
1. **Manual tofu apply commands**:
    * How it occurred: Developers ran `tofu apply` directly on their laptops, bypassing the CI pipeline.
    * Danger: This leads to untracked changes in the infrastructure state. If the state file is not locked or versioned, concurrent changes can cause data loss, resource deletion, or inconsistent states. It also makes it impossible to know what the actual infrastructure looks like.
    * Data loss/outage: If two developers apply changes simultaneously without locking, Terraform might delete resources it thinks are no longer needed, or create conflicting resources. If the state file is not versioned, reverting to a previous state is impossible.
2. **Diverged Helm values files**:
    * How it occurred: Developers made changes to Helm values files in staging and production without committing them to the Git repository or through the CI pipeline.
    * Danger: This leads to a discrepancy between the declared configuration in Git and the actual deployed configuration. It makes deployments unpredictable and difficult to manage.
    * Data loss/outage: If a deployment uses a diverged values file, it might deploy incorrect configurations, leading to service disruptions, incorrect data handling, or security vulnerabilities.
3. **Direct kubectl edit on ConfigMaps**:
    * How it occurred: Developers used `kubectl edit` to modify ConfigMaps directly in the cluster, bypassing the CI/CD pipeline.
    * Danger: This leads to untracked changes in Kubernetes resources. It makes it impossible to know the source of truth for the configuration and can lead to inconsistencies between environments.
    * Data loss/outage: If a critical ConfigMap is edited incorrectly, it can cause services to malfunction or crash. If the change is not rolled back, it can lead to prolonged outages.
