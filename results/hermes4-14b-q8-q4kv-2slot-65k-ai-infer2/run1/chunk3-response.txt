## OpenTofu / Terraform (20 questions)

T1 — Easy: What is the difference between tofu plan and tofu apply?
- `tofu plan` generates an execution plan showing what resources will be created, modified, or destroyed.
- `tofu apply` executes the plan, making the actual changes to the infrastructure.

T2 — Easy: What is state in OpenTofu, and why is remote state important?
- State is a JSON file that tracks the current state of your infrastructure.
- Remote state (e.g., S3 + DynamoDB) is important for collaboration, locking, and backup.

T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?
- `count` creates multiple identical resources with numeric indices.
- `for_each` creates multiple resources with unique keys, allowing for more flexible naming and configuration.
- `for_each` is preferred when resources need unique identifiers or configurations.

T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
- OpenTofu detects the change during `plan` by comparing the current state with the provider's actual state.
- It will show a diff and propose to update the resource to match the provider's state.

T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-abc123"
  instance_type = "t2.micro"
  tags = {
    Name = each.value
  }
}
```

T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
- `terraform_remote_state` fetches state from a remote backend, while output values are defined in the root module.
- The recommended alternative is to use OpenTofu Workspaces or a dedicated state management tool like Terraform Cloud.
- This avoids tight coupling and improves modularity.

T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
- The `null_resource` runs after the module's resources are created, but the output is empty until the next apply.
- Fix: Use `depends_on` to ensure the `null_resource` runs after the cluster is ready, or use a local-exec provisioner to capture the output immediately.

T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
- `tofu import` adds an existing resource to the state file.
- Limitations: Only works for managed resources, may not capture all attributes, and can be error-prone.
- The `import` block in version 1.5+ allows importing resources during apply, with better error handling and validation.

T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
- A variable is a named value that can be passed to a module.
- Input variables are defined in the module and can be set by the caller.
- Output values are defined in a module and can be consumed by other modules or the root module.

T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
- A provider is a plugin that manages resources for a specific cloud or service.
- Running `tofu plan` without `tofu init` will fail because the providers are not initialized.

T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
- The `.terraform.lock.hcl` file locks the versions of providers and modules used in the project.
- Committing it ensures that all team members and CI/CD pipelines use the same versions, preventing unexpected changes.

T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
- `tofu destroy` removes all resources managed by OpenTofu.
- To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
- A data source is used to fetch existing data from a provider, such as an existing resource or a list of resources.
- Example: Using `aws_ami` data source to find the latest AMI ID instead of hardcoding it.

T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
- `variable` blocks define input variables that can be set by the caller.
- `locals` define local variables that are computed within the module and are not exposed to the caller.
- Use `locals` for intermediate values, derived values, or values that are not needed outside the module.

T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
- The `lifecycle` block configures resource behavior.
- `create_before_destroy`: Creates a new resource before destroying the old one, useful for zero-downtime updates.
- `prevent_destroy`: Prevents the resource from being destroyed, useful for critical resources.
- `ignore_changes`: Ignores changes to specific attributes, useful for attributes that are managed outside OpenTofu.

T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
- The `moved` block is used to rename or restructure resources without destroying and recreating them.
- It helps during refactoring by allowing you to change resource names or module structure without losing state.

T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
- OpenTofu builds a dependency graph based on resource references and explicit dependencies.
- Implicit dependencies are inferred from resource references, while explicit dependencies are defined using `depends_on`.
- `depends_on` can force a specific order, but it should be used sparingly as it can reduce parallelism and increase plan time.

T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
- Strategies:
  1. Use OpenTofu Workspaces to parallelize plan for different environments.
  2. Implement incremental plan with `tofu plan -target` to focus on specific resources.
  3. Use OpenTofu's `refresh` option to update state without re-planning.
  4. Optimize resource configurations and reduce unnecessary dependencies.
- Tradeoffs: Workspaces require additional setup, incremental plan may miss cross-resource dependencies, refresh can be slow, and optimization may require refactoring.

T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
- OpenTofu uses a state locking mechanism to prevent concurrent modifications.
- If a lock is not released, subsequent operations will fail until the lock is released.
- To manually break a lock, use `tofu force-unlock` with the lock ID.
- Risks: Breaking a lock can lead to state corruption and inconsistent infrastructure.

T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
- Steps:
  1. Configure the remote backend in `backend.tf`.
  2. Initialize the backend with `tofu init`.
  3. Migrate the state file to the remote backend using `tofu init -migrate-state`.
  4. Verify the migration by running `tofu plan` and checking the state file in the remote backend.
- The existing state file is uploaded to the remote backend, and subsequent operations will use the remote state.

## Ansible (20 questions)

A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?
- A playbook is a YAML file that defines a series of tasks to be executed.
- A role is a directory structure that organizes tasks, templates, and other files for a specific purpose.
- A task is a single action performed by Ansible, such as installing a package or copying a file.

A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?
- `ansible_facts` is a dictionary containing information about the target host, such as OS family, architecture, and network interfaces.
- Access the OS family using `{{ ansible_facts['os_family'] }}`.

A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
- `command` module runs a command on the target host without shell processing.
- `shell` module runs a command through the shell, allowing for shell features like pipes and redirection.
- `raw` module runs a command directly on the target host, bypassing Ansible's module system.
- Use `command` for simple commands, `shell` for complex commands, and `raw` for low-level operations.

A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
- Ansible ensures idempotency by running tasks only when necessary, based on the task's state.
- Idempotent task: `package` module with `state=present` (installs a package if not already installed).
- Non-idempotent task: `command` module with a command that always runs (e.g., `date`).

A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_facts['os_family'] == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
```

A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
- Variable precedence order (from lowest to highest):
  1. Role defaults
  2. Inventory group_vars
  3. Inventory host_vars
  4. Playbook group_vars
  5. Playbook host_vars
  6. Host facts
  7. Playbook vars
  8. Role vars
  9. Task vars
  10. Extra_vars
  11. Set_fact
- `group_vars` and `host_vars` are loaded from inventory, `extra_vars` are passed at runtime, `role defaults` are defined in roles, and `set_fact` sets variables during playbook execution.

A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
- Structure:
  1. Create an inventory group for the first 3 nodes.
  2. Use `serial: 3` in the playbook to limit the number of concurrent tasks.
  3. Use `wait_for` to ensure the first 3 nodes are ready before starting the rest.
- Example:
```yaml
- hosts: rke2_nodes
  serial: 3
  tasks:
    - name: Deploy RKE2 agent
      command: /path/to/rke2-agent
      when: inventory_hostname in groups['rke2_first_3']
      register: rke2_agent_result

    - name: Wait for first 3 nodes to be ready
      wait_for:
        host: "{{ item }}"
        port: 22
        timeout: 300
      loop: "{{ groups['rke2_first_3'] }}"
      when: inventory_hostname not in groups['rke2_first_3']
```

A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
- `ansible-vault` is a tool for encrypting sensitive data in Ansible playbooks and variables.
- To encrypt a single variable, use `ansible-vault encrypt_string` and include the encrypted value in the vars file.

A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
- An inventory file lists the hosts and groups that Ansible manages.
- A static inventory is a fixed list of hosts, while a dynamic inventory is generated on the fly using a script or plugin.

A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?
- Use the `ansible` command: `ansible webservers -m command -a 'df -h'`

A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
- A handler is a task that is only run when notified by another task.
- Handlers are defined in the `handlers` section of a playbook and are triggered using the `notify` keyword.

A12 — Easy: What is the ansible.cfg file used for? Name at 3 settings commonly configured there.
- The `ansible.cfg` file is used to configure Ansible settings.
- Common settings: `inventory`, `remote_user`, `ask_pass`, `forks`, `retry_files_enabled`.

A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
- The `register` keyword captures the output of a task into a variable.
- Use the registered variable in subsequent tasks using `{{ variable_name }}`.

A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
- `include_tasks` dynamically includes tasks at runtime, while `import_tasks` statically imports tasks at parse time.
- Use `include_tasks` for conditional task inclusion and `import_tasks` for static task inclusion.
- `include_tasks` allows for conditional evaluation based on runtime variables, while `import_tasks` evaluates conditions at parse time.

A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
- Ansible Galaxy is a repository for Ansible roles and collections.
- Use a `requirements.yml` file to specify roles and collections to install, then run `ansible-galaxy install -r requirements.yml`.

A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
- Connection plugins define how Ansible connects to target hosts.
- `ssh` is used for remote hosts over SSH.
- `local` is used for tasks that run on the control node.
- `network_cli` is used for network devices over a network protocol.
- Use `ssh` for most remote hosts, `local` for control node tasks, and `network_cli` for network devices.

A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
- `delegate_to` runs a task on a different host than the current play.
- `run_once` runs a task only once, even if it is part of a loop.
- Example:
```yaml
- name: Gather data from remote host
  command: some_command
  register: remote_data
  delegate_to: remote_host

- name: Process data on control node
  command: process_data {{ remote_data.stdout }}
  delegate_to: localhost
  run_once: true
```

A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
- Strategies:
  1. Increase `forks` to run more tasks in parallel.
  2. Enable `pipelining` to reduce SSH overhead.
  3. Use `fact_caching` to cache facts and reduce fact gathering time.
  4. Use `mitogen` or similar plugins to reduce memory usage and improve performance.
- Tradeoffs: Increasing `forks` can lead to resource contention, `pipelining` may not work with all SSH configurations, `fact_caching` requires additional setup, and `mitogen` may have compatibility issues.

A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
- Jinja2 templating allows for dynamic content generation using variables and control structures.
- `{{ }}` is used for variable interpolation.
- `{% %}` is used for control structures like loops and conditionals.
- `{# #}` is used for comments.
- Template snippet:
```jinja2
upstream my_upstream {
{% for server in backend_servers %}
  server {{ server.ip }}:{{ server.port }};
  # Health check: {{ server.health_check }}
{% endfor %}
}
```

A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
- Implementation:
  1. Use `serial` to limit the number of concurrent updates.
  2. Use pre/post tasks to register/deregister servers from the load balancer.
  3. Use `uri` module to perform health checks on updated servers.
  4. Use `block` and `rescue` to implement a rollback strategy on failure.
- Example:
```yaml
- name: Rolling deployment
  hosts: web_servers
  serial: 5
  tasks:
    - name: Deregister from load balancer
      command: deregister_server {{ inventory_hostname }}
      pre_tasks:
        - name: Register with load balancer
          command: register_server {{ inventory_hostname }}

    - name: Update application
      command: update_application

    - name: Health check
      uri:
        url: http://{{ inventory_hostname }}/health
        status_code: 200
      register: health_check
      until: health_check.status == 200
      retries: 5
      delay: 10

    - name: Register with load balancer
      command: register_server {{ inventory_hostname }}
      post_tasks:
        - name: Deregister from load balancer
          command: deregister_server {{ inventory_hostname }}

    - name: Rollback on failure
      block:
        - name: Revert application
          command: revert_application
      rescue:
        - name: Notify on failure
          command: notify_failure
```
