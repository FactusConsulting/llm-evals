K1 — Easy: What is the difference between a Deployment and a StatefulSet?
A Deployment manages stateless pods that can be replaced without preserving identity. A StatefulSet manages stateful pods with stable network identities, persistent storage, and ordered deployment/termination.

K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?
A ClusterIP Service creates a virtual IP (VIP) that is only reachable within the cluster. kube-proxy uses iptables/nftables rules to forward traffic from the VIP to the pods' IPs based on the Service's selector.

K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?
- PersistentVolume (PV): A piece of storage in the cluster, abstracted from the underlying infrastructure.
- PersistentVolumeClaim (PVC): A request for storage by a user, which binds to a PV.
- StorageClass: Defines storage "profiles" that PVs can be provisioned from (dynamic provisioning).
Relationship: PVCs request storage, which is fulfilled by PVs. StorageClasses define how PVs are dynamically provisioned when a PVC matches a StorageClass.

K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).
1. Check pod logs: `kubectl logs <pod-name>` to see error messages.
2. Inspect pod events: `kubectl describe pod <pod-name>` to see events leading to the crash.
3. Verify resource limits: Ensure CPU/memory requests/limits are appropriate for the workload.
4. Check application dependencies: Ensure required services, secrets, or ConfigMaps are available.
5. Review application code: Look for bugs or misconfigurations in the container image.

K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?
CoreDNS provides DNS resolution for services and pods within the cluster. If CoreDNS pods are down, DNS resolution will fail, causing pods to be unable to communicate with each other or external services via DNS names.

K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.
The scheduler selects a node through:
1. Filtering: Eliminates nodes that don't meet pod requirements (e.g., resource availability, taints).
2. Scoring: Ranks remaining nodes based on factors like:
   - Resource utilization (CPU/memory)
   - Node affinity/anti-affinity rules
   - Pod topology spread constraints
   - Node labels and taints
3. Binding: Assigns the pod to the highest-scoring node.

K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?
- The pod will not be scheduled because the node has only 500Mi available (4GB - 3.5GB), which is less than the pod's request of 256Mi.
- If the pod were scheduled and used 600Mi, it would exceed its memory limit, causing the kubelet to kill the pod and restart it.

K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.
1. External LB receives the request and forwards it to the NGINX ingress controller pods.
2. NGINX ingress controller routes the request to the appropriate Service based on Ingress rules.
3. The Service's Endpoints (managed by kube-proxy) direct traffic to the pod IPs.
4. kube-proxy uses iptables/nftables to forward traffic from the Service VIP to the selected pod.

K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?
A NetworkPolicy controls pod network traffic. By default, all ingress/egress is allowed. Applying a NetworkPolicy that selects pods restricts traffic to/from those pods based on rules.

K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?
- RollingUpdate: Updates pods gradually, maintaining availability.
- Recreate: Terminates all old pods before creating new ones.
Choose Recreate for stateless applications where downtime is acceptable, or when you need to ensure all pods are updated simultaneously.

K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?
A namespace is a virtual cluster for resource isolation. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.
`kubectl describe pod` provides detailed pod information, including:
1. Events (e.g., scheduling, restarts)
2. Container status (running, waiting, terminated)
3. Resource requests/limits
4. Init container status
5. Pod IP and node name

K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.
A ConfigMap stores non-confidential data. A pod can consume it via:
1. Environment variables
2. Volume mounts (as files)
3. Command-line arguments

K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?
- ClusterIP: Internal cluster-only service.
- NodePort: Exposes service on a static port on each node.
- LoadBalancer: Exposes service externally using cloud provider's load balancer.

K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?
A DaemonSet ensures a pod runs on every node (or subset). Use it for node-level tasks like monitoring, logging, or storage.

K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?
- Taints: Node attributes that repel pods unless they have matching tolerations.
- Node Affinity: Pod preference for nodes with certain attributes.
Use case for taints: Reserve nodes for critical workloads. Use case for affinity: Ensure pods run on nodes with specific hardware.

K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?
An Operator is a custom controller that extends Kubernetes with domain-specific logic. It differs from standard controllers by managing complex application lifecycles. Operators solve problems like automated application management, upgrades, and recovery.

K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?
etcd uses a Raft consensus algorithm for strong consistency. If quorum is lost, the cluster becomes read-only. To recover from 2/3 etcd nodes lost, you must restore from a backup and rejoin the remaining node.

K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.
RBAC uses Roles/ClusterRoles (permissions) and RoleBindings/ClusterRoleBindings (binding roles to subjects). For read-only access:
```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: <namespace>
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: <namespace>
subjects:
- kind: User
  name: <developer-username>
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.
The ndots setting in /etc/resolv.conf determines how many dots in a domain name trigger a search. A low ndots value causes excessive DNS queries for external domains. Fix by setting `ndots: 5` in the pod's dnsConfig:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "5"
```

- TCP: Reliable, connection-oriented (HTTP, FTP).

D3 — Medium: What is a race condition? Give a concrete example in any language.
A race condition occurs when multiple threads/processes access shared data concurrently, leading to unpredictable results. Example: Two threads incrementing a shared counter without synchronization.

D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?
- Symmetric: Uses same key for encryption/decryption (AES).
- Asymmetric: Uses public/private key pair (RSA).
TLS uses asymmetric encryption for key exchange and symmetric for data encryption.

D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?
A container image layer is a read-only filesystem layer. Layer caching speeds up builds by reusing unchanged layers. Best practices: Order instructions to maximize cache reuse, use multi-stage builds.

1. Check application logs for errors.

D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.
CAP theorem states a distributed system can only guarantee two of: Consistency, Availability, Partition tolerance. Example CP: ZooKeeper. Example AP: Cassandra.

D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?
A deadlock is a situation where processes are blocked waiting for each other. Coffman conditions:
1. Mutual exclusion
2. Hold and wait
3. No preemption
4. Circular wait

D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?
Eventual consistency means data will eventually be consistent across replicas. Cassandra uses tunable consistency levels (e.g., QUORUM, ALL) to balance consistency and availability.

D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?
mTLS authenticates both client and server using certificates. Handshake:
1. Client sends ClientHello.
2. Server responds with ServerHello and certificate.
3. Client verifies server certificate and sends its certificate.
4. Server verifies client certificate.
5. Establish secure session.
Commonly used in service meshes (Istio), API gateways, and internal microservices.

D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?
A hash table maps keys to values using a hash function. Collision resolution:
- Chaining: Store colliding entries in linked lists.
- Open addressing: Find alternative slots.
Time complexity:
- Average: O(1) for insertion, lookup, deletion.
- Worst: O(n) for chaining, O(1) for open addressing.

D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?
A circuit breaker prevents cascading failures by monitoring service health. States:
- Closed: Requests pass through.
- Open: Requests fail fast.
- Half-open: Test requests to check recovery.
Relates to retries by preventing excessive retries during outages.

D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).
- Optimistic: Assume no conflict, check at commit (e.g., row versioning).
- Pessimistic: Lock resources during transaction (e.g., SELECT FOR UPDATE).
Choose optimistic for low conflict scenarios (e.g., web applications). Choose pessimistic for high conflict scenarios (e.g., banking transactions).
