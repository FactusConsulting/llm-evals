## Cloud Infrastructure Architecture (20 questions)

CL1 — Easy: IaaS (Infrastructure as a Service) provides virtualized computing resources (e.g., AWS EC2). PaaS (Platform as a Service) provides a platform for developing and deploying applications (e.g., AWS Elastic Beanstalk). SaaS (Software as a Service) delivers software applications over the internet (e.g., Microsoft 365).

CL2 — Easy: The Shared Responsibility Model defines which security aspects are the cloud provider's responsibility and which are the customer's. For IaaS VMs, the provider secures the underlying infrastructure, while the customer secures the VM OS, data, and applications. For managed Kubernetes, the provider secures the control plane and underlying infrastructure, while the customer secures the cluster configuration, workloads, and data. For SaaS products like M365, the provider secures the entire stack, while the customer secures their data and access.

CL3 — Medium: A VPC (Virtual Private Cloud) is a logically isolated network. A subnet is a segment of the VPC's IP address range. A security group acts as a stateful firewall at the instance level. A NACL (Network ACL) is a stateless firewall at the subnet level. They layer together: VPC > Subnet > NACL > Security Group. Stateful filtering (security groups) tracks connection state, while stateless filtering (NACLs) does not.

CL4 — Medium: A multi-account strategy involves: 
- Landing zone: Initial setup with core services and policies
- Organizational units: Grouping accounts by function (e.g., dev, prod)
- Guardrails: Policies to enforce security/compliance
- Shared networking: Transit Gateway (AWS) or Azure Hub-and-Spoke for inter-account connectivity
- Centralized logging: CloudTrail (AWS) or Azure Monitor for audit trails
A single-account approach is problematic due to blast radius, lack of isolation, and difficulty managing permissions.

CL5 — Medium: Infrastructure as Code (IaC) automates infrastructure provisioning. 
- Terraform/OpenTofu: Declarative, multi-cloud, HCL language
- Pulumi: Declarative, multi-cloud, uses general-purpose languages
- CloudFormation/Bicep: AWS-specific, JSON/TS-based
- Crossplane: Kubernetes-native, multi-cloud
Choose based on cloud ecosystem, team skills, and portability needs.

CL6 — Medium: Cloud-native autoscaling patterns:
- HPA: Scales pods based on metrics (CPU/memory)
- VPA: Recommends/automates vertical pod scaling
- Cluster autoscaler: Scales node pools based on pod demand
- KEDA: Scales based on external event sources (e.g., Kafka, RabbitMQ)
Use KEDA for event-driven scaling beyond traditional metrics.

CL7 — Hard: Disaster recovery strategy:
- RPO/RTO: Define recovery point/objective and recovery time/objective
- Active-active: Both regions serve traffic simultaneously
- Active-passive: One region active, other standby
- Database replication: Sync (strong consistency) vs async (eventual consistency)
- DNS failover: Route53 (AWS) or Traffic Manager (Azure) for traffic rerouting
- State management: Replicate state across regions
- Cost implications: Active-active is more expensive
- DR modes: Pilot light (minimal resources), warm standby (scaled-down), multi-site active-active

CL8 — Hard: GitOps model:
- ArgoCD/FluxCD: Tools for GitOps implementation
- Secrets management: Sealed secrets, external secrets operator, Vault integration
- Manual changes: Drift detection and reconciliation
GitOps uses Git as the single source of truth for infrastructure and application configuration.

CL9 — Hard: Kubernetes architecture for stateful app:
- StatefulSet: Manages stateful applications
- PV/PVC: Persistent volumes with local storage class
- Headless service: Enables DNS-based service discovery
- Init containers: For setup tasks
- ConfigMaps: As volume mounts for config files
- Pod disruption budgets: Ensures availability during maintenance

CL10 — Medium: 
- Service account: Kubernetes identity for pods
- Workload identity: Azure AD identity for pods
- IRSA: AWS IAM roles for service accounts
Mounting cloud provider credentials in pods is bad practice due to security risks. Workload identity federation provides secure, managed identity.

CL11 — Medium: 
- Object storage (S3/Blob): Unstructured data, high durability
- Block storage (EBS/Managed Disk): Low-latency, high IOPS
- File storage (EFS/Azure Files): Shared filesystems
Use based on data type, access patterns, and performance needs.

CL12 — Hard: Zero-trust network architecture:
- Network policies: Pod-to-pod communication control
- Service mesh: mTLS for encrypted service-to-service communication
- Pod identity: Assign identities to pods
- Admission controllers: OPA/Kyverno for policy enforcement
- Image signing: Verify container image integrity
- Runtime security: Falco for anomaly detection
- Secrets management: Secure secret storage and rotation
Differs from perimeter-based security by assuming no implicit trust.

CL13 — Easy: CDN (Content Delivery Network) caches content at edge locations. Cloud-native CDNs: AWS CloudFront, Azure CDN. Use CDN for static content, global distribution, and reduced latency. Serve directly from origin for dynamic content or small sites.

CL14 — Easy: 
- Availability zones: Independent data centers within a region
- Regions: Geographically distinct areas
Deploy across AZs for high availability. Zonal resources are single-AZ, regional resources span multiple AZs.

CL15 — Easy: Managed database services (RDS, Cloud SQL, Azure SQL) handle: 
- Patching, backups, replication, scaling
- High availability, monitoring, security
Compared to self-managed VM databases, they reduce operational overhead.

CL16 — Easy: 
- IAM users: Individual identities
- Groups: Collections of users
- Roles: Temporary permissions
- Policies: Define permissions
Principle of least privilege: Grant only necessary permissions.

CL17 — Easy: Serverless computing (Lambda, Functions, Cloud Functions) runs code without managing servers. 
- Cold starts: Initial invocation latency
- Poor fit: Long-running processes, high resource needs
Compare based on execution model, pricing, and ecosystem.

CL18 — Medium: Kubernetes ingress options:
- Ingress resource: Standard Kubernetes API
- Gateway API: Next-gen, more flexible
- Cloud load balancer annotations: Provider-specific
- Service mesh ingress: Advanced routing
TLS termination varies by layer. Gateway API offers more features than traditional Ingress.

CL19 — Hard: Cost optimization strategy:
- Reserved instances vs savings plans: Commitment discounts
- Spot/preemptible instances: Cost-effective for fault-tolerant workloads
- Right-sizing: Match resources to needs
- Storage tiering: S3 Intelligent-Tiering, Archive
- Idle resource detection: Identify unused resources
- FinOps: Financial operations for cloud cost management
- Showback/chargeback: Allocate costs to teams
Implement tools (CloudHealth, Cloudability) and processes for cost visibility.

CL20 — Hard: Multi-cloud strategy:
- Abstraction layers: Kubernetes, Terraform
- Networking: VPN/interconnect between clouds
- Identity federation: SSO across clouds
- Trade-offs: Complexity vs vendor lock-in avoidance
Multi-cloud is justified for critical workloads, disaster recovery, or avoiding vendor lock-in.

## OT Infrastructure Architecture (20 questions)

OT1 — Easy: Purdue Model (ISA-95) defines enterprise architecture levels:
- Level 0: Physical process equipment
- Level 1: Basic control (PLCs, RTUs)
- Level 2: Supervisory control (SCADA, HMIs)
- Level 3: Manufacturing execution (MES)
- Level 4: Enterprise planning (ERP)
- Level 5: Corporate management

OT2 — Easy: 
- IT networks: Data-centric, high-speed, frequent changes
- OT networks: Process-centric, real-time, stability-critical
Standard IT patching can disrupt OT operations.

OT3 — Medium: Industrial DMZ (IDMZ) isolates IT and OT networks. 
- Traffic allowed: Engineering workstations to SCADA servers (Level 2 to Level 3)
- Direction: Primarily from IT to OT (read-only)
Direct connectivity from Level 4 to Level 1 is dangerous due to risk of disruption.

OT4 — Medium: 
1. Modbus TCP: Level 1 (PLCs) to Level 2 (SCADA)
2. OPC UA: Level 2 (SCADA) to Level 3 (MES)
3. EtherNet/IP (CIP): Level 1 (PLCs) to Level 2 (SCADA)
4. PROFINET: Level 1 (PLCs) to Level 2 (SCADA)
5. MQTT: Level 2 (SCADA) to Level 3 (MES) or cloud

OT5 — Medium: 
- Data diode: One-way communication, no active connections
- Firewall: Two-way filtering, stateful inspection
Use data diodes for critical one-way data flows (e.g., OT to IT). Limitation: No bidirectional communication.

OT6 — Medium: Data flow design:
- Historian: Level 2 (SCADA) collects process data
- OPC UA server: Exposes data to edge gateway
- MQTT broker: Transmits data to cloud ingestion
- Edge gateway: Secures data transfer to cloud
Security boundaries: Historian, OPC UA server, MQTT broker, edge gateway

OT7 — Hard: IEC 62443 security zones and conduits:
- Zone: Group of assets with similar security requirements
- Conduit: Secure communication path between zones
Design for manufacturing plant:
- Zone 1: PLCs and SIS
- Zone 2: HMIs and SCADA servers
- Zone 3: Engineering workstations
- Zone 4: Corporate network
Conduits: Secure connections between zones

OT8 — Hard: Network segmentation strategy:
- VLAN design: Isolate production, engineering, corporate
- Firewall placement: Between VLANs, at network edges
- Switch architecture: Layer 3 switches for segmentation
- Remote access: Jump hosts, MFA, time-limited access
- Transition: Phased approach, minimal downtime

OT9 — Hard: 
- SIS: Safety-critical systems (IEC 61511)
- BPCS: Basic process control
SIS must be isolated from BPCS and IT networks. Ransomware reaching SIS could cause physical damage.

OT10 — Medium: 
- PLC: Local control (Level 1)
- DCS: Distributed control (Level 1-2)
- SCADA: Supervisory control (Level 2)
They can coexist in the same plant.

OT11 — Medium: Remote access architecture:
- Jump hosts: Single point of access
- MFA: Multi-factor authentication
- Session recording: Audit access
- Vendor access: Time-limited, privileged
- RDP directly to HMI: Unacceptable due to security risks

OT12 — Hard: Detection and response plan:
- Network monitoring: IDS, anomaly detection
- Asset inventory: Comprehensive OT asset list
- Incident response: Isolate threat, coordinate with control room
- Plant operator role: Maintain safe operations during incident

OT13 — Easy: 
- HMI: Human-Machine Interface for monitoring/control
- Engineering workstation: For configuration, programming
HMIs are for operators, engineering workstations for engineers.

OT14 — Easy: 
- Historian: Stores process data
- Plant historian (Level 3): Real-time data
- Enterprise historian (Level 4): Aggregated data
Historians are crucial for process optimization and troubleshooting.

OT15 — Easy: 
- Ladder logic: Programming language for PLCs
- Dominant due to simplicity, familiarity
Executed by PLCs in industrial automation.

OT16 — Easy: 
- RTU: Remote Terminal Unit for remote monitoring/control
- PLC: Programmable Logic Controller for local control
RTUs used in remote locations (e.g., pipelines, substations).

OT17 — Easy: 
- Analog signals: Continuous (4-20mA, 0-10V)
- Digital signals: Discrete (on/off)
4-20mA preferred for process instrumentation due to noise immunity.

OT18 — Medium: 
- OT asset inventory: Foundation of OT security
- Discovery tools: Passive network monitoring, active scanning
- Active scanning dangerous due to potential disruption

OT19 — Hard: MITRE ATT&CK for ICS:
- Tactics: Reconnaissance, resource development, initial access, etc.
- Techniques: Spearphishing, remote services, etc.
Differs from enterprise ATT&CK by focusing on ICS-specific threats.

OT20 — Hard: Converged IT/OT SOC:
- Log collection: OT-specific collectors, minimal impact
- SIEM integration: Correlate IT/OT logs
- OT-specific detection rules: ICS-specific threats
- Staffing: Mix of IT analysts and OT engineers
- False positives: Contextual analysis, OT expertise
- Unauthorized firmware changes: Immediate isolation, forensic analysis
