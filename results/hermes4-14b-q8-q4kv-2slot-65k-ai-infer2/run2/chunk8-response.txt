## Cloud Infrastructure Architecture

CL1 — Easy: IaaS (Infrastructure as a Service) provides virtualized computing resources (e.g., AWS EC2). PaaS (Platform as a Service) provides a platform for developing and deploying applications (e.g., AWS Elastic Beanstalk). SaaS (Software as a Service) delivers software applications over the internet (e.g., Microsoft 365).

CL2 — Easy: The Shared Responsibility Model defines which security aspects are the cloud provider's responsibility and which are the customer's. For IaaS VMs, the provider secures the underlying hardware and hypervisor, while the customer secures the VM OS, applications, and data. For managed Kubernetes, the provider secures the control plane and underlying infrastructure, while the customer secures the cluster configuration, workloads, and data. For SaaS products like M365, the provider secures the entire stack, and the customer secures their data and access.

CL3 — Medium: A VPC (Virtual Private Cloud) is a logically isolated network in the cloud. A subnet is a segment of the VPC's IP address space. A security group acts as a stateful firewall at the instance level. A NACL (Network ACL) is a stateless firewall at the subnet level. They layer together: VPC > Subnet > NACL > Security Group. Stateful filtering (security groups) tracks connection state, while stateless filtering (NACLs) does not.

CL4 — Medium: A multi-account AWS/Azure strategy involves: 
- Landing zone: Initial setup with core services and governance.
- Organizational units: Grouping accounts for management.
- Guardrails: Policies to enforce security and compliance.
- Shared networking: Transit Gateway (AWS) or Azure Hub-and-Spoke for cross-account connectivity.
- Centralized logging: CloudWatch (AWS) or Azure Monitor for unified logging.
A single-account approach is problematic due to lack of isolation, governance, and risk concentration.

CL5 — Medium: Infrastructure as Code (IaC) automates infrastructure provisioning. 
- Terraform/OpenTofu: Declarative, multi-cloud, HCL language.
- Pulumi: Declarative, multi-cloud, uses general-purpose languages.
- CloudFormation/Bicep: AWS-specific, declarative.
- Crossplane: Kubernetes-native, multi-cloud.
Choose based on multi-cloud needs, language preference, and Kubernetes integration.

CL6 — Medium: Cloud-native autoscaling patterns:
- HPA: Scales pods based on metrics (CPU/memory).
- VPA: Recommends/automates vertical pod scaling.
- Cluster autoscaler: Scales node count in a cluster.
- KEDA: Scales based on external metrics (e.g., queue length).
Use KEDA over HPA when scaling based on external events or custom metrics.

CL7 — Hard: Disaster recovery strategy for cloud-native apps:
- RPO/RTO: Define recovery point/objective and recovery time objective.
- Active-active vs active-passive: Active-active for low RTO, active-passive for cost savings.
- Database replication: Sync for low RPO, async for performance.
- DNS failover: Route53 (AWS) or Traffic Manager (Azure) for traffic rerouting.
- State management: Use distributed state stores (e.g., etcd, Consul).
- Cost implications: Active-active is more expensive.
DR patterns: Pilot light (minimal resources), warm standby (scaled resources), multi-site active-active.

CL8 — Hard: GitOps model for infrastructure and app delivery:
- ArgoCD/FluxCD: Tools for GitOps, with ArgoCD being more feature-rich.
- Secrets handling: Sealed secrets, external secrets operator, Vault integration.
- Manual changes: Drift detection and reconciliation to Git state.

CL9 — Hard: Migrating stateful legacy app to Kubernetes:
- StatefulSet: For ordered, stable pod identities.
- PV/PVC with local storage class: For low-latency local storage.
- Headless service: For direct pod-to-pod communication.
- Init containers: For setup tasks before main container.
- ConfigMaps as volume mounts: For config files.
- Pod disruption budgets: For graceful maintenance.

CL10 — Medium: Service account vs workload identity vs IRSA:
- Service account: Kubernetes-native identity.
- Workload identity: Azure-specific identity for pods.
- IRSA: AWS-specific IAM roles for service accounts.
Mounting cloud credentials in pods is bad practice due to security risks. Workload identity federation solves this by using cloud-native identity mechanisms.

CL11 — Medium: Cloud storage types:
- Object storage (S3/Blob): For unstructured data, high durability.
- Block storage (EBS/Managed Disk): For VMs, low latency.
- File storage (EFS/Azure Files): For shared file access.
Durability/availability: Object > Block > File.

CL12 — Hard: Zero-trust network architecture for Kubernetes:
- Network policies: For pod-to-pod communication.
- Service mesh with mTLS: For encrypted service-to-service traffic.
- Pod identity: For fine-grained access control.
- Admission controllers (OPA/Kyverno): For policy enforcement.
- Image signing: For trusted images.
- Runtime security (Falco): For anomaly detection.
- Secrets management: For secure secret handling.
Differs from perimeter-based security by assuming no implicit trust.

CL13 — Easy: CDN (Content Delivery Network) caches content at edge locations. Cloud-native CDNs: AWS CloudFront, Azure CDN. Use CDN for static content, origin server for dynamic content.

CL14 — Easy: Availability zones (AZs) are isolated data centers within a region. Regions are geographic areas. Deploy across AZs for high availability. Zonal resources are in one AZ, regional resources span multiple AZs.

CL15 — Easy: Managed database services (RDS, Cloud SQL, Azure SQL) handle backups, patching, scaling. Running on VMs requires manual management.

CL16 — Easy: Cloud identity services: IAM users (human), groups (user collections), roles (temporary permissions), policies (permission definitions). Principle of least privilege: Grant only necessary permissions.

CL17 — Easy: Serverless computing (Lambda, Functions, Cloud Functions) runs code without server management. Cold starts: Initial latency. Poor fit for long-running tasks.

CL18 — Medium: Kubernetes ingress options:
- Ingress resource: Standard Kubernetes ingress.
- Gateway API: Next-gen ingress specification.
- Cloud load balancer annotations: Provider-specific LBs.
- Service mesh ingress gateways: For mesh-managed traffic.
TLS termination varies by layer. Gateway API offers more flexibility.

CL19 — Hard: Cost optimization strategy:
- Reserved instances vs savings plans vs spot/preemptible instances.
- Right-sizing: Matching resources to workload needs.
- Storage tiering: S3 Intelligent-Tiering, Archive.
- Idle resource detection: Identifying unused resources.
- FinOps practices: Cost management processes.
- Showback/chargeback models: Cost allocation.
Tools: Cloud provider cost management tools, third-party solutions.

CL20 — Hard: Multi-cloud strategy:
- Abstraction layers: For portability.
- Kubernetes as common runtime.
- Terraform for IaC portability.
- Networking between clouds: VPN/interconnect.
- Identity federation: For cross-cloud access.
Trade-offs: Complexity vs benefits. Justified for critical workloads, unnecessary for others.

## OT Infrastructure Architecture

OT1 — Easy: Purdue Model (ISA-95) has 5 levels:
- Level 0: Field devices (sensors, actuators).
- Level 1: Basic control (PLCs, RTUs).
- Level 2: Supervisory control (SCADA, HMIs).
- Level 3: Manufacturing execution (MES).
- Level 4: Enterprise (ERP, MES).

OT2 — Easy: IT networks handle data, OT networks handle control. Standard IT patching can disrupt OT operations.

OT3 — Medium: Industrial DMZ (IDMZ) isolates IT and OT networks. Traffic allowed: IT to OT (read-only), OT to IT (limited). Direct connectivity from Level 4 to Level 1 is dangerous due to risk of disruption.

OT4 — Medium: OT protocols and Purdue Model levels:
1. Modbus TCP: Level 1.
2. OPC UA: Level 2.
3. EtherNet/IP (CIP): Level 1.
4. PROFINET: Level 1.
5. MQTT: Level 3.

OT5 — Medium: Data diode allows one-way data transfer, firewall allows bidirectional. Use data diode for critical one-way data. Limitation: No bidirectional communication.

OT6 — Medium: Data flow for SCADA to cloud analytics:
- Historian (Level 3) collects data.
- OPC UA server (Level 2) interfaces with historian.
- MQTT broker (Level 3) receives data.
- Edge gateway (Level 3) processes and forwards data.
- Cloud ingestion (Level 4) receives data.
Security boundaries: Historian, OPC UA server, MQTT broker, edge gateway.

OT7 — Hard: IEC 62443 security zones and conduits:
- Zone: Group of assets with similar security requirements.
- Conduit: Secure communication path between zones.
Design: Corporate network (Zone 4), engineering workstations (Zone 3), SCADA servers (Zone 2), PLCs (Zone 1), SIS (Zone 0).

OT8 — Hard: Network segmentation strategy:
- VLAN design: Segregate by function.
- Firewall placement: Between zones.
- Switch architecture: Layer 3 switches.
- Remote access: Jump hosts, MFA.
- Transition: Phased approach, no production stoppage.

OT9 — Hard: SIS vs BPCS:
- SIS: Safety-critical, independent of BPCS.
- BPCS: Process control.
- IEC 61511: SIS standard.
- SIS network must be isolated to prevent disruption.
- Ransomware reaching SIS can cause safety incidents.

OT10 — Medium: PLC, DCS, SCADA:
- PLC: Local control.
- DCS: Distributed control.
- SCADA: Supervisory control.
- Can coexist in same plant.

OT11 — Medium: Remote access to OT:
- Jump hosts: For access.
- MFA: Mandatory.
- Session recording: For auditing.
- Vendor access: Time-limited, monitored.
- RDP to HMI from corporate network is unacceptable due to risk.

OT12 — Hard: OT security architect response:
- Network monitoring: IDS/anomaly detection.
- Asset inventory: Comprehensive.
- Incident response: Isolate threat, coordinate with control room.
- Plant operator role: Ensure safe operations during incident.

OT13 — Easy: HMI (Human-Machine Interface) displays process data and allows control. Differs from engineering workstation by being used for real-time monitoring.

OT14 — Easy: Historian stores process data. Plant historian (Level 3) stores real-time data, enterprise historian (Level 4) stores aggregated data.

OT15 — Easy: Ladder logic is a programming language for PLCs. Dominant due to simplicity and familiarity.

OT16 — Easy: RTU (Remote Terminal Unit) is a PLC variant for remote locations. Deployed where PLCs are impractical.

OT17 — Easy: Analog signals (4-20mA, 0-10V) vs digital signals. 4-20mA preferred for process instrumentation due to noise immunity.

OT18 — Medium: OT asset inventory is the foundation of OT security. Tools: Passive network monitoring, active scanning. Active scanning dangerous in OT networks.

OT19 — Hard: MITRE ATT&CK for ICS framework:
- Tactics: Reconnaissance, Resource Development, Initial Access, etc.
- Techniques: Spearphishing, Exploitation, Lateral Movement.
- Differs from enterprise ATT&CK by focusing on ICS-specific threats.
- Used to assess defensive gaps.

OT20 — Hard: Converged IT/OT SOC design:
- Log collection: From OT assets without impacting operations.
- SIEM integration: For correlation.
- OT-specific detection rules: For ICS threats.
- Alert triage: IT analysts vs OT engineers.
- False positives: Challenge in OT environments.
- Unauthorized firmware changes: Investigate, isolate, remediate.
