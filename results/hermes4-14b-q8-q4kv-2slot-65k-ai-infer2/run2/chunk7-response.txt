AA1 — Easy: A monolith is a single, unified application, while microservices are a collection of small, independently deployable services. Microservices introduce: 1) Distributed system complexity (network latency, partial failures), 2) Increased operational overhead (monitoring, logging, deployment), 3) Data consistency challenges (distributed transactions).

AA2 — Easy: Synchronous communication requires immediate response (e.g., REST/gRPC), while asynchronous communication decouples sender and receiver (e.g., Kafka/RabbitMQ). Example sync: REST API call. Example async: Kafka event publishing.

AA3 — Medium: An API Gateway handles routing, authentication, rate limiting, and request/response transformation for APIs, while a reverse proxy primarily routes traffic and offloads SSL termination. An API Gateway can replace a reverse proxy for API-specific needs but not for general web traffic routing.

AA4 — Medium: The Saga pattern manages distributed transactions by breaking them into local transactions with compensating actions. Choreography-based sagas use events to trigger actions across services, while orchestration-based sagas use a central coordinator. Choreography is better for decoupled services; orchestration is better for complex, coordinated workflows.

AA5 — Medium: CQRS separates read and write operations into different models. It is often paired with Event Sourcing, which stores state changes as a sequence of events. This combination solves the problem of complex read/write consistency and scalability in traditional CRUD models by decoupling data access and enabling event-driven updates.

AA6 — Medium: The Circuit Breaker pattern prevents cascading failures by temporarily stopping calls to a failing service. It has three states: Closed (normal operation), Open (fail fast), and Half-Open (testing recovery). It differs from retries by preventing repeated calls to a failing service. Use both together for resilience: retries for transient issues and circuit breakers for persistent failures.

AA7 — Hard: 
1. Shared DB/Schema: Low cost, high operational complexity, high noisy-neighbor risk.
2. Shared DB/Schema per Tenant: Moderate cost, moderate complexity, moderate noisy-neighbor risk.
3. Separate DB per Tenant: High cost, low complexity, low noisy-neighbor risk.

AA8 — Hard: Use strong consistency (e.g., with a distributed database like CockroachDB) to prevent overselling. Implement a reservation system with atomic operations and real-time inventory checks.

AA9 — Hard: A sidecar proxy (e.g., Envoy) is a dedicated proxy deployed alongside an application. In Istio, Envoy handles traffic management, security, and observability. The data plane (Envoy instances) handles traffic, while the control plane (Istio components) configures them. mTLS between sidecars provides end-to-end encryption and mutual authentication, solving trust issues that application-level TLS doesn't.

AA10 — Medium: The Strangler Fig pattern incrementally replaces parts of a legacy system. Start by building new microservices around the monolith, routing traffic to them, and gradually replacing functionality. For .NET Framework to .NET 8, create new services, use API gateways, and migrate data incrementally.

AA11 — Medium: The 12-Factor App methodology includes: 
1. Codebase (single code repo), 
2. Dependencies (explicit declarations), 
3. Config (externalized), 
4. Backing services (treat as attached resources), 
5. Build, release, run (separate stages), 
6. Processes (stateless, concurrent), 
7. Port binding (expose services via ports), 
8. Concurrency (scale via processes), 
9. Disposability (fast startup/shutdown), 
10. Dev/prod parity (same environment), 
11. Logs (stream to stdout), 
12. Admin processes (run as one-off). These factors ensure cloud-native deployments are scalable, maintainable, and portable.

AA12 — Hard: 
- Event-driven (Kafka): Loose coupling, high scalability, complex debugging, eventual consistency, robust failure handling.
- Request-driven (REST/gRPC): Tight coupling, moderate scalability, simpler debugging, strong consistency, simpler failure handling.
Choose event-driven for decoupled, scalable systems; request-driven for real-time, low-latency interactions.

AA13 — Easy: A load balancer distributes traffic across servers. Layer 4 (TCP/UDP) balances based on network layer info, while Layer 7 (HTTP) balances based on application layer info. Use Layer 7 for content-based routing.

AA14 — Easy: A message queue (RabbitMQ) is a broker for point-to-point messaging, while a log-based broker (Kafka) is optimized for high-throughput, persistent logs. Use RabbitMQ for reliable messaging; use Kafka for streaming and event sourcing.

AA15 — Easy: A container (e.g., Docker) is a lightweight, isolated environment for applications, while a VM (e.g., VirtualBox) virtualizes hardware. Containers are popular for microservices due to their speed, portability, and resource efficiency.

AA16 — Easy: Stateless services (e.g., web servers) don't store session data, making them easy to scale. Stateful services (e.g., databases) store data, requiring careful management. Stateless services are easier to scale horizontally.

AA17 — Easy: An ORM (e.g., Hibernate, Entity Framework) maps objects to database tables. Trade-offs: ORMs simplify development but may introduce performance overhead; raw SQL offers control but requires more boilerplate.

AA18 — Medium: The Bulkhead pattern isolates resources to prevent cascading failures. In microservices, implement bulkheads using separate thread pools or deployment groups. Example: Isolate database connections per service.

AA19 — Hard: 
- OT: Strong consistency, high latency, complex implementation, no offline support.
- CRDTs: Eventual consistency, low latency, simpler implementation, supports offline editing.
Choose CRDTs for offline editing due to their eventual consistency and offline support.

AA20 — Hard: Distributed tracing challenges include context propagation (W3C Trace Context), sampling strategies (head-based vs tail-based), trace storage (Jaeger, Tempo), and handling asynchronous messaging. Ensure trace continuity with Kafka by propagating trace headers in messages.

OP1 — Easy: Type 1 (bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Proxmox). Type 2 (hosted) run on an OS (e.g., VirtualBox, VMware Workstation).

OP2 — Easy: SAN (Storage Area Network) provides block-level storage over a network (e.g., iSCSI, Fibre Channel). NAS (Network Attached Storage) provides file-level storage (e.g., NFS, SMB). Use SAN for high-performance databases; use NAS for file sharing.

OP3 — Medium: 3-tier architecture (core/distribution/access) is hierarchical. Leaf-spine is preferred for modern data centers due to its low latency and high scalability, solving the problem of bottlenecks in 3-tier.

OP4 — Medium: Design a Proxmox cluster with 3+ nodes for quorum. Use shared storage (Ceph, iSCSI, NFS). During node failure, remaining nodes take over with fencing to prevent split-brain.

OP5 — Medium: VLAN trunking (802.1Q) allows a single NIC to handle multiple VLANs. Configure on Linux using VLAN interfaces (e.g., veth.100).

OP6 — Medium: 
- RAID 1: Mirroring (2 drives).
- RAID 5: Striping with parity (3+ drives).
- RAID 6: Dual parity (4+ drives).
- RAID 10: Mirroring + striping (4+ drives).
- RAID Z2: ZFS dual parity.
Choose RAID 10 for balance of performance, capacity, and fault tolerance.

OP7 — Hard: Design DNS with internal AD, DMZ, split-horizon, and DNSSEC. Use recursive resolvers, authoritative servers, forwarders, and conditional forwarding. Ensure seamless DNS resolution when laptops move between office and VPN.

OP8 — Hard: PKI chain: Root CA (offline) -> Subordinate CA -> End-entity certificates. Deploy internal PKI with root CA offline, subordinate CA for issuance, CRL/OCSP for revocation, and auto-enrollment. Compromised subordinate CA affects only issued certificates; compromised root CA affects all.

OP9 — Hard: 
- MPLS: High cost, reliable, complex.
- IPsec VPN: Low cost, less reliable, simple.
- SD-WAN: Moderate cost, reliable, complex.
- WireGuard: Low cost, reliable, simple.
Recommend SD-WAN for latency-sensitive VoIP with 50 users per site.

OP10 — Medium: iDRAC/iLO/IPMI are out-of-band management interfaces. Critical for remote server management. Exposing IPMI to the internet risks security breaches.

OP11 — Medium: 
- LVM: Block-level storage management.
- LVM-Thin: Thin provisioning.
- ZFS: File system with snapshots and RAID.
Use LVM for flexibility, LVM-Thin for space efficiency, ZFS for snapshots and data integrity.

OP12 — Hard: Design a stretch cluster with Ceph, CRUSH rules, and network latency management. Avoid 2-site Ceph without a tiebreaker to prevent split-brain.

OP13 — Easy: DHCP assigns IP addresses via DORA (Discover, Offer, Request, Acknowledge). If a DHCP server is unavailable, a Windows client renews its lease or uses APIPA.

OP14 — Easy: Managed switches (e.g., Cisco) offer VLANs, QoS, and security; unmanaged switches (e.g., Netgear) are plug-and-play with no advanced features.

OP15 — Easy: NTP synchronizes clocks. Clock drift in clusters can cause authentication failures and data inconsistencies.

OP16 — Easy: Physical server runs directly on hardware; VM runs on a hypervisor; container runs on an OS. Use bare metal for performance-critical workloads.

OP17 — Easy: UPS provides short-term power; generator provides long-term power. Both are needed for redundancy. ATS switches between power sources.

OP18 — Medium: Active-passive clustering (one active, one standby) vs active-active (both active). Implement HA for PostgreSQL using Pacemaker/Corosync with STONITH, virtual IPs, and failover.

OP19 — Hard: Backup strategy: 3-2-1 rule, RPO/RTO, full/incremental/differential backups, deduplication, offsite storage (disk/cloud), immutable backups, and restore testing. Backup is data protection; disaster recovery is system restoration.

OP20 — Hard: 802.1X uses supplicant, authenticator, and authentication server (RADIUS) for port-based access control. EAP methods (EAP-TLS, PEAP) authenticate devices. MAB allows non-802.1X devices to authenticate via MAC address.
