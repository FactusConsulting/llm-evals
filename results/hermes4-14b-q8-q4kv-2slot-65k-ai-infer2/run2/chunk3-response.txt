## OpenTofu / Terraform (20 questions)

T1 — Easy: What is the difference between tofu plan and tofu apply?
- `tofu plan` generates an execution plan by comparing the current state with the desired configuration. It shows what changes will be made but does not execute them.
- `tofu apply` executes the changes described in the plan, modifying the infrastructure to match the configuration.

T2 — Easy: What is state in OpenTofu, and why is remote state important?
- State is a JSON file that tracks the current state of your infrastructure, mapping resources to their IDs and attributes.
- Remote state is important for collaboration, locking to prevent concurrent modifications, and sharing state between modules.

T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?
- `count` creates multiple instances of a resource using an integer index.
- `for_each` creates multiple instances using a map or set of unique keys, providing more flexibility and better resource naming.
- `for_each` is preferred when you need to associate resources with unique identifiers or when you want to iterate over a collection of values.

T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
- If you manually change a resource, OpenTofu detects the discrepancy during the next `plan` or `apply` by comparing the state file with the actual cloud resource.
- OpenTofu will show a diff indicating the resource is out of sync and will attempt to reconcile it by modifying the resource to match the configuration.

T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-abc123"
  instance_type = "t2.micro"
  tags = {
    Name = each.value
  }
}
```

T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
- `terraform_remote_state` data source allows a module to read the state of another OpenTofu configuration.
- Output values are used to share data between modules within the same root configuration.
- The recommended alternative is to use OpenTofu's built-in `data` sources and `output` blocks, as they are more integrated and avoid the complexity of remote state dependencies.

T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
- The `null_resource` with `remote-exec` provisioner runs after the resource is created, but the output is not available until the provisioner completes.
- The dependent resources fail because the output is empty during the initial apply.
- To fix this, use the `depends_on` meta-argument to ensure the dependent resources wait for the `null_resource` to complete, or use a `local-exec` provisioner to capture the output and store it in a file that can be read by subsequent resources.

T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
- `tofu import` is used to import existing infrastructure into OpenTofu's state.
- Limitations include the need to manually map existing resources to OpenTofu resources and the inability to import resources that are not supported by OpenTofu.
- The `import` block in OpenTofu 1.5+ allows you to define import configurations directly in your OpenTofu code, making it easier to manage and version control imports.

T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
- A variable in OpenTofu is a value that can be passed into a configuration to customize its behavior.
- Input variables are defined in the configuration and can be set via command-line arguments, environment variables, or files.
- Output values are used to expose data from a configuration to other configurations or to the user.

T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
- A provider in OpenTofu is a plugin that manages resources for a specific cloud or service.
- If you run `tofu plan` without running `tofu init` first, OpenTofu will not have downloaded the necessary provider plugins, and the plan will fail.

T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
- The `.terraform.lock.hcl` file is a lock file that records the exact versions of provider plugins used in a configuration.
- It should be committed to version control to ensure that all team members and environments use the same provider versions, preventing unexpected changes.

T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
- `tofu destroy` removes all resources managed by OpenTofu.
- To target a single resource for destruction, use the `-target` flag followed by the resource address, e.g., `tofu destroy -target=aws_instance.example`.

T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
- A data source in OpenTofu is used to read information from an external system, such as an existing resource or a configuration file.
- Example: Use a data source to read the current IP address of an existing EC2 instance instead of creating a new instance.

T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
- `variable` blocks define input variables that can be set by the user or environment.
- `locals` blocks define local variables that are computed within the configuration and are not exposed to the user.
- Use `locals` for values that are derived from other variables or constants and do not need to be set externally.

T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
- The `lifecycle` block in a resource defines custom behavior for the resource's lifecycle.
- `create_before_destroy`: Creates a new resource before destroying the old one, useful for ensuring service continuity.
- `prevent_destroy`: Prevents the resource from being destroyed, useful for critical resources that should not be accidentally deleted.
- `ignore_changes`: Ignores changes to specific attributes, useful for attributes that are managed outside of OpenTofu.

T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
- A `moved` block in OpenTofu is used to indicate that a resource has been moved to a new address.
- It helps when refactoring module structure by allowing OpenTofu to recognize the resource as the same one, avoiding unnecessary destruction and recreation.

T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
- OpenTofu builds a dependency graph based on resource references and explicit dependencies.
- Implicit dependencies are automatically inferred from resource references.
- Explicit dependencies are defined using the `depends_on` meta-argument.
- `depends_on` can force a specific order of execution, which can reduce parallelism and increase plan time. It should be used sparingly to avoid unnecessary complexity.

T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
- **Parallelism**: Increase the number of parallel operations using the `-parallelism` flag. Tradeoff: Higher resource consumption.
- **State Locking**: Use a remote state backend with locking to prevent concurrent modifications. Tradeoff: Adds complexity and potential for lock contention.
- **Modularization**: Break down the configuration into smaller, reusable modules. Tradeoff: Requires refactoring and may increase initial setup time.
- **Caching**: Use OpenTofu's built-in state and provider plugin caching. Tradeoff: May not significantly reduce plan time for large configurations.

T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
- OpenTofu uses a state locking mechanism to prevent concurrent modifications to the state file.
- If a lock is not released, subsequent operations will fail until the lock is released.
- To manually break a lock, use the `tofu force-unlock` command with the lock ID. Risks include potential data corruption if the state was in an inconsistent state.

T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
- **Step 1**: Configure the remote backend in your OpenTofu configuration file.
- **Step 2**: Run `tofu init` to initialize the backend and migrate the state file to the remote backend.
- **Step 3**: Verify the migration by running `tofu plan` and ensuring it uses the remote state.
- **Step 4**: Test the state locking mechanism by running concurrent operations and ensuring they are properly locked.

## Ansible (20 questions)

A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?
- A playbook is a YAML file that defines a series of tasks to be executed.
- A role is a way to organize tasks, handlers, templates, and files into reusable units.
- A task is a single action performed by Ansible, such as installing a package or copying a file.

A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?
- `ansible_facts` is a dictionary of facts gathered about a target host.
- Access the OS family using `ansible_facts['os_family']`.

A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
- `command`: Executes a command without a shell, useful for idempotent operations.
- `shell`: Executes a command through a shell, useful for commands that require shell features.
- `raw`: Executes a command directly on the target host, bypassing Ansible's module system, useful for unsupported systems.
- Use `command` for idempotent operations, `shell` for shell-specific features, and `raw` for unsupported systems.

A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
- Ansible ensures idempotency by checking the current state of the system before making changes.
- Idempotent task: `package: name=nginx state=present` (installs nginx if not present).
- Non-idempotent task: `command: echo "Hello World" > /tmp/test.txt` (always creates the file).

A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.
```yaml
- name: Install htop based on OS family
  package:
    name: "{{ 'htop' if ansible_facts['os_family'] == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
```

A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
- Ansible's variable precedence order (from lowest to highest):
  1. Role defaults
  2. Inventory group_vars
  3. Inventory host_vars
  4. Playbook group_vars
  5. Playbook host_vars
  6. Host facts
  7. Role vars
  8. Play vars
  9. Play vars_prompt
  10. Play vars_files
  11. Registered vars
  12. set_fact
  13. extra_vars
  14. Command-line variables

A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
- **Inventory Groups**: Create an inventory group for the first 3 nodes and another for the remaining 47 nodes.
- **Serial**: Use the `serial` keyword in the playbook to limit the number of nodes processed at a time.
- **wait_for**: Use the `wait_for` module to wait for the first 3 nodes to complete before starting the rest.

A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
- `ansible-vault` is a tool for encrypting sensitive data in Ansible playbooks and variables.
- To encrypt a single variable, use the `ansible-vault encrypt_string` command and include the encrypted value in the vars file.

A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
- An Ansible inventory file lists the hosts and groups that Ansible manages.
- A static inventory is a fixed list of hosts, while a dynamic inventory is generated on the fly by a script or plugin.

A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?
- Use the `ansible` command: `ansible webservers -m command -a "df -h"`

A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
- A handler is a task that is only run if notified by another task.
- Handlers are defined in the `handlers` section of a playbook and are triggered using the `notify` keyword.

A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
- The `ansible.cfg` file is used to configure Ansible settings.
- Common settings: `inventory`, `remote_user`, `ask_pass`, `forks`.

A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
- The `register` keyword captures the output of a task into a variable.
- Use the registered variable in a subsequent task using its name, e.g., `debug: var=result.stdout`.

A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
- `include_tasks`: Includes tasks dynamically at runtime, allowing for conditional inclusion.
- `import_tasks`: Imports tasks statically at parse time, making them part of the playbook.
- Use `include_tasks` for dynamic task inclusion and `import_tasks` for static task inclusion. Conditional evaluation is possible with `include_tasks` but not with `import_tasks`.

A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
- Ansible Galaxy is a repository for sharing Ansible roles and collections.
- Use a `requirements.yml` file to specify roles and collections to install, then run `ansible-galaxy install -r requirements.yml`.

A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
- Connection plugins define how Ansible connects to target hosts.
- `ssh`: Connects via SSH, default for remote hosts.
- `local`: Connects to the local machine.
- `network_cli`: Connects to network devices via a CLI.
- Use `ssh` for remote hosts, `local` for local tasks, and `network_cli` for network devices.

A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
- `delegate_to`: Runs a task on a different host than the target host.
- `run_once`: Runs a task only once, even if it is applied to multiple hosts.
- Example: Gather facts from a remote host and run a task on the control node to process the data.

A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
- **Forks**: Increase the number of parallel connections using the `forks` setting. Tradeoff: Higher resource consumption.
- **Pipelining**: Enable pipelining to reduce the number of SSH connections. Tradeoff: May not be supported by all modules.
- **Fact Caching**: Cache facts to avoid gathering them repeatedly. Tradeoff: May not be suitable for dynamic environments.
- **Mitogen**: Use the Mitogen plugin to reduce overhead. Tradeoff: Adds complexity and may not be compatible with all modules.

A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
- Jinja2 templating allows dynamic generation of content using variables and control structures.
- `{{ }}`: Output a variable.
- `{% %}`: Execute a control structure (e.g., loops, conditionals).
- `{# #}`: Add a comment.
- Template snippet:
```jinja2
upstream my_upstream {
{% for server in backend_servers %}
  server {{ server.ip }}:{{ server.port }}; # {{ server.comment }}
{% endfor %}
}
```

A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
- **Serial Batches**: Use the `serial` keyword to deploy in batches.
- **Pre/Post Tasks**: Register servers with the load balancer before deployment and deregister after deployment.
- **Health Checks**: Use the `uri` module to check the health of the application before proceeding.
- **Rollback Strategy**: Use `block` and `rescue` to handle failures and roll back changes if necessary.
