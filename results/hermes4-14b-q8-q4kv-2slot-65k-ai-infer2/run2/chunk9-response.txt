## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A: Explanation of Failure**
The pods are failing because the combination of the new Pod Security Standard (Restricted), the securityContext.runAsNonRoot: true, and the container image's USER directive (root) is causing a conflict. Here's the breakdown:
1.  **Pod Security Standard (Restricted):** This PSS enforces stricter security policies than Baseline. A key requirement under Restricted is that if `runAsNonRoot` is set to `true` (which it is), then `runAsUser` must also be explicitly set to a non-root user ID.
2.  **securityContext.runAsNonRoot: true:** This explicitly states that the container should not run as the root user.
3.  **Container Image USER Directive (root):** The new base image `cgr.dev/chainguard/static:latest` defaults to running as the root user.
4.  **The Conflict:** With `runAsNonRoot: true`, Kubernetes expects the container to run as a non-root user. However, the image's `USER` directive is set to `root`. The PSS (Restricted) then checks if `runAsUser` is explicitly set. Since it's not, Kubernetes cannot satisfy the `runAsNonRoot: true` requirement because it doesn't know which non-root user to use, and the image is configured to run as root. This results in the pod failing to start, leading to CrashLoopBackOff.

**SC1-B: Bash One-Liner for Identifying Failing Pods**
```bash
kubectl get pods --all-namespaces --field-selector=status.phase=CrashLoopBackOff -o jsonpath='{range .items[?(@.status.containerStatuses[0].lastState.waiting.reason=="CrashLoopBackOff")]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.spec.containers[0].securityContext}{end}' | jq -c
```
*Note: This one-liner uses `jq` for pretty-printing JSON. If `jq` is not available, the `jsonpath` output can be used directly, though it will be less readable.*

**SC1-C: Remediation Strategy**
1.  **Immediate Fix (Image-Level):**
    *   Modify the Dockerfile for the base image `cgr.dev/chainguard/static:latest` (or any other base image used) to explicitly set a non-root user. For example:
        ```dockerfile
        USER 1001 # Or any other non-root UID
        ```
    *   Rebuild and push the affected microservice images with this change.
2.  **Kubernetes Manifest Changes:**
    *   For each affected pod manifest, explicitly set `runAsUser` to the non-root user ID chosen (e.g., `1001`). This satisfies the PSS (Restricted) requirement.
        ```yaml
        securityContext:
          runAsNonRoot: true
          runAsUser: 1001 # Explicitly set the non-root user
        ```
3.  **CI Pipeline Gate:**
    *   **Image Scan:** Integrate a scanner (e.g., Trivy, Clair) into the CI pipeline that checks the base image's `USER` directive. If the base image is `root` and `runAsNonRoot: true` is set in the manifest, the build should fail.
    *   **PSS Compliance Check:** Use a tool like `kube-psp-validator` or a custom script to check pod manifests against the target PSS (Restricted) before deployment. This can be done as a pre-commit hook or a CI stage.
4.  **Rollout Without Downtime:**
    *   Use Kubernetes rolling updates (the default for Deployments). This will gradually replace old pods with new ones.
    *   Monitor the rollout status with `kubectl rollout status deployment/<deployment-name>`.
    *   Ensure the new image is correctly tagged and pushed to the registry before starting the rollout.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A: Stale Data Issue Explanation**
1.  **Stale Data Issue:** The stale data occurs because PostgreSQL streaming replication is asynchronous by default for cross-region replicas. When the primary in `us-east-1` fails, the replica in `eu-west-1` is promoted to a standalone primary. However, any Write-Ahead Log (WAL) records generated by the old primary in the last few seconds (or minutes) before it failed were not yet shipped to and applied by the replica. These unreplicated changes are lost, and the new primary in `eu-west-1` does not have them, leading to stale data for those writes.
2.  **Replication Lag Implication:** The replication lag is the time difference between the old primary's commit time and the replica's application of that commit. This lag is the data loss window. If the lag was, for example, 30 seconds, then any writes committed in the last 30 seconds on the old primary are lost.
3.  **WAL Shipping & Data Loss:** PostgreSQL uses WAL shipping to replicate changes. In asynchronous replication, the primary sends WAL records to the replica, but the primary does not wait for an acknowledgment from the replica before committing the transaction. This allows for better performance but introduces the risk of data loss if the primary fails before the WAL is shipped and applied.
4.  **Quantifying Data Loss Window:**
    *   Check the `pg_stat_replication` view on the old primary (if still accessible) for `write_lag` and `flush_lag` (time since last WAL record was written to disk on primary and flushed to replica's disk, respectively).
    *   Check the `pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()` on the replica (before promotion) to see how far behind it was.
    *   After promotion, the data loss window is the time between the last WAL record applied by the replica and the time the old primary failed.

**SC2-B: Terraform Operations for RDS Instance Update**
1.  **Import the Promoted Replica:**
    *   First, ensure the replica is promoted and stable.
    *   Use `terraform import` to import the new primary instance into Terraform state. You'll need its ARN.
        ```bash
        terraform import aws_db_instance.new_primary_arn <new_primary_instance_arn>
        ```
2.  **Update Terraform Configuration:**
    *   Modify your `aws_db_instance` resource definition in the Terraform code to point to the new primary instance's ARN and other attributes (e.g., `identifier`, `engine_version` if changed).
    *   Update any other resources that reference the old instance (e.g., `aws_db_subnet_group`, `aws_security_group`, `aws_route53_record`, `aws_db_parameter_group`) to use the new primary instance's attributes or ARN.
3.  **Apply Changes:**
    *   Run `terraform plan` to see the changes Terraform will make.
    *   Run `terraform apply` to apply the changes. Terraform will update the state to reflect the new primary instance and its dependencies. It will not destroy the old instance if it's still present in the state and not marked for deletion. You will need to manually remove the old instance from Terraform state or mark it for deletion if it's no longer needed.

**SC2-C: Future-Proof Architecture**
1.  **RDS Proxy vs. PgBouncer:**
    *   **RDS Proxy:** Recommended. It provides connection pooling, transparent failover, and enhanced security (IAM authentication, connection throttling). It sits between the application and the database, abstracting the database endpoint.
    *   **PgBouncer:** Can be used but requires more manual management of failover and connection pool configuration.
2.  **Route53 Health Checks & DNS Failover:**
    *   Use Route53 health checks to monitor the health of your database endpoints (primary and replica).
    *   Configure DNS failover (e.g., latency-based routing or failover routing policy) to automatically switch traffic to the healthy region.
3.  **Application-Level Retry Logic:**
    *   Implement retry logic in your application for database operations, with exponential backoff, to handle transient network issues or brief unavailability.
4.  **Achieving RPO < 1 second:**
    *   **Synchronous Replication:** Use synchronous replication for cross-region failover. This ensures that a transaction is committed on both the primary and the replica before the application receives a success response. However, this can introduce latency.
    *   **Aurora Global Database:** This is the best option for achieving RPO < 1 second and low RTO across regions. It uses a primary region with synchronous replication to a secondary region, and asynchronous replication from the secondary to other read replicas. Promoting a secondary region is fast.
5.  **Recommendation: Aurora Global Database**
    *   **Yes, strongly recommend.** It natively provides global read replicas, fast cross-region failover (RTO < 1 minute), and RPO < 1 second. It simplifies management compared to managing RDS replication manually and offers better performance and availability for global applications.

        return []

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A: Top 5 Technical Blockers**
1.  **Blocker: Local Memory for User Sessions (Sticky Sessions via F5)**
    *   **Problem:** Kubernetes does not natively support sticky sessions in the same way F5 does. Sessions stored in local memory are lost if a pod is rescheduled.
    *   **Solution:** Implement a distributed session store (e.g., Redis, Hazelcast, or a database). Modify the application to store and retrieve sessions from this store. Use Kubernetes Services and Ingress to route requests.
2.  **Blocker: Local NFS Mount for Uploaded Files**
    *   **Problem:** Local NFS mounts are not portable across Kubernetes nodes. If a pod is rescheduled, it loses access to its local NFS mount.
    *   **Solution:** Use a PersistentVolume (PV) and PersistentVolumeClaim (PVC) backed by a network-attached storage solution (e.g., NFS CSI driver, Ceph, GlusterFS, or cloud provider block storage). This ensures the storage is accessible to any node where the pod is scheduled.
3.  **Blocker: On-Prem Oracle 19c Database**
    *   **Problem:** The monolith is tightly coupled to an on-prem database. Migrating the database to Kubernetes or a cloud-managed database service is a significant undertaking.
    *   **Solution:** Containerize the Oracle database (if feasible and desired) and run it in Kubernetes, or migrate it to a cloud-managed database service (e.g., Oracle Cloud, AWS RDS for Oracle, Azure Database for Oracle). Update the application's connection string.
4.  **Blocker: IBM MQ Integration**
    *   **Problem:** The application communicates with a mainframe via IBM MQ. Ensuring reliable and secure messaging in a Kubernetes environment requires specific setup.
    *   **Solution:** Deploy IBM MQ in Kubernetes (e.g., using the IBM MQ Operator) or use a managed MQ service. Ensure the application's MQ client libraries are compatible with Kubernetes networking and security models.
5.  **Blocker: Legacy Java 11 Application Architecture**
    *   **Problem:** A monolithic application is often tightly coupled, making it difficult to scale individual components independently and hindering the benefits of Kubernetes.
    *   **Solution:** This is a long-term architectural challenge. The initial migration might involve containerizing the monolith as-is. For a more robust Kubernetes deployment, consider a phased approach towards microservices, potentially using the Strangler Fig pattern (see SC4-C). This involves gradually replacing parts of the monolith with new microservices.

**SC5-B: SQL Diagnostic Query & Go Circuit Breaker**
*   **SQL Diagnostic Query for PostgreSQL:**
    ```sql
    SELECT
        pid,
        usename,
        datname,
        client_addr,
        state,
        wait_event_type,
        wait_event,
        query,
        query_start,
        now() - query_start AS duration,
        backend_xid,
        backend_xmin,
        locktype,
        relation::regclass AS relation,
        mode,
        granted,
        blocked_by.pid AS blocked_by_pid,
        blocked_by.usename AS blocked_by_user,
        blocked_by.query AS blocked_by_query
    FROM pg_stat_activity
    LEFT JOIN pg_locks ON pg_locks.pid = pg_stat_activity.pid
    LEFT JOIN pg_stat_activity AS blocked_by ON blocked_by.pid = pg_locks.pid
    WHERE state = 'active' AND wait_event IS NOT NULL
    ORDER BY query_start;
    ```
    This query helps identify active queries that are waiting on locks, the queries holding those locks, and the duration of the wait.

**SC5-C: Architectural Solution to Eliminate Problem**
1.  **Separate Read Path from Write/Reconciliation Path (CQRS):**
    *   Implement Command Query Responsibility Segregation. The `checkout-service` should only write to the database (or call services that write). It should read from a dedicated read model or a read replica.
2.  **Use a Read Replica for Reconciliation Job:**
    *   Run the inventory reconciliation job against a read replica of the database. This prevents the job from blocking writes on the primary database.
3.  **Implement Bulkhead Isolation for Database Connection Pool:**
    *   Use separate database connection pools for read operations (used by the `checkout-service` and other read-heavy services) and write operations (used by the reconciliation job and other write-heavy services). This prevents the reconciliation job from exhausting the connection pool used by the serving application.
4.  **Adjust CronJob Scheduling:**
    *   Schedule the reconciliation job during off-peak hours to minimize impact on serving applications.
    *   Consider breaking the reconciliation job into smaller, more frequent batches if possible.
5.  **Kubernetes PodDisruptionBudgets (PDBs) and Resource Quotas:**
    *   **PDBs:** Define PDBs for the `inventory-service` pods to ensure a minimum number of replicas are always available during voluntary disruptions (e.g., node maintenance). This helps maintain service availability even if some pods are temporarily unavailable.
    *   **Resource Quotas:** Define resource quotas for the namespace where the reconciliation job runs to limit its CPU and memory consumption, preventing it from starving resources from the serving pods.

## SC6 — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A: Identity and Access Layer Design**
1.  **Machine Identity for Workloads:**
    *   **SPIFFE/SPIRE:** Implement SPIFFE (Secure Production Identity Framework For Everyone) and SPIRE (SPIFFE Runtime Environment) across all environments.
        *   **On-Prem:** Deploy SPIRE Server and SPIRE Agent on vSphere. Workloads (VMs) register with the SPIRE Agent to obtain short-lived SPIFFE IDs (SVIDs) and corresponding X.509 certificates.
        *   **AWS:** Use the AWS SPIRE Agent (or a custom SPIRE Agent) to issue SVIDs to EC2 instances, EKS pods, and Lambda functions. Integrate with AWS IAM roles for EC2/EKS.
        *   **Azure:** Use the Azure SPIRE Agent (or a custom SPIRE Agent) to issue SVIDs to Azure VMs, AKS pods, and Azure Functions. Integrate with Azure Managed Identities.
    *   **Federated Identity:**
        *   **On-Prem PKI:** Use the on-prem PKI to issue root or intermediate certificates to the SPIRE Server in AWS and Azure. This allows the SPIRE Servers in cloud environments to trust SVIDs issued by the on-prem SPIRE Server.
        *   **AWS IAM Roles:** Workloads in AWS can assume IAM roles, and these roles can be mapped to SPIFFE IDs via the SPIRE Agent.
        *   **Azure Managed Identities:** Workloads in Azure can use managed identities, and these can be mapped to SPIFFE IDs via the SPIRE Agent.
        *   **Cross-Environment Authentication:** A workload in AWS (with an SVID issued by the AWS SPIRE Server) can authenticate to a service on-prem (with an SVID issued by the on-prem SPIRE Server) by presenting its X.509 certificate. The on-prem service trusts the AWS SPIRE Server's CA certificate (which is part of the federated trust chain). No shared secrets are needed; authentication is based on the SVIDs and the trust established through the SPIFFE trust domain and the federated PKI.

**SC6-C: VPN Upgrade Options**
1.  **Upgrade to AWS Direct Connect:**
    *   **Cost:** Higher upfront (port fees, cross-connects) and ongoing (port bandwidth). More expensive than VPN.
    *   **Bandwidth:** Significantly higher (up to 100 Gbps per port, with multiple ports aggregatable).
    *   **Encryption:** Typically uses MACsec for encryption over the physical link. Can also use IPsec over Direct Connect.
    *   **Failover:** Can be configured for high availability with multiple Direct Connect connections and BGP.
    *   **Zero-Trust Fit:** Provides a dedicated, high-bandwidth, secure connection. Can be part of a zero-trust architecture by being the primary link for on-prem to cloud traffic, with routing policies enforced.
    *   **Routing Changes:** Requires BGP configuration on both on-prem and AWS sides. Traffic is routed over the Direct Connect link.
2.  **Add a Second VPN Tunnel with ECMP:**
    *   **Cost:** Lower than Direct Connect. AWS VPN costs are based on data processed.
    *   **Bandwidth:** Aggregates bandwidth of two tunnels (e.g., 1 Gbps total if each is 500 Mbps). Still limited by VPN capacity.
    *   **Encryption:** IPsec encryption for both tunnels.
    *   **Failover:** ECMP provides load balancing and basic failover. If one tunnel goes down, traffic shifts to the other. Not as robust as BGP-based failover.
    *   **Zero-Trust Fit:** Can be used, but the shared IPsec encryption and potential for asymmetric routing might be less ideal than Direct Connect for a strict zero-trust model where path isolation is key.
    *   **Routing Changes:** Requires BGP configuration on AWS side to advertise routes over both tunnels. On-prem router must support ECMP for VPN.
3.  **Implement a Hybrid Mesh (Tailscale/Netbird):**
    *   **Cost:** Tailscale has a free tier, paid plans. Netbird is open-source with commercial support options. Generally lower cost than Direct Connect.
    *   **Bandwidth:** Limited by the internet connection of the on-prem site and the cloud instance running the mesh agent.
    *   **Encryption:** End-to-end WireGuard encryption.
    *   **Failover:** Can be resilient if multiple agents are deployed and configured for redundancy.
    *   **Zero-Trust Fit:** Excellent fit for zero-trust. Provides encrypted, authenticated tunnels between any nodes (VMs, containers, devices) across environments. Simplifies network segmentation and policy enforcement.
    *   **Routing Changes:** Requires installing agents on all nodes. Routing is typically handled by the mesh itself, abstracting underlying network topology.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A: Explanation of Drift Sources**
1.  **Manual tofu apply from developer laptops:**
    *   **How it occurred:** Developers ran `tofu apply` locally, likely against the production state file stored in S3, without proper review or approval.
    *   **Danger:** This leads to uncontrolled changes in production. It bypasses any automated testing, validation, or approval processes. It can cause data loss, service disruption, or introduce security vulnerabilities. It makes the state file a single point of failure and a target for accidental or malicious changes.
    *   **Data loss/outage scenarios:** Accidental deletion of resources, overwriting of critical configurations, introducing incompatible changes.
2.  **Staging and production Helm values files diverged:**
    *   **How it occurred:** Developers made changes to Helm values files for staging and production directly, without using a version-controlled, shared source of truth (e.g., a Git repository for values files, or using Helmfile/Kustomize overlays). These changes were not tracked in Git.
    *   **Danger:** This leads to inconsistencies between environments, making it hard to reproduce issues, test changes, or ensure that production is configured correctly. It increases the risk of deploying misconfigured applications.
    *   **Data loss/outage scenarios:** Deploying an application with incorrect database connection strings, misconfigured security settings, or missing critical features can lead to data corruption, security breaches, or service outages.
3.  **Production ConfigMaps edited directly with kubectl edit:**
    *   **How it occurred:** Operators or developers used `kubectl edit cm <configmap-name>` directly in the Kubernetes cluster to make changes to ConfigMaps in production.
    *   **Danger:** This bypasses any CI/CD pipeline, automated testing, or version control for configuration. Changes are not audited, and it's easy to make mistakes or introduce conflicts.
    *   **Data loss/outage scenarios:** Incorrect configuration data can cause applications to malfunction, crash, or behave unexpectedly. For example, changing a critical environment variable or a configuration file format can lead to immediate service disruption.
