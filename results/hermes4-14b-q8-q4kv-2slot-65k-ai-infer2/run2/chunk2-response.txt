K1 — Easy: What is the difference between a Deployment and a StatefulSet?
A Deployment manages stateless pods that can be replaced without preserving identity. A StatefulSet manages stateful pods that require stable network identities, persistent storage, and ordered deployment/termination.

K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?
A ClusterIP Service creates a virtual IP (VIP) that is only accessible within the cluster. It routes traffic to pods via kube-proxy, which uses iptables or IPVS rules to forward traffic to the pods selected by the Service's selector.

K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?
- PersistentVolume (PV): A piece of storage in the cluster, abstracted and consumable by users.
- PersistentVolumeClaim (PVC): A request for storage by a user, which binds to a PV.
- StorageClass: Defines a "class" of storage, which can be dynamically provisioned by the cluster.
Relationship: PVCs request storage, which is fulfilled by PVs. StorageClasses define how PVs are dynamically provisioned when a PVC is created without a pre-existing PV.

K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).
1. Check pod logs with `kubectl logs <pod> -c <container>` to see error messages.
2. Inspect pod events with `kubectl describe pod <pod>` to see scheduling or runtime errors.
3. Verify resource requests/limits in the pod spec to ensure they are not too restrictive.
4. Check if the container image is correct and accessible (e.g., image pull secrets).
5. Ensure the application inside the container is not crashing due to misconfiguration or bugs.

K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?
CoreDNS provides DNS resolution for services and pods within the cluster. If CoreDNS pods are down, DNS resolution will fail, causing pods to be unable to communicate with each other or external services via DNS names.

K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.
The scheduler first filters nodes that meet the pod's requirements (e.g., resource availability, node selectors, taints/tolerations). Then, it scores the remaining nodes based on factors like:
1. Resource utilization (e.g., spreading pods evenly across nodes).
2. Affinity/anti-affinity rules (e.g., co-locating or avoiding certain pods).
3. Node labels and taints/tolerations.
4. Custom predicates (e.g., node-specific constraints).

K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?
The pod will not be scheduled because the node has only 0.5GB of available RAM (4GB - 3.5GB), which is less than the pod's requested 256Mi. If the pod were scheduled and used 600Mi, it would exceed its memory limit, causing the container to be killed by the kubelet.

K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.
1. External LB receives the request and forwards it to the ingress controller.
2. The ingress controller (NGINX) processes the request based on the Ingress resource rules.
3. The ingress controller routes the request to the appropriate Service (e.g., via a ClusterIP Service).
4. The Service's Endpoints (managed by kube-proxy) select the available pods.
5. kube-proxy uses iptables or IPVS to forward the request to the selected pod.
6. The request reaches the application pod, which processes it and returns a response.

K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?
A NetworkPolicy defines how pods can communicate with each other and with external networks. If no NetworkPolicy exists, all pods in the namespace can communicate freely. When a NetworkPolicy is applied, it restricts traffic to only the pods selected by the policy, unless explicitly allowed.

K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?
- RollingUpdate: Updates pods incrementally, maintaining availability. Suitable for most applications.
- Recreate: Terminates all old pods before creating new ones. Suitable for applications that cannot run old and new versions simultaneously (e.g., database migrations).

K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?
A namespace is a virtual cluster that isolates resources. Default namespaces include: `default`, `kube-system`, `kube-public`, and `ingress-nginx` (if installed).

K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.
`kubectl describe pod` provides detailed information about a pod, including:
1. Events (e.g., scheduling, runtime errors).
2. Container status (e.g., restart count, last state).
3. Resource requests/limits.
4. Environment variables and command arguments.

K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.
A ConfigMap stores configuration data. A pod can consume it by:
1. Mounting it as a volume (e.g., as a file in a directory).
2. Injecting it as environment variables.

K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?
- ClusterIP: Internal service, only accessible within the cluster.
- NodePort: Exposes the service on a static port on each node's IP.
- LoadBalancer: Exposes the service externally using a cloud provider's load balancer.

K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?
A DaemonSet ensures a pod runs on every node (or a subset of nodes). Use it for system daemons (e.g., log collectors, monitoring agents) instead of Deployments, which manage stateless applications.

K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?
- Taints: Mark nodes to repel pods unless they have matching tolerations.
- Tolerations: Allow pods to be scheduled on tainted nodes.
- Node Affinity: Attracts pods to specific nodes based on labels.
Use case for taints/tolerations: Reserving nodes for critical workloads. Use case for node affinity: Ensuring pods run on nodes with specific hardware (e.g., GPUs).

K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?
An Operator is a custom controller that extends Kubernetes with domain-specific knowledge. It differs from standard controllers by managing complex applications (e.g., databases) with custom logic. It solves problems like automated backups, upgrades, and scaling for stateful applications.

K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?
etcd uses a Raft consensus algorithm for strong consistency. If the quorum (majority) is lost, the cluster becomes unavailable. To recover from 2 out of 3 etcd nodes being lost, you must restore from a backup and rejoin the remaining node.

K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.
RBAC uses Roles (namespace-scoped) and ClusterRoles (cluster-scoped) to define permissions. RoleBindings and ClusterRoleBindings grant these permissions to users/groups. For read-only access to pods and logs in a namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: <namespace>
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: <namespace>
subjects:
- kind: User
  name: <developer>
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.
The `ndots` parameter in `/etc/resolv.conf` specifies the number of dots in a name before querying external DNS. If set too low, pods may query internal DNS (CoreDNS) for external domains, causing delays. Fix by setting `ndots: 5` in the pod's `dnsConfig` to ensure external domains are resolved via the external DNS server.

D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?
- `git rebase` rewrites commit history by moving a branch's commits to a new base.
- `git merge` combines branches by creating a new merge commit.
Avoid rebasing when working on shared branches to prevent history rewriting conflicts.

- TCP: Connection-oriented, reliable, ordered. Protocols: HTTP, FTP.
- UDP: Connectionless, unreliable, unordered. Protocols: DNS, VoIP.

D3 — Medium: What is a race condition? Give a concrete example in any language.
A race condition occurs when the outcome depends on the sequence or timing of uncontrollable events. Example: Two threads incrementing a shared counter without synchronization, leading to lost updates.

D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?
- Symmetric: Uses the same key for encryption/decryption (e.g., AES).
- Asymmetric: Uses a public key for encryption and a private key for decryption (e.g., RSA).
TLS uses asymmetric encryption for key exchange and symmetric encryption for data transfer.

A container image layer is a read-only filesystem layer. Layer caching speeds up builds by reusing unchanged layers. Best practices: Order instructions to maximize cache reuse, avoid unnecessary changes to base images.

D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.
The CAP theorem states a distributed system can only guarantee two of: Consistency, Availability, Partition Tolerance. Example CP: Cassandra (strong consistency during partitions). Example AP: DynamoDB (high availability during partitions).

D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?
A deadlock is a situation where processes are blocked waiting for each other. Coffman conditions:
1. Mutual exclusion: Resources are held exclusively.
2. Hold and wait: Processes hold resources while waiting for others.
3. No preemption: Resources cannot be forcibly taken.
4. Circular wait: A circular chain of processes waiting for each other.

D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?
Eventual consistency means all replicas will eventually have the same data. Cassandra uses tunable consistency levels (e.g., QUORUM, LOCAL_QUORUM) to balance consistency and availability. Read-after-write consistency is achieved by using the same consistency level for writes and reads.

D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?
mTLS is a security protocol where both client and server authenticate each other using certificates. Handshake process:
1. Client sends a "ClientHello" message.
2. Server responds with a "ServerHello" and its certificate.
3. Client verifies the server's certificate and sends its own certificate.
4. Server verifies the client's certificate.
5. Both generate session keys for encrypted communication.
mTLS is commonly used in service-to-service communication in microservices architectures.

D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?
A hash table uses a hash function to map keys to indices. Collision resolution:
- Chaining: Store colliding entries in a linked list.
- Open addressing: Find an alternative index using probing.
Time complexity:
- Average: O(1) for insertion, lookup, deletion.
- Worst: O(n) for chaining (if many collisions), O(n) for open addressing (if table is full).

D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?
A circuit breaker prevents cascade failures by monitoring service calls. States:
- Closed: Requests are allowed.
- Open: Requests are blocked.
- Half-open: Limited requests are allowed to test recovery.
It prevents overload by blocking requests when a service is failing. It relates to retry policies by allowing retries after a delay (exponential backoff) when the circuit is half-open.

D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).
- Optimistic: Assumes no conflicts, checks for conflicts at commit (e.g., using row versioning).
- Pessimistic: Locks resources during transactions (e.g., using SELECT FOR UPDATE).
Choose optimistic for low conflict scenarios (e.g., e-commerce inventory updates). Choose pessimistic for high conflict scenarios (e.g., banking transactions).
