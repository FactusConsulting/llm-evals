**Go (20 questions)**  

**G1** — *Easy*:  
- **Array**: Fixed-size, value type. The size is part of the type (`[5]int`).  
- **Slice**: Dynamically sized view over an underlying array (`[]int`). It holds a pointer, length, and capacity.  
- **Appending**: When you `append` to a slice and its length exceeds its capacity, Go allocates a new, larger backing array (typically doubling the capacity), copies the existing elements, and returns the new slice. The original slice may point to the old array if it’s used elsewhere.

**G2** — *Easy*:  
- `var x int` declares a variable `x` of type `int` with the zero value `0`. It can appear at package or function scope.  
- `x := 0` is short‑hand declaration **and** initialization; it infers the type from the RHS.  
- **When `:=` cannot be used**: inside a function scope when the variable already exists, at package level (must use `var`), or in places that require an explicit type (e.g., when declaring a variable without initialization).

**G3** — *Medium*:  
- **Goroutine**: A lightweight thread managed by the Go runtime. It’s a function/Go statement that runs concurrently.  
- **Difference from OS thread**: Goroutines have a small stack (few KB) that can grow/shrink; the runtime multiplexes many goroutines onto fewer OS threads.  
- **Go scheduler (GMP model)**:  
  - **M** (Machine) = OS thread.  
  - **P** (Processor) = scheduler context holding a run queue of goroutines and runtime resources.  
  - **G** (Goroutine) = the actual concurrent unit.  
  The scheduler assigns a G to a P, and a P to an M, balancing load and enabling parallel execution.

**G4** — *Medium*:  
- **Channels** are typed conduits for sending/receiving values between goroutines.  
- **Unbuffered**: The sender blocks until a receiver is ready; the receiver blocks until a sender arrives.  
- **Buffered**: Created with `make(chan T, capacity)`. Sends block only when the buffer is full; receives block only when empty.  
- **Full buffered channel**: `ch <- value` blocks until a receiver consumes an element, freeing space.

**G5** — *Medium*:  
- **context package** propagates deadlines, cancellation signals, and request‑scoped values.  
- **Minimal example**:
  ```go
  ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
  defer cancel()
  req, _ := http.NewRequest("GET", "https://example.com", nil)
  req = req.WithContext(ctx)
  resp, err := http.DefaultClient.Do(req)
  // err will be context.DeadlineExceeded if timeout fires
  ```
- The context is passed to the HTTP request; the client cancels when the deadline passes.

**G6** — *Medium*:  
- **Interface satisfaction**: A type implements an interface by providing all its methods. No `implements` keyword; satisfaction is *implicit*.  
- **Difference from Java/C#**: Those languages require explicit declaration; Go’s duck typing is structural.  
- **Empty interface `interface{}`**: Can hold any value (similar to `Object` in Java).  
  - **Powerful**: Enables generic containers, type‑assertions, and polymorphism without casting.  
  - **Dangerous**: Hides type information; runtime `type‑assertion` errors can occur if the stored concrete type isn’t known.

**G7** — *Hard*:  
- The snippet suffers from **data races** and **visibility** issues. The compiler/runtime may reorder reads/writes, so the main goroutine can see `ready = true` before `data = "hello"` is visible.  
- **Why unsafe**: No memory barrier; the writes in the goroutine aren’t guaranteed to be observed in order by the main goroutine.  
- **Correct alternatives**:  
  1. Use a **channel**:
     ```go
     ch := make(chan struct{})
     go func() {
         data = "hello"
         ch <- struct{}{}
     }()
     <-ch
     fmt.Println(data)
     ```
  2. Use **sync.WaitGroup** or **atomic** operations (`atomic.StoreBool`, `atomic.LoadBool`) with proper ordering guarantees.

**G8** — *Hard*:  
- **sync.Mutex**: Exclusive lock; only one goroutine can hold it.  
- **sync.RWMutex**: Reader‑writer lock; many readers or one writer. Use when reads dominate and are thread‑safe without writes.  
- **sync.Map vs map with mutex**:  
  - `sync.Map` is a *concurrent* map with internal optimizations (separate read/write paths, cache line friendly). Good for high contention, dynamic key sets.  
  - Regular `map` + `sync.Mutex` is simpler and may be faster for low contention or static maps.  
- **Performance trade‑offs**: `sync.Map` avoids a single mutex but has overhead for version stamps and hidden entries; a plain map+mutex can be cheaper when contention is low.

**G9** — *Hard*:  
- **Go modules** manage dependencies via `go.mod`.  
- **`go.mod`**: Declares module path, dependency requirements, and replacements.  
- **`go.sum`**: Contains cryptographic hashes of each dependency version (integrity verification).  
- **`go mod tidy`**: Reconciles `go.mod` with the actual code: adds missing requirements, removes unused ones, ensuring the module is self‑contained.  
- **Minimum Version Selection (MVS)**: The algorithm picks the *lowest* acceptable version that satisfies all constraints, preferring minimal upgrades to avoid breakage.

**G10** — *Medium*:  
- **defer** schedules a function call to run **after** the surrounding function returns.  
- **Execution order**: Defer statements are executed **LIFO** (last deferred is run first).  
- **Common gotcha in loops**: If you defer inside a loop without creating a new scope, the same deferred function runs after the loop finishes, not after each iteration. Use an anonymous function or a separate scope:
  ```go
  for i := 0; i < 5; i++ {
      defer func() { fmt.Println(i) }()
  }
  ```

**G11** — *Easy*:  
- **Pointer**: Holds the memory address of a value. Declared with `*T`.  
- **Zero value**: `nil` (points to nothing).  
- **Pointer to struct literal**:
  ```go
  p := &struct{ X int }{X: 10}
  ```

**G12** — *Easy*:  
- **init()**: Package-level initializer; runs once per package **before** `main` starts.  
- **Order**: Multiple `init()` functions in a package run in **arbitrary but deterministic** order (the compiler orders them).  
- Across packages, init functions run **depth‑first** following import dependencies.

**G13** — *Easy*:  
- **new(T)**: Allocates zero‑value of type `T` on the heap and returns a pointer `*T`. Works for any type.  
- **make(T)**: Creates *initialized* values for **slice, map, channel** (and some `sync.Pool`). It returns an *initialized* (non‑nil) instance, not a pointer.  
- **Types**: `new` works for structs, arrays, basic types; `make` only for the three container types mentioned.

**G14** — *Easy*:  
- **Error handling**: The `error` interface (`error.Error() string`). Functions return an `error` value; callers check `if err != nil { … }`.  
- **`errors.Is`**: Checks if an error matches a target (supports wrapped errors).  
- **`errors.As`**: Tries to assert an error to a specific type (useful for sentinel or custom errors).  
- **`==`**: Only works for *exact* same error instance or sentinel values; it doesn’t traverse wrapped errors.

**G15** — *Easy*:  
- **Composite types**:  
  - **map**: `map[K]V` – zero value `nil` (unusable until `make`).  
  - **slice**: `[]T` – zero value `nil`.  
  - **channel**: `chan T` – zero value `nil`.  
  - **struct**: Collection of fields – zero value with each field set to its zero value.  

**G16** — *Medium*:  
- **Race condition**: Concurrent access to shared mutable state without proper synchronization, leading to nondeterministic behavior.  
- **`-race` flag**: Instruments the binary with the *race detector* (based on the Happens‑Before model) to dynamically detect conflicting accesses.  
- **Example**:
  ```go
  var cnt int
  for i := 0; i < 1000; i++ {
      go func() { cnt++ }()
  }
  ```
  *Fix*: Use `sync.Mutex` or an atomic operation:
  ```go
  var mu sync.Mutex
  for i := 0; i < 1000; i++ {
      go func() {
          mu.Lock()
          cnt++
          mu.Unlock()
      }()
  }
  ```
  or `atomic.AddInt32(&cnt, 1)`.

**G17** — *Medium*:  
- **select**: Allows a goroutine to wait on multiple channel operations simultaneously.  
- **Difference from switch**: Cases are channel communications (`case <-ch:`) and execute when the operation is ready; `default` provides a non‑blocking fallback.  
- **Multiple ready cases**: The runtime picks **one** at random (but fair over time).  
- **Timeout**: Use a `time.After` channel:
  ```go
  select {
  case v := <-ch:
      // got value
  case <-time.After(10 * time.Second):
      // timeout
  }
  ```

**G18** — *Hard*:  
- **Escape analysis**: The compiler decides whether an object can be allocated on the stack or must be heap‑allocated. If a pointer to the object escapes the function’s scope (e.g., stored in a global or returned), it escapes to the heap.  
- **Decision factors**: Presence of escapes, function inlining, and whether the object’s lifetime extends beyond the caller.  
- **Inspecting**: Use `go build -gcflags="-m"` to see escape reasons.  
- **Performance impact**: Stack allocation is faster (no GC pressure). Forcing heap allocation can increase latency and GC work.

**G19** — *Hard*:  
- **reflect package**: Provides runtime introspection.  
  - **`reflect.Type`**: Describes a type (name, methods, underlying struct fields, etc.). Immutable and shared.  
  - **`reflect.Value`**: Holds an actual value; supports `Kind()`, `Interface()`, `Elem()`, method invocation via `MethodByName`.  
- **Performance costs**: Reflection bypasses static type checks, involves interface conversions, and can trigger dynamic method lookups—significantly slower than direct code.  
- **When justified**: Code generation, serialization libraries, generic data walkers, or when the type is truly unknown at compile time. Prefer code generation (`go generate`) for performance‑critical paths.

**G20** — *Hard*:  
- **`go:embed`**: Directive (added in Go 1.16) that instructs the compiler to embed file contents directly into the binary.  
  - **Single file**: `//go:embed filename.txt` then `var content = fs.ReadFileString(embed.FS, "filename.txt")`.  
  - **Directory**: `//go:embed dir/*` embeds the whole directory tree.  
  - **File system**: `//go:embed mydir` creates an `embed.FS` representing that directory.  
- **Limitations**: Cannot embed files conditionally at runtime; size of binary grows; not suitable for very large binary assets.  
- **Interaction with `io/fs.FS`**: `embed.FS` implements `fs.FS`, allowing the same APIs (`Open`, `ReadFile`, `ReadDir`) as regular file systems.

**Rust (20 questions)**  

**R1** — *Easy*:  
- **Ownership** rules:  
  1. Each value has a **single owner** (`struct`, `enum`, primitive).  
  2. When the owner goes out of scope, the value is **dropped** (resources freed).  
  3. Ownership **can be transferred** (`move`) but never duplicated.  
  4. At any time, you have **either** one **mutable** reference **or** any number of **immutable** references, but not both (mutual exclusion).  

**R2** — *Easy*:  
- **`String`**: Heap‑allocated, growable UTF‑8 string. Owned, can be mutated.  
- **`&str`**: String slice, a reference to a sequence of UTF‑8 bytes. Immutable view; can point to a `String`, a string literal, or any contiguous UTF‑8 data.  
- **Usage**: Use `&str` in function signatures when you only need to read the string (more generic, works with literals, `String`, `&String`). Use `String` when you need ownership or mutability.

**R3** — *Medium*:  
- **Borrowing**: Temporarily lending access to data via references.  
- **Borrow checker**: Enforces the rules at compile time:  
  - **Shared borrows** (`&T`) can be multiple, but immutable.  
  - **Mutable borrows** (`&mut T`) are **exclusive** – no other references (shared or mutable) may coexist.  
- These rules prevent data races and dangling pointers at compile time.

**R4** — *Medium*:  
- **`Result<T, E>`**: Enum for success (`Ok(T)`) or error (`Err(E)`). Used for operations that can fail.  
- **`Option<T>`**: Enum for presence (`Some(T)`) or absence (`None`). Used for nullable values without `null`.  
- **`?` operator**: In a function returning `Result` or `Option`, `expr?` propagates `Ok`/`Some` value or returns `Err`/`None` early.  
- **Example**:
  ```rust
  use std::fs::File;
  use std::io::{self, Read};

  fn read_file(path: &str) -> Result<String, io::Error> {
      let mut f = File::open(path)?;               // propagate error
      let mut contents = String::new();
      f.read_to_string(&mut contents)?;            // propagate error
      Ok(contents)
  }
  ```

**R5** — *Medium*:  
- **`Box<T>`**: Heap allocation with ownership; size known at compile time (pointer). Used for trait objects, recursive types, or when you need to store a value but don’t know its size.  
- **`Rc<T>`**: Reference‑counted shared ownership (thread‑unsafe). Allows multiple owners; the value is dropped when the count reaches zero.  
- **`Arc<T>`**: Atomically reference‑counted version of `Rc`; safe for concurrent use across threads.  
- **When to use**:  
  - `Box` for moving large data to heap or for trait objects.  
  - `Rc` for single‑threaded sharing.  
  - `Arc` for sharing across threads.

**R6** — *Medium*:  
- **Traits**: Define a set of methods a type must implement. Similar to Go interfaces but with *associated types*, *default methods*, and *trait bounds*.  
- **Trait object (`dyn Trait`)**: An opaque pointer (`&dyn Trait`, `Box<dyn Trait>`) that can refer to any type implementing `Trait`. Enables heterogeneous collections and dynamic dispatch.  
- **Generic with trait bound (`T: Trait`)**: Static dispatch; the compiler generates concrete code for each type `T` used. More efficient, but the set of types is fixed at compile time.  
- **Key difference**: Trait objects → runtime dispatch, heap allocation; generics → compile‑time monomorphization, no runtime overhead.

**R7** — *Hard*:  
- **Compilation failure**: The function returns a reference to a local stack variable (`x` or `y`), which would dangle once the function returns.  
- **Fix with lifetimes**:
  ```rust
  fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
      if x.len() > y.len() { x } else { y }
  }
  ```
  The `'a` lifetime parameter states that the returned reference lives at least as long as both inputs.  
- **Alternative**: Return an owned `String` or `Box<str>` if you need to own the result.

**R8** — *Hard*:  
- **`Send`**: Marker trait indicating a type is safe to transfer across thread boundaries (the runtime can move it to another thread).  
- **`Sync`**: Marker trait indicating a type is safe to share between threads (i.e., it can be `&T` across threads).  
- **`Rc<T>`**: Not `Send` nor `Sync` because its reference count is updated with non‑atomic `usize` operations; sharing across threads would cause data races.  
- **`Arc<T>`**: Implements both `Send` and `Sync` because its internal counter uses atomic operations, making concurrent access safe.

**R9** — *Hard*:  
- **Async/await**: Syntactic sugar over the **Future** trait. An `async fn` returns a `impl Future<Output = T>`. The compiler transforms it into a state machine.  
- **Future**: A `poll`‑based computation that can be resumed later. It returns `Poll<T>` (`Ready(T)` or `Pending`).  
- **Executor**: A runtime (e.g., Tokio, async‑std) that repeatedly calls `poll` on ready futures, driving them to completion. Unlike Go’s goroutines (which are preemptively scheduled by the runtime), Rust futures are **cooperatively** scheduled; a future must `await` to yield control.  
- **Difference**: Go’s model is *M:N* threading with a preemptive scheduler; Rust’s model is *explicit* via executors and relies on the programmer to `await` to avoid blocking the thread.

**R10** — *Medium*:  
- **`unsafe`**: Bypasses Rust’s safety guarantees; the compiler trusts the programmer.  
- **Three things you can do only in `unsafe`**:  
  1. Dereference raw pointers (`*const T`, `*mut T`).  
  2. Call `unsafe` functions or FFI (foreign functions).  
  3. Access or modify `union` fields (except the first).  
- **When justified**: Interfacing with C libraries, implementing low‑level data structures (e.g., custom allocators), or when you can prove memory safety through external reasoning (e.g., using `pin` safely). Always minimize the `unsafe` block and document the invariants.

**R11** — *Easy*:  
- **Pattern matching** via `match` exhaustively checks a value against patterns.  
- **`match` vs `if let`**: `match` requires handling all possible patterns (or a `_` wildcard); `if let` is a concise guard for a single pattern, ignoring others.  
- **Exhaustiveness**: The compiler ensures every possible value is covered, preventing accidental missed cases (e.g., enum variants).

**R12** — *Easy*:  
- **`Vec<T>`**: Dynamically sized, growable array on the heap. Manages its own capacity; when `push` exceeds capacity, it allocates a larger buffer (often doubling) and copies existing elements.  
- **Array `[T; N]`**: Fixed size known at compile time, stored on the stack (unless placed in a box or behind a pointer). Cannot change length.  

**R13** — *Easy*:  
- **Enums**: Algebraic data types that can hold variants, each possibly with different data. Unlike C/Java enums (simple integer constants), Rust enums can carry values and define methods.  
- **`Option<T>`**: `Some(T)` or `None`. Provides a safe alternative to `null`/`nullptr`, forcing explicit handling of the “absent” case via pattern matching or helper methods (`unwrap`, `expect`, `map`, etc.).

**R14** — *Easy*:  
- **`impl` block**: Groups method and associated function definitions for a type or trait.  
- **Method receivers**:  
  - `&self` – immutable borrow (read‑only access).  
  - `&mut self` – mutable borrow (can modify the instance).  
  - `self` – consumes the value (used for moving types or defining destructor‑like behavior).  
- **Associated functions** (`Self::new()`): Do not take `self`; they are called on the type itself, often as constructors.

**R15** — *Easy*:  
- **`derive` macro**: Automatically generates boilerplate trait implementations (`Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, `Default`, `Serialize`, etc.).  
- **When you cannot derive**: If the trait requires custom logic, has conflicting implementations, or the type contains fields that the trait’s default behavior doesn’t support (e.g., `Ord` on a struct without a total order). You must implement the trait manually or write a custom derive proc‑macro.

**R16** — *Medium*:  
- **`Cow<'a, T>` (Clone On Write)**: An enum (`Owned`, `Borrowed`) that may contain a borrowed reference or an owned value. It avoids cloning until a mutation is needed.  
- **Use case**: API that may need to return a value either from a cache (borrowed) or compute and store a new one (owned).  
- **Example**:
  ```rust
  use std::borrow::Cow;

  fn maybe_clone(s: &str) -> Cow<str> {
      if s.len() > 100 {
          Cow::Owned(s.to_owned())
      } else {
          Cow::Borrowed(s)
      }
  }
  ```
  This avoids an unnecessary allocation for short strings.

**R17** — *Medium*:  
- **Module system**: Organizes code into a hierarchy.  
  - **`mod`**: Declares a module; can be in the same file or a separate `.rs` file (e.g., `mod foo;` looks for `foo.rs` or `foo/mod.rs`).  
  - **`use`**: Brings names into scope (`use std::collections::HashMap;`).  
  - **`pub`**: Exposes items outside the module.  
- **File‑system mapping**: In the 2015 edition, `mod.rs` was required; in the 2018 edition, the directory name itself can serve as a module (`src/mylib/mod.rs` → `src/mylib.rs`).  
- **Changes**: The 2018 edition relaxed the `mod.rs` requirement and introduced more flexible `use` paths (`use crate::foo;`, `use super::bar;`).

**R18** — *Hard*:  
- **`Pin<T>`**: Wraps a type to guarantee that it will not be moved after being placed at a certain memory location. Used for self‑referential structs and async futures.  
- **Why needed**: In async, a future may contain pointers to its own fields (e.g., a `struct` holding a buffer and a cursor). Moving the future would invalidate those pointers, causing UB. `Pin` prevents the move.  
- **`Unpin`**: Marker trait indicating a type is safe to move even when pinned. Most types implement `Unpin` automatically; those that don’t (e.g., custom self‑referential futures) must handle pinning explicitly.

**R19** — *Hard*:  
- **Macro system**: Two main kinds:  
  - **Declarative macros** (`macro_rules!`): Hygienic, pattern‑based rewriting. Define reusable syntax constructs (`vec!`, `format!`).  
  - **Procedural macros** (`#[derive(...)]`, `#[attribute]`, function‑like `my_macro!(..)`): Compile‑time functions that take token streams and produce token streams. Implemented as separate crates with `proc-macro` crate type.  
- **Hygiene**: Ensures that identifiers inside a macro do not clash with the surrounding code (e.g., generated variables are scoped correctly). Declarative macros are hygienic by default; procedural macros must use the `syn`/`quote` libraries to preserve hygiene.

**R20** — *Hard*:  
- **Zero‑cost abstractions**: Rust’s design goal that abstractions (generics, traits, iterators, etc.) compile down to as efficient code as hand‑written equivalents, with no runtime overhead.  
- **How achieved**:  
  - **Generics & monomorphization**: The compiler generates concrete code for each type used, eliminating virtual dispatch.  
  - **Iterators**: Implemented via *zero‑overhead* `next` calls; the iterator’s logic is inlined, and loops are unrolled where possible.  
  - **Trait static dispatch**: When the trait is known at compile time (e.g., `T: Display` with a concrete `T`), methods are called directly; when using trait objects (`dyn Display`), dynamic dispatch occurs but is limited to those cases.  
- The result is high‑level, expressive code that compiles to performance comparable to C/C++ while retaining safety guarantees.
