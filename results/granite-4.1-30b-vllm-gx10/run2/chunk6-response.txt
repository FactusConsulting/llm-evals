**JavaScript / TypeScript**

**JS1** — *var, let, const & hoisting*  
- **var**: function-scoped (or global if outside a function) and **hoisted** – the declaration is moved to the top of its scope, but initialization stays.  
- **let** & **const**: block-scoped. They are also hoisted, but are in a *temporal dead zone* from the start of the block until the actual declaration line – accessing them earlier throws a `ReferenceError`.  
- **const** additionally enforces that the binding cannot be reassigned (the object it points to can still be mutated unless it’s a primitive).  
- **Hoisting** means the parser lifts declarations to the top of their containing scope, but for `let`/`const` the initialization is not hoisted, so you cannot use them before the `let`/`const` line.

**JS2** — *Event loop, call stack, microtask & macrotask queues*  
- The **event loop** continuously checks the **call stack**. If the stack is empty, it processes pending tasks from two queues:  
  - **Macrotask queue** (also called the task queue): holds callbacks from timers (`setTimeout`, `setInterval`), I/O, UI rendering, etc. Each macrotask runs to completion before the next one starts.  
  - **Microtask queue**: holds promises’ `.then`/`.catch` handlers, `queueMicrotask`, `MutationObserver` callbacks, etc. After each macrotask finishes, the loop drains the microtask queue (running each microtask to completion) before moving to the next macrotask.  
- This ordering ensures that promise resolutions happen **before** the next timer or rendering event, providing a predictable execution order.

**JS3** — *Closures, classic for‑loop bug, fix*  
- A **closure** is a function that retains access to its lexical scope even after the outer function has returned.  
  ```js
  function makeCounter() {
    let n = 0;
    return function() { return ++n; }; // closure over n
  }
  const c = makeCounter();
  console.log(c()); // 1
  console.log(c()); // 2
  ```
- **Classic for‑loop closure bug**:  
  ```js
  for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i)); // all log "3"
  }
  ```
  Because `var` is function‑scoped, there’s a single `i` shared by all iterations; by the time the callbacks run, the loop has finished and `i` is `3`.  
- **Fixes**:  
  1. Use **`let`** (block‑scoped) inside the loop – each iteration gets its own `i`.  
  2. Or create an **IIFE** per iteration:  
     ```js
     for (var i = 0; i < 3; i++) {
       (function(i) {
         setTimeout(() => console.log(i));
       })(i);
     }
     ```

**JS4** — *Promise, async/await, error handling, Promise.allSettled vs Promise.all*  
- **Promise**: an object representing the eventual completion (or failure) of an asynchronous operation. It has three states: pending, fulfilled, rejected.  
- **async/await**: syntactic sugar over promises. An `async` function always returns a promise; `await` pauses execution until the awaited promise settles.  
  ```js
  async function fetchUser() {
    try {
      const res = await fetch('/api/user');
      const data = await res.json();
      return data;
    } catch (e) {
      // handles both fetch rejection and JSON parsing error
      console.error(e);
    }
  }
  ```
- **Error handling**:  
  - With promises: `.catch()`, `Promise.all([...]).catch()`.  
  - With async/await: use `try { … } catch (err) { … }`. Uncaught exceptions become a rejected promise.  
- **Promise.all** vs **Promise.allSettled**:  
  - `Promise.all` fulfills only if **all** input promises fulfill; it **rejects** as soon as any promise rejects (the error is the first rejection).  
  - `Promise.allSettled` waits for **all** promises to settle and returns an array of objects `{ status: "fulfilled" | "rejected", value | reason }`. Useful when you need results of successful promises even if some fail.

**JS5** — *TypeScript interface vs type, discriminated unions*  
- **Interface**:  
  - Can be **extended** (`interface A extends B`) and **implemented** by classes.  
  - Allows **declaration merging** (multiple `interface Foo { … }` declarations combine).  
  - Primally used for defining **object shapes** and **class contracts**.  
- **Type**:  
  - Can describe **any** kind of type (unions, intersections, primitives, tuples, etc.).  
  - Cannot be extended with `extends` (but can use intersections).  
  - No declaration merging.  
- **When to use**:  
  - Use **interface** for public API shapes and when you expect extension/implementation.  
  - Use **type** for unions, intersections, utility types, or when the definition is not meant to be extended.  
- **Discriminated unions**: A set of object types that share a **common string (or number) literal property** (the *discriminant*). TypeScript can narrow based on that property.  
  ```ts
  type Shape =
    | { kind: 'circle'; radius: number }
    | { kind: 'square'; side: number };
  function area(s: Shape) {
    switch (s.kind) {
      case 'circle': return Math.PI * s.radius ** 2;
      case 'square': return s.side ** 2;
    }
  }
  ```

**JS6** — *Prototypal inheritance, Object.create(), ES6 classes*  
- JavaScript uses **prototype‑based inheritance**: objects have an internal `[[Prototype]]` link to another object. Property lookup walks this chain until `null`.  
- **Object.create(proto, [properties])** creates a new object with `proto` as its prototype. If `proto` is `null`, the object has no prototype (a “pure” object).  
  ```js
  const animal = { eats: true };
  const dog = Object.create(animal);
  dog.barks = true;
  console.log(dog.eats); // true (inherited)
  ```
- **ES6 classes** are syntactic sugar over the prototype mechanism. A class’s `prototype` property becomes the prototype of instances. Methods defined in the class body end up on the prototype, enabling shared method lookup.  
  ```js
  class Animal { constructor(name) { this.name = name; } speak() { console.log(`${this.name} makes a noise`); } }
  // Equivalent to:
  function Animal(name) { this.name = name; }
  Animal.prototype.speak = function() { /* … */ };
  ```
- Class inheritance (`extends`) sets the subclass’s prototype’s `[[Prototype]]` to the superclass’s prototype, preserving the prototype chain.

**JS7** — *`this` keyword, binding rules, `bind()`*  
- **Four binding rules (priority order)**:  
  1. **Explicit binding** via `call`, `apply`, or `bind`.  
  2. **Hard binding** (via `bind` that returns a new function).  
  3. **Implicit binding** (the object before the dot in a method call).  
  4. **Default binding** (global object in non‑strict mode, `undefined` in strict mode).  
- **`bind(target, …args)** returns a **new function** that, when called, has `this` permanently set to `target`. The returned function cannot be re‑bound to a different `this` (unless you `bind` the bound function again, creating another layer).  
  ```js
  const obj = { name: 'Alice' };
  function greet() { console.log(`Hello, ${this.name}`); }
  const bound = greet.bind(obj); // new function with this === obj
  bound(); // Hello, Alice
  // Re‑binding not possible directly; you’d need bound.bind(newObj)
  ```

**JS8** — *WeakRef & FinalizationRegistry, WeakMap keys*  
- **WeakRef**: holds a **weak reference** to an object, allowing the garbage collector (GC) to reclaim the object if there are no other strong references. The reference becomes **detached** when the object is collected. Useful for caches that should not prevent collection.  
- **FinalizationRegistry**: lets you register a **cleanup callback** (finalizer) that runs **after** an object is garbage‑collected. You register objects with `registry.register(target, heldValue, unregisterToken?)`. The callback receives `heldValue`.  
- **Why WeakMap keys must be objects**: WeakMaps store **weak references** to their keys. Only objects (including `null`) can be weakly held; primitives are boxed and thus strongly referenced, defeating the purpose. This ensures the key can be collected when no other strong refs exist, and the WeakMap entry disappears automatically.  
- **Use cases**:  
  - Implementing **ephemeral caches** that drop entries when the original object is no longer used.  
  - Building **observer patterns** where you don’t want to prevent the observed object from being GC’d.

**JS9** — *V8 optimizations: hidden classes, inline caching, deoptimization*  
- **Hidden classes (shapes)**: V8 assigns a hidden class to objects with the same property layout. When properties are added/removed consistently, the engine can generate highly optimized code assuming that shape. Inconsistent property order or dynamic additions cause a new hidden class, hurting performance.  
- **Inline caching (IC)**: V8 records the **type** of objects it sees at a particular property access site. If the next object has the same hidden class, it can **inline** the fast path (direct memory offset). Mismatches trigger a **cache miss** and may lead to deoptimization.  
- **Deoptimization**: When assumptions (e.g., hidden class, IC) are violated, V8 may **deoptimize** the optimized code, falling back to the interpreter or a slower optimized version.  
- **Patterns causing deoptimization**:  
  - Adding/removing properties after object creation.  
  - Using objects with **heterogeneous shapes** in the same loop.  
  - Mixing primitive and object types for the same property (e.g., sometimes `x` is a number, sometimes a string).  
  - Frequent **prototype mutations** (`Object.setPrototypeOf`).  
  - Using `delete` on properties that were previously accessed.

**JS10** — *Tree‑shaking, ES modules vs CommonJS*  
- **Tree‑shaking**: A build‑time optimization that eliminates **unused** exported declarations from the final bundle. It relies on **static analysis** of **ES module** syntax (`import`/`export`).  
- **ES modules**: Use **named exports** (`export const a = 1;`) and **static structure**; the parser can determine at compile time which imports are used. This enables tree‑shaking.  
- **CommonJS**: Uses **dynamic** `require()` and `module.exports = …`. The module’s exports are resolved at runtime, so static analysis cannot reliably tell which exports are used, making effective tree‑shaking impossible without additional heuristics (e.g., `sideEffects` flag in `package.json`).  
- **`"type": "module"`** in `package.json` tells Node.js to treat `.js` files as ES modules, enabling tree‑shaking when bundled with tools like Webpack, Rollup, or esbuild.

**JS11** — *null vs undefined, == vs ===, nullish coalescing & optional chaining*  
- **null**: intentional absence of any object value (explicitly set).  
- **undefined**: variable declared but not yet assigned, or property that doesn’t exist.  
- **Equality**:  
  - `==` performs **type coercion**; `null == undefined` is `true`.  
  - `===` is **strict**; `null === undefined` is `false`.  
- **Nullish coalescing (`??`)**: Returns the left operand if it is **not** `null` **and** not `undefined`; otherwise returns the right operand.  
  ```js
  const value = null ?? 'default'; // 'default'
  ```
- **Optional chaining (`?.`)**: Safely accesses properties/methods; if the left side is `null` or `undefined`, evaluation short‑circuits and returns `undefined`.  
  ```js
  const name = user?.profile?.name;
  ```

**JS12** — *map, filter, reduce, flatMap*  
- **map(callback)**: Transforms each element, returning a new array of the same length.  
  ```js
  [1,2,3].map(x => x * 2); // [2,4,6]
  ```
- **filter(predicate)**: Keeps elements for which `predicate` returns truthy.  
  ```js
  [1,2,3,4].filter(x => x % 2 === 0); // [2,4]
  ```
- **reduce(reducer, initialValue?)**: Accumulates a single value. `reducer(acc, cur, idx, arr)` is called for each element. If `initialValue` is provided, it becomes the first `acc`; otherwise the first array element is used and iteration starts at index 1.  
  ```js
  [1,2,3].reduce((sum, x) => sum + x, 0); // 6
  ```
- **flatMap**: A combination of `map` then `flat` of depth 1. Useful when the mapping function returns an array.  
  ```js
  [[1,2],[3,4]].flatMap(arr => arr.map(x => x * 2)); // [2,4,6,8]
  ```

**JS13** — *Template literals, tagged templates*  
- **Template literals** (`\`…\``) allow multi‑line strings and **expression interpolation** via `${expr}`.  
- **Tagged templates**: A function placed before the template literal receives an array of **raw strings** and the interpolated expressions.  
  ```js
  function htmlEscape(literals, ...subs) {
    let result = '';
    literals.forEach((lit, i) => {
      result += encodeURIComponent(lit);
      if (subs[i] !== undefined) result += encodeURIComponent(subs[i]);
    });
    return result;
  }
  const greeting = htmlEscape`<p>Hello, ${name}!</p>`;
  ```
  Use cases: HTML sanitization, SQL query building, i18n string formatting.

**JS14** — *Destructuring, rest operator*  
- **Object destructuring**: Extract properties into variables.  
  ```js
  const { a, b } = { a: 1, b: 2, c: 3 }; // a=1, b=2
  const { a, b = 5 } = { a: 1 }; // b=5 (default)
  const { a: localA } = obj; // rename
  ```
- **Array destructuring**: Extract by position.  
  ```js
  const [x, , z] = [1,2,3]; // x=1, z=3
  const [first, ...rest] = [1,2,3,4]; // first=1, rest=[2,3,4]
  ```
- **Rest operator (`...`)** in destructuring gathers remaining elements (array) or own enumerable properties (object) into a new array/object.  
  ```js
  const { a, ...others } = { a:1, b:2, c:3 }; // others={b:2,c:3}
  ```

**JS15** — *for…in vs for…of*  
- **for…in**: Iterates over **enumerable property keys** of an object (including inherited ones from the prototype chain). Primarily for **object** iteration.  
- **for…of**: Iterates over **values** of an **iterable** (arrays, strings, `Map`, `Set`, custom objects with `[Symbol.iterator]`). Does **not** include inherited properties.  
- **Why avoid for…in on arrays**: It yields numeric string keys (`"0"`, `"1"`, …) and may also enumerate non‑numeric properties added to `Array.prototype`, leading to unexpected behavior. Use `for…of` or `Array.prototype.forEach`.

**JS16** — *TypeScript generics, constraints, conditional & infer*  
- **Generics**: Parameterize types/functions to be reusable with different concrete types.  
  ```ts
  function identity<T>(arg: T): T { return arg; }
  ```
- **Generic constraints (`extends`)**: Restrict a type parameter to a base type or interface.  
  ```ts
  function getLogger<T extends HasId>(obj: T): string {
    return `ID: ${obj.id}`;
  }
  ```
- **Conditional types** (`T extends U ? X : Y`): Choose a type based on a condition.  
  ```ts
  type NonNullable<T> = T extends null | undefined ? never : T;
  ```
- **`infer` keyword**: Used inside a conditional type to **infer** a type variable from a context.  
  ```ts
  type ElementType<T> = T extends (infer U)[] ? U : T;
  // ElementType<string[]> → string
  ```
- **Practical example**:  
  ```ts
  type PromiseValueType<T> = T extends Promise<infer R> ? R : T;
  // PromiseValueType<Promise<number>> → number
  ```

**JS17** — *JavaScript module systems*  
- **CommonJS** (`require`, `module.exports`):  
  - **Dynamic**, **synchronously** loaded at runtime.  
  - Each module has its own `module` scope.  
  - Widely used in Node.js pre‑ESM era.  
- **ES Modules** (`import`, `export`):  
  - **Static** structure, analyzed at compile‑time, enabling tree‑shaking and cyclic dependency safety.  
  - Asynchronous loading in browsers; synchronous in some Node.js contexts when using `--experimental-modules` or `"type": "module"`.  
- **Node.js handling**:  
  - Files with `.mjs` or `"type": "module"` are treated as ESM.  
  - `.js` files are CommonJS by default, but can be mixed with `import` if the package is marked as a module and the host supports it.  
  - Interop: `import` can load CommonJS modules (Node wraps them), and `require` can load ESM via experimental `import()` function.  
- **`"type": "module"`** in `package.json` makes all `.js` files in the package treated as ES modules, encouraging modern tooling.

**JS18** — *TypeScript structural typing, excess property checks, extends vs satisfies, variance*  
- **Structural type system**: Compatibility is based on **member shape**, not declaration. Two objects are compatible if one’s members are a subset of the other’s.  
- **Excess property checks**: When assigning an object literal to a variable of an interface/type, TypeScript disallows properties not declared in the target type (prevents typos). This check can be bypassed with a **type assertion** or by using a **type index signature** (`[key: string]: any`).  
- **`extends` vs `satisfies`**:  
  - `extends` is used in **generic constraints** and **class/interface inheritance**.  
  - `satisfies` (introduced in TS 4.9) is a **type‑only operator** that asserts a value conforms to a type without affecting the inferred type. Useful for narrowing without creating a new type.  
    ```ts
    const user = { id: 1, name: 'Bob' } satisfies User;
    // typeof user is still { id: number; name: string }
    ```
- **Variance (in, out)** (TS 4.7+):  
  - **Covariant** (`out`) positions: return types, readonly properties. A more derived type can be used where a base type is expected.  
  - **Contravariant** (`in`) positions: parameter types, writeable properties. A base type can be used where a derived type is expected.  
  - **`in`/`out` keywords** let you annotate the variance of a generic parameter in a type:  
    ```ts
    type Pipe<in T, out R> = (value: T) => R;
    ```
  - This guides the type checker in safely assigning more/less specific types.

**JS19** — *Proxy & Reflect*  
- **Proxy**: Creates a **wrapper** object that can intercept and customize operations (property access, assignment, enumeration, function calls, etc.) via a **handler** object containing traps.  
  ```js
  const target = { value: 42 };
  const handler = {
    get(trapTarget, prop, receiver) {
      console.log('accessed', prop);
      return Reflect.get(trapTarget, prop, receiver);
    },
    set(trapTarget, prop, val, receiver) {
      console.log('set', prop, 'to', val);
      return Reflect.set(trapTarget, prop, val, receiver);
    }
  };
  const proxy = new Proxy(target, handler);
  proxy.value; // logs "accessed value"
  proxy.value = 100; // logs "set value to 100"
  ```
- **Reflect** API: A built‑in object with methods that correspond to **proxy traps**. It provides a **standard way** to invoke the default behavior, avoiding manual implementation. Using `Reflect` inside traps ensures consistency with the language’s native semantics.  
- **Practical uses**:  
  - **Validation**: throw on invalid property assignment.  
  - **Logging/auditing**: record accesses.  
  - **Reactive data binding**: notify subscribers on get/set.  
  - **Lazy loading**: compute a property only on first access.  

**JS20** — *SharedArrayBuffer & Atomics, Web Workers*  
- **SharedArrayBuffer**: Allows **shared memory** between the main thread and workers (or between workers). It represents a raw byte buffer that can be accessed concurrently.  
- **Atomics**: Provides **atomic operations** (read‑modify‑write) on `SharedArrayBuffer` to prevent race conditions. Key methods:  
  - `Atomics.add`, `Atomics.sub`, `Atomics.and`, `Atomics.or`, `Atomics.xor`  
  - `Atomics.compareExchange` (CAS)  
  - `Atomics.wait`, `Atomics.notify` for **blocking** synchronization.  
- **Web Workers communication**:  
  - A worker can receive a `SharedArrayBuffer` via `postMessage(buffer, [buffer])`. The main thread and worker share the same memory region.  
  - **Ordering guarantees**: Atomics ensure a **happens‑before** relationship; operations are **sequentially consistent**.  
- **`Atomics.wait` / `Atomics.notify`**:  
  - `Atomics.wait(ab, index, value, timeout)` puts the calling thread into a **sleep** state until `Atomics.notify(ab, index, count)` is called or timeout expires. Useful for **condition variables**.  
  - The index is an element of an `Int32Array` view on the buffer; the value is the expected value to wait on.

**Bash**

**B1** — *$@ vs $*, "$@" vs "$"*  
- **$@**: Expands to the **positional parameters** as separate words, **preserving** each argument (even if empty or containing spaces).  
- **$***: Expands to a **single string** with the parameters joined by the first character of `IFS` (usually a space).  
- **"$@"**: Each parameter is **quoted**, preventing word splitting and pathname expansion; ideal for passing arguments to another command.  
- **"$\***: The whole joined string is quoted, resulting in **one argument** containing the concatenated parameters.

**B2** — *set -euo pipefail*  
- **`set -e`**: Exit immediately if a command exits with a non‑zero status (errors).  
- **`set -u`**: Treat unset variables as an error when referenced, causing the script to exit.  
- **`set -o pipefail`**: The pipeline’s exit status is that of the **rightmost command** that exited with a non‑zero status, rather than just the last command. This catches failures inside any pipeline stage.

**B3** — *$(command) vs `command`, $((expr)) vs expr*  
- **`$(command)`** (preferred): Command substitution that captures the **stdout** of `command` as a string. Supports nesting.  
- **`` `command` ``** (backticks): Older syntax for command substitution; less readable and cannot be nested easily.  
- **$((expression))**: Arithmetic expansion; evaluates a **integer arithmetic expression** and substitutes the result. Supports operators like `+`, `-`, `*`, `/`, `%`, bitwise, etc.  
- **`expr`**: External command for arithmetic and string operations. Slower, requires careful quoting, and has different syntax (e.g., spaces around operators). Use `$(( ))` for pure arithmetic.

**B4** — *Process substitution*  
- Syntax: `<(...)` or `>(...)`. Replaces a command with a **named pipe** (FIFO) or temporary file, allowing the command to read from or write to it as if it were a regular file.  
- **Example with `diff`**:  
  ```bash
  diff <(grep pattern file1) <(grep pattern file2)
  ```
  Here `grep` outputs to two anonymous FIFOs, and `diff` reads from them directly, without creating intermediate files.

**B5** — *Safe iteration over files with spaces*  
- `for f in $(ls)` splits on IFS (space, newline, tab) → breaks filenames with spaces.  
- **Safe approaches**:  
  ```bash
  # Using glob with null‑delimiter (requires IFS=$'\n' and read -r)
  shopt -s nullglob
  for f in *; do
    [[ -e "$f" ]] && echo "Processing $f"
  done
  ```
  Or with `find`:
  ```bash
  find . -maxdepth 1 -type f -print0 | while IFS= read -r -d '' f; do
    echo "Processing $f"
  done
  ```

**B6** — *Here document vs here string*  
- **Here document** (`<<EOF`): Reads **multiple lines** until the delimiter `EOF` is encountered.  
  ```bash
  cat <<EOF > file.txt
  Line 1
  Line 2
  EOF
  ```
- **Here string** (`<<<`): Supplies a **single string** as stdin to a command.  
  ```bash
  grep pattern <<< "some text with pattern"
  ```
- **`<<-EOF`**: Strips leading **tabs** from the delimiter, allowing indentation of the heredoc body for readability.

**B7** — *Redirection differences*  
- `cmd > file 2>&1`:  
  1. `>` redirects **stdout** (`1`) to `file`.  
  2. `2>&1` then **redirects stderr** (`2`) to **where stdout is currently going** (the file).  
  Result: both streams end up in `file`.  
- `cmd 2>&1 > file`:  
  1. `2>&1` first links stderr to stdout (stdout is still the terminal).  
  2. `> file` then redirects **stdout** to `file`, **but stderr remains linked to the original stdout** (the terminal).  
  Result: stdout goes to `file`, stderr stays on the terminal.  
- `cmd &> file`: Shorthand for `cmd > file 2>&1`; both streams go to `file`.

**B8** — *Safe lock‑file function*  
```bash
#!/usr/bin/env bash
lock_dir="/var/lock/myapp"
lock_file="${lock_dir}/lock"

acquire_lock() {
  mkdir -p "$lock_dir" || exit 1
  if ln -T "$lock_file" "$(mktemp -u "$lock_dir/.lock.XXXXXX")" 2>/dev/null; then
    # lock acquired
    return 0
  else
    echo "Lock held by another process" >&2
    return 1
  fi
}

release_lock() {
  rm -f "$lock_file"
}

cleanup() {
  release_lock
}
trap cleanup EXIT INT TERM

acquire_lock || exit 1
# ---- critical section ----
# do work
# -------------------------
```
- **Why `mkdir` (or `ln` into a lock directory) is preferred**: It is **atomic** on most filesystems; either the directory/link is created or it fails, preventing race conditions. Simple file creation (`touch`) is not atomic and can be overwritten by another concurrent instance.

**B9** — *Single vs double quotes vs no quotes*  
- **Single quotes** `''`: Treat **everything** literally; no variable expansion, no special characters.  
  ```bash
  echo '$HOME'   # outputs $HOME
  ```
- **Double quotes** `""`: Allow **variable and command substitution**, but backslashes still escape `$`, `` ` ``, `\`.  
  ```bash
  echo "$HOME"   # expands to user's home directory
  ```
- **No quotes**: Subject to **word splitting** (IFS) and **pathname expansion** (`*`, `?`).  
  ```bash
  echo $HOME *   # expands * to list of files
  ```
- **Example differences**:  
  ```bash
  var="hello world"
  echo $var      # two words: hello world
  echo "$var"    # one argument: hello world
  echo '$var'    # literal string: $var
  ```

**B10** — *File existence checks*  
- **`[ -e file ]`** or **`[[ -e file ]]`**: true if file exists (any type).  
- **`[ -d file ]`** / **`[[ -d file ]]`**: true if it is a directory.  
- **`[ -r file ]`** / **`[[ -r file ]]`**: true if readable by the current user.  
- **`[ ]`** (test command) is POSIX; **`[[ ]]`** is bash‑specific, supports pattern matching, no word splitting, and allows logical operators (`&&`, `||`).  

**B11** — *Special parameters $? $$ $! $#*  
- **`$?`**: Exit status of the **last command** (0 = success).  
- **`$$`**: PID of the **current shell**.  
- **`$!`**: PID of the **most recent background job**.  
- **`$#`**: Number of **positional parameters** passed to the script/function.  
- **Use cases**:  
  - `$?` for error handling (`if [ $? -ne 0 ]; then …`).  
  - `$$` to generate unique temp file names.  
  - `$!` to wait for a specific background process (`wait $!`).  
  - `$#` to check required arguments (`if [ $# -lt 2 ]; then …`).

**B12** — *Functions in bash*  
- **Definition**: `function foo() { … }` or `foo() { … }` (both valid). The `function` keyword is optional but explicit.  
- **Return values**: Use `return <num>` (0‑255) for status; for string/array results, **print** them and **capture** with command substitution or **global variables**.  
  ```bash
  foo() { echo "result"; return 42; }
  val=$(foo)   # val = "result"
  foo; rc=$?   # rc = 42
  ```
- **Scope**: Functions inherit the caller’s environment but **local** variables can be declared with `local var=value` to avoid side effects.

**B13** — *PATH, command resolution, builtins vs externals*  
- **`PATH`**: Colon‑separated list of directories where the shell looks for executables.  
- **Resolution**: Shell first checks **aliases**, then **functions**, then **builtins**, then searches `PATH` for an executable.  
- **Builtin**: Implemented inside the shell (e.g., `cd`, `echo`). Faster, no fork.  
- **External**: Separate executable on disk (e.g., `/bin/ls`).  
- **Check**: `type cmd` shows whether it’s a builtin, alias, or file. `command -v cmd` prints the resolved path (or “builtin”).

**B14** — *trap*  
- **Syntax**: `trap 'commands' SIGNALS`.  
- **Common signals**: `EXIT` (always runs on normal exit or error), `ERR` (when a command fails in a pipeline or with `set -e`), `INT` (Ctrl‑C), `TERM` (termination request).  
- **Example cleanup**:  
  ```bash
  cleanup() {
    rm -f "$tempfile"
    echo "Cleanup done"
  }
  trap cleanup EXIT INT TERM
  ```
- **Execution order**: If multiple traps are set for the same signal, the **most recent** one replaces the previous unless you chain them (`trap 'old; new' SIG`). Signals arriving while a trap is running are **queued** and handled after the current trap finishes.

**B15** — *xargs vs command substitution, parallel execution*  
- **xargs**: Reads items from stdin and **invokes** a command with as many arguments as fit (or `-n` to limit). Handles **null‑delimited** input via `-0` (useful with `find -print0`).  
  ```bash
  find . -name '*.log' -print0 | xargs -0 gzip
  ```
- **Command substitution** `$()` builds a **single command line**; not suitable for very long argument lists (shell may hit ARG_MAX).  
- **Parallel (`-P`)**: `xargs -P N` runs up to `N` jobs concurrently.  
  ```bash
  printf '%s\n' *.txt | xargs -P 4 -I {} sh -c 'process "{}"'
  ```
- **Error handling**: `xargs -P` runs jobs in parallel; failures are reported but do not stop other jobs unless you add `-t` (dry‑run) or check `$?` after each invocation.

**B16** — *Bash arrays & associative arrays*  
- **Indexed array**:  
  ```bash
  arr=(a b c)
  arr[2]=d        # replace
  arr+=('e')      # append
  for v in "${arr[@]}"; do echo "$v"; done
  echo "${#arr[@]}"   # length
  ```
- **Associative array** (requires `declare -A`):  
  ```bash
  declare -A map
  map[key1]=value1
  map[key2]=value2
  for k in "${!map[@]}"; do echo "$k=${map[$k]}"; done
  echo "${#map[@]}"   # number of key/value pairs
  ```
- **Differences**: Indexed arrays are **ordered** and accessed by numeric indices; associative arrays are **unordered** (as of Bash 4) and accessed by string keys. Both support compound assignment and parameter expansion tricks (`${arr[@]}`, `${!arr[@]}`).

**B17** — *Subshell vs group command*  
- **Subshell** `(...)`: Commands run in a **child process**; variable changes, directory changes, and exit status are **not** propagated to the parent.  
  ```bash
  (cd /tmp; echo "PWD=$PWD")   # PWD inside subshell, parent unchanged
  ```
- **Group command** `{ ...; }`: Runs in the **current shell**; no new PID. Variable changes persist, but the block must be followed by a **semicolon** or newline before the closing brace.  
  ```bash
  { a=5; }; echo $a   # a is 5 in parent
  ```
- **While loop & pipe**: `somecommand | while read line; do …; done` executes the `while` body in a **subshell**, so variable assignments inside are lost after the loop. Use `while read line; do …; done` **without** the pipe or redirect the whole block into a subshell that exports variables if needed.

**B18** — *Signals, job control*  
- **SIGINT** (Ctrl‑C): Interrupt signal; default action is to terminate. Can be caught to perform cleanup.  
- **SIGTERM** (termination request): Polite request to exit; default is to terminate. Allows graceful shutdown.  
- **SIGHUP** (hangup): Often used by daemons to **reload config** or restart. Default is to terminate.  
- **SIGKILL** (9): Cannot be caught, blocked, or ignored; forces immediate termination.  
- **Graceful shutdown**:  
  ```bash
  trap 'echo "Shutting down"; cleanup; exit' INT TERM
  # start background jobs
  some_long_running_job &
  wait   # wait for all jobs
  ```
  Ensure background jobs also handle signals or are terminated via `kill -TERM $!`.

**B19** — *Parallel log processing script*  
```bash
#!/usr/bin/env bash
set -euo pipefail

INPUT="large.log"
TMPDIR=$(mktemp -d)
trap "rm -rf '$TMPDIR'; exit" EXIT INT TERM

# Split log into N chunks
N=4
split -l $(( $(wc -l < "$INPUT") / N )) "$INPUT" "$TMPDIR/part_"

# Process each chunk in parallel, writing results to $TMPDIR/
process_chunk() {
  local part=$1
  # Example: grep errors and count
  grep "ERROR" "$part" | wc -l > "${part}.cnt"
}
export -f process_chunk

printf '%s\n' "$TMPDIR"/part_* |
  xargs -n 1 -P "$N" -I {} bash -c 'process_chunk "$@"' _ {}

# Merge results
awk '{sum+=$1} END {print "Total errors:", sum}' "$TMPDIR"/part_*.cnt
```
- **Performance trade‑offs**: Splitting avoids huge memory usage; parallel `xargs -P` utilizes CPU cores. However, I/O contention on disk can become a bottleneck; using a RAM‑based temp directory (`/dev/shm`) can help. Error propagation: any `process_chunk` failure (non‑zero exit) aborts the script because of `set -e`; you can add `|| true` if you want to continue despite failures.

**B20** — *exec vs normal command, file descriptor manipulation, coprocess*  
- **`exec`**: Replaces the current shell process with the specified command (no new process). Useful for **final command** in a script or to **redirect** all future output.  
  ```bash
  exec >output.log   # all subsequent stdout goes to output.log
  exec 3>file        # open file descriptor 3 for writing to file
  exec 3>&-          # close fd 3
  ```
- **File descriptor manipulation**:  
  - `exec {var}>&-` closes a descriptor.  
  - `exec {var}>file` assigns a new descriptor to a file.  
  - Useful for **named pipes**, **socket redirection**, or **passing descriptors** to child processes.  
- **Coprocess**: `coproc CMD` starts `CMD` in a background process and sets up **bidirectional** communication via file descriptors `COPROC[0]` (read) and `COPROC[1]` (write).  
  ```bash
  coproc myproc { nc -l 127.0.0.1 12345; }
  echo "Hello" >&${COPROC[1]}
  read -u ${COPROC[0]} line
  echo "Received: $line"
  ```
  Use cases: long‑running helper processes, interactive protocols, or when you need to both send and receive data without spawning separate pipes manually.

**PowerShell**

**PS1** — *Write-Output vs Write-Host*  
- **`Write-Output`** (alias `Write`/`echo`): Sends objects to the **success output stream** (`stdout`). They become part of the pipeline and can be captured, filtered, or exported.  
- **`Write-Host`**: Writes directly to the **host** (console) **without** using the output streams. The text is **not** captured by `Out-File`, `|` pipeline, or `Start-Transcript`. Use for UI messages that should not interfere with data flow.  

**PS2** — *Pipeline, ForEach-Object vs foreach*  
- **Pipeline (`|`)**: Objects flow from left to right; each cmdlet processes one object at a time (streaming).  
- **`ForEach-Object`** (alias `foreach`, `%`): A **cmdlet** that works in the pipeline, executing a script block for each input object.  
- **`foreach` statement**: A **language construct** that iterates over a **collection** that is already materialized (e.g., an array). It does **not** stream; the entire collection is loaded into memory first.  
- **When to use**:  
  - Use **`ForEach-Object`** when you want to stay in the pipeline and process objects lazily.  
  - Use **`foreach`** when you have a concrete collection and need classic loop control (break, continue) or index access.

**PS3** — *[PSCustomObject] vs [hashtable]*  
- **`[PSCustomObject]`**: Creates an object with **named properties** that appear as regular object members. Good for **structured output** that can be formatted, exported (CSV/JSON), or piped.  
  ```powershell
  $o = [PSCustomObject]@{Name='Alice'; Age=30}
  $o.Name   # Alice
  ```
- **`[hashtable]`**: A key‑value map. Useful for **lookup tables**, temporary data, or when you need mutable key‑value pairs. Not directly serializable to CSV without conversion.  
- **Conversion**:  
  - Hashtable → PSCustomObject: `[PSCustomObject]$ht`  
  - PSCustomObject → Hashtable: `$o | Get-Member` → use `foreach` to build a hashtable or `$o.psobject.Properties | ForEach-Object @{ $_.Name = $_.Value }`.  

**PS4** — *Error handling: terminating vs non‑terminating, -ErrorAction, $ErrorActionPreference, try/catch*  
- **Terminating errors**: By default, cmdlets throw **terminating** exceptions that stop the pipeline (e.g., `Get-ChildItem -Path 'nonexistent'`).  
- **Non‑terminating errors**: Some errors are **recorded** but allow the pipeline to continue (e.g., `Write-Error -NonTerminating`).  
- **`-ErrorAction`** parameter: Controls how a cmdlet reacts (`SilentlyContinue`, `Stop`, `Continue`, `Inquire`). Overrides the session preference for that call.  
- **`$ErrorActionPreference`**: Global default for error action when not specified. Commonly set to `Stop` in scripts to treat all errors as terminating.  
- **`try/catch`**:  
  ```powershell
  try {
    Get-Item -Path 'missing' -ErrorAction Stop
  } catch {
    Write-Error "File not found: $_"
  }
  ```
  `catch` only catches **terminating** errors. Use `trap` for **non‑terminating** errors or set `-ErrorAction Stop` to promote them.

**PS5** — *Splatting (@params)*  
- **Splatting** allows passing a collection of arguments as if they were listed individually.  
  ```powershell
  $params = @{ Path = 'C:\logs'; Filter = '*.log'; Recurse = $true }
  Get-ChildItem @params
  ```
- **Difference from passing a hashtable**: When you pass a hashtable **directly** as a single argument, the cmdlet receives one object. Splatting expands the hashtable into **named parameters** matching its keys.  
- **Use case**: Building dynamic parameter sets, especially when some parameters are optional.

**PS6** — *PowerShell remoting, Invoke-Command vs Enter-PSSession*  
- **Remoting**: Uses **WinRM** (Windows Remote Management) by default; PowerShell 7+ also supports **SSH** remoting.  
- **`Invoke-Command -ComputerName …`**: Executes a script block **remotely** and returns results to the local session. Ideal for **one‑off** or batch commands.  
- **`Enter-PSSession -ComputerName …`**: Opens an **interactive** session where commands typed locally are executed remotely, with output streamed back. Useful for exploration.  
- **Protocol**: WinRM uses **HTTP/HTTPS**; SSH uses **SSH**. Both support **credential delegation** (CredSSP) for double‑hop scenarios.  

**PS7** — *Type system, pipeline behavior, correct pattern*  
- **Snippet analysis**:  
  ```powershell
  function Get-Items {
      $result = @()
      $result += "one"
      return $result
  }
  $x = Get-Items
  $x.GetType().Name   # What is this?
  ```
  - `$result` is initialized as an **array** (`@()`). Adding a string with `+=` keeps it an array.  
  - When the function returns **one or more objects**, PowerShell places them in the **pipeline** as individual elements. However, because the function explicitly **returns** the array, the array object itself is emitted.  
  - **Result**: `$x` is of type **`Object[]`** (an array of strings).  
  - **If the function returns 0 items** (`$result = @(); return $result`), the pipeline still emits an **empty array** (`Object[]`), not `null`.  
  - **Correct pattern** for functions that may return zero or many items: **do not use `return`**; let the function **implicitly** output. Use `Write-Output $result` or simply `$result` at the end. This ensures the pipeline semantics (array vs single object) are handled correctly.  

**PS8** — *[scriptblock] vs function, passing to remote, double‑hop*  
- **Scriptblock** (`[scriptblock]`): A **code snippet** that can be stored, passed around, and invoked later (`& $sb`). Captures its **current scope** (variables) unless explicitly made **self‑contained** (`[scriptblock]::Create(...)`).  
- **Function**: Named, defined with `function` or `filter`. Can have **parameters**, **advanced features** (`CmdletBinding`, `Begin/Process/End`).  
- **Passing to remote**: Use `Invoke-Command -ComputerName … -ScriptBlock $sb`. The scriptblock is serialized and executed on the remote side.  
- **Double‑hop problem**: When a remote session tries to authenticate to a **third** machine, standard Kerberos delegation fails. Solutions:  
  - **CredSSP**: Delegates the client’s credentials to the remote server, allowing it to act on behalf of the user. Enable with `Enable-WSManCredSSP -Role Server -DelegateComputer "*"` and client config.  
  - **`Invoke-Command -ComputerName A -ScriptBlock { Invoke-Command -ComputerName B -Credential $cred … }`**: Pass explicit credentials (`$cred = Get-Credential`) to the second hop.  

**PS9** — *@() vs [array], indexing $null vs []*  
- **`@()`**: The **array subexpression** operator. Forces the evaluation of its contents into an **array**, even if there is a single element or none.  
  ```powershell
  $a = @('one')          # $a is string[]
  $b = @(Get-Item .)     # $b is an array of FileInfo objects
  $c = @()               # empty array
  ```
- **`[array]`**: Cast operator that **converts** an object to an array if possible. If the object is already an array, it’s returned unchanged; if it’s a single scalar, it wraps it in an array.  
  ```powershell
  $x = 'hello'
  [array]$x   # @('hello')
  ```
- **Difference**: `@()` always produces an array (useful for guaranteeing array context), while `[array]` may be a no‑op if the operand is already an array.  
- **Indexing**:  
  - `$null[0]` throws an **error** (`Cannot index into a $null array`).  
  - `@()[0]` returns `$null` (accessing first element of an empty array).  
  - `''[0]` returns the first character of the empty string (also `$null`).  

**PS10** — *Comparison operators*  
- **`-eq`, `-ne`**: Equality and inequality (case‑insensitive for strings in PowerShell by default).  
- **`-ceq`, `-cne`**: Case‑sensitive variants.  
- **`-like`**: Wildcard matching (`*` matches any, `?` matches one). Case‑insensitive by default; `-clike` for case‑sensitive.  
- **`-match`**: Regex matching; returns a **boolean**. `-cmatch` for case‑sensitive.  
- **`-contains`, `-in`**:  
  - `-contains`: Tests if **left** (a collection) **contains** the **right** element.  
    ```powershell
    'a','b','c' -contains 'b'   # true
    ```
  - `-in`: Tests if **left** element **is in** the **right** collection.  
    ```powershell
    'b' -in 'a','b','c'         # true
    ```
  - They are opposites in terms of operand order.  

**PS11** — *PowerShell modules*  
- **Script module** (`.psm1`): Contains PowerShell code (functions, classes, variables). Loaded with `Import-Module`.  
- **Manifest module** (`.psd1`): A metadata file describing a module (including nested script modules, required modules, exported members). Powershell treats it as the module entry point.  
- **Binary module** (`.dll`): Contains .NET types and cmdlets compiled to C#. Loaded via `Import-Module` as well.  
- **`Import-Module`**: Reads the module file(s), executes the script (if any), and makes exported members available in the session. It respects the `ModuleToProcess` key in a manifest.  

**PS12** — *String interpolation, here‑strings*  
- **Double‑quoted strings** (`"..."`): Support **variable expansion** (`$var`) and **subexpressions** (`$(...)`).  
  ```powershell
  $name = 'Alice'
  "Hello, $name"          # Hello, Alice
  "Count: $(Get-Date)"    # Count: <current date>
  ```
- **Single‑quoted strings** (`'...'`): Treat content literally; no expansion.  
- **Here‑string** (`@"..."@`): Multi‑line string preserving line breaks and allowing interpolation (if double‑quoted).  
  ```powershell
  $template = @"
  <html>
    <body>
      <h1>$title</h1>
    </body>
  </html>
  "@
  ```
- **Difference**: Here‑strings avoid escaping quotes and backticks, ideal for scripts, configs, or HTML/JSON payloads.  

**PS13** — *Get‑Member, Select‑Object vs Where‑Object*  
- **`Get-Member`** (`gm`): Inspects an object’s members (properties, methods, notes).  
  ```powershell
  Get-Process | Get-Member
  ```
- **Properties vs Methods vs NoteProperties**:  
  - **Properties**: Simple data fields (`Name`, `Id`).  
  - **Methods**: Callable actions (`Kill()`, `Start()`).  
  - **NoteProperties**: Script properties added via `Add-Member -NotePropertyName`.  
- **`Select-Object`**: Projects **specific properties** (or creates calculated ones) from objects.  
  ```powershell
  Get-Process | Select-Object Name, Id
  ```
- **`Where-Object`** (`?`): Filters objects based on a script block condition.  
  ```powershell
  Get-Process | Where-Object { $_.CPU -gt 10 }
  ```
- **Key difference**: `Select-Object` **transforms** the output shape; `Where-Object` **filters** the input stream.  

**PS14** — *PowerShell classes (v5+)*  
- Introduced to define **.NET‑like** types directly in PowerShell.  
- **Differences from C#**:  
  - No explicit `public`/`private` keywords (all members are public by default; use `[Hidden]` attribute to hide).  
  - Limited **inheritance**: single base class only, no interfaces.  
  - Constructors are defined with a **scriptblock** named `constructor`.  
  - No support for **properties with getters/setters** beyond auto‑implemented properties.  
- **When to use**: When you need **strongly typed objects** for complex data structures, DSC resources, or when integrating with .NET code. For simple data, `[PSCustomObject]` or hashtables are often sufficient.  

**PS15** — *CmdletBinding, advanced functions*  
- **`[CmdletBinding()]`**: Turns a normal function into an **advanced function**, enabling:  
  - **Common parameters** (`-Verbose`, `-Debug`, `-ErrorAction`, `-WarningAction`, `-OutVariable`, `-OutBuffer`).  
  - **Parameter validation** attributes (`[ValidateNotNullOrEmpty]`, `[ValidateRange]`, etc.).  
  - **`SupportsShouldProcess`** for **WhatIf/Confirm** support.  
  - **`DefaultParameterSetName`** to disambiguate parameters.  
  - **`ValueFromPipeline`** / **`ValueFromPipelineByPropertyName`** for automatic parameter binding.  
- **`Begin/Process/End` blocks**:  
  - **Begin**: Runs once before any input is processed (good for setup).  
  - **Process**: Runs once per pipeline object (the main work loop).  
  - **End**: Runs after all input is processed (cleanup, final output).  

**PS16** — *PowerShell providers*  
- Providers expose **drive‑like** access to different data stores (FileSystem, Registry, Certificate, Environment, Alias, Function, Variable, etc.).  
- **`Get-ChildItem`** works uniformly:  
  ```powershell
  Get-ChildItem HKLM:\Software\MyCo   # Registry
  Get-ChildItem Cert:\LocalMachine\My # Certificates
  Get-ChildItem Env:                 # Environment variables
  ```
- **Accessing registry like a file system**: Use the `Registry:` drive. Navigation (`Set-Location`, `Push-Location`) and cmdlets (`New-Item`, `Remove-Item`, `Set-ItemProperty`) operate analogously to file system cmdlets.  

**PS17** — *Runspaces, parallel execution*  
- **Runspace**: An isolated execution environment for PowerShell code. A **runspace pool** manages a collection of runspaces for parallel work.  
- **`[powershell]`**: Represents a **script block** executed within a runspace. You can invoke it synchronously (`Invoke()`) or asynchronously (`BeginInvoke()`).  
- **`ForEach-Object -Parallel`** (PowerShell 7+): Simplifies parallel processing by automatically distributing items across runspaces in the current pool.  
  ```powershell
  Get-ChildItem | ForEach-Object -Parallel {
      $_.Length
  }
  ```
- **Manual runspace management** is needed for more control (e.g., custom error handling, shared state via `System.Collections.Concurrent.BlockingCollection`).  

**PS18** — *PSScriptAnalyzer*  
- Static code analysis tool that enforces **best practices** and **style guidelines**.  
- **Rules**: Predefined checks (e.g., `PSAvoidUsingWriteHost`, `PSUseShouldProcessForStateChangingFunctions`). Each rule has a **severity** (`Error`, `Warning`, `Information`).  
- **Custom rules**: Defined in a JSON/YAML file and loaded via `-CustomRulePath`.  
- **Suppressing**: Use `#pscriptanalyzer:disable <RuleName>` comment or configure the rule severity to `None`.  
- **CI/CD integration**: Run `Invoke-ScriptAnalyzer` in build pipelines; fail the build on errors or treat warnings as needed.  

**PS19** — *Variable scoping: $using:, $args, -ArgumentList, serialization limits*  
- **`$using:`**: In **parallel** scopes (`ForEach-Object -Parallel`, `workflow`, `runspace`), allows **capturing** variables from the outer scope by value (shallow copy).  
  ```powershell
  $path = 'C:\logs'
  $list = Get-ChildItem $path | ForEach-Object -Parallel {
      $using:path   # accessible here
      $_.FullName
  }
  ```
- **`$args`**: Automatic array containing **positional parameters** passed to a script or scriptblock when no explicit parameter list is defined.  
- **`-ArgumentList`** (`-ArgList`): When using `Invoke-Command`, `Start-Job`, or `Register-ObjectEvent`, you can pass **values** that become either `$using:` variables (in parallel) or `$args` (in scriptblocks without parameters).  
- **Serialization limits**: Objects sent to remote sessions or jobs are serialized as **CLIXML**. Deeply nested objects, custom .NET types without `[Serializable]` attributes, or circular references may exceed the default depth (typically 2). Use `-AsJob` with simple types or convert complex objects to `[PSCustomObject]`/hashtables before passing.  

**PS20** — *Desired State Configuration (DSC)*  
- **DSC** is a **declarative** management platform. You write **configuration scripts** that describe the desired state of a node.  
  - **Configuration**: A PowerShell function that calls `Node` blocks to define resources per machine.  
  - **Resources**: Modules implementing `Get-`, `Set-`, `Test-` functions for a specific component (e.g., `xWindowsFeature`, `File`).  
  - **Local Configuration Manager (LCM)**: The agent on each node that applies configurations, performs consistency checks, and reports status.  
- **Windows PowerShell vs PowerShell 7+**:  
  - In **Windows PowerShell**, DSC is tightly integrated with the OS and supports many built‑in resources.  
  - In **PowerShell 7**, DSC is **cross‑platform** (Linux, macOS) but some Windows‑specific resources are unavailable. Community modules (`xPSDesiredStateConfiguration`, `SqlServerDsc`) fill gaps.  
- **Modern IaC alternatives**: Tools like **Terraform**, **Ansible**, **Chef**, or **Azure ARM/Bicep** have largely supplanted DSC for infrastructure provisioning, though DSC remains useful for **operating‑system configuration** and **compliance** on Windows servers.
