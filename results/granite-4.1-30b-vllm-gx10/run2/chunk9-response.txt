**SC1 – Medium – Broken Deployments After Cluster Upgrade**

**SC1‑A**  
The pods fail because the new **Restricted** Pod Security Standard enforces stricter security defaults than the previous **Baseline** policy.  
- **Restricted** requires `runAsNonRoot: true` **and** an explicit `runAsUser` (or a non‑root default UID) for any container that does not already run as a non‑root user.  
- The manifests set `securityContext.runAsNonRoot: true` but leave `runAsUser` undefined.  
- The newly rebuilt images (`cgr.dev/chainguard/static:latest`) declare `USER root` in their Dockerfile. When Kubernetes creates the container, the runtime first applies the image‑level `USER` (root) and then evaluates the pod‑level `runAsNonRoot`. Because the container is effectively running as root, the Restricted PSP rejects the pod, causing it to be terminated and restarted → **CrashLoopBackOff**.  
- **Baseline** would have allowed a non‑root request without a `runAsUser`, so the same manifests worked before the upgrade.

**SC1‑B**  
```bash
kubectl get pods --all-namespaces -o json \
| jq -r '.items[]
        | select(.status.phase=="Running" and .status.containerStatuses[].lastState.terminated!=null and .status.containerStatuses[].lastState.terminated.reason=="CrashLoopBackOff")
        | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.containers[].securityContext}'
```
This one‑liner:
1. Retrieves all pods across namespaces.  
2. Filters for pods whose last container termination reason is `CrashLoopBackOff`.  
3. Emits a JSON object containing the namespace, pod name, and the `securityContext` block of each container.

**SC1‑C**  
**Immediate remediation**  
1. **Image‑level fix** – Rebuild the Go and Python images with a non‑root user defined in the Dockerfile (e.g., `USER 1001`) **or** add a `USER` directive that matches a non‑root UID.  
2. **Manifest changes** – Add `securityContext.runAsUser: <non‑root UID>` (e.g., `1001`) to every container spec that has `runAsNonRoot: true`.  
3. **Rollout without downtime** – Use a rolling update (`kubectl rollout restart deployment/<name>`) after applying the updated manifests. Because the pods are recreated with the correct UID, the Restricted PSP will admit them, and the CrashLoopBackOff will stop.

**Prevent recurrence**  
- **CI gate**: Add a pre‑merge step that runs `kube-score` or `conftest` with a policy checking that any pod with `runAsNonRoot: true` also specifies `runAsUser`. Fail the build if the check fails.  
- **Image scanning**: Integrate Trivy or Syft + Grype to flag containers whose `USER` is `root` when `runAsNonRoot` is required.  
- **Policy as Code**: Store the Pod Security Standard enforcement in a GitOps repo (e.g., using OPA/Gatekeeper) so future changes are automatically validated.

**SC2 – Hard – Cross‑Region Database Failover Gone Wrong**

**SC2‑A**  
*Stale data* occurs because the promoted read replica was **asynchronously** replicating WAL from the primary in us‑east‑1. When the replica is promoted, it becomes the new primary but may still be behind by the amount of WAL not yet shipped.  
- **Streaming replication** in PostgreSQL ships WAL files over the network. Cross‑region latency (≈85 ms) plus any network congestion can cause a lag of seconds to minutes.  
- **Data‑loss scenarios**: If the primary fails before the replica has received the latest WAL, any transactions committed after the last shipped WAL are lost.  
- **Quantifying the window**:  
  - Check `pg_stat_replication` on the old primary (if still reachable) for `pg_last_wal_replay_lsn` vs. `pg_current_wal_lsn`.  
  - On the new primary, run `SELECT pg_last_wal_replay_lsn();` and compare to the LSN at failover time (captured via `pg_controldata` or a timestamped log).  
  - The difference in bytes/LSN gives the exact data‑loss window.

**SC2‑B**  
1. **Import the promoted replica**  
   ```bash
   terraform provider "aws" alias=eu {
     region = "eu-west-1"
   }
   terraform import aws_db_instance.promoted_replica arn:aws:rds:eu-west-1:123456789012:db:mydb-replica
   ```
2. **Detach the old instance from state** (without destroying)  
   ```bash
   terraform state rm aws_db_instance.old_primary
   ```
3. **Update dependent resources** – Use `terraform state mv` to re‑associate security groups, parameter groups, and Route53 records to the new instance. Example for a security group:
   ```bash
   terraform state mv aws_security_group.rds_sg aws_security_group.rds_sg
   ```
   Then adjust the `aws_route53_record` data source to reference the new DB endpoint:
   ```hcl
   data "aws_route53_record" "db_endpoint" {
     zone_id = aws_route53_zone.example.id
     name    = "db.example.com"
     type    = "CNAME"
   }
   ```
   Finally, run `terraform plan` – Terraform will now show **no destroy/create** actions because the resources are already in the desired state; only the DB ARN reference changes.

**SC2‑C**  
**Proposed zero‑downtime, <1 s RPO architecture**  

| Component | Recommended Solution | Rationale |
|-----------|----------------------|-----------|
| **Connection pooling** | **RDS Proxy** (instead of PgBouncer) | Proxy is managed, automatically reconnects to the new primary, and works natively with Aurora Global Database. |
| **DNS failover** | **Route53 health checks + latency‑based routing** with **failover policy** (primary → replica) | Health checks detect loss of primary; DNS TTL set to 30 s ensures quick client redirection. |
| **Application retries** | Implement **exponential back‑off + idempotent writes** in the app layer | Guarantees that transient connection errors during switchover are retried safely. |
| **Database engine** | **Amazon Aurora Global Database** (or multi‑master Aurora Serverless v2) | Provides sub‑second replication across regions with <1 s RPO and automatic failover; eliminates manual promotion. |
| **Monitoring** | Continuous `pg_replication_slots` and `pg_stat_replication` metrics feeding into CloudWatch Alarms | Immediate alert on replication lag > 1 s. |

**Why Aurora Global?**  
- Built‑in **fast, low‑latency cross‑region replication** (WAL shipping over AWS backbone).  
- **Automatic failover** with no manual promotion, reducing human error.  
- Supports **read/write endpoints** that stay constant; the DNS record only points to the endpoint, not the instance ARN.

**SC3 – Medium – Container Image Supply Chain Compromise**

**SC3‑A**  
**Immediate incident response**  

1. **Containment (without destroying evidence)**  
   ```bash
   # Identify compromised pods
   kubectl get pods -A -o json | jq -r '.items[] | select(.metadata.annotations["falco/alert"]!=null) | .metadata.name'
   # Capture process tree inside a compromised container
   kubectl exec -it <pod> -- /bin/sh -c "pstree -p"
   # Capture network connections
   kubectl exec -it <pod> -- /bin/netstat -tunap
   # Capture filesystem diff (requires root in container)
   kubectl exec -it <pod> -- /bin/sh -c "tar cf - . | gzip > /tmp/fs_snapshot.tar.gz"
   # Move snapshot out (e.g., to a secure bucket)
   kubectl cp <pod>:/tmp/fs_snapshot.tar.gz ./fs_snapshot_<pod>.tar.gz
   # Pause the pod to stop further damage (does not terminate)
   kubectl scale deployment/<deploy> --replicas=0
   ```
   - Use `kubectl debug` if the container lacks a shell.  
   - Ensure the node’s audit logs (`/var/log/audit/audit.log`) are preserved.

2. **Evidence preservation** – Snapshot the node’s disk (if on cloud) or create a forensic image of the compromised container’s rootfs before any deletion.

**SC3‑B**  
```python
#!/usr/bin/env python3
import requests, json, subprocess, sys

# Config
CI_DIGEST = "sha256:3f2a1c7e9d..."          # extracted from CI build log
BASE_IMAGE = "node:20-slim"
ECR_REGISTRY = "123456789012.dkr.ecr.us-east-1.amazonaws.com"
API_GATEWAY_IMG = "api-gateway:v2.4.1"

def get_upstream_digest(image: str, tag: str = "latest"):
    url = f"https://registry.hub.docker.com/v2/{image}/tags/{tag}"
    # Docker Hub public API (unauthenticated for public images)
    r = requests.get(url)
    if r.status_code != 200:
        raise RuntimeError(f"Failed to fetch tag {tag} for {image}")
    manifest_url = r.json()["results"][0]["manifest_digest"]
    # Second call to get manifest details
    url = f"https://registry.hub.docker.com/v2/{image}/manifests/{manifest_url}"
    r = requests.get(url, headers={"Authorization": f"Bearer {''}"})  # public
    return manifest_url

def get_ecr_image_layers(repo: str, tag: str):
    # Assume ECR token already configured or use AWS CLI
    out = subprocess.check_output(
        ["aws", "ecr", "batch-get-image", "--repository-name", repo,
         "--image-ids", f"imageTag={tag}", "--output", "json"]
    )
    data = json.loads(out)
    manifest = data["images"][0]["imageManifest"]
    # The manifest is usually Docker Schema v2; layers are in imageManifest
    return [layer["mediaType"] for layer in data["images"][0]["imageManifest"].get("layers", [])]

def main():
    upstream_digest = get_upstream_digest(BASE_IMAGE)
    print(f"Upstream node:20-slim digest = {upstream_digest}")

    layers = get_ecr_image_layers("api-gateway", API_GATEWAY_IMG)
    print("Layers in api-gateway:v2.4.1:")
    for l in layers:
        print(" -", l)

    # Simple flag: if any layer digest differs from known‑good (hard‑coded list)
    known_good = {
        "sha256:deadbeef1...",
        "sha256:deadbeef2...",
        # ... populate from a previous trusted build
    }
    unexpected = [l for l in layers if l not in known_good]
    if unexpected:
        print("⚠️ Unexpected layers detected:", unexpected)
    else:
        print("✅ All layers match known‑good set.")

if __name__ == "__main__":
    main()
```
- The script pulls the **current upstream digest** for `node:20-slim` from Docker Hub, compares it to the digest recorded in the CI log, and lists the layer digests of `api-gateway:v2.4.1`. Any layer not present in a curated “known‑good” set is flagged.

**SC3‑C**  
**Hardened CI/CD pipeline**  

1. **Image signing** – Use **Cosign** (Sigstore) to sign every image at build time. The CI job runs:  
   ```bash
   cosign sign --key $COSIGN_PRIVATE_KEY $ECR_REGISTRY/api-gateway:v2.4.1
   ```
   The signature is stored as an annotation on the image manifest.

2. **Admission control** – Deploy **OPA Gatekeeper** (or **Kyverno**) with a policy that:
   - Requires `cosign.sigstore` annotation to exist.  
   - Verifies the signature against a trusted public key stored in a ConfigMap.  
   - Rejects any container whose base image tag is used (enforce digest pinning).

3. **Base‑image pinning** – In the Dockerfile, reference the base image by **digest**, e.g.:
   ```dockerfile
   FROM node@sha256:3f2a1c7e9d...
   ```
   The CI job extracts the digest from the upstream registry and injects it into the Dockerfile via a template.

4. **SBOM generation** – Integrate **Syft** to produce a CycloneDX or SPDX SBOM for each image and store it in an artifact repository. The admission controller can also cross‑check SBOM entries against a deny‑list of vulnerable components.

5. **Notary v2** – While Cosign is the primary signer, **Notary v2** can be used as a **multi‑signature** store that aggregates Cosign signatures and additional attestations (e.g., vulnerability scan results). The Kubernetes admission webhook can query Notary v2 to ensure all required attestations are present before allowing the pod to run.

**Result:** Any compromised base image or tampered build will fail the signature verification step, preventing the pod from being scheduled.

**SC4 – Hard – Migrating a Stateful Monolith to Kubernetes**

**SC4‑A**  
Top 5 blockers and solutions:

| # | Blocker | Why it’s a problem in K8s | Solution |
|---|----------|---------------------------|----------|
| 1 | **Sticky sessions via F5** (session affinity) | K8s Service objects provide **client‑IP based** session affinity, but the monolith stores sessions **in‑process** (memory). Scaling beyond a single pod loses session continuity. | Migrate session storage to an external store (e.g., Redis or Memcached) and refactor the app to read/write sessions there. |
| 2 | **Local NFS mount for uploads** (`/data/uploads`) | Pods cannot reliably mount host paths; NFS volume must be provisioned as a **PersistentVolume** with **ReadWriteMany** (RWX) access mode. | Create an NFS‑backed **StorageClass** (see SC4‑B) and update the app to use the mounted path via a **PersistentVolumeClaim**. |
| 3 | **On‑prem Oracle 19c** (single point of access) | Direct DB connections from pods may be blocked by network policies; also need HA and connection pooling. | Deploy an **Oracle client library** in the pod, use a **Kubernetes Service** (headless) to expose the DB, and optionally run a **sidecar** (e.g., pgBouncer‑like connection pool) or use **external‑lookup** via `service.alpha.kubernetes.io/tolerate-unbound-service-dns: "true"`. |
| 4 | **IBM MQ integration** (mainframe messaging) | MQ client libraries need reliable network; also need to handle **message durability** across pod restarts. | Run an **MQ client sidecar** or use **IBM MQ Container** as a separate deployment, expose via a Service, and configure the monolith to connect to the internal Service name. |
| 5 | **Monolith’s tight coupling to hardware (CPU, memory, licensing)** | The app may assume specific OS libraries or licensed binaries not container‑friendly. | Containerize the JVM/Java runtime, ensure all native libs are bundled, and negotiate **license mobility** with the vendor or use **license server** pod that the app queries. |

**SC5 – Medium – Mysterious Latency Spike in Microservices**

**SC5‑A**  
**Debugging roadmap**

1. **Istio metrics**  
   - `istio_requests_total` latency distribution per route (`checkout-service → inventory-service`).  
   - `istio_tcp_sent_bytes_total` and `istio_tcp_received_bytes_total` for network health.  
   - `envoy_cluster_upstream_rq_pending_total` (queue length) and `envoy_cluster_upstream_rq_time_ms` (upstream processing time).  

2. **Kubernetes**  
   - `kubectl top pods` for CPU/Memory (already normal).  
   - `kubectl describe pod <inventory>` to see events or restarts.  
   - `kubectl logs <inventory>` for any error messages around 14:00.  

3. **Application logs** (structured JSON) – correlate timestamps with the spike.  

4. **Distributed tracing (Jaeger/Zipkin)**  
   - Query traces for the checkout request during 14:00‑14:30.  
   - Look at **span duration** for the `inventory-service` call.  
   - If the **client‑side** (checkout) span shows long “waiting for upstream” but the **server‑side** span is short, the delay is in the network or Envoy queue.  
   - If the server‑side span itself is long, the problem is inside inventory.  

5. **Envoy metrics to differentiate**  
   - `cluster_external_localhost_7000_rq_pending_total` (requests queued in Envoy) → high value ⇒ proxy‑level throttling.  
   - `cluster_external_localhost_7000_upstream_rq_time_ms` (time spent waiting for the upstream) → high value ⇒ inventory app latency.  

**SC5‑B**  
**PostgreSQL diagnostic query** (shows lock holders, waiters, and query text):

```sql
SELECT
    blocked.pid           AS blocked_pid,
    blocked.usename       AS blocked_user,
    blocked.query         AS blocked_query,
    blocked.query_start   AS blocked_start,
    now() - blocked.query_start AS blocked_duration,
    blocking.pid          AS blocking_pid,
    blocking.usename      AS blocking_user,
    blocking.query        AS blocking_query,
    blocking.query_start  AS blocking_start,
    now() - blocking.query_start AS blocking_duration
FROM
    pg_locks AS blocked
JOIN
    pg_stat_activity AS blocked
    ON blocked.pid = blocked.pid
JOIN
    pg_locks AS blocking
    ON blocking.locktype = blocked.locktype
   AND blocking.database = blocked.database
   AND blocking.relation = blocked.relation
   AND blocking.transactionid = blocked.transactionid
   AND blocking.virtualxid = blocked.virtualxid
   AND blocking.classid = blocked.classid
   AND blocking.objid = blocked.objid
   AND blocking.objsubid = blocked.objsubid
   AND blocking.pid <> blocked.pid
WHERE
    NOT blocked.granted
ORDER BY blocked.query_start;
```

**Go circuit‑breaker snippet (using sony/gobreaker):**

```go
package client

import (
    "context"
    "net/http"
    "time"

    "github.com/sony/gobreaker"
    "go.uber.org/ratelimit"
)

var invBreaker *gobreaker.CircuitBreaker

func init() {
    invBreaker = gobreaker.NewCircuitBreaker(gobreaker.Settings{
        Name:        "inventory",
        MaxRequests: 5,          // min # of requests before judging
        Interval:    60 * time.Second,
        Timeout:     10 * time.Second,
        ReadyToTrip: func(counts gobreaker.Counts) bool {
            return counts.Failures >= 5 // open circuit after 5 failures
        },
    })
}

func CallInventory(ctx context.Context, req *http.Request) (*http.Response, error) {
    // Wrap the HTTP call in the circuit breaker
    result, err := invBreaker.Execute(func() (interface{}, error) {
        client := &http.Client{Timeout: 2 * time.Second}
        return client.Do(req.WithContext(ctx))
    })

    if err != nil {
        // Circuit is open – return a fast failure
        return nil, err
    }
    return result.(*http.Response), nil
}
```
- The breaker trips after 5 consecutive failures, causing subsequent calls to fail fast (short‑circuit) and allowing the system to degrade gracefully.

**SC5‑C**  
**Architectural fix (CQRS + bulkhead + scheduling)**  

1. **Separate read/write paths**  
   - **Read model**: Deploy a **read‑replica** of the inventory DB (or a materialized view) that the checkout service queries.  
   - **Write model**: The nightly reconciliation job writes to the primary DB; it does **not** hit the read replica.  

2. **Bulkhead isolation**  
   - Use **HikariCP** (or similar) with **separate connection pools**: one pool for the checkout service (low max connections, short timeout) and another for the reconciliation job (larger pool, longer timeout). This prevents the job from exhausting the pool needed by the serving traffic.  

3. **CronJob scheduling**  
   - Move the reconciliation job to run **outside peak hours** (e.g., 02:00‑04:00 UTC) or split it into smaller incremental batches.  
   - Add **resource quotas** on the namespace: `requests.cpu`, `limits.cpu`, and a **PodDisruptionBudget** that guarantees at least N inventory pods are always running during the job.  

4. **Kubernetes safeguards**  
   - **PodDisruptionBudget** for `inventory` deployment: `minAvailable: 2` ensures at least two pods survive voluntary evictions (e.g., node maintenance).  
   - **HorizontalPodAutoscaler** with a custom metric (queue length) to auto‑scale inventory pods if the reconciliation job spikes CPU.  

5. **Observability**  
   - Emit a **custom metric** (`inventory_reconciliation_duration_seconds`) and set an alert if it exceeds a threshold, triggering automatic scaling or job throttling.  

Result: The checkout path never contends for DB connections or locks, eliminating the 30‑second latency spikes.

**SC6 – Hard – Zero‑Trust Network Overhaul for a Hybrid Environment**

**SC6‑A**  
**Identity & Access Layer Design**

1. **Workload identity** – Deploy **SPIRE** (the reference implementation of SPIFFE) on every node (on‑prem VMs, EC2, and Azure VMs).  
   - **On‑prem**: SPIRE agent runs as a systemd service, attests to the on‑prem PKI (e.g., HashiCorp Vault PKI).  
   - **AWS**: Use **AWS IAM Roles for Service Accounts (IRSA)** – SPIRE agent fetches an IAM token via the EC2 metadata service and registers the workload with a SPIFFE ID `spiffe://example.com/aws/<account>/<role>`.  
   - **Azure**: Leverage **Azure Managed Identities**; the SPIRE plugin translates the MSI token into a SPIFFE ID `spiffe://example.com/azure/<subscription>/<resourceGroup>`.  

2. **Federation** – Run a **central SPIRE server** (or a federation of servers) that trusts the three upstream CAs (on‑prem PKI, AWS IAM, Azure AD). The server issues **SPIFFE Verifiable Identity Documents (SVIDs)** that are JWTs signed by the respective CA.  

3. **Service‑to‑service authentication** – Use **mTLS** enforced by **Istio** (or **Cilium** in host‑mode) where each sidecar presents its SVID. The mesh policy (`PeerAuthentication`) requires **mtls: STRICT** and validates the SPIFFE URI against the federation policy.  

4. **Human identity** – Users authenticate via **SAML/OIDC** to Azure AD, then Azure AD issues **short‑lived access tokens** that are exchanged for SPIFFE SVIDs via a **token‑translation service** (e.g., OPA Gatekeeper). This enables **least‑privilege** API access from developer laptops or CI runners.  

5. **Policy enforcement** – **OPA** (or **OPA Gatekeeper**) evaluates **Authorization Policies** that reference the SPIFFE ID (`input.request.auth.principal`). Policies can be written as:
   ```rego
   allow {
       input.request.auth.principal == "spiffe://example.com/aws/123456789012/role/checkout-service"
       input.request.method == "GET"
       input.request.path == "/api/v1/orders"
   }
   ```
   This model eliminates reliance on network location.

**SC6‑C**  
**Bandwidth / failover options**

| Option | Cost (approx.) | Bandwidth | Encryption | Failover behavior | Zero‑Trust fit |
|--------|----------------|-----------|------------|-------------------|----------------|
| **AWS Direct Connect (DX)** | $0.25/GB + port fee (~$0.10 k per month) | Up to 10 Gbps (or 100 Gbps with multiple ports) | IPsec optional (native MACsec on DX) | Active‑active with BGP ECMP; automatic failover to secondary DX or VPN as backup | Ideal – dedicated private link, no internet exposure; can terminate at Transit Gateway and enforce mTLS at the application layer. |
| **Dual IPsec VPN + ECMP** | Low (VPN gateway hourly + data transfer) | 1 Gbps per tunnel; two tunnels ≈ 2 Gbps | IPsec (AES‑256) | BGP ECMP routes traffic across both tunnels; if one fails, traffic shifts instantly. | Works, but shared internet path introduces jitter and potential throttling; still compatible with zero‑trust if mTLS is enforced end‑to‑end. |
| **Hybrid mesh (Tailscale/Netbird)** | SaaS subscription (per node) | Depends on internet uplink (typically < 1 Gbps) | WireGuard (ChaCha20) | Automatic mesh failover; nodes self‑heal. | Good for dev‑ops laptops & edge devices, but not suitable for high‑throughput, regulated traffic between data centers; would need to run alongside DX for production. |

**Routing changes**  
- **Direct Connect**: Add a **BGP** session from the on‑prem router to the DX port; advertise the on‑prem CIDR blocks. The Transit Gateway will learn both DX and VPN routes; ECMP will split traffic.  
- **Dual VPN**: Configure **BGP** on both VPN gateways; set `maximum-paths` on the on‑prem router to use both tunnels.  
- **Mesh**: Deploy Tailscale agents on edge nodes; they automatically create overlay tunnels. For production traffic, keep DX as the primary backbone and use the mesh only for management/CI runners.

**Recommendation**: Deploy **Direct Connect** as the primary backbone (ensures predictable latency, meets compliance) and keep a **secondary IPsec VPN** as a fallback. The mesh can be used for developer laptops and CI agents.

**SC7 – Medium – CI/CD Pipeline Causing Production Drift**

**SC7‑A**  
1. **Manual `tofu apply`** – Running `terraform apply` outside the pipeline bypasses version control, locking, and review. If two engineers run it concurrently on the same state file, Terraform may **corrupt** the state (race condition) leading to lost resources or duplicate creations.  
2. **Divergent Helm values** – Staging and production values were edited locally (e.g., `values-prod.yaml`) and never committed. This creates **configuration drift**; future `helm upgrade` may overwrite production with stale values, causing outages.  
3. **Direct `kubectl edit` on ConfigMaps** – Editing resources in‑place bypasses GitOps, so the desired state in the repo no longer matches the cluster. If the ConfigMap holds critical config (e.g., feature flags), the cluster can behave unexpectedly, and rollbacks become impossible without manual intervention.

**SC7‑B**  
```yaml
# .gitlab-ci.yml

  - apply

    - terraform fmt -check

  stage: plan

    - terraform plan -out=tfplan.out

    - PLAN=$(terraform show -json tfplan.out | jq -c .)
    - curl -X POST -H "PRIVATE-TOKEN: $CI_JOB_TOKEN" \
        --data "comment=### Terraform Plan\n```json\n$PLAN\n```" \
```

**SC7‑C**  
**Drift detection & reconciliation system**

1. **Scheduled drift detection** – Add a **nightly GitLab CI job** that runs `terraform plan -refresh-only`. If the plan is non‑empty, fail the job and open a **GitLab issue** (via API) tagging the responsible team.  

2. **Admission webhook / OPA Gatekeeper** – Deploy an **OPA** policy that blocks any `PATCH`/`PUT` on `ConfigMap`, `Secret`, or `Deployment` resources that are managed by Terraform (identified by a label `managed-by=terraform`). The webhook returns a `403` with a message instructing users to change the manifest in Git.  

3. **Helm values governance** – Use **Helmfile** (or **Kustomize**) with a **single source of truth** `values.yaml` and environment‑specific overlays (`values-prod.yaml`, `values-staging.yaml`). Store the base file in the repo; overlays are version‑controlled. CI validates that no direct edits occur by comparing the rendered manifest (`helm template`) against the stored `*_rendered.yaml` artifact.  

4. **RBAC changes**  
   - **Kubernetes**: Create a **ClusterRole** `terraform-admin` with permissions `get, list, watch, create, update, delete` on all resources **except** those labeled `managed-by=terraform`. Bind this role to the CI service account. Regular developers get a role that **cannot** modify those resources.  
   - **AWS**: Restrict the CI IAM role to `terraform-state:*` on the S3 bucket and DynamoDB table only; deny `*` on other services. Use **IAM condition keys** to ensure the role can only assume the `terraform-exec` role via `sts:AssumeRole` from the CI runner’s instance profile.

Result: Drift is automatically surfaced, direct edits are blocked, and only changes flowing through the GitOps pipeline can affect production.

**SC8 – Hard – Observability Stack Scaling Failure**

**SC8‑A**  
| Symptom | Likely Root Cause | Diagnostic Check |
|---------|-------------------|------------------|
| **Prometheus OOM** | **Metric cardinality explosion** (8.2 M series) exceeds RAM; each series consumes memory for label sets and samples. | - Query `prometheus_tsdb_head_series` → should be ~8.2 M. <br> - Run `promtool tsdb list-label-values __name__` to see top metrics. <br> - Use `prometheus_adaptive_cardinality` (if enabled) or `prometheus_tsdb_wal_compression` metrics. |

| **Thanos compactor lag (3 days)** | **Compaction window too small** relative to ingestion rate; also limited CPU/IO on the compactor pod. | - `thanos_compactor_compaction_duration_seconds`. <br> - `thanos_compactor_series_to_process` metric. <br> - Check pod resource requests/limits. |

**SC8‑B**  
```bash
#!/usr/bin/env bash
set -euo pipefail

API="http://prometheus-operated:9090"
TOKEN="YOUR_PROM_TOKEN"   # if auth enabled

# 1. Total unique metric names
metric_names=$(curl -s -H "Authorization: Bearer $TOKEN" "$API/api/v1/label/__name__/values" | jq -r '.data | length')
echo "Total metric names: $metric_names"

# 2. Top 20 metrics by series count

        jq -r '.data[]' |
        while read -r name; do
            series=$(curl -s -G -H "Authorization: Bearer $TOKEN" \
                --data-urlencode "match[]={__name__=\"$name\"}" \
                "$API/api/v1/query" |
                jq '.data.result | length')
            echo "$name $series"
        done | sort -k2 -nr | head -20)

echo "Top 20 metrics by series count:"
echo "$top20" | column -t

# 3. Highest‑cardinality metric → label with most unique values
highest=$(echo "$top20" | head -1 | awk '{print $1}')
label_counts=$(curl -s -G -H "Authorization: Bearer $TOKEN" \
    --data-urlencode "match[]={__name__=\"$highest\"}" \
    "$API/api/v1/label" |
    jq -r '.data[] | "\(.name) \(.values | length)"' |
    sort -k2 -nr | head -1)

echo "Highest‑cardinality metric: $highest"
echo "Label with most unique values: ${label_counts%% *}, count=${label_counts##* }"
```

**SC8‑C**  
**Redesigned observability architecture**

1. **Metrics** – Replace single‑node Prometheus with a **Mimir** (or **VictoriaMetrics**) cluster (3 replicas) using **chunk storage** backed by **S3**.  
   - **Sharding** across nodes reduces per‑node series load.  
   - Enable **remote write** from Prometheus agents to Mimir, allowing horizontal scaling.  
   - **Cardinality governance**: Deploy **Prometheus Adapter** with **Recording Rules** that **drop** or **aggregate** high‑cardinality labels (e.g., `instance` → `job`). Enforce per‑team quotas via **OPA** policies that reject new label creation beyond a threshold.

2. **Logs** – Deploy **Loki** in **micro‑services mode**: separate **ingester**, **distributor**, and **querier** pods, each with **autoscaling** based on CPU and ingestion rate.  
   - Use **GCS/Blob** as the long‑term storage backend (instead of local SSD).  
   - Enable **chunk encoding** and **batch size** tuning to reduce drop rate.  

3. **Traces** – Switch Tempo to use **S3** as the **object store** with **partitioned buckets** (e.g., per day). Enable **compaction** with a **higher parallelism** setting and **increase the compactor pod resources**.  
   - Introduce **trace sampling** policies (e.g., 1% of requests) to limit ingestion volume.  

4. **Governance & Chargeback**  
   - **Per‑team quotas**: Use **Kubernetes ResourceQuotas** on the namespace level for `cpu`, `memory`, and a **custom metric** `observability_series_created`.  
   - **Billing**: Export the series count and storage usage (via Prometheus `prometheus_tsdb_head_series` and S3 storage class metrics) to a **cost‑allocation** pipeline (e.g., AWS Cost Explorer tags). Teams exceeding their quota receive alerts and are billed accordingly.  

5. **Scalability targets** – With sharding, the system can comfortably handle **50 M active series** (≈5 k series per node) and **200 teams** by distributing load and enforcing strict label policies.

**Defense‑in‑depth architecture**

1. **Authentication migration**  
   - **Short‑term**: Rotate all existing API keys, enforce header‑based `Authorization: Bearer <jwt>`.

2. **API Gateway** (Kong or AWS API Gateway) in front of the ALB:

3. **Logging & Auditing**  
   - Enable **CloudTrail Data Events** for S3/EC2 actions and **API Gateway** request logs.

4. **Field‑level encryption**  
   - Store PII columns (e.g., `internal_notes`) encrypted at rest using **AWS KMS** or **client‑side encryption** before persisting. The API layer decrypts only for authorized internal services.

5. **Rollback strategy**  
   - Keep the **API key** endpoint as a **fallback** for a limited grace period (e.g., 30 days).  
   - Use **feature flags** (LaunchDarkly/Unleash) to toggle between key‑based and JWT auth per client, allowing selective migration.

Result: The public API surface is hardened, secrets are no longer logged, and a clear path exists to retire legacy API keys without service disruption.

**SC10‑C**  
**Automated failover orchestration sequence**

1. **Failure detection**  
   - **Heartbeat monitor** (Prometheus + Alertmanager) watches a **custom metric** `site_up{site="chicago"}` exported by a small sidecar on each data‑center node.  
   - If the metric is absent for **> 30 s**, Alertmanager triggers a **runbook** (via webhook) indicating **site‑down**.

2. **DNS / GSLB switchover**  
   - Use **AWS Route 53** with **Failover** record sets (`alias` to the primary ALB).  
   - The webhook updates the **failover policy** to **“Fail to secondary”**, changing the TTL to 30 s so clients resolve the Dallas endpoint within minutes.

3. **PostgreSQL promotion**  
   - Patroni automatically detects the primary loss (via DCS) and **promotes** the Dallas standby to primary using `patroni promote`.  
   - Verify promotion with `SELECT pg_is_in_recovery();` → should return `false`.

4. **Redis Sentinel failover**  
   - Sentinel configuration on Dallas points to the Chicago master. Upon master failure, Sentinel elects the Dallas replica as new master and updates the client connection string (via the same Route 53 alias `redis.service.internal`).

5. **RabbitMQ queue mirroring**  
   - All **critical queues** are declared with `x-ha-policy: all` and `x-ha-policy-parameters: { "mirrored-node-list": ["chi-rabbit","dal-rabbit"] }`.  
   - When the Chicago node disappears, the Dallas node becomes the **master** for those queues automatically. Non‑critical queues can be recreated from backup if needed.

6. **MinIO site replication catch‑up**  
   - MinIO’s **DistSync** runs continuously; on failover, the Dallas site becomes the **leader**.  
   - Run `mc admin heal dal:` to force a final consistency check (should complete within the 15‑minute RPO window because the lag is bounded by the 12 ms network latency and the configured sync interval).

7. **OpenTofu state update**  
   - A **post‑failover job** (run via Ansible or a Lambda) updates the Terraform state S3 bucket’s `state_version` tag to reflect the new primary region.  
   - Subsequent `terraform plan/apply` runs will target the Dallas resources (e.g., update `aws_rds_cluster` endpoint, `aws_elb` DNS names).

8. **Split‑brain prevention**  
   - **Quorum** is enforced via **etcd** (3‑node cluster spanning both sites). A site cannot promote without majority.  
   - If both sites believe they are primary (unlikely due to network partition), the **etcd lease** expiration forces the stale leader to step down automatically.

9. **Fail‑back procedure** (once Chicago is restored)  
   - Restore Chicago services to **warm standby** (re‑enable replication, re‑join etcd).
