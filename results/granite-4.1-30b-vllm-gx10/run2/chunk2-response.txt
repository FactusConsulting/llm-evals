**Kubernetes**

**K1 — Easy:**  
- **Deployment**: Manages replicated, stateless pods. Pods are interchangeable; scaling, rolling updates, and rollbacks are handled automatically. Ideal for web servers, microservices, etc.  
- **StatefulSet**: Manages pods with a stable, unique network identity and persistent storage. Guarantees ordering in creation, scaling, and deletion. Used for databases, stateful applications where pod identity matters.

**K2 — Easy:**  
A Service of type **ClusterIP** creates an internal virtual IP that is only reachable within the cluster. Kubernetes populates the Service’s **Endpoints** object with the IPs of all pods matching the selector. The kube-proxy on each node programs iptables (or IPVS) rules that rewrite traffic destined for the Service IP to one of the endpoint IPs, performing load‑balancing.

**K3 — Medium:**  
- **PersistentVolume (PV)**: A piece of storage in the cluster provisioned by an administrator or dynamically via a **StorageClass**. It is a cluster‑wide resource.  
- **PersistentVolumeClaim (PVC)**: A request for storage by a pod. It binds to a matching PV (based on size, access modes, and optionally storage class). PVCs are namespace‑scoped.  
- **StorageClass**: Describes a class of storage (e.g., SSD, HDD) and defines the provisioner that creates PVs on demand. When a PVC requests a storage class, the cluster automatically provisions a PV of that class.  
Relationship: **PVC → PV** (binding) and **StorageClass** dictates how the PV is created when needed.

**K4 — Medium:** (4+ checks)  
1. **Logs**: `kubectl logs <pod>` to see crash messages or stack traces.  
2. **Events**: `kubectl describe pod <pod>` → look at *Events* for termination reasons (e.g., OOMKill, CrashLoopBackOff).  
3. **Readiness/Liveness probes**: Verify that the probes are correctly configured and that the app passes them.  
4. **Resource limits/requests**: Check if the pod is hitting memory or CPU limits causing OOM kills.  
5. **Container image pull**: Ensure the image can be pulled (`kubectl describe pod` may show `ErrImagePull`).  
6. **Config/Env**: Validate that required ConfigMaps, Secrets, or environment variables are present.

**K5 — Medium:**  
**CoreDNS** provides DNS service for the cluster, resolving service names (e.g., `mysvc.myns.svc.cluster.local`) to IPs. If CoreDNS pods are down:  
- New DNS queries fail → pods/services become unreachable by name.  
- Existing cached resolutions may still work temporarily.  
- The cluster becomes partially or fully non‑functional until CoreDNS recovers.

**K6 — Hard:**  
**Scheduling phases**:  
1. **Filtering (predicate)**: Eliminates nodes that don’t meet requirements (e.g., resource capacity, pod affinity/anti‑affinity, taint‑toleration, node selectors).  
2. **Scoring (priority)**: Ranks remaining nodes based on metrics (e.g., leastRequested, balancedResourceAllocation, nodeAffinityMatching).  
**Key factors considered**:  
- **Resource requests/limits** vs node capacity.  
- **Topology (zone/region) spreading** to ensure high availability.  
- **Pod affinity/anti‑affinity** rules.  
- **Taints & tolerations** (node must tolerate pod’s taints).  

**K7 — Hard:**  
- **Scheduling**: Node has 4 GB RAM, 3.5 GB already requested → only 0.5 GB free. The pod requests 256 Mi (0.25 GB), which fits, so the scheduler will place it.  
- **Runtime usage 600 Mi**: Exceeds the **limit** (512 Mi). The kernel will OOM‑kill the container, and the pod will restart (CrashLoopBackOff) unless the limit is raised or the app’s memory usage is reduced.

**K8 — Hard:** (Ingress → NGINX → Service → Endpoints → kube‑proxy)  
1. **External Load Balancer (LB)** routes external HTTP(S) traffic to the Ingress controller’s NodePort or LoadBalancer IP.  
2. **NGINX Ingress Controller** pod receives the request, consults its config (Ingress resources) to determine the backend Service and path.  
3. **Service (type ClusterIP)** is resolved via CoreDNS to its virtual IP.  
4. **Endpoints** object for the Service lists the IPs of the target pods.  
5. **kube‑proxy** on each node programs iptables (or IPVS) rules that rewrite traffic to the chosen endpoint IP/port, forwarding the request to the pod.  
6. The pod processes the request and returns the response through the reverse path.

**K9 — Medium:**  
- **NetworkPolicy**: Defines rules for ingress/egress traffic between pods.  
- **Default behavior** (no policy): **Allow all** traffic to/from pods in the namespace.  
- **Applying a policy** that selects certain pods: Only traffic matching the policy rules is permitted; all other traffic is blocked for those pods. Policies are additive and can be combined.

**K10 — Medium:**  
- **RollingUpdate**: Gradually replaces old pods with new ones (default: maxUnavailable=25%, maxSurge=25%). Ensures zero‑downtime for most workloads.  
- **Recreate**: Terminates all old pods before creating new ones. Causes a brief full outage.  
**Choose Recreate** when:  
  - The application cannot handle two versions simultaneously (e.g., stateful services with version‑specific data migrations).  
  - You need an all‑or‑nothing rollout (e.g., security patches that must be applied atomically).

**K11 — Easy:**  
A **namespace** provides a scope for names, isolating resources (pods, services, etc.) logically. Default namespaces in a fresh cluster: `default`, `kube-system`, `kube-public`.

**K12 — Easy:** (`kubectl describe pod <name>` shows)  
1. **Events** (creation, restarts, errors).  
2. **Container state** (waiting, running, terminated) with exit codes and reason.  
3. **Mounted volumes** and their source details.  
4. **Pod IP, QoS class, Node name, Annotations** – not displayed by `kubectl get`.

**K13 — Easy:**  
A **ConfigMap** stores non‑confidential key‑value config data. Pods can consume it via:  
- **Environment variables**: `envFrom` or `env` referencing the ConfigMap.  
- **Volume mount**: Mounted as a directory where each key becomes a file.  
- **Command args** (via `args: -config=$(CONFIGMAP_KEY)`).  

**K14 — Easy:**  
- **ClusterIP**: Exposes the Service only inside the cluster (default).  
- **NodePort**: Allocates a port on each node; reachable from outside via `<NodeIP>:<NodePort>`.  
- **LoadBalancer**: Requests an external cloud LB; provides a public IP that forwards to NodePorts.

**K15 — Easy:**  
A **DaemonSet** ensures exactly one pod runs on every (or selected) node, typically for node‑level daemons (logging, monitoring, network plugins). Use a DaemonSet instead of a Deployment when the workload must run once per node, regardless of scaling.

**K16 — Medium:**  
- **Taints** repel pods unless they have matching **tolerations**. They prevent scheduling of arbitrary pods on special nodes (e.g., GPU nodes).  
- **Node affinity** attracts pods to nodes based on labels (preferred or required).  
**Use cases**:  
  - **Taint**: `taint nodes gpu=true:NoSchedule` + toleration in GPU‑requiring pods.  
  - **Node affinity**: Schedule stateful workloads to nodes with SSD (`nodeAffinity: requiredDuringScheduling: {nodeSelectorTerms: …}`).

**K17 — Hard:**  
A **Kubernetes Operator** extends the API with custom resources and embeds domain‑specific operational logic in a controller. Unlike a standard controller (which only reconciles built‑in resources), an Operator encodes application‑level knowledge (e.g., backups, scaling, upgrades). It solves problems like: automated complex state management, versioned upgrades, and self‑healing for apps that aren’t natively declarative (databases, distributed caches).

**K18 — Hard:**  
- **etcd consistency**: Uses the **Raft consensus algorithm**; writes require majority (quorum) agreement. Reads can be **linearizable** (default) or **serializable** (snapshot reads).  
- **Quorum loss** (e.g., 2/3 nodes down in a 3‑node cluster): The cluster becomes **unavailable** for both reads and writes. Existing leader steps down; no new leader can be elected.  
- **Recovery from 2 permanent losses**:  
  1. **Recover the lost nodes** if possible (restore from backup).  
  2. **If not possible**, perform a **cluster reset**:  
     - Stop all kube‑apiserver instances.  
     - Start a new single‑node etcd cluster with `etcd --initial-cluster= new-node=http://new:2380`.  
     - Re‑initialize the Kubernetes control plane (apiserver, controller‑manager, scheduler) pointing to the new etcd.  
     - Restore data from the latest etcd backup (if any).  

**K19 — Hard:**  
**RBAC** (Role‑Based Access Control) grants permissions via:  
- **Role** (namespace‑scoped) or **ClusterRole** (cluster‑wide) defining allowed verbs on resources.  
- **RoleBinding** (namespace) or **ClusterRoleBinding** (cluster) binds subjects (User, Group, ServiceAccount) to those roles.  
**Read‑only access to pods & logs in `my-ns`**:  

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-ns
  name: pod-log-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: my-ns
  name: pod-log-reader-binding
subjects:
- kind: ServiceAccount
  name: my-sa
  namespace: my-ns
roleRef:
  kind: Role
  name: pod-log-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:**  
**ndots** in `/etc/resolv.conf` defines how many dots a name must have before it is treated as *absolute* and searched in the configured DNS search domains. A low `ndots` (e.g., 1) causes short names like `google.com` to be tried as `google.com.<search-domain>`, generating extra queries and latency.  
**Fix with `dnsConfig`**:  

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers: [{name: c, image: nginx}]
  dnsConfig:
    options:
    - name: ndots
      value: "2"   # treat names with >=2 dots as absolute
    nameservers:
    - 8.8.8.8
```

**Development**

**D1 — Easy:**  
- **git merge**: Creates a new merge commit that combines histories of two branches. Keeps the original branch commits intact.  
- **git rebase**: Rewrites history by replaying local commits on top of the target branch, producing a linear history.  
**Avoid rebasing** when the branch is public/shared (others have already pulled it) because it changes commit IDs and can cause confusion/conflicts.

**D2 — Easy:**  
- **TCP**: Connection‑oriented, reliable, ordered byte stream; guarantees delivery, retransmission, flow control.  
  - Protocols: HTTP, FTP, SSH.  
- **UDP**: Connectionless, best‑effort; no guarantee of delivery, ordering, or duplicate protection.  
  - Protocols: DNS, DHCP, RTP (media streaming).  

**D3 — Medium:**  
A **race condition** occurs when two or more threads/processes access shared data concurrently and the outcome depends on the nondeterministic timing of their execution.  
**Example (Python)**:  

```python
import threading

balance = 0
def deposit():
    global balance
    for _ in range(1000):
        balance += 1

threads = [threading.Thread(target=deposit) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(balance)   # Often < 10_000 due to lost updates
```

**D4 — Medium:**  
- **Symmetric encryption**: Same key for encryption & decryption (e.g., AES). Fast, used for bulk data.  
- **Asymmetric encryption**: Public/private key pair (e.g., RSA, ECDSA). Used for key exchange and digital signatures.  
**TLS handshake**:  
1. Client → Server: `ClientHello` (supported ciphers).  
2. Server → Client: `ServerHello`, server cert (public key), `ServerKeyExchange` (often RSA or ECDHE).  
3. Client verifies cert, generates **pre‑master secret**, encrypts with server’s public key, sends it.  
4. Both derive the same **master secret** using the pre‑master secret and ephemeral ECDHE keys → symmetric session keys (AES/GCM) for the rest of the session.

**D5 — Medium:**  
A **container image layer** is a read‑only filesystem representing changes (e.g., `RUN`, `COPY`). Images are built from a stack of layers; each layer is cached based on its instruction and the resulting filesystem state.  
**Best practices**:  
- Put commands that change often **later** in the Dockerfile (to maximize cache reuse).  
- Use multi‑stage builds to discard unnecessary layers.  
- Minimize layer count by combining related commands (`RUN apt-get update && apt-get install ... && rm -rf /var/lib/apt/lists/*`).

**D6 — Medium:** (4 checks for intermittent 503)  
1. **Pod health**: Verify liveness/readiness probes pass; check pod logs for crashes.  
2. **Service & Endpoints**: Ensure the Service has valid Endpoints (`kubectl get ep <svc>`).  
3. **Ingress/LoadBalancer**: Confirm the ingress controller is healthy and the external LB target ports are reachable.  
4. **Upstream dependency**: If the API calls another service, test that dependency (network, latency, auth).  
Order: start with pod health → service connectivity → ingress → downstream services.

**D7 — Hard:**  
**CAP theorem**: In a distributed system, you can have at most two of:  
- **Consistency (C)** – all nodes see the same data at the same time.  
- **Availability (A)** – every request receives a (non‑error) response.  
- **Partition tolerance (P)** – the system continues to operate despite network splits.  
**CP example**: **Cassandra** (tunable consistency) prefers consistency and partition tolerance; during a partition, it may reject writes to maintain consistency.  
**AP example**: **DynamoDB** (eventual consistency) accepts writes during partitions, favoring availability; consistency is reconciled later.

**D8 — Medium:**  
- **Horizontal scaling**: Adds more instances (pods, VMs) across identical machines. Requires stateless design, load balancers, and often a service mesh.  
- **Vertical scaling**: Increases resources (CPU, RAM) of an existing instance. Limited by hardware caps.  
**Patterns enabling horizontal scaling**:  
  - Stateless services / microservices.  
  - Shared‑nothing architecture.  
  - Use of distributed caches (Redis) and databases designed for sharding.  

**D9 — Easy:**  
An **environment variable** is a key‑value pair available to processes. To persist across sessions on Linux: add `export VAR=value` to `~/.bashrc` (or `~/.profile` for login shells) and reload the shell or open a new terminal.

**D10 — Easy:**  
- **JSON**: Lightweight, text‑based, strictly hierarchical (objects/arrays). Widely supported, fast parsing.  
- **YAML**: Superset of JSON, supports comments, more human‑readable with indentation.  
**Advantages**: JSON = simplicity & universal parser support; YAML = readability & expressive features (anchors, multi‑document streams).

**D11 — Easy:**  
A **REST API** uses HTTP methods to operate on resources identified by URIs.  
- **GET**: Retrieve a resource (idempotent, safe).  
- **POST**: Create a new resource (not idempotent).  
- **PUT**: Replace an existing resource entirely (idempotent).  
- **DELETE**: Remove a resource (idempotent).

**D12 — Easy:**  
**Version pinning** locks dependencies to specific versions (e.g., `package==1.2.3`). It ensures builds are reproducible, avoids surprise breakage from transitive updates, and simplifies debugging/auditing.

**D13 — Easy:**  
- **Compiled language**: Source code translated to machine code before execution (e.g., C, Go, Rust).  
- **Interpreted language**: Source code executed directly by an interpreter (e.g., Python, Ruby, JavaScript (Node)).  

**D14 — Medium:**  
A **reverse proxy** sits in front of servers, forwarding client requests to backend services and returning responses. It can perform load balancing, SSL termination, caching, and request transformation.  
A **forward proxy** sits on the client side, forwarding client requests to the internet and hiding the client’s identity.  
**Common reverse proxies**:  
- **NGINX**: High‑performance web server, load balancer, HTTP cache.  
- **HAProxy**: TCP/HTTP load balancer, ideal for high‑throughput scenarios.  
**Use case**: NGINX as an Ingress controller in Kubernetes; HAProxy for database connection pooling.

**D15 — Medium:**  
A **deadlock** occurs when a set of processes are each waiting for a resource held by another, forming a circular wait. The **Coffman conditions** are:  
1. **Mutual exclusion** – at least one resource is non‑shareable.  
2. **Hold and wait** – a process holds resources while waiting for others.  
3. **No preemption** – held resources cannot be forcibly taken.  
4. **Circular wait** – a circular chain of processes each waiting for a resource held by the next. All four must hold for a deadlock.

**D16 — Hard:**  
**Eventual consistency** guarantees that, given no new updates, all replicas will converge to the same value eventually.  
**Cassandra**: Uses **hinted handoff** and **read repair**. Consistency levels (ONE, QUORUM, ALL) let clients trade latency for freshness.  
- **Read‑after‑write**: Choose `QUORUM` for reads and writes to ensure the new value is visible.  
- **Tunable levels**: `ONE`, `TWO`, `THREE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`, etc., allowing applications to select the desired consistency vs. performance trade‑off.

**D17 — Hard:**  
**mTLS (mutual TLS)**: Both client and server present certificates and authenticate each other.  
**Handshake steps**:  
1. Client → Server: `ClientHello` (supported ciphers, extensions including `signature_algorithms`).  
2. Server → Client: `ServerHello`, server cert (public key), `ServerKeyExchange`, `CertificateRequest` (asking client for cert).  
3. Client verifies server cert against its trust store, generates **pre‑master secret**, encrypts with server’s public key, sends `ClientKeyExchange`.  
4. Client sends its own cert, signs a `Finished` message with its private key.  
5. Server verifies client cert, derives the same master secret, sends its `Finished`.  
**Common uses**: Service‑mesh (Istio, Linkerd), API gateways, internal microservice communication, VPN‑less secure RPC.

**D18 — Hard:**  
A **hash table** stores key‑value pairs using a hash function to compute an index into an array of *buckets*.  
- **Collision resolution**:  
  - **Chaining**: Each bucket holds a linked list (or dynamic array) of entries that hash to the same index.  
  - **Open addressing**: Probes alternative buckets (linear, quadratic, double hashing) until an empty slot is found.  
**Complexities**:  
- **Average case**: O(1) for insertion, lookup, deletion (assuming low load factor).  
- **Worst case**: O(n) if many collisions occur (e.g., all keys map to same bucket).  

**D19 — Hard:**  
**Circuit breaker** monitors failures in a remote service and *opens* (short‑circuits) calls to prevent cascading failures.  
- **Closed**: Normal operation; calls pass through, failure metrics are collected.  
- **Open**: Immediate failure response (e.g., fallback) for a timeout period.  
- **Half‑open**: After timeout, a limited number of test requests are allowed; if they succeed, the breaker closes; otherwise, it reopens.  
**Relation to retries**: Retries are often *disabled* while the circuit is open to avoid hammering a failing service. Exponential backoff is used for retries when the circuit is closed, to spread load during recovery.

**D20 — Hard:**  
- **Optimistic concurrency control (OCC)** assumes conflicts are rare. Each transaction reads a version; on commit, the system checks that the version hasn’t changed. If it has, the transaction aborts and must be retried.  
  - **Use case**: Web apps with form edits; `UPDATE table SET … WHERE id = ? AND version = ?`.  
- **Pessimistic concurrency control (PCC)** locks resources (row lock, table lock) before reading, ensuring no other transaction can modify them.  
  - **Use case**: Financial transactions where lost updates are unacceptable; `SELECT … FOR UPDATE` in PostgreSQL.  
**Choice**: Use OCC for high‑throughput, low‑contention workloads; use PCC when data integrity cannot be compromised and contention is expected.
