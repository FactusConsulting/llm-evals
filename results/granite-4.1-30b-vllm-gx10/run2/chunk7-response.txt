**Application Architecture**

**AA1** — *Monolith vs. Microservices*  
- **Monolith**: A single deployable unit containing all application logic, data access, and UI. Simpler to develop and deploy initially but becomes hard to scale, evolve, and maintain as it grows.  
- **Microservices**: Decompose the application into small, independently deployable services, each owning its data and exposing APIs. Benefits include independent scaling, technology heterogeneity, and team autonomy.  

**Three concrete problems introduced by microservices (not present in monoliths):**  
1. **Distributed Transactions & Data Consistency** – Managing ACID transactions across service boundaries requires patterns like Sagas or eventual consistency.  
2. **Operational Complexity** – Service discovery, configuration management, monitoring, and deployment pipelines become essential; failures can cascade.  
3. **Network Latency & Failure** – Inter‑service calls add latency and introduce partial failures (timeouts, retries) that must be handled gracefully (circuit breakers, retries, timeouts).  

**AA2** — *Synchronous vs. Asynchronous Communication*  
- **Synchronous**: Caller waits for a response (request‑response). Example: HTTP/REST, gRPC.  
- **Asynchronous**: Caller sends a message and continues without waiting; the receiver processes it later. Example: Message queues (RabbitMQ, Kafka), event buses.  

**AA3** — *API Gateway vs. Reverse Proxy*  
- **Reverse Proxy** (e.g., NGINX, HAProxy) forwards requests to backend services, providing load balancing, SSL termination, and basic routing.  
- **API Gateway** adds API‑specific concerns: request aggregation, protocol translation (REST → gRPC), authentication/authorization (OAuth2, JWT), rate limiting, request/response transformation, and analytics.  

**Can an API Gateway replace a reverse proxy?**  
- Partially. An API Gateway *includes* reverse‑proxy functionality but also brings higher‑level API management features. If you need only routing/SSL termination, a plain reverse proxy suffices. For comprehensive API‑centric control, an API Gateway is required.  

**AA4** — *Saga Pattern for Distributed Transactions*  
- A saga breaks a long‑running transaction into a series of local transactions, each with a compensating action to undo its effect if later steps fail.  

**Choreography‑based vs. Orchestration‑based:**  
- **Choreography**: Services react to events published by other services; no central coordinator. Simpler scaling, but harder to visualize the overall flow.  
- **Orchestration**: A central saga orchestrator (e.g., a workflow engine) sends commands to services and tracks progress. Easier to understand and debug, but introduces a coordination bottleneck.  

**When to use each:**  
- Use **choreography** for loosely coupled, event‑driven systems where services are autonomous.  
- Use **orchestration** when you need strict control over ordering, visibility, and error handling, or when the flow is complex.  

**AA5** — *CQRS (Command Query Responsibility Segregation)*  
- **CQRS** splits the model into *command* side (writes) and *query* side (reads), allowing each to be optimized independently (different data stores, scaling, security).  

**Why pair with Event Sourcing?**  
- Event sourcing stores state as an immutable sequence of events. CQRS benefits because the command side appends events, while the query side projects read models from those events. This combination provides:  
  - **Audit trail** (every change is an event).  
  - **Temporal queries** (replay events to any point in time).  
  - **Scalable reads** (materialized views can be denormalized for performance).  

**Problem solved vs. traditional CRUD:**  
- CRUD mixes read/write optimizations, leading to contention and limited scalability. CQRS + Event Sourcing decouples them, enabling high‑throughput writes and highly optimized, eventually consistent reads.  

**AA6** — *Circuit Breaker Pattern*  
- **States**:  
  1. **Closed** – Calls proceed normally; failure metrics are collected.  
  2. **Open** – Calls are short‑circuited (fail fast) after threshold breaches; a timeout period allows “half‑open” probing.  
  3. **Half‑Open** – Limited traffic is allowed to test if the downstream service recovered; if successful, the breaker closes; otherwise, it reopens.  

**Difference from simple retry with backoff:**  
- Retries attempt the same failing call repeatedly, potentially amplifying load. A circuit breaker stops retries after a failure threshold, protecting resources and providing immediate failure feedback.  

**Using both together:**  
- Apply retries with exponential backoff *inside* the closed state, then let the circuit breaker open if retries exhaust, preventing cascading failures.  

**AA7** — *Multi‑tenant SaaS Isolation Models*  

| Model | Cost | Security | Operational Complexity | Noisy‑Neighbor Risk |
|-------|------|----------|------------------------|----------------------|
| **1. Shared DB, shared schema (row‑level tenant ID)** | Lowest (single DB, minimal resources) | Moderate – relies on application‑level security; risk of schema‑level privilege escalation | Low – simple to manage | High – a tenant’s heavy load can affect others; DB‑level resource contention |
| **2. Shared DB, separate schema per tenant** | Moderate (more schemas, but still one DB instance) | Higher – schemas provide logical isolation; still share underlying resources | Moderate – schema creation/maintenance, backup granularity | Medium – resource contention at DB instance level, but less than shared schema |
| **3. Separate DB per tenant** | Highest (provisioning many DB instances) | Highest – physical isolation, easier to enforce least‑privilege | High – provisioning, patching, monitoring many DBs | Low – each tenant’s workload isolated; noisy‑neighbor impact minimal |  

**Trade‑off summary:** Choose shared schema for cost‑sensitive, low‑risk tenants; separate schemas for better security with manageable complexity; separate DBs for enterprise‑grade isolation and compliance.  

**AA8** — *Strong vs. Eventual Consistency*  
- **Strong Consistency**: Every read sees the most recent write (linearizability). Guarantees no overselling.  
- **Eventual Consistency**: Updates propagate asynchronously; temporary inconsistencies possible.  

**Architecting an inventory system that never oversells:**  
- **Consistency Model**: Strong consistency for the critical “reserve stock” operation.  
- **Data Store**: Use a transactional datastore with ACID guarantees (e.g., PostgreSQL with SERIALIZABLE isolation, or a distributed transaction manager like two‑phase commit). Alternatively, employ **optimistic concurrency** with version checks (compare‑and‑set) in a strongly consistent NoSQL (e.g., Google Spanner, CockroachDB).  
- **Patterns**:  
  1. **Reservation Service** with atomic decrement of available quantity inside a DB transaction.  
  2. **Idempotent Order API** – client sends a unique order ID; the service checks if the reservation already succeeded (deduplication).  
  3. **Compensating Action** (Saga) if downstream fulfillment fails – release the reserved stock.  

**AA9** — *Sidecar Proxy in a Service Mesh*  
- **Sidecar Proxy**: A lightweight network proxy (e.g., Envoy) deployed alongside each service instance, handling inbound/outbound traffic, telemetry, and security.  

**Envoy in Istio:**  
- **Data Plane**: Envoy instances form the data plane, performing traffic routing, retries, timeouts, mTLS, and metrics collection.  
- **Control Plane**: Istio Pilot (or Citadel, Galley) configures Envoy via xDS APIs, managing routing rules, security policies, and load‑balancing settings.  

**mTLS between sidecars vs. application‑level TLS:**  
- **Application‑level TLS** terminates at the service, requiring each service to manage certificates and trust chains.  
- **mTLS at sidecar** centralizes TLS termination, providing:  
  1. **Identity propagation** (service‑to‑service auth via SPIFFE IDs).  
  2. **Transparent encryption** without code changes.  
  3. **Fine‑grained policy enforcement** (e.g., allow only Service A to call Service B).  

**AA10** — *Strangler Fig Pattern*  
- Incrementally replace parts of a monolith by routing specific functionality to new microservices, leaving the rest in the legacy system until it’s fully “strangled.”  

**Migration strategy for .NET Framework → .NET 8:**  
1. **Identify Bounded Contexts** – map monolith modules to candidate microservices (e.g., Order, Inventory, Billing).  
2. **Expose Facade APIs** – add an API layer (e.g., ASP.NET Core) that proxies requests to either the legacy code or the new service based on routing rules.  
3. **Develop New Service** – rewrite a context in .NET 8, deploy as a container, and configure the facade to route that context’s traffic to it.  
4. **Data Migration** – use database view or change‑data‑capture (CDC) to keep legacy and new services in sync during transition.  
5. **Iterate** – repeat steps 2‑4 for each context, gradually reducing the monolith’s footprint until it can be retired.  

**AA11** — *12‑Factor App Methodology*  
Key factors (6+):  

1. **Codebase** – One repo per app, enabling traceable deployments.  
2. **Dependencies** – Explicitly declare dependencies; no implicit system‑wide packages.  
3. **Config** – Store config in environment variables, not in code.  
4. **Backing Services** – Treat databases, caches, etc., as attached resources, interchangeable via config.  
5. **Build, Release, Run** – Strict separation: build (artifact), release (combines build + config), run (execution environment).  
6. **Processes** – Run apps as one or more stateless processes; enable horizontal scaling.  
7. **Port Binding** – Export services via port; rely on reverse proxy for external exposure.  
8. **Concurrency** – Scale via process model (multiple stateless workers).  
9. **Disposability** – Fast startup/shutdown for elasticity.  
10. **Dev/Prod Parity** – Keep environments as similar as possible.  
11. **Logs** – Treat logs as event streams; let execution environment handle collection.  
12. **Admin Processes** – Run one‑off admin tasks as separate processes.  

These factors promote **portability, scalability, and maintainability** in cloud‑native environments.  

**AA12** — *Event‑Driven (Kafka) vs. Request‑Driven (REST/gRPC)*  

| Aspect | Event‑Driven (Kafka) | Request‑Driven (REST/gRPC) |
|--------|----------------------|----------------------------|
| **Coupling** | Loose – producers/consumers unaware of each other (topic‑based). | Tight – client knows service endpoint and contract. |
| **Scalability** | Highly scalable; consumers can scale independently; back‑pressure via partitions. | Scalable but limited by synchronous request‑response latency; load‑balancing needed. |
| **Debugging Complexity** | More complex: need to trace events across topics, offsets, consumer groups. | Simpler: request‑response logs, HTTP tracing. |
| **Ordering Guarantees** | Per‑partition ordering; global ordering not guaranteed unless single partition. | Request order preserved per connection (gRPC streams) but not across independent calls. |
| **Failure Handling** | Built‑in durability; consumers can replay from offsets; idempotency required. | Retries, circuit breakers; failures are immediate; no built‑in replay. |
| **When to Choose** | High throughput, decoupled workflows, event sourcing, stream processing, eventual consistency. | Low‑latency, request‑response APIs, CRUD operations, synchronous user interactions. |

**AA13** — *Load Balancer (L4 vs. L7)*  
- **Layer 4 (L4)**: Operates on TCP/UDP; distributes based on IP/port. Example: L4 load balancer for database replicas.  
- **Layer 7 (L7)**: Operates on HTTP/HTTPS; can route based on URL, headers, cookies. **Use case requiring L7**: *Content‑based routing* (e.g., directing `/api/v2/*` to a newer service while other paths go to legacy).  

**AA14** — *Message Queue vs. Log‑Based Broker*  
- **Message Queue (RabbitMQ)**: Pull‑based, supports acknowledgments, priority queues, dead‑letter exchanges; suitable for task/work queues with at‑most‑once or at‑least‑once delivery.  
- **Log‑Based Broker (Kafka)**: Append‑only log, high throughput, consumer‑driven offsets, built‑in partitioning and replay; ideal for event streaming and durable log of changes.  

**Pick Queue** when you need reliable task distribution, explicit ACKs, and per‑message control. **Pick Kafka** for high‑volume event pipelines, replayability, and ordering within partitions.  

**AA15** — *Container vs. Virtual Machine*  
- **Container**: OS‑level virtualization; shares host kernel, lightweight, fast startup, encapsulates runtime, libraries, and binary. Popular for microservices due to **resource efficiency**, **portability**, and **consistent environment**.  
- **VM**: Full hardware virtualization; each VM runs its own kernel, heavier, longer boot times. Used when strong isolation (different OS versions, kernels) is required.  

**AA16** — *Stateless vs. Stateful Services*  
- **Stateless**: No client‑specific data retained between requests; can be scaled horizontally by adding instances behind a load balancer. Example: Stateless authentication service using JWT.  
- **Stateful**: Maintains session or per‑client data (e.g., in‑memory cache, file state). Scaling requires session affinity or distributed state store. Example: Game server holding player state.  

**Stateless services are easier to scale** because any instance can handle any request; no need for sticky sessions or complex state migration.  

**AA17** — *ORM (Object‑Relational Mapper)*  
- **ORM**: Maps objects in code to relational database tables, abstracting SQL.  

**Popular ORMs:**  
- **Entity Framework** (C#/.NET)  
- **Hibernate** (Java)  

**Trade‑offs:**  
- **Pros**: Faster development, less boilerplate, database‑agnostic query building, change tracking.  
- **Cons**: Performance overhead (N+1 queries), abstraction leaks (complex mappings), less control over SQL optimization.  

**AA18** — *Bulkhead Pattern*  
- **Bulkhead**: Isolates resources (threads, connection pools, CPU) per service or functional area to prevent a failure in one part from exhausting resources needed by others.  

**Implementation examples:**  
- **Thread‑pool bulkheads**: Allocate separate executor pools for critical vs. non‑critical requests; if the critical pool is exhausted, non‑critical requests are rejected early.  
- **Deployment‑group bulkheads**: Run different microservices in separate Kubernetes namespaces or node pools; a runaway process in one group can’t starve the other.  

**AA19** — *Operational Transformation (OT) vs. CRDTs*  

| Aspect | OT | CRDT |
|--------|----|------|
| **Consistency Guarantees** | **Strong convergence** if transformation functions are correctly implemented; relies on a central server or transformation server to order ops. | **Eventual strong convergence** (commutative, associative ops) without a central authority; guarantees convergence even with offline edits. |
| **Latency** | Requires round‑trip to server for transformation, higher perceived latency for remote users. | Local operations apply immediately; sync later, low latency. |
| **Complexity** | Complex algorithm (transform functions, version vectors) and server coordination. | Simpler mathematically (join‑semilattice structures) but can lead to larger metadata (e.g., tombstones). |
| **Offline Support** | Typically needs server‑side buffering; offline edits must be queued and transformed later. | Naturally supports offline – each replica can apply ops locally and merge later. |
| **Choice for offline‑first collaborative editor** | **CRDT** is preferred** because it allows users to edit without connectivity and guarantees that once reconnected, all replicas converge to the same state without central coordination.  

**AA20** — *Distributed Tracing in Polyglot Microservices*  

**Key challenges & solutions:**  

1. **Context Propagation**  
   - Use **W3C Trace Context** (traceparent/tracestate headers) or **B3** propagation for backward compatibility.  
   - Libraries (OpenTelemetry) inject/extract headers automatically across HTTP, gRPC, and messaging (Kafka headers).  

2. **Sampling Strategies**  
   - **Head‑based**: Decision made at the entry point (e.g., API Gateway) based on request attributes; cheap, consistent.  
   - **Tail‑based**: Collect all traces then sample post‑hoc (e.g., based on latency, error rate); higher overhead but can capture rare errors.  

3. **Trace Storage & Querying**  
   - **Jaeger** (open‑source) and **Tempo** (object‑store backed) store spans; support backend‑agnostic APIs.  
   - Query by trace ID, service name, latency thresholds.  

4. **Asynchronous Messaging (Kafka)**  
   - **Trace continuity**: When a service publishes a Kafka message, it **propagates the trace context** in message headers. The consumer reads the headers and **creates a new span** linked to the parent via `SpanKind = Consumer` and `Parent Span ID`.  
   - Ensure **idempotent processing** so that retries don’t create duplicate spans; use `MessageId` as operation ID.  

5. **Polyglot Considerations**  
   - Instrument each language runtime (Java, Go, Node, Python) with OpenTelemetry SDKs.  
   - Normalize attribute naming (e.g., `http.method`, `db.system`) for cross‑language analysis.  

**Ensuring continuity across Kafka:**  
- **Producer**: `Tracer->startSpan` → inject `traceparent` into Kafka header.  
- **Consumer**: extract header → `Tracer->startSpanAsChildOf` using extracted context.  
- **Result**: A single trace spans synchronous HTTP calls and asynchronous Kafka hops, visible end‑to‑end in the tracing UI.

**On‑Premise Infrastructure Architecture**

**OP1** — *Hypervisor Type 1 vs. Type 2*  
- **Type 1 (Bare‑metal)** runs directly on hardware, managing VMs. Examples: VMware ESXi, Proxmox VE, Hyper‑V (when installed as a standalone hypervisor).  
- **Type 2 (Hosted)** runs as an application on a host OS. Examples: Oracle VirtualBox, VMware Workstation, Parallels Desktop.  

**OP2** — *SAN vs. NAS*  
- **SAN (Storage Area Network)**: Block‑level storage over Fibre Channel, iSCSI, or FC‑o‑Ethernet. Provides low‑latency, high‑performance storage for databases.  
- **NAS (Network Attached Storage)**: File‑level storage over NFS, SMB/CIFS. Suitable for file shares, backups, media libraries.  

**When to use:**  
- **SAN** for workloads needing direct block access (e.g., high‑throughput DBs, virtual machine images).  
- **NAS** for collaborative file storage, home directories, archival data.  

**OP3** — *3‑Tier vs. Leaf‑Spine Network*  
- **3‑Tier**: Core, Distribution, Access layers. Traffic may traverse multiple hops, creating bottlenecks and asymmetric paths.  
- **Leaf‑Spine**: All leaf switches (host‑connected) connect to every spine switch; provides **equal‑cost multipath**, higher bisection bandwidth, and simpler scaling (add leaf or spine as needed).  

**Problem solved:** Leaf‑spine eliminates core bottlenecks and reduces latency/packet loss in modern data centers with east‑west traffic.  

**OP4** — *Highly Available Proxmox Cluster with Shared Storage*  
- **Node Count**: Minimum 3 nodes for quorum (Pacemaker/Corosync).  
- **Quorum**: Uses majority rule; with 3 nodes, 2 must be up.  
- **Fencing**: STONITH (e.g., IPMI/iLO) to power‑off a failed node safely.  
- **Shared Storage Options**:  
  - **Ceph RBD** – distributed, highly available block storage.  
  - **iSCSI** – centralized SAN appliance.  
  - **NFS** – simpler but less scalable.  
- **Node Failure Handling**:  
  1. Cluster detects failure via heartbeat.  
  2. Pacemaker triggers STONITH on the failed node.  
  3. VMs running on the failed node are live‑migrated (if live‑migration storage available) or automatically restarted on surviving nodes using HA policies.  

**OP5** — *VLAN Trunking & 802.1Q*  
- **VLAN Trunking**: A single physical link carries traffic for multiple VLANs using 802.1Q tags.  
- **802.1Q Tagging**: Inserts a 4‑byte header (`TPID` + `TCI`) into Ethernet frames to identify VLAN ID.  

**Configuring a single NIC for 3 VLANs on Linux:**  
```bash
# Load 802.1Q module
modprobe 8021q

# Create VLAN interfaces
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip link add link eth0 name eth0.30 type vlan id 30

# Bring them up and assign IPs
ip addr add 192.168.10.2/24 dev eth0.10
ip addr add 192.168.20.2/24 dev eth0.20
ip addr add 192.168.30.2/24 dev eth0.30
ip link set dev eth0 up
ip link set dev eth0.10 up
ip link set dev eth0.20 up
ip link set dev eth0.30 up
```  

**OP6** — *RAID Levels Comparison (6 drives)*  
- **RAID 1**: Mirroring – 3 pairs possible (3 usable drives). Excellent read performance, good write, simple.  
- **RAID 5**: Single parity – 5 usable drives, good capacity, moderate write penalty.  
- **RAID 6**: Double parity – 4 usable drives, higher fault tolerance (tolerates 2 failures).  
- **RAID 10**: Stripe of mirrors – 3 usable drives, best read/write performance, high cost.  
- **RAID Z2 (ZFS)**: Similar to RAID 6 but with ZFS’s copy‑on‑write and checksumming.  

**Choice for database server (balance performance, capacity, fault tolerance):** **RAID 10** if budget allows (max performance & redundancy). If capacity is critical, **RAID 6** offers a good trade‑off (tolerates 2 disk failures with 4/6 usable).  

**OP7** — *Enterprise DNS Architecture*  

- **Internal AD‑integrated DNS**: Primary DNS for internal hosts, authoritative for `internal.example.com`.  
- **DMZ Public DNS**: Authoritative for `example.com` (external zone) with **split‑horizon** – internal queries resolve to internal IPs, external queries resolve to public IPs.  
- **Recursive Resolvers**: Deploy caching resolvers (e.g., Unbound, BIND) in each site; forward internal queries to AD DNS, external to ISP resolvers.  
- **Conditional Forwarding**: Internal resolver forwards `example.com` queries to DMZ DNS, avoiding public internet lookups.  
- **DNSSEC**: Enable on external zone; sign with private key, publish DS to parent TLD.  
- **Laptop Mobility**:  
  - On‑prem: DHCP offers internal DNS servers.  
  - VPN: DHCP (or DHCP‑option) provides same internal DNS; split‑horizon ensures correct resolution.  

**OP8** — *PKI Chain of Trust & Internal PKI Design*  

- **Root CA** (offline, hardware security module) issues certificates to **Subordinate/Issuing CAs**.  
- **Issuing CA** handles day‑to‑day certificate signing (web servers, clients).  
- **CRL vs. OCSP**:  
  - **CRL** (Certificate Revocation List) – periodic download; simpler but can be large.  
  - **OCSP** (Online Certificate Status Protocol) – real‑time lookup; lower latency, requires reliable responder.  
- **Certificate Templates**: Define allowed key usage (server auth, client auth), extensions (SAN), lifetime.  
- **Auto‑enrollment**: Windows clients use group policy to request certificates automatically.  

**Compromise Scenarios:**  
- **Subordinate CA** compromised → revoke its certificate (update CRL/OCSP). Root remains safe; only certificates issued by that subordinate are affected.  
- **Root CA** compromised → entire trust chain invalid; must generate a new root, reissue all certificates, and redistribute trust anchors.  

**OP9** — *WAN Options for 5 Remote Offices (50 users each, VoIP‑sensitive)*  

| Technology | Cost | Reliability | Latency | Management | Security |
|------------|------|-------------|---------|------------|----------|
| **MPLS** | High (service provider) | Very high (SLA) | Low‑to‑moderate (carrier‑grade) | Centralized (provider) | Built‑in L2/L3 encryption options |
| **IPsec VPN (Internet)** | Low‑moderate (hardware/software) | Dependent on ISP; can be flaky | Variable (Internet jitter) | More complex (key mgmt) | Strong encryption (IPsec) |
| **SD‑WAN** | Moderate (appliance/software) | Optimizes multiple links, failover | Low (path selection) | Centralized controller, policy‑driven | Encryption + segmentation |
| **WireGuard Mesh** | Very low (open‑source) | Depends on internet links; no SLA | Low (lightweight) | Simple key exchange, but mesh scaling | Modern crypto, but less enterprise tooling |

**Recommendation:** **SD‑WAN** – provides path‑aware routing, can combine MPLS + Internet links, offers built‑in QoS for VoIP, and simplifies management across sites.  

**OP10** — *iDRAC/iLO/IPMI*  
- **Out‑of‑band management**: Allows control of server hardware (power cycle, BIOS, remote console) independent of OS/network. Critical for recovery when OS is unresponsive.  

**If IPMI exposed to the internet:**  
- Attack surface for credential brute‑force, firmware exploits, or remote code execution leading to full server compromise. Best practice: isolate IPMI to a management VLAN, use strong passwords, MFA, and firewall rules.  

**OP11** — *LVM, LVM‑Thin, ZFS*  

- **LVM (Logical Volume Manager)**: Traditional block‑level volume management; supports snapshots but they are copy‑on‑write and can become expensive with many changes.  
- **LVM‑Thin**: Provides thin provisioning + snapshots; more efficient space usage, but still POSIX‑based and lacks checksumming.  
- **ZFS**: Integrated filesystem + volume manager; offers snapshots, clones, built‑in checksums, compression, and self‑healing (with RAID‑Z).  

**When to use:**  
- **LVM** for simple Linux environments needing basic resizing.  
- **LVM‑Thin** when you need thin provisioning + snapshots without moving to a new filesystem.  
- **ZFS** for workloads requiring data integrity, advanced snapshots/clones, and efficient storage (e.g., databases, VM images).  

**Snapshot semantics:**  
- **LVM**: Physical copy of extents at snapshot time; grows as changes occur.  
- **LVM‑Thin**: Space allocated on‑demand; snapshots share unchanged blocks.  
- **ZFS**: Copy‑on‑write snapshots are instantaneous and share data blocks; clones can be promoted to full datasets.  

**OP12** — *Stretch Cluster / DR for 3‑Node Proxmox + Ceph*  

- **Ceph CRUSH Map**: Define buckets for each site (e.g., `siteA`, `siteB`). Set `host` as the lowest level, `site` as a higher level. Use `failure_domain` = `site` to ensure replicas span sites.  
- **Monitor Placement**: Deploy at least three monitors, one per site if possible, to maintain quorum across a site failure.  
- **Network Latency**: Ceph requires sub‑10 ms latency between sites for synchronous replication; otherwise use **asynchronous replication** with **RBD mirroring** or **Ceph Object replication**.  
- **Split‑Brain Mitigation**: Enable **`osd_pool_default_pg_num`** and **`osd_pool_default_pgp_num`** tuned for site‑level failure; use **`crush chooseleaf`** to keep replicas local, but **`crush rule`** forces cross‑site copies.  
- **Why 2‑site Ceph is risky**: Without a tiebreaker (e.g., arbiter monitor or quorum‑aware configuration), a network partition can cause both sites to believe they are the primary, leading to divergent data (split‑brain). A third monitor or explicit quorum rules are required.  

**DR Strategy**:  
1. **Active‑Active** at primary site (3 nodes).  
2. **Warm Standby** at secondary site with **Ceph RBD mirroring** to replicate volumes.  
3. **Failover Procedure**: Promote secondary site monitors, update DNS/Proxmox cluster config, and start VMs from mirrored images.  

**OP13** — *DHCP & DORA*  
- **DORA** steps: **D**iscover (client broadcasts DHCPDISCOVER), **O**ffer (server responds with DHCPOFFER), **R**equest (client selects offer and sends DHCPREQUEST), **A**ck (server sends DHCPACK with lease info).  

**If DHCP server unavailable and lease expires:**  
- Client will **renew** attempts (exponential backoff). After final timeout, it falls back to **APIPA** (169.254.0.0/16 on Windows) and cannot communicate on the network until a DHCP server becomes available or a static IP is configured manually.  

**OP14** — *Managed vs. Unmanaged Switch*  
- **Unmanaged**: Plug‑and‑play, fixed configuration; no CLI, no VLANs, no QoS. Suitable for home or simple office LANs.  
- **Managed**: Offers CLI/WEB UI, supports VLANs, STP, LACP, QoS, port mirroring, SNMP, ACLs—essential for enterprise segmentation, monitoring, and traffic engineering.  

**OP15** — *NTP & Time Synchronization*  
- **NTP** synchronizes clocks across devices to a reference (e.g., public NTP pool or internal stratum‑1 server). Accurate time is crucial for:  
  - **Security** (TLS certificate validation, Kerberos).  
  - **Logging & Auditing** (consistent timestamps).  
  - **Distributed Systems** (causality, vector clocks).  

**Clock drift consequences:**  
- Logs out of order, incorrect audit trails, potential security token rejection, flaky consensus algorithms (e.g., Raft) may stall or split.  

**OP16** — *Physical Server vs. VM vs. Container*  
- **Physical Server**: Bare metal, full hardware access; used for workloads needing direct hardware (high‑performance computing, specialized I/O, legacy apps).  
- **Virtual Machine**: OS + hardware virtualization; isolates workloads, easier to manage, but heavier than containers.  
- **Container**: Shares host kernel, lightweight; ideal for microservices, stateless apps, rapid scaling.  

**Run on bare metal** when:  
- Need **maximum performance** (e.g., HPC, real‑time audio/video processing).  
- Require **hardware‑specific features** not virtualizable (e.g., FPGA, certain NIC offloads).  
- Running **legacy OS** not supported in VMs.  

**OP17** — *UPS vs. Generator & ATS*  
- **UPS (Uninterruptible Power Supply)**: Provides immediate short‑term power (seconds to minutes) to ride through outages, allowing graceful shutdown or switch to generator.  
- **Generator**: Supplies longer‑duration power (hours) via diesel/fuel; starts after UPS depletes.  
- **ATS (Automatic Transfer Switch)**: Detects utility loss, switches load from utility to generator (and back) automatically.  

**Need both**: UPS bridges the gap between utility failure and generator startup time; generator ensures continuity for extended outages.  

**OP18** — *Active‑Passive vs. Active‑Active HA for PostgreSQL*  

- **Active‑Passive**: One primary node serves traffic; standby replicates (streaming replication). On failure, STONITH stops primary, promotes standby, updates virtual IP.  
- **Active‑Active**: Multi‑master setups (e.g., BDR, PGPool) where both nodes accept writes; requires conflict resolution and often limited to specific schemas.  

**Pacemaker/Corosync Implementation (Active‑Passive):**  
1. **Resources**:  
   - `postgresql` primitive (service).  
   - `IPaddr2` (virtual IP).  
   - `STONITH` primitive (IPMI).  
2. **Constraints**: Colocation of PostgreSQL and VIP; ordering to ensure STONITH runs before failover.  
3. **Fencing**: STONITH ensures failed node is powered off to avoid split‑brain.  
4. **Failover**: Corosync detects primary loss → Pacemaker stops resource on failed node, starts on standby, updates DNS/IP.  

**OP19** — *Backup & Recovery Strategy (50‑server environment)*  

- **3‑2‑1 Rule**: 3 total copies, 2 on different media, 1 offsite.  
- **RPO/RTO**: Define acceptable data loss (e.g., 15 min) and recovery time (e.g., 2 h).  
- **Backup Types**:  
  - **Full** weekly (baseline).  
  - **Incremental** daily (captures changes since last full).  
  - **Differential** optional for faster restore of recent changes.  
- **Deduplication**: Reduce storage via source‑side or target‑side dedup (e.g., Veeam, Rubrik).  
- **Media Choices**:  
  - **Disk** (local NAS for fast RPO).  
  - **Tape** (long‑term archival, cost‑effective).  
  - **Cloud Offsite** (e.g., AWS S3 Glacier for immutable backups).  
- **Immutable Backups**: Use WORM (Write Once Read Many) or object‑lock features to protect against ransomware.  
- **Testing**: Regularly restore random files/systems to validate integrity; automate with scripts.  

**Backup vs. Disaster Recovery**:  
- **Backup** = data copies for restore.  
- **Disaster Recovery** = comprehensive plan to restore entire IT environment (infrastructure, network, applications) at an alternate site, including failover procedures, site readiness, and runbooks.  

**OP20** — *802.1X Network Access Control*  

- **Supplicant**: Client software (e.g., built‑in OS 802.1X, Cisco AnyConnect) that initiates authentication.  
- **Authenticator**: Network device (switch/port) that enforces access; blocks traffic until successful authentication.  
- **Authentication Server**: RADIUS (or LDAP) that validates credentials (EAP‑TLS, PEAP, etc.).  

**EAP Methods**:  
- **EAP‑TLS**: Mutual certificate authentication – strongest, requires client certificates.  
- **PEAP** (Protected EAP): Wraps inner authentication (e.g., MSCHAPv2) in TLS tunnel; easier for user passwords.  

**RADIUS**: Handles request/response, accounting, and policy enforcement.  

**Dynamic VLAN Assignment**: Post‑auth, RADIUS returns `VLAN-Id` attribute; switch moves port to that VLAN.  

**Failed Authentication**: Port remains in **authorization‑pending** state, traffic blocked (except limited EAP‑start frames).  

**MAB (MAC Authentication Bypass)**: For devices lacking 802.1X supplicant (e.g., printers). Switch extracts MAC, queries RADIUS for a pre‑configured MAC‑to‑VLAN mapping; if approved, port is authorized directly.
