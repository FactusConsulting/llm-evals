**DN1**  
- **Class**: Reference type, allocated on the heap, supports inheritance, can have a parameterless constructor, and can be `null`.  
- **Struct**: Value type, allocated on the stack (or inline in a containing object), cannot inherit from other reference types (except `System.ValueType`), and is never `null` (it has a default value).  
- **When to use a struct**: For small, immutable data structures where the overhead of heap allocation and garbage collection is undesirable (e.g., `Point`, `DateTime`, numeric vectors). Avoid structs for large or mutable data because copying can be expensive and can lead to subtle bugs.

**DN2**  
- **IEnumerable<T>**: Represents a forward‑only, in‑memory collection. Methods like `Where`, `Select` are evaluated in **LINQ to Objects** (i.e., in memory).  
- **IQueryable<T>**: Represents a query that can be translated into an expression tree and executed by a remote data source (e.g., a database). LINQ providers (EF, LINQ to SQL) translate the expression to SQL, enabling server‑side filtering, projection, and paging.  
- **Why it matters**: Using `IQueryable` allows the database to do the heavy lifting, reducing data transferred and improving performance. Using `IEnumerable` forces all data to be loaded into memory first.

**DN3**  
- **async/await** lets you write asynchronous code that looks synchronous. `await` pauses the method until the awaited `Task` completes, without blocking a thread.  
- **Task**: Represents an asynchronous operation that may be long‑running; it allocates an object on the heap.  
- **ValueTask**: A struct that can hold either a `Task` or a result directly, avoiding allocation for hot‑path synchronous completions.  
- **When to use `ValueTask`**: When the async method often completes synchronously (e.g., cached results, simple I/O) and you want to reduce GC pressure. Avoid it for operations that always involve async I/O, as the extra logic can add overhead.

**DN4**  
- **Dependency Injection (DI)** in .NET registers services with a container and resolves them at runtime, promoting loose coupling and testability.  
- **Service lifetimes**:  
  - **Transient** – a new instance per resolution (stateless services).  
  - **Scoped** – a single instance per request (or DI scope) – ideal for per‑request services like `DbContext`.  
  - **Singleton** – a single instance for the app lifetime.  
- **Common bug**: Injecting a **Scoped** service into a **Singleton** causes the scoped instance to be stored in the singleton, leading to state leakage across requests (e.g., shared `DbContext`). The fix is to inject the appropriate lifetime or use `IServiceScopeFactory` to create a new scope when needed.

**DN5**  
- **string**: Immutable reference type, stored on the heap, involves indirection and potential allocations for slicing/substrings.  
- **ReadOnlySpan<char>**: A ref‑like value type that points to a contiguous memory region (stack‑allocated or part of an existing object) without copying. It enables zero‑copy string processing and is ideal for high‑performance parsing, validation, or algorithms that work on character buffers.  
- **When to use `Span<T>`/`ReadOnlySpan<char>`**: When you need low‑level, high‑performance manipulation of character data (e.g., protocol parsing, text formatting) and can guarantee the data lives for the span’s lifetime (no out‑of‑scope references).

**DN6**  
- **Garbage Collector (GC)**: Automatically reclaims memory by identifying objects that are no longer reachable.  
- **Generations**:  
  - **Gen 0** – new objects; collected frequently.  
  - **Gen 1** – survivors of Gen 0; collected less often.  
  - **Gen 2** – long‑living objects; collected rarely.  
- **Large Object Heap (LOH)**: Separate heap for objects > 85 KB; allocations here are more expensive and cause fewer but longer collections.  
- **IDisposable**: Provides a deterministic way to release unmanaged resources (file handles, sockets, etc.) that the GC cannot clean up. Even with a GC, you need `IDisposable` to free native resources promptly and avoid leaks.

**DN7**  
- **ConfigureAwait(false)** tells the awaiter **not** to capture the current `SynchronizationContext` (or `TaskScheduler`). By default, `await` restores the captured context when the awaited task completes, which can cause deadlocks in UI or ASP.NET contexts.  
- **When to use**: In library code or non‑UI async methods where you don’t need to marshal back to the original context; it improves performance and reduces deadlock risk.  
- **When NOT to use**: In UI code (WinForms, WPF, Blazor) or ASP.NET request processing where the context is required for subsequent operations (e.g., updating UI controls).  
- **Relation to SynchronizationContext**: The context is an abstraction that the .NET runtime uses to post continuations back to the appropriate thread (e.g., the UI thread). `ConfigureAwait(false)` bypasses this posting.

**DN8**  
- **Primary Constructors (C# 12+)** allow declaring constructor parameters directly in the class header, reducing boilerplate.  
- **Collection Expressions**: Provide a concise syntax for building collections, e.g., `new List<int> { 1, 2, 3, 4 }` can be written as `new List<int> { 1, 2, 3, 4 }` (already existing) but the new feature enables more complex expressions like `new HashSet<int> { 1, 2, 3, 4 }.AddRange(other)`.  
- **FrozenDictionary**: An immutable dictionary with O(1) lookups, created via `FrozenDictionary<TKey, TValue>.Create` or the new collection expression syntax `new FrozenDictionary<int, string> { [1] = "one" }`.  
- **Minimal DI example with primary constructors**:
  ```csharp
  record HttpClientWrapper(HttpClient http);

  // In DI container setup
  builder.Services.AddScoped<HttpClientWrapper>(provider =>
      new HttpClientWrapper(new HttpClient()));

  // Service using it
  public record MyService(HttpClientWrapper wrapper);
  ```

**DN9**  
- **Likely cause**: `DbContext` is registered as **Scoped** but is being captured and used after the scope disposes (e.g., stored in a static field, passed to a background thread, or used in an async callback that runs after the request ends). Under high concurrency, multiple requests may race, leading to `ObjectDisposedException`.  
- **Fix**: Ensure `DbContext` is only used within the request scope. Options:  
  1. Keep the context local to the async method (don’t capture it).  
  2. Use `OwnsDbContext` pattern or a unit‑of‑work that guarantees disposal after use.  
  3. If background processing is needed, create a **new** scoped instance via `IServiceScopeFactory` inside the background task.  
- **EF Core & DI scoping**: By default, EF Core registers `DbContext` as scoped, matching ASP.NET Core’s per‑request lifetime. The container creates a fresh instance per request and disposes it when the scope ends. Any leakage of the instance beyond that scope results in disposal exceptions.

**DN10**  
- **record vs class**:  
  - **record** (introduced C# 9) is a **reference type** that provides automatic `Equals`, `GetHashCode`, and `ToString` based on its members, and supports **positional syntax** and **with‑expression** for immutable updates.  
  - **class** is the traditional reference type with full control over equality and mutability.  
- **record struct**: A **value type** record (C# 10+). It combines struct semantics (stack allocation, value equality) with record features (positional parameters, `with`). Use when you need an immutable, lightweight value type (e.g., coordinates, monetary amounts).  
- **When to choose**:  
  - Use **record** for immutable aggregates that are naturally reference types (entities, DTOs).  
  - Use **class** when you need mutable state or custom equality.  
  - Use **record struct** for small, immutable value types where copying cost matters.

**DN11**  
- **ref**: Passes a variable’s storage location; the called method can read/write it. The argument must be initialized before the call.  
- **out**: Similar to `ref` but guarantees the variable will be assigned before the method returns. The argument does **not** need initialization beforehand.  
- **in** (C# 7.2+): Passes a read‑only reference; the called method cannot modify the variable. It’s a way to avoid copying large structs while ensuring no mutation.  
- **Usage**: Use `ref`/`out` for methods that need to return multiple values or modify caller state. Use `in` for high‑performance scenarios where you pass large structs and want to prevent accidental mutation.

**DN12**  
- **Nullable reference types** (`?` annotation, `#nullable enable`) make the compiler enforce that reference variables are non‑nullable unless explicitly marked nullable. This helps catch dereference null errors at compile time.  
- **Nullable value types** (`int?`, `Nullable<T>`) allow value types to represent “no value” (e.g., optional database fields). They are structs that carry a `HasValue` flag and a `Value`.  
- **Difference**: Nullable reference types are a **type system** feature affecting how the compiler treats references; nullable value types are **runtime** structs enabling “optional” values for value types.

**DN13**  
- **LINQ (Language Integrated Query)** provides a uniform way to query collections, databases, XML, etc.  
- **Method syntax** (`list.Where(x => x > 0).Select(x => x * 2)`) is more flexible, supports extension methods, and is often clearer for complex pipelines.  
- **Query syntax** (`from x in list where x > 0 select x * 2`) resembles SQL and is syntactic sugar for method calls.  
- **Deferred execution**: LINQ queries are not executed when defined; they run when enumerated (e.g., via `foreach`, `ToList()`, `ToArray()`). This allows chaining operations without intermediate collections and enables efficient database queries.

**DN14**  
- **Generic constraints** restrict the types that can be used for a type parameter.  
  - `where T : class` – `T` must be a reference type.  
  - `where T : struct` – `T` must be a value type (excluding nullable structs).  
  - `where T : new()` – `T` must have a parameterless constructor.  
  - `where T : IComparable<T>` – `T` must implement the specified interface.  
- **Combining constraints**: You can list multiple constraints separated by commas (`where T : class, IMyInterface`). This is useful when a method needs both an interface and a base class, or a value type with a constructor.

**DN15**  
- **abstract class**: Can contain implementation, fields, and a mix of abstract/virtual members. Supports multiple inheritance of interfaces only.  
- **interface**: Pure contract; no implementation (except default methods in C# 8+). A class can implement multiple interfaces.  
- **Default interface methods** (C# 8+) allow adding a concrete implementation to an interface without breaking existing implementations. This narrows the gap between abstract classes and interfaces, letting interfaces evolve with behavior while preserving multiple inheritance.

**DN16**  
- **Middleware pipeline** in ASP.NET Core is a series of components that process `HttpContext` sequentially. Each middleware can perform work before and after the next middleware.  
- **`app.Use()`**: Adds a middleware that **invokes the next middleware** (unless short‑circuited).  
- **`app.Map()`**: Branches the pipeline based on a matching path; only the mapped branch executes.  
- **`app.Run()`**: Terminates the pipeline; typically used for terminal middleware (e.g., response generation).  
- **Ordering matters**: Early middleware can read/modify the request (e.g., authentication, logging) before later middleware sees it. Exception‑handling middleware (e.g., `app.UseExceptionHandler`) must appear **before** the middleware that might throw.  
- **Exception handling**: Middleware can catch exceptions, set `context.Response`, and call `context.Response.Body.WriteAsync(...)` or re‑throw to be caught by later exception‑handling middleware.

**DN17**  
- **Channel<T>** (introduced in .NET Core 3.0) provides a high‑performance, asynchronous, bounded/unbounded communication channel between producers and consumers. It supports completion, cancellation, and back‑pressure via `WaitToReadAsync`/`WaitToWriteAsync`.  
- **Comparison to `BlockingCollection<T>`**: `BlockingCollection` is synchronous, blocks threads, and lacks built‑in cancellation support. `Channel` is fully async, integrates with `await`, and can be bounded (preventing unbounded memory growth).  
- **Bounded channel example** (producer‑consumer with back‑pressure):
  ```csharp
  var chan = Channel.CreateBounded<int>(capacity: 10);
  // Producer
  _ = Task.Run(async () => {
      for (int i = 0; i < 100; i++) {
          await chan.Writer.WaitToWriteAsync();
          if (chan.Writer.TryWrite(i)) continue;
          // optional back‑pressure handling
      }
      chan.Writer.Complete();
  });

  // Consumer
  _ = Task.Run(async () => {
      await foreach (var item in chan.Reader.ReadAllAsync()) {
          Console.WriteLine(item);
      }
  });
  ```

**DN18**  
- **Source Generators** (C# 9+) are compiler plugins that analyze source code and emit additional C# files at compile time. They run during the compilation pipeline, inspecting syntax, symbols, and metadata.  
- **Differences**:  
  - **Reflection** operates at runtime, inspecting types and invoking members dynamically.  
  - **IL weaving** modifies compiled IL after compilation (e.g., PostSharp).  
  - Source generators work **before** IL generation, producing source that the compiler compiles normally, offering zero‑runtime overhead and full type safety.  
- **Incremental Generator**: An advanced source generator that receives an `IncrementalGenerator` API, allowing it to track dependencies and regenerate only affected parts when inputs change, dramatically improving build performance for large projects. It’s preferred over the simpler `ISourceGenerator` for complex, stateful generation scenarios.

**DN19**  
- **TPL Dataflow** (`System.Threading.Tasks.Dataflow`) provides a set of pipeline building blocks for message passing and dataflow processing.  
  - **ActionBlock<T>**: Executes an action for each received message; good for simple fan‑out processing.  
  - **TransformBlock<TInput, TOutput>**: Transforms input to output, propagating the result downstream; useful for mapping or filtering.  
  - **BufferBlock<T>**: Simple in‑memory buffer that stores messages until a consumer pulls them; acts as a decoupling point.  
- **Comparison to Channels**: Channels are lower‑level, focusing on async read/write with explicit completion and cancellation. Dataflow adds higher‑level abstractions (linking, broadcasting, fault tolerance, join/merge semantics) and built‑in support for back‑pressure via `MaxMessages` and `BoundedCapacity`. Use channels for lightweight, direct producer‑consumer; use dataflow for complex pipelines with multiple branches, joins, and reliable processing.

**DN20**  
- **Minimal APIs** (introduced in .NET 6) allow building HTTP APIs with a small, functional style without controllers. Endpoints are defined using `app.MapGet`, `app.MapPost`, etc.  
- **Differences from controller‑based APIs**:  
  - No need for `Controller` base class, action methods, attributes for routing.  
  - Simpler for small services or micro‑gateways.  
  - Less boilerplate, but some features (model binding, validation, OpenAPI generation) have different ergonomics.  
- **Trade‑offs**:  
  - **Testability**: Minimal APIs can be unit‑tested by invoking the delegate directly; integration tests use `WebApplicationFactory`. Controllers offer more built‑in test helpers but add indirection.  
  - **Middleware**: Both can use middleware, but minimal APIs place endpoint logic inline, making flow control explicit.  
  - **OpenAPI**: Minimal APIs generate Swagger via `app.UseSwagger()` and `app.UseSwaggerUI()` similarly, but attribute‑driven metadata (e.g., `[ProducesResponseType]`) is less common; you may need `OpenApiRule` or manual `IOpenApiFilter`.  
- **Route groups & endpoint filters**:  
  - **Route groups** (`app.MapGroup("/{controller}")`) allow prefixing multiple endpoints and sharing common metadata (e.g., `[MapToApiVersion("1.0")]`).  
  - **Endpoint filters** (`app.UseEndpoints(e => e.RequireAuthorization())` or custom filters) run before/after the endpoint delegate, enabling cross‑cutting concerns (auth, logging, metrics) without modifying each endpoint.

**P1**  
- **List** vs **Tuple**:  
  - `list` is mutable, ordered, allows duplicate elements, and supports methods like `append`, `remove`.  
  - `tuple` is immutable, ordered, can contain heterogeneous types, and is often used for fixed‑size records.  
- **Set** vs **frozenset**:  
  - `set` is mutable, unordered collection of unique hashable items.  
  - `frozenset` is immutable and hashable, allowing it to be used as a dictionary key or stored in other sets.

**P2**  
- **GIL (Global Interpreter Lock)**: A mutex that protects access to Python objects, ensuring only one thread executes Python bytecode at a time in CPython.  
- **Affected workloads**: CPU‑bound pure Python code suffers because threads cannot run truly in parallel; I/O‑bound or extensions that release the GIL (e.g., NumPy, I/O operations) benefit from threading.  
- **Workarounds**:  
  - Use **multiprocessing** to spawn separate processes (each with its own GIL).  
  - Use native extensions or libraries that release the GIL during long computations.  
  - Use alternative implementations like **Jython** or **IronPython** that lack a GIL.

**P3**  
- **copy** (`import copy; copy.copy(obj)`) creates a **shallow** copy: the top‑level container is new, but nested objects are shared references.  
- **deepcopy** (`copy.deepcopy(obj)`) recursively copies all nested objects, producing a fully independent replica.  
- **Example of shallow copy issue**:
  ```python
  a = [[1, 2], [3, 4]]
  b = copy.copy(a)
  b[0][0] = 'X'      # modifies nested list in both a and b
  print(a)           # -> [['X', 2], [3, 4]]
  ```
  Here `b` is a shallow copy, so inner lists are still shared.

**P4**  
- **Decorator** syntax:
  ```python
  import time
  from functools import wraps

  def log_time(func):
      @wraps(func)
      def wrapper(*args, **kwargs):
          start = time.time()
          result = func(*args, **kwargs)
          elapsed = time.time() - start
          print(f"{func.__name__} took {elapsed:.4f}s")
          return result
      return wrapper

  @log_time
  def compute():
      time.sleep(0.5)
  ```
  The `@log_time` line applies the decorator, replacing `compute` with `wrapper`.

**P5**  
- **Generators** use `yield` to produce values one at a time, suspending and resuming execution. They return an iterator and compute values lazily, saving memory.  
- **Difference from returning a list**: A list materializes all elements upfront; a generator computes each element on demand.  
- **`yield from`**: Delegates part of the generator’s yielding to another iterable or sub‑generator, flattening nested iteration. Example:
  ```python
  def concat(a, b):
      yield from a
      yield from b
  ```

**P6**  
- **asyncio event loop**: The central scheduler that runs coroutines, manages I/O multiplexing, and drives `await`able objects.  
- **`asyncio.run(main())`**: Convenience function that creates an event loop, runs the supplied coroutine, and closes the loop (single‑call use).  
- **`asyncio.gather(*tasks)`**: Takes multiple awaitables and returns a single future that resolves when all complete, preserving order.  
- **`asyncio.create_task(coro)`**: Schedules a coroutine as a `Task` on the running loop, returning the `Task` object.  
- **Why not `time.sleep()`**: `time.sleep()` blocks the thread, preventing the event loop from running other tasks. Use `asyncio.sleep()` which is a non‑blocking `await`able.

**P7**  
- **MRO (Method Resolution Order)** in Python 3 uses the **C3 linearization** algorithm, ensuring monotonicity and preserving local precedence ordering.  
- **Diamond inheritance example**:
  ```python
  class A: def who(self): return "A"
  class B(A): pass
  class C(A): def who(self): return "C"
  class D(B, C): pass
  print(D().who())  # Outputs: C
  ```
  The MRO for `D` is `[D, B, C, A, object]`. `C` appears before `A`, so `D.who` resolves to `C.who`.  

**P8**  
- **Metaclass**: The class of a class; defines how a class is constructed (`__new__`, `__init__`). Used for class‑level validation, registration, or modification.  
- **`__init_subclass__`**: A class method called when a subclass is created; simpler for many use‑cases (e.g., auto‑registering subclasses).  
- **When to use each**:  
  - **Metaclass** when you need to control instance creation, enforce constraints on class attributes, or modify the class dictionary before the class is finalized.  
  - **`__init_subclass__`** for straightforward per‑subclass setup (e.g., adding fields to a registry).  
- **Practical use cases**:  
  - Metaclass: ORM base model that automatically adds a table name based on class name.  
  - `__init_subclass__`: Plugin system where each subclass registers itself in a module‑level list.

**P9**  
- **`multiprocessing`**: Spawns separate OS processes, each with its own Python interpreter and memory space; bypasses the GIL, ideal for CPU‑bound tasks. Requires pickling objects to send between processes.  
- **`threading`**: Uses OS threads within the same process; subject to the GIL, best for I/O‑bound work or when using extensions that release the GIL.  
- **`concurrent.futures`**: High‑level API providing `ThreadPoolExecutor` (wraps threading) and `ProcessPoolExecutor` (wraps multiprocessing). Simplifies submission of callables and retrieval of `Future` results.  
- **Serialization (pickling)**: Objects passed between processes must be pickleable. Custom classes need `__reduce__` or be defined at the top level of a module. Large objects can cause significant overhead; consider shared memory (`multiprocessing.Array`, `multiprocessing.Value`) for performance.

**P10**  
- **`__slots__`**: Declares a fixed set of instance attributes, preventing the creation of a per‑instance `__dict__`.  
- **When to use**: In classes with many instances where memory footprint and attribute access speed matter (e.g., data‑oriented structs).  
- **What it prevents**: Dynamic addition of new attributes; attempts raise `AttributeError`.  
- **Memory impact**: Reduces memory per instance by avoiding the dict overhead (typically tens of bytes per instance), at the cost of flexibility.

**P11**  
- **Virtual environment**: Isolated Python installation that contains its own site packages, allowing projects to have independent dependencies.  
- **`venv`**: Built‑in, lightweight, creates environments with a symlink to the system Python.  
- **`virtualenv`**: Older third‑party tool offering more customization (e.g., specifying different Python versions, extra scripts).  
- **`conda`**: Environment manager from Anaconda/Miniconda that handles not only Python packages but also binary dependencies (e.g., R, compilers), useful for data‑science stacks.  
- **Why use**: Avoids dependency conflicts between projects and system Python; ensures reproducible builds.

**P12**  
- **Comprehensions** (`[expr for item in iterable if cond]`, `{key: value for ...}`, `{expr for ...}`) provide concise, readable ways to build lists, dicts, or sets.  
- **Relation to `map`/`filter`**: `map(func, iter)` applies a function (similar to `[func(x) for x in iter]`). `filter(pred, iter)` selects items (`[x for x in iter if pred(x)]`). Comprehensions are generally preferred for readability.  
- **When to prefer**: Use comprehensions for simple transformations and filters. Use `map`/`filter` when you already have function objects and want lazy evaluation (they return iterators in Python 3). For complex logic, nested comprehensions can become hard to read—consider generator functions instead.

**P13**  
- **`==`**: Value equality test; compares the contents of objects.  
- **`is`**: Identity test; checks whether two references point to the **same object** in memory.  
- **Object interning**: Python interns certain immutable objects (e.g., small integers, some strings) to reuse instances, so `a is b` can be `True` for those (e.g., `-5 is -5`, `'hello' is 'hello'` in CPython).  
- **Use `is`** for singleton checks (`None`, `True`, `False`, custom singletons). Use `==` for semantic equality.

**P14**  
- **`*args`**: Captures additional positional arguments as a tuple.  
- **`**kwargs`**: Captures additional keyword arguments as a dict.  
- **Positional‑only (`/`)**: Parameters before `/` must be supplied positionally and cannot be passed as keywords (Python 3.8+).  
- **Keyword‑only (`*`)**: Parameters after `*` must be supplied by keyword (or via `**kwargs`).  
- **Example**:
  ```python
  def foo(a, b, /, c, *, d):
      pass
  # a, b are positional‑only; c must be positional or keyword; d is keyword‑only.
  ```

**P15**  
- **Context managers** manage resources with `with` statements, ensuring cleanup via `__enter__`/`__exit__`.  
- **Using `__enter__/__exit__`**:
  ```python
  class OpenFile:
      def __init__(self, filename, mode):
          self.filename = filename
          self.mode = mode
      def __enter__(self):
          self.file = open(self.filename, self.mode)
          return self.file
      def __exit__(self, exc_type, exc, tb):
          self.file.close()
  ```
- **Using `@contextmanager`** from `contextlib`:
  ```python
  from contextlib import contextmanager
  @contextmanager
  def open_file(filename, mode):
      f = open(filename, mode)
      try:
          yield f
      finally:
          f.close()
  ```
- **Beyond file handling**: database connections, locks, temporary directories, or custom cleanup logic.

**P16**  
- **Type hinting** adds static type information for tooling (mypy, pyright, IDEs).  
- **Key constructs**:  
  - `Union[A, B]` (or `A | B` in Python 3.10+): value can be either type.  
  - `Optional[T]` (`T | None`): `T` or `None`.  
  - `Literal['a', 'b']`: restricts to exact literal values.  
  - `TypeVar('T')`: Generic type variable for parametric polymorphism.  
  - `Protocol`: Defines structural subtyping (duck typing) via abstract methods.  
- **Static analysis**: Tools traverse the AST, check that operations conform to declared types, flag mismatches, and can infer types where annotations are missing.

**P17**  
- **Data model (dunder methods)** define object behavior.  
  - `__repr__`: Official string representation, ideally unambiguous (`<ClassName(attr=...)>`). Used by `repr()`.  
  - `__str__`: Informal, human‑readable string (`str()`).  
  - `__eq__`: Defines equality (`==`). If defined, `__hash__` should also be defined unless the object is mutable.  
  - `__hash__`: Enables use as a dictionary key; must be consistent with `__eq__`. If `__eq__` is custom and the object is mutable, omit `__hash__` (makes it “unhashable”).  
  - `__getattr__`: Called for attribute lookup that fails normally; can provide dynamic attributes.  
  - `__getattribute__`: Called for every attribute access; must avoid infinite recursion.  
- **If `__eq__` is defined but not `__hash__`**: The object becomes mutable for hashing purposes and its `__hash__` is set to `None`, preventing its use in sets or as a dict key.

**P18**  
- **Descriptors** implement the descriptor protocol (`__get__`, `__set__`, `__delete__`). When an attribute is accessed on a class or instance, Python checks for these methods.  
- **How built‑ins use descriptors**:  
  - `property`: Combines `__get__`, `__set__`, `__delete__` to create managed attributes.  
  - `classmethod`: Descriptor that wraps a function to receive the class as the first argument.  
  - `staticmethod`: Descriptor that removes the implicit first argument, returning the underlying function.  
- **Use case**: Custom validation logic, lazy initialization, or attribute delegation.

**P19**  
- **Python import system**:  
  - **Finder**: Searches `sys.meta_path` for a loader that can provide module code (e.g., `sys.path` modules, zip files, namespace packages).  
  - **Loader**: Loads the module, typically by reading source/bytecode and executing it.  
- **Absolute vs relative imports**:  
  - Absolute (`import package.module`) starts from the top‑level package.  
  - Relative (`from . import sibling`) is resolved relative to the current module’s package. Relative imports require the module to be part of a package (i.e., have `__init__.py`).  
- **`sys.path` / `PYTHONPATH`**: List of directories searched for modules; `PYTHONPATH` augments it at interpreter startup.  
- **`__init__.py`**: Marks a directory as a package; can contain package‑level code and control subpackage visibility (`__all__`).  
- **Namespace packages**: Introduced in PEP 420; allow a single package to be split across multiple directories without `__init__.py`, enabling “distributable” packages that can be installed independently.

**P20**  
- **dataclasses** (Python 3.7+) automatically generate `__init__`, `__repr__`, `__eq__`, and optionally `__hash__` from class fields (`field(...)`).  
- **Comparison to `attrs`**: `attrs` offers more features out‑of‑box (validators, converters, `frozen` support, `asdict`, `astuple`) and works on older Python versions. `dataclasses` is built‑in and sufficient for many cases.  
- **Comparison to `Pydantic`**: `Pydantic` focuses on **validation** and **parsing** of data, providing type‑safe models with runtime validation, custom root types, and extensive error messages. Use Pydantic for I/O‑bound data (API requests, config files) where validation is critical; use dataclasses for internal data structures where performance and simplicity are priorities.  
- **Key dataclass features**:  
  - `__post_init__`: Hook to run custom initialization logic after `__init__` generated by dataclass.  
  - **Field factories** (`field(default_factory=list)`) create new mutable objects per instance, avoiding shared defaults.  
  - **Frozen dataclasses** (`@dataclass(frozen=True)`) make instances immutable; attempting to assign to a field raises `FrozenInstanceError`.  
  - **Inheritance**: Dataclass fields are merged; base class fields appear first. Use `field(init=False)` to exclude a field from `__init__`.  
- **When to choose Pydantic**: When you need schema validation, custom error handling, or conversion of raw input (JSON, env vars) into typed models. When you need runtime type enforcement beyond simple structural typing.
