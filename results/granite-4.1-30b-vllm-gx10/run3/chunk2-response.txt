**Kubernetes**

**K1 — Easy:**  
- **Deployment**: Manages replicated, stateless pods. Ideal for apps that can be scaled horizontally and don’t require stable network identities or persistent storage. Uses a ReplicaSet under the hood.  
- **StatefulSet**: Extends Deployments for stateful applications. Provides stable, unique network identifiers, ordered, graceful deployment and scaling, and persistent storage via PVCs. Suitable for databases, queues, or any service needing stable identities and ordering.

**K2 — Easy:**  
A Service of type **ClusterIP** creates an internal virtual IP that is only reachable within the cluster. Kubernetes’ **kube-proxy** (using iptables or IPVS) watches the Service and creates rules that load‑balance incoming traffic to the matching pod **Endpoints** (the pod IPs that satisfy the Service’s selector). The client inside the cluster sends requests to the ClusterIP, which is then redirected by kube-proxy to one of the healthy pods.

**K3 — Medium:**  
- **PersistentVolume (PV)**: A piece of storage in the cluster that is provisioned by an administrator or dynamically via a **StorageClass**. It is a cluster‑wide resource.  
- **PersistentVolumeClaim (PVC)**: A request for storage by a user. It binds to a matching PV (based on size, access modes, and optionally storage class). PVCs are namespace‑scoped.  
- **StorageClass**: Describes a class of storage (e.g., SSD, HDD, NFS) and defines the provisioner that creates PVs on demand. When a PVC specifies a storage class, the cluster automatically provisions a PV of that class.  
**Relation**: PVC → selects/requests → PV (via StorageClass). The PV satisfies the PVC’s requirements, and the pod mounts the PVC.

**K4 — Medium:** (4+ checks)  
1. **Pod logs**: `kubectl logs <pod>` to see crash messages or stack traces.  
2. **Container restart count**: `kubectl describe pod <pod>` – high restarts confirm CrashLoopBackOff.  
3. **Readiness/Liveness probes**: Verify they are correctly configured; a failing probe can cause restarts.  
4. **Resource limits/requests**: Check if the pod is OOM‑killed (`kubectl describe pod` shows `OOMKilled`).  
5. **Events**: `kubectl get events --field-selector involvedObject.name=<pod>` for admission or scheduling errors.  
6. **Config/Env**: Ensure required ConfigMaps, Secrets, or environment variables are present.

**K5 — Medium:**  
**CoreDNS** provides DNS service for the cluster, resolving service names (e.g., `mysvc.myns.svc.cluster.local`) to IPs. If CoreDNS pods are down:  
- New DNS queries fail → services become unreachable by name.  
- Existing cached resolutions may still work temporarily.  
- The API server may become unavailable if it relies on DNS for its own endpoints.  
Recovery involves restarting CoreDNS (usually via its Deployment) and ensuring the ConfigMap and StatefulSet are healthy.

**K6 — Hard:**  
**Scheduling phases**:  
1. **Filtering (predicate)** – eliminates nodes that don’t meet requirements (e.g., resource capacity, pod affinity/anti‑affinity, taint‑toleration, node selector, architecture, OS).  
2. **Scoring (priority)** – ranks remaining nodes based on metrics (e.g., leastRequested, balancedResourceAllocation, nodeAffinityMatching, interPodAffinityPriority, imageLocality).  
**Specific factors**:  
- **Resource requests/limits** – ensures enough CPU/Memory.  
- **Node affinity & anti‑affinity** – prefer/avoid nodes based on labels.  
- **Taints & tolerations** – exclude nodes with incompatible taints unless pods have matching tolerations.  
The scheduler picks the highest‑scoring node; if tied, it uses a random or deterministic tie‑breaker.

**K7 — Hard:**  
- **Scheduling**: Node has 4 GB (≈4096 Mi) – 3.5 GB already requested → free 1.5 GB. The pod requests 256 Mi, so it **will be scheduled**.  
- **Runtime usage 600 Mi**:  
  - Requests (256 Mi) are still satisfied.  
  - Limits (512 Mi) are exceeded → the container may be **throttled** (CPU) or **OOM‑killed** if memory pressure triggers. The pod remains running unless OOM kill occurs.

**K8 — Hard:** (Ingress → NGINX → Service → Endpoints → kube‑proxy)  
1. **External Load Balancer (LB)** (cloud‑provider or hardware) receives traffic on port 80/443 and forwards to the Ingress controller’s NodePort or LoadBalancer IP.  
2. **NGINX Ingress Controller** (running as a pod) listens on that port. It reads the Ingress resource, builds an NGINX config, and matches the incoming host/path to a rule.  
3. **Ingress resource** defines rules → maps to a **Kubernetes Service** (type ClusterIP).  
4. **Service** exposes a stable virtual IP; its **Endpoints** object lists the IPs of the backend pods selected by the Service selector.  
5. **kube-proxy** (or IPVS) on each node implements the Service by adding iptables/IPVS rules that rewrite destination IPs/ports to one of the Endpoint IPs. Traffic is then forwarded to the appropriate pod.  
6. The **application pod** receives the request and processes it.

**K9 — Medium:**  
- **NetworkPolicy**: Defines rules for ingress/egress traffic between pods. Applied at the pod level via selectors.  
- **Default behavior** (no policies): **Allow all** traffic between pods in the same namespace.  
- **When applied**: Only traffic matching the policy’s rules is permitted; all other traffic is dropped. Selecting specific pods isolates them, enabling micro‑segmentation.

**K10 — Medium:**  
- **RollingUpdate**: Gradually replaces old pods with new ones, keeping the service available. Controls `maxUnavailable` and `maxSurge`.  
- **Recreate**: Terminates all old pods before creating new ones. Causes a brief full outage.  
**Choose Recreate** when:  
  - The new version is incompatible with the old (e.g., database schema migration).  
  - You need zero traffic during the switch (short maintenance window).  
  - The workload is stateless and can tolerate a brief downtime.

**K11 — Easy:**  
A **namespace** is a virtual cluster that provides scope for names (pods, services, etc.). Default namespaces in a fresh cluster: `default`, `kube-system`, `kube-public`, and often `kube-node-lease` (for node heartbeats).

**K12 — Easy:**  
`kubectl describe pod <name>` shows:  
1. **Events** (creation, scheduling errors, OOM kills).  
2. **Container state** (ready, waiting, terminated) with reason and message.  
3. **Mounted volumes** and their source details.  
4. **Node conditions** and resource requests/limits.  
`kubectl get pod` only provides a concise table of name, ready status, restarts, and age.

**K13 — Easy:**  
A **ConfigMap** holds key‑value configuration data separate from images. Pods can consume it via:  
- **Environment variables**: `envFrom` or `env` referencing the ConfigMap.  
- **Volume mount**: Mount the ConfigMap as a directory; files inside the pod reflect the key‑value pairs.  
Other methods: **Command args** (`args: ["-config", "$(CONFIG_MAP_KEY)"]`) or **Downward API**.

**K14 — Easy:**  
- **ClusterIP**: Exposes the Service only inside the cluster (default).  
- **NodePort**: Opens a specific high‑numbered port on every node; reachable from outside via `<NodeIP>:NodePort`.  
- **LoadBalancer**: Requests an external cloud LB that directs traffic to NodePorts (or directly to the service on cloud providers). Provides a public IP.

**K15 — Easy:**  
A **DaemonSet** ensures exactly one pod runs on every (or selected) node, typically for node‑level daemons (logging, monitoring, network plugins). Use a DaemonSet instead of a Deployment when the workload must run once per node and must start before other pods (e.g., fluentd, kube-proxy).

**K16 — Medium:**  
- **Taints** (on nodes) repel pods unless those pods have matching **tolerations**. They prevent scheduling of unsuitable workloads.  
- **Node affinity** (pod spec) *attracts* pods to nodes based on labels (preferred or required).  
**Use cases**:  
  - **Taint**: Mark a node as `dedicated=infra:NoSchedule` to ensure only infra pods (with toleration) run there.  
  - **Node affinity**: Schedule GPU workloads to nodes labeled `accelerator=nvidia-gpu` with `requiredDuringSchedulingIgnoredDuringExecution`.

**K17 — Hard:**  
A **Kubernetes Operator** is a custom controller that extends the API with domain‑specific resources (CRDs) and encodes operational knowledge (lifecycle, backups, scaling) in code.  
- **Standard controller** (e.g., Deployment controller) manages built‑in resources following generic reconciliation loops.  
- **Operator pattern** solves complex stateful workloads (databases, distributed caches) where manual ops (config, upgrades, failover) are non‑trivial. It automates tasks that are hard to express with native Kubernetes primitives.

**K18 — Hard:**  
- **etcd** uses **Raft** consensus, requiring a majority (quorum) of members to agree on log entries. Writes are durable only after being replicated to a majority.  
- **Quorum loss** (e.g., 2/3 nodes down in a 3‑node cluster) means the cluster cannot accept new writes; existing reads may continue from cached data but eventually stall.  
- **Recovery**:  
  1. **Do NOT** start a new etcd instance with the old data; it would cause divergence.  
  2. **Restore** from a recent snapshot + WAL of a surviving member, or **re‑bootstrap** the cluster with `etcd --initial-cluster` specifying the remaining healthy nodes.  
  3. If only 1 node remains, you must **re‑create** the cluster from backup, as Raft cannot form quorum with a single node.

**K19 — Hard:**  
**RBAC** (Role‑Based Access Control) ties **subjects** (users, groups, service accounts) to **permissions** via Roles/ClusterRoles and Bindings.  
- **Role**: Namespace‑scoped permissions (e.g., read Pods).  
- **ClusterRole**: Cluster‑wide permissions.  
- **RoleBinding**: Binds a Role to subjects within a namespace.  
- **ClusterRoleBinding**: Binds a ClusterRole to subjects cluster‑wide.  
**RBAC manifests for read‑only pod & log access in `my-ns`**:  

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-ns
  name: pod-log-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: my-ns
  name: pod-log-reader-binding
subjects:
- kind: ServiceAccount
  name: my-sa
  namespace: my-ns
roleRef:
  kind: Role
  name: pod-log-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:**  
- **ndots** in `/etc/resolv.conf` defines how many dots a name must have before a **absolute** query is sent directly to DNS (bypassing search domains). Low `ndots` (default 1) causes many short names (e.g., `service`) to be tried as FQDNs with each search suffix, generating extra queries and latency.  
- **Fix with `dnsConfig`**: In the pod spec, set `dnsConfig: { options: [{ name: "ndots", value: "4" }] }` (or appropriate value) to raise the threshold, reducing unnecessary searches. Also specify `nameservers` if needed.

**Development**

**D1 — Easy:**  
- **git merge**: Creates a new merge commit that combines histories of two branches. Keeps the original branch commits intact.  
- **git rebase**: Rewrites history by replaying local commits on top of the target branch, producing a linear history.  
**Avoid rebasing** when the branch is public/shared (others have already pulled it) because it changes commit IDs and can cause confusion or force‑push conflicts.

**D2 — Easy:**  
- **TCP**: Connection‑oriented, reliable, ordered byte stream; guarantees delivery, retransmission, flow control.  
  - Protocols: HTTP, FTP, SSH.  
- **UDP**: Connectionless, best‑effort; no guarantees of delivery, ordering, or duplicate protection. Faster, lower overhead.  
  - Protocols: DNS, DHCP, RTP (media streaming), SNMP.

**D3 — Medium:**  
A **race condition** occurs when two or more threads/processes access shared data concurrently and the outcome depends on the nondeterministic timing of their execution.  
**Example (Python)**:  

```python
import threading

balance = 0
def deposit():
    global balance
    for _ in range(1000):
        balance += 1

threads = [threading.Thread(target=deposit) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(balance)   # Often < 10_000 due to lost updates
```

Without synchronization (locks), increments interleave, causing lost updates.

**D4 — Medium:**  
- **Symmetric encryption**: Same key for encryption & decryption (e.g., AES). Fast, used for bulk data.  
- **Asymmetric encryption**: Public/private key pair (e.g., RSA, EC). Public key encrypts/verifies; private key decrypts/signs.  
**TLS usage**:  
  1. **Handshake** uses asymmetric crypto to securely exchange a **pre‑master secret** (via RSA key exchange or ECDHE).  
  2. The pre‑master secret is turned into a **session key** (symmetric).  
  3. Subsequent data is encrypted with that symmetric session key (AES, ChaCha20) for efficiency.

**D5 — Medium:**  
A **container image layer** is a read‑only filesystem snapshot representing changes (e.g., adding a file, installing a package). Images consist of a stack of layers built on top of a base image.  
**Layer caching**: Docker rebuilds only layers that changed since the last build. Best practices:  
- Put commands that change often (e.g., `COPY . /app`) **late** in the Dockerfile.  
- Install dependencies first (so cache can be reused).  
- Use multi‑stage builds to discard unnecessary layers.

**D6 — Hard:** (4 checks for intermittent 503)  
1. **Pod health**: Verify liveness/readiness probes (`kubectl describe pod`) – pods may be restarting.  
2. **Resource saturation**: Check CPU/memory usage (`kubectl top pod`) – OOM or throttling can cause 503.  
3. **Upstream service**: If the API calls another backend, ensure that backend is reachable and not returning errors.  
4. **Rate limiting / circuit breaker**: Examine application logs for throttling messages or circuit‑breaker state changes.  
Order: start with pod health, then resources, then downstream dependencies, finally application‑level logic.

**D7 — Hard:**  
**CAP theorem**: In a distributed system, you can have at most two of the three guarantees:  
- **Consistency (C)** – all nodes see the same data at the same time.  
- **Availability (A)** – every request receives a (non‑error) response.  
- **Partition tolerance (P)** – system continues to operate despite network splits.  
**CP example**: **Cassandra** (tunable consistency) prefers consistency and partition tolerance; during a partition, it may reject writes to maintain consistency.  
**AP example**: **Amazon DynamoDB** (eventual consistency) stays available even during partitions, allowing divergent views that reconcile later.

**D8 — Medium:**  
- **Horizontal scaling**: Adds more instances (pods, VMs) of a service, spreading load. Requires statelessness or external state store. Enabled by load balancers, service meshes, and orchestration (K8s Deployments).  
- **Vertical scaling**: Increases resources (CPU, RAM) of an existing instance. Limited by hardware and often requires downtime.  
**Patterns for horizontal**: microservices, stateless apps, sharding, consistent hashing, autoscaling (HPA, KEDA).

**D9 — Easy:**  
An **environment variable** is a key‑value pair available to processes. To persist across sessions on Linux:  
- Add `export VAR=value` to `~/.bashrc` or `~/.profile`.  
- For system‑wide, add to `/etc/environment` or create a file under `/etc/profile.d/`.  
- After editing, run `source ~/.bashrc` or restart the shell.

**D10 — Easy:**  
- **JSON**: Lightweight, text‑based, strictly hierarchical (objects/arrays). Widely supported, fast parsing.  
  - Advantage: Simplicity, language‑agnostic, good for APIs.  
- **YAML**: Superset of JSON, supports comments, more human‑readable with indentation, allows anchors & aliases.  
  - Advantage: Better for configuration files where readability and comments matter.  

**D11 — Easy:**  
A **REST API** uses HTTP methods to perform CRUD operations on resources.  
- **GET**: Retrieve a resource (idempotent, safe).  
- **POST**: Create a new resource (not idempotent).  
- **PUT**: Replace an existing resource entirely (idempotent).  
- **DELETE**: Remove a resource (idempotent).

**D12 — Easy:**  
**Version pinning** locks dependencies to specific versions (e.g., `package==1.2.3`). It ensures builds are reproducible, avoids surprise breakage from transitive updates, and simplifies debugging. Without pinning, a dependency could upgrade to an incompatible version, causing flaky builds or runtime errors.

**D13 — Easy:**  
- **Compiled language**: Source code translated to machine code before execution (e.g., C, Go, Rust).  
- **Interpreted language**: Source code executed directly by an interpreter (e.g., Python, Ruby, JavaScript (Node)).  
Compiled languages generally offer better performance; interpreted languages provide faster iteration and dynamic features.

**D14 — Medium:**  
A **reverse proxy** sits in front of servers, forwarding client requests to backend services and returning responses. It can perform load balancing, SSL termination, caching, and request modification.  
A **forward proxy** sits on the client side, forwarding client requests to the internet and hiding client identity.  
**Examples**:  
- **NGINX**: Reverse proxy for web apps, load balancing, HTTP/2, caching.  
- **HAProxy**: High‑performance TCP/HTTP reverse proxy, often used for database traffic.  
**Use case**: NGINX as an Ingress controller in Kubernetes; HAProxy for database connection pooling.

**D15 — Medium:**  
A **deadlock** occurs when a set of processes are each waiting for resources held by others, forming a circular wait. The **Coffman conditions** are:  
1. **Mutual exclusion** – at least one resource is non‑shareable.  
2. **Hold and wait** – a process holds resources while waiting for others.  
3. **No preemption** – held resources cannot be forcibly taken.  
4. **Circular wait** – a ring of processes each waiting for the next.  
All four must hold simultaneously for a deadlock.

**D16 — Hard:**  
**Eventual consistency** guarantees that, given no new updates, all replicas will converge to the same value eventually.  
- **Cassandra**: Uses **hinted handoff** and **read repair**. Consistency levels (`ONE`, `QUORUM`, `ALL`) let clients trade latency for freshness. `READ` with `QUORUM` ensures reading from a majority, giving strong consistency; `ONE` provides fast but possibly stale reads.  
- **Read‑after‑write**: By specifying `QUORUM` for both read and write, a client can be assured the latest write is visible on the read, achieving **read‑your‑writes** consistency.

**D17 — Hard:**  
**mTLS (mutual TLS)**: Both client and server present certificates and authenticate each other.  
**Handshake steps**:  
1. **Client → Server**: `ClientHello` (supported ciphers, extensions including `application_layer_protocol_negotiation` and `status_request`).  
2. **Server → Client**: `ServerHello`, server certificate (signed by CA), `CertificateRequest` (asking client cert).  
3. **Client → Server**: Client certificate, `Finished` message (MAC of handshake).  
4. **Server → Client**: `Finished` message.  
Both sides verify the peer’s certificate chain against trusted CAs.  
**Common uses**: Service‑mesh (Istio, Linkerd), API gateways, internal microservice communication, VPN‑less secure RPC.

**D18 — Hard:**  
A **hash table** stores key‑value pairs using a hash function to compute an index into an array of **buckets**.  
- **Collision resolution**:  
  - **Chaining**: Each bucket holds a linked list (or dynamic array) of entries that hash to the same index. Lookup traverses the list.  
  - **Open addressing** (linear probing, quadratic probing, double hashing): On collision, probe subsequent buckets until an empty or matching slot is found.  
**Complexities**:  
- **Average case**: O(1) for insertion, lookup, deletion (assuming low load factor).  
- **Worst case**: O(n) if many collisions (e.g., all keys map to same bucket) or table is full, requiring rehashing. Proper resizing (when load factor > threshold) keeps amortized O(1).

**D19 — Hard:**  
**Circuit breaker** monitors calls to a downstream service and trips to **open** state after too many failures, short‑circuiting further calls and returning an immediate error.  
- **Closed**: Normal operation; calls pass through, failure metrics are collected.  
- **Open**: Bypasses the remote service; returns fallback/error quickly, allowing the calling system to recover. After a timeout, it moves to **half‑open**.  
- **Half‑open**: Allows a limited number of test requests; if they succeed, it closes; otherwise, it reopens.  
**Relation to retries**: Retries can exacerbate failures (thundering herd). Circuit breakers prevent excessive retries by failing fast. When combined with **exponential backoff**, retries are spaced out, reducing load during recovery.

**D20 — Hard:**  
- **Optimistic concurrency control (OCC)** assumes conflicts are rare. Operations proceed without locks; before committing, the system checks a version/timestamp. If the version changed, the transaction is aborted and must be retried.  
  - **Use case**: Web apps with form edits; `UPDATE table SET … WHERE version = X`.  
- **Pessimistic concurrency control (PCC)** locks resources (row‑level, table‑level) before reading/writing, ensuring no other transaction can modify them.  
  - **Use case**: Financial transactions where lost updates are unacceptable; `SELECT … FOR UPDATE` in PostgreSQL.  
**Choice**: Use OCC for high‑throughput, low‑contention workloads; use PCC when data integrity is critical and conflicts are frequent.
