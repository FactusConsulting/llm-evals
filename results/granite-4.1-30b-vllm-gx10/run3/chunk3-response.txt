**OpenTofu / Terraform**

**T1 — Easy:**  
`tofu plan` generates and displays the execution plan, showing what actions will be performed without making any changes. `tofu apply` executes the actions in the plan, creating, updating, or deleting resources in the infrastructure.

**T2 — Easy:**  
State in OpenTofu is a snapshot of the current infrastructure (resource IDs, attributes, etc.) stored locally (`terraform.tfstate`) or remotely. Remote state is crucial for collaboration (multiple users can safely run commands), state consistency across environments, and security (sensitive data can be encrypted and access‑controlled).

**T3 — Medium:**  
- `count` creates a fixed number of identical instances based on an integer.  
- `for_each` creates instances based on a map or set, allowing each instance to have distinct attributes.  
`for_each` is preferred when you need unique identifiers or properties per instance (e.g., VMs with different names).

**T4 — Medium:**  
If a resource is changed manually, the next `tofu plan`/`apply` will detect a drift: the current live attribute differs from the recorded state. OpenTofu will propose an update to reconcile the difference (e.g., reset a changed VM configuration). To avoid unwanted overwrites, use `prevent_destroy` or `ignore_changes`, or manually refresh state with `tofu refresh`.

**T5 — Medium:**  
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
  image_id = "ami-12345"
  size     = "t2.micro"
}
```

**T6 — Hard:**  
`terraform_remote_state` data source reads state from another workspace/module, exposing all output values. Output values are the named exports defined in a module. The recommended alternative is **module composition** (calling the module directly) because it provides tighter typing, better version pinning, and avoids duplicating state look‑ups.

**T7 — Hard:**  
The `kubeconfig` output depends on a `null_resource` with a `remote-exec` provisioner that runs after the cluster is up. On the first apply, the provisioner hasn’t executed yet, so the output is empty and dependent resources fail. Fix: add an explicit `depends_on = [null_resource.kubeconfig]` or use `null_resource`’s `triggers` to ensure the output is refreshed before dependent resources are created.

**T8 — Medium:**  
`tofu import` brings existing infrastructure under Terraform management by mapping live resources to configuration. Limitations: attribute mismatches, complex resource graphs, and lack of state for imported resources’ dependencies. The `import` block (≥1.5) lets you declare the import directly in configuration, enabling version control of the import mapping and automatic refresh of the imported state.

**T9 — Easy:**  
A **variable** (input) allows users to supply values at runtime (e.g., region, instance type). An **output** exports values computed by the configuration (e.g., public IP, ARN) for consumption by other modules or scripts.

**T10 — Easy:**  
A **provider** defines the API and authentication details for a cloud/service (AWS, Azure, etc.). Running `tofu plan` without `tofu init` fails because the provider plugins and state backend aren’t downloaded/initialized, leading to “no suitable provider found” errors.

**T11 — Easy:**  
`.terraform.lock.hcl` records the exact versions of providers and modules used, ensuring reproducible runs across environments. Committing it guarantees every team member and CI pipeline uses the same dependency graph.

**T12 — Easy:**  
`tofu destroy` deletes all resources managed by the current state. To target a single resource: `tofu destroy -target=module.example.resource_name`. Use with caution as it bypasses dependency checks.

**T13 — Easy:**  
A **data source** reads information from external systems without creating resources (e.g., `aws_ami` to find the latest AMI ID). Use a data source when you need read‑only info (lookup IDs, DNS records) rather than provisioning a managed resource.

**T14 — Medium:**  
- **locals** are computed values scoped to a module, defined at parse time.  
- **variables** are inputs supplied at runtime.  
Use **locals** for reusable constants, derived values, or to simplify expressions without exposing them as configurable inputs.

**T15 — Medium:**  
The **lifecycle** block customizes resource behavior:  
- `create_before_destroy` ensures a new resource is created before the old one is deleted (useful for zero‑downtime migrations).  
- `prevent_destroy` blocks accidental deletion (protect critical resources).  
- `ignore_changes` tells Terraform to tolerate modifications to certain attributes (e.g., auto‑generated IDs).  

**T16 — Medium:**  
A **moved block** records that a resource’s configuration has been relocated (e.g., from one module to another) without destroying/recreating it. It updates the state file to reflect the new address, preserving the underlying infrastructure.

**T17 — Hard:**  
OpenTofu builds a **dependency graph** from implicit connections (references in expressions) and explicit `depends_on`. Implicit dependencies enable parallel execution; explicit `depends_on` forces sequential ordering, reducing parallelism and should be used only when hidden dependencies exist. Misuse can dramatically increase plan/apply time.

**T18 — Hard:**  
1. **State pruning** – remove unused resources (`tofu state rm`) to shrink state size.  
2. **Backend optimizations** – use a fast remote backend (e.g., S3 with DynamoDB locking) and enable **state locking** to avoid contention.  
3. **Workspaces / modularization** – split large configurations into smaller modules with isolated state, limiting the scope of each plan.  
4. **Parallelism tuning** (`-parallelism=N`) – increase parallel resource operations, but watch for rate‑limit errors.  
Trade‑offs include increased complexity, potential for fragmented state management, and risk of missing cross‑module dependencies.

**T19 — Hard:**  
OpenTofu locks the state file during `apply`, `refresh`, and `plan` via the backend (e.g., DynamoDB table entry). If a lock isn’t released (CI crash), subsequent operations block. Manually break the lock by deleting the lock entry from the backend (e.g., via AWS Console or CLI). Risk: concurrent runs may corrupt state, leading to drift or data loss.

**T20 — Hard:**  
1. **Add remote backend** in configuration:  
   ```hcl
   terraform {
     backend "s3" {
       bucket         = "my-terraform-state"
       key            = "path/to/terraform.tfstate"
       region         = "us-east-1"
       dynamodb_table = "terraform-locks"
     }
   }
   ```
2. Run `tofu init` – it prompts to copy the existing local state to the new remote location.  
3. Verify: `tofu state list` should show resources; `tofu plan` should run without state errors.  
4. Optionally, run `tofu refresh` to ensure state matches live resources.  

**Ansible**

**A1 — Easy:**  
- **Playbook**: YAML file that defines a set of plays (host groups + tasks).  
- **Role**: Reusable modular structure (tasks, handlers, files, templates, vars) that can be included in playbooks.  
- **Task**: A single action (module call) executed on a host.

**A2 — Easy:**  
`ansible_facts` is a dictionary of system information gathered by the `setup` module. Access the OS family with `{{ ansible_facts.os_family }}` (e.g., “Debian”, “RedHat”).

**A3 — Medium:**  
- **command**: Executes a system command without a shell; no shell interpolation, safer for simple commands.  
- **shell**: Runs through the target’s shell, allowing pipes, redirects, and variable expansion.  
- **raw**: Bypasses Python dependency, sending raw SSH commands; used for bootstrapping Python‑less hosts.  

Use **command** for basic, single‑argument tasks, **shell** when shell features are needed, and **raw** for initial provisioning.

**A4 — Medium:**  
Idempotency means running a task multiple times produces the same state without side effects.  
- **Idempotent**: `apt: name=nginx state=present` (re‑running leaves nginx installed).  
- **Non‑idempotent**: `command: echo "hello" > /tmp/file` (each run overwrites, changing file content). Use modules with `state` parameters or `when` conditions to enforce idempotence.

**A5 — Medium:**  
```yaml
- name: Install htop with correct package manager
  package:
    name:
      - "{{ ansible_facts.os_family == 'Debian' | ternary('htop', 'epel-release htop') }}"
    state: present
  when: ansible_facts.os_family in ['Debian', 'RedHat']
```
(Alternatively, use block with `when` for each family.)

**A6 — Hard:**  
Variable precedence (highest → lowest):  
1. **Role defaults**  
2. **Role vars (role/vars)**  
3. **Included vars (include_vars)**  
4. **Play vars**  
5. **Play vars_prompt / vars_files**  
6. **Host vars** (`host_vars/hostname`)  
7. **Group vars** (`group_vars/all`, `group_vars/group`)  
8. **Extra vars** (`-e var=val` on CLI)  
9. **set_fact / register** (runtime facts)  

**A7 — Hard:**  
```yaml
- hosts: rke2_nodes
  serial: 3          # first 3 nodes run concurrently
  tasks:
    - name: Deploy RKE2 agent
      # ... agent install task ...
  post_tasks:
    - name: Wait for first 3 nodes to finish
      wait_for:
        host: "{{ inventory_hostname }}"
        port: 6443
        delay: 10
        timeout: 300
  when: inventory_hostname in groups['rke2_nodes'][:3]
```
Use two plays: first play with `serial: 3` for the initial nodes, then a second play (or `when` condition) for the remaining nodes after the first batch completes.

**A8 — Hard:**  
`ansible-vault` encrypts sensitive data. To encrypt a single variable:  
```bash
ansible-vault encrypt_string 'secret_value' --name 'my_var' --vault-password-file .vault_pass.txt
```  
Insert the resulting encrypted string into the vars file, e.g., `my_var: !vault | <encrypted data>`.

**A9 — Easy:**  
An **inventory** lists managed hosts.  
- **Static inventory**: plain text file (INI or YAML) manually edited.  
- **Dynamic inventory**: script or program that generates JSON host lists (e.g., AWS EC2, OpenStack) on demand.

**A10 — Easy:**  
```bash
ansible webservers -m command -a "df -H"
```  
or using the `setup` module: `ansible webservers -m setup -a "filter=ansible_mounts"`.  

**A11 — Easy:**  
A **handler** is a special task notified by other tasks via `notify`. It runs **once** after all tasks in a play complete, typically for service restarts. Trigger with `notify: restart apache`.

**A12 — Easy:**  
`ansible.cfg` centralizes configuration. Common settings:  
- `inventory = ./inventory`  
- `remote_user = ubuntu`  
- `private_key_file = ~/.ssh/id_rsa`  
- `forks = 10` (parallelism)  

**A13 — Easy:**  
`register` captures output of a task in a variable:  
```yaml
- name: Get package list
  command: dpkg -l
  register: pkg_list

- name: Show installed packages
  debug:
    msg: "{{ pkg_list.stdout_lines }}"
```  

**A14 — Medium:**  
- **include_tasks**: dynamically includes a task list during playbook execution; supports conditionals (`when`).  
- **import_tasks**: statically includes tasks at parse time; cannot be conditional.  
Use **include_tasks** for conditional or looped task inclusion; **import_tasks** for reusable, always‑included task collections.

**A15 — Hard:**  
**Ansible Galaxy** is a repository for roles and collections. Use a `requirements.yml` like:  
```yaml
roles:
  - src: geerlingguy.docker
    version: 3.2.0
collections:
  - name: community.general
```
Run `ansible-galaxy install -r requirements.yml` to fetch them.

**A16 — Hard:**  
Connection plugins determine how Ansible reaches hosts.  
- **ssh**: default, uses SSH for Linux/Unix.  
- **local**: runs tasks on the control node itself.  
- **network_cli**: for network devices using CLI (e.g., Cisco IOS).  
Choose based on target type: SSH for servers, local for control‑node tasks, network_cli for routers/switches.

**A17 — Hard:**  
`delegate_to: localhost` runs a task on the control node. `run_once: true` ensures it executes a single time even if multiple hosts are delegated. Example: gather IPs from remote hosts, then use them to update a DNS record on the control node:  
```yaml
- name: Collect remote IPs
  command: hostname -I
  run_once: false
  register: host_ips

- name: Update DNS on control node
  lineinfile:
    path: /etc/hosts
    line: "{{ host_ips.results[item].stdout }} {{ inventory_hostname }}"
  loop: "{{ host_ips.results }}"
  delegate_to: localhost
  run_once: true
```

**A18 — Hard:**  
1. **Increase forks** (`forks: 20`) for more parallelism, but watch memory/CPU usage.  
2. **Enable pipelining** (`pipelining: true`) reduces SSH overhead; requires `requiretty` disabled on remote.  
3. **Fact caching** (`fact_caching: jsonfile`) avoids re‑gathering facts on subsequent runs.  
4. **Mitogen** (or Ansible‑Runner) optimizes connection handling, drastically cutting latency for large inventories, but adds dependency complexity.  

**A19 — Hard:**  
Jinja2 templating syntax:  
- `{{ }}` evaluates and outputs expressions.  
- `{% %}` executes control structures (loops, conditionals).  
- `{# #}` denotes comments (not rendered).  

Template snippet for Nginx upstream:  
```jinja
upstream backend {
{%- for server in servers %}
  server {{ server.host }}:{{ server.port }} {% if server.health_check %} # health check enabled {% endif %};
{%- endfor %}
}
```

**A20 — Hard:**  
```yaml
- hosts: webservers
  serial: 4                     # 20 servers → 5 batches of 4
  become: true
  vars:
    lb_group: loadbalancers

  pre_tasks:
    - name: Deregister server from LB
      uri:
        url: "http://{{ host }}:8080/deregister"
      delegate_to: "{{ host }}"
      ignore_errors: yes   # tolerate if already deregistered

  tasks:
    - name: Deploy new app version
      # ... copy/ template files, install dependencies ...

    - name: Restart service
      service:
        name: myapp
        state: restarted
      notify: Health check

  post_tasks:
    - name: Register server with LB
      uri:
        url: "http://{{ host }}:8080/register"
        method: POST
        body: '{"host": "{{ ansible_host }}", "port": 80}'
      delegate_to: "{{ host }}"

  handlers:
    - name: Health check
      uri:
        url: "http://{{ ansible_host }}:80/health"
        status_code: 200
      register: health
      until: health.status == 200
      retries: 5
      delay: 10
      ignore_errors: no

  rescue:
    - name: Rollback deployment
      # ... revert to previous version ...
      when: health is failed

  when: inventory_hostname in groups['webservers']
```
This playbook performs a rolling update with batch control, LB registration/deregistration, health verification, and automatic rollback on failure.
