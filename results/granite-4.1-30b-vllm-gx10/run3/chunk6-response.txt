**JavaScript / TypeScript**

**JS1** — *var, let, const & hoisting*  
- **var**: function-scoped (or global if outside a function), can be redeclared, and is **hoisted** – the declaration is moved to the top of its scope, but initialization stays.  
- **let** & **const**: block-scoped, cannot be redeclared, and are also hoisted but are in a **temporal dead zone** from the start of the block until the actual declaration line (accessing them earlier throws a ReferenceError).  
- **const** additionally requires an initializer and the binding cannot be reassigned (the object it references can still be mutated).  
- **Hoisting** means that all declarations (var, let, const, function, class) are conceptually moved to the top of their containing scope during the compile phase, but for `let`/`const` the assignment part stays in place, creating the TDZ.

**JS2** — *Event loop, call stack, microtask & macrotask queues*  
- The **event loop** continuously checks the **call stack**. If the stack is empty, it processes pending tasks from two queues:  
  - **Macrotask queue** (also called the task queue): holds callbacks from timers (`setTimeout`, `setInterval`), I/O, UI rendering, etc. Each macrotask runs to completion before the next one starts.  
  - **Microtask queue**: holds promises’ `.then`/`.catch` handlers, `queueMicrotask`, `MutationObserver` callbacks, etc. After each macrotask (and after processing the microtask queue), the loop drains **all** microtasks before moving to the next macrotask.  
- This ordering ensures that promise resolutions happen promptly after the currently executing script, before the next timer fires or the browser repaints.

**JS3** — *Closures, classic for‑loop bug, fix*  
- A **closure** is a function that retains access to its lexical scope even after that scope has finished executing.  
  ```js
  function makeCounter() {
    let n = 0;
    return function() { return ++n; }; // closure over n
  }
  const c = makeCounter(); // c remembers n
  ```
- **Classic for‑loop closure bug**:  
  ```js
  for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i)); // all log 3
  }
  ```  
  Because `var` is function‑scoped, there’s a single `i` shared by all iterations. By the time the callbacks run, the loop has finished and `i` is 3.  
- **Fixes**:  
  1. Use `let` (block‑scoped) inside the loop – each iteration gets its own `i`.  
  2. Or wrap in an IIFE that captures the current `i`:  
     ```js
     for (var i = 0; i < 3; i++) {
       (function(i) {
         setTimeout(() => console.log(i));
       })(i);
     }
     ```

**JS4** — *Promise, async/await, error handling, Promise.allSettled vs Promise.all*  
- **Promise**: an object representing the eventual completion (or failure) of an asynchronous operation. It has three states: pending, fulfilled, rejected.  
- **async/await**: syntactic sugar over promises. An `async` function always returns a promise; `await` pauses execution until the awaited promise settles.  
  ```js
  async function fetchUser() {
    try {
      const res = await fetch('/api/user');
      const data = await res.json();
      return data;
    } catch (e) {
      // handles both rejected fetch and JSON parse errors
      console.error(e);
    }
  }
  ```
- **Error handling**:  
  - With promises: `.catch()`, `Promise.all([...]).catch()`.  
  - With async/await: use `try/catch` around `await` expressions; an uncaught rejection becomes a rejected promise from the async function.  
- **Promise.all**: races all input promises; fulfills with an array of results **only if every promise fulfills**. If any promise rejects, the whole result immediately rejects (first rejection wins).  
- **Promise.allSettled**: waits for **all** promises to settle, returning an array of objects `{ status: "fulfilled" | "rejected", value?: any, reason?: any }`. Useful when you need to process results of both successes and failures.

**JS5** — *TypeScript interface vs type, discriminated unions*  
- **interface**:  
  - Can be extended (`interface A extends B`).  
  - Can be declared multiple times in the same scope (declaration merging).  
  - Primally used for defining object shapes with named properties.  
- **type**:  
  - Can represent any type, including unions, primitives, tuples, etc.  
  - Cannot be extended (but can be combined with intersection types).  
  - Cannot be merged across declarations.  
- **When to use**:  
  - Use `interface` for public API shapes that may grow via extension or merging.  
  - Use `type` for complex unions, intersections, or when you need to alias a primitive or tuple.  
- **Discriminated unions**: a set of types that share a common property (the *discriminant*) whose value uniquely identifies the concrete type. TypeScript can narrow based on that property.  
  ```ts
  interface Square { kind: 'square'; size: number; }
  interface Rectangle { kind: 'rectangle'; width: number; height: number; }
  type Shape = Square | Rectangle;

  function area(s: Shape) {
    switch (s.kind) {
      case 'square':   return s.size ** 2;
      case 'rectangle':return s.width * s.height;
    }
  }
  ```

**JS6** — *Prototypal inheritance, Object.create(), ES6 classes*  
- JavaScript uses **prototype‑based inheritance**: objects have an internal `[[Prototype]]` link to another object. Property lookup walks this chain until `null`.  
- **Object.create()**: creates a new object with the specified prototype (second argument can add properties via a property descriptor object).  
  ```js
  const animal = { eats: true };
  const dog = Object.create(animal, { barks: { value: true } });
  ```  
- **ES6 classes**: syntactic sugar over the prototype model. A class declaration defines a constructor function and its `prototype`. The `extends` keyword sets the prototype of the subclass’s constructor to the superclass’s prototype.  
  ```js
  class Animal { constructor(name) { this.name = name; } }
  class Dog extends Animal { constructor(name) { super(name); this.barks = true; } }
  // Dog.prototype.__proto__ === Animal.prototype
  ```

**JS7** — *`this` keyword, binding rules, bind()*  
- **Four binding rules (priority order)**:  
  1. **Explicit binding** via `call`, `apply`, or `bind`.  
  2. **Hard binding** (arrow functions have no own `this`; they inherit from the enclosing lexical scope).  
  3. **Implicit binding** (the object on the left of the dot when invoking a method).  
  4. **Default binding** (global object in non‑strict mode, `undefined` in strict mode).  
- **`bind()`**: returns a new function with `this` permanently set to the first argument, plus any leading arguments pre‑filled. Once bound, you cannot re‑bind the same function to a different `this` (though you can bind the bound function again, creating another layer).  
  ```js
  const obj = { name: 'Alice' };
  function greet() { console.log(`Hello, ${this.name}`); }
  const bound = greet.bind(obj); // new function with this === obj
  bound(); // Hello, Alice
  ```

**JS8** — *WeakRef & FinalizationRegistry, WeakMap keys*  
- **WeakRef**: holds a weak reference to an object; the target can be garbage‑collected. Accessing the reference returns the object or `undefined` if it’s been reclaimed. Useful for caches that should not prevent collection.  
- **FinalizationRegistry**: lets you register a cleanup callback that runs **after** an object becomes unreachable (but before it’s collected). Often paired with `WeakRef` to know when a weakly‑referenced object is about to be GC’d.  
- **Why WeakMap keys must be objects**: WeakMaps hold **weak references** to their keys. Only objects (including `null`) can have independent identity that can be reclaimed; primitives are boxed and never become unreachable in the same way. This ensures the map entry disappears automatically when the key is GC’d, preventing memory leaks.  

**JS9** — *V8 optimizations: hidden classes, inline caching, deoptimization*  
- **Hidden classes (shapes)**: V8 assigns a hidden class to objects with the same property layout. Property access uses this class to generate highly optimized code (monomorphic path). Adding/removing properties can change the class, triggering **re‑shaping**.  
- **Inline caching (IC)**: V8 records the hidden class of recently accessed objects and generates specialized code (monomorphic, polymorphic, megamorphic). Fast path when the same shape is seen repeatedly.  
- **Deoptimization**: Occurs when assumptions (e.g., shape stability) are violated, forcing V8 to fall back to a generic, slower path. Common triggers:  
  - Adding/removing properties after an object has been used.  
  - Changing prototype chain.  
  - Mixing types in an array (holey arrays).  
  - Using `delete` on an own property that was previously accessed.  
- **Avoiding deoptimization**: Keep object shapes stable, pre‑allocate arrays, avoid sparse arrays, and minimize dynamic property additions after first use.

**JS10** — *Tree‑shaking, ES modules vs CommonJS*  
- **Tree‑shaking**: Static analysis that removes unused exported symbols from the final bundle. It relies on **ES module** syntax (`import/export`) because these are **static** (can be analyzed at build time).  
- **ES modules**: Support named exports, static structure, and are side‑effect‑free by default (though `import` can have side effects). Build tools (Webpack, Rollup, esbuild) can drop unreferenced exports.  
- **CommonJS**: Uses `require`/`module.exports` with **dynamic** loading. The module body is executed at runtime, so the tool cannot know at build time which exports are used, making effective tree‑shaking impossible without additional heuristics (e.g., `sideEffects` flag in `package.json`).  

**JS11** — *null vs undefined, == vs ===, nullish coalescing & optional chaining*  
- **null**: intentional absence of any object value (assigned explicitly).  
- **undefined**: variable declared but not yet assigned, or property that doesn’t exist.  
- **== (abstract equality)**: performs type coercion. `null == undefined` yields `true`; otherwise, they are not loosely equal to any other value.  
- **=== (strict equality)**: no coercion; `null === undefined` is `false`.  
- **Nullish coalescing (`??`)**: returns the left operand if it is **not** `null` or `undefined`; otherwise returns the right operand.  
  ```js
  const value = null ?? 'default'; // 'default'
  ```  
- **Optional chaining (`?.`)**: safely accesses properties/methods; if the left side is `null`/`undefined`, evaluation short‑circuits and returns `undefined`.  
  ```js
  const name = user?.profile?.name;
  ```

**JS12** — *map, filter, reduce, flatMap*  
- **map(callback)**: transforms each element, returning a new array of the same length.  
- **filter(predicate)**: keeps elements for which predicate returns truthy.  
- **reduce(accumulator, [initialValue])**: folds the array into a single value. If no initial value is supplied, the first array element becomes the initial accumulator and reduction starts from the second element. Providing an explicit initial value allows reducing empty arrays without errors.  
- **flatMap**: a combination of `map` then `flat` of depth 1. Useful when the mapping function returns an array and you want to flatten one level.  
  ```js
  [[1,2],[3,4]].flatMap(x => x * 2); // [2,4,6,8]
  ```

**JS13** — *Template literals, tagged templates*  
- **Template literals** (`\`text ${expr} more\``) allow multi‑line strings and embedded expressions.  
- **Tagged templates**: a function placed before the template literal receives an array of string parts and the evaluated expressions.  
  ```js
  function htmlEscape(strings, ...values) {
    let result = '';
    strings.forEach((str, i) => {
      result += str;
      if (i < values.length) {
        result += String(values[i]).replace(/&/g,'&amp;')
                                    .replace(/</g,'&lt;')
                                    .replace(/>/g,'&gt;');
      }
    });
    return result;
  }
  const name = "<script>";
  const safe = htmlEscape`<div>${name}</div>`; // "&lt;script&gt;"
  ```
  Similar patterns exist for SQL query building, i18n, etc.

**JS14** — *Destructuring, rest operator*  
- **Object destructuring**: extracts properties into variables.  
  ```js
  const { a, b } = obj; // a = obj.a, b = obj.b
  const { a: localA, b: localB } = obj; // rename
  const { a, c = 10 } = obj; // default if c missing
  ```  
- **Array destructuring**: extracts by position.  
  ```js
  const [x, , z] = arr; // skip elements
  const [first, ...rest] = arr; // rest collects remaining items
  ```  
- **Rest operator (`...`)** in destructuring gathers remaining elements (array) or own enumerable properties (object) into a new array/object.

**JS15** — *for…in vs for…of*  
- **for…in**: iterates over **enumerable property keys** of an object (including inherited ones). Primarily for dictionaries/objects.  
- **for…of**: iterates over **values** of an iterable (arrays, strings, `Map`, `Set`, custom objects with `[Symbol.iterator]`).  
- **Why avoid for…in on arrays**: It yields numeric string keys (`"0"`, `"1"`, …) and also any enumerable properties added to `Array.prototype`, leading to unexpected behavior. Use `for…of` or `Array.prototype.forEach`.

**JS16** — *TypeScript generics, constraints, conditional & infer*  
- **Generics**: parameterize types/functions to be reusable with different concrete types.  
  ```ts
  function identity<T>(arg: T): T { return arg; }
  ```  
- **Generic constraints (`extends`)**: restrict a type parameter to a base type or interface.  
  ```ts
  function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
  }
  ```  
- **Conditional types (`T extends U ? X : Y`)**: choose a type based on a condition.  
  ```ts
  type NonNullable<T> = T extends null | undefined ? never : T;
  ```  
- **`infer` keyword**: used inside a conditional type to infer a type variable.  
  ```ts
  type ElementType<T> = T extends (infer U)[] ? U : T;
  // ElementType<string[]> → string
  ```  
- **Practical example**: a type that extracts the return type of a function.  
  ```ts
  type ReturnType<T extends (...args: any) => any> = T extends (...args: any) => infer R ? R : any;
  ```

**JS17** — *JavaScript module systems*  
- **CommonJS** (`require`, `module.exports`):  
  - Loaded **synchronously** at runtime.  
  - Each file is a module; `require` resolves modules eagerly.  
  - Widely used in Node.js pre‑ESM era.  
- **ES Modules** (`import`, `export`):  
  - **Static** structure; can be analyzed at compile time (enables tree‑shaking).  
  - Supports **named exports** and a default export.  
  - Loading is **asynchronous** under the hood (module record graph).  
- **Node.js handling**:  
  - Files with `.mjs` extension or a `"type": "module"` field in `package.json` are treated as ESM.  
  - `.js` files are CommonJS by default, but you can opt‑in to ESM via the `"type"` field.  
  - Interop: ESM can `import` CommonJS (the module’s `module.exports` becomes the default export) and CommonJS can `require` an ESM (the ESM’s default export is exposed).  

**JS18** — *TypeScript structural typing, excess property checks, extends vs satisfies, variance*  
- **Structural type system**: compatibility is based on member shape, not declaration. Two objects are compatible if one’s properties are a subset of the other’s.  
- **Excess property checks**: When assigning an object literal, TypeScript disallows properties not present in the target type (prevents typos). This check can be disabled with an index signature (`[key: string]: any`) or by using `satisfies` (see below).  
- **`extends` vs `satisfies`**:  
  - `extends` is used in **type positions** to create a subtype constraint.  
  - `satisfies` (introduced in TS 4.9) is a **type‑checking operator** for expressions: `expr satisfies Type` asserts that `expr` conforms to `Type` without changing its type. It’s useful for suppressing excess‑property errors on literals.  
    ```ts
    const config = { host: 'api', port: 8080 } satisfies ServerConfig;
    ```  
- **Variance (in, out)** (TS 4.7+):  
  - **Covariant** (`out`) positions: return types, readonly array/tuple elements, property values. A subtype is allowed.  
  - **Contravariant** (`in`) positions: parameter types, property keys. A supertype is allowed.  
  - You can annotate a type parameter with `in` or `out` to control variance explicitly.  

**JS19** — *Proxy & Reflect*  
- **Proxy**: creates a wrapper object that can intercept and redefine fundamental operations (property access, assignment, enumeration, function calls, etc.) via **traps**.  
  ```js
  const target = { value: 42 };
  const handler = {
    get(obj, prop) {
      console.log(`reading ${prop}`);
      return Reflect.get(obj, prop);
    },
    set(obj, prop, val) {
      console.log(`writing ${prop} = ${val}`);
      return Reflect.set(obj, prop, val);
    }
  };
  const p = new Proxy(target, handler);
  p.value; // logs reading value
  p.value = 100; // logs writing value = 100
  ```  
- **Reflect**: a built‑in object with methods that correspond to the proxy traps. Using `Reflect` inside a handler ensures the default behavior is preserved and avoids accidental self‑reference bugs.  
- **Practical uses**: validation (e.g., ensuring numeric types), logging, reactive data binding (MobX, Vue), lazy loading, mock objects, etc.

**JS20** — *SharedArrayBuffer & Atomics, Web Workers*  
- **SharedArrayBuffer**: allows **shared memory** between the main thread and workers (or between workers). It represents a raw byte buffer that can be viewed via typed arrays (`Int32Array`, `Float64Array`, etc.).  
- **Atomics**: provides **atomic operations** on `SharedArrayBuffer` to prevent race conditions when multiple agents read/write concurrently. Operations include `load`, `store`, `add`, `sub`, `and`, `or`, `xor`, `exchange`, `compareExchange`, `wait`, `notify`.  
- **Web Workers communication**:  
  - A worker can receive a `SharedArrayBuffer` via `postMessage(buffer, [buffer])`. The main thread and worker share the same memory region.  
  - **Ordering guarantees**: Atomics enforce a **happens‑before** relationship; operations are sequentially consistent.  
  - **`Atomics.wait` / `Atomics.notify`**: implement a **blocking wait** on a memory location. `wait(ab, index, value, timeout)` puts the calling thread to sleep until the value at `index` changes or a notification occurs. `notify(ab, index, count)` wakes up to `count` waiting threads. Useful for condition variables or producer‑consumer patterns.

**Bash**

**B1** — *$@ vs $*, "$@" vs "$"*  
- **$@**: expands to the positional parameters as separate words, **preserving each argument** (even if empty or containing spaces).  
- **$***: expands to a **single string** with the parameters separated by the first character of `IFS` (usually a space).  
- **"$@"**: each parameter is quoted, preventing word splitting and pathname expansion; ideal for passing arguments to another command.  
- **"$\***: quotes the whole concatenated string, treating it as one argument.  

**B2** — *set -euo pipefail*  
- **-e**: **Exit** immediately if a command exits with a non‑zero status (errors).  
- **-u**: Treat **unbound variables** as an error and exit.  
- **-o pipefail**: The pipeline’s return status is that of the **rightmost command** that exited with a non‑zero status, or zero if all succeed. Without it, the pipeline status is the exit status of the **last** command only.  

**B3** — *$(command) vs `command`, $((expr)) vs expr*  
- **$(command)**: modern, nested‑friendly command substitution; supports multiple layers without escaping backticks.  
- **`command`**: older syntax; cannot be nested directly (`echo $(echo $(echo hi))` works, but ``echo `echo `echo hi`` `` fails).  
- **$((expression))**: arithmetic expansion, evaluates integer expressions using C‑style operators.  
- **expr**: external command; requires careful quoting and escapes (`expr 1 + 2`). Slower and less feature‑rich than `$(( ))`.  

**B4** — *Process substitution*  
- Syntax: `<(...)` or `>(...)`. Replaces a command with a FIFO (named pipe) or temporary file, allowing the command to read from or write to it as if it were a file.  
- **Example with diff**:  
  ```bash
  diff <(sort file1) <(sort file2)
  ```  
  Here `sort file1` and `sort file2` run in subshells, their outputs become pseudo‑files that `diff` reads.  

**B5** — *Safe iteration over files with spaces*  
- `for f in $(ls)` splits on IFS, breaking filenames with spaces.  
- **Safe patterns**:  
  ```bash
  # Using glob with null delimiter (requires Bash 4.4+)
  shopt -s nullglob globstar
  for f in **/*; do ...; done

  # Or use find
  find . -maxdepth 1 -type f -print0 | while IFS= read -r -d '' f; do ...; done
  ```  
- The key is to **avoid word splitting** and **use NUL (`\0`) as a delimiter** when filenames may contain newlines or spaces.  

**B6** — *Here document vs here string*  
- **Here document** (`<<EOF`): reads **multiple lines** until the delimiter `EOF` is encountered.  
- **Here string** (`<<<`): treats the following **single line** as the standard input of a command.  
- **`<<-EOF`**: strips leading tabs (but not spaces) from the delimiter, useful for indenting the heredoc inside scripts.  

**B7** — *Redirection differences*  
```bash
cmd > file 2>&1   # 1. First redirect stdout (fd 1) to file. Then duplicate fd 2 (stderr) to wherever fd 1 currently points (file).
cmd 2>&1 > file   # 2. First duplicate fd 2 to fd 1 (stderr goes to stdout). Then redirect fd 1 (which now includes stderr) to file.
cmd &> file       # Equivalent to the first form; shorthand for “both stdout and stderr to file”.
```  
- **Result**: Both `cmd > file 2>&1` and `cmd &> file` send **both** streams to `file`.  
- The second form `cmd 2>&1 > file` works because after `2>&1`, stderr is a copy of stdout; then redirecting stdout also moves stderr along. In practice they are equivalent, but the first/`&>` forms are clearer and avoid subtle ordering bugs in more complex pipelines.  

**B8** — *Lock file function with cleanup*  
```bash
#!/usr/bin/env bash
set -euo pipefail

lock_dir="/var/lock/myapp"
lock_file="${lock_dir}/lock"

acquire_lock() {
  mkdir -p "$lock_dir"  # ensure parent exists
  if ln -s "$$" "$lock_file" 2>/dev/null; then
    # lock acquired
    trap release_lock EXIT
    return 0
  fi
  echo "Lock held by $(readlink "$lock_file")" >&2
  exit 1
}

release_lock() {
  rm -f "$lock_file"
}

# Optional: handle TERM/INT explicitly
trap 'echo "Interrupted, releasing lock"; release_lock; exit 130' TERM INT

acquire_lock
# --- critical section ---
sleep 10   # example work
# --- end critical section ---
release_lock
```
- **Why `mkdir`/symlink?** Creating a **directory** (`mkdir`) is **atomic** on most filesystems, preventing race conditions where two instances both see the lock absent and create it. A symlink to the PID (`$$`) lets you identify the holder.  

**B9** — *Single vs double quotes vs no quotes*  
- **Single quotes** (`'...'`): treat **everything** literally; no variable expansion, no special characters.  
  ```bash
  echo '$HOME'   # outputs $HOME
  ```  
- **Double quotes** (`"..."`): allow **variable and command substitution**, but backslashes still escape `$`, `` ` ``, `\`, and newline.  
  ```bash
  echo "HOME is $HOME"
  ```  
- **No quotes**: word splitting and globbing occur.  
  ```bash
  files=(*)
  echo $files   # splits on IFS, expands *
  ```  

**B10** — *File existence checks*  
- **Test command** `[ -e file ]` (or `test -e file`).  
- **Bash extended test** `[[ -e file ]]` supports pattern matching and is safer with word splitting.  
- **Specific tests**:  
  - `-f` : regular file  
  - `-d` : directory  
  - `-r` : readable  
- **Difference**: `[` is a builtin but follows POSIX rules; `[[` is Bash‑specific, provides additional features (regex `==`, `=~`, no word‑splitting issues).  

**B11** — *Special parameters $? $$ $! $#*  
- **$?**: exit status of the **last** command (0 = success).  
- **$$**: PID of the current shell.  
- **$!**: PID of the **most recent background** job.  
- **$#**: number of positional parameters passed to the script/function.  
- **Use cases**:  
  - `$?` for error handling (`if [ $? -ne 0 ]; then …`).  
  - `$$` for generating unique temp file names.  
  - `$!` to wait for a specific background process (`wait $!`).  
  - `$#` to check required arguments (`if [ $# -lt 2 ]; then …`).  

**B12** — *Functions in Bash*  
- **Definition**: `foo() { ... }` or `function foo { ... }` (both equivalent).  
- **Return values**: Use `return <num>` (0‑255) for status; to return a string, **echo** it and capture with command substitution: `result=$(foo)`.  
- **Local variables**: declare with `local var=value` inside the function to avoid side effects.  

**B13** — *PATH, command resolution, builtins vs externals*  
- **PATH**: colon‑separated list of directories where the shell looks for executables.  
- **Resolution**: Bash first checks **aliases**, then **functions**, then **builtins**, and finally searches `PATH`.  
- **Builtin**: part of the shell (e.g., `cd`, `echo`). No separate process is spawned.  
- **External**: separate executable on disk. Use `type <cmd>` to see if it’s a builtin, function, or file.  

**B14** — *trap*  
- **Syntax**: `trap 'commands' SIGNALS`.  
- **Common signals**: `EXIT` (always runs on normal or error exit), `ERR` (runs after a command that failed when `set -e` is active), `INT` (Ctrl‑C), `TERM` (termination request).  
- **Order**: If multiple traps are set for the same signal, the **most recent** one replaces the previous. For `EXIT`, all registered actions are executed in **reverse order** of registration when the script terminates.  
- **Example**:  
  ```bash
  cleanup() {
    rm -f temp.file
    echo "Cleanup done"
  }
  trap cleanup EXIT INT TERM
  ```  

**B15** — *xargs vs command substitution, parallel execution*  
- **xargs**: reads items from stdin and **invokes** a command with as many arguments as fit per invocation (or one per `-n 1`). Handles NUL (`-0`) and avoids the “argument list too long” error.  
- **Command substitution** (`$(...)`) builds a single string; if the list is huge, the shell may exceed the argument‑list limit.  
- **Parallel**: `xargs -P <n>` runs up to `<n>` jobs concurrently.  
- **Example with find**:  
  ```bash
  find . -type f -print0 | xargs -0 -P 4 -I {} sh -c 'process "{}"'
  ```  
  `-print0` and `-0` ensure filenames with spaces/newlines are safely passed.  

**B16** — *Bash arrays & associative arrays*  
- **Indexed array**: `arr=(a b c)`; access `arr[0]`.  
- **Declare**: `declare -a arr` (optional).  
- **Append**: `arr+=(d)`.  
- **Iterate**: `for v in "${arr[@]}"; do ...; done`.  
- **Length**: `${#arr[@]}`.  
- **Associative array**: `declare -A map`; `map[key]=value`.  
- **Iterate keys/values**: `for k in "${!map[@]}"; do echo "$k = ${map[$k]}"; done`.  
- **Length**: `${#map[@]}` (number of key‑value pairs).  

**B17** — *Subshell vs group command*  
- **Subshell** `(...)`: runs commands in a **child process**; variable changes and `cd` do **not** affect the parent.  
- **Group** `{ ...; }`: runs in the **current shell**; variable changes persist, but the block must be followed by a semicolon or newline.  
- **While loop pitfall**: `somecommand | while read line; do ...; done` executes the loop body in a **subshell**, so `cd`, `export`, etc., are lost after the loop. Use `{ ...; }` or redirect the whole block to avoid this.  

**B18** — *Signals, job control, graceful shutdown*  
- **SIGINT** (Ctrl‑C): interrupt; default action is termination.  
- **SIGTERM**: termination request; allows cleanup.  
- **SIGHUP**: hangup; often used by daemons to reload config or shutdown.  
- **SIGKILL**: cannot be caught or ignored; immediate termination.  
- **Graceful shutdown**: trap `TERM` (and optionally `INT`) to close resources, kill background jobs, and exit. Example:  
  ```bash
  trap 'echo "Shutting down"; kill $child_pid; exit 0' TERM INT
  some_long_running_cmd &
  child_pid=$!
  wait $child_pid
  ```  

**B19** — *Parallel log processing script*  
```bash
#!/usr/bin/env bash
set -euo pipefail

INPUT="large.log"
TMPDIR=$(mktemp -d)
trap "rm -rf $TMPDIR; exit" EXIT INT TERM

# Split into 4 chunks
split -l 100000 "$INPUT" "$TMPDIR/part_"

# Process each chunk in parallel, writing results to $TMPDIR/results/
process_chunk() {
  local part=$1
  local out="${part%.log}_out.log"
  # Example: grep errors
  grep "ERROR" "$part" > "$out"
}
export -f process_chunk

# Find all parts and run in parallel (max 4 jobs)
find "$TMPDIR" -name 'part_*' -print0 | xargs -0 -n 1 -P 4 -I {} bash -c 'process_chunk "$@"' _ {}

# Concatenate results
cat "$TMPDIR"/part_*_out.log > "processed.log"

echo "Processing complete, results in processed.log"
```
- **Performance trade‑offs**: splitting reduces memory per worker but adds I/O overhead; `-P 4` limits CPU usage. Error propagation: if any `process_chunk` fails, `set -e` aborts the script; you can add `|| echo "Error processing $part"` inside the loop to continue or log.  

**B20** — *exec vs normal command, file descriptor manipulation, coprocess*  
- **`exec`**: replaces the current shell (or a subshell) with the specified command; no new process group is created. Useful for **final redirections** that should affect the whole script or for **closing** file descriptors.  
  ```bash
  exec 3>output.txt   # open fd 3 for writing
  exec 3>&-           # close fd 3
  exec myprogram      # replace shell with myprogram
  ```  
- **Normal command**: runs in a **subprocess**, leaving the current shell intact.  
- **Coprocess**: `coproc cmd` starts `cmd` in a background process and sets up two file descriptors: `coproc[0]` (read) and `coproc[1]` (write). Allows bidirectional communication.  
  ```bash
  coproc myserver {
    nc -l 12345
  }
  echo "hello" >&${coproc[1]}
  read -u ${coproc[0]} line
  ```  
  Use cases: long‑running helper processes, interactive protocols, or when you need to send/receive data without spawning a full pipeline.

**PowerShell**

**PS1** — *Write-Output vs Write-Host*  
- **Write-Output** (`Write-Output` or the implicit output): sends objects to the **success output stream** (pipeline). They can be captured, filtered, or redirected.  
- **Write-Host**: writes directly to the host’s display (console) **bypassing the pipeline**. The text is not part of the object stream, so it cannot be captured with `>` or `|`. Use `Write-Host` for UI messages that should not interfere with data flow.  

**PS2** — *Pipeline, ForEach-Object vs foreach*  
- **Pipeline** (`|`): passes **objects** from the left command to the right. Each object is processed sequentially.  
- **ForEach-Object** (`ForEach-Object { ... }` or the alias `foreach` when used as a command): a **cmdlet** that iterates over pipeline input. It supports script blocks with `$_, $_.Property`, and can use `-Begin`, `-Process`, `-End`.  
- **foreach statement** (`foreach ($item in $collection) { ... }`): a **language construct** that iterates over a **collection** you provide explicitly. It does **not** use the pipeline; it’s evaluated eagerly.  
- **When to use**:  
  - Use the pipeline + `ForEach-Object` when you want to keep the data flowing and possibly combine with other cmdlets.  
  - Use the `foreach` statement when you have a local collection and want a simple loop without pipeline overhead.  

**PS3** — *[PSCustomObject] vs [hashtable]*  
- **[hashtable]**: key‑value dictionary, order is not guaranteed (prior to PS5.0) and keys are strings. Good for temporary data or when you need fast lookups.  
- **[PSCustomObject]**: creates an object with **named properties**. Properties are strongly typed, can be displayed nicely by `Format-Table`, and support methods like `.ToString()`. Ideal for returning structured data from functions or for pipeline objects.  
- **Conversion**:  
  ```powershell
  $ht = @{Name='Alice'; Age=30}
  $obj = [PSCustomObject]$ht   # converts hashtable to custom object
  $ht2 = [ordered]@{Name='Bob'; Age=25}  # preserves order
  $obj2 = $ht2 | Select-Object -ExpandProperty *   # another way
  ```  

**PS4** — *Error handling: terminating vs non‑terminating, -ErrorAction, $ErrorActionPreference, try/catch*  
- **Terminating errors**: stop command execution (e.g., `Get-Item -Path "nonexistent" -ErrorAction Stop`). They can be caught by `try/catch`.  
- **Non‑terminating errors**: default behavior; the command continues, error is written to the **error stream**.  
- **-ErrorAction** (`-EA`): per‑command setting (`Stop`, `Continue`, `SilentlyContinue`, `Inquire`). Overrides `$ErrorActionPreference`.  
- **$ErrorActionPreference**: global default for the session.  
- **try/catch**: only catches **terminating** errors. Use `trap` for older style or `try/catch/finally` for structured handling.  
  ```powershell
  try {
    Get-Item -Path $path -ErrorAction Stop
  } catch {
    Write-Error "File not found: $_"
  }
  ```  

**PS5** — *Splatting (@params)*  
- **Splatting** allows passing a collection of arguments as if they were listed individually.  
  ```powershell
  $params = @{
    Path = 'C:\logs'
    Filter = '*.log'
    Recurse = $true
  }
  Get-ChildItem @params
  ```  
- **Difference from a single hashtable**: When a cmdlet expects named parameters, splatting expands each key/value pair into separate arguments. Passing the hashtable itself would be treated as a single argument unless the parameter accepts a hashtable (e.g., `-InputObject`).  

**PS6** — *PowerShell remoting*  
- **Invoke-Command -ComputerName**: executes a script block **remotely** on one or many computers using **WSMan** (Windows Remote Management). It can run in a **disconnected session** (`-AsJob`).  
- **Enter-PSSession**: opens an **interactive** session to a remote computer, similar to an SSH shell.  
- **Protocol**: Primarily **WinRM** (HTTP/HTTPS). PowerShell 7+ also supports **SSH** remoting via the `ssh` subsystem.  
- **Use cases**: `Invoke-Command` for automation/scripts; `Enter-PSSession` for ad‑hoc troubleshooting.  

**PS7** — *Type system & pipeline behavior*  
```powershell
function Get-Items {
    $result = @()
    $result += "one"
    return $result
}
$x = Get-Items
$x.GetType().Name   # What is this?
```
- **Explanation**:  
  - `$result` is initialized as an **array** (`@()`).  
  - `+=` on an array **preserves** the array type, so `$result` remains an `Array` even if it contains a single element.  
  - Therefore `$x.GetType().Name` returns **`Object[]`** (an array of `String`).  
- **When the function returns 0 items**: If you change the function to `return @()`, the result is still an **array** (`System.Object[]`). PowerShell’s pipeline treats a **single non‑collection object** as a scalar, but an explicit empty array is still an array type.  
- **Correct pattern** for functions that may return multiple items: always return an **array** (or use `Write-Output` inside a loop) to guarantee consistent pipeline behavior.  

**PS8** — *[scriptblock] vs function, remoting, double‑hop*  
- **[scriptblock]**: an object representing a piece of code that can be **serialized** and executed later (`& $sb`). Useful for passing code to remote sessions, background jobs, or `ForEach-Object -Parallel`.  
- **Function**: a named, reusable block defined with `function Name { ... }`. It is not directly serializable; to use it remotely you must convert it to a scriptblock (`[scriptblock]::Create(...)` or `Get-Command`).  
- **Passing to remote**: `Invoke-Command -ComputerName … -ScriptBlock $sb`.  
- **Double‑hop problem**: When a remote session tries to authenticate to a third machine, credentials cannot flow by default (Kerberos delegation restrictions). Solutions:  
  - **CredSSP**: delegates credentials (`Enable-WSManCredSSP -Role Client -DelegateComputer *`).  
  - **`Invoke-Command -ComputerName A -ArgumentList $cred -ScriptBlock { param($c) Invoke-Command -ComputerName B -Credential $c … }`** using explicit credential passing.  

**PS9** — *@() vs [array], $null vs []*  
- **@()**: **Array subexpression** operator; forces the result to be an array, even if it contains a single element or nothing.  
  ```powershell
  $a = @(Get-Item .)   # guarantees $a is an array
  ```  
- **[array]**: cast operator; similar effect but less commonly used for this purpose.  
- **Indexing**:  
  - `$null[0]` throws an error (`Cannot index into a null array`).  
  - `@()[0]` returns `null` (the first element of an empty array).  
- **Force single value into array**: `,$value` (comma operator) or `@($value)`.  

**PS10** — *Comparison operators*  
- **-eq / -ne**: equality / inequality (case‑insensitive for strings in PowerShell by default).  
- **-ceq / -cne**: **case‑sensitive** variants.  
- **-like**: wildcard matching (`*`, `?`). Case‑insensitive by default; `-clike` for case‑sensitive.  
- **-match**: regex matching; `-cmatch` for case‑sensitive.  
- **-contains / -in**:  
  - `-contains`: tests if **left** (a collection) contains the **right** element (`$arr -contains 5`).  
  - `-in`: tests if **left** element is in the **right** collection (`5 -in $arr`).  
- **Difference**: `-contains` works on the **left** side as the collection; `-in` reverses the operands.  

**PS11** — *PowerShell modules*  
- **Script module** (`.psm1`): a PowerShell script that defines functions, variables, classes, etc. Loaded with `Import-Module`.  
- **Manifest module** (`.psd1`): a metadata file describing a module (including nested script modules, required modules, exported members). Powershell uses it to auto‑load the associated `.psm1` and other assets.  
- **Binary module** (`.dll`): contains .NET types and cmdlets compiled to C#. Loaded like any other module but provides native performance.  
- **Import-Module**: reads the module manifest, executes the script module, and exports the declared members into the caller’s session.  

**PS12** — *String interpolation, here‑strings*  
- **Double‑quoted strings** (`"..."`): support **substitution** (`"value: $var"`).  
- **Single‑quoted strings** (`'...'`): treat `$` literally.  
- **Here‑string** (`@"..."@`): multi‑line string preserving line breaks and allowing variable expansion if double‑quoted (`@\"...\@"`).  
  ```powershell
  $name = "Alice"
  $template = @"
  Hello, $name!
  Welcome to PowerShell.
  "@
  ```  

**PS13** — *Get‑Member, Select‑Object vs Where‑Object*  
- **Get‑Member** (`gm`): inspects an object’s members (properties, methods, note properties, events).  
  ```powershell
  Get-Process | Get-Member
  ```  
- **Properties**: read/write data fields.  
- **Methods**: callable functions on the object.  
- **NoteProperties**: custom properties added via `Add‑Member` or by some cmdlets.  
- **Select‑Object**: **projects** specific properties or creates calculated ones (`Select-Object Name, Id`).  
- **Where‑Object** (`Where` or `?`): **filters** objects based on a script block (`Where-Object {$_.CPU -gt 10}`).  

**PS14** — *PowerShell classes (v5+)*  
- Introduced to define **.NET‑style** classes directly in PowerShell.  
- **Differences from C#**: limited to a subset (no interfaces, no inheritance beyond a single base class, no generics, no static members).  
- **When to use**: when you need a **strongly‑typed object** with properties and methods that can be passed around the pipeline, especially for DSC resources or complex data structures.  
- **Limitations**: cannot implement interfaces, cannot use inheritance (except inheriting from `System.Object` implicitly), and constructors are limited to parameterless or single parameter list.  

**PS15** — *CmdletBinding & advanced functions*  
- **[CmdletBinding()]**: turns a normal function into an **advanced function**, enabling cmdlet‑like features:  
  - **Parameter validation** (`[ValidateNotNullOrEmpty]`).  
  - **SupportShouldProcess**: integration with `-WhatIf`/`-Confirm`.  
  - **ValueFromPipeline / ValueFromPipelineByPropertyName**: automatic parameter binding.  
  - **DefaultParameterSetName**: disambiguates when multiple parameter sets exist.  
- **Begin/Process/End blocks**:  
  - **Begin**: runs once before any input is processed (good for setup).  
  - **Process**: runs once per pipeline object.  
  - **End**: runs after all input is processed (cleanup, final output).  

**PS16** — *PowerShell providers*  
- **Providers** expose different data stores as **drive‑like** namespaces (`Get-ChildItem`, `Set-Location`).  
- **Examples**:  
  - **FileSystem**: normal file system.  
  - **Registry**: `HKLM:\` drive, works like a file system.  
  - **Certificate**: `Cert:\`.  
  - **Environment**: `Env:\`.  
- **Using Registry like a file system**:  
  ```powershell
  Set-Location HKLM:\Software\MyApp
  Get-ChildItem   # lists subkeys/values
  New-Item -Path . -Name MyValue -Value 42 -ItemType DWord
  ```  

**PS17** — *Runspaces & parallel execution*  
- **Runspace**: an isolated execution environment for PowerShell code. A **RunspacePool** manages a pool of runspaces for parallel work.  
- **[powershell]** object: created from a runspace to invoke scriptblocks.  
- **ForEach‑Object -Parallel** (PowerShell 7+): a **simplified** way to run the scriptblock of a `ForEach-Object` in parallel across the pipeline items, automatically handling runspace creation and serialization.  
- **Manual runspace management**: useful when you need fine‑grained control (custom threading, long‑living runspaces, complex state sharing). Example:  
  ```powershell
  $pool = [RunspaceFactory]::CreateRunspacePool(1, 4)
  $pool.Open()
  $ps = [PowerShell]::Create().AddScript($script).AddArgument($arg)
  $ps.RunspacePool = $pool
  $async = $ps.BeginInvoke()
  # ... do other work
  $result = $ps.EndInvoke($async)
  $pool.Close()
  ```  

**PS18** — *PSScriptAnalyzer*  
- **Static code analysis** tool that checks PowerShell scripts against a set of **rules** (naming conventions, best practices, security).  
- **Rule severity**: `Error`, `Warning`, `Information`.  
- **Custom rules**: can be added via a JSON/YAML rule definition file.  
- **Suppression**: use `#pscriptanalyzer:disable <RuleName>` comment to ignore a specific rule for a line or block.  
- **CI/CD integration**: run `Invoke-ScriptAnalyzer` in build pipelines; fail the build on errors or treat warnings as failures based on policy.  

**PS19** — *$using:, $args, -ArgumentList, serialization limits*  
- **$using:**: in `ForEach-Object -Parallel`, allows **capturing** variables from the calling scope into the parallel scriptblock without full serialization. Only simple types (primitives, arrays, hashtables up to a depth limit) are supported.  
- **$args**: automatic array of positional arguments passed to a scriptblock when invoked with `& $sb arg1 arg2`.  
- **-ArgumentList** (`-ArgList`): used with `Invoke-Command`, `Start-Job`, or `Register-ObjectEvent` to pass values to the remote scriptblock. Values are **serialized** as CLIXML; complex objects may lose methods or cause size limits.  
- **Serialization depth**: By default, CLIXML limits nesting to **100** levels to prevent runaway memory usage. Exceeding this throws an error. Flatten or simplify objects when passing to remote sessions or parallel jobs.  

**PS20** — *Desired State Configuration (DSC)*  
- **DSC** is a **declarative** management platform. You write a **configuration** script that describes the desired state of a node.  
  ```powershell
  Configuration MyWebServer {
      Node 'web01' {
          WindowsFeature IIS {
              Ensure = 'Present'
          }
          File LogFile {
              Ensure = 'Present'
              Type = 'Directory'
              DestinationPath = 'C:\Logs'
          }
      }
  }
  ```  
- **Resources**: reusable building blocks (e.g., `xWebsite`, `cService`) that implement the logic to bring a property into the desired state.  
- **Local Configuration Manager (LCM)**: runs on each node, pulls the compiled MOF, compares current state, and applies resources as needed.  
- **Windows PowerShell vs PowerShell 7+**: Original DSC was tightly coupled to Windows PowerShell and the LCM service. PowerShell 7 introduced **cross‑platform DSC** (still Windows‑centric for many resources) and improved tooling (`Get-DscResource`, `Test-DscConfiguration`).  
- **Modern alternatives**: Infrastructure‑as‑Code tools like **Terraform**, **Ansible**, **Chef**, or **Azure Arc** for hybrid/cloud management have largely supplanted DSC for many scenarios, especially outside pure Windows environments. DSC remains valuable for Windows‑specific configuration enforcement and hybrid on‑prem/cloud setups.
