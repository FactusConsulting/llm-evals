**Go (20 questions)**  

**G1** — *Easy*:  
- **Array**: Fixed-size, value type. The size is part of the type (`[5]int`).  
- **Slice**: Describes a segment of an underlying array (`[]int`). It holds a pointer, length, and capacity.  
- **Appending**: When you `append` to a slice and its length exceeds its capacity, Go allocates a new, larger backing array (typically doubling the capacity), copies the existing elements, and returns the new slice. The original slice may point to the old array if it’s used elsewhere.

**G2** — *Easy*:  
- `var x int` declares a variable `x` of type `int` with the zero value `0`. It can appear at package or function scope.  
- `x := 0` is short‑hand declaration **and** initialization; it infers the type from the RHS.  
- **When `:=` cannot be used**: inside a function scope where the variable already exists, at package level (only `var` is allowed), or in `if`, `switch`, or `for` statements that are not combined with a short declaration.

**G3** — *Medium*:  
- **Goroutine**: A lightweight thread managed by the Go runtime. It’s a function/Go statement that runs concurrently.  
- **Difference from OS thread**: Goroutines have a small stack (few KB) that can grow/shrink; the runtime multiplexes many goroutines onto a smaller number of OS threads.  
- **Go scheduler (GMP model)**:  
  - **M** (Machine) = OS thread.  
  - **P** (Processor) = scheduler context holding a run queue of goroutines and runtime resources.  
  - **G** (Goroutine) = the actual concurrent unit.  
  The scheduler assigns a G to a P, and a P to an M, balancing load and enabling parallel execution.

**G4** — *Medium*:  
- **Channels** are typed conduits for sending (`ch <- value`) and receiving (`<-ch`) values. They enable safe communication and synchronization between goroutines.  
- **Unbuffered channel**: The sender blocks until a receiver is ready; the receiver blocks until a sender arrives.  
- **Buffered channel**: Created with `make(chan T, capacity)`. Sends block only when the buffer is full; receives block only when empty.  
- **Full buffered channel**: Sending to it blocks until space becomes available (i.e., another goroutine receives from it).

**G5** — *Medium*:  
- **context package** provides mechanisms to propagate cancellation signals, deadlines, and request‑scoped values across API boundaries.  
- **Minimal example** using `context.WithTimeout` to cancel an HTTP request:  
  ```go
  ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
  defer cancel() // always cancel to free resources

  req, _ := http.NewRequest("GET", "https://api.example.com/data", nil)
  req = req.WithContext(ctx) // attach context

  client := &http.Client{}
  resp, err := client.Do(req)
  if err != nil {
      // err may be context.DeadlineExceeded
      fmt.Println("request error:", err)
      return
  }
  defer resp.Body.Close()
  // process resp...
  ```

**G6** — *Medium*:  
- **Interface satisfaction**: A type implements an interface if it provides all the methods (with matching signatures and receiver types). This is *implicit*—no `implements` keyword.  
- **Difference from Java/C#**: Those languages require explicit implementation declarations; Go’s duck typing is structural.  
- **Empty interface `interface{}`**: Can hold any value (similar to `Object` in Java or `dynamic` in C#).  
  - **Power**: Enables heterogeneous collections, generic algorithms, type assertions.  
  - **Danger**: Hides type information at compile time; runtime `.(Type)` checks can panic if the underlying value doesn’t match.

**G7** — *Hard*:  
- The snippet suffers from a **data race**: the writer goroutine may set `data` before `ready` becomes visible to the reader due to compiler/CPU reordering and separate memory visibility.  
- **Why unsafe**: The reader may see `ready == true` but still read the old (uninitialized) value of `data`.  
- **Correct alternatives**:  
  1. Use a **channel** to signal readiness:  
     ```go
     readyCh := make(chan struct{})
     go func() {
         data = "hello"
         readyCh <- struct{}{}
     }()
     <-readyCh
     fmt.Println(data)
     ```  
  2. Use a **sync.Mutex** or **atomic** operations:  
     ```go
     var mu sync.Mutex
     var ready bool
     var data string
     go func() {
         mu.Lock()
         data = "hello"
         ready = true
         mu.Unlock()
     }()
     for {
         mu.Lock()
         if ready {
             mu.Unlock()
             break
         }
         mu.Unlock()
         time.Sleep(time.Millisecond)
     }
     fmt.Println(data)
     ```  
  3. Use **sync/atomic**:  
     ```go
     var ready uint32
     go func() {
         data = "hello"
         atomic.StoreUint32(&ready, 1)
     }()
     for atomic.LoadUint32(&ready) == 0 {
         runtime.Gosched()
     }
     fmt.Println(data)
     ```

**G8** — *Hard*:  
- **sync.Mutex**: Exclusive lock; only one goroutine can hold it at a time.  
- **sync.RWMutex**: Reader‑writer lock; multiple readers may hold it concurrently, but writers get exclusive access. Use when reads dominate and are thread‑safe without writes.  
- **sync.Map vs map with mutex**:  
  - `sync.Map` is a *concurrent* map optimized for read‑heavy workloads; it avoids a single mutex by using lock‑striping and cache‑friendly structures.  
  - A plain `map` protected by `sync.Mutex` is simpler and may be faster for write‑heavy or small maps because of lower overhead.  
- **Performance trade‑offs**: `sync.Map` incurs extra indirection and memory overhead; it’s best when you have many goroutines performing independent reads/writes and cannot easily coordinate a single mutex.

**G9** — *Hard*:  
- **Go modules** manage dependencies using a `go.mod` file (lists module path and required versions) and a `go.sum` file (contains cryptographic hashes of module contents for integrity).  
- **go.mod**: Declares the module path, dependency requirements (e.g., `require ( github.com/pkg/errors v0.9.1 )`), and optional replacements.  
- **go.sum**: Stores the expected hash for each dependency version; ensures reproducible builds.  
- **go mod tidy**: Reconciles `go.mod` with the actual code: adds missing dependencies, removes unused ones, and updates `go.sum`.  
- **Minimum Version Selection (MVS)**: The algorithm that picks the *lowest* acceptable version for each dependency that satisfies all constraints, aiming for the minimal set of versions while respecting `require` directives and indirect dependencies.

**G10** — *Medium*:  
- **defer** schedules a function call to run **after** the surrounding function returns (LIFO order).  
- **Execution order**: Multiple `defer`s are executed in *reverse* order of appearance (last deferred is run first).  
- **Common gotcha in loops**: If you `defer` inside a loop without creating a new scope, the same deferred function will run after the loop finishes, potentially using stale loop variables. Use an anonymous function or a separate scope:  
  ```go
  for i := 0; i < 5; i++ {
      defer func(j int) {
          fmt.Println(j)
      }(i) // captures current i
  }
  ```

**G11** — *Easy*:  
- **Pointer**: Holds the memory address of a variable. Declared with `*T`.  
- **Zero value**: `nil` (no valid address).  
- **Pointer to a struct literal**:  
  ```go
  type Person struct { Name string }
  p := &Person{Name: "Alice"} // p is *Person
  ```

**G12** — *Easy*:  
- **init()**: Special function called automatically after all package variables are initialized, *before* the program starts.  
- **Execution**: Each package can have **zero or more** `init()` functions; they run in *dependency order* (packages imported first are initialized first) and within a package in the order they appear.  
- **Example**:  
  ```go
  var DB *sql.DB

  func init() {
      var err error
      DB, err = sql.Open("postgres", dsn)
      if err != nil { panic(err) }
  }
  ```

**G13** — *Easy*:  
- **new(T)**: Allocates zero‑value of type `T` on the heap and returns a pointer `*T`. Works for any type `T`.  
- **make(T)**: Creates *initialized* instances of **slice**, **map**, or **channel** (and some other built‑ins). It returns the *value* itself (not a pointer).  
  - `make([]int, 0, 10)` → slice with capacity 10.  
  - `make(chan int, 5)` → buffered channel.  
  - `make(map[string]int)` → empty map.  
- **Difference**: `new` is for simple zero‑value allocation; `make` is for complex, reference types that need extra initialization.

**G14** — *Easy*:  
- **Error handling**: The `error` type (`interface{ Error() string }`) is the conventional way to signal failures.  
- **Idiomatic pattern**:  
  ```go
  val, err := someFunc()
  if err != nil {
      return nil, err // or handle/log
  }
  ```  
- **errors.Is**: Tests if an error matches a target (including wrapped errors).  
- **errors.As**: Tries to assert an error to a specific type, useful for type‑based handling.  
- **vs `==`**: `==` checks pointer identity; `errors.Is`/`errors.As` work with wrapped errors and interface values.

**G15** — *Easy*:  
| Composite type | Zero value |
|----------------|------------|
| `map[K]V`      | `nil` (no entries) |
| `[]T` (slice)  | `nil` (length & capacity 0) |
| `chan T`       | `nil` (uninitialized) |
| `struct{…}`    | Each field set to its zero value (e.g., `0`, `""`, `nil`) |

**G16** — *Medium*:  
- **Race condition**: Occurs when two goroutines access shared memory concurrently and at least one access is a write, leading to nondeterministic behavior.  
- **`-race` flag**: Instruments the binary with the *race detector* (based on the Happens‑Before model) that records memory accesses and flags conflicting accesses at runtime.  
- **Example & fix**:  
  ```go
  var counter int
  func inc() {
      for i := 0; i < 1000; i++ {
          counter++ // data race!
      }
  }
  go inc(); go inc()
  ```  
  **Fix with mutex**:  
  ```go
  var mu sync.Mutex
  func inc() {
      for i := 0; i < 1000; i++ {
          mu.Lock()
          counter++
          mu.Unlock()
      }
  }
  ```  
  **Fix with channel** (if you prefer message passing):  
  ```go
  ch := make(chan int, 2000)
  func inc() {
      for i := 0; i < 1000; i++ {
          ch <- 1
      }
  }
  go inc(); go inc()
  // in main goroutine
  for i := 0; i < 2000; i++ {
      <-ch
  }
  ```

**G17** — *Medium*:  
- **select**: Allows a goroutine to wait on multiple channel operations simultaneously.  
- **Difference from switch**: `select` blocks until at least one case can proceed; `switch` evaluates a single expression.  
- **Multiple ready cases**: The Go runtime picks *one* at random (but fair) among the ready ones.  
- **Timeout example**:  
  ```go
  select {
  case v := <-ch:
      // received value
  case <-time.After(100 * time.Millisecond):
      // timeout occurred
  }
  ```

**G18** — *Hard*:  
- **Escape analysis**: The compiler determines whether an object can be allocated on the stack or must be heap‑allocated. If a pointer to the object escapes the function’s scope (e.g., stored in a global, returned, or passed to another goroutine), it escapes to the heap.  
- **Decision factors**: Presence of address‑taking operations, function returns, closures capturing the variable, or passing to interfaces.  
- **Inspecting**: Use `go build -gcflags="-m"` to see escape analysis decisions (`leaked heap allocation`).  
- **Performance impact**: Stack allocation is faster (no GC pressure) and reduces latency; heap allocation adds overhead and may trigger GC. Minimizing escapes (e.g., by pre‑allocating buffers, using `append` carefully) can yield significant performance gains.

**G19** — *Hard*:  
- **reflect package**: Provides runtime introspection and manipulation of arbitrary types/values.  
- **`reflect.Type`**: Describes a type (e.g., `*int`, `[]string`). Immutable, used for type inspection (`Kind()`, `NumField()`, etc.).  
- **`reflect.Value`**: Holds an actual value; supports getting/setting fields, calling methods, and invoking functions. Methods like `Elem()`, `Interface()`, `MethodByName()`.  
- **Performance costs**: Reflection bypasses static type checking, involves interface conversions, and often requires heap allocation for `Value`. Use sparingly; prefer code generation (e.g., `go:generate`) for performance‑critical paths.  
- **When justified**: Dynamic serialization/deserialization, generic data structures, testing utilities, or when the type cannot be known at compile time.

**G20** — *Hard*:  
- **`go:embed`**: Directive (added in Go 1.16) that instructs the compiler to embed file contents directly into the binary.  
- **Usage**:  
  - Single file: `//go:embed file.txt` followed by `var content string` and `content = /*local*/.GoGenerate()`.  
  - Directory (recursively): `//go:embed dir/*` embeds all files under `dir`.  
  - File system: `//go:embed fs:` with a custom `embed.FS` implementation.  
- **Limitations**:  
  - Embedded files are read‑only.  
  - Size of the binary grows with embedded content.  
  - Not suitable for very large binaries or files that change frequently at runtime.  
- **Interaction with `io/fs.FS`**: The embedded file system implements `fs.FS`; you can use `embed.FS` to open files with `fs.Open`, enabling the same API as regular file system access but backed by the compiled‑in data.

**Rust (20 questions)**  

**R1** — *Easy*:  
- **Ownership** rules:  
  1. Each value in Rust has a single *owner* (a variable).  
  2. When the owner goes out of scope, the value’s destructor runs (`drop`).  
  3. Ownership may be *transferred* (`move`) to another variable; after transfer, the original variable is no longer usable.  
- These rules guarantee memory safety without a garbage collector.

**R2** — *Easy*:  
- **`String`**: Heap‑allocated, growable UTF‑8 string. Owned, mutable, and can change size.  
- **`&str`**: String slice, a reference to a sequence of UTF‑8 bytes. Immutable, can point to a `String`, a string literal, or any contiguous UTF‑8 data.  
- **When to use**:  
  - Use `String` when you need to own or modify the string.  
  - Use `&str` in function signatures when you only need to read the string (e.g., `fn process(s: &str)`), allowing the caller to pass literals, `String`s (via coercion), or other slices.

**R3** — *Medium*:  
- **Borrowing** lets you temporarily lend references to data without transferring ownership.  
- **Borrow checker** enforces two key rules:  
  - **Exclusive or shared**: You may have *either* one mutable reference (`&mut T`) *or* any number of shared immutable references (`&T`), but not both simultaneously.  
  - **Lifetime constraints**: The borrowed reference must not outlive the owner.  
- These rules prevent data races and dangling pointers at compile time.

**R4** — *Medium*:  
- **`Result<T, E>`**: Enum for recoverable errors (`Ok(T)` or `Err(E)`).  
- **`Option<T>`**: Enum for absence (`Some(T)` or `None`).  
- **`?` operator**: In a function that returns a `Result` or `Option`, `value?` propagates `Ok(value)` or returns `Err(...)/None` early.  
- **Example (file read)**:  
  ```rust
  use std::fs::File;
  use std::io::{self, Read};

  fn read_file(path: &str) -> Result<String, io::Error> {
      let mut file = File::open(path)?; // propagate error
      let mut contents = String::new();
      file.read_to_string(&mut contents)?; // propagate error
      Ok(contents)
  }
  ```

**R5** — *Medium*:  
- **`Box<T>`**: Heap allocation with ownership; used for dynamic sizing, trait objects (`Box<dyn Trait>`), or to store values on the heap without extra indirection.  
- **`Rc<T>`**: Reference‑counted smart pointer for *single‑threaded* shared ownership. Allows multiple owners; the value is dropped when the count reaches zero.  
- **`Arc<T>`**: Atomically reference‑counted version of `Rc` for *safe* shared ownership across threads (`Arc<dyn Trait>` is common for thread‑safe trait objects).  
- **When to use**:  
  - `Box` for moving large data to heap or for trait objects in single‑threaded code.  
  - `Rc` when you need shared immutable ownership without thread safety.  
  - `Arc` when the shared data must be accessed from multiple threads.

**R6** — *Medium*:  
- **Traits**: Define a set of methods a type must implement. They are Rust’s way of achieving *ad‑hoc polymorphism*.  
- **Comparison to Go interfaces**: Rust traits are *statically* checked at compile time (unless using *trait objects*). Go interfaces are *duck‑typed* and dynamically satisfied.  
- **Trait object (`dyn Trait`)**: An opaque pointer (`&dyn Trait`, `Box<dyn Trait>`, `Arc<dyn Trait>`) that erases the concrete type, enabling heterogeneous collections and runtime dispatch.  
- **Generic with trait bound (`T: Trait`)**: Keeps the concrete type known at compile time, allowing monomorphization (code generation for each concrete `T`). This yields zero‑cost abstraction but requires the type to be known statically.

**R7** — *Hard*:  
- **Compilation failure**: The function returns a reference to either `x` or `y`, but the compiler cannot guarantee which one outlives the function call because the lifetimes of the inputs are unknown.  
- **Fix with explicit lifetimes**:  
  ```rust
  fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
      if x.len() > y.len() { x } else { y }
  }
  ```  
  The `'a` bound states that the returned reference lives at least as long as both inputs.  
- **Alternative**: Return an owned `String` or `Box<str>` if you need the result to outlive the inputs.

**R8** — *Hard*:  
- **`Send`**: Marker trait indicating a type is safe to transfer across thread boundaries (the runtime can move it to another thread).  
- **`Sync`**: Marker trait indicating a type is safe to share between threads (i.e., it can be referenced from multiple threads simultaneously).  
- **`Rc<T>`**: Not `Send` nor `Sync` because its reference count is updated with non‑atomic operations; sharing it across threads would cause data races.  
- **`Arc<T>`**: Implements both `Send` and `Sync` because its internal counter uses atomic operations, making concurrent access safe.

**R9** — *Hard*:  
- **Async/await**: Syntactic sugar for building *futures* (lazy computations) that can be suspended and resumed.  
- **Future**: A `struct` implementing the `Future` trait (`poll`) that returns `Poll<Output>`. It represents work that may not be completed immediately.  
- **Executor**: A runtime component (e.g., Tokio, async‑std) that repeatedly calls `poll` on ready futures, driving them to completion. Unlike Go’s goroutine scheduler (which is *preemptive* and managed by the runtime), Rust’s async tasks are *cooperative*—they yield control only when they hit an `await` on a future that isn’t ready.  
- **Key difference**: Go’s goroutines are scheduled by the runtime automatically; Rust requires an explicit executor (or `block_on`) to run async code.

**R10** — *Medium*:  
- **`unsafe`**: Bypasses Rust’s safety guarantees; used when the programmer can prove memory safety manually.  
- **Three things you can do in `unsafe` but not in safe Rust**:  
  1. Dereference a raw pointer (`*const T` / `*mut T`).  
  2. Call an `extern` function or FFI that the compiler cannot verify (e.g., C APIs).  
  3. Access or modify `union` fields (except the last written field) or perform `std::ptr::read/write`.  
- **When justified**: Implementing low‑level system code, wrapping C libraries, creating custom collections with interior mutability, or when proven correct via rigorous review and testing.

**R11** — *Easy*:  
- **Pattern matching** via `match` exhaustively checks a value against patterns.  
- **`match` vs `if let`**:  
  - `match` requires handling *all* possible patterns (compiler enforces exhaustiveness).  
  - `if let` is a concise guard for a single pattern; it ignores other cases and does not enforce exhaustiveness.  
- **Example**:  
  ```rust
  enum Coin { Penny, Nickel, Dime, Quarter }

  // match (exhaustive)
  fn value_in_cents(coin: Coin) -> u8 {
      match coin {
          Coin::Penny   => 1,
          Coin::Nickel  => 5,
          Coin::Dime    => 10,
          Coin::Quarter => 25,
      }
  }

  // if let (single pattern)
  if let Coin::Quarter = coin {
      println!("25 cents!");
  }
  ```

**R12** — *Easy*:  
- **`Vec<T>`**: Growable array on the heap. Internally stores a pointer, current length, and capacity. When `push` exceeds capacity, it allocates a larger block (often doubling) and copies existing elements.  
- **Array `[T; N]`**: Fixed‑size stack allocation; size known at compile time. Cannot change length.  
- **Memory management**: `Vec` manages its own heap buffer and automatically shrinks (via `shrink_to_fit`) if needed, while arrays are allocated on the stack and have no runtime overhead for resizing.

**R13** — *Easy*:  
- **Enums**: Algebraic data types that can hold variants, each possibly with different types and data. Unlike C/Java enums (which are just named constants), Rust enums can carry data.  
- **`Option<T>`**: Defined as `enum Option<T> { None, Some(T) }`. Provides a safe alternative to null pointers; forces the programmer to handle the “absent” case explicitly.  
- **Why no null**: Null pointers are a common source of errors. `Option` makes the possibility of absence explicit in the type system, leading to safer code.

**R14** — *Easy*:  
- **`impl` block**: Associates methods and trait implementations with a type.  
- **Method receivers**:  
  - `&self`: Borrowed immutable reference (read‑only access).  
  - `&mut self`: Borrowed mutable reference (can modify the instance).  
  - `self`: Takes ownership (used for consuming methods, e.g., moving a value).  
- **Associated functions**: Defined without a `self` parameter (e.g., `String::new()`), act like static methods but are namespaced under the type.

**R15** — *Easy*:  
- **`derive` macro**: Automatically generates boilerplate trait implementations for a struct/enum. Common traits:  
  - `Debug` – for `{:?}` formatting.  
  - `Clone` – implements `clone()`.  
  - `Copy` – when all fields are `Copy`.  
  - `PartialEq`/`Eq` – equality comparison.  
  - `Serialize`, `Deserialize` (via `serde`).  
- **When you cannot derive**: If the trait requires custom logic (e.g., `PartialOrd` with a specific ordering), or if the type contains fields that themselves cannot implement the trait (e.g., a `Send` trait on a type holding a raw pointer).

**R16** — *Medium*:  
- **`Cow<'a, T>` (Clone‑On‑Write)**: An enum (`Owned` or `Borrowed`) that provides a value that is borrowed unless mutation is needed, at which point it clones into an owned version.  
- **Usefulness**: Avoids unnecessary cloning when the caller might not need to mutate data. Example:  
  ```rust
  use std::borrow::Cow;

  fn make_uppercase(s: Cow<str>) -> Cow<str> {
      if s == "already upper" {
          s // borrowed, no clone
      } else {
          Cow::Owned(s.to_uppercase()) // clone only when needed
      }
  }
  ```  
  Without `Cow`, you’d have to clone unconditionally or accept only owned values.

**R17** — *Medium*:  
- **Module system**: Organizes code into a hierarchy of `mod` items.  
- **`mod`**: Declares a module; the body can be in the same file or in a separate file named after the module (`mod foo {}` → `foo.rs` or `foo/mod.rs`).  
- **`use`**: Brings names into scope (`use std::collections::HashMap;`). Can rename (`use foo::bar as baz`).  
- **`pub`**: Exposes items outside the module.  
- **File‑system mapping**: By default, `mod foo;` looks for `foo.rs` or `foo/mod.rs`. The 2015 edition required `mod.rs`; the 2018 edition allows the module to be in a file with the same name as the module.  
- **Changes between editions**: 2018 edition made `extern crate` optional, improved `use` paths, and allowed `mod` items to be declared at the crate root without a separate `mod.rs`.

**R18** — *Hard*:  
- **`Pin<T>`**: Wraps a type to guarantee that the value will not be moved after it is pinned. Used for *self‑referential* structs (e.g., a struct containing a pointer to one of its own fields).  
- **Why needed**: In async `Future`s, the compiler cannot assume the future won’t move; `Pin` ensures the future stays at a stable memory location, allowing safe manipulation of interior pointers.  
- **`Unpin`**: A marker trait indicating that a type is safe to move even when pinned. Most types implement `Unpin` automatically; those that don’t (like certain self‑referential futures) must handle pinning explicitly.  
- **Relation to async**: The `Future` trait’s `poll` method receives `self: Pin<&mut Self>`, enforcing that the future cannot be moved while being polled.

**R19** — *Hard*:  
- **Macro system**: Two main kinds:  
  - **Declarative macros** (`macro_rules!`): Pattern‑based, hygienic, define syntax extensions at compile time. Good for repetitive boilerplate.  
  - **Procedural macros** (`proc_macro`): Compile to a function that receives token streams and returns a new token stream. Types include `derive`, `attribute`, and `function-like`. More powerful, can inspect AST, generate code based on complex logic.  
- **Hygiene**: Refers to the macro’s ability to avoid name collisions. By default, identifiers introduced inside a macro are scoped to the macro’s definition site, preventing accidental capture of variables from the caller. Procedural macros can control hygiene via the `proc_macro::TokenStream` API.

**R20** — *Hard*:  
- **Zero‑cost abstractions**: Rust’s design goal that abstractions (generics, traits, iterators, etc.) compile down to as efficient code as hand‑written equivalents, with no runtime overhead.  
- **How it’s achieved**:  
  - **Generics & monomorphization**: At compile time, the compiler generates concrete instantiations for each used type, inlining and optimizing away abstraction layers.  
  - **Iterators**: Implemented via *zero‑overhead* `next` calls; the iterator trait is *statically* dispatched, allowing the compiler to inline and eliminate loops.  
  - **Trait static dispatch**: When the concrete type is known (e.g., `T: Trait` in a generic function), the compiler can call the method directly; when using trait objects (`&dyn Trait`), dynamic dispatch is used but only where necessary.  
- **Result**: High‑level, expressive code (e.g., `iter.filter(...).map(...).collect()`) compiles to tight loops comparable to manually written C, while preserving safety and ergonomics.
