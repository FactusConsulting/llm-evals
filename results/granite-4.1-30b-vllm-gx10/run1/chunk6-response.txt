**JavaScript / TypeScript**

**JS1** — *var, let, const & hoisting*  
- **var**: function-scoped (or global if outside a function) and **hoisted** – the declaration is moved to the top of its scope, but initialization stays.  
- **let** & **const**: block-scoped. They are also hoisted, but are in a **Temporal Dead Zone** from the start of the block until the actual declaration line – any reference before that throws a `ReferenceError`.  
- **const** additionally enforces that the binding cannot be reassigned (the object it points to can still be mutated unless it’s a primitive).  
- **Hoisting** means the parser lifts declarations to the top of their containing scope, but for `let`/`const` the assignment part is not hoisted, so early references are illegal.

**JS2** — *Event loop, call stack, microtask & macrotask queues*  
- The **event loop** continuously checks the **call stack**. If the stack is empty, it processes pending tasks from two queues:  
  - **Macrotask queue** (also called the task queue): holds callbacks from timers (`setTimeout`, `setInterval`), I/O, UI rendering, etc. Each macrotask runs to completion before the next one starts.  
  - **Microtask queue**: holds promises’ `.then`/`.catch` handlers, `queueMicrotask`, `MutationObserver` callbacks, etc. After each macrotask (and after each microtask), the loop drains the microtask queue before moving to the next macrotask.  
- This ordering guarantees that promise resolutions happen **before** the next timer fires or the next render, keeping async code deterministic.

**JS3** — *Closures, classic for‑loop bug, fix*  
- A **closure** is a function that retains access to its lexical scope even after that scope has finished executing.  
  ```js
  function makeCounter() {
    let n = 0;
    return function() { return ++n; }; // closure over n
  }
  const c = makeCounter();
  console.log(c()); // 1
  console.log(c()); // 2
  ```
- **Classic for‑loop closure bug**:  
  ```js
  for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i)); // all log 3
  }
  ```
  Because `var` is function‑scoped, there’s a single `i` shared by all iterations. By the time the callbacks run, the loop has finished and `i` is `3`.  
- **Fixes**:  
  1. Use **`let`** (block‑scoped) inside the loop – each iteration gets its own `i`.  
  2. Or create an **IIFE** per iteration, passing `i` as an argument.  
  3. Or use a **`for…of`** with an array of values.

**JS4** — *Promise, async/await, error handling, Promise.allSettled vs Promise.all*  
- **Promise**: an object representing the eventual completion (or failure) of an async operation. It has three states: pending, fulfilled, rejected.  
- **async/await**: syntactic sugar over promises. An `async` function always returns a promise; `await` pauses execution until the awaited promise settles.  
- **Error handling**:  
  - With promises: `.then(...).catch(fn)` or `try/catch` inside an async function.  
  - With async/await: wrap `await` in a `try/catch` block; uncaught rejections become the promise returned by the async function.  
- **Promise.all(iterable)**: returns a single promise that fulfills when **all** input promises fulfill, **or rejects immediately** if any input promise rejects.  
- **Promise.allSettled(iterable)**: returns a promise that fulfills **after all** input promises have either fulfilled or rejected, with an array of objects `{ status: "fulfilled" | "rejected", value|reason }`. Useful when you need results of all operations regardless of failures.

**JS5** — *TypeScript interface vs type, discriminated unions*  
- **Interface**:  
  - Can be **extended** (`interface A extends B`) and **implemented** by classes.  
  - Allows **declaration merging** (multiple `interface Foo {}` declarations combine).  
  - Primarily used for defining **object shapes** and contracts.  
- **Type**:  
  - Can describe **any** kind of type (unions, intersections, primitives, tuples, etc.).  
  - Cannot be extended with `extends` (but can use intersections).  
  - No declaration merging.  
- **When to use**:  
  - Use **interface** for public API shapes and when you expect extension or implementation.  
  - Use **type** for unions, intersections, utility types, or when the definition is not meant to be extended.  
- **Discriminated unions**: a set of object types that share a **common, literal‑typed property** (the discriminant). TypeScript can narrow based on that property.  
  ```ts
  type Shape =
    | { kind: 'circle'; radius: number }
    | { kind: 'square'; side: number };
  function area(s: Shape) {
    switch (s.kind) {
      case 'circle': return Math.PI * s.radius ** 2;
      case 'square': return s.side ** 2;
    }
  }
  ```

**JS6** — *Prototypal inheritance, Object.create(), ES6 classes*  
- JavaScript uses **prototype‑based inheritance**: objects have an internal `[[Prototype]]` link to another object. Property lookup walks this chain until `null`.  
- **Object.create(proto, [properties])** creates a new object with `proto` as its prototype. If `proto` is `null`, the object has no prototype (a “pure” object).  
  ```js
  const animal = { eats: true };
  const dog = Object.create(animal);
  dog.barks = true;
  console.log(dog.eats); // true (inherited)
  ```
- **ES6 classes** are syntactic sugar over the prototype mechanism. A class’s `prototype` property becomes the prototype of instances. Methods defined in the class body end up on the prototype, enabling shared method lookup.  
  ```js
  class Animal { constructor(name) { this.name = name; } speak() { console.log(`${this.name} makes a noise`); } }
  // Equivalent to:
  function Animal(name) { this.name = name; }
  Animal.prototype.speak = function() { /* … */ };
  ```
- Classes also support **static methods**, **extends** for subclassing (which internally sets the prototype chain), and **super** calls.

**JS7** — *`this` keyword, binding rules, `bind()`*  
- **Four binding rules (priority order)**:  
  1. **Explicit binding** via `call`, `apply`, or `bind`.  
  2. **Hard binding** (via `bind` that returns a new function).  
  3. **Implicit binding** through the context object where the function is called (e.g., `obj.method()`).  
  4. **Default binding** – global object (`window`/`global` in browsers, `global` in Node) in non‑strict mode; `undefined` in strict mode.  
- **`bind(target, ...boundArgs)`** returns a **new function** that, when invoked, has `this` permanently set to `target`. You cannot change that binding later; however, you can **re‑bind** by calling `bind` again on the bound function, creating another layer.  
  ```js
  const foo = { x: 1, say: function() { console.log(this.x); } };
  const bound = foo.say.bind({ x: 2 });
  bound(); // 2
  const doublyBound = bound.bind({ x: 3 });
  doublyBound(); // 2 (original bind wins)
  ```

**JS8** — *WeakRef & FinalizationRegistry, WeakMap keys*  
- **WeakRef**: holds a **weak reference** to an object, allowing the garbage collector (GC) to reclaim the object if there are no other strong references. The reference becomes **“detached”** when the object is collected. Useful for caches that should not prevent collection.  
- **FinalizationRegistry**: lets you register a **cleanup callback** (finalizer) that runs **after** an object is garbage‑collected. You register an object with `registry.register(target, heldValue, unregisterToken?)`. The callback receives `heldValue`.  
- **Why WeakMap keys must be objects**: WeakMaps store **weak references** to their keys, so the keys themselves must be eligible for GC. Primitives (string, number, etc.) are not garbage‑collectible, thus cannot be weakly held. This design ensures that once all strong references to a key disappear, the entry is automatically removed from the map, preventing memory leaks.  

**JS9** — *V8 optimizations: hidden classes, inline caching, deoptimization*  
- **Hidden classes (shapes)**: V8 assigns a hidden class to objects based on their property layout. When properties are added/removed consistently, objects share the same class, enabling **fast property access** via generated machine code.  
- **Inline caching (IC)**: V8 records the hidden class of recently accessed objects and generates **speculative** code that quickly checks the class and directly accesses the property offset. If the class matches, the fast path is used; otherwise, it falls back to a slower lookup.  
- **Deoptimization**: Occurs when an object’s hidden class changes unexpectedly (e.g., adding/removing properties in different orders, mixing types). V8 then discards the optimized code and reverts to the generic lookup path.  
- **Patterns causing deoptimization**:  
  1. **Property order variance** – adding properties in different sequences across instances.  
  2. **Mixing types** – storing both numbers and strings in the same property.  
  3. **Dynamic property names** (e.g., using variables as keys).  
  4. **Deleting properties** (turns the class into a “deleted” state).  
  5. **Using `__proto__` or `Object.setPrototypeOf`** frequently.  
- **Mitigation**: Initialize objects with a **consistent shape** (declare all properties upfront, even if `undefined`), avoid sparse deletions, and keep property access patterns uniform.

**JS10** — *Tree‑shaking*  
- **Tree‑shaking** is a term for **dead‑code elimination** performed by module bundlers (Webpack, Rollup, etc.) during the build of ES modules. It relies on **static analysis** of `import`/`export` statements.  
- **ES Modules (ESM)** use **lexical, immutable bindings** (`import { foo } from 'mod'`). Because imports/exports are declarative, the bundler can determine which exports are actually used and drop the rest.  
- **CommonJS (CJS)** uses **runtime** `require` and `module.exports`, which are **dynamic** and cannot be statically analyzed for unused exports. Hence, CJS bundles typically include the whole module unless manual pruning or special transforms (e.g., `babel-plugin-transform-remove-unused-exports`) are applied.  
- **Why CJS isn’t tree‑shakable**: The `require` call can be conditioned on runtime variables, and `module.exports` can be reassigned, making it impossible for the bundler to know at build time which parts are dead.

**JS11** — *null vs undefined, == vs ===, nullish coalescing & optional chaining*  
- **`null`**: an assignment value meaning “no value” (explicitly set).  
- **`undefined`**: means a variable has been declared but not assigned, or a function lacks a return value.  
- **Abstract equality (`==`)**: performs type coercion. `null == undefined` yields `true`; all other comparisons with `null` or `undefined` are `false` (except `null == 0` or `undefined == 0` which are `false` because the spec treats them as non‑coercible).  
- **Strict equality (`===`)**: no coercion; `null === undefined` is `false`.  
- **Nullish coalescing (`??`)**: returns the left operand if it is **not** `null` **and** not `undefined`; otherwise returns the right operand. Useful for defaulting while preserving `0`, `false`, or `""`.  
  ```js
  const a = null ?? 'default'; // 'default'
  const b = 0 ?? 42;           // 0
  ```
- **Optional chaining (`?.`)**: safely accesses properties/methods; if the left side is `null` or `undefined`, evaluation short‑circuits and returns `undefined` instead of throwing.  
  ```js
  const name = user?.profile?.name;
  ```

**JS12** — *map, filter, reduce, flatMap*  
- **`map(callback)`**: transforms each element, returning a new array of the same length. `callback(item, index, array)`.  
- **`filter(predicate)`**: keeps elements for which `predicate` returns truthy, producing a new array (possibly shorter).  
- **`reduce(accumulator, [initialValue])`**: folds the array into a single value. `accumulator(prev, curr, index, array)`. If `initialValue` is supplied, it becomes the first `prev`; otherwise the first array element is used and reduction starts from the second element.  
  ```js
  [1,2,3].reduce((sum, x) => sum + x, 0); // 6
  ```
- **`flatMap(mapper)`**: first applies `mapper` (like `map`), then **flattens** the result by one level (similar to `map` + `flat(1)`). Useful when `mapper` returns arrays.  
  ```js
  [[1,2],[3,4]].flatMap(x => x * 2); // [2,4,6,8]
  ```

**JS13** — *Template literals, tagged templates*  
- **Template literals** (`\`text ${expr} more\``) allow multi‑line strings and embedded expressions.  
- **Tagged templates**: a function placed before the template literal receives an array of **raw** strings (exactly as written, with template delimiters) and the **interpolated** values.  
  ```js
  function htmlEscape(literals, ...subs) {
    let result = '';
    literals.forEach((l, i) => {
      result += l;
      if (i < subs.length) {
        result += subs[i].replace(/&/g, '&amp;')
                         .replace(/</g, '&lt;')
                         .replace(/>/g, '&gt;');
      }
    });
    return result;
  }
  const name = "<script>";
  const safe = htmlEscape`<div>${name}</div>`; // "&lt;div&gt;&lt;script&gt;&lt;/div&gt;"
  ```
- Common uses: HTML sanitization, SQL query building, i18n string interpolation, logging with formatting.

**JS14** — *Destructuring, rest operator*  
- **Object destructuring**: extracts properties into variables.  
  ```js
  const { a, b } = { a: 1, b: 2, c: 3 }; // a=1, b=2
  const { a, c: renamed } = obj; // rename c → renamed
  const { a = 10 } = { b: 5 }; // default when a missing
  ```
- **Array destructuring**: extracts by position.  
  ```js
  const [x, , z] = [1, 2, 3]; // x=1, z=3
  const [first, ...rest] = [1,2,3,4]; // first=1, rest=[2,3,4]
  ```
- **Rest operator (`...`)** in destructuring gathers remaining elements (array) or own enumerable properties (object) into a new array/object.  
  ```js
  function foo([a, ...b]) { /* a=first, b=rest */ }
  ```

**JS15** — *for…in vs for…of*  
- **`for…in`**: iterates over **enumerable property keys** of an object (including inherited ones from the prototype chain). Primarily for **object** iteration.  
- **`for…of`**: iterates over **values** of an **iterable** (arrays, strings, Maps, Sets, NodeLists, custom objects with `[Symbol.iterator]`). Does **not** include inherited properties and respects the iterator protocol.  
- **Why avoid `for…in` on arrays**: It yields numeric indices **and** any enumerable properties added to `Array.prototype`, leading to unexpected iterations. Use `for…of` (or `Array.prototype.forEach`) for arrays.

**JS16** — *TypeScript generics, constraints, conditional & infer*  
- **Generics**: allow types to be parameterized.  
  ```ts
  function identity<T>(arg: T): T { return arg; }
  ```
- **Generic constraints (`extends`)**: restrict a type parameter to a base type or interface.  
  ```ts
  function logger<T extends { log: (msg: string) => void }>(obj: T) {
    obj.log("hello");
  }
  ```
- **Conditional types** (`T extends U ? X : Y`): choose a type based on a condition.  
  ```ts
  type NonNullable<T> = T extends null | undefined ? never : T;
  ```
- **`infer` keyword**: used inside a conditional type to **infer** a type variable from a construct.  
  ```ts
  type ElementType<T> = T extends (infer U)[] ? U : T;
  // ElementType<string[]> → string
  ```
- **Practical example**:  
  ```ts
  type Promisify<T extends (...args: any) => any> = T extends (...args: infer A) => Promise<infer R>
    ? (...args: A) => Promise<R>
    : T;
  ```

**JS17** — *JavaScript module systems*  
- **CommonJS (CJS)**:  
  - Uses `require('module')` (runtime) and `module.exports`/`exports`.  
  - Loading is **synchronous**, suited for Node’s server‑side environment.  
  - Supports circular references via partially‑ready modules.  
- **ES Modules (ESM)**:  
  - Declarative `import`/`export` syntax, **static** (analyzable at compile time).  
  - Supports **asynchronous loading** (`import()`), top‑level `await`, and **live bindings** (exports can be reassigned).  
  - No circular reference handling; modules are executed in import order with a module record graph.  
- **Node.js handling**:  
  - By default, files with `.mjs` or `"type": "module"` in `package.json` are treated as ESM.  
  - `.js` files are CommonJS unless `"type": "module"` is set.  
  - Interop: ESM can `import` a CJS module (Node wraps it, exposing `module.exports` as the default export). CJS cannot `require` an ESM directly without special loaders.  
- **`"type": "module"`**: Signals that all `.js` files in that package are ESM, enabling tree‑shaking and import/export syntax without extension changes.

**JS18** — *TypeScript structural typing, excess property checks, extends vs satisfies, variance*  
- **Structural type system**: Types are compatible based on their **shape** (members and their types), not the declaration name.  
- **Excess property checks**: When assigning an object literal to a variable of an interface/type, TypeScript disallows properties not declared in the target type **unless**:  
  - The assignment occurs inside a **function call** (the argument is checked against the parameter type, which permits excess properties).  
  - The target type is a **type** (not an interface) **or** you use the `satisfies` operator.  
- **`extends` vs `satisfies`**:  
  - `extends` is used in **type positions** to create a subtype relationship (e.g., `interface Foo extends Bar`).  
  - `satisfies` is a **type‑checking operator** (`expr satisfies Type`) that asserts `expr` conforms to `Type` without affecting the inferred type of `expr`. It enables excess‑property checks in more contexts.  
- **Variance (since TS 4.7)**:  
  - **`in`** (covariant) – type parameter appears only as an output (e.g., `readonly T[]`).  
  - **`out`** (contravariant) – type parameter appears only as an input (e.g., `(arg: T) => void`).  
  - **`in & out`** (bivariant) – default for generic parameters, but can be explicitly set using `in`/`out` modifiers.  
  ```ts
  interface Source<out T> { getItem(): T; }
  interface Sink<in T> { add(item: T): void; }
  ```

**JS19** — *Proxy & Reflect*  
- **Proxy**: creates a wrapper object that can **intercept** fundamental operations (property access, assignment, enumeration, function calls, etc.) via a **handler** object containing traps.  
  ```js
  const target = { value: 42 };
  const handler = {
    get(trapTarget, prop, receiver) {
      console.log('accessed', prop);
      return Reflect.get(trapTarget, prop, receiver);
    },
    set(trapTarget, prop, val, receiver) {
      console.log('set', prop, 'to', val);
      return Reflect.set(trapTarget, prop, val, receiver);
    }
  };
  const proxy = new Proxy(target, handler);
  console.log(proxy.value); // logs, returns 42
  proxy.value = 100;        // logs
  ```
- **Reflect**: a built‑in object with **static methods** that correspond to the proxy traps. Using `Reflect` inside a trap ensures the default behavior (and proper argument handling) while allowing custom logic before/after.  
- **Practical uses**: validation (e.g., ensuring property types), logging/access tracking, lazy loading, reactive data binding (e.g., Vue’s reactivity system), mock objects, sandboxing, etc.

**JS20** — *SharedArrayBuffer & Atomics, Web Workers*  
- **SharedArrayBuffer**: an array‑buffer that can be **shared** between different agents (main thread, workers) because its memory is mapped into the address space of each. Unlike `ArrayBuffer`, it allows **concurrent reads/writes**.  
- **Atomics**: a set of **atomic operations** (read‑modify‑write) that guarantee no race conditions when multiple agents access the same `SharedArrayBuffer`. Operations include `Atomics.add`, `Atomics.sub`, `Atomics.and`, `Atomics.or`, `Atomics.xor`, `Atomics.compareExchange`, `Atomics.wait`, `Atomics.notify`.  
- **Web Workers communication**:  
  - A worker can receive a `SharedArrayBuffer` via `postMessage(buffer, [buffer])`. The main thread and worker share the same binary data.  
  - **Ordering guarantees**: Atomics provide a **happens‑before** relationship; operations are **sequentially consistent** (no reordering across agents).  
  - **`Atomics.wait(ab, index, value, timeout?)`**: Puts the calling thread into a sleep state until the value at `index * sizeof(double)` changes or timeout expires. It releases the lock, allowing another agent to modify the memory and then call `Atomics.notify(ab, index, count?)` to wake up waiting threads. This pattern implements **condition variables** for synchronization.

**Bash**

**B1** — *$@ vs $*, "$@" vs "$"*  
- **`$@`**: Expands to the **positional parameters** as separate words, **preserving** each argument (even if empty or containing spaces).  
- **`$*`**: Expands to all parameters as a **single string**, words are separated by the first character of `IFS` (usually space).  
- **`"$@"`**: Each parameter is quoted, so arguments with spaces are kept intact as individual arguments when passed to a command.  
- **`"$*"`**: The whole expansion is quoted as one argument; e.g., `"$*"` with args `a b` becomes `"a b"` (one argument).  

**B2** — *set -euo pipefail*  
- **`-e`**: **Exit** immediately if a command exits with a non‑zero status (errors).  
- **`-u`**: Treat **unbound variables** as an error and exit.  
- **`-o pipefail`**: The pipeline’s return status is that of the **rightmost command** that exited with a non‑zero status, or zero if all succeed. Without it, the pipeline status is the exit status of the **last** command only.  

**B3** — *$(command) vs `command`, $((expr)) vs expr*  
- **`$(command)`** (preferred): Command substitution that captures the **stdout** of `command`, supports nesting, and is easier to read.  
- **`` `command` ``** (backticks): Older syntax for command substitution; harder to nest and less visually clear.  
- **`$((expression))`**: Arithmetic expansion using **integer arithmetic**; supports operators like `+ - * / % **`.  
- **`expr`**: External command for arithmetic and string operations; slower, requires careful quoting, and has different syntax (`expr $a + $b`). Modern scripts prefer `$(( ))`.  

**B4** — *Process substitution*  
- Syntax: `<(...)` or `>(...)`. Replaces a command with a **named pipe** (FIFO) or temporary file, allowing the command to read from or write to it as if it were a regular file.  
- **Example with `diff`**:  
  ```bash
  diff <(grep pattern file1) <(grep pattern file2)
  ```
  Here `grep` outputs to two anonymous FIFOs, and `diff` reads from them directly, without creating intermediate files.  

**B5** — *Safe iteration over files with spaces*  
- **Why `for f in $(ls)` is dangerous**: `$(ls)` word‑splits on spaces/newlines, and globbing (`*`) does not quote, so filenames like `my file.txt` become two arguments.  
- **Safe approaches**:  
  ```bash
  # Using globbing with nullglob (skip non‑matches) and quoting
  shopt -s nullglob
  for f in "$PWD"/*; do
    [[ -f "$f" ]] && echo "Processing $f"
  done
  ```
  Or with `find`:
  ```bash
  find . -type f -print0 | while IFS= read -r -d '' f; do
    echo "Processing $f"
  done
  ```

**B6** — *Here document vs here string*  
- **Here document** (`<<EOF`): Reads **multiple lines** until the delimiter `EOF` is encountered.  
  ```bash
  cat <<EOF > file.txt
  Line 1
  Line 2
  EOF
  ```
- **Here string** (`<<<`): Supplies a **single string** as stdin to a command.  
  ```bash
  grep pattern <<< "some text with pattern"
  ```
- **`<<-EOF`**: Strips leading **tab** characters from the delimiter, allowing indentation of the here‑doc body for readability. Spaces are **not** stripped.  

**B7** — *Redirection differences*  
- **`cmd > file 2>&1`**: First redirects **stdout** (`1`) to `file`. Then duplicates **stderr** (`2`) to wherever stdout is currently pointing (i.e., the same `file`). Result: both streams go to `file`.  
- **`cmd 2>&1 > file`**: First `2>&1` makes **stderr** follow stdout (stdout is still the terminal). Then `> file` redirects **stdout** to `file`, but stderr (still pointing to the original stdout) remains on the terminal. Hence only stdout ends up in `file`.  
- **`cmd &> file`**: Shorthand for `cmd > file 2>&1`; both streams are merged into `file`.  

**B8** — *Safe lock‑file function*  
```bash
#!/usr/bin/env bash
lock_dir="/var/lock/myapp"
lock_file="${lock_dir}/lock"

acquire_lock() {
  mkdir -p "$lock_dir" || exit 1
  if ln -T "$lock_file" "$(mktemp -u "${lock_file}.XXXXXX")" 2>/dev/null; then
    # lock acquired
    return 0
  else
    echo "Lock held by another process" >&2
    return 1
  fi
}

release_lock() {
  rm -f "$lock_file"
}

cleanup() {
  release_lock
}
trap cleanup EXIT INT TERM

acquire_lock || exit 1
# ---- critical section ----
sleep 10   # example work
# ---------------------------
```
- **Why `mkdir` (or symlink) is preferred**: It is **atomic** on most filesystems; either the directory/file is created or it isn’t, preventing race conditions. Simple file creation (`touch`) is not atomic and can lead to lost updates if two processes check‑and‑create simultaneously.  

**B9** — *Single vs double quotes vs no quotes*  
- **Single quotes** `''`: treat **everything** literally; no variable expansion, no special characters.  
  ```bash
  echo '$HOME'   # outputs $HOME
  ```
- **Double quotes** `""`: allow **variable and command substitution**, but backslashes still escape `$`, `` ` ``, `\`.  
  ```bash
  echo "$HOME"   # expands to user's home directory
  ```
- **No quotes** (bare word): performs **word splitting** and **globbing** (`*`, `?`).  
  ```bash
  echo *         # lists files in current dir
  ```
- **Example differences**:  
  ```bash
  var="hello * world"
  echo $var      # hello (list of files) world   (split+glob)
  echo "$var"    # hello * world                (preserves spaces & *)
  echo '$var'    # $var                         (literal)
  ```

**B10** — *File existence checks*  
- **`[ -e file ]`** or **`test -e file`**: true if file exists (any type).  
- **`[ -d file ]`**: true if it is a **directory**.  
- **`[ -r file ]`**: true if **readable** by the current user.  
- **`[[ ]]`** vs `[ ]`: `[[` is a **bash keyword** with extended features (pattern matching, no word‑splitting on variables, `&&`, `||` inside). `[` is a command (POSIX `test`).  

**B11** — *Special parameters $? $$ $! $#*  
- **`$?`**: Exit status of the **last command** (0 = success).  
- **`$$`**: PID of the **current shell**.  
- **`$!`**: PID of the **most recent background job**.  
- **`$#`**: Number of **positional parameters** passed to the script/function.  
- **Use cases**:  
  - `$?` for error handling (`if [ $? -ne 0 ]; then …`).  
  - `$$` to generate unique temp file names (`tmpfile=$$.tmp`).  
  - `$!` to wait for a specific background process (`wait $!`).  
  - `$#` to check required arguments (`if [ $# -lt 2 ]; then …`).  

**B12** — *Functions in bash*  
- **Definition**: `foo() { ... }` or `function foo { ... }` (both equivalent).  
- **Return values**: Use `return <num>` (0‑255) for status; to return a string, **echo** it and capture with command substitution: `result=$(foo)`.  
- **Example**:  
  ```bash
  sum() {
    local total=0
    for n; do ((total+=n)); done
    return $total   # not portable; better: echo $total
  }
  # Portable version
  sum2() { echo $(( $@ )); }
  val=$(sum2 3 4)   # val=7
  ```

**B13** — *PATH, command resolution, builtins vs externals*  
- **`PATH`**: Colon‑separated list of directories where the shell looks for **external commands**.  
- **Resolution**: Shell first checks **aliases**, then **functions**, then **builtins**, then searches `PATH`.  
- **Builtin**: Implemented inside the shell (e.g., `cd`, `echo`). Faster, no fork.  
- **External**: Separate executable (e.g., `/bin/ls`).  
- **Check**: `type <cmd>` shows if it’s a builtin, alias, or file. `command -v <cmd>` returns the path or “builtin”.  

**B14** — *trap*  
- **Syntax**: `trap 'commands' SIGNALS`.  
- **Common signals**: `EXIT` (always runs on normal or error exit), `ERR` (when a command fails), `INT` (Ctrl‑C), `TERM` (termination request).  
- **Order**: If multiple traps are set for the same signal, the **most recent** one replaces the previous. For `EXIT`, all registered actions are executed in **reverse order** of registration when the script exits.  
- **Example cleanup**:  
  ```bash
  temp_file=$(mktemp)
  trap 'rm -f "$temp_file"; exit' EXIT INT TERM
  # ... use temp_file ...
  ```

**B15** — *xargs vs command substitution, parallel execution*  
- **`xargs`**: Reads items from stdin and **executes** a command with those items as arguments. Handles **word splitting** and **batching** (`-n`, `-L`).  
- **Command substitution** (`$(...)`)**: Captures command output as a **single string**; not suitable for large lists because of **argument‑list length limits**.  
- **Handling spaces/newlines**: Use `find … -print0 | xargs -0 …` – `-0` tells `xargs` to split on NUL, matching `find -print0`.  
- **Parallel**: `xargs -P <n>` runs up to `<n>` jobs concurrently. Example:  
  ```bash
  find . -type f -print0 | xargs -0 -P 4 -I {} sh -c 'process "{}"'
  ```  

**B16** — *Bash arrays & associative arrays*  
- **Indexed array**: `arr=(a b c)` or `arr[0]=a`. Access: `${arr[i]}`. Length: `${#arr[@]}`. Append: `arr+=("new")`. Iterate: `for v in "${arr[@]}"; do …`.  
- **Associative array** (bash ≥4): `declare -A map`. Define: `map[key]=value`. Access: `${map[key]}`. Keys: `${!map[@]}`. Length: `${#map[@]}`. Iterate: `for k in "${!map[@]}"; do echo "$k = ${map[$k]}"; done`.  
- **Differences**: Indexed arrays are **ordered** and use integer indices; associative arrays are **unordered** (as of bash 4.x) and use arbitrary strings as keys.  

**B17** — *Subshell vs group command*  
- **Subshell** `(...)`: Commands run in a **child process**; variable changes **do not affect** the parent. Exit status of the subshell is available to the parent.  
- **Group command** `{ ...; }`: Runs commands in the **current shell**; variable changes persist, but the block itself has no exit status (the status of the last command inside is the block’s status).  
- **While loop & pipe**: `somecommand | while read line; do …; done` executes the `while` body in a **subshell**, so variable assignments inside are lost after the loop. Use `while read line; do …; done` **without** the pipe or redirect the whole block into a subshell that exports variables if needed.  

**B18** — *Signals, job control*  
- **SIGINT** (Ctrl‑C): Interrupt signal; default action is to terminate.  
- **SIGTERM** (kill): Termination request; default is to exit gracefully, allowing cleanup.  
- **SIGHUP**: Hangup; often used by daemons to **reload config** or restart.  
- **SIGKILL**: Cannot be caught or ignored; forces immediate termination.  
- **Graceful shutdown**: Trap `SIGINT SIGTERM` to perform cleanup, stop background jobs (`kill %1`), and then exit. Example:  
  ```bash
  trap 'echo "Cleaning up…"; kill %1; exit' INT TERM
  some_long_running_job &
  wait
  ```  

**B19** — *Parallel log processing script*  
```bash
#!/usr/bin/env bash
set -euo pipefail

INPUT="large.log"
TMPDIR=$(mktemp -d)
trap "rm -rf '$TMPDIR'; exit" EXIT INT TERM

# Split log into N chunks
CHUNKS=4
split -l $(( $(wc -l < "$INPUT") / CHUNKS )) "$INPUT" "$TMPDIR/part_"

# Process each chunk in parallel, writing results to separate files
process_chunk() {
  local part=$1
  # Example: grep errors and count
  grep "ERROR" "$part" | wc -l > "${part}.cnt"
}
export -f process_chunk

# Use xargs -P for parallelism
find "$TMPDIR" -name 'part_*' -print0 | xargs -0 -P "$CHUNKS" -I {} bash -c 'process_chunk "$@"' _ {}

# Merge results
total=0
for cnt in "$TMPDIR"/part_*.cnt; do
  total=$(( total + $(cat "$cnt") ))
done
echo "Total ERROR lines: $total"
```
- **Performance trade‑offs**: Splitting reduces I/O contention; parallel `xargs` uses CPU cores. Error propagation: if any `process_chunk` fails, `set -e` aborts the script; you can add `|| echo "Error processing $part"` inside the loop to continue while logging failures.  

**B20** — *exec vs normal command, file descriptor manipulation, coprocess*  
- **`exec`**: Replaces the **current shell process** with the specified command. No new process is forked; the PID stays the same. Useful for **daemonizing** or **redirecting** all future I/O.  
  ```bash
  exec >output.log   # all subsequent stdout goes to output.log
  exec 2>&1          # merge stderr into stdout
  exec myscript args # replace shell with myscript
  ```
- **File descriptor manipulation**:  
  - `exec 3>file` opens **FD 3** for writing to `file`.  
  - `exec 3>&-` closes FD 3.  
  - `exec 3>&1` duplicates FD 1 (stdout) into FD 3.  
- **Coprocess**: `coproc CMD` starts `CMD` in a background process and sets up **named pipes** `COPROC[0]` (read) and `COPROC[1]` (write). Example:  
  ```bash
  coproc nc -lk 12345
  # read from listener
  read -u "${COPROC[0]}" line
  # write to it
  echo "hello" >&"${COPROC[1]}"
  ```  
  Coprocesses are handy for bidirectional communication with long‑running background programs without spawning separate scripts.

**PowerShell**

**PS1** — *Write-Output vs Write-Host*  
- **`Write-Output`** (alias `Write`/`echo`): Sends objects to the **success output stream** (`stdout`). These objects can be captured, piped, or collected into a variable.  
- **`Write-Host`**: Writes directly to the **host** (console) **without** using any output stream. The text is **not** captured by `Out-File`, `|` pipeline, or `Measure-Object`. Use for UI messages that should not interfere with data flow.  

**PS2** — *Pipeline, ForEach-Object vs foreach*  
- **Pipeline (`|`)**: Transmits **objects** from the left command to the right. Each object is processed **one at a time**, enabling streaming and lazy evaluation.  
- **`ForEach-Object`** (alias `foreach`, `%`): A **cmdlet** that works in the pipeline, executing a script block for each input object.  
- **`foreach` statement**: A **language construct** that iterates over a **collection** that is already materialized (e.g., an array). It does **not** participate in the pipeline; it processes the whole collection eagerly.  
- **When to use**:  
  - Use **pipeline + `ForEach-Object`** for streaming large data (e.g., `Get-ChildItem | ForEach-Object { … }`).  
  - Use **`foreach`** when you have a concrete collection and need classic loop control (`break`, `continue`).  

**PS3** — *[PSCustomObject] vs [hashtable]*  
- **`[PSCustomObject]`**: Creates an object with **named properties**. Properties are **enumerable** and appear as **real object members**, supporting `Select-Object`, `Format-Table`, and serialization (e.g., JSON) nicely.  
  ```powershell
  $o = [PSCustomObject]@{Name='Alice'; Age=30}
  ```
- **`[hashtable]`**: A key‑value map. Keys are strings; values can be any object. Useful for **lookup tables** or when you need mutable key‑value storage. Not as friendly for formatting or JSON serialization (keys become property names but order isn’t guaranteed).  
- **Conversion**:  
  - Hashtable → PSCustomObject: `[PSCustomObject]$ht`  
  - PSCustomObject → Hashtable: `$o | Get-Member` → use `$o.psobject.Properties` or `$o | Select-Object -ExpandProperty *` to rebuild a hashtable.  

**PS4** — *Error handling: terminating vs non‑terminating, -ErrorAction, $ErrorActionPreference, try/catch*  
- **Terminating errors**: By default, **cmdlet** errors that are not handled become **terminating** and stop the pipeline.  
- **Non‑terminating errors**: Often **script** errors (e.g., `Write-Error -ErrorAction SilentlyContinue`) or errors from .NET code that are caught. They allow the script to continue.  
- **`-ErrorAction`** (common parameter): Controls how a **specific cmdlet** reacts (`Stop`, `Continue`, `SilentlyContinue`, `Inquire`).  
- **`$ErrorActionPreference`**: Global default for all cmdlets unless overridden by `-ErrorAction`.  
- **`try/catch`**: Catches **terminating** errors only. `catch [ExceptionType]` can handle specific exceptions; `catch` without type catches all. `finally` runs cleanup code.  

**PS5** — *Splatting (@params)*  
- **Splatting** expands a hashtable or array into individual arguments.  
  ```powershell
  $params = @{ Path = 'C:\temp'; Filter = '*.txt' }
  Get-ChildItem @params
  ```
- **Difference from passing a hashtable as a single parameter**: When you pass `@params` directly, each key becomes a named parameter; if you pass `$params` (the hashtable itself), the cmdlet receives **one** argument (the hashtable) unless the parameter is of type `[hashtable]` and expects it. Splatting is cleaner and works with any parameter set.  

**PS6** — *PowerShell remoting*  
- **`Invoke-Command -ComputerName …`**: Executes a **script block** on one or many remote computers **without** an interactive session. Ideal for one‑off commands or background jobs.  
- **`Enter-PSSession …`**: Opens an **interactive** remote session, similar to an SSH shell, where you can type commands live.  
- **Protocol**: Default is **Windows Remote Management (WinRM)** using **HTTP/HTTPS**. PowerShell 7+ also supports **SSH** remoting (`ssh user@host -p 22 pwsh -c "…"`) via the `SSH` subsystem.  
- **Double‑hop problem**: When a remote session tries to authenticate to a **third** machine, credentials cannot be delegated by default (Kerberos delegation or CredSSP required). Solutions:  
  - Enable **CredSSP** on client and server (`Enable-WSManCredSSP -Role Client -DelegateComputer *` and server side).  
  - Use **`-Authentication Negotiate`** with Kerberos delegation if configured.  
  - Pass explicit credentials via `PSCredential` objects.  

**PS7** — *Type system & pipeline behavior*  
```powershell
function Get-Items {
    $result = @()
    $result += "one"
    return $result
}
$x = Get-Items
$x.GetType().Name   # What is this?
```
- **Explanation**:  
  - Inside the function, `$result` is an **array** (`System.Object[]`).  
  - When the function **returns** an array **with exactly one element**, PowerShell **unwraps** it: the pipeline receives the single object (`"one"`), not the array. Hence `$x` is a `String`, and `$x.GetType().Name` yields `"String"`.  
  - If the function returns **zero** items (`$result = @()`), the return value is an **empty array** (`System.Object[][]`? Actually `System.Object[]` with zero length), so `$x.GetType().Name` would be `"Object[]"`.  
- **Correct pattern** to always get an array regardless of count: use the **array subexpression** `@( … )` or return `$result` **without** `return` (the last expression is returned). Example:  
  ```powershell
  function Get-Items {
      @( "one", "two" )   # always an array
  }
  ```  

**PS8** — *[scriptblock] vs function, passing to remote, double‑hop*  
- **`[scriptblock]`**: A compiled block of code that can be **serialized** and sent to remote sessions or background jobs. Captures its **current scope** (variables) unless using `script:` or `param()` to make it self‑contained.  
- **Function**: Defined with `function Name { … }`. Not directly serializable; to run remotely you must convert it to a scriptblock (`[scriptblock]::Create(...)` ) or use `Invoke-Command` with `-ArgumentList` and a scriptblock literal.  
- **Passing to remote**: Use `Invoke-Command -ComputerName … -ScriptBlock { … }`. Variables from the caller can be injected with `-ArgumentList` or the `$using:` keyword (PowerShell 7+).  
- **Double‑hop**: When a remote scriptblock tries to access another remote resource, credentials cannot flow automatically. Solutions:  
  - **CredSSP**: Enable on client (`Enable-WSManCredSSP -Role Client -DelegateComputer *`) and server (`Enable-WSManCredSSP -Role Server`). Then use `-Authentication CredSSP -Credential $cred`.  
  - **Explicit credentials**: Pass a `PSCredential` object and use it inside the remote block (`Invoke-Command … -Credential $cred`).  
  - **SSH remoting** (PowerShell 7+): Uses the SSH agent forwarding, which handles the hop differently.  

**PS9** — *@() vs [array], indexing $null vs []*  
- **`@()`**: The **array subexpression** operator. Forces the evaluation of its contents into an **array**, even if the result is a single object or nothing.  
  ```powershell
  $a = @('one')          # $a is [string[]] with one element
  $b = @()               # $b is an empty array [object[]]
  $c = @(Get-Item .)     # ensures $c is an array, even if Get-Item returns one item
  ```  
- **`[array]`**: Cast operator. Converts the **entire** input into an array **if it isn’t already**. If the input is already an array, it is returned unchanged.  
  ```powershell
  $x = 'a'
  [array]$x   # becomes [string[]]@('a')
  $y = 1,2,3
  [array]$y   # still [int[]]@(1,2,3)
  ```  
- **Indexing**:  
  - `$null[0]` throws an **error** (`Cannot index into a $null array`).  
  - `@()[0]` returns `$null` because the array exists but has no elements.  
  - An **empty array** (`[array]@()`) also returns `$null` when indexed out of bounds.  

**PS10** — *Comparison operators*  
- **`-eq` / `-ne`**: Equality and inequality (case‑insensitive for strings in PowerShell 7+ unless using `-ceq`/`-cne`).  
- **`-like` / `-clike`**: Wildcard matching (`*`, `?`). `-like` is case‑insensitive; `-clike` is case‑sensitive.  
- **`-match` / `-cmatch`**: Regex matching. `-match` returns a **boolean** and populates automatic variables (`$matches`, `$?`). `-cmatch` is case‑sensitive.  
- **`-contains` / `-in`**:  
  - `-contains` checks if **a collection contains a single element** (`$arr -contains $x`).  
  - `-in` checks if **a value is in a collection** (`$x -in $arr`). They are logical inverses but not interchangeable in syntax.  
- **Case‑sensitive variants** (`-ceq`, `-cne`, `-clike`, `-cmatch`) force ASCII case sensitivity.  

**PS11** — *PowerShell modules*  
- **Script module** (`.psm1`): A PowerShell script file that exports functions, variables, aliases, etc. When imported, its code runs in the caller’s runspace.  
- **Manifest module** (`.psd1`): A **module manifest** describing metadata (ModuleVersion, Author, RequiredModules, etc.) and optionally listing **script modules** to dot‑source. It can also declare **nested modules** and **exported members**.  
- **Binary module** (`.dll`): Contains .NET types and cmdlets compiled to C#. Loaded via `#requires` or `using module`.  
- **`Import-Module`**: Looks for a module by name, reads the manifest (if present), executes the script module(s), and makes exported items available. It respects `PSModulePath`.  

**PS12** — *String interpolation & here‑strings*  
- **Double‑quoted strings** (`"..."`): Support **variable expansion** (`$var`) and **subexpressions** (`$(...)`).  
  ```powershell
  $name = "Alice"
  "Hello, $name"          # Hello, Alice
  "Count: $(Get-Date)"    # Count: <current date>
  ```  
- **Single‑quoted strings** (`'...'`): Treat content **literally**; no expansion.  
- **Here‑string** (`@"..."@`): Multi‑line string preserving line breaks and allowing interpolation (if double‑quoted).  
  ```powershell
  $template = @"
  <html>
    <body>
      <h1>$title</h1>
    </body>
  </html>
  "@
  ```  
- **Differences**: Double quotes enable expansion; single quotes do not; here‑strings are useful for large blocks (e.g., XML, SQL).  

**PS13** — *Get‑Member, Select‑Object vs Where‑Object*  
- **`Get-Member`**: Shows **properties, methods, and notes** of an object or type. Example: `Get-Process | Get-Member`.  
- **Properties vs Methods vs NoteProperties**:  
  - **Properties**: Simple data fields (`Name`, `Id`).  
  - **Methods**: Callable actions (`Kill()`, `ToString()`).  
  - **NoteProperties**: Script properties added by cmdlets (often read‑only, e.g., `PSComputerName`).  
- **`Select-Object`**: Projects **specific properties** or creates **calculated properties**. Can also use `-First`, `-Last`, `-Unique`.  
- **`Where-Object`** (alias `?`): Filters objects based on a **script block** (`$_` represents the current object). Example: `Get-Process | Where-Object { $_.CPU -gt 10 }`.  

**PS14** — *PowerShell classes (v5+)*  
- Introduced to define **.NET‑style classes** directly in PowerShell.  
- **Differences from C#**:  
  - No separate compilation step; classes are compiled on‑the‑fly.  
  - Limited to **single inheritance**; no interfaces (but you can implement interfaces by declaring methods).  
  - Constructors are defined with a **parameter list** after the class name, not with the `class` keyword.  
  - Properties can be auto‑implemented (`property string Name { get; set; }`).  
- **When to use**: When you need **strongly‑typed objects**, encapsulation, or to interoperate with .NET APIs. For simple data containers, a **hashtable** or **PSCustomObject** is often sufficient.  

**PS15** — *CmdletBinding & advanced functions*  
- **`[CmdletBinding()]`**: Turns a normal function into an **advanced function**, enabling common parameters (`-Verbose`, `-ErrorAction`, `-OutVariable`, pipeline support).  
- **`SupportsShouldProcess`**: Adds **WhatIf** and **Confirm** support, allowing the function to announce what it would do without side effects.  
- **`DefaultParameterSetName`**: Determines which parameter set is used when no disambiguating parameters are provided.  
- **`ValueFromPipeline` / `ValueFromPipelineByPropertyName`**: Allow the parameter to accept input from the pipeline (by value or by property name).  
- **`Begin/Process/End` blocks**:  
  - **Begin**: Runs once before any input is processed (good for setup).  
  - **Process**: Runs once per pipeline object (the main loop).  
  - **End**: Runs after all input is processed (cleanup, final calculations).  

**PS16** — *PowerShell providers*  
- **Providers** expose **drive‑like** access to different data stores (FileSystem, Registry, Certificate, Environment, Alias, Function, Variable, etc.).  
- **`Get-ChildItem`** works uniformly:  
  - `Get-ChildItem HKLM:\Software` → registry keys.  
  - `Get-ChildItem Cert:\LocalMachine\My` → certificates.  
  - `Get-ChildItem Env:` → environment variables.  
- **Accessing registry like a file system**: Use `Get-Item`, `Set-Item`, `New-Item`, `Remove-Item` on `HKLM:` or `HKCU:` paths. Example: `Set-ItemProperty -Path 'HKLM:\Software\MyApp' -Name Version -Value '1.0'`.  

**PS17** — *Runspaces & parallel execution*  
- **Runspace**: An isolated execution environment for PowerShell code. A **runspace pool** manages a collection of runspaces, allowing parallel execution without spawning separate processes.  
- **`[powershell]`**: A .NET object representing a **script block** running inside a runspace. You can invoke it, pass inputs, and collect outputs.  
- **`ForEach-Object -Parallel`** (PowerShell 7+): Simplifies parallel processing by automatically distributing items across runspaces in the pool. Example:  
  ```powershell
  Get-ChildItem | ForEach-Object -Parallel {
      $_.Length
  }
  ```  
- **Manual runspace management**: Useful when you need fine‑grained control (custom thread pool, long‑living sessions, or inter‑runspace communication).  

**PS18** — *PSScriptAnalyzer*  
- **Static code analysis** tool that enforces PowerShell best practices.  
- **Rules**: Predefined checks (e.g., `PSAvoidUsingWriteHost`, `PSUseShouldProcessForStateChangingFunctions`). Each rule has a **severity** (`Error`, `Warning`, `Information`).  
- **Custom rules**: Defined in a JSON/YAML file and loaded via `-CustomRulePath`.  
- **Suppressing**: Use `#pscriptanalyzer:disable <RuleId>` comment or configure the rule severity to `None`.  
- **CI/CD integration**: Run `Invoke-ScriptAnalyzer` in build pipelines; fail the build on errors or treat warnings as failures based on policy.  

**PS19** — *$using: vs $args / -ArgumentList, serialization limits*  
- **`$using:`** (PowerShell 7+): Allows a **scriptblock** running in a remote session, background job, or `ForEach-Object -Parallel` to **capture** variables from the calling scope by value. Example:  
  ```powershell
  $path = "C:\temp"
  Invoke-Command -ScriptBlock { Get-ChildItem -Path $using:path }
  ```  
- **`$args` / `-ArgumentList`**: Passes **arguments** positionally to a scriptblock. The block sees them as an array (`$args`). This is the classic way for `Invoke-Command`, `Start-Job`, and `ForEach-Object`.  
- **Serialization limits**: When objects are sent to a remote session or a job, they are serialized as **CLIXML**. Deeply nested objects, custom .NET types without `[Serializable]` attributes, or large data structures may exceed the default depth/size limits, causing truncation or errors. Mitigations:  
  - Use simple data types (PSCustomObject, arrays, hashtables).  
  - Increase limits with `$PSDefaultParameterValues['*:ErrorAction']='Continue'` or by configuring `WSMan` session options (`-MaxMemoryPerShellMB`, `-MaxShellsPerShell`).  
  - For very large data, consider **streaming** or **file‑based** exchange (write to a temp file, process remotely, read back).  

**PS20** — *Desired State Configuration (DSC)*  
- **DSC** is a **declarative** configuration management platform built into PowerShell.  
- **Key components**:  
  - **Configuration**: A PowerShell script block that defines the desired state using DSC **resources**.  
  - **Resources**: Modules implementing `Get-`, `Set-`, and `Test-` functions for a specific domain (e.g., `xWindowsFeature`, `File`).  
  - **Local Configuration Manager (LCM)**: The agent on each node that applies configurations, reports status, and can operate in **Push** (configuration sent from a pull server) or **Pull** (node periodically queries a pull server).  
- **Windows PowerShell vs PowerShell 7+**:  
  - In **Windows PowerShell**, DSC is tightly integrated with the OS and supports many built‑in resources.  
  - In **PowerShell 7**, DSC functionality is **community‑maintained** (`powershell-dsc` module) and works cross‑platform (Linux, macOS) but with a reduced set of native resources.  
- **Modern IaC alternatives**: Tools like **Terraform**, **Ansible**, **Chef**, **Puppet**, or **Azure Arc** have largely supplanted DSC for cloud‑native environments, offering richer ecosystems and multi‑cloud support. DSC remains useful for on‑prem Windows‑centric automation.
