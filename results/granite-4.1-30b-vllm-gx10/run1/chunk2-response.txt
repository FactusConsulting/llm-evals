**Kubernetes**

**K1 — Easy:**  
- **Deployment**: Manages replicated, stateless pods. Ideal for apps that can be scaled horizontally and don’t require stable network identities or persistent storage. Uses a ReplicaSet under the hood.  
- **StatefulSet**: Extends Deployments for stateful applications. Provides stable, unique network identifiers, ordered, graceful deployment and scaling, and persistent storage via PVCs. Suitable for databases, queues, etc.

**K2 — Easy:**  
A Service of type **ClusterIP** creates an internal virtual IP that is only reachable within the cluster. Kubernetes’ **kube-proxy** (using iptables or IPVS) watches the Service and creates rules that load‑balance incoming traffic to the matching pod **Endpoints** (the pod IPs that satisfy the Service’s selector). The client inside the cluster resolves the Service name to the ClusterIP, and the proxy forwards the request to one of the healthy pods.

**K3 — Medium:**  
- **PersistentVolume (PV)**: A piece of storage in the cluster that is provisioned by an administrator or dynamically via a **StorageClass**. It is a cluster‑wide resource.  
- **PersistentVolumeClaim (PVC)**: A request for storage by a pod. It binds to a matching PV (based on size, access modes, and optionally StorageClass). PVCs are namespace‑scoped.  
- **StorageClass**: Describes the “class” of storage (e.g., SSD, HDD, NFS) and defines the provisioner that creates PVs on demand. When a PVC specifies a StorageClass, the cluster automatically provisions a matching PV.  

Relationship: **PVC → PV** (binding) and **StorageClass** governs how the PV is created for the PVC.

**K4 — Medium:** (4+ checks)  
1. **Logs**: `kubectl logs <pod> -p` to see the container’s last run output; look for crash messages or unhandled exceptions.  
2. **Events**: `kubectl describe pod <pod>` → Events section; may show “CrashLoopBackOff”, “Error”, “FailedCreatePodSandBox”, etc.  
3. **Container State**: `kubectl get pod <pod> -o yaml` → `state` field; verify if `waiting` has a non‑nil `message`.  
4. **Resource Limits/Requests**: Check if the pod’s resource requests exceed what the node can provide, causing OOM kills.  
5. **Readiness/Liveness Probes**: Inspect probe configurations; a failing probe can cause restarts.  
6. **Image Pull Issues**: Verify `imagePullErrors` in the describe output; ensure the registry credentials are correct.

**K5 — Medium:**  
**CoreDNS** is the default DNS server in Kubernetes. It resolves Service names (e.g., `mysvc.myns.svc.cluster.local`) to ClusterIPs and handles forwarding to external DNS for other domains. If CoreDNS pods are down:  
- New DNS queries fail (timeouts).  
- Existing cached entries may still work briefly, but eventually all resolution breaks.  
- Services become unreachable by name, causing application failures.  
- The cluster becomes partially or fully non‑functional until CoreDNS recovers.

**K6 — Hard:**  
The scheduler follows a two‑phase process: **filtering** → **scoring**.  

**Filtering** (predicate checks) eliminates nodes that cannot host the pod:  
- **Resource availability** (CPU, memory, ephemeral storage).  
- **Pod affinity/anti‑affinity** and node selectors.  
- **Taints & tolerations** (node must not have untolerated taints).  
- **Volume binding** (if the pod needs PVCs, the node must have access).  
- **Topology constraints** (zone/region).  

**Scoring** (priority functions) ranks the remaining nodes:  
- **LeastRequestedPriority**: prefers nodes with lowest used resources.  
- **BalancedResourceAllocation**: aims for even resource distribution.  
- **NodeAffinityPriority**: gives higher score to nodes matching affinity rules.  
- **TaintTolerationPriority**: penalizes nodes with many taints not tolerated.  
- **InterPodAffinityPriority**: respects pod‑to‑pod affinity/anti‑affinity.  

The node with the highest total score is selected; if tied, a random choice is made.

**K7 — Hard:**  
- **Scheduling**: Node has 4 GiB = 4096 Mi. Already requested = 3500 Mi. Requested memory for the new pod = 256 Mi → total = 3756 Mi ≤ 4096 Mi, so the scheduler **will schedule** the pod.  
- **Runtime usage**: The pod’s **request** (256 Mi) is a guarantee; the **limit** (512 Mi) caps usage. If the pod tries to consume 600 Mi, the kernel will enforce the cgroup limit and may OOM‑kill the process (or cause memory pressure). The node remains stable because the limit prevents exceeding the node’s capacity.

**K8 — Hard:**  
1. **External Load Balancer (LB)** (e.g., cloud LB) receives traffic on a public IP/port and forwards to the Ingress controller’s NodePort.  
2. **Ingress Controller (NGINX)** runs as a Deployment with a **Service of type NodePort** (or LoadBalancer). It watches the **Ingress** resource.  
3. **Ingress Resource** defines rules (host, path) → NGINX builds an `nginx.conf` that maps those rules to backend **Services**.  
4. **Service (type ClusterIP)** for the target app exposes a stable virtual IP.  
5. **Endpoints** object lists the IPs of all pods selected by the Service’s selector.  
6. **kube-proxy** (or IPVS) on each node programs **iptables** (or IPVS) rules that translate the Service IP to the actual pod IPs, performing load‑balancing.  
7. The request finally reaches the **application pod** via its IP.

**K9 — Medium:**  
- **NetworkPolicy**: Defines rules (ingress/egress) that filter traffic to/from pods based on labels, namespace, and IP blocks.  
- **Default behavior** (no NetworkPolicy): **Allow all** traffic to/from pods in the namespace.  
- **When applied**: Only traffic matching the policy’s selectors is permitted; all other traffic is dropped. This isolates services and enforces zero‑trust networking.

**K10 — Medium:**  
- **RollingUpdate**: Gradually replaces old pods with new ones, maintaining a configurable maxUnavailable/maxSurge. Ideal for most stateless apps.  
- **Recreate**: Terminates all old pods **before** creating new ones. Useful when:  
  - The app cannot handle two versions simultaneously (e.g., database migrations that break backward compatibility).  
  - You need a clean, atomic switch with zero overlap.  
  - The deployment is very short‑lived or has strict consistency requirements.

**K11 — Easy:**  
A **namespace** is a virtual cluster that provides scope for names (pods, Services, etc.). Default namespaces in a fresh cluster: `default`, `kube-system`, `kube-public`, and often `kube-node-lease` (for node heartbeats).

**K12 — Easy:**  
`kubectl describe pod <name>` shows:  
1. **Events** (creation, errors, restarts).  
2. **Container state** details (waiting, running, terminated with exit codes).  
3. **Mounted volumes** and their source/paths.  
4. **Node conditions** and resource requests/limits.  
5. **QoS class** (Guaranteed, Burstable, BestEffort).  
These are not displayed by `kubectl get pod`, which only shows a concise status line.

**K13 — Easy:**  
A **ConfigMap** stores non‑confidential key‑value pairs. Pods can consume it via:  
- **Environment variables**: `envFrom` or `env` referencing the ConfigMap.  
- **Command-line arguments**: using the same syntax as env vars.  
- **Mounted files**: as a volume, where each key becomes a file in the directory.  

**K14 — Easy:**  
- **ClusterIP**: Exposes the Service only inside the cluster (default).  
- **NodePort**: Allocates a high‑numbered port on every node; reachable from outside via `<NodeIP>:<NodePort>`.  
- **LoadBalancer**: Requests an external cloud LB; provides a public IP that forwards to NodePorts.  

**K15 — Easy:**  
A **DaemonSet** ensures exactly one pod runs on **every** (or selected) node, typically for system daemons (logging, monitoring, network plugins). Use a DaemonSet instead of a Deployment when you need a per‑node presence, whereas Deployments manage scalable, stateless workloads without node‑level guarantees.

**K16 — Medium:**  
- **Taints** repel pods: a node adds a taint; only pods with matching **tolerations** can schedule there.  
- **Tolerations** allow pods to ignore specific taints (e.g., `key: "critical"` with `operator: "Exists"`).  

**Difference from node affinity**:  
- **Affinity** is **attractive** (prefers nodes with certain labels).  
- **Taints/Tolerations** are **repulsive** (exclude pods unless they explicitly tolerate).  

**Practical use cases**:  
- **Taint**: Mark a node as “dedicated for GPU workloads” (`taint key=dedicated value=GPU toleration`). Only GPU pods tolerate it.  
- **Node affinity**: Schedule a stateful app to nodes in a specific zone (`nodeAffinity requiredDuringSchedulingIgnoredDuringExecution`).

**K17 — Medium:**  
A **Kubernetes Operator** is a custom controller that extends the Kubernetes API with domain‑specific resources (CRDs). It watches custom objects and performs complex, application‑level logic (e.g., backups, scaling, configuration).  

**Difference from a standard controller**:  
- Standard controllers (e.g., Deployment controller) manage built‑in resources.  
- Operators manage **user‑defined** resources and embed operational knowledge (lifecycle, upgrades, monitoring).  

**Problems solved**:  
- Automate complex stateful workloads (databases, distributed caches).  
- Encode operational best practices (rolling upgrades, failover).  
- Provide self‑service APIs for SaaS offerings.

**K18 — Hard:**  
- **etcd** uses **Raft** consensus, requiring a **majority (quorum)** of nodes to agree on log entries. Writes are durable only after replication to a majority.  
- **Quorum loss** (e.g., 2/3 nodes down in a 3‑node cluster) means the cluster cannot accept new writes; existing reads may continue from cached data but eventually stall.  
- **Recovery**:  
  1. **Do NOT** start a new etcd instance with the old data; it would cause split‑brain.  
  2. **Restore from a recent backup** (etcd snapshots) onto a fresh set of nodes.  
  3. **Re‑initialize** the cluster with `etcd --initial-cluster` specifying the new member IDs.  
  4. **Re‑join** any surviving nodes if they can be recovered; otherwise replace them.  

If 2 out of 3 nodes are permanently lost, you must **re‑create the cluster** from backup, as the remaining node cannot form quorum.

**K19 — Hard:**  
**RBAC** (Role‑Based Access Control) ties **subjects** (users, groups, service accounts) to **permissions** via Roles/ClusterRoles and Bindings.  

- **Role**: Namespace‑scoped; defines verbs (get, list, create, etc.) on resources.  
- **ClusterRole**: Cluster‑wide; same structure but applies everywhere.  
- **RoleBinding**: Binds a Role to subjects within a namespace.  
- **ClusterRoleBinding**: Binds a ClusterRole to subjects cluster‑wide.  

**RBAC manifests for read‑only pod & log access in `my-ns`:**  

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-ns
  name: pod-log-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: my-ns
  name: pod-log-reader-binding
subjects:
- kind: ServiceAccount
  name: my-sa
  namespace: my-ns
roleRef:
  kind: Role
  name: pod-log-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:**  
**ndots** in `/etc/resolv.conf` defines how many dots a name must have before the resolver tries absolute lookup. Inside pods, the default `ndots:5` often causes short hostnames (e.g., `my-service`) to be treated as **relative** names, triggering a search suffix (the cluster domain `cluster.local`). The resolver appends the suffix, queries, gets NXDOMAIN, then retries with additional suffixes → **excessive DNS latency** (>5 s).  

**Fix with `dnsConfig`**:  

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
  - name: app
    image: myimage
  dnsConfig:
    options:
    - name: ndots
      value: "2"   # treat names with >=2 dots as absolute
    nameservers:
    - 10.0.0.10
```

Setting `ndots:2` reduces unnecessary suffix searches, speeding up resolution.

**Development**

**D1 — Easy:**  
- **git merge**: Creates a new merge commit that combines the histories of two branches. The original branch history remains intact.  
- **git rebase**: Rewrites history by moving the current branch’s commits onto the tip of the target branch, creating a linear sequence.  

**Avoid rebasing** when the branch is **public/shared** (already pushed) because it changes commit IDs, causing divergence for collaborators.

**D2 — Easy:**  
- **TCP** (Transmission Control Protocol): Connection‑oriented, reliable, ordered delivery, flow control, congestion control.  
  - Protocols: HTTP, FTP, SSH.  
- **UDP** (User Datagram Protocol): Connectionless, best‑effort, no guarantee of order or delivery.  
  - Protocols: DNS (queries), DHCP, RTP (media streaming).  

**D3 — Medium:**  
A **race condition** occurs when two or more threads/processes access shared data concurrently, and the final outcome depends on the non‑deterministic timing of their execution.  

**Example (Python)**:  

```python
import threading

balance = 0
def deposit():
    global balance
    for _ in range(1000):
        balance += 1

threads = [threading.Thread(target=deposit) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(balance)   # Often < 10_000 due to lost updates
```

Without synchronization (locks), increments interleave, causing lost updates.

**D4 — Medium:**  
- **Symmetric encryption**: Same key used for encryption and decryption (e.g., AES). Fast, used for bulk data.  
- **Asymmetric encryption**: Public/private key pair; public key encrypts, private key decrypts (e.g., RSA, ECC). Used for key exchange and digital signatures.  

**TLS handshake**:  
1. Client → Server: `ClientHello` (supported ciphers).  
2. Server → Client: `ServerHello`, server cert (public key), `ServerKeyExchange` (often RSA or ECC key exchange).  
3. Client verifies cert, generates **pre‑master secret**, encrypts with server’s public key, sends it.  
4. Both derive the same **session keys** (symmetric) using a key‑derivation function.  
5. Subsequent data is encrypted with those symmetric keys (e.g., AES‑GCM).

**D5 — Medium:**  
A **container image layer** is a read‑only filesystem snapshot representing changes (e.g., adding a file, installing a package). Images are built from a series of layers stacked on a base image.  

**Layer caching**: Docker rebuilds only layers that changed since the last build, speeding up image creation. Best practices:  
- Put commands that change often (source code) **last**.  
- Group related RUN instructions (e.g., install multiple packages in one `RUN`).  
- Use multi‑stage builds to discard unnecessary layers.

**D6 — Medium:** (4 checks, ordered)  
1. **Pod health**: `kubectl get pods` → look for CrashLoopBackOff, OOMKilled, or failing readiness probes.  
2. **Service/Endpoints**: Verify the Service has **Endpoints** (pods are registered). `kubectl get ep <svc>`; missing endpoints → traffic can’t reach pods.  
3. **Resource saturation**: Check node CPU/memory pressure (`kubectl top node/pod`). OOM or CPU throttling can cause 503s.  
4. **Application logs**: `kubectl logs <pod>` for error messages (e.g., database connection failures, timeouts).  
5. **Ingress/LoadBalancer**: Confirm the external LB/Ingress is healthy and forwarding to the correct NodePort.  

**D7 — Hard:**  
**CAP Theorem**: In a distributed system, you can guarantee at most two of:  
- **Consistency (C)**: All nodes see the same data at the same time.  
- **Availability (A)**: Every request receives a (non‑error) response.  
- **Partition Tolerance (P)**: The system continues to operate despite network partitions.  

**CP example**: **Cassandra** (tunable consistency) prefers consistency and partition tolerance; during a partition, it may reject writes to maintain consistency.  

**AP example**: **Amazon DynamoDB** (eventual consistency) guarantees availability and partition tolerance; during a partition, it accepts writes and resolves conflicts later.

**D8 — Medium:**  
- **Horizontal scaling**: Adding more instances (pods, VMs) of an application, spreading load. Requires statelessness or external state store. Enabled by container orchestration, service discovery, and load balancers.  
- **Vertical scaling**: Increasing resources (CPU, RAM) of an existing instance. Limited by hardware and often requires downtime.  

**Architectural patterns for horizontal scaling**: microservices, stateless services, API gateways, distributed caches, sharding, and using Kubernetes Deployments/StatefulSets.

**D9 — Easy:**  
An **environment variable** is a key‑value pair accessible by processes. To persist across shell sessions on Linux, add the export line to a profile file (e.g., `~/.bashrc`, `~/.profile`, or `/etc/environment`):  

```bash
export MY_VAR="value"
```

Then source the file or restart the shell.

**D10 — Easy:**  
- **JSON** (JavaScript Object Notation): Lightweight, text‑based, strictly hierarchical (objects/arrays). Advantages: simplicity, wide language support, easy to parse.  
- **YAML** (YAML Ain’t Markup Language): Superset of JSON, supports comments, more human‑readable with indentation, and richer types (e.g., anchors, multi‑document). Advantages: readability for config files, comments, concise representation of complex structures.  

**D11 — Easy:**  
A **REST API** uses HTTP methods to perform CRUD operations on resources.  

- **GET**: Retrieve a resource (idempotent, safe).  
- **POST**: Create a new resource (not idempotent).  
- **PUT**: Replace an existing resource entirely (idempotent).  
- **DELETE**: Remove a resource (idempotent).  

**D12 — Easy:**  
**Version pinning** locks dependencies to specific versions (e.g., `package==1.2.3`). It ensures builds are reproducible, avoids surprise breakage from transitive updates, and simplifies debugging by providing a known dependency graph.

**D13 — Easy:**  
- **Compiled language**: Source code translated to machine code before execution (e.g., C, Go, Rust).  
- **Interpreted language**: Source code executed directly by an interpreter (e.g., Python, Ruby, JavaScript (Node)).  

**D14 — Medium:**  
A **reverse proxy** sits in front of servers, forwarding client requests to backend services, often adding features like load balancing, SSL termination, caching.  

A **forward proxy** sits in front of clients, forwarding their requests to the internet, providing anonymity, filtering, or caching.  

**Common reverse proxies**:  
- **NGINX**: High‑performance web server, load balancer, HTTP cache. Use case: terminating TLS for microservices.  
- **HAProxy**: TCP/HTTP load balancer, ideal for high‑throughput, low‑latency routing. Use case: distributing traffic across database replicas.  

**D15 — Medium:**  
A **deadlock** occurs when a set of processes are each waiting for resources held by others, forming a circular wait. The **Coffman conditions** are:  

1. **Mutual Exclusion** – at least one resource is held in an exclusive mode.  
2. **Hold and Wait** – a process holds resources while waiting for others.  
3. **No Preemption** – resources cannot be forcibly taken.  
4. **Circular Wait** – a circular chain of processes exists, each waiting for a resource held by the next.  

All four must hold for a deadlock.

**D16 — Hard:**  
**Eventual consistency** guarantees that, given no new updates, all replicas will converge to the same value eventually.  

**Cassandra** (a Dynamo‑style system) uses **tunable consistency levels** (e.g., `ONE`, `QUORUM`, `ALL`) for reads/writes.  

- **Read‑after‑write consistency**: If a write is performed with `QUORUM` and the subsequent read also uses `QUORUM`, the read is guaranteed to see the write (because quorum intersection ensures at least one replica has both).  
- **Consistency levels**:  
  - `ANY` / `ONE`: Minimal latency, no guarantee.  
  - `TWO`, `THREE`: Higher probability.  
  - `QUORUM`: Majority of replicas (provides strong consistency).  
  - `ALL`: Full consistency (highest latency).  

**D17 — Hard:**  
**mTLS (mutual TLS)** authenticates **both** client and server using certificates.  

**Handshake steps**:  

1. **Client → Server**: `ClientHello` (supported ciphers, extensions including `status_request` for OCSP).  
2. **Server → Client**: `ServerHello`, server cert (signed by CA), `CertificateRequest` (asks client for cert).  
3. **Client → Server**: Sends its client cert, optionally `ClientKeyExchange` (e.g., ECDHE parameters).  
4. **Server** verifies client cert against its trust store; if invalid, aborts.  
5. Both derive the **pre‑master secret** via ECDHE, then symmetric session keys.  
6. `Finished` messages (MAC) confirm handshake integrity.  

**Common uses**: Service‑mesh security (Istio, Linkerd), API gateways, internal microservice communication, VPN‑less secure RPC.

**D18 — Hard:**  
A **hash table** stores key‑value pairs using a hash function to compute an index (bucket) in an underlying array.  

**Collision resolution**:  

- **Chaining**: Each bucket holds a linked list (or dynamic array) of entries that hash to the same index. Lookup traverses the list.  
- **Open addressing** (e.g., linear probing, quadratic probing, double hashing): On collision, probe subsequent buckets until an empty or matching slot is found.  

**Time complexities**:  

- **Average case** (low load factor):  
  - Insertion: O(1)  
  - Lookup: O(1)  
  - Deletion: O(1)  
- **Worst case** (high load factor or many collisions):  
  - Insertion/lookup/deletion: O(n) where n = number of elements in the chain or probe sequence.  

**D19 — Hard:**  
**Circuit Breaker** pattern monitors remote service calls; when failures exceed a threshold, it **opens** (short‑circuits) future calls, returning immediate errors or fallback responses. States:  

- **Closed**: Normal operation; calls are allowed. Failure metrics are collected.  
- **Open**: After threshold breach, subsequent calls fail fast (often with a fallback). A timeout period allows the system to recover.  
- **Half‑Open**: After timeout, a limited number of test requests are permitted. If they succeed, the breaker closes; otherwise, it reopens.  

**Relation to retries & backoff**:  
- Retries are typically **disabled** while the circuit is open to avoid hammering a failing service.  
- Exponential backoff is used for retries when the circuit is closed, preventing thundering herd.  

Together they prevent cascade failures and improve system resilience.

**D20 — Hard:**  
- **Optimistic Concurrency Control (OCC)** assumes conflicts are rare. Each transaction reads data, makes changes, and **validates** before commit (e.g., version check). If conflict detected, the transaction aborts and retries. Ideal for high‑read, low‑write workloads.  

  *Example*: In PostgreSQL, `UPDATE table SET col = ? WHERE id = ? AND version = ?` uses the version column; if rows affected = 0, a conflict occurred.  

- **Pessimistic Concurrency Control (PCC)** locks resources upfront to prevent conflicts.  

  *Example*: `SELECT * FROM table FOR UPDATE` acquires an exclusive lock; other transactions block until the lock releases.  

**When to choose**:  
- **OCC** for systems with many readers, infrequent writes (e.g., web apps, caches).  
- **PCC** for high‑contention write‑heavy scenarios where data integrity must be guaranteed without retries (e.g., financial transactions).
