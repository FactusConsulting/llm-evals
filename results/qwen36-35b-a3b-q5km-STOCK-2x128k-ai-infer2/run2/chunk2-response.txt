K1 — A **Deployment** manages stateless workloads with interchangeable, randomly named pods and supports rolling updates. A **StatefulSet** manages stateful workloads requiring stable network IDs, ordered deployment/scaling, and persistent storage tied to each pod (e.g., databases).

K2 — The Service controller populates an `Endpoints` object with pod IPs. `kube-proxy` watches this and creates iptables/IPVS rules mapping the ClusterIP:Port to the backend pod IPs:Ports. Traffic hitting the ClusterIP is load-balanced across pods via node-level routing.

K3 — A **PersistentVolume (PV)** is cluster storage provisioned statically or dynamically. A **PersistentVolumeClaim (PVC)** is a user request for storage. A **StorageClass** defines the provisioning template. A PVC binds to a PV (or triggers dynamic provisioning via a StorageClass) and mounts to pods.

K4 — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` for OOMKilled, exit codes, or failed probes. 3. Verify resource limits/requests and node capacity. 4. Check app dependencies, config mounts, and startup commands for misconfiguration.

K5 — CoreDNS provides internal DNS resolution for `svc.cluster.local` and pod FQDNs. If CoreDNS pods are down, cluster-internal service discovery fails; external DNS resolution may still work if `stubDomains` or host DNS is configured, but cross-service communication breaks.

K6 — The scheduler **filters** nodes that fail constraints (resources, taints, affinity, node selectors), then **scores** remaining nodes using priority functions. Factors: CPU/memory utilization (LeastRequested), node affinity/anti-affinity, taint tolerations, topology spread constraints, and resource pressure.

K8 — 1. External LB routes traffic to the Ingress Controller (NodePort/LoadBalancer). 2. Ingress Controller reads the Ingress resource and configures NGINX routes. 3. NGINX matches host/path and forwards to the Kubernetes Service. 4. Service routes to the `Endpoints` list (pod IPs). 5. `kube-proxy`/iptables/IPVS handles node-level routing to the pod network. 6. Pod receives the request.

K9 — A **NetworkPolicy** restricts ingress/egress traffic at the pod level. Default behavior (no policy): all traffic allowed. When applied: only traffic matching the policy's `podSelector` and `ingress`/`egress` rules is permitted; all other traffic is denied.

K10 — **RollingUpdate** gradually replaces old pods with new ones (zero downtime). **Recreate** terminates all old pods before starting new ones (downtime). Choose Recreate for stateful apps, strict sequential config updates, or when zero concurrent versions are required.

K11 — A **namespace** provides logical isolation within a cluster. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed state, events, conditions, resource usage, volume mounts, environment variables, and container statuses. `kubectl get pod` only shows basic status, age, and restart count.

K13 — A **ConfigMap** stores non-confidential configuration data. Pods consume it via: 1. Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`). 2. Volume mounts (files appear in the container filesystem).

K14 — **ClusterIP**: internal virtual IP, accessible only within the cluster. **NodePort**: exposes the service on a static port on each node's IP. **LoadBalancer**: provisions a cloud provider external LB that routes to the NodePort/ClusterIP.

K15 — A **DaemonSet** ensures one pod runs on every node (or subset via selector). Use it for node-level agents (logging, monitoring, metrics) instead of a Deployment, which would require manual pod count management.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes based on labels. Use case: Taints for dedicated GPU nodes; Node affinity for zone-specific workloads.

K17 — An **Operator** is a custom controller that manages complex stateful applications using CRDs and custom reconciliation logic. Unlike standard controllers, it encodes operational knowledge (backups, upgrades, failover) into code, reducing manual intervention.

K18 — etcd uses a **linearizable** consistency model via Raft. If quorum is lost, the cluster becomes read-only/unwritable. Recovery from 2/3 loss: run `etcdctl snapshot restore` on the remaining node, or use `--force-new-cluster` to bootstrap a new 1-node cluster and restore data.

K19 — **Role/ClusterRole** define permissions (verbs/resources). **RoleBinding/ClusterRoleBinding** bind roles to users/groups/serviceaccounts.
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` causes the pod to query `svc.cluster.local`, `cluster.local`, `.local`, `.`, etc. before upstream DNS, causing 5+ queries per lookup. Fix: set `dnsConfig: { options: [{ name: "ndots", value: "2" }] }` in the pod spec, or use FQDNs with a trailing dot.

D1 — **Merge** preserves commit history with a merge commit. **Rebase** rewrites history into a linear timeline. Avoid rebasing on shared/public branches or after pushing to remote to prevent history conflicts.

D2 — **TCP** is connection-oriented, reliable, ordered, and flow-controlled. **UDP** is connectionless, unreliable, and low-latency. TCP: HTTP, SSH. UDP: DNS, VoIP, video streaming.

D3 — A **race condition** occurs when concurrent threads/processes access shared state without synchronization, causing unpredictable results. Example: two threads incrementing a shared counter without a mutex, resulting in lost updates.

D4 — **Symmetric** encryption uses one key for encrypt/decrypt (fast). **Asymmetric** uses public/private key pairs (secure key exchange). TLS uses asymmetric encryption for the handshake/key exchange, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates an immutable **image layer**. Layer caching reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., install dependencies before copying source code) to maximize cache hits.

D6 — 1. Check upstream service logs/metrics for errors. 2. Verify resource limits (CPU throttling/OOMKilled). 3. Inspect readiness probes and endpoint health. 4. Check network/LB timeouts, connection limits, or rate limiting.

D7 — **CAP theorem** states a distributed system can only guarantee two of: Consistency, Availability, Partition tolerance. CP example: etcd/ZooKeeper (prioritizes data accuracy over availability during partitions). AP example: Cassandra/DynamoDB (prioritizes availability, accepts eventual consistency).

D8 — **Horizontal scaling** adds more nodes/instances; **vertical scaling** increases resources (CPU/RAM) of existing nodes. Horizontal scaling requires stateless services, distributed databases, message queues, and container orchestration.

D9 — An **environment variable** is a dynamic value affecting process behavior. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON** is strict, machine-friendly, and universally parsed. **YAML** is human-readable, indentation-based, and supports comments. JSON advantage: strict syntax, no parsing ambiguity. YAML advantage: readability, less verbose, easier for config files.

D11 — A **REST API** is an architectural style using HTTP methods. **GET**: retrieve resources. **POST**: create new resources. **PUT**: replace/update existing resources. **DELETE**: remove resources.

D12 — **Version pinning** locks dependencies to exact versions (e.g., `package@1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes, and simplifies debugging by eliminating environment drift.

D13 — **Compiled** languages translate source to machine code before execution (C, Rust). **Interpreted** languages execute source line-by-line at runtime (Python, JavaScript). Note: many modern languages use JIT/hybrid compilation.

D14 — A **reverse proxy** sits in front of servers, routing client requests to backends (Nginx, HAProxy). Use case: load balancing, SSL termination. A **forward proxy** sits in front of clients, routing outbound requests. Use case: corporate content filtering, caching.

D15 — A **deadlock** occurs when processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait.

D16 — **Eventual consistency** guarantees all replicas converge if no new updates. Cassandra uses vector clocks and tunable consistency levels (ONE, QUORUM, ALL, LOCAL_QUORUM). Read-after-write consistency is enforced by requiring QUORUM for both reads and writes, plus read repair/hinted handoff.

D17 — **mTLS** authenticates both client and server via certificates. Handshake: ClientHello → ServerHello + cert → Client verifies server cert → Server requests client cert → Client verifies server → encrypted channel established. Used in: service meshes (Istio), zero-trust microservices, internal API gateways.

D18 — A **hash table** maps keys to values via a hash function. Collision resolution: **chaining** (linked lists per bucket) or **open addressing** (probing: linear/quadratic/double hash). Avg time complexity: O(1). Worst case: O(n) when all keys collide.

D19 — A **circuit breaker** prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal), **Open** (fail fast, trip after error threshold), **Half-open** (test with limited requests). Relates to retries: circuit breakers should wrap retry logic to avoid hammering a failing service; exponential backoff reduces load during recovery.

D20 — **Optimistic** concurrency assumes no conflicts, checks at commit (row versioning/timestamps). **Pessimistic** locks resources during read/write (`SELECT FOR UPDATE`, row locks). Choose optimistic for high read/low write contention; pessimistic for high write contention or critical transactions requiring strict isolation.
