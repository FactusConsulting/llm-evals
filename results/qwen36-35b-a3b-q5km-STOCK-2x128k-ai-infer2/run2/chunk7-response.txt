AA1 — A monolith is a single deployable unit with shared codebase, process, and database. Microservices decompose functionality into independently deployable, loosely coupled services with separate databases/processes. Microservices introduce: (1) network latency and partial failure handling, (2) distributed data consistency challenges, and (3) operational complexity (orchestration, CI/CD pipelines, observability overhead).

AA2 — Synchronous communication blocks the caller until a response is received, enabling real-time interaction but creating tight coupling. Example: REST/gRPC. Asynchronous communication decouples sender and receiver; messages are processed later, improving resilience and throughput. Example: RabbitMQ or Kafka.

AA3 — A reverse proxy routes traffic, terminates TLS, and provides basic load balancing/caching. An API Gateway adds API-specific capabilities: authentication, rate limiting, request/response transformation, versioning, and analytics. An API Gateway can replace a reverse proxy functionally, but in practice they're layered: reverse proxies handle low-level routing/SSL efficiently, while gateways sit above for business logic.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a step fails. Choreography uses events to trigger the next step (decentralized, simpler for linear flows, harder to debug). Orchestration uses a central coordinator sending commands (centralized, easier to monitor/modify, better for complex branching).

AA5 — CQRS separates read (query) and write (command) models. Event Sourcing stores state changes as an immutable sequence of events. They're paired because events naturally drive command processing and can rebuild read models. This solves auditability, temporal queries, complex domain modeling, and independent scaling of reads/writes—problems traditional CRUD handles poorly due to tight coupling and lack of historical state.

AA6 — The Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (fail fast), Half-Open (probe recovery). Unlike retry+backoff (which attempts immediate recovery), the circuit breaker halts traffic to prevent overload. Use both: retry for transient glitches, circuit breaker when failure patterns indicate systemic degradation.

AA7 — 
1. Shared DB/schema: Lowest cost, highest noisy-neighbor risk, weakest security (relies on app/row-level filters), lowest operational complexity.
2. Shared DB/separate schema: Moderate cost, better isolation/security, moderate noisy-neighbor risk, moderate complexity (schema migrations per tenant).
3. Separate DB: Highest cost, strongest security/isolation, zero noisy-neighbor risk, highest complexity (backup/migration/monitoring overhead per tenant).

AA8 — Eventual consistency allows temporary divergence; strong consistency guarantees immediate visibility of updates. For zero oversell: use strong consistency. Data store: Strong-consistency distributed DB (CockroachDB, Spanner) or partitioned PostgreSQL with row-level locking. Patterns: Optimistic concurrency (version columns), distributed locks (Redlock), queue-based inventory reservation with idempotent processing, and SKU/warehouse partitioning to limit lock contention at scale.

AA9 — A sidecar proxy co-locates with a service to intercept all inbound/outbound traffic. In Istio, Envoy (data plane) handles routing, mTLS, retries, and metrics, while Istiod (control plane) pushes configuration. mTLS solves: transparent encryption without app code changes, mutual authentication, automated certificate rotation, and protection against internal threats—unlike app-level TLS, which requires manual implementation and lacks client authentication.

AA10 — The Strangler Fig pattern incrementally replaces functionality by routing traffic to new services while keeping the legacy system intact. Strategy: Place an API gateway in front of the monolith. Identify a bounded context (e.g., auth, billing). Build the .NET 8 microservice. Route specific paths/headers to the new service via the gateway. Implement dual-write or CDC for DB sync. Use feature flags, monitor metrics, and decommission monolith endpoints iteratively until fully migrated.

AA11 — 12-Factor App is a methodology for cloud-native apps. Six factors: (1) Codebase (1 deploys to many envs) ensures consistency. (2) Dependencies (explicit declaration) enables reproducible builds. (3) Config (env vars) keeps code env-agnostic and secure. (4) Backing services (treat as attached resources) allows easy swapping. (5) Build/release/deploy (strict separation) enables immutable artifacts. (6) Processes (stateless) allows horizontal scaling. They matter for portability, resilience, and automated cloud deployments.

AA12 — 
- Coupling: Event = loose; Request = tight.
- Scalability: Event = high throughput, burst handling; Request = predictable, request-rate limited.
- Debugging: Event = complex tracing, replay needed; Request = straightforward logs.
- Ordering: Event = partition-level guaranteed; Request = per-request.
- Failure: Event = DLQs, retries, idempotency; Request = timeouts, retries, circuit breakers.
Choose Event for async workflows, high throughput, decoupled domains, audit trails. Choose Request for real-time, synchronous needs, simple CRUD, strict per-call consistency.

AA13 — A load balancer distributes traffic across backend servers. Layer 4 balances by IP/port (fast, no content inspection). Layer 7 balances by content (URL, headers, cookies, SSL). Layer 7 is required for SNI-based SSL termination, path-based routing (`/api` vs `/static`), or cookie-based session affinity.

AA14 — Message queues (RabbitMQ) use point-to-point/pub-sub, consume/remove messages, and support complex routing/exchanges. Log-based brokers (Kafka) are append-only, retain messages, support replay, and partition for high throughput. Pick RabbitMQ for task queues, strict delivery, and routing complexity. Pick Kafka for event streaming, audit logs, real-time analytics, and replay needs.

AA15 — Containers use OS-level virtualization, sharing the host kernel, while VMs use hardware virtualization with full guest OSes. Containers are lighter, start faster, and have lower overhead. They're popular for microservices because they ensure environment consistency, enable immutable deployments, and integrate seamlessly with orchestration platforms like Kubernetes.

AA16 — Stateless services store no session data locally; each request is independent. Stateful services maintain local session/context. Stateless services scale horizontally easily because instances can be added/removed without session migration or loss. Examples: Stateless: Nginx, REST API. Stateful: Redis, PostgreSQL, WebSocket server.

AA17 — An ORM maps objects to database tables. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs accelerate development, provide abstraction, and reduce SQL injection risk, but can generate inefficient queries and complicate performance tuning. Raw SQL offers full control and optimal performance but requires more code, manual mapping, and careful security handling.

AA18 — The Bulkhead pattern isolates resources so a failure in one component doesn't exhaust shared resources (threads, connections, memory). In microservices, it prevents cascading failures. Implementation: Assign separate thread pools/connection pools per downstream service, or deploy critical vs non-critical services on separate Kubernetes node pools with resource quotas and network policies.

AA19 — OT requires a central server to transform concurrent operations, guaranteeing strong consistency but incurring higher latency, complex algorithms, and poor offline support. CRDTs are data structures that mathematically guarantee convergence without coordination, offering eventual consistency, low latency, simpler conflict resolution, and excellent offline support. Choose CRDTs for offline editing; they allow local modifications that merge deterministically when back online.

AA20 — Challenges include polyglot instrumentation overhead and data volume. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject/extract trace IDs across HTTP/gRPC. Sampling: head-based (random, cheap, loses rare traces) vs tail-based (collects all, samples post-execution, accurate but high overhead). Storage/query: Jaeger/Tempo index traces by ID/service/latency for UI/API search. For Kafka: producers inject trace context into message headers, consumers extract and continue the trace. Use tail-based sampling with consumer groups and ensure idempotent processing to maintain continuity.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and security. Examples: VMware ESXi, Proxmox VE (KVM), Hyper-V, Xen. Type 2 (hosted) hypervisors run as applications on a host OS, offering ease of use but higher overhead. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block storage, presenting virtual disks to servers for high performance and low latency. Protocols: Fibre Channel, iSCSI. NAS provides file storage, sharing files over the network. Protocols: NFS, SMB/CIFS. Use SAN for databases and VMs. Use NAS for file shares, backups, and home directories.

OP3 — 3-tier architecture: Access (edge) → Distribution (policy/aggregation) → Core (backbone). It's hierarchical but suffers from spine bottlenecks and non-deterministic latency for east-west traffic. Leaf-spine is preferred because it's a full-mesh, equal-cost multipath design providing deterministic low latency, predictable bandwidth, and linear scalability, solving the distribution layer bottleneck and poor east-west performance.

OP4 — Use 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing (STONITH via iDRAC/IPMI) isolates failed nodes. Shared storage: Ceph (recommended for redundancy/performance), iSCSI, or NFS. On node failure: quorum is maintained, VMs migrate/restart on survivors, fencing powers off the failed node, and storage remains accessible via surviving OSDs.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte tag to Ethernet frames containing the VLAN ID. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10` (repeat for 20, 30). Assign IPs, configure bridges/routing, and enable `802.1q` kernel module.

OP6 — RAID 1: Mirror, 50% capacity, 1 drive fault tolerance. RAID 5: Striping+parity, N-1 capacity, 1 drive fault tolerance, write penalty. RAID 6: Striping+double parity, N-2 capacity, 2 drive fault tolerance. RAID 10: Mirror+stripe, 50% capacity, 2 drive fault tolerance, high IOPS. RAID Z2: Double parity, N-2 capacity, checksumming, snapshots. Choice: RAID 10 for raw database IOPS/performance, or ZFS Z2 for data integrity, flexibility, and modern storage features. I'd choose ZFS Z2 for production databases due to checksumming and snapshot capabilities.

OP7 — Recursive resolvers: Internal DNS servers (Windows DNS/BIND) for clients. Authoritative: Host internal AD zones and external public zones. Forwarders: Point to ISP/cloud DNS for external queries. Conditional forwarding: Route internal AD zones to internal DNS, external to forwarders. Split-horizon: Internal DNS returns private IPs, external returns public IPs for the same FQDN. DNSSEC: Sign external zone, publish DS record at registrar, validate recursively. Laptop mobility: Roaming clients query internal DNS via DHCP. VPN clients use split tunneling or DNS forwarding to resolve internal names; conditional forwarders ensure correct resolution regardless of location.

OP8 — PKI chain: Root CA → Subordinate CA → End-entity cert. Trust anchored in root. Internal PKI: Root CA offline (air-gapped). Subordinate CA online, issues certs. Use certificate templates for auto-enrollment (Windows AD CS). CRL/OCSP for revocation checking. Compromised subordinate: Revoke certs, issue new subordinate, minimal impact. Compromised root: Entire trust chain broken, requires rebuilding PKI, updating all trust stores, massive operational impact.

OP9 — MPLS: High cost, high reliability, low latency, complex management, secure private network. IPsec VPN: Low cost, variable reliability, higher latency, moderate management, internet-based. SD-WAN: Moderate cost, high reliability (bonding), optimized latency, centralized management, secure with encryption. WireGuard mesh: Low cost, good reliability, low latency, simple management, modern crypto, limited enterprise features. Recommendation: SD-WAN. Balances cost, provides application-aware routing (prioritizes VoIP), centralized management, and reliable failover over internet.

OP10 — iDRAC (Dell), iLO (HPE), IPMI (standard) are out-of-band management interfaces for remote server control (power, console, hardware monitoring). Critical for accessing servers when OS/network is down, enabling remote recovery and maintenance. Exposed to internet: High risk of credential stuffing, firmware exploits, unauthorized access, ransomware, or hardware manipulation. Should be on isolated management networks.

OP11 — LVM: Traditional volume manager, fixed-size volumes, snapshots consume space quickly. LVM-Thin: Overprovisions storage, space-efficient snapshots, but degrades if thin pool fills. ZFS: Integrated FS+volume manager, copy-on-write, space-efficient snapshots, checksumming, self-healing. Use LVM for legacy/simple setups. LVM-Thin for flexible provisioning. ZFS for data integrity, snapshots, and modern storage needs.

OP12 — Design: 3 sites, 2 nodes each, or 3 nodes across 2 sites with a cloud witness. Ceph CRUSH rules place OSDs across failure domains (sites). Monitors distributed across sites. Latency: <10ms ideal, up to 15ms acceptable with tuning. Split-brain: Both sites claim primary, causing data corruption. Tiebreaker: Third site or cloud witness breaks quorum deadlock. 2-site Ceph without tiebreaker is bad because network partitions cause both sites to lose quorum or both claim it, leading to split-brain and data corruption.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. Unavailable server: Client retries, may get APIPA (169.254.x.x) or fail. Expired lease Windows: Client renews at 50% (T1) and 87.5% (T2). If failed, reverts to APIPA, losing network connectivity until lease renewed or static config applied.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, monitoring, ACLs, and link aggregation. Critical for segmentation, traffic prioritization, loop prevention, and security in enterprise environments.

OP15 — NTP synchronizes clocks over networks. Critical for log correlation, security (certs, Kerberos), distributed transactions, and cluster coordination. Clock drift causes: Kerberos auth failures, split-brain in clusters, log timestamp mismatches, database replication lag/errors, and certificate validation failures.

OP16 — Physical servers: Direct hardware access, max performance. VMs: OS-level isolation, full guest OS, hardware abstraction. Containers: Process-level isolation, share host OS, lightweight. Bare metal is used for high-performance computing, low-latency trading, databases requiring direct storage access, compliance/security requirements, or when virtualization overhead is unacceptable.

OP17 — UPS: Short-term battery backup, handles outages/transients, allows graceful shutdown or generator start. Generator: Long-term fuel-based power, high capacity. Both needed: UPS bridges the gap until generator starts (10-30 sec). ATS (Automatic Transfer Switch): Detects outage, switches load to generator, switches back when utility restores.

OP18 — Active-passive: One node handles traffic, standby takes over on failure. Active-active: Both handle traffic, sync data, share load. PostgreSQL HA with Pacemaker/Corosync: Manages resources. Virtual IP floats between nodes. STONITH (fencing) isolates failed nodes. PostgreSQL runs on VIP using streaming replication. On failure, Pacemaker stops PG on primary, promotes standby, moves VIP, starts PG. Fencing prevents split-brain.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO: Define acceptable data loss and downtime. Types: Full (baseline), Incremental (changes since last), Differential (changes since last full). Deduplication: Reduces storage, improves backup window. Media: Disk for fast restore, tape/cloud for cost/offsite. Immutable: WORM storage, ransomware protection. Testing: Regular restore drills, verify integrity, measure RTO/RPO. Backup vs DR: Backup = data protection. DR = comprehensive strategy (infrastructure, processes, failover sites) to restore operations after disaster.

OP20 — 802.1X: Port-based NAC. Supplicant (client), Authenticator (switch/AP), Auth Server (RADIUS). EAP-TLS: Certificate-based, mutual auth, highly secure. PEAP: Username/password with TLS tunnel, easier deployment, less secure. RADIUS: Centralized auth/accounting/authorization. Dynamic VLAN: Auth server returns VLAN ID, switch assigns port. Failed auth: Port stays unauthorized, blocks traffic, may allow limited NAC guest access. MAB: Switch uses device MAC as credentials, queries RADIUS. Fallback for IoT/printers lacking 802.1X supplicant.
