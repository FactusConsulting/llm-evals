CL1 — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, runtime, data, and apps. Example: AWS EC2. PaaS provides managed runtime, middleware, and OS; you manage apps and data. Example: Google App Engine. SaaS provides fully managed applications; you manage only user access and data. Example: AWS WorkSpaces.

CL2 — The Shared Responsibility Model divides security: provider secures the cloud infrastructure (physical, global network, hypervisor, managed service components); customer secures what they put in it. IaaS VM: Provider = physical, hypervisor, host OS. Customer = guest OS, patches, network config, data, IAM. Managed K8s: Provider = control plane, node OS, API server. Customer = worker node hardening, pod security, network policies, app code, secrets. SaaS (M365): Provider = app, infra, compliance, patching. Customer = user accounts, data classification, access policies, MFA, DLP.

CL3 — VPC: Isolated virtual network. Subnet: IP range within a VPC, tied to an AZ. Security Group (SG): Stateful firewall at instance/pod level; only allow rules, automatically permits return traffic. NACL: Stateless firewall at subnet level; requires explicit allow/deny for both inbound and outbound. Layering: Traffic hits NACL first (subnet boundary), then SG (instance boundary), then workload. Stateful (SG) tracks connection state; stateless (NACL) evaluates each packet independently.

CL4 — Landing zone: Pre-configured, secure multi-account foundation with networking, identity, logging, and guardrails. OUs: Logical grouping (e.g., Sandbox, Dev, Prod, Shared Services). Guardrails: SCPs/Azure Policy enforcing compliance, region restrictions, encryption mandates. Shared Networking: Transit Gateway (AWS) / Hub-and-Spoke (Azure) for centralized inter-VPC/VNet peering and on-prem connectivity. Centralized Logging: Dedicated logging account/service aggregating metrics/logs with strict access controls. Single-account problems: Large blast radius, permission sprawl, billing opacity, compliance violations, deployment bottlenecks, lack of environment isolation.

CL5 — IaC: Managing infrastructure via version-controlled, machine-readable definitions. Terraform/OpenTofu: Declarative, HCL, provider-agnostic, massive ecosystem. Best for multi-cloud, complex state, team collaboration. Pulumi: Imperative/Declarative, general-purpose languages (TS, Python, Go). Best for developers, complex logic, dynamic provisioning. CloudFormation/Bicep: AWS-native, declarative. Bicep improves readability. Best for AWS-only shops, tight integration. Crossplane: K8s-native IaC; manages cloud resources as CRDs. Best for GitOps/K8s-centric teams, unified control plane.

CL6 — HPA: Scales pods based on CPU/memory/custom metrics. Reactive, steady-state. VPA: Adjusts pod resource requests/limits; doesn't change replica count. Cluster Autoscaler: Adds/removes nodes based on unschedulable pods. KEDA: Event-driven scaling based on external triggers (queues, Kafka, HTTP). Use KEDA over HPA when scaling must respond to event backlog or external workload bursts rather than internal resource utilization.

CL7 — RPO/RTO: Define by business impact. Active-Active: Both regions serve traffic; lowest RPO/RTO, highest cost/complexity. Active-Passive: One serves, one standby; higher RPO/RTO, lower cost. DB Replication: Sync (strong consistency, higher latency, limits region distance) vs Async (lower latency, potential data loss on failover). DNS Failover: Route53/Traffic Manager health checks route traffic to healthy region. State Management: Externalize state (S3, DynamoDB, managed DB); avoid local disk state. Cost: Active-active doubles infra + data transfer; active-passive saves cost but requires regular failover testing. Pilot Light: Core infra running (DB, minimal compute), scaled up on failover. Warm Standby: Scaled-down but fully functional environment. Multi-site Active-Active: Fully operational in both, load balanced.

CL8 — GitOps: Git as single source of truth; declarative state; automated sync via operators. ArgoCD: Push/pull hybrid, UI-heavy, app-of-apps pattern, strong UI/audit. FluxCD: Git-native, pull-only, tightly integrated with GitHub/GitLab, CLI/CI-focused. Secrets: Sealed Secrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from AWS Secrets Manager/Vault), HashiCorp Vault (dynamic secrets, auth). Drift: Operator detects drift, reconciles back to Git state. Manual changes are overwritten; Git history provides audit trail.

CL9 — StatefulSet: Stable network ID, ordered deployment/termination, stable storage. PV/PVC with local storage: `local` storageClass, `volumeBindingMode: WaitForFirstConsumer` for node affinity. Headless Service: `clusterIP: None` enables direct pod DNS resolution. Init Containers: Pre-load config, check dependencies, set permissions before main app. ConfigMaps as volume mounts: Mount config files at specific paths; use `subPath` if needed. PDB: `minAvailable` or `maxUnavailable` prevents voluntary disruptions from taking down the app. Architecture: StatefulSet + headless svc + local PV/PVC + init containers + configMap volumes + PDB.

CL10 — Service Account: K8s native identity for pods; no cloud IAM binding by default. Workload Identity (GCP): Maps K8s SA to GCP IAM SA via OIDC. IRSA (AWS): Maps K8s SA to AWS IAM role via OIDC provider. Mounting credentials: Bad practice; long-lived, violates least privilege, risk of leakage, hard to rotate, breaks audit trails. Federation solves this: OIDC tokens exchanged for short-lived cloud credentials at runtime. No secrets in pods; dynamic, scoped, auditable.

CL11 — Object (S3/Blob): Unstructured, HTTP API, flat namespace, high durability (11 9s), eventual consistency. Use for backups, media, data lakes. Block (EBS/Managed Disk): Low-latency, mounted as disk, random read/write. Use for OS, databases, VMs. Durability tied to AZ; multi-AZ adds redundancy. File (EFS/Azure Files): NFS/SMB, hierarchical, shared access, POSIX/Windows compliant. Use for shared configs, home dirs, legacy apps. Regional HA but higher latency/cost than block.

CL12 — Zero-trust K8s: Network Policies (default deny, explicit allow). Service Mesh (mTLS) for encrypted service-to-service communication and policy enforcement. Pod Identity (IRSA/Workload Identity) for cloud access. Admission Controllers (OPA/Kyverno) enforce policies at admission (no privileged pods, required labels). Image Signing/Verification (Cosign/Notary) rejects unsigned images. Runtime Security (Falco) detects anomalous behavior. Secrets Management (External Secrets/Vault) avoids env vars/plain ConfigMaps. vs Perimeter: Perimeter trusts internal traffic; zero-trust verifies every request, assumes breach, micro-segments, least privilege, continuous validation.

CL13 — CDN: Distributed edge cache network that proxies content closer to users. Works by fetching from origin once, caching at PoPs, serving subsequent requests from nearest edge based on TTL. Services: CloudFront, Azure CDN, Fastly. Use CDN for static/dynamic content delivery, DDoS mitigation, SSL termination, global latency reduction. Direct origin only for low-traffic, highly dynamic, or compliance-restricted workloads.

CL14 — Region: Geographic area with multiple AZs. AZ: Isolated data centers within a region, independent power/cooling/networking. Multi-AZ deployment protects against single data center failure, ensuring high availability. Zonal resources (EBS, GKE nodes) tied to one AZ. Regional resources (Load Balancers, Cloud SQL, S3) span multiple AZs for HA.

CL15 — Managed DB (RDS/Cloud SQL/Azure SQL): Fully managed relational database. Provider handles: provisioning, patching, backups, replication, failover, monitoring, storage scaling, OS/hypervisor maintenance. Customer handles: schema, queries, IAM access, parameter groups, data migration, app connectivity. Trade-off: Less control, higher cost, but drastically reduces operational overhead.

CL16 — IAM Users: Human/service identities with long-term credentials. Groups: Collections for policy assignment. Roles: Temporary credentials, assumed by users/services/workloads (best practice). Policies: JSON documents defining permissions (actions, resources, conditions). Least Privilege: Grant only necessary permissions. Apply via roles, scoped policies, conditions (IP, MFA, time), regular access reviews, and avoid wildcards.

CL17 — Serverless: Event-driven, managed compute. Pay per execution, auto-scale to zero. Lambda/Functions/Cloud Functions: AWS/Azure/GCP equivalents; similar model, different ecosystems. Cold Starts: First invocation after idle period requires container provisioning, adding latency. Matters for latency-sensitive APIs, real-time apps. Poor fit: Long-running processes, stateful apps, predictable high-throughput (reserved instances cheaper), strict compliance/network isolation needs, vendor lock-in concerns.

CL18 — Ingress Resource: Standard K8s API; requires ingress controller (NGINX, ALB). TLS termination at controller. Gateway API: Newer, more expressive; separates routing (Gateway) from backend (HTTPRoute). Better multi-team ownership, standardized TLS. Cloud LB Annotations: Directly provision cloud LB (ALB/ILB). TLS termination at cloud LB. Simpler but cloud-locked. Service Mesh Ingress: Mesh gateway handles mTLS, routing, security. TLS termination at mesh. Use Gateway API over Ingress for complex routing, multi-tenant environments, standardized TLS management, and clear separation of duties.

CL19 — Cost Optimization ($80k/mo): RI/Savings Plans: Commit 1-3yr for compute; SPs offer flexibility. Spot/Preemptible: Up to 90% savings for fault-tolerant/batch workloads. Right-sizing: Monitor utilization, downsize over-provisioned, use auto-scaling. Storage Tiering: S3 Intelligent-Tiering, Glacier for archives, delete orphaned snapshots/volumes. Idle Detection: Unattached volumes, idle LBs, unused IPs, schedule non-prod shutdowns. FinOps: Cross-functional culture, tagging strategy, budget alerts, regular reviews. Showback/Chargeback: Tag by team/project. Chargeback enforces accountability; showback drives awareness. Tools: Cost Explorer, Azure Cost Management, Kubecost/OpenCost. Processes: Monthly reviews, tagging enforcement, automated alerts, right-sizing automation.

CL20 — Multi-Cloud Strategy: Abstraction: K8s, Terraform, service mesh, API gateways. K8s runtime: EKS/AKS/GKE for consistent deployment. Terraform: Provider-agnostic IaC, portable modules. Networking: Cloud VPN, Interconnect/ExpressRoute, global LBs, DNS routing. Identity: OIDC federation, centralized IAM proxy, SSO. Trade-offs: Increased complexity, data egress costs, inconsistent features, operational overhead. Justified: Regulatory/data sovereignty, catastrophic vendor failure risk, best-of-breed services, M&A. Unnecessary: Most startups/SMBs, teams lacking multi-cloud expertise, when tightly coupled to one provider's native features.

OT1 — Purdue Model (ISA-95): Hierarchy for industrial automation. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, DCS). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations management (MES, production planning). Level 4: Business planning (ERP, finance, supply chain). Level 5: Enterprise/Corporate network (IT infrastructure).

OT2 — IT vs OT: IT focuses on confidentiality, integrity, availability (CIA); fast patching, frequent updates, user-centric. OT focuses on availability, safety, integrity (AIS); legacy systems, real-time constraints, proprietary protocols, physical consequences of failure. Standard IT patching fails in OT due to decades-old OS, lack of patching windows, updates breaking process control, and voiding safety certifications. Requires change management, testing, and maintenance windows.

OT3 — IDMZ: Segmented network between IT (L4) and OT (L0-L2). Acts as buffer. Traffic: One-way or strictly controlled bidirectional. Typically, IT pulls data from OT via DMZ (OPC UA, MQTT). OT does not initiate connections to IT. Direct L4 to L1 danger: Exposes critical control systems to internet threats, bypasses safety controls, enables lateral movement to PLCs, risk of physical damage/safety incidents.

OT4 — OT Protocols & Levels: 1. Modbus TCP: L1/L2. Simple, unencrypted, legacy PLCs. 2. OPC UA: L2/L3. Secure, platform-independent, modern standard. 3. EtherNet/IP (CIP): L1/L2. Industrial Ethernet, real-time, Allen-Bradley. 4. PROFINET: L1/L2. Siemens ecosystem, deterministic real-time Ethernet. 5. MQTT: L2/L3/L4. Lightweight publish/subscribe, edge-to-cloud telemetry.

OT5 — Data Diode vs Firewall: Data Diode: Hardware-enforced unidirectional communication. Physical limitation ensures data flows only one way. Firewall: Policy-based filtering; bidirectional, stateful inspection. Use diode when strict data exfiltration prevention is required (safety-critical, regulatory). Limitation: Cannot allow return traffic (no ACKs, commands, or telemetry back to IT). Firewalls allow controlled bidirectional traffic but are vulnerable to sophisticated attacks/exploits.

OT6 — SCADA to Cloud Flow: PLCs/RTUs -> Historian (L2) -> OPC UA Server -> Edge Gateway (protocol translation, buffering, security) -> MQTT Broker (on-prem/cloud) -> Cloud Ingestion (Kafka, IoT Core, Event Hubs) -> Analytics. Security Boundaries: IDMZ between IT/OT. Edge gateway enforces TLS/mTLS, firewall rules, data filtering. Cloud ingestion uses IAM/OIDC, WAF, DDoS protection. Historian/OPC UA secured with network segmentation and access controls.

OT7 — IEC 62443 Zones & Conduits: Zone: Logical grouping of assets with similar security requirements, defined by function, risk, and access needs. Conduit: Communication path between zones, must be secured. Model: Zone 1: Corporate/IT (L4). Zone 2: Engineering Workstations (L3). Zone 3: SCADA Servers & Historian (L2). Zone 4: PLCs & Controllers (L1). Zone 5: SIS & Safety Systems (L0/L1, isolated). Conduits: Z1-Z2 (secured VPN/mgmt), Z2-Z3 (firewall, restricted), Z3-Z4 (firewall, one-way data pull), Z4-Z5 (data diode or physical isolation).

OT8 — Segmentation Strategy: VLAN Design: Segment by function/process (e.g., VLAN 10: Line 1 PLCs, 20: Line 2, 30: HMIs, 40: SCADA, 50: Engineering). Firewall Placement: Core firewall between IT/OT (IDMZ). Edge firewall for internet. Micro-segmentation via VLANs + ACLs. Switch Architecture: Managed L3 switches, port security, 802.1X (if supported), disable unused ports. Remote Access: Jump host in IDMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, test in staging, communicate with operations.

OT9 — SIS vs BPCS & IEC 61511: BPCS: Basic Process Control System. Manages normal operations (PLCs, DCS). SIS: Safety Instrumented System. Independent system that brings process to safe state on hazardous conditions. IEC 61511: Standard for functional safety of SIS in process industries. Defines SIL requirements. Isolation: SIS must be independent to prevent common-cause failures. IT/BPCS compromise could disable safety functions. Ransomware on SIS: Could prevent safe shutdown, leading to catastrophic failure, environmental damage, or loss of life. Hence, air-gap/isolation is critical.

OT10 — PLC vs DCS vs SCADA: PLC: Programmable Logic Controller. Discrete control, fast, rugged, used for machine/line control (L1). DCS: Distributed Control System. Centralized control architecture, integrated I/O, used for continuous/process industries (L1/L2). SCADA: Supervisory Control and Data Acquisition. Software/hardware for monitoring, data logging, remote control across wide areas (L2). Coexistence: Yes. PLCs/DCS handle control, SCADA provides supervisory layer, HMIs for operators, historians for data.

OT11 — Remote Access Architecture: Jump Host: Isolated bastion in IDMZ. No direct OT access. MFA: Mandatory for all remote access. Session Recording: Audit trail for compliance/forensics. Vendor Access: Time-limited, role-based, approved tickets, just-in-time provisioning. Why RDP to HMI is unacceptable: Exposes OT directly to corporate network threats, bypasses segmentation, lacks audit controls, violates least privilege, high lateral movement risk.

OT12 — Detection & Response (Water Treatment): Network Monitoring: Passive IDS (Snort/Suricata), NetFlow, anomaly detection for OT protocols. No active scanning. Asset Inventory: Baseline known-good state, track changes, map topology. IR Steps: Contain (isolate segment via firewall/VLAN), preserve evidence, eradicate, recover, post-incident review. Coordination: Notify control room, switch to manual/local control if needed, ensure safety systems remain operational. Safe Operations: Prioritize SIS/BPCS integrity, maintain process stability, use fallback procedures. Plant Operator Role: Monitor physical parameters, execute manual overrides, verify system status, communicate with IT/OT security, ensure safety protocols.

OT13 — HMI: Human-Machine Interface. Graphical display for operators to monitor/control processes. Role: Real-time visualization, alarm management, manual overrides, trend analysis. vs Engineering Workstation: HMI is for operators (runtime). Engineering workstation is for programmers/configurers (offline/online programming, logic editing, parameter tuning).

OT14 — Historian: Time-series database optimized for high-volume process data logging. Importance: Trend analysis, compliance reporting, troubleshooting, performance optimization. Plant Historian (L2/L3): On-prem, low latency, real-time process data, direct OPC UA/Modbus integration. Enterprise Historian (L4): Aggregates plant data for business analytics, BI, supply chain, longer retention, integrates with ERP.

OT15 — Ladder Logic: Graphical programming language mimicking relay circuits. Uses rungs, contacts, coils. Execution: PLCs. Dominance: Familiar to electricians, easy to troubleshoot, deterministic execution, widely supported, legacy codebase, low learning curve for industrial workforce.

OT16 — RTU vs PLC: RTU: Remote Terminal Unit. Designed for harsh environments, long-distance communication, telemetry, SCADA integration. Often uses serial/legacy comms, ruggedized. PLC: Designed for factory automation, fast I/O, local control, Ethernet-based. RTU Deployment: Pipelines, water/wastewater distribution, wind farms, remote sites where connectivity is limited and environmental conditions are extreme.

OT17 — Analog vs Digital Signals: Analog: Continuous voltage/current (4-20mA, 0-10V). Represents variable process values. Digital: Discrete on/off or binary signals. 4-20mA vs 0-20mA: 4mA "live zero" indicates wire break/failure (0mA = fault). 0-20mA cannot distinguish between no signal and broken wire. Better noise immunity with current loops.

OT18 — OT Asset Inventory: Comprehensive list of hardware, firmware, network configs, and communication paths. Foundation: You can't secure what you don't know. Enables vulnerability management, segmentation, compliance. Tools: Passive monitoring (packet capture, protocol analyzers), active scanning (limited, risky). Active Scanning Danger: Can crash legacy devices, cause process interruptions, trigger false alarms, or be detected as attacks. Passive is preferred.

OT19 — MITRE ATT&CK for ICS: Maps adversary tactics/techniques specific to industrial control systems. Tactics & Examples: 1. Reconnaissance: Gather network topology (T1580). 2. Resource Development: Acquire exploit tools (T1583). 3. Initial Access: Spearphishing attachment (T1566). 4. Execution: System Services (T1059). 5. Persistence: Event Triggered Execution (T1546). 6. Defense Evasion: Indicator Removal (T1070). 7. Discovery: Network Service Scanning (T1046). 8. Lateral Movement: Remote Services (T1021). 9. Collection: Data from Information Repositories (T1005). 10. Impact: Inhibit System Process Control (T1489). vs Enterprise ATT&CK: ICS focuses on physical processes, safety, legacy protocols, and availability over confidentiality. Techniques target PLCs, HMIs, historians. Assessment: Map current defenses to techniques, identify gaps, prioritize controls, run tabletop exercises.

OT20 — Converged IT/OT SOC: Log Collection: Passive taps, OPC UA historians, syslog from HMIs/SCADA, network packet capture. No active agents on critical control loops. SIEM Integration: Normalize OT logs (custom parsers), correlate with IT logs, use OT-specific data models. Detection Rules: Anomaly-based (baseline deviations), protocol-specific (unexpected Modbus writes), behavioral (unusual HMI access), known IOCs. Triage: OT analysts verify process impact, IT analysts verify network/endpoint. Escalate to plant manager if safety at risk. Staffing: IT analysts (threat intel, malware), OT engineers (process knowledge, protocol expertise), SOC manager (coordination). False Positives: High in OT due to normal maintenance cycles. Mitigate with baselining, allowlisting, tuning rules, OT analyst involvement. Unauthorized Firmware on PLC: Isolate segment, verify backup/restore procedures, assess process impact, revert to known-good firmware, investigate source, update change management, enhance admission controls.
