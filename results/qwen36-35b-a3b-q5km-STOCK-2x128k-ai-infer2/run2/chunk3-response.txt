T1 — `tofu plan` calculates and displays the execution plan (dry-run) without modifying infrastructure. `tofu apply` executes that plan, creating, updating, or destroying resources.

T2 — State is a JSON file mapping configuration to real-world resources. Remote state enables team collaboration, prevents file corruption, enables state locking, and allows secure, versioned storage in cloud backends.

T3 — `count` uses integer indices (0, 1, 2), making it sensitive to list order changes. `for_each` uses maps or sets of strings keyed by stable identifiers. `for_each` is preferred when resources have unique string IDs to prevent unintended recreation during list modifications.

T4 — OpenTofu detects drift via `tofu plan`, which compares the state file to live infrastructure. On `tofu apply`, it overwrites the external change to match the configuration (unless `lifecycle { ignore_changes = [...] }` is set).

T5 —
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.key
  }
}
```

T6 — `terraform_remote_state` reads the entire state file (slow, potential security exposure). Output values expose only specific, filtered data. Recommended alternative: Use `terraform_remote_state` with explicit `outputs` filtering, or pass data via module inputs/outputs. Terraform 1.5+ also supports direct state backend reads for better performance.

T7 — `remote-exec` provisioners run asynchronously after resource creation. If the kubeconfig output depends on it, the output may be evaluated before the provisioner finishes, returning empty. Fix: Use `local-exec` to generate the kubeconfig synchronously, add `depends_on = [null_resource.kubeconfig]` to dependent resources, or write to a file and read via a `local_file` data source.

T8 — `tofu import` manually maps existing infrastructure to state. Limitations: requires manual schema mapping, doesn't generate config, and is error-prone. The `import` block (1.5+) allows declarative imports in config, supports multiple resources, provides better error handling, and integrates seamlessly with `tofu plan`.

T9 — A `variable` is an input parameter passed into a module/root. An `output` exposes a computed value from a module/root to other modules. Inputs flow in; outputs flow out.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a platform (AWS, K8s, etc.). Without `tofu init`, providers aren't downloaded or initialized, causing `tofu plan/apply` to fail with "provider not found" errors.

T11 — `.terraform.lock.hcl` pins provider versions and cryptographic checksums. It should be committed to VCS to ensure reproducible builds, prevent supply-chain attacks, and guarantee consistent environments across teams.

T12 — `tofu destroy` deletes all resources managed by the current state. Target a single resource: `tofu destroy -target=resource_type.resource_name`.

T13 — A data source reads existing infrastructure or external data without managing it. Example: Using `data "aws_ami"` to fetch the latest Ubuntu AMI ID instead of hardcoding it or creating a new instance.

T14 — `locals` compute values within a module and aren't exposed externally. `variables` are inputs from outside. Use `locals` for intermediate calculations, string manipulation, or conditional logic to keep configuration DRY and readable.

T15 — `lifecycle` controls resource creation/deletion behavior. `create_before_destroy`: creates new before deleting old (zero-downtime). `prevent_destroy`: blocks accidental deletion (requires `-force`). `ignore_changes`: skips drift detection for specific attributes (e.g., auto-scaling tags).

T16 — The `moved` block tracks resource address changes during refactoring. It preserves state mapping, preventing recreation. Syntax: `moved { from = module.old.resource "a" to module.new.resource "a" }`.

T17 — OpenTofu builds a DAG of dependencies. Implicit dependencies are inferred from references. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, reducing parallelism. Use sparingly to avoid blocking unrelated resources.

T18 — 1. Use `tofu plan -target` for specific changes (tradeoff: limits scope). 2. Split into multiple modules/workspaces (tradeoff: increases complexity). 3. Use `data` sources to avoid state bloat (tradeoff: increases API calls). 4. Enable state locking/backend optimization (tradeoff: requires backend setup).

T19 — State locking prevents concurrent writes. If a lock isn't released (crash), use `tofu force-unlock <LOCK_ID>`. Risks: data corruption or lost changes if another apply was running concurrently.

T20 — 1. Add S3/DynamoDB backend config. 2. Run `tofu init -migrate-state`. 3. State is copied to S3, local file is removed. 4. Verify with `tofu state list` and check S3/DynamoDB. Ensure IAM permissions and handle sensitive data securely.

A1 — Playbook: YAML file defining automation steps. Role: reusable collection of tasks, handlers, vars. Task: single action/module execution.

A2 — `ansible_facts`: auto-discovered system info. Access OS family: `{{ ansible_os_family }}`.

A3 — `command`: runs command, no shell features. `shell`: runs via shell, supports pipes/redirects. `raw`: runs via SSH without Python, for bootstrapping. Use `command` for safety, `shell` for complex commands, `raw` for unmanaged hosts.

A4 — Idempotency: task produces same result if run multiple times. Idempotent: `apt: name=htop state=present`. Not: `shell: echo "hello" > /tmp/test.txt` (overwrites each time).

A5 —
```yaml
- name: Install htop based on OS
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"
- name: Install epel-release and htop on RHEL
  package:
    name: "{{ item }}"
    state: present
  loop: [epel-release, htop]
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (highest to lowest): Extra vars > Role vars > Play vars > Group vars > Host vars > Inventory vars > Role defaults.

A7 — Use `serial: 3` in playbook. Inventory: `[control_nodes]`, `[worker_nodes]`. Wait for control nodes using `wait_for: port=6443 state=started` before deploying workers.

A8 — `ansible-vault` encrypts sensitive data. Encrypt single variable: `ansible-vault encrypt_string 'value' --name 'var_name'` or wrap in `!vault` inside a vars file.

A9 — Inventory: list of hosts/groups. Static: hardcoded file. Dynamic: script/API that generates inventory on demand (e.g., cloud providers).

A10 — `ansible webservers -m shell -a "df -h"`

A11 — Handler: task that runs only when notified. Differs from regular task (runs unconditionally). Triggered via `notify: handler_name` in a task.

A12 — `ansible.cfg`: global config. Settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`.

A13 — `register`: saves task output to a variable. Use in subsequent tasks via `when: registered_var.stdout == "..."`.

A14 — `include_tasks`: runtime inclusion, supports `when`/`loop`. `import_tasks`: static inclusion at parse time, faster but no conditionals. Use `include` for dynamic, `import` for static.

A15 — Galaxy: Ansible's role/collection registry. `requirements.yml`: lists roles/collections with versions. Install: `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins: manage host communication. `ssh`: standard SSH. `local`: runs on control node. `network_cli`: for network devices (Cisco, Juniper). Use based on target OS/device type.

A17 — `delegate_to`: runs task on specified host. `run_once`: runs task once across all hosts. Example: gather facts from remote, write to localhost config file once.

A18 — 1. Increase `forks` (default 5) to 50+ (tradeoff: higher control node load). 2. Enable `pipelining` in ansible.cfg (tradeoff: requires sudo NOPASSWD). 3. Use fact caching (redis/memcached) (tradeoff: stale facts if infra changes). 4. Use Mitogen or `strategy: free` (tradeoff: Mitogen requires installation, `free` loses ordering).

A19 — `{{ }}` outputs values, `{% %}` controls flow, `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check: {{ server }}
  server {{ server }};
{% endfor %}
}
```

A20 — Use `serial: 1` or `20%`. Pre-task: disable in LB (`uri` to LB API). Post-task: health check (`uri` module). On failure: `rescue` block to re-enable LB and rollback. Use `block/rescue/always`.
