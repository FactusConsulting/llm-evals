DN1 — **class vs struct**: `class` is a reference type (heap-allocated, supports inheritance, null-capable). `struct` is a value type (stack/inline allocated, copy-on-assign, no inheritance). Use `struct` for small (<16 bytes), immutable, short-lived data that doesn't require inheritance (e.g., coordinates, simple DTOs). Avoid if frequently boxed or mutated.

DN2 — **IEnumerable<T> vs IQueryable<T>**: `IEnumerable<T>` executes in-memory (LINQ-to-Objects). `IQueryable<T>` builds expression trees that providers (like EF Core) translate to remote queries (SQL). Distinction matters because using `IEnumerable<T>` on a DB context pulls all rows into memory before filtering/sorting, causing severe performance/memory issues. `IQueryable<T>` pushes operations to the database.

DN3 — **async/await, Task vs ValueTask**: `async/await` compiles to a state machine that captures context, yields control, and resumes when the operation completes, avoiding thread blocking. `Task` is a reference type (heap-allocated). `ValueTask` is a value type that avoids allocation when the operation completes synchronously. Use `ValueTask` when async operations frequently complete synchronously (e.g., cache hits, already-completed tasks) to reduce GC pressure.

DN4 — **DI lifetimes & Scoped-in-Singleton bug**: DI provides dependencies via a container. `Transient`: new instance each request. `Scoped`: new per scope (e.g., HTTP request). `Singleton`: one instance per container/app lifetime. **Bug**: Injecting a `Scoped` service into a `Singleton` captures it for the Singleton's lifetime, effectively making it a Singleton. This causes memory leaks, stale state, and thread-safety issues. Fix: resolve via `IServiceScopeFactory` to create a scope manually.

DN5 — **string vs ReadOnlySpan<char>, Span<T>**: `string` is heap-allocated, immutable, and GC-managed. `ReadOnlySpan<char>` is a stack-only, zero-copy, sliceable view over memory with no GC pressure. `Span<T>` is the mutable counterpart. Use `Span<T>` for high-performance parsing, string manipulation, or buffer operations to avoid allocations. Requires `ref struct` context; not directly usable in async/state machines without `ref`/`scoped` care.

DN6 — **GC, Generations, LOH, IDisposable**: GC traces roots and collects unreachable objects. **Generations**: Gen 0 (short-lived, frequent), Gen 1 (buffer), Gen 2 (long-lived, infrequent). Objects survive collections and are promoted. **LOH**: Objects >85KB, collected only during Gen 2, not compacted (causes fragmentation). `IDisposable` enables deterministic cleanup of unmanaged resources (handles, native memory). GC only manages managed memory; finalizers are non-deterministic and expensive.

DN7 — **ConfigureAwait(false) vs default**: Default captures the current `SynchronizationContext` and resumes continuations on it. `ConfigureAwait(false)` skips context capture, resuming on any thread pool thread. **Use**: Library code, background services, non-UI code to avoid deadlocks and improve throughput. **Don't use**: UI applications (must marshal to UI thread), or when code explicitly depends on context. ASP.NET Core lacks a `SynchronizationContext` by default, making it less critical there but still best practice in shared libraries.

DN8 — **.NET 8/9 features**: 
- **Primary constructors**: `public class Service(IOptions<Config> cfg) { ... }` (full support in .NET 9).
- **Collection expressions**: `[1, 2, 3]`, `[.. arr, 4]` for concise array/span creation.
- **FrozenDictionary**: Immutable, perfect-hashing, lower memory, optimized for lookup-heavy scenarios.
- **DI Example**: `public class MyService(IOptions<AppSettings> settings) { public void Do() => Console.WriteLine(settings.Value.Key); }`

DN9 — **ObjectDisposedException on DbContext under high concurrency**: Likely cause: DbContext is manually disposed, cached across requests, or resolved outside the DI scope. Under high load, race conditions expose premature disposal or cross-request sharing. **Fix**: Register as `Scoped` (`AddDbContext`), ensure resolution per HTTP request, never cache it, and avoid manual `using` if DI manages it. EF Core registers DbContext as `Scoped` by default; DI creates one instance per scope. Sharing across scopes breaks thread safety and disposal guarantees.

DN10 — **record vs class, record struct**: `record` is a reference type with value-based equality, immutability by default, and `with` expressions. `class` is mutable with reference equality. `record struct` is a value type with value equality and zero allocation but no inheritance. **Choose**: `record` for immutable DTOs/domain events. `record struct` for performance-critical, small, immutable data where allocation must be avoided.

DN11 — **ref, out, in**: `ref`: Pass by reference, requires initialization, read/write. `out`: Pass by reference, must be assigned in method, caller doesn't need init. `in`: Pass by reference, read-only, prevents copying large structs. **Use**: `ref` for modifying existing values, `out` for multiple returns/parsing, `in` for performance with large structs or to guarantee reference semantics without mutation.

DN12 — **Nullable reference types vs value types**: NRTs (`string?`) are compile-time warnings for potential null reference exceptions. Runtime behavior unchanged. `int?` is `Nullable<int>`, a runtime value type that can hold null. **Difference**: NRTs enforce null-safety at compile time for references; `int?` is a runtime feature for value types, commonly used for DB columns or optional parameters.

DN13 — **LINQ, method vs query syntax, deferred execution**: LINQ unifies querying across collections, DBs, XML. **Method syntax**: Fluent, composable, preferred for complex queries. **Query syntax**: SQL-like, compiles to method syntax, better for joins/groupings. **Deferred execution**: Query isn't executed until enumerated (e.g., `foreach`, `.ToList()`). Enables composition and lazy evaluation. Immediate execution methods: `.Count()`, `.First()`, `.ToList()`.

DN14 — **Generic constraints**: `where T : class` (reference type), `where T : struct` (value type, non-nullable), `where T : new()` (parameterless constructor), `where T : IComparable<T>` (implements comparison). **Combine**: `where T : class, IComparable<T>, new()` for flexible, type-safe algorithms/collections. Prevents invalid operations at compile time, enabling safe casting, instantiation, and comparison.

DN15 — **abstract class vs interface, default methods**: Abstract classes can hold state, constructors, and implementation; support single inheritance. Interfaces define contracts; support multiple inheritance. **Default interface methods (C# 8+)**: Allow adding methods to interfaces without breaking implementations, slightly blurring the line. Interfaces still cannot hold instance state or have constructors.

DN16 — **Middleware pipeline, Use/Map/Run, ordering, exception handling**: Sequential request processing. `app.Use()` adds middleware. `app.Map()` branches for paths. `app.Run()` is terminal (no `next`). **Ordering matters**: Auth before routing, CORS before auth, static files before MVC, exception handling early. **Exception handling**: `UseExceptionHandler` catches unhandled downstream errors, logs, and returns error responses. Should be near the top.

DN17 — **Channel<T> vs BlockingCollection<T>**: `Channel<T>` is modern, async-native, supports bounded/unbounded, and applies backpressure via `await WriteAsync()`. `BlockingCollection<T>` is older, synchronous/blocking, wraps concurrent collections. **Bounded example**: `var ch = Channel.CreateBounded<int>(new BoundedChannelOptions(100) { FullMode = BoundedChannelFullMode.Wait });` Producers await when full, consumers read, naturally applying backpressure without thread starvation.

DN18 — **Source Generators vs reflection/IL weaving**: Source generators produce C# code at compile time, type-safe, zero runtime reflection overhead. Reflection inspects metadata at runtime (slower, breaks obfuscation). IL weaving modifies compiled IL (harder to debug, fragile). **Incremental generator**: Replaces `ISourceGenerator`, uses `IncrementalGeneratorInitializationContext`, supports caching, incremental compilation, and integrates with Roslyn analyzers. Preferred for performance and modern .NET tooling.

DN19 — **TPL Dataflow vs Channels**: TPL Dataflow builds message-passing pipelines. `ActionBlock` (executes, no output), `TransformBlock` (input→output), `BufferBlock` (stores, no processing). **vs Channels**: Dataflow offers rich composition (`Join`, `Batch`, `GroupBy`, completion propagation), ideal for complex pipelines. Channels are lighter, async-native, and better for simple streaming/backpressure. Dataflow is sync/async hybrid; Channels are async-first.

DN20 — **Minimal APIs vs Controllers**: Minimal APIs are lightweight, inline handlers, faster startup, less boilerplate. Controllers use attributes, model binding, filters, and are better for complex apps. **Trade-offs**: Minimal APIs require explicit middleware setup, harder to test without `WebApplicationFactory`, OpenAPI needs `Swashbuckle`/`Scalar`. Controllers have built-in DI, filters, and validation. **Route groups**: `app.MapGroup("/api").WithTags("Users")`. **Endpoint filters**: Inline or registered cross-cutting concerns (auth, validation) applied per endpoint without full middleware.

P1 — **list vs tuple, set vs frozenset**: `list` is mutable, ordered, indexed, allows duplicates. `tuple` is immutable, ordered, fixed-size, heterogeneous, unpackable. `set` is mutable, unordered, unique elements. `frozenset` is immutable, hashable, can be dict keys or set members.

P2 — **GIL**: Global Interpreter Lock allows only one thread to execute Python bytecode at a time. **Affects**: CPU-bound multithreading (no true parallelism). **Workarounds**: Multiprocessing, C extensions releasing GIL, `asyncio` (I/O bound), or offloading to native/C. Alternative interpreters (Jython/IronPython) exist but are largely deprecated.

P3 — **deepcopy vs copy**: `copy.copy()` creates a shallow copy (new container, shared nested objects). `copy.deepcopy()` recursively copies all nested objects. **Shallow copy bug**: `a = [[1, 2]]; b = copy.copy(a); b[0].append(99); print(a)` outputs `[[1, 2, 99]]` because inner lists are shared references.

P4 — **Decorators, execution time**: Decorators wrap functions to extend behavior. 
```python
import time, functools
def log_time(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — **Generators, yield, yield from**: Generators use `yield` to produce values lazily, preserving state between yields. **vs List**: Lazy evaluation, constant memory, infinite sequences possible. `yield from` delegates to another generator, cleaner syntax for chaining, and properly forwards exceptions/return values.

P6 — **asyncio event loop, run/gather/create_task, time.sleep**: Event loop schedules async tasks and I/O. `asyncio.run()` creates loop, runs coroutine, closes loop. `asyncio.gather()` runs multiple coroutines concurrently, returns results in order. `asyncio.create_task()` schedules a coroutine for later execution/cancellation. `time.sleep()` blocks the entire thread/event loop; use `await asyncio.sleep()` to yield control.

P7 — **MRO, C3 linearization, diamond inheritance**: MRO defines method lookup order. Python 3 uses **C3 linearization** (ensures monotonicity, left-to-right precedence). Diamond `D(B, C)` → MRO: `D → B → C → A`. `D().who()` prints `"C"` because `B` has no `who`, so lookup continues to `C`, which overrides `A`'s implementation.

P8 — **Metaclass vs __init_subclass__**: Metaclass controls class creation (`__new__`, `__init__`), powerful but complex. `__init_subclass__` is a hook called when a class is subclassed, simpler and instance-friendly. **Metaclass use**: ORM model registration, enforcing class-level constraints, modifying class dict during creation. **`__init_subclass__` use**: Plugin registration, automatic field registration, simpler inheritance hierarchies.

P9 — **multiprocessing vs threading vs concurrent.futures**: Threading: I/O bound, shares memory, GIL limits CPU parallelism. Multiprocessing: CPU bound, separate processes, bypasses GIL, uses IPC. `concurrent.futures`: High-level API (`ThreadPoolExecutor`, `ProcessPoolExecutor`) abstracting both. **Pickling**: Multiprocessing serializes args/results via pickle. Unpicklable objects (file handles, locks, lambdas) fail. Use `multiprocessing.shared_memory` or `pathos` for complex objects.

P10 — **__slots__**: Declares fixed attributes, prevents `__dict__` creation. **Use**: Memory optimization for many instances with fixed attributes. **Prevents**: Dynamic attribute addition, `__dict__`/`__weakref__` (unless explicitly included). **Memory impact**: Significant per-instance reduction (no dict overhead), but adds class-level overhead.

P11 — **Virtual environments, venv vs virtualenv vs conda**: Isolated Python environments with separate packages/interpreter. **Why**: Dependency isolation, reproducibility, avoid system conflicts. `venv`: Standard library, lightweight, pure Python. `virtualenv`: Third-party, more features, historically before `venv`. `conda`: Package + env manager, handles non-Python binaries, data-science focused, heavier.

P12 — **Comprehensions vs map/filter**: Comprehensions (`[x for x in lst if x>0]`) are Pythonic, readable, and often faster. `map()`/`filter()` return iterators, can be slower due to function call overhead. **Prefer**: Comprehensions for readability/performance. Use `map`/`filter` when composing functions or working with existing iterators/functions.

P13 — **== vs is, object interning**: `==` checks value equality (`__eq__`). `is` checks identity (same memory address). **Interning**: CPython caches small integers (-5 to 256) and some strings for performance. `a is b` returns `True` for small ints because they reference the same cached object.

P14 — **\*args, \*\*kwargs, /, \***: `*args` collects extra positional args into a tuple. `**kwargs` collects extra keyword args into a dict. `/` marks positional-only parameters. `*` marks keyword-only parameters. **Use**: Flexible APIs, argument forwarding, enforcing calling conventions.

P15 — **Context managers**: Ensure setup/teardown via `with`. **Class-based**: Implement `__enter__`/`__exit__`. **Generator-based**: Use `@contextmanager` for simpler functions. **Example (DB)**:
```python
class DBConn:
    def __enter__(self): self.conn = connect(); return self.conn
    def __exit__(self, *e): self.conn.close()
```

P16 — **Type hinting, Union, Optional, Literal, TypeVar, Protocol**: Static annotations for tooling, not runtime-enforced. `Union[A, B]`/`A | B`: multiple types. `Optional[T]`/`T | None`: allows None. `Literal["a"]`: exact value constraint. `TypeVar`: generic variable with constraints. `Protocol`: structural subtyping (duck typing). **Tools**: mypy/pyright parse annotations, catch mismatches, enable autocomplete.

P17 — **Data model (dunder methods)**: `__repr__`: unambiguous, developer-focused. `__str__`: readable, user-focused. `__eq__`: value equality. `__hash__`: hashability (immutable objects). `__getattr__`: fallback when attribute missing. `__getattribute__`: called for every access (dangerous). **Define `__eq__` without `__hash__`**: Sets `__hash__ = None`, making instances unhashable (can't be dict keys/set members).

P18 — **Descriptors**: Objects implementing `__get__`, `__set__`, `__delete__` that control attribute access on owner classes. **Protocol**: `__get__(self, obj, type)`, `__set__(self, obj, val)`, `__delete__(self, obj)`. `property`, `classmethod`, `staticmethod` are descriptors that modify `__get__` to compute values or pass class/ignore instance. Accessed via `type.__getattribute__`, which checks MRO for descriptors.

P19 — **Import system**: Relative imports (`from . import mod`) resolve relative to package. Absolute imports (`from pkg import mod`) resolve from `sys.path`. `sys.path` lists search directories; `PYTHONPATH` prepends to it. `__init__.py` marks packages and runs on import. Namespace packages allow splitting across paths without `__init__.py`. **Finder**: locates modules in `sys.path`. **Loader**: loads/initializes module. Standardized via `importlib`.

P20 — **dataclasses vs attrs/Pydantic**: `dataclasses` (stdlib) generates `__init__`, `__repr__`, `__eq__`, `__hash__`. `attrs` (third-party) is more flexible/faster. `Pydantic` adds runtime validation, serialization, type coercion. `__post_init__`: runs after `__init__` for validation. `field(default_factory=list)`: avoids mutable defaults. `frozen=True`: immutability + auto `__hash__`. **Choose Pydantic** when needing runtime validation, serialization, API models, or complex type coercion.
