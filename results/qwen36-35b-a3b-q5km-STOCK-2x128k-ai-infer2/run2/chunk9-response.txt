SC1-A
The pods fail because Kubernetes Pod Security Standards (PSS) enforcement changed from `baseline` to `restricted`. The `restricted` profile requires `securityContext.runAsNonRoot: true` AND explicitly requires `runAsUser` to be set to a non-zero UID. The new base image (`cgr.dev/chainguard/static:latest`) sets `USER root` (UID 0) in the Dockerfile. Without an explicit `runAsUser` override in the pod spec, Kubernetes defaults to UID 0, which violates `runAsNonRoot: true`. The `restricted` profile also forbids `privileged: true`, `hostNetwork`, and `hostPID`, but the immediate CrashLoopBackOff is caused by the UID mismatch triggering a security context validation failure at container runtime.

SC1-B
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.securityContext} | @json'
```

SC1-C
**Immediate fix:** Patch deployments to add `runAsUser: 1000` (or non-root UID) under `securityContext` or `securityContext` at container level. Trigger rolling update: `kubectl rollout restart deployment/<name> -n <ns>`.
**Image-level fix:** Rebuild base image with `USER 1000` or use a pre-hardened non-root base.
**CI gate:** Add OPA/Kyverno policy or Trivy/Checkov scan to enforce `runAsUser != 0` and validate against `restricted` PSS. Fail pipeline if missing.
**Rollout without downtime:** Use `kubectl set image` or `kubectl patch` with `--record` to trigger a rolling update. Ensure `minReadySeconds` and `maxSurge` are configured. The old pods terminate only after new ones pass readiness probes.
**Prevention:** Enforce `restricted` PSS via admission controller, pin base image digests, and require security context validation in CI.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL files are shipped from primary to replica with network latency. Promoting the replica severs the replication stream, making any WAL not yet shipped or applied permanently lost. The data loss window equals the replication lag at promotion time. To quantify: check `pg_stat_replication` on the primary for `write_lag`, `flush_lag`, `replay_lag`, and compare `pg_last_xlog_receive_location()` vs `pg_last_xlog_replay_location()` on the replica. Monitor `aws_rds_replica_lag` CloudWatch metric pre-failover.

SC2-B
1. Import the promoted replica: `terraform import aws_db_instance.new_primary <new-arn>`
2. Update Terraform config to reference the new instance identifier/ARN.
3. Remove old instance from state: `terraform state rm aws_db_instance.old_primary`
4. Update dependent resources (SGs, Route53, param groups) in code to reference the new ARN.
5. Run `terraform plan` to verify no destroy/recreate actions. Use `-target` if needed to isolate changes.

Avoid hardcoding ARNs; use variables/data sources. If resources reference the old instance via attributes, use `terraform state mv` to rename the imported resource to match the config.

SC2-C
**RDS Proxy vs PgBouncer:** RDS Proxy handles connection pooling at the DB layer, automatically routes to the new primary on failover, and supports IAM auth. PgBouncer requires app-level DNS updates or VIP changes.
**Route53:** Use latency-based or failover routing with health checks pointing to the new endpoint. TTL < 60s for fast propagation.
**App retry logic:** Implement exponential backoff with jitter, idempotent writes, and circuit breakers.
**RPO < 1s:** Standard RDS cross-region async cannot guarantee this. **Aurora Global Database** is recommended. It uses a single data volume replicated synchronously across regions (up to 3), providing RPO < 1s and RTO < 1 min. It eliminates async lag and simplifies failover via console/API.

SC4-A
1. **Sticky sessions/local memory:** Kubernetes is stateless and scales horizontally. *Fix:* Externalize sessions to Redis/ElastiCache or use JWT-based stateless auth.
2. **Local NFS mount:** Pods are ephemeral; local mounts don't survive rescheduling. *Fix:* Use CSI NFS driver or migrate to cloud-native storage (EFS/S3) with RWX access.
3. **On-prem Oracle 19c:** High latency/complexity for cross-site DB access. *Fix:* Keep on-prem, connect via VPN/ExpressRoute, or migrate to cloud DB (Aurora/Oracle on EC2) with CDC.
4. **IBM MQ integration:** Tightly coupled synchronous messaging. *Fix:* Use MQ client libraries, expose MQ via service mesh/VPN, or migrate to cloud-native messaging (SQS/MSK) with async patterns.
5. **F5 BIG-IP dependency:** Hardware LB doesn't map to K8s services. *Fix:* Replace with Kubernetes Ingress Controller (NGINX/ALB) + Service Mesh for L7 routing, TLS termination, and health checks.

**SQL diagnostic query:**
```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid,
       blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS current_statement_in_blocking_process
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC5-C
**Architectural solution:**
- **CQRS:** Separate read/write models. Reconciliation writes to a write model; serving reads from a read replica or materialized view.
- **Read replica:** Run reconciliation job against a read replica to avoid locking production tables.
- **Bulkhead isolation:** Use separate DB connection pools for serving vs background jobs. Limit pool size for background jobs.
- **CronJob scheduling:** Run during off-peak, set `concurrencyPolicy: Forbid`, `restartPolicy: Never`.
- **PDB & Resource Quotas:** Define PDB for serving pods (`minAvailable: 80%`). Set ResourceQuotas/LimitRanges in the CronJob namespace to cap CPU/memory. Use `podDisruptionBudget` to ensure serving pods aren't evicted during node maintenance.

SC6-C
**Direct Connect:** Dedicated 10Gbps+ link, low latency, predictable cost. Fits zero-trust (still requires mTLS/app auth). Routing: Static routes or BGP. High CAPEX.
**Second VPN + ECMP:** Low cost, scales bandwidth via BGP ECMP. IPsec overhead adds latency/jitter. Failover via BGP path selection. Fits zero-trust. Routing: BGP multi-neighbor, equal-cost paths.
**Tailscale/Netbird:** WireGuard-based mesh, easy setup, low latency, scales with users. Relies on relay nodes for NAT traversal. Cost: per-device/user. Fits zero-trust well (device/auth-based). Routing: MagicDNS, subnet routers, automatic route propagation.
**Recommendation:** Direct Connect for primary backbone (reliability/bandwidth), Tailscale/Netbird for secure overlay/mesh access, or second VPN + ECMP if budget-constrained. All require mTLS at app layer for true zero-trust.

SC10-C
**Failover sequence:**
1. Health checks detect site down (multiple probes, quorum-based, >3 consecutive failures).
2. DNS failover (GSLB) updates to Dallas.
3. Patroni promotes standby (sync commit ensures RPO=0).
4. Redis Sentinel promotes master.
5. RabbitMQ federation catches up, switches to Dallas.
6. MinIO site replication continues, catches up to 15m RPO.
7. Update OpenTofu state (`terraform refresh`/import) to reflect new primary.
**Split-brain:** Use fencing (STONITH), quorum-based DCS, disable primary writes if split detected.
**Failback:** Reverse replication, sync data, verify integrity, DNS switch back to Chicago, update OpenTofu state, decommission Dallas as primary.
