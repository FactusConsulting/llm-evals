T1 — `tofu plan` evaluates configuration against current state and live infrastructure to produce an execution plan (create/update/destroy) without making changes. `tofu apply` executes that plan (or generates one if omitted) and provisions/updates/deletes resources. `apply` requires confirmation unless `-auto-approve` is used.

T2 — State is a JSON file mapping real-world resources to your configuration, tracking IDs, attributes, and dependencies. Remote state is critical for team collaboration, state locking (preventing concurrent modifications), security (storing sensitive data in encrypted, access-controlled storage), and durability (avoiding local file loss/corruption).

T3 — `count` creates resources indexed by integers (0, 1, 2...). Removing an item from the middle shifts indices, forcing recreation of subsequent resources. `for_each` creates resources keyed by strings (maps/sets). Removing an item doesn't affect others. `for_each` is preferred when resources have stable, unique identifiers and you need to avoid unintended recreations during list modifications.

T4 — OpenTofu detects drift during `tofu plan` by comparing the state file with live infrastructure via provider APIs. It shows changes as in-place updates or destroy/create. Running `tofu apply` reconciles state to match configuration. You can also run `tofu refresh` to update state without applying changes.

T5 —
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
  # provider-specific required args...
}
```

T6 — `terraform_remote_state` reads state from another OpenTofu run's backend, potentially pulling entire state or specific outputs. It couples modules to backend structure and can be slow. Output values explicitly expose typed, intentional data. Recommended alternative: Pass data via module outputs (`module.<name>.<output>`). For cross-project sharing, `terraform_remote_state` is acceptable but should only read specific outputs, never the raw state map.

T7 — Provisioners run after resource creation but don't block output evaluation or reliably expose side effects to outputs. Outputs are evaluated during the apply phase, often before provisioners finish or before files are written. Fix: Use a `local_file` resource to capture the kubeconfig, or use `local-exec` to write it to a known path, then read it via `file("${path.module}/kubeconfig")` in an output. Best practice: Avoid provisioners for data extraction; use dedicated resources/data sources.

T8 — `tofu import` associates an existing resource with a managed config entry. Limitations: requires manual config writing, doesn't auto-resolve dependencies, and is error-prone. The `import` block (1.5+) is declarative, runs during `plan/apply`, automatically handles dependencies, supports multiple resources, and integrates with the execution graph, eliminating manual CLI state manipulation.

T9 — Variables (`variable` blocks) are external inputs that customize modules/config. Outputs (`output` blocks) expose internal module/root data to callers. Inputs flow in; outputs flow out. Variables are referenced as `var.<name>`, outputs as `module.<name>.<name>`.

T10 — A provider is a plugin that interacts with cloud/API backends to manage resources. Without `tofu init`, plugins aren't downloaded, and `tofu plan` fails with provider-not-found or schema errors.

T11 — `.terraform.lock.hcl` records exact provider versions, checksums, and source hashes. Commit it to ensure reproducible builds, prevent unexpected provider updates/breaking changes, and guarantee team/CI environments use identical provider versions.

T12 — `tofu destroy` deletes all resources in the current state. Target a single resource with: `tofu destroy -target=<resource_type>.<resource_name>`. Chain `-target` flags for multiple resources.

T13 — A data source reads existing infrastructure/data without managing its lifecycle. Example: `data "aws_ami"` to fetch the latest Ubuntu AMI ID. Use it when you need to reference existing resources rather than create/manage them.

T14 — Variables are external inputs, can be overridden via CLI/files, and require `variable` blocks. Locals are internal computed values defined in `locals` blocks, not exposed externally. Use locals for repeated expressions, filtering, mapping, or avoiding repetition. Use variables for configurable inputs.

T15 — `lifecycle` controls resource creation/destruction behavior:
- `create_before_destroy = true`: Creates new before destroying old (zero-downtime replacements like LBs).
- `prevent_destroy = true`: Blocks `destroy`/replacement (critical data like databases).
- `ignore_changes`: List of attributes to ignore drift on (e.g., manually modified tags, or `last_applied_configuration`).

T16 — `moved` block declares a resource's new address (type/name/module). During `plan/apply`, OpenTofu updates the state mapping automatically, preserving lifecycle, dependencies, and attributes without recreation during refactoring.

T17 — OpenTofu builds a DAG from resource references. Implicit dependencies arise from attribute references (e.g., `vpc.id`). Explicit dependencies use `depends_on`. `depends_on` adds artificial edges to the DAG, forcing sequential execution and reducing parallelism. Use sparingly to avoid slowing apply and masking real dependency issues.

T18 — 1. **State Splitting/Modularization**: Break monolithic state into smaller backends/modules. *Tradeoff*: Increases management overhead, requires careful output passing.
2. **Optimize Provider Refresh**: Use `refresh=false` during plan or configure providers to skip unnecessary reads. *Tradeoff*: May miss drift, requires manual state sync.
3. **Increase `-parallelism`**: Default is 10; raise it to speed up API calls. *Tradeoff*: Higher rate limits, potential state conflicts.
4. **Reduce Resource Count/Use Data Sources**: Replace managed resources with data sources where lifecycle isn't needed. *Tradeoff*: Limits flexibility, may not fit all use cases.

T19 — State locking uses backend-specific mechanisms (e.g., DynamoDB for S3) with a lock record containing process ID/TTL. If a pipeline crashes, the lock persists until TTL expires or is broken. Break with `tofu force-unlock <LOCK_ID>`. Risks: Data corruption, concurrent modifications, state inconsistency. Only break if certain no other process holds it.

T20 — 1. Create S3 bucket & DynamoDB table. 2. Backup `terraform.tfstate`. 3. Add backend block (`s3`, `dynamodb`) to config. 4. Run `tofu init -migrate-state`. OpenTofu copies local state to S3, updates backend config, and removes local state. 5. Verify: `tofu state list` confirms resources present. `tofu plan` shows no unexpected changes. Check S3 console for state file and DynamoDB for lock entries.

A1 — Task: Single action (module + args). Role: Reusable collection of tasks, handlers, vars, templates, files in a standard directory structure. Playbook: YAML file containing one or more plays (lists of tasks/roles) to execute against hosts.

A2 — `ansible_facts` are auto-discovered system attributes gathered by the `setup` module. Access OS family via `{{ ansible_facts.os_family }}` or `{{ ansible_os_family }}`.

A3 — `command`: Runs without shell features (no pipes/redirects). Safest, default. `shell`: Runs via `/bin/sh`, supports pipes/redirects. Use when shell features needed. `raw`: Runs without Python, bypasses module execution. Use for initial bootstrap or when Python isn't installed.

A4 — Ansible modules are designed to be idempotent (check state, only change if needed). Idempotent: `apt: name=nginx state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run). Fix with `copy` or `lineinfile`.

A5 —
```yaml
- name: Install htop (Debian)
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install EPEL & htop (RedHat)
  block:
    - name: Install EPEL
      package: name=epel-release state=present
    - name: Install htop
      package: name=htop state=present
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (low to high): role defaults → inventory (group_vars/host_vars) → extra_vars (`-e`) → `set_fact`/`include_vars`. Priority: `extra_vars` > `set_fact` > `host_vars` > `group_vars` > `role defaults`. `set_fact` overrides almost everything except `extra_vars`.

A7 — Use `serial: 3` in the play. Group nodes in inventory (`[rke2_masters]`, `[rke2_agents]`). Run masters first (`serial: 1`), then agents (`serial: 3`). Use `wait_for` to ensure each batch is ready before the next:
```yaml
- hosts: rke2_agents
  serial: 3
  tasks:
    - include_role: name=rke2_agent
    - name: Wait for RKE2 readiness
      wait_for:
        path: /var/lib/rancher/rke2/server/cred/node-passwd
        state: present
        timeout: 300
```

A8 — `ansible-vault` encrypts sensitive data. To encrypt a single variable without encrypting the file, use inline vault syntax: `password: !vault | $ANSIBLE_VAULT;1.1;AES256...` or generate via `ansible-vault encrypt_string 'secret' --name 'my_var'` and paste the result. The file remains plaintext except for that value.

A9 — Inventory: List of hosts/groups Ansible manages. Static: Hardcoded INI/YAML file. Dynamic: Script/API that generates inventory on-the-fly (e.g., cloud providers, CMDB), supporting auto-scaling and real-time updates.

A10 — `ansible webservers -a "df -h"` (default module is `command`).

A11 — Handler: Special task that only runs when notified. Runs once per play at the end, regardless of notification count. Trigger with `notify: handler_name` in a task.

A12 — Global config for Ansible behavior. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `log_path`.

A13 — `register` captures module output into a variable. Usage: `register: result` → access via `{{ result.stdout }}`, `{{ result.rc }}`, etc. Use in `when`, `debug`, or subsequent tasks.

A14 — `import_tasks`: Static, evaluated at parse time. Tasks load immediately. `include_tasks`: Dynamic, evaluated at runtime. Tasks load when reached. Use `include_tasks` for conditionals (`when`), loops, or dynamic paths. `import_tasks` is faster but doesn't support runtime conditionals.

A15 — Galaxy: Hub for sharing Ansible roles/collections. `requirements.yml` lists roles/collections with names, versions, sources. Install roles: `ansible-galaxy install -r requirements.yml`. Install collections: `ansible-galaxy collection install -r requirements.yml`.

A16 — Connection plugins manage how Ansible connects to hosts. `ssh`: Default, connects via SSH to Linux/Unix. `local`: Runs tasks on control node. `network_cli`: Connects via SSH/Telnet to network devices using CLI interaction. Use `ssh` for servers, `local` for control node tasks, `network_cli` for network gear.

A17 — `delegate_to`: Runs task on a different host. `run_once`: Executes task only once across all matched hosts. Example: Gather package list from remote, write to local file:
```yaml
- name: Get package list
  command: rpm -qa
  register: pkg_list
  delegate_to: localhost
  run_once: true
- name: Save to local file
  copy:
    content: "{{ pkg_list.stdout }}"
    dest: /tmp/packages.txt
  delegate_to: localhost
```

A18 — 1. **Increase `forks`**: More parallel connections (default 5). *Tradeoff*: Higher CPU/memory on control node, potential API/network limits.
2. **Enable `pipelining`**: Reduces SSH sessions by chaining commands. *Tradeoff*: Requires `requiretty` disabled on targets.
3. **Fact Caching**: Cache `ansible_facts` (Redis/JSON). *Tradeoff*: Stale facts if infrastructure changes rapidly, requires cache backend.
4. **Mitogen**: Multiplexes connections, drastically reducing overhead. *Tradeoff*: Requires Python 3, may have module compatibility issues, adds dependency.

A19 — Jinja2 generates dynamic configs. `{{ }}`: Output expression. `{% %}`: Control structure (loops/conditionals). `{# #}`: Comments (not rendered).
```jinja2
upstream backend {
{%- for server in backend_servers %}
  # Health check: {{ server }}:{{ server_port }}
  server {{ server }}:{{ server_port }};
{%- endfor %}
}
```

A20 — Use `serial: 5` for batches. Pre-task removes host from LB. Deploy/restart app. Health check with `uri` module + `retries`/`delay`. Wrap in `block/rescue` for rollback on failure. Handler re-adds to LB on success:
```yaml
- hosts: webservers
  serial: 5
  tasks:
    - name: Rolling deploy
      block:
        - name: Remove from LB
          uri: url="http://lb-api/remove?host={{ inventory_hostname }}" method=POST
        - name: Deploy & restart
          copy: src=./app dest=/opt/app/
          notify: restart nginx
        - name: Health check
          uri: url="http://{{ inventory_hostname }}/health" status_code=200
          retries: 5
          delay: 10
      rescue:
        - name: Rollback
          copy: src=./app_backup dest=/opt/app/
          notify: restart nginx
        - name: Re-add to LB
          uri: url="http://lb-api/add?host={{ inventory_hostname }}" method=POST
  handlers:
    - name: restart nginx
      service: name=nginx state=restarted
    - name: Re-add to LB
      uri: url="http://lb-api/add?host={{ inventory_hostname }}" method=POST
```
This ensures zero downtime: hosts are drained, updated, verified, and returned to rotation sequentially.
