K1 — A **Deployment** manages stateless workloads with interchangeable, randomly named pods. A **StatefulSet** manages stateful workloads requiring stable network identities (stable hostnames), ordered deployment/scaling, and stable persistent storage. StatefulSets guarantee pods are created/terminated in order and retain their identity across rescheduling.

K2 — A `ClusterIP` Service creates a virtual IP and port within the cluster. `kube-proxy` watches the API server and programs `iptables` or `IPVS` rules on each node to DNAT traffic destined for that ClusterIP:Port to one of the healthy backend pod IPs, using round-robin or least-connection load balancing.

K3 — A **PersistentVolume (PV)** is a cluster-wide storage resource (statically provisioned or dynamically created). A **PersistentVolumeClaim (PVC)** is a user's request for storage. A **StorageClass** defines the provisioning template (e.g., SSD, replication factor). Relation: A PVC binds to a PV; if no static PV exists, the StorageClass dynamically provisions a PV to satisfy the PVC.

K4 — 1. `kubectl logs <pod> --previous` to check crash exit codes/stack traces. 2. `kubectl describe pod` to inspect Events, OOMKilled status, or probe failures. 3. Verify resource requests/limits and node capacity. 4. Check app dependencies (DB connectivity, missing env vars, config file permissions).

K5 — CoreDNS provides internal DNS resolution for `Service` and `Pod` names within the cluster. If CoreDNS pods are down, internal service discovery fails (pods can't resolve each other by name), but direct IP communication and external DNS resolution remain unaffected.

K6 — The scheduler uses **filtering** to eliminate nodes that violate constraints (insufficient resources, taints, node selectors, affinity/anti-affinity). It then **scores** remaining nodes using priority functions. Factors: 1) LeastRequested (CPU/memory utilization), 2) NodeAffinity/TaintToleration, 3) PodTopologySpread (balance across zones), 4) ResourcePressure (disk/network), 5) Inter-pod affinity.

K7 — Yes, it will schedule. The node has ~512Mi free; the pod requests 256Mi, which fits. At runtime, if the container uses 600Mi (> `limits.memory: 512Mi`), the kernel OOM killer will terminate it (`OOMKilled`). Kubernetes enforces memory limits strictly; throttling only applies to CPU.

K8 — 1. External LB forwards traffic to the Ingress Controller's NodePort/LoadBalancer IP. 2. NGINX Ingress Controller parses the Ingress resource rules. 3. NGINX routes to the matching Kubernetes Service. 4. Service resolves to backend Pod IPs via Endpoints. 5. `kube-proxy` (iptables/IPVS) DNATs traffic to the specific Pod IP. 6. Pod receives the request.

K9 — A `NetworkPolicy` defines allowed ingress/egress traffic for pods using label selectors. Default behavior (no policies): all traffic is allowed. When a policy is applied: only traffic matching the policy is permitted; all other ingress/egress is explicitly denied.

K10 — `RollingUpdate` gradually replaces old pods with new ones, ensuring zero downtime. `Recreate` terminates all existing pods before starting new ones, causing downtime. Choose `Recreate` for stateful applications that cannot run multiple versions concurrently or require strict sequential updates.

K11 — A namespace provides virtual cluster isolation for resources, users, and quotas. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it reveals: 1) Pod Events (scheduling, pull, probe failures), 2) Container status details (restart counts, last state, exit codes), 3) Resource limits/requests and node affinity/taints, 4) Volume mounts and environment variables.

K13 — A ConfigMap stores non-confidential configuration data. Pods consume it via: 1) Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`), 2) Volume mounts (files appear in a container directory), 3) Command/arguments injection.

K14 — `ClusterIP`: internal-only virtual IP. `NodePort`: exposes the service on a static port on each node's IP. `LoadBalancer`: provisions a cloud provider external LB, routes to the NodePort/ClusterIP, and assigns a public IP.

K15 — A DaemonSet ensures a pod runs on every node (or nodes matching a selector). Use it for node-level daemons: logging agents (Fluentd), monitoring exporters (node-exporter), or storage daemons (Ceph), where one instance per node is required.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Difference: taints/tolerations are node-driven (repel/allow), affinity is pod-driven (attract). Use case: Taints for dedicated GPU nodes; Affinity for zone-aware scheduling.

K17 — An Operator is a custom controller that manages complex, stateful applications using Custom Resource Definitions (CRDs) and custom reconciliation logic. Unlike standard controllers, Operators encode operational knowledge (backups, upgrades, failover, scaling) into code, eliminating manual intervention for stateful services.

K18 — etcd uses a **linearizable** consistency model via Raft. If quorum is lost, the cluster becomes read-only/unwritable. If 2/3 nodes are permanently lost, quorum cannot be restored; the cluster cannot recover without a backup. Workaround: add a 4th node and force-join, but it will contain stale data.

K19 — RBAC controls access via Roles/ClusterRoles (permissions) and RoleBindings/ClusterRoleBindings (assignments). Manifest for read-only pod/logs in `dev` namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` means queries with <5 dots are appended to search domains (`svc.cluster.local`, etc.), causing multiple DNS queries before external resolution. Fix: set `dnsConfig: { ndots: 1 }` in the pod spec, or use FQDNs (trailing dot) in the application to bypass search domain expansion.

D1 — `git merge` preserves history with a merge commit; `git rebase` rewrites history by replaying commits linearly. Avoid rebasing on shared/public branches or branches others are actively working on, as it forces unnecessary re-merges and history conflicts.

D2 — **TCP**: connection-oriented, reliable, ordered delivery. **UDP**: connectionless, unreliable, low-latency. TCP examples: HTTP/HTTPS, SSH, SMTP. UDP examples: DNS, VoIP, DHCP, streaming media.

D3 — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to unpredictable results. Example: Two threads incrementing a shared counter without a mutex; final value may be less than expected due to lost updates.

D4 — **Symmetric**: single key for encryption/decryption (fast). **Asymmetric**: public/private key pair (secure key exchange). TLS uses asymmetric encryption during the handshake to securely exchange a session key, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates a read-only image layer. Layer caching reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., copy dependencies first, then source code) to maximize cache hits and speed up builds.

D6 — 1. Check upstream service logs/metrics for errors or high latency. 2. Verify resource exhaustion (CPU/memory throttling, OOM). 3. Inspect rate limiting/throttling configs (API gateway, app limits). 4. Check network/LB health checks and connection pool saturation. Order: app logs → infra metrics → config/throttling → network/LB.

D7 — CAP theorem: a distributed system can only guarantee two of three: Consistency, Availability, Partition tolerance. **CP**: Distributed SQL (CockroachDB, HBase) prioritizes data correctness; blocks requests during partitions. **AP**: DNS, Cassandra, DynamoDB prioritize availability; return stale data during partitions.

D8 — **Horizontal scaling**: adding more nodes/instances. **Vertical scaling**: increasing CPU/RAM of existing nodes. Horizontal scaling requires: stateless application design, distributed databases, external session storage, message queues, and load balancers.

D9 — An environment variable is a dynamic key-value pair passed to processes to configure behavior. Persist across sessions: add `export VAR_NAME="value"` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict syntax, universal parsing, ideal for APIs. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: strict schema validation & language agnosticism. YAML advantage: readability & reduced boilerplate for configs.

D11 — A REST API is an architectural style using standard HTTP methods. **GET**: retrieve resource. **POST**: create new resource. **PUT**: replace/update entire resource. **DELETE**: remove resource.

D12 — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3` or `package-lock.json`). It ensures reproducible builds, prevents unexpected breaking changes from upstream updates, and guarantees consistent environments across dev/staging/prod.

D13 — **Compiled**: source code is translated to machine code before execution (C, Rust). **Interpreted**: source code is executed line-by-line by a runtime (Python, JavaScript). Note: many modern languages use JIT compilation (Java, Go) bridging both paradigms.

D14 — A **reverse proxy** sits in front of servers, routing client requests to backends. Use cases: SSL termination, load balancing, caching (Nginx, HAProxy). A **forward proxy** sits in front of clients, routing outbound traffic. Use case: corporate content filtering, outbound caching.

D15 — A deadlock occurs when two or more processes wait indefinitely for resources held by each other. Coffman conditions: 1) Mutual Exclusion, 2) Hold and Wait, 3) No Preemption, 4) Circular Wait. All must hold simultaneously.

D16 — Eventual consistency guarantees that if no new updates occur, all replicas will eventually converge. Cassandra uses tunable consistency levels (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`). For read-after-write, clients can use `CL=ALL` or compare `WRITETIME` timestamps to ensure they see their own writes.

D17 — mTLS requires both client and server to present valid certificates. Handshake: ClientHello → ServerHello+Cert → ServerKeyExchange → ClientKeyExchange+Cert → CertificateVerify → Finished. Both sides validate certs via PKI. Used in: service meshes (Istio), zero-trust architectures, internal microservices.

D18 — A hash table maps keys to values via a hash function. Collision resolution: **chaining** (linked lists at buckets) or **open addressing** (probing: linear, quadratic, double hashing). Time complexity: Average O(1) for insert/lookup/delete. Worst case O(n) when all keys hash to the same bucket.

D19 — A circuit breaker prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal traffic), **Open** (fail fast, trip after error threshold), **Half-open** (allow limited test requests). Relates to retries: circuit breakers should wrap retry logic to prevent retry storms during outages; retries should use exponential backoff to avoid overwhelming recovering services.

D20 — **Optimistic**: assumes no conflicts, validates on commit (e.g., `UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND version = 5`). **Pessimistic**: locks resources during transaction (e.g., `SELECT * FROM accounts WHERE id = 1 FOR UPDATE`). Choose optimistic for high read/low write contention; pessimistic for high write contention or critical financial data requiring strict isolation.
