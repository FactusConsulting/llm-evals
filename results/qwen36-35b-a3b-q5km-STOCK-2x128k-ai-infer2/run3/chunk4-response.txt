G1 — A slice is a dynamic view over an array, containing a pointer, length, and capacity. An array has a fixed size baked into its type and is passed by value. When a slice's capacity is exhausted, `append` allocates a new backing array (typically doubling capacity), copies existing elements, and returns a new slice header pointing to it.

G2 — `var x int` declares a variable with explicit type and zero value; `x := 0` is a short variable declaration that infers type and requires at least one new variable on the left. You cannot use `:=` at package scope, when redeclaring an existing variable without introducing a new one, or in function signatures.

G3 — A goroutine is a lightweight, multiplexed execution context managed by the Go runtime (~2KB initial stack). OS threads are kernel-managed, heavier (~1-2MB stack), and 1:1 mapped. The GMP model: G = goroutine, M = OS thread, P = logical processor (scheduler context/work queue). The scheduler multiplexes Gs onto Ms using Ps for work-stealing, preemption, and network poller integration.

G4 — Channels are typed conduits for safe goroutine communication. Unbuffered channels block both sender and receiver until both are ready. Buffered channels have a capacity; send blocks only when full, recv blocks only when empty. Sending to a full buffered channel blocks until space opens or the channel is closed.

G5 — `context` propagates deadlines, cancellation signals, and request-scoped values across API boundaries. Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
client.Do(req) // automatically cancels if timeout hits
```

G6 — Go uses implicit interface satisfaction (duck typing): any type implementing the methods satisfies the interface, without explicit `implements` keywords. Unlike Java/C#, interfaces are decoupled from types. `interface{}`/`any` matches any type. Powerful for abstraction and generics, but dangerous because type assertions can panic and compile-time safety is lost.

G7 — Go's memory model guarantees visibility only through synchronization (channels, mutexes, atomics). The code races: `ready` may be cached in a register/memory, and `data` may not be visible to the main goroutine. Fix with `sync/atomic` (`atomic.Bool`), `sync.Once`, or a channel to establish a happens-before relationship.

G8 — `sync.Mutex` provides exclusive access; `sync.RWMutex` allows concurrent reads or exclusive writes. `sync.Map` is optimized for compile-time-known keys, read-heavy workloads, or disjoint key sets. Trade-offs: `sync.Map` has higher per-operation overhead and memory usage; a regular `map` + `Mutex` is faster for dense, write-heavy, or hot-path scenarios.

G9 — Modules manage dependencies via `go.mod` (declares direct deps, versions, replace directives) and `go.sum` (cryptographic hashes of exact module versions for integrity). `go mod tidy` removes unused deps, adds missing ones, and updates both files. MVS (Minimum Version Selection) resolves dependency constraints to pick the lowest compatible version for each module, preventing version bloat.

G10 — `defer` schedules a function call to run when the surrounding function returns. Multiple defers execute in LIFO order. Gotcha in loops: pre-Go 1.22, closures captured the loop variable by reference, causing all defers to see the final value. Go 1.22 fixed loop variable scoping, but passing values explicitly or using loop-indexed variables remains idiomatic for clarity.

G11 — A pointer stores a memory address. Zero value is `nil`. Create a pointer to a struct literal with `&MyStruct{Field: value}`. Pointers are used for mutability, avoiding copies, and implementing reference semantics.

G12 — `init()` runs automatically before `main()` during package initialization. It runs once per package. A package can have multiple `init()` functions; they execute in declaration order. Complex logic should avoid `init()` due to hidden dependencies and testing difficulties.

G13 — `new(T)` allocates zeroed memory for any type and returns a pointer `*T`. `make(T, args)` initializes only slices, maps, and channels, returning the value itself (not a pointer) with internal structures set up. Use `make` for reference types needing runtime initialization.

G14 — Errors implement `error` interface (`Error() string`). Idiomatic pattern: `if err != nil { return err }`. `errors.Is(err, target)` checks against wrapped errors in the chain. `errors.As(err, &target)` extracts a specific error type from the chain. `==` only matches exact same error instance, failing with wrapped errors.

G15 — Built-in composite types: `map` (nil), `slice` (nil), `channel` (nil), `struct` (zero values of fields). Nil maps/slices/channels are safe to read but unsafe to write without initialization. Structs are zero-initialized by default.

G16 — A race condition occurs when concurrent goroutines access shared data without synchronization, at least one being a write. `-race` flag instruments the runtime to detect conflicting accesses and prints stack traces. Fix with `sync.Mutex` (wrap shared state) or channels (communicate by sharing memory).

G17 — `select` waits on multiple channel operations, like a `switch` for channels. If multiple cases are ready, one is chosen pseudo-randomly. Timeout: `case <-time.After(d):`. Blocks until at least one case is ready or default executes.

G18 — Escape analysis determines stack vs heap allocation. Variables escape if: address taken, returned, stored in heap-allocated struct, or size unknown at compile time. Inspect with `go build -gcflags="-m"`. Matters because heap allocations trigger GC, increasing latency and reducing throughput; stack allocations are fast and zero-cost.

G19 — `reflect` inspects/modifies values at runtime. `reflect.Type` holds static type metadata; `reflect.Value` holds dynamic value and operations. Costs: slow, bypasses compile-time checks, allocates. Justified for serialization, testing, or generic frameworks. Prefer code generation (`go generate`, `stringer`) for performance-critical paths.

G20 — `go:embed` embeds compile-time files/directories into the binary. Syntax: `//go:embed pattern`. Works with single files, directories (recursive), and glob patterns. Limitations: only static files known at compile time, no runtime generation, binary size increases. Returns `embed.FS` implementing `io/fs.FS`, compatible with `http.FS`, `os.DirFS`, and standard library filesystem APIs.

R1 — Ownership is Rust's core memory management paradigm. Rules: 1) Each value has exactly one owner. 2) Only one owner exists at a time. 3) When the owner goes out of scope, the value is dropped. Prevents leaks and double-frees without a garbage collector.

R2 — `String` is an owned, heap-allocated, mutable UTF-8 string. `&str` is an immutable borrowed slice of UTF-8 bytes. Use `String` when ownership or mutation is needed; use `&str` in function signatures for zero-allocation, read-only access and maximum flexibility.

R3 — Borrowing allows accessing data without transferring ownership. Rules: 1) Either one `&mut T` or any number of `&T` references, never both. 2) All references must be valid (no dangling). The borrow checker enforces these at compile time, preventing data races and use-after-free.

R4 — `Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`). `Option<T>` represents `Some(T)` or `None`. The `?` operator propagates errors/returns early if `Err`/`None`. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```

R5 — `Box<T>`: heap-allocated, single owner, moves semantics. `Rc<T>`: reference-counted, single-threaded shared ownership. `Arc<T>`: atomic reference-counted, thread-safe shared ownership. Use `Box` for large/recursive types, `Rc` for shared read-only single-threaded, `Arc` for concurrent shared ownership.

R6 — Traits define shared behavior. Like Go interfaces but explicit. Trait object (`dyn Trait`): dynamic dispatch via vtable, heap-allocated, enables heterogeneous collections. Generic with trait bound (`T: Trait`): static dispatch, monomorphization, zero-cost, type-specific code generation.

R7 — Fails because the compiler cannot guarantee which input lifetime the returned reference will outlive. Fix by introducing a lifetime parameter: `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str { if x.len() > y.len() { x } else { y } }`. Lifetime elision doesn't apply here since both inputs could be returned.

R8 — `Send`: types safe to transfer ownership across threads. `Sync`: types safe to share references across threads. `Rc<T>` isn't `Send`/`Sync` due to non-atomic reference counting. `Arc<T>` uses atomic ref counting, making it `Send`+`Sync` (provided `T` is).

R9 — `async/await` compiles to a state machine implementing `Future`. `Future::poll` advances execution. The executor (e.g., Tokio) drives futures, handles I/O multiplexing, and schedules tasks. Differs from Go: Rust futures are lazy, require explicit executors, and lack implicit preemption (requires async-aware runtime).

R10 — `unsafe` bypasses compile-time safety checks. Three operations: 1) Dereference raw pointers. 2) Call `unsafe` functions. 3) Implement `unsafe` traits or access/modify `static mut`. Justified for FFI, low-level concurrency primitives, or performance-critical code where safety is formally proven.

R11 — Pattern matching exhaustively handles enum variants. `match` requires all variants (compiler enforces exhaustiveness, warns if missing `_`). `if let` matches a single case and ignores the rest. Compiler guarantees no unhandled variants in `match`, preventing runtime panics.

R12 — `Vec<T>`: dynamically sized heap array. `[T; N]`: fixed size, usually stack-allocated. When `Vec` capacity is exceeded, it allocates a new buffer (typically 2x capacity), copies elements, drops the old buffer, and updates the pointer.

R13 — Enums are algebraic data types that can hold data per variant, unlike C/Java enums (which are just named integers). `Option<T>` = `Some(T)` or `None`. Rust has no `null` to prevent null pointer dereferences, forcing explicit handling via `Option`/`Result`.

R14 — `impl` blocks define methods. `&self`: borrows immutably. `&mut self`: borrows mutably. `self`: takes ownership (consumes). Associated functions (e.g., `String::new()`) don't take `self`, acting like static methods or constructors.

R15 — `derive` macro auto-implements traits. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive if trait requires custom logic, contains non-derivable fields (e.g., `Fn` closures, raw pointers for `Send`/`Sync`), or violates trait invariants.

R16 — `Cow<'a, T>` (Clone-on-Write) holds either a borrowed `&'a T` or owned `T`. Useful when a function might return borrowed or owned data. Avoids allocation if input already matches desired format; only clones when mutation/modification is required.

R17 — Module system: `mod` declares a module, `use` imports paths, `pub` exposes items. File mapping: `mod.rs` or `module_name/mod.rs`. Rust 2018 changed path resolution (`crate::`, `super::`, `self::`), removed `extern crate`, and allowed modules to be declared in root or separate files more flexibly.

R18 — `Pin<T>` guarantees a value's memory location won't move. Needed for self-referential structs and async/await (futures may hold references to their own fields). `Unpin` is a marker trait indicating a type is safe to move; most types are `Unpin`, but async futures are `!Unpin`.

R19 — Macros: `macro_rules!` (declarative, pattern-matching token trees). Procedural: `derive` (struct/enum), `attribute` (custom attrs), `function-like` (invoked like functions). Hygiene ensures macros don't capture/leak identifiers from caller scope; bindings are scoped to macro expansion.

R20 — Zero-cost abstractions: high-level features compile to efficient machine code. Iterators compile to tight loops with no intermediate allocations. Generics use monomorphization to generate type-specific code at compile time. Trait static dispatch inlines calls. Achieves C-like performance while providing safety and ergonomics.
