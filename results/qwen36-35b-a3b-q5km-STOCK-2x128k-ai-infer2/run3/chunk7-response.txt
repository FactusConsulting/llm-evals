AA1 — Monoliths are single codebases deployed as one unit with shared memory/processes. Microservices are independently deployable, loosely coupled services with separate databases/processes. Microservices introduce: (1) distributed tracing/debugging complexity, (2) network latency/reliability overhead, and (3) data consistency challenges across service boundaries (distributed transactions).

AA2 — Synchronous communication blocks the caller until a response is received (request-response model). Example: REST/HTTP or gRPC. Asynchronous communication allows the caller to continue without waiting; messages are queued or published for later consumption. Example: RabbitMQ or Apache Kafka.

AA3 — A reverse proxy routes traffic, handles SSL termination, load balancing, and basic caching. An API gateway adds API-specific capabilities: rate limiting, authentication, request/response transformation, versioning, and analytics. An API gateway can functionally replace a reverse proxy, but in practice they're often layered: a reverse proxy (e.g., Nginx) handles high-performance TLS termination and DDoS protection, while the API gateway sits behind it for business logic routing.

AA4 — A Saga breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a later step fails. Choreography uses events to trigger the next step (decentralized, good for simple/decoupled flows, hard to monitor). Orchestration uses a central coordinator that commands each service (better for complex/stateful workflows, easier to debug/rollback, but introduces a coordination dependency).

AA5 — CQRS separates read and write operations into different models. Event Sourcing persists state as an immutable sequence of domain events. Combined, they solve: complex domain modeling (behavior lives in events), full auditability/temporal queries, independent scaling of read/write paths, and avoiding the "anemic domain model" problem that traditional CRUD struggles with.

AA6 — The Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failure threshold met, fail fast), Half-Open (allows test requests). Unlike retries (which assume transient faults and hammer the service), circuit breakers halt traffic entirely. Use both: retries for transient network glitches, circuit breakers for sustained backend failures to protect thread/connection pools.

AA7 — 
1. Shared DB/schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, easiest ops.
2. Shared DB/separate schema: Moderate cost, better isolation, easier per-tenant backup/restore, moderate ops.
3. Separate DB/tenant: Highest cost, best isolation/security, simplest backup/migration, highest ops complexity.
Trade-off curve: Cost ↑, Security ↑, Operational Complexity ↑, Noisy-Neighbor Risk ↓ across models 1→3.

AA8 — Eventual consistency guarantees reads will match writes after a delay; strong consistency guarantees immediate visibility. For inventory oversell prevention: use strong consistency. Architecture: Relational DB (PostgreSQL) with `SELECT FOR UPDATE` row locking or optimistic versioning. At scale: partition inventory by SKU/warehouse, use a dedicated inventory service with distributed locks or a consensus-backed store, enforce idempotent order processing, and reject stock reservations that exceed available quantity. Avoid eventual consistency for stock counts.

AA9 — A sidecar proxy is a co-located container that intercepts all inbound/outbound traffic for the main app. In Istio, Envoy handles L7 routing, retries, circuit breaking, and observability. Data plane = Envoy proxies forwarding traffic; Control plane = Istiod managing config, policies, and cert rotation. mTLS between sidecars solves transparent service-to-service authentication, automatic cert rotation, and zero-code security enforcement, whereas app-level TLS requires code changes, manual cert management, and doesn't secure internal mesh traffic automatically.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality with new services while routing traffic to the new components until the legacy system is decommissioned. Strategy: Place an API gateway in front of the .NET Framework monolith. Identify a bounded context (e.g., user management). Build the .NET 8 microservice, deploy it, and route `/api/users/**` to it via the gateway. Migrate data incrementally (dual-write or CDC). Repeat per domain until the monolith only handles legacy UI/core, then remove it.

AA11 — 12-Factor App is a methodology for building SaaS/cloud-native apps. Six factors: (1) Codebase (one code, many deploys), (2) Dependencies (explicitly declared), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/run (strictly separated stages), (6) Processes (stateless, share-nothing). They matter because they ensure portability, horizontal scalability, predictable deployments, and secure configuration management in cloud environments.

AA12 — 
- Coupling: Event-driven = loose (producers/consumers unaware); Request-driven = tight (caller knows endpoint).
- Scalability: Event-driven = highly scalable, async backpressure; Request-driven = sync bottlenecks, harder under spikes.
- Debugging: Event-driven = complex (requires replay/tracing); Request-driven = straightforward request/response logs.
- Ordering: Event-driven = partition-level guaranteed; Request-driven = naturally ordered per call.
- Failure: Event-driven = durable storage enables retry/replay; Request-driven = requires idempotency & retries.
Choose event-driven for async workflows, decoupled systems, high throughput. Choose request-driven for real-time CRUD, strict latency, simple integrations.

AA13 — A load balancer distributes incoming traffic across multiple backend servers. Layer 4 balances based on IP/port (fast, no content inspection). Layer 7 inspects HTTP headers, URLs, cookies, and content. Layer 7 is required for URL-based routing (e.g., `/api/v1` → service A, `/api/v2` → service B), SSL termination, or cookie-based session affinity.

AA14 — Message queues (RabbitMQ) deliver messages to consumers and delete them after consumption; ideal for task distribution and work queues. Log-based brokers (Kafka) append messages immutably, allowing multiple consumers to read at their own pace and replay data; ideal for event streaming and data pipelines. Pick RabbitMQ for simple routing/workers. Pick Kafka for high-throughput streaming, replayability, and data integration.

AA15 — Containers share the host OS kernel and isolate processes/filesystems; VMs run a full guest OS with hardware virtualization. Containers are lighter, start faster, use less memory, and provide consistent environments across dev/prod, making them ideal for microservices, CI/CD pipelines, and cloud-native deployments.

AA16 — Stateless services store no local session data; any instance can handle any request, making horizontal scaling trivial (add/remove instances without data migration). Example: Web API. Stateful services maintain local state/session; scaling requires data sharding/sync. Example: Database, Redis. Stateless is easier to scale because it eliminates data locality constraints.

AA17 — An ORM maps objects to database tables, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), Prisma (Node). Trade-offs: ORMs accelerate development, improve portability, and reduce boilerplate, but can generate inefficient queries, obscure performance bottlenecks, and leak abstraction boundaries. Raw SQL offers full control, optimal performance, and complex query support, but requires more code, DB-specific tuning, and slower development.

AA18 — The Bulkhead pattern isolates resources so a failure in one component doesn't exhaust shared resources and cascade. It directly enables resource isolation in microservices. Implementation: Use separate thread pools and connection pools per downstream service (e.g., via Resilience4j/Polly), or deploy critical vs non-critical services on separate node pools/availability zones. This ensures a slow payment service doesn't starve the inventory service of threads.

AA19 — OT requires a central server to transform concurrent operations; strong consistency, low storage, high server complexity, requires online connectivity. CRDTs are data structures that merge automatically without coordination; strong eventual consistency, higher structural complexity, excellent offline support, works peer-to-peer. Choose CRDTs for offline editing: they resolve conflicts locally, guarantee convergence without a server, and handle network partitions gracefully, whereas OT breaks without constant server sync.

AA20 — Challenges: polyglot libraries, overhead, high data volume. Context propagation uses W3C Trace Context or B3 headers to inject/extract trace IDs across HTTP/gRPC. Sampling: head-based (random, simple, loses context), tail-based (sample after completion, accurate, high overhead). Storage: Jaeger (OpenTelemetry-native), Tempo (S3-backed, Grafana-native); query by trace ID/service/tags. Kafka continuity: producers inject trace context into message headers, consumers extract and continue the trace. Use tail-based sampling with Kafka offsets, and fallback to correlation IDs if headers are stripped.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and low overhead. Examples: VMware ESXi, Proxmox VE, KVM. Type 2 (hosted) hypervisors run as applications on a host OS, adding overhead. Examples: VMware Workstation, Oracle VirtualBox.

OP2 — SAN provides block storage presented as local disks to servers; high performance, low latency. Protocols: Fibre Channel, iSCSI. NAS provides file-level storage over a network; easier sharing, simpler management. Protocols: NFS, SMB/CIFS. Use SAN for databases/VMs requiring raw IOPS. Use NAS for file shares, backups, and home directories.

OP3 — 3-tier: Core (high-speed backbone), Distribution (policy/routing), Access (edge ports). Leaf-spine replaces this with an all-to-all mesh between leaf (access) and spine (core) switches. It's preferred because it provides non-blocking east-west traffic, predictable latency, eliminates single points of failure, and scales linearly by adding spines/leaves, solving the distribution/core bottlenecks and spanning-tree complexity of 3-tier.

OP4 — Architecture: 3+ nodes (odd count for quorum). Shared storage: Ceph (recommended) or iSCSI/NFS with fencing. Quorum: Majority of nodes must agree to prevent split-brain. Fencing: STONITH via IPMI/iLO powers off unresponsive nodes. Failure behavior: HA manager detects node failure, runs STONITH, migrates VMs to healthy nodes, and ensures the failed node cannot corrupt shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single physical link. 802.1Q adds a 4-byte tag to Ethernet frames containing the VLAN ID. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, `ip link add link eth0 name eth0.20 type vlan id 20`, assign IPs, and enable `net.ipv4.ip_forward=1` if routing between VLANs. Alternatively, use `netplan` or `NetworkManager` with VLAN interfaces.

OP6 — RAID 1: Mirror, 50% capacity, 2-drive fault tolerance. RAID 5: Striping+parity, ~N-1 capacity, 1-drive fault, write penalty. RAID 6: Double parity, ~N-2 capacity, 2-drive fault. RAID 10: Mirror+stripe, 50% capacity, 2-drive fault (different mirrors), high IOPS. RAID Z2: ZFS double parity, flexible capacity, instant snapshots, self-healing. Choice: RAID Z2 for modern systems (data integrity, safe rebuilds, flexible capacity) or RAID 10 if raw database IOPS are critical and budget allows.

OP7 — Recursive resolvers: Internal DNS servers (Windows DNS/BIND) for clients. Authoritative: Internal zone for AD, external zone for public. Forwarders: Point to ISP/Cloudflare for external resolution. Conditional forwarding: Routes internal AD queries to internal DNS, external to forwarders. Split-horizon: Internal DNS returns private IPs, external returns public IPs for same FQDN. DNSSEC: Sign external zone, publish DS record at registrar. Laptop move: DHCP assigns internal DNS. VPN uses split-tunneling; internal queries route to corporate DNS, external to forwarders. Roaming uses cached records or DNS dynamic updates.

OP8 — Chain: Root CA (offline, self-signed, long validity) → Subordinate/Issuing CA (online, signed by root) → End-entity certs. Root CA: Air-gapped, HSM-backed. Subordinate: Issues certs, shorter validity. CRL vs OCSP: CRL = downloadable revocation list; OCSP = real-time status check. Templates: Predefine key usage, EKU, auto-enrollment policies. Auto-enrollment: AD CS pushes certs to clients/servers. Compromise: Subordinate = issue new root/sub, revoke certs, limited blast radius. Root = catastrophic, requires trusting new root everywhere, long recovery.

OP9 — MPLS: High reliability, low latency, expensive, carrier-managed. IPsec VPN: Cheap, internet-based, variable latency, manual config. SD-WAN: Orchestrates multiple links, app-aware routing, centralized management, moderate cost. WireGuard mesh: Modern crypto, fast, simple, lacks enterprise orchestration/SLA. Recommendation: SD-WAN. It optimizes VoIP latency, balances cost/reliability, centralizes management, and outperforms raw IPsec without MPLS pricing.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: Out-of-band management interfaces for remote power control, virtual console, hardware monitoring, and OS recovery. Critical when the OS/network is down, enabling recovery, OS installs, and diagnostics. Exposed to the internet: High risk of credential stuffing, console access, rootkit installation, or DoS. Must be isolated on a management network, behind a firewall, with strong auth/2FA.

OP11 — LVM: Traditional volume manager, fixed-size volumes, snapshots are copy-on-write but consume space quickly. LVM-Thin: Overprovisions storage, snapshots are cheap/fast, but can exhaust pool space and slow recovery. ZFS: Integrated FS+volume manager, copy-on-write, instant/zero-space snapshots, send/receive, self-healing. Use LVM for legacy/simple setups, LVM-Thin for flexible VM storage, ZFS for data integrity and advanced snapshot workflows.

OP12 — Stretch cluster: 2 sites (A, B) + 1 tiebreaker (C) or quorum disk. Ceph CRUSH: Map OSDs to sites, ensure replicas span sites (e.g., `host siteA`, `host siteB`). Monitors: 1 per site + 1 tiebreaker, or 3 monitors with quorum disk. Latency: <10ms ideal, <50ms max. Split-brain: Without tiebreaker, both sites think they're primary → data corruption. 2-site Ceph is bad without a tiebreaker because even split votes cause deadlock/corruption; an odd number of votes or external quorum is mandatory.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover (client broadcasts), Offer (server responds), Request (client accepts), Acknowledge (server confirms). If DHCP is unavailable and lease expires: Client assigns itself an APIPA address (169.254.x.x), resulting in limited connectivity and inability to reach internal resources.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches provide VLANs, QoS, STP, port security, ACLs, monitoring, and PoE. These features are critical for traffic segmentation, VoIP prioritization, security enforcement, and troubleshooting in enterprise environments.

OP15 — NTP synchronizes clocks over a network. Accurate time is critical for log correlation, Kerberos/AD auth, distributed DB consistency, certificate validation, and debugging. Clock drift causes Kerberos auth failures, cluster split-brain, log timeline corruption, and database replication lag/errors.

OP16 — Physical servers run directly on hardware. VMs virtualize hardware to run guest OSes. Containers isolate processes sharing the host kernel. Run bare metal for high-performance databases, real-time processing, GPU/NIC passthrough, maximum IOPS/throughput, or strict compliance/security requirements.

OP17 — UPS provides immediate battery backup for short durations (minutes). Generators provide long-duration power via fuel but have startup delay. Both are needed: UPS bridges the gap until generators start. ATS (Automatic Transfer Switch) detects utility failure, switches load to generators, and switches back when utility is restored.

OP18 — Active-passive: One node handles traffic, standby takes over on failure. Active-active: Both handle traffic, data syncs bidirectionally. PostgreSQL HA: Pacemaker/Corosync + Patroni/replication. Virtual IP floats to active node. Fencing (STONITH) via IPMI kills failed node. Streaming replication keeps standby in sync. Failover: Pacemaker detects failure, runs STONITH, promotes standby, moves VIP. Active-active requires logical replication or Citus, adding complexity.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO defined by business impact (e.g., RPO 1h, RTO 4h). Backup types: Full weekly, incremental daily. Deduplication saves space. Media: Disk for fast restore, tape/cloud for cheap offsite. Immutable backups (WORM, air-gapped) prevent ransomware encryption. Test restores via automated drills. Backup = data protection. Disaster Recovery = full process (infrastructure, data, procedures, testing) to resume operations.

OP20 — 802.1X: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP: EAP-TLS (cert-based, mutual auth, secure), PEAP (username/password, tunneled). RADIUS handles auth/authorization/accounting. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: Port stays unauthorized, traffic blocked, optional guest VLAN fallback. MAB: Switch sends MAC to RADIUS, RADIUS matches MAC to device policy, used for printers/IP phones lacking 802.1X support.
