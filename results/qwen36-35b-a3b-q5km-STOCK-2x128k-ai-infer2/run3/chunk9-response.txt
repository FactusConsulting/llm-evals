SC1-A
The pods fail because the namespace Pod Security Standard (PSS) was upgraded from `baseline` to `restricted`. The `restricted` profile enforces `runAsNonRoot: true` AND requires an explicit `runAsUser` with a non-zero UID. When `runAsUser` is omitted, Kubernetes defaults to UID 0 (root). The new base image (`cgr.dev/chainguard/static:latest`) also defaults to root. The admission controller or kubelet rejects the pod spec or refuses to start the container, causing repeated restarts and `CrashLoopBackOff`. `baseline` allowed root containers; `restricted` explicitly forbids them without explicit non-root UID configuration.

SC1-B

```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.securityContext}'
```

SC1-C
**Image-level fix:** Rebuild the base image with a non-root user (`RUN useradd -u 1000 appuser && USER 1000`). Pin the base image by digest, not tag.
**Manifest changes:** Add `securityContext.runAsUser: 1000` (or `runAsGroup`/`fsGroup`) to all pod/deployment specs. Ensure `runAsNonRoot: true` is explicit.
**CI gate:** Add a Kyverno/OPA policy that rejects deployments lacking `runAsUser: <non-zero>` or where the image digest resolves to root. Integrate `trivy` or `cosign` to verify image provenance and fail if `USER` is root.
**Rollout:** Update deployment manifests with the fixed image and securityContext. Trigger a rolling update (`kubectl rollout restart` or GitOps sync). Set `maxSurge=25%` and `maxUnavailable=0`. Tune readiness probes to prevent premature restarts during container startup. Monitor `CrashLoopBackOff` and `PodSecurityViolation` events.

SC2-A
Cross-region streaming replication is asynchronous by default. Promoting a replica severs the replication stream, meaning any WAL not yet shipped or replayed is permanently lost. The data loss window equals the replication lag at promotion time. To quantify: check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica, or query `pg_stat_replication` on the primary for `write_lag`, `flush_lag`, and `replay_lag`. If lag was >1s at failover, that window of writes is lost.

SC2-B
1. Import the promoted replica: `terraform import aws_db_instance.new_primary <new-arn>`
2. Update TF code to reference the new ARN and remove/replace the old instance resource.
3. Remove old state: `terraform state rm aws_db_instance.old_primary`
4. Update dependent resources (SGs, Route53, parameter groups) to use the new ARN or a variable.
5. Validate: `terraform plan -target=aws_db_instance.new_primary`
6. Apply: `terraform apply`
Use `terraform state mv` if renaming resources. Never run `terraform apply` on the old ARN to avoid destruction.

SC2-C
**RDS Proxy vs PgBouncer:** RDS Proxy handles connection pooling at the DB layer, automatically routes to the new primary after failover, and supports IAM auth. PgBouncer requires app-level DNS updates or connection string changes.
**Route53:** Use latency-based or failover routing with health checks pointing to the RDS endpoint. Enable `Failover` routing policy with `EvaluateTargetHealth=true`.
**App retry logic:** Implement exponential backoff with jitter, idempotent write patterns, and circuit breakers.
**RPO < 1s:** Standard RDS cross-region async cannot guarantee this. **Aurora Global Database** is recommended: it uses dedicated storage replication with ~1s RPO, automatic failover in <1 min, and handles cross-region latency via a global cluster architecture. It eliminates manual promotion and WAL shipping delays.

SC4-A
1. **Sticky sessions/local memory:** Kubernetes is ephemeral; local memory is lost on pod restart. *Fix:* Externalize sessions to Redis/ElastiCache.
2. **Local NFS mount:** Pods schedule across nodes; local paths are inaccessible. *Fix:* Use `nfs.csi.k8s.io` StorageClass or migrate to cloud-native storage (EFS/S3).
3. **On-prem Oracle 19c:** Licensing, network latency, and driver compatibility. *Fix:* Migrate to AWS RDS/Aurora or use DB proxy with persistent connectivity; handle licensing separately.
4. **IBM MQ integration:** Network segmentation and client library compatibility. *Fix:* Deploy MQ client pods, expose MQ via Kubernetes Service, use MQ JMS client libraries, and ensure VPC/VPN routing.
5. **Bare-metal performance:** Kubernetes overhead and resource limits may increase p99 latency. *Fix:* Use dedicated nodes, tune JVM flags (`-XX:+UseContainerSupport`), set accurate requests/limits, and enable HPA.

**SQL Lock Diagnostic:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid, blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement, blocking_activity.query AS current_statement_in_blocking_process
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC6-C
**Direct Connect:** Dedicated 10Gbps+ link, low latency, high throughput. Cost: high upfront + monthly. Fits zero-trust (app-layer encryption still required). Routing: BGP over DX, requires on-prem router config.
**Second VPN + ECMP:** Scales bandwidth, lower cost. Encryption overhead limits throughput. Failover via BGP/ECMP. Routing: multiple tunnels, BGP multipath.
**Tailscale/Netbird:** Zero-trust mesh, easy setup, but not enterprise-grade for 10Gbps dark fiber. Throughput/latency limits. Routing: overlay network, no BGP.
**Recommendation:** Direct Connect for core production traffic (meets bandwidth/latency), Tailscale/Netbird for dev/staging or specific micro-segments. DX requires BGP configuration; VPN ECMP requires multiple tunnels + BGP; mesh requires no routing changes but uses overlay.

SC10-C
**Failover sequence:**
1. Health checks detect site down (multiple probes, quorum-based, >3 consecutive failures).
2. DNS failover (GSLB) updates records to Dallas.
3. Patroni promotes standby (etcd leader election, synchronous commit ensures zero loss).
4. Redis Sentinel promotes master.
5. RabbitMQ federation syncs queues.
6. MinIO site replication catches up (background sync).
7. Update OpenTofu state (GitOps syncs cluster config to new primary).
**Split-brain:** Use fencing (STONITH), quorum-based DCS, disable writes on old primary via firewall/iptables.
**Failback:** Reverse replication, sync data, verify integrity, DNS switch back, update OpenTofu state, decommission old primary.
