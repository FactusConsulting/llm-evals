**CL1** — IaaS provides virtualized compute, network, and storage where you manage the OS, middleware, runtime, data, and applications (e.g., AWS EC2). PaaS provides a managed runtime and middleware where you only manage applications and data (e.g., AWS Elastic Beanstalk). SaaS delivers a fully managed application where you only manage user access and configuration (e.g., AWS WorkSpaces or Google Workspace).

**CL2** — The Shared Responsibility Model divides security: the provider secures the cloud infrastructure (physical, global network, hypervisor, managed service components), while you secure what you put in it. For IaaS VMs, the provider manages physical hosts and hypervisor; you manage guest OS, patches, network config, data, and apps. For managed Kubernetes, the provider secures the control plane, etcd, and node OS; you manage worker node workloads, RBAC, network policies, secrets, and data. For SaaS like M365, the provider secures the app, infra, and compliance; you manage identities, access policies, data classification, and MFA.

**CL3** — A VPC is an isolated virtual network. A subnet is an IP range within a VPC, typically zonal. Security Groups (SGs) are stateful, instance-level firewalls that only allow rules and automatically permit return traffic. Network ACLs (NACLs) are stateless, subnet-level firewalls that support allow/deny rules and require explicit rules for both inbound and outbound traffic. Traffic flows: resource → SG (stateful) → NACL (stateless) → network. Stateful filters track connection state; stateless filters evaluate each packet independently.

**CL4** — A landing zone is a pre-configured, secure multi-account foundation with networking, IAM, logging, and guardrails. Organizational Units (OUs) logically group accounts (e.g., dev, prod, sandbox, shared services). Guardrails (SCPs/Policy Frameworks) enforce compliance, budget limits, and region restrictions. Shared networking uses Transit Gateway (AWS) or Hub-and-Spoke (Azure) for centralized inter-VPC/VNet routing and on-prem connectivity. Centralized logging aggregates CloudTrail, VPC Flow, and security logs to a dedicated security account. Single-account approaches cause excessive blast radius, permission sprawl, billing opacity, compliance violations, and lack of environment isolation.

**CL5** — IaC manages infrastructure via declarative/programmatic code. Terraform/OpenTofu: declarative HCL, provider-agnostic, state-driven; best for multi-cloud, large teams, broad provider support. Pulumi: imperative/declarative using general-purpose languages; best for complex logic, existing dev teams, dynamic infra. CloudFormation/Bicep: AWS-native declarative; Bicep improves syntax; best for AWS-only shops. Crossplane: Kubernetes-native IaC using CRDs; best for GitOps/K8s-centric teams wanting a unified control plane.

**CL6** — HPA scales pods based on CPU/memory/custom metrics. VPA recommends/sets optimal resource requests/limits per pod. Cluster Autoscaler adds/removes nodes based on pending pods/resource pressure. KEDA scales based on external event triggers (queues, HTTP, DB, cron). Use KEDA over HPA when scaling must be driven by external events (e.g., queue depth, scheduled jobs, HTTP spikes) rather than internal resource utilization. HPA is better for steady-state, resource-based scaling.

**CL7** — Define RPO/RTO first. Active-active runs both regions live; lower RPO/RTO, higher cost/complexity. Active-passive runs one region, standby the other; higher RPO/RTO, lower cost. DB replication: sync ensures strong consistency but limits region distance/latency; async reduces latency but risks data loss on failover. DNS failover (Route53/Traffic Manager) uses health checks to route traffic. State must be externalized (DB, object storage, distributed cache). Cost: active-active doubles infra + data transfer; active-passive saves cost but requires warm/cold standby. Pilot light: core infra (DB, minimal compute) running, scaled up on failover (low cost, moderate RTO). Warm standby: scaled-down but fully functional replica (faster failover, moderate cost). Multi-site active-active: full production capacity in both (fastest failover, highest cost).

**CL8** — GitOps uses Git as the single source of truth. Declarative desired state is pushed to Git; operators continuously reconcile cluster state to match. ArgoCD: UI-heavy, app-of-apps pattern, push/pull hybrid. FluxCD: Git-native, pull-only, tightly integrated with GitHub/GitLab, CLI/automation focused. Secrets: Sealed Secrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from Vault/SM), Vault CSI driver. Drift: controllers detect manual changes, auto-revert to Git state on sync, and alert. Prevents configuration drift and enforces auditability.

**CL9** — Use a StatefulSet for stable network IDs and ordered deployment/termination. Configure PV/PVC with `local` storageClass and `volumeBindingMode: WaitForFirstConsumer` to bind to the node with local disk. Use a headless service (`clusterIP: None`) for direct pod DNS resolution. Init containers handle filesystem prep, dependency checks, and config validation before the main app starts. Mount ConfigMaps as volume mounts at specific paths using `subPath`. Define a PodDisruptionBudget (`minAvailable` or `maxUnavailable`) to ensure minimum replicas during voluntary disruptions. Note: local storage limits pod mobility; ensure backup/restore strategies align with this constraint.

**CL10** — A K8s Service Account is a native identity with no cloud permissions by default. Workload Identity (GCP/Azure) and IRSA (AWS) map K8s SAs to cloud IAM identities without static keys. Mounting cloud credentials in pods is bad practice: static keys leak easily, complicate rotation, enable excessive permissions, and lack audit trails. Workload identity federation solves this via OIDC: pods exchange short-lived, scoped tokens with the cloud provider. No static secrets, automatic rotation, least privilege per workload, and full auditability.

**CL11** — Object storage (S3/Blob) uses HTTP APIs, scales infinitely, stores unstructured data, and offers 99.999999999% durability. Use for backups, static sites, data lakes. Block storage (EBS/Managed Disk) provides low-latency, random I/O attached to a single VM, 99.99% durability within an AZ. Use for OS, databases, high-perf apps. File storage (EFS/Azure Files) offers shared NFS/SMB access, POSIX/Windows compliance, 99.999999999% durability. Use for shared configs, home dirs, legacy apps. Block is AZ-bound; object/file are regional (configurable cross-region).

**CL12** — Zero-trust K8s assumes breach and verifies every request. Network policies enforce default-deny with explicit pod-to-pod/namespace rules. A service mesh (Istio/Linkerd) provides mTLS, identity-based routing, and observability. Pod identity (IRSA/Workload Identity) replaces static credentials. Admission controllers (OPA/Kyverno) enforce policies at admission (no privileged pods, required labels, resource limits). Image signing (Cosign/Notary) + Kyverno blocks unsigned/untrusted images. Falco monitors runtime behavior (shell exec, file changes, network calls). Secrets managed via External Secrets Operator + Vault/SM, never in env vars. Differs from perimeter security by micro-segmenting at workload level, continuous validation, and eliminating implicit trust based on network location.

**CL13** — A CDN is a distributed edge cache network that serves content closer to users. DNS routes requests to the nearest edge node; if cached, it serves immediately; otherwise, it fetches from the origin and caches based on TTL. Cloud-native services: AWS CloudFront, Azure CDN, Fastly, Cloudflare. Use a CDN for static assets, media, API caching, DDoS mitigation, and global latency reduction. Serve directly from origin for dynamic, personalized, or cache-busting content. CDN reduces origin load, improves latency, and adds security layers.

**CL14** — A region is a geographic area containing multiple Availability Zones (AZs). An AZ is one or more discrete data centers with independent power, cooling, and networking. Deploying across multiple AZs protects against single data center failure, ensuring high availability. Zonal resources (EBS, EC2, GKE nodes) are tied to a specific AZ and must be deployed per AZ. Regional resources (S3, RDS cross-AZ, ALB, CloudFront) span multiple AZs and provide built-in redundancy.

**CL15** — Managed database services (RDS, Cloud SQL, Azure SQL) abstract infrastructure management. The provider handles provisioning, OS patching, backups, replication, monitoring, failover, and storage scaling. Running a DB on a VM requires you to manage the OS, DB software, backup schedules, HA architecture, scaling, and security patches. Managed services reduce operational overhead, improve reliability, and accelerate deployment, but cost more and limit low-level access.

**CL16** — IAM Users are human/service identities. Groups bundle users/roles for policy assignment. Roles provide temporary credentials for services/workloads via `assume role`. Policies (JSON/YAML) define allowed/denied actions, resources, and conditions. Least privilege means granting only the permissions necessary to perform a task. Apply it via scoped policies, role-based access, just-in-time elevation, regular access reviews, avoiding wildcards (`*`), and using conditions (IP, MFA, time).

**CL17** — Serverless computing provides managed, auto-scaling, pay-per-use compute without server management. AWS Lambda, Azure Functions, and GCP Functions share core concepts but differ in runtime support, cold start behavior, and ecosystem integrations. Cold starts are initial latency when a container spins up; they matter for latency-sensitive apps or high-frequency invocations. Mitigate with provisioned concurrency, keep-warm patterns, and optimized code. Serverless is a poor fit for long-running processes, stateful apps, predictable high-throughput (reserved instances cheaper), strict compliance/network isolation needs, or when vendor lock-in is a primary concern.

**CL18** — Ingress Resource: standard K8s API requiring an ingress controller (NGINX, ALB); TLS terminates at the controller. Gateway API: newer, structured, multi-protocol, better RBAC; TLS terminates at the gateway/controller. Cloud LB annotations: direct cloud LB integration (AWS ALB, GCP ILB); TLS terminates at the cloud LB. Service Mesh Ingress: mesh-level gateway (Istio); mTLS termination, advanced traffic management. Use Gateway API over Ingress for multi-team environments, fine-grained RBAC, protocol flexibility (HTTP, TCP, TLS), and future-proofing. Ingress is simpler but limited and legacy.

**CL19** — RI vs SP vs Spot: RIs (1-3 yr commitment, predictable workloads), SPs (flexible commitment, compute/db/storage), Spot (interruptible, 60-90% discount, fault-tolerant/batch). Right-size via utilization monitoring and auto-scaling. Tier storage (S3 Intelligent-Tiering, Glacier, delete orphaned snapshots/EBS). Detect idle resources via CloudWatch/Azure Monitor and cost explorer. Implement FinOps: cross-functional team, tagging strategy, monthly reviews, cost accountability. Showback/chargeback: tag by team/project, allocate via billing reports, internal dashboards. Tools: AWS Cost Explorer, Azure Cost Management, Kubecost/OpenCost, CloudHealth, automated alerts, budget thresholds, FinOps meetings.

**CL20** — Multi-cloud avoids lock-in via abstraction: Kubernetes as common runtime (EKS/AKS/GKE), Terraform for provider-agnostic IaC, service mesh/API gateways for portability. Networking: Cloud VPN, Interconnect/ExpressRoute, global LBs, DNS routing. Identity: OIDC federation, centralized IAM, cross-cloud SSO. Trade-offs: higher complexity, data egress costs, inconsistent features, operational overhead vs risk mitigation and best-of-breed services. Justified for regulatory/data sovereignty, catastrophic vendor outage risk, specific service needs, or M&A. Unnecessary for most startups/SMBs, when single-cloud maturity isn't reached, or when complexity/cost outweighs benefits.

**OT1** — The Purdue Model (ISA-95) is a hierarchical framework for enterprise/OT integration. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, DCS). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations management (MES, production planning). Level 4: Business planning (ERP, finance, supply chain). Level 5: Enterprise/Cloud (analytics, AI, external partners).

**OT2** — IT networks prioritize confidentiality, integrity, and availability (CIA), with fast patching, frequent updates, and user-centric design. OT networks prioritize availability, safety, and process integrity, with real-time deterministic communication, legacy systems, and long lifecycles. Standard IT patching is unsafe for OT: systems often can't tolerate downtime, lack patch management tools, require validation/testing, and updates may cause process disruption or safety incidents.

**OT3** — An IDMZ is a segmented network between IT and OT, acting as a controlled buffer. Traffic allowed: primarily IT → IDMZ (data requests, production orders) and IDMZ → OT (restricted, via firewall/data diode, limited protocols like OPC UA/MQTT). OT → IDMZ allows monitoring data only. Direct L4 (IT) to L1 (control) connectivity is dangerous because it bypasses security controls, exposes critical systems to internet/IT threats, enables lateral movement, and risks catastrophic physical impact.

**OT4** — Modbus TCP: L1/L2, simple request/response, legacy PLCs. OPC UA: L2/L3, secure, platform-independent, modern standard. EtherNet/IP (CIP): L1/L2, industrial Ethernet, real-time, Allen-Bradley dominant. PROFINET: L1/L2, Siemens ecosystem, deterministic real-time Ethernet. MQTT: L2/L3/L4, lightweight publish/subscribe, IoT/cloud integration, not for real-time control.

**OT5** — A data diode is hardware-enforced unidirectional data flow, physically preventing reverse traffic. A firewall is bidirectional, inspects traffic, and allows/denies based on rules. Use a data diode when strict one-way data flow is required (e.g., OT monitoring data to IT, no commands back). Limitation: cannot inspect return traffic, no bidirectional communication, less flexible than firewalls, and restricted to specific use cases.

**OT6** — Data flow: PLC/RTU → OPC UA Server (historian/SCADA) → Edge Gateway (protocol translation, buffering, security) → MQTT Broker (secure, TLS) → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: OT network (L1/L2) → IDMZ/Edge Gateway (firewall/data diode) → Secure MQTT (mTLS, auth) → Cloud VPC → Analytics. Segment OT, use encrypted channels, authenticate all endpoints, monitor edge devices, and enforce least privilege.

**OT7** — IEC 62443 defines security zones (logical groups of assets with similar requirements) and conduits (secured communication paths between zones). Zone definition: based on function, risk, and access needs. Conduit: secured with firewalls, diodes, encryption. Model: Zone 1 (Corporate/IT L4) → Conduit 1 (Firewall/DMZ) → Zone 2 (Engineering/SCADA L3) → Conduit 2 (Strict firewall/data diode) → Zone 3 (PLCs/HMIs L1/L2) → Conduit 3 (Isolated network) → Zone 4 (SIS, physically/logically isolated, independent power/network). Enforce least privilege, monitor conduits, segment by function.

**OT8** — VLAN design: separate VLANs per production line, HMI, SCADA, engineering, vendor access. Tagged traffic. Firewall placement: core firewall between IT/OT, edge firewalls per VLAN/zone, DMZ for external access. Switch architecture: managed L3 switches, port security, 802.1X, VLANs, QoS for control traffic. Remote access: jump hosts in DMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: phased rollout, parallel run, maintenance windows, backup configs, rollback plan, test in staging, coordinate with production schedule.

**OT9** — BPCS (Basic Process Control System) handles normal operation (PLC/DCS). SIS (Safety Instrumented System) handles emergency shutdown, independent of BPCS. IEC 61511 is the standard for SIS functional safety, defining SIL ratings, lifecycle, and risk assessment. The SIS network must be air-gapped/isolated to prevent cyber attacks on BPCS/IT from compromising safety functions, ensuring fail-safe behavior. If ransomware reaches the SIS, safety functions may fail, leading to catastrophic accidents, environmental damage, or loss of life.

**OT10** — PLC: Programmable Logic Controller. Discrete control, real-time, rugged, used for machine/line control. DCS: Distributed Control System. Centralized control architecture, integrated I/O, used for continuous processes (chemical, oil/gas). SCADA: Supervisory Control and Data Acquisition. Software/hardware for monitoring, data collection, HMI, remote control across wide areas. They coexist: PLCs/DCS handle control, SCADA provides supervisory layer, HMIs for operators, historians for data. Common in modern plants.

**OT11** — Remote access: jump hosts in DMZ, MFA, session recording, time-limited/vendor-scoped access, no direct OT access. RDP directly to an HMI from corporate is unacceptable because it exposes OT directly to the corporate network, bypasses segmentation, increases attack surface, violates the Purdue model, and enables lateral movement to critical control systems.

**OT12** — Detection: passive IDS (Snort/Suricata), network anomaly detection, asset inventory (passive scanning), OT-specific SIEM rules. IR steps: contain (isolate segments), assess impact, preserve evidence, eradicate, recover, post-incident review. Coordination: notify control room, switch to manual/local control if needed, ensure safe process state, communicate with operators. Operator role: monitor process, execute manual overrides, report anomalies, follow emergency procedures, maintain safety. Safe operations: prioritize process safety over IT containment, use fail-safe modes, maintain communication, avoid actions causing physical harm.

**OT13** — HMI (Human-Machine Interface): operator interface for monitoring/control, real-time data, alarms, trends. Engineering Workstation: used by engineers for programming, configuration, diagnostics, firmware updates, logic editing. Difference: HMI is operational (read-only or limited control); engineering workstations are for development/maintenance (full access), not for daily operations.

**OT14** — Historian: time-series database for process data (temperatures, pressures, flows). Optimized for high write/read rates, compression, long-term storage. Importance: trend analysis, compliance, troubleshooting, optimization, predictive maintenance. Plant historian (L3): stores raw/process data, real-time, OT-focused. Enterprise historian (L4): aggregates, correlates with business data, supports analytics/BI, IT-focused.

**OT15** — Ladder logic: graphical programming language mimicking relay circuits. Uses contacts, coils, timers, counters. Executes on PLCs. Dominant because it's intuitive for electricians, decades of training/tooling exist, it's deterministic and reliable, backward compatible, and widely supported by hardware vendors.

**OT16** — RTU (Remote Terminal Unit): designed for harsh environments, long-distance communication (serial, cellular, satellite), telemetry, SCADA integration. PLC: designed for factory automation, local I/O, fast cycle times, complex logic. RTUs deployed in pipelines, water distribution, wind farms, remote sites where communication range and ruggedness matter more than local I/O density.

**OT17** — Analog signals: continuous voltage/current representing process variables. Digital signals: discrete on/off or binary data. 4-20mA preferred over 0-20mA because 4mA is a "live zero" indicating wire break/failure (0mA = fault). It also provides power to field devices and is more noise-immune over long distances.

**OT18** — OT asset inventory: complete list of hardware, software, firmware, network connections. Foundation for risk assessment, patching, segmentation, compliance. Tools: passive monitoring (packet capture, protocol analysis), active scanning (limited, controlled). Active scanning is dangerous because it can crash legacy devices, cause process disruption, trigger alarms, or overwhelm networks. Use passive only, or highly controlled active scans during maintenance.

**OT19** — MITRE ATT&CK for ICS maps adversary tactics/techniques specific to OT. 5 tactics/examples: 1. Reconnaissance (T1592: gather network info). 2. Resource Development (T1583: acquire tools/exploits). 3. Initial Access (T1195: phishing, supply chain compromise). 4. Execution (T1059: run malicious code on PLC/HMI). 5. Impact (T1499: disrupt process, sabotage). Differs from Enterprise ATT&CK by focusing on physical processes, safety, legacy protocols, real-time constraints, and control logic rather than user endpoints. Use to map defenses, identify gaps, prioritize monitoring, simulate attacks, and align with IEC 62443.

**OT20** — Log collection: passive taps, OT-friendly agents, protocol-specific collectors, no active scanning, buffer to avoid impact. SIEM integration: normalize OT logs (Syslog, OPC UA, Modbus), correlate with IT logs, use OT-specific parsers. Detection rules: baseline normal behavior, alert on anomalous commands, unauthorized firmware changes, unusual protocol usage, after-hours access. Triage: OT engineers + IT analysts, prioritize safety/process impact, validate with control room, avoid false positives via whitelisting/maintenance windows. Staffing: IT analysts for general threats, OT engineers for process/protocol expertise, clear escalation. False positives: common due to batch jobs/maintenance; mitigate with baselining, tuning, OT context. Unauthorized firmware change: immediate isolation, verify with engineering, rollback to known good, investigate source, update change management, enhance monitoring.
