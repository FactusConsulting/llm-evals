CL1 — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, runtime, data, and apps. Example: AWS EC2. PaaS provides runtime, middleware, and OS; you manage apps and data. Example: Google App Engine. SaaS provides fully managed applications; you only consume and configure user settings. Example: AWS WorkSpaces.

CL2 — The Shared Responsibility Model divides security: the provider secures the cloud (hardware, global infrastructure, hypervisor, physical security); you secure what's in the cloud. IaaS VM: Provider = infra/hypervisor; You = OS, patches, network, IAM, data. Managed K8s: Provider = control plane, node OS/hypervisor; You = worker apps, network policies, IAM, secrets, pod security. SaaS (M365): Provider = app, infra, compliance config; You = user accounts, data, access policies, MFA, data classification.

CL3 — VPC is an isolated virtual network. Subnet is an IP range within a VPC, tied to an AZ. Security Groups (SG) are stateful firewalls at the instance/pod level (allow rules only, auto-allow return traffic). NACLs are stateless firewalls at the subnet level (allow/deny rules, must explicitly allow inbound/outbound). Traffic flows: SG → NACL → resource. Stateful tracks connection state; stateless evaluates each packet independently.

CL4 — A landing zone is a pre-configured, secure multi-account baseline with networking, IAM, logging, and guardrails. OUs group accounts by function/environment. Guardrails (SCPs/Policy Frameworks) enforce compliance (encryption, MFA, region limits). Shared networking (Transit Gateway/Azure Hub-and-Spoke) centralizes inter-VPC/VNet and on-prem routing. Centralized logging aggregates to a dedicated account/service. Single-account causes blast radius, permission sprawl, billing opacity, compliance risk, and deployment bottlenecks.

CL5 — IaC manages infrastructure via versioned, automated definitions. Terraform/OpenTofu: Declarative HCL, provider-agnostic, large ecosystem. Best for multi-cloud, complex state, team collaboration. Pulumi: Imperative/Declarative, general-purpose languages. Best for devs, complex logic, dynamic provisioning. CloudFormation/Bicep: AWS-native declarative. Bicep improves readability. Best for AWS-only shops. Crossplane: K8s-native IaC extending K8s API. Best for GitOps infra, multi-cloud via K8s control plane.

CL6 — HPA scales pods based on CPU/memory/custom metrics (reactive). VPA adjusts pod resource requests/limits (doesn't change replica count). Cluster Autoscaler adds/removes nodes based on unschedulable pods. KEDA scales pods based on external event queues (Kafka, RabbitMQ, HTTP). Use KEDA over HPA when scaling should be driven by event backlog/throughput rather than internal resource utilization.

CL7 — Define RPO (max data loss) and RTO (max downtime) based on business impact. Active-active: both regions serve traffic, lower RPO/RTO, higher cost/complexity. Active-passive: one serves, one standby, higher RPO/RTO, lower cost. DB replication: sync (strong consistency, latency-limited) vs async (lower latency, potential data loss). DNS failover (Route53/Traffic Manager) uses health checks + low TTL for rapid routing. Externalize state (Redis, DynamoDB, S3). Cost: active-active doubles infra + data transfer; active-passive saves ~40-60%. DR models: pilot light (core infra running, scale up on failover), warm standby (scaled-down prod ready), multi-site active-active (full prod in both).

CL8 — GitOps uses Git as single source of truth; operators continuously reconcile cluster state to Git manifests. ArgoCD: UI-heavy, push/pull, app-of-apps pattern. FluxCD: Git-native, pull-only, tightly integrated with Git providers, CLI/automation focused. Secrets: Sealed Secrets (encrypt in Git, decrypt in cluster), External Secrets Operator (sync from AWS Secrets Manager/Vault), Vault (dynamic secrets, auth). Manual drift is overwritten on next sync; operators enforce desired state, providing auditability and automatic remediation.

CL9 — Use a StatefulSet for stable pod names, ordered deployment/termination, and stable network IDs. PV/PVC with `local` storageClass + `volumeBindingMode: WaitForFirstConsumer` ensures low-latency node-local binding. Headless service (`clusterIP: None`) provides DNS for direct pod-to-pod communication. Init containers prepare filesystems or fetch configs. ConfigMaps mounted as volumes place config files at exact paths. Pod Disruption Budgets (`minAvailable`/`maxUnavailable`) prevent voluntary disruptions from taking down the app. Externalize state where possible, but respect legacy filesystem constraints.

CL10 — K8s Service Account is a native pod identity, not cloud-attached. Workload Identity (GCP/Azure) and IRSA (AWS) map K8s service accounts to cloud IAM identities. Mounting cloud credentials in pods is bad practice: long-lived secrets risk exfiltration, hard to rotate, violates least privilege, breaks audit trails. Workload identity federation uses OIDC to exchange short-lived K8s tokens for cloud IAM tokens dynamically, eliminating static keys and enabling scoped, auditable access.

CL11 — Object storage (S3/Blob): HTTP API, flat namespace, metadata-rich, best for unstructured data/backups/static content. Durability: 11 9s. Availability: 99.99%+. Block storage (EBS/Managed Disk): Low-latency, mounted as drive, random R/W, best for OS/databases/VMs. Durability: 99.999%. Availability: AZ-tied. File storage (EFS/Azure Files): NFS/SMB, hierarchical, shared access, best for shared configs/legacy apps. Durability: 11 9s. Availability: Regional.

CL12 — Zero-trust K8s: Default-deny Network Policies for micro-segmentation. Service mesh (Istio/Linkerd) for mTLS, traffic control, observability. Pod identity (IRSA/Workload Identity) for cloud access without node credentials. Admission controllers (OPA/Kyverno) enforce policies at admission (no privileged pods, required labels). Image signing (Cosign/Notary) + Kyverno blocks unsigned images. Runtime security (Falco) detects anomalous behavior. Secrets via External Secrets Operator + Vault/KMS. Differs from perimeter model by verifying every request, assuming breach, enforcing least privilege at workload level, and eliminating internal trust.

CL13 — CDN is a distributed network of edge servers caching content closer to users. DNS routes to nearest edge; edges serve cache, fetch misses from origin. Services: CloudFront (AWS), Azure CDN, Fastly. Use CDN for static/dynamic content delivery, DDoS mitigation, global latency reduction, and origin offloading. Use origin for dynamic processing, origin-of-truth, and heavy writes.

CL14 — Region: geographic area with multiple AZs. AZ: one or more discrete data centers with independent power/cooling/networking. Deploy across AZs to survive data center failures, meet SLAs, and enable active-active architectures. Zonal resources (EBS, EC2) are tied to one AZ; failover requires recreation. Regional resources (RDS Multi-AZ, ELB, S3) span AZs, providing built-in redundancy.

CL15 — Managed DB (RDS/Cloud SQL/Azure SQL) abstracts provisioning, patching, backups, HA, scaling, and monitoring. Provider handles OS patches, DB engine updates, replication, failover, storage provisioning, backup/restore, and alerting. You handle schema, queries, IAM access, data classification, and application connectivity.

CL16 — IAM Users: human/service identities with long-term credentials. Groups: collections for policy assignment. Roles: temporary credentials for entities (users, services, external accounts), assumed via STS. Policies: JSON documents defining permissions. Least privilege: grant only necessary permissions. Apply via scoped policies, role boundaries, just-in-time access, deny-by-default, and regular reviews.

CL17 — Serverless: event-driven, managed compute where provider handles infra scaling/patching; pay per use. Lambda (AWS), Azure Functions (Azure), GCF (GCP) share models but differ in ecosystem/tooling. Cold starts: initialization time after idle; matters for latency-sensitive apps. Mitigate with provisioned concurrency, smaller packages, language choice. Poor fit: long-running processes, stateful apps, predictable high throughput (reserved VMs cheaper), strict compliance/network isolation, vendor lock-in concerns.

CL18 — Ingress Resource: standard K8s API, requires controller (NGINX/ALB), TLS termination at controller. Gateway API: newer, more expressive, separates routing (Gateway) from backend (HTTPRoute), better multi-team ownership, TLS at Gateway. Cloud LB Annotations: directly provision cloud LB (ALB/ILB), TLS at LB, simpler but less portable. Service Mesh Ingress: mesh gateway handles mTLS, traffic splitting, observability, TLS at mesh. Use Gateway API for complex routing, multi-tenant environments, standardized API, and future-proofing.

CL19 — RI vs SP vs Spot: RIs (1-3 yr, predictable workloads), SPs (flexible commitment, compute/db/storage), Spot (interruptible, 60-90% discount, fault-tolerant/batch). Right-sizing: monitor utilization, downsize overprovisioned, use VPA/HPA. Storage tiering: S3 Intelligent-Tiering, lifecycle policies to Glacier, delete orphaned snapshots/EBS. Idle detection: CloudHealth, Cost Explorer, Azure Advisor, GCP Recommender, tagging. FinOps: cross-functional team, cost accountability culture, forecasting, anomaly detection. Showback/chargeback: tag-based allocation, visibility vs accountability. Tools/processes: automated tagging policy, CI/CD cost gates, monthly FinOps reviews, RI optimizer, spot integration, anomaly alerts.

CL20 — Multi-cloud: abstraction via K8s (EKS/AKS/GKE), Terraform for portability, service mesh/API gateways. Networking: Cloud VPN, Direct Connect/ExpressRoute, global LBs (complex routing, latency, cost). Identity: OIDC federation, centralized IAM (Okta/Azure AD), cross-cloud trust. Trade-offs: adds complexity, cost, operational overhead, data gravity issues, API divergence. Theoretical benefits (avoid lock-in, best-of-breed) often outweighed by reality. Justified: regulatory/data residency, catastrophic vendor outage risk, specific service needs, M&A. Unnecessary: most startups/SMBs, homogeneous workloads, limited engineering bandwidth. Single-cloud with strong architecture is usually superior.

OT1 — Purdue Model (ISA-95) is a hierarchical framework for industrial enterprise integration. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, DCS). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations management (MES, production planning). Level 4: Business planning (ERP, finance, supply chain). Level 5: Enterprise/Corporate IT (optional, often merged with L4).

OT2 — IT networks prioritize confidentiality, integrity, availability (CIA), fast patching, and user-centric updates. OT networks prioritize availability, safety, and real-time deterministic control. OT systems often lack patch mechanisms, cannot be rebooted, or risk process disruption/safety hazards. OT prioritizes stability and safety over latest security fixes.

OT3 — IDMZ is a segmented buffer between IT and OT. Traffic is strictly controlled, typically one-way or filtered bidirectional (IT→OT for commands/updates, OT→IT for data/status). Allowed: OPC UA, MQTT, HTTP/HTTPS, protocol-aware filtered traffic. Direct L4→L1 connectivity bypasses segmentation, exposes control systems to IT threats, enables lateral movement, and risks safety/process disruption.

OT4 — Modbus TCP: L1/L2, simple, unencrypted, legacy PLCs. OPC UA: L2/L3, secure, platform-independent, modern standard. EtherNet/IP (CIP): L1/L2, industrial Ethernet, Rockwell/Allen-Bradley. PROFINET: L1/L2, real-time Ethernet, Siemens-dominated. MQTT: L2/L3/L4, lightweight publish/subscribe, cloud/edge integration, secured with TLS.

OT5 — Data diode: hardware-enforced unidirectional data flow, physically prevents reverse traffic. Firewall: software/hardware, bidirectional, stateful inspection, allows/denies based on rules. Use diode when strict one-way flow is required (OT→IT monitoring, no IT→OT commands). Limitation: cannot allow any return traffic (acknowledgments, commands, updates). Firewalls allow controlled bidirectional flow but are theoretically bypassable via software flaws.

OT6 — Flow: PLCs → Historian (L3) → OPC UA Server → Edge Gateway (translation/buffering) → MQTT Broker → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: L2/L3 firewall between OT and DMZ; DMZ terminates OPC UA/MQTT with TLS/mutual auth; edge uses HSM, signed firmware, isolated segment; cloud uses VPC, IAM, encryption. Ensure OT isolation, no direct cloud exposure, strictly filtered paths.

OT7 — IEC 62443 zones: logical groups of assets with similar security requirements/risk profiles. Conduits: secured communication paths between zones. Model: Zone 1 (Corporate IT/L4), Zone 2 (Engineering Workstations/L3), Zone 3 (SCADA/Historian/L2), Zone 4 (PLCs/HMIs/L1), Zone 5 (SIS, isolated). Conduits: Z1→Z2 (secure VPN), Z2→Z3 (firewall, protocol filtering), Z3→Z4 (firewall/DMZ), Z4↔Z5 (data diode or strict firewall, minimal traffic). Enforce least privilege, segment traffic, monitor conduits.

OT8 — VLAN design: segment by function/process (e.g., VLAN 10: Line 1 PLCs, 20: Line 2, 30: HMIs, 40: SCADA, 50: Engineering). Firewall placement: core between IT/OT, edge between VLANs, DMZ for remote/cloud. Switch architecture: managed L3, port security, 802.1X (if supported), disable unused ports. Remote access: jump host in DMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: phased rollout, parallel run, maintenance windows, rollback plan, engage vendors, never stop production during cutover.

OT9 — SIS: independent system bringing process to safe state on failure. BPCS: normal control system for process optimization. IEC 61511: safety lifecycle standard defining SIL requirements. SIS must be air-gapped/isolated to prevent common-cause failures (cyber attacks, power loss). Ransomware on SIS could disable safety functions, causing catastrophic failure, environmental damage, or loss of life. SIS is designed fail-safe, but cyber compromise can bypass/manipulate it if not isolated.

OT10 — PLC: programmable logic controller, discrete control, fast, rugged, used for machine/line control (L1). DCS: distributed control system, centralized architecture with distributed controllers, optimized for continuous processes (chemical, oil/gas) (L1/L2). SCADA: supervisory control and data acquisition, software/hardware for monitoring, data collection, HMI, remote control (L2). They coexist: PLCs/DCS handle control, SCADA supervises.

OT11 — Remote access: jump hosts in DMZ, MFA required, session recording for audit, time-limited/role-based vendor access, break-glass procedures. RDP directly to HMI from corporate network is unacceptable: exposes OT directly to IT, bypasses segmentation, increases attack surface, violates Purdue model, enables lateral movement.

OT12 — Detection: network IDS/IPS, anomaly detection, passive asset inventory, SIEM integration. Response: isolate compromised segment, preserve logs, activate IR team, coordinate with control room (safety first), engage OT engineers. Coordination: manual override if needed, verify safe process state, notify regulators if required. Safe operations: maintain manual control, verify SIS/BPCS integrity, avoid automated changes. Plant operator role: monitor physical process, execute manual safety procedures, report anomalies, do not rely on compromised digital systems. Critical for safety and bridging cyber/physical domains.

OT13 — HMI: Human-Machine Interface, graphical display for operators to monitor/control process. Role: real-time visualization, alarms, manual overrides, trend analysis. Differs from engineering workstation: HMI is for operators (runtime), engineering workstation is for programmers/configurers (offline/online editing, logic changes, firmware updates).

OT14 — Historian: time-series database storing process data (temperatures, pressures, flows) at high frequency. Importance: trend analysis, compliance, optimization, troubleshooting, predictive maintenance. Plant historian (L3): real-time, low latency, local, process-focused. Enterprise historian (L4): aggregated, longer retention, business analytics, integrated with ERP/BI.

OT15 — Ladder logic: graphical programming language mimicking relay circuits, executed by PLCs. PLCs scan inputs, execute logic cyclically, update outputs. Dominance: familiar to electricians, easy to troubleshoot, deterministic, widely supported, legacy integration, safety-certified.

OT16 — RTU: Remote Terminal Unit, designed for long-distance communication, harsh environments, telemetry, SCADA integration. PLC: designed for local, fast, deterministic control. RTUs deployed in pipelines, water distribution, wind farms, remote sites where communication latency/distance is high and logic complexity is lower.

OT17 — Analog signals: continuous voltage/current (4-20mA, 0-10V) representing process variables. Digital signals: discrete on/off or communication protocols. 4-20mA preferred over 0-20mA: 4mA represents 0% (live zero), detects wire breaks (0mA = fault), more noise-immune, works over long distances.

OT18 — OT asset inventory: complete list of hardware, firmware, network configs, communication flows. Foundation: can't secure what you don't know; enables patching, vulnerability management, segmentation, compliance. Tools: passive monitoring (packet capture, protocol analysis), active scanning (limited, risky). Active scanning dangerous: can crash legacy devices, cause process disruption, trigger alarms, expose network to attacks. Passive is preferred.

OT19 — MITRE ATT&CK for ICS maps adversary tactics/techniques specific to ICS/OT. Tactics/examples: 1. Reconnaissance (1046.001 - Network Service Discovery), 2. Initial Access (1195 - Supply Chain Compromise), 3. Execution (1059 - Command and Scripting Interpreter), 4. Persistence (1053 - Service Registration/Execution), 5. Impact (1489 - Data Manipulation). Differs from enterprise ATT&CK: focuses on safety, physical processes, legacy protocols, real-time constraints, and operational impact rather than just data/confidentiality. Use to map defenses, identify gaps, prioritize controls, simulate attacks, align with IEC 62443.

OT20 — Log collection: passive network taps, OPC UA/MQTT log forwarders, lightweight SIEM agents, edge buffering. SIEM integration: normalize OT logs (Syslog, CEF, OT schemas), correlate with IT logs. OT detection rules: baseline behavior, protocol anomalies, unauthorized PLC changes, unusual HMI access, SIS bypass attempts. Triage: OT-specific playbooks, involve OT engineers early, distinguish maintenance from attacks. Staffing: IT analysts for general alerts, OT engineers for protocol/process expertise, cross-training. False positives: high due to legacy systems/maintenance; mitigate with baselining, allowlists, OT-aware tuning. Unauthorized firmware change: isolate PLC/HMI, verify backup, restore known good, investigate source, update change management, enhance admission controls, notify safety team.
