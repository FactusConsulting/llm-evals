K1 — A **Deployment** manages stateless workloads with interchangeable pods, random names, and no guaranteed startup order. A **StatefulSet** manages stateful workloads with stable, unique network IDs, ordered deployment/scaling, and stable persistent storage per pod.

K2 — `kube-proxy` creates iptables or IPVS rules mapping the Service’s ClusterIP:Port to the backend pod IPs. When traffic hits the ClusterIP, kube-proxy performs DNAT to randomly select one healthy pod IP, routing the request directly to it.

K3 — **PersistentVolume (PV)** is a cluster-wide storage resource (statically provisioned or dynamically created). **PersistentVolumeClaim (PVC)** is a user’s request for storage. **StorageClass (SC)** defines the provisioning template (e.g., SSD, NFS). A PVC binds to a PV; if no static PV exists, the SC dynamically provisions one for the PVC.

K4 — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` for OOMKilled, exit codes, or probe failures. 3. Verify resource limits/requests vs actual usage. 4. Check app dependencies (DB connectivity, missing config files, invalid entrypoint).

K5 — CoreDNS provides internal DNS resolution for `svc.cluster.local` and pod FQDNs. If CoreDNS pods are down, internal service discovery fails (services/pods can’t resolve each other by name), but direct IP communication and external DNS remain unaffected.

K6 — The scheduler uses **filtering** to discard nodes that fail requirements (insufficient resources, taints, affinity, node selectors). **Scoring** ranks remaining nodes. Factors: 1. LeastRequestedPriority (balances CPU/MEM), 2. NodeAffinity/TaintToleration, 3. InterPodAffinity/AntiAffinity, 4. Resource allocation fairness.

K7 — Yes, it will schedule. 3.5GB + 256Mi (~0.25GB) = 3.75GB < 4GB. At runtime, if it uses 600Mi (>512Mi limit), the kubelet OOMKills the container. It restarts, and if the usage persists, it enters CrashLoopBackOff.

K8 — Client → External LB (routes to Ingress Controller IP) → Ingress Controller (NGINX) parses Ingress resource → matches host/path → forwards to Kubernetes Service → Service resolves to Endpoints (pod IPs) → kube-proxy/iptables/IPVS DNATs traffic to pod → pod receives HTTP request.

K9 — A **NetworkPolicy** restricts pod-to-pod and pod-to-external traffic. Default: all traffic allowed. When applied: denies all traffic by default, then only permits flows explicitly allowed by the policy’s ingress/egress rules.

K10 — **RollingUpdate** gradually replaces old pods with new ones (zero downtime). **Recreate** terminates all old pods before starting new ones (downtime). Choose Recreate for stateful apps, database migrations, or when shared storage/state requires exclusive access.

K11 — A **namespace** is a logical cluster partition for resource isolation. Defaults: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed state, events, conditions, resource usage, volume mounts, probe status, and node assignment. `kubectl get pod` only shows basic status, age, and restart count.

K13 — A **ConfigMap** stores non-confidential configuration data. Pods consume it via: 1. Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`). 2. Volume mounts (files appear in the container filesystem).

K14 — **ClusterIP**: internal-only virtual IP. **NodePort**: exposes the service on each node’s IP at a static port (30000-32767). **LoadBalancer**: provisions a cloud provider LB, exposing the service externally with a public IP.

K15 — A **DaemonSet** ensures one pod runs on every node (or subset via selector). Use for logging/monitoring agents, CNI plugins, or storage daemons. A Deployment runs a fixed replica count regardless of node count.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Use taints/tolerations for dedicated hardware (GPUs, spot instances). Use affinity for co-location (app + cache on same zone/node).

K17 — An **Operator** is a custom controller that manages complex stateful applications using CRDs and custom reconciliation logic. Unlike standard controllers (which sync simple desired vs actual state), Operators automate backups, upgrades, failover, and scaling. Solves manual ops for stateful workloads.

K18 — etcd uses **Raft** for linearizable reads/writes. If quorum is lost, the cluster becomes read-only/unwritable. With 2/3 nodes lost, quorum cannot be formed. Recovery: add a 4th node, form a new 2-node cluster (1 surviving + 1 new), then restore from the latest etcd snapshot.

K19 — **Role/ClusterRole** define permissions (verbs/resources). **RoleBinding/ClusterRoleBinding** bind roles to users/groups/serviceaccounts.
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev-ns
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader-binding
  namespace: dev-ns
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` means if a domain has <5 dots, Kubernetes appends cluster suffixes (`svc.cluster.local`, etc.) before querying external DNS, causing multiple failed queries. Fix: set `dnsConfig: { options: [{ name: "ndots", value: "2" }] }` in the pod spec, or use FQDNs with a trailing dot.

D1 — **Merge** preserves history with a merge commit. **Rebase** rewrites history into a linear timeline. Avoid rebasing on shared/public branches or when multiple developers are actively committing to the same branch.

D2 — **TCP**: connection-oriented, reliable, ordered, flow/congestion control. **UDP**: connectionless, unreliable, low-latency. TCP: HTTP, SMTP. UDP: DNS, VoIP, video streaming.

D3 — A **race condition** occurs when concurrent threads/processes access shared state without synchronization, causing unpredictable results. Example: two threads incrementing a shared counter without a mutex, resulting in lost updates.

D4 — **Symmetric**: same key for encryption/decryption (fast). **Asymmetric**: public/private key pair (secure key exchange). TLS uses asymmetric encryption for the handshake/key exchange, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates an immutable **image layer**. Layer caching skips unchanged layers during rebuild. Best practice: order instructions from least to most frequently changing (e.g., copy dependency manifests first, install deps, then copy source code).

D6 — Order: 1. Check service health & endpoint readiness. 2. Review upstream app logs for errors/timeouts. 3. Verify rate limiting/throttling or circuit breakers. 4. Check resource exhaustion (CPU/memory) or dependency health (DB/cache).

D7 — **CAP theorem**: a distributed system can only guarantee two of three: Consistency, Availability, Partition tolerance. **CP**: distributed SQL (CockroachDB, HBase) – prioritizes data accuracy over availability during network splits. **AP**: DNS, Cassandra, DynamoDB – prioritizes availability, accepts eventual consistency.

D8 — **Horizontal scaling**: add more nodes/instances. **Vertical scaling**: increase CPU/RAM of existing node. Horizontal scaling requires: stateless design, shared-nothing architecture, distributed caching, message queues, consistent hashing, and externalized sessions/state.

D9 — An **environment variable** is a dynamic named value that affects process behavior. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict key-value syntax, no comments. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: universal parsing, strict schema validation. YAML advantage: readability, less verbose, easier for configuration files.

D11 — A **REST API** is an architectural style using HTTP methods. **GET**: retrieve resource. **POST**: create new resource. **PUT**: update/replace resource. **DELETE**: remove resource.

D12 — **Version pinning** locks dependencies to exact versions (e.g., `package@1.2.3`). Ensures reproducible builds, prevents unexpected breaking changes from upstream updates, and simplifies debugging.

D13 — **Compiled**: source code is translated to machine code before execution (C, Rust). **Interpreted**: source code is executed line-by-line by a runtime (Python, JavaScript). Note: many modern languages use JIT compilation (hybrid).

D14 — **Reverse proxy**: sits in front of servers, routes client requests to backend. Use: Nginx (SSL termination, load balancing), HAProxy (high-performance TCP/HTTP routing). **Forward proxy**: sits in front of clients, routes outbound requests. Use: corporate proxy (content filtering, caching).

D15 — A **deadlock** occurs when two+ processes wait indefinitely for each other’s resources. Coffman conditions: 1. Mutual exclusion. 2. Hold and wait. 3. No preemption. 4. Circular wait.

D16 — **Eventual consistency** guarantees all replicas converge if no new updates. Cassandra uses vector clocks/Lamport timestamps for read-after-write. Tunable consistency levels: `ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`. Setting read consistency to `QUORUM` ensures the latest write is seen.

D17 — **mTLS** authenticates both client and server via X.509 certificates. Handshake: ClientHello → ServerHello+Cert → ServerKeyExchange → ClientKeyExchange+Cert → verify certs → derive session keys. Used in: service meshes (Istio/Linkerd), internal microservices, zero-trust networks.

D18 — A **hash table** maps keys to values via a hash function. Collision resolution: **chaining** (linked lists per bucket), **open addressing** (linear/quadratic probing, double hashing). Avg time: O(1). Worst case: O(n) when all keys collide.

D19 — A **circuit breaker** prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal), **Open** (fail fast after threshold), **Half-open** (test with limited requests). Works with retries: exponential backoff reduces load during recovery, but the circuit breaker trips faster if retries fail repeatedly.

D20 — **Optimistic**: assumes no conflict, checks at commit (row versioning/ETag). Fails on conflict, triggers retry. Best for low contention. **Pessimistic**: locks resources during read/write (`SELECT FOR UPDATE`). Best for high contention or critical financial transactions.
