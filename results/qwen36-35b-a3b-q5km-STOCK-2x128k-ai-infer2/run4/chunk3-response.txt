T1 — `tofu plan` calculates the desired state vs current state and outputs a dry-run execution plan without making changes. `tofu apply` executes that plan, creating, updating, or destroying infrastructure.

T2 — State is a JSON file mapping configuration to real-world resource IDs and attributes. Remote state stores this file externally (S3, GCS, etc.), enabling team collaboration, state locking, CI/CD integration, and preventing local state loss or corruption.

T3 — `count` uses integer indexing and recreates resources when items are removed from the middle. `for_each` uses a map or set, preserving state for unchanged items when adding/removing. `for_each` is preferred when resources have unique identifiers or when dynamic sets are needed.

T4 — OpenTofu detects drift by comparing the state file against live provider APIs during `tofu plan`. It shows the resource as "modified outside of OpenTofu". You can ignore it, overwrite it with `tofu apply`, or refresh state with `tofu refresh`. Best practice: avoid manual changes or use drift detection.

T5 —
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.key
  }
}
```

T6 — `terraform_remote_state` reads an entire state file, causing tight coupling, performance overhead, and potential secret exposure. Outputs explicitly expose only needed values. Recommended: use direct `module` references for intra-workspace sharing. For cross-workspace, use `data "terraform_remote_state"` with explicit `outputs` mapping to avoid reading the full state.

T7 — The `null_resource` triggers immediately, but the RKE2 control plane isn't ready, so the kubeconfig isn't generated yet. `remote-exec` also runs before the actual cluster resource is fully provisioned. Fix: Add `depends_on = [rke2_cluster_resource]`, add a readiness check (e.g., `local-exec` with `sleep` or `wait_for` on port 6443), and ensure the output is computed only after the cluster reports healthy.

T8 — CLI `tofu import` requires manual config writing and is error-prone. The `import` block (1.5+) is declarative, placed in config, and safely maps existing resources to state during `tofu plan/apply`. It supports multiple resources, better error handling, and CI/CD integration, though it still doesn't auto-generate full resource blocks.

T9 — A `variable` is an external input passed into a module/root. An `output` is a value exposed by a module/root to consumers (other modules, CLI). Variables are writable inputs; outputs are read-only exports.

T10 — A provider is a plugin that interacts with cloud/API backends. Running `tofu plan` without `tofu init` fails because providers aren't downloaded, plugins aren't initialized, and the dependency graph can't be built.

T11 — `.terraform.lock.hcl` records exact provider versions, checksums, and dependencies. Committing it to VCS ensures reproducible environments, prevents provider drift, and guarantees team/CI use identical versions.

T12 — `tofu destroy` deletes all resources tracked in state. Target a single resource: `tofu destroy -target=resource_type.resource_name`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to dynamically fetch the latest Ubuntu AMI instead of hardcoding or managing it as a resource.

T14 — Variables are external inputs validated and typed. Locals are internal computed values used for DRY code, transformations, or conditional logic. Use locals for derived values; use variables for user-defined inputs.

T15 — `create_before_destroy`: Creates new before old (zero-downtime). Use for LBs/DNS. `prevent_destroy`: Blocks deletion/replacement. Use for critical data. `ignore_changes`: Ignores drift on specific attributes. Use for auto-generated fields (timestamps, cloud-init output).

T16 — The `moved` block renames/moves resources in state without destroying/recreating. Syntax: `moved { from = "old_addr"; to = "new_addr" }`. It preserves state and dependencies during module refactoring or naming changes.

T17 — OpenTofu builds a DAG of resources based on references. Implicit dependencies are auto-detected via variable references. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, reducing parallelism. Use sparingly to avoid bottlenecks; prefer implicit references.

T18 — 1. `tofu plan -refresh=false`: Skips state refresh. Tradeoff: May miss drift. 2. Modularize & split state: Reduces scope per run. Tradeoff: Complex management. 3. Use `data` sources instead of managed resources: Faster reads. Tradeoff: Less control. 4. Optimize backend (S3+DynamoDB, GCS): Faster state I/O. Tradeoff: Infrastructure cost.

T19 — State locking prevents concurrent writes. If a crash leaves a lock, future runs block. Break it with `tofu force-unlock <lock_id>`. Risks: Data corruption, lost changes, or inconsistent state if another process is actively writing.

T20 — 1. Backup local state. 2. Add `backend "s3"` config to code. 3. Run `tofu init -migrate-state` and confirm. 4. Verify with `tofu state list` and check S3/DynamoDB. 5. Delete local `terraform.tfstate` after confirmation. The state file is atomically copied to S3; DynamoDB handles locking.

A1 — A task is a single module execution. A role is a reusable collection of tasks, handlers, vars, and templates. A playbook is a YAML file that maps tasks/roles to hosts, defining execution order and variables.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_os_family }}`.

A3 — `command`: Runs without shell features (safest). `shell`: Runs via `/bin/sh`, supports pipes/redirects. `raw`: Runs via SSH without Python, no module support (for minimal/legacy systems).

A4 — Ansible checks desired vs actual state and only acts if different. Idempotent: `apt: name=htop state=present`. Non-idempotent: `shell: echo "x" > /tmp/f.txt` (overwrites every run). Use `copy`/`template` instead.

A5 —
```yaml
- name: Install htop on Debian
  apt: name=htop state=present
  when: ansible_os_family == "Debian"

- name: Install EPEL on RedHat
  yum: name=epel-release state=present
  when: ansible_os_family == "RedHat"

- name: Install htop on RedHat
  yum: name=htop state=present
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (lowest to highest): role defaults → inventory vars → host_vars → group_vars → extra_vars → role vars → `set_fact` → registered vars → task vars.

A7 — Use `serial: 3` in the playbook. Group nodes in inventory (e.g., `rke2_agents`). Add `wait_for_connection` and a readiness check (e.g., `shell: systemctl is-active rke2-server` or `uri` on port 6443) before proceeding to the next batch.

A8 — Ansible vaults files, not individual lines. To encrypt a single variable, use `ansible-vault encrypt_string 'my_secret' --name 'my_secret'` and paste the vaulted assignment into a plain vars file, or vault the entire file with `ansible-vault encrypt file.yml`.

A9 — An inventory lists hosts/groups Ansible manages. Static inventory is a hardcoded file (INI/YAML). Dynamic inventory is a script/API that generates hosts at runtime (cloud providers, CMDBs).

A10 — `ansible webservers -a "df -h"` (uses shell by default) or `ansible webservers -m shell -a "df -h"`.

A11 — A handler is a task that only runs when notified. It runs at the end of the play (or after each task if `flush_handlers` is used). Trigger with `notify: handler_name` in a regular task.

A12 — `ansible.cfg` sets Ansible defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `stdout_callback`.

A13 — `register` captures task output into a variable. Use it in subsequent tasks via `{{ var_name.stdout }}` or `when: var_name.rc == 0`.

A14 — `import_tasks` is static (evaluated at parse time); conditions apply to the whole file. `include_tasks` is dynamic (evaluated at runtime); conditions apply per task. Use `import` for performance/static structure, `include` for dynamic/conditional loading.

A15 — Ansible Galaxy is a repository for roles/collections. `requirements.yml` lists them with names/versions. Install with `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins handle host communication. `ssh`: Default for Linux/Unix via SSH. `local`: Runs on the control node. `network_cli`: Uses Netmiko for network devices (Cisco, Juniper).

A17 — `delegate_to` runs a task on a different host. `run_once` runs it on one host and applies to all. Example:
```yaml
- name: Get remote IP
  ansible.builtin.command: hostname -I
  register: remote_ip
- name: Write config on control node
  ansible.builtin.copy:
    content: "server={{ remote_ip.stdout }}"
    dest: /tmp/config.yml
  delegate_to: localhost
  run_once: true
```

A18 — 1. Increase `forks`: More parallel tasks. Tradeoff: Higher control node CPU/memory. 2. Enable `pipelining`: Reduces SSH connections. Tradeoff: Requires `requiretty` off in sudoers. 3. Fact caching (Redis/Memcached): Skips fact gathering. Tradeoff: Stale facts if hosts change. 4. Mitogen or `strategy: free`: Mitogen speeds execution significantly; `free` runs tasks as hosts finish. Tradeoff: Mitogen needs compatibility checks; `free` breaks play ordering/debugging.

A19 — `{{ }}`: Output/variables. `{% %}`: Control flow (loops/conditionals). `{# #}`: Comments. Template:
```jinja2
upstream backend {
{%- for server in backend_servers %}
    server {{ server }}; # health check: {{ server }}:8080
{%- endfor %}
}
```

A20 — Use `serial: 1` or `20%`. Pre-task: Deregister from LB or stop app. Deploy: Copy code, restart service. Health check: `uri` module polling `/health` with `retries`/`delay`. Post-task: Re-register to LB. Rollback: Wrap in `block/rescue`. If health check fails, `rescue` reverts code, restarts old version, and re-registers to LB.
