SC1-A
The pods fail because the namespace's Pod Security Standard (PSS) enforcement changed from `baseline` to `restricted`. The `restricted` policy mandates that containers must run as a non-root user, explicitly requiring `securityContext.runAsUser` to be set to a non-zero UID. Without an explicit `runAsUser`, Kubernetes defaults to UID 0 (root). The new base image (`cgr.dev/chainguard/static:latest`) also defaults to `USER root`. When the policy enforcement tightened, the admission controller may have allowed the pods (if the policy was applied post-deployment or via mutation), but the containers now run as root in an environment that expects non-root execution. The application likely crashes because it attempts to bind to privileged ports (<1024), write to read-only filesystem layers, or lacks permission to access required resources as root, triggering `CrashLoopBackOff`.

SC1-C
**Immediate Fix:** Rolling update with `maxSurge=1` and `maxUnavailable=0`. Add `securityContext.runAsUser: 1000` and `runAsGroup: 1000` to all deployments.
**Image Fix:** Update Dockerfiles to `USER 1000` and ensure the app runs correctly as non-root. Pin base image digests.
**CI Gate:** Add a Trivy/Checkov step that fails on `runAsUser` missing or `runAsUser: 0`. Integrate an admission controller (Kyverno/OPA) that rejects deployments violating `restricted` PSS.
**Rollout:** Use a rolling update strategy. Monitor readiness probes. If 30% fail, pause, apply manifest fixes, and resume. No downtime if readiness probes are correctly configured and `maxSurge` allows replacement pods to come up before old ones terminate.

SC2-A
Cross-region streaming replication is asynchronous by default. Promoting a read replica means any WAL segments not yet shipped from `us-east-1` are permanently lost. The data loss window equals the replication lag at promotion time. PostgreSQL ships WAL asynchronously; if the primary fails before the replica receives and replays the latest WAL, those transactions are lost. To quantify: check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica, or monitor `pg_stat_replication` lag metrics. A lag of >1s implies potential data loss of that magnitude.

**Architectural Solution:**
- **CQRS:** Separate read/write paths. Checkout reads from a read replica or cache; reconciliation writes to primary.
- **Read Replica:** Run reconciliation job against a read replica to avoid locking production tables.
- **Bulkhead Isolation:** Configure separate connection pools for serving vs. background jobs. Use `pgbouncer` or app-level pool limits.

SC6-C
**Comparison:**
- **AWS Direct Connect:** Dedicated 10G/100G link. Low latency, high throughput, predictable cost. Fits ZT: encrypts at rest/transit, requires BGP routing. Best for enterprise scale.
- **Second VPN + ECMP:** Two IPsec tunnels with equal-cost multipath. Cheap, scales bandwidth, but VPN overhead adds latency/jitter. Routing: BGP with multiple tunnels. Fits ZT but less performant than DX.
- **Tailscale/Netbird:** WireGuard-based mesh overlay. Easy setup, automatic NAT traversal, built-in ZT (ACLs, SSO). Bandwidth limited by WireGuard overhead (~1-2Gbps practical). Routing: overlay routing, no BGP needed. Good for hybrid but not ideal for 10G dark fiber backbone.
**Recommendation:** Direct Connect for primary backbone, keep VPN as backup. Mesh tools for developer/remote access only.

sort -t$'\t' -k2 -nr | head -20 | while read -r metric count; do

SC10-C
**Failover Orchestration Sequence:**
1. **Detection:** Health checks (heartbeat every 5s). Site down = 3 consecutive failures + cross-site latency >500ms.
2. **DNS Failover:** GSLB (Route53/Azure DNS) switches traffic to Dallas. TTL=60s.
3. **Patroni Promotion:** Standby detects primary loss, promotes via etcd quorum. Synchronous commit ensures zero data loss.
4. **Redis/RabbitMQ/MinIO:** Sentinel promotes Redis master. RabbitMQ federation catches up. MinIO site replication continues.
5. **State Update:** Ansible/Terraform updates OpenTofu state to reflect new primary.
**Split-Brain Prevention:** Quorum-based DCS (etcd/Patroni), fencing scripts, manual override via CLI. No automatic promotion if both sites are reachable.
**Failback:** Once Chicago recovers, reconfigure as standby. Sync data via Patroni async replication. Verify consistency. Cutover traffic back via GSLB. Update state. Monitor for 24h.
