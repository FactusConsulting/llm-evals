AA1 — A monolith is a single codebase deployed as one unit with shared processes and databases. Microservices decompose the system into independently deployable, loosely coupled services with separate databases/processes. Microservices introduce: (1) network latency and failure handling (partial outages, retries, circuit breakers), (2) distributed data consistency (no ACID across services, requires sagas/eventual consistency), and (3) operational complexity (orchestration, CI/CD pipelines, distributed tracing, service discovery).

AA2 — Synchronous communication blocks the caller until a response is received, enabling real-time interaction but creating tight coupling and cascading failure risk. Example: REST/gRPC. Asynchronous communication decouples sender and receiver; messages are queued or published and processed later, improving resilience and scalability but introducing eventual consistency. Example: RabbitMQ (queue) or Kafka (event log).

AA3 — A reverse proxy routes traffic, terminates TLS, load balances, and caches. An API gateway adds API-specific capabilities: rate limiting, authentication/authorization, request/response transformation, versioning, and analytics. An API gateway can technically replace a reverse proxy, but they serve different architectural layers. Best practice: use a lightweight reverse proxy (NGINX/Traefik) at the edge for TLS/SSL and DDoS protection, and an API gateway for business logic routing and policy enforcement.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a later step fails. Choreography-based sagas use events to trigger the next step; they are decentralized and loosely coupled but hard to monitor and debug. Orchestration-based sagas use a central coordinator that explicitly directs each step; they are easier to audit, rollback, and manage complex flows. Use choreography for simple, low-coupling workflows; orchestration for complex, multi-step, compliance-heavy processes.

AA5 — CQRS separates read (query) and write (command) operations into distinct models. Event Sourcing stores state changes as an immutable sequence of events. They are paired because commands emit events, which are used to rebuild read models. This combination solves: (1) complete auditability and temporal queries, (2) independent scaling of reads/writes, (3) complex domain logic without CRUD state loss, and (4) eventual consistency patterns that traditional CRUD cannot efficiently support.

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. States: Closed (normal operation), Open (failure threshold met, fast-fail), Half-Open (allows limited probes to test recovery). It differs from retry+backoff because retries assume transient failures and keep hammering the service; circuit breakers halt traffic to prevent resource exhaustion. Use both together: retry with exponential backoff for transient glitches inside Closed/Half-Open states, and circuit breaker to open when failures persist, protecting downstream systems.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, low ops overhead.
2. Shared DB, separate schema: Moderate cost, better isolation, easier per-tenant backup/restore, moderate ops complexity.
3. Separate DB per tenant: Highest cost, maximum security/isolation, trivial backup/restore, high ops complexity, lowest noisy-neighbor risk.
Trade-offs: Cost scales with isolation. Security/compliance requirements dictate schema vs DB separation. Operational complexity and noisy-neighbor risk decrease as isolation increases.

AA8 — Eventual consistency guarantees reads will converge after a delay; strong consistency guarantees immediate visibility across replicas. For inventory oversell prevention: use strong consistency (or linearizable reads/writes). Data store: Relational DB (PostgreSQL) with row-level locking or a strongly consistent distributed DB (CockroachDB/Spanner). Patterns: Optimistic concurrency (version columns), distributed locks (Redis/ZooKeeper), or queue-based reservation with idempotent processing. At scale, partition inventory by SKU/warehouse, enforce strong-consistency reservations, and async-sync to read replicas.

AA9 — A sidecar proxy is a co-located container that intercepts all inbound/outbound traffic for a service. In Istio, Envoy acts as the data plane proxy handling routing, mTLS, retries, and metrics. Istiod (Pilot, Citadel, Galley) is the control plane pushing config, policies, and certificates. Data plane = traffic handling; control plane = configuration/cert management. mTLS between sidecars solves: transparent east-west security without app code changes, automatic cert rotation, identity-based service auth, and prevention of eavesdropping/sniffing in transit. App TLS requires manual cert management and doesn't uniformly secure internal traffic.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is removed. Strategy: Place an API gateway in front of the .NET Framework monolith. Identify a bounded context (e.g., user auth, billing). Build the new .NET 8 microservice. Route specific paths/traffic to it via the gateway. Implement dual-write or CDC for data migration. Use feature flags for safe rollout. Repeat per module. Decommission monolith routes as functionality is fully migrated.

AA11 — 12-Factor App methodology standardizes cloud-native apps. Six factors: (1) Codebase (one dep per app), (2) Dependencies (explicitly declared), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless, exec model). They matter because they enable horizontal scaling, zero-downtime deploys, secure config management, reproducible builds, and resilient, cloud-agnostic operations.

AA12 — 
- Coupling: Event = loose; Request = tight.
- Scalability: Event = high throughput, async scaling; Request = synchronous scaling, connection limits.
- Debugging: Event = hard (distributed state, replay needed); Request = easier (request/response trace).
- Ordering: Event = partition-level guaranteed; Request = per-request, no inherent ordering.
- Failure: Event = retry/dead-letter, idempotency; Request = timeouts, retries, circuit breakers.
Choose Event for async workflows, high throughput, decoupled domains, audit trails. Choose Request for real-time APIs, synchronous validation, low-latency CRUD.

AA13 — A load balancer distributes traffic across backend servers. Layer 4 balances based on IP/port (fast, no content inspection). Layer 7 balances based on HTTP headers, URLs, cookies (slower, intelligent routing). Layer 7 is required for SNI-based SSL termination, path-based routing (`/api` vs `/static`), or header-based routing.

AA14 — A message queue (RabbitMQ) uses point-to-point/pub-sub, deletes messages after consumption, and supports complex routing/exchanges. A log-based broker (Kafka) appends messages to immutable, partitioned logs, persists them, and allows replay. Pick RabbitMQ for task queues, complex routing, and lower volume. Pick Kafka for event streaming, replayability, high throughput, and log aggregation.

AA15 — Containers use OS-level virtualization, sharing the host kernel, making them lightweight. VMs use hardware virtualization with full guest OSes, making them heavier. Containers are popular for microservices due to fast startup, low overhead, consistent environments, immutable deployments, and native Kubernetes/cloud support.

AA16 — Stateless services don't store local session data; each request is independent. Stateful services maintain local state. Stateless services scale horizontally easily because instances can be added/removed without data migration or session affinity. Examples: Stateless: Web API, Nginx. Stateful: Redis, PostgreSQL, WebSocket server.

AA17 — An ORM maps objects to database tables, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORM = faster development, safety, portability, but can generate inefficient queries and complicate complex SQL. Raw SQL = full control, optimal performance, but verbose, error-prone, and DB-specific.

AA18 — The Bulkhead pattern isolates resources (threads, connections, memory) to prevent a single component's failure from exhausting shared resources. Implementation: Use separate thread pools and connection pools per downstream service. In Kubernetes, deploy critical vs non-critical workloads on separate node pools with resource quotas, or use sidecar proxies to enforce per-service rate limits and connection limits.

AA19 — OT transforms concurrent operations on a central server; guarantees strong consistency, low storage, high server complexity, requires online connectivity. CRDTs are data structures that merge automatically without coordination; guarantee eventual consistency, higher storage/structure complexity, work fully offline, and converge deterministically. For offline editing, choose CRDTs because they enable conflict-free merging on client devices without server coordination, essential for offline-first architectures.

AA20 — Distributed tracing challenges include polyglot stacks, network hops, async boundaries, and overhead. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject/extract trace IDs across HTTP/gRPC. Sampling: Head-based (random, cheap, loses rare traces) vs Tail-based (collects all, samples after, accurate but high overhead). Storage/Querying: Jaeger (OpenTelemetry) or Tempo (Grafana, object storage) index spans for trace ID/service queries. For Kafka, trace context must be serialized into message headers; consumers extract and continue the trace, ensuring continuity across async boundaries.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and low overhead. Examples: VMware ESXi, Proxmox VE, KVM, Hyper-V. Type 2 (hosted) hypervisors run as applications on a host OS, offering ease of use but higher overhead. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block storage, presenting disks directly to servers for high performance and low latency. Protocols: Fibre Channel, iSCSI. NAS provides file storage over a network, enabling easy sharing. Protocols: NFS, SMB/CIFS. Use SAN for databases and VMs. Use NAS for file shares, backups, and home directories.

OP3 — 3-tier architecture: Access (edge) → Distribution (policy/aggregation) → Core (backbone). It's hierarchical and can create spine bottlenecks and poor east-west scaling. Leaf-spine is a flat, all-to-all mesh architecture. It solves 3-tier oversubscription, provides predictable low latency, and scales east-west traffic non-blocking by adding spines without redesign.

OP4 — Proxmox HA cluster: 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing (STONITH via IPMI/APC) powers off failed nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. During node failure: HA manager detects failure, fences the node, and restarts VMs on surviving nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, assign IP, repeat for other VLANs. Alternatively, use NetworkManager or `vconfig`.

OP6 — RAID 1: Mirror, 50% capacity, 2-drive fault tolerance. RAID 5: Striping + single parity, 1-drive fault, read-heavy. RAID 6: Double parity, 2-drive fault, higher write penalty. RAID 10: Mirror + stripe, 50% capacity, 2-drive fault (different mirrors), best write perf. Z2 (ZFS): 2 parity, flexible, self-healing, excellent perf. For a 6-drive DB server: RAID 10 for maximum write performance and predictable latency, or Z2 for better capacity utilization and self-healing. I recommend RAID 10 for pure DB workloads.

OP7 — Recursive resolvers (Windows DNS/DHCP) handle client queries. Authoritative servers host internal AD-integrated zones and external public zones. Forwarders route external queries to ISP/recursive resolvers. Conditional forwarding routes specific zones to designated servers. Split-horizon returns private IPs internally and public IPs externally. DNSSEC signs the external zone; DS record at registrar validates externally. Laptop mobility: DHCP provides internal DNS. VPN uses split-tunnel or DNS forwarding to resolve internal names via corporate DNS. Roaming relies on cached records or conditional forwarders.

OP8 — PKI chain: Root CA → Subordinate CA → End-entity cert. Trust anchored in root. Deployment: Root CA offline (air-gapped). Subordinate CA online, issues certs. CRL = periodic download of revoked certs. OCSP = real-time status check. Templates define cert properties (key usage, validity, auto-enrollment). Auto-enrollment pushes certs to domain-joined devices via AD CS. Compromised subordinate: Issue fake certs, but root can revoke it. Compromised root: Catastrophic; requires re-planting trust in all OS/browsers, massive disruption.

OP9 — MPLS: High cost, high reliability, low latency, managed, secure. IPsec VPN: Low cost, variable reliability/latency, unmanaged, secure over internet. SD-WAN: Medium cost, high reliability (bonding), low latency (path selection), centralized management, secure. WireGuard mesh: Low cost, high reliability, low latency, simple config, secure, less enterprise management. Recommendation: SD-WAN. Best balance for VoIP (QoS, path optimization, centralized management), cost-effective vs MPLS, and reliable over internet.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: Out-of-band management interfaces for remote power, console, and hardware monitoring. Critical when OS/network is down for recovery, firmware updates, and diagnostics. Internet exposure: High risk of credential stuffing, firmware exploits, unauthorized access, and hardware manipulation. Should be isolated on a dedicated management network.

OP11 — LVM: Traditional volume manager, fixed-size volumes, COW snapshots that can fill up. LVM-Thin: Overprovisions storage, thin snapshots, space-efficient but performance overhead and complex recovery. ZFS: Filesystem + volume manager, COW, instantaneous/cheap recursive snapshots, self-healing. Use LVM for simple Linux setups. LVM-Thin for VM storage efficiency. ZFS for data integrity, snapshots, and enterprise storage.

OP12 — Stretch cluster: 2 sites (2 nodes each) + 1 tiebreaker node (quorum witness). CRUSH rules distribute OSDs across sites, ensuring replicas span sites. Monitors: 3 monitors (1 per site + tiebreaker) for quorum. Latency: <5ms ideal, <10ms max. Split-brain: Both sites active → data corruption. Tiebreaker provides decisive vote. 2-site Ceph without tiebreaker is bad because 50/50 split yields no quorum, both sites become primary, and data corrupts.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable: Client retries, eventually falls back to APIPA (169.254.x.x) or fails. If Windows lease expires: Client attempts renewal at 50% (T1) and 87.5% (T2). If failed, reboots/retries, may get APIPA or lose connectivity until lease renewed or static fallback.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP, ACLs, and link aggregation. Enterprise importance: Segmentation, traffic prioritization, loop prevention, monitoring, and security enforcement.

OP15 — NTP synchronizes clocks over a network. Critical for log correlation, authentication (Kerberos/certs), distributed transactions, cluster consensus, and audit compliance. Clock drift consequences: Kerberos auth failures, split-brain in clusters, log timeline corruption, database replication lag, and certificate validation errors.

OP16 — Physical servers run directly on hardware (max perf, no overhead). VMs use full OS isolation with hardware virtualization (moderate overhead). Containers use OS-level isolation sharing the host kernel (minimal overhead). Run bare metal for high-performance databases, low-latency trading, GPU-intensive workloads, compliance requiring no hypervisor, or maximum I/O throughput.

OP17 — UPS provides immediate battery backup (short duration, conditions power). Generators provide long-duration fuel power (takes seconds/minutes to start). Both needed: UPS bridges the gap until generator starts. ATS (Automatic Transfer Switch) detects outage, switches load to generator, and switches back when utility power is restored.

OP18 — Active-passive: One node handles traffic, standby takes over on failure. Active-active: Both handle traffic, sync data, require split-brain prevention. PostgreSQL HA with Pacemaker/Corosync: 2-node cluster. STONITH (IPMI/fencing) prevents split-brain. Virtual IP (Pacemaker resource) floats to active node. Patroni/repmgr handles replication. On failure, fencing triggers, VIP moves, standby promotes.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO define acceptable data loss and downtime. Backup types: Full (baseline), Incremental (changes since last), Differential (changes since last full). Deduplication reduces storage and backup windows. Media: Disk (fast restore), Tape (cheap long-term), Cloud (offsite/scalable). Immutable backups: WORM storage protects against ransomware. Testing: Regular restore drills, verify integrity, measure RTO/RPO. Backup = data protection. DR = full recovery process (infrastructure, data, processes, failover).

OP20 — 802.1X: Port-based NAC. Roles: Supplicant (client), Authenticator (switch/AP), Auth Server (RADIUS). EAP-TLS: Cert-based mutual auth, highly secure, complex PKI. PEAP: Username/password tunneled in TLS, easier deployment, less secure. RADIUS handles auth, authorization, accounting. Dynamic VLAN: Auth server returns VLAN ID, switch assigns port. Failure: Port stays unauthorized, no traffic. MAB: Uses MAC address as credential for printers/IoT, fallback for non-802.1X devices, less secure, no user/device identity.
