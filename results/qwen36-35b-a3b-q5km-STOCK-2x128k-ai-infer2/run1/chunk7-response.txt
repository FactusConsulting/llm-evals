AA1 — Monoliths are single, unified codebases deployed as one unit with shared processes and databases. Microservices decompose applications into independently deployable, loosely coupled services with separate databases/processes. Microservices introduce: (1) network latency & failure handling (partial outages, retries, timeouts), (2) distributed data consistency (no ACID across services), and (3) operational complexity (orchestration, CI/CD pipelines, distributed tracing, service discovery).

AA2 — Synchronous communication blocks the caller until a response is received, enabling real-time interaction but creating tight coupling. Example: HTTP/REST or gRPC. Asynchronous communication decouples sender and receiver; messages are queued or published and processed later, improving resilience and throughput. Example: RabbitMQ (queue) or Kafka (pub/sub).

AA3 — A reverse proxy routes traffic, terminates TLS, and provides basic load balancing/caching. An API gateway adds API-specific capabilities: rate limiting, authentication/authorization, request/response transformation, versioning, analytics, and developer portals. An API gateway can technically replace a reverse proxy, but they are often layered: reverse proxies handle low-level routing/SSL efficiently at the edge, while gateways enforce business/API policies closer to services.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a later step fails. Choreography-based sagas use events to trigger the next step; they are decentralized and simple but hard to debug and modify. Orchestration-based sagas use a central coordinator that commands participants; they offer centralized control, easier monitoring, and are better for complex, multi-step workflows.

AA5 — CQRS separates read and write operations into distinct models. Commands modify state; queries read optimized views. It is paired with Event Sourcing because ES provides an immutable, append-only log of state changes that serves as the single source of truth for CQRS writes. Together they solve: auditability/temporal queries, independent scaling of reads/writes, complex domain modeling without ORM mapping leaks, and eventual consistency patterns that traditional CRUD struggles with.

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. States: Closed (normal traffic), Open (fail fast after threshold), Half-Open (allows limited probes to test recovery). It differs from retry+backoff because retries attempt immediate recovery, while circuit breakers halt traffic to prevent overload. Use both: retries handle transient blips; circuit breakers protect against sustained failures.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, low ops overhead.
2. Shared DB, separate schema: Moderate cost, reduced noisy-neighbor, better isolation/security, medium ops complexity (schema migrations scale poorly).
3. Separate DB per tenant: Highest cost, zero noisy-neighbor, maximum security/isolation, high ops complexity (backup, migration, monitoring at scale).

AA8 — Eventual consistency allows temporary stale reads; strong consistency guarantees immediate visibility across replicas. For inventory oversell prevention: use strong consistency for stock counts. Architecture: authoritative PostgreSQL or CockroachDB with row-level locking/optimistic concurrency. Patterns: pre-booking/reservation with TTL, idempotent order processing, partition inventory by SKU/warehouse to limit lock contention. Avoid eventual consistency for stock decrements.

AA9 — A sidecar proxy is a co-located container that intercepts all inbound/outbound traffic for a service. In Istio, Envoy acts as the data plane proxy handling routing, mTLS, retries, and metrics. The control plane (Pilot, Citadel) pushes configuration and certificates. mTLS solves: transparent security without app code changes, automatic cert rotation, service identity verification, and prevention of eavesdropping within the mesh. App TLS requires manual cert management per service and doesn't secure east-west traffic automatically.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is decommissioned. Strategy: Place an API gateway in front of the .NET Framework monolith. Identify a bounded context (e.g., user auth). Build a .NET 8 microservice. Route specific endpoints/paths via the gateway to the new service. Implement dual-write or CDC for data sync. Use feature flags for safe rollout. Repeat per module until the monolith is fully strangulated.

AA11 — 12-Factor App is a methodology for cloud-native software. Six factors: (1) Codebase (one dep per app), (2) Dependencies (explicitly declared), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless, ephemeral). They matter because they enable horizontal scaling, zero-downtime deploys, secure config management, predictable resource usage, and portability across cloud/on-prem environments.

AA12 — 
- Coupling: Event = loose, Request = tight.
- Scalability: Event = high throughput, burst handling; Request = predictable, request-rate limited.
- Debugging: Event = complex tracing, replay needed; Request = straightforward request/response logs.
- Ordering: Event = partition-level ordering guaranteed; Request = per-request ordering.
- Failure: Event = DLQs, retries, idempotency; Request = timeouts, retries, circuit breakers.
Choose Event for async workflows, high throughput, decoupled domains, audit trails. Choose Request for real-time APIs, synchronous user interactions, strict consistency needs.

AA13 — A load balancer distributes incoming traffic across multiple backend servers. Layer 4 balances based on IP/port (fast, no content inspection). Layer 7 inspects HTTP headers, URLs, cookies, and content. Layer 7 is required when routing `/api/v1` to backend A and `/api/v2` to backend B, or serving different content based on cookies/headers.

AA14 — Message queues (RabbitMQ) use point-to-point/pub/sub models, consume/remove messages after delivery, and support complex routing/exchanges. Log-based brokers (Kafka) are append-only logs retained by time/size, allowing multiple consumers to read the same data and replay events. Pick RabbitMQ for task queues, strict delivery, and complex routing. Pick Kafka for event streaming, analytics, log aggregation, and replay needs.

AA15 — Containers share the host OS kernel and virtualize at the process level, making them lightweight and fast to start. VMs virtualize hardware and run full guest OSes, making them heavier but more isolated. Containers are popular for microservices because they provide consistent environments, efficient resource usage, immutable deployments, and native Kubernetes orchestration support.

AA16 — Stateless services hold no local session data; any instance can handle any request. Stateful services maintain local state/session. Stateless services scale horizontally easily because adding/removing instances requires no data migration or session affinity. Examples: Stateless = web API, Redis cache. Stateful = PostgreSQL, Kafka.

AA17 — An ORM maps objects to database tables, abstracting SQL generation. Examples: Entity Framework (.NET), Hibernate (Java), Prisma (Node). Trade-offs: ORMs accelerate development, ensure type safety, and improve portability, but can generate inefficient queries, obscure performance bottlenecks, and leak abstraction boundaries. Raw SQL offers full control, optimal performance, and complex query support, but requires more code, DB-specific tuning, and slower development.

AA18 — The Bulkhead pattern isolates resources so a failure in one component doesn't exhaust resources for others. It prevents cascading failures in microservices by partitioning thread pools, connections, or deployments. Implementation: Use separate thread pools/connection pools per downstream service, deploy critical vs non-critical services on separate Kubernetes node pools, and enforce resource quotas/limit ranges to cap CPU/memory per bulkhead.

AA19 — OT requires a central server to transform concurrent operations; it offers strong consistency, low online latency, high server complexity, and poor offline support. CRDTs are data structures that converge automatically without coordination; they offer eventual consistency, higher client-side complexity/size, lower server complexity, and excellent offline support. Choose CRDTs for offline editing: they allow concurrent local edits, merge automatically when online, require no central coordination, and simplify client implementation.

AA20 — Distributed tracing challenges include polyglot instrumentation overhead, data volume, and context loss. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject/extract trace IDs across HTTP/gRPC. Sampling: head-based is cheap but loses rare traces; tail-based collects all, samples post-facto, and is accurate but high-overhead. Storage/querying uses Jaeger (OpenTelemetry) or Tempo (Grafana, object storage) with span indexing. For async/Kafka: propagate trace context in message headers using OpenTelemetry propagators or Kafka interceptors. Consumers must read headers and continue the trace; if headers are lost, use correlation IDs as fallback.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and low overhead. Examples: VMware ESXi, Proxmox VE, KVM, Hyper-V. Type 2 (hosted) hypervisors run as applications on a host OS, offering easier setup but higher overhead. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block storage, presenting raw disks to servers for high performance and low latency. Protocols: Fibre Channel, iSCSI. NAS provides file storage over a network, enabling easy sharing. Protocols: NFS, SMB/CIFS. Use SAN for databases and VMs requiring block access. Use NAS for file shares, backups, and home directories.

OP3 — 3-tier architecture uses Core, Distribution, and Access layers hierarchically. It suffers from bottlenecks at core/distribution layers and poor scalability. Leaf-spine is preferred because it uses an all-to-all mesh, providing predictable low latency, non-blocking bandwidth, and linear scalability. It solves the bandwidth bottlenecks and single points of congestion inherent in hierarchical 3-tier designs.

OP4 — Design: 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing uses STONITH (IPMI/iDRAC) to power off unresponsive nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. During node failure: HA manager detects failure, fences the node, and restarts VMs on surviving nodes using shared storage. Ceph handles data replication automatically.

OP5 — VLAN trunking carries multiple VLANs over a single physical link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, assign IPs, and configure the switch port as a trunk (802.1Q). Repeat for additional VLANs.

OP6 — RAID 1: Mirror, 50% capacity, 1 drive fault. RAID 5: Striping + single parity, N-1 capacity, 1 fault, write penalty. RAID 6: Double parity, N-2 capacity, 2 faults, higher write penalty. RAID 10: Mirror + stripe, 50% capacity, survives multiple faults (not same pair), fast. Z2 (RAID 6 equivalent): Handles large drives, faster rebuilds, bit-rot protection. Choice: RAID 10 for database write performance and simplicity, or Z2 if capacity and fault tolerance are prioritized over raw write speed.

OP7 — Recursive resolvers: Internal DNS servers (Windows DNS/BIND) for clients. Authoritative: Internal zone for AD, external zone for public. Forwarders: Point to ISP/Cloudflare for external resolution. Conditional forwarding: Routes internal AD domains to internal DNS, external to forwarders. Split-horizon: Internal DNS returns private IPs, external returns public IPs. DNSSEC: Sign external zone, publish DS record at registrar. Laptop move: DHCP assigns internal DNS. VPN uses split-tunneling/conditional forwarding to route internal queries to HQ DNS. Roaming clients rely on cached records or DNS dynamic updates.

OP8 — PKI chain: Root CA (offline, self-signed, long-lived) -> Subordinate CA (online, issues certs) -> End-entity cert. CRL = periodic revocation list download; OCSP = real-time status check. Templates define key usage, validity, and auto-enrollment policies. Auto-enrollment pushes certs to domain-joined devices via AD CS. Compromise: Subordinate CA = revoke & reissue, limited blast radius. Root CA = catastrophic, requires rebuilding entire PKI and updating all trust stores.

OP9 — MPLS: High reliability, low latency, expensive, managed. IPsec VPN: Cheap, internet-based, variable latency, manual config. SD-WAN: Intelligent routing, app-aware, cost-effective, centralized management, hybrid internet/MPLS. WireGuard: Modern, fast, simple, lacks enterprise routing/management. Recommendation: SD-WAN. It prioritizes VoIP traffic with QoS, handles internet outages gracefully, reduces cost, and centralizes management for 50-user sites.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: Out-of-band management interfaces for remote server control (power, console, hardware monitoring) independent of the OS. Critical for recovery when OS/network is down and for remote maintenance. Internet exposure risks: credential stuffing, firmware exploits, unauthorized access, ransomware deployment, and hardware manipulation.

OP11 — LVM: Traditional volume manager, fixed-size LVs, COW snapshots consume space. LVM-Thin: Overprovisions storage, instant snapshots, space-efficient, but risks thin pool exhaustion. ZFS: Filesystem + volume manager, copy-on-write, instant snapshots, send/receive, self-healing. Use LVM for legacy/simple block storage. LVM-Thin for overprovisioning/VMs. ZFS for data integrity, advanced snapshots, and all-in-one storage.

OP12 — Stretch cluster: 2 sites with nodes, 1 tiebreaker (quorum device) at a third location. Ceph CRUSH rules map OSDs to sites, ensuring replicas spread across sites. Monitors: 1 per site + tiebreaker, or 3 monitors with quorum device. Network latency: <10ms ideal, <50ms max. Split-brain: Quorum device breaks ties when site connectivity fails. 2-site Ceph without a tiebreaker fails because both sites lose quorum, assume primary status, and risk data corruption.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable: client uses APIPA (169.254.x.x) or fails. Windows lease expiry: Client attempts renewal at 50% (T1) and 87.5% (T2). If unavailable, lease expires, connectivity drops, and client may fall back to APIPA or prompt the user.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP, ACLs, and link aggregation. Enterprise importance: network segmentation, traffic prioritization, loop prevention, monitoring, and security enforcement.

OP15 — NTP synchronizes clocks over a network. Critical for log correlation, authentication (Kerberos/AD), distributed DB consistency, certificate validation, and debugging. Clock drift causes: Kerberos auth failures, split-brain in clusters, data corruption in distributed systems, and incorrect timestamps in logs/databases.

OP16 — Physical: Hardware directly. VM: OS virtualization, full isolation. Container: Process isolation, shares kernel. Bare metal is used for high-performance databases, real-time processing, hardware passthrough (GPUs/NICs), regulatory compliance, and maximum I/O throughput where virtualization overhead is unacceptable.

OP17 — UPS provides instant battery backup and power conditioning for short outages. Generators provide long-term power but require startup time and fuel. Both are needed because UPS bridges the gap until generators start. ATS (Automatic Transfer Switch) detects utility failure, switches load to generator, and switches back when utility returns.

OP18 — Active-passive: One node handles traffic, standby takes over on failure. Active-active: All nodes handle traffic, data syncs, complex failover. PostgreSQL HA with Pacemaker: 2 nodes, configure STONITH (IPMI/fencing), create virtual IP resource, run PostgreSQL in streaming replication mode. Pacemaker monitors health, fails over VIP, and promotes standby. Fencing prevents split-brain by powering off the failed node.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO define acceptable data loss and downtime. Backup types: Full (baseline), Incremental (changes since last), Differential (since last full). Deduplication reduces storage and backup windows. Media: Disk (fast restore), Tape (cheap long-term), Cloud (offsite/scalable). Immutable backups: WORM storage prevents ransomware deletion. Testing: Regular restore drills, verify integrity, measure RTO/RPO. Backup = data protection; DR = full recovery process (infrastructure, data, procedures) to resume operations.

OP20 — 802.1X is port-based NAC. Roles: Supplicant (client), Authenticator (switch/AP), Auth Server (RADIUS). EAP-TLS: Cert-based, mutual auth, highly secure. PEAP: Username/password, uses TLS tunnel, easier deployment. RADIUS handles auth, authorization, accounting. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: Port stays unauthorized, no network access. MAB: Switch uses MAC address as credential, queries RADIUS, bypasses 802.1X for IoT/printers.
