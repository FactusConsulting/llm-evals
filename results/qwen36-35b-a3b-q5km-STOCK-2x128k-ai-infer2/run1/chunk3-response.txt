T1 — `tofu plan` reads configuration and current state, computes an execution plan, and displays what will be created/changed/destroyed without making changes (dry run). `tofu apply` executes that plan (or prompts for confirmation), provisions/updates infrastructure, and updates the state file.

T2 — State is a JSON file mapping configuration resources to real-world infrastructure IDs and attributes. It tracks dependencies, drift, and lifecycle. Remote state is stored externally (S3, GCS, etc.) to enable team collaboration, enforce state locking, improve security, and prevent local file loss/corruption.

T3 — `count` uses integer indexing and recreates resources when items are added/removed in the middle of a list. `for_each` uses a map or set, preserving resource identity by key. `for_each` is preferred for dynamic collections, when resources have unique identifiers, or when order changes shouldn't trigger recreation.

T4 — Manual changes cause state drift. On next `plan`, OpenTofu refreshes state by querying the provider API, compares it with configuration, and shows a diff. It handles drift by proposing to revert changes (if config differs) or ignoring them (if `ignore_changes` is set). Can be configured to fail on drift.

T5 —
```hcl
variable "vm_names" {
  type    = set(string)
  default = ["web1", "web2", "web3"]
}

resource "null_resource" "vm" {
  for_each = toset(var.vm_names)
  triggers = {
    name = each.value
  }
}
```
*(Replace `null_resource` with your actual provider resource.)*

T6 — `terraform_remote_state` reads another module's state file directly, coupling modules to backend structure, potentially exposing sensitive data, and causing slow API/state reads. Output values explicitly expose only needed data via `output {}`. The recommended alternative is passing data via module outputs and input variables: it's type-safe, decouples modules, improves performance, and follows modern best practices.

T7 — `remote-exec` provisioners run after resource creation but outputs are evaluated before provisioners finish, and provisioners don't update state. This causes empty/missing outputs. Fix: Use `local-exec` to generate kubeconfig locally, then read it via `local_file` data source or output. Better: Use the `kubectl` provider or an `external` data source to fetch kubeconfig after the cluster is ready. Avoid provisioners for state-dependent outputs.

T8 — `tofu import` is a CLI command to map existing infrastructure to a resource block. Limitations: requires manual config, poor dependency handling, hard to automate in CI. The `import` block (1.5+) is declarative, supports multiple resources, integrates with `tofu plan`/`apply`, handles dependencies automatically, and is version-controllable.

T9 — A variable is an input parameter for modules/config. Variables (`variable {}`) are external inputs that customize behavior. Outputs (`output {}`) are internal values returned by a module to consumers. Variables flow in; outputs flow out.

T10 — A provider is a plugin that interacts with cloud/API backends to manage resources. Running `tofu plan` without `tofu init` fails because provider plugins, backend configuration, and module dependencies haven't been downloaded or initialized.

T11 — `.terraform.lock.hcl` records exact provider versions, checksums, and source URLs. Commit it to ensure reproducible builds, prevent unexpected provider updates, and guarantee consistent environments across team members and CI/CD.

T12 — `tofu destroy` deletes all resources in the current state/config. Target a single resource: `tofu destroy -target=resource_type.resource_name`.

T13 — A data source reads existing infrastructure/data without managing its lifecycle. Example: Fetching an existing VPC ID, AMI, or DNS record created outside OpenTofu or by another team, rather than provisioning a new one.

T14 — Variables are external inputs, typed, validated, and overridable. Locals are internal computed values used for expressions, filtering, or avoiding repetition. Use locals for derived values within a module; use variables for external configuration.

T15 — `lifecycle` controls resource creation/deletion behavior:
- `create_before_destroy = true`: Creates new before destroying old (e.g., load balancer target groups, DB migrations).
- `prevent_destroy = true`: Blocks recreation/deletion (e.g., production databases, compliance resources).
- `ignore_changes = [...]`: Ignores drift on specific attributes (e.g., `ami_id` in ASGs, tags managed externally).

T16 — The `moved` block declares resource identity changes (type/name/path) without altering state. It maps old addresses to new ones during refactoring, preserving state and preventing recreation. Syntax: `moved { from = old_addr; to = new_addr }`.

T17 — OpenTofu builds a DAG of resources/data sources/providers to determine execution order. Implicit dependencies come from config references (e.g., `vpc_id = aws_vpc.main.id`). Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, breaking parallelism for unrelated resources. Use sparingly to avoid bloated plan times and masking true dependencies.

T18 — 1. `tofu plan -refresh=false`: Skips state refresh. Tradeoff: May miss drift, faster plan. 2. Split into multiple modules/workspaces: Reduces graph size per run. Tradeoff: Complex state management, cross-module sharing needed. 3. Reduce data sources: Each triggers API calls. Tradeoff: May accept stale data or require external caching. 4. Tune `TF_PARALLELISM` (default 10): Increases concurrent resource operations. Tradeoff: May hit API rate limits or overwhelm control node.

T19 — State locking uses backend-specific mechanisms (e.g., S3+DynamoDB) to write a lock record with TTL/process ID, preventing concurrent writes. If a pipeline crashes, the lock persists until TTL expires or is broken. Break with `tofu force-unlock <LOCK_ID>`. Risks: State corruption, inconsistent infrastructure, overwriting concurrent changes. Only break if certain no other process is running.

T20 — 1. Create S3 bucket & DynamoDB table. 2. Update `backend "s3"` config in code. 3. Run `tofu init -migrate-state`. 4. Confirm when prompted. OpenTofu copies local state to S3, initializes DynamoDB lock, and removes local state. 5. Verify: `tofu state list` shows resources, `tofu plan` shows no changes, S3 contains state file, DynamoDB lock table exists.

A1 — Task: Single action (module + args). Role: Reusable collection of tasks, handlers, vars, templates, files in a standard directory structure. Playbook: YAML file containing one or more plays (lists of tasks/roles) to execute against hosts.

A2 — `ansible_facts` are auto-discovered system variables (OS, IP, CPU, etc.) gathered by the `setup` module. Access OS family via `{{ ansible_facts.os_family }}` or `{{ ansible_os_family }}`.

A3 — `command`: Runs without shell features (no pipes/redirects). Safest, default. `shell`: Runs via `/bin/sh`, supports pipes/redirects/variables. Use when shell features needed. `raw`: Runs via SSH without Python, bypasses module engine. Use for initial bootstrap or when Python isn't installed.

A4 — Idempotency: Modules check current vs desired state, acting only if different. Idempotent: `apt: name=htop state=present` (installs only if missing). Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run). Fix with `copy` or `lineinfile`.

A5 —
```yaml
- name: Install htop on Debian
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install EPEL and htop on RedHat
  package:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
```

A6 — Low to high priority: role defaults → inventory (group_vars/host_vars) → play vars → role vars → host facts → extra_vars → set_fact → registered vars. `extra_vars` and `set_fact` override most others. `set_fact` persists for the play; `extra_vars` always win.

A7 — Inventory: Group all 50 under `rke2_agents`. Play: `serial: 3` then `serial: 100%`. After first 3 nodes, add a `wait_for` task checking RKE2 API port (6443) or a readiness marker file before proceeding. This ensures control plane is ready before agents join.

A8 — `ansible-vault` encrypts/decrypts sensitive data. Vault encrypts entire files, not individual variables. To encrypt a single variable, use `ansible-vault encrypt_string 'my_secret' --name 'my_secret_var'` inline in a playbook/vars file, or store sensitive vars in a separate vault-encrypted vars file.

A9 — Inventory: List of hosts/groups Ansible manages. Static: Plain text/INI/YAML file, manually maintained. Dynamic: Script/API that generates inventory on-the-fly (e.g., AWS EC2, VMWare), scales automatically with infrastructure.

A10 — `ansible webservers -m ansible.builtin.command -a "df -h"`

A11 — Handler: Special task that only runs if notified. Runs once at play end, even if notified multiple times. Differs from regular tasks by deferred execution. Trigger with `notify: handler_name` in a task.

A12 — `ansible.cfg` configures Ansible runtime behavior. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `roles_path`, `pipelining`.

A13 — `register` captures task output (stdout, rc, etc.) into a variable. Use in subsequent tasks via `{{ registered_var.stdout }}` or conditionals like `when: registered_var.rc == 0`.

A14 — `import_tasks`: Static, evaluated at parse time. Cannot be conditional. `include_tasks`: Dynamic, evaluated at runtime. Can be conditional (`when:`) or looped. Use `include_tasks` for conditional/looped inclusion; `import_tasks` for performance (faster parsing).

A15 — Ansible Galaxy: Hub for sharing roles/collections. `requirements.yml` lists roles/collections with names/versions. Install roles: `ansible-galaxy install -r requirements.yml`. Install collections: `ansible-galaxy collection install -r requirements.yml`.

A16 — Connection plugins handle control-to-target communication. `ssh`: Default, uses SSH for Linux/Unix. `local`: Runs tasks on control node. `network_cli`: Uses SSH/Telnet with network device CLI (Cisco, Juniper). Use `ssh` for servers, `local` for control node tasks, `network_cli` for network gear.

A17 — `delegate_to`: Runs task on specified host instead of target. `run_once`: Executes task only once across all hosts. Example: Gather package list from remote host, then run once on localhost to generate a report:
```yaml
- name: Generate report on localhost
  delegate_to: localhost
  run_once: true
  ansible.builtin.copy:
    content: "{{ ansible_facts.packages | list | join('\n') }}"
    dest: /tmp/packages.txt
```

A18 — 1. Increase `forks`: Parallelizes tasks. Tradeoff: Higher CPU/memory on control node, SSH/connection limits. 2. Enable `pipelining`: Reduces SSH sessions per task. Tradeoff: Requires `requiretty` disabled on targets. 3. Fact caching (Redis/Memcached): Skips repeated fact gathering. Tradeoff: Stale facts if infra changes rapidly, adds cache infra. 4. Mitogen: In-process parallelism, bypasses SSH overhead. Tradeoff: Python 3.6+ required, potential module compatibility issues, adds deployment complexity.

A19 — Jinja2 is Ansible's template engine for dynamic config generation. `{{ }}`: Output expression (prints variable/result). `{% %}`: Control structure (loops, conditionals). `{# #}`: Comments (not rendered).
```jinja2
upstream backend {
{# Health check comments generated dynamically #}
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; # health_check={{ server.health_endpoint }}
{% endfor %}
}
```

A20 — Use `serial: 1` or `serial: 20%` for rolling. Pre-task: `uri` to deregister from LB or set maintenance. Deploy: copy code, restart service. Post-task: `uri` health check (`status_code: 200`) with `wait_for` or `retries`. Re-register LB. Wrap deploy/health check in `block`. On failure, `rescue` rolls back (revert code, restart old version, re-register LB), `always` ensures LB state consistency. Example structure:
```yaml
- hosts: webservers
  serial: 1
  tasks:
    - block:
        - name: Deregister from LB
          uri: ...
        - name: Deploy app
          copy: ...
        - name: Restart service
          service: ...
        - name: Health check
          uri: url=http://localhost:80 status_code=200
          retries: 5
          delay: 10
        - name: Re-register LB
          uri: ...
      rescue:
        - name: Rollback
          command: /opt/app/rollback.sh
        - name: Re-register LB on failure
          uri: ...
      always:
        - name: Ensure LB state
          uri: ...
```
