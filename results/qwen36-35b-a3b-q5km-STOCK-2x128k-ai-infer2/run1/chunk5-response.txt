DN1 — **class vs struct**: `class` is a reference type allocated on the heap, supports inheritance/polymorphism, and can be null. `struct` is a value type allocated inline (stack or inlined in heap objects), copied by value, and cannot be null (pre-C# 8). Use `struct` for small, immutable, short-lived data that benefits from stack allocation and value semantics (e.g., `Point`, `Guid`, `Vector3`).

DN2 — **IEnumerable<T> vs IQueryable<T>**: `IEnumerable<T>` executes queries in-memory; filtering/projection happens after data is loaded. `IQueryable<T>` builds an expression tree that providers (like EF Core) translate to remote queries (SQL). This distinction matters because `IQueryable` pushes filtering, paging, and projection to the database, drastically reducing network payload and memory usage.

DN3 — **async/await & Task vs ValueTask**: `async/await` compiles to a state machine that captures context, avoids thread blocking, and resumes on completion. `Task` is a reference type that always allocates. `ValueTask` is a struct that can wrap a cached/synchronous result or a `Task`, avoiding allocations. Use `ValueTask` in hot paths or when an async operation frequently completes synchronously (e.g., cached reads).

DN4 — **Dependency Injection & Lifetimes**: DI containers manage object creation and disposal. `Transient`: new instance per request. `Scoped`: one instance per logical scope (e.g., HTTP request). `Singleton`: one instance per app lifetime. **Captive dependency bug**: Injecting a `Scoped` service into a `Singleton` keeps the `Scoped` instance alive for the app's lifetime, causing memory leaks, stale state, and thread-safety issues.

DN5 — **string vs ReadOnlySpan<char>**: `string` is immutable, heap-allocated, and copies on slicing. `ReadOnlySpan<char>` is a stack-only, zero-allocation view over contiguous memory (strings, arrays, buffers). `Span<T>` is the mutable counterpart. Use `Span<T>`/`ReadOnlySpan<char>` for high-performance parsing, slicing, or buffer manipulation where allocation overhead is unacceptable.

DN6 — **GC, Generations, LOH, IDisposable**: The GC manages the managed heap. `Gen 0`: short-lived objects, collected frequently. `Gen 1`: buffer between 0 and 2. `Gen 2`: long-lived objects, collected rarely. `LOH`: objects >85KB, compacted infrequently, zeroed on allocation. `IDisposable` is needed for deterministic cleanup of unmanaged resources (handles, sockets, DB connections) since the GC only tracks managed memory and runs non-deterministically.

DN7 — **ConfigureAwait(false)**: By default, `await` captures the `SynchronizationContext` (e.g., UI thread) and resumes there. `ConfigureAwait(false)` tells the awaiter not to capture/restore context, allowing continuation on any thread pool thread. **Use** in libraries to prevent deadlocks and improve throughput. **Don't use** in UI/app code where context is required for UI updates or request-scoped services. Relies on `SynchronizationContext` to track thread affinity.

DN8 — **.NET 8/9 Features**: Primary constructors reduce boilerplate (`public record Config(string Host, int Port);`). Collection expressions simplify array/list creation (`int[] nums = [1, 2, 3];`). `FrozenDictionary` is an immutable, optimized lookup dictionary for static data. DI example:
```csharp
public record AppConfig(string ApiUrl, int Timeout);
builder.Services.AddSingleton<AppConfig>(sp => new AppConfig("https://api", 30));
```

DN9 — **DbContext ObjectDisposedException under load**: Likely cause: `DbContext` registered as `Transient` but shared across async operations, or disposed before async continuations complete. EF Core `DbContext` is not thread-safe. **Fix**: Register as `Scoped` (per HTTP request) so DI creates one instance per request and disposes it after the response. Ensure all `await` calls complete before the request scope ends.

DN10 — **record vs class**: `record` is a reference type with value-based equality, immutability by default, and positional syntax. `record struct` is the value-type equivalent. Choose `record` for DTOs, domain events, or immutable data carriers. Choose `class` for mutable, reference-heavy objects with identity semantics. Choose `record struct` for performance-critical, small, immutable data where heap allocation must be avoided.

DN11 — **ref, out, in**: `ref` passes by reference; argument must be initialized before call. `out` passes by reference; must be assigned in the method (no pre-initialization needed). `in` passes by reference readonly; prevents modification, avoids copying large structs. Use `ref` for modifying existing values, `out` for multiple returns/parsing, `in` for large structs where you want pass-by-reference semantics without mutation.

DN12 — **Nullable Reference Types (NRT)**: Compile-time feature (`#nullable enable`) that tracks potential null dereferences using `?` annotation. Not enforced at runtime. Differs from nullable value types (`int?` = `Nullable<int>`) which are runtime types with `HasValue`/`Value` and actual nullability. NRTs are erased at runtime and only provide static warnings.

DN13 — **LINQ & Deferred Execution**: LINQ unifies querying across data sources. Method syntax (`list.Where(...)`) is fluent and chainable; query syntax (`from x in list where ...`) is SQL-like and compiles to method syntax. **Deferred execution** means the query isn't executed until enumerated (`foreach`, `ToList`, etc.), enabling composition, lazy evaluation, and repeated execution over changing data.

DN14 — **Generic Constraints**: Restrict `T` to enable specific operations. `class` (reference), `struct` (non-nullable value), `new()` (parameterless constructor), `IComparable<T>` (implements interface). Combine with `&` (e.g., `where T : class, IComparable<T>, new()`). Use when algorithms require specific capabilities (e.g., sorting, instantiation, or reference semantics).

DN15 — **abstract class vs interface**: Abstract classes support state, constructors, and partial implementation; single inheritance. Interfaces define contracts; multiple inheritance. C# 8+ default interface methods allow implementation in interfaces, blurring the line, but abstract classes still support fields/constructors. Prefer interfaces for polymorphic contracts, abstract classes for shared implementation/state hierarchies.

DN16 — **Middleware Pipeline**: Sequential request processing. `app.Use()` adds middleware that can short-circuit or pass to next. `app.Map()` branches routing. `app.Run()` is terminal. Ordering matters: auth/rate-limiting early, static files before MVC, error handling near the top. Exception handling middleware (`UseExceptionHandler`) catches unhandled exceptions and can rewrite the response without breaking the pipeline.

DN17 — **Channel<T> vs BlockingCollection<T>**: `Channel<T>` is a modern, async-native, thread-safe producer-consumer queue. Bounded channels (`Channel.CreateBounded(n)`) apply backpressure by blocking producers when full. `BlockingCollection<T>` is older, sync-focused, and lacks native async support. Example: bounded channel with `WriteAsync`/`ReadAsync` naturally throttles producers under consumer lag.

DN18 — **Source Generators**: Compile-time code generation via Roslyn APIs. Unlike reflection (runtime overhead) or IL weaving (post-compile, e.g., Fody), generators produce C# code before compilation. **Incremental generators** (`ISourceGenerator` replacement) track dependencies, cache results, and only regenerate when inputs change, drastically reducing build times and enabling IDE integration.

DN19 — **TPL Dataflow**: Message-passing library for pipelines. `ActionBlock` processes items (no output), `TransformBlock` processes and outputs, `BufferBlock` stores/queues. Compares to `Channels`: Dataflow provides built-in flow control, completion propagation, and complex topologies (fan-in/out). Channels are lower-level, more flexible for custom async patterns, but require manual backpressure/completion handling.

DN20 — **Minimal APIs**: Lightweight, route-handler-based APIs without controllers. Trade-offs: faster setup, lower memory, but less structured for large teams, explicit middleware registration, and OpenAPI requires Swashbuckle/NSwag setup. Route groups (`MapGroup`) organize endpoints. Endpoint filters (`AddFilter`) run before/after handlers for auth, validation, or logging, replacing controller action filters.

P1 — **list vs tuple, set vs frozenset**: `list` is mutable, ordered, allows duplicates. `tuple` is immutable, ordered, often used for heterogeneous data. `set` is mutable, unordered, unique elements. `frozenset` is immutable, hashable, usable as dict keys or set elements.

P2 — **GIL**: Global Interpreter Lock allows only one thread to execute Python bytecode at a time. Affects CPU-bound multithreading (threads don't run in parallel). Workarounds: `multiprocessing` (separate processes), C-extensions that release GIL, `asyncio` (I/O concurrency), or alternative runtimes (PyPy, GraalPy).

P3 — **deepcopy vs copy**: `copy` creates a new container but references nested objects. `deepcopy` recursively copies all nested objects. Shallow copy fails when nested mutable objects are modified: `a = [[1]]; b = copy(a); b[0].append(2); a[0]` becomes `[1, 2]`.

P4 — **Decorator logging execution time**:
```python
import time
from functools import wraps
def timer(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — **Generators & yield**: `yield` pauses function execution, returns a value, and resumes on next iteration. Memory-efficient vs lists (no full in-memory storage). `yield from` delegates iteration to another generator, flattening nested iteration without manual loops.

P6 — **asyncio event loop**: Single-threaded concurrency via cooperative scheduling. `asyncio.run()` executes the main coroutine. `asyncio.gather()` runs multiple coroutines concurrently, returning results in order. `asyncio.create_task()` schedules a coroutine for later execution. `time.sleep()` blocks the event loop; use `await asyncio.sleep()` to yield control.

P7 — **MRO & Diamond Inheritance**: Python 3 uses C3 linearization. MRO for `D(B, C)` is `D → B → C → A`. `D().who()` looks up `who` in `D` (none), then `B` (none), then `C` (exists) → returns `"C"`. C3 ensures left-to-right, depth-first resolution without ambiguity.

P8 — **Metaclass vs __init_subclass__**: Metaclass controls class creation (e.g., ORM field registration, singleton enforcement). `__init_subclass__` is a simpler hook called when a subclass is defined. Use `__init_subclass__` for plugin registration or validation. Use metaclasses for framework-level class manipulation or enforcing complex creation rules.

P9 — **multiprocessing vs threading vs concurrent.futures**: Threading: I/O bound, shares memory, GIL limits CPU. Multiprocessing: CPU bound, separate processes, memory overhead, requires pickling for IPC. `concurrent.futures`: high-level API wrapping both. Pickling limits multiprocessing to serializable objects/functions; lambdas/closures often fail.

P10 — **__slots__**: Restricts instance attributes to a predefined list, preventing `__dict__` creation. Saves memory (~50-80% reduction for many instances) and speeds up attribute access. Prevents adding arbitrary attributes at runtime. Use for large numbers of instances with fixed schemas.

P11 — **Virtual environments**: Isolated Python environments with independent packages/interpreters. Prevents dependency conflicts and system pollution. `venv`: stdlib, lightweight. `virtualenv`: third-party, more features. `conda`: package + env manager, handles non-Python deps, standard in data science.

P12 — **Comprehensions vs map/filter**: Comprehensions (`[x for x in lst if x>0]`) are concise, often faster, and more readable. `map()`/`filter()` return iterators, useful for functional style or lazy evaluation. Prefer comprehensions for simple transformations/filters; use `map`/`filter` when composing functions or working with large streams.

P13 — **== vs is & interning**: `==` checks value equality. `is` checks object identity. Object interning caches small integers (-5 to 256) and short strings for performance. `a is b` returns `True` for interned objects because they reference the same memory address.

P14 — **\*args, \*\*kwargs, /, \***: `*args` collects extra positional args into a tuple. `**kwargs` collects extra keyword args into a dict. `/` marks parameters as positional-only. `*` marks parameters as keyword-only. Enforce API contracts, improve clarity, and enable flexible function signatures.

P15 — **Context managers**: Ensure setup/teardown (`with`). Classes implement `__enter__`/`__exit__`. Functions use `@contextmanager` with `yield`. Example beyond files: database transaction or lock acquisition:
```python
@contextmanager
def transaction(db):
    db.begin()
    try:
        yield db
        db.commit()
    except:
        db.rollback()
        raise
```

P16 — **Type hinting**: Static annotations for IDE/tooling. `Union`/`Optional`/`Literal`/`TypeVar`/`Protocol` express complex types. `mypy`/`pyright` parse hints, check consistency, catch bugs pre-runtime. Not enforced at runtime; annotations are metadata.

P17 — **Data model (dunders)**: `__repr__` (dev/debug, unambiguous) vs `__str__` (user-friendly). `__eq__` vs `__hash__`: defining `__eq__` without `__hash__` makes objects unhashable. `__getattr__` (fallback for missing attrs) vs `__getattribute__` (always called, override carefully). Dunders define operator behavior and object representation.

P18 — **Descriptors**: Objects implementing `__get__`, `__set__`, `__delete__` that control attribute access. `property`, `classmethod`, `staticmethod` are descriptors under the hood. They intercept attribute lookup on the class, enabling computed properties, method binding, and static behavior without instance state.

P19 — **Import system**: `sys.path`/`PYTHONPATH` define search order. Absolute imports (`pkg.mod`) vs relative (`.`). `__init__.py` marks packages (optional in Python 3.3+ for implicit namespace packages). Namespace packages span directories. `Finder` locates modules; `Loader` loads/executes them. The system is pluggable via `sys.meta_path`.

P20 — **dataclasses vs attrs vs Pydantic**: `dataclasses` auto-generates `__init__`, `__repr__`, `__eq__`. `attrs` offers more features (validators, converters). `Pydantic` adds runtime validation, serialization, and JSON support. `__post_init__` runs after init. `field()` handles defaults/factories. `frozen=True` enables immutability. Inheritance works but requires care with defaults. Choose Pydantic for API models, config parsing, or strict validation.
