G1 — A slice is a dynamic, reference-like view over an underlying array (header contains pointer, length, capacity). An array is a fixed-size value type. When you `append` to a slice that has reached its capacity, the runtime allocates a new backing array (typically 2× capacity for small slices), copies existing elements, updates the slice header, and returns the new slice.

G2 — `var x int` declares a variable with explicit type and zero value. `x := 0` is a short variable declaration that infers the type. You cannot use `:=` at package level, when all variables on the left-hand side are already declared in the current scope, or when type inference is ambiguous/insufficient and you need explicit typing.

G3 — A goroutine is a lightweight, user-space thread managed by the Go runtime (~2KB initial stack, grows/shrinks). OS threads are heavy, kernel-managed, and typically 1:1 with execution. The GMP model: G = goroutine, M = machine (OS thread), P = processor (execution context/run queue). The scheduler multiplexes Gs onto Ms using Ps for local run queues, with work-stealing to balance load.

G4 — Channels are typed conduits for communication and synchronization. Unbuffered channels block both sender and receiver until both are ready. Buffered channels have a capacity; send blocks only when full, recv blocks only when empty. Sending to a full buffered channel blocks until space is available or the channel is closed.

G5 — The `context` package propagates deadlines, cancellation signals, and request-scoped values across API boundaries. Minimal example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
http.DefaultClient.Do(req)
```

G6 — Go uses implicit interface satisfaction: a type implements an interface if it has the required methods, with no explicit declaration. Java/C# require explicit `implements`/`extends`. `interface{}` (Go 1.18+ `any`) accepts any type. Powerful for generic-like behavior before generics, but dangerous because type assertions can panic at runtime and bypass compile-time safety.

G7 — The code is unsafe due to lack of synchronization: the compiler/CPU may reorder writes, and the reading goroutine may not see updated memory (no happens-before guarantee). Fix with atomic operations:
```go
var ready atomic.Bool
var data atomic.Pointer[string]
go func() {
    data.Store("hello")
    ready.Store(true)
}()
for !ready.Load() {}
fmt.Println(data.Load())
```
Alternatively, use a channel or `sync.Once`.

G8 — `sync.Mutex` provides exclusive locking. `sync.RWMutex` allows multiple concurrent readers or one writer. `sync.Map` is optimized for read-heavy workloads, keys known at startup, or disjoint key sets across goroutines. Trade-offs: `sync.Map` has higher read latency and complex internals; a regular `map` + `sync.RWMutex` is usually faster and simpler for general use.

G9 — `go.mod` declares module path, Go version, and direct dependencies. `go.sum` stores cryptographic hashes of downloaded modules for integrity verification. `go mod tidy` removes unused dependencies, adds missing ones, and updates versions. MVS (Minimum Version Selection) resolves the dependency graph to the lowest compatible versions that satisfy all requirements, preventing version bloat.

G10 — `defer` schedules a function call to run after the surrounding function returns. Multiple defers execute in LIFO order. Common loop gotcha: variables captured by deferred closures are evaluated at defer time, not declaration time. Fix by passing as arguments: `defer func(v int) { fmt.Println(v) }(i)`.

G11 — A pointer holds the memory address of a value. Zero value: `nil`. Create pointer to struct literal: `&MyStruct{Field1: val1, Field2: val2}`.

G12 — `init()` runs automatically before `main()` executes. It runs once per package. A package can have multiple `init()` functions; they execute in source file order, then within each file in declaration order. Cross-package `init()` calls follow dependency order.

G13 — `new(T)` allocates zeroed memory for type `T` and returns `*T`. `make(T, args)` initializes and returns a ready-to-use `slice`, `map`, or `chan` (not a pointer). `make` is only for built-in reference types.

G14 — Go uses explicit error values. `error` is an interface with `Error() string`. Idiomatic: `if err != nil { ... }`. `errors.Is(err, target)` checks if `err` matches `target` in the error chain (unwrap). `errors.As(err, &target)` checks type and extracts the value. `==` only checks exact equality and ignores wrapped errors.

G15 — Zero values: `map` → `nil` (use `make`), `slice` → `nil` (len=0, cap=0), `channel` → `nil` (blocks forever), `struct` → zero values of each field.

G16 — A race condition occurs when concurrent goroutines access shared data without synchronization, causing undefined behavior. `-race` flag instruments the runtime to detect conflicting reads/writes. Example: `var c int; go func(){c++}(); c++`. Fix with `sync.Mutex` or a channel for communication.

G17 — `select` waits on multiple channel operations, like a `switch` for channels. If multiple cases are ready, one is chosen pseudo-randomly. Timeout: `case <-time.After(d):`. Blocks until at least one case is ready or default is present.

G18 — Escape analysis determines whether variables allocate on the stack or heap. Escapes if: address is taken, returned, stored in a heap-allocated struct, or size is unknown at compile time. Inspect with `go build -gcflags="-m"`. Matters because heap allocations trigger GC pressure; stack allocations are faster and zero-cost.

G19 — `reflect.Type` holds type metadata; `reflect.Value` holds the actual value/data. Costs: slow, bypasses compile-time checks, causes allocations. Justified in serialization, ORMs, or testing frameworks. Prefer code generation (`go generate`, `stringer`, `protoc`) for performance-critical paths.

G20 — `//go:embed` embeds compile-time known files/directories into the binary. `var f embed.FS` implements `io/fs.FS`. Directories: `//go:embed dir/...` embeds recursively. Limitations: only static files, no runtime generation, size constraints. Interacts with `io/fs.FS` by providing a read-only, embeddable filesystem view.

R1 — Ownership ensures memory safety without GC. Rules: 1. Each value has exactly one owner. 2. Only one owner at a time. 3. Owner drops value when out of scope. Prevents leaks/dangling pointers via deterministic cleanup.

R2 — `String` is a heap-allocated, growable, owned UTF-8 string. `&str` is an immutable string slice (reference to UTF-8 bytes). Use `String` when you need ownership/modification. Use `&str` in function signatures to avoid allocations and accept both `&String` and `&str` via deref coercion.

R3 — Borrowing provides references without transferring ownership. `&T`: shared read-only, multiple allowed. `&mut T`: exclusive mutable, only one allowed, no other refs during borrow. Borrow checker enforces these rules at compile time to prevent data races and use-after-free.

R4 — `Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`). `Option<T>` represents `Some(T)` or `None`. `?` propagates errors/returns early. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```

R5 — `Box<T>`: heap-allocates, single owner, moves data. `Rc<T>`: reference-counted, single-threaded shared ownership. `Arc<T>`: atomic reference-counted, thread-safe shared ownership. Use `Box` for large data/ownership, `Rc` for single-thread shared, `Arc` for multi-thread shared.

R6 — Traits are Rust's interface mechanism with optional default methods. Like Go interfaces but explicit. `dyn Trait`: trait object, dynamic dispatch via vtable, heap-allocated usually. `T: Trait`: generic with trait bound, static dispatch, monomorphization, zero-cost.

R7 — Compiler can't infer which input lifetime applies to the output. Fix by explicitly tying output lifetime to inputs:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

R8 — `Send`: safe to transfer ownership across threads. `Sync`: safe to share `&T` across threads. `Rc<T>` isn't `Send`/`Sync` due to non-atomic ref count. `Arc<T>` uses atomic ref counting, making it `Sync` (and `Send` if `T: Send`).

R9 — `async/await` compiles to a state machine implementing the `Future` trait. `await` yields control, executor polls the future. Tokio: runtime/executor that drives futures, handles I/O, and manages threads. Differs from Go: Go uses implicit M:N scheduling in the runtime; Rust futures are explicit state machines polled by user-provided executors, with no implicit threading.

R10 — `unsafe` bypasses compiler safety checks. Three things: dereference raw pointers, call `unsafe` functions, implement `unsafe` traits, access/modify `static mut`. Justified for FFI, low-level sys ops, performance-critical code, or building safe abstractions over unsafe foundations.

R11 — Pattern matching exhaustively handles enum variants. `match` binds values and requires exhaustiveness. `if let` is concise for a single case. Compiler enforces exhaustiveness in `match` (must handle all variants or use `_` wildcard).

R12 — `Vec<T>`: heap-allocated, dynamic size. `[T; N]`: stack-allocated (usually), fixed size. When `Vec` capacity is exceeded, it allocates a new larger buffer, moves elements, drops the old buffer, and updates pointer/len/cap.

R13 — Enums are algebraic data types; each variant can hold data. Unlike C (int-backed) or Java (class-based). `Option<T>` = `Some(T)` | `None`. Rust has no `null` to prevent null pointer exceptions and force explicit handling.

R14 — `impl` blocks define methods. `&self`: immutable borrow, can't modify. `&mut self`: mutable borrow, can modify. `self`: takes ownership, consumes the instance. Associated functions (e.g., `String::new()`) don't take `self` and act like static methods.

R15 — `#[derive]` auto-implements traits. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Can't derive if: fields lack the trait, custom logic is needed, or the trait requires manual implementation (e.g., `Drop`, `Fn`).

R16 — `Cow<'a, T>` (Clone on Write) borrows data by default, clones only on mutation. Useful for functions returning borrowed or owned data. Example: `fn process(s: &str) -> Cow<str> { if cond { Cow::Borrowed(s) } else { Cow::Owned(s.to_uppercase()) } }` avoids allocation when borrowing.

R17 — `mod` declares a module, `use` imports names into scope, `pub` makes items public. File system: `mod.rs` or `name.rs` in directories. Rust 2018: `use` paths relative to crate root, introduced `super`/`self`, removed `extern crate`.

R18 — `Pin<T>` guarantees a value's memory location won't change. Needed for self-referential structs and async/await (futures may hold references to their own fields). `Unpin` is a marker trait; most types are `Unpin` by default (pinning has no effect). `!Unpin` types must be pinned to be used safely.

R19 — Declarative macros (`macro_rules!`) use pattern matching on token trees. Procedural macros: `derive` (struct/enum), `attribute` (custom attrs), `function-like`. Hygiene ensures macro-generated identifiers don't capture or collide with caller scope, preventing unexpected behavior.

R20 — Zero-cost abstractions compile high-level features to efficient machine code. Iterators: zero overhead, loop unrolling, no bounds checks. Generics: monomorphization generates type-specific code. Traits: static dispatch (vtable only with `dyn`). Achieves C-like performance while maintaining safety and ergonomics.
