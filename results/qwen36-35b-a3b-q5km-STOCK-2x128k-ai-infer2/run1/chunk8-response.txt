**CL1** IaaS provides virtualized compute, storage, and networking where you manage the OS, middleware, runtime, data, and applications (e.g., AWS EC2). PaaS provides a managed runtime and middleware where you only manage applications and data (e.g., Google App Engine). SaaS delivers fully managed applications where you only manage user access and configuration (e.g., AWS WorkSpaces or Salesforce).

**CL2** The Shared Responsibility Model divides security: the provider secures the global infrastructure, hardware, and managed service control planes; you secure what you put in it. For IaaS VMs, the provider handles physical security, hypervisor, and host OS; you handle guest OS patching, network config, data, and apps. For managed Kubernetes (EKS/AKS), the provider secures the control plane and node OS; you secure worker node config, network policies, RBAC, secrets, and workloads. For SaaS like M365, the provider secures the app, infra, and compliance; you secure data, user identities, MFA, sharing policies, and endpoint access.

**CL3** A VPC is an isolated virtual network. Subnets partition the VPC into IP ranges (public/private). Security Groups (SGs) are stateful, instance/pod-level firewalls that only allow rules. Network ACLs (NACLs) are stateless, subnet-level firewalls that evaluate rules in order and support allow/deny. Traffic flows: VPC → Subnet (NACL evaluated first) → Instance/ENI (SG evaluated second). Stateful (SG) automatically allows return traffic; stateless (NACL) requires explicit return rules.

**CL4** A landing zone is a pre-configured, secure multi-account foundation. Organizational Units (OUs) logically group accounts (e.g., prod, dev, security, shared services). Guardrails (SCPs, IAM boundaries, Config Rules) enforce compliance and prevent misuse. Shared networking uses Transit Gateway or Azure Hub-and-Spoke for centralized inter-VPC/VNet routing and connectivity. Centralized logging aggregates CloudTrail/Log Analytics into a security account. Single-account approaches cause excessive blast radius, permission sprawl, billing opacity, compliance isolation failures, and accidental deletion risks.

**CL5** IaC manages infrastructure via machine-readable definitions. Terraform/OpenTofu: declarative, HCL, provider-agnostic, massive ecosystem; best for multi-cloud, large teams, and established workflows. Pulumi: imperative/declarative using general-purpose languages (TS, Python, Go); best for complex logic, dynamic infra, and existing dev teams. CloudFormation/Bicep: AWS-native declarative; Bicep offers cleaner syntax; best for AWS-only environments and tight CI/CD integration. Crossplane: Kubernetes-native IaC using CRDs to manage cloud resources; best for GitOps/K8s-centric teams and multi-cloud abstraction.

**CL6** HPA scales pods based on CPU/memory/custom metrics. VPA recommends/sets optimal resource requests/limits per pod. Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external event triggers (Kafka, queues, HTTP). Use KEDA over HPA for event-driven, async workloads where CPU/metrics don't correlate with load (e.g., message queue processing). HPA is better for stateless web apps with predictable resource consumption.

**CL7** Define RPO (max tolerable data loss) and RTO (max tolerable downtime). Active-active runs both regions simultaneously with sync replication for near-zero RPO/RTO but doubles cost/complexity. Active-passive runs one region, fails over to standby; higher RPO/RTO, lower cost. DB sync replication ensures consistency but adds latency; async replication reduces latency but risks data loss. DNS failover (Route53/Traffic Manager) uses health checks to route traffic. State must be externalized (DB, object storage, distributed cache). Pilot light: core infra runs at minimum capacity. Warm standby: scaled-down prod environment. Multi-site active-active: full production in both regions.

**CL8** GitOps uses Git as the single source of truth; declarative controllers continuously reconcile cluster state to match Git. ArgoCD is push-based (polls Git, pushes to cluster), UI-focused, beginner-friendly. FluxCD is pull-based (runs in cluster, watches Git), Git-native, tightly integrated with CI. Secrets: Sealed Secrets encrypt in Git, decrypted by controller; External Secrets Operator syncs from cloud vaults; Vault provides dynamic secrets and auth. Manual drift is detected by controllers and automatically reverted to the Git state, preserving auditability.

**CL9** Use a StatefulSet for stable network IDs and ordered deployment. Configure PV/PVC with a `local` storageClass and `volumeBindingMode: WaitForFirstConsumer` to bind to the node with the local disk. Use a headless service (`clusterIP: None`) for direct pod DNS resolution. Init containers prepare filesystems and validate dependencies. Mount ConfigMaps as volumes at required paths. Set a PodDisruptionBudget (`minAvailable: 1` or `maxUnavailable: 0`) to prevent concurrent disruptions. Note: local storage lacks replication; accept the trade-off or implement app-level redundancy.

**CL10** A K8s Service Account is a native identity with no cloud IAM binding. Workload Identity (GCP) and IRSA (AWS) map K8s SAs to cloud service accounts via OIDC federation. Mounting static cloud credentials in pods leaks keys, complicates rotation, violates least privilege, and persists across pod lifecycles. Federation solves this by exchanging short-lived OIDC tokens for temporary cloud credentials at runtime, eliminating static secrets.

**CL11** Object storage (S3/Blob) stores unstructured data via HTTP API, scales infinitely, and offers 99.999999999% durability; ideal for backups, media, and data lakes. Block storage (EBS/Managed Disk) provides raw, low-latency volumes attached to VMs (99.9-99.99% durability); ideal for OS, databases, and apps. File storage (EFS/Azure Files) offers shared NFS/SMB access; ideal for shared configs, home directories, and legacy apps. Object is regional/AZ-redundant; block is AZ-bound; file is regional with AZ failover.

**CL12** Zero-trust K8s eliminates implicit trust. Default-deny Network Policies restrict pod-to-pod traffic. A service mesh (Istio/Linkerd) enforces mTLS and identity-based routing. Pod identity (IRSA/Workload Identity) binds workloads to cloud IAM. Admission controllers (OPA/Kyverno) enforce policies at deployment. Image signing (Cosign) verifies signatures before admission. Runtime security (Falco) monitors syscalls for anomalies. Secrets are managed via External Secrets Operator/Vault. Unlike perimeter security, zero-trust authenticates/authorizes every request, micro-segments traffic, and assumes breach.

**CL13** A CDN is a globally distributed edge cache network that serves static content closer to users, reducing latency and origin load. It works by DNS routing to the nearest edge node, which serves cached content or fetches from the origin. Cloud-native examples: AWS CloudFront, Azure CDN, Fastly. Use a CDN for static assets, media, global distribution, and DDoS mitigation. Serve directly from origin for dynamic, personalized, or highly volatile data.

**CL14** A region is a geographic area containing multiple Availability Zones (AZs). AZs are isolated data centers with independent power, cooling, and networking. Deploying across multiple AZs ensures fault tolerance against AZ failure and enables low-latency synchronous replication. Zonal resources (e.g., EBS, NAT Gateway) are tied to a single AZ. Regional resources (e.g., ALB, Route53, S3) span multiple AZs for high availability.

**CL15** A managed database service (RDS, Cloud SQL, Azure SQL) abstracts operational overhead. The provider handles provisioning, OS patching, backups, replication, monitoring, and automated failover. Running a DB on a VM requires you to manage the OS, database software, backup schedules, replication setup, scaling, HA architecture, and security patches. Managed services trade some low-level control for faster deployment and reduced operational burden.

**CL16** IAM Users are human/service identities. Groups bundle users for policy assignment. Roles provide temporary, assumable credentials for users, services, or external entities. Policies are JSON documents defining allowed/denied actions. Least privilege grants only the permissions necessary to perform a task. Apply it by using roles over long-lived users, scoping policies to specific resources/actions, enforcing deny-by-default, implementing just-in-time access, and conducting regular access reviews.

**CL17** Serverless computing provides managed, auto-scaling, pay-per-use compute without server management. AWS Lambda, Azure Functions, and GCP Cloud Functions share this model but differ in ecosystem integration, runtime support, and tooling. Cold starts occur when a container is provisioned after an idle period, adding latency. They matter for latency-sensitive APIs; mitigate with provisioned concurrency, smaller packages, and lighter runtimes. Serverless is a poor fit for long-running processes, stateful apps, high memory/CPU workloads, or environments requiring dedicated hardware for compliance.

**CL18** Ingress Resource: Standard K8s API relying on an Ingress Controller (NGINX, ALB); TLS terminates at the controller. Gateway API: Newer standardized API separating routing (Gateway) from backend (HTTPRoute); TLS terminates at the Gateway. Cloud LB annotations: Direct cloud load balancer integration; TLS terminates at the cloud LB. Service Mesh Ingress: Mesh gateway handles mTLS, traffic management, and observability. Use Gateway API over Ingress for standardized routing, multi-tenant control, advanced features (gRPC, WebSocket), and avoiding controller-specific annotations.

**CL19** Reserved Instances/Savings Plans commit to 1-3 years for predictable workloads (up to 72% savings). Spot/Preemptible instances offer up to 90% off for fault-tolerant/batch workloads. Right-size by monitoring utilization and adjusting resources. Tier storage using S3 Intelligent-Tiering and Archive/Glacier for cold data. Detect idle resources via native cost tools and tagging. Implement FinOps: cross-functional culture, showback/chargeback via cost allocation tags, monthly reviews, and budget alerts. Tools: Kubecost/OpenCost, CloudHealth, native cost explorers. Process: strict tagging, team accountability, and automated cost anomaly detection.

**CL20** Multi-cloud avoids vendor lock-in using abstraction layers: Kubernetes as a common runtime, Terraform for provider-agnostic IaC, and service meshes/API gateways for portability. Networking uses cloud VPNs, Direct Connect/ExpressRoute, and global DNS. Identity federation uses OIDC and centralized SSO. Trade-offs: increased complexity, data egress costs, inconsistent feature parity, and operational overhead vs. risk mitigation, negotiation leverage, and regulatory compliance. Multi-cloud is justified for strict data residency, catastrophic vendor risk, or specific service needs. It's unnecessary complexity for most organizations where vendor lock-in is manageable and multi-cloud adds cost without clear ROI.

**OT1** The Purdue Model (ISA-95) defines industrial hierarchy. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs). Level 2: Supervisory (SCADA, HMIs). Level 3: Operations/Plant (MES, historians). Level 4: Enterprise (ERP, business planning). Level 5: Strategic/Corporate.

**OT2** IT networks prioritize confidentiality and integrity, support high bandwidth, and allow frequent patching. OT networks prioritize availability and safety, require deterministic latency, and run legacy systems. Standard IT patching is unsafe in OT because updates can break process control, trigger safety systems, or require extended maintenance windows that disrupt production. OT changes require rigorous testing, change management, and scheduled downtime.

**OT3** An Industrial DMZ (IDMZ) is a segmented buffer zone between IT and OT networks. Traffic should be strictly controlled: typically one-way OT→IT for telemetry, and IT→OT commands routed through the IDMZ via firewalls or data diodes. Direct L4→L1 connectivity is dangerous because it bypasses segmentation, exposes the control network to IT threats, increases blast radius, and violates safety/security boundaries.

**OT4** 1. Modbus TCP: L1/L2, unencrypted PLC communication. 2. OPC UA: L2/L3, secure, platform-independent, modern standard. 3. EtherNet/IP (CIP): L1/L2, Allen-Bradley dominant, industrial Ethernet. 4. PROFINET: L1/L2, Siemens dominant, real-time Ethernet. 5. MQTT: L3/L4, lightweight publish/subscribe for cloud/edge data transfer.

**OT5** A data diode is a hardware-enforced one-way communication device that physically prevents return traffic. A firewall inspects and filters bidirectional traffic based on rules. Use a data diode when strict one-way data flow is required (e.g., OT telemetry to IT) with zero return traffic allowed. Limitation: cannot support bidirectional protocols, command/control, or acknowledgments, making it less flexible than firewalls.

**OT6** Data flow: PLCs → Historian (L3) → OPC UA Server → Edge Gateway (protocol translation, buffering) → MQTT Broker (TLS) → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: IDMZ between OT and edge/cloud. Enforce TLS/mTLS everywhere. Edge gateway authenticates, filters, and buffers. Cloud uses IAM, VPC, and WAF. Deploy IDS at boundaries and segment networks to limit lateral movement.

**OT7** IEC 62443 defines security zones (logical groups of assets with similar requirements) and conduits (communication paths with defined controls). Zone model: Zone 1: Corporate (L4). Zone 2: Engineering/SCADA (L3). Zone 3: Control/PLCs (L1/L2). Zone 4: SIS (safety). Conduits: Strict firewall rules, data diodes for OT→IT, jump hosts for engineering, isolated VLANs, and mTLS for control comms. SIS zone is air-gapped or heavily restricted to prevent common-cause failures.

**OT8** VLAN design: Segment by function/process (e.g., VLAN 10: Line 1 PLCs, VLAN 20: Line 2, VLAN 30: HMIs, VLAN 40: SCADA/History). Firewall placement: Core firewall between IT/OT, edge firewalls per VLAN/zone. Switch architecture: Managed L3 switches, port security, disable unused ports. Remote access: Secure jump host in IDMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, and close monitoring.

**OT9** BPCS (Basic Process Control System) handles normal process control. SIS (Safety Instrumented System) is independent and triggers a safe state during hazardous conditions. IEC 61511 defines the safety lifecycle and SIL requirements for SIS. The SIS network must be air-gapped or isolated to prevent common-cause failures; IT/BPCS compromise must not affect safety. Ransomware on SIS could disable safety functions, causing catastrophic failure, environmental damage, or loss of life.

**OT10** PLC: Discrete control, fast, localized, handles I/O directly; used for machine/line control. DCS: Centralized control, integrated I/O, suited for continuous/process industries; better for complex, large-scale processes. SCADA: Supervisory data acquisition and HMI for remote monitoring; commands PLCs/RTUs but doesn't directly control. They coexist commonly: SCADA supervises DCS/PLCs, DCS handles process, PLCs handle discrete machines.

**OT11** Remote access must use isolated jump hosts in the IDMZ, mandatory MFA, session recording, time-limited scoped vendor accounts, and auto-expiry. RDP directly to an HMI from corporate is unacceptable because it bypasses segmentation, exposes OT directly to corporate threats, enables lateral movement, lacks audit control, and violates the Purdue model.

**OT12** Detection: Passive IDS (Zeek/Suricata), network anomaly detection, passive asset inventory, OT-specific SIEM rules. IR steps: Contain (isolate VLANs, disable compromised VPN), investigate (forensics, log analysis), eradicate (patch, rotate creds), recover (restore clean backups), lessons learned. Coordination: Notify control room, switch to manual/local control if needed, prioritize physical safety and water quality. Operator role: Monitor process safety, execute manual overrides, communicate status, avoid network changes. Safe ops: Maintain process stability, isolate cyber threat without disrupting critical treatment.

**OT13** An HMI (Human-Machine Interface) is an operator display for monitoring real-time process data, alarms, and manual controls. It provides situational awareness and enables intervention. It differs from an engineering workstation, which is used for offline/online programming, logic editing, firmware updates, and system configuration, not routine operations.

**OT14** A historian is a time-series database optimized for high-frequency process data (temperatures, pressures, flows). It enables process optimization, compliance, troubleshooting, and predictive maintenance. Plant historian (L3) stores real-time/near-real-time, high-frequency data for immediate operations. Enterprise historian (L4) stores aggregated, lower-frequency data for business reporting, financial analysis, and long-term retention.

**OT15** Ladder logic is a graphical programming language mimicking relay circuits, using contacts, coils, and timers. It executes on PLCs. It remains dominant because it's familiar to electricians, easy to troubleshoot, deterministic, widely supported, has a low barrier to entry, and benefits from decades of legacy code and ecosystem maturity.

**OT16** An RTU (Remote Terminal Unit) is designed for harsh environments, long-distance communication (serial, cellular, satellite), simple I/O, and robustness. A PLC is localized, handles complex logic, processes faster, and supports rich I/O/Ethernet. RTUs are deployed in pipelines, SCADA remote sites, utilities, and harsh/remote locations where connectivity is limited and environmental conditions are extreme.

**OT17** Analog signals are continuous (4-20mA, 0-10V); digital signals are discrete or protocol-based. 4-20mA is preferred over 0-20mA because 4mA acts as a "live zero," allowing the system to distinguish between a valid zero signal and an open-circuit/wire break (0mA). It's also less susceptible to noise over long distances.

**OT18** OT asset inventory is a complete list of hardware, firmware, network configs, and communication patterns. It's the foundation for risk assessment, patching, segmentation, and compliance. Tools: passive network monitoring (packet capture, protocol analyzers) and cautious active scanning. Active scanning is dangerous because it can crash legacy devices, trigger safety systems, cause process disruption, or generate unexpected traffic.

**OT19** MITRE ATT&CK for ICS maps tactics/techniques specific to industrial environments. Examples: Reconnaissance (Gather Victim Network Information), Initial Access (Supply Chain Compromise), Execution (Command and Scripting Interpreter), Persistence (Data Manipulation), Impact (Inhibit Response Function). It differs from Enterprise ATT&CK by focusing on physical processes, safety, legacy protocols, and real-time constraints. Use it to map current defenses, identify gaps, prioritize controls, and align with IEC 62443.

**OT20** Log collection: Passive taps, OT-friendly agents, syslog forwarding, edge buffering to avoid impacting real-time ops. SIEM: Normalize OT logs, correlate with IT logs. Detection rules: OT-specific (unusual PLC writes, unexpected protocol traffic, HMI config changes, after-hours access). Triage: OT engineers validate process impact, IT analysts handle threat intel. Staffing: IT analysts (threat hunting, malware), OT engineers (process safety, protocols), cross-trained. False positives: Tune rules, baseline normal behavior, use allowlists, account for maintenance cycles. Unauthorized firmware on PLC: Isolate segment, verify with engineering, check change management, rollback if unauthorized, investigate source, update detection rules, report to management.
