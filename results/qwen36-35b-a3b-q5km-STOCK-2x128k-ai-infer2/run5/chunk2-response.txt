K1 — A **Deployment** manages stateless workloads with interchangeable pods; pod names/IDs change on restart. A **StatefulSet** manages stateful workloads with stable, unique network identifiers (hostname), stable storage volumes, and ordered, graceful deployment/termination.

K2 — A `ClusterIP` Service creates a virtual IP and a set of backend pod IPs (Endpoints). `kube-proxy` watches the API server, then programs node-level `iptables` or `IPVS` rules to DNAT traffic hitting the Service IP to one of the healthy pod IPs, using round-robin or connection-affinity load balancing.

K3 — **PersistentVolume (PV)**: cluster-provisioned storage resource (static or dynamic). **PersistentVolumeClaim (PVC)**: user request for storage with specific size/access modes. **StorageClass**: defines storage provisioner and parameters for dynamic PV creation. Relation: A PVC binds to a matching PV (static) or triggers a StorageClass to dynamically provision a PV, which then binds to the PVC.

K4 — 1. `kubectl logs <pod>` to check application errors or stack traces. 2. `kubectl describe pod <pod>` to check for OOMKilled events or probe failures. 3. Verify container image exists and env/config mounts are valid. 4. Check dependencies (DB, network, secrets) and resource limits vs actual usage.

K5 — CoreDNS provides internal DNS resolution for `Service` names and pod FQDNs. If CoreDNS pods are down, DNS resolution fails cluster-wide; services become unreachable by name, but direct `ClusterIP` or pod IP communication continues to work.

K6 — **Filtering**: removes nodes that don't meet requirements (taints/tolerations, affinity/anti-affinity, volume constraints, resource capacity). **Scoring**: ranks remaining nodes based on resource balance, topology spread, and priority. **Factors**: 1) CPU/memory request vs capacity, 2) Node taints/tolerations, 3) Pod/node affinity rules, 4) Volume topology constraints, 5) Resource pressure (disk/memory).

K7 — Yes, it will schedule. 3.5GB + 256Mi ≈ 3840Mi < 4096Mi (4GB). At runtime, using 600Mi exceeds the 512Mi limit; the cgroup OOM killer terminates the container, and Kubernetes restarts it (potentially entering CrashLoopBackOff if it consistently exceeds the limit).

K8 — 1. Client hits external Load Balancer (cloud LB). 2. LB forwards to Ingress Controller (NGINX pod). 3. Controller reads Ingress resource, matches host/path to backend Service. 4. Service resolves to healthy pod IPs via Endpoints. 5. `kube-proxy` updates `iptables`/`IPVS` rules on the node to DNAT traffic to those pod IPs. 6. Packet reaches the application pod.

K9 — A `NetworkPolicy` restricts pod-to-pod and pod-to-external traffic. Default behavior (no policy): all ingress/egress allowed. When applied: traffic to/from selected pods is denied by default; only explicitly allowed rules (by pod selector, namespace, or CIDR) pass.

K10 — **RollingUpdate**: gradually replaces old pods with new ones, ensuring zero downtime. **Recreate**: terminates all existing pods before starting new ones. Choose Recreate for stateful services, databases, or when configuration/state requires a full stop to avoid conflicts or corruption.

K11 — A namespace provides virtual cluster isolation (resource quotas, RBAC, network policies). Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it displays: 1) Pod events (scheduling, pull, probe failures), 2) Container conditions & restart counts, 3) Resource requests/limits & actual usage, 4) Environment variables, volume mounts, and probe configurations.

K13 — A ConfigMap stores non-confidential configuration data. Pods consume it via: 1) Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`), 2) Volume mounts (files appear in the container filesystem).

K14 — **ClusterIP**: internal-only virtual IP, accessible only within the cluster. **NodePort**: exposes the Service on a static port on each node's IP (`<NodeIP>:<NodePort>`). **LoadBalancer**: provisions a cloud provider external load balancer with a public IP and routes traffic to the Service.

K15 — A DaemonSet ensures a copy of a pod runs on every node (or subset via selector). Use instead of a Deployment for cluster-wide agents: logging (Fluentd), monitoring (node-exporter), CNI plugins, or storage daemons.

K16 — **Taints/Tolerations**: node-level repulsion mechanism. Taints mark nodes; tolerations allow pods to schedule on them. **Node Affinity**: node-level attraction mechanism; schedules pods to nodes matching labels. Use case taint: GPU nodes tainted to repel CPU-only pods. Use case affinity: schedule to specific AZ/zone for latency.

K17 — An Operator is a custom Kubernetes controller that manages complex, stateful applications via Custom Resource Definitions (CRDs). Unlike standard controllers (which watch built-in resources), Operators encode human operational knowledge (backups, upgrades, failover) into reconciliation loops, automating lifecycle management of stateful services.

K18 — etcd uses **linearizable reads** and **serializable writes** via Raft consensus. If quorum is lost, the cluster becomes read-only/unwritable. Recovery from 2/3 node loss: restore the latest etcd snapshot + WAL on the surviving node, then rejoin new nodes to the cluster.

K19 — **Role/ClusterRole**: defines permissions (verbs + resources). **RoleBinding/ClusterRoleBinding**: binds roles to users/groups/ServiceAccounts. Manifest for read-only pods/logs in `dev` namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` in `/etc/resolv.conf` causes the resolver to try appending `.svc.cluster.local`, `.cluster.local`, `.default.svc.cluster.local`, etc., before using the FQDN. For `google.com`, this generates 5+ queries, causing latency. Fix: set `dnsConfig: { ndots: 2 }` in the pod spec, or use a trailing dot for absolute FQDNs (`google.com.`).

D1 — `git merge` creates a merge commit, preserving full branch history. `git rebase` rewrites commits onto a new base, creating linear history. Avoid rebasing on shared/public branches to prevent forcing others to reconcile divergent histories.

D2 — **TCP**: connection-oriented, reliable, ordered delivery, flow/congestion control. **UDP**: connectionless, unreliable, low latency, no ordering. TCP: HTTP, SMTP, FTP. UDP: DNS, VoIP, DHCP.

D3 — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to non-deterministic results. Example: two threads incrementing a shared counter without a mutex; final value may be less than expected due to lost updates.

D4 — **Symmetric**: single shared key for encryption/decryption (fast). **Asymmetric**: public/private key pair (secure key exchange, slower). TLS uses asymmetric encryption during handshake to authenticate and exchange a session key, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates a read-only image layer. Layer caching reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., install dependencies first, copy source code later) to maximize cache hits and speed up builds.

D6 — Order of checks: 1. Upstream application logs/metrics for errors or timeouts. 2. Resource exhaustion (CPU throttling, OOMKilled). 3. Rate limiting, circuit breakers, or dependency degradation. 4. Load balancer/ingress health check configuration or backend pool status.

D7 — CAP theorem: a distributed system can guarantee at most two of Consistency, Availability, Partition tolerance. **CP**: distributed SQL (CockroachDB, HBase) – prioritizes data correctness during network splits. **AP**: DNS, Cassandra, DynamoDB – prioritizes uptime and responsiveness, accepting stale reads during partitions.

D8 — **Horizontal scaling**: adding more instances/nodes. **Vertical scaling**: increasing CPU/RAM of existing instances. Horizontal scaling requires: stateless application logic, externalized state (DB/cache), consistent hashing/sharding, and load balancing.

D9 — An environment variable is a dynamic named value that affects process behavior. Persist across sessions: add `export VAR_NAME="value"` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict syntax, key-value pairs, arrays. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: strict parsing, universal language support. YAML advantage: readability, less verbose, easier for config files.

D11 — A REST API is an architectural style using standard HTTP methods to interact with resources. **GET**: retrieve data. **POST**: create new resource. **PUT**: replace/update entire resource. **DELETE**: remove resource.

D12 — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3` or `package-lock.json`). Ensures reproducible builds, prevents unexpected breaking changes, and guarantees identical environments across dev, CI, and production.

D13 — **Compiled**: source code translated to machine code before execution (C, Rust). **Interpreted**: source code executed line-by-line at runtime by an interpreter (Python, JavaScript). Note: many modern languages use hybrid approaches (JIT compilation).

D14 — **Reverse proxy**: sits in front of servers, routes client requests to backend services (load balancing, SSL termination). **Forward proxy**: sits in front of clients, routes outbound requests (caching, filtering, anonymity). Examples: Nginx (reverse, API gateway/load balancing), Squid (forward, corporate caching/filtering).

D15 — A deadlock occurs when two or more threads are permanently blocked, each waiting for a resource held by another. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait.

D16 — Eventual consistency guarantees that if no new updates occur, all replicas will eventually converge. Cassandra handles read-after-write by using tunable consistency levels: `QUORUM` for both read/write ensures most replicas agree; `SERIALIZABLE` or `LOCAL_SERIAL` provides strict ordering. Causal consistency features also preserve session guarantees.

D17 — mTLS requires both client and server to present valid certificates. Handshake: ClientHello → ServerHello+Cert → ServerKeyExchange → ClientKeyExchange+Cert → CertificateVerify → Finished. Both sides validate certs against a trusted CA. Commonly used in: service meshes (Istio/Linkerd), internal microservices, zero-trust architectures.

D18 — A hash table maps keys to values via a hash function. Collision resolution: **chaining** (linked lists at each bucket), **open addressing** (linear/quadratic probing, double hashing). Time complexity: average O(1) for insert/lookup/delete; worst-case O(n) when all keys hash to the same bucket (poor hash function or high load factor).

D19 — A circuit breaker monitors downstream calls and fails fast when errors exceed a threshold. States: **Closed** (normal traffic), **Open** (fail fast, trip after threshold), **Half-open** (allow limited test requests). Prevents cascade failures by stopping retries. Relates to retry/backoff: circuit breaker disables retries when open; exponential backoff reduces load during recovery before transitioning to half-open.

D20 — **Optimistic**: assumes no conflicts, validates at commit using row versioning/ETags. **Pessimistic**: locks rows/tables during transaction. Choose optimistic for high read/low write contention; pessimistic for high write contention or critical financial data. Example: Optimistic: `UPDATE accounts SET balance=balance-100 WHERE id=1 AND version=5`. Pessimistic: `SELECT balance FROM accounts WHERE id=1 FOR UPDATE` then `UPDATE`.
