AA1 — A monolith is a single codebase deployed as one unit with shared process/memory/DB. Microservices decompose into independently deployable, loosely coupled services with separate DBs/processes. Microservices introduce: (1) network latency & partial failure handling, (2) distributed data consistency & cross-service transactions, (3) operational complexity (orchestration, CI/CD, observability, service discovery).

AA2 — Synchronous: caller blocks until response arrives; tight coupling, real-time. Example: REST/gRPC. Asynchronous: caller sends request and continues; decoupled, eventual processing. Example: RabbitMQ/Kafka. Async improves resilience and throughput but adds complexity in ordering and state tracking.

AA3 — A reverse proxy routes traffic, terminates TLS, load balances, and caches. An API gateway adds API-specific logic: auth, rate limiting, request/response transformation, versioning, and analytics. An API gateway can technically replace a reverse proxy, but in practice they're layered: a lightweight reverse proxy (NGINX/Traefik) handles edge TLS/SSL and DDoS mitigation, while the API gateway sits behind it for business routing. Replacing entirely adds latency and operational overhead to the gateway.

AA4 — A Saga breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo if a step fails. Choreography: services publish events that trigger next steps; decentralized, loosely coupled, but hard to monitor/debug. Orchestration: a central coordinator sends commands; easier to track, rollback, and enforce business rules, but introduces a coordination bottleneck. Use choreography for simple, decoupled workflows; orchestration for complex, stateful, or regulated processes.

AA5 — CQRS separates read (query) and write (command) models. Event Sourcing stores state changes as immutable events instead of current state. They pair naturally because events drive command processing and can be replayed to rebuild read models. This combination solves auditability, temporal queries, complex domain logic, and independent scaling of reads/writes—problems where CRUD struggles with consistency, replayability, and write/read contention.

AA6 — A circuit breaker stops calls to a failing service to prevent cascading overload. States: Closed (normal), Open (fail fast), Half-Open (probe recovery). Differs from retry/backoff: retry assumes transient failure and attempts again; circuit breaker halts calls after a threshold to protect the system. Use both together: retry/backoff handles transient glitches inside Closed/Half-Open states; circuit breaker opens on sustained failures to prevent resource exhaustion.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, simplest ops.
2. Shared DB, separate schema: Moderate cost, better isolation/noisy-neighbor mitigation, moderate ops complexity, per-schema backup/restore.
3. Separate DB per tenant: Highest cost, best isolation/security, lowest noisy-neighbor risk, highest ops complexity (provisioning, backup, scaling). Choice depends on compliance, budget, and tenant size.

AA8 — Eventual consistency: updates propagate asynchronously; reads may be stale. Strong consistency: all reads see the latest write; requires coordination/locking. For inventory oversell prevention: use strong consistency. Data store: Distributed SQL (CockroachDB/TiDB) or relational DB with row-level locking. Patterns: optimistic concurrency control with versioning, distributed locking per SKU, reservation/hold system, idempotent stock deduction, outbox pattern for sync, and queue-based processing with strict per-SKU ordering.

AA9 — A sidecar proxy co-locates with a service to intercept all inbound/outbound traffic. In Istio, Envoy handles L7 routing, mTLS, retries, and metrics. Data plane = Envoy proxies; control plane = Istiod pushes config/certs/policies. mTLS solves: transparent east-west security without code changes, automatic cert rotation, service identity verification, and MITM prevention. Application TLS requires manual cert management, code changes, and doesn't secure internal mesh traffic automatically.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is removed. Strategy: place an API gateway in front of the .NET Framework monolith. Identify a bounded context (e.g., user auth, billing). Build the new .NET 8 microservice. Route specific endpoints/paths to it via the gateway. Migrate data using dual-write or CDC. Repeat per module, use feature flags for safe rollout, and decommission monolith routes as traffic shifts.

AA11 — 12-Factor App is a methodology for cloud-native SaaS best practices. Six factors: (1) Codebase (one repo per app), (2) Dependencies (explicitly declare), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless, ephemeral). They matter because they ensure portability, secure config management, horizontal scalability, and maintainable CI/CD pipelines in cloud environments.

AA12 — Coupling: Event-driven = loose; Request-driven = tight. Scalability: Event-driven = highly scalable async; Request-driven = sync limits, needs LB. Debugging: Event-driven = harder (traces, replay); Request-driven = easier (direct call chains). Ordering: Event-driven = guaranteed per partition/key; Request-driven = no inherent ordering, can use sequence headers but not guaranteed. Failure: Event-driven = DLQs, idempotency, retries; Request-driven = timeouts, circuit breakers, retries. Choose event-driven for async workflows, high throughput, decoupled systems. Choose request-driven for real-time, simple CRUD, synchronous workflows.

AA13 — A load balancer distributes traffic across multiple backend servers. Layer 4 balances by IP/port (fast, no content inspection). Layer 7 balances by content (URL, headers, cookies, SSL). Layer 7 is required for content-based routing (e.g., `/api/v1` → service A, `/static` → CDN), SSL termination with SNI, or header-based routing.

AA14 — Message queue (RabbitMQ): point-to-point/pub-sub, messages consumed and deleted, supports complex routing. Log-based broker (Kafka): append-only log, messages retained, multiple consumers read at own pace, high throughput. Pick RabbitMQ for task queues, complex routing, low latency. Pick Kafka for event streaming, replayability, audit trails, high throughput.

AA15 — A container shares the host OS kernel, isolates processes/filesystem, and is lightweight/fast. A VM runs a full guest OS with hardware virtualization, heavier/slower. Containers are popular for microservices due to fast startup, consistent environments, efficient resource usage, and native orchestration support (K8s).

AA16 — Stateless services hold no local session data; any instance can handle any request. Stateful services maintain local state/session, requiring affinity/pinning. Stateless services scale horizontally easily because adding/removing instances doesn't require data migration or session loss. Examples: Stateless = web API, Redis; Stateful = PostgreSQL, Kafka.

AA17 — An ORM maps objects to DB tables, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), Prisma (Node). Trade-offs: ORM = faster dev, portability, safety, but can generate inefficient queries, harder to optimize, abstraction leaks. Raw SQL = full control, performance tuning, complex queries, but more code, DB-specific, slower dev.

AA18 — The Bulkhead pattern isolates resources so one failure doesn't exhaust shared resources. In microservices, it prevents cascading failures by partitioning thread pools, connections, or deployments. Implementation: separate thread pools per downstream service, or deploy critical vs non-critical services on different node pools/K8s namespaces with resource quotas. Use connection pool limits per tenant/service to isolate noisy neighbors.

AA19 — OT: central server transforms operations to resolve conflicts. Strong consistency, low online latency, high server complexity, poor offline support. CRDTs: data structures with mathematical convergence guarantees without coordination. Eventual consistency, higher latency/size, lower complexity (client-side), excellent offline support. Choose CRDTs for offline editing: they allow concurrent local edits, merge automatically when online, require no central coordination, and guarantee convergence.

AA20 — Challenges: polyglot stacks, network hops, async boundaries, overhead. Context propagation: W3C Trace Context (standard) or B3; inject/extract trace IDs across HTTP/gRPC. Sampling: head-based (random, cheap, loses rare traces); tail-based (collects all, samples after, accurate but high overhead). Storage/querying: Jaeger (OTel native, rich UI), Tempo (Loki-style, cost-effective, metadata-only indexing). Async/Kafka: trace context must be serialized into message headers. Continuity ensured by propagating `traceparent`/`tracestate` or B3 headers through Kafka producers/consumers using OpenTelemetry SDKs.

OP1 — Type 1 (bare-metal): runs directly on hardware, high performance, low overhead. Examples: VMware ESXi, Proxmox VE, KVM, Hyper-V. Type 2 (hosted): runs as an app on a host OS, lower performance, easier setup. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN: block storage, presented as local disk, high performance/low latency. Protocols: Fibre Channel, iSCSI. Use for databases, VMs. NAS: file storage, shared over network, easier management. Protocols: NFS, SMB/CIFS. Use for file shares, backups, home directories.

OP3 — 3-tier: Access (edge) → Distribution (policy/aggregation) → Core (backbone). Hierarchical, potential bottlenecks, asymmetric routing. Leaf-spine: all-to-all mesh, equal-cost multipath, low latency, predictable bandwidth. Preferred because it eliminates distribution/core bottlenecks, supports east-west traffic, and scales horizontally without redesign.

OP4 — Proxmox HA cluster: 3+ nodes for quorum. Quorum: majority votes prevent split-brain. Fencing: STONITH (IPMI/iDRAC) powers off failed nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. Node failure: HA manager detects failure, fences node, restarts VMs on healthy nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, repeat for VLANs 20/30, assign IPs, enable `net.ipv4.ip_forward=1` if routing. Alternatively, use `systemd-networkd` or `netplan` with VLAN interfaces.

OP6 — RAID 1: mirror, 50% capacity, 1 drive fault. RAID 5: stripe+parity, N-1 capacity, 1 fault, write penalty. RAID 6: double parity, N-2 capacity, 2 faults, higher write penalty. RAID 10: mirror+stripe, 50% capacity, survives multiple faults (not same pair), excellent perf. RAID Z2 (ZFS): double parity, N-2 capacity, self-healing, excellent for large drives. For 6 drives + DB: RAID 10 for max write IOPS/low latency, or Z2 if capacity/fault tolerance outweighs raw write perf.

OP7 — Recursive resolvers: internal DNS (Windows DNS/BIND) for clients. Authoritative: internal zone for AD (dynamic updates), external zone for public services. Forwarders: point to ISP/cloud DNS for external queries. Conditional forwarding: routes internal AD domains to internal DNS, external to forwarders. Split-horizon: internal DNS returns private IPs, external returns public IPs for same FQDN. DNSSEC: signs external zone, DS record at registrar, validates on recursive resolvers. Laptop mobility: DHCP provides internal DNS; VPN clients use split/full-tunnel DNS. Conditional forwarding ensures internal names resolve correctly regardless of location.

OP8 — PKI chain: Root CA → Subordinate CA → End-entity cert. Root CA: offline, self-signed, long-lived. Subordinate: online, issues certs, shorter lifetime. CRL vs OCSP: CRL = periodic download of revoked list; OCSP = real-time status check (lower latency, privacy trade-offs). Templates: define key usage, validity, enrollment permissions. Auto-enrollment: SCEP/EST or AD CS auto-enrolls devices/users. Compromise: Subordinate = issue fake certs, but root can revoke/rotate sub. Root = catastrophic, requires rebuilding entire PKI and updating all trust stores.

OP9 — MPLS: high reliability, low latency, expensive, managed, secure. IPsec VPN: cheap, internet-based, variable latency, manual management. SD-WAN: orchestrates multiple links, dynamic path selection, centralized management, moderate cost. WireGuard mesh: modern crypto, fast, simple config, lacks orchestration/telemetry. Recommendation: SD-WAN. Handles latency-sensitive VoIP via QoS/policy routing, combines cost-effective broadband with reliability, centralized management, and dynamic failover.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: out-of-band management interfaces for remote power, console, hardware monitoring. Critical for recovery when OS/network is down, automated provisioning, and diagnostics. Internet exposure: high risk of credential stuffing, firmware exploits, unauthorized remote power cycling/console access. Should be on isolated management network.

OP11 — LVM: traditional, fixed-size volumes, COW snapshots (can fill up). LVM-Thin: overprovisions storage, instant/space-efficient snapshots, performance degrades if pool fills. ZFS: filesystem+volume manager, COW, instant/read-only snapshots, space-efficient, self-healing, clones. Use LVM for simple/legacy needs, LVM-Thin for VMs needing many snapshots, ZFS for data integrity, advanced snapshots, compression, modern storage.

OP12 — Stretch cluster: 2 sites with 2 nodes each + 1 tiebreaker (quorum disk/VM) in 3rd site. CRUSH rules: distribute OSDs across sites, ensure replicas span sites. Monitors: 3 monitors (1 per site + tiebreaker) for quorum. Latency: <5ms ideal, <10ms acceptable; higher degrades performance. Split-brain: both sites think primary → data corruption. Tiebreaker breaks deadlock. 2-site Ceph without tiebreaker is bad because 2 sites split votes 1-1, no quorum, both stop or both write → corruption. Ceph requires odd monitor/OSD counts for quorum.

OP13 — DHCP assigns IP/config dynamically. DORA: Discover, Offer, Request, Acknowledge. Unavailable server: client retries, may use APIPA (169.254.x.x) or fail. Expired lease: client sends DHCPREQUEST to renew. If unavailable, retries until lease expires, releases IP, may get APIPA or lose connectivity.

OP14 — Unmanaged: plug-and-play, no config, basic switching. Managed: configurable, supports VLANs, QoS, STP, port security, monitoring, ACLs, link aggregation. Critical for segmentation, traffic prioritization, security, and troubleshooting in enterprise environments.

OP15 — NTP synchronizes clocks over network. Critical for authentication, logging, clustering, distributed transactions, certificate validation, audit compliance. Clock drift: cluster split-brain, Kerberos auth failures, log correlation issues, DB replication lag, certificate errors.

OP16 — Physical: bare hardware, full control, highest perf. VM: OS virtualization, isolation, overhead. Container: process isolation, shares kernel, lightweight. Bare metal use cases: high-performance computing, low-latency trading, GPU-intensive workloads, compliance requirements, database cores needing direct hardware access.

OP17 — UPS: battery backup, instant power, short duration (minutes). Generator: fuel-powered, long duration, startup delay. Both needed: UPS bridges gap until generator starts, prevents data loss/crashes. ATS: automatically transfers load from utility to UPS/generator on failure, switches back when utility restores.

OP18 — Active-passive: one handles traffic, standby takes over on failure. Active-active: both handle traffic, sync data, failover requires split-brain prevention. PostgreSQL HA: Pacemaker/Corosync cluster, 2 nodes. STONITH fencing (IPMI) prevents split-brain. Virtual IP (Pacemaker resource) floats to active node. Patroni/repmgr handles DB replication. On failure, Pacemaker fences failed node, promotes standby, moves VIP.

OP19 — 3-2-1: 3 copies, 2 media types, 1 offsite. RPO/RTO: define acceptable data loss/downtime. Types: Full (baseline), Incremental (changes since last), Differential (changes since last full). Deduplication: reduces storage, improves backup window. Media: disk (fast restore), tape (cheap long-term), cloud (offsite/scalable). Immutable: WORM storage, ransomware protection. Testing: regular restore drills, verify integrity, measure RTO/RPO. Backup vs DR: backup = data protection/restoration; DR = comprehensive strategy (processes, infrastructure, failover) to resume operations after disaster.

OP20 — 802.1X: port-based NAC. Roles: Supplicant (client), Authenticator (switch/AP), Auth Server (RADIUS). EAP-TLS: mutual cert auth, most secure, requires PKI. PEAP: tunnel, server cert + inner auth (password/MS-CHAPv2), easier deployment. RADIUS: auth, authorization, accounting. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: port stays unauthorized, no traffic. MAB: switch sends MAC to RADIUS, RADIUS matches MAC to policy, grants access. Used for printers/IoT without 802.1X supplicant.
