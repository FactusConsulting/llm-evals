SC1-A
The pods fail because Kubernetes Pod Security Standards (PSS) `Restricted` explicitly requires `runAsNonRoot: true` AND an explicit `runAsUser` set to a non-zero UID. The `Baseline` profile only checks for dangerous capabilities and privileged containers, allowing root by default. When enforcement switched to `Restricted`, the admission controller validates that containers cannot run as root. Since the new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root` and the manifests lack `runAsUser`, the kubelet attempts to start the container as root, which the `Restricted` policy rejects. The pod enters `CrashLoopBackOff` as the container repeatedly fails to start due to the security policy violation.

SC1-B
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

SC1-C
**Immediate Fix:** Add `runAsUser: 1000` (or the UID of the non-root user in the base image) to each pod/deployment's `securityContext`. This satisfies `Restricted` PSS.
**Image Fix:** Rebuild images with a non-root user explicitly defined in the Dockerfile (`RUN adduser -D appuser` + `USER appuser`) and pin the base image digest.
**CI Gate:** Deploy a Kyverno/OPA policy that rejects deployments lacking `securityContext.runAsUser` and `securityContext.runAsNonRoot: true`. Add a Trivy/Syft scan that fails if the base image defaults to root.
**Rollout:** Use `kubectl rollout restart` with `maxSurge=25%` and `maxUnavailable=0` to perform a rolling update. Monitor `kubectl rollout status` and verify `CrashLoopBackOff` clears before proceeding.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped from the primary to the replica over the network. When the primary fails, the replica is promoted, but any transactions committed in the primary after the last successfully shipped/replayed WAL are permanently lost. The data loss window equals the replication lag at failover time. To quantify: query `pg_stat_replication` for `write_lag`, `flush_lag`, and `replay_lag` before/during failover. Check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica. Asynchronous replication inherently risks data loss proportional to network latency and primary write throughput.

SC2-B
1. Import the promoted replica into Terraform state:
   `terraform import aws_db_instance.promoted_replica <arn-of-eu-west-1-instance>`
2. Update the Terraform config to rename/reference the new instance and update dependent resources (security groups, Route53, parameter groups).
3. Use the `moved` block to shift state references without destroying:
   ```hcl
   moved {
     from = aws_db_instance.old_primary
     to   = aws_db_instance.promoted_replica
   }
   ```
4. Run `terraform state rm aws_db_instance.old_primary` to detach the decommissioned instance.
5. `terraform plan` to verify no `destroy`/`create` actions, then `terraform apply`.

SC2-C
**Connection Management:** Use RDS Proxy instead of PgBouncer. RDS Proxy handles failover DNS resolution automatically, maintains persistent backend connections, and reduces connection pool thrashing during promotions.
**DNS Failover:** Route53 failover routing policy with health checks on the RDS endpoint. Applications use a single CNAME.
**Retry Logic:** Implement exponential backoff with jitter in the application driver.
**RPO < 1s:** Standard RDS cross-region async replication cannot guarantee RPO < 1s. Recommend **Aurora Global Database**. It uses a dedicated global log writer, replicates data at the storage layer with <1s lag, and provides automatic failover with minimal data loss. It also simplifies cross-region read/write routing and reduces operational overhead compared to manual Patroni/PgBouncer setups.

SC4-A
1. **Sticky Sessions (F5):** K8s is stateless by design. *Fix:* Externalize sessions to Redis/ElastiCache or use `service.spec.sessionAffinity: ClientIP` with short TTLs.
2. **Local NFS Mount:** K8s pods are ephemeral; local mounts break on rescheduling. *Fix:* Use a CSI NFS driver with `ReadWriteMany` or migrate uploads to S3/MinIO.
3. **On-Prem Oracle 19c:** Network latency and firewall rules may break DB connections. *Fix:* Maintain on-prem DB but use dedicated VPC peering/ExpressRoute, optimize JDBC pool settings, and consider eventual migration to cloud-native DB.
4. **IBM MQ Integration:** MQ clients require stable network and specific TLS/cert configs. *Fix:* Deploy MQ client libraries in containers, ensure network connectivity, and consider migrating to cloud-managed MQ or using MQ bridge patterns.
5. **Bare-Metal Performance:** K8s overhead + JVM tuning may increase p99 latency. *Fix:* Use dedicated node pools, set CPU/memory requests/limits, enable JVM tiered compilation, and implement horizontal pod autoscaling.

```sql
SELECT blocked_locks.pid AS blocked_pid, blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid, blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement, blocking_activity.query AS blocking_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC5-C
**Architectural Solution:**
- **CQRS:** Separate read/write paths. Checkout reads from a read replica or materialized view; reconciliation writes to primary.
- **Read Replica:** Run the reconciliation CronJob against a read replica to avoid locking production tables.
- **Bulkhead Isolation:** Configure separate connection pools per service (e.g., HikariCP with `maximumPoolSize` tuned per tenant).
- **CronJob Scheduling:** Run during off-peak, set `concurrencyPolicy: Forbid`, and use `schedule: "30 2 * * *"`.
- **PDBs & Quotas:** Set `minAvailable: 2` for serving pods. Use `LimitRange` and `ResourceQuota` in the CronJob's namespace to cap CPU/memory, preventing resource starvation.

SC6-A

SC7-A
1. **Manual `tofu apply`:** Bypasses CI peer review and state locking. Two concurrent applies cause race conditions: last-write-wins corrupts state, partial applies leave resources in inconsistent states, and drift goes undetected.
2. **Diverged Helm values:** Untracked changes break reproducibility. Deployments become environment-specific, causing "works on my machine" issues and making rollbacks impossible.
3. **`kubectl edit` ConfigMaps:** Creates config drift outside GitOps. Changes are ephemeral (lost on pod restart) or inconsistent across replicas, leading to unpredictable behavior.
**State Locking Risk:** Without DynamoDB/S3 locking, concurrent `tofu apply` commands read the same state, compute overlapping plans, and overwrite each other, potentially destroying resources or leaving orphaned infrastructure.

SC10-A
**Active-Passive (Velero):** RPO depends on backup frequency (min 15m). RTO depends on restore time. With 200TB MinIO, Velero restore will exceed 1hr RTO. Not viable for data plane.
**Active-Active (Istio/Cilium):** Lower RPO/RTO. Requires stateless workloads or async-replicated state. Given 12ms latency, active-active is feasible for compute, but stateful components need careful replication.
**Replication Strategy:**
- **PostgreSQL:** Patroni async replication with `synchronous_commit = on` for critical transactions. RPO ~0-1s.
- **Redis:** Sentinel with async replication. RPO ~1-5s.
- **RabbitMQ:** Federation/shovel or mirrored queues. RPO ~0-2s.
- **MinIO:** Site replication (async, near-zero RPO). Handles 200TB efficiently.
**Recommendation:** Active-active for stateless services, active-passive with pre-warmed DR for stateful. Use MinIO site replication + Patroni async for data. Istio multi-cluster for traffic steering.

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks (TCP/HTTP) + heartbeat to etcd. "Site down" = 3 consecutive failures + quorum loss.
2. **Validation:** Cross-check with external monitor to avoid false positives.
3. **DNS Failover:** GSLB (Route53/Azure Traffic Manager) switches VIP to Dallas.
4. **Patroni Promotion:** etcd triggers standby promotion. `synchronous_standby_names` ensures zero data loss for committed txns.
5. **Redis Sentinel:** Automatic master election.
6. **RabbitMQ:** Federation catches up missed messages.
7. **MinIO:** Site replication syncs delta.
8. **State Update:** GitOps operator updates OpenTofu state/config to reflect new primary.
**Split-Brain Prevention:** etcd quorum-based DCS, fencing scripts, manual override required if split-brain detected.
**Failback:** Reverse replication (Dallas → Chicago), sync data, verify integrity, switch DNS back, decommission Dallas primary. Test quarterly with chaos engineering.
