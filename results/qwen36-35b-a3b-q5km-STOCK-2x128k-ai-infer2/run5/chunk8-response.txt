CL1 — IaaS provides virtualized compute, network, and storage where you manage the OS and above (e.g., AWS EC2). PaaS provides a managed runtime and platform services for application development (e.g., AWS Elastic Beanstalk). SaaS delivers fully managed applications over the internet (e.g., AWS WorkDocs). Abstraction increases from IaaS to SaaS, reducing operational overhead but decreasing infrastructure control.

CL2 — The Shared Responsibility Model divides security duties: the provider secures the cloud infrastructure, the customer secures what they put in it. IaaS VM: Provider secures hypervisor/physical host; customer secures OS, apps, data, and network config. Managed Kubernetes: Provider secures control plane, etcd, and node OS; customer secures workloads, network policies, RBAC, and secrets. SaaS (M365): Provider secures application code, data storage, and physical infrastructure; customer manages identity, access, data classification, and endpoint security.

CL3 — A VPC is an isolated virtual network. Subnets partition VPCs into CIDR blocks across AZs. Security Groups (SGs) are stateful, instance-level firewalls allowing outbound by default. Network ACLs (NACLs) are stateless, subnet-level firewalls denying outbound by default. They layer as: VPC → Subnet → NACL (subnet boundary) → Instance → SG (instance boundary). Stateful filters track connection state and automatically allow return traffic; stateless filters evaluate each packet independently, requiring explicit allow rules for both directions.

CL4 — A landing zone is a pre-configured, secure multi-account baseline. OUs group accounts by environment/function. Guardrails enforce compliance via SCPs/policies. Shared networking uses Transit Gateway/Azure Hub-and-Spoke for centralized inter-VPC/VNet routing. Centralized logging aggregates logs to a dedicated security account. Single-account approaches lack isolation, cause massive blast radiuses, complicate billing/cost allocation, and make compliance auditing nearly impossible.

CL5 — IaC manages infrastructure via machine-readable definition files. Terraform/OpenTofu: Provider-agnostic, state-driven, best for multi-cloud/general purpose. Pulumi: General-purpose languages (TS/Python/Go), imperative, ideal for complex logic/CI integration. CloudFormation/Bicep: AWS-native, declarative, best for AWS-only shops. Crossplane: Kubernetes-native, manages cloud resources via CRDs, ideal for GitOps/K8s-centric teams wanting a unified control plane.

CL6 — HPA scales pods based on CPU/memory/custom metrics. VPA adjusts pod resource requests/limits automatically. Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales workloads based on external event sources (queues, streams, HTTP). Use KEDA over HPA when scaling is driven by event-driven triggers (e.g., Kafka lag, RabbitMQ queue depth) rather than standard resource utilization.

CL7 — Define RPO/RTO first. Active-active distributes traffic across regions with low latency; active-passive routes to a standby region. DB replication: sync (zero RPO, higher latency) vs async (near-zero RPO, lower latency). DNS failover uses health checks to route traffic. State management requires distributed caches or region-local storage with cross-region replication. Pilot light: minimal core services running. Warm standby: scaled-down but ready. Multi-site active-active: full capacity in both regions. Cost: Active-active doubles baseline; pilot light is cheapest but highest RTO.

CL8 — GitOps uses Git as the single source of truth, with controllers reconciling cluster state to declared manifests. ArgoCD is UI-focused, push/pull, app-of-apps; FluxCD is Git-native, pull-only, tightly integrated with Git providers. Secrets: Sealed Secrets encrypts in Git; External Secrets Operator syncs from Vault/AWS SM; SOPS encrypts files. Drift: Controllers detect manual changes and automatically revert them to match Git state, or flag them for review depending on configuration.

CL9 — Use a StatefulSet for stable network IDs and ordered deployment. PV/PVC with `local` storage class binds to node-specific disks for low latency. Headless service provides stable DNS for pod discovery. Init containers handle filesystem prep/config injection. ConfigMaps/Secrets mount as volumes at required paths. Pod Disruption Budgets (PDB) ensure minimum available pods during voluntary disruptions. Add anti-affinity rules to spread replicas across nodes.

CL10 — Service accounts are K8s-native identities for pods. Workload Identity (GCP) and IRSA (AWS) map K8s service accounts to cloud IAM roles without long-lived credentials. Mounting cloud credentials in pods exposes them to container escapes, logs, and backups, violating least privilege. Workload identity federation uses short-lived, auditable tokens exchanged via OIDC, eliminating static keys and enabling fine-grained, time-bound access.

CL11 — Object storage (S3/Blob) stores unstructured data via APIs, highly durable (99.999999999%), available but not low-latency. Block storage (EBS/Managed Disk) provides raw, mountable volumes for OS/DBs, low latency, high IOPS, durable within AZ. File storage (EFS/Azure Files) offers NFS/SMB shared filesystems, scalable, moderate latency. Use object for backups/media, block for databases/VMs, file for shared app configs or legacy file shares.

CL12 — Zero-trust K8s assumes no implicit trust. Network policies restrict pod-to-pod traffic. Service mesh (Istio/Linkerd) enforces mTLS for service-to-service auth. Pod identity binds workloads to cloud IAM. Admission controllers (OPA/Kyverno) enforce policies at deploy time. Image signing (Cosign) verifies artifacts. Runtime security (Falco) detects anomalous behavior. Unlike perimeter models, zero-trust verifies every request, micro-segments traffic, and eliminates lateral movement, even if the network is breached.

CL13 — A CDN caches content at edge locations globally to reduce latency and origin load. It works by routing user requests to the nearest PoP, serving cached assets, and refreshing from origin on cache miss. Cloud-native examples: CloudFront (AWS), Azure Front Door/CDN (Azure). Use CDN for static assets, media, and public APIs to offload origin, improve performance, and mitigate DDoS. Avoid for highly dynamic, personalized, or low-latency internal traffic.

CL14 — Regions are geographic areas with multiple AZs. AZs are isolated data centers within a region with independent power/network. Deploy across multiple AZs to survive data center failures and meet high availability SLAs. Zonal resources (e.g., EBS, EC2 instances) are tied to a specific AZ. Regional resources (e.g., S3, Route53, IAM) span all AZs/regions automatically.

CL15 — Managed DB services (RDS, Cloud SQL, Azure SQL) abstract database administration. The provider handles provisioning, patching, backups, replication, failover, and monitoring. Customers manage schema, queries, access, and data. This reduces operational overhead, improves availability, and accelerates deployment compared to self-managed VM databases.

CL16 — IAM users are individuals/services, groups bundle permissions, roles are assumable identities for cross-account/service access, policies define permissions (JSON). Least privilege grants only necessary permissions for a specific task. Apply it by using granular policies, avoiding `*` actions/resources, leveraging roles over long-lived keys, and regularly auditing access via IAM Access Analyzer.

CL17 — Serverless runs code without managing servers, scaling automatically per request. Lambda (AWS), Azure Functions, GCP Cloud Functions are function-as-a-service platforms. Cold starts occur when the runtime initializes a new container, causing latency spikes. They matter for latency-sensitive apps. Serverless is a poor fit for long-running processes, stateful workloads, predictable high-throughput workloads (reserved capacity is cheaper), or environments with strict egress/network constraints.

CL18 — Ingress resource routes external HTTP/HTTPS to services using a controller. Gateway API is the modern, extensible replacement with better RBAC and multi-tenant support. Cloud LB annotations provision cloud load balancers directly. Service mesh ingress gateways handle traffic at the mesh edge. TLS termination: Ingress/LB terminate at the controller/LB; Gateway API terminates at the gateway; mesh ingress terminates at the sidecar/gateway. Use Gateway API for complex routing, fine-grained access control, and multi-team environments.

CL19 — RI/SP commit to usage for 1-3 years for 30-70% discount; Spot/Preemptible offers 60-90% discount but can be reclaimed. Right-size via monitoring and auto-scaling. Storage tiering moves cold data to cheaper classes. Idle detection finds unattached volumes, unused IPs, zombie instances. FinOps establishes cross-functional cost ownership, budgeting, and forecasting. Showback/chargeback allocates costs by team/project. Tools: AWS Cost Explorer, Azure Cost Management, Kubecost, CloudHealth. Processes: monthly reviews, tagging policies, automated alerts, and optimization backlogs.

CL20 — Multi-cloud avoids lock-in by abstracting infrastructure. Use Kubernetes as a common runtime, Terraform for portable IaC, and cloud-agnostic networking (Terraform Cloud, WireGuard, or cloud interconnects). Identity federation via SAML/OIDC across providers. Trade-offs: increased complexity, higher networking costs, fragmented tooling, and operational overhead. Justified when regulatory requirements mandate it, or when leveraging best-of-breed services outweighs complexity. Unnecessary when a single cloud meets all needs, as multi-cloud rarely delivers promised cost savings and often increases risk.

OT1 — The Purdue Model (ISA-95) structures industrial automation hierarchically. Level 0: Physical process/sensors/actuators. Level 1: Field devices (PLCs, RTUs, sensors). Level 2: Control systems (SCADA, HMIs, historians). Level 3: Site operations (MES, plant management). Level 4: Enterprise (ERP, business planning). Level 5: Supply chain/network. It enforces logical separation between operational and business functions.

OT2 — IT networks prioritize confidentiality and integrity, use frequent patching, and tolerate downtime. OT networks prioritize availability and safety, run legacy/unsupported OS, and cannot tolerate unplanned downtime or reboot cycles. IT patching can break proprietary protocols, cause system reboots, or introduce instability, directly risking production safety and continuity.

OT3 — An Industrial DMZ (IDMZ) sits between IT (L4) and OT (L0-L2) networks, acting as a controlled buffer. Only specific, unidirectional or tightly controlled bidirectional traffic crosses (e.g., OPC UA data pulls, batch uploads). Direct L4-to-L1 connectivity bypasses segmentation, allowing IT malware or misconfigurations to directly impact physical processes, causing safety hazards or production halts.

OT4 — 1. Modbus TCP: Simple request/response, L1-L2 (PLC/RTU). 2. OPC UA: Secure, platform-independent, L2-L3 (SCADA/Historian). 3. EtherNet/IP (CIP): Industrial Ethernet, L1-L2 (PLC/IO). 4. PROFINET: Real-time industrial Ethernet, L1-L2 (PLC/Drives). 5. MQTT: Lightweight publish/subscribe, L2-L4 (Edge/Cloud ingestion).

OT5 — A firewall inspects and filters bidirectional traffic based on rules. A data diode is a hardware-enforced unidirectional link allowing only outbound data flow. Use a data diode when absolute one-way data transfer is required (e.g., secure telemetry to cloud, or air-gapped safety systems). Limitation: It cannot allow any return traffic, commands, or acknowledgments, making it unsuitable for interactive control or bidirectional protocols.

OT6 — Data flow: PLCs/RTUs → OPC UA Server (L2) → Historian (L2) → Edge Gateway (L2/L3 boundary) → MQTT Broker (DMZ) → Cloud Ingestion (IoT Core/Event Hubs). Security boundaries: Firewall between L2 and DMZ, data diode or strict firewall rules for DMZ-to-Cloud, TLS/mTLS for MQTT, network segmentation isolating the historian. The edge gateway handles protocol translation, buffering, and initial filtering.

OT7 — IEC 62443 defines security zones (groups of assets with similar security requirements) and conduits (communication paths between zones). Zone: e.g., "Production Control Zone" (PLCs, HMIs, SCADA). Conduit: Secured link between zones. Design: Corporate (L4) ↔ IDMZ ↔ SCADA/Historian (L3) ↔ Firewall/DMZ ↔ PLCs/HMIs (L2) ↔ SIS (L1, isolated). SIS gets its own zone with strict conduits, no direct IT/SCADA links, and hardware data diodes or one-way gateways for non-critical data.

OT8 — Segment flat L2 into VLANs per production line, utility, and management. Place industrial firewalls between VLANs and at the L2/L3 boundary. Use managed switches with port security and STP. Vendor access via jump hosts in a dedicated VLAN with MFA, session recording, and time-limited credentials. Transition: Phase migration during planned shutdowns, use temporary parallel networks, validate traffic flow, and implement monitoring before decommissioning the flat network.

OT9 — BPCS handles routine process control; SIS handles emergency shutdowns to prevent hazardous conditions. IEC 61511 mandates safety lifecycle and SIL ratings for SIS. SIS must be air-gapped/isolated to prevent IT/OT cyber threats from compromising safety functions. If ransomware reaches SIS, it could disable emergency shutdowns, leading to catastrophic physical damage, environmental release, or loss of life.

OT10 — PLC: Rugged controller for discrete/sequential control at L1. DCS: Integrated system for continuous/process control across multiple PLCs/loops at L1-L2. SCADA: Supervisory system for monitoring/control and data logging at L2. Use PLCs for machine-level control, DCS for large continuous plants, SCADA for wide-area monitoring. They coexist seamlessly; SCADA aggregates PLC/DCS data.

OT11 — Remote access uses jump hosts in a DMZ, MFA, session recording, vendor-specific accounts, and time-limited access. Direct RDP to HMIs from corporate networks bypasses segmentation, exposes legacy RDP vulnerabilities, and allows lateral movement into control networks. Jump hosts enforce authentication, logging, and network isolation, ensuring only authorized, monitored sessions reach OT assets.

OT12 — Detection: Deploy passive IDS (e.g., Nozomi, Claroty) for anomaly detection, maintain real-time asset inventory, monitor L3 for lateral movement. IR steps: Isolate compromised vendor VPN, preserve logs, assess impact, engage OT engineers. Coordination: Notify control room, shift to manual/local control if needed, ensure safe plant state. Operator role: Monitor physical parameters, execute manual overrides, verify safety systems, communicate status. False positives minimized by baseline profiling and OT-specific tuning.

OT13 — An HMI is an operator interface displaying process data and allowing manual control inputs. It bridges human operators and automated systems. Differs from an engineering workstation, which is used for programming, configuration, and diagnostics of PLCs/SCADA, not for routine operational monitoring or control.

OT14 — A historian is a time-series database optimized for storing and retrieving process data (temperatures, pressures, flows). It’s critical for trend analysis, compliance, and optimization. Plant historian (L3) stores real-time operational data for shift/production analysis. Enterprise historian (L4) aggregates plant data for business intelligence, ERP integration, and long-term corporate reporting.

OT15 — Ladder logic is a graphical programming language mimicking relay circuits, executed by PLCs. It remains dominant because it’s intuitive for electricians/technicians, highly reliable, standardized (IEC 61131-3), and deeply integrated into decades of industrial automation ecosystems.

OT16 — An RTU is a ruggedized controller designed for remote, harsh environments (pipelines, utilities) with long-distance communication (cellular, satellite, radio). Unlike PLCs optimized for factory floors, RTUs prioritize low power, wide I/O ranges, and robust telemetry. Deploy RTUs in geographically dispersed, unattended locations.

OT17 — Analog signals use continuous voltage/current (4-20mA, 0-10V); digital signals use discrete on/off states. 4-20mA is preferred over 0-20mA because a 4mA "live zero" distinguishes between a valid zero reading and a broken wire/fault (0mA), enabling immediate fault detection.

OT18 — OT asset inventory catalogs all hardware, firmware, and network connections, forming the security baseline for risk assessment and patching. Tools: Passive monitoring (packet sniffing, protocol analysis) safely discovers assets. Active scanning (port scans, ping sweeps) is dangerous because it can crash legacy controllers, trigger false alarms, or disrupt real-time processes.

OT19 — MITRE ATT&CK for ICS maps adversary tactics to industrial environments. Tactics: Reconnaissance (e.g., Gather Victim Network Security Configurations), Resource Development, Initial Access (e.g., Supply Chain Compromise), Execution (e.g., Command and Scripting Interpreter), Defense Evasion (e.g., Indicator Removal). Differs from enterprise ATT&CK by focusing on physical process impact, legacy protocols, and safety constraints. Use it to map current defenses, identify gaps in detection/response for ICS-specific techniques, and prioritize controls.

OT20 — Log collection: Passive network taps, OPC UA audit logs, syslog forwarding (non-intrusive). SIEM: Centralize logs, tag OT assets, use OT-specific correlation rules. Triage: Separate IT/OT alerts, involve OT engineers for process impact assessment. Staffing: IT analysts handle IT alerts; OT engineers handle process/safety alerts. False positives: Baseline normal OT traffic, use allowlists, tune rules to avoid nuisance alerts. Unauthorized firmware change: Immediately isolate affected PLC, verify safety state, revert to known-good firmware from secure vault, audit change management logs, and report to safety committee.
