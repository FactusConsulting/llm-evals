# JavaScript / TypeScript

**JS1** — `var` is function-scoped, hoisted and initialized to `undefined`. `let`/`const` are block-scoped and hoisted into the Temporal Dead Zone (referencing before the declaration line throws a `ReferenceError`). `const` must be initialized at declaration and the *binding* is immutable (object contents can still mutate). **Hoisting** = the creation phase moves declarations to the top of their scope: `var` gets `undefined`, function declarations are fully hoisted (callable before the line), `let`/`const` are hoisted but uninitialized (TDZ).

**JS2** — The event loop takes callbacks off queues when the **call stack** empties. Order: run all synchronous code → drain the **entire microtask queue** (promise callbacks, `queueMicrotask`, `MutationObserver`; in Node, `process.nextTick` runs before promise microtasks) → execute **one macrotask** (timers, I/O callbacks, UI events, `setImmediate`) → drain microtasks again → render (browser). A recursive `Promise.resolve().then()` can starve macrotasks forever.

**JS3** — A closure is a function plus its retained lexical scope; it can read/write variables of the defining function after it returns. Practical: private counters, memoization, event callbacks. The classic bug:

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // logs 3,3,3
```

`var` is one function-scoped binding; by the time the callbacks run, the loop finished and `i` is 3. Fix: use `let` (a fresh binding per iteration), an IIFE `((j) => ...)(i)`, or `.bind(null, i)`.

**JS4** — A `Promise` is a placeholder for a future result with states pending → fulfilled/rejected (settled, one-time). `async/await` is syntax over promises: an `async` function always returns a promise; `await` pauses that function (not the thread) and unwraps the promise. Errors: `try/catch` around `await` catches rejections and thrown errors; in promise chains use `.catch()`; unhandled rejections fire `unhandledrejection`. **`Promise.all`** rejects fast with the first rejection (other results discarded); **`Promise.allSettled`** never rejects — it waits for all and returns `[{status:'fulfilled', value} | {status:'rejected', reason}]`, ideal for batch work where partial results are acceptable.

**JS5** — `interface` describes object shapes, can `extends`, supports declaration merging (re-opening the same name), and is preferred for public APIs/classes. `type` can alias anything: primitives, unions, intersections, mapped/conditional/utility types. Rule of thumb: `interface` for extendable object contracts, `type` for unions and type algebra. **Discriminated union**: a union whose members share a literal "tag" property (`kind`/`type`); narrowing on the tag gives correct types per branch, and a `default`/`never` case gives exhaustiveness checking:

```ts
type Shape = { kind:'circle'; r:number } | { kind:'square'; side:number };
```

**JS6** — Every object has an internal `[[Prototype]]` link; property lookup walks that chain until found or `null`. `Object.create(proto)` builds an object whose prototype is `proto` (optionally with property descriptors); `Object.create(null)` makes a dict with no prototype. ES6 `class` is syntactic sugar over this: methods live on `Class.prototype`, `new` sets `[[Prototype]]` to `Class.prototype`, `super` delegates to the parent prototype, `instanceof` walks the chain. Differences from plain functions: classes are strict-mode, must be called with `new` (else `TypeError`), and aren't hoisted like `var`.

**JS7** — `this` binding rules in priority order: **1) `new` binding** (fresh object), **2) explicit binding** (`call`/`apply`/`bind`), **3) implicit binding** (`obj.fn()` → `this = obj`), **4) default binding** (`undefined` in strict mode, global otherwise). Arrow functions ignore all of these — `this` is lexical from the enclosing scope. `bind()` returns a new **bound function** with permanently fixed `this` (and optional prepended args); later `call`/`apply` on it are ignored — it cannot be re-bound. Exception: `new` on a bound function overrides the bound `this` with the newly constructed object.

**JS8** — `WeakRef` holds a weak reference that doesn't keep its target alive; `deref()` returns the target or `undefined` once collected. `FinalizationRegistry` registers a callback to run after an object is garbage-collected (cleanup of external/native resources). Both are nondeterministic (GC timing is unspecified) — use for caches/diagnostics, never for correctness. `WeakMap` keys must be objects because the key is held *weakly*: the GC must be able to trace and observe the key's liveness, which requires identity — primitives are copied by value and can't be "weakly observed." When the key object becomes unreachable, the entry is pruned automatically. (ES2023 added non-registered symbols as an exception.)

**JS9** — V8 pipeline: parse → AST → Ignition (bytecode interpreter) → TurboFan (optimizing compiler). **Hidden classes (Maps)**: each object shape gets a hidden class; adding properties causes a transition, so objects created with the same properties in the same order share classes → fast, fixed-offset property access. **Inline caching**: load/call sites cache (hidden class → offset) pairs; monomorphic (one shape) is fastest, polymorphic/megamorphic slower. **Deoptimization**: when runtime facts contradict TurboFan's assumptions, optimized code bails out ("deopt") back to bytecode and may re-optimize. Deopt-inducing patterns: adding/deleting properties after creation (`delete` → dictionary mode), same property with different types across instances, polymorphic call sites, `arguments` aliasing parameters in sloppy mode, `eval`/`with`, mutating prototypes. Best practice: initialize all fields in constructors, same order, consistent types.

**JS10** — Tree-shaking is dead-code elimination at bundle time: the bundler marks unused exports as unused and drops them. ES modules are **static**: `import`/`export` are parsed declarations, so the full graph and bindings are known before execution — safe to prune (with `"sideEffects": false` in package.json and `usedExports` in webpack). CommonJS is **dynamic**: `require()` is a runtime call with computable paths, `exports` is mutated at runtime, and usage can't be known statically — so bundlers must include whole modules. Transpiling ESM to CJS (old Babel output) also breaks shaking.

**JS11** — `undefined` means "not assigned/missing" (type `undefined`); `null` means intentional "no value" (an object). `null == undefined` is `true` (loose equality treats them as equivalent); `===` is `false` because types differ. `x == null` is the idiom to catch both. **`??`** returns the right operand only when the left is `null`/`undefined` (unlike `||`, which triggers on all falsy values — `0` and `''` included). **`?.`** short-circuits to `undefined` when the left side is nullish; variants: `a?.b`, `a?.[b]`, `a?.()`.

**JS12** — `map` transforms every element into a new array; `filter` keeps elements passing a predicate; `reduce` folds the array into one value via an accumulator. With an initial value, the accumulator starts there and iteration covers all indices; without one, the first element is the initial accumulator and iteration starts at index 1 — an empty array without an initial value throws `TypeError`. `flatMap` = `map` then flatten one level; useful for one-to-many transforms, e.g. splitting lines into words: `lines.flatMap(l => l.split(' '))`.

**JS13** — Template literals are backtick strings supporting `${expr}` interpolation and multiline text. A **tagged template** calls a function instead of producing a string: `tag\`a ${x} b\`` invokes `tag(strings, x)` where `strings` is the frozen cooked-parts array (`.raw` gives raw text). Example:

```js
const esc = s => String(s).replace(/[&<>"']/g, c =>
  ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]));
function html(strings, ...vals) {
  let out = '';
  strings.forEach((s, i) => { out += s; if (i < vals.length) out += esc(vals[i]); });
  return out;
}
html`<p>${userInput}</p>`;            // userInput escaped

function sql(strings, ...vals) {      // parameterized SQL
  return { text: strings.join('?'), params: vals };
}
```

**JS14** — Destructuring extracts data into variables by pattern. Object: `const { a, b: renamed, c = 5 } = obj;` (rename + default), nested: `const { u: { name } } = data;`. Array: `const [first, , third] = arr;` (holes skip). **Rest**: `const { a, ...others } = obj;` / `const [x, ...rest] = arr;` collects the remainder (must be last element; object rest copies own enumerable props). Also used for parameter defaults and swapping: `[a, b] = [b, a]`.

**JS15** — `for...in` iterates **enumerable string keys** of an object, including inherited enumerable ones. `for...of` iterates **iterables** (arrays, strings, Maps/Sets, generators, NodeList) via `Symbol.iterator`. Avoid `for...in` on arrays: keys come out as strings, inherited properties (e.g., anything added to `Array.prototype`) leak in, order isn't guaranteed, and non-index properties are included. For plain objects use `for...of` with `Object.keys/entries/values`.

**JS16** — Generics parameterize types: `function identity<T>(v: T): T`. **Constraints** limit `T`: `function getId<T extends { id: number }>(x: T) { return x.id; }` (also `keyof T` for valid keys). **Conditional types** compute a type from a test: `type TypeName<T> = T extends string ? 'string' : T extends number ? 'number' : 'other';` (distributes over unions). **`infer`** declares a type variable inside a conditional to extract: `type ElementType<T> = T extends (infer U)[] ? U : never;` `type Unwrap<T> = T extends Promise<infer V> ? V : T;` (this is how `ReturnType`, `Awaited` work).

**JS17** — **CommonJS**: runtime, synchronous `require()`, `module.exports` object, dynamic paths, value copies; Node's legacy default. **ESM**: static, hoisted imports, live bindings, async loading, strict by default, `import.meta`, top-level `await`, dynamic `import()`. Node distinguishes by extension and `package.json`: `"type": "module"` makes `.js` files ESM (`.cjs`/`.mjs` force either regardless); default is `"commonjs"`. Interop: ESM can `import()` CJS (default export = `module.exports`); CJS `require()` of ESM is only supported in recent Node versions. CJS globals like `__dirname` have ESM equivalents derived from `import.meta.url`.

**JS18** — TypeScript is **structural**: compatibility is by shape, not name. **Excess property checks** apply only to *fresh object literals* assigned to a typed target — `{x:1, y:2}` against `{x:number}` errors, but the same object via an intermediate variable passes (no literal = no check). **`extends` vs `satisfies`**: `const a: T = ...` widens the variable's type to `T` (losing literal precision); `const b = ... satisfies T` checks conformance but keeps the inferred, more precise type:

```ts
const a: Record<string,string> = { home: '/' };  // a.home: string
const b = { home: '/' } satisfies Record<string,string>; // b.home: '/'
```

**Variance (4.7+)**: `out T` marks covariant (output-only positions), `in T` contravariant (input-only) — e.g. `interface Producer<out T> { next(): T }`, `interface Consumer<in T> { send(v: T): void }`. This makes variance explicit and sound for mutable containers where structural inference is unsound.

**JS19** — `Proxy(target, handler)` intercepts fundamental operations via traps: `get`, `set`, `has`, `deleteProperty`, `apply`, `construct`, `ownKeys`, etc. `Reflect` exposes the default behaviors with identical signatures — call `Reflect.*` inside traps to forward correctly. The engine enforces invariants (e.g., a `get` trap can't lie about non-configurable, non-writable properties). Example:

```js
function reactive(obj, onChange) {
  return new Proxy(obj, {
    set(t, prop, value, recv) {
      const ok = Reflect.set(t, prop, value, recv);
      if (ok) onChange(prop, value);   // reactive data binding
      return ok;
    },
    get(t, prop, recv) {
      track(prop);                     // dependency tracking (Vue 3 style)
      return Reflect.get(t, prop, recv);
    }
  });
}
```

Function-call interception uses the `apply` trap on a proxied function (validation wrappers, logging, memoization).

**JS20** — `SharedArrayBuffer` is raw fixed-length memory shareable between the main thread and Web Workers (browsers require cross-origin isolation: COOP/CORP headers). Both sides build `TypedArray` views over the same buffer and coordinate with **`Atomics`**: `load/store/add/exchange/compareExchange/and/or/xor`. **Ordering**: atomic ops are sequentially consistent and give cross-thread visibility; plain (non-atomic) reads/writes have no such guarantee — always use `Atomics.load/store` for shared flags. `Atomics.wait(ta, idx, expected, timeout)` blocks the thread until `Atomics.notify` wakes it, the value changes, or timeout (futex-style; it throws on browser main threads — use `Atomics.waitAsync` there, or wait in workers). Typical pattern: SAB for data + a `compareExchange` spin/`wait` loop for a mutex, plus `postMessage` to transfer the buffer.

# Bash

**B1** — Unquoted, `$@` and `$*` both expand to all positional parameters and are then word-split/globbed. Quoted: **`"$*"`** joins all parameters into **one string** using the first character of `IFS`; **`"$@"`** keeps each parameter a **separate word**. With `./s.sh "a b" c`: `"$*"` → `"a b c"` (one word), `"$@"` → `"a b" "c"` (two words). Use `"$@"` almost always.

**B2** — `-e`: exit immediately when any command (or pipeline) returns non-zero (exempt contexts: `if`/`while` conditions, `&&`/`||` chains). `-u`: treat unset variables as errors instead of empty strings (catches typos). `-o pipefail`: a pipeline's exit status is the first non-zero exit of any stage (default is only the last command's status). Together: fail fast and don't let errors hide. Caveats: guard expected failures with `|| true`, and `-e` has subtle context rules.

**B3** — `$(cmd)` is command substitution; it nests naturally, unlike legacy backticks (which can't nest without escaping). `$((expr))` is arithmetic expansion: bash-native, no word-splitting surprises, supports bases (`16#ff`); `expr` is an external, legacy tool that needs quoting/escaping (`expr 3 \* 4`) and is error-prone — prefer `$((...))`, and `bc` for floating point.

**B4** — Process substitution `<(cmd)` runs the command, connects it to a pipe, and substitutes a `/dev/fd/N` path — letting programs that require *filename arguments* read command output. Classic use:

```bash
diff <(sort file1) <(sort file2)
```

Also `while IFS= read -r line; do ...; done < <(grep pat file)` keeps loop variables in the current shell (unlike piping into `while`).

**B5** — Never parse `ls`. `for f in $(ls)` breaks on spaces/newlines (word splitting), globs metacharacters, and depends on `ls` output format. Safe patterns: use globs directly (`for f in *; do` — globbing doesn't word-split), or `find` with null delimiters: `find . -type f -print0 | while IFS= read -r -d '' f; do ...; done`, or `find ... -print0 | xargs -0`. Add `shopt -s nullglob` so empty globs expand to nothing.

**B6** — `cmd <<EOF ... EOF` feeds a multi-line literal (here document) to stdin; variables expand unless the delimiter is quoted (`<<'EOF'`). `cmd <<<"string"` (here string) feeds one string plus newline. `<<-EOF` strips **leading tabs only** (not spaces) from each line, so indented scripts still work.

**B7** — Redirections are processed **left to right**, and `2>&1` means "make stderr a copy of *where stdout points right now*":
- `cmd > file 2>&1` — stdout → file first; then stderr → same file. **Both go to the file.**
- `cmd 2>&1 > file` — stderr → current stdout (the terminal) first; then stdout → file. **stderr shows on screen, stdout goes to the file.**
- `cmd &> file` — bash shorthand for `> file 2>&1` (both to file; not POSIX).

**B8** — `mkdir` is preferred because it is a **single atomic syscall**: it fails if the directory exists, so there's no check-then-create (TOCTOU) race. A file-based lock (`[ -e lock ] && exit; touch lock`) can be entered by two processes between the test and the create.

```bash
#!/usr/bin/env bash
LOCK=/tmp/myjob.lock
cleanup() { rm -rf "$LOCK"; }
trap cleanup EXIT INT TERM          # runs on normal exit, Ctrl-C, SIGTERM

if ! mkdir "$LOCK" 2>/dev/null; then
  echo "already running (pid $(cat "$LOCK/pid" 2>/dev/null))" >&2
  exit 1
fi
echo $$ > "$LOCK/pid"
# ... work ...
```

SIGTERM/SIGINT trigger the trap → cleanup runs. SIGKILL can't be trapped → stale lock; mitigate with a PID-liveness check or, better, `flock` (kernel releases the lock when the process dies): `exec 9>"$LOCK.flock"; flock -n 9 || exit 1`.

**B9** — Single quotes: fully literal, nothing expands (`echo '$var'` → `$var`). Double quotes: expand variables/command substitution but no word splitting or globbing (`var="a b"; echo "$var"` → `a b` as one arg). No quotes: expansion **plus** word splitting and globbing (`touch $var` creates two files `a` and `b`). Rule: quote everything unless you explicitly want splitting/globbing.

**B10** — Tests: `-e` exists, `-f` regular file, `-d` directory, `-r`/`-w`/`-x` readable/writable/executable, `-s` non-empty, `-L` symlink. `[ ]` is the POSIX `test` builtin: its arguments undergo word splitting/globbing, so quote variables (`[ -f "$f" ]`), and combine tests with `-a`/`-o` or separate brackets. `[[ ]]` is a bash keyword: no splitting/globbing, supports `&&`/`||`, `<`/`>` sorting, and regex `=~` — safer and more expressive.

**B11** — `$?` exit status of the last command (error handling: `cmd || exit 1`); `$$` current shell PID (log/trap file naming; note it stays the parent's PID in subshells — `$BASHPID` differs); `$!` PID of the last background job (`pid=$!; ...; wait $pid`); `$#` number of positional args (usage validation: `[ $# -lt 1 ] && usage`).

**B12** — `foo() { ...; }` is POSIX; `function foo { ...; }` is a ksh-style variant bash also accepts (and `function foo() {}` works too) — functionally equivalent. "Return" options: (1) `return N` sets the exit status, read via `$?`; (2) `echo` data and capture with command substitution (trailing newlines stripped); (3) set global variables; (4) namerefs: `declare -n ref=$1` for by-reference output.

**B13** — `PATH` is a colon-separated list of directories searched in order; the first match wins (cached in the hash table — `hash -r` after installing binaries). Builtins (`cd`, `echo`, `kill`) execute inside the shell process (no fork/exec); external commands are separate binaries from `PATH`. Check with `type -a cmd` (lists aliases/functions/builtins/all PATH matches), `command -v cmd`, or `which cmd`.

**B14** — `trap 'commands' SIGNAL` runs commands when the signal (or event) fires: `trap cleanup EXIT INT TERM` handles normal exit, Ctrl-C, and SIGTERM; `trap 'echo failed' ERR` fires on simple-command failure (not in `if`/`while` conditions or `||` chains). Bash does not interrupt the current command to run a trap — it waits for it to finish. If signals arrive while a handler runs, bash defers them and runs the pending traps after it returns (same-signal bursts may coalesce). The `EXIT` trap runs last, after any signal handler that exits the script.

**B15** — Command substitution captures output into a string (word-split on `IFS`, all in memory, then passed as one command line — can hit `ARG_MAX`). `xargs` streams stdin, splits into **batches** sized to avoid `ARG_MAX`, and invokes the command repeatedly. `find ... -print0 | xargs -0 cmd` uses NUL delimiters so spaces/newlines/globs in filenames are safe. `-P N` runs up to N invocations concurrently (`-P 0` = unlimited); `-I{}` substitutes each input line for `{}`.

**B16** — Indexed arrays: `declare -a a; a[0]=x; a+=(y); echo "${a[@]}"; echo "${#a[@]}"` (sparse, numeric keys). Associative (bash 4+): `declare -A m; m[key]=val; echo "${m[key]}"; for k in "${!m[@]}"; do echo "$k -> ${m[$k]}"; done; echo "${#m[@]}"`. Differences: indexed arrays use automatic numeric subscripts and preserve insertion order; associative arrays take arbitrary string keys, require `declare -A`, and have no guaranteed order. `"${a[@]}"` keeps elements separate; `"${a[*]}"` joins with `IFS`; slicing: `"${a[@]:1:2}"`.

**B17** — `(...)` runs in a **subshell**: a forked copy — variable changes, `cd`, and options don't affect the parent; its exit code is the last command's. `{ ...; }` is a **group command** in the current shell: variables persist, needs a space before `{` and a trailing `;`. Piping into `while` loses changes because each side of a pipe runs in its own subshell (`cat f | while read...; done` — the loop's variables vanish). Fixes: `while ...; done < <(cat f)` (process substitution), a here-string, `mapfile`, or `shopt -s lastpipe` (with job control off).

**B18** — SIGINT: Ctrl-C, trappable, default terminate. SIGTERM: "please terminate," trappable, the standard polite kill. SIGHUP: terminal hangup (bash may propagate to jobs with `hup`/`huponexit`); conventionally "reload" for daemons. SIGKILL (9): **cannot be caught or ignored** — no cleanup, possible stale locks/temp files. Graceful shutdown with background children:

```bash
pids=()
trap 'for p in "${pids[@]}"; do kill -TERM "$p" 2>/dev/null; done; wait' INT TERM
worker & pids+=($!)
# ...
wait   # interruptible; trap runs, children get TERM, wait reaps them
```

**B19** —

```bash
#!/usr/bin/env bash
set -euo pipefail

process_chunk() {                 # $1=input, $2=output
  awk '/ERROR/ {c++} END {print c+0}' "$1" > "$2"
}
export -f process_chunk           # so child bash can call it

split -n l/8 -d --additional-suffix=.part big.log /tmp/chunk_
ls /tmp/chunk_*.part | xargs -P 8 -I{} bash -c 'process_chunk "$1" "$1.count"' _ {}
cat /tmp/chunk_*.part.count | awk '{s+=$1} END {print s}' > merged.txt
```

Trade-offs: parallelism bounded by CPU cores and disk I/O (grep/awk are fast, so I/O often bottlenecks); per-job `bash -c` startup overhead; `-P` gives no ordering — numbered chunks let you reassemble deterministically. Error propagation: `xargs` exits 123 if any child fails, so `set -e` aborts the script; for finer control, launch jobs yourself, `wait` each PID, and collect exit codes, or write per-chunk status files.

**B20** — Running a command normally forks a child and the shell continues after it exits. `exec cmd` **replaces** the shell process image with the command (same PID, no return — the shell is gone), saving a process (useful for wrapper scripts' last step). `exec` with only redirections applies them to the current shell permanently: `exec 3>file` opens fd 3 for writing (`echo x >&3`), `exec 3>&-` closes it, `exec 3>&1` duplicates stdout onto fd 3 (the classic stdout/stderr swap trick). Coprocess:

```bash
coproc GREP { grep -i pattern; }   # GREP[0]=its stdout (read), GREP[1]=its stdin (write)
exec 3>&${GREP[1]} 4<&${GREP[0]}
echo "search term" >&3; read -r line <&4
```

Use one for a persistent interactive backend (database CLI, ssh session, long-running filter) instead of paying process startup per interaction.

# PowerShell

**PS1** — `Write-Output` writes to the **success stream**: objects flow through the pipeline, can be captured (`$x = f`), filtered, and redirected. `Write-Host` writes to the **information stream** (since PS 5.0) for display only — it isn't pipeline output and can't be assigned. This matters because `Write-Host` inside a function pollutes nothing but also can't be consumed, while stray `Write-Output` pollutes return values: callers capturing `$x = Get-Thing` get your "status messages" mixed into `$x`.

**PS2** — The pipeline passes full objects (not strings) downstream, streaming item by item. `ForEach-Object` is a cmdlet: works mid-pipeline, streams (starts before upstream finishes), has `-Begin/-Process/-End`, `$ _`/`$PSItem`, and `-Parallel` (v7). The `foreach` statement is a language construct: faster (no cmdlet overhead), operates on in-memory collections, but can't receive pipeline input and has no streaming. Use the statement for known in-memory collections; use `ForEach-Object` inside pipelines or for parallelism.

**PS3** — `[PSCustomObject]` preserves property order, is pipeline/format-table friendly, and is the right shape for ad-hoc structured output; `[hashtable]` is a key-value dictionary with O(1) lookup, unordered (use `[ordered]@{}` for order), and case-insensitive keys by default. Use hashtables for lookup tables, PSCustomObject for rows of data you emit. Convert:

```powershell
$obj = [PSCustomObject]$ht                      # hashtable -> object
$ht2 = @{}; $obj.PSObject.Properties |
  ForEach-Object { $ht2[$_.Name] = $_.Value }   # object -> hashtable
```

**PS4** — **Terminating** errors stop execution and are caught by `try/catch`; **non-terminating** errors are written by a cmdlet and execution continues. `-ErrorAction` is per-cmdlet; `$ErrorActionPreference` is the scope-wide default (`Continue`, `SilentlyContinue`, `Stop`, `Inquire`, `Ignore`). Setting `-ErrorAction Stop` (or preference `Stop`) promotes non-terminating errors to exceptions so `try/catch` can catch them — otherwise `catch` only sees terminating errors/exceptions. `-ErrorVariable +name` captures errors without stopping; `Ignore` (unlike `SilentlyContinue`) doesn't add to `$Error`.

**PS5** — Splatting passes a hashtable as named parameters: `$params = @{ Path='C:\logs'; Filter='*.log'; Recurse=$true }; Get-ChildItem @params` (note `@` not `$`). Passing `$params` normally would hand the hashtable itself as a single positional value. Splatting is cleaner for long/dynamic parameter lists, reusable, and splatting an *array* (`$a = @('v1','v2'); cmd @a`) supplies positional arguments.

**PS6** — `Invoke-Command -ComputerName` executes a script block/command remotely and returns (deserialized) output — one-shot, like `ssh host command`. `Enter-PSSession` creates a persistent **interactive** session (like an ssh login); `New-PSSession`/`Exit-PSSession` manage explicit sessions. Transport: **WS-MAN (WinRM)** over HTTP (5985) / HTTPS (5986); PowerShell 7 adds **SSH-based** remoting (`Invoke-Command -HostName user@host`) using OpenSSH as transport. JEA endpoints provide constrained remoting.

**PS7** — PowerShell **unrolls** collections into the pipeline one item at a time, and a pipeline with exactly one item assigns a **scalar**:

```powershell
function Get-Items { $result = @(); $result += "one"; return $result }
$x = Get-Items
$x.GetType().Name    # -> String  (the 1-element array was unrolled)
```

Two items → `Object[]`; **zero items → `$null`**, so `$x.GetType()` throws ("You cannot call a method on a null-valued expression"). Also note `$result += ...` copies the whole array each time (O(n²)). Correct pattern: accumulate in `[System.Collections.Generic.List[string]]`, emit with `Write-Output`, and coerce at the call site — `$x = @(Get-Items)` — or prevent unrolling with `return ,$result` / `Write-Output -NoEnumerate`.

**PS8** — A `[scriptblock]` is an anonymous, invokable code unit (`& $sb`, `.Invoke()`, `.GetNewClosure()`); a function is a named, registered command with its own scope and module surface. Remoting: `Invoke-Command -ScriptBlock { param($a) ... } -ArgumentList $val` — the script block is serialized as text and evaluated remotely, so it must be self-contained; to send a local function, pass `${function:MyFunc}` or use `-FilePath`. The **double-hop problem**: Kerberos credentials can't be delegated from machine A (where you ran `Invoke-Command`) to machine B that A's command touches. Solutions: **CredSSP** (delegates explicit credentials to the second hop — powerful but a security risk, credentials land on the remote), Kerberos resource-based constrained delegation, JEA endpoints, or SSH remoting. `-ArgumentList` passes local values as parameters (serialized snapshot).

**PS9** — `@(...)` is the array subexpression operator: it guarantees an array (empty, single, or many). `[array]` is the .NET type accelerator (`[array]$x` casts/enforces). Force a single result into an array: `@($value)`, `$value = @($value)`, or the comma operator `, $value`. Indexing: `$null[0]` → `$null` (no error); out-of-range array indexing also returns `$null` silently; `@()[0]` → `$null`. Since PS 3, member enumeration makes `$null.Count` → 0 and `@($null).Count` → 1.

**PS10** — `-eq`/`-ne` equality, `-like` wildcard (`*`, `?`, `[a-z]`), `-match` regex (sets `$Matches`), `-contains` (LHS is a **collection**: `$list -contains $item`), `-in` (reversed: `$item -in $list`, PS 3+). All are **case-insensitive by default**; the `c` variants (`-ceq`, `-clike`, `-cmatch`, `-cnotmatch`, `-cin`, …) are case-sensitive. `-contains` vs `-in` is purely operand order: collection-on-left vs value-on-left.

**PS11** — A module is a reusable package of commands. A **script module** (`.psm1`) is PowerShell code with `Export-ModuleMember` controlling exports; a **manifest** (`.psd1`) adds metadata — version, author, `RequiredModules`, `PowerShellEdition`, exported commands, dependencies; a **binary module** is a compiled .NET assembly (C# cmdlets, fastest). `Import-Module` resolves the name against `$env:PSModulePath`, loads the `.psm1` into a module scope (or the assembly), applies the manifest, and imports the exported commands. Since PS 3, modules **auto-load** when you invoke an installed command; `Remove-Module` unloads; `-RequiredVersion` pins versions.

**PS12** — Double quotes interpolate: `"$var"`, `"$($obj.Prop)"` subexpressions, `"$($a + $b)"`; single quotes are literal. Escape with backtick (`` `"$ ``) or use `"$($var)"` to disambiguate. Here-strings: `@" ... "@` (expandable) and `@' ... '@` (literal); the closing `"@` must be the first thing on its own line. Also `-f` for .NET format strings: `'{0:C}' -f 1234`.

**PS13** — `Get-Member` shows the .NET type and every member of pipeline objects (`-Force` reveals hidden/base members, `-Static` for static ones). **Properties** are native .NET properties; **NoteProperties** are added metadata (via `Add-Member` or created by cmdlets like `Select-Object`); **Methods** are .NET methods. `Where-Object` **filters** which objects continue down the pipeline (`Where-Object Name -eq 'x'`); `Select-Object` **projects** — picks/renames properties (building a new PSCustomObject) or trims (`-First`, `-Last`, `-Skip`, `-Unique`).

**PS14** — PowerShell classes (v5+) are compiled .NET types: no pipeline integration (no `begin/process/end`), no dynamic member access, no splatting, and stricter syntax. Limitations vs C#: constructors can't chain with `:this(...)`, a hidden default constructor exists unless suppressed, custom interfaces must be defined in the same session/module to be implemented, and instances don't survive remoting/serialization as their class. Use classes for type-safe data structures with methods, validation attributes, and DSC resources; use advanced functions for pipeline cmdlets. Emit pipeline-friendly `[PSCustomObject]` from functions even when classes exist internally.

**PS15** — `[CmdletBinding()]` turns a function into an **advanced function**: common parameters (`-Verbose`, `-ErrorAction`, `-WhatIf`, `-Confirm`…), parameter-set validation, and the `$PSCmdlet` object. `SupportsShouldProcess` adds `-WhatIf`/`-Confirm`, honored when you call `$PSCmdlet.ShouldProcess($target)`; `DefaultParameterSetName` disambiguates mutually exclusive parameter groups; `[Parameter(Mandatory, ValueFromPipeline, ValueFromPipelineByPropertyName)]` controls binding. With pipeline input, `begin` runs once, `process` runs **once per input item**, `end` runs after — without a `process` block, the whole input arrives at once in `end`.

```powershell
function Remove-Thing {
  [CmdletBinding(SupportsShouldProcess, DefaultParameterSetName='Name')]
  param(
    [Parameter(Mandatory, Position=0, ParameterSetName='Name')] [string]$Name,
    [Parameter(Mandatory, ParameterSetName='Id')] [int]$Id
  )
  process { if ($PSCmdlet.ShouldProcess($Name)) { # remove } }
}
```

**PS16** — Providers expose heterogeneous data stores as hierarchical drives: `FileSystem` (C:), `Registry` (HKLM:, HKCU:), `Certificate` (Cert:), `Environment` (Env:), plus `Variable`/`Function`. `Get-ChildItem` works uniformly over any provider: `Get-ChildItem Env:`, `Get-ChildItem Cert:\CurrentUser\My`. Registry-as-filesystem: `Set-Location HKLM:\SOFTWARE`, `Get-ChildItem` lists keys, `Get-Item`/`Get-ItemProperty` read, `Set-ItemProperty`/`New-ItemProperty` write — note registry **values are properties of key items**, not child items. Providers add `PSPath`/`PSChildName` NoteProperties to every item; create custom drives with `New-PSDrive -PSProvider ...`.

**PS17** — A **runspace** is an independent PowerShell execution environment (one thread, own session state); a **`[powershell]`** object wraps a runspace plus a pipeline invocation API (`[powershell]::Create().AddScript(...).Invoke()`); a **`[runspacepool]`** (`[runspacefactory]::CreateRunspacePool(min,max)`) recycles runspaces across many invocations. Runspaces are the unit of thread safety: each is single-threaded, and objects (PSObject, collections) must not be shared across runspaces — pass serialized data. `ForEach-Object -Parallel` (v7) spawns a fresh runspace per item with `-ThrottleLimit` (default 5) and `$using:` for outer variables — simple but pays runspace startup per item; manual runspace pools are better for long-lived workers and fine-grained control (`BeginInvoke`/`EndInvoke` for async).

**PS18** — PSScriptAnalyzer is the official static-analysis linter for PowerShell. It parses files and applies **rules** (e.g., `PSAvoidUsingWriteHost`, `PSUseDeclaredVarsMoreThanAssignments`, `PSAvoidUsingPositionalParameters`) with **severity levels**: `Error` (includes parse errors), `Warning`, `Information`. Custom rules are classes (C# or PowerShell) implementing the rule interfaces, loaded via `-CustomRulePath`. Suppress per-site with `[System.Diagnostics.CodeAnalysis.SuppressMessageAttribute('PSAvoidUsingWriteHost', '')]` or per-project via a settings file (`PSScriptAnalyzerSettings.psd1`) with `ExcludeRules`; filter with `-Severity`/`-IncludeRule`. CI/CD: run `Invoke-ScriptAnalyzer -Recurse -Severity Error` and fail the build on findings; it integrates with VS Code, GitHub Actions, and can emit SARIF-style reports.

**PS19** — **`$using:`** references variables from the *caller's* scope inside remote sessions (`Invoke-Command`), background jobs (`Start-Job`), and `ForEach-Object -Parallel`; the values are serialized as a snapshot (changes don't flow back). **`-ArgumentList`** passes values as positional parameters to the remote script block (`param($a)`); also a serialization snapshot. Serialization limits: remote output is deserialized into `Deserialized.<Type>` PSObjects — **methods are stripped**, only properties remain, and nested objects are expanded only to a limited depth (a couple of levels) before deeper properties collapse to strings. Complex/live objects therefore degrade across the boundary; return flat, simple data (or rehydrate explicitly) instead of relying on remote object behavior.

**PS20** — **DSC** is declarative configuration-as-code: a `configuration` keyword block compiles to a **MOF** file describing desired state; **resources** are the building blocks (built-in: `File`, `Service`, `Registry`, `Script`; plus community/custom, each exposing `Get/Set/Test`); the **Local Configuration Manager (LCM)** is the per-node engine that receives, applies, and monitors configurations — push (`Start-DscConfiguration`) or pull-server based, with modes `ApplyOnly`, `ApplyAndMonitor`, `ApplyAndAutoCorrect` (`Get/Set-DSCLocalConfigurationManager`). **Windows PowerShell 5.1 vs PS7**: full DSC (LCM, pull server, `Get-DscResource`) exists only in Windows PowerShell 5.1; PowerShell 7+ has no built-in DSC engine (only partial support via compatibility mechanisms). Modern replacements: the cross-platform **DSC v3** (microsoft/DSC — YAML/JSON based, runs PowerShell and native resources), and in practice Terraform, Ansible, Pulumi, Chef, plus Azure's Guest Configuration/Automanage have largely displaced classic DSC for infrastructure-as-code.
