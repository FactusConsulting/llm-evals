# Go

**G1** — An array has a fixed size known at compile time (`[4]int`); the size is part of its type and it's a value type (copied on assignment/passing). A slice is a descriptor `{pointer to backing array, len, cap}` referencing an array; it's dynamically sized and cheap to pass (one 24-byte header on 64-bit). When you `append` to a slice at full capacity, the runtime allocates a **new, larger backing array** (roughly doubling for small slices, ~1.25× growth for large ones), copies the elements over, and returns the new slice — which is why you must capture the return value: `s = append(s, x)`. If capacity remains, elements are written in place.

**G2** — `var x int` declares `x` with its zero value (works at package and function scope). `x := 0` is a short variable declaration with type inference — **only valid inside functions**, and the left side must contain at least one *new* variable. You cannot use `:=` at package scope, for assignment-only to existing variables in the same scope (`no new variables on left side of :=`), or when redeclaring in the same scope without a new variable (except inside `if`/`for` bodies, where it legally shadows).

**G3** — A goroutine is a lightweight, runtime-managed execution unit: ~2 KB initial stack that grows by copying, microseconds to spawn, millions can coexist. OS threads have MB-scale stacks and kernel-level context switches. The scheduler is an **M:N preemptive scheduler** using the **GMP model**: **G** (goroutine), **M** (OS thread), **P** (processor — a scheduling context holding a local run queue; count = `GOMAXPROCS`). Gs are queued on Ps; Ms execute Gs; the scheduler work-steals between Ps, parks Ms during blocking syscalls, uses the netpoller for network I/O, and (since Go 1.14) preempts long-running goroutines asynchronously via signals.

**G4** — Channels are typed conduits for communication and synchronization; a send/receive (or close) establishes a happens-before edge. **Unbuffered**: send blocks until a receiver is ready (rendezvous). **Buffered**: has capacity; send only blocks when the buffer is full, receive blocks when empty. Sending to a **full buffered channel** parks the sending goroutine on the channel's send queue until space frees or a receiver arrives; if no receiver ever comes, the goroutine blocks forever (and if all goroutines are blocked, the runtime panics with `all goroutines are asleep - deadlock!`).

**G5** — `context` carries cancellation signals, deadlines, and request-scoped values across API boundaries (typically `Context` as the first parameter). Minimal example:

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel() // always: releases resources associated with ctx

req, err := http.NewRequestWithContext(ctx, http.MethodGet, "https://example.com/api", nil)
if err != nil { return err }
resp, err := http.DefaultClient.Do(req) // aborted if ctx deadline expires
if err != nil {
    if errors.Is(err, context.DeadlineExceeded) { /* timed out */ }
    return err
}
defer resp.Body.Close()
```

**G6** — Go uses **structural, implicit satisfaction**: a type implements an interface by simply having the required method set — no `implements` keyword. Java/C# require nominal, explicitly declared implementations. This enables decoupling (small interfaces like `io.Reader` satisfied by many types) but means you can't attach methods to types you don't own without wrappers. `interface{}`/`any` is satisfied by every type: powerful as a universal container (pre-generics JSON, containers) but dangerous because it **erases type information** — you recover it only via unchecked-at-compile-time type assertions, which can panic, and it defeats static checking. Generics (Go 1.18) reduce the need for it.

**G7** — Go's memory model guarantees visibility only via **happens-before** edges (channel ops, mutex lock/unlock, `go` statement, `WaitGroup.Wait`, atomics). The example is unsafe for three reasons: (1) it's a **data race** (unsynchronized write/read of `ready`) — undefined behavior; (2) the compiler may hoist the `ready` load out of the loop (`for {}`), spinning forever; (3) even if `ready` is observed, `data` may not be visible — the compiler/CPU may reorder the two writes. Correct alternatives:

```go
// Channel (best here)
done := make(chan string)
go func() { done <- "hello" }()
fmt.Println(<-done) // happens-before guaranteed

// Or sync.WaitGroup + mutex, or atomic.Value / atomic.Bool
// (Go 1.19+ atomics behave as sequentially consistent and are race-free)
```

**G8** — `sync.Mutex` is exclusive; `sync.RWMutex` allows many concurrent readers *or* one writer (a blocked writer blocks new readers to prevent writer starvation). RWMutex has higher constant costs (reader-count contention on shared cache lines), so it only wins with long, genuinely read-dominated critical sections — often a plain `Mutex` is faster. `sync.Map` is specialized: use it for (1) append-only caches where keys are written once and read many times, or (2) read-mostly maps with a stable key set. It uses a read map with atomic loads plus a dirty map for writes, avoiding lock contention. Trade-offs: `sync.Map` is not type-safe (`any` keys/values), slower for write-heavy/churning workloads, and harder to reason about; a regular map + `RWMutex` is simpler, type-safe, and usually fast enough.

**G9** — A module is a versioned unit of dependency managed by `go.mod`, which declares the module path, Go version, `require` directives (direct deps + versions), `replace`, `exclude`, `retract`. `go.sum` contains checksums (of each dependency's `go.mod` and module zip) used to verify downloads against the checksum database — it's a lock/verification file, not a dependency list. `go mod tidy` adds missing and removes unused dependencies (including test dependencies of imported packages) and updates both files. **MVS**: starting from the main module's requirements and transitively reading each module's `go.mod`, the build list for each module path is the **maximum of all minimum versions required** anywhere in the graph — i.e., the *minimum version that satisfies every requirement*. There's no central resolution; upgrades/downgrades are explicit via `go get`, `exclude`, `replace`.

**G10** — `defer` schedules a function call to run just before the enclosing function returns (after the return value is computed; with named results, deferred closures can modify them). Multiple defers execute in **LIFO order**. Loop gotcha: defers accumulate until the *function* returns, so `defer f.Close()` in a loop leaks file descriptors until the end — wrap the body in a function or close explicitly. Related gotcha (pre-Go 1.22): deferred closures capturing the loop variable see its final value.

**G11** — A pointer holds the memory address of a value; declared `*T`, dereferenced with `*p`, address taken with `&x`. Its **zero value is `nil`** (dereferencing nil panics). Pointer to a struct literal — taking the address of a composite literal is allowed:

```go
p := &Point{X: 1, Y: 2} // p is *Point
```

**G12** — `init()` runs during package initialization: after package-level variables are initialized (in dependency order), before `main()`; imported packages are initialized before their importers. A package (and even a single file) may have **multiple `init()` functions**; they execute in the order they appear, with files processed in the order given to the compiler (typically sorted by filename). `init()` takes no arguments, returns nothing, and cannot be called directly.

**G13** — `make` only works with slices, maps, and channels: it allocates *and initializes* the internal structure and returns the type itself (`T`, not `*T`). `new(T)` works with any type: it allocates a zeroed `T` and returns `*T`. Use `make` for the built-ins; `new` is rarely needed (e.g., `p := new(int)` for a pointer to a zeroed basic value).

**G14** — Errors are values: `type error interface { Error() string }`. Idiomatic pattern: check immediately and return/annotate — `if err != nil { return fmt.Errorf("doing x: %w", err) }`. `==` compares only the immediate error value (fine for sentinel errors *if* nothing wrapped them). **`errors.Is`** walks the `Unwrap()` chain (including multi-error `Unwrap() []error`) checking identity or a custom `Is` method — use it for sentinel values. **`errors.As`** walks the chain looking for a value of a specific *type* and binds it — use it to extract structured errors. Both work through `%w` wrapping; `==` does not.

**G15** — Built-in composite types and zero values:
- **array** `[N]T`: every element is T's zero value.
- **slice**: `nil` (len/cap 0; reading is fine, writing requires `make` or `append` — `append` works on nil).
- **map**: `nil` (reads OK, writes panic until `make`).
- **channel**: `nil` (send/receive block forever; usable only after `make`).
- **struct**: each field is its zero value.

**G16** — A data race: two goroutines access the same memory concurrently, at least one is a write, with no synchronization → undefined behavior. `-race` enables compiler instrumentation + the ThreadSanitizer runtime, which dynamically checks accesses against a happens-before relation (vector clocks) and reports conflicting pairs. Costs: ~2–20× CPU, ~5–10× memory; only builds with the flag detect races.

```go
// RACE:
var n int
for i := 0; i < 100; i++ { go func() { n++ }() } // unsynchronized read-modify-write

// Fix with mutex:
var mu sync.Mutex
go func() { mu.Lock(); n++; mu.Unlock() }()

// Fix with channel:
ch := make(chan int, 1); ch <- 0
go func() { v := <-ch; ch <- v + 1 }() // or use sync/atomic.AddInt64
```

**G17** — `select` waits on multiple **channel operations**, proceeding with whichever is ready; unlike `switch` (which picks a branch by evaluating expressions, non-blocking), `select` blocks, its cases are sends/receives, it may have a `default` (non-blocking mode), and operands are evaluated once, in order, before choosing. When **multiple cases are ready, a uniform pseudo-random choice** is made (avoids starvation/bias). Timeout pattern:

```go
select {
case v := <-ch:
    use(v)
case <-time.After(2 * time.Second):
    return ErrTimeout
case <-ctx.Done():
    return ctx.Err()
}
```

**G18** — Escape analysis is a compiler pass deciding stack vs heap allocation: if a variable's lifetime provably ends with its function (its address never "escapes"), it's stack-allocated; otherwise heap. Things that force escape: returning/taking a pointer that outlives the frame, storing into an interface, capturing by a closure/goroutine that outlives it, unknown/very large sizes, and reflection. Inspect with `go build -gcflags="-m"` (add `-m -m` for detail; `-l` to disable inlining). It matters because heap allocation + GC pressure dominate performance in hot paths — reducing allocations (preallocated buffers, value types, avoiding interface boxing) is Go's main optimization lever. It's a best-effort heuristic, not part of the spec.

**G19** — `reflect` provides runtime introspection. `reflect.Type` (from `reflect.TypeOf`) is static type metadata (name, kind, methods, struct fields); `reflect.Value` (from `reflect.ValueOf`) wraps a value plus its type, allowing field access, `Elem()`, `Call()`, and `Set()` (only when `CanSet()` — i.e., the value is addressable). Costs: heavy allocations (boxing into `interface{}`), 10–100× slower than direct code, defeats inlining/escape analysis, no compile-time checking (panics at runtime), and complicated APIs. Justified when the schema is genuinely dynamic (encoding/json, database/sql, ORMs, template engines). For hot paths or known schemas, prefer **code generation** (`go generate`, stringer, protobuf) — type-safe, fast, debuggable.

**G20** — `//go:embed` bakes files into the binary at build time. A single file: `//go:embed hello.txt` above a `string`, `[]byte`, or `embed.FS` variable. Directories: patterns like `//go:embed static/*` into an `embed.FS` (recursive; `all:` prefix includes dot/underscore files). `embed.FS` implements **`io/fs.FS`**, so it composes with `fs.ReadFile`, `fs.WalkDir`, `fs.Sub`, and serves HTTP via `http.FileServer(http.FS(content))`. Limitations: files must be inside the package's directory (no `..` paths), `.`/`_`-prefixed files excluded unless explicitly named or `all:` used, content is read-only and uncompressed (binary size grows), and patterns are resolved at compile time only.

# Rust

**R1** — Ownership is Rust's memory-management model: the compiler statically tracks who owns each value and inserts drops — no GC, no manual free. The three rules: (1) every value has exactly one **owner**; (2) at any time there is either **one mutable reference OR any number of immutable references** (enforced by the borrow checker, see R3); (3) when the owner goes out of scope, the value is **dropped** (RAII — `Drop` runs, heap memory freed). `Copy` types (ints, etc.) are duplicated instead of moved; non-`Copy` values are **moved** on assignment/passing, invalidating the source.

**R2** — `String` is an owned, heap-allocated, growable UTF-8 buffer (`Vec<u8>` with a UTF-8 invariant). `&str` is a borrowed string slice — a view into a `String`, a literal (`&'static str`), or memory elsewhere. In signatures: prefer **`&str` for read-only parameters** (accepts literals and `&String` via deref coercion, so callers never clone); return **`String`** when the caller receives new/owned data; use `String` in structs/fields when you own it; `&str` in structs requires a lifetime annotation.

**R3** — A borrow is a temporary, compiler-tracked reference. Rules: shared `&T` — any number may exist, but they're read-only; mutable `&mut T` — exactly one may exist, and it may mutate. **Aliasing XOR mutability**: you can't have both simultaneously. References must never outlive (dangle from) the owned data — lifetimes prove this at compile time. With NLL, a borrow ends at its *last use*, not lexically, so `let y = &x; println!("{y}"); let z = &mut x;` is fine. The borrow checker turns use-after-free and iterator-invalidation bugs into compile errors.

**R4** — `Result<T, E>` models recoverable failure (`Ok`/`Err`); `Option<T>` models absence (`Some`/`None`). `?` desugars to "return early on `Err`/`None`", applying `From::from` to convert the error type, so `?` works across error types when your error implements `From`. Example:

```rust
use std::io;

fn read_config(path: &str) -> Result<String, io::Error> {
    let contents = std::fs::read_to_string(path)?; // io::Error propagated
    Ok(contents.trim().to_string())
}
```

**R5** — `Box<T>`: single-owner heap allocation, no reference counting — for large values, recursive types (`Box<Node>` in an enum), or `dyn Trait`. `Rc<T>`: single-threaded shared ownership via non-atomic refcounting; `clone()` bumps the count; last owner drops the value. `Arc<T>`: same idea with **atomic** refcounts, safe to share across threads. Use `Box` when you just need heap ownership; `Rc` for shared data within one thread (e.g., graph nodes, immutable caches); `Arc` for cross-thread sharing. Pair `Rc`/`Arc` with `Weak` to break reference cycles.

**R6** — Traits define shared behavior (methods, associated types/consts, default implementations) that types opt into with explicit `impl Trait for Type` blocks — unlike Go's implicit satisfaction. **`dyn Trait`** (trait object): type erased behind a pointer (`&dyn`, `Box<dyn>`), dispatched via a vtable at runtime — dynamic dispatch, allows heterogeneous collections, but has indirection cost and requires object safety (no generic methods, no `Self` by value). **`T: Trait`** (generic bound): monomorphized per concrete type — static dispatch, inlinable, zero-cost, but code bloat and homogeneous-only (one `T` per instantiation). Rule of thumb: generics for performance/compile-time flexibility, `dyn` when you need heterogeneity or smaller code.

**R7** — It fails because the return type is a reference, but the compiler can't tell *which input's* lifetime it follows — it can't infer whether the result borrows from `x` or `y` (elision rules only cover the single-input case). Fix by declaring an explicit lifetime tying the output to both inputs:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

`'a` here means the returned reference is valid only as long as **both** inputs are valid (the intersection of their lifetimes) — callers then can't keep the result beyond the shorter input's scope, which is exactly the safety guarantee.

**R8** — `Send`: the type can have ownership moved to another thread. `Sync`: `&T` is `Send` — the type can be shared by reference across threads. Both are auto-derived marker traits the compiler verifies. `Rc<T>` is neither: its refcount uses non-atomic increments/decrements, so two threads could concurrently bump the count, miss a decrement, and both believe they're the last owner → double free / use-after-free. `Arc<T>` performs refcount updates with atomic RMW operations (with correct ordering), so counts are always consistent across threads; `Arc<T>` is `Send`/`Sync` exactly when `T: Send + Sync`.

**R9** — `async fn` compiles to a **state machine** implementing `Future` (an `Output`-producing type with `poll(Pin<&mut Self>, &mut Context) -> Poll<Output>`). Futures are **lazy** — nothing runs until polled. `.await` marks suspension points; the compiler stores locals across them (which is why futures can be self-referential → `Pin`, see R18). An **executor** (Tokio, async-std, smol) owns tasks, polls them, and drives I/O/timer reactors; a `Waker` re-schedules a task when its event completes. Tokio adds a work-stealing multi-thread scheduler. Versus Go: goroutines are **stackful, preemptively scheduled** by the runtime, and blocking-style code just works (the runtime parks goroutines on blocking calls via its netpoller). Rust async is **stackless, cooperative, runtime-optional** ("colored" functions — `async` propagates through signatures), but has zero implicit runtime cost and integrates with any executor.

**R10** — `unsafe` opts a block/function/impl into extra capabilities. Three things you can't do in safe Rust: (1) **dereference raw pointers** (`*const T`/`*mut T`); (2) **call `unsafe` functions** — including FFI `extern` functions and intrinsics; (3) **access or mutate `static mut`** / access union fields / implement `unsafe` traits (`Send`, `Sync`, `GlobalAlloc`). Justified for FFI bindings, SIMD/performance-critical kernels, and building safe abstractions over primitives (like `Vec`'s internals) whose invariants the type system can't express. The contract: uphold the relevant invariants manually, encapsulate `unsafe` inside a *safe* public API, document with `// SAFETY:` comments, and validate with Miri/Clippy.

**R11** — Pattern matching deconstructs values against patterns: literals, enum variants, tuples, structs, ranges, bindings (`x @ 1..=5`), with optional `if` guards. `match` can test many patterns and is an expression; `if let` handles a single pattern (with optional `else`/`else if`) — convenient when you only care about one case. The compiler enforces **exhaustiveness**: every possible value must be handled, either by explicit arms or a `_` wildcard — adding a new enum variant breaks compilation at every non-exhaustive `match`, which is a major safety feature.

**R12** — `[T; N]` is a fixed-size array; `N` is part of the type, stored inline (stack or wherever the owner lives). `Vec<T>` is a heap buffer tracked by `{pointer, len, capacity}`. Pushing past capacity triggers reallocation: allocate a new buffer with larger capacity (amortized doubling), **move** the elements (bit-copies + ownership transfer, since `Vec` owns them), free the old buffer. Growth is amortized O(1) per push; use `Vec::with_capacity` to avoid repeated reallocations.

**R13** — Rust enums are **sum types / tagged unions**: each variant can carry its own data (`enum Shape { Circle { r: f64 }, Rect { w: f64, h: f64 } }`), destructured by pattern matching. C enums are just named integer constants; Java enums are fixed sets of object instances (fields are shared per-enum, not per-variant payloads) — neither gives you per-variant data with exhaustive matching. `Option<T>` is `Some(T) | None`: the standard encoding of "maybe a value." Rust has no `null` because null-able pointers cause the "billion-dollar mistake" — absence is instead encoded in the *type system*, so the compiler forces you to handle the `None` case before you can touch the value.

**R14** — An `impl` block attaches functions to a type. `&self` — read-only access to the instance (shared borrow); `&mut self` — may mutate state (exclusive borrow); `self` — takes ownership, consuming the value (e.g., `into_iter`, builder-style `finish`), useful for transformations that invalidate the original. **Associated functions** have no `self` and are namespaced on the type (`String::new()`, `Vec::with_capacity()`), typically constructors.

**R15** — `#[derive(...)]` invokes a proc macro that generates trait implementations mechanically: `Debug`, `Clone`, `Copy`, `PartialEq`/`Eq`, `Hash`, `Default`, plus external ones like serde's `Serialize`/`Deserialize`. You **cannot** derive when: (1) no derive macro exists for that trait (e.g., `Drop`, `Fn` — derivable traits are opt-in per trait); (2) a field's type doesn't implement the trait (derives generate bounds-free code requiring every field to satisfy it); (3) the type has generic parameters that don't satisfy the required bounds; (4) the trait needs custom semantics (e.g., `PartialOrd` ordering nuances, or `Clone` that shouldn't copy everything).

**R16** — `Cow<'a, T>` is `enum Cow<'a, T> { Borrowed(&'a T), Owned(<T as ToOwned>::Owned) }` — a value that is either borrowed or owned, with mutation promoting it to owned ("clone on write"). Useful when a function sometimes modifies its input: callers avoid allocations in the common no-change case.

```rust
use std::borrow::Cow;

fn sanitize(s: &'static str) -> Cow<'static, str> {
    if s.contains("bad") { Cow::Owned(s.replace("bad", "good")) }
    else { Cow::Borrowed(s) } // zero allocations in the common path
}
```

Also common in APIs/structs that accept `Cow<'a, str>` to accept both `&str` and `String` without copying.

**R17** — `mod` *declares* a module — inline (`mod foo { ... }`) or from a file (`mod foo;` → `foo.rs` or `foo/mod.rs`); it defines the privacy boundary and the tree. `use` brings already-declared paths into local scope (`use crate::foo::Bar;`) — pure ergonomics, no effect on structure. `pub` controls visibility (`pub`, `pub(crate)`, `pub(in path)`, `pub(super)`); without it, items are private to the module. Filesystem mapping: crate root is `lib.rs`/`main.rs`; child modules map to files/directories below it. Edition 2015 used global absolute paths, required `extern crate`, and nested modules needed `mod.rs`; **2018** introduced `crate::` absolute paths, uniform paths, dropped `extern crate` (mostly), and allowed `foo.rs` alongside `foo/` (no forced `mod.rs`).

**R18** — `Pin` is a type that (via the type system, for `!Unpin` types) guarantees the pointee will not be moved until it's dropped. It's needed because some values are **self-referential**: `async` state machines store pointers to their own locals across `.await` points; moving such a struct (a `memcpy`) would leave interior pointers dangling → UB. `poll` therefore takes `Pin<&mut Self>`, and executors hold futures in `Pin<Box<T>>`. **`Unpin`** is an auto marker trait meaning "moving this type is harmless" — nearly every type is `Unpin`, so `Pin` is trivial for them (`Pin::new` requires `Unpin`); futures generated by `async` are `!Unpin`, forcing them through `Pin`-aware APIs. `Pin` also imposes "structural pinning" rules: if you pin a field, you must not offer a safe way to move it out.

**R19** — `macro_rules!` (declarative) matches against token *patterns* and expands to code at compile time; supports recursion but can't inspect syntax beyond tokens. **Procedural macros** are Rust functions over `TokenStream → TokenStream`: **derive** macros (generate impls for an annotated struct/enum, e.g., serde), **attribute** macros (rewrite arbitrary items, e.g., `#[tokio::main]`), and **function-like** macros (arbitrary syntax, e.g., `sqlx::query!`). Hygiene: declarative macros are hygienic for identifiers — local variables created inside the macro can't collide with or capture caller identifiers, and `$crate` refers to the defining crate. Proc macros have **no hygiene**: they see raw tokens and control everything, so generated identifiers can accidentally collide and must be chosen carefully (or use spans/unique names).

**R20** — Zero-cost abstraction: a high-level construct compiles to machine code as good as (or better than) the hand-written version — "what you don't use, you don't pay for." **Iterators**: chains like `iter().filter().map().sum()` are fully inlined; LLVM fuses them, elides bounds checks (iterator semantics prove access patterns), and vectorizes — often beating a naive C `for` loop because ownership gives LLVM aliasing guarantees. **Generics/monomorphization**: each instantiation is compiled into specialized code for the concrete type — no vtable indirection, enables devirtualization and inlining of trait methods. **Trait static dispatch**: `T: Trait` calls resolve to direct (inlinable) calls; `dyn Trait` dynamic dispatch exists but is opt-in. Combined with no GC, move semantics, and `Drop` for deterministic cleanup, you get GC-free, allocation-controlled, high-level code. The costs shift to compile time and binary size (code duplication from monomorphization).
