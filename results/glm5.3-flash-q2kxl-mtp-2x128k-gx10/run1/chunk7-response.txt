# Application Architecture

**AA1** — A monolith is a single deployable unit: components make in-process calls, typically share one database, and are built/released together. Microservices split the system into independently deployable services, each owning its own data, communicating over a network.

Three problems microservices introduce that monoliths don't:
1. **The network is a failure point** — every call can fail, time out, or add latency; you must handle partial failures (monolith calls are function calls).
2. **Distributed data consistency** — no ACID transactions spanning services; you need sagas, eventual consistency, and compensations.
3. **Operational complexity** — N build pipelines, service discovery, distributed tracing, versioning, and orchestration instead of one deployment. (Also: harder end-to-end testing and debugging.)

**AA2** — **Synchronous**: the caller blocks until the callee responds; request/response semantics; the caller and callee must both be up. Example: gRPC over HTTP/2 (or REST over HTTP). **Asynchronous**: the caller doesn't wait — fire-and-forget events, queued commands, or async request/reply via correlation IDs; producer and consumer are temporally decoupled. Example: publishing to Kafka (or RabbitMQ), webhooks. Note: "async I/O" (non-blocking sockets) is a different axis from async communication patterns.

**AA3** — A **reverse proxy** is a generic L7 traffic broker: TLS termination, routing, caching, compression, static content, basic security. An **API gateway** adds API-specific concerns: authentication/authorization (JWT/OAuth), rate limiting and quotas, API versioning, request/response transformation, aggregation, metering, developer portals. A gateway can front API traffic and do TLS/routing, but it doesn't replace a reverse proxy/CDN for static content caching, WAF, and global edge presence — and gateways add latency and policy overhead. The common pattern is LB/CDN → gateway → services. For a pure-API estate, a gateway can largely replace the reverse proxy; for general web estates, no.

**AA4** — A **Saga** is a sequence of local transactions, each paired with a compensating transaction; if a step fails, previously completed steps are compensated (semantic rollback, not ACID). **Choreography**: services react to each other's events with no coordinator — fewer moving parts, but the flow logic is scattered and hard to visualize; appropriate for few participants and simple flows. **Orchestration**: a central coordinator (Temporal, Camunda, custom) tells each service what to do — explicit, observable, easy to modify flows, but the coordinator is a failure point and can become a god object; appropriate for complex, long-running, or compliance-sensitive flows.

**AA5** — **CQRS** separates the write model (commands enforcing business invariants) from read model(s) (denormalized views optimized for queries), often in different stores. **Event sourcing** persists state changes as immutable events; current state is derived by replay. They pair naturally because the event stream is the raw material for building projections/read models asynchronously. The combination solves what CRUD can't: independent scaling of reads vs. writes, read models shaped per query (no expensive joins), a built-in audit trail, temporal queries ("what was X's state last March?"), and decoupling the write schema from divergent read needs. Costs: complexity, eventually consistent reads, projection rebuilds.

**AA6** — A **Circuit Breaker** wraps remote calls and tracks failures. Three states: **Closed** (normal; failures counted), **Open** (threshold exceeded — fail fast without touching the dependency, for a timeout period), **Half-Open** (trial requests allowed; success closes it, failure reopens it). A **retry with backoff** re-attempts transient failures per call; a breaker stops the whole system from hammering a failing dependency and causing cascades/thread-pool exhaustion. Use both together: bounded retries with jitter (idempotent operations required) inside the Closed state, with the breaker tripping when the error rate or retry budget is exhausted — retry storms are exactly what breakers prevent.

**AA7** —
1. **Shared DB, shared schema (tenant ID column)**: cheapest, highest density, one migration for all. Weakest isolation: every query must filter tenant ID (or use Postgres RLS), cross-tenant leakage via query bugs, noisy neighbor at the DB level, per-tenant backup/restore is painful.
2. **Shared DB, schema per tenant**: namespace isolation, easier per-tenant restore, moderate security. But migrations across thousands of schemas, connection-pooling complications (pgbouncer), catalog bloat, still shared resources → noisy neighbor persists.
3. **DB per tenant**: strongest isolation (security, compliance, blast radius), per-tenant tuning/backup/scale, noisy neighbor contained at the infrastructure level. Highest cost (instance sprawl), operational overhead, cross-tenant analytics hard.
Typical answer: tier it — shared schema for small tenants, dedicated DBs for premium/compliance tenants.

**AA8** — **Eventual consistency**: writes are accepted and propagated; reads may be stale until convergence — high availability/latency, divergence window. **Strong consistency**: reads reflect the latest committed write, usually via consensus or a single leader — costs latency and availability during partitions. For never-oversell inventory: make the stock decrement **strongly consistent and atomic** — a single-leader store (PostgreSQL) with a conditional update (`UPDATE stock SET qty = qty - ? WHERE sku = ? AND qty >= ?`) in a transaction, or `SELECT ... FOR UPDATE`; idempotency keys on orders; a **reservation pattern** (TTL holds during checkout) to avoid long lock windows; the **outbox pattern** for downstream events. At scale: partition by SKU so each SKU's writes serialize on one leader/shard; hot SKUs get a per-SKU queue/actor or sharded counters with reconciliation; caches hold display counts only, never the decrement decision. Use distributed SQL (CockroachDB/Spanner) only if multi-region strong consistency is required.

**AA9** — A **sidecar proxy** is a proxy container deployed alongside each service instance (same pod) that intercepts all its inbound/outbound traffic. In Istio, **istiod** is the control plane: service discovery, xDS config distribution, and a CA issuing SPIFFE workload certificates. **Envoy sidecars are the data plane**: enforcing mTLS, L7 routing, retries/timeouts, telemetry, and policy (traffic redirected through them via iptables, ports 15001/15006). Data plane = traffic handling; control plane = configuration, policy, identity. **mTLS between sidecars** gives every workload a cryptographic identity (auto-issued, auto-rotated SPIFFE certs), mutual authentication plus encryption hop-by-hop, and uniform zero-trust without touching application code. Application-level TLS, even when implemented, authenticates connections rather than workloads uniformly, requires per-app cert management, doesn't cover non-HTTP traffic or probes, and offers no central policy — sidecar mTLS solves identity, uniformity, and operational burden.

**AA10** — The **Strangler Fig pattern**: put a facade (reverse proxy) in front of the legacy system and incrementally route functionality to new services until the legacy core is "strangled." Concrete plan for .NET Framework → .NET 8:
1. Front the monolith with YARP (or Nginx).
2. Pick a bounded context with clear seams (e.g., invoicing).
3. Build the .NET 8 service with its own schema.
4. Route `/api/invoicing/*` to the new service; feature-flag the route for rollback.
5. Migrate data incrementally: dual writes or CDC (Debezium) from the legacy DB, or an anti-corruption layer while the legacy DB remains source of truth.
6. Move auth to OIDC/JWT rather than sharing legacy sessions.
7. Delete the legacy code path; repeat per feature.
End state: the monolith shrinks to a small core or is retired.

**AA11** — The **12-Factor App** methodology defines cloud-native application properties. Key factors:
- **Codebase** — one repo, many deploys → traceability.
- **Config** — configuration in the environment, not code → same artifact across environments; fits containers/orchestration.
- **Dependencies** — explicitly declared → reproducible builds.
- **Backing services** — DB/queue attached as URL+credentials → swap without code changes.
- **Build/Release/Run** — strict separation → immutable releases with rollback.
- **Processes** — stateless, share-nothing → horizontal scaling and rescheduling by orchestrators.
- **Port binding** — self-contained service listening on a port → container-friendly.
- **Disposability** — fast startup, graceful shutdown → elastic scaling and deploys.
- **Dev/prod parity** and **logs as stdout streams** → less drift, platform-managed aggregation.
These matter because they make apps schedulable, scalable, and replaceable by platforms like Kubernetes.

**AA12** —
- **Coupling**: REST/gRPC has temporal/availability coupling (caller needs callee up); Kafka decouples in time (producers/consumers independent), though schema coupling remains.
- **Scalability**: Kafka partitions + consumer groups scale linearly and buffer bursts; REST requires autoscaling both sides with explicit backpressure.
- **Debugging**: async flows have no single call stack — you need correlation IDs, tracing, and lag monitoring; REST is easier to reason about.
- **Ordering**: Kafka guarantees order only per partition (key-based partitioning for per-entity ordering); REST/gRPC gives natural per-connection, synchronous ordering.
- **Failure handling**: Kafka — retries, DLQs, replay, idempotent consumers, poison-pill handling; REST — timeouts, circuit breakers, errors surfaced immediately to the caller.
Choose **Kafka** for high-throughput event fan-out, event sourcing/audit, stream processing, and burst buffering. Choose **REST/gRPC** for request/response, low-latency synchronous workflows, strong per-call contracts, and simple CRUD.

**AA13** — A **load balancer** distributes traffic across backends. **L4** (transport): routes by connection/flow (IP:port), no payload awareness — fast and cheap (AWS NLB, Azure LB, IPVS). **L7** (application): inspects HTTP — routes by path/host/headers, cookie affinity, canary routing, TLS termination (NGINX, HAProxy, Envoy, ALB). L7 is required for **content-based routing**, e.g., `/api/*` to the API cluster and `/static/*` to a CDN-backed pool, or header-based canary deployments.

**AA14** — A **message queue** (RabbitMQ) is point-to-point work distribution: messages are consumed, acked, and deleted; supports complex routing (exchanges), per-message acks, priorities, dead-lettering; moderate throughput. A **log-based broker** (Kafka) is an append-only, partitioned log: consumers track offsets, messages are retained and replayable, multiple independent consumer groups can read the same data, throughput is very high, ordering is strict per partition. Pick a **queue** for task/job distribution, per-message semantics, and complex routing. Pick **Kafka** for event streaming, event sourcing, replay/analytics, fan-out to many consumers, and high throughput.

**AA15** — A **container** is OS-level virtualization: processes isolated via namespaces (pid, net, mnt, uts, ipc, user) and resource-limited via cgroups, sharing the host kernel. A **VM** virtualizes hardware; each VM runs a full guest OS under a hypervisor. Containers are popular for microservices because they start in seconds, have MB-sized images, achieve high density, are built as immutable layered images, and fit orchestrators (Kubernetes) and CI/CD pipelines natively — ideal for many small, independently deployed, rapidly scaled units.

**AA16** — **Stateless** services hold no client/session state between requests (state is externalized to a DB/Redis); **stateful** services hold state locally that affects behavior. Stateless services scale horizontally because any replica can serve any request: no session affinity, no data partitioning, any instance can be replaced, autoscaling is trivial. Examples: stateless — a REST API service or web frontend; stateful — PostgreSQL, a Kafka broker, Redis, a game/session server.

**AA17** — An **ORM** maps classes to tables and queries to generated SQL, returning objects. Examples: **Hibernate** (Java), **Entity Framework Core** (.NET), SQLAlchemy (Python), GORM (Go), ActiveRecord (Ruby). Trade-offs: ORMs give productivity, type safety, DB portability, injection-safe queries, and migrations; they cost a leaky abstraction (N+1 queries, lazy-loading surprises), sometimes suboptimal generated SQL, awkwardness for complex/analytic queries, and hidden behavior (implicit transactions, cascades). Raw SQL gives full control, DB-specific features, and predictable performance, at the cost of boilerplate, manual mapping, and injection risk if careless. Pragmatic pattern: ORM for OLTP CRUD, raw or lightweight mapping (Dapper-style) for hot paths and reporting.

**AA18** — The **Bulkhead pattern** partitions resources into isolated compartments (like a ship's hull) so a failure or surge in one doesn't sink the rest. In microservices, isolate resources per dependency. Example: a service calls Payments (critical) and Recommendations (nice-to-have) — give each its own thread pool/connection pool with bounded queues and timeouts (Hystrix-style; in .NET, Polly's Bulkhead policy or separate HttpClient pools). If the Recommendations pool saturates, Payments is untouched. Deployment-level bulkheads: run batch/analytics workloads on separate node groups with their own resource quotas so they can't starve latency-critical API pods; separate connection pools per downstream; per-priority queues.

**AA19** — **OT** transforms each operation against concurrent operations so all replicas converge; most designs require a central, ordered server (Google Docs uses OT). Correctness proofs are notoriously hard; metadata overhead is low; latency is good with server relay; offline support is weak because ordering is server-mediated. **CRDTs** are data structures whose concurrent updates merge commutatively and deterministically without coordination (sequence CRDTs like RGA/LSEQ; libraries: Yjs, Automerge). No central authority needed; offline-first and peer-to-peer sync are natural; consistency is eventual (replicas converge, no mid-flight strong ordering); costs are metadata/memory overhead and complex internals — though modern libraries hide much of it. **For offline editing, choose CRDTs**: edits proceed locally without coordination and merge deterministically when connectivity returns — which is precisely what OT's server-mediated model cannot offer.

**AA20** — Challenges of distributed tracing in polyglot ecosystems:
- **Context propagation**: every hop must forward trace context. **W3C Trace Context** (`traceparent`: version-traceid-parentid-flags, plus `tracestate`) is the standard; **B3** (`X-B3-TraceId` etc.) is the legacy Netflix standard. Polyglot ecosystems need consistent propagators (support both during migration) and instrumentation across languages — OpenTelemetry SDKs plus auto-instrumentation (Java agents, eBPF) are the practical answer.
- **Sampling**: **head-based** decides at the root and propagates the decision — cheap but may discard interesting traces. **Tail-based** buffers whole traces at a collector and decides at the end (keep errors, p99 latency) — better signal, higher cost. Combine probabilistic head sampling with tail-based error/latency rules.
- **Storage/query**: **Jaeger** (Cassandra/Elasticsearch backends, rich query by service/operation/tags) vs. **Grafana Tempo** (object-store backed, cheap, trace-by-ID lookups, paired with metrics/logs for service discovery).
- **Async messaging**: a queue breaks the synchronous span tree. Ensure continuity through Kafka by injecting `traceparent` into **Kafka message headers** on produce (OTel Kafka instrumentation), extracting it on consume, creating a consumer span **linked** to the producer span (FollowsFrom/child-of), then propagating downstream; propagate the sampling decision in headers; handle batching by giving each message its own context.

# On-Premise Infrastructure Architecture

**OP1** — **Type 1 (bare-metal)**: the hypervisor runs directly on hardware — better performance and security; data-center standard. Examples: VMware ESXi, Microsoft Hyper-V, KVM/Proxmox VE, Xen/XCP-ng. **Type 2 (hosted)**: runs atop a host OS. Examples: VMware Workstation/Fusion, Oracle VirtualBox, Parallels.

**OP2** — A **SAN** provides block storage over a dedicated network: it presents LUNs and the host builds its own filesystem; protocols: Fibre Channel, FCoE, iSCSI. Use for databases, clustered hypervisors (shared VM disks), and high-IOPS workloads. A **NAS** provides file-level storage over IP: the server-side filesystem is shared as files; protocols: NFS, SMB/CIFS. Use for file shares, home directories, media, backups, general-purpose storage. SAN = low latency, deterministic (FC), block semantics; NAS = easier management, file locking/permissions, Ethernet-based.

**OP3** — **3-tier (core/distribution/access)**: hosts connect to access switches, which uplink to distribution (policy/routing), which uplink to a high-speed core; classic campus design using STP, which blocks redundant links. Problems: blocked links waste capacity, bandwidth bottlenecks at distribution/core, east-west (server-to-server) traffic hairpins up the tree, and latency varies by path. **Leaf-spine**: every leaf connects to every spine in a full mesh with ECMP on all links — any-to-any latency is predictable (same hop count), scaling means adding spines/leaves, and there's no STP because it's an L3 fabric (often EVPN-VXLAN overlays). It solves variable latency, chokepoints, and non-scalable east-west bandwidth — the dominant traffic pattern in modern data centers.

**OP4** — **Nodes**: 3+ (odd count) for reliable quorum; a 2-node cluster needs a QDevice. **Corosync** handles membership/heartbeats (dedicated, ideally redundant NICs). **Fencing**: Proxmox uses watchdog-based self-fencing — a node that loses quorum panics itself via watchdog (~60 s); optionally add external fencing (fence_iLO/PDU) for faster, deterministic fencing. **Shared storage**: **Ceph RBD** is best — replicated 3× across nodes, live migration works, no SPOF; **iSCSI** shared LUN requires a cluster-aware filesystem or VM-on-LUN with locking, and the LUN is a SPOF; **NFS** is simple but the NFS server is a SPOF — not truly HA. **Node failure**: corosync detects it → the HA manager waits for the node to be fenced (watchdog reboot) → recovers HA-flagged VMs on remaining nodes. If the cluster loses quorum, HA operations stop entirely to avoid split-brain — which is why odd node count and shared storage matter.

**OP5** — **VLAN trunking** carries multiple VLANs over one link. **802.1Q** inserts a 4-byte tag containing a 12-bit VLAN ID (4094 usable; 0 and 4095 reserved) into the Ethernet frame; untagged frames belong to the native VLAN. Server with one NIC on 3 VLANs: configure the switch port as a trunk (allowed VLANs 10, 20, 30). On Linux: `modprobe 8021q`, then create subinterfaces — `ip link add link eth0 name eth0.10 type vlan id 10` (repeat for .20/.30) — or declare them in netplan/systemd-networkd; optionally attach each VLAN subinterface to a bridge for VMs.

**OP6** — **RAID 1**: mirror, 2 drives, 50% capacity, tolerates 1 failure. **RAID 5**: striping + single parity, 3+ drives, tolerates 1, capacity N−1; risks: write hole and URE during rebuild on large drives. **RAID 6**: dual parity, tolerates 2, capacity N−2, slower parity writes. **RAID 10**: striped mirrors, 50% capacity, tolerates 1 drive per mirror pair (up to N/2 if lucky), best random I/O and rebuild speed. **RAID Z2**: ZFS dual parity (RAID 6 equivalent) with transactional writes (no write hole), checksums, and self-healing via scrub. For 6 drives on a database server: **RAID 10** — three mirrored pairs striped: ~50% capacity, no parity penalty on writes, fast rebuilds, tolerates one drive per pair. Databases are random-I/O heavy and parity schemes hurt write performance. Choose RAID Z2 instead if capacity matters more and you're on ZFS (with recordsize/SLOG tuning for the DB).

**OP7** — Design:
- **Internal**: AD-integrated DNS on the DCs hosting the internal zone (secure dynamic updates, AD replication).
- **External**: authoritative DNS for the public zone — hosted, or a hidden primary in the DMZ with secondaries; **DNSSEC-signed** (KSK/ZSK, DS at the registrar, scheduled key rollovers, signing on the primary).
- **Split-horizon**: same zone name with different answers — internal zone holds private IPs, external holds public; or use distinct internal/external zone names.
- **Recursive resolvers**: clients point to DC resolvers via DHCP; DCs forward external queries to a resolver pair (Unbound/Infoblox) or root; **conditional forwarders** for partner/trusted domains.
- **DMZ**: separate resolvers that resolve external names plus a minimal set of DMZ records; DMZ must **not** query internal DNS — no conditional forwarding from DMZ inward.
- **Laptop office ↔ VPN**: in office, DHCP hands out AD DNS. On VPN, the client pushes VPN DNS servers + search domain; Windows **NRPT** rules route internal-domain queries through VPN DNS (split DNS, prevents leaks to public resolvers); VPN resolvers conditionally forward internal names to DCs and resolve external normally; flush the DNS cache on transition; AD-joined machines must always find DCs via SRV records, so VPN DNS must answer them.

**OP8** — Chain of trust: **root CA** (self-signed, offline, key in HSM/encrypted media, signs only subordinate CAs and CRLs) → **subordinate/issuing CA** (online, signs end-entity certs) → **end-entity certificates** (servers, users, devices). Validation walks the chain to a trusted root and checks revocation. **CRL**: signed periodic revocation list — simple but stale up to its cache lifetime. **OCSP**: real-time per-cert status, requires responder availability; **OCSP stapling** embeds the response in the TLS handshake. In AD CS, **certificate templates** define type/EKU/validity/subject policy (web server, user, computer, code signing); **auto-enrollment** via GPO (+ DCOM/CEP for non-domain enrollment) issues and renews certificates for domain-joined machines. Consequences: a **compromised subordinate** is recoverable — revoke it, publish the CRL, reissue the certs it issued; root trust survives. A **compromised root** is catastrophic — the trust anchor can't revoke itself; you must re-trust out-of-band (update GPO/enterprise trust stores) and reissue everything. That's why the root stays offline with a strict key ceremony.

**OP9** — **MPLS**: carrier-grade, SLA-backed, predictable latency/jitter, any-to-any routing; expensive per Mbps, carrier-managed, private (though not encrypted by default). **IPsec VPN over internet**: cheapest, ubiquitous, strong crypto; variable latency/jitter, subject to internet outages, no QoS guarantees. **SD-WAN**: overlays multiple links (broadband + MPLS/LTE), app-aware path selection (steers VoIP to the best path), central policy management, built-in encryption, cost-effective; adds appliance/license complexity. **WireGuard mesh**: modern, fast crypto, tiny codebase, cheap; but DIY — no SLA, app-awareness, or QoS, and key management at scale needs tooling (Tailscale/Netmaker). **Recommendation for 50 users/site with VoIP**: SD-WAN with at least one reliable link per site (MPLS or dedicated fiber) plus broadband — SD-WAN steers VoIP per application policy, provides central management, and the MPLS link preserves the SLA. Pure IPsec is too jittery for VoIP; pure MPLS is too expensive at this scale.

**OP10** — **iDRAC** (Dell), **iLO** (HPE), **IPMI** (generic BMC standard) are out-of-band management controllers independent of the OS: remote KVM console, power control, virtual media, sensors, logs. They're critical because they work when the OS is down, the network stack is misconfigured, or the kernel is hung — firmware updates, power cycling, and OS reinstalls via mounted ISO. If exposed to the internet, they're prime attack surface: default/weak credentials, historical RCEs, IPMI cipher-0 anonymous authentication, brute forcing, and malicious virtual media → full server takeover, firmware implant, and a pivot into the LAN. They must live on an isolated management VLAN, reachable only via VPN/jump host, with strong authentication, patched firmware, and weak IPMI ciphers disabled.

**OP11** — **LVM**: block-device volume manager (PV→VG→LV) on top of disks/RAID — flexible resizing, striping/mirroring; snapshots are copy-on-write of the block device, space-limited, living in the same VG. **LVM-Thin**: thin-provisioned pool — volumes allocate on demand, snapshots are cheap and numerous, supports overprovisioning (risk: pool exhaustion), discard/TRIM support. **ZFS**: integrated filesystem + volume manager + RAID (pools, datasets/zvols) — copy-on-write everything, checksums with self-healing, compression, snapshots are transactional and near-free, clones, and send/recv replication. Use **LVM** for simple flexible block on hardware RAID; **LVM-Thin** for overprovisioned VM disk images (Proxmox); **ZFS** when integrity, snapshots, replication (Proxmox `pvesr`), and compression matter.

**OP12** — To survive a complete site failure with 3 nodes + Ceph:
- **Stretch cluster**: 2 sites + tiebreaker. Ceph stretch mode needs odd monitor consensus: 2 monitors at site A, 2 at site B, 1 **tiebreaker** at a third site (or cloud). CRUSH rules use **site as the failure domain** with replica size 4 (2 per site) plus the tiebreaker. Latency between sites must be low — Ceph stretch-mode guidance is roughly ≤10 ms RTT (single-digit preferred) — because replication is synchronous; corosync also needs low latency.
- **Async DR alternative**: keep the 3-node cluster at site A, build a separate cluster at the DR site, and replicate via **RBD mirroring** (async) or Proxmox ZFS replication (`pvesr`), with per-site HA and DNS/VIP redirection on failover. RPO > 0, but no strict latency requirement.
- **Why 2-site Ceph without a tiebreaker is bad**: quorum requires a monitor majority. With even monitor counts, a site failure leaves a minority (cluster halts — safe but no HA) or, worse, a network partition gives each site 2 monitors → **split-brain**, divergent placement groups, potential data corruption. The tiebreaker provides a clean majority decision.

**OP13** — **DHCP** automatically assigns IP configuration. **DORA**: **D**iscover (client broadcasts, UDP 68→67) → **O**ffer (server offers IP + options) → **R**equest (client broadcasts its request for the offered IP) → **A**cknowledge (server confirms lease duration + options: router, DNS, lease time). Renewal: T1 at 50% of the lease (unicast renew), T2 at 87.5% (broadcast rebind), then expiry. If no server is reachable and the lease expires, a Windows client self-assigns an **APIPA** address (169.254.0.0/16) and keeps periodically retrying — connectivity is limited to the local segment (no gateway/DNS), effectively broken networking visible as 169.254.x addresses.

**OP14** — An **unmanaged switch** is plug-and-play: it forwards frames with no configuration, no visibility, and no loop protection beyond basics. A **managed switch** provides VLANs (802.1Q), STP/RSTP with loop guards, LACP, SNMP/telemetry, port security, ACLs, QoS, DHCP snooping, dynamic ARP inspection, 802.1X, IGMP snooping, port mirroring (for IDS/troubleshooting), stacking, and remote management (SSH/SNMP). Enterprises need segmentation, monitoring, security features, redundancy, and centralized management — none of which unmanaged switches offer.

**OP15** — **NTP** synchronizes clocks over a stratum hierarchy from authoritative sources (GPS/radio/atomic clocks) down to clients (chrony/ntpd). Accurate time is critical on-prem because: Kerberos/AD tolerates only ~5 minutes of skew (beyond that, logons fail), TLS certificate validity windows break, cluster consistency and heartbeats (Ceph, corosync, etcd) depend on time, distributed locks/leases expire incorrectly, and log correlation for forensics becomes impossible. Clock drift consequences: authentication failures, "certificate not yet valid" TLS errors, false failure detection or split-brain, replication conflicts, out-of-order/duplicate events, and unusable audit trails.

**OP16** — A **physical server** runs an OS directly on hardware with full resource access. A **VM** runs a guest OS under a hypervisor on virtualized hardware — strong isolation, full OS per workload. A **container** shares the host kernel with namespace/cgroup isolation — lightweight and dense. Run on **bare metal** when you need: maximum IOPS/latency (NUMA-tuned databases), GPU or hardware passthrough beyond what virtualization handles well, real-time/latency-critical behavior, specialized hardware (HBA/SAS), extreme memory footprints, or when licensing/support constraints apply — though SR-IOV/VFIO mitigate many of these cases inside VMs.

**OP17** — A **UPS** (batteries or flywheel) bridges power gaps for seconds to minutes and conditions power (sags, transients, frequency events). A **generator** provides fuel-driven power for extended outages (hours to days) but takes 10–60 s to start and stabilize. The **ATS** senses utility loss, starts the generator, transfers the load when generator power is stable, and transfers back when utility returns. You need both: the UPS covers the transfer gap and power-quality events the generator can't react to; the generator covers durations the UPS can't. Typical chain: utility → ATS → generator, with UPS riding through on critical loads.

**OP18** — **Active-passive**: one node serves while a standby waits (idle or hot with replication); failover moves the service. **Active-active**: all nodes serve simultaneously — requires multi-master or shared-nothing partitioning, which vanilla PostgreSQL doesn't do. For a PostgreSQL pair: **Corosync** provides messaging/quorum (add a QDevice or third vote for 2 nodes), **Pacemaker** manages resources. Resources: PostgreSQL in streaming replication (primary + sync/async standby), a **Virtual IP** (`ocf:heartbeat:IPaddr2`) that moves with the primary, and **STONITH fencing** (fence_iLO/IPMI, or fence_scsi via SCSI-3 persistent reservations) — mandatory, because fencing the failed node before failover prevents split-brain double-primary and guarantees data consistency. Failover: node dies → corosync detects → Pacemaker fences it → starts PostgreSQL on the standby and moves the VIP; clients reconnect to the VIP. Modern alternative: **Patroni** (with etcd/Consul) managing PostgreSQL plus a VIP/TCP proxy — cleaner automated failover and leader election.

**OP19** —
- **3-2-1 rule**: 3 copies (production + 2 backups), 2 different media (disk + tape/cloud), 1 offsite (ideally offline/immutable).
- **RPO/RTO**: RPO = acceptable data loss (drives backup frequency/replication); RTO = acceptable downtime (drives restore method and DR infrastructure). Define per system.
- **Backup types**: full (simplest restore, slowest), incremental (fastest backup, chain-dependent restores), differential (grows until the next full, simpler chains). Common mix: weekly full + daily incrementals/differentials.
- **Deduplication**: target-side (Proxmox Backup Server, Veeam) slashes storage and enables long retention.
- **Media**: disk (fast restores, costly at scale), tape (cheap long-term, offline/immutable, slow random access), cloud (easy offsite, object lock; watch egress/restore costs).
- **Immutability for ransomware**: S3 Object Lock (compliance mode), verified/append-only PBS backups, air-gapped or offline tape — because attackers delete or encrypt anything reachable.
- **Test restores**: scheduled drills — file-level restores, full VM boots, application-consistency checks, measure actual RTO. Untested backups are unverified hope.
- **Backup vs DR**: backup is copies of data; DR is the capability to resume the service within the RTO — infrastructure, runbooks, alternate site, people, process. Backups feed DR, but DR is broader and may rely on replication/failover rather than restores.

**OP20** — **802.1X roles**: the **supplicant** is the client (wpa_supplicant, Windows native, macOS); the **authenticator** is the switch/AP — it enforces the gate and relays EAP; the **authentication server** is RADIUS (NPS, FreeRADIUS, Cisco ISE) validating credentials and policy. Flow: the port starts unauthorized (only EAPOL allowed) → EAP exchange relayed in RADIUS Access-Request/Challenge → Access-Accept opens the port. **EAP methods**: **EAP-TLS** — mutual certificate authentication (client + server certs), strongest, requires PKI and client cert deployment; **PEAP-MSCHAPv2** — the server cert creates a TLS tunnel protecting password authentication, easier rollout, but password-based (vulnerable to phishing/credential attacks). **Dynamic VLAN**: the RADIUS Access-Accept carries VLAN attributes (Tunnel-Type=VLAN, Tunnel-Medium-Type=802, Tunnel-Private-Group-ID=<VLAN>) and the switch assigns the port to that VLAN — enabling role-based access (staff/student/guest/quarantine). **Failed authentication**: the port stays unauthorized (no data) or is redirected to a restricted/guest/quarantine VLAN per policy, with re-authentication timers. **MAB**: for devices without supplicants (printers, IoT, cameras) — the switch detects no EAPOL, waits, then sends a RADIUS Access-Request with the MAC as identity (Service-Type=Call-Check); RADIUS checks a MAC whitelist → authorize with a VLAN, or reject → guest/quarantine VLAN. MAB is weak (MACs are spoofable), so use it only as a fallback after 802.1X attempts, layered with DHCP snooping, dynamic ARP inspection, and port security.
