# JavaScript / TypeScript

**JS1 — var/let/const & hoisting**
- `var`: function-scoped (or global), re-declarable, hoisted and initialized to `undefined`.
- `let`: block-scoped, reassignable but not re-declarable, hoisted but uninitialized (Temporal Dead Zone until the declaration line).
- `const`: block-scoped, must be initialized, binding can't be reassigned (object *contents* are still mutable).
- **Hoisting**: declarations are processed before code executes. `var` is usable early (as `undefined`); `let`/`const` are in the TDZ (ReferenceError); function *declarations* are fully hoisted (body included).

**JS2 — Event loop**
- Single-threaded: the **call stack** runs frames. When the stack empties, the event loop drains the **microtask queue** completely (promise callbacks, `queueMicrotask`, `MutationObserver`), then takes **one macrotask** (timers, I/O callbacks, UI events, rendering), then microtasks again.
- Consequence: `Promise.then` callbacks always run before the next `setTimeout` callback, even with `setTimeout(..., 0)`.

**JS3 — Closures**
- A closure is a function plus its retained lexical environment — it can read/write variables from the scope where it was defined.
- Practical: a counter factory `function counter(){ let n=0; return ()=>++n; }`, memoization, event handlers.
- **Classic bug**: `for (var i=0;i<3;i++) setTimeout(()=>console.log(i))` logs `3,3,3` — one shared `var` binding captured by all callbacks.
- **Fixes**: use `let` (fresh per-iteration binding), an IIFE `((j)=>setTimeout(()=>console.log(j)))(i)`, or `.bind(null, i)`.

**JS4 — Promises & async/await**
- A `Promise` is a state machine: pending → fulfilled/rejected, consumed via `.then/.catch/.finally`. `async/await` is syntax sugar: `await` pauses the async function (non-blocking for the event loop) and rejections become thrown errors, so `try/catch` works; without try/catch the returned promise rejects.
- `Promise.all`: resolves with an array of values; **rejects fast** on the first rejection (other results are lost).
- `Promise.allSettled`: always waits for all; returns `[{status:'fulfilled',value}|{status:'rejected',reason}]` — use when you want every outcome (e.g., batch operations).

**JS5 — interface vs type**
- `interface`: describes object shapes; can be `extends`/`implements`d; supports **declaration merging** (open). Best for public APIs and class contracts.
- `type`: alias for *any* type — unions, intersections, primitives, tuples, mapped/conditional types. Best for union models and utility types.
- **Discriminated union**: union of variants sharing a literal tag field (`kind: 'circle' | 'square'`); switching on the tag narrows the type and enables exhaustiveness checks (`never` in the default branch).

**JS6 — Prototypal inheritance**
- Every object has an internal `[[Prototype]]`; property lookup walks the prototype chain until found or `null`.
- `Object.create(proto)` creates a new object whose `[[Prototype]]` is `proto` (2nd arg = property descriptors); `Object.getPrototypeOf`/`Object.setPrototypeOf` inspect/change it.
- ES6 `class` is declarative sugar over the same mechanism: methods live on `class.prototype`, `extends` chains `Sub.prototype → Base.prototype`, `super()` calls the parent constructor. It's still prototypes underneath — just with enforced `new`-only construction.

**JS7 — `this` binding rules (priority order)**
1. **new binding** — `new Foo()`: `this` = newly created object.
2. **Explicit** — `call/apply/bind`: `this` = first argument.
3. **Implicit** — `obj.fn()`: `this` = the containing object (nearest dot).
4. **Default** — plain call: global object, or `undefined` in strict mode.
- Arrow functions ignore all four (lexical `this` from enclosing scope). `bind()` returns a **new bound function** with permanently fixed `this` (and prepended args); calling `call/apply/bind` on it again has **no effect** — it's already bound.

**JS8 — WeakRef / FinalizationRegistry / WeakMap**
- `WeakRef` holds a target without keeping it alive; `deref()` returns the object or `undefined` if GC'd. `FinalizationRegistry` runs a callback after an object is collected (timing is unreliable; use `unregister`/cleanup handles). Legitimate uses: caches, external-resource cleanup — discouraged for core logic because GC timing is nondeterministic.
- `WeakMap` keys must be objects because the GC must track key *identity by reference* to know when the entry is dead. Primitives are copied by value, so there's no reference to observe. WeakMap/WeakSet don't hold strong references to keys, so entries vanish when the key is collected — no memory leaks.

**JS9 — V8 optimization**
- Pipeline: parse → Ignition (bytecode interpreter) → TurboFan (optimizing compiler) using feedback from execution.
- **Hidden classes**: each object has a "shape" mapping property names to fixed offsets; adding properties causes transitions. **Inline caching**: call sites cache (shape → offset) pairs, degrading monomorphic → polymorphic → megamorphic. **Deopt**: when runtime reality breaks TurboFan's assumptions, optimized code bails out to the interpreter.
- Deopt-inducing patterns: adding/deleting properties after creation, changing element kinds (packed→holey, SMI→double→tagged), `arguments` object, `eval`/`with`, `Object.defineProperty`, polymorphic call sites, changing function return types, using objects as string-keyed dictionaries.

**JS10 — Tree-shaking**
- Build-time dead-code elimination of unused ES module exports (plus minifier cleanup).
- ES modules have a static, top-level, unchangeable import/export graph → bundlers can prove reachability. CommonJS `require()` is dynamic (computed strings, conditionals, runtime `exports` mutation) → the dependency graph can't be statically proven, so nothing can be safely removed. The `sideEffects` field in `package.json` tells bundlers which files are safe to drop.

**JS11 — null/undefined, ==/===, ??/?.**
- `undefined`: not assigned/missing; `null`: deliberate "no value".
- `null == undefined` → `true` (special-case loose equality); `null === undefined` → `false`.
- `??` returns the right side only when the left is `null`/`undefined` (unlike `||`, which also triggers on `0`, `''`, `false`). `?.` short-circuits property access/calls when the base is nullish, yielding `undefined`.

**JS12 — map/filter/reduce/flatMap**
- `map` transforms every element; `filter` keeps elements passing a predicate; `reduce` folds the array into one value: `reduce((acc, cur, idx, arr) => newAcc, initialValue)`.
- With an initial value the accumulator starts there (safe on empty arrays); without one, the first element is the seed (throws on empty).
- `flatMap` = `map` then `flat(1)` — ideal when each input produces 0..n outputs (e.g., splitting lines into words).

**JS13 — Template literals & tagged templates**
- Backtick strings with `${expr}` interpolation and native multiline support.
- A tagged template calls a function: ``tag`a ${x} b` `` → `tag(['a ',' b'], x)` (strings array + substitutions; `strings.raw` available).
- Example (HTML escaping):
```js
const esc = s => String(s).replace(/[&<>"]/g, c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;'}[c]));
const html = (strings, ...vals) => strings.reduce((o, s, i) => o + s + (i < vals.length ? esc(vals[i]) : ''), '');
html`<p>${userInput}</p>`; // safe interpolation
```
Same pattern parameterizes SQL safely (strings + bound values).

**JS14 — Destructuring**
- Object: `const {a, b: renamed, c = 5, ...rest} = obj;` (extract, rename, default, rest).
- Array: `const [first, , third, ...tail] = arr;` (holes skip elements).
- Works in parameters and nested patterns; the rest element must be last. Rest collects remaining own enumerable properties (object) or remaining elements (array).

**JS15 — for...in vs for...of**
- `for...in` iterates **enumerable string keys** (own *and inherited*) of an object.
- `for...of` iterates **iterables** (arrays, strings, Map/Set, generators) via `Symbol.iterator`.
- Avoid `for...in` on arrays: keys are string indices, inherited enumerable properties (e.g., `Array.prototype` additions) leak in, and it enumerates properties rather than elements. Use `for...of`, `forEach`, or index loops.

**JS16 — Generics, constraints, conditionals, infer**
- Generic: `function identity<T>(v: T): T { return v; }`
- Constraint: `function get<T, K extends keyof T>(obj: T, key: K): T[K]` — limits `T` and links key to value type.
- Conditional type: `type IsString<T> = T extends string ? true : false;` (basis of `Exclude`, `NonNullable`).
- `infer`: captures a type inside a conditional — `type Elem<T> = T extends (infer U)[] ? U : never;` and built-in `ReturnType<T> = T extends (...a:any)=>infer R ? R : never`.

**JS17 — Module systems**
- CommonJS: `require`/`module.exports` — synchronous, dynamic (runtime-resolved), Node's legacy default.
- ESM: `import`/`export` — statically analyzable, hoisted, async loading, top-level `await`, live bindings.
- Node resolution: `.mjs` is always ESM, `.cjs` always CJS, and `.js` follows the nearest `package.json` `"type"` field: `"module"` → ESM, absent/`"commonjs"` → CJS. ESM can import CJS (its `module.exports` becomes the default export).

**JS18 — Structural typing, excess checks, satisfies, variance**
- TypeScript compares by *shape*, not name: any object with compatible members is assignable.
- **Excess property checks** flag unknown properties only on *fresh object literals* assigned to a typed target; assigning via an intermediate variable bypasses them.
- `extends` (on classes/interfaces) declares inheritance; `satisfies` (TS 4.9) validates an expression against a type **without widening literal types** — `const c = { port: 8080 } satisfies Config` keeps `port`'s narrow type while checking compatibility.
- Variance (TS 4.7+): `in`/`out` annotations on type parameters enforce variance checking — `out` = covariant (output position), `in` = contravariant (input position) — catching unsound subtyping in interfaces.

**JS19 — Proxy & Reflect**
- `Proxy(target, handler)` intercepts fundamental operations via traps: `get`, `set`, `has`, `deleteProperty`, `apply`, `construct`, etc. `Reflect` exposes the default implementations — call `Reflect.get/set(...)` inside traps to forward correctly (preserving receiver, invariants).
- Example (reactive binding):
```js
function reactive(obj) {
  return new Proxy(obj, {
    get(t, k, r) { track(k); return Reflect.get(t, k, r); },
    set(t, k, v, r) { const ok = Reflect.set(t, k, v, r); trigger(k); return ok; }
  });
}
```
Also used for validation (throw in `set`), logging, and default-behavior delegation.

**JS20 — SharedArrayBuffer & Atomics**
- `SharedArrayBuffer` is raw memory shared between the main thread and Workers (requires cross-origin isolation: COOP/COEP headers). Workers receive the same buffer via `postMessage` (no copy) and coordinate through `Atomics`.
- `Atomics` provides atomic reads/writes and RMW ops (`add`, `exchange`, `compareExchange`, `and/or/xor`), plus futex-like `wait`/`notify` on an `Int32Array` view.
- Ordering: atomic ops are **sequentially consistent**; plain (non-atomic) access to shared memory is a data race (undefined behavior). `Atomics.wait` **blocks** the calling agent until `notify`/timeout — it throws on the browser main thread, so use `Atomics.waitAsync` there. `Atomics.notify` wakes waiting agents on the same location.

# Bash

**B1 — $@ vs $***
- Unquoted `$@` and `$*` are effectively the same (both subject to word splitting).
- `"$*"`: all positional parameters joined into **one string** using the first char of `IFS` (usually a space).
- `"$@"`: each parameter stays a **separate word**, even if it contains spaces — almost always what you want: `"$@"` when forwarding arguments.

**B2 — set -euo pipefail**
- `-e` (errexit): exit immediately on any command failure (with caveats inside `if`/`&&` conditions).
- `-u` (nounset): error on use of undefined variables — catches typos.
- `-o pipefail`: a pipeline's exit status is the rightmost *non-zero* status (default is only the last command's status), so `grep x file | wc` failing at `grep` no longer hides.

**B3 — $( ) vs backticks; $(( )) vs expr**
- `$(cmd)` nests cleanly (`$( $(cmd) )`) and is easier to escape; `` `cmd` `` is legacy, nesting requires escaping backticks.
- `$((expr))` is shell built-in integer arithmetic (no fork, no escaping of `*`); `expr` is an external binary, needs `\*` etc., and is slower — prefer `$(( ))` or `let`/arithmetic expansion.

**B4 — Process substitution**
- `<(cmd)` (and `>(cmd)`) runs the command and connects it via a filename-like fd (`/dev/fd/N`), letting programs that require file arguments read from a command.
- Example: `diff <(sort a.txt) <(sort b.txt)` — compares sorted views without temp files. Also `while read ... done < <(grep ...)` to keep the loop in the main shell.

**B5 — Safe iteration over filenames**
- Use null-delimited data: `find . -type f -print0 | while IFS= read -r -d '' f; do ...; done`, or `find ... -print0 | xargs -0 ...`, or plain globs: `for f in *.txt` (with `shopt -s nullglob`).
- `for f in $(ls)` is dangerous: output undergoes word splitting (spaces break names), glob expansion (filenames like `*` explode), newlines are lost, and parsing `ls` output is never reliable.

**B6 — Heredoc vs here-string**
- `cmd <<EOF ... EOF` feeds a multi-line block as stdin until the delimiter; `cmd <<<"string"` feeds a single string/word as stdin.
- `<<-EOF` strips **leading tabs only** (not spaces) from each line, allowing indented heredocs in scripts.

**B7 — Redirection order**
- `cmd > file 2>&1`: stdout → file; then stderr → *where stdout now points* (the file). Both land in the file.
- `cmd 2>&1 > file`: stderr → *current* stdout (the terminal/screen); then stdout → file. stderr shows on screen, stdout goes to the file.
- `cmd &> file` (bash): shorthand for `> file 2>&1` — both to the file. The difference is purely the **order** of redirections: `2>&1` duplicates whatever stdout is *at that moment*.

**B8 — Safe lock file**
```bash
#!/usr/bin/env bash
LOCK_DIR="/tmp/myapp.lock"

if ! mkdir "$LOCK_DIR" 2>/dev/null; then
  # recover stale lock if the recorded PID is dead
  if [[ -f "$LOCK_DIR/pid" ]] && ! kill -0 "$(cat "$LOCK_DIR/pid")" 2>/dev/null; then
    rm -rf "$LOCK_DIR"; mkdir "$LOCK_DIR" || { echo "lock failed" >&2; exit 1; }
  else
    echo "already running" >&2; exit 1
  fi
fi
echo $$ > "$LOCK_DIR/pid"
trap 'rm -rf "$LOCK_DIR"' EXIT INT TERM   # cleanup on normal exit and signals
```
- `mkdir` is preferred because it is a **single atomic syscall**: it either succeeds or fails — no TOCTOU race. The common `if [ -f lock ]; then touch lock; fi` has a window between test and create where two scripts both succeed. (For robustness, prefer `flock -n /tmp/myapp.lock`, which also handles SIGKILL via kernel-managed locks; SIGKILL can't be trapped, hence the PID-liveness stale-lock check.)

**B9 — Quoting**
- `'...'`: fully literal — `echo 'a $b'` → `a $b`.
- `"..."`: expands `$var`, `` ` `` , `\`, `$()` — `echo "a $b"` → `a <value of b>`.
- Unquoted: subject to word splitting + globbing — `var="a b"; echo $var` prints `a b` as two words; `echo *.txt` expands the glob.

**B10 — File tests, [ ] vs [[ ]]**
- `[ -e f ]` exists, `[ -d f ]` directory, `[ -f f ]` regular file, `[ -r f ]` readable, `[ -w f ]` writable, `[ -x f ]` executable, `[ -s f ]` non-empty, `[ -L f ]` symlink.
- `[ ]` is the POSIX test builtin: needs quoting, uses `-a/-o`, no `&&`/`||`/`<`. `[[ ]]` is a bash keyword: no word splitting/globbing inside, supports `&&`, `||`, `<`/`>`, and regex `=~`.

**B11 — Special parameters**
- `$?` — exit status of the last command (error handling: `cmd || exit $?`).
- `$$` — current shell PID (unique temp/log filenames).
- `$!` — PID of the most recent background job (`kill $!`, `wait $!`).
- `$#` — number of positional parameters (argument validation: `[ $# -lt 1 ] && exit 1`).

**B12 — Functions**
- `foo() { ...; }` and `function foo { ...; }` are equivalent in bash (`function` keyword is non-POSIX); call by name `foo arg1 arg2`.
- `return N` sets the **exit status** (0–255 only); to return *data*, write to stdout and capture: `result=$(foo)`, or use a global variable, or a nameref (`declare -n`).

**B13 — PATH, builtins**
- `PATH` is a colon-separated list of directories searched in order; the first match executes.
- Builtins (`cd`, `echo`, `read`) run inside the shell process (no fork, can change shell state); external commands are separate binaries from PATH.
- Check with `type -a cmd` (lists all matches and whether each is a builtin/function/file), `command -v cmd`, or `which -a cmd`.

**B14 — trap**
- `trap 'commands' SIGNAL` runs commands when the signal (or event) fires: `EXIT` (any shell exit), `ERR` (non-zero simple command status), `INT` (Ctrl-C), `TERM` (kill).
- Typical: `trap cleanup EXIT INT TERM` with an idempotent cleanup function.
- Ordering: bash runs traps **between commands**; if a trap is already running, further signals are queued and processed one at a time (the running handler finishes first). On `TERM` whose handler exits, the `EXIT` trap then runs. `SIGKILL` cannot be trapped.

**B15 — xargs vs command substitution**
- `$(cmd)` embeds output as arguments of a single command — limited by ARG_MAX and subject to word splitting. `xargs` reads stdin and **batches** arguments across multiple invocations automatically.
- `find ... -print0 | xargs -0 ...` uses NUL delimiters, making it safe for filenames with spaces, newlines, quotes.
- `xargs -P N` runs up to N invocations **concurrently** (e.g., `-P 8` for parallel compression); `-P 0` = unlimited.

**B16 — Arrays**
- Indexed: `a=(x y z)`, `${a[0]}`, append `a+=("w")`, length `${#a[@]}`, iterate `for v in "${a[@]}"`; order preserved.
- Associative: `declare -A h=([key]=val)`, `${h[key]}`, keys `${!h[@]}`, length `${#h[@]}`; arbitrary string keys, but **no guaranteed order**.
- Differences: indexed arrays are ordered integer-indexed lists; associative arrays are string-keyed maps (hash). Both need `"${arr[@]}"` quoting when iterating.

**B17 — Subshell vs group command**
- `( ... )` runs in a **forked subshell**: variable/`cd` changes don't affect the parent; exit code is that of the last command.
- `{ ...; }` runs in the **current shell**: changes persist; needs a space after `{` and a trailing `;`; same exit-code semantics.
- Piping into `while` (`cmd | while read ...`) runs the loop in a subshell, so counters/variables set inside are lost. Fixes: `while ... done < <(cmd)` (process substitution), a here-string, `mapfile`, or `shopt -s lastpipe` (with job control off).

**B18 — Signals & graceful shutdown**
- `SIGINT` (2, Ctrl-C), `SIGTERM` (15, polite terminate request), `SIGHUP` (1, terminal hangup), `SIGKILL` (9, **uncatchable**, immediate).
- Graceful shutdown: `trap 'cleanup' INT TERM EXIT`; cleanup should kill children (`kill $child_pids`), `wait` for them, remove temp files, then exit. `nohup`/`setsid` or trapping SIGHUP keeps scripts alive after terminal close.

**B19 — Parallel log processing**
```bash
#!/usr/bin/env bash
set -euo pipefail

process_chunk() {  # example: count ERROR lines per chunk
  grep -c ERROR "$1" > "${1}.out"
}
export -f process_chunk            # make the function visible to child bash

split -n l/8 -d access.log /tmp/chunk_        # 8 ordered chunks: chunk_00..07
printf '%s\n' /tmp/chunk_* |
  xargs -n1 -P8 bash -c 'process_chunk "$1"' _   # 8 parallel jobs

cat /tmp/chunk_*.out | awk '{s+=$1} END {print "total errors:", s}'
rm -f /tmp/chunk_* /tmp/chunk_*.out
```
- Trade-offs: chunk size (too many → process-spawn overhead; too few → no parallelism), CPU-bound vs I/O-bound (parallelism helps CPU-bound work; disk may bottleneck), memory, and ordering (numeric `-d` suffixes make reassembly deterministic).
- Error propagation: `xargs` exits 123 if any invocation fails; with `set -e` the script aborts — or write per-job status files and aggregate, or use GNU `parallel`'s `--joblog` for robust reporting.

**B20 — exec & coprocesses**
- `exec cmd` **replaces** the shell process image with `cmd` — no return, no shell afterward (used for wrapper scripts, and `exec` in `set -e` style entrypoints).
- FD manipulation: `exec 3> file` opens fd 3 for writing; `echo hi >&3` uses it; `exec 3< file` opens for reading (`read -u 3`); `exec 3>&-` closes fd 3; `exec 3>&1` duplicates stdout onto fd 3 (saving/restoring streams).
- Coprocess: `coproc CURL { curl -s http://host }` starts it in the background with pipes; read via `${CURL[0]}` (stdout) and write via `${CURL[1]}` (stdin). Classic alternative: create a FIFO, run the command with its I/O on the FIFO, then `exec 3<> fifo`. Use coprocesses for interactive/long-lived programs (ssh, database CLIs) to avoid repeated process startup and to have a persistent bidirectional channel.

# PowerShell

**PS1 — Write-Output vs Write-Host**
- `Write-Output` writes to the **success stream** — it flows through the pipeline, can be captured (`$x = f`), redirected, and formatted.
- `Write-Host` (PS5+) writes to the **information stream** aimed at the host console — it bypasses the pipeline and can't be assigned.
- Matters because "host-only" output pollutes nothing but also can't be consumed, while `Write-Output` inside a loop becomes function return data — mixing them causes unexpected pipeline results.

**PS2 — Pipeline; ForEach-Object vs foreach**
- The pipeline passes full objects one at a time, enabling streaming and uniform binding.
- `ForEach-Object` is a cmdlet: pipeline-aware, supports `-Begin/-Process/-End`, streaming, and `-Parallel` (v7); use inside pipelines.
- `foreach` is a language statement: faster on in-memory collections (no pipeline overhead), requires a collection variable, can't stream directly from a pipeline — use for local iteration over known arrays.

**PS3 — [PSCustomObject] vs [hashtable]**
- `[PSCustomObject]`: preserves property order, case-insensitive members, ideal for structured/JSON-like output and pipeline formatting.
- `[hashtable]`: fast key-value lookup, keys case-insensitive by default, **unordered** (use `[ordered]@{}` for order).
- Convert: hashtable → PSCustomObject by iterating keys (`$ht.GetEnumerator() | ForEach-Object { [PSCustomObject]@{ $_.Key = $_.Value } }` pattern or `Add-Member`); PSCustomObject → hashtable by iterating its properties into a new hashtable.

**PS4 — Error handling**
- **Terminating** errors stop execution (caught by `try/catch`); **non-terminating** errors are written to the error stream and execution continues.
- `-ErrorAction Stop` (per-command) or `$ErrorActionPreference = 'Stop'` (scope-based) promotes non-terminating errors to terminating so `try/catch` catches them; `-ErrorAction` overrides the preference locally; `-ErrorVariable` captures errors without stopping.
- `$ErrorActionPreference` values: Continue (default), Stop, SilentlyContinue, Inquire, Ignore; `catch` blocks see `$_` (the ErrorRecord).

**PS5 — Splatting**
- `$p = @{ Path = 'C:\x'; Recurse = $true; Filter = '*.log' }; Get-ChildItem @p` — the `@` (no `$`) passes hashtable entries as **named parameters**; arrays splat positionally.
- Passing `$p` (with `$`) instead sends the hashtable itself as a single value bound to one parameter — completely different behavior. Splatting improves readability, enables conditional parameter sets, and passes parameter dictionaries around.

**PS6 — Remoting**
- `Invoke-Command -ComputerName` runs a command/scriptblock remotely (one-shot or via sessions) and returns **deserialized** output; `Enter-PSSession` creates an interactive persistent session.
- Protocol: WS-Management (WSMan) via **WinRM** (HTTP 5985 / HTTPS 5986); PowerShell 6+ (Core) additionally supports **SSH** remoting (`-HostName`), making remoting cross-platform.

**PS7 — Pipeline unrolling gotcha**
- `$result += "one"` builds a 1-element array, but when the function emits it, the pipeline **unrolls** it — the caller receives the `String` `"one"`, so `$x.GetType().Name` is `String`.
- If the function returns 0 items, `$x` is `$null` (and `$x.GetType()` throws "you cannot call a method on a null-valued expression").
- Correct patterns: `Write-Output $result -NoEnumerate` or `return ,$result` to preserve array-ness; wrap at the call site `$x = @(Get-Items)`; and build collections efficiently with `[System.Collections.Generic.List[string]]` or stream with `Write-Output` per item (`+=` on arrays is O(n²)).

**PS8 — Scriptblocks, remoting, double-hop**
- A `[scriptblock]` is an anonymous, invokable code unit; a function is a *named* scriptblock (visible in the `function:` drive). Scriptblocks support `.Invoke()`, binding, `param()`.
- Remoting serializes the scriptblock as **text**: `Invoke-Command -ScriptBlock { param($a) ... } -ArgumentList $a` — closures/state don't survive; pass data via `-ArgumentList` or `$using:`.
- **Double-hop problem**: credentials authenticate to server A but aren't delegated to server B when A accesses a remote resource. Solutions: **CredSSP** (enables explicit credential delegation — security-sensitive), Kerberos constrained delegation, passing explicit credentials, or JEA/second-hop patterns.

**PS9 — @() and arrays**
- `@(...)` is the array-subexpression operator: it guarantees an array result (`@($x)`, `@(Get-Thing)`), even for single/empty output.
- Force a single result into an array: `@($x)`, `[array]$x`, or the unary comma `,$x`.
- Gotchas: `@($null)` yields a **1-element array containing $null** (count 1), while `@()` is empty; `$null.Count` is 0 (intrinsic members, PS3+); indexing out of range (`@()[0]`, `$null[0]`) returns `$null` rather than throwing.

**PS10 — Comparison operators**
- `-eq/-ne` equality, `-like` wildcard (`*`, `?`, `[]`), `-match` regex (sets `$Matches`), `-contains` (LHS **collection** contains RHS element), `-in` (reversed: LHS element in RHS collection: `5 -in (1..5)`).
- Default comparisons are **case-insensitive**; `-ceq/-clike/-cmatch/-ccontains` etc. are case-sensitive variants.
- Note: `-eq` against a collection acts as a filter — `(1,2,3) -eq 2` returns `2`.

**PS11 — Modules**
- A module packages commands. `.psm1` **script module**: functions defined in PowerShell. `.psd1` **manifest**: metadata — version, author, exported functions, dependencies (`RequiredModules`), PS edition. **Binary module**: compiled .NET assembly (C#) exposing cmdlets.
- `Import-Module` loads the module and exposes its exported commands (with `-Prefix`, `-RequiredVersion` options); modules are discovered via `$env:PSModulePath`; `Get-Module`/`Get-Command -Module` inspect what loaded.

**PS12 — String interpolation**
- `"..."` interpolates variables and subexpressions; `'...'` is fully literal.
- Expressions: `"$($obj.Name)"`, `"$(1 + 2)"` — `$(...)` inside double quotes; escape with backtick or `"$"`-style quoting.
- Here-strings: `@" ... "@` (interpolating) and `@' ... '@` (literal) for multi-line text; the closing `"@` must be at the start of its own line.

**PS13 — Get-Member & object exploration**
- `Get-Member` shows an object's type and members (`-Force` reveals hidden/base members, `-Static` statics).
- **Properties** include native .NET properties; **NoteProperties** are properties added at runtime (by `Select-Object`, `Add-Member`, or deserialization); **Methods** are real .NET methods.
- `Select-Object` **projects** — creates new objects with chosen/added properties (as NoteProperties); `Where-Object` **filters** the pipeline by a condition. Both are complementary: filter first, then select.

**PS14 — PowerShell classes**
- Introduced in v5: real .NET types with typed properties/methods, compiled at runtime, no pipeline integration (can't stream or use parameter binding).
- Limitations: single inheritance only, can implement existing .NET interfaces (no PS-defined interfaces, no explicit interface implementation), no generic classes, constructors are positional (no named-parameter invocation), `hidden` keyword for visibility.
- Use **classes** for data models, complex object logic, and performance (no pipeline overhead); use **functions** for pipeline tools with validation, `-WhatIf` support, and streaming.

**PS15 — CmdletBinding / advanced functions**
- `[CmdletBinding()]` promotes a function to an **advanced function**: common parameters (`-Verbose`, `-ErrorAction`, `-WhatIf`…), parameter attributes/validation, `$PSCmdlet` access, named parameter sets.
- `SupportsShouldProcess` adds `-WhatIf`/`-Confirm` (implement via `$PSCmdlet.ShouldProcess($target, $action)`); `DefaultParameterSetName` resolves ambiguity when multiple parameters belong to different sets; `ValueFromPipeline` binds pipeline objects to a parameter.
- `Begin` runs once (setup), `Process` per pipeline item (streaming — essential for large input), `End` once (cleanup/final output).

**PS16 — Providers**
- Providers expose data stores as PSDrives with a uniform noun-verb API, so `Get-ChildItem` works everywhere: `FileSystem` (files), `Registry` (`HKLM:`, `HKCU:`), `Certificate` (`Cert:\CurrentUser\My`), `Environment` (`Env:`), plus `Variable`/`Function`.
- Registry as a filesystem: `Set-Location HKLM:\SOFTWARE`; `Get-ChildItem` enumerates **keys** (containers); `Get-ItemProperty` reads **values**; `New-PSDrive` can mount additional roots.

**PS17 — Runspaces & parallelism**
- A **runspace** is an independent PowerShell execution environment within a process; a `[powershell]` object hosts a runspace and lets you invoke commands programmatically (`AddScript`/`Invoke`); a `[runspacepool]` manages a pool of runspaces for scaling.
- `ForEach-Object -Parallel` (v7) manages runspaces for you: `$using:` imports variables, `-ThrottleLimit` (default 5) caps concurrency.
- Manual: `[runspacefactory]::CreateRunspace()` → `[powershell]::Create($rs)` → `AddScript(...)` → `BeginInvoke/EndInvoke` → close/dispose. Thread safety: a runspace is **not** thread-safe — one per thread; share state only via thread-safe structures (e.g., `[System.Collections.Hashtable]::Synchronized(@{})`).

**PS18 — PSScriptAnalyzer**
- A static linter/analyzer that parses scripts into an AST and applies rules — enforcing standards like `PSAvoidUsingWriteHost`, `PSUseDeclaredVarsMoreThanAssignments`, `PSUseSingularNouns`.
- **Rules** are individual checks; **severity levels** are Error/Warning/Information (configurable); a settings file (`.PSScriptAnalyzerSettings.psd1`) controls `IncludeRules`/`ExcludeRules`.
- **Custom rules**: author rule modules (classes implementing `ICustomRule`) for org-specific checks. **Suppression**: `[System.Diagnostics.CodeAnalysis.SuppressMessageAttribute('PSScriptAnalyzer','RuleName')]` or ExcludeRules. **CI/CD**: run `Invoke-ScriptAnalyzer -Recurse` and fail the build on severity threshold; `-Fix` auto-remediates; integrates with VS Code, GitHub Actions, and PSGallery validation.

**PS19 — $using: vs -ArgumentList; serialization**
- `$using:` captures local variable **values** at invocation time for `Invoke-Command`, `Start-Job`, and `ForEach-Object -Parallel`; `-ArgumentList` passes values as positional parameters to the scriptblock's `param()`. Both deliver serialized copies — mutations don't flow back.
- Serialization limits: remoting/jobs serialize via CLIXML/XML with a **depth limit (default 2)**; complex objects arrive as `Deserialized.<Type>` PSCustomObjects — properties only, **no methods**, no live state; deeply nested data is truncated. Workarounds: pass primitives, serialize to JSON/strings yourself, or rehydrate objects remotely.

**PS20 — DSC**
- **Configurations**: declarative `configuration` keyword blocks that compile to MOF documents describing desired state. **Resources**: atomic units of state (built-in: File, Service, Registry; plus class-based/composite/community resources). **LCM** (Local Configuration Manager): the engine on each node that applies, monitors (and with `ApplyAndAutoCorrect`, reverts) configurations, and can pull from pull servers.
- Windows PowerShell 5.1 has full DSC (LCM v2, meta-configuration, HTTP/SMB pull servers). PowerShell 7+ does **not** include full DSC support (no LCM; DSC runs via Windows PowerShell compatibility with limitations).
- Modern landscape: **DSC v3** — the open-source, cross-platform redesign (new `dsc` CLI, resource adapters, any-language resources) — is the successor; for broader infrastructure-as-code, most teams use Terraform, Ansible, or Pulumi alongside/instead of DSC.
