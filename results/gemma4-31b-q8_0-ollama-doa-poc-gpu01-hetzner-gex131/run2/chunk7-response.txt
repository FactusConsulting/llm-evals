## Application Architecture

**AA1** — A **monolith** is a single unified unit where all business logic, data access, and UI are bundled into one codebase and deployment. **Microservices** decompose the application into small, independent services communicating over a network. 
*Problems introduced by microservices:* 1. **Network Latency/Reliability:** Inter-service calls introduce lag and partial failure modes. 2. **Data Consistency:** Managing transactions across multiple databases (distributed transactions) is complex. 3. **Operational Overhead:** Requires sophisticated CI/CD, monitoring, and service discovery for dozens of deployables.

**AA2** — **Synchronous** communication requires the caller to wait for a response before proceeding (e.g., REST/HTTP). **Asynchronous** communication allows the caller to send a message and continue processing without waiting for an immediate result (e.g., RabbitMQ/Kafka).

**AA3** — A **Reverse Proxy** (e.g., Nginx) primarily handles request routing, load balancing, and SSL termination. An **API Gateway** (e.g., Kong, AWS API Gateway) is a specialized reverse proxy that adds "API-aware" logic: rate limiting, authentication/authorization, request transformation, and orchestration. 
*Can it replace a reverse proxy?* Yes, but it may be overkill for simple static site routing or basic load balancing where the overhead of a gateway is unnecessary.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. Each local transaction updates the database and publishes an event. If a step fails, the Saga executes "compensating transactions" to undo the preceding steps.
*   **Choreography:** Services exchange events without a central coordinator. Best for simple workflows with few services.
*   **Orchestration:** A central "orchestrator" tells participants which local transactions to execute. Best for complex business logic with many steps.

**AA5** — **CQRS** separates the data models for reading (Query) and writing (Command). It is paired with **Event Sourcing**, which stores the state of an application as a sequence of immutable events rather than just the current state. 
*Problem solved:* Traditional CRUD overwrites data, losing history. This combination provides a perfect audit log, allows "time travel" (reconstructing state at any point), and optimizes read performance by creating specialized read-views (projections).

**AA6** — The **Circuit Breaker** prevents a service from repeatedly trying to call a failing downstream service, avoiding cascading failures.
*   **Closed:** Requests flow normally.
*   **Open:** Requests fail immediately without calling the downstream service.
*   **Half-Open:** A limited number of requests are allowed through to test if the service has recovered.
*   **Vs. Retry:** Retries are for transient glitches; Circuit Breakers are for systemic failures. Use both by wrapping a retry logic inside a circuit breaker to avoid "hammering" a dead service.

**AA7** — 
1. **Shared DB, Shared Schema:** Lowest cost, lowest security (relies on `WHERE tenant_id = X`), highest noisy-neighbor risk.
2. **Shared DB, Separate Schema:** Medium cost, better security (schema-level permissions), medium noisy-neighbor risk.
3. **Separate DB:** Highest cost, highest security (physical isolation), lowest noisy-neighbor risk.

**AA8** — **Strong Consistency** ensures all nodes see the same data at the same time. **Eventual Consistency** guarantees that if no new updates are made, all nodes will eventually converge.
*Architecture for Inventory:* Use **Strong Consistency**. I would use a Relational Database (PostgreSQL) or a Distributed SQL DB (CockroachDB) utilizing the **Raft or Paxos consensus algorithms**. I would implement **pessimistic locking** or **atomic increments** at the database level to ensure a stock count never drops below zero.

**AA9** — A **sidecar proxy** is a helper container deployed alongside every service instance. In Istio, **Envoy** is the sidecar that intercepts all network traffic.
*   **Data Plane:** The collection of Envoy proxies handling actual traffic.
*   **Control Plane:** (Istiod) Manages and configures the proxies.
*   **mTLS:** Sidecar mTLS provides transparent encryption and identity verification between services without requiring the application code to manage certificates or TLS handshakes.

**AA10** — The **Strangler Fig pattern** involves incrementally replacing legacy functionality with new services until the old system is gone.
*Strategy:* 1. Place an API Gateway/Proxy in front of the .NET Framework monolith. 2. Identify a single bounded context (e.g., "Payments"). 3. Build the "Payments" service in .NET 8. 4. Update the Gateway to route `/payments` traffic to the new service while everything else goes to the monolith. 5. Repeat until the monolith is empty.

**AA11** — A methodology for building scalable, maintainable cloud-native apps. 
1. **Codebase:** One codebase tracked in revision control, many deploys.
2. **Dependencies:** Explicitly declare and isolate dependencies.
3. **Config:** Store configuration in the environment.
4. **Backing Services:** Treat attached resources (DBs, queues) as attached resources.
5. **Processes:** Execute the app as one or more stateless processes.
6. **Port Binding:** Export services via port binding.
*Why:* These ensure portability, scalability, and consistency across Dev/Staging/Prod.

**AA12** — 
*   **Coupling:** Event-driven (Loose) vs Request-driven (Tight).
*   **Scalability:** Event-driven (High, async buffers) vs Request-driven (Limited by synchronous chain).
*   **Debugging:** Event-driven (Hard, requires tracing) vs Request-driven (Easier, linear stack trace).
*   **Ordering:** Event-driven (Guaranteed per partition in Kafka) vs Request-driven (Sequential by nature).
*   **Failure:** Event-driven (DLQs, retries) vs Request-driven (Immediate error/timeout).
*   **Choice:** Use Request-driven for immediate feedback (UI actions); Event-driven for background processing and cross-service synchronization.

**AA13** — A **Load Balancer** distributes incoming network traffic across multiple servers.
*   **Layer 4 (Transport):** Routes based on IP and TCP/UDP ports. Fast, but "blind" to content.
*   **Layer 7 (Application):** Routes based on HTTP headers, cookies, or URL paths.
*   **L7 Use Case:** Routing `/api/v1` to one cluster and `/api/v2` to another.

**AA14** — A **Message Queue** is a component that stores messages until they are processed.
*   **Queue (RabbitMQ):** Messages are deleted once consumed. Best for "Task Distribution" (one worker handles one task).
*   **Log-based (Kafka):** Messages are persisted in an append-only log. Multiple consumers can read the same data at their own pace. Best for "Event Streaming" and audit trails.

**AA15** — A **Container** shares the host OS kernel and isolates the application process. A **VM** includes a full guest OS and runs on a hypervisor. Containers are popular because they are lightweight, start in seconds, and ensure "it works on my machine" consistency.

**AA16** — **Stateless** services do not store client data between requests (e.g., a Currency Converter API). **Stateful** services remember client state (e.g., a Database or a WebSocket chat server). Stateless services scale horizontally easily because any instance can handle any request without needing session synchronization.

**AA17** — An **ORM** maps database tables to objects in a programming language. Examples: **Entity Framework** (C#), **Hibernate** (Java).
*Trade-offs:* ORMs increase developer productivity and prevent SQL injection; however, they can produce inefficient queries and hide the underlying performance costs of database interactions.

**AA18** — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function.
*Implementation:* 1. **Thread Pools:** Assign a dedicated thread pool to the "Payment" service so that if it hangs, it doesn't exhaust all threads and crash the "Catalog" service. 2. **Deployment Groups:** Run critical services on separate hardware/clusters from non-critical ones.

**AA19** — 
*   **OT (Operational Transformation):** Requires a central server to transform operations to maintain consistency. High complexity, low latency for users, but difficult to implement offline.
*   **CRDTs (Conflict-free Replicated Data Types):** Mathematically designed so that concurrent updates can be merged without conflicts. High offline support, lower server complexity, but higher memory overhead.
*   **Choice:** **CRDTs** for offline editing, as they allow local mutations that merge seamlessly upon reconnection without a central coordinator.

**AA20** — Challenges include maintaining a "Trace ID" across different languages and protocols.
*   **Propagation:** Use **W3C Trace Context** or **B3** headers to pass the Trace ID from service to service.
*   **Sampling:** **Head-based** (decide to trace at the start) vs **Tail-based** (decide to keep the trace after it finishes, e.g., only keep traces that resulted in an error).
*   **Storage:** **Jaeger** or **Grafana Tempo** index and visualize these spans.
*   **Kafka:** Inject the trace context into the **Kafka Record Headers**. The consumer extracts the header to continue the trace.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal)** runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V). **Type 2 (Hosted)** runs as an app on a host OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network)** provides block-level access (looks like a local disk). Uses **iSCSI or Fibre Channel**. Use for databases. **NAS (Network Attached Storage)** provides file-level access (looks like a network share). Uses **NFS or SMB**. Use for shared documents/backups.

**OP3** — **3-Tier** (Core $\rightarrow$ Distribution $\rightarrow$ Access) is designed for North-South traffic (client to server). **Leaf-Spine** (every Leaf connects to every Spine) is designed for East-West traffic (server to server). It solves the bottleneck and latency issues caused by Spanning Tree Protocol (STP) in 3-tier designs.

**OP4** — 
*   **Architecture:** 3+ nodes to maintain **quorum** (majority vote).
*   **Fencing:** Use **STONITH** (Shoot The Other Node In The Head) via IPMI/iDRAC to ensure a failed node is truly dead before migrating VMs.
*   **Storage:** **Ceph** (distributed) for high availability or **iSCSI** (centralized) for simplicity.
*   **Failure:** If a node fails, the remaining nodes detect the loss of heartbeat, fence the dead node, and restart its VMs on healthy nodes.

**OP5** — **VLAN Trunking** allows a single physical link to carry traffic for multiple VLANs. **802.1Q** is the standard that adds a "tag" to the Ethernet frame to identify the VLAN.
*Linux Config:* Create tagged sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — 
*   **RAID 1:** Mirroring (High safety, low capacity).
*   **RAID 5:** Parity (1 disk fail, good balance).
*   **RAID 6:** Dual Parity (2 disk fail, safer than 5).
*   **RAID 10:** Mirror of stripes (High performance, high safety, 50% capacity).
*   **RAID Z2:** ZFS dual parity (similar to RAID 6 but avoids "write hole").
*   **Choice for DB (6 drives):** **RAID 10**. Databases require high IOPS (random writes), and RAID 10 provides the best performance and fast recovery.

**OP7** — 
*   **Internal:** AD-integrated DNS for internal name resolution.
*   **DMZ:** Separate authoritative servers for public records.
*   **Split-Horizon:** The DNS server returns different IPs for `app.company.com` depending on whether the request is internal (private IP) or external (public IP).
*   **DNSSEC:** Digitally signs external zones to prevent cache poisoning.
*   **VPN:** DHCP pushes the internal DNS server IP to the laptop via the VPN tunnel.

**OP8** — **Root CA** (Self-signed, kept offline) $\rightarrow$ **Subordinate CA** (Issued by Root, online) $\rightarrow$ **End-Entity Cert** (Issued to server/user).
*   **CRL:** A list of revoked certs. **OCSP:** A real-time protocol to check cert status.
*   **Compromise:** A compromised Sub CA requires revoking that Sub CA's cert via the Root. A compromised Root CA is catastrophic; the entire trust chain is void, and every single certificate must be re-issued.

**OP9** — 
*   **MPLS:** High cost, guaranteed QoS, high reliability.
*   **IPsec VPN:** Low cost, relies on public internet, variable latency.
*   **SD-WAN:** Medium cost, manages multiple links (MPLS + Internet) dynamically.
*   **WireGuard Mesh:** Low cost, high performance, complex to manage at scale.
*   **Recommendation:** **SD-WAN**. It allows prioritizing VoIP traffic over the best available link (MPLS or Internet) while reducing costs.

**OP10** — **iDRAC/iLO/IPMI** are Baseboard Management Controllers (BMCs) that allow hardware management regardless of the OS state. Critical for remote power cycling and BIOS access. If exposed to the internet, an attacker can gain full console access, reinstall the OS, or brick the hardware.

**OP11** — 
*   **LVM:** Logical Volume Manager; allows resizing partitions. Snapshots are "thick" and can impact performance.
*   **LVM-Thin:** Allows over-provisioning (allocate more than exists). Snapshots are more efficient.
*   **ZFS:** Combined FS and Volume Manager. Uses Copy-on-Write (CoW). Snapshots are near-instant and extremely efficient.

**OP12** — 
*   **Design:** 3 sites (Site A, Site B, and a Witness site). 
*   **Ceph:** Use **CRUSH rules** to ensure replicas are distributed across sites. 
*   **Latency:** Must be very low (usually $<10\text{ms}$) to avoid write timeouts.
*   **Split-Brain:** If Site A and B lose connectivity, both might try to become primary. A **tiebreaker (witness)** in a 3rd site ensures only one side maintains quorum.

**OP13** — **DHCP** assigns IP addresses. **DORA:** Discover (Client), Offer (Server), Request (Client), Acknowledge (Server). If the server is unavailable and the lease expires, Windows clients assign themselves an **APIPA** address (`169.254.x.x`).

**OP14** — **Unmanaged** is a basic plug-and-play switch. **Managed** switches allow **VLANs** (segmentation), **STP** (preventing loops), **Port Mirroring** (for IDS/monitoring), and **SNMP** (remote health monitoring).

**OP15** — **NTP** synchronizes clocks across the network. Critical for: 1. **Log Correlation** (debugging across servers). 2. **Authentication** (Kerberos fails if clocks drift $>5$ mins). 3. **Database Replication** (ordering of transactions).

**OP16** — **Physical:** Hardware. **VM:** Hardware abstraction via hypervisor. **Container:** OS abstraction via kernel namespaces. Run on **bare metal** for: High-performance databases, GPU-intensive AI workloads, or when running the hypervisor itself.

**OP17** — **UPS** provides immediate battery power for minutes. **Generator** provides long-term power via fuel. **ATS** (Automatic Transfer Switch) detects power loss and switches the load from the utility grid to the generator. You need both because generators take seconds/minutes to start; the UPS bridges that gap.

**OP18** — **Active-Passive:** One node works, one waits. **Active-Active:** Both nodes handle traffic.
*Postgres HA:* Use **Pacemaker/Corosync** for cluster membership. Use a **Virtual IP (VIP)** that floats to the active node. Use **STONITH** to kill the passive node if it becomes unresponsive to prevent "split-brain" (two nodes writing to the same data).

**OP19** — 
*   **3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
*   **RPO (Recovery Point Objective):** Max acceptable data loss (e.g., 15 mins).
*   **RTO (Recovery Time Objective):** Max acceptable downtime (e.g., 4 hours).
*   **Immutable Backups:** WORM (Write Once Read Many) storage to prevent ransomware from encrypting backups.
*   **Backup vs DR:** Backup is the *copy of data*; DR is the *entire plan/infrastructure* to restore business operations.

**OP20** — **802.1X** provides port-level security.
*   **Roles:** **Supplicant** (Client device), **Authenticator** (Switch), **Auth Server** (RADIUS).
*   **Methods:** **EAP-TLS** (Certificate-based, most secure) vs **PEAP** (Username/Password).
*   **Failure:** Device is placed in a "Guest VLAN" or the port is shut down.
*   **MAB:** For devices like printers that can't run a supplicant, the switch sends the device's **MAC address** to the RADIUS server for approval.
