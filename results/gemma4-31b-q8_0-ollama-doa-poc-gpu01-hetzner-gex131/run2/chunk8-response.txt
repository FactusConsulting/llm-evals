## Cloud Infrastructure Architecture

**CL1 — Easy:** 
*   **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and everything above it. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing the underlying OS or runtime. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Fully managed software delivered via a browser/API. *Example: Microsoft 365.*

**CL2 — Easy:** 
The Shared Responsibility Model dictates that the provider is responsible for the security **of** the cloud (hardware, global infrastructure), and the customer is responsible for security **in** the cloud (data, config).
*   **IaaS VMs:** Provider handles physical host/hypervisor; You handle OS patching, firewall, and apps.
*   **Managed Kubernetes (EKS/GKE):** Provider handles the Control Plane; You handle worker node patching (usually), pod security, and network policies.
*   **SaaS (M365):** Provider handles almost everything; You handle identity/access management and data governance.

**CL3 — Medium:** 
*   **VPC:** An isolated virtual network in the cloud.
*   **Subnet:** A range of IP addresses in the VPC used to group resources (e.g., Public vs. Private).
*   **Security Group (SG):** An instance-level virtual firewall. **Stateful:** If an inbound request is allowed, the outbound response is automatically allowed.
*   **NACL:** A subnet-level firewall. **Stateless:** You must explicitly define both inbound and outbound rules.
*   **Layering:** VPC $\rightarrow$ Subnet (NACL) $\rightarrow$ Instance (SG).

**CL4 — Medium:** 
*   **Landing Zone:** A pre-configured, multi-account environment based on best practices (security, logging, networking).
*   **Organizational Units (OUs):** Logical groupings of accounts (e.g., Prod, Dev, Security) to apply policies.
*   **Guardrails:** Service Control Policies (SCPs) that set the maximum available permissions for an account.
*   **Shared Networking:** Using a Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize egress/ingress and connect VPCs.
*   **Centralized Logging:** Aggregating all logs (CloudTrail, Flow Logs) into a dedicated security account's S3 bucket.
*   **Single-account problems:** Blast radius (one compromise affects all), API rate limits, and billing complexity.

**CL5 — Medium:** 
IaC is the management of infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu:** HCL-based, cloud-agnostic. Best for multi-cloud or general-purpose infra.
*   **Pulumi:** Uses general-purpose languages (TS, Python). Best for developers who want loops/logic in infra.
*   **CloudFormation/Bicep:** Cloud-specific (AWS/Azure). Best for deep integration and "day zero" support of native features.
*   **Crossplane:** K8s-native. Best for managing cloud resources as K8s objects (Control Plane approach).

**CL6 — Medium:** 
*   **HPA:** Scales pods based on CPU/RAM or custom metrics.
*   **VPA:** Adjusts the CPU/RAM requests/limits of existing pods.
*   **Cluster Autoscaler:** Adds/removes physical nodes from the cluster when pods cannot be scheduled.
*   **KEDA:** Event-driven autoscaling. Use KEDA over HPA when scaling is based on external events (e.g., number of messages in a Kafka topic or RabbitMQ queue) rather than resource utilization.

**CL7 — Hard:** 
*   **Strategy:** Deploy across two regions. Use **Async replication** for databases to avoid latency penalties on writes, accepting a small RPO (data loss). Use **Route53/Traffic Manager** for DNS failover.
*   **Active-Active:** Traffic split across both regions. RTO $\approx$ 0. Highest cost.
*   **Active-Passive:** One region primary, one standby. RTO depends on failover speed.
*   **Pilot Light:** Core data is synced; app servers are off/minimal. Low cost, medium RTO.
*   **Warm Standby:** Scaled-down version of the app is always running. Medium cost, low RTO.
*   **Multi-site Active-Active:** Full capacity in both. Zero RTO, highest cost.

**CL8 — Hard:** 
GitOps uses Git as the single source of truth for infrastructure and app state. A controller (ArgoCD/Flux) continuously reconciles the live state with the Git state.
*   **ArgoCD:** Feature-rich UI, application-centric.
*   **FluxCD:** Lightweight, CLI-driven, highly modular.
*   **Secrets:** **Sealed Secrets** (encrypted in Git, decrypted by controller), **External Secrets Operator** (fetches from Vault/AWS SM), or **HashiCorp Vault** (direct integration).
*   **Drift:** The controller detects the manual change and automatically overwrites it to match Git (Self-healing).

**CL9 — Hard:** 
*   **StatefulSet:** Ensures stable network IDs and ordered deployment/scaling.
*   **PV/PVC with Local Storage Class:** Maps pods to specific physical disks on nodes for low latency.
*   **Headless Service:** Provides DNS records for individual pods (essential for clustering).
*   **Init Containers:** Handle filesystem preparation or waiting for DB readiness.
*   **ConfigMaps as Volume Mounts:** Inject config files into specific paths (e.g., `/etc/app/config.yaml`).
*   **Pod Disruption Budgets (PDB):** Ensures a minimum number of replicas remain available during maintenance.

**CL10 — Medium:** 
*   **Service Account:** An identity for a process running in a pod.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Bad Practice:** Mounting static JSON keys in pods is dangerous because keys are long-lived, hard to rotate, and easily leaked.
*   **Federation:** The cloud provider trusts the K8s cluster's OIDC provider, issuing short-lived STS tokens to the pod automatically.

**CL11 — Medium:** 
*   **Object (S3/Blob):** Unstructured data, accessed via API. High durability (11 9s), virtually infinite scale. Use for backups, images, logs.
*   **Block (EBS/Managed Disk):** Raw volumes attached to one VM. Low latency. Use for OS disks, databases.
*   **File (EFS/Azure Files):** Shared network filesystem (NFS/SMB). Use for shared content across multiple pods/VMs.

**CL12 — Hard:** 
*   **Architecture:** Remove the "trusted perimeter." Use **Network Policies** (deny-all by default), **Service Mesh (Istio/Linkerd)** for mTLS between all services, and **Pod Identity** for least-privilege API access.
*   **Governance:** **OPA/Kyverno** to block non-compliant pods; **Cosign** for image signing; **Falco** for runtime anomaly detection.
*   **Difference:** Traditional security relies on a "hard shell, soft center" (Firewall). Zero Trust assumes the network is already compromised and verifies every single request.

**CL13 — Easy:** 
A CDN is a distributed network of proxy servers (Edge locations) that cache content closer to users.
*   **Services:** AWS CloudFront, Akamai.
*   **Use Case:** Use a CDN for static assets (JS, CSS, Images) or video to reduce latency and origin server load. Serve directly from origin only for highly dynamic, user-specific, or private data.

**CL14 — Easy:** 
*   **Region:** A geographic area (e.g., us-east-1).
*   **Availability Zone (AZ):** One or more discrete data centers within a region with redundant power/networking.
*   **Why Multi-AZ:** To protect against a single data center failure.
*   **Zonal vs Regional:** Zonal resources (e.g., an EC2 instance) exist in one AZ. Regional resources (e.g., S3, Lambda) are replicated across multiple AZs by the provider.

**CL15 — Easy:** 
A managed DB service abstracts the underlying server.
*   **Provider handles:** OS patching, hardware failure recovery, automated backups, point-in-time recovery, and high-availability mirroring.
*   **User handles:** Database schema design, query optimization, user permissions, and application-level logic.

**CL16 — Easy:** 
*   **Users:** Permanent identities for people.
*   **Groups:** Collections of users for easier permission management.
*   **Roles:** Temporary identities assumed by users or services.
*   **Policies:** JSON documents defining "Who can do what on which resource."
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply it by using specific Resource ARNs instead of `*` and using Roles instead of Users.

**CL17 — Easy:** 
Serverless is an execution model where the provider manages the server allocation.
*   **Comparison:** Lambda (AWS), Azure Functions, Google Cloud Functions are all event-driven and scale to zero.
*   **Cold Starts:** The latency incurred when a function is triggered after being idle (provider must spin up a container).
*   **Poor Fit:** Long-running processes (timeouts), apps requiring ultra-low consistent latency, or workloads with constant, high-volume traffic (where VMs are cheaper).

**CL18 — Medium:** 
*   **Ingress Resource:** Basic L7 rules (host/path) for routing.
*   **Gateway API:** Modern, role-based evolution of Ingress; allows separate management of infrastructure and routing.
*   **Annotations:** Cloud-specific tweaks (e.g., `service.beta.kubernetes.io/aws-load-balancer-type`).
*   **Mesh Gateway:** Handles mTLS and advanced traffic splitting (Canary/Blue-Green).
*   **TLS Termination:** Can happen at the Cloud LB (Edge), the Ingress Controller, or the Sidecar (End-to-End mTLS).
*   **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenancy, and better standardization.

**CL19 — Hard:** 
*   **Compute:** Use **Savings Plans/RIs** for baseline load; **Spot Instances** for stateless/batch jobs.
*   **Sizing:** Use **Right-sizing** tools to downsize over-provisioned VMs.
*   **Storage:** Move old data to **S3 Intelligent-Tiering** or **Glacier**.
*   **FinOps:** Implement **Tagging policies** for every resource.
*   **Visibility:** Use **Showback** (reporting costs to teams) and **Chargeback** (billing teams' budgets).
*   **Tools:** AWS Cost Explorer, Kubecost (for K8s), and automated "idle resource" scripts.

**CL20 — Hard:** 
*   **Design:** Use **Kubernetes** as the common runtime to abstract the OS. Use **Terraform** for consistent provisioning. Use **OIDC/SAML** for identity federation. Connect clouds via **Site-to-Site VPN** or **DirectConnect/ExpressRoute**.
*   **Trade-offs:** Theoretical benefit is "no lock-in" and "best-of-breed." Real-world cost is massive operational complexity, higher egress costs, and "lowest common denominator" feature usage.
*   **Justification:** Justified for strict regulatory requirements (sovereignty) or extreme disaster recovery needs. Unnecessary for most companies where the cost of complexity outweighs the risk of lock-in.

## OT Infrastructure Architecture

**OT1 — Easy:** 
The Purdue Model is a structural framework for ICS network segmentation.
*   **Level 0 (Process):** The physical equipment (sensors, actuators, motors).
*   **Level 1 (Basic Control):** PLCs and PID controllers.
*   **Level 2 (Area Supervisory):** HMIs and SCADA workstations.
*   **Level 3 (Site Operations):** Historians, site-wide control, and domain controllers.
*   **Level 4/5 (Enterprise):** Corporate IT network and Internet.

**OT2 — Easy:** 
*   **IT:** Focuses on Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability (CIA). Fast update cycles.
*   **OT:** Focuses on Availability $\rightarrow$ Integrity $\rightarrow$ Confidentiality (AIC). Safety is paramount.
*   **Patching:** Standard IT patching (auto-updates) can crash legacy PLCs or cause unplanned downtime, which in OT can lead to physical damage or loss of life.

**OT3 — Medium:** 
The **IDMZ** is a buffer zone that ensures no direct communication between the Enterprise (L4) and the Control Zone (L3 and below).
*   **Traffic:** Only proxied traffic (e.g., via a jump host or data broker). Traffic should generally flow from OT $\rightarrow$ IT (pushing data).
*   **Danger:** Direct L4 $\rightarrow$ L1 connectivity allows a compromised corporate laptop to send a "Stop" command directly to a PLC, bypassing all safety and supervisory checks.

**OT4 — Medium:** 
1.  **Modbus TCP:** L1/L2 (Simple, no security, widely used).
2.  **OPC UA:** L2/L3 (Secure, object-oriented, used for interoperability).
3.  **EtherNet/IP:** L1/L2 (Common in Rockwell/Allen-Bradley environments).
4.  **PROFINET:** L1/L2 (High-speed, common in Siemens environments).
5.  **MQTT:** L3/Cloud (Lightweight pub/sub for IoT/Telemetry).

**OT5 — Medium:** 
*   **Firewall:** Software-based, allows bidirectional traffic based on rules.
*   **Data Diode:** Hardware-based, physically allows light/data to travel in **one direction only**.
*   **Use Case:** Use a diode to send data from a high-security OT zone to a low-security IT zone without any possibility of an inbound attack.
*   **Limitation:** No TCP handshakes or ACKs; requires specialized proxy software to handle the one-way flow.

**OT6 — Medium:** 
**Flow:** PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Plant Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Security Boundaries:** 
    1. Firewall between L2 and L3.
    2. IDMZ between L3 and the Edge Gateway.
    3. Outbound-only firewall/diode from Edge Gateway to Cloud.

**OT7 — Hard:** 
*   **Zone:** A grouping of assets with similar security requirements.
*   **Conduit:** The communication path (and security controls) between zones.
*   **Design:** 
    *   **Corporate Zone** $\rightarrow$ (Conduit: MFA/VPN) $\rightarrow$ **IDMZ** $\rightarrow$ (Conduit: Proxy) $\rightarrow$ **SCADA Zone** $\rightarrow$ (Conduit: Firewall) $\rightarrow$ **Control Zone (PLCs)** $\rightarrow$ (Conduit: Air-gap/Strict Firewall) $\rightarrow$ **SIS Zone**.

**OT8 — Hard:** 
*   **Segmentation:** Create VLANs per production line (L2) and a separate VLAN for SCADA/Historians (L3).
*   **Architecture:** Use Industrial Managed Switches with ACLs. Place a firewall between L3 and L2.
*   **Remote Access:** Implement a Jump Host in the IDMZ with MFA.
*   **Transition:** Build the new segmented network in parallel. Migrate one production line at a time during scheduled maintenance windows to minimize risk.

**OT9 — Hard:** 
*   **BPCS:** Manages the normal process (e.g., keeping a tank at 50%).
*   **SIS:** A separate system that triggers a safe shutdown if the BPCS fails (e.g., venting a tank if pressure hits 100%).
*   **IEC 61511:** The international standard for functional safety in the process industry.
*   **Isolation:** SIS must be isolated so a failure/attack on the BPCS doesn't also disable the safety system.
*   **Ransomware in SIS:** Could prevent a safety shutdown during a crisis, leading to explosions or environmental disasters.

**OT10 — Medium:** 
*   **PLC (Programmable Logic Controller):** Fast, discrete control of a specific machine.
*   **DCS (Distributed Control System):** Integrated system for complex, continuous processes (e.g., oil refinery).
*   **SCADA (Supervisory Control and Data Acquisition):** High-level monitoring of geographically dispersed assets.
*   **Coexistence:** Yes. SCADA often acts as the "umbrella" monitoring multiple PLCs or a DCS.

**OT11 — Medium:** 
**Architecture:** User $\rightarrow$ VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (IDMZ) $\rightarrow$ Target HMI.
*   **Controls:** Session recording (for auditing), time-limited access (Just-in-Time), and vendor-specific accounts.
*   **RDP Danger:** Direct RDP allows lateral movement; if the corporate user is compromised, the attacker has a direct path to the HMI, which often has high privileges.

**OT12 — Hard:** 
*   **Detection:** Deploy passive IDS (e.g., Nozomi, Claroty) to detect anomalous Modbus/S7 traffic.
*   **Response:** 
    1. Isolate the compromised VPN segment.
    2. Shift to "Manual Mode" for critical processes.
    3. Use asset inventory to identify all devices the attacker touched.
*   **Operator Role:** The plant operator is the final authority; they decide if it is safer to keep the plant running or perform an emergency shutdown based on physical process stability.

**OT13 — Easy:** 
*   **HMI:** A dashboard (screen) that allows operators to monitor and control the process in real-time.
*   **Difference:** An HMI is for **operation** (start/stop/setpoint); an Engineering Workstation (EWS) is for **configuration** (writing logic, changing PLC code).

**OT14 — Easy:** 
A historian is a time-series database optimized for industrial data.
*   **Importance:** Essential for regulatory compliance, root-cause analysis, and process optimization.
*   **Plant Historian (L3):** High-resolution data, short retention, used for real-time operations.
*   **Enterprise Historian (L4):** Aggregated data, long-term retention, used for business reporting.

**OT15 — Easy:** 
Ladder Logic is a graphical programming language used in PLCs. It is dominant because it visually resembles the electrical relay diagrams that electricians used for decades, making it easy for maintenance staff to troubleshoot.

**OT16 — Easy:** 
*   **RTU (Remote Terminal Unit):** Designed for wide-area telemetry, often low-power, supports diverse communication (radio, cellular).
*   **PLC:** Designed for high-speed, local factory floor control.
*   **Environment:** RTUs are used in pipelines, water grids, and electrical substations.

**OT17 — Easy:** 
*   **Analog:** Continuous signal (e.g., 4-20mA).
*   **Digital:** Binary signal (On/Off).
*   **4-20mA vs 0-20mA:** 4mA is the "Live Zero." If the wire breaks, the signal drops to 0mA, allowing the system to distinguish between a "low reading" (4mA) and a "wire fault" (0mA).

**OT18 — Medium:** 
Asset inventory is the list of every device, firmware version, and IP on the network. You cannot protect what you don't know exists.
*   **Passive Monitoring:** Sniffing traffic (Safe).
*   **Active Scanning:** Sending probes (Dangerous).
*   **Danger:** Old PLCs have fragile TCP/IP stacks; a standard Nmap scan can crash the PLC, stopping the production line.

**OT19 — Hard:** 
MITRE ATT&CK for ICS focuses on the physical impact of cyber attacks.
*   **Tactics/Techniques:** 
    1. **Initial Access:** Engineering Workstation compromise.
    2. **Execution:** Valid Function Code (sending a legitimate but malicious command).
    3. **Persistence:** Modify PLC Firmware.
    4. **Inhibition of Response:** Alarm Suppression.
    5. **Impair Process Control:** Unauthorized Command Message.
*   **Difference:** Enterprise focuses on data theft; ICS focuses on process disruption/physical damage.

**OT20 — Hard:** 
*   **Collection:** Use SPAN/Mirror ports on switches to send traffic to an OT-IDS; avoid polling.
*   **Integration:** Feed OT-IDS alerts into a SIEM (e.g., Sentinel) via the IDMZ.
*   **Staffing:** Pair an IT Security Analyst (for log analysis) with an OT Engineer (to determine if the alert is a real process anomaly).
*   **Firmware Alert:** 
    1. Verify with the plant manager if a maintenance window was scheduled.
    2. If unauthorized, isolate the PLC from the network.
    3. Perform a forensic dump of the PLC memory.
    4. Restore from a known-good "Gold" backup.
