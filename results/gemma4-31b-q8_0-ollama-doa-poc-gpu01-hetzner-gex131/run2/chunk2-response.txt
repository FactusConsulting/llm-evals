## Kubernetes

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** is for stateless applications; pods are interchangeable, have random hashes in their names, and can be terminated/replaced in any order. A **StatefulSet** is for stateful applications (e.g., databases); pods have a stable, ordinal index (pod-0, pod-1), maintain a persistent identity, and are created/scaled in a strict sequential order.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
ClusterIP provides a stable virtual IP. `kube-proxy` (running on every node) manages the routing rules (via `iptables` or `IPVS`). When traffic hits the ClusterIP, the rules intercept it and load-balance it across the current set of healthy Pod IPs associated with the Service's selector.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an admin or dynamically (the "actual disk").
*   **PersistentVolumeClaim (PVC):** A request for storage by a user (the "ticket" specifying size and access mode).
*   **StorageClass (SC):** A template/profile that defines different "tiers" of storage (e.g., SSD vs HDD) and enables dynamic provisioning.
**Relation:** A user creates a PVC $\rightarrow$ the PVC references a StorageClass $\rightarrow$ the SC automatically provisions a PV $\rightarrow$ the PVC binds to that PV.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps.**
1.  `kubectl logs <pod>`: Check application stdout/stderr for panic or configuration errors.
2.  `kubectl describe pod <pod>`: Check "Events" for OOMKilled, failed probes, or mounting errors.
3.  Check Liveness/Readiness probes: Ensure the probe isn't killing the pod because the app takes too long to start.
4.  Verify ConfigMaps/Secrets: Ensure all required environment variables and secrets are present and correctly named.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS provides service discovery by mapping Service names to their ClusterIPs. If CoreDNS pods are down, pods cannot resolve internal service names (e.g., `my-api.default.svc.cluster.local`), causing all internal network communication relying on DNS to fail, though direct IP communication would still work.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on.**
The scheduler follows a two-step process:
1.  **Filtering (Predicates):** It removes nodes that cannot host the pod (e.g., insufficient CPU/RAM, node selector mismatch, or taints the pod doesn't tolerate).
2.  **Scoring (Priorities):** It ranks remaining nodes to find the "best" fit.
**Factors considered:**
*   **Resource Fit:** Preferring nodes where the pod's request leaves the most balanced resource distribution.
*   **Affinity/Anti-Affinity:** Placing pods near (or far from) other pods/nodes.
*   **Image Locality:** Preferring nodes that already have the container image cached.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
**Scheduling:** Yes. The scheduler looks at *requests*. $3.5\text{GB} + 256\text{Mi} \approx 3.75\text{GB}$, which is $\le 4\text{GB}$.
**Runtime:** If the pod uses 600Mi, it exceeds its *limit* (512Mi). The Linux kernel will trigger an Out-Of-Memory (OOM) event, and the kubelet will terminate the process with an `OOMKilled` status.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller.**
1.  **External LB:** Traffic hits a Cloud Load Balancer, which forwards it to the NodePort of the NGINX Ingress Controller pods.
2.  **Ingress Controller:** NGINX receives the request, matches the Host/Path against its configured Ingress rules.
3.  **Service/Endpoints:** NGINX does not route to the Service IP; it queries the Kubernetes API for the **Endpoints** (the actual Pod IPs) of the target Service.
4.  **Pod:** NGINX forwards the request directly to a Pod IP via the internal network, bypassing `kube-proxy` for efficiency.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A NetworkPolicy is an L3/L4 firewall for pods.
*   **Default:** All pods are "non-isolated" and accept traffic from any source.
*   **Applying a policy:** Once a policy selects a pod, that pod becomes "isolated." It will drop all traffic that is not explicitly allowed by the policy (Default Deny).

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old pods with new ones, ensuring zero downtime.
*   **Recreate:** Kills all existing pods before starting new ones, causing downtime.
**Choose Recreate when:** The application does not support running two different versions simultaneously (e.g., a database migration that is not backward compatible).

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A namespace is a virtual cluster partition used to isolate resources and provide scope for names.
**Defaults:** `default` (user apps), `kube-system` (cluster components), `kube-public` (publicly readable), and `kube-node-lease` (heartbeats).

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
It provides detailed metadata and status of a pod.
**Extra info:** 1. Events (e.g., Pulling image, Failed scheduling), 2. Container status/exit codes, 3. Volume mount details.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A ConfigMap stores non-confidential configuration data in key-value pairs.
**Consumption methods:** 1. As environment variables, 2. As files mounted in a volume.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Internal IP; only reachable from within the cluster.
*   **NodePort:** Exposes the service on a static port on every Node's IP.
*   **LoadBalancer:** Provisions an external cloud load balancer that routes to the NodePort/ClusterIP.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A DaemonSet ensures that a copy of a pod runs on all (or selected) nodes. Use it for infrastructure-level services like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints/Tolerations:** Taints are applied to *nodes* to repel pods. Tolerations are applied to *pods* to allow them to stay on tainted nodes. (Use case: Taint a node with a GPU so only GPU-enabled pods can land there).
*   **Node Affinity:** Applied to *pods* to attract them to specific nodes. (Use case: Ensure a pod runs in a specific availability zone for low latency).

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An Operator is a custom controller that uses a **Custom Resource Definition (CRD)** to manage a complex application. While standard controllers manage generic objects (like Deployments), Operators encode domain-specific operational knowledge (e.g., how to perform a MySQL backup or a schema upgrade) into code.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
etcd uses the **Raft** consensus algorithm for strong consistency. If quorum is lost (e.g., 2/3 nodes fail), the cluster becomes read-only or unavailable because it cannot commit new writes.
**Recovery:** You cannot recover via Raft. You must restore the remaining node from a recent snapshot and re-initialize the cluster as a single-member cluster, then add new members.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding.**
RBAC controls access based on roles.
*   **Role:** Permissions within a specific namespace.
*   **ClusterRole:** Permissions cluster-wide (or across all namespaces).
*   **RoleBinding:** Grants a Role to a user/group in a specific namespace.
*   **ClusterRoleBinding:** Grants a ClusterRole to a user/group cluster-wide.

**Manifest for read-only pods/logs in namespace `dev`:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "watch", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
- kind: User
  name: developer-user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf causes this and how to fix it.**
By default, `ndots` is 5. If a DNS query has fewer than 5 dots (e.g., `google.com`), K8s tries to resolve it as an internal service first by appending search paths (e.g., `google.com.default.svc.cluster.local`). This causes multiple failed queries before finally trying the absolute name.
**Fix:** Set `dnsConfig` in the pod spec to `ndots: 1`.

## Development

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
`merge` combines branches by creating a new "merge commit," preserving the exact history of how branches diverged. `rebase` rewrites history by moving the base of a branch to the tip of another, creating a linear history. **Avoid rebasing** public/shared branches, as it rewrites commit hashes and breaks other developers' histories.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP:** Connection-oriented, guarantees delivery, ordered packets (e.g., HTTP, SSH).
*   **UDP:** Connectionless, faster, no guarantee of delivery or order (e.g., DNS, VoIP/Streaming).

**D3 — Medium: What is a race condition? Give a concrete example.**
A race condition occurs when the outcome of a program depends on the non-deterministic timing/interleaving of multiple threads accessing shared data.
**Example:** Two threads incrementing a shared variable `count = 0`. Both read `0`, both increment to `1`, and both write `1` back. The final value is `1` instead of the expected `2`.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric:** Same key for encryption and decryption (Fast, e.g., AES).
*   **Asymmetric:** Public key encrypts, private key decrypts (Slow, e.g., RSA).
**TLS:** Asymmetric encryption is used during the "handshake" to securely exchange a symmetric session key. Once the session key is established, symmetric encryption is used for the actual data transfer for performance.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
A layer is a read-only filesystem delta created by each instruction in a Dockerfile. Docker caches these layers.
**Best Practice:** Order instructions from "least frequently changed" to "most frequently changed." Put OS updates and dependency installs (e.g., `npm install`) before copying source code, so code changes don't trigger a full reinstall of all dependencies.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe 4 things you would check, in order.**
1.  **Load Balancer/Ingress Logs:** Is the 503 coming from the LB (no healthy backends) or the app itself?
2.  **Pod Health/Events:** Check for `OOMKilled` or crashing pods (CrashLoopBackOff).
3.  **Downstream Dependencies:** Check if the database or a third-party API is timing out or rate-limiting.
4.  **Resource Saturation:** Check CPU/Memory metrics for the pods to see if they are throttling or saturated.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of CP and AP.**
CAP states a distributed system can only provide two of three: **Consistency** (all nodes see same data), **Availability** (every request gets a response), and **Partition Tolerance** (system works despite network failure).
*   **CP (Consistency/Partition):** MongoDB (in default config). It will stop accepting writes if a primary cannot be elected to ensure data consistency.
*   **AP (Availability/Partition):** Cassandra. It allows writes to any node and resolves conflicts later (eventual consistency).

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical:** Adding more power (CPU/RAM) to an existing machine.
*   **Horizontal:** Adding more machines to the pool.
**Patterns:** Statelessness (no session data on server), Load Balancing, Database Sharding, and Asynchronous Messaging (Queues).

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An environment variable is a dynamic value available to a process and its children. To persist it, add `export VAR_NAME=value` to the user's shell configuration file (e.g., `~/.bashrc` or `~/.zshrc`) or `/etc/environment` for system-wide persistence.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each.**
Both are data serialization formats. JSON is strict, uses brackets/braces, and is a subset of JavaScript. YAML is a superset of JSON that uses indentation and is more human-readable.
*   **JSON Advantage:** Faster parsing and universal support in APIs.
*   **YAML Advantage:** Supports comments and is much easier for humans to write/edit (ideal for config).

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE.**
REST is an architectural style for networked applications using HTTP.
*   **GET:** Retrieve a resource.
*   **POST:** Create a new resource.
*   **PUT:** Update/Replace an existing resource.
*   **DELETE:** Remove a resource.

**D12 — Easy: What is version pinning in dependency management, and why is it important?**
Version pinning is specifying the exact version of a library (e.g., `requests==2.25.1` instead of `requests>=2.0`). It ensures **reproducible builds**, preventing the application from breaking when a dependency releases a new version with breaking changes.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled:** Source code is translated to machine code by a compiler before execution (Fast). Examples: C++, Rust.
*   **Interpreted:** Source code is read and executed line-by-line by a runtime/interpreter (Flexible). Examples: Python, Ruby.

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common servers.**
*   **Reverse Proxy:** Sits in front of servers and forwards requests to them (protects servers, handles SSL, load balances).
*   **Forward Proxy:** Sits in front of clients and forwards requests to the internet (hides client identity, filters content).
**Servers:** Nginx (Load balancing/Static content), HAProxy (High-performance TCP/HTTP balancing).

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold?**
A deadlock is a state where two or more processes are unable to proceed because each is waiting for the other to release a resource.
**Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard: Explain eventual consistency. How do Cassandra handle read-after-write consistency?**
Eventual consistency guarantees that if no new updates are made, all accesses to a data item will eventually return the last updated value.
**Cassandra:** Uses "Tunable Consistency." You can specify the number of nodes that must acknowledge a read/write. To achieve read-after-write consistency (Strong Consistency), you ensure that $R + W > N$ (where $R$ is read quorum, $W$ is write quorum, and $N$ is replication factor).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the handshake and common use cases.**
mTLS is TLS where *both* the client and server present certificates to authenticate each other.
**Handshake:** 1. Server sends its cert $\rightarrow$ Client verifies. 2. Server requests client cert $\rightarrow$ Client sends its cert $\rightarrow$ Server verifies. 3. Both agree on a symmetric session key.
**Use Case:** Service-to-service communication in a Service Mesh (e.g., Istio) to ensure zero-trust security.

**D18 — Hard: Explain how a hash table works internally. Collision resolution and time complexity?**
A hash table uses a hash function to map keys to indices in an array.
**Collision Resolution:**
*   **Chaining:** Each index points to a linked list of all entries that hashed to that index.
*   **Open Addressing:** If a collision occurs, the system searches for the next empty slot (Linear Probing).
**Complexity:**
*   **Average:** $O(1)$ for Insertion, Lookup, and Deletion.
*   **Worst Case:** $O(n)$ (when all keys collide into one bucket).

**D19 — Hard: What is a circuit breaker pattern? Explain the three states and its relation to retries.**
It prevents a client from repeatedly calling a failing service, avoiding cascade failures.
*   **Closed:** Normal operation; requests flow through.
*   **Open:** Failure threshold reached; requests fail immediately without calling the service.
*   **Half-Open:** After a timeout, a few requests are let through to check if the service has recovered.
**Relation:** While retries attempt to fix transient errors, the circuit breaker stops retries from overloading a service that is completely down.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control. When to choose each?**
*   **Optimistic:** Assumes conflicts are rare. It doesn't lock; instead, it checks for changes at commit time (e.g., using a `version` column). If the version changed, the transaction fails. (Use for: Low contention, high-read environments).
*   **Pessimistic:** Assumes conflicts are likely. It locks the record immediately so no one else can modify it (e.g., `SELECT ... FOR UPDATE`). (Use for: High contention, critical financial data).
