## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the **Restricted Pod Security Standard (PSS)** requires that a pod must not run as root. While `securityContext.runAsNonRoot: true` tells Kubernetes to validate that the container does not run as root, it does not *set* the user. The new base image (`chainguard/static`) defaults to `USER root`. Under the **Baseline** policy, this was permitted. Under **Restricted**, Kubernetes checks the image's default user; since it is root and no `runAsUser` (non-zero ID) is specified in the manifest to override it, the Kubelet refuses to start the container, leading to a `CrashLoopBackOff` (or `CreateContainerConfigError`).

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[0].state.waiting.reason=="CrashLoopBackOff") | [.metadata.namespace, .metadata.name, .spec.securityContext, .spec.containers[0].securityContext] | @tsv'
```

**SC1-C:**
*   **Image-level fix:** Update the Dockerfile of the base image or the application image to include `USER 10001` (or any non-zero UID).
*   **Manifest fix:** Explicitly set `securityContext.runAsUser: 10001` in the Deployment spec.
*   **CI Pipeline Gate:** Integrate `kube-linter` or `polaris` into the CI pipeline to scan manifests for PSS Restricted compliance. Alternatively, use a Kyverno policy in a staging cluster to block pods that don't define `runAsUser`.
*   **Rollout:** Perform a **Canary Deployment**. Update the image/manifest for a small percentage of traffic, verify the `runAsNonRoot` validation passes, and then proceed with a rolling update (`maxUnavailable: 25%`) to ensure zero downtime.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is caused by **asynchronous replication lag**. In cross-region RDS, WAL (Write Ahead Log) records are shipped asynchronously to avoid blocking primary writes with 85ms+ latency. If the primary fails before the latest WALs reach the replica, those transactions are lost. To quantify the loss, I would check the `pg_stat_replication` view on the old primary (if accessible) or compare the `pg_last_xact_replay_timestamp()` on the promoted replica against the last known successful application write timestamp in the logs.

**SC2-B:**
1.  **Import:** `terraform import aws_db_instance.primary <new-rds-instance-id>`
2.  **State Move:** If the resource name in code differs: `terraform state mv aws_db_instance.replica aws_db_instance.primary`.
3.  **Update Code:** Update the `aws_db_instance` block to match the promoted instance's attributes (instance class, etc.) and update the `identifier`.
4.  **Dependencies:** Update the Route53 CNAME record to point to the new endpoint.
5.  **Apply:** Run `terraform plan` to ensure no "destroy/create" actions are planned, then `terraform apply`.

**SC2-C:**
*   **Connection Management:** Replace PgBouncer with **RDS Proxy**. It handles failovers more gracefully by maintaining application connections while the backend switches.
*   **DNS:** Use **Route53 Failover Routing** with health checks on the primary endpoint; it automatically updates the DNS record to the DR endpoint.
*   **RPO < 1s:** Standard RDS cannot guarantee this cross-region. I recommend **Aurora Global Database**. It uses storage-level replication (faster than PG streaming) and typically offers RPO < 1 second and RTO < 1 minute.
*   **Retry Logic:** Implement exponential backoff with jitter in the application to handle the transient "login retry" errors during the promotion window.

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Sticky Sessions:** K8s pods are ephemeral. **Solution:** Move sessions to an external Redis cluster.
2.  **Local NFS:** Pods cannot share local disk. **Solution:** Use an NFS CSI driver or migrate uploads to AWS S3.
3.  **Oracle 19c:** Heavyweight, non-cloud-native. **Solution:** Keep Oracle external (on-prem) and connect via VPN/Direct Connect, or use an Oracle Operator.
4.  **IBM MQ:** State-dependent messaging. **Solution:** Use a dedicated MQ cluster outside K8s or a managed MQ service.
5.  **Monolith Size:** Long startup times cause probe failures. **Solution:** Tune `initialDelaySeconds` and `startupProbe`.

**SC4-B:**
```hcl
variable "nfs_server" { default = "nfs.internal.com" }
variable "nfs_path"   { default = "/exports/uploads" }

resource "kubernetes_storage_class" "nfs_sc" {
  metadata { name = "nfs-csi" }
  storage_provisioner = "nfs.csi.k8s.io"
  parameters = {
    server = var.nfs_server
    path   = var.nfs_path
  }
}

resource "kubernetes_persistent_volume_claim" "uploads_pvc" {
  metadata { name = "uploads-pvc" }
  spec {
    access_modes = ["ReadWriteMany"] # Required: multiple pods must write to the same upload dir
    storage_class_name = kubernetes_storage_class.nfs_sc.metadata[0].name
    resources { requests = { storage = "1Ti" } }
  }
}
```

**SC4-C:**
*   **Phase 1 (Edge):** Deploy K8s Ingress. Route 5% of traffic to K8s $\rightarrow$ F5 $\rightarrow$ Monolith. (Verify connectivity).
*   **Phase 2 (Extraction):** Move a low-risk module (e.g., "User Profile") to a microservice in K8s. F5 routes `/profile` to K8s, everything else to Monolith.
*   **Phase 3 (Full Migration):** Move the core monolith into a container. Route all traffic to K8s.
*   **Integration:** IBM MQ remains external; K8s pods connect via a Service of type `ExternalName`.
*   **Rollback:** DNS weighted records (Route53) to shift traffic back to F5.
*   **Metrics:** p99 latency $\le$ 2s and Error Rate $\le$ 0.1% per phase.

## SC5 — Mysterious Latency Spike in Microservices

**SC5-A:**
1.  **Tracing:** Use Jaeger to find the "gap." If the span for `checkout-service` $\rightarrow$ `inventory-service` is long, but the `inventory-service` internal span is short, the latency is in the **Envoy sidecar or network**.
2.  **Envoy Metrics:** Check `envoy_cluster_upstream_rq_pending_total`. If high, the proxy is queueing requests because the upstream is saturated.
3.  **K8s Metrics:** Check `container_cpu_cfs_throttled_seconds_total` to see if the Go service is being throttled despite low average CPU.

**SC5-B:**
**SQL Diagnostic:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid, 
       blocking_activity.query AS blocking_query, blocked_activity.query AS blocked_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_locks.pid = blocked_activity.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype 
     AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
     AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid
WHERE NOT blocked_locks.granted;
```
**Go Circuit Breaker:**
```go
var cb = gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name: "inventory-service",
    MaxRequests: 5,
    Interval: 10 * time.Second,
    Timeout: 30 * time.Second,

func CallInventory() {
    body, err := cb.Execute(func() (interface{}, error) {
```

**SC5-C:**
*   **CQRS:** Use a **Read Replica** for the reconciliation job to avoid locking the primary write table.
*   **Bulkhead:** Create two separate DB connection pools in the `inventory-service`: one for API requests (high priority) and one for the CronJob (low priority).
*   **Scheduling:** Randomize the CronJob start time (jitter) or move it to 02:00 UTC.
*   **K8s:** Set a `PriorityClass` for the API pods and a lower priority for the CronJob pod. Use a `PodDisruptionBudget` to ensure at least 80% of API pods are always available.

## SC6 — Zero-Trust Network Overhaul

**SC6-A:**
*   **Machine Identity:** Deploy **SPIRE** (SPIFFE Runtime Environment). SPIRE agents on VMware, AWS, and Azure attest the workload (via AWS Instance Identity Document or Azure MSI) and issue short-lived SVIDs (X.509 certificates).
*   **Federation:** Use **SPIFFE Federation**. The AWS SPIRE server and On-Prem SPIRE server exchange trust bundles. A workload in AWS presents its SVID; the on-prem service verifies it against the AWS trust bundle. No shared secrets are needed.

**SC6-B:**
```hcl
resource "aws_ec2_transit_gateway" "main" { name = "zt-tgw" }

variable "vpc_endpoints" {
  default = ["s3", "rds", "ecr.api", "ecr.dkr"]
}

resource "aws_vpc_endpoint" "endpoints" {
  for_each          = toset(var.vpc_endpoints)
  vpc_id            = aws_vpc.main.id
  service_name      = "com.amazonaws.${var.region}.execute-api" # Simplified
  vpc_endpoint_type = "Interface"
  security_group_ids = [aws_security_group.endpoint_sg.id]
}

resource "aws_security_group" "default_deny" {
  vpc_id = aws_vpc.main.id
  # No ingress rules = default deny
}
```

**SC6-C:**
*   **Direct Connect:** Highest bandwidth, lowest latency, most expensive. Best for the 10Gbps need.
*   **ECMP VPN:** Cheaper, but limited by CPU overhead of IPsec and jitter.
*   **Tailscale/Netbird:** WireGuard-based mesh. Easiest to implement Zero Trust (identity-based routing), but requires an agent on every node.
*   **Recommendation:** **Direct Connect** for the backbone, with **Tailscale** layered on top for identity-based access control.
*   **Routing:** Direct Connect requires BGP configuration on the on-prem router; Tailscale handles routing via a virtual overlay network.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
1.  **Manual Apply:** Bypasses peer review and CI tests.
2.  **Divergent Values:** Leads to "environment snowflake" syndrome where staging is no longer a valid proxy for prod.
3.  **`kubectl edit`:** Creates "ghost" configurations that are wiped out during the next `tofu apply`.
*   **State Locking Danger:** Without locking, two engineers running `apply` simultaneously can cause a **race condition**, resulting in a corrupted state file or partial resource creation/deletion, leading to an outage.

**SC7-B:**
```yaml
stages: [validate, plan, apply]

validate:
  script: [tofu fmt -check, tofu validate]

plan:
  script: 
    - tofu plan -out=tfplan
    - # Script to post tfplan to MR comment
  artifacts: { paths: [tfplan] }

apply_prod:
  stage: apply
  script: tofu apply tfplan
  when: manual
  environment: production
  # Backend config in tofu.tfvars: backend "s3" { dynamodb_table = "tofu-lock" }
```

**SC7-C:**
*   **Drift Detection:** A scheduled GitLab CI job runs `tofu plan -detailed-exitcode`. If it returns `2` (drift detected), it triggers a Slack alert.
*   **Blocking Edits:** Use **Kyverno** to block `UPDATE` and `PATCH` requests on `ConfigMaps` and `Deployments` unless the user is the `gitlab-ci-sa` service account.
*   **Helm Structure:** Use **Helmfile**. Define a `base` values file and `prod-values.yaml` for overrides.
*   **RBAC:** Remove `cluster-admin` from all human users. Grant `edit` role to humans in `dev`, `view` in `prod`. Only the CI Service Account gets `cluster-admin` in `prod`.

## SC8 — Observability Stack Scaling Failure

**SC8-A:**
1.  **Prometheus OOM:** **High Cardinality**. Too many unique label combinations (e.g., putting `user_id` in a label) are exhausting RAM. Check `prometheus_tsdb_head_series`.
2.  **Loki Drops:** **Ingester Saturation**. The write path cannot keep up with the log volume. Check `loki_ingester_flush_failed_chunks_total`.
3.  **Tempo Timeouts:** **S3 Latency/Indexing**. Querying old traces requires scanning too many blocks. Check `tempo_querier_request_duration_seconds`.
4.  **Thanos Lag:** **Compactor Resource Starvation**. The compactor cannot merge blocks faster than they are created. Check `thanos_compactor_halted`.

**SC8-B:**
```bash
#!/bin/bash
PROM_URL="http://prometheus:9090"
echo -e "Metric\tSeriesCount"
curl -s "$PROM_URL/api/v1/label/__name__/values" | jq -r '.data[].value' | while read metric; do
  count=$(curl -s "$PROM_URL/api/v1/query?query=count(count_over_time({__name__=\"$metric\"}[1m]))" | jq -r '.data.result[0].value[1]')
  echo -e "$metric\t$count"
done | sort -rnk2 | head -n 20
```

**SC8-C:**
*   **Metrics:** Migrate to **Mimir**. It horizontally scales the read/write paths and handles billions of series via sharding.
*   **Logs:** Deploy Loki in **Microservices Mode**. Separate the `ingester`, `querier`, and `distributor` to scale them independently.
*   **Traces:** Use Tempo's **Parquet storage** on S3 for better compression and faster retrieval.
*   **Governance:** Implement **Relabeling configs** to drop high-cardinality labels at the agent level.
*   **Chargeback:** Use the `tenant_id` label in Mimir/Loki. Query `sum(prometheus_remote_storage_samples_total)` grouped by `tenant_id` to bill teams based on their ingestion volume.

## SC9 — Securing a Public-Facing API After a Breach

**SC9-A:**
1.  **BOLA (API1:2023):** User A accesses User B's data. **Fix:** Validate ownership in the view.
    ```python
    def get_object(self, queryset=None):
        obj = super().get_object()
        if obj.owner != self.request.user:
            raise PermissionDenied("Not your record")
        return obj
    ```
2.  **Excessive Data Exposure (API3:2023):** Internal fields leaked. **Fix:** Use a dedicated DRF `Serializer` that explicitly lists allowed fields.
3.  **Lack of Resources (API4:2023):** Scraping. **Fix:** Implement WAF rate limiting and DRF `Throttling`.
4.  **Security Misconfiguration (API7:2023):** Keys in logs. **Fix:** Move API keys to `Authorization: Bearer <key>` header.

**SC9-B:**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {

  # ... scope and default_action ...
  rule {
    name     = "RateLimit"
    priority = 1

  }
  rule {
    name     = "BlockKeyInUrl"
    priority = 2
    action { block {} }
    statement { byte_match_statement { 
      field_to_match { query_string {} }
      text_transformation { priority = 0; type = "NONE" }
      positional_constraint = "CONTAINS"
      search_string = "api_key=" 
    } }
  }
  # Add ManagedRuleGroup and GeoMatch using var.allowed_countries
}
```

**SC9-C:**
*   **Auth:** Transition to **OAuth2/OIDC** with JWTs.
*   **Gateway:** Deploy **Kong** to handle JWT validation, rate limiting, and request transformation before traffic hits the ALB.
*   **Auditing:** Enable **CloudTrail Data Events** for the ALB and S3 to track every API call.
*   **Encryption:** Use **AWS KMS** for field-level encryption of PII (e.g., SSN) before storing in PostgreSQL.
*   **Migration:** Support both API keys and JWTs for a 30-day window. Return a `Warning` header in API key responses: `Warning: 299 - "API keys are deprecated. Please migrate to OAuth2."`

## SC10 — Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Architecture:** **Active-Passive with Cilium Cluster Mesh**. Active-Active is too complex for 200TB of MinIO.
*   **RPO/RTO:** RPO 15m is achievable via async replication. RTO 1h is tight for 200TB; we cannot "restore" from backup. We must use **continuous replication**.
*   **Replication:**
    *   **PostgreSQL:** Patroni with async streaming replication.
    *   **Redis:** Redis Sentinel with cross-site replication.
    *   **RabbitMQ:** Federation plugin (avoids the latency penalty of mirroring).
    *   **MinIO:** Site-to-Site Bucket Replication (asynchronous).

**SC10-B:**
```yaml
- name: Configure Patroni
  hosts: db_nodes
  tasks:
    - template: src=patroni.yml.j2 dest=/etc/patroni.yml
      notify: restart patroni
    - name: Ensure etcd is reachable
      uri: url=http://etcd-cluster:2379/health
```
*`patroni.yml` snippet:*
```yaml
postgresql:
  parameters:
    synchronous_commit: "on"
    synchronous_standby_names: "dallas_node_1, dallas_node_2"
```

**SC10-C:**
1.  **Detection:** A quorum of monitors (e.g., Route53 Health Checks + external probes) must agree the Chicago site is unreachable for > 2 minutes.
2.  **DNS:** GSLB updates the CNAME to point to the Dallas Load Balancer.
3.  **Promotion:** Patroni promotes the Dallas standby to Primary.
4.  **Statefuls:** Redis Sentinel promotes the Dallas slave; RabbitMQ switches to the local federation queue.
5.  **MinIO:** Trigger a "failover" to make the Dallas bucket writable.
6.  **Split-Brain:** Use **Fencing (STONITH)** to ensure the Chicago site is completely powered off or network-isolated before promotion.
7.  **Failback:** Re-introduce Chicago as a standby $\rightarrow$ Sync data $\rightarrow$ Perform a planned switchover during a maintenance window.
