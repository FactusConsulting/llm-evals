SC1-A
The pods fail because Kubernetes Pod Security Standards (PSS) enforcement changed from `Baseline` to `Restricted`. `Restricted` requires `securityContext.runAsNonRoot: true` AND an explicit `runAsUser` set to a non-zero UID. The new base image (`cgr.dev/chainguard/static:latest`) sets `USER root` (UID 0) in the Dockerfile. Without an explicit `runAsUser` override, the container attempts to run as UID 0, violating the `Restricted` policy. The kubelet rejects the pod or the container runtime kills it, resulting in `CrashLoopBackOff`. `Baseline` allowed root, so the upgrade exposed the misconfiguration.


SC1-C
**Immediate Fix:** Patch deployments to add `securityContext.runAsUser: 1000` (or the UID of the non-root user in the image). Use `kubectl rollout restart` for rolling updates.
**Image Fix:** Update Dockerfiles to `USER nonroot` or use a base image that sets a non-root user. Pin to a specific digest.
**CI Gate:** Add a policy check (e.g., OPA/Kyverno or Trivy) to reject images where `USER root` is the final instruction, and reject Helm/K8s manifests missing `runAsUser` when `runAsNonRoot: true` is set.
**Rollout:** Use `maxSurge=1` and `maxUnavailable=0` in deployment specs. Run `kubectl rollout status` to verify zero downtime. Monitor `CrashLoopBackOff` metrics post-rollback window.

SC2-A
Cross-region streaming replication is asynchronous by default. WAL shipping across regions experiences network latency and buffering. When the replica is promoted, any WAL not yet shipped or replayed is permanently lost. The data loss window equals the replication lag at promotion time. To quantify: check `pg_stat_replication` for `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn` differences, or query `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()`. Also check `pg_stat_replication.application_name` lag metrics. Asynchronous replication inherently risks data loss proportional to lag and network partition duration.

SC2-C
**Architecture:** Use RDS Proxy instead of PgBouncer for transparent connection pooling and automatic failover handling. Implement Route53 failover routing with health checks targeting the proxy endpoint. Add application-level retry logic with exponential backoff and jitter.
**RPO < 1s:** Standard async RDS cannot guarantee this. Recommend Aurora Global Database. SC6-C
**Comparison:**
- **Direct Connect:** Dedicated 10Gbps/100Gbps, lower latency, higher cost. Fits ZT if paired with MACsec/IPsec. Requires BGP routing changes.
- **ECMP VPN:** Two IPsec tunnels with BGP ECMP. Scales bandwidth, lower cost, but IPsec overhead adds latency. Routing: multiple tunnels, BGP multipath.
- **Tailscale/Netbird:** WireGuard mesh, zero-config, but not designed for 10Gbps dark fiber enterprise routing. Adds overlay latency. Not recommended for core infrastructure.
**Recommendation:** Direct Connect for primary backbone (cost justifies performance/security). ECMP VPN as fallback. Routing changes: DX requires BGP peering and route propagation; ECMP requires multiple tunnel configs and BGP multipath; mesh changes to overlay routing.

SC10-A
**Architecture Comparison:**
- **Active-Passive (Velero):** RPO depends on backup frequency (e.g., 15min). RTO depends on restore time. 200TB restore via Velero will take hours, failing RTO=1h. Not feasible for this data volume.
- **Active-Active (Istio/Cilium):** Requires stateless workloads. Stateful components need replication. 12ms latency is acceptable for sync replication but impacts write performance.

- PostgreSQL: Patroni async replication with synchronous commit for critical writes.
- Redis: Sentinel with AOF + RDB sync, or Redis Cluster with cross-cluster replication.
- RabbitMQ: Federation/Shovel or Quorum Queues with cross-site replication.
- MinIO: Site replication (async) with versioning.
**Feasibility:** Active-active with synchronous replication for stateful can meet RPO/RTO but requires careful tuning. Recommend active-passive with faster backup (Velero + snapshot) OR active-active with stateless K8s + replicated stateful, using Patroni sync and MinIO site replication.

SC10-C
**Failover Orchestration Sequence:**
1. **Detection:** Health checks (heartbeat, DB ping, node status). "Site down" = >3 consecutive failures + quorum loss.
2. **Fencing:** Prevent split-brain via STONITH or DCS quorum. Only promote if primary is unreachable.
3. **DNS Failover:** GSLB updates records to point to Dallas.
4. **Patroni Promotion:** Standby promoted, synchronous commit disabled temporarily.
5. **Redis Sentinel:** Sentinel promotes replica, updates config.
6. **RabbitMQ:** Federation syncs queues, quorum queues elect new leader.
7. **MinIO:** Site replication catches up, versioning ensures consistency.
8. **OpenTofu State:** Update state to reflect new primary, disable Chicago resources.
**Split-Brain:** Use fencing (power off/kill processes on old primary), DCS quorum, or external orchestrator (Consul/Etcd) to enforce single leader.
**Failback:** Reverse replication, sync data, verify integrity, switch DNS back, re-enable Chicago, update OpenTofu state. Test failback quarterly.
