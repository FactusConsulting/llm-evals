AA1 — Monoliths are single, unified codebases deployed as one unit with shared processes and databases. Microservices are independently deployable, loosely coupled services with separate codebases, databases, and runtime environments. Three concrete problems microservices introduce: (1) Distributed transactions/consistency challenges, (2) Network latency and partial failure handling, (3) Operational complexity (deployment orchestration, distributed tracing, monitoring, and configuration management).

AA2 — Synchronous communication uses request-response where the caller blocks until a reply arrives. Asynchronous communication uses message passing where the producer sends data and the consumer processes it later without blocking the caller. Example sync: REST/HTTP or gRPC. Example async: RabbitMQ or Apache Kafka.

AA3 — A reverse proxy routes traffic to backend servers, handling SSL termination, load balancing, and caching at the network/transport layer. An API gateway adds API-specific capabilities: rate limiting, authentication, request/response transformation, service discovery, and analytics. An API gateway can technically replace a reverse proxy since it includes proxying functionality, but in practice they are often layered: a lightweight reverse proxy (e.g., Nginx) handles edge TLS/DDoS protection, then routes to the API gateway for business logic enforcement.

AA4 — The Saga pattern manages distributed transactions by breaking them into local transactions, each with a compensating action to roll back if a later step fails. Choreography-based sagas use events: services publish state changes and react autonomously. Orchestration-based sagas use a central coordinator that sends commands to services. Choreography is appropriate for simple, loosely coupled, event-driven workflows. Orchestration is appropriate for complex, stateful, or multi-step workflows requiring explicit control, rollback logic, and easier debugging.

AA5 — CQRS separates read (Query) and write (Command) operations into distinct models. Event Sourcing stores state as an immutable sequence of domain events rather than current snapshots. They are paired because CQRS reads from optimized projections while Event Sourcing provides the authoritative write model. This combination solves the CRUD impedance mismatch, enables full audit trails, temporal queries, and independent scaling of read/write workloads.

AA6 — The Circuit Breaker pattern prevents repeated calls to a failing service. States: Closed (normal operation), Open (fail fast, skip calls), Half-Open (allow limited test requests). It differs from retry with backoff because retry attempts immediate recovery, while circuit breaker halts calls entirely to prevent cascading failures and allow downstream recovery. Use both together: apply retry/backoff for transient failures inside the Closed state, and open the circuit when failures persist to stop retry storms.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, lower security (relies on row-level filtering), lowest ops complexity.
2. Shared DB, separate schema: Moderate cost, moderate noisy-neighbor, better security/isolation, moderate ops (schema migrations per tenant).
3. Separate DB per tenant: Highest cost, lowest noisy-neighbor, highest security, highest ops (backup/restore/migration per tenant). Best for regulated/enterprise tenants.

AA8 — Eventual consistency allows temporary stale reads as updates propagate; strong consistency guarantees all reads see the latest write immediately. For inventory that must never oversell: use strong consistency. Data store: distributed strong-consistency DB (CockroachDB, Spanner) or relational DB with row-level locking. Patterns: synchronous stock validation before order placement, reservation/hold patterns with TTLs, optimistic/pessimistic locking, and partition inventory by SKU/warehouse to scale while maintaining strong consistency per partition.

AA9 — A sidecar proxy is a container co-located with an app that intercepts all inbound/outbound traffic. In Istio, Envoy handles the data plane (traffic routing, mTLS, metrics), while Istio control plane (Pilot, Citadel) pushes config and manages certificates. Data plane = Envoy proxies handling traffic; control plane = Istio components managing config/certs. mTLS between sidecars solves transparent service-to-service authentication and encryption without application code changes, automatic cert rotation, and zero-trust enforcement, which application-level TLS cannot provide efficiently at scale.

AA10 — The Strangler Fig pattern incrementally replaces monolith functionality by routing traffic to new services until the legacy system is decommissioned. Strategy: (1) Place API gateway in front of the .NET Framework monolith. (2) Identify a bounded context (e.g., Auth, Billing). (3) Build the new .NET 8 microservice. (4) Route that context’s traffic through the gateway to the new service. (5) Migrate data via dual-write or CDC. (6) Repeat for other contexts. (7) Decommission the monolith once all routes are migrated.

AA11 — The 12-Factor App methodology standardizes cloud-native app design. Six factors: (1) Codebase (one repo per app), (2) Dependencies (explicitly declare), (3) Config (store in env vars), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless, exec model). They matter because they ensure portability, horizontal scalability, resilience, config security, and seamless CI/CD integration in cloud environments.

AA12 — Coupling: Event-driven = loose (async), Request-driven = tight (sync). Scalability: Event-driven = highly scalable, burst-tolerant; Request-driven = linear, connection-bound. Debugging: Event-driven = harder (distributed state, replay needed); Request-driven = easier (request/response trace). Ordering: Event-driven = partition/key-based guarantees; Request-driven = per-request. Failure: Event-driven = durable queues, retry/replay; Request-driven = timeouts, retries, circuit breakers. Choose event-driven for async workflows, high throughput, decoupled systems, or event sourcing. Choose request-driven for real-time queries, strict latency, synchronous workflows, or simple CRUD.

AA13 — A load balancer distributes incoming traffic across multiple backend servers. Layer 4 routes based on IP/port (TCP/UDP), offering fast, protocol-agnostic forwarding. Layer 7 routes based on HTTP headers, URLs, cookies, or content. Layer 7 is required when routing `/api/v1` to service A and `/api/v2` to service B, or when routing based on session cookies or content type.

AA14 — A message queue (RabbitMQ) consumes and removes messages, supporting point-to-point and pub/sub with routing. A log-based broker (Kafka) appends messages to an immutable log, retains them, and allows multiple consumers to read independently at their own pace. Pick RabbitMQ for task distribution, work queues, and low-latency routing. Pick Kafka for event streaming, high throughput, replayability, and data pipelines.

AA15 — Containers share the host OS kernel and isolate processes/filesystems; VMs run a full guest OS under a hypervisor. Containers are lighter, faster to start, and use fewer resources. They’re popular for microservices because they enable consistent environments, rapid independent deployments, efficient resource utilization, and immutable infrastructure, aligning with microservices’ need for agility and horizontal scaling.

AA16 — Stateless services store no local session data; each request is independent. Stateful services maintain local state/session data. Stateless services scale horizontally easily because instances can be added/removed without data migration or session sync. Example stateless: Web API, Nginx. Example stateful: PostgreSQL, Redis, WebSocket server with in-memory sessions.

AA17 — An ORM maps database tables to application objects and abstracts SQL generation. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs accelerate development, provide type safety, and simplify migrations, but can generate inefficient queries, obscure performance bottlenecks, and leak abstraction boundaries. Raw SQL offers full control, optimal performance, and easier complex query tuning, but requires more boilerplate, DB-specific code, and maintenance overhead.

AA18 — The Bulkhead pattern isolates resources (threads, connections, pools) so a failure in one component doesn’t exhaust resources for others. It prevents cascading failures in microservices. Implementation: Use separate thread pools or connection pools per downstream service call, or deploy critical vs non-critical services on separate Kubernetes namespaces/node pools with resource quotas and network policies to enforce isolation.

AA19 — OT requires a central server to transform operations, providing strong consistency and low online latency, but has complex server logic and requires queueing for offline support. CRDTs use mathematical structures that converge automatically without coordination, offering eventual consistency, higher message size/latency, simpler client logic, and excellent offline support. For offline editing, choose CRDTs: they guarantee convergence without a central server, handle concurrent edits gracefully, and sync seamlessly when back online.

AA20 — Challenges include polyglot context injection, network hops, async flows, and performance overhead. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject/extract trace IDs across HTTP/gRPC. Sampling: head-based (random, simple, loses context), tail-based (sample after processing, accurate, high overhead). Storage/querying: Jaeger/Tempo index traces by trace ID, searchable by service/span. Async/Kafka continuity: propagate trace context in message headers. Producers inject, consumers extract and continue the trace, linking spans via correlation IDs. Kafka partitioning may break ordering but tracing remains continuous via header propagation.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and data center use. Examples: VMware ESXi, KVM, Hyper-V. Type 2 (hosted) hypervisors run on a host OS, offering lower performance and desktop use. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block-level storage presented as local disks, optimized for databases/VMs. Protocols: Fibre Channel, iSCSI. NAS provides file-level storage accessed over the network, optimized for file shares/backups. Protocols: NFS, SMB/CIFS. Use SAN for low-latency, high-IOPS workloads; use NAS for shared file access and easier management.

OP3 — 3-tier architecture: Access (edge) → Distribution (policy/aggregation) → Core (high-speed backbone). Leaf-spine is preferred because it’s a flat, all-to-all mesh where every leaf connects to every spine. It solves 3-tier bottlenecks by providing predictable low latency, better bandwidth utilization, horizontal scalability, and eliminating single points of failure at the distribution/core layers.

OP4 — Architecture: 3+ nodes (odd for quorum). Quorum requires majority online (2 of 3). Fencing via STONITH (IPMI/iDRAC) prevents split-brain. Shared storage: Ceph (recommended, distributed) or iSCSI/NFS (centralized, SPOF risk). Node failure: Proxmox HA manager detects failure, powers off failed node via fencing, and migrates VMs to remaining nodes. Ceph maintains data replication; cluster remains operational if quorum is preserved.

OP5 — VLAN trunking carries multiple VLANs over a single physical link. 802.1Q adds a 4-byte tag to Ethernet frames containing the VLAN ID. Linux config: Create VLAN subinterfaces: `ip link add link eth0 name eth0.10 type vlan id 10`, repeat for 20/30. Assign IPs/configure bridges via `systemd-networkd` or `NetworkManager`. Traffic is tagged egress and untagged ingress per VLAN.

OP6 — RAID 1: Mirror, 50% capacity, 1 drive fault tolerance. RAID 5: Striping + single parity, 1 drive tolerance, read-heavy, write penalty. RAID 6: Striping + double parity, 2 drive tolerance, higher write penalty. RAID 10: Mirror + stripe, 50% capacity, 2 drive tolerance, excellent perf. RAID Z2: Double parity, flexible capacity, checksums, safe rebuilds. For 6 drives + DB: Choose RAID Z2. It balances capacity, tolerates 2 drive failures, and provides superior data integrity and rebuild safety over RAID 5/6. RAID 10 is viable if write latency is critical and 50% capacity waste is acceptable.

OP7 — Recursive resolvers: Internal clients use AD-integrated DNS; forwarders point to ISP/external. Authoritative: Internal zone (AD-integrated, secure dynamic updates); external zone (public, DNSSEC-signed). Split-horizon: Internal DNS returns private IPs; external DNS returns public IPs. Conditional forwarding: Internal DNS forwards external queries to forwarders; DMZ DNS forwards internal queries to internal DNS. Laptop mobility: On LAN, uses internal DNS for split-horizon resolution; on VPN, switches to remote DNS. DNSSEC validates external responses; conditional forwarding ensures correct routing regardless of location.

OP8 — PKI chain: Root CA → Subordinate/Issuing CA → End-entity cert. Trust flows downward. Internal PKI: Root CA offline (air-gapped). Subordinate CA online, issues certs. Use certificate templates for auto-enrollment (Windows AD CS). CRL/OCSP for revocation checking. Compromise consequences: Subordinate CA compromise = rogue certs issued, but root remains safe; revoke subordinate and issue new. Root CA compromise = total trust collapse; must rebuild entire PKI and update all trust stores.

OP9 — MPLS: High cost, high reliability, low latency, complex management, private security. IPsec VPN: Low cost, variable reliability, higher latency, simple management, basic security. SD-WAN: Moderate cost, high reliability (multi-path), low latency (optimized), easy management, integrated security. WireGuard mesh: Low cost, variable reliability, low latency, simple management, strong crypto. Recommendation: SD-WAN. Best balance for VoIP (QoS, path optimization, reliability), manageable at scale, cost-effective vs MPLS, and superior to plain IPsec for latency-sensitive apps.

OP10 — iDRAC (Dell), iLO (HPE), IPMI (standard) are out-of-band management interfaces for remote power control, console access, and hardware monitoring. Critical because they enable recovery when OS/network is down and facilitate remote maintenance. Internet exposure: High risk. Default credentials, known CVEs, and lack of network isolation allow attackers to power cycle, access console, extract hardware info, or pivot into the network. Should be restricted to isolated management VLANs.

OP11 — LVM: Traditional volume manager, fixed-size volumes, COW snapshots consume space quickly. LVM-Thin: Overprovisions storage, efficient snapshots, but can exhaust thin pool space. ZFS: Integrated FS+volume manager, COW, instant space-efficient snapshots, checksums, self-healing. When to use: LVM for legacy/simple Linux, LVM-Thin for VM storage needing overprovisioning, ZFS for data integrity and modern Linux/BSD. Snapshot semantics: LVM/LVM-Thin require pre-allocation or thin pool management; ZFS snapshots are instant, recursive, space-efficient, and immutable until cloned.

OP12 — Stretch cluster: 2 sites (primary/secondary) + 1 arbiter site. CRUSH rules distribute OSDs across sites. Monitors: 2 in primary, 1 in arbiter (or 3 with split quorum). Latency: <10ms ideal, <50ms acceptable for stretch; higher degrades performance. Split-brain: Both sites act primary; arbiter breaks tie. 2-site Ceph without tiebreaker is bad because no quorum resolution exists, leading to split-brain, dual writes, and data corruption. Arbiter or odd monitor placement is mandatory.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover (broadcast), Offer (server reply), Request (client asks), Acknowledge (server confirms). Server unavailable: Client uses APIPA (169.254.x.x) or retains old IP if lease valid. Windows lease expiry: Client unicasts renewal at 50% lease, then broadcasts at 87.5%. If server unreachable, it retries until lease expires, then falls back to APIPA or static configuration.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, ACLs, port security, SNMP monitoring, and PoE. Enterprise importance: VLAN segmentation isolates traffic, QoS prioritizes VoIP/Video, STP prevents loops, ACLs enforce security, and monitoring enables troubleshooting and scalability.

OP15 — NTP synchronizes clocks over the network. Critical for log correlation, auth tokens (Kerberos/JWT), distributed consensus (Raft/Paxos), backup ordering, and certificate validity. Clock drift consequences: Cluster split-brain, auth failures, log misalignment, database replication lag, certificate validation errors, and failed distributed transactions.

OP16 — Physical servers provide direct hardware access and full control. VMs virtualize OS under a hypervisor with full guest isolation. Containers isolate processes sharing the host kernel. Run bare metal when needing maximum performance (HPC, HFT), direct hardware access (GPU passthrough, specialized NICs), compliance/security requirements, or avoiding hypervisor overhead.

OP17 — UPS provides short-term battery backup and power conditioning, bridging the gap to generator startup. Generators provide long-term fuel-based backup for extended outages. Both are needed because UPS handles immediate transition and protects against surges/brownouts, while generators sustain power for hours/days. ATS (Automatic Transfer Switch) detects utility loss, switches load to generator, and switches back when utility restores, preventing backfeeding.

OP18 — Active-passive: One node handles traffic, standby takes over on failure. Simple, no split-brain. Active-active: All nodes handle traffic, share load. Complex, requires distributed DB or sync replication. PostgreSQL HA with Pacemaker/Corosync: Pacemaker manages virtual IP, monitors DB health, and triggers failover. STONITH fencing ensures failed node is powered off. Failover: VIP moves to standby, standby promotes to primary via streaming replication, and sync resumes. Use Patroni or Pacemaker-native PostgreSQL agents for robust management.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO define acceptable data loss and downtime. Backup types: Full (baseline), Incremental (changes since last), Differential (changes since last full). Deduplication reduces storage and backup windows. Media: Disk (fast restore), Tape (cheap offsite), Cloud (scalable). Immutable backups (WORM) protect against ransomware. Test restores regularly to verify integrity and measure RTO/RPO. Backup = data protection; Disaster Recovery = comprehensive strategy (infrastructure, processes, failover) to restore operations after a disaster.

OP20 — 802.1X is port-based NAC. Roles: Supplicant (client), Authenticator (switch/AP), Authentication Server (RADIUS). EAP methods: EAP-TLS (cert-based, mutual auth, highly secure), PEAP (username/password, tunneled, common). RADIUS handles AAA (auth, authorization, accounting). Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: Port stays unauthorized, no network access. MAB (MAC Authentication Bypass): Uses MAC address as credential; RADIUS checks MAC against database. Fallback for IoT/printers lacking 802.1X support, but offers lower security.
