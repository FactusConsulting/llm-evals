T1 — `tofu plan` performs a dry-run: it reads the current state, fetches provider data, and calculates the diff between your configuration and the real infrastructure, outputting what will be created, updated, or destroyed. `tofu apply` executes that plan, making the actual API calls to provision/update resources. Plan is for validation; apply is for execution.

T2 — State is a JSON file mapping your configuration to real-world resource IDs and attributes. Remote state stores this file in a shared backend (e.g., S3, GCS, Terraform Cloud), enabling team collaboration, preventing state file corruption, enabling state locking, and allowing CI/CD pipelines to access infrastructure metadata securely.

T3 — `count` uses integer indices and creates resources in a flat list; adding/removing items can cause destructive recreation due to index shifting. `for_each` uses maps or sets, assigning each resource a unique key. `for_each` is preferred when resources have distinct identifiers or attributes, as it preserves existing resources when the collection changes.

T4 — OpenTofu detects drift during `plan` by comparing the state file to live provider data. If a resource was modified externally, the plan shows it as a change. On `apply`, OpenTofu will revert it to match your configuration (unless `lifecycle.ignore_changes` or `lifecycle.prevent_destroy` is configured).

T5:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `terraform_remote_state` reads the entire state file, which can be slow, expose sensitive data, and couple modules tightly. Output values are explicit, filtered, and safer. Recommended alternative: expose only necessary data via explicit `output` blocks in the source module, then consume them via `terraform_remote_state`'s `outputs` filter or pass them directly as input variables to downstream modules.

T7 — `remote-exec` provisioners run *after* the resource is created, but outputs are evaluated during the apply phase before the provisioner finishes, leaving the output empty. Fix: Add `depends_on = [rke2_cluster_resource]` to the output/resource, or replace `remote-exec` with a `local-exec` provisioner that polls until the kubeconfig file exists, or use a `null_resource` with `triggers` and `depends_on` on the actual cluster resource.

T8 — `tofu import` (CLI) manually maps an existing resource to config by reading state and prompting for HCL, which is error-prone. The `import` block (1.5+) is declarative, supports multiple resources, integrates with `plan`/`apply`, and automatically generates HCL from state, reducing manual drift and improving UX.

T9 — A `variable` block defines external input parameters passed into a module or root configuration. An `output` block exposes computed values from a module or root configuration to consumers. Variables flow in; outputs flow out.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a specific platform (AWS, K8s, etc.). Without `tofu init`, providers aren't downloaded or initialized, so `plan`/`apply` fails with "provider not installed" errors.

T11 — `.terraform.lock.hcl` pins exact provider versions and checksums. Committing it ensures reproducible builds, prevents supply-chain attacks from version drift, and guarantees all team members/CI use identical provider binaries.

T12 — `tofu destroy` removes all resources tracked in the state file. To target a single resource: `tofu destroy -target=<resource_type.resource_name>`. It safely removes only that resource and its dependencies.

T13 — A data source reads read-only information from external APIs without managing lifecycle. Example: `aws_ami` to dynamically fetch the latest Ubuntu image ID instead of hardcoding it or managing the image as a resource.

T14 — `variable` blocks accept external inputs; `locals` compute internal values within the configuration. Use `locals` for derived values, transformations, or avoiding repetition (e.g., combining variables, formatting strings, or conditional defaults) to keep code DRY and readable.

T15 — `lifecycle` controls resource behavior: `create_before_destroy` creates new instances before destroying old ones (zero-downtime upgrades). `prevent_destroy` adds a safeguard against accidental deletion. `ignore_changes` skips drift detection on specific attributes (e.g., manually updated tags or auto-scaling metadata).

T16 — The `moved` block declaratively maps an old resource address to a new one. OpenTofu uses it to update the state file without destroying/recreating resources, enabling safe refactoring of module structure, naming, or provider changes.

T17 — OpenTofu builds a DAG of resource dependencies. Implicit dependencies are inferred from direct references in configuration. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, reducing parallelism and increasing plan/apply time. Use sparingly only when implicit inference fails or for strict ordering requirements.

T18 — 1. Split into multiple modules/workspaces to reduce scope per run (tradeoff: increased management complexity). 2. Replace managed resources with `data` sources where possible (tradeoff: less lifecycle control). 3. Use `-refresh=false` or targeted plans for CI (tradeoff: potential stale state). 4. Optimize providers (e.g., `skip_metadata_api_check`, reduce API calls, use `parallelism` flag) (tradeoff: may miss metadata or increase memory usage).

T19 — State locking uses a backend mechanism (e.g., DynamoDB) to prevent concurrent writes. If a CI pipeline crashes, the lock persists. Break it with `tofu force-unlock <lock_id>`. Risks: race conditions, state corruption, or overwriting concurrent changes if others are actively applying.

T20: 1. Add `backend "s3"` config with `dynamodb_table` for locking. 2. Run `tofu init` (prompts to copy local state to S3). 3. Verify with `tofu state list` and check S3/DynamoDB. 4. Run `tofu plan` to confirm no drift. The local state file is safely migrated; remote state becomes the source of truth.

A1 — A playbook is a YAML file defining automation steps. A role is a reusable collection of tasks, handlers, variables, and templates. A task is a single module execution within a playbook or role.

A2 — `ansible_facts` are auto-discovered system metadata gathered during connection. Access OS family via `{{ ansible_os_family }}`.

A3 — `command` runs without shell features (safest). `shell` runs with a shell (supports pipes, `$VAR`). `raw` runs without Python, ideal for bootstrapping or initial host setup where Python isn't installed.

A4 — Idempotency means running a task multiple times yields the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run).

A5:
```yaml
- name: Install htop conditionally
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian" or ansible_os_family == "RedHat"
```

A6 — Precedence (highest to lowest): Extra vars > Command line vars > Host vars > Group vars > Role vars > Role defaults > Registered vars > `set_fact` > Inventory vars. `set_fact` overrides most except extra/command-line vars.

A7 — Use `serial: 3` in the playbook to deploy 3 nodes at a time. Group first 3 nodes in an inventory group (e.g., `rke2_first`). Use `wait_for` module to check node readiness (e.g., port 6443 or kubelet health) before proceeding to the next batch.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'my_secret' --name 'my_secret'` (outputs vault format). Alternatively, manually wrap in `!vault | <base64>` inside a vars file.

A9 — An inventory lists hosts and groups. Static inventory is a file (INI/YAML) manually maintained. Dynamic inventory is a script/API that generates inventory at runtime (e.g., cloud provider APIs), ideal for ephemeral infrastructure.

A10 — `ansible webservers -m shell -a "df -h"` or `ansible webservers -a "df -h"` (defaults to shell).

A11 — A handler is a task triggered by `notify`, running only if notified and at the end of the play. Differs from regular tasks (run immediately). Trigger via `notify: handler_name` in a task.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `private_key_file`, `host_key_checking`, `log_path`.

A13 — `register` saves a task's output to a variable. Use it in subsequent tasks via `when: var.stdout == "..."` or `debug: var={{ var }}`.

A14 — `import_tasks` is static (evaluated at parse time), faster but doesn't support `when`. `include_tasks` is dynamic (evaluated at runtime), supports conditionals. Use `include` for conditional execution, `import` for performance/static structure.

A15 — Ansible Galaxy is a repository for roles/collections. `requirements.yml` lists them. Install via `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible communicates with hosts. `ssh` = standard Linux/Unix hosts. `local` = runs on the control node. `network_cli` = Telnet/SSH for network devices. Use `ssh` for servers, `local` for control-node tasks, `network_cli` for routers/switches.

A17 — `delegate_to` runs a task on a different host. `run_once` runs it once across a group. Example: Gather disk metrics from all hosts, then write a single summary config to `localhost` using `run_once: true` + `delegate_to: localhost`.

A18 — 1. Increase `forks` (parallelism) (tradeoff: control node resource exhaustion). 2. Enable `pipelining` (reduces SSH overhead) (tradeoff: requires passwordless sudo or specific config). 3. Fact caching (Redis/Memcached) (tradeoff: stale facts if not refreshed). 4. Mitogen (async execution) (tradeoff: compatibility/maintenance overhead).

A19 — `{{ }}` outputs expressions. `{% %}` controls flow (if/for). `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check: {{ server }}
  server {{ server }};
{% endfor %}
}
```

A20 — Use `serial: 1` or `2`. Pre-task: deregister from LB (e.g., `uri` module calling LB API). Deploy task: update app version/config. Post-task: health check via `uri` module. Wrap in `block` (deploy) `rescue` (rollback to previous version/config) `always` (re-register to LB). Ensures zero-downtime and automatic rollback on failure.
