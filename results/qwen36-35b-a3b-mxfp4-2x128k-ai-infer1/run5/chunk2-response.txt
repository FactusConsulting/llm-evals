K1 — A **Deployment** manages stateless workloads with interchangeable pods (random names, no guaranteed order). A **StatefulSet** manages stateful workloads with stable network identities (hostname-0, hostname-1), stable storage bindings, and ordered deployment/scaling.

K2 — A `ClusterIP` Service creates an internal virtual IP. `kube-proxy` (via iptables or IPVS) dynamically programs node-level routing rules that map the Service IP:Port to the backend Pod IPs. Traffic hitting the ClusterIP is transparently redirected to one of the healthy pods.

K3 — A **PersistentVolume (PV)** is a cluster-level storage resource. A **PersistentVolumeClaim (PVC)** is a user's request for storage. A **StorageClass** defines a provisioning template. They relate via binding: a PVC binds to a static PV, or triggers a StorageClass to dynamically provision a new PV.

K4 — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` for ExitCode/OOMKilled events. 3. Verify resource requests/limits (CPU throttling or memory limits). 4. Check config/env/mounts for missing files or invalid arguments. 5. Inspect liveness/readiness probe failures.

K5 — CoreDNS provides internal DNS resolution for Services and Pods. If CoreDNS pods are down, internal name resolution fails (services can't resolve each other by DNS name), but direct IP-based communication and external DNS remain unaffected.

K6 — The scheduler uses **filtering** (removes ineligible nodes) then **scoring** (ranks remaining nodes). Filtering checks: taints/tolerations, node selectors, resource requests, affinity/anti-affinity, topology spread. Scoring factors include: available CPU/memory, node/pod affinity, inter-pod anti-affinity, and resource pressure.

K7 — Yes, it will schedule (3.5GB + 256Mi ≈ 3.756GB < 4GB). At runtime, if it uses 600Mi (exceeds 512Mi limit), the kubelet enforces the limit and **OOMKills** the container, triggering a restart per the pod's restart policy.

K8 — 1. External LB routes traffic to the Ingress Controller's Service (NodePort/LoadBalancer). 2. Ingress Controller reads the Ingress resource and configures NGINX routes. 3. NGINX matches host/path and forwards to the backend Service. 4. Service resolves to Endpoints (Pod IPs). 5. `kube-proxy` (iptables/IPVS) directs traffic to the target Pod. 6. Pod handles the request.

K9 — A `NetworkPolicy` restricts ingress/egress traffic to/from pods. Default behavior (no policy): all traffic allowed. When applied: only traffic matching the policy's podSelector and rules is permitted; all other traffic is explicitly denied.

K10 — `RollingUpdate` gradually replaces old pods with new ones (zero downtime). `Recreate` terminates all old pods before starting new ones (causes downtime). Choose `Recreate` for stateful apps, shared storage mounts, or when configuration changes require a full restart.

K11 — A namespace is a virtual cluster partition for resource isolation and multi-tenancy. Default namespaces: `default`, `kube-system`, `kube-public`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it reveals: 1. Pod events (scheduling, pull, start failures). 2. Resource usage vs limits. 3. Mount paths, probe status, and node affinity details.

K13 — A ConfigMap stores non-confidential configuration data. Pods consume it via: 1. Environment variables (key-value injection). 2. Volume mounts (files exposed in the container filesystem).

K14 — `ClusterIP`: internal-only virtual IP. `NodePort`: exposes the Service on a static port on each node's IP. `LoadBalancer`: provisions a cloud provider's external load balancer and exposes the Service externally.

K15 — A DaemonSet ensures one pod runs on every node (or subset via taints). Use it for node-level agents (logging, monitoring, metrics) instead of a Deployment, which scales replicas independently of node count.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Use case: Taints for dedicated GPU nodes (`gpu=true:NoSchedule` + toleration). Affinity for zone-aware scheduling (`topology.kubernetes.io/zone`).

K17 — An Operator is a custom controller that manages complex stateful applications using CRDs and custom reconciliation logic. Unlike standard controllers (which just sync simple state), Operators solve manual ops, upgrades, backups, scaling, and self-healing for stateful workloads.

K18 — etcd uses **Raft consensus** for linearizable reads/writes. If quorum is lost, the cluster becomes read-only/unwritable (cannot make progress). Recovery from 2/3 loss: restore from backup on the remaining node using `etcdctl snapshot restore ... --force-new-cluster` to bootstrap a single-node cluster.

K19 — **Role/ClusterRole** define permissions (rules). **RoleBinding/ClusterRoleBinding** bind roles to users/groups/serviceaccounts.
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: namespace: default
  name: dev-pod-reader
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` makes the resolver try 5 suffixes (e.g., `svc.cluster.local`, `cluster.local`) before querying external DNS, causing excessive queries. Fix: add `dnsConfig: options: [{name: "ndots", value: "1"}]` to the pod spec to skip internal suffixes for external domains.

D1 — `git merge` preserves history with a merge commit. `git rebase` rewrites history by replaying commits linearly. Avoid rebasing on shared/public branches or after pushing to remote to prevent history conflicts.

D2 — **TCP**: connection-oriented, reliable, ordered, flow/congestion control (HTTP, SSH). **UDP**: connectionless, unreliable, low-latency, no ordering (DNS, VoIP/streaming).

D3 — A race condition occurs when concurrent threads/processes access shared state without synchronization, yielding unpredictable results. Example: two threads incrementing a shared counter without a mutex, causing lost updates.

D4 — **Symmetric**: same key for encryption/decryption (fast). **Asymmetric**: public/private key pair (secure key exchange). In TLS: asymmetric cryptography handles the handshake/key exchange; symmetric cryptography encrypts bulk data transfer.

D5 — Each Dockerfile instruction creates a read-only image layer. Layer caching reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., dependencies before source code) to maximize cache hits and speed builds.

D6 — 1. Check backend health/endpoints (is the service actually up?). 2. Review application logs for errors/timeouts. 3. Verify resource limits (CPU throttling or OOM kills). 4. Check downstream dependencies (DB, external APIs). 5. Inspect load balancer/ingress health check failures.

D7 — CAP theorem: a distributed system can only guarantee 2 of 3: Consistency, Availability, Partition tolerance. **CP**: Banking ledger (strong consistency, may become unavailable during network partition). **AP**: DNS or social media feeds (high availability, eventual consistency).

D8 — **Horizontal scaling**: add more nodes/instances. **Vertical scaling**: increase CPU/RAM of existing node. Horizontal scaling requires: stateless services, distributed databases, message queues, and container orchestration.

D9 — An environment variable is a dynamic value passed to processes. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict syntax, key-value pairs, arrays. **YAML**: indentation-based, human-readable, supports comments. Advantage JSON: strict parsing, universal language support. Advantage YAML: readability, comments, less verbose for configs.

D11 — A REST API is an architectural style using HTTP methods, stateless requests, and resource-based URLs. **GET**: retrieve. **POST**: create. **PUT**: update/replace. **DELETE**: remove.

D12 — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes, and guarantees CI/CD environments match production.

D13 — **Compiled**: source code is translated to machine code before execution (C++, Rust). **Interpreted**: source code is executed line-by-line at runtime (Python, JavaScript). (Note: modern languages often use JIT compilation, but the execution model distinction remains.)

D14 — A **forward proxy** sits on the client side, forwarding requests to the internet (e.g., corporate proxy). A **reverse proxy** sits on the server side, routing client requests to backend servers. Examples: Nginx (SSL termination, load balancing), HAProxy (high-performance routing).

D15 — A deadlock occurs when two or more processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion. 2. Hold and wait. 3. No preemption. 4. Circular wait.

D16 — Eventual consistency guarantees that if no new updates are made, all replicas will eventually converge. Cassandra uses tunable consistency levels (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`). For read-after-write strength, use `QUORUM` or `SERIALIZABLE` with Lightweight Transactions (`cas`).

D17 — mTLS requires both client and server to authenticate via X.509 certificates. Handshake: ClientHello/ServerHello, cert exchange, mutual verification, session key derivation. Commonly used in: service meshes (Istio, Linkerd), zero-trust architectures, and internal microservice communication.

D18 — A hash table maps keys to values via a hash function. Collision resolution: **chaining** (linked lists per bucket) or **open addressing** (probing: linear/quadratic). Time complexity: average O(1) for insert/lookup/delete. Worst case O(n) if all keys hash to the same bucket.

D19 — A circuit breaker prevents cascade failures by stopping calls to a failing service. States: **Closed** (normal), **Open** (failure threshold reached, fail fast), **Half-open** (test call; success closes, failure reopens). It pairs with retry policies: retries should use exponential backoff and be capped; the circuit breaker prevents retries from overwhelming a degraded service.

D20 — **Optimistic**: assumes no conflict, checks at commit (e.g., row versioning, `UPDATE ... WHERE version = ?`). **Pessimistic**: locks resources during transaction (e.g., `SELECT ... FOR UPDATE`). Choose optimistic for high read/low write contention. Choose pessimistic for high write contention or critical consistency needs.
