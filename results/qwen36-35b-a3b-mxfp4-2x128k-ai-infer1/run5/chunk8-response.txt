CL1 — IaaS provides virtualized compute, network, and storage where you manage the OS, middleware, and applications (e.g., AWS EC2). PaaS provides a managed runtime/environment where you deploy applications without managing underlying infrastructure (e.g., Google App Engine). SaaS delivers fully managed applications where the provider handles everything (e.g., Salesforce).

CL2 — The Shared Responsibility Model divides security duties. IaaS VM: Provider secures hypervisor, physical infrastructure, and network; you secure OS, patches, applications, data, and host-level firewall. Managed Kubernetes: Provider secures the control plane, node OS, and cluster networking; you secure workloads, RBAC, secrets, and network policies. SaaS (M365): Provider secures the application, infrastructure, and compliance; you secure user identities, data classification, access policies, and endpoint compliance.

CL3 — A VPC is an isolated virtual network. A subnet partitions the VPC (public/private). Security Groups (SG) are stateful instance-level firewalls (allow rules only; return traffic auto-allowed). Network ACLs (NACL) are stateless subnet-level firewalls (allow/deny rules evaluated in order). Layering: NACLs filter traffic entering/leaving a subnet first, then SGs filter traffic targeting individual resources. Stateful (SG) tracks connection state; Stateless (NACL) requires explicit rules for both directions.

CL4 — A landing zone is a pre-configured, secure multi-account foundation. Organizational Units (OUs) logically group accounts (by environment, workload, or function). Guardrails are automated compliance/security policies (e.g., SCPs, Azure Policy) enforcing baseline controls. Shared networking uses Transit Gateway or Azure Hub-and-Spoke to centralize VPC peering, on-prem connectivity, and service endpoints. Centralized logging aggregates audit trails to an immutable, secure bucket/account. Single-account approaches fail due to high blast radius, permission sprawl, billing opacity, compliance isolation violations, and inability to separate environments.

CL5 — IaC is declarative/programmatic infrastructure provisioning. Terraform/OpenTofu: State-driven, broad provider support, ideal for multi-cloud or general-purpose infra. Pulumi: General-purpose languages (TS/Python), imperative, best for complex logic or teams already using those languages. CloudFormation/Bicep: AWS-native, tightly integrated, fastest for AWS-only shops. Crossplane: Kubernetes-native, manages cloud resources via CRDs, ideal for GitOps/K8s-centric teams wanting a unified control plane.

CL6 — HPA scales pods based on CPU/memory/custom metrics. VPA adjusts pod resource requests/limits. Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external event sources (queues, HTTP, DB, cron). Use KEDA over HPA when scaling is driven by event throughput (e.g., RabbitMQ queue depth, Kafka lag) rather than static resource utilization.

CL7 — Define RPO/RTO (e.g., RPO=15min, RTO=1hr). Active-passive: Primary handles traffic; secondary stands by. DNS failover (Route53/Traffic Manager) with low TTL directs traffic. DB replication: Async (lower latency, higher RPO) vs sync (zero RPO, higher latency/cost). Externalize state to managed DB/cache. Cost: Active-active doubles infra; active-passive saves ~40-60%. Pilot light: Core infra running at minimal capacity. Warm standby: Full infra running at reduced capacity. Multi-site active-active: Full capacity in both regions, load-balanced.

CL8 — GitOps uses Git as the single source of truth; controllers sync cluster state to manifests. ArgoCD: UI-focused, push/pull, strong audit trail. FluxCD: Git-native, pull-only, tightly integrated with Git providers. Secrets: SealedSecrets (encrypted in Git), External Secrets Operator (syncs from cloud/Vault), Vault (dynamic secrets). Drift: Controllers detect manual changes and automatically revert to Git state or alert; manual overrides are overwritten on next sync.

CL9 — Use a StatefulSet for stable network IDs and persistent storage. PV/PVC with `local` storage class requires node affinity. Headless service (`clusterIP: None`) provides stable DNS per pod. Init containers handle config prep/migration. ConfigMaps/Secrets mounted as volumes at fixed paths. PDB (`minAvailable`/`maxUnavailable`) ensures quorum during node drains. Sticky sessions via headless DNS or external LB. Ordered startup via `podManagementPolicy: OrderedReady`.

CL10 — Service Account: K8s-native pod identity. Workload Identity (GCP/AWS): Maps K8s SA to cloud IAM role without keys. IRSA: AWS OIDC-based role assumption via K8s SA. Mounting static credentials is bad: hard to rotate, long-lived, high blast radius, violates least privilege. Workload identity federation uses short-lived, OIDC-backed tokens scoped to specific workloads, eliminating static keys.

CL11 — Object storage (S3/Blob): Unstructured data, HTTP API, ~11-12 nines durability, eventual consistency. Use for backups, media, logs. Block storage (EBS/Disk): Low-latency, VM-attached, formatted filesystem. Use for OS, databases, apps. File storage (EFS/Azure Files): NFS/SMB, shared across VMs. Use for shared configs, home dirs. Availability: Object high, Block zonal, File regional.

CL12 — Zero-trust K8s: Default-deny network policies, service mesh (mTLS), pod identity (Workload ID/IRSA), admission controllers (OPA/Kyverno), image signing (Cosign), runtime security (Falco), external secrets. Differs from perimeter model: No implicit trust based on network location; every request is authenticated, authorized, and encrypted regardless of origin.

CL13 — CDN distributes edge nodes to cache content closer to users. DNS routes requests to the nearest edge, which serves cached responses or fetches from origin. Services: CloudFront, Fastly. Use CDN for high global traffic, static assets, DDoS mitigation, TLS termination, and origin load reduction. Serve directly from origin only for low traffic, highly dynamic/personalized content, or strict data residency.

CL14 — Region: Geographic area with multiple AZs. AZ: Isolated data center(s) with independent power/network. Multi-AZ deployment ensures high availability against single datacenter failure. Zonal resources (EBS, EC2) tie to one AZ. Regional resources (ALB, RDS Multi-AZ, S3) span multiple AZs.

CL15 — Managed DB (RDS/Cloud SQL) handles provisioning, patching, backups, replication, monitoring, failover, and storage scaling. Self-hosted on VM requires you to manage OS, DB software, patches, backups, replication, tuning, and HA. Managed reduces operational overhead but limits low-level access and may increase cost.

CL16 — IAM Users: Human/service identities. Groups: Collections for policy assignment. Roles: Temporary credentials for services, cross-account, or workloads. Policies: JSON permission documents. Least privilege: Grant only necessary permissions. Apply via scoped policies, avoid `*`, use IAM Access Analyzer, enforce MFA, prefer roles over long-lived keys, and audit regularly.

CL17 — Serverless: Event-driven, managed compute (no server mgmt). Lambda/Functions/GCF differ in runtime support, cold start behavior, pricing, and ecosystem. Cold starts: Initialization delay when runtime/container spins up; impacts latency-sensitive apps. Poor fit: Long-running processes (>15min), sustained high CPU/memory, strict stateful requirements, or predictable high-throughput where provisioned capacity is cheaper.

CL18 — Ingress resource: K8s standard, relies on controller, TLS at controller. Gateway API: Modern standard separating traffic routing (Gateway) from backend rules (HTTPRoute), better RBAC, multi-tenant. LB annotations: Cloud LB directly exposing services, TLS at LB. Mesh ingress: Service mesh edge proxy, mTLS termination. TLS terminates at edge proxy (Ingress/LB) or sidecar (Mesh). Use Gateway API for multi-tenant routing, fine-grained RBAC, standardized HTTP/TCP/UDP routing, and future-proofing.

CL19 — RI/SP: 1-3yr commitments for 30-72% discount vs on-demand. Spot: Up to 90% off, interruptible, for fault-tolerant workloads. Right-sizing: Match instance type to actual CPU/mem usage. Storage tiering: Intelligent-Tiering, Glacier for cold data. Idle detection: CloudWatch/Cloud Asset Inventory for unattached volumes, idle LBs. FinOps: Cross-functional team, tagging, budget alerts, monthly reviews. Showback/chargeback: Allocate costs by team/project via tags. Tools: Cost Explorer, Kubecost, OpenCost. Process: Tag enforcement, automated scaling, spot fleet strategies, cost reviews.

CL20 — Multi-cloud strategy: Abstraction via K8s, Terraform, service mesh. K8s runtime (EKS/AKS) ensures consistent deployment. Terraform provides provider-agnostic IaC (note provider-specific resource limits). Networking: Cloud VPN/Interconnect. Identity: OIDC federation, centralized IAM proxy. Trade-offs: Increased complexity, networking latency/cost, duplicated tooling, skill fragmentation. Justified for regulatory/data residency mandates, vendor risk mitigation, or best-of-breed needs. Unnecessary when single-cloud capabilities suffice, team size/skills are limited, or complexity outweighs benefits.

OT1 — Purdue Model (ISA-95) hierarchy: Level 0: Physical process (sensors/actuators). Level 1: Basic control (PLCs, RTUs). Level 2: Supervisory control (SCADA, HMIs). Level 3: Site operations (historians, MES). Level 4: Enterprise (ERP, business planning). Level 5: Business network (corporate IT).

OT2 — IT networks prioritize confidentiality/integrity, use standardized OS, and apply frequent patches. OT networks prioritize availability/safety, run legacy OS, require deterministic latency, and face physical process impact. IT patching fails in OT due to unpatchable legacy firmware, strict change windows, validation requirements, and risk of disrupting real-time control or causing safety hazards.

OT3 — IDMZ is a segmented network between IT (L4) and OT (L0-2). Allows controlled data exchange (e.g., OPC UA, MQTT) via application gateways. Traffic: IT→IDMZ (downstream commands/reports), IDMZ→OT (upstream process data). Direct L4→L1 bypasses segmentation, exposes control networks to IT threats, enables lateral movement, and risks process disruption/safety incidents.

OT4 — 1. Modbus TCP: L2/L3, legacy PLC/RTU communication. 2. OPC UA: L2/L3, secure, platform-independent, modern standard. 3. EtherNet/IP (CIP): L2/L3, Allen-Bradley dominant, industrial Ethernet. 4. PROFINET: L2/L3, Siemens dominant, real-time Ethernet. 5. MQTT: L3/L4, lightweight publish/subscribe, edge-to-cloud.

OT5 — Data diode: Hardware-enforced unidirectional communication (physical/optical). Firewall: Bidirectional, stateful inspection. Use diode for strict regulatory compliance or critical infrastructure requiring guaranteed one-way data flow (e.g., SCADA to cloud). Limitation: Cannot allow return traffic (acknowledgments/commands), requiring application-level workarounds for bidirectional needs.

OT6 — Flow: PLCs/RTUs → Historian (L3) → OPC UA Server → Edge Gateway (translation/buffering) → MQTT Broker (TLS) → Cloud Ingestion (Kafka/EventBridge) → Analytics. Security boundaries: IDMZ between OT and edge, TLS/mTLS for all comms, firewall at edge-cloud boundary, zero-trust cloud access, encrypted data at rest/transit.

OT7 — IEC 62443: Zones = logical/physical groupings with similar security requirements. Conduits = communication paths between zones. Zone definition: Based on function, risk, and security level (SL). Design: Zone 1: SIS (SL 4, air-gapped/isolated). Zone 2: PLCs/BPCS (SL 3, controlled access). Zone 3: SCADA/Historian (SL 3, IDMZ boundary). Zone 4: Engineering (SL 2, jump hosts, MFA). Zone 5: Corporate (SL 1). Conduits: Strictly controlled, firewalled, unidirectional where possible, monitored.

OT8 — Segmentation: VLANs per production line, utility, engineering. Firewall placement: Between VLANs, at OT/IT boundary, at edge. Switch architecture: Managed L3 switches with ACLs, port security, STP. Remote access: Secure jump host, MFA, session recording, time-bound vendor accounts, out-of-band management. Transition: Phased rollout, parallel run, maintenance windows, rollback plan, vendor coordination, non-disruptive VLAN migration.

OT9 — SIS: Independent system for emergency shutdown/safety (IEC 61511 defines lifecycle, SIL requirements). BPCS: Normal process control. SIS must be isolated/air-gapped to prevent IT/OT cyber threats from compromising safety functions. Ransomware on SIS could disable safety interlocks, cause uncontrolled release, equipment damage, or loss of life. Physical isolation ensures safety remains intact during cyber incidents.

OT10 — PLC: Discrete control, deterministic, line/process-specific. DCS: Integrated control for continuous processes, centralized architecture, high reliability. SCADA: Supervisory monitoring/control, geographically dispersed, data aggregation. Use PLC for discrete manufacturing, DCS for continuous/process industries, SCADA for utilities/pipelines. They coexist: PLCs/DCS handle control, SCADA provides oversight.

OT11 — Remote access: Secure jump host/bastion, MFA, session recording, vendor-specific time-limited accounts, out-of-band network. Direct RDP to HMI from corporate is unacceptable: exposes OT to IT threats, bypasses segmentation, lacks auditability, enables lateral movement, violates IEC 62443.

OT12 — Detection/response: Deploy passive IDS (Nozomi/Claroty) for anomaly detection. Maintain real-time asset inventory. IR steps: Isolate compromised L3 segments, preserve logs, assess impact on L0-2, coordinate with control room for safe manual override if needed. Operator role: Monitor physical process, execute safety procedures, communicate status, do not rely on compromised digital systems. Ensure safe operations via manual controls, redundant systems, and phased isolation.

OT13 — HMI: Operator interface for monitoring/control (displays process data, alarms, controls). Differs from engineering workstation: HMI is for operators (run-time), engineering workstation is for programmers/configurers (offline/online tuning, logic editing, firmware updates).

OT14 — Historian: Time-series database for process data. Plant historian (L3): Stores real-time process data, alarms, events for local monitoring, compliance, optimization. Enterprise historian (L4): Aggregates plant data for business analytics, ERP integration, cross-site reporting. Critical for trend analysis, root cause, regulatory compliance, predictive maintenance.

OT15 — Ladder logic: Graphical programming language mimicking relay circuits. Executed by PLCs. Dominant due to familiarity, low learning curve, deterministic execution, backward compatibility, extensive legacy codebase, and safety certification.

OT16 — RTU: Remote Terminal Unit, designed for harsh environments, long-distance communication, serial/SCADA protocols, often battery/solar powered. Differs from PLC: RTU optimized for telemetry/remote sites, PLC for local control. Deploy RTUs in pipelines, water distribution, wind farms, remote mining, where distance and harsh conditions prevail.

OT17 — Analog signals: Continuous voltage/current representing process variable. Digital: Discrete on/off or binary. 4-20mA preferred over 0-20mA because: 4mA "live zero" indicates wire break/failure (0mA = fault), provides power to 2-wire transmitters, reduces noise susceptibility, and is industry standard.

OT18 — Asset inventory: Complete list of OT hardware/software/firmware. Foundation because you can't secure what you don't know, enabling vulnerability management, patching, and compliance. Tools: Passive monitoring (packet capture, protocol analysis), active scanning (ping, port scan). Active scanning dangerous: Can crash legacy devices, trigger safety interlocks, cause network congestion, or disrupt real-time control.

OT19 — MITRE ATT&CK for ICS tactics: Reconnaissance, Resource Development, Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command & Control, Impact. Example techniques: Initial Access (Supply Chain Compromise), Execution (Command and Scripting Interpreter), Impact (Inhibit Response Function). Differs from enterprise: Focuses on physical process impact, safety, legacy protocols, OT-specific tools. Usage: Map current defenses to tactics, identify gaps (e.g., no passive monitoring for C2), prioritize controls.

OT20 — Converged SOC: Log collection: Passive taps, OPC UA/MQTT forwarders, no active polling. SIEM: Correlate IT/OT logs, tag OT assets. OT rules: Protocol-specific anomalies, unexpected commands, firmware changes. Triage: OT engineers validate process impact, IT analysts handle threat intel. Staffing: Hybrid team (IT security + OT engineers). False positives: Tune rules to OT baselines, use passive data only. Firmware change alert: Isolate affected PLC, verify against change management, check for unauthorized access, restore from known-good image if compromised, report to safety/engineering, update inventory.
