K1 — A **Deployment** manages stateless workloads with interchangeable pods; pods have random names and no guaranteed startup order. A **StatefulSet** manages stateful workloads with stable, unique network identities (e.g., `pod-0`, `pod-1`), ordered deployment/scaling, and stable storage bindings.

K2 — A `ClusterIP` Service creates an internal virtual IP. `kube-proxy` watches Service objects and programs node-level `iptables` or `IPVS` rules that load-balance traffic hitting the ClusterIP:Port to the backend pod IPs:Ports.

K3 — **PersistentVolume (PV)**: cluster-provisioned storage resource (static or dynamic). **PersistentVolumeClaim (PVC)**: user request for storage. **StorageClass**: template for dynamic PV provisioning. Relation: A PVC binds to a PV (or triggers a StorageClass to provision one). Once bound, the PVC acts as the pod's storage mount point.

K4 — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` for Exit Codes, OOMKilled events, or probe failures. 3. Verify resource requests/limits vs node capacity. 4. Check app dependencies, config/env vars, and startup scripts for misconfiguration or missing binaries.

K5 — CoreDNS provides internal DNS resolution for `Service` and `Pod` names. If CoreDNS pods are down, internal name resolution fails (services can't find each other by DNS), though direct IP communication and external DNS remain unaffected.

K6 — The scheduler uses **filtering** (removes nodes failing constraints) then **scoring** (ranks remaining nodes). Factors: 1. Resource availability (CPU/memory requests vs capacity). 2. Taints/tolerations and node selectors. 3. Node affinity/anti-affinity and topology spread constraints. 4. Resource pressure (e.g., disk pressure, memory pressure).

K7 — Yes, it will schedule: 3.5GB + 256Mi ≈ 3.756GB < 4GB. At runtime, if the container uses 600Mi, the cgroup memory limit (512Mi) is enforced. The kernel OOM killer will terminate the container (`OOMKilled`), and Kubernetes will restart it per the restart policy.

K8 — Client → External LB (routes to Ingress Controller IP) → Ingress Controller (NGINX) parses Ingress resource → matches host/path → forwards to Kubernetes Service → Service resolves to pod IPs via Endpoints → `kube-proxy` (iptables/IPVS) redirects traffic to pod IP → pod receives request.

K9 — A `NetworkPolicy` restricts ingress/egress traffic at the pod level. Default behavior (no policy): all traffic allowed. When applied: only traffic matching the policy's `ingress`/`egress` rules is permitted; all other traffic is explicitly denied.

K10 — `RollingUpdate` gradually replaces old pods with new ones (zero downtime). `Recreate` terminates all old pods before creating new ones (downtime). Choose `Recreate` for stateful apps requiring exclusive access to shared resources, or when configuration changes mandate a full restart.

K11 — A namespace is a logical cluster partition for resource isolation and multi-tenancy. Default namespaces: `default`, `kube-system`, `kube-public`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it reveals: 1. Pod events (scheduling, probe failures, OOMKilled). 2. Resource requests/limits and volume mounts. 3. Node assignment, pod IP, and environment variables.

K13 — A `ConfigMap` stores non-sensitive configuration data. Pods consume it via: 1. Environment variables (`envFrom` or `env`). 2. Volume mounts (files injected into the container filesystem).

K14 — `ClusterIP`: internal-only virtual IP. `NodePort`: exposes the service on a static port on each node's IP. `LoadBalancer`: provisions a cloud provider LB, exposing the service externally with a public IP.

K15 — A `DaemonSet` ensures one pod runs on every node (or subset via taints/tolerations). Use it for node-level daemons: logging agents, monitoring collectors, network plugins, or storage drivers. Deployments run a fixed replica count regardless of node count.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to be scheduled on tainted nodes. **Node affinity** attracts pods to nodes. Taints/tolerations are node-driven (repel/attract), affinity is pod-driven. Use case taints: GPU nodes (`gpu=true:NoSchedule`) with toleration on ML pods. Use case affinity: schedule on specific AZs for latency-sensitive workloads.

K17 — An Operator is a custom controller that manages complex stateful applications using CRDs and custom reconciliation logic. Unlike standard controllers (which only manage replica counts), Operators handle upgrades, backups, scaling, and self-healing. It solves manual operational overhead and state drift for complex apps.

K18 — etcd uses Raft consensus providing linearizable reads/writes. If quorum is lost, the cluster becomes read-only. Recovery from 2/3 node loss: restore the latest snapshot + WAL from the surviving node, then rejoin new etcd nodes to restore quorum. If no nodes survive, restore from offline backup.

K19 — RBAC uses Roles/ClusterRoles (define permissions) bound to subjects via RoleBindings/ClusterRoleBindings.
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev-ns
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: dev-ns
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` causes Kubernetes to query 5 parent domains before using search paths, generating excessive DNS traffic. Fix: add `dnsConfig: options: [{name: "ndots", value: "2"}]` to the pod spec, or adjust `search` domains to reduce resolution depth.

D1 — `merge` creates a merge commit, preserving full branch history. `rebase` rewrites commits onto the target branch, creating a linear history. Avoid rebasing on shared/public branches or after pushing to remote to prevent history conflicts.

D2 — **TCP**: connection-oriented, reliable, ordered, flow/congestion control. (HTTP, SMTP). **UDP**: connectionless, unreliable, low-latency, no ordering. (DNS, VoIP, real-time gaming).

D3 — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to unpredictable results. Example: two threads incrementing a shared counter without a mutex, resulting in lost updates.

D4 — **Symmetric**: single key for encryption/decryption (fast). **Asymmetric**: public/private key pair (slower, enables secure key exchange). TLS uses asymmetric encryption for the handshake/key exchange, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates a read-only image layer. Layer caching speeds builds: Docker reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., copy dependencies first, then source code) to maximize cache hits.

D6 — 1. Check service readiness/liveness probes. 2. Verify upstream dependencies (DB, cache, other services). 3. Check resource limits/OOM events. 4. Inspect load balancer/ingress health checks and connection limits. 5. Review application logs for timeouts or errors.

D7 — CAP theorem: a distributed system can only guarantee two of Consistency, Availability, Partition tolerance. **CP**: distributed SQL (CockroachDB, HBase) – prioritizes consistency, may block during network partitions. **AP**: Cassandra, DynamoDB – prioritizes availability, may serve stale data during partitions.

D8 — **Horizontal**: add more nodes/instances. **Vertical**: increase CPU/RAM of existing node. Horizontal scaling requires: stateless services, externalized state (DB/cache), load balancing, microservices architecture, and data partitioning/sharding.

D9 — An environment variable is a dynamic key-value pair passed to processes. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict syntax, key-value pairs, arrays. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: strict parsing, universal API support. YAML advantage: readability, less boilerplate, better for config files.

D11 — A REST API is an architectural style using HTTP methods. **GET**: retrieve resource. **POST**: create new resource. **PUT**: replace/update resource. **DELETE**: remove resource.

D12 — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3`). Ensures reproducible builds, prevents unexpected breaking changes, and guarantees CI/CD environments match production.

D13 — **Compiled**: source code is translated to machine code before execution (C++, Rust). **Interpreted**: source code is executed line-by-line at runtime (Python, JavaScript). (Note: modern languages often use JIT/AOT compilation, but this is the foundational distinction.)

D14 — A **forward proxy** sits on the client side, routing outbound traffic. A **reverse proxy** sits on the server side, routing inbound traffic to backend servers. Examples: Nginx (load balancing, caching, SSL termination), HAProxy (high-performance TCP/HTTP routing).

D15 — A deadlock occurs when two+ processes wait indefinitely for each other's locks. Coffman conditions: 1. Mutual exclusion. 2. Hold and wait. 3. No preemption. 4. Circular wait.

D16 — Eventual consistency guarantees that, without new updates, all reads will eventually return the last written value. Cassandra uses vector clocks and tunable consistency levels (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`). Read-after-write is typically enforced via `QUORUM`/`ALL` or Linearizable Write-Tombstones (LWT/CAS).

D17 — mTLS requires both client and server to present and validate certificates. Handshake: ClientHello → ServerHello + cert → Client verifies server cert → Server verifies client cert → session keys derived. Used in: service meshes (Istio, Linkerd), zero-trust architectures, and internal microservice communication.

D18 — A hash table maps keys to values via a hash function → array index. Collision resolution: **chaining** (linked lists per bucket) or **open addressing** (probing: linear, quadratic, double hashing). Time complexity: average O(1) for insert/lookup/delete; worst O(n) if all keys collide.

D19 — A circuit breaker prevents cascade failures by stopping calls to a failing service. States: **Closed** (normal), **Open** (failure threshold reached, fail fast), **Half-open** (test call; success closes, failure reopens). Relates to retries: circuit breakers should wrap retry policies; retrying a failing service amplifies load, so the breaker opens to halt retries and allow recovery.

D20 — **Optimistic**: assumes no conflict, validates at commit (e.g., row versioning, application-level version checks). **Pessimistic**: locks resources during transaction (e.g., `SELECT ... FOR UPDATE`, advisory locks). Choose optimistic for high read/low write contention. Choose pessimistic for high write contention or critical consistency requirements.
