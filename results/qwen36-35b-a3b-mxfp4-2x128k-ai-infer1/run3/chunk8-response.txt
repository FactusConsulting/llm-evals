CL1 — IaaS provides virtualized compute, network, and storage where you manage the OS, middleware, and applications. PaaS provides a managed runtime/environment where you manage only your applications and data. SaaS delivers complete applications where the provider manages everything. Examples: AWS EC2 (IaaS), Google App Engine (PaaS), Salesforce (SaaS).

CL2 — The Shared Responsibility Model divides security duties. IaaS VM: Provider secures physical infra, hypervisor, and network; you secure OS, patches, apps, data, and host-level config. Managed Kubernetes: Provider secures the control plane, node OS, and cluster networking; you secure workloads, RBAC, network policies, and secrets. SaaS (M365): Provider secures the app, infrastructure, and compliance; you manage user access, data classification, DLP, and device compliance.

CL3 — VPC is an isolated virtual network. Subnets partition the VPC into public/private CIDR blocks. Security Groups (SG) are stateful, instance-level firewalls that only allow rules. Network ACLs (NACL) are stateless, subnet-level firewalls that allow/deny rules. They layer: NACLs filter traffic at the subnet boundary, SGs filter at the instance boundary. Stateful (SG) automatically allows return traffic; stateless (NACL) requires explicit rules for both directions.

CL4 — A landing zone is a pre-configured, secure multi-account foundation. Organizational Units (OUs) logically group accounts (e.g., by environment or team). Guardrails are automated policy controls (e.g., SCPs) enforcing compliance. Shared networking uses Transit Gateway or Azure Hub-and-Spoke for centralized VPC peering, on-prem connectivity, and traffic inspection. Centralized logging aggregates logs to a dedicated account/service. Single-account is problematic due to high blast radius, permission sprawl, billing opacity, compliance isolation failures, and inability to separate environments.

CL5 — IaC is declarative/programmatic infrastructure provisioning. Terraform/OpenTofu: State-driven, HCL, broad provider support; ideal for multi-cloud or general-purpose infra. Pulumi: General-purpose languages (TS/Python), state-driven; ideal for teams wanting full programming power. CloudFormation/Bicep: AWS-native, tightly integrated; ideal for AWS-only shops. Crossplane: Kubernetes-native, manages cloud resources via CRDs; ideal for GitOps/K8s-centric teams wanting a unified control plane.

CL6 — HPA scales pods based on CPU/memory/custom metrics. VPA adjusts pod resource requests/limits (requires restart). Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external event sources (queues, HTTP, DB, cron). Use KEDA over HPA when scaling is driven by event-driven workloads (e.g., Kafka queue depth, HTTP request rate) rather than static resource utilization.

CL7 — Define RPO/RTO (e.g., RPO=1h, RTO=4h). Active-passive: Primary handles traffic, secondary stands by; failover via DNS (Route53/Traffic Manager) with low TTL. DB replication: Async (lower latency, higher RPO) vs sync (zero RPO, higher latency/cost). State: Externalize to managed services (Redis/ElastiCache, S3). Cost: Active-active doubles infra; active-passive saves ~40-60%. Pilot light: Core infra running, scaled up on failover. Warm standby: Scaled-down but ready environment. Multi-site active-active: Full traffic split, zero downtime, highest cost/complexity.

CL8 — GitOps uses Git as the single source of truth; controllers sync cluster state to match. ArgoCD: UI-focused, push/pull, strong UX. FluxCD: Git-native, pull-only, tightly integrated with Git providers. Secrets: SealedSecrets (encrypted in Git), External Secrets Operator (syncs from Vault/AWS SM), Vault (dynamic secrets, mTLS). Drift: Controllers detect manual changes, auto-revert to Git state, or alert; manual overrides are overwritten on next sync.

CL9 — Use a StatefulSet for stable identity/network. PV/PVC with a `local` storage class for low-latency disk. Headless service (`clusterIP: None`) for stable DNS per pod. Init containers for config prep/mounts. ConfigMaps as volume mounts for baked-in configs. PDB to ensure minimum available pods during disruptions. Use `volumeClaimTemplates` for PVCs and `podAntiAffinity` for redundancy.

CL10 — Service Account: K8s-native pod identity. Workload Identity: Maps K8s SA to cloud IAM role without keys (GCP/AWS). IRSA (AWS): Maps K8s SA to IAM role via OIDC. Mounting static cloud credentials is bad: hard to rotate, high blast radius, violates least privilege, easily exfiltrated. Workload identity federation solves this by using short-lived, OIDC-backed tokens scoped to specific roles, eliminating static keys.

CL11 — Object storage (S3/Blob): Unstructured data, HTTP API, high durability (~11-12 nines), eventual consistency. Use for backups, media, logs. Block storage (EBS/Disk): Raw volumes, attached to VMs, low latency, high IOPS. Use for OS, databases, apps. File storage (EFS/Azure Files): NFS/SMB, shared access, scalable. Use for shared configs, home dirs, legacy apps. Durability: Object ~11-12 nines, Block/File ~99.999999999%. Availability: Object high, Block zonal, File regional.

CL12 — Zero-trust K8s: Network policies restrict pod-to-pod traffic. Service mesh (Istio/Linkerd) enforces mTLS and policy. Pod identity (Workload ID/IRSA) binds pods to cloud IAM. Admission controllers (OPA/Kyverno) enforce policies at deploy time. Image signing (Cosign/Notary) + verification prevents untrusted images. Runtime security (Falco) detects anomalous behavior. Secrets: External Secrets/Vault. Differs from perimeter security by assuming breach, verifying every request, and enforcing micro-segmentation rather than trusting internal network traffic.

CL13 — CDN is a distributed edge network that caches content closer to users. DNS routes requests to the nearest edge node, which serves cached assets and fetches from origin on cache miss. Services: CloudFront, Fastly. Use CDN for global static/dynamic content to reduce origin load, improve latency, and mitigate DDoS. Use origin only for highly dynamic, personalized, or low-traffic content where cache overhead isn't justified.

CL14 — Region is a geographic area with multiple AZs. AZ is an isolated data center or group with independent power/network. Deploy across multiple AZs for high availability and fault tolerance against single-site failure. Zonal resources are tied to one AZ (EBS, most VMs). Regional resources span multiple AZs (ALB, Route53, RDS Multi-AZ, S3).

CL15 — Managed DB services (RDS/Cloud SQL) handle provisioning, patching, backups, replication, monitoring, failover, and storage scaling. Self-hosting on a VM requires manual OS/db patching, backup scripting, replication setup, HA configuration, and capacity planning. Managed services reduce operational overhead and improve reliability.

CL16 — IAM: Users (identities), Groups (collections), Roles (assumable identities), Policies (JSON permissions). Least privilege means granting only necessary permissions. Apply via scoped policies, avoid `*`, use roles over users, enable MFA, audit with access analyzers, and implement just-in-time access.

CL17 — Serverless is event-driven, managed compute without provisioning servers. Lambda/Functions/GCF share core models but differ in runtime support, cold start behavior, and ecosystem integration. Cold starts are initialization delays when a function spins up a container; they matter for latency-sensitive apps. Poor fit: Long-running processes, stateful workloads, predictable high-throughput (reserved instances cheaper), or when vendor lock-in/runtime constraints are unacceptable.

CL18 — Ingress resource: K8s standard, relies on a controller. Gateway API: Modern, multi-protocol, fine-grained control. LB annotations: Cloud-specific, direct to cloud LB. Mesh ingress: Service mesh, mTLS, advanced routing. TLS termination: Ingress/LB at edge, mesh at sidecar. Use Gateway API over Ingress for multi-protocol support (HTTP/gRPC/TCP), better RBAC, and standardized multi-cloud deployments.

CL19 — Cost optimization ($80k/mo): RI/SP: Commit to usage for 1-3yr discounts (60-70%). Spot/Preemptible: Up to 90% off for fault-tolerant workloads. Right-sizing: Match instance type to actual CPU/mem usage. Storage tiering: Move cold data to Glacier/Archive. Idle detection: Find unattached volumes, unused IPs, idle LBs. FinOps: Cross-functional team, cloud cost tools (AWS Cost Explorer, CloudHealth, Kubecost). Showback/chargeback: Tag resources, allocate costs by team/project, monthly reviews. Tools: Kubecost, CloudHealth, native cost analyzers, custom tagging policies.

CL20 — Multi-cloud strategy: Abstraction via Kubernetes, Terraform, and service mesh. K8s provides a common runtime. Terraform enables provider-agnostic IaC. Networking uses Cloud VPN/Interconnect. Identity uses OIDC federation and centralized IAM proxies. Trade-offs: Increased complexity, data egress costs, fragmented tooling, and operational overhead vs theoretical flexibility. Justified when regulatory/data sovereignty requires it or specific cloud services are critical. Unnecessary when single-cloud maturity, cost, and simplicity outweigh flexibility needs.

OT1 — Purdue Model (ISA-95) is a hierarchy for industrial automation. Level 0: Physical process (sensors/actuators). Level 1: Basic control (PLCs/RTUs). Level 2: Supervisory control (SCADA/HMI). Level 3: Site operations (historian, MES). Level 4: Enterprise (ERP, business planning). Level 5: Business network (corporate IT).

OT2 — IT networks prioritize confidentiality/integrity, high bandwidth, frequent updates, and standardized OS. OT networks prioritize availability/safety, deterministic latency, long lifecycles, and proprietary OS. IT patching causes downtime, breaks deterministic timing, and can introduce instability, violating OT safety/availability requirements.

OT3 — IDMZ is a segmented network between IT (L4) and OT (L1-3). It allows controlled data exchange (e.g., OPC UA, MQTT) via application-level gateways. Traffic: Unidirectional or strictly filtered bidirectional (IT→OT for commands only when necessary, OT→IT for data). Direct L4→L1 is dangerous because IT threats (ransomware, malware) can directly compromise safety-critical control logic, causing physical damage or injury.

OT4 — Modbus TCP: L2/L3, legacy PLC/RTU communication, unencrypted. OPC UA: L2/L3, modern secure data exchange, supports information modeling. EtherNet/IP (CIP): L2/L3, industrial Ethernet, widely used in automation. PROFINET: L2, real-time industrial Ethernet, deterministic. MQTT: L3/L4, lightweight publish/subscribe, used for edge-to-cloud telemetry.

OT5 — Data diode is a hardware-enforced unidirectional network link. Firewall is bidirectional, inspecting/controlling traffic both ways. Use a diode when strict one-way data flow is required (e.g., OT→IT telemetry) to guarantee no malicious return traffic. Limitation: Cannot support bidirectional protocols, remote control, or dynamic responses; only suitable for data extraction, not command/control.

OT6 — Data flow: PLCs/RTUs → Historian (L3) → OPC UA Server → Edge Gateway (protocol translation, buffering) → MQTT Broker (secure TLS) → Cloud Ingestion (Kafka/EventBridge) → Analytics. Security boundaries: IDMZ between L3/L4, TLS/mTLS at edge, network segmentation, firewall at cloud ingress, zero-trust access for cloud services.

OT7 — IEC 62443: Zones are logical/physical groupings with similar security requirements. Conduits are communication paths between zones with defined security levels. Zone design: Corporate (L4, SL 2), Engineering (L3, SL 3), SCADA/PLC (L2, SL 3), SIS (L1, SL 4). Conduits: Corporate↔Engineering (firewall, SL 2), Engineering↔SCADA (firewall, SL 3), SCADA↔PLC (firewall/switch, SL 3), PLC↔SIS (data diode or strict firewall, SL 4). Enforce least privilege and audit logging at each conduit.

OT8 — Segmentation: VLANs per production line, HMI group, SCADA, historian. Firewalls at VLAN boundaries and IDMZ. Switches: Managed Layer 3 with ACLs, port security, STP. Remote access: Jump host in IDMZ, MFA, session recording, time-limited vendor accounts, no direct L1/L2 access. Transition: Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, validate with engineering before cutover.

OT9 — SIS is an independent safety system that triggers a safe state on hazardous conditions (IEC 61511 defines SIL requirements). BPCS handles normal process control. SIS must be isolated/air-gapped to prevent IT/OT cyber threats from compromising safety functions. Ransomware on SIS could disable safety interlocks, causing catastrophic physical failure, environmental damage, or loss of life.

OT10 — PLC: Discrete control for specific machines/lines. DCS: Integrated control for continuous processes (chemical, oil/gas). SCADA: Supervisory monitoring/control across geographically dispersed assets. Use PLC for discrete, DCS for continuous, SCADA for wide-area monitoring. They coexist: PLCs/DCS handle control, SCADA provides HMI/historian/remote oversight.

OT11 — Remote access: Jump host in IDMZ, MFA, session recording, vendor-specific time-limited accounts, network segmentation. RDP directly to HMI from corp is unacceptable because it bypasses segmentation, exposes HMI to corporate malware, lacks audit controls, and violates IEC 62443 zone/conduit requirements.

OT12 — Detection/response: Deploy passive IDS (e.g., Nozomi, Claroty) in OT, maintain asset inventory, isolate compromised L3 segments, engage IR team. Coordinate with control room: Verify physical safety, switch to manual/local control if needed, do not disrupt critical processes. Operator role: Monitor physical parameters, execute emergency procedures, communicate status, never rely solely on compromised digital systems. Prioritize physical safety over cyber containment.

OT13 — HMI is an operator interface for monitoring/controlling processes. Role: Real-time visualization, alarm management, manual overrides. Differs from engineering workstation: HMI is for operators (run-time), engineering workstation is for programmers (offline/online configuration, logic editing, diagnostics).

OT14 — Historian is a time-series database for process data. Importance: Trend analysis, compliance, troubleshooting, optimization. Plant historian (L3): Stores real-time process data, high frequency, short retention. Enterprise historian (L4): Aggregated data, longer retention, integrates with business systems (ERP/MES).

OT15 — Ladder logic is a graphical programming language mimicking relay circuits. Executed by PLCs. Dominant because: Low learning curve for electricians, deterministic execution, widely supported by legacy hardware, and sufficient for most discrete control applications.

OT16 — RTU (Remote Terminal Unit) is designed for harsh environments, long-distance communication, analog I/O, and remote telemetry. Differs from PLC: RTUs focus on communication and analog processing; PLCs focus on discrete logic and local control. Deploy RTUs in pipelines, utilities, oil/gas fields, or geographically dispersed assets.

OT17 — Analog signals are continuous voltage/current representing process variables. Digital signals are discrete on/off or binary data. 4-20mA is preferred over 0-20mA because 4mA "live zero" indicates wire break/failure (0mA = fault), enables two-wire loop-powered devices, and provides noise immunity over long distances.

OT18 — OT asset inventory is a complete list of hardware, firmware, network configs, and communication paths. It's the foundation because you can't secure what you don't know. Tools: Passive monitoring (packet capture, protocol analysis) is safe. Active scanning (port scans, ping sweeps) is dangerous because it can crash legacy devices, trigger alarms, or disrupt deterministic control loops.

OT19 — MITRE ATT&CK for ICS covers industrial-specific tactics: Reconnaissance, Resource Development, Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command & Control, Exfiltration, Impact. Example techniques: Initial Access (Supply Chain Compromise), Execution (Command and Scripting Interpreter), Impact (Data Destruction/Inhibit Response Function). Differs from enterprise ATT&CK by focusing on physical processes, safety, legacy protocols, and industrial equipment. Use to map current defenses, identify gaps in OT-specific attack paths, and prioritize controls.

OT20 — Converged SOC: Log collection via passive taps and OPC UA/MQTT forwarders (no active polling). SIEM normalizes OT logs and correlates with IT. OT rules baseline normal behavior and alert on protocol anomalies/unauthorized commands. Triage: OT engineers validate physical impact, IT analysts handle cyber scope. Staffing: Hybrid team (IT security + OT engineers). False positives: Tune rules to OT cycles/maintenance windows. Unauthorized firmware alert: Isolate affected PLC, verify with engineering, restore from known-good backup, audit change management, update baseline, implement signed firmware enforcement.
