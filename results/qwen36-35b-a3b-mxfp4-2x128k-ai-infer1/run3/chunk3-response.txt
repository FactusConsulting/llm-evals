T1 — `tofu plan` evaluates the configuration against the current state and live infrastructure to show a preview of proposed changes without modifying anything. `tofu apply` executes that plan, creating, updating, or destroying resources to match the configuration.

T2 — State is a JSON file mapping configuration resources to real-world infrastructure IDs and attributes. Remote state is important because it enables team collaboration, prevents local state loss, enables state locking to avoid race conditions, and allows secure storage in version-controlled or encrypted backends.

T3 — `count` uses integer indices and creates a list of resources; adding/removing items can cause destructive recreation of subsequent resources. `for_each` uses maps or sets of strings, creating resources keyed by unique identifiers. `for_each` is preferred when resources have distinct names/IDs, as it preserves existing resources when adding/removing items.

T4 — OpenTofu detects drift during `tofu plan` by comparing the state file to live infrastructure. If a resource was modified externally, the plan shows it as a change. `tofu apply` will revert it to match the configuration (unless `ignore_changes` or similar is configured), ensuring declarative consistency.

T5:
```hcl
resource "null_resource" "web" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `data "terraform_remote_state"` reads the entire state file, which can be inefficient and expose sensitive data. Output values expose only specific, intentional data. Recommended alternative: use `data "terraform_remote_state"` with an explicit `outputs` list to limit reads, or better, pass outputs directly via `module` blocks if both configurations share the same workspace/backend. This avoids state file parsing overhead and enforces explicit data contracts.

T7 — `remote-exec` provisioners run asynchronously after resource creation, but outputs are evaluated during the apply phase before the provisioner finishes writing the kubeconfig. Fix: Add `depends_on = [null_resource.kubeconfig]` to the output block, or restructure to use a `local_file` resource with `triggers` matching the cluster creation, ensuring the file is written before the output is evaluated.

T8 — `tofu import` is a CLI command that manually adds an existing resource to state, requiring manual config writing and offering no dependency handling. The `import` block (1.5+) is declarative, integrates with `plan`/`apply`, supports multiple resources, handles dependencies automatically, and reduces human error.

T9 — A `variable` is an input parameter passed into a module or root configuration. An `output` is a value exposed from a module or root configuration for other modules to consume. Variables flow in; outputs flow out.

T10 — A provider defines the API, authentication, and resource types for a cloud/platform. Running `tofu plan` without `tofu init` fails because providers aren't downloaded, the backend isn't initialized, and modules aren't fetched.

T11 — `.terraform.lock.hcl` pins exact provider versions and checksums. It should be committed to VCS to ensure reproducible builds, prevent unexpected provider updates, and maintain consistent behavior across environments.

T12 — `tofu destroy` removes all resources tracked in the state file from infrastructure. Target a single resource: `tofu destroy -target=module.name.resource_name`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to find the latest Ubuntu AMI instead of managing an AMI resource.

T14 — `variable` blocks accept external input; `locals` compute values internally. Use `locals` for complex expressions, filtering, or repeated calculations to keep configuration DRY and avoid passing unnecessary variables.

T15 — `lifecycle` controls resource behavior:
- `create_before_destroy`: Creates new instance before destroying old (zero-downtime upgrades).
- `prevent_destroy`: Blocks `destroy` to prevent accidental deletion (use with caution).
- `ignore_changes`: Ignores drift on specific attributes (e.g., auto-scaling tags).

T16 — The `moved` block declaratively renames or relocates resources/modules without destroying/recreating them. It maps the old address to the new address, preserving state and dependencies during refactoring.

T17 — OpenTofu builds a dependency graph from resource references (implicit). `depends_on` forces explicit dependencies. Implicit dependencies allow parallel execution; `depends_on` serializes resources, reducing parallelism. Use sparingly to avoid plan bottlenecks and unnecessary serialization.

T18 — Strategies to reduce plan time:
1. `tofu plan -refresh=false`: Skips state refresh. Tradeoff: drift detection skipped, may show stale changes.
2. Split into multiple workspaces/modules: Reduces graph size. Tradeoff: increased complexity and state management overhead.
3. Use `data` sources instead of managed resources: Avoids infrastructure reads. Tradeoff: less direct control over resource lifecycle.
4. Increase `parallelism` or use `tofu plan -target`: Focuses on relevant resources. Tradeoff: potential state inconsistencies if not carefully scoped.

T19 — State locking prevents concurrent modifications using a backend-specific mechanism (e.g., DynamoDB). If a lock isn't released (CI crash), it persists. Break it with `tofu force-unlock <lock-id>`. Risks: race conditions, state corruption, or duplicate resource creation if another apply is running.

T20 — Steps:
1. Create S3 bucket and DynamoDB table for locking.
2. Add `backend "s3"` block to config with `bucket`, `key`, `region`, `dynamodb_table`.
3. Run `tofu init` (prompts to copy local state to S3).
4. Verify: `tofu state list` should match, S3 object exists, DynamoDB has lock entries. Local state file is replaced by backend references.

A1 — A playbook is an ordered list of plays (host groups + tasks). A role is a reusable collection of tasks, variables, handlers, and templates. A task is a single unit of work (module + arguments).

A2 — `ansible_facts` are auto-discovered system variables. Access OS family: `{{ ansible_os_family }}`.

A3 — `command`: runs without shell features (safer, faster). `shell`: runs with shell (supports pipes, `$VAR`). `raw`: runs without Python, ideal for bootstrapping or unsupported systems.

A4 — Idempotency means running a task multiple times yields the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run).

A5:
```yaml
- name: Install htop on Debian
  apt:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel-release and htop on RedHat
  yum:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (highest to lowest): `extra_vars` > command-line arguments > `host_vars` > `group_vars` > role `defaults` > `set_fact` (runtime). `set_fact` overrides most but is evaluated at runtime.

A7 — Use `serial: 3` in the playbook. Group nodes: `[rke2_first]`, `[rke2_rest]`. Run first batch, then use `wait_for` (or `uri`/`command` with retries) to verify RKE2 readiness before proceeding to the rest.

A8 — `ansible-vault` encrypts sensitive files. Encrypt a single variable: `ansible-vault encrypt_string 'my_secret' --name 'db_password'`, then paste the encrypted string into the vars file.

A9 — Inventory defines hosts and groups. Static: file-based (`hosts.ini`). Dynamic: script/API that generates inventory at runtime (e.g., cloud provider APIs).

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task triggered by `notify`, running only if notified and at the end of the play. Differs from regular tasks (run immediately). Trigger: `notify: restart_service`.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `private_key_file`, `host_key_checking`.

A13 — `register` saves task output to a variable. Use in subsequent tasks: `when: my_var.stdout == "success"` or `debug: var={{ my_var }}`.

A14 — `include_tasks` is dynamic (evaluated at runtime, supports `when`). `import_tasks` is static (evaluated at parse time, no `when`). Use `include` for conditionals, `import` for performance/static structure.

A15 — Ansible Galaxy is a repository for roles/collections. `requirements.yml` lists them. Install: `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible connects to hosts. `ssh`: standard Linux/Unix hosts. `local`: runs on control node. `network_cli`: for network devices (routers/switches) via Telnet/SSH.

A17 — `delegate_to` runs a task on a different host. `run_once` runs it once across a group. Example: gather disk metrics on remote hosts, then process on localhost:
```yaml
- name: Process metrics on control node
  debug: var=host_metrics
  delegate_to: localhost
  run_once: true
```

A18 — Performance strategies:
1. Increase `forks`: More parallel hosts. Tradeoff: higher control node memory/CPU.
2. Enable `pipelining`: Reduces SSH connections. Tradeoff: requires passwordless sudo or specific config.
3. Fact caching: Avoids repeated fact gathering. Tradeoff: stale facts if infrastructure changes.
4. Mitogen: Replaces SSH with persistent connections. Tradeoff: compatibility issues with some modules/callbacks.

A19 — `{{ }}` outputs expressions. `{% %}` control flow (if/for). `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check: {{ server }}
  server {{ server }};
{% endfor %}
}
```

A20 — Rolling deployment:
- `serial: 1` (or 2) for batch processing.
- Pre-task: `uri` module to deregister from LB.
- Post-task: deploy app, then `uri` health check (`status_code: 200`).
- Rollback: `block` (deploy) / `rescue` (re-register to LB, notify ops). Ensures zero-downtime and automatic recovery on failure.
