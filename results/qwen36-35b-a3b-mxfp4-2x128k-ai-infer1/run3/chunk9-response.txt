SC1-A
The pods fail because the namespace's Pod Security Standard (PSS) enforcement changed from `Baseline` to `Restricted`. `Restricted` is the most restrictive preset and explicitly requires that if `securityContext.runAsNonRoot: true` is set, `securityContext.runAsUser` must also be explicitly defined as a non-zero UID. Kubernetes does not infer a UID from the container image's `USER` directive at admission time; it validates the pod spec against the policy. The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`, but the pod spec only declares `runAsNonRoot: true` without a `runAsUser`. The admission controller rejects the pod, or if it slips through (e.g., via a mutating webhook), the container runtime refuses to start it as root, causing `CrashLoopBackOff`. `Baseline` would have allowed this configuration, but `Restricted` enforces explicit non-root UID/GID and drops all capabilities.

SC1-C
**Immediate Fix:** Rebuild the container image with an explicit non-root user: `RUN groupadd -r app && useradd -r -g app app && USER app`. Update the deployment image tag.
**Manifest Fix:** Add `runAsUser: 1000` and `runAsGroup: 1000` to `securityContext` in all deployments.
**CI Gate:** Add a Kyverno policy or OPA Gatekeeper constraint that enforces `runAsUser > 0` whenever `runAsNonRoot: true` is present. Integrate `trivy` or `checkov` in CI to fail builds that violate PSS requirements.
**Rollout:** Use a rolling update strategy (`maxSurge: 25%, maxUnavailable: 0%`). Deploy the fixed image to a canary namespace first, validate readiness probes, then promote to production. Monitor `kubectl rollout status` and pod restart counts before scaling.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped from the primary to the replica over the network. During an outage, the replica stops receiving WALs. Promoting it to primary means any transactions committed on the original primary after the last successfully shipped WAL are permanently lost. The data loss window equals the time between the last WAL write on the primary and the promotion command. To quantify it, check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica, or query `pg_stat_replication` for `sent_lsn`, `write_lsn`, `flush_lsn`, and `replay_lsn`. The difference in LSNs, divided by WAL size, gives the lag in transactions.

SC2-B
1. Import the promoted replica into Terraform state:
   `terraform import aws_db_instance.promoted_replica <arn-of-promoted-replica>`
2. Update the Terraform configuration to reference the new ARN for all dependent resources (security groups, Route53, parameter groups).
3. Safely detach the old instance without triggering a destroy:
   `terraform state rm aws_db_instance.old_primary`
   (If dependencies still reference it, update the config first, then run `terraform plan` to verify no destroy actions are queued. Alternatively, add `lifecycle { prevent_destroy = true }` to the old resource block to block accidental deletion, then remove it from state.)

SC2-C
**Architecture:** Use Amazon RDS Proxy instead of PgBouncer. RDS Proxy handles connection pooling, automatic retries, and integrates natively with IAM auth and multi-AZ/region failover. Implement Route53 failover routing with health checks pointing to the RDS Proxy endpoint. Add application-level retry logic with exponential backoff and jitter.
**RPO < 1s:** Standard async RDS cannot guarantee this. Recommend **Aurora Global Database**. It uses a primary cluster in one region and secondary clusters in others with a single-write, multi-read model. Failover is automated, typically completes in <1 minute, and uses a global transaction log that minimizes data loss. It also provides lower cross-region latency for reads and eliminates manual promotion steps.

```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid,
       blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS current_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC6-C
**Direct Connect:** Dedicated 10Gbps+ link, lower latency, predictable cost. Fits ZT when combined with encryption (MACsec or IPsec over DC). Routing: BGP over DC, replace VPN routing tables.
**Second VPN + ECMP:** Low cost, scales bandwidth linearly. IPsec overhead adds ~10-15% latency. Routing: BGP with equal-cost multi-path, requires route table updates.
**Tailscale/Netbird:** WireGuard-based mesh, ZT-native, automatic routing. Cost: subscription-based. Bandwidth: limited by WireGuard MTU and cloud egress. Routing: MagicDNS, subnet routers. Not ideal for enterprise compliance or >1Gbps sustained throughput.
**Recommendation:** Direct Connect for primary backbone, keep VPN as failover. ECMP second VPN is a cheaper interim step but lacks enterprise-grade encryption/failover. Tailscale is unsuitable for core infrastructure due to compliance and bandwidth limits.

SC10-A
**Active-Passive (Velero):** Backup/restore takes hours. Cannot meet RPO < 15m. Not viable.
**Active-Active (Istio/Cilium):** Continuous replication meets RPO/RTO. With 12ms latency, synchronous replication is feasible.
**Replication Strategy:**
- **PostgreSQL:** Patroni with async replication + synchronous standby for critical writes. RPO ~0s, RTO < 1m.
- **Redis:** Sentinel with `min-slaves-to-write 1` and `min-slaves-max-lag 5`. RPO ~0s.
- **RabbitMQ:** Federation/Shovel or Quorum Queues with cross-site sync. RPO ~0s.
- **MinIO:** Site replication with `mc replicate add`. RPO depends on replication interval; tune to < 15m.
**Verdict:** Active-active with Patroni/Redis/RabbitMQ sync + MinIO site replication meets RPO < 15m and RTO < 1h. Velero fails RPO.

*Note: `patroni.yml.j2` should include `scope: mydb`, `namespace: /service/mydb`, `etcd` DCS config, `postgresql` with `synchronous_commit: on`, and `synchronous_standby_names: 'standby1,standby2'`.*

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks (Patroni, Redis Sentinel, RabbitMQ) monitor site connectivity. Site down = >3 consecutive failures + etcd quorum loss.
2. **DNS Failover:** GSLB (Route53/Cloudflare) switches traffic to Dallas endpoint.
3. **Patroni Promotion:** Standby promotes via etcd lock. Synchronous commit ensures zero data loss.
4. **Redis/RabbitMQ:** Sentinel/federation automatically promotes standby nodes.
5. **MinIO:** Site replication catches up. Pause writes during catch-up if needed.
6. **Terraform State:** Update state file to reflect new primary cluster. Run `terraform apply` to adjust DNS, security groups, and routing.
**Split-Brain:** Use etcd quorum fencing. Patroni uses `failover_timeout` and `retry_timeout` to prevent dual promotion. Disable writes on old primary via firewall rules.
**Failback:** Reverse replication (Dallas -> Chicago). Sync data, verify integrity, switch DNS back, update Terraform state, decommission Dallas as primary.
