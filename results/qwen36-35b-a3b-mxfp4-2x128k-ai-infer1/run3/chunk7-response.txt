AA1 — A monolith is a single, unified codebase deployed as one unit with shared memory/process space. Microservices decompose the system into independently deployable, network-communicating services. Microservices introduce: (1) Network latency and failure modes (no local calls), (2) Distributed data consistency challenges (no ACID across services), (3) Operational complexity (CI/CD pipelines, service discovery, distributed tracing, orchestration overhead).

AA2 — Synchronous communication blocks the caller until a response is received, creating tight coupling and real-time guarantees. Example: REST/HTTP or gRPC. Asynchronous communication decouples sender and receiver; messages are queued and processed independently. Example: RabbitMQ, Kafka, or AWS SQS. Async improves resilience and scalability but introduces eventual processing and ordering challenges.

AA3 — A reverse proxy handles low-level traffic routing, SSL termination, load balancing, and caching at the network/transport layer. An API Gateway sits above it, adding business logic: authentication, rate limiting, request/response transformation, service discovery, and API versioning. An API Gateway cannot fully replace a reverse proxy because reverse proxies are optimized for high-performance, low-latency L4/L7 routing and TLS termination. They complement each other: reverse proxy → API Gateway → services.

AA4 — A Saga manages distributed transactions by breaking them into local transactions, each with a compensating action to undo changes if a later step fails. Choreography-based sagas use events: services publish state changes and react to others. Decentralized, good for simple, linear flows. Orchestration-based sagas use a central coordinator that explicitly commands each service. Centralized, better for complex branching, retries, and error handling.

AA5 — CQRS separates read and write models: commands modify state, queries read optimized views. Event Sourcing stores state as an immutable sequence of events. They pair naturally because CQRS writes need a durable source of truth; ES provides it. Queries can be built by replaying events. This combination solves auditability, temporal queries, concurrent update conflicts, and independent scaling of reads/writes—problems traditional CRUD struggles with due to shared read/write models and state corruption risks.

AA6 — The Circuit Breaker prevents cascading failures by failing fast when a downstream service is unhealthy. States: Closed (normal, passes requests), Open (failure threshold met, blocks requests), Half-Open (allows limited probes to test recovery). Differs from retry/backoff: retry attempts immediate recovery; circuit breaker prevents resource exhaustion during sustained outages. Use both together: apply retry with exponential backoff for transient blips inside the Closed state, but open the circuit if retries consistently fail, then use half-open to validate recovery.

AA7 — 
1. Shared DB/Shared Schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, easiest ops.
2. Shared DB/Separate Schema: Moderate cost, better isolation, easier per-tenant backups/migrations, moderate ops complexity.
3. Separate DB: Highest cost, best security/isolation, simplest backups/migrations, highest ops complexity (connection pooling, scaling).
Trade-offs: Cost ↑ as isolation ↑. Security ↑ as isolation ↑. Ops complexity ↑ as isolation ↑. Noisy-neighbor risk ↓ as isolation ↑.

AA8 — Eventual consistency allows temporary stale reads; strong consistency guarantees all reads see the latest write. For inventory that must never oversell, use strong consistency. Architecture: PostgreSQL or a distributed SQL DB (CockroachDB/Yugabyte) with row-level locking (`SELECT ... FOR UPDATE`) or optimistic concurrency control. At scale, partition inventory by SKU/warehouse, use a reservation queue (Kafka) to serialize stock decrements, and apply idempotent processing. Avoid eventual consistency for stock counts; use it only for non-critical read replicas.

AA9 — A sidecar proxy (e.g., Envoy) runs alongside each service, intercepting all inbound/outbound traffic. In Istio, the control plane (Pilot, Citadel) pushes config and rotates certs; the data plane (Envoy) handles routing, mTLS, and telemetry. mTLS between sidecars authenticates service-to-service identity automatically, encrypts traffic without app code changes, and enables fine-grained access policies. Application-level TLS only secures external/client traffic and requires manual cert management and code integration.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is decommissioned. Strategy: Deploy an API Gateway. Identify bounded contexts (e.g., auth, billing, catalog). Build .NET 8 microservices for these. Configure gateway routes to forward matching paths to new services while legacy handles the rest. Repeat per context. Monitor metrics, validate functionality, then decommission legacy routes. Zero-downtime migration with rollback capability.

AA11 — 12-Factor App is a methodology for cloud-native software. Six factors: (1) Codebase (one repo, many deploys), (2) Dependencies (explicitly declared), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless, ephemeral). They matter because they enable horizontal scaling, zero-downtime deploys, secure config management, portable infrastructure, and resilient cloud deployments.

AA12 — 
- Coupling: Event-driven = loose; Request-driven = tight.
- Scalability: Event-driven = highly scalable, async burst handling; Request-driven = synchronous limits, predictable load.
- Debugging: Event-driven = harder (distributed, async, replay needed); Request-driven = easier (traceable request chain).
- Ordering: Event-driven = partition-based ordering guaranteed; Request-driven = per-request ordering.
- Failure: Event-driven = durable queues, retries, dead-letter; Request-driven = timeouts, circuit breakers, immediate feedback.
Choose event-driven for async workflows, high throughput, decoupled systems. Choose request-driven for real-time APIs, synchronous CRUD, and simple request-response flows.

AA13 — A load balancer distributes incoming traffic across multiple backend servers. Layer 4 (transport) routes by IP/port (TCP/UDP), fast but content-agnostic. Layer 7 (application) routes by HTTP headers, URLs, cookies, enabling content-aware decisions. Layer 7 is required for SNI-based SSL termination, path-based routing (`/api` vs `/static`), or cookie-based session affinity.

AA14 — Message queues (RabbitMQ) use point-to-point or pub/sub, consume/delete messages, support complex routing, and excel at task queues. Log-based brokers (Kafka) use append-only logs, retain messages, support multiple independent consumers, and enable replay. Pick RabbitMQ for complex routing, low-latency task processing, or strict delivery guarantees. Pick Kafka for event streaming, audit logs, high throughput, or replayability.

AA15 — Containers share the host OS kernel and isolate processes/filesystems; VMs run a full guest OS under a hypervisor. Containers are lightweight, fast-starting, and consistent across environments. They're popular for microservices because they enable rapid scaling, ephemeral deployments, efficient resource utilization, and seamless CI/CD integration without hypervisor overhead.

AA16 — Stateless services store no local session data; each request is independent. Stateful services maintain local state (sessions, caches, DB connections). Stateless services scale horizontally easily because any instance can handle any request without sticky sessions or state synchronization. Example stateless: REST API, web server. Example stateful: PostgreSQL, Redis, WebSocket server.

AA17 — An ORM maps objects to database tables and automates query generation/relationship management. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORM accelerates development, ensures type safety, and abstracts DB differences, but can generate inefficient queries, hide performance bottlenecks, and complicate complex joins. Raw SQL offers full control, optimal performance, and transparency, but requires more code, DB-specific tuning, and maintenance.

AA18 — The Bulkhead pattern isolates resources (threads, connections, memory) per service/component to prevent cascading failures. It relates to microservices by ensuring one failing service doesn't exhaust shared infrastructure. Implementation: Use separate thread pools per downstream service. In Kubernetes, deploy critical vs non-critical services in separate namespaces/nodes with resource quotas and network policies. Separate connection pools per tenant/service to isolate resource consumption.

AA19 — OT requires a central server to transform concurrent operations; guarantees strong consistency, low online latency, but is complex server-side and poor for offline. CRDTs are data structures that merge automatically without coordination; guarantee eventual consistency, higher client-side complexity, but excel offline. For offline editing, choose CRDTs. They guarantee convergence regardless of operation order or network partitions, enabling seamless offline-to-online sync without a central coordinator.

AA20 — Distributed tracing challenges include context propagation, sampling, storage, and async continuity. Context propagation uses W3C Trace Context (`traceparent`) or B3 headers, injected/extracted across all services. Sampling: head-based (random, loses context), tail-based (sample after processing, accurate but high overhead); modern systems use adaptive tail-based. Storage/querying: Jaeger/Tempo use columnar/object storage optimized for trace queries. Async/Kafka continuity: trace ID must be propagated in message headers. Use tail-based sampling with producer/consumer span correlation via trace ID. Kafka partitions can break ordering; use trace correlation IDs and consistent partitioning strategies.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and enterprise reliability. Examples: VMware ESXi, KVM, Hyper-V, Xen. Type 2 (hosted) hypervisors run on a host OS, offering convenience but higher overhead. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block-level storage, presenting disks as local devices. Used for databases, VMs, high-performance workloads. Protocols: Fibre Channel, iSCSI. NAS provides file-level storage, mounted via network. Used for shared files, backups, media. Protocols: NFS, SMB/CIFS. Choose SAN for low-latency block access; NAS for collaborative file sharing and simplicity.

OP3 — 3-tier architecture (core/distribution/access) is hierarchical, prone to bottlenecks, asymmetric routing, and high east-west latency. Leaf-spine is fully meshed, providing equal-cost multipath routing, predictable bandwidth, and low latency. It solves 3-tier bottlenecks by eliminating tier dependencies, simplifying routing (ECMP), and supporting scalable east-west traffic for modern data centers.

OP4 — Proxmox HA cluster: 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing uses STONITH (IPMI/APC) to power off failed nodes. Shared storage: Ceph (recommended for redundancy/HA), iSCSI, or NFS. During node failure: Proxmox HA manager detects failure, fences the node, and restarts VMs on healthy nodes. Shared storage ensures VM disks remain accessible.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte VLAN ID tag to Ethernet frames. Linux config for 3 VLANs on one NIC: `ip link add link eth0 name eth0.10 type vlan id 10`, repeat for IDs 20/30. Assign IPs, `ip link set eth0.{10,20,30} up`. Alternatively, use `netplan` or `NetworkManager` with VLAN interfaces.

OP6 — RAID 1: Mirror, 50% capacity, 1 drive fault tolerance. RAID 5: Striping + single parity, N-1 capacity, 1 drive tolerance, write penalty. RAID 6: Striping + double parity, N-2 capacity, 2 drive tolerance, higher write penalty. RAID 10: Mirror + stripe, 50% capacity, tolerates 1 drive per pair, excellent perf. RAID Z2 (ZFS): Equivalent to RAID 6 + checksums, snapshots, self-healing. For 6 drives + DB: RAID 10 for maximum write performance/low latency, or Z2 for capacity/integrity. I choose RAID 10 for pure DB performance.

OP7 — Internal AD DNS servers act as authoritative for internal zones and recursive resolvers for clients. External DNS (DMZ/cloud) hosts authoritative public zones with DNSSEC. Forwarders route internet queries to external DNS. Conditional forwarding routes internal queries to AD DNS. Split-horizon: internal DNS returns private IPs, external returns public IPs. Laptop mobility: DHCP provides internal DNS. On VPN, DNS suffixes/conditional forwarding route internal queries correctly. Split-horizon ensures public services resolve to public IPs externally, private IPs internally. DNSSEC validates external responses.

OP8 — PKI chain: Root CA → Subordinate/Issuing CA → End-entity cert. Trust flows downward. Internal PKI: Root CA offline (air-gapped). Subordinate CA online, issues certs. Use certificate templates for roles (web, email, client). Auto-enrollment via GPO/AD CS. Revocation: CRL (periodic download) vs OCSP (real-time query); OCSP stapling improves performance. Compromise: Subordinate CA requires revoking its certs and reissuing (manageable). Root CA compromise requires rebuilding entire PKI, updating global trust stores (catastrophic).

OP9 — MPLS: High cost, high reliability, low latency, ISP-managed, secure. IPsec VPN: Low cost, variable reliability/latency, self-managed, basic security. SD-WAN: Moderate cost, high reliability (dynamic routing), low latency, centralized management, advanced security. WireGuard mesh: Low cost, high reliability, low latency, simple config, modern crypto. Recommendation: SD-WAN. Best balance for VoIP (QoS, traffic steering, low latency), manageable at scale, cost-effective vs MPLS, superior to plain IPsec/WireGuard for enterprise features.

OP10 — iDRAC/iLO/IPMI provide out-of-band (OOB) server management independent of OS/hardware state. Critical for remote reboot, console access, firmware updates, and diagnostics during crashes or network outages. Internet exposure is dangerous: default credentials, unpatched firmware, and exposed management interfaces lead to full server compromise, ransomware, or physical damage. Should be on isolated management networks.

OP11 — LVM: Block device manager, volumes/groups, snapshots are COW requiring pre-allocated space. LVM-Thin: Overprovisions storage, thin-provisioned COW snapshots, efficient space but performance overhead. ZFS: Filesystem + volume manager, COW, instantaneous space-efficient snapshots, self-healing, checksums. Use LVM for traditional Linux block storage. LVM-Thin for VMs/containers needing overprovisioning. ZFS for data integrity, advanced snapshots, and modern storage needs.

OP12 — Stretch cluster: 2 sites with 2 nodes each + 1 arbiter node (tiebreaker). CRUSH rules distribute OSDs across sites, ensuring replicas span sites. Monitors: 3 monitors (1 per site) for quorum; arbiter site has no OSDs, only monitor. Latency: <5ms ideal, <10ms acceptable. Higher latency causes performance degradation and split-brain risk. Split-brain: Without tiebreaker, both sites think they have quorum, causing data corruption. Arbiter breaks ties. 2-site Ceph is bad without a tiebreaker because high latency causes false failures, and there's no reliable mechanism to prevent simultaneous writes during network partitions.

OP13 — DHCP uses DORA: Discover, Offer, Request, Acknowledge. If server is unavailable, client retries, eventually falls back to APIPA (169.254.x.x) if lease expires. Windows renewal: T1 (50%) attempts renewal, T2 (87.5%) broadcasts. If both fail, client reboots/retries, eventually gets APIPA.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP, ACLs, and link aggregation. Enterprise importance: Network segmentation, traffic prioritization, loop prevention, security enforcement, and monitoring/automation.

OP15 — NTP synchronizes clocks across networks. Critical for authentication (Kerberos), logging, clustering, distributed transactions, certificate validation, and audit compliance. Clock drift consequences: Kerberos auth failures, database replication breaks, split-brain in clusters, incorrect log timestamps, security certificate errors.

OP16 — Physical servers: Direct hardware access, highest performance, no virtualization overhead. VMs: Full OS isolation, hypervisor overhead, good for legacy/OS-specific workloads. Containers: Shared kernel, lightweight, fast, ideal for microservices. Bare metal is chosen for HPC, low-latency trading, GPU-intensive AI, database cores needing direct disk access, or compliance requirements.

OP17 — UPS provides instant battery-backed power during outages, bridging the gap to generator startup. Generators provide long-term power via fuel, taking seconds/minutes to start. Both are needed: UPS handles immediate transition and smooths power; generator handles sustained outages. ATS (Automatic Transfer Switch) detects outages, switches load from utility to generator, and switches back when utility restores.

OP18 — Active-passive: One node handles traffic, standby takes over on failure. Simple, no split-brain. Active-active: Both handle traffic, share load. Complex, requires distributed locking/replication. PostgreSQL HA with Pacemaker/Corosync: Primary/Replica setup. Pacemaker manages virtual IP, monitors health, triggers failover. STONITH fencing ensures failed node is powered off. Streaming replication syncs data. On failure, Pacemaker promotes replica, moves VIP, starts services.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO define acceptable data loss/downtime, driving backup frequency and replication. Types: Full (baseline), Incremental (changes since last), Differential (changes since last full). Deduplication reduces storage and backup windows. Media: Disk for fast restores, tape/cloud for cost/offsite. Immutable backups (WORM) protect against ransomware. Testing: Regular restore drills, verify integrity, measure RTO/RPO. Backup = data preservation. DR = comprehensive strategy (infrastructure, processes, failover) to restore operations.

OP20 — 802.1X roles: Supplicant (client), Authenticator (switch/AP), Authentication Server (RADIUS). EAP methods: EAP-TLS (certificate-based, mutual auth, secure), PEAP (username/password, tunneled, common). RADIUS validates credentials, returns auth result + VLAN attributes. Dynamic VLAN: Switch assigns port to VLAN based on RADIUS response. Failure: Port stays unauthorized, blocks traffic, logs event. MAB: Uses MAC address as credential. Switch sends MAC to RADIUS, RADIUS matches to user/group, assigns VLAN. Less secure, fallback for IoT/legacy devices.
