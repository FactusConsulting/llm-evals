**DN1** — `class` is a reference type (heap-allocated, supports inheritance, can be null). `struct` is a value type (stack/inline-allocated, no inheritance, non-null by default). Use `struct` for small, immutable, short-lived data that doesn't require inheritance (e.g., coordinates, points, simple DTOs) to avoid heap allocation and GC pressure.

**DN2** — `IEnumerable<T>` enumerates in-memory collections (LINQ-to-Objects). `IQueryable<T>` represents an expression tree that a provider translates to a query language (e.g., SQL). The distinction matters because `IQueryable` pushes filtering, projection, and sorting to the database, reducing memory and network overhead, while `IEnumerable` pulls all data and filters in memory.

**DN3** — `async/await` compiles to a state machine that non-blocking returns to the caller and resumes when the awaited operation completes. `Task` is a reference type representing an async operation. `ValueTask` is a value type that avoids heap allocation when the result is already available or synchronous. Use `ValueTask` when an async method frequently completes synchronously or returns cached data to reduce GC pressure.

**DN4** — DI is an IoC pattern where a container manages object creation and lifetime. `Transient`: new instance per resolution. `Scoped`: one instance per request scope (e.g., HTTP request). `Singleton`: one instance per container lifetime. Injecting a `Scoped` service into a `Singleton` causes a "captive dependency": the scoped service lives forever, holding onto request-scoped resources (DB connections, caches) indefinitely, leading to memory leaks and connection pool exhaustion.

**DN5** — `string` is immutable, heap-allocated, and GC-managed. `ReadOnlySpan<char>` is a stack-allocated, zero-copy view over memory (strings, arrays, unmanaged buffers). `Span<T>` is the mutable counterpart. Use `Span<T>`/`ReadOnlySpan<char>` for high-performance string/memory operations (parsing, slicing, encoding) to eliminate allocations and avoid copying data.

**DN6** — The GC uses mark-and-sweep with compaction. `Gen 0`: short-lived objects, collected frequently. `Gen 1`: buffer between 0 and 2. `Gen 2`: long-lived objects, collected rarely. `Large Object Heap (LOH)`: objects >85KB, not compacted (prone to fragmentation), collected in Gen 2. `IDisposable` is for deterministic cleanup of unmanaged resources (file handles, sockets, DB connections). The GC only manages managed memory; `IDisposable` ensures resources are released immediately via `using` or explicit disposal.

**DN7** — By default, `async` captures the `SynchronizationContext` (UI thread, ASP.NET request context) to resume on the same context. `ConfigureAwait(false)` ignores the context and resumes on any thread pool thread. Use it in libraries/shared code to avoid deadlocks and improve throughput. Do NOT use it in UI apps or code that must run on a specific context (e.g., updating UI, ASP.NET Core request-scoped services).

**DN8** — Primary constructors reduce boilerplate: `public class Service(string name, int id) { Name = name; Id = id; }`. Collection expressions: `[1, 2, 3]`, `[.. array]`, `[.. list]`. `FrozenDictionary`: immutable, optimized for read-only lookups, lower memory, faster than `Dictionary`. DI example: `public class MyService(string config, ILogger<MyService> logger) { ... }` registered via `builder.Services.AddScoped<MyService>();` and resolved automatically.

**DN9** — Cause: `DbContext` is scoped. High concurrency often exposes race conditions where a `DbContext` is shared across requests, cached, or accessed by background threads after its HTTP scope ends, triggering `ObjectDisposedException`. Fix: never cache or share `DbContext` instances. Rely on DI scoping. Background tasks must create explicit scopes via `IServiceScopeFactory`. EF Core's `DbContext` lifetime is tied to DI scoping: one instance per HTTP request, disposed when the scope ends.

**DN10** — `record` is a reference type with immutable-by-default semantics, value-based equality, and positional syntax. `record struct` is a value type with the same semantics. Choose `class` for mutable/stateful objects or when inheritance is needed. Choose `record` for immutable DTOs, configuration, or domain events. Choose `record struct` for high-performance, stack-allocated immutable data.

**DN11** — `ref`: passes a reference to an existing variable (read/write), must be initialized before call. `out`: passes a reference, must be assigned inside the method, caller doesn't need initialization. `in`: passes a read-only reference, prevents modification, avoids copying large structs. Use `ref` for modifying existing values, `out` for multiple return values, `in` for performance with large structs.

**DN12** — Nullable Reference Types (NRT) use `string?` vs `string` for compile-time static analysis only; they don't affect runtime behavior. Nullable Value Types (`int?`) are `Nullable<int>`, runtime types that can hold null and use boxing/unboxing. NRTs catch potential null dereferences at compile time; value types use runtime nullability.

**DN13** — LINQ provides a unified querying syntax for collections, databases, XML, etc. Method syntax (`list.Where(...)`) is fluent and chainable, preferred for complex queries. Query syntax (`from x in list where ...`) is SQL-like and compiles to method syntax. Deferred execution means the query isn't executed until enumerated (e.g., `foreach`, `ToList()`), enabling composition and lazy evaluation.

**DN14** — `where T : class`: reference type. `where T : struct`: value type (non-nullable). `where T : new()`: parameterless constructor. `where T : IComparable<T>`: implements comparison. Combine constraints for type safety, e.g., `where T : class, IComparable<T>, new()` ensures T is a reference type, comparable, and instantiable.

**DN15** — Abstract classes can have state, constructors, and partial implementation; support single inheritance. Interfaces define contracts with no state (except static/default); support multiple inheritance. Default interface methods (C# 8+) allow interfaces to have implementations, slightly narrowing the gap, but abstract classes still win for shared state, constructors, and protected members.

**DN16** — Middleware is a sequence of delegates handling requests/responses. `app.Use()` adds middleware that can pass context to the next delegate. `app.Map()` branches the pipeline based on path match. `app.Run()` is terminal (doesn't call next). Ordering matters: auth before routing, caching before heavy processing, exception handling early. `UseExceptionHandler` catches unhandled downstream exceptions, logs them, and returns an error response.

**DN17** — `Channel<T>` is modern, async-first, supports bounded/unbounded, and natively handles backpressure. `BlockingCollection<T>` is older, sync-focused, wraps concurrent collections. Example: `Channel.CreateBounded<int>(10)`. Producers await `WriteAsync` when full; consumers read asynchronously. This naturally applies backpressure without blocking threads.

**DN18** — Source Generators produce C# source files at compile-time via Roslyn, offering type safety and zero runtime overhead. Reflection inspects at runtime (slower, no compile-time checks). IL weaving modifies compiled assemblies (harder to debug, breaks some tools). Incremental generators (`ISourceGenerator` replacement) support caching, incremental compilation, and better IDE integration, significantly speeding up builds.

**DN19** — TPL Dataflow is a message-passing library for pipelines/flowgraphs. `BufferBlock`: FIFO storage. `TransformBlock`: async input-to-output transformation. `ActionBlock`: async processing with no output. Compared to `System.Threading.Channels`, Dataflow offers richer composition (join, fan-out, completion propagation) and is better for complex workflows, while Channels are simpler and ideal for straightforward producer-consumer pipelines.

**DN20** — Minimal APIs are lightweight, inline-routing, low-boilerplate alternatives to controllers. Trade-offs: harder to test (requires `WebApplicationFactory`), explicit middleware integration, OpenAPI via `Microsoft.AspNetCore.OpenApi`. Controllers offer richer tooling, attribute routing, and easier complex app structuring. Route groups (`app.MapGroup("/api")`) apply prefixes/middleware. Endpoint filters (`AddEndpointFilter`) enable cross-cutting concerns (auth, validation) per endpoint.

**P1** — `list` is mutable, ordered, indexed, allows duplicates. `tuple` is immutable, ordered, fixed-size, heterogeneous, ideal for returning multiple values. `set` is mutable, unordered, unique elements. `frozenset` is immutable, hashable, can be used as a dictionary key.

**P2** — The GIL is a mutex allowing only one thread to execute Python bytecode at a time. It severely impacts CPU-bound multi-threaded workloads. Workarounds: use `multiprocessing`, C extensions that release the GIL, `asyncio` for I/O-bound tasks, or offload to external services/processes.

**P3** — `copy()` creates a shallow copy (new container, references original nested objects). `deepcopy()` recursively creates independent copies. Shallow copy pitfall: `a = [[1,2]]; b = copy(a); b[0].append(5);` modifies `a` because inner lists are shared.

**P4** — Decorators wrap functions to extend behavior without modifying source. Execution time example:
```python
import time, functools
def log_time(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

**P5** — Generators are lazy iterators using `yield` to produce items one at a time, saving memory vs loading a full list. `yield from` delegates to another generator/iterable, replacing manual loops with cleaner syntax.

**P6** — The asyncio event loop manages async tasks and I/O. `asyncio.run()` starts the loop and runs a main coroutine. `asyncio.gather()` runs multiple coroutines concurrently and returns results. `asyncio.create_task()` schedules a coroutine and returns a `Task` for later awaiting. `time.sleep()` blocks the entire thread/event loop; use `asyncio.sleep()` instead.

**P7** — MRO defines the method lookup order. Python 3 uses C3 linearization. For diamond inheritance `D(B, C)` → `B(A)`, `C(A)`, MRO is `D → B → C → A`. `D().who()` prints `"C"` because C's `who()` overrides A's, and C appears before A in the MRO.

**P8** — A metaclass controls class creation. `__init_subclass__` is a simpler, instance-level hook for subclass creation without metaclasses. Metaclass use case: enforcing class-level constraints, auto-registering plugins, ORM model definitions. `__init_subclass__` use case: auto-adding attributes to subclasses, lightweight plugin registration.

**P9** — Threading: I/O-bound, shares memory, GIL limits CPU parallelism. Multiprocessing: CPU-bound, separate processes, bypasses GIL, higher overhead. `concurrent.futures`: high-level API (`ThreadPoolExecutor`, `ProcessPoolExecutor`) for both. Multiprocessing serializes objects via pickling; unpicklable objects (locks, open files, lambdas) fail. Use `__reduce__` or avoid complex state.

**P10** — `__slots__` declares fixed attributes, preventing `__dict__` creation. Use it when instantiating many objects to save memory. Prevents dynamic attribute addition and `__dict__`/`__weakref__` (unless explicitly included). Memory impact: significant per-instance reduction, eliminates dict overhead.

**P11** — A virtual environment isolates dependencies, preventing package conflicts and ensuring reproducible builds. `venv`: built-in (Python 3.3+), lightweight. `virtualenv`: third-party, older, more features. `conda`: package + environment manager, handles non-Python dependencies, data-science focused.

**P12** — Comprehensions (`[x for x in it if cond]`) are concise and Pythonic. `map()`/`filter()` are functional, return lazy iterators. Prefer comprehensions for readability and simple transformations. Prefer `map()`/`filter()` for complex functions, lazy evaluation, or reusing existing functions.

**P13** — `==` checks value equality. `is` checks object identity. Python interns small integers (-5 to 256) and some strings for performance. `a is b` returns `True` for small ints because they reference the same cached object in memory.

**P14** — `*args` collects extra positional arguments into a tuple. `**kwargs` collects extra keyword arguments into a dict. `/` marks parameters before it as positional-only. `*` marks parameters after it as keyword-only. Used for flexible, clear API design.

**P15** — Context managers ensure setup/teardown (resource management). `__enter__`/`__exit__` is class-based. `@contextmanager` is function-based using `yield`. Example (DB transaction):
```python
@contextmanager
def transaction(db):
    db.begin()
    try: yield db
    except: db.rollback(); raise
    db.commit()
```

**P16** — Type hinting adds static annotations. `Union[A, B]`: A or B. `Optional[A]`: `Union[A, None]`. `Literal["x"]`: exact value. `TypeVar`: constrained generic. `Protocol`: structural typing (duck typing). `mypy`/`pyright` analyze code against hints, catching type errors before runtime.

**P17** — Dunder methods define object behavior. `__repr__`: unambiguous, dev-focused. `__str__`: readable, user-focused. `__eq__`: equality. `__hash__`: hash value. `__getattr__`: fallback when attr missing. `__getattribute__`: called for every attr access. Defining `__eq__` without `__hash__` sets `__hash__ = None`, making instances unhashable (can't be dict keys/set members).

**P18** — Descriptors implement `__get__`, `__set__`, `__delete__` to control attribute access. `property` is a data descriptor wrapping getters/setters. `classmethod` and `staticmethod` are non-data descriptors binding methods to class/instance. All are descriptors applied to class attributes under the hood.

**P19** — Import system resolves modules, caches in `sys.modules`. Relative imports (`from . import mod`) are package-relative; absolute imports are `sys.path`-based. `sys.path` lists search directories; `PYTHONPATH` prepends to it. `__init__.py` marks packages and runs on import. Namespace packages omit `__init__.py` to allow split packages. Finders locate modules; loaders load/initialize them.

**P20** — `dataclasses` auto-generates `__init__`, `__repr__`, `__eq__`, `__hash__`. `attrs` offers more flexibility/validation. `Pydantic` adds runtime validation, serialization, and type coercion. `__post_init__` runs after `__init__` for validation. `field(default_factory=list)` avoids mutable default pitfalls. `frozen=True` makes instances immutable and auto-generates `__hash__`. Inheritance works but requires careful `__init__` merging. Choose `Pydantic` for validation, config parsing, serialization, or complex type coercion.
