AA1 — Monoliths are single, unified codebases deployed as one unit with shared runtime and database. Microservices are independently deployable, loosely coupled services with separate runtimes and databases. Microservices introduce: (1) distributed system complexity (network latency, partial failures, eventual consistency), (2) operational overhead (CI/CD pipelines, service discovery, distributed monitoring/logging), and (3) data consistency challenges (distributed transactions, cross-service integrity).

AA2 — Synchronous communication blocks the caller until a response is received, ensuring immediate feedback but creating tight coupling and latency bottlenecks. Example: REST/gRPC over HTTP. Asynchronous communication decouples producer and consumer; messages are queued and processed later, improving resilience and scalability. Example: RabbitMQ, Kafka, or AWS SQS.

AA3 — A reverse proxy routes traffic to backend servers, handling TLS termination, load balancing, and caching at the network/infrastructure layer. An API gateway adds business/developer-facing capabilities: authentication, rate limiting, request transformation, API versioning, and analytics. An API gateway can functionally replace a reverse proxy, but they are often layered together: a lightweight reverse proxy (Nginx/Traefik) at the edge for TLS/traffic routing, and an API gateway internally for policy enforcement and developer tooling.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to roll back if a later step fails. Choreography-based sagas use events: services publish state changes, and others react. Best for simple, loosely coupled flows but hard to monitor/debug. Orchestration-based sagas use a central coordinator that commands services via APIs. Best for complex, stateful, or regulated workflows where visibility and control are critical.

AA5 — CQRS separates read (query) and write (command) operations into distinct models, often with different schemas or databases optimized for each. Event Sourcing stores state as an immutable sequence of domain events rather than current snapshots. Combined, they solve auditability, temporal queries, and complex domain modeling. Traditional CRUD struggles with replaying history, maintaining immutable audit trails, and independently scaling read/write workloads.

AA6 — The Circuit Breaker prevents repeated calls to a failing service, avoiding cascade failures and resource exhaustion. States: Closed (normal operation), Open (fail fast after threshold), Half-Open (allows limited test requests). Unlike simple retry (which assumes transient failure and waits), the circuit breaker stops calls entirely during sustained outages. Use both together: retry handles transient glitches within closed/half-open states; the circuit breaker opens when retries consistently fail, preventing system fatigue.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, simplest ops.
2. Shared DB, separate schema: Moderate cost, better isolation/noisy-neighbor mitigation, moderate ops complexity, easier per-tenant backups.
3. Separate DB per tenant: Highest cost, best security/isolation/noisy-neighbor control, highest ops complexity (schema migrations, backups), easiest compliance and tenant-specific tuning.

AA8 — Eventual consistency allows temporary stale reads as updates propagate; strong consistency guarantees reads always reflect the latest write. For inventory that must never oversell, use strong consistency. Architecture: Relational DB (PostgreSQL) with `SELECT ... FOR UPDATE` row locking or optimistic locking with retries. At scale: partition stock by SKU/warehouse, use distributed locks (Redis Redlock) or consensus KV (etcd) for critical reservations, and implement short-TTL hold/checkout patterns. Avoid eventual consistency for the authoritative stock ledger.

AA9 — A sidecar proxy is a co-located container that intercepts all inbound/outbound traffic for a service. In Istio, Envoy handles the data plane (routing, mTLS, metrics, retries), while Istiod (Pilot/Citadel) manages the control plane (pushes CDS/LDS/SDS config, rotates certs). Data plane = traffic handling; control plane = configuration/security management. mTLS between sidecars solves infrastructure-level service identity, automatic cert rotation, and zero-code security. Application-level TLS requires manual cert management, code integration, and doesn't enforce internal service authentication.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality with new services, routing traffic to new components until the legacy system is retired. Strategy: Deploy .NET 8 microservices alongside the legacy app. Use an API gateway/reverse proxy to route specific endpoints/URLs to new services. Start with isolated, low-risk features (e.g., reporting, auth). Migrate DB access via dual-write or CDC to avoid tight coupling. Gradually shift routes as new services stabilize, then decommission legacy endpoints.

AA11 — The 12-Factor App is a methodology for building SaaS/cloud-native apps. Six factors: (1) Codebase (one repo, many deploys), (2) Dependencies (explicitly declared), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless, ephemeral). They matter because they enable portability, horizontal scaling, resilient deployments, automated CI/CD, and prevent vendor lock-in or hardcoded configurations.

AA12 — 
- Coupling: Event-driven = loose (async, schema-based); Request-driven = tight (sync, API contract).
- Scalability: Event-driven = highly scalable, backpressure via queues; Request-driven = limited by sync calls, needs LB/circuit breakers.
- Debugging: Event-driven = harder (distributed, async, replay needed); Request-driven = easier (request/response tracing, logs).
- Ordering: Event-driven = partition-level ordering guaranteed; Request-driven = per-request only, no global ordering.
- Failure: Event-driven = durable, retryable, eventual consistency; Request-driven = immediate failure, requires retries/circuit breakers.
Choose event-driven for decoupled, high-throughput, async workflows or event sourcing. Choose request-driven for real-time, synchronous, low-latency APIs or simple CRUD.

AA13 — A load balancer distributes incoming traffic across multiple backend servers. Layer 4 (transport) routes based on IP/port (TCP/UDP), offering fast, protocol-agnostic forwarding. Layer 7 (application) routes based on HTTP headers, URLs, cookies, or content. Layer 7 is required when routing `/api/v1` vs `/api/v2`, terminating SSL, enforcing cookie-based session affinity, or applying content-based routing.

AA14 — A message queue (RabbitMQ) uses point-to-point or pub/sub routing, consumes/deletes messages after processing, and excels at task queues and complex routing. A log-based broker (Kafka) is an append-only log, retains messages, allows multiple consumers to read at their own pace, and supports replay. Pick RabbitMQ for task queues, lower throughput, or complex routing. Pick Kafka for event streaming, log aggregation, real-time analytics, or replayability.

AA15 — Containers share the host OS kernel and isolate processes/filesystems via namespaces/cgroups, making them lightweight and fast to start. VMs run a full guest OS with hardware virtualization via a hypervisor, providing stronger isolation but higher overhead. Containers are popular for microservices because they ensure environment consistency, minimize resource usage, enable rapid scaling, and integrate seamlessly with CI/CD and orchestration platforms like Kubernetes.

AA16 — Stateless services store no local session data; each request is independent. They scale horizontally easily because any instance can handle any request without affinity. Example: REST API, CDN. Stateful services maintain local session/cache/data. They require sticky sessions or distributed state, making horizontal scaling harder. Example: PostgreSQL, Redis, WebSocket server. Stateless is easier to scale because instances are interchangeable and load balancers can distribute evenly.

AA17 — An ORM maps objects to database tables, abstracting SQL generation and management. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs accelerate development, provide type safety, and simplify migrations, but can generate inefficient queries, obscure performance bottlenecks, and leak abstraction boundaries. Raw SQL offers full control, optimal performance tuning, and DB-specific features, but requires more boilerplate, is harder to maintain, and ties code to specific dialects.

AA18 — The Bulkhead pattern isolates resources (threads, connections, memory) per service/component to prevent cascade failures. It relates to resource isolation by ensuring one failing service doesn't exhaust shared infrastructure. Implementation: Assign dedicated thread pools and connection pools per downstream service. In deployment, separate critical and non-critical services into different node pools or Kubernetes namespaces with resource quotas/limits. Example: Payment service gets a dedicated thread pool; logging/metrics service gets a constrained pool.

AA19 — OT requires a central server to transform concurrent operations, ensuring strong consistency but demanding constant connectivity and complex algorithms. CRDTs are mathematical data structures that guarantee convergence without coordination, enabling decentralized operation. OT offers lower latency and simpler implementation but poor offline support. CRDTs handle network partitions gracefully, support full offline editing, and guarantee eventual consistency, but can have higher memory overhead and implementation complexity. Choose CRDTs for offline editing: they allow conflict-free local merging without server sync and guarantee convergence when connectivity returns.

AA20 — Distributed tracing in polyglot ecosystems faces instrumentation overhead, varying frameworks, and high data volume. Context propagation uses W3C Trace Context (`traceparent`) or B3 headers to carry trace/span IDs across HTTP/gRPC. Sampling: head-based (random at start, loses context) vs tail-based (sample after processing, preserves full trace, higher overhead; preferred for production). Storage/querying: Jaeger (OpenTelemetry native, rich UI) or Tempo (Loki-style, cost-effective for high volume). Async/Kafka: Trace context must be serialized into message headers (not body). Producers inject, consumers extract using OpenTelemetry propagators. Without explicit header propagation, spans break and trace continuity is lost.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, managing VMs with minimal overhead. Examples: VMware ESXi, Proxmox VE, KVM. Type 2 (hosted) hypervisors run on a host OS, using the host's drivers and kernel. Examples: VirtualBox, VMware Workstation. Type 1 is used in data centers for performance; Type 2 is used for desktop/server virtualization and development.

OP2 — SAN provides block-level storage, presenting virtual disks to servers. Used for databases, VMs, and performance-critical apps. Protocols: Fibre Channel, iSCSI, NVMe-oF. NAS provides file-level storage, mounted as network filesystems. Used for file sharing, backups, and home directories. Protocols: NFS (Linux), SMB/CIFS (Windows). Choose SAN for block access and low latency; NAS for easy file sharing and collaborative storage.

OP3 — 3-tier architecture uses Core (high-speed backbone), Distribution (policy/routing), and Access (edge/ports). It suffers from hierarchical bottlenecks, asymmetric routing, and limited east-west scalability. Leaf-spine replaces this with an all-to-all mesh where every leaf connects to every spine. It solves the core bottleneck, provides predictable low latency, simplifies scaling (add spine or leaf), and supports high east-west traffic efficiently.

OP4 — A highly available Proxmox cluster requires 3+ nodes (odd number for quorum). Shared storage: Ceph is recommended for distributed, self-healing block storage; iSCSI/NFS require HA controllers. Quorum: Majority of nodes must agree to prevent split-brain (3 nodes = 2 required). Fencing: STONITH via IPMI/iDRAC powers off failed nodes before VM migration. On node failure: HA manager detects failure, fences the node, verifies quorum, and restarts VMs on remaining healthy nodes.

OP5 — VLAN trunking carries multiple VLANs over a single physical link. 802.1Q adds a 4-byte tag to Ethernet frames containing the VLAN ID. Linux configuration: Create virtual interfaces with `ip link add link eth0 name eth0.10 type vlan id 10` (repeat for VLANs 20, 30). Assign IPs, enable forwarding, and use `systemd-networkd` or `NetworkManager` for persistence. Switch port must be configured as a trunk (802.1Q) to accept tagged traffic.

OP6 — RAID 1: Mirror, 50% capacity, 1 drive fault tolerance. RAID 5: Striping + single parity, N-1 capacity, 1 drive fault tolerance, slow rebuild. RAID 6: Striping + double parity, N-2 capacity, 2 drive fault tolerance, slower writes. RAID 10: Mirror + stripe, 50% capacity, 2 drive fault tolerance (different mirrors), fast IOPS. RAID Z2 (ZFS): Double parity, flexible capacity, instant snapshots, self-healing. For 6 drives on a DB server, choose RAID Z2: best balance of capacity, 2-drive fault tolerance, and safe rebuild performance. RAID 10 if maximum IOPS is prioritized over capacity.

OP7 — Recursive resolvers: Internal DNS servers (Windows DNS/BIND) for clients. Authoritative: Internal zone for AD (dynamic updates), external zone for public services. Forwarders: Point to ISP/Cloudflare for external queries. Conditional forwarding: Routes internal AD queries to internal DNS, external to forwarders. Split-horizon: Internal DNS returns private IPs for public domains; external returns public IPs. DNSSEC: Sign external zone, publish DS record at registrar. Laptop movement: DHCP assigns internal DNS; VPN client pushes DNS settings or uses split tunneling. DNSSEC validation works regardless of location; split-horizon ensures correct resolution based on network context.

OP8 — PKI chain: Root CA (offline, self-signed) -> Subordinate/Issuing CA (online, signed by root) -> End-entity certs (signed by issuing CA). Deployment: Root CA air-gapped. Subordinate CA online, handles issuance via certificate templates (key usage, validity, auto-enrollment via AD CS). Use CRL/OCSP for revocation. Compromised subordinate: Revoke issuing CA cert, issue new subordinate, reissue end-entity certs. Limited blast radius. Compromised root: Catastrophic. Requires rebuilding entire PKI, updating global trust stores, and revoking all certs. Root must be meticulously protected.

OP9 — MPLS: High reliability, low latency, predictable, expensive, carrier-managed. IPsec VPN: Cheap, internet-based, variable latency/reliability, manual management. SD-WAN: Intelligent routing, cost-effective, improves reliability/latency via QoS/path selection, centralized management, app-aware. WireGuard mesh: Lightweight, fast, secure, but lacks centralized management, routing intelligence, and SLA guarantees. Recommendation: SD-WAN. Best balance of cost, reliability, latency optimization, and centralized management. Ideal for VoIP (prioritizes voice traffic, handles internet failover gracefully).

OP10 — iDRAC (Dell), iLO (HPE), and IPMI are out-of-band management interfaces providing remote power control, console access, and hardware monitoring independent of the OS. Critical for data center recovery, remote maintenance, and hardware diagnostics. If exposed to the internet, attackers can exploit known vulnerabilities to gain root access, reset passwords, or mine cryptocurrency. Must be isolated on a management VLAN, use strong authentication/MFA, and restrict source IPs.

OP11 — LVM: Traditional volume manager, fixed-size volumes, COW snapshots that consume allocated space. LVM-Thin: Overprovisions storage, instant snapshots, space-efficient, but performance degrades if pool fills. ZFS: Integrated FS + volume manager, COW, instant snapshots that share blocks (space-efficient), supports compression, scrubbing, and self-healing. Use LVM for legacy/simple setups. LVM-Thin for virtualization/overprovisioning. ZFS for data integrity, advanced features, and modern storage workloads.

OP12 — Stretch cluster: 2 sites (A, B) + 1 tiebreaker (C or quorum disk). Ceph monitors split: 2 in A, 2 in B, 1 in C. CRUSH rules distribute OSDs across sites, ensuring replicas span sites. Network latency: <1ms ideal, <5ms acceptable; higher causes split-brain/performance degradation. Split-brain prevention: Odd monitor count + tiebreaker. Without a tiebreaker, a 2-site even split causes both sites to believe they have quorum, leading to data corruption. 2-site Ceph is generally bad without a tiebreaker due to latency ambiguity and quorum conflicts.

OP13 — DHCP dynamically assigns IP addresses and network config. DORA: Discover (client broadcasts), Offer (server responds), Request (client requests), Acknowledge (server confirms). If DHCP server is unavailable, client uses APIPA (169.254.x.x) or retains old IP if lease valid. On lease expiry, client attempts renewal at 50% (T1) and 87.5% (T2). If renewal fails, client reverts to APIPA/manual config and loses network connectivity.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, ACLs, SNMP, port security, and link aggregation. Enterprise importance: VLANs enable traffic segmentation and security; QoS prioritizes VoIP/video; STP prevents loops; ACLs enforce access control; SNMP enables monitoring; link aggregation increases bandwidth. Essential for scalable, secure, and manageable networks.

OP15 — NTP synchronizes system clocks over the network. Accurate time is critical for authentication (Kerberos, certificates), log correlation, distributed systems, backups, and clustering. Clock drift consequences: Kerberos auth failures, certificate validation errors, impossible log correlation, database replication lag, cluster split-brain, and backup corruption.

OP16 — Physical servers run directly on hardware with full control and maximum performance. VMs virtualize hardware, running guest OSes with good isolation. Containers share the host kernel, providing lightweight, fast app-level isolation. Run workloads on bare metal for high-performance computing, low-latency trading, GPU-intensive tasks, legacy hardware dependencies, maximum I/O performance, or strict compliance requirements.

OP17 — UPS provides battery-backed power for instantaneous switchover during outages, bridging the gap to generator startup. Generators provide long-term power using fuel, taking seconds/minutes to start. Both are needed: UPS handles surges, brownouts, and immediate transition; generator sustains power for extended outages. ATS (Automatic Transfer Switch) automatically detects utility failure, switches load to generator, and switches back when utility power is restored.

OP18 — Active-passive: One node handles traffic, standby takes over on failure. Simple, no split-brain risk. Active-active: Both handle traffic, requiring distributed DB sync or app-level routing. Complex. PostgreSQL HA with Pacemaker/Corosync: STONITH fencing via IPMI prevents split-brain. Virtual IP (keepalived/DRBD) floats to active node. Patroni/repmgr handles DB replication. Failover: Pacemaker detects node down, fences it, promotes standby, moves VIP, and updates DNS.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO define acceptable data loss and downtime, driving backup frequency and recovery procedures. Backup types: Full (baseline), Incremental (changes since last), Differential (changes since last full). Balance storage vs restore time. Deduplication reduces storage and backup windows. Media: Disk (fast restore), Tape (cheap offsite/long-term), Cloud (scalable/offsite). Immutable backups (WORM, air-gapped, object lock) protect against ransomware. Test restores regularly to verify integrity and measure RTO. Backup = data preservation. Disaster Recovery = comprehensive strategy (infrastructure, processes, failover) to restore operations after a disaster.

OP20 — 802.1X: Port-based NAC. Supplicant (client), Authenticator (switch/AP), Authentication Server (RADIUS). EAP-TLS: Mutual certificate auth, highly secure, requires PKI. PEAP: Tunnel, uses username/password + server cert, easier deployment. RADIUS centralizes auth, returns results + attributes (VLAN, ACL). Dynamic VLAN: Switch assigns VLAN based on RADIUS response, enabling policy-based access. Failure: Port remains unauthorized, blocking all traffic. MAB: Switch uses device MAC address as credential, queries RADIUS. Fallback for IoT/printers lacking 802.1X supplicant. Less secure, requires MAC whitelisting.
