CL1 — IaaS provides raw compute, network, and storage; you manage OS, middleware, runtime, and data. Example: AWS EC2. PaaS provides a managed runtime/environment; you manage application code and data. Example: Google App Engine. SaaS provides a fully managed application; you manage only configuration and user data. Example: AWS WorkSpaces.

CL2 — The Shared Responsibility Model divides security: provider secures the cloud infrastructure (physical, hypervisor, managed service components); customer secures what they put in it. IaaS VM: Provider = infra/hypervisor. Customer = OS, patching, host firewall, data, IAM, app code. Managed K8s: Provider = control plane, node OS, underlying networking. Customer = worker node config, app, secrets, network policies, RBAC, pod security. SaaS (M365): Provider = app, infra, patching, compliance framework. Customer = data, user access, MFA, sharing policies, endpoint security.

CL3 — VPC: Isolated virtual network boundary. Subnet: IP range within a VPC (public/private). Security Group (SG): Stateful firewall attached to ENI/instance; evaluates all allow rules, denies by default, automatically permits return traffic. NACL: Stateless firewall attached to subnet; evaluates rules in order, requires explicit allow/deny for both directions. Layering: Traffic enters VPC → hits NACL (subnet) → hits SG (instance). Stateful (SG) tracks connection state; Stateless (NACL) requires manual return rules.

CL4 — Landing zone: Pre-configured, secure multi-account foundation with baseline controls. OUs: Logical grouping (e.g., dev, prod, sandbox, shared services). Guardrails: SCPs, IAM boundaries, mandatory controls (logging, encryption, MFA). Shared Networking: Transit Gateway/Azure Hub-and-Spoke centralizes routing, peering, and policy enforcement. Centralized Logging: Dedicated logging account with CloudTrail/Log Analytics, strict access, immutable storage. Single-account problems: Unbounded blast radius, permission sprawl, billing opacity, compliance violations, accidental cross-environment deletion, lack of environment isolation.

CL5 — IaC: Declarative/programmatic management of infrastructure. Terraform/OpenTofu: HCL, state-based, vast provider ecosystem. Choose for broad cloud support, team familiarity, mature state management. Pulumi: Programmatic (TS/Python/Go), state-based. Choose for complex logic, existing codebases, strong typing. CloudFormation/Bicep: AWS-native, declarative, tightly integrated. Choose for AWS-only, rapid deployment, native features. Crossplane: K8s-native, manages cloud resources via CRDs. Choose for GitOps/K8s-centric teams, multi-cloud abstraction.

CL6 — HPA: Scales pods based on CPU/memory/custom metrics. VPA: Recommends/sets resource requests/limits per pod (requires restart). Cluster Autoscaler: Adds/removes nodes based on pending pods. KEDA: Event-driven scaling based on external triggers (queues, DB, HTTP). Use KEDA over HPA when workload load correlates with events (message queues, cron, webhooks) rather than resource utilization.

CL7 — RPO/RTO dictate acceptable data loss and downtime. Active-active: Both regions serve traffic; lower RPO/RTO, higher cost/complexity. Active-passive: One serves, one standby; higher RPO/RTO, lower cost. DB replication: Sync (strong consistency, higher latency, suits active-active) vs Async (eventual consistency, lower latency, suits active-passive). DNS failover: Route53/Traffic Manager health checks route to healthy region. State management: Externalize to Redis/DynamoDB/S3; avoid local disk state. Cost: Active-active doubles infra + data transfer; active-passive saves compute but needs replication/storage. Pilot light: Core infra running at minimal scale. Warm standby: Scaled-down but fully functional. Multi-site active-active: Fully operational in both regions.

CL8 — GitOps: Git as single source of truth; declarative sync from Git to cluster via operators that reconcile state. ArgoCD: Push/pull, UI, app-of-apps, easier onboarding. FluxCD: Pull-only, Git-native, modular, strict GitOps philosophy. Secrets: Sealed Secrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from cloud/Vault), Vault (dynamic secrets, auth). Drift: Controllers detect manual changes and automatically revert to match Git state.

CL9 — StatefulSet: Stable network ID, ordered deployment/termination, stable storage. PV/PVC with local storage: `local` storageClass, `volumeBindingMode: WaitForFirstConsumer` ensures node affinity. Headless service: `clusterIP: None` enables direct pod DNS resolution. Init containers: Pre-load config, check dependencies, mount volumes before main app. ConfigMaps as volume mounts: Mount at specific paths via `subPath` or direct mount. PDB: `minAvailable: 1` or `maxUnavailable: 0` ensures critical stateful pods survive disruptions.

CL10 — SA: K8s native identity, no cloud IAM binding by default. IRSA (AWS): Binds K8s SA to AWS IAM role via OIDC; pods assume role via STS. Workload Identity (GCP/Azure): OIDC-based federation for cloud resource access. Mounting static credentials in pods is bad practice: leads to leakage, rotation issues, excessive permissions, and audit gaps. Workload identity federation solves this via OIDC token exchange, short-lived credentials, least privilege per workload, and automatic rotation.

CL11 — Object (S3/Blob): Unstructured, HTTP API, highly scalable. Durability: 99.999999999%. Availability: High across AZs. Use: Backups, media, data lakes. Block (EBS/Managed Disk): Raw volumes, attached to VM, low latency, consistent. Durability: 99.9999%. Availability: AZ-bound (unless replicated). Use: OS, databases, apps needing file system. File (EFS/Azure Files): NFS/SMB, shared, scalable. Durability: 99.999999999%. Availability: Regional/AZ-redundant. Use: Shared configs, home dirs, legacy POSIX apps.

CL12 — Network policies: Default deny, explicit allow for pod-to-pod/external. Service mesh (mTLS): Istio/Linkerd for encrypted service-to-service, identity-based routing. Pod identity: IRSA/Workload Identity for cloud access. Admission controllers (OPA/Kyverno): Enforce policies (no root, signed images, resource limits). Image signing: Cosign/Notary + admission rejection of unsigned. Runtime security: Falco monitors syscalls, detects anomalies. Secrets: External Secrets Operator/Vault, never plaintext in Git/etcd. vs Perimeter: Traditional trusts internal network; zero-trust verifies every request, micro-segments, enforces least privilege, and continuously validates identity/context.

CL13 — CDN: Distributed edge cache network that stores content closer to users, reducing latency and offloading origin. Cloud-native: AWS CloudFront, Azure Front Door. Use CDN for static assets, video, global distribution, DDoS mitigation. Serve directly from origin for dynamic, personalized, or highly volatile data where caching adds complexity or stale content risk.

CL14 — Region: Geographic area with multiple AZs. AZ: Isolated data center within a region (independent power, cooling, networking). Deploy across multiple AZs to survive single-AZ failure, improving availability. Zonal resources: Tied to one AZ (EBS, NAT GW). Regional resources: Span multiple AZs (ALB, RDS Multi-AZ, S3).

CL15 — Managed DB (RDS/Cloud SQL/Azure SQL): Provider handles provisioning, patching, backups, HA, monitoring, scaling, and maintenance windows. Self-hosted on VM: You manage OS, DB software, config, backups, failover, security patches, and performance tuning. Managed saves operational overhead and improves reliability.

CL16 — IAM Users: Human/service identities. Groups: Collections of users. Roles: Temporary credentials for AWS services/external entities. Policies: JSON permissions. Least privilege: Grant only necessary permissions. Apply via scoped policies, avoid `*`, use IAM Access Analyzer, enforce MFA, use roles over long-term keys, and regularly audit permissions.

CL17 — Serverless: Managed compute, auto-scaling, pay-per-use. Lambda/Functions/Cloud Functions. Cold starts: First invocation after idle period requires provisioning; matters for latency-sensitive apps. Poor fit: Long-running processes, stateful apps, predictable high throughput (provisioned may be cheaper), strict compliance/network constraints.

CL18 — Ingress resource: Standard K8s API, relies on controller (NGINX/ALB). TLS termination at controller. Gateway API: Modern, structured, separates traffic routing (Gateway) from backend routing (HTTPRoute). TLS at Gateway. Cloud LB annotations: Direct cloud LB integration. TLS at LB. Service mesh ingress: Istio/Linkerd gateway. mTLS, advanced traffic mgmt. Use Gateway API over Ingress for multi-tenant environments, fine-grained RBAC, structured routing, and future-proofing.

CL19 — RI/SP: Commit to usage for 1-3 yrs. RI = specific instance, SP = flexible. Spot = up to 90% discount, interruptible. Right-sizing: Monitor utilization, downsize over-provisioned, use auto-scaling. Storage tiering: S3 Intelligent-Tiering, Glacier for archives, delete snapshots. Idle detection: CloudHealth, Cost Explorer, Azure Advisor. Tagging, shutdown schedules. FinOps: Cross-functional team, cost accountability culture, showback/chargeback via tags/cost allocation. Tools: Kubecost, CloudHealth, native cost tools, custom dashboards, monthly reviews.

CL20 — Abstraction: K8s (EKS/AKS), Terraform, Crossplane, service mesh. Networking: Cloud VPN, Direct Connect/ExpressRoute, global load balancers. Identity: OIDC federation, centralized IAM proxy, SAML. Trade-offs: Complexity, data egress costs, inconsistent features, operational overhead. Justified: Regulatory/data sovereignty, vendor failure risk, specific service needs. Unnecessary: Most workloads run efficiently single-cloud; multi-cloud often adds cost without proportional benefit.

OT1 — Purdue Model (ISA-95): Level 0: Physical process (sensors/actuators). Level 1: Control devices (PLCs, RTUs). Level 2: SCADA/HMI. Level 3: Plant operations (historian, MES). Level 4: Enterprise (ERP, business planning). Level 5: Corporate network.

OT2 — IT networks prioritize confidentiality/integrity, use standard protocols, and tolerate frequent patching. OT networks prioritize availability/safety, use legacy/real-time protocols, and have long lifecycles. Standard IT patching is unsafe in OT: untested patches can crash controllers, trigger safety systems, or cause process disruption; maintenance windows are often unavailable.

OT3 — IDMZ: Segmented zone between IT (L4) and OT (L1-L3). Traffic: Strictly controlled bidirectional or one-way. Typically OT→IT for data, IT→OT for commands via OPC UA/HTTPS or MQTT. Direct L4→L1 connectivity is dangerous: exposes real-time control to internet threats, bypasses safety controls, and risks catastrophic process disruption.

OT4 — Modbus TCP: L1/L2, simple, unencrypted, widely used. OPC UA: L2/L3, secure, structured, cross-platform, modern standard. EtherNet/IP (CIP): L1/L2, industrial Ethernet, Rockwell dominant. PROFINET: L1/L2, real-time Ethernet, Siemens dominant. MQTT: L3/L4, lightweight pub/sub, cloud/edge analytics.

OT5 — Data diode: Hardware-enforced one-way communication; physically prevents return traffic. Firewall: Bidirectional, inspects traffic, can be misconfigured or bypassed. Use diode for critical safety systems or high-security OT zones requiring strict data exfiltration prevention. Limitation: Cannot send commands/acknowledgments back, restricting bidirectional control.

OT6 — Flow: PLCs → Historian (L3) → OPC UA Server → Edge Gateway (protocol translation, buffering) → MQTT Broker → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: IDMZ between L3/L4, TLS/mTLS everywhere, edge gateway authentication, cloud IAM, network segmentation, firewall/data diode at IDMZ.

OT7 — IEC 62443: Zone = logical grouping of assets with similar security requirements. Conduit = communication path between zones. Model: Zone 1: SIS (highest security, isolated). Zone 2: PLCs/Control. Zone 3: SCADA/HMI/Historian. Zone 4: Engineering workstations. Zone 5: Corporate/IT. Conduits: Strictly controlled, firewalls/data diodes, least privilege, monitored. SIS zone isolated from all others.

OT8 — VLANs: Segment by function/process line (e.g., VLAN 10-13 for lines, 20 for HMIs, 30 for SCADA, 40 for engineering). Firewall: Between VLANs, enforce strict ACLs, log all traffic. Switch: Managed industrial switches, port security, 802.1X where possible. Remote access: Jump host in DMZ, MFA, session recording, time-bound, vendor-specific credentials. Transition: Phased rollout, parallel run, backup configs, maintenance windows, rollback plan, minimal disruption testing.

OT9 — BPCS: Basic process control (PLC/DCS), maintains normal operation. SIS: Independent safety system, triggers on dangerous conditions to bring to safe state. IEC 61511: Safety lifecycle standard for SIS. Isolation prevents cyber attacks from compromising safety functions. Ransomware on SIS: Could disable safety interlocks, leading to catastrophic failure, environmental damage, or loss of life.

OT10 — PLC: Discrete control, fast, localized, handles I/O. DCS: Centralized control, integrated I/O, suited for continuous processes (chemical, oil). SCADA: Supervisory, data collection, HMI, remote monitoring, spans large geographic areas. Coexist: Yes, common in large plants. PLCs/DCS handle control, SCADA supervises.

OT11 — Remote access: Jump hosts in DMZ, MFA, session recording. Vendor access: Time-limited, role-based, approved changes only, no direct HMI access. RDP directly to HMI from corporate network is unacceptable: exposes HMI to corporate threats, bypasses segmentation, increases attack surface, and violates Purdue model.

OT12 — Detection: Passive IDS (Zeek/Suricata), anomaly detection on OT protocols, asset inventory baseline. Response: Isolate compromised L3 segments, preserve logs, engage control room, verify physical safety, coordinate with plant operator. Operator role: Monitor physical process, execute manual overrides if needed, ensure safety, communicate status. Safe ops: Maintain manual control capability, verify SIS integrity, avoid automated responses that could disrupt process.

OT13 — HMI: Operator interface for monitoring/control. Displays process data, allows manual overrides. vs Engineering Workstation: HMI for operators (run mode). EWS for engineers (programming, configuration, diagnostics).

OT14 — Historian: Time-series database for process data (temp, pressure, flow). Importance: Trend analysis, compliance, optimization, troubleshooting. Plant historian (L3): High-frequency, raw process data. Enterprise historian (L4): Aggregated, business-relevant data for reporting/ERP.

OT15 — Ladder logic: Graphical programming language mimicking relay circuits. Executed by PLCs. Dominant: Familiar to electricians, easy to debug, deterministic, widely supported, legacy codebase inertia.

OT16 — RTU: Remote Terminal Unit, designed for harsh environments, long-distance communication, telemetry, often serial/SCADA focused. PLC: Local control, faster I/O, more complex logic, factory floor. RTU use: Pipelines, utilities, remote sites, SCADA telemetry.

OT17 — Analog: Continuous (4-20mA, 0-10V). Digital: Discrete (on/off). 4-20mA preferred: 4mA live zero detects wire breaks (0mA = fault), less susceptible to noise, industry standard, robust.

OT18 — Asset inventory: Complete list of hardware, firmware, network configs, communication paths. Foundation: Can't secure what you don't know. Enables patching, vulnerability mgmt, segmentation. Tools: Passive monitoring (packet capture, protocol analysis), active scanning (limited, risky). Active scanning dangerous: Can crash legacy devices, trigger safety systems, cause process disruption.

OT19 — MITRE ATT&CK for ICS: Tactics/techniques specific to ICS/OT. Examples: Reconnaissance (Gather Process Control Information), Resource Development (Acquire Infrastructure), Initial Access (Exploit Remote Services), Execution (Command and Scripting Interpreter), Persistence (Create Account), Privilege Escalation (Exploit Privilege Escalation), Defense Evasion (Indicator Removal), Collection (Data from Local System), Command and Control (Protocol Tunneling), Impact (Inhibit Response Function). vs Enterprise: Focuses on physical process impact, safety, legacy protocols, real-time constraints. Use: Gap analysis, control mapping, red teaming, defensive tuning.

OT20 — Log collection: Passive taps, OT-friendly agents, buffer to avoid latency, forward to SIEM. SIEM: Correlate IT/OT logs, normalize OT protocols. Detection rules: OT-specific (unexpected PLC write, abnormal valve movement, protocol anomalies). Triage: OT engineers validate process impact, IT analysts handle network/endpoint. Escalation matrix. Staffing: IT analysts (threat intel, malware), OT engineers (process safety, protocol expertise). False positives: Tune rules to baseline, involve OT engineers, prioritize safety-critical alerts. Unauthorized firmware alert: Isolate PLC, verify backup, assess process impact, coordinate with engineering, restore from known good, investigate root cause, update change management.
