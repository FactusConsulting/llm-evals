## Kubernetes

**K1** — A **Deployment** manages stateless workloads: pods are interchangeable, have random names, and are replaced without order. A **StatefulSet** manages stateful workloads: pods have stable, unique network identities (e.g., `app-0`, `app-1`), ordered deployment/scaling, and stable storage bindings that persist across restarts.

**K2** — `kube-proxy` watches Service objects and creates iptables/IPVS rules mapping the Service's `ClusterIP:Port` to the backend Pod IPs. When traffic hits the ClusterIP, the node's netfilter redirects it to one of the healthy pod IPs using round-robin or least-connection load balancing.

**K3** — A **PersistentVolume (PV)** is a cluster-wide storage resource provisioned by an admin or dynamically. A **PersistentVolumeClaim (PVC)** is a user's request for storage matching size/access mode. A **StorageClass (SC)** defines the provisioning template (e.g., `gp3`, `standard`). Relation: PVCs bind to PVs (static) or trigger an SC to dynamically provision a PV (dynamic).

**K4** — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` to inspect Exit Codes, OOMKilled events, and probe failures. 3. Verify resource requests/limits and node capacity (CPU/Memory pressure). 4. Check mounted ConfigMaps/Secrets, environment variables, and binary/executable paths for missing or invalid configs.

**K5** — CoreDNS provides internal DNS resolution for Service names and cluster-internal endpoints. If CoreDNS pods are down, pods cannot resolve internal service names or cluster DNS records, breaking inter-service communication. External DNS resolution remains unaffected.

**K6** — The scheduler uses **filtering** (predicate functions) to eliminate ineligible nodes, then **scoring** (priority functions) to rank remaining nodes. Factors considered: (1) Resource utilization (LeastRequestedPriority favors less loaded nodes), (2) Node Affinity/Taints & Tolerations, (3) Pod Topology Spread Constraints, (4) Inter-Pod Affinity/Anti-Affinity, (5) Volume binding constraints.

**K7** — Yes, it will schedule: 3.5GB + 256Mi ≈ 3.75GB < 4GB node capacity. At runtime, if it uses 600Mi, it exceeds the `limits.memory: 512Mi`. The cgroup enforces the limit, the kernel OOM-killer terminates the container, and Kubernetes restarts the pod (potentially triggering CrashLoopBackOff if the leak persists).

**K8** — Client → External Cloud LB (routes to Ingress Controller IP) → Ingress Controller (NGINX) parses Ingress resource → matches `host`/`path` → forwards to Kubernetes Service → Service resolves to Endpoints (Pod IPs) → `kube-proxy`/iptables redirects traffic to the target Pod → Pod handles request.

**K9** — A `NetworkPolicy` restricts ingress/egress traffic to/from pods using label selectors and port/protocol rules. Default behavior (no policy): all traffic allowed. When applied: only traffic explicitly permitted by the policy is allowed; all other traffic is denied.

**K10** — `RollingUpdate` gradually replaces old pods with new ones (zero downtime, supports health checks). `Recreate` terminates all existing pods before creating new ones (causes downtime). Choose `Recreate` for stateful apps, shared storage mounts, or when configuration changes require a full restart to take effect.

**K11** — A namespace provides logical isolation and resource scoping within a cluster. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

**K12** — `kubectl describe pod` shows detailed runtime state. Unlike `get pod`, it displays: (1) Events (scheduling, pull, restart history), (2) Conditions (Ready, Initialized, PodScheduled), (3) Resource limits/requests, (4) Mounted volumes/ConfigMaps/Secrets, (5) Container status details (state, restart count, probe results).

**K13** — A `ConfigMap` stores non-sensitive configuration data. Pods consume it via: (1) Volume mounts (files appear in a directory), (2) Environment variables (key-value pairs injected into the container).

**K14** — `ClusterIP`: internal-only, reachable only within the cluster. `NodePort`: exposes the service on a static port on each node's IP (`<NodeIP>:<NodePort>`). `LoadBalancer`: provisions a cloud provider's external load balancer, exposing the service publicly with a stable external IP.

**K15** — A `DaemonSet` ensures one pod runs on every node (or subset via selector). Use it for node-level daemons: logging agents (Fluentd), monitoring (Prometheus node-exporter), network plugins (CNI), or storage drivers. Unlike Deployments, it focuses on node coverage, not replica count.

**K16** — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes based on labels. Taints/tolerations are node-driven (repel/allow); affinity is pod-driven (attract). Use case taints: dedicate GPU nodes to ML workloads. Use case affinity: schedule to specific AZs or hardware tiers.

**K17** — An Operator is a custom controller that manages complex, stateful applications using Custom Resource Definitions (CRDs). Unlike standard controllers (which watch basic resources), Operators encode operational knowledge (backups, upgrades, scaling, failover) into code, automating lifecycle management and reducing manual DevOps toil.

**K18** — etcd uses a **linearizable** consistency model via the Raft consensus algorithm. If quorum is lost, the cluster becomes read-only/unwritable. Recovery from 2/3 node loss: restore from the latest snapshot/wal backup, add a new etcd node, join it to the cluster, and run `etcdctl snapshot restore` to rebuild the datastore.

**K19** — RBAC controls access via Roles/ClusterRoles (define permissions) and RoleBindings/ClusterRoleBindings (bind roles to users/groups/serviceaccounts). Manifests for read-only pods/logs in one namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev-namespace
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev-namespace
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — Default `ndots=5` in `/etc/resolv.conf` causes the resolver to try 5 parent domains before using search domains, generating excessive DNS queries for external hosts. Fix: add `dnsConfig` to the pod spec:
```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "2"
```

## Development

**D1** — `git merge` creates a merge commit, preserving branch history. `git rebase` rewrites commits onto a new base, creating a linear history. Avoid rebasing on shared/public branches or after pushing to remote, as it rewrites history and causes conflicts for collaborators.

**D2** — **TCP**: connection-oriented, reliable, ordered delivery, flow/congestion control. **UDP**: connectionless, unreliable, low latency, no ordering. TCP examples: HTTP, FTP, SSH. UDP examples: DNS, VoIP, live video streaming.

**D3** — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to unpredictable results. Example: Two threads increment a shared counter without a mutex; final value may be less than expected due to lost updates.

**D4** — **Symmetric encryption** uses one key for encrypt/decrypt (fast). **Asymmetric encryption** uses a public/private key pair (secure key exchange). In TLS: asymmetric crypto authenticates the server and exchanges a session key; symmetric crypto encrypts all subsequent data transfer.

**D5** — Each Dockerfile instruction creates a read-only image layer. Layer caching skips rebuilding unchanged layers. Best practices: order instructions from least to most frequently changing, combine `RUN` commands, use `.dockerignore`, and place dependency installation before source code copy.

**D6** — Order of checks: 1. Verify backend health/endpoints (is the service actually up?). 2. Check rate limiting/throttling or circuit breakers. 3. Inspect resource exhaustion (CPU/memory limits, connection pools). 4. Validate downstream dependencies (database, external APIs, cache).

**D7** — CAP theorem: a distributed system can only guarantee two of Consistency, Availability, Partition tolerance. **CP** (Consistency + Partition tolerance): banking ledger, distributed SQL (HBase, CockroachDB). **AP** (Availability + Partition tolerance): DNS, Cassandra, DynamoDB.

**D8** — **Horizontal scaling** adds more nodes/instances; **vertical scaling** increases resources (CPU/RAM) of an existing node. Horizontal scaling requires: stateless services, distributed databases, message queues, container orchestration, and externalized sessions/cache.

**D9** — An environment variable is a dynamic key-value pair that influences process behavior. To persist across sessions on Linux: add `export VAR_NAME="value"` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

**D10** — **JSON**: strict syntax, key-value pairs, arrays. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: universal parsing, strict schema validation. YAML advantage: readability, less boilerplate, better for config files.

**D11** — A REST API is an architectural style using HTTP methods to interact with resources. **GET**: retrieve data. **POST**: create a new resource. **PUT**: update/replace a resource. **DELETE**: remove a resource.

**D12** — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes from minor/patch updates, and simplifies debugging and compliance auditing.

**D13** — **Compiled languages** translate source code to machine code before execution (C++, Rust). **Interpreted languages** execute source code line-by-line via a runtime (Python, JavaScript). Note: many modern languages use hybrid approaches (JIT compilation).

**D14** — A **forward proxy** sits on the client side, routing outbound traffic (e.g., corporate internet proxy). A **reverse proxy** sits on the server side, routing inbound traffic to backend servers. Examples: NGINX (SSL termination, load balancing), HAProxy (high-performance TCP/HTTP routing).

**D15** — A deadlock occurs when two or more processes wait indefinitely for resources held by each other. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait. All must hold simultaneously.

**D16** — Eventual consistency guarantees that if no new updates occur, all replicas will eventually converge. Cassandra handles read-after-write via tunable consistency levels (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`, `SERIALIZABLE`). For strong read-after-write, use `QUORUM` or `SERIALIZABLE` with `CAS`/`LWT`, or implement client-side session consistency.

**D17** — mTLS requires both client and server to present valid certificates. Handshake: ClientHello → ServerHello + ServerCert → Client verifies server cert → ClientKeyExchange + ClientCert → Server verifies client cert → both derive session keys. Commonly used in: service meshes (Istio/Linkerd), zero-trust architectures, and internal microservice communication.

**D18** — A hash table maps keys to values using a hash function to compute bucket indices. Collision resolution: **chaining** (linked lists at each bucket), **open addressing** (probing: linear, quadratic, double hashing). Time complexity: average O(1) for insert/lookup/delete; worst-case O(n) if all keys collide (poor hash function or high load factor).

**D19** — A circuit breaker prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal traffic), **Open** (fail fast, trip after error threshold), **Half-open** (allow limited test requests). Relates to retries/backoff: circuit breakers stop infinite retries during outages; exponential backoff is applied within closed/half-open states to avoid overwhelming recovering services.

**D20** — **Optimistic concurrency** assumes no conflicts, validates at commit (e.g., row versioning, `UPDATE ... WHERE version = ?`). **Pessimistic concurrency** locks resources during read/write (e.g., `SELECT ... FOR UPDATE`, row locks). Choose optimistic for high-read/low-conflict workloads; choose pessimistic for high-contention or critical financial transactions.
