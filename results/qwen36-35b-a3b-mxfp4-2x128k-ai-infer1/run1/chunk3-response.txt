T1 — `tofu plan` calculates the desired state vs. current state and produces a dry-run execution plan showing what will be created, updated, or destroyed. `tofu apply` executes that plan, makes API calls to provision/update infrastructure, and updates the state file. Plan is for review; apply is for execution.

T2 — State is a JSON file mapping your configuration to real-world resources (IDs, attributes, dependencies). Remote state is important for team collaboration, secure storage, state locking to prevent concurrent writes, and CI/CD integration. It keeps state out of VCS and enables consistent infrastructure across environments.

T3 — `count` uses integer indices (`0`, `1`, `2`) and is simple but prone to index drift when items are added/removed. `for_each` uses maps or sets with stable keys, preserving resource identity across changes. `for_each` is preferred for non-sequential naming, avoiding index drift, and when you need to reference resources by meaningful keys.

T4 — OpenTofu detects drift during `plan` by comparing the state file to live infrastructure. If a resource was modified externally, `plan` shows an in-place update or destroy/create. `apply` will revert changes to match your config unless `lifecycle { ignore_changes = [...] }` or `create_before_destroy` is configured.

T5 —
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `terraform_remote_state` reads the entire state file, which can be slow, expose sensitive data, and create tight coupling. Output values are explicit, versioned, and scoped. Recommended alternative: Pass outputs as input variables to the consuming module. Why: explicit contract, better performance, security, and easier testing/mocking.

T7 — The `output` block is evaluated during the plan/apply phase, but `remote-exec` provisioners run asynchronously during apply. The output may read the kubeconfig file before the provisioner finishes writing it, resulting in an empty value. Fix: Add `depends_on = [null_resource.kubeconfig]` to the output block, or use a `local_file` resource with `triggers` tied to the cluster resource's readiness.

T8 — `tofu import` CLI manually maps an existing resource to a config block, requiring manual writing and prone to drift. The `import` block (1.5+) is declarative, auto-generates config, supports multiple resources, and integrates cleanly into CI/CD. It reduces manual errors and aligns with Infrastructure-as-Code principles.

T9 — A `variable` block defines expected input values for a module/root (validated, typed). An `output` block exposes computed values from a module/root to other modules or the state. Variables flow in; outputs flow out.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a specific platform. Running `tofu plan` without `tofu init` fails because providers aren't downloaded, plugins are missing, and the backend isn't configured, leaving OpenTofu unable to interact with infrastructure.

T11 — `.terraform.lock.hcl` pins provider versions, checksums, and supported platforms. It should be committed to VCS to ensure reproducible builds, prevent supply chain attacks, and guarantee that all team members/CI use identical provider versions.

T12 — `tofu destroy` destroys all resources tracked in the current state. Target a single resource with `tofu destroy -target=<resource_address>` (e.g., `tofu destroy -target=aws_instance.web`).

T13 — A data source reads existing infrastructure or external data without managing it. Example: `aws_ami` to find the latest Ubuntu AMI, or `aws_vpc` to reference an existing VPC. Use data sources when you need to reference pre-existing resources rather than create new ones.

T14 — `variable` blocks accept external inputs, support validation, and are typed. `locals` compute internal values, lack validation, and are used for transformations, avoiding repetition, or complex expressions. Use `locals` for derived values within a module; use `variables` for external configuration.

T15 — `lifecycle` controls resource behavior:
- `create_before_destroy`: Creates new instance before destroying old (zero-downtime). Tradeoff: temporary duplicate resources.
- `prevent_destroy`: Blocks `destroy` operations. Tradeoff: manual state manipulation needed to remove.
- `ignore_changes`: Ignores drift on specific attributes. Tradeoff: masks external modifications, may hide misconfigurations.

T16 — The `moved` block tracks resource address changes without destroying/recreating. It helps refactor modules, rename resources, or change types while preserving state. OpenTofu maps old addresses to new ones, preventing drift and downtime.

T17 — OpenTofu builds a DAG of dependencies. Implicit dependencies are inferred from config references. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, reducing parallelism. Use sparingly to avoid blocking unrelated resources and slowing plans/applies.

T18 — Strategies to reduce plan time:
1. `tofu plan -refresh=false`: Skips state refresh. Tradeoff: stale state, may miss drift.
2. Modularize/Split state: Separate into multiple workspaces/modules. Tradeoff: increased operational complexity.
3. `tofu plan -target=<resource>`: Plan only specific resources. Tradeoff: doesn't fix full-plan latency.
4. Reduce data source calls/cache: Cache results or use static values. Tradeoff: less dynamic, may require manual updates.

T19 — State locking prevents concurrent writes using a backend-specific mechanism (e.g., DynamoDB). If a lock isn't released (CI crash), run `tofu force-unlock <lock_id>`. Risks: data corruption, lost changes, or race conditions if another process is actively modifying state.

T20 — Steps:
1. Create S3 bucket & DynamoDB table for locking.
2. Add backend config (`backend "s3" { ... }`) to config.
3. Run `tofu init` (prompts to copy state to S3).
4. Existing state is copied to S3; local state becomes a pointer.
5. Verify: `tofu state list` should match, S3 object exists, DynamoDB has lock entries. Ensure no concurrent operations during migration.

A1 — A playbook is a YAML file defining automation steps. A role is a reusable collection of tasks, handlers, vars, and templates. A task is a single unit of work (module execution). Playbooks orchestrate roles/tasks; roles package them for reuse.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_os_family }}`.

A3 — `command`: runs commands without shell features (safer). `shell`: runs via shell, supports pipes/redirects. `raw`: runs without Python, ideal for bootstrapping or unbootstrapped hosts. Use `command` for safety, `shell` for shell features, `raw` for low-level/initial setup.

A4 — Idempotency means a task produces the same result if run multiple times. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run).

A5 —
```yaml
- name: Install htop conditionally
  package:
    name: htop
  when: ansible_os_family == "Debian"

- name: Install EPEL and htop on RedHat
  block:
    - name: Install EPEL release
      package:
        name: epel-release
    - name: Install htop
      package:
        name: htop
  when: ansible_os_family == "RedHat"
```

A6 — Variable precedence (highest to lowest): Extra vars (`-e`) > Play vars > Role vars > Group vars > Host vars > Role defaults. Extra vars override everything; role defaults are lowest priority.

A7 — Use `serial: 3` in the playbook. Inventory groups: `[rke2_first]`, `[rke2_rest]`. Run first batch, then use `wait_for` to check node readiness (e.g., port 6443 or kubelet health) before proceeding to the rest. Example: `wait_for: port=6443 timeout=300`.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string --name 'my_secret' 'my_value'` or manually wrap the line in a vars file with `!vault | <base64>`.

A9 — An inventory file lists hosts and groups. Static inventory is a hardcoded file. Dynamic inventory is a script/API that generates inventory on the fly (e.g., cloud provider APIs), ideal for ephemeral infrastructure.

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task triggered by `notify`, runs only if notified, and executes once per play at the end. Differs from regular tasks (run immediately). Trigger with `notify: handler_name`.

A12 — `ansible.cfg` configures global Ansible behavior. Common settings: `inventory`, `remote_user`, `forks`, `private_key_file`, `host_key_checking`, `log_path`.

A13 — `register` saves task output to a variable. Use in subsequent tasks via `when: my_var.stdout == "success"` or `debug: var=my_var`.

A14 — `include_tasks` is dynamic (evaluated at runtime), supports `when`/`loop`. `import_tasks` is static (evaluated at parse time), faster but doesn't support conditionals. Use `include_tasks` for dynamic logic; `import_tasks` for static, performance-critical includes.

A15 — Ansible Galaxy is a repository for roles and collections. `requirements.yml` lists dependencies with versions. Install via `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible connects to hosts. `ssh`: standard SSH for Linux/Unix. `local`: runs on the control node. `network_cli`: for network devices (Cisco, Juniper) using CLI. Use `ssh` for servers, `local` for localhost tasks, `network_cli` for network gear.

A17 — `delegate_to` runs a task on a specified host. `run_once` runs a task once across all hosts. Example: Gather facts from a remote host, then process on `localhost` once:
```yaml
- name: Process remote data on control node
  debug:
    msg: "{{ remote_data }}"
  delegate_to: localhost
  run_once: true
  vars:
    remote_data: "{{ ansible_facts }}"
```

A18 — Performance strategies:
1. Increase `forks` (e.g., 50): Tradeoff: higher memory/CPU on control node.
2. Enable `pipelining`: Tradeoff: requires passwordless sudo or specific config, reduces SSH overhead.
3. Fact caching: Tradeoff: stale facts if not refreshed, requires cache backend.
4. Use Mitogen: Tradeoff: compatibility issues with some modules, but massive speedup via multiplexing.

A19 — Jinja2: `{{ }}` for expressions/variables, `{% %}` for control flow (loops, ifs), `{# #}` for comments.
Template snippet:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check: {{ server }}
  server {{ server }};
{% endfor %}
}
```

A20 — Rolling deployment structure:
- `serial: 1` (or 2)
- `pre_tasks`: Deregister from LB via `uri` module (call LB API to remove host)
- `tasks`: Deploy new version
- `post_tasks`: Health check via `uri` module (`/healthz`, `status_code: 200`)
- `block/rescue`: `block` contains deploy+healthcheck; `rescue` rolls back (re-add to LB, revert version) on failure. Ensures zero downtime and automatic rollback.
