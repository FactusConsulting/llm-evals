G1 — A Go array has a fixed size baked into its type (`[N]T`), while a slice is a dynamic view over a contiguous backing array (`[]T`) containing a pointer, length, and capacity. When you `append` to a slice that has reached its capacity, the runtime allocates a new backing array (typically 2x the old capacity), copies the existing elements, updates the slice header, and returns the new slice.

G2 — `var x int` declares a variable with explicit type and zero value; `x := 0` is a short variable declaration that infers the type. You cannot use `:=` outside function bodies, when redeclaring an existing variable in the same scope without assigning a new value, or alongside `var`/`const`/`type` declarations.

G3 — A goroutine is a lightweight, user-space thread managed by the Go runtime (~2-4KB stack vs ~1-2MB OS thread). The GMP scheduler maps Goroutines (G) to logical processors (P) that run on OS threads (M). P holds a run queue of Gs, enabling work-stealing, non-blocking syscalls via M parking, and efficient M:N scheduling without OS thread context switches for every G.

G4 — Channels are typed conduits for sending/receiving values between goroutines. Unbuffered channels block both sender and receiver until both are ready. Buffered channels allow sends to succeed until the buffer is full. Sending to a full buffered channel blocks until a receiver consumes a value.

G5 — `context` propagates cancellation, deadlines, and request-scoped values across API boundaries. Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
client.Do(req) // cancels if timeout exceeds 5s
```

G6 — Go uses structural (duck-typing) interface satisfaction: any type implementing the methods automatically satisfies the interface. Java/C# require explicit declaration. `interface{}` (Go 1.18+) / `any` is a type-erased container. Powerful for generic utilities and JSON, but dangerous because it bypasses compile-time type safety and can hide runtime panics.

G7 — The code has a data race: `ready` and `data` are accessed concurrently without synchronization, violating Go's memory model (writes in one goroutine aren't guaranteed visible to another). Fix with `sync/atomic` (e.g., `atomic.Bool` + `atomic.StorePointer`/`LoadPointer`) or a channel/mutex to establish a happens-before relationship.

G8 — `sync.Mutex` blocks all concurrent access; `sync.RWMutex` allows multiple readers or one writer. `sync.Map` is optimized for read-heavy workloads or disjoint key sets (low contention), but has higher overhead for writes and sequential reads compared to a `map` + `Mutex`/`RWMutex`. Use `sync.Map` only when profiling shows it outperforms a locked map.

G9 — `go.mod` declares module path, Go version, and direct dependencies. `go.sum` stores cryptographic checksums of dependency versions for integrity. `go mod tidy` removes unused deps, adds missing ones, and cleans `go.mod`. MVS (Minimum Version Selection) resolves transitive dependencies by picking the highest version required by any direct/indirect dependency, ensuring deterministic builds.

G10 — `defer` schedules a function call to run after the surrounding function returns. Multiple defers execute in LIFO order. Classic gotcha: in pre-Go 1.22 loops, deferred closures captured the loop variable by reference, causing all defers to see the final value. Go 1.19+ fixed this; modern code should still avoid capturing loop vars in deferred closures or use explicit scoping.

G11 — A pointer holds a memory address. Its zero value is `nil`. Create a pointer to a struct literal with `&MyStruct{Field: value}`. Pointers enable mutation, avoid copying large structs, and are required for channels/interfaces.

G12 — `init()` runs automatically before `main()` during package initialization. A package can have multiple `init()` functions; they execute in file order, then alphabetically within each file. Multiple files are parsed in lexical order. `init()` cannot be called manually.

G13 — `new(T)` allocates zeroed memory for type `T` and returns a pointer `*T`. `make(T, args...)` initializes and returns the value itself (not a pointer) for slices, maps, and channels only, setting up internal structures like capacity and buckets.

G14 — Go uses explicit error values. The `error` interface has `Error() string`. Idiomatic pattern: `if err != nil { return err }`. `errors.Is(err, target)` checks semantic equality (unwrapping). `errors.As(err, &target)` performs type assertion to extract wrapped errors. `==` only checks pointer/value equality, ignoring wrapping.

G15 — Zero values: `map` → `nil`, `slice` → `nil`, `channel` → `nil`, `struct` → zero values of each field. `nil` slices/maps/channels are safe to use (append to nil slice works, range over nil map yields nothing, send to nil channel blocks forever).

G16 — A race occurs when concurrent goroutines access shared data without synchronization, at least one write, and no happens-before ordering. `-race` flag instruments memory accesses at compile time, detecting races at runtime. Example: `go func(){m["k"]="v"}(); m["k"]`. Fix: wrap with `sync.Mutex` or use a channel for exclusive access.

G17 — `select` multiplexes channel operations like `switch` multiplexes values. It evaluates all cases; if multiple are ready, one is chosen pseudo-randomly. If none are ready and no `default`, it blocks. Timeout: `case <-time.After(d):`.

G18 — Escape analysis determines if a variable's lifetime exceeds its stack frame, forcing heap allocation. The compiler tracks aliasing, pointer escapes, and closure captures. Inspect with `go build -gcflags="-m"`. Heap allocations increase GC pressure; stack allocations are faster and zero-cost. Minimizing escapes improves latency and throughput.

G19 — `reflect.Type` describes type metadata; `reflect.Value` holds the actual value and allows runtime inspection/manipulation. Reflection is slow (indirect calls, type checks, allocations) and bypasses compile-time safety. Justified for serialization, ORM, or framework scaffolding. Prefer code generation (`go generate`) for hot paths or performance-critical code.

G20 — `go:embed` embeds files/directories into the binary at compile time. Works with single files (`//go:embed file.txt`), directories (`//go:embed dir/`), and glob patterns. Limitations: static at compile, no symlinks, no runtime modification. Returns `fs.FS` (or `[]byte`/`string`), enabling seamless integration with `io/fs` APIs like `os.DirFS` or `http.FS`.

R1 — Ownership ensures memory safety without GC. Rules: 1) Each value has exactly one owner. 2) Only one owner exists at a time. 3) When the owner goes out of scope, the value is dropped. Transfers occur via move semantics; borrowing provides temporary access without ownership transfer.

R2 — `String` is an owned, heap-allocated, mutable string. `&str` is an immutable, borrowed string slice (view into existing memory). Use `String` when you need ownership or mutation; use `&str` in function signatures for zero-copy borrowing and maximum flexibility.

R3 — Borrowing enforces aliasing rules at compile time. Shared references (`&T`): unlimited count, immutable access. Mutable references (`&mut T`): exactly one, exclusive access, mutable. You cannot hold `&T` and `&mut T` simultaneously, preventing data races and iterator invalidation.

R4 — `Result<T, E>` represents success/failure; `Option<T>` represents `Some(T)` or `None`. The `?` operator propagates errors (`?` on `Err` returns early) or unwraps `Some`/panics on `None`. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```

R5 — `Box<T>`: single owner, heap-allocated, enables recursive types. `Rc<T>`: reference-counted, single-threaded sharing. `Arc<T>`: atomic reference-counted, thread-safe sharing. Use `Box` for owned heap data, `Rc` for shared ownership in single-threaded contexts, `Arc` for concurrent shared ownership.

R6 — Rust traits require explicit `impl` blocks; Go interfaces are satisfied implicitly. Trait objects (`dyn Trait`) use dynamic dispatch (vtable) and erase type info, enabling heterogeneous collections. Generic bounds (`T: Trait`) use static dispatch (monomorphization), generating type-specific code with zero runtime overhead.

R7 — Fails because the compiler cannot determine which input lifetime (`x` or `y`) matches the output lifetime. Fix by introducing a lifetime parameter:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

R8 — `Send` means ownership can be transferred across threads; `Sync` means shared references (`&T`) can be sent across threads. `Rc<T>` isn't `Send` because its non-atomic ref count isn't thread-safe. `Arc<T>` uses atomic ref counting, making it `Send` + `Sync` for concurrent reference counting.

R9 — `async fn` returns a `Future` state machine. `await` suspends execution until the future is ready, yielding control to the executor. The executor (e.g., Tokio) polls futures, manages I/O readiness, and drives the state machine. Differs from Go: Go's runtime handles M:N scheduling and blocking syscalls internally; Rust's `async` is just a trait, requiring an explicit executor and manual I/O driver integration.

R10 — `unsafe` disables compiler safety checks. Three things: 1) Dereference raw pointers. 2) Call `unsafe` functions. 3) Read/write `static mut`. Justified for FFI, low-level concurrency primitives, performance-critical code, or building safe abstractions that uphold invariants.

R11 — Pattern matching exhaustively handles enum variants. `match` requires all variants; `if let` handles only one case. The compiler enforces exhaustiveness in `match`, preventing unhandled cases at compile time. `_` catches remaining variants.

R12 — `[T; N]` is a fixed-size stack array. `Vec<T>` is a heap-allocated, dynamically sized collection. When pushing beyond capacity, `Vec` allocates a new buffer (typically 2x growth), copies elements, drops the old buffer, and updates internal pointers.

R13 — Rust enums are algebraic data types that can hold data per variant. Unlike C/Java enums, they're first-class types. `Option<T>` = `Some(T)` | `None`. Rust has no `null`; `Option` forces explicit handling via `match`/`if let`/`?`, eliminating null pointer exceptions.

R14 — `impl` blocks define methods. `&self` borrows immutably, `&mut self` borrows mutably, `self` consumes the value. Associated functions (e.g., `String::new()`) don't take `self` and act as constructors or utility functions.

R15 — `#[derive]` auto-generates trait implementations. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive when the trait requires custom logic, has incompatible bounds (e.g., `PartialEq` on types with `!` or custom equality), or when deriving would violate invariants.

R16 — `Cow<'a, T>` (Clone-on-Write) holds either a borrowed `&'a T` or an owned `T`. Useful when you want to avoid allocation if input matches expected type, but clone only on mutation. Example: formatting strings where you can return `&str` if already formatted, but `String` if interpolation occurs.

R17 — `mod` declares a module, `use` imports items into scope, `pub` exposes them. File system maps: `mod foo;` looks for `foo.rs` or `foo/mod.rs`. Rust 2015 required `mod.rs`/`lib.rs` tree. Rust 2018 allows `mod foo;` in `foo.rs` or `foo/mod.rs`, simplifying flat module layouts.

R18 — `Pin<T>` guarantees a value won't move in memory. Needed for self-referential structs and async/await (futures hold references to their own fields). `Unpin` is auto-implemented; types that must stay pinned implement `!Unpin`. `Pin` prevents `Drop`/`mem::replace` from moving the value.

R19 — Declarative macros (`macro_rules!`) match token trees and rewrite them. Procedural macros (derive, attribute, function-like) operate on parsed ASTs via Rust APIs. Hygiene ensures macro-expanded identifiers don't leak or collide with outer scope bindings, preventing accidental shadowing.

R20 — Zero-cost abstractions compile to machine code as efficient as hand-written C. Iterators use loop unrolling and inlining. Generics use monomorphization (type-specific code generation). Traits use static dispatch (inline calls) unless `dyn` forces dynamic dispatch. High-level ergonomics incur no runtime overhead when used idiomatically.
