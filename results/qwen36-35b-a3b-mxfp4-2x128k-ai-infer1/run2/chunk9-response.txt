SC1-A
The pods fail because Kubernetes Pod Security Standards (PSS) enforcement changed from `Baseline` to `Restricted`. Under `Restricted`, `runAsNonRoot: true` is mandatory, but it **must** be paired with an explicit `runAsUser` set to a non-zero UID. Without `runAsUser`, the kubelet cannot guarantee the container won't run as root, violating the standard. Additionally, the new base image (`cgr.dev/chainguard/static:latest`) sets `USER root` in the Dockerfile, which conflicts with `runAsNonRoot: true`. The cluster upgrade triggered the namespace-level `Restricted` policy, causing admission rejection or runtime crashes for pods that previously passed `Baseline` checks.

SC1-C
**Immediate Fix:** 
1. Image: Add `USER 1000` (or app-specific UID) to the Dockerfile.
2. Manifest: Add `runAsUser: 1000` to `securityContext` in deployments.
3. Rollout: Use `kubectl rollout restart` with `maxSurge=25%` and `maxUnavailable=25%`. Ensure `readinessProbe` is strict to prevent traffic to unhealthy pods during restart.

**Prevention:**
- CI Gate: Run `kubectl apply --dry-run=server` against the cluster's `Restricted` policy in CI. Fail if securityContext violates PSS.
- Admission Controller: Deploy Kyverno/OPA Gatekeeper in prod to enforce `runAsUser` + `runAsNonRoot` at admission time.
- Image Policy: Use OPA/Conftest to scan images for `USER root` and reject builds.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous. WAL files are shipped over the network and replayed on the replica. During an outage, promoting the replica cuts replication, leaving any WAL not yet shipped or replayed permanently lost. The data loss window equals the replication lag at promotion time. To quantify: query `pg_last_wal_receive_lsn` vs `pg_last_wal_replay_lsn` on the replica, or check `pg_stat_replication` for `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn`. The difference in LSNs translates to time/data loss.

SC2-C
**Architecture:**
- **Connection Management:** Use RDS Proxy instead of PgBouncer. RDS Proxy handles failover transparently, maintains connection pools per AZ, and reduces login retry storms.
- **DNS Failover:** Route53 failover routing policy with health checks against RDS Proxy endpoints.
- **App Retry:** Exponential backoff with jitter, idempotent write design, and circuit breakers.
- **RPO < 1s:** Standard RDS cross-region async replication cannot guarantee <1s RPO. Recommend **Aurora Global Database**. It uses dedicated global storage with <1s cross-region lag, automatic failover, and consistent RPO/RTO.
- **Why Aurora Global DB:** Managed, eliminates manual promotion, provides synchronous-like cross-region consistency, and integrates natively with Route53/RDS Proxy.

**PostgreSQL Lock Diagnostic:**
```sql
SELECT 
  blocked_locks.pid AS blocked_pid,
  blocked_activity.usename AS blocked_user,
  blocking_locks.pid AS blocking_pid,
  blocking_activity.usename AS blocking_user,
  blocked_activity.query AS blocked_statement,
  blocking_activity.query AS current_statement_in_blocking_process
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks 
  ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC5-C
**Architectural Solution:**
- **CQRS:** Separate read/write paths. Checkout reads from a read replica or materialized view.
- **Read Replica:** Run reconciliation CronJob against a read replica to avoid locking production tables.
- **Bulkhead Isolation:** Separate DB connection pools for serving vs background jobs. Use `pgbouncer` with pool modes `transaction` for serving, `statement` for jobs.
- **CronJob Scheduling:** Run during off-peak, set `concurrencyPolicy: Forbid`, `restartPolicy: OnFailure`.
- **PDBs & Quotas:** Set `minAvailable: 80%` for serving pods. Use ResourceQuotas to cap CronJob CPU/memory. Use `priorityClassName` to ensure serving pods preemption over CronJob.

SC6-C
**Comparison:**
- **AWS Direct Connect:** Dedicated 10G/100G link. Low latency, high throughput, predictable cost (~$5k/mo + data). Requires BGP routing, TGW attachment. Fits ZT but needs additional auth layers.
- **Second VPN + ECMP:** Scales bandwidth via IPsec tunnels. Lower cost, higher latency/overhead. Routing: multiple TGW attachments with equal-cost routing. Fits ZT with mTLS overlay.
- **Tailscale/Netbird:** WireGuard mesh, zero-trust native, automatic routing. Low cost, easy setup. Bandwidth limited by WireGuard overhead and cloud egress. Routing: overlay network. Best ZT fit, but may not meet enterprise SLA for 10G dark fiber replacement.
**Recommendation:** Direct Connect for backbone reliability, overlay with SPIRE/mTLS for ZT. Use ECMP VPN as fallback.

SC7-A
**Drift Sources & Risks:**
1. **Manual `tofu apply`:** Bypasses CI, no locking. Concurrent runs cause race conditions, state corruption, partial updates, or destroy/recreate cycles. Data loss if resources are overwritten.
2. **Diverged Helm values:** Untracked config changes break GitOps declarative model. Hard to audit, causes environment inconsistency, silent failures.

SC10-C
**Failover Orchestration Sequence:**
1. **Detection:** Health checks (heartbeat, DB ping, node reachability). "Site down" = >3 consecutive failures across multiple monitors.
2. **DNS Failover:** GSLB (Route53/Azure DNS) switches traffic to Dallas. TTL <60s.
3. **Patroni Promotion:** etcd triggers Dallas node promotion. Synchronous commit ensures zero data loss.
4. **Redis Sentinel:** Sentinel detects master down, promotes replica.
5. **RabbitMQ:** Federation/shovel catches up, queues mirrored.
6. **MinIO:** Site replication catches up, read/write switches to Dallas bucket.
7. **Terraform State:** CI pipeline updates state to reflect new primary, disables Chicago resources.
**Split-Brain:** Fencing via STONITH (power cycle), etcd quorum, manual override via runbook.
**Failback:** Reverse replication, sync data, DNS switch back to Chicago, update Terraform state, verify consistency.
