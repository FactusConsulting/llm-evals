CL1 — **IaaS** provides raw compute, network, and storage; you manage OS, middleware, runtime, and data. Example: AWS EC2. **PaaS** provides a managed runtime/environment; you manage app code and data. Example: Google App Engine. **SaaS** provides a fully managed application; you only manage user access and configuration. Example: AWS WorkSpaces.

CL2 — The **Shared Responsibility Model** divides security: provider secures the cloud infrastructure; customer secures what they put in it. **IaaS VM**: Provider = physical, hypervisor, host OS. Customer = guest OS, patching, network config, data, IAM. **Managed K8s**: Provider = control plane, node OS patching, networking infra. Customer = worker config, app, secrets, RBAC, network policies. **SaaS (M365)**: Provider = app, infra, patching, compliance framework. Customer = user accounts, data, access policies, MFA, data classification.

CL3 — **VPC**: Virtual network isolation. **Subnet**: IP range within a VPC, tied to an AZ. **Security Group (SG)**: Stateful, instance/pod-level, allow-only rules, evaluated at ENI. **NACL**: Stateless, subnet-level, allow/deny rules, evaluated at subnet boundary. **Layering**: Traffic hits NACL first, then SG. **Stateful** (SG) remembers return traffic automatically; **Stateless** (NACL) requires explicit allow rules for both directions.

CL4 — **Landing zone**: Pre-configured baseline environment (network, IAM, logging, security). **OUs**: Logical grouping (dev, prod, shared services). **Guardrails**: SCPs, IAM boundaries, mandatory controls (encryption, logging). **Shared networking**: Transit Gateway/Azure Hub-and-Spoke for centralized peering, on-prem connectivity, and service mesh. **Centralized logging**: CloudTrail/Config or Azure Monitor routed to a security account. **Single-account problems**: Massive blast radius, permission sprawl, billing opacity, compliance violations, accidental deletion, and lack of environment isolation.

CL5 — **Terraform/OpenTofu**: Declarative HCL, multi-cloud, state-managed, vast ecosystem. Best for multi-cloud, mature infra teams. **Pulumi**: Imperative/Declarative, general-purpose languages (TS, Python, Go). Best for complex logic or teams already using dev languages. **CloudFormation/Bicep**: AWS-native, declarative, tightly integrated. Best for AWS-only shops seeking rapid adoption. **Crossplane**: K8s-native IaC, manages cloud resources via CRDs. Best for GitOps/K8s-centric teams wanting a unified control plane.

CL6 — **HPA**: Scales pods based on CPU/memory/custom metrics. Reactive. **VPA**: Adjusts resource requests/limits per pod; requires restart. **Cluster Autoscaler**: Adds/removes nodes based on pending pods. **KEDA**: Event-driven scaling; scales to zero. **KEDA vs HPA**: Use KEDA for event-driven workloads (queues, streams, webhooks) where HPA's metric polling is inefficient or scale-to-zero is required.

CL7 — **RPO/RTO**: Define by business impact. **Active-active**: RPO≈0, RTO≈0, high cost/complexity. **Active-passive**: RPO>0, RTO>0, lower cost. **DB replication**: Sync (strong consistency, latency, single-writer) vs Async (eventual consistency, lower latency, potential data loss). **DNS failover**: Route53/Traffic Manager health checks, weighted routing, low TTL. **State management**: Externalize state (Redis/DB), avoid local disk. **Cost**: Active-active doubles infra; pilot light cheapest but higher RTO. **DR models**: Pilot light (minimal core running, scale up quickly), Warm standby (scaled-down prod ready), Multi-site active-active (full traffic split, seamless failover).

CL8 — **GitOps**: Git is the single source of truth; controllers sync cluster state to Git state. **ArgoCD**: Push model, UI-heavy, app-of-apps, beginner-friendly. **Flux**: Pull model, Git-native, CLI-focused, tight GitHub/GitLab integration. **Secrets**: SealedSecrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from AWS Secrets Manager/Vault), Vault (dynamic secrets, auth). **Drift**: Manual changes are overwritten on next sync. GitOps enforces reconciliation and provides audit trails via Git history.

CL9 — **StatefulSet**: Stable network ID, ordered deployment/termination, stable storage. **PV/PVC local storage**: Use `local` storage class with `volumeBindingMode: WaitForFirstConsumer` for node affinity. **Headless service**: `clusterIP: None` enables direct pod DNS resolution. **Init containers**: Pre-load config, check dependencies, mount volumes. **ConfigMaps**: Volume mounts for config files at specific paths. **PDB**: `minAvailable: 1` or `maxUnavailable: 0` to prevent simultaneous pod loss. Note: Local storage lacks native replication; implement external backups.

CL10 — **Service Account**: K8s-native identity, no cloud IAM binding by default. **IRSA (AWS)**: Maps K8s SA to AWS IAM role via OIDC; pods assume role via STS. **Workload Identity (GCP/Azure)**: Maps K8s SA to cloud IAM identity via OIDC/federation. **Mounting creds**: Bad practice (leaks, rotation issues, violates least privilege, pod compromise = full cloud access). **Federation**: Uses OIDC token exchange, short-lived credentials, scoped IAM roles, automatic rotation, and eliminates static keys in pods.

CL11 — **Object (S3/Blob)**: HTTP API, metadata, scalable. Durability: 11 9s. Availability: 99.99%. Use: Archives, media, backups, static web. **Block (EBS/Disk)**: Low latency, attached to single VM, snapshots. Durability: 99.8–99.99%. Availability: High but zonal. Use: OS, databases, high-IOPS apps. **File (EFS/Azure Files)**: NFS/SMB, shared across VMs, POSIX compliant. Durability: 11 9s. Availability: Regional. Use: Shared configs, home dirs, legacy apps needing file shares.

CL12 — **Network policies**: Default deny, explicit allow. **Service mesh (mTLS)**: Istio/Linkerd for encrypted service-to-service, identity-based routing. **Pod identity**: Workload identity/IRSA for cloud access. **Admission controllers**: OPA/Kyverno enforce policies (image tags, resource limits, security contexts) at admission. **Image signing**: Cosign/Notary, verify signatures in admission. **Runtime security**: Falco monitors syscalls, detects anomalies. **Secrets**: External Secrets Operator/Vault, never in env vars. **vs Perimeter**: Zero-trust assumes breach, verifies every request, micro-segments, identity-centric. Perimeter relies on network boundaries and trusts internal traffic.

CL13 — **CDN**: Distributed edge cache network. **How it works**: Caches static/dynamic content at PoPs, routes users to nearest PoP, reduces origin load/latency. **Services**: CloudFront, Azure CDN, Fastly. **CDN vs Origin**: Use CDN for static assets, media, global distribution, DDoS mitigation. Use origin for dynamic, personalized, real-time data.

CL14 — **Region**: Geographic area with multiple AZs. **AZ**: Isolated data centers with independent power/network/cooling, low-latency links. **Multi-AZ**: Fault tolerance, high availability, avoids single point of failure. **Zonal vs Regional**: Zonal resources (EBS, single-AZ LB) tied to one AZ. Regional resources (S3, global LB, Route53) span multiple AZs/regions.

CL15 — **Managed DB**: RDS/Cloud SQL/Azure SQL. **Provider handles**: Provisioning, patching, backups, replication, failover, monitoring, storage scaling, maintenance windows. **Customer handles**: Schema, queries, IAM access, data, security groups, parameter tuning. Trade-off: Less control, higher cost, but massive ops reduction.

CL16 — **Users**: Human/service accounts with long-term creds (avoid). **Groups**: Collections for policy assignment. **Roles**: Temporary credentials, assumed by users/services/external identities. **Policies**: JSON documents defining permissions (allow/deny, conditions). **Least privilege**: Grant only necessary permissions. Apply via roles, scoped policies, conditions (IP, MFA, time), regular access reviews, avoid wildcard `*`.

CL17 — **Serverless**: Event-driven, managed compute, pay-per-use, auto-scaling to zero. **Compare**: Lambda (AWS), Functions (Azure), Cloud Functions (GCP). Similar models, different ecosystems. **Cold starts**: First invocation after idle period requires env init. Matters for latency-sensitive apps. Mitigated by provisioned concurrency, smaller runtimes, container images. **Poor fit**: Long-running processes, high memory/CPU, strict latency SLAs, complex networking, predictable high throughput (EC2/K8s cheaper).

CL18 — **Ingress resource**: Standard K8s API, relies on controller (NGINX, ALB), TLS termination at controller. **Gateway API**: Newer, structured, multi-protocol, better RBAC, separates network from app routing. TLS at gateway. **Cloud LB annotations**: Direct cloud LB (ALB/ILB) via Ingress controller or `LoadBalancer` service. TLS at cloud LB. **Service mesh ingress**: Istio/Linkerd gateway, mTLS, advanced traffic mgmt. TLS at mesh gateway. **Gateway API over Ingress**: Better RBAC, multi-tenant, protocol flexibility, standardized config, future-proof.

CL19 — **RI/SP**: Commit 1–3yr for predictable workloads. SP more flexible. **Spot/Preemptible**: 60–90% discount for fault-tolerant, interruptible workloads. **Right-sizing**: Monitor utilization, downsize overprovisioned, use auto-scaling. **Storage tiering**: S3 Intelligent-Tiering, Glacier for archives, lifecycle policies. **Idle detection**: CloudHealth, AWS Cost Explorer, Azure Advisor, tag-based tracking, auto-shutdown dev envs. **FinOps**: Cross-functional team, cost accountability culture, showback/chargeback via tags/cost allocation, quarterly reviews. **Tools/Processes**: Kubecost, OpenCost, native cost tools, tagging standards, budget alerts, optimization sprints.

CL20 — **Abstraction**: Kubernetes, Terraform, service mesh, API gateways. **K8s runtime**: EKS/AKS/GKE, GitOps, Helm/Kustomize. **Terraform**: Multi-provider, state management, modules for portability. **Networking**: Cloud VPN, Direct Connect/ExpressRoute, global LB, DNS routing. **Identity**: OIDC federation, centralized IAM proxy, SSO. **Trade-offs**: Complexity, cost, skill fragmentation, data egress fees, inconsistent features. **Justified**: Regulatory/data sovereignty, vendor leverage, risk diversification, specific service needs. **Unnecessary**: Most mid-size companies; adds overhead without proportional benefit. Single-cloud optimized is usually better.

OT1 — **Purdue Model (ISA-95)**: Industrial hierarchy. **Level 0**: Physical process (sensors, actuators). **Level 1**: Direct control (PLCs, RTUs, DCS). **Level 2**: Supervisory control (SCADA, HMIs, historians). **Level 3**: Plant operations (MES, production scheduling, quality control). **Level 4**: Enterprise (ERP, business planning, supply chain). **Level 5**: Corporate/IT (network management, security, external comms).

OT2 — **IT vs OT**: IT prioritizes confidentiality/integrity, frequent patching, user-centric, dynamic. OT prioritizes availability/safety, real-time deterministic, machine-centric, stable/legacy. **Patching**: OT systems often run decades-old OS, lack patch windows, updates can break process/safety, require vendor validation, and must be tested in staging first.

OT3 — **DMZ (IDMZ)**: Secure buffer between IT (L4) and OT (L1-L3). **Traffic**: Strictly controlled bidirectional or one-way. IT→OT: requests, commands, updates. OT→IT: process data, alarms, status. **Direction**: Data diodes or strict firewall rules; reverse proxies for OT→IT. **Direct L4→L1 danger**: Lateral movement, ransomware, unvalidated commands, network congestion, compliance violations, safety risks.

OT4 — **Modbus TCP**: L1/L2, PLC communication, master/slave, unencrypted. **OPC UA**: L2/L3, secure, structured, cross-platform, info modeling. **EtherNet/IP (CIP)**: L1/L2, industrial Ethernet, Allen-Bradley dominant, unencrypted. **PROFINET**: L1/L2, real-time Ethernet, Siemens dominant, IO/IRT cycles. **MQTT**: L3/L4, lightweight pub/sub, cloud/edge analytics, TLS optional.

OT5 — **Data diode**: Hardware-enforced unidirectional flow. Physically prevents return traffic. **Firewall**: Software/hardware, bidirectional, stateful inspection, allows/denies based on rules. **Use diode**: Critical OT→IT data exfiltration (historian, alarms) where zero return traffic is mandatory. **Limitation**: No bidirectional communication, no inspection of return traffic (by design), less flexible for complex protocols.

OT6 — **Data flow**: PLCs → OPC UA Server (L2) → Historian (L3) → Edge Gateway (protocol translation, buffering) → MQTT Broker (secure, TLS) → Cloud Ingestion (Kafka/Event Hub) → Analytics. **Security boundaries**: L2/L3 firewall, IDMZ, edge gateway with HSM, TLS/mTLS for MQTT, cloud IAM, network segmentation, data validation at edge. Edge handles offline buffering, protocol conversion, and initial security filtering.

OT7 — **IEC 62443**: **Zone**: Logical/physical grouping with common security requirements. **Conduit**: Communication path between zones with defined controls. **Model**: Zone 1: SIS (highest integrity, air-gapped/isolated). Zone 2: PLCs/RTUs (control). Zone 3: SCADA/Historian/HMI (supervisory). Zone 4: Engineering workstations (maintenance). Zone 5: Corporate/IT (business). Conduits: Strict firewall/Diode between 3-4, 3-5. 2-3 controlled. 1 isolated. RBAC, mTLS, audit logging on all conduits.

OT8 — **Segmentation**: VLAN design by function/process (e.g., VLAN 10: Line 1 PLCs, 20: Line 2, 30: HMIs, 40: SCADA, 50: Engineering). **Firewall placement**: Core firewall between IT/OT, edge firewalls per VLAN/subnet, DMZ for external access. **Switch architecture**: Managed industrial switches, 802.1Q, port security, STP/RSTP, redundant links. **Remote access**: Jump host in IDMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. **Transition**: Phased rollout, parallel run, maintenance windows, rollback plans, vendor coordination, minimal disruption testing.

OT9 — **SIS vs BPCS**: SIS is independent safety system that brings process to safe state on failure/danger. BPCS handles normal control. **IEC 61511**: Safety lifecycle standard for process industry SIS; defines SIL ratings. **Isolation**: Prevents cyber/IT faults from compromising safety functions. SIS must be deterministic and fail-safe. **Ransomware on SIS**: Could disable safety interlocks, cause catastrophic failure, environmental release, loss of life. Hence strict isolation/air-gap.

OT10 — **PLC**: Discrete control, fast, rugged, used for specific machines/lines. **DCS**: Integrated control for continuous processes, distributed I/O, centralized HMI, higher redundancy. **SCADA**: Supervisory system, collects data from multiple PLCs/RTUs, long-distance monitoring, HMI/historian. **Coexist**: Yes. PLCs/DCS handle control, SCADA supervises. Common in large plants.

OT11 — **Remote access**: Jump hosts isolated in IDMZ, no direct OT access. MFA mandatory. Session recording for audit. Vendor access time-limited, scoped, approved, monitored. **Why RDP to HMI unacceptable**: Exposes OT directly to corporate threats, bypasses segmentation, lacks audit, violates least privilege, increases attack surface.

OT12 — **Detection**: IDS/IPS at IDMZ, network anomaly detection, asset inventory baseline, EDR on L3, SIEM correlation. **Inventory**: Real-time OT asset map, passive network discovery, configuration baselines. **IR steps**: Contain (isolate segment, block vendor IP), investigate (forensics, logs), eradicate (patch, revoke creds), recover (clean backups). **Coordination**: Notify control room, switch to manual/local control if needed, maintain safety, document timeline. **Operator role**: Monitor physical process, execute manual overrides, report anomalies, follow cyber incident playbook, prioritize safety over production. **Safe ops**: Maintain SIS/BPCS integrity, use fallback modes, avoid remote changes during incident.

OT13 — **HMI**: Operator interface for monitoring/control of industrial processes. **Role**: Visualizes data, allows manual overrides, alarms, trend analysis. **vs EWS**: HMI is for operators (run-time). EWS is for engineers (programming, configuration, diagnostics, offline).

OT14 — **Historian**: Time-series database for process data (temperatures, pressures, flows). **Importance**: Trend analysis, compliance, optimization, troubleshooting, regulatory reporting. **Plant (L3) vs Enterprise (L4)**: Plant stores high-frequency, raw process data for operations. Enterprise stores aggregated, business-relevant data for ERP, analytics, supply chain.

OT15 — **Ladder logic**: Graphical programming language mimicking relay circuits. **Device**: PLC executes it. **Dominance**: Familiar to electricians, deterministic scan cycle, easy to troubleshoot, legacy codebase, safety-certified environments, low learning curve for industrial workforce.

OT16 — **RTU**: Remote, rugged, designed for long-distance telemetry, SCADA integration, often serial/legacy comms, simpler logic. **PLC**: Localized, complex logic, fast I/O, modern Ethernet comms, modular. **RTU use**: Pipelines, utilities, remote sites, harsh environments, wide geographic distribution.

OT17 — **Analog vs Digital**: Analog (4-20mA, 0-10V) represents continuous variable process values. Digital (on/off, pulses) represents state or count. **4-20mA vs 0-20mA**: 4mA "live zero" indicates wire break/failure (0mA = fault), improves diagnostics, reduces noise impact, industry standard.

OT18 — **Asset inventory**: Complete, accurate map of all OT assets (hardware, firmware, network config, dependencies). **Foundation**: Enables risk assessment, patching, segmentation, incident response, compliance. **Tools**: Passive monitoring (packet capture, protocol analysis), active scanning (limited, vendor-approved), CMDB integration. **Active scanning danger**: Can crash legacy devices, trigger alarms, cause process disruption, unknown compatibility. Passive is safer.

OT19 — **MITRE ATT&CK ICS**: Maps adversary tactics/techniques specific to ICS/OT. **Tactics & examples**: 1. Reconnaissance: Gather network architecture (T1580). 2. Resource Development: Acquire infrastructure (T1583). 3. Initial Access: Phishing/Supply chain (T1195). 4. Execution: Command/scripting on PLC/HMI (T1059). 5. Persistence: Modify PLC program/config (T1053). 6. Defense Evasion: Disable logging/IDS (T1070). 7. Impact: Sabotage/process disruption (T1499). **vs Enterprise ATT&CK**: ICS focuses on safety, real-time control, legacy protocols, physical impact. Enterprise focuses on data, users, cloud. **Assessment**: Map current defenses to techniques, identify gaps, prioritize controls (segmentation, EDR, change management, monitoring).

OT20 — **Converged SOC**: **Log collection**: Passive network taps, OPC UA/Modbus gateways, SIEM agents on L3/L4, avoid L1/L2 impact. **SIEM integration**: Normalize OT logs (Syslog, JSON), correlate with IT logs, OT-specific parsers. **Detection rules**: Anomaly-based (baseline deviations), protocol-specific (unexpected Modbus writes), behavioral (unusual HMI access), threat intel. **Triage**: OT engineers + IT analysts, prioritize safety/availability, validate with process engineers, reduce false positives via OT context. **Staffing**: IT analysts (threat hunting, malware), OT engineers (protocol expertise, process safety), SOC manager (coordination). **False positives**: OT environments have predictable cycles; tune rules to production schedules, use whitelists, validate with control room. **Unauthorized firmware on PLC**: Immediate isolation, verify with engineering, rollback to signed baseline, investigate source, update change management, report to safety team.
