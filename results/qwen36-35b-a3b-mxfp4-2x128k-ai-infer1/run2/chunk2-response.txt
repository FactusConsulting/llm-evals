K1 — A **Deployment** manages stateless workloads with interchangeable, randomly named pods and supports rolling updates. A **StatefulSet** manages stateful workloads requiring stable network IDs, ordered deployment/scaling, and stable persistent storage.

K2 — A `ClusterIP` Service assigns a virtual IP and creates `Endpoints` pointing to healthy pod IPs. `kube-proxy` watches these resources and programs node-level `iptables` or `IPVS` rules to route traffic arriving at the Service IP to the backend pod IPs.

K3 — A **PersistentVolume (PV)** is a cluster-wide storage resource. A **PersistentVolumeClaim (PVC)** is a user's request for storage. A **StorageClass** defines a provisioning template. PVCs bind to static PVs or trigger dynamic PV creation via a StorageClass.

K4 — 1. `kubectl logs <pod> --previous` to check crash output. 2. `kubectl describe pod` to inspect Exit Codes and Events (e.g., OOMKilled). 3. Verify resource requests/limits and node capacity. 4. Check liveness/readiness probes and mounted configs/env vars for misconfiguration.

K5 — CoreDNS provides internal DNS resolution for services and pods. If CoreDNS pods are down, internal DNS resolution fails, preventing pods from resolving service names or cluster-internal endpoints (external DNS may still work if fallback resolvers are configured, but cluster networking breaks).

K6 — The scheduler **filters** nodes that fail requirements (resources, taints, affinity, node selectors), then **scores** remaining nodes. Factors include: `LeastRequestedPriority` (balances CPU/memory), `NodeAffinity`/`PodAffinity` (placement rules), and `TaintToleration` (tolerates node taints).

K7 — Yes, it will schedule. Available node memory = 4GB - 3.5GB = 0.5GB. Pod request = 256Mi (~0.25GB), which fits. At runtime, using 600Mi exceeds the 512Mi limit, triggering an `OOMKilled` event. The pod restarts and is re-scheduled.

K8 — Client → External LB (routes to Ingress Controller IP) → Ingress Controller (NGINX) parses Ingress resource → matches host/path → routes to Kubernetes Service → Service resolves to Endpoints (pod IPs) → `kube-proxy`/`iptables`/`IPVS` forwards to pod → pod handles request.

K9 — A `NetworkPolicy` restricts ingress/egress traffic to/from pods. Default behavior (no policy): all traffic allowed. When applied: only traffic matching the policy's pod selectors and rules is permitted; all other traffic is explicitly denied.

K10 — `RollingUpdate` gradually replaces old pods with new ones (zero downtime). `Recreate` terminates all old pods before starting new ones (downtime). Choose `Recreate` for stateful apps, shared storage, or when configuration changes require a full restart.

K11 — A namespace provides logical isolation within a cluster. Default namespaces: `default`, `kube-system`, `kube-public`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it displays: 1. Events (scheduling, pull, restart reasons). 2. Resource requests/limits. 3. Volume mounts and config references. 4. Pod/Node IPs and conditions.

K13 — A ConfigMap stores non-sensitive configuration data. Pods consume it via: 1. Environment variables (key-value mapping). 2. Volume mounts (files injected into the container filesystem).

K14 — `ClusterIP`: internal cluster-only access. `NodePort`: exposes the service on a static port on each node's IP. `LoadBalancer`: provisions a cloud provider's external load balancer and exposes the service externally.

K15 — A DaemonSet ensures one pod runs on every node (or subset via taints/tolerations). Use it for node-level agents (logging, monitoring, metrics) rather than application workloads managed by Deployments.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Use case: Taints for dedicated GPU nodes (repel general workloads); Affinity for zone-aware scheduling (attract pods to specific AZs).

K17 — An Operator is a custom controller that manages complex, stateful applications using Custom Resource Definitions (CRDs). It differs from a standard controller by encoding operational knowledge (scaling, backups, upgrades) into code, solving manual ops overhead for services like databases.

K18 — etcd uses a **strongly consistent** (linearizable) Raft consensus model. If quorum is lost, the cluster becomes completely unavailable (reads and writes fail). Recovery: restore from the latest backup, add a new etcd node, join it to the cluster, and restore data.

K19 — RBAC uses Roles/ClusterRoles (define permissions) and RoleBindings/ClusterRoleBindings (bind roles to users/groups/SAs). Manifest:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` causes the resolver to try multiple suffixes (`svc.cluster.local`, `cluster.local`, etc.) before querying external DNS, causing excessive queries and latency. Fix: add `dnsConfig: options: [{name: "ndots", value: "1"}]` to the pod spec to reduce suffix attempts.

D1 — `git merge` preserves history with a merge commit. `git rebase` rewrites commit history onto a new base, creating a linear timeline. Avoid rebasing on shared/public branches or after pushing to remote to prevent history conflicts.

D2 — **TCP** is connection-oriented, reliable, and ordered. **UDP** is connectionless, unreliable, and low-latency. TCP: HTTP, SMTP. UDP: DNS, VoIP/Streaming.

D3 — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to unpredictable results. Example: two threads incrementing a shared counter without a mutex, causing lost updates.

D4 — **Symmetric** encryption uses one key for encrypt/decrypt (fast). **Asymmetric** uses a public/private key pair (secure key exchange). In TLS: asymmetric cryptography establishes the session and exchanges keys; symmetric cryptography encrypts the actual data transfer.

D5 — Each Dockerfile instruction creates an immutable image layer. Layer caching reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., copy `package.json` and install deps before copying source code).

D6 — 1. Check upstream service health/status codes. 2. Verify resource exhaustion (CPU/memory throttling). 3. Check dependency connectivity (DB, cache, external APIs). 4. Review rate limiting/throttling configs. Order: immediate service status → resources → dependencies → config.

D7 — CAP theorem states a distributed system can only guarantee two of three: Consistency, Availability, Partition tolerance. CP: banking ledger (strong consistency, may block during network partition). AP: DNS or Cassandra (high availability, eventual consistency).

D8 — **Horizontal scaling** adds more nodes/instances. **Vertical scaling** increases resources (CPU/RAM) of an existing node. Horizontal scaling is enabled by: stateless services, distributed databases, message queues, and container orchestration.

D9 — An environment variable is a dynamic key-value pair passed to processes. To persist across sessions on Linux, add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON** is a strict, machine-friendly key-value format. **YAML** is indentation-based and human-readable. JSON advantage: strict parsing, universal language support. YAML advantage: readability, comments, less boilerplate.

D11 — A REST API is an architectural style using HTTP methods to interact with resources. `GET`: retrieve. `POST`: create. `PUT`: update/replace. `DELETE`: remove.

D12 — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes from upstream updates, and simplifies debugging and auditing.

D13 — **Compiled** languages translate source to machine code before execution (C, Rust). **Interpreted** languages execute source line-by-line at runtime (Python, JavaScript). (Note: modern languages often use JIT compilation, but the distinction remains in execution model.)

D14 — A **reverse proxy** sits in front of servers, routing client requests to backends (Nginx, HAProxy). Use case: load balancing, SSL termination. A **forward proxy** sits in front of clients, routing outbound requests. Use case: corporate content filtering, outbound caching.

D15 — A deadlock occurs when two or more processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait. All must hold simultaneously.

D16 — Eventual consistency guarantees that if no new updates occur, all replicas will eventually converge. Cassandra uses tunable consistency levels (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`). For read-after-write, use `QUORUM` for both reads/writes or `SERIAL` consistency for strict ordering.

D17 — mTLS requires both client and server to present and verify certificates. Handshake: ClientHello → ServerHello + cert → Client verifies server cert → Server verifies client cert → session keys derived. Used in: service meshes (Istio), internal microservices, zero-trust architectures.

D18 — A hash table maps keys to values via a hash function. Collision resolution: **chaining** (linked lists per bucket) or **open addressing** (probing for next empty slot). Average time complexity: O(1) for insert/lookup/delete. Worst case: O(n) if all keys collide.

D19 — A circuit breaker prevents cascade failures by stopping calls to a failing service. States: **Closed** (normal), **Open** (failure threshold reached, fail fast), **Half-open** (tests a call; success closes, failure reopens). It complements retries: without a circuit breaker, retries overload the failing service. Exponential backoff reduces retry frequency.

D20 — **Optimistic** concurrency assumes no conflict, checking at commit (e.g., row versioning, `UPDATE ... WHERE version = old`). **Pessimistic** locks resources during the transaction (e.g., `SELECT ... FOR UPDATE`). Choose optimistic for high read/low write contention; pessimistic for high write contention or critical consistency needs.
