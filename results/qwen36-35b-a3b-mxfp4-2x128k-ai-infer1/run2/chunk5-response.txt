DN1 — **class vs struct**: `class` is a reference type (heap-allocated, supports inheritance, nullable, GC-managed). `struct` is a value type (stack/inline-allocated, no inheritance, copied on assignment, non-nullable by default). Use `struct` for small, immutable, logically single-value data (e.g., `Point`, `Color`, coordinates) to avoid heap allocations and improve cache locality.

DN2 — **IEnumerable<T> vs IQueryable<T>**: `IEnumerable<T>` executes in-memory (LINQ to Objects). `IQueryable<T>` builds expression trees that providers translate to remote queries (LINQ to Entities/SQL). Distinction matters for DBs: `IQueryable` pushes filtering/joining to the database, reducing memory/network overhead. `IEnumerable` pulls all rows first, then filters in memory.

DN3 — **async/await, Task vs ValueTask**: `async/await` compiles to a state machine that yields control when awaiting I/O or CPU-bound work, resuming on a captured context. `Task` is a heap-allocated reference type for async operations. `ValueTask` is a struct representing async operations that may complete synchronously or be cached. Use `ValueTask` when an async method frequently completes synchronously or returns cached results to eliminate allocation overhead.

DN4 — **DI & lifetimes**: DI inverts control by injecting dependencies rather than creating them internally. Lifetimes: `Transient` (new instance each request), `Scoped` (new per request/context), `Singleton` (one instance for app lifetime). Common bug: Injecting a `Scoped` service into a `Singleton` creates a "captive dependency" – the scoped service lives as long as the singleton, leaking state, breaking request isolation, and causing thread-safety issues.

DN5 — **string vs ReadOnlySpan<char>, Span<T>**: `string` is heap-allocated, immutable, and involves allocations/copies. `ReadOnlySpan<char>` is a stack-allocated, zero-copy slice over contiguous memory. `Span<T>` is the mutable counterpart. Use `Span<T>`/`ReadOnlySpan<char>` for high-performance string/buffer processing (parsing, formatting, slicing) to avoid allocations and improve cache efficiency.

DN6 — **GC, Generations, LOH, IDisposable**: GC traces live objects and reclaims unreachable ones. Generations: `Gen 0` (short-lived, frequent collections), `Gen 1` (buffer), `Gen 2` (long-lived, infrequent). Objects promote on surviving collections. `LOH` (Large Object Heap) holds objects >85KB, is not compacted (causes fragmentation), and collects only during Gen 2. `IDisposable` provides deterministic cleanup for unmanaged resources (file handles, DB connections, native memory). GC only manages managed memory; it cannot release OS handles or external resources.

DN7 — **ConfigureAwait(false) vs default**: Default `await` captures the current `SynchronizationContext` (or `TaskScheduler`) and resumes on it. `ConfigureAwait(false)` skips context capture, resuming on any thread pool thread. Use `false` in libraries/executable paths where context doesn't matter (improves throughput, avoids deadlocks). Do NOT use in UI apps (WPF/WinForms) or legacy ASP.NET where UI updates or request context are required. It relates to `SynchronizationContext` by bypassing the context-switching mechanism that causes overhead and sync-over-async deadlocks.

DN8 — **.NET 8/9 features**: 
- Primary constructors: `public record User(string Name, int Age);` reduces boilerplate.
- Collection expressions: `[1, 2, 3]`, `[.. array]`, `[.. list]` for concise creation.
- `FrozenDictionary`: Immutable, highly optimized read-only lookup using perfect hashing, lower memory footprint.
- DI example: `public class MyService(string config, ILogger<MyService> logger) : IMyService { ... }` (constructor parameters auto-registered if types match DI services).

DN9 — **ObjectDisposedException on DbContext**: Cause: DbContext is likely registered as `Singleton` or shared across threads. DbContext is **not thread-safe** and must be `Scoped`. Fix: Register as `AddDbContext<DbContext>(options => ..., ServiceLifetime.Scoped)`. Ensure DI resolves a fresh instance per request. EF Core DbContext tracks entities, caches queries, and holds connections; sharing it breaks change tracking, causes concurrency conflicts, and leads to disposed/connection errors under load.

DN10 — **record vs class, record struct**: `record` is a reference type with value-based equality, immutability by default, and compiler-generated `Equals`/`GetHashCode`/`ToString`. `class` is mutable with reference equality. `record struct` is the value-type equivalent (zero-allocation, immutable, value equality). Choose `record` for domain models/DTOs needing value semantics, `record struct` for performance-critical small immutable data, and `class` for mutable/stateful objects.

DN11 — **ref, out, in**: `ref` passes by reference, must be initialized before call, read/write allowed. `out` passes by reference, must be assigned inside method, initialization before call not required. `in` passes by reference, read-only, prevents modification. Use `ref` for modifying existing values, `out` for multiple return values/`Try` patterns, `in` for large structs to avoid copies while guaranteeing immutability.

DN12 — **Nullable reference types vs value types**: NRT (`string?`) is a compile-time warning system tracking nullability for reference types. Runtime behavior unchanged. `#nullable enable` activates it. Nullable value types (`int?`) are actual CLR `Nullable<T>` types that can hold null at runtime, with `.HasValue`/`.Value`. NRT is compile-time safety; value type nullable is runtime-capable.

DN13 — **LINQ, method vs query syntax, deferred execution**: LINQ unifies querying across collections, DBs, XML. Method syntax (`list.Where(...)`) is fluent, chainable, preferred for complex ops. Query syntax (`from x in list where ...`) is SQL-like, compiles to method syntax. Deferred execution means the query isn't executed until enumerated (`foreach`, `ToList()`), enabling composition and lazy evaluation.

DN14 — **Generic constraints**: `where T : class` (reference type), `where T : struct` (non-nullable value type), `where T : new()` (parameterless constructor), `where T : IComparable<T>` (implements comparison). Combine for compile-time safety: e.g., `where T : class, IComparable<T>, new()` ensures T is reference, comparable, and instantiable, preventing invalid operations at runtime.

DN15 — **abstract class vs interface, default methods**: Abstract classes can hold state, constructors, and implementation; support single inheritance. Interfaces define contracts; support multiple inheritance. C# 8+ default interface methods allow interfaces to contain implementations, enabling backward-compatible API evolution without breaking implementers. They still cannot hold instance state, preserving the core distinction.

DN16 — **Middleware pipeline**: Sequential request/response processing. `app.Use()` adds middleware to the pipeline. `app.Map()` branches based on path prefix. `app.Run()` is terminal (no `next`). Ordering matters: auth before routing, caching before expensive handlers, exception handling at the end (or beginning for catch-all). Exception middleware (`UseExceptionHandler`) wraps downstream handlers, catches unhandled exceptions, logs, and returns error responses.

DN17 — **Channel<T> vs BlockingCollection<T>**: `Channel<T>` is async-native, supports bounded/unbounded, built-in backpressure, and integrates with `await foreach`. `BlockingCollection<T>` is sync/blocking, requires manual async wrapping. Bounded channel example:
```csharp
var ch = Channel.CreateBounded<int>(10);
// Producer: await ch.Writer.WriteAsync(item); // blocks when full
// Consumer: await foreach (var item in ch.Reader.ReadAllAsync()) { ... }
```
Backpressure naturally flows upstream when the buffer is full.

DN18 — **Source Generators**: Compile-time code generation via Roslyn APIs injecting C# source before compilation. Differs from reflection (runtime, slower, breaks obfuscation) and IL weaving (modifies compiled assemblies, harder to debug). Incremental generators (`ISourceGenerator` replacement) support caching, track input changes, and enable incremental compilation, drastically improving build performance for large projects.

DN19 — **TPL Dataflow**: Async message-passing library for pipelines/flow networks. `ActionBlock<T>` executes actions (no output). `TransformBlock<TIn, TOut>` transforms async. `BufferBlock<T>` stores messages for manual consumption. Compared to `Channels`, Dataflow offers built-in flow control, linking, completion propagation, and complex topologies. Use Dataflow for complex pipelines; Channels for simple producer-consumer.

DN20 — **Minimal APIs**: Lightweight, route-based endpoints without controllers (`app.MapGet("/", () => "Hello")`). Less boilerplate, faster startup vs controllers. Trade-offs: harder to test (requires `WebApplicationFactory`), explicit middleware integration, OpenAPI via `Microsoft.AspNetCore.OpenApi`. Route groups (`app.MapGroup("/api")`) share prefixes/middleware. Endpoint filters (`WithFilter()`) apply cross-cutting concerns (auth, validation) per endpoint.

P1 — **list vs tuple, set vs frozenset**: `list` is mutable, ordered, indexed, allows duplicates. `tuple` is immutable, ordered, fixed-size, heterogeneous (often for returning multiple values). `set` is mutable, unordered, unique elements, supports math ops. `frozenset` is immutable, hashable, usable as dict keys or set elements.

P2 — **GIL**: Global Interpreter Lock is a mutex allowing only one thread to execute Python bytecode at a time. Affects CPU-bound multi-threaded workloads (threads don't run in parallel). Workarounds: `multiprocessing`, C extensions releasing GIL, `asyncio` (I/O bound), or offloading to native code.

P3 — **deepcopy vs copy**: `copy.copy()` creates a shallow copy (new container, references original nested objects). `copy.deepcopy()` recursively copies all nested objects. Shallow copy bug: modifying a nested mutable object in the copy affects the original. Example: `a = [[1]]; b = copy.copy(a); b[0].append(2); print(a)` → `[[1, 2]]`.

P4 — **Decorators & timing**:
```python
import time, functools
def log_time(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — **Generators & yield**: Functions using `yield` produce iterators lazily, pausing/resuming state. Differ from lists by lazy evaluation, constant memory for large sequences, and supporting infinite sequences. `yield from` delegates to another generator/iterable, replacing manual loop/yield with cleaner syntax.

P6 — **asyncio event loop**: Core runtime managing async tasks and I/O scheduling. `asyncio.run()` creates loop, runs coroutine, closes loop. `asyncio.gather()` runs multiple coroutines concurrently, returns results. `asyncio.create_task()` schedules a coroutine for concurrent execution. `time.sleep()` blocks the entire event loop; use `await asyncio.sleep()` to yield control.

P7 — **MRO & diamond inheritance**: MRO defines method/attribute search order. Python 3 uses **C3 Linearization** (ensures monotonicity, preserves left-to-right order, avoids diamond issues). For `D(B, C)` where `B,C` inherit `A`, MRO is `D → B → C → A`. `D().who()` prints `"C"` because `B` doesn't override `who`, so lookup continues to `C`, which does.

P8 — **Metaclass vs __init_subclass__**: Metaclass controls class creation (`__new__`/`__init__`), powerful but complex. `__init_subclass__` is a class method called when a subclass is created, simpler and instance-like. Metaclass use case: ORM model registration, enforcing strict class structure. `__init_subclass__` use case: auto-registering plugins, adding default attributes to subclasses.

P9 — **multiprocessing vs threading vs concurrent.futures**: Threading: I/O bound, shares memory, GIL limits CPU parallelism. Multiprocessing: CPU bound, separate processes, bypasses GIL, higher overhead. `concurrent.futures`: High-level API wrapping both (`ThreadPoolExecutor`/`ProcessPoolExecutor`). Multiprocessing uses pickling for IPC; unpicklable objects (open files, locks, lambdas) fail. Use `__getstate__`/`__setstate__` or avoid complex state.

P10 — **__slots__**: Declares fixed attributes, prevents `__dict__` creation. Use for memory optimization, faster attribute access, and preventing accidental attributes. Memory impact: significant reduction per instance (no dict overhead), crucial for millions of objects. Trade-off: breaks inheritance flexibility, requires explicit slot declaration.

P11 — **Virtual environments**: Isolated Python environment with its own packages/interpreter. Prevents dependency conflicts and ensures reproducibility. `venv`: Standard library, lightweight, Python 3.3+. `virtualenv`: Third-party, older, largely superseded. `conda`: Package + environment manager, handles non-Python dependencies, data-science focused.

P12 — **Comprehensions vs map/filter**: Comprehensions (`[x for x in lst if cond]`) are Pythonic, readable, and often faster. `map()`/`filter()` are functional, return lazy iterators. Prefer comprehensions for readability. Use `map`/`filter` when composing functions or building lazy functional pipelines.

P13 — **== vs is, interning**: `==` checks value equality (`__eq__`). `is` checks identity (same memory address). CPython interns small integers (-5 to 256) and some strings for performance. `a is b` returns `True` for small ints because they reference the same cached object. Not guaranteed for larger values or different creation contexts.

P14 — **\*args, \*\*kwargs, /, \***: `*args` collects variable positional arguments into a tuple. `**kwargs` collects variable keyword arguments into a dict. `/` marks parameters as positional-only. `*` marks parameters as keyword-only. Use for flexible APIs, plugin systems, or when parameter names matter but count varies.

P15 — **Context managers**: `with` ensures cleanup (`__exit__`) even on exceptions. Class-based: implement `__enter__`/`__exit__`. Generator-based: use `@contextmanager` where `yield` acts as the boundary. Example (DB transaction):
```python
@contextmanager
def transaction(db):
    try:
        db.begin()
        yield
        db.commit()
    except:
        db.rollback()
        raise
```

P16 — **Type hinting**: Optional annotations for static analysis. `Union[A, B]` (either), `Optional[T]` (`Union[T, None]`), `Literal["a"]` (exact value), `TypeVar` (generic constraints), `Protocol` (structural subtyping). `mypy`/`pyright` parse annotations, check consistency, catch type errors pre-runtime, and enable IDE autocomplete.

P17 — **Data model (dunder methods)**: `__repr__` (unambiguous, dev-focused), `__str__` (readable, user-focused). `__eq__` (value equality), `__hash__` (hash for dict/set). `__getattr__` (fallback when attr missing), `__getattribute__` (intercepts every access, dangerous). Defining `__eq__` without `__hash__` sets `__hash__ = None`, making instances unhashable.

P18 — **Descriptors**: Objects implementing `__get__`, `__set__`, `__delete__` that control attribute access on other objects. `property` wraps getters/setters as a data descriptor. `classmethod`/`staticmethod` are non-data descriptors modifying lookup behavior. Attribute lookup checks descriptor protocol on the class before instance `__dict__`, allowing descriptors to intercept and customize access.

P19 — **Import system**: Relative imports (`from .module import X`) resolve relative to current package. Absolute imports (`from package.module import X`) resolve from `sys.path`. `PYTHONPATH` prepends to `sys.path`. `__init__.py` marks directories as packages. Namespace packages lack `__init__.py`, allowing split packages. Finders locate modules; loaders execute code. Custom finders/loaders enable dynamic imports.

P20 — **dataclasses vs attrs vs Pydantic**: `dataclasses` (built-in) generates `__init__`, `__repr__`, `__eq__`; simple and fast. `attrs` (third-party) offers more flexibility, validation, converters. `Pydantic` adds validation, serialization, type coercion, JSON/schema generation. `__post_init__` runs after init for custom setup. `field(default_factory=list)` avoids mutable default bugs. `frozen=True` makes instances immutable. Choose `Pydantic` for validation/serialization/API schemas; `dataclasses` for simple, fast, built-in DTOs.
