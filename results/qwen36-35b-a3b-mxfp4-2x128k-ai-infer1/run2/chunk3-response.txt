T1 — `tofu plan` evaluates your configuration against the current state and live infrastructure, producing a preview of what will be created, updated, or destroyed without making changes. `tofu apply` executes that plan, making the actual API calls to provision/modify resources.

T2 — State is a JSON file mapping your configuration to real-world resource IDs and attributes. Remote state stores this file in a shared backend (S3, GCS, Terraform Cloud, etc.), enabling team collaboration, preventing state corruption via locking, and keeping sensitive data out of local repos.

T3 — `count` uses integers to create sequential resources; adding/removing items can cause destructive recreation due to index shifting. `for_each` uses maps or sets, mapping each item to a unique key. `for_each` is preferred when resources have distinct identifiers or when you need stable addresses to avoid unintended replacements.

T4 — OpenTofu detects drift during `tofu plan` by comparing the state file to live API responses. If attributes changed outside OpenTofu, it proposes an update. If the resource schema doesn't match or the ID changed, it may mark the resource as tainted, requiring recreation.

T5:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `terraform_remote_state` reads the entire state file, exposing all outputs and risking performance/security issues. Outputs expose only specific values. The recommended alternative is passing outputs directly via module arguments or using `data "terraform_remote_state"` only when necessary with explicit `outputs` filtering. Direct module output passing avoids state coupling and improves security.

T7 — `remote-exec` provisioners run during apply, but outputs are evaluated before the provisioner finishes, leaving the kubeconfig empty. Fix: Use `local-exec` to write the kubeconfig to a file, then read it with `file("${path.module}/kubeconfig")`, or add `depends_on = [null_resource.kubeconfig]` to the output/resource, or use the cluster provider's native kubeconfig output instead of a null_resource.

T8 — `tofu import` manually maps existing infrastructure to config by running `tofu import <address> <id>`. Limitations: requires manual schema mapping, doesn't handle dependencies, and can break if the resource type changes. The `import` block (1.5+) allows declarative imports in config, supports multiple resources, provides better error messages, and integrates with `tofu plan` for safer migrations.

T9 — A `variable` is an input parameter that flows into your configuration/module. An `output` is a value exposed from your configuration/module to consumers. Variables are for external input; outputs are for internal computation exposed outward.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a specific platform (AWS, K8s, etc.). Without `tofu init`, providers aren't downloaded or initialized, so `tofu plan`/`apply` fails with "provider not found" errors.

T11 — `.terraform.lock.hcl` is a dependency lock file that pins provider and module versions to exact digests. Commit it to version control to ensure reproducible builds, prevent supply chain attacks, and avoid unexpected breaking changes.

T12 — `tofu destroy` removes all resources managed by the current state. Target a single resource: `tofu destroy -target=<resource_type.resource_name>`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to dynamically fetch the latest Ubuntu image instead of hardcoding an ID or managing the image as a resource.

T14 — `locals` compute values within the configuration and aren't exposed as inputs. `variables` accept external input. Use `locals` for complex expressions, filtering, or computed values to keep code DRY and avoid cluttering input variables.

T15 — The `lifecycle` block controls resource behavior:
- `create_before_destroy = true`: Creates new resource before deleting old (zero-downtime upgrades).
- `prevent_destroy = true`: Blocks accidental deletion (safety net for critical resources).
- `ignore_changes = ["tags"]`: Skips drift detection for specified attributes (e.g., externally managed tags).

T16 — The `moved` block declares a resource address change without destroying/recreating. It updates the state mapping so OpenTofu recognizes the resource at its new address, enabling safe refactoring of module structure or resource naming.

T17 — OpenTofu builds a DAG of dependencies. Implicit dependencies are inferred from references in config. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, reducing parallelism and creating bottlenecks. Use sparingly; prefer implicit references for optimal concurrency.

T18 — Strategies to reduce plan time:
1. Split into multiple modules/backends → Tradeoff: Increased management overhead.
2. Use `tofu plan -target` for scoped changes → Tradeoff: Limited to specific resources.
3. Cache data sources / use `tofu console` for pre-computation → Tradeoff: May miss live changes.
4. Increase `parallelism` or use `tofu plan -refresh=false` → Tradeoff: Higher API rate limits or potential drift.

T19 — State locking prevents concurrent writes to the backend. If a CI pipeline crashes, the lock remains, blocking future runs. Break it with `tofu force-unlock <LOCK_ID>`. Risks: concurrent modifications, state corruption, or lost changes if another process is actively writing.

T20 — Steps:
1. Add remote backend config (S3 + DynamoDB) to your `.tf` files.
2. Run `tofu init -migrate-state`. OpenTofu uploads the local state to S3 and sets up DynamoDB locking.
3. Verify: Check S3 bucket for the state file, confirm DynamoDB table has a lock item, and run `tofu plan` to ensure no drift.
4. The local state file is replaced; all future operations use the remote backend.

A1 — A playbook is a YAML file defining automation steps. A role is a reusable collection of tasks, handlers, vars, and templates. A task is a single unit of work (usually a module call). Roles organize playbooks; tasks execute them.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_os_family }}`.

A3 — `command` runs without shell features (no pipes/redirects). `shell` runs via `/bin/sh`, supporting shell syntax. `raw` runs without JSON/Python, useful for bootstrapping or minimal systems lacking Python.

A4 — Idempotency means a task produces the same result regardless of execution count. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run) or `command: rm -rf /tmp/*`.

A5:
```yaml
- name: Install htop conditionally
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel and htop on RedHat
  block:
    - name: Install epel-release
      package:
        name: epel-release
        state: present
    - name: Install htop
      package:
        name: htop
        state: present
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (high to low): Extra vars > Task vars > Role vars > Play vars > Host vars > Group vars > Role defaults > Inventory vars. `set_fact` overrides most except extra vars. Extra vars always win.

A7 — Use `serial: 3` to process 3 nodes at a time. Add `max_fail_percentage: 0` to ensure the first batch succeeds before proceeding. Use inventory groups (`rke2_first`, `rke2_rest`) and `wait_for` or `pause` if explicit gating is needed. `serial` handles batching natively.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'secret_value' --name 'my_secret' > vars.yml`, then paste the `!vault` block into your vars file. Only that line is encrypted.

A9 — An inventory lists hosts and groups. Static inventory is a hardcoded file. Dynamic inventory is a script/API that generates inventory at runtime (e.g., AWS EC2, Azure, GCP).

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task triggered by `notify`. It only runs if notified, runs once per play, and executes at the end of the play. Trigger with `notify: handler_name`.

A12 — `ansible.cfg` configures global Ansible behavior. Common settings: `inventory`, `remote_user`, `forks`, `private_key_file`, `host_key_checking`, `pipelining`.

A13 — `register` saves task output to a variable. Use it in subsequent tasks: `when: my_var.stdout == "success"` or `debug: var=my_var`.

A14 — `include_tasks` is dynamic (evaluated at runtime), supports `when`/`loop`. `import_tasks` is static (evaluated at parse time), ignores `when`/`loop`. Use `include` for conditionals/loops, `import` for performance/static inclusion.

A15 — Ansible Galaxy is a repository for roles/collections. `requirements.yml` lists them. Install with `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible connects to hosts. `ssh` = standard SSH for Linux/Unix. `local` = runs on control node. `network_cli` = Telnet/SSH for network devices. Use `ssh` for servers, `local` for control node tasks, `network_cli` for routers/switches.

A17 — `delegate_to` runs a task on a different host. `run_once` runs it once across a group. Example: Gather facts from a remote host, then process on localhost:
```yaml
- name: Process remote data on control node
  debug: msg="{{ remote_data }}"
  delegate_to: localhost
  run_once: true
```

A18 — Strategies:
1. Increase `forks` (e.g., 20-50) → Tradeoff: Higher CPU/memory on control node.
2. Enable `pipelining` in `ansible.cfg` → Tradeoff: Requires sudoers config, reduces SSH overhead.
3. Use fact caching (Redis/Memcached) → Tradeoff: Stale facts if not refreshed.
4. Use Mitogen (forking plugin) → Tradeoff: Experimental, potential compatibility issues.

A19 — Jinja2 generates dynamic configs. `{{ }}` outputs expressions. `{% %}` controls flow (if/for). `{# #}` comments.
Template snippet:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check: {{ server }}
  server {{ server }};
{% endfor %}
}
```

A20 — Rolling deploy structure:
- `serial: 1` (or 2) for batch processing.
- `pre_tasks`: Deregister from LB via `uri` module.
- `tasks`: Deploy app.
- `post_tasks`: Register to LB, health check with `uri` module.
- `block/rescue`: On failure, rollback LB registration or revert config. Use `max_fail_percentage: 0` to halt on first failure.
