CL1 — IaaS provides virtualized compute, network, and storage where you manage the OS, middleware, and applications (e.g., AWS EC2). PaaS provides a managed runtime/environment where you deploy applications and manage data (e.g., Google App Engine). SaaS delivers fully managed applications where the provider handles everything (e.g., Salesforce).

CL2 — The Shared Responsibility Model divides security duties. IaaS VM: Provider secures hypervisor, physical infrastructure, and network; you secure OS, patches, applications, data, and host-level firewall. Managed Kubernetes: Provider secures the control plane, node OS, and cluster networking; you secure workloads, RBAC, network policies, and secrets. SaaS (M365): Provider secures the application, infrastructure, and compliance; you manage user access, data classification, DLP policies, and device compliance.

CL3 — VPC: Isolated virtual network. Subnet: VPC partition (public/private). Security Group (SG): Stateful, instance/pod-level, allow-only rules. NACL: Stateless, subnet-level, allow/deny rules. Layering: Traffic is evaluated by NACL first (subnet boundary), then SG (resource boundary). Stateful (SG): Automatically allows return traffic regardless of outbound rules. Stateless (NACL): Requires explicit allow rules for both inbound and outbound traffic.

CL4 — Landing zone: Pre-configured, secure multi-account foundation with baseline networking, logging, and guardrails. OUs: Logical grouping by environment, team, or workload. Guardrails: Automated policy enforcement (e.g., SCPs, Azure Policy) preventing risky actions. Shared networking: Transit Gateway/Azure Hub-and-Spoke centralizes VPC peering, on-prem connectivity, and traffic inspection. Centralized logging: Dedicated account/service aggregates logs for compliance and monitoring. Single-account is problematic due to high blast radius, permission sprawl, opaque billing, compliance isolation failures, and inability to separate environments safely.

CL5 — IaC: Declarative/programmatic provisioning. Terraform/OpenTofu: State-driven, HCL, broad provider support; ideal for multi-cloud or general infrastructure. Pulumi: General-purpose languages (TS, Python), state-driven; ideal for teams wanting full programming power and complex logic. CFN/Bicep: AWS-native, tightly integrated; ideal for AWS-only shops. Crossplane: Kubernetes-native, manages cloud resources via CRDs; ideal for GitOps/K8s-centric teams wanting a unified control plane.

CL6 — HPA: Scales pods based on CPU/memory/custom metrics. VPA: Recommends/sets optimal resource requests/limits per pod. Cluster Autoscaler: Adds/removes nodes based on pending pods. KEDA: Event-driven scaling (queues, HTTP, DB, cron). Use KEDA over HPA when scaling is driven by external events (e.g., message queue depth, HTTP concurrency) rather than static resource metrics.

CL7 — DR Strategy: Define RPO (max data loss) and RTO (max downtime). Active-passive: Primary handles traffic, secondary idle/warm; lower cost, higher RTO. Active-active: Both regions serve traffic; higher cost, lower RTO. DB: Sync replication (strong consistency, higher latency, active-active) vs Async (eventual consistency, lower latency, active-passive). DNS: Route53/Traffic Manager with health checks for automatic failover. State: Externalize to managed DB/cache; avoid local state. Cost: Active-active doubles infra; pilot light/warm standby reduce cost but increase RTO. Pilot light: Core infra running, minimal data. Warm standby: Scaled-down but ready. Multi-site active-active: Full capacity in both regions.

CL8 — GitOps: Git as single source of truth; controllers sync cluster state to Git manifests. ArgoCD: UI-focused, push-based, strong audit/UI; ideal for app delivery. FluxCD: Git-native, pull-based, tightly integrated with Git providers; ideal for infra/automation. Secrets: SealedSecrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from cloud/Vault), Vault (dynamic secrets, auth). Drift: Controllers detect drift, automatically revert to Git state or alert; manual changes are overwritten on next sync.

CL9 — Architecture: StatefulSet provides stable network ID and storage. PV/PVC: Use `local` storage class with `volumeBindingMode: WaitForFirstConsumer` to ensure node affinity. Headless service: Provides stable DNS for pods. Init containers: Pre-load config, validate dependencies. ConfigMaps: Mount as volumes at specific filesystem paths. PDB: Set `minAvailable` to ensure quorum during node failures. Add pod anti-affinity to spread replicas and prevent single-point failures.

CL10 — Service Account: K8s-native identity for pods. Workload Identity (GCP/AWS): Maps K8s SA to cloud IAM role without keys. IRSA: AWS-specific, uses OIDC to assume IAM role via K8s SA. Mounting static credentials is bad: hard to rotate, high blast radius, violates least privilege, easily exfiltrated. Workload identity federation solves this by using short-lived, scoped tokens via OIDC, eliminating static credentials and enabling automatic rotation.

CL11 — Object (S3/Blob): Unstructured data, HTTP API, high durability (11 9s), eventual consistency. Use for backups, media, logs. Block (EBS/Disk): Low-latency, attached to VM, formatted filesystem. Use for OS, databases, apps. File (EFS/Azure Files): NFS/SMB, shared across VMs. Use for shared configs, home dirs. Availability: Object is regional/zonal; Block is zonal; File is regional.

CL12 — Zero-Trust K8s: Network policies restrict pod-to-pod traffic (default deny). Service mesh (Istio/Linkerd) enforces mTLS for east-west traffic. Pod identity (Workload Identity/IRSA) binds pods to cloud IAM. Admission controllers (OPA/Kyverno) enforce policies on deploy. Image signing (Cosign/Notary) + verification prevents malicious images. Runtime security (Falco) detects anomalous behavior. Secrets: External Secrets Operator/Vault. Differs from perimeter model by assuming breach, verifying every request, and securing east-west traffic instead of just north-south.

CL13 — CDN: Distributed edge network caching static/dynamic content closer to users. Works via DNS routing to nearest edge, caching responses, invalidating on change. Services: CloudFront, Azure CDN. Use CDN when: reducing origin load, improving latency globally, handling traffic spikes, offloading TLS, or serving static assets. Direct origin is fine for low-traffic, geo-localized, or highly dynamic/private content.

CL14 — Region: Geographic area with multiple AZs. AZ: Isolated data center(s) within a region, independent power/network. Deploy across AZs for high availability and fault tolerance against single-site failure. Zonal resources: Tied to one AZ (EBS, EC2 instances). Regional resources: Span multiple AZs (ALB, RDS Multi-AZ, S3).

CL15 — Managed DB (RDS/Cloud SQL): Provider handles provisioning, patching, backups, replication, monitoring, failover, and storage scaling. Self-hosted on VM: You manage OS, DB software, patches, backups, replication, tuning, and HA setup. Managed saves operational overhead but reduces low-level control.

CL16 — IAM: Users (human/service), Groups (collections), Roles (assumable identities with policies), Policies (JSON permissions). Least privilege: Grant only necessary permissions. Apply via scoped policies, avoid `*`, use roles over users, enable MFA, audit regularly, and use permission boundaries.

CL17 — Serverless: Event-driven, managed compute, auto-scaling, pay-per-use. Lambda/Functions/GCF: Similar core model, differ in runtime support, cold start behavior, and ecosystem integration. Cold starts: Delay when provisioning new container/instance for first request. Matter for latency-sensitive apps. Poor fit: Long-running processes, high memory/CPU needs, strict latency requirements, complex stateful workloads, or when vendor lock-in is unacceptable.

CL18 — Ingress options: Ingress resource (K8s standard, relies on controller, TLS at controller). Gateway API (K8s standard, decouples controller, supports multiple gateways, TLS at gateway). Cloud LB annotations (direct cloud LB, TLS at LB). Mesh ingress (service mesh, TLS at mesh sidecar). TLS termination: Ingress/Mesh at proxy/gateway; Cloud LB at load balancer. Use Gateway API for: multiple ingress controllers, advanced traffic splitting, better RBAC, and future-proofing beyond Ingress limitations.

CL19 — Cost optimization ($80k/mo): RI/SP: Commit to usage for 1-3yr discounts (compute). Spot/Preemptible: Up to 90% off, interruptible (batch, fault-tolerant). Right-sizing: Match instance size to actual metrics. Storage tiering: Lifecycle policies to Glacier/Archive. Idle detection: Cloud Health/Trusted Advisor, auto-shutdown dev envs. FinOps: Cross-functional team, cloud cost visibility, accountability. Showback/chargeback: Allocate costs by team/project via tags. Tools: CloudHealth, Kubecost, native cost explorer. Process: Tagging strategy, monthly reviews, budget alerts, automated remediation.

CL20 — Multi-cloud strategy: Abstraction: Kubernetes, Terraform, service mesh. K8s: Common runtime across clouds. Terraform: Provider-agnostic IaC. Networking: Cloud VPN/Interconnect for hybrid/multi-cloud traffic. Identity: Federation via OIDC/SAML to central IdP. Trade-offs: Increased complexity, higher networking costs, fragmented tooling, delayed feature parity. Justified when: regulatory/data sovereignty requires it, negotiating leverage, or catastrophic vendor failure risk. Unnecessary when: single-cloud features provide better performance/cost, or team lacks multi-cloud expertise.

OT1 — Purdue Model: ISA-95 hierarchy for industrial automation. Level 0: Physical process (sensors/actuators). Level 1: Basic control (PLCs/RTUs). Level 2: Supervisory control (SCADA/HMI). Level 3: Site operations (historian, MES). Level 4: Enterprise (ERP, business planning). Level 5: Business network (corporate IT).

OT2 — IT: Focuses on confidentiality/integrity, fast patching, standard OS, user-centric. OT: Focuses on availability/safety, real-time control, legacy OS, process-centric. Standard IT patching fails in OT because patches require downtime, can break legacy drivers/protocols, and may alter timing/control logic, risking safety/production.

OT3 — IDMZ: Segmented network between IT (L4) and OT (L1-3). Allows controlled data exchange (e.g., historian sync, reporting) via unidirectional or strictly filtered bidirectional traffic. Only specific protocols (OPC UA, MQTT) and IPs allowed. Direct L4 to L1 is dangerous because IT threats (malware, ransomware) can directly compromise control logic, cause physical damage, or disrupt safety systems.

OT4 — Modbus TCP: L2/L3, legacy PLC communication, unencrypted. OPC UA: L2/L3, modern secure data exchange, platform-independent. EtherNet/IP (CIP): L2/L3, Allen-Bradley dominant, industrial Ethernet. PROFINET: L2, real-time deterministic, Siemens dominant. MQTT: L3/L4, lightweight IoT/cloud messaging, often used at edge/cloud boundary.

OT5 — Data diode: Hardware-enforced unidirectional network link. Firewall: Bidirectional, inspects/controls traffic both ways. Use diode when: data must flow strictly one-way (e.g., OT to IT for monitoring) with zero risk of return traffic. Limitation: Cannot support bidirectional protocols (e.g., command/control, acknowledgments), making it unsuitable for interactive control or protocols requiring two-way handshakes.

OT6 — Data flow: PLCs/RTUs (L1) -> SCADA/Historian (L2/L3) -> OPC UA server -> Edge gateway (protocol translation, buffering) -> MQTT broker (secure TLS) -> Cloud ingestion (Kafka/Event Hub) -> Analytics. Security boundaries: IDMZ between OT/IT, edge gateway as security choke point, mutual TLS for MQTT, cloud WAF/IDS, network segmentation, and data validation at ingestion.

OT7 — IEC 62443: Zones = logical/physical groupings with similar security requirements. Conduits = communication paths between zones. Zone definition: Based on function, risk, and security level (SL). Design: Zone 1: PLCs/SIS (SL 3-4). Zone 2: SCADA/HMI/Historian (SL 2-3). Zone 3: Engineering WS (SL 2). Zone 4: Corporate/IT (SL 1). Conduits: Zone 1↔2 (firewall/data diode, strict protocols). Zone 2↔3 (firewall, jump host). Zone 3↔4 (IDMZ, controlled sync). SIS isolated in Zone 1 with physical/logical separation from BPCS.

OT8 — Segmentation: VLANs per production line, utility, and management. Firewalls at VLAN boundaries and IDMZ. Switch architecture: Managed Layer 3 switches with ACLs, port security, and 802.1X. Remote access: Secure jump host in IDMZ, MFA, session recording, time-bound vendor accounts, no direct L1/L2 access. Transition: Phased rollout, parallel run, backup configs, maintenance windows, rollback plan, validate control logic before cutting over.

OT9 — SIS: Independent system for emergency shutdown/safety (IEC 61511 defines lifecycle). BPCS: Normal process control. SIS must be isolated/air-gapped to prevent IT/OT cyber threats from compromising safety functions. Ransomware on SIS: Could disable safety interlocks, cause uncontrolled release, equipment damage, or loss of life. Physical/logical isolation ensures safety remains intact during cyber incidents.

OT10 — PLC: Discrete control for specific machines/lines. DCS: Integrated control for continuous processes (chemical, oil/gas). SCADA: Supervisory monitoring/control across geographically dispersed assets. Use PLC for discrete manufacturing, DCS for continuous process, SCADA for utilities/pipelines. They coexist: PLCs/DCS handle control, SCADA provides HMI/historian/oversight.

OT11 — Remote access: Jump host in IDMZ, MFA, session recording (video/CLI), vendor accounts with time limits, network segmentation, no direct HMI access. RDP to HMI from corp is unacceptable because it bypasses segmentation, exposes control interfaces to corporate threats, lacks audit trails, and violates IEC 62443 zone/conduit principles.

OT12 — Detection/Response: IDS/ANOMALY detection on OT network (passive monitoring), asset inventory baseline, isolate compromised L3 segments, block vendor VPN, engage IR team. Coordination: Notify control room, switch to manual/local control if needed, preserve evidence. Safe ops: Maintain SIS/BPCS integrity, avoid disruptive actions, prioritize safety over data. Operator role: Monitor physical process, execute manual overrides if automated systems fail, report anomalies, follow cyber-physical incident playbook.

OT13 — HMI: Operator interface for monitoring/controlling processes (displays trends, alarms, controls). Differs from engineering workstation: HMI is for operators (read-only or limited control, no programming). Engineering WS is for programmers/configurators (ladder logic editing, parameter changes, firmware updates).

OT14 — Historian: Time-series database for process data (temperatures, pressures, setpoints). Important for compliance, optimization, troubleshooting. Plant historian (L3): Stores raw process data, real-time, high frequency. Enterprise historian (L4): Aggregated, lower frequency, used for business analytics, reporting, ERP integration.

OT15 — Ladder logic: Graphical programming language mimicking relay circuits. Executed by PLCs. Dominant because: intuitive for electricians, deterministic execution, decades of training/tooling, backward compatibility, and safety certification familiarity.

OT16 — RTU: Remote Terminal Unit, designed for harsh environments, long-distance communication (cellular/satellite), analog I/O, and telemetry. Differs from PLC: RTUs focus on remote data collection/aggregation; PLCs focus on local control. Deploy RTUs in: pipelines, water/wastewater, wind farms, oil/gas fields.

OT17 — Analog signals: Continuous voltage/current representing process values. Digital: Discrete on/off or binary. 4-20mA preferred over 0-20mA because 4mA "live zero" indicates wire break/failure (0mA = fault), enables two-wire loop-powered instruments, and provides noise immunity over long distances.

OT18 — Asset inventory: Complete list of OT hardware/software/firmware. Foundation because you can't secure/patch what you don't know. Tools: Passive monitoring (packet capture, protocol analysis) safe for OT. Active scanning (port scans, ping sweeps) dangerous because it can crash legacy devices, trigger alarms, or disrupt control loops. Use passive or vendor-approved low-impact tools.

OT19 — MITRE ATT&CK for ICS: Tactics: Reconnaissance, Resource Development, Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command & Control, Impact. Example techniques: Initial Access (Supply Chain Compromise), Execution (Command and Scripting Interpreter), Impact (Data Destruction, Process Disruption). Differs from enterprise: Focuses on physical processes, safety, legacy protocols, and industrial equipment. Use for gap assessment: Map existing controls to tactics/techniques, identify missing detections (e.g., no monitoring for unauthorized PLC programming), prioritize mitigations.

OT20 — Converged SOC: Log collection: Passive network taps, OT-friendly agents, forward to SIEM without impacting real-time. SIEM: Correlate IT/OT logs, tag OT assets. OT rules: Focus on protocol anomalies, unauthorized changes, safety interlock violations. Triage: OT engineers validate physical impact, IT analysts handle data. Staffing: Hybrid team (IT security + OT engineers). False positives: Tune rules to OT baselines, use passive data, avoid alert fatigue. Firmware alert: Isolate affected PLC, verify change request, check backup/rollback plan, engage engineering, document, update baseline, monitor for lateral movement.
