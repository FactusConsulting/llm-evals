G1 — An array `[T; N]` has a fixed size baked into its type and is typically stack-allocated. A slice `[T]` or `&[T]` has a dynamic length, size is not part of the type, and points to a heap-allocated backing array. When `append` exceeds a slice's capacity, Go allocates a new backing array (usually doubling capacity), copies elements, and returns a new slice. The original slice remains unchanged.

G2 — `var x int` declares a variable with Go's zero value (`0`), can be used at package level, and doesn't infer type. `x := 0` is a short variable declaration, infers type, requires a right-hand side, and is only valid inside functions. You cannot use `:=` outside functions, to redeclare an existing variable in the same scope without introducing a new one, or when type inference is ambiguous/undesired.

G3 — A goroutine is a lightweight (~2–4KB stack) concurrency primitive managed by the Go runtime. OS threads are heavy (~1–2MB stack) and managed by the kernel. The GMP scheduler multiplexes G (goroutines) onto M (OS threads) using P (processors/scheduler contexts). Ps enable work-stealing, preemption, and efficient CPU utilization without blocking OS threads.

G4 — Channels are typed communication pipes. Unbuffered channels synchronize senders and receivers (send blocks until a receiver is ready). Buffered channels allow asynchronous sends up to their capacity. Sending to a full buffered channel blocks until a receiver reads a value, freeing space.

G5 — `context` carries deadlines, cancellation signals, and request-scoped values across API boundaries. Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
client.Do(req) // cancels automatically on timeout
```

G6 — Go uses structural interface satisfaction: any type implementing the required methods implicitly satisfies the interface (duck typing). Java/C# require explicit declaration (`implements`/`:`). `interface{}` (Go 1.18+ `any`) accepts any type. It's powerful for flexible APIs but dangerous because it bypasses compile-time type safety, requiring runtime type assertions or reflection.

G7 — Unsafe due to a data race: no synchronization guarantees `data` is visible before `ready` is read. Fixes: (1) Use `sync/atomic` with `atomic.Pointer[string]` (Go 1.19+), (2) Signal via channel, (3) Use `sync.Mutex` protecting both variables, or (4) `sync.WaitGroup`. Channels or atomics are idiomatic for this pattern.

G8 — `sync.Mutex` provides exclusive access. `sync.RWMutex` allows concurrent readers or a single writer. `sync.Map` is optimized for read-heavy workloads or disjoint key sets. Trade-offs: `sync.Map` has higher per-operation overhead and memory usage; a regular `map`+`Mutex` is faster for frequent writes or dense key sets. `RWMutex` wins for read-dominant workloads.

G9 — Modules manage versioned dependencies. `go.mod` declares direct dependencies and Go version. `go.sum` cryptographically hashes indirect dependencies for integrity. `go mod tidy` removes unused deps, adds missing ones, and updates `go.sum`. MVS (Minimum Version Selection) picks the lowest version satisfying all direct/indirect constraints, ensuring reproducible builds and preventing version skew.

G10 — `defer` schedules a function call to run after the surrounding function returns. Multiple defers execute in LIFO order. Gotcha in loops: variables captured by closures are evaluated at defer execution time, not call time. Fix: pass as arguments `defer func(v int) { ... }(v)` or create a new scope per iteration.

G11 — A pointer stores a memory address. Zero value is `nil`. Pointer to a struct literal: `&MyStruct{Field: value}`.

G12 — `init()` runs automatically before `main()`. Executes once per package. Multiple `init()` functions run in declaration order; files in the same package run in filename order. Used for setup, registration, or validation. Cannot be called manually.

G13 — `new(T)` allocates zeroed memory for type `T` and returns `*T`. Works for any type. `make(T, args)` initializes internal data structures and returns `T` (not a pointer). Only works for slices, maps, and channels.

G14 — Errors use the `error` interface (`Error() string`). Idiomatic pattern: check `if err != nil` immediately. `errors.Is(err, target)` checks if the error matches `target` anywhere in the wrapping chain. `errors.As(err, &target)` extracts a specific error type from the chain. `==` only checks direct equality and fails with wrapped errors.

G15 — Map: `nil` (reads OK, writes panic). Slice: `nil` (len/cap 0). Channel: `nil` (blocks forever). Struct: zero values of fields. All are safe to read; nil maps/slices/channels behave differently on writes/ops.

G16 — A race occurs when concurrent goroutines access shared data without synchronization, with at least one write. `-race` flag instruments the binary with shadow memory to detect races at runtime. Example: concurrent `counter++` and `fmt.Println(counter)`. Fix: wrap access in `sync.Mutex` or use a channel for communication.

G17 — `select` waits on multiple channel operations. Unlike `switch` (evaluates immediately), `select` blocks until at least one case is ready. If multiple are ready, one is chosen randomly. Timeout: `case <-time.After(d):` or `case <-ctx.Done():`.

G18 — Escape analysis determines if a variable must live on the heap (outlives stack frame) vs stack. Decisions depend on pointer aliasing, closure captures, interface boxing, and return addresses. Inspect with `go build -gcflags="-m"`. Matters because heap allocations trigger GC; minimizing escapes improves latency and throughput.

G19 — `reflect` provides runtime introspection. `reflect.Type` holds type metadata; `reflect.Value` holds actual data. Costs: slow, bypasses compile-time checks, creates GC roots. Justified for serialization, testing, or generic-like frameworks. Prefer code generation (`go generate`, `stringer`, `mockgen`) for performance-critical paths.

G20 — `go:embed` compiles static files into the binary at compile time. Works for single files, directories (`//go:embed dir/`), and exposes them via `embed.FS` implementing `io/fs.FS`. Limitations: static-only, no runtime paths, must be in the same package, size constraints. Interacts with `io/fs.FS` by providing a virtual tree accessible via `fs.Sub`, `fs.ReadDir`, etc.

R1 — Ownership is Rust's core memory management model. Rules: (1) Each value has exactly one owner. (2) When the owner goes out of scope, the value is dropped. (3) At any time, you can have either one mutable reference (`&mut T`) or any number of shared references (`&T`), but not both. Prevents leaks/dangling pointers without a GC.

R2 — `String` is a heap-allocated, growable, owned string. `&str` is a borrowed, fixed-size reference to UTF-8 bytes. Function signatures: use `&str` for read-only input (zero-copy, accepts both `String` and literals). Use `String` when ownership transfer or mutation is required.

R3 — Borrowing accesses data without taking ownership. The borrow checker enforces: (1) References must be valid. (2) Either one `&mut T` or any number of `&T` references at a time. (3) No simultaneous mutable and shared references. Prevents data races and dangling references at compile time.

R4 — `Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`). `Option<T>` represents `Some(T)` or `None`. The `?` operator unwraps `Ok`/`Some` or returns early on `Err`/`None`. Example:
```rust
use std::fs;
fn read_file(path: &str) -> Result<String, std::io::Error> {
    fs::read_to_string(path)
}
```

R5 — `Box<T>`: heap allocation, single owner, moves data. `Rc<T>`: reference counting, single-threaded shared ownership. `Arc<T>`: atomic reference counting, thread-safe shared ownership. Use `Box` for large/recursive types, `Rc` for shared read-only data in one thread, `Arc` for concurrent shared data.

R6 — Traits are Rust's interface mechanism. Like Go interfaces but require explicit `impl Trait for Type`. `dyn Trait`: trait object, dynamic dispatch (vtable), heap-allocated, enables heterogeneous collections. `T: Trait`: generic with trait bound, static dispatch (monomorphization), zero-cost, type-specific code generation.

R7 — Fails: compiler cannot determine which input lifetime applies to the output. Fix: tie input lifetimes to the output:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

R8 — `Send`: type can be transferred across thread boundaries. `Sync`: type can be shared across threads (`&T` is `Send`). `Rc<T>` is neither `Send` nor `Sync` due to non-atomic ref counting. `Arc<T>` uses atomic ref counting, making it `Send`+`Sync` (requires `T: Send`).

R9 — `async/await` compiles to a state machine implementing `Future`. `Future::poll()` advances the state. An executor (e.g., Tokio) drives futures, handles I/O multiplexing, and schedules tasks. Differs from Go: Go uses preemptive green threads (blocking syscalls yield), Rust uses cooperative async (explicit polling, non-blocking by design, executor-driven).

R10 — `unsafe` bypasses compile-time safety checks. Three things: (1) Dereference raw pointers, (2) Call `unsafe` functions, (3) Read/write `static mut`. Justified when interfacing with C, implementing low-level primitives, or optimizing critical paths where safety invariants are manually upheld.

R11 — Pattern matching: `match` exhaustively matches enum/struct variants. `if let` matches a single case and ignores others. The compiler enforces exhaustiveness in `match` (compile error if missing), but `if let` is intentionally partial. Enables safe, expressive control flow.

R12 — `Vec<T>`: heap-allocated, growable array. `[T; N]`: fixed-size, typically stack-allocated. When `Vec` is pushed beyond capacity, it allocates a new larger buffer (usually doubles), copies elements, drops the old buffer. `Vec::reserve()` can pre-allocate to avoid reallocations.

R13 — Enums are algebraic data types that can hold data per variant. Unlike C/Java (integer-backed or flat), Rust enums are memory-efficient and type-safe. `Option<T>`: `Some(T)` or `None`. Rust has no `null`; `Option` forces explicit handling, preventing null pointer exceptions.

R14 — `impl` blocks define methods/associated functions for a type. `&self`: borrows instance (read-only). `&mut self`: mutates instance. `self`: takes ownership (consumes instance). Associated functions don't take `self` and act like constructors/static methods (e.g., `String::new()`).

R15 — `derive` macro auto-generates trait implementations. Common: `Debug` (fmt), `Clone`/`Copy` (duplication), `PartialEq` (equality), `Serialize` (serde). Cannot derive if the type contains non-derivable fields (e.g., `Fn` closures, raw pointers, or custom logic requiring specific behavior).

R16 — `Cow<'a, T>` (Clone on Write) holds either a borrowed `&'a T` or owned `T`. Useful when a function may return borrowed or owned data. Example: `fn process(s: &str) -> Cow<str> { if condition { Cow::Borrowed(s) } else { Cow::Owned(s.to_uppercase()) } }` avoids allocation when input already matches output format.

R17 — Module system: `mod` declares a module, `use` imports names, `pub` exposes. File system: `mod.rs` or `mod_name.rs` maps to a module. Rust 2018: `use` paths relative to crate root, `extern crate` removed, inline module declarations allowed. 2015: `use` relative to current module, required `extern crate`.

R18 — `Pin<T>` guarantees a pointer to `T` won't move in memory. Needed for self-referential structs and async/await (futures may hold references to their own fields). `Unpin` is a marker trait for types that can be safely moved. `Pin` enforces address immutability during `Future::poll`, preventing dangling self-references.

R19 — Macros: `macro_rules!` (declarative) uses pattern-matching on token trees, expands at compile time. Procedural macros: `derive` (struct/enum impl), `attribute` (custom `#[...]`), `function-like` (invoked like functions). Hygiene: declarative macros are hygienic by default (no identifier leakage/capture); procedural macros use explicit hygiene rules to control scope.

R20 — Zero-cost abstractions: high-level features compile to efficient machine code. Iterators are lazy and inlined to zero overhead. Generics use monomorphization (compile-time type-specific code generation). Trait static dispatch uses direct function calls (no vtable). Together, they achieve C-like performance while enabling safe, composable, expressive code.
