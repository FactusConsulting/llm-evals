SC1-A
The failure stems from the cluster's Pod Security Standards (PSS) enforcement shifting from `Baseline` to `Restricted`. `Restricted` PSS mandates that containers must run as a non-root user with an explicitly defined UID (`runAsUser: <non-zero>`), `runAsNonRoot: true`, and `allowPrivilegeEscalation: false`. The manifests only set `runAsNonRoot: true` without `runAsUser`. When the new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`, Kubernetes attempts to run the container as root, violating `Restricted`. The pods pass admission (if the policy was applied retroactively or via mutating webhook) but crash at runtime because the application expects root privileges or lacks proper UID/GID mapping, causing repeated exits and `CrashLoopBackOff`.

SC1-C
**Immediate Fix:** Update Dockerfiles to explicitly set `USER 1000` (or matching UID) and add `runAsUser: 1000` to pod/container securityContext.
**Manifest Changes:** Add `runAsUser`, `runAsGroup`, and `fsGroup` to `securityContext`; set `allowPrivilegeEscalation: false`.
**CI Gate:** Add a Kyverno policy or OPA rule that rejects deployments missing `runAsUser` when `runAsNonRoot: true` is present. Integrate `trivy` or `checkov` to scan images for root defaults and fail builds.
**Rollout:** Use a rolling update (`strategy: rollingUpdate`, `maxSurge: 25%`, `maxUnavailable: 0`) with strict readiness probes. Deploy to a staging namespace first, verify PSS compliance, then promote. No downtime if readiness gates traffic until containers pass health checks.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped from primary to replica with network-dependent latency. Promoting the replica cuts off the primary, discarding any WAL not yet received or replayed. The stale data issue occurs because application reads hit the replica before WAL catch-up completes, or because the promotion itself lost unshipped transactions. To quantify loss: check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica, and correlate with application commit timestamps. The loss window equals the replication lag at promotion time, typically seconds to minutes across regions.

SC2-B

2. `terraform state mv 'aws_db_instance.old_primary' 'aws_db_instance.promoted_replica'` (rename old state entry)
3. Update Terraform code: change `identifier`, `engine_version`, and `availability_zone` to match the promoted instance.
4. `terraform plan -target=aws_db_instance.promoted_replica` to verify no destroy/create.
5. `terraform apply -target=aws_db_instance.promoted_replica` to sync state.
6. Run `terraform plan` to ensure dependent resources (SGs, Route53) reference the new ARN without recreation.

SC2-C
**Connection Management:** Use RDS Proxy instead of PgBouncer. RDS Proxy handles connection pooling server-side, survives failover transparently, and reduces connection churn during promotion.
**DNS Failover:** Route53 failover routing with health checks on the RDS endpoint. Update app config to use the Route53 alias.
**Retry Logic:** Implement exponential backoff with jitter in the application driver.
**RPO < 1s:** Standard RDS cross-region cannot guarantee this. Recommend **Aurora Global Database**. It uses dedicated storage replication across regions with RPO < 1s and RTO < 1 min, automatic failover, and global data distribution. It eliminates async WAL shipping lag by replicating at the storage layer.

```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid,
       blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS current_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

SC6-C
**Direct Connect:** Dedicated 10Gbps/100Gbps link. Low latency, high cost. Requires BGP. Fits ZT if combined with IPsec overlay or TLS. Routing: BGP peering, static routes.
**Second VPN + ECMP:** Two IPsec tunnels, BGP ECMP. Scales bandwidth, same encryption, lower cost. Routing: Multiple tunnels, BGP multipath.
**Tailscale/Netbird:** WireGuard-based mesh. ZT-native, automatic routing, no IP planning. Lower bandwidth ceiling (~1-10Gbps), higher cost per GB. Routing: Overlay network, magic DNS.
**Recommendation:** Netbird/Tailscale for ZT alignment and simplicity. Direct Connect for raw bandwidth if cost allows. VPN ECMP is fallback. Mesh best fits zero-trust by design.

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks monitor site quorum. Site down = >3 consecutive failures + etcd partition.
2. **DNS Failover:** GSLB switches traffic to Dallas.
3. **Patroni Promote:** etcd triggers Dallas node promotion.
4. **Redis Sentinel:** Sentinel promotes Dallas master.
5. **RabbitMQ:** Federation/shovel catches up queues.
6. **MinIO:** Site replication syncs delta.
7. **Terraform State:** Update state to reflect new primary.
**Split-Brain:** Quorum-based DCS (etcd/Patroni) prevents dual promotion. STONITH fencing on failed nodes. Manual override if needed.
**Failback:** Reverse replication, sync data, verify integrity, DNS switch back to Chicago, update state, decommission Dallas as primary.
