## Kubernetes

**K1** — A **Deployment** manages stateless workloads: pods are interchangeable, have random names, and are replaced without preserving identity. A **StatefulSet** manages stateful workloads: pods have stable, unique network identities (e.g., `app-0`, `app-1`), ordered deployment/scaling, and stable storage bindings that persist across restarts.

**K2** — `kube-proxy` watches Service objects and creates iptables (or IPVS) rules mapping the Service's `ClusterIP:Port` to the backend Pod IPs. When traffic hits the ClusterIP, the kernel's netfilter redirects it to one of the healthy pod IPs using round-robin or least-connection load balancing.

**K3** — A **PersistentVolume (PV)** is a cluster-level storage resource. A **PersistentVolumeClaim (PVC)** is a pod's request for storage. A **StorageClass** defines a provisioning template (e.g., SSD, cloud disk). Relation: PVCs bind to existing PVs (static provisioning) or trigger a StorageClass to dynamically create a PV (dynamic provisioning).

**K4** — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` for exit codes, OOMKilled events, or probe failures. 3. Verify resource requests/limits and node capacity (OOMKilled if exceeding limits). 4. Check mounted ConfigMaps/Secrets, env vars, and entrypoint commands for missing files or syntax errors.

**K5** — CoreDNS provides internal DNS resolution for `Service` and `Pod` names. If CoreDNS pods are down, internal name resolution fails (services can't find each other by DNS), but external DNS (via host `/etc/resolv.conf`) and direct IP communication remain unaffected.

**K6** — The scheduler uses **filtering** (removes nodes failing requirements) then **scoring** (ranks remaining nodes). Filtering checks: resource capacity, taints/tolerations, node selectors, affinity/anti-affinity, and node conditions. Scoring factors: resource balance (prefer less loaded nodes), topology spread constraints, node affinity weights, and taint toleration costs.

**K7** — Yes, it will schedule: 3.5GB + 256Mi ≈ 3.75GB < 4GB node capacity. At runtime, using 600Mi exceeds the 512Mi limit. The cgroup enforces the limit, triggers an OOMKilled event, and the pod restarts (respecting `restartPolicy`).

**K8** — 1. Client hits External LB → routes to Ingress Controller IP. 2. Ingress Controller (NGINX) reads Ingress resource → matches `host`/`path` → forwards to Kubernetes Service. 3. Service resolves to Endpoints (pod IPs). 4. `kube-proxy`/iptables redirects traffic to the target pod IP. 5. Pod receives request.

**K9** — A `NetworkPolicy` restricts ingress/egress traffic to/from pods using label selectors. Default behavior (no policy): all traffic allowed. When applied: only traffic matching the policy's `ingress`/`egress` rules is permitted; all other traffic is implicitly denied.

**K10** — `RollingUpdate` gradually replaces old pods with new ones (zero downtime). `Recreate` terminates all old pods before starting new ones (downtime). Choose `Recreate` for stateful apps that cannot run two versions simultaneously, or when clean state/zero cross-version compatibility is required.

**K11** — A namespace is a logical cluster partition for resource isolation and multi-tenancy. Default namespaces: `default`, `kube-system`, `kube-public`.

**K12** — `kubectl describe pod` shows detailed runtime state. Unlike `get`, it displays: 1. Pod events (scheduling, pull, OOMKilled). 2. Node name & pod IP. 3. Container resource requests/limits, environment variables, volume mounts, and probe configurations.

**K13** — A `ConfigMap` stores non-confidential configuration data. Pods consume it via: 1. Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`). 2. Volume mounts (files injected into the container filesystem).

**K14** — `ClusterIP`: internal-only virtual IP. `NodePort`: exposes the service on a static port on each node's IP. `LoadBalancer`: provisions a cloud provider LB, exposing the service externally with a public IP.

**K15** — A `DaemonSet` ensures one pod runs on every node (or subset via taints/tolerations). Use it for node-level agents (logging, monitoring, metrics collection) instead of a Deployment, which would require manual pod placement or scaling.

**K16** — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Taints/tolerations are node-driven (repel/attract), while affinity is pod-driven (preference). Use case taints: GPU nodes tainted to block general workloads. Use case affinity: schedule ML workloads on nodes with NVMe storage.

**K17** — An Operator is a custom controller that manages complex applications using Custom Resource Definitions (CRDs). Unlike a standard controller (which watches built-in resources), an Operator encodes operational knowledge (scaling, backups, upgrades) into code. It solves manual intervention for stateful/complex services by automating lifecycle management.

**K18** — etcd uses a **linearizable** consistency model via Raft consensus. If quorum is lost, the cluster becomes read-only (existing state readable, but no writes/updates allowed). Recovery from 2/3 permanent loss: restore from the last known-good snapshot (`etcdctl snapshot restore`), add new nodes, and rejoin them to the cluster.

**K19** — `Role`/`ClusterRole` define permissions (rules). `RoleBinding`/`ClusterRoleBinding` bind roles to users/groups/serviceaccounts. Manifest for read-only pods/logs in one namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — Default `ndots:5` in `/etc/resolv.conf` makes the resolver try 5 suffixes (`svc.cluster.local`, `cluster.local`, etc.) before falling back to upstream DNS. This causes excessive queries for external domains. Fix: add `dnsConfig: options: [{name: "ndots", value: "1"}]` to the pod spec to reduce suffix attempts.

## Development

**D1** — `merge` creates a merge commit, preserving full branch history. `rebase` rewrites commits onto the target branch, creating a linear history. Avoid rebasing on shared/public branches or after pushing to remote, as it rewrites history and causes conflicts for collaborators.

**D2** — **TCP**: connection-oriented, reliable, ordered delivery. **UDP**: connectionless, unreliable, low-latency. TCP examples: HTTP, FTP. UDP examples: DNS, VoIP/RTSP.

**D3** — A race condition occurs when concurrent threads/processes access shared state without synchronization, leading to unpredictable results. Example: two threads incrementing a shared counter without a mutex, resulting in lost updates.

**D4** — **Symmetric**: single key for encryption/decryption (fast). **Asymmetric**: public/private key pair (secure key exchange). TLS uses asymmetric encryption during the handshake to securely exchange a session key, then switches to symmetric encryption for bulk data transfer.

**D5** — Each Dockerfile instruction creates an immutable image layer. Layer caching speeds up rebuilds by reusing unchanged layers. Best practice: order instructions from least to most frequently changing, combine `RUN` commands, and use `.dockerignore` to avoid unnecessary context.

**D6** — Order of checks: 1. App logs/metrics for error traces or timeouts. 2. Upstream dependencies (DB, cache, third-party APIs). 3. Resource limits/OOMKilled events. 4. Load balancer/proxy config (connection pool exhaustion, rate limits, health check failures).

**D7** — CAP theorem: a distributed system can only guarantee two of three: Consistency, Availability, Partition tolerance. **CP**: banking ledger (strong consistency, may block during network partition). **AP**: DNS or social media feeds (high availability, eventual consistency).

**D8** — **Horizontal**: add more nodes/instances. **Vertical**: increase CPU/RAM of existing node. Horizontal scaling requires: stateless services, distributed databases, message queues, container orchestration, and externalized sessions/state.

**D9** — An environment variable is a dynamic value that influences process behavior. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

**D10** — **JSON**: strict key-value syntax, no comments. **YAML**: indentation-based, supports comments, human-readable. JSON advantage: strict parsing, universal language support. YAML advantage: readability, less boilerplate, better for config files.

**D11** — A REST API is an architectural style using HTTP methods to interact with resources. `GET`: retrieve. `POST`: create. `PUT`: replace/update. `DELETE`: remove.

**D12** — Version pinning locks dependencies to exact versions (e.g., `package@1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes, and guarantees consistency across environments and CI/CD pipelines.

**D13** — **Compiled**: source code is translated to machine code before execution (C++, Rust). **Interpreted**: source code is executed line-by-line at runtime (Python, JavaScript). (Note: modern languages often use JIT compilation, but the distinction remains in build/runtime model.)

**D14** — A **reverse proxy** sits in front of servers, routing client requests to backend services. A **forward proxy** sits in front of clients, routing outbound requests. Reverse proxy use cases: Nginx (load balancing/SSL termination), HAProxy (high-performance TCP/HTTP routing).

**D15** — A deadlock occurs when two or more processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait. All must hold simultaneously.

**D16** — Eventual consistency guarantees that if no new updates occur, all replicas will eventually converge. Cassandra uses tunable consistency levels: `ONE`, `QUORUM`, `ALL`, `LOCAL`, `EACH_QUORUM`, `SERIAL`. For read-after-write consistency, use `SERIAL` or `QUORUM` with client-side session tracking.

**D17** — mTLS requires both client and server to present valid certificates. Handshake: ClientHello → ServerHello → cert exchange → mutual verification → key exchange → encrypted channel. Commonly used in: service meshes (Istio/Linkerd), internal microservices, and zero-trust architectures.

**D18** — A hash table maps keys to values via a hash function. Collision resolution: **chaining** (linked lists per bucket) or **open addressing** (probing for next empty slot). Time complexity: average O(1) for insert/lookup/delete. Worst case O(n) if all keys hash to the same bucket.

**D19** — A circuit breaker prevents cascade failures by stopping calls to a failing service. States: **closed** (normal), **open** (failure threshold reached, fail fast), **half-open** (tests with limited requests). Relates to retry/backoff: circuit breaker caps retries; exponential backoff reduces load during recovery, preventing thundering herd.

**D20** — **Optimistic**: assumes no conflict, validates at commit (e.g., row versioning, `UPDATE ... WHERE version = ?`). **Pessimistic**: locks resources during transaction (e.g., `SELECT ... FOR UPDATE`). Choose optimistic for high-read/low-conflict workloads; pessimistic for high-conflict/critical data. Example: optimistic uses a `version` column; pessimistic uses explicit row locks.
