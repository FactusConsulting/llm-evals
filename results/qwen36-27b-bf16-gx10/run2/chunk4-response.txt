G1 — Arrays have fixed size and are value types. Slices are dynamic views over arrays, consisting of a pointer, length, and capacity. When `append` exceeds capacity, Go allocates a new underlying array (typically doubling capacity for small slices, scaling logarithmically for large ones), copies existing elements, and updates the slice header. This amortizes to O(1) per append.

G2 — `var x int` declares a package- or block-level variable initialized to the zero value (`0`). `x := 0` is a short variable declaration that infers the type and requires initialization. You cannot use `:=` at package scope, when redeclaring a variable without introducing a new one, or when you need to explicitly declare a type without an initializer.

G3 — A goroutine is a lightweight, user-space thread managed by the Go runtime. Unlike OS threads (1–8MB stack, 1:1 kernel mapping), goroutines start with ~2KB stacks that grow/shrink dynamically and use M:N scheduling. The GMP model: G=goroutine, M=OS thread, P=logical processor. The scheduler binds Gs to Ps, Ps run on Ms, and handles preemption, syscall parking, and work-stealing to maximize CPU utilization.

G4 — Channels are typed conduits for safe goroutine communication. Unbuffered channels block until both sender and receiver are ready (synchronous). Buffered channels hold N values; sends block only when full, receives block only when empty. Sending to a full buffered channel blocks the sender until a receiver frees a slot.

G5 — `context` carries deadlines, cancellation signals, and request-scoped values across API boundaries. Minimal example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, http.MethodGet, "https://example.com", nil)
resp, err := http.DefaultClient.Do(req)
```

G6 — Go uses implicit/structural interface satisfaction: a type implements an interface if it defines all its methods, with no explicit declaration. Java/C# require explicit `implements`. `interface{}` (now `any`) matches any type. It's powerful for generic-like behavior but dangerous because it defers type checking to runtime via type assertions/switches, losing compile-time safety and requiring error handling.

G7 — Go's memory model guarantees visibility only when synchronization establishes a happens-before relationship. The code is unsafe because `ready` and `data` writes may be reordered by the compiler/CPU and cached, so the main goroutine may see `ready=true` but stale `data`. Alternatives: use a channel (`ch <- data`), `sync/atomic` (`atomic.StoreInt32(&ready, 1)`), or `sync.Mutex`.

G8 — `sync.Mutex` allows exclusive access. `sync.RWMutex` allows multiple concurrent readers or one exclusive writer. `sync.Map` is optimized for concurrent read-heavy workloads with mostly distinct key sets per goroutine. Regular map + mutex is better for mixed workloads or heavy key overlap. Trade-offs: `sync.Map` avoids read lock contention but has higher write/delete overhead, lacks `len()`, and doesn't support arbitrary key types without boxing.

G9 — Go modules manage dependencies. `go.mod` declares the module path, Go version, and direct dependencies. `go.sum` stores cryptographic hashes of all resolved dependencies for reproducibility. `go mod tidy` adds missing and removes unused dependencies. MVS (Minimum Version Selection) picks the lowest version of each dependency that satisfies all requirements, guaranteeing a single, deterministic dependency tree without version conflicts.

G10 — `defer` schedules a function call to run after the surrounding function returns. Multiple defers execute in LIFO order. Common loop gotcha: deferred closures capture loop variables by reference, so they all see the final iteration value. Fix: pass the loop variable as an argument to the deferred function (`defer func(i int){...}(i)`).

G11 — A pointer holds the memory address of another variable. Its zero value is `nil`. Create a pointer to a struct literal with `&Struct{Name: "val"}`.

G12 — `init()` is a special function with no parameters or return values. It runs automatically after package-level variables are initialized and before `main()`. A package can have multiple `init()` functions; their execution order within the package is unspecified (but deterministic per run). Across packages, they execute in import dependency order.

G13 — `make` initializes and returns slices, maps, and channels with internal structures ready for use. `new` allocates zeroed memory for any type and returns a pointer to it (`*T`). `make` works with reference-like composite types; `new` works with everything but returns a pointer to the zero value.

G14 — Errors are values implementing `error` (`Error() string`). Idiomatic pattern: `if err != nil { return err }`. `errors.Is` checks if an error matches a target (supports wrapping). `errors.As` unwraps to find a specific error type. `==` only checks pointer equality and fails with wrapped errors.

G15 — Built-in composite types: `map[K]V`, `[]T`, `chan T`, `struct{}`. Zero values: `nil` for map, slice, and channel. Struct zero value is a struct with all fields at their respective zero values.

G16 — A race condition occurs when concurrent goroutines access shared memory without synchronization, with at least one write. The `-race` flag instruments the binary to detect data races at runtime using vector clocks/lockset tracking. Example: concurrent map writes. Fix: protect with `sync.Mutex` or serialize access via a channel.

G17 — `select` waits on multiple channel operations. Unlike `switch`, it evaluates channel readiness, not expressions. If multiple cases are ready, one is chosen pseudo-randomly. Timeout: `select { case <-ch: ... case <-time.After(5 * time.Second): ... }`.

G18 — Escape analysis determines if a variable's lifetime exceeds the function scope. If yes, it's allocated on the heap; otherwise, on the stack. Inspect with `go build -gcflags="-m"`. It matters because heap allocations trigger GC, while stack allocations are cheap. Avoiding escapes reduces GC pressure and improves latency.

G19 — `reflect` inspects/modifies types and values at runtime. `reflect.Type` holds static type info; `reflect.Value` holds the actual value and allows reading/writing. Costs: dynamic dispatch, type checks, heap allocation, breaks inlining. Justified for serialization, frameworks, or plugins. Prefer code generation (`go generate`) for performance-critical paths.

R20 — `go:embed` embeds files into the binary at compile time. Works for single files (`//go:embed file.txt`), directories (`//go:embed dir`), and file systems (`//go:embed dir/*` into `embed.FS`). Limitations: only targets `string`, `[]byte`, or `embed.FS`. Interacts with `io/fs.FS` to provide standard file operations on embedded content without disk I/O.

R1 — Ownership is Rust's memory management system. Rules: 1. Each value has exactly one variable (owner). 2. Only one owner exists at a time. 3. When the owner goes out of scope, the value is dropped (memory freed).

R2 — `String` is an owned, growable, heap-allocated UTF-8 string. `&str` is an immutable borrowed string slice pointing to UTF-8 data (literals or parts of a `String`). Use `&str` in function signatures for flexibility (accepts both); use `String` when you need ownership, mutation, or to return newly allocated data.

R3 — Borrowing allows temporary references to data without taking ownership. Rules: either multiple `&T` (shared) OR one `&mut T` (mutable), never both simultaneously. The borrow checker enforces this at compile time to prevent data races and dangling pointers.

R4 — `Result<T, E>` represents success/failure with values. `Option<T>` represents a value or absence. `?` unwraps `Ok`/`Some` or propagates `Err`/`None` up. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```

R5 — `Box<T>`: heap allocation, single ownership. `Rc<T>`: reference counting, single-threaded shared ownership. `Arc<T>`: atomic reference counting, thread-safe shared ownership. Use `Box` for recursive types/trait objects, `Rc` for shared data in one thread, `Arc` for concurrent sharing.

R6 — Traits define shared behavior. Similar to Go interfaces but support generics, associated types, and default implementations. `dyn Trait`: dynamic dispatch, fat pointer (data + vtable), runtime cost. `T: Trait`: static dispatch, monomorphization, compile-time cost, usually faster.

R7 — Lifetimes annotate reference validity scopes. The code fails because the compiler can't infer which input lifetime the output should match. Fix:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

R8 — `Send`: type can be transferred across threads. `Sync`: type can be shared across threads (`&T` is `Send`). `Rc<T>` isn't `Send`/`Sync` because its ref counting uses non-atomic operations. `Arc<T>` uses atomic operations, making it safe for concurrent use.

R9 — Async/await uses cooperative multitasking. A `Future` is a lazy state machine representing async computation, polled by an executor. Executors (e.g., Tokio) manage I/O, schedule tasks on threads, and drive futures to completion. Differs from Go: Go uses preemptive M:N scheduling with eager goroutines and a built-in runtime; Rust uses explicit async runtimes, lazy futures, and no scheduler in stdlib.

R10 — `unsafe` opts out of safety guarantees. Three things: dereference raw pointers, call unsafe functions, access `mut static` variables. Justified for FFI, low-level optimizations, OS/hardware interaction, or when invariants are manually proven and encapsulated.

R11 — Pattern matching matches values against structural patterns. `match` requires exhaustive coverage (compiler enforces `_` or all variants). `if let` matches one pattern and ignores others, useful for optional/single-variant checks.

R12 — `Vec<T>`: growable, heap-allocated array. `[T; N]`: fixed-size, stack-allocated array. When `push` exceeds capacity, `Vec` allocates a new larger buffer (typically 2x), moves elements, and drops the old buffer.

R13 — Enums are algebraic data types; each variant can hold different data. Unlike C/Java enums (just integers), Rust enums carry payloads. `Option<T>` has `Some(T)` and `None`, replacing null to force explicit absence handling and eliminate null pointer exceptions.

R14 — `impl` defines methods/associated items for a type. `&self`: immutable borrow (read-only). `&mut self`: mutable borrow (can modify). `self`: takes ownership (consumes). Associated functions don't take `self`, called on the type itself (e.g., constructors).

R15 — `#[derive(...)]` auto-implements traits via procedural macros. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive if fields don't implement the trait, or if custom logic is required (e.g., `Hash` with custom equality, or traits requiring manual invariants).

R16 — `Cow<'a, T>` (Clone on Write) borrows data if unmodified, clones on first mutation. Useful when processing data that may or may not change. Avoids unnecessary allocations when most inputs are borrowed and left untouched.

R17 — `mod` declares a module, `use` imports names, `pub` controls visibility. `mod foo;` maps to `foo.rs` or `foo/mod.rs`. Rust 2018 simplified paths, removed `extern crate`, made `mod.rs` optional, and improved relative/absolute path resolution.

R18 — `Pin<T>` prevents memory movement after pinning. Required for self-referential structs (pointers to own fields) and async state machines (which hold references to internal buffers). `Unpin` is a marker trait for types that don't require pinning (most types).

R19 — Macros generate code at compile time. Declarative (`macro_rules!`): pattern-based, hygienic (identifiers don't clash), limited to expressions/items. Procedural: functions generating code, used for `derive`, `attr`, `func-like`. Proc macros are unhygienic but use `syn`/`quote` to manage scope. Hygiene prevents macro-generated names from conflicting with user code.

R20 — Zero-cost abstractions compile to efficient machine code with no runtime overhead. Iterators inline to tight loops. Generics use monomorphization (type-specific code per instantiation). Trait static dispatch resolves at compile time. Achieves C-like performance while providing memory safety, type checking, and high-level ergonomics.
