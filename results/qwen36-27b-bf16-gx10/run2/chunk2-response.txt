K1 — Deployments manage stateless, interchangeable pods with random names and shared storage, ideal for web servers. StatefulSets manage stateful workloads, providing stable network identities (pod names), ordered deployment/scaling, and dedicated persistent storage per pod, ideal for databases.

K2 — A ClusterIP Service creates a virtual IP within the cluster. `kube-proxy` watches the Service and its Endpoints, then programs `iptables` or `IPVS` rules on each node to intercept traffic destined for the ClusterIP and NAT/route it to a healthy pod IP in the Endpoints list.

K3 — A PersistentVolume (PV) is a cluster-level storage resource. A PersistentVolumeClaim (PVC) is a user/pod request for storage. A StorageClass defines dynamic provisioning parameters. Relation: A PVC either binds to an existing PV (static) or triggers a StorageClass to dynamically create a matching PV. Pods mount the PVC.

K4 — 1. `kubectl logs <pod>` to check application errors or panics. 2. `kubectl describe pod <pod>` to inspect Events, probe failures, and OOMKilled status. 3. Verify resource requests/limits vs actual usage (CPU throttling or memory limits). 4. Check mounted volumes, secrets, and configmaps for missing paths or permission errors. 5. Validate external dependencies (DB connectivity, DNS, network policies).

K5 — CoreDNS provides internal DNS resolution for services and pods, translating `<service>.<namespace>.svc.cluster.local` to ClusterIPs, and forwards external queries to upstream DNS. If CoreDNS pods are down, internal service discovery fails, and external DNS resolution fails unless pods have fallback resolvers configured.

K6 — The scheduler runs in two phases: Filtering (predicates) removes nodes that violate constraints (resource requests, taints/tolerations, node/pod affinity, volume node affinity, port conflicts). Scoring (priorities) ranks remaining nodes using weighted factors. Key factors: least requested resources, balanced resource allocation, image locality, inter-pod affinity, and topology spread constraints.

K7 — Yes, it will be scheduled. The node has 4GB total, 3.5GB requested, leaving 512Mi available. The pod requests 256Mi, so 3.5GB + 256Mi = 3.75GB ≤ 4GB. At runtime, if it uses 600Mi, it exceeds its 512Mi limit. The cgroup enforces the limit, the kernel triggers an OOM kill, and the pod restarts (likely entering CrashLoopBackOff if it repeatedly exceeds the limit).

K8 — Client → External Cloud LB (terminates TLS, forwards to ingress controller IPs) → NGINX Ingress Controller pod (matches host/path rules, applies rewrite/headers) → ClusterIP Service → `kube-proxy` (iptables/IPVS rules) → Endpoints (healthy pod IPs) → Target application pod. The path relies on service discovery, L4/L7 routing, and pod network plugins for cross-node routing.

K9 — A NetworkPolicy is a L3/L4 firewall that controls pod-to-pod and pod-to-external traffic using labels. Default behavior (no policies): all ingress and egress traffic is allowed. When a policy is applied to a namespace, it becomes restrictive: only explicitly allowed traffic is permitted; all other traffic matching the policy selector is dropped.

K10 — RollingUpdate gradually replaces old pods with new ones, maintaining availability via `maxSurge` and `maxUnavailable`. Recreate terminates all old pods before creating new ones, causing downtime. Choose Recreate for database schema migrations, config changes requiring full restart, or when old/new versions cannot coexist or share state.

K11 — A namespace is a logical partition for isolating resources, RBAC, and network policies. Default namespaces: `default` (user workloads), `kube-system` (cluster components), `kube-public` (publicly readable resources), `kube-node-lease` (node heartbeat/lease objects).

K12 — `kubectl describe pod` shows detailed diagnostic data. Three pieces not in `get`: 1. Events (scheduling, image pull, probe failures). 2. Volume mounts and environment variables. 3. Conditions, QoS class, and exact resource requests/limits. Also shows node assignment and container state history.

K13 — A ConfigMap stores non-confidential configuration data as key-value pairs. Consumption methods: 1. Environment variables (`env` or `envFrom`). 2. Volume mount (exposes keys as files in the container filesystem). 3. Command/argument substitution in the container spec.

K14 — ClusterIP: exposes service internally via a virtual IP (default). NodePort: exposes service on a static port across all node IPs, allowing external access via `<NodeIP>:<NodePort>`. LoadBalancer: provisions a cloud provider external LB that forwards traffic to the NodePort/ClusterIP, providing a stable external IP.

K15 — A DaemonSet ensures exactly one pod runs on each node (or a subset via node selectors). Use instead of a Deployment when you need node-level agents: log collectors (Fluentd), monitoring exporters (Node Exporter), network plugins (Calico), or storage drivers.

K16 — Taints/Tolerations repel pods: a node taint says "only pods with this toleration may run here." Node Affinity attracts pods: a pod says "I prefer/require nodes with these labels." Use case: Taints for dedicated GPU/debug nodes. Affinity for spreading pods across availability zones or pinning to specific hardware generations.

K17 — An Operator extends Kubernetes with Custom Resource Definitions (CRDs) and a custom controller that encapsulates domain-specific operational logic. Unlike standard controllers (which manage built-in resources), Operators automate complex, stateful application lifecycles (backups, upgrades, scaling, failover). Solves: operational knowledge silos, manual toil, and inconsistent state management.

K18 — etcd uses the Raft consensus algorithm for strong linearizable consistency. If quorum is lost, the cluster becomes unavailable for writes and may lose the leader, halting all API operations. Recovery from 2/3 lost: You cannot recover without a backup. Restore the latest `etcdctl snapshot` on a fresh single-node etcd, reinitialize the cluster, then scale back to 3 nodes and rejoin.

K19 — RBAC authorizes requests via Roles/ClusterRoles (define verbs/resources) and RoleBindings/ClusterRoleBindings (bind roles to users/groups/service accounts in a namespace or cluster-wide). Manifest for dev read-only access:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: name: dev-pod-reader namespace: dev
subjects: [{kind: User, name: dev-user, apiGroup: rbac.authorization.k8s.io}]
roleRef: {kind: Role, name: dev-pod-reader, apiGroup: rbac.authorization.k8s.io}
```

D1 — `git merge` creates a new merge commit preserving branch history. `git rebase` rewrites history by replaying commits on top of the target branch, creating a linear history. Avoid rebasing on shared/public branches because it rewrites commit hashes, causing conflicts and history divergence for collaborators.

D2 — TCP is connection-oriented, reliable, ordered, with flow/congestion control (HTTP, SSH, FTP). UDP is connectionless, unreliable, unordered, with minimal overhead (DNS, VoIP, live streaming). TCP guarantees delivery; UDP prioritizes speed and low latency.

D3 — A race condition occurs when concurrent processes/threads access shared state without synchronization, and the outcome depends on execution timing. Example (Python): Two threads increment a shared counter `x += 1` without a lock. Both read `x=5`, both write `6`, losing one increment.

D4 — Symmetric encryption uses one shared key for encryption/decryption (fast, e.g., AES). Asymmetric uses a public/private key pair (slower, enables key exchange/signatures, e.g., RSA/ECC). In TLS: asymmetric keys authenticate the server (and optionally client) and negotiate a symmetric session key, which then encrypts the actual data transfer for performance.

D5 — A container image layer is a read-only filesystem delta. Docker caches layers based on instruction content and context. Best practices: order instructions from least to most frequently changing, combine `RUN` commands to reduce layers, use `.dockerignore`, and leverage multi-stage builds to keep final images small and cache-friendly.

D6 — Order of checks: 1. Application logs & metrics (errors, OOM, thread exhaustion). 2. Upstream dependencies (DB connections, cache, external APIs). 3. Load balancer/ingress health checks, rate limits, and connection pooling. 4. Recent deployments, config changes, or resource limit adjustments. 5. Network/DNS latency or certificate expiration.

D7 — CAP theorem states a distributed system can only guarantee two of three: Consistency, Availability, Partition tolerance. CP example: etcd/Zookeeper (strong consistency, may become unavailable during network partitions). AP example: Cassandra/DynamoDB (always available, may return stale data during partitions, converges later).

D8 — Vertical scaling adds CPU/RAM to existing nodes; horizontal scaling adds more nodes/instances. Horizontal scaling is enabled by: stateless application design, load balancers, distributed databases/caches, message queues for async processing, and container orchestration for auto-scaling.

D9 — An environment variable is a dynamic key-value pair in a process's execution environment. To persist across Linux shell sessions, export it in `~/.bashrc` or `~/.profile` (e.g., `export MY_VAR=value`), then run `source ~/.bashrc` or open a new terminal.

D10 — JSON is a strict, machine-parsable data interchange format with no comments. YAML is a human-readable superset of JSON supporting comments, multi-document streams, and complex types. JSON advantage: strict parsing, universal language support. YAML advantage: readability, comments, anchors/aliases for DRY configs.

D11 — REST is an architectural style using HTTP for stateless client-server communication. GET: retrieve resources (safe, idempotent). POST: create new resources (not idempotent). PUT: fully replace/update a resource (idempotent). DELETE: remove a resource (idempotent).

D12 — Version pinning locks dependencies to exact versions (e.g., `==1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes from upstream updates, and guarantees identical environments across development, staging, and production.

D13 — Compiled languages translate source code to machine code before execution (C, Rust). Interpreted languages execute code line-by-line via a runtime interpreter (Python, JavaScript). Compiled typically offers better performance; interpreted offers faster iteration and cross-platform portability.

D14 — A reverse proxy sits in front of backend servers, forwarding client requests to them (NGINX, HAProxy). Use cases: load balancing, TLS termination, caching, WAF. A forward proxy sits in front of clients, forwarding their requests to the internet (Squid, corporate proxies). Use cases: anonymity, content filtering, caching outbound traffic.

D15 — A deadlock occurs when two or more processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion (resources non-shareable). 2. Hold and wait (process holds one resource while waiting for another). 3. No preemption (resources cannot be forcibly taken). 4. Circular wait (cycle of waiting processes).

D16 — Eventual consistency guarantees that if no new updates occur, all replicas will converge to the same value over time. Cassandra handles read-after-write via tunable consistency levels (ANY, ONE, QUORUM, ALL, LOCAL_QUORUM, EACH_QUORUM). Using QUORUM for both reads and writes guarantees read-after-write consistency. Read-repair and anti-entropy background processes eventually sync stale replicas.

D17 — mTLS requires both client and server to present and verify X.509 certificates. Handshake: ClientHello → ServerHello + ServerCert → Client verifies server cert → ClientCert → Server verifies client cert → Key exchange → Encrypted channel. Commonly used in service meshes (Istio), internal microservices, zero-trust architectures, and secure API gateways.

D18 — A hash table uses an array and a hash function to map keys to indices. Collisions are resolved via chaining (linked list/tree at each index) or open addressing (probing next slots: linear/quadratic). Average time complexity: O(1) for insert, lookup, delete. Worst case: O(n) when all keys hash to the same index (poor hash function or high load factor).

D19 — A circuit breaker prevents cascade failures by stopping calls to a failing service. States: Closed (normal, tracks failure rate), Open (fails fast, blocks calls, waits timeout), Half-Open (allows limited test requests; success → Closed, failure → Open). Relates to retry/backoff: retries are disabled in Open state; exponential backoff prevents thundering herds when transitioning to Half-Open or retrying in Closed state.

D20 — Pessimistic concurrency assumes conflicts are likely and locks data on read/write (`SELECT FOR UPDATE`). Optimistic assumes conflicts are rare, uses no locks, and validates version/timestamp on commit (row versioning). Choose pessimistic for high-contention critical data (bank transfers). Choose optimistic for low-contention, read-heavy workloads (e-commerce carts, content updates).
