### Application Architecture

**AA1** — A monolith is a single deployable unit where all components share memory, processes, and a database. Microservices split functionality into independently deployable services with isolated data stores. Microservices introduce: (1) Distributed transaction complexity (no ACID across services), (2) Network latency and failure handling (every call can fail), (3) Operational overhead (deployment pipelines, service discovery, distributed tracing, and config management multiply per service).

**AA2** — Synchronous communication is request-response; the caller blocks until a reply arrives. Example: REST/gRPC. Asynchronous communication is decoupled; the sender dispatches a message and continues, while the receiver processes it later. Example: RabbitMQ/Kafka. Sync is simpler for low-latency interactions; async improves resilience and throughput for non-critical or batch workflows.

**AA3** — A reverse proxy operates at L7 to route traffic, terminate SSL, cache, and load balance. An API Gateway adds API-specific logic: authentication, rate limiting, versioning, request/response transformation, and developer portal features. An API Gateway *can* replace a reverse proxy functionally, but in practice they're layered: the gateway handles API policy, while a lightweight reverse proxy (e.g., Nginx/HAProxy) handles raw traffic, SSL termination, and static assets to avoid gateway overhead on non-API traffic.

**AA4** — The Saga pattern manages distributed transactions as a sequence of local transactions, each with a compensating action to undo changes on failure. *Choreography*: services publish events that trigger the next step; no central coordinator. *Orchestration*: a central workflow engine directs steps and handles failures. Use choreography for simple, highly decoupled flows. Use orchestration for complex, long-running processes requiring visibility, error handling, and human-in-the-loop steps.

**AA5** — CQRS separates read (query) and write (command) models, allowing independent optimization and scaling. It's paired with Event Sourcing because events naturally feed read projections. This combination solves: (1) Read/write contention in CRUD, (2) Inability to scale reads/writes independently, (3) Lack of auditability/temporal queries, (4) Complex domain logic tangled with read optimizations.

**AA6** — The Circuit Breaker prevents cascading failures by stopping requests to a failing dependency after a threshold. States: *Closed* (normal), *Open* (fail fast, no requests), *Half-Open* (test recovery with limited requests). Unlike retry+backoff (which keeps trying), the CB halts traffic during prolonged outages. Use together: retry with exponential backoff for transient errors within the closed state; the CB prevents retry storms and resource exhaustion when the dependency is truly down.

**AA7** — 
1. *Shared DB/Schema*: Lowest cost, simplest ops, highest noisy-neighbor risk, requires row-level security. Best for low-security, high-volume SaaS.
2. *Shared DB/Separate Schema*: Moderate cost, better isolation, schema migrations per tenant, moderate noisy-neighbor. Good for mid-tier SaaS needing some isolation.
3. *Separate DB*: Highest cost, best security/isolation, complex ops (provisioning, backups, scaling), lowest noisy-neighbor. Required for regulated/enterprise tenants or strict compliance.

**AA8** — *Strong consistency*: all nodes see the same data at the same time. *Eventual consistency*: nodes converge over time. To prevent overselling, you need strong/linearizable consistency. Architecture: partition inventory by SKU, use a strongly consistent datastore (e.g., CockroachDB, Spanner, or Redis with Lua/atomic ops), and implement atomic compare-and-swap (CAS) or optimistic locking with retries. At scale, use a reservation queue: decrement stock atomically, publish reservation event, confirm on payment, release on timeout.

**AA9** — A sidecar proxy is a lightweight network proxy deployed alongside each app container. In Istio, Envoy acts as the sidecar. *Data plane*: Envoy sidecars forwarding traffic, enforcing policies, collecting metrics. *Control plane*: Istiod distributing configs, certificates, and service discovery. mTLS via sidecars solves: transparent encryption without app code changes, dynamic cert rotation, zero-trust network enforcement, and consistent policy application across polyglot services, unlike app-level TLS which requires manual per-service configuration and key management.

**AA10** — The Strangler Fig pattern incrementally replaces a monolith by routing traffic to new services. Strategy: (1) Deploy an API Gateway in front of the .NET Framework monolith. (2) Identify bounded contexts (e.g., User Auth, Orders). (3) Build .NET 8 microservices for each context. (4) Configure gateway routes to forward specific paths to new services while keeping others on the monolith. (5) Migrate data incrementally via dual-write or CDC. (6) Decommission monolith routes until fully replaced.

**AA11** — 12-Factor App methodology for cloud-native apps. Six factors: (1) *Codebase*: one repo, many deploys (enables CI/CD). (2) *Dependencies*: explicitly declare/isolate (prevents env drift). (3) *Config*: store in env vars (secrets/config separation). (4) *Backing services*: treat as attached resources (swappable DBs/queues). (5) *Build/Release/Run*: strict separation (immutable artifacts). (6) *Processes*: stateless, concurrent scaling (enables horizontal scaling). These ensure portability, elasticity, and automated deployments.

**AA12** — *Event-driven (Kafka)*: loose coupling, high scalability (async buffering), complex debugging (async traces), partition-level ordering, requires idempotency/retries for failures. *Request-driven (REST/gRPC)*: tight coupling, limited by sync throughput, straightforward debugging, per-request ordering, needs circuit breakers/retries. Choose ED for high-throughput, decoupled, async workflows (analytics, event processing). Choose RD for simple, low-latency, request-response interactions (user-facing APIs, CRUD).

**AA13** — A load balancer distributes incoming traffic across multiple backends. *Layer 4*: operates at transport layer (IP/Port), fast, no content inspection. *Layer 7*: operates at application layer (HTTP/HTTPS), inspects headers/cookies/paths, enables SSL termination, path-based routing, WAF integration. L7 is required for microservices routing by path/header, API versioning, or content-aware load balancing.

**AA14** — A message queue decouples producers/consumers via async messaging. *Queue (RabbitMQ)*: work distribution, at-most/least-once delivery, routing via exchanges, message removed after consumption. *Log-based (Kafka)*: append-only log, retention, replayability, high throughput, partition-based ordering. Pick queue for task distribution/workflows. Pick log for event streaming, analytics, replay, high-volume data pipelines, or multiple independent consumers.

**AA15** — A container packages an app and its dependencies, sharing the host OS kernel. A VM includes a full guest OS and runs on a hypervisor. Containers are lighter, start faster, and use fewer resources. Popular for microservices due to: consistent environments, high density, portability, and native orchestration support (Kubernetes).

**AA16** — *Stateless*: no client data stored between requests; any instance handles any request. Scales easily via horizontal scaling. Example: web server, API. *Stateful*: maintains state (DB, cache, session); requires sticky sessions or distributed state management. Harder to scale. Example: PostgreSQL, Redis.

**AA17** — An ORM maps objects to database tables. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs accelerate development, provide abstraction, and improve portability, but can cause N+1 queries, performance overhead, and obscure complex SQL. Raw SQL offers full control, optimization, and predictability, but is verbose, error-prone, and less portable.

**AA18** — The Bulkhead pattern isolates resources to prevent cascade failure. In microservices, it limits blast radius by partitioning threads, connections, or deployments. Implementation: assign separate thread pools/connection pools per dependency (e.g., 10 threads for payment API, 20 for inventory DB). If payment fails, inventory remains unaffected. In K8s, use separate deployment groups with resource quotas and pod disruption budgets.

**AA19** — *OT*: transforms operations centrally, requires server coordination, low latency online, complex offline support, strong consistency. *CRDTs*: mathematically conflict-free, decentralized, supports offline, eventual consistency, higher implementation complexity, larger state sync. For offline editing: choose CRDTs (e.g., Yjs, Automerge). They guarantee convergence without a central server, handle concurrent edits seamlessly offline, and sync efficiently when reconnected.

**AA20** — Challenges: context propagation requires consistent header mapping (W3C Trace Context/B3) across polyglot SDKs. Sampling: head-based drops early (saves cost, misses errors), tail-based collects all then filters (higher cost, better visibility). Storage/query: Jaeger (Elasticsearch), Tempo (object storage, fast). Async messaging breaks trace context. Kafka continuity: inject trace ID/span ID into message headers; consumer extracts and continues the span. Ensure all SDKs support standard propagation and test header passthrough in integration tests.

### On-Premise Infrastructure Architecture

**OP1** — *Type 1 (bare-metal)*: runs directly on hardware, higher performance, used in production. Examples: VMware ESXi, Proxmox VE, Microsoft Hyper-V. *Type 2 (hosted)*: runs as an application on a host OS, lower performance, used for dev/testing. Examples: VirtualBox, VMware Workstation.

**OP2** — *SAN*: block-level storage, high performance, low latency, uses Fibre Channel or iSCSI. Best for databases, VMs, high-I/O workloads. *NAS*: file-level storage, network-attached, uses NFS or SMB/CIFS. Best for file shares, backups, media, collaboration. Use SAN when apps need raw block access; use NAS for shared file access across heterogeneous clients.

**OP3** — 3-tier: core (backbone), distribution (aggregation/policy), access (end devices). Hierarchical, creates bottlenecks, high east-west latency. *Leaf-spine*: flat topology, every leaf connects to every spine. Solves: east-west traffic bottlenecks, unpredictable latency, and scaling limits. Preferred in modern DCs for consistent low latency, better utilization, and cloud-native workloads.

**OP4** — Architecture: 3+ nodes (odd for quorum). Quorum via Corosync. Fencing via IPMI/STONITH to prevent split-brain. Shared storage: Ceph (recommended for HA) or iSCSI/NFS. During node failure: Corosync detects loss, STONITH fences the node, VMs auto-migrate to surviving nodes if storage is accessible and resources permit. Quorum ensures only one cluster state survives.

**OP5** — VLAN trunking carries multiple VLANs over a single physical link. 802.1Q adds a 4-byte tag to Ethernet frames to identify VLANs. Linux config for 3 VLANs on `eth0`:
```bash
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip link add link eth0 name eth0.30 type vlan id 30
ip addr add 10.0.10.5/24 dev eth0.10
# repeat for .20 and .30
```
Enable with `ip link set eth0.10 up`.

**OP6** — RAID 1: mirror. RAID 5: single parity. RAID 6: dual parity. RAID 10: mirror+stripe. RAID Z2: ZFS dual parity. For a 6-drive DB server: choose RAID 10 (4 drives usable, highest read/write performance, survives 1 drive per pair). If capacity is critical, RAID 6/Z2 (4 drives usable, survives 2 failures, better write performance than RAID 5). Modern DBs often prefer ZFS mirrors or RAID 10 for performance + integrity.

**OP7** — Internal: AD-integrated DNS (recursive + authoritative for internal zones). DMZ: separate authoritative servers for public zones. Split-horizon: internal resolver returns private IPs for public names; external returns public. DNSSEC: sign external zone, validate on resolvers. Forwarders: internal forwards to ISP/Cloudflare. Conditional forwarding: for partner domains. Laptop on VPN: receives internal DNS via DHCP, resolves internal names; off-network uses public DNS. Conditional forwarding ensures seamless name resolution across boundaries.

**OP8** — Chain: Root CA (offline, self-signed) → Subordinate/Issuing CA (online, issues certs) → End-entity. CRL: periodic revocation list. OCSP: real-time revocation check. Templates: define key usage, validity, enrollment. Auto-enrollment: GPO/SCCM. Compromised sub CA: revoke sub CA cert, reissue affected certs, limited blast radius. Compromised root CA: catastrophic; must rebuild entire PKI, revoke all certs, massive trust loss, long recovery.

**OP9** — *MPLS*: high reliability, low latency, expensive, complex. *IPsec VPN*: cheap, variable latency/reliability, moderate complexity. *SD-WAN*: dynamic path selection, app-aware, cost-effective, good reliability, centralized management. *WireGuard mesh*: fast, simple, lacks centralized policy/QoS. Recommendation: SD-WAN over broadband + LTE backup. Provides QoS for VoIP, cost savings, centralized management, and handles latency better than pure IPsec.

**OP10** — iDRAC/iLO/IPMI: out-of-band management interfaces for remote server control. Critical: access when OS is dead, remote power cycle, console access, firmware updates. Exposed to internet: severe risk (brute force, default creds, firmware exploits, full server compromise). Must be on isolated management VLAN, firewall-protected, strong auth, and patched.

**OP11** — *LVM*: block-level, thick provisioning, snapshots copy-on-write (space grows as data changes). *LVM-Thin*: thin provisioning, overcommit, snapshots share space until modified. *ZFS*: filesystem+volume manager, CoW, checksums, efficient snapshots/clones, deduplication. Use LVM for simple Linux storage, LVM-Thin for VMs/overcommit, ZFS for data integrity, NAS, advanced features. Snapshot semantics: LVM thick = full copy initially, thin/ZFS = metadata pointer, space used only on write.

**OP12** — Stretch cluster: 2 sites + 1 tiebreaker (3rd site or quorum device). Ceph CRUSH: place replicas across sites, require 3 replicas. Monitors: 1 per site + tiebreaker. Latency: <2ms RTT between sites for synchronous replication. Split-brain: prevented by tiebreaker/quorum. 2-site Ceph without tiebreaker is dangerous: network partition causes both sites to think they're primary, leading to data corruption. Tiebreaker breaks ties safely.

**OP13** — DHCP: dynamically assigns IPs. DORA: Discover (client broadcast), Offer (server reply), Request (client accepts), Acknowledge (server confirms). If server unavailable at lease expiry: client renews at 50% (T1), then 87.5% (T2). If fails, continues using IP until expiration, then stops sending traffic (Windows falls back to APIPA 169.254.x.x).

**OP14** — *Unmanaged*: plug-and-play, no config. *Managed*: VLANs, QoS, STP, port mirroring, SNMP, ACLs, LAG. Important for enterprise: network segmentation, traffic prioritization, security policies, monitoring, and redundancy.

**OP15** — NTP: Network Time Protocol. Critical: Kerberos auth fails if >5min drift, log correlation impossible, distributed transactions/consensus break, certificates may appear invalid. Drift causes: auth failures, replication errors, split-brain, audit gaps, and inconsistent backups.

**OP16** — *Physical*: bare metal, max performance, no virtualization overhead. *VM*: full OS isolation, heavier. *Container*: shared kernel, lightweight. Run on bare metal when: GPU/PCIe passthrough needed, extreme performance/low latency, licensing restrictions, or hardware-specific workloads (HPC, real-time, certain DBs).

**OP17** — *UPS*: instant power, bridges gap (seconds/minutes), protects against surges, allows graceful shutdown. *Generator*: long-term power, takes time to start. Need both: UPS handles immediate loss, generator takes over after UPS drains. *ATS*: automatically switches load from utility to generator when power fails, ensuring seamless transition.

**OP18** — *Active-Passive*: one primary, one standby (failover). *Active-Active*: both handle traffic (load balancing). PostgreSQL HA with Pacemaker/Corosync: AP model. Fencing (STONITH): IPMI kills failed node to prevent split-brain. Virtual IP: floats to active node. Failover: if primary dies, STONITH triggers, VIP moves, standby promotes to primary via `pg_ctl promote`.

**OP19** — Strategy: 3-2-1 rule (3 copies, 2 media, 1 offsite). Define RPO/RTO. Types: full (baseline), incremental (since last backup), differential (since last full). Deduplication: saves space. Media: disk for speed, tape for long-term/air-gapped, cloud for offsite. Immutable: WORM storage, prevents ransomware encryption. Test restores: regular drills, verify RTO/RPO. Backup vs DR: backup = data copy; DR = full system recovery process + infrastructure + runbooks.

**OP20** — 802.1X roles: *Supplicant* (client), *Authenticator* (switch/AP), *Authentication Server* (RADIUS). EAP-TLS: mutual cert auth (strongest). PEAP: MSCHAPv2 over TLS tunnel. Dynamic VLAN: RADIUS assigns VLAN based on user/device. Failed auth: port goes to restricted VLAN or disabled. MAB: fallback using MAC address for legacy/IoT devices, less secure, used when supplicant unsupported.
