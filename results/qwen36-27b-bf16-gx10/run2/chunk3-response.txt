### OpenTofu / Terraform

**T1** `tofu plan` generates an execution plan by comparing your configuration against the current state and remote infrastructure. It shows what will be created, updated, or destroyed without making changes. `tofu apply` executes that plan, making the actual API calls to provision or modify resources.

**T2** State is a JSON file that maps OpenTofu configuration resources to real-world infrastructure IDs and metadata. Remote state is critical for team collaboration (prevents local file conflicts), enables state locking (prevents concurrent writes), provides versioning/backup, and improves security by keeping sensitive data off developer workstations.

**T3** `count` creates resources based on an integer index, while `for_each` creates resources based on map/set keys. `for_each` is preferred when resources need stable, unique identifiers (e.g., DNS names, IAM roles), when adding/removing items shouldn't shift indices and cause unintended recreations, or when resources require distinct configurations per key.

**T4** Manual changes cause "drift." During `tofu plan`, OpenTofu queries the provider API, compares the live state to the tracked state, and detects differences. It will propose changes to revert the resource to match your configuration. You can resolve drift by running `tofu apply` (reverts to config), updating the config to match reality, or using `tofu state` commands to adjust tracking.

**T5**
```hcl
resource "aws_instance" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  tags = { Name = each.value }
}
```

**T6** `terraform_remote_state` reads another workspace's raw state file, creating tight coupling, security risks (exposes all state data), and fragility (breaks if state schema changes). Outputs are explicit, versioned, and only expose intended data. Recommended alternative: pass data via variables in a parent/root module. If cross-workspace sharing is unavoidable, use `remote_state` but only read explicit outputs, never raw state attributes.

**T7** Provisioners run during `apply`, but outputs are evaluated before/during the apply phase. The `null_resource` hasn't finished writing the kubeconfig when the output is computed, resulting in an empty value. Fix: Avoid relying on provisioner side-effects for outputs. Use a `data "local_file"` or `external` data source to read the generated file in a subsequent apply, or use a provider/resource that natively exposes the kubeconfig. Add `depends_on` to ensure ordering, but restructure to eliminate the race condition.

**T8** `tofu import` maps existing infrastructure to state by CLI command. Limitations: doesn't generate config, requires exact address matching, and can fail on complex dependencies. The `import` block (1.5+) is declarative, lives in config, runs during `tofu apply`, and supports `-generate-config-out` to auto-generate resource blocks, making imports repeatable and auditable.

**T9** A variable is a named value used in configuration. Input variables (`variable` block) accept external values (CLI, env vars, files). Outputs (`output` block) expose computed values from state or configuration to users, CI/CD, or other modules. Inputs configure; outputs report.

**T10** A provider is a plugin that translates OpenTofu operations into API calls for a specific platform (AWS, Azure, etc.). Running `tofu plan` without `tofu init` fails because providers aren't downloaded or initialized. OpenTofu will error with "provider not found" or similar, as it cannot resolve resource/data source schemas.

**T11** `.terraform.lock.hcl` pins exact provider versions and cryptographic checksums. It ensures reproducible builds, prevents supply-chain attacks, and guarantees all team members/CI pipelines use identical provider binaries. It should always be committed to version control.

**T12** `tofu destroy` removes all resources managed in the current state. To target a single resource: `tofu destroy -target=aws_instance.web`. Note: targeting may leave dependent resources in an inconsistent state; use cautiously.

**T13** A data source reads existing infrastructure without managing it. Use it when you need to reference IDs, attributes, or configurations of resources created outside OpenTofu (e.g., fetching an existing VPC ID, latest AMI, or DNS record) rather than creating them.

**T14** `variable` blocks define external inputs. `locals` compute derived values within module scope using variables, data sources, or other locals. Use `locals` for complex expressions, avoiding repetition, or creating intermediate values that shouldn't be exposed as inputs. Don't use `locals` for external configuration.

**T15** `lifecycle` controls resource behavior:
- `create_before_destroy`: Creates replacement before deleting old (zero-downtime deployments).
- `prevent_destroy`: Blocks deletion even during `tofu destroy` (protects critical data stores).
- `ignore_changes`: Ignores drift on specific attributes (e.g., auto-scaling tags, managed IAM policies).

**T16** `moved` tracks resource or module renames/structural changes in state. It maps old addresses to new addresses, preventing OpenTofu from destroying and recreating resources during refactoring. It updates state references transparently while preserving infrastructure.

**T17** OpenTofu builds a Directed Acyclic Graph (DAG) from configuration references. Implicit dependencies come from attribute references (`aws_instance.foo.id`). Explicit dependencies use `depends_on`. `depends_on` forces ordering, reducing parallelism. Use it sparingly (only for side effects, `null_resource`, or when implicit references can't be expressed) to maintain apply speed.

**T18** Strategies to reduce plan time:
1. **Split state/modules**: Smaller state files = faster reads/writes. Tradeoff: increased management complexity.
2. **`-refresh=false`**: Skips API calls to check live state. Tradeoff: drift risk.
3. **Optimize provider configs**: Disable unused features (`skip_metadata`, `ignore_tags` where applicable). Tradeoff: may miss platform-specific attributes.
4. **Upgrade OpenTofu/Terraform**: Newer versions optimize graph building and state handling. Tradeoff: migration/testing overhead.

**T19** State locking prevents concurrent modifications via backend-specific mechanisms (DynamoDB, Consul, etc.). If a lock isn't released (e.g., CI crash), subsequent runs fail. Manually break via backend CLI (e.g., `aws dynamodb delete-item`). Risks: state corruption, split-brain, inconsistent infrastructure. Only break after verifying no other process is running.

**T20** Migration steps:
1. Backup current state: `cp terraform.tfstate terraform.tfstate.bak`
2. Update config with new backend block (S3 + DynamoDB)
3. Run `tofu init -migrate-state`
4. Verify: `tofu state list` and `tofu plan` (should show no changes)
5. Commit new backend config. The existing state file is uploaded to S3, DynamoDB handles locks, and local state is replaced with a backend reference.

### Ansible

**A1** A **playbook** is a YAML file containing plays (target hosts + tasks). A **role** is a reusable directory structure organizing tasks, vars, templates, handlers, etc. A **task** is a single unit of work (module invocation) within a play or role.

**A2** `ansible_facts` is a dictionary of auto-collected host information. Access OS family: `{{ ansible_os_family }}`.

**A3** `command`: runs binaries directly, no shell parsing (safe, predictable). `shell`: runs via `/bin/sh`, supports pipes, redirection, and environment variables. `raw`: sends command directly over SSH, bypassing module overhead. Use `command` for safety, `shell` for complex bash, `raw` for non-standard targets or speed.

**A4** Ansible ensures idempotency by designing modules to check current state before acting. Idempotent: `apt: name=htop state=present` (skips if installed). Not idempotent: `shell: echo "data" >> /tmp/log` (appends every run).

**A5**
```yaml
- name: Install htop and dependencies
  package:
    name: "{{ 'epel-release htop' if ansible_os_family == 'RedHat' else 'htop' }}"
    state: present
```

**A6** Precedence (lowest to highest): role defaults < inventory/group_vars < host_vars < extra_vars (`-e`) < `set_fact`. `set_fact` overrides almost everything; extra_vars override inventory/role vars; role defaults are the baseline.

**A7** Structure:
1. Split inventory: `[rke2_servers]` (3 hosts), `[rke2_agents]` (47 hosts)
2. Play 1: `hosts: rke2_servers`, `serial: 3`, deploy RKE2 server
3. Play 2: `hosts: rke2_agents`, `serial: 10`, use `wait_for` or `uri` to check `https://<server>:6443/healthz` before joining
4. Use `run_once: true` with `delegate_to` for coordination if needed. `serial` controls batch size; `wait_for` ensures server readiness.

**A8** `ansible-vault` encrypts files/variables. Encrypt a single variable: `ansible-vault encrypt_string 'mysecret' --name 'db_password'` (outputs YAML with `!vault` tag). Paste the tag into your vars file; only that variable is encrypted.

**A9** Inventory defines target hosts/groups. Static: YAML/INI file manually maintained. Dynamic: script/plugin that queries cloud APIs/CMDBs to generate inventory on-the-fly (e.g., AWS EC2 plugin).

**A10** `ansible webservers -m command -a "df -h"`

**A11** A handler is a task that runs only when notified by another task. It differs by running once at the end of a play, regardless of how many times it's notified. Trigger: `notify: restart nginx` in a task.

**A12** `ansible.cfg` configures Ansible behavior. Common settings: `host_key_checking = False`, `forks = 20`, `remote_user = deploy`, `private_key_file = ~/.ssh/id_rsa`, `log_path = /var/log/ansible.log`, `retry_files_enabled = False`.

**A13** `register` captures task output (stdout, rc, stderr) into a variable. Use: `{{ my_result.stdout }}` or `{{ my_result.rc }}` in subsequent tasks for conditionals or logging.

**A14** `import_tasks` is static (parsed at compile time), faster, conditionals apply to included tasks individually. `include_tasks` is dynamic (evaluated at runtime), supports conditionals/loops on the include itself. Use `import` for performance/static includes; `include` for dynamic/runtime decisions.

**A15** Ansible Galaxy is a community hub for roles/collections. Create `requirements.yml` listing roles/collections, then run `ansible-galaxy install -r requirements.yml` to download them into `roles/` or `collections/`.

**A16** Connection plugins define how Ansible reaches targets. `ssh`: default, uses SSH for Linux/Unix. `local`: runs on control node. `network_cli`: persistent SSH for network devices (Cisco, Juniper). Use `ssh` for servers, `local` for localhost tasks, `network_cli` for routers/switches.

**A17** `delegate_to` runs a task on a specific host instead of the target. `run_once` runs it once per play. Example: gather remote host IP, then `delegate_to: localhost run_once: true` to update a DNS record or trigger a webhook using that IP.

**A18** Performance strategies:
1. **Increase `forks`**: Parallelizes hosts. Tradeoff: control node CPU/memory, network/API rate limits.
2. **Enable `pipelining`**: Reduces SSH round trips. Tradeoff: requires `requiretty` disabled in sudoers.
3. **Fact caching** (`redis`, `jsonfile`): Skips `setup` module. Tradeoff: stale facts, storage overhead.
4. **Mitogen**: Replaces SSH with high-performance RPC. Tradeoff: extra dependency, occasional module compatibility issues.

**A19** Jinja2: `{{ }}` expressions/variables, `{% %}` statements (loops/conditionals), `{# #}` comments.
Snippet:
```jinja2
upstream backend {
{% for server in backends %}
    server {{ server.ip }}:{{ server.port }}; # health_check: {{ server.health_endpoint }}
{% endfor %}
}
```

**A20** Rolling deploy playbook:
- `serial: 2` (or `10%`) for batched updates
- `block/rescue` for rollback safety
- Pre-task: `notify: deregister_from_lb`
- Main: deploy app, restart service
- Post-task: `notify: register_to_lb`, then `uri` module health check (`status_code: 200`)
- `rescue`: revert to previous version, re-register, fail play
- Handlers manage LB state; `uri` validates health before proceeding to next batch. Ensures zero downtime with automatic rollback on failure.
