## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A**
The pods fail because the `Restricted` Pod Security Standard (PSS) enforces `runAsNonRoot: true` at the pod/container level. When `runAsUser` is omitted, Kubernetes falls back to the `USER` directive in the container image. The new Chainguard base image defaults to `root` (UID 0). Under `Baseline` PSS, running as root was permitted. `Restricted` PSS explicitly blocks containers that would run as root, causing the container runtime to reject startup, resulting in `CrashLoopBackOff`. The PSS admission controller evaluates the effective UID before the container starts; if it resolves to 0, the pod is denied.

**SC1-B**
```bash
kubectl get pods --all-namespaces -o json | jq -r '.items[] | select(any(.status.containerStatuses[].state.waiting.reason; . == "CrashLoopBackOff")) | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C**
*Immediate Fix:* Patch affected deployments to add `securityContext.runAsUser: 1000` (or a non-root UID) and redeploy. Alternatively, temporarily relax PSS to `Baseline` via namespace labels if immediate restoration is critical, then patch.
*Image-Level Fix:* Add `USER 1000` in the Dockerfile or use `--user=1000` in `docker run`/`kubectl run`.
*Manifest Changes:* Explicitly set `runAsUser`, `runAsGroup`, and `fsGroup` in pod specs. Remove reliance on image defaults.
*CI Gate:* Add a Conftest/OPA policy or Trivy check that fails if `runAsNonRoot: true` is set without `runAsUser`, or if the final image `USER` is root.
*Rollout:* Use rolling updates with `maxUnavailable: 0` and PodDisruptionBudgets. Deploy patched manifests/images to a canary namespace first, verify health, then promote to production.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A**
Promoting a cross-region read replica with asynchronous replication means any WAL segments not yet shipped or applied are permanently lost. The 85ms latency causes replication lag, so the replica's replay LSN trails the primary's flush LSN. Stale data occurs because the replica hasn't applied recent transactions. To quantify the loss window, compare `pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()` on the replica against `pg_current_wal_lsn()` on the former primary. The difference in bytes/time represents the exact data loss window.

**SC2-B**
```bash
# 1. Import the promoted replica into state (overwrites old reference)
terraform import aws_db_instance.primary arn:aws:rds:eu-west-1:<account>:db:<new-instance-id>

# 2. Update Terraform variables/config to match the new region/ARN
# 3. Verify no unintended changes
terraform plan

# 4. For dependent resources (SGs, Route53, Parameter Groups), update their references in code to point to the new instance ID/ARN, then:
terraform apply -target=aws_route53_record.db -target=aws_security_group_rule.db_access
```
Use `terraform state rm` only if the old instance is already destroyed and you need to clean orphaned state.

**SC2-C**
*Connection Management:* Replace PgBouncer with RDS Proxy. It natively handles IAM auth, connection pooling, and transparent failover without app changes.
*DNS Failover:* Route53 health checks (TCP/5432) with failover routing policies. Route traffic to the healthy region's RDS Proxy endpoint.
*App Retry Logic:* Implement exponential backoff with jitter and circuit breakers for transient connection failures during failover.
*RPO < 1s:* Standard RDS async replication cannot guarantee <1s RPO across regions. Recommend **Aurora Global Database**. It uses optimized async replication with ~1s RPO, automatic failover, and eliminates manual promotion steps.
*Architecture:* Aurora Global + RDS Proxy + Route53 failover + app-level retries. This removes manual promotion, reduces RPO, and handles connection storms automatically.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A**
1. **In-Memory Sessions:** K8s pods are ephemeral. Sticky sessions break horizontal scaling. *Fix:* Externalize to Redis with session affinity disabled.
2. **Local NFS Mount:** Bare-metal NFS doesn't translate to K8s. *Fix:* Use `nfs.csi.k8s.io` StorageClass with PVCs, or migrate uploads to S3-compatible object storage.
3. **Oracle 19c Dependency:** Oracle isn't cloud-native. *Fix:* Lift & shift to Oracle RDS/Exadata, or migrate schema to PostgreSQL/MySQL on RDS.
4. **IBM MQ Integration:** Mainframe MQ clients expect stable IPs/ports. *Fix:* Deploy IBM MQ on K8s or use a service mesh to abstract endpoints. Keep legacy MQ during transition.
5. **F5/Bare-Metal Networking:** F5 iRules and hardware LBs don't map to K8s. *Fix:* Deploy NGINX/HAProxy Ingress Controller or AWS ALB Ingress. Use ExternalDNS for DNS routing.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A**
*Debugging Approach:*
1. **Istio Metrics:** Check `istio_request_duration_milliseconds` (histogram) for checkout→inventory. Look at `istio_requests_total` for error rates.
2. **Envoy Metrics:** `upstream_rq_pending_total` (proxy queueing), `upstream_rq_timeout`, `downstream_cx_active`. High pending = proxy bottleneck. High upstream duration = app bottleneck.

**SC6-A**
*Identity Layer:*
1. **SPIFFE/SPIRE:** Deploy SPIRE Server in each environment. Workloads get SPIFFE IDs (`spiffe://trustdomain/ns/pod`) via SPIRE Agent.
2. **AWS IAM:** Use IRSA to map K8s ServiceAccounts to IAM roles. SPIRE can fetch AWS credentials via OIDC federation.

**SC7-A**

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A**
*Architecture Comparison:*
- **Active-Passive (Velero):** RPO met (15m backups). RTO risk: Restoring 200TB MinIO + stateful apps exceeds 1h. Not viable for strict RTO.
- **Active-Active (Istio/Cilium):** Stateless traffic routed dynamically. Stateful components use async/sync replication. 12ms latency allows synchronous DB replication. RPO < 15m easily met. RTO ~5-10 mins (DNS + auto-promotion).
*Replication Strategy:*
- PostgreSQL: Patroni synchronous commit to Dallas. Zero data loss.
- Redis: Sentinel async replication. RPO ~1-5s.
- RabbitMQ: Quorum queues with cross-site mirroring. RPO ~1s.
- MinIO: Site replication (async). 200TB at 10Gbps = ~55m full sync, but incremental keeps RPO < 15m.
*Verdict:* Active-active for stateless, synchronous/async replication for stateful. Meets RPO 15m, RTO 1h comfortably.

**SC10-C**
*Failover Sequence:*
1. **Detection:** Multi-region health checks (HTTP, TCP, DB ping). "Site down" = 3 consecutive failures + BGP flapping. False positive mitigation: require 2/3 monitors to agree.
2. **DNS:** GSLB (Route53/Cloudflare) switches CNAME to Dallas endpoint. TTL pre-set to 60s.
3. **Patroni:** Automatic promotion via etcd leader election. Synchronous commit ensures zero data loss.
4. **Redis Sentinel:** Auto-promotes replica. App reconnects via Sentinel discovery.
