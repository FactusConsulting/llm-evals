CL1 — IaaS provides raw compute, storage, and networking; you manage the OS, middleware, and apps (e.g., AWS EC2). PaaS provides a managed runtime/environment; you manage code and data (e.g., Azure App Service). SaaS delivers a fully managed application; you only configure and use it (e.g., Microsoft 365).

CL2 — The Shared Responsibility Model splits security duties: the provider secures the cloud infrastructure; you secure what you put in it. For IaaS VMs, the provider secures the host/hypervisor/physical network; you secure the guest OS, patches, firewall rules, data, and IAM. For managed Kubernetes (EKS/AKS), the provider secures the control plane; you secure worker nodes, pod configs, network policies, workloads, and secrets. For SaaS like M365, the provider secures everything infra/runtime; you secure tenant configuration, user access, data classification, and DLP policies.

CL3 — A VPC is a logically isolated virtual network. Subnets divide the VPC into IP ranges, typically mapped to AZs. Security Groups are instance-level, stateful firewalls (return traffic auto-allowed, allow-only rules). NACLs are subnet-level, stateless firewalls (explicit inbound/outbound rules, support allow/deny). Layering: Traffic hits NACL → SG → OS firewall. Stateful filtering tracks connection state; stateless treats each packet independently, requiring explicit rules for both directions.

CL4 — A Landing Zone is a pre-configured, secure multi-account baseline. Organizational Units (OUs) group accounts by function/environment for policy inheritance. Guardrails (SCPs/Organizational Policies) enforce compliance (e.g., block public S3, mandate MFA). Shared networking uses Transit Gateway or Hub-and-Spoke for centralized routing, NAT, and cross-account peering. Centralized logging aggregates CloudTrail/Activity Logs to S3/Log Analytics → SIEM. Single-account approaches fail due to blast radius, permission sprawl, noisy neighbors, poor cost attribution, and compliance isolation failures.

CL5 — IaC manages infrastructure via versioned code. Terraform/OpenTofu: declarative HCL, multi-cloud, mature state management; best for broad infra. Pulumi: uses general-purpose languages (TS/Python/Go), supports complex logic; best for dev-heavy teams. CloudFormation/Bicep: native AWS/Azure, deep service integration; best for single-cloud, provider-specific features. Crossplane: K8s-native, manages cloud resources via CRDs; best for GitOps/K8s-centric orgs. Choose based on team skills, cloud scope, and deployment model.

CL6 — HPA scales pod count based on CPU/metrics/custom sources. VPA adjusts pod resource requests/limits (requires restart). Cluster Autoscaler adds/removes nodes based on pending pods. KEDA is event-driven, scales on external triggers (queues, streams, DB connections) and can scale to zero. Use KEDA over HPA when scaling depends on event rates rather than resource utilization, or when zero-scale cost optimization is required.

CL7 — Define RPO/RTO first. Active-Active runs both regions synchronously/async, complex, high cost, lowest RTO/RPO. Active-Passive runs primary, standby syncs/asyncs, DNS failover, lower cost, higher RTO. DB replication: sync (zero RPO, latency penalty), async (low RPO, better perf). DNS failover uses Route53/Traffic Manager health checks with tuned TTLs. State must be externalized (managed DB/cache, S3). Pilot Light: minimal core infra pre-provisioned, scales on failover. Warm Standby: fully running but scaled down. Multi-site Active-Active: full redundancy everywhere. Cost scales with redundancy level.

CL8 — GitOps uses Git as the single source of truth; controllers continuously reconcile cluster state to Git. ArgoCD offers a UI, app-centric workflows, and broad ecosystem. FluxCD is CNCF, CLI-focused, highly modular, integrates tightly with Kustomize/Helm. Secrets are handled via Sealed Secrets (encrypts for Git), External Secrets Operator (pulls from Vault/AWS SM), or Vault Agent Injector. Manual drift is detected by the controller and auto-reverted to Git state (or flagged/alerted based on policy).

CL9 — Use a StatefulSet for stable network IDs, ordered deployment, and persistent storage. Attach PVCs backed by a `local` StorageClass for low-latency, node-affinity storage. Use a Headless Service for direct pod DNS resolution (sticky sessions/ordered discovery). Init containers handle legacy path mapping, config file placement, and pre-flight checks. Mount ConfigMaps as volumes to specific filesystem paths. Set a PodDisruptionBudget (`minAvailable`) to maintain availability during node drains. Architecture: StatefulSet → Headless SVC → Local PVCs → Init containers mount ConfigMaps → PDB protects scaling events.

CL10 — A Service Account is a K8s identity for pod-to-API server auth; it has no cloud permissions. IRSA (AWS) / Workload Identity (GCP/Azure) maps a K8s SA to a cloud IAM role via OIDC federation. Mounting static cloud credentials is bad practice: rotation is manual, blast radius is high, secrets sprawl, and compliance is hard. Federation solves this by issuing short-lived tokens, enabling dynamic role assumption, enforcing least privilege per workload, and eliminating static secrets.

CL11 — Object storage (S3/Blob): flat namespace, HTTP API, 11x9s durability, 99.99%+ availability; use for unstructured data, backups, static assets. Block storage (EBS/Managed Disk): raw disk, low latency, single-attach; use for OS, databases, high IOPS workloads. File storage (EFS/Azure Files): NFS/SMB, shared access, POSIX/SMB semantics; use for dev environments, CMS, legacy apps needing shared mounts. Durability/availability vary by tier but object storage offers the highest durability guarantees.

CL12 — Zero-trust K8s: Default-deny Network Policies segment pod traffic. Service mesh (Istio/Linkerd) enforces mTLS and fine-grained authz. Pod identity (IRSA/Workload Identity) replaces static credentials. Admission controllers (OPA/Kyverno) enforce policies at deploy time (no root, resource limits, approved registries). Image signing (Cosign) + admission webhooks reject unsigned/tampered images. Runtime security (Falco) detects syscall/process anomalies. Secrets managed via External Secrets/Vault. Differs from perimeter models by assuming breach, verifying every request, micro-segmenting, and being identity-centric rather than network-boundary trust.

CL13 — A CDN caches content at edge PoPs closer to users, reducing latency and origin load. DNS routes requests to the nearest PoP; cached content is served, misses hit the origin. Services: CloudFront, Azure Front Door, Cloudflare. Use CDN for static assets, media, global distribution, cacheable APIs, and DDoS mitigation. Serve directly from origin for highly dynamic, personalized, low-traffic, or internal-only workloads where caching adds complexity.

CL14 — A Region is a geographic area with multiple isolated data centers. An Availability Zone (AZ) is a physically separate facility within a region with independent power/cooling/networking, connected via low-latency links. Deploy across AZs for fault tolerance, high availability, and automatic failover. Zonal resources live in one AZ (EC2, EBS). Regional resources span AZs automatically (RDS Multi-AZ, ALB, S3).

CL15 — A managed database (RDS, Cloud SQL, Azure SQL) offloads infrastructure operations to the provider. The provider handles provisioning, patching, backups, failover, monitoring, scaling, and high availability. Running on a VM requires you to manage the OS, DB software, patches, replication, HA architecture, tuning, security hardening, and backup automation. Managed services provide SLAs, automated backups, point-in-time recovery, and built-in monitoring.

CL16 — IAM Users are human/service identities. Groups bundle users for policy assignment. Roles are temporary permissions assumed by users/services. Policies are JSON/YAML documents granting/denying actions on resources. Least privilege means granting only permissions required for a task. Apply via scoped policies, resource-level conditions, temporary credentials, regular access reviews, automated rotation, and just-in-time access.

CL17 — Serverless is event-driven, auto-scaling, pay-per-use compute without server management. Lambda/Functions/GCF share core concepts but differ in runtime support, concurrency limits, and ecosystem integrations. Cold starts are initialization delays after idle periods; they matter for latency-sensitive APIs and synchronous requests. Mitigate with provisioned concurrency, smaller packages, or warm-up patterns. Poor fit for long-running processes, high sustained load (costly), custom OS/kernel needs, strict latency SLAs without provisioned concurrency, or large stateful workloads.

CL18 — Ingress Resource: L7 routing, TLS termination at ingress controller, limited spec. Gateway API: next-gen, separates listeners/routes/secrets, supports multi-tenant, better TLS/HTTPRoute/GRPCRoute. Cloud LB annotations: direct cloud LB provisioning, TLS at cloud LB. Service mesh ingress: Istio Gateway, mTLS termination, advanced routing. TLS termination occurs at the cloud LB, ingress controller, or mesh gateway depending on architecture. Use Gateway API over Ingress for advanced routing, multi-tenant isolation, standardized L4/L7 abstractions, and better TLS management.

CL19 — Reserved Instances for predictable steady-state compute. Savings Plans for flexible compute across services. Spot/Preemptible for fault-tolerant/batch workloads (up to 90% savings). Right-size via utilization analysis and auto-scaling. Storage tiering: S3 Intelligent-Tiering, Glacier/Archive for cold data, lifecycle policies. Idle detection: tagging, usage metrics, automated shutdown, orphaned resource cleanup. FinOps: cross-functional culture, continuous monitoring, anomaly detection, budget alerts, showback/chargeback via tags. Tools: native Cost Explorer, OpenCost, CloudHealth, custom dashboards. Process: monthly reviews, engineering accountability, automated guardrails.

CL20 — Abstraction via Terraform, Pulumi, Kubernetes, and containerization. K8s provides a consistent runtime across EKS/AKS. IaC portability via reusable modules, avoiding provider-specific lock-in where possible. Networking via Direct Connect/ExpressRoute, VPN, global LBs, DNS routing. Identity federation via OIDC/SAML, centralized IdP, cross-cloud role mapping. Trade-offs: operational complexity, skill fragmentation, data egress costs, compliance mapping. Theoretical benefits: resilience, best-of-breed services, negotiation leverage. Justified for regulatory requirements, risk mitigation, specific service needs, or customer proximity. Unnecessary when single-cloud maturity, cost, and performance suffice; multi-cloud adds real overhead and should only be adopted when business value outweighs complexity.

OT1 — The Purdue Model (ISA-95) hierarchically segments industrial networks. Level 0: Physical process (sensors, actuators). Level 1: Control devices (PLCs, RTUs, DCS). Level 2: Supervisory control (SCADA, HMI, historians). Level 3: Site operations (MES, production scheduling). Level 4: Enterprise (ERP, business planning). Level 5: External (partners, cloud, internet). Defines security boundaries and data flow direction.

OT2 — IT networks are data-centric, prioritize confidentiality/integrity/availability, support frequent updates, and use virtualized/short-lifecycle hardware. OT networks are process-centric, prioritize availability/safety/integrity, run legacy hardware with 10-20 year lifecycles, and enforce real-time constraints. Standard IT patching can't be applied because patches may break real-time control loops, cause unplanned downtime, or invalidate safety certifications; OT patching requires rigorous testing, validation, and scheduled maintenance windows.

OT3 — The IDMZ buffers IT (L4) and OT (L0-L3), hosting proxies, data concentrators, unidirectional gateways, and secure file transfer. Allowed traffic: IT→OT (read-only data collection, authorized firmware updates via secure vault), OT→IT (process data, alarms, historian exports). Traffic is strictly controlled, often unidirectional. Direct L4→L1 connectivity is dangerous because it bypasses supervision, exposes control logic to IT malware, violates safety principles, and enables direct manipulation of physical processes.

OT4 — Modbus TCP: L1/L2, simple master-slave, legacy/SCADA. OPC UA: L2/L3, secure, platform-independent, modern info modeling. EtherNet/IP (CIP): L1/L2, Rockwell ecosystem, implicit/explicit messaging. PROFINET: L1/L2, Siemens ecosystem, real-time Ethernet. MQTT: L3/L4, lightweight pub/sub, edge-to-cloud telemetry, not for real-time control.

OT5 — A data diode enforces hardware-level unidirectional data flow via physical/optical isolation, guaranteeing zero reverse traffic. A firewall performs stateful, rule-based bidirectional inspection. Use a hardware diode for high-security OT, safety-critical systems, or strict regulatory requirements where reverse traffic must be physically impossible. Limitations: no bidirectional communication, higher cost, complex management, harder troubleshooting, requires separate return channel if needed.

OT6 — Data flow: PLCs/RTUs (L1) → OPC UA Server (L2) → Historian (L3) → Edge Gateway in IDMZ → MQTT Broker → Cloud Ingestion (Kafka/Event Hubs) → Analytics. Security boundaries: L1/L2 isolated VLANs, OT-aware firewall at L2/L3, IDMZ at L3/L4, edge gateway with protocol translation/filtering, TLS/mTLS for MQTT, cloud VPC with private endpoints, IAM least privilege, and network segmentation between ingestion and analytics.

OT7 — IEC 62443 defines Zones (groups of assets with similar security/function requirements) and Conduits (communication paths between zones with defined security controls). Design: Zone 1: Corporate/IT (L4). Zone 2: Engineering/IDMZ (L3/L4). Zone 3: SCADA/Historian (L2/L3). Zone 4: PLCs/Control (L1). Zone 5: SIS (Safety, isolated). Conduits: IT→IDMZ (filtered, MFA, read-only), IDMZ→SCADA (protocol-aware firewall, unidirectional preferred), SCADA→PLC (VLAN segmented, allow only control protocols), SIS isolated (air-gapped or strict diode/conduit, no IT/SCADA direct access).

OT8 — VLAN design: Segment by function/line (L1 PLCs, L2 SCADA, L3 MES, Engineering, Maintenance, Corporate). Firewall placement: OT-aware firewalls at L2/L3 boundary, IDMZ at L3/L4, inline IDS/IPS. Switch architecture: Managed L3 switches, RSTP, port security, 802.1X where feasible, dedicated OT switches. Remote access: Bastion in IDMZ, MFA, session recording, time-limited vendor credentials, secure portal. Transition: Phased rollout, parallel validation, non-disruptive VLAN migration during maintenance windows, rollback plans, control loop verification post-migration.

OT9 — BPCS handles normal process operations (PLCs/DCS). SIS handles emergency shutdown/safety functions, rated to SIL levels per IEC 61511. IEC 61511 defines functional safety lifecycle, validation, and SIL requirements. SIS must be air-gapped or strictly isolated from BPCS/IT to prevent cyber attacks or BPCS failures from compromising safety functions. Ransomware on SIS could disable emergency shutdown, causing catastrophic failure, environmental damage, or loss of life.

OT10 — PLC: Discrete/sequential control, modular, rugged, used for machinery/assembly. DCS: Continuous process control, distributed architecture, high reliability, used for chemical/petrochemical/power. SCADA: Supervisory monitoring/data acquisition, wide-area, HMI/alarms, used for utilities/pipelines. They coexist commonly: PLCs/DCS handle L1 control, SCADA provides L2 supervision, integrated via OPC UA/Modbus.

OT11 — Remote access architecture: Bastion/jump hosts in IDMZ, hardened, MFA mandatory, session recording enabled. Vendor access: time-limited, scoped, monitored, pre-approved, revoked post-session. RDP directly to an HMI from corporate is unacceptable because it bypasses security controls, exposes the control network to IT threats, lacks audit trails, increases blast radius, and violates segmentation. Use secure remote desktop via bastion with strict policies and OT-aware monitoring.

OT12 — Detection: OT-aware IDS (Nozomi/Claroty), anomaly detection on control traffic, asset inventory baselining, SIEM correlation. Response: Isolate compromised segment (firewall rules, VLAN shutdown), preserve logs, engage control room for manual/safe mode, verify SIS integrity, coordinate with plant manager. Safe operations: Switch to manual/local control if needed, maintain water quality/safety, use offline backups. Operator role: Monitor physical processes, follow emergency procedures, report anomalies, prioritize safety, do not attempt IT fixes. Coordination: Cyber team isolates, OT engineers validate control integrity, management communicates, regulatory reporting if required.

OT13 — An HMI provides operators with a visual interface to monitor processes, acknowledge alarms, and execute controlled inputs. It differs from an engineering workstation: HMIs are runtime-focused, read-heavy, limited write access, and engineered for safety/usability. Engineering workstations are for programming, configuration, diagnostics, require higher privileges, and are typically isolated from runtime networks.

OT14 — A historian is a time-series database optimized for high-write throughput, compression, and trend analysis of process data. It's critical for process optimization, compliance, troubleshooting, and predictive maintenance. Plant historian (L3) stores raw/high-frequency data for local operations. Enterprise historian (L4) aggregates normalized data for business analytics, cross-plant comparison, and ERP integration.

OT15 — Ladder logic is a graphical programming language resembling electrical relay circuits, executed by PLCs. It remains dominant because it's intuitive for electricians/technicians, matches control schematics, has decades of legacy code, is highly reliable, well-supported, and has a low barrier to entry for OT engineers.

OT16 — An RTU (Remote Terminal Unit) is designed for wide-area/remote monitoring, rugged, event-driven, often uses serial/modem connectivity, and focuses on telemetry. PLCs handle high-speed local logic and control. RTUs are deployed in geographically dispersed, harsh environments with low bandwidth, such as pipelines, utilities, and remote SCADA sites.

OT17 — Analog signals (4-20mA, 0-10V) represent continuous physical variables; digital signals represent discrete states or communication protocols. 4-20mA is preferred over 0-20mA because 4mA represents zero, allowing wire-break detection at 0mA. It's immune to noise, supports long-distance transmission, enables loop-powered devices, and is the industry standard.

OT18 — OT asset inventory is the foundation of OT security because you can't protect what you don't know. It enables risk assessment, patch management, anomaly detection, and compliance. Tools/techniques: passive network monitoring (packet capture, protocol decoding), active scanning (Nmap, asset discovery), vendor records, engineering drawings. Active scanning is dangerous because it can crash legacy devices, disrupt real-time control, trigger alarms, violate safety, and cause unplanned downtime. Use passive first; active only in approved maintenance windows.

OT19 — MITRE ATT&CK for ICS maps adversary tactics/techniques specific to industrial environments. Five tactics + examples: 1. Initial Access: Vendor compromise or phishing. 2. Execution: Run malicious code on engineering workstation. 3. Persistence: Create backdoor account on HMI. 4. Lateral Movement: Pass-the-hash to PLC network. 5. Impact: Modify control logic to cause physical damage. Differs from enterprise matrix by focusing on physical impact, ICS protocols, safety systems, longer dwell times, and different attack paths. Use it to map controls to techniques, identify gaps, prioritize defenses, simulate attacks, and improve detection rules.

OT20 — Converged IT/OT SOC: Log collection via passive taps, protocol-aware parsers, low-impact agents, syslog/MQTT to SIEM (avoid polling). SIEM integration normalizes OT logs, correlates with IT, uses OT-specific playbooks. Detection rules: protocol anomalies, unauthorized commands, firmware changes, off-hours activity, known ICS malware. Triage: IT analysts handle initial alert, escalate to OT engineers for validation, clear runbooks. Staffing: IT analysts (cyber) + OT engineers (process); cross-training essential. False positives are high due to legacy protocols, maintenance, vendor activity; mitigate with baselining, tuning, context enrichment. Unauthorized firmware alert: verify with OT engineer, check change management, isolate if unapproved, capture forensic image, restore from known-good backup, update rules, report.
