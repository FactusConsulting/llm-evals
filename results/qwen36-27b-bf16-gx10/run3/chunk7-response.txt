AA1 — A monolith is a single deployable unit where all components share memory and a single codebase. Microservices split functionality into independently deployable services communicating over a network. Microservices introduce: (1) Distributed transaction complexity (no ACID across services), (2) Network latency and partial failure modes (timeouts, retries, cascading failures), (3) Operational overhead (deployment orchestration, service discovery, distributed tracing, and config management).

AA2 — Synchronous communication is request-response; the caller blocks until a reply arrives (e.g., REST over HTTP, gRPC). Asynchronous communication is decoupled; the sender dispatches a message and continues, with the receiver processing later (e.g., RabbitMQ, Kafka). Sync is simpler for immediate responses; async improves resilience and throughput for non-critical or batch workflows.

AA3 — A reverse proxy operates at L4/L7 to route traffic, terminate TLS, and load balance. An API Gateway adds application-layer logic: authentication, rate limiting, request/response transformation, service discovery, and policy enforcement. An API Gateway can replace a reverse proxy, but it's often overkill for pure routing; reverse proxies are lighter and faster. In practice, gateways sit behind reverse proxies or replace them when business logic is needed.

AA4 — The Saga pattern manages distributed transactions using a sequence of local transactions, each with a compensating action to undo changes on failure. Choreography-based sagas use events: each service listens and triggers the next step (decentralized, flexible, but hard to trace/debug). Orchestration-based sagas use a central coordinator that directs steps (easier to monitor, version, and handle failures, but introduces a single point of coordination). Use choreography for simple, well-defined workflows; orchestration for complex, long-running, or frequently changing processes.

AA5 — CQRS separates read and write operations into distinct models, allowing independent optimization and scaling. It's paired with Event Sourcing because events naturally feed the read model via projection. This combination solves the CRUD bottleneck where read/write workloads compete for the same schema, provides full auditability, enables temporal queries, and allows read models to be denormalized for high-performance queries without write-side complexity.

AA6 — The Circuit Breaker pattern prevents cascade failures by stopping calls to a failing service. States: Closed (normal traffic), Open (calls fail fast after threshold), Half-Open (allows limited test requests to check recovery). Unlike retry with backoff (which keeps attempting), the CB halts traffic to protect resources. Use both together: retry within the Closed state for transient errors; the CB opens after repeated failures, preventing retry storms and allowing recovery.

AA7 — 
1. Shared DB/Schema: Lowest cost, simplest ops, but highest noisy-neighbor risk, weakest security/isolation, and schema changes affect all tenants.
2. Shared DB/Separate Schema: Moderate cost, better isolation, easier per-tenant backups/migrations, still shares compute/storage limits.
3. Separate DB: Highest security/compliance, eliminates noisy-neighbor, simplifies tenant-specific scaling, but highest cost, complex ops (provisioning, patching, backups), and harder global analytics.
Trade-off: Start with #2 for balance; move to #3 for enterprise/compliance tenants; use #1 only for low-risk, high-volume SaaS.

AA8 — Strong consistency guarantees linearizability (all reads see the latest write). Eventual consistency allows temporary divergence. To prevent overselling: use strong consistency for the reservation path. Architecture: partition inventory by SKU, use a strongly consistent store (PostgreSQL with `SERIALIZABLE` isolation or DynamoDB strong reads), and apply optimistic concurrency control (version columns) or distributed locks (Redis/ZooKeeper) for hot SKUs. At scale, use a dedicated inventory service with synchronous reservation APIs, and decouple downstream fulfillment via async events.

AA9 — A sidecar proxy is a lightweight process co-deployed with an application to handle cross-cutting concerns. In Istio, Envoy runs as the data plane (handles traffic routing, mTLS, retries, observability). Istiod is the control plane (distributes config, manages certs, service discovery). mTLS via sidecars solves: zero application code changes, automatic certificate rotation, consistent policy enforcement across polyglot services, and decouples security from business logic.

AA10 — The Strangler Fig pattern incrementally replaces a monolith by routing traffic to new services via a gateway. Strategy: (1) Identify bounded contexts (e.g., Auth, Billing, Catalog). (2) Deploy .NET 8 microservices for each context. (3) Configure an API Gateway to route specific endpoints to new services, falling back to the monolith. (4) Migrate endpoints gradually, validate parity, and decommission monolith routes. (5) Once all routes are migrated, retire the monolith.

AA11 — 12-Factor App factors (6 examples): 
1. Codebase: One repo per app, deployed multiple times → enables CI/CD and version control.
2. Dependencies: Explicitly declared → ensures reproducible builds.
3. Config: Stored in environment → decouples config from code, enables multi-env parity.
4. Backing services: Treated as attached resources → enables swapping DBs/brokers without code changes.
5. Build/Release/Run: Strict separation → ensures immutable deployments and fast rollbacks.
6. Processes: Stateless, concurrent → enables horizontal scaling and zero-downtime deploys.
These matter for cloud-native because they enforce portability, elasticity, and automated operations.

AA12 — Event-driven (Kafka) vs Request-driven (REST/gRPC):
- Coupling: ED loose (producers/consumers independent), RD tight (caller knows callee).
- Scalability: ED high (async buffering, independent scaling), RD limited by sync call chains.
- Debugging: ED complex (async traces, replay needed), RD straightforward (request/response).
- Ordering: ED partition-level guarantees, RD per-request.
- Failure: ED resilient (replay, dead-letter queues), RD needs retries/CB.
Choose ED for high-throughput pipelines, event sourcing, analytics, or async workflows. Choose RD for simple CRUD, low-latency interactions, or strict synchronous consistency.

AA13 — A load balancer distributes client requests across multiple backend servers. Layer 4 operates at transport layer (IP/port), fast, no content inspection. Layer 7 operates at application layer (HTTP headers, paths, cookies), enables routing, SSL termination, and WAF. L7 is required for path-based routing, header-based routing, or SNI-based SSL termination.

AA14 — A message queue decouples producers and consumers. Queue (RabbitMQ): work distribution, at-least-once delivery, routing/exchanges, ideal for task processing. Log-based broker (Kafka): append-only, durable, replayable, high throughput, ideal for event streaming, analytics, and event sourcing. Pick queues for job processing; Kafka for event-driven architectures and data pipelines.

AA15 — A container packages an application and its dependencies into an isolated user-space environment sharing the host OS kernel. VMs virtualize hardware and run full guest OSes. Containers are popular for microservices because they're lightweight, start in seconds, provide consistent environments across dev/prod, enable high density, and integrate seamlessly with orchestration (Kubernetes) and CI/CD.

AA16 — Stateless services retain no client data between requests; any instance can handle any request, enabling trivial horizontal scaling. Stateful services maintain state (DB, cache, sessions), requiring sticky sessions or distributed state management, complicating scaling. Example stateless: REST API server. Example stateful: PostgreSQL, Redis.

AA17 — An ORM maps object-oriented code to relational database tables. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python), Prisma (Node). Trade-offs: ORMs accelerate development, provide DB abstraction, and reduce boilerplate, but can cause N+1 queries, poor performance for complex joins, and hide SQL. Raw SQL offers full control, optimal performance, and explicit transactions, but is verbose, error-prone, and less portable.

AA18 — The Bulkhead pattern isolates resources to prevent a single failure from exhausting all capacity. In microservices, it partitions thread pools, connection pools, or deployment groups per dependency. Example: Allocate separate thread pools for database calls vs external API calls. If the external API fails, it exhausts its pool, leaving the DB pool intact. In Kubernetes, deploy critical paths as separate pods/deployments with independent resource limits.

AA19 — OT transforms concurrent operations against a base document, requiring a central server, complex logic, and low latency for online use. CRDTs use mathematical structures that guarantee eventual convergence without coordination, supporting offline edits, higher bandwidth/storage, and simpler conflict resolution. For offline support: choose CRDTs (e.g., Yjs, Automerge) because they merge deterministically without a central authority and handle network partitions gracefully.

AA20 — Challenges: Context propagation requires injecting trace IDs (W3C/B3) into headers across all services. Sampling: head-based drops early (saves cost, misses errors), tail-based collects all then filters (higher cost, better visibility). Storage: Jaeger (Elasticsearch), Tempo (S3, high performance). Async messaging breaks trace continuity unless context is embedded in message headers/metadata. For Kafka: producer injects trace ID into message headers; consumer extracts it and continues the span, preserving the distributed trace.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware (ESXi, Proxmox, Hyper-V). Type 2 (hosted) run on a host OS (VirtualBox, VMware Workstation). Type 1 offers better performance and production readiness; Type 2 is for development/testing.

OP2 — SAN provides block-level storage, low latency, high performance, using Fibre Channel or iSCSI. NAS provides file-level storage, network shares, using NFS or SMB. Use SAN for databases, VMs, and high-I/O workloads. Use NAS for file shares, backups, and collaborative storage.

OP3 — 3-tier architecture (core/distribution/access) is hierarchical, creates oversubscription, and has high east-west latency. Leaf-spine is flat, non-blocking, with equal hop counts and high east-west bandwidth. It solves oversubscription and latency bottlenecks for modern cloud/VM workloads that require frequent cross-server communication.

OP4 — Highly available Proxmox cluster: 3+ nodes (odd for quorum). Quorum via Corosync. Fencing via IPMI/SSH. Shared storage: Ceph (recommended for native integration) or iSCSI/NFS. During node failure: Corosync detects loss, fencing isolates the failed node, and VMs with shared storage auto-migrate to surviving nodes. Ceph handles data replication transparently.

OP5 — VLAN trunking carries multiple VLANs over a single link using 802.1Q tags. On Linux with one NIC: create VLAN subinterfaces (`ip link add link eth0 name eth0.10 type vlan id 10`), assign IPs, and configure the switch port as a trunk allowing those VLANs. Traffic is tagged/untagged automatically by the kernel.

OP6 — RAID 1: mirror. RAID 5: single parity (1 drive loss). RAID 6: dual parity (2 drive loss). RAID 10: mirror+stripe. RAID Z2: ZFS dual parity. For 6 drives on a DB server: choose RAID 10 or Z2. RAID 10 offers best read/write performance and survives multiple failures (if not in same mirror), but uses 50% capacity. Z2 offers similar fault tolerance, better space efficiency, and self-healing checksums. I'd choose RAID 10 for raw DB IOPS, or Z2 if data integrity/snapshots are prioritized.

OP7 — DNS architecture: Internal AD-integrated DNS handles recursive resolution and internal authoritative zones. DMZ hosts separate authoritative servers for public zones. Split-horizon: internal resolvers return private IPs for public names; external returns public. DNSSEC: sign external zone, validate on resolvers. Forwarders: internal forwards to ISP/Cloudflare. Conditional forwarding: for partner domains. Laptop on VPN: receives internal DNS via DHCP, resolves internal names seamlessly; off-network uses public DNS.

OP8 — PKI chain: Offline Root CA (self-signed) → Online Subordinate CA (issues certs) → End-entity. CRL: periodic revocation list. OCSP: real-time check. Templates: define key usage, validity, extensions. Auto-enrollment: via AD/GPO. Compromised subordinate CA: revoke sub CA cert, reissue affected certs, limited blast radius. Compromised root CA: catastrophic; must rebuild entire trust chain, revoke all certs, and reissue across all systems.

OP9 — MPLS: reliable, low latency, expensive, complex. IPsec: cheap, variable latency/reliability, complex config. SD-WAN: overlays internet/MPLS, dynamic path selection, QoS for VoIP, moderate cost. WireGuard mesh: fast, simple, lacks centralized policy/QoS. Recommendation: SD-WAN over broadband with optional MPLS fallback for VoIP QoS. Balances cost, performance, and centralized management for latency-sensitive traffic.

OP10 — iDRAC/iLO/IPMI are out-of-band management interfaces for remote power control, console access, and hardware monitoring. Critical when the OS is unresponsive. If exposed to the internet: severe risk of brute force, firmware exploits, and full server compromise. Must be behind a firewall, use strong auth/MFA, keep firmware updated, and restrict access to management VLANs.

OP11 — LVM: block-level, flexible, thick provisioning. LVM-Thin: overprovisioning, efficient snapshots. ZFS: filesystem+volume manager, checksums, compression, native snapshots/replication. Use LVM for standard Linux, Thin for VMs with overcommit, ZFS for data integrity/NAS. Snapshots: LVM (COW, block-level), Thin (COW, space-efficient), ZFS (COW, instant, highly efficient, supports recursive snapshots).

OP12 — Stretch cluster: 2 sites + tiebreaker (3rd site or arbiter). CRUSH rules: replicate across sites, max 1 failure per site. Monitors: 1 per site + tiebreaker. Latency: <2ms RTT for sync replication. Split-brain: quorum prevents; tiebreaker breaks ties. 2-site Ceph without tiebreaker is bad because equal votes cause quorum loss during network partition, leading to split-brain and data corruption.

OP13 — DHCP DORA: Discover, Offer, Request, Acknowledge. When lease expires and server is unavailable: client attempts renewal at 50% (T1), then 87.5% (T2). If both fail, client keeps IP but may lose network access until server returns or lease fully expires (then client stops using IP and may use APIPA).

OP14 — Unmanaged switches: plug-and-play, no configuration. Managed switches: support VLANs, QoS, STP, port mirroring, SNMP, ACLs. Important for enterprise: network segmentation, traffic prioritization, monitoring, security policies, and troubleshooting.

OP15 — NTP synchronizes system clocks. Critical for: Kerberos authentication, log correlation, certificate validation, cluster consensus (Raft/Paxos), and database replication. Clock drift causes: auth failures, split-brain, replication conflicts, audit gaps, and TLS handshake errors.

OP16 — Physical: bare metal, max performance, no virtualization overhead. VM: full OS isolation, heavier. Container: OS-level isolation, lightweight. Run on bare metal when: GPU/PCIe passthrough needed, extreme low latency required, licensing restrictions apply, or hypervisor overhead is unacceptable.

OP17 — UPS provides instant power, bridges gaps (seconds/minutes), protects against surges. Generator provides long-term power, takes time to start. Need both: UPS handles immediate loss, generator kicks in for extended outages. ATS automatically switches between utility and generator power, ensuring seamless transition.

OP18 — Active-passive: one primary, one standby, failover on failure. Active-active: both handle traffic, load balanced. PostgreSQL HA with Pacemaker/Corosync: use streaming replication, virtual IP (VIP) managed by Pacemaker, STONITH (fencing) via IPMI to prevent split-brain, and automatic failover that moves VIP and promotes replica.

OP19 — Backup strategy: 3-2-1 rule (3 copies, 2 media types, 1 offsite). Define RPO/RTO. Types: full (baseline), incremental (since last backup), differential (since last full). Deduplication saves space. Tiered storage: disk for recent, tape/cloud for archive. Immutable backups (WORM) prevent ransomware encryption. Test restores regularly. Backup is data copy; DR is full system/process recovery plan including infrastructure, network, and runbooks.

OP20 — 802.1X roles: Supplicant (client), Authenticator (switch/AP), Authentication Server (RADIUS). EAP-TLS: mutual certificate auth (strongest). PEAP: MSCHAPv2 over TLS tunnel. Dynamic VLAN: RADIUS assigns VLAN based on auth. Failed auth: port moves to unauthorized VLAN or blocked. MAB: fallback using MAC address for legacy/IoT devices that lack 802.1X support; less secure, used as last resort.
