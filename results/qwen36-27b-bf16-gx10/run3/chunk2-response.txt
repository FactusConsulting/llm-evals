## Kubernetes

**K1** — A **Deployment** manages stateless, interchangeable pods with random names, shared storage, and unordered scaling. A **StatefulSet** manages stateful workloads, providing stable network identities (e.g., `web-0`, `web-1`), ordered deployment/scaling/deletion, and persistent storage that persists across pod rescheduling.

**K2** — A `ClusterIP` Service creates a virtual IP within the cluster. `kube-proxy` watches the Service and its Endpoints, then programs `iptables` or `IPVS` rules on each node. When traffic hits the ClusterIP, these rules NAT/route the packet to one of the backing pod IPs (typically round-robin or least-conn).

**K3** — A **PersistentVolume (PV)** is a cluster-level storage resource (actual disk). A **PersistentVolumeClaim (PVC)** is a user/pod request for storage capacity and access modes. A **StorageClass** defines dynamic provisioning parameters (provisioner, reclaim policy, parameters). Relation: A PVC either binds to an existing PV (static) or triggers a StorageClass to dynamically create a matching PV. Pods mount the PVC.

**K4** — 1. `kubectl logs <pod> --previous` to check crash cause. 2. Inspect events (`kubectl describe pod`) for `OOMKilled`, probe failures, or mount errors. 3. Verify config/env/secrets and dependency connectivity (DB, APIs). 4. Check resource requests/limits and node capacity. 5. Validate liveness/readiness probe thresholds and startup delays.

**K5** — CoreDNS provides cluster-internal DNS resolution, mapping service names to ClusterIPs and forwarding external queries to upstream DNS. If CoreDNS pods are down, internal service discovery fails, and external DNS resolution fails (unless pods have custom `dnsConfig`), causing widespread connectivity issues.

**K6** — The scheduler runs in two phases: **Filtering** (predicate) removes nodes that violate hard constraints (insufficient resources, taints without tolerations, node/pod affinity violations, volume node affinity, PDB limits). **Scoring** (priority) ranks remaining nodes using weighted algorithms. Key factors: least requested resources, balanced resource allocation, image locality, inter-pod affinity/anti-affinity, and topology spread constraints.

**K7** — Yes, it will be scheduled. The node has 4GB total, 3.5GB requested; adding 256Mi leaves ~1.25GB free, satisfying the request. At runtime, if the pod exceeds its 512Mi limit (uses 600Mi), the kernel cgroup triggers an OOM kill. `kubelet` marks the container `OOMKilled`, and the pod restarts (likely entering `CrashLoopBackOff`).

**K8** — Client → Cloud External LB (routes to ingress controller nodes) → NGINX Ingress Controller pod (terminates TLS, matches host/path rules) → Routes to target `ClusterIP` Service → `kube-proxy`/`iptables` or `IPVS` rules on the node → Resolves to `Endpoints` (matching pod IPs) → Application pod. The ingress controller handles rate limiting, retries, and header rewriting before forwarding.

**K9** — A `NetworkPolicy` is a L3/L4 firewall that controls pod-to-pod and pod-to-external traffic using labels. Default behavior (if no policies exist): allow all ingress and egress. When a policy is applied to a namespace, it only affects selected pods; unselected pods remain unaffected. Selected pods only allow traffic explicitly permitted by the policy.

**K10** — `RollingUpdate` gradually replaces old pods with new ones, maintaining availability via `maxSurge` and `maxUnavailable`. `Recreate` terminates all old pods before creating new ones, causing downtime. Choose `Recreate` for database migrations, schema changes, or when old/new versions cannot coexist or share state safely.

**K11** — A namespace is a logical partition for isolating resources and applying RBAC/quota policies. Default namespaces: `default` (user workloads), `kube-system` (cluster components), `kube-public` (publicly readable resources), `kube-node-lease` (node heartbeat/lease objects).

**K12** — `kubectl describe pod` shows detailed runtime state. Three pieces `get` doesn't show: 1. Events (scheduling, pull, probe failures). 2. Container conditions & restart counts. 3. Volume mounts, node assignment, QoS class, and exact resource requests/limits.

**K13** — A `ConfigMap` stores non-confidential configuration data as key-value pairs. Consumption methods: 1. Environment variables (`env` or `envFrom`). 2. Volume mounts (exposed as files in the container filesystem). 3. Command-line arguments via `args` referencing keys.

**K14** — `ClusterIP`: internal-only virtual IP. `NodePort`: exposes service on a static port across all node IPs, routes to ClusterIP. `LoadBalancer`: provisions a cloud provider external LB, maps to NodePort/ClusterIP, and provides a public IP.

**K15** — A `DaemonSet` ensures exactly one pod runs on each node (or a subset via node selectors). Use it for node-level agents: log collectors (Fluentd), monitoring (Node Exporter), network plugins (Calico), or storage drivers. Unlike Deployments (fixed replica count), DaemonSets auto-scale with node count.

**K16** — **Taints/Tolerations** repel pods; tolerations allow scheduling despite taints. **Node Affinity** attracts pods to nodes matching labels. Taints are "hard" exclusions (e.g., `dedicated=debug:NoSchedule` for debug nodes). Affinity is preference or hard requirement (e.g., `preferredDuringScheduling` for cache co-location, `requiredDuringScheduling` for zone constraints).

**K17** — An **Operator** extends the Kubernetes API with Custom Resource Definitions (CRDs) and a custom controller that encodes operational knowledge. Unlike standard controllers (which manage built-in resources), Operators manage complex stateful applications (databases, caches) by automating lifecycle tasks: backups, upgrades, failover, and scaling. Solves manual ops, reduces human error, and enables GitOps for complex apps.

**K18** — etcd uses **Raft** for strong linearizable consistency. If quorum is lost, the cluster becomes read/write unavailable to prevent split-brain. Recovery from 2/3 lost: 1. Stop `kube-apiserver` on surviving node. 2. Restore etcd from a recent snapshot (`etcdctl snapshot restore`). 3. Start etcd as a new single-node cluster. 4. Restart `apiserver`, verify cluster health, then rejoin remaining nodes or rebuild. Without a snapshot, data is unrecoverable.

**K19** — RBAC grants permissions via `Role`/`ClusterRole` (permissions) bound to subjects via `RoleBinding`/`ClusterRoleBinding`. Roles are namespace-scoped; ClusterRoles are cluster-wide. Bindings map roles to users/groups/service accounts.
Manifest for dev read-only pods/logs in `dev-ns`:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev-ns
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader-binding
  namespace: dev-ns
subjects:
- kind: User
  name: dev-user@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — Default `ndots:5` in `/etc/resolv.conf` causes the resolver to append up to 5 search domains to short names before trying the literal FQDN, generating excessive DNS queries for external domains. Fix: set `ndots` to `1` via pod `dnsConfig`:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "1"
```

## Development

**D1** — `git merge` creates a new merge commit preserving branch history. `git rebase` rewrites history by replaying commits onto the target branch, creating a linear history. Avoid rebasing on shared/public branches because it rewrites commit hashes, causing conflicts and confusion for collaborators.

**D2** — **TCP**: connection-oriented, reliable, ordered, flow/congestion control. Protocols: HTTP, SSH. **UDP**: connectionless, unreliable, unordered, low latency. Protocols: DNS, RTP (video streaming).

**D3** — A race condition occurs when concurrent threads/processes access shared state without synchronization, and the outcome depends on execution timing. Example (Python):
```python
counter = 0
def increment():
    global counter
    for _ in range(100000):
        counter += 1  # Read-modify-write is not atomic
```
Two threads running `increment()` may yield `counter < 200000` due to lost updates.

**D4** — **Symmetric**: same key for encryption/decryption, fast (AES). **Asymmetric**: public/private key pair, slower, enables secure key exchange & signatures (RSA/ECC). In TLS: asymmetric cryptography authenticates the server (and optionally client) and negotiates a session key; symmetric cryptography then encrypts the actual data transfer for performance.

**D5** — An image layer is a read-only filesystem snapshot created by each `Dockerfile` instruction. Layer caching reuses unchanged layers, speeding up builds. Best practices: order instructions by change frequency (install deps first, copy code last), combine related commands to reduce layers, and use multi-stage builds to discard build tools.

**D6** — 1. Check application logs & metrics for errors, panics, or connection pool exhaustion. 2. Verify backend/upstream health, connectivity, and response times. 3. Inspect load balancer/proxy configuration, health check endpoints, and rate limits. 4. Review resource constraints (CPU throttling, memory limits, file descriptors) and circuit breaker states.

**D7** — **CAP theorem**: In a distributed system, you can only guarantee two of Consistency, Availability, Partition tolerance. **CP example**: etcd/ZooKeeper (strong consistency; becomes unavailable during network partitions). **AP example**: Cassandra/DynamoDB (always available; may return stale data during partitions, converges later).

**D8** — **Vertical scaling**: upgrading a single node's resources (CPU/RAM). **Horizontal scaling**: adding more nodes/instances. Horizontal scaling is enabled by: stateless application design, load balancers, distributed data stores, message queues, and container orchestration (Kubernetes).

**D9** — An environment variable is a dynamic key-value pair in a process's execution environment. To persist across Linux shell sessions: add `export VAR_NAME=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

**D10** — **JSON**: strict, machine-optimized, single document, no comments. **YAML**: human-readable, supports comments, multi-document, complex types. JSON advantage: strict parsing, universal language support. YAML advantage: readability, comments, anchors/aliases for DRY configs.

**D11** — A REST API uses HTTP methods to manipulate resources. `GET`: retrieve (safe, idempotent). `POST`: create (not idempotent). `PUT`: update/replace entire resource (idempotent). `DELETE`: remove resource (idempotent).

**D12** — Version pinning locks dependencies to exact versions (e.g., `==1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes from upstream updates, and guarantees identical environments across development, staging, and production.

**D13** — **Compiled**: translated to machine code before execution (C, Rust). Faster, platform-specific binaries. **Interpreted**: executed line-by-line by a runtime/VM (Python, JavaScript). Portable, dynamic, easier debugging, but slower startup/runtime.

**D14** — A **reverse proxy** sits behind servers, forwarding client requests to backends (load balancing, TLS termination, caching). A **forward proxy** sits in front of clients, forwarding their requests to the internet (anonymity, filtering). Examples: Nginx (reverse proxy for web apps), Squid (forward proxy for corporate internet access).

**D15** — A deadlock occurs when two or more processes wait indefinitely for each other's resources. **Coffman conditions**: 1. Mutual exclusion. 2. Hold and wait. 3. No preemption. 4. Circular wait. All four must hold simultaneously.

**D16** — **Eventual consistency**: data will converge to a consistent state over time without further writes. Cassandra handles read-after-write via tunable consistency levels (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`, `EACH_QUORUM`). Using `QUORUM` for both reads and writes guarantees read-after-write consistency. For strong consistency, use Lightweight Transactions (LWT) with `SELECT ... IF`.

**D17** — **mTLS** requires both client and server to present and verify certificates. Handshake: 1. ClientHello → 2. ServerHello + ServerCert → 3. Client verifies server cert → 4. ClientCert + signature → 5. Server verifies client cert → 6. Key exchange → 7. Encrypted channel. Commonly used in service meshes (Istio), internal microservices, zero-trust architectures, and API gateways.

**D18** — A hash table uses an array and a hash function to map keys to indices. **Collision resolution**: Chaining stores colliding keys in linked lists at each bucket. Open addressing probes subsequent slots (linear/quadratic probing) until an empty slot is found. **Time complexity**: Average O(1) for insert/lookup/delete. Worst O(n) when all keys hash to the same bucket or table is full.

**D19** — A **circuit breaker** prevents cascade failures by stopping calls to a failing service. **States**: Closed (normal, tracks failures), Open (fails fast, blocks calls, waits timeout), Half-Open (allows limited test requests; success → Closed, failure → Open). Relates to retry/backoff: retries only occur in Closed/Half-Open states; exponential backoff prevents thundering herds when transitioning from Open to Half-Open.

**D20** — **Pessimistic concurrency** assumes conflicts are likely and locks data on access (`SELECT ... FOR UPDATE`). Best for high-contention, critical data (e.g., bank transfers). **Optimistic concurrency** assumes conflicts are rare, uses no locks, and validates version/timestamp on commit (row versioning). Best for read-heavy, low-contention workloads (e.g., e-commerce carts). Example: Optimistic uses `UPDATE items SET qty=qty-1, version=version+1 WHERE id=1 AND version=5`; if 0 rows updated, retry.
