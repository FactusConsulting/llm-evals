DN1 — Classes are reference types allocated on the heap, support inheritance, and can be null. Structs are value types allocated inline/stack, support only interface implementation, and are immutable by convention. Use structs for small (<16 bytes), immutable data representing a single value (e.g., `Point`, `DateTime`, `Complex`) to reduce GC pressure and improve CPU cache locality. Avoid if polymorphism or large size is needed.

DN2 — `IEnumerable<T>` executes LINQ in-memory using C# iterators. `IQueryable<T>` builds expression trees that providers (e.g., EF Core) translate to SQL. The distinction matters because `IQueryable` pushes filtering, projection, and pagination to the database, minimizing network transfer and memory usage. `IEnumerable` pulls all data first, then filters client-side, causing performance bottlenecks at scale.

DN3 — `async/await` compiles to a state machine that yields control when awaiting, resuming on a captured context. `Task` is a reference type representing an async operation, always heap-allocated. `ValueTask` is a struct that wraps either a completed result or a `Task`, avoiding allocation when operations complete synchronously. Use `ValueTask` in high-frequency, low-latency APIs (e.g., caching, I/O with pre-allocated buffers) where sync completion is common.

DN4 — DI manages object creation and dependency resolution. Lifetimes: `Transient` (new per injection), `Scoped` (new per request/scope), `Singleton` (one per app). Bug: Captive Dependency. Injecting a `Scoped` service into a `Singleton` causes the scoped service to live as long as the singleton, breaking scope boundaries (e.g., `DbContext` becomes app-wide, causing concurrency/state corruption). Fix: Use `IServiceScopeFactory` inside the singleton to create explicit scopes, or align lifetimes correctly.

DN5 — `string` is immutable, heap-allocated, and GC-managed. `ReadOnlySpan<char>` is a stack-only struct providing a zero-allocation view into memory (strings, arrays, `stackalloc`). `Span<T>` is the mutable variant. Use `Span<T>` for high-performance slicing, parsing, or I/O to avoid allocations and improve cache locality. Cannot be used in `async` methods or stored in fields due to stack-only constraints.

DN6 — The GC uses mark-sweep-compact to reclaim unused heap memory. Generations: Gen 0 (short-lived, frequent collection), Gen 1 (buffer), Gen 2 (long-lived, infrequent). LOH stores objects >85KB, isn't compacted by default (causes fragmentation), and collects with Gen 2. `IDisposable` enables deterministic cleanup of unmanaged resources (files, DB connections, handles). The GC is non-deterministic; `IDisposable` ensures timely release via `using` or explicit `Dispose()`.

DN7 — Default `await` captures the current `SynchronizationContext` (e.g., UI thread, ASP.NET request context) and resumes on it. `ConfigureAwait(false)` skips capture, resuming on a thread pool thread. Use it in library code to avoid deadlocks and improve performance. Avoid in app/UI code where you need context-specific state (e.g., `HttpContext`, UI controls). It directly controls post-back behavior relative to the captured context.

DN8 — Primary constructors (C# 12) declare parameters in the type signature, accessible in the body. Collection expressions (`[1, 2, ..arr]`) unify array/list syntax. `FrozenDictionary` is an immutable, highly optimized dictionary with zero-allocation lookups. Example:
```csharp
public class UserService(IUserRepository repo, ILogger<UserService> log)
{
    public Task<User> GetByIdAsync(int id) => repo.GetByIdAsync(id);
}
// DI: builder.Services.AddScoped<UserService>();
```

DN9 — Likely cause: `DbContext` is being cached, reused across requests, or registered as `Singleton` instead of `Scoped`. EF Core's `DbContext` is not thread-safe and is designed for short-lived scopes. Fix: Ensure `AddDbContext<T>()` (Scoped by default) is used. Never cache `DbContext` instances. In background services, use `IServiceScopeFactory` to create per-operation scopes. Ensure async methods don't capture `DbContext` beyond request lifetime.

DN10 — `record` is a reference type with value-based equality, immutability by default, and auto-generated `with`/`Equals`/`ToString`. `record struct` is the value-type equivalent. Use `record` for DTOs, domain models, and immutable data. Use `class` for mutable state, identity-based equality, or complex behavior. Use `record struct` for small, high-performance immutable data to avoid heap allocation.

DN11 — `ref`: passed by reference, must be initialized before call, read/write. `out`: passed by reference, need not be initialized before call, must be assigned in method. `in`: passed by reference but read-only, avoids copying large structs. Use `ref` for in/out parameters, `out` for multiple return values, `in` for performance with large structs.

DN12 — `int?` (`Nullable<T>`) is a runtime value-type wrapper that can hold a value or null. `string?` (nullable reference type) is a compiler-only feature (C# 8+) enabling null-state tracking via flow analysis, with zero runtime overhead. `#nullable enable` activates analysis. Reference types are nullable at runtime; NRTs add compile-time safety without changing IL.

DN13 — LINQ provides unified querying for collections/DBs. Method syntax uses fluent extension methods (`Where`, `Select`). Query syntax uses SQL-like keywords (`from x in list where ...`). The compiler translates query syntax to method syntax. Deferred execution means the query isn't executed until enumerated (`foreach`, `ToList()`), enabling composition and lazy evaluation.

DN14 — Constraints restrict generic type parameters: `class` (reference type), `struct` (non-nullable value type), `new()` (parameterless constructor), `IComparable<T>` (implements interface). Combine to enable operations: `where T : class, IComparable<T>, new()` ensures T is a reference type, comparable, and instantiable. Multiple constraints are comma-separated and evaluated together.

DN15 — Abstract classes support single inheritance, state, constructors, and partial implementation. Interfaces support multiple inheritance and historically had no implementation. C# 8+ default interface methods allow implementation in interfaces, enabling backward-compatible evolution. Prefer abstract classes for shared state/behavior hierarchies; interfaces for contracts/capabilities. Default methods blur the line but don't replace inheritance semantics.

DN16 — Middleware pipeline executes delegates sequentially per request. `Use` continues to next middleware. `Map` branches on request path. `Run` is terminal, stops pipeline. Ordering matters: first registered runs first on request, last on response. Exception handling middleware (e.g., `UseExceptionHandler`) must be early to wrap downstream middleware in try/catch, catching and transforming errors before they bubble up.

DN17 — `Channel<T>` is async, lock-free, designed for async producer-consumer patterns with cancellation support. `BlockingCollection<T>` is sync, lock-based, older. Bounded channel example:
```csharp
var ch = Channel.CreateBounded<int>(new BoundedChannelOptions(100) { FullMode = BoundedChannelFullMode.Wait });
// Producer: await ch.Writer.WriteAsync(item);
// Consumer: while (await ch.Reader.WaitToReadAsync()) while (ch.Reader.TryRead(out var item)) { }
```
Provides backpressure by blocking/writing when full, preventing memory exhaustion.

DN18 — Source Generators produce C# source files at compile time, adding zero runtime overhead. Unlike reflection (runtime, slow) or IL weaving (post-compile, complex), generators integrate directly into compilation. Incremental generators (`IIncrementalGenerator`) cache results and only re-run on changed inputs, drastically improving build times vs `ISourceGenerator` (runs every build). Preferred for performance and IDE integration.

DN19 — TPL Dataflow provides block-based pipelines: `ActionBlock` processes items, `TransformBlock` maps input to output, `BufferBlock` stores items. Rich features: fan-in/out, ordering, buffering, error handling. `Channels` are simpler, async-first, lower overhead, better for high-throughput producer-consumer. Use Dataflow for complex workflows; Channels for simple async pipelines.

DN20 — Minimal APIs use delegate-based routing (`app.MapGet(...)`) with less boilerplate. Controllers are class-based with attribute routing and richer conventions. Trade-offs: Minimal APIs are lighter but harder to test/mock without DI setup, and require explicit OpenAPI/Swagger configuration. Route groups (`MapGroup()`) organize endpoints. Endpoint filters (`IEndpointFilter`) handle cross-cutting concerns (auth, validation) without middleware complexity.

P1 — Lists are mutable, ordered, allow duplicates. Tuples are immutable, ordered, hashable (if contents are). Sets are mutable, unordered, unique. Frozensets are immutable sets, hashable, usable as dict keys. Use tuples for fixed collections, lists for dynamic sequences, sets for membership testing/deduplication.

P2 — The GIL is a mutex protecting Python object access, allowing only one thread to execute bytecode at a time. It affects CPU-bound multithreaded code (no true parallelism). Workarounds: `multiprocessing`/`ProcessPoolExecutor` for CPU work, `asyncio` for I/O-bound work, C extensions that release the GIL, or offloading to Rust/C via bindings.

P3 — `copy.copy()` creates a shallow copy: new container, but nested objects are shared references. `copy.deepcopy()` recursively duplicates all nested objects. Example: `a = [1, [2, 3]]; b = copy.copy(a); b[1].append(4); print(a)` → `[1, [2, 3, 4]]` (unexpected mutation). `deepcopy` prevents this by duplicating nested structures.

P4 — Decorators modify/extend function behavior using `@` syntax. Timing decorator:
```python
import time, functools
def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — Generators use `yield` to return an iterator, computing values lazily and saving memory. Unlike lists, they don't materialize all items upfront. `yield from` delegates to another generator/iterable, simplifying nested iteration and automatically forwarding `send()`/`throw()`/`close()`.

P6 — The asyncio event loop is a single-threaded scheduler managing coroutines, I/O, and timers. `asyncio.run()` creates/runs the loop (top-level entry). `asyncio.gather()` runs multiple coroutines concurrently, awaiting all. `asyncio.create_task()` schedules a coroutine, returning a `Task`. `time.sleep()` blocks the thread, starving the loop; use `await asyncio.sleep()` instead.

P7 — MRO defines method lookup order. Python 3 uses C3 linearization (consistent, monotonic). For `D(B, C)`, MRO is `(D, B, C, A)`. `B` doesn't override `who`, so lookup continues to `C`, which defines it. `D().who()` prints `"C"`. C3 ensures predictable resolution even in complex diamond hierarchies.

P8 — Metaclasses control class creation (`__new__`, `__init__`). `__init_subclass__` is a class method called when a subclass is created, simpler and preferred for most cases. Use `__init_subclass__` for registration, validation, or modifying subclass attributes. Use metaclasses for complex creation logic, overriding `__new__`, or intercepting class creation before `__init_subclass__` runs. Example: `__init_subclass__` for plugin registries; metaclass for ORM model introspection.

P9 — Threading shares memory, GIL-limited, ideal for I/O. Multiprocessing uses separate processes, true parallelism, ideal for CPU. `concurrent.futures` provides high-level wrappers (`ThreadPoolExecutor`, `ProcessPoolExecutor`). Multiprocessing serializes args/results via pickle; objects must be picklable, can't share live state, and large objects cause overhead. Use futures for simplicity, threading for I/O, multiprocessing for CPU.

P10 — `__slots__` declares allowed instance attributes, replacing the per-instance `__dict__`. Prevents dynamic attribute assignment, saves ~40-50% memory, and speeds up attribute access. Use for millions of instances of simple data objects. Trade-offs: breaks some pickling scenarios, prevents `__weakref__` unless explicitly declared, and reduces flexibility.

P11 — Virtual environments isolate Python installations and packages, preventing dependency conflicts. `venv` is stdlib, basic. `virtualenv` is third-party, faster, more features. `conda` manages cross-language dependencies, environments, and packages. Use `venv` for pure Python projects; `conda` for data science/C++ dependencies.

P12 — Comprehensions (`[x for x in ...]`, `{k:v for ...}`, `{x for ...}`) are readable, Pythonic, and support inline conditionals. `map()`/`filter()` apply functions, return iterators, and are functional. Prefer comprehensions for readability and complex transformations; `map`/`filter` for simple function application or when chaining with existing iterators.

P13 — `==` checks value equality. `is` checks identity (same object in memory). Interning caches small integers (-5 to 256) and some strings for performance. `a is b` returns `True` for small ints because they reference the same cached object. Never use `is` for value comparison except `None`.

P14 — `*args` packs positional args into a tuple. `**kwargs` packs keyword args into a dict. `/` marks parameters as positional-only (left of `/`). `*` marks remaining parameters as keyword-only (right of `*`). Example: `def f(a, /, b, *, c):` → `a` positional-only, `b` either, `c` keyword-only.

P15 — Context managers manage setup/teardown via `with`. `__enter__`/`__exit__` are class-based; `__exit__` handles exceptions. `@contextmanager` is a decorator for generator-based managers using `yield`. Example:
```python
from contextlib import contextmanager
@contextmanager
def hold_lock(lock):
    lock.acquire()
    try: yield
    finally: lock.release()
```
Use for DB transactions, locks, or temporary resources.

P16 — Type hints annotate variables/functions for static analysis. `Union[A,B]`/`A|B`: multiple types. `Optional[T]` = `T|None`. `Literal`: exact values. `TypeVar`: generics. `Protocol`: structural subtyping (duck typing). `mypy`/`pyright` analyze code statically, catch type errors before runtime, and enable IDE autocomplete/refactoring without execution.

P17 — Data model dunder methods define object behavior. `__repr__`: unambiguous/dev-focused. `__str__`: readable/user-focused. `__eq__`: equality. `__hash__`: hash for dicts/sets. If `__eq__` is defined without `__hash__`, `__hash__` becomes `None`, making the object unhashable. `__getattr__` handles missing attributes; `__getattribute__` intercepts all attribute access (use cautiously).

P18 — Descriptors implement `__get__`, `__set__`, `__delete__` to control attribute access. `property` is a data descriptor (has `__set__`), intercepting access. `classmethod`/`staticmethod` are non-data descriptors (only `__get__`), returning bound methods or functions. Used for validation, lazy loading, or custom attribute behavior.

P19 — Import system locates/loads modules. Absolute: `import pkg.mod`. Relative: `from . import mod`. `sys.path`: search paths. `PYTHONPATH`: env var prepended to `sys.path`. `__init__.py`: marks regular packages (optional in 3.3+ for namespace packages). Namespace packages split across directories without `__init__.py`. Finders locate modules; loaders execute/load code. `importlib` orchestrates this.

P20 — `dataclasses` auto-generate `__init__`, `__repr__`, etc. `__post_init__` runs after `__init__`. Field factories: `default_factory=list`. `frozen=True` makes immutable. Inheritance merges fields; `__post_init__` calls parent. `attrs` is older, faster, more features. `Pydantic` adds validation, serialization, JSON schema, strict typing. Choose Pydantic for APIs/configs needing validation; dataclasses for internal data structures.
