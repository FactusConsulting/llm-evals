T1 — `tofu plan` generates an execution plan by comparing your configuration to the current state and remote infrastructure, showing what will be created, modified, or destroyed without making changes. `tofu apply` executes that plan, making the actual API calls to provision or modify resources.

T2 — State is a JSON file that maps your OpenTofu configuration to real-world infrastructure, tracking resource IDs, attributes, and dependencies. Remote state is important for team collaboration, state locking (preventing concurrent writes), versioning/audit trails, and security (encrypting sensitive data at rest).

T3 — `count` creates resources based on an integer index, while `for_each` creates resources based on map or set keys. `for_each` is preferred because it provides stable resource addresses (keys don't shift when items are removed), allows independent lifecycle management per resource, and avoids index-based drift issues.

T4 — Manual changes cause configuration drift. `tofu plan` detects it by querying the provider API and comparing the live state to the recorded state file. OpenTofu will show the drift in the plan output. Running `tofu apply` will revert the resource to the desired configuration (or update state if you use `tofu refresh`/`import` to accept the drift).

T5 — 
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  tags = { Name = each.value }
}
```

T6 — `terraform_remote_state` reads another state file directly, creating tight coupling, bypassing module validation, and exposing sensitive state data. Outputs are designed for explicit, validated data sharing between modules. The recommended alternative is to pass outputs through the parent module hierarchy or use a centralized configuration management approach. If cross-workspace sharing is unavoidable, use `data "terraform_remote_state"` sparingly with strict access controls, but prefer restructuring modules to eliminate direct state dependencies.

T7 — Provisioners run after resource creation, but outputs are evaluated during the apply graph before provisioners complete. You cannot reference provisioner results in outputs. Fix: Use `local-exec` to write the kubeconfig to a file, then read it with `file("${path.module}/kubeconfig")`, or better, use a provider that natively exposes kubeconfig (e.g., `kubernetes` provider or cloud provider's managed service). If using `null_resource`, add `depends_on` and use `local_file` + `file()` to bridge the evaluation gap.

T8 — `tofu import` maps existing infrastructure to the state file without generating configuration. Limitations: requires exact resource address, doesn't create config, can fail on complex/nested resources, and is CLI-only. The `import` block (1.5+) improves this by allowing declarative imports in code, running during `tofu apply`, and supporting `-generate-config` to auto-create matching resource blocks.

T9 — A variable is a configurable value. Input variables (`variable` block) accept values from CLI, env vars, or variable files. Outputs (`output` block) expose computed values or resource attributes from your configuration to users or parent modules. Inputs go in; outputs come out.

T10 — A provider is a plugin that implements API interactions for a specific cloud, SaaS, or infrastructure platform. Running `tofu plan` without `tofu init` fails because providers aren't downloaded or initialized; OpenTofu will throw a "provider not found" or "plugin not installed" error.

T11 — `.terraform.lock.hcl` pins exact provider versions and SHA256 checksums. It ensures reproducible builds, prevents supply-chain attacks, and guarantees all team members/CI pipelines use identical provider binaries. It should always be committed to VCS.

T12 — `tofu destroy` removes all resources managed in the current state. To target a single resource: `tofu destroy -target=aws_instance.web`. Note: dependent resources may also be destroyed or left dangling; use with caution.

T13 — A data source reads existing external data without managing it. Example: `data "aws_ami" "ubuntu" { most_recent = true }` to fetch the latest Ubuntu AMI ID instead of creating or managing an AMI resource.

T14 — `locals` compute derived values within a module and cannot be overridden externally. `variable` blocks define configurable inputs. Use `locals` for complex expressions, internal constants, or to avoid repetition (e.g., `locals { common_tags = merge(var.default_tags, { Environment = var.env }) }`).

T15 — `lifecycle` controls resource behavior:
- `create_before_destroy = true`: Creates replacement before deleting old (zero-downtime deployments).
- `prevent_destroy = true`: Blocks accidental deletion (safety for critical DBs).
- `ignore_changes = [tags]`: Ignores drift on specified attributes (e.g., auto-scaling groups that modify tags).

T16 — `moved` declaratively tracks resource or module renames/moves in state. It maps old addresses to new ones, preventing destroy/recreate during refactoring. Example: `moved { from = aws_instance.old to = aws_instance.new }`.

T17 — OpenTofu builds a Directed Acyclic Graph (DAG) of resources. Implicit dependencies come from direct attribute references (`resource.a.id`). Explicit dependencies use `depends_on`. `depends_on` forces ordering, reduces parallelism, and should be used sparingly (only for side effects, external triggers, or when implicit references can't be expressed) to maintain apply speed.

T18 — Strategies to reduce plan time:
1. `tofu plan -refresh=false`: Skips API calls to verify state. Tradeoff: risk of undetected drift.
2. Split into smaller modules/workspaces: Reduces state size and graph complexity. Tradeoff: increased operational overhead and cross-module coordination.
3. Use `tofu plan -target`: Plan only changed resources. Tradeoff: manual management, risk of missing implicit dependencies.
4. Optimize provider caching & hardware: Use `TF_PLUGIN_CACHE_DIR`, upgrade CI runners. Tradeoff: infrastructure cost, setup complexity.

T19 — State locking prevents concurrent modifications (e.g., DynamoDB for S3 backend). If a lock isn't released (CI crash), subsequent runs fail. Manually break with `tofu force-unlock <LOCK_ID>`. Risks: state corruption, split-brain, inconsistent infrastructure if another process was actually writing. Always verify no active applies are running before forcing.

T20 — Migration steps:
1. Backup current state: `cp terraform.tfstate terraform.tfstate.bak`
2. Update config with new backend block (S3 + DynamoDB)
3. Run `tofu init -migrate-state` (confirms migration)
4. Verify: `tofu plan` should show no changes
5. Commit new backend config to VCS
The existing state file is copied to S3, DynamoDB table is created for locking, and local state is removed. Verify by checking S3 bucket contents and running a dry-run plan.

A1 — Playbook: YAML file containing plays (target hosts + tasks). Role: reusable directory structure bundling tasks, vars, templates, handlers, etc. Task: single action calling a module (e.g., `apt`, `copy`).

A2 — `ansible_facts` is a dictionary of auto-collected system information. Access OS family: `{{ ansible_os_family }}`.

A3 — `command`: runs binary directly, no shell parsing (safe, predictable). `shell`: runs via `/bin/sh`, supports pipes, redirection, loops. `raw`: sends command directly over SSH, bypasses module overhead. Use `command` for safety, `shell` for complex commands, `raw` for non-standard targets or maximum speed.

A4 — Ansible ensures idempotency by designing modules to check current state before acting. Idempotent: `apt: name=htop state=present` (skips if installed). Not idempotent: `command: echo "log" >> /var/log/app.log` (appends every run).

A5 — 
```yaml
- name: Install htop and epel-release based on OS
  package:
    name: "{{ item }}"
    state: present
  loop: "{{ ['htop'] + (['epel-release'] if ansible_os_family == 'RedHat' else []) }}"
```

A6 — Precedence (highest to lowest): extra_vars > set_fact > role defaults > inventory vars (host_vars > group_vars) > host facts > registered vars > play vars > block vars > task vars > include vars. `extra_vars` always wins; `role defaults` are lowest priority for role variables.

A7 — Structure:
```yaml
- hosts: rke2_agents
  serial: 3  # First batch
  tasks:
    - name: Install & start agent
      ...
    - name: Wait for agent ready
      uri:
        url: "https://localhost:9345/healthz"
        validate_certs: no
      register: health
      until: health.status == 200
      retries: 30
      delay: 5

- hosts: rke2_agents
  serial: 10  # Remaining nodes
  tasks:
    - name: Install & start agent
      ...
```
Use inventory groups `[rke2_init]` and `[rke2_agents]` for logical separation. `wait_for`/`uri` ensures cluster readiness before next batch.

A8 — `ansible-vault` encrypts files/variables. Encrypt a single variable: `ansible-vault encrypt_string 'my_secret' --name 'db_password'` outputs a `!vault` block. Paste it into your vars file. The rest of the file remains plaintext.

A9 — Inventory defines target hosts and groups. Static: YAML/INI file manually maintained. Dynamic: script/plugin (e.g., AWS, Azure) that queries APIs to generate inventory on-the-fly, ideal for auto-scaling/cloud environments.

A10 — `ansible webservers -a "df -h"` or `ansible webservers -m command -a "df -h"`

A11 — A handler is a task that runs only when explicitly notified by another task. It runs once at the end of the play, regardless of how many times notified. Trigger: `notify: restart nginx` in a task.

A12 — `ansible.cfg` configures Ansible behavior. Common settings: `host_key_checking = False`, `forks = 20`, `remote_user = deploy`, `private_key_file = ~/.ssh/id_rsa`, `log_path = /var/log/ansible.log`, `retry_files_enabled = False`.

A13 — `register` captures task output (stdout, rc, stderr) into a variable. Use: `{{ my_var.stdout }}` or `{{ my_var.rc }}` in subsequent tasks. Example: `shell: uptime | register: up | debug: var=up.stdout`

A14 — `import_tasks` is static (parsed at compile time), faster, but `when` on the import itself doesn't work. `include_tasks` is dynamic (evaluated at runtime), supports conditionals/loops on the include, but slightly slower. Use `import` for static/reusable tasks, `include` for dynamic behavior.

A15 — Ansible Galaxy is a hub for community roles/collections. Use `requirements.yml` to list dependencies:
```yaml
roles:
  - name: geerlingguy.docker
collections:
  - name: amazon.aws
```
Install: `ansible-galaxy install -r requirements.yml`

A16 — Connection plugins define how Ansible reaches targets. `ssh`: default, uses SSH keys/passwords. `local`: runs on control node. `network_cli`: for network devices (Cisco/Juniper) using persistent SSH + CLI parsing. Use `ssh` for servers, `local` for control-node tasks, `network_cli` for switches/routers.

A17 — `delegate_to` runs a task on a specific host instead of the target. `run_once` runs it once across all hosts in the play. Example:
```yaml
- name: Gather remote IP
  debug: var=ansible_host
  register: remote_ip

- name: Update DNS record
  delegate_to: localhost
  run_once: true
  community.aws.route53:
    zone: example.com
    record: app.example.com
    type: A
    value: "{{ remote_ip.stdout }}"
```

A18 — Performance strategies:
1. Increase `forks`: Parallelizes host execution. Tradeoff: control node CPU/memory, target SSH limits.
2. Enable `pipelining`: Reduces SSH round-trips. Tradeoff: requires `requiretty` disabled in sudoers.
3. Fact caching (`redis`/`jsonfile`): Skips fact gathering on reruns. Tradeoff: stale facts, cache maintenance.
4. Use `mitogen`: Replaces SSH with high-performance RPC. Tradeoff: compatibility quirks, extra dependency.

A19 — Jinja2: `{{ }}` expressions (output values), `{% %}` statements (logic/loops), `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backends %}
    server {{ server.ip }}:{{ server.port }}; # health_check: {{ server.health }}
{% endfor %}
}
```

A20 — Zero-downtime rolling deploy:
```yaml
- hosts: webservers
  serial: 2
  pre_tasks:
    - name: Deregister from LB
      amazon.aws.elb_target_group_attachment:
        target_group_arn: "{{ tg_arn }}"
        target_id: "{{ inventory_hostname }}"
        state: absent
  tasks:
    - block:
        - name: Deploy app
          ansible.builtin.copy:
            src: app.tar.gz
            dest: /opt/app/
        - name: Restart service
          ansible.builtin.systemd:
            name: myapp
            state: restarted
        - name: Register to LB
          amazon.aws.elb_target_group_attachment:
            target_group_arn: "{{ tg_arn }}"
            target_id: "{{ inventory_hostname }}"
            state: present
        - name: Health check
          ansible.builtin.uri:
            url: "http://{{ inventory_hostname }}:8080/health"
            status_code: 200
      rescue:
        - name: Rollback to previous version
          ansible.builtin.copy:
            src: app-previous.tar.gz
            dest: /opt/app/
        - name: Restart service
          ansible.builtin.systemd:
            name: myapp
            state: restarted
        - name: Re-register to LB
          amazon.aws.elb_target_group_attachment:
            target_group_arn: "{{ tg_arn }}"
            target_id: "{{ inventory_hostname }}"
            state: present
```
`serial` controls batch size. Pre/post tasks manage LB state. `uri` validates health. `block/rescue` handles rollback on failure.
