### Cloud Infrastructure Architecture

**CL1** — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, and apps (e.g., AWS EC2). PaaS provides a runtime/platform for deploying apps; provider manages OS, scaling, and patching (e.g., Azure App Service). SaaS delivers complete software over the internet; you only configure and use it (e.g., Microsoft 365).

**CL2** — The Shared Responsibility Model divides security duties: provider secures the cloud infrastructure; customer secures what runs in it. For IaaS VMs: provider secures host/hypervisor/physical; you secure OS, patches, firewall rules, data, and IAM. For managed Kubernetes: provider secures control plane and node infrastructure; you secure workloads, network policies, secrets, and app code. For SaaS (M365): provider secures everything infra/platform; you secure tenant config, user access, data classification, and DLP policies.

**CL3** — VPC: logically isolated virtual network. Subnet: IP range within a VPC, bound to an AZ. Security Group: instance-level firewall, stateful (return traffic auto-allowed), allow-only rules. NACL: subnet-level firewall, stateless (explicit inbound/outbound rules), supports allow/deny. Layering: Traffic hits NACL → SG → OS firewall. Stateful tracks connection state; stateless evaluates each packet independently.

**CL4** — Landing Zone: pre-configured secure baseline (accounts, networking, logging, IAM). OUs: group accounts by function/environment for policy inheritance. Guardrails: SCPs/policy-as-code enforcing compliance (e.g., block public buckets, mandatory tagging). Shared Networking: Transit Gateway/Azure Hub-and-Spoke centralizes routing, internet/NAT, and DNS. Centralized Logging: CloudTrail/Activity Log → object storage → SIEM/data lake. Single-account problems: massive blast radius, permission sprawl, noisy neighbors, poor cost attribution, and compliance boundary violations.

**CL5** — IaC manages infrastructure via version-controlled config files. Terraform/OpenTofu: declarative HCL, multi-cloud, mature state management; best for broad infrastructure. Pulumi: uses real programming languages, supports complex logic; best for dev-heavy teams. CloudFormation/Bicep: native to AWS/Azure, tight integration; best for deep single-cloud features. Crossplane: K8s-native, manages cloud resources via CRDs; best for K8s-centric orgs. Choose based on team skills, cloud scope, and runtime preference.

**CL6** — HPA scales pod count based on CPU/metrics/custom sources. VPA adjusts CPU/memory requests/limits per pod (usually requires restart). Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external event sources (queues, streams, DB connections) and supports scale-to-zero. Use KEDA over HPA when load is event-driven, metrics don't correlate with actual work, or you need zero-idle-cost scaling.

**CL7** — Define RPO (max data loss) and RTO (max downtime) first. Active-Active: both regions serve traffic; near-zero RTO/RPO, high cost, complex sync. Active-Passive: primary serves, standby ready; lower cost, higher RTO/RPO. DB replication: sync (zero RPO, latency penalty), async (low RPO, acceptable latency). DNS failover: Route53/Traffic Manager health checks with failover routing. State: externalize to managed services; avoid local ephemeral. Cost: Active-active doubles infra; async replication cheaper. Pilot Light: minimal core infra running, low cost, longer RTO. Warm Standby: scaled-down but ready, medium cost/RTO. Multi-site Active-Active: full duplicate, high cost, near-zero RTO.

**CL8** — GitOps uses Git as single source of truth, automated pull-based sync, and declarative state. ArgoCD: UI-driven, app-centric, broader ecosystem. Flux: CNCF, CLI-focused, highly modular, simpler. Secrets: Sealed Secrets (encrypt in Git), External Secrets Operator (pull from Vault/AWS SM), or SOPS; never store plaintext. Drift: Controller detects divergence, auto-reverts or alerts. Manual changes are overwritten or flagged for audit, enforcing compliance.

**CL9** — Use a StatefulSet for stable network IDs and ordered deployment. PV/PVC with `local` storage class + node affinity ensures low-latency, node-bound storage. Headless Service (`clusterIP: None`) enables direct pod DNS for sticky sessions. Init containers pre-load config, set permissions, and bake files to required paths before main container starts. ConfigMaps mounted as volumes provide path-specific configs. PDB (`minAvailable`) ensures continuity during node drains/updates.

**CL10** — Service Account: K8s identity for pod-to-API server auth; no cloud permissions. IRSA (AWS) / Workload Identity (GCP/Azure): maps K8s SA to cloud IAM role via OIDC federation. Mounting static cloud credentials is bad: long-lived, high blast radius, hard to rotate, violates least privilege. Federation solves this by issuing short-lived, scoped tokens automatically, eliminating static secrets and enabling per-workload least privilege.

**CL11** — Object (S3/Blob): unstructured, HTTP API, highly durable (11x9s), massively scalable; use for backups, media, data lakes. Block (EBS/Managed Disk): raw disk, low latency, single-attach; use for OS, databases, high-perf apps; durability ~99.999%. File (EFS/Azure Files): NFS/SMB, shared access, metadata-heavy; use for shared configs, legacy apps, CI/CD artifacts. Object wins on durability/scalability; block wins on latency.

**CL12** — Network Policies: default deny, explicit pod-to-pod allow. Service Mesh: mTLS for all east-west traffic, fine-grained authz. Pod Identity: workload identity for cloud API access. Admission Controllers: OPA/Kyverno enforce policies (no root, resource limits, approved images). Image Signing: Cosign/Notary + webhook verify signatures. Runtime Security: Falco detects anomalous syscalls/processes. Secrets: External Secrets/Vault, never in images/env vars. Differs from perimeter: assumes breach, verifies every request, micro-segments, zero implicit trust.

**CL13** — CDN: distributed edge servers caching content closer to users. Works via DNS routing to nearest PoP, caching static/dynamic content, reducing origin load/latency. Services: CloudFront, Azure Front Door. Use CDN for static assets, global users, DDoS mitigation, high traffic. Serve directly from origin for low traffic, highly dynamic/personalized content, or strict compliance requiring direct control.

**CL14** — Region: geographic area with multiple data centers. AZ: isolated facility within a region (independent power, cooling, network). Multi-AZ deployment provides fault tolerance, high availability, and automatic failover. Zonal resources exist in one AZ (e.g., EC2, EBS). Regional resources span AZs (e.g., ALB, RDS Multi-AZ, VPC).

**CL15** — Managed DB (RDS/Cloud SQL/Azure SQL): provider handles infrastructure, patching, backups, failover, scaling, and monitoring. On a VM, you manage OS, DB software, patches, backup schedules, HA configuration, storage tuning, and security hardening. Managed services shift operational burden to the provider, letting you focus on schema, queries, and performance.

**CL16** — IAM Users: human/service identities. Groups: collections of users. Roles: temporary permissions assumed by users/services. Policies: JSON/YAML granting/denying actions on resources. Least Privilege: grant only permissions needed for a task. Apply via scoped policies, resource ARN restrictions, condition keys, regular access reviews, automated rotation, and just-in-time access.

**CL17** — Serverless: event-driven, auto-scaling, pay-per-use, no server management. Lambda (AWS): mature, wide runtime support. Azure Functions: tight Azure integration. Cloud Functions (GCP): simplified, migrating to Cloud Run. Cold starts: delay when scaling from zero or after inactivity; matters for latency-sensitive APIs. Mitigate with provisioned concurrency, keep-warm, smaller packages. Poor fit: long-running processes, high sustained load (costly), strict latency SLAs, large memory/CPU needs, legacy monoliths.

**CL18** — Ingress Resource: L7 routing, TLS, path/host-based; limited spec, vendor annotations. Gateway API: next-gen, standardized, supports listeners, routes, reference grants, better multi-tenant. Cloud LB Annotations: direct cloud LB provisioning. Service Mesh Ingress: Istio Gateway/Envoy, advanced traffic mgmt, mTLS, observability. TLS termination can occur at LB, Ingress controller, or mesh sidecar. Use Gateway API for complex routing, multi-tenant environments, standardized APIs, and better extensibility.

**CL19** — RI vs SP vs Spot: RI for predictable steady-state compute; SP for flexible compute across services; Spot for fault-tolerant/batch (up to 90% savings). Right-sizing: monitor utilization, downsize overprovisioned, auto-scale. Storage Tiering: S3 Intelligent-Tiering, Glacier/Archive for cold data, lifecycle policies. Idle Detection: tagging, usage metrics, automated shutdown, orphan cleanup. FinOps: collaborative culture, showback/chargeback by team, budget alerts, anomaly detection. Tools: CloudHealth, Kubecost, native cost explorers, strict tagging governance, automated reporting dashboards.

**CL20** — Abstraction: Terraform, Pulumi, K8s, CNCF projects. K8s Runtime: standardizes deployment, networking, storage. IaC Portability: Terraform modules, avoid cloud-specific features. Networking: Direct Connect/ExpressRoute, VPN, global DNS, consistent security. Identity: OIDC federation, centralized IdP, cross-cloud SSO. Trade-offs: complexity, skill fragmentation, egress costs, lost vendor features, operational overhead. Justified: compliance/data sovereignty, risk mitigation, best-of-breed services, customer proximity. Unnecessary: cost savings alone, lack of expertise, simple workloads.

### OT Infrastructure Architecture

**OT1** — Purdue Model (ISA-95) structures OT/IT integration. Level 0: Physical process (sensors, actuators, motors). Level 1: Control devices (PLCs, RTUs, DCS controllers). Level 2: Supervisory (SCADA, HMI, historians). Level 3: Site operations (MES, batch, local servers). Level 4: Enterprise (ERP, business systems). Level 5: External (cloud, partners, internet).

**OT2** — IT prioritizes confidentiality, availability, integrity; uses standard TCP/IP, frequent patching, virtualization. OT prioritizes safety, availability, integrity, confidentiality; uses real-time deterministic control, legacy systems, proprietary protocols. Standard IT patching fails in OT because reboots disrupt production, patches may break certified control logic, require extensive validation, and downtime costs are prohibitive.

**OT3** — IDMZ buffers IT (L4) and OT (L2/L3). Hosts data collectors, protocol converters, firewalls. Traffic: strictly filtered/unidirectional. IT→OT: only authorized commands/configs. OT→IT: telemetry, alarms, logs. Direct L4→L1 is dangerous: bypasses supervision, increases blast radius, exposes control logic to IT malware, violates safety/security boundaries, and risks physical harm.

**OT4** — Modbus TCP: L1/L2, simple, unencrypted, legacy. OPC UA: L2/L3, secure, platform-independent, modern data exchange. EtherNet/IP (CIP): L1/L2, Rockwell, implicit/explicit messaging. PROFINET: L1/L2, Siemens, real-time Ethernet. MQTT: L3/L4, lightweight pub/sub, ideal for edge-to-cloud telemetry.

**OT5** — Data Diode: hardware-enforced unidirectional flow; physically blocks reverse traffic. Firewall: software/hardware, bidirectional filtering, rule-based. Use diode for high-security OT, strict compliance, critical infrastructure where any inbound risk is unacceptable. Limitation: no bidirectional comms, harder to manage, expensive, incompatible with interactive protocols.

**OT6** — Flow: PLCs → OPC UA Server (L2) → Historian (L3) → Edge Gateway (protocol translation, filtering, caching) → MQTT Broker (TLS/mTLS) → Cloud Ingestion (IoT Hub/EventBridge) → Analytics. Security boundaries: firewall between L2/L3, IDMZ at L3/L4, edge gateway with local auth, TLS for MQTT, cloud IAM, network segmentation.

**OT7** — IEC 62443 defines zones (assets with same security/function) and conduits (communication paths with controls). Design: Zone 1: Corporate/IT (L4). Zone 2: Engineering/IT-OT Bridge (L3). Zone 3: SCADA/Historian (L2/L3). Zone 4: PLCs/Control (L1/L2). Zone 5: SIS (safety, isolated). Conduits: IT→Eng (filtered, MFA), Eng→SCADA (read-only telemetry, command approval), SCADA→PLC (control traffic, encrypted), SIS isolated (hardwired or strict diode/firewall).

**OT8** — VLANs: separate by function/line (Line1-PLC, Line1-HMI, SCADA, Engineering, SIS). Firewalls: next-gen at L2/L3 boundary, between lines, at IDMZ. Switches: managed L3, STP/RSTP, port security, 802.1X where possible. Remote Access: bastion host, MFA, session recording, time-bound, jump through IDMZ. Transition: phased rollout, parallel run, weekend windows, rollback plans, stakeholder comms, hot-swapping/stacked switches to avoid downtime.

**OT9** — BPCS: normal process control (PLC/DCS). SIS: independent safety system, triggers on failure to bring process to safe state. IEC 61511: functional safety standard, defines SIL levels, lifecycle. SIS must be isolated to prevent common-cause failures. Ransomware on SIS could disable safety trips, causing catastrophic physical harm. Air-gap/isolation prevents IT/OT malware from reaching safety logic.

**OT10** — PLC: discrete/sequential control, rugged, modular, L1. DCS: continuous process control, distributed architecture, high reliability, L1/L2. SCADA: supervisory monitoring/control, wide-area, HMI-focused, L2/L3. Coexistence: yes. PLCs/DCS handle control; SCADA supervises multiple sites/lines.

**OT11** — Architecture: Corporate → ZTNA → Jump Host/Bastion (L3) → OT Network. Controls: MFA, PAM, session recording, time-limited access, least privilege, segmentation. RDP directly to HMI is unacceptable: bypasses controls, exposes outdated HMI OS, high blast radius, no audit trail, violates Purdue model, and risks direct control manipulation.

**OT12** — Detection: passive OT IDS (Nozomi/Claroty), anomaly detection on control traffic, asset inventory baseline. Response: isolate compromised segment (firewall rules, VLAN shutdown), preserve logs, engage control room for manual override, verify SIS integrity. Coordination: OT security + plant operators + IT SOC. Safe Ops: manual control, bypass compromised systems, verify safety interlocks, gradual restoration. Operator Role: physical safety first, report anomalies, execute manual procedures, avoid compromised IT systems.

**OT13** — HMI: screen/interface for operators to monitor/control processes. Role: real-time visualization, alarms, manual overrides. Differs from Engineering WS: HMI for operations (read-heavy, limited write); Eng WS for programming/configuring PLCs (full access, development tools, higher privilege).

**OT14** — Historian: time-series DB for process data. Importance: trend analysis, compliance, optimization, troubleshooting. Plant Historian (L3): local, high-frequency, real-time ops. Enterprise Historian (L4): aggregated, lower frequency, business analytics, cross-site reporting.

**OT15** — Ladder Logic: graphical programming language resembling electrical relay circuits. Executes on PLCs. Dominance: intuitive for electricians, deterministic, decades of legacy code, certified for safety, easy to troubleshoot, and deeply embedded in industrial training.

**OT16** — RTU: Remote Terminal Unit, designed for harsh/remote environments, telemetry-focused, often serial/modem-based, autonomous. PLC: factory/industrial control, high I/O, deterministic, Ethernet-focused. RTU deployment: oil/gas pipelines, utilities, remote substations, wide-area monitoring where power/network is limited.

**OT17** — Analog: continuous signals (4-20mA, 0-10V) for sensors (temp, pressure). Digital: discrete (on/off, 0/24V) for switches, relays. 4-20mA preferred over 0-20mA: 4mA "live zero" detects wire breaks (0mA = fault), better noise immunity, allows two-wire power/signal sharing.

**OT18** — OT Asset Inventory: foundation of OT security; enables baseline, anomaly detection, patch management, compliance. Tools/Techniques: passive network monitoring (packet capture, protocol decoding), active scanning (Nmap, asset discovery). Active scanning danger: can crash legacy devices, disrupt real-time control, trigger false alarms, violate safety, and cause unplanned downtime.

**OT19** — MITRE ATT&CK for ICS: adversary tactics/techniques for ICS. Tactics/Examples: 1. Initial Access (T1190: Exploit Public-Facing App). 2. Execution (T1059: Command/Scripting Interpreter). 3. Persistence (T1098: Account Manipulation). 4. Collection (T1005: Data from Local System). 5. Impact (T1499: Endpoint DoS). Differs from Enterprise: focuses on OT protocols, physical impact, safety systems, PLC/SCADA specifics. Use: map controls to techniques, run purple team exercises, identify monitoring/response gaps.

**OT20** — Converged SOC: Log collection via passive taps, protocol-aware parsers, low-impact agents, batch/sampled telemetry. SIEM: centralized correlation, OT-specific playbooks, normalized logs. Detection Rules: protocol anomalies, unauthorized commands, firmware changes, off-hours activity. Triage: IT analysts filter noise, OT engineers validate impact, escalation matrix. Staffing: hybrid team, OT SMEs for context, IT for cyber tradecraft. False Positives: high due to legacy noise, maintenance windows, protocol quirks; tune baselines, use ML/anomaly detection. PLC Firmware Alert: verify with OT engineer, check change management logs, isolate if unauthorized, capture forensic image, restore from known-good backup, report to management/regulators if critical.
