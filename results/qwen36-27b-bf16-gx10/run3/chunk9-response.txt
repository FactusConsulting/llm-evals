## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A**
The pods fail because Kubernetes' `Restricted` Pod Security Standard (PSS) enforces `runAsNonRoot: true` strictly. When `runAsNonRoot: true` is set, the kubelet validates that the container's effective UID is not `0`. The new Chainguard base image defaults `USER` to `root` (UID 0), causing the kubelet to reject the container startup. Under the `Baseline` standard, `runAsNonRoot` was not enforced by default, and containers could run as root unless explicitly restricted. `Restricted` PSS automatically applies `runAsNonRoot: true` and validates it against the image's `USER` directive or `securityContext.runAsUser`. Without an explicit non-root `runAsUser`, the image's root default triggers a `SecurityContextDeny` or `CrashLoopBackOff` (kubelet kills it immediately).

**SC1-B**
```bash
kubectl get pods -A -o json | jq '.items[] | select(any(.status.containerStatuses[].state.waiting.reason; . == "CrashLoopBackOff")) | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C**
*Immediate Fix & Rollout:* Update container images to set `USER 65532` (or a non-root UID) in the Dockerfile, or add `runAsUser: 1000` to the pod `securityContext`. Apply updated manifests with `kubectl apply` and trigger a rolling restart (`kubectl rollout restart deployment/<name>`). Use `maxUnavailable: 0` to avoid downtime.
*Prevention:* 
1. **Image-level:** Pin base images by digest and enforce `USER nonroot` in Dockerfiles.
2. **Manifest:** Add `securityContext.runAsUser` explicitly to all deployments.
3. **CI Gate:** Add a build step that runs `docker inspect --format='{{.Config.User}}' <image>` or uses `kaniko`/`buildah` to verify effective UID ≠ 0. Integrate `trivy` or `checkov` to scan manifests for missing `runAsUser` when `runAsNonRoot: true` is set.
4. **Admission:** Deploy OPA Gatekeeper/Kyverno to reject pods violating `runAsNonRoot` without explicit `runAsUser`.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A**
Promoting a cross-region read replica introduces stale data because PostgreSQL streaming replication is asynchronous by default across regions. WAL segments are shipped and applied with network latency + disk I/O delay. Any transactions committed on the primary but not yet shipped/applied to the replica are lost upon promotion. The data loss window equals the replication lag at the moment of promotion. To quantify it, check `SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(), pg_current_wal_lsn();` on the replica, or monitor AWS RDS `ReadReplicaLag` CloudWatch metric. Asynchronous replication trades consistency for availability; cross-region latency amplifies the lag.

**SC2-B**
```bash
# 1. Import the promoted replica into state
terraform import aws_db_instance.primary <new-eu-west-1-instance-id>

# 2. Remove the old us-east-1 instance from state (if still tracked)
terraform state rm aws_db_instance.old_primary

# 3. Update Terraform config to reference the new instance ID/ARN
# 4. Apply to sync dependent resources (SGs, Route53, parameter groups)
terraform plan -target=aws_db_instance.primary
terraform apply -target=aws_db_instance.primary
```
Use `terraform state mv` if you renamed the resource in code. Run `terraform plan` first to verify no destructive changes occur.

**SC2-C**
*Architecture:*
- **Connection Management:** Replace PgBouncer with **RDS Proxy**. It handles connection pooling, IAM authentication, and automatically routes to the new primary during failover without app reconfiguration.
- **DNS Failover:** Use Route53 Failover Routing with active/passive health checks. Health checks probe the DB endpoint; Route53 switches DNS to EU within seconds.
- **App Retry Logic:** Implement exponential backoff + jitter for transient connection errors. Use idempotent writes where possible.
- **RPO < 1s:** Standard RDS async replication cannot guarantee <1s cross-region. **Aurora Global Database** is recommended: it uses optimized log shipping (not full WAL), achieves ~1s lag, supports automatic cross-region failover, and maintains consistent snapshots. It eliminates manual promotion and reduces data loss windows significantly.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A**
1. **In-Memory Sessions:** K8s pods are ephemeral; sticky sessions break scaling. *Fix:* Externalize to Redis/Valkey with session affinity disabled.
2. **Local NFS Mount:** Direct host mounts don't translate to K8s. *Fix:* Use NFS CSI driver with PVCs (`ReadWriteMany`).
3. **Oracle 19c Dependency:** Monolith tightly coupled to on-prem DB. *Fix:* Keep Oracle on-prem, expose via VPC peering/PrivateLink, or migrate to RDS/Cloud SQL later.
4. **IBM MQ Integration:** Mainframe messaging requires persistent, ordered delivery. *Fix:* Containerize IBM MQ with persistent storage or use cloud-managed MQ (AWS MQ/Azure Service Bus).
5. **F5 BIG-IP Dependency:** Hardware LB doesn't integrate with K8s service discovery. *Fix:* Deploy NGINX/HAProxy Ingress Controller + Service Mesh (Istio/Linkerd) for internal routing.

*PostgreSQL Lock Diagnostic:*
```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocked_activity.usename AS blocked_user,
       blocking_locks.pid AS blocking_pid,
       blocking_activity.usename AS blocking_user,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS blocking_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A**
- **Manual `tofu apply`:** Bypasses audit, state locking, and peer review. Concurrent runs without locking overwrite the state file, causing resource orphaning, double-creation, or accidental deletion.
- **Divergent Helm values:** Config drift leads to unexpected runtime behavior, security misconfigurations, and environment parity loss.
- **Direct `kubectl edit`:** Bypasses GitOps, leaves no audit trail, and breaks declarative state. Changes are lost on redeploy or cause reconciliation loops.
*State Locking Danger:* Without DynamoDB/S3 locking, two `tofu apply` runs read the same state, compute diffs independently, and write back sequentially. The second write overwrites the first, causing Terraform to think resources were deleted or modified, triggering destructive `apply` actions.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A**
*Architecture Comparison:*
- **Active-Passive (Velero):** Meets RPO 15m/RTO 1h easily. Velero backs up K8s resources + PVs. Restore takes ~30-45m. MinIO 200TB async replication feasible over 12ms. PG: Patroni async/sync. Redis: Sentinel async. RabbitMQ: Quorum queues or federation. MinIO: Site replication (async).

*Recommendation:* Active-passive with automated failover. Replication: PG (Patroni sync commit to Dallas), Redis (Sentinel async), RabbitMQ (Quorum queues sync), MinIO (site replication async, ~5-10m lag).

**SC10-C**
*Failover Sequence:*
1. **Detection:** Multi-region health checks (EC2 status, DB ping, network latency). Require 3 consecutive failures over 60s to avoid flapping.
2. **DNS:** Route53 GSLB switches traffic to Dallas via failover routing policy.
3. **Patroni:** Automatic promotion of Dallas standby. `synchronous_commit: on` ensures zero data loss if Chicago fails cleanly.
4. **Redis:** Sentinel detects master failure, promotes replica.
5. **RabbitMQ:** Quorum queues auto-recover. Federation catches up missed messages.
6. **MinIO:** Site replication catches up. Switch application endpoints to Dallas.
7. **OpenTofu:** Update state/vars to reflect Dallas as primary. Run `tofu apply` to sync DNS/SGs.
*Split-Brain:* Use network fencing, quorum-based DCS (etcd), and `synchronous_standby_names` to prevent dual-primary writes.
*Failback:* Sync Dallas data back to Chicago (PG logical replication, MinIO reverse sync). Verify consistency. Switch DNS back. Monitor for 24h before decommissioning Dallas primary role.
