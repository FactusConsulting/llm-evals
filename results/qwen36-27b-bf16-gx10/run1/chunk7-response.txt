## Application Architecture

**AA1** — Monoliths bundle all functionality into a single deployable unit sharing one process and database. Microservices split functionality into independently deployable services, each owning its data and process. Microservices introduce: (1) distributed transaction complexity (no ACID across services), (2) network latency and partial failure modes (timeouts, retries, cascading failures), and (3) operational overhead (deployment pipelines, service discovery, distributed tracing, and config management multiply per service).

**AA2** — Synchronous communication blocks the caller until a response is received (request-response). Example: REST over HTTP or gRPC. Asynchronous communication decouples sender and receiver; the caller continues without waiting. Example: Kafka or RabbitMQ (pub/sub or queue). Sync is simpler for low-latency, tightly coupled flows; async scales better, handles bursts, and improves resilience.

**AA3** — A reverse proxy operates at L4/L7 to forward traffic, terminate TLS, cache, and load balance. An API Gateway adds application-layer logic: authentication, rate limiting, request/response transformation, service aggregation, and versioning. A gateway can replace a reverse proxy for API traffic, but it's often overkill for static assets, internal service-to-service routing, or high-throughput L4 forwarding where a lightweight proxy (HAProxy, Nginx) performs better with less overhead.

**AA4** — The Saga pattern manages distributed transactions as a sequence of local transactions, each with a compensating action to undo changes on failure. Choreography-based sagas use events: each service publishes an event that triggers the next step. Decentralized and flexible, but hard to trace/debug. Orchestration-based sagas use a central coordinator that directs steps and handles failures. Easier to monitor and modify, but introduces a single point of failure. Use choreography for simple, well-understood workflows; orchestration for complex, long-running, or frequently changing business processes.

**AA5** — CQRS separates read and write operations into distinct models, allowing independent optimization and scaling. It's paired with Event Sourcing because events naturally feed read projections (materialized views) while the event log serves as the write store. This combination solves the read/write performance mismatch, provides a complete audit trail, enables time-travel debugging, and supports multiple read models for different UIs/APIs—something traditional CRUD struggles with at scale.

**AA6** — The Circuit Breaker pattern prevents cascading failures by stopping requests to a failing dependency after a threshold. States: Closed (normal), Open (failing, requests short-circuited), Half-Open (allows limited test requests to check recovery). Unlike retry+backoff (which keeps attempting), the CB halts traffic to protect resources. Use both together: retry+backoff handles transient errors within the Closed/Half-Open states, while the CB prevents overload during sustained outages.

**AA7** — 
1. *Shared DB/schema*: Lowest cost, simplest ops, highest noisy-neighbor risk, requires row-level security. Best for low-compliance, high-volume SaaS.
2. *Shared DB/separate schema*: Medium cost, better isolation, schema migrations require per-tenant execution, moderate noisy-neighbor risk. Good balance for mid-tier SaaS.
3. *Separate DB*: Highest cost and ops complexity, strongest security/compliance, zero noisy-neighbor risk. Required for regulated industries or enterprise tenants demanding isolation.

**AA8** — Strong consistency guarantees all nodes see the same data immediately; eventual consistency allows temporary divergence with guaranteed convergence. To prevent overselling, use strong consistency for the inventory reservation path. Architect with a strongly consistent datastore (PostgreSQL with Serializable isolation or DynamoDB strong reads), partition inventory by SKU, and use optimistic concurrency control (version columns) or distributed locks. Scale reads via eventual-consistent replicas; keep the critical write path strongly consistent and sharded.

**AA9** — A sidecar proxy (Envoy) intercepts all inbound/outbound traffic for a service pod. In Istio, the data plane consists of Envoy sidecars handling routing, mTLS, and observability. The control plane (Istiod) distributes configs and certificates. mTLS via sidecars solves: zero application code changes, automatic certificate rotation, consistent policy enforcement across polyglot services, and simplified key management—unlike app-level TLS which requires manual crypto handling and per-service implementation.

**AA10** — The Strangler Fig pattern incrementally replaces a monolith by routing traffic to new services. Strategy: Place an API gateway in front of the .NET Framework monolith. Identify bounded contexts (e.g., Billing, User Profiles). Build .NET 8 microservices for each context. Configure the gateway to route specific paths/headers to the new services while falling back to the monolith. Gradually migrate features, update database access via dual-write or CDC, and decommission monolith routes until fully replaced.

**AA11** — 12-Factor App methodology defines cloud-native best practices. Six factors: (1) Codebase: one repo per app, tracked in VCS. (2) Dependencies: explicitly declared, isolated. (3) Config: stored in environment, not code. (4) Backing services: treated as attached resources via URLs. (5) Build/Release/Run: strict separation, immutable artifacts. (6) Processes: stateless, concurrent, disposable. They matter because they enable elasticity, environment parity, automated CI/CD, and vendor/platform portability.

**AA12** — *Event-driven (Kafka)*: Loose coupling, high scalability via buffering, complex debugging (async traces), partition-level ordering, resilient (replayable). *Request-driven (REST/gRPC)*: Tight coupling, limited by sync call chains, straightforward debugging, per-request ordering, requires retries/CB for failures. Choose event-driven for high-throughput, decoupled workflows, audit trails, or async processing. Choose request-driven for simple, low-latency, synchronous interactions or when immediate consistency is required.

**AA13** — A load balancer distributes client requests across multiple backend servers. Layer 4 operates at transport level (IP/port), fast, no application awareness. Layer 7 operates at application level (HTTP headers, paths, cookies), enables content-based routing, SSL termination, and caching. L7 is required for microservices routing by path/header, A/B testing, or API versioning.

**AA14** — A message queue decouples producers and consumers. Queue-based (RabbitMQ): message-oriented, routing/exchanges, at-least/once delivery, ideal for task distribution and RPC. Log-based (Kafka): append-only, partitioned, high throughput, replayable, ideal for event streaming, analytics, and event sourcing. Pick queues for workflow/task processing; pick logs for high-volume event pipelines and historical replay.

**AA15** — A container packages an application and its dependencies into an isolated user-space environment sharing the host OS kernel. VMs virtualize hardware and run full guest OSes. Containers are popular for microservices because they start in seconds, have minimal overhead, ensure environment consistency, and integrate natively with orchestration platforms like Kubernetes for elastic scaling.

**AA16** — Stateless services retain no client data between requests; any instance can handle any request, enabling trivial horizontal scaling. Stateful services maintain data (DB, cache, sessions), requiring sticky sessions, data partitioning, or replication, complicating scaling. Examples: Stateless: Nginx web server, REST API. Stateful: PostgreSQL, Redis.

**AA17** — An ORM maps object-oriented code to relational database tables. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs accelerate development, abstract SQL dialects, and reduce boilerplate, but can cause N+1 query problems, performance overhead, and struggle with complex joins. Raw SQL offers full control, optimal performance, and precise tuning, but requires more code and is database-specific.

**AA18** — The Bulkhead pattern isolates failures by partitioning resources (threads, connections, pods) so one failing component doesn't exhaust all capacity. In microservices, it prevents a slow downstream dependency from starving the entire service. Implementation: assign dedicated thread pools or connection pools per external dependency, or deploy separate pod groups per service tier. Example: payment API gets a 10-thread pool; if it hangs, order processing (separate pool) continues unaffected.

**AA19** — OT transforms concurrent operations against a base document, requiring a central server, offering low online latency but complex implementation and poor offline support. CRDTs use mathematical structures that guarantee convergence without coordination, supporting offline edits, higher bandwidth/storage, and simpler conflict resolution. For offline editing, choose CRDTs (e.g., Yjs, Automerge) because they guarantee eventual consistency without central synchronization and handle concurrent offline changes seamlessly.

**AA20** — Challenges: context propagation requires injecting trace IDs (W3C/B3) into headers across all services; sampling strategies trade cost vs visibility (head-based drops early, tail-based collects all then filters); storage/query tools like Jaeger (Elasticsearch) or Tempo (object storage) handle retention and search. Async messaging breaks trace continuity unless trace context is embedded in message headers/metadata. For Kafka: producers inject `traceparent`/`X-B3-*` into message headers; consumers extract them and continue the span, preserving the distributed trace across async boundaries.

## On-Premise Infrastructure Architecture

**OP1** — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and production readiness (ESXi, Proxmox VE, Hyper-V Server). Type 2 (hosted) hypervisors run as applications on a general-purpose OS, suited for development/testing (VirtualBox, VMware Workstation).

**OP2** — SAN provides block-level storage, low latency, high performance, using Fibre Channel or iSCSI. NAS provides file-level storage over the network, using NFS or SMB/CIFS. Use SAN for databases, VMs, and high-I/O workloads. Use NAS for file sharing, backups, and collaborative workspaces.

**OP3** — 3-tier architecture (core/distribution/access) is hierarchical, creates oversubscription, and has high east-west latency. Leaf-spine is a flat, non-blocking topology where every leaf connects to every spine, providing equal hop counts, high east-west bandwidth, and linear scalability. It solves modern data center needs for pod-to-pod traffic, low latency, and cloud-native workloads.

**OP4** — Deploy 3+ nodes (odd number for quorum). Use Corosync for quorum and cluster communication. Enable STONITH fencing via IPMI/iLO to isolate failed nodes. Use Ceph for shared storage (recommended) or iSCSI/NFS. During node failure, quorum remains, fencing kills the failed node, and VMs automatically restart on surviving nodes with accessible storage.

**OP5** — VLAN trunking carries multiple VLANs over a single link using 802.1Q tags. On Linux with one NIC: create VLAN subinterfaces (`ip link add link eth0 name eth0.10 type vlan id 10`), assign IPs, and configure the switch port as a trunk allowing VLANs 10, 20, 30. Repeat for each VLAN.

**OP6** — RAID 1: mirror (2 drives). RAID 5: single parity (3+). RAID 6: dual parity (4+). RAID 10: mirror+stripe (4+). RAID Z2: ZFS dual parity. For a 6-drive DB server: choose RAID 10 (4 usable drives) for maximum read/write performance and predictable latency. If capacity is prioritized over write performance, RAID 6 or Z2 (4 usable) offers better space efficiency with dual-drive fault tolerance.

**OP7** — Internal: AD-integrated DNS servers (recursive + authoritative for internal zones). DMZ: separate authoritative servers for public zones. Split-horizon: internal resolvers return private IPs for public FQDNs; external returns public IPs. DNSSEC: sign external zone, configure resolvers to validate. Forwarders: internal forwards to ISP/cloud DNS. Conditional forwarding: for partner domains. Laptop on VPN: receives internal DNS via DHCP, resolves internal names; off-network uses public DNS. Seamless transition via DHCP scope options.

**OP8** — Chain: Offline Root CA (self-signed) → Online Subordinate CA (issues certs) → End-entity. CRL: periodic revocation list. OCSP: real-time revocation check. Templates: define key usage, validity, extensions. Auto-enrollment: via AD/GPO. Compromised subordinate CA: revoke sub CA cert, reissue affected certs, limited blast radius. Compromised root CA: catastrophic; entire PKI must be rebuilt, all certs revoked, trust anchors replaced.

**OP9** — MPLS: high reliability, low latency, expensive, complex provisioning. IPsec VPN: cheap, variable latency/reliability, easy setup. SD-WAN: dynamic path selection, QoS, cost-effective, moderate complexity. WireGuard mesh: fast, simple, lacks centralized policy/QoS. Recommendation: SD-WAN over broadband with QoS prioritization for VoIP, optionally with MPLS fallback for critical circuits. Balances cost, latency, and management.

**OP10** — iDRAC (Dell), iLO (HPE), IPMI are out-of-band management interfaces providing remote console, power control, and hardware monitoring independent of the OS. Critical for recovery when OS is unbootable. If exposed to the internet: severe risk of brute-force attacks, default credential exploitation, firmware vulnerabilities, and full server compromise. Must be firewalled, use strong auth, disable remote access by default, and keep firmware updated.

**OP11** — LVM: block-level, thick provisioning, snapshots copy-on-write (space allocated upfront). LVM-Thin: thin provisioning, overcommit, snapshots share space until modified. ZFS: filesystem+volume manager, copy-on-write, checksums, efficient snapshots, deduplication. Use LVM for simple Linux storage, Thin for overcommit scenarios, ZFS for data integrity and advanced features. Snapshot semantics: LVM thick = full copy initially; Thin/ZFS = metadata pointer, space consumed only on write.

**OP12** — Deploy 2 sites + 1 tiebreaker (3rd site or cloud). CRUSH rules: replicate across sites, max 1 failure per site. Monitors: 1 per site + tiebreaker. Latency: <2ms RTT for synchronous replication. Split-brain: quorum loss halts writes to prevent corruption. 2-site Ceph without tiebreaker is dangerous: network partition causes both sides to lose quorum, risking data loss or split-brain. Tiebreaker breaks ties and maintains quorum.

**OP13** — DHCP assigns IPs via DORA: Discover, Offer, Request, Acknowledge. When lease expires and server is unavailable: client attempts renewal at 50% (T1), then 87.5% (T2). If both fail, client continues using the IP until expiration, then stops sending traffic. Windows may fall back to APIPA (169.254.x.x) if no lease is obtained.

**OP14** — Managed switches support configuration: VLANs, QoS, STP, port mirroring, SNMP, ACLs. Unmanaged switches are plug-and-play with no configuration. Enterprise environments require managed switches for network segmentation, traffic prioritization, monitoring, security policies, and troubleshooting.

**OP15** — NTP synchronizes system clocks. Critical for Kerberos authentication (≤5 min skew), log correlation, distributed transactions, certificate validation, and cluster quorum. Clock drift causes: auth failures, split-brain scenarios, replication errors, audit timeline gaps, and TLS handshake failures.

**OP16** — Physical server: bare metal, maximum performance, no virtualization overhead. VM: full OS isolation, hardware virtualization, heavier footprint. Container: OS-level isolation, shared kernel, lightweight. Run on bare metal for: GPU/accelerator workloads, high-frequency trading, legacy apps with strict licensing, or when virtualization overhead is unacceptable.

**OP17** — UPS provides instant power backup (seconds/minutes), protects against surges, and bridges the gap until generators start. Generators provide long-term power but take time to start. Both are needed: UPS handles immediate loss, generator sustains operations. ATS automatically switches load from utility to generator when power fails, then back when restored.

**OP18** — Active-passive: one primary handles traffic, standby waits for failover. Active-active: both handle traffic simultaneously. PostgreSQL HA with Pacemaker/Corosync: active-passive setup. Primary holds VIP, runs DB. Standby streams WAL. STONITH (IPMI) fences failed node. VIP floats to survivor. Failover is automatic on node loss, manual for maintenance. Ensures data integrity via fencing and streaming replication.

**OP19** — Strategy: 3-2-1 rule (3 copies, 2 media types, 1 offsite). Define RPO/RTO per workload. Use full backups weekly, incremental/differential daily. Deduplication saves storage. Tier storage: disk for fast restore, tape/cloud for long-term/offsite. Immutable backups (WORM) prevent ransomware encryption. Test restores quarterly via drills. Backup = data copy; DR = full recovery process, infrastructure rebuild, and business continuity procedures.

**OP20** — 802.1X roles: Supplicant (client), Authenticator (switch/AP), Authentication Server (RADIUS). EAP-TLS: mutual certificate auth, most secure. PEAP: server cert + user/pass, common. RADIUS handles auth/authorization. Dynamic VLAN: RADIUS assigns VLAN based on identity. Failed auth: port moves to restricted VLAN or disables. MAB: fallback using MAC address for legacy/IoT devices lacking supplicant support; less secure, used as last resort.
