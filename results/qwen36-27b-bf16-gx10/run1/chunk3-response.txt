T1 — `tofu plan` generates an execution plan by comparing your configuration to the current state and remote infrastructure. It shows what will be created, updated, or destroyed without making changes. `tofu apply` executes that plan, making the actual API calls to provision or modify resources.

T2 — State is a JSON file that maps your OpenTofu configuration to real-world infrastructure (IDs, attributes, dependencies). Remote state is critical for team collaboration (prevents local file conflicts), enables state locking (prevents concurrent applies), provides versioning/backup, and improves security by keeping sensitive state off developer workstations.

T3 — `count` creates resources using an integer index (`count.index`), while `for_each` uses map or set keys (`each.key`, `each.value`). `for_each` is preferred because it provides stable resource addresses tied to meaningful keys, making additions/deletions safer (no index shifting) and enabling easier updates to individual resources.

T4 — Manual changes cause configuration drift. `tofu plan` detects it by querying the provider API and comparing the live state to the recorded state file. OpenTofu will show the drift as a planned change. Running `tofu apply` will revert the resource to match your configuration. You can also run `tofu refresh` to update state without applying changes, or use `ignore_changes` if the drift is intentional.

T5 — 
```hcl
resource "aws_instance" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  tags = { Name = each.value }
}
```

T6 — `terraform_remote_state` is a data source that reads outputs from another state file. `output` blocks expose values from the current configuration. `terraform_remote_state` is discouraged because it creates tight coupling, exposes state files, and breaks modularity. The recommended alternative is to use a single root module that calls child modules directly (passing outputs as module arguments), or to pass shared data via CI/CD pipelines or external data sources.

T7 — OpenTofu evaluates outputs before provisioners complete. Since `remote-exec` runs asynchronously during apply, the output referencing the kubeconfig is empty on first run. Fix: Add `depends_on = [null_resource.kubeconfig_gen]` to the output block, or better, avoid provisioners for this pattern. Use a `local_file` resource to write the config, or use a `data` source that reads the file after the cluster is ready, ensuring proper dependency ordering.

T8 — `tofu import` maps existing infrastructure to the state file but does not generate configuration. Limitations: requires manual config writing, exact address matching, and can fail on complex/nested resources. The `import` block (1.5+) is declarative, lives in your config, and allows `tofu import` to auto-generate the corresponding resource block. It also handles state mapping more safely and supports importing into modules.

T9 — A variable is a named value used in configuration. Input variables (`variable` block) accept values from outside the module (CLI, env vars, files). Outputs (`output` block) expose computed values or resource attributes from the module to the caller or CLI. Inputs configure; outputs report.

T10 — A provider is a plugin that enables OpenTofu to interact with a specific cloud, SaaS, or API. Running `tofu plan` without `tofu init` fails because providers aren't downloaded or installed. OpenTofu will throw an error like "Provider registry.terraform.io/hashicorp/aws is not installed."

T11 — `.terraform.lock.hcl` pins exact provider versions and their cryptographic checksums. It should be committed to VCS to guarantee reproducible builds, prevent unexpected version upgrades, and mitigate supply-chain attacks by verifying provider binaries.

T12 — `tofu destroy` removes all resources managed by the current state file. To target a single resource: `tofu destroy -target=aws_instance.web`. Note: targeting can leave dependent resources in an inconsistent state if not handled carefully.

T13 — A data source reads existing infrastructure without managing its lifecycle. Use it when you need to reference external resources (e.g., fetching the latest Amazon Linux AMI ID, looking up a VPC ID, or reading a DNS record) rather than creating or owning them.

T14 — `locals` define computed values scoped to the module, while `variable` blocks define inputs from outside. Use `locals` for derived values, complex expressions, or internal logic to avoid repetition and keep input variables clean. Locals cannot be overridden by callers.

T15 — The `lifecycle` block controls resource behavior:
- `create_before_destroy = true`: Creates replacement before deleting old (zero-downtime deployments).
- `prevent_destroy = true`: Blocks accidental deletion (safety for critical DBs).
- `ignore_changes = [tags]`: Ignores drift on specific attributes (e.g., auto-scaling groups or external tools managing tags).

T16 — A `moved` block tells OpenTofu that a resource or module has been renamed or relocated in the config. It updates the state mapping without destroying and recreating the resource, enabling safe refactoring of module structure or naming conventions.

T17 — OpenTofu builds a Directed Acyclic Graph (DAG) of resources based on references. Implicit dependencies come from direct attribute references (`aws_instance.foo.id`). Explicit dependencies use `depends_on`. `depends_on` forces ordering, reducing parallelism. Use it sparingly (only when implicit refs aren't possible, like with `null_resource` or `data` sources) to maintain apply speed.

T18 — Strategies to reduce plan time:
1. Split state/configs: Break monolith into smaller workspaces/modules. Tradeoff: increases operational complexity and cross-config dependency management.
2. Use `-refresh=false`: Skips API calls to verify current state. Tradeoff: drift goes undetected.
3. Optimize provider configs: Disable telemetry, skip metadata, use `skip_region_validation`. Tradeoff: minor loss of diagnostic info.
4. Targeted plans: `tofu plan -target=...` for isolated changes. Tradeoff: misses cross-resource dependencies, requires careful validation.

T19 — State locking prevents concurrent modifications using backend-specific mechanisms (e.g., DynamoDB, S3, Consul). If a lock isn't released (CI crash), subsequent runs fail. Manually break it via backend CLI (e.g., `aws dynamodb delete-item`). Risks: state corruption, split-brain, or inconsistent infrastructure if two processes wrote simultaneously. Always verify state integrity after manual unlock.

T20 — Migration steps:
1. Backup local state: `cp terraform.tfstate terraform.tfstate.bak`
2. Update config: Replace local backend block with S3+DynamoDB backend.
3. Run `tofu init -migrate-state`. OpenTofu copies state to S3 and initializes DynamoDB table.
4. Verify: Run `tofu plan`. Should show no changes.
5. Commit new backend config. State file moves to S3; DynamoDB handles locks. Existing state is preserved verbatim.

A1 — A playbook is a YAML file containing plays (target hosts + tasks). A role is a reusable directory structure packaging tasks, vars, templates, handlers, etc. A task is a single unit of work (usually a module call) within a play or role.

A2 — `ansible_facts` is a dictionary of auto-collected host information (OS, IP, CPU, etc.). Access OS family: `{{ ansible_os_family }}`.

A3 — `command`: runs a binary directly, no shell parsing (safe, idempotent-friendly). `shell`: runs via `/bin/sh`, supports pipes, redirection, and environment variables. `raw`: sends raw command over SSH without module overhead. Use `command` for simple binaries, `shell` for complex bash logic, `raw` for non-standard targets or performance-critical scripts.

A4 — Ansible ensures idempotency by designing modules to check current state before acting. Idempotent example: `apt: name=htop state=present` (skips if installed). Non-idempotent: `command: echo "data" >> /tmp/log` (appends every run).

A5 — 
```yaml
- name: Install htop on Debian
  ansible.builtin.apt:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel-release and htop on RedHat
  ansible.builtin.yum:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
```

A6 — Variable precedence (highest to lowest for requested items): `extra_vars` > `set_fact` > `host_vars` > `group_vars` > `role defaults`. `extra_vars` override everything. `set_fact` overrides inventory/role vars. `host_vars` override `group_vars`. Role defaults are the lowest priority.

A7 — Structure:
```yaml
- hosts: rke2_init
  serial: 1
  tasks:
    - name: Deploy RKE2 server
      # ... deployment tasks ...
    - name: Wait for API ready
      ansible.builtin.uri:
        url: "https://localhost:6443/healthz"
        validate_certs: no
      register: api_health
      until: api_health.status == 200
      retries: 30
      delay: 5

- hosts: rke2_agents
  serial: 5
  tasks:
    - name: Deploy RKE2 agent
      # ... deployment tasks ...
```
Use inventory groups to separate init vs agents. `serial` controls batch size. `wait_for`/`uri` ensures control plane readiness before agents join.

A8 — `ansible-vault` encrypts files or variables. To encrypt a single variable: `ansible-vault encrypt_string --name 'db_password'` (outputs `!vault` YAML tag), or use `ansible-vault edit vars.yml` and encrypt inline. The `!vault` tag allows mixed encrypted/plaintext vars in one file.

A9 — Inventory defines target hosts and groups. Static inventory is a YAML/INI file committed to repo. Dynamic inventory is a script or plugin that queries cloud APIs/CMDBs to generate inventory at runtime, ideal for auto-scaling or ephemeral environments.

A10 — `ansible webservers -m command -a "df -h"` or simply `ansible webservers -a "df -h"`.

A11 — A handler is a task that runs only when explicitly notified by another task. It differs by running once at the end of the play, regardless of how many times it's notified. Trigger with `notify: handler_name` in a task.

A12 — `ansible.cfg` configures Ansible behavior. Common settings: `forks` (parallelism), `host_key_checking = False` (SSH key verification), `remote_user` (default SSH user), `private_key_file`, `retry_files_enabled = False`, `log_path`.

A13 — `register` captures task output (stdout, rc, stderr) into a variable. Use it in subsequent tasks: `{{ my_result.stdout }}`, `{{ my_result.rc }}`, or `{{ my_result.failed }}`.

A14 — `include_tasks` is dynamic (evaluated at runtime), supports conditionals/loops on the include itself. `import_tasks` is static (parsed at compile time), faster, but conditionals on the import statement don't work. Use `include` for dynamic branching, `import` for static, reusable task files.

A15 — Ansible Galaxy is the official repository for roles and collections. Use `requirements.yml` to list sources, then run `ansible-galaxy install -r requirements.yml` to download them into `roles/` or `collections/`.

A16 — Connection plugins define how Ansible reaches hosts. `ssh`: default, uses SSH for Linux/Unix. `local`: runs tasks on the control node. `network_cli`: SSH-based state machine for network devices (Cisco, Juniper). Use `ssh` for servers, `local` for control-node processing, `network_cli` for routers/switches.

A17 — `delegate_to` runs a task on a specific host instead of the current one. `run_once` executes the task once per play, not per host. Example: Gather remote config, then `delegate_to: localhost run_once: true` to update a central DNS record or database on the control node using aggregated data.

A18 — Performance strategies:
1. Increase `forks`: More parallel connections. Tradeoff: higher CPU/network load on control/targets.
2. Enable `pipelining`: Reduces SSH round-trips by sending modules in one stream. Tradeoff: requires `requiretty` disabled in sudoers.
3. Fact caching (`fact_caching = jsonfile`): Skips fact gathering on reruns. Tradeoff: stale facts if hosts change.
4. Use `mitogen`: Replaces SSH with high-performance RPC. Tradeoff: extra dependency, occasional module compatibility issues.

A19 — Jinja2 uses `{{ }}` for expressions, `{% %}` for statements (loops/conditionals), `{# #}` for comments. Template snippet:
```jinja2
upstream backend_pool {
{% for server in backend_servers %}
    # Health check: {{ server.name }}
    server {{ server.ip }}:{{ server.port }};
{% endfor %}
}
```

A20 — Zero-downtime rolling deploy:
```yaml
- hosts: webservers
  serial: 25%
  tasks:
    - block:
        - name: Deregister from LB
          # ... LB API call ...
        - name: Deploy new version
          # ... package/file copy ...
        - name: Restart service
          systemd: name=myapp state=restarted
        - name: Register to LB
          # ... LB API call ...
        - name: Health check
          uri:
            url: "http://localhost:8080/health"
            status_code: 200
          register: hc
          until: hc.status == 200
          retries: 10
          delay: 3
      rescue:
        - name: Rollback to previous version
          # ... revert package/config ...
        - name: Restart service
          systemd: name=myapp state=restarted
        - name: Re-register to LB
          # ... LB API call ...
        - fail: msg="Deployment failed, rolled back."
```
`serial` controls batch size. Pre/post tasks manage LB state. `uri` validates health. `block/rescue` ensures automatic rollback on failure, maintaining zero-downtime guarantees.
