K1 — Deployments manage stateless, interchangeable pods with random names and shared storage, optimized for scaling and rolling updates. StatefulSets manage stateful workloads, providing stable network identities (pod names), ordered deployment/scaling, and dedicated persistent storage per pod replica.

K2 — A ClusterIP Service creates a virtual IP within the cluster. `kube-proxy` watches the Service and its backing Endpoints, then programs `iptables` or `IPVS` rules on each node to NAT incoming traffic destined for the ClusterIP to the actual IP:port of a healthy backing pod.

K3 — A PersistentVolume (PV) is a cluster-level storage resource. A PersistentVolumeClaim (PVC) is a user/pod request for storage. A StorageClass defines dynamic provisioning parameters. Relation: A PVC either binds to an existing PV (static) or triggers a StorageClass to dynamically create a matching PV. Pods mount the PVC, which abstracts the underlying PV.

K4 — 1. Run `kubectl logs <pod> --previous` to check crash output. 2. Run `kubectl describe pod <pod>` to inspect Events, exit codes, and OOMKilled status. 3. Verify environment variables, secrets, and configmaps are correctly mounted and formatted. 4. Check liveness/readiness probe configurations for false negatives. 5. Validate resource requests/limits against actual usage.

K5 — CoreDNS provides DNS resolution for the cluster, translating service names to ClusterIPs and forwarding external queries to upstream DNS. If CoreDNS pods are down, internal service discovery fails, and external DNS resolution fails unless pods have hardcoded upstream nameservers. Cluster functionality degrades significantly.

K6 — The scheduler runs in two phases: Filtering (predicates) removes nodes that violate hard constraints (resource requests, taints/tolerations, node/pod affinity, volume node affinity, security contexts). Scoring (priorities) ranks remaining nodes using weighted factors. Key factors: least requested resources, balanced resource allocation, image locality, inter-pod affinity/anti-affinity, and topology spread constraints.

K7 — Yes, it will be scheduled. Kubernetes schedules based on requests: 3.5GB + 256Mi = 3.75GB, which is under the 4GB node capacity. At runtime, if the pod uses 600Mi, it exceeds its 512Mi limit. The kubelet will OOMKill the container, causing a restart and likely a CrashLoopBackOff.

K8 — Client → External Cloud Load Balancer (routes to ingress controller NodePort/ClusterIP) → NGINX Ingress Controller pod (matches Ingress host/path rules, terminates TLS) → ClusterIP Service (kube-proxy/iptables/IPVS rules) → Endpoints (list of healthy pod IPs) → Application Pod. Traffic is load-balanced across matching pods via the Service abstraction.

K9 — A NetworkPolicy is a Kubernetes resource that defines allowed ingress/egress traffic for pods using labels and CIDR ranges. Default behavior: allow all ingress and egress. When a NetworkPolicy is applied to a namespace, it becomes deny-by-default for any pod selected by the policy; only explicitly allowed traffic is permitted.

K10 — RollingUpdate gradually replaces old pods with new ones, maintaining availability via `maxSurge` and `maxUnavailable`. Recreate terminates all old pods before creating new ones, causing downtime. Choose Recreate when old and new versions cannot coexist (e.g., database schema migrations, shared port conflicts, or strict config reload requirements).

K11 — A namespace is a logical partition for isolating resources, RBAC, and network policies. Default namespaces: `default` (user workloads), `kube-system` (cluster components), `kube-public` (publicly readable resources), `kube-node-lease` (node heartbeat/lease management).

K12 — `kubectl describe pod` shows detailed diagnostic data not in `get`: 1. Events (scheduling, image pulls, probe failures, OOMKills). 2. Conditions (Initialized, Ready, ContainersReady). 3. Volume mounts, environment variables, and resource QoS class.

K13 — A ConfigMap stores non-confidential configuration data as key-value pairs. Pods consume it via: 1. Environment variables (`env` or `envFrom`). 2. Volume mounts (exposed as files in the container filesystem). 3. Command-line arguments (`args` referencing keys).

K14 — ClusterIP: exposes service internally on a virtual IP. NodePort: exposes on each node's IP at a static high port (30000-32767), routing to ClusterIP. LoadBalancer: provisions an external cloud provider LB, which forwards traffic to the NodePort/ClusterIP.

K15 — A DaemonSet ensures one pod runs on every node (or a subset via node selectors). Use for node-level agents: log collectors (Fluentd), monitoring (Node Exporter), network plugins (Calico), or storage drivers. Unlike Deployments (fixed replica count), DaemonSets auto-scale with node count.

K16 — Taints/Tolerations repel pods: a node taints itself, and only pods with matching tolerations can schedule. Node Affinity attracts pods: a pod specifies preferred/required node labels. Use case: Taints for dedicated GPU/debug nodes. Affinity for pinning workloads to specific availability zones or instance families.

K17 — An Operator extends Kubernetes with Custom Resource Definitions (CRDs) and a custom controller that implements domain-specific operational logic. Unlike standard controllers (which manage built-in resources), Operators automate complex, stateful application lifecycles (backups, upgrades, failover). Solves: manual operational toil for databases, message queues, and complex stacks.

K18 — etcd uses Raft consensus for strong linearizability. If quorum is lost, the cluster becomes unavailable for writes and may lose read capability depending on version/config. Recovery from 2/3 lost: stop remaining etcd, restore from the latest consistent snapshot/backup, reinitialize the cluster with new etcd members, restore data, and restart the API server.

K19 — RBAC grants permissions via Roles/ClusterRoles (what actions on which resources) and RoleBindings/ClusterRoleBindings (who gets those permissions). Roles are namespace-scoped; ClusterRoles are cluster-wide. Bindings link subjects (users/groups/service accounts) to roles.
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev-team
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader-binding
  namespace: dev-team
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots: 5` causes the resolver to append up to 5 search domains to unqualified names before trying the literal query, generating excessive DNS lookups for external domains. Fix: set `dnsConfig` in the pod spec:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "1"
```
This forces the resolver to try the literal query first, drastically reducing latency.

D1 — `git merge` creates a new merge commit preserving branch history. `git rebase` rewrites history by replaying commits on top of the target branch, creating a linear history. Avoid rebasing on shared/public branches, as it rewrites commit hashes and breaks collaborators' histories.

D2 — TCP is connection-oriented, reliable, ordered, with flow/congestion control (HTTP, SSH, FTP). UDP is connectionless, unreliable, unordered, with minimal overhead (DNS, VoIP, live streaming).

D3 — A race condition occurs when concurrent processes/threads access shared state without synchronization, and the outcome depends on execution timing. Example: Two threads read a counter value `5`, both increment to `6`, and write back. Expected `7`, actual `6` (lost update).

D4 — Symmetric encryption uses one shared key for encrypt/decrypt (fast, e.g., AES). Asymmetric uses a public/private key pair (slower, enables key exchange/signatures, e.g., RSA/ECC). TLS uses asymmetric for the handshake and key exchange, then switches to symmetric for bulk data transfer.

D5 — An image layer is a read-only filesystem snapshot created by each Dockerfile instruction. Layer caching reuses layers if inputs are unchanged. Best practice: order instructions from least to most frequently changing, combine `RUN` commands to reduce layers, and use multi-stage builds to minimize final image size.

D6 — 1. Check application logs/metrics for errors or panics. 2. Verify backend/upstream health and connectivity (DB, cache, downstream APIs). 3. Inspect load balancer/proxy configuration and health check endpoints. 4. Monitor resource utilization (CPU, memory, file descriptors, connection pools) for throttling or circuit breaker triggers.

D7 — CAP theorem states a distributed system can only guarantee two of: Consistency, Availability, Partition tolerance. CP example: etcd/ZooKeeper (strong consistency, may become unavailable during network splits). AP example: Cassandra/DynamoDB (always available, may return stale data during splits).

D8 — Horizontal scaling adds more instances/nodes; vertical scaling upgrades existing hardware (CPU/RAM). Horizontal scaling requires: stateless services, shared-nothing architecture, load balancing, distributed caching, message queues, and database sharding/replication.

D9 — An environment variable is a dynamic key-value pair in a process's execution environment. To persist across Linux shell sessions, export it in `~/.bashrc` or `~/.profile` (e.g., `export MY_VAR=value`), then run `source ~/.bashrc`.

D10 — JSON is a strict, machine-parsable data interchange format. YAML is a human-friendly superset with comments, multi-document support, and complex types. JSON advantage: strict parsing, universal language support. YAML advantage: readability, comments, and anchors for configuration files.

D11 — REST is an architectural style using HTTP for stateless client-server communication. GET: retrieve resources. POST: create new resources. PUT: fully update/replace a resource. DELETE: remove a resource.

D12 — Version pinning locks dependencies to exact versions (e.g., `==1.2.3`). It ensures reproducible builds, prevents unexpected breaking changes from upstream updates, and guarantees consistent behavior across development, testing, and production environments.

D13 — Compiled languages translate source code to machine code before execution (C, Rust). Interpreted languages execute source code line-by-line via an interpreter at runtime (Python, JavaScript). Modern runtimes blur this line (JIT compilation), but the distinction remains in build/deployment workflows.

D14 — A reverse proxy sits in front of servers, forwarding client requests to backend services (NGINX, HAProxy). Use: load balancing, SSL termination, caching. A forward proxy sits in front of clients, forwarding requests to the internet (Squid, corporate proxies). Use: content filtering, anonymity, access control.

D15 — A deadlock occurs when two or more processes wait indefinitely for each other's resources. Coffman conditions: 1. Mutual exclusion. 2. Hold and wait. 3. No preemption. 4. Circular wait. All four must hold simultaneously.

D16 — Eventual consistency guarantees that, without further writes, all replicas will converge to the same state over time. Cassandra handles read-after-write by using tunable consistency levels (ONE, QUORUM, ALL, LOCAL_QUORUM). For strong read-after-write, use QUORUM for both reads and writes, leveraging read-repair and anti-entropy background processes.

D17 — mTLS requires both client and server to present and verify X.509 certificates. Handshake: ClientHello → ServerHello + ServerCert → Client verifies server → ClientCert → Server verifies client → Key exchange → Encrypted channel. Used in: service meshes (Istio), internal microservice communication, zero-trust architectures, and secure API gateways.

D18 — A hash table uses an array and a hash function to map keys to indices. Collisions are resolved via chaining (linked list/tree at each index) or open addressing (probing next available slot). Average complexity: O(1) for insert/lookup/delete. Worst case: O(n) when all keys hash to the same index or load factor is too high.

D19 — A circuit breaker prevents cascade failures by stopping calls to a failing service. States: Closed (normal, tracks failure rate), Open (fails fast, blocks calls, waits timeout), Half-open (allows limited test requests; success → closed, failure → open). Relates to retry/backoff: retries only occur in closed/half-open states; exponential backoff prevents thundering herds when transitioning from open to half-open.

D20 — Pessimistic concurrency assumes conflicts are likely and locks data on read/write (`SELECT FOR UPDATE`). Optimistic assumes conflicts are rare, uses no locks, and validates version/timestamp on commit (row versioning). Choose pessimistic for high-contention critical data (bank transfers). Choose optimistic for low-contention, read-heavy workloads (e-commerce carts, content management).
