CL1 — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, and apps (e.g., AWS EC2). PaaS abstracts infrastructure, providing runtime environments and managed services; you manage apps and data (e.g., AWS Elastic Beanstalk or Azure App Service). SaaS delivers complete applications over the internet; you only manage data and access (e.g., Microsoft 365 or Salesforce). Responsibility shifts from infrastructure management (IaaS) to application configuration (SaaS).

CL2 — The Shared Responsibility Model divides security duties: the provider secures the cloud (physical, hypervisor, global infra), you secure what's in the cloud. For IaaS VMs: provider handles hardware/network; you handle OS patching, firewall rules, app security, and data. For managed Kubernetes (EKS/AKS): provider manages the control plane; you manage node OS, workloads, network policies, and secrets. For SaaS (M365): provider handles everything; you manage identity/access, data classification, and endpoint security.

CL3 — A VPC is an isolated virtual network. Subnets divide the VPC into IP ranges, each tied to an Availability Zone. Security Groups are stateful, instance-level firewalls that allow return traffic automatically. NACLs are stateless, subnet-level firewalls requiring explicit allow rules for both inbound and outbound traffic. Layering: VPC → Subnets → NACLs → Security Groups → Instances. Stateful filtering remembers connection state; stateless evaluates each packet independently.

CL4 — A landing zone is a secure, multi-account baseline with standardized networking, identity, and logging. Organizational Units (OUs) group accounts by function/environment for policy application. Guardrails (SCPs, policy compliance) enforce boundaries. Shared networking uses Transit Gateway (AWS) or Hub-and-Spoke (Azure) for centralized routing and internet/NAT egress. Centralized logging aggregates CloudTrail, VPC Flow Logs, and security alerts into a dedicated log account. Single-account approaches cause permission sprawl, massive blast radius, billing opacity, and compliance boundary violations.

CL5 — Infrastructure as Code (IaC) provisions infrastructure via version-controlled, machine-readable files. Terraform/OpenTofu: declarative, multi-cloud, state-file driven; best for broad cloud coverage and team standardization. Pulumi: imperative, uses general-purpose languages (TS, Python, Go); best for complex logic and developer familiarity. CloudFormation/Bicep: AWS-native, declarative, tightly integrated with AWS services; best for AWS-heavy stacks. Crossplane: Kubernetes-native, uses CRDs to provision cloud resources; best for orgs already running K8s as their control plane.

CL6 — HPA scales pod replicas based on CPU/memory/custom metrics. VPA adjusts resource requests/limits per pod. Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external event sources (queues, streams, HTTP). Use KEDA over HPA when scaling depends on event-driven workloads (e.g., Kafka lag, SQS depth, cron jobs) rather than resource utilization, enabling scale-to-zero and precise event-driven elasticity.

CL7 — DR strategy starts with RPO/RTO targets. Active-active: low RTO/RPO, high cost, requires sync replication and complex state management. Active-passive: higher RTO/RPO, lower cost, uses async replication. DB replication: sync ensures zero data loss but adds latency; async trades RPO for performance. DNS failover (Route53/Traffic Manager) uses health checks to route traffic. State must be externalized to managed DBs/object storage. Pilot light: minimal infra, spin up on failover (low cost, higher RTO). Warm standby: scaled-down running copy (medium cost/RTO). Multi-site active-active: full redundancy everywhere (highest cost, lowest RTO). Cost scales with redundancy level and data sync frequency.

CL8 — GitOps stores declarative infra/app state in Git; an operator syncs cluster state to match. ArgoCD offers a rich UI, broader features, and heavier footprint; FluxCD is CNCF-native, lighter, and CLI-focused. Secrets are handled via Sealed Secrets (encrypt in Git), External Secrets Operator (sync from Vault/AWS SM), or Vault (dynamic, short-lived). Manual drift is detected by the controller and auto-reconciled (overwritten) or flagged for alerting, depending on configuration, ensuring Git remains the single source of truth.

CL9 — Use a StatefulSet for stable network IDs and ordered deployment. Provision PVs with a `local` storage class and node affinity for low-latency, node-bound storage. Use a headless Service for stable DNS resolution per pod. Init containers handle pre-start setup (e.g., permissions, schema checks). Mount ConfigMaps to exact filesystem paths required by the legacy app. Configure PodDisruptionBudgets to limit voluntary disruptions and maintain quorum. This architecture provides deterministic stateful behavior while leveraging K8s orchestration.

CL10 — A Service Account is a K8s identity for pod processes. Workload Identity maps a K8s SA to a cloud IAM role. IRSA is AWS's implementation of workload identity. Mounting static cloud credentials in pods is dangerous: they're long-lived, easily exfiltrated, and create a massive blast radius. Workload identity federation solves this by exchanging short-lived OIDC tokens for cloud credentials dynamically, enforcing least privilege, eliminating secret rotation, and binding permissions to pod identity.

CL11 — Object storage (S3/Blob): unstructured, highly durable (11x9s), globally scalable, eventual/strong consistency; use for backups, media, data lakes. Block storage (EBS/Managed Disk): low-latency, mountable filesystem, RAID-backed; use for OS volumes, databases. File storage (EFS/Azure Files): shared NFS/SMB, concurrent access; use for dev/test, media editing, legacy apps. Durability/availability: Object > Block ≈ File, with tiered SLAs based on redundancy configuration.

CL12 — Zero-trust K8s assumes breach and verifies every request. Network policies restrict pod-to-pod traffic. Service mesh (Istio/Linkerd) enforces mTLS and fine-grained authz. Pod identity (IRSA/Azure AD) binds workloads to cloud IAM. Admission controllers (OPA/Kyverno) enforce policies pre-deploy. Image signing (Cosign/Notary) verifies integrity at admission. Runtime security (Falco) detects anomalies. Secrets use Vault/External Secrets. Differs from perimeter models by replacing network boundaries with identity-centric, micro-segmented, continuous verification.

CL13 — A CDN caches content at edge locations globally, routing users to the nearest node to reduce latency and origin load. Examples: AWS CloudFront, Azure Front Door. Use a CDN for static assets, media, global audiences, and DDoS mitigation. Serve directly from origin for dynamic, personalized, low-traffic, or highly sensitive real-time data where caching is inappropriate or latency requirements are met by regional infrastructure.

CL14 — Regions are geographic areas containing multiple isolated data centers (AZs). AZs provide fault isolation within a region. Deploy across AZs for high availability and fault tolerance. Zonal resources (EC2, EBS) reside in a single AZ. Regional resources (S3, RDS Multi-AZ, ALB) automatically span AZs for redundancy.

CL15 — Managed databases (RDS, Cloud SQL, Azure SQL) handle provisioning, patching, backups, failover, monitoring, and scaling. You manage schema, queries, application configuration, and data. Running on a VM requires full OS/DB administration, manual backup/restore, custom HA setup, and patch coordination, increasing operational overhead and risk.

CL16 — IAM Users represent individuals, Groups bundle users, Roles provide temporary permissions for services/assumption, and Policies define JSON permissions. Least privilege grants only necessary permissions. Apply via role-based access, scoped policies, regular access reviews, automated credential rotation, and deny-by-default configurations.

CL17 — Serverless executes code in response to events with auto-scaling and pay-per-use billing. Lambda/Functions/GCF are functionally similar but provider-specific. Cold starts occur when a function initializes after idle, causing latency spikes; critical for real-time APIs. Poor fit for long-running tasks, sustained high load, custom OS/low-level control, or strict latency SLAs.

CL18 — Ingress resource: L7 routing via annotations, limited extensibility. Gateway API: next-gen, separates routing from implementation, highly extensible. Cloud LB annotations: provider-specific, simple. Service mesh ingress: advanced traffic management, mTLS, observability. TLS termination can occur at LB, Ingress controller, or mesh gateway. Use Gateway API over Ingress for multi-tenant routing, policy separation, and future-proof standardization.

CL19 — Cost optimization: Commit to RIs/Savings Plans for baseline workloads. Use Spot/Preemptible for fault-tolerant, batch, or stateless workloads. Right-size via utilization monitoring. Tier storage (Intelligent-Tiering, Archive) for lifecycle management. Detect idle resources via tagging and auto-stop. Implement FinOps culture with showback/chargeback. Tools: native Cost Explorer, Kubecost, CloudHealth, budget alerts, automated cleanup scripts, and mandatory tagging policies for team accountability.

CL20 — Multi-cloud strategy: Use Terraform for portable IaC, Kubernetes as a common runtime, and CNCF tools for abstraction. Connect via Direct Connect/ExpressRoute or VPN. Federate identity via OIDC. Trade-offs: increased complexity, cost, skill fragmentation, and loss of vendor-specific features. Justified for compliance, risk mitigation, best-of-breed services, or geographic requirements. Unnecessary for most startups or standard web apps where single-cloud maturity and integration outweigh theoretical flexibility.

OT1 — The Purdue Model (ISA-95) hierarchically segments industrial networks. Level 0: Physical process (sensors, actuators). Level 1: Control (PLCs, RTUs). Level 2: Supervisory (SCADA, HMI). Level 3: Operations (MES, Historian). Level 4: Enterprise (ERP, IT). Level 5: External (Internet, partners). Each level has distinct security, latency, and availability requirements.

OT2 — IT prioritizes confidentiality, availability, integrity; OT prioritizes safety, availability, integrity, confidentiality. Standard IT patching is unsafe for OT: systems are legacy, tightly coupled, safety-critical, and downtime causes physical/economic damage. OT patching requires rigorous testing, maintenance windows, rollback plans, and often vendor validation.

OT3 — The IDMZ buffers IT (L4) and OT (L2/L3), enabling controlled data exchange. Allowed traffic: unidirectional or strictly filtered (e.g., historian→ERP, authorized firmware updates). Direct L4→L1 connectivity is dangerous: bypasses supervision, increases blast radius, exposes control logic to IT threats, and violates safety protocols.

OT4 — Modbus TCP: L1/L2, simple, unencrypted. OPC UA: L2/L3, secure, platform-independent. EtherNet/IP (CIP): L1/L2, real-time, Rockwell ecosystem. PROFINET: L1/L2, real-time, Siemens ecosystem. MQTT: L3/L4, lightweight pub/sub for IIoT/cloud telemetry.

OT5 — A data diode enforces physical unidirectional flow; a firewall filters bidirectional traffic logically. Use a hardware diode for critical safety/SCADA data where zero inbound risk is mandatory. Limitation: breaks bidirectional protocols, prevents return traffic, expensive, and complex to manage compared to firewalls.

OT6 — Data flow: PLCs → OPC UA Server (L2) → Historian (L3) → Edge Gateway (protocol translation, filtering, caching) → MQTT Broker (TLS, auth) → Cloud Ingestion (IoT Hub/EventBridge). Security boundaries: L2/L3 firewall, edge gateway encryption/auth, cloud ingress IAM/VPC, and IDMZ isolation.

OT7 — IEC 62443 defines Zones (group assets by function/trust) and Conduits (connections between zones with security requirements). Define zones by process function, risk, and connectivity. Conduits specify allowed protocols, direction, and encryption. Design: Corporate (L4) ↔ IDMZ ↔ Engineering (L3) ↔ SCADA (L2) ↔ PLCs (L1) ↔ SIS (isolated). Conduits enforce strict filtering, unidirectional flow where possible, and complete SIS separation.

OT8 — Segmentation: VLANs per production line and function (PLC, HMI, SCADA). Firewalls at L2/L3 boundaries, between lines, and at IDMZ. Managed L3 switches with STP/RSTP and PoE. Remote access: bastion host, MFA, session recording, time-limited, jump through IDMZ. Transition: phased rollout, parallel runs, maintenance windows, rollback plans, and stakeholder communication to avoid production stops.

OT9 — BPCS handles normal control; SIS handles safety shutdowns (emergency stops). IEC 61511 governs functional safety. SIS must be isolated/air-gapped to prevent cyber attacks from triggering false trips or disabling safety. Ransomware on SIS could disable safety functions, cause physical damage, environmental harm, or prevent safe shutdown.

OT10 — PLC: discrete control, modular, L1. DCS: continuous process control, distributed, integrated I/O, L1/L2. SCADA: supervisory, remote monitoring/control, HMI, L2/L3. They coexist: PLCs/DCS at L1, SCADA at L2 supervising them.

OT11 — Remote access: jump host/bastion in IDMZ, MFA, session recording, vendor access via MSP portal, time-limited credentials, network segmentation. Direct RDP to HMI is unacceptable: exposes control systems to internet/corporate threats, bypasses audit, and creates high ransomware/malware risk.

OT12 — Detection/Response: Passive IDS (Nozomi/Claroty), protocol anomaly detection, CMDB inventory. IR steps: isolate compromised segment, preserve logs, engage OT/IT team, coordinate with control room for manual overrides. Plant operator role: maintain safe physical operations, follow manual procedures, report anomalies, avoid interacting with compromised systems.

OT13 — HMI: graphical interface for operators to monitor/control processes. Role: real-time visualization, alarms, manual overrides. Differs from engineering workstation: HMI is for operations (read-only/limited control), engineering is for programming/configuration (higher privileges, isolated).

OT14 — Historian: time-series database for process data. Critical for trend analysis, compliance, optimization. Plant historian (L3): local, high-frequency, real-time, supports SCADA/MES. Enterprise historian (L4): aggregated, lower frequency, integrates with ERP/business analytics.

OT15 — Ladder logic: graphical programming resembling electrical relay logic, executed by PLCs. Dominant due to intuitive design for electricians/engineers, decades of legacy code, reliability, IEC 61131-3 standardization, and low barrier to entry for OT staff.

OT16 — RTU: remote, rugged, telemetry-focused, serial/modem comms, for wide-area (pipelines, utilities). PLC: local, high-speed I/O, complex logic, for factories. Deploy RTUs in geographically dispersed, harsh environments with limited connectivity.

OT17 — Analog: continuous voltage/current (4-20mA, 0-10V), noise-susceptible. Digital: discrete signals (0/1, fieldbus). 4-20mA preferred: 4mA represents zero, enabling wire break detection (0mA) and sensor failure identification, with better noise immunity than 0-20mA.

OT18 — OT asset inventory is the security foundation; you can't protect unknown assets. Tools: passive network monitoring (packet capture, protocol decoding), active scanning (Nmap, vuln scanners). Active scanning is dangerous: can crash legacy devices, disrupt real-time control, trigger safety systems, and cause downtime.

OT19 — MITRE ATT&CK for ICS: ICS-specific adversary framework. Tactics/Techniques: Initial Access (compromised vendor), Execution (PLC programming software), Persistence (firmware modification), Lateral Movement (network scanning), Impact (process disruption). Differs from enterprise: focuses on physical impact, ICS protocols, safety systems. Use for gap assessment: map controls to techniques, run purple team exercises, prioritize defenses.

OT20 — Converged IT/OT SOC: Log collection via passive taps/lightweight agents (no polling). SIEM with OT connectors. Detection rules: protocol anomalies, unauthorized commands, firmware changes. Triage: IT filters noise, OT validates impact. Staffing: hybrid team with OT SMEs for context. False positives: high due to legacy protocols/batch processes; mitigate with baselining, ML, tuning. PLC firmware alert: verify with OT engineer, isolate segment, check integrity, rollback if needed, follow IR plan, ensure safety.
