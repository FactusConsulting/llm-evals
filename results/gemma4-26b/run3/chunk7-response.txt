## Application Architecture

**AA1**
A **monolith** is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. **Microservices** decompose this into small, independent services communicating over a network.
**3 Problems introduced by microservices:**
1. **Network Latency/Complexity:** Inter-service calls add overhead and failure points.
2. **Distributed Tracing/Debugging:** Harder to follow a single request across multiple processes.
3. **Data Consistency:** Maintaining ACID properties across distributed databases is significantly harder (requires Saga/2PC).

**AA2**
**Synchronous:** The client sends a request and waits (blocks) for a response. Example: **REST/HTTP**.
**Asynchronous:** The client sends a message and continues processing without waiting for an immediate response. Example: **RabbitMQ/Kafka**.

**AA3**
An **API Gateway** handles application-level concerns (routing, authentication, rate limiting, request transformation). A **Reverse Proxy** handles network-level concerns (load balancing, SSL termination, caching).
**Can it replace?** Not entirely. While a modern Gateway (like Kong) can perform reverse proxy tasks, it lacks the low-level, high-performance packet manipulation and specialized protocol handling (like certain WAF features) of a dedicated proxy like Nginx or HAProxy.

**AA4**
The **Saga pattern** manages distributed transactions by using a sequence of local transactions. If one fails, "compensating transactions" undo the previous steps.
* **Choreography:** Each service produces/listens to events. No central controller. Best for simple workflows with low coupling.
* **Orchestration:** A central "orchestrant" tells each service what to do. Best for complex, multi-step workflows where centralized logic is easier to manage.

**AA5**
**CQRS** separates the models for updating data (Commands) from the models for reading data (Queries).
**Pairing with Event Sourcing:** Event Sourcing stores the state as a sequence of events rather than just the current snapshot. This provides a perfect "audit log" to rebuild the read models.
**Problem Solved:** It solves the performance bottleneck of complex joins and locking in traditional CRUD when scaling read-heavy workloads.

**AA6**
The **Circuit Breaker** prevents a failing service from causing a cascading failure.
**Three States:**
1. **Closed:** Requests flow normally.
2. **Open:** Requests fail immediately without calling the service.
3. **Half-Open:** A limited number of test requests are sent to check if the service has recovered.
**Difference from Retry:** Retry handles transient blips; Circuit Breaker handles persistent failures. Use **Retry with Backoff** for short-lived network hiccups, but wrap it in a **Circuit Breaker** to stop retrying when the downstream service is clearly down.

**AA7**
1. **Shared DB, Shared Schema:**
   * *Cost:* Lowest (single DB instance).
   * *Security:* Lowest (risk of "leaky" queries).
   * *Complexity:* Low.
   * *Noisy Neighbor:* High (one tenant can hog CPU/IO).
2. **Shared DB, Separate Schema:**
   * *Cost:* Medium.
   * *Security:* Medium (logical isolation).
   * *Complexity:* Medium (managing migrations across schemas).
   * *Noisy Neighbor:* Medium.
/3. **Separate DB per Tenant:**
   * *Cost:* Highest (many DB instances).
   * *Security:* Highest (physical isolation).
   * *Complexity:* High (infrastructure overhead).
   * *Noisy Neighbor:* Lowest (resource isolation).

**AA8**
**Eventual Consistency:** Data will be consistent across all nodes "eventually" (latency-dependent). **Strong Consistency:** All reads return the most recent write immediately.
**Architecture for Inventory:**
* **Model:** Strong Consistency (to prevent overselling).
* **Data Store:** Distributed SQL (e.g., CockroachDB) or a RDBMS with strict ACID properties.
* **Pattern:** Use **Distributed Locking** (via Redis/Etcd) or **Atomic Decrement** operations at the database level within a transaction to ensure the inventory count never drops below zero.

**AA9**
A **sidecar proxy** is a helper container (like Envoy) running alongside the application container in the same Pod.
* **Istio/Envoy:** The **Data Plane** consists of all Envoy sidecars handling traffic. The **Control Plane** (Istiod) manages configuration and distributes it to the sidecars.
* **mTLS:** Solves the problem of identity verification and encryption between services. Application-level TLS is hard to manage/rotate across polygl/different languages; mTLS offloads this to the infrastructure layer, ensuring all traffic is encrypted and authenticated by default.

**AA10**
**Strangler Fig Pattern:** Incrementally replace legacy functionality with new services until the old system is "strangled."
**Strategy:**
1. Place an **API Gateway/Proxy** in front of the .NET Framework monolith.
2. Identify a single bounded context (e.g., "User Profile").
3. Build the new .NET 8 microservice.
4. Update the Gateway to route "User Profile" traffic to the new service, while everything else goes to the monolith.
5. Repeat for other modules until the monolith is empty.

**AA11**
The **12-Factor App** provides principles for building SaaS/Cloud-native apps.
1. **Codebase:** One codebase tracked in version control, many deploys.
2. **Dependencies:** Explicitly declare and isolate dependencies (e.npm, NuGet).
3. **Config:** Store config in the environment (not in code).
4. **Backing Services:** Treat resources (DBs, queues) as attached resources.
5. **Build, Release, Run:** Strict separation of stages.
6. **Processes:** Execute the app as one or more stateless processes.
*Why it matters:* Ensures portability, scalability, and reliability in environments like Kubernetes/AWS.

**AA12**
* **Coupling:** Kafka is loosely coupled (producer doesn't know consumer); REST is tightly coupled (request/response).
* **Scalability:** Kafka scales via partitions; REST scales via load balancing.
* **Debugging:** REST is easier (traceable request/response); Kafka is harder (asynchronous flow).
* **Ordering:** Kafka guarantees order within a partition; REST has no inherent ordering.
* **Failure:** Kafka handles consumer downtime via offsets; REST requires retries/dead-letter queues.
**Choice:** Use **REST/gRPC** for real-time, low-latency user-facing actions. Use **Kafka** for high-throughput, background processing, and complex event-driven workflows.

**AA13**
A **Load Balancer** distributes incoming network traffic across a group of backend servers.
* **Layer 4:** Operates at the Transport layer (TCP/UDP). It routes based on IP and Port.
* **Layer 7:** Operates at the Application layer (HTTP/HTTPS). It can inspect headers, cookies, and URL paths.
**Use Case for L7:** **URL-based routing** (e.g., sending `/api/v1` to Service A and `/static` to Service B).

**AA14**
A **Message Queue** is a buffer that holds messages until a consumer processes them.
* **Queue (RabbitMQ):** Focuses on message delivery, complex routing (exchanges), and individual message acknowledgment. Best for task distribution.
* **Log-based Broker (Kafka):** An append-only log where messages persist. Consumers track their own position (offset). Best for high-throughput stream processing and replaying history.
**Pick RabbitMQ** for complex routing/task queues. **Pick Kafka** for event streaming/log aggregation.

**AA15**
A **Container** is an isolated user-space environment sharing the host OS kernel. A **VM** includes a full guest OS and a hypervisor.
**Why popular?** Containers are lightweight, start instantly, and ensure "it works on my machine" consistency across dev/prod, making them ideal for the rapid scaling required by microservices.

**AA16**
**Stateless:** Each request contains all info needed to process it; no client context is stored on the server. **Stateful:** The server remembers previous interactions (e.g., via local session).
**Scaling:** Stateless services are easier to scale because any instance can handle any request; you don't need "sticky sessions."
**Example:** Stateless (a REST API calculating tax); Stateful (a shopping cart stored in local server memory).

**AA17**
An **ORM** maps database tables to objects in code.
**Examples:** **Hibernate** (Java), **Entity Framework** (C#).
**Trade-offs:**
* **Pros:** Faster development, type safety, prevents SQL injection.
* **Cons:** "N+1" query problems, abstraction overhead, difficulty writing highly optimized complex joins.

**AA18**
The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function.
**Implementation:**
* **Thread Pools:** Assign a dedicated thread pool to each downstream service dependency. If Service A hangs, only its pool exhausts; Service B's pool remains available.
* **Deployment Groups:** Deploy critical services on separate hardware/clusters so a resource leak in one doesn't crash the other.

**AA19**
* **OT:** Centralized server resolves conflicts by transforming operations. High complexity, low latency, but requires a central authority.
* **CRDT:** Mathematically designed to merge state without a central server. High complexity to implement, but excellent for distributed/offline use.
**Choice for Offline Editing:** **CRDT**. It allows users to edit locally and merge changes seamlessly when they reconnect, without needing a server to "decide" the winner, providing a much smoother user experience.

**AA20**
**Challenges:** Context must be passed through every hop (headers).
* **Context Propagation:** Using **W3C Trace Context** or **B3** headers to carry `trace-id` and `span-id`.
* **Sampling:** **Head-based** (decide at start) is cheap but might miss errors; **Tail-based** (decide after trace completes) is expensive but captures all interesting traces (e.g., high latency).
* **Storage:** **Jaeger/Tempo** ingest spans.
* **Kafka Continuity:** The producer must inject the trace context into the **Kafka Message Header**. The consumer must then extract that header to start a new span linked to the parent.

/## On-Premise Infrastructure Architecture

**OP1**
**Type 1 (Bare-metal):** Runs directly on hardware (e.g., **VMware ESXi, Xen**).
**Type 2 (Hosted):** Runs on top of an OS (e.g., **Oracle VirtualBox, VMware Workstation**).

**OP2**
**SAN (Storage Area Network):** Block-level storage (presents as a local disk). Use for databases/VM disks. Protocols: **Fibre Channel, iSCSI**.
**NAS (Network Attached Storage):** File-level storage (presents as a network share). Use for file sharing/backups. Protocols: **NFS, SMB/CIFS**.

**OP3**
**3-Tier:** Core, Distribution, Access.
**Leaf-Spine:** Every Leaf switch connects to every Spine switch.
**Problem Solved:** 3-tier has high latency for "East-West" (server-to-server) traffic due to North-South bottlenecks. Leaf-Spine provides predictable, low-latency, high-bandwidth connectivity for modern distributed workloads.

**OP4**
**Architecture:**
* **Node Count:** Minimum 3 for quorum.
* **Quorum:** Ensures the cluster can make decisions (majority rule).
* **Fencing:** (e.g., STONITH) Prevents "split-brain" by forcibly powering off a rogue node.
* **Storage:** **Ceph** (distributed block) is preferred for high availability.
* **Failure:** If a node fails, the cluster detects loss of heartbeat, the remaining nodes maintain quorum, and VMs are restarted on healthy nodes using the shared storage.

**OP5**
**VLAN Trunking:** Carrying multiple VLANs over a single link using **80/1Q tagging** (adding a VLAN ID to the Ethernet frame).
**Linux Configuration:** Use `vconfig` or `ip link`.
`ip link add link eth0 name eth0.10 type vlan id 10` (creates a sub-interface for VLAN 10).

**OP6**
**RAID Types:**
* **1:** Mirroring (High safety, low capacity).
* **5:** Parity (Good balance, 1 drive failure).
* **6:** Double Parity (2 drive failure).
* **10:** Stripe of Mirrors (High performance/safety, expensive).
* **Z2:** ZFS equivalent of RAID 6.
**Choice for Database:** **RAID 10**. It provides the best write performance (no parity calculation) and high fault tolerance, which is critical for database IOPS.

**OP7**
* **Internal AD:** Uses internal DNS for domain resources.
* **DMZ:** Isolated segment for public servers.
* **Split-Horizon:** Different DNS responses for internal vs. external queries (e.g., `app.corp` resolves to private IP internally, but doesn't exist externally).
* **DNSSEC:** Adds cryptographic signatures to prevent DNS spoofing.
* **Process:** A laptop on VPN uses the company's **Recursive Resolver**. When moving to the office, it switches to the local **Authoritative**-driven resolution. **Conditional Forwarding** directs specific queries (e.ran `partner.com`) to specific servers.

**OP8**
**Chain of Trust:** Root CA (Self-signed) $\rightarrow$ Intermediate/Subordinate CA $\rightarrow$ End-entity (Server) Cert.
**Deployment:**
* **Root CA:** Kept **offline** to prevent total compromise.
* **Subordinate CA:** Online to issue certs.
* **CRL/OCSP:** Methods to check if a cert is revoked.
* **Auto-enrollment:** Uses Group Policy to push certs to domain joined machines.
**Consequences:** Compromised **Subordinate** = only certs issued by that branch are invalid. Compromised **Root** = The entire organization's trust is destroyed; every device must be manually re-trusted.

**OP9**
* **MPLS:** High cost, high reliability, low latency, complex.
* **IPsec VPN:** Low cost, relies on public internet (variable latency).
* **SD-WAN:** Intelligent path selection (uses both).
* **WireGuard:** Extremely fast, modern, easy to mesh.
**Recommendation:** **SD-WAN**. It can use a cheap internet VPN for standard traffic and a reliable MPLS/Private link for the **latency-sensitive VoIP**, automatically routing based on real-time link quality.

**OP10**
**iDRAC/iLO/IPMI:** Out-of-band (OOB) management allows hardware control (power, remote console) even if the OS is crashed.
**Criticality:** Essential for remote recovery without physical presence.
**Risk:** If exposed to the internet, attackers can gain full control of the hardware, wipe disks, or install persistent firmware rootkits.

**OP11**
* **LVM:** Logical volume management; easy to resize partitions.
* **LVM-Thin:** Allows over-provisioning of space; only writes actual data.
* **ZFS:** Integrated file system and volume manager; provides snapshots, checksums, and self-healing.
**Snapshots:** LVM uses "copy-on-write" (can be slow); ZFS uses "redirect-on-write" (highly efficient). Use ZFS for data integrity; LVM for simple disk management.

**OP12**
**Strategy:** A **Stretch Cluster** across two sites.
* **CRUSH Rules:** Define rules to ensure data replicas are placed in different sites.
* **Monitors:** Must be placed in a 3rd site (or a 3rd location/cloud) to act as a **tiebreaker** to prevent split-brain.
* **Latency:** Requires very low RTT (usually <5-10ms) for synchronous replication.
**Why 2-site is bad:** Without a 3rd site/tiebreaker, if the link between sites breaks, both sites might try to become "Primary," leading to data corruption (split-brain).

**OP13**
**DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge.
**Failure:** If the DHCP server is down, the client will eventually fall back to an **APIPA** address (169.254.x.x), which allows local communication but no internet/network access.

**OP14**
**Unmanaged:** Plug-and-play; no configuration.
**Managed:** Supports **VLANs, Spanning Tree (STP), SNMP, Port Security, and QoS**.
**Enterprise Importance:** Essential for segmenting guest/staff traffic, detecting loops, and monitoring network health.

**OP15**
**NTP:** Synchronizes clocks across the network.
**Criticality:** Essential for log correlation (forensics), Kerberos authentication (time skew breaks logins), and database transaction ordering.
**Drift:** Can cause authentication failures, broken backups, and impossible-to-audit logs.

**OP16**
**Physical Server:** Dedicated hardware. **VM:** Virtualized hardware/OS. **Container:** Shared kernel/isolated process.
**Use Bare Metal when:** The workload requires direct hardware access (e.g., high-performance GPU/FPGA), extreme low-latency (no hypervisor overhead), or massive throughput (100Gbps+ networking).

**OP17**
**UPS:** Battery backup for immediate, short-term power (bridges the gap).
**Generator:** Long-term power (runs for hours/days).
**Why both?** The UPS provides "clean" power and keeps the server running during the seconds/minutes it takes for the generator to crank and stabilize.
**ATS:** Automatically switches the power source from the utility to the generator when a failure is detected.

**OP18**
**Active-Passive:** One node works; one waits. **Active-Active:** Both nodes handle traffic.
**PostgreSQL HA (Pacemaker/Corosync):**
1. **Corosync** manages cluster membership/heartbeats.
2. **Pacemaker** manages the resource (Postgres).
3. **Fencing (STONITH):** If a node is unresponsive, the cluster "kills" it to prevent data corruption.
4. **Virtual IP (VIP):** The application connects to a VIP; if the primary fails, Pacemaker moves the VIP to the standby node.

**OP19**
* **3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
* **RPO/RTO:** RPO (how much data loss is acceptable); RTO (how long until we are back online).
* **Types:** Full (everything), Incremental (changes since last backup), Differential (changes since last full).
* **Immutable Backups:** Write-Once-Read-Many (WORM) storage that cannot be deleted/encrypted by ransomware.
* **Backup vs. DR:** Backup is the *data* (the files); Disaster Recovery is the *process* (the infrastructure, networking, and plan to restore service).
* **Testing:** You must perform regular **Restore Drills** to ensure backups aren't corrupted.

**OP20**
**802.1X Roles:**
* **Supplicant:** The client device.
* **Authenticator:** The Switch.
* **Authentication Server:** RADIUS.
**Methods:** **EAP-TLS** (Cert-based, very secure) vs. **PEAP** (Username/Password, easier to deploy).
**Dynamic VLAN:** RADIUS tells the switch to move a specific port to "VLAN 20" after successful login.
**MAB:** For "dumb" devices (printers), the switch identifies the device by its **MAC address** and allows it on a restricted VLAN.
**Failure:** If authentication fails, the port is typically moved to a "Guest" VLAN or shut down entirely.
