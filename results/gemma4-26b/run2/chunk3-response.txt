## OpenTofu / Terraform

**T1**
`tofu plan` is a dry run that compares the current state against the desired configuration and generates an execution plan. `tofu apply` executes that plan to reach the desired state, making actual changes to the infrastructure.

**T2**
State is a JSON file that maps real-world resources to your configuration. Remote state is critical for team collaboration, as it provides a single source of truth, enables state locking to prevent concurrent writes, and allows for secure storage of sensitive data outside local machines.

**T3**
`count` uses an integer to create multiple resources, making it difficult to remove items from the middle of a list without shifting indices. `for_each` uses a map or set, allowing you to add or remove specific elements without affecting others. Use `for_each` when the identity of the resource depends on a specific key rather than its position in a list.

**T4**
This is "configuration drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy between the actual cloud state and the recorded state. It will then propose an action (e.g., modifying the VM back to the configured state or recreating it) to resolve the drift.

**T5**
```hcl
resource "example_vm" "web" {
  for_call = toset(["web1", "web2", "web3"])
  name     = each.value
}
```

**T6**
`terraform_remote_state` reads the entire state file of another workspace, which can expose sensitive data and creates tight coupling. Output values are more granular and secure. The recommended alternative is using a shared configuration/module or a dedicated service discovery mechanism (like SSM Parameter Store) to pass specific values.

**T7**
The `null_resource` provisioner runs during the apply phase, but the output is calculated during the planning phase. On the first run, the output is empty because the resource hasn't been created yet. To fix this, use a `data` source that reads the result of the resource or use a `depends_on` in the dependent resources to force them to wait until the `null_resource` completes.

**T8**
`tofu import` brings existing infrastructure into management by mapping a real ID to a resource block. Limitations include the requirement that the resource must already be defined in code and the manual nature of the process. The `import` block (1.5+) is declarative; it allows you to define imports in code, making them part of the plan/apply workflow, which is more auditable and easier to manage in CI/CD.

**T9**
A `variable` is an input parameter used to customize configurations (like a function argument). An `output` is a return value used to expose information (like an IP address) to the user or other modules.

**T10**
A provider is a plugin that translates OpenTofu code into API calls for a specific service (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, OpenTofu will fail because it lacks the necessary provider binaries and backend configuration to communicate with the APIs.

**T11**
The `.terraform.lock.hcl` file contains the specific versions and hashes of providers used. It should be committed to version control to ensure that every environment (Dev, Prod) and every team member uses the exact same provider versions, preventing "it works on my machine" issues.

**T12**
`tofu destroy` removes all resources managed by the current configuration. To target a single resource, use the `-target` flag: `tofu destroy -target=resource_type.resource_name`.

**T13**
A data source allows you to fetch information from existing infrastructure that is *not* managed by your current OpenTofu code. Example: Fetching the latest Amazon Linux 2 AMI ID to use in a launch template.

**T14**
`variables` are external inputs provided at runtime. `locals` are internal, computed values used for logic within the module. Use `locals` for complex transformations, repeated logic, or derived values to keep your code DRY (Don't Repeat Yourself).

**T15**
`lifecycle` controls resource behavior during updates:
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime updates).
- `prevent_destroy`: Prevents accidental deletion of critical resources (e.g., a production database).
- `ignore_changes`: Tells OpenTofu to ignore specific attribute updates (e.g., ignoring tags added by an external process).

**T16**
A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module in the code. This allows OpenTofu to update the state file's address without destroying and recreating the actual physical resource.

**T17**
OpenTofu builds a Directed Acyclic Graph (DAG). **Implicit dependencies** are created when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are defined via `depends_on`. `depends_on` forces a strict ordering, which reduces parallelism (OpenTofu cannot plan/apply independent branches simultaneously). Use it sparingly as it can significantly slow down execution.

**T18**
1. **Reduce Module Scope**: Split large states into smaller, decoupled state files (Tradeoff: increased complexity in managing dependencies).
2. **Targeted Refactoring**: Use `moved` blocks to avoid massive refreshes (Tradeoff: requires careful state management).
s3/DynamoDB backend: Use a remote backend to avoid local file locking/latency (Tradeoff: requires network connectivity).
4. **Reduce Refreshing**: Use `-refresh=false` if you know the state is accurate (Tradeoff: risk of drift).

**T19**
State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a process crashes, the lock remains. You can break it using `tofu force-unlock <LOCK_ID>`. **Risk**: If you force unlock while another process is actually running, you will almost certainly corrupt your state file.

**T20**
1. Configure the new `backend "s3"` block in your code.
2. Run `tofu init`. OpenTofu will detect the change from local to S3 and prompt you to "migrate" the state.
3. Type `yes` to allow OpenTofu to copy the local `.tfstate` to S3.
4. Verify by checking the S3 bucket for the `.tfstate` file and running `tofu plan` to ensure no unexpected changes are detected.

## Ansible

**A1**
A **task** is a single action (e.g., installing a package). A **playbook** is a collection of plays that execute tasks. A **role** is a structured, reusable bundle of tasks, variables, files, and templates.

**A2**
`ansible_facts` is a dictionary of system information gathered by Ansible. You access the OS family via `ansible_facts['os_family']` (e.s., "Debian" or "RedHat").

**A3**
- `command`: Executes a command without a shell environment (most secure, no variable expansion).
- `shell`: Executes via `/bin/sh`, allowing pipes, redirects, and environment variables.
- `raw`: Executes via SSH without needing Python on the target (used for bootstrapping).

**A4**
Idempotency means running a task multiple times results in the same state.
- **Idempotent**: `apt: name=nginx state=present` (if installed, does nothing).
- **NOT Idempotent**: `shell: echo "config_line" >> /etc/config` (appends a new line every single time).

**A5**
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install htop on RedHat
  package:
    name: [epel-release, htop]
    state: present
  when: ansible_os_family == "RedHat"
```

**A6**
Priority (lowest to highest): `role defaults` < `inventory group_vars` < `inventory host_vars` < `playbook vars` < `role vars` < `task vars` < `set_fact` < `extra_vars`.

**A7**
Use `serial: 3` in the play to process the first 3 nodes. Use `wait_for` or a `delegate_to: localhost` task with a `pause` or `retries` loop to ensure the first batch is healthy before the next batch of the `serial` group begins.

**A8**
You can use `!vault` in a YAML file to encrypt a single string, but for a single variable in a file, you typically use `ansible-vault encrypt_string 'my_secret_value'`.

**A9**
An **inventory** is a list of managed hosts. A **static inventory** is a fixed file (INI/YAML). A **dynamic inventory** is a script or plugin that queries a cloud provider (AWS/GCP) to generate the list of hosts in real-time.

**A10**
`ansible webservers -m shell -a "df -h"`

**A11**
A **handler** is a special task that only runs when "notified" by another task that reported a `changed` status. You trigger it using the `notify` keyword in a task.

**A12**
`ansible.cfg` configures Ansible behavior. Common settings: `inventory` (path to inventory), `remote_user` (default user), and `forks` (number of parallel processes).

**A13**
`register` saves the output of a task into a variable. You can then use `{{ variable_name }}` in a subsequent task, for example, to check `{{ result.rc == 0 }}`.

**A14**
`import_tasks` is **static** (processed at parse time); variables are resolved when the playbook is loaded. `include_tasks` is **dynamic** (processed at runtime); it allows for conditional inclusion. Use `include_tasks` if the task file name depends on a variable.

**A15**
Ansible Galaxy is a community hub for roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16**
- `ssh`: Standard for Linux (uses Python on target).
- `local`: Executes tasks on the control node itself.
- `network_cli`: Used for network devices (switches/routers) that do not support Python.

**A1/A17**
`delegate_to` runs a task on a different host than the current one. `run_once` ensures the task executes only once for the whole play.
*Example*:
```yaml
- name: Get remote uptime
  command: uptime
  register: remote_uptime
  delegate_to: "{{ target_host }}"

- name: Log uptime to local file
  lineinfile:
    path: /tmp/audit.log
    line: "Host {{ inventory_hostname }} uptime is {{ remote_uptime.stdout }}"
  run_once: true
  delegate_to: localhost
```

**A18**
1. **Forks**: Increase `forks` in `ansible.cfg` to run more parallel connections (Tradeoff: higher CPU/RAM on control node).
2. **Pipelining**: Enable `pipelining = True` to reduce SSH overhead (Tradeoff: requires `requiretty` to be disabled in sudoers).
3. **Fact Caching**: Use Redis/Memcached to store facts so they aren't re-gathered every time (Tradeoff: extra infrastructure to manage).
4. **Mitogen**: Use the Mitogen plugin to replace the standard SSH execution engine (Tradeoff: requires installing a plugin on the control node).

**A19**
- `{{ }}`: Variable interpolation.
- `{% %}`: Control structures (loops, conditionals).
- `{# #}`: Comments.
*Template Snippet*:
```jinja2
upstream backend_servers {
{% for server in backend_list %}
    server {{ server.ip }}:8080; # Health check: {{ server.status }}
{% endfor %}
}
```

**A20**
1. **Batching**: Use `serial: 5` to update 5 servers at a time.
2. **Pre-task**: Use `uri` module to remove the server from the Load Balancer.
3. **Deployment**: Run the application update tasks.
4. **Post-task**: Use `uri` module to perform a health check; if successful, re-add to LB.
5. **Error Handling**: Wrap the deployment in a `block`. Use `rescue` to execute a rollback task (e.g., reverting the package version) if the health check fails.
