## Kubernetes (20 questions)

**K1** — **Deployments** are for stateless applications where pods are interchangeable. **StatefulSets** are for stateful applications requiring stable, unique network identifiers and persistent storage that persists across pod rescheduling.

**K2** — A **ClusterIP** service uses `kube-proxy` (via iptables or IPVS) on each node to intercept traffic sent to the Service's virtual IP and load balance it across the IP addresses of the underlying Pods listed in the Service's **Endpoints** object.

**K3** — **PersistentVolume (PV)** is the actual storage resource (the "disk"). **PersistentVolumeClaim (PVC)** is a request for storage by a user. **StorageClass** is a template that allows for dynamic provisioning of PVs. Relation: A user creates a PVC referencing a StorageClass, which triggers the automatic creation of a PV.

**K4** — 
1. `kubectl logs <pod-name>`: Check application-level error logs/stack traces.
2. `kubectl describe pod <pod-name>`: Check Kubernetes events (e.g., OOMKilled, failed probes).
3. Check resource limits: Ensure the container isn't hitting memory limits (OOM).
4. Check Liveness/Readiness probes: Ensure the probe configuration isn't too aggressive or pointing to the wrong port.

**K5** — **CoreDNS** provides service discovery by translating service names into IP addresses. If CoreDNS pods are down, internal DNS resolution fails, meaning pods cannot communicate with each other via service names (e.g., `my-svc.my-namespace.svc.cluster.local`).

**K6** — The scheduler follows a two-step process:
1. **Filtering (Predicates):** Removes nodes that don't meet requirements (e.g., insufficient CPU/RAM, node selectors, taints).
2. **Scoring (Priorities):** Ranks remaining nodes. 
**Factors:** Resource availability (least requested), Node Affinity (matching labels), and Image Locality (is the image already on the node?).

**K7** — **Yes**, it will be scheduled because the requested 256Mi is less than the available 500Mi (4GB - 3.5GB). However, if it uses **600Mi** at runtime, it will exceed its `limit.memory` (512Mi) and the kernel will trigger an **OOMKill** (Out of Memory) on the container.

**K8** — 
1. **External LB** receives the request and forwards it to the **Ingress Controller** (e.g., NGINX).
2. The **Ingress Controller** matches the host/path to a **Service**.
3. The **Service** uses its **Endpoints** (list of Pod IPs) to route the request.
4. **kube-proxy** (via iptables/IPVS) ensures the traffic reaches the specific **Pod** IP.

**K9** — A **NetworkPolicy** is a specification of how groups of pods are allowed to communicate with each other and other network endpoints. By default, if no policy exists, all traffic is allowed (open). Once a policy is applied to a pod, that pod becomes "isolated," and only traffic explicitly permitted by the policy is allowed.

**K10** — **RollingUpdate** replaces pods one-by-one to ensure zero downtime. **Recreate** kills all existing pods before starting new ones. Choose **Recreate** when an application cannot handle two versions running simultaneously (e.g., a singleton database migration).

**K11** — A **Namespace** is a logical partition within a cluster for resource isolation. Default namespaces: `default`, `kube-system`, and `kube-public`.

**K12** — `kubectl describe pod` provides detailed metadata and lifecycle info. Unlike `get`, it shows: **Events** (recent history), **Container Status** (reasons like `CrashLoopBackOff`), and **Conditions** (PodReady, Initialized).

**K13** — A **ConfigMap** stores non-confidential configuration data in key-value pairs. Consumption methods: 1. As **Environment Variables**. 2. As **Files** mounted in a volume.

**K14** — **ClusterIP**: Internal-only IP. **NodePort**: Exposes the service on a specific port on every Node's IP. **LoadBalancer**: Provisions an external load balancer (via cloud provider) to route traffic to the service.

**K15** — A **DaemonSet** ensures that a copy of a specific pod runs on all (or selected) nodes. Use it for background services like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16** — **Taints** are applied to **Nodes** to repel pods. **Tolerations** are applied to **Pods** to allow them to stay on tainted nodes. **Node Affinity** is applied to **Pods** to attract them to specific nodes. 
*Use Case:* Taint a node with a GPU to keep general pods away; use Affinity to ensure a ML pod specifically targets that GPU node.

**K17** — An **Operator** is a custom controller that uses **Custom Resource Definitions (CRDs)** to manage complex, stateful applications. Unlike a standard controller (which manages generic resources like Pods), an Operator encodes human operational knowledge (e.g., how to perform a database backup or a schema upgrade) into software.

**K18** — **etcd** uses the **Raft** consensus algorithm. If the cluster loses **quorum** (majority), the API server becomes read-only or unresponsive to prevent data divergence. To recover from losing 2 out of 3 nodes, you must restore from a recent snapshot to a new set of 3 nodes to re-establish a quorum.

**K19** — **Role** is namespace-scoped; **ClusterRole** is cluster-wide. **RoleBinding** attaches a Role to a user/group in a namespace; **ClusterRoleBinding** attaches a ClusterRole cluster-wide.
**Manifest:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: target-ns
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: target-ns
subjects:
- kind: User
  name: developer@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** — The `ndots:5` setting causes the resolver to append multiple search domains before trying the absolute name, leading to 4-5 unnecessary queries for every external request. **Fix:** Use `dnsConfig` in the Pod spec to set `ndots: 1` or use fully qualified domain names (ending in a dot, e.g., `google.com.`).

## Development (20 questions)

**D1** — **Merge** combines histories by creating a new "merge commit." **Rebase** moves the entire feature branch to begin on the tip of the main branch, rewriting history. **Avoid rebasing** on public/shared branches as it changes commit IDs and breaks other developers' histories.

**D2** — **TCP** is connection-oriented and reliable (guarantees delivery). **UDP** is connectionless and faster (no delivery guarantee). 
*TCP:* HTTP, SSH. *UDP:* DNS, VoIP.

**D3** — A **race condition** occurs when the outcome depends on the timing/sequence of uncontrollable events. *Example:* Two threads reading `counter = 10` simultaneously, both incrementing it to `11` and writing it back, instead of the expected `12`.

**D4** — **Symmetric** uses one key for both encryption/decryption. **Asymmetric** uses a public/private key pair. In **TLS**, asymmetric encryption is used for the initial handshake (to securely exchange a session key), and symmetric encryption is used for the actual data transfer.

**D5** — A **layer** is a read-only filesystem change in a Docker image. **Layer caching** means Docker reuses layers if the instruction and files haven't changed. *Best practice:* Order instructions from "least likely to change" to "most likely to change" to maximize cache hits.

**D6** — 
1. Check **Application Logs** (is the app crashing?).
2. Check **Service/Endpoints** (is the traffic reaching the right place?).
3. Check **Resource Usage** (is the app hitting CPU/RAM limits?).
4. Check **Upstream Dependencies** (is a database or external API failing?).

**D7** — **CAP Theorem:** You can only have two of Consistency, Availability, and Partition Tolerance. 
*CP (Consistency/Partition):* **Zookeeper** (prioritizes data accuracy over availability). 
*AP (Availability/Partition):* **Cassandra** (prioritizes uptime/responsiveness over immediate consistency).

**D8** — **Horizontal** is adding more instances (scaling out). **Vertical** is adding more power to one instance (scaling up). *Patterns:* Statelessness (allows any instance to handle any request) and Load Balancing.

**D9** — An **environment variable** is a dynamic value used by processes. To persist on Linux, add `export VAR_NAME=value` to your `~/.bashrc` or `~/.profile` file.

**D10** — **JSON** is a data format using braces/brackets; **YAML** uses indentation. *JSON advantage:* Extremely fast and easy for machines to parse. *YAML advantage:* Highly human-readable.

**D11** — **REST API** is an architectural style for networked applications. 
*GET:* Retrieve data. *POST:* Create data. *PUT:* Replace/Update data. *DELETE:* Remove data.

**D12** — **Version pinning** is specifying exact versions of dependencies (e.g., `package==1.2.3`). It is vital for **reproducible builds**, ensuring the same code runs identically in Dev, Staging, and Prod.

**D13** — **Compiled:** Converted to machine code before execution (e.g., C++, Go). **Interpreted:** Read and executed line-by-line at runtime (e.g., Python, JavaScript).

**D14** — A **Reverse Proxy** sits in front of servers to protect them (e.g., NGINX). A **Forward Proxy** sits in front of clients to hide them (e.g., Squid). 
*Reverse Proxy:* NGINX (Load balancing), HAProxy (SSL termination).

**D15** — **Deadlock** is a state where processes are stuck waiting for each other. **Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16** — **Eventual Consistency** means data will be consistent across all nodes given enough time. **Cassandra** uses tunable consistency: `ONE` (fast, low consistency), `QUORUM` (majority), or `ALL` (slow, high consistency).

**D17** — **mTLS** requires both client and server to present certificates. 
*Handshake:* Client sends cert $\rightarrow$ Server verifies $\rightarrow$ Server sends cert $\rightarrow$ Client verifies $\rightarrow$ Session key established. Commonly used in **Service Meshes** (e.g., Istio) for zero-trust networking.

**D18** — A **Hash Table** maps keys to indices via a hash function. 
*Collision Resolution:* **Chaining** (linked lists at each index) or **Open Addressing** (finding the next empty slot). 
*Complexity:* Avg: $O(1)$ for all. Worst: $O(n)$ (all keys hash to one index).

**D19** — A **Circuit Breaker** prevents a failing service from overwhelming the system. 
*States:* **Closed** (normal), **Open** (failing, requests blocked), **Half-Open** (testing if service recovered). It works with **retries** and **exponential backoff** to avoid "thundering herd" problems.

**D20** — **Optimistic** assumes conflicts are rare; it checks for changes at the end (e.g., using a `version` column). **Pessimistic** assumes conflicts will happen and locks the resource immediately (e.g., `SELECT FOR UPDATE`). Use Optimistic for high-concurrency/low-contention; Pessimistic for high-contention/critical data.
