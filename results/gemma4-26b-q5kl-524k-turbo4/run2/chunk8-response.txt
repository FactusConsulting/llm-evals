## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking (e.g., AWS EC2). **PaaS (Platform as a Service):** Provides a managed environment for deploying code without managing OS (e.g., Azure App Service). **SaaS (Software as a Service):** Provides a complete application via web/API (e.g., Google Workspace).

**CL2** — The provider is responsible for the "security *of* the cloud" (physical, hardware, hypervisor); the user is responsible for "security *in* the cloud" (data, config, OS). **IaaS VMs:** User manages OS, apps, and data. **Managed Kubernetes:** Provider manages control plane; user manages worker nodes, pods, and apps. **SaaS (M365):** Provider manages everything except user identity and data.

**CL3** — **VPC:** A private isolated network. **Subnet:** A range of IP addresses within a VPC. **Security Group (SG):** Instance-level firewall (stateful). **NACL:** Subnet-level firewall (stateless). **Layering:** VPC $\rightarrow$ Subnet $\rightarrow$ SG. **Stateful (SG):** Remembers connections; if inbound is allowed, outbound is automatically allowed. **Stateless (NACL):** Requires explicit rules for both inbound and outbound.

**CL4** — **Landing Zone:** A pre-configured, multi-account environment with foundational security/networking. **OUs (Organizational Units):** Logical groupings of accounts (e.g., Prod, Dev). **Guardrails:** Service Control Policies (SCPs) or Azure Policies to restrict actions. **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) centralizes connectivity. **Centralized Logging:** Aggregating logs to a dedicated security account. **Single-account is problematic** due to massive blast radius and lack of isolation.

**CL5** — **IaC:** Managing infrastructure via machine-readable files. **Terraform/OpenTofu:** Provider-agnostic, state-managed, industry standard. **Pulumi:** Uses general-purpose languages (Python, TS). **CloudFormation/Bicep:** Cloud-native, provider-specific (AWS/Azure). **Crossplane:** K8s-native IaC. **Choice:** Use Terraform for multi-cloud; Pulumi for complex logic; CloudFormation/Bicep for deep native integration; Crossplane for K8s-centric workflows.

**CL6** — **HPA:** Scales pods based on CPU/RAM. **VPA:** Adjusts pod resource requests/limits. **Cluster Autoscaler:** Adds/removes nodes. **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag). **Use KEDA** when scaling is triggered by external events rather than just resource metrics.

**CL7** — **RPO (Recovery Point Objective):** Max data loss; **RTO (Recovery Time Objective):** Max downtime. **Active-Active:** Traffic split across regions (Zero RTO). **Active-Passive:** One region idle. **Replication:** Sync (no data loss, high latency) vs Async (low latency, potential loss). **DNS:** Route53/Traffic Manager for failover. **Pilot Light:** Minimal core services running. **Warm Standby:** Scaled-down version of full environment. **Multi-site:** Full active-active.

**CL8** — **GitOps:** Using Git as the single source of truth for infrastructure/apps. **ArgoCD/FluxCD:** Both pull-based controllers that reconcile Git state to K8s. **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault/AWS SM), or **Vault**. **Drift:** The controller detects the difference and automatically overwrites manual changes to match Git.

**CL9** — Use **StatefulSet** for stable network IDs/storage. **PV/PVC** with a **Local Storage Class** for low latency. **Headless Service** for direct pod addressing. **Init Containers** to prepare the filesystem. **ConfigMaps** mounted as volumes for files. **Pod Disruption Budgets (PDB)** to ensure availability during maintenance.

**CL10** — **Service Account:** K8s identity. **Workload Identity:** Mapping K8s identity to Cloud IAM. **IRSA:** AWS-specific implementation of workload identity. **Bad Practice:** Mounting long-lived credentials (JSON keys) in pods risks theft. **Federation (OIDC):** Allows K8s to exchange a short-lived token for a cloud IAM role, eliminating static keys.

**CL11** — **Object (S3/Blob):** Unstructured data, high durability (11 9s), accessed via API. **Block (EBS):** High-performance, attached to a single VM. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB) for multiple instances. **Durability:** Object is highest; **Availability:** Block is highest for local IO.

**CL12** — **Zero-Trust:** "Never trust, always verify." **Architecture:** Network Policies (L3/4 isolation), Service Mesh (mTLS for L7), Pod Identity (IAM), Admission Controllers (OPA/Kyverno for policy), Image Signing (Cosign), and Runtime Security (Falco for anomaly detection). **Difference:** Traditional models trust anything inside the perimeter; Zero-Trust assumes the network is already compromised.

**CL13** — **CDN:** A distributed network of proxy servers that cache content near users. **Services:** CloudFront, Azure CDN. **Use CDN** for static assets (images/JS) to reduce latency and origin load. **Serve directly** for dynamic, highly personalized, or low-traffic content.

**CL14** — **Region:** Geographic area. **AZ:** Isolated data centers within a region. **Multi-AZ:** Protects against data center failure. **Zonal:** Tied to one AZ; **Regional:** Available across multiple AZs.

**CL15** — **Managed DB:** Provider handles patching, backups, HA, and scaling. **User handles:** Schema, queries, and optimization. **Managed** reduces operational overhead significantly compared to a VM.

**CL16** — **IAM Users:** Individuals. **Groups:** Collections of users. **Roles:** Temporary identities for services/users. **Policies:** JSON documents defining permissions. **Least Privilege:** Granting only the minimum permissions required to perform a task.

**CL17** — **Serverless:** Event-driven compute (Lambda/Functions). **Cold Starts:** Latency when a function is invoked after being idle. **Poor fit:** Long-running processes, constant high-load workloads, or latency-sensitive apps requiring sub-millisecond response.

**CL18** — **Ingress:** L7 K8s resource. **Gateway API:** Next-gen, role-oriented (Infrastructure vs. App dev). **LB Annotations:** Cloud-specific (e.g., AWS ALB). **Service Mesh Ingress:** L7/mTLS entry point. **Gateway API** is preferred for complex, multi-tenant environments where infra and app teams are separate.

**CL19** — **Optimization:** Reserved Instances/Savings Plans (Commitment), Spot (Cheap/Interruptible), Right-sizing (matching capacity to demand), Storage Tiering (moving old data to Archive). **FinOps:** Culture of accountability. **Tools:** AWS Cost Explorer, CloudHealth, or tagging for **Showback/Chargeback** (allocating costs to specific departments).

**CL20** — **Multi-cloud:** Use **Kubernetes** as the abstraction, **Terraform** for IaC, and **VPN/Interconnect** for networking. **Identity Federation** (OIDC) links clouds. **Trade-offs:** High complexity and egress costs vs. redundancy and avoiding lock-in. **Justified** for regulatory/compliance; **Unnecessary** for most startups/mid-size firms.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** **L0:** Physical process (sensors/actuators). **L1:** Basic Control (PLCs). **L2:** Supervisory Control (HMI/SCADA). **L3:** Site Operations (Historians). **L4:** Enterprise/IT. **L5:** External/Cloud.

**OT2** — **IT:** Focuses on Data Confidentiality. **OT:** Focuses on Availability and Safety. **Patching:** OT systems require rigorous testing and downtime windows to avoid disrupting physical processes or causing safety hazards.

**OT3** — **IDMZ:** A buffer between L3 and L4. **Traffic:** Only controlled, inspected traffic (e.g., Historian data sync via proxy). **Danger:** Direct L4-to-L1 connectivity allows an IT breach to bypass all controls and directly manipulate physical hardware.

**OT4** — **Modbus TCP:** L1/L2 (Legacy/Simple). **OPC UA:** L2/L3 (Secure/Modern). **EtherNet/IP:** L1/L2 (Industrial Ethernet). **PROFINET:** L1 (Real-time). **MQTT:** L3/L4 (Edge-to-Cloud).

**OT5** — **Firewall:** Software-based, bidirectional (rules-based). **Data Diode:** Hardware-based, strictly unidirectional (physical light/signal). **Use Diode** for high-security segments where data must leave but nothing can enter.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway (with firewall/IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud. **Boundary:** The IDMZ/Edge Gateway is the primary security boundary.

**OT7** — **Zone:** Group of assets with similar security requirements. **Conduit:** The communication path between zones. **Model:** Corporate (Zone 1) $\rightarrow$ IDMZ $\rightarrow$ SCADA (Zone 2) $\rightarrow$ Control/PLC (Zone 3) $\rightarrow$ SIS (Isolated/Air-gapped Zone).

**OT8** — **Strategy:** Segment by production line using VLANs. Place firewalls between lines and between L3/L4. Use a **Jump Host** in the IDMZ for vendor access. **Transition:** Implement in parallel (shadow network) and migrate one line at a time to avoid total shutdown.

**OT9** — **SIS:** Safety-critical (emergency shutdown). **BPCS:** Standard process control. **IEC 61511:** Functional safety standard. **Isolation:** SIS must be isolated to prevent a single compromise from disabling safety. **Ransomware on SIS:** Could lead to physical explosions or environmental catastrophe.

**OT10** — **PLC:** Single device. **DCS:** Distributed system for complex processes. **SCADA:** Supervisory system for wide-area monitoring. They **can and do** coexist in large plants.

**OT11** — **Architecture:** Jump hosts with MFA, session recording, and time-limited access. **RDP to HMI** is unacceptable because it lacks visibility, bypasses the IDMZ, and provides no audit trail for critical commands.

**OT12** — **Plan:** Deploy IDS for anomaly detection, maintain an asset inventory, and isolate the L3 network. **Response:** Coordinate with the control room to move to manual/safe state. **Operator Role:** Monitor physical gauges and execute manual emergency shutdowns if digital controls fail.

**OT13** — **HMI:** Visual interface for operators to interact with the process. **Engineering Workstation:** Used by engineers to program/configure PLCs/HMIs.

**OT14** — **Historian:** Time-series database for process data. **Plant Historian (L3):** Local, high-speed. **Enterprise Historian (L4):** Aggregated, used for business analytics.

**OT15** — **Ladder Logic:** Visual, Boolean-based programming. Executed by **PLCs**. Dominant due to its simplicity, reliability, and legacy widespread adoption.

**OT16** — **RTU:** Remote Terminal Unit. Used for long-distance/remote telemetry (e.g., pipelines). **PLC:** Local, high-speed logic. RTUs are better for low-bandwidth, remote environments.

**OT17** — **Analog (4-20mA):** Preferred because 0mA indicates a broken wire (fault detection), whereas 0-10V cannot distinguish between a zero reading and a broken wire.

**OT18** — **Inventory:** Foundation of security (you can't protect what you don't know). **Discovery:** Passive (network sniffing) is safe; **Active scanning** is dangerous as it can crash sensitive, older PLCs.

**OT19** — **MITRE ATT&CK for ICS:** Focuses on physical impact. **Tactics:** Initial Access, Execution, Persistence, Impair Process Control, Inhibit Response Function. **Difference:** It includes ICS-specific protocols and physical consequences.

**OT20** — **SOC Design:** Use passive monitoring to avoid impacting real-time ops. **Integration:** Send logs to SIEM via unidirectional gateways. **Alert:** Unauthorized firmware change on a PLC requires immediate isolation and physical verification of the process state.
