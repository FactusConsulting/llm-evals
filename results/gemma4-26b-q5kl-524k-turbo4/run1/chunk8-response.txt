## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides virtualized computing resources over the internet (e.g., AWS EC2). **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying OS (e.g., Azure App Service). **SaaS (Software as a Service):** Fully functional applications delivered via web (e.g., Google Workspace).

**CL2** — In **IaaS**, the provider manages hardware/virtualization; you manage the OS, middleware, and data. In **Managed Kubernetes**, the provider manages the control plane; you manage worker nodes, pods, and data. In **SaaS**, the provider manages everything; you only manage your data and user access.

**CL3** — A **VPC** is your private network boundary. A **Subnet** is a range of IP addresses within a VPC. A **Security Group** is a stateful firewall at the instance level (remembers connection state). A **NACL** is a stateless firewall at the subnet level (must define both inbound and outbound rules). They layer from VPC $\rightarrow$ Subnet $\rightarrow$ Security Group.

**CL4** — A **Landing Zone** is a pre-configured, multi-account environment. **Organizational Units (OUs)** group accounts by function (e.g., Prod, Dev). **Guardrails** (like AWS SCPs) enforce compliance. **Shared Networking** uses a Hub-and-Spoke model (via Transit Gateway or Azure Virtual WAN) to centralize egress/ingress. A **single-account approach** is problematic due to limited blast radius control, hitting service quotas, and lack of administrative isolation.

**CL5** — **IaC** is managing infrastructure via machine-readable files. **Terraform/OpenTofu** (Provider-agnostic, HCL) is best for multi-cloud. **Pulumi** (General-purpose languages) is best for dev-centric teams. **CloudFormation/Bicep** (Cloud-specific) is best for deep, native integration. **Crossplane** (K8s-native) is best for managing cloud resources via Kubernetes APIs.

**CL6** — **HPA** scales pods based on CPU/RAM. **VPA** adjusts pod resource requests/limits. **Cluster Autoscaler** adds/removes nodes. **KEDA** scales based on external events (e.g., Kafka lag). Use **KEDA** when scaling needs to be driven by external metrics rather than just resource utilization.

**CL7** — **RPO** (Recovery Point Objective) is max data loss; **RTO** (Recovery Time Objective) is max downtime. **Active-Active** runs in two regions simultaneously (zero RTO); **Active-Passive** has a standby (higher RTO). **Sync replication** ensures no data loss but adds latency; **Async** is faster but risks data loss. **Pilot Light** (minimal resources running), **Warm Standby** (scaled-down version), and **Multi-site Active-Active** (full capacity in both) represent increasing costs and decreasing RTO.

**CL8** — **GitOps** uses Git as the single source of truth for state. **ArgoCD** (Pull-based, K8s native) vs. **FluxCD** (Lightweight, modular). For **Secrets**, use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault/AWS SM), or **HashiCorp Vault**. Manual changes cause **drift**, which GitOps controllers automatically revert to match the Git state.

**CL9** — Use a **StatefulSet** for stable identities. Use **PV/PVC** with a **Local Storage Class** for low latency. Use a **Headless Service** for direct pod addressing. Use **Init Containers** to prepare the filesystem. Mount **ConfigMaps** as volumes for specific paths. Use **Pod Disruption Budgets (PDB)** to ensure availability during maintenance.

**CL10** — **Service Account** is K8s-internal; **Workload Identity** is the cloud-native mapping of K8s identities to Cloud IAM; **IRSA** is the AWS implementation. Mounting static credentials in a pod is bad because they are long-lived and easily stolen. **Workload Identity Federation** uses OIDC to exchange a short-lived K8s token for a cloud IAM token.

**CL11** — **Object Storage** (S3/Blob) is for unstructured data (unlimited scale, high durability). **Block Storage** (EBS/Managed Disk) is for OS/Databases (low latency, attached to one VM). **File Storage** (EFS/Azure Files) is for shared access (NFS/SMB). Durability is typically "11 nines"; availability varies by tier/redundancy.

**CL12** — **Zero-Trust** assumes no implicit trust. Use **Network Policies** (pod-level), **Service Mesh/mTLS** (identity-based encryption), **Admission Controllers** (OPA/Kyverno to enforce rules), **Image Signing** (ensure only trusted code runs), and **Falco** (detect runtime anomalies). Unlike perimeter security, Zero-Trust verifies every request regardless of location.

**CL13** — A **CDN** caches content at edge locations closer to users to reduce latency. Services: **AWS CloudFront**, **Azure CDN**. Use a CDN for static assets (images, JS) or global users; use an **Origin Server** for dynamic, non-cacheable data.

**CL14** — **Regions** are geographic areas; **Availability Zones (AZs)** are isolated data centers within a region. Deploy across multiple AZs for **High Availability**. **Zonal resources** (e.g., a single EBS volume) live in one AZ; **Regional resources** (e.g., S3) are available across the whole region.

**CL15** — A **Managed Database** (RDS/Cloud SQL) handles patching, backups, hardware provisioning, and high availability. In a **VM-based DB**, you must manually manage the OS, disk scaling, and replication.

**CL16** — **Users** (individuals), **Groups** (collections of users), **Roles** (temporary identities), and **Policies** (permission definitions). **Least Privilege** means granting only the minimum permissions required for a task. Apply it by using fine-grained IAM policies and avoiding `*` (wildcard) permissions.

**CL17** — **Serverless** is event-driven execution without managing servers. **Lambda/Functions** scale automatically. **Cold starts** are the latency delay when a function is invoked after being idle. Serverless is a poor fit for long-running processes or applications requiring constant, high-performance throughput.

**CL18** — **Ingress** is the standard K8s resource; **Gateway API** is the modern, role-oriented evolution. **Cloud Load Balancers** handle L4/L7 at the edge. **Service Mesh** handles L7/mTLS between pods. Use **Gateway API** when you need to decouple infrastructure management from application routing.

**CL19** — Use **Reserved Instances/Savings Plans** for predictable workloads; **Spot Instances** for fault-tolerant/batch jobs. **Right-sizing** ensures resources match demand. **Storage Tiering** moves old data to cheaper tiers (S3 Glacier). Implement **FinOps** (culture of cost awareness) and use **Showback/Chargeback** to hold teams accountable via tagging.

**CL20** — **Multi-cloud** uses **Kubernetes** as an abstraction, **Terraform** for IaC, and **Identity Federation** to bridge clouds. **Networking** uses VPNs or Interconnects. It is justified for compliance or extreme DR but is often unnecessary complexity due to the high overhead of managing two different control planes.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** L0 (Physical Process), L1 (Basic Control/PLCs), L2 (Supervisory/HMI), L3 (Site Operations/SCADA), L4 (Business/IT), L5 (Enterprise).

**OT2** — **IT** focuses on Data Confidentiality; **OT** focuses on Safety and Availability. You cannot use standard IT patching because OT systems are sensitive to latency and downtime; a reboot can cause physical damage or safety risks.

**OT3** — An **IDMZ** acts as a buffer. Only specific, inspected traffic (e.g., OPC UA, MQTT) should cross. Direct L4 $\rightarrow$ L1 connectivity is dangerous as it allows an IT breach to directly manipulate physical hardware.

**OT4** — **Modbus TCP** (L1/L2), **OPC UA** (L2/L3), **EtherNet/IP** (L1/L2), **PROFINET** (L1/L2), **MQTT** (L3/L4/Cloud).

**OT5** — A **Data Diode** is a hardware device that physically allows data to flow in only one direction (unidirectional). A **Firewall** is software-based and bidirectional. Use a diode for high-security isolation where no return path is permitted.

**OT6** — **Flow:** PLC $\rightarrow$ SCADA/Historian $\rightarrow$ Edge Gateway $\rightarrow$ MQTT Broker $\rightarrow$ Cloud. Security boundaries should be placed at the **IDMZ** (between L3 and L4) and at the **Edge Gateway** (between OT and IT/Cloud).

**OT7** — **Zones** are groups of assets with similar security requirements. **Conduits** are the communication paths between zones. **Model:** Corporate (L4) $\rightarrow$ IDMZ $\rightarrow$ SCADA (L3) $\rightarrow$ PLC (L1). The **SIS** (Safety Instrumented System) should be in its own isolated zone.

**OT8** — Use **VLANs** to segment production lines. Place **Firewalls** between lines and between L3/L4. Use **Jump Hosts** with MFA for vendor access. Transition via a **phased approach**: mirror traffic to test segmentation before enforcing rules to avoid production stops.

**OT9** — **BPCS** controls the process; **SIS** is the independent safety layer. **IEC 61511** governs functional safety. The SIS must be isolated because if a ransomware attack reaches it, an attacker could disable safety shutdowns, leading to catastrophic physical failure.

**OT10** — **PLC** (Logic/Device), **DCS** (Integrated process control), **SCADA** (Supervisory/Wide area). They can coexist; SCADA often supervises multiple PLCs or DCS components.

**OT11** — Use **Jump Hosts** with **MFA**, **Session Recording**, and **Time-limited access**. Direct RDP from corporate to HMI is unacceptable as it bypasses all segmentation and creates a direct path for lateral movement.

**OT12** — **Plan:** Deploy **IDS** for anomaly detection, perform **Asset Inventory** to find the breach, **Isolate** the L3 network, and **Coordinate** with the control room. The **Plant Operator** must be able to take manual control of the process to ensure safety during the cyber incident.

**OT13** — An **HMI** is a visual interface for operators to interact with machines. An **Engineering Workstation** is used by engineers to program and configure the controllers.

**OT14** — A **Historian** logs process data for analysis. A **Plant Historian (L3)** is for real-time/local operations; an **Enterprise Historian (L4)** is for long-term business analytics.

**OT15** — **Ladder Logic** is a graphical programming language used by **PLCs**. It remains dominant because it is intuitive for electricians and highly reliable for simple, deterministic logic.

**OT16** — An **RTU** (Remote Terminal Unit) is used for long-distance telemetry (e.g., pipelines); a **PLC** is used for high-speed, local logic. RTUs are better for geographically dispersed, low-bandwidth environments.

**OT17** — **Analog** (continuous, e.g., 4-20mA) vs. **Digital** (discrete, e.g., On/Off). **4-20mA** is preferred because a "0mA" reading indicates a broken wire (Live Zero), whereas 0-20mA cannot distinguish between a zero reading and a failed sensor.

**OT18** — **Asset Inventory** is the foundation of visibility. Use **Passive Monitoring** (SPAN/Mirror ports) to avoid disruption. **Active Scanning** is dangerous because it can overwhelm old PLC stacks and cause them to crash.

**OT19** — **MITRE ATT&CK for ICS** focuses on physical impact. Tactics: **Initial Access** (e.g., Phishing), **Execution** (e.g., Program Upload), **Inhibition of Response Function** (e.g., Blinding the HMI). It differs by focusing on the "Physical" impact of cyber actions.

**OT20** — Use **Passive Log Collection** to avoid impacting real-time traffic. Integrate with a **SIEM**. For **unauthorized firmware changes**, triage by involving an **OT Engineer** to verify if the change was a scheduled maintenance or a malicious act, ensuring the physical process remains safe.
