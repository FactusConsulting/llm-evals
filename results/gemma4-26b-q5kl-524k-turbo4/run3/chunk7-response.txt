## Application Architecture

**AA1** — A **monolith** is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. **Microservices** decompose this into independent, loosely coupled services. 
*Three problems introduced by microservices:* 1. Network latency/complexity, 2. Distributed data consistency (distributed transactions), 3. Observability challenges (distributed tracing).

**AA2** — **Synchronous** communication requires the caller to wait for a response before proceeding (e.g., **HTTP/REST**). **Asynchronous** communication allows the caller to send a message and continue immediately (e.g., **RabbitMQ**).

**AA3** — A **reverse proxy** sits in front of servers to handle routing, SSL termination, or caching. An **API Gateway** adds application-level logic like authentication, rate limiting, and request orchestration. An API Gateway can replace a reverse proxy, but a reverse proxy is often a component *within* an API Gateway.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. 
*   **Choreography:** Each service produces/listens to events; no central controller. Best for simple workflows.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex, multi-step business logic.

**AA5** — **CQRS** separates the models for reading data from the models for writing data. It is paired with **Event Sourcing** (storing state as a sequence of events) because Event Sourcing provides the "source of truth" needed to rebuild the specialized read models required by CQRS. This solves the problem of complex queries and audit requirements that traditional CRUD models struggle to handle efficiently.

**AA6** — The **Circuit Breaker** prevents a service from repeatedly trying an operation that is likely to fail. 
*   **States:** **Closed** (requests flow), **Open** (requests fail immediately), **Half-Open** (limited requests allowed to test recovery). 
*   **Difference:** A **retry with backoff** handles transient "glitches"; a **Circuit Breaker** handles systemic failures. Use both together: retry for a single timeout, but trip the circuit if retries keep failing.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, lowest complexity, highest security risk (data leakage), highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Medium cost/complexity, better security isolation, moderate noisy-neighbor risk.
3. **Separate DB:** Highest cost and operational complexity, highest security, lowest noisy-neighbor risk.

**AA8** — **Strong consistency** ensures all nodes see the same data simultaneously. For an inventory system: Use **Strong Consistency** with an **RDBMS** (e.g., PostgreSQL) using **ACID** transactions and **pessimistic locking** (SELECT FOR UPDATE) to prevent overselling. At scale, use distributed locks (e.g., via **Redis/Etcd**) to coordinate across service instances.

**AA9** — A **sidecar proxy** is a helper process running alongside an application. In **Istio**, **Envoy** acts as the sidecar (Data Plane) handling all network traffic, while **Istio** acts as the **Control Plane**, managing configuration and policy. **mTLS** between sidecars ensures identity and encryption at the infrastructure layer, preventing "man-in-the-middle" attacks without requiring the application code to manage certificates.

**AA10** — The **Strangler Fig** pattern involves placing a proxy in front of the monolith. 
*   **Strategy:** 1. Deploy a proxy/gateway. 2. Identify a specific bounded context (e.g., "Billing"). 3. Build "Billing" as a new .NET 8 microservice. 4. Update the proxy to route all `/billing` traffic to the new service. 5. Repeat until the monolith is "strangled."

**AA11** — The **12-Factor App** ensures cloud-native portability. 
1. **Codebase:** One repo per app. 2. **Dependencies:** Explicitly declare/isolate. 3. **Config:** Store in environment. 4. **Backing Services:** Treat as attached resources. 5. **Processes:** Stateless and stateless. 6. **Port Binding:** Export services via port binding. (These matter for scaling, automation, and environment parity).

**AA12** — 
*   **Event-Driven (Kafka):** High decoupling, massive scalability, complex debugging, eventual consistency, high ordering guarantees (within partitions).
*   **Request-Driven (REST/gRPC):** Tight coupling, lower scale, easy debugging, strong consistency/immediate failure.
*   **Choice:** Use Kafka for high-throughput, asynchronous workflows; use REST/gRPC for real-time, synchronous user-facing requests.

**AA13** — A **load balancer** distributes incoming traffic across multiple servers. **Layer 4** works at the transport level (IP/Port). **Layer 7** works at the application level (HTTP). **Use case:** Path-based routing (e.g., sending `/api` to one cluster and `/images` to another).

**AA14** — A **message queue** (RabbitMQ) is designed for task distribution (competing consumers) and usually deletes messages after processing. A **log-based broker** (Kafka) is an append-only immutable log where messages persist, allowing for "replayability." Pick MQ for simple task offloading; pick Kafka for stream processing and event sourcing.

**AA15** — A **container** shares the host OS kernel, making it lightweight. A **VM** includes a full guest OS and runs on a hypervisor. Containers are popular because they start instantly and have minimal overhead, making them ideal for rapid microservice scaling.

**AA16** — **Stateless** services do not store client data locally (e.g., a REST API). **Stateful** services maintain data (e.g., a Database). Stateless services scale horizontally easily because any instance can handle any request.

**AA17** — An **ORM** maps database rows to objects in code. Examples: **Hibernate** (Java), **Entity Framework** (.NET). **Trade-offs:** ORMs increase developer productivity but can introduce performance overhead and "N+1" query problems compared to raw SQL.

**AA18** — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue. 
*   **Implementation:** Use separate **thread pools** for different service calls or deploy services into separate **resource groups/clusters** so a memory leak in one doesn't starve the others.

**AA19** — **OT** requires a central server to resolve conflicts (high complexity, high consistency). **CRDTs** allow decentralized, mathematical convergence (lower complexity for the server, better offline support). For **offline editing**, choose **CRDTs** because they allow local updates that merge seamlessly when connectivity returns without a central coordinator.

**AA20** — Challenges include maintaining a single trace across services. 
*   **Context Propagation:** Passing IDs (W3C Trace Context/B3) in headers. 
*   **Sampling:** **Head-based** (decide at start) vs **Tail-based** (decide after the trace completes, e.g., keep only errors). 
*   **Kafka:** To ensure continuity, the producer must inject the trace context into the **Kafka message headers**, which the consumer then extracts to continue the span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., **ESXi, Proxmox**). **Type 2 (Hosted):** Runs on an OS (e.g., **VirtualBox, VMware Workstation**).

**OP2** — **SAN (Storage Area Network):** Block-level storage (e.g., **iSCSI, Fibre Channel**). **NAS (Network Attached Storage):** File-level storage (e.g., **NFS, SMB**). Use SAN for high-perf databases/VMs; NAS for shared file storage.

**OP3** — **3-tier** is Core/Dist/Access. **Leaf-Spine** connects every leaf switch to every spine switch. It solves the "East-West" latency problem in modern data centers by providing predictable, low-latency paths between servers.

**OP4** — A HA Proxmox cluster needs **3+ nodes** for quorum. Use **Ceph** or **iSCSI** for shared storage. Use **Fencing (STONITH)** to kill a failing node to prevent data corruption. If a node fails, the cluster detects the loss of quorum/heartbeat and restarts the VMs on healthy nodes.

**OP5** — **VLAN trunking** allows multiple VLANs over one link using **802.1Q** tags. On Linux, configure this using sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — **RAID 1** (Mirror), **5** (Parity, 1 drive loss), **6** (Double parity, 2 drives), **10** (Striped Mirror), **Z2** (ZFS parity). For a database: **RAID 10** is best as it provides the highest performance and redundancy.

**OP7** — Use **Internal AD** for local auth. **Split-horizon DNS** serves different IPs for internal vs external queries. **DNSSEC** signs external zones. **Recursive resolvers** handle client queries; **Forwarders** send unknown queries to the internet. A laptop on VPN uses **Conditional Forwarding** to reach internal resources.

**OP8** — **Root CA** (Offline/Master) $\rightarrow$ **Subordinate CA** (Issuing) $\rightarrow$ **End-entity**. Use **CRL/OCSP** for revocation. A compromised **Subordinate CA** is a localized breach; a compromised **Root CA** destroys the entire trust chain.

**OP9** — **MPLS** (High cost/reliability), **IPsec** (Low cost/Internet), **SD-WAN** (Smart/Hybrid), **WireGuard** (Fast/Mesh). For **latency-sensitive VoIP**, I recommend **SD-WAN** for its ability to prioritize traffic and intelligently route over the best available path.

**OP10** — **iDRAC/iLO/IPMI** provide **out-of-band** management (accessing hardware even if the OS is down). It is critical for remote recovery. If exposed to the internet, it is a massive security risk (unauthenticated hardware control).

**OP11** — **LVM** (Logical volumes), **LVM-Thin** (Space-efficient, thin-provisioned), **ZFS** (Copy-on-write, integrated volume/FS). LVM snapshots are metadata-based; ZFS snapshots are near-instant and highly efficient.

**OP12** — A **stretch cluster** requires low latency (<5ms). Use **Ceph CRUSH rules** to ensure data is spread across sites. A **2-site Ceph** setup is dangerous because if the link breaks, neither side has a majority (quorum), leading to **split-brain**. A 3rd site (witness) is required.

**OP13** — **DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge. If the server is unavailable, the client uses an **APIPA** address (169.254.x.x).

**OP14** — **Managed switches** allow VLANs, SNMP, and Spanning Tree. **Unmanaged** are "dumb" plug-and-play. Managed switches are essential for security and traffic segmentation in enterprises.

**OP15** — **NTP** synchronizes clocks. Drift causes: Log correlation failure, Kerberos/Authentication failures, and database transaction inconsistencies.

**OP16** — **Physical** (Hardware), **VM** (Hypervisor), **Container** (OS-level). Run on **bare metal** for high-performance workloads like heavy databases or ML training to avoid hypervisor overhead.

**OP17** — **UPS** provides short-term battery power; **Generator** provides long-term power. An **ATS** automatically switches the load from mains to the generator when power fails.

**OP18** — **Active-Passive** has a standby node. Using **Pacemaker/Corosync**, you manage a **Virtual IP**. If the primary fails, **STONITH** (Shoot The Other Node In The Head) ensures the failed node is truly powered off before the VIP moves to the standby.

**OP19** — **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite. **RPO** (how much data you can lose) and **RTO** (how long you can be down). **Immutable backups** protect against ransomware. **Backup** is data copying; **Disaster Recovery** is the plan to resume operations.

**OP20** — **Supplicant** (Client), **Authenticator** (Switch), **Server** (RADIUS). **EAP-TLS** (Certificates) is more secure than **PEAP** (Passwords). **MAB** allows non-802.1X devices (printers) to connect based on their MAC address.
