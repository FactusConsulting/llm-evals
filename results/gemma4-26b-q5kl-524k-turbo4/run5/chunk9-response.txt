## SC1
**SC1-A:** The pods are failing because the transition from **Baseline** to **Restricted** Pod Security Standards (PSS) enforces stricter requirements on user IDs. Under the **Baseline** profile, `runAsNonRoot: true` is permitted even if a specific `runAsUser` is not defined, as long as the container doesn't attempt to start as UID 0. However, the **Restricted** profile requires that the pod spec explicitly defines a non-zero `runAsUser` (e.g., `runAsUser: 1000`) to ensure the container cannot escalate to root. Since the new Chainguard base image defaults to `USER root` and the manifests lack an explicit `runAsUser`, the Kubernetes admission controller (or the container runtime) rejects the pod because it violates the "must run as non-root" requirement without a defined non-root UID.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -c '.items[] | select(.status.containerStatuses != null and (.status.containerStatuses[].state.waiting.reason == "CrashLoopBackOff")) | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level:** Rebuild images with an explicit `USER 1000` (or any non-zero UID) in the Dockerfile.
*   **Manifests:** Add `securityContext: { runAsNonRoot: true, runAsUser: 1000 }` to the Deployment templates.
*   **CI Pipeline:** Implement a `conftest` or `checkov` step that scans manifests for the presence of `runAsUser` when `runAsNonRoot` is true.
*   **Rollout:** Perform a RollingUpdate. Since the issue is a configuration mismatch, the new manifests will resolve the `CrashLoopBackOff` as the new pods will satisfy the Restricted PSS.

## SC2
**SC2-A:** The stale data is caused by **asynchronous replication**. In PostgreSQL streaming replication, the primary sends WAL (Write Ahead Log) records to the replica. In an async setup, the primary acknowledges the write to the application before the replica confirms receipt. When you promote the replica, any WAL records that were in flight but not yet applied to the EU instance are lost. To quantify the data loss window, check `pg_stat_replication` on the old primary (if reachable) or monitor `write_lag` and `replay_lag` metrics.

**SC2-B:**
1.  **Identify:** Run `terraform plan` to see the proposed changes.
2.  **Remove from State:** `terraform state rm aws_db_instance.old_instance_name` (to stop TF from trying to manage/delete it).
3.  **Import New Instance:** `terraform import aws_db_instance.new_instance_name <new_arn_or_id>`.
4.  **Update Code:** Manually update the HCL to point to the new ARN.
5.  **Apply:** `terraform apply` to align the state with the new promoted instance and update dependent resources (SGs, Route53).

**SC2-C:**
*   **Architecture:** Use **Amazon Aurora Global Database**. It uses storage-level replication with a dedicated replication fleet, offering RPO < 1 second.
*   **Connection Management:** Use **RDS Proxy** to handle connection pooling and gracefully manage failovers/reconnects.
*   **DNS:** Use **Route53 Health Checks** with a Failover Routing Policy pointing to the primary endpoint.
*   **App Logic:** Implement exponential backoff and jitter in the application's connection retry logic.

## SC4
**SC4-A:**
1.  **Sticky Sessions:** K8s Services are load-balanced; local memory sessions will break. *Solution:* Move sessions to Redis.
2.  **Local NFS:** Pods are ephemeral; `/data/uploads` will vanish on restart. *Solution:* Use a CSI driver with `ReadWriteMany` (RWX) storage.
3.  **Oracle DB:** Hard to scale/migrate. *Solution:* Use a managed service or a dedicated DB operator.
4.  **IBM MQ:** Requires specific connectivity/protocols. *Solution:* Use a sidecar proxy or a dedicated bridge service.
5.  **F5 Load Balancer:** Moving to K8s requires an Ingress Controller. *Solution:* Replace F5 with NGINX or HAProxy Ingress.

**SC4-B:**
```hcl
variable "nfs_server" { type = string }
variable "export_path" { type = string }
variable "storage_capacity" { type = string }

resource "kubernetes_csi_storage_class" "nfs" {
  metadata { name = "nfs-csi" }
  driver = "nfs.csi.k8s.io"
  parameters = {
    server = var.nfs_server
    share  = var.export_path
  }
}

resource "kubernetes_persistent_volume" "pv" {
  metadata { name = "nfs-pv" }
  spec {
    capacity = { storage = var.storage_capacity }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source {
      csi { volume_handle = "nfs-vol" }
    }
  }
}

resource "kubernetes_persistent_volume_claim" "pvc" {
  metadata { name = "nfs-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    resources { requests = { storage = var.storage_capacity } }
    storage_class = "nfs-csi"
  }
}
```
*Note: `ReadWriteMany` is required because multiple pods (replicas) need to access the same shared filesystem simultaneously.*

**SC4-C:**
*   **Phase 1 (Proxy):** Deploy the app to K8s but keep the DB/MQ on-prem. Use the F5 to route a small % of traffic to the K8s Ingress.
*   **Phase 2 (Data):** Migrate the file storage to the CSI/NFS. Use a "Data Bridge" for MQ.
*   **Phase 3 (Full Cutover):** Move the DB.
*   **Rollback:** Keep the F5 pointing to bare-metal; if K8s error rates spike, flip the F5 weight back to 100% bare-metal.
*   **Metrics:** Error rate (5xx), Latency (p99), and MQ queue depth.

## SC7
**SC7-A:**
*   **Manual Apply:** Causes "State Drift."
*   **Diverged Values:** Causes "Configuration Drift."
*   **kubectl edit:** Causes "Shadow IT/Manual Drift."
*   **No Locking:** If two engineers run `apply` simultaneously, the state file can be corrupted or partially written, leading to a "split-brain" infrastructure where the state doesn't match reality.

**SC7-B:**

  environment: production

*Note: Use a DynamoDB backend for `tofu` to enable state locking.*

**SC7-C:**

*   **Prevention:** Use **OPA Gatekeeper** to deny `kubectl edit` on specific resources.
*   **Structure:** Use **Kustomize** to have a `base/` directory and `overlays/prod/` for environment-specific values.
*   **RBAC:** Grant `AdministratorAccess` only to the CI Service Account in AWS and `cluster-admin` only to the CI runner in K8s.
