**CL1** — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, runtime, data, and apps (e.g., AWS EC2). PaaS provides runtime, middleware, and OS; you manage apps and data (e.g., AWS Elastic Beanstalk). SaaS provides fully managed applications; you only manage user access and data (e.g., AWS WorkSpaces).

**CL2** — The Shared Responsibility Model divides security: provider secures the cloud infrastructure (hardware, global network, hypervisor, physical facilities); customer secures what they put in it. IaaS VM: Provider = infra/hypervisor; Customer = OS, patches, network config, data, app. Managed K8s: Provider = control plane, node OS/patches, etcd; Customer = worker apps, network policies, RBAC, data, secrets. SaaS (M365): Provider = app, infra, compliance config, patching; Customer = user accounts, data, access policies, MFA, device compliance.

**CL3** — VPC: Isolated virtual network. Subnet: IP range within a VPC, tied to an AZ. Security Group (SG): Instance-level, stateful, allow-only rules. NACL: Subnet-level, stateless, allow/deny rules. Layering: Traffic enters VPC → hits NACL (subnet) → hits SG (instance). Stateful (SG): Return traffic automatically permitted. Stateless (NACL): Return traffic must be explicitly allowed.

**CL4** — Landing zone: Pre-configured, secure multi-account baseline with networking, logging, IAM, and guardrails. OUs: Logical groupings (Sandbox, Dev, Prod, Shared). Guardrails: SCPs/policies enforcing compliance (region restrictions, encryption mandates). Shared Networking: Transit Gateway/Azure Hub-and-Spoke for centralized inter-VPC/VNet routing. Centralized Logging: Dedicated account/service aggregates logs for audit/forensics. Single-account problems: Unbounded blast radius, permission sprawl, billing opacity, compliance violations, environment isolation failure, resource contention.

**CL5** — IaC: Managing infrastructure via version-controlled, machine-readable definitions. Terraform/OpenTofu: Declarative HCL, multi-cloud, mature ecosystem; best for multi-cloud, broad provider support. Pulumi: Imperative/Declarative using general-purpose languages; best for complex logic, existing dev teams. CloudFormation/Bicep: AWS-native declarative; Bicep improves syntax; best for AWS-only, tight CI/CD integration. Crossplane: K8s-native IaC (CRDs); best for GitOps/K8s-centric teams managing cloud resources as K8s objects.

**CL6** — HPA: Scales pods based on CPU/memory/custom metrics. VPA: Recommends/sets optimal resource requests/limits per pod. Cluster Autoscaler: Adds/removes nodes based on pending pods/resource pressure. KEDA: Event-driven scaling based on external triggers (queues, streams, HTTP). Use KEDA over HPA when scaling must be driven by external event volumes or custom metrics not tied to pod resource consumption.

**CL7** — RPO/RTO define acceptable data loss and downtime. Active-Active: Both regions serve traffic; lower RPO/RTO, higher cost/complexity. Active-Passive: One serves, one standby; higher RTO, lower cost. DB Replication: Sync (strong consistency, higher latency, active-active) vs Async (eventual consistency, lower latency, active-passive). DNS Failover: Route53/Traffic Manager health checks route to healthy region. State Management: Externalize state (S3, DynamoDB, Redis) to avoid region lock-in. Cost: Active-active doubles infra; passive saves ~40-60%. DR Types: Pilot Light (core infra running, scaled down), Warm Standby (scaled-down but fully functional), Multi-site Active-Active (both fully operational).

**CL8** — GitOps: Git is the single source of truth; controllers continuously reconcile cluster state with Git. ArgoCD: Push/pull, UI-heavy, app-of-apps, easier UX. Flux: Git-native, Kustomize/Helm, CLI-first, tight GitHub/GitLab integration. Secrets: Sealed Secrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from Vault/AWS SM), SOPS + Kustomize. Drift: Manual changes are overwritten on next sync; GitOps enforces declarative state and reverts drift automatically.

**CL9** — StatefulSet: Stable network ID, ordered deployment/termination, stable storage. PV/PVC + Local Storage: `local` storageClass with `volumeBindingMode: WaitForFirstConsumer` to bind to node with local disk. Headless Service: `clusterIP: None` enables direct pod DNS resolution. Init Containers: Pre-load config, check dependencies, set permissions before main app. ConfigMaps: Mount as volumes at specific paths via `subPath` or direct mount. PDB: `minAvailable`/`maxUnavailable` ensures minimum pods during disruptions. Note: Local storage lacks replication; implement external backups.

**CL10** — SA: K8s-native identity, no cloud permissions by default. Workload Identity (GCP/Azure): Maps K8s SA to cloud IAM identity without keys. IRSA (AWS): Maps K8s SA to IAM Role via OIDC provider; pod assumes role via STS. Mounting static credentials is bad practice due to leakage, rotation overhead, and over-privilege. Federation solves this via OIDC-based trust, short-lived tokens, automatic rotation, and least-privilege per workload.

**CL11** — Object (S3/Blob): Unstructured data, HTTP API, 11 9s durability, eventual consistency; use for backups, media, logs. Block (EBS/Managed Disk): Raw volumes, low latency, high IOPS, 99.999% durability; use for OS, databases, apps needing file systems. File (EFS/Azure Files): NFS/SMB, shared across VMs, scalable; use for shared configs, home dirs, legacy apps. Availability: Object ~99.99%, Block ~99.99%, File varies by tier but matches block/object guarantees.

**CL12** — Network Policies: Default deny, explicit pod-to-pod allow. Service Mesh (mTLS): Istio/Linkerd for encrypted service-to-service comms and identity-based routing. Pod Identity: IRSA/Workload Identity for cloud access. Admission Controllers: OPA/Kyverno enforce policies (no privileged pods, require limits). Image Signing: Cosign/Notary + admission controller rejects unsigned images. Runtime Security: Falco monitors syscalls for anomalies. Secrets: External Secrets Operator/Vault, never in env vars/plain ConfigMaps. Differs from perimeter: No implicit trust based on network location; every request authenticated/authorized regardless of origin.

**CL13** — CDN: Distributed edge cache network serving content from locations closest to users. Works via Anycast/DNS routing, caching static/dynamic content at edge nodes, fetching from origin only on cache miss. Services: CloudFront (AWS), Azure CDN, Fastly, Cloudflare. Use CDN for static assets, global distribution, DDoS mitigation, and origin offloading. Serve directly from origin for low-latency dynamic APIs, private/internal content, or when edge caching adds unnecessary complexity.

**CL14** — Region: Geographic area with multiple AZs. AZ: Discrete data centers with independent power/cooling/networking, low-latency interconnects. Multi-AZ deployment protects against single data center failure, ensuring high availability. Zonal resources: Tied to specific AZ (EBS, EC2, subnets). Regional resources: Span multiple AZs (ELB, Route53, S3, IAM).

**CL15** — Managed DB (RDS/Cloud SQL/Azure SQL): Provider handles provisioning, patching, backups, automated failover, monitoring, storage scaling, and minor version upgrades. Self-hosted on VM: You manage OS, DB software, backups, replication, HA setup, security patches, and scaling. Operational tasks offloaded include patching, point-in-time recovery, automated failover, storage tiering, and monitoring/alerts.

**CL16** — IAM Users: Human/service identities with long-term credentials (avoid). Groups: Collections for policy assignment. Roles: Temporary credentials for services/workloads, assumed via trust policies. Policies: JSON documents defining permissions. Least Privilege: Grant only necessary permissions. Apply via role-based access, scoped policies, deny-by-default, regular access reviews, and just-in-time access.

**CL17** — Serverless: Managed compute where provider handles scaling/infra; pay per execution. Compare: Lambda (AWS), Azure Functions (Azure), GCF (GCP). Similar event-driven/auto-scaling but differ in runtime support, cold start behavior, and ecosystem lock-in. Cold Starts: Initialization delay for first request; matters for latency-sensitive apps. Mitigate with provisioned concurrency, keep-warm, lighter runtimes. Poor fit: Long-running processes, stateful apps, predictable high-throughput (reserved VMs cheaper), strict compliance/network isolation, or vendor lock-in concerns.

**CL18** — Ingress Resource: Standard K8s API, requires Ingress Controller (nginx, ALB); TLS termination at controller. Gateway API: Newer, structured, multi-protocol, better RBAC; TLS termination at Gateway. Cloud LB Annotations: Directly provision cloud LB (ALB/NLB); TLS termination at cloud LB. Service Mesh Ingress: Istio/Linkerd gateway; mTLS termination, advanced traffic management. Use Gateway API over Ingress for fine-grained RBAC, multi-tenant routing, protocol flexibility (HTTP/gRPC/TCP), or standardized policy attachment.

**CL19** — RI/SP: Commit 1-3yr for compute; SP more flexible. Spot/Preemptible: Up to 90% savings for fault-tolerant/batch workloads. Right-sizing: Monitor utilization, downsize over-provisioned, use auto-scaling. Storage Tiering: Lifecycle policies to IA/Glacier, delete orphaned snapshots/EBS. Idle Detection: Unattached volumes, idle LBs, unused IPs, schedule non-prod shutdowns. FinOps: Cross-functional culture, tagging, budget alerts, regular reviews. Showback/Chargeback: Tag by team/project, allocate via billing reports, incentivize optimization. Tools: Cost Explorer, CUR, Kubecost/OpenCost, native budgeting. Process: Monthly reviews, optimization backlogs, automated tagging enforcement.

**CL20** — Abstraction: K8s, Terraform, service meshes, API gateways decouple from vendor specifics. K8s runtime: EKS/AKS/GKE for consistent deployment. Terraform: Provider-agnostic IaC, modular design, isolated state. Networking: Cloud VPN, Direct Connect/ExpressRoute, global LBs, DNS routing. Identity: OIDC federation, centralized IdP, cross-cloud trust. Trade-offs: Higher complexity, operational overhead, data egress costs, inconsistent features, talent fragmentation. Justified: Regulatory/data sovereignty, avoiding single-vendor risk, best-of-breed services, M&A. Unnecessary: Startups, homogeneous workloads, limited budget/talent, when cloud-native features outweigh lock-in risk.

**OT1** — Purdue Model (ISA-95): Enterprise-control system integration framework. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, relays). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Manufacturing operations (MES, scheduling). Level 4: Business planning (ERP, finance). Level 5: Corporate/IT network.

**OT2** — IT networks prioritize confidentiality/integrity, are dynamic, and support frequent patching. OT networks prioritize availability/safety, are static/legacy, and require real-time deterministic operation. Standard IT patching fails in OT due to decades-old OS/software, lack of maintenance windows, update-induced downtime/safety risks, and requirement for vendor validation and strict change management.

**OT3** — DMZ (IDMZ): Segmented network zone between IT and OT, firewalled. Traffic: Strictly controlled bidirectional or unidirectional. OT→IT: Process data, alarms, metrics (preferred unidirectional). IT→OT: Commands/schedules (filtered, audited). Direct L4→L1 connectivity bypasses security controls, exposes critical control logic to IT threats, enables lateral movement to safety systems, and violates Purdue segmentation principles.

**OT4** — Modbus TCP: L1/L2, PLC communication, master/slave, unencrypted. OPC UA: L2/L3, secure, platform-independent, information modeling, pub/sub or client/server. EtherNet/IP (CIP): L1/L2, industrial Ethernet, TCP/UDP, Rockwell dominant. PROFINET: L1/L2, real-time Ethernet, IO/IRT variants, Siemens dominant. MQTT: L2/L3/L4, lightweight pub/sub, IoT/cloud telemetry, secured with TLS.

**OT5** — Data Diode: Hardware-enforced unidirectional communication (fiber/electrical); only allows data flow one way. Firewall: Bidirectional, inspects packets, allows/denies based on rules. Use diode when strict unidirectional flow is required (e.g., OT→IT telemetry) with zero reverse traffic risk. Limitation: Cannot allow any return traffic (acknowledgments, commands), less flexible than firewalls, requires careful protocol design.

**OT6** — Flow: PLCs/RTUs → OPC UA Server (historian/edge) → Edge Gateway (translation, buffering, hardening) → MQTT Broker (TLS, client certs) → Cloud Ingestion (AWS IoT Core/Azure IoT Hub) → Analytics/Storage. Security Boundaries: OPC UA server (internal OT, mutual TLS, RBAC). Edge gateway (firewalled, hardened, local buffering). MQTT broker (TLS, network segmentation). Cloud ingestion (IAM, VPC endpoints, DDoS protection). DMZ between OT and edge/cloud.

**OT7** — Zone: Logical grouping of assets with similar security requirements/risk. Conduit: Controlled communication path between zones. Model: Zone 1: Corporate/IT (L4/5). Zone 2: Engineering Workstations (L3). Zone 3: SCADA/Historian (L2). Zone 4: PLCs/Controllers (L1). Zone 5: SIS (isolated). Conduits: Z1→Z2 (firewall, MFA), Z2→Z3 (firewall, audit), Z3→Z4 (firewall/diode, strict allow-list), Z4↔Z5 (physical/logical isolation, no direct conduit).

**OT8** — VLAN Design: Segment by function/process (e.g., VLAN 10: Line 1 PLCs, 20: Line 2 PLCs, 30: HMIs, 40: SCADA, 50: Engineering). Firewall Placement: Core firewall IT/OT, edge firewalls between VLANs, DMZ for vendor access. Switch Architecture: Managed L3 switches, port security, 802.1X (if supported), disable unused ports. Remote Access: Jump host in DMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: Phased rollout, parallel run, maintenance windows, rollback plan, validate control logic before cutover, coordinate with operations.

**OT9** — BPCS: Basic Process Control System (PLCs/DCS) for routine control. SIS: Safety Instrumented System for emergency shutdown, independent of BPCS. IEC 61511: Standard for functional safety of SIS in process industry; defines SIL requirements. Isolation: Prevents cyber attacks on BPCS/IT from compromising safety functions; SIS must operate independently to guarantee safety during failures. Ransomware on SIS: Safety functions may fail to activate, causing catastrophic incidents, environmental damage, or loss of life. Hence, air-gap/isolation is critical.

**OT10** — PLC: Programmable Logic Controller, discrete control, fast, modular, used for specific machines/lines. DCS: Distributed Control System, centralized architecture, integrated I/O, used for continuous/process industries. SCADA: Supervisory Control and Data Acquisition, software layer for monitoring/control across dispersed assets, aggregates PLC/DCS data. Coexist: Yes. PLCs/DCS handle local control, SCADA provides supervisory view, historians store data, HMIs display to operators.

**OT11** — Remote Access Architecture: Jump hosts in DMZ for all sessions, mandatory MFA, session recording for audit, time-limited/role-based vendor access with approved tickets. RDP directly to HMI from corporate is unacceptable because it exposes OT directly to IT, bypasses segmentation, increases attack surface, violates least privilege, and enables lateral movement to critical control systems.

**OT12** — Detection: Network monitoring (IDS/NTA), asset inventory (CMDB), anomaly detection (baseline behavior), EDR at IT/OT boundaries. IR Steps: Contain (isolate segment, block C2), Eradicate (remove malware, patch), Recover (restore clean backups, validate), Post-incident review. Coordination: Notify control room, switch to manual/local control if needed, prioritize safety over data. Safe Operations: Maintain manual overrides, ensure SIS/BPCS isolation, monitor critical parameters, communicate with operators. Operator Role: Monitor physical processes, execute manual procedures, report anomalies, follow cyber playbooks, avoid compromised IT systems.

**OT13** — HMI: Human-Machine Interface, graphical display for operators to monitor/control processes in real-time. Role: Visualization, alarm management, manual overrides, trend analysis. vs Engineering Workstation: HMI is for operators (runtime, read/write control). Engineering WS is for developers (programming, configuration, firmware updates, offline testing).

**OT14** — Historian: Time-series database optimized for high-volume, continuous process data logging. Importance: Trend analysis, compliance, performance optimization, troubleshooting, predictive maintenance. Plant Historian (L3): Real-time/near-real-time, high resolution, local storage, operational focus. Enterprise Historian (L4): Aggregated, lower resolution, long-term retention, business/financial reporting, ERP integration.

**OT15** — Ladder Logic: Graphical programming language mimicking relay circuits, executed by PLCs. PLCs scan inputs, execute logic cyclically, update outputs. Dominance: Familiar to electricians, easy to troubleshoot, deterministic, widely supported, legacy integration, low learning curve for industrial workforce.

**OT16** — RTU: Remote Terminal Unit, designed for harsh environments, long-distance communication, serial/telemetry protocols, often solar/battery powered. PLC: Designed for factory automation, modular I/O, fast processing, Ethernet/fieldbus. RTU deployment: Pipelines, water/wastewater distribution, wind farms, remote monitoring where communication is slow/unreliable and environmental conditions are extreme.

**OT17** — Analog: Continuous voltage/current (4-20mA, 0-10V) representing process variables. Digital: Discrete on/off or binary data. 4-20mA preferred: 4mA live zero detects wire breaks/failures (0mA = fault), less susceptible to noise over long distances, intrinsically safe, industry standard.

**OT18** — OT Asset Inventory: Comprehensive list of OT assets, firmware, network connections, vulnerabilities. Foundation: Cannot secure what you don't know; enables risk assessment, patching, segmentation, compliance. Tools: Passive monitoring (packet capture, protocol analysis), active scanning (limited, controlled). Active scanning danger: Can crash legacy devices, cause network congestion, trigger false alarms, disrupt real-time control. Passive is safer.

**OT19** — MITRE ATT&CK for ICS: Maps adversary tactics/techniques specific to ICS/OT. Tactics & Examples: 1. Reconnaissance: Gather network topology (T1580). 2. Resource Development: Acquire ICS malware (T1587). 3. Initial Access: Phishing for credentials (T1566). 4. Execution: Run malicious commands on PLC (T1059). 5. Impact: Manipulate process values to cause physical damage (T1491). Differs from Enterprise: Focuses on physical process impact, legacy protocols, safety constraints, longer dwell times, different attack paths. Assessment: Map defenses to techniques, identify gaps, prioritize controls (segmentation, monitoring, access control), simulate attacks.

**OT20** — Log Collection: Passive taps, syslog from firewalls/switches, OPC UA/SCADA audit logs, no active agents on critical OT. SIEM Integration: Normalize OT logs (custom parsers), correlate with IT logs. OT Detection Rules: Baseline deviations, unauthorized protocol usage, firmware changes, after-hours access, anomalous PLC commands. Triage: OT analysts review, validate with control room, prioritize safety impact. Staffing: IT analysts (threat intel, malware), OT engineers (protocol/process safety), joint playbooks. False Positives: Tune rules to maintenance windows, use allowlists, correlate with change management. Unauthorized Firmware Change: Isolate PLC, verify backup, restore signed image, investigate source, update change management, enhance admission controls, notify safety team.
