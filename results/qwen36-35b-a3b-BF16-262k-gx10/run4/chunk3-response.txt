T1 — `tofu plan` evaluates configuration against current state and infrastructure to preview changes without modifying anything. `tofu apply` executes those planned changes, creating, updating, or destroying resources.

T2 — State is a JSON file mapping real-world resources to configuration blocks. Remote state is critical for team collaboration, enables state locking to prevent concurrent modifications, and keeps sensitive data out of local repositories.

T3 — `count` iterates over integers, while `for_each` iterates over maps or sets. `for_each` is preferred when resources have unique, stable keys because changing a list element order with `count` can cause unintended recreation, whereas `for_each` only creates/destroys items that actually changed.

T4 — OpenTofu detects drift during `tofu plan` by comparing state to live infrastructure. On `tofu apply`, it will revert manual changes to match the configuration/state. If drift is intentional, use `lifecycle { ignore_changes = [...] }` or `terraform import` to sync state.

T5:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = { name = each.key }
}
```

T6 — `terraform_remote_state` reads the entire state file, which can expose sensitive data and lacks type safety. Output values are explicit, scoped, and type-checked. Recommended alternative: Pass outputs directly via module inputs/outputs, or use `data "terraform_remote_state"` with an explicit `outputs` map to limit exposure.

T7 — Provisioners run asynchronously during apply, but outputs are evaluated synchronously. The kubeconfig output may be empty because the dependent resource evaluates before `remote-exec` finishes writing. Fix: Add `depends_on = [null_resource.kubeconfig]` to the consuming resource, or better, use a `local_file` resource with `remote-exec` writing to it, then read via `file()` data source.

T8 — `tofu import` adds existing infrastructure to state but doesn't generate config. The `import` block (1.5+) declares imports in configuration, enabling version control, better error handling, and multi-resource imports. It also supports `tofu plan` validation before applying.

T9 — A `variable` block defines external inputs passed into a module/root. An `output` block exposes internal values from a module/root to callers or state. Variables flow in; outputs flow out.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a platform. Running `tofu plan` without `tofu init` fails because providers aren't downloaded, initialized, or locked, leaving OpenTofu unable to interact with the infrastructure.

T11 — `.terraform.lock.hcl` pins provider versions, checksums, and platforms. Commit it to ensure reproducible builds, prevent supply-chain attacks from unexpected provider updates, and guarantee CI/CD consistency.

T12 — `tofu destroy` removes all managed resources tracked in state. Target a single resource with `tofu destroy -target=module.name.resource[0]`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami"` to dynamically fetch the latest Ubuntu image instead of hardcoding an AMI ID that becomes outdated.

T14 — `locals` compute internal values within a module/root and aren't exposed to callers. `variables` accept external input. Use `locals` for derived values, transformations, or avoiding repetition of complex expressions.

T15 — `lifecycle` controls resource behavior: `create_before_destroy` creates new before deleting old (zero-downtime). `prevent_destroy` blocks accidental deletion via plan errors. `ignore_changes` skips drift on specific attributes (e.g., auto-generated tags).

T16 — The `moved` block remaps old resource addresses to new ones in state without destroying/recreating. It enables safe refactoring (renaming, moving modules) by telling OpenTofu to preserve existing infrastructure.

T17 — OpenTofu builds a DAG of dependencies. Implicit dependencies are inferred from variable references. Explicit `depends_on` forces ordering but disables parallelism for those resources. Use sparingly to avoid bottlenecking the entire apply.

T18 — 1. Increase `-parallelism` (default 10 → 20-50): faster but risks API rate limits. 2. Split monolithic state into multiple workspaces/modules: reduces scope but increases management overhead. 3. Use `data` sources with `refresh=false` or defer evaluation: faster plans but may show stale data. 4. Use `terraform plan -target` in CI: faster but limits change visibility.

T19 — State locking uses backend-specific mechanisms (e.g., DynamoDB) to prevent concurrent writes. If a lock isn't released, run `tofu force-unlock <LOCK_ID>`. Risks: data corruption or lost changes if another process was actively modifying state.

T20 — 1. Create S3 bucket & DynamoDB table. 2. Add `backend "s3"` config to `.tf` files. 3. Run `tofu init -migrate-state`. 4. Verify with `tofu state list`. Existing state is uploaded to S3; local file remains as backup. Locking is handled via DynamoDB.

A1 — A playbook is a YAML file orchestrating plays. A role is a reusable collection of tasks, files, templates, and variables. A task is a single module execution within a play.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_os_family }}`.

A3 — `command` runs without shell features (safest). `shell` runs via `/bin/sh`, supporting pipes/redirects. `raw` executes over SSH without Python, used for bootstrapping or unpatched systems.

A4 — Idempotency means running a task multiple times yields the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "timestamp" > /tmp/log.txt` (overwrites every run).

A5:
```yaml
- name: Install htop conditionally
  package:
    name: htop
  when: ansible_os_family == "Debian"

- name: Install epel and htop on RedHat
  package:
    name:
      - epel-release
      - htop
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (lowest to highest): inventory vars → host_vars → group_vars → role defaults → role vars → play vars → extra_vars. Extra_vars always win.

A7 — Use `serial: 3` in the playbook to process 3 nodes at a time. Group nodes in inventory as `rke2_first` and `rke2_rest`. Ansible automatically batches execution; no `wait_for` needed unless waiting for service readiness.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'mysecret' --name 'my_secret'`. Paste the output into a vars file.

A9 — Inventory defines hosts and groups. Static inventory is a file (INI/YAML). Dynamic inventory is a script/API that generates inventory on-demand, ideal for cloud environments.

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task triggered by `notify`. It runs only if notified and executes once at the end of the play. Regular tasks run unconditionally in order.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `log_path`.

A13 — `register` saves task output to a variable. Use it in subsequent tasks via `{{ var.stdout }}` or conditionally with `when: var.rc == 0`.

A14 — `include_tasks` is dynamic (evaluated at runtime, supports `when`). `import_tasks` is static (evaluated at parse time, no `when`). Use `include_tasks` for conditional execution.

A15 — Ansible Galaxy is a hub for community roles/collections. `requirements.yml` lists them; run `ansible-galaxy install -r requirements.yml` to download.

A16 — Connection plugins define how Ansible reaches hosts. `ssh` = standard SSH. `local` = runs on control node. `network_cli` = Telnet/SSH for network devices. Use `network_cli` for routers/switches.

A17 — `delegate_to` runs a task on a different host. `run_once` runs it once across a group. Example: Gather remote host data, then write a consolidated config to `localhost` once using `delegate_to: localhost` and `run_once: true`.

A18 — 1. Increase `forks` (5 → 20-50): faster but strains control node CPU/RAM. 2. Enable `pipelining`: reduces SSH overhead but requires SSH config changes. 3. Fact caching (Redis/Memcached): speeds up subsequent runs but risks stale facts. 4. Use Mitogen or `strategy: free`: Mitogen speeds up execution but needs installation; `free` loses task ordering.

A19 — `{{ }}` outputs expressions. `{% %}` controls flow/loops. `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
    # Health check: {{ server }}
    server {{ server }};
{% endfor %}
}
```

A20 — Use `serial: 1` or `20%`. Pre-tasks: set LB to drain/remove host. Deploy tasks: update app. Post-tasks: health check via `uri` module polling `status_code: 200`. On success, re-enable in LB. Wrap in `block/rescue`: if health check fails, `rescue` rolls back to previous version and restores LB config.
