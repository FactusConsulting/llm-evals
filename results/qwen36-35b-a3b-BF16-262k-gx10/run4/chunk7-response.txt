AA1 — Monoliths are single, unified codebases deployed as one unit with shared memory/processes. Microservices are independently deployable, loosely coupled services communicating over a network. Microservices introduce: (1) network latency & reliability issues, (2) distributed data consistency challenges, and (3) operational complexity (orchestration, CI/CD pipelines, distributed tracing, and deployment coordination).

AA2 — Synchronous communication blocks the caller until a response is received (request-response model). Example: REST/gRPC. Asynchronous communication decouples producer and consumer; messages are placed in a queue/topic and processed later without blocking. Example: RabbitMQ, Kafka, AWS SQS.

AA3 — A reverse proxy handles low-level traffic routing, SSL termination, load balancing, and caching (e.g., Nginx, HAProxy). An API Gateway adds API-specific concerns: rate limiting, authentication, request transformation, versioning, developer portals, and analytics. An API Gateway cannot fully replace a reverse proxy; they operate at different layers. Reverse proxies excel at network performance and TLS offloading, while API gateways sit on top to manage API lifecycle and security policies.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a later step fails. Choreography-based sagas use events to trigger the next step (decentralized, good for simple flows, hard to monitor/debug). Orchestration-based sagas use a central coordinator that sends commands (decentralized events, better control, easier rollback/monitoring, appropriate for complex, multi-step workflows).

AA5 — CQRS separates read and write operations into different models. Commands modify state; queries read from optimized projections. It’s paired with Event Sourcing because events become the single source of truth, and projections are built by replaying them. This combination solves complex domain modeling, provides full audit trails/temporal queries, and allows independent scaling of read/write paths—problems traditional CRUD struggles with due to rigid schema and coupled read/write models.

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. States: Closed (normal operation), Open (failure threshold met, fast-fail), Half-Open (allows limited probes to test recovery). It differs from retry+backoff because retries assume transient failures and keep hammering the service, while circuit breakers halt traffic to protect downstream systems. Use both together: retry+backoff handles transient errors within the closed state; circuit breaker activates when errors persist to prevent cascade/fatigue.

AA7 — 
1. Shared DB/Schema: Lowest cost, highest noisy-neighbor risk, weakest security/backup isolation, simplest ops.
2. Shared DB/Schema per tenant: Moderate cost, better isolation/security, easier per-tenant backup/restore, moderate ops complexity.
3. Separate DB per tenant: Highest cost, strongest isolation/security, complex ops (connection pooling, migrations, backups), lowest noisy-neighbor risk. Trade-off scales linearly: isolation/security ↑, cost/ops ↑, noisy-neighbor risk ↓.

AA8 — Eventual consistency allows temporary stale reads; strong consistency guarantees immediate visibility and linearizable state. For inventory that must never oversell: use strong consistency. Architecture: dedicated inventory service with a relational DB (PostgreSQL) using serializable isolation or row-level locking, combined with a reservation/hold pattern. At scale, use distributed locking (Redis Redlock/ZooKeeper) or optimistic concurrency control (version columns). Queue out-of-band events (returns, shipping) to avoid blocking reads, and implement idempotent compensation for failed reservations.

AA9 — A sidecar proxy is a co-located container that intercepts all inbound/outbound traffic for a service. In Istio, Envoy acts as the data plane proxy handling routing, retries, mTLS, and metrics. The control plane (Istiod) pushes configuration, manages service discovery, and rotates certificates. Data plane = traffic handling; control plane = config/cert management. mTLS between sidecars solves transparent, zero-code security: automatic cert rotation, service identity verification, and MITM prevention without requiring each service to implement TLS manually.

AA10 — The Strangler Fig pattern incrementally replaces functionality by routing traffic to new services while keeping the legacy system intact until it’s fully decommissioned. Strategy: Deploy an API Gateway. Route new features to .NET 8 microservices. Gradually extract modules (auth, billing, reporting) into new services. Update gateway routing rules. Implement data sync (CDC or dual-write) during transition. Use feature flags for safe rollouts. Once all endpoints are migrated, decommission the .NET Framework monolith.

AA11 — 12-Factor App methodology optimizes apps for cloud-native deployment. Six factors: (1) Codebase (1 dep per app), (2) Dependencies (explicitly declare), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless, exec model). They matter for portability, reproducible builds, secure config management, horizontal scaling, and resilient cloud deployments.

AA12 — 
- Coupling: Event-driven = loose; Request-driven = tight.
- Scalability: Event = high throughput, async scaling; Request = sync scaling, connection-bound.
- Debugging: Event = harder (distributed state, replay needed); Request = easier (request/response trace).
- Ordering: Event = partition-level ordering guaranteed; Request = per-request ordering.
- Failure: Event = retry/dead-letter, idempotency critical; Request = timeouts, retries, circuit breakers.
Choose Event for async workflows, high throughput, audit trails, and decoupled systems. Choose Request for real-time APIs, simple CRUD, and synchronous dependencies.

AA13 — A load balancer distributes traffic across multiple backend servers. Layer 4 balances based on IP/port (fast, no content inspection). Layer 7 inspects HTTP headers, URLs, cookies, and content (slower but smarter). Layer 7 is required for SNI-based SSL termination, URL/path-based routing, or header-based routing.

AA14 — Message queues (RabbitMQ) are point-to-point/pub-sub systems where messages are consumed and removed; ideal for task queues and complex routing. Log-based brokers (Kafka) are append-only logs with retention, multiple consumers, and replay capability; ideal for event streaming and analytics. Pick RabbitMQ for strict delivery, task processing, and complex routing. Pick Kafka for high-throughput event pipelines, log aggregation, and replay needs.

AA15 — Containers share the host OS kernel and isolate processes/filesystems; VMs run a full guest OS under a hypervisor. Containers are lighter, faster to start, and use fewer resources. They’re popular for microservices because they ensure environment consistency, enable rapid scaling, simplify CI/CD, and integrate seamlessly with orchestration platforms like Kubernetes.

AA16 — Stateless services store no client data between requests; any instance can handle any request, making horizontal scaling trivial. Example: Web/API servers. Stateful services maintain client/session data locally; scaling requires sticky sessions or external state stores. Example: Databases, WebSocket servers, caches.

AA17 — An ORM maps database tables to application objects, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs accelerate development, improve safety, and enable DB portability, but can generate inefficient queries and complicate complex optimizations. Raw SQL offers full performance control and clarity but is verbose, DB-specific, and requires more boilerplate.

AA18 — The Bulkhead pattern isolates resources so a failure in one component doesn’t exhaust shared resources and cascade. In microservices, it prevents thread/connection pool exhaustion from taking down the whole app. Implementation: Use separate thread pools and connection pools per downstream service, deploy critical vs non-critical services on different node pools, or route traffic through separate queues with backpressure limits.

AA19 — OT transforms operations on a central server; ensures strong consistency, lower storage, but requires server mediation and complex conflict resolution. CRDTs are mathematical structures that converge automatically; enable decentralized, offline editing, but require careful design and higher storage. For offline editing, choose CRDTs: they handle concurrent edits without server sync, merge automatically, and gracefully survive network partitions, whereas OT breaks offline capability.

AA20 — Challenges include polyglot instrumentation, async flow tracking, and high data volume. Context propagation uses W3C Trace Context or B3 headers injected/extracted across HTTP/gRPC. Sampling: head-based (random, cheap, loses rare traces) vs tail-based (collect all, sample later, accurate but high overhead). Storage/query: Jaeger/Tempo use columnar, trace-centric indexes for fast retrieval. In Kafka, trace context must be injected into message headers by the producer and extracted by the consumer. Tail-based sampling or sampling at the producer ensures continuity without blocking async flows.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Proxmox VE, KVM). Type 2 (hosted) run as applications on a host OS (e.g., VirtualBox, VMware Workstation). Type 1 offers near-native performance and enterprise features; Type 2 is easier for development/testing.

OP2 — SAN provides block storage presented as disks to servers; uses Fibre Channel or iSCSI. Ideal for databases/VMs requiring low-latency block access. NAS provides file storage over a network; uses NFS or SMB/CIFS. Ideal for file shares, backups, and home directories. SAN = performance/complexity; NAS = simplicity/sharing.

OP3 — 3-tier architecture: Core (backbone), Distribution (policy/routing), Access (edge). Hierarchical but suffers from oversubscription and non-deterministic latency. Leaf-spine uses an all-to-all mesh with ECMP routing, providing deterministic low latency, predictable east-west traffic, and linear scalability. It solves the bottlenecks and oversubscription inherent in 3-tier designs.

OP4 — Use 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing (STONITH via iDRAC/IPMI) powers off unresponsive nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. On node failure: HA manager detects failure, fences the node, and restarts VMs on healthy nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, assign IPs, enable `net.ipv4.ip_forward=1`, and configure the switch port as a trunk (allow VLANs).

OP6 — RAID 1: Mirror, 50% cap, 1 fault. RAID 5: Striping+parity, N-1 cap, 1 fault, write penalty. RAID 6: Double parity, N-2 cap, 2 faults, higher write penalty. RAID 10: Mirror+stripe, 50% cap, multiple faults, high IOPS. RAID Z2: Double parity, N-2 cap, self-healing, COW. For 6 drives balancing perf/capacity/fault tolerance for a DB: RAID Z2 or RAID 6. Z2 is preferred for modern drives due to self-healing, better write performance, and flexible capacity.

OP7 — Recursive resolvers: Internal DNS servers (Windows DNS/BIND) for clients. Authoritative: Internal zone for AD, external zone for public. Forwarders: Point to ISP/Cloudflare for external queries. Conditional forwarding: Routes internal AD queries to internal DNS, external to forwarders. Split-horizon: Internal DNS returns private IPs, external returns public IPs. DNSSEC: Sign external zone, chain to root. Laptop roaming: DHCP provides internal DNS IP; split tunneling/conditional forwarding routes internal queries correctly; roaming clients use cached records or dynamic updates.

OP8 — PKI chain: Root CA (offline, self-signed, long-lived) → Subordinate CA (online, issues certs, shorter life) → End-entity cert. CRL = periodic revocation list; OCSP = real-time status check. Templates define key usage, validity, and auto-enrollment policies. Auto-enrollment pushes certs via AD CS. Compromised subordinate: Revoke, reissue, update trust. Compromised root: Catastrophic; requires rebuilding entire PKI and updating all trust stores.

OP9 — MPLS: High reliability, low latency, expensive, managed. IPsec VPN: Cheap, internet-based, variable latency, manual config. SD-WAN: Orchestrates MPLS/IPsec/WiFi, app-aware routing, centralized management, moderate cost. WireGuard mesh: Modern crypto, fast, simple, lacks enterprise mgmt/SLA. Recommendation: SD-WAN. Balances cost, reliability, and latency; supports QoS for VoIP, dynamic path selection, and centralized policy.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: Out-of-band management interfaces for remote power, console, and hardware monitoring. Critical for OS recovery, provisioning, and management without network/OS access. Exposed to internet: High risk of credential theft, console access, hardware info leakage, and DoS. Should be isolated on a dedicated management network.

OP11 — LVM: Block manager, snapshots are COW (full copy initially). LVM-Thin: Overprovisions storage, snapshots are instant/space-efficient, but performance degrades if pool fills. ZFS: Filesystem+volume manager, COW, snapshots are instant/read-only, self-healing. Use LVM for traditional Linux, LVM-Thin for VM storage efficiency, ZFS for data integrity and advanced snapshot/replication features.

OP12 — Ceph CRUSH rules define failure domains (host, rack, site) and place replicas across sites. Monitor placement: Odd number, ideally 3 per site or 5 total with geographic distribution. Network latency: <10ms ideal for Ceph, <50ms for stretch. Split-brain: Both sites act primary; CRUSH mitigates but requires quorum. 2-site Ceph without a tiebreaker is bad because 2 votes = no majority, risking data corruption. Add a witness/tiebreaker node for 3-way quorum.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable: Client uses APIPA (169.254.x.x) or fails. On lease expiry: Client tries renewal at T1 (50%) and T2 (87.5%). If failed, releases IP and falls back to APIPA/manual config.

OP14 — Unmanaged switches are plug-and-play with no config. Managed switches support VLANs, QoS, STP, ACLs, monitoring, PoE, and link aggregation. Critical for segmentation, traffic prioritization, loop prevention, and troubleshooting in enterprise environments.

OP15 — NTP synchronizes clocks over a network. Critical for log correlation, Kerberos/AD auth, distributed DB consistency, certificate validation, and audit compliance. Clock drift causes Kerberos auth failures, misaligned logs, cluster split-brain, replication errors, and security alert inaccuracies.

OP16 — Physical: Hardware directly. VM: OS virtualization, full isolation. Container: Process virtualization, shared kernel. Run bare metal for max performance/low latency, hardware passthrough (GPUs/NVMe), compliance/security requirements, or latency-sensitive databases/real-time workloads.

OP17 — UPS: Battery backup, handles short outages, conditions power, bridges to generator. Generator: Long-term power, fuel-based. Need both: UPS for immediate transition/surge protection; generator for sustained outages. ATS: Automatically switches load from utility to generator on failure, and back when restored.

OP18 — Active-passive: One handles traffic, standby takes over on failure. Active-active: Both handle traffic, sync data, failover possible. PostgreSQL HA: Pacemaker/Corosync cluster. Primary runs PG, standby replicates (streaming). Virtual IP floats. STONITH fencing prevents split-brain. On failure, Pacemaker promotes standby, moves VIP, starts services. (Note: Patroni is often preferred for PG-specific HA, but Pacemaker/Corosync provides the underlying cluster framework.)

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO defined by business impact. Backup types: Full (baseline), Incremental (changes since last), Differential (since last full). Deduplication reduces storage/backup windows. Media: Disk for fast restore, tape/cloud for cheap offsite. Immutable backups: WORM/air-gapped storage for ransomware protection. Test restores: Regular drills, verify integrity, measure RTO/RPO. Backup = data preservation; DR = full recovery process (infrastructure, data, processes) to resume operations.

OP20 — 802.1X: Port-based NAC. Roles: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP: EAP-TLS (cert-based, highly secure), PEAP (username/password, tunneled). RADIUS handles auth/authorization/accounting. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: Port stays unauthorized, no traffic. MAB: Uses MAC address as credential for non-802.1X devices (printers/IoT). Falls back to MAB if supplicant fails, assigns guest VLAN.
