SC1-A
The pods fail because the namespace policy was upgraded from Baseline to Restricted Pod Security Standard (PSS). Baseline allows root containers and permissive security contexts. Restricted PSS enforces stricter rules: containers must run as non-root, and if `runAsNonRoot: true` is set, Kubernetes requires either an explicit `runAsUser` with a non-zero UID or an image that explicitly defines a non-root `USER`. The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`. When pods restart (or are created), the container runtime attempts to run as root, violating the Restricted policy. Kubernetes either rejects admission or the container crashes on startup due to security context enforcement, leading to CrashLoopBackOff.

SC1-C
**Immediate Fix:** 
1. *Image:* Rebuild with `USER 1000` (or non-root UID) in the Dockerfile, or pin to a known non-root tag.
2. *Manifest:* Add `runAsUser: 1000` and `runAsGroup: 1000` to `securityContext` in deployments.
3. *Rollout:* Use `kubectl rollout restart deployment/<name>` with `maxSurge=25%` and `maxUnavailable=0` to avoid downtime. Monitor with `kubectl rollout status`.

**Prevention:**
- *CI Gate:* Add OPA/Kyverno policy-as-code in CI to validate PSS compliance against manifests. Add Trivy/Grype to scan images for root users (`trivy image --exit-code 1 --severity HIGH --ignore-unfixed <image>`).
- *Pipeline:* Enforce image digest pinning and require `runAsUser` in base Helm charts. Use admission controllers in-cluster to reject non-compliant pods.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped from the primary to the replica over the network. During an outage, if the primary is lost before all WAL is shipped, those transactions are permanently lost. The stale data issue occurs because the application reads from the promoted replica before replication lag catches up, or because the promotion cut off in-flight transactions. To quantify the loss window, check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica before failover, or monitor `pg_stat_replication` lag metrics. The data loss window equals the replication lag at the exact moment of promotion.

SC6-A
**Identity & Access Layer:**

SC6-C
**Comparison:**
- *AWS Direct Connect:* Dedicated 10Gbps+ link, low latency, high cost. Fits ZT if combined with IPsec/TLS overlay. Routing: BGP peering, requires on-prem router config.
- *Second VPN + ECMP:* Low cost, doubles bandwidth, same encryption. Routing: BGP with ECMP, requires multiple tunnels and route weighting.
- *Tailscale/Netbird:* SaaS mesh, zero-config, built-in encryption, medium cost. Fits ZT natively (device/workload identity, ACLs). Routing: Overlay network, no on-prem router changes.
**Recommendation:** For ZT, Tailscale/Netbird offers fastest deployment and native identity-based access. For enterprise scale, Direct Connect + SPIRE/mTLS provides best performance and control. ECMP is a temporary bridge.

SC10-A
**Architecture Comparison:**
- *Active-Passive (Velero):* Backups to DR site, restore on failover. RPO limited by backup frequency, RTO by restore time. With 200TB MinIO, restore exceeds RTO 1h. Not viable.
- *Active-Active (Istio/Cilium):* Traffic split across sites. Stateful components replicate asynchronously. 12ms latency allows async replication with sub-15m RPO. Service mesh handles failover routing.
**Replication Strategy:**
- PostgreSQL: Patroni async replication with `synchronous_commit=remote_write` for zero data loss on primary failure.
- Redis: Sentinel async replication, automatic failover.
- RabbitMQ: Federation/shovel or mirrored queues across sites.
- MinIO: Site replication (async), catch-up during failover.
**Recommendation:** Active-active with async replication + periodic backups. Meets RPO 15m, RTO 1h given 12ms latency and modern replication tools.

SC10-C
**Failover Orchestration Sequence:**
1. *Detection:* Health checks (Patroni, Redis Sentinel, RabbitMQ, MinIO) monitor site heartbeat. Site down = >3 consecutive failures + quorum loss.
2. *DNS Failover:* GSLB (Route53/Azure Traffic Manager) detects health check failure, switches DNS to Dallas endpoint.
3. *Patroni:* Standby in Dallas promotes via etcd quorum. `synchronous_standby_names` ensures zero data loss.
4. *Redis Sentinel:* Promotes replica, updates client config.
5. *RabbitMQ:* Federation catches up queues, mirrors resume.
6. *MinIO:* Site replication syncs pending objects. App switches to Dallas bucket.
7. *Terraform State:* Update state to reflect new primary region. Run `terraform apply` to update DNS/SGs.
**Split-Brain:** Prevented by etcd/Patroni quorum fencing. Only one node can hold leadership. Use `failover_ignore_standby_list` and network fencing.
