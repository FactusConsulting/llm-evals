SC1-A
The pods fail because the namespace Pod Security Standard (PSS) enforcement changed from `Baseline` to `Restricted`. `Restricted` enforces strict security contexts: `runAsNonRoot: true` is required, and crucially, `runAsUser` must be explicitly set to a non-zero UID (or `fsGroup`/`seccomp`/`capabilities` must be restricted). The new base image (`cgr.dev/chainguard/static:latest`) defaults `USER` to `root`. Without an explicit `runAsUser` in the pod spec, the container runtime attempts to run as UID 0, violating the `Restricted` policy. Kubernetes rejects the pod admission or the container runtime fails to start, resulting in `CrashLoopBackOff`.

SC1-C
**Immediate Fix:** Update container images to include `USER 1000` (or equivalent non-root user) in the Dockerfile. Update Helm/manifests to add `securityContext.runAsUser: 1000` and `runAsNonRoot: true`.
**CI Gate:** Add `kubeconform` or `opa/kyverno` policy validation in CI to enforce `runAsNonRoot: true` and explicit `runAsUser` for all deployments. Add Trivy/Grype scans to flag base images defaulting to root.
**Rollout:** Use a rolling update with `maxSurge=1` and `maxUnavailable=0`. Deploy to a canary namespace first, verify health checks, then promote. Use Helm `--wait --timeout` to ensure readiness before proceeding.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous. WAL segments are shipped over the network and replayed on the replica. During an outage, the replica is promoted, cutting off replication. Any WAL not yet shipped or replayed is permanently lost. The stale data issue stems from replication lag at promotion time. To quantify loss: check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica before promotion, and query `pg_stat_replication` for `lag` in bytes/seconds. The data loss window equals the network latency + replay delay at the moment of failover.

SELECT 
  blocked_locks.pid AS blocked_pid,
  blocked_activity.usename AS blocked_user,
  blocking_locks.pid AS blocking_pid,
  blocking_activity.usename AS blocking_user,
  blocked_activity.query AS blocked_statement,
  blocking_activity.query AS blocking_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
  AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
  AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;

SC10-A
**Active-Passive (Velero):** RPO = backup interval (15m), RTO = restore time (hours). Fails RTO < 1h for 200TB MinIO. 
**Active-Active (Istio/Cilium):** RPO/RTO depend on data sync. 12ms latency allows near-real-time sync. 
**Replication Strategy:**
- **PostgreSQL:** Patroni synchronous replication (`synchronous_standby_names = 'standby1'`). RPO=0, RTO < 30s.
- **Redis:** Sentinel with `min-slaves-to-write 1` or Redis Cluster cross-region sync. RPO < 1s.
- **RabbitMQ:** Quorum queues with cross-site replication or federation. RPO < 5s.
- **MinIO:** Site replication (async, eventual consistency). RPO ~minutes, RTO depends on catch-up.
**Recommendation:** Active-active with Istio multi-cluster + Patroni sync + MinIO site replication. Meets RPO/RTO given 12ms latency and 10Gbps fiber.

SC10-C
**Failover Sequence:**
1. **Detection:** Prometheus monitors site health (ping, DB replication lag, node readiness). Site down = >3 consecutive failures + etcd quorum loss.
2. **DNS Failover:** GSLB (Route53/Azure Traffic Manager) switches VIP to Dallas.
3. **Patroni Promotion:** Standby detects leader loss, runs `pg_ctl promote`, becomes primary.
4. **Redis/RabbitMQ/MinIO:** Sentinel/federation triggers failover; MinIO site replication catches up.
5. **State Update:** Ansible/Terraform updates state files, DNS, and load balancer configs.
**Split-Brain Prevention:** Patroni uses etcd quorum + fencing (STONITH). Only one node can hold the lock. Network partition triggers automatic demotion of isolated leader.
**Failback:** Once Chicago recovers, rejoin as standby via Patroni. Sync WAL, verify data consistency, switch DNS back during maintenance window, decommission Dallas primary. Run chaos tests quarterly.
