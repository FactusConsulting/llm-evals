**CL1** — IaaS provides virtualized compute, network, and storage where you manage the OS, middleware, runtime, and applications (e.g., AWS EC2). PaaS provides a managed runtime and middleware where you only deploy code and manage data (e.g., Google App Engine). SaaS delivers a fully managed application where you only configure user access and data (e.g., AWS WorkSpaces).

**CL2** — The Shared Responsibility Model divides security *of* the cloud (provider: physical, global infra, hypervisor, managed service control plane) from security *in* the cloud (customer: data, IAM, OS/network config, app code). For IaaS VMs, you patch the guest OS, configure firewalls, and manage data. For managed Kubernetes, the provider secures the control plane and node OS; you secure pods, network policies, secrets, and app code. For SaaS like M365, the provider secures the app and infrastructure; you manage user access, data classification, sharing policies, and MFA.

**CL3** — A VPC is an isolated virtual network; subnets are IP ranges within it. Security Groups (SGs) are stateful, instance/pod-level allow-only rules evaluated first. Network ACLs (NACLs) are stateless, subnet-level allow/deny rules evaluated after SGs. Stateful filtering tracks connection state and automatically allows return traffic; stateless requires explicit inbound and outbound rules for every flow.

**CL4** — A landing zone is a pre-configured, secure multi-account foundation. Organizational Units (OUs) group accounts by function (dev, prod, shared). Guardrails (SCPs, IAM boundaries) enforce mandatory controls. Shared networking (Transit Gateway/Azure Hub-and-Spoke) centralizes inter-VPC/VNet routing. Centralized logging aggregates logs to a single account for audit. Single-account approaches cause massive blast radius, permission sprawl, billing opacity, compliance isolation failures, and accidental deletion risks.

**CL5** — IaC manages infrastructure via version-controlled, machine-readable definitions. Terraform/OpenTofu uses declarative HCL, multi-cloud, and state files; ideal for mature, multi-cloud teams. Pulumi uses imperative/declarative code (TS/Python/Go) with native SDKs; best for complex logic or teams avoiding state files. CloudFormation/Bicep are AWS-native, tightly integrated, and faster for single-cloud deployments. Crossplane is Kubernetes-native, managing cloud resources via CRDs; ideal for GitOps/K8s-centric workflows.

**CL6** — HPA scales pods based on CPU/memory/custom metrics. VPA adjusts pod resource requests/limits (requires restart). Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external events (queues, streams, HTTP). Use KEDA over HPA for event-driven workloads where metric-based scaling causes over-provisioning or can't scale to zero efficiently.

**CL7** — Define RPO (max data loss) and RTO (max downtime). Active-active runs both regions simultaneously with sync replication; low RTO/RPO but high cost/complexity. Active-passive runs one region, fails over to standby; lower cost, higher RPO. DB sync replication ensures consistency but adds latency; async replication reduces latency but risks data loss. DNS failover (Route53/Traffic Manager) uses health checks and TTL tuning. Externalize state to managed DBs/caches. Cost doubles in active-active. Pilot light: core infra/data running, app ready to scale. Warm standby: scaled-down app running. Multi-site active-active: full production in both regions.

**CL8** — GitOps uses Git as the single source of truth; controllers continuously sync cluster state to Git. ArgoCD is agent-based, UI-first, supports app-of-apps. Flux is pull-only, CLI-first, tightly integrated with Git providers. Secrets: SealedSecrets (encrypted in Git), External Secrets Operator (syncs from Vault/AWS SM), or SOPS+KMS. Manual drift is detected by the controller, which reverts changes to match Git state and logs the event.

**CL9** — Use a StatefulSet for stable identity and ordered deployment. PV/PVC with `local` storageClass and `volumeBindingMode: WaitForFirstConsumer` ensures low-latency node-local storage. A headless service (`clusterIP: None`) enables direct pod DNS resolution. Init containers prepare filesystems and validate dependencies. ConfigMaps mount as volumes at required paths. PDBs (`minAvailable`) ensure minimum pods during disruptions. Note: local storage limits HA; replicate data at the app layer or use distributed storage if availability is critical.

**CL10** — K8s Service Accounts are native identities with no cloud permissions. Workload Identity (GCP/Azure) and IRSA (AWS) map K8s SAs to cloud IAM identities without static keys. Mounting credentials in pods leaks secrets, breaks least privilege, complicates rotation, and hinders auditing. Workload identity federation uses OIDC to exchange short-lived tokens, enabling automatic rotation, scoped permissions, and zero static secrets.

**CL11** — Object storage (S3/Blob) is HTTP-based, unstructured, highly durable (~11 nines), and cost-effective for backups/media. Block storage (EBS/Disk) is mounted to VMs, low-latency, high-IOPS, durable (~99.999%), used for OS/databases. File storage (EFS/Azure Files) is shared via NFS/SMB, scalable, durable (~99.999%), used for shared configs/legacy POSIX apps. Availability typically ranges 99.9%–99.99% depending on tier and replication.

**CL12** — Zero-trust K8s enforces: default-deny Network Policies, service mesh mTLS for east-west encryption, workload identity federation, admission controllers (OPA/Kyverno) to enforce deploy-time policies, image signing (cosign) verified at admission, runtime security (Falco) for anomaly detection, and external secrets management. Unlike perimeter models, it assumes breach, verifies every request, micro-segments traffic, and ties access to identity rather than network location.

**CL13** — A CDN is a distributed edge cache network that serves content from POPs closest to users via DNS/Anycast routing, pulling from origin on cache misses. Services: CloudFront, Azure CDN, Fastly. Use a CDN for static assets, global reach, DDoS mitigation, and SSL offload. Serve directly from origin for dynamic, personalized, or cache-busting content where edge caching adds latency or complexity.

**CL14** — A region is a geographic area with multiple Availability Zones (AZs). AZs are isolated data centers with independent power/networking, connected via low-latency links. Multi-AZ deployment protects against single data center failure, enabling high availability. Zonal resources (EBS, subnets, some LBs) are tied to one AZ. Regional resources (ALB, Route53, S3, IAM) span multiple AZs.

**CL15** — Managed databases (RDS, Cloud SQL, Azure SQL) abstract operational overhead. The provider handles provisioning, patching, backups, point-in-time recovery, replication, failover, monitoring, and storage scaling. Self-hosted on VMs requires you to manage the OS, database software, HA setup, backups, scaling, and security patches.

**CL16** — IAM Users are human/service identities. Groups bundle users. Roles provide temporary credentials for entities. Policies are JSON rules granting/denying actions. Least privilege grants only necessary permissions for required duration. Apply it by using roles over users, attaching policies to groups/roles, leveraging condition keys, enforcing MFA, conducting regular access reviews, and implementing just-in-time access.

**CL17** — Serverless is managed, event-driven compute with pay-per-use and auto-scaling. Lambda (AWS), Functions (Azure), and GCF (GCP) share core concepts but differ in ecosystems, timeout limits, and cold start behavior. Cold starts are initialization delays when containers spin up; they matter for latency-sensitive or high-spike workloads. Serverless is a poor fit for long-running processes, stateful apps, predictable high throughput (reserved instances cheaper), or strict network isolation/compliance needs.

**CL18** — Ingress Resource is a standard K8s CRD requiring a controller (NGINX/ALB); TLS terminates at the controller. Gateway API is newer, standardized, separates routing (Gateway) from backends (HTTPRoute), and enables multi-tenant RBAC. Cloud LB annotations directly provision cloud load balancers; TLS terminates at the LB. Service mesh ingress (Istio/Envoy) terminates TLS at the mesh edge with mTLS. Use Gateway API over Ingress for standardized routing, multi-tenant isolation, fine-grained RBAC, or cloud-agnostic deployments.

**CL19** — Commit to Reserved Instances/Savings Plans for 30–70% discounts (SPs are more flexible). Use Spot/Preemptible for fault-tolerant workloads (up to 90% off). Right-size by monitoring utilization and auto-scaling. Tier storage with lifecycle policies and Intelligent-Tiering. Detect idle resources (unattached volumes, zombie LBs). Implement FinOps: tag-based accountability, budget alerts, weekly reviews. Use showback/chargeback dashboards to incentivize optimization. Tools: Cost Explorer, CUR, Kubecost/OpenCost, CloudHealth. Process: mandatory tagging, automated rightsizing recommendations, cross-functional FinOps council.

**CL20** — Multi-cloud avoids lock-in via abstraction: Kubernetes as runtime, Terraform for IaC, service mesh/API gateways for traffic, VPN/interconnect for networking, and OIDC federation for identity. Trade-offs: higher complexity, cost, skill fragmentation, and data gravity vs resilience, negotiation leverage, and regulatory compliance. Justified for data residency mandates, catastrophic vendor risk, or specific service superiority. Unnecessary for most organizations lacking multi-cloud maturity, where operational overhead outweighs theoretical benefits.

**OT1** — The Purdue Model (ISA-95) structures industrial automation hierarchically. Level 0: Physical process (sensors/actuators). Level 1: Direct control (PLCs/RTUs). Level 2: Supervisory control (SCADA/HMIs). Level 3: Operations/MES (production scheduling). Level 4: Enterprise/ERP (finance/supply chain). Level 5: Corporate/External (cloud/partners).

**OT2** — IT prioritizes confidentiality, integrity, availability (CIA) with fast patching and user-centric dynamics. OT prioritizes safety, availability, integrity (AIS) with stability over speed and physical consequences. Standard IT patching fails in OT because legacy systems lack patch windows, updates require vendor validation, testing in staging is mandatory, and unvalidated patches can cause catastrophic downtime or safety failures.

**OT3** — An Industrial DMZ (IDMZ) is a segmented buffer between IT and OT. Traffic flows: IT→OT (commands, schedules, updates via DMZ); OT→IT (telemetry, alarms, metrics). Direct Level 4 (IT) to Level 1 (control) connectivity bypasses security controls, exposes critical systems to internet/IT threats, enables lateral movement, and risks physical/catastrophic impact.

**OT4** — Modbus TCP (L1/L2): simple request/response, legacy PLCs. OPC UA (L2/L3): secure, platform-independent, modern information modeling. EtherNet/IP/CIP (L1/L2): real-time industrial Ethernet, Allen-Bradley dominant. PROFINET (L1/L2): deterministic real-time Ethernet, Siemens dominant. MQTT (L3/L4): lightweight publish/subscribe for IoT/cloud telemetry, not real-time control.

**OT5** — A data diode is hardware-enforced one-way communication (optical/electrical) that physically prevents return traffic. A firewall inspects and allows/denies bidirectional traffic based on rules. Use a diode for high-security OT networks requiring strict one-way data flow (e.g., telemetry to IT) or compliance mandates. Limitation: no bidirectional communication, cannot handle commands/acknowledgments, and lacks firewall flexibility.

**OT6** — Flow: PLCs/RTUs → OPC UA Server (historian/SCADA) → Edge Gateway (protocol translation, buffering, secure boot) → MQTT Broker (TLS/mTLS) → Cloud Ingestion (IoT Core/Kafka) → Analytics. Security boundaries: OT network (firewall/data diode to DMZ), DMZ (MQTT broker, strict ACLs), Edge (hardware security, network segmentation), Cloud (IAM, encryption, WAF). Enforce least privilege and monitor all boundaries.

**OT7** — IEC 62443 defines security Zones (logical asset groupings with similar requirements) and Conduits (controlled communication paths). Model: Zone 1 (Corporate/L4), Zone 2 (Engineering/L3), Zone 3 (SCADA/Historian/L2), Zone 4 (PLCs/L1), Zone 5 (SIS). Conduits: Z1→Z2 (firewall, MFA), Z2→Z3 (firewall, change control), Z3→Z4 (firewall/data diode, strict ACLs), Z4↔Z5 (physical/logical isolation, no direct conduit).

**OT8** — VLAN design: segment by function/process (e.g., Line 1 PLCs, Line 2 PLCs, HMIs, SCADA, Engineering). Firewall placement: core firewall IT/OT boundary, edge firewalls between VLANs, DMZ for external access. Switch architecture: managed L3 switches, port security, 802.1X where supported, disable unused ports. Remote access: jump host in DMZ, MFA, session recording, time-limited scoped vendor accounts. Transition: phased rollout, parallel run, maintenance windows, rollback plan, vendor coordination, monitor latency/availability impact.

**OT9** — BPCS manages normal process operations optimized for throughput. SIS is independent, triggers safe states on hazardous conditions, optimized for safety. IEC 61511 mandates functional safety lifecycle and SIL ratings for SIS. SIS must be air-gapped/isolated to prevent cyber attacks from compromising safety functions, ensuring independent operation if BPCS/IT is breached. Ransomware reaching SIS could disable shutdowns, causing catastrophic failure, environmental damage, or loss of life.

**OT10** — PLC: discrete control, fast I/O, rugged, used for machine/line control. DCS: centralized architecture with distributed controllers, optimized for continuous processes, high integration. SCADA: software/hardware for monitoring, data collection, HMI, remote control across wide areas. They coexist commonly: DCS for core process, PLCs for auxiliary systems, SCADA for supervision and data aggregation.

**OT11** — Remote access: isolated jump host in DMZ, mandatory MFA, session recording, time-limited scoped vendor accounts, no direct OT access. RDP directly to an HMI from corporate is unacceptable because it bypasses segmentation, exposes OT directly to corporate threats, increases attack surface, and violates the Purdue model.

**OT12** — Detection: IDS/IPS at OT/IT boundary, passive anomaly detection, real-time asset inventory, baseline normal behavior. IR steps: contain (isolate segments), assess impact, preserve evidence, eradicate, recover, post-incident review. Coordination: notify control room, switch to manual/local control if needed, maintain safe operations, avoid disruptive actions. Operator role: monitor physical parameters, execute manual overrides, communicate status, follow emergency procedures, do not touch IT/OT systems. Prioritize safety over containment.

**OT13** — HMI (Human-Machine Interface) provides operators with real-time visualization, alarm management, and manual control of processes. It differs from an Engineering Workstation (EWS), which is used for configuration, programming, diagnostics, and maintenance, not run-time operations.

**OT14** — A historian is a time-series database optimized for high-volume process data logging. It enables trend analysis, compliance, troubleshooting, and predictive maintenance. Plant historians (L3) store raw, high-frequency process data for operations. Enterprise historians (L4) aggregate, filter, and integrate data with ERP/business systems for reporting and finance.

**OT15** — Ladder logic is a graphical programming language mimicking relay circuits, executed cyclically by PLCs. It remains dominant because it's familiar to electricians, easy to troubleshoot, deterministic, widely supported, integrates with legacy systems, and has a low learning curve for the industrial workforce.

**OT16** — RTUs (Remote Terminal Units) are designed for harsh environments, long-distance communication, and SCADA telemetry, often battery/solar powered. PLCs are optimized for factory automation, fast I/O, and local control. RTUs are deployed in pipelines, oil/gas, water distribution, and remote sites requiring wide-area monitoring.

**OT17** — Analog signals (4-20mA, 0-10V) are continuous representations of physical variables; digital signals are discrete or protocol-based. 4-20mA is preferred because 4mA "live zero" detects wire breaks (0mA = fault), it's less susceptible to noise over long distances, intrinsically safe, and is the industry standard.

**OT18** — OT asset inventory is a comprehensive list of hardware, software, firmware, and connections; it's the security foundation because you cannot secure or patch what you don't know. Tools: passive monitoring (packet capture, protocol analysis) and active scanning (vulnerability scanners). Active scanning is dangerous because it can crash legacy devices, cause network congestion, trigger false alarms, or disrupt processes.

**OT19** — MITRE ATT&CK for ICS maps tactics/techniques to industrial environments. Examples: Reconnaissance (T1580: Gather network topology), Resource Development (T1583: Acquire exploit tools), Initial Access (T1195: Supply chain compromise), Execution (T1059: Run malicious code on EWS), Persistence (T1547: Modify PLC firmware), Impact (T1499: Disrupt process). It differs from Enterprise ATT&CK by focusing on physical processes, safety, legacy protocols, and real-time constraints. Use it to map defenses, identify gaps, prioritize controls, and align with IEC 62443.

**OT20** — Log collection: passive taps, OT-friendly agents, protocol-specific collectors, buffer data to avoid impact. SIEM integration: normalize OT logs, correlate with IT, use OT data models. Detection rules: baseline normal traffic, alert on protocol anomalies, unauthorized commands, firmware changes, after-hours access. Triage: OT engineers validate physical impact, IT analysts handle context, joint playbook, prioritize safety. Staffing: IT analysts (threat intel), OT engineers (process/PLC knowledge), SOC manager (coordination), cross-training. False positives: tune rules, use allowlists, correlate with change management. Unauthorized firmware alert: isolate segment, verify safety, revert to secure vault firmware, audit change request, investigate source, update baseline.
