AA1 — A monolith is a single codebase deployed as one unit with shared memory/process. Microservices are independently deployable, loosely coupled services communicating over a network. Microservices introduce: (1) network latency/reliability overhead, (2) distributed data consistency challenges, and (3) operational complexity (orchestration, CI/CD pipelines, distributed tracing, and deployment coordination).

AA2 — Synchronous communication blocks the caller until a response is received, enabling tight coupling and real-time feedback (e.g., REST, gRPC). Asynchronous communication decouples sender/receiver; messages are queued and processed independently, improving resilience and throughput (e.g., RabbitMQ, Kafka, AWS SQS).

AA3 — A reverse proxy routes traffic, terminates SSL, and provides basic load balancing/caching. An API gateway adds API-specific capabilities: rate limiting, auth/authorization, request/response transformation, versioning, developer portals, and analytics. An API gateway cannot fully replace a reverse proxy; gateways typically sit behind or rely on reverse proxies for low-level traffic termination, DDoS mitigation, and L4/L7 routing efficiency.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to rollback if a step fails. Choreography uses events to trigger the next step (decentralized, harder to debug, best for simple/linear flows). Orchestration uses a central coordinator sending commands (centralized, easier to monitor/modify, best for complex/branching flows).

AA5 — CQRS separates read and write models. Event Sourcing stores state changes as an immutable event log. They pair naturally: CQRS reads from optimized projections, while ES provides the authoritative source of truth. This solves auditability, temporal queries, complex domain modeling, and independent scaling of reads/writes—problems where traditional CRUD struggles with performance, history tracking, and schema rigidity.

AA6 — The Circuit Breaker pattern prevents cascading failures by monitoring error rates. States: Closed (normal, passes requests), Open (threshold breached, fast-fails), Half-Open (allows limited probes to test recovery). Unlike retry+backoff (which assumes transient failures), a circuit breaker stops hammering a down service. Use both: retry+backoff for transient errors inside the Closed state; circuit breaker when errors persist to protect system stability.

AA7 — 
1. Shared DB/Schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, simplest ops.
2. Shared DB/Sep Schema: Medium cost, better isolation, easier per-tenant backup/restore, moderate ops.
3. Sep DB: Highest cost, best security/isolation, simplest backup/restore, highest ops complexity, lowest noisy-neighbor risk.
Trade-offs scale linearly: isolation/security improve with cost and operational overhead.

AA8 — Eventual consistency allows temporary divergence; strong consistency guarantees immediate visibility. For inventory that must never oversell: use strong consistency within partitions. Architecture: partition inventory by SKU/warehouse, use a strongly consistent store (PostgreSQL with row-level locking or Redis with Lua atomic decrements), implement optimistic concurrency control or distributed locks, and enforce idempotent claims. At scale, accept eventual consistency only across partitions if business rules allow; otherwise, use a centralized reservation service with strong consistency.

AA9 — A sidecar proxy co-locates with each service, intercepting all inbound/outbound traffic. In Istio, Envoy acts as the data plane (traffic routing, mTLS, metrics, retries), while Istiod is the control plane (config distribution, service discovery, cert rotation). Data plane = traffic forwarding; control plane = configuration/cert management. mTLS between sidecars solves infrastructure-level service authentication, automatic cert rotation, and uniform encryption without application code changes—unlike app-level TLS, which requires manual cert management and doesn't secure internal mesh traffic transparently.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is obsolete. Strategy: Deploy an API gateway. Route new endpoints to .NET 8 microservices. Keep legacy .NET Framework for existing endpoints. Gradually migrate features one-by-one, sharing the database initially, then decouple data per service. Update auth/logging in the gateway/middleware. Decommission legacy routes as coverage reaches 100%, then retire the monolith.

AA11 — 12-Factor App methodology optimizes apps for cloud deployment. Six factors: (1) Codebase (one repo, many deploys), (2) Dependencies (explicitly declared, isolated), (3) Config (env vars, not code), (4) Backing services (treated as attached resources), (5) Build/release/run (strictly separated stages), (6) Processes (stateless, ephemeral). They matter for portability, secure config management, reproducible deployments, horizontal scalability, and resilience in cloud-native environments.

AA12 — 
- Coupling: Event = loose; Request = tight.
- Scalability: Event = high throughput, burst handling; Request = predictable, synchronous scaling.
- Debugging: Event = complex tracing, replay needed; Request = straightforward logs.
- Ordering: Event = partition-level guaranteed; Request = per-request.
- Failure: Event = retry/Dead Letter Queue, idempotency; Request = timeouts, retries, circuit breakers.
Choose Event for async workflows, high throughput, audit trails, and decoupled systems. Choose Request for real-time APIs, strict consistency, and synchronous user-facing flows.

AA13 — A load balancer distributes traffic across backend servers. Layer 4 balances by IP/port (fast, no content inspection). Layer 7 balances by content (URL, headers, cookies, SSL). Layer 7 is required for routing `/api/v1` vs `/api/v2` to different services, SSL termination, or cookie-based session affinity.

AA14 — Message queues (RabbitMQ) consume and delete messages, support complex routing/exchanges, and guarantee delivery per consumer. Log-based brokers (Kafka) append messages, retain them, and allow multiple consumers to read the same data with replayability. Pick RabbitMQ for task queues, strict delivery, and complex routing. Pick Kafka for event streaming, log aggregation, real-time analytics, and replayability.

AA15 — Containers share the host OS kernel, package binaries/libs, and are lightweight/fast. VMs run a full guest OS under a hypervisor, consuming more resources. Containers are popular for microservices due to fast startup, consistent environments, efficient resource usage, and native orchestration support (Kubernetes).

AA16 — Stateless services hold no local session data; any instance can handle any request. Stateful services maintain local state. Stateless services scale horizontally easily because no affinity is needed; instances can be added/removed freely, and load balancers distribute evenly. Examples: Stateless = web/API server; Stateful = database, Redis cache.

AA17 — An ORM maps objects to database tables. Examples: Entity Framework (.NET), Hibernate (Java), Prisma (Node.js). Trade-offs: ORMs accelerate development, abstract DB differences, and simplify CRUD, but can generate inefficient queries, complicate complex joins, and require performance tuning. Raw SQL offers full control, optimal performance, and DB-specific features, but is verbose, DB-locked, and slower to develop.

AA18 — The Bulkhead pattern isolates resources so a failure in one component doesn't exhaust shared resources. It prevents thread/connection pool exhaustion from cascading. Implementation: Use separate thread pools and connection pools per downstream service, deploy critical vs non-critical services on different nodes/queues, or use resilience libraries (Resilience4j, Polly) to enforce bulkhead limits per dependency.

AA19 — OT requires a central server to transform concurrent operations, ensuring consistency but adding latency and complexity. CRDTs are mathematical structures that guarantee convergence without central coordination, enabling offline editing and higher client-side complexity. Choose CRDTs for offline-first collaborative editing: they allow concurrent edits offline, merge automatically when online, remove server dependency for conflict resolution, and simplify client architecture.

AA20 — Challenges include polyglot instrumentation, high volume, and async flow tracking. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject/extract trace IDs across HTTP/gRPC. Sampling: head-based is cheap but loses context; tail-based samples after processing for accuracy but adds overhead. Storage: Jaeger (OpenTelemetry-native) or Tempo (S3-backed, cost-effective). Async/Kafka: propagate trace context in message headers, use tail-based sampling to avoid dropping critical traces, and ensure producers/consumers inject/extract context. Without native tracing, use correlation IDs and log aggregation.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and security (e.g., VMware ESXi, Proxmox VE, KVM). Type 2 (hosted) run as applications on a host OS, offering ease of use but lower performance (e.g., VirtualBox, VMware Workstation).

OP2 — SAN provides block storage over a dedicated network, presenting disks to servers for high performance/low latency (protocols: Fibre Channel, iSCSI). NAS provides file storage over IP networks, enabling easy sharing (protocols: NFS, SMB/CIFS). Use SAN for databases/VMs; use NAS for file shares, backups, and home directories.

OP3 — 3-tier architecture uses Core, Distribution, and Access layers, creating hierarchical bottlenecks and asymmetric routing. Leaf-spine uses an all-to-all mesh with equal-cost multipath, providing predictable bandwidth, low latency, and no single point of failure. It solves spine-layer oversubscription and complex routing inherent in 3-tier designs, making it ideal for scale-out data centers.

OP4 — Use 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing (STONITH via IPMI/iLO) powers off failed nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. On node failure: HA manager detects failure, fences the node, and restarts VMs on healthy nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, `ip link set eth0.10 up`, then assign IPs/configure routing. Alternatively, use NetworkManager or netplan with VLAN interfaces.

OP6 — RAID 1: mirror, 50% cap, 1 fault. RAID 5: striping+parity, N-1 cap, 1 fault, write penalty. RAID 6: double parity, N-2 cap, 2 faults, higher write penalty. RAID 10: mirror+stripe, 50% cap, fast, survives multiple faults (not same pair). Z2: ZFS double parity, self-healing, flexible. For 6 drives + DB: RAID 10 for maximum write performance and fault tolerance, or Z2 for better capacity utilization and self-healing. I recommend RAID 10 for raw DB performance.

OP7 — Recursive resolvers: internal DNS servers (Windows DNS/BIND) for clients. Authoritative: internal AD DNS for internal zones, external DNS for public. Forwarders: point to ISP/Cloudflare for external resolution. Conditional forwarding: routes internal AD queries to AD DNS, external to forwarders. Split-horizon: internal DNS returns private IPs, external returns public. DNSSEC: signs external zone, validates recursively. Laptop roaming: DHCP assigns internal DNS; VPN uses split tunneling or conditional forwarding to route internal queries to corporate DNS. Roaming clients use cached records or dynamic updates.

OP8 — PKI chain: Root CA (offline, self-signed, long-lived) → Subordinate CA (online, issues certs) → End-entity cert. CRL = periodic revocation list; OCSP = real-time status check. Templates define key usage, validity, and auto-enrollment policies. Auto-enrollment pushes certs to domain-joined devices via AD CS. Compromised subordinate: issue new root/sub, revoke certs, minimal blast radius. Compromised root: catastrophic, requires rebuilding entire PKI and trust anchors.

OP9 — MPLS: high reliability, low latency, expensive, managed. IPsec VPN: cheap, internet-based, variable latency, manual. SD-WAN: app-aware routing, hybrid internet/MPLS, centralized management, cost-effective. WireGuard: modern, fast, simple, lacks enterprise QoS/management. Recommendation: SD-WAN. Best balance of cost, reliability, VoIP QoS, centralized management, and security for 50 users/site.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: out-of-band management interfaces for remote power control, console access, and hardware monitoring. Critical for OS recovery, provisioning, and management without physical access. Internet exposure: high risk due to default credentials and known CVEs; allows full server takeover, bypassing OS security. Must be isolated on a management network.

OP11 — LVM: traditional, fixed-size volumes, snapshots consume space quickly. LVM-Thin: overprovisions storage, cheap/fast snapshots, but performance degrades if pool fills. ZFS: integrated FS+volume manager, copy-on-write, instant space-efficient snapshots, self-healing, replication. Use LVM for legacy/simple needs, LVM-Thin for overprovisioning (monitor pool), ZFS for modern data integrity, snapshots, and all-in-one storage.

OP12 — Stretch cluster: 2 sites (A, B) + 1 quorum witness/tiebreaker. Ceph CRUSH rules spread replicas across sites. Monitors: 1 per site + witness, or 3 monitors with witness. Network latency: <5ms ideal, <10ms max. Split-brain prevented by quorum. 2-site Ceph without tiebreaker is bad because network partitions cause both sites to claim majority, leading to data corruption. The tiebreaker breaks deadlocks.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable: client retries, eventually falls back to APIPA (169.254.x.x), losing connectivity. On lease expiry: client attempts renewal at T1 (50%) and T2 (87.5%). If server down, lease expires, client drops IP, gets APIPA, and loses network access.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP monitoring, ACLs, and link aggregation. These features enable network segmentation, traffic prioritization, loop prevention, security enforcement, and troubleshooting in enterprise environments.

OP15 — NTP synchronizes clocks over networks. Critical for log correlation, Kerberos/certificate validation, distributed transactions, cluster consensus, and forensics. Clock drift causes Kerberos auth failures, split-brain in clusters, mismatched logs, database replication errors, and certificate validation issues.

OP16 — Physical: hardware directly. VM: full guest OS under hypervisor, strong isolation. Container: shared kernel, lightweight process isolation. Run bare metal for high-performance databases, real-time processing, hardware passthrough (GPUs/NICs), regulatory compliance, maximum I/O throughput, and ultra-low latency requirements.

OP17 — UPS provides battery backup, conditions power, and bridges short outages. Generators provide long-term power via fuel. Both are needed: UPS handles immediate transitions and protects against surges/brownouts; generators cover extended outages. ATS (Automatic Transfer Switch) detects utility failure, switches load to generator, and switches back when utility returns.

OP18 — Active-passive: one node handles traffic, standby takes over on failure. Active-active: both handle traffic, sync data, load balance. PostgreSQL HA with Pacemaker/Corosync: primary runs on node A, standby on B. VIP floats between nodes. STONITH fencing ensures failed node is powered off. Patroni/repmgr manages replication. On failure, Pacemaker promotes standby, moves VIP, and restarts services.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO defined by business criticality. Backup types: full (baseline), incremental (changes since last), differential (since last full). Deduplication reduces storage and backup windows. Media: disk for fast restore, tape/cloud for cheap offsite. Immutable backups: WORM/air-gapped storage for ransomware protection. Test restores: regular drills, verify integrity, measure RTO/RPO. Backup = data protection; DR = full recovery process (infrastructure, data, procedures) after catastrophic failure.

OP20 — 802.1X: supplicant (client), authenticator (switch), authentication server (RADIUS). EAP-TLS: cert-based, mutual auth, highly secure. PEAP: username/password, tunneled, common. RADIUS handles auth/authorization/accounting. Dynamic VLAN: switch assigns VLAN based on RADIUS attributes post-auth. Failure: port stays unauthorized, no access (or guest VLAN). MAB: switch uses device MAC as credentials to RADIUS. Fallback for printers/IoT lacking 802.1X; less secure, no per-user auth.
