T1 — `tofu plan` calculates and displays the execution plan (what will be created, changed, or destroyed) without making changes. `tofu apply` executes that plan, provisioning and managing infrastructure.

T2 — State is a JSON file mapping real-world resources to your configuration. Remote state stores this file in a shared backend (e.g., S3, GCS, Terraform Cloud), enabling team collaboration, state locking, and secure access control.

T3 — `count` iterates over integers; `for_each` iterates over maps or sets. `for_each` is preferred when resources have unique, non-sequential identifiers because removing an item from a list changes indices and forces recreation, whereas `for_each` only affects the specific key.

T4 — OpenTofu detects drift on the next `plan`/`apply`. It compares the remote state to the actual infrastructure. If config matches reality, it ignores drift. If config differs, it plans to overwrite or error. Use `lifecycle { ignore_changes = [...] }` to suppress expected manual changes.

T5:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `terraform_remote_state` reads entire state files, which is slow and exposes sensitive data. Output values expose only specific data. The recommended alternative is passing outputs directly via module inputs or using a dedicated state data source with explicit `outputs` filtering. This enforces least-privilege and improves performance.

T7 — `remote-exec` runs during resource creation, but the cluster may not be ready when the provisioner executes, leaving the kubeconfig empty. Fix: 1) Add `depends_on = [rke2_cluster]` to the null_resource. 2) Replace `remote-exec` with `local-exec` that polls until the cluster is healthy. 3) Prefer a dedicated kubeconfig data source that waits for readiness instead of provisioners.

T8 — `tofu import` maps existing infrastructure to config by manually editing state. Limitations: no config generation, error-prone, breaks on complex dependencies. The `import` block (1.5+) allows declarative imports in HCL, supports multiple resources, provides better error messages, and integrates with `plan` for validation.

T9 — A `variable` block defines input parameters for modules/root. An `output` block exposes computed values from modules/root to consumers. Variables flow in; outputs flow out.

T10 — A provider is a plugin that translates OpenTofu config into API calls for a platform. Without `tofu init`, providers aren't downloaded or initialized, causing `plan`/`apply` to fail with missing provider errors.

T11 — `.terraform.lock.hcl` pins provider versions, checksums, and sources. Commit it to ensure reproducible builds, prevent supply-chain attacks, and guarantee all team members/CI use identical provider binaries.

T12 — `tofu destroy` removes all managed resources in the current state. Target a single resource: `tofu destroy -target=module.name.resource.address`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to fetch the latest Ubuntu AMI ID instead of managing an AMI resource.

T14 — `locals` compute values within the configuration; `variable` blocks accept external inputs. Use `locals` for transformations, computed defaults, or values not intended to be configurable by users.

T15 — `lifecycle` controls resource behavior:
- `create_before_destroy`: Creates new before destroying old (zero-downtime for load balancers/security groups).
- `prevent_destroy`: Blocks accidental deletion; fails on `destroy`/`replace`.
- `ignore_changes`: Skips drift detection on specific attributes (e.g., auto-scaling tags, instance metadata).

T16 — The `moved` block remaps state addresses during refactoring. It tells OpenTofu to treat `old.address` as `new.address` without destroying/recreating, preserving state and dependencies.

T17 — OpenTofu builds a DAG of dependencies. Implicit dependencies are inferred from variable/resource references. Explicit `depends_on` forces ordering but disables parallelism for those resources. Overuse creates bottlenecks; use only when references can't express the dependency.

T18 — Strategies & tradeoffs:
1. `-refresh=false`: Skips remote state sync. Faster but risks stale state.
2. Split into multiple modules/workspaces: Reduces graph size. Increases maintenance overhead.
3. Use `depends_on`/references strategically: Minimizes unnecessary graph edges. Can reduce parallelism if misused.
4. Optimize backend/state: Use `terraform_remote_state` with explicit outputs, avoid heavy data sources. Improves speed but requires careful data modeling.

T19 — State locking uses a backend mechanism (e.g., DynamoDB) to prevent concurrent writes. If a lock isn't released, run `tofu force-unlock <lock-id>`. Risks: data corruption, lost changes, or overwriting concurrent work. Only break locks when safe.

T20 — Steps:
1. Backup local state (`cp .terraform/state.tfstate backup.tfstate`).
2. Update backend config in code to S3/DynamoDB.
3. Run `tofu init -migrate-state`. Confirm migration.
4. Verify: `tofu state list` should show resources under the new backend. State file is now in S3; DynamoDB handles locking.

A1 — A playbook is a YAML file orchestrating tasks across hosts. A role is a reusable collection of tasks, files, templates, and variables. A task is a single action/unit of work executed by a module.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_os_family }}`.

A3 — `command`: runs without shell features (safest). `shell`: runs via `/bin/sh`, supports pipes/redirects. `raw`: runs without Python, used for bootstrapping or unmanaged hosts.

A4 — Idempotency means repeated runs produce the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "timestamp" > /tmp/log.txt` (overwrites every run).

A5:
```yaml
- name: Install htop and epel-release
  package:
    name: "{{ item }}"
  loop:
    - htop
    - "{{ 'epel-release' if ansible_os_family == 'RedHat' else omit }}"
  when: ansible_os_family in ['Debian', 'RedHat']
```

A6 — Precedence (lowest to highest): role defaults → play vars → host_vars → group_vars → extra_vars. `set_fact` overrides at runtime. Command-line vars and extra vars always win.

A7 — Use `serial: [3, "100%"]` in the play. Group first 3 nodes in `[rke2_masters]`, rest in `[rke2_agents]`. Add a `wait_for` task on the first 3 to verify readiness before proceeding. Alternatively, split into two plays with separate `serial` values.

A8 — `ansible-vault encrypt_string 'my_secret' --name 'db_password' >> vars.yml`. This appends an encrypted inline variable without encrypting the whole file.

A9 — Inventory defines hosts/groups. Static inventory is a file (INI/YAML). Dynamic inventory is a script/API that generates inventory on-demand, ideal for cloud environments.

A10 — `ansible webservers -m shell -a "df -h"` or `ansible webservers -a "df -h"` (defaults to shell).

A11 — A handler is a task triggered by `notify`. It runs only if notified, at the end of the play. Regular tasks always run. Handlers prevent unnecessary restarts.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `log_path`.

A13 — `register` saves task output to a variable. Use it in subsequent tasks via `{{ var_name.stdout }}` or `when: var_name.rc == 0`.

A14 — `include_tasks` is dynamic (evaluated at runtime, supports `when`). `import_tasks` is static (evaluated at parse time, faster, no conditionals). Use `import` for performance, `include` for dynamic branching.

A15 — Ansible Galaxy is a hub for community roles/collections. `requirements.yml` lists them. Install via `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible reaches hosts. `ssh`: standard Linux/Unix. `local`: runs on control node. `network_cli`: CLI-based for routers/switches. Choose based on target OS/device type.

A17 — `delegate_to` runs a task on a different host. `run_once` runs once across a group. Example: gather disk metrics from a remote host, then `delegate_to: localhost` to write a single summary file once.

A18 — Strategies & tradeoffs:
1. Increase `forks`: More parallelism. Higher CPU/memory on control node.
2. Enable `pipelining`: Reduces SSH overhead. Requires sudoers config.
3. Fact caching (Redis/Memcached): Skips repeated fact gathering. Adds infrastructure dependency.
4. Mitogen: Replaces SSH with persistent connections. Faster but requires installation and may conflict with some modules.

A19 — Jinja2 uses `{{ }}` for output/expression, `{% %}` for control flow, `{# #}` for comments.
Template snippet:
```jinja2
upstream backend {
{# Health check comments generated dynamically #}
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; # {{ server.name }} - {{ 'UP' if server.healthy else 'DOWN' }}
{% endfor %}
}
```

A20 — Structure:
- `serial: 20%` (or `1`)
- `pre_tasks`: `uri` to deregister host from LB
- `tasks`: Deploy app
- `post_tasks`: `uri` health check loop. If healthy, register to LB.
- `block/rescue`: Wrap deploy+health check. On failure, `rescue` rolls back (revert code, re-register previous version, re-add to LB). Use `max_fail_percentage: 0` for strict zero-downtime.
