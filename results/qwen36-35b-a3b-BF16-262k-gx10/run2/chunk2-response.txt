K1 — A **Deployment** manages stateless workloads with interchangeable pods; pods have random names and no guaranteed startup order. A **StatefulSet** manages stateful workloads with stable, unique network IDs, ordered deployment/scaling, and persistent storage tied to each pod identity.

K2 — The Service Endpoint Controller populates an `Endpoints` object with pod IPs. `kube-proxy` watches Services and Endpoints, then programs node-level iptables or IPVS rules that load-balance traffic hitting the ClusterIP:Port to the backend pod IPs:Ports.

K3 — **PersistentVolume (PV)**: cluster-provisioned storage resource (static). **PersistentVolumeClaim (PVC)**: user request for storage matching size/access mode. **StorageClass**: dynamic provisioning template. Relation: PVC binds to an existing PV or triggers a StorageClass to dynamically create a PV, which is then bound to the PVC.

K4 — 1. `kubectl logs <pod> --previous` to check crash reason/exit code. 2. `kubectl describe pod` for OOMKilled events, liveness/readiness probe failures, or mount errors. 3. Verify resource requests/limits vs node capacity. 4. Check app dependencies (DB connectivity, env vars, startup command, config files).

K5 — CoreDNS provides internal DNS resolution for `svc.cluster.local` and pod FQDNs. If CoreDNS pods are down, internal service discovery fails (pods can't resolve cluster services), but external DNS resolution remains unaffected.

K6 — **Filtering**: removes nodes failing requirements (insufficient resources, taints, node selectors, affinity/anti-affinity, topology spread). **Scoring**: ranks remaining nodes using priority functions. Factors: LeastRequested/BalancedResourceAllocation (CPU/memory), NodeAffinity/TaintToleration, PodTopologySpread, VolumeBinding, and resource pressure.

K7 — Yes, it will schedule. 3.5GB + 256Mi ≈ 3.75GB < 4GB, so the scheduler sees enough requested capacity. At runtime, if it uses 600Mi (exceeds 512Mi limit), the cgroup OOM killer terminates the container, and Kubernetes restarts it (potentially CrashLoopBackOff).

K8 — 1. External LB routes traffic to the Ingress Controller Service (LoadBalancer/NodePort). 2. Ingress Controller watches Ingress resources and configures NGINX upstreams. 3. NGINX matches host/path, forwards request to the Kubernetes Service. 4. Service routes to Endpoints (pod IPs). 5. `kube-proxy`/iptables/IPVS handles node-level routing to the pod's network namespace. 6. Pod receives the request.

K9 — A **NetworkPolicy** restricts ingress/egress traffic at the pod level using labels. Default behavior (no policy): all traffic allowed. When applied: only traffic matching the policy's `ingress`/`egress` rules is permitted; all other traffic is explicitly denied.

K10 — **RollingUpdate** gradually replaces old pods with new ones (zero downtime). **Recreate** terminates all old pods before starting new ones (downtime). Choose Recreate for single-writer databases, stateful apps requiring atomic config/state replacement, or when zero-downtime isn't required and simplicity is preferred.

K11 — A **namespace** provides logical isolation and resource scoping within a cluster. Default namespaces: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed runtime state. Unlike `get pod`, it reveals: 1. Events (warnings, probe failures, scheduling issues). 2. Container last state/exit codes. 3. Resource requests/limits and node selectors/affinity. 4. Mounted ConfigMaps/Secrets/volumes. 5. Pod conditions and QoS class.

K13 — A **ConfigMap** stores non-sensitive configuration data. Pods consume it via: 1. Environment variables (`envFrom` or `env.valueFrom.configMapKeyRef`). 2. Volume mounts (files appear in the container filesystem).

K14 — **ClusterIP**: internal virtual IP, accessible only within the cluster. **NodePort**: exposes the service on a static port on each node's IP. **LoadBalancer**: provisions a cloud provider LB, routes to NodePort/ClusterIP, and exposes an external IP.

K15 — A **DaemonSet** ensures one pod runs on every (or selected) node. Use it for node-level daemons: logging agents, metrics collectors, network plugins, or storage drivers. Deployments manage a fixed replica count independent of node count.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes. Difference: taints/tolerations are about exclusion/inclusion, affinity is about preference/matching. Use case taints: dedicate GPU nodes to ML workloads. Use case affinity: schedule to specific AZs or hardware tiers.

K17 — An **Operator** is a custom controller that manages complex, stateful applications using CRDs and domain-specific reconciliation logic. Differs from a standard controller by automating lifecycle tasks (backups, upgrades, scaling, self-healing). Solves the gap between Kubernetes primitives and operational expertise for stateful apps.

K18 — etcd uses **Raft** for linearizable reads/writes. If quorum is lost, the cluster becomes read-only/unwritable (cannot commit new transactions). Recovery from 2/3 nodes lost: restore the surviving node from the latest snapshot + WAL, or add new nodes and restore from a known-good backup. Without a backup, data is permanently lost.

K19 — **Role/ClusterRole** define permissions (rules). **RoleBinding/ClusterRoleBinding** bind roles to users/groups/serviceaccounts. Manifest:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` (default 5) tells the resolver to try appending up to 5 search domains before querying upstream. For external domains, this causes 5+ unnecessary internal DNS queries, causing latency. Fix: set `dnsConfig.options: [{name: "ndots", value: "2"}]` in the pod spec, or use FQDNs with a trailing dot (`service.external.com.`).

D1 — **Merge** creates a merge commit, preserving branch history. **Rebase** rewrites commits onto a new base, linearizing history. Avoid rebasing on shared/public branches or after pushing to remote, as it rewrites history and causes conflicts for collaborators.

D2 — **TCP**: connection-oriented, reliable, ordered, flow/congestion control. **UDP**: connectionless, unreliable, low-latency, no ordering. TCP: HTTP, SSH, FTP. UDP: DNS, VoIP, live streaming.

D3 — A **race condition** occurs when concurrent threads/processes access shared state without synchronization, leading to non-deterministic results. Example: two threads incrementing a shared counter without a mutex, resulting in lost updates.

D4 — **Symmetric**: single key for encryption/decryption (fast). **Asymmetric**: public/private key pair (slower, enables secure key exchange). TLS uses asymmetric encryption during handshake to authenticate and exchange a session key, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates an immutable **image layer**. Layer caching speeds up builds by reusing unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., copy `package.json`/install deps first, then copy source code).

D6 — 1. Check upstream service logs/metrics for errors or timeouts. 2. Verify rate limiting/throttling or circuit breaker trips. 3. Inspect resource exhaustion (CPU/memory throttling, OOM). 4. Review load balancer/ingress health checks, connection limits, and TLS handshake failures. Order: app → infra → network → config.

D7 — **CAP theorem**: a distributed system can only guarantee two of Consistency, Availability, Partition tolerance. **CP**: CockroachDB, HBase (prioritize consistency; may become unavailable during network partitions). **AP**: Cassandra, DynamoDB (prioritize availability; may return stale data during partitions).

D8 — **Horizontal scaling**: add more nodes/instances. **Vertical scaling**: increase CPU/RAM of existing node. Patterns enabling horizontal scaling: stateless services, distributed databases, message queues, container orchestration, microservices architecture, and externalized sessions/state.

D9 — An **environment variable** is a dynamic value passed to processes at runtime. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict, key-value/array syntax, universally parsed by machines. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: strict schema/parsing, ideal for APIs. YAML advantage: readability, less verbose, ideal for config files.

D11 — A **REST API** is an architectural style using HTTP methods on resource URIs. **GET**: retrieve data. **POST**: create a new resource. **PUT**: replace/update a resource. **DELETE**: remove a resource.

D12 — **Version pinning** locks dependencies to exact versions (e.g., `package@1.2.3`). Critical for reproducible builds, preventing unexpected breaking changes, simplifying security auditing, and ensuring CI/CD parity with production.

D13 — **Compiled**: source code is translated to machine code before execution (C, Rust). **Interpreted**: source code is executed line-by-line by a runtime (Python, JavaScript). Note: many modern languages use JIT compilation (Java, Go, C#).

D14 — A **reverse proxy** sits in front of servers, routing client requests to backends. **Forward proxy** sits in front of clients, routing outbound requests. Reverse proxy use cases: Nginx (load balancing, SSL termination), HAProxy (high-performance TCP/HTTP routing). Forward proxy use cases: corporate content filtering, outbound caching.

D15 — A **deadlock** occurs when two or more processes wait indefinitely for resources held by each other. **Coffman conditions**: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait. All must hold simultaneously.

D16 — **Eventual consistency** guarantees that, without new updates, all replicas will eventually converge. Cassandra handles read-after-write via **tunable consistency**: `QUORUM` on both reads and writes provides strong consistency for that key. `SERIALIZABLE` offers stricter guarantees. Lightweight transactions (LWT) use Paxos for atomic read-modify-write.

D17 — **mTLS** requires both client and server to present valid certificates. Handshake: ClientHello → ServerHello+Cert → ServerKeyExchange → ClientKeyExchange+Cert → certificate verification → session key derivation. Commonly used in: service meshes (Istio/Linkerd), internal microservices, zero-trust architectures, and database replication.

D18 — A **hash table** maps keys to values via a hash function → array index. **Collision resolution**: chaining (linked lists at each bucket) or open addressing (linear/quadratic probing, double hashing). Time complexity: average O(1) for insert/lookup/delete. Worst O(n) if all keys hash to the same bucket.

D19 — The **circuit breaker** prevents cascade failures by failing fast when a downstream service is unhealthy. **States**: Closed (normal traffic), Open (fail fast after error threshold), Half-open (allow limited test requests). Relates to retries: circuit breakers should be paired with exponential backoff retries to avoid overwhelming a recovering service while allowing gradual recovery.

D20 — **Optimistic concurrency** assumes no conflicts, validates at commit (e.g., row versioning: `UPDATE table SET val=? WHERE version=?`). **Pessimistic concurrency** locks resources during transaction (e.g., `SELECT ... FOR UPDATE`). Choose optimistic for high read/low write contention. Choose pessimistic for high write contention or critical financial/booking systems.
