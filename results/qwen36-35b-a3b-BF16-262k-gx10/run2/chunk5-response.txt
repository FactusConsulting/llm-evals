DN1 — **class** is a reference type (heap-allocated, supports inheritance, nullable, GC-managed). **struct** is a value type (stack/inline-allocated, copy-on-assign, no inheritance, not nullable by default). Use structs for small, immutable, short-lived data that doesn't require inheritance (e.g., coordinates, IDs, math vectors, cache keys).

DN2 — `IEnumerable<T>` executes in-memory (LINQ to Objects), pulling data first then filtering. `IQueryable<T>` builds an expression tree that translates to a remote query (e.g., SQL), pushing filtering/joins to the data source. This matters because `IQueryable` reduces memory footprint, network traffic, and DB load by executing operations server-side.

DN3 — `async/await` compiles to a state machine that yields control without blocking threads, preserving context by default. `Task` is a reference type (heap-allocated). `ValueTask` is a value type that avoids allocation when completed synchronously. Use `ValueTask` in hot paths where async methods frequently complete synchronously or are called repeatedly to eliminate GC pressure.

DN4 — DI inverts control by letting a container resolve and manage object lifecycles. **Transient**: new instance per resolution. **Scoped**: one instance per scope (e.g., HTTP request). **Singleton**: one instance per container. Injecting a Scoped service into a Singleton captures it at creation, effectively making it Singleton-lived → stale state, thread-safety bugs, or memory leaks. Fix: inject `IServiceScopeFactory` and create a scope manually inside the Singleton.

DN5 — `string` is immutable, heap-allocated, and GC-managed. `ReadOnlySpan<char>` is a stack-only, zero-copy slice with no GC pressure. `Span<T>` is the mutable counterpart. Use `Span<T>`/`ReadOnlySpan<char>` for high-performance parsing, string manipulation, or buffer processing in hot paths to avoid allocations and enable contiguous memory access.

DN6 — The GC traces live objects, reclaims unreachable memory, and compacts Gen 0/1. **Gen 0**: short-lived, collected frequently. **Gen 1**: buffer. **Gen 2**: long-lived, collected rarely. **LOH**: objects >85KB, not compacted (causes fragmentation), collected with Gen 2. `IDisposable` is for deterministic cleanup of unmanaged resources (handles, DB connections, file streams). GC only manages managed memory; it doesn't understand OS resources.

DN7 — Default `async` captures the current `SynchronizationContext` (or `TaskScheduler`) to resume on the original thread. `ConfigureAwait(false)` skips capture, resuming on any thread pool thread. Use `ConfigureAwait(false)` in libraries/shared code to avoid deadlocks and reduce context-switch overhead. Do NOT use it in UI/app code where you must update UI/state on the original thread. It directly interacts with `SynchronizationContext` to prevent sync-over-async deadlocks.

DN8 — **Primary constructors**: `public class Service(IOptions<AppSettings> cfg) { ... }` (reduces boilerplate). **Collection expressions**: `[1, 2, 3]`, `..array`, `..list` for concise array/span creation. **FrozenDictionary**: immutable, highly optimized for lookup-heavy scenarios, lower memory/CPU than `Dictionary`. Example with DI:
```csharp
public class MyService(IOptions<AppSettings> settings) {
    private readonly AppSettings _cfg = settings.Value;
}
```

DN9 — Likely cause: `DbContext` is registered as `Scoped` but resolved/shared outside the request scope (e.g., in a Singleton, static field, or prematurely disposed via `using`). Under high concurrency, async operations outlive the scope, causing `ObjectDisposedException`. Fix: ensure `DbContext` is `AddScoped`, resolved per-request, and never manually disposed if managed by DI. EF Core's `DbContext` is thread-unsafe; DI scoping guarantees one instance per request, preventing cross-request state corruption.

DN10 — `record` is a reference type with value-based equality, immutability by default, positional syntax, and `with` expressions. `class` is mutable with reference equality. `record struct` is a value type with value equality and zero-allocation semantics. Choose `record` for immutable DTOs/state snapshots. Choose `record struct` for performance-critical, short-lived, small data (e.g., game entities, math structs, cache entries).

DN11 — `ref`: pass by reference, must be initialized before call, read/write. `out`: pass by reference, must be assigned inside method, initialization before call not required. `in`: pass by reference, read-only, prevents copying large structs. Use `ref` for modifying existing values, `out` for multiple return values/parsing, `in` for large structs to avoid copy overhead.

DN12 — Nullable Reference Types (`string?`) are compile-time annotations that warn about potential null dereferences; they don't change runtime behavior. Nullable Value Types (`int?`) are runtime types (`Nullable<T>`) that can actually hold `null`, affect boxing/unboxing, and impact memory. NRTs are static analysis; `int?` is a runtime feature.

DN13 — LINQ unifies querying across collections, DBs, XML, etc. **Method syntax** (`.Where(...)`) is fluent and preferred for complex chains. **Query syntax** (`from x in list where ...`) is SQL-like and compiles to method syntax. **Deferred execution** means the query isn't executed until enumerated (e.g., `foreach`, `.ToList()`), enabling composition, lazy evaluation, and remote translation.

DN14 — `where T : class` (reference type), `where T : struct` (value type, non-nullable), `where T : new()` (parameterless constructor), `where T : IComparable<T>` (implements comparison). Combine when a type needs multiple guarantees (e.g., `where T : class, IComparable<T>, new()`). Prevents invalid operations at compile time and enables safe generic algorithms.

DN15 — Abstract classes can have state, constructors, and non-virtual methods; support single inheritance. Interfaces define contracts; support multiple inheritance. **Default interface methods** (C# 8+) allow interfaces to contain implementations, enabling backward-compatible API evolution without breaking existing implementers, narrowing the historical gap between the two.

DN16 — Middleware processes requests/responses sequentially. `app.Use()` adds middleware that can call `next()` to pass down. `app.Map()` branches the pipeline by path prefix. `app.Run()` is terminal (no `next()`). Ordering matters: auth/routing before static files, exception handling early. `UseExceptionHandler` catches unhandled exceptions, logs them, and returns a standardized error response before other middleware runs.

DN17 — `Channel<T>` is async-native, supports bounded/unbounded modes, and built-in backpressure. `BlockingCollection<T>` is older, sync/blocking, less async-friendly. Example:
```csharp
var channel = Channel.CreateBounded<int>(10);
// Producer: await channel.Writer.WriteAsync(item); // blocks when full
// Consumer: var item = await channel.Reader.ReadAsync(); // blocks when empty
```
Bounded channels naturally apply backpressure: producers await when the buffer is full, preventing memory exhaustion.

DN18 — Source Generators compile-time code generation via Roslyn APIs, outputting C# source. Faster/safer than reflection (runtime, slower) and IL weaving (modifies compiled IL, breaks debuggers/tools). **Incremental generators** (`ISourceGenerator` replacement) use `IncrementalGeneratorInitializationContext`, support caching, incremental compilation, and integrate with the Roslyn analyzer pipeline. Preferred for performance, modern .NET build integration, and better IDE support.

DN19 — TPL Dataflow provides an async pipeline/actor model. `ActionBlock` processes items (no output), `TransformBlock` processes and outputs transformed items, `BufferBlock` stores/passes through unchanged. Compared to `Channels`, Dataflow offers richer composition (fan-out/in, completion propagation, backpressure tuning, link options) and is better for complex pipelines. Channels are simpler, async-first, and ideal for straightforward producer-consumer patterns.

DN20 — Minimal APIs are lightweight, inline routing/handlers with less boilerplate and faster startup. Controllers use attribute-based routing, richer DI/middleware integration, and scale better for complex apps. Trade-offs: Minimal APIs are harder to test (inline), have limited per-endpoint middleware, and require Swashbuckle/NSwag for OpenAPI. Controllers offer better structure for large teams. Route groups (`app.MapGroup("/api").WithTags("Users")`) apply prefixes/metadata. Endpoint filters (`builder.AddFilter(...)`) inject cross-cutting logic (auth, validation, logging) per endpoint.

P1 — **List**: mutable, ordered, indexed, allows duplicates. **Tuple**: immutable, ordered, fixed size, heterogeneous, ideal for returning multiple values. **Set**: mutable, unordered, unique elements, hash-based. **Frozenset**: immutable set, hashable, can be dict keys or set members.

P2 — **GIL**: a mutex allowing only one thread to execute Python bytecode at a time. **Affects**: CPU-bound multithreading (no true parallelism). **Workarounds**: Multiprocessing, C extensions that release the GIL, `asyncio` for I/O-bound work, or offloading to native/C/Rust.

P3 — `copy.copy()` creates a shallow copy (new container, references nested objects). `copy.deepcopy()` recursively copies all nested objects. Example: `a = [[1,2]]; b = copy.copy(a); b[0].append(99); print(a)` → `[[1, 2, 99]]` because inner lists are shared.

P4 — Decorators wrap/modify functions without changing source. Timing example:
```python
import time, functools
def log_time(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

P5 — Generators use `yield` to produce iterators lazily, preserving state between yields. Unlike lists, they compute on-demand, use minimal memory, and are single-pass. `yield from` delegates to another generator/iterable, simplifying nesting and forwarding.

P6 — The event loop is a single-threaded scheduler for async tasks. `asyncio.run()` creates the loop and runs a coroutine. `asyncio.gather()` runs multiple coroutines concurrently, returning results. `asyncio.create_task()` schedules a coroutine for background execution. `time.sleep()` blocks the entire event loop thread; use `await asyncio.sleep()` instead.

P7 — MRO defines the method lookup order. Python 3 uses **C3 linearization**. Diamond inheritance (`D(B, C)` where both inherit `A`) is resolved left-to-right: `D → B → C → A`. `B` doesn't override `who`, `C` does, so `C.who()` is called. Output: `C`. C3 guarantees consistent, predictable resolution without diamond ambiguity.

P8 — A **metaclass** controls class creation (`__new__`, `__init__`), enabling class-level hooks but adding complexity. `__init_subclass__` is a simpler hook called when a class is subclassed, without metaclasses. **Metaclass use case**: ORM model registration, enforcing class-level constraints. **`__init_subclass__` use case**: Auto-registering plugins, setting default attributes on subclasses.

P9 — **Threading**: I/O-bound, shares memory, GIL limits CPU parallelism. **Multiprocessing**: CPU-bound, separate processes, bypasses GIL, higher overhead. **concurrent.futures**: High-level API unifying both (`ThreadPoolExecutor`, `ProcessPoolExecutor`). **Pickling**: Multiprocessing serializes args/results via pickle. Unpicklable objects (locks, DB connections, lambdas) fail. Use `multiprocessing.shared_memory` or `pathos` for complex objects.

P10 — `__slots__` declares a fixed set of attributes, preventing `__dict__` creation. Use it for memory optimization, performance, and preventing accidental attribute assignment. Memory impact: significant per-instance reduction (no dict overhead), but doesn't reduce class-level memory. Prevents dynamic attribute addition.

P11 — A virtual environment isolates Python packages/interpreter per project, preventing dependency conflicts. `venv`: standard library module (Python 3.3+). `virtualenv`: third-party, older, more features (e.g., pip upgrade). `conda`: package + environment manager, handles non-Python binaries, data-science focused.

P12 — Comprehensions (`[x for x in lst if x > 0]`) are Pythonic, readable, and often faster. `map()`/`filter()` return lazy iterators, functional in style. Prefer comprehensions for readability/simple logic. Use `map()`/`filter()` for performance with C-implemented functions or when composing functional pipelines.

P13 — `==` checks value equality. `is` checks object identity (same memory address). **Interning**: CPython caches small integers (-5 to 256) and some strings for memory/performance. `a is b` returns `True` for small ints because they reference the same cached object.

P14 — `*args` collects extra positional arguments into a tuple. `**kwargs` collects extra keyword arguments into a dict. `/` marks parameters before it as positional-only. `*` marks parameters after it as keyword-only. Use for flexible APIs, argument forwarding, and enforcing calling conventions.

P15 — Context managers (`with`) guarantee cleanup (`__exit__`) even on exceptions. Implement via `__enter__`/`__exit__` (class-based) or `@contextmanager` (generator-based, simpler). Example beyond files: database transactions, lock acquisition, temporary directory changes, or HTTP request/response lifecycle management.

P16 — Type hints are static annotations ignored at runtime. `Union[X, Y]`/`Optional[X]` (Union[X, None]): multiple types. `Literal[x]`: exact value constraint. `TypeVar`: generic type variables with constraints/bounds. `Protocol`: structural subtyping (duck typing). `mypy`/`pyright` parse hints for static type checking, catching errors early and enabling IDE autocomplete.

P17 — `__repr__`: unambiguous, developer-focused. `__str__`: readable, user-focused. `__eq__`: equality check. `__hash__`: hash value for dict/set keys. `__getattr__`: fallback when attribute not found. `__getattribute__`: called for every attribute access (dangerous). Defining `__eq__` without `__hash__` sets `__hash__ = None`, making instances unhashable (can't be dict keys/set members).

P18 — Descriptors implement `__get__`, `__set__`, `__delete__` to intercept attribute access on the owner class. `property` uses descriptors for computed attributes. `classmethod`/`staticmethod` are descriptors that modify `self`/`cls` binding. Under the hood, they're assigned to the class dict; the descriptor protocol triggers when accessed via an instance.

P19 — Relative imports (`from . import mod`) resolve relative to the package. Absolute imports (`import pkg.mod`) resolve from `sys.path`. `sys.path` lists search directories; `PYTHONPATH` prepends to it. `__init__.py` marks directories as packages and runs on import. Namespace packages (PEP 420) omit `__init__.py`, allowing split packages. **Finder**: locates modules. **Loader**: loads/compiles them. `importlib` standardizes this.

P20 — `dataclasses` (built-in) generates `__init__`, `__repr__`, `__eq__`. `attrs` (third-party) offers more features/validators. `Pydantic` adds validation, serialization, type coercion, and ORM integration. `__post_init__` runs after `__init__` for custom logic. `field(default_factory=list)` avoids mutable default argument bugs. `frozen=True` makes instances immutable. Inheritance works but requires careful `__init__` merging. Choose Pydantic when validation, serialization, or config parsing is critical.
