AA1 — Monoliths are single codebases deployed as one unit with shared memory/processes. Microservices are independently deployable, loosely coupled services communicating over networks. Microservices introduce: (1) network latency/failure handling, (2) distributed tracing/debugging complexity, and (3) data consistency challenges across service boundaries.

AA2 — Synchronous communication blocks the caller until a response is received (e.g., REST/gRPC). Asynchronous communication decouples sender/receiver; messages are processed independently (e.g., RabbitMQ, Kafka). Sync is simpler for immediate feedback; async enables scalability and resilience.

AA3 — A reverse proxy routes traffic, handles SSL termination, and load balances at L4/L7. An API gateway adds business logic: rate limiting, auth, versioning, request transformation, and analytics. An API gateway cannot fully replace a reverse proxy; gateways sit behind infrastructure proxies for performance, L4 routing, and separation of concerns.

AA4 — A Saga breaks distributed transactions into local transactions with compensating actions for rollback. Choreography uses events to trigger next steps (decentralized, harder to debug, good for simple flows). Orchestration uses a central coordinator sending commands (easier monitoring/modification, good for complex flows).

AA5 — CQRS separates read and write models. Event Sourcing persists state as an immutable event log. Combined, they solve auditability, temporal queries, complex domain modeling, and independent read/write scaling. Traditional CRUD struggles with historical state reconstruction, immutable audit trails, and optimizing read/write workloads separately.

AA6 — Circuit Breaker prevents cascading failures. States: Closed (normal), Open (threshold breached, fast-fail), Half-Open (tests recovery). Differs from retry: retry assumes transient spikes; circuit breaker assumes systemic degradation. Use together: retry handles transient errors; circuit breaker stops calls when a service is truly down.

AA7 — (1) Shared DB/schema: lowest cost, highest noisy-neighbor risk, complex row-level security, simplest ops. (2) Shared DB/separate schema: better isolation, moderate cost/ops, easier per-tenant backup. (3) Separate DB/tenant: highest security/isolation, highest cost/ops, eliminates noisy-neighbor, best for compliance.

AA8 — Eventual consistency allows temporary divergence; strong consistency guarantees immediate visibility. For inventory oversell prevention: use strong consistency within a single authoritative partition (e.g., PostgreSQL with row-level locking or Redis atomic ops). Implement optimistic locking (version fields) or synchronous reservation patterns. At scale, partition by SKU/warehouse, keep strong consistency per partition, and avoid async reconciliation for oversell-critical paths.

AA9 — A sidecar proxy co-locates with an app to handle traffic. In Istio, Envoy proxies manage L7 routing, retries, and mTLS. Data plane = Envoy proxies forwarding traffic; control plane = Istiod pushing config/certs. mTLS between sidecars solves MITM risks and identity verification transparently without app code changes, unlike application-level TLS which requires manual cert management and code integration.

AA10 — The Strangler Fig pattern incrementally replaces functionality by routing traffic to new services while keeping the legacy intact. Strategy: Deploy an API gateway. Route new/changed endpoints to .NET 8 microservices. Keep .NET Framework handling remaining routes. Gradually migrate features, split data as needed, and decommission legacy routes once fully replaced.

AA11 — 12-Factor App methodology for cloud-native apps. Key factors: (1) Codebase (1 dep per app), (2) Dependencies (explicitly declare), (3) Config (env vars), (4) Backing services (treat as attached resources), (5) Build/release/deploy (strict separation), (6) Processes (stateless/ephemeral). They matter for horizontal scaling, zero-downtime deploys, secure config management, and predictable multi-environment behavior.

AA12 — Coupling: Event = loose, Request = tight. Scalability: Event = high throughput/async scaling, Request = synchronous limits. Debugging: Event = complex tracing/state, Request = straightforward flow. Ordering: Event = partition-level guaranteed, Request = per-request. Failure: Event = retry/DLQ/idempotency needed, Request = immediate error/simple retries. Choose Event for decoupled systems, high throughput, audit trails. Choose Request for real-time responses, simple CRUD, synchronous validation.

AA13 — A load balancer distributes traffic across servers. L4 balances by IP/port (fast, no content inspection). L7 inspects HTTP headers/URLs, enables routing/SSL termination. L7 is required for URL-based routing, SNI, or header-based load balancing.

AA14 — Message queues (RabbitMQ) consume/remove messages, ideal for task queues and complex routing. Log-based brokers (Kafka) retain messages, support multiple consumers reading the same data, ideal for streaming and replay. Pick RabbitMQ for strict delivery/task processing; pick Kafka for high-throughput event streaming and consumer independence.

AA15 — Containers share the host OS kernel, are lightweight, and start instantly. VMs run full guest OSes via a hypervisor, consuming more resources. Containers are popular for microservices due to density, portability, immutable infrastructure, and rapid scaling.

AA16 — Stateless services hold no local session data; any instance can handle any request, making horizontal scaling trivial (add/remove without data migration). Example: Web/API server. Stateful services maintain local state; scaling requires data affinity/replication. Example: Database, Redis.

AA17 — An ORM maps objects to DB tables, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java). Trade-offs: ORM accelerates dev and reduces SQL expertise needs but can generate inefficient queries, leak abstraction on complex joins, and complicate performance tuning. Raw SQL offers full control and optimal performance but requires more code, DB-specific knowledge, and slower development.

AA18 — The Bulkhead pattern isolates resources to prevent cascading failures. In microservices, it stops one failing dependency from exhausting threads/memory of others. Implementation: Separate thread/connection pools per downstream service, or deploy critical vs non-critical services on separate node pools/K8s namespaces with resource quotas and network policies.

AA19 — OT requires a central server to transform concurrent operations, ensuring consistency but adding latency and complexity. CRDTs use mathematical structures that converge automatically without server coordination, enabling offline editing and lower latency. For offline support, choose CRDTs: local changes merge automatically, no round-trip transformation needed, and architecture is simpler.

AA20 — Challenges: polyglot instrumentation, async flows, overhead, data volume. Context propagation: W3C Trace Context (standard) or B3; inject/extract trace IDs across services. Sampling: head-based (cheap, loses context), tail-based (accurate, high overhead). Storage: Jaeger/Tempo use columnar/object storage optimized for trace queries. Kafka continuity: propagate trace headers in Kafka message metadata; SDKs/interceptors auto-extract and continue spans.

OP1 — Type 1 (bare-metal) runs directly on hardware, offering high performance and security (e.g., VMware ESXi, Proxmox VE, KVM). Type 2 (hosted) runs on a host OS, easier to set up but lower performance (e.g., VirtualBox, VMware Workstation).

OP2 — SAN provides block storage over a dedicated network (Fibre Channel, iSCSI), ideal for databases/VMs requiring low latency. NAS provides file-level storage over standard networks (NFS, SMB/CIFS), ideal for file shares/backups. Choose SAN for performance/VMs; NAS for simplicity/file sharing.

OP3 — 3-tier (core/distribution/access) is hierarchical but suffers from oversubscription and asymmetric routing. Leaf-spine uses an all-to-all mesh, providing predictable low latency, non-blocking bandwidth, and horizontal scalability. It solves spine congestion and complex routing inherent in 3-tier designs.

OP4 — Use 3+ nodes for quorum. Quorum prevents split-brain via majority voting. Fencing (STONITH) via IPMI/iDRAC powers off failed nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. On node failure: HA manager detects it, fences the node, and restarts VMs on healthy nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, assign IPs, and configure the switch port as a trunk.

OP6 — RAID 1: mirror, 50% cap, 1 fault. RAID 5: striping+parity, N-1 cap, 1 fault, write penalty. RAID 6: double parity, N-2 cap, 2 faults, higher write penalty. RAID 10: mirror+stripe, 50% cap, fast, survives multiple faults. RAID Z2: ZFS double parity, flexible cap, scrubbing, superior recovery. For 6 drives + DB: RAID 10 for write-heavy performance, or Z2 for capacity/fault tolerance and data integrity.

OP7 — Recursive resolvers: internal DNS servers for clients. Authoritative: internal zone for AD, external for public. Forwarders: point to ISP/Cloudflare. Conditional forwarding: routes internal AD queries to DCs. Split-horizon: internal returns private IPs, external returns public. DNSSEC: signs external zone, chains to root. Laptop move: DHCP provides internal DNS on LAN; VPN pushes internal DNS/conditional forwarders, ensuring seamless resolution.

OP8 — PKI chain: Root CA (offline, self-signed, long-lived) → Subordinate CA (online, issues certs) → End-entity. CRL = periodic revocation list; OCSP = real-time status. Templates = predefined cert properties. Auto-enrollment = AD CS pushes certs to machines/users. Compromised subordinate: issue new subordinate, revoke certs, minimal blast radius. Compromised root: catastrophic, requires rebuilding entire PKI and trust anchors.

OP9 — MPLS: reliable, low latency, expensive, managed. IPsec VPN: cheap, internet-based, variable latency, manual. SD-WAN: orchestrates MPLS/IPsec/WiFi, app-aware routing, centralized management, moderate cost. WireGuard mesh: modern crypto, fast, lacks enterprise QoS/orchestration. Recommendation: SD-WAN for 50 users/site with VoIP (QoS, dynamic path selection, centralized management).

OP10 — iDRAC/iLO/IPMI provide out-of-band management independent of the OS/hardware. Critical for remote recovery, power cycling, console access, and firmware updates. Internet exposure risks brute force, credential stuffing, and unauthorized hardware control. Should be isolated on a management network.

OP11 — LVM: traditional, fixed volumes, COW snapshots consume space. LVM-Thin: overprovisioning, dynamic allocation, thin snapshots, can exhaust pool space. ZFS: integrated FS+volume manager, COW, space-efficient snapshots, send/receive, scrubbing. Use LVM for legacy/simple, LVM-Thin for flexible dev/test, ZFS for data integrity and enterprise storage.

OP12 — Ceph CRUSH maps OSDs to failure domains (sites), replicating across them. Monitors: odd number, spread across sites, require <10ms latency. Split-brain: both sites write independently, causing corruption. 2-site Ceph without a tiebreaker fails because neither side can win quorum. A tiebreaker (quorum device/VM) breaks deadlocks, ensuring only one site writes.

OP13 — DHCP uses DORA: Discover, Offer, Request, Acknowledge. If the server is unavailable and a Windows lease expires, the client falls back to APIPA (169.254.x.x), losing network connectivity until renewal or server recovery.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches provide VLANs, QoS, STP, port security, ACLs, and monitoring. Critical for segmentation, traffic prioritization, loop prevention, and security in enterprises.

OP15 — NTP synchronizes clocks over networks. Critical for log correlation, Kerberos/AD auth, distributed transactions, certificate validation, and cluster consensus. Clock drift causes Kerberos failures, split-brain, log timeline corruption, and replication lag.

OP16 — Physical servers: direct hardware access. VMs: OS virtualization with isolation. Containers: process isolation sharing the host kernel. Run bare metal for high-performance DBs, real-time processing, hardware passthrough (GPUs/NICs), regulatory compliance, or maximum I/O throughput.

OP17 — UPS provides short-term battery backup and power conditioning, bridging to generators. Generators provide long-term fuel-based power. Both are needed: UPS handles switchover/transients; generators sustain load. ATS automatically switches power from utility to generator during outages.

OP18 — Active-passive: one handles traffic, standby takes over. Active-active: all handle traffic, sync state. PostgreSQL HA: Pacemaker/Corosync manages resources. STONITH (fencing) via IPMI/pacemaker-remote. Virtual IP floats to active node. Streaming replication syncs data. Failover: Pacemaker detects failure, fences old master, promotes standby, moves VIP.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. Define RPO/RTO by business impact. Full (baseline), incremental (since last), differential (since last full). Deduplication reduces storage/backup windows. Disk for fast restore, tape/cloud for cheap offsite. Immutable (WORM/air-gapped) protects against ransomware. Test restores regularly to verify integrity and measure RTO. Backup = data protection; DR = full environment recovery (infra, apps, data, processes).

OP20 — 802.1X roles: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP-TLS: cert-based mutual auth, highly secure. PEAP: username/password in encrypted tunnel, common. RADIUS handles AAA. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: port stays unauthorized, blocks traffic (may fall back to guest VLAN). MAB: switch uses device MAC as credential, queries RADIUS, bypasses 802.1X for IoT/printers.
