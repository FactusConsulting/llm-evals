**CL1** — IaaS provides virtualized compute, network, and storage; you manage OS, middleware, runtime, data, and apps (e.g., AWS EC2). PaaS provides managed runtime and middleware; you manage apps and data (e.g., AWS Elastic Beanstalk). SaaS provides fully managed applications; you manage only configuration and user data (e.g., AWS WorkSpaces or Salesforce).

**CL2** — The Shared Responsibility Model divides security: provider secures the cloud (physical, global infra, hypervisor, managed service control plane); you secure what you put in it. IaaS VM: provider = infra/hypervisor; you = OS, patches, network, data, app. Managed K8s: provider = control plane, node OS, API server; you = worker config, pod security, network policies, app, secrets. SaaS (M365): provider = app, infra, compliance config; you = user access, data classification, sharing policies, MFA.

**CL3** — VPC: virtual network boundary. Subnet: IP range within a VPC, typically AZ-scoped. Security Group (SG): stateful, instance/pod-level, allow-only rules, evaluated at ENI. NACL: stateless, subnet-level, allow/deny rules, evaluated at subnet boundary. Layering: traffic hits NACL → SG → app. Stateful (SG): automatically allows return traffic. Stateless (NACL): requires explicit allow rules for both inbound and outbound.

**CL4** — Landing zone: pre-configured, secure multi-account foundation with networking, identity, logging, and guardrails. OUs: group accounts by function/environment (dev, prod, shared services). Guardrails: SCPs/policies enforcing compliance, budget caps, region restrictions. Shared networking: Transit Gateway/Azure Hub-and-Spoke for centralized peering, on-prem links, and traffic inspection. Centralized logging: aggregated audit/network logs in a dedicated security account. Single-account problems: massive blast radius, permission sprawl, billing opacity, compliance violations, deployment bottlenecks, and lack of isolation.

**CL5** — IaC: managing infrastructure via version-controlled code. Terraform/OpenTofu: declarative HCL, state-based, vast provider ecosystem; best for multi-cloud, mature teams. Pulumi: imperative/declarative via general-purpose languages; best for complex logic, dynamic infra, existing dev teams. CloudFormation/Bicep: AWS-native declarative; best for AWS-only, tight CI/CD integration. Crossplane: Kubernetes-native IaC (XRs/providers); best for GitOps/K8s-centric teams unifying cloud resources as CRDs.

**CL6** — HPA: scales pod count based on CPU/memory/custom metrics. VPA: adjusts pod resource requests/limits (doesn't scale replicas). Cluster Autoscaler: adds/removes nodes based on pending pods/resource pressure. KEDA: event-driven scaling based on external triggers (queues, Kafka, HTTP). Use KEDA over HPA for event-driven workloads (queue consumers, batch jobs) where CPU/memory doesn't correlate with load. HPA is better for steady-state, request-driven services.

**CL7** — RPO/RTO: define by business impact. Active-active: both regions serve traffic, lowest RPO/RTO, highest cost/complexity. Active-passive: one serves, one standby, higher RPO/RTO, lower cost. DB replication: sync (strong consistency, latency-bound, active-active) vs async (eventual consistency, lower latency, active-passive). DNS failover: Route53/Traffic Manager health checks, failover routing, low TTL. State management: externalize to managed Redis/S3/DB; avoid local disk. Cost: active-active doubles infra + data transfer; active-passive saves compute but needs standby capacity. DR models: pilot light (minimal core running, scale up on failover), warm standby (scaled-down prod ready to scale), multi-site active-active (full prod in both).

**CL8** — GitOps: Git is single source of truth; controllers continuously reconcile cluster state with manifests. ArgoCD: UI-first, push/pull, app-of-apps, enterprise-friendly. Flux: Git-native, Kustomize/Helm, CLI-first, tight GitHub/GitLab integration. Secrets: SealedSecrets (encrypt in Git, decrypt in cluster), External Secrets Operator (sync from AWS SM/Vault), Vault (dynamic secrets, auth). Drift: controllers detect drift, auto-revert to Git state, or flag for review. Manual changes are overwritten on next sync unless explicitly excluded.

**CL9** — StatefulSet: stable network ID, ordered deployment/termination, stable storage. PV/PVC + local storage: `local` storageClass with `volumeBindingMode: WaitForFirstConsumer` ensures node locality and low latency. Headless service: `clusterIP: None` enables direct pod DNS resolution. Init containers: pre-load config, migrate data, or set permissions before main app. ConfigMaps as volume mounts: mount at specific paths, use `subPath` if needed. PDB: `minAvailable`/`maxUnavailable` ensures quorum during drains. Note: local storage lacks live migration; implement regular backups.

**CL10** — K8s Service Account: native identity, no cloud permissions by default. Workload Identity (GCP/Azure): maps K8s SA to cloud IAM without keys. IRSA (AWS): maps K8s SA to IAM Role via OIDC; pod assumes role via STS. Mounting credentials is bad practice: leaks, rotation issues, violates least privilege, hard to audit. Federation solves this via OIDC token exchange, short-lived credentials, automatic rotation, and scoped permissions per workload.

**CL11** — Object (S3/Blob): unstructured, HTTP API, 11 9s durability, eventual consistency, low cost. Use for backups, media, data lakes. Block (EBS/Managed Disk): low-latency, single-VM attached, snapshots. Use for OS, databases, high-IOPS apps. File (EFS/Azure Files): NFS/SMB, shared across VMs, POSIX/SMB compliant. Use for shared configs, home dirs, legacy apps. Durability/Availability: Object = 99.999999999% durability, 99.99% avail. Block = 99.999% durability, AZ-bound. File = multi-AZ, similar durability, higher latency.

**CL12** — Zero-trust K8s: default-deny Network Policies, service mesh (Istio/Linkerd) for mTLS and east-west identity, pod identity (IRSA/Workload Identity) for cloud access, admission controllers (OPA/Kyverno) to enforce policies (no privileged pods, signed images), image signing (Cosign/Notary) with admission rejection, runtime security (Falco) for syscall anomaly detection, secrets via External Secrets/Vault. Differs from perimeter model: assumes breach, verifies every request, micro-segments traffic, identity-centric, rather than trusting internal network traffic.

**CL13** — CDN: distributed edge cache network. Works by caching static content at PoPs, routing users to nearest PoP, origin-pulling on cache miss. Services: CloudFront, Azure CDN, Fastly, Cloudflare. Use CDN for static/media to reduce latency, offload origin, and absorb DDoS. Serve directly from origin only for dynamic, authenticated, or highly personalized content.

**CL14** — Region: geographic area with multiple AZs. AZ: one or more discrete data centers with independent power/cooling/network, low-latency interconnects. Deploy across multiple AZs to survive single data center failure and enable high availability. Zonal resources: tied to one AZ (EBS, NAT GW). Regional resources: span multiple AZs (ALB, Route53, S3).

**CL15** — Managed DB (RDS/Cloud SQL/Azure SQL): cloud provider handles provisioning, patching, backups, replication, failover, monitoring, and storage scaling. You manage schema, queries, IAM/network access, parameter groups, and capacity planning. Trade-off: less low-level control, higher cost, but massive operational savings.

**CL16** — IAM Users: human/service identities. Groups: collections of users. Roles: temporary credentials assumable by users/services. Policies: JSON rules granting/denying actions. Least privilege: grant only necessary permissions. Apply via scoped policies, avoid `*:*`, use IAM Access Analyzer, enforce MFA, conduct regular access reviews, and implement just-in-time access.

**CL17** — Serverless: event-driven, managed compute, pay-per-use, auto-scaling. Lambda (AWS), Functions (Azure), GCF (GCP) share core models but differ in ecosystem/tooling. Cold starts: first invocation after idle period requires container init; matters for latency-sensitive apps. Mitigate with provisioned concurrency, small functions, and keep-alive pings. Poor fit: long-running processes, stateful apps, predictable high throughput (reserved VMs cheaper), strict compliance/network constraints.

**CL18** — Ingress Resource: standard K8s CRD, relies on controller (NGINX/ALB), TLS termination at controller. Gateway API: newer, separates routing (Gateway) from rules (HTTPRoute), explicit TLS/cert management, better RBAC. Cloud LB Annotations: directly provision cloud LB (ALB/NLB), TLS at LB. Service Mesh Ingress: Istio/Linkerd gateway, mTLS termination, advanced traffic splitting. Use Gateway API over Ingress for multi-team environments, explicit TLS management, better extensibility, and fine-grained RBAC for routing.

**CL19** — RI/SP: commit 1-3yr for predictable workloads (30-70% savings); SP more flexible. Spot/Preemptible: 60-90% discount for fault-tolerant/batch workloads with fallbacks. Right-sizing: monitor utilization, downsize overprovisioned, use HPA/KEDA. Storage tiering: lifecycle policies, S3 Intelligent-Tiering, Glacier for archives. Idle detection: unattached volumes, idle LBs, unused IPs, zombie resources. FinOps: cross-functional team, tag strategy, showback/chargeback, monthly reviews, budget alerts. Tools: Cost Explorer, Kubecost/OpenCost, CloudHealth. Process: tag → allocate → optimize → govern.

**CL20** — Abstraction: Terraform, Crossplane, K8s for runtime. Networking: Cloud VPN, Direct Connect/ExpressRoute, global LB, consistent DNS. Identity: OIDC federation, centralized IdP, cross-cloud trust. Trade-offs: higher complexity, data egress costs, inconsistent features, operational overhead. Justified: regulatory/data residency, vendor failure risk, specific service needs, M&A. Unnecessary: most startups/SMBs, tightly coupled cloud-native features, limited ops bandwidth. Often "multi-cloud" is just "cloud-agnostic where needed."

**OT1** — Purdue Model (ISA-95): hierarchical control architecture. Level 0: physical process (sensors, actuators). Level 1: direct control (PLCs, RTUs, relays). Level 2: control systems (SCADA, HMIs, historians). Level 3: operations/MES (production scheduling, batch management). Level 4: enterprise (ERP, finance, supply chain). Level 5: corporate/IT (business strategy, external networks).

**OT2** — IT networks prioritize confidentiality/integrity, frequent patching, user-driven, TCP/IP dominant. OT networks prioritize availability/safety, real-time deterministic control, legacy protocols, maintenance-window patching. Standard IT patching fails in OT: systems run 24/7, unpatched firmware/OS is often safety-certified, reboot/patch can cause process shutdown, safety hazards, or production loss.

**OT3** — IDMZ: secure buffer between IT (L4) and OT (L0-L2). Traffic: strictly controlled, typically one-way or pull-based (IT pulls data from OT via OPC UA/MQTT). OT never initiates to IT. Direct L4→L1 connectivity is dangerous: enables lateral movement, ransomware propagation, unauthorized control commands, network congestion, and compliance violations.

**OT4** — Modbus TCP: L1/L2, PLC communication, request/response, unencrypted. OPC UA: L2/L3, secure, platform-independent, information modeling, pub/sub or client/server. EtherNet/IP (CIP): L1/L2, industrial Ethernet, CIP messaging, Rockwell-dominant. PROFINET: L1/L2, real-time Ethernet, IO/IRT, Siemens-dominant. MQTT: L2/L3/L4, lightweight pub/sub, IoT/cloud edge, QoS levels.

**OT5** — Data diode: hardware-enforced unidirectional flow (fiber optic with LED/photodiode). Physically prevents return traffic. Firewall: software/hardware, inspects/controls bidirectional traffic, can be misconfigured or bypassed. Use diode for high-security OT data export or regulatory air-gap alternatives. Limitation: no bidirectional communication, no response traffic, requires application-level ACKs or separate return channel.

**OT6** — Data flow: PLCs → OPC UA Server (historian/SCADA) → Edge Gateway (protocol translation, buffering, security) → MQTT Broker (on-prem/DMZ) → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: OT network (L0-L2) isolated. Edge gateway in DMZ or secure OT zone. TLS/mTLS for all comms. MQTT auth. Cloud IAM for ingestion. Network segmentation between OT and DMZ.

**OT7** — IEC 62443 Zones: logical groups of assets with similar security requirements. Conduits: secured communication paths between zones (firewalls/data diodes, inspected traffic). Model: Zone 1: SIS (highest integrity, isolated). Zone 2: PLCs/RTUs (control). Zone 3: SCADA/Historian/HMIs. Zone 4: Engineering Workstations. Zone 5: Corporate/IT. Conduits: Z3-Z4 (firewall, jump host), Z4-Z5 (firewall, DMZ), Z2-Z3 (firewall, strict ACLs), Z1 isolated.

**OT8** — VLANs: segment by function/process (Lines 1-4, Engineering, IT, DMZ, SIS). Firewalls: core IT/OT firewall, edge firewalls per VLAN, micro-segmentation if supported. Switches: managed L3, port security, 802.1X (if viable), disable unused ports. Remote access: jump host in DMZ, MFA, session recording, time-bound vendor accounts, no direct OT access. Transition: phased rollout, parallel run, maintenance windows, backup configs, rollback plan, test in staging, coordinate with ops.

**OT9** — SIS: independent safety system that brings process to safe state on hazardous conditions. BPCS: normal process control. IEC 61511: functional safety standard for SIS, defines SIL ratings. SIS must be air-gapped/isolated to prevent cyber attacks from compromising safety functions; SIS requires deterministic, independent operation. Ransomware on SIS could disable interlocks, causing catastrophic failure, environmental damage, or loss of life.

**OT10** — PLC: discrete control, fast, rugged, used for machine/line control. DCS: centralized control architecture, integrated I/O, used for continuous/process industries (chemical, oil). SCADA: supervisory system, HMI, data acquisition, remote monitoring, aggregates PLCs/RTUs. Coexist: yes. DCS often uses PLCs/RTUs as field controllers. SCADA supervises both.

**OT11** — Remote access: jump hosts in DMZ, MFA required, session recording for audit, time-limited/scoped vendor access, no direct OT access. RDP directly to HMI from corporate is unacceptable: exposes OT directly to corporate network, bypasses segmentation, high lateral movement risk, HMIs often run legacy/unsupported OS.

**OT12** — Detection: passive IDS (Zeek/Suricata), anomaly detection on OT protocols, asset inventory baseline, network flow monitoring. Inventory: real-time passive discovery, tag critical assets. IR steps: contain (isolate segment, don't kill process), verify impact, eradicate, recover, post-incident. Coordination: notify control room, switch to manual/local control if needed, prioritize safety over data. Safe operations: maintain manual override, monitor physical parameters, avoid remote commands until safe. Operator role: monitor physical process, execute manual safety procedures, communicate status, do not rely on compromised digital systems.

**OT13** — HMI: interface for operators to monitor/control process (graphs, alarms, controls). Role: human-machine interaction, situational awareness, command input. Differs from engineering workstation: HMI = operations (run-time). EWS = configuration, programming, diagnostics, firmware updates (maintenance/engineering).

**OT14** — Historian: time-series database for process data (temperatures, pressures, flows). Importance: trend analysis, compliance, optimization, troubleshooting. Plant historian (L3): high-frequency, real-time, process-specific, short retention. Enterprise historian (L4): aggregated, lower frequency, business/financial metrics, long retention, integrated with ERP.

**OT15** — Ladder logic: graphical programming language mimicking relay logic circuits. Executed by PLC. Dominant because: familiar to electricians, deterministic, easy to troubleshoot, massive legacy codebase, safety-certified, low learning curve for field technicians.

**OT16** — RTU: remote, rugged, designed for long-distance telemetry, serial/SCADA comms, solar/wind/water applications. PLC: localized, modular, fast I/O, factory automation. Deploy RTUs in geographically dispersed assets, harsh environments, low bandwidth comms, and SCADA telemetry scenarios.

**OT17** — Analog: continuous signals (4-20mA, 0-10V). Digital: discrete signals (on/off, pulses). 4-20mA preferred over 0-20mA because 4mA "live zero" indicates wire break/failure at 0mA. Better noise immunity, loop-powered, and fault detection.

**OT18** — OT asset inventory: complete list of hardware, firmware, network configs, dependencies. Foundation of security: enables patching, segmentation, risk assessment, and baseline behavior. Tools: passive monitoring (packet capture, protocol analyzers), limited active scanning. Active scanning dangerous: broadcasts/high traffic can crash legacy devices, trigger safety interlocks, or disrupt real-time control.

**OT19** — MITRE ATT&CK for ICS: tactics/techniques specific to ICS/OT. Tactics & examples: Reconnaissance (T1592), Resource Development (T1583), Initial Access (T1195), Execution (T1059), Persistence (T1177), Impact (T1496). Differs from enterprise: focuses on physical process impact, safety, legacy protocols, deterministic timing. Use to map current defenses, identify gaps (e.g., no PLC change monitoring), prioritize controls, and simulate OT-specific attacks.

**OT20** — Log collection: passive taps, OPC UA/MQTT log forwarders, SIEM agents on non-critical assets, avoid active polling. SIEM integration: normalize OT logs (Syslog, CEF), correlate with IT logs, use OT-specific parsers. Detection rules: baseline normal process behavior, alert on unauthorized PLC writes, protocol anomalies, after-hours access, firmware changes. Triage: OT engineers validate process impact, IT analysts handle data/identity. Escalation matrix. Staffing: IT analysts (threat intel, malware), OT engineers (process safety, protocol expertise). False positives: OT has predictable cycles/maintenance windows; tune rules, use allowlists, correlate with schedules. Unauthorized firmware change on PLC: isolate segment, verify physical safety, revert to known good image, investigate source, update change management, enhance admission controls.
