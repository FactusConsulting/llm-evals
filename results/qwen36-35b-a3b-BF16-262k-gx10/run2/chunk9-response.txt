SC1-A
The pods fail because the namespace policy was upgraded from Baseline to Restricted Pod Security Standard (PSS). Baseline allows containers to run as root and doesn't enforce strict security contexts. Restricted PSS requires `runAsNonRoot: true` AND either an explicit `runAsUser` set to a non-zero UID, or a container image that explicitly defines a non-root `USER`. The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`. When the policy enforcement switched, the container runtime refuses to start the container as root, causing immediate startup failure and CrashLoopBackOff. Kubernetes doesn't automatically adjust `securityContext` to match image defaults; it strictly enforces the declared policy.

SC1-C
- **Image fix:** Add `USER 1000` (or appropriate non-root UID) to the Dockerfile, or switch to a pre-built non-root base image.
- **Manifest fix:** Explicitly set `securityContext.runAsUser: 1000` and `runAsNonRoot: true` in deployments.
- **CI gate:** Integrate `kube-score` or `conftest` with OPA/Kyverno PSS policies to fail builds that violate Restricted standards. Add a Trivy/Grype scan that flags root-defaulting images.
- **Rollout:** Update the image tag in manifests and run `kubectl rollout restart deployment/<name> -n <ns>`. Use `maxSurge=1` and `maxUnavailable=0` to ensure zero downtime. Monitor rollout status before proceeding to next namespace.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. The primary ships WAL segments to the replica without waiting for acknowledgment. When the primary fails, any transactions committed but not yet shipped are permanently lost. The data loss window equals the time between the last committed transaction on the primary and the last WAL shipped to the replica. To quantify: on the primary, run `SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), pg_last_wal_replay_lsn()) AS lag_bytes;` and check `pg_stat_replication` for `write_lsn`, `flush_lsn`, and `replay_lsn`. The difference between `pg_current_wal_lsn()` and `pg_last_committed_xact()` on the replica indicates the exact loss window.

       blocking_locks.pid AS blocking_pid,

SC6-C
- **AWS Direct Connect:** High cost, dedicated 10Gbps+, low latency, BGP routing. Fits ZT (private, no internet exposure). Requires on-prem router config and BGP peering.
- **Dual VPN + ECMP:** Lower cost, IPsec encryption, dynamic routing (BGP/OSPF). Fits ZT but adds latency/jitter. Requires ECMP routing config and health checks.

SC10-A
- **Active-passive (Velero):** RPO = backup interval (15m), RTO = restore time (hours). Fails RTO <1h for 200TB MinIO. Not recommended.
- **Active-active (Istio/Cilium):** RPO ~0 (sync replication), RTO <1m (DNS failover). 12ms latency supports synchronous replication. Recommended.
- **Replication strategy:**
  - PostgreSQL: Patroni with synchronous replication (`synchronous_standby_names = 'standby1'`). RPO=0, RTO <30s.
  - Redis: Sentinel with `min-slaves-to-write 1`, async replication. RPO <1s.
  - RabbitMQ: Quorum queues with federation/shovel. RPO <1s.
  - MinIO: Site replication (async, eventual consistency). RPO ~minutes, RTO <1h with cache warming.
- **Feasibility:** Active-active meets RPO/RTO. MinIO site replication is the bottleneck; use tiered storage or async replication with read-through cache.
