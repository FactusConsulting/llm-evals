AA1 — Monoliths are single, unified codebases deployed as one unit with shared memory/processes. Microservices are independently deployable, loosely coupled services communicating over a network. Microservices introduce: (1) network latency & partial failure handling, (2) distributed tracing/debugging complexity, (3) data consistency challenges across service boundaries.

AA2 — Synchronous communication blocks the caller until a response is received (request-response model). Example: REST/gRPC. Asynchronous communication allows the caller to continue processing while the message is handled later (fire-and-forget or pub/sub). Example: RabbitMQ, Kafka, AWS SQS.

AA3 — A reverse proxy routes traffic, terminates TLS, and provides basic load balancing/caching at the network/transport layer. An API gateway adds business-layer features: rate limiting, auth, request transformation, developer portals, and API versioning. An API gateway cannot fully replace a reverse proxy; reverse proxies are faster, simpler, and better suited for static content, DDoS mitigation, and internal service routing.

AA4 — The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a later step fails. Choreography uses events to trigger the next step (decoupled, hard to trace, best for simple/stable workflows). Orchestration uses a central coordinator sending commands (easier to monitor/modify, creates a control dependency, best for complex/dynamic workflows).

AA5 — CQRS separates read (query) and write (command) models. Event Sourcing stores state as an immutable sequence of events. They pair naturally because commands emit events that update the read model. This combination solves auditability, temporal queries, independent read/write scaling, and avoids ORM mapping bottlenecks that traditional CRUD faces under complex domain logic.

AA6 — The Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (fail fast), Half-Open (probe recovery). Unlike retry+backoff (which attempts immediate recovery), the circuit breaker halts traffic to prevent overload. Use both: retry+backoff for transient glitches, circuit breaker for sustained failures to protect system stability.

AA7 — 
1. Shared DB, shared schema: Lowest cost, highest noisy-neighbor risk, requires row-level security, simplest ops.
2. Shared DB, separate schema: Moderate cost, better isolation, moderate noisy-neighbor risk, moderate ops complexity.
3. Separate DB per tenant: Highest cost, maximum isolation/security, zero noisy-neighbor, highest ops complexity (backup/migration scales linearly with tenants).

AA8 — Eventual consistency allows temporary stale reads; strong consistency guarantees immediate visibility. For inventory oversell prevention: use strong consistency. Architecture: single authoritative inventory service, PostgreSQL with row-level locking/optimistic concurrency (version columns), or a partitioned queue with exactly-once semantics + idempotent processing. At scale, partition by product ID, use distributed locks only for hot items, and async-reserve stock for non-critical paths.

AA9 — A sidecar proxy is a co-located container intercepting all network I/O for the main app. In Istio, Envoy handles L7 routing, load balancing, observability, and mTLS. Data plane = Envoy proxies forwarding traffic. Control plane = Istiod pushing configs/certs/routes. mTLS solves: transparent service-to-service auth, automatic cert rotation, and encryption without modifying application code (app-level TLS requires manual implementation and key management).

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is decommissioned. Strategy: Deploy .NET 8 microservices alongside the monolith. Place an API gateway/reverse proxy in front. Route specific endpoints/URLs to new services. Start with low-risk, independent modules (e.g., notifications, reporting). Use dual-write or CDC for data migration. Gradually decommission monolith routes as functionality shifts.

AA11 — 12-Factor App methodology for cloud-native apps. Six factors: (1) Codebase (one repo, many deploys), (2) Dependencies (explicitly declared/locked), (3) Config (env vars, never in code), (4) Backing services (treat as attached resources), (5) Build/release/run (strictly separate stages), (6) Processes (stateless, share-nothing). They matter because they enable portability, secure config management, horizontal scaling, and reliable CI/CD without state leakage.

AA12 — 
- Coupling: Event = loose, Request = tight.
- Scalability: Event = highly scalable async, Request = sync limits but simpler scaling.
- Debugging: Event = complex cross-service tracing, Request = straightforward.
- Ordering: Event = partition/key-based guarantees, Request = per-request only.
- Failure: Event = retry/Dead Letter Queue + idempotency, Request = immediate error/timeout.
Choose Event for decoupled systems, audit trails, high throughput, async processing. Choose Request for real-time responses, simple CRUD, or when tight coupling is acceptable.

AA13 — A load balancer distributes incoming traffic across multiple servers. Layer 4 balances by IP/port (fast, no content inspection). Layer 7 balances by HTTP headers, URLs, cookies (slower, content-aware). Layer 7 is required for SNI-based SSL termination, URL-based routing, or header-based canary deployments.

AA14 — A message queue (RabbitMQ) routes messages to consumers and removes them after consumption, supporting complex routing/exchanges. A log-based broker (Kafka) appends messages to an immutable log, retains them, and allows multiple consumers to replay. Pick RabbitMQ for task queues, complex routing, lower volume. Pick Kafka for event streaming, audit logs, high throughput, and replayability.

AA15 — Containers share the host OS kernel, are lightweight, and start instantly. VMs run a full guest OS under a hypervisor, consuming more resources. Containers are popular for microservices because they provide consistent environments, efficient resource usage, fast deployment, and native orchestration support (Kubernetes).

AA16 — Stateless services store no local session data; each request is independent. Stateful services maintain local state/session. Stateless services scale horizontally easily because instances are interchangeable and require no data migration or session stickiness. Examples: Stateless = Web API, Nginx. Stateful = PostgreSQL, Redis, Kafka.

AA17 — An ORM maps objects to database tables. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORM accelerates development and abstracts SQL but can generate inefficient queries and struggles with complex joins/analytics. Raw SQL offers full performance control and optimization but requires more boilerplate, is DB-specific, and harder to maintain.

AA18 — The Bulkhead pattern isolates resources so one failing component doesn't exhaust shared resources (threads, connections, memory). In microservices, it prevents cascading failures. Implementation: Use separate thread pools/connection pools per downstream service, or deploy critical vs non-critical services on separate node pools/Kubernetes namespaces with resource quotas and network policies.

AA19 — OT requires a central server to transform concurrent operations; strong consistency, low online latency, complex server logic, poor offline support. CRDTs are data structures that converge automatically without coordination; eventual consistency, higher latency/size, simpler client logic, excellent offline support. Choose CRDTs for offline editing: native conflict resolution, no central coordination needed, and seamless reconnection sync.

AA20 — Challenges: polyglot instrumentation, async flows, high volume, performance overhead. Context propagation: W3C Trace Context (industry standard) or B3; inject/extract trace IDs across HTTP/gRPC. Sampling: head-based (random, cheap, loses rare traces), tail-based (sample after processing, accurate, high overhead). Storage: Jaeger (OTel-native, rich UI), Tempo (S3-backed, cost-effective, metadata-only indexing). Async/Kafka: propagate trace context in message headers using OpenTelemetry propagators or Kafka interceptors. Consumers read headers and continue the trace. Tail-based sampling can aggregate spans across async boundaries for accurate cost/performance analysis.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and low overhead. Examples: VMware ESXi, Proxmox VE, KVM, Hyper-V. Type 2 (hosted) hypervisors run as applications on a host OS, offering ease of use but higher overhead. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block storage, presenting raw disks to servers for high performance/low latency. Protocols: Fibre Channel, iSCSI. NAS provides file storage over a network, easier sharing. Protocols: NFS, SMB/CIFS. Use SAN for databases/VMs requiring block access. Use NAS for file shares, backups, and home directories.

OP3 — 3-tier architecture (core/distribution/access) is hierarchical, prone to east-west bottlenecks, and asymmetric routing. Leaf-spine is flat: every leaf connects to every spine. It provides predictable low latency, non-blocking bandwidth, and linear scalability. It solves the oversubscription and scaling limits of 3-tier in modern data centers.

OP4 — Use 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing (STONITH via iDRAC/IPMI) powers off failed nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. On node failure: HA manager detects failure, fences the node, and restarts VMs on remaining nodes using shared storage.

OP5 — VLAN trunking carries multiple VLANs over a single physical link. 802.1Q adds a 4-byte VLAN tag to Ethernet frames. Linux config: `modprobe 8021q`, `ip link add link eth0 name eth0.10 type vlan id 10`, assign IPs, configure switch port as trunk (802.1Q).

OP6 — RAID 1: mirror, 50% cap, 1 drive fault. RAID 5: striping+parity, N-1 cap, 1 fault, write penalty. RAID 6: double parity, N-2 cap, 2 faults, higher write penalty. RAID 10: mirror+stripe, 50% cap, survives multiple faults, high perf. Z2 (ZFS): double parity, self-healing, flexible. Choice: RAID 10 for a database server due to superior write performance and predictable fault tolerance. Z2 is a strong modern alternative if capacity/flexibility outweighs raw write speed.

OP7 — Recursive resolvers (Windows DNS) serve clients. Authoritative servers host internal AD zones and external public zones. Forwarders handle external queries. Conditional forwarding routes specific zones to designated servers. Split-horizon returns private IPs internally and public IPs externally. DNSSEC signs the external zone; DS record at registrar. Laptop mobility: DHCP provides internal DNS; VPN client pushes internal DNS servers. Split-horizon ensures correct resolution regardless of location. AD replication keeps internal DNS consistent.

OP8 — PKI chain: Root CA (offline, anchors trust) -> Subordinate/Issuing CA (online, issues certs) -> End-entity cert. Deployment: Air-gap root, use subordinate for issuance, CRL/OCSP for revocation, AD CS templates for auto-enrollment. Compromised subordinate: Revoke cert, update CRL/OCSP, issue new subordinate. Minimal impact. Compromised root: Trust broken globally, requires full PKI rebuild and device/browser trust store updates. Catastrophic.

OP9 — MPLS: high cost, high reliability, low latency, complex management, private/security. IPsec VPN: low cost, variable reliability/latency, simple, internet-based security. SD-WAN: medium cost, high reliability (dynamic path selection), low latency (optimization), centralized management, secure. WireGuard mesh: low cost, high reliability, low latency, simple config, modern crypto, lacks enterprise management. Recommendation: SD-WAN. Best balance for 50 users/site, VoIP sensitivity, centralized management, and cost-effective reliability.

OP10 — iDRAC (Dell), iLO (HPE), IPMI: out-of-band management interfaces for remote hardware control (power, console, diagnostics). Critical for recovery from OS crashes, remote installs, and hardware troubleshooting without physical access. Internet exposure risks: brute force, credential theft, ransomware, unauthorized power cycling, and hardware manipulation. Should be isolated on a dedicated management network.

OP11 — LVM: traditional, fixed-size volumes, COW snapshots consume space quickly. LVM-Thin: overprovisions storage, cheap/fast snapshots, but can exhaust pool space. ZFS: integrated FS+volume manager, COW, space-efficient snapshots, self-healing, compression. Use LVM for legacy/simple setups, LVM-Thin for flexible provisioning, ZFS for data integrity and modern Linux. Snapshot semantics: LVM/LVM-Thin require pre-allocation or thin provisioning; ZFS provides instant, recursive, space-efficient snapshots.

OP12 — Design: 3 sites, 2 nodes each (6 total) or 3 nodes across 2 sites with a quorum device. CRUSH rules distribute replicas across failure domains (sites). Monitors: odd number spread across sites, or use a quorum device (external server) for tiebreaking. Latency: <5ms ideal, <10ms acceptable for Ceph. Split-brain: both sites claim primary, causing corruption. Quorum prevents this. 2-site Ceph without a tiebreaker is bad because even node counts cause split-brain on network partitions; a quorum device or odd node count is required.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If unavailable, clients use APIPA (169.254.x.x) or rely on cached leases. Windows attempts renewal at 50% (T1) and 87.5% (T2). If failed, reverts to APIPA or loses connectivity until lease renewal or static config.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP, ACLs, and link aggregation. These features are critical for traffic segmentation, security, performance optimization, redundancy, and troubleshooting in enterprise environments.

OP15 — NTP synchronizes clocks over a network. Critical for log correlation, authentication (Kerberos, certificates), distributed transactions, cluster coordination, and forensics. Clock drift causes Kerberos auth failures, split-brain in clusters, data corruption in distributed DBs, log misalignment, and certificate validation errors.

OP16 — Physical servers: direct hardware access, max performance. VMs: full isolation, guest OS, moderate overhead. Containers: shared kernel, lightweight, fast. Bare metal is preferred for HPC, low-latency trading, databases requiring direct disk access, GPU/NIC passthrough, or compliance requirements mandating no virtualization layer.

OP17 — UPS: short-term battery backup, handles outages/transients, allows graceful shutdown or generator start. Generator: long-term fuel-powered backup for extended outages. Both are needed because UPS bridges the 10-30 second gap until generators start. ATS (Automatic Transfer Switch): automatically switches load from utility to generator during failure, and back when utility is restored.

OP18 — Active-passive: one node handles traffic, standby takes over on failure. Active-active: both handle traffic, require complex sync and split-brain prevention. PostgreSQL HA with Pacemaker/Corosync: cluster manages resources. STONITH fencing (IPMI) isolates failed nodes. Virtual IP floats to the active node. PostgreSQL runs as a managed resource with streaming replication. On failure, Pacemaker fences the node, promotes the standby, and moves the VIP.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO define acceptable data loss and downtime. Backup types: full (baseline), incremental (changes since last), differential (changes since last full). Deduplication reduces storage and backup windows. Media: disk (fast restore), tape (cheap long-term), cloud (offsite/scalable). Immutable backups (WORM) protect against ransomware. Test restores regularly to verify integrity and measure RTO/RPO. Backup = data protection. DR = full recovery process (infrastructure, data, procedures, failover).

OP20 — 802.1X: port-based NAC. Roles: Supplicant (client), Authenticator (switch/AP), Auth Server (RADIUS). EAP-TLS: mutual certificate auth, most secure, requires PKI. PEAP: username/password with server cert, easier deployment. RADIUS handles auth/authorization/accounting. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: port stays unauthorized, no traffic. MAB: switch uses device MAC as credentials to RADIUS. Fallback for non-802.1X devices (printers, IoT). Less secure, no user context.
