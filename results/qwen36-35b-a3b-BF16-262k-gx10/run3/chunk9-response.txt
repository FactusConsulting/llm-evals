SC1-A
The pods fail because the namespace Pod Security Standard (PSS) was upgraded from `Baseline` to `Restricted`. `Restricted` enforces `runAsNonRoot: true` and explicitly forbids `runAsUser: 0`. The container images set `USER root` (UID 0) in their Dockerfiles. When `runAsNonRoot: true` is set without an explicit `runAsUser`, Kubernetes assigns a random non-zero UID at runtime, but the container's `USER` directive overrides it back to UID 0. The `Restricted` PSS admission controller rejects the pod spec or the kubelet refuses to start the container because it violates the non-root requirement, resulting in `CrashLoopBackOff`.

SC1-C
**Immediate fix:** Update the Dockerfiles to create a non-root user (e.g., `RUN adduser -D appuser` and `USER appuser`). Update manifests to explicitly set `securityContext.runAsUser: 1000` and `runAsGroup: 1000`.
**Prevention:** Add a CI gate using `cosign verify` or `trivy` to reject images running as root. Deploy a Kyverno/OPA admission controller policy that enforces `runAsNonRoot: true` and `runAsUser != 0` across all namespaces.
**Rollout:** Use a rolling update (`strategy: rollingUpdate: maxSurge: 25% maxUnavailable: 0`) with readiness probes. The new image/manifest combo deploys incrementally; old pods terminate only after new ones pass readiness, ensuring zero downtime.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous by default. WAL segments are shipped and replayed with network-dependent lag. Promoting the replica severs replication, permanently losing any WAL not yet shipped or replayed. The data loss window equals the replication lag at promotion time. To quantify: check `pg_stat_replication` for `write_lag`, `flush_lag`, and `replay_lag`, or compare `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()`. Stale data occurs because the replica was promoted before catching up, and application caches/queries hit the new primary before WAL replay completes for recent transactions.

SC2-B
1. Import the promoted replica into Terraform state: `terraform import aws_db_instance.new_primary <replica-arn>`
2. Remove the old instance from state (do not destroy): `terraform state rm aws_db_instance.old_primary`
3. Update HCL: Change the resource name to `aws_db_instance.new_primary`, update the `identifier` and `endpoint` attributes, and update all dependent resources (SGs, Route53, parameter groups) to reference the new ARN/endpoint.
4. Verify no destroy/recreate: `terraform plan -target=aws_db_instance.new_primary`
5. Apply: `terraform apply`

SC2-C
**Connection Management:** Use RDS Proxy instead of PgBouncer. RDS Proxy handles connection pooling, IAM auth, and transparently routes traffic to the new primary after failover without app restarts.
**Routing & Resilience:** Route53 failover routing with health checks pointing to RDS Proxy endpoints. Implement application-level retry logic with exponential backoff and jitter.
**RPO < 1s:** Standard RDS async replication cannot guarantee <1s RPO across regions due to network variance. **Recommend Aurora Global Database:** It uses a dedicated global cluster with async replication optimized for cross-region, typically achieving <1s RPO and sub-minute failover. It also handles endpoint updates automatically.

SC6-C
**Direct Connect:** Dedicated 10G/100G link, BGP routing, low latency, high cost ($/port + data). Fits ZT when combined with IPsec overlay or hardware encryption. Requires BGP peering config.
**Second VPN + ECMP:** Cheap, scales bandwidth linearly, but IPsec CPU overhead and ECMP routing complexity. Fits ZT natively (IPsec encrypts all traffic). Requires multiple tunnels and route table updates.
**Tailscale/Netbird:** WireGuard mesh, zero-config, end-to-end encryption, scales effortlessly. Fits ZT perfectly (identity-based, no IP trust). Depends on relay nodes for NAT traversal. Routing handled automatically via MagicDNS/routing ACLs.
**Recommendation:** Direct Connect for core backbone + Tailscale/Netbird for east-west/mesh connectivity to balance cost, performance, and zero-trust identity enforcement.

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks (Patroni, Redis Sentinel, RabbitMQ, MinIO) monitor site heartbeat. Site down = 3 consecutive failures + etcd quorum loss.
2. **DNS Failover:** GSLB (Route53/Azure Traffic Manager) switches VIP to Dallas.
3. **State Promotion:** Patroni promotes Dallas standby. Redis Sentinel promotes master. RabbitMQ federation catches up. MinIO site replication syncs delta.
4. **State Update:** OpenTofu state updated via CI/CD to reflect new primary endpoints.
**Split-Brain:** Patroni etcd DCS uses quorum fencing. Only the partition with majority nodes promotes. Network partition triggers automatic demotion of minority.
**Failback:** Reverse replication (Dallas → Chicago). Sync MinIO. Verify data consistency. Switch DNS back. Update OpenTofu state. Decommission Dallas as primary.
