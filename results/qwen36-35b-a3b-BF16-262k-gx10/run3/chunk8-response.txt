**CL1** — IaaS provides virtualized compute, storage, and networking; you manage OS, middleware, runtime, data, and apps. Example: AWS EC2. PaaS provides runtime, middleware, and OS managed by the provider; you manage apps and data. Example: Google App Engine. SaaS provides fully managed applications; you only consume and configure user settings. Example: AWS WorkSpaces or Salesforce.

**CL2** — The Shared Responsibility Model divides security: provider secures the cloud infrastructure (hardware, global network, managed service control planes); you secure what you put in it. IaaS VM: Provider = hypervisor, physical host, network. You = OS, patches, firewall, data, IAM. Managed K8s: Provider = control plane, node OS, API server. You = worker config, pod security, network policies, app code, secrets. SaaS (M365): Provider = app, infra, patching, compliance config. You = user accounts, data classification, access policies, MFA, DLP.

**CL3** — VPC: Isolated virtual network. Subnet: IP range within a VPC, tied to an AZ. Security Group (SG): Instance-level, stateful, allow-only rules, evaluated at the ENI. NACL: Subnet-level, stateless, allow/deny rules, evaluated at the subnet boundary. Layering: Traffic hits NACL first, then routes to the instance, then hits the SG. Stateful (SG) automatically allows return traffic matching established connections. Stateless (NACL) requires explicit rules for both inbound and outbound traffic.

**CL4** — Landing zone: Pre-configured, secure multi-account foundation with networking, identity, logging, and guardrails. OUs: Group accounts by environment (dev/test/prod) or function (security, networking, workloads). Guardrails: SCPs/policies enforcing compliance (region restrictions, encryption mandates, root account lockdown). Shared Networking: Transit Gateway/Azure Hub-and-Spoke for centralized inter-VPC/VNet routing, peering, and on-prem connectivity. Centralized Logging: Aggregated to a dedicated security account for audit, threat detection, and compliance. Single-account problems: Massive blast radius, permission sprawl, billing opacity, compliance violations, environment isolation failure, and resource contention.

**CL5** — Terraform/OpenTofu: Declarative HCL, multi-cloud, state-based, vast provider ecosystem. Best for general multi-cloud and mature teams. Pulumi: Imperative/Declarative using general-purpose languages (TS, Python, Go). Best for teams needing code flexibility and complex logic. CloudFormation/Bicep: AWS-native, declarative, tightly integrated, Bicep improves syntax. Best for AWS-only, rapid CI/CD deployment. Crossplane: Kubernetes-native, manages cloud resources via CRDs. Best for GitOps/K8s-centric teams wanting a unified control plane. Choice depends on cloud scope, team language proficiency, GitOps maturity, and ecosystem needs.

**CL6** — HPA: Scales pod count based on CPU/memory/custom metrics. Reactive, standard for stateless apps. VPA: Recommends/sets resource requests/limits per pod; doesn't scale replicas. Used for right-sizing. Cluster Autoscaler: Adds/removes nodes based on unschedulable pods. Works with HPA. KEDA: Event-driven scaling based on external triggers (Kafka, queues, HTTP, cron). Use KEDA over HPA when scaling must be driven by event backlog/throughput rather than static resource metrics, especially for async workloads or microservices with bursty event patterns.

**CL7** — RPO/RTO dictate strategy: Active-active offers RPO≈0, RTO≈0; active-passive offers RPO=sync/async, RTO=mins-hours. Active-active splits traffic across regions with bidirectional data sync; high cost, complex conflict resolution. Active-passive keeps a standby region; lower cost, simpler. DB replication: Sync ensures strong consistency but adds latency; async reduces latency but risks data loss. DNS failover (Route53/Traffic Manager) uses health checks and TTL to route traffic; lower TTL speeds failover but increases DNS load. State must be externalized (Redis, object storage, distributed DBs). DR models: Pilot light (core infra running, scale up on failover), warm standby (full scaled-down env ready), multi-site active-active (all regions live). Cost: Active-active doubles infra + data transfer; pilot light/warm standby are cheaper but increase RTO.

**CL8** — GitOps uses Git as the single source of truth. Declarative state is pushed to the cluster; operators continuously reconcile actual vs desired state. ArgoCD: UI-first, push/pull, strong visual diffing. FluxCD: Git-native, pull-only, tightly integrated with GitHub/GitLab, CLI/automation focused. Secrets: Sealed Secrets (encrypted in Git, decrypted by controller), External Secrets Operator (syncs from cloud secret managers/Vault), Vault (dynamic secrets, auth). Drift handling: Controllers detect manual changes and auto-revert to Git state on next sync. Requires strict access controls to prevent bypass.

**CL9** — StatefulSet provides stable pod identity, ordered deployment/termination, and stable DNS. PV/PVC with `local` storageClass + `volumeBindingMode: WaitForFirstConsumer` binds storage to the node where the pod schedules, ensuring low latency. Headless service (`clusterIP: None`) enables DNS discovery for StatefulSet pods. Init containers prepare filesystems, migrate legacy configs, or wait for dependencies before the app starts. ConfigMaps mounted as volumes place config files at specific paths; use `subPath` if needed. Pod Disruption Budgets (`minAvailable`/`maxUnavailable`) ensure minimum replicas during voluntary disruptions. Note: Local storage pins pods to nodes; use node affinity/tolerations and implement explicit backup strategies.

**CL10** — K8s Service Account: Native pod identity, not cloud-recognized by default. Workload Identity (GCP/Azure): Maps K8s SA to cloud IAM identity without long-lived credentials. IRSA (AWS): Maps K8s SA to AWS IAM Role via OIDC provider; pod assumes role dynamically. Mounting cloud credentials in pods is bad practice: long-lived, hard to rotate, violates least privilege, and risks credential leakage in logs/volumes. Workload identity federation solves this by issuing short-lived, dynamically scoped tokens, enabling auditability, automatic rotation, and strict least-privilege access.

**CL11** — Object storage (S3/Blob): Scalable, HTTP API, flat namespace, metadata-rich. Durability: 99.999999999%. Availability: 99.99%. Use for unstructured data, backups, static sites, data lakes. Block storage (EBS/Managed Disk): Low-latency, fixed-size, mounted as a drive. Durability: 99.999% (multi-AZ). Availability: Tied to AZ. Use for OS disks, databases, high-IOPS apps. File storage (EFS/Azure Files): NFS/SMB, hierarchical, shared access. Durability: 99.999999999%. Availability: 99.99%. Use for shared configs, home dirs, legacy POSIX/SMB apps. Trade-offs: Block = performance, Object = scale/cost, File = shared access/compatibility.

**CL12** — Zero-trust K8s architecture: Default-deny Network Policies restrict pod-to-pod/namespace traffic. Service mesh (Istio/Linkerd) enforces mTLS, identity-based routing, and observability. Pod identity (IRSA/Workload Identity) replaces static creds. Admission controllers (OPA/Kyverno) enforce policies (no privileged pods, required labels, resource limits). Image signing (Cosign/Notary) + admission controllers reject unsigned/untrusted images. Runtime security (Falco) monitors syscalls for anomalies. Secrets managed via External Secrets Operator/Vault, never in env vars or plain ConfigMaps. Differs from perimeter security by eliminating implicit trust, verifying every request, assuming breach, and enforcing least privilege at the workload level rather than network boundary.

**CL13** — CDN (Content Delivery Network): Distributed edge cache network serving content from locations closest to users. Works by caching origin content at edge nodes; subsequent requests are served from cache until TTL expires. Services: CloudFront (AWS), Azure CDN, Fastly, Cloudflare. Use CDN for static/dynamic content delivery, DDoS mitigation, SSL termination, and global latency reduction. Serve directly from origin only for low-traffic, highly dynamic, or compliance-restricted data where edge caching adds unnecessary complexity or cost.

**CL14** — Region: Geographic area containing multiple AZs. AZ: One or more discrete data centers with independent power/cooling/networking, connected via low-latency links. Deploy across multiple AZs to protect against single data center failure and ensure high availability. Zonal resources (EBS, subnets, some LBs) are tied to one AZ. Regional resources (S3, Route53, ALB, IAM) span multiple AZs/regions and provide higher availability.

**CL15** — Managed database services (RDS, Cloud SQL, Azure SQL) abstract infrastructure management. Provider handles: provisioning, OS/db engine patching, backups, replication, monitoring, automated failover, and storage scaling. You handle: schema design, queries, IAM, network config, connection pooling, and application-level optimization. Benefits: Reduced ops overhead, built-in HA, faster recovery, and compliance certifications.

**CL16** — IAM Users: Human/service identities. Groups: Collections of users. Roles: Temporary credentials for entities (users, services, external). Policies: JSON documents defining permissions. Principle of least privilege: Grant only necessary permissions. Apply via scoped policies, avoid `*:*`, use conditions (IP, MFA, time), enforce via SCPs/OUs, conduct regular access reviews, and implement just-in-time access.

**CL17** — Serverless: Managed compute where provider handles scaling, patching, and infra. Pay per execution. Compare: Lambda (AWS), Functions (Azure), GCF (GCP). Similar event-driven model, differing language support, limits, and cold start behavior. Cold starts: Initialization time for runtime/container on first request. Matter for latency-sensitive apps. Mitigate with provisioned concurrency, keep-warm, or lighter runtimes. Poor fit: Long-running processes, stateful apps, predictable high-throughput (reserved VMs cheaper), strict compliance/network isolation needs, or vendor lock-in concerns.

**CL18** — Ingress Resource: Standard K8s CRD requiring a controller (nginx, ALB). TLS termination at controller. Gateway API: Newer, standardized, separates routing (Gateway) from backend (HTTPRoute). Better RBAC, multi-tenant, explicit TLS config. Cloud LB Annotations: Directly provision cloud LB (ALB/NLB). TLS termination at cloud LB. Simpler but less portable. Service Mesh Ingress: Istio/Linkerd gateway. mTLS, advanced traffic splitting, observability. TLS termination at mesh gateway. Use Gateway API over Ingress for multi-tenant environments, explicit RBAC, standardized TLS/HTTP routing, and future-proofing.

**CL19** — RI/SP: Commit 1-3yr for predictable workloads (RI for specific instance, SP for flexible compute). Spot/Preemptible: Up to 90% savings for fault-tolerant/batch/dev workloads. Right-sizing: Use cost explorer to identify underutilized resources; downsize or consolidate. Storage tiering: S3 Intelligent-Tiering, lifecycle policies to Glacier/Archive, delete orphaned snapshots/EBS. Idle detection: Tagging, unused LBs, unattached EBS, idle RDS, schedule non-prod shutdowns. FinOps: Cross-functional culture (Eng, Fin, Ops), regular reviews, unit economics, showback/chargeback by team/project. Tools/Processes: CloudHealth, Kubecost, AWS/Azure Cost Management. Implement tagging strategy, budget alerts, automated rightsizing scripts, and monthly cost review meetings.

**CL20** — Multi-cloud strategy: Abstraction via Kubernetes, Terraform, service mesh, and standard APIs. K8s as runtime (EKS/AKS/GKE) with GitOps/Helm for portability. Terraform for provider-agnostic IaC, modules for abstraction, per-cloud state. Networking: Cloud VPN, Direct Connect/ExpressRoute, global LBs, DNS routing. Identity: OIDC federation, centralized IdP, cross-cloud IAM mapping. Trade-offs: Complexity, data egress costs, inconsistent features, operational overhead, fragmented support. Justified for: Regulatory/data residency, catastrophic vendor outage risk, strategic negotiation leverage, or specific service superiority. Unnecessary for: Most startups/SMBs, tightly coupled cloud-native workloads, or teams lacking multi-cloud ops capacity. Single-cloud with strong exit strategy is often preferable.

**OT1** — Purdue Model (ISA-95): Hierarchical framework for enterprise-control system integration. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, DCS controllers). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations/MES (production scheduling, batch management). Level 4: Business/Enterprise (ERP, finance, supply chain). Level 5: Strategic/Corporate (executive planning, external partners).

**OT2** — IT networks prioritize confidentiality, integrity, availability (CIA), fast patching, and user-centric updates. OT networks prioritize availability, safety, integrity (AIS), real-time deterministic operation, and long lifecycles with physical consequences for failure. Standard IT patching fails in OT because systems often can't tolerate downtime, lack patch management tools, run unsupported OS, and patches can break process logic. OT requires change windows, validation, and compensating controls.

**OT3** — IDMZ: Segmented network between IT and OT acting as a controlled buffer. Traffic: Strictly filtered, often one-way or bidirectional with heavy inspection. IT→IDMZ: Data requests, validated commands. IDMZ→OT: Filtered, authenticated process commands. OT→IDMZ: Process data, status. Allowed: OPC UA, MQTT, SQL, file transfers. Direct L4→L1 connectivity is dangerous because it bypasses security controls, exposes real-time control systems to IT threats, enables lateral movement, and risks physical safety/process disruption.

**OT4** — Modbus TCP: Legacy, unencrypted, request/response. Operates L1-L2 (PLC to HMI/SCADA). OPC UA: Modern, secure, platform-independent, information modeling. Operates L2-L3 (SCADA to MES/Cloud). EtherNet/IP (CIP): Industrial Ethernet, real-time, CIP messaging. Operates L1-L2 (PLC to drives/HMI). PROFINET: Real-time Ethernet, deterministic, I/O communication. Operates L1 (PLC to I/O modules). MQTT: Lightweight publish/subscribe, IoT/cloud friendly. Operates L2-L4 (Edge to cloud/analytics).

**OT5** — Data diode: Hardware-enforced unidirectional communication allowing data flow in only one direction. Firewall: Bidirectional, inspects traffic, allows/denies based on rules. Use a data diode when strict data exfiltration prevention is required (e.g., OT reporting to IT, secure log forwarding). Limitation: Cannot allow any return traffic (no ACKs, no commands, no bidirectional protocols). Firewalls allow controlled bidirectional flow but can be misconfigured or bypassed.

**OT6** — Data flow: PLCs/RTUs → OPC UA Server (historian/edge) → Edge Gateway (protocol translation, buffering, security) → MQTT Broker (secure, TLS) → Cloud Ingestion (IoT Core/Kafka) → Analytics/DB. Security boundaries: 1) OT Network (L1-L2): Firewall to IDMZ. 2) IDMZ: OPC UA server, edge gateway, MQTT broker with mTLS and strict segmentation. 3) Cloud Boundary: WAF, API gateway, IAM, VPC peering/VPN. 4) Data: Encryption at rest/transit, strict RBAC. Edge buffering handles connectivity loss; maintain minimal IT→OT command paths.

**OT7** — Zone: Logical grouping of assets with similar security requirements, risk profile, and access needs, defined by function, data sensitivity, and blast radius. Conduit: Secured communication path between zones requiring firewalls, data diodes, strict ACLs, and monitoring. Zone-and-Conduit Model: Zone 1: SIS (highest integrity, air-gapped/isolated). Zone 2: BPCS/PLCs/RTUs (L1). Zone 3: SCADA/Historians/HMIs (L2). Zone 4: Engineering Workstations (L3). Zone 5: Corporate/IT (L4). Conduits: Z2→Z3 (firewall, OPC UA), Z3→Z4 (firewall, secure file transfer), Z4→Z5 (firewall, IDMZ). Z1 isolated. All conduits monitored, authenticated, encrypted.

**OT8** — VLAN Design: Segment by function/process (e.g., VLAN 10: Line 1 PLCs, 20: Line 2 PLCs, 30: HMIs, 40: SCADA, 50: Engineering). Use 802.1Q. Firewall Placement: Core firewall between IT/OT, edge firewalls between VLANs, DMZ for vendor access. Stateful, protocol-aware filtering. Switch Architecture: Managed L3 switches, port security, 802.1X (if supported), disable unused ports, trunk only to firewalls/core. Remote Access: Jump host in IDMZ, MFA, session recording, time-limited vendor accounts, no direct OT access. Transition: Phased rollout, parallel run, maintenance windows, backup configs, rollback plan, validate process continuity, monitor for latency/loss.

**OT9** — SIS: Independent system designed to bring process to a safe state on hazardous conditions. BPCS: Normal process control system. IEC 61511: Safety lifecycle standard defining SIL requirements for process industry SIS. SIS must be air-gapped or strictly isolated from BPCS/IT to prevent common-cause failures; IT/BPCS compromise could disable safety functions. Ransomware reaching SIS could disable interlocks, causing catastrophic failure, environmental release, or loss of life. SIS requires validation, testing, and physical/logical isolation.

**OT10** — PLC: Discrete control, fast, rugged, used for machine/line control (L1). DCS: Integrated control system for continuous processes, centralized architecture, built-in redundancy (L1-L2). SCADA: Supervisory system for monitoring/control over wide areas, collects data from PLCs/RTUs, provides HMIs (L2). Coexist: Yes. PLCs handle local control, DCS manages integrated process, SCADA provides oversight, data logging, and operator interface. Common in refineries, water plants, and large manufacturing.

**OT11** — Remote access architecture: Jump hosts isolated in IDMZ, no direct OT access. MFA required for all remote sessions. Session recording for audit/forensics. Vendor access: Time-limited, role-based, ticket-approved, break-glass procedures. RDP directly to HMI from corporate is unacceptable because it exposes OT directly to the corporate network, bypasses segmentation, increases attack surface, violates least privilege, and lacks session control. Architecture: Corporate → VPN → Jump Host (MFA, recording) → Firewall → OT Network (strict ACLs, protocol filtering).

**OT12** — Detection: Network monitoring (IDS/IPS, NetFlow, passive packet capture), asset inventory (CMDB, passive discovery), anomaly detection (baseline behavior, alert on unusual PLC commands, unexpected outbound traffic). IR Steps: Contain (isolate segment, block C2), Assess (scope, identify entry), Eradicate (patch, remove malware, reset creds), Recover (restore clean backups, validate), Lessons Learned. Coordination: Notify control room, shift to manual/local control if needed, ensure safety systems remain operational, communicate with regulators if required. Safe Operations: Prioritize SIS/BPCS integrity, maintain manual overrides, monitor process parameters, avoid automated changes. Plant Operator Role: Monitor physical process, execute manual controls, report anomalies, follow cyber incident playbook, do not disconnect safety systems unless directed.

**OT13** — HMI (Human-Machine Interface): Graphical interface for operators to monitor and control industrial processes. Role: Real-time visualization, alarm management, manual overrides, trend analysis. Differs from Engineering Workstation: HMI is for operators (runtime, read/write control). Engineering workstation is for programmers/configurers (offline/online programming, logic editing, parameter tuning, firmware updates).

**OT14** — Historian: Time-series database optimized for high-volume, continuous process data collection, compression, and retrieval. Importance: Process optimization, compliance, troubleshooting, predictive maintenance, performance analysis. Plant Historian (L3): Real-time/near-real-time, process-focused, high frequency, local storage, supports SCADA/PLC data. Enterprise Historian (L4): Aggregated, lower frequency, business-focused, integrates with ERP/MES, longer retention, supports reporting/analytics.

**OT15** — Ladder Logic: Graphical programming language mimicking relay wiring diagrams. Executed by PLCs, which scan inputs, execute logic, and update outputs cyclically. Dominance: Familiar to electricians, easy to troubleshoot, deterministic, widely supported, low barrier to entry, legacy integration, and safety-certified environments.

**OT16** — RTU (Remote Terminal Unit): Designed for harsh environments, long-distance communication (cellular, satellite, microwave), modular I/O, often used in SCADA. PLC: Localized control, faster scan times, integrated I/O, used for machine/line automation. RTU deployment: Pipelines, water distribution, wind farms, oil/gas remote sites, wide-area monitoring where connectivity is limited and environmental conditions are extreme.

**OT17** — Analog signals: Continuous voltage/current (4-20mA, 0-10V) representing variable process values (temp, pressure). Digital signals: Discrete on/off or binary communication (Modbus, Ethernet). 4-20mA preferred over 0-20mA because 4mA "live zero" indicates an active signal vs wire break/failure (0mA = fault). Improves diagnostics, noise immunity, and supports loop-powered devices.

**OT18** — OT asset inventory: Comprehensive list of hardware, firmware, software, network configs, and communication paths. Foundation for risk assessment, patching, segmentation, and compliance. Tools: Passive monitoring (packet capture, protocol analyzers), active scanning (SNMP, Modbus scanners, Nmap). Active scanning is dangerous because it can crash legacy devices, cause process disruption, trigger alarms, or be detected as an attack. Passive is safer but may miss unresponsive devices.

**OT19** — MITRE ATT&CK for ICS: Maps adversary tactics/techniques specific to ICS/OT environments. Differs from enterprise ATT&CK by focusing on physical processes, safety, legacy protocols, and industrial equipment. Tactics & Examples: 1) Reconnaissance: Gather network topology (T1580). 2) Resource Development: Acquire industrial control software (T1588). 3) Initial Access: Phishing for credentials (T1566). 4) Execution: Run malicious code on engineering workstation (T1059). 5) Impact: Manipulate process control (T1499). Assessment: Map current defenses to techniques, identify gaps (e.g., no protocol filtering, unpatched EWS), prioritize mitigations, simulate attacks, validate detection rules.

**OT20** — Converged IT/OT SOC: Log collection via passive network taps, OPC UA/MQTT log forwarding, SIEM agents on non-critical assets, edge aggregators to avoid impacting real-time operations. SIEM integration: Normalize OT logs (Syslog, CEF, OT-specific schemas), correlate with IT logs, use OT-aware parsers. Detection rules: Baseline normal behavior, alert on unexpected PLC writes, unauthorized engineering access, protocol anomalies, data exfiltration. Triage: OT-specific playbooks, involve OT engineers early, distinguish process transients from cyber events, prioritize safety impact. Staffing: IT analysts for general alerts, OT engineers for process/protocol validation, dedicated OT SOC analyst, clear escalation. False positives: High due to process variations; mitigate with tuning, baseline learning, OT context enrichment, feedback loops. Unauthorized firmware change: Immediate isolation of EWS/PLC, verify change request, check digital signatures, rollback if unauthorized, forensic analysis, update change management, enhance admission controls.
