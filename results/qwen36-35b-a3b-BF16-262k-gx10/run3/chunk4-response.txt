G1 — A slice is a dynamic, reference-like view over an underlying array (header: pointer, length, capacity). An array is a fixed-size value type with compile-time known length. When you `append` to a slice that has reached capacity, Go allocates a new backing array (typically doubling capacity), copies existing elements, and returns a new slice pointing to it.

G2 — `var x int` declares a variable with explicit type and zero value; `x := 0` is a short variable declaration that infers type. You cannot use `:=` outside functions, when redeclaring an existing variable without introducing at least one new variable, or when type inference is ambiguous.

G3 — A goroutine is a lightweight, multiplexed execution context managed by the Go runtime (~2KB initial stack vs OS thread's MBs). The GMP model: G=goroutine, M=OS thread worker, P=processor context (run queue, GC state). The scheduler multiplexes Gs onto Ms, handles blocking syscalls (parking M), and uses work-stealing for load balancing.

G4 — Channels are typed pipes for communication and synchronization. Unbuffered channels block both sender and receiver until both are ready. Buffered channels have a capacity; send blocks only when full, recv blocks only when empty. Sending to a full buffered channel blocks until space opens or the channel is closed/cancelled.

G5 — `context` propagates deadlines, cancellation signals, and request-scoped values across API boundaries.
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
resp, err := http.Get(ctx, "https://example.com")
```

G6 — Go uses implicit interface satisfaction: any type implementing the methods automatically satisfies the interface (duck typing). Unlike Java/C#, no `implements` keyword or inheritance hierarchy is needed. `interface{}`/`any` accepts any type. Powerful for abstraction and generics; dangerous because type assertions can panic, and compile-time type safety is lost.

G7 — The code has a data race: `ready` and `data` are written in one goroutine and read in another without synchronization. The busy loop `for !ready {}` is not guaranteed to see `data` due to CPU caching and compiler reordering. Fix with a channel or `sync.Once`:
```go
var data string
done := make(chan struct{})
go func() {
    data = "hello"
    close(done)
}()
<-done
fmt.Println(data)
```

G8 — `sync.Mutex` provides exclusive access; `sync.RWMutex` allows concurrent readers or a single writer. `sync.Map` is optimized for compile-time-known keys, mostly-read workloads, or disjoint key sets. Trade-offs: `sync.Map` has higher overhead for frequent writes/overlapping keys; a `map` + `sync.Mutex` is faster for dense writes/updates.

G9 — Modules manage dependencies. `go.mod` declares direct dependencies, versions, and replace directives. `go.sum` stores cryptographic hashes of direct/transitive deps for integrity. `go mod tidy` removes unused deps, adds missing ones, and updates `go.sum`. MVS (Minimum Version Selection) picks the lowest version of each module that satisfies all direct and transitive constraints, ensuring deterministic builds.

G10 — `defer` schedules a function call to run after the surrounding function returns. Multiple defers execute in LIFO order. Gotcha in loops: variables captured by deferred closures are evaluated at defer time, not loop iteration time. Fix by passing as arguments: `defer func(v T) { ... }(v)` or create a new scope per iteration.

G11 — A pointer stores the memory address of a value. Zero value: `nil`. Pointer to a struct literal: `&MyStruct{Field: val}`.

G12 — `init()` runs automatically after package-level variables are initialized, before `main()`. A package can have multiple `init()` functions; they execute in declaration order within a file. Across files, execution order is undefined but deterministic per file.

G13 — `make(T, args)` initializes slice/map/channel and returns the initialized value (not a pointer). `new(T)` allocates zeroed memory and returns `*T`. `make` only works with built-in reference types; `new` works with any type.

G14 — Go uses explicit error handling via the `error` interface (`Error() string`). Idiomatic: `if err != nil { ... }`. `errors.Is(err, target)` checks if `err` wraps `target` (uses `Unwrap`). `errors.As(err, &target)` extracts a wrapped error to a specific type. `==` only matches exact errors, not wrapped chains.

G15 — Composite types and zero values: `map` (nil=empty, read-only), `slice` (nil=empty, zero-length), `channel` (nil=blocks forever), `struct` (zero values per field). All are safe to use at zero value except nil maps/channels.

G16 — A race condition occurs when concurrent goroutines access shared data without synchronization, with at least one write. `-race` instruments the runtime to detect conflicting accesses and prints stack traces. Fix with `sync.Mutex` around the critical section or a channel to serialize access.

G17 — `select` waits on multiple channel operations, picking one ready case at random. Unlike `switch` (evaluates expressions), `select` blocks until at least one case is ready. Multiple ready: random selection. Timeout: `case <-time.After(d):` or `case <-ctx.Done():`.

G18 — Escape analysis determines stack vs heap allocation. Values escape if: address taken, size unknown at compile time, returned, or stored in heap-allocated structures. Inspect with `go build -gcflags="-m"`. Matters because heap allocations trigger GC, impacting latency/throughput; stack is faster and zeroed automatically.

G19 — `reflect` inspects/modifies values at runtime. `reflect.Type` holds static type info; `reflect.Value` holds dynamic value. Costs: slow, bypasses compile-time checks, cannot modify unexported fields. Justified in frameworks/ORMs/JSON parsers. Prefer code generation (`go generate`, `stringer`) for performance-critical paths.

G20 — `go:embed` compiles static files/directories into the binary. Syntax: `//go:embed pattern`. Embeds into `fs.FS` (e.g., `embed.FS`), `[]byte`, or `string`. Limitations: only static files at compile time, limited glob patterns, no runtime generation. Interacts with `io/fs.FS` by implementing the interface, enabling standard filesystem APIs on embedded data.

R1 — Ownership ensures memory safety without GC. Rules: 1) Each value has exactly one owner. 2) Only one owner at a time. 3) Owner drops value when it goes out of scope.

R2 — `String` is heap-allocated, growable, and owned. `&str` is a borrowed, fixed-size reference to UTF-8 bytes. Use `String` when owning/modifying; use `&str` in function signatures to accept both `String` and `&str` efficiently.

R3 — Borrowing accesses data without transferring ownership. Rules: 1) Either one `&mut` or multiple `&` references. 2) References must be valid (no dangling). 3) No aliasing mutable references. The borrow checker enforces these at compile time.

R4 — `Result<T, E>` represents success/failure; `Option<T>` represents `Some(T)`/`None`. `?` unwraps `Ok`/`Some` or returns early on `Err`/`None`.
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```

R5 — `Box<T>`: heap allocation, single owner, moves data. `Rc<T>`: reference counting, single-threaded shared ownership. `Arc<T>`: atomic reference counting, thread-safe shared ownership. Use `Box` for large/recursive types, `Rc` for shared read-only single-threaded, `Arc` for shared across threads.

R6 — Traits define behavior. Like Go, they use duck typing, but Rust requires explicit implementation. `dyn Trait`: trait object, dynamic dispatch (vtable), heap-allocated, enables heterogeneous collections. `T: Trait`: generic with static dispatch (monomorphization), zero-cost, type-specific code.

R7 — Fails because the return type's lifetime isn't tied to inputs. Fix:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
The compiler infers `'a` as the shorter of the two input lifetimes.

R8 — `Send`: types safe to transfer ownership across threads. `Sync`: types safe to share references across threads. `Rc<T>` isn't `Send`/`Sync` because its ref count isn't atomic. `Arc<T>` uses `AtomicUsize` for the count, making it `Send`+`Sync` (requires `T: Send`).

R9 — `async/await` compiles to a state machine implementing the `Future` trait. `Future::poll()` advances execution. The executor (e.g., Tokio) drives futures, schedules tasks, and handles I/O. Differs from Go: Go's runtime handles M:N scheduling internally; Rust separates the `Future` trait from the executor, offering flexibility but requiring explicit executor setup.

R10 — `unsafe` bypasses certain compiler safety checks. Three things: dereference raw pointers, call `unsafe` functions, implement `unsafe` traits, access/modify `static mut`, or break reference aliasing rules. Justified when interfacing with C, building safe abstractions, or optimizing critical paths.

R11 — Pattern matching exhaustively evaluates values. `match` requires all variants or `_`; `if let` is shorthand for a single arm + optional `else`. The compiler enforces exhaustiveness in `match` (error if missing), but only warns on `if let` if not exhaustive.

R12 — `Vec<T>`: heap-allocated, growable. `[T; N]`: fixed-size, usually stack-allocated. When `Vec` exceeds capacity, it allocates a new buffer (typically 2x), moves/copies elements, drops the old buffer, and updates the pointer.

R13 — Rust enums are algebraic data types: named variants that can carry data. Unlike C/Java, they support exhaustive matching and payloads. `Option<T>` is `Some(T)` or `None`. Rust has no `null`; `Option` forces explicit handling, preventing null pointer exceptions.

R14 — `impl` blocks define methods. `&self`: borrows instance (immutable). `&mut self`: mutable borrow. `self`: takes ownership (consumes). Associated functions (e.g., `String::new()`) don't take `self` and act like static methods.

R15 — `#[derive(...)]` auto-implements common traits. Examples: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive if fields lack the trait, or if custom logic is required (e.g., complex equality, non-trivial cloning).

R16 — `Cow<'a, T>` (Clone-on-Write) holds either `&'a T` or `T`. Useful when a function might return borrowed or owned data. Example: `fn process(s: &str) -> Cow<str> { if s.is_ascii() { Cow::Borrowed(s) } else { Cow::Owned(s.to_uppercase()) } }` avoids allocation when input already matches desired output.

R17 — `mod` declares a module, `use` imports names, `pub` exposes. File system: `mod foo;` resolves to `foo.rs` or `foo/mod.rs`. Rust 2018 changed path resolution (`use crate::foo` vs `use foo`), removed `extern crate`, and allowed modules to be declared anywhere.

R18 — `Pin<T>` guarantees a value won't be moved in memory. Needed for self-referential structs and async/await (futures may hold references to their own fields). `Unpin` is a marker trait indicating a type is safe to move. `!Unpin` types require pinning to guarantee pointer stability.

R19 — Declarative macros (`macro_rules!`) use pattern matching for compile-time code generation. Procedural macros: `derive` (custom `#[derive]`), `attribute` (custom `#[foo]`), `function-like` (invoked like `foo!(...)`). Hygiene ensures macros don't capture/leak identifiers from caller scope; variables are scoped to the macro expansion.

R20 — Zero-cost abstractions: high-level features compile to efficient machine code. Iterators compile to tight loops with no intermediate collections. Generics use monomorphization to generate type-specific code at compile time. Trait static dispatch uses direct function calls, avoiding vtable overhead. Result: C-like performance with safety and ergonomics.
