T1 — `tofu plan` evaluates your configuration against the current state and cloud APIs to generate an execution plan showing what will be created, updated, or destroyed. It does not modify infrastructure. `tofu apply` executes that plan, making the actual API calls to provision/update resources.

T2 — State is a JSON file mapping real-world resources to your configuration. Remote state stores this file in a shared backend (S3, GCS, Terraform Cloud, etc.), enabling team collaboration, state locking, and secure access control. It prevents state loss and drift from local-only workflows.

T3 — `count` iterates over integers (0, 1, 2...), while `for_each` iterates over maps or sets using explicit keys. `for_each` is preferred when resources have unique identifiers (names, IDs) because removing an item from a list changes indices, causing unintended recreation. `for_each` preserves resources when items are added/removed.

T4 — OpenTofu detects this via drift detection during `tofu plan`. It compares the live state against the configuration. On `tofu apply`, it will revert the manual change to match the desired state. To ignore intentional drift, use `lifecycle { ignore_changes = [attribute] }`.

T5:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `terraform_remote_state` reads the entire state file, which is heavy and exposes sensitive data. Output values expose only specific computed values. The recommended alternative is using the `outputs` attribute in the data source (`data.terraform_remote_state.foo.outputs.my_output`) or, if in the same root module, passing outputs directly via module calls. This minimizes state coupling and improves security/performance.

T7 — Provisioners run asynchronously after resource creation. Outputs are evaluated during the apply phase, so the kubeconfig file may not exist yet, causing empty outputs. Fix: Use a `local_file` resource with a `remote-exec` provisioner to write the kubeconfig, then reference the file via `file()` data source. Alternatively, add `depends_on = [null_resource.kubeconfig]` to any resource that consumes the output.

T8 — `tofu import` CLI creates a state entry but requires manual HCL configuration. It doesn't handle dependencies well and can cause plan drift. The `import` block (1.5+) generates HCL config alongside state, supports `tofu plan` before apply, handles dependencies automatically, and reduces manual error. Limitations: Still requires manual attribute mapping for complex resources.

T9 — A `variable` block defines external input parameters passed into a module/root. An `output` block exposes computed values from a module/root to consumers. Variables are inputs; outputs are outputs.

T10 — A provider is a plugin that translates OpenTofu configuration into API calls for a specific platform (AWS, Azure, etc.). Running `tofu plan` without `tofu init` fails because providers aren't downloaded, initialized, or locked, leaving OpenTofu unable to communicate with the cloud API.

T11 — `.terraform.lock.hcl` records exact provider versions and cryptographic checksums. Commit it to ensure reproducible builds, prevent supply-chain attacks, and guarantee that all team members/CI use identical provider binaries.

T12 — `tofu destroy` removes all resources managed by the current state. Target a single resource: `tofu destroy -target=module.name.resource_type.resource_name`.

T13 — A data source reads existing infrastructure without managing it. Example: `data "aws_ami" "ubuntu"` to fetch the latest Ubuntu AMI ID dynamically instead of hardcoding it or managing it as a resource.

T14 — `locals` compute values internally within a configuration block. `variable` blocks accept external input. Use `locals` for computed values, string transformations, or avoiding repetition of complex expressions. Use `variable` for configurable inputs from users/CI.

T15 — `lifecycle` controls resource behavior:
- `create_before_destroy = true`: Creates new resource before destroying old (zero-downtime for load balancers/DBs).
- `prevent_destroy = true`: Blocks accidental deletion via plan/apply (safety net for critical infra).
- `ignore_changes = [attribute]`: Skips drift detection on specific fields (e.g., `user_data` modified by cloud-init).

T16 — The `moved` block remaps old resource addresses to new ones in state without destroying/recreating. Example: `moved { from = aws_instance.web[0] to = aws_instance.web["primary"] }`. It preserves resources during module restructuring or naming changes.

T17 — OpenTofu builds a Directed Acyclic Graph (DAG) of dependencies. Implicit dependencies are inferred from variable/resource references. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, breaking DAG parallelism. Use sparingly to avoid bottlenecks; prefer implicit references for optimal concurrency.

T18 — Strategies & tradeoffs:
1. Split into multiple modules/workspaces: Reduces graph size. Tradeoff: Increased management overhead & cross-module coupling.
2. Use `tofu plan -target` in CI: Skips unrelated resources. Tradeoff: Misses full-system drift detection.
3. Cache/async data sources & reduce remote state reads: Cuts API calls. Tradeoff: Potential stale data if not refreshed.
4. Optimize backend (remote state, compression, parallelism): Faster state reads/writes. Tradeoff: Backend complexity/cost.

T19 — State locking uses a backend mechanism (DynamoDB, Consul, etc.) to prevent concurrent writes. If a lock isn't released (crash), run `tofu force-unlock <LOCK_ID>`. Risks: Data corruption, lost changes, or state inconsistency if another process modifies state concurrently. Always verify state integrity after force-unlock.

T20 — Steps:
1. Create S3 bucket & DynamoDB table (enable locking).
2. Add backend config to `backend.tf`.
3. Run `tofu init -migrate-state`. OpenTofu uploads local state to S3, initializes DynamoDB lock.
4. Verify: `tofu state list` and `tofu plan` should show no changes. Delete local `terraform.tfstate` if desired.

A1 — A **playbook** is a YAML file defining automation workflows. A **role** is a reusable collection of tasks, files, templates, and variables. A **task** is a single module execution (e.g., install package, copy file).

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `{{ ansible_os_family }}`.

A3 — `command`: runs without shell features (safer, no pipes/vars). `shell`: runs with shell interpreter (supports pipes, `$VAR`). `raw`: runs without Python, ideal for bootstrapping or minimal systems. Use `command` for security, `shell` for complex commands, `raw` for initial setup.

A4 — Idempotency means running a task multiple times yields the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "hello" > /tmp/test.txt` (overwrites every run). Use `copy` or `template` for idempotent file management.

A5:
```yaml
- name: Install htop based on OS
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel and htop on RedHat
  package:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
```

A6 — Precedence (lowest to highest): role defaults → inventory vars → host_vars → group_vars → extra_vars → `set_fact` → role vars. Extra vars and `set_fact` override most others.

A7 — Use `serial: 3` in the playbook to process 3 nodes at a time. Group first 3 nodes in inventory (e.g., `[rke2_first]`). Use `wait_for` or `uri` module to check RKE2 readiness before proceeding to next batch. Example: `serial: ["3", "100%"]` processes first 3, then remaining in parallel.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'mysecret' --name 'my_var'`, then paste the output into a vars file. The file remains plaintext except for the encrypted value.

A9 — Inventory lists managed hosts/groups. **Static**: file-based (`hosts.ini`). **Dynamic**: script/API that generates inventory on-demand (e.g., AWS EC2, Azure RM). Dynamic scales better and auto-updates with cloud changes.

A10 — `ansible webservers -m shell -a "df -h"` or `ansible webservers -a "df -h"` (defaults to `command` module).

A11 — A **handler** is a task triggered by `notify`. It runs only if notified, at the end of the play. Differs from regular tasks (run unconditionally). Trigger: `notify: restart_service`.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`, `log_path`.

A13 — `register` saves task output to a variable. Example: `shell: uname -a` → `register: os_info`. Use in next task: `debug: var=os_info.stdout`.

A14 — `include_tasks` is dynamic (evaluated at runtime, supports `when`). `import_tasks` is static (evaluated at parse time, faster, no conditionals). Use `include` for conditional logic, `import` for performance/static inclusion.

A15 — Ansible Galaxy is the community hub for roles/collections. `requirements.yml` lists dependencies. Install: `ansible-galaxy install -r requirements.yml`. Supports `roles:` and `collections:` sections.

A16 — Connection plugins define how Ansible communicates. `ssh`: standard Linux/Unix hosts. `local`: runs on control node. `network_cli`: network devices (Cisco, Juniper) using CLI. Choose based on target OS/architecture.

A17 — `delegate_to` runs a task on a different host. `run_once` runs a task once across a group. Example: Gather facts from remote hosts, then write aggregated config to `localhost` once:
```yaml
- debug: msg="{{ ansible_hostname }}"
  delegate_to: "{{ item }}"
  run_once: true
  loop: "{{ groups['all'] }}"
```

A18 — Strategies & tradeoffs:
1. Increase `forks`: More parallel SSH connections. Tradeoff: Higher control node CPU/memory.
2. Enable `pipelining`: Reduces SSH overhead by chaining commands. Tradeoff: Requires SSH config changes, may conflict with sudo.
3. Fact caching (Redis/Memcached): Skips fact gathering on subsequent runs. Tradeoff: Adds infrastructure, stale facts if not refreshed.
4. Mitogen: Async execution engine. Tradeoff: Requires installation, compatibility checks, not officially supported by Ansible.

A19 — `{{ }}` outputs expressions/values. `{% %}` control flow (if/for). `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
    # Health check: {{ server }}
    server {{ server }};
{% endfor %}
}
```

A20 — Structure:
- `serial: 1` (or `20%`) for rolling.
- `pre_tasks`: Disable host in LB (`uri` module to set maintenance mode).
- `tasks`: Deploy app.
- `post_tasks`: Health check (`uri` module checking `/healthz`).
- `block/rescue`: On failure, rollback (re-enable LB, revert config, notify).
- Use `max_fail_percentage: 0` to halt on first failure. Ensure idempotent deployments and quick health checks to minimize downtime.
