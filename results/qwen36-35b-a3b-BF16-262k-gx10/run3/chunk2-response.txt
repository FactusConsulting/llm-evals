K1 — A **Deployment** manages stateless workloads with interchangeable pods, random names, and no guaranteed startup order. A **StatefulSet** manages stateful workloads with stable, unique network IDs, ordered deployment/scaling, and stable persistent storage per pod.

K2 — The Service Endpoint Controller populates an `Endpoints` object with pod IPs. `kube-proxy` watches Services and Endpoints, then programs `iptables` or `IPVS` rules on each node to DNAT traffic destined for the ClusterIP:Port to the backing pod IPs.

K3 — **PersistentVolume (PV)**: cluster-provisioned storage resource (static or dynamic). **PersistentVolumeClaim (PVC)**: user request for storage. **StorageClass**: template that dynamically provisions PVs. Relation: PVC binds to a PV (or triggers a StorageClass to create one); PVs are cluster-scoped, PVCs are namespace-scoped.

K4 — 1. `kubectl logs <pod> --previous` to check crash reason. 2. `kubectl describe pod` for ExitCode, OOMKilled, or event warnings. 3. Verify resource requests/limits vs node capacity. 4. Check app dependencies, config mounts, startup scripts, and health check endpoints.

K5 — CoreDNS provides internal DNS resolution for `svc.cluster.local` and pod FQDNs. If CoreDNS pods are down, internal service discovery fails, but direct pod IP communication and external DNS resolution remain unaffected.

K6 — **Filtering**: removes nodes failing constraints (insufficient resources, taints, node selectors, affinity/anti-affinity, topology spread). **Scoring**: ranks remaining nodes using priority functions. Factors: LeastRequested/BalancedResourceAllocation, NodeAffinity/TaintToleration, PodTopologySpread, InterPodAffinity, and resource pressure.

K7 — Yes, it will schedule (3.5GB + 256Mi ≈ 3.75GB < 4GB). At runtime, memory limits are hard caps. If the pod uses 600Mi, the kernel OOM killer terminates it (`OOMKilled`), and Kubernetes restarts it.

K8 — Client → External LB (routes to Ingress Controller IP) → Ingress Controller (NGINX) parses Ingress resource → matches host/path → forwards to Kubernetes Service → Service resolves to Endpoints (pod IPs) → `kube-proxy`/`iptables` DNATs traffic to pod → pod handles request.

K9 — A **NetworkPolicy** restricts pod-to-pod and pod-to-external traffic. Default: all traffic allowed. When applied: denies all ingress/egress for selected pods by default; only traffic matching explicit policy rules is permitted.

K10 — **RollingUpdate**: gradually replaces old pods with new ones (zero downtime). **Recreate**: terminates all old pods before starting new ones (downtime). Choose Recreate for stateful apps, database migrations, or when shared storage/state requires exclusive access.

K11 — A **namespace** provides virtual cluster isolation and resource scoping. Defaults: `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — `kubectl describe pod` shows detailed state, events, conditions, resource usage, volume mounts, environment variables, and container statuses. `kubectl get pod` only shows basic status, age, and restart count.

K13 — A **ConfigMap** stores non-confidential configuration data. Pod consumption methods: 1. As environment variables. 2. Mounted as files in a volume.

K14 — **ClusterIP**: internal cluster-only access. **NodePort**: exposes service on each node’s IP at a static port (30000–32767). **LoadBalancer**: provisions a cloud provider LB, routes to NodePort/ClusterIP.

K15 — A **DaemonSet** ensures one pod runs on every (or selected) node. Use for logging/monitoring agents, CNI plugins, or storage daemons. Deployments run a fixed replica count and are not node-bound.

K16 — **Taints** repel pods from nodes; **tolerations** allow pods to schedule on tainted nodes. **Node affinity** attracts pods to nodes based on labels. Taints/tolerations = node exclusion/inclusion. Affinity = node selection. Use case taints: `dedicated=gpu:NoSchedule` for GPU workloads. Use case affinity: `topology.kubernetes.io/zone=us-east-1a` for zone-aware scheduling.

K17 — An **Operator** is a custom controller that manages complex stateful applications using CRDs and custom reconciliation logic. Unlike standard controllers, it encodes operational knowledge (backup, upgrade, failover, scaling) into code, reducing manual intervention.

K18 — etcd uses **Raft consensus** with linearizable reads/writes. If quorum is lost, the cluster becomes read-only/unwritable. With 2/3 nodes permanently lost, quorum cannot be restored; recovery requires restoring from the latest etcd snapshot on remaining/new nodes or bootstrapping a new cluster and importing the backup.

K19 — **Role/ClusterRole** define permissions (verbs/resources). **RoleBinding/ClusterRoleBinding** bind roles to users/groups/serviceaccounts. Manifest:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Default `ndots:5` means queries with <5 dots are appended to search domains (`svc.cluster.local`, `cluster.local`, etc.), causing multiple DNS queries. Fix: set `dnsConfig: { options: [{ name: "ndots", value: "2" }] }` in the pod spec, or use FQDNs with a trailing dot.

D1 — **Rebase** rewrites commit history into a linear sequence; **merge** preserves history with a merge commit. Avoid rebasing on shared/public branches or when collaborating to prevent history conflicts.

D2 — **TCP**: connection-oriented, reliable, ordered, flow/congestion control. **UDP**: connectionless, unreliable, low-latency. TCP: HTTP, SSH. UDP: DNS, VoIP, video streaming.

D3 — A **race condition** occurs when concurrent threads/processes access shared state without synchronization, yielding unpredictable results. Example: two threads incrementing a shared counter without a mutex, causing lost updates.

D4 — **Symmetric**: same key for encryption/decryption (fast). **Asymmetric**: public/private key pair (secure key exchange). TLS uses asymmetric encryption for the handshake/key exchange, then switches to symmetric encryption for bulk data transfer.

D5 — Each Dockerfile instruction creates an **image layer**. Layer caching reuses unchanged layers. Best practice: order instructions from least to most frequently changing (e.g., copy dependency manifests first, install deps, then copy source code).

D6 — 1. Check upstream app logs/metrics for errors or timeouts. 2. Verify resource limits (CPU throttling, OOMKilled). 3. Inspect dependency health (DB, cache, external APIs). 4. Review LB/Ingress health checks and rate-limiting configs. Order: app → infra → dependencies → routing.

D7 — **CAP theorem**: a distributed system can guarantee at most two of Consistency, Availability, Partition tolerance. CP example: banking ledger, CockroachDB (prioritizes consistency over availability during partitions). AP example: DNS, Cassandra, DynamoDB (prioritize availability, allow eventual consistency).

D8 — **Horizontal scaling**: add more nodes/instances. **Vertical scaling**: increase CPU/RAM of existing node. Horizontal scaling requires: stateless design, shared-nothing architecture, distributed caching, message queues, consistent hashing, and externalized state.

D9 — An **environment variable** is a dynamic value passed to processes. Persist across sessions: add `export VAR=value` to `~/.bashrc` or `~/.profile`, then run `source ~/.bashrc`.

D10 — **JSON**: strict syntax, key-value pairs, arrays. **YAML**: indentation-based, human-readable, supports comments. JSON advantage: universal parsing, strict validation. YAML advantage: readability, less boilerplate, native comments.

D11 — A **REST API** is an architectural style using HTTP methods on resources. **GET**: retrieve. **POST**: create. **PUT**: replace/update. **DELETE**: remove.

D12 — **Version pinning** locks dependencies to exact versions (e.g., `package@1.2.3`). Critical for reproducible builds, predictable behavior, security auditing, and avoiding unexpected breaking changes.

D13 — **Compiled**: source → binary via compiler (C, Rust). **Interpreted**: source → executed line-by-line by runtime (Python, JavaScript). Note: many modern languages use JIT compilation (Java, Go).

D14 — **Reverse proxy**: sits in front of servers, routes client requests to backends (Nginx, HAProxy). Use case: load balancing, SSL termination, caching. **Forward proxy**: sits in front of clients, routes outbound requests. Use case: corporate content filtering, outbound caching.

D15 — A **deadlock** occurs when two+ processes wait indefinitely for each other’s resources. Coffman conditions: 1. Mutual exclusion, 2. Hold and wait, 3. No preemption, 4. Circular wait.

D16 — **Eventual consistency** guarantees all replicas converge if no new updates. Cassandra uses **tunable consistency levels** (ONE, QUORUM, LOCAL_QUORUM, ALL, SERIAL). For read-after-write: use `QUORUM` for both read/write, or enable causal consistency features to guarantee session consistency.

D17 — **mTLS** authenticates both client and server via X.509 certificates. Handshake: ClientHello → ServerHello+Cert → ServerKeyExchange → ClientKeyExchange+Cert → verify certs → derive session keys. Commonly used in: service meshes (Istio/Linkerd), internal microservices, zero-trust networks.

D18 — A **hash table** maps keys to values via a hash function → array index. **Collision resolution**: chaining (linked lists at index) or open addressing (linear/quadratic probing, double hashing). Avg complexity: O(1). Worst case (all collide): O(n).

D19 — A **circuit breaker** prevents cascade failures by failing fast when a downstream service is unhealthy. States: **Closed** (normal), **Open** (fail fast, trip after error threshold), **Half-open** (allow limited test requests). Relates to retries: circuit breakers should wrap retry logic to prevent retry storms during outages.

D20 — **Optimistic**: assumes no conflict, validates at commit (row versioning, `UPDATE ... WHERE version=old`). **Pessimistic**: locks resources during read/write (`SELECT ... FOR UPDATE`). Choose optimistic for high-read/low-write workloads; pessimistic for high-contention/write-heavy. Example: Optimistic uses `row_version` column; Pessimistic uses explicit row locks.
