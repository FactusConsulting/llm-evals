T1 — `tofu plan` evaluates the configuration against the current state and cloud APIs to generate an execution plan showing what will be created, updated, or destroyed without making changes. `tofu apply` executes that plan, making the actual infrastructure changes.

T2 — State is a JSON file mapping real-world resources to your configuration. Remote state stores this file in a shared backend (e.g., S3, GCS), enabling team collaboration, state locking, and secure access control, unlike local state which is prone to corruption and sharing issues.

T3 — `count` iterates over integers, while `for_each` iterates over maps or sets of strings. `for_each` is preferred when resources have unique identifiers (like names or IDs) because adding/removing items doesn't shift indices, preventing unintended recreation of unrelated resources.

T4 — OpenTofu detects this via drift detection during `tofu plan`. On `tofu apply`, it will revert the manual change to match the state/config. If drift is intentional, use `lifecycle { ignore_changes = [...] }` to prevent OpenTofu from overwriting it.

T5 —
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — `terraform_remote_state` reads the entire state file, which can be inefficient and expose sensitive data. Outputs read specific values. Recommended alternative: Use `data "terraform_remote_state"` with explicitly defined outputs. This enforces least-privilege access, improves performance, and makes dependencies explicit.

T7 — Provisioners run asynchronously after resource creation, but outputs are evaluated during the apply phase before the file is fully written. Fix: Use a `local_file` resource that depends on the `null_resource`, then output the file content. Alternatively, use `depends_on` in the output block (OpenTofu 1.5+).

T8 — `tofu import` adds an existing resource to state but requires manual config writing and doesn't handle dependencies well. The `import` block (1.5+) is declarative, supports multiple resources, integrates with `tofu plan`, and provides better error handling and dependency resolution.

T9 — A `variable` is an input passed into a module or run. An `output` is a value exposed from a module or run for other modules to consume. Variables configure behavior; outputs share results.

T10 — A provider defines how OpenTofu interacts with a cloud/API (e.g., AWS, Azure). Running `tofu plan` without `tofu init` fails because provider plugins aren't downloaded, and the backend/state directory isn't initialized.

T11 — `.terraform.lock.hcl` pins exact provider versions and checksums. Commit it to VCS to ensure reproducible builds, prevent supply-chain attacks, and avoid unexpected breaking changes from provider updates.

T12 — `tofu destroy` deletes all resources tracked in the current state. Target a single resource: `tofu destroy -target=resource_type.resource_name`.

T13 — A data source reads existing infrastructure or external data without managing it. Example: `data "aws_ami" "ubuntu"` to find the latest Ubuntu AMI instead of managing an AMI resource.

T14 — `locals` compute values within a module and aren't exposed externally. `variables` are inputs from outside. Use `locals` for computed values, string transformations, or avoiding repetition of complex expressions.

T15 — `lifecycle` controls resource behavior: `create_before_destroy` creates new before old (zero-downtime), `prevent_destroy` blocks accidental deletion, `ignore_changes` skips drift on specific attributes (e.g., auto-generated tags).

T16 — The `moved` block maps old resource addresses to new ones during refactoring. It updates the state mapping without destroying/recreating resources, preserving infrastructure while changing configuration structure.

T17 — Implicit dependencies are inferred from variable/resource references. Explicit dependencies use `depends_on`. `depends_on` forces sequential execution, reducing parallelism. Use sparingly to avoid bottlenecks; prefer implicit references.

T18 — 1. Split into multiple modules/workspaces (tradeoff: increased complexity). 2. Use `data` sources instead of managed resources where possible (tradeoff: may miss drift). 3. Run `tofu plan -target` for scoped changes (tradeoff: hides full impact). 4. Optimize providers (disable unnecessary metadata calls) (tradeoff: may hide configuration issues).

T19 — State locking prevents concurrent writes that corrupt state. If a CI crash leaves a lock, run `tofu force-unlock <lock-id>`. Risks: Data corruption or lost changes if another apply is actively running.

T20 — 1. Create S3 bucket & DynamoDB table. 2. Add `backend "s3"` config to `.tf` files. 3. Run `tofu init -migrate-state`. 4. Verify: `tofu state list` matches, check S3/DynamoDB. The local state file is uploaded to S3; local file can be safely deleted.

A1 — A playbook is a YAML file containing a list of plays. A role is a reusable directory structure of tasks, handlers, vars, and templates. A task is a single action (module call) within a play.

A2 — `ansible_facts` are auto-discovered system variables. Access OS family via `ansible_facts['os_family']` or the shorthand `ansible_os_family`.

A3 — `command` runs without a shell (safe, no pipes). `shell` runs via `/bin/sh` (supports pipes/redirects). `raw` runs via SSH without Python (for bootstrapping unmanaged hosts). Use `command` for safety, `shell` for complex commands, `raw` for initial setup.

A4 — Idempotency means running a task multiple times yields the same result. Idempotent: `apt: name=htop state=present`. Not idempotent: `shell: echo "data" > /tmp/file.txt` (overwrites every run). Fix with `copy` or `lineinfile`.

A5 —
```yaml
- name: Install htop
  package:
    name: htop
  when: ansible_os_family == "Debian" or ansible_os_family == "RedHat"
```

A6 — Precedence (highest to lowest): extra_vars > command line > host_vars > group_vars > role vars > role defaults > set_fact > inventory vars. `set_fact` overrides most but is lower than extra_vars/command line.

A7 — Use `serial: 3` in the playbook to batch execution. Group nodes in inventory (`[rke2_control]`, `[rke2_worker]`). Use `wait_for` or `pause` after the first 3 nodes to verify cluster readiness before proceeding to the rest.

A8 — `ansible-vault` encrypts sensitive data. Encrypt a single variable: `ansible-vault encrypt_string 'my_secret' --name 'db_password'`, then paste the output into a vars file.

A9 — Inventory lists managed hosts. Static inventory is a file with hardcoded hosts/groups. Dynamic inventory is a script/API that generates hosts/groups at runtime (e.g., from cloud APIs).

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A handler is a task triggered by `notify`. It runs only if notified, at the end of the play. Differs from regular tasks (run unconditionally). Trigger with `notify: handler_name`.

A12 — `ansible.cfg` sets global defaults. Common settings: `inventory`, `remote_user`, `forks`, `host_key_checking`, `vault_password_file`.

A13 — `register` saves a task's output to a variable. Use it later: `when: my_var.stdout == "success"` or `debug: msg="{{ my_var.stdout_lines }}"`.

A14 — `include_tasks` is dynamic (evaluated at runtime, supports `when`). `import_tasks` is static (evaluated at parse time, faster, no `when`). Use `include` for conditionals, `import` for performance/static inclusion.

A15 — Ansible Galaxy is a hub for roles/collections. `requirements.yml` lists them. Install with `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define how Ansible connects. `ssh` = standard Linux hosts. `local` = runs on control node. `network_cli` = Telnet/SSH for network devices. Use `ssh` for Linux, `local` for localhost, `network_cli` for switches/routers.

A17 — `delegate_to` runs a task on a different host. `run_once` runs it once across a group. Example: Gather remote facts, write summary to localhost once: `delegate_to: localhost`, `run_once: true`.

A18 — 1. Increase `forks` (tradeoff: strains control node CPU/RAM). 2. Enable `pipelining` (tradeoff: requires sudoers `NOPASSWD` config). 3. Fact caching (Redis/Memcached) (tradeoff: may serve stale facts). 4. Use Mitogen (tradeoff: adds setup complexity, requires Python compatibility checks).

A19 — `{{ }}` outputs expressions. `{% %}` controls flow (if/for). `{# #}` comments. Template:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check: {{ server }}
  server {{ server }};
{% endfor %}
}
```

A20 — Use `serial: 1` or `20%`. Pre-task: `uri` to set LB maintenance. Deploy tasks. Post-task: `uri` health check. Wrap in `block`/`rescue`: on failure, `rescue` reverts config, re-enables LB, and fails play. Ensures zero-downtime and automatic rollback.
