**CL1** — IaaS provides virtualized compute, network, and storage where you manage the OS and above (e.g., AWS EC2). PaaS provides a managed runtime/platform where you deploy code and manage data (e.g., Azure App Service). SaaS delivers a fully managed application where the provider handles everything (e.g., AWS WorkSpaces). The core difference is the level of operational control vs. management overhead.

**CL2** — The Shared Responsibility Model divides security: the provider secures the global infrastructure, hardware, and hypervisor; you secure what you put in the cloud. For IaaS VMs, you manage OS, patches, network config, and data. For managed Kubernetes (EKS/AKS), the provider secures the control plane and node OS; you secure workloads, RBAC, network policies, and secrets. For SaaS like M365, the provider secures the app and infra; you secure data, user access, MFA, and sharing policies.

**CL3** — A VPC is an isolated virtual network; subnets partition it into IP ranges. Security Groups (SGs) are instance-level, stateful firewalls that only support allow rules. Network ACLs (NACLs) are subnet-level, stateless firewalls that evaluate rules in order and support allow/deny. They layer as VPC → Subnet → Instance, with NACLs filtering subnet traffic and SGs filtering ENI/instance traffic. Stateful (SG) automatically allows return traffic; stateless (NACL) requires explicit inbound and outbound rules.

**CL4** — A landing zone is a pre-configured, secure multi-account foundation. Organizational Units (OUs) group accounts by function/environment (dev, prod, sandbox). Guardrails (SCPs/policies) enforce compliance and prevent destructive actions. Shared networking uses Transit Gateway or Azure Hub-and-Spoke for cross-account routing. Centralized logging aggregates CloudTrail, VPC Flow Logs, and metrics to a single account/service. Single-account approaches create massive blast radius, IAM complexity, billing opacity, compliance risks, and accidental deletion exposure.

**CL5** — IaC manages infrastructure via version-controlled code for reproducibility and testing. Terraform/OpenTofu (HCL) is multi-cloud, mature, and ideal for vendor-agnostic, complex infra. Pulumi uses general-purpose languages (TS/Python/Go) for imperative logic and fine-grained control, best for dev-heavy teams. CloudFormation/Bicep are AWS-native, declarative, and optimal for AWS-only environments with tight service integration. Crossplane is K8s-native, managing infra via CRDs; choose it for GitOps workflows or when infra must be managed alongside K8s workloads.

**CL6** — HPA scales pods based on CPU/memory/custom metrics. VPA recommends or sets optimal CPU/memory per pod. Cluster Autoscaler adds/removes nodes based on pending pod requests. KEDA scales workloads based on external events (queues, streams, HTTP). Use KEDA over HPA when scaling to zero is required, when triggers are external (Kafka, RabbitMQ, pub/sub), or when event-driven batch processing is the workload pattern.

**CL7** — Define RPO/RTO based on business impact. Active-active runs both regions simultaneously with sync replication (strong consistency, low RPO/RTO, high cost). Active-passive uses async replication (eventual consistency, higher RPO/RTO, lower cost). DNS failover (Route53/Traffic Manager) uses health checks to route traffic. Externalize state to managed DBs/object storage. Pilot light keeps core infra running with minimal data; warm standby runs a scaled-down full environment; multi-site active-active runs full production in both regions with real-time sync. Cost scales linearly with active sites.

**CL8** — GitOps uses Git as the single source of truth; controllers continuously sync cluster state to Git manifests. ArgoCD is pull-based, UI-rich, and supports app-of-apps; FluxCD is event-driven, Git-native, and CLI-focused. Secrets are handled via SealedSecrets, External Secrets Operator, or SOPS+KMS—never committed plaintext. Manual drift is detected by controllers, which auto-revert to Git state and alert. Enforce via admission controllers (OPA/Kyverno) to block direct `kubectl apply`.

**CL9** — Use a StatefulSet for stable pod identities and ordered deployment/termination. Configure a `local` storageClass with `volumeBindingMode: WaitForFirstConsumer` to bind PVCs to node-local disks for low latency. Use a headless service (`clusterIP: None`) for stable DNS resolution. Init containers fetch/configure data before the app starts. Mount ConfigMaps as volumes at exact filesystem paths using `subPath` if needed. Set a PDB (`minAvailable: 1` or `maxUnavailable: 0`) to prevent simultaneous disruption. Note: local storage lacks node-failure resilience; implement external data replication or accept the risk.

**CL10** — A K8s Service Account is a native pod identity with no cloud permissions. Workload Identity (GCP/Azure) and IRSA (AWS) securely map K8s SAs to cloud IAM identities. Mounting cloud credentials in pods is bad practice: they persist on disk, leak via logs/debugging, violate least privilege, and are hard to rotate. Workload identity federation uses OIDC to exchange a K8s SA JWT for short-lived, scoped cloud credentials at runtime, eliminating long-lived keys and enabling automatic rotation.

**CL11** — Object storage (S3/Blob) is HTTP-based, highly scalable, and metadata-rich; use for unstructured data, backups, static sites. Durability: 11 9s; Availability: 99.99%+. Block storage (EBS/Managed Disk) is low-latency, fixed-size, and VM-attached; use for OS, databases, high-IOPS apps. Durability: 99.999% (AZ-replicated); Availability: tied to AZ/VM. File storage (EFS/Azure Files) is NFS/SMB, shared, and hierarchical; use for shared configs, home dirs, legacy apps. Durability: 11 9s; Availability: regional, multi-AZ.

**CL12** — Zero-trust K8s assumes breach and verifies every request. Default-deny Network Policies restrict pod-to-pod traffic. A service mesh enforces mTLS and identity-based routing. Pod identity (IRSA/Workload Identity) grants least-privilege cloud access. Admission controllers (OPA/Kyverno) enforce policies (no privileged pods, required labels). Image signing (Cosign) verifies signatures before deployment. Falco monitors runtime system calls for anomalies. Secrets are managed via External Secrets Operator + Vault, never stored plaintext in etcd. Unlike perimeter models, zero-trust uses micro-segmentation, continuous validation, and identity/context rather than network boundaries.

**CL13** — A CDN is a globally distributed edge cache that serves content from locations closest to users. Requests route via DNS to the nearest edge node; cache hits serve instantly, misses fetch from origin. Cloud-native examples: AWS CloudFront, Azure Front Door. Use a CDN for static/dynamic content, media, cached APIs, DDoS mitigation, and global latency reduction. Serve directly from origin only for non-cacheable, highly personalized, or real-time data.

**CL14** — A region is a geographic area containing multiple Availability Zones (AZs). An AZ is one or more isolated data centers with independent power/network. Deploy across multiple AZs to survive data center failures, achieve high availability, and reduce latency. Zonal resources (EBS, NAT Gateway, some LBs) are tied to a single AZ. Regional resources (ALB, Route53, S3, RDS Multi-AZ) span multiple AZs for resilience.

**CL15** — Managed database services (RDS, Cloud SQL, Azure SQL) abstract operational overhead. The provider handles provisioning, OS/DB patching, backups, replication, monitoring, failover, and storage scaling. Self-hosting on a VM requires you to manage the OS, database software, patching, backup/restore, replication topology, scaling, and security hardening. Managed services trade some low-level control for significant operational savings and higher baseline reliability.

**CL16** — IAM users are long-term identities for humans/services. Groups bundle users for policy assignment. Roles provide temporary credentials for entities (users, services, external systems). Policies are JSON documents defining permissions. Least privilege means granting only the permissions required to perform a task. Apply it by scoping policies to specific resources/actions, avoiding `*:*`, using IAM Access Analyzer, enforcing MFA, rotating keys, and preferring roles over long-term credentials.

**CL17** — Serverless is event-driven, managed compute that scales automatically and charges per execution. AWS Lambda, Azure Functions, and GCP Cloud Functions differ in runtime support, cold start performance, and ecosystem integration. Cold starts are initialization delays when a container spins up for the first request; they matter for latency-sensitive apps but are mitigated via provisioned concurrency, keep-warm patterns, or faster runtimes. Serverless is a poor fit for long-running processes, stateful workloads, predictable high-throughput (reserved instances are cheaper), or strict network isolation/compliance needs.

**CL18** — Ingress resources route HTTP/HTTPS traffic with TLS termination at the controller; simple but limited. Gateway API offers structured, multi-gateway routing with better RBAC and TLS termination at the Gateway. Cloud LB annotations map to provider load balancers (ALB/NLB) with TLS termination at the LB or controller. Service mesh ingress gateways handle mesh-level routing and mTLS termination. Use Gateway API over Ingress for complex routing, multi-tenant environments, fine-grained control, or when Ingress limitations (single controller, flat structure) hinder operations.

**CL19** — Commit to Reserved Instances or Savings Plans for 1-3 years to save 30-70% on baseline workloads. Use Spot/Preemptible instances for fault-tolerant, interruptible workloads (up to 90% savings). Right-size using cost explorer and actual CPU/memory utilization. Tier storage with S3 Intelligent-Tiering and Archive/Glacier for cold data. Detect idle resources (unattached volumes, idle LBs, unused IPs) and schedule non-prod shutdowns. Implement FinOps: cross-functional ownership, strict tagging, monthly reviews, and automated alerts. Use showback/chargeback via billing reports tagged by team/project. Tools: Cost Explorer, Azure Cost Management, Kubecost/OpenCost, CloudHealth.

**CL20** — Multi-cloud avoids lock-in by abstracting infra via Kubernetes (common runtime), Terraform/OpenTofu (portable IaC), and service meshes. Networking uses cloud VPN/interconnects and global DNS. Identity federation uses OIDC with a centralized IdP. Trade-offs: higher complexity, cost, skill requirements, inconsistent SLAs/features, and data egress fees. Multi-cloud is justified for regulatory/data residency, catastrophic vendor risk, best-of-breed service needs, or M&A integration. It's unnecessary complexity for most startups/SMBs, deeply coupled cloud-native apps, or when operational overhead outweighs benefits.

**OT1** — The Purdue Model (ISA-95) layers industrial control systems. Level 0: Physical process (sensors, actuators). Level 1: Direct control (PLCs, RTUs, relays). Level 2: Supervisory control (SCADA, HMIs, historians). Level 3: Operations/Manufacturing Execution (MES, scheduling). Level 4: Enterprise/Business (ERP, finance). Level 5: Connected enterprise/cloud (external partners, IoT analytics).

**OT2** — IT networks prioritize confidentiality and integrity, run standardized OSes, and tolerate frequent reboots/updates. OT networks prioritize availability and safety, run legacy/proprietary OSes, and require deterministic real-time operation. Standard IT patching fails in OT because systems often cannot reboot, patches may break control logic or safety interlocks, and change windows are strictly controlled. OT patching requires validation, maintenance scheduling, and rollback plans.

**OT3** — An Industrial DMZ (IDMZ) is a segmented network between IT and OT hosting data historians, OPC servers, and DMZ proxies. Traffic is strictly controlled: IT→OT carries commands, schedules, and patches (via IDMZ); OT→IT carries process data, alarms, and logs. Direct Level 4 (IT) to Level 1 (control) connectivity is dangerous because it bypasses security controls, exposes critical systems to IT threats (ransomware, lateral movement), violates Purdue isolation, and risks safety/production disruption.

**OT4** — 1. Modbus TCP: L1/L2, simple request/response, legacy PLCs. 2. OPC UA: L2/L3, secure, platform-independent, modern standard. 3. EtherNet/IP (CIP): L1/L2, industrial Ethernet, real-time, Allen-Bradley ecosystem. 4. PROFINET: L1/L2, deterministic, real-time, European manufacturing. 5. MQTT: L3/L4, lightweight publish/subscribe, cloud/edge analytics, not for real-time control.

**OT5** — A data diode is hardware-enforced one-way communication (optical/electrical) guaranteeing no return traffic. A firewall is bidirectional, stateful, and rule-based. Use a data diode for critical safety systems, high-security zones, or when compliance mandates strict unidirectional flow. Limitation: cannot handle bidirectional protocols (acknowledgments, commands), requires protocol adaptation, and offers less flexibility than firewalls.

**OT6** — Data flow: PLCs/RTUs → SCADA → Historian → OPC UA Server → Edge Gateway (protocol translation, buffering, TLS) → MQTT Broker → Cloud Ingestion (IoT Core/Event Hubs) → Analytics. Security boundaries: IDMZ between SCADA/IT, edge gateway with mTLS, firewall between OT and cloud, network segmentation, mutual authentication, encrypted transit, and zero-trust edge policies.

**OT7** — A zone groups assets with similar security requirements; a conduit is the communication path between zones with defined controls. Design: Zone 0 (SIS), Zone 1 (PLCs/BPCS), Zone 2 (SCADA/Historian), Zone 3 (Engineering), Zone 4 (Corporate/IT). Conduits: Z1→Z2 (firewall, data diode if required), Z2→Z3 (secure gateway), Z3→Z4 (IDMZ, strict ACLs). SIS is physically/logically isolated, BPCS is segmented, engineering uses jump hosts, corporate access flows only through the IDMZ with monitoring.

**OT8** — VLANs segment by function (PLCs, HMIs, SCADA, Engineering, IT) using 802.1Q. Firewalls sit between VLANs enforcing least-privilege OT protocol rules. Managed L3 switches handle routing, port security, and disable unused ports. Remote access uses a jump host in the IDMZ, MFA, session recording, time-limited vendor accounts, and no direct OT access. Transition: phased rollout during maintenance windows, parallel run, validate control logic, rollback plan, start with non-critical lines, and maintain clear stakeholder communication.

**OT9** — SIS independently brings the process to a safe state on failure; BPCS handles normal control. IEC 61511 defines the safety lifecycle and SIL ratings for SIS. The SIS network must be air-gapped or strictly isolated to prevent cyber threats from compromising safety functions and to maintain SIL integrity. If ransomware reaches the SIS, it could disable safety functions, causing uncontrolled releases, equipment damage, or fatalities. Physical/logical separation, manual override capability, and regular safety validation are mandatory.

**OT10** — PLCs handle discrete, fast, modular control for machines/lines. DCS provides integrated, centralized control for continuous processes (chemical, oil/gas). SCADA provides supervisory monitoring/control over wide geographic areas (water, pipelines). They coexist commonly: PLCs/DCS handle control, SCADA provides oversight, historians store data, and all integrate via standard protocols.

**OT11** — Remote access: vendor connects to corporate → jump host in IDMZ → MFA → session recording → proxy to OT asset. Access is time-limited, role-based, and audited. RDP directly to an HMI from corporate is unacceptable because it exposes the HMI directly to the corporate network, bypasses segmentation, increases attack surface, violates least privilege, enables lateral movement, and lacks proper auditability.

**OT12** — Detection: NTA/IDS, EDR on OT servers, protocol anomaly detection, baseline asset inventory. IR steps: contain (isolate segment, block vendor VPN), investigate (forensics, log correlation), eradicate (patch, rotate creds), recover (restore clean backups), post-incident review. Coordination: notify control room, switch to manual/local control if needed, prioritize safety. Operator role: monitor physical process, execute manual overrides, report anomalies, follow cyber playbook, maintain safe state. Ensure safe ops via redundant control paths, manual fallback, continuous process monitoring, and clear IT/OT comms.

**OT13** — An HMI is an operator interface for monitoring real-time process data, viewing alarms, and performing manual overrides. An engineering workstation is used by engineers for programming, configuration, diagnostics, and firmware updates. HMIs are for routine operational use; engineering workstations are for development/maintenance and are not intended for daily process control.

**OT14** — A historian is a time-series database storing process data (temperatures, pressures, flows) for trend analysis, compliance, optimization, and troubleshooting. Plant historians (L3) store high-frequency, real-time/near-real-time operational data locally. Enterprise historians (L4) store aggregated, lower-frequency data for business/financial reporting, long-term retention, and ERP/BI integration.

**OT15** — Ladder logic is a graphical programming language mimicking relay circuits, executed by PLCs. It remains dominant because it's easy to learn for electricians, visually intuitive, deterministic, widely supported, has a massive legacy codebase, is safety-certified, and requires minimal training for maintenance personnel.

**OT16** — An RTU is a ruggedized, remote device optimized for telemetry over long distances (cellular, satellite, radio) with limited I/O. A PLC is local, high-speed, and handles complex logic with dense I/O. RTUs are deployed in pipelines, water distribution, wind farms, and remote monitoring where connectivity is limited and environmental conditions are harsh.

**OT17** — Analog signals (4-20mA, 0-10V) represent continuous process variables; digital signals are discrete on/off or binary. 4-20mA is preferred over 0-20mA because 4mA is a "live zero" that indicates wire break/failure at 0mA, provides power to the transmitter, and is less susceptible to electrical noise over long distances.

**OT18** — OT asset inventory is a complete list of hardware, software, firmware, and network connections; it's the foundation for risk assessment, patching, compliance, and threat detection. Tools: passive (NTA, packet capture, protocol analyzers) and active (SCADA scanners, ping/sweep). Active scanning is dangerous because it can crash legacy devices, cause unexpected state changes, disrupt control loops, trigger safety systems, and violate change management. Passive discovery is safer and non-disruptive.

**OT19** — MITRE ATT&CK for ICS focuses on physical processes, safety, legacy protocols, and operational continuity vs enterprise IT's data/confidentiality focus. Tactics/Techniques: 1. Reconnaissance (T1595: Active Scanning), 2. Initial Access (T1190: Exploit Public-Facing App), 3. Execution (T1059: Command & Scripting Interpreter), 4. Defense Evasion (T1070: Indicator Removal), 5. Impact (T1486: Data Encrypted for Impact). Use it to map existing defenses, identify gaps (e.g., no protocol inspection, no change monitoring), prioritize controls, simulate attacks, and align with IEC 62443.

**OT20** — Log collection: passive tapping, OT-friendly agents, syslog from HMIs/SCADA, avoid high-frequency polling. SIEM: centralized, tag OT assets, correlate with IT logs, use OT parsers. Detection rules: protocol anomalies, unauthorized PLC changes, after-hours access, unusual data exfiltration, safety bypass. Triage: OT analysts verify process impact, IT analysts verify network/endpoint, joint escalation for safety-critical alerts. Staffing: IT analysts handle general alerts, OT engineers validate control impact, dedicated OT SOC role for critical systems. False positives: tune to baseline OT behavior, use allowlists for engineering tools, reduce noise via correlation. Firmware alert: isolate PLC, verify change request, check backup/rollback, validate with engineering, monitor stability, document, update baseline.
