SC1-A
The pods fail because the Restricted Pod Security Standard (PSS) enforces stricter constraints than Baseline. Baseline only blocks obviously dangerous settings (e.g., `privileged: true`, `hostNetwork: true`). Restricted adds: `runAsNonRoot: true` must be explicitly set, and if set, `runAsUser` must be explicitly defined as a non-zero UID. The images default to `USER root`. When `runAsNonRoot: true` is enforced without `runAsUser`, Kubernetes attempts to run the container as root, violating the policy. The container runtime rejects this, causing the container to crash immediately, leading to CrashLoopBackOff. The cluster upgrade likely enabled the Restricted PSS namespace label (`pod-security.kubernetes.io/enforce=restricted`), which was previously Baseline or disabled.

SC1-C
**Immediate Fix:** Update deployments to add `runAsUser: 1000` (or matching UID) to `securityContext` and rebuild images with `USER 1000` in the Dockerfile.
**Manifest Changes:** Add explicit `securityContext.runAsUser`, `runAsGroup`, and `fsGroup` to pod specs. Ensure `runAsNonRoot: true` is present.
**CI Gate:** Add a PSS validation step using `conftest` or `kube-score` with OPA policies that enforce `runAsUser > 0` when `runAsNonRoot` is true. Integrate Trivy/Grype to scan for root-defaulting base images and fail builds.
**Rollout:** Use a rolling update with `maxSurge=25%` and `maxUnavailable=0`. Deploy the fixed image to a canary namespace first, verify health, then promote. Use Helm/Kustomize overlays to manage environment-specific security contexts.

SC2-A
Cross-region PostgreSQL streaming replication is asynchronous. WAL segments are shipped from primary to replica over the network. Promoting the replica severs replication, so any WAL not yet shipped or applied is permanently lost. The data loss window equals the replication lag at promotion time. To quantify: check RDS CloudWatch `ReplicaLag` metric, or query `pg_stat_replication` for `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn`. Compare `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` on the replica. Asynchronous replication guarantees no data loss only if you accept lag; cross-region async typically has 100ms-2s lag, but network blips can increase it.

SC2-C
**Architecture:** Use RDS Proxy to manage connection pooling, eliminating PgBouncer retry storms. Implement Route53 failover routing with health checks pointing to the new primary. Add application-level retry with exponential backoff and jitter. For RPO < 1s, standard RDS async replication is insufficient. Recommend **Aurora Global Database**: it uses a primary region and up to 5 secondary regions with async replication optimized for <1s lag, automatic failover, and global data distribution. Aurora also provides faster failover (~1 min) and built-in read/write splitting. If sticking to RDS, use synchronous cross-region replication (not natively supported by AWS RDS, requires third-party tools like Striim or custom Patroni setups), making Aurora the pragmatic choice.

SC10-C
**Failover Sequence:**
1. **Detection:** Health checks (heartbeat, DB ping, app probes) across Chicago. If >3 consecutive failures or etcd quorum loss, declare site down.
2. **DNS Failover:** GSLB (Route53/Azure Traffic Manager) switches VIP to Dallas. TTL < 60s.
3. **Patroni Promotion:** etcd triggers standby promotion. `synchronous_standby_names` ensures zero loss.
4. **Redis/RabbitMQ:** Sentinel/federation auto-promotes replicas.
5. **MinIO:** Site replication catches up. App switches to Dallas endpoint.
6. **Terraform State:** Update `primary_region` variable, run `terraform apply` to update DNS/ALB configs.
**Split-Brain:** Quorum-based DCS (etcd/Consul) prevents dual promotion. Fencing via shared storage or STONITH.
**Failback:** Reverse replication, sync Dallas->Chicago, verify data integrity, switch DNS back, decommission Dallas as primary. Run chaos tests quarterly.
