AA1 — A monolith is a single, unified codebase deployed as one unit with shared memory/process. Microservices decompose the system into independently deployable, network-communicating services. Microservices introduce: (1) Network latency and failure handling (partial outages, retries, timeouts), (2) Distributed data consistency (no ACID across services, requires sagas/eventual consistency), (3) Operational complexity (orchestration, CI/CD pipelines, distributed tracing, service discovery).

AA2 — Synchronous communication blocks the caller until a response is received, enforcing tight coupling and real-time guarantees. Example: REST/gRPC. Asynchronous communication decouples sender and receiver; messages are queued or published, and responses are handled later or not at all. Example: RabbitMQ (queue) or Kafka (pub/sub). Async improves resilience and throughput but introduces eventual consistency and ordering challenges.

AA3 — A reverse proxy routes traffic, terminates TLS, and provides basic load balancing/caching. An API gateway adds business-layer features: rate limiting, authentication/authorization, request transformation, versioning, and analytics. An API gateway can technically replace a reverse proxy, but they serve different layers. Best practice: use a lightweight reverse proxy (nginx/envoy) at the edge for TLS/SSL offloading and DDoS protection, then route to an API gateway for business logic. Replacing entirely adds unnecessary overhead to the gateway.

AA4 — A Saga breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo changes if a later step fails. Choreography-based sagas use events to trigger the next step; they are decentralized and simple but hard to debug and modify. Orchestration-based sagas use a central coordinator that sends commands; they are easier to monitor, version, and modify but introduce a single point of failure (mitigated by redundancy). Use choreography for stable, simple workflows; orchestration for complex, frequently changing, or auditable processes.

AA5 — CQRS separates read and write operations into distinct models. Commands modify state; queries read optimized projections. It is paired with Event Sourcing because events naturally drive state changes and can be replayed to rebuild read models. This combination solves: (1) Auditability and temporal queries (full history of state changes), (2) Read/write scaling independently (different schemas/DBs), (3) Complex domain modeling where traditional CRUD obscures business rules.

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping requests to a failing service. States: Closed (normal, requests pass), Open (failure threshold met, fast-fail), Half-Open (tests recovery with limited traffic). It differs from retry+backoff: retries assume transient errors and hammer the service; circuit breakers halt traffic to allow recovery. Use both together: retry+backoff handles transient spikes within the Closed state; the circuit breaker protects against persistent/systemic failures.

AA7 — 
1. Shared DB/schema: Lowest cost, highest noisy-neighbor risk, complex row-level security, easiest ops.
2. Shared DB/separate schema: Moderate cost, better isolation, easier per-tenant backup/restore, moderate ops.
3. Separate DB: Highest cost, best security/isolation, simplest backup/migration, highest ops complexity.
Trade-offs: Cost scales inversely with isolation. Security and noisy-neighbor risk improve with schema/DB separation. Operational complexity increases with isolation due to provisioning, backup, and migration overhead.

AA8 — Eventual consistency guarantees reads will eventually reflect writes after propagation delay. Strong consistency guarantees immediate visibility. For inventory that must never oversell: use strong consistency. Architecture: Dedicated inventory service backed by a relational DB (PostgreSQL) with row-level locking (`SELECT ... FOR UPDATE`) or optimistic locking with retries. At scale: partition by SKU/warehouse, use distributed transactions (2PC) or a saga with compensation, and avoid caching stock counts. Never rely on eventual consistency for stock deduction.

AA9 — A sidecar proxy is a co-located container that intercepts all inbound/outbound traffic for a service. In Istio, Envoy acts as the data plane proxy handling routing, mTLS, metrics, and retries. The control plane (Istiod) manages configuration and pushes it to Envoy. Data plane = traffic handling; control plane = configuration/management. mTLS between sidecars solves: transparent encryption without app code changes, automatic mutual authentication, centralized certificate rotation, and protection against network-level MITM attacks. App TLS requires manual cert management and doesn't authenticate service identity automatically.

AA10 — The Strangler Fig pattern incrementally replaces legacy functionality by routing traffic to new services until the old system is removed. Strategy: Place an API gateway/reverse proxy in front of the .NET Framework monolith. Identify a bounded context (e.g., user auth, billing). Build the new .NET 8 microservice. Route specific URL paths to the new service via the gateway. Implement dual-write or CDC for data migration. Use feature flags for safe rollout. Repeat per module. Decommission monolith endpoints once traffic is fully migrated.

AA11 — 12-Factor App is a methodology for cloud-native software. Six factors: (1) Codebase (one repo, many deploys), (2) Dependencies (explicitly declared), (3) Config (env vars, not code), (4) Backing services (treat as attached resources), (5) Build/release/run (strictly separate stages), (6) Processes (stateless, ephemeral). They matter because they enable horizontal scaling, zero-downtime deploys, secure config management, predictable resource allocation, and resilience in dynamic cloud environments.

AA12 — 
- Coupling: Event = loose (producer unaware of consumers). Request = tight (caller knows endpoint).
- Scalability: Event = high throughput, async scaling. Request = synchronous, can bottleneck.
- Debugging: Event = harder (distributed state, replay needed). Request = easier (request/response trace).
- Ordering: Event = partition/key ordering guaranteed. Request = per-request ordering.
- Failure: Event = retry/DLQ, idempotency required. Request = timeouts, retries, circuit breakers.
Choose event-driven for async workflows, high throughput, decoupled systems, and audit trails. Choose request-driven for real-time, simple CRUD, and synchronous workflows.

AA13 — A load balancer distributes incoming traffic across multiple servers. Layer 4 balances based on IP/port (fast, no content inspection). Layer 7 balances based on HTTP headers, URLs, cookies (slower, feature-rich). Layer 7 is required for content-based routing (e.g., `/api/v1` → backend A, `/static` → CDN) or SNI-based TLS termination.

AA14 — A message queue (RabbitMQ) uses point-to-point or pub/sub, deletes messages after consumption, and excels at task routing and low-latency processing. A log-based broker (Kafka) appends messages to an immutable log, retains them, and supports replay/high-throughput streaming. Pick RabbitMQ for task queues, routing, and strict delivery guarantees. Pick Kafka for event streaming, audit logs, data pipelines, and replay requirements.

AA15 — A container packages an app and its dependencies, sharing the host OS kernel. A VM includes a full guest OS and runs on a hypervisor. Containers are lighter, start faster, and use fewer resources. They are popular for microservices because they provide consistent environments, enable rapid independent scaling, support immutable deployments, and integrate seamlessly with orchestration platforms.

AA16 — Stateless services store no local session data; any instance can handle any request. They scale horizontally easily because instances are interchangeable. Example: Web API, CDN. Stateful services maintain local state/session. Scaling requires sticky sessions or distributed state management. Example: Database, Redis, WebSocket server.

AA17 — An ORM maps objects to database tables, abstracting SQL. Examples: Entity Framework (.NET), Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs accelerate development, ensure type safety, and abstract DB differences, but can generate inefficient queries, complicate complex joins, and obscure performance bottlenecks. Raw SQL offers full control, optimal performance, and complex query support, but requires more code, DB-specific tuning, and slower development.

AA18 — The Bulkhead pattern isolates resources (threads, connections, memory) so a failure in one component doesn't exhaust resources for others. It directly prevents cascade failures in microservices. Implementation: Use separate thread pools and connection pools per downstream service. In Kubernetes, deploy critical vs non-critical services on separate node pools with resource quotas, or use sidecar proxies to enforce per-service rate limits and circuit breakers.

AA19 — OT requires a central server to transform concurrent operations into a consistent state. It's complex, server-dependent, and works well for text. CRDTs are mathematical structures that guarantee convergence without central coordination. They support offline editing, have higher storage/compute overhead, and are decentralized. For offline editing, choose CRDTs. They allow disconnected clients to edit concurrently and merge deterministically upon reconnection without requiring a central server for conflict resolution.

AA20 — Distributed tracing challenges include polyglot instrumentation, high volume, and async flows. Context propagation uses W3C Trace Context (standard) or B3 (Zipkin) to inject/extract trace IDs across HTTP/gRPC. Sampling: head-based is cheap but loses rare traces; tail-based samples after processing for accuracy but adds overhead. Storage/query uses Jaeger/Tempo (distributed DBs optimized for time-range/span queries). For async/Kafka: propagate trace context in message headers. Use tail-based sampling with Kafka to correlate producer/consumer spans. Ensure idempotent span creation and use correlation IDs to maintain continuity across topic boundaries.

OP1 — Type 1 (bare-metal) hypervisors run directly on hardware, offering high performance and security. Examples: VMware ESXi, Proxmox VE, KVM. Type 2 (hosted) hypervisors run as applications on a host OS, offering ease of use but lower performance. Examples: VirtualBox, VMware Workstation, Parallels.

OP2 — SAN provides block-level storage, presenting disks to servers. It offers high performance and low latency. Protocols: Fibre Channel, iSCSI. NAS provides file-level storage, presenting network shares. It's easier to manage. Protocols: NFS, SMB/CIFS. Use SAN for databases and VMs. Use NAS for file shares, backups, and home directories.

OP3 — 3-tier architecture (core/distribution/access) is hierarchical, prone to bandwidth bottlenecks, asymmetric routing, and high latency between tiers. Leaf-spine (Clos) architecture connects every leaf switch to every spine switch, providing equal-cost multipath routing, predictable bandwidth, and low latency. It solves 3-tier's scalability limits and complex routing by enabling horizontal scaling and consistent east-west traffic performance.

OP4 — Design: 3+ nodes for quorum. Quorum requires majority votes to prevent split-brain. Fencing uses STONITH (IPMI/iDRAC) to power off failed nodes. Shared storage: Ceph (recommended), iSCSI, or NFS. During node failure: HA manager detects failure, fences the node, and restarts VMs on remaining nodes. Shared storage ensures VM disks remain accessible, and Ceph rebalances replicas automatically.

OP5 — VLAN trunking carries multiple VLANs over a single physical link. 802.1Q adds a 4-byte tag to Ethernet frames containing the VLAN ID. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`, `ip link set eth0.10 up`, assign IP. Alternatively, use `netplan` or `NetworkManager` with VLAN interfaces.

OP6 — RAID 1: Mirror, 50% capacity, 1 drive fault. RAID 5: Striping + single parity, N-1 capacity, 1 fault, read-heavy. RAID 6: Double parity, N-2 capacity, 2 faults, write penalty. RAID 10: Mirror + stripe, 50% capacity, survives multiple faults (not same mirror), fast. Z2 (ZFS): Double parity, flexible, self-healing, similar to RAID 6. Choice: RAID 10 for maximum DB write performance and fault tolerance. Z2 if capacity utilization and data integrity/self-healing are priorities.

OP7 — Architecture: Internal DNS servers (Windows DNS/BIND) act as recursive resolvers for clients. Authoritative servers host internal AD zone and external public zone. Forwarders point to ISP/Cloudflare for external resolution. Conditional forwarding routes internal AD queries to domain controllers and external queries to forwarders. Split-horizon returns private IPs internally and public IPs externally. DNSSEC signs the external zone with a chain of trust to the root. Laptop roaming: DHCP assigns internal DNS. On VPN, split tunneling or conditional forwarding routes internal queries to corporate DNS. Roaming clients use cached records or DNS dynamic updates.

OP8 — PKI chain: Root CA (offline, self-signed, highly secured) → Subordinate/Issuing CA (online, issues certs) → End-entity cert. Internal PKI: Use AD CS. Root CA stays offline. Subordinate CA issues certs via templates (workstation, server, email). CRL = periodic revocation list download. OCSP = real-time status check. Auto-enrollment pushes certs to domain-joined devices. Compromise consequences: Subordinate CA = issue new root/sub, revoke certs, minimal blast radius. Root CA = catastrophic, requires rebuilding entire PKI and updating trust stores globally.

OP9 — MPLS: High reliability, low latency, expensive, managed. IPsec VPN: Cheap, internet-based, variable latency, manual mgmt. SD-WAN: Orchestrates MPLS/IPsec/WiFi, app-aware routing, centralized mgmt, moderate cost. WireGuard mesh: Modern crypto, fast, simple, lacks enterprise features (QoS, SLA, central mgmt). Recommendation: SD-WAN. Balances cost, reliability, latency, and centralized management. Supports QoS for VoIP, dynamic path selection, and scales efficiently for 50 users/site.

OP10 — iDRAC (Dell), iLO (HPE), IPMI (standard) are out-of-band management interfaces for remote power control, console access, and hardware monitoring. Critical for recovering from OS crashes, deploying OS, and managing servers without physical access. Exposed to the internet: High risk of brute force, firmware exploits, unauthorized access, ransomware, or hardware manipulation. Should be isolated on a dedicated management network.

OP11 — LVM: Traditional volume manager, fixed-size volumes, snapshots are copy-on-write and consume space. LVM-Thin: Overprovisions storage, snapshots are instant and space-efficient, but performance degrades under heavy writes. ZFS: Filesystem + volume manager, copy-on-write, snapshots are instant, read-only, zero initial space overhead, self-healing. Use LVM for legacy/simple setups. LVM-Thin for VM storage efficiency. ZFS for data integrity, advanced snapshots, compression, and modern Linux.

OP12 — Stretch cluster: 2 sites with nodes, 1 witness/tiebreaker site. Ceph CRUSH rules map OSDs to sites, ensuring replicas span sites. Monitors: 1 per site + 1 witness for quorum. Network latency: <10ms recommended; stretch pushes limits. Split-brain: Witness breaks tie when sites lose connectivity. 2-site Ceph without a tiebreaker is bad because both sites can claim quorum, leading to data corruption and no automatic resolution.

OP13 — DHCP dynamically assigns IP/config. DORA: Discover, Offer, Request, Acknowledge. If server unavailable: Client uses APIPA (169.254.x.x) or retains old IP. When lease expires: Client unicasts renewal to server. If fails, broadcasts. If still fails, drops IP and restarts DORA.

OP14 — Unmanaged switches are plug-and-play with no configuration. Managed switches support VLANs, QoS, STP, port security, SNMP, ACLs, and link aggregation. These features enable network segmentation, traffic prioritization, loop prevention, monitoring, and security in enterprise environments.

OP15 — NTP synchronizes clocks over a network. Accurate time is critical for log correlation, authentication (Kerberos/AD), distributed DB consistency, security certificates, and debugging. Clock drift causes: Kerberos auth failures, cluster split-brain, log timeline mismatch, database replication lag/errors, and certificate validation issues.

OP16 — Physical: Hardware directly. VM: OS + hypervisor. Container: App + libs, shares host OS. Run bare metal for: High-performance databases, real-time processing, hardware passthrough (GPUs/NICs), regulatory compliance, maximum I/O throughput, and ultra-low latency requirements.

OP17 — UPS provides battery backup for short outages, conditions power, and bridges to generators. Generators provide long-term power via fuel. Both are needed: UPS handles immediate transition and surge protection; generators sustain power during extended outages. ATS (Automatic Transfer Switch) automatically switches load from utility to generator during failure and back when restored.

OP18 — Active-passive: One handles traffic, standby waits. Active-active: Both handle traffic, requires data sync. PostgreSQL HA with Pacemaker/Corosync: Pacemaker manages resources (VIP, PG service). Primary runs PG, standby streams WAL. STONITH fences failed nodes. On failure, Pacemaker promotes standby, moves VIP, and starts services. Use Patroni/repmgr for PG-level replication, Pacemaker for resource orchestration.

OP19 — 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO/RTO defined by business impact. Backup types: Full (baseline), Incremental (changes since last), Differential (since last full). Deduplication reduces storage and backup windows. Media: Disk for fast restore, tape/cloud for cheap offsite. Immutable backups: WORM storage/air-gapped for ransomware protection. Test restores: Regular drills, verify integrity, measure RTO/RPO. Backup = data protection. DR = full recovery process (infrastructure, data, procedures) to resume operations.

OP20 — 802.1X is port-based NAC. Roles: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP: EAP-TLS (cert-based, secure), PEAP (username/password, tunneled). RADIUS handles auth, authorization, accounting. Dynamic VLAN: RADIUS returns VLAN ID, switch assigns port. Failure: Port stays unauthorized, no traffic. MAB: Switch uses device MAC as credential, checks RADIUS DB, grants access. Bypasses 802.1X for printers/IoT devices.
