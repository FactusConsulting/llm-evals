**T1 — Easy:** `tofu plan` performs a dry run, showing what changes OpenTofu intends to make to your infrastructure without actually executing them. `tofu apply` executes those changes, creating or updating the resources defined in your configuration.

**T2 — Easy:** State is a file (or database) that tracks the current state of your infrastructure (resource IDs, attributes). Remote state is important because it allows multiple team members to work on the same infrastructure without conflicts, provides versioning and backup, and enables state locking to prevent concurrent modifications.

**T3 — Medium:** `count` creates a number of instances based on an integer (e.g., 3). `for_each` creates instances based on a map or set of strings (e.g., 3 instances with specific names). `for_each` is preferred when you need to reference specific instances by name (e.g., `aws_instance.web["web1"]`) or when the configuration logic is complex and requires unique keys.

**T4 — Medium:** If you manually change a resource outside of OpenTofu (e.g., via a cloud console), OpenTofu detects this as "drift" or "out of sync" during the next plan. It will flag the resource as changed. When you run `apply`, OpenTofu will attempt to reconcile the state with reality, typically by recreating the resource to match the state file.

**T5 — Medium:**
```hcl
resource "null_resource" "web_servers" {
  for_each = toset(["web1", "web2", "web3"])
  # Example resource creation logic
  # provider "example" {
  #   instance_name = each.value
  # }
}
```

**T6 — Hard:** `terraform_remote_state` reads the state file of another module, which is hard to manage, version, and can lead to circular dependencies. Output values are the recommended alternative because they explicitly define what data should be shared, are easier to manage, and provide a cleaner interface for module consumers.

**T7 — Hard:** The `remote-exec` provisioner runs *before* the resource it depends on is created. Since the kubeconfig file doesn't exist yet, the command fails. To fix this, use the `triggers` argument on the `null_resource` to create a dependency on the creation of the cluster (e.g., referencing the cluster's ID or creation timestamp), ensuring the provisioner runs only after the cluster is ready.

**T8 — Medium:** `terraform import` is a CLI command used to bring existing resources into state manually. Its limitation is that it doesn't update the state structure (e.g., renaming resources requires manual `moved` blocks). The `import` block (available in OpenTofu 1.5+) allows you to declare this mapping declaratively within your code, handling the state migration automatically.

**T9 — Easy:** A variable is a placeholder for a value that can be passed in. An input variable is the value provided by the user (via CLI, file, or environment). An output is a value exposed from the module or root configuration to the user after the plan/apply.

**T10 — Easy:** A provider is a plugin that allows OpenTofu to interact with a cloud provider or service (e.g., AWS, Azure). If you run `tofu plan` without running `tofu init` first, OpenTofu cannot find the required provider plugins and will fail with an error stating that the provider is missing.

**T11 — Easy:** The `.terraform.lock.hcl` file locks the specific versions of providers and modules used in the project. It should be committed to version control to ensure that every developer and CI/CD pipeline uses the exact same versions, guaranteeing reproducibility and preventing "it works on my machine" issues.

**T12 — Easy:** `tofu destroy` tears down all resources defined in the state. To target a single resource, use the `-target` flag (e.g., `tofu destroy -target=aws_instance.web_server`).

**T13 — Easy:** A data source is used to read information about existing resources (read-only). You use a data source instead of a managed resource when you need to reference an existing resource (like an existing VPC ID) to configure another resource, rather than creating a new one.

**T14 — Medium:** `locals` are used for internal calculations or static values that do not need to be configurable by the user. You should use locals instead of input variables when the value is derived from other variables, is a constant, or is internal logic that shouldn't be exposed to the user.

**T15 — Medium:** The `lifecycle` block controls resource behavior.
*   `create_before_destroy`: Creates the new resource before destroying the old one (useful for databases to avoid downtime).
*   `prevent_destroy`: Prevents a resource from being destroyed (useful for critical infrastructure).
*   `ignore_changes`: Ignores changes to specific attributes (useful if a cloud provider manages tags automatically).

**T16 — Medium:** A `moved` block allows you to rename resources in the state file without destroying and recreating them. This is crucial for refactoring module structures (e.g., moving a resource from `module.vpc` to `module.network`) while preserving the existing cloud resources.

**T17 — Hard:** OpenTofu builds a dependency graph where resources depend on each other. **Implicit dependencies** are created automatically when one resource references another (e.g., passing an ID). **Explicit dependencies** are created using the `depends_on` block. `depends_on` forces sequential execution, reducing parallelism and slowing down the apply. It should be used sparingly, only when automatic detection fails (e.g., with `null_resource`).

**T18 — Hard:** Strategies to reduce plan time:
1.  **Parallelism Limit:** Reduce the `parallelism` setting in `terraform` config to limit concurrent operations (Tradeoff: Slower execution).
2.  **Local State Caching:** Use a local backend for `plan` and `refresh` operations to avoid hitting the remote backend repeatedly (Tradeoff: Risk of state drift if not synced).
3.  **Provider Optimization:** Use local provider binaries or faster cloud SDKs (Tradeoff: Requires setup).
4.  **Remove Unused Data Sources:** Ensure `data` sources are not querying unnecessarily or are cached (Tradeoff: Requires code review).

**T19 — Hard:** State locking prevents concurrent writes. If a CI pipeline crashes mid-apply, the lock remains active, blocking other users. To manually break a lock, run `terraform force-unlock <LOCK_ID>`. The risk is that if another user is applying changes simultaneously, breaking the lock could cause data corruption or state conflicts.

**T20 — Hard:**
1.  **Create Backend:** Create an S3 bucket and a DynamoDB table for locking.
2.  **Configure Backend:** Update `terraform.tfstate` or create `backend.tf` to point to the new S3/DynamoDB configuration.
3.  **Init:** Run `terraform init` to download the backend plugin.
4.  **Push State:** Run `terraform state push terraform.tfstate` to upload the local state file to S3.
5.  **Verify:** Check the S3 console to confirm the state file exists.
6.  **Cleanup:** Delete the local `terraform.tfstate` file.

A **Role** is a reusable collection of files (tasks, variables, handlers, templates) that can be included in playbooks. **A2 — Easy:** `ansible_facts` is a dictionary containing information about the target host (OS, IP, etc.). You access the OS family using `ansible_facts['os_family']` or `ansible_facts.ansible_os_family`.

*   **command:** Executes a command without a shell (pipes and redirects fail). Use for simple commands.
*   **shell:** Executes a command via the shell (pipes and redirects work). Use when shell features are needed.
*   **raw:** Executes a command over SSH without Python. Use for bare-metal targets or initial setup.

**A4 — Medium:** Idempotency means running the same task multiple times results in the same final state. An **idempotent** example is the `yum` or `apt` module (installs only if missing). A **non-idempotent** example is `shell: echo "hello" > /tmp/file` (creates the file every time it runs).

**A9 — Easy:** An **inventory file** lists the hosts you want to manage. A **static inventory** is a text file (e.g., `hosts`). A **dynamic inventory** is a script (e.g., AWS EC2 dynamic inventory) that queries an API to generate the host list at runtime.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A **handler** is a task that is only executed if a task with the same name notifies it has changed state. It differs from a regular task by running only once at the end of the play. You trigger a handler by using the `notify` keyword in a task.

**A12 — Easy:** The `ansible.cfg` file configures Ansible behavior. Common settings include `inventory` (path to inventory), `host_key_checking` (security), `timeout` (connection), and `roles_path`.

**A13 — Easy:** The `register` keyword stores the output of a task into a variable. You can use this variable in subsequent tasks, for example: `set_fact: my_var={{ my_result }}` or `when: my_result.rc == 0`.

**A14 — Medium:** `include_tasks` dynamically includes a task file at runtime (parsed per host), allowing for conditional inclusion based on host facts. `import_tasks` statically includes a file (parsed once at runtime), which is better for loops or conditions that apply to the file itself. Conditional evaluation differs: `import_tasks` evaluates the condition on the file, `include_tasks` evaluates per host.

**A15 — Medium:** **Ansible Galaxy** is a repository for sharing Ansible roles and collections. A `requirements.yml` file lists these dependencies. You use `ansible-galaxy install -r requirements.yml` to download and install them into your project.

**A16 — Medium:** Connection plugins define how Ansible connects to a host.

1.  **Forks:** Increase the number of parallel processes (Tradeoff: High CPU load on control node).
2.  **Pipelining:** Transmits commands via SSH pipes instead of full file transfer (Tradeoff: Requires shell on target).
3.  **Fact Caching:** Cache `ansible_facts` in Redis (Tradeoff: Requires Redis setup).
4.  **Mitogen:** Uses ZeroMQ for faster transport (Tradeoff: Requires Python on target).
