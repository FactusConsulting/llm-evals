**AA1 — Easy:** A **monolith** is a single, indivisible codebase deployed as one unit, while **microservices** are independent services deployed separately. Microservices introduce: 1. **Distributed Tracing Complexity** (tracking requests across services is harder), 2. **Data Consistency Challenges** (ACID transactions across services require sagas or eventual consistency), and 3. **Operational Overhead** (orchestrating and monitoring many services is more complex than managing one).

**AA2 — Easy:** **Synchronous** communication requires the caller to wait for a response (e.g., HTTP REST). **Asynchronous** communication decouples the caller from the receiver (e.g., RabbitMQ). Example technologies: Synchronous = REST (gRPC), Asynchronous = RabbitMQ (Message Queue) or Kafka (Event Stream).

**AA3 — Medium:** A **Reverse Proxy** (like Nginx) handles generic traffic routing, SSL termination, and security for a single server or pool. An **API Gateway** is a specialized reverse proxy that handles API-specific concerns like authentication, rate limiting, and request routing to specific microservices. An API Gateway *can* replace a reverse proxy, but it adds latency and complexity. It is best to keep them separate: use a reverse proxy for infrastructure security and an API Gateway for application logic.

**AA4 — Medium:** The **Saga pattern** manages distributed transactions by breaking a long-running transaction into a sequence of local transactions, each updating the database and publishing an event. **Choreography** relies on events to trigger the next step (loose coupling, harder to debug). **Orchestration** uses a central coordinator to manage the sequence (tighter coupling, easier to debug). Use choreography for simple flows; use orchestration for complex dependencies where you need to enforce a specific order or handle compensation logic centrally.

**AA5 — Medium:** **CQRS** (Command Query Responsibility Segregation) separates the read and write models of an application. It is often paired with **Event Sourcing** (storing state changes as a sequence of events) to allow for complex queries and rebuilding state from history. This combination solves the problem of complex reporting and auditing that a traditional CRUD model cannot handle efficiently, as the read model can be optimized for specific query patterns.

**AA6 — Medium:** The **Circuit Breaker** pattern prevents cascading failures by stopping calls to a failing service. The three states are: **Closed** (circuit is active, requests pass), **Open** (circuit is tripped, requests are rejected immediately), and **Half-Open** (circuit is testing, allowing a limited number of requests to see if the service recovers). It differs from retry/backoff by stopping the call entirely rather than retrying. You use both: Circuit Breaker protects against a service that is down or unresponsive, while Retry/Backoff handles transient network blips.

**AA7 — Hard:**
1.  **Shared DB, Shared Schema (Row-level ID):** *Pros:* Cheapest, easiest to query. *Cons:* High noisy-neighbor risk, security risk (SQL injection affects all tenants), schema changes are difficult.
2.  **Shared DB, Separate Schema:** *Pros:* Better isolation, schema changes are tenant-specific. *Cons:* Higher cost, complex data synchronization if needed.
3.  **Separate DB per Tenant:** *Pros:* Best isolation and security. *Cons:* Highest cost, complex data replication if multi-region, difficult to join data across tenants.

**AA8 — Hard:** **Strong consistency** ensures every read receives the most recent write. **Eventual consistency** allows reads to be stale temporarily. For an inventory system that must never oversell, you need **Strong Consistency**. You would use a **Relational Database** (like PostgreSQL) with **Optimistic or Pessimistic Locking** (e.g., SELECT FOR UPDATE) or a distributed SQL database. You would avoid eventual consistency models like NoSQL unless you implement complex pre-booking logic.

**AA9 — Hard:** A **sidecar proxy** is a container that runs alongside an application and shares its network stack. In **Istio**, **Envoy** is the sidecar proxy. The **Control Plane** (Istiod) manages configuration and security policies, while the **Data Plane** (Envoy) handles the actual traffic routing and mTLS. mTLS solves the problem of mutual authentication and encryption between services without requiring the application code to handle SSL/TLS, preventing man-in-the-middle attacks and ensuring secure communication.

**AA10 — Medium:** The **Strangler Fig pattern** involves gradually replacing parts of a monolith with new services, like a strangler fig tree strangling a host tree. **Migration Strategy:** Create a facade API that sits in front of the legacy monolith. Build the new .NET 8 microservice. Route traffic for specific endpoints (e.g., `/api/users`) from the facade to the new microservice. Over time, decompose the monolith code until the legacy application is completely replaced.

**AA11 — Medium:** The **12-Factor App** methodology standardizes deployment practices for cloud-native apps. Key factors include: **Codebase** (single source control), **Dependencies** (explicit declaration), **Config** (environment variables), **Backing Services** (treated as attached resources), **Build/Release/Run** (strict separation), **Logs** (stdout), **Processes** (stateless), **Port Binding** (port 8080), **Concurrency** (shared stateless processes), and **Disposability** (rapid startup/shutdown). They matter for portability, scalability, and maintainability.

**AA12 — Hard:** **Event-Driven (Kafka):** Loose coupling, high scalability, decoupling of consumers, but complex debugging and ordering guarantees (per partition). **Request-Driven (REST/gRPC):** Tight coupling, synchronous, easier to debug, but harder to scale independently. Choose **Event-Driven** when you need high throughput, decoupling, or background processing. Choose **Request-Driven** when you need immediate feedback or simple, direct interaction between services.

**AA13 — Easy:** A **Load Balancer** distributes incoming network traffic across multiple servers. **Layer 4** balances based on IP/Port (TCP/UDP). **Layer 7** balances based on HTTP content (URL, headers, cookies). A use case for Layer 7 is **SSL Termination** (decrypting HTTPS at the LB) or **Content-Based Routing** (sending `/api/v1` traffic to Service A and `/api/v2` to Service B).

**AA14 — Easy:** A **Message Queue** (RabbitMQ) is a point-to-point buffer ensuring delivery and decoupling. A **Log-based Broker** (Kafka) is an append-only log optimized for high throughput and sequential reads/writes. Pick **RabbitMQ** when you need guaranteed delivery, complex routing, and reliability. Pick **Kafka** when you need high throughput, event streaming, and time-series data analysis.

**AA15 — Easy:** A **Container** is a lightweight, standalone package of software that includes the code and all its dependencies, sharing the host OS kernel. A **Virtual Machine** (VM) includes a full guest OS. Containers are popular for microservices because they are lightweight (fast startup), portable (consistent across environments), and efficient (share kernel).

**AA16 — Easy:** **Stateless** services do not store local data; they rely on external storage. **Stateful** services maintain local state (e.g., in-memory cache). Stateless services are easier to scale horizontally because you can add more instances without worrying about data synchronization. Examples: Stateless (API Gateway, Auth Service), Stateful (PostgreSQL Database, Redis Cache).

**AA17 — Easy:** An **ORM** (Object-Relational Mapper) maps database records to objects in code. Popular examples: **Hibernate** (Java), **Entity Framework** (C#). Trade-offs: ORMs increase developer productivity and reduce boilerplate, but they can introduce performance overhead (N+1 queries) and abstract away complex SQL, making debugging difficult.

**AA18 — Medium:** The **Bulkhead pattern** isolates resources (threads, connections, services) to prevent a failure in one area from cascading to the whole system. In microservices, this prevents a slow database from blocking the entire application. Implementation: Use separate **Thread Pools** for different services, or deploy critical services in separate **Deployment Groups** with resource quotas.

**AA19 — Hard:** **Operational Transformation (OT)** is an algorithmic approach to resolving conflicts by transforming operations to maintain a linear history. **CRDTs** (Conflict-free Replicated Data Types) use mathematical properties to ensure that merging different versions of data results in the same final state without conflict. Consistency: OT is linearizable (strong), CRDTs are eventually consistent. Complexity: OT is complex to implement; CRDTs are simpler. Offline support: OT is difficult; CRDTs are excellent. For a system requiring offline editing, **CRDTs** are the better choice because they guarantee convergence without complex conflict resolution logic.

**AA20 — Hard:** Distributed tracing involves propagating a unique **Trace ID** and **Span ID** across services. **Context Propagation:** Use **W3C Trace Context** headers or **B3** headers. **Sampling:** **Head-based** (random at start) vs **Tail-based** (sampling based on latency). **Storage:** Jaeger or Grafana Tempo. **Async Messaging:** Consumers read the trace headers from the message and create child spans. To ensure continuity through Kafka, the consumer application must extract the trace ID from the incoming message headers and include it in the outgoing message headers.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** **Type 1 (Bare-metal)** hypervisors run directly on hardware without a host OS (e.g., ESXi, Hyper-V). **Type 2 (Hosted)** hypervisors run on top of a host OS (e.g., VMware Workstation, VirtualBox).

**OP2 — Easy:** A **SAN** (Storage Area Network) provides block-level storage (e.g., for databases) using protocols like Fibre Channel or iSCSI. A **NAS** (Network Attached Storage) provides file-level storage (e.g., for file sharing) using NFS or SMB. Use SAN for high-performance, low-latency needs (databases); use NAS for general file storage.

**OP3 — Medium:** A **3-tier architecture** uses Core, Distribution, and Access switches. **Leaf-Spine** replaces the Distribution layer with Spine switches that connect directly to all Leaf switches. It solves the scalability bottleneck of the 3-tier model (spine switches don't need to know every host) and eliminates the spanning tree protocol (STP) complexity.

**OP4 — Medium:** A **Proxmox cluster** typically uses 3 nodes. **Quorum** is required to prevent split-brain; if 2 nodes vote, the cluster is active. **Fencing** (STONITH) is critical to kill a failed node's access to shared storage. **Shared Storage** options: Ceph (RADOS), iSCSI, or NFS. During a node failure, the cluster votes out the failed node, reboots services on the remaining nodes, and the shared storage remains accessible to the surviving nodes.

**OP5 — Medium:** **VLAN Trunking** allows multiple VLANs to pass over a single physical link. **802.1Q** tagging adds a 4-byte header to frames identifying the VLAN ID. To configure a single NIC for 3 VLANs on Linux, you would create VLAN interfaces using `ip link add link eth0 name eth0.10 type vlan id 10`, `ip link add link eth0 name eth0.20 type vlan id 20`, etc.

**OP6 — Hard:** **RAID 1** (Mirror) offers redundancy and good read performance but poor write performance and low capacity. **RAID 5** offers good capacity and redundancy but poor write performance and is vulnerable to disk failure. **RAID 6** offers double parity (good redundancy) but poor write performance. **RAID 10** offers redundancy and good read/write performance. **RAID Z2** (ZFS) offers similar benefits to RAID 6 with copy-on-write. For a **database server** balancing performance and fault tolerance with 6 drives, **RAID 10** is usually the best choice because it offers the highest write performance and redundancy.

**OP7 — Hard:** **Architecture:** Use a primary **Authoritative DNS** server for the external zone (with DNSSEC) and a secondary for redundancy. Use **Recursive Resolvers** (AD Integrated DNS) for internal clients. Use **Conditional Forwarders** to send internal queries to the internal DNS. **Split-Horizon:** Internal DNS resolves internal names to private IPs; external DNS resolves public names to public IPs. **VPN Scenario:** When a laptop connects via VPN, the VPN client routes DNS queries to the internal Recursive Resolver, which uses Conditional Forwarders to resolve internal names correctly.

**OP8 — Hard:** The **PKI Chain of Trust** starts with a **Root CA** (offline, self-signed), which issues a **Subordinate/Issuing CA**. The Issuing CA signs end-entity certificates. **CRL** (Certificate Revocation List) vs **OCSP** (Online Certificate Status Protocol). **Templates** define certificate usage. **Auto-enrollment** automates distribution. **Compromised Subordinate CA:** You revoke the specific CA and reissue certificates. **Compromised Root CA:** You must revoke the Root, revoke all intermediate CAs, and reissue *all* certificates organization-wide, as trust is lost for the entire organization.

**OP9 — Hard:** **MPLS:** High reliability and low latency, but expensive. **IPsec VPN:** Cheaper, but latency varies and reliability depends on internet quality. **SD-WAN:** Cost-effective, intelligent traffic routing, but management complexity varies. **WireGuard:** Simple, fast, but less feature-rich than MPLS/SD-WAN. For a company with **50 users per site and latency-sensitive VoIP**, **MPLS** is the recommended choice due to its guaranteed low latency and high reliability.

**OP10 — Medium:** **iDRAC/iLO/IPMI** is out-of-band management hardware that allows remote access to the server's BIOS, OS, and hardware status independent of the OS. It is critical for rebooting servers when the OS hangs or for monitoring hardware health. If exposed to the internet, an attacker can reboot the server, exfiltrate data, or install malware, effectively taking control of the infrastructure.

**OP11 — Medium:** **LVM** is a logical volume manager for standard disks. **LVM-Thin** allows overprovisioning (thin provisioning). **ZFS** is a file system with advanced features like snapshots and deduplication. Use **LVM** for standard server needs. Use **LVM-Thin** for development/test environments to save space. Use **ZFS** for storage servers or environments requiring frequent snapshots. **Snapshots:** LVM snapshots are copy-on-write blocks; ZFS snapshots are copy-on-write filesystem states.

**OP12 — Hard:** **Stretch Cluster:** 2 sites with a WAN link. **Ceph CRUSH rules** must be configured to place replicas across sites. **Network latency** must be low enough for quorum. **Split-brain:** If the WAN link fails, the cluster splits. **Tiebreaker:** A third node or quorum vote is needed. **2-site Ceph is generally bad** without a tiebreaker because a network partition can lead to split-brain, where both sites think they are the primary and corrupt data.

**OP13 — Easy:** **DHCP** dynamically assigns IP addresses. The **DORA process**: **D**iscover (client), **O**ffer (server), **R**equest (client), **A**cknowledgment (server). When a lease expires and the server is unavailable, the client will typically try to renew the lease using the cached information. If it cannot renew, it will eventually release the IP and attempt to obtain a new one from another server or fail to connect.

**OP14 — Easy:** A **Managed Switch** offers configuration capabilities like VLANs, Quality of Service (QoS), and link aggregation. An **Unmanaged Switch** is plug-and-play. In an enterprise, managed switches are important for network segmentation (VLANs), prioritizing traffic (VoIP), and optimizing bandwidth (Link Aggregation).

**OP15 — Easy:** **NTP** (Network Time Protocol) synchronizes clocks. Accurate time is critical for clustering (quorum votes, lock management) and auditing. If clocks drift significantly between servers in a cluster, it can lead to **split-brain** (both nodes thinking they are the master), **lock timeouts** (services hanging), or data corruption.

**OP16 — Easy:** A **Physical Server** runs directly on hardware. A **Virtual Machine** runs on a hypervisor. A **Container** runs on the host OS kernel. You would run a workload directly on **bare metal** for high-performance requirements (e.g., gaming servers, high-frequency trading, or HPC) where the overhead of a hypervisor or container runtime is unacceptable.

**OP17 — Easy:** A **UPS** (Uninterruptible Power Supply) provides battery backup for seconds to minutes, allowing a graceful shutdown. A **Generator** provides power from fuel for hours or days. You need both to bridge the gap between power loss and generator startup. An **ATS** (Automatic Transfer Switch) automatically switches the power source from utility to UPS to generator seamlessly.

**OP18 — Medium:** **Active-Passive:** One node is active, the other is standby. **Active-Active:** Both nodes are active and share the load. **Implementation:** Use **Pacemaker/Corosync** to manage the cluster. Configure a **Virtual IP (VIP)**. Set up **STONITH** (fencing) to kill a failed node. If the active node fails, Pacemaker moves the VIP to the passive node, and services restart.

**OP19 — Hard:** **Strategy:** Follow the **3-2-1 rule** (3 copies, 2 media types, 1 offsite). Define **RPO/RTO**. Use **Full, Incremental, and Differential** backups. Use **Deduplication** to save space. Use **Immutable backups** (WORM) for ransomware protection. Test restores monthly. **Backup** is the copy of data; **Disaster Recovery** is the plan and process to restore operations and data to a functional state after a disaster.

**OP20 — Hard:** **802.1X** works via a **Supplicant** (client), **Authenticator** (switch port), and **Authentication Server** (RADIUS). **EAP-TLS** uses certificates (high security), **PEAP** uses passwords (easier). The server assigns a **Dynamic VLAN**. If a device fails authentication, the port is usually shut down or placed in a restricted VLAN. **MAB** (MAC Authentication Bypass) allows a device that doesn't support 802.1X to authenticate based solely on its MAC address, often placing it in a restricted guest VLAN.
