**K1 — Easy:** A **Deployment** manages stateless applications, ensuring a specified number of replica pods are running. It handles scaling and rolling updates. A **StatefulSet** manages stateful applications, providing stable, unique network identities (DNS names) and persistent storage for each pod, ensuring pods start and stop in a specific order.

**K2 — Easy:** A ClusterIP Service creates a virtual IP (ClusterIP) internal to the cluster. The `kube-proxy` component runs on every node and uses iptables or IPVS to set up forwarding rules. When traffic hits the ClusterIP, `kube-proxy` routes it to the backend Pods matching the Service selector via the Endpoints list.

**K3 — Medium:** A **PersistentVolume (PV)** is a cluster-level resource representing actual storage (e.g., a disk) that is provisioned by an administrator. A **PersistentVolumeClaim (PVC)** is a request for storage by a user/pod. A **StorageClass** defines the "class" of storage (e.g., SSD, HDD) and the provisioner used to dynamically create PVs for PVCs. The relationship is: PVC requests storage -> StorageClass provisions a PV -> Pod mounts the PV.

**K4 — Medium:** Troubleshooting steps:
1.  **Check Events:** Run `kubectl describe pod` to see why the pod failed (e.g., ImagePullBackOff, CrashLoopBackOff).
2.  **Check Logs:** Run `kubectl logs` to see the error message inside the container.
3.  **Verify Image:** Ensure the container image name and tag are correct and accessible.
4.  **Check Resources:** Verify if the pod is being killed due to OOMKilled (Out Of Memory) or insufficient CPU.

**K5 — Medium:** CoreDNS is a DNS server for the Kubernetes cluster, providing DNS records for Services and Pods. It allows pods to resolve internal service names (e.g., `my-service.default.svc.cluster.local`). If CoreDNS pods are down, pods cannot resolve internal DNS names, breaking service discovery and connectivity to other services.

**K6 — Hard:** The scheduler uses a two-phase algorithm:

2.  **Scoring:** Assigns a score to each remaining node based on heuristics (e.g., node resource utilization, inter-node affinity/anti-affinity, pod affinity).
3.  **Selection:** The node with the highest score is chosen.
**Factors considered:** Resource availability (CPU/Memory), Taints and Tolerations, NodeSelectors, and Pod Affinity rules.

You would choose **Recreate** for databases or applications that cannot handle simultaneous connections or require a clean state during deployment.

**K11 — Easy:** A **Namespace** provides logical isolation of resources within a cluster. Default namespaces created in a new cluster are: `kube-system` (system components), `default` (user resources), and `kube-public` (publicly readable data).

**K12 — Easy:** `kubectl describe pod <name>` is used to inspect the detailed state of a pod. It shows information `kubectl get` does not, such as: **Events** (reasons for failures), **Node Name**, **IP Address**, **Init Container Status**, and **Conditions** (e.g., `Ready`, `Initialized`).

**K13 — Easy:** A **ConfigMap** is an API object used to store non-confidential data in key-value pairs. Pods consume it via: 1. **Environment Variables** (injecting values), or 2. **Volume Mount** (mounting the ConfigMap as a file inside the container).

**K18 — Hard:** Kubernetes uses **etcd** for storage, which provides **strong consistency** (linearizability). **K20 — Hard:** The `ndots` setting in `/etc/resolv.conf` determines how many dots are required for a name to be considered a Fully Qualified Domain Name (FQDN). If `ndots` is high (e.g., 5), CoreDNS will query the local DNS first (e.g., `api.mycompany.local`) before querying the internet. ```yaml

## Development (20 questions)

**D1 — Easy:** **Git Rebase** rewrites history to create a linear sequence of commits, making the history cleaner. **Git Merge** preserves the full branching history. Avoid rebasing when you have already shared your branch with others, as it rewrites commits and can cause confusion or data loss for collaborators.

**D2 — Easy:** **TCP** (Transmission Control Protocol) is connection-oriented and reliable (guarantees delivery). **UDP** (User Datagram Protocol) is connectionless and fast (no guarantees). Examples: TCP = HTTP, SMTP; UDP = DNS, VoIP.

**D3 — Medium:** A **race condition** occurs when the outcome of a computation depends on the sequence or timing of uncontrollable events. **Example:** In a multi-threaded environment, two threads increment a shared counter `count++`. If they read the value 10 simultaneously, both write 11, resulting in a lost increment.

**D4 — Medium:** Troubleshooting a 503 error:
1.  **Upstream Status:** Check if the backend service is actually running and healthy.
2.  **Database:** Check if the database is reachable and responding.
3.  **Load Balancer:** Check if the Load Balancer's health checks are passing.
4.  **Logs:** Check application logs for errors indicating the service is overloaded or unavailable.

**D5 — Medium:** A **container image layer** is a read-only filesystem snapshot. **Layer caching** affects Dockerfile builds by caching layers that haven't changed. If a layer changes, subsequent layers are rebuilt. **Best practice:** Combine commands like `RUN`, `COPY`, and `CMD` into single instructions to minimize the number of layers and maximize cache hits.

**D6 — Medium:** Troubleshooting a 503 error:
1.  **Upstream Service:** Verify the upstream service is running and accepting connections.
2.  **Database:** Check database connectivity and query performance.
3.  **Load Balancer Health Checks:** Ensure the LB is not marking healthy nodes as unhealthy.
4.  **Application Logs:** Look for errors like "Service Unavailable" or "Connection Refused".

**D7 — Hard:** The **CAP theorem** states a distributed system can only provide **C**onsistency, **A**vailability, or **P**artition Tolerance, but not all three simultaneously.
*   **CP Example:** A Relational Database (e.g., PostgreSQL). It sacrifices availability during a network partition to ensure data consistency.
*   **AP Example:** A NoSQL Database (e.g., Cassandra). It sacrifices consistency during a partition to ensure the system remains available.

**D8 — Medium:** **Horizontal Scaling** increases the number of instances (scale out) to handle more load. **Vertical Scaling** increases the resources (CPU/RAM) of a single instance (scale up). Architectural patterns enabling horizontal scaling include **Stateless Services** (e.g., microservices) and **Load Balancing**.

**D9 — Easy:** An **environment variable** is a dynamic-named value that can affect the behavior of running processes. To set one that persists across shell sessions on Linux, use `export VAR_NAME=value`.

**D10 — Easy:** **JSON** (JavaScript Object Notation) is a lightweight data-interchange format primarily used for machine-to-machine communication. **YAML** (YAML Ain't Markup Language) is a human-readable data serialization language. Advantage of JSON: Easier for machines to parse. Advantage of YAML: More readable and concise for humans.

**D11 — Easy:** A **REST API** is an architectural style for designing networked applications using HTTP methods. **GET** retrieves data, **POST** creates data, **PUT** updates existing data, and **DELETE** removes data.

**D12 — Easy:** **Version pinning** involves locking specific versions of dependencies (e.g., `package-lock.json` or `requirements.txt`). It is important for **reproducible builds** to ensure that the exact same code runs in production as it did in development, preventing "it works on my machine" issues.

**D13 — Easy:** A **compiled language** (e.g., C++, Go) is translated into machine code before execution, resulting in high performance. An **interpreted language** (e.g., Python, JavaScript) is executed line-by-line by an interpreter, resulting in slower execution but easier portability.

**D14 — Medium:** A **Reverse Proxy** sits in front of servers and forwards client requests to those servers. It hides server topology and handles SSL. A **Forward Proxy** sits in front of clients and forwards their requests to the internet, often used for caching or bypassing filters. Common Reverse Proxies: Nginx (routing), HAProxy (load balancing). Use case: Nginx for serving static files and routing API traffic.

**D15 — Medium:** A **deadlock** is a situation where two or more processes block each other indefinitely, each waiting for a resource held by the other. The four **Coffman conditions** required for a deadlock are: 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** **Eventual Consistency** means that updates to a distributed system may not be immediately visible to all readers, but will eventually be consistent. **Cassandra** handles this with tunable consistency levels (e.g., `ONE`, `QUORUM`, `ALL`). A client can choose `ONE` for high availability/low latency or `QUORUM` for stronger consistency.

**D17 — Hard:** **mTLS (Mutual TLS)** authenticates both the client and the server. The **Handshake** involves: 1. Server sends its certificate to Client. 2. Client verifies Server cert and sends its own certificate. 3. Server verifies Client cert. 4. Both derive a session key. It is commonly used in **Service Meshes** (like Istio) to secure inter-service communication.

**D18 — Hard:** A **Hash Table** uses an array and a hash function to map keys to indices. **Collision Resolution** strategies include **Chaining** (linked list at each index) and **Open Addressing** (finding the next empty slot). **Time Complexity:** Average case O(1) for all operations; Worst case O(n) (e.g., all keys hash to the same index).

**D19 — Hard:** The **Circuit Breaker** pattern prevents cascading failures in microservices. It has three states: 1. **Closed:** Normal operation, requests pass through. 2. **Open:** Failure threshold reached, requests are rejected immediately (fail fast). 3. **Half-Open:** After a timeout, a few requests are allowed to test if the service is healthy. It relates to **Retry Policies** and **Exponential Backoff** to avoid overwhelming a failing service.

**D20 — Hard:** **Optimistic Concurrency Control** assumes conflicts are rare. It checks if data has changed before writing. **Pessimistic Concurrency Control** assumes conflicts are common and locks data before reading. **Example:** Optimistic uses **Row Versioning** (check version number). Pessimistic uses **SELECT FOR UPDATE** (lock the row). Choose Optimistic for low-conflict reads; Pessimistic for high-conflict writes.
