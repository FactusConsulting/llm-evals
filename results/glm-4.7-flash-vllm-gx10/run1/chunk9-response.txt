### SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A**
The stale data issue is caused by **asynchronous replication**. When the replica in eu-west-1 was promoted, it only contained data up to the last successful WAL (Write Ahead Log) sync. Any transactions committed on the primary in us-east-1 after that sync point were lost. WAL shipping across regions is asynchronous; the primary sends logs, but the replica applies them with network latency (85ms). To quantify data loss, check `pg_stat_replication` on the new primary for `pg_lag`. The data loss window is the time elapsed between the last successful WAL receipt and the failover event.

**SC2-B**
1.  **Import the new primary:** `terraform import aws_db_instance.new_primary <eu-west-1-replica-ARN>`
2.  **Update dependent resources:** Use `terraform state mv` to move the resource ID from the old instance to the new instance, or manually edit the state file to update references (e.g., Route53 records) to point to the new ARN.
3.  **Remove the old instance:** `terraform state rm aws_db_instance.old_primary`
4.  **Apply:** `terraform apply -auto-approve` (ensuring no destroy is triggered).

**SC2-C**
*   **RDS Proxy vs PgBouncer:** Use **RDS Proxy**. It handles connection pool failover gracefully and is optimized for RDS.
*   **Route53:** Configure **Route53 Health Checks** on the old primary. Configure a **Route53 Traffic Policy** or **Failover Routing** to switch DNS to the new primary if the health check fails.
*   **RPO < 1s:** This is impossible with standard RDS cross-region replication (async). You must use **Amazon Aurora Global Database**, which offers synchronous replication to a secondary region, ensuring RPO is effectively zero.
*   **Recommendation:** Yes, use Aurora Global Database. It provides synchronous replication, automatic failover, and built-in point-in-time recovery, meeting the strict RPO/RTO requirements.

### SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

2.  **Local NFS Mount:** Kubernetes pods are ephemeral; local NFS mounts are not. **Solution:** Use a CSI driver (e.g., nfs.csi.k8s.io) to provision a `ReadWriteMany` PersistentVolume.

5.  **Java Heap:** Bare metal allows large RAM; K8s limits this. **Solution:** Set appropriate `resources.requests` and `limits` for memory and CPU.

*   **Hybrid Mesh (Tailscale/Netbird):** Overlay network using WireGuard. NAT traversal is easy. Adds ~1-2ms latency. Fits zero-trust (mTLS built-in). Requires a central management node.

**SC7-C**
*   **Drift Detection:** Run a scheduled CI job (e.g., nightly) with `tofu plan -refresh-only`. If the plan output is not empty, fail the job and alert.
*   **Webhook:** Deploy an OPA Gatekeeper admission webhook that enforces a policy `deny-direct-kubectl-edit` to block `kubectl edit` on specific resources.
*   **Helm:** Use `helmfile` or `kustomize` to enforce a single source of truth for values.
*   **RBAC:** In Kubernetes, create a `ServiceAccount` for the CI pipeline with `roles` restricted to `deployments`, `configmaps`, etc., and no `edit` or `admin` permissions. In AWS, use IAM policies that restrict actions to specific resources.

### SC8 — Hard — Observability Stack Scaling Failure

**SC8-A**
1.  **Prometheus OOM:** 8.2 million active series is massive. Each series consumes ~1-2MB of RAM. 64GB is insufficient. The root cause is **high cardinality** (too many unique labels).
2.  **Loki Drops:** The ingester cannot keep up with the ingestion rate. 15% drop indicates the write path is saturated.
3.  **Tempo Timeout:** Local storage is likely full or the query is too complex for the in-memory index.
4.  **Thanos Lag:** Compaction is CPU/IO bound. 3 days behind means the cluster cannot process the backlog.

**SC8-B**
```bash
#!/bin/bash
echo "=== Prometheus Cardinality Report ==="
echo "Total Unique Metrics:"
curl -s http://prometheus:9090/api/v1/label/__name__/values | jq '.data | length'

echo -e "\nTop 20 Metrics by Series Count:"
curl -s 'http://prometheus:9090/api/v1/label/__name__/values' | jq -r '.data[]' | while read metric; do
  count=$(curl -s "http://prometheus:9090/api/v1/query?query=count(${metric})" | jq -r '.data.result[0].value[1]')
  echo "$metric: $count"
done | sort -t: -k2 -rn | head -n 20

echo -e "\nMetric with highest cardinality:"
HIGHEST=$(curl -s 'http://prometheus:9090/api/v1/label/__name__/values' | jq -r '.data[]' | while read metric; do
  count=$(curl -s "http://prometheus:9090/api/v1/query?query=count(${metric})" | jq -r '.data.result[0].value[1]')
  echo "$count $metric"
done | sort -rn | head -n 1 | awk '{print $2}')
echo "Metric: $HIGHEST"
```

**SC8-C**
*   **TSDB:** Replace Prometheus with **VictoriaMetrics Cluster** or **Grafana Mimir**. These are designed for high cardinality and cost-effective storage.
*   **Loki:** Deploy in **microservices mode** (separate ingester, querier, compactor) to scale read/write paths independently.
*   **Tempo:** Switch to **S3-backed** backend to offload storage.
*   **Governance:** Implement **Recording Rules** to downsample high-cardinality metrics (e.g., aggregate by 5-minute buckets). Enforce **Relabeling** to drop high-cardinality labels (like pod names) at the scrape level.

### SC9 — Medium — Securing a Public-Facing API After a Breach

**SC9-A**
1.  **BOLA (OWASP API Top 10 #1):** Violates **Authorization**. **Fix:** Implement object-level permissions in the serializer (Django) to check `request.user.id == obj.user_id`.
2.  **Information Disclosure:** Violates **Confidentiality**. **Fix:** Use `Meta.fields` in Django REST Framework serializers to exclude internal fields.
3.  **No Rate Limiting:** Violates **Availability**. **Fix:** Implement WAF or API Gateway rate limiting.
4.  **API Keys in URL:** Violates **Security** (Credential Exposure). **Fix:** Move to Authorization headers and rotate keys.

**SC9-B**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {
  name        = "api-waf"
  description = "WAF for public API"
  scope       = "REGIONAL"
  default_action {
    allow {}
  }

  rule {
    name     = "RateLimit"
    priority = 1
    override_action {
      none {}
    }
    statement {
      rate_based_statement {
        limit              = 100
        aggregate_key_type = "IP"
      }
    }
  }

  rule {
    name     = "BlockQueryKeys"
    priority = 2
    override_action {
      none {}
    }
    statement {
      byte_match_statement {
        field_to_match {
          single_header {
            name = "X-API-Key"
          }
        }
        positional_constraint = "EXACTLY"
        text_transformation   = "URL_DECODE"
        target_string         = "api_key"
      }
    }
  }
  
  # Add Managed Rule Groups for SQLi/XSS and Geo Block
}
```

**SC9-C**
*   **Auth:** Migrate to **OAuth2 (JWT)** using a provider like Auth0 or AWS Cognito. Rotate all old keys.
*   **Gateway:** Deploy **Kong** or **AWS API Gateway** in front of the ALB. It handles auth, rate limiting, and request transformation.
*   **Audit:** Enable **CloudTrail Data Events** for API calls.
*   **Encryption:** Implement **Field-Level Encryption** (e.g., using AWS KMS) for PII in the database.
*   **Migration:** Use a dual-write strategy or a versioned API endpoint (e.g., `/v2/`) that accepts the new OAuth2 token, while keeping `/v1/` for legacy clients for a transition period.

### SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A**
*   **Active-Passive (Velero):** RPO depends on backup frequency (minutes). RTO depends on restore time (hours). **200TB MinIO** makes restore impossible within RTO.
*   **Active-Active (Istio):** Traffic routing is instant. RPO/RTO met if traffic switches fast. **PostgreSQL:** Use synchronous replication (requires Aurora or Patroni with `synchronous_standby_names`). **MinIO:** Async replication is too slow for RPO < 15m. **Verdict:** Active-Active is viable for app and DB, but MinIO requires a different strategy (e.g., active-active with async replication accepting RPO, or a separate DR strategy for MinIO).
*   **Replication Strategy:**
    *   PostgreSQL: Synchronous replication (Aurora or Patroni).
    *   Redis: Sentinel or Cluster replication.
    *   RabbitMQ: Federation or Mirroring.
    *   MinIO: Active-Active replication (async) or separate DR bucket.

**SC10-B**

**SC10-C**
1.  **Failure Detection:** Health checks on Chicago nodes (Kubelet, App probes). If Chicago is unreachable, trigger failover.
2.  **DNS Failover:** **GSLB** (Global Server Load Balancer) switches DNS records to Dallas.
3.  **Promotion:** Patroni detects etcd quorum loss in Chicago and promotes Dallas to primary.
4.  **Redis:** Sentinel promotes Dallas replica to master.
5.  **RabbitMQ:** Federation mirrors queues to Dallas.
6.  **MinIO:** Replication catches up.
7.  **Split-Brain:** Patroni uses etcd quorum. If Chicago returns, it becomes secondary.
8.  **Failback:** Once Chicago is healthy, trigger a manual failback via the Patroni API or operator to demote Dallas.
