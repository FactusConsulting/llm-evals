```bash
# Get total metric names
TOTAL_METRICS=$(curl -s http://prometheus:9090/api/v1/label/__name__/values | jq '.data | length')
echo "Total Unique Metric Names: $TOTAL_METRICS"

# Get top 20 metrics by series count
TOP_METRICS=$(curl -s 'http://prometheus:9090/api/v1/query?query=count({__name__=~".+"}) by (__name__)' | jq -r '.data.result[] | "\(.metric.__name__)\t\(.value[1])"')
echo "Top 20 Metrics by Series Count:"
echo "$TOP_METRICS" | sort -t$'\t' -k2 -rn | head -n 20

# Find highest cardinality metric and its top label
MAX_METRIC=$(echo "$TOP_METRICS" | sort -t$'\t' -k2 -rn | head -n 1 | cut -f1)
echo "Highest Cardinality Metric: $MAX_METRIC"

# Get top label for this metric
TOP_LABEL=$(curl -s "http://prometheus:9090/api/v1/query?query=count({__name__=\"$MAX_METRIC\"}) by (label)" | jq -r '.data.result[] | "\(.metric.label)\t\(.value[1])"' | sort -t$'\t' -k2 -rn | head -n 1 | cut -f1)
echo "Label with most unique values for $MAX_METRIC: $TOP_LABEL"
```

**SC8-C**
*   **Metrics Store:** Replace Prometheus with **VictoriaMetrics Cluster** or **Grafana Mimir**. These are designed to handle high cardinality and scale horizontally.
*   **Logs:** Deploy Loki in **microservices mode** (separate ingester, querier, compactor) to handle high ingestion rates and separate read/write paths.
*   **Traces:** Switch Tempo backend from local to **S3** (or MinIO) to handle large trace volumes and improve query performance.
*   **Governance:** Implement **Recording Rules** to aggregate high-cardinality metrics into lower-cardinality summaries. Use **Relabeling** to drop unnecessary labels (e.g., `kubernetes_pod_name` if not needed). Enforce a **cardinality limit per team** (e.g., 1M series per team).
*   **Chargeback:** Tag all metrics and logs with the owning team. Use the observability platform's cost reporting features (or integrate with AWS Cost Explorer) to bill teams based on storage used and query volume.

**SC9-A**
1.  **BOLA (Broken Object Level Authorization):** Violates OWASP API Security #1. Blast radius: Full data breach. Fix: Implement object-level permissions in Django DRF (e.g., `IsOwner` or custom permission class).
    ```python
    class IsOwner(permissions.BasePermission):
        def has_object_permission(self, request, view, obj):
            return obj.user == request.user
    ```
2.  **Excessive Data Exposure:** Violates OWASP API Security #2. Blast radius: Internal data leakage. Fix: Use `Meta.fields` in DRF Serializers to exclude sensitive fields (e.g., `created_by_employee_id`, `internal_notes`).
3.  **No Rate Limiting:** Violates OWASP API Security #3. Blast radius: DoS/DDoS. Fix: Implement rate limiting middleware or use AWS WAF.
4.  **API Keys in URL:** Violates OWASP API Security #4. Blast radius: Key exposure. Fix: Move API keys to HTTP Headers (`Authorization: Bearer <key>`).

**SC9-C**
*   **Authentication:** Move API keys to Headers. Rotate all compromised keys immediately.
*   **OAuth2:** Implement OAuth2 with short-lived JWTs (e.g., 5 minutes) using an Identity Provider (IdP) like Auth0 or Okta.
*   **API Gateway:** Deploy Kong or AWS API Gateway in front of the ECS Fargate. This provides centralized auth, rate limiting, request transformation (to strip query params), and logging.
*   **Auditing:** Enable **CloudTrail Data Events** to log every API call.
*   **Field Encryption:** Implement field-level encryption for PII in the database (e.g., using PostgreSQL's pgcrypto or application-level encryption).
*   **Migration:** Version the API (e.g., `/v2/`). Update the ALB listener to route `/v2/` to the new secured endpoint. Redirect `/v1/` to `/v2/` for backward compatibility.

**SC10-A**
*   **Active-Passive (Velero):** RPO depends on backup frequency. With 200TB of MinIO, a full backup is impossible for RPO 15 mins. RTO depends on restore speed. This approach fails the RPO requirement.
*   **Active-Active (Istio/Cilium):** RPO is determined by replication lag (12ms). RTO is near-instant (seconds) because traffic is routed instantly. This meets requirements.
*   **Replication Strategy:**
    *   **PostgreSQL:** Streaming replication with synchronous commit (or very tight async) to Dallas.
    *   **Redis:** Sentinel or Cluster replication.
    *   **RabbitMQ:** Mirroring queues or Federation.
    *   **MinIO:** Erasure coding or replication (MinIO Gateway or native replication).

**SC10-C**
1.  **Failure Detection:** Use **Keepalived** or **HAProxy** on the control plane to monitor the health of the Chicago nodes. If the control plane is unreachable, trigger failover.
2.  **DNS Failover:** Use **Route53 Health Checks** on the Chicago primary endpoint. When the check fails, Route53 updates the DNS record to point to the Dallas IP.
3.  **Promotion:** Patroni detects the loss of quorum (etcd) and promotes the Dallas node to primary.
4.  **Redis:** Sentinel detects the master is down and promotes a replica in Dallas.
5.  **RabbitMQ:** The federation plugin replicates queues to Dallas. If Chicago goes down, the Dallas nodes take over.
6.  **MinIO:** The replication process in Dallas catches up on the data that was written to Chicago.
7.  **State Update:** Terraform state is updated to reflect the new primary (though in an active-active setup, this might be less critical than in active-passive).
8.  **Split-Brain:** Prevented by using **etcd quorum**. Only the node with the majority of votes can promote itself.
9.  **Failback:** Once Chicago is healthy, promote it back to primary. Drain Dallas to ensure no writes are happening there. Update DNS back to Chicago.
