**CL1 — Easy:** IaaS (Infrastructure as a Service) provides virtualized computing resources over the internet (e.g., AWS EC2, Azure VMs). You manage the OS and applications. PaaS (Platform as a Service) provides a platform allowing you to deploy applications without managing the underlying infrastructure (e.g., AWS Elastic Beanstalk, Google App Engine). SaaS (Software as a Service) provides complete software applications over the internet (e.g., Salesforce, Microsoft 365). The provider manages everything.

**CL2 — Easy:** The Shared Responsibility Model defines security duties. For **IaaS VMs**, the provider secures the physical hardware and network, while you secure the OS, runtime, data, and applications. For **managed Kubernetes**, the provider secures the control plane and underlying nodes, while you secure the workloads, configuration, and runtime. For **SaaS (M365)**, the provider secures the entire platform, while you manage user identities and data privacy settings.

**CL3 — Medium:** A **VPC** is a virtual private network within a cloud provider's region. A **Subnet** is a range of IP addresses within a VPC. A **Security Group** is a virtual firewall at the instance level (stateful). A **NACL** is a firewall at the subnet level (stateless). They layer together: Traffic enters via the VPC, is filtered by NACLs (Subnet level), then by Security Groups (Instance level). Stateful filtering (Security Groups) remembers connections, allowing return traffic automatically; stateless filtering (NACLs) requires explicit rules for both directions.

**CL4 — Medium:** A **Landing Zone** is the foundational multi-account structure providing network connectivity, identity management, and governance. **Organizational Units (OUs)** group accounts for management. **Guardrails** (e.g., AWS OPA Gatekeeper) enforce policies. **Shared Networking** (e.g., Transit Gateway) connects accounts centrally. **Centralized Logging** aggregates CloudTrail and VPC Flow Logs. A single-account approach is problematic because it lacks isolation; a security breach or misconfiguration can impact the entire organization, and billing/management becomes unscalable.

**CL5 — Medium:** **Infrastructure as Code (IaC)** is managing infrastructure through code and version control. **Terraform/OpenTofu** uses HCL and is provider-agnostic. **Pulumi** uses general-purpose programming languages (Python/Go) and is more flexible for complex logic. **CloudFormation/Bicep** are declarative JSON/YAML templates specific to AWS/Azure. **Crossplane** extends Kubernetes to manage cloud resources. Choose Terraform for broad portability, Pulumi for language preference, CloudFormation for AWS-only speed, and Crossplane for K8s-native infra.

**CL6 — Medium:** **HPA** scales pods based on CPU/Memory metrics. **VPA** scales pods by adjusting resource requests. **Cluster Autoscaler** scales the node pool based on pending pods. **KEDA** scales pods based on external event queues (e.g., Kafka, RabbitMQ). Use **KEDA over HPA** when your application's load is driven by external events or message backlogs rather than just raw compute resources.

## OT Infrastructure Architecture

**OT1 — Easy:** The **Purdue Model** (ISA-95) standardizes industrial automation levels. **Level 0:** Field devices (sensors/actuators). **Level 1:** PLCs/RTUs (control). **Level 2:** Control systems (SCADA/DCS). **Level 3:** Manufacturing Operations Management (historians, MES). **Level 4:** Business Systems (ERP, CRM).

**OT2 — Easy:** **IT** focuses on data processing, storage, and communication. **OT** focuses on the physical control of machinery and processes. You cannot apply standard IT patching practices to OT because a reboot or incompatible patch can cause immediate physical damage, production stoppages, or safety hazards.

**OT3 — Medium:** An **IDMZ (Industrial DMZ)** acts as a security buffer between the corporate IT network and the OT network. **Traffic:** IT sends reports to OT; OT sends alarms to IT. **Direction:** Generally IT -> OT (read-only) and OT -> IT (alerts). Direct connectivity from Level 4 (IT) to Level 1 (control) is dangerous because it bypasses safety layers and control logic, allowing unauthorized manipulation of physical processes.

**OT4 — Medium:**
1.  **Modbus TCP:** Industrial protocol for reading/writing registers. (Level 2)
2.  **OPC UA:** Secure, platform-independent protocol for industrial automation. (Level 3)
3.  **EtherNet/IP (CIP):** Industrial protocol over Ethernet. (Level 2)
4.  **PROFINET:** Industrial Ethernet protocol. (Level 2)
5.  **MQTT:** Lightweight publish/subscribe messaging protocol. (Level 3)

**OT5 — Medium:** A **Data Diode** is a hardware device that allows data to pass in only one direction (unidirectional). A **Firewall** allows bidirectional traffic based on rules. Use a **hardware data diode** when you need guaranteed physical security and unidirectional data flow (e.g., sending data to the cloud). The limitation is that you cannot receive data back through the diode.

**OT6 — Medium:** **Data Flow:** Process data is collected by the **Historian** (Level 3). The Historian exposes data via an **OPC UA Server**. An **Edge Gateway** subscribes to the OPC UA data and pushes it to an **MQTT Broker**. The Cloud ingests the MQTT data. **Security Boundaries:** The Edge Gateway acts as the primary security boundary; it should perform protocol translation, filtering, and encryption before sending data to the cloud.

**OT7 — Hard:** **IEC 62443 Zones and Conduits:** A **Zone** is a logical grouping of assets with a common security level and access policy. A **Conduit** is a controlled path (usually a firewall) between zones. **Design:** **Corporate Network (Z4)** connects via a conduit to **Engineering Workstations (Z3)**. **SCADA Servers (Z3)** connect via a conduit to **PLCs (Z2)**. **SIS (Z1)** is isolated (air-gapped) from the BPCS (Z2) and IT (Z4).

**OT8 — Hard:** **Network Segmentation Strategy:** Create **VLANs** for each production line (Z2) and a separate VLAN for engineering (Z3). Place **Firewalls** between VLANs to enforce the Zone/Conduit model. Use **Layer 3 Switches** to route traffic. For remote access, use a **VPN** with a **Jump Host** and MFA. **Transition:** Perform a "cutover" during a scheduled maintenance window, or use a "phased" approach where new VLANs are created and traffic migrated while old VLANs remain active.

**OT9 — Hard:** **SIS** is dedicated to safety (stopping the process if dangerous). **BPCS** is for normal process control. **IEC 61511** is the standard for safety instrumented systems. The SIS network must be isolated to prevent malware from corrupting safety logic. If ransomware reaches the SIS, it could disable safety functions, leading to catastrophic physical damage or environmental release.

**OT10 — Medium:** **PLC** (Programmable Logic Controller) is for discrete control (on/off) in small to medium setups. **DCS** (Distributed Control System) is for continuous process control (temperature/pressure) in large plants. **SCADA** (Supervisory Control and Data Acquisition) is for supervisory monitoring and control over multiple locations. They can coexist; for example, a DCS controls the process, while a SCADA system monitors the DCS and provides remote access.

**OT11 — Medium:** **Remote Access Architecture:** Use a **Jump Host** (bastion) in the IDMZ. Require **MFA** for all access. Implement **Session Recording** for auditing. Use **Vendor Access** portals with time-limited credentials. **RDP directly to an HMI** is unacceptable because it bypasses the IDMZ, jump host, and MFA controls, creating a direct attack vector into the OT network.

**OT12 — Hard:** **Detection and Response Plan:** Deploy **IDS/IPS** and **Anomaly Detection** on the network. Maintain a live **Asset Inventory**. **Incident Response:** Isolate the compromised network segment immediately. Coordinate with the **Control Room** to ensure safe operations (manual override if needed). **Operator Role:** The operator is the final line of defense; they must be trained to recognize anomalies and execute safe shutdown procedures if the system is compromised.

**OT13 — Easy:** A **HMI** (Human-Machine Interface) is a graphical screen used by operators to visualize and control machinery. It plays a role in monitoring and basic control. It differs from an **Engineering Workstation**, which is used by technicians to configure, program, and debug the control logic.

**OT14 — Easy:** A **Historian** stores time-series data from the process for analysis and trending. It is crucial for performance optimization and troubleshooting. A **Plant Historian** (Level 3) stores data for the local plant. An **Enterprise Historian** (Level 4) aggregates data from multiple plants for corporate-level analysis.

**OT15 — Easy:** **Ladder Logic** is a graphical programming language based on electrical relay logic. It is executed by a **PLC**. It remains dominant because it is intuitive for electricians, widely understood, and legacy codebases are extensive.

**OT16 — Easy:** An **RTU** (Remote Terminal Unit) is a microprocessor-controlled device that interfaces with field devices in remote locations. It differs from a **PLC** (which is usually local) by being designed for harsh environments and remote telemetry. RTUs are typically used in utility, pipeline, and SCADA applications.

**OT17 — Easy:** **Analog signals** (4-20mA, 0-10V) represent continuous values. **Digital signals** represent discrete states (on/off). **4-20mA** is preferred over 0-20mA because the "4 mA" offset provides a live-zero, allowing the system to detect a broken wire or open circuit (zero current = no signal = fault).

**OT18 — Medium:** **Asset Inventory** is the foundation of OT security because you cannot protect what you do not know exists. **Tools:** Passive network monitoring (sniffing traffic) to discover assets without impacting operations. **Active scanning** (pinging/OS fingerprinting) is dangerous because it can cause PLCs to reboot or disrupt real-time control loops.

**OT19 — Hard:** **MITRE ATT&CK for ICS** is a knowledge base of adversary tactics and techniques specific to industrial control systems. **Tactics:** Resource Development, Initial Access, Execution, Persistence, Defense Evasion, Impact. **Example Techniques:** Exploiting Public-Facing Application (Initial Access), Modbus Enumeration (Discovery), PLC Firmware Modification (Persistence), Logic Bomb (Defense Evasion), Safety Instrumented System Disabling (Impact). It differs from the enterprise matrix by focusing on physical impact and specific ICS protocols. It is used to assess defensive gaps by mapping detected threats to these techniques.

**OT20 — Hard:** **Converged SOC:** Collect logs via **Syslog** or **OPC UA** without impacting real-time operations (using passive collectors). Integrate with a **SIEM**. Use **OT-specific detection rules** (e.g., unexpected Modbus writes). **Staffing:** Requires a mix of IT analysts and OT engineers. **False Positives:** OT engineers must tune rules to minimize false alarms to avoid alert fatigue. **Handling Firmware Alert:** Immediately isolate the affected PLC, investigate the alert, and if confirmed, revert to a known good firmware image or safe state.
