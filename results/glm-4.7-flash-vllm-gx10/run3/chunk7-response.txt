**AA1 — Easy:** A **monolith** is a single, indivisible codebase where all components (UI, business logic, data access) run together. A **microservices** architecture decomposes the application into small, independent services that communicate over the network.
*   **3 Problems introduced by Microservices:**
    1.  **Distributed Tracing:** Debugging issues across multiple services and networks is significantly harder than in a single process.
    2.  **Data Consistency:** Managing transactions across different databases (ACID vs. BASE) is complex (e.g., the Saga pattern).
    3.  **Operational Overhead:** You must manage the lifecycle, scaling, and networking of many more services than a single monolith.

**AA2 — Easy:** **Synchronous** communication requires the caller to wait for a response (e.g., REST/gRPC). **Asynchronous** communication decouples the sender and receiver; the sender publishes a message and moves on (e.g., RabbitMQ, Kafka).
*   **Example Tech:** Synchronous = HTTP/REST; Asynchronous = Apache Kafka.

**AA3 — Medium:** An **API Gateway** acts as a single entry point for clients, handling routing, authentication, rate limiting, and protocol translation. A **Reverse Proxy** is a server that sits in front of a web server (like Nginx) to handle SSL termination, caching, and load balancing for a specific application.
*   **Can it replace a reverse proxy?** No. While an API Gateway can handle basic routing, a dedicated reverse proxy is often better suited for static asset serving, SSL offloading at the edge, and caching, which are distinct from API management logic.

**AA4 — Medium:** The **Saga pattern** is a design pattern for managing distributed transactions. Instead of a global transaction, a saga breaks the operation into a sequence of local transactions, each updating the database and publishing an event.
*   **Choreography vs. Orchestration:**
    *   *Choreography:* Services communicate by listening to events and reacting. No central coordinator.
    *   *Orchestration:* A central orchestrator (like a state machine) tells services what to do and handles compensation.
*   **When to use:** Use choreography for simpler flows with low coupling. Use orchestration for complex flows where a central brain is needed to manage state and compensation logic.

**AA5 — Medium:** **CQRS** (Command Query Responsibility Segregation) separates the read and write models of an application. **Event Sourcing** stores the state of an entity as a sequence of state-changing events rather than just the current state.
*   **Why paired:** Event Sourcing provides the immutable log needed for CQRS to rebuild the current state for reads. This combination solves the problem of **complex reporting and analytics** (you can query the event log for historical data) and allows for **optimistic concurrency** and **event replay**, which a traditional CRUD model (which only stores the "now") cannot easily support.

**AA6 — Medium:** The **Circuit Breaker** pattern prevents a service from being overwhelmed by failing dependencies. It stops requests when a failure threshold is reached.
*   **States:** Closed (Normal operation), Open (Circuit tripped, requests fail immediately), Half-Open (Allows a few requests to test if the dependency is recovered).
*   **Difference from Retry:** A retry blindly sends requests, potentially worsening the failure. A Circuit Breaker stops sending requests to prevent cascading failures.
*   **Using both:** You use a Circuit Breaker to stop calling a failing service, and a Retry with Backoff to attempt to recover from temporary blips (e.g., network hiccups) *before* tripping the circuit.

**AA7 — Hard:**
1.  **Shared DB, Shared Schema (Row-level):** *Pros:* Cheapest, lowest complexity. *Cons:* Security risk (tenant ID leakage), high noisy-neighbor risk (one tenant's heavy query affects others), difficult to scale DB schema changes.
2.  **Shared DB, Separate Schema:** *Pros:* Better isolation than row-level, easier to scale DB instances per tenant. *Cons:* Higher cost (more DB instances), moderate complexity, still risks noisy neighbors if not managed well.
3.  **Separate DB per Tenant:** *Pros:* Maximum security, maximum isolation, no noisy neighbors. *Cons:* Highest cost, highest operational complexity (scaling, backups, patching).

**AA8 — Hard:** **Strong consistency** ensures all nodes see the same data at the same time. **Eventual consistency** allows temporary discrepancies.
*   **Inventory Architecture:** To prevent overselling, you must use **Strong Consistency**.
*   **Tech:** Use a database with strong consistency guarantees (e.g., PostgreSQL with row-level locking, or a distributed SQL database like CockroachDB/Spanner).
*   **Patterns:** Use **Optimistic Locking** (check version, update) or **Pessimistic Locking** (SELECT FOR UPDATE) to ensure inventory is reserved atomically.

**AA9 — Hard:** A **sidecar proxy** is a container that runs alongside a main application container, sharing the same network namespace, to handle cross-cutting concerns like observability and security.
*   **Envoy in Istio:** Envoy is the **Data Plane** (proxy) that handles traffic routing, mTLS, and metrics. Istio is the **Control Plane** (Pilot, Citadel, Galley) that manages the Envoy proxies and configures them.
*   **mTLS Problem:** Application-level TLS requires every service to manage certificates and keys. mTLS between sidecars provides mutual authentication and encryption transparently to the application, simplifying security management and preventing man-in-the-middle attacks.

**AA10 — Medium:** The **Strangler Fig pattern** involves gradually replacing parts of a legacy system with new services, effectively "strangling" the old system over time.
*   **Migration Strategy:**
    1.  Build a reverse proxy (e.g., Nginx) that sits in front of the legacy .NET app.
    2.  Identify a small, well-defined API endpoint in the legacy app (e.g., `/api/users/get`).
    3.  Create a new .NET 8 microservice for this endpoint.
    4.  Configure the proxy to route traffic for `/api/users/get` to the new microservice and the rest to the legacy app.
    5.  Repeat this process for other endpoints, slowly migrating the entire application until the legacy monolith is decommissioned.

**AA11 — Medium:** The **12-Factor App** methodology is a set of best practices for building SaaS apps.
*   **6 Factors & Why:**
    1.  **Codebase:** One codebase tracked in revision control. *Why:* Enables CI/CD and collaboration.
    2.  **Dependencies:** Explicitly declare and isolate dependencies. *Why:* Ensures consistency across environments.
    3.  **Config:** Store config in the environment. *Why:* Separates code from infrastructure settings.
    4.  **Backing Services:** Treat backing services (DBs, caches) as attached resources. *Why:* Allows easy swapping of infrastructure.
    5.  **Build, Release, Run:** Strict separation of build, release, and run stages. *Why:* Ensures reproducible deployments.
    6.  **Processes:** Execute the app as one or more stateless processes. *Why:* Enables horizontal scaling.

**AA12 — Hard:**
*   **Coupling:** Event-driven (Kafka) is loosely coupled; Request-driven (REST) is tightly coupled.
*   **Scalability:** Event-driven scales better for bursty workloads; Request-driven scales well for request-response patterns.
*   **Debugging:** Request-driven is easier to debug (stack traces); Event-driven is harder (distributed tracing required).
*   **Ordering:** Request-driven offers end-to-end ordering; Event-driven offers ordering only per partition/consumer group.
*   **Failure Handling:** Event-driven is more resilient to network blips (messages are buffered); Request-driven fails fast.
*   **Choice:** Choose **Request-driven (REST/gRPC)** for internal service-to-service communication where low latency and debugging are critical. Choose **Event-driven (Kafka)** for decoupling external systems, background processing, or when dealing with high throughput and eventual consistency needs.

**AA13 — Easy:** A **load balancer** distributes incoming network traffic across multiple servers to ensure no single server bears too much load.
*   **L4 vs L7:** **L4** (Transport) makes decisions based on IP and Port (TCP/UDP). **L7** (Application) makes decisions based on content (HTTP headers, URLs, cookies).
*   **L7 Use Case:** Routing traffic based on the URL path (e.g., `/api` goes to Service A, `/static` goes to Service B) or A/B testing.

**AA14 — Easy:** A **message queue** (e.g., RabbitMQ) is a buffer that holds messages for consumers to process at their own pace. A **log-based broker** (e.g., Kafka) is a distributed commit log designed for high throughput and storing data for long periods.
*   **Difference:** Queues are typically point-to-point (one consumer). Log brokers are publish-subscribe (many consumers).
*   **Choice:** Use **RabbitMQ** for task queues requiring reliability, ordering, and complex routing. Use **Kafka** for high-throughput data pipelines, log aggregation, or event sourcing where replayability is key.

**AA15 — Easy:** A **container** is a lightweight, standalone package of software that includes everything needed to run it: code, runtime, system tools, libraries, and settings. A **VM** is a full virtual machine with a hypervisor, a guest OS, and the application.
*   **Popularity:** Containers are popular for microservices because they are lightweight (seconds to start), portable (runs anywhere), and have a smaller footprint than VMs, allowing for higher density.

**AA16 — Easy:** **Stateless** services do not store local data (session state) and rely on external storage (like a database) for persistence. **Stateful** services maintain local state (e.g., in-memory caches, file systems).
*   **Scaling:** Stateless services are easier to scale horizontally because you can spin up multiple instances without worrying about data synchronization or conflicts.
*   **Examples:** Stateless = API Gateway, Auth Service; Stateful = Database, Session Store.

**AA17 — Easy:** An **ORM** (Object-Relational Mapper) maps database records to objects in code, allowing developers to interact with the DB using code objects.
*   **Examples:** Hibernate (Java), Entity Framework (C#), SQLAlchemy (Python).
*   **Trade-offs:** ORMs abstract SQL, speeding up development and reducing boilerplate. However, they can generate inefficient SQL, hide database-specific features, and introduce "impedance mismatch" complexity.

**AA18 — Medium:** The **Bulkhead pattern** isolates parts of a system to prevent a failure in one area from cascading to the whole system.
*   **Relation:** In microservices, it prevents a slow or failing service from consuming all resources (threads, memory) of a dependent service.
*   **Implementation:** Use separate thread pools for different services or deploy critical services in separate deployment groups (e.g., a separate Kubernetes namespace or VM cluster) with dedicated resources.

**AA19 — Hard:**
*   **Operational Transformation (OT):** Modifies operations to make them compatible. *Pros:* Strong consistency, low latency. *Cons:* High complexity, difficult to support offline editing (requires merging history).
*   **CRDTs:** Conflict-free Replicated Data Types. *Pros:* Extremely simple math, supports offline editing perfectly, eventual consistency. *Cons:* Higher latency (due to replication), potentially larger data size.
*   **Choice:** For a system requiring **offline editing**, **CRDTs** are the superior choice. The complexity of OT makes it very hard to handle offline scenarios robustly, whereas CRDTs are designed specifically for conflict resolution in disconnected environments.

**AA20 — Hard:** Distributed tracing involves propagating a unique `trace_id` and `span_id` across services to visualize the request flow.
*   **Context Propagation:** Use **W3C Trace Context** (standard headers `traceparent`) or **B3** (Zipkin headers) to pass context headers.
*   **Sampling:** **Head-based** (sample at entry) is efficient but misses backend issues. **Tail-based** (sample at exit) is expensive but catches latency issues at the end of the chain.
*   **Storage:** Use tools like **Jaeger** or **Grafana Tempo** to store and query traces.
*   **Async Messaging:** When a request passes through Kafka, the consumer creates a new span. To ensure continuity, the consumer must extract the parent span ID from the incoming message headers and set it as the parent of the new outgoing span.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** **Type 1 (Bare-metal)** hypervisors run directly on hardware without a host OS (e.g., VMware ESXi, Microsoft Hyper-V). **Type 2 (Hosted)** hypervisors run on top of a host OS (e.g., Oracle VirtualBox, VMware Workstation).
*   **Examples:** Type 1 = ESXi, Hyper-V; Type 2 = VirtualBox, Parallels.

**OP2 — Easy:** A **SAN** (Storage Area Network) provides block-level storage over a dedicated network (e.g., Fibre Channel, iSCSI). A **NAS** (Network Attached Storage) provides file-level storage over a standard IP network (e.g., NFS, SMB).
*   **Use Cases:** SAN for databases and VMs (low latency, block access). NAS for file sharing, backups, and general storage.
*   **Protocols:** SAN = Fibre Channel, iSCSI; NAS = NFS, SMB/CIFS.

**OP3 — Medium:** A **3-tier architecture** (Core, Distribution, Access) uses a hierarchical design where the Core switches connect to Distribution switches, which connect to Access switches.
*   **Leaf-Spine:** A **spine-leaf** architecture is a flat, non-blocking design where all Leaf switches connect to all Spine switches.
*   **Problem Solved:** The 3-tier design creates a single point of failure at the Distribution layer and can become a bottleneck (convergence delay) as the network grows. Leaf-Spine provides full mesh connectivity, eliminates bottlenecks, and scales linearly.

**OP4 — Medium:** **Proxmox Cluster Design:**
*   **Node Count:** Typically 3 or 5 nodes for quorum.
*   **Quorum:** Uses a majority vote system (e.g., 2 out of 3) to prevent split-brain.
*   **Fencing:** Uses `STONITH` (Shoot The Other Node In The Head) to power off a failed node to prevent it from accessing shared storage.
*   **Shared Storage:** **Ceph** (RADOS) is preferred for high availability and resilience. **iSCSI** or **NFS** can be used but are single points of failure if not configured with HA (e.g., DRBD).
*   **Failure:** If a node fails, the remaining nodes maintain quorum and continue serving VMs from the shared storage. If storage fails, services stop.

**OP5 — Medium:** **VLAN Trunking** allows a single physical link to carry traffic for multiple VLANs. **802.1Q tagging** adds a 4-byte header to the Ethernet frame identifying the VLAN ID.
*   **Linux Config:** Use `8021q` module. Create a bridge (e.g., `br0`), add the physical interface (e.g., `eth0`) to the bridge, and then add VLAN interfaces (e.g., `eth0.10`, `eth0.20`) to the bridge.

**OP6 — Medium:**
*   **RAID 1:** Mirroring (2 drives). High performance read, low write, 50% capacity.
*   **RAID 5:** Striping + Parity. Good balance, 1 drive fault tolerance, slower write due to parity calculation.
*   **RAID 6:** Striping + Double Parity. 2 drive fault tolerance, slower write than RAID 5.
*   **RAID 10:** Mirrored stripes. Best performance and fault tolerance, 50% capacity.
*   **RAID Z2:** ZFS implementation of RAID 6.
*   **Choice:** For a **database server** needing performance and fault tolerance, **RAID 10** is usually the best choice. It offers high read/write performance and can survive multiple drive failures (usually 2), though it uses 50% of the raw capacity.

**OP7 — Hard:**
*   **Architecture:**
    *   **Recursive Resolvers:** AD Integrated DNS servers (or Forwarders to ISP).
    *   **Authoritative Servers:** Separate internal and external zones.
    *   **Split-Horizon:** Internal DNS resolves internal names (AD, intranet) to internal IPs; external DNS resolves public names to public IPs.
    *   **Forwarders:** Forward external queries to ISP DNS to reduce load on internal servers.
    *   **Conditional Forwarders:** Forward specific internal domains (e.g., `corp.example.com`) to the internal AD DNS.
*   **Laptop Move:** When on VPN, the laptop routes traffic through the VPN tunnel. The internal DNS server resolves the laptop's internal IP. When at the office, the DHCP server updates the internal DNS with the new IP.

**OP8 — Hard:**
*   **Chain of Trust:** Root CA signs Subordinate CA; Subordinate CA signs End-Entity certificates. Browsers trust the Root CA.
*   **Deployment:**
    *   **Root CA:** Offline, air-gapped, stored on a smart card.
    *   **Subordinate CA:** Online, issues certificates.
    *   **CRL vs OCSP:** CRLs list revoked certs (heavy bandwidth). OCSP checks revocation status in real-time (lighter bandwidth).
    *   **Templates:** Define certificate requirements (validity, key usage).
    *   **Auto-enrollment:** Windows clients request certs from the Subordinate CA.
*   **Consequences:** Compromised **Subordinate CA** allows attackers to issue fake certs for internal or external domains, breaking trust for that subtree. Compromised **Root CA** breaks trust for *all* domains signed by that root, requiring a full re-issuance of all certificates globally.

**OP9 — Hard:**
*   **MPLS:** High reliability, low latency, high cost. Good for VoIP.
*   **IPsec VPN:** Lower cost, variable reliability/latency (depends on internet). Good for branch offices.
*   **SD-WAN:** Software-defined, flexible, cost-effective, prioritizes traffic (VoIP).
*   **WireGuard Mesh:** Very fast, simple, low cost, but requires careful configuration for high availability.
*   **Recommendation:** **SD-WAN** or **MPLS**. For 50 users with latency-sensitive VoIP, MPLS offers the most consistent latency, but SD-WAN is a modern, cost-effective alternative that can prioritize VoIP traffic over general internet traffic.

**OP10 — Medium:** **iDRAC/iLO/IPMI** are out-of-band management interfaces that allow administrators to manage servers even if the OS is down or the server is powered off.
*   **Criticality:** Essential for remote maintenance, monitoring hardware health, and rebooting servers without physical access.
*   **Security Risk:** If exposed to the internet, attackers can gain administrative control of the server, potentially pivoting into the network or exfiltrating data.

**OP11 — Medium:**
*   **LVM:** Logical Volume Manager. Flexible, allows resizing volumes, snapshots.
*   **LVM-Thin:** LVM with thin provisioning. Allows over-allocating space, efficient snapshots.
*   **ZFS:** Advanced filesystem with built-in RAID (RAID-Z), snapshots, deduplication, and checksums.
*   **Snapshots:** LVM/ZFS snapshots are copy-on-write (COW), meaning they are fast and take minimal space until data is modified.
*   **Use Cases:** LVM for general Linux VM storage; LVM-Thin for testing/dev environments; ZFS for high-value data or NAS storage.

**OP12 — Hard:**
*   **Design:** A **2-site Ceph cluster**.
*   **CRUSH Rules:** Configure rules to place replicas across sites (e.g., `size=3` -> 1 replica in Site A, 1 in Site B, 1 in a third site or split).
*   **Network:** Requires high-bandwidth, low-latency WAN links between sites.
*   **Split-Brain:** If the WAN link fails, the cluster splits into two independent clusters. Without a tiebreaker, both sites might think they have quorum and serve data, leading to data corruption.
*   **Why Bad:** Ceph requires a majority of monitors to form a quorum. In a 2-site setup, if one site loses power, the other site might lose monitors, losing quorum and becoming read-only or unresponsive.

**OP13 — Easy:** **DHCP** (Dynamic Host Configuration Protocol) assigns IP addresses automatically.
*   **DORA:** **D**iscover (Client -> Server), **O**ffer (Server -> Client), **R**equest (Client -> Server), **A**cknowledgment (Server -> Client).
*   **Lease Expiration:** If the server is unavailable, the client will continue using the IP until the lease expires (usually 24-48 hours), after which it will stop working until it finds a new server.

**OP14 — Easy:** A **managed switch** allows configuration of VLANs, port mirroring, QoS, and link aggregation. An **unmanaged switch** is a "plug-and-play" device with no configuration options.
*   **Enterprise Features:** VLANs for segmentation, Link Aggregation (LACP) for bandwidth, QoS for prioritizing VoIP, and Port Mirroring for troubleshooting.

**OP15 — Easy:** **NTP** (Network Time Protocol) synchronizes clocks across devices.
*   **Criticality:** Ensures logs are in order, authentication timestamps are valid, and cluster quorum calculations are accurate.
*   **Clock Drift Issues:** If clocks drift significantly (e.g., +10 minutes), a cluster might lose quorum (thinking it has 2 votes when it actually has 3), causing services to stop or split-brain.

**OP16 — Easy:** **Physical Server:** Bare metal. **VM:** Virtual machine (hypervisor). **Container:** Isolated process with shared OS kernel.
*   **Bare Metal:** Use for high-performance computing (HPC), legacy applications requiring direct hardware access, or when virtualization overhead is unacceptable.

**OP17 — Easy:** A **UPS** (Uninterruptible Power Supply) provides battery backup during power outages to allow a graceful shutdown. A **Generator** provides long-term power during extended outages.
*   **Why Both:** UPS bridges the gap during short outages; Generator handles long outages.
*   **ATS:** The **Automatic Transfer Switch** detects power loss and seamlessly switches the load from the utility grid to the UPS or Generator.

**OP18 — Medium:** **Active-Passive:** One node is active, the other is standby. **Active-Active:** Both nodes are active and share the load.
*   **Pacemaker/Corosync Implementation:**
    *   Configure **Corosync** for messaging and quorum.
    *   Configure **Pacemaker** to manage resources (PostgreSQL service).
    *   Use **STONITH** (fencing) to kill the passive node if the active node dies.
    *   Assign a **Virtual IP (VIP)** to the active node so clients connect to the same IP regardless of which physical server is running.
    *   **Failover:** If the active node fails, Pacemaker detects the resource loss, fences the failed node, and promotes the passive node, moving the VIP to it.

**OP19 — Hard:**
*   **3-2-1 Rule:** 3 copies of data, on 2 different media, with 1 offsite.
*   **RPO/RTO:** Define Recovery Point Objective (data loss tolerance) and Recovery Time Objective (downtime tolerance).
*   **Types:** Full, Incremental, Differential.
*   **Deduplication:** Reduces storage footprint.
*   **Tape vs Disk vs Cloud:** Tape is cheap for long-term cold storage but slow to restore. Disk is fast but expensive. Cloud is good for offsite but has latency.
*   **Immutable Backups:** Store backups in a format that cannot be modified (e.g., WORM storage) to prevent ransomware encryption.
*   **Testing:** Regularly test restores to ensure backups are valid.
*   **Backup vs DR:** Backup is a copy of data for recovery. DR is a comprehensive plan and infrastructure to restore operations after a disaster.

**OP20 — Hard:**
*   **802.1X Process:**
    *   **Supplicant:** The client device (e.g., laptop) trying to connect.
    *   **Authenticator:** The network switch port.
    *   **Authentication Server:** RADIUS server (e.g., IAS/NPS) verifying credentials.
*   **EAP Methods:** **EAP-TLS** uses certificates (most secure). **PEAP** wraps credentials in TLS (easier to manage than TLS).
*   **Dynamic VLAN:** The RADIUS server sends the VLAN ID back to the switch, which moves the port into that VLAN.
*   **Failed Auth:** Port is placed in an unauthorized state (no IP assignment).
*   **MAB (MAC Authentication Bypass):** If a device doesn't support 802.1X, the switch can fall back to authenticating based on the MAC address (often mapped to a specific VLAN in the RADIUS server).
