**K1 — Easy:** A **Deployment** manages stateless applications, ensuring a specified number of replica pods are running. A **StatefulSet** manages stateful applications, providing stable, unique network identities (DNS names) and persistent storage for each pod, ensuring pods are started and stopped in a specific order.

**K2 — Easy:** A ClusterIP Service creates a virtual IP (ClusterIP) internal to the cluster. The kube-proxy component watches the Service and Endpoints resources, creating iptables (or IPVS) rules on each node that forward traffic destined for the ClusterIP to the IP addresses of the matching Pods.

**K3 — Medium:**
*   **PersistentVolume (PV):** A cluster resource representing actual storage (e.g., AWS EBS, NFS) that is provisioned by an administrator or dynamically via StorageClass.
*   **PersistentVolumeClaim (PVC):** A user request for storage. It claims a specific amount of storage and access mode (ReadWriteOnce, ReadOnlyMany, etc.) from a PV.
*   **StorageClass:** Defines the "class" of storage (e.g., fast SSD, standard HDD) and the provisioner (e.g., AWS EBS CSI) used to dynamically create PVs when a PVC is created.

**K4 — Medium:**
1.  **Check Logs:** Run `kubectl logs <pod-name>` to see the error message causing the crash.
2.  **Check Events:** Run `kubectl describe pod <pod-name>` to see events related to the pod (e.g., ImagePullBackOff, CrashLoopBackOff).
3.  **Check Resource Limits:** Verify if the pod is being OOMKilled (Out Of Memory) by checking the "OOMKilled" status in describe or logs.
4.  **Check Image:** Ensure the image name and tag are correct and accessible from the cluster's registry.

**K5 — Medium:** CoreDNS provides DNS-based service discovery within the cluster, resolving service names (e.g., `my-service.default.svc.cluster.local`) to Pod IPs. If CoreDNS pods are down, internal DNS resolution fails, breaking service-to-service communication and preventing pods from starting if they rely on DNS for configuration.

**K6 — Hard:** The scheduler uses a two-phase algorithm:
1.  **Filtering:** It removes nodes that cannot run the pod (e.g., insufficient resources, node affinity mismatch, taints).
2.  **Scoring:** It assigns a score to each remaining node based on heuristics (e.g., node resource utilization, inter-node affinity, priority classes).
Factors considered include CPU/Memory availability, node labels, taints/tolerations, and Pod Disruption Budgets.

**K7 — Hard:** Yes, the pod will be scheduled. The node has 4GB (4096Mi) total. 3.5GB (3500Mi) is requested, leaving 596Mi free. The pod requests 256Mi, so 3500 + 256 = 3756Mi < 4096Mi.
If the pod uses 600Mi at runtime, it exceeds its memory limit of 512Mi. The Kubernetes OOM Killer will terminate the pod, and it will restart in a CrashLoopBackOff state.

**K8 — Hard:** 1. **External LB** (e.g., AWS ELB) receives traffic. 2. **Ingress Controller** (e.g., NGINX) receives traffic on port 80/443 and matches the Host/Path rules defined in the **Ingress** resource. 3. The Ingress Controller forwards traffic to the **Service** (ClusterIP). 4. **kube-proxy** on nodes updates iptables/IPVS to route traffic from the Service IP to the **Endpoints** (list of Pod IPs). 5. Traffic reaches the **Application Pod**.

**K9 — Medium:** A NetworkPolicy is a set of rules that allow or block traffic from pods to other pods. If no NetworkPolicy exists, the default behavior is **allow all traffic** (allow by default). When you apply a NetworkPolicy that selects specific pods, it acts as a firewall, blocking ingress/egress traffic unless explicitly allowed by another policy.

**K10 — Medium:** **RollingUpdate** replaces old pods with new ones gradually, maintaining availability during the update. **Recreate** kills all existing pods before creating new ones, causing downtime. You would choose Recreate for applications where data integrity is critical during the update (e.g., databases) or when you cannot tolerate any traffic during the transition.

**K11 — Easy:** A Namespace is a logical isolation mechanism to divide cluster resources into multiple virtual clusters. Default namespaces in a new cluster are: `kube-system` (system components), `default` (user resources), and `kube-public` (publicly readable data).

**K12 — Easy:** `kubectl describe pod <name>` provides detailed status, events, IP addresses, node name, resource usage, and specific error messages (like why a container failed). `kubectl get pod` only shows the basic status (Running, Pending) and basic metadata like name and age.

**K13 — Easy:** A ConfigMap is an API object used to store non-confidential data in key-value pairs. Pods consume it via:
1.  **Environment Variables:** Injecting values into container environment.
2.  **Volume Mount:** Mounting the ConfigMap as a file inside the container.

**K14 — Easy:**
*   **ClusterIP:** A virtual IP internal to the cluster; accessible only within the cluster.
*   **NodePort:** Exposes the Service on each Node's IP at a specific port; accessible from outside via `<NodeIP>:<Port>`.
*   **LoadBalancer:** Exposes the Service externally using a cloud provider's load balancer; accessible via a public IP.

**K15 — Easy:** A DaemonSet ensures a copy of a Pod runs on all (or selected) nodes in the cluster. You use it instead of a Deployment when you need a sidecar or agent process running on every node, such as log collectors (Fluentd), monitoring agents (Prometheus Node Exporter), or network plugins.

**K16 — Medium:** **Taints and Tolerations** are used to repel pods from specific nodes (Taints), and pods can choose to ignore this (Tolerations). **Node Affinity** is a preference rule for scheduling pods onto specific nodes. *Use Case:* Taint the master node so only control-plane pods (with tolerations) run there; use Node Affinity to prefer nodes with high GPU resources for AI workloads.

**K17 — Medium:** A Kubernetes Operator is a custom controller that extends the Kubernetes API to manage complex, stateful applications (like databases) that standard controllers cannot handle. It differs from a standard controller (like Deployment) by encapsulating domain-specific knowledge and lifecycle management. It solves the problem of managing application state, upgrades, and backups alongside the Kubernetes infrastructure.

**K18 — Hard:** Kubernetes uses a **strong consistency (linearizable)** model via etcd. If the etcd quorum is lost (e.g., 2 out of 3 nodes down), the cluster becomes unavailable because it cannot agree on the state of the system. To recover, you must restore the lost etcd nodes from a backup snapshot or rebuild the cluster from a quorum of healthy nodes using the backup data.

**K19 — Hard:** RBAC uses **Role** (namespace-scoped permissions) and **ClusterRole** (cluster-scoped permissions) bound to subjects via **RoleBinding** (namespace-scoped) or **ClusterRoleBinding** (cluster-scoped).
*Manifests:*

```yaml
  name: developer-view
  namespace: my-namespace

- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list"]

apiVersion: rbac.authorization.k8s.io/v1

  name: developer-view-binding
  namespace: my-namespace

- kind: User
  name: "dev-user"
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: developer-view
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:** The `ndots` setting in `/etc/resolv.conf` determines how many dots are required for a name to be considered a fully qualified domain name (FQDN). If `ndots` is high (e.g., 5) and the pod is in a subdomain, the DNS resolver tries to query the local domain first, then the root, leading to excessive queries and latency. To fix this, you can use `dnsConfig` in the pod spec to override the search domains or set `dnsPolicy: ClusterFirstWithHostNet` to use the host's resolv.conf, effectively reducing the search scope.

## Development (20 questions)

**D1 — Easy:** **Git Rebase** rewrites history to create a linear sequence, often squashing commits. **Git Merge** preserves the full history by creating a merge commit. Avoid rebasing when you have shared branches (e.g., `main` or `feature` branches worked on by others), as it rewrites history and can confuse other developers.

**D2 — Easy:** **TCP** is connection-oriented and reliable (guarantees delivery). **UDP** is connectionless and unreliable (best-effort). Protocols: TCP (HTTP, SSH), UDP (DNS, VoIP).

**D3 — Medium:** A race condition occurs when the output of a program depends on the sequence or timing of uncontrollable events. *Example:* In Java, two threads increment a shared counter variable `count++`. If they read the value 5 simultaneously, both write back 6, resulting in a lost increment.

**D4 — Medium:** **Symmetric encryption** uses the same key for encryption and decryption. **Asymmetric encryption** uses a public key for encryption and a private key for decryption. In TLS, the server uses Asymmetric encryption (e.g., RSA) to securely exchange a Symmetric Session Key, which is then used for the actual data transfer.

**D5 — Medium:** A **container image layer** is a filesystem change set (diff) representing the difference between the base image and the current state. **Layer caching** affects Dockerfile best practices by caching layers that haven't changed; if you move `RUN apt-get install` to the top of the Dockerfile, changing a file later in the file won't invalidate the cache for the install step, speeding up builds.

**D6 — Medium:**
1.  **Check Upstream Service:** Verify if the upstream service (e.g., a microservice) is healthy and returning 200 OK.
2.  **Check Database/Dependencies:** Ensure the database connection pool is not full and the database is responding.
3.  **Check Rate Limiting:** Verify if the API is hitting rate limits or throttling.
4.  **Check Logs:** Look for specific errors in the application logs indicating connection failures or timeouts.

**D7 — Hard:** **CAP Theorem** states a distributed system can only provide two of three guarantees: Consistency (all nodes see same data at same time), Availability (every request receives a response), and Partition Tolerance (system continues despite network failures).
*   **CP Example:** HBase or MongoDB (prioritizes consistency over availability during partitions).
*   **AP Example:** Cassandra or DynamoDB (prioritizes availability and partition tolerance over strict consistency).

**D8 — Medium:** **Horizontal Scaling** adds more machines (nodes) to handle load. **Vertical Scaling** adds more resources (CPU/RAM) to a single machine. Architectural patterns enabling horizontal scaling include Microservices (stateless services) and Stateless applications.

**D9 — Easy:** An **environment variable** is a dynamic-named value that can affect the behavior of running processes. To set one that persists across shell sessions on Linux, use `export VAR_NAME="value"` or append `export VAR_NAME="value"` to `~/.bashrc` or `~/.profile`.

**D10 — Easy:** **JSON** (JavaScript Object Notation) is a lightweight data-interchange format that is strictly text-based and requires double quotes for keys. **YAML** (YAML Ain't Markup Language) is a human-readable data serialization language that uses indentation and allows single quotes. Advantage: YAML is more readable for complex nested structures; JSON is more machine-parsable and standard.

**D11 — Easy:** A **REST API** is an architectural style for web services using HTTP methods. **GET** retrieves data, **POST** creates data, **PUT** updates existing data, and **DELETE** removes data.

**D12 — Easy:** **Version pinning** involves fixing the specific version of a dependency (e.g., `package-lock.json` or `requirements.txt`). It is important for reproducible builds to ensure that the exact same code runs in production as it did in development, preventing "it works on my machine" issues.

**D13 — Easy:** **Compiled languages** (e.g., C++, Go) are translated into machine code before execution. **Interpreted languages** (e.g., Python, JavaScript) are executed line-by-line by an interpreter at runtime.

**D14 — Medium:** A **Reverse Proxy** sits in front of servers and forwards client requests to those servers, hiding their existence. A **Forward Proxy** sits in front of clients and forwards their requests to the internet, hiding the client's identity. Common reverse proxies: Nginx (web serving), HAProxy (load balancing).

**D15 — Medium:** A **deadlock** is a situation where two or more processes block each other indefinitely, each waiting for a resource held by the other. The four **Coffman conditions** required for a deadlock are: 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** **Eventual consistency** means that if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. Distributed databases like Cassandra handle this by allowing clients to choose a **consistency level** (e.g., ONE, QUORUM, ALL). Read-after-write consistency is often achieved by requiring a QUORUM read and write.

**D17 — Hard:** **mTLS (Mutual TLS)** requires both the client and server to authenticate each other using digital certificates. The handshake involves the client sending its certificate to the server, and the server sending its certificate to the client. Both sides verify the other's certificate chain and validity. It is commonly used in service meshes (like Istio) and secure API gateways.

**D18 — Hard:** A **hash table** uses an array and a hash function to map keys to indices. **Collision resolution** strategies include **Chaining** (storing multiple items in a linked list at the same index) and **Open Addressing** (finding the next empty slot). Time complexity: Average O(1), Worst Case O(n).

**D19 — Hard:** The **Circuit Breaker** pattern stops cascading failures in microservices. It has three states: **Closed** (normal operation, requests pass through), **Open** (failure threshold exceeded, requests are rejected immediately), and **Half-Open** (allows a few test requests to see if the service has recovered). It relates to retry policies by preventing retries on a failing service, and exponential backoff is often used when transitioning to the Half-Open state.

**D20 — Hard:** **Optimistic concurrency control** assumes conflicts are rare and checks for conflicts only at commit time (e.g., using row versioning). **Pessimistic concurrency control** assumes conflicts are common and locks resources before reading them (e.g., `SELECT FOR UPDATE`). You would choose Optimistic for web apps (low contention) and Pessimistic for banking systems (high contention).
