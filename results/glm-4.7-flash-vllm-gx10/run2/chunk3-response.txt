Let's write the final response.</think>## OpenTofu / Terraform (20 questions)

**T1 — Easy:** `tofu plan` generates an execution plan showing what OpenTofu will change to reach the desired state. `tofu apply` executes that plan, creating, updating, or destroying the actual infrastructure.

**T2 — Easy:** State is a file (or database) that tracks the real-world resources managed by OpenTofu. Remote state is important because it prevents conflicts when multiple engineers work on the same infrastructure, allows for state locking to prevent concurrent modifications, and enables collaboration.

**T3 — Medium:** `count` creates multiple instances based on an integer index (e.g., 0, 1, 2). `for_each` creates instances based on a map or set (e.g., `key: value`). `for_each` is preferred when you need to map resources to specific names or IDs for readability and to avoid duplicate keys.

**T4 — Medium:** If you manually change a resource (e.g., in the cloud console), OpenTofu detects this as "drift" in the plan. When you run `apply`, OpenTofu will attempt to recreate the resource to match the state file, overwriting your manual changes.

**T5 — Easy:**
```hcl
resource "null_resource" "web_vm" {
  for_each = toset(["web1", "web2", "web3"])
  # Resource configuration
}
```

**T6 — Hard:** `terraform_remote_state` is a data source used to fetch outputs from another module's state. Output values are used to expose specific values from a module to its caller. The recommended alternative is to pass values directly via module arguments rather than using `terraform_remote_state`. This reduces coupling, avoids circular dependencies, and simplifies the dependency graph.

**T7 — Hard:** The null_resource runs immediately upon creation, but the RKE2 cluster might not be fully initialized or the kubeconfig file might not be written yet. The output is empty because the provisioner hasn't finished executing. **Fix:** Use `triggers` on the null_resource to ensure it only runs when the cluster changes, or use a `local_file` resource that depends on the cluster output to capture the kubeconfig content.

**T8 — Medium:** `terraform import` maps existing resources to the state file but requires the resource block to already exist in the code. The `import` block (1.5+) allows you to define the resource block in the code and run `terraform import`, automatically linking the existing resource to the state without manual editing.

**T9 — Easy:** A variable is a placeholder for a value defined in `.tf` files (input). An output is a value defined in `.tf` files to be displayed to the user or passed to other modules upon completion.

**T10 — Easy:** A provider is a plugin that allows OpenTofu to interact with the API of a cloud provider or service. If you run `tofu plan` without `tofu init`, OpenTofu will not have the provider binaries downloaded, causing the plan to fail or use a default (if available), which is rarely correct.

**T11 — Easy:** The `.terraform.lock.hcl` file locks the exact versions of provider plugins used in the project. It should be committed to version control to ensure that all team members and CI/CD pipelines use the exact same provider versions, guaranteeing reproducibility.

**T12 — Easy:** `tofu destroy` removes all resources defined in the state. To target a single resource, use the `-target` flag (e.g., `tofu destroy -target=aws_instance.web_server`).

**T13 — Easy:** A data source allows you to read data from an existing resource without creating or modifying it (e.g., `aws_subnet` to find an IP range). You use this instead of a managed resource when you need to reference existing infrastructure (like an existing VPC ID) rather than provisioning a new one.

**T14 — Medium:** `locals` are internal variables calculated from other variables or expressions within the module. You use `locals` instead of input variables when the value is derived logic (e.g., a concatenated string or a calculated list) and does not need to be configurable by the user.

**T15 — Medium:** The `lifecycle` block controls resource behavior.
*   `create_before_destroy`: Recreates the resource before destroying the old one (useful for databases to avoid downtime).
*   `prevent_destroy`: Blocks the resource from being destroyed (useful for critical infrastructure).
*   `ignore_changes`: Ignores changes to specific attributes (useful for auto-generated IDs or immutable fields).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource has moved from one address to another in the code. It updates the state file to reflect this new address without destroying and recreating the resource, preserving the history and state of the existing infrastructure.

**T17 — Hard:** OpenTofu builds a dependency graph where resources are nodes. **Implicit dependencies** are created automatically when a resource references another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are defined using `depends_on`. `depends_on` forces a specific order, reducing parallelism. It should be used sparingly to avoid unnecessary serialization; implicit dependencies are preferred.

**T18 — Hard:**
1.  **Parallelism:** Increase `parallelism` in the provider config (tradeoff: higher memory/CPU usage).
2.  **Sparse Plans:** Use `-target` for specific resources (tradeoff: partial state, requires manual cleanup).
3.  **Local State:** Use a local state file for planning (tradeoff: no collaboration, no locking).
4.  **Provider Plugins:** Download plugins locally (tradeoff: setup complexity).
5.  **Terraform Cloud:** Use remote execution (tradeoff: cost/external dependency).

**T19 — Hard:** State locking prevents concurrent writes. If a CI pipeline crashes, the lock remains. **Manual break:** Run `terraform force-unlock <LOCK_ID>`. **Risks:** If another apply is running, breaking the lock will corrupt the state file and cause data loss.

**T20 — Hard:**
1.  Create the S3 bucket and DynamoDB table.
2.  Update `backend.tf` to point to the new S3/DynamoDB configuration.
3.  Run `terraform init` to download the S3/DynamoDB backend provider.
4.  Run `terraform apply`. This uploads the local state to S3.
5.  Verify the state file exists in the S3 bucket.
6.  Delete the local `terraform.tfstate` file.

## Ansible (20 questions)

**A1 — Easy:** A **Playbook** is a YAML file containing a list of tasks to be executed on target hosts. A **Role** is a reusable collection of files (tasks, variables, handlers, templates) organized in a standard directory structure. A **Task** is a single unit of work (e.g., install a package, start a service).

**A2 — Easy:** `ansible_facts` is a dictionary of information gathered from the target host. You access the OS family using `ansible_facts['os_family']` or the shortcut `ansible_os_family`.

**A3 — Medium:**
*   **command:** Executes a command without a shell (pipes and redirects fail). Use for simple commands.
*   **shell:** Executes a command via the shell (pipes and redirects work). Use for complex shell logic.
*   **raw:** Executes a command directly on the target, bypassing the Ansible module system (rarely used now, mostly for bootstrapping).

**A4 — Medium:** Idempotency means a task can be run multiple times and produce the same result. **Idempotent:** `yum: name=htop state=present` (installs if missing, does nothing if present). **Not Idempotent:** `shell: echo "hello" > /tmp/hello` (overwrites the file every time).

**A5 — Medium:**
```yaml
- name: Install htop
  block:
    - name: Install htop on Debian/Ubuntu
      apt:
        name: htop
        state: present
      when: ansible_os_family == "Debian"
    - name: Install htop on RHEL/Amazon
      yum:
        name: epel-release,htop
        state: present
      when: ansible_os_family == "RedHat"
```

**A6 — Hard:** Variable precedence (highest to lowest):
1.  Extra vars (`-e`)
2.  Role defaults
3.  Inventory group_vars
4.  Inventory host_vars
5.  Inventory file vars
6.  Role vars
7.  Play vars
8.  Set_facts
9.  Facts (gathered)

**A7 — Hard:**
*   **Inventory:** Group the first 3 nodes in a group (e.g., `rke2_initial`) and the rest in `rke2_workers`.
*   **Serial:** Use `serial: 3` in the playbook to limit execution to 3 hosts at a time.
*   **Wait:** Use `wait_for` or `delegate_to` to ensure the first 3 nodes are fully joined before starting the next batch.

**A8 — Easy:** `ansible-vault` encrypts sensitive data. To encrypt a single variable inside a vars file without encrypting the whole file, use `ansible-vault encrypt_string --stdin-name my_secret_var`.

**A9 — Easy:** An **inventory file** lists the target hosts. A **static inventory** is a file (INI or YAML). A **dynamic inventory** is a script or API that generates the inventory list at runtime (e.g., from AWS EC2).

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A **handler** is a task that is only run if triggered by another task. It differs from a regular task by being defined in the `handlers` section and triggered by the `notify` keyword in a task.

**A12 — Easy:** The `ansible.cfg` file configures Ansible behavior. Common settings include `inventory`, `remote_user`, `host_key_checking`, and `roles_path`.

**A13 — Easy:** The `register` keyword stores the output of a task in a variable. You can use this variable in a subsequent task, e.g., `debug: msg="{{ my_result }}"`.

**A14 — Medium:** `include_tasks` dynamically includes a task file at runtime (evaluated when the playbook runs). `import_tasks` statically includes a task file at parse time (evaluated when the code is read). Use `include_tasks` when you need to conditionally include files or loop over them.

**A15 — Medium:** **Ansible Galaxy** is a repository for Ansible roles and collections. You use a `requirements.yml` file to list the roles/collections you need, then run `ansible-galaxy install -r requirements.yml` to download and install them.

**A16 — Medium:** Connection plugins define how Ansible connects to a host.
*   **ssh:** Standard SSH connection.
*   **local:** Runs tasks on the control node.
*   **network_cli:** Uses Netmiko to connect to network devices (Cisco/Juniper).
*   **winrm:** Connects to Windows hosts.

**A17 — Hard:** `delegate_to` runs a task on a different host than the target. `run_once` ensures a task runs only once per host group. **Example:** Gather facts on all remote hosts, then run a task on localhost once to aggregate those facts.

**A18 — Hard:**
1.  **Forks:** Increase `forks` in `ansible.cfg` (tradeoff: higher CPU usage).
2.  **Pipelining:** Enable pipelining (tradeoff: requires `become: false`).
3.  **Fact Caching:** Use Redis to cache facts (tradeoff: setup complexity).
4.  **Mitogen:** Use Mitogen for faster SSH connections (tradeoff: requires specific setup).
5.  **Limit Hosts:** Reduce the number of hosts in the inventory.

**A19 — Hard:** Jinja2 is the templating engine.
*   `{{ }}`: Variable interpolation.
*   `{% %}`: Logic (loops, conditionals).
*   `{# #}`: Comments (ignored in output).

**Template Snippet:**
```jinja2
upstream backend {
{% for server in servers %}
  # Health check for {{ server.name }}
  server {{ server.ip }}:{{ server.port }};
{% endfor %}
}
```

**A20 — Hard:**
1.  **Batching:** Use `serial: 5` to deploy in small batches.
2.  **Pre-Task:** Add the new server to the Load Balancer (e.g., using `community.general.haproxy`).
3.  **Deploy:** Run the application deployment task.
4.  **Health Check:** Use the `uri` module to check the health endpoint on the new server.
5.  **Post-Task:** Remove the old server from the Load Balancer.
6.  **Rollback:** Use `block: ... rescue: ...` to revert changes (remove from LB, stop service) if the health check fails.
