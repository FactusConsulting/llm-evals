**K1 — Easy:** A **Deployment** manages stateless applications, allowing for easy scaling and rolling updates of pods. A **StatefulSet** manages stateful applications, ensuring pods have a stable, unique network identity (hostname) and persistent storage, and maintains the order in which pods are deployed and scaled.

**K2 — Easy:** A ClusterIP Service creates a virtual IP (ClusterIP) internal to the cluster. The `kube-proxy` component watches the Service and updates the node's `iptables` or `IPVS` rules to forward traffic destined for that ClusterIP to the backend Pods identified in the Service's Endpoints list.

**K3 — Medium:**
*   **PersistentVolume (PV):** A cluster-level resource representing actual storage (e.g., AWS EBS, NFS) that is provisioned by an administrator or dynamically provisioned.
*   **PersistentVolumeClaim (PVC):** A user-level request for storage. It claims a specific amount of storage and access mode (ReadWriteOnce, ReadOnlyMany, etc.) from a PV.
*   **StorageClass:** Defines the "class" of storage (e.g., fast SSD, standard HDD) and the provisioner (e.g., AWS EBS CSI, local-path) used to dynamically create PVs when a PVC is created.

**K4 — Medium:** Troubleshooting steps for CrashLoopBackOff:
1.  **Check Events:** Run `kubectl describe pod` to see why the pod failed (e.g., ImagePullBackOff, CrashLoopBackOff).
2.  **Check Logs:** Run `kubectl logs <pod>` to see the actual error message from the application.
3.  **Verify Image:** Ensure the image name, tag, and registry credentials are correct.
4.  **Check Config:** Verify ConfigMaps and Secrets are mounted correctly and contain valid data.

**K5 — Medium:** CoreDNS is the DNS server for the Kubernetes cluster, providing DNS resolution for Services and Pods. If CoreDNS pods are down, internal DNS resolution fails; pods cannot reach other Services by their DNS names, breaking inter-service communication and application functionality.

**K6 — Hard:** The scheduler uses a two-phase process:
1.  **Filtering:** Removes nodes that cannot run the pod (e.g., insufficient resources, node selectors, taints).
2.  **Scoring:** Ranks the remaining nodes based on heuristics (e.g., resource efficiency, node affinity, spread constraints).
**Factors considered:** CPU/Memory requests/limits, Taints and Tolerations, NodeSelectors, Node Affinity rules, and Pod Anti-Affinity.

**K7 — Hard:**
*   **Scheduling:** The node has 3.5GB requested. The pod requests 256Mi. Total requested = 3.756GB < 4GB. **Yes, the pod will be scheduled.**
*   **Runtime:** If the pod uses 600Mi, it exceeds its limit of 512Mi. The Kubernetes OOM Killer will terminate the pod, causing it to restart in CrashLoopBackOff.

**K8 — Hard:** The lifecycle is:
1.  **External LB:** Traffic hits the cloud Load Balancer (e.g., AWS ALB).
2.  **Ingress Controller:** The Ingress Controller (running as a Deployment) receives the traffic based on the Ingress resource rules (Host/Path).
3.  **Service:** The Controller forwards traffic to the Kubernetes Service (ClusterIP).
4.  **kube-proxy:** The node's `kube-proxy` uses iptables/IPVS to route traffic from the Service IP to the specific Pod IP.
5.  **Endpoints:** The Service points to the Endpoints list containing the Pod IPs.
6.  **Application Pod:** The traffic reaches the application container.

**K9 — Medium:** A **NetworkPolicy** is a resource that defines ingress/egress traffic rules for a set of pods. If no NetworkPolicy exists, the default behavior is **allow all traffic**. When you apply a NetworkPolicy, it enforces the rules (e.g., "allow ingress only from namespace A"), effectively blocking traffic that does not match the policy.

**K10 — Medium:** **RollingUpdate** replaces old pods with new ones gradually, maintaining availability. **Recreate** terminates all existing pods before creating new ones, causing downtime. You would choose **Recreate** for databases or applications where a brief downtime is acceptable and data consistency is critical during the switch.

**K11 — Easy:** A **Namespace** provides logical isolation of resources within a cluster. The default namespaces created in a new cluster are: `kube-system` (system components), `default` (user resources), and `kube-public` (publicly readable data).

**K12 — Easy:** `kubectl describe pod <name>` is used for detailed debugging. It shows information not present in `kubectl get pod`, specifically: **Pod Events** (crash reasons), **Conditions** (Ready status details), **IP address**, **Node name**, and **Resource usage** (CPU/Memory limits).

**K13 — Easy:** A **ConfigMap** is an API object used to store non-confidential data in key-value pairs. Pods consume it via:
1.  **Environment Variables:** `envFrom` or `env` with `valueFrom`.
2.  **Volume Mount:** Mounting the ConfigMap as a volume to read files.

**K14 — Easy:**
*   **ClusterIP:** A virtual IP internal to the cluster; accessible only within the cluster.
*   **NodePort:** Exposes the Service on each Node's IP at a static port; accessible from outside via `<NodeIP>:<Port>`.
*   **LoadBalancer:** Allocates an external load balancer (usually cloud-native) and assigns a static external IP.

**K15 — Easy:** A **DaemonSet** ensures that a copy of a Pod runs on all (or selected) nodes in the cluster. You use it instead of a Deployment for logging agents, monitoring agents, or network plugins that need to run on every node.

**K16 — Medium:** **Taints and Tolerations** are used to repel pods from nodes (Imperative approach). **Node Affinity** is used to prefer specific nodes (Declarative approach).
*   *Use Case for Taints:* Marking Master nodes as unschedulable so regular workloads don't run there.
*   *Use Case for NodeAffinity:* Prefer a node with high memory or specific hardware features.

**K17 — Medium:** A **Kubernetes Operator** is a custom controller that extends Kubernetes to manage complex, stateful applications (like databases). It differs from a standard controller (like Deployment) by managing the *entire lifecycle* (provisioning, scaling, backup, failover) of a custom resource (CRD), solving the problem of managing stateful applications that standard controllers cannot handle.

**K18 — Hard:** Kubernetes uses **etcd** for a **Linearizable/Strong Consistency** model. If the etcd quorum is lost (e.g., 2 out of 3 nodes down), the cluster becomes unavailable because it cannot agree on the state of the system. **Recovery:** You must restore the lost etcd nodes from a snapshot of the healthy quorum, then add them back to the cluster.

**K19 — Hard:** **RBAC** (Role-Based Access Control) controls access to API resources.
*   **Role:** Namespace-scoped permissions.
*   **ClusterRole:** Cluster-scoped permissions.
*   **RoleBinding:** Binds a Role to subjects (users/groups) in a namespace.
*   **ClusterRoleBinding:** Binds a ClusterRole to subjects cluster-wide.
*   **Manifests:**

    ```yaml
      kind: Role

      apiGroup: rbac.authorization.k8s.io
    ```

**K20 — Hard:** The `ndots` setting in `/etc/resolv.conf` determines how many dots are required for a name to be treated as a Fully Qualified Domain Name (FQDN). If `ndots` is high (e.g., 5), the DNS resolver tries the local DNS server first. If the name isn't found, it queries the root servers, causing excessive latency.
**Fix:** Use `dnsConfig` in the pod spec to override the default search domain behavior:
```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "2"
```

## Development (20 questions)

**D1 — Easy:** **Git Rebase** rewrites history to create a linear sequence of commits, while **Git Merge** preserves the branching history. You should avoid rebasing on shared branches (like `main` or `develop`) because it rewrites commit hashes, confusing other developers and potentially causing merge conflicts.

**D2 — Easy:** **TCP** is connection-oriented, reliable, and ordered (e.g., HTTP, SMTP). **UDP** is connectionless, unreliable, and fast (e.g., DNS, VoIP).

**D3 — Medium:** A **race condition** occurs when the output of a computation depends on the sequence or timing of other uncontrollable events. **Example:** Two threads increment a shared counter variable `count` simultaneously. If they both read `count` as 10, increment to 11, and write back, the final value is 11 instead of 12.

**D4 — Medium:** **Symmetric encryption** uses a single shared key for encryption and decryption. **Asymmetric encryption** uses a public key for encryption and a private key for decryption. In **TLS**, the server uses Asymmetric encryption (with its public key) to securely exchange a symmetric session key, which is then used for the bulk data transfer.

**D5 — Medium:** A **container image layer** is a read-only filesystem change set. **Layer caching** affects Dockerfile best practices because Docker builds layers sequentially; if a layer changes, all subsequent layers must be rebuilt. Best practice is to group commands that change the filesystem (RUN, COPY) together to maximize cache hits.

**D6 — Medium:** Troubleshooting intermittent HTTP 503:
1.  **Check Service Endpoints:** Ensure the Service is actually routing to healthy Pods.
2.  **Check Upstream Service:** Verify the backend application or database is responding.
3.  **Check Rate Limiting:** Look for throttling or circuit breakers in the upstream service.
4.  **Check Caching:** Verify if a CDN or reverse proxy is caching an error response.

**D7 — Hard:** The **CAP theorem** states a distributed system can only provide two of three guarantees: **Consistency** (all nodes see same data at same time), **Availability** (every request receives a response), and **Partition Tolerance** (system continues despite network failures).
*   **CP Example:** A traditional SQL Database (e.g., PostgreSQL) prioritizes consistency over availability during a partition.
*   **AP Example:** A NoSQL Database like Cassandra prioritizes availability and partition tolerance over strict consistency.

**D8 — Medium:** **Horizontal Scaling** increases the number of instances to handle more load. **Vertical Scaling** increases the resources (CPU/RAM) of a single instance. Architectural patterns enabling horizontal scaling include **Load Balancing** and designing applications as **Stateless**.

**D9 — Easy:** An **environment variable** is a dynamic-named value that can affect the behavior of running processes. To set a variable that persists across shell sessions on Linux, use `export VAR_NAME=value`.

**D10 — Easy:** **JSON** (JavaScript Object Notation) is a lightweight data-interchange format using key-value pairs and no whitespace. **YAML** is a human-readable data serialization language that uses indentation and whitespace. **Advantages:** JSON is easier to parse programmatically; YAML is more readable and concise for configuration files.

**D11 — Easy:** A **REST API** is an architectural style for web services using HTTP methods. **GET** retrieves data, **POST** creates data, **PUT** updates existing data, and **DELETE** removes data.

**D12 — Easy:** **Version pinning** in dependency management (e.g., `npm@1.2.3` or `go.mod`) locks the specific version of a library. It is important for **reproducible builds** (ensuring the exact same code runs everywhere) and **security** (preventing the automatic update of vulnerable libraries).

**D13 — Easy:** A **compiled language** (e.g., C++, Go) is translated into machine code before execution, resulting in fast performance. An **interpreted language** (e.g., Python, JavaScript) is executed line-by-line by an interpreter, resulting in slower startup but greater flexibility.

**D14 — Medium:** A **reverse proxy** sits between clients and servers, forwarding client requests to specific internal servers (e.g., Nginx, HAProxy). A **forward proxy** sits between clients and the internet, masking client identities (e.g., corporate web filters). **Use cases:** Reverse proxies for load balancing and security; Forward proxies for access control and caching.

**D15 — Medium:** A **deadlock** occurs when a set of processes are blocked because each process is holding a resource and waiting for another resource acquired by another process in the set. The **Coffman conditions** required for a deadlock are: 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** **Eventual consistency** means that if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. **Cassandra** handles this using **Tunable Consistency**. Users can choose consistency levels like `ONE` (fast, low consistency), `QUORUM` (balanced), or `ALL` (strong consistency) per read/write operation.

**D17 — Hard:** **mTLS (Mutual TLS)** authenticates both the client and the server. **Handshake:** The client sends a ClientHello with supported ciphers. The server sends a ServerHello with a cert. The client verifies the server cert. The server requests a client cert. The client sends a cert signed by a trusted CA. Both sides verify each other's certs and establish a session. **Use:** Service-to-service communication in Service Meshes (e.g., Istio, Linkerd).

**D18 — Hard:** A **Hash Table** maps keys to values using a hash function. **Collision resolution:** **Chaining** (linked lists at each index) or **Open Addressing** (finding the next empty slot). **Time Complexity:** Average case O(1) for all operations; Worst case O(n) (e.g., all keys hash to the same index).

**D19 — Hard:** The **Circuit Breaker** pattern stops a cascade failure by stopping calls to a failing service. **States:**
1.  **Closed:** Normal operation, requests pass through.
2.  **Open:** Failure threshold exceeded; requests are rejected immediately (fail fast).
3.  **Half-Open:** A few requests are allowed through to test if the service is recovered.
It relates to **Retry policies** and **Exponential Backoff** by preventing retries on a failing service, which wastes resources and increases latency.

**D20 — Hard:** **Optimistic concurrency control** assumes conflicts are rare. It allows transactions to proceed without locking; if a conflict is detected (e.g., version mismatch), the transaction is rolled back. **Pessimistic concurrency control** assumes conflicts are frequent and locks resources (e.g., `SELECT FOR UPDATE`) immediately.
*   **Choose Optimistic:** For low-conflict data (e.g., user profiles).
*   **Choose Pessimistic:** For high-conflict data (e.g., banking ledgers).
*   **Example:** Optimistic uses row versioning (checking `WHERE version = X`); Pessimistic uses explicit locks.
