**AA1 — Easy:** A **monolith** is a single, indivisible codebase where all components (UI, business logic, data access) run together. A **microservices** architecture breaks the application into small, independent services that communicate over the network.
*   **Problems introduced by microservices:**
    1.  **Distributed System Complexity:** Managing network latency, distributed transactions, and eventual consistency becomes significantly harder.
    2.  **Operational Overhead:** You must manage the lifecycle, scaling, and monitoring of many more services than in a monolith.
    3.  **Data Consistency:** Ensuring data integrity across multiple databases (ACID transactions) requires patterns like Sagas, which add complexity.

**AA2 — Easy:** **Synchronous** communication requires the caller to wait for a response (e.g., REST API call). **Asynchronous** communication decouples the sender and receiver; the sender publishes a message and continues without waiting (e.g., Kafka or RabbitMQ).
*   **Example Technologies:**
    *   Synchronous: HTTP/REST, gRPC.
    *   Asynchronous: Apache Kafka, RabbitMQ, AWS SQS.

**AA3 — Medium:** An **API Gateway** acts as a single entry point for clients, handling routing, authentication, rate limiting, and request aggregation. A **reverse proxy** primarily handles routing and SSL termination to hide backend server details.
*   **Can it replace a reverse proxy?** Yes, an API Gateway can handle basic routing and SSL offloading. However, reverse proxies are often used for internal infrastructure routing (e.g., routing traffic to specific backend services or static assets) and are lighter weight. In many architectures, the API Gateway sits in front of a reverse proxy for a layered security approach.

**AA4 — Medium:** The **Saga pattern** is a design pattern for managing distributed transactions across multiple services. Instead of a global transaction, each service performs an operation and publishes an event to trigger the next step in the transaction.
*   **Choreography vs. Orchestration:**
    *   **Choreography:** Services communicate via events directly. It is loosely coupled but hard to debug and understand the flow.
    *   **Orchestration:** A central coordinator (orchestrator) tells services what to do. It is easier to manage but creates a central point of failure and tighter coupling.
*   **When to use:** Use Choreography for simple flows where services are loosely coupled. Use Orchestration for complex flows requiring strict control or when you need to coordinate many services.

**AA5 — Medium:** **CQRS** (Command Query Responsibility Segregation) separates the read and write models of an application. **Event Sourcing** stores the state of an entity as a sequence of events rather than just the current state.
*   **Why pair them:** They solve the problem of complex querying requirements. A traditional CRUD model often requires complex joins or denormalization to support complex reporting. By separating reads and writes and storing events, you can build optimized read models (e.g., materialized views) that are perfect for reporting without impacting write performance.

**AA6 — Medium:** The **Circuit Breaker** pattern prevents a service from being overwhelmed by failing calls. It monitors the health of a downstream service and "trips" the circuit open if failures exceed a threshold.
*   **States:** Closed (normal operation), Open (fail fast, no calls made), Half-Open (allows a few test calls to see if the service has recovered).
*   **Difference from Retry/Backoff:** Retry/Backoff attempts to fix the call immediately, potentially adding load to a failing system. The Circuit Breaker stops calling the failing service entirely to allow it to recover.
*   **Using both:** Use the Circuit Breaker to stop cascading failures from a known-down service, and use Retry/Backoff for transient network errors on services that are currently healthy.

**AA7 — Hard:**
1.  **Shared DB, Shared Schema:** *Pros:* Lowest cost, easiest to implement. *Cons:* High security risk (SQL injection risks), high "noisy neighbor" risk (one tenant can impact others), difficult to scale DB schema changes.
2.  **Shared DB, Separate Schema:** *Pros:* Good balance of cost and isolation. *Cons:* Still shares the DB instance (resource contention), schema migration is complex.
3.  **Separate DB per Tenant:** *Pros:* Maximum security and isolation, no noisy neighbor risk. *Cons:* Highest cost (hardware, licensing), highest operational complexity (managing many DB instances).

**AA8 — Hard:** **Strong consistency** ensures all nodes see the same data at the same time. **Eventual consistency** allows temporary discrepancies but guarantees convergence over time.
*   **Architecture for Inventory:** You must use **Strong Consistency**.
*   **Data Store:** A relational database (PostgreSQL) with ACID guarantees or a key-value store with atomic operations (Redis).
*   **Patterns:** Use **Optimistic Locking** (versioning) or **Pessimistic Locking** (SELECT FOR UPDATE) to prevent overselling. At scale, you might use a distributed lock service (like ZooKeeper or etcd) to coordinate access to inventory items.

**AA9 — Medium:** A **sidecar proxy** is a container that runs alongside an application service to handle cross-cutting concerns like networking and observability.
*   **Envoy in Istio:** Envoy is the data plane proxy. Istio is the control plane that configures Envoy.
*   **Data Plane vs. Control Plane:** Data plane handles traffic (Envoy). Control plane manages configuration and policy (Istiod).
*   **mTLS:** mTLS provides mutual authentication and encryption at the network layer. It solves the problem of verifying service identities without requiring the application code to implement TLS logic, simplifying security and preventing man-in-the-middle attacks.

**AA10 — Medium:** The **Strangler Fig pattern** involves gradually replacing parts of a legacy system with new services, effectively "strangling" the old system over time.
*   **Migration Strategy:**
    1.  Create a new API Gateway that routes specific URLs (e.g., `/api/users`) to the new microservice.
    2.  Keep the legacy monolith running for other URLs (e.g., `/api/orders`).
    3.  Migrate the `/api/users` logic from the monolith to the new service.
    4.  Repeat for other endpoints until the monolith is decommissioned.

**AA11 — Medium:** The **12-Factor App** methodology defines standards for building software-as-a-service apps.
*   **Factors:**
    1.  **Codebase:** Single source control repo.
    2.  **Dependencies:** Explicitly declare and lock dependencies.
    3.  **Config:** Store config in the environment.
    4.  **Backing Services:** Treat DBs, queues, etc., as attached resources.
    5.  **Build, Release, Run:** Strict separation of build, release, and run stages.
    6.  **Processes:** Stateless processes.
    *   *Why it matters:* Ensures portability between cloud providers and simplifies deployment.

**AA12 — Hard:**
*   **Kafka (Event-Driven):** Loose coupling (services don't know about each other), high scalability (backpressure), hard debugging (events are lost or delayed), ordering guarantees (per partition), failure handling (DLQ).
*   **REST/gRPC (Request-Driven):** Tight coupling (services know about each other), lower scalability (blocking calls), easier debugging, ordering guaranteed (usually), failure handling (HTTP codes).
*   **Choice:** Choose Event-Driven (Kafka) for decoupling, high throughput, and background processing. Choose Request-Driven for direct interaction, simple flows, and when ordering is critical.

**AA13 — Easy:** A **load balancer** distributes incoming network traffic across multiple servers.
*   **Layer 4 vs Layer 7:**
    *   **Layer 4 (Transport):** Routes based on IP and Port (TCP/UDP). Fast but dumb.
    *   **Layer 7 (Application):** Routes based on content (HTTP headers, URLs, cookies). Intelligent.
*   **Use Case for Layer 7:** Routing traffic based on the URL (e.g., `/api` goes to service A, `/static` goes to service B) or SSL termination.

**AA14 — Easy:** A **message queue** (e.g., RabbitMQ) ensures reliable delivery where the consumer pulls messages. A **log-based broker** (e.g., Kafka) is an append-only stream optimized for high throughput and replayability.
*   **Difference:** Queues are for task processing (decoupling). Kafka is for data streaming, analytics, and event sourcing (handling high volume of data).
*   **Pick Queue if:** You need guaranteed delivery, acknowledgments, and complex routing. Pick Kafka if you need high throughput, time-travel queries, or to aggregate logs.

**AA15 — Easy:** A **container** is a lightweight, standalone package of software that includes everything needed to run it (code, runtime, libs, settings). It shares the host OS kernel.
*   **Difference from VM:** VMs have a full Guest OS, are heavier, and take longer to start. Containers are lighter and faster.
*   **Popularity:** They are popular for microservices because they are portable (run anywhere), consistent across environments, and have low overhead, making scaling easy.

**AA16 — Easy:** **Stateless** services do not store local data; they rely on external storage (like a DB). **Stateful** services maintain local state (like a session or cache).
*   **Why Stateless scales easier:** You can add more instances of a stateless service to handle load without worrying about data synchronization between instances.
*   **Examples:** Stateless (API Gateway, Auth Service), Stateful (Database, Redis Cache).

**AA17 — Easy:** An **ORM** maps database tables to objects in code.
*   **Examples:** Hibernate (Java), Entity Framework (C#).
*   **Trade-offs:** ORMs increase developer productivity and reduce boilerplate code. However, they can hide SQL complexity, lead to performance issues (like the N+1 problem), and make complex queries difficult to write and optimize compared to raw SQL.

**AA18 — Medium:** The **Bulkhead** pattern isolates resources (like thread pools or connection pools) so that a failure in one part of the system does not consume all resources, causing the whole system to crash.
*   **Implementation:** Create separate thread pools for different services or deployment groups. If Service A's thread pool is exhausted, Service B can still use its own pool.
*   **Example:** A web server has a dedicated thread pool for handling API requests and a separate pool for processing background email jobs. If the email job hangs, API requests are unaffected.

**AA19 — Hard:**
*   **OT:** Centralized state, complex algorithms, good latency, poor offline support (needs server).
*   **CRDTs:** Decentralized, conflict-free (no need to resolve), higher latency (propagation), excellent offline support.
*   **Choice:** Choose **CRDTs** for a system that must support offline editing. They handle network partitions and offline changes gracefully by merging them automatically without conflicts.

**AA20 — Hard:** Distributed tracing tracks requests as they pass through services.
*   **Context Propagation:** Uses headers (W3C Trace Context, B3) to pass a `trace-id` and `span-id` from one service to the next.
*   **Sampling:** **Head-based** (sample at start) is efficient but misses late errors. **Tail-based** (sample at end) catches errors but is expensive.
*   **Storage:** Tools like Jaeger or Grafana Tempo store traces.
*   **Async Messaging:** To ensure continuity, the trace ID must be propagated as a message header (e.g., `Kafka-Trace-ID`) through the broker so the consumer can link the message to the parent trace.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** A **Type 1 hypervisor** runs directly on the hardware (bare-metal) without a host OS (e.g., VMware ESXi, Microsoft Hyper-V). A **Type 2 hypervisor** runs as an application on top of a host OS (e.g., Oracle VirtualBox, VMware Workstation).
*   **Examples:** Type 1 (ESXi, Hyper-V), Type 2 (VirtualBox, Parallels).

**OP2 — Easy:** A **SAN** (Storage Area Network) provides block-level storage over a network (e.g., iSCSI, Fibre Channel). It is used for databases. A **NAS** (Network Attached Storage) provides file-level storage (e.g., NFS, SMB). It is used for file sharing.
*   **Protocols:** SAN uses iSCSI/FC; NAS uses NFS/SMB.
*   **Use Case:** Use SAN for high-performance, low-latency needs like databases. Use NAS for general file storage and backup repositories.

**OP3 — Medium:** A **3-tier architecture** (Core, Distribution, Access) is hierarchical. A **Leaf-Spine** architecture is a flat, two-layer design.
*   **Why Leaf-Spine:** It eliminates the bottleneck of the distribution layer in 3-tier, offers better scalability, and reduces latency.
*   **Problem Solved:** 3-tier struggles to scale to thousands of servers due to the single distribution layer bottleneck. Leaf-Spine scales linearly.

**OP4 — Medium:** A **Proxmox cluster** typically requires at least 3 nodes.
*   **Quorum:** Required to prevent split-brain; a majority (2 out of 3) is needed to form a cluster.
*   **Fencing (STONITH):** Hardware-level power control to ensure a failed node cannot access shared storage.
*   **Shared Storage:** Ceph, iSCSI, or NFS.
*   **Failure Scenario:** If a node fails, the remaining nodes detect the loss of quorum or fencing. The cluster migrates VMs/Containers from the failed node to healthy nodes using the shared storage.

**OP5 — Medium:** **VLAN trunking** allows a single physical link to carry traffic for multiple VLANs. **802.1Q tagging** adds a 4-byte header to the Ethernet frame identifying the VLAN.
*   **Linux Configuration:** You create a VLAN interface on the physical NIC (e.g., `eth0`) with the specific ID (e.g., `ip link add link eth0 name eth0.10 type vlan id 10`). The OS then routes traffic for VLAN 10 to `eth0.10`.

**OP6 — Medium:**
*   **RAID 1:** Mirroring (Fast read, 50% capacity, 1 drive fault).
*   **RAID 5:** Striping + Parity (Good capacity, slow write, 1 drive fault).
*   **RAID 6:** Striping + Double Parity (Good capacity, slow write, 2 drive faults).
*   **RAID 10:** Striping + Mirroring (Fast read/write, 50% capacity, 1 drive fault).
*   **RAID Z2:** ZFS equivalent of RAID 6.
*   **Choice for DB:** **RAID 10**. It offers the best performance (read and write) and fault tolerance (1 drive failure) with acceptable capacity usage (50%).

**OP7 — Hard:**
*   **Architecture:**
    *   **Recursive Resolvers:** Clients query these to resolve names.
    *   **Authoritative Servers:** Host the actual DNS zones.
    *   **Forwarders:** Internal servers that cache queries to the internet.
    *   **Split-Horizon:** Separate zones for internal (AD) and external (Internet) use.
*   **DNSSEC:** Cryptographic signatures on the external zone.
*   **Laptop Move:** When on VPN, the client is configured to use internal DNS servers (via DHCP or static config). When in the office, it uses the office DNS. The split-horizon ensures the laptop resolves internal AD names correctly in both locations.

**OP8 — Hard:**
*   **Chain of Trust:** Root CA (offline) signs Subordinate CA, which signs End-Entity certificates.
*   **PKI Deployment:** Root (offline), Subordinate (online), CRL (revocation list) or OCSP (online check), Templates (auto-enrollment policies).
*   **Consequences:**
    *   **Compromised Subordinate CA:** Limited impact; only certificates issued by that CA are compromised.
    *   **Compromised Root CA:** Total compromise; all certificates issued by the root and its subordinates are invalid.

**OP9 — Hard:**
*   **MPLS:** High reliability, low latency, QoS, but expensive.
*   **IPsec VPN:** Cheaper, less reliable, higher latency.
*   **SD-WAN:** Flexible, software-defined, good for branch offices.
*   **WireGuard:** Fast, simple, modern.
*   **Recommendation:** **MPLS**. For 50 users per site with latency-sensitive VoIP, the guaranteed low latency and QoS of MPLS are worth the higher cost compared to the internet or SD-WAN.

**OP10 — Medium:** **iDRAC/iLO** is the out-of-band management interface (BMC) on servers.
*   **Criticality:** Allows you to reboot, install OS, or check logs even if the host OS is down or frozen.
*   **Risk:** If exposed to the internet, it is a major security vulnerability, often leading to remote code execution and full server compromise.

**OP11 — Medium:**
*   **LVM:** Standard logical volume manager for Linux.
*   **LVM-Thin:** Overprovisioning (allows more space than physical).
*   **ZFS:** File system + volume manager with advanced features (snapshots, checksums).
*   **Snapshots:** LVM and ZFS both use copy-on-write. ZFS snapshots are generally more efficient and atomic.

**OP12 — Hard:**
*   **Strategy:** A **Stretch Cluster** (2 sites).
*   **Ceph:** Use CRUSH rules to place replicas across sites.
*   **Latency:** Requires low latency (usually <5ms) between sites.
*   **Split-Brain:** If the WAN link fails, both sites have a majority of monitors and could both think they are the primary.
*   **Why 2-site is bad:** Without a tiebreaker (like a third site or a quorum disk), a split-brain scenario occurs where both sites try to write to storage, corrupting data.

**OP13 — Easy:** **DHCP** assigns IP addresses dynamically.
*   **DORA:** Discover (client) -> Offer (server) -> Request (client) -> Ack (server).
*   **Lease Expiry:** If the server is unavailable, the client will try to renew the lease. If it fails, it will use the cached IP until the lease expires completely, at which point it will stop working until it finds a server.

**OP14 — Easy:** A **managed switch** allows configuration of VLANs, QoS, and ACLs. An **unmanaged switch** is plug-and-play.
*   **Features:** VLANs for segmentation, QoS for prioritizing traffic (VoIP), and ACLs for security are critical in an enterprise environment.

**OP15 — Easy:** **NTP** (Network Time Protocol) synchronizes clocks.
*   **Criticality:** Essential for clustering (quorum), log correlation, and authentication (Kerberos).
*   **Drift Issues:** Clock skew can cause authentication failures, split-brain in clusters (where nodes disagree on who is the leader), and log confusion.

**OP16 — Easy:**
*   **Physical Server:** Runs directly on hardware (max performance, no virtualization overhead).
*   **VM:** Virtual machine (isolation, hypervisor overhead).
*   **Container:** Lightweight process (shared kernel, minimal overhead).
*   **Bare Metal:** Run workload directly on hardware for maximum performance (e.g., HPC, gaming, high-frequency trading).

**OP17 — Easy:** A **UPS** (Uninterruptible Power Supply) provides battery backup and filters power noise. A **Generator** provides long-term power from fuel.
*   **Why both:** The UPS bridges the gap between power loss and generator startup. The ATS automatically switches between utility power, UPS, and generator.

**OP18 — Medium:** **Active-Passive:** One node is active, one is standby. **Active-Active:** Both nodes are active and share the load.
*   **Implementation (Pacemaker/Corosync):**
    *   **Fencing (STONITH):** Ensures a failed node is powered off to prevent it from stealing resources.
    *   **Virtual IP:** A floating IP address moves to the active node.
    *   **Failover:** If the active node fails, the cluster detects the loss of the VIP and moves it to the passive node.

**OP19 — Hard:**
*   **3-2-1 Rule:** 3 copies of data, 2 different media types, 1 offsite.
*   **RPO/RTO:** Recovery Point Objective (data loss tolerance) and Recovery Time Objective (downtime tolerance).
*   **Types:** Full, Incremental, Differential.
*   **Deduplication:** Reduces storage footprint.
*   **Tape vs Disk vs Cloud:** Tape is cheap/archival; Disk is fast/standard; Cloud is offsite/accessible.
*   **Immutable Backups:** WORM (Write Once Read Many) to prevent ransomware encryption.
*   **Testing:** Regular restore drills.
*   **Backup vs DR:** Backup is a copy of data. DR is the plan, processes, and infrastructure to restore business operations after a disaster.

**OP20 — Hard:**
*   **802.1X Process:**
    *   **Supplicant:** The client device (e.g., laptop).
    *   **Authenticator:** The network switch port.
    *   **Authentication Server:** RADIUS server (e.g., ISE).
*   **EAP Methods:** **EAP-TLS** (certificates, highest security) vs **PEAP** (passwords, easier to deploy).
*   **Dynamic VLAN:** The switch assigns the client to a specific VLAN based on the user's identity.
*   **MAB (MAC Auth Bypass):** If a device doesn't support 802.1X, the switch falls back to authenticating based solely on the MAC address (usually restricted to a specific list).
