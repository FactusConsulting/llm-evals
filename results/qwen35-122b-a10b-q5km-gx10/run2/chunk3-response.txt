T1 — **Plan vs. Apply**
`tofu plan` generates an execution plan, showing what changes will be made without applying them. It is used for review and validation. `tofu apply` executes the changes defined in the plan (or auto-generates one), modifying the actual infrastructure.

T2 — **State and Remote State**
State is a JSON file mapping real-world resources to your configuration, tracking metadata and dependencies. Remote state stores this file in a shared backend (e.g., S3, GCS). It is important for team collaboration, enabling state locking to prevent concurrent writes, and securing sensitive data.

T3 — **count vs. for_each**
`count` creates resources based on an integer index (0, 1, 2...), which can cause resource reordering if items are removed. `for_each` iterates over a map or set, using keys as identifiers. `for_each` is preferred when resource identity matters (e.g., adding/removing items without destroying others) or when keys are meaningful.

T4 — **Manual Changes (Drift)**
If you change a resource outside OpenTofu, it creates "drift." OpenTofu detects this during `tofu plan` (which runs a refresh by default). It will show the configuration as needing to be updated to match the real state (or vice versa) and will attempt to revert or update the resource on `apply`.

T5 — **Snippet: 3 VMs with for_each**
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.key
  }
}
```

T6 — **remote_state vs. Outputs & Alternatives**
`terraform_remote_state` is a data source used to read `output` values from another root module's state file. Direct outputs cannot be accessed across root modules. The recommended alternative is to avoid cross-root-module dependencies entirely (using a single root module or CI/CD variables) to prevent tight coupling and state dependency cycles.

T7 — **Output Dependency Failure**
The output is empty because the `null_resource` hasn't finished executing when the dependent resource tries to read the output. This often happens if dependencies aren't explicitly declared. Fix: Ensure the dependent resource has `depends_on = [null_resource.kubeconfig]` or restructure so the output is only consumed after the resource is fully provisioned.

T8 — **Import CLI vs. Import Block**
`tofu import` (CLI) is imperative; you run it manually to map existing resources to state. The `import` block (v1.5+) is declarative; you define the mapping in HCL, allowing version control and automated planning. The block improves reproducibility and reduces manual CLI steps.

T9 — **Variable vs. Output**
A `variable` is an input parameter passed into a module or root configuration (e.g., instance size). An `output` is a value exposed after execution (e.g., public IP). Variables configure resources; outputs expose resource attributes for other modules or users.

T10 — **Provider and Init**
A provider is a plugin that interacts with an API (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, it fails because the provider plugins are not downloaded or configured in the `.terraform` directory. `init` initializes the working directory and downloads providers.

T11 — **.terraform.lock.hcl**
This file locks the specific versions of providers and modules used. It should be committed to version control to ensure all team members and CI pipelines use identical dependency versions, guaranteeing reproducible builds.

T12 — **Destroy and Target**
`tofu destroy` removes all resources managed by the state. To target a single resource, use the `-target` flag (e.g., `tofu destroy -target=aws_instance.web`). Note: Targeting can leave orphaned resources if dependencies aren't handled.

T13 — **Data Source**
A data source reads information from existing infrastructure without managing it. Use it when you need to reference external data (e.g., looking up an AMI ID, fetching a VPC ID) rather than creating a new resource.

T14 — **Locals vs. Variables**
`locals` define computed values within the module that aren't passed in as input. `variables` are inputs from the caller. Use `locals` for intermediate calculations, formatting, or values that don't need to be configurable by the user.

T15 — **Lifecycle Block**
*   `create_before_destroy`: Creates a new resource before destroying the old one (useful for immutable infrastructure like load balancers).
*   `prevent_destroy`: Prevents accidental deletion (useful for production databases).
*   `ignore_changes`: Ignores specific attribute changes (useful for tags managed externally).

T16 — **Moved Block**
A `moved` block tells OpenTofu that a resource has changed address (e.g., moved to a different module) without changing its identity. It updates the state file to point to the new address, preventing the resource from being destroyed and recreated during refactoring.

T17 — **Dependency Graph**
OpenTofu builds a Directed Acyclic Graph (DAG) to determine execution order.
*   **Implicit:** Created automatically when one resource references another (e.g., `aws_instance.web.subnet_id = aws_subnet.main.id`).
*   **Explicit:** Created using `depends_on`.
`depends_on` forces serialization, reducing parallelism. Use sparingly only when implicit dependencies are insufficient.

T18 — **Reducing Plan Time**
1.  **Split State:** Break monolithic state into smaller backend files (reduces refresh scope).
2.  **Parallelism:** Increase `-parallelism` flag (uses more CPU/network).
3.  **Caching:** Use remote backend caching or local caching plugins.
4.  **Import:** Import existing resources instead of recreating them (reduces API calls).
*Tradeoffs:* Splitting state increases complexity; higher parallelism may hit API rate limits.

T19 — **State Locking**
Locking prevents concurrent writes to state (usually via DynamoDB or backend API). If a CI pipeline crashes, the lock may remain stale. Break it manually with `tofu force-unlock <LOCK_ID>`. Risk: If two processes write simultaneously after unlocking, state corruption can occur.

T20 — **Migrate Local to S3/DynamoDB**
1.  Configure `backend "s3"` block with `dynamodb_table` in `terraform.tf`.
2.  Run `tofu init -migrate-state`.
3.  Confirm migration when prompted.
4.  Verify by running `tofu state list` and checking the S3 bucket for the state file.
The existing local state is uploaded to S3; the local file is removed.

A1 — **Playbook, Role, Task**
*   **Playbook:** YAML file defining a set of plays/tasks to run.
*   **Role:** Directory structure organizing tasks, vars, and handlers for reuse.
*   **Task:** A single unit of work (e.g., install a package) executed by a module.

A2 — **ansible_facts**
`ansible_facts` is a dictionary of system information gathered from the target host (e.g., IP, OS). Access OS family via `{{ ansible_os_family }}`.

A3 — **command, shell, raw**
*   **command:** Runs commands without shell features (safe, idempotent).
*   **shell:** Runs commands through a shell (supports pipes, redirection).
*   **raw:** Executes commands without Python (used for bootstrapping or minimal environments).

A4 — **Idempotency**
Idempotency means running a task multiple times yields the same result without side effects.
*   **Idempotent:** `apt: name=nginx state=present` (installs only if missing).
*   **Not Idempotent:** `shell: echo "hello" >> file.txt` (appends every time).

A5 — **Install htop Task**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
```

A6 — **Variable Precedence**
Low to High: Role defaults < Inventory file vars < Group vars < Host vars < Role vars < Play vars < Extra vars (`-e`). `set_fact` acts like host vars (high priority).

A7 — **RKE2 Agent Deployment**
Use `serial: 3` in the play to limit concurrency. Group the first 3 nodes in a specific inventory group (e.g., `rke2_masters`). Use `wait_for_connection` or a custom task to ensure the first batch is ready before the next batch starts (via `meta: flush_handlers` or loop logic).

A8 — **ansible-vault**
`ansible-vault` encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'secret_value' --name 'my_var'` and paste the result into the vars file, or encrypt the specific variable block within a file using `--encrypt` flags on the file content.

A9 — **Inventory File**
Lists target hosts.
*   **Static:** Hardcoded file (INI/YAML).
*   **Dynamic:** Script/API that generates the list at runtime (e.g., AWS EC2 inventory).

A10 — **Ad-hoc Disk Check**
`ansible webservers -m shell -a "df -h"`

A11 — **Handler**
A handler is a task that runs only if notified (i.e., when a task reports a change). Triggered via `notify: handler_name` in a task. Unlike regular tasks, handlers run once at the end of the play.

A12 — **ansible.cfg**
Configuration file for Ansible defaults. Common settings: `inventory` (path), `forks` (parallelism), `remote_user` (SSH user).

A13 — **register Keyword**
Stores the output of a task into a variable. Use it in subsequent tasks for conditional logic (e.g., `when: my_var.rc == 0`) or debugging.

A14 — **include_tasks vs. import_tasks**
*   **include_tasks:** Dynamic (loaded at runtime). Conditionals apply to the include statement itself.
*   **import_tasks:** Static (loaded at parse time). Conditionals apply to every task inside the imported file. Use `import` for static logic, `include` for dynamic loops.

A15 — **Ansible Galaxy**
A repository for sharing roles and collections. Use `requirements.yml` to list dependencies, then run `ansible-galaxy install -r requirements.yml` to install them.

A16 — **Connection Plugins**
*   **ssh:** Standard remote Linux/Unix management.
*   **local:** Runs tasks on the control node itself.
*   **network_cli:** For network devices (Cisco, Juniper) using CLI over SSH/Telnet.

A17 — **delegate_to and run_once**
*   `delegate_to`: Runs a task on a different host (e.g., localhost) instead of the current target.
*   `run_once`: Runs the task only once per play, regardless of host count.
*   **Example:** Generate a certificate on `localhost` using facts gathered from a remote web server.
```yaml
- name: Generate cert
  delegate_to: localhost
  run_once: true
  command: openssl req ...
```

A18 — **Performance Strategies**
1.  **Forks:** Increase `forks` in `ansible.cfg` (more parallel SSH connections).
2.  **Pipelining:** Enable `pipelining = True` (reduces SSH overhead).
3.  **Fact Caching:** Use `jsonfile` or `redis` to cache facts (skips gathering on re-runs).
4.  **Mitogen:** Plugin that optimizes SSH communication (significant speedup).
*Tradeoffs:* Higher forks consume more control node resources; caching requires storage management.

A19 — **Jinja2 Templating**
*   `{{ }}`: Expressions (variables).
*   `{% %}`: Statements (loops, if).
*   `{# #}`: Comments.
*   **Snippet:**
```jinja2
upstream backend {
{% for server in servers %}
  server {{ server.ip }}:{{ server.port }}; {# {{ server.name }} #}
{% endfor %}
}
```

A20 — **Zero-Downtime Rolling Deployment**
1.  **Serial:** Set `serial: 20%` to update batches.
2.  **Pre-task:** Remove host from Load Balancer (LB).
3.  **Deploy:** Run deployment tasks.
4.  **Health Check:** Use `uri` module to verify app status.
5.  **Post-task:** Add host back to LB.
6.  **Rollback:** Wrap in `block/rescue`. If health check fails, trigger rollback tasks (restore previous version) and re-add to LB.
