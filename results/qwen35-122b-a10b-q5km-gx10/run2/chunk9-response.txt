SC1-A
**Root Cause:** The failure is caused by the interaction between the **Pod Security Standard (PSS) Restricted** profile and the container image's default user.
1.  **PSS Baseline vs. Restricted:** Baseline allows `runAsNonRoot: true` without explicitly setting `runAsUser`, assuming the image might run as root but the policy allows it if not enforced. Restricted is stricter: if `runAsNonRoot: true` is set, Kubernetes *requires* an explicit `runAsUser` (non-zero) or `runAsGroup` to be defined in the `securityContext`.
2.  **Image USER Directive:** The new base image (`cgr.dev/chainguard/static:latest`) defaults `USER` to `root` (UID 0).
3.  **Conflict:** When the pod starts, the kubelet checks the `securityContext`. It sees `runAsNonRoot: true` but no `runAsUser`. The Restricted policy blocks the pod from starting because it cannot guarantee the container won't run as root (since the image defaults to root). The container runtime attempts to start as root, the admission controller or kubelet rejects it, or the container crashes immediately upon entrypoint execution due to permission errors, resulting in `CrashLoopBackOff`.

SC1-C
**Remediation Strategy:**
1.  **Immediate Fix:** Update the Kubernetes manifests to explicitly set `securityContext.runAsUser: 65534` (nobody) or a specific non-root UID. Update the Dockerfile to `USER 65534` explicitly.
2.  **Manifest Change:** Add `runAsUser` and `fsGroup` to the `securityContext` in all affected deployments.
3.  **CI Pipeline Gate:** Integrate a policy-as-code check (e.g., **Kyverno** or **OPA Gatekeeper**) in the CI pipeline. The pipeline should scan the manifest YAML before deployment. Rule: "If `securityContext.runAsNonRoot` is true, `securityContext.runAsUser` must be defined and non-zero."
4.  **Rollout:** Use a **Canary Deployment**. Apply the fix to 5% of pods first. Monitor for `CrashLoopBackOff` and error rates. If stable, progressively roll out to 100%. Use `kubectl rollout status` to ensure readiness before proceeding.

SC2-A
**Stale Data & Replication Lag:**
1.  **Implication:** Cross-region read replicas in AWS RDS use **asynchronous streaming replication**. When you promote a replica, any WAL (Write-Ahead Log) records not yet shipped from the primary are lost.
2.  **WAL Shipping:** WAL segments are shipped over the network. In cross-region scenarios (us-east-1 to eu-west-1), network latency (85ms) and bandwidth constraints cause lag.
3.  **Data Loss:** If the primary fails before shipping the last committed transaction, that data is lost upon promotion.
4.  **Quantification:** Check `pg_stat_replication` on the primary before failure for `sent_lsn`, `write_lsn`, and `replay_lsn`. The difference between `sent_lsn` and `replay_lsn` indicates the lag in bytes/transactions. Post-failover, check `pg_last_wal_receive_lsn()` vs `pg_last_wal_replay_lsn()` to see if catch-up is complete.

SC2-B
**Terraform Operations:**
1.  **Import:** Do not destroy the old instance yet. Import the promoted replica into state using its new ARN.
    ```bash
    terraform import aws_db_instance.primary <new-promoted-instance-arn>
    ```
2.  **Update References:** Update the Terraform code to reference the new ARN (or use a variable that points to the new ARN).
3.  **Detach Old:** Modify the old instance resource in code to `deletion_protection = false` and `skip_final_snapshot = true` (if safe), then run `terraform apply` to terminate it.
4.  **Avoid Recreate:** Ensure `lifecycle { prevent_destroy = true }` is removed from the old resource temporarily to allow termination, but ensure dependent resources (Security Groups, Route53) are updated to point to the new instance ID *before* applying the termination of the old one. Use `terraform state mv` if resource IDs change significantly.

SC2-C
**Architecture Design:**
1.  **Connection Management:** Use **RDS Proxy** instead of PgBouncer. RDS Proxy handles connection pooling, failover transparency, and IAM authentication, reducing the load on the DB during failover.
2.  **DNS Failover:** Configure **Route53 Health Checks** on the DB endpoint. Use a Failover Routing Policy. When the primary health check fails, Route53 updates the DNS TTL to point to the replica's endpoint.
3.  **Retry Logic:** Implement **Exponential Backoff with Jitter** in the application. Catch connection errors and retry with a circuit breaker (e.g., Hystrix/Resilience4j) to prevent thundering herd.
4.  **RPO < 1s:** Standard RDS cross-region async replication cannot guarantee RPO < 1s consistently. **Recommend Aurora Global Database**. Aurora replicates storage across regions with < 1s latency and allows promotion in < 60s with minimal data loss.
5.  **Why Aurora:** It separates compute from storage, enabling faster failover and consistent low-latency replication compared to standard RDS streaming replication.

SC4-A
**Top 5 Blockers & Solutions:**
1.  **Sticky Sessions (Local Memory):** K8s pods are ephemeral; local memory is lost on restart. **Solution:** Externalize sessions to **Redis** or a distributed cache.
2.  **Local NFS Mount (`/data/uploads`):** K8s nodes are stateless; local mounts don't persist across nodes. **Solution:** Use **ReadWriteMany (RWX)** Persistent Volumes (e.g., NFS CSI, EFS, or CephFS).
3.  **On-Prem Oracle:** Hard to containerize and manage HA on K8s. **Solution:** Migrate to **Oracle Cloud Infrastructure (OCI)** or **AWS RDS for Oracle**, or refactor to PostgreSQL if possible.
4.  **IBM MQ:** Legacy protocol, hard to run in containers. **Solution:** Use **IBM MQ on Cloud** or containerize MQ with persistent storage, or migrate to **RabbitMQ/Kafka**.
5.  **Stateful Monolith:** Hard to scale horizontally. **Solution:** Apply **Strangler Fig** to break into microservices; use **StatefulSets** for components requiring stable network IDs.

SC5-C
**Architectural Solution:**
1.  **CQRS:** Separate the **Write Model** (for transactions) from the **Read Model** (for reconciliation). The reconciliation job queries the Read Model or a dedicated **Read Replica**.
2.  **Read Replica:** Configure PostgreSQL to stream to a replica specifically for the CronJob. This isolates heavy analytical queries from the primary transactional DB.
3.  **Bulkhead Isolation:** Use **Kubernetes Resource Quotas** and **LimitRanges** to ensure the CronJob cannot consume all node CPU/Memory. Use **Database Connection Pooling** (PgBouncer) with separate pools for app vs. jobs.
4.  **Scheduling:** Move CronJob to off-peak hours (e.g., 03:00 UTC) or use **Kubernetes Job** with `backoffLimit` and `activeDeadlineSeconds`.
5.  **PDB:** Set `PodDisruptionBudget` on serving pods to ensure at least 2 replicas are always available, preventing the CronJob from evicting them during node pressure.

SC6-C
**Connectivity Comparison:**
1.  **AWS Direct Connect:**
    *   **Pros:** High bandwidth (10G+), low latency, dedicated.
    *   **Cons:** High cost, long setup time.
    *   **Zero-Trust:** Fits well; traffic stays on private backbone.
    *   **Routing:** Requires BGP configuration on TGW.
2.  **Second VPN + ECMP:**
    *   **Pros:** Cheaper, faster setup.
    *   **Cons:** Shared internet path, higher latency/jitter, IPsec overhead.
    *   **Zero-Trust:** Still encrypted, but less reliable.
    *   **Routing:** ECMP on TGW for load balancing.
3.  **Tailscale/Netbird (Mesh):**
    *   **Pros:** Easy setup, NAT traversal, built-in zero-trust (WireGuard).
    *   **Cons:** Overlay network overhead, dependency on control plane.
    *   **Zero-Trust:** Native identity-based routing.
    *   **Routing:** Overlay routing, bypasses traditional VPC routing tables.
    *   **Recommendation:** **Direct Connect** for production backbone reliability + **Tailscale** for management/developer access.

SC10-C
**Failover Orchestration:**
1.  **Detection:** **Prometheus Alertmanager** monitors site health (HTTP checks, DB latency). If > 3 nodes down in Chicago, trigger failover.
2.  **Sequence:**
    1.  **DNS:** GSLB updates DNS TTL to point to Dallas VIP.
    2.  **DB:** Patroni promotes Dallas standby to Primary.
    3.  **Cache:** Redis Sentinel promotes Dallas replica.
    4.  **MQ:** RabbitMQ Federation ensures queues are mirrored; consumers reconnect to Dallas.
    5.  **Storage:** MinIO Site Replication catches up (async).
    6.  **IaC:** Update OpenTofu state to reflect Dallas as primary region.
3.  **Split-Brain:** Use **Fencing** (STONITH). If Chicago comes back, it must not write. Patroni `nostream` mode prevents old primary from accepting writes.
4.  **Failback:** Once Chicago is stable, re-establish replication from Dallas to Chicago. Perform a controlled switchover (maintenance window) to revert DNS and DB roles.
