## Cloud Infrastructure Architecture

**CL1 — Easy:**
**IaaS (Infrastructure as a Service):** Provides virtualized computing resources over the internet. You manage OS, middleware, and apps. *Example:* AWS EC2.
**PaaS (Platform as a Service):** Provides a platform allowing customers to develop, run, and manage applications without dealing with infrastructure. *Example:* Azure App Service.
**SaaS (Software as a Service):** Delivers software applications over the internet, managed entirely by the provider. *Example:* Microsoft 365.

**CL2 — Easy:**
**Shared Responsibility Model:** The provider secures the cloud (hardware, network, hypervisor); the customer secures what is in the cloud (data, OS, config).
*   **IaaS VMs:** Provider secures physical hardware/network. You secure OS, patches, firewall rules, and data.
*   **Managed Kubernetes:** Provider secures control plane and nodes (OS). You secure workloads, RBAC, and container images.
*   **SaaS (M365):** Provider secures everything (app, infra, data). You secure user access (MFA), data classification, and device compliance.

**CL3 — Medium:**
*   **VPC:** Virtual network boundary (IP range).
*   **Subnet:** Segment within a VPC (specific IP range, tied to an AZ).
*   **Security Group (SG):** Instance-level firewall, **stateful** (tracks connections, allows return traffic automatically).
*   **NACL:** Subnet-level firewall, **stateless** (must explicitly allow inbound and outbound rules).
**Layering:** VPC contains Subnets. Subnets have NACLs. Instances in Subnets have SGs. Traffic flows: Internet -> NACL -> SG -> Instance.

**CL4 — Medium:**
**Landing Zone:** A pre-configured, secure multi-account environment baseline.
**OUs:** Organizational Units group accounts by function (Prod, Dev, Security).
**Guardrails:** SCPs (Service Control Policies) or Azure Policy to enforce compliance (e.g., block public S3).
**Shared Networking:** AWS Transit Gateway or Azure Hub-and-Spoke connects accounts securely without peering mesh.
**Centralized Logging:** Aggregates CloudTrail/Activity Logs to a security account for auditing.
**Single-Account Problem:** High blast radius, noisy billing, difficult permission management, lack of isolation between environments.

**CL5 — Medium:**
**Infrastructure as Code (IaC):** Managing infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu:** Declarative, multi-cloud, large ecosystem. Choose for multi-cloud or complex provisioning.
*   **Pulumi:** Imperative (general-purpose languages like Python/Go). Choose for teams wanting code logic in IaC.
*   **CloudFormation/Bicep:** Native to AWS/Azure. Choose for deep integration with provider-specific features.
*   **Crossplane:** Kubernetes-native IaC. Choose if managing cloud resources via K8s API.

**CL6 — Medium:**
*   **HPA:** Scales pods based on CPU/Memory metrics.
*   **VPA:** Adjusts pod resource requests/limits (requires restart).
*   **Cluster Autoscaler:** Adds/removes nodes based on pending pods.
*   **KEDA:** Event-driven autoscaler (e.g., queue depth, custom metrics).
**KEDA vs HPA:** Use KEDA when scaling depends on external events (e.g., Kafka lag, SQS messages) rather than resource utilization.

**CL7 — Hard:**
**Strategy:** Active-Passive (Warm Standby) is cost-effective for most.
*   **RPO/RTO:** Define max data loss (RPO) and recovery time (RTO).
*   **DB:** Async replication for cost/latency; Sync for zero data loss (higher latency).
*   **DNS:** Route53 Health Checks + Failover routing.
*   **State:** Use object storage (S3) for static state; DB for transactional.
**DR Types:**
*   **Pilot Light:** Minimal core running (DB), scale up on failover.
*   **Warm Standby:** Scaled-down version running continuously.
*   **Multi-site Active-Active:** Full traffic load in both regions (highest cost, lowest RTO).

**CL8 — Hard:**
**GitOps:** Git repository is the single source of truth for infrastructure and app state.
*   **ArgoCD vs Flux:** ArgoCD (UI-focused, Kubernetes-native), Flux (CLI-focused, CNCF standard). Both sync Git to Cluster.
*   **Secrets:** Do not store plain text in Git. Use Sealed Secrets (encrypted in Git), External Secrets Operator (fetch from Vault/AWS Secrets Manager), or Vault Agent.
*   **Drift:** GitOps controllers detect drift and automatically revert changes to match Git state (self-healing).

**CL9 — Hard:**
*   **StatefulSet:** Ensures stable network IDs and ordered, graceful deployment/deletion.
*   **PV/PVC:** Use `local` storage class for low latency (node-affinity required).
*   **Headless Service:** `clusterIP: None` for direct pod DNS resolution (e.g., `pod-0.service`).
*   **Init Containers:** Run before main app to prepare filesystem/config.
*   **ConfigMaps:** Mount as volumes to specific paths.
*   **PDB:** Prevents voluntary disruptions from taking down all pods simultaneously.

**CL10 — Medium:**
*   **Service Account:** K8s identity for pods.
*   **Workload Identity:** Mapping K8s SA to Cloud IAM identity (e.g., Azure AD Workload Identity).
*   **IRSA:** AWS-specific (IAM Roles for Service Accounts) using OIDC.
**Bad Practice:** Mounting static keys/credentials in pods exposes them to theft and rotation issues.
**Solution:** Workload Identity Federation uses OIDC to exchange a short-lived token for cloud credentials dynamically.

**CL11 — Medium:**
*   **Object Storage (S3):** Unstructured data (images, logs). High durability (11x9s).
*   **Block Storage (EBS):** Raw volumes for OS/DB. Low latency, high IOPS.
*   **File Storage (EFS):** Shared file system (NFS). Multi-attach.
**Use Cases:** DB on Block, Logs/Backups on Object, Shared Config on File.

**CL12 — Hard:**
**Zero Trust K8s:**
*   **Network Policies:** Default deny all traffic between pods.
*   **Service Mesh:** Enforce mTLS between services (Istio/Linkerd).
*   **Pod Identity:** No node credentials; use IRSA/Workload Identity.
*   **Admission:** OPA/Kyverno to enforce policies (e.g., no root user).
*   **Image Signing:** Cosign/Notary to verify images.
*   **Runtime:** Falco for syscall monitoring.
**Diff:** Traditional relies on perimeter firewalls; Zero Trust assumes breach and verifies every request/identity.

**CL13 — Easy:**
**CDN:** Distributed network of servers caching content closer to users.
**How:** DNS resolves to nearest edge node; edge serves cached content or fetches from origin.
**Services:** AWS CloudFront, Azure CDN.
**Use:** Static assets (JS, CSS, Images), video streaming. Avoid for dynamic, personalized, or real-time data.

**CL14 — Easy:**
**Region:** Geographic area (e.g., us-east-1).
**AZ:** Isolated data centers within a region.
**Multi-AZ:** Protects against data center failure (power, fire).
**Zonal Resources:** Tied to one AZ (e.g., EBS volume).
**Regional Resources:** Span multiple AZs (e.g., S3, Route53).

**CL15 — Easy:**
**Managed DB:** Cloud provider manages hardware, OS, patching, backups, and failover.
**Provider Tasks:** Provisioning, patching, backups, scaling storage, HA setup.
**User Tasks:** Schema design, query optimization, data management, access control.

**CL16 — Easy:**
**IAM:**
*   **Users:** Individual identities.
*   **Groups:** Collections of users.
*   **Roles:** Temporary credentials for services/users.
*   **Policies:** JSON documents defining permissions.
**Least Privilege:** Grant only permissions necessary for the task. Apply by starting with deny-all and adding specific allow rules.

**CL17 — Easy:**
**Serverless:** Event-driven compute without server management.
**Comparison:** AWS Lambda (broad ecosystem), Azure Functions (Microsoft stack), GCP Functions (Google stack).
**Cold Starts:** Latency when initializing a new container instance. Matters for latency-sensitive apps.
**Poor Fit:** Long-running processes (>15 mins), stateful apps, consistent high throughput (costlier than VMs).

**CL18 — Medium:**
*   **Ingress:** L7 routing, simple, controller-dependent.
*   **Gateway API:** Extensible, CRD-based, vendor-neutral standard.
*   **LB Annotations:** Cloud provider specific (L4/L7).
*   **Mesh Ingress:** Sidecar-based (Istio).
**TLS:** Terminate at LB/Ingress (easier) or Mesh (end-to-end).
**Gateway API:** Use for complex routing, multi-cluster, and future-proofing over legacy Ingress.

**CL19 — Hard:**
**Strategy:**
*   **Compute:** Savings Plans (flexible) or Reserved Instances (stable). Spot for fault-tolerant workloads.
*   **Storage:** Intelligent-Tiering for unknown access patterns. Archive for compliance data.
*   **Detection:** Automated idle resource detection (e.g., unused EIPs, low CPU VMs).
*   **FinOps:** Tagging strategy, showback/chargeback to teams.
*   **Tools:** AWS Cost Explorer, Kubecost, CloudHealth.
**Process:** Monthly budget reviews, anomaly detection alerts.

**CL20 — Hard:**
**Strategy:**
*   **Abstraction:** Kubernetes as the runtime layer.
*   **IaC:** Terraform for portability (providers differ).
*   **Networking:** Interconnect/VPN between clouds.
*   **Identity:** Federated SSO (Okta/Azure AD) across clouds.
**Trade-offs:** Multi-cloud increases complexity, cost, and skill requirements.
**Justification:** Compliance (data residency), avoiding single vendor outage, negotiating leverage.
**Unnecessary:** If one provider meets 99% of needs, multi-cloud adds overhead without value.

## OT Infrastructure Architecture

**OT1 — Easy:**
**Purdue Model (ISA-95):** Hierarchy of industrial control systems.
*   **Level 0:** Physical process (sensors/actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Supervisory Control (HMI, SCADA).
*   **Level 3:** Operations Management (MES, Historian).
*   **Level 4:** Business Planning (ERP).
*   **Level 5:** Enterprise Network.

**OT2 — Easy:**
**IT vs OT:** IT prioritizes Confidentiality; OT prioritizes Availability and Safety.
**Patching:** OT systems often run legacy OS (Win7/XP), proprietary software, and cannot tolerate downtime. Patching can break control logic or cause safety incidents.

**OT3 — Medium:**
**IDMZ:** Buffer zone between IT and OT.
**Traffic:** IT -> OT (Read-only data requests). OT -> IT (Data push to enterprise).
**Danger:** Direct L4->L1 allows malware to bypass security controls and directly manipulate physical processes.

**OT4 — Medium:**
1.  **Modbus TCP:** L1/L2 (Simple, legacy).
2.  **OPC UA:** L2/L3 (Secure, cross-platform).
3.  **EtherNet/IP:** L1 (Industrial Ethernet).
4.  **PROFINET:** L1 (Real-time).
5.  **MQTT:** L3/L4 (Lightweight messaging for IoT/Cloud).

**OT5 — Medium:**
**Data Diode:** Hardware device allowing data flow in only one direction.
**Firewall:** Software/Hardware allowing bi-directional traffic based on rules.
**Use Diode:** When OT data must go to IT/Cloud but IT must never send commands back (high security).
**Limitation:** No feedback loop; cannot acknowledge receipt or send commands.

**OT6 — Medium:**
**Flow:** PLC (L1) -> Historian (L3) -> OPC UA Server -> Edge Gateway -> MQTT Broker -> Cloud.
**Security:** Firewall between PLC and Historian. IDMZ between Historian and Edge. Encryption (TLS) on MQTT.
**Boundaries:** Physical separation at IDMZ; logical separation via VLANs.

**OT7 — Hard:**
**IEC 62443:**
*   **Zone:** Group of assets with same security requirements (e.g., "Safety Zone").
*   **Conduit:** Communication path between zones.
**Design:**
*   **Zone 1:** Corporate (L4).
*   **Zone 2:** Engineering (L3).
*   **Zone 3:** SCADA (L2).
*   **Zone 4:** PLCs (L1).
*   **Zone 5:** SIS (Safety).
*   **Conduits:** Firewalls between each zone. SIS Zone isolated from all others.

**OT8 — Hard:**
**Segmentation:**
*   **VLANs:** One per production line.
*   **Firewalls:** Between VLANs and at plant edge.
*   **Switches:** Managed L3 switches for routing.
*   **Remote Access:** Jump host in IDMZ with MFA and session recording.
*   **Transition:** Implement VLANs on new switches first, migrate line-by-line during maintenance windows.

**OT9 — Hard:**
**SIS vs BPCS:** BPCS controls process; SIS shuts down process if unsafe.
**IEC 61511:** Standard for Functional Safety.
**Isolation:** SIS must be independent. If ransomware hits BPCS, SIS must still function to prevent explosion/flood.
**Risk:** If SIS is compromised, safety is lost; physical damage or injury can occur.

**OT10 — Medium:**
**PLC:** Device-level control (fast, deterministic).
**DCS:** Plant-wide control (integrated, redundant).
**SCADA:** Monitoring and data collection (wide area).
**Coexistence:** Yes. DCS often manages PLCs; SCADA monitors DCS.

**OT11 — Medium:**
**Architecture:**
*   **Jump Host:** Bastion in IDMZ.
*   **MFA:** Required for all access.
*   **Recording:** Session logging for audit.
*   **Vendor:** Time-limited, supervised access.
**No Direct RDP:** Exposes HMI to internet/corporate threats; HMIs often lack modern security patches.

**OT12 — Hard:**
**Plan:**
*   **Detect:** IDS on Level 3/4 boundaries.
*   **Respond:** Isolate compromised segment (firewall block).
*   **Coordination:** Incident Commander + Plant Manager.
*   **Operator Role:** Switch to manual control if automation is compromised; prioritize physical safety over cyber recovery.
*   **Safety:** Do not reboot systems blindly; verify process state first.

**OT13 — Easy:**
**HMI:** Interface for operators to view/process data and issue commands.
**Role:** Real-time monitoring and control.
**Diff:** Engineering Workstation is for programming logic/configuring HMIs (L3/L2), not typically for runtime control.

**OT14 — Easy:**
**Historian:** Time-series database storing process data.
**Importance:** Trend analysis, compliance, troubleshooting.
**Plant Historian (L3):** High frequency, local retention.
**Enterprise Historian (L4):** Aggregated data, long-term retention, business analytics.

**OT15 — Easy:**
**Ladder Logic:** Graphical programming language resembling electrical relay logic.
**Device:** PLC.
**Dominance:** Legacy investment, easy for electricians to read, deterministic execution.

**OT16 — Easy:**
**RTU:** Remote Terminal Unit. Focuses on telemetry and communication over long distances.
**Diff:** PLC is for local control; RTU is for remote data collection.
**Environment:** Oil/gas pipelines, water distribution (remote, harsh environments).

**OT17 — Easy:**
**Analog:** Continuous signal (temperature, pressure). **Digital:** On/Off (valve open/closed).
**4-20mA:** "Live zero" (4mA = 0%). Allows detection of broken wire (0mA = fault). 0-20mA cannot distinguish 0 signal from broken wire.

**OT18 — Medium:**
**Asset Inventory:** List of all devices (IP, MAC, Firmware). Foundation for security (can't protect what you don't know).
**Tools:** Passive monitoring (packet capture), Active scanning (ping/port scan).
**Active Scanning Danger:** Can crash legacy PLCs/RTUs that don't handle unexpected traffic. Prefer passive.

**OT19 — Hard:**
**MITRE ATT&CK for ICS:** Framework mapping adversary tactics to OT-specific techniques.
**Tactics:** Reconnaissance, Initial Access, Execution, Persistence, Impact.
**Example:** Impact -> Manipulation of Control Logic.
**Diff:** Enterprise focuses on data theft; ICS focuses on physical disruption/safety.
**Use:** Map current controls against techniques to find gaps (e.g., lack of firmware integrity monitoring).

**OT20 — Hard:**
**Converged SOC:**
*   **Logs:** Passive collection (NetFlow, Syslog) to avoid load.
*   **SIEM:** Correlate IT and OT logs.
*   **Rules:** OT-specific (e.g., "PLC write command from IT IP").
*   **Staffing:** IT analysts handle network; OT engineers handle logic/safety.
*   **False Positives:** Tune rules carefully; OT traffic is noisy.
*   **Firmware Alert:** Verify legitimacy with vendor. If malicious: Isolate network segment, restore from known good backup, do not reboot until safe.
