AA1 — **Monolith vs. Microservices:** A monolith is a single unified codebase deployed as one unit; microservices are independently deployable services communicating over a network.
**3 Microservice Problems:**
1. **Distributed Tracing:** Debugging requests across multiple services is complex compared to local stack traces.
2. **Network Latency/Reliability:** Network calls are slower and less reliable than in-process calls; requires handling timeouts/retries.
3. **Data Consistency:** Maintaining ACID transactions across services is difficult; requires eventual consistency patterns (Sagas).

AA2 — **Sync vs. Async:**
*   **Synchronous:** Client waits for a response before proceeding. Example: **HTTP/REST** or **gRPC**.
*   **Asynchronous:** Client sends a request and continues; response is handled later via callback or polling. Example: **RabbitMQ** (AMQP) or **Kafka**.

AA3 — **API Gateway vs. Reverse Proxy:**
*   **Reverse Proxy:** Routes traffic based on IP/Host/Path, handles SSL termination, load balancing.
*   **API Gateway:** Adds business logic: authentication, rate limiting, request transformation, aggregation, and monitoring.
*   **Replacement:** An API Gateway *can* replace a reverse proxy, but it is heavier. For simple internal routing without auth logic, a lightweight reverse proxy (e.g., Nginx) is more efficient.

AA4 — **Saga Pattern:** A sequence of local transactions where each updates data within a single service. If one fails, compensating transactions undo previous changes.
*   **Choreography:** Services emit events; others listen and react. Decentralized, good for simple workflows.
*   **Orchestration:** A central coordinator tells services what to do. Centralized, better for complex workflows with many steps.
*   **Appropriateness:** Use Choreography for loose coupling; Orchestration for complex business logic requiring visibility.

AA5 — **CQRS:** Separates read (Query) and write (Command) models.
*   **Pairing with Event Sourcing:** Event Sourcing stores state changes as a log of events. CQRS reads from a projection of these events.
*   **Problem Solved:** Traditional CRUD couples read/write schemas, causing contention. CQRS + ES allows independent scaling of reads/writes and provides a full audit trail.

AA6 — **Circuit Breaker:** Prevents cascading failures by stopping requests to a failing service.
*   **States:** **Closed** (normal), **Open** (fail fast), **Half-Open** (test if service recovered).
*   **Differs from Retry:** Retry assumes transient failure; Circuit Breaker assumes persistent failure to save resources.
*   **Together:** Use Retry for transient network glitches; use Circuit Breaker when the service is consistently down to prevent resource exhaustion.

AA7 — **Multi-Tenant Isolation:**
1.  **Shared DB, Shared Schema:** *Low cost, high risk.* Noisy neighbors affect all. Security relies on row-level security.
2.  **Shared DB, Separate Schema:** *Medium cost/risk.* Better isolation, easier backup per tenant. Still shares DB engine resources.
3.  **Separate DB per Tenant:** *High cost, high security.* Complete isolation, easy to scale/backup per tenant. Noisy neighbor risk is minimal.
*   **Trade-off:** Start with Shared Schema for cost; move to Separate DB for enterprise/regulated tenants.

AA8 — **Eventual vs. Strong Consistency:**
*   **Eventual:** Updates propagate asynchronously; replicas may differ temporarily.
*   **Strong:** All reads see the latest write immediately.
*   **Inventory Architecture:** Use **Strong Consistency**.
*   **Data Store:** Relational DB (PostgreSQL) with ACID transactions.
*   **Patterns:** Pessimistic locking (`SELECT FOR UPDATE`) or Optimistic locking (versioning) to prevent overselling. At scale, use a dedicated inventory service with distributed locks (e.g., Redis Redlock) if DB throughput is insufficient.

AA9 — **Sidecar Proxy:** A helper container deployed alongside the main app container to handle network traffic.
*   **Envoy in Istio:** Envoy handles L7 routing, mTLS, and observability.
*   **Data Plane:** Envoy proxies (handle traffic). **Control Plane:** Istiod (manages config/policies).
*   **mTLS:** Encrypts traffic between services automatically. Solves the problem of managing certificates and auth in application code; ensures zero-trust network security.

AA10 — **Strangler Fig:** Incrementally migrate functionality from a legacy system to a new system by routing traffic to the new system.
*   **Strategy:** Place a reverse proxy (e.g., Nginx) in front of the .NET Framework monolith. Route specific paths (e.g., `/api/v2/`) to new .NET 8 microservices. Gradually move more endpoints until the monolith is "strangled" and can be decommissioned.

AA11 — **12-Factor App:** Methodology for building SaaS apps.
1.  **Codebase:** One codebase tracked in VCS.
2.  **Dependencies:** Explicitly declare dependencies.
3.  **Config:** Store config in environment variables.
4.  **Backing Services:** Treat services (DB, Queue) as attached resources.
5.  **Build/Release/Run:** Strictly separate stages.
6.  **Processes:** Execute app as one or more stateless processes.
*   **Why:** Ensures portability, scalability, and parity between dev/prod.

AA12 — **Event-Driven (Kafka) vs. Request-Driven (REST/gRPC):**
*   **Coupling:** Kafka (Loose), REST (Tight).
*   **Scalability:** Kafka (High throughput, async), REST (Limited by request/response).
*   **Debugging:** Kafka (Harder, need log replay), REST (Easier, request logs).
*   **Ordering:** Kafka (Partition-level), REST (None).
*   **Failure:** Kafka (Retry via consumer lag), REST (Retry logic in client).
*   **Choice:** Use REST for immediate user feedback (APIs). Use Kafka for background processing, audit trails, and decoupling heavy workflows.

AA13 — **Load Balancer:** Distributes network traffic across multiple servers.
*   **Layer 4 (Transport):** Routes based on IP/Port (TCP/UDP). Fast, no app awareness.
*   **Layer 7 (Application):** Routes based on HTTP headers, URL, cookies.
*   **Use Case:** L7 required for path-based routing (e.g., `/api` to backend, `/static` to CDN) or SSL termination.

AA14 — **Message Queue vs. Log Broker:**
*   **Queue (RabbitMQ):** Tasks are consumed and deleted. Point-to-point or Pub/Sub. Good for work distribution.
*   **Log (Kafka):** Messages are retained for a period. Consumers read at their own pace. Good for event streaming and replay.
*   **Pick:** RabbitMQ for task queues (emails, jobs). Kafka for event sourcing, analytics, or high-throughput streaming.

AA15 — **Container vs. VM:**
*   **Container:** Shares the host OS kernel; isolates user space. Lightweight, fast startup.
*   **VM:** Virtualizes hardware; runs a full guest OS. Heavier, slower startup.
*   **Popularity:** Containers are ideal for microservices due to density, portability, and CI/CD integration.

AA16 — **Stateless vs. Stateful:**
*   **Stateless:** No client data stored on server between requests (e.g., Web Server).
*   **Stateful:** Server stores session/data (e.g., Database).
*   **Scaling:** Stateless services can scale horizontally by adding nodes behind a load balancer without session affinity. Stateful services require complex data replication/sharding.

AA17 — **ORM:** Maps objects in code to database tables.
*   **Examples:** **Hibernate** (Java), **Entity Framework** (.NET), **SQLAlchemy** (Python).
*   **Trade-offs:**
    *   *ORM:* Faster development, abstraction.
    *   *Raw SQL:* Better performance, fine-grained control, harder to maintain.

AA18 — **Bulkhead Pattern:** Isolates resources to prevent a failure in one part of the system from affecting others.
*   **Relation:** Like bulkheads on a ship; if one compartment floods, the ship stays afloat.
*   **Implementation:** Assign separate thread pools to different external service calls. If Service A hangs, its thread pool exhausts, but Service B's pool remains available. In Kubernetes, use separate Deployment groups with resource limits.

AA19 — **OT vs. CRDT:**
*   **OT:** Server-centric. Operations are transformed against each other. Complex to implement correctly.
*   **CRDT:** Decentralized. Data structures mathematically guarantee convergence.
*   **Comparison:** OT has lower latency for simple text but struggles with offline. CRDTs handle offline editing naturally but have higher memory overhead.
*   **Choice:** **CRDTs** for offline support. They allow local edits to merge automatically without a central server resolving conflicts.

AA20 — **Distributed Tracing Challenges:**
*   **Context Propagation:** Use W3C Trace Context headers (`traceparent`) to pass trace ID across services.
*   **Sampling:** Head-based (decide at entry) vs. Tail-based (decide after seeing errors). Tail-based is better for debugging but requires buffering.
*   **Storage:** Jaeger/Tempo store traces; query via trace ID.
*   **Async Messaging:** Inject trace ID into Kafka message headers. The consumer extracts the header to continue the trace span, ensuring continuity across async boundaries.

OP1 — **Hypervisor Types:**
*   **Type 1 (Bare-metal):** Runs directly on hardware. Examples: **VMware ESXi, Microsoft Hyper-V**.
*   **Type 2 (Hosted):** Runs on top of an OS. Examples: **VirtualBox, VMware Workstation**.
*   **Use:** Type 1 for production servers; Type 2 for development/testing.

OP2 — **SAN vs. NAS:**
*   **SAN (Storage Area Network):** Block-level storage. Protocols: **Fibre Channel, iSCSI**. Use for databases requiring low latency.
*   **NAS (Network Attached Storage):** File-level storage. Protocols: **NFS, SMB/CIFS**. Use for file shares and backups.

OP3 — **3-Tier vs. Leaf-Spine:**
*   **3-Tier:** Core, Distribution, Access. High latency for East-West traffic (server-to-server).
*   **Leaf-Spine:** Every leaf connects to every spine. Constant 2-hop latency.
*   **Problem Solved:** Leaf-spine eliminates bottlenecks in modern data centers where server-to-server traffic (East-West) exceeds client-to-server (North-South).

OP4 — **Proxmox HA Architecture:**
*   **Nodes:** Minimum 3 nodes for quorum (prevents split-brain).
*   **Storage:** Ceph (integrated) or iSCSI/NFS.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) to power off failed nodes.
*   **Failure:** If a node fails, the cluster detects loss of quorum (if 2 nodes left) or restarts VMs on remaining nodes (if 2 nodes remain).

OP5 — **VLAN Trunking:**
*   **Concept:** Carries multiple VLANs over a single physical link.
*   **802.1Q:** Adds a 4-byte tag to Ethernet frames identifying the VLAN ID.
*   **Linux Config:** Create sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`. Assign IPs to `eth0.10`, `eth0.20`, etc.

OP6 — **RAID Levels:**
*   **RAID 1:** Mirror (50% capacity).
*   **RAID 5:** Striping + Parity (N-1 capacity). Write penalty.
*   **RAID 6:** Striping + Dual Parity (N-2 capacity). Tolerates 2 drive failures.
*   **RAID 10:** Mirror + Stripe (50% capacity). High performance, high redundancy.
*   **RAID Z2:** ZFS equivalent of RAID 6.
*   **Choice:** **RAID 10** for 6 drives DB. Better write performance than RAID 5/6, sufficient redundancy for most DBs.

OP7 — **Enterprise DNS Architecture:**
*   **Internal:** Windows AD Integrated DNS (Authoritative + Recursive).
*   **External:** Authoritative servers in DMZ (e.g., Route53, BIND).
*   **Split-Horizon:** Internal clients resolve `internal.corp` to private IPs; external resolve to public.
*   **Forwarders:** Internal DNS forwards external queries to ISP/Cloud DNS.
*   **Conditional Forwarding:** Forward specific internal zones to specific servers.
*   **Laptop Move:** DHCP updates DNS records; client switches DNS server IP based on network profile (Office vs. VPN).

OP8 — **PKI Chain:**
*   **Chain:** Root CA (Offline) -> Subordinate CA (Issuing) -> End Entity (Server/User).
*   **Revocation:** CRL (List) vs. OCSP (Real-time query).
*   **Templates:** Define key usage, validity periods.
*   **Consequences:** Compromised Subordinate = Revoke Sub CA cert, reissue all end-entity certs. Compromised Root = Revoke Root, rebuild entire PKI infrastructure (catastrophic).

OP9 — **WAN Consolidation:**
*   **MPLS:** High cost, high reliability, SLA guaranteed.
*   **IPsec:** Low cost, variable latency, complex config.
*   **SD-WAN:** Intelligent routing over multiple links (MPLS + Internet), cost-effective, good for VoIP.
*   **WireGuard:** Simple, fast, but lacks enterprise management features.
*   **Recommendation:** **SD-WAN**. Balances cost, manages latency-sensitive VoIP via QoS over multiple links, and simplifies management for 5 remote sites.

OP10 — **OOB Management:**
*   **Tools:** iDRAC (Dell), iLO (HPE), IPMI (Generic).
*   **Criticality:** Allows remote power cycle, BIOS access, and console access when OS is down.
*   **Risk:** Exposed IPMI = Remote Root Access. Attackers can reboot, install malware, or steal data. Must be on a management VLAN, never internet-facing.

OP11 — **LVM vs. ZFS:**
*   **LVM:** Logical Volume Manager (Linux). Flexible resizing. Snapshots are copy-on-write but depend on underlying FS.
*   **LVM-Thin:** Allows over-provisioning of storage pools.
*   **ZFS:** Combined Filesystem + Volume Manager. Snapshots are instant, space-efficient, and include data integrity (checksums).
*   **Use:** LVM for general Linux flexibility. ZFS for data integrity, advanced snapshots, and storage pools.

OP12 — **Stretch Cluster/DR:**
*   **Design:** 3-node cluster across 2 sites is risky. Use a **Witness Node** (3rd site or cloud) for quorum.
*   **Ceph:** CRUSH rules must ensure replicas are on different sites.
*   **Latency:** Ceph requires <5ms latency. If sites are far, performance degrades.
*   **Split-Brain:** Without a tiebreaker (witness), both sites may think they are primary, corrupting data.
*   **Recommendation:** Active-Passive DR (Backup/Restore) is often safer than Active-Active Stretch Cluster for Ceph unless latency is very low.

OP13 — **DHCP:**
*   **Process:** **D**iscover (Client broadcasts), **O**ffer (Server proposes IP), **R**equest (Client accepts), **A**ck (Server confirms).
*   **Unavailable:** Client uses **APIPA** (169.254.x.x) if lease expires and no server is found. No internet access.

OP14 — **Managed vs. Unmanaged Switch:**
*   **Unmanaged:** Plug-and-play. No config.
*   **Managed:** Configurable via CLI/Web.
*   **Features:** VLANs, Port Security, QoS, SNMP monitoring, STP (loop prevention).
*   **Importance:** Essential for network segmentation, security, and troubleshooting in enterprises.

OP15 — **NTP:**
*   **Purpose:** Network Time Protocol synchronizes clocks.
*   **Criticality:** Kerberos auth fails if time drift >5 mins. Logs become uncorrelatable. DB replication fails.
*   **Drift:** Causes authentication errors, data inconsistency, and security vulnerabilities (token replay).

OP16 — **Physical vs. VM vs. Container:**
*   **Physical:** Bare metal.
*   **VM:** Virtualized OS.
*   **Container:** Virtualized App.
*   **Bare Metal Use:** High-performance databases, HPC, or workloads requiring direct hardware access (GPU passthrough) where virtualization overhead is unacceptable.

OP17 — **UPS vs. Generator:**
*   **UPS:** Battery backup. Bridges gap between power loss and generator start (seconds).
*   **Generator:** Fuel-powered. Provides power for hours/days.
*   **ATS:** Automatically switches power source from Utility to Generator.
*   **Need Both:** UPS prevents immediate shutdown during transfer; Generator sustains long outages.

OP18 — **Active-Passive vs. Active-Active:**
*   **Active-Passive:** One node handles traffic; other waits.
*   **Active-Active:** Both handle traffic.
*   **PostgreSQL HA:** Use **Pacemaker/Corosync**.
*   **Fencing:** STONITH ensures failed node is powered off to prevent split-brain.
*   **VIP:** Virtual IP floats to the active node.
*   **Failover:** Automatic promotion of standby to primary upon failure detection.

OP19 — **Backup & Recovery:**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO:** Max data loss. **RTO:** Max downtime.
*   **Types:** Full (slow), Incremental (fast, complex restore), Differential.
*   **Immutable:** Write-Once-Read-Many (WORM) storage to prevent ransomware encryption of backups.
*   **Backup vs. DR:** Backup is data copy. DR is the plan/process to restore operations (including network, config, and data).
*   **Testing:** Regular restore drills to verify integrity.

OP20 — **802.1X:**
*   **Roles:** **Supplicant** (Client), **Authenticator** (Switch), **Authentication Server** (RADIUS).
*   **EAP:** **EAP-TLS** (Certificates, most secure), **PEAP** (Username/Password).
*   **Dynamic VLAN:** RADIUS returns VLAN ID; switch assigns port to that VLAN.
*   **Fail:** Port blocked or assigned to "Guest/Quarantine" VLAN.
*   **MAB:** Uses MAC address as credential. Used for printers/phones that lack 802.1X supplicants. Less secure (MAC spoofing).
