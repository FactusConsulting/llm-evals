## OpenTofu / Terraform (20 questions)

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` creates an execution plan, showing what actions OpenTofu will take (create, update, destroy) without making changes. `tofu apply` executes the plan, modifying the infrastructure to match the configuration. Plan is for review; Apply is for execution.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file mapping real-world resources to your configuration, tracking metadata and dependencies. Remote state (e.g., S3, GCS) is crucial for team collaboration (shared source of truth), state locking (prevents concurrent writes), and security (state often contains secrets).

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` creates resources based on an integer index (0, 1, 2). `for_each` creates resources based on keys in a map or set. `for_each` is preferred because removing an item from a `count` list shifts indices, causing unintended recreation of downstream resources. `for_each` keys remain stable.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This creates "drift." On the next `tofu plan`, OpenTofu compares the state file against the actual cloud API. It detects the difference and proposes a change to either revert the manual change or update the state to match the manual change (depending on the diff). `tofu apply` enforces the configuration state.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads the raw state file of another project, creating tight coupling and versioning issues. The recommended alternative is using a **Module** with explicit `output` values passed to the root module. This ensures type safety, encapsulation, and prevents accidental dependency on internal state structure.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
**Why:** Outputs are evaluated during the plan phase, but provisioners run during the apply phase. The output cannot be known until the provisioner executes, causing a dependency loop or empty value during planning.
**Fix:** Avoid using provisioners for critical outputs. Instead, use cloud-init/userdata to generate the config, or split the workflow: Apply the cluster first, then run a separate OpenTofu run to fetch the kubeconfig (using a data source or script) and pass it to dependent modules.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` maps existing infrastructure to state. Limitations: Not all resources support import; config must match the imported resource exactly. The `import` block (v1.5+) allows declarative imports within the HCL code, making the import process version-controlled and reproducible, rather than a one-off CLI command.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a placeholder for values. **Input variables** (`variable` block) accept values from the user or environment to configure the module. **Output values** (`output` block) expose specific data from the module to the caller or CLI.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that interacts with APIs (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, it fails because the provider plugins are not downloaded and the backend is not configured. `init` initializes the working directory.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It locks the versions of providers and modules used in the project. Committing it ensures all team members and CI pipelines use the exact same provider versions, preventing unexpected breaking changes or behavior differences.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all managed resources defined in the configuration. To target a single resource, use the `-target` flag: `tofu destroy -target=aws_instance.web`. Note: This leaves orphaned dependencies.

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source reads information from existing infrastructure without managing it. Example: Use `data "aws_ami" "latest"` to find the latest Ubuntu AMI ID instead of creating a new AMI resource.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
`variables` are inputs from outside the module. `locals` are internal computed values. Use `locals` for derived values, complex expressions, or to reduce repetition within a module. Do not expose internal logic via `variables` unless it needs to be configurable by the caller.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
*   `create_before_destroy`: Creates new resource before destroying old one (useful for immutable infrastructure like load balancers).
*   `prevent_destroy`: Prevents accidental deletion (useful for production databases).
*   `ignore_changes`: Ignores specific attribute drift (useful for attributes managed externally, like `tags` updated by a script).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has changed address (e.g., moved from one module to another) but is the same physical resource. It updates the state mapping without triggering a destroy/create cycle, preserving data and avoiding downtime.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG) of resources. **Implicit dependencies** are inferred from attribute references (e.g., `aws_instance.web.subnet_id = aws_subnet.main.id`). **Explicit dependencies** use `depends_on`. `depends_on` forces serialization, reducing parallelism. Use sparingly because it slows down execution and should only be used when implicit references are insufficient (e.g., external API dependencies).

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1.  **State Sharding:** Split state into multiple backends (e.g., by environment or service). *Tradeoff:* Increased complexity in managing dependencies between states.
2.  **Targeted Planning:** Use `-target` to plan specific modules. *Tradeoff:* Risk of missing global drift; requires manual coordination.
3.  **Disable Refresh:** Use `-refresh=false` if you trust the state. *Tradeoff:* Plan may not reflect actual cloud drift.
4.  **Optimize Provider Config:** Reduce unnecessary data source lookups or use `skip_destroy` on heavy resources. *Tradeoff:* May hide configuration issues.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**
Locking prevents concurrent writes to state (usually via DynamoDB or backend API). If a pipeline crashes, the lock may persist (stale lock). You can break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually writing, forcing unlock can corrupt the state file. Verify no other process is running before unlocking.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process.**
1.  Configure the new `backend "s3"` block in `main.tf` with `dynamodb_table` for locking.
2.  Run `tofu init -migrate-state`.
3.  OpenTofu will prompt to migrate the local `terraform.tfstate` to S3. Confirm.
4.  Verify the state exists in S3 and the lock table is active.
5.  Commit the updated `main.tf` and `.terraform.lock.hcl`.
6.  Run `tofu plan` to ensure no drift is detected post-migration.

## Ansible (20 questions)

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
*   **Task:** A single action (e.g., install package).
*   **Playbook:** A YAML file containing one or more plays (lists of tasks) executed on hosts.
*   **Role:** A reusable directory structure containing tasks, vars, handlers, etc., designed to be shared and imported into playbooks.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary of system information gathered by the `setup` module. Access OS family via `{{ ansible_os_family }}`.

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
*   `command`: Runs commands without shell features (safe, idempotent). Use for simple commands.
*   `shell`: Runs commands through a shell (supports pipes, variables). Use when shell features are needed.
*   `raw`: Executes commands without Python on the remote node. Use for bootstrapping or when Python is unavailable.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means running a task multiple times yields the same result without side effects.
*   **Idempotent:** `apt: name=nginx state=present` (Installs only if missing).
*   **Not Idempotent:** `shell: echo "log" >> /var/log/app.log` (Appends every run).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
From lowest to highest priority:
1.  Role defaults
2.  Inventory file or script group vars
3.  Playbook group vars
4.  Inventory host vars
5.  Playbook host vars
6.  Role vars
7.  Block vars
8.  Task vars
9.  Include vars
10. **set_fact** / register
11. **extra_vars** (`-e`)
*Note: `extra_vars` always win.*

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**
Use `serial: 3` in the play to limit concurrency. Use `wait_for` in a task to ensure the first 3 nodes are ready (e.g., port 6443 open) before the next batch proceeds.
```yaml
- hosts: rke2_nodes
  serial: 3
  tasks:
    - name: Install RKE2
      ...
    - name: Wait for API
      wait_for: port=6443 host={{ inventory_hostname }}
```

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` encrypts sensitive data. To encrypt a single variable, you cannot do it natively within a standard vars file without encrypting the whole file. The workaround is to store the sensitive variable in a separate file (e.g., `secrets.yml`), encrypt that file with `ansible-vault encrypt secrets.yml`, and import it.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
Inventory defines target hosts. **Static:** A simple INI or YAML file listing hosts. **Dynamic:** A script or plugin that queries an API (e.g., AWS, Azure) to generate the host list at runtime.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a task that runs only if notified. It runs once at the end of the play, even if notified multiple times. Triggered using `notify: handler_name` within a task.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
It configures Ansible behavior. Common settings: `inventory` (path), `remote_user` (SSH user), `forks` (parallelism), `host_key_checking` (security).

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
`register` saves the output of a task into a variable. Use it in subsequent tasks via `{{ registered_var.stdout }}` or `{{ registered_var.rc }}`.
Example:
```yaml
- shell: echo "test"
  register: out
- debug: msg="{{ out.stdout }}"
```

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
`import_tasks` is static (parsed at playbook load time). `include_tasks` is dynamic (parsed at runtime). Use `include_tasks` when you need to apply conditions (`when`) to the inclusion itself or loop over files. `import_tasks` is faster but less flexible for conditionals.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Galaxy is a repository for sharing Ansible content. Create `requirements.yml` listing roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins define how Ansible talks to the target.
*   `ssh`: Standard Linux/Unix remote execution.
*   `local`: Runs tasks on the control node itself (`localhost`).
*   `network_cli`: For network devices (Cisco, Juniper) using CLI over SSH/Telnet.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
`delegate_to` runs a task on a different host than the target. `run_once` runs the task only once per play.
**Example:** Generate a certificate on localhost using facts from a remote web server.
```yaml
- name: Generate Cert
  delegate_to: localhost
  run_once: true
  command: openssl req ...
  vars:
    cn: "{{ ansible_fqdn }}"
```

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs.**
1.  **Increase Forks:** `forks = 50` (default 5). *Tradeoff:* Higher CPU/RAM on control node.
2.  **Pipelining:** `pipelining = True` in `ansible.cfg`. *Tradeoff:* Requires SSH config changes; reduces file transfer overhead.
3.  **Fact Caching:** Use `jsonfile` or `redis` cache. *Tradeoff:* Stale facts if system changes outside Ansible.
4.  **Mitogen:** Plugin for async execution. *Tradeoff:* Adds complexity and dependency; not officially supported by Ansible Core.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
*   `{{ }}`: Print variable/expression.
*   `{% %}`: Control flow (loops, if).
*   `{# #}`: Comment.
**Snippet:**
```jinja2
upstream backend {
{% for server in backends %}
  server {{ server.ip }}:{{ server.port }}; # {{ server.name }}
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.**
1.  **Serial:** Set `serial: 4` to update 4 servers at a time.
2.  **Pre-tasks:** Deregister server from Load Balancer (LB).
3.  **Tasks:** Deploy new code.
4.  **Health Check:** Use `uri` module to check `/health`. Fail if not 200 OK.
5.  **Post-tasks:** Register server back to LB.
6.  **Rollback:** Wrap deployment in `block/rescue`. If health check fails, `rescue` triggers a rollback task (revert code) and re-registers to LB.
```yaml
- hosts: webservers
  serial: 4
  tasks:
    - block:
        - name: Deregister LB
          ...
        - name: Deploy
          ...
        - name: Health Check
          uri: ...
          register: health
          failed_when: health.status != 200
        - name: Register LB
          ...
      rescue:
        - name: Rollback
          ...
        - name: Re-register LB
          ...
```
