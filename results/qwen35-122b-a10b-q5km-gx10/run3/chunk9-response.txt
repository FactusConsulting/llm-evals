SC1-A
**Root Cause:** The failure is caused by a conflict between the **Restricted Pod Security Standard (PSS)** and the container image's default user.
1.  **PSS Interaction:** The `Restricted` profile enforces `runAsNonRoot: true`. This means the container *must* run as a non-root user (UID != 0).
2.  **Image Directive:** The new base image (`cgr.dev/chainguard/static:latest`) sets `USER root` in its Dockerfile.
3.  **Pod Spec:** The pod spec sets `securityContext.runAsNonRoot: true` but does *not* set `securityContext.runAsUser`.
4.  **The Conflict:** Kubernetes attempts to run the container as the user defined in the image (`root`). The Kubelet checks the `runAsNonRoot` constraint. Since the effective user is root, the admission controller (or Kubelet enforcement) rejects the pod, or the container runtime fails to start it because it violates the security policy. In Baseline mode, running as root was allowed; in Restricted, it is forbidden.
5.  **Result:** The pod fails to start, enters `CrashLoopBackOff` (or `CreateContainerConfigError` depending on enforcement point), and restarts repeatedly.

SC1-C
**Remediation Strategy:**
1.  **Immediate Fix (Image):** Modify the Dockerfile to set a non-root user explicitly (e.g., `USER 1000`). Rebuild and push the image.
2.  **Manifest Fix:** Update the Kubernetes Deployment manifests to explicitly set `securityContext.runAsUser: 1000` and `runAsGroup: 1000` to ensure compliance with Restricted PSS.
3.  **CI Pipeline Gate:** Add a pre-commit or CI step using **OPA Gatekeeper** or **Kyverno** to validate manifests against PSS Restricted before merging. Additionally, integrate **Trivy** or **Grype** to scan images for `USER root` in the Dockerfile history.
4.  **Rollout:** Use a **Rolling Update** strategy with `maxSurge: 1` and `maxUnavailable: 0`. Monitor `kubectl rollout status`. If the new image fails, the old version remains available.
5.  **Prevention:** Enforce image signing (Cosign) and require non-root user in the base image policy.

SC2-A
**Stale Data & Replication Lag:**
1.  **Implication:** Cross-region read replicas typically use **asynchronous replication**. When the primary (us-east-1) fails, the replica (eu-west-1) promotes itself. Any transactions committed on the primary but not yet shipped/applied to the replica are lost.
2.  **WAL Shipping:** PostgreSQL ships Write-Ahead Logs (WAL) segments. In async mode, the primary acknowledges the client commit before the replica confirms receipt.
3.  **Data Loss:** The "data loss window" is the time between the last confirmed transaction on the replica and the primary failure.
4.  **Quantification:** Check `pg_stat_replication` on the primary before failure (if accessible) or `pg_last_wal_receive_lsn` vs `pg_last_wal_replay_lsn` on the replica immediately after promotion. The difference in LSN (Log Sequence Number) converted to bytes/time indicates the lag.

SC2-B
**Terraform Operations:**
1.  **Import Replica:** Import the promoted replica into the state as the primary resource.
    ```bash
    terraform import aws_db_instance.primary <new_replica_arn>
    ```
2.  **Update Config:** Modify the `aws_db_instance` resource in code to match the new ARN/ID and remove `replica_source` configuration.
3.  **Update Dependents:** Update Security Groups, Route53, and Parameter Groups to reference the new instance ID.
4.  **Apply:** Run `terraform apply`. Terraform will update the resources to point to the new instance without destroying the DB instance itself (since it's now managed as `primary`).
5.  **Detach Old:** Once verified, remove the old primary instance resource from the Terraform state (`terraform state rm aws_db_instance.old_primary`) and destroy it manually or via a separate plan.

SC2-C
**Future Architecture:**
1.  **Connection Management:** Use **RDS Proxy** instead of PgBouncer. RDS Proxy handles connection pooling, failover transparency, and IAM authentication natively, reducing connection storms during failover.
2.  **DNS Failover:** Configure **Route53 Health Checks** with a latency-based or failover routing policy. Point the application endpoint to a CNAME that Route53 updates upon health check failure.
3.  **Retry Logic:** Implement **Exponential Backoff with Jitter** in the application layer to handle transient connection errors during the failover window.
4.  **RPO < 1s:** Use **Aurora Global Database**. It replicates storage across regions with < 1s latency and allows promotion in < 1 minute. Standard RDS async replication cannot guarantee < 1s RPO across regions reliably.
5.  **Recommendation:** **Aurora Global Database** is recommended over standard RDS for this requirement due to lower RPO/RTO and built-in cross-region replication management.

SC4-A
**Top 5 Blockers & Solutions:**
1.  **Local Memory Sessions:** Kubernetes pods are ephemeral; local memory is lost on restart. **Solution:** Externalize sessions to **Redis Cluster**.
2.  **Local NFS Mount:** `/data/uploads` is local to the bare-metal server. **Solution:** Migrate to **Amazon EFS** or **NFS CSI Driver** with `ReadWriteMany` access.
3.  **Sticky Sessions:** F5 sticky sessions rely on IP/Session affinity which breaks with pod scaling. **Solution:** Use **Redis** for session affinity or remove stickiness if stateless.
4.  **Oracle 19c On-Prem:** Hard to manage in K8s. **Solution:** Migrate to **Amazon RDS for Oracle** or **Oracle Cloud Infrastructure** managed DB.
5.  **IBM MQ:** Legacy protocol. **Solution:** Use **Amazon MQ** (managed MQ) or migrate to **RabbitMQ/Kafka** on K8s with a sidecar adapter.

SC6-C
**Connectivity Comparison:**
1.  **AWS Direct Connect:**
    *   **Pros:** High bandwidth (10G+), low latency, stable.
    *   **Cons:** High cost, long setup time.
    *   **Zero-Trust:** Fits well; traffic is private. Requires BGP routing config.
2.  **Second VPN (ECMP):**
    *   **Pros:** Cheap, fast setup.

    *   **Pros:** Easy mesh, NAT traversal, built-in identity (OIDC).
    *   **Cons:** Overlay network overhead, dependency on control plane.
    *   **Zero-Trust:** Native fit (identity-based routing).
    *   **Routing:** Requires changing app endpoints to use Tailnet IPs instead of VPC IPs.
    *   **Recommendation:** **Direct Connect** for backbone stability + **Tailscale** for service-to-service zero-trust overlay.

SC10-C
**Failover Orchestration:**
1.  **Detection:** **Prometheus Alertmanager** monitors site health (HTTP probes, DB latency). If > 3 nodes down in Chicago, trigger failover.
2.  **DNS:** **GSLB (Route53/NS1)** switches DNS TTL to 0 and points to Dallas VIP.
3.  **DB:** **Patroni** detects primary loss, promotes standby in Dallas automatically (via etcd consensus).
4.  **Cache:** **Redis Sentinel** promotes new master.
5.  **MQ:** **RabbitMQ** Federation mirrors queues; Dallas node takes over.
6.  **Storage:** **MinIO** Site Replication ensures data is synced; Dallas becomes writeable.
7.  **TF State:** Update OpenTofu state to reflect Dallas as `primary_region`.
8.  **Split-Brain:** Prevented by **etcd** quorum. If Chicago network partitions, etcd in Dallas loses quorum and refuses writes until Chicago is isolated.
9.  **Failback:** Once Chicago recovers, sync data from Dallas to Chicago (reverse replication), then switch DNS back. Verify data integrity before cutover.
