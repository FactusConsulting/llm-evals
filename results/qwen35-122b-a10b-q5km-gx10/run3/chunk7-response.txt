AA1 — **Monolith vs. Microservices:** A monolith is a single deployable unit where all components share memory and process space. Microservices are independently deployable services communicating over a network.
**3 Microservice Problems:**
1. **Distributed Tracing:** Debugging requests across services is complex compared to stack traces in a monolith.
2. **Network Latency:** Inter-service calls introduce latency and failure points not present in local function calls.
3. **Data Consistency:** Maintaining ACID transactions across services requires complex patterns (e.g., Sagas) instead of local DB transactions.

AA2 — **Sync vs. Async:**
*   **Synchronous:** The caller waits for a response before proceeding. Example: **HTTP/REST** or **gRPC**.
*   **Asynchronous:** The caller sends a request and continues without waiting; a response is handled later via callback or polling. Example: **RabbitMQ** or **Kafka**.

AA3 — **API Gateway vs. Reverse Proxy:**
*   **Reverse Proxy:** Routes traffic based on host/path, handles SSL termination, and load balances.
*   **API Gateway:** Adds business logic like authentication, rate limiting, request transformation, and aggregation.
*   **Replacement:** An API Gateway *is* a specialized reverse proxy. It can replace a generic reverse proxy (like Nginx) for ingress, but a simple reverse proxy is often preferred for internal service-to-service routing due to lower overhead.

AA4 — **Saga Pattern:** A sequence of local transactions where each updates data within a single service. If one fails, compensating transactions undo previous changes.
*   **Choreography:** Services emit events to trigger the next step. Decentralized, good for simple workflows.
*   **Orchestration:** A central coordinator tells services what to do. Centralized, better for complex workflows with many steps.
*   **Appropriateness:** Use Choreography for loose coupling; use Orchestration when visibility and control over the workflow are critical.

AA5 — **CQRS:** Separates read (Query) and write (Command) models.
*   **Pairing with Event Sourcing:** Event Sourcing stores state changes as a log of events. CQRS uses this log to project optimized read models.
*   **Problem Solved:** Traditional CRUD couples read/write schemas, causing contention. CQRS + ES allows independent scaling of reads/writes and provides a full audit trail of state changes.

AA6 — **Circuit Breaker:** Prevents cascading failures by stopping requests to a failing service.
*   **States:** **Closed** (normal), **Open** (fail fast), **Half-Open** (test recovery).
*   **Differs from Retry:** Retry assumes transient failure; Circuit Breaker assumes persistent failure.
*   **Usage:** Use Retry for transient network glitches; use Circuit Breaker when a service is consistently down to save resources.

AA7 — **Multi-Tenant Isolation:**
1.  **Shared DB, Shared Schema:** *Low cost, Low security, High complexity (row-level security), High noisy-neighbor risk.*
2.  **Shared DB, Separate Schema:** *Medium cost, Medium security, Medium complexity, Medium noisy-neighbor risk.*
3.  **Separate DB per Tenant:** *High cost, High security, High complexity (ops), Low noisy-neighbor risk.*
*   **Trade-off:** Choose #1 for SaaS at scale with low security needs; #3 for enterprise/regulated industries.

AA8 — **Consistency:**
*   **Eventual:** Data converges over time (high availability).
*   **Strong:** All nodes see the same data at the same time (high consistency).
*   **Inventory Architecture:** Use **Strong Consistency**.
*   **Store:** Relational DB (PostgreSQL) with ACID transactions.
*   **Pattern:** Pessimistic locking (`SELECT ... FOR UPDATE`) or Optimistic locking with versioning to prevent overselling.

AA9 — **Sidecar Proxy:** A helper container deployed alongside the main app container to handle networking/security.
*   **Envoy/Istio:** Envoy handles traffic (Data Plane); Istio Pilot/Control Plane configures Envoy.
*   **Data vs. Control:** Data Plane moves traffic; Control Plane manages policies.
*   **mTLS:** Encrypts service-to-service traffic automatically. Solves the problem of managing certificates and auth in application code.

AA10 — **Strangler Fig:** Incrementally migrate functionality by routing traffic to new services while keeping the legacy app running.
*   **Strategy:** Place a reverse proxy (e.g., Nginx) in front. Route specific paths (e.g., `/api/v2`) to new .NET 8 services. Route remaining paths to .NET Framework monolith. Gradually move more paths until the monolith is "strangled" and removed.

AA11 — **12-Factor App:** Methodology for building SaaS apps.
*   **6 Factors:**
    1.  **Codebase:** One codebase tracked in VCS.
    2.  **Dependencies:** Explicitly declare and isolate.
    3.  **Config:** Store config in environment variables.
    4.  **Backing Services:** Treat services (DB, queue) as attached resources.
    5.  **Build/Release/Run:** Strictly separate stages.
    6.  **Processes:** Execute app as one or more stateless processes.
*   **Why:** Ensures portability, scalability, and parity between dev/prod.

AA12 — **Event-Driven (Kafka) vs. Request-Driven (REST):**
*   **Coupling:** Kafka (Loose), REST (Tight).
*   **Scalability:** Kafka (High throughput, async), REST (Limited by request/response).
*   **Debugging:** Kafka (Harder, replay logs), REST (Easier, logs).
*   **Ordering:** Kafka (Partition-level), REST (N/A).
*   **Failure:** Kafka (Retry via consumer lag), REST (Retry logic in client).
*   **Choice:** REST for immediate user feedback; Kafka for background processing, audit trails, and decoupling.

AA13 — **Load Balancer:** Distributes traffic across servers.
*   **Layer 4:** Works at Transport (TCP/UDP). Fast, no content inspection.
*   **Layer 7:** Works at Application (HTTP). Can inspect headers/URLs.
*   **Use Case:** L7 required for path-based routing (e.g., `/api` to backend, `/static` to CDN) or SSL termination.

AA14 — **Message Queue:** Buffers messages between producers and consumers.
*   **Queue (RabbitMQ):** Task-oriented. Message deleted after ack. Good for work distribution.
*   **Log (Kafka):** Stream-oriented. Messages retained for replay. Good for event sourcing/analytics.
*   **Pick:** RabbitMQ for task queues; Kafka for high-volume event streaming.

AA15 — **Container vs. VM:**
*   **Container:** Shares host OS kernel, lightweight, fast startup.
*   **VM:** Virtualizes hardware, runs full OS, heavier.
*   **Popularity:** Containers allow higher density, faster CI/CD, and consistent environments for microservices.

AA16 — **Stateless vs. Stateful:**
*   **Stateless:** No client data stored on server (e.g., Web Server).
*   **Stateful:** Stores session/data (e.g., Database).
*   **Scaling:** Stateless services can be scaled horizontally by adding nodes behind a load balancer without session affinity.

AA17 — **ORM:** Maps objects to database tables.
*   **Examples:** **Hibernate** (Java), **Entity Framework** (.NET).
*   **Trade-offs:** ORM speeds dev and prevents SQL injection; Raw SQL offers better performance and control for complex queries.

AA18 — **Bulkhead Pattern:** Isolates resources to prevent one failure from consuming all resources.
*   **Relation:** Prevents cascade failures in microservices.
*   **Implementation:** Assign separate thread pools per service call. If Service A hangs, Service B's thread pool remains available. In Kubernetes, use separate Deployment groups with resource limits.

AA19 — **OT vs. CRDT:**
*   **OT:** Server-centric, transforms operations to maintain consistency. Complex, requires server.
*   **CRDT:** Client-centric, mathematically guarantees convergence. Supports offline editing.
*   **Choice:** **CRDTs**. They allow offline editing and merge automatically upon reconnection without complex server-side transformation logic.

AA20 — **Distributed Tracing:**
*   **Challenges:** Polyglot languages, async boundaries.
*   **Propagation:** Use W3C Trace Context headers.
*   **Sampling:** Head-based (decide at entry) vs. Tail-based (decide after seeing error).
*   **Storage:** Jaeger/Tempo (ClickHouse/Elastic).
*   **Async:** Inject trace ID into Kafka message headers. Consumer extracts header to continue the trace span.

OP1 — **Hypervisors:**
*   **Type 1 (Bare-metal):** Runs directly on hardware. Examples: **VMware ESXi, Microsoft Hyper-V**.
*   **Type 2 (Hosted):** Runs on top of an OS. Examples: **VirtualBox, VMware Workstation**.

OP2 — **SAN vs. NAS:**
*   **SAN:** Block-level storage (like a local disk). Protocols: **Fibre Channel, iSCSI**. Use for databases/VMs.
*   **NAS:** File-level storage. Protocols: **NFS, SMB/CIFS**. Use for file shares/backups.

OP3 — **3-Tier vs. Leaf-Spine:**
*   **3-Tier:** Core, Distribution, Access. High latency for East-West traffic.
*   **Leaf-Spine:** Every leaf connects to every spine. Predictable low latency, non-blocking.
*   **Problem Solved:** Leaf-spine eliminates bottlenecks in modern data centers with high server-to-server traffic.

OP4 — **Proxmox HA:**
*   **Architecture:** 3 nodes (quorum). Shared storage via **Ceph** (integrated) or iSCSI.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) to prevent split-brain.
*   **Failure:** If a node fails, the cluster detects loss of quorum (if 2/3) or node down. VMs restart on remaining nodes automatically.

OP5 — **VLAN Trunking:** Carries multiple VLANs over one link using **802.1Q** tags.
*   **Linux Config:** Create sub-interfaces.
    `ip link add link eth0 name eth0.10 type vlan id 10`
    `ip link set eth0.10 up`
    Repeat for VLAN 20, 30.

OP6 — **RAID Levels:**
*   **RAID 1:** Mirror (50% capacity).
*   **RAID 5:** Striping + Parity (N-1 capacity).
*   **RAID 6:** Striping + Dual Parity (N-2 capacity).
*   **RAID 10:** Mirror + Stripe (50% capacity, high perf).
*   **RAID Z2:** ZFS equivalent of RAID 6.
*   **Choice:** **RAID 10**. For a database, write performance is critical. RAID 5/6 has a write penalty; RAID 10 offers best I/O performance with 6 drives.

OP7 — **DNS Architecture:**
*   **Internal:** AD-integrated DNS for internal resolution.
*   **External:** Authoritative servers in DMZ.
*   **Split-Horizon:** Internal clients resolve `internal.corp` to private IPs; external resolve to public.
*   **Forwarders:** Internal DNS forwards external queries to ISP/Root.
*   **Laptop:** On office -> Internal DNS. On VPN -> Conditional forwarding or split-tunnel to use Internal DNS.

OP8 — **PKI Chain:**
*   **Chain:** Root CA (Offline) -> Subordinate CA (Issuing) -> End Entity (Server/User).
*   **Revocation:** CRL (List) vs. OCSP (Real-time check).
*   **Auto-enrollment:** GPO/MDM requests certs via SCEP/EST.
*   **Compromise:** Sub CA compromised = Revoke Sub CA, issue new. Root CA compromised = Revoke Root, rebuild entire PKI infrastructure.

OP9 — **WAN Consolidation:**
*   **MPLS:** High cost, reliable.
*   **IPsec:** Secure, manual config.
*   **SD-WAN:** Intelligent path selection, cost-effective.
*   **WireGuard:** Simple, fast, mesh.
*   **Recommendation:** **SD-WAN**. It optimizes VoIP traffic over multiple links (MPLS + Internet), manages latency, and reduces cost compared to pure MPLS.

OP10 — **OOB Management:**
*   **Tools:** iDRAC (Dell), iLO (HPE), IPMI (Generic).
*   **Criticality:** Allows remote power cycle/console access when OS is down.
*   **Risk:** Exposed IPMI = Remote Root Access. Must be on isolated management VLAN, never internet-facing.

OP11 — **Storage Managers:**
*   **LVM:** Linux Volume Manager (block layer). Snapshots: Copy-on-write (instant).
*   **LVM-Thin:** Pool-based allocation. Snapshots: Space efficient.
*   **ZFS:** Filesystem + Volume Manager. Snapshots: Copy-on-write, immutable, data integrity (checksums).
*   **Use:** LVM for general Linux; ZFS for data integrity and advanced features.

OP12 — **Stretch Cluster/DR:**
*   **Design:** 2 sites + 1 Witness (Quorum).
*   **Ceph:** CRUSH rules to replicate across sites.
*   **Latency:** < 5ms RTT recommended for synchronous replication.
*   **Split-Brain:** Without a witness, 2-site cluster loses quorum on link failure.
*   **Why Bad:** 2-site Ceph without witness risks data loss or unavailability during network partition.

OP13 — **DHCP:**
*   **DORA:** Discover, Offer, Request, Acknowledge.
*   **Unavailable:** Client uses APIPA (169.254.x.x) if lease expires and no server found. Connectivity limited to local subnet.

OP14 — **Switches:**
*   **Unmanaged:** Plug-and-play, no config.
*   **Managed:** Configurable VLANs, ACLs, SNMP monitoring, STP.
*   **Enterprise:** Managed required for security segmentation, troubleshooting, and traffic control.

OP15 — **NTP:**
*   **Role:** Time synchronization.
*   **Criticality:** Kerberos auth fails if clock skew > 5 mins. Logs become uncorrelatable. DB replication fails.
*   **Drift:** Causes authentication errors, data inconsistency, and security vulnerabilities.

OP16 — **Server Types:**
*   **Physical:** Bare metal hardware.
*   **VM:** Virtualized OS.
*   **Container:** Virtualized App.
*   **Bare Metal:** High-performance DBs, HPC, or workloads requiring direct hardware access (GPU passthrough) where virtualization overhead is unacceptable.

OP17 — **Power:**
*   **UPS:** Battery backup for short outages (minutes).
*   **Generator:** Fuel-powered for long outages (hours/days).
*   **ATS:** Automatically switches power source from Utility to Generator when utility fails.
*   **Need Both:** UPS bridges the gap until generator starts.

OP18 — **Clustering:**
*   **Active-Passive:** One node serves, one standby.
*   **Active-Active:** Both serve traffic.
*   **PostgreSQL HA:** Pacemaker/Corosync.
*   **Fencing:** STONITH device to power off failed node.
*   **VIP:** Virtual IP floats to active node.
*   **Failover:** Automatic promotion of standby to primary upon failure detection.

OP19 — **Backup Strategy:**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Define max data loss and max downtime.
*   **Types:** Full (baseline), Incremental (changes since last), Differential (changes since full).
*   **Protection:** Immutable backups (WORM) prevent ransomware encryption.
*   **Backup vs. DR:** Backup is data copy; DR is the plan/process to restore operations (includes failover).
*   **Testing:** Regular restore drills to verify integrity.

OP20 — **802.1X:**
*   **Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
*   **EAP:** EAP-TLS (Cert-based, secure) vs. PEAP (Password-based).
*   **Dynamic VLAN:** RADIUS returns VLAN ID upon success.
*   **Fail:** Port blocked or assigned to Guest VLAN.
*   **MAB:** Uses MAC address as credential for devices without 802.1X (printers, IoT). Less secure, fallback method.
