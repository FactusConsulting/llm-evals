CL1 — **IaaS vs PaaS vs SaaS:**
*   **IaaS (Infrastructure as a Service):** You manage OS, runtime, data, and apps; provider manages hardware/network. *Example:* AWS EC2.
*   **PaaS (Platform as a Service):** You manage apps and data; provider manages OS, runtime, and infrastructure. *Example:* Azure App Service.
*   **SaaS (Software as a Service):** You manage user access and data; provider manages everything. *Example:* Microsoft 365.

CL2 — **Shared Responsibility Model:**
*   **IaaS VMs:** Provider secures physical hardware, hypervisor, network. You secure OS, patches, apps, data, IAM.
*   **Managed Kubernetes:** Provider secures control plane, nodes (sometimes), network. You secure worker nodes (if self-managed), workloads, images, secrets.
*   **SaaS (M365):** Provider secures infrastructure, app, data at rest/in transit. You secure user access, data classification, device compliance.

CL3 — **VPC, Subnet, SG, NACL:**
*   **VPC:** Logical network boundary (CIDR block).
*   **Subnet:** IP range within VPC (public/private).
*   **Security Group (SG):** Instance-level firewall, **stateful** (allows return traffic automatically).
*   **NACL:** Subnet-level firewall, **stateless** (must explicitly allow return traffic).
*   **Layering:** Traffic flows VPC → Subnet (NACL) → Instance (SG).

CL4 — **Multi-Account Strategy:**
*   **Landing Zone:** Pre-configured secure environment (networking, identity, logging).
*   **OUs:** Group accounts by function (Prod, Dev, Security).
*   **Guardrails:** SCPs (Service Control Policies) to enforce limits.
*   **Shared Networking:** Transit Gateway (AWS) or Hub-Spoke (Azure) for centralized egress.
*   **Logging:** Centralized S3/Log Analytics account.
*   **Single Account Risk:** Security blast radius, noisy billing, permission conflicts, lack of isolation.

CL5 — **Infrastructure as Code (IaC):**
*   **Terraform/OpenTofu:** Declarative, multi-cloud, state file management. Choose for portability.
*   **Pulumi:** Imperative (general-purpose languages), good for complex logic.
*   **CloudFormation/Bicep:** Native provider tools, deep integration, no state file (provider-managed). Choose for single-cloud depth.
*   **Crossplane:** Kubernetes-native IaC, manages cloud resources as K8s CRDs. Choose for K8s-centric teams.

CL6 — **Kubernetes Autoscaling:**
*   **HPA:** Scales pods based on CPU/Memory metrics.
*   **VPA:** Adjusts pod resource requests/limits (requires restart).
*   **Cluster Autoscaler:** Adds/removes nodes based on pending pods.
*   **KEDA:** Event-driven scaling (queues, DB connections).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external events (e.g., SQS queue depth) rather than internal pod metrics.

CL7 — **Disaster Recovery (DR) Strategy:**
*   **RPO/RTO:** Define max data loss (RPO) and max downtime (RTO).
*   **Active-Active:** Traffic in both regions (Low RTO/RPO, High Cost).
*   **Active-Passive:** Primary region active, secondary standby (Lower Cost, Higher RTO).
*   **DB Replication:** Sync (Strong consistency, latency) vs Async (Performance, potential data loss).
*   **DNS Failover:** Route53 Health Checks/Traffic Manager to redirect traffic.
*   **DR Types:** Pilot Light (Minimal core running), Warm Standby (Scaled down), Multi-site (Full scale).

CL8 — **GitOps:**
*   **Model:** Git repository is the single source of truth; controllers sync cluster state to Git state.
*   **ArgoCD vs Flux:** ArgoCD has UI, K8s-native; Flux is CLI-driven, CNCF standard.
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetch from Vault/AWS Secrets Manager).
*   **Drift:** GitOps controller detects manual change and automatically reverts to Git state.

CL9 — **Stateful App on K8s:**
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC:** Use `local` storage class for low latency (node-affinity).
*   **Headless Service:** Provides stable DNS for pod-to-pod communication.
*   **Init Containers:** Run before main container (e.g., config generation).
*   **ConfigMaps:** Mounted as volumes to specific paths.
*   **PDB:** Prevents voluntary disruptions from taking down all replicas simultaneously.

CL10 — **Identity in K8s:**
*   **Service Account:** K8s identity for pods.
*   **Workload Identity:** Mapping K8s SA to Cloud IAM role (GCP/Azure).
*   **IRSA:** AWS-specific implementation of Workload Identity.
*   **Bad Practice:** Mounting static keys exposes them to anyone with pod access; keys rotate poorly.
*   **Solution:** Federation issues short-lived tokens via OIDC, reducing exposure window.

CL11 — **Storage Types:**
*   **Object (S3/Blob):** Unstructured data, HTTP access. High durability (11 9s).
*   **Block (EBS/Disk):** OS disks, databases. Low latency, attached to single instance.
*   **File (EFS/Azure Files):** Shared filesystem, multiple instances.
*   **Use Case:** Object for backups/media, Block for DB/OS, File for shared app data.

CL12 — **Zero Trust K8s:**
*   **Network Policies:** Default deny all ingress/egress.
*   **Service Mesh:** mTLS for service-to-service encryption.
*   **Pod Identity:** No cloud creds in pods.
*   **Admission:** OPA/Kyverno to enforce policies (e.g., no root).
*   **Image Sig:** Cosign/Notary to verify images.
*   **Runtime:** Falco for anomaly detection.
*   **Diff:** Traditional trusts internal network; Zero Trust verifies every request regardless of origin.

CL13 — **CDN:**
*   **Definition:** Distributed edge servers caching content closer to users.
*   **Mechanism:** DNS resolves to nearest edge; edge caches static assets.
*   **Services:** AWS CloudFront, Azure CDN.
*   **Use:** Static assets (images, JS, CSS). Direct origin for dynamic, personalized content.

CL14 — **Regions and AZs:**
*   **Region:** Geographic area (e.g., us-east-1).
*   **AZ:** Isolated datacenter within a region.
*   **Multi-AZ:** Protects against datacenter failure.
*   **Zonal Resource:** Tied to one AZ (e.g., specific VM).
*   **Regional Resource:** Spans AZs (e.g., S3, Route53).

CL15 — **Managed Database:**
*   **Service:** RDS, Cloud SQL, Azure SQL.
*   **Provider Handles:** Patching, backups, HA setup, hardware scaling.
*   **Customer Handles:** Schema design, query optimization, access control, data migration.

CL16 — **IAM and Least Privilege:**
*   **Users:** Human identities.
*   **Groups:** Collections of users.
*   **Roles:** Temporary credentials for services/users.
*   **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Grant only permissions necessary for the specific task. Apply by denying by default and allowing specific actions.

CL17 — **Serverless:**
*   **Definition:** Event-driven compute without server management.
*   **Comparison:** AWS Lambda (ecosystem), Azure Functions (enterprise), GCP Functions (GCP native).
*   **Cold Start:** Latency on first invocation after inactivity.
*   **Poor Fit:** Long-running processes, stateful apps, strict low-latency requirements.

CL18 — **Kubernetes Ingress:**
*   **Ingress Resource:** L7 routing, simple, controller-dependent.
*   **Gateway API:** L4/L7, extensible, standardizing.
*   **Cloud LB:** L4/L7, provider-specific annotations.
*   **Mesh Ingress:** L7, integrated with service mesh.
*   **TLS:** Terminate at LB (offload) or Ingress (end-to-end).
*   **Gateway API:** Use for complex routing, multi-cluster, or when Ingress limitations are hit.

CL19 — **Cost Optimization ($80k/mo):**
*   **Commitments:** Reserved Instances/Savings Plans for steady state.
*   **Spot/Preemptible:** For fault-tolerant batch workloads.
*   **Right-sizing:** Analyze CPU/Mem usage, downsize over-provisioned resources.
*   **Storage:** Move old data to Archive/Intelligent-Tiering.
*   **FinOps:** Tagging strategy, showback/chargeback to teams.
*   **Tools:** AWS Cost Explorer, Kubecost, CloudHealth.

CL20 — **Multi-Cloud Strategy:**
*   **Abstraction:** Kubernetes (EKS/AKS/GKE), Terraform.
*   **Networking:** Cloud Interconnect/VPN for hybrid.
*   **Identity:** Federated SSO (Okta/Azure AD).
*   **Trade-offs:** Complexity increases (2x tooling, 2x skills).
*   **Justification:** Compliance (data residency), avoiding single vendor risk, best-of-breed services.
*   **Unnecessary:** If one cloud meets 95% of needs, multi-cloud adds cost without value.

OT1 — **Purdue Model (ISA-95):**
*   **Level 0:** Physical process (sensors/actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Supervisory Control (HMI, SCADA).
*   **Level 3:** Operations Management (MES, Historian).
*   **Level 4:** Business Planning (ERP).
*   **Level 5:** Enterprise/Internet.

OT2 — **IT vs OT:**
*   **IT:** Prioritizes Confidentiality. Standard patching cycles.
*   **OT:** Prioritizes Availability and Safety. Patching risky (legacy OS, vendor validation required, downtime cost).
*   **Difference:** OT systems often run Windows XP/7, proprietary protocols, cannot tolerate reboots.

OT3 — **IDMZ (Industrial DMZ):**
*   **Role:** Buffer zone between IT (L4) and OT (L1-L3).
*   **Traffic:** IT→DMZ (Data collection), DMZ→OT (Read-only commands). No direct IT→OT.
*   **Risk:** Direct L4→L1 allows malware to bypass security controls and crash physical processes.

OT4 — **OT Protocols:**
*   **Modbus TCP:** L1/L2 (Simple, unencrypted).
*   **OPC UA:** L2/L3 (Secure, cross-platform).
*   **EtherNet/IP:** L1 (Industrial Ethernet).
*   **PROFINET:** L1 (Real-time control).
*   **MQTT:** L3/L4 (Lightweight messaging for IIoT).

OT5 — **Data Diode vs Firewall:**
*   **Data Diode:** Hardware-enforced one-way traffic (Optical).
*   **Firewall:** Software logic, bi-directional.
*   **Use Case:** Diode for high-security data exfiltration (OT→IT) where no return path is allowed.
*   **Limitation:** Cannot receive commands or updates from the other side.

OT6 — **Data Flow Design:**
*   **Flow:** PLC → Historian (L3) → OPC UA Server → Edge Gateway → MQTT Broker → Cloud.
*   **Security:** Firewall between PLC and Historian. Diode/Firewall between OT and DMZ. TLS for MQTT.
*   **Boundaries:** DMZ separates OT network from Cloud ingestion.

OT7 — **IEC 62443 Zones & Conduits:**
*   **Zone:** Logical grouping of assets with same security requirements.
*   **Conduit:** Communication path between zones.
*   **Design:** Zone 4 (Corp), Zone 3 (Eng/SCADA), Zone 2 (PLC Network), Zone 1 (Safety SIS). Conduits firewalled between zones.

OT8 — **Segmentation Strategy:**
*   **VLANs:** Separate VLAN per production line.
*   **Firewalls:** Between VLANs and at network edge.
*   **Switches:** Managed switches with ACLs, disable unused ports.
*   **Vendor Access:** Jump host in DMZ, MFA, time-limited.
*   **Transition:** Implement in parallel, test during maintenance windows, avoid production impact.

OT9 — **SIS vs BPCS:**
*   **BPCS:** Controls normal process (PLC/DCS).
*   **SIS:** Safety layer (E-Stop, trip) if BPCS fails.
*   **IEC 61511:** Functional Safety standard.
*   **Isolation:** SIS must be isolated to prevent IT malware from disabling safety trips.
*   **Ransomware on SIS:** Could prevent safety shutdown, leading to physical explosion/injury.

OT10 — **PLC vs DCS vs SCADA:**
*   **PLC:** Localized logic control.
*   **DCS:** Centralized control for continuous processes (refineries).
*   **SCADA:** Supervisory monitoring over wide areas (pipelines).
*   **Coexistence:** Yes. PLCs control machines, DCS manages plant, SCADA monitors overall.

OT11 — **Remote Access:**
*   **Architecture:** Jump Host (Bastion) in DMZ.
*   **Controls:** MFA, Session Recording, Time-limited tokens.
*   **Vendor Access:** Specific accounts, audit logs.
*   **RDP Direct:** Unacceptable (bypasses controls, no audit, direct attack path).

OT12 — **Incident Response (Water Treatment):**
*   **Detection:** IDS on L3, Anomaly detection on traffic.
*   **Response:** Isolate compromised VLANs (Firewall), disconnect vendor VPN.
*   **Coordination:** Inform Control Room immediately.
*   **Operator Role:** Maintain physical safety manually if automation is compromised.
*   **Safety First:** Security actions must not compromise physical safety (e.g., don't shut down pumps if it causes overflow).

OT13 — **HMI:**
*   **Role:** Operator interface to view/process data and issue commands.
*   **Diff:** HMI is runtime (L2). Engineering Workstation is for programming logic (L3). HMI should not be used for coding.

OT14 — **Historian:**
*   **Role:** Time-series database for process data.
*   **Importance:** Trend analysis, compliance, troubleshooting.
*   **Plant (L3):** High frequency, real-time.
*   **Enterprise (L4):** Aggregated, lower frequency, business reporting.

OT15 — **Ladder Logic:**
*   **Device:** PLC.
*   **Definition:** Visual programming resembling electrical relay diagrams.
*   **Dominance:** Legacy investment, easy for electricians to understand, deterministic execution.

OT16 — **RTU:**
*   **Definition:** Remote Terminal Unit.
*   **Diff:** RTU focuses on telemetry and comms (often wireless); PLC focuses on local logic.
*   **Environment:** Remote sites (oil wells, pipelines) where wiring to a central PLC is impossible.

OT17 — **Analog vs Digital:**
*   **Analog:** Continuous signal (4-20mA, 0-10V).
*   **Digital:** Discrete (On/Off).
*   **4-20mA:** "Live zero" (4mA = 0%). 0mA indicates wire break/fault, 0-20mA cannot distinguish 0 signal from broken wire.

OT18 — **Asset Inventory:**
*   **Foundation:** Cannot secure what you don't know.
*   **Tools:** Passive monitoring (Mirroring ports), Active scanning (Risky).
*   **Active Scanning Danger:** Can crash legacy devices (e.g., sending TCP SYN to Modbus port). Prefer passive.

OT19 — **MITRE ATT&CK for ICS:**
*   **Tactics:** Reconnaissance, Initial Access, Execution, Persistence, Impact.
*   **Example:** Recon (Network Scanning), Initial Access (Phishing), Impact (Process Disruption).
*   **Diff:** Focuses on physical impact and legacy protocols.
*   **Use:** Map controls to gaps (e.g., do we have IDS for Modbus?).

OT20 — **Converged SOC:**
*   **Log Collection:** Syslog/Agents on OT assets (non-intrusive).
*   **SIEM:** Splunk/Sentinel with OT parsers.
*   **Rules:** OT-specific (e.g., "Write to PLC memory").
*   **Staffing:** IT Analysts + OT Engineers (Hybrid).
*   **False Positives:** Tune rules to avoid alert fatigue.
*   **Firmware Alert:** Verify legitimacy, isolate device, restore from known good backup manually.
