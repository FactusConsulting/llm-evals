T1 — **Plan vs. Apply**
`tofu plan` creates an execution plan, showing what changes will be made without applying them. It is a read-only operation used for verification. `tofu apply` executes the changes defined in the plan, modifying the infrastructure to match the configuration.

T2 — **State and Remote State**
State is a file (`terraform.tfstate`) that maps real-world resources to your configuration, tracks metadata, and stores output values. Remote state is crucial for team collaboration (preventing conflicts), security (storing secrets in backend, not local files), and enabling state locking to prevent concurrent writes.

T3 — **count vs. for_each**
`count` creates resources based on an integer index (0, 1, 2...), which can cause resource replacement if items are inserted/removed from the middle of a list. `for_each` iterates over a map or set, using keys as identifiers. `for_each` is preferred when resource identity matters (e.g., adding/removing items without shifting indices) or when managing resources with unique keys.

T4 — **Manual Changes (Drift)**
If you modify a resource outside OpenTofu, it creates "drift." Running `tofu plan` detects the difference between the state file and the actual cloud resource. `tofu apply` will then attempt to revert the change or update the state to match the configuration, depending on the configuration's intent.

T5 — **Snippet: 3 VMs with for_each**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

T6 — **remote_state vs. Outputs & Alternative**
`terraform_remote_state` reads the state file of another root module directly. Outputs are values passed from a module to its caller. The recommended alternative to `remote_state` for sharing data between root modules is **Module Composition** (combining logic into a single root module). This avoids tight coupling, state dependency chains, and CI/CD complexity associated with managing multiple root modules.

T7 — **Provisioner Output Dependency**
Outputs are evaluated after resources are created, but provisioners run during the apply phase. If a downstream resource depends on an output generated by a provisioner, OpenTofu cannot know the value during the plan phase ("known after apply"), causing the plan to fail or the resource to be skipped. **Fix:** Avoid using provisioners for data flow. Use cloud-init/user-data or split the workflow into two separate applies (one to create the cluster, one to consume the config).

T8 — **Import and Import Block**
`tofu import` maps existing infrastructure to state manually via CLI. Limitations: requires manual ID lookup, config must match exactly, and it is not version-controlled. The `import` block (v1.5+) allows declarative import within the configuration file, making the import process reproducible, version-controlled, and safer for CI/CD pipelines.

T9 — **Variable vs. Output**
A `variable` is an input parameter passed into a module or root configuration (e.g., instance type). An `output` is a value exposed from a module or root configuration for use elsewhere (e.g., public IP). Variables configure resources; outputs expose resource data.

T10 — **Provider and Init**
A provider is a plugin that interacts with an API (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, it fails because the provider plugins are not downloaded or configured in the `.terraform` directory. `tofu init` initializes the working directory and downloads required providers.

T11 — **lock.hcl File**
`.terraform.lock.hcl` records the specific versions of providers and modules used. It should be committed to version control to ensure reproducibility across environments and team members, preventing unexpected breaking changes from provider updates.

T12 — **Destroy and Target**
`tofu destroy` removes all resources managed by the current configuration. To target a single resource for destruction, use the `-target` flag: `tofu destroy -target=aws_instance.web`. Note: This may leave orphaned resources if dependencies exist.

T13 — **Data Source**
A data source reads existing data from the infrastructure provider without managing it. **Example:** Use `data "aws_ami"` to find the latest Ubuntu AMI ID instead of creating a new AMI resource. Use data sources for read-only lookups; use managed resources for creation/deletion.

T14 — **locals vs. variables**
`variables` are inputs passed from outside the module. `locals` are computed values defined internally within the module. Use `locals` for derived values, complex expressions, or to avoid repeating logic. Use `variables` when the value needs to be configurable by the caller.

T15 — **lifecycle Block**
Controls resource behavior.
*   `create_before_destroy`: Replaces resources by creating the new one before destroying the old (useful for immutable attributes like VPC CIDR).
*   `prevent_destroy`: Prevents accidental deletion (useful for production databases).
*   `ignore_changes`: Ignores specific attribute changes (useful for tags managed externally).

T16 — **moved Block**
A `moved` block tells OpenTofu that a resource has changed address in the configuration (e.g., moved to a different module) but represents the same real-world resource. It updates the state file to point to the new address without destroying and recreating the resource.

T17 — **Dependency Graph**
OpenTofu builds a Directed Acyclic Graph (DAG) based on resource references. **Implicit dependencies** are created automatically when one resource references another's attribute. **Explicit dependencies** use `depends_on`. `depends_on` forces serialization, reducing parallelism. Use it sparingly only when implicit dependencies are insufficient (e.g., external API calls).

T18 — **Reducing Plan Time (200+ resources)**
1.  **Split State:** Break into multiple state files/modules to reduce scope per plan. (Tradeoff: Increased complexity).
2.  **Targeting:** Use `-target` for specific changes. (Tradeoff: Risk of drift if not applied globally later).
3.  **Parallelism:** Increase `parallelism` in backend config. (Tradeoff: API rate limits).
4.  **Cleanup:** Remove unused resources from config/state. (Tradeoff: Risk of accidental deletion).

T19 — **State Locking**
Locking prevents concurrent writes to state (e.g., via DynamoDB). If a CI pipeline crashes, the lock may remain stale. **Fix:** Run `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually writing, forcing unlock can corrupt the state file. Always verify no other process is running before unlocking.

T20 — **Migrate to S3/DynamoDB**
1.  Backup local `terraform.tfstate`.
2.  Create S3 bucket and DynamoDB table for locking.
3.  Add `backend "s3"` block to config with `bucket`, `key`, `region`, and `dynamodb_table`.
4.  Run `tofu init -migrate-state`.
5.  Verify with `tofu plan` (should show no changes).
6.  Delete local state file.

A1 — **Playbook, Role, Task**
A **Playbook** is a YAML file defining a set of plays. A **Role** is a reusable directory structure containing tasks, vars, and handlers. A **Task** is a single action (module call) within a playbook or role.

A2 — **ansible_facts**
`ansible_facts` is a dictionary of system information gathered by the `setup` module. Access OS family via `{{ ansible_os_family }}`.

A3 — **command, shell, raw**
`command`: Runs a command without shell features (safe, idempotent). `shell`: Runs via shell (supports pipes, variables). `raw`: Executes without Python on the remote node (useful for bootstrapping). Use `command` by default; `shell` for complex logic; `raw` for minimal environments.

A4 — **Idempotency**
Idempotency means running a task multiple times yields the same result. **Idempotent:** `apt: name=nginx state=present`. **Not Idempotent:** `shell: echo "hello" >> file.txt` (appends every time).

A5 — **Install htop Task**
```yaml
- name: Install htop
  package:
    name: "{{ ['epel-release', 'htop'] if ansible_os_family == 'RedHat' else ['htop'] }}"
    state: present
```

A6 — **Variable Precedence**
Highest to Lowest: `extra_vars` (CLI) > `role vars` > `host_vars` > `group_vars` > `role defaults`. `set_fact` overrides `host_vars` but is lower than `extra_vars`.

A7 — **RKE2 Agent Deployment**
Use `serial: 3` in the play to limit concurrency. Group nodes in inventory. Use `wait_for` or a custom task to check RKE2 readiness before proceeding to the next batch.

A8 — **ansible-vault**
Encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'secret_value' --name 'my_var'` and paste the output into the vars file, or encrypt the specific variable block within the file using `--encrypt-vault-id`.

A9 — **Inventory**
A list of hosts. **Static:** A file (INI/YAML). **Dynamic:** A script/API that generates the list at runtime (e.g., AWS EC2 inventory plugin).

A10 — **Ad-hoc Disk Check**
`ansible webservers -m shell -a "df -h"`

A11 — **Handler**
A handler is a task that runs only if notified by another task (e.g., config change). It runs once at the end of the play. Triggered via `notify: restart nginx`.

A12 — **ansible.cfg**
Configuration file for Ansible behavior. Common settings: `inventory` (default path), `remote_user` (SSH user), `host_key_checking` (security).

A13 — **register**
Stores the output of a task into a variable. Use `{{ registered_var.stdout }}` or `{{ registered_var.rc }}` in subsequent tasks for conditional logic.

A14 — **include_tasks vs. import_tasks**
`import_tasks`: Static inclusion (parsed at play start). Conditionals on the import apply to the whole file. `include_tasks`: Dynamic inclusion (parsed at runtime). Conditionals apply per task. Use `include_tasks` for loops/conditionals inside the file.

A15 — **Ansible Galaxy**
A repository for sharing roles and collections. Use `requirements.yml` to list dependencies and run `ansible-galaxy install -r requirements.yml` to install them.

A16 — **Connection Plugins**
Defines how Ansible connects. `ssh`: Default for Linux. `local`: Runs on control node. `network_cli`: For network devices (Cisco, Juniper). Use `local` for control tasks, `ssh` for servers, `network_cli` for routers.

A17 — **delegate_to and run_once**
`delegate_to`: Runs a task on a different host (e.g., localhost). `run_once`: Runs the task only once across the play. **Example:** Update a Load Balancer on `localhost` using IP gathered from a remote host.
```yaml
- name: Update LB
  delegate_to: localhost
  run_once: true
  uri: ...
```

A18 — **Performance (500 hosts)**
1.  **Forks:** Increase `forks` in `ansible.cfg` (Tradeoff: Network load).
2.  **Pipelining:** Enable `pipelining = True` (Tradeoff: Requires sudo config).
3.  **Fact Caching:** Use `jsonfile` or `redis` cache (Tradeoff: Stale facts risk).
4.  **Mitogen:** Use `ansible-mitogen` plugin (Tradeoff: Complexity/Compatibility).

A19 — **Jinja2 Templating**
`{{ }}`: Print variables. `{% %}`: Control flow (loops/if). `{# #}`: Comments.
**Snippet:**
```jinja2
{% for server in backends %}
# {{ server.name }}
server {{ server.ip }}:{{ server.port }};
{% endfor %}
```

A20 — **Zero-Downtime Rolling Deploy**
1.  **Serial:** Set `serial: 20%` to batch servers.
2.  **Pre-tasks:** Remove host from Load Balancer (LB).
3.  **Tasks:** Deploy new code.
4.  **Post-tasks:** Run `uri` health check. If fail, trigger `rescue` block to rollback and re-add to LB. If pass, add to LB.
5.  **Rescue:** Stop deployment, revert code, notify on failure.
