AA1 — **Monolith vs. Microservices:** A monolith is a single deployable unit where all components share memory and process space. Microservices are independently deployable services communicating over a network.
**3 Microservice Problems:**
1.  **Distributed Tracing:** Debugging requests across service boundaries is complex compared to stack traces in a monolith.
2.  **Network Latency:** Inter-service calls introduce latency and failure points (network partitions) absent in local function calls.
3.  **Data Consistency:** Maintaining ACID transactions across services requires complex patterns (Sagas) instead of local database transactions.

AA2 — **Sync vs. Async:** Synchronous communication requires the caller to wait for a response before proceeding (blocking). Asynchronous communication allows the caller to continue without waiting (non-blocking).
**Examples:**
*   **Sync:** HTTP/REST, gRPC.
*   **Async:** RabbitMQ (AMQP), Apache Kafka.

AA3 — **API Gateway vs. Reverse Proxy:** A reverse proxy routes traffic based on host/path (L7). An API Gateway adds cross-cutting concerns like authentication, rate limiting, transformation, and aggregation.
**Replacement:** An API Gateway can replace a reverse proxy, but it is heavier. For simple internal routing without auth logic, a lightweight reverse proxy (e.g., Nginx) is more efficient.

AA4 — **Saga Pattern:** A sequence of local transactions where each updates data within a single service. If one fails, compensating transactions undo previous changes.
**Choreography:** Services emit events to trigger the next step (decentralized). Good for simple workflows.
**Orchestration:** A central coordinator tells services what to do (centralized). Good for complex workflows requiring visibility and control.

AA5 — **CQRS:** Separates read (Query) and write (Command) models.
**Pairing with Event Sourcing:** Event Sourcing stores state changes as a log of events. CQRS uses this log to build optimized read projections.
**Problem Solved:** Traditional CRUD couples read/write schemas, causing contention. CQRS+ES allows independent scaling of reads and writes and provides a full audit trail.

AA6 — **Circuit Breaker:** Prevents cascading failures by stopping requests to a failing service.
**States:** Closed (normal), Open (failing fast), Half-Open (testing recovery).
**Differs from Retry:** Retry assumes transient failure; Circuit Breaker assumes persistent failure.
**Usage:** Use retry for transient network glitches; use Circuit Breaker when a service is down to save resources.

AA7 — **Multi-Tenant Isolation:**
1.  **Shared DB, Shared Schema:** Low cost, high complexity (row-level security), high noisy-neighbor risk.
2.  **Shared DB, Separate Schema:** Medium cost, medium security (schema isolation), medium noisy-neighbor risk.
3.  **Separate DB:** High cost, high security (physical isolation), low noisy-neighbor risk.
**Trade-off:** Choose Separate DB for regulated/enterprise tenants; Shared Schema for SaaS scale.

AA8 — **Eventual vs. Strong Consistency:** Eventual means data converges over time; Strong means all nodes see the same data immediately.
**Inventory Architecture:** Use **Strong Consistency**.
**Data Store:** Relational DB (PostgreSQL) with ACID transactions.
**Pattern:** Pessimistic locking (`SELECT ... FOR UPDATE`) or distributed locks (Redis Redlock) to prevent overselling.

AA9 — **Sidecar Proxy:** A helper container deployed alongside the main app container to handle networking/security.
**Envoy/Istio:** Envoy handles traffic (data plane); Istiod manages config/policies (control plane).
**mTLS:** Encrypts service-to-service traffic automatically. Solves the problem of managing certificates and auth in application code.

AA10 — **Strangler Fig:** Incrementally replace a legacy system by routing traffic to new services.
**Strategy:**
1.  Place a reverse proxy in front of the .NET Framework monolith.
2.  Identify a feature (e.g., "Checkout").
3.  Build the feature as a .NET 8 microservice.
4.  Update the proxy to route `/checkout` to the new service, rest to legacy.
5.  Repeat until monolith is strangled.

AA11 — **12-Factor App:** Methodology for building SaaS apps.
**6 Factors:**
1.  **Codebase:** One codebase tracked in VCS.
2.  **Dependencies:** Explicitly declare and isolate.
3.  **Config:** Store config in environment variables.
4.  **Backing Services:** Treat services (DB, Queue) as attached resources.
5.  **Processes:** Execute app as one or more stateless processes.
6.  **Port Binding:** Export services via port binding.
**Why:** Ensures portability, scalability, and parity between dev/prod.

AA12 — **Event-Driven (Kafka) vs. Request-Driven (REST):**
*   **Coupling:** Kafka (loose), REST (tight).
*   **Scalability:** Kafka (high throughput, async), REST (limited by request/response).
*   **Debugging:** Kafka (harder, replay logs), REST (easier, logs).
*   **Ordering:** Kafka (partition-level), REST (none).
*   **Failure:** Kafka (retry/consumer lag), REST (immediate error).
**Choice:** REST for user-facing APIs; Kafka for background processing, auditing, and decoupling.

AA13 — **Load Balancer:** Distributes traffic across servers.
**L4 vs. L7:** L4 routes based on IP/Port (TCP/UDP). L7 routes based on HTTP headers/URL.
**Use Case:** L7 required for path-based routing (e.g., `/api` to backend, `/static` to CDN) or SSL termination.

AA14 — **Message Queue vs. Log Broker:**
*   **Queue (RabbitMQ):** Messages deleted after consumption. Point-to-point.
*   **Log (Kafka):** Messages retained for time/size. Publish-Subscribe.
**Pick:** Queue for task distribution (work queues). Log for event streaming and replayability.

AA15 — **Container vs. VM:** Containers share the host OS kernel; VMs virtualize hardware with a full guest OS.
**Popularity:** Containers are lightweight, start in seconds, and use fewer resources, ideal for microservices density.

AA16 — **Stateless vs. Stateful:** Stateless services hold no session data locally (e.g., Web Server). Stateful services persist data locally (e.g., Database).
**Scaling:** Stateless services can be scaled horizontally by adding instances behind a load balancer without data migration.

AA17 — **ORM:** Maps objects to database tables.
**Examples:** Hibernate (Java), Entity Framework (.NET).
**Trade-offs:** ORM speeds development and abstracts SQL dialects but can generate inefficient queries and hide performance issues.

AA18 — **Bulkhead Pattern:** Isolates resources to prevent one failure from consuming all capacity.
**Relation:** Prevents "noisy neighbor" issues in microservices.
**Implementation:** Assign separate thread pools to different external API calls. If API A hangs, API B threads remain available.

AA19 — **OT vs. CRDT:**
*   **OT:** Central server resolves conflicts. Complex logic, requires server.
*   **CRDT:** Mathematically guaranteed convergence without central coordination.
**Choice:** **CRDTs**. They support offline editing naturally because changes merge automatically upon reconnection without server intervention.

AA20 — **Distributed Tracing:**
*   **Context:** Propagate TraceID/SpanID via headers (W3C Trace Context).
*   **Sampling:** Head-based (at entry) vs. Tail-based (keep errors). Tail-based is better for debugging.
*   **Storage:** Jaeger/Tempo (index traces).
*   **Async:** Inject TraceID into Kafka message headers. Consumer reads header to continue the trace span.

OP1 — **Hypervisor Type 1 vs. 2:** Type 1 runs directly on hardware (Bare-metal). Type 2 runs on top of an OS (Hosted).
**Examples:** Type 1: VMware ESXi, Microsoft Hyper-V. Type 2: Oracle VirtualBox, VMware Workstation.

OP2 — **SAN vs. NAS:** SAN provides block-level storage (like a local disk). NAS provides file-level storage (like a network folder).
**Use:** SAN for databases/VMs. NAS for file sharing.
**Protocols:** SAN (Fibre Channel, iSCSI). NAS (NFS, SMB/CIFS).

OP3 — **3-Tier vs. Leaf-Spine:** 3-Tier (Core/Dist/Access) has variable hop counts. Leaf-Spine has uniform 2-hop latency.
**Preference:** Leaf-Spine preferred for East-West traffic (server-to-server) in modern data centers.
**Problem Solved:** 3-Tier creates bottlenecks at the distribution layer; Leaf-Spine provides non-blocking bandwidth.

OP4 — **Proxmox HA:**
*   **Nodes:** 3 nodes (odd number for quorum).
*   **Storage:** Ceph (integrated) or iSCSI.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) to prevent split-brain.
*   **Failure:** If a node fails, the cluster detects loss of quorum (if 2 fail) or restarts VMs on remaining nodes (if 1 fails).

OP5 — **VLAN Trunking:** Carries multiple VLANs over a single link using 802.1Q tags.
**Linux Config:** Use `ip link` or `vconfig`. Example: `ip link add link eth0 name eth0.10 type vlan id 10`. Assign IPs to `eth0.10`, `eth0.20`, etc.

OP6 — **RAID Levels:**
*   **RAID 1:** Mirror (50% cap).
*   **RAID 5:** Parity (N-1 cap, slow writes).
*   **RAID 6:** Double Parity (N-2 cap).
*   **RAID 10:** Mirror+Stripe (50% cap, fast).
*   **RAID Z2:** ZFS equivalent of RAID 6.
**Choice:** **RAID 10**. For a database, write performance and rebuild speed are critical. 6 drives allow 3 usable pairs.

OP7 — **DNS Architecture:**
*   **Internal:** AD-integrated DNS for internal resolution.
*   **External:** Authoritative servers in DMZ.
*   **Split-Horizon:** Internal clients resolve internal IPs; external resolve public IPs.
*   **Forwarders:** Internal DNS forwards unknown queries to ISP/Root.
*   **Laptop:** DHCP assigns DNS server. Conditional forwarding ensures internal names resolve correctly regardless of network location.

OP8 — **PKI Chain:** Root CA (offline) signs Subordinate CA. Sub CA signs End-Entity certs.
**Revocation:** CRL (list) vs. OCSP (real-time check).
**Compromise:** Sub CA compromised = revoke Sub CA cert, reissue. Root CA compromised = rebuild entire PKI infrastructure.

OP9 — **WAN Comparison:**
*   **MPLS:** Reliable, expensive.
*   **IPsec:** Secure, complex config.
*   **SD-WAN:** Intelligent routing, app-aware, manageable.
*   **WireGuard:** Simple, fast, but less enterprise features.
**Recommendation:** **SD-WAN**. It optimizes VoIP traffic over multiple links (MPLS + Internet) and simplifies management for 5 sites.

OP10 — **OOB Management:** iDRAC/iLO/IPMI allow remote power control and console access independent of OS.
**Criticality:** Essential for unattended reboots or OS crashes.
**Risk:** Exposed IPMI = Remote Root Access. Must be on a management VLAN, never internet-facing.

OP11 — **LVM vs. ZFS:**
*   **LVM:** Logical Volume Manager on Linux. Flexible resizing.
*   **LVM-Thin:** Allows overcommitment of storage.
*   **ZFS:** Integrated FS and Volume Manager. Copy-on-write.
**Snapshots:** LVM (instant, space efficient). ZFS (instant, space efficient, read-only).
**Use:** ZFS for data integrity/caching. LVM for general Linux flexibility.

OP12 — **Stretch Cluster/DR:**
*   **Design:** 2 sites + 1 witness node (tiebreaker).
*   **Ceph:** CRUSH rules to replicate data across sites.
*   **Latency:** <5ms RTT recommended for synchronous replication.
*   **Split-Brain:** Without a tiebreaker, both sites may think they are primary. The witness node breaks the tie to ensure quorum.

OP13 — **DHCP:** Dynamic Host Configuration Protocol.
**DORA:** Discover (client), Offer (server), Request (client), Acknowledge (server).
**Unavailable:** Client uses APIPA (169.254.x.x) or retries lease renewal. If lease expires completely, connectivity is lost.

OP14 — **Managed vs. Unmanaged:** Unmanaged is plug-and-play. Managed allows configuration.
**Features:** VLANs, QoS, Port Security, SNMP monitoring.
**Importance:** Essential for network segmentation, traffic prioritization, and security in enterprises.

OP15 — **NTP:** Network Time Protocol.
**Criticality:** Logs correlation, Kerberos auth (5 min drift limit), DB consistency.
**Drift:** Causes authentication failures, data corruption in distributed DBs, and broken scheduled tasks.

OP16 — **Physical vs. VM vs. Container:** Physical = Bare metal. VM = Virtualized OS. Container = Virtualized App.
**Bare Metal:** High-performance DBs, HPC, or workloads requiring direct hardware access (GPU passthrough).

OP17 — **UPS vs. Generator:** UPS provides immediate power (seconds/minutes). Generator provides long-term power (hours/days).
**ATS:** Automatically switches power source from Utility to Generator.
**Need Both:** UPS bridges the gap between outage and generator startup.

OP18 — **Active-Passive vs. Active-Active:** Passive = One node works, one waits. Active = Both work.
**PostgreSQL HA:** Pacemaker manages resources.
**Fencing:** STONITH ensures failed node is powered off to prevent data corruption.
**Failover:** VIP moves to surviving node.

OP19 — **Backup Strategy:**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Define data loss tolerance and recovery time.
*   **Immutable:** Protect against ransomware (WORM storage).
*   **Backup vs. DR:** Backup is data copy; DR is the plan/process to restore operations.
*   **Testing:** Regular restore drills are mandatory.

OP20 — **802.1X:** Port-based Network Access Control.
**Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
**EAP:** EAP-TLS (Certificates, most secure), PEAP (Password).
**MAB:** Falls back to MAC address authentication for devices without 802.1X (e.g., printers).
**Failure:** Port is blocked or assigned to a "Guest" VLAN.
