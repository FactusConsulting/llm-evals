CL1 — **IaaS vs PaaS vs SaaS:**
*   **IaaS (Infrastructure as a Service):** You manage OS, runtime, data, and apps; provider manages hardware/network. *Example:* AWS EC2.
*   **PaaS (Platform as a Service):** You manage data and apps; provider manages OS, runtime, and infrastructure. *Example:* Google App Engine.
*   **SaaS (Software as a Service):** You manage user access and data; provider manages everything. *Example:* Microsoft 365.

CL2 — **Shared Responsibility Model:**
*   **IaaS VMs:** Provider secures physical hardware/network. You secure OS, patches, apps, data, and IAM.
*   **Managed Kubernetes:** Provider secures control plane, nodes (sometimes), and networking. You secure worker nodes (if self-managed), workloads, images, and secrets.
*   **SaaS (M365):** Provider secures the application and infrastructure. You secure user identities, data classification, and device access.

CL3 — **VPC, Subnet, SG, NACL:**
*   **VPC:** Virtual network boundary (IP range).
*   **Subnet:** IP range within a VPC, tied to an AZ.
*   **Security Group (SG):** Instance-level firewall, **stateful** (allows return traffic automatically).
*   **NACL:** Subnet-level firewall, **stateless** (must explicitly allow return traffic).
*   **Layering:** Traffic flows VPC → Subnet (NACL) → Instance (SG).

CL4 — **Multi-Account Strategy:**
*   **Landing Zone:** Pre-configured secure environment (networking, IAM, logging).
*   **OUs:** Organizational Units group accounts by function (Prod, Dev, Security).
*   **Guardrails:** SCPs (Service Control Policies) enforce limits.
*   **Shared Networking:** Transit Gateway (AWS) or Hub-Spoke (Azure) centralizes connectivity.
*   **Logging:** Centralized S3/Log Analytics account for audit trails.
*   **Single Account Risk:** Security blast radius, noisy billing, difficult permission management, lack of isolation.

CL5 — **Infrastructure as Code (IaC):**
*   **Terraform/OpenTofu:** Declarative, multi-cloud, state file management. Choose for portability.
*   **Pulumi:** Imperative (general-purpose languages like Python/Go). Choose for complex logic.
*   **CloudFormation/Bicep:** Native to AWS/Azure. Choose for deep provider integration.
*   **Crossplane:** K8s-native IaC. Choose for managing cloud resources via K8s API.

CL6 — **K8s Autoscaling:**
*   **HPA:** Scales pods based on CPU/Memory.
*   **VPA:** Adjusts pod resource requests/limits (requires restart).
*   **Cluster Autoscaler:** Adds/removes nodes when pods are pending.
*   **KEDA:** Event-driven scaling (e.g., queue depth).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external metrics (queues, APIs) rather than pod resource utilization.

CL7 — **Disaster Recovery (DR) Strategy:**
*   **RPO/RTO:** Recovery Point Objective (data loss tolerance) vs Recovery Time Objective (downtime tolerance).
*   **Active-Active:** Traffic in both regions (Low RTO, High Cost). **Active-Passive:** One region standby (Higher RTO, Lower Cost).
*   **DB Replication:** Sync (Strong consistency, latency) vs Async (Performance, potential data loss).
*   **DNS Failover:** Route53 Health Checks/Traffic Manager to redirect traffic.
*   **State:** Use global storage (S3) or replicated DBs.
*   **DR Types:** **Pilot Light** (Minimal core running), **Warm Standby** (Scaled down env), **Multi-site** (Full production in both).

CL8 — **GitOps:**
*   **Model:** Git repository is the single source of truth for infra/app state. Controller syncs cluster to Git.
*   **ArgoCD vs Flux:** ArgoCD has a UI, easier for beginners. Flux is CLI-driven, CNCF standard, lighter.
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetch from Vault), Vault Agent.
*   **Drift:** GitOps controller detects manual changes and reverts them to match Git state (unless configured otherwise).

CL9 — **Stateful K8s Migration:**
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC:** Use `local` storage class for low latency (node affinity).
*   **Headless Service:** Provides direct DNS to pods for stable networking.
*   **Init Containers:** Handle config file generation before main app starts.
*   **ConfigMaps:** Mounted as volumes to specific paths.
*   **PDB:** Prevents voluntary disruptions from taking down all replicas simultaneously.

CL10 — **Identity in K8s:**
*   **Service Account:** K8s identity for pods.
*   **Workload Identity:** Maps K8s SA to Cloud IAM role (Azure/GCP).
*   **IRSA:** AWS specific (IAM Roles for Service Accounts).
*   **Bad Practice:** Mounting static keys/secrets exposes them to compromise and rotation is hard.
*   **Federation:** Uses OIDC to exchange short-lived tokens, reducing credential exposure.

CL11 — **Storage Types:**
*   **Object (S3/Blob):** Unstructured data, HTTP access. High durability (11 9s).
*   **Block (EBS/Disk):** OS disks, databases. Low latency, attached to one VM.
*   **File (EFS/Azure Files):** Shared filesystem, multiple VMs.
*   **Use Case:** Object for backups/media, Block for DBs/OS, File for shared configs/logs.

CL12 — **Zero Trust K8s:**
*   **Network Policies:** Default deny all ingress/egress.
*   **Service Mesh:** mTLS for service-to-service encryption.
*   **Pod Identity:** No cloud creds in pods.
*   **Admission:** OPA/Kyverno enforce policies (e.g., no root user).
*   **Image Signing:** Cosign/Notary verify images.
*   **Runtime:** Falco detects anomalies.
*   **Diff:** Traditional trusts perimeter; Zero Trust verifies every request regardless of origin.

CL13 — **CDN:**
*   **Definition:** Distributed network of edge servers caching content closer to users.
*   **Mechanism:** DNS resolves to nearest edge node; cache hit serves content, miss fetches from origin.
*   **Services:** AWS CloudFront, Azure CDN.
*   **Use:** Static assets (images, JS), global users. Direct origin for dynamic/private data.

CL14 — **Regions & AZs:**
*   **Region:** Geographic area (e.g., us-east-1).
*   **AZ:** Isolated data center within a region.
*   **Multi-AZ:** Protects against data center failure.
*   **Zonal Resources:** Tied to one AZ (e.g., specific VM). **Regional Resources:** Span multiple AZs (e.g., S3, Load Balancer).

CL15 — **Managed Database:**
*   **Service:** RDS, Cloud SQL, Azure SQL.
*   **Provider Handles:** Hardware, OS patching, backups, replication, failover.
*   **You Handle:** Schema design, query optimization, access control, data migration.

CL16 — **IAM & Least Privilege:**
*   **Components:** Users (people), Groups (collections), Roles (assumed identities), Policies (permissions).
*   **Least Privilege:** Grant only permissions necessary for the task.
*   **Application:** Start with deny-all, add specific allow rules, audit regularly.

CL17 — **Serverless:**
*   **Definition:** Event-driven compute without server management.
*   **Comparison:** AWS Lambda, Azure Functions, GCP Cloud Functions.
*   **Cold Start:** Latency when initializing a new container instance.
*   **Poor Fit:** Long-running processes, stateful apps, constant high load (cost inefficiency).

CL18 — **K8s Ingress:**
*   **Ingress Resource:** L7 routing, simple, controller-dependent.
*   **Gateway API:** L4/L7, extensible, standardizing.
*   **LB Annotations:** Cloud provider specific, L4/L7.
*   **Mesh Ingress:** L7, integrated with service mesh.
*   **TLS:** Terminate at LB, Ingress Controller, or Mesh sidecar.
*   **Gateway API:** Use for complex routing, multi-cluster, or standardization needs.

CL19 — **Cost Optimization ($80k/mo):**
*   **Commitments:** Reserved Instances/Savings Plans for steady state.
*   **Spot/Preemptible:** For fault-tolerant batch workloads.
*   **Right-sizing:** Downsize over-provisioned resources.
*   **Storage:** Tiering (Intelligent-Tiering, Glacier).
*   **FinOps:** Tagging, showback/chargeback, automated alerts.
*   **Tools:** AWS Cost Explorer, Azure Cost Management, Kubecost.

CL20 — **Multi-Cloud Strategy:**
*   **Abstraction:** K8s as runtime, Terraform for IaC.
*   **Networking:** Interconnect/VPN between clouds.
*   **Identity:** Federated SSO across providers.
*   **Trade-offs:** Complexity, skill requirements, data egress costs vs. vendor lock-in avoidance.
*   **Justification:** Compliance, resilience, specific service needs. **Unnecessary:** If one provider meets 95% of needs.

OT1 — **Purdue Model (ISA-95):**
*   **Level 0:** Physical Process (Sensors/Actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Supervisory Control (SCADA, HMIs).
*   **Level 3:** Operations Management (MES, Historians).
*   **Level 4:** Business Planning (ERP).
*   **Level 5:** Enterprise Network (Corporate IT).

OT2 — **IT vs OT:**
*   **IT:** Prioritizes Confidentiality. Patching is frequent.
*   **OT:** Prioritizes Availability and Safety. Patching is risky (downtime, instability).
*   **Patching:** OT systems often run legacy OS; patching requires vendor validation and scheduled maintenance windows.

OT3 — **IDMZ (Industrial DMZ):**
*   **Role:** Buffer zone between IT (L4) and OT (L1-L3).
*   **Traffic:** IT→DMZ (Data collection), DMZ→OT (Read-only commands). No direct IT→OT.
*   **Risk:** Direct L4→L1 allows malware to bypass controls and cause physical damage.

OT4 — **OT Protocols:**
*   **Modbus TCP:** L1/L2 (Simple, unencrypted).
*   **OPC UA:** L2/L3 (Secure, cross-platform).
*   **EtherNet/IP:** L1 (Industrial Ethernet).
*   **PROFINET:** L1 (Real-time control).
*   **MQTT:** L3/L4 (Lightweight messaging for IIoT).

OT5 — **Data Diode vs Firewall:**
*   **Data Diode:** Hardware-enforced one-way traffic.
*   **Firewall:** Software logic, bi-directional.
*   **Use Diode:** When data must flow OT→IT only (e.g., telemetry) with zero risk of IT→OT commands.
*   **Limitation:** Cannot send commands back to OT; requires separate channel for control.

OT6 — **Data Flow Design:**
*   **Flow:** PLC → Historian (L3) → OPC UA Server → Edge Gateway → MQTT Broker → Cloud.
*   **Security:** Firewall between PLC and Historian. IDMZ between Historian and Edge. TLS for MQTT.
*   **Boundaries:** Enforce at every hop (PLC, Historian, Gateway, Cloud).

OT7 — **IEC 62443 Zones & Conduits:**
*   **Zone:** Logical grouping of assets with same security requirements.
*   **Conduit:** Communication path between zones.
*   **Design:** Zone 1 (PLCs/SIS), Zone 2 (SCADA), Zone 3 (Engineering), Zone 4 (Corporate). Conduits firewalled between zones. SIS isolated in its own zone.

OT8 — **Segmentation Strategy:**
*   **VLANs:** Separate VLAN per production line.
*   **Firewalls:** Between lines and IT.
*   **Switches:** Managed switches with port security.
*   **Vendor Access:** Jump host in DMZ, MFA, time-limited.
*   **Transition:** Parallel run, test in non-prod first, schedule during maintenance windows.

OT9 — **SIS vs BPCS:**
*   **BPCS:** Controls process (run). **SIS:** Safety (trip on danger).
*   **IEC 61511:** Functional Safety standard.
*   **Isolation:** SIS must be isolated to prevent IT malware from disabling safety trips.
*   **Ransomware:** If SIS is compromised, physical safety is at risk (explosion, leak).

OT10 — **PLC vs DCS vs SCADA:**
*   **PLC:** Local, discrete control.
*   **DCS:** Plant-wide, continuous control.
*   **SCADA:** Supervisory, monitoring across wide areas.
*   **Coexistence:** Yes. PLCs feed DCS; SCADA monitors both.

OT11 — **Remote Access:**
*   **Architecture:** Jump Host (Bastion) in DMZ.
*   **Controls:** MFA, Session Recording, Time-limited tokens.
*   **Vendor:** Vetted access, monitored.
*   **RDP Direct:** Unacceptable (exposes HMI to internet/corporate network).

OT12 — **Water Treatment Incident Response:**
*   **Detection:** IDS on L3, Anomaly detection on traffic.
*   **Inventory:** Know all assets.
*   **Response:** Isolate L3 from IT. Do not shut down OT unless unsafe.
*   **Operator Role:** Maintain manual control, follow safety procedures, do not reboot systems blindly.
*   **Safety:** Security actions must not compromise physical safety.

OT13 — **HMI vs Engineering Workstation:**
*   **HMI:** Operator interface for monitoring/control during runtime.
*   **Engineering Workstation:** Used for programming, configuration, and logic changes.
*   **Difference:** HMI is runtime; EW is development. EW should not be on the control network during operation.

OT14 — **Historian:**
*   **Definition:** Time-series database for process data.
*   **Importance:** Trend analysis, compliance, optimization.
*   **Plant (L3):** High frequency, real-time.
*   **Enterprise (L4):** Aggregated, lower frequency, business reporting.

OT15 — **Ladder Logic:**
*   **Definition:** Graphical programming language resembling relay logic.
*   **Device:** PLCs.
*   **Dominance:** Legacy systems, electrician familiarity, deterministic execution, ease of troubleshooting.

OT16 — **RTU vs PLC:**
*   **RTU:** Remote Terminal Unit. Telemetry, comms-focused, rugged.
*   **PLC:** Programmable Logic Controller. Logic-focused, local control.
*   **Environment:** RTUs for remote sites (pipelines, wells) with poor connectivity. PLCs for factory floors.

OT17 — **Analog vs Digital:**
*   **Analog:** Continuous signal (4-20mA, 0-10V).
*   **Digital:** Discrete (On/Off).
*   **4-20mA:** "Live zero" (4mA = 0%, 0mA = fault). Better noise immunity than voltage.

OT18 — **Asset Inventory:**
*   **Foundation:** You cannot secure what you don't know.
*   **Tools:** Passive monitoring (packet capture), Active scanning (risky).
*   **Active Scanning Danger:** Can crash legacy PLCs/RTUs due to unexpected traffic. Prefer passive.

OT19 — **MITRE ATT&CK for ICS:**
*   **Framework:** Tactics/Techniques specific to ICS.
*   **Tactics:** Reconnaissance, Initial Access, Execution, Persistence, Impact.
*   **Example:** T861 (Exploit Public-Facing Application), T810 (Modify Controller Logic).
*   **Diff:** Focuses on physical impact (Safety) vs Enterprise (Data theft).
*   **Use:** Map controls to techniques to find gaps.

OT20 — **Converged SOC:**
*   **Log Collection:** Passive agents or network taps (no impact on real-time).
*   **SIEM:** Ingest OT logs, normalize.
*   **Rules:** OT-specific (e.g., PLC write attempts).
*   **Workflow:** IT Analyst triage → OT Engineer validation.
*   **False Positives:** Tune aggressively; OT noise is high.
*   **Firmware Alert:** Verify signature, isolate device, contact vendor, do not patch immediately without testing.
