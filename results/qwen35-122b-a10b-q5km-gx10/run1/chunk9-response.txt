SC1-A
**Root Cause:** The failure stems from a conflict between the **Pod Security Standard (PSS) Restricted** profile and the container image's default user.
1.  **PSS Restricted:** This profile enforces `runAsNonRoot: true`. It requires the container to run as a non-root user (UID != 0).
2.  **Image Configuration:** The new base image (`cgr.dev/chainguard/static:latest`) defaults `USER` to `root` (UID 0) in the Dockerfile.
3.  **Manifest Configuration:** The pod spec sets `securityContext.runAsNonRoot: true` but omits `runAsUser`.
4.  **The Conflict:** Kubernetes attempts to run the container. The image specifies root. The PSS policy forbids root. Since `runAsUser` is not explicitly set to a non-root UID in the pod spec, the admission controller (or the kubelet enforcing PSS) rejects the pod or the container runtime fails to start it because it cannot satisfy `runAsNonRoot` without an explicit non-root user assignment.
5.  **Baseline vs. Restricted:** The Baseline profile allows `runAsNonRoot: true` but does not strictly enforce the user ID resolution logic as aggressively as Restricted, or the previous cluster version allowed the image's root user to pass if the policy wasn't strictly enforced. The upgrade to 1.29 likely tightened enforcement or the namespace policy changed from Baseline to Restricted, causing the rejection.

SC1-C
**Remediation Strategy:**
1.  **Immediate Fix:** Update the Kubernetes manifests to explicitly set `securityContext.runAsUser: 65534` (nobody) or a specific non-root UID in the pod spec. This satisfies PSS Restricted.
2.  **Image Fix:** Modify the Dockerfile to set `USER 65534` (or appropriate non-root user) before the final stage. This ensures the image is compliant regardless of manifest settings.
3.  **CI Pipeline Gate:** Add a step in the CI pipeline using `kube-score` or `checkov` to validate manifests against PSS Restricted before deployment. Add a Dockerfile linting step (e.g., `hadolint`) to flag `USER root`.
4.  **Rollout:** Use a RollingUpdate strategy. Apply the manifest fix first to new pods. Once stable, rebuild and push the corrected image. Gradually shift traffic. Monitor `CrashLoopBackOff` counts in Prometheus.

SC2-A
**Stale Data & Replication Lag:**
1.  **Cause:** Cross-region read replicas in RDS use asynchronous streaming replication. There is inherent lag (network latency + WAL shipping time).
2.  **Implication:** When promoting the replica, any WAL records not yet shipped/applied from the primary are lost. Queries immediately after failover may read data that was committed on the primary but not yet replicated.
3.  **WAL Shipping:** WAL segments are shipped via TCP. In cross-region (us-east-1 to eu-west-1), latency (85ms+) increases the time to ship segments.
4.  **Data Loss:** Asynchronous replication means RPO > 0. If the primary fails before shipping the last transaction, that data is lost.
5.  **Quantification:** Check `pg_stat_replication` on the primary before failure for `sent_lsn`, `write_lsn`, `flush_lsn`, and `replay_lsn`. Calculate the byte difference between `sent_lsn` and `replay_lsn` to estimate data loss window.

SC2-C
**Architecture Design:**
1.  **Connection Management:** Use **RDS Proxy** instead of PgBouncer. RDS Proxy handles connection pooling, failover transparency, and IAM authentication natively, reducing connection storms during failover.
2.  **DNS Failover:** Configure **Route53 Health Checks** on the primary endpoint. Set up a failover routing policy to point to the replica endpoint upon primary failure.
3.  **Retry Logic:** Implement application-level exponential backoff with jitter for database connections to handle transient failover latency.
4.  **RPO < 1s:** Standard RDS cross-region async replication cannot guarantee RPO < 1s consistently. **Recommend Aurora Global Database**. It uses storage-level replication with typically < 1s latency and allows faster promotion (seconds vs minutes).
5.  **Why Aurora:** Aurora decouples compute from storage, replicating storage across 3 AZs in primary and 3 in DR. Failover is faster, and RPO is significantly lower than RDS async replication.

SC4-A
**Top 5 Blockers:**
1.  **Local Memory Sessions:** Kubernetes pods are ephemeral. Sticky sessions on F5 won't work if pods restart. **Solution:** Externalize sessions to Redis.
2.  **Local NFS Mount:** `/data/uploads` on bare metal won't persist across pods. **Solution:** Use EFS or NFS CSI Driver with RWX access.
3.  **Oracle 19c On-Prem:** Hard to containerize legacy DB. **Solution:** Migrate to RDS Oracle or keep on-prem with secure VPC peering.
4.  **IBM MQ:** Legacy protocol integration. **Solution:** Use IBM MQ Cloud or containerize MQ with persistent storage, expose via Service.
5.  **Sticky Sessions:** F5 relies on IP/Session affinity. **Solution:** Use Kubernetes Ingress with Session Affinity (Cookie-based) or remove affinity if state is externalized.

SC6-C
**Connectivity Comparison:**
1.  **Direct Connect (DX):**
    *   *Pros:* High bandwidth (10G+), low latency, stable.
    *   *Cons:* High cost, long setup time.
    *   *Zero Trust:* Fits well; traffic stays on private backbone.
    *   *Routing:* Requires BGP configuration on TGW.
2.  **VPN ECMP:**
    *   *Pros:* Lower cost, faster setup.
    *   *Cons:* Limited bandwidth (aggregated), higher latency variance.
    *   *Zero Trust:* IPsec encrypts traffic, but relies on public internet.
    *   *Routing:* Requires BGP on both ends for ECMP.
3.  **Tailscale/Netbird:**
    *   *Pros:* Easy mesh, NAT traversal, zero config routing.
    *   *Cons:* Overlay network overhead, dependency on control plane.
    *   *Zero Trust:* Built on WireGuard, identity-based access.
    *   *Routing:* Automatic mesh routing, no BGP needed.
    *   *Recommendation:* Use **Direct Connect** for production backbone (cost justified by reliability) + **Tailscale** for management/developer access.

SC10-C
**Failover Orchestration:**
1.  **Detection:** Prometheus Alertmanager monitors site health (heartbeat). If > 3 nodes down in Chicago, trigger failover.
2.  **DNS:** GSLB (Route53/NS1) switches DNS TTL to 0 and points to Dallas VIP.
3.  **DB:** Patroni detects primary loss, promotes Dallas standby (sync mode ensures no data loss).
4.  **Cache:** Redis Sentinel promotes new master.
5.  **MQ:** RabbitMQ federation ensures queues are mirrored.
6.  **Storage:** MinIO Site Replication catches up (async).
7.  **TF State:** Update OpenTofu state to reflect Dallas as primary (manual or automated via CI).
8.  **Split-Brain:** Patroni DCS (etcd) prevents split-brain by requiring quorum. If etcd is lost, manual intervention required.
9.  **Failback:** Once Chicago recovers, sync data from Dallas to Chicago. Switch DNS back. Re-establish replication.
