K1 — **Deployment vs. StatefulSet**
A **Deployment** manages stateless applications with random pod names and parallel scaling. A **StatefulSet** manages stateful applications with stable, unique network IDs (e.g., `pod-0`, `pod-1`), ordered scaling (0 to N), and stable persistent storage bindings. Use StatefulSet for databases or apps requiring stable identity.

K2 — **ClusterIP Routing**
A ClusterIP Service exposes a virtual IP (VIP) internal to the cluster. **kube-proxy** runs on each node and configures **iptables** (or IPVS) rules to intercept traffic destined for the VIP. It load-balances this traffic to the backend Pod IPs listed in the Service’s **Endpoints** object.

K3 — **PV, PVC, and StorageClass**
*   **StorageClass:** Defines the "type" of storage (provisioner, parameters) for dynamic provisioning.
*   **PersistentVolume (PV):** A cluster-wide storage resource (like a disk).
*   **PersistentVolumeClaim (PVC):** A user request for storage.
*   **Relation:** A PVC requests storage; if dynamic provisioning is enabled, the StorageClass provisions a PV automatically, and the PVC binds to it.

K4 — **CrashLoopBackOff Troubleshooting**
1.  **Logs:** `kubectl logs <pod> --previous` to see why the last instance died.
2.  **Events:** `kubectl describe pod` to check for OOMKilled, Liveness Probe failures, or scheduling errors.
3.  **Resources:** Check if memory/CPU limits are too low causing kills.
4.  **Config:** Verify ConfigMaps/Secrets are mounted correctly and environment variables are valid.

K5 — **CoreDNS Role**
CoreDNS provides DNS resolution within the cluster, mapping Kubernetes Service names to ClusterIPs. If CoreDNS pods are down, **internal service discovery fails**; pods cannot resolve service names (e.g., `my-service.default.svc`), breaking inter-pod communication, though direct IP access may still work.

K6 — **Kubernetes Scheduler Logic**
The scheduler uses a **Filter** (Predicate) phase to remove unsuitable nodes, then a **Score** (Priority) phase to rank remaining nodes.
*   **Factors:** 1. **Resource Requests** (CPU/Memory fit), 2. **Node Affinity** (label requirements), 3. **Taints/Tolerations** (node restrictions), 4. **Pod Affinity/Anti-Affinity** (co-location rules).

K7 — **Resource Scheduling & Limits**
*   **Scheduling:** Yes. Node available = 4GB - 3.5GB = 500Mi. Pod requests 256Mi. 256Mi < 500Mi, so it fits.
*   **Runtime:** If the pod uses 600Mi, it exceeds its **limit** (512Mi). The OOM Killer will terminate the container, causing a restart.

K8 — **Ingress Request Lifecycle**
1.  **External LB** forwards traffic to the **Ingress Controller** Pod.
2.  **Ingress Controller** reads Ingress Resource rules to determine the target Service.
3.  Traffic hits the **Service** ClusterIP.
4.  **kube-proxy** (iptables/IPVS) on the node DNATs traffic to a **Pod IP** from the Endpoints list.
5.  Request reaches the **Application Pod**.

K9 — **NetworkPolicy**
A NetworkPolicy acts as a firewall for pods.
*   **Default:** If no policy exists, all traffic (in/out) is allowed.
*   **Applied:** If a policy selects pods, it **denies all traffic** not explicitly allowed by the policy rules (default-deny behavior for selected pods).

K10 — **RollingUpdate vs. Recreate**
*   **RollingUpdate:** Spawns new pods before terminating old ones (zero downtime).
*   **Recreate:** Terminates all existing pods before creating new ones (downtime).
*   **Use Recreate:** For stateful apps that cannot handle parallel writes (e.g., certain databases) or when schema changes require exclusive access.

K11 — **Namespace**
A logical cluster partition for isolation and resource quotas.
*   **Defaults:** `default`, `kube-system`, `kube-public`, `kube-node-lease`.

K12 — **kubectl describe pod**
Shows detailed spec and status not in `get`.
1.  **Events:** Recent warnings or scheduling actions.
2.  **Conditions:** Pod readiness, container states.
3.  **Volumes/Mounts:** ConfigMap/Secret mounts and storage details.

K13 — **ConfigMap**
A key-value store for non-sensitive configuration.
*   **Methods:** 1. Inject as **Environment Variables** (`envFrom` or `env`). 2. Mount as **Files** in a Volume.

K14 — **Service Types**
*   **ClusterIP:** Internal-only IP (default).
*   **NodePort:** Exposes service on a static port on each Node's IP.
*   **LoadBalancer:** Provisions an external cloud Load Balancer to route traffic to the service.

K15 — **DaemonSet**
Ensures a copy of a Pod runs on **all (or some) nodes**. Use for node-level agents like logging (Fluentd), monitoring (Node Exporter), or storage drivers, whereas Deployments manage application replicas.

K16 — **Taints/Tolerations vs. Affinity**
*   **Taints/Tolerations:** Taints **repel** pods from a node; Tolerations allow pods to **accept** the taint. Use for dedicated nodes (e.g., GPU nodes).
*   **Affinity:** Rules to **attract** or **repel** pods based on node labels. Use for co-locating pods (e.g., app + cache on same rack).

K17 — **Kubernetes Operator**
An Operator is a custom controller + Custom Resource Definition (CRD) that extends the Kubernetes API. Unlike standard controllers (which manage Pods/Deployments), Operators manage complex stateful applications (e.g., databases) by automating lifecycle tasks like backups, failover, and upgrades.

K18 — **etcd Consistency & Recovery**
*   **Model:** Strong consistency via Raft consensus.
*   **Quorum Loss:** If >50% of nodes fail (e.g., 2 of 3), the cluster becomes read-only/unavailable.
*   **Recovery:** Restore the remaining node(s) from a recent **etcd snapshot**. If data is lost, you must rebuild the cluster and restore application state from backups.

K19 — **RBAC & Manifests**
*   **Role/ClusterRole:** Define permissions (verbs/resources). Role is namespace-scoped; ClusterRole is cluster-wide.
*   **Binding:** Links a Subject (User/Group/ServiceAccount) to a Role.
*   **Manifest:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — **DNS ndots Issue**
*   **Cause:** Default `ndots:5` means if a domain has <5 dots, the resolver tries appending search domains (e.g., `svc`, `default.svc`, `cluster.local`) before querying the external DNS. This causes multiple queries for external domains.
*   **Fix:** Set `dnsConfig.options` in the Pod spec: `name: ndots`, `value: "1"`. This forces external queries to be sent directly to the upstream DNS.

D1 — **git rebase vs. merge**
*   **Merge:** Creates a new commit preserving history branches.
*   **Rebase:** Rewrites history to create a linear sequence.
*   **Avoid Rebasing:** On **shared/public branches** (e.g., `main`), as it changes commit hashes and disrupts collaborators.

D2 — **TCP vs. UDP**
*   **TCP:** Connection-oriented, reliable, ordered delivery. Protocols: **HTTP**, **SSH**.
*   **UDP:** Connectionless, unreliable, fast. Protocols: **DNS**, **VoIP**.

D3 — **Race Condition**
A bug where system behavior depends on the timing of uncontrollable events.
*   **Example:** Two threads incrementing a shared counter `i++` without synchronization. Both read `i=0`, both write `i=1`, resulting in `i=1` instead of `2`.

D4 — **Symmetric vs. Asymmetric Encryption**
*   **Symmetric:** Same key for encrypt/decrypt (fast).
*   **Asymmetric:** Public/Private key pair (secure exchange).
*   **TLS:** Uses Asymmetric for the handshake (key exchange) and Symmetric for the session data (performance).

D5 — **Container Image Layers**
Images are stacked read-only layers. **Layer Caching** speeds up builds.
*   **Best Practice:** Order Dockerfile commands to maximize cache hits. Place rarely changing commands (e.g., `apt-get install`) before frequently changing ones (e.g., `COPY .`).

D6 — **HTTP 503 Troubleshooting**
1.  **Upstream Health:** Check Service Endpoints (are pods ready?).
2.  **App Logs:** Check for application errors or panics.
3.  **Resources:** Check for CPU throttling or OOMKills.
4.  **Ingress/LB:** Check timeout configurations or health check paths.

D7 — **CAP Theorem**
Consistency, Availability, Partition Tolerance. You can only guarantee 2 of 3 during a network partition.
*   **CP:** **Zookeeper** (Consistency over Availability).
*   **AP:** **Cassandra** (Availability over Consistency).

D8 — **Scaling**
*   **Vertical:** Adding resources (CPU/RAM) to a single node.
*   **Horizontal:** Adding more nodes/instances.
*   **Patterns:** Stateless architecture, Load Balancers, Database Sharding.

D9 — **Environment Variable**
A key-value pair passed to a process.
*   **Persist:** Add `export VAR=value` to `~/.bashrc` or `/etc/environment`.

D10 — **JSON vs. YAML**
*   **JSON:** Data interchange, strict syntax. Advantage: Fast parsing.
*   **YAML:** Configuration, human-readable. Advantage: Readability (indentation, comments).

D11 — **REST API**
Architectural style using HTTP methods.
*   **GET:** Retrieve resource.
*   **POST:** Create resource.
*   **PUT:** Replace/Update resource.
*   **DELETE:** Remove resource.

D12 — **Version Pinning**
Locking dependencies to specific versions (e.g., `package-lock.json`).
*   **Importance:** Ensures **reproducible builds**; prevents breaking changes from upstream updates.

D13 — **Compiled vs. Interpreted**
*   **Compiled:** Source code translated to machine binary before execution. Examples: **C++**, **Go**.
*   **Interpreted:** Source code executed line-by-line by a runtime. Examples: **Python**, **JavaScript**.

D14 — **Reverse vs. Forward Proxy**
*   **Reverse Proxy:** Server-side (protects backend). Examples: **Nginx** (Load Balancing), **HAProxy**.
*   **Forward Proxy:** Client-side (protects client). Example: Corporate firewall proxy.

D15 — **Deadlock**
A state where processes wait indefinitely for resources held by each other.
*   **Coffman Conditions:** 1. Mutual Exclusion, 2. Hold & Wait, 3. No Preemption, 4. Circular Wait.

D16 — **Eventual Consistency**
Data updates propagate asynchronously; all nodes agree eventually.
*   **Cassandra:** Uses tunable consistency levels (ONE, QUORUM, ALL). Read-after-write consistency is achieved by setting the read consistency level >= write consistency level.

D17 — **mTLS (Mutual TLS)**
Both client and server authenticate each other using certificates.
*   **Handshake:** Server sends cert -> Client verifies. Client sends cert -> Server verifies.
*   **Use Case:** Service Meshes (Istio), internal microservice communication.

D18 — **Hash Table**
Maps keys to indices via a hash function.
*   **Collision Resolution:** **Chaining** (linked list at index) or **Open Addressing** (probe next slot).
*   **Complexity:** Average O(1), Worst O(n) (all keys collide).

D19 — **Circuit Breaker**
Prevents cascade failures by stopping calls to failing services.
*   **States:** **Closed** (normal), **Open** (fail fast), **Half-Open** (test recovery).
*   **Relation:** Works with retries; if circuit is open, retries are skipped to save resources.

D20 — **Optimistic vs. Pessimistic Concurrency**
*   **Optimistic:** Assume no conflict; check version on commit (e.g., `UPDATE ... WHERE version = old`).
*   **Pessimistic:** Lock row immediately (e.g., `SELECT ... FOR UPDATE`).
*   **Choice:** Optimistic for high read/low write; Pessimistic for high contention/financial transactions.
