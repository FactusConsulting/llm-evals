## Application Architecture

**AA1** — Monoliths are single-unit deployments where all business logic shares one codebase and database. Microservices decompose the app into small, independent services communicating via APIs. **Problems:** 1. Network latency/reliability (inter-service calls), 2. Data consistency (distributed transactions), 3. Operational overhead (deployment/monitoring of N services).

**AA2** — **Synchronous:** Caller waits for a response (e.g., REST/HTTP). **Asynchronous:** Caller sends a message and continues without waiting (e.g., RabbitMQ/Kafka).

**AA3** — A **Reverse Proxy** handles basic routing, load balancing, and SSL termination. An **API Gateway** is a specialized reverse proxy that adds "API-aware" features: rate limiting, authentication, request transformation, and service discovery. It cannot entirely replace a reverse proxy in all contexts (e.g., simple static site hosting), but in a microservices stack, it usually encompasses the reverse proxy's role.

**AA4** — **Saga:** A sequence of local transactions. If one fails, "compensating transactions" undo previous steps. **Choreography:** Services exchange events; no central coordinator. Best for simple workflows. **Orchestration:** A central "orchestrator" tells services what to do. Best for complex business logic.

**AA5** — **CQRS:** Separates read models (Queries) from write models (Commands). **Event Sourcing:** Stores state as a sequence of events rather than current state. **Combination:** Solves the problem of complex read requirements on high-write data; the event store is the source of truth, and CQRS creates optimized "read views" from those events.

**AA6** — **Circuit Breaker:** Prevents a service from repeatedly trying to call a failing downstream service. **States:** Closed (requests flow), Open (requests fail fast), Half-Open (test requests allowed). **vs. Retry:** Retries assume transient failure; Circuit Breakers assume systemic failure. Use both: Retry for a few seconds, then trip the breaker if failure persists.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, highest noisy-neighbor risk, lowest security (relies on `WHERE tenant_id = X`).
2. **Shared DB/Separate Schema:** Medium cost, medium security, medium complexity (migrations are harder).
3. **Separate DB:** Highest cost, highest security, highest operational complexity, lowest noisy-neighbor risk.

**AA8** — **Strong:** All nodes see the same data simultaneously. **Eventual:** Data converges over time. **Inventory System:** Use **Strong Consistency**. Architect with a distributed SQL DB (e.g., CockroachDB) or a RDBMS with pessimistic locking/ACID transactions. Use the **Transactional Outbox pattern** to notify other services of stock changes.

**AA9** — **Sidecar:** A helper container running alongside the app container. **Envoy/Istio:** Envoy is the data plane (handles traffic); Istio is the control plane (manages Envoy config). **mTLS:** Solves identity and encryption between services without the application needing to manage certificates or trust stores.

**AA10** — **Strangler Fig:** Gradually replacing legacy functionality with new services. **Strategy:** 1. Place a proxy (API Gateway) in front of the monolith. 2. Implement a new feature in .NET 8. 3. Route specific paths from the proxy to the new service. 4. Repeat until the monolith is "strangled" and can be deleted.

**AA11** — **12-Factor App:** A methodology for cloud-native apps. **Factors:** 1. Codebase (one version control), 2. Dependencies (explicitly declared), 3. Config (stored in environment), 4. Backing services (treated as attached resources), 5. Build/Release/Run (strictly separated), 6. Processes (stateless). These ensure portability and scalability.

**AA12** — 
- **Coupling:** Event-driven (Loose) vs Request-driven (Tight).
- **Scalability:** Event-driven (High, async) vs Request-driven (Limited by synchronous chains).
- **Debugging:** Event-driven (Hard, distributed traces needed) vs Request-driven (Easier, stack traces).
- **Ordering:** Event-driven (Guaranteed per partition in Kafka) vs Request-driven (Sequential by nature).
- **Failure:** Event-driven (Retries via queue) vs Request-driven (Immediate error).
**Choice:** Request-driven for immediate feedback (UI); Event-driven for background processing/high throughput.

**AA13** — **Load Balancer:** Distributes traffic across multiple servers. **L4:** Routes based on IP/TCP port. **L7:** Routes based on application data (HTTP headers, URL paths). **Use Case:** Routing `/api/users` to one service and `/api/orders` to another.

**AA14** — **Message Queue:** Point-to-point; message is deleted after consumption (RabbitMQ). **Log-based Broker:** Append-only log; messages persist and can be replayed (Kafka). **Choice:** RabbitMQ for complex routing/task queues; Kafka for event streaming/high-throughput telemetry.

**AA15** — **Container:** Shares the host OS kernel, packaging only app and dependencies. **VM:** Includes a full guest OS and runs on a hypervisor. **Popularity:** Containers are lightweight, start instantly, and ensure "it works on my machine" consistency.

**AA16** — **Stateless:** No client data stored on server (e.g., a calculator API). **Stateful:** Remembers client state (e.g., a legacy FTP server). **Scaling:** Stateless is easier because any instance can handle any request; no need for "sticky sessions."

**AA17** — **ORM:** Maps database tables to objects in code. **Examples:** Entity Framework (.NET), Hibernate (Java). **Trade-offs:** ORM provides speed of development and type safety; Raw SQL provides maximum performance and control over complex queries.

**AA18** — **Bulkhead:** Isolates elements to prevent a failure in one from cascading. **Implementation:** 1. Thread pools: Assign a dedicated pool for "Payment Service" so a hang there doesn't exhaust threads for "Catalog Service." 2. Deployment: Run critical services on separate hardware/clusters.

**AA19** — **OT:** Central server transforms operations to maintain consistency. High complexity, low latency. **CRDTs:** Data structures that merge automatically without conflict. High offline support, lower server complexity. **Choice:** CRDTs for offline editing, as they allow local mutations that merge deterministically upon reconnection.

**AA20** — **Challenges:** Passing a `trace_id` across different languages and protocols. **Context:** W3C Trace Context is the standard header. **Sampling:** Head-based (decide at start) vs Tail-based (decide after trace completes based on errors). **Kafka:** Inject the trace context into the Kafka record headers; the consumer extracts it to continue the span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1:** Runs directly on hardware (ESXi, Xen). **Type 2:** Runs on top of an OS (VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network):** Block-level storage (iSCSI, Fibre Channel). Used for DBs/VM disks. **NAS (Network Attached Storage):** File-level storage (NFS, SMB). Used for shared folders/backups.

**OP3** — **3-Tier:** Core $\rightarrow$ Distribution $\rightarrow$ Access. **Leaf-Spine:** Every leaf connects to every spine. **Problem solved:** Reduces "east-west" latency and eliminates Spanning Tree Protocol (STP) bottlenecks common in 3-tier.

**OP4** — **Architecture:** $\ge 3$ nodes for quorum. **Fencing:** STONITH (Shoot The Other Node In The Head) to prevent data corruption. **Storage:** Ceph (distributed) or iSCSI (centralized). **Failure:** If a node fails, the remaining nodes detect loss of heartbeat, fence the dead node, and restart VMs on healthy nodes.

**OP5** — **Trunking:** Carrying multiple VLANs over one link. **802.1Q:** Adds a tag to the Ethernet frame to identify the VLAN. **Linux Config:** Create sub-interfaces (e.g., `eth0.10`, `eth0.20`) using the `vlan` module or `nmcli`.

**OP6** — **RAID 1:** Mirror. **RAID 5:** Parity (1 disk fail). **RAID 6:** Dual parity (2 disk fail). **RAID 10:** Mirror of stripes. **RAID Z2:** ZFS dual parity. **Choice:** RAID 10 for a DB server (best IOPS and fault tolerance).

**OP7** — **Architecture:** Internal AD DNS for local resolution. **Split-Horizon:** Different records for internal vs external queries. **DMZ:** Authoritative servers for public zones. **VPN:** Laptop uses a VPN tunnel to reach internal recursive resolvers. **DNSSEC:** Digitally signs external zones to prevent spoofing.

**OP8** — **Chain:** Root CA $\rightarrow$ Intermediate CA $\rightarrow$ End Entity. **Root:** Kept offline. **Sub-CA:** Issues certs. **CRL/OCSP:** Methods to check for revoked certs. **Compromise:** Sub-CA compromise requires revoking that CA; Root compromise requires rebuilding the entire PKI trust anchor.

**OP9** — **Comparison:** MPLS (Expensive, guaranteed QoS), IPsec (Cheap, unpredictable), SD-WAN (Flexible, software-managed), WireGuard (Fast, simple). **Recommendation:** SD-WAN. It allows prioritizing VoIP traffic (QoS) over multiple paths (MPLS + Internet) for reliability and cost.

**OP10** — **OOB Management:** Dedicated hardware for remote power/console access. **Criticality:** Allows fixing a server that has crashed or has no OS network. **Internet Exposure:** Extreme risk; allows attackers to reboot, reinstall OS, or steal data via virtual media.

**OP11** — **LVM:** Logical volume management (flexible resizing). **LVM-Thin:** Over-provisioning (allocates space on demand). **ZFS:** Combined FS/Volume manager with checksums. **Snapshots:** LVM (Copy-on-write), LVM-Thin (Efficient pointers), ZFS (Near-instant, highly efficient).

**OP12** — **Design:** 3 nodes across 2 sites + 1 tiebreaker (witness) at a 3rd site. **CRUSH:** Configure failure domains to ensure replicas are in different sites. **Latency:** Must be very low (<10ms) for synchronous writes. **2-Site Problem:** Without a tiebreaker, a network split causes "split-brain" where both sites think they are the master.

**OP13** — **DHCP/DORA:** Discover $\rightarrow$ Offer $\rightarrow$ Request $\rightarrow$ Acknowledge. **Failure:** Windows client attempts to renew; if it fails, it eventually assigns itself an APIPA address (`169.254.x.x`).

**OP14** — **Managed Switch:** Allows configuration of VLANs, STP, Link Aggregation (LACP), and Port Mirroring. **Unmanaged:** Plug-and-play, no config. Managed is required for security and traffic segmentation.

**OP15** — **NTP:** Network Time Protocol. **Criticality:** Log correlation, Kerberos authentication, and DB transaction ordering. **Drift:** Can cause cluster heartbeat failures, leading to unnecessary fencing/reboots.

**OP16** — **Physical:** Hardware. **VM:** Hardware abstraction. **Container:** OS abstraction. **Bare Metal Use Case:** High-performance DBs or GPU workloads where hypervisor overhead is unacceptable.

**OP17** — **UPS:** Battery for short-term power/smoothing. **Generator:** Fuel for long-term power. **ATS:** Switches power source from Utility $\rightarrow$ Generator automatically. **Need both:** UPS covers the gap between power loss and generator startup.

**OP18** — **Active-Passive:** One standby. **Active-Active:** Both serve traffic. **PostgreSQL HA:** Use Corosync for membership and Pacemaker for resource management. **STONITH** ensures the failed node is powered off before the standby promotes itself to avoid data corruption.

**OP19** — **Strategy:** 3-2-1 (3 copies, 2 media, 1 offsite). **RPO/RTO:** Recovery Point (data loss) vs Recovery Time (downtime). **Immutable:** S3 Object Lock or WORM tapes. **Backup vs DR:** Backup is getting data back; DR is getting the entire business operation back.

**OP20** — **802.1X:** Supplicant (Client) $\rightarrow$ Authenticator (Switch) $\rightarrow$ Auth Server (RADIUS). **EAP-TLS:** Certificate-based (most secure). **PEAP:** Password-based. **MAB:** Switch sends MAC address to RADIUS for devices (printers) that can't run a supplicant. **Failure:** Port is shut or moved to a "Guest" VLAN.
