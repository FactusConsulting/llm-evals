## Cloud Infrastructure Architecture

**CL1**: **IaaS** (Infrastructure as a Service) provides raw compute, storage, and networking; you manage the OS and apps (e.g., AWS EC2). **PaaS** (Platform as a Service) provides a framework for developers to build/deploy apps without managing the underlying OS (e.g., Azure App Service). **SaaS** (Software as a Service) is a fully managed application delivered via web (e.g., Google Workspace).

**CL2**: The provider manages the "Cloud" (hardware, virtualization); you manage "in the Cloud" (data, config).
*   **IaaS VMs**: Provider manages hardware/hypervisor; you manage OS, patching, and apps.
*   **Managed K8s**: Provider manages control plane; you manage worker node OS (usually) and pod configurations.
*   **SaaS (M365)**: Provider manages almost everything; you manage users, access permissions, and data.

**CL3**: **VPC** is the isolated virtual network. **Subnet** is a range of IP addresses within a VPC. **Security Group** is a stateful firewall at the instance/NIC level (allows return traffic automatically). **NACL** is a stateless firewall at the subnet level (must explicitly define both inbound and outbound rules).
*   **Layering**: VPC $\rightarrow$ Subnet (NACL) $\rightarrow$ Instance (Security Group).

**CL4**: A **Landing Zone** is a pre-configured, secure multi-account environment. **OUs** group accounts by function (Prod, Dev, Security). **Guardrails** (SCP/Azure Policy) enforce mandatory constraints. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes egress/ingress. **Centralized Logging** aggregates logs into a locked-down security account.
*   **Single-account problems**: Blast radius (one compromise affects all), quota limits, and "noisy neighbor" resource contention.

**CL5**: **IaC** is managing infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu**: Cloud-agnostic, HCL-based, state-managed. Best for multi-cloud.
*   **Pulumi**: Uses general-purpose languages (TS, Python). Best for developers who prefer code over DSL.
*   **CloudFormation/Bicep**: Provider-specific. Best for deep integration and "day zero" support of new services.
*   **Crossplane**: K8s-native (Control Plane). Best for managing cloud resources as K8s objects.

**CL6**: **HPA** scales pods based on CPU/RAM. **VPA** adjusts pod resource requests/limits. **Cluster Autoscaler** adds/removes nodes from the cluster. **KEDA** (Kubernetes Event-driven Autoscaling) scales based on external events (e.g., Kafka lag, RabbitMQ queue length).
*   **KEDA vs HPA**: Use KEDA when scaling is driven by external event volume rather than internal resource consumption.

**CL7**: **RPO** (Data loss window) and **RTO** (Downtime window).
*   **Active-Passive**: Primary handles traffic; secondary is standby.
*   **Active-Active**: Both regions serve traffic; requires global load balancing (Route53/Traffic Manager) and synchronous or near-sync DB replication.
*   **DB Replication**: Sync (zero data loss, high latency) vs Async (potential data loss, low latency).
*   **DR Types**: **Pilot Light** (DB sync'd, apps off); **Warm Standby** (scaled-down version running); **Multi-site** (full capacity in both).

**CL8**: **GitOps** uses Git as the single source of truth for infrastructure/apps; a controller pulls state from Git to the cluster. **ArgoCD** is UI-centric and push/pull; **FluxCD** is more lightweight and Git-native.
*   **Secrets**: Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift**: The controller detects the difference between Git and Live state and automatically overwrites manual changes to match Git.

**CL9**:
*   **StatefulSet**: Ensures stable network IDs and ordered deployment.
*   **PV/PVC**: Use a `local` storage class for low-latency SSDs.
*   **Headless Service**: Provides DNS for individual pod discovery (essential for clustered apps).
*   **Init Containers**: Handle filesystem preparation or waiting for DB readiness.
*   **ConfigMaps**: Mounted as volumes to specific paths.
*   **PDB**: Ensures a minimum number of replicas remain available during maintenance.

**CL10**: **Service Account** is an identity for a K8s process. **Workload Identity/IRSA** maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Bad Practice**: Mounting static JSON keys in pods is risky (leakage, rotation overhead).
*   **Federation**: Allows the cloud provider to trust the K8s cluster's identity provider, issuing short-lived tokens automatically.

**CL11**:
*   **Object (S3)**: Unstructured data, accessed via API. High durability (11 9s), virtually infinite scale.
*   **Block (EBS)**: Low-latency, formatted as a disk. High performance, attached to one VM.
*   **File (EFS)**: Shared filesystem (NFS/SMB). Accessible by many VMs simultaneously.

**CL12**: **Zero Trust** assumes the network is compromised.
*   **Components**: Network Policies (L3/L4 isolation), Service Mesh (mTLS for L7 identity/encryption), OPA/Kyverno (policy enforcement), Falco (runtime anomaly detection), Cosign (image signing).
*   **Difference**: Traditional security relies on a "hard shell" (firewall) and "soft center." Zero Trust requires verification for every single request, regardless of location.

**CL13**: A **CDN** caches content at "Edge Locations" closer to the user to reduce latency. Examples: CloudFront, Akamai. Use a CDN for static assets (images, JS, video) to reduce origin load and improve global load times.

**CL14**: **Regions** are geographic areas. **Availability Zones (AZs)** are isolated data centers within a region. Deploying across AZs protects against a single data center failure. **Zonal resources** (e.g., EBS) exist in one AZ; **Regional resources** (e.g., S3, Lambda) are replicated across the region.

**CL15**: A **Managed DB** (RDS) is a database where the provider handles: OS patching, hardware provisioning, automated backups, and high-availability failover. You handle: Schema design, query optimization, and user access.

**CL16**: **Users** (people), **Groups** (collections of users), **Roles** (assumable identities for services/users), **Policies** (JSON documents defining permissions). **Least Privilege** means granting only the minimum permissions required to perform a task. Apply it by using granular policies instead of `AdministratorAccess`.

**CL17**: **Serverless** is an execution model where the provider manages the server allocation. **Cold Starts** occur when a function is invoked after being idle, causing a delay while the environment initializes.
*   **Poor fit**: Long-running processes (timeouts), apps requiring extremely low latency (cold starts), or workloads with constant, high-volume traffic (cheaper on VMs).

**CL18**: **Ingress**: Basic L7 routing. **Gateway API**: Modern, role-oriented API for complex routing. **Annotations**: Cloud-specific tweaks (e.g., ALB settings). **Service Mesh**: Advanced traffic splitting/mTLS.
*   **TLS**: Terminated at the Load Balancer (offloading) or at the Pod (end-to-end).
*   **Gateway API**: Use it for multi-tenancy, advanced traffic splitting (canary), and better separation of concerns between infra and app teams.

**CL19**:
*   **Compute**: Savings Plans/RIs for baseline; Spot for fault-tolerant batch jobs.
*   **Right-sizing**: Use Compute Optimizer to downsize over-provisioned VMs.
*   **Storage**: S3 Intelligent-Tiering for unknown patterns; Glacier for archives.
*   **FinOps**: Implement tagging policies, automated "stop" schedules for Dev, and chargeback (billing by tag).
*   **Tools**: AWS Cost Explorer, Kubecost (for K8s), CloudHealth.

**CL20**:
*   **Strategy**: Use K8s as the abstraction layer; Terraform for consistent provisioning; VPN/Interconnect for cross-cloud networking; OIDC for identity federation.
*   **Trade-offs**: Theoretical benefit is "no lock-in" and "best-of-breed." Real-world cost is massive operational complexity and "lowest common denominator" architecture (avoiding provider-specific features).
*   **Justification**: Justified for strict regulatory requirements or extreme availability needs; otherwise, it's usually unnecessary complexity.

## OT Infrastructure Architecture

**OT1**: The **Purdue Model** segments industrial networks to ensure security and stability.
*   **Level 0**: Process (Sensors, Actuators).
*   **Level 1**: Basic Control (PLCs).
*   **Level 2**: Area Supervisory Control (HMIs, SCADA).
*   **Level 3**: Site Manufacturing Operations (Historians, MES).
*   **Level 4/5**: Enterprise/Business Logistics (ERP, Corporate IT).

**OT2**: IT focuses on **Confidentiality**; OT focuses on **Availability and Safety**. Standard IT patching (rebooting every Tuesday) is impossible in OT because it can cause physical danger or millions in lost production. Patching requires scheduled outages and rigorous testing.

**OT3**: The **IDMZ** prevents direct communication between IT and OT. Only brokered traffic (e.g., via a jump host or proxy) is allowed. Direct L4 $\rightarrow$ L1 connectivity is dangerous because a compromised corporate laptop could send a "Stop" command directly to a PLC, causing a physical crash.

**OT4**:
1.  **Modbus TCP**: L1/L2 (Simple, no security).
2.  **OPC UA**: L2/L3 (Secure, platform-independent).
3.  **EtherNet/IP**: L1/L2 (Common in Rockwell/Allen-Bradley).
4.  **PROFINET**: L1/L2 (Common in Siemens).
5.  **MQTT**: L3 $\rightarrow$ Cloud (Lightweight pub/sub).

**OT5**: A **Firewall** filters traffic based on rules (software). A **Data Diode** is a hardware device that physically allows data to flow in only one direction (using light/fiber).
*   **Use Case**: Sending data from a high-security zone (L2) to a lower one (L4) without any possibility of an inbound attack.
*   **Limitation**: No "handshake" or acknowledgement; purely one-way.

**OT6**: **Flow**: PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Boundaries**: Firewall between L2/L3; IDMZ between L3/L4; TLS encryption and API keys from Edge Gateway to Cloud.

**OT7**: **Zones** are groupings of assets with similar security requirements. **Conduits** are the communication paths between zones.
*   **Model**:
    *   Zone A: SIS (Highest security, isolated).
    *   Zone B: PLCs (Control zone).
    *   Zone C: SCADA/HMI (Supervisory zone).
    *   Zone D: Engineering Workstations (Admin zone).
    *   Zone E: Corporate (IT zone).
    *   **Conduits**: L2 $\rightarrow$ L3 (OPC UA), L3 $\rightarrow$ L4 (via IDMZ).

**OT8**:
*   **Design**: Create VLANs per production line. Place an Industrial Firewall between the SCADA/Historian and the PLC VLANs.
*   **Remote Access**: Implement a VPN $\rightarrow$ Jump Host (MFA) $\rightarrow$ Specific PLC.
*   **Transition**: Implement "Transparent Mode" firewalls first to map traffic, then gradually apply "Deny" rules during planned maintenance windows.

**OT9**: **BPCS** manages the process; **SIS** is a separate system that triggers a safe shutdown if the BPCS fails or limits are exceeded. **IEC 61511** is the safety standard.
*   **Isolation**: SIS must be isolated so a failure/attack on the BPCS doesn't disable the safety mechanism.
*   **Ransomware**: If SIS is hit, the plant loses its "safety net," requiring an immediate manual emergency shutdown.

**OT10**:
*   **PLC**: Hardware for discrete logic/local control.
*   **DCS**: Integrated system for complex, continuous processes (e.g., oil refinery).
*   **SCADA**: Software for wide-area monitoring and control.
*   **Coexistence**: Yes; SCADA often monitors multiple PLCs or a DCS.

**OT11**: **Architecture**: Corporate $\rightarrow$ VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (with session recording) $\rightarrow$ OT Asset.
*   **Why no direct RDP**: RDP is a primary vector for lateral movement. Direct access bypasses auditing and allows a compromised IT device to directly manipulate a physical process.

**OT12**:
*   **Detection**: Use passive IDS (e.g., Dragos, Nozomi) to find anomalous Modbus/S7 traffic.
*   **Response**: Isolate the compromised VPN segment; switch to "Manual Mode" for critical processes.
*   **Operator Role**: The operator is the final authority; they determine if a cyber-action requires a physical emergency stop (E-Stop).

**OT13**: **HMI** is the dashboard for operators to monitor and control the process. An **Engineering Workstation** is used to program the PLCs and configure the HMI; it has much higher privileges and software tools.

**OT14**: A **Historian** is a time-series database for process data.
*   **Plant Historian (L3)**: High-resolution, real-time data for local operations.
*   **Enterprise Historian (L4)**: Aggregated, lower-resolution data for business reporting and KPIs.

**OT15**: **Ladder Logic** is a graphical language resembling electrical relay diagrams, executed by **PLCs**. It remains dominant because it is intuitive for electricians/technicians and highly deterministic.

**OT16**: An **RTU** is designed for wide-area telemetry (e.g., pipelines, water towers) and often supports low-bandwidth/wireless comms. **PLCs** are designed for high-speed, local factory floor control.

**OT17**: **Analog** is a continuous range (e.g., 4-20mA); **Digital** is binary (On/Off). **4-20mA** is preferred over 0-20mA because 4mA represents "Live Zero"—if the wire breaks, the signal drops to 0mA, allowing the system to detect a "Wire Break" fault.

**OT18**: **Asset Inventory** identifies what is on the network (firmware, IP, vendor).
*   **Passive**: Sniffing traffic (Safe).
*   **Active**: Sending queries (Dangerous).
*   **Danger**: Active scanning can crash old PLCs that cannot handle unexpected packets or high traffic volumes.

**OT19**: **MITRE ATT&CK for ICS** focuses on physical impact.
*   **Tactics**: 1. Initial Access (VPN compromise), 2. Execution (PLC program upload), 3. Persistence (Firmware modification), 4. Impair Process Control (Modify setpoints), 5. Inhibit Response Function (Disable alarms).
*   **Difference**: Enterprise focuses on data theft; ICS focuses on process disruption/physical damage.

**OT20**:
*   **Design**: Use passive TAPs/SPAN ports to send OT traffic to a SIEM.
*   **Staffing**: IT analysts handle the alerts; OT engineers validate if the alert is a "process anomaly" or a "cyber attack."
*   **Firmware Alert**: Treat as a Critical Incident. Immediately verify the change with the engineering team; if unauthorized, isolate the PLC and revert to a known-good backup from the offline vault.
