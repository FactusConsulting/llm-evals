## Cloud Infrastructure Architecture

**CL1**: **IaaS** (Infrastructure as a Service) provides raw compute, storage, and networking; you manage the OS and apps. *Example: AWS EC2*. **PaaS** (Platform as a Service) provides a framework for developers to build/deploy apps without managing the underlying OS. *Example: Azure App Service*. **SaaS** (Software as a Service) is a fully managed application delivered via web. *Example: Google Workspace*.

**CL2**: The provider manages the "Cloud" (hardware, virtualization); you manage "in the Cloud" (data, config).
*   **IaaS VMs**: Provider manages hardware/hypervisor; you manage OS, patching, and apps.
*   **Managed K8s**: Provider manages control plane; you manage worker node OS (usually) and pod configurations.
*   **SaaS (M365)**: Provider manages almost everything; you manage users, access permissions, and data.

**CL3**: **VPC** is the isolated virtual network. **Subnet** is a range of IP addresses within a VPC. **Security Group** is a stateful firewall for instances (allows return traffic automatically). **NACL** is a stateless firewall for subnets (must explicitly define inbound and outbound rules).
*   **Layering**: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group.

**CL4**: **Landing Zone** is a pre-configured, secure multi-account environment. **OUs** group accounts by function (Prod, Dev, Security). **Guardrails** are SCPs (Service Control Policies) that prevent forbidden actions. **Shared Networking** uses a Hub-and-Spoke model (Transit Gateway/Azure Virtual WAN) to centralize egress/ingress. **Centralized Logging** aggregates logs (CloudTrail/Log Analytics) into a locked-down security account.
*   **Single-account problems**: Blast radius (one compromise affects all), quota limits, and "noisy neighbor" billing/resource contention.

**CL5**: **IaC** is managing infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu**: Cloud-agnostic, HCL-based, state-file managed. Best for multi-cloud.
*   **Pulumi**: Uses general-purpose languages (TS, Python). Best for developers who want loops/logic.
*   **CloudFormation/Bicep**: Provider-specific. Best for deep integration and "day zero" support of new services.
*   **Crossplane**: K8s-native (Control Plane). Best for managing cloud resources as K8s objects.

**CL6**: **HPA** scales pods based on CPU/RAM. **VPA** adjusts pod resource requests/limits. **Cluster Autoscaler** adds/removes VM nodes to the cluster. **KEDA** (Kubernetes Event-driven Autoscaling) scales based on external events (e.g., Kafka lag, RabbitMQ queue length).
*   **KEDA vs HPA**: Use KEDA when scaling is triggered by an external event rather than internal resource consumption.

**CL7**: **Strategy**: Active-Passive (Warm Standby) for cost-efficiency or Active-Active for zero downtime.
*   **RPO/RTO**: RPO (Data loss) minimized via async replication; RTO (Downtime) minimized via DNS failover.
*   **DB**: Sync replication (zero loss, high latency) vs Async (low latency, potential loss).
*   **DNS**: Route53 Health Checks trigger failover to secondary region.
*   **DR Types**: **Pilot Light** (DB is live, apps are off); **Warm Standby** (Scaled-down version of app is live); **Multi-site Active-Active** (Full traffic split across regions).

**CL8**: **GitOps** uses Git as the single source of truth; a controller pulls state from Git to the cluster.
*   **ArgoCD vs FluxCD**: ArgoCD has a rich UI/Dashboard; FluxCD is more lightweight and "invisible."
*   **Secrets**: Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift**: The controller detects the difference between Git and Live state and automatically overwrites manual changes to match Git.

**CL9**: **Architecture**:
*   **StatefulSet**: Ensures stable network IDs and ordered deployment.
*   **PV/PVC**: Use a `local-storage` storage class for low-latency NVMe.
*   **Headless Service**: Provides DNS for individual pod discovery (e.g., `pod-0.service`).
*   **Init Containers**: Handle filesystem preparation or waiting for DB readiness.
*   **ConfigMaps**: Mounted as volumes to specific paths.
*   **PDB**: Ensures a minimum number of replicas remain available during maintenance.

**CL10**: **Service Account**: K8s identity for a pod. **Workload Identity/IRSA**: Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Bad Practice**: Mounting static JSON keys in pods is a security risk (leakage, rotation difficulty).
*   **Federation**: Allows the pod to exchange a K8s token for a short-lived cloud token, eliminating static secrets.

**CL11**: **Object (S3)**: Unstructured data, accessed via API. High durability (11 9s). Use for backups/media. **Block (EBS)**: Low-latency disk attached to one VM. Use for DBs/OS. **File (EFS)**: Shared network filesystem (NFS/SMB). Use for shared app config/home dirs.

**CL12**: **Zero Trust**: "Never trust, always verify."
*   **Components**: Network Policies (L3/L4 isolation), Service Mesh (mTLS for L7 identity/encryption), OPA/Kyverno (Policy as Code), Cosign (Image signing), Falco (Runtime syscall monitoring).
*   **Difference**: Traditional security relies on a "hard shell" (firewall) and "soft center." Zero Trust assumes the network is already compromised and secures every single request.

**CL13**: **CDN**: A distributed network of proxy servers that cache content closer to users.
*   **Services**: CloudFront, Akamai, Azure Front Door.
*   **Use Case**: Use CDN for static assets (JS, CSS, Images) to reduce latency and origin load; serve directly from origin for highly dynamic, personalized data.

**CL14**: **Region**: A geographic area (e.g., us-east-1). **AZ**: One or more discrete data centers within a region.
*   **Multi-AZ**: Protects against a single data center failure.
*   **Zonal vs Regional**: Zonal resources (e.g., EBS volume) exist in one AZ; Regional resources (e.g., S3, Lambda) are replicated across the region.

**CL15**: **Managed DB**: A service where the provider manages the DB engine.
*   **Provider handles**: Hardware provisioning, OS patching, automated backups, high availability (failover), and scaling.
*   **You handle**: Schema design, query optimization, and user access.

**CL16**: **IAM**: Users (people), Groups (collections of users), Roles (identities for services/temporary access), Policies (JSON documents defining permissions).
*   **Least Privilege**: Granting only the minimum permissions required to perform a task. Apply by using granular policies instead of `AdministratorAccess`.

**CL17**: **Serverless**: Event-driven compute where the provider manages all infrastructure.
*   **Cold Start**: The delay when a function is invoked after being idle (provider must spin up a container).
*   **Poor Fit**: Long-running processes (timeouts), apps requiring extremely low latency (cold starts), or predictable, high-constant loads (cheaper on VMs).

**CL18**: **Ingress**: L7 load balancing. **Gateway API**: The modern, role-oriented successor to Ingress (separates Infrastructure, Gateway, and Route providers). **Annotations**: Cloud-specific tweaks (e.g., `alb.ingress.kubernetes.io`). **Service Mesh**: Advanced traffic splitting/canary.
*   **TLS**: Terminated at the Load Balancer (Cloud), Ingress Controller (Nginx), or Sidecar (mTLS).
*   **Gateway API**: Use for complex routing, multi-tenancy, and better standardization.

**CL19**: **Strategy**:
*   **Compute**: Use Savings Plans for baseline, Spot for stateless/batch, Reserved for predictable DBs.
*   **Storage**: S3 Intelligent-Tiering for unknown patterns; Glacier for archives.
*   **Right-sizing**: Use Compute Optimizer to downsize over-provisioned VMs.
*   **FinOps**: Implement tagging policies $\rightarrow$ Cost Explorer $\rightarrow$ Chargeback (billing costs to specific departments).
*   **Tools**: Kubecost (K8s), AWS Cost Explorer, Azure Cost Management.

**CL20**: **Design**: Use K8s as the "Cloud OS" to abstract the runtime. Use Terraform for consistent provisioning. Use a VPN or Interconnect (DirectConnect/ExpressRoute) for networking. Use OIDC/SAML for identity federation.
*   **Trade-offs**: Theoretical benefit is "no lock-in" and "best-of-breed." Real-world cost is massive operational overhead and "lowest common denominator" architecture (avoiding provider-specific features).
*   **Justification**: Justified for regulatory requirements (sovereignty) or extreme availability needs. Unnecessary for most mid-size companies.

## OT Infrastructure Architecture

**OT1**: **Purdue Model**: A framework for ICS network segmentation.
*   **Level 0**: Process (Sensors, Actuators).
*   **Level 1**: Basic Control (PLCs, PID controllers).
*   **Level 2**: Area Supervisory Control (HMIs, SCADA).
*   **Level 3**: Site Manufacturing Operations (Historians, MES).
*   **Level 4/5**: Enterprise/Business Logistics (ERP, Corporate IT).

**OT2**: **IT** focuses on Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability (CIA). **OT** focuses on Availability $\rightarrow$ Integrity $\rightarrow$ Confidentiality (AIC).
*   **Patching**: OT systems cannot be patched like IT because they require strict validation, often have 24/7 uptime requirements, and patches can cause unplanned process shutdowns or "brick" legacy hardware.

**OT3**: **IDMZ**: A buffer zone that prevents direct IT-to-OT communication.
*   **Traffic**: Only brokered traffic (e.g., Historian replication, Jump Host access). No direct L4 $\rightarrow$ L1.
*   **Danger**: Direct L4 $\rightarrow$ L1 access allows a compromised corporate laptop to send a "Stop" command directly to a PLC, potentially causing physical damage or safety hazards.

**OT4**:
1.  **Modbus TCP**: L1/L2 (Simple, no security).
2.  **OPC UA**: L2/L3 (Secure, platform-independent data exchange).
3.  **EtherNet/IP**: L1/L2 (Common in Rockwell/Allen-Bradley).
4.  **PROFINET**: L1/L2 (Common in Siemens).
5.  **MQTT**: L3 $\rightarrow$ Cloud (Lightweight pub/sub for IoT).

**OT5**: **Firewall**: Software/Hardware that filters packets based on rules (bidirectional). **Data Diode**: Hardware that physically allows data to flow in only one direction (using light/fiber).
*   **Use Case**: Use a diode to push data from OT to IT without any possibility of an inbound attack.
*   **Limitation**: No "handshake" or acknowledgement; purely unidirectional.

**OT6**: **Flow**: PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Boundaries**: Firewall between L2/L3; IDMZ between L3/L4; TLS encryption from Edge Gateway to Cloud.

**OT7**: **Zone**: A grouping of assets with similar security requirements. **Conduit**: The communication path between zones.
*   **Model**:
    *   **Zone A (SIS)**: Highest security, isolated.
    *   **Zone B (Control)**: PLCs/HMIs.
    *   **Zone C (Operations)**: SCADA/Historian.
    *   **Zone D (Engineering)**: Workstations (restricted access).
    *   **Zone E (Corporate)**: IT network.
    *   **Conduits**: Strictly defined firewall rules between each zone.

**OT8**: **Strategy**:
*   **VLANs**: Separate production lines into different VLANs to limit broadcast domains and lateral movement.
*   **Firewalls**: Place Industrial Firewalls between the SCADA (L3) and the PLC VLANs (L2).
*   **Remote Access**: Implement a Jump Host in the IDMZ with MFA.
*   **Transition**: Implement "Transparent Mode" (monitoring only) on firewalls first to map traffic, then move to "Enforcement Mode" during scheduled maintenance windows.

**OT9**: **BPCS** manages the process; **SIS** is a separate system that takes the plant to a "safe state" if the BPCS fails. **IEC 61511** is the standard for functional safety.
*   **Isolation**: SIS must be isolated so a failure/attack on the BPCS doesn't disable the safety triggers.
*   **Ransomware**: If SIS is hit, the plant loses its "safety net," requiring an immediate manual emergency shutdown.

**OT10**: **PLC**: Hardware for discrete logic/small-scale control. **DCS**: Integrated system for complex, continuous processes (e.g., oil refinery). **SCADA**: Software for wide-area supervisory control (e.g., pipelines).
*   **Coexistence**: Yes; a SCADA system often monitors multiple PLCs and a DCS.

**OT11**: **Architecture**: Corporate $\rightarrow$ MFA $\rightarrow$ IDMZ Jump Host $\rightarrow$ OT Asset.
*   **Requirements**: Session recording (audit trail), time-limited access (Just-in-Time), and MFA.
*   **RDP Danger**: Direct RDP allows an attacker to move laterally from a compromised IT PC directly to a control interface, bypassing all security layers.

**OT12**: **Plan**:
*   **Detection**: Use passive IDS (e.g., Dragos, Nozomi) to find anomalous PLC write commands.
*   **Response**: Isolate the compromised VPN segment; switch to manual control if necessary.
*   **Coordination**: The SOC alerts the Plant Operator; the Operator decides if the process can remain running or needs a controlled shutdown.
*   **Operator Role**: The final authority on "Process Safety." They ensure that cyber-isolation doesn't cause a physical explosion/leak.

**OT13**: **HMI**: A screen/dashboard for operators to monitor and control the process.
*   **Difference**: HMI is for *operation* (start/stop/setpoints); Engineering Workstation is for *configuration* (changing PLC code/logic).

**OT14**: **Historian**: A time-series database for process data.
*   **Plant Historian (L3)**: High-resolution, real-time data for local operations.
*   **Enterprise Historian (L4)**: Aggregated, lower-resolution data for business reporting/KPIs.

**OT15**: **Ladder Logic**: A graphical language resembling electrical relay diagrams, executed by PLCs.
*   **Dominance**: It is intuitive for electricians/technicians and provides deterministic execution (guaranteed timing).

**OT16**: **RTU**: A ruggedized device for remote sites (e.g., a pump station 10 miles away).
*   **Difference**: RTUs often have better integrated telemetry (radio/cellular) and lower power consumption than PLCs.

**OT17**: **Analog**: Continuous signal (e.g., 4-20mA). **Digital**: Binary (On/Off).
*   **4-20mA**: Preferred because 0mA indicates a "wire break" (fault), whereas 0-20mA cannot distinguish between a zero reading and a broken wire.

**OT18**: **Asset Inventory**: Knowing every IP, MAC, firmware version, and rack slot.
*   **Techniques**: Passive monitoring (sniffing traffic) is preferred. Active scanning (Nmap) can crash old PLCs by sending unexpected packets to fragile TCP stacks.

**OT19**: **MITRE ATT&CK for ICS**:
1.  **Inhibit Response Function**: Disabling alarms.
2.  **Impair Process Control**: Changing setpoints.
3.  **Modify Parameter**: Changing PLC logic.
4.  **Rootkit**: Hiding malicious code in firmware.
5.  **Damage**: Causing physical equipment failure.
*   **Difference**: Focuses on physical impact (loss of control/view) rather than just data theft.

**OT20**: **SOC Design**:
*   **Collection**: Use SPAN ports/TAPs for passive traffic analysis to avoid latency.
*   **Staffing**: Pair an IT Security Analyst (threat hunting) with an OT Engineer (process context).
*   **Firmware Alert**: Treat as a Critical Incident. Verify via "Golden Image" comparison. Coordinate with the plant floor to see if a scheduled maintenance change occurred before initiating an incident response.
