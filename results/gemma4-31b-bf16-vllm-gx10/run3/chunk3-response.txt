## OpenTofu / Terraform

**T1**: `tofu plan` is a dry run; it compares the current state with the desired configuration and shows what changes will be made without executing them. `tofu apply` executes those changes to reach the desired state.

**T2**: State is a JSON file mapping real-world resources to your configuration. Remote state stores this file in a shared location (e.g., S3), enabling team collaboration, preventing state loss, and providing state locking to prevent concurrent modifications.

**T3**: `count` uses an index (0, 1, 2) to create multiple resources; `for_each` uses a map or set of strings. `for_each` is preferred when resources are not identical or when you need to add/remove items from the middle of a list without triggering a destructive "shift" of all subsequent resources.

**T4**: This is called "drift." OpenTofu detects it during the next `plan` or `apply` by refreshing the state (comparing the state file to the actual cloud API). It will propose a change to revert the manual modification back to the configuration's desired state.

**T5**:
```hcl
resource "aws_instance" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  tags = { Name = each.key }
  # ... other required args (ami, instance_type)
}
```

**T6**: `terraform_remote_state` reads the entire state file of another project; `output` values are specific exported attributes. The recommended alternative is using a dedicated "Data" resource (e.g., `aws_vpc`) to look up resources by tags/names, as it decouples modules and avoids granting broad read access to state files.

**T7**: Provisioners run during the resource creation phase, but outputs are evaluated after the resource is created. If the `null_resource` fails or the output depends on a value only generated *after* the provisioner finishes, the first apply may fail. **Fix**: Use a `remote-exec` to write the kubeconfig to a file on the VM, then use a `data` source or a separate module to read that file, or use a `depends_on` chain to ensure the provisioner completes before the output is accessed.

**T8**: `tofu import` brings existing infrastructure under management by mapping a real ID to a resource address. **Limitation**: It only updates state, not the `.tf` code. The `import` block (1.5+) allows importing via code, enabling `tofu plan` to generate the necessary HCL configuration automatically.

**T9**: A `variable` (input) is a parameter passed into the module to make it reusable. An `output` is a value exported by the module for use by other modules or the CLI.

**T10**: A provider is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS, Azure). Running `plan` without `init` fails because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11**: It is the Dependency Lock File. It records the exact versions and hashes of providers used. Committing it ensures every team member and CI/CD pipeline uses the exact same provider version, preventing "it works on my machine" bugs.

**T12**: `tofu destroy` removes all managed infrastructure. To target a single resource: `tofu destroy -target=aws_instance.web_server`.

**T13**: A data source fetches information from an external source (API, existing state) without managing it. **Example**: Using `data "aws_ami"` to find the latest Ubuntu AMI ID instead of hardcoding it.

**T14**: `variables` are inputs provided at runtime. `locals` are internal constants or computed values. Use `locals` to avoid repeating complex expressions or to transform input variables into a usable format.

**T15**:
- `create_before_destroy`: Creates the new resource before deleting the old one (prevents downtime for DNS/Load Balancers).
- `prevent_destroy`: Errors out if a destroy is attempted (protects critical DBs).
- `ignore_changes`: Ignores drift for specific attributes (e.g., ignore tags added by an external security scanner).

**T16**: A `moved` block tells OpenTofu that a resource has changed its address (e.g., moved into a module) without changing the physical resource. This prevents OpenTofu from destroying and recreating the resource during a refactor.

**T17**: OpenTofu builds a Directed Acyclic Graph (DAG) to determine the order of operations. **Implicit**: Created when one resource references another's attribute. **Explicit**: Created via `depends_on`. `depends_on` forces a strict sequence, reducing parallelism and potentially slowing down applies; it should only be used when dependencies are hidden (e.g., IAM roles for a service).

**T18**:
1. **Modularization**: Split the monolith into smaller state files (reduces the number of resources refreshed per plan).
2. **`-refresh=false`**: Skip refreshing state from the API (fast, but risks drift).
3. **Targeting**: Use `-target` for specific changes (fast, but can lead to inconsistent state).
4. **Parallelism**: Adjust `-parallelism=N` (increases API load, may hit rate limits).

**T19**: State locking prevents two users from modifying state simultaneously. If a crash occurs, the lock remains. Manually break it with `tofu force-unlock <LOCK_ID>`. **Risk**: If another process is actually still running, you risk state corruption.

**T20**: 
1. Add the `backend "s3" { ... }` block to the config.
2. Run `tofu init`.
3. OpenTofu detects the local state and asks to migrate it to S3. Type `yes`.
4. OpenTofu uploads `terraform.tfstate` to S3 and creates the DynamoDB lock table.
5. **Verify**: Check the S3 bucket for the state file and run `tofu plan` to ensure no changes are pending.

## Ansible

**A1**: A **task** is a single unit of work (one module call). A **playbook** is a YAML file containing one or more "plays" (mapping hosts to tasks). A **role** is a structured bundle of tasks, variables, files, and templates for reuse.

**A2**: `ansible_facts` is a dictionary containing system information gathered at the start of a play. Access OS family via `ansible_facts['os_family']` or `ansible_os_family`.

**A3**: 
- `command`: Safest; executes a binary directly (no shell features like pipes/redirects).
- `shell`: Runs through `/bin/sh`; allows pipes, redirects, and environment variables.
- `raw`: Bypasses the Python requirement on the target; used for bootstrapping Python or interacting with minimal devices.

**A4**: Idempotency means running the same operation multiple times results in the same state without making unnecessary changes.
- **Idempotent**: `apt: name=nginx state=present` (only installs if missing).
- **NOT Idempotent**: `shell: echo "hello" >> /tmp/log` (appends text every single time).

**A5**:
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'epel-release' }}"
  when: ansible_os_family == 'Debian' or ansible_os_family == 'RedHat'

- name: Install htop on RedHat (second pass)
  package:
    name: htop
  when: ansible_os_family == 'RedHat'
```
*(Note: For a single task, one could use a variable for the package list based on OS family).*

**A6**: (Lowest to Highest)
1. Role defaults $\rightarrow$ 2. `group_vars` $\rightarrow$ 3. `host_vars` $\rightarrow$ 4. `set_fact` $\rightarrow$ 5. `extra_vars` (highest).

**A7**: 
1. Use `serial: 3` to limit the batch size.
2. Create two inventory groups: `[initial_nodes]` and `[remaining_nodes]`.
3. Run the play against `initial_nodes` first.
4. Use the `wait_for` module to ensure the RKE2 port (e.g., 6443) is open on the first 3 nodes before starting the `remaining_nodes` play.

**A8**: `ansible-vault` encrypts files or strings. To encrypt a single variable: use `ansible-vault encrypt_string 'my_password' --name 'db_password'`. This allows the rest of the vars file to remain plain text.

**A9**: An inventory is a list of managed nodes. **Static**: A flat file (INI/YAML) listing IPs/hostnames. **Dynamic**: A script or plugin that queries an API (e.g., AWS EC2) to generate the host list in real-time.

**A10**: `ansible webservers -m shell -a "df -h"`

**A11**: A handler is a task that only runs if "notified" by another task that reported a `changed` status. Trigger it using the `notify: handler_name` keyword.

**A12**: `ansible.cfg` defines global settings. Common settings: `inventory` (path to hosts file), `remote_user` (SSH user), and `forks` (parallel processes).

**A13**: `register` captures the output of a task into a variable.
```yaml
- shell: uptime
  register: uptime_result
- debug: msg="{{ uptime_result.stdout }}"
```

**A14**: `import_tasks` is static (processed at parse time); `include_tasks` is dynamic (processed at runtime). Use `include_tasks` if the task list depends on a variable or a conditional (`when`) evaluated during execution.

**A15**: Ansible Galaxy is a public hub for sharing roles/collections. Use a `requirements.yml` file:
```yaml
roles:
  - name: geerlingguy.nginx
```
Install via: `ansible-galaxy install -r requirements.yml`.

**A16**: Connection plugins determine how Ansible communicates with the host.
- `ssh`: Standard for Linux/Unix.
- `local`: Runs tasks on the control node itself.
- `network_cli`: Persistent connection for network devices (Cisco/Juniper) that don't support full Python.

**A17**: `delegate_to` runs a task on a different host than the current one. `run_once` ensures the task executes only once for the entire batch.
**Example**: Update a load balancer (localhost) with the IP of a remote host:
```yaml
- name: Update LB
  uri: url="http://lb/api" method=POST body="ip={{ ansible_default_ipv4.address }}"
  delegate_to: localhost
  run_once: true
```

**A18**:
1. **Forks**: Increase `forks` in `ansible.cfg` to process more hosts in parallel.
2. **Pipelining**: Enable `pipelining = True` to reduce the number of SSH operations.
3. **Fact Caching**: Use a Redis/JSON cache for facts to avoid gathering them every run.
4. **Mitogen**: Use the Mitogen plugin to replace the Ansible execution engine for massive speed gains (reduces SSH overhead).

**A19**: 
- `{{ }}`: Variable interpolation.
- `{% %}`: Control structures (loops, ifs).
- `{# #}`: Comments.
**Snippet**:
```jinja2
upstream backend {
{% for server in backend_servers %}
  # Health check for {{ server }}
  server {{ server }};
{% endfor %}
}
```

**A20**:
1. **Serial**: Set `serial: 20%` to update in batches.
2. **Pre-task**: Use `uri` or a LB module to mark the current batch as "draining."
3. **Deployment**: Update the app code.
4. **Health Check**: Use the `uri` module to poll the local app endpoint until it returns 200 OK.
5. **Post-task**: Re-enable the node in the LB.
6. **Rollback**: Wrap the deployment in a `block`. In the `rescue` section, trigger a task to revert the app version and notify the team.
