## Application Architecture

**AA1** — Monoliths are single-unit deployments where all business logic resides in one codebase/process. Microservices decompose the application into small, independent services communicating over a network. **Problems introduced:** 1. Network latency/reliability (distributed system fallacies), 2. Data consistency (distributed transactions), 3. Operational complexity (deployment, monitoring, and tracing across N services).

**AA2** — **Synchronous:** Client sends a request and waits for a response (blocking). Example: REST/HTTP. **Asynchronous:** Client sends a message and continues processing without waiting for an immediate result (non-blocking). Example: RabbitMQ/Kafka.

**AA3** — A **Reverse Proxy** (e.g., Nginx) handles basic routing, SSL termination, and load balancing. An **API Gateway** (e.g., Kong, AWS API Gateway) is a specialized reverse proxy that adds "API-aware" features: rate limiting, authentication, request transformation, and billing. It cannot replace a reverse proxy because it *is* one, but a simple reverse proxy cannot replace a gateway's complex orchestration logic.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions, each with a corresponding "compensating transaction" to undo changes if a later step fails.
- **Choreography:** Services exchange events; each service knows what to do when it sees a specific event. Best for simple workflows with few services.
- **Orchestration:** A central coordinator tells participants which local transactions to execute. Best for complex workflows with many steps.

**AA5** — **CQRS** separates the data model for writing (Commands) from the model for reading (Queries). It is paired with **Event Sourcing** (storing state as a sequence of events) because the event log serves as the "source of truth" from which read-optimized projections are built. This solves the problem of complex joins and performance bottlenecks in traditional CRUD when read and write patterns differ drastically.

**AA6** — The **Circuit Breaker** prevents a service from repeatedly trying to call a failing downstream service. **States:** 1. Closed (requests flow), 2. Open (requests fail fast immediately), 3. Half-Open (limited requests allowed to test if the service recovered). **Difference from retry:** Retries increase load on a struggling service; Circuit Breakers stop the load. Use both by retrying a few times, then tripping the breaker if failures persist.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, highest noisy-neighbor risk, lowest security (relies on `WHERE tenant_id = X`).
2. **Shared DB/Separate Schema:** Medium cost, medium security (schema-level permissions), medium complexity.
3. **Separate DB:** Highest cost, highest security (physical isolation), highest operational complexity (migrations across N DBs), lowest noisy-neighbor risk.

**AA8** — **Strong Consistency:** All reads return the most recent write. **Eventual Consistency:** Reads will eventually converge, but may return stale data. **Inventory System:** Use **Strong Consistency**. Architect with a distributed SQL database (e.g., CockroachDB) or a RDBMS with pessimistic locking/ACID transactions. At scale, use **sharding by product ID** to ensure a single partition handles a specific item's inventory to avoid cross-node locking overhead.

**AA9** — A **Sidecar** is a helper container running alongside the app container in the same pod. **Envoy** acts as the data plane (handling actual traffic), while **Istio** is the control plane (managing configuration/policies). **mTLS** solves the "trust" problem: it ensures that not only is the traffic encrypted, but both the client and server identities are verified via certificates, preventing spoofing within the cluster.

**AA10** — The **Strangler Fig** pattern involves wrapping a legacy system with a proxy and incrementally replacing specific functionalities with new services. **Strategy:** 1. Place an API Gateway/Reverse Proxy in front of the .NET Framework monolith. 2. Identify a small, low-risk module. 3. Build that module in .NET 8. 4. Update the proxy to route traffic for that specific endpoint to the new service. 5. Repeat until the monolith is an empty shell.

**AA11** — **12-Factor App:** A methodology for building scalable, maintainable cloud-native apps. **Factors:** 1. Codebase (one version control), 2. Dependencies (explicitly declared), 3. Config (stored in environment), 4. Backing services (treated as attached resources), 5. Build, release, run (strictly separated), 6. Processes (stateless). These ensure portability and scalability across environments.

**AA12** — 
- **Coupling:** Event-driven is loosely coupled (producer doesn't know consumer); Request-driven is tightly coupled.
- **Scalability:** Event-driven scales better for high-throughput writes/async processing.
- **Debugging:** Request-driven is easier (linear stack trace); Event-driven is hard (distributed event chains).
- **Ordering:** Request-driven is implicit; Event-driven requires partitioning keys (Kafka).
- **Failure:** Request-driven fails immediately; Event-driven allows consumers to catch up later.
**Choice:** Use REST/gRPC for immediate feedback (UI requests); use Kafka for background processing and data synchronization.

**AA13** — A **Load Balancer** distributes traffic across multiple servers. **Layer 4 (TCP/UDP):** Routes based on IP and port. **Layer 7 (HTTP/HTTPS):** Routes based on content (URL, headers, cookies). **Use case:** Routing `/api/users` to the User Service and `/api/orders` to the Order Service.

**AA14** — A **Message Queue** (RabbitMQ) is designed for "point-to-point" delivery; once a message is consumed, it's gone. A **Log-based Broker** (Kafka) is an append-only log; messages persist and can be replayed by multiple consumers. **Pick RabbitMQ** for task queues/work distribution; **pick Kafka** for event streaming and high-throughput data pipelines.

**AA15** — A **Container** shares the host OS kernel and isolates the application process. A **VM** includes a full guest OS and runs on a hypervisor. Containers are popular for microservices because they start in seconds, use fewer resources, and ensure "it works on my machine" consistency.

**AA16** — **Stateless:** Does not store client data between requests (e.g., a calculation API). **Stateful:** Remembers previous interactions (e.g., a database or a game server). Stateless services scale horizontally easily because any instance can handle any request.

**AA17** — An **ORM** maps database tables to objects in code. Examples: **Entity Framework** (C#), **Hibernate** (Java). **Trade-offs:** ORMs increase developer productivity and prevent SQL injection; however, they can produce inefficient queries ("N+1 problem") and hide the underlying database performance characteristics.

**AA18** — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function. **Implementation:** 1. **Thread Pools:** Assign a dedicated thread pool to each downstream service call so one slow service doesn't exhaust all app threads. 2. **Deployment Groups:** Deploy critical services on separate hardware/clusters from non-critical ones.

**AA19** — **OT (Operational Transformation):** Central server transforms operations to maintain consistency. High complexity, requires a central server. **CRDTs:** Data structures that merge automatically without conflicts. Lower server complexity, better offline support. **Choice:** CRDTs for offline editing, as they allow local mutations that can be merged asynchronously without a central coordinator.

**AA20** — **Challenges:** Maintaining a unique `trace_id` across different languages and protocols. **Context Propagation:** Using headers (W3C Trace Context) to pass the ID. **Sampling:** Head-based (decide at start) vs Tail-based (decide after the trace completes based on errors/latency). **Kafka:** To ensure continuity, the `trace_id` must be injected into the Kafka **Message Header**, not the payload, so the consumer can extract it and start a new span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware. Examples: VMware ESXi, Proxmox (KVM). **Type 2 (Hosted):** Runs as an app on an OS. Examples: Oracle VirtualBox, VMware Workstation.

**OP2** — **SAN (Storage Area Network):** Block-level storage (looks like a local disk). Uses Fibre Channel or iSCSI. Used for databases/VM disks. **NAS (Network Attached Storage):** File-level storage (shared folder). Uses NFS or SMB/CIFS. Used for shared documents/backups.

**OP3** — **3-Tier:** Core (routing), Distribution (policy/VLANs), Access (device connection). **Leaf-Spine:** Every Leaf switch connects to every Spine switch. It solves the "East-West" traffic bottleneck (server-to-server) and eliminates Spanning Tree Protocol (STP) blocking by using ECMP (Equal-Cost Multi-Path).

**OP4** — **Architecture:** Minimum 3 nodes for quorum. **Quorum:** Prevents split-brain. **Fencing:** STONITH (Shoot The Other Node In The Head) to kill a failed node. **Storage:** Ceph (distributed) is preferred for HA. **Failure:** If a node fails, the remaining nodes detect the loss of heartbeat, fence the dead node, and restart the VMs on healthy nodes.

**OP5** — **VLAN Trunking:** Carrying multiple VLANs over a single physical link. **802.1Q:** The standard for adding a "tag" to the Ethernet frame to identify the VLAN. **Linux Config:** Create sub-interfaces (e.g., `ip link add link eth0 name eth0.10 type vlan id 10`).

**OP6** — **RAID 1:** Mirroring. **RAID 5:** Parity (1 drive failure). **RAID 6:** Double parity (2 drive failures). **RAID 10:** Mirror of stripes (Fast, safe). **RAID Z2:** ZFS version of RAID 6. **Choice for DB:** RAID 10. It provides the best IOPS (no parity calculation) and high fault tolerance.

**OP7** — **Architecture:** 
- **Internal:** AD-integrated DNS for internal resolution.
- **DMZ:** Separate authoritative servers for public records.
- **Split-Horizon:** Different records for `app.company.com` depending on if the request is internal (private IP) or external (public IP).
- **DNSSEC:** Signed zones on external servers to prevent cache poisoning.
- **VPN:** Laptop uses a VPN tunnel to reach internal recursive resolvers via conditional forwarding.

**OP8** — **Chain:** Root CA $\rightarrow$ Intermediate/Issuing CA $\rightarrow$ End-entity Cert. **Root CA** must be kept offline. **CRL/OCSP:** Methods to check if a cert was revoked. **Compromise:** A compromised Sub-CA requires revoking that CA's cert (affecting only its branch); a compromised Root CA requires rebuilding the entire PKI trust anchor for every device in the org.

**OP9** — **MPLS:** Expensive, guaranteed SLA, high reliability. **IPsec VPN:** Cheap, internet-dependent, higher latency. **SD-WAN:** Orchestrated VPNs, dynamic path selection. **WireGuard Mesh:** High performance, simple, but manual management. **Recommendation:** SD-WAN. It allows prioritizing VoIP traffic (QoS) over multiple links (MPLS + Internet) for reliability and cost.

**OP10** — **OOB Management:** A dedicated hardware chip (iDRAC/iLO) allowing power control and console access regardless of OS state. **Criticality:** Allows fixing a server that won't boot or has a crashed OS. **Internet Exposure:** Catastrophic; allows an attacker to reinstall the OS, steal data via virtual media, or brick the hardware.

**OP11** — **LVM:** Logical volume management (resizing). **LVM-Thin:** Over-provisioning (allocates space on demand). **ZFS:** Combined FS and Volume Manager with checksums. **Snapshots:** LVM is copy-on-write (CoW) but can be slow; LVM-Thin is more efficient; ZFS uses a highly optimized CoW tree for near-instant snapshots.

**OP12** — **Design:** Use a 3-site deployment (Site A, Site B, and a small Witness site). **Ceph:** Use CRUSH rules to ensure replicas are spread across sites. **Latency:** Must be very low (<10ms) for synchronous writes. **Split-Brain:** 2-site Ceph is bad because if the link breaks, both sites might think they are the master, leading to data corruption. A 3rd site (tiebreaker) provides the majority vote.

**OP13** — **DHCP:** Assigns IP addresses. **DORA:** Discover, Offer, Request, Acknowledge. **Failure:** When the lease expires and no server is found, Windows clients assign themselves an **APIPA** address (169.254.x.x).

**OP14** — **Unmanaged:** Plug-and-play, no config. **Managed:** Allows VLANs, STP, Port Mirroring (for monitoring), and Link Aggregation (LACP). Essential for security (segmentation) and performance (bandwidth).

**OP15** — **NTP:** Network Time Protocol. **Criticality:** Logs must be synchronized for forensics; Kerberos authentication fails if clocks drift >5 mins. **Cluster Drift:** Can cause "split-brain" or database corruption in distributed systems that rely on timestamps for ordering.

**OP16** — **Physical:** Hardware. **VM:** Hardware abstraction via hypervisor. **Container:** OS abstraction via kernel namespaces. **Bare Metal Use Case:** High-performance databases (SQL Server/Oracle) or GPU-heavy workloads where hypervisor overhead is unacceptable.

**OP17** — **UPS:** Battery for immediate power (seconds/minutes). **Generator:** Fuel-based for long-term power (hours/days). **Both:** UPS bridges the gap until the generator starts. **ATS:** Automatically switches the power source from the grid to the generator.

**OP18** — **Active-Passive:** One node works, one waits. **Active-Active:** Both work. **PostgreSQL HA:** Use **Pacemaker/Corosync** to monitor health. **VIP:** A virtual IP that moves to the active node. **STONITH:** If the active node is unresponsive but not dead, the passive node "fences" it (cuts power) before taking over the VIP to prevent data corruption.

**OP19** — **3-2-1 Rule:** 3 copies, 2 different media, 1 offsite. **RPO (Recovery Point Objective):** Max data loss (e.g., 1 hour). **RTO (Recovery Time Objective):** Max downtime (e.g., 4 hours). **Immutable Backups:** S3 Object Lock or WORM tapes to prevent ransomware from deleting backups. **Backup vs DR:** Backup is about recovering *data*; DR is about recovering the *entire business service* (infrastructure + data).

**OP20** — **802.1X:** **Supplicant** (Client) $\rightarrow$ **Authenticator** (Switch) $\rightarrow$ **Auth Server** (RADIUS). **EAP-TLS:** Certificate-based (most secure). **PEAP:** Username/Password. **Dynamic VLAN:** RADIUS tells the switch which VLAN to put the user in after auth. **MAB:** For printers/IoT; the switch sends the MAC address to RADIUS to check against a whitelist.
