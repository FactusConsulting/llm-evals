## Cloud Infrastructure Architecture

**CL1**: **IaaS** (Infrastructure as a Service) provides raw compute, storage, and networking; you manage the OS and apps. *Example: AWS EC2*. **PaaS** (Platform as a Service) provides a framework for developers to build/deploy apps without managing the underlying OS. *Example: Azure App Service*. **SaaS** (Software as a Service) provides a fully managed application via a browser. *Example: Google Workspace*.

**CL2**: The provider manages the "Cloud" (hardware, virtualization, global infra); you manage "in the Cloud" (data, config, IAM).
*   **IaaS VMs**: Provider manages hardware/hypervisor; you manage OS, patching, and apps.
*   **Managed K8s (EKS/AKS)**: Provider manages the Control Plane; you manage worker node OS (usually) and the pods/apps.
*   **SaaS (M365)**: Provider manages almost everything; you manage users, access permissions, and data.

**CL3**: **VPC** is the isolated virtual network. **Subnet** is a range of IP addresses within a VPC. **Security Group** is a stateful firewall for instances (allows return traffic automatically). **NACL** is a stateless firewall for subnets (must explicitly allow both inbound and outbound).
*   **Layering**: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group.
*   **Stateful**: Remembers connection state (SG). **Stateless**: Evaluates every packet independently (NACL).

**CL4**: A **Landing Zone** is a pre-configured, multi-account environment. **OUs** group accounts by function (Prod, Dev, Security). **Guardrails** (SCP/Azure Policy) enforce mandatory constraints. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes egress/ingress and interconnects VPCs. **Centralized Logging** aggregates logs (S3/Log Analytics) for auditing.
*   **Single-account problems**: Blast radius (one mistake kills everything), quota limits, and messy billing/permissions.

**CL5**: **IaC** is managing infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu**: Cloud-agnostic, HCL-based, state-file driven. Best for multi-cloud.
*   **Pulumi**: Uses general-purpose languages (TS, Python). Best for developers who hate DSLs.
*   **CloudFormation/Bicep**: Provider-specific. Best for deep integration and "day zero" support of new services.
*   **Crossplane**: K8s-native (Control Plane). Best for managing infra as K8s resources.

**CL6**: **HPA**: Scales pods based on CPU/RAM. **VPA**: Adjusts pod resource requests/limits. **Cluster Autoscaler**: Adds/removes VM nodes to the cluster. **KEDA**: Event-driven autoscaling (e.g., scale based on RabbitMQ queue length).
*   **KEDA vs HPA**: Use KEDA when scaling is triggered by external events rather than internal resource consumption.

**CL7**: **Strategy**: Active-Passive (Warm Standby) for cost, Active-Active for zero downtime.
*   **RPO/RTO**: RPO (data loss) $\rightarrow$ Async replication (minutes) or Sync (zero). RTO (downtime) $\rightarrow$ DNS failover (seconds/minutes).
*   **DNS**: Route53/Traffic Manager routes traffic to healthy region.
*   **State**: Global DB (Aurora Global/CosmosDB) or cross-region replication.
*   **DR Types**: **Pilot Light** (DB is live, apps are off); **Warm Standby** (Scaled-down version of app is live); **Multi-site Active-Active** (Full capacity in both, load balanced).

**CL8**: **GitOps** uses Git as the single source of truth; a controller pulls the state into the cluster. **ArgoCD** (UI-heavy, application-centric) vs **FluxCD** (lightweight, CLI/Git-centric).
*   **Secrets**: Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift**: The controller detects the difference between Git and Live state and automatically overwrites the manual change to match Git.

**CL9**: **Architecture**:
*   **StatefulSet**: Ensures stable network IDs and ordered deployment.
*   **PV/PVC**: Use a `local-storage` storage class for low latency.
*   **Headless Service**: Provides DNS for individual pod discovery.
*   **Init Containers**: Handle filesystem setup or wait for DB readiness.
*   **ConfigMaps**: Mounted as volumes to specific paths.
*   **PDB**: Ensures a minimum number of replicas remain available during maintenance.

**CL10**: **Service Account**: K8s identity for a pod. **Workload Identity/IRSA**: Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Bad Practice**: Mounting static JSON keys in pods is a security risk (leakage, rotation pain).
*   **Federation**: Allows the pod to exchange a K8s token for a short-lived cloud token, eliminating static secrets.

**CL11**: **Object (S3)**: Unstructured data, accessed via API. High durability (11 9s). Use for backups/media. **Block (EBS)**: Low-latency disk attached to one VM. High availability within a zone. Use for DBs/OS. **File (EFS)**: Shared network drive (NFS/SMB). High availability across zones. Use for shared config/home dirs.

**CL12**: **Zero Trust**: "Never trust, always verify."
*   **Components**: Network Policies (L3/L4 isolation), Service Mesh (mTLS for L7 identity/encryption), Pod Identity (IRSA), OPA/Kyverno (policy enforcement), Cosign (image signing), Falco (runtime anomaly detection).
*   **Difference**: Traditional security relies on a "hard shell" (firewall) and "soft center." Zero Trust assumes the network is already compromised and secures every single request.

**CL13**: **CDN**: A distributed network of proxy servers (Edge locations) that cache content closer to users. *Examples: CloudFront, Akamai*. Use a CDN to reduce latency, lower origin load, and protect against DDoS. Use origin servers for dynamic, personalized, or highly sensitive data.

**CL14**: **Region**: A geographic area (e.g., us-east-1). **AZ**: One or more discrete data centers within a region.
*   **Multi-AZ**: Protects against a single data center failure.
*   **Zonal**: Tied to one AZ (e.g., EBS volume). **Regional**: Spans multiple AZs (e.g., S3, VPC).

**CL15**: **Managed DB**: A service where the provider manages the DB engine.
*   **Provider handles**: Hardware provisioning, OS patching, automated backups, high availability (failover), and scaling.
*   **You handle**: Schema design, query optimization, and user access.

**CL16**: **Users**: People. **Groups**: Collections of users. **Roles**: Identities assumed by services/users for temporary access. **Policies**: JSON documents defining permissions.
*   **Least Privilege**: Granting only the minimum permissions required to perform a task. Apply by using granular policies instead of `AdministratorAccess`.

**CL17**: **Serverless**: Event-driven compute where the provider manages all scaling and server allocation. *Examples: Lambda, Azure Functions*.
*   **Cold Starts**: Latency when a function is invoked after being idle (provider must spin up a container).
*   **Poor Fit**: Long-running processes (timeouts), apps requiring constant low-latency response, or heavy local state.

**CL18**: **Ingress**: Basic L7 routing. **Gateway API**: Modern, role-oriented API (more flexible). **Annotations**: Cloud-specific tweaks (e.g., ALB settings). **Mesh Gateway**: Advanced traffic splitting/mTLS.
*   **TLS**: Terminated at the Load Balancer (Cloud) or at the Ingress Controller (K8s).
*   **Gateway API**: Use it for complex routing, multi-tenancy, and better separation of concerns (Infra vs App teams).

**CL19**: **Strategy**:
*   **Compute**: Savings Plans for baseline, Spot for stateless/batch, RI for predictable DBs.
*   **Storage**: S3 Intelligent-Tiering for unknown patterns, Glacier for archives.
*   **Right-sizing**: Use Compute Optimizer to shrink over-provisioned VMs.
*   **FinOps**: Implement tagging (Cost Center, Project), monthly reviews, and "Showback" (reporting costs to teams) to drive accountability.

**CL20**: **Design**: Use K8s as the "Cloud OS" to standardize deployment. Use Terraform for provider-agnostic workflow. Connect via Site-to-Site VPN or DirectConnect/ExpressRoute. Use OIDC for identity federation.
*   **Trade-offs**: Theoretical benefit is "no lock-in"; real-world cost is "lowest common denominator" (you can't use provider-specific "magic" features).
*   **Justification**: Justified for regulatory requirements or extreme availability. Unnecessary for most companies due to operational overhead.

## OT Infrastructure Architecture

**OT1**: **Purdue Model**: A framework for industrial network segmentation.
*   **Level 0**: Process (Sensors, Actuators).
*   **Level 1**: Basic Control (PLCs).
*   **Level 2**: Area Supervisory Control (HMIs, SCADA).
*   **Level 3**: Site Manufacturing Operations (Historians, MES).
*   **Level 4/5**: Enterprise/Business Logistics (ERP, Corporate IT).

**OT2**: **IT** focuses on Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability (CIA). **OT** focuses on Availability $\rightarrow$ Integrity $\rightarrow$ Confidentiality (AIC).
*   **Patching**: OT systems often have strict uptime requirements (24/7/365) and legacy software that may crash if patched, requiring vendor validation before any update.

**OT3**: **IDMZ**: A buffer zone where no direct traffic flows from IT to OT.
*   **Traffic**: Only brokered traffic (e.g., Historian replication, Jump Host access). Traffic should be terminated in the DMZ and re-initiated.
*   **Danger**: Direct L4 $\rightarrow$ L1 connectivity allows a compromised corporate laptop to send "Stop" commands directly to a PLC, potentially causing physical damage or death.

**OT4**:
1. **Modbus TCP**: L1/L2 (Simple, no security).
2. **OPC UA**: L2/L3 (Secure, platform-independent).
3. **EtherNet/IP**: L1/L2 (Common in Rockwell/Allen-Bradley).
4. **PROFINET**: L1/L2 (Common in Siemens).
5. **MQTT**: L3 $\rightarrow$ Cloud (Lightweight, pub/sub).

**OT5**: **Firewall**: Software-based, allows bidirectional traffic based on rules. **Data Diode**: Hardware-based, physically allows data to flow in only one direction (optical).
*   **Use Case**: Use a diode to send logs from OT to IT without any possibility of an external attack reaching the OT network.
*   **Limitation**: No "handshake" or acknowledgement (TCP is difficult); purely unidirectional.

**OT6**: **Flow**: PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud.
*   **Boundaries**: Firewall between L3 and IDMZ; Data Diode or strict Firewall between IDMZ and Cloud.

**OT7**: **Zone**: A grouping of assets with similar security requirements. **Conduit**: The communication path between zones.
*   **Model**:
    *   **Zone A (SIS)**: Highest security, isolated.
    *   **Zone B (Control)**: PLCs/HMIs.
    *   **Zone C (Operations)**: SCADA/Historian.
    *   **Zone D (Engineering)**: Workstations.
    *   **Zone E (Corporate)**: IT.
    *   **Conduits**: Strict firewall rules between each zone.

**OT8**: **Strategy**:
*   **VLANs**: Separate by production line and function (e.g., VLAN 10-Line1-PLC, VLAN 20-Line1-HMI).
*   **Architecture**: Use an Industrial Switch (L3) at the cell level and a Core Firewall at the plant level.
*   **Remote Access**: VPN $\rightarrow$ MFA $\rightarrow$ Jump Host in IDMZ $\rightarrow$ Target Asset.
*   **Transition**: Implement "Transparent Mode" firewalls (bridge) to monitor traffic first, then switch to "Enforcement Mode" to block.

**OT9**: **BPCS** manages the process; **SIS** is a separate system that takes the plant to a "safe state" if the BPCS fails. **IEC 61511** is the standard for functional safety.
*   **Isolation**: SIS must be isolated so a failure/attack on the BPCS doesn't disable the safety triggers.
*   **Ransomware**: If SIS is hit, the plant loses its "safety net," forcing an immediate manual emergency shutdown.

**OT10**: **PLC**: Small, fast, logic-based (discrete control). **DCS**: Integrated system for complex, continuous processes (e.g., oil refinery). **SCADA**: Supervisory system for wide-area monitoring (e.g., pipelines).
*   **Coexistence**: Yes; SCADA often sits on top of multiple PLCs and DCSs.

**OT11**: **Architecture**: Corporate $\rightarrow$ VPN (MFA) $\rightarrow$ IDMZ Jump Host $\rightarrow$ OT Asset.
*   **Controls**: Session recording (audit trail), time-limited access (tickets), and "Approval" workflows.
*   **RDP Danger**: Direct RDP allows lateral movement and exposes the HMI (often an unpatched Windows box) to corporate malware.

**OT12**: **Plan**:
*   **Detection**: Use passive IDS (e.g., Nozomi/Claroty) to find anomalous PLC writes.
*   **Response**: Isolate the compromised VPN segment; shift to "Manual Mode" for critical processes.
*   **Coordination**: The SOC alerts the Plant Operator; the Operator decides if it's safe to keep running or if a controlled shutdown is needed.
*   **Operator Role**: The final authority on physical safety; they determine if a cyber-action requires a physical E-Stop.

**OT13**: **HMI**: A screen/dashboard for operators to monitor and control the process. **Engineering Workstation**: A PC used to program the PLCs and configure the system. HMIs are for *operation*; Workstations are for *configuration*.

**OT14**: **Historian**: A time-series database for process data.
*   **Plant Historian (L3)**: High-resolution, real-time data for local operations.
*   **Enterprise Historian (L4)**: Aggregated, lower-resolution data for business reporting/KPIs.

**OT15**: **Ladder Logic**: A graphical language resembling electrical relay diagrams, executed by PLCs.
*   **Dominance**: It is intuitive for electricians/technicians (non-programmers) and highly deterministic.

**OT16**: **RTU**: A ruggedized device for remote sites (e.g., a pump station 10 miles away).
*   **Difference**: RTUs often have better integrated telemetry (radio/cellular) and lower power consumption than PLCs. Use RTUs for wide-area distributed assets.

**OT17**: **Analog**: Continuous signal (e.g., 4-20mA). **Digital**: On/Off (0 or 1).
*   **4-20mA vs 0-20mA**: 4mA is the "Live Zero." If the wire breaks, the signal drops to 0mA, allowing the system to distinguish between a "low reading" (4mA) and a "broken wire" (0mA).

**OT18**: **Asset Inventory**: Knowing every IP, MAC, firmware version, and rack slot.
*   **Passive**: Sniffing traffic (Safe). **Active**: Polling devices (Dangerous).
*   **Danger**: Active scanning can crash legacy PLCs that cannot handle unexpected TCP packets or high-frequency requests.

**OT19**: **MITRE ATT&CK for ICS**:
1. **Inhibit Response Function**: Disabling alarms.
2. **Impair Process Control**: Changing PLC logic.
3. **Rootkit**: Hiding malicious code in firmware.
4. **Damage**: Over-pressurizing a tank.
5. **Discovery**: Scanning for Modbus devices.
*   **Difference**: Focuses on physical impact (Loss of Control/View) rather than just data theft. Use it to map "what happens if X is compromised" to physical outcomes.

**OT20**: **SOC Design**:
*   **Collection**: Use SPAN ports/TAPs for passive monitoring to avoid latency.
*   **Triage**: IT analysts handle the "network" alert; OT engineers validate if the "firmware change" was a scheduled maintenance or an attack.
*   **False Positives**: Common during maintenance windows; requires "Maintenance Mode" flags in the SIEM.
*   **Firmware Alert**: Immediate isolation of the engineering workstation $\rightarrow$ Compare current PLC hash against known-good backup $\rightarrow$ Manual verification of logic.
