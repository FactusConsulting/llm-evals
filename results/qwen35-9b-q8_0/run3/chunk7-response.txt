AA1 — Monoliths are a single, unified codebase deployed as one unit. Microservices are independent services communicating over a network. Three problems microservices introduce: 1. Distributed transactions (complexity of ACID across services), 2. Network latency and coupling (services depend on network availability), 3. Operational overhead (deploying, monitoring, and debugging many moving parts).

AA2 — Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST). Asynchronous communication involves sending a message without waiting for an immediate response (e.g., Message Queues like RabbitMQ).

AA3 — An API Gateway handles business logic (auth, rate limiting, aggregation), while a reverse proxy primarily forwards traffic. An API Gateway can replace a reverse proxy if the proxy is L7 (HTTP), but it cannot replace an L4 (TCP/UDP) load balancer or a proxy requiring raw TCP passthrough.

AA4 — The Saga pattern manages distributed transactions by breaking them into local transactions. Choreography uses events to trigger the next step (services react to events). Orchestration uses a central coordinator to manage steps. Choreography is better for loosely coupled systems; Orchestration is better for complex workflows requiring strict control.

AA5 — CQRS separates read and write models. Paired with Event Sourcing, it stores state as a sequence of events. This solves the problem of scaling read-heavy workloads and maintaining an audit trail, which traditional CRUD models struggle with due to denormalization and lack of history.

AA6 — Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (fail fast), Half-Open (testing). It differs from retry because retry attempts the same failing service, potentially worsening the load. Use both: Retry for transient errors, Circuit Breaker for persistent failures.

AA7 — 1. Shared DB/Schema: Low cost, high noise-neighbor risk, high ops complexity. 2. Shared DB/Separate Schema: Medium cost, better isolation, moderate ops. 3. Separate DB: High cost, best security/isolation, highest ops complexity.

AA8 — Eventual consistency allows temporary inconsistency; Strong consistency guarantees immediate agreement. For inventory (no oversell), use Strong Consistency. Data store: Relational DB (PostgreSQL). Patterns: Optimistic locking or distributed locks (Redis/Zookeeper) to ensure atomicity.

AA9 — A sidecar proxy runs alongside the app to handle traffic. Envoy is the proxy; Istio is the control plane managing Envoy instances. Data plane = traffic flow; Control plane = config management. mTLS between sidecars solves service-to-service encryption without modifying application code.

AA10 — Strangler Fig pattern migrates functionality incrementally. Strategy: Use an API Gateway to route new features to .NET 8 microservices while legacy endpoints remain on .NET Framework. Gradually replace legacy endpoints with microservices until the monolith is retired.

AA11 — 12-Factor App: 1. Codebase (versioned), 2. Dependencies (explicit), 3. Config (env vars), 4. Backing Services (attached), 5. Build/Release/Run (separated), 6. Processes (stateless). They ensure portability, scalability, and environment consistency in the cloud.

AA12 — Event-driven (Kafka): Loose coupling, high scalability, complex debugging, ordering guarantees, async failure handling. Request-driven (REST): Tight coupling, lower latency, easier debugging, synchronous failure. Choose Event for decoupling/streaming; Request for real-time interaction.

AA13 — A load balancer distributes traffic. L4 balances at IP/Port (TCP/UDP). L7 balances at HTTP/URL (headers). Use case: SSL termination or routing based on URL path.

AA14 — Message Queue (RabbitMQ) is for task queues (point-to-point). Log-based (Kafka) is for event streaming (append-only log). Pick MQ for task processing; Kafka for event sourcing/streaming.

AA15 — A container shares the host OS kernel; a VM has a full OS. Containers are popular for microservices due to lightweight footprint, fast startup, and consistent runtime environments.

AA16 — Stateless services don't store session data; Stateful services do. Stateless scales horizontally because any node can handle any request. Stateless: Web API. Stateful: Database.

AA17 — ORM maps objects to DB rows. Examples: Entity Framework (.NET), Hibernate (Java). Trade-offs: Abstraction vs performance (N+1 queries), and potential learning curve vs raw SQL control.

AA18 — Bulkhead pattern isolates resources to prevent total failure. Example: Separate thread pools for DB connections vs HTTP requests. If DB pool is exhausted, HTTP requests don't block the entire service.

AA19 — OT transforms operations to resolve conflicts; CRDTs use mathematical convergence. CRDTs are better for offline editing because they guarantee convergence without a central server to resolve conflicts.

AA20 — Distributed tracing propagates context IDs (W3C Trace Context) via headers. Sampling: Head (start) vs Tail (end). Storage: Distributed DB (Jaeger/Tempo). Kafka: Extract trace ID from producer headers and inject into consumer context to maintain continuity.

OP1 — Type 1 (Bare-metal) runs VMs directly on hardware (e.g., VMware ESXi). Type 2 (Hosted) runs on an OS (e.g., VirtualBox).

OP2 — SAN is block storage (iSCSI, Fibre Channel). NAS is file storage (NFS, SMB). Use SAN for databases; NAS for file sharing.

OP3 — 3-tier: Core (high speed), Distribution (aggregation), Access (edge). Leaf-Spine provides non-blocking bandwidth and equal path latency, solving the scalability bottleneck of 3-tier where core switches become bottlenecks.

OP4 — 3+ nodes for quorum. Shared storage: Ceph (distributed) or iSCSI. Fencing (STONITH) prevents split-brain. On failure, node is fenced, cluster re-balances storage, and services restart on remaining nodes.

OP5 — VLAN trunking carries multiple VLANs over one link. 802.1Q tags frames. Linux config: `ip link add link eth0 name eth0.10 type vlan id 10`.

OP6 — RAID 1 (Mirror), 5 (Striping+Parity), 6 (Dual Parity), 10 (Stripe+Mirror), Z2 (ZFS). For 6 drives and a DB: RAID 10 (4 usable, high perf) or ZFS RAIDZ2 (4 usable, high fault tol).

OP7 — Recursive resolvers query upstreams; Authoritative servers host zones. Forwarders send queries to upstreams; Conditional forwards specific domains. Laptop moves: DHCP updates IP, DNS updates A record, or split-horizon handles internal vs external resolution.

OP8 — Root CA (offline) -> Subordinate CA (online) -> End Entity. CRL lists revoked certs; OCSP checks status. Compromised Sub: Local certs revoked. Compromised Root: All certs invalid.

OP9 — MPLS (Expensive, reliable). IPsec (Cheap, internet). SD-WAN (Smart routing). WireGuard (Simple, fast). Recommendation: SD-WAN for VoIP (latency management and path selection).

OP10 — iDRAC/iLO/IPMI are out-of-band management interfaces. Critical for rebooting/monitoring without OS. Internet exposure allows attackers to brute-force access and control hardware.

OP11 — LVM (Logical volumes), LVM-Thin (Overcommit), ZFS (Filesystem+RAID). Snapshots: LVM (COW), Thin (pointer), ZFS (COW). Use LVM for simple VMs, ZFS for file systems/DBs.

OP12 — Stretch cluster: 2 sites. CRUSH rules for site affinity. Monitors split. Latency high. Split-brain: Without a tiebreaker (shared storage quorum), both sites write divergent data. 2-site Ceph is bad without tiebreaker due to data loss risk.

OP13 — DHCP assigns IPs. DORA: Discover, Offer, Request, Acknowledge. Unavailable: Client uses APIPA (169.254.x.x).

OP14 — Managed: Configurable (VLAN, QoS). Unmanaged: Plug and play. Enterprise needs VLANs, monitoring, and security policies.

OP15 — NTP synchronizes time. Critical for logs, Kerberos auth. Drift causes auth failures and log correlation issues.

OP16 — Physical: Hardware. VM: Virtualized OS. Container: App isolation. Bare metal: High performance DB, legacy apps, or security isolation.

OP17 — UPS: Battery backup (seconds/minutes). Generator: Fuel (hours). ATS switches power source. Need both for seamless transition during power outage.

OP18 — Active-Passive: One active, one standby. Active-Active: Both serve. Pacemaker: Corosync (cluster comm), Fencing (STONITH) prevents split-brain, VIP moves on failover.

OP19 — 3-2-1: 3 copies, 2 media, 1 offsite. RPO (data loss), RTO (downtime). Full/Inc/Diff. Dedup saves space. Immutable backups prevent ransomware. Backup = data copy; DR = system restoration.

OP20 — 802.1X: Supplicant (Client), Authenticator (Switch), Auth Server (RADIUS). EAP-TLS (Cert), PEAP (Pass). MAB uses MAC address for devices without supplicants. Failed auth denies network access.
