CL1 — IaaS provides virtualized computing resources (e.g., AWS EC2). PaaS provides a platform for developing/deploying apps without managing infrastructure (e.g., Google App Engine). SaaS provides ready-to-use software over the internet (e.g., Salesforce).

CL2 — The Shared Responsibility Model divides security duties. Provider secures the cloud (hardware, network, hypervisor). User secures what they put in the cloud (data, OS, config).
*   **IaaS VMs:** Provider secures physical host; User secures OS, patches, firewall.
*   **Managed Kubernetes:** Provider secures control plane; User secures nodes, workloads, policies.
*   **SaaS (M365):** Provider secures everything (app, infra, data); User secures identity, data access.

CL3 — **VPC:** Logical isolation boundary. **Subnet:** IP range within VPC. **Security Group:** Stateful firewall at instance level. **NACL:** Stateless firewall at subnet level.
*   **Layering:** VPC contains Subnets; Subnets have NACLs; Instances have Security Groups.
*   **Stateful:** Security Groups remember return traffic (allow in = allow out). **Stateless:** NACLs evaluate every packet independently.

CL4 — **Landing Zone:** Pre-configured foundation for multi-account environments. **OUs:** Group accounts for policy inheritance. **Guardrails:** SCPs/Policy-as-Code to enforce compliance. **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) for centralized routing. **Centralized Logging:** Unified log aggregation (e.g., CloudWatch/Log Analytics).
*   **Single Account Problem:** No logical isolation, difficult to scale, high risk of misconfiguration, compliance challenges.

CL5 — **IaC** manages infrastructure via code.
*   **Terraform/OpenTofu:** Declarative, multi-cloud, state-based.
*   **Pulumi:** Code-based (Python/TS), supports multiple providers.
*   **CloudFormation/Bicep:** Native AWS/Azure templates.
*   **Crossplane:** Kubernetes-native, uses CRDs to manage cloud resources.
*   **Choice:** Terraform for multi-cloud infra; Pulumi for code-heavy teams; CFN for AWS-only; Crossplane for K8s operators.

CL6 — **HPA:** Scales pods based on metrics (CPU/Mem). **VPA:** Scales resource requests/limits. **Cluster Autoscaler:** Adds/removes nodes. **KEDA:** Scales based on external events (queues, Kafka).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external event rates (e.g., message queue depth) rather than internal resource utilization.

CL7 — **RPO:** Data loss tolerance. **RTO:** Downtime tolerance. **Active-Active:** Both regions serve traffic (High cost, high resilience). **Active-Passive:** One active, one standby.
*   **DB:** Sync (low RPO, high latency) vs Async (high RPO, low latency). **DNS:** Route53 Health Checks + Latency Routing.
*   **DR Types:** Pilot Light (min infra), Warm Standby (partial infra), Multi-site Active-Active (full infra).

CL8 — **GitOps:** Git is the source of truth; controllers reconcile state. **ArgoCD:** K8s-native, Helm support. **FluxCD:** GitOps Toolkit, broader K8s support.
*   **Secrets:** Sealed Secrets (encrypt in Git), External Secrets (connect to Vault).
*   **Drift:** Auto-remediation (revert to Git) or alerting.

CL9 — **StatefulSet:** Manages stable network IDs and ordered startup. **PV/PVC:** Local Persistent Volume (LocalPathCS) for low latency. **Headless Service:** DNS for stable pod IPs. **Init Containers:** Pre-startup setup. **ConfigMaps:** Mount config files. **PDB:** Ensures availability during updates.

CL10 — **Service Account:** K8s identity. **Workload Identity:** Cloud IAM binding to K8s SA. **IRSA:** AWS-specific implementation.
*   **Mounting Creds:** Bad practice (rotation issues, exposure). **Workload Identity:** Federates K8s identity to cloud IAM, allowing pods to assume roles without secrets.

CL11 — **Object (S3/Blob):** Files, high durability (11 9s), high availability. **Block (EBS/Disk):** VM attached, low latency, 99.999% durability. **File (EFS/Files):** Shared mount, 99.99% durability.
*   **Use:** Object (static assets), Block (OS/App data), File (shared app data).

CL12 — **Zero Trust:** Verify every request. **Network Policies:** Deny all by default. **Service Mesh:** mTLS (Istio/Linkerd). **Pod Identity:** SPIFFE/SPIRE. **Admission:** OPA/Kyverno. **Image Signing:** Cosign. **Runtime:** Falco.
*   **Differs from Perimeter:** Perimeter trusts inside; Zero Trust verifies every request regardless of location.

CL13 — **CDN:** Caches content at edge locations. **Services:** CloudFront, Azure CDN.
*   **Use CDN:** High traffic, global latency reduction. **Use Origin:** Low traffic, dynamic content requiring freshness.

CL14 — **Region:** Geo-location. **AZ:** Isolated data centers within a region.
*   **Deploy across AZs:** High Availability (HA) against zone failure. **Zonal:** Single AZ resources. **Regional:** Multi-AZ resources.

CL15 — **Managed DB:** Provider handles patching, backups, HA, scaling, monitoring.
*   **User Tasks:** Schema design, data management, query optimization. **VM Tasks:** OS patching, hardware maintenance, backup management.

CL16 — **IAM Users:** People. **Groups:** Collections of users. **Roles:** Permissions attached to users/services. **Policies:** Rules defining permissions.
*   **Least Privilege:** Grant only necessary permissions. Apply via Role-based Access Control (RBAC) and policies.

CL17 — **Serverless:** Event-driven compute (AWS Lambda, Azure Functions).
*   **Cold Start:** Latency on first invocation. **Matters:** Real-time apps. **Poor Fit:** Long-running processes, high latency sensitivity, stateful apps.

CL18 — **Ingress:** K8s resource. **Gateway API:** Standardized API (K8s Gateway API). **Cloud LB:** Annotations. **Service Mesh:** Sidecar.
*   **TLS:** Ingress (Controller), Gateway (API), Mesh (Sidecar).
*   **Gateway API:** Use for future-proofing, standardization, and advanced routing features.

CL19 — **Cost Opt:** Reserved Instances (1-3yr), Savings Plans (flexible), Spot (interruptible). **Right-sizing:** Match resources to load. **Storage:** Tiering (Archive/Intelligent). **Idle Detection:** Auto-terminate. **FinOps:** Visibility, tagging. **Showback/Chargeback:** Allocate costs to teams.
*   **Tools:** AWS Cost Explorer, Azure Cost Management, CloudHealth.

CL20 — **Multi-cloud:** Abstraction (K8s), Terraform (portability), Networking (Direct Connect/ExpressRoute), Identity (OIDC).
*   **Trade-offs:** Cost, complexity, latency. **Justified:** Compliance, risk mitigation, avoiding lock-in. **Unnecessary:** Simple apps, single-region workloads.

OT1 — **Purdue Model (ISA-95):**
*   **L0:** Field Devices (Sensors/Actuators).
*   **L1:** Basic Process Control (PLCs/Controllers).
*   **L2:** Supervisory Control (SCADA/HMI).
*   **L3:** Enterprise Control (MES).
*   **L4:** Business Planning (ERP).
*   **L5:** Business Management (Corporate).

OT2 — **IT:** Data/Information. **OT:** Operations/Physical processes.
*   **Patching:** IT patches for security/updates. OT patches risk downtime, safety hazards, and process disruption.

OT3 — **IDMZ:** Buffer zone between IT (L3/4) and OT (L1/2).
*   **Traffic:** L4 to L2 allowed (Monitoring). L2 to L1 allowed (Control). L4 to L1 blocked.
*   **Direct L4-L1:** Dangerous because it bypasses security layers, exposing control systems to corporate threats.

OT4 — **Protocols:**
*   **Modbus TCP:** L1, Serial over IP.
*   **OPC UA:** L1/L2, Secure, platform-independent.
*   **EtherNet/IP:** L1, CIP protocol.
*   **PROFINET:** L1, Siemens ecosystem.
*   **MQTT:** L2/L3, Pub/Sub messaging.

OT5 — **Data Diode:** Hardware enforces one-way traffic (e.g., OT to IT). **Firewall:** Two-way traffic control.
*   **Use Diode:** Critical data export (e.g., to cloud) where return traffic is unacceptable.
*   **Limitation:** No return traffic, cannot block inbound threats.

OT6 — **Data Flow:** PLC -> Historian/OPC UA -> Edge Gateway (MQTT) -> Cloud Ingestion.
*   **Boundaries:** Edge Gateway to Cloud (Firewall/DMZ). OT Network to Edge (Physical/Logical isolation).

OT7 — **IEC 62443:**
*   **Zone:** Network segment with similar security requirements.
*   **Conduit:** Connection between zones (e.g., Firewall).
*   **Model:** Zone 1 (PLCs), Zone 2 (SCADA), Zone 3 (Engineering), Zone 4 (Corporate). Conduits: Firewalls between zones.

OT8 — **Segmentation:**
*   **VLANs:** Per production line/function.
*   **Firewalls:** Between VLANs (L3).
*   **Switches:** Layer 3 for routing.
*   **Vendor Access:** Jumpbox with MFA.
*   **Transition:** Phased migration, maintenance windows, parallel run.

OT9 — **SIS:** Safety Instrumented Systems (Stop process). **BPCS:** Basic Process Control (Run process).
*   **IEC 61511:** Safety Lifecycle standard.
*   **Isolation:** SIS must be isolated to prevent IT threats from disabling safety.
*   **Ransomware:** Attack on SIS = Catastrophic safety failure.

OT10 — **PLC:** Single controller, local control. **DCS:** Distributed, large plants, integrated. **SCADA:** Monitoring/Remote control.
*   **Coexist:** Yes. PLC controls process, SCADA monitors/visualizes.

OT11 — **Remote Access:**
*   **Jump Host:** Bastion server.
*   **MFA:** Mandatory.
*   **Recording:** Session logging.
*   **Vendor:** Time-limited access.
*   **No RDP to HMI:** Direct access bypasses security, high risk of malware.

OT12 — **Incident Response:**
*   **Monitoring:** IDS/Anomaly detection.
*   **Inventory:** Know assets.
*   **Steps:** Contain (Isolate), Eradicate, Recover.
*   **Operator:** Monitor physical safety, not IT.
*   **Role:** Ensure safe operations, follow safety procedures, not IT commands.

OT13 — **HMI:** Operator interface for monitoring/control.
*   **Role:** Visualize process, initiate commands.
*   **Differs from Eng Workstation:** HMI is for operators; Eng Workstation is for configuration/engineering.

OT14 — **Historian:** Time-series database for process data.
*   **Importance:** Trend analysis, compliance, troubleshooting.
*   **Plant (L3):** Process data. **Enterprise (L4):** Business data (production rates).

OT15 — **Ladder Logic:** Programming language for PLCs.
*   **Device:** PLC.
*   **Dominant:** Familiarity to electricians, deterministic behavior.

OT16 — **RTU:** Remote Terminal Unit.
*   **Differs from PLC:** RTU is for remote, harsh environments (pipelines). PLC is for factory floors.
*   **Deploy RTU:** Oil/Gas, long-distance telemetry.

OT17 — **Analog:** Continuous signal (4-20mA, 0-10V). **Digital:** On/Off.
*   **4-20mA:** Preferred over 0-20mA because 4mA is "live zero" (detects wire break). Current loop is less susceptible to noise.

OT18 — **Asset Inventory:** Foundation of security.
*   **Tools:** Passive (Promiscuous), Active (Ping/Scan).
*   **Active Scanning:** Dangerous (DoS, network disruption).

OT19 — **MITRE ATT&CK for ICS:**
*   **Tactics:** Reconnaissance, Execution, Persistence, Privilege Escalation, Credential Access.
*   **Differs from Enterprise:** ICS-specific techniques (e.g., PLC manipulation).
*   **Use:** Gap analysis against known ICS threats.

OT20 — **Converged SOC:**
*   **Logs:** Syslog/Agent (non-intrusive).
*   **SIEM:** Centralized analysis.
*   **Rules:** OT-specific (e.g., protocol anomalies).
*   **Staffing:** Hybrid (IT + OT engineers).
*   **False Positives:** High in OT; tune rules.
*   **Firmware Alert:** Verify integrity, isolate if unauthorized, notify OT team.
