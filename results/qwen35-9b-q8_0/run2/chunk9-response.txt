SC1-A
The pods fail because the Kubernetes Pod Security Standards (PSS) enforcement changed from Baseline to Restricted. Under **Restricted**, `runAsNonRoot: true` is required, and `runAsUser` must be explicitly set to a non-root UID. In the PodSpec, `runAsUser` is unset, so the container defaults to UID 0 (root). Additionally, the new base image (`cgr.dev/chainguard/static:latest`) defaults its USER to root. When the admission controller or runtime enforces Restricted PSS on restart, it detects the container running as root (either from the image default or the missing `runAsUser` in the spec), violating the `runAsNonRoot` constraint, causing the pod to be killed and restarted (CrashLoopBackOff).

SC1-B
```bash
kubectl get pods --all-namespaces --field-selector=status.phase=CrashLoopBackOff -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{json .spec.securityContext}{"\n"}{end}'
```

SC1-C
1.  **Image Fix:** Update the Dockerfile to explicitly set `USER 1000` (or a non-root UID) in the base image or the application layer.
2.  **Manifest Fix:** Update the PodSpec to include `securityContext: { runAsUser: 1000, runAsNonRoot: true }`.
3.  **CI Gate:** Add a pre-commit hook and CI step that scans Dockerfiles for `USER` directives and validates manifests against PSS policies (e.g., using `kube-score` or `kubebuilder`).
4.  **Rollout:** Use a Canary deployment. Deploy the fixed image to a small subset of pods, verify health, then promote to full rollout. This avoids downtime by keeping the old pods running until the new ones are stable.

SC2-A
The stale data issue arises from **asynchronous replication**. When the replica was promoted, it contained data up to the last WAL shipped. If replication lag was significant, the new primary lacks recent transactions committed on the old primary. To quantify data loss, check the **replication lag** (in seconds) at the time of failover using `pg_stat_replication` (for self-managed) or RDS metrics (`ReplicationLagSeconds`). The data loss window is the replication lag duration.

SC2-B
1.  **Import:** `terraform import aws_db_instance.main <new-eu-west-1-arn>`
2.  **Update State:** `terraform refresh` to sync state with the imported resource.
3.  **Detach Old:** `terraform state rm aws_db_instance.old` (if no longer needed) or update the ARN in the state.
4.  **Update Deps:** Modify Terraform variables for the new ARN and run `terraform apply` to update Security Groups, Route53 records, and Parameter Groups to reference the new instance.

SC2-C
1.  **Connection Management:** Use **RDS Proxy** (preferred over PgBouncer for RDS) to manage connections and handle failover transparently.
2.  **DNS Failover:** Configure Route53 Health Checks on the primary and replica endpoints. Use Latency-based routing or failover routing policies to switch traffic.
3.  **Retry Logic:** Implement application-level retry logic with exponential backoff for connection pool errors.
4.  **Architecture:** Recommend **Aurora Global Database**. It supports multi-master replication with low latency (RPO < 1s) and automatic failover, unlike standard RDS cross-region async replication.

SC4-A
1.  **Local Sessions:** Kubernetes stateless pods cannot share local memory. **Solution:** Externalize sessions to Redis.
2.  **NFS Storage:** NFS is not ideal for K8s PVs. **Solution:** Use NFS CSI driver with ReadWriteMany (RWX) or migrate to S3-compatible storage.
3.  **Oracle DB:** Bare-metal DBs don't scale well. **Solution:** Migrate to RDS/Aurora.
4.  **IBM MQ:** Hard to containerize. **Solution:** Use Kafka or RabbitMQ on K8s.
5.  **F5 Sticky:** K8s Service doesn't support sticky sessions natively. **Solution:** Use Ingress with session affinity or external session store.

SC6-C
