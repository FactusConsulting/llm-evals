## Cloud Infrastructure Architecture

**CL1**
*   **IaaS (Infrastructure as a Service):** Provides virtualized computing resources (VMs, storage, networks). You manage OS, apps, and data. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a platform for developing/deploying apps without managing underlying infrastructure. You manage code and data. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Delivers software over the internet. You manage user access and data; provider manages everything else. *Example: Salesforce.*

**CL2**
*   **Shared Responsibility Model:** Provider secures the cloud (physical hardware, hypervisor); Customer secures what they put in the cloud.
*   **IaaS VMs:** Provider secures hardware/network; Customer secures OS, patches, firewall rules, data.
*   **Managed Kubernetes:** Provider secures control plane; Customer secures node OS, workloads, network policies.
*   **SaaS (M365):** Provider secures app, infrastructure, and updates; Customer secures user identity, data classification, and device compliance.

**CL3**
*   **VPC:** Logical isolation of network resources within a cloud region.
*   **Subnet:** Division of a VPC into smaller IP ranges (Public/Private).
*   **Security Group (SG):** Stateful firewall at the instance level. Allows inbound/outbound based on rules.
*   **NACL:** Stateless firewall at the subnet level. Rules apply to traffic entering/leaving the subnet.
*   **Layering:** VPC contains Subnets. NACL filters traffic at the subnet boundary. SG filters traffic at the instance boundary.
*   **Stateful vs Stateless:** SG tracks connection state (return traffic allowed automatically). NACL does not (must explicitly allow return traffic).

**CL4**
*   **Landing Zone:** Pre-configured foundation (accounts, networking, identity) for rapid deployment.
*   **Organizational Units (OUs):** Hierarchical grouping of accounts for policy application.
*   **Guardrails:** SCPs (AWS) or Policy Sets (Azure) enforcing compliance (e.g., no public S3).
*   **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) connects multiple VPCs/VNets centrally.
*   **Centralized Logging:** Unified logging (e.g., CloudWatch Logs Insights, Azure Monitor) across all accounts.
*   **Single-Account Problem:** Permission sprawl, lack of isolation, single point of failure, difficult compliance auditing.

**CL5**
*   **IaC:** Managing infrastructure via code rather than manual clicks.
*   **Terraform/OpenTofu:** Declarative, multi-cloud, state-based. Best for complex, multi-cloud environments.
*   **Pulumi:** Imperative/Declarative using general-purpose languages (Python/TS). Best for teams preferring code over DSL.
*   **CloudFormation/Bicep:** Native AWS/Azure. Best for deep native integration and smaller AWS/Azure shops.
*   **Crossplane:** K8s-native. Best for managing cloud resources as K8s Custom Resources.

**CL6**
*   **HPA:** Scales pods based on CPU/Memory metrics.
*   **VPA:** Suggests or adjusts resource requests/limits for pods.
*   **Cluster Autoscaler:** Adds/removes nodes based on pending pods.
*   **KEDA:** Scales based on external events (e.g., Kafka messages, SQS queue depth).
*   **KEDA vs HPA:** Use KEDA when scaling should be driven by external demand (queue depth) rather than internal resource utilization.

**CL7**
*   **RPO/RTO:** Recovery Point Objective (data loss limit), Recovery Time Objective (downtime limit).
*   **Active-Active:** Both regions handle traffic (High cost, high resilience).
*   **Active-Passive:** One region active, one standby (Lower cost, higher RTO).
*   **DB Replication:** Sync (Zero RPO, high latency) vs Async (Low RPO, low latency).
*   **DNS Failover:** Route53/Traffic Manager routes traffic to healthy region.
*   **DR Types:**
    *   *Pilot Light:* Minimal infra (DB standby), spin up on failover.
    *   *Warm Standby:* Partial infra running, scaled up on failover.
    *   *Multi-site Active-Active:* Full infra in both regions, traffic split.

**CL8**
*   **GitOps:** Using Git as the single source of truth for infrastructure/app state.
*   **ArgoCD vs FluxCD:** ArgoCD is K8s-native, FluxCD supports Helm/Operators and non-K8s targets.
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS Secrets Manager).
*   **Drift:** GitOps controllers detect drift (manual changes) and auto-remediate by syncing Git state to the cluster.

**CL9**
*   **StatefulSet:** Manages stable network IDs and persistent storage for pods.
*   **PV/PVC:** Persistent Volume/Claim with Local Storage Class for low-latency local disk.
*   **Headless Service:** DNS service without a load balancer (returns IP list) for stable pod IPs.
*   **Init Containers:** Run before main container to prepare filesystems/configs.
*   **ConfigMaps:** Mount config files as volumes to specific paths.
*   **PDB:** Ensures minimum availability during updates/failures.

**CL10**
*   **Service Account:** K8s identity for pods.
*   **Workload Identity:** Cloud-native binding (e.g., AWS IRSA, Azure AAD Pod Identity).
*   **IRSA:** AWS specific binding of IAM Role to K8s Service Account.
*   **Mounting Creds:** Bad practice due to secret rotation lag, exposure in logs, and credential theft.
*   **Workload Identity:** Solves this by federating K8s identity with Cloud IAM, allowing pods to assume roles without secrets.

**CL11**
*   **Object Storage (S3/Blob):** Files as objects, high durability (11 9s), global access. Use for backups, static assets.
*   **Block Storage (EBS/Managed Disk):** Attached to VMs, high IOPS, ephemeral. Use for OS, databases.
*   **File Storage (EFS/Azure Files):** Network file system, shared access. Use for shared app data.
*   **Guarantees:** Object (99.999999999%), Block (99.99% availability), File (99.99% availability).

**CL12**
*   **Zero Trust:** Never trust, always verify.
*   **Network Policies:** Deny all traffic by default, allow only required.
*   **Service Mesh (mTLS):** Enforces encryption between services.
*   **Pod Identity:** K8s-native identity for service-to-service auth.
*   **Admission Controllers (OPA/Kyverno):** Enforce policies before pod creation.
*   **Image Signing:** Verify container images before deployment.
*   **Runtime Security (Falco):** Detect anomalous behavior (e.g., shell in container).
*   **Differs from Perimeter:** Perimeter trusts internal; Zero Trust verifies every request regardless of location.

**CL13**
*   **CDN:** Network of edge servers caching content closer to users.
*   **How it works:** Caches static assets at edge nodes; origin fetches on cache miss.
*   **Services:** AWS CloudFront, Azure CDN.
*   **Use Case:** Use CDN for static assets (images, JS) to reduce latency. Use Origin for dynamic content requiring real-time data.

**CL14**
*   **Regions:** Geographically distinct data centers (e.g., us-east-1).
*   **Availability Zones (AZs):** Isolated data centers within a region with independent power/network.
*   **Multi-AZ:** Deploy across AZs for High Availability (HA) and fault tolerance.
*   **Zonal vs Regional:** Zonal resources are in one AZ (cheaper, single point of failure). Regional resources span AZs (HA, more expensive).

**CL15**
*   **Managed DB:** Fully managed database service (RDS, Cloud SQL).
*   **Provider Tasks:** Patching, backups, failover, scaling, monitoring.
*   **VM DB:** Customer handles all ops (OS, DB engine, backups, HA).

**CL16**
*   **IAM:** Users (people), Groups (collections), Roles (permissions), Policies (rules).
*   **Least Privilege:** Grant only permissions necessary for a specific task.
*   **Application:** Use Roles for services, Policies for users, Permissions Boundaries to cap max access.

**CL17**
*   **Serverless:** Event-driven execution without managing servers.
*   **Comparison:** Lambda (AWS), Functions (Azure), Cloud Functions (GCP).
*   **Cold Starts:** Latency on first invocation after inactivity.
*   **Poor Fit:** Long-running processes, high-frequency low-latency requirements, stateful apps.

**CL18**
*   **Ingress:** K8s resource for external access to services.
*   **Gateway API:** New K8s standard (more flexible, multi-protocol).
*   **LB Annotations:** Cloud provider specific config on Ingress.
*   **Mesh Ingress:** Service mesh handles traffic (e.g., Istio).
*   **TLS:** Terminate at Cloud LB (Ingress passes through) or Ingress (Ingress terminates).
*   **Gateway API:** Use for multi-protocol support (HTTP/2, gRPC) and standardization across clusters.

**CL19**
*   **Commitments:** Reserved Instances (1-3yr, specific instance), Savings Plans (flexible, compute).
*   **Spot/Preemptible:** Discounted, interruptible instances for fault-tolerant workloads.
*   **Right-Sizing:** Analyze utilization to match instance size.
*   **Storage Tiering:** Move infrequent data to Archive/Intelligent-Tiering.
*   **FinOps:** Culture of cost awareness, Showback/Chargeback models to allocate costs to teams.
*   **Tools:** AWS Cost Explorer, CloudHealth, Azure Cost Management.

**CL20**
*   **Strategy:** Use Kubernetes as common runtime, Terraform for IaC portability.
*   **Networking:** AWS Direct Connect / Azure ExpressRoute + Interconnect.
*   **Identity:** SAML/OIDC federation across clouds.
*   **Trade-offs:** Complexity, cost, management overhead vs. resilience, compliance, avoiding lock-in.
*   **Justification:** Justified for geo-redundancy, compliance requirements, or specific vendor features. Unnecessary if single cloud meets all needs.

## OT Infrastructure Architecture

**OT1**
*   **Purdue Model (ISA-95):** Hierarchical model for industrial automation security.
*   **Level 0:** Field Devices (Sensors/Actuators).
*   **Level 1:** Basic Process Control System (PLCs/Controllers).
*   **Level 2:** Supervisory Control and Data Acquisition (SCADA/HMI).
*   **Level 3:** Enterprise Control System (MES).
*   **Level 4:** Business/Enterprise Systems (ERP).
*   **Level 5:** Business Planning (Supply Chain).

**OT2**
*   **IT vs OT:** IT focuses on data availability/integrity; OT focuses on safety/availability of physical processes.
*   **Patching:** OT patching risks downtime, safety hazards, and equipment damage. IT patching is frequent; OT patching is planned and tested.

**OT3**
*   **IDMZ:** Isolated Demilitarized Zone between IT and OT.
*   **Traffic:** L4 (IT) to L2 (OT) allowed (e.g., ERP to SCADA). L1 (OT) to L2 allowed (Control to Supervisory).
*   **Danger:** Direct L4 to L1 bypasses security layers, allowing malware to reach critical control systems directly.

**OT4**
*   **Modbus TCP:** L1 (PLC-to-PLC), simple polling.
*   **OPC UA:** L1/L2 (Secure, platform-independent data exchange).
*   **EtherNet/IP:** L1 (Rockwell automation, CIP protocol).
*   **PROFINET:** L1 (Siemens automation, real-time).
*   **MQTT:** L2/L3 (Lightweight messaging for telemetry).

**OT5**
*   **Data Diode:** Hardware device allowing traffic in only one direction (e.g., OT to IT).
*   **Firewall:** Bi-directional filtering.
*   **Use Diode:** When data must leave OT (e.g., to cloud) but no return traffic is allowed.
*   **Limitation:** Cannot receive commands or updates from the other side.

**OT6**
*   **Data Flow:** PLC -> OPC UA Server -> Historian -> Edge Gateway -> MQTT Broker -> Cloud Ingestion.
*   **Security Boundaries:**
    *   *Edge to Cloud:* Firewall/DMZ.
    *   *OT to IT:* IDMZ.
    *   *PLC to Historian:* Internal OT network (no direct internet).

**OT7**
*   **IEC 62443:** Security standard for industrial automation.
*   **Zone:** Logical or physical boundary (e.g., a network segment).
*   **Conduit:** Connection between zones (e.g., firewall, gateway).
*   **Model:**
    *   *Zone 1:* PLCs/Controllers.
    *   *Zone 2:* SCADA Servers/HMI.
    *   *Zone 3:* Engineering Workstations.
    *   *Zone 4:* Corporate Network.
    *   *Conduits:* Firewalls between zones.

**OT8**
*   **VLAN Design:** Separate VLANs per production line and function (Engineering, SCADA, PLC).
*   **Firewall Placement:** Between VLANs and at network edge.
*   **Switch Architecture:** Layer 3 switches for routing between VLANs.
*   **Transition:** Phased migration (parallel run), vendor access via jump hosts, no production downtime.

**OT9**
*   **SIS vs BPCS:** SIS (Safety Instrumented System) stops processes to prevent hazards. BPCS (Basic Process Control) runs normal operations.
*   **IEC 61511:** Functional safety standard for SIS.
*   **Isolation:** SIS must be isolated to prevent IT malware from disabling safety functions.
*   **Ransomware Impact:** If ransomware reaches SIS, it could cause physical damage, injury, or environmental disaster.

**OT10**
*   **PLC:** Discrete control (on/off), rugged, local.
*   **DCS:** Continuous process control (chemical plants), integrated, centralized.
*   **SCADA:** Monitoring and data collection over wide areas.
*   **Coexistence:** Yes. PLCs control machines, SCADA monitors them, DCS manages large processes.

**OT11**
*   **Remote Access:** Jump Host (Bastion), MFA, Session Recording.
*   **Vendor Access:** Time-limited, audited, via jump host.
*   **RDP to HMI:** Unacceptable because it bypasses network security, exposes HMI directly to internet/corporate network.

**OT12**
*   **Detection:** IDS (e.g., NetScout), Anomaly Detection (baseline traffic).
*   **Inventory:** Know all assets (IPs, protocols).
*   **Response:** Contain (Isolate network segment), Recover (Restore from clean backup), Notify (Management/Regulators).
*   **Operator Role:** Monitor physical status, do not interact with compromised systems, follow safety procedures.

**OT13**
*   **HMI:** Graphical interface for operators to monitor/control processes.
*   **Role:** Runtime interaction.
*   **Differs from Engineering Workstation:** HMI is for operators (read-only or limited control), Engineering Workstation is for configuration/programming (write access).

**OT14**
*   **Historian:** Time-series database for process data.
*   **Importance:** Trend analysis, compliance, troubleshooting.
*   **Plant Historian (L3):** Real-time, high frequency, local.
*   **Enterprise Historian (L4):** Aggregated, long-term, business reporting.

**OT15**
*   **Ladder Logic:** Programming language resembling relay logic (rungs).
*   **Device:** PLC.
*   **Dominance:** Familiarity to electricians, reliability, ease of troubleshooting, hardware support.

**OT16**
*   **RTU:** Remote Terminal Unit, collects data from field devices, communicates via serial/radio.
*   **Differs from PLC:** RTU is for telemetry in harsh environments; PLC is for complex local control logic.
*   **Deployment:** Pipelines, remote oil/gas wells, utility grids.

**OT17**
*   **Analog:** Continuous signal (4-20mA, 0-10V).
*   **Digital:** Discrete signal (On/Off).
*   **4-20mA vs 0-20mA:** 4-20mA allows "live zero" (0mA indicates wire break), 0-20mA cannot distinguish between 0 signal and broken wire.

**OT18**
*   **Asset Inventory:** List of all OT assets (IPs, types, criticality).
*   **Foundation:** Cannot secure what you don't know.
*   **Discovery:** Passive (Promiscuous mode, NetFlow), Active (Ping, Nmap).
*   **Active Scanning Risk:** Can cause network congestion, trigger safety shutdowns, or crash legacy devices.

**OT19**
*   **MITRE ATT&CK for ICS:** Framework mapping adversary tactics to OT environments.
*   **Tactics/Techniques:**
    *   *Reconnaissance:* T1595 (Identify Services).
    *   *Execution:* T1059 (Command and Scripting Interpreter).
    *   *Persistence:* T1546 (Scheduled Task).
    *   *Privilege Escalation:* T1068 (Exploitation for Privilege Escalation).
    *   *Exfiltration:* T1041 (Exfiltration Over C2 Protocol).
*   **Differs from Enterprise:** Includes ICS-specific techniques (e.g., PLC manipulation).
*   **Usage:** Assess gaps by mapping current defenses against known ICS threats.

**OT20**
*   **Log Collection:** Syslog, NetFlow (passive), avoid agent installation on critical PLCs.
*   **SIEM:** Splunk, QRadar (OT-specific parsers).
*   **Detection Rules:** Focus on anomalies (e.g., unexpected firmware updates, port scans).
*   **Staffing:** Hybrid team (IT analysts for logs, OT engineers for context).
*   **False Positives:** High in OT due to legacy protocols; tune rules based on baseline.
*   **Alert Handling:** Verify change via engineering logs, check safety impact, isolate if malicious, notify control room.
