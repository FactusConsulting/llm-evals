## Application Architecture (20 questions)

**AA1**
*   **Difference:** Monoliths are a single codebase deployed as one unit; microservices are modular, independently deployable services communicating over a network.
*   **3 Problems:**
    1.  **Distributed Transactions:** Requires complex patterns (Saga) instead of ACID transactions.
    2.  **Network Latency/Complexity:** Inter-service calls introduce latency and failure points not present in local method calls.
    3.  **Data Consistency:** Data is split across databases, making global consistency harder to maintain.

**AA2**
*   **Synchronous:** Caller waits for a response before proceeding (Request-Response). Example: HTTP/REST, gRPC.
*   **Asynchronous:** Caller sends a message and continues without waiting. Example: Message Queues (RabbitMQ, Kafka), WebSockets (for push).

**AA3**
*   **Difference:** A Reverse Proxy handles traffic routing, SSL termination, and load balancing (L4/L7). An API Gateway adds business logic (auth, rate limiting, aggregation, versioning).
*   **Replacement:** No. A Gateway cannot replace a reverse proxy entirely because proxies often handle lower-level traffic (L4 TCP/UDP) and edge security (DDoS protection) that gateways do not.

**AA4**
*   **Saga:** Manages distributed transactions by breaking them into local transactions with compensating actions on failure.
*   **Choreography:** Services publish events; other services subscribe and react. Good for simple, decoupled flows.
*   **Orchestration:** A central coordinator manages the flow and compensations. Good for complex, long-running workflows requiring strict control.

**AA5**
*   **CQRS:** Separates read and write operations into different models.
*   **Event Sourcing:** Stores state as a sequence of events rather than current snapshots.
*   **Problem Solved:** Allows independent scaling of read/write models, provides a complete audit trail, and decouples complex read queries from write logic.

**AA6**
*   **Pattern:** Protects a system from failures in a downstream service by stopping requests after a threshold.
*   **States:** Closed (Normal), Open (Failing), Half-Open (Testing recovery).
*   **Difference:** Retry with backoff attempts the same request; Circuit Breaker stops sending requests to a dead service to prevent cascading failure.
*   **Usage Together:** Use Circuit Breaker to stop traffic, and Retry with Backoff for transient errors within the "Half-Open" state.

**AA7**
1.  **Shared DB, Shared Schema:**
    *   *Cost:* Low. *Security:* Low (data leakage risk). *Ops:* Low. *Noise:* High (one tenant affects all).
2.  **Shared DB, Separate Schema:**
    *   *Cost:* Medium. *Security:* Medium. *Ops:* Medium. *Noise:* Low.
3.  **Separate DB:**
    *   *Cost:* High. *Security:* High. *Ops:* High (many DBs to manage). *Noise:* None.

**AA8**
*   **Difference:** Strong consistency guarantees immediate visibility of updates; eventual consistency allows temporary divergence.
*   **Architecture:** Strong consistency is required for inventory. Use a Relational DB (PostgreSQL) with distributed locking (e.g., Redis or ZooKeeper) or optimistic locking to prevent overselling.

**AA9**
*   **Sidecar:** A proxy container deployed alongside the main app to handle traffic, security, and observability.
*   **Envoy/Istio:** Envoy is the data plane (handles traffic); Istiod is the control plane (manages Envoy config).
*   **mTLS:** Solves service-to-service encryption without modifying application code, ensuring mutual authentication between services.

**AA10**
*   **Pattern:** Gradually replace legacy functionality with new services while keeping the old system running.
*   **Strategy:** Deploy .NET 8 microservices behind an API Gateway. Route specific endpoints (e.g., `/api/v2/users`) to the new services and legacy endpoints to the .NET Framework monolith. Slowly migrate traffic until the monolith is retired.

**AA11**
*   **Methodology:** Best practices for building cloud-native apps.
*   **6 Factors:**
    1.  **Codebase:** Versioned and immutable.
    2.  **Dependencies:** Explicitly declared.
    3.  **Config:** Externalized (not in code).
    4.  **Backing Services:** Treated as attached resources.
    5.  **Build/Run/Deploy:** Strictly separated.
    6.  **Processes:** Stateless, scaled out.

**AA12**
*   **Coupling:** Event-driven (Loose) vs Request-driven (Tight).
*   **Scalability:** Event-driven scales horizontally better (decoupled consumers).
*   **Debugging:** Event-driven is harder (asynchronous logs).
*   **Ordering:** Kafka guarantees ordering per partition; REST is request-based.
*   **Failure:** Event-driven allows retry/compensation; REST fails immediately.
*   **Choice:** Use Kafka for batch processing/event streaming; REST for real-time user interactions.

**AA13**
*   **Load Balancer:** Distributes traffic across servers.
*   **L4:** Operates at Transport Layer (TCP/UDP). L7 operates at Application Layer (HTTP/HTTPS).
*   **L7 Use Case:** SSL Termination or URL-based routing (e.g., `/api` to Service A, `/static` to CDN).

**AA14**
*   **Message Queue (RabbitMQ):** Point-to-point or Pub/Sub, low latency, message acknowledgment.
*   **Log Broker (Kafka):** Append-only log, high throughput, replayable.
*   **Choice:** Use MQ for task queues (e.g., sending emails). Use Kafka for event streaming and log aggregation.

**AA15**
*   **Container:** Lightweight, shares host OS kernel, includes app + dependencies.
*   **VM:** Full OS, heavier, isolated kernel.
*   **Popularity:** Fast startup, high density, consistent environment across dev/prod.

**AA16**
*   **Stateless:** No memory of previous requests (e.g., Web API).
*   **Stateful:** Maintains session data (e.g., Database, Session Store).
*   **Scaling:** Stateless scales easily (any node handles any request). Stateful requires sticky sessions or session replication.

**AA17**
*   **ORM:** Maps database tables to object classes.
*   **Examples:** Entity Framework (.NET), Hibernate (Java).
*   **Trade-offs:** ORM increases productivity but can lead to performance issues (N+1 queries) and reduced SQL flexibility.

**AA18**
*   **Pattern:** Isolates resources to prevent one failure from affecting others.
*   **Relation:** Ensures that if one service fails, it doesn't exhaust shared resources (CPU/Memory) for the whole system.
*   **Example:** Allocate separate thread pools for "Payment" and "Inventory" services within a monolith so a payment spike doesn't block inventory checks.

**AA19**
*   **OT:** Transforms operations to resolve conflicts (server-dependent).
*   **CRDTs:** Data types that converge mathematically (client-side capable).
*   **Offline Support:** CRDTs are superior because they allow local edits to merge automatically without server intervention.
*   **Choice:** CRDTs for offline-first systems.

**AA20**
*   **Context Propagation:** Pass `TraceID` and `SpanID` via HTTP headers (W3C Trace Context).
*   **Sampling:** Head-based (sample at start) vs Tail-based (sample at end).
*   **Storage:** Jaeger/Tempo store spans for visualization.
*   **Async/Messaging:** Trace continuity requires passing headers into Kafka message metadata or payload so downstream consumers can link spans.

## On-Premise Infrastructure Architecture (20 questions)

**OP1**
*   **Type 1 (Bare-metal):** Runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V).
*   **Type 2 (Hosted):** Runs on top of an OS (e.g., VMware Workstation, VirtualBox).
*   **Difference:** Type 1 is for production/data centers; Type 2 is for development/testing.

**OP2**
*   **SAN (Storage Area Network):** Block-level storage (e.g., iSCSI, Fibre Channel). Used for databases.
*   **NAS (Network Attached Storage):** File-level storage (e.g., NFS, SMB/CIFS). Used for file sharing.
*   **Usage:** SAN for performance-critical apps; NAS for general file storage.

**OP3**
*   **3-Tier:** Core (High speed), Distribution (Aggregation), Access (Edge).
*   **Leaf-Spine:** Every leaf connects to every spine.
*   **Problem Solved:** Eliminates uplink bottlenecks and latency of 3-tier architectures, providing non-blocking bandwidth.

**OP4**
*   **Architecture:** 3+ nodes for quorum. Shared storage (Ceph preferred for HA).
*   **Quorum:** Majority vote required to write.
*   **Fencing:** Prevents split-brain by isolating failed nodes (STONITH).
*   **Failure:** Cluster elects a new leader; storage remains accessible via surviving nodes.

**OP5**
*   **VLAN Trunking:** Carries multiple VLANs over a single link.
*   **802.1Q:** Adds a 4-byte tag to Ethernet frames.
*   **Linux Config:** `ip link add link eth0 name eth0.10 type vlan id 10` (creates sub-interface for VLAN 10).

**OP6**
*   **RAID 1:** Mirror (50% capacity). RAID 5: Striping+1 Parity (N-1). RAID 6: Striping+2 Parity (N-2). RAID 10: Stripe+Mirror (50%). ZFS RAIDZ2: ZFS equivalent of RAID 6.
*   **Choice:** ZFS RAIDZ2. With 6 drives, it offers better capacity efficiency than RAID 10 and provides data integrity (checksums) crucial for databases.

**OP7**
*   **Architecture:** Recursive resolvers (ISP) query Authoritative servers (AD).
*   **Forwarders:** Internal servers forward queries to public DNS.
*   **Split-Horizon:** Internal queries go to AD; External queries go to Public DNS.
*   **Laptop Move:** DHCP updates DNS records; Split-horizon ensures internal traffic stays internal even when on VPN.

**OP8**
*   **Chain:** Root CA (Offline) -> Subordinate CA -> End-Entity Cert.
*   **CRL vs OCSP:** CRL is a list of revoked certs (periodic); OCSP is real-time check.
*   **Compromised Sub:** Revoke certs issued by that CA.
*   **Compromised Root:** Revoke all certs, rebuild PKI (catastrophic).

**OP9**
*   **MPLS:** Reliable, expensive, private. IPsec: Cheap, public internet. SD-WAN: Smart routing, cost-effective. WireGuard: Simple, mesh.
*   **Recommendation:** SD-WAN. Balances cost, reliability, and latency for VoIP better than raw IPsec or expensive MPLS.

**OP10**
*   **iDRAC/iLO/IPMI:** Out-of-band (OOB) management interfaces.
*   **Criticality:** Allows remote management (console access) even if the OS is down.
*   **Risk:** Exposing to the internet allows attackers to pivot into the network or brute-force access.

**OP11**
*   **LVM:** Logical volumes on physical disks. LVM-Thin: Over-provisioning. ZFS: Filesystem with RAID.
*   **Snapshots:** LVM (Copy-on-write), ZFS (Copy-on-write with checksums).
*   **Usage:** ZFS for DBs (integrity); LVM-Thin for VMs (flexibility).

**OP12**
*   **Strategy:** 3 nodes (2 at Site A, 1 at Site B) or 2 sites + Cloud tiebreaker.
*   **CRUSH:** Rules determine where data replicas are placed.
*   **Split-Brain:** If network partitions, one site loses quorum.
*   **Risk:** 2-site Ceph without a tiebreaker risks data loss if one site loses quorum and the other writes.

**OP13**
*   **DHCP:** Dynamic Host Configuration Protocol.
*   **DORA:** Discover, Offer, Request, Acknowledge.
*   **Unavailable:** Client gets APIPA address (169.254.x.x) and cannot communicate.

**OP14**
*   **Managed:** Configurable (VLANs, QoS, STP). Unmanaged: Plug-and-play.
*   **Features:** Port mirroring, ACLs, Spanning Tree Protocol.
*   **Importance:** Prevents loops, controls traffic priority, and segments networks.

**OP15**
*   **NTP:** Network Time Protocol.
*   **Criticality:** Logs, Kerberos authentication, Certificate validation.
*   **Drift:** Causes authentication failures and inability to correlate logs across servers.

**OP16**
*   **Physical:** Raw hardware. VM: OS abstraction. Container: App abstraction.
*   **Bare Metal:** Use for high-performance DBs, HFT, or workloads requiring direct hardware access.

**OP17**
*   **UPS:** Battery backup for seconds/minutes (surge protection). Generator: Long-term power (hours/days).
*   **ATS:** Switches power source from Utility to Generator automatically.
*   **Need:** UPS bridges the gap between outage and generator startup.

**OP18**
*   **Active-Passive:** One active, one standby. Active-Active: Both handle load.
*   **Pacemaker/Corosync:** Manages cluster state.
*   **STONITH:** Fencing mechanism to ensure only one node writes to storage during failure.
*   **Failover:** VIP moves to the active node; cluster detects failure and promotes standby.

**OP19**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Recovery Point Objective (data loss) / Recovery Time Objective (downtime).
*   **Types:** Full (slow, complete), Incremental (fast, small), Differential (medium).
*   **Immutable:** WORM storage prevents ransomware encryption.
*   **Backup vs DR:** Backup is data copy; DR is restoring full system functionality.

**OP20**
*   **802.1X:** Port-based access control.
*   **Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
*   **Methods:** EAP-TLS (Certificate), PEAP (Password).
*   **Failure:** Port drops traffic until authenticated.
*   **MAB:** MAC Authentication Bypass allows devices (printers) without supplicants to authenticate via MAC address.
