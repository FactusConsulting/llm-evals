T1 — Easy: `tofu plan` analyzes the configuration and state to determine what changes are needed without making any changes. `tofu apply` executes the plan, creating, updating, or destroying resources to match the desired state.

T2 — Easy: State is the record of all known resources managed by OpenTofu, including their attributes and dependencies. Remote state is important for collaboration (multiple users/teams), security (encryption at rest), and persistence (state survives local machine loss).

T3 — Medium: `count` creates a list of resources indexed by integer (0, 1, 2...), while `for_each` creates resources indexed by a map key (string, object, or set). `for_each` is preferred when resources need unique names or when iterating over a set of specific identifiers rather than a count.

T4 — Medium: OpenTofu detects drift by comparing the current state against the configuration during `plan`. If a resource is modified externally, the state shows the old attributes, and the plan suggests an update to match the config. If the external change makes the resource incompatible with the config, it may suggest destruction/recreation.

T5 — Medium:
```hcl
resource "aws_instance" "web_servers" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

T6 — Hard: `terraform_remote_state` reads outputs from another state file, coupling modules tightly. Output values are read-only from the current state. The recommended alternative is using a shared backend (e.g., S3 with DynamoDB) or a dedicated data source like `aws_ssm_parameter` or a CI/CD artifact store to avoid circular dependencies and state coupling.

T7 — Hard: The `null_resource` with `remote-exec` runs asynchronously. On first apply, the provisioner hasn't finished executing when the dependent resource tries to read the output. Fix: Use `depends_on` to ensure the `null_resource` completes before dependent resources run, or use `local-exec` to write the config to a file and read that file in the dependent resource.

T8 — Medium: `tofu import` attaches an existing resource to the state without recreating it. Limitations: The resource must match the configuration exactly; complex resources may fail. The `import` block (1.5+) allows defining the import ID directly in the code, making it declarative and reusable across runs, unlike the CLI command which is imperative.

T9 — Easy: A variable is an input value passed to a module or root module. Input variables are defined in `variable` blocks and passed in; output values are defined in `output` blocks and returned from a module.

T10 — Easy: A provider is a plugin that interacts with a cloud API (e.g., AWS, Azure). Running `tofu plan` without `tofu init` fails because `init` downloads the necessary provider plugins and sets up the working directory.

T11 — Easy: `.terraform.lock.hcl` records the exact versions of providers used. It should be committed to prevent "dependency hell" where different environments use different provider versions, causing plan drift or failures.

T12 — Easy: `tofu destroy` removes all resources defined in the configuration. To target a single resource, use `tofu destroy -target=resource_type.name`.

T13 — Easy: A data source fetches existing data from a provider (e.g., `aws_ami`). Use it when you need to reference an existing resource (like an AMI ID) rather than creating a new one.

T14 — Medium: `locals` are computed values within a module, calculated at runtime. `variables` are inputs passed from outside. Use `locals` for derived values (e.g., concatenating strings, calculating env vars) to avoid passing complex logic through inputs.

T15 — Medium: The `lifecycle` block controls resource behavior. `create_before_destroy` ensures the new resource exists before the old one is deleted (prevents downtime). `prevent_destroy` stops accidental deletion of critical resources. `ignore_changes` prevents specific attributes from being updated during apply (useful for immutable attributes managed externally).

T16 — Medium: The `moved` block tells OpenTofu how to map resources from an old address to a new one during a state refresh. It helps refactor code (e.g., renaming a resource) without destroying and recreating the underlying infrastructure.

T17 — Hard: The dependency graph orders resource execution based on dependencies. Implicit dependencies are inferred from references (e.g., `aws_instance` referencing `aws_security_group`). Explicit dependencies use `depends_on`. `depends_on` forces specific ordering but reduces parallelism; use sparingly because it can hide logical errors and slow down plans.

T18 — Hard: Strategies: 1. `tofu plan -refresh-only` (check drift without full plan). 2. `tofu plan -target` (plan specific resources). 3. `tofu plan -var-file` (split large configs). 4. `tofu state list` (identify unused resources). Tradeoffs: `-target` limits scope but ignores dependencies; `-refresh-only` doesn't show create/destroy actions.

T19 — Hard: State locking prevents concurrent modifications. If a lock isn't released (crash), the backend (e.g., DynamoDB) holds it. Manually break the lock via the backend console (e.g., delete the lock record in DynamoDB). Risk: Race conditions where two users modify state simultaneously, leading to corruption.

T20 — Hard: 1. Create new state bucket/DynamoDB table. 2. Run `tofu state pull` to get current state. 3. Update backend config in `terraform` block. 4. Run `tofu state push` to migrate state. 5. Verify by running `tofu plan` (should show no changes). 6. Delete old state file.

A1 — Easy: A playbook is a YAML file defining a sequence of tasks. A role is a reusable directory structure containing tasks, handlers, and variables. A task is a single unit of work within a playbook or role.

A2 — Easy: `ansible_facts` is a dictionary of system information gathered during the run. Access OS family via `{{ ansible_os_family }}`.

A3 — Medium: `command` runs a command without shell interpretation (no pipes/loops). `shell` runs a command through the system shell (allows pipes/loops). `raw` sends raw bytes without privilege escalation (no sudo). Use `command` for simple scripts, `shell` for complex logic, `raw` for unprivileged execution.

A4 — Medium: Idempotency means running the task multiple times yields the same result without side effects. Idempotent: `copy` a file (only copies if different). Not Idempotent: `shell` command that appends to a log file every run.

A5 — Medium:
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"
  tags: htop
- name: Install epel-release and htop
  package:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_os_family == "RedHat"
  tags: htop
```

A6 — Hard: Priority (High to Low): 1. Command line args (`-e`). 2. `extra_vars`. 3. `host_vars`/`group_vars`. 4. Role defaults. 5. `set_fact` (runtime). 6. Role vars. 7. Role defaults.

A7 — Hard: Use `serial: 3` in the playbook to limit concurrent execution. Define inventory groups (e.g., `webservers:1-3`, `webservers:4-50`). Use `wait_for` or `pause` in tasks to ensure synchronization if needed, though `serial` handles the flow control primarily.

A8 — Medium: `ansible-vault` encrypts files. To encrypt a single variable, use `ansible-vault encrypt_string` to generate a vault string, then paste it into the `vars` file using `!vault` syntax.

A9 — Easy: An inventory file lists hosts and groups. Static inventory is a text file (static list). Dynamic inventory uses a script/plugin to fetch hosts from a cloud provider or API.

A10 — Easy: `ansible all -m disk_usage -a "path=/"` or `ansible webservers -m shell -a "df -h"` (using `disk_usage` is deprecated, `shell` is standard).

A11 — Easy: A handler is a task that runs only if notified by another task (e.g., `notify: Restart nginx`). It differs from a regular task which runs immediately. Triggered by `notify` in a task.

A12 — Easy: `ansible.cfg` configures global settings. Common settings: `inventory`, `remote_user`, `host_key_checking`, `forks`.

A13 — Easy: `register` stores the output of a task in a variable. Use it in subsequent tasks via `{{ registered_var.stdout }}` or `{{ registered_var.rc }}`.

A14 — Medium: `include_tasks` is dynamic (evaluated at runtime, allowing conditionals). `import_tasks` is static (evaluated at parse time). Use `include` when you need to conditionally load tasks; `import` for static structure.

A15 — Medium: Ansible Galaxy is a repository for roles and collections. Use `requirements.yml` to list dependencies, then run `ansible-galaxy install -r requirements.yml`.

A16 — Medium: Connection plugins define how Ansible talks to hosts. `ssh` uses SSH protocol. `local` runs commands on the control node. `network_cli` (e.g., `nxos`, `eos`) uses CLI protocols like NETCONF/SSH for network devices.

A17 — Hard: `delegate_to` runs a task on a different host. `run_once` runs a task only once on the first host. Example: Gather facts on all hosts, then run a single task on the control node to aggregate data using `delegate_to: localhost` and `run_once: true`.

A18 — Hard: Strategies: 1. Increase `forks` (parallelism). 2. Enable `pipelining` (reduces SSH overhead). 3. Use `fact_caching` (avoid re-gathering facts). 4. Use `mitogen` (forks processes to reduce SSH overhead). Tradeoffs: `forks` increases memory; `mitogen` adds complexity; `fact_caching` requires backend.

A19 — Hard: `{{ }}` inserts variables. `{% %}` is for control flow (loops, conditionals). `{# #}` is for comments. Snippet:
```jinja
{% for server in backends %}
  upstream {{ server.name }} {
    server {{ server.ip }}:{{ server.port }};
    {% if server.health_check %}
      # Health check: {{ server.health_check }}
    {% endif %}
  }
{% endfor %}
```

A20 — Hard: 1. Set `serial: 5` (deploy 5 at a time). 2. Pre-task: Update LB config with new IP. 3. Deploy app. 4. Post-task: Health check with `uri` module. 5. If health check fails, `rescue` block triggers rollback (revert LB config, restore previous version). 6. Repeat until all nodes deployed.
