**AA1**
A monolith is a single, unified codebase deployed as one unit, while microservices decompose functionality into independent, deployable services communicating over a network.
Three concrete problems microservices introduce:
1.  **Distributed Complexity:** Debugging and tracing across services is harder than in a single process.
2.  **Network Latency:** Inter-service calls introduce network overhead and potential bottlenecks not present in local method calls.
3.  **Operational Overhead:** Requires managing multiple deployment pipelines, monitoring systems, and service discovery mechanisms.

**AA2**
Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST). Asynchronous communication involves sending a message without waiting for an immediate response (e.g., Message Queues).
*   **Synchronous Example:** REST API (HTTP).
*   **Asynchronous Example:** RabbitMQ or Apache Kafka.

**AA3**
An API Gateway is a specialized reverse proxy that handles cross-cutting concerns (auth, rate limiting, routing) and aggregates microservices. A reverse proxy is a generic server that forwards requests to backend servers.
An API Gateway cannot entirely replace a reverse proxy. While a gateway handles logic, a reverse proxy is often needed for low-level traffic management (SSL termination, load balancing) at the network edge before the gateway, or for specific protocol translation that the gateway doesn't support.

**AA4**
The Saga pattern manages distributed transactions by breaking them into local transactions, each with a compensating action to undo changes if a step fails.
*   **Choreography:** Services publish events; other services react. No central coordinator. Good for loosely coupled systems.
*   **Orchestration:** A central coordinator manages the flow and compensations. Good for complex workflows requiring strict ordering.

**AA5**
CQRS separates the model for writing data (Commands) from reading data (Queries). It is paired with Event Sourcing, which stores state as a sequence of events.
This combination solves the problem of **write/read performance mismatch**. Traditional CRUD models struggle when read requirements vastly exceed write requirements or when complex queries need denormalized data. CQRS allows optimizing the read model independently.

**AA6**
The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service after a threshold of failures.
*   **States:** Closed (normal), Open (fail fast), Half-Open (testing recovery).
*   **Difference from Retry:** Retry attempts to fix transient errors; Circuit Breaker stops attempts to prevent resource exhaustion.
*   **Usage Together:** Use retry for transient network glitches, but wrap it in a circuit breaker to stop retrying if the service is down.

**AA7**
1.  **Shared DB, Shared Schema:**
    *   *Cost:* Lowest.
    *   *Security:* Low (data leakage risk).
    *   *Complexity:* Low.
    *   *Noisy Neighbor:* High (one tenant's load affects others).
2.  **Shared DB, Separate Schema:**
    *   *Cost:* Medium.
    *   *Security:* Medium (schema isolation).
    *   *Complexity:* Medium (schema management).
    *   *Noisy Neighbor:* Medium.
3.  **Separate DB:**
    *   *Cost:* Highest.
    *   *Security:* High (logical isolation).
    *   *Complexity:* High (provisioning/management).
    *   *Noisy Neighbor:* None.

**AA8**
**Eventual Consistency:** Data converges over time; **Strong Consistency:** Data is identical across nodes immediately.
For an inventory system that must never oversell:
*   **Consistency Model:** Strong Consistency.
*   **Data Store:** Relational DB (PostgreSQL) or NewSQL (CockroachDB).
*   **Patterns:** Optimistic locking or distributed locks (Redis/Zookeeper) to ensure atomicity during the check-and-update operation.

**AA9**
A sidecar proxy is a lightweight process running alongside a service to handle networking. In Istio, Envoy acts as the sidecar.
*   **Data Plane:** Handles actual traffic flow (proxying packets).
*   **Control Plane:** Manages Envoy configuration (policies, routing).
*   **mTLS Problem:** Application-level TLS requires code changes. Sidecar mTLS handles encryption/decryption transparently between services without modifying the application code.

**AA10**
The Strangler Fig pattern incrementally replaces a monolith with microservices by routing specific functionality to new services.
**Strategy:**
1.  Deploy new .NET 8 services for specific features (e.g., "User Management").
2.  Update the legacy .NET Framework app to call the new service via API Gateway.
3.  Gradually move more features to new services.
4.  Once legacy features are exhausted, decommission the monolith.

**AA11**
The 12-Factor App methodology provides best practices for building modern cloud-native apps.
**6 Factors:**
1.  **Codebase:** One codebase per service.
2.  **Dependencies:** Explicitly declared and isolated.
3.  **Config:** Externalized (env vars), not in code.
4.  **Backing Services:** Treat as attached resources (DBs, queues).
5.  **Build, Release, Run:** Strict separation of concerns.
6.  **Processes:** Run as one process per instance.

**AA12**
*   **Coupling:** REST/gRPC is synchronous (tighter coupling); Kafka is asynchronous (looser).
*   **Scalability:** Kafka scales horizontally better for throughput; REST scales via load balancers.
*   **Debugging:** REST is easier to trace; Kafka requires log aggregation.
*   **Ordering:** Kafka guarantees ordering per partition; REST does not.
*   **Failure:** Kafka decouples failures; REST propagates them.
*   **Choice:** Use Kafka for event logging, analytics, and decoupled workflows. Use REST/gRPC for real-time user interactions and APIs.

**AA13**
A load balancer distributes incoming traffic across multiple servers.
*   **Layer 4 (Transport):** Operates on IP/Port (TCP/UDP). Fast, less context.
*   **Layer 7 (Application):** Operates on HTTP/Content. Can route based on URL/headers.
*   **Use Case:** Layer 7 is required for routing traffic to different backend services based on URL paths (e.g., `/api` to Service A, `/static` to CDN).

**AA14**
A message queue (RabbitMQ) is typically point-to-point or pub/sub with guaranteed delivery semantics. A log-based broker (Kafka) is a distributed log optimized for high throughput and replayability.
*   **Pick Queue:** When you need guaranteed delivery, acknowledgments, and complex routing (e.g., order processing).
*   **Pick Kafka:** When you need high throughput, event sourcing, and replayability (e.g., analytics pipelines).

**AA15**
A container packages code and dependencies into a lightweight, isolated unit using OS-level virtualization. A VM virtualizes the entire OS kernel.
**Difference:** Containers share the host kernel; VMs have a separate kernel.
**Popularity:** Containers are faster to start, smaller in size, and provide consistent environments across dev/prod, ideal for microservices.

**AA16**
*   **Stateless:** No server-side memory between requests (e.g., Web Server).
*   **Stateful:** Maintains session data (e.g., Database, Cache).
*   **Scaling:** Stateless services scale horizontally easily because any instance can handle any request. Stateful services require sticky sessions or complex state replication.

**AA17**
An ORM maps database tables to object classes.
*   **Examples:** Entity Framework (.NET), Hibernate (Java).
*   **Trade-offs:** ORMs reduce boilerplate and improve developer productivity but can lead to performance issues (N+1 problem) and less control over complex queries compared to raw SQL.

**AA18**
The Bulkhead pattern isolates resources (threads, connections) to prevent one failing service from exhausting resources for others.
**Implementation:** Allocate separate thread pools for different services. If the "Payment" service fails, it exhausts its thread pool, but the "Inventory" service continues using its own pool.

**AA19**
*   **OT:** Transforms operations to resolve conflicts (complex, hard to implement).
*   **CRDTs:** Data types that converge automatically (simpler, math-heavy).
*   **Offline Support:** CRDTs are superior for offline editing because they allow local changes to merge automatically without a server.
*   **Choice:** CRDTs for offline-first systems due to automatic conflict resolution and offline capability.

**AA20**
**Challenges:** Context propagation across languages requires standard headers (W3C Trace Context).
**Propagation:** Inject trace ID into headers (e.g., `traceparent`) on every request.
**Kafka:** Use headers in the message payload or broker metadata to carry the trace ID.
**Storage:** Use distributed tracing systems (Jaeger/Tempo) to store spans.
**Sampling:** Head-based (at start) is better for cost; Tail-based (at end) is better for debugging specific errors.

**OP1**
*   **Type 1 (Bare-metal):** Hypervisor runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V).
*   **Type 2 (Hosted):** Hypervisor runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2**
*   **SAN (Storage Area Network):** Block-level storage (e.g., iSCSI, Fibre Channel). Used for databases requiring direct disk access.
*   **NAS (Network Attached Storage):** File-level storage (e.g., NFS, SMB). Used for file sharing and backups.

**OP3**
A 3-tier architecture uses Core (high speed), Distribution (routing), and Access (edge) layers.
**Leaf-Spine:** Preferred in modern DCs because it provides non-blocking bandwidth and equal latency between all servers. It solves the scalability bottleneck of 3-tier architectures where core switches become a bottleneck.

**OP4**
**Architecture:** 3+ nodes (odd number for quorum).
**Quorum:** Majority voting to prevent split-brain.
**Fencing:** STONITH (Shoot The Other Node In The Head) to physically isolate failed nodes.
**Storage:** Ceph (distributed) preferred over iSCSI/NFS for HA.
**Failure:** If a node fails, the cluster detects via heartbeat, fences the node, and remounts storage on remaining nodes.

**OP5**
VLAN trunking allows multiple VLANs over a single link. 802.1Q tags frames with a 4-byte VLAN ID.
**Linux Config:**
```bash
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip addr add 192.168.10.10/24 dev eth0.10
ip addr add 192.168.20.10/24 dev eth0.20
```

**OP6**
*   **RAID 1:** Mirror (50% cap).
*   **RAID 5:** Striping + 1 parity (N-1 cap).
*   **RAID 6:** Striping + 2 parity (N-2 cap).
*   **RAID 10:** Mirror + Stripe (50% cap, high perf).
*   **RAID Z2:** ZFS equivalent of RAID 6.
**Choice:** **RAID 10**. For a database, IOPS and write performance are critical. With 6 drives, RAID 10 offers 3TB usable with 4TB raw, providing the best balance of speed and fault tolerance for a DB.

**OP7**
**Architecture:**
*   **Recursive Resolvers:** Forward queries to root servers.
*   **Authoritative Servers:** Host AD and DMZ zones.
*   **Split-Horizon:** Internal clients query internal DNS; external clients query public DNS.
*   **DNSSEC:** Signs external zones to prevent spoofing.
*   **Laptop Move:** When on VPN, the laptop uses conditional forwarding to internal DNS. When on office, it uses local DNS.

**OP8**
**Chain:** Root CA (offline) -> Subordinate CA (online) -> End-Entity Cert.
**Internal PKI:** Root CA signs Subordinate CA certs. Subordinate CA issues server/user certs.
**CRL vs OCSP:** CRL is a list of revoked certs (periodic check); OCSP is real-time status check.
**Compromise:** Compromised Subordinate CA affects only issued certs; Compromised Root CA invalidates the entire trust chain.

**OP9**
*   **MPLS:** High cost, reliable, low latency.
*   **IPsec:** Low cost, internet dependent, variable latency.
*   **SD-WAN:** Low cost, dynamic path selection, good for VoIP.
*   **WireGuard:** Low latency, high security, mesh complexity.
**Recommendation:** **SD-WAN**. It balances cost and reliability, with dynamic path selection ensuring VoIP quality even if the internet link degrades.

**OP10**
iDRAC/iLO/IPMI are out-of-band management interfaces allowing remote server control (power, console) independent of the OS.
**Importance:** Critical for troubleshooting OS failures or hardware issues remotely.
**Risk:** Exposing IPMI to the internet allows attackers to gain root access to the hardware, potentially compromising the entire server.

**OP11**
*   **LVM:** Logical Volume Manager (ext4/xfs).
*   **LVM-Thin:** Thin provisioning (allocate space on demand).
*   **ZFS:** Filesystem + Volume Manager (copy-on-write, checksums).
**Snapshots:** LVM (copy-on-write or linked), LVM-Thin (instant), ZFS (instant, consistent).
**Use:** LVM for general Linux; ZFS for data integrity/backup; LVM-Thin for VMs needing flexible storage.

**OP12**
**Strategy:** Use a 3-site setup (2 active, 1 DR) or a single site with offsite replication.
**Ceph CRUSH:** Configure rules to place monitors and OSDs across sites.
**Latency:** Ceph requires low latency (<10ms) between sites for quorum.
**Split-Brain:** 2-site Ceph is risky because if one site loses quorum, the cluster may stop. A tiebreaker (3rd site) is required to prevent data loss.

**OP13**
DHCP assigns IP addresses. **DORA:** Discover, Offer, Request, Acknowledge.
**Unavailable Server:** Client uses APIPA (169.254.x.x) or retains lease until expiry.
**Lease Expiry:** Client attempts to renew. If server is down, client loses connectivity and must reconfigure or reboot.

**OP14**
*   **Unmanaged:** Plug-and-play, no configuration.
*   **Managed:** Configurable (VLANs, QoS, Port Security).
**Enterprise Features:** VLANs for segmentation, QoS for traffic prioritization, Port Security to prevent unauthorized access.

**OP15**
NTP synchronizes system clocks.
**Importance:** Critical for logging correlation, Kerberos authentication, and database replication.
**Drift Issues:** Clock drift causes authentication failures (Kerberos), log mismatch, and replication conflicts.

**OP16**
*   **Physical:** Bare metal hardware.
*   **VM:** OS virtualized on hardware.
*   **Container:** App virtualized on OS.
**Bare Metal:** Use for high-performance computing (HPC), legacy hardware, or workloads requiring direct hardware access (e.g., specific GPU passthrough).

**OP17**
*   **UPS:** Battery backup for short-term power loss (minutes).
*   **Generator:** Long-term power (hours/days).
*   **ATS:** Switches power source from Utility to Generator automatically.
**Need Both:** UPS bridges the gap between outage and generator startup.

**OP18**
*   **Active-Passive:** One active, one standby.
*   **Active-Active:** Both handle load.
**PostgreSQL HA:**
1.  **Pacemaker/Corosync:** Manages cluster state.
2.  **STONITH:** Fences the failed node (e.g., power off) to prevent split-brain.
3.  **Virtual IP:** Floats to the active node.
4.  **Failover:** If primary fails, Pacemaker promotes secondary and moves VIP.

**OP19**
**3-2-1 Rule:** 3 copies, 2 media types, 1 offsite.
**RPO/RTO:** Recovery Point Objective (data loss limit), Recovery Time Objective (downtime limit).
**Types:** Full (complete), Incremental (changes since last), Differential (changes since last full).
**Ransomware:** Immutable backups (WORM) prevent deletion/modification.
**Backup vs DR:** Backup is data protection; DR is business continuity (restoring operations).

**OP20**
**802.1X:**
*   **Supplicant:** Client device.
*   **Authenticator:** Network switch.
*   **Auth Server:** RADIUS server.
**EAP:** EAP-TLS (cert-based), PEAP (username/password).
**Failure:** Device is blocked from network access.
**MAB:** MAC Authentication Bypass allows devices without 802.1X (printers, IoT) to authenticate via MAC address.
