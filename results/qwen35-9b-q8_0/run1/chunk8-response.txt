CL1 — IaaS (Infrastructure as a Service) provides virtualized computing resources (VMs, storage, networks) where the customer manages the OS and applications. Example: AWS EC2. PaaS (Platform as a Service) provides a managed runtime environment for applications, handling OS and middleware. Example: AWS Elastic Beanstalk. SaaS (Software as a Service) delivers fully managed software applications over the internet. Example: Microsoft 365.

CL2 — The Shared Responsibility Model defines security boundaries. For IaaS VMs, the provider secures the physical hardware and hypervisor; the customer secures the OS, data, and network config. For managed Kubernetes, the provider secures the control plane and nodes; the customer secures the workloads, policies, and data. For SaaS like M365, the provider secures the application and infrastructure; the customer secures user identity, data, and access policies.

CL3 — A VPC is a logical isolation boundary. A subnet is a range of IP addresses within a VPC. A Security Group (SG) is a stateful firewall at the instance level. A Network ACL (NACL) is a stateless firewall at the subnet level. Layering: VPC contains Subnets, which contain NACLs, which filter traffic before reaching the SG on the instance. Stateful filtering (SG) remembers connection state (return traffic allowed automatically). Stateless filtering (NACL) evaluates every packet independently.

CL4 — A Landing Zone is a pre-configured, secure foundation for cloud accounts. Organizational Units (OUs) group accounts for policy application. Guardrails enforce compliance (e.g., no public S3 buckets). Shared Networking uses a Transit Gateway (AWS) or Hub-and-Spoke (Azure) to connect accounts securely. Centralized logging aggregates logs to a central account. Single-account approaches lack isolation, making scaling, compliance, and security management difficult and risky.

CL5 — Infrastructure as Code (IaC) manages infrastructure via code. Terraform/OpenTofu is declarative and multi-cloud. Pulumi uses programming languages (Python/TS) for IaC. CloudFormation/Bicep are provider-specific (AWS/Azure). Crossplane uses Kubernetes CRDs to manage cloud resources. Choose Terraform for multi-cloud infra, Pulumi for developer-friendly code, CloudFormation for deep AWS integration, and Crossplane for K8s-native cloud management.

CL6 — HPA scales pods based on metrics (CPU/Mem). VPA scales pod resource requests. Cluster Autoscaler adds/removes nodes. KEDA scales based on external events (e.g., Kafka messages). Use KEDA over HPA when scaling should be triggered by external events (queue depth, API calls) rather than internal resource utilization.

CL7 — DR Strategy depends on RPO (data loss) and RTO (downtime). Active-Active offers high availability but high cost; Active-Passive is cheaper. Database replication: Sync (low RPO, high latency) vs Async (higher RPO, lower latency). DNS failover routes traffic to the healthy region. Pilot Light (min infra), Warm Standby (scaled-down active infra), Multi-site Active-Active (full infra in both regions). Cost increases with higher availability and replication frequency.

CL8 — GitOps uses Git as the single source of truth for infrastructure. ArgoCD and FluxCD are GitOps controllers that sync clusters to Git. Secrets are handled via Sealed Secrets (encrypted in Git) or External Secrets Operator (syncs from Vault). Manual changes cause drift; GitOps tools detect drift and auto-remediate or alert to revert changes to the Git state.

CL9 — Use a StatefulSet for stable network identities and storage. Use Local Persistent Volumes (LocalPath) for low-latency local storage. Use a Headless Service for DNS-based stable IPs. Use Init Containers to prepare the filesystem. Mount ConfigMaps as volumes for config files. Use Pod Disruption Budgets (PDB) to ensure availability during updates.

CL10 — A Service Account is a K8s identity. Workload Identity binds a K8s SA to a cloud IAM identity. IRSA (IAM Roles for Service Accounts) is AWS-specific implementation. Mounting cloud credentials in a pod is bad practice due to rotation risks and exposure. Workload Identity federation allows the pod to assume the cloud role dynamically without storing secrets.

CL11 — Object storage (S3/Blob) stores files as objects with high durability (11 9s). Block storage (EBS/Disk) is low-latency, attached to VMs (99.99%). File storage (EFS/Files) allows shared mount points. Use Object for backups/media, Block for OS/App data, File for shared app data. Durability: Object > Block > File.

CL12 — Zero Trust verifies every request. Network Policies deny all by default. Service Mesh (Istio) enforces mTLS. Pod Identity (SPIFFE) authenticates workloads. Admission Controllers (OPA) validate config. Image signing ensures integrity. Runtime security (Falco) detects anomalies. This differs from perimeter security by assuming breach and verifying identity/device continuously.

CL13 — A CDN caches content at edge locations closer to users. Services: AWS CloudFront, Cloudflare. Use CDN for static assets, high traffic, and global distribution. Use origin server for dynamic content or low-traffic scenarios where latency is critical.

CL14 — Regions are geographic areas with multiple Availability Zones (AZs). AZs are isolated data centers within a region. Deploy across AZs for fault tolerance. Zonal resources are in one AZ; Regional resources span AZs.

CL15 — A managed database (RDS/Cloud SQL) handles patching, backups, scaling, and HA. Running on a VM requires manual management of all these tasks, increasing operational overhead and risk.

CL16 — IAM Users are individuals. Groups aggregate users. Roles are permissions attached to users/groups. Policies define permissions. Principle of Least Privilege grants only necessary access. Apply by reviewing policies regularly and using just-in-time access.

CL17 — Serverless runs code without managing servers. AWS Lambda, Azure Functions, GCP Functions. Cold starts are latency spikes on first invocation. Poor fit for long-running processes or latency-sensitive real-time systems.

CL18 — Ingress resource is a K8s API object. Gateway API is the newer standard. Cloud LB annotations configure K8s to use cloud LBs. Service Mesh ingress handles traffic via sidecars. TLS termination: Ingress/Gateway terminates at the edge. Use Gateway API for standardization and future-proofing over traditional Ingress.

CL19 — Cost optimization: Reserved Instances (1-3yr commitment), Savings Plans (flexible), Spot Instances (cheaper, interruptible). Right-sizing based on utilization. Storage tiering moves infrequent data to cheaper storage. FinOps practices include tagging, budgeting, and showback/chargeback models. Tools: AWS Cost Explorer, CloudHealth.

CL20 — Multi-cloud strategy uses Kubernetes for a common runtime and Terraform for IaC portability. Networking uses Direct Connect/ExpressRoute. Identity uses federation (SAML/OIDC). Trade-offs: Higher cost and complexity vs. lock-in avoidance. Justified for compliance, DR, or specific vendor features; unnecessary if a single cloud meets needs.

OT1 — The Purdue Model (ISA-95) defines industrial automation hierarchy. Level 0: Field Devices (Sensors/Actuators). Level 1: Basic Process Control (PLCs). Level 2: Supervisory Control (SCADA). Level 3: Enterprise Control (MES). Level 4: Business/ERP. Level 5: IT/Corporate.

OT2 — IT networks prioritize data availability and confidentiality. OT networks prioritize safety and availability. Standard IT patching (reboots, remote changes) can disrupt OT processes or cause safety hazards, so changes require strict change management and testing.

OT3 — An IDMZ (Industrial DMZ) isolates IT and OT networks. Allowed traffic: Level 2 (OT) to Level 3 (IT) for monitoring. Direct connectivity from Level 4 (IT) to Level 1 (Control) is dangerous because it bypasses security layers, risking direct access to critical control systems.

OT4 — 1. Modbus TCP: L1 (Device communication). 2. OPC UA: L2/L3 (Secure data exchange). 3. EtherNet/IP: L1 (Industrial Ethernet). 4. PROFINET: L1 (Real-time control). 5. MQTT: L2/L3 (Lightweight messaging).

OT5 — A data diode allows one-way traffic (e.g., OT to IT only). A firewall allows bidirectional traffic. Use a data diode when exporting critical OT data to IT systems to prevent malware from moving back into the OT network. Limitation: No return traffic control.

OT6 — Data Flow: PLC -> Historian (L1) -> Edge Gateway (L2) -> MQTT Broker -> Cloud. Security boundaries: The Edge Gateway acts as the firewall between OT and IT. The Historian buffers data before it leaves the OT network.

OT7 — IEC 62443 defines Zones (logical/physical boundaries) and Conduits (connections). Zone: A collection of assets with similar security requirements. Conduit: A connection between zones. Model: Zone 1 (PLCs), Zone 2 (SCADA), Zone 3 (Engineering), Zone 4 (IT). Conduits connect these zones with firewalls.

OT8 — Segmentation: VLANs per production line. Firewalls between VLANs and the corporate network. Switches: Managed, stackable for redundancy. Transition: Parallel run new network alongside old, migrate line by line to avoid production stoppage.

OT9 — SIS (Safety Instrumented Systems) protects against catastrophic failure. BPCS (Basic Process Control) manages normal operations. IEC 61511 governs SIS. SIS must be isolated to prevent IT malware from disabling safety functions. Ransomware on SIS could cause physical damage or loss of life.

OT10 — PLC: Discrete control (on/off). DCS: Continuous process control (complex). SCADA: Monitoring and data collection. They coexist: PLCs control machinery, SCADA monitors them, DCS manages large continuous processes.

OT11 — Remote Access: Use a Jump Host (Bastion) with MFA. Session recording logs all activity. Vendor access is time-limited and audited. RDP directly to HMI is unacceptable as it bypasses security controls and exposes critical systems.

OT12 — Detection: Network IDS monitors for anomalies. Inventory: Know all assets. Response: Isolate compromised segments. Operator role: Manual override to ensure safety during isolation. Safe operations: Maintain critical processes while containing the threat.

OT13 — HMI: Operator interface for monitoring and control. Engineering Workstation: Used for configuration and programming. HMI is for operators; Engineering Workstations are for engineers.

OT14 — Historian: Time-series database for process data. Plant Historian (L3) stores operational data. Enterprise Historian (L4) aggregates data for business analysis.

OT15 — Ladder Logic: Programming language resembling relay logic. Executed by PLCs. Dominant due to familiarity, reliability, and deterministic behavior in industrial environments.

OT16 — RTU: Remote Terminal Unit for remote sites (pipelines). PLC: Local control. RTUs are used in harsh, remote environments where physical access is difficult.

OT17 — Analog (4-20mA, 0-10V) represents continuous values. Digital (On/Off) represents states. 4-20mA is preferred because 0mA indicates a broken wire (live zero), whereas 0-20mA cannot distinguish between 0 signal and broken wire.

OT18 — Asset Inventory: List of all OT devices. Foundation for security. Passive monitoring (sniffing) is safe. Active scanning (ping/scan) can disrupt devices and is dangerous in OT.

OT19 — MITRE ATT&CK for ICS maps adversary tactics to OT. Tactics: Reconnaissance (T1498), Execution (T1499), Persistence (T1496). Differs from Enterprise by focusing on PLC/SCADA. Use to identify gaps in OT defenses against known threats.

OT20 — Converged SOC: Collect logs via Syslog/NetFlow without impacting operations. SIEM integrates IT and OT logs. OT rules focus on protocol anomalies. Staffing: Hybrid IT/OT analysts. False positives: Tune rules based on OT behavior. Firmware Alert: Verify integrity, quarantine device, patch offline.
