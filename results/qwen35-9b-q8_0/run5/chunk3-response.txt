T1 — Easy: `tofu plan` calculates the changes required to reach the desired state defined in the configuration without making changes. `tofu apply` executes those changes to update the infrastructure to match the desired state.

T2 — Easy: State is a JSON file that maps real-world resources to the configuration code. Remote state is important for collaboration (multiple users), security (encryption at rest), and availability (state persistence across machines).

T3 — Medium: `count` creates a list of resources indexed by integers (0, 1, 2...). `for_each` creates resources from a map or set, indexed by the key. `for_each` is preferred when resources need unique names or when the number of resources is dynamic and not sequential.

T4 — Medium: OpenTofu detects drift by comparing the current state against the configuration during `plan`. It marks the resource as "drifted" and suggests a plan to reconcile the state. It does not automatically revert changes; it requires user confirmation to apply the fix.

T5 — Medium:
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-12345678"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

T6 — Hard: `terraform_remote_state` reads outputs from another state file, creating a dependency. Output values are read directly from the current state. The recommended alternative is using a shared backend (e.g., S3 with DynamoDB locking) or a dedicated API/Service (like Consul or Vault) to avoid circular dependencies and state coupling.

T7 — Hard: The `null_resource` output is empty because the provisioner runs asynchronously or the output is not captured correctly before the resource is destroyed. Fix: Use `output` with `value = local.kubeconfig` where `local` is defined after the provisioner, or use `local-exec` to write the config to a file and read that file in the output.

T8 — Medium: `tofu import` attaches an existing resource to the state. Limitations: Requires the resource ID to be known and the state to match the configuration. The `import` block (1.5+) allows defining import logic within the code, making it reusable and declarative rather than a CLI-only command.

T9 — Easy: A variable is an input value passed to a module. Input variables are defined in `variable.tf` and passed in. Output variables are defined in `output.tf` and returned from a module.

T10 — Easy: A provider is a plugin that interacts with a cloud API (e.g., AWS, Azure). Running `tofu plan` without `tofu init` fails because providers are not downloaded or initialized.

T11 — Easy: `.terraform.lock.hcl` records the exact versions of providers used. It should be committed to prevent "dependency hell" where different environments use incompatible provider versions.

T12 — Easy: `tofu destroy` removes all resources managed by the configuration. Target a single resource using `tofu destroy -target=aws_instance.my_vm`.

T13 — Easy: A data source fetches existing data (e.g., `aws_ami`). Use it when you need to reference an existing resource (like an AMI ID) rather than creating a new one.

T14 — Medium: `locals` are computed values within a module. `variables` are inputs. Use `locals` for derived values (e.g., concatenating strings, calculating IDs) to avoid passing complex logic through inputs.

T15 — Medium: Lifecycle blocks control resource behavior. `create_before_destroy` ensures the new resource exists before deleting the old (needed for load balancers). `prevent_destroy` stops accidental deletion (needed for DBs). `ignore_changes` prevents specific attributes from being updated (needed for immutable tags).

T16 — Medium: `moved` block tells OpenTofu that a resource has been renamed or moved to a new address. It prevents state loss during refactoring without needing to recreate the resource.

T17 — Hard: The dependency graph orders execution. Implicit dependencies are inferred from references (e.g., `aws_instance` referencing `aws_security_group`). Explicit dependencies use `depends_on`. `depends_on` reduces parallelism by forcing sequential execution, so use it sparingly to avoid bottlenecks.

T18 — Hard: 1. `tofu plan -refresh-only` to check drift without full plan. 2. `tofu plan -target` to plan specific resources. 3. Modularize code to reduce state size. 4. Use `tofu state list` to identify unused resources. Tradeoffs: Targeting reduces scope but requires manual selection; modularization requires refactoring.

T19 — Hard: State locking prevents concurrent modifications. If a lock isn't released (crash), the state is locked indefinitely. Manually break the lock via the backend (e.g., `aws dynamodb delete_item` for DynamoDB). Risk: Race conditions and state corruption if two users apply simultaneously.

T20 — Hard: 1. Create new backend config in `backend` block. 2. Run `tofu state push` to migrate state to new backend. 3. Run `tofu state pull` to verify. 4. Run `tofu init` with new backend. 5. Run `tofu plan` to ensure state matches. 6. Delete old backend config.

A1 — Easy: A playbook is a YAML file defining tasks. A role is a reusable directory structure containing tasks, handlers, and variables. A task is a single unit of work within a playbook or role.

A2 — Easy: `ansible_facts` are variables populated by Ansible during the run (e.g., OS info). Access via `{{ ansible_distribution }}` or `{{ ansible_facts['distribution'] }}`.

A3 — Medium: `command` runs a shell command without shell features. `shell` allows shell features (pipes, loops). `raw` sends raw bytes without interpretation. Use `command` for simple scripts, `shell` for complex logic, `raw` for binary data.

A4 — Medium: Idempotency means running the task multiple times yields the same result. Idempotent: `copy` with `src` and `dest` (only copies if different). Not Idempotent: `command: echo "hello"` (runs every time).

A5 — Medium:
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"
- name: Install htop on RHEL
  package:
    name: htop
    state: present
  when: ansible_os_family == "RedHat"
```

A6 — Hard: Priority (High to Low): 1. Command line args. 2. `extra_vars`. 3. `host_vars`/`group_vars`. 4. Role defaults. 5. Role vars. 6. `set_fact` (runtime).

A7 — Hard: Use `serial: 3` in the playbook to limit concurrent hosts. Group the first 3 nodes in a specific group or use `when` logic with `wait_for`. Example: `serial: 3` ensures only 3 run at a time, naturally handling the first 3 before the rest.

A8 — Medium: `ansible-vault` encrypts files. To encrypt a single variable: `ansible-vault encrypt_string 'secret' --name 'my_secret' --vault-password-file=pass`. Or use `ansible-vault encrypt_string` to generate a string and paste it into the vars file.

A9 — Easy: Inventory lists hosts and groups. Static inventory is a file (YAML/INI). Dynamic inventory fetches data from an API (e.g., cloud provider) at runtime.

A10 — Easy: `ansible all -m disk_usage -a "path=/"` or `ansible webservers -m shell -a "df -h"`.

A11 — Easy: A handler is a task that runs only if notified by another task (e.g., on file change). Triggered using `notify: handler_name` in a task.

A12 — Easy: `ansible.cfg` configures global settings. Common settings: `inventory`, `host_key_checking`, `forks`, `timeout`.

A13 — Easy: `register` stores the output of a task in a variable. Use `{{ result.stdout }}` or `{{ result.rc }}` in subsequent tasks.

A14 — Medium: `include_tasks` is dynamic (evaluated at runtime, supports conditionals). `import_tasks` is static (evaluated at parse time). Use `include` for dynamic logic; `import` for static structure.

A15 — Medium: Ansible Galaxy is a repository for roles/collections. Use `requirements.yml` to list dependencies, then run `ansible-galaxy install -r requirements.yml`.

A16 — Medium: Connection plugins define how Ansible talks to hosts. `ssh` is default for remote. `local` runs on control node. `network_cli` for network devices (Cisco). Use `ssh` for servers, `local` for control node tasks, `network_cli` for routers/switches.

A17 — Hard: `delegate_to` runs a task on a different host. `run_once` runs a task only once across all hosts. Example: Gather facts on all, then run a single task on `localhost` to process data.

A18 — Hard: 1. Increase `forks` (parallelism). 2. Enable `pipelining` (reduces SSH overhead). 3. Use `fact_caching` (Redis) to avoid gathering facts repeatedly. 4. Use `mitogen` for deep parallelism. Tradeoffs: `forks` increases memory; `mitogen` adds complexity.

A19 — Hard: `{{ }}` inserts variables. `{% %}` is for control flow (loops, if). `{# #}` is for comments. Snippet:
```jinja
{% for server in backends %}
  upstream {{ server.name }} {
    server {{ server.ip }}:{{ server.port }};
    # Health check: {{ server.health_check }}
  }
{% endfor %}
```

A20 — Hard: 1. `serial: 5` for batches. 2. Pre-task: Update LB config. 3. Deploy app. 4. `wait_for` with `uri` module for health check. 5. Post-task: Update LB. 6. `block/rescue` to rollback LB config if health check fails.
