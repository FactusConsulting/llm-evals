CL1 — IaaS (Infrastructure as a Service) provides virtualized computing resources (VMs, storage, networks) where you manage the OS and applications (e.g., AWS EC2). PaaS (Platform as a Service) provides a managed runtime environment for developing and deploying apps without managing the underlying OS (e.g., AWS Elastic Beanstalk). SaaS (Software as a Service) delivers fully managed software applications over the internet (e.g., Salesforce).

CL2 — The Shared Responsibility Model divides security duties. For IaaS VMs, the provider secures the physical hardware and hypervisor; you secure the OS, data, and network config. For managed Kubernetes, the provider manages the control plane and node infrastructure; you manage the cluster configuration, policies, and workloads. For SaaS like M365, the provider manages the entire application stack and security; you manage user access and data classification.

CL3 — A VPC is a virtual network isolated from the public cloud. Subnets are subdivisions of the VPC (public/private). Security Groups are stateful virtual firewalls attached to instances. NACLs are stateless firewalls at the subnet level. Layering: VPC contains Subnets; Subnets have NACLs; Instances have Security Groups. Stateful means return traffic is automatically allowed (Security Groups); Stateless means rules must be explicitly defined for both directions (NACLs).

CL4 — A landing zone is a pre-configured, multi-account AWS/Azure structure. Organizational Units (OUs) group accounts for policy application. Guardrails enforce compliance (e.g., no public S3 buckets). Shared networking uses Transit Gateway (AWS) or Hub-and-Spoke (Azure) to connect accounts securely. Centralized logging aggregates logs to a central account. Single-account approaches are problematic due to lack of isolation, difficult scaling, and inability to enforce granular policies.

CL5 — IaC manages infrastructure via code. Terraform/OpenTofu uses declarative HCL; best for multi-cloud and complex state management. Pulumi uses general-purpose languages (TypeScript, Python); best for teams with strong coding backgrounds. CloudFormation/Bicep are native AWS/Azure tools; best for deep native integration. Crossplane manages infrastructure as Kubernetes resources; best for cloud-agnostic control planes.

CL6 — HPA scales pods based on CPU/memory metrics. VPA scales individual pod resources (CPU/RAM) automatically. Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external events (e.g., Kafka messages). Use KEDA over HPA when scaling should be driven by external triggers (queue depth, API calls) rather than just resource utilization.

CL7 — DR strategy depends on RPO (data loss) and RTO (downtime). Active-active replicates workloads in both regions (high cost, high availability). Active-passive keeps one active, one standby (lower cost). Database replication: Sync for zero RPO, Async for lower latency. DNS failover routes traffic to the healthy region. Pilot light keeps config/DB in standby (low cost, high RTO). Warm standby runs minimal services (medium cost). Multi-site active-active runs full workloads (high cost, low RTO).

CL8 — GitOps uses Git as the single source of truth for infrastructure and apps. ArgoCD and FluxCD sync cluster state to Git. Secrets are managed via Sealed Secrets (encrypted in Git) or External Secrets Operator (fetches from Vault). Manual changes cause drift; GitOps tools detect drift and auto-remediate by reverting to Git state.

CL9 — Use a StatefulSet for ordered deployment and stable network identities. Use Local Persistent Volumes (PV) with a LocalStorageClass for low-latency local storage. Use a Headless Service for DNS-based sticky sessions. Use Init Containers to bake config files into the filesystem before the main app starts. Use ConfigMaps as volume mounts for config. Use Pod Disruption Budgets (PDB) to ensure availability during maintenance.

CL10 — Service accounts are Kubernetes identities for pods. Workload Identity (GCP/Azure) or IRSA (AWS) maps K8s identities to cloud IAM roles. Mounting cloud credentials in pods is bad practice because it exposes secrets and requires rotation. Workload Identity federation allows pods to assume cloud roles dynamically without storing keys.

CL11 — Object storage (S3/Blob) is for unstructured data, high durability (99.999999999%), scalable. Block storage (EBS/Managed Disk) is for OS/DBs, low latency, attached to VMs. File storage (EFS/Azure Files) is for shared file systems, NFS/SMB protocols. Use Object for backups/media, Block for databases, File for shared app data.

CL12 — Zero-trust assumes no implicit trust. Network Policies restrict pod-to-pod traffic. Service mesh (Istio/Linkerd) enforces mTLS. Pod Identity authenticates workloads. Admission controllers (OPA/Kyverno) enforce policies before deployment. Image signing verifies container integrity. Runtime security (Falco) detects anomalies. Unlike perimeter security, zero-trust verifies every request regardless of origin.

CL13 — A CDN caches content at edge locations closer to users. It works by routing requests to the nearest cache. Services: AWS CloudFront, Azure CDN. Use CDN for static assets (images, JS) to reduce latency and DDoS protection. Use origin directly for dynamic content requiring real-time processing.

CL14 — Regions are geographic areas with multiple Availability Zones (AZs). AZs are isolated data centers within a region. Deploy across AZs for high availability (if one AZ fails, others survive). Zonal resources are in one AZ; Regional resources span AZs.

CL15 — Managed databases (RDS/Cloud SQL) handle patching, backups, scaling, and failover. You manage the schema and data. On VMs, you handle OS updates, database software installation, backups, and monitoring.

CL16 — IAM Users are individuals. Groups organize users. Roles are permissions attached to users or resources. Policies define permissions. Principle of Least Privilege grants only necessary permissions. Apply it by creating specific roles for services/users and auditing regularly.

CL17 — Serverless runs code without managing servers (AWS Lambda, Azure Functions, GCP Functions). Cold starts occur when a function is invoked for the first time or after inactivity, causing latency. Poor fit for long-running processes or strict latency requirements.

CL18 — Ingress resource routes traffic to services. Gateway API is the newer standard for more flexibility. Cloud load balancer annotations configure LB behavior. Service mesh ingress handles mTLS and observability. TLS termination can happen at the LB, Ingress, or Service Mesh. Use Gateway API for multi-protocol support and advanced routing.

CL19 — Cost optimization: Use Savings Plans/Reserved Instances for steady workloads. Spot/Preemptible for fault-tolerant batch jobs. Right-size instances based on usage. Tier storage (S3 Intelligent-Tiering) for infrequent access. Use idle resource detection (AWS Compute Optimizer). Implement FinOps with showback/chargeback to make teams accountable. Use tools like AWS Cost Explorer or Azure Cost Management.

CL20 — Multi-cloud strategy uses Kubernetes as a common runtime to abstract infrastructure. Terraform manages resources across clouds. Networking uses Direct Connect/ExpressRoute + Transit Gateway peering. Identity uses federation (OIDC/SAML). Trade-offs: Higher complexity and cost vs. vendor lock-in avoidance. Justified for compliance or specific cloud features; unnecessary if one cloud meets all needs.

OT1 — The Purdue Model (ISA-95) defines IT/OT hierarchy. Level 0: Field Devices (sensors/actuators). Level 1: Basic Process Control (PLCs/DCS). Level 2: Supervisory Control (SCADA/HMI). Level 3: Enterprise Control (MES). Level 4: Business Planning (ERP). Level 5: Enterprise IT.

OT2 — IT networks prioritize data availability and confidentiality. OT networks prioritize safety and availability. Standard IT patching can disrupt OT processes or cause safety hazards. OT systems often run legacy OS that cannot be patched.

OT3 — An IDMZ (Industrial DMZ) separates IT and OT networks. It allows controlled traffic (e.g., engineering workstations to SCADA servers) but blocks direct IT-to-OT access. Direct connectivity from Level 4 to Level 1 is dangerous because it bypasses security layers, risking direct control system compromise.

OT4 — 1. Modbus TCP: Level 1/2, serial over Ethernet. 2. OPC UA: Level 2/3, secure data exchange. 3. EtherNet/IP: Level 1/2, industrial Ethernet. 4. PROFINET: Level 1/2, real-time control. 5. MQTT: Level 2/3, lightweight messaging for IoT.

OT5 — A data diode allows traffic in only one direction (physical or logical). A firewall allows bidirectional traffic with rules. Use a data diode when preventing data exfiltration is critical (e.g., OT to IT). Limitation: Cannot allow return traffic.

OT6 — Data flow: PLCs send data to Historian (Level 1/2). Historian pushes to Edge Gateway (Level 2). Gateway converts to MQTT and sends to Cloud Broker. Cloud Ingestion processes data. Security boundaries: Firewall between OT and IT, DMZ for gateway, encryption in transit.

OT7 — Zones are logical network segments (e.g., PLCs, HMIs). Conduits are controlled connections between zones. Model: Zone 1 (Corporate), Zone 2 (Engineering), Zone 3 (SCADA), Zone 4 (PLCs), Zone 5 (SIS). Conduits: Engineering to SCADA (read-only), SCADA to PLCs (control).

OT8 — VLANs segment traffic (e.g., VLAN 10 for PLCs, VLAN 20 for HMIs). Firewalls between VLANs enforce policies. Switch architecture uses redundant rings for redundancy. Remote access via jump hosts with MFA. Transition: Use parallel networks or phased migration with strict change management.

OT9 — SIS (Safety Instrumented Systems) handles emergency shutdowns. BPCS handles normal operation. IEC 61511 defines SIS safety integrity. SIS must be isolated to prevent IT malware from disabling safety functions. Ransomware on SIS could cause physical damage or loss of life.

OT10 — PLC: Single controller for specific tasks. DCS: Distributed control for large plants. SCADA: Supervisory monitoring over wide areas. They can coexist (e.g., PLCs control machines, SCADA monitors them).

OT11 — Remote access via Jump Hosts (bastion hosts) with MFA. Session recording logs all activity. Vendor access is time-limited and audited. RDP directly to HMI is unacceptable because it bypasses security layers and exposes control systems.

OT12 — Detection: Deploy IDS/IPS and monitor for anomalies. Inventory: Map all assets. Response: Isolate affected network segments. Coordinate with control room to maintain safe operations. Operator role: Monitor physical processes, follow emergency procedures, verify isolation.

OT13 — HMI is the interface for operators to monitor/control processes. It displays real-time data and allows manual overrides. Engineering workstations are for configuration and maintenance, not real-time control.

OT14 — Historian stores time-series process data. Important for trend analysis and compliance. Plant historian (Level 3) stores operational data. Enterprise historian (Level 4) aggregates data for business analysis.

OT15 — Ladder logic is a programming language resembling electrical relay logic. Executed by PLCs. Dominant due to ease of understanding for electricians and reliability.

OT16 — RTU (Remote Terminal Unit) is for remote, harsh environments (e.g., pipelines). PLCs are for indoor, controlled environments. RTUs often have built-in comms (radio/cellular).

OT17 — Analog signals (4-20mA, 0-10V) represent continuous values. Digital signals represent discrete states. 4-20mA preferred because it allows loop power and distinguishes between 0mA (broken wire) and 4mA (0% value).

OT18 — Asset inventory lists all OT devices. Foundation for security. Passive monitoring (sniffing) is safe. Active scanning (port scanning) is dangerous as it can disrupt control loops.

OT19 — MITRE ATT&CK for ICS maps adversary tactics to OT environments. Tactics: Reconnaissance (e.g., scanning), Execution (e.g., remote code), Persistence (e.g., registry keys). Differs from enterprise by focusing on safety and control systems. Use to identify gaps in OT defenses.

OT20 — Converged SOC collects logs via agents or agents (e.g., Splunk OT). SIEM integrates logs. OT rules focus on safety events (e.g., unexpected shutdowns). Staffing requires OT engineers for triage. False positives are common due to process variability. Unauthorized firmware changes trigger immediate isolation and vendor verification.
