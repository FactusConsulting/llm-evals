K1 — A Deployment manages stateless applications and ensures a desired number of replicas are running, replacing old pods with new ones. A StatefulSet manages stateful applications requiring stable network identities (pod names), persistent storage, and ordered deployment/termination. Deployments are for web servers; StatefulSets are for databases or message queues.

K2 — A ClusterIP Service creates a virtual IP within the cluster. kube-proxy creates iptables rules (or IPVS rules) that match traffic destined for the Service IP and forward it to the backend pods based on the Service selector labels.

K3 — A PersistentVolume (PV) is a cluster-wide resource representing storage. A PersistentVolumeClaim (PVC) is a request for storage resources made by a user. A StorageClass defines how dynamic PVs are provisioned automatically. The PVC binds to a PV (static or dynamic) to mount storage to a pod.

K4 — 1. Check logs (`kubectl logs <pod>`). 2. Check events (`kubectl describe pod <pod>`). 3. Check resource limits (CPU/Memory) via `kubectl top pod`. 4. Check readiness/liveness probe configurations. 5. Verify the image is pulling correctly.

K5 — CoreDNS provides internal DNS resolution for services (e.g., `my-service.default.svc.cluster.local`). If CoreDNS pods are down, internal service discovery fails, pods cannot reach each other by name, and external traffic routing via DNS fails.

K6 — The scheduler filters nodes based on hard constraints (taints/tolerations, node selectors, resource availability). It then scores remaining nodes based on soft constraints (least requested resources, pod topology spread, affinity). Factors include: 1. Node affinity/anti-affinity. 2. Resource requests vs. capacity. 3. Pod topology spread constraints.

K7 — Yes, it will be scheduled because requests (256Mi) fit within available RAM (3.5GB free). If it uses 600Mi at runtime, it exceeds the limit (512Mi), triggering an OOMKilled event and restarting the pod.

K8 — External LB receives traffic -> Ingress Controller (NGINX) parses Ingress rules -> Routes to Service ClusterIP -> kube-proxy updates iptables/IPVS -> Traffic forwarded to Pod IP -> Pod receives request.

K9 — A NetworkPolicy restricts network traffic to/from pods. If no policy exists, all ingress/egress traffic is allowed by default. When a policy is applied, it acts as a deny-all default unless specific rules allow traffic.

K10 — RollingUpdate updates pods gradually (rolling restart), maintaining availability. Recreate kills all old pods before starting new ones, causing downtime. Choose Recreate for stateful apps or when zero downtime is not required.

K11 — A namespace isolates resources (names, objects) within a cluster. Default namespaces are `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

K12 — It shows detailed status, events, conditions, and resource usage. 3 pieces of info: 1. Events (reasons for state changes). 2. Conditions (Ready, ContainersReady). 3. Resource limits/requests.

K13 — A ConfigMap stores non-confidential configuration data as key-value pairs. Pods consume it via: 1. Environment variables. 2. Mounting as files in a volume.

K14 — ClusterIP: Internal cluster-only access. NodePort: Exposes service on a static port on each node's IP. LoadBalancer: Provisions an external cloud load balancer to expose the service externally.

K15 — A DaemonSet ensures a copy of a pod runs on all (or selected) nodes. Use it for system-level agents (logging, monitoring, network plugins) rather than user applications.

K16 — Taints repel pods; tolerations allow specific pods to ignore taints. Node affinity selects nodes based on labels. Use case: Taints for GPU nodes (only GPU pods allowed). Use case: Affinity for placing DB and App on same rack.

K17 — An Operator is a controller that encapsulates the logic to manage complex applications (CRDs). It differs from standard controllers by managing the lifecycle of the application itself (upgrades, backups). It solves the "how to manage" problem for complex stateful apps.

K18 — etcd uses Raft consensus for strong consistency. If quorum is lost (e.g., 2/3 nodes down), the cluster becomes unavailable. To recover from 2/3 loss, you must restore the remaining node from a backup and rejoin it to form a new quorum.

K19 — RBAC controls permissions. Role defines permissions in a namespace; ClusterRole defines cluster-wide. RoleBinding/ClusterRoleBinding links subjects (users/groups) to Roles.
Manifests:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: read-pods
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` defines how many dots must precede a name to treat it as a domain. Low `ndots` (e.g., 1) causes the resolver to query internal DNS for every short name, causing latency. Fix: Set `ndots: 5` in `dnsConfig` to prioritize external DNS for short names.

D1 — Rebase rewrites history to integrate changes linearly; Merge creates a merge commit preserving history. Avoid rebasing on public/shared branches or when others are working on the same commits.

D2 — TCP is connection-oriented, reliable, ordered (HTTP, SSH). UDP is connectionless, unreliable, fast (DNS, VoIP).

D3 — A race condition occurs when program behavior depends on the timing of events. Example: Two threads incrementing a shared counter without locks; one read-modify-write sequence overwrites the other.

D4 — Symmetric uses same key for encryption/decryption (AES). Asymmetric uses public/private key pairs (RSA). TLS uses asymmetric to exchange a symmetric session key, then symmetric for data transfer.

D5 — A layer is a read-only filesystem image. Layer caching speeds up builds by reusing unchanged layers. Best practice: Order Dockerfile instructions to maximize cache hits (e.g., install dependencies before copying source code).

D6 — 1. Check application logs for errors. 2. Check infrastructure health (disk, network). 3. Check database connection pool exhaustion. 4. Check upstream service availability.

D7 — CAP theorem states a system can only guarantee 2 of 3: Consistency, Availability, Partition Tolerance. CP: ZooKeeper (strong consistency). AP: Cassandra (eventual consistency).

D8 — Horizontal scaling adds more instances; Vertical scaling increases resources (CPU/RAM) of an instance. Horizontal scaling is enabled by stateless architecture and load balancers.

D9 — An environment variable is a dynamic name-value pair. Use `export VAR=value` in a shell session to persist it for that session.

D10 — JSON is data interchange format (key-value pairs). YAML is human-readable data serialization. JSON advantage: Strict typing. YAML advantage: Indentation-based readability.

D11 — REST uses HTTP methods to manipulate resources. GET (retrieve), POST (create), PUT (replace), DELETE (remove).

D12 — Version pinning specifies exact versions of dependencies. It ensures builds are reproducible and prevents unexpected breaking changes from upstream updates.

D13 — Compiled languages translate to machine code before runtime (C++, Rust). Interpreted languages translate during runtime (Python, JavaScript).

D14 — Reverse proxy sits behind the client, forwarding requests to servers (Nginx, HAProxy). Forward proxy sits behind the server, forwarding client requests to the internet. Use case: Nginx for load balancing; Forward proxy for corporate internet access.

D15 — A deadlock is when processes wait indefinitely for each other. Coffman conditions: 1. Mutual Exclusion. 2. Hold and Wait. 3. No Preemption. 4. Circular Wait.

D16 — Eventual consistency means data converges to a consistent state over time. Cassandra uses tunable consistency levels (ONE, QUORUM, ALL) to balance speed vs. accuracy.

D17 — mTLS authenticates both client and server using certificates. Handshake: Client sends cert -> Server verifies -> Server sends cert -> Client verifies -> TLS session established. Used in service-to-service communication (Istio).

D18 — Hash table maps keys to indices. Chaining uses linked lists at indices; Open addressing probes for empty slots. Average: O(1). Worst: O(n) (high collision).

D19 — Circuit breaker stops calls to a failing service. Closed (normal), Open (fail fast), Half-Open (test recovery). Prevents cascade failures by stopping load on unhealthy services. Relates to retry by limiting retries during Open state.

D20 — Optimistic concurrency assumes no conflicts, checks on commit (e.g., versioning). Pessimistic locks resources before access (e.g., SELECT FOR UPDATE). Choose Optimistic for high concurrency/low conflict. Choose Pessimistic for critical data integrity.
