AA1 — Easy: A monolith is a single, unified codebase deployed as one unit, while microservices are a collection of small, independent services communicating over a network. Three concrete problems microservices introduce that monoliths don't have:
1.  **Distributed Complexity:** Debugging and tracing requests across multiple services is harder than in a single process.
2.  **Network Latency:** Services communicate over the network (IPC overhead), introducing latency and potential failure points not present in in-process calls.
3.  **Operational Overhead:** Managing multiple deployment pipelines, monitoring systems, and service discovery is significantly more complex than managing one application.

AA2 — Easy: Synchronous communication involves a request-response pattern where the caller waits for a reply before proceeding (e.g., HTTP/REST). Asynchronous communication involves sending a message and continuing without waiting for an immediate response (e.g., Message Queues).
*   **Synchronous Example:** REST API (HTTP).
*   **Asynchronous Example:** RabbitMQ or Apache Kafka.

AA3 — Medium: An API Gateway is a specialized reverse proxy that handles cross-cutting concerns like authentication, rate limiting, and request transformation. A reverse proxy is a general network layer device that forwards requests to backend servers.
*   **Can it replace?** An API Gateway can replace a standard reverse proxy for application-layer traffic, but it cannot replace a network-layer reverse proxy (e.g., for SSL termination at Layer 4, load balancing based on IP, or DDoS protection at the network edge) entirely.
*   **Why:** Gateways operate at Layer 7 (application logic), while reverse proxies often operate at Layer 4 (transport) or Layer 7. You may need both for full coverage.

AA4 — Medium: The Saga pattern manages distributed transactions by breaking them into local transactions within each service, where each transaction updates its local database and publishes an event to trigger the next step.
*   **Choreography:** Services react to events autonomously. No central coordinator. Good for simple flows, but hard to manage complex rollback logic.
*   **Orchestration:** A central coordinator manages the flow and compensations. Good for complex flows requiring strict ordering and centralized error handling.

AA5 — Medium: CQRS separates the model for writing data (Commands) from reading data (Queries). It is often paired with Event Sourcing, which stores state as a sequence of events rather than current snapshots.
*   **Problem Solved:** Traditional CRUD models struggle with scaling read and write operations independently and maintaining complex read models (denormalization). CQRS + Event Sourcing allows optimizing read performance (via materialized views) and auditability (via event logs) independently of the write path.

AA6 — Medium: The Circuit Breaker pattern prevents a system from cascading failures by stopping calls to a failing service after a threshold of failures.
*   **Three States:** Closed (normal operation), Open (fail fast, no calls), Half-Open (testing recovery).
*   **Difference from Retry:** Retry attempts to fix transient errors; Circuit Breaker stops attempts to prevent resource exhaustion.
*   **Usage Together:** Use retry with backoff for transient network glitches, but wrap it in a Circuit Breaker to stop retrying if the service is down for good.

AA7 — Hard:
1.  **Shared DB, Shared Schema:**
    *   *Cost:* Lowest (single DB instance).
    *   *Security:* Lowest (data leakage risk via SQL injection or logic errors).
    *   *Complexity:* Low.
    *   *Noisy Neighbor:* High (one tenant can exhaust resources).
2.  **Shared DB, Separate Schema:**
    *   *Cost:* Medium (schema management overhead).
    *   *Security:* Medium (logical isolation).
    *   *Complexity:* Medium (schema migrations per tenant).
    *   *Noisy Neighbor:* Medium.
3.  **Separate DB per Tenant:**
    *   *Cost:* High (many DB instances).
    *   *Security:* Highest (physical isolation).
    *   *Complexity:* High (provisioning, backups, scaling).
    *   *Noisy Neighbor:* None (complete isolation).

AA8 — Hard: Eventual consistency means data converges to the same state after some time; strong consistency means all reads see the latest write immediately.
*   **Architecture:** For inventory (never oversell), use **Strong Consistency**.
*   **Data Store:** Use a database with strong consistency guarantees (e.g., PostgreSQL, DynamoDB with strong consistency enabled).
*   **Patterns:** Use optimistic locking or distributed locks (e.g., Redis Redlock) to ensure only one transaction can decrement the inventory count at a time. Avoid eventual consistency for the critical inventory check.

AA9 — Hard: A sidecar proxy is a lightweight process running alongside a service to handle networking, security, and observability.
*   **Envoy/Istio:** Envoy is the sidecar proxy (data plane) handling traffic. Istio is the control plane managing Envoy configurations.
*   **Data Plane:** The actual traffic flow (Envoy). **Control Plane:** The management layer (Istiod).
*   **mTLS Problem:** Application-level TLS requires managing certificates in the app code. Sidecar mTLS handles encryption automatically between services, simplifying certificate rotation and enforcing security policies without app changes.

AA10 — Medium: The Strangler Fig pattern involves incrementally migrating functionality from a legacy system to a new system, cutting off pieces of the legacy system as they are replaced.
*   **Strategy:**
    1.  Deploy a new .NET 8 service for a specific feature (e.g., User Auth).
    2.  Update the legacy .NET Framework app to route Auth requests to the new service via an API Gateway.
    3.  Repeat for other features (Orders, Inventory).
    4.  Once all features are migrated, decommission the legacy monolith.

AA11 — Medium: The 12-Factor App methodology provides best practices for building modern cloud-native applications.
*   **Factors:**
    1.  **Codebase:** One codebase tracked in VCS.
    2.  **Dependencies:** Explicitly declared and isolated.
    3.  **Config:** Config stored in the environment, not code.
    4.  **Backing Services:** Treat all external services as attached resources.
    5.  **Build, Release, Run:** Strict separation of these stages.
    6.  **Processes:** Run the app as one or more stateless processes.
    7.  **Port Binding:** Export services via ports.
    8.  **Concurrency:** Scale out via process replication.
    9.  **Disposability:** Fast startup and graceful shutdown.
    10. **Dev/Prod Parity:** Keep environments similar.
    11. **Logs:** Treat logs as event streams.
    12. **Admin Processes:** Run admin tasks as one-off processes.

AA12 — Hard:
*   **Coupling:** Event-driven (Kafka) is looser coupling; Request-driven (REST) is tighter.
*   **Scalability:** Kafka scales horizontally better for high throughput; REST scales well but requires stateless endpoints.
*   **Debugging:** REST is easier to debug (direct HTTP); Kafka requires replaying logs/events.
*   **Ordering:** Kafka guarantees ordering per partition; REST guarantees ordering per request.
*   **Failure Handling:** Kafka supports async retries; REST requires client-side retry logic.
*   **Choice:** Use Kafka for decoupled, high-throughput background jobs. Use REST/gRPC for synchronous, real-time user interactions.

AA13 — Easy: A load balancer distributes incoming network traffic across multiple servers to ensure no single server is overwhelmed.
*   **Layer 4 (Transport):** Balances based on IP/Port (e.g., TCP). Faster, less context.
*   **Layer 7 (Application):** Balances based on HTTP headers/URLs (e.g., routing /api to Service A).
*   **Use Case:** Layer 7 is required for SSL termination (offloading decryption) or routing based on URL paths (e.g., /images vs /api).

AA14 — Easy: A message queue is a system for passing messages between producers and consumers.
*   **Difference:** RabbitMQ (Queue) is point-to-point or pub/sub with guaranteed delivery per queue; Kafka (Log) is a distributed log where messages are retained for replay.
*   **Choice:** Use RabbitMQ for task queues where messages are consumed once. Use Kafka for event streaming where history and replayability are needed.

AA15 — Easy: A container is a lightweight, standalone package containing code and dependencies.
*   **Difference:** VMs include a full OS kernel; containers share the host OS kernel.
*   **Popularity:** Containers are faster to start, smaller in size, and provide consistent environments across dev, test, and prod, ideal for microservices.

AA16 — Easy: Stateless services do not store session data locally; stateful services store data (e.g., session, DB connection).
*   **Scaling:** Stateless services scale horizontally easily because any instance can handle any request. Stateful services require sticky sessions or complex state management.
*   **Example:** Stateless = API Gateway. Stateful = Database or Session Store.

AA17 — Easy: An ORM maps database tables to object classes in code.
*   **Examples:** Entity Framework (.NET), Hibernate (Java).
*   **Trade-offs:** ORMs reduce boilerplate code and improve developer productivity but can lead to performance issues (N+1 queries) and less control over SQL optimization compared to raw SQL.

AA18 — Medium: The Bulkhead pattern isolates resources (like threads or connections) to prevent a failure in one part of the system from affecting others.
*   **Relation:** It ensures that if one microservice fails, it doesn't exhaust the shared thread pool of the application.
*   **Implementation:** Configure separate thread pools for different services (e.g., one pool for "Orders", one for "Inventory") so a spike in Orders doesn't starve Inventory processing.

AA19 — Hard:
*   **OT:** Optimistic Transformation. Optimizes for consistency but requires complex algorithms to resolve conflicts. High latency, hard to implement.
*   **CRDTs:** Conflict-free Replicated Data Types. Data structures that converge to the same state regardless of update order.
*   **Comparison:** CRDTs are easier to implement, support offline editing natively, and guarantee eventual consistency without complex conflict resolution logic.
*   **Choice:** CRDTs are better for offline editing because they allow local changes to be stored and merged automatically when connectivity is restored.

AA20 — Hard:
*   **Context Propagation:** Use W3C Trace Context headers (traceparent, tracestate) to pass trace IDs across services.
*   **Sampling:** Head-based (decide at start) vs Tail-based (decide based on error rate). Tail-based is better for cost optimization.
*   **Storage:** Jaeger (open source) or Tempo (high performance).
*   **Async/Messaging:** Tracing spans must be created when a message is produced and continued when consumed.
*   **Kafka Continuity:** Use a distributed tracing library (e.g., OpenTelemetry) that injects headers into the message payload or metadata so the consumer can link the span to the producer's trace ID.

OP1 — Easy: Type 1 (Bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V). Type 2 (Hosted) run as an application on an OS (e.g., VirtualBox, VMware Workstation).

OP2 — Easy: SAN (Storage Area Network) provides block-level storage (like a hard drive); NAS (Network Attached Storage) provides file-level storage.
*   **Use Case:** SAN for databases (needs block access); NAS for file sharing (needs file access).
*   **Protocols:** SAN uses iSCSI or Fibre Channel; NAS uses NFS or SMB/CIFS.

OP3 — Medium: 3-tier architecture separates Core (high speed), Distribution (aggregation), and Access (edge).
*   **Leaf-Spine:** Preferred in modern DCs because it provides non-blocking bandwidth and equal latency between all servers.
*   **Problem Solved:** 3-tier can create bottlenecks at the distribution layer; Leaf-Spine ensures every leaf connects to every spine, eliminating congestion.

OP4 — Medium:
*   **Node Count:** Minimum 3 nodes for quorum.
*   **Quorum:** Majority of nodes must agree to prevent split-brain.
*   **Fencing:** Prevents a failed node from accessing shared storage (STONITH).
*   **Storage:** Ceph (distributed) or iSCSI (shared SAN).
*   **Failure:** If one node fails, the cluster maintains quorum and continues. If storage fails, data is lost or degraded depending on replication.

OP5 — Medium: VLAN trunking allows a single physical link to carry traffic for multiple VLANs.
*   **802.1Q:** Adds a 4-byte tag to Ethernet frames to identify the VLAN ID.
*   **Linux Config:** Use `ip link add vlan X type vlan id X` for each VLAN on the interface, or use `bridge` with VLAN tagging.

OP6 — Medium:
*   **RAID 1:** Mirror (50% capacity, 1 drive failure).
*   **RAID 5:** Striping + Parity (N-1 drives, 1 failure).
*   **RAID 6:** Striping + 2 Parity (N-2 drives, 2 failures).
*   **RAID 10:** Mirror + Stripe (50% capacity, 1 drive failure per mirror).
*   **RAID Z2:** ZFS equivalent of RAID 6 (striping + 2 parity).
*   **Choice:** For 6 drives and a database, choose **RAID 10** (if budget allows) for best performance, or **RAID 6** (ZFS) for better capacity efficiency with good fault tolerance.

OP7 — Hard:
*   **Recursive Resolvers:** Query external DNS (e.g., 8.8.8.8).
*   **Authoritative:** Serve internal zones (AD).
*   **Forwarders:** Internal servers forward external queries to recursive resolvers.
*   **Conditional Forwarding:** Forward specific domains (e.g., partner.com) to specific servers.
*   **Laptop Move:** Laptop uses DHCP to get DNS. If on VPN, DNS points to internal resolver. If on office, DNS points to local AD DNS. Split-horizon ensures internal names resolve internally, external names resolve externally.

OP8 — Hard:
*   **Chain:** Root CA (trusted by OS) -> Intermediate CA -> End Entity.
*   **Deployment:** Root CA kept offline. Subordinate CA issues certs.
*   **CRL vs OCSP:** CRL is a list of revoked certs (periodic check); OCSP is real-time status check.
*   **Compromise:** Compromised Subordinate CA affects only issued certs (can revoke). Compromised Root CA invalidates all certs in the chain (requires reissuing all certs).

OP9 — Hard:
*   **MPLS:** High reliability, expensive, provider-managed.
*   **IPsec:** Cheaper, relies on internet, complex management.
*   **SD-WAN:** Optimizes traffic, easy management, moderate cost.
*   **WireGuard:** Simple, fast, but mesh topology is complex for 5 sites.
*   **Recommendation:** **SD-WAN** or **MPLS**. For 50 users and VoIP, SD-WAN offers the best balance of cost and latency optimization over the internet, provided SLAs are met.

OP10 — Medium: iDRAC/iLO/IPMI are out-of-band management interfaces allowing remote server control (power on/off, console access) independent of the OS.
*   **Criticality:** Essential for troubleshooting when OS is dead.
*   **Risk:** Exposing IPMI to the internet allows attackers to gain root access to the hardware, potentially compromising the entire server.

OP11 — Medium:
*   **LVM:** Logical Volume Manager (Linux). Good for resizing volumes.
*   **LVM-Thin:** Thin provisioning (allocate space on demand).
*   **ZFS:** Filesystem + Volume Manager. Built-in snapshots, compression, checksums.
*   **Snapshots:** LVM (copy-on-write, slower); ZFS (instant, consistent).
*   **Use Case:** LVM for simple VM storage; ZFS for databases requiring integrity and snapshots.

OP12 — Hard:
*   **Stretch Cluster:** Replicates data across two sites.
*   **CRUSH Rules:** Define data placement and replication strategy.
*   **Monitor Placement:** Monitors must be in a quorum-safe location (often a third site or cloud).
*   **Latency:** High latency between sites slows replication.
*   **Split-Brain:** If both sites lose connectivity, they might both think they are primary.
*   **2-Site Bad Idea:** Without a tiebreaker (3rd site), if the link breaks, the cluster might stop writing to avoid data corruption.

OP13 — Easy: DHCP assigns IP addresses dynamically.
*   **DORA:** Discover, Offer, Request, Acknowledge.
*   **Unavailable:** Client uses APIPA (169.254.x.x) or retains old lease until expiration.
*   **Windows Lease:** If expired and server unavailable, client cannot renew and loses network access.

OP14 — Easy: Managed switches allow configuration (VLANs, QoS, ACLs); Unmanaged switches are plug-and-play.
*   **Features:** Managed switches provide VLANs, port mirroring, STP, and QoS, critical for enterprise traffic segmentation and security.

OP15 — Easy: NTP synchronizes time across systems.
*   **Criticality:** Essential for logging correlation, Kerberos authentication, and database replication.
*   **Drift:** Clock drift causes authentication failures, log analysis errors, and replication conflicts.

OP16 — Easy: Physical server = bare metal. VM = OS on top of hypervisor. Container = App + libs on OS.
*   **Bare Metal:** Use for high-performance, low-latency workloads (HPC, Databases) where hypervisor overhead is unacceptable.

OP17 — Easy: UPS provides battery backup for seconds/minutes; Generator provides long-term power (hours).
*   **Need Both:** UPS bridges the gap between outage and generator startup.
*   **ATS:** Automatically switches power source from grid to generator during outage.

OP18 — Medium: Active-Passive = one active, one standby. Active-Active = both handle load.
*   **Implementation:** Pacemaker/Corosync manages the cluster.
*   **Fencing:** STONITH ensures a failed node is physically disconnected from storage before failover.
*   **Failover:** VIP moves to the active node. If Node A dies, Node B takes VIP and resources.

OP19 — Hard:
*   **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Recovery Point Objective (data loss limit) and Recovery Time Objective (downtime limit).
*   **Types:** Full (slow, complete), Incremental (fast, small), Differential (medium).
*   **Ransomware:** Immutable backups (WORM) prevent deletion/modification.
*   **Backup vs DR:** Backup is data protection; DR is restoring full system functionality.
*   **Testing:** Regular restore drills to verify data integrity.

OP20 — Hard:
*   **Roles:** Supplicant (client), Authenticator (switch), Authentication Server (RADIUS).
*   **EAP:** EAP-TLS (certificates, secure), PEAP (username/password).
*   **RADIUS:** Protocol for authentication.
*   **Dynamic VLAN:** Server assigns VLAN ID based on user role.
*   **Failure:** Device is placed in a "Guest" VLAN or blocked.
*   **MAB:** Switch authenticates based on MAC address if 802.1X fails (less secure, fallback).
