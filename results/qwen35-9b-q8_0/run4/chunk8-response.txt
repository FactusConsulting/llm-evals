CL1 — IaaS (Infrastructure as a Service) provides virtualized computing resources (VMs, storage, networks) where you manage the OS and applications (e.g., AWS EC2). PaaS (Platform as a Service) provides a managed runtime environment for developing and deploying apps without managing the underlying OS (e.g., Google App Engine). SaaS (Software as a Service) delivers fully managed software applications over the internet (e.g., Salesforce).

CL2 — The Shared Responsibility Model divides security duties. For IaaS VMs, the provider secures the physical hardware and hypervisor; you secure the OS, data, and network config. For managed Kubernetes, the provider manages the control plane and node infrastructure; you manage the cluster policies, workloads, and secrets. For SaaS like M365, the provider manages the entire application and infrastructure; you manage user identity, access, and data classification.

CL3 — A VPC is a virtual network isolated from the public cloud. Subnets divide the VPC into smaller address ranges (public/private). Security Groups are stateful stateful firewalls attached to instances (allow/deny rules). NACLs are stateless stateless firewalls at the subnet level (allow/deny rules). Layering: VPC contains Subnets, which contain Instances protected by Security Groups, all filtered by NACLs. Stateful means return traffic is automatically allowed (Security Groups); Stateless means return traffic must be explicitly allowed (NACLs).

CL4 — A Landing Zone is a pre-configured, secure, and scalable foundation for cloud adoption. Organizational Units (OUs) group accounts for policy enforcement. Guardrails enforce compliance (e.g., no public S3 buckets). Shared networking uses Transit Gateway (AWS) or Hub-and-Spoke (Azure) to connect accounts securely. Centralized logging aggregates logs to a single account for analysis. Single-account approaches are problematic due to lack of isolation, difficulty in scaling, and inability to enforce consistent governance across teams.

CL5 — Infrastructure as Code (IaC) manages infrastructure via code. Terraform/OpenTofu uses declarative HCL; best for multi-cloud and state management. Pulumi uses strong typed languages (TypeScript/Python); best for teams with strong dev backgrounds. CloudFormation/Bicep are native AWS/Azure tools; best for deep native integration. Crossplane manages infrastructure via Kubernetes CRDs; best for cloud-native teams using K8s as the control plane.

CL6 — HPA scales pods based on metrics (CPU/Memory). VPA scales individual pod resources (CPU/RAM) up or down. Cluster Autoscaler adds/removes nodes based on pending pods. KEDA scales based on external events (e.g., Kafka messages, HTTP requests). Use KEDA over HPA when scaling needs depend on external event queues rather than internal resource utilization.

CL7 — DR strategy depends on RPO (data loss) and RTO (downtime). Active-Active offers lowest RTO/RPO but highest cost; Active-Passive is cheaper but higher RTO. Database replication: Sync for zero RPO, Async for lower latency. DNS failover routes traffic to the healthy region. Pilot Light keeps minimal resources running (low cost, high RTO). Warm Standby runs scaled-down production (medium cost, medium RTO). Multi-site Active-Active runs full production in both regions (high cost, low RTO).

CL8 — GitOps uses Git as the single source of truth for infrastructure and app state. ArgoCD and FluxCD are controllers that sync cluster state to Git. Secrets are managed via Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault), or HashiCorp Vault Agent. Manual changes cause drift; GitOps detects this and either auto-reverts or alerts the operator to reconcile the state.

CL9 — Use a StatefulSet for ordered deployment and stable network identities. Use Local Persistent Volumes (Local PV) with a Local Storage Class for low-latency storage. Use a Headless Service for DNS-based service discovery without a load balancer. Use Init Containers to prepare the filesystem or fetch configs. Mount ConfigMaps as volumes for config files. Use Pod Disruption Budgets (PDB) to ensure availability during voluntary disruptions.

CL10 — Service Accounts are Kubernetes identities for pods. Workload Identity (GCP/Azure) or IRSA (AWS) maps K8s identities to cloud IAM roles. Mounting cloud credentials in pods is bad practice because it exposes secrets to the pod environment and potential compromise. Workload Identity federation solves this by allowing the pod to assume a role dynamically without storing credentials.

CL11 — Object Storage (S3/Blob) stores unstructured data as objects; high durability (99.999999999%), scalable, but higher latency. Block Storage (EBS/Managed Disk) is attached to VMs for OS/apps; low latency, high IOPS. File Storage (EFS/Azure Files) is network file system (NFS/SMB); shared access, higher latency. Use Object for backups/media, Block for databases/OS, File for shared app data.

CL12 — Zero Trust assumes no implicit trust. Network Policies restrict pod-to-pod traffic. Service Mesh (Istio/Linkerd) enforces mTLS between services. Pod Identity authenticates pods to the cloud. Admission Controllers (OPA/Kyverno) enforce policies before deployment. Image signing verifies container integrity. Runtime security (Falco) detects anomalies. Unlike perimeter security, Zero Trust verifies every request regardless of origin.

CL13 — A CDN caches content geographically closer to users to reduce latency. It works by routing requests to edge servers. Services: CloudFront (AWS), Azure CDN. Use CDN for static assets (images, CSS) and high-traffic content. Use origin directly for dynamic content requiring real-time data or low latency API calls.

CL14 — Regions are geographic areas with multiple data centers. Availability Zones (AZs) are isolated data centers within a region. Deploy across AZs for high availability (survives zone failure). Zonal resources are in one AZ (cheaper, less resilient). Regional resources span AZs (more resilient, higher cost).

CL15 — Managed databases (RDS, Cloud SQL) handle patching, backups, scaling, and failover. You manage the schema and data. On VMs, you handle OS patching, database patching, backups, and hardware monitoring. Managed services reduce operational overhead and security risks.

CL16 — IAM Users are individuals. Groups organize users. Roles are permissions attached to users, groups, or services. Policies define permissions. Principle of Least Privilege grants only necessary permissions. Apply it by creating specific roles for tasks (e.g., "S3 Read Only") rather than granting admin access.

CL17 — Serverless runs code without managing servers (AWS Lambda, Azure Functions, GCP Functions). Cold starts occur when a function is invoked for the first time or after inactivity, causing latency. They matter for latency-sensitive apps. Serverless is poor for long-running processes, high I/O latency requirements, or when you need fine-grained control over the runtime environment.

CL18 — Ingress resource is the standard K8s API for external access. Gateway API is the newer, more flexible standard (supports HTTP/2, gRPC). Cloud Load Balancer annotations configure K8s to use cloud LBs. Service Mesh Ingress Gateways handle mTLS and observability. TLS termination at Ingress is common; Gateway API allows multiple TLS contexts. Use Gateway API for complex routing, gRPC, or multi-protocol support.

CL19 — Cost optimization: Reserved Instances/Savings Plans for steady-state workloads. Spot/Preemptible for fault-tolerant batch jobs. Right-sizing via utilization reports. Storage tiering moves infrequent data to cheaper storage. Idle resource detection shuts down unused resources. FinOps involves collaboration between finance and tech. Showback/chargeback assigns costs to teams. Tools: AWS Cost Explorer, Azure Cost Management, CloudHealth.

CL20 — Multi-cloud strategy uses Kubernetes as a common runtime to abstract infrastructure. Terraform with modules abstracts cloud-specific resources. Networking uses Interconnects (AWS Direct Connect, Azure ExpressRoute) and VPNs. Identity uses federation (OIDC/SAML) to share credentials. Trade-offs: Higher complexity, cost, and latency vs. vendor lock-in avoidance. Justified for compliance, disaster recovery, or specific cloud features; unnecessary if one cloud meets all needs.

OT1 — The Purdue Model (ISA-95) defines security zones for industrial automation. Level 0: Field Devices (sensors/actuators). Level 1: Basic Process Control System (PLCs). Level 2: Supervisory Control (SCADA/HMI). Level 3: Enterprise Information System (MES). Level 4: Business/ERP. Level 5: Corporate/Management.

OT2 — IT networks prioritize data availability and confidentiality; OT networks prioritize safety and availability. OT systems often run legacy hardware with long lifecycles. Standard IT patching can disrupt critical processes or introduce instability, so changes require rigorous testing and maintenance windows.

OT3 — An IDMZ (Industrial DMZ) separates IT and OT networks. It allows secure communication (e.g., engineering workstations to SCADA servers) but blocks direct IT-to-OT traffic. Direct connectivity from Level 4 (IT) to Level 1 (Control) is dangerous because IT threats (ransomware, malware) can directly compromise safety systems.

OT4 — 1. Modbus TCP: Level 1/2, serial/ethernet protocol for PLCs. 2. OPC UA: Level 2/3, secure, platform-independent data exchange. 3. EtherNet/IP: Level 1/2, CIP protocol for industrial Ethernet. 4. PROFINET: Level 1/2, real-time industrial Ethernet. 5. MQTT: Level 2/3, lightweight messaging for IoT/Cloud.

OT5 — A data diode allows traffic in only one direction (physical or logical). A firewall allows bidirectional traffic with rules. Use a data diode when preventing data exfiltration is critical (e.g., from OT to IT). Limitation: Cannot block inbound traffic; only allows outbound.

OT6 — Data flow: PLCs send data to Historian (Level 1/2). Historian pushes to Edge Gateway (Level 2/3). Edge Gateway uses MQTT to push to Cloud Broker. Cloud Broker ingests to Analytics. Security boundaries: Firewall between Historian and Edge; Firewall between Edge and Cloud.

OT7 — Zones are logical network segments (e.g., Engineering, SCADA). Conduits are secure connections between zones. Model: Corporate Network (Zone A) connects via Conduit to Engineering Workstations (Zone B). Zone B connects via Conduit to SCADA Servers (Zone C). Zone C connects via Conduit to PLCs (Zone D). SIS (Zone E) is air-gapped or isolated from Zone D.

OT8 — VLAN design: Separate VLANs for PLCs, HMIs, SCADA, and Engineering. Firewall placement: Between IT and OT DMZ, and between OT zones. Switch architecture: Layer 3 switches for segmentation. Transition: Use parallel networks or phased migration with temporary firewalls to maintain production while upgrading.

OT9 — SIS (Safety Instrumented Systems) handles emergency shutdowns. BPCS handles normal operation. IEC 61511 defines functional safety. SIS must be isolated to prevent IT threats from disabling safety systems. If ransomware reaches SIS, it could cause physical damage, environmental hazards, or loss of life.

OT10 — PLC: Programmable Logic Controller, local control. DCS: Distributed Control System, large-scale process control. SCADA: Supervisory Control and Data Acquisition, monitoring and data collection. They can coexist: PLCs control machines, DCS manages processes, SCADA monitors both.

OT11 — Remote access architecture: Jump Host (bastion) with MFA. Session recording for audit. Vendor access via time-limited tickets. RDP directly to HMI is unacceptable because it bypasses security controls and exposes critical control systems to the internet.

OT12 — Detection: Deploy IDS/IPS on network segments. Asset inventory to identify critical PLCs. Response: Isolate affected network segment. Coordinate with control room to switch to manual mode if needed. Role of operator: Monitor physical indicators, follow emergency procedures, and communicate status to security team.

OT13 — HMI is the interface for operators to monitor and control processes. It displays real-time data and allows manual overrides. Engineering workstations are for configuration, programming, and maintenance, not real-time operation.

OT14 — Historian stores time-series process data. Important for trend analysis, compliance, and troubleshooting. Plant Historian (Level 3) stores operational data. Enterprise Historian (Level 4) aggregates data for business reporting.

OT15 — Ladder logic is a graphical programming language resembling electrical relay logic. Executed by PLCs. Dominant due to ease of understanding for electricians and reliability in legacy systems.

OT16 — RTU (Remote Terminal Unit) is for remote, unattended locations (pipelines, oil rigs). PLCs are for local, accessible control rooms. RTUs have built-in comms; PLCs often need external comms modules.

OT17 — Analog signals (4-20mA, 0-10V) represent continuous values. Digital signals represent discrete states. 4-20mA is preferred over 0-20mA because 4mA indicates a live signal (0mA indicates a broken wire), allowing fault detection.

OT18 — OT asset inventory lists all devices, firmware, and connections. Foundation for security because you cannot protect what you don't know. Passive monitoring (sniffing) is safe. Active scanning (pinging/scanning) can disrupt processes or trigger alarms.

OT19 — MITRE ATT&CK for ICS maps adversary tactics to ICS-specific techniques. Tactics: Reconnaissance (e.g., T1595.001), Execution (e.g., T1059.001), Persistence (e.g., T1545.001), Privilege Escalation (e.g., T1078), Defense Evasion (e.g., T1070). Differs from Enterprise by focusing on safety and control systems. Use it to identify gaps in monitoring and controls.

OT20 — Converged SOC: Collect logs via agents or syslog from OT assets. SIEM integrates OT logs with IT logs. OT-specific rules detect anomalies (e.g., unexpected PLC writes). Triage: IT analysts handle IT alerts; OT engineers handle OT alerts. False positives are common due to legitimate process changes. Unauthorized firmware changes: Isolate device, verify integrity, check for malware, and update firmware via secure channel.
