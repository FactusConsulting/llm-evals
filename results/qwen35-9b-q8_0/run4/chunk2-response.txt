K1 — A Deployment manages stateless applications and ensures a desired number of replicas are running, treating pods as fungible. A StatefulSet manages stateful applications, providing stable network identities (hostname), ordered deployment/termination, and persistent storage per pod. Use Deployments for web servers; StatefulSets for databases or message queues.

K2 — A ClusterIP Service creates a virtual IP within the cluster. kube-proxy watches the Service and updates iptables (or IPVS) rules to forward traffic destined for that IP to the backend pods listed in the Service's Endpoints. Pods communicate via the Service IP, and external traffic is not routed to it by default.

K3 — A PersistentVolume (PV) is a cluster-wide resource representing storage. A PersistentVolumeClaim (PVC) is a request for storage resources made by a user. A StorageClass defines the provisioner and parameters for dynamically creating PVs. A PVC requests storage from a StorageClass, and the system creates a PV to satisfy the claim.

K4 — 1. Check logs (`kubectl logs <pod>`) for application errors. 2. Check events (`kubectl describe pod <pod>`) for OOMKilled or scheduling issues. 3. Verify readiness/liveness probes configuration (too aggressive?). 4. Check resource limits vs. node capacity (CPU/Memory pressure).

K5 — CoreDNS provides DNS resolution for services, pods, and nodes within the cluster. If CoreDNS pods are down, internal service discovery fails (pods cannot resolve `service-name.namespace.svc.cluster.local`), breaking service-to-service communication and potentially causing ingress routing failures.

K6 — The scheduler filters nodes based on hard constraints (taints/tolerations, node selectors, affinity, resource availability). It then scores remaining nodes using a scoring algorithm (e.g., LeastAllocated, BalancedResource). Factors include: 1. Node affinity/anti-affinity rules. 2. Resource requests vs. available capacity. 3. Pod topology spread constraints. 4. Taints and tolerations.

K7 — Yes, it will be scheduled. The scheduler checks `requests` (256Mi) against available memory (4GB - 3.5GB = 0.5GB). 256Mi < 512Mi (limit) and 256Mi < 512Mi (available). If it uses 600Mi at runtime, it exceeds the limit (512Mi), triggering an OOMKilled event and restart.

K8 — 1. External LB receives traffic on port 80. 2. LB forwards to the Ingress Controller (NGINX) on port 80. 3. NGINX Controller matches the Ingress rule (host/path) and routes to the backend Service IP. 4. Service IP is resolved via kube-proxy to Pod IPs (Endpoints). 5. kube-proxy updates iptables/IPVS to DNAT traffic to the Pod IP. 6. Pod receives traffic and responds.

K9 — A NetworkPolicy defines rules for ingress/egress traffic. If no policy exists, all ingress/egress traffic is allowed by default. When a policy is applied, it restricts traffic to/from the selected pods based on the rules defined (e.g., allow only from specific namespaces).

K10 — RollingUpdate updates pods gradually (old -> new), ensuring availability. Recreate kills all old pods before creating new ones, causing downtime. Choose Recreate for stateful applications (e.g., databases) where rolling updates might cause data corruption or require manual migration.

K11 — A namespace isolates resources (names, objects) within a cluster. Default namespaces are `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

K12 — It shows detailed metadata, events, and conditions. 1. Events (reasons for restarts/scheduling). 2. Conditions (Ready, Running, Initialized status). 3. Container status (restart count, image ID, last state).

K13 — A ConfigMap stores non-confidential configuration data as key-value pairs. Pods consume it via: 1. Environment variables. 2. Mounting as files in a volume.

K14 — ClusterIP: Internal-only service (cluster-wide IP). NodePort: Exposes service on a static port on each node's IP. LoadBalancer: Provisions an external cloud load balancer to expose the service externally.

K15 — A DaemonSet ensures a copy of a Pod runs on all (or selected) nodes. Use it for system-level agents (logging, monitoring, network plugins) rather than Deployments, which manage a fixed number of replicas across nodes.

K16 — Taints repel pods; tolerations allow pods to ignore taints. Node affinity selects nodes based on labels. Use case: Taint a GPU node to ensure only GPU-enabled pods schedule there. Use case: Affinity to schedule pods on nodes in a specific rack for latency.

K17 — An Operator is a controller that encapsulates the logic to manage a specific application's lifecycle (install, upgrade, backup). It differs from standard controllers by implementing domain-specific logic (e.g., managing a database cluster's replication). It solves the "how to run" problem for complex stateful apps.

K18 — etcd uses Raft consensus for strong consistency. If quorum is lost (e.g., 2 out of 3 nodes lost), the cluster becomes unavailable (read/write blocked). Recovery requires restoring the remaining node(s) from a backup and rejoining the cluster, ensuring the restored data matches the majority.

K19 — RBAC controls permissions. Role defines permissions in a namespace; ClusterRole defines cluster-wide. RoleBinding binds a Role to a user/group; ClusterRoleBinding binds a ClusterRole.
Manifest:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` defines how many dots must precede a name to treat it as a domain name. Default is 5. If a name has fewer dots (e.g., `google.com`), it queries internal DNS first, failing, then external. This causes multiple retries. Fix: Set `dnsConfig.nameservers` and `options` in pod spec: `options: [ndots:1]` to prioritize external DNS for short names.

D1 — Rebase rewrites history to integrate changes linearly; Merge creates a merge commit preserving history. Avoid rebasing on shared/public branches (e.g., main) as it rewrites history for others.

D2 — TCP is connection-oriented, reliable, ordered (HTTP, SSH). UDP is connectionless, unreliable, fast (DNS, QUIC).

D3 — A race condition occurs when program behavior depends on the relative timing of events. Example: Two threads increment a shared counter without locks; one read-modify-write sequence overwrites the other, losing an update.

D4 — Symmetric uses same key for encrypt/decrypt (fast, e.g., AES). Asymmetric uses public/private key pairs (secure key exchange). TLS uses asymmetric to exchange a symmetric session key, then symmetric for data transfer.

D5 — Layers are read-only filesystems stacked in a container image. Caching works by reusing unchanged layers. Best practice: Order `RUN` commands to group dependencies and minimize changes to cached layers.

D6 — 1. Check application logs for errors. 2. Check infrastructure health (disk, memory, network). 3. Check upstream dependencies (database, cache). 4. Check rate limiting or circuit breaker states.

D7 — CAP theorem: A system can only guarantee 2 of Consistency, Availability, Partition Tolerance. CP (e.g., ZooKeeper) prioritizes consistency during network splits. AP (e.g., Cassandra) prioritizes availability, allowing eventual consistency.

D8 — Horizontal adds more instances (scale-out); Vertical increases resources of one instance (scale-up). Horizontal scaling requires stateless design, load balancing, and service discovery.

D9 — An environment variable is a dynamic name-value pair. To persist across sessions, export it in the shell (`export VAR=value`) or add it to `.bashrc`/`.zshrc`.

D10 — JSON is text-based, strict syntax, widely used for APIs. YAML is human-readable, indentation-based. JSON advantage: Strict validation. YAML advantage: Readability for config files.

D11 — REST uses HTTP methods to manipulate resources. GET (retrieve), POST (create), PUT (replace), DELETE (remove).

D12 — Version pinning specifies exact versions of dependencies. It ensures builds are reproducible and prevents unexpected breaking changes from upstream updates.

D13 — Compiled languages translate code to machine code before execution (C++, Rust). Interpreted languages translate code at runtime (Python, JavaScript).

D14 — Reverse proxy sits behind clients, forwarding requests to servers (Nginx, HAProxy). Forward proxy sits behind servers, forwarding client requests to external sites. Use case: Reverse proxy for load balancing/SSL termination. Forward proxy for corporate internet access.

D15 — A deadlock is when two or more processes wait for each other indefinitely. Coffman conditions: 1. Mutual Exclusion. 2. Hold and Wait. 3. No Preemption. 4. Circular Wait.

D16 — Eventual consistency means data converges to a consistent state after updates. Cassandra allows tunable consistency (ONE, QUORUM, ALL) per operation. Read-after-write consistency is handled by routing reads to replicas that have acknowledged the write.

D17 — mTLS authenticates both client and server using certificates. Handshake: Client sends cert -> Server verifies -> Server sends cert -> Client verifies -> TLS session established. Used in service mesh (Istio) and secure internal APIs.

D18 — Hash table maps keys to indices via a hash function. Chaining uses linked lists at indices; Open addressing probes for empty slots. Average: O(1). Worst: O(n) (due to collisions).

D19 — Circuit breaker stops calls to a failing service to prevent cascade failures. Closed (normal), Open (stop calls), Half-Open (test calls). Relates to retry policies by limiting retries when the breaker is open to avoid hammering a dead service.

D20 — Optimistic concurrency assumes no conflicts, using versioning (CAS). Pessimistic locks resources to prevent conflicts (SELECT FOR UPDATE). Choose Optimistic for high contention/low conflict (web apps). Choose Pessimistic for critical data integrity (banking).
