T1 — Easy: `tofu plan` calculates the changes required to reach the desired state defined in the configuration without making changes. `tofu apply` executes those changes to update the infrastructure to match the configuration.

T2 — Easy: State is a JSON file tracking the real-world resources managed by OpenTofu, including their IDs and attributes. Remote state is important for collaboration (multiple users/teams), security (keeping state out of local repos), and reliability (preventing concurrent modifications).

T3 — Medium: `count` creates a list of resources indexed by integer (0, 1, 2...), while `for_each` creates resources indexed by a map or set of keys. `for_each` is preferred when you need to reference resources by a specific name (key) rather than an index, or when the number of resources is dynamic and you want to avoid index-based logic.

T4 — Medium: OpenTofu detects drift by comparing the current state (from the backend) against the configuration during `plan`. If a resource exists in the state but its attributes differ from the config, OpenTofu marks it as "drifted" and suggests a plan to reconcile it.

T5 — Medium:
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.key
  }
}
```

T6 — Hard: `terraform_remote_state` reads outputs from another state file, creating a dependency. Output values are the actual values exposed. The recommended alternative is using `output` with `tofu`'s `tofu_remote_state` or better yet, using a shared configuration pattern or a dedicated "data" module to avoid circular dependencies and state coupling. However, the specific recommended alternative in modern Terraform is often using `output` with `tofu_remote_state` or simply passing values via `terraform_remote_state` if state sharing is necessary, but the *best* practice is to avoid sharing state entirely by using a shared module or a dedicated data source provider (like AWS SSM Parameter Store) instead of reading state files.

T7 — Hard: The `null_resource` with `remote-exec` runs asynchronously or blocks until completion. If the provisioner fails or the output is empty, the dependent resource (which reads the output) fails. Fix: Ensure the `provisioner` completes successfully and the `output` block returns a valid value. Use `local-exec` to verify or ensure the `remote-exec` script actually writes to the file and the `output` reads it correctly. Also, ensure the `depends_on` is correct if the output is used in a different module.

T8 — Medium: `terraform import` (or `tofu import`) populates the state with existing infrastructure without creating new resources. Limitations: It requires knowing the exact resource ID and type; it doesn't handle complex dependencies automatically. The `import` block (1.5+) allows defining import logic within the configuration, making it declarative and reusable across runs, rather than a one-off CLI command.

T9 — Easy: A variable is an input value passed to a module or configuration. Input variables are defined in `variable` blocks and passed in. Output values are defined in `output` blocks and returned from a module or configuration.

T10 — Easy: A provider is a plugin that interacts with a cloud API (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, OpenTofu will fail because it cannot download the necessary provider plugins and initialize the working directory.

T11 — Easy: `.terraform.lock.hcl` is a lock file that records the exact versions of providers used. It should be committed to version control to ensure consistency across environments and prevent "dependency hell" where different machines use different provider versions.

T12 — Easy: `tofu destroy` removes all resources defined in the configuration. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

T13 — Easy: A data source fetches existing data from a provider (e.g., `aws_ami`). Use a data source when you need to read information about existing resources (like finding an AMI ID) rather than creating a new one.

T14 — Medium: `locals` are computed values within a module that are not inputs or outputs. Use `locals` for derived values (e.g., concatenating strings, calculating IDs) to avoid passing complex values as inputs or creating circular dependencies.

T15 — Medium: The `lifecycle` block controls resource behavior. `create_before_destroy` ensures the new resource exists before the old one is deleted (useful for DBs). `prevent_destroy` stops deletion unless a condition is met (useful for critical resources). `ignore_changes` prevents specific attributes from being updated by drift (useful for immutable attributes managed externally).

T16 — Medium: A `moved` block tells OpenTofu how to map resources from an old address to a new address during a state refresh. It helps refactor code (e.g., renaming a resource) without destroying and recreating the underlying infrastructure.

T17 — Hard: The dependency graph determines execution order. Implicit dependencies are inferred from references (e.g., `aws_instance` referencing `aws_security_group`). Explicit dependencies use `depends_on`. `depends_on` forces a specific order but can reduce parallelism and should be used sparingly because it often indicates a design issue (missing references).

T18 — Hard: Strategies: 1. `tofu plan -refresh-only` to check drift without full plan. 2. `tofu plan -target` to plan specific resources. 3. Use `tofu state list` to identify unused resources. 4. Split large modules into smaller ones. Tradeoffs: Targeting reduces scope but requires manual management; splitting modules increases complexity.

T19 — Hard: State locking prevents concurrent modifications. If a lock isn't released (e.g., crash), the state is locked indefinitely. To break a lock, manually delete the lock file (e.g., `s3` backend lock file) or use `terraform force_unlock`. Risks: Race conditions, state corruption, or conflicting changes.

T20 — Hard: 1. Create new state file in S3 with DynamoDB locking. 2. Run `tofu state pull` to export current state. 3. Run `tofu state push` to import into new backend. 4. Verify state matches. 5. Run `tofu plan` to ensure no drift. 6. Switch backend in config. 7. Run `tofu apply` to finalize.

A1 — Easy: A playbook is a YAML file defining tasks. A role is a reusable directory structure containing tasks, handlers, and variables. A task is a single unit of work within a playbook or role.

A2 — Easy: `ansible_facts` are variables populated by Ansible during the run (e.g., OS info). Access OS family via `{{ ansible_os_family }}`.

A3 — Medium: `command` runs a command without shell features (no pipes/loops). `shell` runs a command with shell features. `raw` sends the command as-is without interpretation (no shell, no escaping). Use `command` for simple scripts, `shell` for complex logic, `raw` for idempotency or when shell isn't available.

A4 — Medium: Ansible is idempotent by default; running a task multiple times yields the same result. Idempotent: `copy` a file (only copies if different). Not Idempotent: `command: echo "hello"` (runs every time).

A5 — Medium:
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"
  become: yes
- name: Install htop on RedHat
  package:
    name: htop
    state: present
  when: ansible_os_family == "RedHat"
  become: yes
```

A6 — Hard: Priority (High to Low): 1. `extra_vars` (CLI). 2. `host_vars`/`group_vars`. 3. `role_vars` (defaults). 4. `set_fact` (runtime). 5. `defaults` (role defaults).

A7 — Hard: Use `serial: 3` in the playbook to limit concurrent execution. Group the first 3 nodes in a specific group or use `when` conditions. Use `wait_for` to ensure the first 3 nodes are ready before proceeding.

A8 — Medium: `ansible-vault` encrypts files. To encrypt a single variable, use `ansible-vault encrypt_string` and paste the encrypted string into the `vars` file, or use `ansible-vault encrypt_string --vault-password-file` to encrypt a specific line.

A9 — Easy: An inventory file lists hosts and groups. Static inventory is a text file. Dynamic inventory is generated by a script/plugin (e.g., cloud provider API).

A10 — Easy: `ansible all -m disk_usage -a "path=/"` or `ansible webservers -m df -a "path=/`

A11 — Easy: A handler is a task that runs only if notified by another task (e.g., `notify: Restart nginx`). It differs from a regular task which runs immediately. Triggered via `notify` in a task.

A12 — Easy: `ansible.cfg` configures Ansible behavior. Settings: `inventory`, `host_key_checking`, `forks`, `timeout`.

A13 — Easy: `register` stores the output of a task in a variable. Use it in a subsequent task via `{{ registered_var }}`.

A14 — Medium: `include_tasks` is dynamic (evaluated at runtime), allowing conditionals. `import_tasks` is static (evaluated at compile time). Use `include` for conditional logic.

A15 — Medium: Ansible Galaxy is a repository for roles and collections. Use `requirements.yml` to list dependencies and run `ansible-galaxy install -r requirements.yml`.

A16 — Medium: Connection plugins define how Ansible connects to hosts. `ssh` is default for remote hosts. `local` for localhost tasks. `network_cli` for network devices (Cisco, etc.).

A17 — Hard: `delegate_to` runs a task on a different host. `run_once` runs a task only once on the first host. Example: Gather facts on all hosts, then run a task on the control node to process the data.

A18 — Hard: Strategies: 1. Increase `forks`. 2. Enable `pipelining` (reduces SSH overhead). 3. Use `fact_caching` (e.g., `jsonfile`, `redis`). 4. Use `mitogen` (forks processes). Tradeoffs: `forks` increases memory; `pipelining` reduces security (no SSH key check); `mitogen` adds complexity.

A19 — Hard: `{{ }}` for variables, `{% %}` for control structures (if/for), `{# #}` for comments. Snippet:
```jinja
{% for server in backends %}
  upstream {{ server.name }} {
    server {{ server.ip }}:{{ server.port }};
    # Health check: {{ server.health_check }}
  }
{% endfor %}
```

A20 — Hard: 1. `serial: 5` to deploy in batches. 2. Pre-task: Update load balancer config. 3. Deploy app. 4. Post-task: Health check with `uri` module. 5. If health check fails, `rescue` block rolls back (revert LB config). 6. If success, `notify` handler to update LB.
