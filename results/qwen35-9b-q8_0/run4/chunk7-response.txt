AA1 — Easy: A monolith is a single, unified codebase deployed as one unit, while microservices are small, independent services communicating over a network. Three concrete problems microservices introduce that monoliths don't have:
1.  **Distributed Complexity:** Debugging and tracing requests across multiple services is harder than in a single process.
2.  **Data Consistency:** Maintaining ACID transactions across multiple databases is difficult compared to a single database.
3.  **Operational Overhead:** Managing multiple deployment pipelines, monitoring systems, and network configurations adds significant operational burden compared to a single deployment.

AA2 — Easy: Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST, gRPC). Asynchronous communication involves sending a message without waiting for an immediate reply (e.g., Message Queues like RabbitMQ, Kafka). Synchronous is better for real-time interactions; asynchronous is better for decoupling and handling high throughput.

AA3 — Medium: An API Gateway manages business logic, authentication, rate limiting, and aggregation, while a reverse proxy handles traffic routing, SSL termination, and load balancing. An API Gateway cannot replace a reverse proxy entirely because the reverse proxy often operates at Layer 4 (TCP/UDP) for performance and basic routing, whereas the Gateway operates at Layer 7 (HTTP) with application logic. A reverse proxy is needed for raw traffic entry and security hardening before the Gateway.

AA4 — Medium: The Saga pattern manages distributed transactions by breaking them into local transactions within each service. Choreography-based sagas use events to trigger the next step (services react to events), while orchestration-based sagas use a central coordinator to manage the flow. Choreography is appropriate for loosely coupled systems with simple flows; orchestration is better for complex flows requiring strict control and rollback logic.

AA5 — Medium: CQRS separates the model for writing data (Commands) from reading data (Queries). It is often paired with Event Sourcing, which stores state as a sequence of events. This combination solves the problem of read/write performance bottlenecks and schema rigidity in traditional CRUD models, allowing optimized read models and complex query capabilities without impacting write performance.

AA6 — Medium: The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. The three states are Closed (normal operation), Open (fail fast, no calls), and Half-Open (testing recovery). It differs from simple retry with backoff because it stops retrying entirely after a threshold is met, whereas retry keeps trying. They are used together when you want to retry transient errors but fail fast on persistent failures.

AA7 — Hard:
1.  **Shared DB, Shared Schema:** Lowest cost and operational complexity, but highest noisy-neighbor risk and security risk (data leakage).
2.  **Shared DB, Separate Schema:** Moderate cost, better isolation than shared schema, but still shared infrastructure risks.
3.  **Separate DB:** Highest cost and operational complexity, but best security isolation and lowest noisy-neighbor risk.
*Trade-off:* Shared schema is cheap but risky; separate DB is expensive but secure and isolated.

AA8 — Hard: Eventual consistency means data converges over time, while strong consistency guarantees immediate visibility of updates. For an inventory system that must never oversell, strong consistency is required. At scale, use a distributed database with strong consistency guarantees (e.g., CockroachDB, Spanner) or a single-region database with optimistic locking/pessimistic locking. Patterns include distributed transactions (2PC) or optimistic concurrency control with immediate validation.

AA9 — Hard: A sidecar proxy is a process running alongside a service to handle networking. In Istio, Envoy acts as the sidecar. The control plane manages configuration, while the data plane handles actual traffic flow. mTLS between sidecars solves the problem of application-level TLS complexity by offloading encryption/decryption to the proxy, ensuring secure service-to-service communication without modifying application code.

AA10 — Medium: The Strangler Fig pattern involves incrementally replacing parts of a legacy system with new services. Strategy: Identify a specific feature in the .NET Framework monolith. Create a new .NET 8 microservice that handles that feature. Route traffic for that feature to the new service via a reverse proxy or API Gateway. Repeat until the monolith is fully replaced.

AA11 — Medium: The 12-Factor App methodology provides best practices for building cloud-native apps. Six factors:
1.  **Codebase:** One codebase per service.
2.  **Dependencies:** Explicitly declared.
3.  **Config:** Environment-based, not hardcoded.
4.  **Backing Services:** Treat as attached resources.
5.  **Build, Release, Run:** Strict separation.
6.  **Processes:** Stateless.
They matter because they ensure portability, scalability, and ease of deployment in cloud environments.

AA12 — Hard:
*   **Coupling:** Event-driven (Kafka) is looser; Request-driven (REST) is tighter.
*   **Scalability:** Kafka scales better for high throughput; REST scales well for low latency.
*   **Debugging:** REST is easier to debug; Kafka requires tracing events.
*   **Ordering:** Kafka guarantees order per partition; REST guarantees order per request.
*   **Failure:** Kafka decouples failures; REST couples them.
*   **Choice:** Use Kafka for async, decoupled, high-volume data pipelines. Use REST for synchronous, real-time user interactions.

AA13 — Easy: A load balancer distributes traffic across multiple servers. Layer 4 (TCP/UDP) balances based on IP/Port; Layer 7 (HTTP/HTTPS) balances based on content/headers. Layer 7 is required for content-based routing, SSL termination, or URL-based routing (e.g., routing /api to Service A and /static to Service B).

AA14 — Easy: A message queue (RabbitMQ) is typically point-to-point or pub/sub with strict delivery guarantees. A log-based broker (Kafka) is append-only, durable, and optimized for high throughput streaming. Pick RabbitMQ for task queues requiring acknowledgments and routing; pick Kafka for event streaming and log aggregation.

AA15 — Easy: A container packages code and dependencies into a lightweight unit sharing the host OS kernel. A VM includes a full OS kernel. Containers are popular for microservices because they are lightweight, start fast, and ensure consistent environments across development and production.

AA16 — Easy: Stateless services do not store session data locally; stateful services do. Stateless services are easier to scale horizontally because any instance can handle any request. Example: Stateless = API Gateway; Stateful = Database or Session Store.

AA17 — Easy: An ORM maps database tables to object classes. Popular ORMs: Entity Framework (.NET), Hibernate (Java). Trade-offs: ORMs improve productivity and type safety but can lead to performance issues (N+1 problem) and vendor lock-in compared to raw SQL.

AA18 — Medium: The Bulkhead pattern isolates resources to prevent one failure from affecting the whole system. It relates to resource isolation by separating thread pools or deployment groups. Example: Implement separate thread pools for database connections and external API calls so a slow API doesn't exhaust the DB thread pool.

AA19 — Hard: OT transforms operations to resolve conflicts in real-time, while CRDTs use mathematical structures to ensure convergence. CRDTs offer better offline support and eventual consistency without complex transformation logic. For offline editing, CRDTs are preferred because they handle concurrent edits locally and merge seamlessly when connectivity is restored.

AA20 — Hard: Distributed tracing challenges include context propagation (passing trace IDs via headers like W3C Trace Context), sampling (head-based for cost, tail-based for debugging), and storage (Jaeger/Tempo). Tracing interacts with async messaging by embedding trace context in messages. Trace continuity in Kafka is ensured by propagating trace headers in the message metadata or using a sidecar proxy to inject headers into the message.

OP1 — Easy: Type 1 (Bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) run on top of an OS (e.g., VirtualBox, VMware Workstation). Type 1 is for production; Type 2 is for development.

OP2 — Easy: SAN (Storage Area Network) provides block-level storage (e.g., Fibre Channel, iSCSI). NAS (Network Attached Storage) provides file-level storage (e.g., NFS, SMB). Use SAN for databases requiring raw performance; use NAS for file sharing and backups.

OP3 — Medium: 3-tier architecture separates Core (high-speed backbone), Distribution (aggregation), and Access (edge). Leaf-spine is preferred because it provides equal-cost multi-pathing and non-blocking bandwidth, solving the scalability and latency issues of the 3-tier model where traffic must traverse multiple hops.

OP4 — Medium: A Proxmox cluster needs odd node counts (e.g., 3 or 5) for quorum. Use Ceph for shared storage. Fencing (STONITH) prevents split-brain. If a node fails, the cluster detects the failure via heartbeat, removes the node from the cluster, and migrates VMs to remaining nodes.

OP5 — Medium: VLAN trunking allows multiple VLANs over a single link. 802.1Q tags frames with a VLAN ID. On Linux, use `ip link add link eth0 name eth0.10 type vlan id 10` for each VLAN. The server can then assign IPs to these interfaces.

OP6 — Medium: RAID 1 (Mirror), RAID 5 (Striping+Parity), RAID 6 (Striping+2 Parity), RAID 10 (Mirror+Striping), RAID Z2 (ZFS). For 6 drives balancing performance, capacity, and fault tolerance: RAID 10 (4 drives usable, 2 mirrors) or RAID Z2 (ZFS). RAID 10 offers best performance; RAID Z2 offers better capacity efficiency. Choose RAID 10 for database performance.

OP7 — Hard: DNS architecture requires internal recursive resolvers (e.g., BIND) forwarding to external resolvers. Authoritative servers hold AD zones. Forwarders handle external queries. Conditional forwarding sends internal queries to internal servers. When a laptop moves to VPN, split-horizon DNS ensures internal names resolve to internal IPs while external names resolve to public IPs.

OP8 — Hard: PKI chain: Root CA (trusted) -> Subordinate CA (issues certs) -> End Entity. Root CA is offline for security. CRL lists revoked certs; OCSP checks status in real-time. Templates define cert attributes. Compromised Subordinate CA affects issued certs only; Compromised Root CA invalidates all certs in the chain.

OP9 — Hard: MPLS is reliable but expensive. IPsec VPN is cheap but relies on internet quality. SD-WAN optimizes traffic paths. WireGuard is a modern, secure mesh protocol. For 50 users with latency-sensitive VoIP, SD-WAN or WireGuard mesh is recommended for low latency and cost-effectiveness compared to MPLS.

OP10 — Medium: iDRAC/iLO/IPMI are out-of-band management interfaces. Critical for remote management during OS failure. If exposed to the internet, it creates a massive security risk allowing attackers to control hardware directly.

OP11 — Medium: LVM manages physical volumes; LVM-Thin allows over-provisioning; ZFS provides file system features and snapshots. Use LVM for simple VM storage; LVM-Thin for VMs needing snapshots; ZFS for file servers requiring data integrity. Snapshots: LVM is copy-on-write; ZFS is copy-on-write with checksums.

OP12 — Hard: A stretch cluster requires geographically separated sites. Ceph CRUSH rules determine data placement. Monitor placement must be distributed. Network latency must be low (<10ms). 2-site Ceph is bad without a tiebreaker because a network partition can cause split-brain, leading to data corruption or loss.

OP13 — Easy: DHCP assigns IP addresses. DORA: Discover, Offer, Request, Acknowledge. If the server is unavailable, the client uses APIPA (169.254.x.x). When a lease expires, the client attempts renewal; if unavailable, it must reboot or reconfigure.

OP14 — Easy: Managed switches allow configuration (VLANs, QoS); unmanaged switches are plug-and-play. Managed switches provide VLANs, port mirroring, and QoS, which are critical for enterprise traffic segmentation and prioritization.

OP15 — Easy: NTP synchronizes time. Accurate time is critical for logging, authentication (Kerberos), and database replication. Clock drift can cause authentication failures, log correlation issues, and replication conflicts.

OP16 — Easy: Physical server = bare metal; VM = OS on hardware; Container = App + libs on OS. Run workloads on bare metal for maximum performance (e.g., HPC, high-frequency trading) where OS overhead is unacceptable.

OP17 — Easy: UPS provides immediate backup power; generators provide long-term power. You need both because UPS bridges the gap until the generator starts. ATS switches power between utility and generator automatically.

OP18 — Medium: Active-passive has one standby; active-active handles load on both. For PostgreSQL with Pacemaker/Corosync: Configure two nodes with shared storage or streaming replication. Use fencing (STONITH) to prevent split-brain. Virtual IPs float to the active node. Failover occurs when the active node fails and the standby takes the VIP.

OP19 — Hard: 3-2-1 rule: 3 copies, 2 media types, 1 offsite. RPO (Recovery Point Objective) is data loss tolerance; RTO (Recovery Time Objective) is downtime tolerance. Types: Full (complete), Incremental (changes since last), Differential (changes since last full). Deduplication saves space. Immutable backups prevent ransomware. Backup is data protection; DR is system restoration.

OP20 — Hard: 802.1X uses Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP-TLS uses certificates; PEAP uses passwords. RADIUS validates credentials. Dynamic VLAN assigns ports to VLANs based on auth. Failed auth blocks traffic. MAB (MAC Authentication Bypass) allows devices without supplicants (printers) to authenticate via MAC address.
