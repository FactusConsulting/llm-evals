## Cloud Infrastructure Architecture

**CL1** — **IaaS** (Infrastructure as a Service): Raw compute, storage, and networking. You manage the OS and above. *Example: AWS EC2.* **PaaS** (Platform as a Service): Managed runtime/framework. You manage the code. *Example: Azure App Service.* **SaaS** (Software as a Service): Fully managed application. You manage configuration/data. *Example: Microsoft 365.*

**CL2** — **Shared Responsibility Model**: The provider manages the "security *of* the cloud"; the user manages "security *in* the cloud."
*   **IaaS VMs**: Provider: Physical hardware/hypervisor. User: Guest OS, patching, apps, firewall rules.
*   **Managed K8s (EKS/AKS)**: Provider: Control plane (API server, etcd). User: Worker node OS (usually), pod security, network policies.
*   **SaaS (M365)**: Provider: Application, infrastructure, OS. User: Identity/Access management, data classification.

**CL3** — **VPC**: A private isolated network. **Subnet**: A range of IP addresses within a VPC. **Security Group (SG)**: A virtual firewall for an instance (stateful). **NACL**: A firewall for a subnet (stateless).
*   **Layering**: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Instance $\rightarrow$ SG.
*   **Stateful (SG)**: Remembers requests; if you allow inbound on port 80, the return traffic is automatically allowed.
*   **Stateless (NACL)**: Does not remember; you must explicitly define both inbound and outbound rules.

**CL4** — **Multi-account Strategy**:
*   **Landing Zone**: A pre-configured environment with baseline security/networking.
*   **OUs**: Logical groupings of accounts (e.g., Prod, Dev, Shared Services).
*   **Guardrails**: Service Control Policies (SCPs) that set maximum permission boundaries.
*   **Shared Networking**: Transit Gateway (AWS) or Hub-and-Spoke (Azure) centralizes egress/ingress and connects VPCs.
*   **Centralized Logging**: Aggregating all CloudTrail/Activity logs into a dedicated security account.
*   **Single-account problem**: Blast radius (one compromise affects everything), billing chaos, and quota limits.

**CL5** — **IaC**: Managing infrastructure via machine-readable files.
*   **Terraform/OpenTofu**: Cloud-agnostic, HCL-based, state-file driven. Best for multi-cloud.
*   **Pulumi**: Uses general languages (TS, Python). Best for developers who want loops/logic.
*   **CloudFormation/Bicep**: Cloud-specific. Best for deep integration with AWS/Azure native features.
*   **Crossplane**: K8s-native IaC. Best for managing infra as K8s resources.

**CL6** — **Autoscaling**:
*   **HPA**: Scales pods based on CPU/RAM.
*   **VPA**: Adjusts pod resource requests/limits.
*   **Cluster Autoscaler**: Adds/removes physical nodes to the cluster.
*   **KEDA**: Event-driven scaling (e.g., scale based on RabbitMQ queue length).
*   **KEDA vs HPA**: Use KEDA when scaling depends on external metrics (Kafka, Prometheus) rather than just internal resource usage.

**CL7** — **DR Strategy**:
*   **RPO (Recovery Point Objective)**: Max acceptable data loss. **RTO (Recovery Time Objective)**: Max acceptable downtime.
*   **Active-Active**: Traffic split across regions; zero downtime. **Active-Passive**: Failover to secondary region.
*   **Replication**: Sync (zero data loss, high latency) vs Async (potential data loss, low latency).
*   **Failover**: Route53/Traffic Manager uses health checks to redirect DNS.
*   **Tiers**: **Pilot Light** (DB mirrored, apps off) $\rightarrow$ **Warm Standby** (Scaled down apps running) $\rightarrow$ **Multi-site** (Full capacity in both).

**CL8** — **GitOps**: Using Git as the single source of truth for infra/apps.
*   **ArgoCD**: Pull-based, strong UI, manages multiple clusters.
*   **FluxCD**: Pull-based, lightweight, focuses on automation/simplicity.
*   **Secrets**: Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift**: GitOps controllers detect the difference between Git and the cluster; they either auto-overwrite the manual change or alert the admin.

**CL9** — **Stateful K8s Design**:
*   **StatefulSet**: Ensures stable network IDs and ordered deployment.
*   **PV/PVC**: Local Storage Class for low-latency disk access.
*   **Headless Service**: Provides DNS for individual pods (pod-0, pod-1).
*   **Init Containers**: Handle filesystem setup or config downloads before the app starts.
*   **ConfigMaps**: Mounted as volumes to specific paths.
*   **PDB**: Ensures a minimum number of pods remain available during maintenance.

**CL10** — **Identity**:
*   **Service Account**: K8s-internal identity for pods.
*   **Workload Identity/IRSA**: Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Bad Practice**: Mounting static JSON keys in pods is a security risk (leakage, rotation difficulty).
*   **Federation**: Allows the cloud provider to trust the K8s cluster's identity provider, issuing short-lived tokens automatically.

**CL11** — **Storage**:
*   **Object (S3/Blob)**: Unstructured data, highly durable, accessed via API. Use for backups/media.
*   **Block (EBS/Managed Disk)**: Low-latency, attached to one VM. Use for OS disks/DBs.
*   **File (EFS/Azure Files)**: Shared network filesystem (NFS/SMB). Use for shared app configs/home dirs.
*   **Durability**: Object storage is typically the highest (99.999999999%).

**CL12** — **Zero Trust K8s**:
*   **Network Policies**: L3/L4 isolation (deny-all by default).
*   **Service Mesh (Istio/Linkerd)**: mTLS for encrypted pod-to-pod communication.
*   **Admission Controllers**: OPA/Kyverno to enforce policies (e.g., "no root containers").
*   **Runtime**: Falco for anomaly detection (e.g., "shell opened in pod").
*   **Difference**: Traditional security relies on a "hard shell" (perimeter); Zero Trust assumes the network is compromised and verifies every single request.

**CL13** — **CDN**: A distributed network of edge servers that cache content closer to users.
*   **Services**: CloudFront, Akamai.
*   **Use Case**: Use a CDN for static assets (JS, CSS, Images) to reduce latency and origin server load. Serve directly from origin only for dynamic, user-specific content.

**CL14** — **AZs/Regions**:
*   **Region**: A geographic area (e.g., us-east-1). **AZ**: One or more isolated data centers within a region.
*   **Multi-AZ**: Protects against a single DC failure.
*   **Zonal**: Resource exists in one AZ. **Regional**: Resource is replicated across AZs (e.g., S3, DynamoDB).

**CL15** — **Managed DB**: RDS/Cloud SQL.
*   **Provider handles**: Hardware, OS patching, automated backups, failover/replication, and scaling.
*   **User handles**: Database schema, query optimization, and user access control.

**CL16** — **IAM**:
*   **Users**: Individual people. **Groups**: Collections of users. **Roles**: Temporary identities assumed by users/services. **Policies**: JSON documents defining permissions.
*   **Least Privilege**: Granting only the minimum permissions required to perform a task. Apply by using granular policies instead of `AdministratorAccess`.

**CL17** — **Serverless**: Event-driven compute (Lambda/Functions).
*   **Cold Start**: Latency when a function is invoked after being idle (provider must spin up a container).
*   **Poor Fit**: Long-running processes (timeouts), heavy CPU/RAM requirements, or apps requiring constant WebSocket connections.

**CL18** — **Ingress**:
*   **Ingress Resource**: Basic L7 routing (host/path).
*   **Gateway API**: Modern, role-based, more expressive (header-based routing).
*   **LB Annotations**: Cloud-specific tweaks (e.g., AWS ALB settings).
*   **Mesh Gateway**: Advanced traffic splitting/canary deployments.
*   **TLS**: Terminated at the LB (Edge) or at the Mesh sidecar (End-to-End). Use Gateway API for complex, multi-team routing requirements.

**CL19** — **Cost Optimization**:
*   **Commitments**: Reserved Instances (RI) or Savings Plans for predictable workloads.
*   **Spot/Preemptible**: Use for fault-tolerant, stateless workloads (up to 90% cheaper).
*   **Storage**: S3 Intelligent-Tiering moves data to cheaper tiers based on access patterns.
*   **FinOps**: Implement tagging for "showback" (who spent what) and "chargeback" (billing teams).
*   **Tools**: AWS Cost Explorer, Kubecost for K8s.

**CL20** — **Multi-Cloud**:
*   **Abstraction**: Use Kubernetes as the common runtime and Terraform for portable IaC.
*   **Networking**: Site-to-Site VPN or dedicated interconnects (DirectConnect/ExpressRoute).
*   **Identity**: Use OIDC/SAML federation to avoid duplicating users.
*   **Trade-offs**: Theoretical benefit is no lock-in; real-world cost is massive complexity and "lowest common denominator" feature usage. Justified for extreme regulatory requirements or critical availability.

## OT Infrastructure Architecture

**OT1** — **Purdue Model**: A structural model for ICS security.
*   **Level 0**: The physical process (sensors, actuators).
*   **Level 1**: Basic Control (PLCs, PID controllers).
*   **Level 2**: Supervisory Control (HMIs, SCADA).
*   **Level 3**: Site-wide Operations (Historians, Site Engineering).
*   **Level 4**: Enterprise/Business Network (ERP, Email).

**OT2** — **IT vs OT**: IT prioritizes Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability. OT prioritizes Availability $\rightarrow$ Integrity $\rightarrow$ Confidentiality.
*   **Patching**: OT systems cannot be patched like IT because a reboot could stop a physical process, causing safety risks or equipment damage. Patching requires scheduled maintenance windows.

**OT3** — **IDMZ**: A buffer zone between IT (L4) and OT (L3).
*   **Traffic**: Only specific, proxied traffic (e.g., data to a historian) should cross.
*   **Direction**: L3 $\rightarrow$ L4 (Push data). L4 $\rightarrow$ L3 should be strictly controlled via jump hosts.
*   **Danger**: Direct L4 $\rightarrow$ L1 connectivity allows a compromised office laptop to directly stop a PLC, potentially causing physical catastrophe.

**OT4** — **Protocols**:
1. **Modbus TCP**: L1/L2 (Simple, unauthenticated).
2. **OPC UA**: L2/L3 (Secure, object-oriented, cross-vendor).
3. **EtherNet/IP**: L1/L2 (Common in Rockwell/Allen-Bradley).
4. **PROFINET**: L1/L2 (Real-time, common in Siemens).
5. **MQTT**: L3/Cloud (Lightweight pub/sub for IoT).

**OT5** — **Data Diode vs Firewall**:
*   **Firewall**: Software-based, bidirectional, can be misconfigured.
*   **Data Diode**: Hardware-based, physically allows light/data to move in one direction only.
*   **Limitation**: Diodes cannot receive acknowledgments (TCP handshakes), requiring specialized protocols or UDP.

**OT6** — **Data Flow**: PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Plant Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Boundaries**: Firewall between L3 and IDMZ; Data Diode or strict Firewall between IDMZ and Cloud.

**OT7** — **IEC 62443**:
*   **Zone**: A group of assets with similar security requirements.
*   **Conduit**: The communication path between zones.
*   **Design**: Zone 1 (SIS - isolated), Zone 2 (PLCs), Zone 3 (SCADA/HMI), Zone 4 (Engineering), Zone 5 (IDMZ), Zone 6 (Corporate).

**OT8** — **Segmentation Strategy**:
*   **VLANs**: Separate each production line into its own VLAN.
*   **Firewalls**: Place an Industrial Firewall between L2 and L3.
*   **Remote Access**: VPN $\rightarrow$ MFA $\rightarrow$ Jump Host in IDMZ.
*   **Transition**: Build the new segmented network in parallel; migrate one line at a time during planned outages to avoid production stops.

**OT9** — **SIS vs BPCS**:
*   **BPCS**: Maintains the process (e.g., keeps temperature at 100C).
*   **SIS**: Safety Instrumented System; triggers emergency shutdown if BPCS fails (e.g., vents pressure at 150C).
*   **IEC 61511**: The standard for functional safety.
*   **Isolation**: SIS must be isolated so a BPCS failure or cyber attack cannot disable the safety "brake." Ransomware in SIS could prevent a plant from shutting down during a disaster.

**OT10** — **PLC vs DCS vs SCADA**:
*   **PLC**: Local, fast, logic-based control of a specific machine.
*   **DCS**: Integrated system for a whole plant (centralized control).
*   **SCADA**: Wide-area monitoring and control (e.g., pipelines, power grids).
*   **Coexistence**: Yes; SCADA often gathers data from multiple PLCs and DCSs.

**OT11** — **Remote Access**:
*   **Architecture**: Corporate VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (IDMZ) $\rightarrow$ Target HMI.
*   **Controls**: Session recording, time-limited access, and approval workflows.
*   **RDP Danger**: Direct RDP allows lateral movement and lacks the auditing/control needed for critical infrastructure.

**OT12** — **Detection & Response**:
*   **Detection**: Use passive IDS (e.g., Dragos, Nozomi) to find anomalies without polling.
*   **Response**: Isolate the L3 network from L4. Verify PLC integrity via checksums.
*   **Coordination**: The plant operator has final say on isolation to ensure the process remains in a "safe state."
*   **Operator Role**: Ensures that cybersecurity actions don't cause a physical safety incident.

**OT13** — **HMI vs Engineering Station**:
*   **HMI**: A dashboard for operators to monitor and control the process in real-time.
*   **Engineering Station**: A specialized PC used to program the PLC logic and configure the system.

**OT14** — **Historian**: A time-series database for process data.
*   **Plant Historian (L3)**: High-resolution, raw data for local troubleshooting.
*   **Enterprise Historian (L4)**: Aggregated, filtered data for business reporting/KPIs.

**OT15** — **Ladder Logic**: A graphical language mimicking electrical relay circuits, executed by PLCs.
*   **Dominance**: It is intuitive for electricians/technicians and highly deterministic/reliable.

**OT16** — **RTU vs PLC**:
*   **RTU**: Designed for wide-area, remote sites (e.g., a pump station 10 miles away), often with low power and integrated telemetry.
*   **PLC**: Designed for high-speed, local control within a factory.

**OT17** — **Analog vs Digital**:
*   **Digital**: On/Off (0 or 1).
*   **Analog**: Continuous range (e.g., 4-20mA).
*   **4-20mA**: Preferred because 0mA indicates a broken wire (fail-safe), whereas 0-20mA cannot distinguish between a "zero" reading and a cut cable.

**OT18** — **Asset Inventory**: You cannot protect what you don't know.
*   **Passive**: Mirroring traffic (SPAN) to identify devices by their packets.
*   **Active**: Sending queries to devices.
*   **Danger**: Active scanning can crash old PLCs that cannot handle unexpected TCP packets or high volumes of requests.

**OT19** — **MITRE ATT&CK for ICS**:
*   **Tactics**: 1. Initial Access (e.g., Engineering Workstation), 2. Persistence (e.g., PLC Firmware), 3. Impair Process Control (e.g., Modify Parameter), 4. Inhibit Response (e.g., Disable Alarm), 5. Discovery (e.g., Network Scanning).
*   **Difference**: Focuses on physical impact (e.g., "Loss of Control") rather than just data theft.

**OT20** — **Converged SOC**:
*   **Collection**: Use passive TAPs/SPAN ports to send traffic to a SIEM without adding latency.
*   **Staffing**: IT analysts handle the "how" (network alerts); OT engineers handle the "what" (process impact).
*   **Firmware Alert**: Treat as a Critical Incident. Immediately verify the physical state of the PLC and compare the running hash against the known-good baseline.
