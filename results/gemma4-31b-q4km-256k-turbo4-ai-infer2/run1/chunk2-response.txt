## Kubernetes

**K1 — Easy:** A **Deployment** is for stateless applications; pods are interchangeable and have no unique identity. A **StatefulSet** is for stateful applications; pods have a stable, ordinal index (e.g., `pod-0`, `pod-1`) and stable network identities, ensuring persistent storage is attached to the same pod across restarts.

**K2 — Easy:** A **ClusterIP** service creates a virtual IP. When a request hits this IP, `kube-proxy` (using iptables or IPVS) intercepts the traffic and load-balances it across the set of healthy Pod IPs listed in the Service's **Endpoints** object.

**K3 — Medium:** 
- **PersistentVolume (PV):** A piece of storage in the cluster (the actual "disk").
- **PersistentVolumeClaim (PVC):** A request by a user for storage of a specific size and access mode.
- **StorageClass (SC):** A "template" that allows for dynamic provisioning of PVs.
**Relation:** A user creates a PVC $\rightarrow$ Kubernetes looks for a matching PV or uses a StorageClass to automatically create a PV $\rightarrow$ The PVC binds to the PV.

**K4 — Medium:** 
1. `kubectl logs <pod>`: Check for application crashes or stack traces.
2. `kubectl describe pod <pod>`: Check "Events" for OOMKilled, failed probes, or scheduling issues.
3. Check **Liveness/Readiness probes**: Ensure the app isn't being killed because it takes too long to start.
4. Check **Resource Limits**: Verify if the pod is hitting memory limits (OOMKilled).

**K5 — Medium:** **CoreDNS** provides service discovery. It allows pods to resolve service names (e.g., `my-svc.default.svc.cluster.local`) to IPs. If CoreDNS pods are down, pods cannot resolve internal services or external domains, causing application failures.

**K6 — Hard:** The scheduler uses a two-step process:
1. **Filtering (Predicates):** Removes nodes that don't meet requirements (e.g., insufficient CPU/RAM, Taints, NodeSelector).
2. **Scoring (Priorities):** Ranks remaining nodes to find the "best" fit.
**Factors:** Resource availability (least requested), Node Affinity/Anti-affinity, and Pod Topology Spread Constraints.

**K7 — Hard:** 
- **Scheduling:** Yes. Total requested on node is $3.5\text{GB} + 256\text{Mi} \approx 3.75\text{GB}$, which is less than the $4\text{GB}$ capacity.
- **Runtime:** If it uses $600\text{Mi}$, it exceeds its `limits.memory` ($512\text{Mi}$). The kernel will trigger an **OOMKill**, and the pod will be restarted.

**K8 — Hard:** 
External LB $\rightarrow$ Ingress Controller (NGINX Pod) $\rightarrow$ Ingress Rules (Host/Path) $\rightarrow$ Service $\rightarrow$ Endpoints (Pod IPs) $\rightarrow$ Pod. 
The Ingress Controller bypasses the Service's virtual IP and routes traffic directly to the **Endpoints** (Pod IPs) to avoid an extra hop, while `kube-proxy` manages the underlying network rules.

**K9 — Medium:** A **NetworkPolicy** is an L3/L4 firewall for pods. 
- **Default:** If no policy exists, all traffic is allowed.
- **Applying one:** Once a policy selects a pod, that pod becomes "isolated." Only traffic explicitly allowed by the policy is permitted; all other traffic is denied.

**K10 — Medium:** 
- **RollingUpdate:** Gradually replaces old pods with new ones (zero downtime).
- **Recreate:** Kills all old pods before starting new ones (downtime).
**Choose Recreate** when the application cannot handle two different versions of the app running simultaneously (e.g., a database schema migration).

**K11 — Easy:** A **Namespace** provides logical isolation within a cluster. Default namespaces: `default`, `kube-system` (system components), `kube-public` (publicly visible), and `kube-node-lease` (heartbeats).

**K12 — Easy:** `kubectl describe pod` provides detailed metadata. It shows: 
1. **Events** (e.g., Pulling image, Failed scheduling).
2. **Container State** (Exit codes, restart counts).
3. **Volume Mounts** and specific resource requests/limits.

**K13 — Easy:** A **ConfigMap** stores non-confidential configuration. Consumption methods:
1. **Environment Variables:** Injected into the container process.
2. **Volume Mount:** Mounted as files in a directory.

**K14 — Easy:** 
- **ClusterIP:** Internal only.
- **NodePort:** Exposes service on a static port on every Node IP.
- **LoadBalancer:** Provisions a cloud provider LB that routes to NodePorts.

**K15 — Easy:** A **DaemonSet** ensures one copy of a pod runs on every node (or a subset of nodes). Use it for infrastructure services like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium:** 
- **Taints (Node):** Repel pods. (e.g., Taint a node as "GPU" so only GPU-compatible pods land there).
- **Tolerations (Pod):** Allow pods to ignore taints.
- **Node Affinity (Pod):** Attract pods to specific nodes. (e.g., "Prefer nodes in zone-us-east-1a").

**K17 — Medium:** An **Operator** is a custom controller using **Custom Resource Definitions (CRDs)** to manage complex applications. While a standard controller manages basic K8s objects, an Operator encodes "operational knowledge" (e.g., how to backup a DB or perform a failover) into code.

**K18 — Hard:** etcd uses the **Raft** consensus algorithm. 
- **Quorum:** Requires $(n/2)+1$ nodes. If quorum is lost, the cluster becomes read-only or unavailable.
- **Recovery:** If 2/3 nodes are lost, you must restore from a backup snapshot on a new cluster or a single remaining node.

**K19 — Hard:** 
- **Role/RoleBinding:** Namespace-scoped.
- **ClusterRole/ClusterRoleBinding:** Cluster-wide.
**Manifests:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: dev, name: pod-reader }
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: dev, name: dev-user-binding }
subjects: [{ kind: User, name: "developer", apiGroup: rbac.authorization.k8s.io }]
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
```

**K20 — Hard:** `ndots:5` means the resolver tries all search paths in `/etc/resolv.conf` before trying the absolute domain. This causes multiple failed queries for external domains. 
**Fix:** Set `dnsConfig` in the pod spec to `ndots: 1` or use a Fully Qualified Domain Name (ending with a dot, e.g., `google.com.`).

## Development

**D1 — Easy:** **Merge** combines branches and creates a merge commit, preserving history. **Rebase** rewrites history by moving the base of a branch to a new commit, creating a linear timeline. **Avoid rebasing** on public/shared branches as it rewrites history and breaks other developers' clones.

**D2 — Easy:** **TCP** is connection-oriented, reliable, and ordered (HTTP, SSH). **UDP** is connectionless, faster, and allows packet loss (DNS, VoIP).

**D3 — Medium:** A **race condition** occurs when the outcome depends on the non-deterministic timing of multiple threads accessing shared data. 
**Example:** Two threads incrementing a shared variable `count++`. Both read `10`, both increment to `11`, and both write `11` back, losing one increment.

**D4 — Medium:** **Symmetric:** One key for both encryption/decryption. **Asymmetric:** Public key encrypts, private key decrypts. 
**TLS:** Uses asymmetric encryption to securely exchange a symmetric session key, which is then used for the actual data transfer (for performance).

**D5 — Medium:** A **layer** is a read-only snapshot of a filesystem change. Docker caches layers; if a line in the Dockerfile hasn't changed, Docker reuses the cached layer. **Best practice:** Put stable instructions (OS, dependencies) at the top and frequently changing code at the bottom.

**D6 — Medium:** 
1. **LB/Ingress Logs:** Check for timeouts or 503s from the backend.
2. **Pod Health:** Check for restarts or OOMKills.
3. **Resource Saturation:** Check CPU/RAM usage on the pods.
4. **Downstream Dependencies:** Check if a database or external API is timing out.

**D7 — Hard:** **CAP Theorem:** A distributed system can only provide two of Consistency, Availability, and Partition Tolerance.
- **CP (Consistency/Partition):** MongoDB/etcd (will stop accepting writes if quorum is lost).
- **AP (Availability/Partition):** Cassandra/DynamoDB (will accept writes and resolve conflicts later).

**D8 — Medium:** **Horizontal:** Adding more machines (scaling out). **Vertical:** Adding more CPU/RAM to one machine (scaling up). 
**Patterns:** Statelessness (no local session state), Load Balancing, and Database Sharding.

**D9 — Easy:** An **environment variable** is a dynamic value available to a process. To persist on Linux, add `export VAR=value` to `~/.bashrc` or `~/.profile`.

**D10 — Easy:** **JSON** is strict and fast for machines. **YAML** is human-readable and supports comments. 
- **JSON Advantage:** Ubiquitous, strict parsing.
- **YAML Advantage:** Easier to write/read by humans.

**D11 — Easy:** **REST** is an architectural style for network APIs.
- **GET:** Retrieve resource.
- **POST:** Create resource.
- **PUT:** Update/Replace resource.
- **DELETE:** Remove resource.

**D12 — Easy:** **Version pinning** is specifying an exact version of a dependency (e.g., `requests==2.25.1`). It prevents "breaking changes" from being introduced automatically during a build, ensuring reproducibility.

**D13 — Easy:** **Compiled:** Translated to machine code before execution (C++, Rust). **Interpreted:** Executed line-by-line by a runtime (Python, JavaScript).

**D14 — Medium:** A **Forward Proxy** acts on behalf of the client (hides client). A **Reverse Proxy** acts on behalf of the server (hides server).
- **NGINX:** Reverse proxy for load balancing.
- **Squid:** Forward proxy for caching/filtering web traffic.

**D15 — Medium:** A **deadlock** is a state where two or more threads are blocked forever, each waiting for the other to release a resource. 
**Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** **Eventual Consistency** means that if no new updates are made, all reads will eventually return the last updated value. 
**Cassandra:** Uses tunable consistency. `ONE` (fast, low consistency), `QUORUM` (majority of nodes must agree), `ALL` (all nodes must agree, highest consistency).

**D17 — Hard:** **mTLS** requires both client and server to present certificates. 
**Handshake:** Server sends cert $\rightarrow$ Client verifies server $\rightarrow$ Client sends its own cert $\rightarrow$ Server verifies client $\rightarrow$ Session key established. 
**Usage:** Common in Service Meshes (Istio/Linkerd) for zero-trust security.

**D18 — Hard:** A **Hash Table** uses a hash function to map keys to array indices. 
- **Collision Resolution:** **Chaining** (linked lists at each index) or **Open Addressing** (finding the next empty slot).
- **Complexity:** Average: $O(1)$ for all. Worst: $O(n)$ if all keys hash to the same index.

**D19 — Hard:** A **Circuit Breaker** prevents a failing service from crashing the whole system.
- **Closed:** Normal operation.
- **Open:** Service is failing; requests fail immediately without hitting the backend.
- **Half-Open:** Periodically tests if the service has recovered.
**Relation:** It prevents "cascading failures"; **exponential backoff** ensures the service isn't hammered immediately upon recovery.

**D20 — Hard:** 
- **Optimistic:** Assumes no conflict; checks for a version change at commit time (e.g., MVCC in PostgreSQL). Use for low-contention environments.
- **Pessimistic:** Locks the resource immediately (e.g., `SELECT FOR UPDATE` in SQL). Use for high-contention environments where conflicts are frequent.
