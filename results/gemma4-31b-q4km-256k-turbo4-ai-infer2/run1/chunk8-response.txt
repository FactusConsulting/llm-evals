## Cloud Infrastructure Architecture

**CL1 — Easy:** 
*   **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing the underlying OS. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Fully managed software delivered via web/API. *Example: Microsoft 365.*

**CL2 — Easy:** 
The Shared Responsibility Model defines who is responsible for security.
*   **IaaS VMs:** Provider handles physical hardware/hypervisor; you handle OS patching, firewall, and data.
*   **Managed Kubernetes (EKS/GKE):** Provider handles the Control Plane; you handle worker node configuration, pod security, and network policies.
*   **SaaS (M365):** Provider handles almost everything (infrastructure, app, OS); you handle identity/access management and the data you put in.

**CL3 — Medium:** 
*   **VPC:** An isolated virtual network.
*   **Subnet:** A range of IP addresses in a VPC (Public or Private).
*   **Security Group (SG):** A stateful firewall at the instance/NIC level.
*   **NACL:** A stateless firewall at the subnet level.
*   **Layering:** Traffic hits VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group $\rightarrow$ Instance.
*   **Stateful vs Stateless:** Stateful (SG) remembers the request; if you allow inbound on port 80, the return traffic is automatically allowed. Stateless (NACL) requires explicit rules for both inbound and outbound traffic.

**CL4 — Medium:** 
*   **Landing Zone:** A pre-configured, multi-account environment based on best practices.
*   **OU (Organizational Units):** Logical groupings of accounts (e.g., Prod, Dev, Security).
*   **Guardrails:** Service Control Policies (SCPs) that set maximum permission boundaries.
*   **Shared Networking:** Using a Hub-and-Spoke model (Transit Gateway/Azure Virtual WAN) to centralize egress/ingress and connect VPCs.
*   **Centralized Logging:** Aggregating all CloudTrail/Activity logs into a dedicated security account.
*   **Single-account problem:** Blast radius (one compromise affects everything), quota limits, and billing complexity.

**CL5 — Medium:** 
IaC is managing infrastructure via code files.
*   **Terraform/OpenTofu:** HCL-based, provider-agnostic. Best for multi-cloud.
*   **Pulumi:** Uses general-purpose languages (TS, Python). Best for developers who want loops/logic.
*   **CloudFormation/Bicep:** Cloud-specific. Best for deep integration with AWS/Azure.
*   **Crossplane:** K8s-native IaC. Best for managing cloud resources as K8s objects.

**CL6 — Medium:** 
*   **HPA:** Scales pods based on CPU/RAM.
*   **VPA:** Adjusts pod resource requests/limits.
*   **Cluster Autoscaler:** Adds/removes nodes to the cluster.
*   **KEDA:** Event-driven scaling (e.g., scale based on Kafka lag or RabbitMQ queue length).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external events rather than internal resource metrics.

**CL7 — Hard:** 
*   **RPO (Recovery Point Objective):** Max acceptable data loss. **RTO (Recovery Time Objective):** Max acceptable downtime.
*   **Active-Active:** Traffic split across regions; zero RTO. Expensive.
*   **Active-Passive:** Primary region active; secondary on standby.
*   **Replication:** Sync (No data loss, high latency) vs Async (Faster, potential data loss).
*   **DNS Failover:** Route53/Traffic Manager redirects traffic to the healthy region.
*   **DR Types:** 
    *   *Pilot Light:* Core data synced; app servers off.
    *   *Warm Standby:* Scaled-down version of app running.
    *   *Multi-site:* Full capacity in both regions.

**CL8 — Hard:** 
GitOps uses Git as the "Source of Truth." A controller (ArgoCD/Flux) monitors Git and syncs the cluster state.
*   **ArgoCD:** UI-heavy, push/pull, powerful visualization.
*   **FluxCD:** Lightweight, Git-native, focuses on automation.
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM).
*   **Drift:** If a manual change occurs, the GitOps controller detects the difference and automatically overwrites the manual change to match Git.

**CL9 — Hard:** 
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC:** Use a `local` storage class for low-latency disk access.
*   **Headless Service:** Provides DNS entries for individual pods (e.g., `pod-0.service.ns`).
*   **Init Containers:** Handle filesystem setup or waiting for dependencies.
*   **ConfigMaps:** Mounted as volumes to specific paths.
*   **PDB (Pod Disruption Budget):** Ensures a minimum number of replicas stay available during maintenance.

**CL10 — Medium:** 
*   **Service Account:** An identity for a pod.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Bad Practice:** Mounting static keys (JSON/CSV) in pods leads to credential leakage.
*   **Federation:** The cloud provider trusts the K8s cluster's OIDC provider, issuing short-lived tokens instead of static keys.

**CL11 — Medium:** 
*   **Object (S3/Blob):** Unstructured data, highly durable, accessed via API. Use for backups/media.
*   **Block (EBS/Managed Disk):** Low-latency, attached to one VM. Use for OS disks/DBs.
*   **File (EFS/Azure Files):** Shared network filesystem (NFS/SMB). Use for shared app config/home dirs.
*   **Durability:** Object storage usually offers 99.999999999% (11 9s) durability.

**CL12 — Hard:** 
*   **Network Policies:** L3/L4 isolation (deny-all by default).
*   **Service Mesh (Istio/Linkerd):** mTLS for encrypted pod-to-pod communication.
*   **Admission Controllers:** OPA/Kyverno to enforce policies (e.g., "no root containers").
*   **Runtime:** Falco for anomaly detection (e.g., shell opened in pod).
*   **Image Signing:** Cosign/Notary to ensure only trusted images run.
*   **Difference:** Traditional security relies on a "hard shell" (perimeter); Zero Trust assumes the network is already compromised and verifies every single request.

**CL13 — Easy:** 
A CDN caches content at "Edge Locations" closer to the user.
*   **Services:** CloudFront, Akamai.
*   **Use Case:** Use a CDN for static assets (JS, CSS, Images) to reduce latency and offload traffic from the origin server.

**CL14 — Easy:** 
*   **Region:** A geographic area (e.g., us-east-1).
*   **AZ:** One or more isolated data centers within a region.
*   **Multi-AZ:** Protects against a single DC failure.
*   **Zonal vs Regional:** Zonal resources (e.g., EBS) exist in one AZ; Regional resources (e.g., S3, Lambda) are distributed across the region.

**CL15 — Easy:** 
Managed DBs (RDS/Cloud SQL) automate: patching, backups, hardware scaling, and high availability (failover). You only manage the schema, queries, and indexing.

**CL16 — Easy:** 
*   **Users:** Individual identities. **Groups:** Collections of users. **Roles:** Temporary identities assumed by users/services. **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply by using granular IAM roles instead of `AdministratorAccess`.

**CL17 — Easy:** 
Serverless is event-driven compute where the provider manages scaling and allocation.
*   **Cold Start:** Latency when a function is invoked after being idle (provider must spin up a container).
*   **Poor Fit:** Long-running processes (timeouts), high-memory requirements, or apps requiring constant WebSocket connections.

**CL18 — Medium:** 
*   **Ingress:** Basic L7 routing.
*   **Gateway API:** Modern, role-based API for advanced traffic splitting/canary deployments.
*   **LB Annotations:** Cloud-specific settings (e.g., AWS ALB settings).
*   **Service Mesh:** L7 control via a sidecar (Envoy).
*   **TLS Termination:** Can happen at the LB (offloading), Ingress Controller, or Pod (end-to-end).
*   **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenancy, and better standardization.

**CL19 — Hard:** 
*   **Commitments:** Reserved Instances (RI) or Savings Plans for predictable workloads.
*   **Spot/Preemptible:** Use for fault-tolerant, batch workloads (up to 90% discount).
*   **Right-sizing:** Using tools (AWS Compute Optimizer) to downsize over-provisioned VMs.
*   **Tiering:** S3 Intelligent-Tiering moves data to Archive/Glacier automatically.
*   **FinOps:** Implementing tagging for "showback" (who spent what) and "chargeback" (billing departments).

**CL20 — Hard:** 
*   **Abstraction:** Use Kubernetes as the common runtime and Terraform for IaC.
*   **Networking:** Site-to-Site VPN or Dedicated Interconnect (DirectConnect/ExpressRoute).
*   **Identity:** OIDC/SAML federation so users have one identity across clouds.
*   **Trade-offs:** Theoretical benefit is "no lock-in"; real-world cost is massive operational overhead and "lowest common denominator" feature usage.
*   **Justified:** Regulatory requirements (sovereignty) or extreme availability needs.

## OT Infrastructure Architecture

**OT1 — Easy:** 
The Purdue Model segments industrial networks.
*   **Level 0:** Process (Sensors, Actuators).
*   **Level 1:** Basic Control (PLCs).
*   **Level 2:** Supervisory Control (HMIs, SCADA).
*   **Level 3:** Site Operations (Historians, Site-wide control).
*   **Level 4:** Enterprise/IT (ERP, Business apps).

**OT2 — Easy:** 
IT focuses on Confidentiality; OT focuses on Availability and Safety. You cannot apply standard IT patching because OT systems often require 24/7 uptime, and a patch could crash a PLC, causing physical damage or safety hazards.

**OT3 — Medium:** 
The IDMZ is a buffer zone. Only specific, proxied traffic (e.g., via a Jump Host) should cross. Direct L4 $\rightarrow$ L1 connectivity is dangerous because an IT-side ransomware attack could directly manipulate physical hardware (PLCs).

**OT4 — Medium:** 
1. **Modbus TCP:** L1/L2 (Simple device communication).
2. **OPC UA:** L2/L3 (Standardized data exchange).
3. **EtherNet/IP:** L1/L2 (High-speed control).
4. **PROFINET:** L1/L2 (Real-time industrial Ethernet).
5. **MQTT:** L3/Cloud (Lightweight pub/sub for telemetry).

**OT5 — Medium:** 
*   **Data Diode:** A physical hardware device that allows data to flow in only one direction (physically impossible to send data back).
*   **Firewall:** Software-based rules (bidirectional).
*   **Use Case:** Use a diode for high-security zones (e.g., Nuclear) to ensure no external actor can send commands into the control network.

**OT6 — Medium:** 
Flow: PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Edge Gateway (L3) $\rightarrow$ MQTT Broker (IDMZ) $\rightarrow$ Cloud Ingestion.
*   **Boundaries:** Firewall between L3 and IDMZ; Firewall between IDMZ and L4/Cloud.

**OT7 — Hard:** 
*   **Zone:** A group of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Design:** 
    *   Zone A: SIS (Isolated/Air-gapped).
    *   Zone B: Control (PLCs/HMIs).
    *   Zone C: Supervisory (SCADA/Historian).
    *   Zone D: Corporate (IT).
    *   Conduits: Strictly controlled via firewalls between each zone.

**OT8 — Hard:** 
*   **Segmentation:** Create VLANs per production line.
*   **Architecture:** Use a collapsed core switch with a firewall acting as the gateway between VLANs.
*   **Remote Access:** VPN $\rightarrow$ MFA $\rightarrow$ Jump Host $\rightarrow$ Target.
*   **Transition:** Build the new segmented network in parallel; migrate one line at a time during scheduled maintenance windows.

**OT9 — Hard:** 
*   **BPCS:** Handles normal process control.
*   **SIS:** A separate system that triggers a "safe state" (shutdown) if the BPCS fails.
*   **IEC 61511:** The standard for functional safety.
*   **Isolation:** If ransomware hits the BPCS, the SIS must remain functional to prevent a catastrophic explosion or leak.

**OT10 — Medium:** 
*   **PLC:** Local, fast, logic-based control.
*   **DCS:** Integrated system for complex, large-scale plants.
*   **SCADA:** Wide-area monitoring and control.
*   **Coexistence:** Yes; SCADA often sits on top of DCS and PLCs to provide a plant-wide view.

**OT11 — Medium:** 
Architecture: User $\rightarrow$ VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (Bastion) $\rightarrow$ Target HMI.
*   **Why no direct RDP?** RDP is a common attack vector; direct access allows lateral movement and lacks auditing/session recording.

**OT12 — Hard:** 
*   **Detection:** Deploy passive IDS (e.g., Dragos/Claroty) to detect anomalous Modbus/S7 traffic.
*   **Response:** 1. Isolate L3 from L4. 2. Verify SIS integrity. 3. Use asset inventory to identify compromised nodes.
*   **Operator Role:** The operator is the final authority; they must decide if the process is safe to continue or if a manual emergency shutdown is required.

**OT13 — Easy:** 
*   **HMI:** A screen allowing operators to monitor and control the process.
*   **Difference:** An HMI is for *operation*; an Engineering Workstation is for *programming* and changing the PLC logic.

**OT14 — Easy:** 
A Historian is a time-series database for process data.
*   **Plant Historian (L3):** High-resolution, raw data for local troubleshooting.
*   **Enterprise Historian (L4):** Aggregated data for business reporting and KPIs.

**OT15 — Easy:** 
Ladder Logic is a graphical language used by PLCs. It is dominant because it mimics electrical relay diagrams, making it intuitive for electricians and technicians to troubleshoot.

**OT16 — Easy:** 
*   **RTU:** Designed for wide-area, low-power, remote telemetry (e.g., pipelines).
*   **PLC:** Designed for high-speed, local control (e.g., assembly line).
*   **Environment:** Use RTUs for geographically dispersed assets.

**OT17 — Easy:** 
*   **Analog:** Continuous signal (e.g., 4-20mA). **Digital:** On/Off (0 or 1).
*   **4-20mA vs 0-20mA:** 4mA is the "live zero." If the wire breaks, the signal drops to 0mA, allowing the system to distinguish between a "zero reading" and a "broken wire."

**OT18 — Medium:** 
Asset inventory is the foundation because you cannot protect what you don't know exists.
*   **Passive:** Mirroring traffic (SPAN) to identify devices without touching them.
*   **Active:** Polling devices.
*   **Danger:** Active scanning can crash old PLCs that cannot handle unexpected TCP packets.

**OT19 — Hard:** 
MITRE ATT&CK for ICS focuses on physical impact.
*   **Tactics:** 1. Initial Access (VPN compromise), 2. Execution (PLC logic upload), 3. Persistence (Firmware modification), 4. Impair Process Control (Modify setpoints), 5. Inhibit Response (Disable alarms).
*   **Difference:** IT ATT&CK focuses on data theft; ICS ATT&CK focuses on physical manipulation and safety.

**OT20 — Hard:** 
*   **Collection:** Use passive TAPs/SPAN ports to send logs to a SIEM without impacting real-time traffic.
*   **Staffing:** IT analysts handle the SIEM; OT engineers validate if an alert is a "process anomaly" or a "cyber attack."
*   **Firmware Alert:** 1. Check change logs for authorized maintenance. 2. If unauthorized, isolate the PLC. 3. Compare current firmware hash against a known-good baseline.
