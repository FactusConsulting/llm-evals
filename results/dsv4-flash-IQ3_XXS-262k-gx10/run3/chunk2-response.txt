## Kubernetes

**K1 — Easy:**  
A Deployment manages stateless applications, ensuring desired replicas via ReplicaSets, supports rolling updates and rollbacks. A StatefulSet manages stateful applications, giving each pod a stable identity (ordinal index), stable network hostname, and stable persistent storage per pod. StatefulSets also guarantee ordered startup/shutdown and scaling.

**K2 — Easy:**  
A ClusterIP Service has a stable virtual IP. It selects pods via label selector, and the control plane creates Endpoints (or EndpointSlices) listing pod IPs. kube-proxy on each node programs iptables/IPVS rules to forward traffic destined to the Service IP to a randomly chosen backend pod IP, with load balancing.

**K3 — Medium:**  
- **PersistentVolume (PV):** cluster-level storage resource provisioned by admin or dynamically.  
- **PersistentVolumeClaim (PVC):** a request for storage by a user, bound to a PV.  
- **StorageClass:** defines storage provisioning types (e.g., SSD, NFS) and parameters; enables dynamic provisioning of PVs when a PVC references it.  
They relate: PVC references a StorageClass to dynamically create a PV, or binds to a pre-existing PV; the PV is then mounted into pods via the PVC.

**K4 — Medium:**  
1. Check pod events: `kubectl describe pod` for crash reason and exit code.  
2. Inspect logs: `kubectl logs <pod> --previous` to see last crash logs.  
3. Verify image/command/args and container startup probes.  
4. Check resource limits (OOMKilled) and node resources.  
5. Test connectivity to dependencies (DB, API) and configmaps/secrets.  
6. Run a shell in the container if possible to reproduce.

**K5 — Medium:**  
CoreDNS is the cluster DNS server. It serves DNS records for Services and Pods (e.g., `service.namespace.svc.cluster.local`). If CoreDNS pods are down, internal DNS resolution fails, so Service discovery by name breaks; existing connections may continue but new lookups fail. External DNS also fails unless pods use host DNS or fallback.

**K6 — Hard:**  
The scheduler first filters nodes to those that satisfy resource requests, node selectors, affinity/anti-affinity, taints/tolerations, and other constraints. Then it scores remaining nodes based on factors like:  
- Resource fit (requested vs. allocatable)  
- Node affinity and pod affinity  
- Taints/tolerations  
- Data locality (eact)  
- Inter-pod anti-affinity  
- Node conditions (ready, disk pressure)  
- Spreading across zones  
It picks the highest-scoring node.

**K7 — Hard:**  
The pod will be scheduled because the scheduler only considers requests: 3.5GB + 256Mi = 3.75GB < 4GB. Limits are not used for scheduling. At runtime, if the pod uses 600Mi, it exceeds its memory limit of 512Mi. The kernel will likely OOM-kill the container (or the container may be evicted if node pressure). The pod may enter CrashLoopBackOff if it keeps exceeding limits.

**K8 — Hard:**  
1. Client sends request to external LB (e.g., cloud load balancer) that forwards to the Ingress controller service (NodePort or LoadBalancer).  
2. NGINX Ingress controller pod receives traffic, matches host/path rules from Ingress object.  
3. It forwards to the backend Service’s ClusterIP (or directly to endpoints).  
4. The Service selects pods via Endpoints.  
5. kube-proxy updates iptables rules to route Service IP to pod IPs.  
6. NGINX sends HTTP request to a pod’s IP:port.  
7. Application pod processes and returns response back through the chain.

**K9 — Medium:**  
A NetworkPolicy is a resource that controls traffic to/from pods at the IP/port level. Default behavior: if no NetworkPolicy exists, all traffic is allowed. When you apply a NetworkPolicy that selects certain pods, it isolates those pods and only allows traffic explicitly permitted by the policy (default-deny for non-matching traffic).

**K10 — Medium:**  
RollingUpdate gradually replaces old pods with new ones, keeping the service available. Recreate terminates all old pods before creating new ones, causing downtime. Choose Recreate when the application cannot run multiple versions simultaneously (e.g., database schema migrations that are incompatible) or when downtime is acceptable.

**K11 — Easy:**  
A namespace is a virtual cluster partition for isolating resources. Default namespaces: `default`, `kube-system`, `kube-public`, and `kube-node-lease` (newer clusters).

**K12 — Easy:**  
`kubectl describe pod` shows detailed information including:  
- Events (warnings, scheduling, image pulls)  
- Container status (restart count, state, last termination reason)  
- Node and pod IP, labels, annotations  
- Resource requests/limits  
- Mounts, volumes, tolerations, conditions.

**K13 — Easy:**  
A ConfigMap stores configuration data as key-value pairs. Pods can consume it via:  
1. Environment variables (e.g., `valueFrom.configMapKeyRef`)  
2. Volume mounts (e.g., `volumes` with `configMap` and `items`)  
3. Command-line arguments (via env expansion).

**K14 — Easy:**  
- **ClusterIP:** exposes Service on internal cluster IP, only reachable within cluster.  
- **NodePort:** exposes Service on a static port on each node’s IP, accessible from outside via `NodeIP:NodePort`.  
- **LoadBalancer:** provisions an external load balancer (cloud provider) that routes to NodePort/ClusterIP, providing external access.

**K15 — Easy:**  
A DaemonSet ensures a copy of a pod runs on every node (or selected nodes). Use it for node-level services like logging agents, monitoring agents, or network plugins. A Deployment runs replicas across nodes but not necessarily on every node.

**K16 — Medium:**  
Taints and tolerations restrict which pods can be scheduled on a node: a node has taints, and pods must tolerate them to be scheduled. Node affinity is a preference/requirement to place pods on nodes with specific labels. Use taints/tolerations to dedicate nodes to specific workloads (e.g., GPU nodes) or to prevent scheduling on master nodes. Use node affinity to spread pods across zones or to prefer certain hardware.

**K17 — Medium:**  
A Kubernetes Operator is an application-specific controller that extends the Kubernetes API to manage complex stateful applications (e.g., databases, monitoring). It differs from a standard controller (like a Deployment controller) because it encodes domain knowledge about the application’s lifecycle, upgrades, backups, and failure recovery. It solves the problem of automating operational tasks that are typically manual.

**K18 — Hard:**  
etcd uses the Raft consensus algorithm. It requires a quorum (majority) of nodes to agree on writes and linearizable reads. If quorum is lost (e.g., 2 of 3 etcd nodes are down), the cluster cannot accept writes or consistent reads, so Kubernetes API becomes read-only or unavailable. To recover from permanent loss of 2 of 3 nodes: restore the remaining node from a backup, or add new etcd nodes and rebuild the cluster from backup. If no backup, data is lost.

**K19 — Hard:**  
RBAC uses Roles (namespaced) and ClusterRoles (cluster-wide) to define permissions. RoleBindings bind Roles to subjects (users, groups, ServiceAccounts) within a namespace; ClusterRoleBindings bind ClusterRoles cluster-wide. For a developer needing read-only access to pods and logs in a single namespace:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: dev-pod-reader
subjects:
- kind: User
  name: dev@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:**  
In `/etc/resolv.conf`, `ndots:5` means the resolver will try the domain as-is first if it has fewer than 5 dots? Actually it tries the absolute domain first if the number of dots is >= ndots; otherwise it tries search domains first. For external domains like `example.com` (1 dot), with ndots:5, the resolver first tries `example.com.namespace.svc.cluster.local`, then `example.com.svc.cluster.local`, etc., causing many DNS queries and delays. Fix by setting `dnsConfig` in the pod spec:

```yaml
dnsConfig:
  ndots: 4  # or 3
  searches:
    - default.svc.cluster.local
    - svc.cluster.local
    - cluster.local
```

This reduces search domain attempts.

## Development

**D1 — Easy:**  
`git rebase` rewrites commit history by applying commits onto a new base, creating a linear history. `git merge` creates a merge commit, preserving branch history. Avoid rebasing shared/public branches because it rewrites history and can cause conflicts for other developers.

**D2 — Easy:**  
TCP is connection-oriented, reliable, ordered, with retransmission; UDP is connectionless, unreliable, low-latency. TCP protocols: HTTP, SSH. UDP protocols: DNS, video streaming.

**D3 — Medium:**  
A race condition occurs when multiple threads/processes access shared data concurrently and the outcome depends on timing. Example in Python:

```python
counter = 0
def increment():
    global counter
    temp = counter
    # context switch
    counter = temp + 1
# Two threads call increment() concurrently -> lost update
```

**D4 — Medium:**  
Symmetric encryption uses the same key for encryption/decryption (fast, e.g., AES). Asymmetric uses a public/private key pair (slow, e.g., RSA). In TLS, asymmetric encryption is used to exchange a session key (e.g., via RSA or ECDHE), then symmetric encryption is used for the bulk data transfer.

**D5 — Medium:**  
A container image layer is a filesystem diff created by each Dockerfile instruction. Layers are cached; if a layer hasn’t changed, it can be reused. Best practices: order instructions from least to most frequently changing, combine `RUN` commands, use `.dockerignore`, and use specific base image tags to maximize cache hits.

**D6 — Medium:**  
1. Check server logs for errors and stack traces.  
2. Monitor CPU/memory/disk usage and connection limits.  
3. Check database connection pool and external API dependencies.  
4. Inspect load balancer health checks and auto-scaling events.  
5. Review recent deployments or config changes.  
6. Test with curl and check response headers.

**D7 — Hard:**  
CAP theorem states a distributed data store can only guarantee two of: Consistency, Availability, Partition tolerance. Under network partition, choose consistency or availability. CP example: etcd (or ZooKeeper) — sacrifices availability during partition to maintain consistency. AP example: Cassandra — remains available but may serve stale data.

**D8 — Medium:**  
Horizontal scaling adds more machines/nodes; vertical scaling increases resources of a single machine. Patterns enabling horizontal scaling: stateless services, load balancing, shared storage, distributed databases, message queues, and microservices.

**D9 — Easy:**  
An environment variable is a key-value pair in the process environment. To persist across shell sessions on Linux, add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `/etc/environment`, then source the file.

**D10 — Easy:**  
JSON is a text format for structured data using key-value pairs and arrays; YAML is a human-readable superset that uses indentation. JSON advantage: widely supported, strict parsing. YAML advantage: more readable, supports comments and multi-line strings.

**D11 — Easy:**  
REST API is an architectural style using HTTP methods to manipulate resources. GET retrieves, POST creates, PUT updates/replaces, DELETE removes. They are idempotent (GET, PUT, DELETE) except POST.

**D12 — Easy:**  
Version pinning specifies exact dependency versions (e.g., `package.json` with exact version, `requirements.txt` with `==`). It ensures reproducible builds by preventing unexpected updates that could break code.

**D13 — Easy:**  
Compiled languages are translated to machine code before execution (e.g., C, Go). Interpreted languages are executed line-by-line by an interpreter (e.g., Python, JavaScript).

**D14 — Medium:**  
A reverse proxy sits in front of backend servers, forwarding client requests to them (e.g., Nginx, HAProxy). A forward proxy sits in front of clients, making requests on their behalf (e.g., corporate proxy). Use cases: Nginx for load balancing and TLS termination; HAProxy for high-availability routing.

**D15 — Medium:**  
A deadlock occurs when two or more processes wait indefinitely for resources held by each other. Coffman conditions:  
1. Mutual exclusion  
2. Hold and wait  
3. No preemption  
4. Circular wait.

**D16 — Hard:**  
Eventual consistency means that if no new updates occur, all replicas will eventually converge to the same value. Cassandra offers tunable consistency levels (ONE, QUORUM, ALL) for reads/writes. For read-after-write consistency, use QUORUM for both read and write to ensure the latest value is returned.

**D17 — Hard:**  
mTLS (mutual TLS) is TLS where both client and server present certificates. Handshake:  
1. Client sends `ClientHello`.  
2. Server responds with `ServerHello`, certificate, and requests client certificate.  
3. Client verifies server certificate, sends its certificate and encrypted pre-master secret.  
4. Server verifies client certificate.  
5. Both derive session keys and finish handshake.  
mTLS is used in service meshes (e.g., Istio), zero-trust networks, and API authentication.

**D18 — Hard:**  
A hash table uses a hash function to map keys to indices in an array. Collisions are handled by chaining (linked list at each bucket) or open addressing (probing). Average time complexity: O(1) for insertion, lookup, deletion. Worst-case (many collisions): O(n). Deletion in open addressing requires tombstones.

**D19 — Hard:**  
Circuit breaker pattern prevents repeated calls to a failing service. States:  
- **Closed:** normal operation, calls pass through.  
- **Open:** after failures exceed threshold, calls fail fast without hitting the service.  
- **Half-open:** after a timeout, a few trial calls are allowed; if successful, close; if fail, reopen.  
It relates to retry policies by avoiding immediate retries; exponential backoff increases wait time between retries, while circuit breaker stops retries entirely during open state.

**D20 — Hard:**  
Optimistic concurrency control assumes conflicts are rare; it checks a version/timestamp before committing and aborts if changed. Pessimistic locks resources (e.g., `SELECT FOR UPDATE`) to prevent conflicts. Choose optimistic for read-heavy workloads with low contention; pessimistic for high contention or when conflicts are costly. Example: optimistic uses `version` column and `UPDATE ... WHERE version = ?`; pessimistic uses `SELECT FOR UPDATE` to lock a row.
