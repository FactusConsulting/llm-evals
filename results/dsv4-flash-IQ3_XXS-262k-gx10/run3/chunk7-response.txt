AA1 — Easy:  
A monolith is a single deployable unit where all components (UI, business logic, data access) are tightly coupled. Microservices decompose the system into independently deployable services that communicate over a network. Three concrete problems microservices introduce that monoliths don't have:  
1. **Distributed system complexity** – network latency, partial failures, and the need for service discovery.  
2. **Operational overhead** – deploying, monitoring, and scaling many services requires automation and observability.  
3. **Data consistency** – transactions span services, requiring patterns like Saga or eventual consistency, which are harder than ACID in a single database.

AA2 — Easy:  
Synchronous communication: the caller blocks and waits for a response. Example: REST/HTTP (e.g., a service calls another via GET/POST). Asynchronous communication: the caller sends a message and continues without waiting. Example: message queues (e.g., RabbitMQ, Kafka) or event-driven patterns.

AA3 — Medium:  
An API Gateway is a specialized reverse proxy for APIs, adding features like rate limiting, authentication, request/response transformation, and API versioning. A reverse proxy is a generic intermediary that forwards client requests to backend servers, often used for load balancing, TLS termination, and routing. An API Gateway can replace a reverse proxy for API traffic, but not entirely: it may lack features for non-HTTP protocols (e.g., WebSocket, TCP), static content serving, or low-level traffic management. In practice, an API Gateway often sits behind a reverse proxy (e.g., Nginx) or includes reverse proxy capabilities.

AA4 — Medium:  
The Saga pattern manages distributed transactions by breaking them into a series of local transactions, each with a compensating action to undo it if a later step fails. Choreography-based sagas: each service publishes events and reacts to events from others; no central coordinator. Orchestration-based sagas: a central coordinator (e.g., a service or workflow engine) tells each service what to do and handles compensation. Choreography is simpler for small workflows and avoids a single point of failure, but harder to track. Orchestration is better for complex workflows with clear business logic, easier to monitor and maintain, but introduces a central bottleneck.

AA5 — Medium:  
CQRS separates the read model (queries) from the write model (commands), allowing them to be optimized independently (e.g., different databases, scaling). Event Sourcing stores state changes as a sequence of events, rather than only the current state. Combined, they solve problems like high write contention, complex querying, and auditability. Traditional CRUD models struggle with high concurrency, historical analysis, and scaling reads/writes independently. CQRS+Event Sourcing enables event replay, eventual consistency, and better performance for read-heavy systems.

AA6 — Medium:  
Circuit Breaker pattern prevents an application from repeatedly calling a failing service. It has three states: **Closed** (normal operation), **Open** (failures exceed threshold, calls fail fast), and **Half-Open** (allows a limited number of test calls to see if the service recovered). Unlike a simple retry with backoff, which keeps trying and can overload a failing service, a circuit breaker stops calls entirely for a period. They are used together: retry with backoff for transient errors (e.g., network blips), and circuit breaker for longer outages to give the service time to recover and avoid cascading failures.

AA7 — Hard:  
**1. Shared database, shared schema (row-level tenant ID)**  
- Cost: lowest (one database, one schema).  
- Security: weakest – tenant isolation relies on application logic; a SQL injection could expose all tenants.  
- Operational complexity: low (single DB to manage).  
- Noisy-neighbor: high – one tenant's heavy queries can affect others.  
**2. Shared database, separate schema per tenant**  
- Cost: moderate (one DB, multiple schemas).  
- Security: better – schema-level isolation, but still shared DB instance.  
- Operational complexity: moderate – need to manage schema migrations per tenant.  
- Noisy-neighbor: medium – tenants share DB resources but can be isolated via resource limits.  
**3. Separate database per tenant**  
- Cost: highest (many DB instances).  
- Security: strongest – full isolation.  
- Operational complexity: high – many DBs to back up, monitor, and migrate.  
- Noisy-neighbor: low – tenants are physically isolated.  
Trade-offs: choose based on compliance, tenant size, and budget.

AA8 — Hard:  
Eventual consistency means updates propagate asynchronously and reads may see stale data temporarily. Strong consistency guarantees that reads always reflect the latest committed write. For an inventory system that must never oversell, you need strong consistency on the inventory count. At scale, use a database with row-level locking (e.g., PostgreSQL) and transactions, or use a distributed lock service (e.g., Redis with Redlock) to serialize updates per item. Patterns: optimistic concurrency with version numbers, or a single-writer-per-item design. For high throughput, use a queue to buffer orders and process them sequentially per item, ensuring no oversell.

AA9 — Hard:  
A sidecar proxy is a separate container that runs alongside an application service, handling network communication (e.g., Envoy). In Istio, Envoy proxies are deployed as sidecars to each pod. The **data plane** consists of all sidecar proxies that handle traffic between services. The **control plane** (e.g., Istiod) configures the proxies, distributes certificates, and collects telemetry. mTLS between sidecars encrypts and authenticates service-to-service traffic at the network layer, providing identity-based security that application-level TLS might not enforce if applications don't implement mutual TLS or if they use plain HTTP internally. It also provides consistent security policy across a polyglot environment.

AA10 — Medium:  
The Strangler Fig pattern incrementally replaces parts of a monolith with microservices. For a legacy .NET Framework monolith migrating to .NET 8:  
1. Create a facade (API Gateway or routing layer) that intercepts all requests.  
2. Identify bounded contexts (e.g., user management, orders) and extract them one at a time.  
3. For each extracted service, build a .NET 8 microservice, move the data, and update the facade to route traffic to the new service.  
4. Keep the monolith running for the remaining features until all are migrated, then decommission it.  
This reduces risk and allows incremental delivery.

AA11 — Medium:  
12-Factor App is a methodology for building cloud-native applications. Six factors:  
1. **Codebase** – one codebase per app, tracked in version control.  
2. **Dependencies** – explicitly declare and isolate dependencies (e.g., package manifests).  
3. **Config** – store configuration in environment variables, not code.  
4. **Backing services** – treat databases, queues, etc. as attached resources, replaceable.  
5. **Build, release, run** – separate stages for reproducibility.  
6. **Processes** – run as stateless processes, no local state.  
These factors enable portability, scalability, and continuous deployment in cloud environments.

AA12 — Hard:  
Event-driven (Kafka) vs request-driven (REST/gRPC):  
- **Coupling**: Event-driven is loosely coupled – services don't know each other; request-driven is tightly coupled – client knows server.  
- **Scalability**: Event-driven scales well for high throughput and fan-out; request-driven scales with load balancers but can be limited by synchronous calls.  
- **Debugging complexity**: Event-driven is harder – tracing across async boundaries; request-driven is easier with request IDs.  
- **Ordering guarantees**: Kafka preserves order per partition; REST/gRPC has no inherent ordering.  
- **Failure handling**: Event-driven can retry via replay; request-driven requires timeouts and retries.  
Choose event-driven for high-volume, decoupled, and asynchronous workflows (e.g., data pipelines). Choose request-driven for low-latency, interactive, and transactional operations (e.g., CRUD APIs).

AA13 — Easy:  
A load balancer distributes incoming network traffic across multiple servers to ensure availability and performance. Layer 4 (L4) load balancing operates at the transport layer (TCP/UDP) and routes based on IP and port, without inspecting content. Layer 7 (L7) operates at the application layer (HTTP) and can route based on URL, headers, cookies, etc. L7 is required for HTTP-based routing, e.g., sending `/api` requests to one backend and `/static` to another, or for sticky sessions based on cookies.

AA14 — Easy:  
A message queue (e.g., RabbitMQ) is a point-to-point or pub/sub broker that delivers messages to consumers, typically with acknowledgments and immediate removal after consumption. A log-based broker (e.g., Kafka) stores messages in a log, allows replay, and supports multiple consumers with offsets. Choose RabbitMQ for task distribution and complex routing; choose Kafka for event streaming, high throughput, and replayable data.

AA15 — Easy:  
A container is a lightweight, isolated environment that shares the host OS kernel, while a virtual machine runs a full OS on a hypervisor. Containers are popular for microservices because they are fast to start, have low overhead, and provide consistent runtime across environments.

AA16 — Easy:  
Stateless services do not store session data between requests; each request is independent. Stateful services maintain state (e.g., user sessions, database data). Stateless services are easier to scale horizontally because any instance can handle any request, and you can add/remove instances without worrying about session affinity. Examples: stateless – a REST API that uses JWT; stateful – a database or a web server with in-memory sessions.

AA17 — Easy:  
An ORM maps database tables to objects in code, allowing developers to work with data using programming language constructs. Examples: Hibernate (Java), Entity Framework (C#), SQLAlchemy (Python). Trade-offs: ORMs increase productivity and reduce boilerplate, but can lead to performance issues (N+1 queries), less control over SQL, and hidden complexity. Raw SQL gives full control and optimization but is more verbose and error-prone.

AA18 — Medium:  
The Bulkhead pattern isolates failures by partitioning resources (e.g., thread pools, connections) so that a failure in one part doesn't exhaust resources for others. In microservices, it prevents a slow downstream service from consuming all threads and causing cascading failures. Example: use separate thread pools for different service clients (e.g., one pool for orders, one for payments). If the payment service is slow, it only exhausts its own pool, leaving order threads available. Alternatively, deploy services in separate containers or VMs to isolate CPU/memory.

AA19 — Hard:  
Operational Transformation (OT) and CRDTs are both conflict resolution strategies for collaborative editing. OT transforms operations to converge, requires a central server or coordination, and is complex to implement correctly. CRDTs are data structures that merge deterministically without coordination, providing eventual consistency. CRDTs have lower latency (no central coordination), support offline editing well, and are simpler to reason about. For a system that must support offline editing, CRDTs are preferable because they allow concurrent edits to merge automatically when reconnected, without needing a central server to resolve conflicts.

AA20 — Hard:  
Distributed tracing across polyglot microservices requires propagating trace context (e.g., W3C Trace Context headers) through all service calls. Sampling strategies: head-based (sample at the start of a trace) vs tail-based (sample after completion based on latency/errors). Trace storage and querying: Jaeger or Tempo store spans and allow querying by trace ID. For asynchronous messaging (e.g., Kafka), trace context must be injected into message headers so consumers can continue the trace. Ensure continuity by adding trace headers to Kafka messages and extracting them in consumers, and by using a consistent propagation library across languages.

OP1 — Easy:  
Type 1 hypervisor runs directly on hardware (bare-metal), e.g., VMware ESXi, Microsoft Hyper-V, KVM. Type 2 hypervisor runs on top of an operating system, e.g., Oracle VirtualBox, VMware Workstation. Type 1 is used in data centers for performance and stability; Type 2 is for development/testing.

OP2 — Easy:  
SAN (Storage Area Network) provides block-level storage, typically using Fibre Channel or iSCSI. NAS (Network Attached Storage) provides file-level storage, using NFS or SMB. Use SAN for databases and applications requiring high performance and low latency; use NAS for file sharing and general-purpose storage.

OP3 — Medium:  
3-tier network architecture: core (high-speed backbone), distribution (policy and routing), access (user connectivity). Leaf-spine is a two-layer design where every leaf (access) switch connects to every spine (core) switch, providing predictable latency and high bandwidth. It solves the bottleneck of east-west traffic in 3-tier (where traffic between servers often traverses multiple hops) and scales horizontally by adding more spines.

OP4 — Medium:  
A highly available Proxmox cluster with shared storage:  
- Node count: at least 3 nodes to maintain quorum (majority).  
- Quorum: uses Corosync; a node must have quorum to run VMs.  
- Fencing: STONITH (Shoot The Other Node In The Head) to isolate failed nodes.  
- Shared storage options: Ceph (distributed, self-healing), iSCSI (centralized SAN), NFS (simple but single point of failure).  
- On node failure: the cluster detects loss of quorum, fences the node, and migrates VMs to healthy nodes. Ceph provides data redundancy; iSCSI/NFS require HA at the storage layer.

OP5 — Medium:  
VLAN trunking allows multiple VLANs to traverse a single link using 802.1Q tagging, which inserts a tag into Ethernet frames. To put a single NIC on 3 VLANs on Linux, create VLAN subinterfaces: `ip link add link eth0 name eth0.10 type vlan id 10`, similarly for 20 and 30, then assign IP addresses to each subinterface. The switch port must be configured as a trunk with allowed VLANs.

OP6 — Medium:  
RAID levels:  
- RAID 1: mirroring, 2 disks, 50% capacity, high redundancy.  
- RAID 5: striping with parity, requires 3+ disks, tolerates 1 disk failure, good read performance, write penalty.  
- RAID 6: striping with double parity, tolerates 2 failures, lower write performance.  
- RAID 10: striped mirrors, requires 4+ disks, high performance and fault tolerance, 50% capacity.  
- RAID Z2 (ZFS): similar to RAID 6 but with variable stripe width, better data integrity.  
For a database server with 6 drives, RAID 10 gives best performance and fault tolerance (can lose one disk per mirror), but capacity is 3 TB. RAID 6 gives 4 TB capacity but slower writes. If performance is critical, choose RAID 10; if capacity is more important, RAID 6.

OP7 — Hard:  
DNS architecture for 500-person enterprise:  
- Internal AD: use AD-integrated DNS zones on domain controllers.  
- DMZ: separate DNS servers for public-facing services.  
- Split-horizon DNS: same domain names resolve differently internally vs externally.  
- Recursive resolvers: internal DNS servers forward external queries to a forwarder (e.g., ISP or public DNS).  
- Authoritative servers: internal zones are authoritative; external zones are on DMZ DNS.  
- Conditional forwarding: forward queries for specific domains to partner DNS servers.  
- DNSSEC on external zone: sign the zone with keys.  
- Laptop moving between office and VPN: when on VPN, it uses internal DNS; when off, it uses external DNS. This requires VPN to push DNS settings and split-horizon to resolve internal names correctly.

OP8 — Hard:  
PKI chain: Root CA (offline) signs subordinate CA certificates. Subordinate CA issues end-entity certificates. CRL (Certificate Revocation List) is a list of revoked certs; OCSP (Online Certificate Status Protocol) provides real-time status. Certificate templates define attributes (e.g., web server, user). Auto-enrollment uses Group Policy to issue certs automatically. If a subordinate CA is compromised, you can revoke its certificate and issue a new one, but all certs issued by it become invalid. If the root CA is compromised, the entire PKI is compromised, requiring rebuilding the trust chain and reissuing all certificates.

OP9 — Hard:  
Compare WAN options:  
- MPLS: high cost, reliable, low latency, managed by provider, secure (private).  
- IPsec VPN over internet: low cost, variable latency, less reliable, complex to manage, secure with encryption.  
- SD-WAN: moderate cost, uses multiple links (MPLS, broadband, LTE), improves reliability and latency, centralized management, secure with IPsec.  
- WireGuard mesh: very low cost, simple, but requires internet connectivity, latency depends on internet, security good.  
For 50 users per site with latency-sensitive VoIP, SD-WAN is recommended because it can prioritize VoIP traffic, use multiple paths for failover, and reduce latency by selecting best path.

OP10 — Medium:  
iDRAC (Dell), iLO (HPE), IPMI are out-of-band management interfaces that allow remote access to a server's console, power control, and hardware monitoring even when the OS is down. Out-of-band management is critical for remote troubleshooting and recovery. If exposed to the internet, it becomes a security risk – attackers can gain full control of the server, install malware, or cause physical damage. Always restrict access via VPN or dedicated management network.

OP11 — Medium:  
LVM (Logical Volume Manager) provides logical volumes on top of physical disks, allowing resizing and snapshots (copy-on-write). LVM-Thin is a thin-provisioned variant that supports snapshots and efficient space usage. ZFS is a file system and volume manager with built-in checksums, snapshots, and RAID-Z. Use LVM for simple volume management, LVM-Thin for thin provisioning and snapshots, ZFS for data integrity and advanced features. Snapshot semantics: LVM snapshots are copy-on-write and can be mounted; LVM-Thin snapshots are also copy-on-write but more efficient; ZFS snapshots are instantaneous and can be sent/received.

OP12 — Hard:  
To survive a complete site failure with a 3-node Proxmox cluster and Ceph, you need a stretch cluster across two sites. Ceph CRUSH rules must be configured to replicate data across sites (e.g., 2 replicas in site A, 1 in site B). Monitor placement: place monitors in both sites, but ensure quorum – typically 3 monitors, with one in a third location or a tiebreaker. Network latency between sites must be low (<10ms RTT) for Ceph to perform well. Split-brain problem: if the two sites lose connectivity, each may try to form its own quorum. To avoid this, use a tiebreaker node (e.g., a monitor in a third site) or a fencing mechanism. 2-site Ceph without a tiebreaker is bad because a network partition can cause both sites to operate independently, leading to data divergence.

OP13 — Easy:  
DHCP (Dynamic Host Configuration Protocol) assigns IP addresses. DORA: Discover (client broadcasts), Offer (server offers IP), Request (client requests), Acknowledge (server confirms). When a DHCP server is unavailable and a Windows client's lease expires, the client continues using the IP address but periodically tries to renew. After lease expiry, it may fall back to APIPA (169.254.x.x) if no DHCP is found.

OP14 — Easy:  
A managed switch allows configuration of VLANs, QoS, SNMP, port mirroring, link aggregation, and security features. An unmanaged switch is plug-and-play with no configuration. In enterprise, managed switches are essential for network segmentation, monitoring, and troubleshooting.

OP15 — Easy:  
NTP (Network Time Protocol) synchronizes clocks across servers. Accurate time is critical for log correlation, authentication (Kerberos), and distributed systems. Clock drift can cause issues like failed Kerberos authentication, inconsistent timestamps, and problems with distributed databases (e.g., conflict resolution).

OP16 — Easy:  
Physical server: dedicated hardware. Virtual machine: full OS running on hypervisor. Container: isolated process sharing host OS. Run workloads directly on bare metal when you need maximum performance, low latency, or access to specialized hardware (e.g., GPU, FPGA), or when virtualization overhead is unacceptable.

OP17 — Easy:  
UPS provides short-term battery power during outages, allowing graceful shutdown. Generator provides long-term power during extended outages. ATS (Automatic Transfer Switch) automatically switches between utility power and generator/UPS. You need both: UPS covers the gap until generator starts and stabilizes.

OP18 — Medium:  
Active-passive clustering: one node handles traffic, the other is standby. Active-active: both nodes handle traffic simultaneously. For PostgreSQL HA with Pacemaker/Corosync:  
- Configure a cluster with two nodes.  
- Use STONITH (fencing) to ensure a failed node is powered off before failover.  
- Create a virtual IP (VIP) that moves to the active node.  
- Pacemaker manages resources (PostgreSQL, VIP, filesystem).  
- On failure, the standby promotes to primary, VIP moves, and clients reconnect.

OP19 — Hard:  
Backup strategy for 50 servers:  
- 3-2-1 rule: 3 copies, 2 different media, 1 offsite.  
- Define RPO (Recovery Point Objective) and RTO (Recovery Time Objective).  
- Backup types: full, incremental, differential.  
- Deduplication reduces storage.  
- Media: tape (cheap, long-term), disk (fast), cloud (offsite).  
- Immutable backups (write-once) protect against ransomware.  
- Test restores regularly.  
- Backup is copying data; disaster recovery is the process of restoring IT infrastructure after a disaster, including failover and recovery procedures.

OP20 — Hard:  
802.1X:  
- Supplicant: client device requesting network access.  
- Authenticator: network switch (or AP) that controls port access.  
- Authentication server: RADIUS server that validates credentials.  
- EAP methods: EAP-TLS (certificate-based, secure), PEAP (password-based with TLS tunnel).  
- RADIUS: central authentication.  
- Dynamic VLAN assignment: RADIUS returns VLAN attributes, switch assigns port to that VLAN.  
- If authentication fails, the port is blocked or placed in a guest VLAN.  
- MAB (MAC Authentication Bypass): for devices that don't support 802.1X, the switch uses the device's MAC address to authenticate against RADIUS, allowing fallback.
