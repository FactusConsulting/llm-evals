CL1 — Easy: IaaS provides virtualized infrastructure (VMs, storage, networks) on demand; you manage OS and above. Example: AWS EC2. PaaS provides a managed platform for application development and deployment; you manage code and data, provider handles runtime, middleware, OS. Example: Google App Engine. SaaS provides fully managed software applications; you just use them. Example: Microsoft 365.

CL2 — Easy: The Shared Responsibility Model defines which security and compliance tasks are handled by the provider vs customer. For IaaS VMs: provider secures physical infrastructure, network, hypervisor; customer is responsible for OS, applications, data, network configurations, access. For managed Kubernetes (e.g., EKS): provider manages control plane, nodes, and some security patches; customer manages worker node OS, workloads, RBAC, network policies, data. For SaaS (M365): provider manages almost everything including application security, but customer is responsible for user access, data classification, and compliance.

CL3 — Medium: VPC is a virtual network boundary in the cloud; subnets are segments within a VPC (public/private). Security groups are stateful virtual firewalls attached to instances, allowing rules based on source/destination IP/port; they automatically allow return traffic. NACLs are stateless network ACLs applied at subnet level, requiring explicit allow rules for both inbound and outbound. They layer: NACL filters traffic entering/exiting subnet, then security groups filter at instance level. Stateful filtering tracks connection state and allows return traffic automatically; stateless requires both directions explicitly.

CL4 — Medium: Multi-account strategy: Use a landing zone (e.g., AWS Control Tower, Azure LZ) to set up a structured multi-account environment. Organizational units (OUs) group accounts by function (e.g., security, infrastructure, workloads). Guardrails are preventive/detective policies (SCPs, Azure Policy) to enforce compliance. Shared networking: use Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize connectivity between accounts. Centralized logging: aggregate logs to a central account (e.g., S3, Log Analytics). Single-account is problematic: no isolation, blast radius large, difficult to manage access and compliance, no separation of environments.

CL5 — Medium: IaC is managing infrastructure via code, enabling versioning, review, and automation. Terraform/OpenTofu: declarative, provider-agnostic, state-based; good for multi-cloud and broad ecosystem. Pulumi: uses general-purpose languages (Python, TS), allows more logic, but steeper learning curve. CloudFormation/Bicep: AWS/Azure native, tightly integrated, but vendor-locked. Crossplane: control plane for infrastructure, extends Kubernetes API to provision cloud resources; good for platform teams. Choose Terraform for portability and maturity; Pulumi for complex logic; native for deep integration; Crossplane for GitOps-style infrastructure on K8s.

CL6 — Medium: HPA scales pods based on CPU/memory or custom metrics. VPA adjusts pod resource requests/limits automatically. Cluster autoscaler scales nodes based on pending pods. KEDA is event-driven autoscaler that scales based on external sources (queues, Kafka, etc.) and can scale to zero. Use KEDA over HPA when scaling on non-Kubernetes metrics like message queue length, or when you need scale-to-zero for event-driven workloads.

CL7 — Hard: DR design: Define RPO (acceptable data loss) and RTO (time to recover). Active-active: both regions serve traffic, data replicated synchronously (or near-sync) for consistency; requires complex conflict handling. Active-passive: one active, other standby; failover via DNS. Database replication: sync (low RPO but latency) vs async (higher RPO but better performance). DNS failover: Route53 health checks, Azure Traffic Manager. State management: use external stores (S3, Redis) or replicated DB. Cost: active-active doubles infrastructure; pilot light (minimal resources, scale up on failover) is cheaper; warm standby (pre-provisioned but idle) moderate; multi-site active-active highest. Pilot light: only core services running, scale up on DR. Warm standby: full stack running but idle. Multi-site active-active: both serve traffic.

CL8 — Hard: GitOps: Git is single source of truth; changes via pull requests; automated sync to cluster. ArgoCD and FluxCD both implement GitOps; ArgoCD has UI, supports multi-cluster; Flux has more flexible engine, works with Kustomize/Helm. Secrets: use sealed secrets (encrypted in Git), external secrets operator (pull from Vault/AWS Secrets Manager), or Vault agent. Drift: GitOps tools detect and revert manual changes (or alert) to maintain desired state.

CL9 — Hard: For stateful legacy app: Use StatefulSet for stable network identity and ordered startup. Use local persistent storage via local PV/PVC with node affinity to ensure pod stays on same node. Headless service for stable DNS. Init containers to prepare config or wait for dependencies. ConfigMaps mounted at specific paths. PodDisruptionBudget to protect availability during node maintenance. Also consider node pools dedicated to stateful workloads.

CL10 — Medium: Service account (K8s) is an identity for pods to access K8s API. Workload identity (cloud) is an identity for cloud resources (e.g., AWS IAM role for a pod). IRSA (IAM Roles for Service Accounts) on EKS maps K8s service account to IAM role. Mounting cloud credentials in pod is bad because credentials are static, can be exfiltrated, and hard to rotate. Workload identity federation uses OIDC to issue short-lived credentials, eliminating static secrets.

CL11 — Medium: Object storage (S3/Blob): highly durable (11 9s), for unstructured data, accessed via HTTP, pay per storage/requests. Block storage (EBS/Managed Disk): attached to a VM, low latency, for databases, filesystems; durability depends on replication (often 3 copies). File storage (EFS/Azure Files): shared file system over NFS/SMB, for shared content, multiple VMs. Use object for backups, static assets; block for DB; file for shared config.

CL12 — Hard: Zero-trust: assume breach, verify every request. Network policies: define ingress/egress rules between pods. Service mesh (Istio/Linkerd) with mTLS encrypts traffic and provides identity. Pod identity: use service accounts with OIDC. Admission controllers (OPA/Kyverno) enforce policies (e.g., no privileged containers). Image signing and verification (Cosign, Notary). Runtime security (Falco) monitors syscalls. Secrets management: use Vault or external secrets. This differs from perimeter security: no implicit trust inside network; every request authenticated/authorized.

CL13 — Easy: CDN is a distributed network of edge servers that cache content closer to users. It works by routing requests to nearest edge, caching static content, reducing latency and origin load. Examples: AWS CloudFront, Azure CDN. Use CDN for static assets, video, global users; serve directly from origin for dynamic, personalized, or real-time data.

CL14 — Easy: Regions are geographic areas with multiple availability zones (AZs) - isolated data centers. Deploy across AZs for high availability (fault tolerance). Zonal resources are tied to a specific AZ (e.g., EC2 instance, EBS volume); regional resources are available across AZs (e.g., S3, ELB). Use multiple AZs to survive AZ failures.

CL15 — Easy: Managed DB (RDS, Cloud SQL, Azure SQL) automates provisioning, patching, backups, replication, and monitoring. You manage schema, data, access. On VM, you handle all OS, DB software, patching, backups, high availability.

CL16 — Easy: IAM users are individual identities; groups are collections of users; roles are identities with permissions assumed by users/services; policies define permissions. Least privilege: grant only necessary permissions. Apply by using roles, scoping policies to resources, and regularly reviewing.

CL17 — Easy: Serverless: run code without managing servers; auto-scaling, pay per execution. AWS Lambda, Azure Functions, Google Cloud Functions are event-driven. Cold starts: delay when function is invoked after idle; matters for latency-sensitive apps. Poor fit for long-running processes, stateful apps, or workloads with predictable high load.

CL18 — Medium: Ingress resource: K8s native, uses controller (NGINX) to route HTTP/HTTPS. Gateway API: newer, more expressive, supports multiple protocols, better for service mesh integration. Cloud LB annotations: directly configure cloud load balancer (e.g., AWS NLB) via annotations. Service mesh ingress gateway: uses mesh proxy (e.g., Istio Gateway) for advanced routing. TLS termination can happen at LB, ingress controller, or mesh gateway. Gateway API is more flexible and portable, recommended over Ingress for new projects.

CL19 — Hard: Cost optimization: Use reserved instances/savings plans for steady-state, spot/preemptible for fault-tolerant workloads. Right-size by analyzing utilization. Storage tiering: S3 Intelligent-Tiering, archive for cold data. Idle resource detection: use AWS Trusted Advisor, Azure Advisor, or custom scripts. FinOps: establish tagging, showback/chargeback to teams, budget alerts, and regular reviews. Tools: CloudHealth, Cloudability, native cost explorer. Process: monthly cost review, tagging standards, and automated shutdown of non-prod.

CL20 — Hard: Multi-cloud: Use abstraction layers like Kubernetes for workloads, Terraform for IaC, and cloud-agnostic services (e.g., object storage via S3-compatible). Networking: connect clouds via VPN or dedicated interconnect. Identity federation: use OIDC/SAML to unify access. Trade-offs: increased complexity, latency, and cost; benefits: avoid lock-in, resilience, best-of-breed. Justified when regulatory requirements, disaster recovery, or negotiating leverage. Unnecessary complexity for most orgs.

OT1 — Easy: Purdue Model (ISA-95) defines levels: Level 0: Physical process (sensors/actuators). Level 1: Basic control (PLCs, DCS). Level 2: Supervisory control (SCADA, HMI). Level 3: Operations management (historian, MES). Level 4: Enterprise (ERP, business systems). Level 5: Cloud/Internet (not always included). It separates OT from IT.

OT2 — Easy: IT networks prioritize confidentiality/integrity, dynamic, patched frequently. OT networks prioritize availability/safety, often legacy, fragile, cannot be patched without disrupting production. Standard IT patching can cause downtime or break control systems.

OT3 — Medium: IDMZ is a buffer zone between IT and OT, with firewalls and proxies. Only allow specific protocols (e.g., HTTPS, MQTT) from IT to OT for data collection, and OT to IT for historian replication. Direct connectivity from Level 4 to Level 1 is dangerous because it exposes control systems to IT threats, bypasses security zones, and can cause unintended changes.

OT4 — Medium: Modbus TCP: industrial protocol for PLC communication, typically Level 1-2. OPC UA: machine-to-machine communication, often Level 2-3. EtherNet/IP (CIP): industrial Ethernet protocol, Level 1-2. PROFINET: real-time Ethernet for automation, Level 1. MQTT: lightweight pub/sub, often used for IoT/cloud, Level 3-4.

OT5 — Medium: Data diode: hardware that allows one-way data transfer, physically prevents reverse traffic. Firewall: allows bidirectional traffic with rules. Use data diode when you need absolute security (e.g., from OT to IT) and no return communication needed. Limitation: cannot receive commands or acknowledgments.

OT6 — Medium: Data flow: PLCs -> OPC UA server (Level 2) -> historian (Level 3) -> edge gateway (Level 3.5) -> MQTT broker (in DMZ) -> cloud ingestion. Security boundaries: firewalls between levels, IDMZ, TLS for MQTT, authentication, and allowlist.

OT7 — Hard: IEC 62443 defines zones (grouping assets with similar security requirements) and conduits (communication paths between zones). Define zones based on function, risk, and trust. Conduits are controlled channels with specific rules. For plant: Zone 1: Corporate IT; Zone 2: Engineering workstations; Zone 3: SCADA servers; Zone 4: PLCs; Zone 5: SIS. Conduits between zones with firewalls, only necessary protocols.

OT8 — Hard: Segmentation: Create VLANs per production line, separate SCADA, engineering, and IT. Use managed switches with VLANs, firewalls between zones. Place firewalls at plant network boundaries and between lines. Remote access: use jump host with MFA, session recording, time-limited. Transition: implement in phases, use temporary ACLs, schedule during maintenance windows, and test.

OT9 — Hard: SIS is independent safety protection (e.g., emergency shutdown) vs BPCS is process control. IEC 61511 is functional safety standard for SIS. SIS must be isolated to prevent cyber attacks from affecting safety functions. If ransomware reaches SIS, it could disable safety systems, leading to catastrophic accidents. Air-gap or strict isolation is critical.

OT10 — Medium: PLC: dedicated controller for discrete automation, fast, deterministic. DCS: distributed control system for complex continuous processes, integrates many controllers. SCADA: supervisory control and data acquisition, monitors and controls remote sites. They can coexist: PLCs for local control, DCS for plant-wide, SCADA for remote monitoring.

OT11 — Medium: Remote access: Use a jump host (bastion) in DMZ, with MFA, session recording, and time-limited access. Vendor access: provide temporary credentials, restrict to specific systems, and monitor. Direct RDP to HMI is unacceptable because it exposes HMI to network, lacks security controls, and can be exploited.

OT12 — Hard: Detection: Deploy IDS/IPS at network boundaries, monitor for anomalies, use asset inventory to baseline. Response: Isolate compromised systems, maintain safety, coordinate with control room, follow incident response plan. Plant operator should be trained to recognize signs and follow procedures to maintain safe operation while IT/OT security team investigates.

OT13 — Easy: HMI is a graphical interface for operators to monitor and control processes. It displays data, alarms, and allows commands. Engineering workstation is used by engineers to program, configure, and maintain control systems, not for real-time operations.

OT14 — Easy: Historian is a time-series database that stores process data (temperatures, pressures) for analysis, reporting, and troubleshooting. Plant historian (Level 3) collects data from control systems; enterprise historian (Level 4) aggregates data across plants for business analytics.

OT15 — Easy: Ladder logic is a programming language for PLCs, resembling relay logic diagrams. It is executed cyclically by PLCs. It remains dominant because it is intuitive for electricians, reliable, and widely understood.

OT16 — Easy: RTU is a remote terminal unit used for telemetry and control in remote locations, often battery/solar powered, communicates via serial/cellular. PLC is more powerful, local control. RTUs are used in oil/gas, water, electric grid where remote monitoring is needed.

OT17 — Easy: Analog signals represent continuous values (4-20mA, 0-10V); digital signals are discrete (on/off). 4-20mA preferred because it can detect wire break (0mA), has better noise immunity, and can power devices.

OT18 — Medium: OT asset inventory is knowing all devices, their firmware, and connections. Tools: passive network monitoring (e.g., using SPAN ports) to identify devices without sending packets; active scanning (e.g., Nmap) can disrupt fragile OT devices. Active scanning is dangerous because it may cause devices to fail or trigger safety systems.

OT19 — Hard: MITRE ATT&CK for ICS includes tactics: Initial Access (e.g., exploit public-facing application), Execution (e.g., command-line interface), Persistence (e.g., modify registry), Evasion (e.g., masquerading), Discovery (e.g., network scanning), Lateral Movement (e.g., remote services), Collection (e.g., process capture), Command & Control (e.g., standard protocols), Impact (e.g., damage to process). Differs from enterprise: focuses on ICS-specific impacts (loss of safety, process disruption). Use to map defenses to tactics.

OT20 — Hard: SOC design: Collect logs from OT via passive monitoring, use syslog or SPAN, avoid interfering. Integrate with SIEM (e.g., Splunk, Azure Sentinel). OT-specific detection rules: monitor for unauthorized firmware changes, unusual protocol usage, etc. Alert triage: IT analysts handle IT alerts, OT engineers handle OT alerts, with escalation. False positives: high in OT due to legacy protocols; need baselining and context. For unauthorized firmware change: verify with asset inventory, isolate device, check if change was planned, and follow change management.
