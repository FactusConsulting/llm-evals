AA1 — A monolith is a single deployable unit containing all application logic, while microservices decompose the application into independently deployable services. Three concrete problems microservices introduce that monoliths don't: (1) network latency and partial failure handling (services must handle timeouts, retries, and cascading failures), (2) distributed data management (transactions span services, requiring sagas or eventual consistency), and (3) operational complexity (deployment, monitoring, service discovery, and orchestration overhead).

AA2 — Synchronous communication blocks the caller until a response is received, e.g., REST/HTTP or gRPC. Asynchronous communication decouples sender and receiver via a message broker, e.g., RabbitMQ or Kafka. Synchronous is simpler for request-reply, asynchronous is better for decoupling, buffering, and scalability.

AA3 — A reverse proxy forwards client requests to backend servers, handling TLS termination, load balancing, and routing. An API Gateway adds API-specific features: authentication, rate limiting, request/response transformation, analytics, and API versioning. An API Gateway can replace a reverse proxy for HTTP/API traffic, but not entirely—reverse proxies are often used for non-API traffic, internal routing, or as a first-line edge component.

AA4 — Saga is a sequence of local transactions with compensating actions to maintain consistency across services. Choreography-based sagas use events: each service reacts and emits events, no central coordinator. Orchestration-based sagas use a central coordinator that sends commands and tracks state. Choreography is simpler but harder to trace; orchestration is more centralized and easier to manage. Use choreography for simple workflows, orchestration for complex workflows requiring monitoring and rollback.

AA5 — CQRS separates read and write models, allowing independent optimization. Event Sourcing stores state changes as events, providing an audit log and enabling replay. Combined, they solve problems like scalability (reads can be scaled independently), complex domain logic (events capture intent), and auditability. Traditional CRUD often struggles with high write contention and complex queries.

AA6 — Circuit Breaker has three states: closed (normal), open (fail fast), and half-open (test recovery). It differs from retry with backoff by preventing repeated calls to a failing service, reducing load. Use both: retry for transient failures, circuit breaker for longer outages.

AA7 — Multi-tenant isolation models:
1. Shared DB, shared schema: lowest cost, but row-level security is fragile, noisy-neighbor risk high, operational complexity moderate.
2. Shared DB, separate schema: moderate cost, better isolation, still shared DB, noisy-neighbor risk moderate, operational complexity moderate.
3. Separate DB per tenant: highest cost, best isolation, noisy-neighbor risk low, operational complexity high (many DBs to manage). Choose based on security requirements and budget.

AA8 — Eventual consistency means updates propagate asynchronously; strong consistency means reads always reflect the latest write. For an inventory system that must never oversell, use strong consistency. Architect with a database that supports atomic operations (e.g., PostgreSQL with row-level locks, or Redis with atomic decrement). Use optimistic locking, atomic decrement, or a queue to serialize updates. At scale, partition by item and use single-writer per item.

AA9 — A sidecar proxy is a separate container that mediates network traffic for a service. In Istio, Envoy sidecars handle all traffic, forming the data plane. The control plane (Istiod) configures proxies, discovers services, and manages policies. mTLS between sidecars provides service-to-service authentication and encryption, which application-level TLS doesn't necessarily provide (e.g., mutual auth, identity).

AA10 — Strangler Fig pattern: incrementally replace parts of a monolith with microservices. Strategy: identify seams (e.g., modules), create a facade to route traffic, gradually move functionality to new services, and decommission old code. For .NET Framework to .NET 8, start with low-risk modules, use API gateway to route, and maintain data consistency via shared database initially.

AA11 — 12-Factor App factors: (1) Codebase (one codebase, multiple deploys), (2) Dependencies (explicitly declared), (3) Config (stored in environment), (4) Backing services (treat as attached resources), (5) Build/release/run (separate stages), (6) Processes (stateless, share nothing), (7) Port binding (self-contained), (8) Concurrency (scale via processes), (9) Disposability (fast start/graceful shutdown), (10) Dev/prod parity, (11) Logs (stream to stdout), (12) Admin processes (one-off tasks). These matter for cloud-native deployments because they enable portability, scalability, and resilience.

AA12 — Event-driven (Kafka) vs request-driven (REST/gRPC):
- Coupling: event-driven loose, request-driven tight.
- Scalability: event-driven better for async, request-driven easier for sync.
- Debugging: request-driven easier to trace, event-driven harder.
- Ordering: event-driven can have ordering issues, request-driven ordered.
- Failure handling: event-driven can retry, request-driven need timeouts.
Choose event-driven for decoupling, high throughput, and replayability; request-driven for low latency, simple request-reply, and strong consistency.

AA13 — Load balancer distributes traffic. Layer 4 (L4) operates at transport layer (IP/port), Layer 7 (L7) at application layer (HTTP). L7 is required for content-based routing (e.g., path-based, header-based) and for features like SSL termination, cookies, and API routing.

AA14 — Message queue (RabbitMQ) removes messages after consumption, supports routing, and is ideal for task queues. Log-based broker (Kafka) retains messages, allows replay, and is designed for high-throughput event streaming. Pick RabbitMQ for simple task distribution, Kafka for event sourcing, stream processing, and audit trails.

AA15 — Container shares the host OS kernel, while a VM has its own OS. Containers are lightweight, start quickly, and are portable. They are popular for microservices because they enable consistent deployment, isolation, and efficient resource utilization.

AA16 — Stateless services don't store session data; any instance can handle any request, making horizontal scaling trivial. Stateful services store data (e.g., databases) and require sticky sessions or shared storage. Examples: stateless REST API, stateful database.

AA17 — ORM maps objects to database tables. Examples: Hibernate (Java), Entity Framework (C#), SQLAlchemy (Python). Trade-offs: ORM increases productivity and reduces SQL errors, but can be slower, cause N+1 queries, and obscure performance tuning. Raw SQL gives more control and performance but is verbose and error-prone.

AA18 — Bulkhead pattern isolates failures by partitioning resources. In microservices, implement with thread pools per service (e.g., separate executors for different dependencies) or separate deployment groups (e.g., different clusters). Example: a service with two downstream APIs uses two thread pools; if one API fails, it doesn't exhaust the other's threads.

AA19 — OT (Operational Transformation) requires a central server, provides low latency, but is complex and offline support is hard. CRDTs (Conflict-free Replicated Data Types) provide eventual consistency, merge automatically, and support offline editing, but may have conflicts and higher latency. For offline editing, choose CRDTs because they allow local edits and sync later without a central coordinator.

AA20 — Distributed tracing challenges: context propagation (W3C Trace Context, B3), sampling (head-based vs tail-based), storage/querying (Jaeger, Tempo), and async messaging. For Kafka, inject trace context into message headers so consumers can continue the trace. Ensure propagation across all services, including async boundaries.

OP1 — Type 1 hypervisor runs directly on hardware (bare-metal), e.g., VMware ESXi, Microsoft Hyper-V. Type 2 runs on a host OS, e.g., VirtualBox, VMware Workstation. Type 1 is more efficient and used in data centers.

OP2 — SAN (Storage Area Network) provides block-level storage via Fibre Channel or iSCSI, used for databases and VMs. NAS (Network Attached Storage) provides file-level access via NFS or SMB, used for file sharing. Use SAN for performance, NAS for simplicity.

OP3 — 3-tier network: core, distribution, access. Leaf-spine is a two-layer design where every leaf connects to every spine, reducing latency and east-west traffic bottlenecks. It solves oversubscription and provides predictable performance.

OP4 — Proxmox cluster with shared storage: use 3+ nodes for quorum. Quorum requires majority; fencing via watchdog or IPMI. Shared storage options: Ceph (preferred for scalability), iSCSI, NFS. On node failure, HA services migrate to healthy nodes.

OP5 — VLAN trunking uses 802.1Q tagging to carry multiple VLANs on one link. On Linux, create VLAN interfaces with `ip link add link eth0 name eth0.10 type vlan id 10` and assign IPs.

OP6 — RAID 1: mirror, RAID 5: striping with single parity, RAID 6: double parity, RAID 10: stripe of mirrors, RAID Z2: ZFS double parity. For 6 drives database, choose RAID 10 for performance and fault tolerance, or RAID 6 for capacity.

OP7 — DNS architecture: internal recursive resolvers (e.g., AD-integrated DNS), authoritative servers for internal and external zones, forwarders for external queries, conditional forwarding for partner domains. Split-horizon DNS serves different records internally vs externally. DNSSEC on external zone. Laptop moves: use VPN and internal DNS when remote.

OP8 — PKI chain: root CA (offline) -> subordinate CA (online) -> end-entity certificates. Use CRL or OCSP for revocation. Certificate templates define attributes; auto-enrollment via GPO. Compromised subordinate CA: revoke and reissue; compromised root CA: catastrophic, requires rebuilding trust.

OP9 — WAN options: MPLS (reliable, expensive), IPsec VPN (cheap, less reliable), SD-WAN (dynamic, cost-effective), WireGuard mesh (simple, low overhead). For 50 users per site with VoIP, recommend SD-WAN with MPLS backup or IPsec for reliability and low latency.

OP10 — iDRAC/iLO/IPMI are out-of-band management interfaces. They allow remote console, power control, and hardware monitoring. Critical for remote management. Exposed to internet: security risk (unauthorized access, firmware attacks).

OP11 — LVM: logical volume management, snapshots (copy-on-write). LVM-Thin: thin provisioning, better snapshot support. ZFS: copy-on-write, checksums, snapshots, high data integrity. Use LVM for simple volume management, LVM-Thin for thin provisioning, ZFS for data integrity and advanced features.

OP12 — Stretch cluster with Ceph: use CRUSH rules to distribute data across sites, monitors in both sites plus a tiebreaker (e.g., third site). Network latency must be low (<10ms RTT). Split-brain problem: avoid by using a tiebreaker. 2-site Ceph is bad because a network partition can cause split-brain; a tiebreaker is needed.

OP13 — DHCP DORA: Discover, Offer, Request, Ack. If DHCP server unavailable, Windows client uses APIPA (169.254.x.x) after lease expiry.

OP14 — Managed switch: supports VLANs, QoS, SNMP, port security, link aggregation, and remote management. Unmanaged switch: plug-and-play, no configuration. Enterprise needs managed switches for segmentation, monitoring, and security.

OP15 — NTP synchronizes clocks. Accurate time is critical for Kerberos authentication, log correlation, distributed transactions, and certificate validation. Clock drift can cause authentication failures, inconsistent logs, and transaction errors.

OP16 — Physical server: dedicated hardware, full control. VM: virtualized, isolated, portable. Container: lightweight, shares OS. Run on bare metal for high-performance workloads, specialized hardware, or when virtualization overhead is unacceptable.

OP17 — UPS provides immediate battery power for short outages; generator provides long-term power. ATS (Automatic Transfer Switch) automatically switches between power sources (e.g., utility to generator) to ensure continuous power.

OP18 — Active-passive: one node active, other standby. Active-active: both nodes active. For PostgreSQL HA with Pacemaker/Corosync: configure STONITH (fencing) to avoid split-brain, use a virtual IP that moves to the active node, and failover automatically on node failure.

OP19 — Backup strategy: follow 3-2-1 rule (3 copies, 2 media, 1 offsite). Define RPO/RTO. Use full/incremental/differential backups, deduplication, and immutable backups for ransomware. Test restores regularly. Backup is data copy; disaster recovery is full recovery of systems and infrastructure.

OP20 — 802.1X: supplicant (client), authenticator (switch), authentication server (RADIUS). EAP-TLS uses certificates, PEAP uses passwords. RADIUS authenticates and can assign dynamic VLAN. Failed devices are denied access or placed in a guest VLAN. MAB (MAC Authentication Bypass) allows devices without 802.1X to authenticate by MAC address, often for legacy devices.
