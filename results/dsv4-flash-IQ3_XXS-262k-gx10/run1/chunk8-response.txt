CL1 — Easy: IaaS provides virtualized infrastructure (VMs, storage, networks) that you manage; PaaS provides a platform for developing and deploying apps without managing underlying infrastructure; SaaS provides fully managed software applications. Examples: IaaS – AWS EC2; PaaS – Azure App Service; SaaS – Microsoft 365.

CL2 — Easy: Shared Responsibility Model defines who secures what. For IaaS VMs: provider secures physical hosts, network, hypervisor; customer secures OS, applications, data, patches. For managed Kubernetes: provider secures control plane, nodes, and managed services; customer secures workloads, pods, RBAC, and container images. For SaaS (M365): provider secures the service, infrastructure, and application; customer secures user access, data, and client devices.

CL3 — Medium: A VPC is a virtual network boundary; subnets are IP address ranges within it. Security groups are stateful instance-level firewalls that automatically allow return traffic; NACLs are stateless subnet-level firewalls requiring explicit allow/deny rules for both inbound and outbound. They layer: NACL filters traffic at subnet edge, then SG filters at instance level. Stateful filtering tracks connection state (SG), stateless does not (NACL).

CL4 — Medium: A multi-account strategy uses a landing zone (pre-configured baseline), organizational units (OUs) for grouping accounts, guardrails (SCPs, preventive/detective controls), shared networking via Transit Gateway (AWS) or hub-and-spoke (Azure), and centralized logging (e.g., S3/Log Analytics). Single-account is problematic: no blast radius isolation, poor cost allocation, compliance risk, and limited experimentation.

CL5 — Medium: IaC is managing infrastructure via code. Terraform/OpenTofu: declarative, multi-cloud, state-based; Pulumi: imperative (Python/TS), multi-cloud; CloudFormation/Bicep: AWS/Azure native, declarative; Crossplane: control plane that composes infrastructure using Kubernetes CRDs. Choose Terraform for broad multi-cloud, Pulumi for developer-friendly code, native tools for deep cloud-specific features, Crossplane for platform teams wanting K8s-native IaC.

CL6 — Medium: HPA scales pods based on CPU/memory or custom metrics; VPA adjusts pod resource requests; cluster autoscaler scales nodes; KEDA is event-driven scaling based on external sources (queues, Kafka, etc.). Use KEDA when scaling on non-CPU metrics like message queue length, or when you need scale-to-zero.

CL7 — Hard: DR design: Define RPO (acceptable data loss) and RTO (time to recover). Active-active serves traffic from both regions; active-passive has one standby. Database replication: sync (lower RPO, higher latency) vs async (higher RPO, better performance). DNS failover via Route53/Traffic Manager health checks. State management: use replicated DB, distributed cache, or session affinity. Cost: active-active doubles infrastructure; pilot light (minimal standby) is cheaper; warm standby has pre-provisioned resources. Pilot light: only core services running; warm standby: scaled-down but ready; multi-site active-active: full capacity in both.

CL8 — Hard: GitOps uses Git as the source of truth for declarative infrastructure and apps. ArgoCD and FluxCD both reconcile Git state to cluster. Secrets: Sealed Secrets (encrypt in Git), External Secrets Operator (sync from Vault/AWS Secrets Manager), Vault (dynamic secrets). Manual changes that drift are detected and reverted by the controller (self-healing). If drift is intentional, it must be committed to Git.

CL9 — Hard: Use StatefulSet for stable network identity and ordered startup. Local persistent storage via local PV/PVC with a storage class that binds to node. Headless service for stable DNS. Init containers to prepare config files (e.g., copy from ConfigMap to required paths). ConfigMaps mounted as volumes. Pod Disruption Budget to ensure availability during maintenance. Also consider node affinity to pin pods to nodes with local storage.

CL10 — Medium: Service account is a Kubernetes identity for pods; workload identity is a cloud IAM identity for a workload (e.g., AWS IAM role for service account); IRSA (IAM Roles for Service Accounts) maps K8s service account to IAM role. Mounting cloud credentials in a pod is bad because they are long-lived, hard to rotate, and exposed. Workload identity federation uses OIDC to exchange a K8s token for a cloud role, eliminating static credentials.

CL11 — Medium: Object storage (S3/Blob) is for unstructured data, highly durable (11 nines), accessed via HTTP, ideal for backups, media, data lakes. Block storage (EBS/Managed Disk) is for VMs, low latency, single-attach, durable within AZ. File storage (EFS/Azure Files) is shared file system, supports NFS/SMB, for multi-VM access. Durability: object 99.999999999%, block 99.999%, file 99.999999% (varies). Availability: object 99.99%, block 99.99%, file 99.99%.

CL12 — Hard: Zero-trust: enforce network policies (K8s NetworkPolicy) to restrict east-west traffic; service mesh (Istio) with mTLS for encrypted and authenticated communication; pod identity via SPIFFE/SPIRE; admission controllers (OPA/Kyverno) to validate security policies; image signing (Cosign) and verification; runtime security with Falco to detect anomalies; secrets management via Vault or External Secrets. This differs from perimeter security by assuming breach and verifying every request.

CL13 — Easy: A CDN is a distributed network of edge servers that cache content closer to users. It works by routing requests to the nearest edge node, which serves cached content or fetches from origin. Examples: AWS CloudFront, Azure CDN. Use CDN for static content, global distribution, DDoS protection; use origin for dynamic, personalized, or real-time data.

CL14 — Easy: Regions are geographic areas with multiple availability zones (AZs). AZs are isolated data centers with independent power and networking. Deploy across AZs for high availability and fault tolerance. Zonal resources are tied to a specific AZ (e.g., EC2 instance, EBS volume); regional resources are redundant across AZs (e.g., S3, ELB).

CL15 — Easy: Managed DB (RDS, Cloud SQL, Azure SQL) automates provisioning, patching, backups, replication, and failover. You manage schema, data, and access. On a VM, you handle all OS, DB software, patching, backups, and HA yourself.

CL16 — Easy: IAM users are individual identities; groups are collections of users; roles are temporary identities for services or federated users; policies are JSON documents defining permissions. Least privilege means granting only necessary permissions. Apply by using groups, scoping policies to resources, and regularly reviewing access.

CL17 — Easy: Serverless computing runs code without provisioning servers. AWS Lambda, Azure Functions, Google Cloud Functions are event-driven, auto-scaling, pay-per-use. Cold starts are delays when a function is invoked after being idle, causing latency. Poor fit for long-running processes, stateful apps, or workloads with predictable high utilization.

CL18 — Medium: Ingress resource is a K8s API object that routes HTTP traffic; Gateway API is a newer, more expressive standard with multiple layers (gateway, routes). Cloud LB annotations configure the cloud provider's load balancer directly. Service mesh ingress gateways (e.g., Istio) provide advanced routing and mTLS. TLS termination can happen at the LB, ingress controller, or service mesh. Gateway API is better for complex routing, multi-team environments, and portability.

CL19 — Hard: Cost optimization: Use reserved instances/savings plans for steady-state, spot/preemptible for fault-tolerant workloads. Right-size by analyzing utilization. Storage tiering: S3 Intelligent-Tiering, Archive for cold data. Detect idle resources (e.g., unattached EIPs, idle DBs). FinOps: establish tagging, budgeting, and showback/chargeback. Tools: AWS Cost Explorer, Azure Cost Management, Terraform cost estimation. Processes: regular reviews, automated shutdowns, and team ownership.

CL20 — Hard: Multi-cloud strategy: Use abstraction layers like Kubernetes for workloads, Terraform for IaC, and a common identity federation (OIDC). Networking via VPN or interconnect. Trade-offs: increased complexity, latency, and cost; benefits: resilience, avoiding lock-in. Justified when regulatory requirements, disaster recovery, or leveraging best-of-breed services. Unnecessary when single-cloud meets needs and adds complexity.

OT1 — Easy: Purdue Model (ISA-95) levels: Level 0 – Physical process (sensors/actuators); Level 1 – Basic control (PLCs, DCS); Level 2 – Supervisory control (SCADA, HMI); Level 3 – Operations management (historian, MES); Level 4 – Plant/business network (ERP, business apps); Level 5 – Enterprise network (corporate IT). (Note: Some models combine 4/5.)

OT2 — Easy: IT networks prioritize confidentiality and integrity; OT networks prioritize availability and safety. OT systems often run legacy OS, real-time protocols, and cannot tolerate downtime for patching. Patching may break control loops or require production shutdowns.

OT3 — Medium: The IDMZ (Industrial DMZ) is a buffer zone between IT and OT. It allows controlled traffic, typically from IT to OT for data collection (e.g., historians) and from OT to IT for business analytics. Direct IT-to-Level 1 connectivity is dangerous because it exposes control systems to untrusted traffic, increasing attack surface and risk of disruption.

OT4 — Medium: Modbus TCP – Level 1/2, industrial protocol for PLC communication. OPC UA – Level 2/3, machine-to-machine communication, cross-platform. EtherNet/IP (CIP) – Level 1/2, industrial Ethernet protocol. PROFINET – Level 1/2, real-time Ethernet for automation. MQTT – Level 3/4, lightweight pub/sub for IoT/cloud integration.

OT5 — Medium: A data diode is a hardware device that allows data to flow in one direction only, ensuring no return traffic. It is used when absolute security is required (e.g., critical infrastructure). A firewall allows bidirectional traffic with rules. Data diode limitation: no acknowledgment, no remote control, and can be complex to implement.

OT6 — Medium: Data flow: PLCs/SCADA → Historian (Level 3) → OPC UA server → Edge gateway (Level 3.5) → MQTT broker → Cloud ingestion. Security boundaries: place firewall between Level 3 and edge gateway, use TLS, authenticate MQTT, and isolate cloud access via VPN or private link.

OT7 — Hard: IEC 62443 zones are logical groupings of assets with similar security requirements; conduits are communication paths between zones. Define zones based on function, risk, and trust. For a plant: Zone 1 – Corporate IT; Zone 2 – Engineering workstations; Zone 3 – SCADA servers; Zone 4 – PLCs; Zone 5 – SIS. Conduits: between zones with firewalls, allow only necessary protocols.

OT8 — Hard: Segmentation: Create VLANs per production line, SCADA, engineering, and corporate. Place firewalls between VLANs, with rules allowing only required traffic. Use managed switches with 802.1Q. For remote access, use a jump host with MFA and session recording. Transition: implement in phases, using temporary ACLs, and schedule during planned outages.

OT9 — Hard: SIS is a separate safety system that protects against hazardous events; BPCS is the basic process control. IEC 61511 is a standard for functional safety of SIS. SIS must be isolated because a cyber attack could disable safety functions, leading to catastrophic accidents. If ransomware hits SIS, it could prevent safety shutdowns, causing explosions or releases.

OT10 — Medium: PLC is a single-purpose controller for discrete automation; DCS is a distributed control system for continuous processes; SCADA is a supervisory system for remote monitoring and control. Use PLC for small machines, DCS for large continuous plants, SCADA for geographically distributed assets. They can coexist: PLCs under DCS, SCADA over PLCs.

OT11 — Medium: Remote access should use a jump host (bastion) with MFA, session recording, and time-limited access. Vendor access should be via a separate VPN with limited permissions. Direct RDP to HMI is unacceptable because it exposes the HMI to the corporate network, lacks audit, and increases risk.

OT12 — Hard: Detection: Deploy passive IDS/NDR at Level 3, monitor for anomalies, maintain asset inventory. Response: Isolate compromised systems, preserve evidence, coordinate with control room to ensure safe shutdown if needed. Operator role: follow procedures, maintain situational awareness, and execute manual overrides if necessary.

OT13 — Easy: HMI is a graphical interface for operators to monitor and control processes. Engineering workstation is used by engineers to program and configure PLCs, HMIs, and other devices. HMI is for operations; engineering workstation is for development and maintenance.

OT14 — Easy: A historian is a time-series database that stores process data (temperatures, pressures, etc.). Plant historian (Level 3) collects real-time data from control systems; enterprise historian (Level 4) aggregates data across plants for business analytics.

OT15 — Easy: Ladder logic is a programming language for PLCs, resembling relay logic diagrams. It is executed cyclically by PLCs. It remains dominant because it is intuitive for electricians, reliable, and well-supported in legacy systems.

OT16 — Easy: RTU is a remote terminal unit used for telemetry and control in remote locations, often battery/solar powered. PLC is more powerful and used in local control. RTUs are deployed in oil/gas pipelines, electrical substations, and remote monitoring.

OT17 — Easy: Analog signals are continuous (4-20mA, 0-10V) representing process variables; digital signals are discrete (on/off). 4-20mA is preferred because it can detect wire break (0mA) and has a live zero, making it more reliable.

OT18 — Medium: OT asset inventory is a complete list of all devices, their firmware, and connections. It is foundational because you cannot protect what you don't know. Discovery: passive monitoring (SPAN ports, packet analysis) is safe; active scanning can disrupt fragile OT devices. Use passive first, then controlled active scanning in maintenance windows.

OT19 — Hard: MITRE ATT&CK for ICS includes tactics: Initial Access (e.g., exploit public-facing application), Execution (e.g., command-line interface), Persistence (e.g., modify registry), Privilege Escalation (e.g., exploit vulnerability), Evasion (e.g., obfuscated files), Discovery (e.g., network scanning), Lateral Movement (e.g., remote services), Collection (e.g., process capture), Command & Control (e.g., standard protocols), Impact (e.g., damage to equipment). It differs from enterprise by focusing on ICS-specific impacts like loss of safety. Use it to map defenses and identify gaps.

OT20 — Hard: Log collection: Use passive taps or SPAN ports, send logs to SIEM via a gateway. Integrate OT-specific detection rules (e.g., firmware change, protocol anomalies). Triage: IT analysts handle initial, escalate to OT engineers for context. False positives are high; tune rules with OT knowledge. For unauthorized firmware change: verify with asset inventory, isolate device, and investigate if it's a legitimate maintenance action.
