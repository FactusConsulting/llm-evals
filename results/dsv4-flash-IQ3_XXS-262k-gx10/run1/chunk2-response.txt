K1 — A Deployment manages stateless applications: it ensures a desired number of identical pods, supports rolling updates and rollbacks, and pods are interchangeable. A StatefulSet is for stateful applications: each pod has a stable identity (name, network ID), stable persistent storage (via PVCs), and ordered deployment/scaling (e.g., databases, Kafka).

K2 — A ClusterIP Service has a selector that matches pod labels. It creates an Endpoints object (or EndpointSlices) listing the IPs of matching pods. kube-proxy on each node programs iptables/IPVS rules to forward traffic destined to the Service’s ClusterIP:port to one of those pod IPs, using random or session-affinity-based load balancing.

K3 — A PersistentVolume (PV) is cluster-level storage provisioned either statically or dynamically. A PersistentVolumeClaim (PVC) is a request for storage by a user; it binds to a PV. A StorageClass defines the provisioner, parameters, and reclaim policy, enabling dynamic provisioning: a PVC with a storageClassName triggers automatic PV creation. Relationship: PVC → StorageClass → PV.

K4 — Troubleshooting CrashLoopBackOff:
1. `kubectl logs <pod> --previous` to see the last crash’s logs.
2. `kubectl describe pod <pod>` for events, image pull failures, liveness/readiness probe failures, and exit codes.
3. Check container exit code: 137 = OOMKilled, 1 = app error, etc.
4. `kubectl exec` into the container (if possible) to test connectivity, config, or run commands.
5. Verify resource limits (memory/CPU) and node pressure.
6. Check dependent services (DB, API) and ConfigMap/Secret values.

K5 — CoreDNS is the cluster DNS server. It serves DNS records for Services and Pods, enabling service discovery. If CoreDNS pods are down, DNS queries fail, so Services cannot be resolved by name, but direct pod IPs and ClusterIPs still work. Existing DNS caches in pods may persist until TTL expires.

K6 — The scheduler uses a two-phase process:
- **Filtering** removes nodes that cannot run the pod: insufficient resources (requests), node selector mismatch, taints not tolerated, affinity/anti-affinity conflicts, volume zone mismatches, node pressure, etc.
- **Scoring** ranks remaining nodes based on factors like: resource fit (requested vs. allocatable), image locality (node already has the image), spread topology (zone/region), inter-pod affinity, and node preferences.
The node with the highest score is chosen.

K7 — Node has 4GB RAM, 3.5GB already requested, leaving 0.5GB (512Mi). The pod requests 256Mi, so it fits and will be scheduled (assuming no other constraints). If the pod actually uses 600Mi at runtime, it exceeds its limit of 512Mi; the kernel OOM killer will terminate the container (or the pod may be evicted if node memory is under pressure).

K8 — Request lifecycle:
1. Client hits external load balancer (cloud LB).
2. LB forwards to the Ingress controller’s Service (NodePort or LoadBalancer).
3. NGINX Ingress controller pod receives traffic, terminates TLS, and applies Ingress rules (host/path).
4. It selects the backend Service (ClusterIP) defined in the Ingress.
5. kube-proxy updates iptables/IPVS rules for that Service.
6. Traffic is DNATed to a pod IP from the Endpoints list.
7. Application pod receives the request.

K9 — A NetworkPolicy controls traffic to/from selected pods using labels, namespaces, and IP blocks. Default behavior: if no NetworkPolicy exists, all traffic is allowed. When you apply a NetworkPolicy that selects certain pods, those pods become isolated: only traffic explicitly allowed by the policy is permitted; if the policy has no rules, it denies all traffic to/from those pods.

K10 — RollingUpdate gradually replaces old pods with new ones, keeping the service available and allowing rollback. Recreate terminates all old pods before creating new ones, causing downtime. Choose Recreate when the application cannot run multiple versions simultaneously (e.g., incompatible database schema migrations) or requires exclusive access to shared resources.

K11 — A namespace is a logical partition that isolates resources (pods, services, RBAC, quotas) within a cluster. Default namespaces: `default`, `kube-system`, `kube-public`, and `kube-node-lease` (in newer clusters).

K12 — `kubectl describe pod` shows detailed information not in `kubectl get pod`, including:
1. Events (warnings, scheduling failures, probe failures).
2. Node assignment and pod IP.
3. Container statuses (restart count, state, image).
4. Resource requests/limits.
5. Labels, annotations, tolerations, volumes, and conditions.

K13 — A ConfigMap stores key-value configuration data. Pods consume it via:
1. Environment variables (`valueFrom.configMapKeyRef`).
2. Volume mounts (ConfigMap as files).
3. Command-line arguments using env expansion.
4. Also as a volume for individual keys.

K14 — ClusterIP: internal virtual IP, only reachable inside the cluster. NodePort: exposes a static port on every node’s IP, accessible externally via `nodeIP:nodePort`. LoadBalancer: provisions a cloud provider load balancer that routes external traffic to the Service (which internally uses NodePort/ClusterIP).

K15 — A DaemonSet ensures one pod runs on every node (or a subset). Use it for node-level daemons like log collectors (Fluentd), monitoring agents (Prometheus node exporter), network plugins, or storage daemons. A Deployment manages a set of replicas across the cluster, not per-node.

K16 — Taints and tolerations: taints are applied to nodes to repel pods; a pod must have a matching toleration to be scheduled. Node affinity attracts pods to nodes based on labels (required or preferred). Taints/tolerations are for **preventing** scheduling; affinity is for **preferring** scheduling. Use case: taint a GPU node with `gpu=true:NoSchedule` and add toleration to GPU workloads; use node affinity to co-locate services in the same zone.

K17 — A Kubernetes Operator is a controller that extends the Kubernetes API using Custom Resource Definitions (CRDs) to manage complex applications. It automates operational tasks like backups, upgrades, scaling, and self-healing. A standard controller watches built-in resources (e.g., Deployment); an Operator watches custom resources and implements domain-specific logic. The Operator pattern solves the problem of encoding human operational knowledge into automation.

K18 — etcd uses the Raft consensus algorithm. It requires a quorum (majority) of nodes to elect a leader and commit writes. If quorum is lost (e.g., 2 of 3 etcd nodes are down), the cluster becomes read-only or unavailable for writes, and no leader can be elected. Recovery from permanent loss of 2 nodes: stop the remaining etcd node, take a snapshot, restore it to a new etcd cluster, and update the Kubernetes API server configuration to point to the new etcd endpoints.

K19 — RBAC:
- **Role**: permissions within a single namespace.
- **ClusterRole**: permissions cluster-wide (or across all namespaces).
- **RoleBinding**: binds a Role to a user/SA within a namespace.
- **ClusterRoleBinding**: binds a ClusterRole cluster-wide.

For a developer needing read-only access to pods and logs in namespace `dev`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: pod-reader-binding
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — The default `ndots:5` in `/etc/resolv.conf` means that if a domain has fewer than 5 dots, the resolver tries the search domains first. For an external domain like `example.com` (1 dot), it first tries `example.com.namespace.svc.cluster.local`, then `example.com.svc.cluster.local`, etc., causing many DNS queries and delays. Fix: set `dnsConfig` in the pod spec to `ndots: 1` (or 2) and optionally reduce search domains, or use a fully qualified domain name with a trailing dot.

D1 — `git rebase` rewrites commit history by applying commits onto a new base, creating a linear history. `git merge` creates a merge commit, preserving the full branch history. Avoid rebasing shared/public branches because it rewrites history and can cause conflicts for other developers who have based work on the old commits.

D2 — TCP is connection-oriented, reliable, ordered, and uses handshakes; used by HTTP, SSH, FTP. UDP is connectionless, unreliable, low-latency; used by DNS, video streaming, NTP, VoIP.

D3 — A race condition occurs when multiple threads access shared data without synchronization, and the outcome depends on the timing of execution. Example (Python):

```python
counter = 0
def increment():
    global counter
    temp = counter
    # context switch
    counter = temp + 1
# Two threads call increment() concurrently; both read counter=0, both write 1, losing one increment.
```

D4 — Symmetric encryption uses the same key for encryption and decryption (fast). Asymmetric encryption uses a public/private key pair (slow). In TLS: the client verifies the server’s certificate using asymmetric encryption, then the client and server exchange a session key (often via ECDHE) using asymmetric cryptography, and finally use symmetric encryption for the actual data transfer.

D5 — Container image layers are read-only filesystem diffs created by each Dockerfile instruction. Layer caching allows unchanged layers to be reused from the cache, speeding up builds. Best practices: order instructions from least to most changing (e.g., copy package files first, then run install, then copy source), combine `apt-get install` commands, use `.dockerignore`, and minimize the number of layers.

D6 — For intermittent HTTP 503:
1. Check application logs for errors or stack traces.
2. Check load balancer health checks and target group status.
3. Check backend CPU/memory and request rate (capacity saturation).
4. Check database connection pool and external API dependencies.
5. Check rate limiting or WAF rules.
6. Check network/firewall issues.

D7 — CAP theorem states that in a distributed system, during a network partition, you can choose Consistency (all nodes see same data) or Availability (every request gets a response), but not both. CP example: etcd/ZooKeeper (sacrifice availability during partition). AP example: Cassandra/DynamoDB (sacrifice consistency, eventually consistent).

D8 — Horizontal scaling adds more instances/nodes; vertical scaling increases resources (CPU/RAM) of a single instance. Patterns enabling horizontal scaling: stateless services, load balancing, shared/distributed storage, microservices, auto-scaling groups, and database sharding.

D9 — An environment variable is a key-value pair in the process environment. To persist across shell sessions on Linux, add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `~/.bash_profile`, then run `source ~/.bashrc`.

D10 — JSON is a text format with strict syntax (objects, arrays, strings, numbers). YAML is human-readable, indentation-based, supports comments, and is more flexible. JSON advantage: widely supported, strict parsing. YAML advantage: readability and ease of writing config files.

D11 — REST API is an architectural style using HTTP methods: GET (retrieve), POST (create), PUT (update/replace), DELETE (remove). It is stateless, resource-based, and uses status codes.

D12 — Version pinning means specifying exact dependency versions (e.g., `package-lock.json`, `requirements.txt` with `==`). It ensures reproducible builds by preventing unexpected changes from dependency updates.

D13 — Compiled languages are translated to machine code ahead of time (e.g., C, Go). Interpreted languages are executed line by line by an interpreter (e.g., Python, JavaScript). Some languages like Java use bytecode/JIT, but still considered compiled.

D14 — A reverse proxy sits in front of backend servers, forwarding client requests to them, providing load balancing, TLS termination, caching, and security. A forward proxy sits in front of clients, hiding them and filtering outbound traffic. Common reverse proxies: Nginx (load balancing, static serving), HAProxy (high-availability load balancing), and Traefik (API gateway).

D15 — A deadlock occurs when processes wait indefinitely for resources held by each other. Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait.

D16 — Eventual consistency means that if no new updates occur, all replicas will eventually converge to the same value. Cassandra handles read-after-write consistency via tunable consistency levels: `ONE` (fast, may read stale), `QUORUM` (majority), `ALL` (strongest). You can choose per query based on need.

D17 — mTLS (mutual TLS) requires both client and server to present certificates. Handshake: client sends hello, server sends its certificate, client verifies it, client sends its certificate, server verifies it, then key exchange and session key establishment. mTLS is used in service meshes (e.g., Istio), zero-trust networks, and API authentication.

D18 — A hash table uses a hash function to map keys to bucket indices. Collision resolution:
- **Chaining**: each bucket holds a linked list; insert/lookup/delete traverse the list.
- **Open addressing**: probing (linear, quadratic, double hashing) finds next empty slot.
Average time complexity: O(1) for insert/lookup/delete. Worst case: O(n) when many collisions.

D19 — Circuit breaker pattern: three states:
- **Closed**: normal operation, requests pass.
- **Open**: after failures exceed threshold, requests fail fast without hitting the service.
- **Half-open**: after a timeout, a few trial requests are allowed; if successful, close; if failed, reopen.
It prevents cascade failures by failing fast. Retry policies with exponential backoff avoid overwhelming a recovering service; circuit breaker stops retries when open.

D20 — Optimistic concurrency control assumes conflicts are rare: read data with a version/timestamp, update only if version matches, retry on conflict. Pessimistic concurrency locks rows (`SELECT FOR UPDATE`) to prevent conflicts. Choose optimistic for read-heavy, low-contention workloads; choose pessimistic for high-contention or when conflicts are costly (e.g., financial transactions).
