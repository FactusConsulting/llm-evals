### OpenTofu / Terraform

**T1 — Easy:**  
`tofu plan` reads the configuration and state, compares them, and shows the changes that would be made without applying them. `tofu apply` executes the changes proposed by the plan, updating the real infrastructure and state. You can also run `tofu apply` with a saved plan file to apply exactly the changes reviewed.

**T2 — Easy:**  
State is OpenTofu’s record of the current real-world infrastructure, mapping resources to their configuration and metadata. Remote state stores this file in a shared backend (e.g., S3, Terraform Cloud) instead of locally. It is important because it enables team collaboration, provides a single source of truth, supports state locking to prevent concurrent modifications, and allows the state to survive local machine failures.

**T3 — Medium:**  
`count` creates a list of resources indexed by numbers (0, 1, 2…), while `for_each` creates a map of resources keyed by unique values (e.g., strings). `for_each` is preferred when you need to reference each instance by a meaningful key, when the set of instances may change dynamically, or when you need to delete/update specific instances without affecting others. It also avoids the “index out of range” issues when reordering.

**T4 — Medium:**  
If you manually change a resource outside OpenTofu (e.g., via the cloud console), OpenTofu detects the drift during the next `plan` or `apply` by comparing the state to the actual infrastructure. It will propose an update to bring the resource back to the configuration-defined state. If the change is intentional, you can use `ignore_changes` in the `lifecycle` block or import the change into state.

**T5 — Medium:**  
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
  # other configuration...
}
```
This creates three VMs named `web1`, `web2`, and `web3`.

**T6 — Hard:**  
`terraform_remote_state` is a data source that reads outputs from another root module’s state file, creating a direct dependency on that state’s location and format. Output values are the standard way to expose data from a module, but they are only accessible within the same configuration. For sharing data between separate root modules, the recommended alternative is to use a shared data store (e.g., AWS SSM Parameter Store, Consul, or an HTTP API) that both modules can read/write. This decouples the modules, avoids state file coupling, and improves maintainability and security.

**T7 — Hard:**  
The issue occurs because the `null_resource` with a `remote-exec` provisioner runs after the resource is created, but the `kubeconfig` output is evaluated during the apply phase. If dependent resources reference that output, they may be created before the provisioner has finished, resulting in an empty value. The fix is to add an explicit `depends_on` in the dependent resources to ensure they wait for the `null_resource` to complete. Additionally, you can use a `local-exec` provisioner to write the kubeconfig to a file and then read it with a `file` data source, or use a `terraform_data` resource with a `triggers_replace` to force proper ordering.

**T8 — Medium:**  
`tofu import` (or `terraform import`) brings an existing resource into OpenTofu state so it can be managed. Limitations: you must manually write the configuration for the resource, it imports only the resource itself (not its dependencies), and it does not automatically generate the configuration. The import block (introduced in 1.5) allows you to declare imports in the configuration itself, making the process more declarative, repeatable, and easier to review. It also supports generating configuration for some providers.

**T9 — Easy:**  
A `variable` (input variable) is a parameter that allows you to customize a module or root configuration without hardcoding values. An `output` is a value that a module exposes to its parent or to the CLI. Input variables are set via `-var`, `.tfvars` files, or environment variables; outputs are used to retrieve information after apply.

**T10 — Easy:**  
A provider is a plugin that enables OpenTofu to interact with a specific cloud or API (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without running `tofu init` first, OpenTofu will fail because the provider plugins are not installed and the provider schema is not available.

**T11 — Easy:**  
`.terraform.lock.hcl` is a dependency lock file that records the exact provider versions and checksums used. It should be committed to version control to ensure that everyone on the team uses the same provider versions, preventing unexpected changes and ensuring reproducible deployments.

**T12 — Easy:**  
`tofu destroy` removes all resources defined in the configuration (or the state) from the infrastructure. To destroy a single resource, use the `-target` flag: `tofu destroy -target=resource_type.name`. This will destroy only that resource and its dependencies.

**T13 — Easy:**  
A data source is a read-only query to the provider that retrieves information from the infrastructure (e.g., an AMI ID, a VPC ID, or a list of availability zones). You use a data source instead of a managed resource when you need to reference existing infrastructure that is not managed by OpenTofu, or when you need to fetch dynamic values that are not known until apply time.

**T14 — Medium:**  
`locals` are local values computed within a module, used for intermediate calculations or to simplify expressions. `variable` blocks are inputs that allow users to pass values into the module. Use `locals` when you need to derive values from other variables or resources, or when you want to avoid repeating complex expressions. Use `variables` when you need to make the module configurable from outside.

**T15 — Medium:**  
The `lifecycle` block controls resource creation/destruction behavior.  
- `create_before_destroy` creates a new resource before destroying the old one, enabling zero-downtime replacements (e.g., for an autoscaling group).  
- `prevent_destroy` prevents a resource from being destroyed, protecting critical infrastructure (e.g., a database).  
- `ignore_changes` tells OpenTofu to ignore specific attribute changes made outside of OpenTofu, preventing drift detection from triggering unwanted updates (e.g., auto-scaling group desired capacity).

**T16 — Medium:**  
A `moved` block tells OpenTofu that a resource or module has been renamed or moved to a new address in the configuration. It updates the state to reflect the new address without destroying and recreating the resource. This is useful when refactoring module structure, renaming resources, or moving resources between modules.

**T17 — Hard:**  
OpenTofu builds a dependency graph from references between resources. Implicit dependencies are created when one resource references another (e.g., using an attribute from another resource). Explicit dependencies are declared with `depends_on`. The graph determines the order of operations and parallelism: resources with no dependencies can be created in parallel, while dependent resources wait. `depends_on` forces a strict ordering and reduces parallelism, which can slow down apply. It should be used sparingly because it can hide missing implicit dependencies and make the graph less efficient.

**T18 — Hard:**  
Four strategies to reduce plan time:  
1. **Use `-refresh=false`** – Skips refreshing state from the provider, but may miss external changes. Tradeoff: plan may be based on stale data.  
2. **Targeted plans** – Use `-target` to limit the plan to specific resources, reducing the graph size. Tradeoff: you may miss changes in other resources.  
3. **Enable state caching** – Use a remote backend with caching (e.g., S3 with DynamoDB) to reduce state retrieval time. Tradeoff: requires additional setup and may still be slow for large states.  
4. **Split the configuration into smaller modules** – Break the codebase into independent modules with separate state files, allowing parallel plans. Tradeoff: increases complexity and requires orchestration.

**T19 — Hard:**  
OpenTofu uses state locking to prevent concurrent modifications. When a lock is not released (e.g., a CI pipeline crashes mid-apply), the lock remains held, blocking other operations. To manually break the lock, use `tofu force-unlock <lock-id>`. Risks: if another process is actually running, force-unlocking can cause state corruption or conflicts. Always verify that no other apply is in progress before forcing.

**T20 — Hard:**  
To migrate from local state to an S3-compatible backend with DynamoDB locking:  
1. Add a `backend "s3"` block to your configuration, specifying bucket, key, region, and `dynamodb_table` for locking.  
2. Run `tofu init -migrate-state`. OpenTofu will prompt to copy the existing local state to the new backend.  
3. Confirm the migration; the state file is copied to S3 and the local state is removed (or kept as backup).  
4. Verify by running `tofu state list` to ensure resources are still present, and `tofu plan` to confirm no unexpected changes.  
5. Check the S3 bucket to confirm the state file exists and the DynamoDB table is used for locking.

### Ansible

**A1 — Easy:**  
A **playbook** is a YAML file that defines one or more plays, each targeting a group of hosts and containing tasks. A **role** is a reusable, organized set of tasks, handlers, variables, and templates with a defined directory structure. A **task** is a single unit of work (e.g., install a package, copy a file) within a play or role.

**A2 — Easy:**  
`ansible_facts` is a dictionary of system information gathered by the `setup` module (e.g., OS, IP addresses, hardware). To access the OS family, use `ansible_facts['os_family']` or the shorthand `ansible_os_family`.

**A3 — Medium:**  
- `command` – Executes a command without shell features (no pipes, redirects, variable expansion). It is safe and idempotent if the command itself is idempotent.  
- `shell` – Executes a command through the shell, allowing pipes, redirects, and variable expansion. Use when you need shell features.  
- `raw` – Executes a command over SSH without using modules, useful when Python is not available on the target or for bootstrapping. Use `raw` for low-level operations or when modules are not yet installed.

**A4 — Medium:**  
Ansible achieves idempotency by checking the current state before making changes. For example, `yum: name=htop state=present` is idempotent because it only installs if not already installed. A non-idempotent task would be `command: echo "hello" > /tmp/file` because it overwrites the file every time, even if the content is identical.

**A5 — Medium:**  
```yaml
- name: Install htop
  package:
    name: "{{ item }}"
    state: present
  with_items:
    - "{{ 'htop' if ansible_os_family == 'Debian' else 'epel-release' }}"
    - "{{ 'htop' if ansible_os_family == 'RedHat' else '' }}"
  when: ansible_os_family in ['Debian', 'RedHat']
```
Alternatively, use separate tasks with `when` conditions:
```yaml
- name: Install htop on Debian
  apt: name=htop state=present
  when: ansible_os_family == "Debian"

- name: Install epel-release and htop on RedHat
  yum: name={{ item }} state=present
  with_items:
    - epel-release
    - htop
  when: ansible_os_family == "RedHat"
```

**A6 — Hard:**  
Ansible variable precedence (highest to lowest):  
1. `extra_vars` (command line)  
2. `set_fact` (runtime)  
3. `host_vars` (inventory)  
4. `group_vars` (inventory)  
5. `role defaults` (lowest within roles)  
6. Play vars, then inventory vars, then facts, etc.  
`extra_vars` override everything, `set_fact` overrides inventory and role defaults, and role defaults are the lowest priority.

**A7 — Hard:**  
To deploy RKE2 agents on 50 nodes with the first 3 completing before the rest:  
- Use an inventory group `rke2_agents` with all 50 nodes.  
- Create a play that runs on the first 3 nodes using `serial: 3` and a `when` condition based on inventory order, or split into two plays: one for the first 3 (using `serial: 1` or `serial: 3`) and another for the remaining 47.  
- Use `wait_for` to wait for the RKE2 agent port (e.g., 9345) to be open on the first 3 nodes before starting the rest.  
- Example:  
  ```yaml
  - hosts: rke2_agents[0:3]
    tasks:
      - name: Install RKE2 agent
        ...
      - name: Wait for agent to be ready
        wait_for: port=9345 host={{ inventory_hostname }} timeout=300

  - hosts: rke2_agents[3:]
    tasks:
      - name: Install RKE2 agent
        ...
  ```

**A8 — Medium:**  
`ansible-vault` encrypts sensitive data. To encrypt a single variable inside a vars file without encrypting the whole file, use `ansible-vault encrypt_string` to generate an encrypted string, then place it in the vars file. For example:  
```bash
ansible-vault encrypt_string 'mysecret' --name 'db_password'
```
Then paste the output into the vars file. The variable will be decrypted at runtime when the vault password is provided.

**A9 — Easy:**  
An inventory file defines the hosts and groups that Ansible manages. A **static inventory** is a plain text file (INI or YAML) that lists hosts and groups. A **dynamic inventory** is a script or program that generates the inventory on the fly, pulling from cloud providers, LDAP, or other sources, allowing Ansible to manage ephemeral infrastructure.

**A10 — Easy:**  
```bash
ansible webservers -m command -a "df -h"
```
This runs the `df -h` command on all hosts in the `webservers` group.

**A11 — Easy:**  
A handler is a task that runs only when notified by another task via `notify`. It is typically used for actions like restarting a service after a config change. Handlers run once at the end of the play, even if notified multiple times. To trigger a handler, use `notify: handler_name` in a task.

**A12 — Easy:**  
`ansible.cfg` is the configuration file for Ansible, setting defaults for the control node. Common settings: `inventory` (path to inventory file), `forks` (number of parallel processes), `roles_path` (directory for roles), `remote_user` (default SSH user), and `host_key_checking` (enable/disable SSH host key verification).

**A13 — Easy:**  
`register` captures the output of a task (stdout, stderr, exit status) into a variable. For example:  
```yaml
- command: cat /etc/hostname
  register: hostname_output
- debug: msg="Hostname is {{ hostname_output.stdout }}"
```
The registered variable can be used in subsequent tasks with conditionals or loops.

**A14 — Medium:**  
`include_tasks` dynamically includes tasks at runtime, allowing conditionals to be evaluated per host. `import_tasks` statically imports tasks at parse time, so conditionals are evaluated once for the entire play. Use `include_tasks` when you need to conditionally include tasks based on host-specific facts, and `import_tasks` when you want to ensure tasks are always included and to benefit from static analysis.

**A15 — Medium:**  
Ansible Galaxy is a community hub for roles and collections. A `requirements.yml` file lists roles and collections to install. Example:  
```yaml
roles:
  - name: geerlingguy.nginx
collections:
  - name: community.general
```
Install with `ansible-galaxy install -r requirements.yml`. This allows you to reuse community-maintained content.

**A16 — Medium:**  
Connection plugins define how Ansible connects to managed hosts.  
- `ssh` – Default, uses SSH to connect to remote hosts.  
- `local` – Runs tasks on the control node itself, useful for localhost or when no SSH is needed.  
- `network_cli` – Used for network devices (e.g., Cisco, Juniper) that support CLI over SSH, without requiring Python on the device.  
Choose `ssh` for most Linux/Unix hosts, `local` for control-node tasks, and `network_cli` for network hardware.

**A17 — Hard:**  
`delegate_to` runs a task on a different host than the one in the play’s `hosts`. `run_once` ensures a task runs only once per play, even if multiple hosts are targeted. Example: gather facts from a remote host, then run a task on localhost using those facts.  
```yaml
- hosts: webservers
  tasks:
    - name: Gather facts
      setup:
    - name: Print remote IP on localhost
      debug:
        msg: "Remote IP is {{ ansible_default_ipv4.address }}"
      delegate_to: localhost
      run_once: true
```

**A18 — Hard:**  
Four strategies to improve performance for 500 hosts:  
1. **Increase `forks`** – Run more tasks in parallel. Tradeoff: higher memory and SSH connection overhead.  
2. **Enable SSH pipelining** – Reduce SSH connections by reusing them. Tradeoff: requires `requiretty` disabled on sudo.  
3. **Use fact caching** – Cache facts to avoid gathering them on every run. Tradeoff: facts may become stale.  
4. **Use Mitogen or async** – Mitogen speeds up SSH by using a faster transport; async allows long-running tasks to run in background. Tradeoff: Mitogen requires extra installation and may have compatibility issues; async complicates error handling.

**A19 — Hard:**  
Jinja2 templating in Ansible uses:  
- `{{ }}` for expressions (e.g., `{{ ansible_os_family }}`)  
- `{% %}` for statements (e.g., `{% for server in servers %}`)  
- `{# #}` for comments (ignored in output)  
Template snippet for nginx upstream:  
```nginx
upstream backend {
{% for server in backend_servers %}
    server {{ server }};  # health check enabled
{% endfor %}
}
```

**A20 — Hard:**  
Zero-downtime rolling deployment across 20 servers:  
- Use `serial: 5` to deploy in batches of 5.  
- Pre-task: remove each server from the load balancer (e.g., via API or script).  
- Deploy the new version (e.g., copy files, restart service).  
- Post-task: run a health check using `uri` module to verify the service responds.  
- If health check fails, use `block`/`rescue` to rollback: in the `rescue` block, restore the previous version and re-add the server to the load balancer.  
- After each batch, wait for the load balancer to re-add the servers and verify overall health.  
Example structure:  
```yaml
- hosts: webservers
  serial: 5
  tasks:
    - block:
        - name: Remove from LB
          ...
        - name: Deploy new version
          ...
        - name: Health check
          uri:
            url: http://{{ inventory_hostname }}/health
            return_content: yes
      rescue:
        - name: Rollback
          ...
        - name: Re-add to LB
          ...
```
