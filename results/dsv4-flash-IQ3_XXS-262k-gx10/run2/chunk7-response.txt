## Application Architecture

### AA1
A monolith is a single deployable unit where all components are tightly coupled, while microservices decompose an application into independently deployable services. Three concrete problems microservices introduce that monoliths don't:
1. **Network latency and partial failures** – remote calls can fail or time out, requiring resilience patterns.
2. **Distributed data consistency** – transactions span services, requiring sagas or eventual consistency.
3. **Operational complexity** – many services need orchestration, monitoring, and deployment pipelines.

### AA2
Synchronous communication blocks the caller until a response is received (e.g., REST/HTTP, gRPC). Asynchronous communication decouples sender and receiver via messages (e.g., Kafka, RabbitMQ, MQTT). Synchronous is simpler for request-reply; asynchronous improves resilience and scalability.

### AA3
An API Gateway is a specialized reverse proxy that adds cross-cutting concerns: authentication, rate limiting, request routing, aggregation, and API management. A reverse proxy typically only forwards traffic (e.g., Nginx, HAProxy). An API Gateway can replace a reverse proxy for most application-level routing, but a reverse proxy may still be needed for low-level TCP/UDP load balancing, TLS termination at the edge, or when a lightweight solution is preferred.

### AA4
The Saga pattern manages distributed transactions by breaking them into a series of local transactions with compensating actions. **Choreography** uses events: each service publishes events and reacts to others; no central coordinator. **Orchestration** uses a central coordinator that tells each service what to do. Choreography is simpler and more decoupled but harder to track; orchestration is more centralized and easier to monitor. Use choreography for simple workflows with few services; use orchestration for complex workflows requiring clear control and rollback.

### AA5
CQRS separates read models (queries) from write models (commands). Event Sourcing stores state changes as an immutable event log. Combined, writes append events, and reads are served from projections built from those events. This solves problems like scalability (independent read replicas), auditability (full history), and complex domain logic that traditional CRUD handles poorly (e.g., high contention, need for event replay).

### AA6
The Circuit Breaker pattern prevents an application from repeatedly calling a failing service. It has three states: **closed** (normal), **open** (fail fast), and **half-open** (trial a limited number of requests). Unlike simple retry with backoff, which only handles transient errors, a circuit breaker stops calls for a longer period, allowing the downstream service to recover. Use both: retry for transient failures (e.g., network blips) and circuit breaker for sustained outages.

### AA7
| Model | Cost | Security | Operational Complexity | Noisy-Neighbor Risk |
|-------|------|----------|------------------------|---------------------|
| Shared DB, shared schema | Lowest | Weakest (row-level isolation, SQL injection risk) | Low (one schema) | High (resource contention) |
| Shared DB, separate schema | Moderate | Better (schema-level isolation) | Moderate (multiple schemas) | Medium |
| Separate DB per tenant | Highest | Strongest (full isolation) | High (many DBs to manage) | Low (dedicated resources) |

### AA8
Eventual consistency means updates propagate asynchronously and reads may see stale data; strong consistency guarantees every read sees the latest write. For an inventory system that must never oversell, use strong consistency. Architect with a single-node database per item (or use a distributed DB with linearizable transactions), optimistic locking (e.g., conditional updates), and a queue to serialize updates. At scale, partition by item ID and use a strongly consistent store like etcd or a relational DB with row-level locks.

### AA9
A sidecar proxy is a lightweight proxy deployed alongside each service instance, handling all network traffic. In Istio, Envoy sidecars form the **data plane** (actual traffic), while Istio’s control plane (Pilot, Mixer, Citadel) configures and manages them. mTLS between sidecars provides service-to-service authentication and encryption, verifying both client and server identities, which application-level TLS (often only server-side) does not.

### AA10
The Strangler Fig pattern incrementally replaces parts of a monolith with new services. Strategy: identify seams (e.g., modules, APIs), extract one service at a time, route traffic through a facade/proxy that redirects requests to the new service, and gradually decommission old code. For a .NET Framework monolith to .NET 8 microservices, start with low-risk, high-value modules, use an API gateway to route, and maintain a database per service with data migration.

### AA11
The 12-Factor App methodology includes: 
1. **Codebase** – one codebase per app, tracked in VCS.
2. **Dependencies** – explicitly declare and isolate dependencies.
3. **Config** – store config in environment variables.
4. **Backing services** – treat them as attached resources.
5. **Build, release, run** – strict separation of stages.
6. **Processes** – run as stateless processes.
7. **Port binding** – export services via ports.
8. **Concurrency** – scale out via processes.
9. **Disposability** – fast startup and graceful shutdown.
10. **Dev/prod parity** – keep environments similar.
11. **Logs** – treat logs as event streams.
12. **Admin processes** – run as one-off processes.
These factors enable cloud-native deployments by promoting portability, scalability, and resilience.

### AA12
**Event-driven (Kafka)** vs **request-driven (REST/gRPC)**:
- **Coupling**: Event-driven is decoupled (producers/consumers don’t know each other); request-driven is tightly coupled.
- **Scalability**: Event-driven scales independently (consumers can be added); request-driven requires load balancing and session affinity.
- **Debugging**: Event-driven is harder to trace (async, no direct response); request-driven is easier.
- **Ordering**: Kafka preserves order per partition; REST has no ordering guarantee.
- **Failure handling**: Event-driven can retry/replay; request-driven fails immediately.
Choose event-driven for asynchronous workflows, high throughput, and decoupling; choose request-driven for low-latency, synchronous interactions, and simple CRUD.

### AA13
A load balancer distributes incoming traffic across multiple servers. Layer 4 (transport) balances based on IP and port (e.g., TCP/UDP). Layer 7 (application) balances based on HTTP headers, URLs, cookies, etc. Layer 7 is required for content-based routing (e.g., /api to one backend, /web to another), SSL termination, and sticky sessions.

### AA14
A message queue (e.g., RabbitMQ) delivers messages to consumers and removes them after acknowledgment; it supports complex routing and priority. A log-based broker (e.g., Kafka) stores an immutable log of events, allows replay, and supports multiple consumers with offsets. Choose RabbitMQ for task queues and RPC-style patterns; choose Kafka for event streaming, log aggregation, and replayable data.

### AA15
A container shares the host OS kernel and isolates processes, while a VM includes a full OS with its own kernel. Containers are lightweight (MBs), start in seconds, and are portable. They are popular for microservices because they enable consistent environments, efficient resource usage, and fast scaling.

### AA16
Stateless services do not store session data between requests; each request is independent. Stateful services maintain state (e.g., databases, caches). Stateless services are easier to scale horizontally because any instance can handle any request; stateful services require session affinity or shared storage. Example: a stateless web server (e.g., Nginx) vs a stateful database (e.g., PostgreSQL).

### AA17
An ORM maps database tables to objects in code, automating CRUD operations. Examples: Hibernate (Java), Entity Framework (C#), SQLAlchemy (Python). Trade-offs: ORMs increase productivity and reduce boilerplate but can cause performance issues (N+1 queries) and hide SQL complexity; raw SQL gives full control and optimization but is more verbose and error-prone.

### AA18
The Bulkhead pattern isolates failures by partitioning resources (e.g., thread pools, connections) so a failure in one part doesn’t exhaust resources for others. In microservices, you can use separate thread pools for each downstream service or deploy services in separate containers/VMs. Example: a service calls two external APIs; give each API its own thread pool with a max size, so if one API is slow, it doesn’t block the other.

### AA19
**OT** (Operational Transformation) requires a central server to coordinate transformations; it provides strong consistency and low latency but is complex and has poor offline support. **CRDTs** (Conflict-free Replicated Data Types) are commutative and associative, allowing eventual consistency without a central coordinator; they support offline editing and merge automatically. For a system that must support offline editing, choose CRDTs because they handle concurrent edits without a server and merge seamlessly.

### AA20
Distributed tracing across polyglot services requires propagating trace context (e.g., W3C Trace Context, B3) via HTTP headers or message metadata. Sampling strategies: head-based (sample at the start) vs tail-based (sample after completion). Trace storage/querying: Jaeger, Tempo. For async messaging (Kafka), inject trace context into message headers so consumers can continue the trace. Ensure trace continuity by propagating the same trace ID and span ID across all hops, including Kafka producers/consumers.

## On-Premise Infrastructure Architecture

### OP1
Type 1 hypervisor runs directly on hardware (bare-metal), e.g., VMware ESXi, Microsoft Hyper-V. Type 2 hypervisor runs on top of an OS, e.g., VirtualBox, VMware Workstation. Type 1 is more efficient and stable for production; Type 2 is for development/testing.

### OP2
SAN (Storage Area Network) provides block-level storage via Fibre Channel or iSCSI; NAS (Network Attached Storage) provides file-level storage via NFS or SMB. Use SAN for databases requiring low latency and high throughput; use NAS for file sharing and general-purpose storage.

### OP3
3-tier network: core (high-speed backbone), distribution (policy/routing), access (end-user connectivity). Leaf-spine uses two layers: leaf switches connect to servers, spine switches interconnect leafs. Leaf-spine solves the bottleneck of east-west traffic and provides predictable latency and scalability, unlike 3-tier which is hierarchical and can have oversubscription.

### OP4
A highly available Proxmox cluster with shared storage: use at least 3 nodes for quorum. Quorum requires majority to avoid split-brain. Fencing via watchdog or IPMI to remove failed nodes. Shared storage options: Ceph (preferred for scalability), iSCSI (centralized), NFS (simple). On node failure, HA services migrate to healthy nodes.

### OP5
VLAN trunking uses 802.1Q tagging to carry multiple VLANs on a single link. On Linux, create VLAN interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`, then assign IPs. The NIC must be in trunk mode on the switch.

### OP6
RAID 1: mirror (2 disks), RAID 5: striping with single parity (min 3), RAID 6: double parity (min 4), RAID 10: stripe of mirrors (min 4), RAID Z2: ZFS double parity (min 4). For 6 drives on a database server, choose RAID 10 for best performance and fault tolerance (survives two disk failures if in different mirrors).

### OP7
DNS architecture: internal recursive resolvers (e.g., Windows AD DNS) for internal queries, authoritative servers for internal zones. DMZ uses separate authoritative servers with split-horizon (internal vs external views). DNSSEC on external zone. Forwarders for external queries, conditional forwarding for AD domains. When a laptop moves between office and VPN, DNS updates via DHCP and the client uses the appropriate resolver (internal or VPN).

### OP8
PKI chain: root CA (offline) signs subordinate CA, which issues end-entity certificates. Use CRL (Certificate Revocation List) or OCSP (Online Certificate Status Protocol) for revocation. Certificate templates define attributes; auto-enrollment via GPO. Compromised subordinate CA: revoke its certificate, reissue, and rebuild. Compromised root CA: catastrophic – must rebuild entire PKI and revoke all certificates.

### OP9
WAN options: MPLS (reliable, low latency, expensive), IPsec VPN over internet (cheaper, less reliable), SD-WAN (dynamic, uses multiple links, good for VoIP), WireGuard mesh (simple, secure, but requires internet). For 50 users per site with latency-sensitive VoIP, recommend SD-WAN (or MPLS if budget allows) for low latency and failover.

### OP10
iDRAC/iLO/IPMI are out-of-band management interfaces for remote server management (BIOS, power, console). Critical for troubleshooting when network/OS is down. Exposing IPMI to the internet is a severe security risk – attackers can gain full control; always isolate on a management network.

### OP11
LVM: logical volume management with snapshots (copy-on-write). LVM-Thin: thin provisioning, better snapshot efficiency. ZFS: filesystem with built-in volume management, checksums, and snapshots. Use LVM for simple volume management, LVM-Thin for thin provisioning, ZFS for data integrity and advanced features.

### OP12
A stretch cluster with Ceph across two sites requires CRUSH rules to place data across sites, monitors in both sites (odd number), and low latency (<10ms RTT). Split-brain is avoided with a tiebreaker (third site or witness). 2-site Ceph without a tiebreaker is bad because a network partition can cause both sites to operate independently, leading to data divergence.

### OP13
DHCP DORA: Discover (client broadcasts), Offer (server offers IP), Request (client requests), Ack (server acknowledges). If DHCP is unavailable and lease expires, Windows client uses APIPA (169.254.x.x) and continues to retry.

### OP14
Managed switches offer VLANs, QoS, SNMP, port security, link aggregation, and remote management. Unmanaged switches are plug-and-play but lack these features. Enterprise environments need managed switches for segmentation, monitoring, and security.

### OP15
NTP synchronizes clocks across servers. Accurate time is critical for Kerberos authentication, log correlation, distributed databases, and TLS. Clock drift can cause authentication failures, inconsistent timestamps, and split-brain in clusters.

### OP16
Physical server: dedicated hardware. VM: virtualized hardware with its own OS. Container: OS-level virtualization. Run on bare metal for performance-critical workloads, specialized hardware (GPU, NVMe), or when virtualization overhead is unacceptable.

### OP17
UPS provides short-term battery power (minutes) to allow graceful shutdown. Generator provides long-term power (hours/days). ATS (Automatic Transfer Switch) automatically switches between utility power and generator/UPS. Both are needed for continuous uptime.

### OP18
Active-passive: one node handles traffic, the other is standby. Active-active: both nodes handle traffic. For PostgreSQL HA with Pacemaker/Corosync: configure STONITH (fencing) to prevent split-brain, use a virtual IP that moves to the active node, and failover automatically promotes the standby.

### OP19
Backup strategy: 3-2-1 rule (3 copies, 2 media, 1 offsite). Define RPO/RTO. Use full/incremental/differential backups. Deduplication reduces storage. Tape for archival, disk for fast recovery, cloud for offsite. Immutable backups protect against ransomware. Test restores regularly. Backup is copying data; disaster recovery is the process of restoring IT infrastructure after a disaster.

### OP20
802.1X: supplicant (client) requests access, authenticator (switch) forwards to authentication server (RADIUS). EAP-TLS uses certificates; PEAP uses passwords. RADIUS authenticates and can assign dynamic VLAN. Failed devices are denied or placed in a guest VLAN. MAB (MAC Authentication Bypass) uses the device MAC address as credentials for devices that don’t support 802.1X, allowing them on the network with limited access.
