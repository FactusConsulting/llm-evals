## SC1 — Medium — Broken Deployments After Cluster Upgrade

### SC1-A
The failure occurs because the cluster now enforces the **Restricted** Pod Security Standard, which requires that containers **must not run as root**. The affected pods set `securityContext.runAsNonRoot: true` but do **not** set an explicit `runAsUser`. When `runAsNonRoot` is true, the kubelet checks the image's `USER` directive. The newly rebuilt images (based on `cgr.dev/chainguard/static:latest`) default `USER` to `root`. Since no `runAsUser` is provided, the kubelet refuses to start the container, resulting in `CrashLoopBackOff`. Under the previous **Baseline** standard, `runAsNonRoot` was not required, so the same configuration was accepted. The upgrade to Restricted made this a hard failure.

### SC1-B
```bash
kubectl get pods -A -o json | jq -r '
  .items[] |
  select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") |
  {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.containers[].securityContext}
'
```

### SC1-C
**Immediate fix:** Rebuild the affected images with a non‑root `USER` (e.g., `USER 65532:65532`) and push new tags.  
**Manifest fix:** Add explicit `runAsUser: 65532` (or any non‑zero UID) to the pod securityContext, or remove `runAsNonRoot` if the image is already non‑root.  
**CI pipeline gate:** Add a step that inspects the image manifest (e.g., `docker inspect --format='{{.Config.User}}'`) and fails the build if the USER is root or missing. Also validate that Kubernetes manifests set `runAsUser` when `runAsNonRoot` is true.  
**Rollout:** Use a rolling update with `maxSurge: 1` and `maxUnavailable: 0` to avoid downtime. Deploy the fixed images to a canary namespace first, then gradually roll out to production.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

### SC2-A
The stale data is caused by **asynchronous replication lag**. The promoted replica in eu‑west‑1 was not fully caught up with the primary in us‑east‑1 at the moment of promotion. Any transactions committed on the old primary after the last WAL position received by the replica are lost. Queries against the new primary return data as of the last replayed WAL, which is behind the old primary’s state. To quantify the loss window, check `pg_stat_replication` on the old primary (if still accessible) for `replay_lag` or `write_lag`, and on the replica check `pg_last_wal_replay_lsn` vs. the primary’s `pg_current_wal_lsn`. Also inspect the replica’s `pg_control` for the last checkpoint.

### SC2-B
1. **Import the promoted replica** into Terraform state:
   ```bash
   terraform import aws_db_instance.new_primary <new_instance_arn>
   ```
2. **Remove the old instance** from state:
   ```bash
   terraform state rm aws_db_instance.old_primary
   ```
3. **Update all references** in the Terraform code (security groups, Route53, parameter groups) to point to the new instance ID/ARN.
4. Run `terraform plan` to verify that no resources are marked for destruction or recreation. If any are, adjust the code to use `lifecycle { ignore_changes = [...] }` or `prevent_destroy` as needed.

### SC2-C
**Recommended architecture:** Use **Aurora Global Database** instead of standard RDS. Aurora Global Database provides a primary cluster in one region and up to five secondary clusters in other regions with **typical replication lag under 1 second**. It supports automatic failover and promotes a secondary with minimal data loss.  
**Connection management:** Use **RDS Proxy** (or PgBouncer) in each region to pool connections and handle failover transparently.  
**DNS failover:** Use Route53 health checks on the primary endpoint and a failover routing policy to redirect traffic to the secondary region.  
**Application retry:** Implement retry logic with exponential backoff for transient connection errors.  
**RPO < 1 second:** Aurora Global Database’s synchronous replication (within the global cluster) meets this requirement. For standard RDS, you would need to use synchronous replication (e.g., `synchronous_commit = on` and `synchronous_standby_names`), but cross‑region synchronous replication is not supported by RDS.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

### SC4-A
**Top 5 blockers and solutions:**
1. **Sticky sessions (local memory):** Kubernetes pods are ephemeral and can be rescheduled. Solution: Externalize sessions to Redis or use a session affinity with a load balancer, but better to use a distributed cache.
2. **Local NFS mount (`/data/uploads`):** Pods need shared, persistent storage. Solution: Use an NFS CSI driver (e.g., `nfs.csi.k8s.io`) with a `ReadWriteMany` PersistentVolume.
3. **Oracle 19c database:** Running a stateful database in Kubernetes is complex. Solution: Use a managed Oracle service (e.g., Oracle Cloud or RDS for Oracle) or run Oracle in a StatefulSet with persistent storage and proper backups.
4. **IBM MQ integration:** The monolith communicates with a mainframe via MQ. Solution: Run an MQ client as a sidecar container or use a Kubernetes-native MQ integration (e.g., IBM MQ on Kubernetes).
5. **Stateful application logic:** The monolith may rely on local filesystem state. Solution: Refactor to use external storage (S3, NFS) and make the application stateless.

### SC4-B

**Why ReadWriteMany?** The monolith writes uploaded files to a shared mount. Multiple replicas (or pods) must be able to read/write the same files concurrently, which requires `ReadWriteMany` access mode.

### SC4-C
**Phased migration (Strangler Fig):**
- **Phase 1:** Move static assets (e.g., CSS, JS) to an object store (S3) and serve via CDN. No downtime.
- **Phase 2:** Move session storage to Redis (external). Update the monolith to use Redis instead of local memory. Keep F5 routing to the monolith.
- **Phase 3:** Deploy the monolith to Kubernetes behind an Ingress. Use F5 to route a small percentage of traffic (e.g., 5%) to the Kubernetes Ingress, gradually increasing. Monitor latency and errors.
- **Phase 4:** Once stable, cut over fully and decommission the F5.

**Traffic splitting:** Use F5’s ratio or weighted pools to send a percentage of requests to the Kubernetes Ingress.  
**IBM MQ:** Run an MQ client sidecar in the Kubernetes pod, or use a Kubernetes-native MQ deployment.  
**Rollback:** Keep the legacy environment running until the new one is proven stable. If a phase fails, revert the traffic split to 100% legacy.  
**Go/no-go metrics:** p99 latency < 2s, error rate < 0.1%, CPU/memory within limits, and successful completion of business transactions.

## SC5 — Medium — Mysterious Latency Spike in Microservices

### SC5-A
**Systematic debugging:**
1. **Istio metrics:** Check `istio_request_duration_milliseconds` for the checkout-service to inventory-service call. Look at `istio_requests_total` for error codes.
2. **Envoy metrics:** Examine `envoy_http_downstream_rq_time` and `envoy_cluster_upstream_rq_time` for the sidecar. Specifically, `envoy_cluster_upstream_rq_time` (upstream response time) vs. `envoy_cluster_upstream_connection_time` (connection establishment). If upstream response time is high, the latency is in the inventory-service; if connection time is high, it’s network/proxy.
3. **Distributed tracing:** Use Jaeger to trace a request from checkout-service to inventory-service. Look at span durations for each hop. If the client span shows high duration but the server span is low, the latency is in the network or proxy. If both are high, the inventory-service is slow.
4. **Application logs:** Check inventory-service logs for slow queries, lock waits, or GC pauses.

### SC5-C
**Architectural solution:**
- **CQRS:** Separate the read path (serving queries) from the write/reconciliation path. Use a read replica for the reconciliation job.
- **Read replica:** Point the CronJob to a read replica to avoid lock contention on the primary.
- **Bulkhead isolation:** Use separate connection pools for the reconciliation job and the serving path (e.g., HikariCP with different pool sizes).
- **CronJob scheduling:** Move the reconciliation to off-peak hours (e.g., 02:00 UTC) or use a Kubernetes `CronJob` with a `startingDeadlineSeconds` and `concurrencyPolicy: Forbid`.
- **PodDisruptionBudget:** Create a PDB for the serving pods to prevent voluntary disruptions during the CronJob.
- **Resource quotas:** Set resource requests/limits for the CronJob pods to prevent them from consuming all CPU/memory.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

### SC6-A
**Identity and access layer:**
- **Workload identity:** Deploy **SPIFFE/SPIRE** in each environment (on-prem, AWS, Azure). Each workload gets a SPIFFE ID (e.g., `spiffe://trust-domain/workload/name`).
- **AWS IAM roles:** Use IAM roles for EKS pods (IRSA) to grant AWS permissions. Map the SPIFFE ID to an IAM role via OIDC.
- **Azure Managed Identities:** Use Azure AD Workload Identity for AKS pods, mapping SPIFFE IDs to Azure identities.
- **On-prem PKI:** Use SPIRE’s built-in CA or integrate with an existing PKI to issue short-lived certificates.
- **Federation:** Establish trust between SPIFFE trust domains (e.g., `spiffe://aws-prod`, `spiffe://on-prem`). Use SPIRE federation to allow workloads in AWS to authenticate to on-prem services via mTLS without shared secrets.

### SC6-C
**Comparison of connectivity options:**
- **AWS Direct Connect:** Dedicated 1 Gbps or 10 Gbps connection, lower latency, higher cost (monthly fee). Encryption requires IPsec over the connection. Failover requires a second connection.
- **Second VPN with ECMP:** Two VPN tunnels with equal-cost multipath routing, doubling bandwidth to 2 Gbps. Cost is per-hour, encryption is native IPsec. Failover is automatic if one tunnel fails.
- **Hybrid mesh (Tailscale/Netbird):** Overlay network using WireGuard, encrypted, can use existing internet. Bandwidth limited by internet, but can be scaled with multiple endpoints. Cost is per-user/per-device. Fits zero-trust by providing identity-based access.

**Routing changes:**
- Direct Connect: Update BGP routes to advertise VPC CIDRs over the DX connection.
- Second VPN: Configure both tunnels in a VPN connection and enable ECMP on the CGW.
- Mesh: Install agents on all workloads and use the mesh’s routing.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

### SC7-A
**Drift sources:**

2. **Helm values divergence:** Staging and production values files were edited directly, not tracked in Git, leading to configuration drift.

## SC9 — Medium — Securing a Public-Facing API After a Breach

### SC9-A
**Vulnerabilities and fixes:**
1. **BOLA (OWASP API1: Broken Object Level Authorization):** Users can access other users’ records by changing IDs. Fix: Implement object-level permissions in the view. Use `get_object` to check ownership.
2. **Over-fetching (OWASP API3: Excessive Data Exposure):** API returns internal fields. Fix: Use serializers that only expose necessary fields.
3. **No rate limiting (OWASP API4: Lack of Resource & Rate Limiting):** Attacker extracted 100k records. Fix: Add rate limiting at the API gateway or application level.
4. **API keys in URL (OWASP API2: Broken Authentication):** Keys are logged. Fix: Move keys to headers, rotate compromised keys, and use short-lived tokens.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

### SC10-A
**Multi-cluster architecture comparison:**
- **Active-passive with Velero:** Backup and restore to DR. RPO depends on backup frequency (e.g., hourly backups) and RTO on restore time. With 200TB of MinIO, restoring could take hours, exceeding RTO. Not suitable.
- **Active-active with service mesh (Istio multi-cluster or Cilium Cluster Mesh):** Both clusters serve traffic, with data replication. RPO can be near-zero if synchronous replication is used, but cross-site latency (12ms) may impact performance. For PostgreSQL, use synchronous replication (Patroni with `synchronous_commit`). For Redis, use Sentinel with cross-site replication. For RabbitMQ, use federation or quorum queues. For MinIO, use site replication (continuous sync). This approach can meet RPO=15min and RTO=1h if failover is automated.

**Replication strategies:**
- **PostgreSQL:** Patroni with synchronous replication (synchronous_standby_names) to ensure zero data loss.
- **Redis:** Sentinel with cross-site replication (master-replica) and automatic failover.
- **RabbitMQ:** Use quorum queues and federation to replicate messages across sites.
- **MinIO:** Use site replication to continuously sync objects between sites.

### SC10-C
**Automated failover orchestration:**
1. **Failure detection:** Use health checks (e.g., Route53 health checks, Prometheus alerts) to detect site down. Define a threshold (e.g., 3 failed checks) to avoid false positives.
2. **DNS failover:** Update GSLB/DNS to point to Dallas endpoints.
3. **Patroni promotion:** Patroni automatically promotes the standby to primary when the primary fails.
4. **Redis Sentinel:** Sentinel promotes a replica to master.
5. **RabbitMQ:** Use quorum queues and federation; the DR site takes over.
6. **MinIO:** Site replication catches up; ensure the DR site is promoted to active.
7. **OpenTofu state:** Update the state to reflect the new primary (e.g., change the RDS instance ID or Patroni endpoint).

**Split-brain prevention:** Use a quorum-based system (e.g., etcd) and fencing mechanisms. Ensure only one site is active at a time.

**Failback:** Once Chicago recovers, reverse the replication direction, sync data, and switch back during a maintenance window. Update DNS and Terraform state accordingly.
