## Go

### G1
An array has a fixed length and is a value type; a slice is a dynamic view into an underlying array. When appending to a slice at capacity, Go allocates a new larger array, copies the existing elements, and returns a new slice referencing the new array.

### G2
`var x int` declares `x` with zero value (0). `x := 0` declares and initializes with type inference. You cannot use `:=` at package level (outside functions) or when the variable is already declared in the same scope (unless at least one new variable is on the left).

### G3
A goroutine is a lightweight thread managed by the Go runtime, with a growable stack and multiplexed onto OS threads. The GMP model: G (goroutine), M (OS thread), P (logical processor). The scheduler distributes runnable goroutines across P’s, which are bound to M’s, enabling efficient concurrency.

### G4
Channels are typed communication pipes. An unbuffered channel blocks send until a receiver is ready and blocks receive until a sender is ready. A buffered channel has capacity; sending to a full buffered channel blocks until space is available. Receiving from an empty buffered channel blocks until a value is sent.

### G5
The `context` package carries deadlines, cancellation signals, and request-scoped values. Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
resp, err := http.DefaultClient.Do(req)
if err != nil { /* handle timeout/cancel */ }
```

### G6
Go interfaces are satisfied implicitly—a type implements an interface if it has all required methods, no explicit declaration. Unlike Java/C#, this is structural typing. The empty interface `interface{}` (or `any`) accepts any type, enabling generic-like code but requiring type assertions, which can lead to runtime panics if unchecked.

### G7
The code has a data race: `ready` and `data` are accessed without synchronization. Go’s memory model does not guarantee visibility across goroutines without explicit synchronization. Correct alternatives: use a channel, `sync.Mutex`, or `sync/atomic` to establish happens-before relationships.

### G8
`sync.Mutex` provides exclusive locking; `sync.RWMutex` allows multiple readers or one writer, improving concurrency for read-heavy workloads. `sync.Map` is optimized for specific cases: when keys are written once and read many times, or when goroutines access disjoint keys. A regular map with a mutex is simpler and often faster for general use; `sync.Map` avoids lock contention but has overhead for small maps.

### G9
Go modules are versioned units of packages. `go.mod` declares module path, Go version, and dependencies; `go.sum` contains cryptographic checksums for dependency verification. `go mod tidy` adds missing dependencies and removes unused ones. Minimum Version Selection (MVS) chooses the minimum version of each dependency that satisfies all transitive requirements, ensuring reproducible builds.

### G10
`defer` schedules a function call to run when the surrounding function returns. Multiple defers execute in LIFO order. A common gotcha: deferring in a loop accumulates calls until function exit, not per iteration; also, arguments are evaluated immediately, so `defer fmt.Println(i)` captures the current `i`, not the final value.

### G11
A pointer stores the memory address of a value. The zero value of a pointer is `nil`. To create a pointer to a struct literal: `p := &MyStruct{Field: 1}`.

### G12
`init()` runs automatically before `main()` for each package, after variable initialization. A package can have multiple `init()` functions; they execute in source order within a file, and files are processed in filename order (though this is not guaranteed across compilers). They are used for setup that cannot be done in variable initializers.

### G13
`make` is used only for slices, maps, and channels; it returns an initialized, usable value. `new` allocates memory for any type and returns a pointer to the zero value. For example, `new(int)` returns `*int` pointing to 0.

### G14
Error handling is explicit: functions return `error` values, and idiomatic code checks `if err != nil`. The `error` interface has `Error() string`. `errors.Is` checks for a specific sentinel error in the chain; `errors.As` finds a specific error type. `==` only works for direct comparison and fails with wrapped errors.

### G15
Built-in composite types:
- Map: zero value is `nil`; cannot be written to without initialization.
- Slice: zero value is `nil`; `len` and `cap` are 0.
- Channel: zero value is `nil`; sending/receiving blocks forever.
- Struct: zero value has all fields set to their zero values.

### G16
A race condition occurs when multiple goroutines access shared data without synchronization, and at least one writes. The `-race` flag instruments the code to detect data races at runtime. Example:
```go
var counter int
go func() { counter++ }()
go func() { counter++ }()
```
Fix with a mutex:
```go
var mu sync.Mutex
go func() { mu.Lock(); counter++; mu.Unlock() }()
```

### G17
`select` waits on multiple channel operations. It differs from `switch` in that it is specifically for channel communication and blocks until one case is ready. If multiple cases are ready, it picks one randomly. Timeout example:
```go
select {
case res := <-ch:
    // use res
case <-time.After(1 * time.Second):
    // timeout
}
```

### G18
Escape analysis determines whether a value is allocated on the stack or heap. If a value’s address escapes the function (e.g., returned, stored in a global), it goes to the heap. Inspect with `go build -gcflags=-m`. It matters because heap allocations increase GC pressure and overhead.

### G19
`reflect.Type` describes the type itself; `reflect.Value` holds the actual value and allows inspection/modification. Reflection is slow due to runtime type checks and should be avoided in hot paths. It is justified for serialization, testing, or generic utilities; code generation (e.g., `go generate`) is often a better alternative.

### G20
`go:embed` embeds files into the binary at compile time. Syntax: `//go:embed file.txt` for a single file, `//go:embed dir/*` for a directory, and `//go:embed all:dir` for recursive. It works with `string`, `[]byte`, or `embed.FS`. Limitations: cannot embed files outside the module, and paths with `..` are disallowed. `embed.FS` implements `io/fs.FS`, enabling standard filesystem operations.

## Rust

### R1
Ownership rules:
1. Each value has a single owner.
2. When the owner goes out of scope, the value is dropped.
3. Ownership can be transferred (moved) but not copied (unless type implements `Copy`).

### R2
`String` is an owned, heap-allocated UTF-8 string; `&str` is a borrowed string slice. Use `&str` for function parameters to accept both `String` and string literals without taking ownership; use `String` when you need to own or modify the string.

### R3
Borrowing creates references without transferring ownership. Rules:
- You can have many immutable references (`&T`) or one mutable reference (`&mut T`), but not both simultaneously.
- References must always be valid (no dangling references).
- The borrow checker enforces these at compile time.

### R4
`Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`); `Option<T>` represents presence (`Some(T)`) or absence (`None`). The `?` operator unwraps the value or returns the error from the function. Example:
```rust
fn read_file(path: &str) -> Result<String, io::Error> {
    std::fs::read_to_string(path)
}
```

### R5
- `Box<T>`: single owner, heap-allocated, used for recursive types or to avoid stack overflow.
- `Rc<T>`: single-threaded shared ownership with non-atomic reference counting.
- `Arc<T>`: thread-safe shared ownership with atomic reference counting.

### R6
Traits define shared behavior. Unlike Go interfaces, Rust traits can include associated types, generic parameters, and default methods. Trait objects (`dyn Trait`) use dynamic dispatch and are sized; generics with trait bounds (`T: Trait`) use static dispatch (monomorphization) and are more efficient.

### R7
The function lacks a lifetime parameter linking the input and output references. Fix:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This tells the compiler the returned reference lives as long as the shorter of the inputs.

### R8
`Send` means a type can be moved to another thread safely; `Sync` means it can be shared across threads. `Rc<T>` is not `Send` because its reference count is not atomic, so concurrent increments could corrupt it. `Arc<T>` uses atomic operations, making it `Send` and `Sync` (if `T: Send + Sync`).

### R9
`async`/`await` in Rust is based on `Future`—a state machine that can be polled. Executors like Tokio drive futures to completion, handling I/O and scheduling. Unlike Go’s goroutines (which are preemptively scheduled on OS threads), Rust async tasks are cooperative and must yield at `await` points.

### R10
`unsafe` allows:
1. Dereferencing raw pointers.
2. Calling unsafe functions (e.g., FFI).
3. Accessing mutable static variables.
4. Implementing unsafe traits.
It is justified for FFI, low-level memory manipulation, or performance-critical code where safety invariants are manually upheld.

### R11
Pattern matching with `match` is exhaustive—the compiler requires all possible cases to be handled. `if let` is a shorthand for matching a single pattern and ignores the rest. The compiler enforces exhaustiveness for `match`, preventing unhandled cases.

### R12
`Vec<T>` is a heap-allocated dynamic array; `[T; N]` is a fixed-size stack array. When `Vec` exceeds capacity, it allocates a new larger buffer, copies elements, and deallocates the old one.

### R13
Rust enums are sum types that can hold data (e.g., `enum Message { Quit, Move { x: i32, y: i32 } }`), unlike C/Java enums which are just integers. `Option<T>` is an enum with `Some(T)` or `None`, eliminating null pointer errors by forcing explicit handling.

### R14
`impl` blocks define methods and associated functions. Methods take `&self` (borrow), `&mut self` (mutable borrow), or `self` (consume). Associated functions (e.g., `String::new()`) do not take `self` and are called with `::`.

### R15
`derive` automatically generates trait implementations. Common traits: `Debug`, `Clone`, `PartialEq`, `Serialize` (via serde). You cannot derive a trait if the type’s fields do not implement that trait (e.g., `Clone` requires all fields to be `Clone`).

### R16
`Cow<'a, T>` (clone-on-write) is an enum that either borrows (`Borrowed`) or owns (`Owned`) data. It avoids allocation when you only need to read, and clones only when mutation is required. Example:
```rust
fn process(s: &str) -> Cow<'_, str> {
    if s.contains(" ") { Cow::Owned(s.replace(" ", "_")) } else { Cow::Borrowed(s) }
}
```

### R17
Modules are declared with `mod`, brought into scope with `use`, and made public with `pub`. In Rust 2015, paths are relative to the crate root; in 2018, paths are relative to the current module, and `use` paths are absolute or `crate::`/`self::`.

### R18
`Pin<T>` prevents the value from being moved, which is essential for self-referential structs (e.g., futures that hold pointers to their own fields). `Unpin` is an auto trait indicating a type can be moved freely; most types are `Unpin`, but `Pin` is needed for async futures.

### R19
Declarative macros (`macro_rules!`) match patterns and generate code. Procedural macros (derive, attribute, function-like) run code at compile time to generate tokens. Hygiene rules prevent name collisions by scoping macro variables to the macro’s definition site.

### R20
Zero-cost abstractions mean high-level code compiles to efficient machine code without runtime overhead. Iterators are inlined and optimized into loops; generics are monomorphized (specialized per type) enabling static dispatch; trait bounds with generics avoid virtual calls. This yields performance comparable to hand-written C.
