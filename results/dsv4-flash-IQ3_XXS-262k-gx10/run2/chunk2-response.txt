K1 — Easy: A Deployment manages stateless applications, ensuring a desired number of replicas, supporting rolling updates and rollbacks. A StatefulSet is for stateful applications, providing stable unique network identities, stable persistent storage, and ordered deployment/scaling (e.g., databases).

K2 — Easy: A ClusterIP Service has a virtual IP and a selector that matches pod labels. It creates Endpoints (or EndpointSlices) listing the pod IPs. kube-proxy watches the Service and Endpoints and programs iptables/IPVS rules to forward traffic from the ClusterIP to the pod IPs, providing load balancing.

K3 — Medium: A PersistentVolume (PV) is cluster storage provisioned by an admin or dynamically. A PersistentVolumeClaim (PVC) is a request for storage by a user, which binds to a PV. A StorageClass defines the provisioner and parameters for dynamic PV creation. A PVC can reference a StorageClass to create a PV on demand, or bind to an existing PV.

K4 — Medium: Troubleshoot CrashLoopBackOff:
1. `kubectl logs <pod>` — inspect application errors.
2. `kubectl describe pod <pod>` — check events, exit codes, and probe failures.
3. Verify container image, command, and resource limits.
4. Check liveness/readiness probe configuration and whether the app is ready.
5. `kubectl exec` into the container to test dependencies (DB, config, network).

K5 — Medium: CoreDNS is the cluster DNS server, providing DNS records for Services and pods. If CoreDNS is down, pod DNS resolution for cluster services fails; external DNS may also fail because pods use the cluster DNS IP as their resolver, and without it all DNS queries fail.

K6 — Hard: The scheduler first filters nodes that cannot run the pod (e.g., insufficient resources, node selector mismatch, taints not tolerated, affinity rules). Then it scores remaining nodes based on factors like resource fit (request vs. allocatable), spread across zones, node affinity, and inter-pod anti-affinity. It selects the highest-scoring node.

K7 — Hard: The pod is schedulable because total requested memory is 3.5GB + 256Mi = 3.75GB, which is less than the node’s 4GB. At runtime, if the pod uses 600Mi, it exceeds its limit of 512Mi, so the container will be killed by the OOM killer (or evicted) because it exceeds the memory limit.

K8 — Hard: Request → external cloud load balancer → NodePort or Ingress service → NGINX ingress controller pod. The controller reads Ingress rules and routes to the backend Service. The Service selects pods via labels and updates Endpoints. kube-proxy programs iptables/IPVS to forward traffic from the Service virtual IP to the actual pod IPs.

K9 — Medium: A NetworkPolicy controls ingress/egress traffic to/from selected pods. Default behavior: if no NetworkPolicy exists, all traffic is allowed. When a policy selects certain pods, it isolates them, and only traffic explicitly allowed by the policy is permitted.

K10 — Medium: RollingUpdate gradually replaces old pods with new ones, avoiding downtime. Recreate terminates all old pods before creating new ones, causing downtime. Recreate is chosen when the application cannot run multiple versions simultaneously (e.g., database schema incompatible with old version).

K11 — Easy: A namespace partitions cluster resources and provides scope for names. Default namespaces: `default`, `kube-system`, `kube-public`, and `kube-node-lease` (in newer clusters).

K12 — Easy: `kubectl describe pod` shows detailed information including events, labels, node assignment, container status, resource requests/limits, conditions, tolerations, and restart counts—none of which are shown by `kubectl get pod`.

K13 — Easy: A ConfigMap stores configuration data. Pods consume it via:
- Environment variables (`valueFrom.configMapKeyRef`)
- Volume mounts (configMap volume)
- Command-line arguments
- ConfigMap as a volume for files.

K14 — Easy: ClusterIP exposes a virtual IP only inside the cluster. NodePort exposes a static port on each node, allowing external access via `nodeIP:nodePort`. LoadBalancer provisions a cloud load balancer and routes traffic to the NodePort/ClusterIP.

K15 — Easy: A DaemonSet ensures one pod runs on every node (or a subset). Use it for node-level services like log collectors, monitoring agents, or network daemons. A Deployment runs replicas across the cluster, not necessarily on every node.

K16 — Medium: Taints are applied to nodes to repel pods unless they have a matching toleration. Tolerations allow pods to schedule on tainted nodes. Node affinity is a rule based on node labels, either required or preferred. Use taints/tolerations to dedicate nodes (e.g., GPU nodes) and node affinity to place pods on specific hardware or zones.

K17 — Medium: An Operator is a controller that manages complex applications using Custom Resource Definitions (CRDs). It encodes operational knowledge (backups, upgrades, scaling) into code. A standard controller watches built-in resources; an Operator extends the Kubernetes API and automates the full lifecycle of an application.

K18 — Hard: etcd uses the Raft consensus algorithm, requiring a majority (quorum) for writes and reads. If quorum is lost, the cluster cannot elect a leader, so it becomes unavailable. If 2 of 3 etcd nodes are permanently lost, only one remains—no quorum. Recovery requires restoring from a backup snapshot into a new etcd cluster, or (risky) starting the remaining node with `--force-new-cluster` to create a single-node cluster.

K19 — Hard: RBAC uses Roles (namespace-scoped) and ClusterRoles (cluster-scoped) to define permissions. RoleBindings bind Roles to users/groups within a namespace; ClusterRoleBindings bind ClusterRoles cluster-wide. For a developer with read-only access to pods and logs in namespace `dev`:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: pod-reader-binding
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — Hard: Pods default to `ndots:5` in `/etc/resolv.conf`. For a domain with fewer than 5 dots (e.g., `example.com`), the resolver first tries the search domains (e.g., `example.com.namespace.svc.cluster.local`), causing multiple DNS queries and delays. Fix by setting `dnsConfig` in the pod spec:
```yaml
dnsConfig:
  options:
    - name: ndots
      value: "1"
```
or use a fully qualified domain name with a trailing dot.

D1 — Easy: `git rebase` rewrites commit history by reapplying commits onto a new base, creating a linear history. `git merge` creates a merge commit and preserves branch history. Avoid rebasing shared/public branches because it rewrites history and can cause conflicts for other developers.

D2 — Easy: TCP is connection-oriented, reliable, and ordered; UDP is connectionless and does not guarantee delivery. TCP protocols: HTTP, SSH. UDP protocols: DNS, video streaming.

D3 — Medium: A race condition occurs when multiple threads access shared data without synchronization, and the outcome depends on timing. Example: two threads increment a shared counter:
```python
counter = 0
def increment():
    global counter
    temp = counter
    # context switch
    counter = temp + 1
```
If both read `counter=0`, both write `1`, losing an increment.

D4 — Medium: Symmetric encryption uses the same key for encryption and decryption (fast). Asymmetric encryption uses a public/private key pair. In TLS, the client verifies the server’s certificate using the CA’s public key, then the client and server use asymmetric encryption to exchange a symmetric session key, which encrypts the rest of the communication.

D5 — Medium: Container image layers are filesystem changes stacked read-only. Each Dockerfile instruction creates a layer. Layer caching speeds builds if earlier layers are unchanged. Best practices: order stable layers first, combine commands, use specific base tags, and avoid invalidating cache unnecessarily.

D6 — Medium: Check in order:
1. Load balancer / ingress health and backend pool.
2. Application logs for errors or timeouts.
3. Database and external dependencies.
4. Resource limits, auto-scaling, and pod restarts.
5. Network policies and DNS.

D7 — Hard: CAP theorem states a distributed system can guarantee only two of Consistency, Availability, and Partition tolerance. CP example: ZooKeeper (prefers consistency, becomes unavailable during partition). AP example: Cassandra (prefers availability, may serve stale data).

D8 — Medium: Horizontal scaling adds more instances (scale out); vertical scaling increases resources of a single instance (scale up). Patterns enabling horizontal scaling: stateless services, load balancing, shared storage, microservices, and auto-scaling.

D9 — Easy: An environment variable is a key-value pair in a process’s environment. To persist across shell sessions, add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `/etc/environment`.

D10 — Easy: JSON is a text format with objects and arrays, strict syntax. YAML is human-friendly, indentation-based, and supports comments. JSON is easier to parse; YAML is more readable and supports complex data.

D11 — Easy: REST API uses HTTP methods: GET retrieves resources, POST creates, PUT updates/replaces, DELETE removes.

D12 — Easy: Version pinning specifies exact dependency versions (e.g., `package==1.2.3`), ensuring reproducible builds and preventing unexpected changes from breaking the application.

D13 — Easy: Compiled languages are translated to machine code ahead of time (C, Go). Interpreted languages are executed line by line by an interpreter (Python, JavaScript).

D14 — Medium: A reverse proxy sits in front of backend servers and forwards client requests to them. A forward proxy acts on behalf of clients. Common reverse proxies: Nginx (load balancing, TLS termination), HAProxy (high availability, routing).

D15 — Medium: A deadlock occurs when processes are blocked waiting for resources held by each other. Four Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait.

D16 — Hard: Eventual consistency means updates propagate asynchronously and replicas eventually converge. Cassandra offers tunable consistency levels (ONE, QUORUM, ALL) for reads and writes. For read-after-write consistency, use QUORUM for both read and write to ensure the latest value is returned.

D17 — Hard: mTLS (mutual TLS) requires both client and server to present certificates. Handshake: client sends hello, server sends its certificate, client verifies it, client sends its certificate, server verifies it, then key exchange and session key establishment. mTLS is used in service meshes, zero-trust networks, and API authentication.

D18 — Hard: A hash table uses a hash function to map keys to indices. Collisions are resolved by chaining (linked list at each index) or open addressing (probing). Average time complexity is O(1) for insertion, lookup, and deletion; worst case is O(n) when many collisions occur.

D19 — Hard: Circuit breaker pattern prevents repeated calls to a failing service. States: closed (normal), open (fail fast), half-open (allow a few test requests). It prevents cascade failures by stopping retries. Retry policies with exponential backoff can be used alongside, but the circuit breaker cuts off after a threshold.

D20 — Hard: Optimistic concurrency assumes conflicts are rare; it checks a version/timestamp before updating and retries on conflict. Pessimistic concurrency locks rows to prevent conflicts. Choose optimistic for read-heavy workloads, pessimistic for high contention. Example: optimistic uses a `version` column and `UPDATE ... WHERE version = ?`; pessimistic uses `SELECT FOR UPDATE`.
