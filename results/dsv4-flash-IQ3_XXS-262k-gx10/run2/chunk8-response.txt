CL1 — Easy: IaaS provides virtualized infrastructure (compute, storage, networking) on demand; PaaS provides a platform for developing and deploying applications without managing underlying infrastructure; SaaS provides fully managed software applications. Examples: IaaS: AWS EC2; PaaS: Azure App Service; SaaS: Microsoft 365.

CL2 — Easy: The Shared Responsibility Model defines which security tasks are handled by the provider vs the customer. For IaaS VMs (e.g., EC2), the provider secures physical infrastructure, network, and hypervisor; the customer is responsible for OS, patches, applications, and data. For managed Kubernetes (e.g., EKS), the provider manages the control plane and node patching, but the customer secures workloads, RBAC, and pod configurations. For SaaS (e.g., M365), the provider handles nearly everything, including application security, while the customer manages user access and data.

CL3 — Medium: A VPC is a virtual network boundary; subnets are segments within it. Security groups are stateful instance-level firewalls that automatically allow return traffic; NACLs are stateless subnet-level firewalls requiring explicit inbound/outbound rules. They layer: NACLs filter traffic at the subnet boundary, then security groups filter at the instance level. Stateful filtering tracks connection state, while stateless does not.

CL4 — Medium: A multi-account strategy uses a landing zone (pre-configured baseline), organizational units (OUs) to group accounts by function, guardrails (SCPs, preventive/detective controls), shared networking via Transit Gateway (AWS) or Hub-and-Spoke (Azure), and centralized logging (e.g., S3 + Athena, Log Analytics). A single-account approach is problematic because it creates a single blast radius, lacks isolation for compliance, complicates cost allocation, and hinders team autonomy.

CL5 — Medium: Infrastructure as Code (IaC) manages infrastructure via declarative or imperative code. Terraform/OpenTofu: declarative, multi-cloud, state-based; Pulumi: imperative (Python/TS), multi-cloud; CloudFormation/Bicep: AWS/Azure native, tightly integrated; Crossplane: control plane that composes infrastructure using Kubernetes CRDs. Choose Terraform for broad multi-cloud adoption, Pulumi for developer-friendly code, native tools for deep cloud-specific features, and Crossplane for platform teams building internal abstractions.

CL6 — Medium: HPA scales pods based on CPU/memory or custom metrics; VPA adjusts resource requests/limits; cluster autoscaler scales nodes; KEDA is event-driven scaling based on external sources (e.g., queue length, Kafka lag). Use KEDA over HPA when scaling is driven by event backlog or throughput rather than resource utilization, enabling scale-to-zero and fine-grained triggers.

CL7 — Hard: DR design: Define RPO (acceptable data loss) and RTO (recovery time). Active-active serves traffic from both regions; active-passive has one standby. Database replication: sync (lower RPO, higher latency) vs async (higher RPO, better performance). DNS failover via Route53/Traffic Manager with health checks. State management: use replicated databases, distributed caches, or session affinity. Cost: active-active doubles infrastructure; pilot light keeps minimal resources; warm standby runs scaled-down; multi-site active-active is most expensive. Pilot light: minimal core services running, ready to scale; warm standby: idle but fully configured; multi-site: both regions serve traffic.

CL8 — Hard: GitOps uses Git as the single source of truth for infrastructure and apps. ArgoCD and FluxCD both reconcile desired state from Git. Secrets: Sealed Secrets encrypts secrets in Git; External Secrets Operator syncs from Vault/AWS Secrets Manager; Vault can be integrated. If a manual change drifts, the GitOps controller detects and reverts it to the Git state, ensuring consistency.

CL9 — Hard: For a stateful legacy app: Use StatefulSet for stable network identities and ordered startup. Use local persistent storage via a local storage class (PV/PVC) for low latency. Headless service for stable DNS. Init containers to handle ordered startup dependencies. ConfigMaps mounted as volumes for config files. Pod Disruption Budgets to protect availability during maintenance.

CL10 — Medium: Service accounts are Kubernetes identities for pods; workload identity (e.g., Azure AD Workload Identity) and IRSA (IAM Roles for Service Accounts) map Kubernetes service accounts to cloud IAM roles. Mounting cloud provider credentials in a pod is bad because they are long-lived, hard to rotate, and exposed. Workload identity federation uses OIDC to issue short-lived credentials, eliminating static secrets.

CL11 — Medium: Object storage (S3/Blob) is for unstructured data, highly durable (11 nines), accessed via HTTP; block storage (EBS/Managed Disk) is for VM disks, low latency, single-attach; file storage (EFS/Azure Files) is for shared file systems, supports NFS/SMB. Durability: object storage offers 99.999999999% (11 nines); block and file typically 3-4 nines. Availability: object storage 99.99%, block 99.95%, file 99.9%.

CL12 — Hard: Zero-trust for Kubernetes: Network policies to segment east-west traffic; service mesh (e.g., Istio) with mTLS for identity-based encryption; pod identity via SPIFFE/SPIRE; admission controllers (OPA/Kyverno) to enforce policies; image signing and verification (Cosign); runtime security with Falco; secrets management via Vault/External Secrets. This differs from perimeter security by assuming breach and verifying every request.

CL13 — Easy: A CDN is a distributed network of edge servers that cache content closer to users. It works by routing requests to the nearest edge node, reducing latency and origin load. Examples: AWS CloudFront, Azure CDN. Use a CDN for static content (images, JS, CSS) to improve performance; serve dynamic content directly from origin if it cannot be cached.

CL14 — Easy: Regions are geographic areas with multiple availability zones (AZs). AZs are isolated data centers within a region. Deploy across AZs for high availability and fault tolerance. Zonal resources are tied to a specific AZ (e.g., EC2 instance), while regional resources are resilient across AZs (e.g., S3, ELB).

CL15 — Easy: A managed database service (RDS, Cloud SQL, Azure SQL) automates backups, patching, replication, and scaling. The provider handles hardware, OS, and DB engine maintenance; the customer manages data, schema, and access. Compared to running a DB on a VM, you avoid operational overhead but may have less control.

CL16 — Easy: IAM users are individual identities; groups are collections of users; roles are temporary identities for services or federated users; policies define permissions. Least privilege means granting only necessary permissions. Apply by using roles, scoping policies to resources, and regularly reviewing access.

CL17 — Easy: Serverless computing runs code without provisioning servers. AWS Lambda, Azure Functions, and Google Cloud Functions are event-driven, auto-scaling, and pay-per-use. Cold starts are delays when a function is invoked after being idle. Serverless is a poor fit for long-running processes, stateful applications, or workloads with predictable high utilization.

CL18 — Medium: Ingress options: Ingress resource (traditional, L7 routing), Gateway API (more expressive, multi-protocol), cloud load balancer annotations (direct LB integration), service mesh ingress gateways (e.g., Istio). TLS termination can occur at the LB, ingress controller, or service mesh sidecar. Gateway API is preferred over Ingress for its portability, extensibility, and support for multiple protocols.

CL19 — Hard: Cost optimization: Use reserved instances/savings plans for baseline, spot/preemptible for fault-tolerant workloads, right-size resources based on utilization, tier storage (S3 Intelligent-Tiering, Archive), detect idle resources, implement FinOps with showback/chargeback. Tools: AWS Cost Explorer, Azure Cost Management, Terraform cost estimation, and automated policies to stop unused resources.

CL20 — Hard: Multi-cloud strategy: Use abstraction layers like Kubernetes for workloads, Terraform for IaC, and a common identity federation (OIDC). Networking via VPN/interconnect. Trade-offs: increased complexity, latency, and cost. Justified when avoiding vendor lock-in is critical, for compliance, or for resilience. Unnecessary complexity if one provider meets all needs.

OT1 — Easy: Purdue Model (ISA-95) levels: Level 0: Physical process (sensors/actuators). Level 1: Basic control (PLCs, RTUs). Level 2: Supervisory control (SCADA, HMI). Level 3: Operations management (historian, MES). Level 4: Enterprise (ERP, IT). Level 5: Internet/cloud.

OT2 — Easy: IT networks prioritize data confidentiality and integrity; OT networks prioritize availability and safety. OT systems often run legacy OS, require real-time communication, and cannot tolerate downtime for patching. Standard IT patching can disrupt production, so OT patching requires careful testing and scheduled windows.

OT3 — Medium: The IDMZ (Industrial DMZ) is a buffer zone between IT and OT. It allows controlled data exchange, typically from IT to OT for business data (e.g., production orders) and from OT to IT for process data (e.g., historian). Direct connectivity from Level 4 to Level 1 is dangerous because a compromise in IT can directly reach control systems, bypassing security controls.

OT4 — Medium: Modbus TCP: used for communication between controllers and devices, operates at Level 1-2. OPC UA: machine-to-machine communication, typically at Level 3. EtherNet/IP (CIP): industrial protocol for real-time control, Level 1-2. PROFINET: similar, Level 1-2. MQTT: lightweight pub/sub for IoT, often at Level 3-4.

OT5 — Medium: A data diode is a hardware device that allows data to flow in only one direction, physically preventing reverse traffic. A firewall can filter two-way traffic. Use a data diode when absolute one-way security is required (e.g., sending data from a high-security OT network to a lower-security IT network). Limitation: no return traffic, so remote management or acknowledgments are impossible.

OT6 — Medium: Data flow: SCADA -> historian (Level 3) -> OPC UA server -> edge gateway (Level 3.5) -> MQTT broker (DMZ) -> cloud ingestion. Security boundaries: place firewalls between levels, use TLS for MQTT, authenticate at each hop, and isolate the edge gateway in a DMZ.

OT7 — Hard: IEC 62443 zones are groups of assets with similar security requirements; conduits are communication paths between zones. Define zones based on function, risk, and trust. For a plant: corporate network (Zone 1), engineering workstations (Zone 2), SCADA servers (Zone 3), PLCs (Zone 4), SIS (Zone 5). Conduits: allow only necessary protocols between zones, with firewalls and IDS.

OT8 — Hard: Segmentation strategy: Create VLANs per production line, place firewalls between zones (e.g., corporate, SCADA, PLC), use a core switch with routing, and implement remote access via a jump host with MFA. Transition: plan in phases, use temporary ACLs, and schedule changes during maintenance windows to avoid production impact.

OT9 — Hard: SIS is designed to bring the process to a safe state if hazardous conditions occur; BPCS controls normal operation. IEC 61511 is the safety standard for SIS. The SIS must be isolated because a cyber attack could disable safety functions, leading to catastrophic accidents. If ransomware reaches the SIS, it could prevent safety actions, causing explosions or toxic releases.

OT10 — Medium: PLC: programmable logic controller for discrete control (e.g., assembly lines). DCS: distributed control system for continuous processes (e.g., chemical plants). SCADA: supervisory control and data acquisition for remote monitoring and control. They can coexist: PLCs for local control, DCS for complex processes, SCADA for overall supervision.

OT11 — Medium: Remote access should use a jump host (bastion) with MFA, session recording, and time-limited access for vendors. Direct RDP to an HMI from corporate network is unacceptable because it exposes the HMI to the internet and lacks auditability. Use a secure gateway with granular access controls.

OT12 — Hard: Detection: Deploy network monitoring (IDS/NDR) at Level 3, maintain asset inventory, and use anomaly detection. Response: isolate compromised systems, preserve evidence, coordinate with control room to maintain safe operations, and follow incident response plan. Plant operators must be trained to recognize cyber incidents and follow manual procedures if automation is disrupted.

OT13 — Easy: HMI is a graphical interface for operators to monitor and control processes. An engineering workstation is used by engineers to program and configure controllers. HMI focuses on real-time operation; engineering workstation focuses on development and maintenance.

OT14 — Easy: A historian is a time-series database that stores process data (e.g., temperatures, pressures) for analysis and reporting. Plant historian (Level 3) collects real-time data from control systems; enterprise historian (Level 4) aggregates data across plants for business intelligence.

OT15 — Easy: Ladder logic is a graphical programming language used in PLCs, resembling relay logic. It remains dominant because it is reliable, familiar to electricians, and well-suited for discrete control. It is still widely used due to legacy systems and industry standards.

OT16 — Easy: An RTU is a remote terminal unit used for telemetry and control in remote locations, often battery/solar powered. It differs from a PLC in that it is designed for remote communication and low power. Deploy RTUs in pipelines, substations, and remote wellheads where local control is minimal.

OT17 — Easy: Analog signals represent continuous values (4-20mA, 0-10V); digital signals are discrete (on/off). 4-20mA is preferred because 4mA represents a live zero, allowing detection of wire break (0mA) and providing power to the instrument.

OT18 — Medium: OT asset inventory is the foundation because you cannot secure what you don't know. Tools: passive network monitoring (e.g., using SPAN ports) to identify devices without sending packets; active scanning (e.g., Nmap) can disrupt fragile OT devices. Active scanning is dangerous because it may cause PLCs to crash or produce unexpected outputs.

OT19 — Hard: MITRE ATT&CK for ICS includes tactics: Initial Access (e.g., exploit public-facing application), Execution (e.g., command-line interface), Persistence (e.g., external remote services), Evasion (e.g., masquerading), Discovery (e.g., network service scanning), Lateral Movement (e.g., remote services), Collection (e.g., process capture), Command & Control (e.g., standard application protocol), Impact (e.g., loss of safety). It differs from enterprise by focusing on ICS-specific impacts like safety and process disruption. Use it to map defensive gaps by comparing current controls to techniques.

OT20 — Hard: Converged SOC: Collect logs from OT assets via passive monitoring or syslog with careful filtering to avoid impact. Integrate into SIEM with OT-specific rules (e.g., unexpected protocol changes). Triage: IT analysts handle IT alerts, OT engineers handle OT alerts. False positives are high in OT due to noisy protocols; use baselining. For unauthorized firmware change on a PLC: treat as critical, isolate the PLC, verify with vendor, and restore from known-good backup while preserving forensic evidence.
