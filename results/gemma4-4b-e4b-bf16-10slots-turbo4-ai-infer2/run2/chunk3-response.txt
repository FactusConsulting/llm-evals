## OpenTofu / Terraform (20 questions)

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
Tofu plan generates an execution plan, showing exactly what changes (additions, modifications, deletions) will be made to the infrastructure without applying them. Tofu apply executes the plan, making the actual changes to the cloud resources.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a mapping file that records the current real-world state of the infrastructure managed by OpenTofu (e.g., resource IDs, attributes). Remote state is crucial because it provides a centralized, shared, and durable source of truth for the state file, enabling collaboration and preventing state corruption across team members.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` creates multiple instances of a resource based on a numerical index (e.g., `count.index`). `for_each` creates multiple instances based on a map or set of strings, using the key/value pair as the identifier. `for_each` is preferred when the resource needs to be uniquely identified by a specific attribute (like a name or tag) rather than just an index, as it makes the configuration more readable and resilient to reordering.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?**
OpenTofu detects this drift during `tofu plan`. The plan will show a difference between the desired state (in the configuration) and the actual state (in the cloud). OpenTofu will flag the resource as needing modification to match the configuration, or it may suggest a replacement if the change is incompatible.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
resource "aws_instance" "web_vm" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-0abcdef1234567890"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
*   **Output Values:** Used to pass data *from* a module *to* its caller.
*   **Data Source:** Used to fetch external, existing data (e.g., finding the latest AMI ID).
*   **`terraform_remote_state`:** Used to read the state of *another* remote backend.
*   **Recommended Alternative:** Using **module outputs** is the standard and preferred method. It keeps the dependency explicit and clean. Using `terraform_remote_state` is complex, brittle, and often unnecessary unless you are specifically reading the state of a completely separate, unrelated infrastructure stack.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
The `null_resource` provisioner runs *during* the apply phase, but the output value is only populated *after* the provisioner successfully executes. If dependent resources try to read this output immediately, it will be empty on the first run.
**Fix:** Use a `local_file` resource or a `null_resource` with a `triggers` block that depends on the provisioner's output. This forces OpenTofu to wait for the provisioner to complete and populate the output before proceeding to the dependent resources.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
Import allows you to bring existing, manually provisioned infrastructure into OpenTofu management without writing the configuration code first.
**Limitations:** It only imports the resource ID and basic attributes; it does not automatically infer complex configuration or dependencies.
**Improvement (Import Block):** The import block allows you to define the resource type and name *within* the configuration file, making the configuration file immediately valid and allowing you to start writing the desired state configuration alongside the imported resource.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a placeholder for input data (e.g., region, instance count) defined in the configuration.
*   **Variable (Input):** Data provided *to* the configuration at runtime (e.g., via `-var` or `terraform.tfvars`).
*   **Output:** Data exposed *from* the configuration after it has been applied (e.g., public IP address), allowing other parts of the infrastructure or external systems to consume it.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that enables OpenTofu to interact with external APIs (e.g., AWS, Azure, Kubernetes).
If you run `tofu plan` without `tofu init`, OpenTofu will fail because it cannot locate or download the necessary provider plugins and configuration required to communicate with the target infrastructure.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
The `.terraform.lock.hcl` file pins the exact versions and checksums of all required provider plugins and modules. It should be committed to version control to ensure that every developer or CI/CD pipeline running the code uses the exact same, tested versions of dependencies, preventing unexpected behavior due to upstream provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the current state file. To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web_vm["web1"]`).

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source retrieves information about existing infrastructure or external data that is *not* managed by the current OpenTofu configuration.
**Example:** Using `aws_ami` to find the latest Amazon Machine Image ID for a specific region. You use this instead of a managed resource because you don't want OpenTofu to *manage* the AMI; you just need to *reference* its ID.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
*   **Variable Block:** Used for external inputs (parameters) that are passed into the configuration (e.g., `region = "us-east-1"`).
*   **Locals Block:** Used for internal, derived values or complex calculations *within* the configuration (e.g., calculating a subnet CIDR based on a base network variable).
**Use Locals when:** The value is derived from other variables or resources within the same configuration, or when you need to define reusable, internal constants that don't need to be passed in from the command line.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block controls how OpenTofu manages the resource during updates.
*   **`create_before_destroy`:** Creates a new resource instance before destroying the old one. *Use Case:* Database migrations or critical services where downtime must be avoided during replacement.
*   **`prevent_destroy`:** Prevents the resource from being destroyed by OpenTofu. *Use Case:* Critical production resources (e.g., a primary load balancer) that should never be accidentally deleted.
*   **`ignore_changes`:** Tells OpenTofu to ignore changes made to specific attributes outside of the configuration. *Use Case:* Allowing manual tagging or metadata updates in the cloud console without triggering a resource replacement.

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
The `moved` block allows you to change the resource address (the path/name) of a resource in your configuration without forcing OpenTofu to destroy and recreate that resource. This is vital during refactoring (e.g., renaming a module or changing a resource type) as it preserves the resource's state and identity.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
The dependency graph maps out all resource relationships.
*   **Implicit Dependency:** Occurs when one resource references an attribute of another (e.g., `aws_instance.web.subnet_id` references `aws_subnet.main.id`). OpenTofu automatically knows the order.
*   **Explicit Dependency:** Defined using `depends_on = [resource_address]`.
**Impact:** `depends_on` forces sequential execution, even if the resources are otherwise independent. It should be used sparingly because it artificially limits OpenTofu's ability to run independent resources in parallel, slowing down the plan/apply process.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1.  **Modularization:** Break large configurations into smaller, focused modules. *Tradeoff:* Increased complexity in module management and dependency tracking.
2.  **Targeting/Filtering:** Use `tofu plan -target=...` to only plan changes for specific components during development/testing. *Tradeoff:* Not suitable for full CI/CD runs; requires careful management of targets.
3.  **Provider Optimization:** Ensure providers are configured efficiently (e.g., limiting API calls, using regional endpoints). *Tradeoff:* Requires deep knowledge of provider APIs and potential configuration overhead.
4.  **State Splitting:** Split the monolithic state file into multiple, smaller state files (e.g., one state per service/environment). *Tradeoff:* Increases the number of state files to manage and requires more complex cross-state referencing.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**
State locking prevents concurrent modifications to the state file, ensuring data integrity. When an apply starts, OpenTofu acquires a lock on the remote backend (e.g., DynamoDB).
**Failure:** If the lock is not released (e.g., crash), the state remains locked, preventing *all* subsequent operations until the lock is cleared, leading to a service outage.
**Manual Break:** You must manually delete the lock entry in the backend service (e.g., deleting the DynamoDB lock item).
**Risks:** Manually breaking a lock bypasses safety checks and risks state corruption if another process is actively modifying the state.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.**
1.  **Configure Backend:** Update the `backend` block in the configuration to point to the S3 bucket and specify the DynamoDB table for locking.
2.  **Initialize:** Run `tofu init`. OpenTofu will detect the new backend configuration and prompt the user to migrate the existing local state.
3.  **Migration:** Confirm the migration. OpenTofu uploads the local state file to S3 and registers the lock mechanism.
4.  **Verification:** Run `tofu plan`. If successful, the plan will execute against the remote state, confirming that the configuration and the remote state are correctly linked and accessible.

## Ansible (20 questions)

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
*   **Playbook:** A YAML file that defines a set of actions (plays) to be executed against a group of hosts. It is the entry point.
*   **Role:** A standardized directory structure that packages related tasks, handlers, variables, and templates for a specific function (e.g., `webserver`, `database`). Roles promote reusability.
*   **Task:** A single unit of work within a playbook or role, defining a specific action (e.g., `apt install nginx`, `copy file`).

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary of information gathered about the target host during the initial connection phase (e.g., OS version, memory, network interfaces).
To access the OS family, you would use: `{{ ansible_os_family }}`.

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
*   **`command`:** Executes a command directly. It is non-interactive and does not handle shell features (like pipes or redirection). Use when you need simple, atomic execution.
*   **`shell`:** Executes a command through the shell (e.g., `/bin/sh`). It supports shell features (pipes, redirection). Use when complex shell logic is required.
*   **`raw`:** Executes a command directly on the remote machine without using the Ansible connection plugin's shell. Use when you need to bypass the standard connection mechanism (e.g., for specific low-level system calls).

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means that running the same task multiple times yields the same result without causing unintended side effects. Ansible achieves this by using modules that check the current state before making changes.
*   **Idempotent Example:** `ansible.builtin.package` (e.g., `apt` or `yum`). If the package is installed, the task reports "ok" and makes no changes.
*   **Non-Idempotent Example:** `ansible.builtin.command` (e.g., `echo "hello" >> /etc/file.txt`). Running this multiple times will append "hello" repeatedly, changing the state each time.

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS family
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
Ansible uses a strict hierarchy, with later sources overriding earlier ones:
1.  **Role Defaults** (Lowest priority)
2.  **Inventory Variables** (e.g., `group_vars/all`)
3.  **Host Variables** (e.g., `host_vars/server1`)
4.  **Extra Variables** (Passed via `-e` or `--extra-vars`)
5.  **Set Fact** (Variables set during runtime using `set_fact`) (Highest priority)

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**
1.  **Inventory Grouping:** Divide the 50 nodes into two groups: `initial_nodes` (3 nodes) and `remaining_nodes` (47 nodes).
2.  **Serial Execution:** Use `serial: 1` on the initial deployment tasks to ensure only one node is processed at a time, allowing for controlled rollout.
3.  **Wait/Dependency:** Use `wait_for` or a `meta: flush_handlers` combined with a loop/delay to ensure the initial nodes are fully operational before the subsequent tasks targeting `remaining_nodes` begin.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible files.
To encrypt a single variable without encrypting the whole file, you use the `ansible.builtin.vars` module or define the variable in a separate, encrypted file, referencing it in the main playbook. The variable itself must be marked as encrypted using the vault syntax (e.g., `secret_password: "{{ lookup('ansible.builtin.env', 'SECRET_PASSWORD') }}"` if using environment variables, or by using the vault CLI to encrypt only that specific line/variable definition).

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
The inventory file lists the target hosts and groups Ansible will manage.
*   **Static Inventory:** A manually defined list of hosts (e.g., `hosts.ini`).
*   **Dynamic Inventory:** A script or plugin that connects to an external source (e.g., AWS EC2 API, VMware vCenter) to generate the host list and group membership in real-time.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a task that is only executed when explicitly notified by another task. It is typically used for cleanup or post-configuration actions (e.g., restarting a service).
**Difference:** A regular task runs sequentially; a handler is queued and only runs once all tasks in the play have completed, unless explicitly triggered.
**Triggering:** A task uses `notify: handler_name`.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
`ansible.cfg` is a configuration file that controls how Ansible behaves globally.
**Common Settings:**
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Defines the default user to connect as on remote hosts.
3.  `host_key_checking`: Controls whether host keys are verified (e.g., `False` for testing).

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
The `register` keyword captures the output of a task and stores it in a variable (a "registered variable").
**Usage:** If a task is registered as `my_result`, you can access its output in a subsequent task using Jinja2 templating, such as `{{ my_result.stdout }}` or `{{ my_result.rc }}`.

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
*   **`include_tasks`:** Includes tasks from a file *during* the playbook run. It is evaluated *before* the playbook starts, meaning conditional logic (`when:`) in the included file is evaluated immediately.
*   **`import_tasks`:** Includes tasks from a file *after* the playbook starts. It is evaluated *during* the playbook run.
**Usage:** Use `import_tasks` when you need to conditionally include a large block of tasks based on runtime variables.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Ansible Galaxy is a community repository for sharing reusable Ansible content (roles and collections).
You use a `requirements.yml` file to list the required roles/collections and their versions. You then run the command `ansible-galaxy install -r requirements.yml` to download and install them into the local Ansible environment.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins define how Ansible connects to and executes commands on the target host.
*   **`ssh`:** The default. Connects via SSH to execute commands remotely. Used for standard remote server management.
*   **`local`:** Executes tasks directly on the Ansible control node itself. Used for local configuration or file manipulation.
*   **`network_cli`:** Used to manage network devices (routers, switches) via CLI protocols (e.g., Telnet, SSH). Used when managing infrastructure hardware.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
*   **`delegate_to: localhost`:** Forces a task to run on the Ansible control node, even if the play is targeting remote hosts.
*   **`run_once: true`:** Ensures that a task is executed only once across *all* hosts in the current play, regardless of how many hosts are targeted.
**Example:** Gathering the public IP of a web server (`register: web_ip`) and then using `delegate_to: localhost` and `run_once: true` to update a central DNS record on the control node using that IP.

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).**
1.  **Increase Forks:** Increase the number of parallel connections (`forks:`). *Tradeoff:* Higher load on the control node and target hosts; potential for connection saturation.
2.  **Pipelining:** Run multiple plays concurrently. *Tradeoff:* Requires careful dependency management; complex to orchestrate.
3.  **Fact Caching:** Cache gathered facts (`ansible_facts`) on the target hosts. *Tradeoff:* Requires persistent storage on the target hosts; introduces a slight delay in fact freshness.
4.  **Mitogen/Parallel Execution:** Use tools like Mitogen to distribute the execution load across multiple control nodes. *Tradeoff:* Significant increase in infrastructure complexity and setup overhead.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
Jinja2 is the templating engine.
*   **`{{ variable }}`:** Prints the value of a variable (output).
*   **`{% control_structure %}`:** Executes control flow logic (loops, conditionals).
*   **`{# comment #}`:** Inserts a comment that is not rendered in the final output.
**Snippet:**
```nginx
upstream backend_servers {
    server {{ item.ip }}:8080; # Primary backend
    server {{ item.ip }}:8080; # Secondary backend
}
```
*Where `item` is iterated over a list of servers.*

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.**
1.  **Serial Batches:** Use `serial: 4` (or similar) to deploy to small batches of servers, ensuring only a fraction is down at any time.
2.  **Pre/Post Tasks:**
    *   **Pre-Task:** Remove the server from the load balancer pool.
    *   **Deployment Task:** Deploy the new code/configuration.
    *   **Health Check:** Use `uri` module to check the new server's health endpoint.
    *   **Post-Task:** Add the server back to the load balancer pool.
3.  **Rollback:** Wrap the deployment tasks in a `block`/`rescue` structure. If the health check fails (in the `block`), the `rescue` block executes, which runs a task to revert the server to the old code version and remove it from the load balancer.
