## Application Architecture

**AA1** — The primary difference is scope and structure. A **monolith** is a single, tightly coupled, unified application where all business logic (UI, data access, business rules) resides in one codebase and is deployed as a single unit. **Microservices** decompose the application into a collection of small, independent, loosely coupled services, each running its own process and communicating via lightweight mechanisms (usually APIs).

**Problems introduced by microservices:**
1. **Distributed Complexity:** Managing inter-service communication, network latency, and distributed transactions is significantly harder than managing in-process calls.
2. **Operational Overhead:** Requires sophisticated infrastructure (service mesh, service discovery, centralized logging/tracing) to manage hundreds of small services.
3. **Testing/Debugging:** End-to-end testing and debugging require simulating complex distributed environments, making local development and debugging more challenging.

**AA2** — **Synchronous communication** requires the calling service to wait (block) for a response from the called service before continuing its own execution. The caller and callee are tightly coupled in time. *Example Technology: REST/HTTP (e.g., using `HttpClient` in C#).* **Asynchronous communication** allows the calling service to send a message or event and immediately continue its own execution without waiting for a response. The response, if needed, is handled later via a callback or a separate event. *Example Technology: Kafka or RabbitMQ.*

**AA3** — A **Reverse Proxy** sits in front of a group of servers, receiving client requests and routing them to the appropriate backend server. Its primary function is load balancing, SSL termination, and basic request routing. An **API Gateway** sits in front of microservices and acts as a specialized facade. It handles cross-cutting concerns specific to the microservices ecosystem, such as authentication/authorization, rate limiting, request aggregation, and protocol translation.

**Can an API Gateway replace a reverse proxy entirely?** No. While an API Gateway *contains* many of the functions of a reverse proxy (like routing and load balancing), a traditional reverse proxy is a foundational network component. An API Gateway adds layers of *application-level intelligence* (e.g., JWT validation, business logic routing) that a simple reverse proxy lacks. They are often used together, or the API Gateway is implemented *as* a sophisticated reverse proxy.

**AA4** — The **Saga pattern** is a mechanism to manage distributed transactions in a microservices architecture where a single business process spans multiple services. Since traditional two-phase commit (2PC) is often avoided in microservices due to coupling, a Saga ensures eventual consistency by executing a sequence of local transactions. If one local transaction fails, the Saga executes compensating transactions to undo the work of the preceding successful transactions, maintaining data integrity.

* **Choreography-based Sagas:** Services communicate by producing and consuming events. There is no central coordinator. Each service reacts to events published by others. *Appropriate when:* The workflow is simple, loosely coupled, and the number of participants is small.
* **Orchestration-based Sagas:** A dedicated service (the orchestrator) manages the workflow. It tells each participant service what local transaction to execute and handles the logic for compensating transactions upon failure. *Appropriate when:* The workflow is complex, requires strict ordering, or when centralized monitoring and failure handling are critical.

**AA5** — **CQRS (Command Query Responsibility Segregation)** separates the model used to update data (Commands) from the model used to read data (Queries). Commands are responsible for state changes (writes), while Queries are optimized solely for retrieval (reads).

It is often paired with **Event Sourcing (ES)** because ES dictates that the state of an entity is not stored directly, but rather as a sequence of immutable events. The current state is derived by replaying these events.

**Problem solved:** A traditional CRUD model forces the read and write models to be tightly coupled and often optimized for the same structure. In complex systems, the optimal read model (e.g., a denormalized view for a dashboard) is often vastly different from the optimal write model (e.g., a normalized transactional database). CQRS/ES allows you to build highly optimized, specialized read models (projections) without affecting the transactional integrity of the write model.

**AA6** — The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a remote service that is down or overloaded). It acts like an electrical circuit breaker: if failures exceed a threshold, it "trips" and immediately fails subsequent calls without attempting the network request, allowing the failing service time to recover.

**Three states:**
1. **Closed:** Normal operation. Requests pass through. If failure rate exceeds a threshold, it transitions to Open.
2. **Open:** Requests are immediately rejected (fail-fast) without hitting the downstream service. After a timeout period, it transitions to Half-Open.
3. **Half-Open:** A limited number of test requests are allowed through to check if the downstream service has recovered. If they succeed, it transitions to Closed; if they fail, it returns to Open.

**Difference from simple retry with backoff:** Retry with backoff attempts the operation again, assuming the failure was transient. The Circuit Breaker assumes the failure is systemic (the service is down) and prevents the client from wasting resources hammering a failing service.

**Using both together:** You use the Circuit Breaker to prevent cascading failures (systemic protection). You use Retry with Backoff *within* the Closed state (or for specific, known transient errors) to handle minor, temporary network hiccups without tripping the breaker.

**AA7** — Designing a multi-tenant SaaS platform requires balancing isolation, cost, and operational complexity.

| Model | Cost | Security | Operational Complexity | Noisy-Neighbor Risk | Trade-offs |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. Shared DB, Shared Schema** | Lowest | Lowest (Requires strict application logic) | Lowest | High (One bad query affects all) | Easiest to manage, but highest risk of data leakage and performance contention. |
| **2. Shared DB, Separate Schema** | Medium | Medium | Medium | Medium (Schema separation helps) | Better isolation than shared schema, but still shares database resources (CPU, I/O). |
| **3. Separate DB per Tenant** | Highest | Highest | Highest | Lowest | Maximum isolation and security. Ideal for regulated industries (HIPAA, PCI). Highest operational cost (managing N databases). |

**AA8** — **Strong Consistency** guarantees that once a write operation is complete, all subsequent read operations will immediately see that updated value. There is no delay. **Eventual Consistency** guarantees that if no new updates are made to a data item, eventually all reads will return the last updated value, but there is a period of inconsistency during propagation.

**Inventory System Architecture (Never Oversell):**
* **Consistency Model:** Strong Consistency (or near-strong consistency). Overselling is a critical business failure.
* **Data Store:** A transactional relational database (e.g., PostgreSQL, CockroachDB) or a distributed ledger/database designed for strong consistency (e.g., Spanner).
* **Patterns:**
    1. **Pessimistic Locking:** When a user attempts to purchase, the inventory record is locked immediately, and the transaction proceeds. This guarantees no other transaction can modify the count until the first transaction commits or rolls back.
    2. **Atomic Operations:** Use database transactions and atomic decrement operations (`UPDATE inventory SET count = count - 1 WHERE item_id = X AND count >= 1`). This ensures the check and the decrement happen as a single, indivisible operation.

**AA9** — A **sidecar proxy** is a small, dedicated proxy container that runs alongside the application container in the same pod/host. It intercepts all network traffic to and from the application.

**Envoy in Istio:** Istio uses Envoy as its data plane proxy. When Istio is deployed, it injects an Envoy sidecar into every service pod. Envoy intercepts all incoming and outgoing traffic. Istio's **Control Plane** (e.g., Pilot) configures these Envoy proxies, telling them routing rules, security policies, and telemetry requirements. The **Data Plane** is the collection of all running Envoy proxies that handle the actual traffic.

**mTLS between sidecars:** Application-level TLS requires the application code to manage certificates, key rotation, and trust chains. mTLS handled by the sidecar proxy (via the service mesh) automates this process. It ensures that all service-to-service communication is encrypted and mutually authenticated (both client and server verify each other's identity) without the application developer needing to write any TLS code. This provides zero-trust networking at the infrastructure level.

**AA10** — The **Strangler Fig pattern** is an incremental migration strategy where new functionality is built around a legacy system, gradually replacing the old system piece by piece until the legacy system is "strangled" and can be retired.

**Migration Strategy (.NET Framework Monolith to .NET 8 Microservices):**
1. **Identify Seams:** Identify a specific, non-critical domain or feature within the monolith (e.g., User Profile Management, Notification Service) that can be isolated.
2. **Build the New Service:** Re-implement that feature as a new, independent microservice using .NET 8.
3. **Implement the Facade/Proxy:** Place an API Gateway or a routing layer in front of the monolith.
4. **Reroute Traffic:** Configure the gateway to route requests for the new feature (e.g., `/api/v2/users`) to the new .NET 8 microservice, while all other requests (e.g., `/api/v1/orders`) still go to the monolith.
5. **Data Synchronization:** Implement a mechanism (e.g., event publishing or dual writes) to keep the data between the old monolith database and the new microservice database synchronized during the transition.
6. **Iterate:** Repeat the process, strangling more and more functionality until the monolith is only a shell or is completely retired.

**AA11** — The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, and scalable software-as-a-service applications.

**6 Factors and Why They Matter:**
1. **Config:** Store configuration (credentials, API keys) in the environment, not in the code. *Why:* Allows the application to be deployed across different environments (dev, staging, prod) without code changes.
2. **Backing Services:** Treat backing services (databases, caches) as attached resources. *Why:* Allows easy swapping of databases (e.g., MySQL to Postgres) without rewriting the application logic.
3. **Stateless Processes:** Any request must be self-contained and not rely on local session data. *Why:* Enables horizontal scaling; any instance can handle any request.
4. **Port Binding:** The app should be self-contained and expose itself via a port, not rely on a specific host/port provided by the infrastructure. *Why:* Essential for containerization and dynamic scaling.
5. **Logs:** Treat logs as event streams, writing them to standard output/error. *Why:* Allows centralized log aggregation (ELK stack, Splunk) regardless of where the container runs.
6. **Concurrency:** Scale out by adding more processes, not by making a single process more powerful. *Why:* Leverages cloud elasticity and commodity hardware.

**AA12** — **Event-Driven Architecture (EDA) using Kafka:**
* **Coupling:** Loose. Services only know about the event schema, not the consumers.
* **Scalability:** Excellent. Kafka scales horizontally by adding partitions and consumers.
* **Debugging Complexity:** High. Tracing a request requires tracing events across multiple services and topics.
* **Ordering Guarantees:** Guaranteed within a partition.
* **Failure Handling:** High resilience. If a consumer fails, the message remains in the log and can be reprocessed.
* **When to choose:** When the system needs to react to state changes (e.g., "Order Placed" triggers Inventory, Shipping, and Billing services).

**Request-Driven Architecture (REST/gRPC):**
* **Coupling:** Tighter. The client must know the API contract and the availability of the server.
* **Scalability:** Good, but scaling is tied to the service endpoint.
* **Debugging Complexity:** Low. The flow is linear (A calls B calls C).
* **Ordering Guarantees:** Guaranteed by the synchronous nature of the call.
* **Failure Handling:** Requires explicit client-side retry logic and circuit breakers.
* **When to choose:** When a request requires an immediate, synchronous response (e.g., "Get User Profile").

**AA13** — A **Load Balancer (LB)** distributes incoming network traffic across a group of backend servers (a server farm or cluster) to ensure no single server is overwhelmed, maximizing throughput and availability.

* **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It makes routing decisions based on network parameters like IP address and port number. It is fast because it does not inspect the content of the packet.
* **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (e.g., HTTP headers, URL paths, cookies) to make routing decisions.

**Layer 7 Use Case:** Required when you need **content-aware routing**. Example: Routing `/api/v1/users` to the User Service and `/api/v2/products` to the Product Service, even if they are running on the same cluster.

**AA14** — A **Message Queue (MQ)** (e.g., RabbitMQ) is a system designed for point-to-point or publish/subscribe communication where messages are consumed and then *removed* from the queue. It is designed for transient tasks.

A **Log-based Message Broker (LMB)** (e.g., Kafka) is a distributed commit log. Messages are appended to topics and are *retained* for a configurable period. It is designed for stream processing and historical data access.

**When to pick one over the other:**
* **Pick MQ (RabbitMQ):** When you need guaranteed delivery of a task and the task is ephemeral (e.g., "Send this email notification"). Once the email is sent, the message is done.
* **Pick LMB (Kafka):** When you need to replay events, build data pipelines, or allow multiple downstream services to consume the same stream of data independently (e.g., "User Registered" event needs to trigger logging, analytics, and welcome email).

**AA15** — A **container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and configuration. It shares the host operating system's kernel.

A **Virtual Machine (VM)** is a complete emulation of a physical computer. It includes its own full guest OS, kernel, and application, running on top of a hypervisor.

**Why containers are popular for microservices:** Containers are highly portable, lightweight, and have a small footprint because they do not carry a full OS. They allow for rapid deployment and consistent environments across development, staging, and production, making them ideal for the rapid, independent deployment cycles of microservices.

**AA16** — **Stateless services** are services that do not retain any client session data or persistent state between requests. Every request contains all the necessary information to be processed independently. *Example: A simple API endpoint that calculates a tax rate.*

**Stateful services** are services that maintain data or session information between requests. The state must be stored locally or in an external store (like a database). *Example: A shopping cart service that remembers items added across multiple user requests.*

**Why stateless services are easier to scale horizontally:** Because they hold no state, you can add or remove instances (scale up/down) instantly, and any incoming request can be routed to any available instance without worrying about session continuity or data loss.

**AA17** — An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using object-oriented programming language constructs (objects, methods) rather than writing raw SQL queries. The ORM handles the translation between the object model and the relational database schema.

**Popular ORMs:**
* **Python:** SQLAlchemy
* **Java:** Hibernate

**Trade-offs of using an ORM vs. raw SQL:**
* **ORM Pros:** Increased developer productivity, improved type safety, abstraction from specific SQL dialects, and easier refactoring.
* **ORM Cons:** Performance overhead (due to the mapping layer), potential for generating inefficient SQL (the "N+1 query problem"), and a steep learning curve for complex queries.
* **Raw SQL Pros:** Maximum performance, complete control over query optimization, and efficiency for complex joins.
* **Raw SQL Cons:** Requires more boilerplate code, less portable across different database types, and is prone to SQL injection if not handled carefully.

**AA18** — The **Bulkhead pattern** is a design pattern that isolates components or resources within a system so that a failure or overload in one component does not cascade and bring down the entire application. It partitions resources (like thread pools or memory) into isolated compartments, much like the watertight compartments of a ship.

**Relation to Resource Isolation:** It ensures that if a dependency (e.g., a slow external API) consumes all the resources of one service, it only consumes the resources allocated to its specific "bulkhead," leaving the rest of the application functional.

**Concrete Implementation:**
* **Thread Pools:** Instead of having one global thread pool for all external API calls, you create separate, limited thread pools for different external dependencies. If the "Payment Gateway" thread pool is saturated due to slow responses, the "User Profile" thread pool remains available and unaffected.
* **Separate Deployment Groups:** Deploying critical services (e.g., payment processing) on dedicated, isolated infrastructure (separate Kubernetes node pools or VMs) ensures that resource contention (CPU/memory) from a less critical service (e.g., logging) cannot starve the critical service.

**AA19** — **Operational Transformation (OT)** and **CRDTs (Conflict-free Replicated Data Types)** are strategies for resolving concurrent edits in collaborative systems.

| Feature | Operational Transformation (OT) | CRDTs (Conflict-free Replicated Data Types) |
| :--- | :--- | :--- |
| **Consistency** | Strong Consistency (Requires centralized coordination/server) | Eventual Consistency (Designed for decentralized operation) |
| **Latency** | Low (If centralized) | Low (Optimized for local operations) |
| **Complexity** | High (Complex transformation algorithms required) | Medium (Requires careful data structure design) |
| **Offline Support** | Poor (Requires server reconciliation) | Excellent (Designed to merge conflicts automatically) |

**Choice for Offline Editing:** **CRDTs.**
CRDTs are inherently designed for decentralized, peer-to-peer operation. They allow users to make changes locally while offline. When connectivity is restored, the CRDTs merge the divergent states mathematically and automatically, guaranteeing convergence to a single, correct state without needing a central server to resolve conflicts.

**AA20** — **Challenges of Distributed Tracing in a Polyglot Ecosystem:**
1. **Context Propagation:** The trace context (a unique ID and span ID) must be passed across service boundaries. In a polyglot environment, this requires standardized headers (e.g., W3C Trace Context or B3 headers) to be consistently injected by the client and extracted by the server, regardless of the language.
2. **Sampling Strategies:** Since tracing every request is too expensive, sampling is used.
    * **Head-based:** The decision to trace is made at the start of the request (the "head"). If the initial service decides not to trace, no subsequent service will.
    * **Tail-based:** The decision is made after the entire trace is complete (at the "tail"). This is more accurate but requires collecting all spans first, which is more resource-intensive.
3. **Trace Storage and Querying:** Tools like Jaeger or Tempo are used to ingest the span data (timing, metadata, logs) and provide a UI for visualizing the flow and latency across services.
4. **Asynchronous Messaging (Kafka):** This is the hardest part. When a request is sent to Kafka, the trace context must be injected into the message headers. The consuming service must then extract this context and start a *new child span* linked to the original parent span, ensuring trace continuity across the asynchronous boundary.

**Ensuring Trace Continuity through Kafka:** The producer must inject the current trace context (e.g., `trace_id`, `span_id`) into the Kafka message headers. The consumer service must read these headers, use the `trace_id` as the parent ID for its new span, and continue the trace.

## On-Premise Infrastructure Architecture

**OP1** — A **Type 1 Hypervisor** (bare-metal) runs directly on the host hardware, managing the hardware resources and providing virtualization services. It offers near-native performance. *Examples: VMware ESXi, Microsoft Hyper-V.* A **Type 2 Hypervisor** (hosted) runs as an application *on top* of a conventional host operating system (like Windows or Linux). It relies on the host OS to manage hardware access. *Examples: VirtualBox, VMware Workstation.*

**OP2** — **SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage to servers. The server sees the storage as a local disk (LUN). *Use Case: High-performance database storage.* *Protocols: Fibre Channel (FC), iSCSI.* **NAS (Network Attached Storage):** A dedicated device that provides file-level storage accessible over the standard network. The server accesses it as a shared folder. *Use Case: File sharing, backups.* *Protocols: NFS, SMB/CIFS.*

**OP3** — **3-Tier Architecture:**
1. **Access Layer:** Where end-user devices connect (switches, endpoints).
2. **Distribution Layer:** Aggregates traffic from the Access Layer, provides policy enforcement (ACLs, QoS), and acts as a routing boundary.
3. **Core Layer:** High-speed backbone responsible for moving traffic between distribution blocks.

**Leaf-Spine (Clos) Architecture:** In a leaf-spine design, all leaf switches (connecting to servers/endpoints) connect to all spine switches. This creates a non-blocking, highly redundant mesh.

**Problem solved:** The 3-tier architecture creates bottlenecks at the Distribution layer, which can become a single point of failure or congestion. Leaf-spine eliminates this bottleneck by providing multiple, parallel paths between any two points, ensuring predictable, low-latency, and high-bandwidth communication across the entire data center.

**OP4** — **Proxmox Cluster Design (High Availability):**
* **Node Count:** Minimum 3 nodes for quorum.
* **Quorum:** Achieved via Corosync/Pacemaker. A majority of nodes must agree on the cluster state.
* **Fencing (STONITH):** Critical. A mechanism (e.g., IPMI, power control) that ensures a failed node is forcibly shut down or isolated to prevent it from corrupting shared storage (split-brain).
* **Shared Storage Options:**
    * **Ceph:** Distributed storage, highly scalable, and resilient.
    * **iSCSI/NFS:** Traditional shared storage accessed over the network.
* **Node Failure:** If one node fails, the cluster detects the failure (via heartbeats). The HA manager (Pacemaker) uses STONITH to fence the failed node. The VMs/services running on that node are automatically migrated (live migration, if possible) or restarted on a healthy node, ensuring service continuity.

**OP5** — **VLAN Trunking:** A mechanism that allows a single physical link (NIC) to carry traffic for multiple logical VLANs. **802.1Q tagging** is the standard protocol used to achieve this. It inserts a 4-byte tag into the Ethernet frame header, specifying which VLAN the frame belongs to.

**Linux Configuration (Single NIC on 3 VLANs):**
1. **Create VLAN Interfaces:** Use `ip link add link eth0 name eth0.10 type vlan id 10` (for VLAN 10). Repeat for VLAN 20 and 30.
2. **Assign IP/Gateway:** Configure the IP address and gateway on each new virtual interface (e.g., `ip addr add 192.168.10.1/24 dev eth0.10`).
3. **Configure Trunk Port:** Ensure the physical switch port connected to the server is configured as a trunk port, allowing traffic for VLANs 10, 20, and 30.

**OP6** — **RAID 1:** Mirroring (100% redundancy, 50% capacity). **RAID 5:** Striping with parity (tolerates 1 drive failure). **RAID 6:** Striping with double parity (tolerates 2 drive failures). **RAID 10:** Striping over mirrored sets (high performance, tolerates multiple failures, but complex). **RAID Z2 (ZFS):** Similar to RAID 6, using parity across multiple disks, optimized for ZFS.

**Database Server Choice (6 drives, Balance Performance/Capacity/Fault Tolerance):** **RAID 10.**
* **Why:** RAID 10 combines the speed of striping (RAID 0) with the fault tolerance of mirroring (RAID 1). For a database, high I/O performance is critical. RAID 10 provides excellent read/write performance while tolerating multiple drive failures, offering a superior balance compared to the parity-heavy RAID 5/6, which can suffer from performance degradation during rebuilds.

**OP7** — **DNS Architecture for 500-person Enterprise:**
* **Recursive Resolvers (Internal):** Internal DNS servers (e.g., Active Directory DNS) that handle queries from internal clients. They forward external queries to public DNS servers.
* **Authoritative Servers:** Servers that hold the official records for the enterprise's domains (e.g., `corp.local`).
* **Forwarders:** The internal resolvers are configured to forward external queries to trusted public DNS servers (e.g., Google 8.8.8.8).
* **Conditional Forwarding:** Used to direct specific domain queries (e.g., `partner.com`) to a specific, external DNS server, bypassing the standard forwarders.
* **Split-Horizon DNS:** The internal DNS servers serve different records based on the client's location (internal vs. external). For example, the internal DNS resolves `intranet.corp.local` to the internal IP, while the external DNS resolves it to a public-facing load balancer IP.
* **DNSSEC:** Used on the external zone to cryptographically sign DNS records, ensuring that the client can verify the authenticity of the response and prevent DNS spoofing.

**Laptop Movement:** When a laptop moves from the office (on the internal network) to the VPN, the DNS resolution changes. The internal DNS server resolves `intranet.corp.local` to the internal IP. When on VPN, the laptop is logically placed on the internal network, and the internal DNS server still resolves it to the internal IP. If the laptop is outside the VPN, the DNS server must be configured to resolve the name to the public/external IP address (via split-horizon).

**OP8** — **PKI Chain of Trust:**
1. **Root CA (Offline):** The highest authority. It signs the subordinate CA certificate. It is kept offline (air-gapped) to prevent compromise.
2. **Subordinate/Issuing CA:** This CA is online and performs the actual signing of end-entity certificates (e.g., server certificates, user certificates). It is signed by the Root CA.
3. **End-Entity Certificate:** The certificate issued to the final resource (e.g., a web server). It is signed by the Subordinate CA.

**CRL vs OCSP:**
* **CRL (Certificate Revocation List):** A periodically published list of all revoked certificates. Clients must download and check this list.
* **OCSP (Online Certificate Status Protocol):** A real-time query where the client asks a responder if a specific certificate is valid. OCSP is faster and more efficient than downloading a massive CRL.

**Consequences of Compromise:**
* **Compromised Subordinate CA:** Catastrophic. An attacker can issue fraudulent certificates for any domain under that CA's trust, allowing them to impersonate internal services. The Root CA must be used to revoke the subordinate CA's certificate.
* **Compromised Root CA:** Catastrophic and existential. If the Root CA is compromised, the entire trust chain is broken. Every certificate issued by that Root CA is untrustworthy, requiring a complete, costly re-issuance of all certificates and trust anchors across the organization.

**OP9** — **WAN Consolidation Comparison:**

| Technology | Cost | Reliability | Latency | Management Complexity | Security Posture |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **MPLS** | High | Very High | Low (Guaranteed QoS) | Low (Managed by carrier) | High (Private network) |
| **IPsec VPN** | Low | Medium | Medium (Internet jitter) | Medium (Requires firewall/VPN concentrator) | High (Encrypted tunnel) |
| **SD-WAN** | Medium | High | Low (Optimizes path selection) | Medium (Centralized orchestration) | High (Encrypted tunnels) |
| **WireGuard Mesh** | Very Low | Medium | Medium | High (Requires manual configuration) | High (Modern cryptography) |

**Recommendation (50 users/site, latency-sensitive VoIP):** **SD-WAN.**
SD-WAN provides the best balance. It leverages the low cost of the public internet (unlike MPLS) but adds intelligent path selection and quality-of-service (QoS) features. For VoIP, SD-WAN can dynamically detect high latency or packet loss on one internet path and instantly switch traffic to a better-performing path, ensuring the low latency required for real-time voice communication, while maintaining strong encryption.

**OP10** — **iDRAC/iLO/IPMI:** These are remote management interfaces built into server hardware. They allow administrators to manage the server (power cycle, view hardware logs, access console) without needing the operating system to be running or the server to be connected to the main network.

**Why Out-of-Band Management is Critical:** It provides a lifeline. If the primary network stack or OS fails, the out-of-band interface remains functional, allowing the administrator to diagnose the failure, reboot the server, or reconfigure the network settings.

**Exposure to the Internet:** If the IPMI interface is exposed to the internet, it is a massive security vulnerability. It provides a direct, low-level access point to the server hardware. An attacker could potentially perform remote power cycling, read hardware logs, or even exploit firmware vulnerabilities to gain control of the physical machine. It must be strictly firewalled and accessed only via a secure jump box or VPN.

**OP11** — **LVM (Logical Volume Manager):** A system that abstracts physical storage into logical volumes, allowing flexible resizing and partitioning. It manages blocks but does not inherently provide advanced features like snapshots or copy-on-write.

**LVM-Thin:** An extension of LVM that supports thin provisioning and snapshots. It allows you to allocate more space than physically exists, and snapshots are created efficiently by tracking block changes.

**ZFS:** A comprehensive file system and volume manager that integrates storage management, RAID, and advanced features. It is known for its data integrity and powerful snapshot capabilities.

**Usage and Snapshot Semantics:**
* **LVM:** Used for flexible volume management. Snapshots are typically block-level copies, which can be resource-intensive to create and maintain.
* **LVM-Thin:** Used when flexible provisioning and snapshots are needed on top of LVM. Snapshots are efficient (copy-on-write).
* **ZFS:** Used for maximum data integrity and advanced features. Snapshots are extremely efficient, leveraging copy-on-write semantics, making them fast and space-efficient.

**OP12** — **Stretch Cluster/DR Strategy (3-node Proxmox/Ceph):**
* **Challenge:** Ceph is designed for high availability within a single data center (DC). A 3-node cluster cannot survive a complete site failure (loss of 2 nodes).
* **Design:** To survive a complete site failure, you must use a **multi-site Ceph cluster** (often using Ceph RBD Mirroring or Ceph Metro).
* **Ceph CRUSH Rules:** CRUSH (Controlled Replication Under Scalable Hashing) is used to determine where data should be placed. For a multi-site cluster, CRUSH rules must be configured to ensure that replicas are placed across different failure domains (e.g., different racks, different data centers).
* **Monitor Placement:** Monitors must be distributed across both sites.
* **Network Latency:** Multi-site Ceph requires low, consistent latency (ideally <10ms) between sites for synchronous replication to function correctly.
* **Split-Brain Problem:** This occurs when network partitioning causes nodes in different sites to believe the other site has failed, leading them to independently take control of resources. **Why 2-site Ceph is bad without a tiebreaker:** Without a tiebreaker (a quorum mechanism that dictates which site is the "master" during a partition), both sites might attempt to write to the same data simultaneously, leading to data corruption. A tiebreaker (like a third, geographically separate witness node) is essential to maintain quorum and prevent split-brain.

**OP13** — **DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses and other network configuration parameters (subnet mask, gateway, DNS servers) to devices on a network.

**DORA Process:**
1. **Discover:** Client broadcasts a DHCP Discover message (looking for a server).
2. **Offer:** DHCP server receives the Discover and sends a DHCP Offer, proposing an IP address.
3. **Request:** Client receives the Offer and sends a DHCP Request, formally accepting the offered IP.
4. **Acknowledge:** DHCP server sends a DHCP ACK, confirming the lease and providing the full configuration.

**Server Unavailable (Lease Expiration):** When the lease expires, the client attempts to renew the lease (usually 50% of the lease time). If the DHCP server is unavailable, the client will continue to use the IP address until the lease expires completely. At that point, the client will stop using the IP address and will attempt to broadcast a new DHCP Discover message, hoping to find a new server.

**OP14** — **Unmanaged Switch:** A plug-and-play device that simply forwards frames based on MAC addresses. It has no configuration interface, no intelligence, and operates at Layer 2. It is suitable for small, simple home networks.

**Managed Switch:** A sophisticated device that allows administrators to configure and control network traffic.

**Features important in an enterprise environment:**
* **VLAN Support:** Allows segmentation of the network (e.g., separating VoIP traffic from data traffic).
* **QoS (Quality of Service):** Prioritizes certain types of traffic (e.g., prioritizing VoIP packets over bulk file transfers).
* **Port Security:** Restricts which MAC addresses can connect to a specific port, preventing unauthorized devices.
* **Spanning Tree Protocol (STP):** Prevents network loops, which can cause broadcast storms.

**OP15** — **NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network.

**Why accurate time synchronization is critical:**
1. **Logging and Forensics:** Accurate timestamps are essential for correlating events across multiple servers during troubleshooting or security investigations.
2. **Security:** Kerberos and other authentication protocols rely heavily on time synchronization (clock skew tolerance).
3. **Clustering:** Distributed databases and clustering systems rely on synchronized time to maintain data consistency and ordering.

**What goes wrong when clocks drift:**
* **Authentication Failure:** Kerberos tickets may be rejected if the clock skew exceeds the allowed tolerance.
* **Data Inconsistency:** In distributed databases, if transactions are logged with different timestamps, the system may incorrectly determine the order of events, leading to data corruption or inconsistent state.
* **Cluster Instability:** Clustering software (like Pacemaker) may fail to achieve quorum or failover correctly if nodes disagree on the current time.

**OP16** — **Physical Server:** A dedicated, tangible piece of hardware (rack-mounted server) running an operating system directly on the bare metal.

**Virtual Machine (VM):** A software emulation of a physical computer. It runs on a hypervisor, which abstracts the physical hardware and allocates virtual resources (vCPU, vRAM) to the guest OS.

**Container:** A lightweight, isolated process environment that packages an application and its dependencies. It shares the host OS kernel, making it much lighter and faster to start than a VM.

**When to run on bare metal:** When the workload requires absolute maximum performance, minimal latency, or specific hardware access (e.g., high-frequency trading, specialized GPU computing, or legacy applications that cannot be virtualized).

**OP17** — **UPS (Uninterruptible Power Supply):** A battery backup system that provides immediate, short-term power to critical equipment when the main utility power fails. It bridges the gap between utility failure and generator startup.

**Generator:** A large, long-term power source that kicks in after the UPS/ATS detects the outage. It provides sustained power for hours or days.

**Why you need both:** The UPS handles the immediate, instantaneous transition (seconds) and provides enough time for the generator to spool up and stabilize. The generator provides the long-term power supply.

**ATS (Automatic Transfer Switch):** A device that monitors the power source. When the utility power fails, the ATS automatically switches the load from the utility power to the UPS/generator power. When utility power returns, the ATS switches the load back to the utility power.

**OP18** — **Active-Passive Clustering:** One server (the passive node) is running but is idle, waiting to take over the workload if the active node fails. This provides high availability but utilizes only 50% of the hardware capacity.

**Active-Active Clustering:** All nodes in the cluster are running and actively serving traffic simultaneously. This provides higher resource utilization and better scalability, but requires more complex synchronization and state management.

**PostgreSQL HA Implementation (Pacemaker/Corosync):**
1. **Corosync:** The cluster communication layer that manages heartbeats and membership among the nodes.
2. **Pacemaker:** The resource manager that monitors the health of the services (e.g., PostgreSQL).
3. **STONITH (Shoot The Other Node In The Head):** A fencing mechanism. If a node fails, Pacemaker uses STONITH (e.g., via IPMI) to forcibly power off the suspected failed node. This prevents the "split-brain" scenario where both nodes think they are the primary.
4. **Virtual IPs (VIP):** A single, floating IP address is configured. Pacemaker ensures that only the active node owns this VIP.
5. **Failover Behavior:** If the primary node fails, Pacemaker detects the failure, uses STONITH to fence the failed node, and then moves the VIP and restarts the PostgreSQL service on the passive node, making it the new active primary.

**OP19** — **Backup and Recovery Strategy (50-server environment):**
* **3-2-1 Rule:** Maintain at least **3** copies of data, on **2** different types of media, with **1** copy stored **offsite**.
* **RPO/RTO:** **Recovery Point Objective (RPO):** The maximum acceptable amount of data loss (e.g., 4 hours). **Recovery Time Objective (RTO):** The maximum acceptable downtime (e.g., 2 hours). These define the backup frequency and recovery speed requirements.
* **Backup Types:**
    * **Full:** Complete copy of data (slow, large).
    * **Incremental:** Backs up only data changed since the *last* backup (fast, small).
    * **Differential:** Backs up all data changed since the *last full* backup (medium size).
* **Deduplication:** Reduces storage footprint by identifying and storing only unique data blocks.
* **Storage:** Use a tiered approach: Disk (fast recovery), Tape (long-term archival/offsite), Cloud (offsite/immutable).
* **Immutable Backups:** Backups stored in a state that cannot be modified or deleted for a set period, providing protection against ransomware.
* **Testing Restores:** Crucial. Regularly perform full, end-to-end restore drills to validate the RTO/RPO assumptions and ensure the backup integrity.

**Backup vs. Disaster Recovery (DR):**
* **Backup:** The process of creating copies of data to protect against data loss (e.g., hardware failure, accidental deletion).
* **Disaster Recovery:** The comprehensive plan and process of restoring the entire business operation (applications, infrastructure, data) after a catastrophic event (e.g., fire, flood, regional power grid failure).

**OP20** — **802.1X (Port-Based Network Access Control):** A standard that controls which devices are allowed to connect to a wired network port.

**Roles:**
* **Supplicant:** The client device (laptop, PC) requesting network access.
* **Authenticator:** The network access device (switch/WAP) that enforces the policy and acts as the gatekeeper.
* **Authentication Server:** The central server (RADIUS) that verifies the credentials and makes the access decision.

**EAP Methods:**
* **EAP-TLS:** The most secure method. Requires both the supplicant and the server to present digital certificates, ensuring mutual authentication.
* **PEAP (Protected EAP):** Encapsulates an inner authentication method (like MS-CHAPv2) within a TLS tunnel, protecting the credentials during transmission.

**RADIUS:** The protocol used by the Authenticator to communicate with the Authentication Server. The RADIUS server receives the credentials, validates them, and sends an Access-Accept or Access-Reject message back to the switch.

**Dynamic VLAN Assignment:** The RADIUS server can dynamically assign a VLAN ID to the supplicant based on the user's credentials (e.g., if the user is in the "Guest" group, the RADIUS server tells the switch to place them in VLAN 50).

**Device Failing Authentication:** The switch (Authenticator) will place the port into an unauthorized state (e.g., a restricted VLAN or a "quarantine" VLAN) and will not allow the device to communicate with the main network until successful authentication occurs.

**MAB (MAC Authentication Bypass):** Used for devices that cannot run 802.1X supplicants (e.g., IP phones, printers). MAB allows the switch to treat the device's MAC address as its username/password and sends it to the RADIUS server for authentication. The RADIUS server then validates the MAC address against a known list and grants access.
