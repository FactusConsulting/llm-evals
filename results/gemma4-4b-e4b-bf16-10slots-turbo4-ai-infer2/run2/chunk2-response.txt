## Kubernetes Answers

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A Deployment manages stateless applications, ensuring a specified number of identical, interchangeable replicas are running. It treats pods as fungible. A StatefulSet, conversely, is used for stateful applications (like databases) where each pod requires a stable, unique identity and persistent storage (e.g., `web-0`, `web-1`).

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
A ClusterIP Service exposes a stable internal IP address within the cluster. It uses `kube-proxy` (which runs on every node) to manage network rules (typically using iptables or IPVS). When traffic hits the ClusterIP, `kube-proxy` intercepts it and load-balances it across the healthy backend pods associated with that Service.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator (or dynamically). It is the actual storage resource (e.g., an AWS EBS volume).
*   **PersistentVolumeClaim (PVC):** A request for storage made by a user/application. It is a request object that specifies the required size and access mode.
*   **StorageClass:** A definition that describes the "class" of storage (e.g., fast SSD, slow HDD). It dictates how PVs are dynamically provisioned.
*   **Relationship:** A PVC requests storage based on a StorageClass. The StorageClass then allows the cluster to bind a suitable PV to satisfy the PVC's request.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**
1.  **Check Logs:** Use `kubectl logs <pod-name>` to see the application's exit code and error messages.
2.  **Check Events/Status:** Use `kubectl describe pod <pod-name>` to check the `Events` section for scheduling failures, image pull errors, or OOMKills.
3.  **Check Configuration:** Verify the Pod spec (ConfigMaps, Secrets, environment variables) is correct and accessible.
4.  **Check Resources:** Ensure the pod's resource requests/limits are reasonable and the node has sufficient available resources.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS acts as the cluster's internal DNS server. It translates internal service names (e.g., `my-service.my-namespace.svc.cluster.local`) into the IP addresses of the corresponding Service endpoints. If CoreDNS pods are down, internal DNS resolution fails entirely. Pods will be unable to resolve other services within the cluster, leading to application failures, although external DNS resolution (if configured) might remain functional.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**
The scheduler uses a two-phase process:
1.  **Filtering (Predicates):** The scheduler eliminates nodes that cannot run the pod. Examples include:
    *   *Resource Check:* Does the node have enough CPU/Memory?
    *   *Taints/Tolerations:* Does the node have taints that the pod cannot tolerate?
    *   *Volume Zone:* Does the node support the required volume topology?
2.  **Scoring (Priorities):** The scheduler ranks the remaining viable nodes based on how well they meet the pod's requirements. Examples include:
    *   *Least Requested Priority:* Preferring nodes with the most available resources.
    *   *Node Affinity:* Giving higher scores to nodes matching specific labels.
    *   *Spread:* Distributing pods across different nodes to prevent single-point failures.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
*   **Scheduling:** The pod will likely **not** be scheduled. The scheduler primarily considers *requests* (256Mi) when calculating available capacity. The node has 4GB - 3.5GB = 500Mi available. Since 256Mi < 500Mi, the scheduler *might* schedule it, but if the node's capacity calculation is strict, it might fail. However, the critical point is that the node is already heavily utilized.
*   **Runtime Behavior:** If the pod uses 600Mi, it will exceed its defined limit (512Mi). Kubernetes will trigger an **OOMKill (Out-Of-Memory Kill)**, terminating the pod.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.**
1.  **External Request:** The request hits the **External Load Balancer (LB)**, which is provisioned by the cloud provider and points to the Ingress Controller's node IPs.
2.  **Ingress Controller:** The LB forwards the traffic to the NGINX Ingress Controller pod. The controller reads the Ingress resource rules (host/path matching).
3.  **Service Lookup:** The controller determines which internal **Service** IP and port should receive the traffic based on the Ingress rules.
4.  **Endpoints:** The Service object points to a list of healthy backend Pod IPs stored in the **Endpoints** object.
5.  **Routing (kube-proxy):** The traffic is routed to the node hosting the target pod. **kube-proxy** intercepts the traffic using iptables/IPVS rules, translating the Service ClusterIP to one of the actual backend Pod IPs and forwarding the packet to the correct application pod.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
*   **NetworkPolicy:** A Kubernetes resource that defines how groups of pods are allowed to communicate with each other and with external network endpoints.
*   **Default Behavior:** If no NetworkPolicy exists in a namespace, the default behavior is **allow-all** (all traffic is permitted).
*   **Applying a Policy:** When a NetworkPolicy is applied, it enforces a **default deny** policy for the selected pods. Only traffic explicitly allowed by the policy (e.g., ingress from specific labels, egress to specific IPs) will be permitted.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** The new version is deployed gradually. Kubernetes spins up new pods and gradually terminates old pods, ensuring zero downtime. This is the default and preferred method.
*   **Recreate:** All old pods are terminated *before* any new pods are started. This results in a period of downtime during the update.
*   **When to choose Recreate:** When the application is extremely sensitive to traffic during the transition, or if the application requires a clean, fresh start (e.g., database migrations that must run before the new version starts).

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A namespace is a mechanism to partition cluster resources (like pods, services, and deployments) into isolated virtual clusters. It provides scope and organizational boundaries.
Default namespaces include: `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
`kubectl describe pod <name>` provides detailed metadata, status, and events for a specific pod.
Information it shows that `kubectl get pod` does not:
1.  **Detailed Status/Conditions:** (e.g., `Reason: ImagePullBackOff`, `Ready: False`).
2.  **Events:** A chronological log of events related to the pod (e.g., scheduling attempts, volume mounting failures).
3.  **Resource Limits/Requests:** Specific configuration details and current resource usage.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A ConfigMap is a Kubernetes object used to store non-sensitive configuration data (like environment variables or configuration files) external to the container image.
Methods to consume it:
1.  **Environment Variables:** Injecting keys/values directly into the container's environment variables via the Pod spec.
2.  **Volume Mounts:** Mounting the ConfigMap as a file volume inside the container, allowing the application to read configuration files.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Exposes the Service internally within the cluster only, using a stable ClusterIP.
*   **NodePort:** Exposes the Service on a specific port on *every* node in the cluster. This allows external access via `NodeIP:NodePort`.
*   **LoadBalancer:** Provisions an external cloud load balancer (e.g., AWS ELB, GCP Load Balancer) that routes external traffic to the Service.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A DaemonSet ensures that a copy of a pod runs on *every* (or a selected subset of) node in the cluster.
You use a DaemonSet when the application needs to run a specific agent or service on every node, such as log collectors (Fluentd), monitoring agents (Prometheus Node Exporter), or network plugins (CNI).

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints:** A property applied to a node that repels (or "taints") pods unless the pod explicitly tolerates that taint.
*   **Tolerations:** A property applied to a pod that allows it to be scheduled on a node that has a matching taint.
*   **Difference from Affinity:** Affinity (Node Affinity) is a *preference* or *requirement* based on labels (e.g., "prefer nodes with GPU"). Taints/Tolerations are a *hard exclusion* mechanism.
*   **Use Case (Taints/Tolerations):** Isolating critical, resource-intensive workloads (e.g., GPU jobs) onto specific nodes, preventing general workloads from consuming those resources.
*   **Use Case (Affinity):** Ensuring a database pod is only scheduled on nodes labeled as having high-speed storage.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An Operator is a method of packaging, deploying, and managing a complex application (like a database cluster) using custom controllers.
*   **Difference from Controller:** A standard controller reacts to the current state and moves it toward a desired state (e.g., ensuring 3 replicas exist). An Operator encapsulates *human operational knowledge* (e.g., backup procedures, failover logic, scaling specific database clusters) into automated control loops.
*   **Problem Solved:** It automates complex, multi-step, and domain-specific operational tasks that traditional controllers cannot handle, allowing the cluster to manage stateful applications like a human administrator would.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
*   **Consistency Model:** etcd uses a strong consistency model (Raft consensus algorithm). This ensures that all nodes agree on the state of the cluster data before any write is committed.
*   **Quorum Loss:** If the quorum (majority) of etcd nodes is lost, the cluster cannot achieve consensus. It enters a read-only or unavailable state, meaning the control plane cannot reliably read or write cluster state (e.g., new pods cannot be scheduled, configuration changes fail).
*   **Recovery (2/3 lost):** If 2 out of 3 nodes are permanently lost, the cluster is irrecoverable because the minimum required quorum (2 out of 3) is lost. The cluster must be rebuilt from scratch, and the remaining healthy node must be re-provisioned into a new cluster configuration.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
*   **RBAC Flow:** RBAC defines permissions (what actions can be taken) and binds those permissions to users/groups (who can take them).
*   **Role:** Defines permissions scoped to a single namespace.
*   **ClusterRole:** Defines permissions scoped across the entire cluster.
*   **RoleBinding:** Binds a Role to a specific user/group within a specific namespace.
*   **ClusterRoleBinding:** Binds a ClusterRole to a user/group across the entire cluster.
*   **Manifests (Read-only Pods/Logs in one namespace):**

```yaml
# 1. Define the Role (Permissions within a namespace)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-app-ns
  name: pod-reader-role
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

---
# 2. Bind the Role to a user/group (The actual permission grant)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: my-app-ns
  name: developer-reader-binding
subjects:
- kind: User
  name: developer-user # Replace with actual user name
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader-role
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
*   **The Problem (ndots):** The `ndots` value specifies the number of dots a hostname must contain before the system attempts a search domain lookup. If `ndots` is high (e.g., 5), and the pod tries to resolve a simple external domain like `google.com`, the system first tries to resolve it using the cluster's internal search domains (e.g., `google.com.svc.cluster.local`). If the internal DNS server (CoreDNS) doesn't know the domain, it fails, and the pod must then fall back to the external DNS server, leading to multiple, unnecessary queries and latency.
*   **The Fix (dnsConfig):** By using `dnsConfig` in the Pod spec, you can explicitly override the DNS settings, setting `options` to include `ndots: 0`. This forces the pod to query the specified nameservers directly without attempting internal search domain lookups first, drastically reducing query overhead and latency for external domains.

## Development Answers

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
*   **Merge:** Combines two branches by creating a new "merge commit." It preserves the exact history of both branches, showing exactly when and where the branches diverged.
*   **Rebase:** Rewrites history by moving the commits from one branch onto the tip of another. It creates a linear history, making the project history cleaner and easier to read.
*   **When to avoid rebasing:** Never rebase commits that have already been pushed to a shared, public branch (like `main` or `develop`). Rebasing rewrites history, and if others have based their work on the original commits, rebasing will cause massive conflicts and confusion for collaborators.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP (Transmission Control Protocol):** Connection-oriented. It guarantees reliable, ordered, and error-checked delivery. It establishes a handshake before data transfer. (Protocols: HTTP/S, FTP).
*   **UDP (User Datagram Protocol):** Connectionless. It is fast and lightweight but offers no guarantees of delivery, order, or error checking. (Protocols: DNS, VoIP/SIP).

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A race condition occurs when the output or result of a program depends on the sequence or timing of uncontrollable events (like thread scheduling). If the timing changes, the result changes unpredictably.
*   **Example:** Two threads (Thread A and Thread B) try to increment a shared counter variable initialized to 0.
    1.  Thread A reads the counter (0).
    2.  Thread B reads the counter (0).
    3.  Thread A increments its local copy (1) and writes it back.
    4.  Thread B increments its local copy (1) and writes it back.
    *Expected result: 2. Actual result: 1.*

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is very fast.
*   **Asymmetric Encryption:** Uses a pair of keys: a public key (for encryption) and a private key (for decryption). Data encrypted with the public key can only be decrypted by the corresponding private key (e.g., RSA). It is computationally expensive.
*   **TLS Usage:**
    1.  **Handshake (Asymmetric):** The client and server use asymmetric encryption (RSA/Diffie-Hellman) to securely exchange a temporary, random **session key**.
    2.  **Data Transfer (Symmetric):** Once the session key is established, all subsequent application data is encrypted using the fast symmetric algorithm (AES) with that session key.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
A container image is built from a series of read-only layers. Each instruction in a Dockerfile (e.g., `RUN`, `COPY`) creates a new layer on top of the previous one.
*   **Layer Caching:** Docker caches the result of each layer. If a layer's instruction and its inputs (files) have not changed, Docker reuses the cached layer instead of rebuilding it.
*   **Best Practices:** Place instructions that change infrequently (like installing OS dependencies: `RUN apt-get update && apt-get install -y ...`) near the top of the Dockerfile. Place instructions that change frequently (like copying application code: `COPY . /app`) near the bottom to maximize cache hits.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**
1.  **Application Logs/Metrics (Internal):** Check the application logs for exceptions, memory leaks, or thread pool exhaustion. Check CPU/Memory usage metrics to see if the application is hitting resource limits. (Is the app crashing or overloaded?)
2.  **Service/Container Health (Kubernetes/Orchestrator):** Check the pod status (`kubectl describe pod`) and resource requests/limits. Is the pod restarting? Is the readiness probe failing? (Is the container healthy?)
3.  **Load Balancer/Ingress Metrics (External):** Check the ingress controller and external LB logs. Is the LB health check failing? Is the traffic being routed correctly? (Is the entry point failing?)
4.  **Dependency Health (External/Internal):** Check if the API relies on external services (databases, caches). Is the database connection pool saturated or is the database itself experiencing latency? (Are upstream dependencies failing?)

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
*   **CAP Theorem:** States that a distributed data store can only guarantee two out of three properties simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest data), and **Partition Tolerance** (the system continues to operate despite network partitions).
*   **CP (Consistency over Availability):** The system prioritizes data correctness. If a network partition occurs, the system will refuse requests to the minority side of the partition to prevent data divergence.
    *   *Example:* Traditional relational databases (like PostgreSQL/MySQL in a clustered setup) or systems requiring strong transactional integrity.
*   **AP (Availability over Consistency):** The system prioritizes always responding to requests, even if the data returned might be stale or inconsistent during a partition.
    *   *Example:* DNS or social media feeds (like Twitter/Facebook), where eventual consistency is acceptable for high uptime.

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) of an *existing* single instance. (e.g., upgrading a VM from 4GB to 16GB RAM).
*   **Horizontal Scaling (Scaling Out):** Adding *more* instances of the application to distribute the load. (e.g., running 10 identical web servers instead of 1).
*   **Patterns for Horizontal Scaling:**
    1.  **Statelessness:** Ensuring the application does not store session data locally.
    2.  **Load Balancing:** Using a load balancer to distribute incoming requests across multiple instances.
    3.  **Microservices:** Decomposing the application into smaller, independent services that can be scaled individually.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An environment variable is a dynamic named value that can affect the way running processes behave on a computer. They are used to configure applications without changing code.
To set a persistent variable on Linux, you must add the export command to a shell configuration file, such as `~/.bashrc` or `~/.zshrc`.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
*   **JSON (JavaScript Object Notation):** A lightweight data-interchange format based on key-value pairs and arrays.
    *   *Advantage:* Universally supported by JavaScript and most modern programming languages, making it ideal for API communication.
*   **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that uses indentation to denote structure.
    *   *Advantage:* Highly readable and concise, making it ideal for configuration files (like Kubernetes manifests).

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
A REST (Representational State Transfer) API is an architectural style for networked applications that uses standard HTTP methods to perform CRUD (Create, Read, Update, Delete) operations on resources.
*   **GET:** Retrieves a resource or a collection of resources (Read). It should be idempotent (calling it multiple times has the same effect as calling it once).
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource (Create).
*   **PUT:** Replaces an entire resource with new data. It is idempotent (sending the same PUT request multiple times results in the same state).
*   **DELETE:** Removes a specified resource (Delete). It is idempotent.

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
Version pinning is the practice of specifying an exact, fixed version number for a dependency (e.g., `library-x@1.2.3`) rather than a range (e.g., `library-x>=1.0`).
It is crucial for reproducible builds because it guarantees that the build environment will always use the exact same code for that dependency, regardless of when the build is run. This prevents unexpected bugs caused by upstream dependency updates.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled Language:** Source code is translated entirely into machine code (binary) *before* execution. This results in faster execution speed. (Examples: C++, Go).
*   **Interpreted Language:** Source code is executed line-by-line by an interpreter *during* runtime. This allows for greater flexibility and easier debugging. (Examples: Python, JavaScript).

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
*   **Forward Proxy:** Sits in front of the client. It acts as an intermediary for the client, hiding the client's identity and often used to filter or cache requests *from* the client to the internet.
*   **Reverse Proxy:** Sits in front of the server(s). It intercepts requests from the internet and forwards them to the appropriate backend server. It hides the backend structure and provides security, load balancing, and SSL termination.
*   **Servers & Use Cases:**
    1.  **NGINX:** Used for high-performance load balancing and SSL termination.
    2.  **HAProxy:** Used for sophisticated traffic distribution and health checking across multiple backend servers.

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A deadlock is a state in which two or more competing actions are waiting for the other to finish, resulting in a permanent standstill.
The four necessary conditions (Coffman conditions) are:
1.  **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2.  **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3.  **No Preemption:** A resource cannot be forcibly taken away from the process holding it.
4.  **Circular Wait:** A closed chain of processes exists, where each process is waiting for a resource held by the next process in the chain.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
*   **Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, all reads will eventually return the last updated value. There is a period of inconsistency between writes and reads.
*   **Cassandra Handling:** Cassandra uses a decentralized, peer-to-peer architecture. When a write occurs, it is written to a subset of nodes (replicas). The system then asynchronously propagates this write to all other replicas.
*   **Tunable Consistency Levels:** Users define how many replicas must acknowledge a write or read.
    *   **Write Consistency:** `QUORUM` (requires a majority of replicas to confirm the write).
    *   **Read Consistency:** `QUORUM` (requires a majority of replicas to respond to the read).
    *   *Read-After-Write:* To ensure read-after-write consistency, the client must typically use a consistency level that overlaps the nodes involved in the write (e.g., writing with `QUORUM` and reading with `QUORUM`).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
*   **mTLS:** Mutual Transport Layer Security. Unlike standard TLS where only the client verifies the server's identity, mTLS requires *both* the client and the server to present and validate cryptographic certificates during the handshake.
*   **Handshake Process:**
    1.  Client initiates connection.
    2.  Server sends its certificate.
    3.  Client verifies the server's certificate.
    4.  Server requests the client's certificate.
    5.  Client sends its certificate.
    6.  Server verifies the client's certificate.
    7.  If both are verified, a symmetric session key is established, and encrypted communication begins.
*   **Common Use:** Microservice mesh communication (e.g., Istio/Linkerd), securing internal API calls, and zero-trust network architectures.

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
*   **Internal Mechanism:** A hash table maps keys to indices (buckets) in an array using a hash function. The hash function converts the key into an index.
*   **Collision Resolution:** When two different keys hash to the same index:
    *   **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) of all key-value pairs that hash to that index.
    *   **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing).
*   **Time Complexity:**
    *   **Average Case (Good Hash Function):** $O(1)$ for insertion, lookup, and deletion.
    *   **Worst Case (Many Collisions):** $O(n)$ for insertion, lookup, and deletion (when all elements hash to the same bucket, degenerating into a linked list traversal).

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
*   **Circuit Breaker:** A pattern used to detect failures in a remote service call. Instead of immediately retrying a failing call (which can overload the failing service), the circuit "trips" and prevents further calls for a period, allowing the failing service time to recover.
*   **States:**
    1.  **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the circuit trips to Open.
    2.  **Open:** The circuit is tripped. All requests are immediately failed (fail-fast) without hitting the downstream service, preventing cascade failure. After a timeout, it moves to Half-Open.
    3.  **Half-Open:** A limited number of test requests are allowed through. If they succeed, the circuit closes; if they fail, it returns to Open.
*   **Relation to Retry/Backoff:** Circuit breakers are a *fail-fast* mechanism that *replaces* aggressive retries. Exponential backoff is used *within* a retry policy to increase the delay between retries, preventing the client from overwhelming the recovering service.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**
*   **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks resources *before* they are accessed, preventing other transactions from modifying the data until the lock is released.
    *   *When to choose:* High contention environments where data integrity is paramount and conflicts are frequent.
    *   *Example:* Using `SELECT FOR UPDATE` in SQL to lock a row immediately upon reading it, preventing other transactions from modifying it until the current transaction commits.
*   **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read. If so, the transaction fails and must be retried.
    *   *When to choose:* Low contention environments where locking would introduce unacceptable performance bottlenecks.
    *   *Example:* Using version columns or row versioning (e.g., `version_number` column). The update query includes a `WHERE version_number = :old_version`. If the version doesn't match, the update fails, indicating a conflict.
