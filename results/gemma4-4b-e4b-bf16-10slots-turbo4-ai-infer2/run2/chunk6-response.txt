## JavaScript / TypeScript

**JS1** — **var, let, and const, and Hoisting**
*   **var:** Function-scoped or globally scoped. It is hoisted to the top of its scope and initialized with `undefined`. It can be redeclared and updated.
*   **let:** Block-scoped (`{}`). It is hoisted but remains in the "Temporal Dead Zone" (TDZ) until declaration, preventing access before initialization. It can be updated but not redeclared in the same scope.
*   **const:** Block-scoped. It must be initialized upon declaration and cannot be reassigned. For objects/arrays, the reference is constant, but the contents can still be mutated.
*   **Hoisting:** The mechanism where variable and function declarations are moved conceptually to the top of their scope during the compilation phase, before code execution. Only the declaration is hoisted, not the assignment.

**JS2** — **Event Loop, Call Stack, Microtask, Macrotask**
The Event Loop is the core mechanism that allows JavaScript (a single-threaded language) to handle asynchronous operations.
*   **Call Stack:** Where synchronous code is executed. When a function is called, it is pushed onto the stack; when it returns, it is popped off.
*   **Macrotask Queue (Task Queue):** Holds tasks like `setTimeout`, `setInterval`, and I/O operations. The Event Loop pulls one macrotask at a time from this queue.
*   **Microtask Queue:** Holds high-priority tasks like Promises (`.then()`, `.catch()`, `.finally()`) and `queueMicrotask()`.
*   **Relationship:** The Event Loop continuously checks the Call Stack. If the stack is empty, it first checks the Microtask Queue. It processes *all* tasks in the Microtask Queue before pulling the next single task from the Macrotask Queue.

**JS3** — **Closure, Loop Closure Bug**
*   **Closure:** A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). In simpler terms, a function "remembers" the variables from the scope in which it was created, even if that scope has finished executing.
*   **Example:**
    ```javascript
    function createCounter() {
      let count = 0;
      return function() {
        count++;
        return count;
      };
    }
    const counter = createCounter();
    console.log(counter()); // 1
    ```
*   **Classic For Loop Closure Bug:** When using `var` in a `for` loop, the loop variable (`i`) is function-scoped. If you create an asynchronous callback inside the loop (e.g., using `setTimeout`), all callbacks reference the *same* final value of `i` after the loop completes, not the value of `i` at the time the iteration started.
*   **Fix:** Use `let` instead of `var`. `let` is block-scoped, creating a new binding for `i` for every iteration, thus isolating the scope for each callback.

**JS4** — **Promise, async/await, Error Handling, Promise.allSettled vs Promise.all**
*   **Promise:** An object representing the eventual completion (or failure) of an asynchronous operation. It can be in one of three states: pending, fulfilled, or rejected.
*   **async/await:** Syntactic sugar built on Promises. `async` functions always return a Promise. `await` pauses the execution of the `async` function until the awaited Promise resolves.
*   **Error Handling:**
    *   **Promises:** Handled using `.catch(error => ...)` attached to the Promise chain.
    *   **async/await:** Handled using standard `try...catch` blocks, treating the awaited Promise rejection like a synchronous exception.
*   **Promise.all:** Takes an array of Promises and returns a single Promise that resolves when *all* input Promises resolve. If *any* Promise rejects, `Promise.all` immediately rejects with the reason of the first Promise that rejected.
*   **Promise.allSettled:** Takes an array of Promises and returns a single Promise that resolves when *all* input Promises have settled (either fulfilled or rejected). The result is an array of objects, each describing the outcome (`{status: 'fulfilled', value: ...}` or `{status: 'rejected', reason: ...}`).

**JS5** — **Interface vs Type, Discriminated Unions**
*   **Type:** A runtime concept (though TypeScript uses it for compile-time checks). It describes the shape of data at runtime. Types are used to define the structure of variables and function signatures.
*   **Interface:** Primarily a compile-time construct used to define the "contract" or shape of an object. It is often used to describe the structure of classes or objects.
*   **When to use each:**
    *   **Interface:** Best for defining object shapes, especially when extending or merging types (declaration merging).
    *   **Type:** Best for defining complex unions, primitives, or utility types (e.g., `type ID = string | number`).
*   **Discriminated Unions:** A pattern where a union type is defined by a common literal property (the "discriminator"). This allows TypeScript to narrow the type within a `switch` statement or `if/else` block.
    *   *Example:* `type Shape = { kind: 'circle', radius: number } | { kind: 'square', side: number };`

**JS6** — **Prototypal Inheritance, Object.create(), ES6 Classes**
*   **Prototypal Inheritance:** JavaScript objects inherit properties and methods from other objects (prototypes). When you try to access a property on an object, if it's not found directly, the engine looks up the prototype chain until it reaches `Object.prototype`.
*   **Object.create(proto):** A method that creates a new object, setting the prototype of the new object to the object passed as an argument (`proto`). This is the fundamental way to create an object inheriting from a prototype.
*   **ES6 Classes:** Classes are syntactic sugar over JavaScript's existing prototypal inheritance model. They provide a cleaner, more familiar (class-based) syntax for defining constructors and methods, but under the hood, they still rely on prototypes.

**JS7** — **The `this` Keyword and Binding Rules**
*   **`this` Keyword:** Refers to the object that is currently executing the code. Its value is determined dynamically based on *how* a function is called, not where it is defined.
*   **4 Binding Rules (in priority order):**
    1.  **`new` binding:** When a function is called with `new`, `this` refers to the newly created instance.
    2.  **Explicit binding (`.call()`, `.apply()`, `.bind()`):** When `this` is explicitly set using these methods.
    3.  **Implicit binding:** When a function is called as a method of an object (e.g., `obj.method()`). `this` refers to `obj`.
    4.  **Default binding:** When a function is called standalone (in non-strict mode), `this` defaults to the global object (`window` or `global`).
*   **`bind()`:** Returns a *new function* that is permanently bound to a specific `this` context.
*   **Re-binding:** Yes, the returned function can be re-bound using `.bind()` again, but the original binding context is preserved unless explicitly overridden.

**JS8** — **WeakRef and FinalizationRegistry**
*   **WeakRef:** A reference to an object that allows the garbage collector (GC) to reclaim the object even if the `WeakRef` itself is still held. It does not prevent the object from being collected.
*   **FinalizationRegistry:** A mechanism that allows you to register a callback function that will be executed *after* the garbage collector has finalized (reclaimed) an object that was registered.
*   **Use Cases:**
    *   **WeakRef:** Implementing caches or maps where you want to hold references to objects without preventing them from being garbage collected (e.g., memory management in large applications).
    *   **FinalizationRegistry:** Performing cleanup tasks (like removing listeners or closing resources) associated with an object *after* it is no longer reachable by the application.
*   **WeakMap Keys:** WeakMap keys must be objects because the GC needs to track the object's reachability. If a key were a primitive (like a string or number), the GC would treat it as a strong reference, preventing the key object from ever being collected, defeating the purpose of the WeakMap.

**JS9** — **V8 Optimization (Hidden Classes, Inline Caching, Deoptimization)**
*   **V8 Optimization:** V8 uses sophisticated techniques to optimize JavaScript, which is dynamically typed. It attempts to treat JS code like statically typed code during runtime.
*   **Hidden Classes (Maps):** V8 tracks the structure (shape) of objects. When an object is created, V8 assigns it a "hidden class" based on the order and types of its properties. If all instances of an object share the same structure, V8 can optimize property access (e.g., accessing `obj.prop` becomes a direct memory offset lookup instead of a hash map lookup).
*   **Inline Caching (IC):** When a function is called, V8 caches the results of property lookups or method calls for the specific object type it just saw. The next time the function runs with the same object type, it skips the lookup process.
*   **Deoptimization:** Occurs when V8's assumptions about the code's structure are violated. For example, if an object that was previously optimized (e.g., having only properties A and B) suddenly gains a new property C, V8 must discard the optimized code path and revert to slower, generic property lookup (hash map).
*   **Deoptimization Triggers:** Changing the structure of objects (adding/deleting properties), or changing the type of a variable that was previously assumed to be consistent.

**JS10** — **Tree-shaking**
*   **Tree-shaking:** A form of dead code elimination used by module bundlers (like Webpack or Rollup). It analyzes the dependency graph of the application and removes any code (functions, classes, modules) that are imported but never actually used.
*   **ES Modules (ESM):** ESM uses static `import` and `export` syntax. Because these imports are static (they are known at compile time), bundlers can reliably trace the dependency graph and determine which exports are unused, allowing for effective tree-shaking.
*   **CommonJS (CJS):** CJS uses dynamic `require()` calls. Since `require()` can be called conditionally or based on runtime logic, bundlers cannot reliably determine which parts of a module are used, making effective tree-shaking extremely difficult or impossible.

**JS11** — **null vs undefined, == vs ===, ?? and ?.**
*   **null:** Represents the intentional absence of any object value. It is an assignment value.
*   **undefined:** Means a variable has been declared but has not yet been assigned a value. It is a state of a variable.
*   **== vs ===:**
    *   `==` (Loose Equality): Performs type coercion before comparison. `null == undefined` is `true`.
    *   `===` (Strict Equality): Compares both value and type without coercion. `null === undefined` is `false`.
*   **Nullish Coalescing (`??`):** Returns the right-hand operand when the left-hand operand is `null` or `undefined`. It specifically avoids coercing other "falsy" values (like `0` or `""`).
    *   *Example:* `const result = value ?? defaultValue;`
*   **Optional Chaining (`?.`):** Allows you to safely access nested properties of an object without having to explicitly check if each intermediate property exists. If any part of the chain is `null` or `undefined`, the expression short-circuits and returns `undefined`.
    *   *Example:* `user?.address?.street`

**JS12** — **map(), filter(), reduce(), flatMap()**
*   **map():** Creates a new array populated with the results of calling a provided function on every element in the calling array. It always returns an array of the same length.
*   **filter():** Creates a new array with all elements that pass the test implemented by the provided function. The resulting array is shorter than or equal to the original.
*   **reduce():** Executes a reducer function on each element of the array, resulting in a single output value.
    *   **With Initial Value:** The initial value is passed as the second argument to `reduce()`. This value becomes the initial accumulator (`acc`). If no initial value is provided, the first element of the array is used as the initial accumulator, and iteration starts from the second element.
*   **flatMap():** A combination of `map()` followed by `flat()` (or `reduce()` followed by `flat()`). It maps each element using a mapping function, and then flattens the result into a new array by one level.
    *   **Usefulness:** Useful when mapping an array results in an array of arrays, and you want a single, flat output array.

**JS13** — **Template Literals and Tagged Templates**
*   **Template Literals:** Strings enclosed by backticks (`` `...` ``). They allow for embedded expressions using `${expression}` and support multi-line strings without needing `\n`.
*   **Tagged Templates:** A function that is executed before the template literal is converted into a string. The function receives two arguments: the strings (the literal parts) and an array of substitutions (the values inside `${}`).
*   **Example (HTML Escaping):**
    ```javascript
    function htmlEscape(strings, ...values) {
      let result = strings[0];
      for (let i = 0; i < values.length; i++) {
        result += values[i].toString().replace(/[&<>"']/g, '');
        result += strings[i + 1];
      }
      return result;
    }
    const safeHtml = htmlEscape`<h1>Hello ${'World <script>'}!</h1>`;
    // safeHtml is now a string with HTML characters escaped.
    ```

**JS14** — **Destructuring**
*   **Destructuring:** A syntax that allows you to unpack values from arrays or properties from objects into distinct variables.
*   **Object Destructuring:** Extracts properties from an object into variables based on the property names.
    ```javascript
    const user = { name: 'Alice', age: 30 };
    const { name, age } = user; // name = 'Alice', age = 30
    ```
*   **Array Destructuring:** Extracts values from an array based on position.
    ```javascript
    const colors = ['red', 'green', 'blue'];
    const [first, second] = colors; // first = 'red', second = 'green'
    ```
*   **Default Values:** Allows you to assign a fallback value if the property/element is missing.
    ```javascript
    const { age = 25 } = user; // age = 25 if missing
    ```
*   **Renaming:** Allows you to assign the extracted value to a different variable name.
    ```javascript
    const { name: userName } = user; // userName = 'Alice'
    ```
*   **Rest Operator (`...`):** When used in destructuring, it collects all remaining properties/elements into a new array.
    ```javascript
    const { id, ...rest } = user; // rest = { age: 30 }
    ```

**JS15** — **for...in vs for...of**
*   **for...in:** Iterates over the *enumerable properties* of an object (including inherited enumerable properties). It is designed for iterating over object keys.
    *   *Use Case:* Iterating over object keys/values.
    *   *Warning:* Should be avoided on arrays because it iterates over enumerable properties, which might include non-index properties added to the array object, and the order is not guaranteed.
*   **for...of:** Iterates over the *values* of an iterable object (like Arrays, Strings, Maps, Sets).
    *   *Use Case:* Iterating over array elements or string characters.
*   **Why avoid for...in on arrays:** It iterates over properties, not indices, and the iteration order is not guaranteed to be sequential, leading to unpredictable behavior.

**JS16** — **TypeScript Generics**
*   **Generics:** Allow you to write reusable code that can work over a variety of types rather than a single one. They allow you to define components that are agnostic to the specific type they will operate on.
*   **Generic Constraints (`extends`):** Restricts the types that a generic parameter can be. This ensures that the generic type has certain properties or methods before the code attempts to use them.
    *   *Example:* `function identity<T extends { length: number }>(arg: T): T { return arg; }` (T must have a `length` property).
*   **Conditional Types:** Allows you to define a type based on a condition.
    *   *Example:* `type IsStringOrNumber<T> = T extends string ? string : number;`
*   **Infer Keyword:** Used to infer the type of a value or property automatically, often used in utility types or when defining complex generic constraints.
    *   *Example:* `type MyType = infer T;` (T will be inferred as the type of the value provided).

**JS17** — **Module Systems (CJS vs ESM)**
*   **Module System:** The mechanism by which code is organized into reusable, encapsulated units.
*   **CommonJS (CJS):** Synchronous module system used primarily by Node.js historically. Uses `require()` to import and `module.exports` to export. It is synchronous and relies on runtime resolution.
*   **ES Modules (ESM):** Standardized, asynchronous module system (`import`/`export`). It is static, meaning the dependencies are known at parse time, which enables tree-shaking.
*   **Node.js Handling:** Node.js supports both. By default, `.js` files are often treated as CJS.
*   **`"type": "module"`:** When set in `package.json`, it tells Node.js to treat all `.js` files in that project as ES Modules, enabling the use of `import`/`export` syntax and enabling modern features like top-level `await`.

**JS18** — **Structural Type System, Excess Property Checks, extends vs satisfies, Variance**
*   **Structural Type System:** TypeScript determines compatibility based on the *shape* of the types, not their declared name. If two types have the same structure (same properties and types), they are considered compatible, even if they don't share a common ancestor.
*   **Excess Property Checks:** A compiler option that enforces that an object passed to a function or assigned to a variable does not contain properties that are not defined in the expected type. This helps prevent accidental data pollution.
*   **`extends` vs `satisfies`:**
    *   **`extends`:** Used for inheritance. The derived type *is* a subtype of the base type.
    *   **`satisfies`:** Used for type checking. It asserts that a value *conforms* to a type, but it does not change the type of the value itself. This is useful when you want to keep all properties of a value while ensuring it meets a specific interface contract.
*   **Variance (in/out):** Defines how subtyping works with generics.
    *   **Covariance (`out`):** A type is covariant if a subtype can be used where a supertype is expected (e.g., `Dog` is a subtype of `Animal`). Used for return types.
    *   **Contravariance (`in`):** A type is contravariant if a supertype can be used where a subtype is expected (e.g., a function accepting `Animal` can be used where a function accepting `Dog` is expected). Used for input parameters.

**JS19** — **Proxy and Reflect**
*   **Proxy:** An object that wraps another object (the target) and allows you to intercept fundamental operations performed on that target.
*   **Reflect:** A set of static methods that provide a standardized, low-level interface for performing operations (like `get`, `set`, `apply`) on objects. Proxies use the `Reflect` API to perform the actual operation after interception.
*   **Interception:**
    *   **Property Access (`get`):** Intercepts reading a property value.
    *   **Property Assignment (`set`):** Intercepts writing a property value.
    *   **Function Calls (`apply`/`construct`):** Intercepts calling a function wrapped by the Proxy.
*   **Practical Example (Validation/Logging):** A Proxy can intercept a property assignment (`set`) to validate the input data before it modifies the target object, or log every time a property is accessed.

**JS20** — **SharedArrayBuffer and Atomics**
*   **SharedArrayBuffer (SAB):** A low-level JavaScript object that allows multiple execution contexts (like Web Workers) to share the same block of memory. This is crucial for high-performance, shared-memory concurrency.
*   **Atomics:** A set of methods that operate on the integer values within a SharedArrayBuffer. They guarantee that operations (like reading or writing a value) are performed atomically—meaning they complete entirely without interruption from other threads.
*   **Web Worker Communication:** Instead of passing messages (which involves copying data), workers can access and modify the same memory region (the SAB) simultaneously, provided they use `Atomics` to manage concurrent access safely.
*   **Ordering Guarantees:** Atomics operations provide memory ordering guarantees, ensuring that memory operations appear in a specific sequence to all threads, preventing race conditions.
*   **Atomics.wait/Atomics.notify:** These methods allow threads to block (sleep) until a specific condition is met, preventing busy-waiting.
    *   `Atomics.wait(typedArray, index, expectedValue)`: Blocks the thread until the value at `index` is *not* equal to `expectedValue`, or until a timeout occurs.
    *   `Atomics.notify(typedArray, index, count)`: Wakes up a specified number of waiting threads.

## Bash

**B1** — **$@ vs $* and "$@" vs "$*"**
*   **$@:** Expands to all positional parameters, with each parameter quoted separately. This is the safest and most robust way to iterate over arguments, preserving spaces and special characters.
    *   *Example:* If arguments are `file 1`, `"$@"` expands to `"file" "1"`.
*   **$*:** Expands to all positional parameters as a single string.
    *   *Example:* If arguments are `file 1`, `"$*"` expands to `"file 1"`.
*   **$@ vs $*:**
    *   `$@` (quoted): Treats each argument as a separate word.
    *   `$*` (quoted): Treats all arguments as a single word.

**B2** — **set -euo pipefail**
This command sets strict error handling for the script:
*   **`set -e` (errexit):** Causes the script to exit immediately if any command exits with a non-zero status (i.e., fails).
*   **`set -u` (nounset):** Causes the script to exit immediately if an unset variable is used. This prevents silent errors due to typos.
*   **`set -o pipefail`:** Ensures that a pipeline's exit status is the exit status of the *last* command that failed, not just the exit status of the final command. This is crucial for reliable pipeline error checking.

**B3** — **$(command) vs `command`, $((expression)) vs expr**
*   **$(command) (Command Substitution):** Executes the `command` and replaces the substitution with the standard output (stdout) of that command. This is used to capture the output of a command into a variable or use it as an argument.
    *   *Example:* `echo "The date is $(date)"`
*   **`command` (Backticks):** An older, deprecated form of command substitution that works identically to `$(command)`.
*   **$((expression)) (Arithmetic Expansion):** Evaluates a mathematical expression. This is used for integer arithmetic.
    *   *Example:* `result=$(( 5 + 3 * 2 ))`
*   **`expr`:** An external utility command used to evaluate expressions. It is less efficient and more verbose than `$((...))`.

**B4** — **Process Substitution (<(command))**
*   **Process Substitution:** Allows the output of a command to be treated as a temporary file that can be used as an argument for another command (like `diff` or `sort`). The shell creates a named pipe or FIFO and redirects the command's output into it.
*   **When to use:** When a command expects a file path as an argument, but you want to feed it the output of another command.
*   **Practical Example with diff:**
    ```bash
    # Compare the output of 'ls -l' with the output of 'find . -name "*.txt"'
    diff <(ls -l) <(find . -name "*.txt")
    ```

**B5** — **Safe Iteration over Files**
*   **The Danger of `for f in $(ls)`:** `ls` outputs filenames separated by newlines and spaces. If a filename contains a space (e.g., `My File.txt`), `$(ls)` will split it into multiple tokens (`My`, `File.txt`), causing the loop to process incorrect names.
*   **Safe Iteration:** Use a glob pattern combined with a `while read` loop, or use `find` with the `-print0` option and `xargs -0`.
    ```bash
    # Safest method using find and xargs
    find . -type f -print0 | xargs -0 -I {} echo "Processing: {}"
    
    # Alternative using globbing (if no complex filtering is needed)
    for f in *; do
        echo "Processing: $f"
    done
    ```

**B6** — **Here Document (<<EOF) vs Here String (<<<)**
*   **Here Document (`<<EOF`):** Allows you to provide multiple lines of input to a command. The shell reads input until it encounters the delimiter line (e.g., `EOF`).
    ```bash
    cat <<EOF
    Line 1
    Line 2
    EOF
    ```
*   **Here String (`<<<`):** Provides a single string as standard input to a command. It is used for single-line input.
    ```bash
    echo "Hello World" <<< "Hello World"
    ```
*   **`<<-EOF` (Escaped Here Document):** This variant allows you to use tabs within the input lines without them being expanded into spaces. By default, bash expands tabs to spaces. Using `<<-EOF` tells bash to treat tabs literally.

**B7** — **Redirection Differences**
*   **`cmd > file 2>&1`:**
    1.  `> file`: Redirects standard output (stdout, file descriptor 1) to `file`.
    2.  `2>&1`: Redirects standard error (stderr, file descriptor 2) to the same location as stdout (which is now `file`).
    *   *Result:* Both stdout and stderr go into `file`.
*   **`cmd 2>&1 > file`:**
    1.  `2>&1`: Redirects stderr (2) to stdout (1).
    2.  `> file`: Redirects stdout (1) to `file`.
    *   *Result:* Both stdout and stderr go into `file`. (This is functionally equivalent to the first example, but the order matters conceptually).
*   **`cmd &> file`:** (Bash specific) A shorthand that redirects both stdout and stderr to the specified file.
*   **Why the first two produce different results (if interpreted strictly):** If the shell processes the redirection sequentially, the order matters. In `cmd > file 2>&1`, `2>&1` happens *after* `> file` has established `file` as the target for stdout. In `cmd 2>&1 > file`, `2>&1` happens *before* `> file` establishes the final target. However, in modern bash, both sequences usually achieve the same result of merging both streams into the file. The key difference is the *order of operation* and the use of the shorthand `&>`.

**B8** — **Safe Lock File Creation**
*   **Why mkdir is preferred:** Using `mkdir` with the `-p` (parents) and `-m` (mode) flags, combined with the `-p` flag, allows you to use the atomic `mkdir` operation. If the directory already exists, `mkdir` succeeds without error, but if it fails, it means another process is likely holding the lock.
*   **Locking Script:**
    ```bash
    LOCK_DIR="/tmp/my_script.lock"
    
    # Attempt to create the lock directory atomically
    if ! mkdir "$LOCK_DIR" 2>/dev/null; then
        echo "Lock already held. Exiting."
        exit 1
    fi
    
    # Trap handler for cleanup
    cleanup() {
        echo "Releasing lock..."
        rmdir "$LOCK_DIR" 2>/dev/null
    }
    trap cleanup EXIT SIGINT SIGTERM
    
    # Main script logic here...
    echo "Lock acquired. Running script..."
    sleep 5
    ```
*   **Explanation:**
    *   `mkdir "$LOCK_DIR"` is atomic. If the directory exists, the command fails (non-zero exit code).
    *   `trap cleanup EXIT SIGINT SIGTERM`: Ensures the `cleanup` function runs when the script exits normally (`EXIT`) or is interrupted (`SIGINT`, `SIGTERM`).
    *   `rmdir`: Used instead of `rm -rf` because the lock directory should only be removed if it is empty, ensuring no other processes are using it.

**B9** — **Quotes in Bash**
*   **No Quotes:** Allows for variable expansion, command substitution, and globbing.
    *   *Example:* `echo $VAR` (expands variable)
*   **Double Quotes (`"`...`"`):** Allows for variable expansion (`$VAR`) and command substitution (`$(cmd)`), but prevents word splitting and pathname expansion (globbing).
    *   *Example:* `echo "Hello $VAR"` (expands variable, keeps spaces intact)
*   **Single Quotes (`'`...`'`):** Treats everything literally. No expansion occurs.
    *   *Example:* `echo 'Hello $VAR'` (prints `$VAR` literally)

**B10** — **File Checks and [ ] vs [[ ]]**
*   **File Existence:** `[ -e filename ]` (checks if file/directory exists).
*   **Directory Check:** `[ -d directory ]` (checks if it is a directory).
*   **Readability Check:** `[ -r filename ]` (checks if the file is readable).
*   **`[ ]` (Test):** The traditional `test` command. It uses single brackets and requires spaces around the brackets. It is POSIX compliant and less feature-rich.
*   **`[[ ]]` (Conditional Expression):** Bash-specific. It is more powerful, supports regex matching (`=~`), and allows for more complex logical operations without needing to worry about word splitting.

**B11** — **$?, $$, $!, $#**
*   **$? (Exit Status):** Holds the exit status (0 for success, non-zero for failure) of the most recently executed foreground command.
    *   *Use Case:* Checking if a command succeeded: `if [ $? -eq 0 ]; then ...`
*   **$$ (Process ID):** The Process ID (PID) of the current shell.
    *   *Use Case:* Logging or debugging: `echo "Running as PID $$"`
*   **$! (Last Background PID):** The Process ID of the most recently executed background job.
    *   *Use Case:* Monitoring background tasks: `bg &; echo "Background PID: $!"`
*   **$# (Argument Count):** The number of positional parameters passed to the current script or function.
    *   *Use Case:* Validating input: `if [ $# -lt 2 ]; then echo "Need at least two arguments"; exit 1; fi`

**B12** — **Functions in Bash**
*   **Definition:** Functions group related commands.
*   **Syntax Difference:**
    *   `function foo {}`: Explicit keyword syntax.
    *   `foo() {}`: Standard, concise syntax.
    *   *Note:* Functionality is identical; the concise syntax is preferred.
*   **Returning Values:** Bash functions do not return values in the traditional sense. They return an *exit status* (0-255). To return data, you must print it to stdout, and the caller must capture it using command substitution.
    *   *Example:* `my_func() { echo "Result Data"; } result=$(my_func)`

**B13** — **PATH, Builtin vs External Commands**
*   **PATH Environment Variable:** A list of directories that the shell searches sequentially when a command is executed. When you type `ls`, the shell checks the directories listed in `$PATH` (e.g., `/bin`, `/usr/bin`) until it finds an executable named `ls`.
*   **Command Resolution:** The shell searches the directories listed in `$PATH` for the executable file matching the command name.
*   **Builtin Command:** A command that is part of the shell itself (e.g., `cd`, `echo`, `alias`). They are executed directly by the shell and do not require spawning a new process.
*   **External Command:** An executable file located in one of the directories listed in `$PATH` (e.g., `grep`, `awk`).
*   **Checking:** You can use `type command_name`. If it returns `command_name is a builtin`, it's a builtin. If it returns a path (e.g., `/bin/ls`), it's an external command.

**B14** — **Trap in Bash**
*   **Trap:** A mechanism that allows a script to define a function that will be executed when a specific signal is received or when the script exits.
*   **Cleanup Handlers:**
    *   `EXIT`: Runs when the script finishes, regardless of success or failure.
    *   `ERR`: Runs when a command fails (non-zero exit status), provided `set -e` is active.
    *   `INT`: Received when the user presses Ctrl+C (SIGINT).
    *   `TERM`: Received when the user requests termination (SIGTERM).
*   **Execution Order:** When multiple signals arrive, the shell handles them based on the signal priority and the order in which traps were set. Generally, `EXIT` runs last. If a script receives multiple signals simultaneously, the shell handles them sequentially, but the order of trap execution is determined by the `trap` command's definition.

**B15** — **xargs vs Command Substitution**
*   **Command Substitution:** Executes a command and captures its output as a string, which is then passed as arguments to another command. This is limited by word splitting and quoting issues.
    *   *Example:* `ls | xargs rm` (Dangerous if filenames contain spaces).
*   **xargs:** Takes standard input (usually a list of items) and builds and executes command lines using those items as arguments.
*   **Handling Spaces/Newlines (Safe):**
    ```bash
    find . -type f -print0 | xargs -0 -I {} mv {} {}.bak
    ```
    *   `-0`: Tells `xargs` to expect null-terminated input, correctly handling filenames with spaces or newlines.
    *   `-I {}`: Defines a replacement string (`{}`) that `xargs` will substitute for each input item.
*   **xargs -P:** Enables parallel execution. `-P N` specifies that `xargs` should run up to $N$ processes in parallel, significantly speeding up tasks on large datasets.

**B16** — **Bash Arrays and Associative Arrays**
*   **Indexed Arrays (Standard):** Ordered lists accessed by numerical index (0, 1, 2...).
    *   *Declaration:* `my_array=(apple banana cherry)`
    *   *Append:* `my_array+=("date")`
    *   *Iteration:* `for item in "${my_array[@]}"; do ...`
    *   *Length:* `${#my_array[@]}`
*   **Associative Arrays (Maps/Dictionaries):** Key-value pairs accessed by string keys.
    *   *Declaration:* `declare -A my_map`
    *   *Assignment:* `my_map[key]="value"`
    *   *Iteration:* `for key in "${!my_map[@]}"; do ...`
    *   *Length:* `echo ${#my_map[@]}`
*   **Differences:** Indexed arrays maintain order and use integers as keys. Associative arrays use arbitrary strings as keys and are used for mapping data.

**B17** — **Subshell vs Group Command**
*   **Group Command `{ ...; }`:** Executes commands in the *current* shell environment. Any variables set or modified inside the group command persist in the parent shell.
    *   *Scope:* Shared.
    *   *Exit Code:* The exit code of the last command in the group is the group's exit code.
*   **Subshell `(...)`:** Executes commands in a *new, separate* shell process. Any variables set or modified inside the subshell are lost when the subshell exits.
    *   *Scope:* Isolated.
    *   *Exit Code:* The exit code of the subshell is returned to the parent shell.
*   **Why piping into a while loop loses variable changes:** When you pipe output into a `while read` loop, the loop runs in a subshell (or a sub-process context). Any variables modified inside that subshell are local to that subshell and are not reflected back in the parent shell environment. To avoid this, use `while IFS= read -r line; do ... done < file`.

**B18** — **Signals and Job Control**
*   **Signals:** Notifications sent to a process to request or inform it of an event.
    *   **SIGINT (2):** Interrupt signal (Ctrl+C). Requests immediate termination.
    *   **SIGTERM (15):** Termination signal. A polite request for the process to shut down gracefully.
    *   **SIGHUP (1):** Hangup signal. Often used to tell a daemon to reload its configuration without stopping.
    *   **SIGKILL (9):** Uncatchable, immediate termination. The kernel kills the process instantly; no cleanup is possible.
*   **Graceful Shutdown:** To handle graceful shutdown, the script must `trap` `SIGINT` and `SIGTERM`. The trap handler should perform necessary cleanup (e.g., closing database connections, releasing locks) before exiting.
*   **Background Processes:** Use `&` to run a command in the background. The shell returns control immediately, allowing the script to continue while the background job runs. You can manage these jobs using `jobs` and `fg`/`bg`.

**B19** — **Parallel Log Processing Script**
*   **Goal:** Process a large file in parallel, merge results, and handle errors.
*   **Script Structure:**
    ```bash
    LOG_FILE="large.log"
    OUTPUT_DIR="results"
    mkdir -p "$OUTPUT_DIR"
    
    # Function to process a chunk of the log
    process_chunk() {
        local chunk_file="$1"
        local output_file="$2"
        
        # Simulate processing (e.g., filtering, counting)
        grep "ERROR" "$chunk_file" | wc -l > "$output_file"
        
        # Return status
        return $?
    }
    
    # 1. Split the file into chunks
    split -l 1000 "$LOG_FILE" "$OUTPUT_DIR/chunk_"
    
    # 2. Process chunks in parallel
    # Use find/xargs -0 to handle filenames safely
    find "$OUTPUT_DIR" -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c '
        # $0 is the chunk file, $1 is the output file
        process_chunk "$0" "$1"
    ' _ {} "$OUTPUT_DIR/result_"
    
    # 3. Merge results
    cat "$OUTPUT_DIR"/result_* > final_summary.txt
    
    # 4. Error Handling (Requires checking the exit status of the parallel jobs)
    # This is complex; typically, you check the exit status of the xargs command itself.
    if [ $? -ne 0 ]; then
        echo "One or more parallel jobs failed." >&2
    fi
    ```
*   **Performance Trade-offs:** Parallel processing (using `-P`) drastically reduces wall-clock time by utilizing multiple CPU cores. However, it introduces overhead due to process creation and inter-process communication (IPC). For very small files, the overhead of parallelization can be slower than sequential processing.
*   **Error Propagation:** When using `xargs -P`, the exit status of `xargs` reflects the exit status of the last job, or if `set -e` is used inside the parallel function, it will fail the entire `xargs` command if any child process fails.

**B20** — **exec vs Normal Command, Coprocess**
*   **Normal Command:** Spawns a new process (forks). The parent shell continues execution while the child runs independently.
*   **`exec`:** Replaces the current shell process image with the command specified. The shell *is* the command. The shell does not continue execution after `exec` unless the command itself exits.
    *   *Use Case:* When you want the shell to become the new program (e.g., running a script or a new shell).
*   **File Descriptor Manipulation:**
    *   `exec 3>file`: Opens a file and assigns it to file descriptor 3.
    *   `exec 3>&-`: Closes file descriptor 3.
*   **Bash Coprocess:** A mechanism that allows a shell to run two or more processes concurrently within the same shell environment, allowing them to communicate via pipes.
    *   **Use Case:** Running a long-running background task (like a server or a complex calculation) and allowing the main script to interact with it (e.g., sending configuration changes or reading status) without relying on external pipes or background job management.

## PowerShell

**PS1** — **Write-Output vs Write-Host**
*   **Write-Output:** Sends objects to the PowerShell pipeline. This is the standard, programmatic way to output data. The output is treated as data objects that can be piped to other cmdlets, allowing for filtering, formatting, and further processing.
*   **Write-Host:** Writes text directly to the console (the host window). It bypasses the pipeline. It is used for displaying user-friendly messages, progress bars, or simple status updates that do not need to be processed by other cmdlets.
*   **Why it matters:** If you use `Write-Host` inside a function, the output is not captured by the pipeline or returned by the function, which can lead to unexpected behavior when scripting.

**PS2** — **Pipeline, ForEach-Object vs foreach statement**
*   **PowerShell Pipeline:** The mechanism where objects flow from one cmdlet to the next. Cmdlets receive objects from the pipeline and process them.
*   **`ForEach-Object` (Pipeline Cmdlet):** This cmdlet processes objects *as they flow through the pipeline*. It is designed to handle streaming data efficiently.
    *   *Syntax:* `Get-ChildItem | ForEach-Object { $_.Name }`
*   **`foreach` statement (Script Block):** This is a control flow structure used within a script or function. It iterates over a collection (an array, a list, etc.) that is already loaded into memory.
    *   *Syntax:* `$myArray | foreach { ... }`
*   **When to use each:**
    *   **`ForEach-Object`:** When processing a stream of objects (e.g., reading thousands of files from a directory).
    *   **`foreach`:** When iterating over a finite, in-memory collection (e.g., iterating over a list of user names).

**PS3** — **[PSCustomObject] vs [hashtable]**
*   **[hashtable]:** A collection of key-value pairs where the keys are strings. It is a dictionary-like structure. It is excellent for quick lookups and storing arbitrary data.
    *   *Example:* `$data = @{ Name = "Alice"; Age = 30 }`
*   **[PSCustomObject]:** A structured object created specifically for the pipeline. It has defined properties (like a class instance) and is designed to be easily consumed by other cmdlets.
    *   *Example:* `$data = [PSCustomObject]@{ Name = "Alice"; Age = 30 }`
*   **When to use each:**
    *   **Hashtable:** When you need a flexible dictionary structure for internal logic or configuration.
    *   **PSCustomObject:** When you are generating output that needs to be structured and consumed by other cmdlets in the pipeline.
*   **Conversion:**
    *   `[hashtable] to PSCustomObject`: `$ht = @{...}; [PSCustomObject]$ht`
    *   `PSCustomObject to hashtable`: `$pso = [PSCustomObject]@{...}; $ht = @{}` ; $pso.PSObject.Properties | ForEach-Object { $ht[$_.Name] = $_.Value }`

**PS4** — **Error Handling (Terminating vs Non-Terminating)**
*   **Non-Terminating Errors (Warnings):** Errors that do not stop the script execution. They are logged and can be handled by the script, allowing execution to continue.
*   **Terminating Errors:** Errors that stop the script execution immediately (unless explicitly caught).
*   **Interaction:**
    *   **`-ErrorAction`:** Specifies how a specific cmdlet handles errors. Values include `Stop` (terminating), `Continue` (non-terminating), or `SilentlyContinue`.
    *   **`$ErrorActionPreference`:** A global variable that sets the default error handling behavior for the entire session (e.g., `ErrorActionPreference = "Stop"`).
    *   **`try/catch`:** The structured way to handle errors. The `try` block executes code; if a terminating error occurs, execution jumps to the `catch` block, allowing the script to recover or log the error without crashing.

**PS5** — **Splatting (@params)**
*   **Splatting:** The practice of passing a hashtable (or array) to a cmdlet parameter, which automatically expands the key-value pairs into individual arguments for that cmdlet.
*   **Example:**
    ```powershell
    $params = @{
        Path = "C:\Logs"
        Recurse = $true
        ErrorAction = "Stop"
    }
    Get-ChildItem @params
    ```
*   **Difference from passing a hashtable as a single parameter:** If you pass a hashtable as a single parameter, the cmdlet receives the hashtable object itself. If you use splatting, the cmdlet receives the *values* of the hashtable as separate, individual arguments.

**PS6** — **PowerShell Remoting**
*   **PowerShell Remoting:** Allows you to execute PowerShell commands and scripts on a remote machine.
*   **`Invoke-Command -ComputerName`:** Executes a script block on a remote machine and returns the results to the local session. It is used for running specific commands.
*   **`Enter-PSSession`:** Establishes an interactive, persistent session on a remote machine, allowing you to run commands as if you were logged into that machine.
*   **Protocol:** PowerShell Remoting primarily uses **WinRM (Windows Remote Management)**. WinRM is a SOAP-based protocol that allows management of Windows systems.
*   **Relation to SSH:** While WinRM is the native Windows protocol, PowerShell 7+ supports SSH remoting, allowing it to function similarly to Linux/Unix environments.

**PS7** — **Type System and Implicit Behavior**
*   **Implicit Behavior:** PowerShell is highly dynamic and object-oriented. When a function returns a collection (even if it's an empty array), PowerShell treats it as an object collection.
*   **The Problem:** When a function returns an empty array (`@()`), the variable `$x` holds an array object. When you try to access properties on an empty array, you are accessing properties of the *array object itself*, not the elements within it.
*   **Example Analysis:**
    ```powershell
    # $x is an array object, even if empty.
    $x.GetType().Name  # Output: Object[] (or Array)
    ```
*   **When 0 items are returned:** If the function returns nothing (i.e., it doesn't explicitly return anything), the variable `$x` will be `$null`.
*   **Correct Pattern:** If you intend for the function to return *no* results, ensure the function simply finishes without an explicit `return` statement. If you must return a variable, check if it is `$null` before attempting to index or access properties.

**PS8** — **[scriptblock] vs Function, Double-Hop Problem**
*   **[scriptblock]:** A block of code that can be passed as an argument to a cmdlet or function. It is essentially a piece of executable code that is not necessarily wrapped in a named function.
*   **Function:** A named, reusable block of code with defined parameters and scope.
*   **Passing to Remote Session:** You pass a scriptblock using the `-ScriptBlock` parameter of `Invoke-Command`.
*   **Double-Hop Problem:** When running a script block remotely, variables defined in the *local* session are not automatically available in the *remote* session's scope. If the script block tries to access a local variable, it fails.
*   **Solutions:**
    *   **CredSSP:** Uses a credential delegation mechanism to allow the remote session to inherit local security context.
    *   **`Invoke-Command -ArgumentList`:** Explicitly passes local variables into the remote script block as parameters, solving the scope issue.

**PS9** — **@() vs [array], Indexing $null vs Empty Array**
*   **`@()`:** Creates an empty array object. It is the standard, idiomatic way to initialize an empty collection in PowerShell.
*   **`[array]`:** This is a type accelerator. While you can use it to define an array, it is less common for initialization than `@()`.
*   **Forcing a single result into an array:** Use the array constructor or the pipeline: `1 | Select-Object -First 1` or `[array]@{Value=1}`.
*   **Indexing $null vs Empty Array:**
    *   **$null:** Attempting to index `$null` (e.g., `$null[0]`) results in a terminating error because `$null` is not an object and has no properties or indices.
    *   **Empty Array (`@()`):** Attempting to index an empty array (e.g., `$emptyArray[0]`) results in a non-terminating error (an index out of bounds error), which is generally safer and easier to handle.

**PS10** — **Comparison Operators**
*   **Standard Operators (Case-Insensitive):**
    *   `-eq`: Equal to (case-insensitive).
    *   `-ne`: Not equal to (case-insensitive).
    *   `-like`: Wildcard matching (uses `*` and `?`).
    *   `-match`: Regular expression matching.
    *   `-contains`: Checks if a collection contains a specific item.
    *   `-in`: Checks if a value is present in a list of values.
*   **Case-Sensitive Variants:**
    *   `-ceq`: Case-sensitive equal to.
    *   `-clike`: Case-sensitive wildcard matching.
    *   (And others, like `-cmatch` for case-sensitive regex).
*   **`Contains` vs `In`:**
    *   **`-contains`:** Checks if a *single value* exists within a *collection* (array).
    *   **`-in`:** Checks if a *single value* is present within a *list of values* (often used in a comparison, e.g., `if ($value -in @('A', 'B'))`).

**PS11** — **PowerShell Modules**
*   **Module:** A collection of cmdlets, functions, and variables that provide a cohesive set of functionality. They encapsulate logic and prevent naming conflicts.
*   **Script Module (.psm1):** A file containing PowerShell code (functions, cmdlets). It is the most common type.
*   **Manifest Module (.psd1):** A metadata file that describes the module (version, dependencies, required parameters, etc.). It does not contain code itself but is used by the module loader.
*   **Binary Module:** A module that contains compiled code (e.g., C# assemblies) that PowerShell can load and execute.
*   **`Import-Module`:** The cmdlet used to load a module into the current session, making its functions and cmdlets available for use.

**PS12** — **String Interpolation and Here-Strings**
*   **String Interpolation:** The process of embedding variables or expressions directly into a string literal.
*   **Double Quotes (`"`...`"`):** Enables interpolation. Variables and expressions inside double quotes are evaluated at runtime.
    *   *Example:* `"The value is $variable."`
*   **Single Quotes (`'`...`'`):** Treats the string literally. No interpolation or expansion occurs.
    *   *Example:* `'The value is $variable.'` (prints the literal string)
*   **Including Expressions:** Use curly braces `{}` to explicitly define the scope of a variable or expression within an interpolated string.
    *   *Example:* `"The length is {($myArray.Count)}."`
*   **Here-String (`@"..."@`):** Allows multi-line strings without needing the `\n` character. It is useful for embedding large blocks of text or code.
    *   *Example:* `@"Line 1`n`Line 2"@`

**PS13** — **Get-Member, Object Exploration, Select-Object vs Where-Object**
*   **Get-Member:** A cmdlet used to retrieve the properties, methods, and other members of an object. It is essential for introspection in PowerShell.
*   **Object Exploration:** You use `Get-Member` to see what an object can do.
*   **Properties:** Data fields that hold values (e.g., `Name`, `Size`).
*   **Methods:** Functions or actions that can be called on the object (e.g., `.Calculate()`).
*   **NoteProperties:** Properties that are not standard data fields but are metadata about the object (e.g., `PSIsContainer`).
*   **`Select-Object` vs `Where-Object`:**
    *   **`Select-Object`:** Used for *projection*—choosing which properties to keep or renaming them. It filters the *output structure*.
    *   **`Where-Object`:** Used for *filtering*—selecting which objects in the pipeline meet a specific condition. It filters the *objects themselves*.

**PS14** — **PowerShell Classes**
*   **Classes:** Structures that define a blueprint for creating objects, encapsulating data (properties) and behavior (methods).
*   **Difference from C# Classes:** PowerShell classes are more dynamic and often rely on the underlying .NET framework. They are less rigid than C# classes, allowing for more dynamic property creation and runtime modification.
*   **Limitations:** While they support inheritance and interfaces, the implementation is often more complex than in C#. Inheritance can be tricky, and constructors are used to initialize state.
*   **Class vs Function:**
    *   **Function:** Best for simple, stateless operations (e.g., calculating a value).
    *   **Class:** Best for complex, stateful operations where the object needs to maintain internal data across multiple method calls (e.g., a `DatabaseConnection` object).

**PS15** — **CmdletBinding and Advanced Functions**
*   **CmdletBinding:** An attribute used in advanced functions that automatically grants the function the behavior of a standard cmdlet (e.g., accepting common parameters like `-Verbose`, `-Debug`, and supporting the pipeline).
*   **Advanced Functions:** Functions decorated with `[CmdletBinding()]` that adhere to strict cmdlet standards.
*   **`SupportsShouldProcess`:** A parameter that allows the function to check if the user wants to proceed with a potentially destructive action (like deleting a file) before executing it. This is crucial for safety.
*   **`DefaultParameterSetName`:** Allows the function to define a default set of parameters that should be used if the user does not specify any parameter set.
*   **`ValueFromPipeline`:** A parameter attribute that tells the function to accept input objects from the pipeline, allowing the function to process streamed data.
*   **Begin, Process, End Blocks:**
    *   **Begin:** Runs once before the pipeline starts. Used for setup (e.g., connecting to a database).
    *   **Process:** Runs for every object received from the pipeline. This is where the core logic resides.
    *   **End:** Runs once after the pipeline finishes. Used for cleanup (e.g., closing the database connection).

**PS16** — **PowerShell Providers System**
*   **Providers:** A mechanism that allows PowerShell to treat different types of data sources (files, registry keys, environment variables, certificates) as if they were standard file system objects.
*   **How Get-ChildItem works:** `Get-ChildItem` is the core cmdlet, but its behavior is determined by the provider it is operating on. When you run `Get-ChildItem C:\`, it uses the `FileSystem` provider. When you run `Get-ChildItem HKCU:\`, it uses the `Registry` provider.
*   **Accessing Registry like a File System:** The registry is exposed as a provider path. You navigate it using standard path syntax: `Get-ChildItem -Path HKCU:\Software\Microsoft\Windows`.

**PS17** — **Runspaces and Thread Safety**
*   **Runspace:** An isolated execution environment where PowerShell commands are run. It manages the state, session, and execution context.
*   **[runspace]:** A single, active execution environment.
*   **[runspacepool]:** A pool of runspaces. Instead of creating a new runspace for every command, the pool reuses existing ones, which is highly efficient for parallel operations.
*   **Parallel Execution:**
    *   **`ForEach-Object -Parallel` (v7+):** The modern, simple way to run a script block in parallel. PowerShell manages the runspaces and thread safety internally.
    *   **Manual Runspace Management:** For older versions or highly customized scenarios, you manually create and manage `[runspace]` objects, often pooling them yourself, to achieve parallelism.

**PS18** — **PSScriptAnalyzer**
*   **PSScriptAnalyzer:** A static code analysis tool for PowerShell. It checks scripts against a defined set of best practices, coding standards, and security guidelines.
*   **Enforcement:** It identifies potential issues like poor naming conventions, inefficient loops, security vulnerabilities, and non-standard practices.
*   **Rules, Severity, Custom Rules:**
    *   **Rules:** Specific checks (e.g., `PSBestPractice-UseCmdletBinding`).
    *   **Severity Levels:** Categorize the rule's impact (e.g., `Warning`, `Error`, `Critical`).
    *   **Custom Rules:** Allows users to define their own rules based on organizational standards.
*   **Suppression and CI/CD:** Rules can be suppressed using `#Requires -ErrorAction SilentlyContinue` or specific comments. In CI/CD, PSScriptAnalyzer is run as a gate check; if it finds rules above a certain severity, the build fails, enforcing quality standards.

**PS19** — **$using: scope vs $args/-ArgumentList**
*   **$args/-ArgumentList:** Used when passing variables to a remote session (`Invoke-Command`). The variables are serialized (converted to a format like CLIXML) and sent across the network.
*   **$using: scope:** Used when running a script block in parallel (`ForEach-Object -Parallel`). This scope allows the script block to access variables defined in the *parent* scope without serialization, as the parallel job inherits the parent's environment.
*   **Serialization Limits (CLIXML):** When using `-ArgumentList`, complex objects (like large custom objects or nested arrays) can hit the CLIXML serialization depth limit, causing the transfer to fail or truncate data.
*   **Solution:** For complex objects, it is often better to pass the object's *data* (e.g., a list of IDs) via `-ArgumentList` and then retrieve the full object on the remote side, rather than trying to serialize the entire object.

**PS20** — **Desired State Configuration (DSC)**
*   **DSC:** A management framework that allows administrators to define the desired state of a system (e.g., "IIS must be installed," "Firewall port 80 must be open") and ensures that the system remains in that state, automatically remediating any drift.
*   **Configurations:** The blueprint that defines the desired state (e.g., a configuration file specifying the required services and settings).
*   **Resources:** The smallest unit of configuration. A resource is a module that knows how to manage a specific component (e.g., `Service`, `Registry`, `File`).
*   **Local Configuration Manager (LCM):** The engine on the target node that reads the configuration and uses the resources to enforce the desired state.
*   **DSC Difference (WinPS vs PS 7+):**
    *   **Windows PowerShell (v5):** DSC was tightly integrated into Windows Server and relied heavily on Windows-specific components.
    *   **PowerShell 7+:** DSC has been modernized and made cross-platform, allowing it to run on Linux and macOS, making it a true infrastructure-as-code tool.
*   **Modern Replacement:** While DSC is still used, modern Infrastructure-as-Code (IaC) tools like **Ansible**, **Terraform**, and **Chef** have largely superseded DSC for broader cloud and multi-platform configuration management due to their wider adoption and declarative nature.
