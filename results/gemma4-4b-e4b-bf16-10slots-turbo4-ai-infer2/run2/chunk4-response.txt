## Go (Go Questions)

**G1 — Easy: What is the difference between a slice and an array in Go? What happens when you append to a slice that has reached its capacity?**
A slice is a dynamically sized, flexible view into an underlying array. An array is a fixed-size, contiguous block of memory defined at compile time. When you append to a slice that has reached its capacity, Go automatically allocates a new, larger underlying array (usually doubling the capacity), copies the existing elements over, and updates the slice header to point to the new memory location.

**G2 — Easy: Explain the difference between `var x int` and `x := 0`. When can you NOT use `:=`?**
`var x int` is a declaration using the `var` keyword, which initializes `x` to its zero value (0 for an integer). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` if the variable is already declared in the current scope, as `:=` implies a new declaration.

**G3 — Medium: What is a goroutine, and how does it differ from an OS thread? What is the role of the Go scheduler (GMP model)?**
A goroutine is a lightweight, independently executing function managed by the Go runtime. Unlike an OS thread, which requires significant kernel resources, goroutines are multiplexed onto a smaller number of OS threads. The Go scheduler (GMP model) manages this: G (Goroutine) runs on M (Machine/OS Thread), which is managed by P (Processor/Context). The scheduler maps Gs onto Ms, allowing thousands of goroutines to run efficiently on a few OS threads.

**G4 — Medium: Explain how channels work in Go. What is the difference between a buffered and unbuffered channel? What happens when you send to a full buffered channel?**
Channels are typed conduits through which goroutines communicate and synchronize. An **unbuffered channel** requires both the sender and receiver to be ready simultaneously (a synchronous rendezvous). A **buffered channel** allows a specified number of values to be stored before the sender blocks. When sending to a full buffered channel, the sender goroutine blocks until a receiver reads a value, freeing up space.

**G5 — Medium: What is the context package used for? Write a minimal example of using context.WithTimeout to cancel a long-running HTTP request.**
The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. It is crucial for managing the lifecycle of concurrent operations.
*Example:*
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // Always call cancel to release resources
req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
client := &http.Client{}
resp, err := client.Do(req)
// If the request times out, err will be context.DeadlineExceeded
```

**G6 — Medium: Explain Go's interface satisfaction model. How does it differ from Java/C# interfaces? What is the empty interface interface{} (or any) and why is it both powerful and dangerous?**
Go uses an implicit satisfaction model: a type satisfies an interface if it implements all the methods defined by that interface. Unlike Java/C# where you must explicitly `implements` an interface, Go requires no declaration. The empty interface `interface{}` (or `any`) can hold a value of any type, making it powerful for generic data handling, but dangerous because the compiler loses type information, requiring type assertions or type switches at runtime.

**G8 — Hard: What is the difference between sync.Mutex and sync.RWMutex? When would you use sync.Map vs a regular map with a mutex? What are the performance trade-offs?**
`sync.Mutex` provides exclusive locking (only one goroutine can hold the lock at a time). `sync.RWMutex` allows multiple readers to hold the lock simultaneously, but requires exclusive access for writers. Use `RWMutex` when reads vastly outnumber writes.
`sync.Map` is optimized for scenarios where keys are written once and read many times, or when concurrent access is expected across many goroutines. A regular map with a mutex is simpler and often faster for small maps or when contention is low. `sync.Map` has higher overhead but handles concurrent access without explicit locking logic, making it suitable for highly concurrent, large-scale data structures.

**G9 — Hard: Explain how Go modules work. What is the difference between go.mod and go.sum? What does go mod tidy do, and what is the Minimum Version Selection (MVS) algorithm?**
Go modules manage dependencies. `go.mod` lists the required modules and their specific versions. `go.sum` contains cryptographic checksums for the dependencies listed in `go.mod`, ensuring that the downloaded code has not been tampered with. `go mod tidy` cleans up the module file by removing unused dependencies and adding any missing ones required by the source code. MVS is an algorithm that selects the highest version of a dependency that satisfies all version constraints defined in the project.

**G10 — Medium: What is a defer statement? In what order do multiple defers execute? What is a common gotcha with defer in a loop?**
`defer` schedules a function call to be executed immediately before the surrounding function returns. Multiple defers execute in LIFO (Last-In, First-Out) order. The common gotcha in a loop is capturing the loop variable. If you defer a function that references the loop variable, the function will execute *after* the loop finishes, and the variable will hold its final value, not the value it had during each iteration. The fix is to pass the loop variable as a parameter to a new function or use a local copy.

**G11 — Easy: What is a pointer in Go? What is the zero value of a pointer? How do you create a pointer to a struct literal?**
A pointer is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`. To create a pointer to a struct literal, you first define the struct, then use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12 — Easy: Explain Go's init() function. When does it run? Can a package have multiple init() functions, and if so, in what order do they execute?**
The `init()` function is a special function that runs automatically before the `main` function (or before any other code in the package) is executed. It is used for package-level setup. A package can have multiple `init()` functions, and they execute in the order they appear in the source files, starting from the first package initialization.

**G13 — Easy: What is the difference between make and new in Go? What types does each work with?**
`make` is used to initialize built-in reference types (slices, maps, and channels). It allocates and initializes the underlying data structure. `new` is used to allocate memory for a value of a specific type and returns a pointer to the zero value of that type. `new` works with any type, while `make` is restricted to composite types.

**G14 — Easy: How does error handling work in Go? What is the error interface, and what is the idiomatic pattern for checking errors? How do errors.Is and errors.As differ from ==?**
Error handling is done via return values, typically the last return value being an `error` interface. The idiomatic pattern is `if err != nil { return err }`. `errors.Is` checks if an error matches a specific sentinel error value (e.g., `io.EOF`). `errors.As` checks if an error matches a specific type, allowing you to extract structured error information. Neither is a simple `==` comparison because errors can wrap other errors.

**G15 — Easy: What are Go's built-in composite types (map, slice, channel, struct)? What is the zero value of each?**
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil`.
*   **Slice:** `[]Type`. Zero value: `nil` (a nil slice).
*   **Channel:** `chan Type`. Zero value: `nil`.
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.

**G16 — Medium: What is a race condition in Go? How does the -race flag work? Give an example of a data race and show how to fix it with sync.Mutex or a channel.**
A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, leading to unpredictable results. The `-race` flag instruments the Go runtime to detect these data races during execution.
*Fix Example:*
```go
var data int
var mu sync.Mutex
go func() {
    for i := 0; i < 100; i++ {
        mu.Lock()
        data++ // Protected write
        mu.Unlock()
    }
}()
```

**G17 — Medium: Explain Go's select statement. How does it differ from a switch? What happens when multiple cases are ready? How do you implement a timeout with select?**
`select` is used to wait on multiple communication operations (channels). It differs from `switch` because `select` is specifically designed for concurrency and blocking on I/O operations. When multiple cases are ready, `select` chooses one of them pseudo-randomly. A timeout is implemented by using `select` alongside a `time.After` channel:
```go
select {
case <-ch:
    // Channel received data
case <-time.After(timeout):
    // Timeout occurred
}
```

**G18 — Hard: What is escape analysis in Go? How does the compiler decide whether to allocate on the stack or the heap? How can you inspect escape analysis decisions, and why does it matter for performance?**
Escape analysis is a compiler optimization that determines whether a variable's memory should be allocated on the stack (fast, local memory) or the heap (slower, garbage-collected memory). The compiler decides based on whether the variable's lifetime extends beyond the function call scope. If a variable is returned or stored in a global/pointer, it usually escapes to the heap. You can inspect this using the `-gcflags="-m"` flag. It matters for performance because heap allocation and garbage collection introduce significant overhead.

**G19 — Hard: Explain Go's reflection package (reflect). What is reflect.Type vs reflect.Value? What are the performance costs, and when is reflection justified vs code generation?**
The `reflect` package allows inspecting and manipulating types and values at runtime. `reflect.Type` describes the structure of a type (e.g., its fields, methods), while `reflect.Value` represents a specific instance of that type. Reflection incurs significant runtime overhead because the compiler cannot optimize the code path. It is justified only when dynamic behavior is absolutely necessary (e.g., serialization libraries, ORMs), but code generation is always preferred for performance.

**G20 — Hard: What is the go:embed directive? How does it work for single files, directories, and file systems? What are the limitations, and how does it interact with io/fs.FS?**
The `go:embed` directive allows embedding external files or directories directly into the compiled binary as byte slices. It works by specifying the path and the target variable type (usually `string` or `[]byte`). It can embed single files, entire directories, or complex file systems. The limitation is that the embedded content is static and cannot be modified at runtime. It interacts with `io/fs.FS` by allowing the embedded content to be treated as a virtual file system, enabling standard file I/O operations on the embedded data.

## Rust (Rust Questions)

**R1 — Easy: What is ownership in Rust? Explain the three ownership rules.**
Ownership is Rust's core memory management concept. It dictates that every value in Rust has a single variable that is its *owner*.
The three rules are:
1.  Every value has a single owner.
2.  There can only be one owner at a time.
3.  When the owner goes out of scope, the value is automatically dropped (memory is freed).

**R2 — Easy: What is the difference between String and &str? When would you use each in function signatures?**
`String` is a heap-allocated, mutable, growable string type (owned data). `&str` is a string slice—a borrowed, immutable reference to a string stored elsewhere (usually in the binary or on the stack).
*Usage:* Use `String` when you need to build, modify, or own the string data. Use `&str` in function signatures when you only need to read the string data, as it avoids unnecessary memory allocation and copying.

**R3 — Medium: Explain borrowing and the borrow checker. What are the rules for shared (&T) and mutable (&mut T) references?**
Borrowing allows you to use a value without taking ownership of it. The borrow checker enforces Rust's ownership rules at compile time.
*Rules:*
1.  You can have any number of immutable references (`&T`) to a piece of data simultaneously (shared access).
2.  You can have only one mutable reference (`&mut T`) to a piece of data at any given time (exclusive access).
3.  You cannot have a mutable reference while any immutable references exist, and vice versa.

**R4 — Medium: What is a Result<T, E> and an Option<T>? How does the ? operator work? Write a function that reads a file and returns its contents or an error.**
`Option<T>` is an enum representing the presence or absence of a value (`Some(T)` or `None`). `Result<T, E>` is an enum representing success or failure (`Ok(T)` or `Err(E)`).
The `?` operator is syntactic sugar for propagating errors. If the expression it is applied to returns an `Err`, the function immediately returns that error; otherwise, it unwraps the `Ok` value and continues execution.
*Example:*
```rust
use std::fs::File;
use std::io::Read;
fn read_file(path: &str) -> Result<String, std::io::Error> {
    let mut file = File::open(path)?; // Propagates error if file fails to open
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates error if read fails
    Ok(contents)
}
```

**R5 — Medium: Explain the difference between Box<T>, Rc<T>, and Arc<T>. When would you use each?**
These are smart pointers used for heap allocation and managing shared ownership:
*   **`Box<T>`:** Allocates data on the heap. Used when you need to put a type behind a pointer (e.g., recursive data structures) or when you want to hide the concrete type (trait objects). It has unique ownership.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data on the heap. It uses atomic reference counting. Used for single-threaded shared ownership.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>`, but uses atomic operations for reference counting, making it safe to share across multiple threads. Used for multi-threaded shared ownership.

**R6 — Medium: What are traits in Rust? How do they compare to Go interfaces? What is a trait object (dyn Trait) vs a generic with a trait bound (T: Trait)?**
Traits define shared behavior (like interfaces). They are similar to Go interfaces, but traits are more powerful; they can define default implementations and are used for compile-time polymorphism.
*   **Generic with Trait Bound (`T: Trait`):** Achieves *static dispatch*. The compiler knows the exact type at compile time and generates specialized code for that type, resulting in zero runtime overhead (zero-cost abstraction).
*   **Trait Object (`dyn Trait`):** Achieves *dynamic dispatch*. The type is erased, and the program uses a vtable (virtual method table) lookup at runtime to call the correct method. This incurs a small runtime cost but allows for heterogeneous collections.

**R7 — Hard: Explain lifetimes in Rust. Why does the following fail to compile, and how do you fix it?**
Lifetimes (`'a`) are a mechanism the borrow checker uses to ensure that references remain valid for as long as they are used. The code fails because the returned reference (`&str`) refers to data (`x` or `y`) that is local to the `longest` function. Once `longest` returns, that local data is dropped, leaving the returned reference dangling (a use-after-free bug).
*Fix:* The function must return a reference that lives as long as the *caller* needs it, meaning the input references must be the lifetime anchor:

**R8 — Hard: What is Send and Sync in Rust? Why can't you send an Rc<T> across threads? What makes Arc<T> safe for concurrent use?**
`Send` and `Sync` are marker traits that indicate if a type can be safely moved (`Send`) or shared (`Sync`) across thread boundaries.
`Rc<T>` is not `Send` because its internal reference counter is not atomic; if multiple threads tried to increment/decrement the counter simultaneously, it would lead to a data race.
`Arc<T>` is safe because it uses atomic operations (like `std::sync::atomic`) to manage the reference count, ensuring thread-safe modification of the counter.

**R9 — Hard: Explain how Rust's async/await works under the hood. What is a Future? What is the role of the executor (e.g., Tokio)? How does this differ from Go's goroutines?**
Rust's `async/await` is built on the `Future` trait. A `Future` is a trait representing a value that may not be available yet. When you `await` a future, you are essentially registering a callback (a "poll") that the executor will run when the future is ready.
The **executor** (like Tokio) is the runtime environment that drives the futures. It polls the futures, checking their state, and when a future is ready, it executes the next step of the async function.
*Difference from Go:* Go uses green threads (goroutines) managed by a runtime scheduler that handles blocking I/O implicitly. Rust's async is cooperative multitasking; the programmer must explicitly define the `Future` and the executor must actively poll it.

**R10 — Medium: What is unsafe in Rust? Give 3 things you can do in an unsafe block that you can't do in safe Rust. When is unsafe justified?**
`unsafe` blocks bypass the borrow checker and allow direct manipulation of memory, pointers, and raw types.
*Things you can do:* Dereference raw pointers, call `unsafe` functions, and implement `unsafe` traits.
*Justification:* `unsafe` is justified only when implementing low-level systems programming, FFI (Foreign Function Interface) calls to C libraries, or when optimizing performance by manually managing memory (e.g., implementing custom data structures).

**R11 — Easy: What is pattern matching in Rust? How does match differ from if let? What does the compiler enforce about exhaustiveness?**
Pattern matching (`match`) allows you to compare a value against a series of patterns and execute code based on which pattern matches. `if let` is syntactic sugar used to conditionally destructure a value (e.g., `if let Some(x) = option { ... }`).
The compiler enforces **exhaustiveness** in `match` statements, meaning you must cover every possible variant of the enum being matched. If you miss a variant, the compiler will issue a warning or error, preventing runtime crashes.

**R12 — Easy: What is the difference between Vec<T> and an array [T; N]? How does Vec manage memory when elements are pushed beyond its current capacity?**
An array `[T; N]` has a fixed size `N` defined at compile time and is stored contiguously on the stack (if small enough). `Vec<T>` is a heap-allocated, dynamically sized vector.
When `Vec` is pushed beyond its current capacity, it performs a reallocation: it allocates a new, larger block of memory (often doubling the capacity), copies all existing elements from the old memory to the new memory, and then drops the old memory block.

**R13 — Easy: What are enums in Rust, and how do they differ from enums in C or Java? What is the Option<T> enum, and why does Rust not have null?**
Rust enums are powerful because they can hold associated data (variants). Unlike C/Java enums (which are often just integer constants), Rust enums are algebraic data types.
`Option<T>` is an enum that explicitly models the possibility of absence (`None`) or presence (`Some(T)`). Rust avoids `null` because `Option<T>` forces the programmer to handle the absence case explicitly at compile time, eliminating the possibility of a runtime `NullPointerException`.

**R14 — Easy: Explain the impl block. What is the difference between methods that take &self, &mut self, and self? What are associated functions (e.g., String::new())?**
The `impl` block is where methods and associated functions for a struct or enum are defined.
*   `&self`: Takes an immutable reference. Used for methods that only read the data.
*   `&mut self`: Takes a mutable reference. Used for methods that modify the data.
*   `self`: Takes ownership. Used when the method consumes the instance (e.g., `String::into_bytes()`).
Associated functions (like `String::new()`) are functions defined within the `impl` block but do not take `self` as a parameter; they are called directly on the type name.

**R15 — Easy: What is the derive macro? Give examples of commonly derived traits (Debug, Clone, PartialEq, Serialize). When can you NOT derive a trait?**
A derive macro is a procedural macro that automatically implements standard traits for a struct or enum.
*Examples:* `#[derive(Debug)]` (allows printing with `{:#?}`), `#[derive(Clone)]` (allows deep copying), `#[derive(PartialEq)]` (allows comparison using `==`), `#[derive(Serialize)]` (used by serialization libraries).
You cannot derive a trait if the type does not meet the requirements of that trait (e.g., you cannot derive `PartialEq` if the type contains a field that is not `PartialEq`).

**R16 — Medium: What is Cow<'a, T> (clone on write)? When is it useful? Give an example where it avoids unnecessary allocations compared to always cloning.**
`Cow<'a, T>` (Clone on Write) is a smart type that can hold either an owned value (`T`) or a borrowed reference (`&T`). It allows a function to accept either a reference or an owned value, and only performs a deep copy (cloning) if the value needs to be modified.
*Usefulness:* It is useful in functions that might receive data either as a reference (read-only) or as an owned value (which might need modification).
*Example:* If a function receives a `Cow<str>`, and it only needs to read the string, it uses the cheap reference. If it needs to modify it, it converts the `Cow` into an owned `String` only when necessary, avoiding an allocation if the data remains unchanged.

**R17 — Medium: Explain Rust's module system. What is the difference between mod, use, and pub? How does the file system map to modules, and what changed between Rust 2015 and 2018 editions?**
The module system organizes code into hierarchical units.
*   `mod`: Declares a module, which can contain other items or sub-modules.
*   `use`: Brings items from another module into the current scope, allowing them to be referenced directly.
*   `pub`: Makes items (functions, structs, etc.) visible outside the current module.
The file system maps to modules: a file named `foo.rs` typically corresponds to a module named `foo`.
*Change (2018):* The 2018 edition introduced the concept of **crates** (packages) and standardized the use of `Cargo.toml` for dependency management, making the build system much more robust and standardized.

**R18 — Hard: What is the Pin<T> type and why is it needed? How does it relate to self-referential structs and async/await? What is Unpin?**
`Pin<T>` is a wrapper that guarantees that the data inside it will not be moved in memory. This is crucial because if a struct containing a reference to itself were moved, the reference would become dangling.
*Self-referential structs:* These structs contain a pointer to some part of themselves. If the struct moves, the pointer breaks. `Pin` prevents this movement.
*Async/await:* Futures often need to store state that references the future itself. `Pin` ensures that the future remains fixed in memory while it awaits I/O, allowing the executor to safely poll it later.
`Unpin` is a marker trait indicating that a type is safe to move even if it is wrapped in `Pin`.

**R19 — Hard: Explain Rust's macro system. What is the difference between declarative macros (macro_rules!) and procedural macros (derive, attribute, function-like)? What are hygiene rules?**
Macros allow metaprogramming—writing code that writes code.
*   **Declarative Macros (`macro_rules!`):** Use pattern matching to substitute tokens. They are simple and compile-time.
*   **Procedural Macros (derive, attribute, function-like):** These are complex functions that take Rust code as input (Abstract Syntax Tree - AST) and output new Rust code. They are far more powerful.
*   **Hygiene Rules:** These rules prevent macro expansion from accidentally capturing or interfering with identifiers defined elsewhere in the code. They ensure that the macro operates only on the tokens it was intended to process, preventing name collisions.

**R20 — Hard: What are zero-cost abstractions in Rust? Explain how iterators, generics (monomorphization), and trait static dispatch achieve performance comparable to hand-written C while providing high-level ergonomics.**
Zero-cost abstractions mean that high-level language features (like generics or iterators) do not impose a runtime performance penalty compared to writing the equivalent low-level code by hand.
*How it works:*
1.  **Generics (Monomorphization):** When the compiler sees a generic function (e.g., `fn map<T>(list: Vec<T>) -> Vec<T>`), it doesn't generate one generic version. Instead, it generates a specialized, concrete version of the function for *every* type `T` used. This eliminates runtime overhead associated with dynamic dispatch.
2.  **Trait Static Dispatch:** When a generic function uses a trait bound (`T: Trait`), the compiler resolves the specific implementation of `Trait` at compile time, effectively replacing the trait call with a direct function call, achieving the same performance as a C function call.
3.  **Iterators:** Rust's iterator trait allows chaining operations (like `map`, `filter`) without allocating intermediate collections. The compiler optimizes this chain into a single, efficient loop, achieving C-like performance while providing functional programming ergonomics.
