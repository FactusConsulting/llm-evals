## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:**
The pods are failing because of a conflict between the new base image's default user and the cluster's new security enforcement policy.
1.  **SecurityContext Interaction:** The pods specify `securityContext.runAsNonRoot: true` but omit `runAsUser`. When `runAsUser` is not explicitly set, the container runtime defaults to the user specified by the image's `USER` directive (or the default user if none is specified).
2.  **Image Change:** The new base image (`cgr.dev/chainguard/static:latest`) defaults its `USER` to `root`.
3.  **Failure Mechanism:** The combination of `runAsNonRoot: true` and the image defaulting to `root` creates a conflict. The Kubernetes runtime attempts to run the container as a non-root user (due to the security context), but the image is configured to run as root. This conflict often leads to the container failing to start or immediately exiting, resulting in `CrashLoopBackOff`.
4.  **Policy Change:** The shift from Baseline to Restricted Pod Security Standard (PSS) enforcement is critical. Baseline PSS allows certain deviations (like running as root if explicitly allowed by the image/runtime), but Restricted PSS is much stricter, enforcing non-root execution and dropping capabilities. The upgrade likely tightened the enforcement mechanism, making the implicit root execution (due to the image default) explicitly forbidden under the new Restricted standard.

**SC1-B:**
```bash
kubectl get pods --all-namespaces -o json | jq -r '.items[] | select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, podName: .metadata.name, securityContext: .spec.containers[0].securityContext}'
```

**SC1-C:**
**Immediate Outage Fix:**
1.  **Manifest Change:** Update the deployment manifest to explicitly set `securityContext.runAsUser` to a non-root UID (e.g., 1000) and ensure `runAsNonRoot: true` is maintained.
2.  **Image Fix:** Rebuild the Dockerfile to explicitly set `USER <non-root-user>` *before* the final image layer, overriding the base image's default.
**Recurrence Prevention:**
1.  **CI Pipeline Gate:** Implement a static analysis tool (e.g., Hadolint, Trivy) in the CI pipeline that checks the Dockerfile for the presence of a `USER` instruction and verifies that the specified user ID is non-root.
2.  **Policy Enforcement:** Use a Kubernetes Admission Controller (e.g., Kyverno) to enforce that all deployed pods must specify `securityContext.runAsUser` and `runAsNonRoot: true`.
**Zero Downtime Rollout:**
Use a standard rolling update strategy (`kubectl rollout restart deployment/<name>` or updating the image tag in the deployment manifest). Kubernetes will gradually replace old pods with new ones, ensuring the minimum required number of replicas remains available throughout the transition.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:**
**Stale Data Issue:** The stale data is a direct consequence of asynchronous replication. When the primary fails, the replica is promoted, but any Write-Ahead Log (WAL) records that were generated on the old primary and had not yet been successfully shipped and applied to the replica before the failure are lost.
**Replication Lag Implication:** Cross-region replication inherently introduces latency. If the replication is asynchronous, the replica is always slightly behind the primary. The promotion process assumes the replica is up-to-date, but if the lag was significant, data loss occurs.
**WAL Shipping:** PostgreSQL uses streaming replication, where the primary continuously streams WAL segments to the standby. Across regions, this involves high-latency network transfers.
**Data Loss Scenarios:** Data loss occurs if the primary fails before the WAL segment is flushed and acknowledged by the replica (asynchronous mode).
**Quantifying Data Loss:** Check the `pg_stat_replication` view on the new primary (the promoted replica) and examine the `pg_last_wal_receive_lsn` and `pg_last_wal_replay_lsn` to determine the exact point in the WAL stream where the replica stopped receiving/applying data relative to the moment of failure.

**SC2-B:**
The goal is to transition the promoted replica into the stateful infrastructure managed by Terraform without destroying the existing resources.

1.  **Importing the Replica:** The promoted replica is now a standalone instance. We must import it into the Terraform state file.
    ```bash
    # Assuming the promoted instance ARN is known
    terraform import aws_db_instance.primary_instance arn:aws:rds:eu-west-1:ACCOUNT_ID:db:NEW_PRIMARY_ARN
    ```
2.  **Updating Dependencies:** After the import, the Terraform configuration must be updated to reference the new ARN.
3.  **Detaching the Old Instance:** Once the new instance is stable and all dependent resources (Security Groups, Route53, etc.) are updated to point to the new ARN, the old instance can be safely destroyed.
    ```bash
    terraform destroy -target=aws_db_instance.old_primary_instance
    ```
    *Crucially, all dependent resources must be updated in the HCL *before* running the destroy command.*

**SC2-C:**
**Architecture Design:**
*   **Connection Management:** Use **RDS Proxy**. It handles connection pooling, automatic failover detection, and connection routing transparently, eliminating the need for manual PgBouncer management during failover.
*   **DNS Failover:** Use **Route53 Health Checks** configured against the application endpoints in both regions. Implement weighted or failover routing policies (e.g., failover to EU if US health check fails).
*   **Application Retry Logic:** Implement exponential backoff and jitter in the application code to handle transient network issues during failover.
*   **RPO < 1 second:** This requires **Synchronous Replication**. The primary must wait for confirmation from the replica before committing a transaction. This is achievable but increases write latency.
**Aurora Global Database vs. RDS:**
**Recommendation: Aurora Global Database.**
*   **Why:** Standard RDS cross-region replication is typically asynchronous, making RPO guarantees difficult. Aurora Global Database is specifically designed for low-latency, cross-region failover with near-zero RPO (often measured in seconds) because it uses a dedicated, highly optimized replication mechanism. It simplifies the failover process significantly compared to managing Patroni/streaming replication manually.

1.  **Containment:** Isolate the affected pods. Do *not* kill them immediately, as this destroys volatile memory/process state. Use `kubectl cordon` on the node hosting the compromised pods to prevent new scheduling.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
| Blocker | Problem in K8s | Specific Solution |
| :--- | :--- | :--- |
| **1. Local Session State** | Kubernetes is ephemeral. Local memory sessions are lost upon pod restart/migration, breaking user experience. | Externalize state: Migrate sessions to a distributed cache (e.g., Redis Cluster or Memcached) accessible by all pods. |
| **2. Local NFS Mount** | Kubernetes prefers cloud-native storage. Local mounts are non-portable and non-scalable. | Use a CSI driver (e.g., NFS CSI) to provision Persistent Volumes (PVs) and Persistent Volume Claims (PVCs) that mount the NFS share dynamically. |
| **3. Sticky Sessions (F5)** | Kubernetes load balancing is typically stateless and round-robin. Sticky sessions require complex configuration (e.g., session affinity). | Refactor the application to be truly stateless. If not possible, use a service mesh (Istio) or Ingress controller with session affinity based on a cookie. |
| **4. On-Prem Oracle DB** | Requires complex networking, high latency, and potential licensing issues when moving to a cloud-native architecture. | Use a dedicated database service (e.g., AWS RDS for Oracle) or establish a secure, high-throughput VPN/Direct Connect link to the existing on-prem DB. |
| **5. IBM MQ Integration** | MQ is a proprietary, tightly coupled messaging system. Kubernetes prefers cloud-native message queues (Kafka, RabbitMQ). | Introduce a message broker layer (e.g., Kafka) as an abstraction layer. The monolith communicates with the MQ via a dedicated adapter service that translates MQ messages to Kafka topics. |

**SC4-B:**

**Why ReadWriteMany (RWX) is necessary:** The application writes uploaded files to the NFS mount (`/data/uploads`). **SC4-C:**
**Phased Migration Plan (Strangler Fig Pattern):**

**Phase 1: Data and State Abstraction (Shadowing)**
*   **What Moves:** Session state and file uploads.
*   **Action:** Implement the externalized state (Redis/S3) and migrate the file upload logic to write to the new PV/S3 endpoint. The monolith still runs on bare metal but now uses the new storage layer.
*   **Cutover:** None. The legacy system continues to run, but its dependencies are being modernized.
*   **Rollback:** Simple: revert the application code to use the local NFS mount/in-memory session.
*   **Go/No-Go:** Successful read/write tests against the new storage layer; latency remains within acceptable limits.

**Phase 2: Traffic Shadowing and Integration (Strangling)**
*   **What Moves:** API endpoints and core business logic.
*   **Action:** Deploy the monolith as a Kubernetes service. Use the F5 BIG-IP to implement **traffic mirroring/shadowing**. A small percentage (e.g., 1%) of live production traffic is sent to the new K8s ingress, but the response is ignored. The K8s service processes the request and logs the result.
*   **Cutover:** Gradually increase traffic split (e.g., 5%, 10%, 25%).
*   **MQ Handling:** Introduce a Kafka bridge. The legacy MQ adapter service reads from MQ and publishes to Kafka. The new K8s monolith consumes from Kafka.
*   **Rollback:** Immediately revert the traffic split percentage back to 0% on the F5.
*   **Go/No-Go:** Error rates and latency of the K8s service match the legacy service; no critical business errors are observed during shadowing.

**Phase 3: Full Cutover and Decommissioning**
*   **What Moves:** All traffic and the entire application.
*   **Action:** Once confidence is high, shift 100% of traffic from the F5 to the Kubernetes Ingress. The legacy bare-metal servers are kept running in a passive state for a grace period.
*   **Rollback:** If critical failure occurs, immediately flip the F5 routing back to the legacy servers.
*   **Go/No-Go:** Sustained performance (p99 latency) meets or exceeds the legacy baseline for 72 hours.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A:**
**Systematic Debugging Approach:**
1.  **Istio/Envoy Metrics:** Examine Istio metrics (via Prometheus) for the `checkout-service` to `inventory-service` path. Look specifically at:
    *   `istio_request_duration_seconds_bucket`: Check the P99 latency distribution.
    *   `istio_request_duration_seconds_sum`: Compare the total latency added by the sidecar proxy vs. the upstream service.
    *   **Envoy Metrics:** Look at `envoy_cluster_upstream_rq_pending_requests` and `envoy_cluster_upstream_rq_active_requests`. High pending requests indicate the sidecar is waiting for the upstream service to accept connections, suggesting upstream resource exhaustion (e.g., connection pool exhaustion).
2.  **Kubernetes/Application Logs:** Check `checkout-service` logs for connection timeouts or retry attempts. Check `inventory-service` logs for database connection errors or long-running query warnings during the spike window.
3.  **Distributed Tracing (Jaeger/Zipkin):** Trace a request that experiences the spike. The trace will visually show where the time is spent. If the time is spent *inside* the `inventory-service` span, the issue is application logic/DB. If the time is spent *between* the spans (in the sidecar/network), the issue is infrastructure/proxy.

**SC5-B:**
**SQL Diagnostic Query (PostgreSQL):**
```sql
SELECT
    a.pid AS blocking_pid,
    a.usename AS blocking_user,
    a.query AS blocking_query,
    b.pid AS waiting_pid,
    b.usename AS waiting_user,
    b.query AS waiting_query,
    pg_blocking_pids(a.pid) AS blocked_pids
FROM
    pg_stat_activity a
JOIN
    pg_stat_activity b ON b.wait_event_type = 'Lock'
WHERE
    a.wait_event_type = 'Lock'
    AND a.pid IN (SELECT unnest(pg_blocking_pids(pid)) FROM pg_stat_activity WHERE pid = a.pid);
```

**SC5-C:**
**Architectural Solution:**
1.  **CQRS (Command Query Responsibility Segregation):** Separate the read path (queries) from the write path (reconciliation/updates). The reconciliation job should run against a dedicated, highly optimized read replica, preventing it from locking the primary database used by the live checkout service.
2.  **Bulkhead Isolation:** Implement connection pool isolation. Use separate connection pools for the high-volume, low-latency read queries (checkout) and the long-running, batch reconciliation queries. This prevents the reconciliation job from exhausting the pool needed by the serving pods.
3.  **CronJob Scheduling:** Reschedule the reconciliation job to run during off-peak hours (e.g., 03:00 UTC) or use a staggered, throttled execution pattern.
4.  **Resource Governance:**
    *   **PodDisruptionBudgets (PDB):** Use PDBs on the serving pods to ensure that during voluntary disruptions (like node maintenance), a minimum number of checkout pods remain running, preventing service degradation.
    *   **Resource Quotas:** Apply resource quotas to the namespace containing the serving pods and the CronJob. This limits the total CPU/Memory the CronJob can consume, preventing it from starving the critical serving pods.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:**
**Identity and Access Layer Design:**
1.  **SPIFFE/SPIRE (Workload Identity):** SPIFFE (Secure Production Identity Framework for Everyone) provides a standard way to define workload identities. SPIRE acts as the agent that verifies the workload (e.g., Kubernetes service account, AWS IAM role) and issues a cryptographically verifiable X.509 certificate (SVID) containing the SPIFFE ID (e.g., `spiffe://mycorp.com/service/checkout`).
2.  **Federation:**
    *   **AWS:** SPIRE agents are configured to trust AWS IAM roles. When a pod assumes an IAM role, the agent issues a certificate tied to that role.
    *   **Azure:** Use Azure Managed Identities, which are mapped to SPIRE identities.
    *   **On-Prem:** Use PKI infrastructure to verify host identity, which is then mapped to a SPIRE identity.
3.  **Cross-Environment Authentication:** The key is that the identity (the SPIFFE ID) is portable. A service in AWS presents its SVID. The service on-prem (or in Azure) uses a trust bundle (the root CA of the SPIFFE system) to validate the certificate. The service then uses the SPIFFE ID to authorize the request via a centralized Policy Enforcement Point (PEP), such as a service mesh (Istio/Linkerd) or a centralized authorization service.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:**
**Drift Sources and Dangers:**
1.  **Manual `tofu apply`:** Bypasses the centralized, auditable pipeline. This is dangerous because the state file is not updated correctly, leading to configuration drift and potential resource conflicts.
2.  **Diverged Helm Values:** Changes made directly to values files without Git tracking means the source of truth (Git) no longer reflects the deployed state. This leads to unpredictable behavior and difficult debugging.
3.  **`kubectl edit`:** This is the most dangerous. It bypasses *all* infrastructure-as-code (IaC) and CI/CD controls. The state file (if managed by Terraform) will not reflect the change, leading to the next `tofu plan` showing a massive, unexpected difference, or worse, Terraform attempting to revert the manual change.
**State Locking Failure:**
If two engineers run `tofu apply` simultaneously without state locking, they are operating on the same state file. The first engineer might read the state, and the second engineer might read the *same* state. Both engineers then apply changes based on the old state, leading to a **race condition**. The second engineer's changes will overwrite or conflict with the first engineer's changes, resulting in resource corruption or failure.

**SC7-B:**

**SC7-C:**
**Drift Detection and Reconciliation:**
1.  **Scheduled Plan:** Schedule a nightly or weekly CI job that runs `tofu plan` against the production state. The output of this plan is compared against the expected state (e.g., stored in a Git repository or a dedicated drift detection service). If the plan shows changes, an alert is triggered (e.g., PagerDuty/Slack).
2.  **Admission Webhook/OPA Gatekeeper:** Deploy a policy that intercepts API requests. The policy checks the resource type and name. If the resource is critical (e.g., `ConfigMap` in the production namespace), the webhook rejects the request if the user is not the designated CI service account.
3.  **Helm/Kustomize Structure:** Use **Helmfile** or **Kustomize** to define a common base configuration (the shared values/templates) and then apply environment-specific overlays (e.g., `prod-values.yaml` overrides `base-values.yaml`). This ensures the core structure is version-controlled and only environment-specific parameters change.
**RBAC Changes:**
*   **Kubernetes:** The CI service account must be granted `cluster-admin` or specific `get/list/watch/update/patch` permissions *only* on the resources it manages. All human users should have read-only access to production resources.
*   **AWS:** The CI service account's IAM role must be the *only* role granted permissions to run `tofu apply` or modify the state backend (S3/DynamoDB).

## SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:**
**Diagnosis:**
1.  **Prometheus OOM-killed:** **Root Cause: High Cardinality.** Prometheus stores metrics as time series, and each unique combination of metric name + label values is a unique series. 8.2 million active series is massive. High cardinality leads to excessive memory usage for storing label sets and metric data, causing OOM kills.

**SC8-C:**
**Redesigned Observability Architecture:**
1.  **Metrics (Prometheus Replacement):** Replace Prometheus with a **Mimir** or **VictoriaMetrics** cluster. These systems are designed for massive scale, offering horizontal scalability, better cardinality handling, and native support for long-term storage and global query views.

from rest_framework import permissions

class IsOwnerOrReadOnly(permissions.BasePermission):
    """
    Custom permission to only allow owners of an object to edit it.
    """
    def has_object_permission(self, request, view, obj):
        # Read permissions are allowed to any request
        if request.method in permissions.SAFE_METHODS:
            return True
        # Write permissions are only allowed to the owner of the snippet.
        return obj.owner == request.user

1.  **Dual Endpoint Strategy:** Run both the old API key endpoint and the new OAuth2 endpoint simultaneously.
2.  **Phased Migration:** For existing consumers, provide a migration tool or documentation. Gradually deprecate the API key endpoint while monitoring usage.
3.  **Gateway Transformation:** Configure the API Gateway to accept both API keys (for legacy clients) and JWTs (for new clients), translating the API key into a temporary internal user identity before passing it to the backend.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
**Multi-Cluster Architecture Comparison:**

| Feature | Active-Passive (Velero) | Active-Active (Service Mesh) |
| :--- | :--- | :--- |
| **RPO/RTO Feasibility** | RPO: Minutes (depends on backup frequency). RTO: Hours (requires manual/automated restore). | RPO: Seconds (near real-time replication). RTO: Minutes (automatic failover). |
| **Latency Impact (12ms)** | Minimal impact on the primary site. | Minimal impact on replication traffic, but increases application latency slightly. |
| **200TB MinIO Replication** | Requires periodic, large-scale snapshot/restore. Slow. | Requires continuous, asynchronous replication (e.g., MinIO replication features). |
| **PostgreSQL/Redis/RabbitMQ** | Requires continuous streaming replication setup. | Requires multi-master or federated replication setup. |
| **Conclusion** | Meets RPO/RTO if RTO is automated, but complex for stateful components. | Best fit for RPO/RTO, but significantly more complex to configure and manage. |

**Replication Strategy:**
*   **PostgreSQL (Patroni):** Synchronous streaming replication (Chicago $\rightarrow$ Dallas). Patroni ensures the primary waits for confirmation from the standby before committing, guaranteeing zero data loss (RPO=0).
*   **Redis Sentinel:** Active-Passive replication with Sentinel monitoring. Sentinel automatically promotes the replica upon failure.
*   **RabbitMQ:** Use queue mirroring and federation across the two clusters. Queues are mirrored, ensuring messages are delivered to both sites.
*   **MinIO:** Utilize MinIO's built-in cross-site replication feature, which asynchronously replicates objects between the two storage buckets.

**SC10-C:**
**Automated Failover Orchestration Sequence:**

1.  **Failure Detection:**
    *   **Monitor:** A dedicated external monitoring system (e.g., Prometheus/Alertmanager) monitors the health of the Chicago primary (via Patroni's API endpoint and application health checks).
    *   **Trigger:** If the primary fails to respond to health checks for $N$ consecutive intervals (e.g., 5 minutes), the system declares the site down.
2.  **Patroni Promotion:** The monitoring system triggers the Patroni cluster (via etcd) to initiate failover. Patroni automatically promotes the Dallas standby to the new primary.
3.  **DNS Failover (GSLB):** The GSLB (Global Server Load Balancing) system detects the failure of the Chicago endpoint and automatically updates the DNS records to point all traffic to the Dallas primary endpoint.
4.  **Redis Sentinel Failover:** Sentinel detects the primary failure and promotes the Dallas replica.
5.  **RabbitMQ Federation:** The RabbitMQ federation mechanism automatically redirects queues and consumers to the Dallas cluster.
6.  **MinIO Catch-up:** The MinIO replication mechanism continues to run asynchronously. The Dallas cluster must ensure it has caught up on the last few minutes of object writes before accepting writes.
7.  **OpenTofu State Update:** A final, automated script runs to update the Terraform state file, reflecting that the Dallas cluster is now the authoritative primary infrastructure.
**Split-Brain Handling:**
*   **Mechanism:** Patroni uses etcd (or Consul) as the Distributed Configuration Store (DCS). Only one node can hold the leader lock in etcd. If the Chicago primary loses quorum with etcd, it automatically steps down, preventing two primaries from running simultaneously.
**Failing Back to Chicago:**
1.  **Recovery:** Once Chicago is stable, it is configured as a new standby replica of the Dallas primary.
2.  **Re-synchronization:** The Chicago cluster performs a full data synchronization (catch-up) from Dallas.
3.  **Planned Failover:** A planned, controlled failover is executed (Dallas $\rightarrow$ Chicago) using the same orchestration sequence, ensuring the new primary is Chicago.
