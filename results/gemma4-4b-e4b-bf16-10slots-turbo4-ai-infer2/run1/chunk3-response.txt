## OpenTofu / Terraform Answers

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` calculates the changes needed to reach the desired state defined in the configuration files and displays them (what will be created, modified, or destroyed) without making any actual changes to the infrastructure. `tofu apply` executes the plan, applying the calculated changes to the real infrastructure.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
The state file (`terraform.tfstate`) is a mapping that records the real-world resources managed by OpenTofu and links them to the configuration code. Remote state (e.g., S3, Azure Storage) is crucial because it provides a single source of truth, enables collaboration among team members, and, most importantly, allows for state locking to prevent concurrent modifications and corruption.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
*   **`count`**: Creates a specific number of identical instances (e.g., `count = 3`). It uses an index (0, 1, 2...) to differentiate instances.
*   **`for_each`**: Creates instances based on a set of unique keys (e.g., a map or a set). It uses the key itself to differentiate instances.
*   **Preference**: `for_each` is preferred when the instances need to be uniquely identified by a meaningful name or attribute (e.g., `web1`, `web2`) rather than just a numerical index, as it makes refactoring and dependency management cleaner.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?**
OpenTofu detects this drift during the `tofu plan` phase. It performs a refresh operation, querying the cloud provider API to compare the current real-world state against the state recorded in the state file. If a discrepancy is found, OpenTofu reports this as a planned change (drift) and will attempt to revert the resource back to the configuration defined in the code during `tofu apply`, unless the change is explicitly ignored.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
locals {
  vm_names = toset(["web1", "web2", "web3"])
}

resource "aws_instance" "web_vm" {
  for_each = local.vm_names

  ami           = "ami-0abcdef1234567890"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
*   **`output` values**: These are values explicitly defined and exposed by a module. They are the standard way to pass data *up* the module hierarchy.
*   **`terraform_remote_state` data source**: This is used to read the state file of *another* separate infrastructure deployment (often a different root module or workspace).
*   **Recommended Alternative**: The recommended alternative is to use **module outputs** and pass the required data as input variables to the consuming module.
*   **Why**: Relying on `terraform_remote_state` tightly couples the modules to the specific state file location and structure of the remote deployment, making the configuration brittle and harder to test. Passing outputs via variables maintains modular independence.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
The failure occurs because the `null_resource` with a `remote-exec` provisioner runs *after* the resource creation phase, but the output value is often only populated *after* the provisioner successfully completes. If dependent resources try to read this output immediately, it might be empty or null during the initial plan/apply phase.
**Fix:** Use an **implicit dependency** or explicitly use `depends_on` on the dependent resources, ensuring they only run after the `null_resource` (or the resource that generates the output) has successfully completed its provisioner. Alternatively, if the output is complex, ensure the provisioner is configured to write the output to a file that can be read by the dependent resource.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` allows you to take an existing, managed resource from a cloud provider and bring it under the management of your OpenTofu configuration.
**Limitations of CLI:** The CLI command is manual and requires the user to know the exact resource type and ID, and it only imports the resource; it does not automatically update the configuration code to match the imported resource's attributes.
**Improvement (Import Block):** The `import` block allows you to define the resource type and local configuration *within* the HCL code. OpenTofu then automatically runs the import, updates the state, and generates the necessary configuration code, making the process declarative and repeatable.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
*   **Variable (Input)**: A placeholder defined in the configuration that accepts external values (e.g., user input, environment variables, or values from a `.tfvars` file) to make the configuration dynamic.
*   **Output**: A value explicitly defined and exposed by a module or root configuration that allows other parts of the infrastructure (or users) to retrieve important information generated by the deployment (e.g., public IP addresses, DNS names).

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that enables OpenTofu to interact with external APIs (e.g., AWS, Azure, Kubernetes). It contains the logic and API calls necessary to manage resources in that specific platform.
If you run `tofu plan` without `tofu init`, OpenTofu will fail because it has not downloaded or initialized the necessary provider plugins and configuration dependencies required to communicate with the target cloud API.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
The `.terraform.lock.hcl` file records the exact versions and checksums of all providers and modules used in the configuration. It should be committed to version control to ensure that every developer and CI/CD pipeline uses the exact same, tested versions of the dependencies, preventing unexpected failures or security issues caused by provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the current state file.
To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web_vm["web1"]`).

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source is a block that allows OpenTofu to fetch information about existing infrastructure or external data without creating or managing it.
**Example:** Instead of creating a new VPC, you might use a data source to look up the ID of an existing VPC that was provisioned by a different team or system, allowing your new resources to reference it.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
*   **Variables**: Used for external inputs—data that comes from outside the configuration (user input, environment).
*   **Locals**: Used for internal computation—data derived or calculated *within* the configuration itself (e.g., combining strings, calculating a list, or defining reusable maps).
*   **When to use locals**: Use locals when you need to perform transformations, define complex reusable structures, or simplify the configuration logic *before* the resource creation phase.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block allows fine-grained control over how OpenTofu manages a resource during updates.
*   **`create_before_destroy`**: Ensures a new resource is created before the old one is destroyed. *Use Case:* Migrating a critical database instance (e.g., RDS) to a new version without downtime.
*   **`prevent_destroy`**: Prevents the resource from being destroyed by OpenTofu, even if the configuration changes. *Use Case:* Protecting a critical, manually configured resource that should never be deleted by the automation.
*   **`ignore_changes`**: Tells OpenTofu to ignore specific attributes when calculating drift. *Use Case:* Allowing a specific attribute (like a monitoring tag added manually by an operations team) to drift without triggering a plan change.

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
The `moved` block is a configuration directive used during refactoring. It tells OpenTofu how to map the old resource address to the new resource address.
It helps by allowing you to change the location or name of a resource in your code (e.g., moving it from `module.old_module.vm` to `module.new_module.vm`) without OpenTofu seeing it as a deletion and recreation. This preserves the resource's ID and state, preventing downtime and data loss.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
The dependency graph is a directed acyclic graph (DAG) that OpenTofu builds, mapping out the order in which resources must be created, updated, or destroyed.
*   **Implicit Dependency**: Occurs when one resource references an attribute of another resource (e.g., `resource_b` uses `resource_a.id`). OpenTofu automatically detects this and enforces the correct order.
*   **Explicit Dependency**: Defined using `depends_on`. It forces a resource to wait for another resource to complete, even if there is no direct attribute reference.
*   **Parallelism/Sparingly**: `depends_on` forces sequential execution. If you use it unnecessarily, you prevent OpenTofu from running independent resources concurrently, significantly increasing the total plan time. It should only be used when an implicit dependency is impossible to define.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1.  **Modularization**: Break large configurations into smaller, focused modules. *Tradeoff:* Increases complexity in managing module dependencies and requires more boilerplate code.
2.  **Targeting/Filtering**: Use `tofu plan -target` to only plan changes for specific, critical components. *Tradeoff:* Reduces the scope of the plan but can lead to configuration drift if not managed carefully.
3.  **State Splitting/Isolation**: Separate related resources into different state files or workspaces. *Tradeoff:* Increases the number of state files to manage and requires careful cross-state referencing.
4.  **Optimizing Providers/Resources**: Review resource definitions for unnecessary attributes or complex loops. *Tradeoff:* Requires deep knowledge of the provider APIs and may require sacrificing some configuration flexibility.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**
State locking ensures that only one operation (plan or apply) can modify the state file at any given time, preventing concurrent writes that could corrupt the state.
**If a lock is not released (e.g., crash):** The state remains locked, and all subsequent attempts to run `tofu plan` or `tofu apply` will fail with a "state locked" error, halting all infrastructure changes.
**Manually Breaking a Lock:** This is done using provider-specific CLI commands (e.g., `aws s3api unlock-bucket` or specific backend commands).
**Risks:** Manually breaking a lock is extremely dangerous. If the state is currently being modified by another process, breaking the lock will allow a second process to write to the state file, resulting in **irreversible state corruption** and potential infrastructure damage.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.**
1.  **Configure Backend:** Update the `backend` block in the configuration to point to the S3 bucket and specify the DynamoDB table name for locking.
2.  **Initialize Backend:** Run `tofu init`. OpenTofu will detect the change and prompt whether to migrate the existing state.
3.  **Migration:** Confirm the migration. OpenTofu will upload the contents of the local state file to the S3 bucket and register the lock mechanism in DynamoDB.
4.  **Verification:**
    *   Run `tofu plan` to ensure the configuration can successfully read the state from S3.
    *   Verify the state file exists in the S3 bucket.
    *   Run a concurrent operation (e.g., two CI jobs running `tofu plan` simultaneously) to confirm that the DynamoDB lock successfully blocks the second operation.

## Ansible Answers

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
*   **Playbook**: A YAML file that defines a set of plays. A play is a collection of tasks that are executed against a specific group of hosts defined in the inventory. Playbooks are the entry point for automation.
*   **Role**: A standardized way to organize related tasks, handlers, variables, and files. Roles promote reusability and structure (e.g., a `webserver` role).
*   **Task**: A single unit of work within a playbook or role. It specifies a module (e.g., `apt`, `service`) and the parameters to execute (e.g., `name: nginx`, `state: started`).

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary containing system information gathered from the target host during the connection phase (e.g., OS distribution, memory, CPU).
To access the OS family, you typically use the `ansible_distribution_family` fact:
```yaml
- name: Check OS family
  debug:
    msg: "This host is running {{ ansible_distribution_family }}"
```

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
*   **`command` module**: Executes a command directly. It is safe and does not invoke a shell, making it suitable for simple, non-shell-dependent commands (e.g., `ls -l`).
*   **`shell` module**: Executes a command through the system's shell (e.g., `/bin/bash`). It is necessary when the command requires shell features like pipes (`|`), redirection (`>`), or environment variables.
*   **`raw` module**: Executes a command directly on the remote host using the underlying connection method (e.g., SSH). It is generally used for low-level, highly specific tasks and is less idempotent than other modules.
*   **Usage**: Use `command` when possible for safety; use `shell` when shell features are required; use `raw` for advanced, low-level interactions.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means that running the same task multiple times will result in the same system state without causing unintended side effects. Ansible achieves this by using modules that check the current state before making changes.
*   **Idempotent Example**: Using the `apt` module to install a package: `name: apt`, `pkg: nginx`, `state: present`. If Nginx is already installed, Ansible does nothing and reports "ok."
*   **Non-Idempotent Example**: Using the `shell` module to append a line to a file: `shell: echo "new line" >> /etc/config.txt`. If run twice, the line will be appended twice, changing the state.

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS family
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_distribution_family == 'Debian' else 'htop' }}"
    state: present
  when: ansible_distribution_family == 'Debian'
  become: yes

- name: Install EPEL and htop on RedHat
  ansible.builtin.package:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_distribution_family == 'RedHat'
  become: yes
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
Ansible uses a strict precedence order, where variables defined later override variables defined earlier. The general order (from lowest to highest priority) is:
1.  **Role Defaults** (Variables defined within the role itself)
2.  **Inventory Variables** (Variables defined in `group_vars/` or `host_vars/`)
3.  **Host Variables** (Variables defined in `host_vars/`)
4.  **Extra Variables** (Variables passed via the command line: `-e`)
5.  **Set Fact** (Variables set dynamically during runtime using `set_fact`)

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**
This requires using the `serial` keyword in the play and potentially using `wait_for` or a custom loop structure.

1.  **Inventory Grouping:** Divide the 50 nodes into groups (e.g., `initial_nodes` (3 hosts) and `remaining_nodes` (47 hosts)).
2.  **Play 1 (Initial Nodes):** Run the RKE2 deployment tasks on the `initial_nodes` group.
3.  **Play 2 (Remaining Nodes):** Run the RKE2 deployment tasks on the `remaining_nodes` group, but use `serial: 1` (or a small number) to control the rollout speed.

*Self-Correction:* To enforce that Play 2 only starts *after* Play 1 finishes, you simply run them sequentially in the playbook file. The `serial` keyword controls the concurrency *within* the play.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible files.
To encrypt a single variable without encrypting the entire file, you must use the `ansible-vault encrypt` command and specify the exact variable path.
Example:
```bash
ansible-vault encrypt vars/secrets.yml --var "db_password"
```
This command encrypts only the specified variable, leaving the rest of the file readable.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory file lists the hosts that Ansible will manage.
*   **Static Inventory**: A manually maintained file (e.g., `hosts.ini`) where hosts and groups are defined manually.
*   **Dynamic Inventory**: A script or plugin that connects to a source (e.g., AWS, Azure, VMware) at runtime to generate the inventory list. This is crucial for large, ephemeral, or cloud-based environments, as it ensures the inventory is always up-to-date.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a task that is designed to perform a specific, usually reactive action, such as restarting a service.
**Difference**: A regular task runs unconditionally during the playbook execution. A handler is only triggered when explicitly notified by a task that has changed the system state (i.e., the task reports a change).
**Triggering**: A task notifies a handler using the `notify` keyword:
```yaml
- name: Install Nginx
  ansible.builtin.apt:
    name: nginx
    state: present
  notify: restart nginx
```

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
`ansible.cfg` is a configuration file that controls how Ansible behaves globally. It allows you to override default settings without modifying the playbook.
Commonly configured settings include:
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Defines the default SSH user to connect as.
3.  `host_key_checking`: Controls whether Ansible checks the host's SSH key (often set to `False` in automated environments).

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
The `register` keyword captures the output of a task (including stdout, stderr, and return codes) and stores it in a variable.
**Usage**: The captured data is accessed using Jinja2 templating syntax (`register_name.variable`).
```yaml
- name: Get current uptime
  ansible.builtin.command: uptime
  register: uptime_output

- name: Display uptime
  ansible.builtin.debug:
    msg: "System uptime is: {{ uptime_output.stdout }}"
```

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
*   **`include_tasks`**: Includes tasks from a file *during* playbook execution. It is used for dynamic inclusion (e.g., based on a loop or a conditional check).
*   **`import_tasks`**: Includes tasks from a file *before* playbook execution. It is used for static inclusion (e.g., including a common set of tasks that are always needed).
*   **Conditional Evaluation**: `include_tasks` allows for conditional evaluation (e.g., `when: condition`) because the playbook is still running. `import_tasks` does not support conditional evaluation; the file is loaded entirely before the playbook starts.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Ansible Galaxy is a community repository where users share reusable Ansible content (roles and collections).
To install roles and collections from a `requirements.yml` file, you use the `ansible-galaxy` command:
```bash
ansible-galaxy install -r requirements.yml
```
The `requirements.yml` file lists the required roles or collections, often specifying version constraints:
```yaml
# requirements.yml
roles:
  - src: community.general
    version: 3.1.0
  - src: my_custom_role
```

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins define how Ansible connects to the target host.
*   **`ssh`**: The default. Ansible connects to the remote host via SSH and executes commands. *Use Case:* Managing Linux/Unix servers.
*   **`local`**: Ansible executes the tasks directly on the control machine (the machine running the playbook). *Use Case:* Running local scripts, managing configuration files on the control node, or tasks that don't require remote access.
*   **`network_cli`**: Ansible uses a specialized plugin to interact with network devices (routers, switches) using CLI commands (like Telnet or SSH). *Use Case:* Configuring Cisco, Juniper, or other network hardware.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
*   **`delegate_to`**: Allows a task to be executed on a host *other* than the target host defined in the inventory.
*   **`run_once`**: When used with `delegate_to`, it ensures that the delegated task is executed only once across the entire set of hosts, even if multiple hosts are targeted.
*   **Practical Example**: You need to gather the IP addresses of all web servers (remote hosts) and then use those IPs to configure a firewall rule on the load balancer (which is running on the control node).
```yaml
- name: Gather web server IPs
  ansible.builtin.setup:
    gather_subset:
      - network
  register: web_servers_data

- name: Configure firewall on localhost
  ansible.builtin.command: firewall-cmd --add-source {{ web_servers_data.ansible_facts.all | map(attribute='ansible_host') | join(',') }}
  delegate_to: localhost
  run_once: true
```

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).**
1.  **Increase Forks**: Increase the `forks` setting in `ansible.cfg` (e.g., from 5 to 50). This allows Ansible to run multiple tasks concurrently across different hosts. *Tradeoff:* Increases resource consumption on the control node and can overwhelm target hosts.
2.  **Fact Caching**: Use the `ansible_facts_cache` module or a dedicated caching plugin. This stores gathered facts locally or remotely, preventing the need to run the `setup` module on every run. *Tradeoff:* Requires maintaining a cache infrastructure and risks using stale data if the cache is not refreshed.
3.  **Pipelining**: Use the `pipelining` setting in `ansible.cfg`. This allows Ansible to send commands to all hosts simultaneously and collect results in parallel, rather than waiting for each host to finish sequentially. *Tradeoff:* Can increase network load and complexity in handling error reporting.
4.  **Mitogen/Parallel Execution**: Use tools like Mitogen or custom parallel execution frameworks. These tools manage the parallel execution of playbooks across multiple control nodes, effectively scaling the automation infrastructure itself. *Tradeoff:* Significant increase in infrastructure complexity and setup time.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
Jinja2 is a templating engine that allows you to inject dynamic data into static files.
*   **`{{ variable }}`**: Used for outputting the value of a variable (e.g., `{{ server_ip }}`).
*   **`{% control_structure %}`**: Used for control flow logic (e.g., loops, conditionals: `{% for item in list %}`).
*   **`{# comment #}`**: Used for comments within the template that are stripped out before rendering.

**Template Snippet:**
```nginx
upstream backend_servers {
{% for server in backend_servers %}
    server {{ server.ip }}:80; # Health Check: {{ server.name }}
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.**
1.  **Serial Batches**: Use `serial: 2` (or similar) in the play to ensure only 2 servers are updated at a time, maintaining capacity.
2.  **Pre-Task (Deregister)**: Before updating a batch, use the `uri` module (or load balancer module) to deregister the servers from the load balancer.
3.  **Update Task**: Run the application update/deployment tasks on the batch.
4.  **Health Check**: Use the `uri` module to perform a health check against the newly updated servers. If the check fails, the playbook execution immediately jumps to the `rescue` block.
5.  **Post-Task (Register)**: If the health check passes, use the `uri` module to re-register the servers with the load balancer.
6.  **Rollback Strategy**: Wrap the entire deployment logic in a `block`/`rescue` structure. If the health check fails (or any task fails), the `rescue` block executes, which contains tasks to revert the deployment (e.g., redeploy the previous stable version) and re-register the servers.
