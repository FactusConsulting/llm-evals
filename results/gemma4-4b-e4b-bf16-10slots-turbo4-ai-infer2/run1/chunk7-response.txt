## Application Architecture

**AA1 — Easy: What is the difference between a monolith and a microservices architecture? Name 3 concrete problems that microservices introduce that monoliths don't have.**
A monolith is a single, tightly coupled, unified application where all components (UI, business logic, data access) are packaged and deployed together. Microservices is an architectural style where the application is broken down into a collection of small, independent, loosely coupled services, each running its own process and communicating via APIs.

Three concrete problems microservices introduce:
1. **Distributed Complexity:** Managing inter-service communication, latency, and failure modes across many network boundaries.
2. **Observability:** Tracing requests across dozens of services requires sophisticated distributed tracing tools.
3. **Operational Overhead:** Managing, deploying, and monitoring hundreds of small services requires significant automation (e.g., Kubernetes, CI/CD pipelines).

**AA2 — Easy: Explain the difference between synchronous and asynchronous communication between services. Give an example technology for each.**
*   **Synchronous Communication:** The calling service blocks and waits for an immediate response from the called service. It requires the caller to know the service's availability.
    *   *Example Technology:* REST/HTTP (e.g., using `requests` in Python).
*   **Asynchronous Communication:** The calling service sends a message or event and immediately continues its work without waiting for a response. The receiving service processes the message later.
    *   *Example Technology:* Message Queue/Event Broker (e.g., Kafka, RabbitMQ).

**AA3 — Medium: What is the difference between an API Gateway and a reverse proxy? Can an API Gateway replace a reverse proxy entirely? Why or why not?**
*   **Reverse Proxy:** A general-purpose server that sits in front of one or more backend servers, forwarding client requests to them. Its primary function is load balancing, SSL termination, and basic request routing.
*   **API Gateway:** A specialized proxy that sits in front of microservices. It adds business logic and cross-cutting concerns specific to APIs, such as authentication, rate limiting, request aggregation, and request transformation, in addition to routing.

**Can an API Gateway replace a reverse proxy entirely?** No. While an API Gateway *acts* as a reverse proxy, a general reverse proxy is a foundational networking component. An API Gateway adds layers of *application-level* intelligence (like OAuth validation or rate limiting) that a basic reverse proxy lacks. You could use a sophisticated reverse proxy (like NGINX) to handle basic routing, but you would still need a dedicated API Gateway layer for complex microservice governance.

**AA4 — Medium: Explain the Saga pattern for distributed transactions. What is the difference between choreography-based and orchestration-based sagas? When is each appropriate?**
The Saga pattern is a design pattern used to manage data consistency across multiple services in a distributed system where a traditional two-phase commit (2PC) is not feasible. A Saga is a sequence of local transactions; if one transaction fails, the Saga executes compensating transactions to undo the preceding successful transactions.

*   **Choreography-based Saga:** Services communicate by producing and consuming events. Each service knows what to do next based on the events it receives.
    *   *Appropriate when:* The business process is simple, loosely coupled, and the number of services is small.
*   **Orchestration-based Saga:** A central service (the Orchestrator) manages the entire workflow. It tells each participant service what local transaction to execute and handles the logic for compensating transactions upon failure.
    *   *Appropriate when:* The workflow is complex, long-running, or requires centralized monitoring and control over failure paths.

**AA5 — Medium: What is CQRS (Command Query Responsibility Segregation)? Why is it often paired with Event Sourcing? What problem does this combination solve that a traditional CRUD model doesn't?**
*   **CQRS:** Separates the model used for updating data (Commands) from the model used for reading data (Queries). Commands change state; Queries retrieve state.
*   **Pairing with Event Sourcing (ES):** ES dictates that instead of storing the current state of an entity, you store a sequence of immutable events that led to that state. The read model (Query side) is then built by projecting these events.
*   **Problem Solved:** A traditional CRUD model forces the read and write models to be the same, which is inefficient when read patterns are complex (e.g., needing aggregated data) or when writes are highly transactional. CQRS/ES allows you to optimize the write model for transactional integrity and the read model for query performance (e.g., using a denormalized NoSQL store for reads while maintaining a relational store for writes).

**AA6 — Medium: Explain the Circuit Breaker pattern. What are the three states? How does it differ from a simple retry with backoff, and when would you use both together?**
The Circuit Breaker pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a remote service that is down or overloaded).

*   **Three States:**
    1.  **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the circuit opens.
    2.  **Open:** Requests are immediately failed without attempting the call, preventing resource exhaustion. After a timeout, the circuit moves to half-open.
    3.  **Half-Open:** A few test requests are allowed through. If they succeed, the circuit closes; if they fail, it returns to open.

*   **Difference from Retry/Backoff:** Retry/Backoff attempts to fix transient failures by waiting and trying again. Circuit Breaker assumes the failure is systemic (the service is down) and *stops* the attempts entirely to protect both the caller and the failing service.
*   **Using Both Together:** You use the Circuit Breaker as the primary defense against systemic failure. If the circuit is closed, you might use a small, exponential backoff retry mechanism *within* the circuit breaker's allowed attempts to handle minor, transient network hiccups before declaring the service "down."

**AA8 — Hard: Explain the difference between eventual consistency and strong consistency. A product team wants their inventory system to never oversell. How would you architect this — what consistency model, what data store, and what patterns would you use at scale?**
*   **Strong Consistency:** Every read receives the most recent write. All replicas agree on the data at the same time. (e.g., ACID transactions in traditional RDBMS).
*   **Eventual Consistency:** If no new updates are made, eventually all reads will return the same value. There is a window of inconsistency. (e.g., DynamoDB, Cassandra).

**Inventory System Architecture (Never Oversell):**
*   **Consistency Model:** Strong Consistency (or near-strong consistency).
*   **Data Store:** A transactional database (e.g., PostgreSQL, CockroachDB, or a distributed SQL database).
*   **Patterns:**
    1.  **Pessimistic Locking:** When a user attempts to purchase, lock the inventory record for that SKU until the transaction commits.
    2.  **Atomic Operations:** Use database transactions to ensure the check (`IF stock > 0`) and the decrement (`stock = stock - 1`) happen as a single, indivisible unit.
    3.  **Saga/Reservation Pattern:** For high-volume systems, use a reservation service that holds inventory temporarily, ensuring the final commit is atomic, preventing overselling during the checkout flow.

**AA9 — Hard: What is a sidecar proxy in a service mesh? Explain how Envoy works in an Istio deployment. What is the data plane vs control plane? What problem does mTLS between sidecars solve that application-level TLS doesn't?**
*   **Sidecar Proxy:** A secondary container deployed alongside the main application container in the same pod. It intercepts all incoming and outgoing network traffic for the application.
*   **Envoy in Istio:** Envoy is the high-performance proxy that runs as the sidecar. Istio uses Envoy to intercept traffic, apply policies (like routing, retries, circuit breaking), and manage service discovery without the application code needing to know about these concerns.
*   **Data Plane vs Control Plane:**
    *   **Data Plane:** The set of proxies (Envoy sidecars) that handle the actual traffic flow, enforcing policies.
    *   **Control Plane:** The management layer (e.g., Istio's Pilot) that configures and pushes policies and routing rules to the data plane proxies.
*   **mTLS Solution:** Application-level TLS requires the application code to handle certificate management, key rotation, and encryption logic. mTLS between sidecars (managed by the mesh) automates this process transparently. It ensures that *all* service-to-service communication is encrypted and mutually authenticated, guaranteeing that only trusted services within the mesh can communicate, regardless of the application's internal code.

**AA10 — Medium: Explain the Strangler Fig pattern. You have a legacy .NET Framework monolith and need to incrementally migrate to .NET 8 microservices. Describe a concrete migration strategy using this pattern.**
The Strangler Fig pattern involves gradually replacing specific functionalities of a legacy system with new services, routing traffic away from the old system until the monolith is "strangled" and can be retired.

**Migration Strategy:**
1.  **Identify Boundaries:** Identify a low-risk, self-contained domain within the monolith (e.g., User Profile Management).
2.  **Build New Service:** Reimplement that domain functionality as a new, independent .NET 8 microservice.
3.  **Implement Facade/Router:** Place an API Gateway (the "strangler") in front of the monolith.
4.  **Reroute Traffic:** Configure the API Gateway to route requests for the new domain (e.g., `/api/v2/users`) to the new .NET 8 service, while all other requests (e.g., `/api/v1/orders`) still go to the monolith.
5.  **Iterate:** Repeat this process, moving domain by domain, until the monolith is only handling legacy or trivial functions, which are then retired.

**AA11 — Medium: What is the 12-Factor App methodology? Name at least 6 factors and explain why they matter for cloud-native deployments.**
The 12-Factor App is a set of best practices for building modern, cloud-native software-as-a-service applications.

**6 Factors and Importance:**
1. **Codebase:** One codebase tracked in many locations (e.g., multiple deployments). *Importance:* Allows for rapid, independent deployment across environments.
2. **Dependencies:** Explicitly declare and isolate dependencies (e.g., using package managers). *Importance:* Ensures reproducibility and avoids dependency hell in dynamic cloud environments.
3. **Config:** Store configuration (database credentials, API keys) in the environment. *Importance:* Allows the same code to run in development, staging, and production without code changes.
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. *Importance:* Enables easy swapping of services (e.g., switching from MySQL to Postgres) without code changes.
5. **Build, Release, Run:** Strictly separate the build, release, and run stages. *Importance:* Enables immutable infrastructure and reliable deployment pipelines.
6. **Processes:** Execute the application as one or more stateless processes. *Importance:* Allows for easy horizontal scaling (adding more instances) and resilience.

**AA12 — Hard: Compare event-driven architecture using an event broker (Kafka) vs request-driven architecture using REST/gRPC. Cover: coupling, scalability, debugging complexity, ordering guarantees, and failure handling. When would you choose each?**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Decoupled (Services don't know who consumes the event) | Tightly Coupled (Caller must know the recipient's endpoint) |
| **Scalability** | Highly scalable; producers and consumers scale independently. | Scales well, but scaling requires managing load balancer distribution. |
| **Debugging** | High complexity; requires tracing tools to follow event flow. | Lower complexity; direct request/response flow is easy to trace. |
| **Ordering** | Guaranteed ordering *within a partition* (critical for state changes). | Guaranteed ordering by the caller/client. |
| **Failure Handling** | High resilience; messages persist in the broker until consumed. | Requires explicit retry logic and circuit breakers on the client side. |
| **When to Choose** | When processes are long-running, asynchronous, or involve many downstream consumers (e.g., order fulfillment, notifications). | When an immediate response is required (e.g., user login, fetching a profile). |

**AA13 — Easy: What is a load balancer? Explain the difference between Layer 4 and Layer 7 load balancing. Give one use case where Layer 7 is required.**
*   **Load Balancer:** A device or software that distributes incoming network traffic across a group of backend servers to ensure no single server is overwhelmed, improving availability and performance.
*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It distributes traffic based on IP addresses and ports. It is "dumb" and only looks at the network headers.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (e.g., HTTP headers, URL path, cookies).
*   **Layer 7 Use Case:** **Content-Based Routing.** If you have a single IP address serving multiple microservices (e.g., `/api/users` vs `/api/payments`), a Layer 7 load balancer can inspect the URL path and route the request to the correct backend service.

**AA14 — Easy: What is a message queue? Explain the difference between a message queue (e.g., RabbitMQ) and a log-based message broker (e.g., Kafka). When would you pick one over the other?**
*   **Message Queue (e.g., RabbitMQ):** Focuses on transient message delivery. Messages are consumed and then *removed* from the queue. It is designed for point-to-point or publish/subscribe patterns where the message is processed once.
*   **Log-Based Message Broker (e.g., Kafka):** Focuses on persistent, ordered logs. Messages are appended to a topic and retained for a configurable period. Consumers read from the log at their own pace and can re-read past messages.

**When to Pick Which:**
*   **RabbitMQ (Queue):** Use when you need guaranteed, single processing of a task (e.g., processing a single user registration request).
*   **Kafka (Log):** Use when you need multiple services to react to the same event, or when you need historical data replay or stream processing (e.g., tracking all user activity logs).

**AA15 — Easy: What is a container and how does it differ from a virtual machine? Why are containers popular for deploying microservices?**
*   **Container:** A lightweight, isolated environment that packages an application and all its dependencies (libraries, binaries). It shares the host OS kernel.
*   **Virtual Machine (VM):** A complete emulation of a physical computer. It includes a full guest OS and hypervisor, running on top of a host OS.
*   **Difference:** VMs virtualize the hardware; containers virtualize the operating system. Containers are much smaller, start faster, and require fewer resources because they don't carry a full OS image.
*   **Popularity for Microservices:** Containers provide perfect isolation (each service runs in its own container) while maintaining high density and portability, making deployment consistent across any environment (local machine, cloud, on-prem).

**AA16 — Easy: Explain the difference between stateless and stateful services. Why are stateless services easier to scale horizontally? Give an example of each.**
*   **Stateless Service:** A service that does not store any session-specific data or client state between requests. Every request contains all the necessary information.
    *   *Example:* A simple API endpoint that calculates a price based on input parameters.
*   **Stateful Service:** A service that retains data or session information between requests.
    *   *Example:* A shopping cart service or a database server.
*   **Scaling Advantage:** Stateless services are easy to scale horizontally because any incoming request can be routed to *any* available instance. State management is externalized (e.g., to a distributed cache like Redis), allowing for simple load balancing and failure tolerance.

**AA17 — Easy: What is an ORM (Object-Relational Mapper)? Name two popular ORMs in different languages. What are the trade-offs of using an ORM vs writing raw SQL?**
*   **ORM:** A programming technique that allows developers to interact with a relational database using the objects and methods of an object-oriented programming language, rather than writing raw SQL queries.
*   **Popular ORMs:**
    1.  **Entity Framework Core** (C#/.NET)
    2.  **Hibernate** (Java)
*   **Trade-offs:**
    *   **ORM Pros:** Increased developer productivity, abstraction from specific SQL dialects, improved type safety.
    *   **ORM Cons:** Performance overhead (due to object mapping and query generation), potential for generating inefficient or overly complex SQL (the "N+1 problem"), and abstraction can hide database-specific optimizations.
    *   **Raw SQL Pros:** Maximum performance control, ability to leverage database-specific features, and optimal query tuning.

**AA18 — Medium: Explain the Bulkhead pattern. How does it relate to resource isolation in a microservices architecture? Give a concrete example of how you would implement bulkheads using thread pools or separate deployment groups.**
*   **Bulkhead Pattern:** A design pattern that isolates components of a system so that the failure or overload of one component does not cascade and bring down the entire application. It partitions resources (like thread pools or connection pools) into separate, isolated compartments.
*   **Resource Isolation:** It ensures that if one service or function experiences heavy load or failure, it only consumes its allocated resources, leaving the rest of the system operational.
*   **Implementation Example (Thread Pools):** If a service handles three types of requests (e.g., `HighPriority`, `LowPriority`, `ExternalAPI`), you would assign three separate, fixed-size thread pools. If the `ExternalAPI` requests flood the system and exhaust their dedicated thread pool, the `HighPriority` requests can still be processed by their own pool, preventing the entire service from freezing.

**AA19 — Hard: You are designing a real-time collaborative editing system (like Google Docs). Compare Operational Transformation (OT) and CRDTs (Conflict-free Replicated Data Types) as conflict resolution strategies. Cover: consistency guarantees, latency, complexity, and offline support. Which would you choose for a system that must support offline editing and why?**
| Feature | Operational Transformation (OT) | CRDTs (Conflict-free Replicated Data Types) |
| :--- | :--- | :--- |
| **Consistency** | Strong (Requires complex server coordination) | Eventual (Guaranteed convergence without coordination) |
| **Latency** | High (Requires constant server communication for transformation) | Low (Operations can be applied locally immediately) |
| **Complexity** | Very High (Requires complex transformation logic and state tracking) | Medium (Requires defining the correct data structure) |
| **Offline Support** | Poor (Requires synchronization with a central server to resolve conflicts) | Excellent (Operations are commutative and associative; they converge regardless of order) |

**Choice for Offline Editing:** **CRDTs.** They are inherently designed for eventual consistency and decentralized operation. Since CRDTs guarantee that all replicas will converge to the same state regardless of the order of operations or network latency, they are ideal for supporting robust offline editing where the client must apply changes locally before syncing.

**AA20 — Hard: Explain the challenges of distributed tracing across a polyglot microservices ecosystem. Cover: context propagation (W3C Trace Context, B3), sampling strategies (head-based vs tail-based), trace storage and querying (Jaeger, Tempo), and how tracing interacts with asynchronous messaging. How do you ensure trace continuity when a request passes through Kafka?**
*   **Challenges:** Polyglot systems make standardized instrumentation difficult. Asynchronous communication breaks the linear request flow, making it hard to link events.
*   **Context Propagation:** To link spans, a unique Trace ID and Span ID must be passed between services.
    *   **W3C Trace Context/B3:** Standardized header formats used to inject these IDs into HTTP headers (synchronous) or message metadata (asynchronous).
*   **Sampling Strategies:**
    *   **Head-Based:** Deciding whether to trace a request at the entry point (the "head"). Simple, but may miss critical errors in downstream services.
    *   **Tail-Based:** Deciding whether to trace a request *after* it has completed, based on criteria like latency or error status. More accurate but requires buffering all traces.
*   **Storage/Querying:** Tools like Jaeger or Grafana Tempo store the trace data (spans) and provide a UI to visualize the flow and latency.
*   **Kafka Continuity:** When a request passes through Kafka, the trace context must be injected into the message headers *before* it is published. The consuming service must then extract this context from the message headers and use it to start its own span, ensuring the trace ID remains the same across the asynchronous boundary.

## On-Premise Infrastructure Architecture

**OP1 — Easy: Explain the difference between a hypervisor Type 1 (bare-metal) and Type 2 (hosted). Give 2 examples of each.**
*   **Type 1 (Bare-Metal):** Runs directly on the host hardware, managing the hardware resources and hosting the guest OSes. It is highly efficient and used in production data centers.
    *   *Examples:* VMware ESXi, Microsoft Hyper-V.
*   **Type 2 (Hosted):** Runs as an application *on top* of a conventional host operating system. It is easier for development/testing but less performant.
    *   *Examples:* Oracle VirtualBox, VMware Workstation.

**OP2 — Easy: What is a SAN vs NAS? When would you use each? What protocols does each typically use?**
*   **SAN (Storage Area Network):** Provides block-level storage access. The storage is presented to the server as raw disks, and the server's OS manages the file system.
    *   *Use Case:* High-performance, transactional workloads (e.g., databases).
    *   *Protocols:* Fibre Channel (FC), iSCSI.
*   **NAS (Network Attached Storage):** Provides file-level storage access. The storage device itself manages the file system and presents shared folders over the network.
    *   *Use Case:* File sharing, backups, media storage.
    *   *Protocols:* NFS, SMB/CIFS.

**OP3 — Medium: Explain a 3-tier network architecture (core/distribution/access). Why is leaf-spine preferred in modern data centers? What problem does it solve that 3-tier doesn't?**
*   **3-Tier Architecture:**
    *   **Access:** Connects end devices (servers, workstations).
    *   **Distribution:** Aggregates traffic from access switches, applies policy (ACLs, QoS), and acts as the routing boundary.
    *   **Core:** High-speed backbone that connects distribution layers.
*   **Leaf-Spine (Clos) Architecture:** Replaces the hierarchical 3-tier model with a non-blocking, flattened topology. All leaf switches connect to all spine switches.
*   **Problem Solved:** The 3-tier model introduces bottlenecks and limits scalability due to the reliance on the distribution layer for routing and aggregation. Leaf-Spine ensures that there are multiple, equal-cost paths between any two servers, providing predictable, low-latency, and highly scalable east-west traffic flow.

**OP4 — Medium: You need to design a highly available Proxmox cluster with shared storage. Describe the architecture covering: node count, quorum, fencing, shared storage options (Ceph, iSCSI, NFS), and what happens during a node failure.**
*   **Node Count & Quorum:** Minimum 3 nodes for a cluster. Quorum requires a majority (e.g., 3 nodes = 2 votes needed).
*   **Fencing (STONITH):** A mechanism to ensure that a failed node is completely isolated from the network to prevent "split-brain" scenarios (where two nodes think they are the primary).
*   **Shared Storage Options:**
    *   **Ceph:** Recommended for high-scale, distributed storage. Provides object/block/file storage natively.
    *   **iSCSI:** Good for block-level storage if a dedicated SAN is available.
    *   **NFS:** Good for file-level storage, simple to set up.
*   **Node Failure:** If a node fails, the cluster quorum detects the failure. The cluster manager (e.g., Corosync) initiates failover. VMs/containers running on the failed node are automatically migrated (live migration or cold migration) to a healthy node, and the shared storage ensures the data is accessible to the new host.

**OP5 — Medium: What is VLAN trunking? Explain 802.1Q tagging. A server has a single NIC but needs to be on 3 VLANs — how do you configure this on Linux?**
*   **VLAN Trunking:** A method that allows multiple VLANs to travel over a single physical link (trunk).
*   **802.1Q Tagging:** The standard protocol that inserts a 4-byte tag into the Ethernet frame header. This tag contains a VLAN ID (VID), allowing the receiving switch to know which VLAN the frame belongs to, even though it traveled over a shared physical link.
*   **Linux Configuration (VLAN Sub-interfaces):** You create multiple virtual interfaces (sub-interfaces) on the single physical NIC, each assigned a specific VLAN ID.
    *   *Example:* `eth0.10` (for VLAN 10), `eth0.20` (for VLAN 20), etc. Each sub-interface is then configured with the appropriate IP address and routing rules for its respective VLAN.

**OP6 — Medium: Explain the difference between RAID 1, RAID 5, RAID 6, RAID 10, and RAID Z2 (ZFS). You have 6 drives and need to balance performance, capacity, and fault tolerance for a database server — which do you choose and why?**
*   **RAID 1 (Mirroring):** Duplicates data across drives. High read performance, 50% capacity loss. Excellent fault tolerance (can lose any drive).
*   **RAID 5 (Striping with Parity):** Stripes data and parity across drives. Good capacity utilization, can lose 1 drive.
*   **RAID 6 (Striping with Dual Parity):** Stripes data and two sets of parity. Excellent fault tolerance (can lose 2 drives).
*   **RAID 10 (Striping of Mirrors):** Stripes data across mirrored pairs. Excellent performance and fault tolerance. High capacity loss (50%).
*   **RAID Z2 (ZFS):** Similar to RAID 6, using multiple parity blocks. Highly robust and integrates advanced features like snapshots.

**Choice for Database Server (6 drives):** **RAID 10 or RAID Z2.**
*   **RAID 10:** Offers the best balance of high read/write performance (due to striping) and excellent fault tolerance (due to mirroring).
*   **RAID Z2:** Offers superior data integrity and redundancy (can survive two drive failures) while maintaining good capacity.
*   *Recommendation:* If performance is paramount, choose **RAID 10**. If data integrity and resilience against multiple simultaneous failures are paramount, choose **RAID Z2**.

**OP7 — Hard: Design a DNS architecture for a 500-person enterprise with: internal Active Directory, a DMZ with public-facing services, split-horizon DNS, and DNSSEC on the external zone. Cover: recursive resolvers, authoritative servers, forwarders, conditional forwarding, and what happens when a laptop moves between office and VPN.**
*   **Architecture Components:**
    1.  **External/Public DNS Servers (Authoritative):** Hosted in the DMZ. These servers hold the public records (A, CNAME, MX) for the company domain and are configured with DNSSEC.
    2.  **Internal DNS Servers (Authoritative/Caching):** Internal servers that hold the internal records (AD, internal hostnames).
    3.  **Recursive Resolvers:** These servers (often running on the internal DNS servers) handle queries from client devices.
    4.  **Forwarders:** The internal resolvers are configured to forward external queries (e.g., `google.com`) to trusted external DNS providers (e.g., 8.8.8.8).
    5.  **Conditional Forwarding:** The internal DNS servers are configured to forward queries for the company's own domain to the internal AD servers, ensuring internal resolution is fast and accurate.
*   **Split-Horizon DNS:** The internal DNS servers provide different records based on the client's location (e.g., internal IPs for AD, public IPs for DMZ services).
*   **Laptop Movement:** When the laptop is on the office LAN, it uses the internal DNS servers. When the laptop connects via VPN, the VPN client must be configured to use the internal DNS servers as its primary resolver. The internal DNS servers, recognizing the VPN source, will serve the correct internal records, maintaining continuity.

**OP8 — Hard: Explain the PKI chain of trust from root CA to end-entity certificate. You need to deploy an internal PKI for your organization. Cover: root CA (offline), subordinate/issuing CA, CRL vs OCSP, certificate templates, and auto-enrollment. What are the consequences of a compromised subordinate CA vs a compromised root CA?**
*   **PKI Chain of Trust:**
    1.  **Root CA (Offline):** The highest authority. Its private key is kept offline (air-gapped) and is used only to sign the subordinate CA certificate.
    2.  **Subordinate/Issuing CA:** The operational CA. It is online and uses its private key (signed by the Root CA) to issue certificates to end-entities (users, servers).
    3.  **End-Entity Certificate:** The final certificate issued to the device/user.
*   **CRL vs OCSP:**
    *   **CRL (Certificate Revocation List):** A periodically published list of all revoked certificates. Clients must download and check this list.
    *   **OCSP (Online Certificate Status Protocol):** A real-time query system where a client asks an OCSP responder if a specific certificate is valid.
*   **Certificate Templates:** Define the rules for what can be issued (e.g., "Server Template" requires a specific Subject Alternative Name; "User Template" requires specific attributes).
*   **Auto-Enrollment:** Automated process where devices request and receive certificates from the Issuing CA without manual intervention, typically using protocols like SCEP or EST.
*   **Consequences of Compromise:**
    *   **Compromised Subordinate CA:** High risk. An attacker can issue fraudulent certificates for internal services, allowing them to impersonate internal systems. The damage is contained to the subordinate CA's scope.
    *   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, its compromise invalidates *every* certificate issued by the entire PKI, requiring a complete, costly, and disruptive re-issuance of all certificates and trust anchors.

**OP10 — Medium: What is iDRAC/iLO/IPMI? Why is out-of-band management critical? What happens if your IPMI interface is exposed to the internet?**
*   **iDRAC/iLO/IPMI:** These are remote management interfaces built into server hardware. They allow administrators to manage the server (power cycle, view logs, access console) independently of the operating system or network connectivity.
*   **Out-of-Band Management (OOB):** It is critical because it provides a lifeline. If the server's OS crashes, the network stack fails, or the primary NIC dies, OOB management allows the administrator to diagnose, reboot, or repair the hardware without needing physical access to the rack.
*   **Exposure to Internet:** Catastrophic security risk. If the IPMI interface is exposed, an attacker can gain full, low-level control over the physical server hardware. They could remotely power cycle, access console output, or potentially exploit firmware vulnerabilities to compromise the entire machine. It must be strictly firewalled and isolated.

**OP11 — Medium: Explain the difference between LVM, LVM-Thin, and ZFS. When would you use each? What are the snapshot semantics for each?**
*   **LVM (Logical Volume Manager):** A software layer that abstracts physical storage devices into logical volumes. It allows for flexible resizing and volume management.
    *   *Snapshot Semantics:* Typically block-level snapshots, which are point-in-time copies of the block data.
*   **LVM-Thin:** An extension of LVM that allows for thin provisioning (allocating space only when data is written). It is highly efficient for storage utilization.
    *   *Snapshot Semantics:* Similar to LVM, it provides efficient, space-efficient snapshots.
*   **ZFS (Zettabyte File System):** A modern, integrated file system and volume manager. It manages storage, data integrity, and snapshots in one system.
    *   *Snapshot Semantics:* Copy-on-Write (CoW). When data is modified, the new data is written to a new block, and the snapshot continues to point to the old block, ensuring the snapshot is immutable and consistent.
*   **When to Use:**
    *   **LVM:** Simple volume abstraction and resizing.
    *   **LVM-Thin:** When you need to maximize storage efficiency and use snapshots on top of existing block storage.
    *   **ZFS:** When data integrity, advanced features (checksumming, self-healing), and robust, consistent snapshots are critical (e.g., database backups).

**OP12 — Hard: You have a 3-node Proxmox cluster with Ceph storage and need to survive a complete site failure. Design a stretch cluster or DR strategy. Cover: Ceph CRUSH rules, monitor placement, network latency requirements, and the split-brain problem. Why is 2-site Ceph generally a bad idea without a tiebreaker?**
*   **Stretch Cluster/DR Strategy:** A stretch cluster spans two geographically distant sites. The key is ensuring the cluster maintains quorum and data consistency across the WAN link.
*   **Ceph CRUSH Rules:** CRUSH (Controlled Replication Under Scalable Hashing) rules must be configured to understand the topology (Site A, Site B) and ensure data replicas are placed across different failure domains (i.e., one replica in Site A, one in Site B).
*   **Monitor Placement:** Ceph monitors must be distributed across both sites to maintain quorum.
*   **Network Latency:** Latency must be low enough (typically <100ms) to allow the cluster to maintain synchronous replication and quickly detect failures.
*   **Split-Brain Problem:** If the WAN link fails, both sites might believe the other is down. If both sites continue to accept writes, they will diverge, leading to data corruption.
*   **Why 2-Site Ceph is Bad without Tiebreaker:** In a 2-site setup, if the link fails, both sites have an equal number of monitors. They cannot achieve a majority quorum (2 out of 2). Both sites will enter a split-brain state, leading to data divergence. A tiebreaker (e.g., a third, small witness node placed in a neutral location) is required to maintain quorum.

**OP13 — Easy: What is DHCP and how does the DORA process work? What happens when a DHCP server is unavailable and a Windows client's lease expires?**
*   **DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses and other network configuration parameters (subnet mask, gateway, DNS) to devices on a network.
*   **DORA Process:**
    1.  **Discover:** Client broadcasts a request to find a DHCP server.
    2.  **Offer:** DHCP server responds with an IP address offer.
    3.  **Request:** Client formally requests the offered IP address.
    4.  **Acknowledge:** DHCP server sends a final confirmation, granting the lease.
*   **Server Unavailable/Lease Expiration:** When the lease expires, the client attempts to renew the lease (usually via DHCP Request). If the server is unavailable, the client will continue to use the expired IP address until the lease time runs out completely. At that point, the client will attempt to re-discover a server. If none is found, the client will lose network connectivity.

**OP14 — Easy: Explain the difference between a managed switch and an unmanaged switch. What features does a managed switch provide that are important in an enterprise environment?**
*   **Unmanaged Switch:** A plug-and-play device. It simply forwards frames based on MAC addresses. It has no configuration interface and cannot be monitored or controlled.
*   **Managed Switch:** A configurable device that allows network administrators to control, monitor, and configure traffic flow.
*   **Enterprise Features:**
    *   **VLAN Support (802.1Q):** Segmenting broadcast domains for security and performance.
    *   **QoS (Quality of Service):** Prioritizing critical traffic (e.g., VoIP) over bulk data transfers.
    *   **Port Security:** Limiting the number of MAC addresses allowed on a port to prevent unauthorized devices.
    *   **SNMP Monitoring:** Allowing network management systems to monitor port status, traffic load, and errors.

**OP15 — Easy: What is NTP and why is accurate time synchronization critical in an on-premise environment? What can go wrong when clocks drift between servers in a cluster?**
*   **NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.
*   **Criticality:** Accurate time is vital for:
    1.  **Security:** Kerberos authentication, SSL/TLS certificate validation, and logging correlation rely on accurate timestamps.
    2.  **Data Integrity:** Database replication and distributed transaction logging require synchronized timestamps.
    3.  **Compliance:** Auditing and regulatory requirements often mandate precise time logging.
*   **Consequences of Clock Drift:**
    *   **Authentication Failures:** Kerberos tickets may be rejected if the time difference exceeds the allowed skew.
    *   **Replication Errors:** Database replication or distributed state management can fail if the order of events cannot be reliably determined.
    *   **Log Correlation Failure:** Debugging becomes impossible if logs from different servers are not chronologically aligned.

**OP16 — Easy: What is the difference between a physical server, a virtual machine, and a container? When would you run a workload directly on bare metal instead of virtualizing it?**
*   **Physical Server:** A dedicated piece of hardware running a single OS.
*   **Virtual Machine (VM):** A software emulation of a physical server, running a full guest OS on top of a hypervisor.
*   **Container:** A lightweight, isolated process running on the host OS kernel.
*   **Bare Metal Use Case:** When absolute maximum performance and minimal latency are required, and the workload is highly specialized (e.g., high-frequency trading, specialized scientific computing). Running directly on bare metal eliminates the overhead of the hypervisor and the OS abstraction layer, providing the highest possible I/O and CPU efficiency.

**OP17 — Easy: Explain the difference between a UPS (Uninterruptible Power Supply) and a generator in a data center context. Why do you need both? What is the role of an ATS (Automatic Transfer Switch)?**
*   **UPS:** Provides immediate, short-term power backup (usually battery-based) to bridge the gap between a power failure and the generator starting. It protects against short outages and voltage spikes.
*   **Generator:** Provides long-term, sustained power during extended outages.
*   **Why Both:** The UPS handles the immediate, critical transition (seconds to minutes), ensuring zero downtime during the switchover. The generator handles the hours-long outage.
*   **ATS (Automatic Transfer Switch):** A safety device that monitors the incoming utility power and the generator power. When utility power fails, the ATS automatically switches the load from the utility source to the generator source, ensuring seamless power delivery to the critical equipment.

**OP18 — Medium: Explain the difference between active-passive and active-active clustering for high availability. You have a pair of Linux servers running a PostgreSQL database — describe how you would implement HA using Pacemaker/Corosync, covering fencing (STONITH), virtual IPs, and failover behavior.**
*   **Active-Passive:** One server handles all traffic (Active); the other is running but idle, waiting to take over (Passive). Simple, but wastes resources.
*   **Active-Active:** Both servers handle traffic simultaneously. Requires complex data synchronization and is more complex to manage.
*   **Implementation (Pacemaker/Corosync):**
    1.  **Corosync:** Used for cluster communication and membership (ensuring both nodes agree on the cluster state).
    2.  **STONITH (Fencing):** Critical. Before failover, the cluster must ensure the old primary node is truly dead (fenced) to prevent it from causing data corruption.
    3.  **Virtual IP (VIP):** A single IP address is assigned to the cluster, not the individual nodes. This VIP is managed by Pacemaker.
    4.  **Failover Behavior:** If the primary node fails, Corosync detects the failure. STONITH ensures the failed node is isolated. Pacemaker then moves the VIP and starts the PostgreSQL service on the secondary node, making it the new primary.

**OP19 — Hard: You are designing the backup and recovery strategy for a 50-server on-premise environment. Cover: the 3-2-1 rule, RPO/RTO requirements, backup types (full/incremental/differential), deduplication, tape vs disk vs cloud offsite, immutable backups for ransomware protection, and how you test restores. What is the difference between backup and disaster recovery?**
*   **3-2-1 Rule:** 3 copies of data, on 2 different media types, with 1 copy stored offsite.
*   **RPO (Recovery Point Objective):** The maximum acceptable amount of data loss (how old the recovered data can be).
*   **RTO (Recovery Time Objective):** The maximum acceptable downtime after a disaster.
*   **Backup Types:**
    *   **Full:** Copies all selected data.
    *   **Incremental:** Copies only data that has changed since the *last* backup (full or incremental).
    *   **Differential:** Copies all data that has changed since the *last full* backup.
*   **Storage:**
    *   **Disk:** Fast recovery, used for short-term backups.
    *   **Tape/Cloud Offsite:** Used for long-term archival and meeting the 3-2-1 rule.
    *   **Immutable Backups:** Backups that cannot be modified or deleted for a set period, crucial for ransomware protection.
*   **Testing Restores:** Regular, scheduled test restores (e.g., quarterly) to a staging environment are mandatory to validate the RTO and ensure the backup chain is valid.
*   **Backup vs. Disaster Recovery (DR):**
    *   **Backup:** A copy of data used to restore a single system or file after localized failure (e.g., hard drive failure).
    *   **Disaster Recovery:** The comprehensive plan and infrastructure to restore *entire business operations* (systems, applications, data) after a catastrophic event (e.g., fire, flood, regional power grid failure).

**OP20 — Hard: Explain how 802.1X (port-based network access control) works in an enterprise wired network. Cover: the supplicant, authenticator, and authentication server roles; EAP methods (EAP-TLS vs PEAP); RADIUS; dynamic VLAN assignment; and what happens to a device that fails authentication. How does MAB (MAC Authentication Bypass) work for devices that don't support 802.1X?**
*   **Roles:**
    *   **Supplicant:** The client device (laptop, phone) requesting network access.
    *   **Authenticator:** The network access device (the switch) that controls the physical port and mediates the communication.
    *   **Authentication Server:** The central server (RADIUS) that verifies the supplicant's credentials.
*   **Process:** The switch (Authenticator) intercepts the connection attempt and forces the supplicant to authenticate with the RADIUS server.
*   **EAP Methods:**
    *   **EAP-TLS:** Highly secure. Requires both the client and the server to present digital certificates for mutual authentication.
    *   **PEAP (Protected EAP):** Encapsulates an inner authentication method (like username/password) within a TLS tunnel, providing strong protection.
*   **Dynamic VLAN Assignment:** The RADIUS server, after successful authentication, sends an Access-Accept message back to the switch, which includes a Vendor-Specific Attribute (VSA) specifying which VLAN the supplicant should be placed into.
*   **Failure:** If authentication fails, the switch port is placed into an unauthorized state (quarantined VLAN or blocked entirely), preventing the device from accessing the main network resources.
*   **MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., IP phones, printers). The switch sends the device's MAC address to the RADIUS server. The RADIUS server is configured to trust specific MAC addresses and grants access based on that identity, bypassing the full EAP handshake.
