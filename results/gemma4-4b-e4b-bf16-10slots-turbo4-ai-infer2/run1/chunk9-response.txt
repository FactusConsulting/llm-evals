## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A: Explain why these pods are failing. Walk through how Kubernetes Pod Security Standards interact with securityContext and container image USER directives. What changed between Baseline and Restricted enforcement that causes this specific failure?**

The pods are failing because the new cluster configuration enforces the **Restricted Pod Security Standard (PSS)**, which prohibits running containers as the root user.

1.  **Interaction:** The pods have `securityContext.runAsNonRoot: true` but no explicit `runAsUser` defined. This tells Kubernetes that the container *must* run as a non-root user (UID > 0).
2.  **Image Conflict:** The new base image (`cgr.dev/chainguard/static:latest`) defaults its `USER` directive in the Dockerfile to `root` (UID 0).
3.  **The Failure:** When Kubernetes attempts to run the pod, the container runtime (e.g., containerd) attempts to start the process as the user specified by the image (root). However, the Pod Security Standard (PSS) validation fails because the runtime is attempting to violate the `runAsNonRoot: true` constraint. The pod fails to start, resulting in `CrashLoopBackOff`.
4.  **Change from Baseline to Restricted:** The **Baseline PSS** allows running as root if the container image explicitly defines a non-root user or if the pod spec explicitly overrides it. The **Restricted PSS** is much stricter; it mandates that the container must run as a non-root user, and it often restricts capabilities and user IDs more aggressively. The transition to Restricted enforcement, combined with the new image defaulting to root, is the direct cause of the failure.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A: Explain the stale data issue. What is the replication lag implication of promoting a cross-region read replica? How does PostgreSQL streaming replication handle WAL shipping across regions, and what data loss scenarios exist with asynchronous replication? What would you check to quantify the data loss window?**

**Stale Data Issue:** The stale data is a direct consequence of **asynchronous replication**. When the primary (us-east-1) commits a transaction, it acknowledges the commit to the application *before* the Write-Ahead Log (WAL) record has been successfully shipped and applied to the replica (eu-west-1). If the primary fails before the WAL segment is shipped, that committed transaction is lost.

**Replication Lag Implication:** Replication lag means the replica is always slightly behind the primary. Promoting a replica means accepting the state of the database *at the moment of promotion*. Any transactions that occurred on the primary after the last successfully received WAL segment are lost.

**WAL Shipping:** PostgreSQL uses **streaming replication**. The primary continuously streams WAL records to the replica. The replica applies these records sequentially. Across regions, this involves high latency (85ms in this case), which increases the window for lag.

**Data Loss Scenarios (Asynchronous):**
1.  **Primary Crash:** The primary fails before flushing the latest committed transactions to the WAL stream.
2.  **Network Partition:** The primary commits transactions, but the network link to the replica is severed before the WAL segment is sent.

**Quantifying Data Loss:**
1.  **Check `pg_stat_replication`:** Query this view on the *new* primary (eu-west-1) to check the `flush_lsn` and `write_lsn` of the old primary (if accessible) and compare it to the current LSN.
2.  **Check WAL Archiving:** Review the WAL archive logs on the old primary to see the last successfully archived segment.
3.  **Application Logs:** Correlate application transaction IDs with the database logs to identify the last successfully committed transaction ID before the outage.

**PostgreSQL Lock Diagnostic Query:**
```sql
SELECT
    a.pid AS blocking_pid,
    a.usename AS blocking_user,
    a.query AS blocking_query,
    pg_blocking_pids(a.pid) AS blocked_pids,
    b.pid AS blocked_pid,
    b.usename AS blocked_user,

FROM pg_stat_activity a
```

    *   **Time Shifting:** Move the reconciliation job to a time when traffic is lowest (e.g., 03:00 UTC) or, ideally, run it asynchronously via a message queue triggered by events, rather than a fixed time window.

**Drift Sources and Dangers:**

1.  **Manual `tofu apply` (Developer Laptops):**
    *   **How:** Developers bypassed the controlled pipeline, making changes directly to the infrastructure (e.g., adding a resource, changing a tag).
    *   **Danger:** Loss of auditability and reproducibility. The Git repository no longer reflects the actual state of production, making debugging and disaster recovery impossible.
2.  **Diverged Helm Values Files (Staging/Prod):**
    *   **How:** Manual overrides or ad-hoc changes were made to the Helm values files in the target environment, bypassing version control.

    *   **How:** An engineer used `kubectl edit` to change a ConfigMap directly in the cluster.

*   **Data Loss/Outage:** If two engineers run `tofu apply` simultaneously, they both read the same state file. They both calculate their changes based on the *same initial state*. *   **Simultaneous Run:** The second engineer's `tofu apply` will likely fail with a concurrency error or, if the state file is corrupted, lead to an unpredictable and potentially catastrophic state corruption.

```python
from rest_framework import permissions

class IsOwnerOrReadOnly(permissions.BasePermission):
    """
    Custom permission to only allow owners of an object to edit it.

    def has_object_permission(self, request, view, obj):
```

    *   **Redis:** Sentinel detects the primary failure and promotes the Dallas replica.
    *   **RabbitMQ:** Queue mirroring automatically redirects writes to the Dallas cluster.
    *   **MinIO:** The Dallas cluster continues serving reads and begins catching up on any missed writes from Chicago.
4.  **Application Traffic Shift (DNS Failover):**
    *   GSLB/Route53 health checks fail for Chicago and automatically shift 100% of traffic to the Dallas endpoint.
5.  **Infrastructure State Update:**
    *   A post-failover automation script (e.g., a CI/CD job triggered by the DR event) runs `terraform apply` to update the infrastructure state, changing the primary database endpoint and updating any dependent resources (e.g., application configuration, Route53 records) to point to the Dallas cluster.

**Handling Split-Brain Scenarios:**
*   **Prevention:** Patroni's use of etcd (DCS) is the primary defense. etcd ensures that only one node can hold the leader lock at any given time. If the network partitions, the minority side loses quorum and cannot promote itself, preventing two primaries.
*   **Mitigation:** If a split-brain occurs, manual intervention is required. The system must be forced into a read-only mode, and the conflicting data must be reconciled manually before the system can be brought back online.

**Failing Back to Chicago (Recovery):**
1.  **Chicago Recovery:** The Chicago cluster is brought back online and configured as a *new standby* to the Dallas primary.
2.  **Data Sync:** The Chicago cluster performs a full WAL recovery/catch-up from the Dallas primary.
3.  **Testing:** Extensive validation is performed to ensure data consistency.
4.  **Controlled Failover:** The GSLB is manually configured to shift traffic back to Chicago, and the roles are reversed (Dallas becomes standby, Chicago becomes primary).
