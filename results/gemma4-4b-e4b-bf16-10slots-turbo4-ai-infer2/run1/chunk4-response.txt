## Go Answers

**G1 — Easy: What is the difference between a slice and an array in Go? What happens when you append to a slice that has reached its capacity?**
An array in Go has a fixed size defined at compile time (e.g., `[5]int`). A slice is a dynamically sized view into an underlying array. A slice is a descriptor containing a pointer to the underlying array, a length, and a capacity. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array (typically doubling the capacity), copies the elements from the old array to the new one, and updates the slice header to point to the new array.

**G2 — Easy: Explain the difference between `var x int` and `x := 0`. When can you NOT use `:=`?**
`var x int` declares a variable and initializes it to its zero value (0 for `int`). `x := 0` is a short variable declaration, which declares and initializes a variable in a single step. You cannot use `:=` when declaring a variable outside of a function body, or when you are reassigning a variable that has already been declared using `var` or `:=` in the same scope.

**G3 — Medium: What is a goroutine, and how does it differ from an OS thread? What is the role of the Go scheduler (GMP model)?**
A goroutine is a lightweight, independently executing function managed by the Go runtime. It is much cheaper and lighter than an OS thread. The Go scheduler (using the GMP model: G=Goroutine, M=Machine/OS Thread, P=Processor/Context) maps many goroutines (G) onto a smaller number of OS threads (M). The P acts as a logical processor, managing the execution of Gs on M. This allows Go to efficiently handle thousands of concurrent goroutines without the overhead of creating a corresponding OS thread for each.

**G4 — Medium: Explain how channels work in Go. What is the difference between a buffered and unbuffered channel? What happens when you send to a full buffered channel?**
Channels are typed conduits through which goroutines communicate and synchronize.
*   **Unbuffered Channel:** Requires both the sender and receiver to be ready simultaneously (a synchronous rendezvous). The send operation blocks until a receiver is ready, and the receive operation blocks until a sender is ready.
*   **Buffered Channel:** Has a fixed capacity. The sender blocks only when the buffer is full, and the receiver blocks only when the buffer is empty.
When you send to a full buffered channel, the sending goroutine blocks until another goroutine reads an element from the channel, freeing up space.

**G5 — Medium: What is the context package used for? Write a minimal example of using context.WithTimeout to cancel a long-running HTTP request.**
The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. It is crucial for managing the lifecycle of requests, ensuring that long-running operations can be gracefully terminated if they exceed a time limit or if the caller decides to cancel them.

*Minimal Example:*
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // Always call cancel to release resources

req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com/long", nil)
client := &http.Client{}
resp, err := client.Do(req)
// Check for context cancellation error here
```

**G6 — Medium: Explain Go's interface satisfaction model. How does it differ from Java/C# interfaces? What is the empty interface interface{} (or any) and why is it both powerful and dangerous?**
Go uses implicit interface satisfaction. A type satisfies an interface if it implements all the methods defined by that interface; there is no explicit declaration required. This differs from Java/C# where a class must explicitly `implement` an interface.
The empty interface (`interface{}` or `any` in Go 1.18+) is an interface with zero methods. It can hold a value of any type. It is powerful because it allows for maximum flexibility and generic handling of data. It is dangerous because it requires type assertions or type switches to use the underlying value, which can lead to runtime panics if the type is incorrect.

**G8 — Hard: What is the difference between sync.Mutex and sync.RWMutex? When would you use sync.Map vs a regular map with a mutex? What are the performance trade-offs?**
*   **`sync.Mutex`:** Provides exclusive access. Only one goroutine can hold the lock (read or write) at any time.
*   **`sync.RWMutex`:** Allows multiple readers simultaneously, but requires exclusive access for writers. Readers do not block other readers, but they block writers, and writers block all readers.
*   **`sync.Map` vs. Map+Mutex:** `sync.Map` is optimized for scenarios where keys are written once and read many times (read-heavy workloads). It avoids locking the entire map structure for every operation. A regular map with a mutex is simpler and often faster for small maps or write-heavy workloads, as `sync.Map` has overhead for managing its internal structure.

**G9 — Hard: Explain how Go modules work. What is the difference between go.mod and go.sum? What does go mod tidy do, and what is the Minimum Version Selection (MVS) algorithm?**
Go modules manage dependencies. `go.mod` lists the required modules and their specific versions (e.g., `require github.com/pkg/errors v0.9.1`). `go.sum` contains cryptographic checksums for the exact content of every dependency listed in `go.mod`. This ensures that the downloaded code has not been tampered with.
`go mod tidy` cleans up the module file by adding any missing dependencies required by the source code and removing any dependencies that are no longer used.
MVS (Minimum Version Selection) is an algorithm used by Go to select the highest possible version of a dependency that satisfies all version constraints specified in the `go.mod` file, ensuring compatibility while allowing for the latest features.

**G10 — Medium: What is a defer statement? In what order do multiple defers execute? What is a common gotcha with defer in a loop?**
A `defer` statement schedules a function call to be executed just before the surrounding function returns.
Multiple defers execute in **Last-In, First-Out (LIFO)** order.
The common gotcha is capturing loop variables. If a `defer` statement references a loop variable, it captures the variable's *address*, not its value at the time of declaration. By the time the deferred function runs, the loop variable will hold the value from the final iteration. The fix is to create a new local variable inside the loop iteration.

**G11 — Easy: What is a pointer in Go? What is the zero value of a pointer? How do you create a pointer to a struct literal?**
A pointer is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`.
To create a pointer to a struct literal, you first declare the struct literal, and then use the address-of operator (`&`):
```go
type Point struct { X, Y int }
p := Point{X: 10, Y: 20}
ptr := &p // ptr is a *Point
```

**G12 — Easy: Explain Go's init() function. When does it run? Can a package have multiple init() functions, and if so, in what order do they execute?**
The `init()` function is a special function that runs automatically before the `main` function of a package. It is used for package-level setup, such as initializing global variables or registering drivers.
Yes, a package can have multiple `init()` functions. They execute in the order that the packages are imported and initialized. If multiple packages define `init()` functions, the initialization order follows the dependency graph (packages are initialized before the packages that depend on them).

**G13 — Easy: What is the difference between make and new in Go? What types does each work with?**
*   **`new(T)`:** Allocates memory for a value of type `T` and returns a pointer to it, initialized to the zero value. It works for any type.
*   **`make(T, ...)`:** Allocates and initializes a value of a specific type, typically for composite types like slices, maps, and channels. It initializes them to a usable state (e.g., a slice with a specific length/capacity).

**G14 — Easy: How does error handling work in Go? What is the error interface, and what is the idiomatic pattern for checking errors? How do errors.Is and errors.As differ from ==?**
Error handling is idiomatic and explicit, relying on returning an `error` type as the last return value. The `error` interface is a simple interface defined as `type error interface { Error() string }`.
The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`.
*   `errors.Is(err, target)`: Checks if the error chain contains a specific sentinel error (e.g., checking if an I/O error is specifically `os.ErrNotExist`).
*   `errors.As(err, target)`: Checks if the error chain contains a value that matches a specific type (e.g., checking if a wrapped error contains a specific custom struct type).
*   `==`: Only checks for exact pointer equality, which is rarely useful for error checking.

**G15 — Easy: What are Go's built-in composite types (map, slice, channel, struct)? What is the zero value of each?**
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be used until initialized with `make`).
*   **Slice:** `[]Type`. Zero value: `nil` (a slice header pointing to no underlying array).
*   **Channel:** `chan Type`. Zero value: `nil` (cannot be used until initialized with `make`).
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values (e.g., `0` for integers, `""` for strings).

**G16 — Medium: What is a race condition in Go? How does the -race flag work? Give an example of a data race and show how to fix it with sync.Mutex or a channel.**
A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, leading to unpredictable results.
The `-race` flag is a runtime tool that instruments the Go program to detect data races during execution.
*Example (Data Race):* Two goroutines incrementing a shared counter without synchronization.
*Fix (Mutex):* Wrap the critical section (the increment) with `mutex.Lock()` and `mutex.Unlock()`.
*Fix (Channel):* Use a single goroutine to manage the state (the counter) and communicate updates via a channel, ensuring sequential access.

**G17 — Medium: Explain Go's select statement. How does it differ from a switch? What happens when multiple cases are ready? How do you implement a timeout with select?**
The `select` statement is used to wait on multiple communication operations (channel receives or sends). It is the concurrency equivalent of a `switch` statement.
*   **Difference from `switch`:** A `switch` evaluates a single expression; a `select` waits on multiple channel operations.
*   **Multiple Ready Cases:** If multiple cases are ready, `select` chooses one of them pseudo-randomly.
*   **Timeout Implementation:** Use the `time.After()` function as a channel case.
```go
select {
case msg := <-ch:
    // Handle message
case <-time.After(5 * time.Second):
    // Timeout occurred
}
```

**G18 — Hard: What is escape analysis in Go? How does the compiler decide whether to allocate on the stack or the heap? How can you inspect escape analysis decisions, and why does it matter for performance?**
Escape analysis is a compiler optimization that determines where a variable should be allocated in memory.
*   **Stack Allocation:** If a variable's lifetime is confined to the function call stack (it does not "escape" the function), it is allocated on the stack. This is extremely fast.
*   **Heap Allocation:** If the variable's address is returned from the function, or if it is stored in a global variable, it must be allocated on the heap. Heap allocation requires garbage collection overhead.
*   **Inspection:** You can use the `-gcflags="-m"` flag during compilation to see the escape analysis decisions.
*   **Performance:** Minimizing heap allocations is critical for performance, as it reduces the load on the garbage collector.

**G19 — Hard: Explain Go's reflection package (reflect). What is reflect.Type vs reflect.Value? What are the performance costs, and when is reflection justified vs code generation?**
The `reflect` package allows a program to inspect and manipulate types and values at runtime.
*   `reflect.Type`: Represents the metadata of a type (e.g., its name, fields, methods).
*   `reflect.Value`: Represents the actual value of a variable.
Reflection is powerful for building generic frameworks, ORMs, or serialization libraries.
*   **Performance Costs:** Reflection is significantly slower than direct type access because it involves runtime introspection and dynamic lookups, bypassing compile-time optimizations.
*   **Justification:** Reflection is justified when the structure of the data is unknown until runtime (e.g., processing arbitrary JSON payloads) or when building highly generic, metaprogramming tools. For performance-critical code, code generation or static generics (if available) are preferred.

**G20 — Hard: What is the go:embed directive? How does it work for single files, directories, and file systems? What are the limitations, and how does it interact with io/fs.FS?**
`go:embed` is a directive that allows developers to embed external files (like static assets, templates, or configuration files) directly into the compiled binary.
*   **Usage:** It uses the `embed.FS` type. You can embed single files, entire directories, or even custom file systems.
*   **Interaction with `io/fs.FS`:** The embedded content is exposed as an `fs.FS` interface, allowing standard Go libraries (like `http.FileServer` or `io.Copy`) to treat the embedded assets as if they were on the filesystem.
*   **Limitations:** The embedded content is static; it cannot be modified at runtime. It increases the size of the binary.

## Rust Answers

**R1 — Easy: What is ownership in Rust? Explain the three ownership rules.**
Ownership is Rust's core memory management system. It dictates that every value in Rust has a single variable that is its *owner*. When the owner goes out of scope, the value is automatically dropped (memory is freed).
The three rules are:
1.  Every value has an owner.
2.  There can only be one owner at a time.
3.  When the owner goes out of scope, the value is dropped.

**R2 — Easy: What is the difference between String and &str? When would you use each in function signatures?**
*   **`String`:** A heap-allocated, growable, mutable string type. It owns its data.
*   **`&str`:** A string slice; a borrowed, immutable view into string data (which could be owned by a `String` or a static literal).
*   **Usage:** Use `&str` in function signatures when you only need to read the string data (most common). Use `String` when you need to create, modify, or own a string within the function.

**R3 — Medium: Explain borrowing and the borrow checker. What are the rules for shared (&T) and mutable (&mut T) references?**
Borrowing allows you to refer to data without taking ownership. The borrow checker enforces rules to prevent data races at compile time.
*   **Shared Reference (`&T`):** Allows multiple readers. You can have any number of shared references to a piece of data simultaneously.
*   **Mutable Reference (`&mut T`):** Allows exactly one writer. If a mutable reference exists, no other references (shared or mutable) can exist for that data.
*   **The Rule:** You can have either many shared references OR one mutable reference, but never both simultaneously.

**R4 — Medium: What is a Result<T, E> and an Option<T>? How does the ? operator work? Write a function that reads a file and returns its contents or an error.**
*   **`Option<T>`:** Represents the presence or absence of a value. It is an enum: `Some(T)` (value present) or `None` (value absent).
*   **`Result<T, E>`:** Represents the outcome of an operation that might fail. It is an enum: `Ok(T)` (success, containing value T) or `Err(E)` (failure, containing error E).
*   **`?` Operator:** Used for propagating errors. If the expression evaluates to `Err(E)`, the `?` operator immediately returns that error from the current function. If it evaluates to `Ok(T)`, it unwraps the value `T` and continues execution.

*Example:*
```rust
use std::fs;
use std::io;

fn read_file(path: &str) -> Result<String, io::Error> {
    // The ? operator handles the Result: if fs::read_to_string fails, 
    // it returns the error immediately.
    let contents = fs::read_to_string(path)?; 
    Ok(contents)
}
```

**R5 — Medium: Explain the difference between Box<T>, Rc<T>, and Arc<T>. When would you use each?**
These are smart pointers used for heap allocation and shared ownership:
*   **`Box<T>`:** A smart pointer that allocates data on the heap. It represents *unique* ownership. Use it when you need to put a type on the heap (e.g., recursive data structures) or when you need to hide the size of a type (trait objects).
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data. It keeps a count of references; the data is dropped only when the last `Rc` is dropped. Use it for single-threaded shared ownership.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>`, but uses atomic operations for reference counting. This makes it safe to share ownership across multiple threads. Use it for multi-threaded shared ownership.

**R6 — Medium: What are traits in Rust? How do they compare to Go interfaces? What is a trait object (dyn Trait) vs a generic with a trait bound (T: Trait)?**
Traits are Rust's mechanism for defining shared behavior (like interfaces). They define a set of methods that implementing types must provide.
*   **Comparison to Go Interfaces:** Traits are more powerful and explicit. They can define default implementations and are often used for compile-time polymorphism. Go interfaces are implicit and rely on duck typing.
*   **Trait Object (`dyn Trait`):** A pointer to a trait implementation. It allows you to treat different types uniformly at runtime (dynamic dispatch). It incurs a small runtime overhead (vtable lookup).
*   **Generic with Trait Bound (`T: Trait`):** Allows the compiler to generate specialized code for each type `T` that implements the trait (static dispatch/monomorphization). This is zero-cost and generally faster than trait objects.

**R7 — Hard: Explain lifetimes in Rust. Why does the following fail to compile, and how do you fix it?**
Lifetimes (`'a`) are a mechanism the compiler uses to ensure that references are always valid and do not outlive the data they point to. They are compile-time guarantees against dangling pointers.
*Failure:* The function returns a reference (`&str`) that points to a local variable (`x` or `y`) inside the function. When the function returns, the local variable is dropped, and the returned reference becomes invalid (a dangling pointer).
*Fix:* The function must return a reference whose lifetime is tied to the *caller's* scope, not the local scope. This usually means the function must take references that live long enough to cover the returned reference.

**R8 — Hard: What is Send and Sync in Rust? Why can't you send an Rc<T> across threads? What makes Arc<T> safe for concurrent use?**
*   **`Send`:** A marker trait indicating that a type can be safely transferred (moved) to another thread.
*   **`Sync`:** A marker trait indicating that a type can be safely shared (referenced) across threads.
*   **`Rc<T>` Issue:** `Rc<T>` uses non-atomic reference counting. If multiple threads modify the reference count simultaneously, a data race occurs on the counter itself, leading to memory corruption.
*   **`Arc<T>` Safety:** `Arc<T>` uses atomic operations (like `std::sync::atomic`) for its reference counting. This ensures that the reference count updates are thread-safe, making `Arc<T>` safe for concurrent use.

**R9 — Hard: Explain how Rust's async/await works under the hood. What is a Future? What is the role of the executor (e.g., Tokio)? How does this differ from Go's goroutines?**
*   **Future:** A trait representing a value that may not be available yet. It is essentially a state machine that knows how to poll itself until it completes. When polled, it either returns a value or indicates that it is not ready yet.
*   **Executor (e.g., Tokio):** The executor is the runtime environment responsible for driving the futures. It polls the futures, managing the task scheduling and ensuring that when a future is ready (e.g., I/O completes), it is polled again.
*   **Difference from Goroutines:** Goroutines are managed by a runtime scheduler (Go runtime) that maps them to OS threads. Rust's `async/await` is *zero-cost*—it is a compiler transformation that turns asynchronous code into state machines. The executor is external and must be provided by the user (e.g., Tokio).

**R10 — Medium: What is unsafe in Rust? Give 3 things you can do in an unsafe block that you can't do in safe Rust. When is unsafe justified?**
`unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. It is a contract: the programmer guarantees that they will maintain memory safety within that block.
Three things you can do in an `unsafe` block:
1.  Dereference raw pointers (`*const T` or `*mut T`).
2.  Call an `unsafe` function or method.
3.  Access or modify a mutable static variable.
*Justification:* `unsafe` is justified when interfacing with external C libraries (FFI), implementing highly optimized data structures, or when implementing low-level OS-like primitives where the compiler cannot guarantee safety.

**R11 — Easy: What is pattern matching in Rust? How does match differ from if let? What does the compiler enforce about exhaustiveness?**
Pattern matching is a powerful control flow construct that allows you to check a value against a series of patterns and execute code based on which pattern matches.
*   **`match` vs. `if let`:** `match` is exhaustive; it checks against multiple patterns and requires a catch-all (`_`) to ensure all possibilities are covered. `if let` is syntactic sugar for matching a single pattern and is used when you only care about one specific pattern.
*   **Exhaustiveness:** The compiler enforces exhaustiveness for `match` expressions. This means you must provide a pattern that covers every possible state of the input type (e.g., both `Some` and `None` for an `Option`).

**R12 — Easy: What is the difference between Vec<T> and an array [T; N]? How does Vec manage memory when elements are pushed beyond its current capacity?**
*   **Array `[T; N]`:** A fixed-size collection whose size is known at compile time. Its memory is allocated on the stack (if small enough) or statically.
*   **`Vec<T>`:** A dynamically sized, heap-allocated vector. It manages its own memory.
*   **Capacity Management:** When `Vec<T>` is pushed beyond its current capacity, it performs a reallocation: it allocates a new, larger block of memory (usually doubling the capacity), copies all existing elements from the old memory block to the new one, and then drops the old memory.

**R13 — Easy: What are enums in Rust, and how do they differ from enums in C or Java? What is the Option<T> enum, and why does Rust not have null?**
Rust enums are powerful algebraic data types (ADTs) that can hold different types of data depending on the variant. Unlike C/Java enums (which are usually just integer constants), Rust enums can be complex types.
*   **`Option<T>`:** This is an enum that explicitly models the possibility of absence. It is defined as `enum Option<T> { Some(T), None }`.
*   **Why no null?** Rust avoids the concept of `null` because `null` is a dangerous, undefined state that can lead to memory corruption (null pointer dereference). By using `Option<T>`, Rust forces the programmer to explicitly handle the case where a value might be absent, making the absence of a value a first-class, safe concept.

**R14 — Easy: Explain the impl block. What is the difference between methods that take &self, &mut self, and self? What are associated functions (e.g., String::new())?**
The `impl` block is where you define methods and associated functions for a specific type.
*   **`&self`:** Takes an immutable reference to the instance. The method can read the data but cannot change it.
*   **`&mut self`:** Takes a mutable reference to the instance. The method can read and modify the data.
*   **`self`:** Takes ownership of the instance. The method consumes the instance, and it cannot be used afterward.
*   **Associated Functions:** Functions defined within the `impl` block that do not take `self` as an argument (e.g., `String::new()`). They are called using the type name itself, not an instance of the type.

**R15 — Easy: What is the derive macro? Give examples of commonly derived traits (Debug, Clone, PartialEq, Serialize). When can you NOT derive a trait?**
A derive macro is a procedural macro that automatically implements a trait for a struct or enum at compile time. It automates boilerplate code.
*   **Examples:**
    *   `#[derive(Debug)]`: Allows the type to be printed in a developer-friendly format.
    *   `#[derive(Clone)]`: Allows the type to be copied.
    *   `#[derive(PartialEq)]`: Allows comparison using `==`.
    *   `#[derive(Serialize)]`: Used by serialization libraries (like Serde) to convert the type to JSON/YAML.
*   **When you cannot derive:** You cannot derive a trait if the type contains types that do not implement that trait (e.g., if a struct contains a raw pointer, it cannot automatically derive `Clone`).

**R16 — Medium: What is Cow<'a, T> (clone on write)? When is it useful? Give an example where it avoids unnecessary allocations compared to always cloning.**
`Cow<'a, T>` (Clone on Write) is a type that can either hold an owned value (`T`) or a borrowed reference (`&T`). It allows you to defer the decision of whether to clone the data until it is actually modified.
*   **Usefulness:** It is useful when a function might receive data that is either already owned or borrowed, and the function might modify it. If the function only reads the data, it uses the borrowed reference (`Cow::Borrowed`), avoiding a copy. If it needs to modify it, it clones the data (`Cow::Owned`).
*   **Example:** If a function takes `Cow<'a, str>`, and the function only prints the string, it uses the borrowed reference. If it needs to append a suffix, it clones the borrowed string into an owned `String` and returns it.

**R17 — Medium: Explain Rust's module system. What is the difference between mod, use, and pub? How does the file system map to modules, and what changed between Rust 2015 and 2018 editions?**
The module system organizes code into hierarchical units.
*   **`mod`:** Declares a module, which can be a file or a block of code.
*   **`use`:** Brings items (functions, structs) from another module into the current scope, allowing you to refer to them without the full path.
*   **`pub`:** Makes an item publicly accessible outside of its current module.
*   **File System Mapping:** By default, a file named `foo.rs` corresponds to the module `foo`. A directory named `foo/` corresponds to the module `foo`, and files inside it are modules within that structure.
*   **2018 Edition Change:** The 2018 edition introduced the ability to use `mod` inside a module to declare sub-modules, allowing for more flexible and nested module structures.

**R18 — Hard: What is the Pin<T> type and why is it needed? How does it relate to self-referential structs and async/await? What is Unpin?**
*   **`Pin<T>`:** A wrapper type that guarantees that a value `T` will not be moved in memory for the duration of its lifetime.
*   **Need:** It is required for types that are *self-referential* (i.e., a part of the struct holds a pointer to another part of the same struct). If the struct were moved in memory, the internal pointer would become invalid (dangling).
*   **Async/Await:** `Pin` is crucial for `Future`s. A `Future` often needs to store a pointer to its own internal state. If the executor moves the `Future` in memory while it is running, that internal pointer breaks. `Pin` prevents this movement, ensuring the future remains stable while it is being polled.
*   **`Unpin`:** A marker trait indicating that a type can be safely moved in memory without invalidating its internal pointers.

**R19 — Hard: Explain Rust's macro system. What is the difference between declarative macros (macro_rules!) and procedural macros (derive, attribute, function-like)? What are hygiene rules?**
Rust macros allow metaprogramming—writing code that writes code.
*   **Declarative Macros (`macro_rules!`):** Pattern matching macros. They operate on tokens and are used for simple, repetitive code generation (e.g., defining simple logging functions).
*   **Procedural Macros:** These are functions that take Rust code (tokens) as input and output new Rust code. They are far more powerful.
    *   *Derive Macros:* Automatically implement traits (e.g., `#[derive(Debug)]`).
    *   *Attribute Macros:* Modify the code surrounding an item (e.g., `#[tokio::main]`).
    *   *Function-like Macros:* Act like regular functions but operate on tokens.
*   **Hygiene Rules:** Macros are designed to be hygienic, meaning they do not accidentally capture or conflict with identifiers (variable names, function names) defined in the surrounding scope. This prevents naming collisions.

**R20 — Hard: What are zero-cost abstractions in Rust? Explain how iterators, generics (monomorphization), and trait static dispatch achieve performance comparable to hand-written C while providing high-level ergonomics.**
Zero-cost abstractions mean that the high-level features (like iterators or generics) do not incur runtime performance penalties compared to writing the equivalent low-level code manually.
*   **Generics (Monomorphization):** When you use a generic type `T`, the Rust compiler generates a specialized version of the code for every concrete type used (e.g., one version for `i32`, one for `String`). This eliminates the need for runtime type checks or virtual function lookups, achieving static dispatch.
*   **Iterators:** Rust iterators are implemented using traits. The compiler optimizes the trait calls into highly efficient, often loop-unrolled, machine code, avoiding the overhead of dynamic dispatch.
*   **Trait Static Dispatch:** Instead of using a dynamic lookup table (like a vtable in C++ or Java), the compiler resolves the exact method call at compile time, resulting in performance identical to a direct function call.
