## JavaScript / TypeScript (20 questions)

**JS1**
The difference is:
*   **`var`**: Function-scoped or globally scoped. It is hoisted and can be redeclared and updated without error.
*   **`let`**: Block-scoped (limited to the nearest `{}`). It is hoisted but remains in the Temporal Dead Zone (TDZ) until declaration.
*   **`const`**: Block-scoped. It must be initialized upon declaration and cannot be reassigned. (Note: For objects/arrays declared with `const`, the *contents* can still be mutated, but the variable reference cannot be changed.)
**Hoisting** is JavaScript's behavior of moving declarations (but not initializations) to the top of the scope during compilation. `var` declarations are hoisted and initialized to `undefined`. `let` and `const` are hoisted but remain uninitialized, leading to the TDZ.

**JS2**
The **Event Loop** is the mechanism that allows JavaScript (a single-threaded language) to perform non-blocking I/O operations. It continuously checks the Call Stack and the various queues.
*   **Call Stack**: Where synchronous code execution happens (LIFO).
*   **Microtask Queue**: Holds high-priority tasks (e.g., Promise callbacks, `queueMicrotask`). The Event Loop processes *all* microtasks after the current script finishes executing, before moving to the next macrotask.
*   **Macrotask Queue**: Holds lower-priority tasks (e.g., `setTimeout`, `setInterval`, I/O events). The Event Loop processes one macrotask at a time.
**Relationship**: When the Call Stack is empty, the Event Loop checks the Microtask Queue first. If it's not empty, it drains it completely. Only then does it check the Macrotask Queue for the next task.

**JS3**
A **closure** is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). Essentially, a function "remembers" the variables from the scope in which it was created, even after that outer scope has finished executing.
*   **Practical Example**: A counter function factory:
    ```javascript
    function createCounter() {
      let count = 0;
      return function() {
        count++;
        return count;
      };
    }
    const counter = createCounter();
    console.log(counter()); // 1
    console.log(counter()); // 2
    ```
*   **Classic Closure Bug**: When using `var` in a loop, the closure captures the *variable* `i`, not the *value* of `i` at each iteration. By the time the callbacks execute, `i` has reached the loop's final value.
*   **Fix**: Use `let` (which creates a new binding for each iteration) or wrap the callback in an Immediately Invoked Function Expression (IIFE) to capture the current value of `i`.

**JS4**
*   **Promise**: An object representing the eventual completion (or failure) of an asynchronous operation and its resulting value.
*   **`async/await`**: Syntactic sugar built on Promises. `async` functions always return a Promise, and `await` pauses execution until the Promise resolves.
*   **Error Handling**: With Promises, errors are caught using `.catch()` or `try...catch` blocks around `await` calls.
*   **`Promise.allSettled` vs `Promise.all`**:
    *   `Promise.all()`: Waits for *all* promises to resolve. If *any* promise rejects, `Promise.all()` immediately rejects with the reason of the first promise that failed.
    *   `Promise.allSettled()`: Waits for *all* promises to settle (either resolve or reject). It returns an array of objects describing the outcome of each promise, allowing you to inspect failures without stopping the process.

**JS5**
*   **`interface`**: A contract that defines the shape of an object. It is purely a compile-time construct (TypeScript only). It describes *what* an object must look like.
*   **`type`**: A more versatile type alias. It can define primitives, unions, intersections, tuples, and complex types. It is also a compile-time construct.
*   **When to use**: Use `interface` when defining the structure of objects (especially classes or external data). Use `type` when defining complex unions, intersections, or mapping existing types.
*   **Discriminated Unions**: A union type where one or more members share a common, literal property (the "discriminator"). This allows TypeScript to narrow the type safely using a `switch` statement or `if/else` chain, ensuring you handle every possible state.
    *   *Example*: `type Shape = { kind: "circle", radius: number } | { kind: "square", side: number };`

**JS6**
**Prototypal Inheritance**: JavaScript objects inherit properties and methods from other objects (their prototypes). When you try to access a property on an object, if it's not found directly, the engine looks up the prototype chain until it finds it or reaches `Object.prototype`.
*   **`Object.create()`**: Creates a new object, setting the prototype of the new object to the object passed as the first argument. This is the fundamental way to establish inheritance in JS.
    *   *Example*: `const child = Object.create(parent);` (child inherits from parent).
*   **ES6 Classes**: ES6 classes are syntactic sugar over the existing prototypal inheritance model. They provide a cleaner, more familiar (class-based) syntax while still operating entirely on prototypes under the hood.

**JS7**
The **`this` keyword** refers to the object that is currently executing the function. Its value is determined dynamically based on *how* the function is called, not where it is defined.
**4 Binding Rules (in priority order):**
1.  **`new` binding**: If the function is called with `new`, `this` refers to the newly created instance.
2.  **Explicit binding**: If `call()`, `apply()`, or `bind()` are used, `this` is set to the object passed as the first argument.
3.  **Implicit binding**: If the function is called as a method of an object (e.g., `obj.method()`), `this` refers to `obj`.
4.  **Default binding**: If none of the above apply (e.g., a standalone function call), `this` defaults to the global object (`window` in browsers, `global` in Node.js).
*   **`bind()`**: Returns a *new* function with a permanently bound `this` value.
*   **Re-binding**: Yes, the returned function can be re-bound using `bind()` again, but it is generally discouraged as it can lead to complex behavior.

**JS8**
*   **`WeakRef`**: A reference to a JavaScript object that does not prevent the garbage collector (GC) from collecting the object. It allows you to hold a reference to an object without creating a strong reference.
*   **`FinalizationRegistry`**: A mechanism that allows you to register a callback function to be executed when a specific object (registered via `WeakRef`) is garbage collected.
*   **Use Case**: Implementing memory cleanup or tracking objects that are about to be destroyed (e.g., cleaning up event listeners attached to a DOM element that is about to be removed).
*   **WeakMap Keys**: WeakMap keys must be objects because the GC needs to track whether the key object is still reachable. If the key object is garbage collected, the entry in the WeakMap is automatically removed. This prevents memory leaks by allowing the map to shrink when the associated objects are destroyed.

**JS9**
The V8 engine optimizes JS using several techniques:
*   **Hidden Classes (Maps)**: V8 tracks the structure (shape) of objects. Instead of treating every object as a unique entity, it assigns it a "hidden class" based on the order and type of its properties. This allows V8 to optimize property access (e.g., knowing that `obj.a` will always be a number).
*   **Inline Caching (IC)**: When a property is accessed repeatedly, V8 caches the location of that property access. Subsequent accesses can skip the full property lookup, leading to massive speed gains.
*   **Deoptimization**: If V8's assumptions about an object's structure (its hidden class) are violated—for example, if a property is added or its type changes—the engine must "deoptimize." It reverts to slower, safer execution paths to maintain correctness.
*   **Deoptimization Causes**: Changing the shape of an object (adding/deleting properties), or changing the type of a property (e.g., changing a property from a number to a string).

**JS10**
**Tree-shaking** is a build-time optimization technique that eliminates unused code (dead code) from the final bundle.
*   **How it works**: The bundler (like Webpack or Rollup) analyzes the dependency graph of the application. If an exported function or module is never imported or referenced, the bundler removes it from the output bundle.
*   **ES Modules (ESM)**: ESM uses static `import` and `export` syntax. Because these imports are static (known at compile time), the bundler can reliably trace the dependency graph and perform effective tree-shaking.
*   **CommonJS (CJS)**: CJS uses dynamic `require()` calls. Since `require()` can be called conditionally or based on runtime logic, the bundler cannot statically determine which parts of a module are actually used, making effective tree-shaking impossible.

**JS11**
*   **`null` vs `undefined`**:
    *   `undefined`: Means a variable has been declared but has not yet been assigned a value. It is the default value for uninitialized variables.
    *   `null`: Is an assignment value. It explicitly means "no value" or "empty." It must be assigned manually.
*   **`==` vs `===`**:
    *   `==` (Loose equality): Performs type coercion. It checks if the values are equal after converting them to a common type. (e.g., `0 == false` is true).
    *   `===` (Strict equality): Checks for both value and type equality without performing type coercion. (e.g., `0 === false` is false).
*   **Nullish Coalescing (`??`)**: Returns the right-hand operand only if the left-hand operand is `null` or `undefined`. It specifically ignores `0` and `""` (empty string).
*   **Optional Chaining (`?.`)**: Allows you to read the value of a property deep within an object without having to explicitly check if every intermediate property exists. If any property in the chain is `null` or `undefined`, the expression short-circuits and returns `undefined` instead of throwing an error.

**JS12**
*   **`map()`**: Creates a new array populated with the results of calling a provided function on every element in the calling array. It always returns a new array of the same length.
*   **`filter()`**: Creates a new array with all elements that pass the test implemented by the provided function. It returns a new array whose length may be shorter than the original.
*   **`reduce()`**: Executes a reducer function on each element of the array, resulting in a single output value.
*   **`reduce()` with Initial Value**: The initial value acts as the starting accumulator value. If provided, the callback starts iterating from the first element. If not provided, the first element of the array is used as the initial accumulator, and iteration starts from the second element.
*   **`flatMap()`**: Combines `map()` and `flat()` into one operation. It maps each element using a mapping function, and then flattens the result into a new array by one level. It is useful when your mapping function might return an array, and you want the final result to be a single, flat array.

**JS13**
*   **Template Literals**: Strings enclosed by backticks (`` ` ``). They allow for embedded expressions using `${expression}` and support multi-line strings without needing `\n`.
    *   *Example*: `` `Hello, ${name}. You are ${age} years old.` ``
*   **Tagged Templates**: A function that is executed before the template literal is converted into a string. The function receives the string parts (the static text) and the interpolated values (the expressions) as arguments.
*   **Tagged Template Example (HTML Escaping)**:
    ```javascript
    function escapeHtml(strings, ...values) {
      let result = strings[0];
      for (let i = 0; i < values.length; i++) {
        // Simple escaping logic
        const escapedValue = String(values[i]).replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;");
        result += escapedValue;
        result += strings[i + 1];
      }
      return result;
    }
    const userInput = "<script>alert('xss')</script>";
    const safeHtml = escapeHtml`<div>User input: ${userInput}</div>`;
    // safeHtml will contain the escaped characters.
    ```

**JS14**
**Destructuring** is a syntax that allows you to unpack values from arrays or properties from objects into distinct variables.
*   **Object Destructuring**: Extracts properties from an object into variables using the property name.
    *   *Example*: `const { name, age } = user;`
*   **Array Destructuring**: Extracts values from an array into variables based on position.
    *   *Example*: `const [first, second] = myArray;`
*   **Default Values**: Allows you to assign a default value if the property/element is missing or `undefined`.
    *   *Example*: `const { city = 'Unknown' } = user;`
*   **Renaming**: Allows you to extract a property but assign it to a different variable name.
    *   *Example*: `const { userEmail: email } = user;`
*   **Rest Operator (`...`)**: When used in destructuring, it collects all remaining, unassigned properties/elements into a new array.
    *   *Example*: `const { id, ...rest } = user;` (`rest` will be an object containing all other properties).

**JS15**
*   **`for...in`**: Iterates over the *enumerable properties* of an object. It iterates over keys (property names).
*   **`for...of`**: Iterates over the *values* of an iterable object (like Arrays, Maps, Sets, Strings).
*   **Iteration**:
    *   `for...in` iterates over keys (e.g., `for (const key in obj)`).
    *   `for...of` iterates over values (e.g., `for (const value of arr)`).
*   **Avoiding `for...in` on Arrays**: `for...in` iterates over all enumerable properties, including inherited properties and properties added to the prototype chain. This can lead to unexpected iteration order and include non-index properties, making it unreliable for array traversal. Always use `for...of` or `Array.prototype.forEach()` for arrays.

**JS16**
**Generics** allow you to write components (functions, classes) that can work over a variety of types while still maintaining type safety. They allow you to abstract over types.
*   **Generic Constraints (`extends`)**: Restricts the types that a generic type parameter can be. This ensures that the generic type has certain required properties or methods.
    *   *Example*: `function identity<T extends { id: number }>(arg: T): T { return arg; }` (T must have an `id` property).
*   **Conditional Types (`T extends U ? X : Y`)**: Allows you to define a type that resolves to one of two types based on a condition.
    *   *Example*: `type IsString<T> = T extends string ? true : false;`
*   **`infer` Keyword**: Used within conditional types to *infer* a type from a pattern match. It allows you to extract a type from a complex structure.
    *   *Example*: `type GetArrayType<T> = T extends (infer U)[] ? U : never;` (If T is an array, extract the type U of its elements).

**JS17**
*   **Module System**: The mechanism by which code dependencies are managed and modules are loaded.
*   **CommonJS (CJS)**: Synchronous module system used primarily by Node.js. It uses `require()` to import and `module.exports` to export. It is dynamic.
*   **ES Modules (ESM)**: Standardized module system (`import`/`export`). It is static, meaning the dependencies are known at compile time.
*   **Node.js Handling**: Node.js supports both. By default, `.js` files are CJS. Using `"type": "module"` in `package.json` tells Node.js to treat `.js` files as ESM, allowing the use of `import`/`export`.
*   **`"type": "module"`**: This field signals to Node.js that the project should use the ES Module specification, enabling static `import` syntax and other ESM features.

**JS18**
**Structural Type System**: TypeScript checks types based on the *shape* of the object, not its name. If two objects have the same structure (same properties and types), TypeScript considers them compatible, even if they were defined with different names.
*   **Excess Property Checks**: A compiler option that prevents you from adding properties to an object that were not defined in its type definition. This helps prevent accidental pollution of objects.
*   **`extends` vs `satisfies`**:
    *   `extends`: Used for inheritance. It dictates that the derived type *is* a subtype of the base type.
    *   `satisfies`: Used for type checking without changing the type. It asserts that a value conforms to a type, but the value retains its original, more specific type.
    *   *Example*: `const data: MyType = { ... };` (Type check). `class Child extends Parent {}` (Inheritance).
*   **Variance (in, out)**: Defines how subtyping works with generic types.
    *   **`in` (Contravariance)**: A type is "more general" if it accepts a wider range of types. Used for input parameters (e.g., function arguments).
    *   **`out` (Covariance)**: A type is "more general" if it produces a wider range of types. Used for return values.

**JS19**
*   **`Proxy`**: Allows you to create an object that wraps another object and intercepts fundamental operations (like property lookup, assignment, function calls) before they reach the target object.
*   **`Reflect`**: Provides methods that mirror the operations intercepted by `Proxy`. It is the standard way to implement the logic inside a `Proxy` handler.
*   **Interception**:
    *   *Property Access*: Intercepted by the `get` trap.
    *   *Assignment*: Intercepted by the `set` trap.
    *   *Function Calls*: Intercepted by the `apply` trap.
*   **Practical Example (Validation)**:
    ```javascript
    const handler = {
      set(target, prop, value) {
        if (prop === 'age' && typeof value !== 'number') {
          throw new TypeError('Age must be a number.');
        }
        return Reflect.set(target, prop, value);
      }
    };
    const user = {};
    const proxiedUser = new Proxy(user, handler);
    // proxiedUser.age = "twenty"; // Throws TypeError
    ```

**JS20**
*   **`SharedArrayBuffer`**: A raw binary data buffer that can be shared between multiple execution contexts (like Web Workers). It allows multiple threads to access the same memory space.
*   **`Atomics`**: A set of methods that operate on `SharedArrayBuffer` data in a thread-safe manner. They ensure that operations (like reading or writing a value) are atomic—meaning they complete entirely without interruption from other threads.
*   **Communication**: Web Workers communicate using shared memory by accessing the same `SharedArrayBuffer`.
*   **Ordering Guarantees**: `Atomics` operations provide strict ordering guarantees, preventing race conditions. For example, `Atomics.store()` guarantees that the value is visible to all other threads before any subsequent memory operations.
*   **`Atomics.wait/notify`**: These methods allow threads to block (wait) until a specific condition is met, preventing busy-waiting.
    *   `Atomics.wait(typedArray, index, expectedValue)`: Blocks the current thread until the value at `index` is no longer `expectedValue`, or until a timeout occurs.
    *   `Atomics.notify(typedArray, index, count)`: Wakes up a specified number of threads that are currently waiting on that specific index.

## Bash (20 questions)

**B1**
*   **`$@`**: Expands to all positional parameters, correctly quoted. When used in a loop, it expands to separate arguments, preserving spaces and special characters.
    *   *Example*: `for arg in "$@"; do echo "$arg"; done`
*   **`$*`**: Expands to all positional parameters as a single string. If used without quotes, it expands to a single string separated by the first character of the `IFS` variable (usually a space).
*   **`"$@"` vs `"$*"`**:
    *   `"$@"`: Expands to separate, quoted arguments. This is the safest way to iterate over arguments, ensuring arguments containing spaces are treated as single units.
    *   `"$*"`: Expands to a single string, which is dangerous if arguments contain spaces.

**B2**
`set -euo pipefail` is a set of robust scripting options:
*   **`-e` (errexit)**: Causes the script to exit immediately if any command exits with a non-zero status (i.e., fails). This prevents the script from continuing with bad state.
*   **`-u` (nounset)**: Treats unset variables as an error and exits. This prevents silent bugs caused by typos in variable names.
*   **`-o pipefail`**: Causes a pipeline to return a non-zero exit status if *any* command in the pipeline fails, not just the last one. This is crucial for reliable data processing.

**B3**
*   **`$(command)` (Command Substitution)**: Executes the `command` and replaces the substitution with the standard output (stdout) of that command. This output is treated as a string or argument.
    *   *Example*: `echo "The date is $(date +%Y-%m-%d)"`
*   **`command`**: Executes the command directly.
*   **`$((expression))` (Arithmetic Expansion)**: Performs integer arithmetic. The result is the numerical value of the expression.
    *   *Example*: `echo $((10 + 5 * 2))`
*   **`expr`**: An external utility used for evaluating expressions. It is less efficient than `$(( ))` and requires spaces around operators.
    *   *Example*: `expr 10 + 5 * 2`

**B4**
**Process Substitution (`<(command)`)**: This feature allows the output of a command to be treated as a temporary file path. This is extremely useful when a command needs to be passed to another command that expects a file path (like `diff` or `sort`).
*   **Practical Example with `diff`**:
    ```bash
    # Compare the output of 'ls -l' with the output of 'find . -name "*.txt"'
    diff <(ls -l) <(find . -name "*.txt")
    ```
    Without process substitution, you would have to pipe the output to a temporary file and then use the file path, which is cumbersome.

**B5**
The safest way is to use a `while read` loop combined with `find` and `find -print0` (or `find -print0` piped to `xargs -0`).
*   **Dangerous `for f in $(ls)`**: This is dangerous because:
    1.  `ls` output is not guaranteed to be sorted or consistent.
    2.  If filenames contain spaces or newlines, the shell splits them based on the `IFS` variable, treating parts of a single filename as multiple arguments.
*   **Safe Method**:
    ```bash
    find . -type f -print0 | while IFS= read -r -d $'\0' filename; do
        echo "Processing: $filename"
    done
    ```
    The `-print0` and `read -d $'\0'` ensure that filenames containing spaces, newlines, or special characters are handled correctly as single units.

**B6**
*   **Here Document (`<<EOF`)**: Allows you to pass multiple lines of input (a block of text) to a command. The input is read until the delimiter (e.g., `EOF`) is encountered on a line by itself.
    *   *Example*: `cat <<EOF > file.txt\nLine 1\nLine 2\nEOF`
*   **Here String (`<<<`)**: Passes a single string as standard input to a command. It is used for short, single-line inputs.
    *   *Example*: `grep "pattern" <<< "This is the input line"`
*   **`<<-EOF` (Dashed Delimiter)**: This variation allows the here document to handle lines that start with a tab character. By default, bash treats lines starting with a tab as part of the content, but `<<-` strips leading tabs, making it useful for indented code blocks (like configuration files).

**B7**
*   **`cmd > file 2>&1`**: Redirects stdout (`> file`) and then redirects stderr (`2>&1`) to the same location as stdout (`file`). **Result**: Both stdout and stderr go into `file`.
*   **`cmd 2>&1 > file`**: Redirects stderr (`2`) to stdout (`&1`) *first*, and then redirects the combined stdout/stderr stream (`> file`) to the file. **Result**: Both stdout and stderr go into `file`.
*   **`cmd &> file`**: (Bash 4+ shorthand) A combined redirection that redirects both stdout and stderr to the specified file.
*   **Why the first two are different (in theory, though often equivalent in modern shells)**: The order matters because of how redirection is processed. In `cmd 2>&1 > file`, the redirection to `file` happens *after* the stderr redirection, meaning the file descriptor 1 (stdout) is redirected *before* the file descriptor 2 (stderr) is redirected to it. In `cmd > file 2>&1`, stdout is redirected first, and then stderr is redirected to the *current* stdout (which is `file`). While modern shells often handle this gracefully, the explicit order in `> file 2>&1` is the canonical way to ensure both streams go to the file.

**B8**
A robust lock file function requires atomic creation and cleanup handlers.
```bash
LOCK_FILE="/tmp/my_script.lock"

acquire_lock() {
    # Use mkdir for atomic locking
    if mkdir "$LOCK_FILE" 2>/dev/null; then
        echo "Lock acquired."
        return 0
    else
        echo "Lock already held."
        return 1
    fi
}

cleanup() {
    echo "Releasing lock..."
    rmdir "$LOCK_FILE" 2>/dev/null
}

# Trap SIGTERM and EXIT to ensure cleanup runs
trap cleanup EXIT SIGTERM SIGINT

if acquire_lock; then
    # Main script logic here
    echo "Running critical task..."
    sleep 5
else
    exit 1
fi
```
**Why `mkdir` is preferred**: `mkdir` is an atomic operation. When you attempt to create a directory, the operating system ensures that only one process can successfully create it at a given moment. If the directory already exists, the command fails (non-zero exit code), which is the desired behavior for detecting a lock. File creation (`touch`) is not atomic; two processes could simultaneously check for existence and then create the file.

**B9**
*   **Single Quotes (`'...'`)**: Literal string. All characters inside are treated literally, including special characters like `$`, `\`, and backticks. No variable expansion occurs.
    *   *Example*: `echo 'The price is $10'` (Output: The price is $10)
*   **Double Quotes (`"..."`)**: Interpolated string. Allows variable expansion (`$VAR`) and command substitution (`$(cmd)`).
    *   *Example*: `echo "The price is $PRICE"` (If PRICE=10, Output: The price is 10)
*   **No Quotes**: Word splitting. The shell splits the string into arguments based on the characters in the `IFS` (Internal Field Separator) variable (default: space, tab, newline).
    *   *Example*: `echo $VAR` (If VAR="hello world", output is "hello world" but treated as two arguments).

**B10**
*   **File Exists**: `[ -e filename ]` or `[[ -e filename ]]`
*   **Is a Directory**: `[ -d filename ]` or `[[ -d filename ]]`
*   **Is Readable**: `[ -r filename ]` or `[[ -r filename ]]`
*   **`[ ]` (test)**: The traditional POSIX test command. It is simple, widely compatible, and uses single brackets.
*   **`[[ ]]`**: Bash keyword (not a command). It offers extended features, such as regex matching (`=~`), globbing, and better handling of word splitting. It is generally preferred in modern Bash scripting for its robustness and features.

**B11**
*   **`$?`**: The exit status of the most recently executed foreground command (0 means success, non-zero means failure).
*   **`$$`**: The Process ID (PID) of the current shell or script.
*   **`$!`**: The PID of the most recently backgrounded job (a job started with `&`).
*   **`$#`**: The number of positional arguments passed to the script.
*   **Use Cases**:
    *   `$?`: Checking if a command succeeded (`if [ $? -ne 0 ]`).
    *   `$$`: Logging the PID for debugging/logging.
    *   `$!`: Monitoring a background process.
    *   `$#`: Validating required input arguments.

**B12**
*   **Defining Functions**:
    ```bash
    # Style 1 (POSIX/Standard)
    foo() {
        echo "Hello"
    }

    # Style 2 (Bash specific)
    function foo_alt {
        echo "Hello"
    }
    ```
*   **Difference**: Function style 1 (`foo() {}`) is more portable and standard. Style 2 (`function foo {}`) is Bash-specific. Functionally, they are nearly identical in modern Bash.
*   **Returning Values**: Bash functions do not return values like C/Python. They return an *exit status* (0-255) via `$?`. To return data, you must print the data to stdout and capture it using command substitution.
    *   *Example*: `result=$(my_function)`

**B13**
*   **`PATH`**: An environment variable that specifies a list of directories the shell searches through when a command is executed.
*   **Command Resolution**: When you type a command (e.g., `ls`), the shell searches the directories listed in `$PATH` sequentially until it finds an executable file with that name.
*   **Builtin vs External**:
    *   **Builtin**: Commands implemented directly within the shell itself (e.g., `cd`, `echo`, `read`). They are faster because they don't require spawning a new process.
    *   **External**: Standalone executable programs located in directories listed in `$PATH` (e.g., `grep`, `awk`, `ls`).
*   **Checking**: Use `type command_name`.
    *   *Example*: `type cd` (Output: `cd is a shell builtin`)
    *   *Example*: `type grep` (Output: `grep is /bin/grep`)

**B14**
*   **`trap`**: A shell built-in command that allows you to catch and handle signals sent to the shell or script. It executes a specified command or function when a signal is received.
*   **Cleanup Handlers**:
    *   `EXIT`: Runs when the script exits, regardless of success or failure.
    *   `ERR`: Runs when a command exits with a non-zero status (if `set -e` is active).
    *   `INT`: Catches the interrupt signal (usually Ctrl+C).
    *   `TERM`: Catches the termination signal (used by process managers like `systemd`).
*   **Execution Order**: When multiple signals arrive, the shell handles them based on its internal signal handling mechanism. If a signal handler is defined, it runs. If multiple signals arrive rapidly, the shell processes them sequentially, but the order of execution of the *handlers* is determined by the order they were trapped.

**B15**
*   **`xargs` vs Command Substitution**:
    *   **Command Substitution**: Executes a command and captures its output as a single string/argument. This is often limited by the shell's argument length limits and is poor for handling special characters.
    *   **`xargs`**: Takes input from standard input and builds and executes command lines from that input. It is designed to handle large lists of items efficiently.
*   **Handling Spaces/Newlines**:
    ```bash
    find . -type f -print0 | xargs -0 -I {} echo "Processing {}"
    ```
    *   `-print0` (find): Outputs filenames separated by null characters (`\0`).
    *   `xargs -0`: Reads the input separated by null characters.
    *   `-I {}`: Specifies a replacement string (`{}`) for each input item.
*   **`xargs -P`**: Runs `xargs` in parallel. `-P N` specifies that up to $N$ processes should run concurrently, significantly speeding up I/O-bound tasks.

**B16**
*   **Bash Arrays**: Indexed arrays (like C arrays). They are zero-indexed.
    *   *Declaration*: `my_array=(item1 item2 item3)`
    *   *Append*: `my_array+=("new_item")`
    *   *Iteration*: `for item in "${my_array[@]}"; do ...`
    *   *Length*: `${#my_array[@]}`
*   **Associative Arrays (Hash Maps)**: Key-value maps. They are indexed by strings (keys) rather than sequential integers.
    *   *Declaration*: `declare -A my_map`
    *   *Assignment*: `my_map["key"]=value`
    *   *Iteration*: `for key in "${!my_map[@]}"; do ...`
    *   *Length*: `${#my_map[@]}`
*   **Differences**: Arrays are ordered and indexed numerically; Associative arrays are unordered and indexed by arbitrary strings.

**B17**
*   **Subshell (`(...)`)**: A separate, isolated shell process. Any variables set or modified inside the subshell are *not* visible to the parent shell after the subshell exits.
*   **Group Command (`{ ...; }`)**: Executes commands in the current shell environment. Variables modified inside the group command *are* visible to the parent shell.
*   **Exit Codes**: Both return an exit code, but the group command's exit code is the exit code of the *last* command executed within the group.
*   **Piping into `while` loop**: When you pipe output into a `while read` loop, the loop runs in a subshell. Any variable changes made inside that subshell are lost when the subshell exits, meaning the parent shell's variables remain unchanged.
    *   *Fix*: Use process substitution or redirect the loop to run in the current shell context.

**B18**
*   **Signals and Job Control**: Signals are asynchronous notifications sent to a process. Job control allows the shell to manage background processes (jobs).
*   **Signal Differences**:
    *   **SIGINT (2)**: Interrupt signal (usually Ctrl+C). Used for graceful interruption.
    *   **SIGTERM (15)**: Termination signal. A polite request for the process to shut down gracefully.
    *   **SIGHUP (1)**: Hangup signal. Often used to tell a daemonized process to reload its configuration without stopping.
    *   **SIGKILL (9)**: Immediate, uncatchable termination. The OS kills the process instantly; no cleanup is possible.
*   **Graceful Shutdown**: To handle graceful shutdown, you must use `trap` to catch `SIGINT` and `SIGTERM`. In the handler, you should signal background processes to stop, wait for them to finish (using `wait`), and then exit cleanly.

**B19**
```bash
# 1. Split the large file into chunks
split -l 10000 large_log.txt chunk_

# 2. Define the processing function
process_chunk() {
    CHUNK_FILE=$1
    echo "Processing $CHUNK_FILE..."
    # Simulate processing and error check
    if grep -q "ERROR" "$CHUNK_FILE"; then
        echo "ERROR found in $CHUNK_FILE" >&2
        return 1 # Signal failure
    fi
    # Output processed results to a new file
    grep "SUCCESS" "$CHUNK_FILE" > "processed_$(basename $CHUNK_FILE).txt"
    return 0
}

# 3. Process chunks in parallel
# We use a loop and wait to track errors
for chunk in chunk_*; do
    process_chunk "$chunk" &
done

# Wait for all background jobs to finish
wait

# 4. Check exit status of all jobs (requires careful tracking)
# A simpler approach is to check the return code of the last job, 
# but for robust error handling, we'd need to track PIDs and their statuses.

# 5. Merge results
cat processed_*.txt > final_results.txt
```
**Performance Trade-offs**: Parallel processing (`xargs -P` or background jobs `&`) significantly reduces wall-clock time for I/O-bound tasks (like reading/writing logs) by utilizing multiple CPU cores. However, it introduces overhead from process creation and context switching.
**Error Propagation**: In the example above, the `wait` command waits for all jobs, but it only returns the status of the *last* job. To handle errors robustly, you must check the exit status of each background PID individually using `wait $PID` or use a more complex job control array to track return codes.

**B20**
*   **`exec` vs Normal Command**:
    *   **Normal Command**: Spawns a new process. The shell remains active, and the new process runs independently.
    *   **`exec`**: Replaces the current shell process image with the new command. The shell process is entirely replaced; it does not continue running after the command finishes.
*   **File Descriptor Manipulation**: `exec` is used to manipulate file descriptors (FDs).
    *   `exec 3>file`: Opens a file and assigns it to file descriptor 3.
    *   `exec 3>&-`: Closes file descriptor 3.
*   **Bash Coprocess**: A coprocess allows a shell script to run a background command and communicate with it using standard input/output streams, treating it like a child process that is tightly coupled to the parent.
    *   **Use Case**: When you need continuous, bidirectional communication with a background process (e.g., streaming data back and forth, or running a long-running server process that needs to be controlled by the parent script).
    *   *Implementation*: `coproc cmd_name <args>` followed by `read` or `echo` to communicate.

## PowerShell (20 questions)

**PS1**
*   **`Write-Output`**: Sends objects to the pipeline. This is the standard, preferred way to output data in PowerShell. It allows the data to be processed by subsequent cmdlets.
*   **`Write-Host`**: Writes text directly to the console (the host). It bypasses the pipeline and is used for displaying user-facing messages or status updates.
*   **Why it matters**: If you use `Write-Host`, the data is just text on the screen and cannot be captured by variables or piped to other cmdlets. If you use `Write-Output`, the data is an object that can be manipulated by the pipeline.

**PS2**
*   **PowerShell Pipeline**: A mechanism where the output objects of one cmdlet are automatically passed as input objects to the next cmdlet. This is object-oriented, unlike Unix pipes which pass raw text.
*   **`ForEach-Object` (or `%`)**: A cmdlet that iterates over objects passed through the pipeline. It is designed to process objects and can modify them or output new objects.
*   **`foreach` statement**: A standard programming construct used to iterate over collections (arrays, lists). It is used when you have a collection in memory and want to execute a block of code for each item.
*   **When to use**:
    *   **`ForEach-Object`**: When processing objects coming *from the pipeline* (e.g., `Get-Service | ForEach-Object { ... }`).
    *   **`foreach`**: When iterating over a collection already stored in a variable (e.g., `foreach ($item in $myArray) { ... }`).

**PS3**
*   **`[PSCustomObject]`**: A type used to dynamically create a custom object on the fly. It allows you to define properties and values for a single, specific object instance.
    *   *Example*: `[PSCustomObject]@{ Name = "Alice"; Age = 30 }`
*   **`[hashtable]`**: A collection type that stores key-value pairs, similar to a dictionary or map. It is a collection of properties, not a single object instance.
    *   *Example*: `$data = @{ Name = "Alice"; Age = 30 }`
*   **When to use**:
    *   **`[PSCustomObject]`**: When you need a single, structured object instance that can be passed through the pipeline or returned by a function.
    *   **`[hashtable]`**: When you need a flexible collection of key-value pairs, often used for configuration or parameter passing (splatting).
*   **Conversion**:
    *   *Hashtable to CustomObject*: You can iterate over the hashtable keys and properties to construct a custom object.
    *   *CustomObject to Hashtable*: You can use `[hashtable]@{}`, then iterate over the object's properties to populate the hashtable.

**PS4**
*   **Error Handling**: PowerShell distinguishes between two types of errors:
    *   **Non-Terminating Errors**: Errors that are expected or recoverable (e.g., trying to access a non-existent registry key). The script continues execution.
    *   **Terminating Errors**: Errors that are critical and prevent the script from continuing (e.g., a required file is missing).
*   **Interaction**:
    *   **`-ErrorAction`**: Specifies how a specific cmdlet should handle errors (e.g., `Stop`, `Continue`, `SilentlyContinue`).
    *   **`$ErrorActionPreference`**: A global variable that sets the default behavior for *all* cmdlets in the current scope.
    *   **`try/catch`**: A structured block that allows you to explicitly trap and handle terminating errors. The `catch` block only executes if a terminating error occurs.
*   *Example*: `Get-Item -Path "nonexistent" -ErrorAction Stop | catch { Write-Error $_.Exception.Message }`

**PS5**
*   **Splatting (`@params`)**: The practice of passing a hashtable to a cmdlet parameter that accepts a parameter list. This allows you to pass a dynamic set of parameters to a cmdlet, making scripts reusable and cleaner.
*   **Example**:
    ```powershell
    $params = @{
        Path = "C:\Logs"
        Filter = "*.log"
        Force = $true
    }
    Get-ChildItem @params
    ```
*   **Difference from Hashtable as Single Parameter**: If you pass a hashtable as a single parameter, the cmdlet treats the entire hashtable as a single object value for that parameter. Splatting unpacks the hashtable, treating each key-value pair as a separate parameter assignment.

**PS6**
*   **PowerShell Remoting**: Allows execution of PowerShell commands and scripts on remote computers.
*   **`Invoke-Command -ComputerName`**: Executes a script block or command on a remote computer. It is typically used for one-off commands or short script executions. It is the most common method.
*   **`Enter-PSSession`**: Establishes an interactive, persistent session on a remote computer. Once entered, you are operating directly within the remote machine's PowerShell environment until you exit.
*   **Protocol**: PowerShell Remoting primarily uses **WS-Management (WinRM)** on Windows systems. On Linux/Unix, it can use SSH. WinRM is the standard protocol for managing Windows servers remotely.

**PS7**
*   **Type System/Pipeline Behavior**: PowerShell is object-oriented. When a function returns a collection (like an array), it returns an array of objects.
*   **The Issue**: When you use `return $result` where `$result` is an array, PowerShell often treats the array as a single object *if* the array is implicitly cast or if the function is not explicitly designed to output multiple objects.
*   **Code Analysis**:
    ```powershell
    function Get-Items {
        $result = @()
        $result += "one"
        return $result
    }
    $x = Get-Items
    $x.GetType().Name  # Output: System.Object (or System.Array, depending on context, but often treated as a single object)
    ```
    The issue is that PowerShell often wraps the returned array in a single object wrapper, making it appear as a single object rather than an array of strings.
*   **Zero Items**: If the function returns 0 items (i.e., `$result` is empty), the function returns `$null` or an empty array, which is generally handled correctly.
*   **Correct Pattern**: To ensure the function outputs multiple objects that can be piped, use `Write-Output` inside the function, or use `return` on each item individually.
    ```powershell
    function Get-ItemsCorrect {
        "one" | Write-Output
        "two" | Write-Output
    }
    ```

**PS8**
*   **`[scriptblock]`**: A block of code that can be passed as a parameter. It is essentially a function definition that is not executed until called.
*   **Function vs Scriptblock**: A function is a named, callable entity. A scriptblock is a piece of code that can be passed around and executed later.
*   **Passing to Remote Session**: You pass a scriptblock to `Invoke-Command` using the `-ScriptBlock` parameter.
*   **Double-Hop Problem**: When running a scriptblock remotely, variables defined in the local scope are not automatically available in the remote scope. The "double-hop" refers to the complexity of ensuring variables are correctly serialized and available for execution on the remote machine.
*   **Solving it**:
    1.  **`Invoke-Command -ArgumentList`**: Pass variables explicitly as arguments to the remote scriptblock.
    2.  **`CredSSP`**: Used for complex authentication scenarios where the remote session needs to assume the identity of the local user.

**PS9**
*   **`@()` vs `[array]`**:
    *   **`@()`**: An empty array literal. It is the most common and concise way to create an empty array.
    *   **`[array]`**: A type accelerator. It forces a variable to be of the array type.
*   **Forcing Single Result into Array**: Use the array constructor or the pipeline:
    ```powershell
    $singleItem = "Hello"
    $array = @($singleItem) # Creates an array containing one item
    ```
*   **Indexing `$null` vs Empty Array**:
    *   **`$null`**: Indexing `$null` throws a runtime error because it is not an object/collection.
    *   **Empty Array (`@()`)**: Indexing an empty array (e.g., `$myArray[0]`) returns `$null` without throwing an error.

**PS10**
*   **Comparison Operators**:
    *   `-eq`: Equal (case-insensitive by default).
    *   `-ne`: Not equal.
    *   `-like`: Wildcard matching (uses `*` and `?`).
    *   `-match`: Regular expression matching.
    *   `-contains`: Checks if an array contains a specific value.
    *   `-in`: Checks if a value is present within a collection.
*   **Case-Sensitive Variants**:
    *   `-ceq`: Case-sensitive equality.
    *   `-clike`: Case-sensitive wildcard matching.
    *   `-cmatch`: Case-sensitive regex matching.
*   **`-contains` vs `-in`**:
    *   **`-contains`**: Used to check if a *specific value* exists within a collection (e.g., `$list -contains "apple"`).
    *   **`-in`**: Used to check if a *single value* is contained within a list of possible values (e.g., `"apple" -in $allowedFruits`).

**PS11**
*   **PowerShell Module**: A collection of cmdlets, functions, variables, and scripts that provide functionality to the PowerShell environment.
*   **Module Types**:
    *   **Script Module (`.psm1`)**: A script file containing functions and code. It is the most common type.
    *   **Manifest Module (`.psd1`)**: A metadata file that describes the module (version, required dependencies, versioning). It is often used alongside a `.psm1`.
    *   **Binary Module**: A compiled module (e.g., C# assembly) that provides high performance.
*   **`Import-Module`**: Loads the module's definitions (functions, cmdlets) into the current session's scope, making them available for use.

**PS12**
*   **String Interpolation**: Allows embedding variables and expressions directly into a string using double quotes (`"`).
    *   *Example*: `"The value is $variable and the result is $((2+2))"`
*   **`"..."` vs `'...'`**:
    *   **`"..."` (Double Quotes)**: Allows variable interpolation and command substitution.
    *   **`'...'` (Single Quotes)**: Literal string. No interpolation or expansion occurs.
*   **Including Expressions**: Expressions are enclosed in double parentheses `$(...)` or evaluated directly within the string using `$()` syntax.
*   **Here-String (`@"`...`"@`)**: A multi-line string literal that supports interpolation. It is useful for defining large blocks of text or configuration files.
    *   *Example*: `@"Line 1`n`Line 2"`

**PS13**
*   **`Get-Member`**: A cmdlet used to retrieve the properties, methods, and other characteristics of an object. It is essential for introspection.
*   **Exploring Objects**: You pipe objects through `Get-Member` to see what capabilities they have.
*   **Properties, Methods, NoteProperties**:
    *   **Properties**: Attributes or data fields of an object (e.g., `Name`, `Size`).
    *   **Methods**: Functions that can be called on an object (e.g., `.Calculate()`, `.ToString()`).
    *   **NoteProperties**: Properties that are metadata about the object (e.g., `PSIsContainer`).
*   **`Select-Object` vs `Where-Object`**:
    *   **`Select-Object`**: Filters or selects *which properties* are displayed or passed down the pipeline. It changes the structure of the object.
    *   **`Where-Object`**: Filters *which objects* are passed down the pipeline based on a condition. It does not change the object structure.

**PS14**
*   **PowerShell Classes (v5+)**: Classes are object-oriented constructs that allow you to define blueprints for creating objects, encapsulating data (properties) and behavior (methods).
*   **Difference from C# Classes**: While PowerShell classes are object-oriented, they are generally less strict and more dynamic than C# classes. They are designed to integrate seamlessly with the dynamic nature of the PowerShell pipeline.
*   **Limitations**: They support inheritance and interfaces, but the implementation is often more flexible and less rigid than the strict compile-time checks of C#.
*   **Class vs Function**:
    *   **Function**: Best for encapsulating logic and performing a specific task (e.g., `Get-Service`).
    *   **Class**: Best for modeling a real-world entity or stateful object that needs to maintain internal data and behavior over time (e.g., a `User` object).

**PS15**
*   **`CmdletBinding` and Advanced Functions**: `CmdletBinding` is a attribute that allows a function to behave like a true cmdlet. This enables advanced features like parameter validation, pipeline support, and standard cmdlet behavior.
*   **`[CmdletBinding()]`**: When placed on a function, it enables the function to accept standard parameters (like `-Verbose`, `-ErrorAction`, `-Confirm`) and handle pipeline input.
*   **Advanced Features**:
    *   **`SupportsShouldProcess`**: Allows the cmdlet to ask the user for confirmation before performing a destructive action (e.g., `Confirm` parameter).
    *   **`DefaultParameterSetName`**: Defines the default set of parameters used when the cmdlet is called without specifying a parameter set.
    *   **`ValueFromPipeline`**: Tells the cmdlet that it can accept input objects from the pipeline and should process them.
*   **Blocks**:
    *   **`Begin`**: Runs once at the start of the cmdlet execution (setup).
    *   **`Process`**: Runs for every object received from the pipeline (the main work).
    *   **`End`**: Runs once at the end of the cmdlet execution (cleanup).

**PS16**
*   **PowerShell Providers System**: A unified abstraction layer that allows cmdlets (like `Get-ChildItem`) to interact with various data sources (FileSystem, Registry, Certificate Store, Environment) using a consistent interface.
*   **How `Get-ChildItem` works**: When you run `Get-ChildItem`, PowerShell checks the drive prefix (e.g., `C:`, `HKLM:`, `Cert:`) and routes the request to the corresponding provider module, which knows how to query that specific data source.
*   **Accessing Registry like File System**: You use the `Registry` provider.
    *   *Example*: `Get-ChildItem -Path "HKLM:\Software\Microsoft"`
    *   The `HKLM:` prefix tells PowerShell to use the Registry provider, which then translates the path into the appropriate registry key structure.

**PS17**
*   **Runspaces**: An isolated execution environment in PowerShell. A runspace is a container that holds the state of a PowerShell session, including loaded modules and variables.
*   **`[runspace]`**: A single, isolated execution environment.
*   **`[runspacepool]`**: A pool of runspaces. Instead of creating a new runspace for every task, the pool manages a set of pre-initialized runspaces, allowing tasks to be executed concurrently by borrowing an available runspace and returning it to the pool.
*   **Parallel Execution**:
    *   **`ForEach-Object -Parallel` (v7+)**: The modern, simpler way. It handles the runspace management internally, allowing you to write parallel code without manually managing pools.
    *   **Manual Runspace Management**: Required in older versions or for highly complex scenarios. You manually create, connect, and manage the lifecycle of `[runspace]` objects, often using a `[runspacepool]` to manage concurrency and resource usage.

**PS18**
*   **PSScriptAnalyzer**: A tool that enforces coding standards and best practices in PowerShell scripts. It analyzes code for potential bugs, performance issues, and adherence to style guides.
*   **Rules**: Specific checks defined by the analyzer (e.g., "Do not use `Write-Host` for output," "Always use `try/catch`").
*   **Severity Levels**: Rules are assigned severity (e.g., `Warning`, `Error`, `Information`). This allows developers to prioritize which issues to fix.
*   **Custom Rules**: Users can define their own rules to enforce organizational standards specific to their codebase.
*   **Suppression and CI/CD**:
    *   **Suppression**: Rules can be suppressed using comments (`# .SYSA_NOWARNINGS`) when a violation is intentional or unavoidable.
    *   **CI/CD Integration**: PSScriptAnalyzer is typically integrated into CI/CD pipelines (e.g., Azure DevOps, GitHub Actions) as a mandatory build step. If the analyzer finds rules above a certain severity threshold, the build fails, preventing non-compliant code from being merged.

**PS19**
*   **Scope Differences**:
    *   **`$using:` scope**: Used when passing variables to background jobs or `ForEach-Object -Parallel`. It allows the remote/parallel job to access the *current* scope's variables without needing to serialize them explicitly.
    *   **`$args/-ArgumentList`**: Used when passing variables to remote sessions (`Invoke-Command`). The variables must be explicitly passed as arguments to the remote scriptblock.
*   **Serialization Limits (CLIXML Depth)**: When running remote sessions, PowerShell serializes the scriptblock and its parameters into XML (CLIXML). This serialization has limits on complexity (e.g., maximum nesting depth). Complex, deeply nested objects or very large data structures can fail to serialize, leading to errors when the remote session cannot reconstruct the object structure.

**PS20**
*   **Desired State Configuration (DSC)**: A management framework that allows administrators to define the desired state of a system (e.g., "IIS must be installed," "Firewall port 80 must be open") and ensures the system remains in that state.
*   **Components**:
    *   **Configurations**: The high-level definition of the desired state (e.g., "Web Server Config").
    *   **Resources**: The specific components that implement the configuration (e.g., the `WindowsFeature` resource, the `Service` resource). Resources contain the logic to check the current state and apply changes.
    *   **Local Configuration Manager (LCM)**: The agent running on the target machine. It periodically checks the system against the defined configuration and remediates any drift.
*   **DSC Differences**:
    *   **Windows PowerShell**: DSC was a core feature, often requiring specific configuration files and LCM setup.
    *   **PowerShell 7+**: DSC functionality has been modernized and integrated into the broader PowerShell ecosystem, often simplifying the configuration syntax and improving cross-platform support.
*   **Modern Replacement**: While DSC is still used, modern Infrastructure-as-Code (IaC) tools like **Terraform** (for infrastructure provisioning) and **Ansible** (for configuration management) have largely replaced or augmented DSC, offering broader cloud and multi-platform support.
