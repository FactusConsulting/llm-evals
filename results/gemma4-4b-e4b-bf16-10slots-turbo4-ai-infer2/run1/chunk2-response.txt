## Kubernetes

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
K1: A Deployment manages stateless applications, ensuring a specified number of identical, interchangeable replicas are running. It treats pods as fungible. A StatefulSet, conversely, is designed for stateful applications (like databases). It provides stable, unique network identifiers and persistent storage for each pod, ensuring that if a pod dies and is recreated, it returns to the same identity and retains its data.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
K2: A ClusterIP Service exposes a stable internal IP address within the cluster. When traffic hits this IP, the underlying `kube-proxy` component (which runs on every node) intercepts the traffic. It uses iptables or IPVS rules to load balance incoming requests across the set of healthy backing pods associated with that Service, routing the traffic internally within the cluster.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
K3:
*   **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator (or dynamically) that is available to pods. It represents the actual storage resource (e.g., an AWS EBS volume).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a request object that specifies the required size and access mode (e.g., ReadWriteOnce).
*   **StorageClass:** A cluster-level definition that describes the "class" of storage (e.g., fast SSD, slow HDD). It defines the policies and parameters for dynamic provisioning.
*   **Relationship:** A PVC requests storage based on a specific StorageClass. The StorageClass then dictates how a PV is dynamically provisioned (or how an existing PV is matched) to fulfill the PVC's request.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**
K4:
1.  **Check Logs and Events:** Use `kubectl logs <pod-name>` to see the application's output and `kubectl describe pod <pod-name>` to check the Events section for immediate failure reasons (e.g., ImagePullBackOff, OOMKilled).
2.  **Check Container Status and Exit Code:** Verify the container's restart count and exit code using `kubectl get pod <pod-name>`. A non-zero exit code indicates an application failure.
3.  **Check Resource Constraints:** Review the pod's resource requests and limits against the node's capacity. If the pod is being killed due to exceeding memory limits (OOMKilled), this is the cause.
4.  **Check Configuration/Dependencies:** Verify that environment variables, ConfigMaps, or Secrets are correctly mounted and accessible. Also, check if external dependencies (databases, APIs) are reachable from the pod.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster. What happens to DNS resolution if the CoreDNS pods are down?**
K5: CoreDNS acts as the cluster's internal DNS service. It translates service names (e.g., `my-service.my-namespace.svc.cluster.local`) and pod IP addresses into resolvable names. If the CoreDNS pods are down, all internal DNS resolution within the cluster will fail. Pods will be unable to resolve other services or pods by name, leading to application failures, although external DNS resolution might still work if the node's `/etc/resolv.conf` points to an external resolver.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**
K6: The scheduler operates in two main phases:
1.  **Filtering (Predicates):** The scheduler first filters out nodes that cannot possibly run the pod. This is a hard requirement check. Factors include:
    *   *Resource Availability:* Does the node have enough CPU/Memory?
    *   *Taints/Tolerations:* Does the node have taints that the pod does not tolerate?
    *   *Node Selectors/Affinity:* Does the pod require a specific node label that the node lacks?
2.  **Scoring (Priorities):** From the remaining viable nodes, the scheduler assigns a score to each node based on how suitable it is. The node with the highest score is chosen. Factors include:
    *   *Least Requested Priority:* Preferring nodes with the least utilized resources.
    *   *Node Affinity/Anti-Affinity:* Preferring or avoiding nodes based on labels.
    *   *Spread Constraints:* Distributing pods across multiple nodes for high availability.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
K7:
*   **Scheduling:** Yes, the pod will likely be scheduled. The scheduler primarily considers the *requests* (256Mi) when determining if there is enough guaranteed capacity (3.5GB + 256Mi < 4GB).
*   **Runtime Behavior:** If the pod uses 600Mi, it will exceed its defined *limit* (512Mi). When a container exceeds its memory limit, the Linux kernel's OOM Killer will terminate the process, and Kubernetes will report the pod status as `OOMKilled`.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.**
K8:
1.  **External LB:** The request hits the external Load Balancer (LB), which routes traffic to the external IP of the Ingress Controller Pods.
2.  **Ingress Controller:** The LB forwards the traffic to the NGINX Ingress Controller Pod. The controller reads the Ingress resource rules (host/path matching) and determines which backend Service should receive the request.
3.  **Service:** The Ingress Controller forwards the request to the stable ClusterIP of the target Service.
4.  **Endpoints:** The Service object maintains a list of healthy backing Pod IPs via the Endpoints object. The Service uses this list to know where the application pods are.
5.  **kube-proxy/iptables:** The Service's ClusterIP is translated by `kube-proxy` rules (iptables/IPVS) running on the node. These rules perform the final load balancing, directing the traffic from the Service IP to one of the actual healthy Pod IPs.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
K9: A NetworkPolicy is a Kubernetes resource that defines rules for how groups of pods are allowed to communicate with each other and with external network endpoints.
*   **Default Behavior:** If no NetworkPolicy exists in a namespace, the default behavior is "allow all" traffic.
*   **When Applied:** When a NetworkPolicy is applied, the default behavior changes to "deny all" traffic *unless* explicitly allowed by a rule in the policy. If a policy selects certain pods, those pods will only communicate with endpoints explicitly permitted by the policy.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
K10:
*   **RollingUpdate:** The new version is gradually rolled out by replacing old pods with new ones incrementally. This minimizes downtime and allows for zero-downtime deployments.
*   **Recreate:** All old pods are terminated before any new pods are started. This results in a period of downtime during the deployment.
*   **When to Choose Recreate:** You would choose Recreate when the application is highly sensitive to state or when the new version requires a clean, fresh start that cannot be handled gracefully by a rolling replacement (e.g., major database schema migrations that require a full restart).

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
K11: A namespace is a mechanism to partition cluster resources, providing a scope for names and isolation. It allows multiple applications to run in the same cluster without interfering with each other. Default namespaces typically include `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
K12: `kubectl describe pod <name>` provides detailed metadata, status, and events for a specific pod. It is used for deep inspection and troubleshooting.
Three pieces of information it shows that `kubectl get pod` does not:
1.  **Events:** A chronological log of events related to the pod (e.g., scheduling, pulling image, readiness checks).
2.  **Detailed Status/Conditions:** Specific status fields like `Reason` and `Message` for conditions (e.g., `ImagePullBackOff`).
3.  **Resource Requests/Limits:** Detailed breakdown of requested and limited resources.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
K13: A ConfigMap is an API object used to store non-sensitive configuration data (like environment variables, configuration files, or command-line arguments) external to the container image.
Two methods to consume it:
1.  **Environment Variables:** Injecting key-value pairs from the ConfigMap directly into the container's environment variables.
2.  **Volume Mounts:** Mounting the ConfigMap as a volume inside the pod, allowing the application to read configuration files from a specific path in the filesystem.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
K14:
*   **ClusterIP:** Exposes the Service on an internal IP address only, accessible only from within the cluster. (Internal only).
*   **NodePort:** Exposes the Service on a static port on every Node's IP address. Traffic can be accessed from outside the cluster by hitting `<NodeIP>:<NodePort>`. (External, basic).
*   **LoadBalancer:** Provisions an external cloud load balancer (e.g., AWS ELB, GCP Load Balancer) that routes traffic to the Service. This is the standard way to expose services externally in cloud environments. (External, managed).

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
K15: A DaemonSet ensures that a copy of a pod runs on *every* eligible node in the cluster. Unlike a Deployment, which manages a fixed number of replicas, a DaemonSet ensures coverage. You would use a DaemonSet for cluster-level services that need to run locally on every node, such as log collectors (Fluentd/Logstash), monitoring agents (Prometheus Node Exporter), or network plugins (CNI agents).

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
K16:
*   **Taints:** A property applied to a Node that repels (or "taints") pods from being scheduled onto it unless the pod explicitly tolerates that taint.
*   **Tolerations:** A property defined on a Pod that allows it to be scheduled onto a Node that has a matching taint.
*   **Difference from Affinity:** Taints/Tolerations are about *exclusion* (repelling pods). Node Affinity is about *preference* (attracting pods).
*   **Practical Use Cases:**
    *   *Taints/Tolerations:* Isolating a node for specialized workloads (e.g., marking a GPU node with `dedicated=gpu:NoSchedule` so only GPU-aware pods can run there).
    *   *Node Affinity:* Ensuring a database pod is always scheduled on a node with specific storage characteristics (e.g., `topology.kubernetes.io/zone: us-west-2a`).

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
K17: An Operator is a method of packaging, deploying, and managing a complex application. It extends the Kubernetes API to manage complex, stateful applications.
*   **Difference from Controller:** A standard controller (like Deployment) watches a resource (e.g., Deployment) and ensures the current state matches the desired state (e.g., 3 replicas). An Operator, however, contains domain-specific logic (business knowledge) to manage the *lifecycle* of a complex application (e.g., a database).
*   **Problems Solved:** Operators automate operational tasks that are typically performed manually by human SREs (e.g., database backups, failover, schema migrations, scaling complex stateful services).

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
K18:
*   **Consistency Model:** Kubernetes uses etcd, which operates on a strong consistency model (Raft consensus algorithm). This ensures that all nodes agree on the state of the cluster (the desired state).
*   **Quorum Loss:** If the etcd quorum (majority) is lost, the cluster cannot reliably read or write state. The API server will fail to communicate with etcd, leading to the cluster becoming read-only or completely unavailable, as it cannot guarantee the integrity of the configuration.
*   **Recovery (2/3 lost):** If 2 out of 3 nodes are permanently lost, the remaining single node cannot form a quorum (which requires a majority, i.e., 2 out of 3). The cluster is effectively dead. Recovery requires restoring the etcd data onto a new, third node, typically by bootstrapping the new node using a snapshot taken from one of the lost nodes or by using specialized etcd recovery tools.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
K19:
*   **RBAC Mechanism:** RBAC defines permissions (verbs like `get`, `list`, `create`) on specific resources (like `pods`, `deployments`).
*   **Roles vs. ClusterRoles:**
    *   **Role:** Defines permissions within a specific namespace.
    *   **ClusterRole:** Defines permissions across the entire cluster.
*   **Bindings:**
    *   **RoleBinding:** Binds a Role to a user/group within a specific namespace.
    *   **ClusterRoleBinding:** Binds a ClusterRole to a user/group cluster-wide.
*   **Manifests (Developer needs read-only access to pods and logs in `dev` namespace):**

```yaml
# 1. Define the Role (Permissions within the 'dev' namespace)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader-role
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

---
# 2. Bind the Role to a user/group (assuming user 'developer')
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-reader-binding
  namespace: dev
subjects:
- kind: User
  name: developer # Replace with actual user/group name
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader-role
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
K20:
*   **The Problem (ndots):** The `ndots` setting in `/etc/resolv.conf` specifies the number of domain name separators (dots) that must appear in a hostname before the system assumes the query is a fully qualified domain name (FQDN). If `ndots` is set to 5, and the pod tries to resolve `api.service.local`, the system will assume this is a local hostname because it only has one dot, and it will query the local cluster DNS first. If the local DNS fails, it then queries external resolvers, leading to excessive, unnecessary queries and high latency.
*   **The Fix (dnsConfig):** You can override the DNS configuration using `dnsConfig` in the Pod specification. This allows you to explicitly define the `options` (including `ndots`) or provide a custom `nameservers` list, ensuring the pod uses the correct, optimized DNS settings.

## Development

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
D1:
*   **Merge:** Combines two divergent branches by creating a new "merge commit." It preserves the history exactly as it happened.
*   **Rebase:** Rewrites history by moving the starting point of a feature branch to the tip of another branch. It makes the history linear and clean, but it changes the commit SHAs.
*   **Avoid Rebasing:** You should *never* rebase commits that have already been pushed to a shared, public repository, as this rewrites history that other developers are relying on, causing significant synchronization issues and headaches.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
D2:
*   **TCP (Transmission Control Protocol):** A connection-oriented protocol. It guarantees reliable, ordered, and error-checked delivery through a three-way handshake. It is slower but reliable. (Protocols: HTTP/S, FTP).
*   **UDP (User Datagram Protocol):** A connectionless protocol. It sends packets without establishing a connection or guaranteeing delivery. It is faster but unreliable. (Protocols: DNS, VoIP/SIP).

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
D3: A race condition occurs when the output or result of a program depends on the sequence or timing of uncontrollable events (like thread scheduling). If multiple threads access and modify shared data concurrently, and the outcome depends on which thread finishes its operation first, a race condition exists.
*   **Example:** Two threads (T1 and T2) try to increment a shared counter initialized to 0.
    1.  T1 reads counter (0).
    2.  T2 reads counter (0).
    3.  T1 increments its local copy (1) and writes it back.
    4.  T2 increments its local copy (1) and writes it back.
    *Expected result: 2. Actual result: 1.*

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
D4:
*   **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption. It is extremely fast but requires a secure method to exchange the key. (Example: AES).
*   **Asymmetric Encryption:** Uses a pair of keys: a public key (shared widely) and a private key (kept secret). Data encrypted with the public key can only be decrypted by the corresponding private key. It is computationally expensive but solves the key exchange problem. (Example: RSA, ECC).
*   **TLS Usage:** TLS uses both. The initial handshake uses **asymmetric encryption** (e.g., RSA) to securely exchange a temporary, random **symmetric session key**. Once the session key is established, all subsequent data transfer is encrypted using the fast **symmetric encryption** algorithm.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
D5: A container image is built from a series of read-only layers. Each instruction in a Dockerfile (e.g., `RUN`, `COPY`, `ADD`) creates a new layer on top of the previous one.
*   **Layer Caching:** Docker caches these layers. If a layer's instruction and its inputs (files) have not changed since the last build, Docker reuses the cached layer, significantly speeding up the build process.
*   **Best Practices:** To maximize caching efficiency, place instructions that change infrequently (like installing OS dependencies, `RUN apt-get update`) at the top of the Dockerfile, and place instructions that change frequently (like copying application code, `COPY . .`) near the bottom.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**
D6:
1.  **Application Logs/Metrics (Application Layer):** Check the application logs for internal errors, exceptions, or resource exhaustion (e.g., thread pool saturation, database connection pool exhaustion). This determines if the application itself is failing.
2.  **Service Health Checks (Service/Container Layer):** Check the health endpoints (Liveness/Readiness probes) of the container. If the container is failing its health checks, the orchestrator (Kubernetes/Docker) might be restarting it or marking it unhealthy.
3.  **Resource Utilization (Infrastructure Layer):** Check CPU and Memory usage on the host/node. High resource pressure can cause processes to be throttled or killed, leading to 503s.
4.  **Load Balancer/Proxy Logs (Edge Layer):** Check the logs of the ingress controller or load balancer. This verifies if the request is even reaching the application layer, or if the LB is timing out before the application responds.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
D7: The CAP theorem states that a distributed data store can only guarantee two out of three properties simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest data), and **Partition Tolerance** (the system continues to operate despite arbitrary message loss or failure of part of the system).
*   **CP (Consistency over Availability):** If a network partition occurs, the system sacrifices availability to ensure data consistency. If it cannot guarantee consistency, it stops responding.
    *   *Example:* Banking/Financial Transaction Systems. You cannot allow a withdrawal to succeed if the ledger state is uncertain.
*   **AP (Availability over Consistency):** If a network partition occurs, the system continues to operate and respond to requests, even if the data returned might be stale or inconsistent across nodes.
    *   *Example:* Social Media Feeds (e.g., Twitter/Facebook). It is acceptable if a follower sees a post slightly delayed or out of order, as long as the service remains available.

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
D8:
*   **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) of a single machine or instance. It is simpler but has physical limits.
*   **Horizontal Scaling (Scaling Out):** Adding more machines or instances to distribute the load. This is generally preferred in modern cloud architectures.
*   **Architectural Patterns for Horizontal Scaling:**
    1.  **Statelessness:** Ensuring that no single instance holds session data or critical state.
    2.  **Load Balancing:** Distributing incoming traffic evenly across multiple identical instances.
    3.  **Microservices:** Decomposing the application into small, independent services that can be scaled individually.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
D9: An environment variable is a dynamic named value that can affect the way running processes behave on a computer. They are used to configure applications without hardcoding values.
To set a variable that persists across shell sessions on Linux, you must add the export command to a shell configuration file, such as `~/.bashrc` or `~/.zshrc`.
*Example: `echo 'export MY_VAR="value"' >> ~/.bashrc`*

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
D10:
*   **JSON (JavaScript Object Notation):** A lightweight data-interchange format based on key-value pairs and arrays. It is highly structured and machine-readable.
    *   *Advantage:* Excellent for API communication due to its native support in JavaScript and ease of parsing.
*   **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard. It relies heavily on indentation and minimal syntax.
    *   *Advantage:* Highly readable, making it ideal for configuration files (like Kubernetes manifests).

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
D11: A REST (Representational State Transfer) API is an architectural style for designing networked applications. It uses standard HTTP methods to perform CRUD (Create, Read, Update, Delete) operations on resources identified by URLs.
*   **GET:** Retrieves a resource or a list of resources (Read). It should be idempotent and safe (no side effects).
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource (Create).
*   **PUT:** Replaces an existing resource entirely with new data (Update). It is idempotent.
*   **DELETE:** Removes a specified resource (Delete). It is idempotent.

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
D12: Version pinning is the practice of explicitly locking a dependency to a specific, immutable version number (e.g., `library@1.2.3`) rather than using a range (e.g., `library@^1.0`).
*   **Importance:** It ensures reproducible builds. If you rely on a range, a future update to the dependency might introduce breaking changes (a bug or API change) that your application was not tested against. Pinning guarantees that the exact same dependency code is used every time the build runs.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
D13:
*   **Compiled Language:** Source code is translated entirely into machine code (binary) by a compiler *before* execution. This results in faster runtime execution but requires a compilation step. (Examples: C++, Go).
*   **Interpreted Language:** Source code is executed line-by-line by an interpreter at runtime. This is slower but allows for greater flexibility and easier debugging. (Examples: Python, Ruby).

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
D14:
*   **Reverse Proxy:** Sits in front of one or more web servers. It intercepts client requests, forwards them to the appropriate backend server, and returns the response to the client. The client never knows the backend server's identity.
*   **Forward Proxy:** Sits in front of clients. It intercepts requests from clients and forwards them to the internet on behalf of the clients. It is used to control or filter outbound traffic.
*   **Servers & Use Cases:**
    *   **NGINX:** Used for load balancing, SSL termination, and serving static content.
    *   **HAProxy:** Used for high-performance, complex load balancing across geographically distributed services.

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
D15: A deadlock is a state in a concurrent system where two or more competing actions are waiting for the other to finish, and thus neither ever finishes.
The four necessary conditions (Coffman conditions) are:
1.  **Mutual Exclusion:** At least one resource must be non-shareable (only one process can use it at a time).
2.  **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3.  **No Preemption:** A resource cannot be forcibly taken away from a process; it must be released voluntarily.
4.  **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
D16: Eventual consistency is a consistency model where, if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. It prioritizes availability and partition tolerance (AP).
*   **Cassandra Handling:** Cassandra uses a decentralized, peer-to-peer architecture. When a write occurs, it is written to a subset of nodes (replicas). The system then asynchronously propagates this write to all other replicas.
*   **Tunable Consistency Levels:** Cassandra allows the developer to specify the consistency level for *each* read or write operation.
    *   *Example:* `QUORUM` requires a majority of replicas to acknowledge the write/read, providing a stronger guarantee than simple eventual consistency, but still allowing for some availability trade-offs.

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
D17: mTLS requires both the client and the server to present and validate cryptographic certificates to each other during the TLS handshake. It is a two-way authentication mechanism.
*   **Handshake Process:**
    1.  Client initiates connection.
    2.  Server sends its certificate and requests the client's certificate.
    3.  Client sends its certificate.
    4.  Server validates the client's certificate against its trusted CA list.
    5.  Client validates the server's certificate against its trusted CA list.
    6.  If both validations pass, the symmetric session key is established, and encrypted communication begins.
*   **Common Use:** Used heavily in microservice mesh architectures (e.g., Istio, Linkerd) to ensure that only authenticated and authorized services can communicate with each other, providing zero-trust networking.

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
D18: A hash table stores key-value pairs by mapping the key to an index (bucket) in an array using a hash function.
*   **Collision:** Occurs when two different keys map to the same index.
*   **Collision Resolution Strategies:**
    *   **Chaining:** Each bucket holds a pointer to a linked list (or other data structure). When a collision occurs, the new key-value pair is simply added to that bucket's list.
    *   **Open Addressing:** When a collision occurs, the system probes for the next available empty slot in the array (e.g., linear probing, quadratic probing).
*   **Time Complexity:**
    *   *Average Case (Good Hash Function):* O(1) for insertion, lookup, and deletion.
    *   *Worst Case (All keys collide):* O(N) for insertion, lookup, and deletion.

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
D19: The circuit breaker pattern is a design pattern used to prevent a system from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service). It acts like an electrical circuit breaker.
*   **States:**
    1.  **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the circuit trips to Open.
    2.  **Open:** The circuit is tripped. All requests are immediately failed (fail-fast) without hitting the failing service. This gives the downstream service time to recover.
    3.  **Half-Open:** After a timeout period, the circuit allows a small number of test requests through. If these requests succeed, the circuit closes; if they fail, it returns to Open.
*   **Relation to Retries/Backoff:** The circuit breaker *replaces* aggressive retry policies. Instead of retrying immediately (which can overwhelm a failing service), the circuit breaker fails fast, allowing the service to recover. Exponential backoff is often used *within* the half-open state or when retrying external calls to prevent overwhelming the recovering service.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**
D20: Concurrency control manages simultaneous access to shared data to prevent corruption.
*   **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data *before* the transaction starts, preventing other transactions from modifying it until the current transaction commits or rolls back.
    *   *When to Choose:* When data integrity is paramount and conflicts are frequent (e.g., inventory management, financial transfers).
    *   *Example:* Using `SELECT FOR UPDATE` in SQL, which places an exclusive lock on the selected rows.
*   **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read. If it has, the transaction fails and must be retried.
    *   *When to Choose:* When conflicts are rare and high throughput is needed (e.g., user profile updates, comment systems).
    *   *Example:* Using a version column (row versioning). The transaction reads the data and its version number. When updating, it includes a `WHERE version = [original_version]`. If the update affects 0 rows, a conflict occurred.
