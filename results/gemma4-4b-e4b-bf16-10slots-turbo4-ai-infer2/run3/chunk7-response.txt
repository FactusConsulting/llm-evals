## Application Architecture (20 questions)

**AA1 — Easy: What is the difference between a monolith and a microservices architecture? Name 3 concrete problems that microservices introduce that monoliths don't have.**
A monolith is a single, unified, tightly coupled application where all components (UI, business logic, data access) are packaged and deployed as one unit. Microservices architecture is a collection of small, independent, loosely coupled services, each running its own process and communicating via lightweight mechanisms (like APIs).
Three concrete problems microservices introduce:
1. **Operational Complexity:** Managing, monitoring, and deploying dozens of services instead of one.
2. **Distributed Transactions:** Handling data consistency across multiple services (e.g., using the Saga pattern).
3. **Network Latency/Failure:** Increased reliance on network calls between services, introducing potential latency and cascading failures.

**AA2 — Easy: Explain the difference between synchronous and asynchronous communication between services. Give an example technology for each.**
*   **Synchronous Communication:** The calling service sends a request and *blocks* (waits) until it receives a response from the called service. It requires immediate feedback. *Example Technology: REST/HTTP (using synchronous calls).*
*   **Asynchronous Communication:** The calling service sends a message/event and immediately continues its work without waiting for a response. The response, if needed, is handled later via a callback or event. *Example Technology: Kafka or RabbitMQ.*

**AA3 — Medium: What is the difference between an API Gateway and a reverse proxy? Can an API Gateway replace a reverse proxy entirely? Why or why not?**
*   **Reverse Proxy:** A server that sits in front of web servers, forwarding client requests to the appropriate backend server. Its primary function is traffic routing, load balancing, and basic security (SSL termination).
*   **API Gateway:** A specialized proxy that sits in front of microservices and provides a unified entry point for clients. It adds business logic capabilities like rate limiting, authentication/authorization, request transformation, and routing.
*   **Replacement:** No, an API Gateway cannot entirely replace a reverse proxy. While an API Gateway *includes* the routing and load balancing functions of a reverse proxy, it adds a layer of *application-level intelligence* (security, throttling, service discovery) that a basic reverse proxy lacks.

**AA4 — Medium: Explain the Saga pattern for distributed transactions. What is the difference between choreography-based and orchestration-based sagas? When is each appropriate?**
The Saga pattern manages distributed transactions by breaking them into a sequence of local transactions. If any local transaction fails, the Saga executes compensating transactions to undo the preceding changes, ensuring eventual consistency.
*   **Choreography-based Saga:** Services communicate by producing and consuming events. Each service listens for events and decides what to do next. *Appropriate when:* Services are highly decoupled and the flow is simple or decentralized.
*   **Orchestration-based Saga:** A central service (the orchestrator) manages the entire workflow. It tells each service what local transaction to execute and waits for confirmation before proceeding. *Appropriate when:* The workflow is complex, long-running, or requires strict control and centralized monitoring.

**AA5 — Medium: What is CQRS (Command Query Responsibility Segregation)? Why is it often paired with Event Sourcing? What problem does this combination solve that a traditional CRUD model doesn't?**
*   **CQRS:** Separates the model used to update data (Commands, which change state) from the model used to read data (Queries, which retrieve state). They can use different data structures and even different databases.
*   **Pairing with Event Sourcing (ES):** ES stores the state of an application as a sequence of immutable events, rather than just the current state.
*   **Problem Solved:** Traditional CRUD models struggle when read and write loads are vastly different, or when complex historical auditing is required. CQRS allows the write model (Commands) to be optimized for transactional integrity, while the read model (Queries) can be optimized for high-speed querying (e.g., denormalized views), and ES provides a perfect audit log of *how* the state was reached.

**AA6 — Medium: Explain the Circuit Breaker pattern. What are the three states? How does it differ from a simple retry with backoff, and when would you use both together?**
The Circuit Breaker pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service).
*   **Three States:**
    1. **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the circuit opens.
    2. **Open:** Requests are immediately failed without attempting the call, preventing resource exhaustion. After a timeout, the circuit moves to half-open.
    3. **Half-Open:** A limited number of test requests are allowed through to see if the downstream service has recovered. If they succeed, the circuit closes; if they fail, it opens again.
*   **Difference from Retry/Backoff:** Retry/Backoff attempts to fix a transient failure by waiting and trying again. Circuit Breaker assumes the failure is systemic and *stops* the attempts entirely to protect both the caller and the failing service.
*   **Using Both:** Use the Circuit Breaker as the primary defense against systemic failure. Use Retry/Backoff *within* the closed state (or for specific, known transient errors) to handle minor, temporary network hiccups before the circuit trips.

**AA8 — Hard: Explain the difference between eventual consistency and strong consistency. A product team wants their inventory system to never oversell. How would you architect this — what consistency model, what data store, and what patterns would you use at scale?**
*   **Strong Consistency:** All reads return the most recent write immediately. If a write succeeds, all subsequent reads see that write. (e.g., ACID transactions).
*   **Eventual Consistency:** If no new updates are made, eventually all reads will return the last updated value, but there is a period where different reads may return different values.
*   **Inventory Architecture (Preventing Oversell):**
    *   **Consistency Model:** Strong Consistency is required for the critical inventory decrement operation.
    *   **Data Store:** A transactional, strongly consistent database (e.g., PostgreSQL, CockroachDB, or a distributed SQL database).
    *   **Patterns:**
        1. **Optimistic Locking:** Use version numbers or timestamps on the inventory record. When a user tries to purchase, the system checks if the version matches the one read. If it doesn't, the transaction fails, preventing oversell.
        2. **Atomic Decrement:** Use database transactions and atomic operations (e.g., `UPDATE inventory SET stock = stock - 1 WHERE product_id = X AND stock >= 1`). This ensures the check and the update happen as a single, indivisible operation.

**AA9 — Hard: What is a sidecar proxy in a service mesh? Explain how Envoy works in an Istio deployment. What is the data plane vs control plane? What problem does mTLS between sidecars solve that application-level TLS doesn't?**
*   **Sidecar Proxy:** A lightweight proxy (like Envoy) deployed alongside every service instance (in the same pod/container). It intercepts all inbound and outbound network traffic for that service.
*   **Envoy in Istio:** Envoy acts as the data plane. Istio's control plane (e.g., Istiod) configures and manages the Envoy proxies, telling them routing rules, security policies, and telemetry collection points.
*   **Data Plane vs Control Plane:**
    *   **Data Plane:** The proxies (Envoy) that handle the actual traffic, enforcing policies, routing, and collecting metrics.
    *   **Control Plane:** The management layer (Istiod) that configures the data plane proxies.
*   **mTLS Solution:** Application-level TLS requires the application code to handle certificate management, key rotation, and trust establishment. mTLS between sidecars handles this automatically and transparently at the network layer. It ensures that *all* service-to-service communication is encrypted and authenticated, regardless of the application language, without requiring code changes.

**AA10 — Medium: Explain the Strangler Fig pattern. You have a legacy .NET Framework monolith and need to incrementally migrate to .NET 8 microservices. Describe a concrete migration strategy using this pattern.**
*   **Strangler Fig Pattern:** A pattern where new functionality is built as microservices, and the old monolith is gradually replaced by routing new requests to the new services. The monolith is "strangled" until it eventually shrinks to nothing.
*   **Migration Strategy (Monolith to Microservices):**
    1. **Identify Boundaries:** Identify a bounded context in the monolith (e.g., User Authentication, Order Processing).
    2. **Build New Service:** Re-implement that context as a new, independent .NET 8 microservice.
    3. **Implement Facade/Router:** Place an API Gateway (the "strangler") in front of the monolith.
    4. **Reroute Traffic:** Configure the API Gateway to route requests for the new context (e.g., `/api/v2/orders`) to the new microservice, while routing all other requests (e.g., `/api/v1/legacy`) to the monolith.
    5. **Decommission:** Once all functionality is migrated, the corresponding code in the monolith is removed.

**AA11 — Medium: What is the 12-Factor App methodology? Name at least 6 factors and explain why they matter for cloud-native deployments.**
The 12-Factor App is a set of best practices for building modern, cloud-native, portable, and scalable applications.
1. **Codebase:** One codebase tracked in revision control, many deploys. (Ensures consistency across environments).
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures reproducibility).
3. **Config:** Store configuration in the environment. (Allows the same code to run anywhere without modification).
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. (Allows easy swapping of infrastructure).
5. **Build, Release, Run:** Strictly separate these stages. (Enables CI/CD pipelines).
6. **Logs:** Treat logs as event streams. (Crucial for centralized logging and observability in distributed systems).

**AA12 — Hard: Compare event-driven architecture using an event broker (Kafka) vs request-driven architecture using REST/gRPC. Cover: coupling, scalability, debugging complexity, ordering guarantees, and failure handling. When would you choose each?**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Services don't know who consumes the event). | Tight (Caller must know the recipient's endpoint). |
| **Scalability** | Excellent (Consumers can scale independently). | Good (Requires scaling the entire service stack). |
| **Debugging** | High Complexity (Tracing asynchronous flows is hard). | Lower Complexity (Linear request/response flow). |

*   **When to Choose:**
    *   **Event-Driven:** When services need to react to state changes (e.g., "Order Placed" triggers Inventory Update, Email Notification, and Analytics logging).
    *   **Request-Driven:** When an immediate, synchronous response is required (e.g., "Get User Profile," "Login").

**AA13 — Easy: What is a load balancer? Explain the difference between Layer 4 and Layer 7 load balancing. Give one use case where Layer 7 is required.**
*   **Load Balancer:** A device or software that distributes incoming network traffic across a group of backend servers (a server farm) to ensure no single server is overwhelmed.
*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It distributes traffic based purely on network information (IP address and port number). It is "dumb" and doesn't inspect the content of the request.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the content of the request (headers, URLs, cookies, HTTP methods) and can make intelligent routing decisions based on the application content.
*   **L7 Use Case:** Routing traffic based on the URL path (e.g., routing `/api/users` to the User Service and `/api/products` to the Product Service, even if they run on the same port).

**AA14 — Easy: What is a message queue? Explain the difference between a message queue (e.g., RabbitMQ) and a log-based message broker (e.g., Kafka). When would you pick one over the other?**
*   **Message Queue (MQ - RabbitMQ):** Designed for point-to-point communication. Messages are consumed and *removed* from the queue. It is transactional and focuses on reliable delivery.
*   **Log-Based Broker (Kafka):** Designed as a distributed commit log. Messages are *retained* and can be read multiple times by multiple consumers at different speeds. It focuses on stream processing and historical data.
*   **When to Pick:**
    *   **MQ:** When a task needs to be executed exactly once (e.g., processing a payment, sending a single email).
    *   **Kafka:** When you need to stream data, replay events, or have multiple consumers needing access to the same stream of data (e.g., logging, analytics, event sourcing).

**AA15 — Easy: What is a container and how does it differ from a virtual machine? Why are containers popular for deploying microservices?**
*   **Container:** A lightweight, executable package of software that includes everything needed to run an application (code, runtime, libraries, configuration). It shares the host OS kernel.
*   **VM:** A full emulation of a computer system, including its own dedicated Guest OS, kernel, and hardware abstraction layer.
*   **Difference:** VMs virtualize the hardware; containers virtualize the operating system. Containers are much smaller, boot faster, and have less overhead than VMs.
*   **Popularity for Microservices:** Containers provide perfect isolation for small, independent services while maintaining high density and portability. They allow developers to package a service and run it identically in development, staging, and production environments.

**AA16 — Easy: Explain the difference between stateless and stateful services. Why are stateless services easier to scale horizontally? Give an example of each.**
*   **Stateless Service:** A service that does not store any client session data or persistent state between requests. Every request contains all the necessary information.
    *   *Example:* A simple REST API endpoint that calculates a tax rate.
*   **Stateful Service:** A service that stores session data or persistent state locally (e.g., in memory or local disk) that must be maintained across multiple requests.
    *   *Example:* A session manager or a database server.
*   **Scaling:** Stateless services are easy to scale horizontally because any incoming request can be routed to any available instance without worrying about session affinity or data loss.

**AA17 — Easy: What is an ORM (Object-Relational Mapper)? Name two popular ORMs in different languages. What are the trade-offs of using an ORM vs writing raw SQL?**
*   **ORM:** A programming technique that allows developers to interact with a relational database using objects and methods in their programming language, rather than writing raw SQL queries. It maps database tables to objects.
*   **Popular ORMs:**
    *   Python: SQLAlchemy
    *   Java: Hibernate
*   **Trade-offs:**
    *   **ORM Pros:** Increased developer productivity, abstraction from specific SQL dialects, improved code readability.
    *   **ORM Cons:** Performance overhead (the ORM might generate inefficient queries), steep learning curve, difficulty in optimizing complex, highly specific queries.

**AA18 — Medium: Explain the Bulkhead pattern. How does it relate to resource isolation in a microservices architecture? Give a concrete example of how you would implement bulkheads using thread pools or separate deployment groups.**
*   **Bulkhead Pattern:** A design pattern that isolates components or services so that the failure or resource exhaustion in one component does not cascade and bring down the entire system. It partitions resources into isolated compartments.
*   **Resource Isolation:** In microservices, it prevents a single, overloaded service (e.g., the Recommendation Engine) from consuming all available resources (CPU, memory, threads) and starving other critical services (e.g., Checkout).
*   **Implementation Example:**
    *   **Thread Pools:** Instead of using a single global thread pool for all external calls, dedicate separate, smaller thread pools for different downstream services. If the Recommendation Engine service starts timing out and consuming all threads, only its dedicated pool will be exhausted, leaving the thread pools for the Checkout service available.
    *   **Deployment Groups:** Deploying critical services (e.g., Payment Processing) on dedicated, high-priority infrastructure separate from less critical services (e.g., Analytics Logging).

**AA19 — Hard: You are designing a real-time collaborative editing system (like Google Docs). **AA20 — Hard: Explain the challenges of distributed tracing across a polyglot microservices ecosystem. Cover: context propagation (W3C Trace Context, B3), sampling strategies (head-based vs tail-based), trace storage and querying (Jaeger, Tempo), and how tracing interacts with asynchronous messaging. How do you ensure trace continuity when a request passes through Kafka?**
*   **Challenges:** Maintaining a single, coherent trace ID across multiple services written in different languages (polyglot) and across asynchronous boundaries.
*   **Context Propagation:** The trace ID and span ID must be injected into the request headers (e.g., `traceparent` for W3C Trace Context, or `X-B3-TraceId` for B3) at the entry point and passed to every downstream service.
*   **Sampling Strategies:**
    *   **Head-based:** Deciding whether to trace a request at the beginning (head). Simple, but may miss critical errors that occur later.
    *   **Tail-based:** Collecting all spans and only deciding to keep the full trace *after* it has completed, often based on criteria like error status or latency. More accurate but computationally expensive.
*   **Storage/Querying:** Tools like Jaeger or Grafana Tempo ingest the spans and allow engineers to visualize the entire request flow.
*   **Asynchronous Continuity (Kafka):** When a request passes through Kafka, the trace context must be injected into the *message headers* before publishing. The consuming service must then extract this context from the message headers and use it to start a new child span, ensuring the trace ID remains continuous across the queue boundary.

## On-Premise Infrastructure Architecture (20 questions)

**OP1 — Easy: Explain the difference between a hypervisor Type 1 (bare-metal) and Type 2 (hosted). Give 2 examples of each.**
*   **Type 1 (Bare-Metal):** The hypervisor runs directly on the host hardware, managing the hardware resources and allocating them to guest VMs. It is highly efficient and used in production data centers. *Examples: VMware ESXi, Microsoft Hyper-V.*
*   **Type 2 (Hosted):** The hypervisor runs as an application *within* a conventional operating system (like Windows or Linux). It relies on the host OS to manage hardware access. It is easier for development/testing but less performant. *Examples: VMware Workstation, VirtualBox.*

**OP2 — Easy: What is a SAN vs NAS? When would you use each? What protocols does each typically use?**
*   **SAN (Storage Area Network):** A dedicated, high-speed network that connects servers to shared storage devices. It presents storage as block-level devices (like a local hard drive) to the server. *Use Case: High-performance database servers, virtualization clusters.* *Protocols: Fibre Channel (FC), iSCSI.*
*   **NAS (Network Attached Storage):** A dedicated storage device connected to the network that provides file-level access to data. It presents storage as shared folders. *Use Case: File sharing, backups, centralized document storage.* *Protocols: NFS, SMB/CIFS.*

**OP3 — Medium: Explain a 3-tier network architecture (core/distribution/access). Why is leaf-spine preferred in modern data centers? What problem does it solve that 3-tier doesn't?**
*   **3-Tier Architecture:**
    *   **Access:** Where end devices (servers, PCs) connect.
    *   **Distribution:** Aggregates traffic from access switches, applies policy, and acts as a routing boundary.
    *   **Core:** High-speed backbone that connects distribution layers.
*   **Leaf-Spine (Clos) Architecture:** A flattened, non-blocking architecture where "Leaf" switches connect to servers, and "Spine" switches connect all the leaves. Every leaf is connected to every spine.
*   **Problem Solved:** The 3-tier model creates bottlenecks and limits scalability because traffic must traverse up to the distribution layer and back down. Leaf-Spine provides predictable, low-latency, and high-bandwidth paths between any two servers, enabling massive horizontal scaling and simplifying routing.

**OP4 — Medium: You need to design a highly available Proxmox cluster with shared storage. Describe the architecture covering: node count, quorum, fencing, shared storage options (Ceph, iSCSI, NFS), and what happens during a node failure.**
*   **Node Count & Quorum:** Minimum 3 nodes for a robust cluster. Quorum requires a majority (e.g., 2 out of 3 nodes must agree on the cluster state).
*   **Shared Storage:** Ceph is the preferred choice for high availability and self-healing within the cluster.
*   **Fencing (STONITH):** Critical. If a node fails, the cluster must ensure that the failed node cannot corrupt data by writing to shared storage (split-brain). Fencing mechanisms (e.g., power cycling the node) are used to forcibly isolate the failed node.
*   **Node Failure:** If one node fails, the remaining nodes maintain quorum. The cluster manager (Corosync/Pacemaker) detects the failure, and the VMs/containers running on the failed node are automatically migrated (live or cold) to the remaining healthy nodes, ensuring service continuity.

**OP5 — Medium: What is VLAN trunking? Explain 802.1Q tagging. A server has a single NIC but needs to be on 3 VLANs — how do you configure this on Linux?**
*   **VLAN Trunking:** A method allowing multiple VLANs to be carried over a single physical link (trunk).
*   **802.1Q Tagging:** The standard protocol that inserts a 4-byte tag into the Ethernet frame header. This tag identifies which VLAN the frame belongs to, allowing the receiving switch to correctly process the frame.
*   **Linux Configuration (VLAN Sub-interfaces):** The server must have a single physical interface (e.g., `eth0`). You create multiple logical sub-interfaces on that physical interface, each assigned a specific VLAN ID:
    *   `eth0.10` (VLAN 10)
    *   `eth0.20` (VLAN 20)
    *   `eth0.30` (VLAN 30)
    Each sub-interface is configured with its own IP address and routing rules.

**OP6 — Medium: Explain the difference between RAID 1, RAID 5, RAID 6, RAID 10, and RAID Z2 (ZFS). You have 6 drives and need to balance performance, capacity, and fault tolerance for a database server — which do you choose and why?**
*   **RAID 1 (Mirroring):** Duplicates data across drives. High read performance, 50% capacity loss. Excellent fault tolerance (can lose N-1 drives).
*   **RAID 5 (Striping with Parity):** Distributes data and parity across drives. Good balance, can lose 1 drive.
*   **RAID 6 (Striping with Dual Parity):** Distributes data and two parity blocks. Excellent fault tolerance (can lose 2 drives).
*   **RAID 10 (Striping + Mirroring):** Stripes data across mirrored pairs. Excellent performance and fault tolerance.
*   **RAID Z2 (ZFS):** Similar to RAID 6, using multiple parity blocks. Highly robust and integrates advanced features like snapshots.
*   **Choice for Database Server (6 drives):** **RAID 10 or RAID Z2.**
    *   **RAID 10:** Offers the best combination of high read/write performance (due to striping) and excellent fault tolerance (due to mirroring).
    *   **RAID Z2:** Offers superior data integrity and features (snapshots, self-healing) while providing high fault tolerance (can lose 2 drives). Given the need for a database, **RAID Z2** is often preferred for its data integrity features.

**OP7 — Hard: Design a DNS architecture for a 500-person enterprise with: internal Active Directory, a DMZ with public-facing services, split-horizon DNS, and DNSSEC on the external zone. Cover: recursive resolvers, authoritative servers, forwarders, conditional forwarding, and what happens when a laptop moves between office and VPN.**
*   **Architecture Components:**
    1. **Internal DNS Servers (Authoritative/Recursive):** Hosted internally, authoritative for internal domains (e.g., `corp.local`). They use Active Directory for internal resolution.
    2. **External DNS Servers (Authoritative):** Hosted publicly, authoritative for external domains (e.g., `company.com`). These are secured with DNSSEC.
    3. **Forwarders:** Internal DNS servers forward requests for external domains to public recursive resolvers (e.g., Google 8.8.8.8).
    4. **Conditional Forwarding:** Used to direct specific domain queries (e.g., `corp.local`) to the internal AD DNS servers, while all other queries go to external forwarders.
    5. **Split-Horizon DNS:** The internal DNS servers provide different records based on the client's location (internal vs. external/DMZ). For example, the internal DNS might point `intranet.corp.local` to an internal IP, while the external DNS points it to a public IP.
*   **Laptop Movement:**
    *   **Office (Internal):** The laptop uses the internal DNS servers, which resolve internal names via AD and external names via forwarders.
    *   **VPN (Remote):** The VPN client must be configured to push the internal DNS server IPs to the laptop. The laptop then uses the internal DNS servers, which correctly resolve both internal and external resources.

**OP8 — Hard: Explain the PKI chain of trust from root CA to end-entity certificate. You need to deploy an internal PKI for your organization. Cover: root CA (offline), subordinate/issuing CA, CRL vs OCSP, certificate templates, and auto-enrollment. What are the consequences of a compromised subordinate CA vs a compromised root CA?**
*   **Chain of Trust:**
    1. **Root CA (Offline):** The highest authority. It signs the Intermediate/Subordinate CA certificate. It is kept offline (air-gapped) to prevent compromise.
    2. **Subordinate/Issuing CA:** Signed by the Root CA. This CA is used to sign end-entity certificates (servers, users). It is online and handles daily operations.
    3. **End-Entity Certificate:** The certificate issued to the actual resource (e.g., a web server).
*   **CRL vs OCSP:**
    *   **CRL (Certificate Revocation List):** A list published periodically by the CA containing all revoked certificates. Clients must download and check this list.
    *   **OCSP (Online Certificate Status Protocol):** A real-time query service where a client asks the CA, "Is this specific certificate valid?" This is faster and more immediate than checking a large CRL.
*   **Consequences of Compromise:**
    *   **Compromised Subordinate CA:** High impact. An attacker can issue fraudulent certificates for internal services, allowing man-in-the-middle attacks within the organization. The damage is contained to the scope of that CA.
    *   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, an attacker can issue certificates that are trusted by *every* system in the organization, effectively compromising the entire PKI infrastructure.

**OP10 — Medium: What is iDRAC/iLO/IPMI? Why is out-of-band management critical? What happens if your IPMI interface is exposed to the internet?**
*   **iDRAC/iLO/IPMI:** These are hardware management interfaces (Intelligent Platform Management Interface) that allow administrators to remotely monitor and manage a server's hardware (power cycling, viewing sensor data, remote console access) *independent* of the operating system.
*   **Criticality of Out-of-Band Management:** It is essential because if the OS or the primary network stack fails, you still need a way to access and troubleshoot the server. It provides a lifeline for recovery.
*   **Exposure to Internet:** If the IPMI interface is exposed to the internet, it becomes a critical security vulnerability. An attacker could gain remote, low-level access to the server hardware, potentially allowing them to:
    1. Force a reboot or power cycle the server.
    2. Access the console to bypass OS security controls.
    3. Extract firmware or configuration data.

**OP11 — Medium: Explain the difference between LVM, LVM-Thin, and ZFS. When would you use each? What are the snapshot semantics for each?**
*   **LVM (Logical Volume Manager):** A software layer that abstracts physical storage into logical volumes. It allows for flexible resizing and volume management on top of traditional block devices.
    *   *Use Case:* General volume management, resizing partitions.
    *   *Snapshot Semantics:* Copy-on-write (CoW) at the volume level.
*   **LVM-Thin:** An extension of LVM that allows for thin provisioning, meaning you can allocate more logical space than physically exists, and only consume space as data is written.
    *   *Use Case:* Efficiently managing large, sparse volumes where space needs to be conserved.
    *   *Snapshot Semantics:* Copy-on-write.
*   **ZFS:** A complete file system and volume manager. It is highly integrated, providing data integrity checks, pooling, and advanced features.
    *   *Use Case:* Mission-critical data storage, databases, where data integrity and snapshots are paramount.
    *   *Snapshot Semantics:* Copy-on-write.

**OP12 — Hard: You have a 3-node Proxmox cluster with Ceph storage and need to survive a complete site failure. Design a stretch cluster or DR strategy. Cover: Ceph CRUSH rules, monitor placement, network latency requirements, and the split-brain problem. Why is 2-site Ceph generally a bad idea without a tiebreaker?**
*   **Stretch Cluster/DR Strategy:** For a 3-node cluster, a single site failure is survivable. For a multi-site (stretched) cluster, you need a mechanism to handle network partitions.
*   **Ceph CRUSH Rules:** CRUSH (Controlled Replication Under Scalable Hashing) rules dictate where data is placed. For DR, you would configure rules to ensure replicas are placed across different failure domains (e.g., different racks, different data centers).
*   **Monitor Placement:** Monitors must be placed strategically across sites to maintain quorum.
*   **Network Latency:** Low latency is critical. High latency can cause the cluster to incorrectly assume a node is dead during a network partition.
*   **Split-Brain Problem:** If the network link between two sites fails, both sites might believe the other site is down and attempt to take over resources simultaneously, leading to data corruption.
*   **Why 2-site Ceph is bad without a tiebreaker:** In a 2-site setup, if the link fails, both sites have 1 monitor each. They are equally isolated and equally capable of forming a quorum (1/2). They will both assume the other site is down and attempt to become the sole authority, leading to data corruption. A tiebreaker (e.g., a third, small witness node) is required to break the tie and maintain quorum.

**OP13 — Easy: What is DHCP and how does the DORA process work? What happens when a DHCP server is unavailable and a Windows client's lease expires?**
*   **DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses and other network configuration parameters (subnet mask, gateway, DNS) to devices on a network.
*   **DORA Process:**
    1. **Discover:** Client broadcasts a request looking for a DHCP server.
    2. **Offer:** DHCP server responds with an IP address offer.
    3. **Request:** Client sends a request to formally accept the offered IP address.
    4. **Acknowledge:** DHCP server sends a final confirmation (ACK) and lease details.
*   **Server Unavailable/Lease Expiration:** When the lease expires, the client attempts to renew the lease (usually by sending a request to the original server). If the server is unavailable, the client will eventually fail to renew the lease. After a grace period, the client's IP address will be released, and it will attempt to re-acquire a new address via the DORA process.

**OP14 — Easy: Explain the difference between a managed switch and an unmanaged switch. What features does a managed switch provide that are important in an enterprise environment?**
*   **Unmanaged Switch:** A plug-and-play device that simply forwards data frames based on MAC addresses. It has no configuration options and is used for simple, small networks.
*   **Managed Switch:** A configurable device that allows administrators to control and monitor network traffic.
*   **Enterprise Features:**
    1. **VLAN Support (802.1Q):** Segmenting the network for security and traffic isolation.
    2. **QoS (Quality of Service):** Prioritizing critical traffic (like VoIP) over less critical traffic (like file transfers).
    3. **Port Security:** Limiting the number of MAC addresses allowed on a port to prevent unauthorized devices.
    4. **SNMP/Syslog:** Allowing remote monitoring and logging of switch health and events.

**OP15 — Easy: What is NTP and why is accurate time synchronization critical in an on-premise environment? What can go wrong when clocks drift between servers in a cluster?**
*   **NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.
*   **Criticality:** Accurate time is vital for:
    1. **Logging and Auditing:** Correlating events across multiple servers (e.g., "Did the login fail before or after the database write?").
    2. **Security:** SSL/TLS certificates rely on accurate timestamps for validity checks.
    3. **Clustering/Replication:** Ensuring data replication and failover mechanisms operate correctly.
*   **Consequences of Clock Drift:**
    1. **Data Corruption:** In distributed databases, transactions relying on timestamps can fail or be incorrectly ordered.
    2. **Security Failures:** Certificate validation fails because the system believes the certificate is expired or not yet valid.
    3. **Cluster Instability:** Clustering software (like Pacemaker) relies on synchronized time to determine which node is the primary master. Drift can cause unnecessary failovers or split-brain scenarios.

**OP16 — Easy: What is the difference between a physical server, a virtual machine, and a container? When would you run a workload directly on bare metal instead of virtualizing it?**
*   **Physical Server:** Actual hardware machine.
*   **Virtual Machine (VM):** A software emulation of a full computer, including its own OS, running on a hypervisor.
*   **Container:** A lightweight, isolated process that shares the host OS kernel.
*   **When to use Bare Metal:**
    1. **Extreme Performance/Low Latency:** For workloads that require direct, unmediated access to hardware resources (e.g., high-frequency trading, specialized GPU computing).
    2. **Legacy/Specialized Hardware:** When the workload requires specific hardware drivers or features that are difficult or impossible to virtualize.
    3. **Minimal Overhead:** When the overhead of the hypervisor layer is unacceptable.

**OP17 — Easy: Explain the difference between a UPS (Uninterruptible Power Supply) and a generator in a data center context. Why do you need both? What is the role of an ATS (Automatic Transfer Switch)?**
*   **UPS:** Provides immediate, short-term power backup (seconds to minutes). It bridges the gap between a power outage and the generator startup, protecting sensitive equipment from sudden power loss and brownouts.
*   **Generator:** Provides long-term, sustained power backup (hours or days) when the utility power is down.
*   **Why Both:** The UPS handles the immediate, transient failure, while the generator handles the prolonged failure.
*   **ATS (Automatic Transfer Switch):** A safety device that monitors the utility power. When utility power fails, the ATS automatically switches the load from the utility grid to the generator. When utility power returns, the ATS switches the load back to the grid.

**OP18 — Medium: Explain the difference between active-passive and active-active clustering for high availability. You have a pair of Linux servers running a PostgreSQL database — describe how you would implement HA using Pacemaker/Corosync, covering fencing (STONITH), virtual IPs, and failover behavior.**
*   **Active-Passive:** One node is active (handling traffic); the other is passive (on standby). If the active node fails, the passive node takes over. (Simpler, less resource efficient).
*   **Active-Active:** Both nodes are active and handle traffic simultaneously. Load is distributed. (More complex, requires careful state management).
*   **Pacemaker/Corosync Implementation:**
    1. **Corosync:** Provides the cluster communication and consensus mechanism (quorum).
    2. **Pacemaker:** The resource manager that monitors the PostgreSQL service.
    3. **Virtual IP (VIP):** A single IP address is assigned to the cluster. Pacemaker ensures this VIP is only active on the currently running PostgreSQL node.
    4. **STONITH (Fencing):** Crucial. Before failing over, Pacemaker uses STONITH to ensure the failed node is completely isolated (e.g., power cycling it) so it cannot attempt to write to the shared storage and corrupt the data.
    5. **Failover:** If the active node fails, Corosync detects the failure, Pacemaker executes STONITH, and then moves the VIP and the PostgreSQL service to the passive node.

**OP19 — Hard: You are designing the backup and recovery strategy for a 50-server on-premise environment. Cover: the 3-2-1 rule, RPO/RTO requirements, backup types (full/incremental/differential), deduplication, tape vs disk vs cloud offsite, immutable backups for ransomware protection, and how you test restores. What is the difference between backup and disaster recovery?**
*   **3-2-1 Rule:** 3 copies of data, on 2 different media types, with 1 copy offsite.
*   **RPO (Recovery Point Objective):** The maximum acceptable amount of data loss (how old the data can be).
*   **RTO (Recovery Time Objective):** The maximum acceptable downtime (how quickly the system must be operational).
*   **Backup Types:**
    *   **Full:** Copies all selected data.
    *   **Incremental:** Copies only data changed since the *last* backup of any type.
    *   **Differential:** Copies all data changed since the *last full* backup.
*   **Storage:** Use disk for fast recovery (local/cloud) and tape/immutable cloud for long-term, air-gapped retention.
*   **Immutable Backups:** Backups that cannot be modified or deleted for a set period, protecting against ransomware encryption.
*   **Testing Restores:** The most critical step. Regularly perform full, end-to-end restore drills to validate RTO/RPO and ensure the backup chain is viable.
*   **Backup vs. Disaster Recovery:** **Backup** is the process of creating copies of data. **Disaster Recovery (DR)** is the comprehensive plan and process of restoring the entire business operation (people, processes, systems) after a catastrophic event.

**OP20 — Hard: Explain how 802.1X (port-based network access control) works in an enterprise wired network. Cover: the supplicant, authenticator, and authentication server roles; EAP methods (EAP-TLS vs PEAP); RADIUS; dynamic VLAN assignment; and what happens to a device that fails authentication. How does MAB (MAC Authentication Bypass) work for devices that don't support 802.1X?**
*   **802.1X Roles:**
    *   **Supplicant:** The client device (laptop, server) requesting network access.
    *   **Authenticator:** The network device (switch/port) that enforces the policy and mediates the connection.
    *   **Authentication Server (RADIUS):** The central server that verifies the supplicant's credentials against user/device databases.
*   **EAP Methods:**
    *   **EAP-TLS:** Uses digital certificates for both the client and the server. Highly secure, as it verifies identity cryptographically.
    *   **PEAP (Protected EAP):** Encapsulates authentication credentials within a TLS tunnel. Easier to deploy than EAP-TLS but relies on username/password credentials.
*   **Dynamic VLAN Assignment:** The RADIUS server, after successful authentication, sends an Access-Accept message back to the switch, which includes attributes instructing the switch to place the supplicant into a specific VLAN (e.g., VLAN 10 for employees, VLAN 50 for guests).
*   **Failure:** If a device fails authentication, the switch (Authenticator) denies the port access, placing the device in a restricted or quarantined VLAN, or simply blocking all traffic until credentials are provided.
*   **MAB (MAC Authentication Bypass):** Used for devices (like printers, IP phones) that cannot run the 802.1X supplicant. MAB allows the switch to authenticate the device based solely on its MAC address, which is then checked against a list in the RADIUS server.
