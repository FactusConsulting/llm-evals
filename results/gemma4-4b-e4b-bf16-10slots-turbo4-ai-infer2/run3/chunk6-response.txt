## JavaScript / TypeScript (20 questions)

**JS1** — The difference is scope and hoisting.
*   **`var`**: Function-scoped or globally scoped. It is hoisted to the top of its scope and initialized with `undefined`. It can be redeclared and updated within the same scope, which often leads to bugs.
*   **`let`**: Block-scoped (`{}`). It is hoisted, but unlike `var`, it is not initialized, leading to the Temporal Dead Zone (TDZ) until the declaration is reached. It cannot be redeclared in the same scope.
*   **`const`**: Block-scoped. It must be initialized upon declaration and cannot be reassigned. While the binding is constant, if the value is an object or array, the contents of that object/array can still be mutated.
*   **Hoisting**: The mechanism where variable and function declarations are moved conceptually to the top of their scope during the compilation phase. Only the *declaration* is hoisted, not the assignment or initialization.

**JS2** — The Event Loop is the mechanism that allows JavaScript (a single-threaded language) to perform non-blocking I/O operations.
*   **Call Stack**: Where synchronous code execution happens. Functions are pushed onto the stack and popped off when they return.
*   **Microtask Queue**: Holds tasks like Promise resolutions (`.then()`, `.catch()`, `await`). The Event Loop processes *all* tasks in the Microtask Queue completely after the current synchronous code finishes, before moving to the next macrotask.
*   **Macrotask Queue**: Holds tasks like `setTimeout()`, `setInterval()`, and I/O events. The Event Loop processes one macrotask at a time, then checks the Microtask Queue, and repeats.

**JS3** — A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). It allows an inner function to access variables from its outer function's scope even after the outer function has finished executing.
*   **Example**: A function factory that creates counters:
    ```javascript
    function createCounter() {
        let count = 0;
        return function() {
            count++;
            return count;
        };
    }
    const counter = createCounter();
    console.log(counter()); // 1
    ```
*   **Classic Closure Bug**: Using `var` in a `for` loop. Since `var` is function-scoped, all callbacks reference the *same* loop variable instance.
    ```javascript
    for (var i = 0; i < 3; i++) {
        setTimeout(function() { console.log(i); }, 100);
    } // Output: 3, 3, 3
    ```
*   **Fix**: Use `let` (which is block-scoped, creating a new binding for each iteration) or wrap the callback in an Immediately Invoked Function Expression (IIFE) to capture the current value of `i`.

**JS4** — **Promise**: An object representing the eventual completion (or failure) of an asynchronous operation.
*   **`async/await`**: Syntactic sugar built on Promises. `async` functions always return a Promise. `await` pauses the execution of the `async` function until the Promise resolves, making asynchronous code look synchronous.
*   **Error Handling**:
    *   **Promises**: Use `.catch(error => {})` or `try...catch` blocks around `await` calls.
    *   **`async/await`**: Standard `try...catch` blocks are used, as `await` throws an exception if the awaited Promise rejects.
*   **`Promise.allSettled` vs `Promise.all`**:
    *   **`Promise.all`**: Waits for *all* promises to resolve. If *any* promise rejects, `Promise.all` immediately rejects with the reason of the first rejection.
    *   **`Promise.allSettled`**: Waits for *all* promises to settle (either resolve or reject). It returns an array of objects describing the outcome of each promise (e.g., `{status: 'fulfilled', value: ...}` or `{status: 'rejected', reason: ...}`).

**JS5** — Both define structure, but they serve different purposes in TypeScript.
*   **`interface`**: Primarily used for defining the shape of objects. It is often used for defining contracts for classes and can be extended (`extends`). Interfaces are generally merged (declaration merging) if defined multiple times.
*   **`type`**: Used for defining any type, including primitives, unions, tuples, and complex object shapes. It is more versatile and cannot be merged.
*   **When to use each**: Use `interface` for defining public APIs or object shapes that might be extended by multiple modules. Use `type` for complex unions, mapped types, or when defining primitive aliases.
*   **Discriminated Unions**: A union type where all members share a common, literal property (the "discriminator"). This allows TypeScript to narrow the type safely using a `switch` statement.
    ```typescript
    type Shape = { kind: "circle", radius: number } | { kind: "square", side: number };
    // TypeScript knows which properties to access based on the 'kind' property.
    ```

**JS6** — **Prototypal Inheritance**: JavaScript objects inherit properties and methods from other objects (their prototypes). When you try to access a property on an object, if it's not found directly, JS looks up the prototype chain until it finds it or reaches `Object.prototype`.
*   **`Object.create()`**: Creates a new object, using an existing object as the prototype of the new object. The new object inherits properties from the provided prototype object.
    ```javascript
    const proto = { greet: () => "Hello" };
    const child = Object.create(proto); // child inherits greet
    ```
*   **ES6 Classes**: ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance. They provide a cleaner, more familiar syntax (like classical inheritance) but fundamentally operate using the prototype chain under the hood.

**JS7** — The `this` keyword refers to the object that is currently executing the function. Its value is determined dynamically based on *how* the function is called.
*   **4 Binding Rules (in priority order)**:
    1.  **`new` binding**: When a function is called with `new`, `this` refers to the newly created instance.
    2.  **Explicit binding**: When `call()`, `apply()`, or `bind()` are used, `this` is explicitly set to the provided object.
    3.  **Implicit binding**: When a function is called as a method of an object (e.g., `obj.method()`), `this` refers to `obj`.
    4.  **Default binding**: If none of the above apply (e.g., a standalone function call), `this` defaults to the global object (or `undefined` in strict mode).
*   **`bind()`**: Returns a *new* function with the `this` keyword permanently bound to a specified value.
*   **Re-binding**: Yes, the returned function can be re-bound using `bind()` again, or it can be called using `call()`/`apply()` to override the bound context temporarily.

**JS8** — **WeakRef**: A reference to an object that does not prevent the garbage collector (GC) from collecting the object. It allows you to hold a reference without creating a memory leak.
*   **`FinalizationRegistry`**: A mechanism that allows you to register a callback function that will be executed *after* a weakly referenced object has been garbage collected.
*   **Use Case**: Implementing caches or observers where you need to track an object's existence without keeping a strong reference to it.
*   **WeakMap Keys**: WeakMap keys must be objects because the GC needs to track the object's lifecycle. If a key were a primitive (like a string), the GC would treat it as a standard value, and the WeakMap would retain a strong reference to it, defeating the purpose of weak referencing.

**JS9** — V8 optimizes JavaScript by compiling code into machine code and using various heuristics to predict runtime behavior.
*   **Hidden Classes (or Maps)**: V8 groups objects with the same structure (same property names and order) into the same hidden class. This allows V8 to optimize property access (e.g., accessing `obj.name` is a direct memory offset lookup instead of a hash map lookup).
*   **Inline Caching (IC)**: V8 caches the results of property lookups and method calls. If a property is accessed repeatedly, V8 uses the cached location instead of re-calculating the lookup every time.
*   **Deoptimization**: Occurs when V8's assumptions about the code's structure (e.g., assuming an object always has a certain shape or that a function will always be called with certain types) are violated at runtime. When deoptimization occurs, V8 must discard the optimized machine code and revert to a slower, safer interpretation mode.
*   **Deoptimization Triggers**: Frequent changes to object structure (adding/deleting properties), using dynamic property access (e.g., `obj[key]`), or using highly dynamic function calls.

**JS10** — **Tree-shaking**: A form of dead-code elimination used by bundlers (like Webpack or Rollup). It analyzes the dependency graph of the application and removes unused exports (code that is imported but never actually used).
*   **ES Modules (ESM)**: Tree-shaking works effectively because ESM uses static `import` and `export` syntax. The bundler can statically analyze the entire dependency tree before runtime to determine exactly which exports are needed.
*   **CommonJS (CJS)**: CJS uses dynamic `require()` calls. Since `require()` is a runtime function call, the bundler cannot statically determine which modules are used, making it impossible to reliably identify and remove unused code.

**JS11** — **`null` vs `undefined`**:
*   **`undefined`**: Means a variable has been declared but has not yet been assigned a value. It is the default value for uninitialized variables.
*   **`null`**: Is an assignment value. It explicitly means "no value" or "empty." It must be explicitly assigned.
*   **`==` vs `===`**:
    *   `==` (Loose equality): Performs type coercion. `null == undefined` is `true`.
    *   `===` (Strict equality): Compares both value and type without coercion. `null === undefined` is `false`.
*   **Nullish Coalescing (`??`)**: Returns the right-hand operand when the left-hand operand is `null` or `undefined`. It specifically ignores `0` or `""` (empty string), unlike `||`.
*   **Optional Chaining (`?.`)**: Allows you to read the value of a property deep within an object without having to explicitly check if every intermediate property exists. If any part of the chain is `null` or `undefined`, the expression short-circuits and returns `undefined`.

**JS12** — Array methods for functional programming:
*   **`map()`**: Creates a new array by applying a function to every element in the original array. It transforms the array.
*   **`filter()`**: Creates a new array containing only the elements that pass a test implemented by the provided function. It selects elements.
*   **`reduce()`**: Executes a reducer function on each element of the array, resulting in a single output value.
*   **`reduce()` with Initial Value**: The initial value is the accumulator's starting point. If provided, it is used as the first accumulator value and the iteration starts from the first element. If not provided, the first element is used as the initial accumulator, and iteration starts from the second element.
*   **`flatMap()`**: First maps each element using a mapping function, and then flattens the result into a new array. It is useful when your mapping function might return an array, and you want the final result to be a single, flat array.

**JS13** — **Template Literals**: Strings enclosed by backticks (`` ` ``). They allow for embedded expressions and multi-line strings without needing concatenation.
*   **Tagged Templates**: A function that receives the string parts and the interpolated values as arguments. It allows you to process the template literal before it is constructed.
*   **Example (HTML Escaping)**:
    ```javascript
    function htmlEscape(strings, ...values) {
        let result = '';
        strings.forEach((string, i) => {
            result += string;
            if (values[i] !== undefined) {
                // Simple escaping logic
                result += values[i].toString().replace(/</g, '&lt;').replace(/>/g, '&gt;');
            }
        });
        return result;
    }
    const name = "Alice";
    const html = htmlEscape`<h1>Hello, ${name}!</h1>`;
    // html is now safe HTML string
    ```

**JS14** — **Destructuring**: A syntax that allows you to unpack values from arrays or properties from objects into distinct variables.
*   **Object Destructuring**: Extracts properties from an object into variables based on the property name.
    ```javascript
    const user = { name: 'Bob', age: 30 };
    const { name, age } = user; // name = 'Bob', age = 30
    ```
*   **Array Destructuring**: Extracts values from an array based on position.
    ```javascript
    const colors = ['red', 'green', 'blue'];
    const [first, second] = colors; // first = 'red', second = 'green'
    ```
*   **Default Values**: Allows you to assign a default value if the property/element is missing or `undefined`.
    ```javascript
    const { age = 25 } = user; // age will be 25 if not present
    ```
*   **Renaming**: Allows you to assign the extracted value to a different variable name.
    ```javascript
    const { name: userName } = user; // userName = 'Bob'
    ```
*   **Rest Operator (`...`)**: When used in destructuring, it collects all remaining properties/elements into a new array.
    ```javascript
    const { id, ...rest } = user; // rest = { age: 30 }
    ```

**JS15** — **`for...in` vs `for...of`**:
*   **`for...in`**: Iterates over the *enumerable properties* (keys) of an object. It is designed for iterating over object properties, not array elements.
*   **`for...of`**: Iterates over the *values* of an iterable object (like Arrays, Maps, Sets). It is designed for iterating over elements.
*   **Why avoid `for...in` on arrays**: It iterates over enumerable properties, which includes properties added to the array object itself (like `length`), and it does not guarantee iteration order, making it unreliable for array processing.

**JS16** — **TypeScript Generics**: Allow you to write reusable components that can work over a variety of types rather than a single one. They allow you to abstract over types while maintaining type safety.
*   **Generic Constraints (`extends`)**: Restricts the types that can be used with a generic parameter. It ensures the type has certain properties or methods.
    ```typescript
    function identity<T extends { length: number }>(arg: T): T { return arg; }
    ```
*   **Conditional Types (`T extends U ? X : Y`)**: Allows you to define a type that resolves to one type (`X`) or another (`Y`) based on whether a condition is true.
    ```typescript
    type IsString<T> = T extends string ? true : false;
    ```
*   **`infer` Keyword**: Used within conditional types to extract a type from a complex type structure.
    ```typescript
    type GetArray<T> = T extends (infer U)[] ? U : never;
    ```

**JS17** — **Module System**: The mechanism by which code dependencies are managed and shared between files.
*   **CommonJS (CJS)**: Synchronous module system used primarily in Node.js. Uses `require()` to import and `module.exports` to export. It is synchronous and loads modules at runtime.
*   **ES Modules (ESM)**: Standardized module system (`import`/`export`). It is asynchronous and designed for static analysis.
*   **Node.js Handling**: Node.js supports both. By default, `.js` files are treated as CJS.
*   **`"type": "module"`**: When added to `package.json`, it instructs Node.js to treat all `.js` files in that package as ES Modules, enabling the use of `import`/`export` syntax natively.

**JS18** — **Structural Type System**: TypeScript determines compatibility based on the *shape* of the object (what properties it has and what types they are), not on explicit inheritance or declaration. If two objects have the same structure, they are considered compatible, even if they don't share a common ancestor class.
*   **Excess Property Checks**: A compiler option that flags properties on an object that are not defined in the type or interface. This helps prevent accidental property pollution.
*   **`extends` vs `satisfies`**:
    *   **`extends`**: Used for inheritance. It means the derived type *is* the base type (e.g., `class Dog extends Animal`).
    *   **`satisfies`**: Used for type checking without inheritance. It means the type *conforms to* the shape of the base type, but doesn't inherit from it. It allows you to use a type definition for validation while keeping the original object structure.
*   **Variance (`in`, `out`)**: Defines how subtyping works with generic types.
    *   **Covariance (`out`)**: A type that only *outputs* values (e.g., `Promise<T>`). If `Dog` extends `Animal`, then `Dog` is a subtype of `Animal`.
    *   **Contravariance (`in`)**: A type that only *inputs* values (e.g., a function parameter). If `Dog` extends `Animal`, then a function expecting `Animal` can safely accept a `Dog`.

**JS19** — **Proxy and Reflect**:
*   **Proxy**: An object that wraps another object (the target) and allows you to intercept fundamental operations (like property lookups, assignments, function calls) before they happen.
*   **Reflect**: An API that provides methods for performing operations on objects (like `Reflect.get`, `Reflect.set`). It is the standard, low-level way to perform these operations, which Proxies wrap.
*   **Interception**:
    *   **Property Access**: Intercepted via `get` trap in the Proxy handler.
    *   **Assignment**: Intercepted via `set` trap.
    *   **Function Calls**: Intercepted via `apply` or `construct` traps.
*   **Practical Example (Validation)**: Using a Proxy to ensure a user object's `age` property never drops below 18.
    ```javascript
    const handler = {
        set: (target, property, value) => {
            if (property === 'age' && value < 18) {
                throw new Error("Age must be 18 or older.");
            }
            return Reflect.set(target, property, value);
        }
    };
    const user = { age: 20 };
    const proxiedUser = new Proxy(user, handler);
    ```

**JS20** — **SharedArrayBuffer and Atomics**: Mechanisms for safe, concurrent memory access across multiple threads (Web Workers).
*   **SharedArrayBuffer (SAB)**: A buffer object that can be shared between multiple execution contexts (threads). It allows threads to read and write to the same block of memory.
*   **Web Workers Communication**: Workers communicate by sharing the SAB. Instead of sending copies of data (which is slow), they share a reference to the same memory block.
*   **Ordering Guarantees**: Standard memory operations are not guaranteed to be visible immediately across threads. **Atomics** operations (like `Atomics.add`, `Atomics.load`) ensure that operations are performed atomically (indivisibly) and provide memory ordering guarantees, preventing race conditions.
*   **`Atomics.wait/Atomics.notify`**:
    *   `Atomics.wait(typedArray, index, expectedValue)`: Causes the current thread to block (sleep) until the value at the specified index changes from `expectedValue` or a timeout occurs.
    *   `Atomics.notify(typedArray, index, count)`: Wakes up a specified number of threads that are currently waiting on that index.

## Bash (20 questions)

**B1** — Both refer to positional parameters, but the quoting changes how they are treated by the shell.
*   **`$@`**: Expands to separate arguments, and each argument is quoted individually. This is the preferred way to iterate over arguments, as it preserves spaces and special characters within arguments.
*   **`$*`**: Expands to a single string containing all arguments, separated by the first character of the `IFS` (Internal Field Separator, usually space). This often causes arguments with spaces to be treated as one large argument.
*   **`"$@"` vs `"$*"`**:
    *   `"$@"`: Expands to separate, quoted arguments (safe).
    *   `"$*"`: Expands to a single, quoted string (unsafe if arguments contain spaces).

**B2** — This command sets strict error handling modes for the shell script.
*   **`set -e`**: Exit immediately if a command exits with a non-zero status (i.e., fails). This prevents the script from continuing after an error.
*   **`set -u`**: Treat unset variables as an error and exit. This forces the use of defined variables.
*   **`set -o pipefail`**: If any command in a pipeline fails (i.e., returns a non-zero exit status), the entire pipeline command returns a non-zero status, rather than just the last command's status.

**B3** — **Command Substitution**:
*   **`$(command)`**: Executes the `command` and substitutes its standard output into the current command line. This is the modern, preferred syntax.
*   **`command`**: Simply executes the command. If used without substitution, it runs the command and its output is printed to stdout.
*   **`$((expression))`**: Performs arithmetic evaluation. The shell evaluates the expression and substitutes the resulting number.
*   **`expr`**: An external utility used to evaluate expressions. It is less efficient and requires specific syntax (e.g., using `\-` for subtraction).

**B4** — **Process Substitution (`<(command)`)**: Allows the output of a command to be treated as a temporary file path. This is useful when a command needs to be passed as an argument to another command that expects a file descriptor.
*   **Practical Example with `diff`**: Comparing the output of two commands without writing them to temporary files:
    ```bash
    diff <(ls -l /etc) <(ls -l /var/log)
    ```

**B5** — The safest way is to use a `while read` loop combined with `find -print0` and `xargs -0`.
*   **Dangerous `for f in $(ls)`**: If filenames contain spaces or special characters, `$(ls)` splits them based on the IFS, causing the loop to iterate over incorrect tokens.
*   **Safe Method**:
    ```bash
    find . -type f -print0 | while IFS= read -r -d '' f; do
        echo "Processing file: $f"
    done
    ```

**B6** — **Here Document (`<<EOF`)**: Allows you to pass multiple lines of input to a command until the delimiter (`EOF`) is encountered. The content is treated as standard input.
*   **Here String (`<<<`)**: Passes a single string (or a single line) as standard input to a command.
*   **`<<-EOF`**: This is a variation of the here document. It allows leading tabs in the input lines to be treated as spaces (un-indented), which is extremely useful for writing configuration files or scripts within the here document.

**B7** — Redirection order is critical.
*   **`cmd > file 2>&1`**:
    1.  `cmd > file`: Redirects standard output (FD 1) to `file`.
    2.  `2>&1`: Redirects standard error (FD 2) to the same location as FD 1 (which is now `file`).
    *   **Result**: Both stdout and stderr go to `file`.
*   **`cmd 2>&1 > file`**:
    1.  `cmd 2>&1`: Redirects standard error (FD 2) to the current standard output (FD 1).
    2.  `> file`: Redirects standard output (FD 1) to `file`.
    *   **Result**: Both stdout and stderr go to `file`. (In this specific case, the result is the same, but the order matters when redirecting to different files or when dealing with complex pipelines.)
*   **`cmd &> file`**: (Bash 4+) A shorthand that redirects both stdout and stderr to the specified file.
*   **Why the first two are different (conceptually)**: The first method redirects stderr *to* the destination of stdout. The second method redirects stderr *to* stdout, and then redirects stdout to the destination.

**B8** — A robust lock file function must use atomic operations and signal traps.
*   **Locking Mechanism**: Use `mkdir` (Make Directory) instead of file creation. `mkdir /tmp/lockfile` is atomic; if the directory already exists, the command fails, preventing a race condition.
*   **Function Structure**:
    ```bash
    LOCK_DIR="/tmp/my_app.lock"
    function acquire_lock() {
        if mkdir "$LOCK_DIR" 2>/dev/null; then
            echo "Lock acquired."
            trap 'rmdir "$LOCK_DIR"' EXIT INT TERM # Cleanup on exit/interrupt
            return 0
        else
            echo "Lock already held."
            return 1
        fi
    }
    # ... main script logic ...
    ```
*   **Why `mkdir` is preferred**: File creation (`touch`) is not guaranteed to be atomic across all filesystems, especially under heavy load. `mkdir` is an atomic operation that guarantees only one process can successfully create the directory at a given time.

**B9** — The quotes control how the shell interprets special characters (like spaces, `*`, `$`, `\`).
*   **Single Quotes (`'...'`)**: Literal interpretation. All characters inside are treated literally, including variable expansion and special characters.
    *   Example: `'Hello World'` -> `Hello World`
*   **Double Quotes (`"..."`)**: Parameter expansion and command substitution are processed. Variables are expanded, but special characters like `$` are still interpreted.
    *   Example: `"Hello $USER"` -> `Hello [username]`
*   **No Quotes**: Wildcard expansion and command substitution occur immediately before the command is executed.
    *   Example: `echo $USER` -> `echo [username]`

**B10** — Bash uses `[ ]` (which is an alias for the `test` command) and `[[ ]]` (which is a Bash keyword).
*   **`[ ]` (test)**: Older, POSIX compliant. It is less powerful and requires careful quoting.
*   **`[[ ]]` (Bash keyword)**: More powerful, supports regex matching, and handles word splitting and globbing differently.
*   **Checks**:
    *   File exists: `[ -f filename ]` or `[[ -f filename ]]`
    *   Is a directory: `[ -d dirname ]` or `[[ -d dirname ]]`
    *   Is readable: `[ -r filename ]` or `[[ -r filename ]]`

**B11** — Positional parameters hold information about the execution environment.
*   **`$?`**: The exit status of the most recently executed foreground command (0 means success, non-zero means failure).
*   **`$$`**: The Process ID (PID) of the current shell.
*   **`$!`**: The PID of the most recently backgrounded job.
*   **`$#`**: The number of positional arguments passed to the script.
*   **Use Cases**:
    *   `$?`: Checking if `grep` found a match.
    *   `$$`: Ensuring only one instance of the script runs (locking).
    *   `$!`: Waiting for a background process to finish (`wait $!`).
    *   `$#`: Validating that the user provided the required number of inputs.

**B12** — **Definition/Usage**:
*   **`foo() { ... }`**: Standard function syntax.
*   **`function foo { ... }`**: Alternative, older syntax. Functionally identical in modern Bash.
*   **Return Values**: Bash functions do not return values in the programming sense. They return an exit status (0-255) using `return`. To pass data, you must print the data to stdout and capture it using command substitution: `result=$(foo)`.

**B13** — **PATH**: An environment variable that contains a list of directories (separated by colons) where the shell searches for executable commands.
*   **Command Resolution**: When you type `ls`, the shell searches the directories listed in `$PATH` sequentially until it finds an executable file named `ls`.
*   **Builtin vs External**:
    *   **Builtin**: Commands implemented directly within the shell itself (e.g., `cd`, `echo`, `alias`). They are faster because they don't require spawning a new process.
    *   **External**: Standard executable programs found in the `$PATH` (e.g., `grep`, `awk`).
*   **Checking**: Use `type command`. If it says `command is a builtin`, it's a builtin. If it shows a path (e.g., `/bin/grep`), it's external.

**B14** — **`trap`**: A mechanism to execute a specified command or function when the shell receives a specific signal.
*   **Cleanup Handlers**:
    *   `EXIT`: Runs when the script finishes normally (regardless of success/failure).
    *   `ERR`: Runs when a command fails (non-zero exit status, often used with `set -e`).
    *   `INT`: Runs when the script receives SIGINT (Ctrl+C).
    *   `TERM`: Runs when the script receives SIGTERM (standard termination signal).
*   **Execution Order**: When multiple signals arrive simultaneously, the order is generally unpredictable, but the shell processes the signal handlers sequentially. For graceful shutdown, it is best practice to handle `INT` and `TERM` first, and ensure the `EXIT` trap runs last to perform final cleanup.

**B15** — **`xargs` vs Command Substitution**:
*   **Command Substitution**: Executes a command and captures its output as a string.
*   **`xargs`**: Takes input from standard input and builds and executes command lines from that input. It is used to efficiently run a command on a list of items.
*   **Handling Spaces/Newlines**: Using `find -print0` (null-delimited output) and `xargs -0` (null-delimited input) ensures that filenames containing spaces or newlines are treated as single arguments.
*   **Parallel Execution (`xargs -P`)**: The `-P` flag specifies the maximum number of processes to run in parallel. This is crucial for speeding up I/O-bound tasks (like processing many files) by distributing the workload across multiple CPU cores.

**B16** — **Bash Arrays**:
*   **Indexed Arrays**: Ordered lists accessed by numerical index.
    *   *Declaration*: `my_array=(item1 item2)`
    *   *Append*: `my_array+=(item3)`
    *   *Iterate*: `for item in "${my_array[@]}"; do ...`
    *   *Length*: `${#my_array[@]}`
*   **Associative Arrays (Maps)**: Key-value stores accessed by string keys.
    *   *Declaration*: `declare -A my_map`
    *   *Set*: `my_map[key]="value"`
    *   *Iterate*: `for key in "${!my_map[@]}"; do ...`
    *   *Length*: `echo ${#my_map[@]}`
*   **Differences**: Indexed arrays maintain order and use integer indices. Associative arrays use arbitrary strings as keys and do not guarantee iteration order.

**B17** — **Subshell vs Group Command**:
*   **Subshell (`(...)`)**: Executes commands in a completely new, isolated shell process. Any variables or environment changes made inside the subshell are lost when the subshell exits.
*   **Group Command (`{ ...; }`)**: Executes commands within the *current* shell process, but within a subshell job control group. Variables and environment changes persist in the parent shell.
*   **Piping into `while` loop**: When you pipe output into a `while` loop (`command | while read line; do ... done`), the loop runs in a subshell. Any changes made to variables inside that loop (e.g., `count=1`) are local to the subshell and are lost when the loop finishes, meaning the parent shell variable remains unchanged.

**B18** — **Signals and Job Control**:
*   **Job Control**: Allows the shell to manage background processes (`&`) and foreground processes.
*   **Signals**: Notifications sent to processes.
    *   **`SIGINT` (Interrupt)**: Sent by Ctrl+C. Used for graceful user interruption.
    *   **`SIGTERM` (Terminate)**: Standard request for a process to shut down gracefully.
    *   **`SIGHUP` (Hangup)**: Sent when a controlling terminal is closed. Often used to signal background processes to reload configuration.
    *   **`SIGKILL`**: Cannot be caught or ignored. Forces immediate, non-graceful termination by the kernel.
*   **Graceful Shutdown**: Use `trap` to catch `SIGINT` and `SIGTERM`. In the trap handler, you should send a signal to all background processes (`kill $!`) and then exit cleanly.

**B19** — **Parallel Log Processing Script**:
*   **Script Logic**:
    1.  `split -l 1000 large.log chunk_` (Splits the file into manageable pieces).
    2.  `find . -name "chunk_*" | xargs -0 -P 4 -I {} bash -c 'process_file "$@"' _ {}` (Runs the processing function on 4 files in parallel).
    3.  `cat chunk_* | merge_results` (Merges the processed output).
*   **Performance Trade-offs**: Parallel processing significantly reduces wall-clock time for I/O-bound tasks (like reading/writing many small files). However, it increases CPU overhead due to process creation and context switching.
*   **Error Propagation**: Error handling is complex. Since `xargs` runs jobs independently, the main script doesn't automatically know if a parallel job failed. You must modify the processing function to write a status flag (e.g., to a separate status file) and then check these flags after the parallel execution completes.

**B20** — **`exec` vs Normal Command**:
*   **Normal Command**: Spawns a new process. The parent shell continues running after the child process finishes.
*   **`exec`**: Replaces the current shell process image with the new command. The shell itself is replaced; it does not continue running.
*   **File Descriptor Manipulation**: `exec 3>file` opens a new file descriptor (FD 3) and associates it with the file. `exec 3>&-` closes FD 3. This is used to manage persistent connections or logs.
*   **Bash Coprocess**: A mechanism that allows a parent shell to communicate with a child process using named pipes (FIFOs). The parent can send input to the child and read output from it, allowing for bidirectional communication without relying on standard stdout/stdin. Use case: running a long-running service and communicating configuration changes to it.

## PowerShell (20 questions)

**PS1** — **`Write-Output` vs `Write-Host`**:
*   **`Write-Output`**: Sends objects to the pipeline. This is the standard, idiomatic way to output data in PowerShell. It allows the data to be processed by subsequent cmdlets.
*   **`Write-Host`**: Writes text directly to the console window. It bypasses the pipeline and is used for displaying status messages or user prompts.
*   **Why it matters**: If you use `Write-Host` inside a function, the output is not captured by the pipeline, meaning subsequent cmdlets cannot process the data.

**PS2** — **Pipeline**: PowerShell is an object-oriented pipeline. Cmdlets pass structured objects (not just strings) from one to the next, allowing for powerful filtering and manipulation.
*   **`ForEach-Object` (or `%`)**: A cmdlet that iterates over the objects received from the pipeline. It is designed to process the input object by object.
*   **`foreach` statement**: A standard scripting construct used to iterate over collections (arrays, lists). It is used for control flow within a script block.
*   **When to use each**:
    *   Use `ForEach-Object` when you are piping data from a cmdlet (e.g., `Get-Service | Where-Object { ... } | ForEach-Object { ... }`).
    *   Use `foreach` when iterating over a collection variable already stored in memory (e.g., `foreach ($item in $myArray) { ... }`).

**PS3** — **`[PSCustomObject]` vs `[hashtable]`**:
*   **`[PSCustomObject]`**: Creates a structured object with defined properties and types. It is the preferred way to return structured data in PowerShell.
    ```powershell
    [PSCustomObject]@{ Name = "Alice"; Age = 30 }
    ```
*   **`[hashtable]`**: A dictionary-like structure where keys map to values. It is less structured and is often used for configuration or parameter passing.
    ```powershell
    @{ Name = "Alice"; Age = 30 }
    ```
*   **Conversion**:
    *   Hashtable to PSCustomObject: `[PSCustomObject]$myHash`
    *   PSCustomObject to Hashtable: `$myObject | Select-Object * | ConvertTo-Hashtable`

**PS4** — **Error Handling**: PowerShell distinguishes between two types of errors.
*   **Non-Terminating Errors**: Errors that do not stop the script execution. They are typically warnings or expected failures (e.g., trying to access a non-existent registry key).
*   **Terminating Errors**: Errors that halt the script execution immediately.
*   **Interaction**:
    *   **`-ErrorAction`**: Specifies how a cmdlet should handle errors (e.g., `Stop` (terminating), `Continue` (non-terminating), `SilentlyContinue`).
    *   **`$ErrorActionPreference`**: A global variable that sets the default behavior for all cmdlets (e.g., `Continue`, `Stop`).
    *   **`try/catch`**: Allows you to explicitly wrap code blocks. The `catch` block only executes if a terminating error occurs, allowing you to handle it gracefully without stopping the script.

**PS5** — **Splatting (`@params`)**: The practice of passing a hashtable or an array of parameters to a cmdlet, allowing you to define parameters dynamically outside the function call.
*   **Example**:
    ```powershell
    $params = @{
        Path = "C:\Logs"
        Filter = "*.log"
        Recurse = $true
    }
    Get-ChildItem @params
    ```
*   **Difference from Hashtable Parameter**: If you pass a hashtable as a single parameter, the cmdlet receives the hashtable object itself. When you use splatting (`@params`), PowerShell unpacks the hashtable, treating each key-value pair as a distinct parameter argument for the cmdlet.

**PS6** — **PowerShell Remoting**: Allows remote execution of PowerShell commands on a target machine.
*   **`Invoke-Command -ComputerName`**: Executes a script block or cmdlet on a remote machine. It is a single, non-interactive command execution.
*   **`Enter-PSSession`**: Establishes an interactive, persistent remote session. You are dropped into a remote shell environment where you can run multiple commands interactively.
*   **Protocol**: PowerShell Remoting primarily uses **WinRM (Windows Remote Management)** on Windows. On Linux/Unix, it can leverage SSH. WinRM is the underlying service that facilitates the communication.

**PS7** — **Type System and Implicit Behavior**: PowerShell's pipeline is object-oriented, but when a function returns an array of strings (which are treated as `System.String` objects), the resulting variable `$x` is an array of strings.
*   **The Code**:
    ```powershell
    $x = Get-Items
    $x.GetType().Name  # Output: String[] (Array of Strings)
    ```
*   **The Problem**: When the function returns 0 items, `$x` is an empty array (`String[]`). If you try to access properties on an empty array, you might get unexpected behavior or errors, as the array itself is the object, not the elements.
*   **Correct Pattern**: Always return a collection of objects, even if empty. If the function fails to find items, return an empty array of the expected object type:
    ```powershell
    function Get-Items {
        # Return an empty array of the expected type
        return @()
    }
    ```

**PS8** — **`[scriptblock]` vs Function**:
*   **Function**: A named, reusable block of code that can accept parameters and return values. It is a callable object.
*   **`[scriptblock]`**: An anonymous, executable block of code. It is often used when passing code to cmdlets (e.g., `Where-Object { ... }`).
*   **Passing to Remote Session**: You pass a scriptblock using the `-ScriptBlock` parameter of `Invoke-Command`.
*   **Double-Hop Problem**: When running code remotely, variables defined in the local session are not automatically available in the remote session's scope.
*   **Solution**:
    1.  **`Invoke-Command -ArgumentList`**: Pass variables as arguments to the script block.
    2.  **CredSSP**: Used for complex authentication scenarios, allowing the remote session to inherit credentials from the local user.

**PS9** — **`@()` vs `[array]`**:
*   **`@()`**: A shorthand syntax for creating an empty array. It is the most common way to initialize an empty collection.
*   **`[array]`**: The type accelerator used to explicitly define a variable as an array type.
*   **Forcing Single Result into Array**: Use the array constructor: `[array]@{Property = "Value"}` or simply wrap the object in parentheses: `(@{Property = "Value"})`.
*   **Indexing**:
    *   `$null`: Indexing `$null` throws a runtime error.
    *   Empty Array (`@()`): Indexing an empty array throws an `IndexOutOfRangeException`.

**PS10** — **Comparison Operators**:
*   **Standard Operators (`-eq`, `-ne`, `-like`, `-match`, `-contains`, `-in`)**: These are case-insensitive by default (unless the underlying object type dictates otherwise).
*   **Case-Sensitive Variants (`-ceq`, `-clike`, etc.)**: These force a case-sensitive comparison.
*   **`-contains` vs `-in`**:
    *   **`-contains`**: Checks if a *specific value* exists within a collection (e.g., `$array -contains "apple"`).
    *   **`-in`**: Checks if a *value* is present within a list of possible values (e.g., `$color -in ("red", "blue")`).

**PS11** — **PowerShell Modules**: Collections of cmdlets, functions, and scripts that provide functionality.
*   **Script Module (`.psm1`)**: A file containing functions and scripts. It is the most common type.
*   **Manifest Module (`.psd1`)**: A metadata file that describes the module (version, required dependencies, exported cmdlets). It is used to define the module's structure.
*   **Binary Module**: A compiled module (often C# or compiled code) that provides high performance.
*   **`Import-Module`**: Loads the module's definitions (functions, cmdlets) into the current session's scope, making them available for use.

**PS12** — **String Interpolation**: Allows embedding variables and expressions directly inside a string.
*   **Double Quotes (`"..."`)**: Enables interpolation. Variables are expanded, and expressions can be evaluated using `$()` syntax.
    *   Example: `"The value is $variable."`
*   **Single Quotes (`'...'`)**: Literal interpretation. No interpolation or variable expansion occurs.
    *   Example: `'The value is $variable.'`
*   **Expressions**: Use `$()` to execute code within the string: `"The result is $((2 + 2))."`
*   **Here-String (`@"...@"@`)**: Allows multi-line strings where interpolation is supported. The opening and closing delimiters must be on their own lines.

**PS13** — **`Get-Member`**: A cmdlet used to retrieve the properties, methods, and events of an object passed through the pipeline.
*   **Exploring Objects**: `Get-Member` is the primary tool for introspection.
*   **Properties**: Data fields that hold values (e.g., `Name`, `Age`).
*   **Methods**: Functions that can be called on the object (e.g., `Get-Service.Start()`).
*   **NoteProperties**: Properties that are not directly accessible but are related to the object's internal state (less common).
*   **`Select-Object` vs `Where-Object`**:
    *   **`Select-Object`**: Selects and projects specific properties from objects.
    *   **`Where-Object`**: Filters objects based on a condition (a boolean test).

**PS14** — **PowerShell Classes (v5+)**: Classes allow for object-oriented programming in PowerShell, enabling encapsulation, inheritance, and complex data modeling.
*   **Difference from C# Classes**: PowerShell classes are dynamic and highly flexible. They are designed to integrate seamlessly with the pipeline and are often used to define custom object structures for cmdlets. C# classes are statically typed and compiled.
*   **Limitations**: While they support inheritance and interfaces, they are generally less rigid than C# classes. Constructors are used, but the object creation process is often more dynamic.
*   **Class vs Function**:
    *   **Function**: Best for simple, procedural tasks (e.g., calculating a value, running a single command).
    *   **Class**: Best for modeling complex entities that require state, methods, and inheritance (e.g., a `User` object, a `NetworkDevice` object).

**PS15** — **CmdletBinding and Advanced Functions**:
*   **`[CmdletBinding()]`**: An attribute that enables advanced features for functions, allowing them to behave like native cmdlets (e.g., accepting parameters, handling pipeline input, supporting error actions).
*   **`SupportsShouldProcess`**: Enables the `-WhatIf` and `-Confirm` parameters. This allows the cmdlet to simulate actions without actually executing them, which is crucial for safety.
*   **`DefaultParameterSetName`**: Defines which parameter set is used by default when the cmdlet is called without specifying parameters.
*   **`ValueFromPipeline`**: Allows the cmdlet to accept input objects from the pipeline and assign those objects to a specific parameter.
*   **Blocks**:
    *   **`Begin`**: Runs once before the pipeline starts processing. Used for setup (e.g., connecting to a database).
    *   **`Process`**: Runs for every object received from the pipeline. This is the main logic block.
    *   **`End`**: Runs once after the pipeline has finished processing. Used for cleanup (e.g., closing connections).

**PS16** — **PowerShell Providers System**: A mechanism that allows PowerShell to treat different types of data sources (like file systems, registry keys, or environment variables) as if they were standard file system objects.
*   **How `Get-ChildItem` works**: The cmdlet is generic. When you run `Get-ChildItem`, PowerShell checks the provider specified (or defaults to `FileSystemProvider`). The provider then implements the logic to list items from that specific source (e.g., the Registry Provider lists registry keys).
*   **Accessing Registry**: You use the `Registry` provider:
    ```powershell
    Get-ChildItem -Path "HKLM:\Software" -ProviderName Registry
    ```

**PS17** — **Runspaces and Thread Safety**:
*   **`[runspace]`**: An isolated execution environment where PowerShell commands run. It manages the execution context, including the pipeline and session state.
*   **`[runspacepool]`**: A collection of runspaces that can be reused. This is used for managing parallel execution efficiently, as it avoids the overhead of creating and destroying a new runspace for every task.
*   **`[powershell]`**: The object representing the PowerShell engine itself.
*   **Parallel Execution**:
    *   **`ForEach-Object -Parallel` (v7+)**: The modern, preferred way. It manages the runspace pool internally, simplifying parallel execution and handling thread safety automatically.
    *   **Manual Runspace Management**: Requires the developer to explicitly create, manage, and dispose of the runspaces and runspace pools, which is complex but offers maximum control.

**PS18** — **PSScriptAnalyzer**: A static code analysis tool that checks PowerShell scripts against a set of best practices and coding standards.
*   **Enforcement**: It scans scripts for common anti-patterns, security risks, and style violations (e.g., using deprecated cmdlets, poor variable naming).
*   **Rules/Severity**:
    *   **Rules**: Specific checks defined by PSScriptAnalyzer (e.g., `PSBestPracticeManagement`).
    *   **Severity Levels**: Define the impact of a violation (e.g., `Error`, `Warning`, `Info`).
    *   **Custom Rules**: Users can define their own checks to enforce organizational standards.
*   **Suppression**: Rules can be suppressed using comments (e.g., `# .PARAMETER PSBestPracticeManagement.RuleName -Suppress`) or by configuring the analyzer.
*   **CI/CD Integration**: PSScriptAnalyzer is run as a step in the CI/CD pipeline. If the analyzer finds rules with a severity of `Error`, the pipeline fails, preventing non-compliant code from being merged.

**PS19** — **Scope and Serialization**:
*   **`$using:` scope**: Used when passing variables to parallel jobs (`ForEach-Object -Parallel`). `$using:` allows the parallel job to access variables defined in the parent scope.
*   **`$args` / `-ArgumentList`**: Used when invoking a remote session (`Invoke-Command`). These variables are passed as explicit arguments to the remote script block.
*   **Difference**: `$using:` is for parallel execution within the same machine; `$args` is for remote execution across machines.
*   **Serialization Limits**: When passing complex objects (like large custom classes or nested hashtables) across a network (e.g., via `Invoke-Command`), PowerShell serializes the object (often using CLIXML). This serialization has depth and size limits. If an object is too complex or too large, the transmission fails, requiring the object to be flattened or simplified before transmission.

**PS20** — **Desired State Configuration (DSC)**: A management framework that allows administrators to define the desired state of a system (e.g., "IIS must be installed," "Firewall must be open on port 80") and ensures the system remains in that state.
*   **Configurations**: The blueprint defining the desired state (e.g., a configuration file stating the required services).
*   **Resources**: The building blocks of DSC. A resource is a module that knows how to check and enforce a specific state (e.g., the `Service` resource ensures a service is running).
*   **Local Configuration Manager (LCM)**: The agent running on the target node. It receives the configuration from the central server and uses the resources to enforce the desired state.
*   **DSC Difference (WinPS vs PS 7+)**:
    *   **Windows PowerShell (v5)**: DSC was tightly integrated with Windows Server and relied heavily on the Windows infrastructure.
    *   **PowerShell 7+**: DSC functionality has been modernized and made cross-platform, allowing it to run on Linux and macOS, making it a true cross-platform IaC tool.
*   **Modern Replacement**: While DSC is still used, modern Infrastructure-as-Code (IaC) tools like **Terraform** and **Ansible** have largely replaced DSC for provisioning and configuration management due to their broader scope and declarative nature.
