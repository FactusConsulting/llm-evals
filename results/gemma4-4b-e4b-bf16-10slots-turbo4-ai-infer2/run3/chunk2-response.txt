## Kubernetes

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A Deployment manages stateless applications, ensuring a specified number of identical, interchangeable replicas are running. It treats pods as fungible. A StatefulSet manages stateful applications, providing stable, unique network identifiers and persistent storage to each pod instance. Pods managed by a StatefulSet maintain a specific ordinal index (e.g., `web-0`, `web-1`), which is crucial for clustered databases or stateful services.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
A ClusterIP Service exposes a stable internal IP address within the cluster. It uses `kube-proxy` (which runs on every node) to manage routing. `kube-proxy` typically configures iptables or IPVS rules on the node. When traffic hits the ClusterIP, the rules intercept it and randomly or round-robin forward the traffic to one of the healthy backend Pod IPs selected from the Service's Endpoints list.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator (or dynamically). It is the actual storage resource (e.g., an AWS EBS volume).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a request object that specifies the required size and access mode (e.g., ReadWriteOnce).
*   **StorageClass:** A template that defines the "class" of storage (e.g., fast SSD, slow HDD). It dictates how PVs are dynamically provisioned when a PVC requests storage.
*   **Relationship:** A PVC requests storage based on a specific StorageClass. The StorageClass then instructs the provisioner to create a PV, which is then bound to the PVC, allowing the Pod to mount the storage.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**
1.  **Check Logs:** Use `kubectl logs <pod-name>` to see the application-level error or crash reason.
2.  **Check Events/Status:** Use `kubectl describe pod <pod-name>` to check the events section for scheduling failures, image pull errors, or volume mounting issues.
3.  **Check Configuration:** Verify the Pod spec (ConfigMaps, Secrets, environment variables) are correctly mounted and accessible by the container.
4.  **Check Resources:** Use `kubectl describe pod <pod-name>` to ensure the pod is not being killed by the OOM Killer (Out Of Memory) due to exceeding resource limits.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS acts as the cluster's internal DNS server. It translates service names (e.g., `my-service.default.svc.cluster.local`) and pod names into cluster IP addresses. If CoreDNS pods are down, internal DNS resolution within the cluster fails. Pods will be unable to resolve service names, leading to application connection failures, even if the services themselves are running.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**
The scheduler uses a two-phase process:
1.  **Filtering (Predicates):** The scheduler first filters out nodes that *cannot* run the pod. Factors include:
    *   Resource availability (Node must have enough CPU/Memory).
    *   Taints and Tolerations (Node must not have a taint the pod cannot tolerate).
    *   Node selector/Affinity (Node must match required labels).
2.  **Scoring (Priorities):** From the remaining eligible nodes, the scheduler scores them based on various factors to determine the "best" fit. Factors include:
    *   Least utilized resources (packing pods efficiently).
    *   Node affinity/Anti-affinity rules (e.g., spreading pods across different nodes).
    *   Hardware requirements (e.g., GPU availability).

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
**Scheduling:** No, the pod will likely not be scheduled. The scheduler considers the *requested* resources (256Mi) against the *available* resources (4GB - 3.5GB = 512Mi). Since 256Mi is less than 512Mi, it *should* pass the initial scheduling check based on requests. However, if the cluster uses strict resource management, the scheduler might fail if the total requested resources exceed the node capacity. Assuming standard scheduling, it passes the request check.
**Runtime Behavior:** If the pod uses 600Mi, it will exceed its defined limit (512Mi). Kubernetes will enforce the limit, and the container runtime will terminate the process, resulting in the pod being killed by the OOM Killer (Out Of Memory), leading to a crash and potentially entering `OOMKilled` status.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.**
1.  **External LB:** The request hits the cloud provider's Load Balancer (LB), which routes traffic to the external IP of the NGINX Ingress Controller Pods.
2.  **Ingress Controller:** The NGINX controller receives the request, matches the hostname/path defined in the Ingress resource, and determines the target Service.
3.  **Service:** The Ingress Controller forwards the request to the stable ClusterIP of the target Service.
4.  **kube-proxy/iptables:** `kube-proxy` rules (iptables/IPVS) intercept the traffic destined for the Service ClusterIP.
5.  **Endpoints:** The rules look up the Service's Endpoints object, which lists the actual IP addresses of the healthy backend Pods.
6.  **Pod:** The traffic is routed from the node running the Service/kube-proxy rules to one of the healthy backend Pod IPs, where the application receives the request.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A NetworkPolicy is a Kubernetes resource that defines rules about how groups of pods are allowed to communicate with each other and with external network endpoints.
*   **Default Behavior (No Policy):** By default, Kubernetes is highly permissive. All pods can communicate with all other pods and external endpoints within the cluster unless explicitly restricted.
*   **When Policy is Applied:** If *any* NetworkPolicy exists in a namespace, the default behavior changes to "deny all." Only traffic explicitly allowed by a NetworkPolicy will be permitted. If a policy selects certain pods, only those pods will be subject to the rules defined in that policy.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old versions of pods with new versions. It maintains service availability throughout the update by running both old and new versions concurrently for a period. This is the default and preferred strategy.
*   **Recreate:** Terminates all existing pods running the old version, waits for them to terminate, and then creates all new pods running the new version.
*   **When to Choose Recreate:** You would choose Recreate when the application is highly sensitive to mixed versions (e.g., database schema migrations that cannot handle mixed versions) or when the application requires a clean, fresh start that cannot tolerate transitional states.

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A namespace is a mechanism to partition a single Kubernetes cluster into multiple virtual clusters. It provides scope for names, resources, and access control. The default namespaces typically include `default`, `kube-system` (for cluster components like DNS, scheduler), and sometimes `kube-public` and `kube-node-lease`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
`kubectl describe pod <name>` provides detailed metadata and status information about a specific pod.
1.  **Events:** Shows a chronological list of events related to the pod (e.g., image pull failures, scheduling decisions, volume mounting errors).
2.  **Conditions:** Shows the current state of the pod (e.g., `Ready`, `Progressing`, `Unschedulable`) and why it is in that state.
3.  **Resource/Container Details:** Provides detailed status for each container, including specific container exit codes, restart counts, and resource usage metrics that are not summarized in the basic `get` output.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A ConfigMap is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) that can be injected into Pods.
1.  **As Environment Variables:** The ConfigMap data can be mounted directly as environment variables within the container specification.
2.  **As Mounted Files:** The ConfigMap data can be mounted as a volume (a file system) inside the container, allowing the application to read configuration from a file path.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Exposes the service internally within the cluster using a stable virtual IP. Only reachable from within the cluster.
*   **NodePort:** Exposes the service on a specific port on *every* node in the cluster. This allows external access via `<NodeIP>:<NodePort>`.
*   **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider like AWS/GCP). The LB routes external traffic to the cluster nodes, providing a stable external IP address.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A DaemonSet ensures that a copy of a Pod runs on *every* (or a specified subset of) node in the cluster. You use a DaemonSet when the workload needs to run on every node to provide a cluster-wide service. Examples include log collectors (like Fluentd), monitoring agents (like Prometheus Node Exporter), or network monitoring tools.

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints:** A property applied to a Node that repels (prevents) Pods from being scheduled onto that node unless the Pod explicitly tolerates the taint.
*   **Tolerations:** A property applied to a Pod that allows it to be scheduled onto a Node that has a matching taint.
*   **Node Affinity:** A rule applied to a Pod that *prefers* or *requires* the pod to be scheduled on nodes matching specific labels.
*   **Difference:** Taints/Tolerations are about *repelling* pods from nodes, while Node Affinity is about *attracting* pods to nodes.
*   **Use Case:**
    *   *Taints/Tolerations:* Isolating GPU-intensive workloads onto dedicated GPU nodes (taint the GPU node, only GPU pods tolerate it).
    *   *Node Affinity:* Ensuring a database replica pod is always scheduled on a node with high I/O capacity.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An Operator is a method of packaging, deploying, and managing a complex application (like a database or monitoring system) using Kubernetes patterns.
*   **Difference from Controller:** A standard controller (like Deployment controller) manages a simple desired state (e.g., "I want 3 replicas of this web server"). An Operator extends this by implementing domain-specific knowledge. It watches a Custom Resource Definition (CRD) and contains complex business logic (e.g., "If the database replica fails, automatically trigger a failover, promote a new primary, and update the connection strings").
*   **Problem Solved:** It automates human operational knowledge (the "operator" role) into software, allowing complex, stateful applications to be managed declaratively within Kubernetes.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
*   **Consistency Model:** etcd uses a strong consistency model (Raft consensus algorithm). This ensures that all nodes agree on the state of the cluster data (the single source of truth).
*   **Quorum Loss:** If the quorum (majority) of etcd nodes is lost (e.g., 2 out of 3), the cluster cannot achieve consensus. The cluster becomes read-only or completely unavailable, as no changes can be committed to the state store.
*   **Recovery (2/3 lost):** Recovery is extremely difficult and usually requires manual intervention. If 2 out of 3 nodes are permanently lost, the cluster is permanently broken because the remaining single node cannot form a quorum. The only recovery path is to provision a new etcd cluster (e.g., 3 nodes) and manually bootstrap the remaining data from a backup, effectively losing the state of the lost nodes.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
*   **RBAC Flow:** RBAC defines permissions (verbs like `get`, `list`, `create`) on resources (like `pods`) and binds those permissions to users/groups.
*   **Role:** Defines permissions *within a specific namespace*.
*   **ClusterRole:** Defines permissions across *all* namespaces.
*   **RoleBinding:** Binds a Role to a user/group *within a specific namespace*.
*   **ClusterRoleBinding:** Binds a ClusterRole to a user/group across *all* namespaces.
*   **Manifests (Read-only access to pods/logs in `my-namespace`):**

```yaml
# 1. Define the permissions (Role)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader-role
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"] # Accessing logs
  verbs: ["get"]

---
# 2. Bind the permissions to a user/group (RoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: my-namespace
subjects:
- kind: User # Or Group
  name: developer-user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader-role
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
The `ndots` setting in `/etc/resolv.conf` specifies the maximum number of dots (periods) a local DNS resolver should attempt to match before querying external nameservers. If `ndots` is set too low (e.g., 1), and the pod tries to resolve a fully qualified domain name (FQDN) like `api.service.example.com`, the resolver will first try to match `api.service.example.com` against local hostnames. If it fails, it will query external DNS. If the pod is constantly trying to resolve FQDNs, and `ndots` is low, the resolver might perform unnecessary, slow lookups for internal hostnames before giving up and querying external servers, leading to perceived slowness.
**Fix:** Set `dnsConfig` in the Pod spec to explicitly define the `options` and ensure the `ndots` value is appropriate for the application's needs, or simply ensure the cluster's CoreDNS is configured correctly to handle external resolution efficiently.

## Development

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
*   **Merge:** Combines two or more divergent branches by creating a new "merge commit." It preserves the history exactly as it happened, showing the branching structure.
*   **Rebase:** Rewrites history by moving the entire feature branch to start on top of the target branch. It creates a linear history, making the commit history cleaner and easier to follow.
*   **When to Avoid Rebasing:** Never rebase commits that have already been pushed to a shared, public repository. Rebasing rewrites history (changes commit SHAs), which causes major conflicts and confusion for collaborators who have already pulled the original history.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP (Transmission Control Protocol):** Connection-oriented, reliable, and ordered. It establishes a handshake (SYN, SYN-ACK, ACK) and guarantees that data arrives completely and in sequence. Used for applications where data integrity is paramount. (Protocols: HTTP/HTTPS, FTP, SSH).
*   **UDP (User Datagram Protocol):** Connectionless, unreliable, and unordered. It sends packets without establishing a handshake and offers no guarantee of delivery or order. Used for applications where speed and low latency are more critical than perfect delivery. (Protocols: DNS, VoIP, Streaming Video).

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A race condition occurs when the output or outcome of a program depends on the sequence or timing of uncontrollable events (like thread scheduling). If multiple threads access and modify shared data concurrently, and the final result depends on which thread finishes last, a race condition exists.
**Example (Counter Increment):**
If two threads try to increment a shared counter initialized to 0:
1. Thread A reads counter (0).
2. Thread B reads counter (0).
3. Thread A calculates 0 + 1 = 1 and writes 1.
4. Thread B calculates 0 + 1 = 1 and writes 1.
The expected result is 2, but the actual result is 1, because the operations overlapped.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is fast and efficient for bulk data encryption.
*   **Asymmetric Encryption:** Uses a pair of keys: a public key (shared widely) and a private key (kept secret). Data encrypted with the public key can only be decrypted by the corresponding private key. It is computationally expensive but essential for secure key exchange.
*   **TLS Usage:**
    1.  **Handshake (Asymmetric):** The client uses the server's public key (from its certificate) to securely exchange a temporary, random **symmetric session key** with the server.
    2.  **Data Transfer (Symmetric):** Once the session key is established, all subsequent bulk data transfer is encrypted using the fast symmetric algorithm (e.g., AES) using that session key.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
A container image layer is a read-only, immutable snapshot of the filesystem state created during the build process. Each instruction in a Dockerfile (e.g., `RUN`, `COPY`, `ADD`) creates a new layer on top of the previous one.
**Layer Caching Best Practices:** Docker caches layers based on the instruction and the content of the files used. To maximize caching and speed up builds:
1.  **Order Matters:** Place instructions that change infrequently (like installing OS dependencies, `RUN apt-get install`) early in the Dockerfile.
2.  **Minimize Changes:** Place instructions that change frequently (like copying application code, `COPY . /app`) later. If the application code changes, only the final layers are rebuilt, not the entire image.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**
1.  **Service Health/Resource Saturation (Immediate Check):** Check CPU/Memory usage of the application pods. Is the service hitting resource limits or running out of memory? (This is the most common cause of 503s).
2.  **Dependency Health (External Check):** Check the health and latency of upstream services or databases the API relies on. A 503 often means the service cannot connect to a required dependency.
3.  **Load Balancer/Ingress Health (Infrastructure Check):** Check the logs and metrics of the Ingress Controller or Load Balancer. Is it failing health checks, or is it overloaded/throttling requests?
4.  **Application Logs/Error Traces (Deep Dive):** Review the application logs for specific exceptions (e.g., connection timeouts, connection pool exhaustion, thread pool saturation) that occur just before the 503 response is generated.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
The CAP theorem states that a distributed data store can only guarantee two out of three properties: **C**onsistency, **A**vailability, and **P**artition Tolerance. In a distributed system, Partition Tolerance (P) is usually mandatory, forcing a trade-off between C and A.
*   **CP (Consistency over Availability):** If a network partition occurs, the system sacrifices availability to ensure that all nodes return the same, consistent data.
    *   *Example:* Traditional relational databases (like PostgreSQL/MySQL clusters) configured for strong consistency. If the primary node cannot communicate with the replicas, the system may refuse writes to maintain data integrity.
*   **AP (Availability over Consistency):** If a network partition occurs, the system remains available, even if some nodes return stale data.
    *   *Example:* Cassandra or DynamoDB. If a node is unreachable, the system continues serving reads/writes from other nodes, prioritizing uptime over immediate global consistency.

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) of a single existing server or instance. It is simpler but has physical limits.
*   **Horizontal Scaling (Scaling Out):** Adding more instances (servers/pods) to distribute the load. This is the preferred method in cloud-native architectures.
*   **Architectural Patterns for Horizontal Scaling:**
    1.  **Statelessness:** The application must not store session data locally; all state must be externalized (e.g., in Redis or a database).
    2.  **Load Balancing:** Using a load balancer to distribute incoming requests evenly across multiple instances.
    3.  **Microservices:** Breaking the application into small, independent services that can be scaled individually.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An environment variable is a dynamic named value that can affect the way running processes behave on a computer. It allows configuration to be externalized from the code.
To set a variable that persists across shell sessions on Linux, you must add the definition to a shell configuration file, such as `~/.bashrc` or `~/.zshrc`.
*Example:* `export MY_VAR="value"` added to `~/.bashrc`.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
*   **JSON (JavaScript Object Notation):** A lightweight data-interchange format that uses key-value pairs and arrays. It is natively supported by JavaScript and is widely used for API data transfer.
    *   *Advantage:* Excellent for machine parsing and is the standard for web APIs.
*   **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard. It uses indentation and minimal syntax to represent complex data structures.
    *   *Advantage:* Highly readable and is the standard configuration format for Kubernetes and infrastructure tools.

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
A REST (Representational State Transfer) API is an architectural style for designing networked applications, typically using HTTP methods to perform CRUD (Create, Read, Update, Delete) operations on resources.
*   **GET:** Retrieves a resource or a collection of resources. (Read)
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource. (Create)
*   **PUT:** Replaces an entire resource with the data provided in the request body. (Update/Replace)
*   **DELETE:** Removes the specified resource. (Delete)

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
Version pinning is the practice of specifying an exact, fixed version number for every dependency in a project (e.g., `library@1.2.3` instead of `library@^1.2`).
**Importance:** It ensures reproducible builds. Without pinning, a dependency update (e.g., from 1.2.3 to 1.2.4) might introduce breaking changes or subtle bugs that were not tested, causing the application to fail in production, even if the code itself hasn't changed.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled Language:** Source code is translated entirely into machine code (binary executable) *before* runtime by a compiler. This results in faster execution speed. (Examples: C++, Go, Rust).
*   **Interpreted Language:** Source code is executed line-by-line at runtime by an interpreter. This allows for greater flexibility and easier debugging but is generally slower than compiled code. (Examples: Python, Ruby, JavaScript).

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
*   **Reverse Proxy:** Sits in front of web servers/applications. It intercepts client requests and forwards them to the appropriate backend server. The client never knows the identity of the backend server.
    *   *Use Case:* Load balancing, SSL termination, and hiding the internal network structure.
*   **Forward Proxy:** Sits in front of clients. It intercepts requests from clients and forwards them to the internet on behalf of the clients.
    *   *Use Case:* Anonymizing client requests or enforcing corporate access policies/filtering.
*   **Servers:** NGINX, HAProxy.

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A deadlock is a state in a concurrent system where two or more competing actions are waiting for each other to finish, and thus neither ever finishes.
The four necessary conditions (Coffman conditions) are:
1.  **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2.  **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3.  **No Preemption:** A resource cannot be forcibly taken from a process; it must be voluntarily released.
4.  **Circular Wait:** A set of processes must exist where each process in the set is waiting for a resource held by the next process in the set.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
**Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. It prioritizes availability over immediate consistency.
**Cassandra Handling:** Cassandra uses a decentralized, peer-to-peer architecture. When a write occurs, it is written to a quorum of nodes. Read-after-write consistency is managed by the client specifying a **Consistency Level (CL)** for both reads and writes.
**Tunable Consistency Levels:**
*   **Write CL:** Specifies how many replicas must acknowledge the write before it is considered successful (e.g., `QUORUM`).
*   **Read CL:** Specifies how many replicas must respond to the read request.
*   *Read-After-Write:* To guarantee read-after-write consistency, the client must ensure that the Read CL + Write CL > Total Replicas (N).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
**mTLS (Mutual TLS):** An extension of standard TLS where *both* the client and the server authenticate each other using digital certificates, not just the server authenticating to the client.
**Handshake Process:**
1.  **Client Hello:** Client initiates the connection.
2.  **Server Hello & Certificate:** Server sends its certificate.
3.  **Client Certificate Request:** Server requests the client's certificate.
4.  **Client Certificate & Verification:** Client sends its certificate and proves possession of the private key (by signing a challenge).
5.  **Server Verification:** Server verifies the client's certificate against its trusted CAs.
6.  **Key Exchange:** Both parties securely exchange the symmetric session key.
7.  **Secure Communication:** Data is encrypted using the symmetric key.
**Use Case:** Service Mesh communication (e.g., Istio, Linkerd) where microservices must cryptographically verify the identity of every service they communicate with, ensuring zero-trust networking.

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
A hash table maps keys to values using a hash function, which converts the key into an index (bucket) in an array.
*   **Collision:** Occurs when two different keys hash to the same index.
*   **Collision Resolution:**
    *   **Chaining:** Each bucket holds a pointer to a linked list (or other data structure) containing all key-value pairs that hash to that index.
    *   **Open Addressing:** If a bucket is full, the algorithm probes for the next available empty slot in the array (e.g., linear probing, quadratic probing).
*   **Time Complexity:**
    *   *Average Case (Good Hash Function, Low Load):* $O(1)$ for insertion, lookup, and deletion.
    *   *Worst Case (All keys hash to the same bucket):* $O(N)$ for all operations, as the table degrades into a linked list.

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
A circuit breaker is a design pattern used to prevent an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing microservice). This prevents resource exhaustion and cascading failures.
**States:**
1.  **Closed:** Normal operation. Requests pass through. If the failure rate exceeds a threshold, the circuit trips to Open.
2.  **Open:** The circuit blocks all requests immediately, failing fast without attempting the call. This gives the failing service time to recover.
3.  **Half-Open:** After a timeout, the circuit allows a small number of test requests through. If these succeed, the circuit closes; if they fail, it returns to Open.
**Relation to Retries/Backoff:** Circuit breakers prevent the need for aggressive retries. If the circuit is open, retries are blocked. If the service is recovering, exponential backoff is used for retries to avoid overwhelming the recovering service with a sudden flood of requests.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**
*   **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data *before* the transaction reads or modifies it, preventing other transactions from accessing the data until the lock is released.
    *   *When to Choose:* High-contention environments where data integrity is paramount and conflicts are frequent (e.g., banking transactions).
    *   *Example:* Using `SELECT ... FOR UPDATE` in SQL, which places an exclusive lock on the selected rows.
*   **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Instead, they check for conflicts *before* committing. If the data has changed since the transaction started, the transaction is rolled back and retried.
    *   *When to Choose:* Low-contention environments where throughput is more important than immediate locking (e.g., e-commerce product reviews).
    *   *Example:* Using row versioning (a timestamp or version number column). The update query includes a `WHERE version = original_version`. If the version doesn't match, the update fails, indicating a conflict.
