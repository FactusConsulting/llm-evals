## Go (20 questions)

**G1 — Easy: What is the difference between a slice and an array in Go? What happens when you append to a slice that has reached its capacity?**
A slice is a dynamically sized, view into an underlying array, while an array has a fixed size defined at compile time. When you append to a slice that has reached its capacity, Go automatically allocates a new, larger underlying array (typically doubling the capacity), copies the existing elements over, and then appends the new element.

**G2 — Easy: Explain the difference between `var x int` and `x := 0`. When can you NOT use `:=`?**
`var x int` declares a variable and initializes it to its zero value (0 for `int`). `x := 0` is a short variable declaration, which declares and initializes the variable in one step. You cannot use `:=` when declaring a variable outside of a function body (at the package level) or when you are reassigning a variable that has already been declared using `var`.

**G3 — Medium: What is a goroutine, and how does it differ from an OS thread? What is the role of the Go scheduler (GMP model)?**
A goroutine is a lightweight, independently executing function managed by the Go runtime, not the OS. It is much cheaper to create and manage than an OS thread. The Go scheduler (GMP model) maps $G$ (Goroutines) onto $M$ (OS Threads), which are run by $P$ (Processors/Logical CPUs). The scheduler dynamically manages the distribution of goroutines across available OS threads to maximize CPU utilization.

**G4 — Medium: Explain how channels work in Go. What is the difference between a buffered and unbuffered channel? What happens when you send to a full buffered channel?**
Channels are typed conduits through which goroutines communicate and synchronize. An unbuffered channel requires both the sender and receiver to be ready simultaneously (synchronous communication). A buffered channel has a finite capacity, allowing the sender to proceed without waiting until the buffer is full. When sending to a full buffered channel, the sender goroutine blocks until a receiver reads an element, freeing up space.

**G5 — Medium: What is the context package used for? Write a minimal example of using context.WithTimeout to cancel a long-running HTTP request.**
The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and goroutine calls. This is crucial for managing the lifecycle of requests.

*Minimal Example:*
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // Always call cancel to release resources

req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
// ... use req in client.Do(req)
```

**G6 — Medium: Explain Go's interface satisfaction model. How does it differ from Java/C# interfaces? What is the empty interface interface{} (or any) and why is it both powerful and dangerous?**
Go uses implicit satisfaction: a type satisfies an interface simply by implementing all the methods defined by that interface; no explicit declaration is needed. This differs from Java/C# where explicit `implements` keywords are required. The empty interface (`interface{}` or `any`) can hold a value of any type. It is powerful because it allows for generic handling of unknown types, but it is dangerous because it requires type assertions or reflection to use the underlying value, leading to runtime panics if the type assertion fails.

**G7 — Hard: Explain Go's memory model regarding goroutine visibility. Why is the following unsafe, and what are the correct alternatives?**
The Go memory model guarantees that writes made by one goroutine are visible to other goroutines only if synchronization primitives (like channels or mutexes) are used. The provided code is unsafe because the write to `data` and `ready` happens in a separate goroutine without any synchronization mechanism. The main goroutine might read the stale, zero-value state of `data` before the write completes.

*Correct Alternatives:*

**G8 — Hard: What is the difference between sync.Mutex and sync.RWMutex? When would you use sync.Map vs a regular map with a mutex? What are the performance trade-offs?**
`sync.Mutex` provides exclusive locking (only one goroutine can hold the lock at a time). `sync.RWMutex` allows multiple readers simultaneously but requires exclusive locking for writers. Use `RWMutex` when reads vastly outnumber writes.

Use `sync.Map` when you have a map where keys are unknown or frequently added/deleted concurrently, and you want to avoid the overhead of locking the entire map structure. A regular map with a mutex is generally faster for high-read/low-write scenarios because the mutex overhead is minimal, whereas `sync.Map` has more complex internal locking mechanisms.

**G9 — Hard: Explain how Go modules work. What is the difference between go.mod and go.sum? What does go mod tidy do, and what is the Minimum Version Selection (MVS) algorithm?**
Go modules manage dependencies. `go.mod` lists the required modules and their versions. `go.sum` contains cryptographic checksums of the dependencies listed in `go.mod` to ensure integrity and prevent supply chain attacks. `go mod tidy` cleans up the module files by removing unused dependencies and adding any missing ones required by the source code. MVS is an algorithm that selects the highest version of a dependency that satisfies all constraints and is compatible with the project's requirements.

**G10 — Medium: What is a defer statement? In what order do multiple defers execute? What is a common gotcha with defer in a loop?**
`defer` schedules a function call to be executed immediately before the surrounding function returns. Defers execute in Last-In, First-Out (LIFO) order. The common gotcha is when a defer statement captures a loop variable. If the loop runs multiple times, the deferred function will execute *after* the loop finishes, and all deferred calls will reference the final value of the loop variable, not the value it had during that specific iteration.

**G11 — Easy: What is a pointer in Go? What is the zero value of a pointer? How do you create a pointer to a struct literal?**
A pointer is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12 — Easy: Explain Go's init() function. When does it run? Can a package have multiple init() functions, and if so, in what order do they execute?**
The `init()` function is a special function that runs automatically before the `main` function of a package. It is used for setup tasks (e.g., initializing global variables). A package can have multiple `init()` functions; they execute in the order they are defined in the source code, and package-level `init()` functions run before any `main` function.

**G13 — Easy: What is the difference between make and new in Go? What types does each work with?**
`make` is used to initialize built-in reference types (slices, maps, channels). It allocates and initializes the underlying data structure. `new` allocates memory for a value of a specified type and returns a pointer to the zero value of that type. `new` works with any type, but it does not initialize the contents.

**G14 — Easy: How does error handling work in Go? What is the error interface, and what is the idiomatic pattern for checking errors? How do errors.Is and errors.As differ from ==?**
Error handling is done by returning an `error` type (which satisfies the built-in `error` interface, requiring an `Error() string` method). The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`.
* `errors.Is(err, target)` checks if the error chain contains a specific sentinel error value.
* `errors.As(err, target)` checks if the error chain contains a specific error type, allowing you to extract structured information from it.
* `==` only checks for exact pointer equality, which is rarely useful for complex error chains.

**G15 — Easy: What are Go's built-in composite types (map, slice, channel, struct)? What is the zero value of each?**
* **Map:** `map[K]V`. Zero value: `nil`.
* **Slice:** `[]T`. Zero value: `nil` (a nil slice).
* **Channel:** `chan T`. Zero value: `nil`.
* **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.

**G16 — Medium: What is a race condition in Go? How does the -race flag work? Give an example of a data race and show how to fix it with sync.Mutex or a channel.**
A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization. The `-race` flag in the Go toolchain detects these unsynchronized concurrent memory accesses.

*Example Fix (Mutex):*
```go
var data int
var mu sync.Mutex

func increment() {
    mu.Lock()
    data++ // Protected access
    mu.Unlock()
}
```

**G17 — Medium: Explain Go's select statement. How does it differ from a switch? What happens when multiple cases are ready? How do you implement a timeout with select?**
The `select` statement waits on multiple communication operations (channel receives/sends). It differs from `switch` because `switch` evaluates expressions, while `select` waits for I/O or communication events. When multiple cases are ready, `select` chooses one of them pseudo-randomly. To implement a timeout, you use `select` alongside a `time.After` channel:
```go
select {
case result := <-ch:
    // Process result
case <-time.After(5 * time.Second):
    // Timeout occurred
}
```

**G18 — Hard: What is escape analysis in Go? How does the compiler decide whether to allocate on the stack or the heap? How can you inspect escape analysis decisions, and why does it matter for performance?**
Escape analysis is a compiler optimization that determines whether a variable's memory allocation must live only within the function's scope (stack allocation) or if it must persist beyond the function's return (heap allocation). The compiler decides based on whether the variable's address is returned or stored in a global/escaped location. It matters because stack allocation is extremely fast and avoids garbage collection overhead, while heap allocation requires more complex memory management.

**G19 — Hard: Explain Go's reflection package (reflect). What is reflect.Type vs reflect.Value? What are the performance costs, and when is reflection justified vs code generation?**
The `reflect` package allows inspecting and manipulating types and values at runtime. `reflect.Type` describes the type (metadata), while `reflect.Value` represents a specific instance of that type. Reflection incurs significant performance overhead because it bypasses compile-time type safety and requires runtime introspection. It is justified only when dynamic behavior (e.g., serialization, ORMs, plugin systems) is absolutely necessary; otherwise, code generation is preferred for performance.

**G20 — Hard: What is the go:embed directive? How does it work for single files, directories, and file systems? What are the limitations, and how does it interact with io/fs.FS?**
The `go:embed` directive allows embedding external assets (files, directories) directly into the compiled binary. It works by treating the embedded content as a string or a file system interface. It can embed single files, entire directories, or custom `fs.FS` implementations. The limitation is that the embedded content is static and cannot be dynamically modified at runtime. It integrates seamlessly with `io/fs.FS`, allowing embedded assets to be treated like any other file system resource.

## Rust (20 questions)

**R1 — Easy: What is ownership in Rust? Explain the three ownership rules.**
Ownership is Rust's system for managing memory without a garbage collector. It dictates that every value in Rust has a single variable that is its *owner*. The three rules are:
1. Every value has an owner.
2. There can only be one owner at a time.
3. When the owner goes out of scope, the value is dropped (memory is freed).

**R2 — Easy: What is the difference between String and &str? When would you use each in function signatures?**
`String` is a heap-allocated, mutable, growable UTF-8 string type (owned data). `&str` is a string slice—a borrowed, immutable reference to a sequence of UTF-8 bytes (a view into data, which could be owned or static).
* Use `String` when you need to own and modify the string data.
* Use `&str` in function signatures when you only need to read the string data, as it avoids unnecessary memory allocation and copying.

**R3 — Medium: Explain borrowing and the borrow checker. What are the rules for shared (&T) and mutable (&mut T) references?**
Borrowing allows you to use a value without taking ownership of it. The borrow checker enforces Rust's rules to prevent data races at compile time.
* **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously.
* **Mutable Reference (`&mut T`):** Allows only one mutable reference to the data at any given time.
* **The Rule:** You can have either many immutable references OR exactly one mutable reference, but never both concurrently.

**R4 — Medium: What is a Result<T, E> and an Option<T>? How does the ? operator work? Write a function that reads a file and returns its contents or an error.**
* **`Option<T>`:** Represents a value that may or may not be present (`Some(T)` or `None`).
* **`Result<T, E>`:** Represents an operation that may succeed (`Ok(T)`) or fail (`Err(E)`).
* **`?` Operator:** This operator is syntactic sugar for propagating errors. If the expression it is applied to is an `Err`, the function immediately returns that error. If it is `Ok`, it unwraps the value and continues execution.

*Example:*
```rust
use std::fs;
use std::io;

fn read_file(path: &str) -> Result<String, io::Error> {
    // If fs::read_to_string returns Err, the ? operator returns that Err immediately.
    let contents = fs::read_to_string(path)?;
    Ok(contents)
}
```

**R5 — Medium: Explain the difference between Box<T>, Rc<T>, and Arc<T>. When would you use each?**
All three enable heap allocation and shared ownership, but they differ in how they manage reference counting:
* **`Box<T>`:** A smart pointer that allocates data on the heap. It is used when you need to put a type on the heap (e.g., recursive types) or when you want to hide the size of a type. It is non-shared.
* **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data. The data is dropped only when the last `Rc` pointing to it is dropped. Used for single-threaded shared ownership.
* **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>`, but uses atomic operations for reference counting, making it safe to share across multiple threads (thread-safe).

**R6 — Medium: What are traits in Rust? How do they compare to Go interfaces? What is a trait object (dyn Trait) vs a generic with a trait bound (T: Trait)?**
Traits define shared behavior (like interfaces). They specify a set of methods that a type must implement.
* **Comparison to Go:** Traits are more powerful than Go interfaces because they can define default implementations for methods, whereas Go interfaces only define signatures.
* **Generic (T: Trait):** Provides static dispatch. The compiler knows the concrete type at compile time, leading to zero-cost abstraction (monomorphization).
* **Trait Object (`dyn Trait`):** Provides dynamic dispatch. The compiler does not know the concrete type until runtime, requiring a vtable lookup, which incurs a small runtime cost.

**R7 — Hard: Explain lifetimes in Rust. Why does the following fail to compile, and how do you fix it?**
*Failure:* The function signature `fn longest(x: &str, y: &str) -> &str` implies that the returned reference (`&str`) lives as long as the function call. However, the reference points to either `x` or `y`, which are local variables passed into the function. Once the function returns, these local variables are dropped, invalidating the returned reference.

*Fix:* We must use lifetime annotations (`'a`) to tell the compiler that the returned reference's lifetime is tied to the lifetime of the shortest input reference.
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

**R8 — Hard: What is Send and Sync in Rust? Why can't you send an Rc<T> across threads? What makes Arc<T> safe for concurrent use?**
* **`Send`:** A marker trait indicating that a type can be safely moved to another thread.
* **`Sync`:** A marker trait indicating that a type can be safely referenced across thread boundaries (i.e., multiple threads can hold shared references to it).
* **`Rc<T>`:** Is not `Send` or `Sync` because its internal reference counting mechanism is not atomic, leading to potential data races if accessed concurrently.
* **`Arc<T>`:** Is safe for concurrent use because its reference counting is implemented using atomic operations, ensuring that the count is updated safely even when multiple threads are modifying it simultaneously.

**R9 — Hard: Explain how Rust's async/await works under the hood. What is a Future? What is the role of the executor (e.g., Tokio)? How does this differ from Go's goroutines?**
* **Future:** A trait representing a value that may not be available yet. It is a state machine that implements the `poll` method. When polled, it checks if the operation is complete; if not, it registers a Waker and returns `Poll::Pending`.
* **Executor (Tokio):** The executor is the runtime that drives the futures. It polls the futures, managing the asynchronous execution flow.
* **Difference from Goroutines:** Go uses green threads managed by a runtime scheduler (M:N model). Rust's async/await is based on cooperative multitasking. The futures yield control back to the executor when they are blocked (e.g., waiting for I/O), allowing the executor to poll other ready futures.

**R10 — Medium: What is unsafe in Rust? Give 3 things you can do in an unsafe block that you can't do in safe Rust. When is unsafe justified?**
`unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees.
* **Things you can do:** Dereference raw pointers, call `unsafe` functions, and implement `unsafe` traits.
* **When justified:** When interacting with external C libraries (FFI), implementing highly optimized data structures, or when the programmer has proven mathematically that the safety invariants are maintained.

**R11 — Easy: What is pattern matching in Rust? How does match differ from if let? What does the compiler enforce about exhaustiveness?**
Pattern matching is a powerful control flow mechanism that allows matching values against patterns (e.g., matching on enum variants or struct fields).
* **`match` vs `if let`:** `match` is exhaustive and powerful, allowing complex pattern matching and binding variables. `if let` is syntactic sugar for matching a single pattern and is used when you only care about one specific case.
* **Exhaustiveness:** The compiler enforces exhaustiveness in `match` statements, meaning you must handle every possible variant of the enum or pattern, preventing runtime bugs.

**R12 — Easy: What is the difference between Vec<T> and an array [T; N]? How does Vec manage memory when elements are pushed beyond its current capacity?**
An array `[T; N]` has a fixed size $N$ determined at compile time and is typically allocated on the stack. `Vec<T>` is a heap-allocated, dynamically sized vector.
When `Vec<T>` is pushed beyond its capacity, it performs a reallocation: it allocates a new, larger block of memory (often doubling the capacity), copies all existing elements from the old memory location to the new one, and then deallocates the old memory.

**R13 — Easy: What are enums in Rust, and how do they differ from enums in C or Java? What is the Option<T> enum, and why does Rust not have null?**
Rust enums are powerful algebraic data types that can hold data (variants). Unlike C/Java enums, Rust enums can have associated data (e.g., `enum Message { Quit, Move { x: i32, y: i32 } }`).
`Option<T>` is an enum variant of `Some(T)` or `None`. Rust avoids `null` because `None` is a type-safe, explicit variant of the `Option` enum, forcing the programmer to handle the absence of a value explicitly, thus eliminating null pointer exceptions.

**R14 — Easy: Explain the impl block. What is the difference between methods that take &self, &mut self, and self? What are associated functions (e.g., String::new())?**
The `impl` block defines methods and associated functions for a specific type.
* **`&self`:** Takes an immutable reference; the method can read the data but not change it.
* **`&mut self`:** Takes a mutable reference; the method can read and modify the data.
* **`self`:** Takes ownership of the instance; the method consumes the instance.
* **Associated Functions:** Functions defined within the `impl` block that do not take `self` (like `String::new()`). They are called directly on the type, not on an instance.

**R15 — Easy: What is the derive macro? Give examples of commonly derived traits (Debug, Clone, PartialEq, Serialize). When can you NOT derive a trait?**
A derive macro is a procedural macro that automatically implements standard traits for a struct or enum based on its structure.
* **Examples:** `#[derive(Debug)]` (allows printing with `{:#?}`), `#[derive(Clone)]` (allows deep copying), `#[derive(PartialEq)]` (allows `==` comparison), `#[derive(Serialize)]` (for serialization).
* **Cannot derive:** You cannot derive a trait if the type contains a field that itself cannot implement that trait (e.g., if a struct contains a raw pointer or a type that doesn't implement `Clone`).

**R16 — Medium: What is Cow<'a, T> (clone on write)? When is it useful? Give an example where it avoids unnecessary allocations compared to always cloning.**
`Cow<'a, T>` (Clone-on-Write) is a smart pointer that can hold either an owned value (`T`) or a borrowed reference (`&T`). It is useful when a function might receive data that is either already owned or is a slice/reference, and you only need to modify it sometimes.
* **Example:** If a function receives a string slice (`&str`), it uses the borrowed reference (no allocation). If the function needs to modify it, `Cow` automatically clones the data into an owned `String` only at the moment of modification, avoiding unnecessary allocations when the data is read-only.

**R17 — Medium: Explain Rust's module system. What is the difference between mod, use, and pub? How does the file system map to modules, and what changed between Rust 2015 and 2018 editions?**
* **`mod`:** Declares a module, which can contain other items (structs, functions, other modules).
* **`use`:** Brings items from another module into the current scope, allowing them to be referenced without the full path.
* **`pub`:** Makes items visible outside their defining module.
* **File System Mapping:** Rust modules map directly to the file system structure (e.g., `mod foo;` often corresponds to a file `foo.rs` or a directory `foo/`).
* **2018 Edition Change:** The 2018 edition introduced the ability to define modules in separate files (e.g., `mod foo;` pointing to `foo.rs`), which was previously limited to inline definitions.

**R18 — Hard: What is the Pin<T> type and why is it needed? How does it relate to self-referential structs and async/await? What is Unpin?**
* **`Pin<T>`:** A wrapper that guarantees that the data pointed to by `T` will not be moved in memory after it has been pinned.
* **Need:** It is crucial for self-referential structs (where a part of the struct holds a pointer to another part of the same struct) and for async/await. When an async function is polled, its state machine must maintain its memory location; if the compiler were allowed to move the state machine, the internal pointers would become invalid.
* **`Unpin`:** A marker trait indicating that a type is safe to move in memory. If a type does not implement `Unpin`, it must be wrapped in `Pin` to prevent movement.

**R19 — Hard: Explain Rust's macro system. What is the difference between declarative macros (macro_rules!) and procedural macros (derive, attribute, function-like)? What are hygiene rules?**
* **Declarative Macros (`macro_rules!`):** Pattern matching macros that operate on tokens (syntactic sugar). They are simple and used for repetitive code generation (e.g., simple loops, simple function calls).
* **Procedural Macros:** Macros that operate on the Abstract Syntax Tree (AST) of the code. They are much more powerful and are used for complex code generation (e.g., `#[derive(Serialize)]`, custom attribute macros).
* **Hygiene Rules:** These rules prevent macro expansion from accidentally capturing or interfering with identifiers defined by the user in the surrounding scope. They ensure that macro-generated code is locally scoped and does not pollute the user's namespace.

**R20 — Hard: What are zero-cost abstractions in Rust? Explain how iterators, generics (monomorphization), and trait static dispatch achieve performance comparable to hand-written C while providing high-level ergonomics.**
Zero-cost abstractions mean that the high-level features (like iterators, traits, generics) do not impose a runtime performance penalty compared to writing the equivalent low-level code.
* **Generics (Monomorphization):** When generics are used, the compiler generates a specialized version of the code for every concrete type used. This eliminates the need for runtime type checks or virtual function lookups, resulting in highly optimized, type-specific machine code.
* **Trait Static Dispatch:** When a trait is used with generics (e.g., `fn process<T: Trait>(item: T)`), the compiler resolves the exact method call at compile time, similar to C++ templates, avoiding the runtime overhead of dynamic dispatch (vtable lookups).
* **Iterators:** Rust's iterator trait allows for lazy evaluation and chaining of operations (map, filter, etc.) without creating intermediate collections, minimizing memory overhead and maximizing efficiency.
