## OpenTofu / Terraform (20 questions)

**T1 — Easy:** The `tofu plan` command calculates the difference between the desired state (defined in the HCL configuration) and the actual state (as recorded in the state file and observed in the cloud provider). It shows *what* changes will be made. The `tofu apply` command executes those calculated changes, modifying the infrastructure to match the desired state.

**T2 — Easy:** State in OpenTofu is a file (usually stored remotely) that maps the resources defined in the configuration to the real-world infrastructure objects in the cloud. It acts as a database of the infrastructure. Remote state is crucial because it allows multiple team members and CI/CD pipelines to safely collaborate on the same infrastructure without overwriting each other's changes, and it provides a single source of truth for the entire infrastructure lifecycle.

**T3 — Medium:**
*   **`count`**: Creates a specified number of *identical* instances. If you change the count, all instances are recreated.
*   **`for_each`**: Creates instances based on the elements of a map or set. Each instance is uniquely identified by the key/value provided in the input.
*   **Preference**: `for_each` is preferred when the instances need unique identities or when you need to manage them individually (e.g., `web1`, `web2`). If you use `count`, changing the order of elements can cause OpenTofu to destroy and recreate resources unnecessarily.

**T4 — Medium:** This is known as **configuration drift**. If you manually change a resource outside of OpenTofu, the actual state diverges from the desired state recorded in the HCL. When you run `tofu plan`, OpenTofu detects this drift by querying the cloud provider API and comparing the actual attributes to the attributes defined in the configuration. It will report the difference as a planned change, allowing you to either accept the drift (by ignoring the change) or correct the drift (by updating the HCL to match the manual change).

**T5 — Medium:**
```hcl
resource "aws_instance" "web_server" {
  count = length(toset(["web1", "web2", "web3"]))
  for_each = toset(["web1", "web2", "web3"])

  ami           = "ami-0abcdef1234567890"
  instance_type  = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

**T6 — Hard:**
*   **`terraform_remote_state` data source**: Used to read the state of resources managed by *another* OpenTofu configuration or module. It fetches specific attributes (like an IP address or ARN) from a remote state file.
*   **Output values**: Used to expose data *from* the current module/root configuration to consumers (e.g., exposing a VPC ID).
*   **Difference**: Data sources are for *reading* external state; outputs are for *exposing* internal state.
*   **Recommended Alternative**: The recommended alternative is to use **module outputs** and pass them as inputs to consuming modules. This maintains clear dependency boundaries and avoids coupling modules to external state files, leading to better modularity and testability.

**T7 — Hard:** The issue arises because the `null_resource` provisioner runs *after* the resource is created, but the kubeconfig output might not be immediately available or stable during the initial API call. The provisioner attempts to execute the remote command before the necessary service or file is fully ready.
**Fix:** Instead of relying on a provisioner, the fix is to use a **data source** or a **local-exec provisioner** that explicitly waits for the resource to stabilize, or, more robustly, use a dedicated resource (like a Kubernetes provider resource) that handles the dependency internally. If the output is truly dynamic, you must ensure the dependency graph is explicit using `depends_on` to force the kubeconfig generation step to wait for the RKE2 cluster to be fully operational.

**T8 — Medium:** `tofu import` allows you to take an existing piece of infrastructure (e.g., an existing AWS EC2 instance) and register it into your OpenTofu state file, allowing you to manage it with the configuration code.
**Limitations**: The primary limitation is that you must know the exact resource type and the unique ID of the existing resource.
**Improvement (1.5+)**: The import block allows you to define the resource type and the ID *within* the configuration file itself, rather than relying solely on the CLI command, making the configuration more self-documenting and easier to manage.

**T9 — Easy:**
*   **Variable (Input)**: A value provided *to* the configuration, typically by the user or CI/CD pipeline (e.g., `var.instance_type = "t2.micro"`). Variables are used to make configurations flexible.
*   **Output**: A value exposed *by* the configuration, typically from a module, allowing other parts of the infrastructure to consume it (e.g., `module.vpc.public_ip`). Outputs are used to communicate results.

**T10 — Easy:** A provider is a plugin that enables OpenTofu to interact with a specific API (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without running `tofu init` first, the command will fail because `tofu init` is responsible for downloading the necessary provider plugins and configuring the backend state storage.

**T11 — Easy:** The `.terraform.lock.hcl` file pins the exact versions of all providers and providers dependencies used in the project. It should be committed to version control because it guarantees **reproducibility**. Without it, different team members or CI environments might pull slightly different provider versions, leading to unexpected plan/apply failures or state inconsistencies.

**T12 — Easy:** `tofu destroy` removes all resources managed by the current OpenTofu state file. To target a single resource, you use the `-target` flag, specifying the resource type and its local name (e.g., `tofu destroy -target=aws_instance.web_server`).

**T13 — Easy:** A data source is a mechanism used to fetch information about existing infrastructure or external data that is *not* managed by the current OpenTofu configuration.
**Example**: Instead of creating a new VPC, you might use a data source to look up the ID of the existing VPC that your application must connect to.
**Use Case**: Use a data source when you need to reference existing infrastructure (e.g., finding the latest Amazon Machine Image (AMI) ID) without taking ownership of that resource.

**T14 — Medium:**
*   **Variables**: External inputs provided by the user or environment. They are the primary way to inject configuration flexibility.
*   **Locals**: Variables defined *within* the configuration file itself. They are used for intermediate calculations, complex string manipulation, or defining reusable values based on other variables/resources.
*   **When to use locals**: Use locals when the value is derived from other configuration elements (e.g., `local.instance_name = "${var.project_name}-${var.environment}"`) rather than being a raw input parameter.

**T15 — Medium:** The lifecycle block controls how a resource behaves during updates and destruction.
*   **`create_before_destroy`**: When updating a resource, OpenTofu first creates the new replacement resource, waits for it to be ready, and *then* destroys the old resource. **Use Case**: Zero-downtime deployments (e.g., replacing a load balancer target group).
*   **`prevent_destroy`**: Prevents the resource from being destroyed by OpenTofu, even if the configuration attempts to remove it. **Use Case**: Critical resources (e.g., a production database cluster) that should never be accidentally deleted.
*   **`ignore_changes`**: Tells OpenTofu to ignore changes to specific attributes during an update. **Use Case**: When an attribute is managed externally (e.g., a tag added by a monitoring agent) and you don't want OpenTofu to try and revert it.

**T16 — Medium:** A `moved` block is used to rename or relocate a resource within the configuration (e.g., moving a resource from one module to another, or renaming it) without causing OpenTofu to destroy and recreate the underlying infrastructure. It updates the state file to reflect the new location/name while preserving the resource ID.

**T17 — Hard:**
*   **Dependency Graph**: OpenTofu builds a directed acyclic graph (DAG) of all resources. It determines the order of operations by identifying which resources depend on the outputs of others.
*   **Implicit Dependency**: Occurs when one resource uses the output of another resource (e.g., `aws_instance.a.id` is used as an input for `aws_security_group.b`). OpenTofu automatically detects this and ensures the dependency is met.
*   **Explicit Dependency**: Defined using `depends_on = [resource_reference]`. This forces a specific execution order regardless of whether an output is used.
*   **Parallelism**: OpenTofu executes independent resources concurrently. Using `depends_on` forces a sequential execution path, which can reduce parallelism and increase plan time. It should be used sparingly, only when the dependency is structural or non-obvious.

**T18 — Hard:**
1.  **Modularization**: Break the monolithic configuration into smaller, focused modules (e.g., Networking, Compute, Database). This reduces the scope of each plan run. *Tradeoff: Increased complexity in module management.*
2.  **State Splitting**: Separate concerns into different state files (e.g., `vpc.tfstate`, `compute.tfstate`). This limits the number of resources OpenTofu must check during a plan. *Tradeoff: Increased complexity in cross-module referencing.*
3.  **Data Source Utilization**: Where possible, use data sources to look up existing IDs or configurations instead of creating and managing them. *Tradeoff: Requires the external resource to already exist.*
4.  **Optimize Resource Dependencies**: Review the graph and eliminate unnecessary `depends_on` blocks. Ensure that all dependencies are implicit (using outputs) to allow OpenTofu's scheduler to maximize parallelism. *Tradeoff: Requires deep understanding of the infrastructure flow.*

**T19 — Hard:** OpenTofu's state locking mechanism ensures that only one operation (plan or apply) can modify the state file at any given time. This is typically achieved by using a backend that supports locking (like DynamoDB or S3 with specific configurations).
**If a lock is not released**: Subsequent `tofu plan` or `tofu apply` commands will fail immediately with a "State is locked" error, preventing concurrent modifications.
**Manually breaking a lock**: You can use `tofu state unlock` (or the equivalent CLI command for your backend).
**Risks**: Manually breaking a lock is extremely dangerous. If another process is actively modifying the state file, forcing the lock release can lead to **state corruption**, resulting in an inconsistent and unmanageable infrastructure state.

**T20 — Hard:**
1.  **Configure Backend**: Update the configuration to specify the S3 bucket and DynamoDB table for locking.
    ```hcl
    terraform {
      backend "s3" {
        bucket = "my-tf-state"
        key    = "path/to/state"
        region = "us-east-1"
        dynamodb_table = "tf-locks" # State locking table
      }
    }
    ```
2.  **Initialize**: Run `tofu init`. This downloads the provider plugins and configures the backend connection.
3.  **Migrate State**: Use `tofu state mv` or `tofu import` to move the resources from the local state file into the newly configured remote state file. If the local state is clean, you can use `tofu state push` after configuring the backend.
4.  **Verification**: Run `tofu plan`. If the plan shows "No changes. Your infrastructure matches the configuration," the migration was successful, and the state is correctly stored and locked in S3/DynamoDB.

## Ansible (20 questions)

**A1 — Easy:**
*   **Playbook**: The top-level YAML file that defines the entire automation workflow. It contains one or more plays, which define the hosts, tasks, and handlers to be run.
*   **Role**: A standardized, reusable structure that groups related tasks, handlers, variables, and files. Roles promote modularity and reusability (e.g., a `webserver` role).
*   **Task**: A single unit of work within a playbook or role (e.g., `apt install nginx`, `copy file`, `service restart`).

**A2 — Easy:** `ansible_facts` is a dictionary containing system information gathered about the target host during the connection phase (e.g., OS version, memory, CPU count). You access the OS family using: `ansible_facts['os_family']`.

**A3 — Medium:**
*   **`command` module**: Executes a command without invoking a shell. It is safer and preferred because it does not interpret shell features (like pipes or redirects). Use when you need to run a simple, non-shell-dependent command.
*   **`shell` module**: Executes a command through the system shell (e.g., `/bin/sh`). Use when you need shell features like pipes (`|`), redirects (`>`), or environment variable expansion.
*   **`raw` module**: Executes a raw command and returns the output. It is generally discouraged as it bypasses Ansible's idempotency checks and error handling. Use only when absolutely necessary.

**A4 — Medium:** Idempotency means that running a task multiple times will produce the same result without causing unintended side effects.
*   **Idempotent Example**: Using the `apt` module to install a package (`apt: name: nginx state: present`). If Nginx is already installed, the task reports "ok" and makes no changes.
*   **Not Idempotent Example**: Using the `shell` module to append text to a file (`shell: echo "log entry" >> /var/log/app.log`). Each run adds a new line.

**A5 — Medium:**
```yaml
- name: Install htop based on OS family
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
    state: present
  when: ansible_os_family == 'Debian' or ansible_os_family == 'RedHat'
  # Note: For true OS-specific package management, you would use separate tasks
  # or conditional logic within the package module itself.
```
*(Self-Correction/Refinement: While the above is technically correct, a more robust solution uses separate tasks for package management based on OS family.)*

**A6 — Hard:** Ansible uses a strict hierarchy to resolve variable values. The order of precedence (highest to lowest) is:
1.  **`extra_vars`**: Variables passed directly on the command line (`-e`).
2.  **`host_vars`**: Variables defined specifically for a single host in the inventory.
3.  **`group_vars`**: Variables defined for an entire group of hosts.
4.  **Inventory Variables**: Variables defined directly in the inventory file.
5.  **Role Defaults**: Variables defined in the `defaults/main.yml` file within a role.

**A7 — Hard:**
1.  **Serial Execution**: Use the `serial` keyword in the play to control how many hosts are processed in parallel.
    ```yaml
    - name: Deploy RKE2 agents
      hosts: rke2_nodes
      serial: 3 # Only 3 nodes run at a time
      tasks:
        # ... deployment tasks ...
    ```
2.  **Inventory Groups**: Define a group for the initial batch (e.g., `rke2_initial`) and the remaining nodes (`rke2_remaining`).
3.  **Wait/Dependency**: If the deployment requires the first 3 nodes to be fully operational before the rest start, you must use a combination of `serial` and potentially a custom check (like a `wait_for` task or a custom script) that checks the status of the first 3 nodes before the play proceeds to the next batch.

**A8 — Medium:** `ansible-vault` is a tool and feature that allows you to encrypt sensitive data (passwords, API keys, etc.) within Ansible files.
**Encrypting a single variable**: Instead of encrypting the entire `vars/main.yml`, you create a separate, dedicated encrypted file (e.g., `vars/secrets.yml`) containing only the sensitive variable, and then reference that file in your playbook using the `vars_files` directive.

**A9 — Easy:**
*   **Inventory File**: A list of hosts (servers) that Ansible will manage. It defines groups and host names.
*   **Static Inventory**: A manually defined file (e.g., `hosts.ini`) where you list hostnames and groups.
*   **Dynamic Inventory**: An inventory that is generated automatically at runtime by a script or API call (e.g., querying AWS EC2 or Azure to get a list of running instances).

**A10 — Easy:**
```bash
ansible webservers -m command -a "df -h"
```

**A11 — Easy:** A handler is a task that is only executed when explicitly "notified" by another task that made a change. Handlers are typically used for actions like restarting services or reloading configurations.
**Difference**: A regular task runs every time the playbook reaches it. A handler only runs if notified, ensuring that service restarts only happen when necessary, which is key to idempotency.
**Trigger**: A task notifies a handler using the `notify:` keyword (e.g., `notify: restart nginx`).

**A12 — Easy:** `ansible.cfg` is the configuration file that controls how Ansible runs. It allows you to override default behaviors globally.
**Common Settings**:
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Defines the user Ansible connects as on the remote host.
3.  `forks`: Sets the number of parallel connections Ansible should make.

**A13 — Easy:** The `register` keyword captures the output of a task and stores it in a variable.
**Usage**: You use the registered variable in a subsequent task by referencing it using Jinja2 syntax (e.g., `{{ registered_variable.stdout }}`).
*Example:*
```yaml
- name: Get disk usage
  command: df -h
  register: disk_usage

- name: Display usage
  debug:
    msg: "Disk usage is: {{ disk_usage.stdout }}"
```

**A14 — Medium:**
*   **`import_tasks`**: The tasks are evaluated at **parse time** (when the playbook is read). They are static inclusions.
*   **`include_tasks`**: The tasks are evaluated at **runtime** (when the playbook is executed). This allows for conditional logic.
*   **When to use**: Use `import_tasks` for static, foundational components (e.g., common setup tasks). Use `include_tasks` when you need to conditionally include a set of tasks based on runtime variables (e.g., only run database setup if `db_enabled: true`).

**A15 — Medium:** Ansible Galaxy is a community repository where users share reusable Ansible Roles and Collections.
**Usage**: You define the required roles and collections in a `requirements.yml` file. You then use the `ansible-galaxy` command to install them:
```yaml
# requirements.yml
roles:
  - src: community.general/nginx
```
Command: `ansible-galaxy install -r requirements.yml`

**A16 — Medium:** Connection plugins define the mechanism Ansible uses to connect to and execute commands on a remote host.
*   **`ssh`**: The standard, most common connection. Ansible connects via SSH, executes commands, and receives output. Used for Linux/Unix hosts.
*   **`local`**: The task is executed directly on the Ansible control node itself, not on a remote host. Used for local file manipulation or running local scripts.
*   **`network_cli`**: Specialized for network devices (routers, switches). It uses specific protocols (like Telnet/SSH) to interact with the device's CLI, often requiring specific device-specific modules.

**A17 — Hard:**
*   **`delegate_to`**: Allows a task to be executed on a host *other* than the one defined in the current play. You can delegate to a specific host, or to `localhost` (the control node).
*   **`run_once`**: Ensures that a task is executed only one time across the entire inventory, even if it is targeted at multiple hosts.
*   **Practical Example**: You need to gather a list of all active IP addresses from 50 remote servers, but you only want to process and log this list once on the central server.
    ```yaml
    - name: Gather IPs and log once
      ansible.builtin.shell: "ip a"
      register: ip_data
      delegate_to: localhost # Run the command on the control node
      run_once: true       # Ensure it only runs once
    ```

**A18 — Hard:**
1.  **Increase `forks`**: Increase the number of parallel connections Ansible makes. This is the most direct way to improve speed, but too high a number can overwhelm the target hosts or the control node.
2.  **Fact Caching**: Use `ansible_facts_cache` to cache gathered facts. This prevents Ansible from re-running expensive fact-gathering tasks on every single playbook run, significantly speeding up subsequent runs.
3.  **Pipelining**: Instead of running tasks sequentially, pipeline tasks together. This allows Ansible to stream data between tasks without waiting for the full output of the previous task, reducing latency.
4.  **Serial Execution (Strategic)**: While `serial` slows down a single play, strategically using it can prevent resource exhaustion on the target hosts, which can lead to timeouts and failures, ultimately improving overall stability and run time.

**A19 — Hard:** Jinja2 is the templating engine used by Ansible.
*   **`{{ variable }}`**: Used to output the value of a variable (e.g., `{{ server_name }}`).
*   **`{% control_structure %}`**: Used for control flow logic (e.g., `{% if condition %}`, `{% for item in list %}`).
*   **`{# comment #}`**: Used for comments within the template that are ignored by the engine.
**Template Snippet:**
```jinja2
upstream backend_servers {
    server {{ backend_servers[0].ip }}:8080;
    server {{ backend_servers[1].ip }}:8080;
    # Health check for {{ backend_servers[2].ip }}
    server {{ backend_servers[2].ip }}:8080;
}
```

**A20 — Hard:**
1.  **Serial Batching**: Set `serial: 1` (or a small number like 2) in the play to ensure only one server is updated at a time.
2.  **Pre-Task (LB Health Check)**: Before updating, ensure the load balancer (LB) is configured to check the health of the *old* server.
3.  **Deployment Task**: Run the update/deployment task on the target server.
4.  **Post-Task (Health Check)**: Use the `uri` module to perform a health check against the newly updated server.
5.  **Rollback Strategy**: Wrap the deployment and health check in a `block/rescue` structure. If the health check fails (the `rescue` block is triggered), the `rescue` block executes a rollback task (e.g., reverting the configuration or restarting the old version) and notifies the operator.
6.  **LB Registration**: After successful health check, update the LB configuration to route traffic to the new server, and then deregister the old server.
