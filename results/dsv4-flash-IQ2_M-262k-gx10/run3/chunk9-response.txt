**SC1-A — Broken Deployments After Cluster Upgrade**

The failure stems from the interaction between the newly enforced **Restricted Pod Security Standard** and the container image’s default user. Kubernetes Pod Security Standards (PSS) are admission controls that enforce predefined security contexts. The **Restricted** profile requires, among other things, that `securityContext.runAsNonRoot: true` **and** that `runAsUser` be set to a non-root UID (or that the image itself runs as non-root). The affected pods set `runAsNonRoot: true` but did **not** set `runAsUser`. Previously, with the **Baseline** profile, this was allowed because Baseline only requires `runAsNonRoot` to be true, not that a specific UID be provided. The container images were rebuilt with `cgr.dev/chainguard/static:latest`, which by default runs as **root** (UID 0) unless overridden. When the cluster enforced Restricted, the admission controller rejected the pod because the effective user (from the image) was root, even though `runAsNonRoot: true` was set. The pod was created but the container failed to start (CrashLoopBackOff) because the runtime detected a violation (or the image’s entrypoint attempted privileged operations). The fix is to explicitly set `runAsUser` to a non-root UID (e.g., 65532) in the pod’s security context, or rebuild the image to run as non-root by default.

**SC1-B — Bash One-liner to Identify Failing Pods**

```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.containers[0].securityContext}' | jq -s .
```

This outputs a JSON array of objects with namespace, pod name, and securityContext for all pods in CrashLoopBackOff across all namespaces.

**SC1-C — Remediation Strategy**

1. **Immediate fix**: Add `runAsUser: 65532` (or another non-root UID) to the `securityContext` of all affected deployments. Use a script to patch all deployments:
   ```bash
   kubectl get deploy -A -o json | jq -r '.items[] | select(.spec.template.spec.securityContext.runAsNonRoot == true and .spec.template.spec.securityContext.runAsUser == null) | .metadata.name' | xargs -I{} kubectl patch deploy {} -n <namespace> --type='json' -p='[{"op":"add","path":"/spec/template/spec/securityContext/runAsUser","value":65532}]'
   ```
2. **Image-level fix**: Rebuild the base image to include a non-root user and set `USER` in the Dockerfile. Use a specific non-root UID (e.g., 65532) and ensure the image runs as that user by default.
3. **Manifest changes**: Update all Kubernetes manifests to include `runAsUser` and `runAsGroup` explicitly. Use a policy-as-code tool (e.g., OPA Gatekeeper) to enforce that `runAsUser` is always set when `runAsNonRoot: true`.
4. **CI pipeline gate**: Add a validation step in CI that scans Kubernetes manifests for Restricted PSS compliance. Use `kubectl dry-run` or a tool like `kubeconform` with a custom schema that requires `runAsUser` when `runAsNonRoot` is true. Also, run Trivy or `dive` to check the image’s default user.
5. **Rollout without downtime**: Use a rolling update strategy with `maxUnavailable: 0` and `maxSurge: 25%`. First patch a small canary deployment, verify health, then gradually increase the rollout percentage using `kubectl rollout restart` with a deployment strategy that ensures availability.

**SC2-A — Stale Data After Cross-Region Replica Promotion**

The stale data issue arises because the promoted replica was **asynchronously replicated** from the primary. PostgreSQL streaming replication ships WAL records across regions asynchronously by default. When the replica was promoted, it may have been **behind** the primary by some amount of committed transactions. Any transactions that were committed on the old primary but not yet shipped to the replica are **lost**. After promotion, the new primary (eu-west-1) starts serving reads and writes, but some application queries may hit data that was replicated before the promotion, while other queries may see newer data written after promotion—this inconsistency is due to the replica having a lag at the moment of promotion. The data loss window is the replication lag at promotion time. To quantify it, check:
- The `pg_last_xact_replay_timestamp()` on the replica before promotion (or the `pg_stat_replication` `replay_lag`).
- The WAL segment files still present on the old primary that were not shipped.
- The `pg_current_wal_lsn()` on the old primary and the `pg_last_wal_replay_lsn()` on the replica.
- Any transactions in the old primary’s `pg_stat_activity` that were committed but not yet replicated.

**SC2-B — Terraform Operations for Promoting Replica**

1. **Import the promoted replica** into Terraform state:
   ```bash
   terraform import aws_db_instance.promoted_replica <replica_arn>
   ```
2. **Remove the old instance** from state (if it’s still referenced) using `terraform state rm aws_db_instance.old_primary`.
3. **Update dependent resources** (security groups, Route53, parameter groups) to reference the new instance ID. Use `terraform state mv` to rename resources if needed, or edit the configuration to point to the new instance and run `terraform apply` with `-target` to only update dependencies.
4. **Prevent destroy/recreate**: Ensure the new instance is imported with the same resource name as the old one (or use `terraform state mv` to rename). Use `terraform plan` to verify no `destroy` actions are planned. If the old instance is still in state, remove it first.

**SC2-C — Future-Proof Architecture**

- **RDS Proxy vs PgBouncer**: Use RDS Proxy for managed connection pooling, automatic failover, and IAM authentication. It reduces connection churn and handles failover better than PgBouncer, which requires manual reconfiguration.
- **Route53 health checks with DNS failover**: Use Route53 health checks on the primary and replica endpoints, with failover routing policy to automatically update DNS records when the primary fails.
- **Application-level retry logic**: Implement retries with exponential backoff and jitter, and use a circuit breaker to avoid overwhelming the database during failover.
- **RPO < 1 second**: Use **Aurora Global Database** with `Aurora Global Database` which supports cross-region replication with typical RPO of less than 1 second (using asynchronous replication but with minimal lag). Alternatively, use PostgreSQL logical replication with synchronous replication across regions (not possible with standard RDS due to latency). Aurora Global Database is recommended because it provides managed cross-region failover, fast failover, and lower RPO compared to standard RDS with asynchronous replication.

**SC3-A — Immediate Incident Response**

1. **Isolate affected pods** without killing them: Use `kubectl label` to mark them, then use network policies to block egress, or use `kubectl scale` to zero replicas but keep the pod objects for forensics.
2. **Capture process tree**: `kubectl exec <pod> -c <container> -- nsenter --target 1 --mount --net --pid -- sh -c 'ps aux'` (if privileged) or `kubectl exec <pod> -- ps -ef`.
3. **Capture network connections**: `kubectl exec <pod> -- ss -tulpn` or `kubectl exec <pod> -- netstat -tulpn`.
4. **Filesystem diff**: Use `kubectl exec <pod> -- tar czf /tmp/fs.tar.gz /` and copy it out, or use `kubectl cp` to retrieve the archive. Also, check `/proc/<pid>/fd` for open files.
5. **Preserve evidence**: Use `kubectl get pod <pod> -o yaml` to capture the spec, and `kubectl logs <pod>` for logs. Do not delete the pod until evidence is collected.

**SC4-A — Top 5 Technical Blockers**

1. **Sticky sessions (local memory)**: Kubernetes does not guarantee session affinity across replicas. Solution: Use an external session store (Redis) or implement distributed sessions.
2. **NFS mount for uploads**: Kubernetes supports NFS via CSI, but the monolith writes to a single mount. Solution: Use a shared NFS CSI driver with ReadWriteMany access, or migrate to object storage (S3-compatible) with a gateway.
3. **Oracle 19c database**: Oracle is not natively containerized; need to use a sidecar or external service. Solution: Keep Oracle on-prem and connect via network, or use a Kubernetes operator for Oracle.
4. **IBM MQ integration**: MQ requires native JMS and network access. Solution: Use a sidecar container with MQ client, or use a message gateway (e.g., IBM MQ bridge).
5. **Stateful filesystem**: The monolith assumes a single filesystem for logs, temp files, etc. Solution: Use ephemeral storage for non-critical data, and persistent volumes for critical data.

**SC5-A — Systematic Debugging Approach**

1. **Check Istio metrics**: Look at Envoy sidecar metrics for `istio_requests_total`, `istio_request_duration_ms`, and `envoy_cluster_upstream_rq_time` for the checkout-service to inventory-service. Compare `envoy_cluster_upstream_rq_time` (time spent waiting for upstream) vs `envoy_cluster_connect_time` (connection time).
2. **Distributed tracing**: Use Jaeger to trace a checkout request. Look at spans for checkout-service and inventory-service. If the span for inventory-service shows high duration, the latency is in the application; if the span for checkout-service shows a gap before the inventory span, it’s in the network or sidecar.
3. **Kubernetes metrics**: Check inventory-service pod CPU, memory, and network. Also check database connection pool metrics (e.g., `pg_stat_activity`).
4. **Application logs**: Look for slow queries, lock waits, or connection timeouts in inventory-service logs.
5. **Envoy metrics**: `envoy_cluster_upstream_rq_retry` and `envoy_cluster_upstream_rq_timeout` can indicate proxy-level issues. `envoy_cluster_upstream_rq_time` includes queueing; `envoy_cluster_upstream_rq_retry` indicates retries.

**SC5-B — SQL Diagnostic Query and Go Circuit Breaker**

```sql
SELECT
  blocked.pid AS blocked_pid,
  blocked.usename AS blocked_user,
  blocked.query AS blocked_query,
  blocking.pid AS blocking_pid,
  blocking.usename AS blocking_user,
  blocking.query AS blocking_query

JOIN pg_stat_activity AS blocking ON blocking.pid = ANY(
```

**SC5-C — Architectural Solution**

**SC6-C — VPN Bottleneck Solutions**

- **Direct Connect**: Provides dedicated bandwidth (e.g., 10 Gbps), lower latency, and private connectivity. Cost is higher (monthly port fee + data transfer). Encryption can be done with IPsec over Direct Connect or using MACsec. Failover requires a second Direct Connect or VPN.
- **Second VPN tunnel with ECMP**: Adds bandwidth (up to 2 Gbps) but still limited by VPN throughput. Cost is lower. Encryption is IPsec. Failover is automatic if both tunnels are active.
- **Hybrid mesh (Tailscale/Netbird)**: Uses WireGuard-based mesh, provides encrypted tunnels, and can route over existing internet. Cost is per-user or per-node. Bandwidth is limited by internet, but can be scaled with multiple paths. Failover is automatic. Fits zero-trust by providing identity-based access.

Routing changes: For Direct Connect, need BGP over the connection; for ECMP, need multiple VPN tunnels with equal-cost routing; for mesh, need to deploy agents on each workload and adjust routing tables.

**SC7-A — Drift Sources and Dangers**

1. **Manual tofu apply**: Bypasses CI/CD, no review, no state locking, can cause unintended changes, and state file corruption.
2. **Diverged Helm values**: Staging and production values not tracked in Git means changes are not reproducible, and rollback is impossible.
3. **Direct kubectl edit**: Bypasses GitOps, can cause configuration drift, and may be overwritten by next deployment.

**Dangers of no state locking**: Two engineers running `tofu apply` simultaneously can corrupt the state file, leading to lost resources or duplicate resources. Data loss can occur if one apply deletes resources that another depends on.

**SC10-A — Multi-Cluster DR Architecture**

- **Active-passive with Velero**: Backup/restore can meet RPO of 15 minutes if backups are taken frequently (e.g., every 10 minutes) and RTO of 1 hour if restore is automated. However, 200TB of MinIO data would require continuous replication, which Velero does not provide. Use MinIO site replication for object storage.
- **Active-active with service mesh**: Istio multi-cluster or Cilium Cluster Mesh allows active-active serving, but stateful components need cross-cluster replication. PostgreSQL with Patroni can be active-passive with synchronous replication across sites (12ms latency is acceptable for synchronous commit). Redis Sentinel can be active-passive. RabbitMQ can use federation or queue mirroring. MinIO site replication provides active-active object storage.

Given RPO 15 min and RTO 1 hour, active-active with service mesh is better for RTO (no restore needed) but requires careful stateful replication. For PostgreSQL, use synchronous replication to achieve zero data loss, but 12ms latency may impact performance; asynchronous with replication slots can meet RPO 15 min.

**SC10-C — Automated Failover Orchestration**

1. **Failure detection**: Use health checks from both sites (e.g., `pg_isready`, Redis ping, MinIO health). A site is considered down if all health checks fail for 3 consecutive intervals (e.g., 30 seconds).
2. **DNS failover**: Update GSLB DNS records to point to Dallas endpoints.
3. **Patroni promotion**: Patroni automatically promotes the standby when the primary is unreachable (if using etcd as DCS). Ensure `synchronous_standby_names` is updated.
4. **Redis Sentinel**: Sentinel automatically promotes a replica to master.
5. **RabbitMQ**: Use queue mirroring across sites; on failover, promote a mirrored queue.
6. **MinIO site replication**: MinIO site replication is asynchronous; on failover, the Dallas site may have some lag. Use `mc admin replicate status` to check and catch up.
7. **OpenTofu state**: Update Terraform state to reflect the new primary by importing the Dallas resources and removing Chicago resources.

**Split-brain**: Use a majority-based DCS (etcd) to prevent both sites from promoting. If both sites are up, only one can be primary.

**Failback**: Once Chicago recovers, replicate data back, then switch primary back using a controlled failover (e.g., `patronictl failover`).
