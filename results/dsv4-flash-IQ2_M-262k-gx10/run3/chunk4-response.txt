## Go (20 questions)

### G1 — Easy: Slice vs Array
An **array** has a fixed length that is part of its type (`[5]int`), is a value type, and copying it copies the entire array. A **slice** is a dynamic view into an underlying array, with a length and capacity, and is a reference type (header: pointer, len, cap). When you append to a slice at capacity, Go allocates a new larger array (typically doubling), copies the existing elements, and returns a new slice header pointing to the new array. The original array may be garbage-collected if no longer referenced.

### G2 — Easy: `var x int` vs `x := 0`
`var x int` declares a variable with the zero value (0) and explicit type. `x := 0` uses short declaration, inferring the type from the literal (int). You **cannot** use `:=` at package level (only inside functions), and you cannot use it if the variable is already declared in the same scope (unless at least one variable on the left is new). `:=` also cannot be used with a type-only declaration (e.g., `x := nil` without a type).

### G3 — Medium: Goroutines and GMP
A **goroutine** is a lightweight, cooperatively scheduled unit of execution managed by the Go runtime. It starts with a small stack (~2KB) that grows dynamically, and switching between goroutines is much cheaper than OS thread context switches. An **OS thread** is heavyweight, managed by the kernel, with a large fixed stack (~1MB+). The **GMP model**: G (goroutine), M (OS thread), P (processor/context). The scheduler multiplexes many goroutines onto a smaller number of OS threads. Each P has a local run queue of goroutines; when a P's queue is empty, it can steal from other Ps or the global queue. This enables efficient parallelism and load balancing.

### G4 — Medium: Channels
A **channel** is a typed conduit for communication between goroutines. An **unbuffered channel** has no capacity: every send blocks until a receiver is ready, and every receive blocks until a sender is ready (synchronous). A **buffered channel** has capacity N: sends succeed until the buffer is full; sends block when full. Receives succeed until the buffer is empty; receives block when empty. Sending to a **full buffered channel** blocks the sender until another goroutine receives from the channel, freeing space. Channels are goroutine-safe and provide synchronization.

### G5 — Medium: context package
The `context` package provides cancellation, deadlines, and request-scoped values. It's used to propagate cancellation signals across goroutines and to bound operations (e.g., HTTP requests, DB queries). Minimal example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

req, err := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
if err != nil { /* handle */ }
resp, err := http.DefaultClient.Do(req)
if err != nil { /* handle timeout/cancel */ }
```
When the timeout expires, `ctx.Done()` is closed, and the HTTP client cancels the request.

### G6 — Medium: Interface satisfaction
Go uses **implicit satisfaction**: a type implements an interface simply by having all the methods the interface requires. There's no explicit `implements` keyword. This differs from Java/C# where you must declare the interface. The empty interface `interface{}` (or `any` in Go 1.18+) accepts any type. It's powerful because it enables generic-like behavior (e.g., `fmt.Println` accepts anything), but dangerous because it erases type information, requiring type assertions or reflection, which can lead to runtime panics and poor performance if overused.

### G7 — Hard: Memory model and goroutine visibility
The code is **unsafe** because it has a data race: `ready` and `data` are accessed by two goroutines without synchronization. The Go memory model guarantees that a write in one goroutine is visible to another only if there's a synchronization operation (channel, mutex, atomic, etc.). Without it, the compiler/CPU may reorder operations, and the loop `for !ready {}` may never see the update, or `data` may not be visible even after `ready` is true. **Correct alternatives**: use a channel to signal completion, use `sync.Mutex` to protect both variables, or use `sync/atomic` with `atomic.LoadBool`/`atomic.StoreBool` and a happens-before edge.

### G8 — Hard: Mutex vs RWMutex vs sync.Map
`sync.Mutex` provides exclusive access: only one goroutine can hold the lock at a time. `sync.RWMutex` allows multiple readers OR a single writer: `RLock()` for reads, `Lock()` for writes. Use `RWMutex` when reads are frequent and writes are rare. `sync.Map` is optimized for read-heavy workloads with distinct keys (e.g., cache), using atomic operations and sharded maps to reduce contention. Trade-offs: `Mutex` is simple and predictable; `RWMutex` improves read concurrency but has writer starvation; `sync.Map` has higher overhead for writes and is only beneficial when reads dominate and keys are mostly distinct.

### G9 — Hard: Go modules
`go.mod` defines the module path, Go version, and dependencies (module path + version). `go.sum` contains cryptographic checksums of module content for verification, ensuring integrity. `go mod tidy` adds missing dependencies, removes unused ones, and updates `go.sum`. **Minimum Version Selection (MVS)**: when multiple modules depend on different versions of the same module, Go picks the **minimum version that satisfies all constraints** (the max of the minimums). This ensures reproducibility and avoids the "diamond dependency" problem.

### G10 — Medium: defer
`defer` schedules a function call to run when the enclosing function returns. Multiple defers execute in **LIFO order** (last deferred runs first). A common gotcha: `defer` inside a loop accumulates calls until the function returns, not per iteration. For example:
```go
for i := 0; i < 3; i++ {
    defer fmt.Println(i) // prints 2,1,0 at function exit
}
```
To defer per iteration, wrap in a helper function or use a closure.

### G11 — Easy: Pointers
A **pointer** holds the memory address of a value. The zero value is `nil`. You create a pointer to a struct literal with `&Struct{...}` or `new(Struct)`. Example:
```go
p := &Person{Name: "Alice"} // p is *Person
```
Pointers allow sharing values and mutating them without copying.

### G12 — Easy: init() function
`init()` runs automatically when a package is initialized, before `main()`. It's used for setup that can't be done in variable declarations. A package can have **multiple `init()` functions** (in the same file or across files). They execute in this order: (1) all variable initializations, (2) `init()` functions in file order (by filename), then declaration order within a file. Across packages, dependencies are initialized first.

### G13 — Easy: make vs new
`make` is used only for **slices, maps, and channels**; it returns an initialized value (not a pointer) ready for use. `new` allocates zeroed memory for any type and returns a **pointer** to it. Example: `make([]int, 5)` creates a slice; `new(int)` returns `*int` pointing to 0. You rarely use `new`; `&T{}` is more common.

### G14 — Easy: Error handling
Go's `error` interface has one method: `Error() string`. Idiomatic pattern: check `if err != nil` immediately after a call, handle or return. `errors.Is(err, target)` checks if `err` matches `target` (including wrapped errors via `%w`). `errors.As(err, &target)` checks if `err` can be cast to a specific error type. `==` only works for direct comparison (no wrapping) and is fragile; `Is`/`As` are preferred for wrapped errors.

### G15 — Easy: Composite types and zero values
- **map**: zero value is `nil` (read-only, cannot write)
- **slice**: zero value is `nil` (len=0, cap=0)
- **channel**: zero value is `nil` (blocks forever)
- **struct**: zero value is a struct with all fields at their zero values

### G16 — Medium: Race conditions
A **race condition** occurs when two goroutines access the same memory concurrently, at least one writes, without synchronization. The `-race` flag instruments the binary to detect races at runtime (using happens-before analysis). Example:
```go
var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }() // race
}
```
Fix with `sync.Mutex`:
```go
var mu sync.Mutex
for i := 0; i < 1000; i++ {
    go func() { mu.Lock(); counter++; mu.Unlock() }()
}
```
Or use a channel to accumulate results.

### G17 — Medium: select statement
`select` waits on multiple channel operations. It differs from `switch` because it's for channels only and blocks until one case is ready. If **multiple cases are ready**, it picks one at random (uniformly). To implement a timeout:
```go
select {
case msg := <-ch:
    fmt.Println(msg)
case <-time.After(2 * time.Second):
    fmt.Println("timeout")
}
```
You can also use `default` for non-blocking sends/receives.

### G18 — Hard: Escape analysis
**Escape analysis** is a compiler optimization that determines whether a variable can be allocated on the stack or must go to the heap. If a variable's address escapes (e.g., returned, stored in a global, passed to a function that keeps it), it's heap-allocated. Stack allocation is fast (no GC), heap allocation incurs GC overhead. Inspect with `go build -gcflags=-m` (or `-m=2` for more detail). It matters for performance: minimizing heap allocations reduces GC pressure and improves cache locality.

### G19 — Hard: Reflection
`reflect.Type` describes the type (e.g., name, kind, methods), `reflect.Value` holds the runtime value and allows inspection/modification. Reflection is **slow** (dynamic dispatch, no inlining) and can be error-prone. It's justified for generic serialization (e.g., JSON), ORMs, or testing frameworks. For performance-critical code, prefer **code generation** (e.g., `go generate`) or generics (Go 1.18+) to avoid runtime overhead.

### G20 — Hard: go:embed
`go:embed` embeds files into the binary at compile time. Syntax:
```go
//go:embed static
var staticFS embed.FS
```
It works for single files, directories (recursively), and `embed.FS` implements `io/fs.FS`. Limitations: no `..` paths, no absolute paths, files must be in the module (or subdirectories), and you can't embed files with names starting with `_` or `.` unless using `all:` prefix. It's useful for serving static assets or templates without external files.

## Rust (20 questions)

### R1 — Easy: Ownership
Ownership rules: (1) Each value has a single **owner**; (2) When the owner goes out of scope, the value is **dropped**; (3) You can **borrow** or **move** values, but not both simultaneously. This ensures memory safety without a garbage collector.

### R2 — Easy: String vs &str
`String` is an owned, heap-allocated, mutable UTF-8 string. `&str` is a borrowed reference to a string slice (a `&[u8]` with UTF-8 guarantee). In function signatures, use `&str` for reading (avoids allocation), `String` when you need to own or mutate the data. Example: `fn greet(name: &str)` vs `fn create_name() -> String`.

### R3 — Medium: Borrowing and borrow checker
Borrowing allows using a value without taking ownership. Rules: (1) You can have **many shared references** (`&T`) OR **one mutable reference** (`&mut T`), but not both; (2) References must be valid (lifetimes). The borrow checker enforces these at compile time, preventing data races and dangling pointers.

### R4 — Medium: Result and Option
`Result<T, E>` is for operations that can fail: `Ok(T)` or `Err(E)`. `Option<T>` is for optional values: `Some(T)` or `None`. The `?` operator unwraps `Ok`/`Some` or returns `Err`/`None` early from the function. Example:
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}
```
Usage: `let contents = read_file("file.txt")?;` propagates the error.

### R5 — Medium: Box, Rc, Arc
- `Box<T>`: single ownership, heap allocation (for recursive types, large data).
- `Rc<T>`: multiple ownership, single-threaded (non-atomic refcount).
- `Arc<T>`: multiple ownership, thread-safe (atomic refcount).
Use `Box` for a single owner, `Rc` for shared immutable data in one thread, `Arc` for shared data across threads.

### R6 — Medium: Traits
Traits define shared behavior (like Go interfaces) but are more powerful: they can have associated types, generic parameters, and default methods. **Trait objects** (`dyn Trait`) use dynamic dispatch (vtable) and are similar to Go interfaces. **Generics with trait bounds** (`T: Trait`) use static dispatch (monomorphization) — faster, but code bloat. Prefer generics for performance, `dyn Trait` for heterogeneous collections.

### R7 — Hard: Lifetimes
The code fails because the return type `&str` has no lifetime parameter — the compiler can't determine how long the returned reference is valid. Fix by adding a lifetime parameter:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This says the returned reference lives as long as both inputs.

### R8 — Hard: Send and Sync
`Send` means a type can be moved to another thread safely. `Sync` means a type can be shared across threads (references). `Rc<T>` is **not Send** because its refcount is non-atomic — concurrent increments would race. `Arc<T>` uses atomic refcounting, making it `Send + Sync` (if `T: Send + Sync`). `Mutex<T>` makes `T` Sync by providing interior mutability.

### R9 — Hard: async/await
Rust's async/await is **cooperative**: a `Future` is a state machine that yields control when it awaits. An **executor** (e.g., Tokio) polls futures and schedules them. This differs from Go's goroutines, which are **preemptive** (the runtime can interrupt them). Rust's model gives more control (no runtime overhead) but requires manual executor management. Futures are lazy — they only run when polled.

### R10 — Medium: unsafe
In `unsafe`, you can: (1) dereference raw pointers (`*const T`), (2) call unsafe functions (e.g., FFI), (3) access mutable static variables. Unsafe is justified for FFI, performance-critical code (e.g., SIMD), or implementing safe abstractions (e.g., `Vec`). It must be encapsulated in safe APIs with invariants documented.

### R11 — Easy: Pattern matching
`match` is exhaustive — the compiler requires all possible patterns to be covered. `if let` is a shorthand for matching a single pattern (e.g., `if let Some(x) = opt`). The compiler enforces exhaustiveness, preventing unhandled cases (e.g., `None`).

### R12 — Easy: Vec vs array
`Vec<T>` is a dynamic, heap-allocated growable array. `[T; N]` is a fixed-size array on the stack (or inline in structs). When `Vec` exceeds capacity, it reallocates (typically doubles capacity), copies elements, and drops the old allocation. This amortizes push cost to O(1).

### R13 — Easy: Enums
Rust enums are **algebraic data types** — they can hold data (e.g., `enum Message { Quit, Move { x: i32, y: i32 } }`). C/Java enums are just named constants. `Option<T>` is `Some(T)` or `None`, replacing null. Rust has **no null** — absence is explicit via `Option`, preventing null-pointer errors.

### R14 — Easy: impl blocks
`impl` defines methods and associated functions. Methods take `&self` (immutable borrow), `&mut self` (mutable borrow), or `self` (ownership, consuming). Associated functions (e.g., `String::new()`) don't take `self` and are called with `::`. Example:
```rust
impl Rectangle {
    fn area(&self) -> u32 { self.width * self.height }
    fn square(size: u32) -> Rectangle { Rectangle { width: size, height: size } }
}
```

### R15 — Easy: derive macro
`#[derive(...)]` auto-implements traits. Common ones: `Debug` (formatting), `Clone` (deep copy), `PartialEq` (equality), `Serialize` (serde). You **cannot** derive a trait if the trait requires custom logic (e.g., `Display` for custom formatting) or if the type contains fields that don't implement the trait (e.g., `Clone` for `Rc<T>` is fine, but `Copy` for `String` is not).

### R16 — Medium: Cow
`Cow<'a, T>` (clone-on-write) is an enum: `Borrowed(&'a T)` or `Owned(T)`. It's useful when you may need to modify data but want to avoid cloning if not necessary. Example:
```rust
fn process(input: &str) -> Cow<'_, str> {
    if input.contains("bad") {
        Cow::Owned(input.replace("bad", "good"))
    } else {
        Cow::Borrowed(input)
    }
}
```
This avoids allocation when no change is needed.

### R17 — Medium: Module system
`mod` declares a module (inline or from a file), `use` brings items into scope, `pub` makes items public. In Rust 2015, modules were file-based with `mod foo;` for `foo.rs` or `foo/mod.rs`. In Rust 2018, the path system was simplified: `use crate::foo::bar;` and `use self::...` for relative paths. The 2018 edition removed `extern crate` and made `crate` refer to the current crate.

### R18 — Hard: Pin and Unpin
`Pin<T>` prevents moving the value it wraps. It's needed for **self-referential structs** (e.g., a struct with a pointer to its own field) because moving would invalidate the pointer. Async/await uses `Pin` because futures may be self-referential. `Unpin` is a marker trait: types that are safe to move after pinning (most types). `Pin<Box<T>>` is common for heap-allocated pinned values.

### R19 — Hard: Macros
**Declarative macros** (`macro_rules!`) match patterns and generate code (e.g., `vec!`). **Procedural macros** (derive, attribute, function-like) run code at compile time to generate tokens. **Hygiene** means macros don't accidentally capture variables from the caller's scope — identifiers are scoped to the macro definition, preventing name collisions.

### R20 — Hard: Zero-cost abstractions
Rust's abstractions compile to efficient machine code: **iterators** are inlined and fused into loops (no allocation), **generics** use monomorphization (each instantiation is specialized), and **trait static dispatch** (generics) avoids vtable overhead. This achieves performance comparable to hand-written C while providing high-level ergonomics. Example: `v.iter().map(|x| x * 2).filter(|x| x > 10).sum()` compiles to a tight loop with no heap allocation.
