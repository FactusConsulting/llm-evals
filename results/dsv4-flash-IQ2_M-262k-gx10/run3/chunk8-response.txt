# Cloud Infrastructure Architecture

**CL1 — IaaS vs PaaS vs SaaS**
- **IaaS**: Provider offers raw compute, storage, networking. You manage OS, middleware, apps. Example: AWS EC2.
- **PaaS**: Provider manages runtime, OS, middleware; you deploy apps. Example: Azure App Service.
- **SaaS**: Fully managed application; you only configure usage. Example: Microsoft 365.

**CL2 — Shared Responsibility Model**
- **IaaS VMs**: Provider responsible for physical host, hypervisor, network, storage infrastructure. You're responsible for guest OS, patches, middleware, applications, data, and VM-level security.
- **Managed Kubernetes**: Provider handles control plane, nodes, OS patching, cluster upgrades. You're responsible for workloads, namespaces, RBAC, pod security, container images, and application data.
- **SaaS (M365)**: Provider handles everything except your data, user identities, access policies, and compliance obligations. You configure tenant settings and manage user accounts.

**CL3 — VPC, Subnet, Security Group, NACL**
- **VPC**: Virtual private network boundary in cloud—your isolated logical network.
- **Subnet**: IP range segment within a VPC, typically tied to an availability zone.
- **Security Group**: Instance-level stateful firewall—allows/denies traffic based on rules; stateful means return traffic is automatically allowed.
- **NACL**: Subnet-level stateless firewall—each rule evaluated independently; return traffic must be explicitly allowed.
- **Layering**: NACL filters traffic at subnet boundary; security groups filter at instance level. NACL applies to all instances in subnet; SG applies per instance. Stateful (SG) tracks connection state; stateless (NACL) does not.

**CL4 — Multi-Account Strategy**
- **Landing Zone**: Pre-configured baseline environment with identity, security, and networking foundations.
- **Organizational Units (OUs)**: Hierarchical grouping of accounts (e.g., Dev, Prod, Security) for policy inheritance.
- **Guardrails**: Preventive/detective controls via SCPs (AWS) or Azure Policy to enforce compliance.
- **Shared Networking**: Transit Gateway (AWS) or Hub-and-Spoke (Azure) centralizes connectivity between VPCs and on-prem.
- **Centralized Logging**: Aggregated CloudTrail/Flow Logs/Activity Logs into a central account for SIEM.
- **Single-account problems**: No blast radius isolation, no clear ownership boundaries, hard to enforce different policies per environment, poor cost allocation, and compliance risk.

**CL5 — Infrastructure as Code (IaC)**
- **Terraform/OpenTofu**: Declarative, cloud-agnostic, state-based. Best for multi-cloud and mature ecosystems.
- **Pulumi**: Declarative with imperative programming languages (Python, Go, TS). Good for complex logic and code reuse.
- **CloudFormation/Bicep**: Native to AWS/Azure, deeply integrated, but vendor-locked. Bicep is simpler than ARM templates.
- **Crossplane**: Control-plane-based IaC—Kubernetes-native, reconciles cloud resources continuously. Best for platform teams wanting GitOps-style cloud provisioning.
- **Choice**: Terraform for general multi-cloud; Pulumi for code-heavy teams; CloudFormation/Bicep for single-cloud deep integration; Crossplane for platform engineering on K8s.

**CL6 — Autoscaling Patterns**
- **HPA**: Scales pod replicas based on CPU/memory/custom metrics. Good for stateless workloads.
- **VPA**: Adjusts CPU/memory requests of existing pods. Good for stateful or legacy apps that can't scale horizontally.
- **Cluster Autoscaler**: Adds/removes worker nodes when pods can't be scheduled. Handles capacity at node level.
- **KEDA**: Event-driven autoscaler—scales based on queue depth, Kafka lag, custom metrics. Use KEDA over HPA when scaling on non-Kubernetes-native signals (e.g., messages in a queue, database queries, external API metrics).

**CL7 — Disaster Recovery Design**
- **RPO/RTO**: Define acceptable data loss (RPO) and downtime (RTO). Typically RPO ≤ 15 min, RTO ≤ 1 hour for critical apps.
- **Active-Active**: Both regions serve traffic; data replicated synchronously. Complex but zero downtime.
- **Active-Passive**: One region active, other standby; async replication. Simpler, lower cost, but failover takes minutes.
- **Database Replication**: Sync replication for active-active (low RPO); async for active-passive (higher RPO but lower latency).
- **DNS Failover**: Route53 health checks or Azure Traffic Manager route traffic to healthy region.
- **State Management**: Use managed services (S3, Cosmos DB, DynamoDB) with cross-region replication; avoid local state.
- **Cost**: Active-active doubles infrastructure cost; warm standby reduces cost but requires failover time; pilot light minimizes cost but longest RTO.
- **DR Patterns**: Pilot light (minimal resources running, scale up on failover), warm standby (full stack running but no traffic), multi-site active-active (both serving traffic).

**CL8 — GitOps Model**
- **GitOps**: Git is the single source of truth for desired state; controllers reconcile actual state to match.
- **ArgoCD vs FluxCD**: ArgoCD has richer UI, multi-cluster management, and app-level sync; FluxCD is more lightweight, uses Git as source, and has better multi-tenancy support. Both support Kustomize/Helm.
- **Secrets**: Sealed Secrets (encrypt secrets in Git), External Secrets Operator (sync from Vault/AWS Secrets Manager), or Vault agent injecting secrets at runtime.
- **Drift**: If someone manually changes cluster state, the controller detects drift and reverts to Git state (auto-sync) or alerts (manual sync). GitOps ensures convergence back to desired state.

**CL9 — Stateful Legacy App on Kubernetes**
- **StatefulSet**: Provides stable network identity, ordered startup/shutdown, and stable storage.
- **PV/PVC with Local Storage Class**: Use local SSDs for low latency; PVC binds to specific node.
- **Headless Service**: Gives each pod a stable DNS name (e.g., pod-0.service) for peer discovery.
- **Init Containers**: Handle ordered startup dependencies (e.g., wait for DB, initialize config).
- **ConfigMaps as Volume Mounts**: Mount config files at exact paths (e.g., /etc/app/config.ini) without rebuilding images.
- **Pod Disruption Budgets**: Ensure minimum availability during voluntary disruptions (e.g., node maintenance).

**CL10 — Service Accounts vs Workload Identity vs IRSA**
- **Service Account (K8s)**: Kubernetes identity for pods to access K8s API.
- **Workload Identity (GCP/Azure)**: Cloud identity mapped to K8s service account for cloud API access.
- **IRSA (AWS)**: IAM roles for service accounts—maps K8s SA to IAM role via OIDC federation.
- **Bad practice**: Mounting cloud credentials (e.g., AWS keys) in pods—long-lived, hard to rotate, risk of leakage.
- **Workload identity federation**: Uses OIDC to exchange K8s SA tokens for cloud credentials—short-lived, scoped, no static keys.

**CL11 — Object vs Block vs File Storage**
- **Object Storage (S3/Blob)**: Key-value store for unstructured data; highly durable (11 nines), scalable, cheap. Use for backups, media, analytics.
- **Block Storage (EBS/Managed Disk)**: Raw disk attached to VMs; low latency, high IOPS. Use for databases, OS disks.
- **File Storage (EFS/Azure Files)**: Shared file system over NFS/SMB; multi-attach. Use for shared app data, home directories.
- **Durability**: Object 99.999999999%; Block 99.999999%; File 99.999999%. Availability: Object 99.99%; Block 99.99%; File 99.99%.

**CL12 — Zero-Trust Network Architecture for K8s**
- **Network Policies**: Micro-segmentation at pod level—allow only required east-west traffic.
- **Service Mesh (mTLS)**: Encrypts pod-to-pod traffic; identity-based auth (e.g., Istio, Linkerd).
- **Pod Identity**: Workload identity federation (IRSA/Workload Identity) for cloud API access.
- **Admission Controllers (OPA/Kyverno)**: Enforce policies at deploy time (e.g., no privileged containers, required labels).
- **Image Signing/Verification**: Sign images with Cosign; verify signatures before admission.
- **Runtime Security (Falco)**: Detect anomalous behavior (e.g., unexpected exec, file access).
- **Secrets Management**: Use Vault/External Secrets; never store secrets in Git or env vars.
- **Difference from perimeter model**: No implicit trust inside network; every request authenticated/authorized; continuous monitoring.

**CL13 — CDN**
- **CDN**: Distributed edge servers that cache content closer to users, reducing latency and origin load.
- **How it works**: Edge nodes cache static content (images, CSS, video); requests route to nearest PoP; origin serves only cache misses.
- **Services**: AWS CloudFront, Azure CDN (or Azure Front Door).
- **When to use**: Static content, global distribution, high-traffic media. When not: dynamic personalized data, low-traffic internal apps.

**CL14 — Regions and Availability Zones**
- **Region**: Geographic area with multiple AZs (e.g., us-east-1).
- **Availability Zone**: Isolated data center within a region; independent power/cooling/network.
- **Multi-AZ deployment**: Provides high availability—if one AZ fails, traffic shifts to another.
- **Zonal vs Regional resources**: Zonal (e.g., EBS volume, EC2 instance) tied to one AZ; Regional (e.g., S3, ELB) spans AZs and survives AZ failure.

**CL15 — Managed Database Services**
- **Managed DB (RDS, Cloud SQL, Azure SQL)**: Provider handles backups, patching, replication, failover, monitoring, and scaling.
- **On VM**: You handle OS patches, DB software, backups, replication, high availability, and monitoring.
- **Benefits**: Reduced operational burden, built-in HA, automated backups, managed security patches.

**CL16 — Cloud Identity Services**
- **IAM Users**: Individual accounts for people/services.
- **Groups**: Collections of users with shared permissions.
- **Roles**: Identity with permissions that can be assumed by users/services (no long-term credentials).
- **Policies**: JSON documents defining permissions (allow/deny).
- **Principle of Least Privilege**: Grant only required permissions. Apply by: using roles over users, scoping policies to resources, regularly auditing and removing unused permissions.

**CL17 — Serverless Computing**
- **Serverless**: Run code without managing servers; pay per invocation; auto-scaling.
- **AWS Lambda**: Event-driven, supports many languages, integrates with AWS services.
- **Azure Functions**: Similar, integrates with Azure services, supports durable functions.
- **Google Cloud Functions**: Lightweight, integrates with GCP services.
- **Cold starts**: Delay when a function instance is created after idle—affects latency-sensitive apps.
- **Poor fit**: Long-running processes, stateful workloads, low-latency critical paths, heavy compute (ML training), or applications with predictable high utilization.

**CL18 — Kubernetes Ingress Options**
- **Ingress Resource**: Defines routing rules; controller (e.g., NGINX) implements them. TLS termination at controller.
- **Gateway API**: Newer, more expressive; separates routing from implementation; supports HTTP, TLS, TCP/UDP. TLS termination at gateway.
- **Cloud LB Annotations**: Use cloud-specific annotations (e.g., AWS ALB Ingress Controller) for direct cloud LB integration. TLS termination at LB.
- **Service Mesh Ingress Gateways**: Mesh ingress (e.g., Istio Gateway) handles external traffic with mTLS, routing, and policy. TLS termination at mesh gateway.
- **Gateway API over Ingress**: Use Gateway API for multi-protocol support, better namespace isolation, and vendor-neutral abstraction.

**CL19 — Cost Optimization Strategy**
- **Reserved Instances/Savings Plans**: Commit to 1-3 years for 40-60% savings on baseline workloads.
- **Spot/Preemptible**: Use for fault-tolerant, stateless workloads (CI, batch) for 60-90% savings.
- **Right-sizing**: Analyze utilization; downsize over-provisioned resources.
- **Storage Tiering**: Use Intelligent-Tiering (S3) or Archive for cold data; delete unused snapshots.
- **Idle Resource Detection**: Use tools (AWS Compute Optimizer, Azure Advisor) to find idle resources.
- **FinOps Practices**: Tag resources, allocate costs per team, set budgets, review monthly.
- **Showback/Chargeback**: Allocate costs to business units via tags; showback reports for visibility.
- **Tools**: Cloud Cost Management (CloudHealth, FinOps platforms), native cost explorer, budget alerts.

**CL20 — Multi-Cloud Strategy**
- **Abstraction Layers**: Use Terraform for IaC, Kubernetes for runtime, and cloud-agnostic services (e.g., S3-compatible storage).
- **Kubernetes as Common Runtime**: Run workloads on EKS and AKS with similar manifests.
- **Networking**: Connect clouds via VPN or dedicated interconnect (e.g., AWS Direct Connect + Azure ExpressRoute).
- **Identity Federation**: Use OIDC/SAML to federate identities across clouds.
- **Trade-offs**: Multi-cloud adds complexity, latency, and cost; benefits are avoiding lock-in, resilience, and best-of-breed services.
- **When justified**: Regulatory requirements, vendor risk mitigation, or leveraging unique services. When not: small teams, low complexity, or when cost of operations exceeds benefits.

# OT Infrastructure Architecture

**OT1 — Purdue Model (ISA-95)**
- **Level 0**: Physical process (sensors, actuators).
- **Level 1**: Basic control (PLCs, RTUs, DCS controllers).
- **Level 2**: Supervision (HMIs, SCADA servers, historian).
- **Level 3**: Operations management (MES, batch management, plant historian).
- **Level 4**: Business planning (ERP, enterprise historian).
- **Level 5**: Enterprise network (internet, cloud, corporate IT).

**OT2 — IT vs OT Networks**
- **IT**: Focus on data integrity, confidentiality, and availability; frequent patching; dynamic environments.
- **OT**: Focus on safety, availability, and reliability; uptime is critical; patching can cause process disruptions; systems are often legacy and unsupported.
- **Why IT patching fails in OT**: OT systems have long lifecycles, no downtime windows, and patches may break real-time control or safety functions.

**OT3 — DMZ/IDMZ**
- **IDMZ**: Industrial DMZ sits between IT (Level 4) and OT (Level 3) networks.
- **Allowed traffic**: Only necessary data flows—e.g., historian data to enterprise, MES to ERP, remote access via jump hosts. Traffic is typically one-way or strictly controlled.
- **Direction**: From IT to OT is minimized; OT to IT is limited to data exports.
- **Why direct IT-to-Level 1 is dangerous**: A compromise in IT can directly reach control systems, bypassing security zones; Level 1 devices are often insecure and lack monitoring.

**OT4 — OT Protocols**
- **Modbus TCP**: Level 1/2—PLC-to-HMI/SCADA communication; simple master-slave protocol.
- **OPC UA**: Level 2/3—standardized data exchange between controllers and supervisory systems; supports encryption and authentication.
- **EtherNet/IP (CIP)**: Level 1/2—industrial Ethernet protocol for real-time control and I/O.
- **PROFINET**: Level 1/2—industrial Ethernet for distributed I/O and motion control.
- **MQTT**: Level 3/4—publish-subscribe for IoT/cloud data; often used for edge-to-cloud telemetry.

**OT5 — Data Diode vs Firewall**
- **Data Diode**: Hardware device that allows one-way data transfer; physically prevents reverse traffic.
- **Firewall**: Filters traffic in both directions based on rules.
- **When to use data diode**: For unidirectional data flows (e.g., OT to IT historian) where absolute security is required—no possibility of reverse compromise.
- **Limitation**: Cannot support bidirectional protocols (e.g., remote access, control commands); requires protocol-specific gateways.

**OT6 — SCADA Data Flow to Cloud**
- **Data Flow**: PLCs → OPC UA server (Level 2) → historian (Level 3) → edge gateway → MQTT broker → cloud ingestion.
- **Security Boundaries**: 
  - Between Level 2 and Level 3: Firewall with protocol filtering.
  - Between Level 3 and edge gateway: IDMZ with data diode or one-way gateway.
  - Edge gateway: Authenticate, encrypt (TLS), and validate data before sending to cloud.
  - Cloud: Use managed ingestion (e.g., IoT Hub, MQTT broker) with identity and access controls.

**OT7 — IEC 62443 Zones and Conduits**
- **Zone**: Group of assets with similar security requirements (e.g., control zone, safety zone).
- **Conduit**: A communication path between zones with defined security controls (e.g., firewall rules, protocol filtering).
- **Design for manufacturing plant**:
  - **Zone 1**: Corporate network (IT)—low security requirements.
  - **Zone 2**: Engineering workstations—medium security; access to PLCs.
  - **Zone 3**: SCADA servers—high security; central control.
  - **Zone 4**: PLCs—critical; minimal external access.
  - **Zone 5**: SIS—highest security; isolated or air-gapped.
  - **Conduits**: Between zones, use firewalls with allow-listed protocols; between SCADA and PLCs, allow only Modbus/OPC UA; between engineering and PLCs, allow only during maintenance windows.

**OT8 — Network Segmentation for Manufacturing Plant**
- **VLAN Design**: Separate VLANs per production line, per device type (PLC, HMI, SCADA), and per function (control, safety, engineering).
- **Firewall Placement**: Deploy firewalls between VLANs and at the plant perimeter; use industrial firewalls (e.g., Tofino, MGuard) for protocol-aware filtering.
- **Switch Architecture**: Use managed switches with VLAN support; segment at access layer; avoid flat Layer 2.
- **Remote Access**: Use jump hosts in IDMZ with MFA and session recording; never direct VPN to control network.
- **Transition**: Phased approach—start with monitoring and asset inventory, then segment one line at a time during planned outages; use temporary ACLs to minimize disruption.

**OT9 — SIS vs BPCS**
- **BPCS**: Basic Process Control System—handles normal operations (e.g., temperature control, flow regulation).
- **SIS**: Safety Instrumented System—detects dangerous conditions and initiates protective actions (e.g., emergency shutdown).
- **IEC 61511**: Standard for functional safety in process industries—defines SIS design, integrity levels (SIL), and lifecycle.
- **Why SIS must be isolated**: A cyber attack on SIS could prevent safety shutdowns, leading to catastrophic accidents; SIS is designed for safety, not security, and often lacks monitoring.
- **Ransomware on SIS**: Could disable safety functions, cause loss of containment, or force manual intervention; worst case—physical harm, environmental damage, or loss of life.

**OT10 — PLC vs DCS vs SCADA**
- **PLC**: Programmable Logic Controller—discrete control, fast I/O, used for individual machines or small processes.
- **DCS**: Distributed Control System—integrated control for large continuous processes (e.g., chemical plants); redundant controllers, centralized engineering.
- **SCADA**: Supervisory Control and Data Acquisition—monitoring and control of geographically distributed assets (e.g., pipelines, power grids); uses RTUs/PLCs at remote sites.
- **Coexistence**: Yes—many plants use PLCs for local control, DCS for process-wide control, and SCADA for remote monitoring.

**OT11 — Remote Access to OT**
- **Architecture**: Vendor connects via VPN to IDMZ, then via jump host to OT network; MFA required; session recording for audit.
- **Time-limited access**: Use temporary credentials or Just-In-Time access; auto-expire after maintenance window.
- **Why RDP directly to HMI is unacceptable**: Exposes HMI to internet/IT network, bypasses security controls, no audit trail, and increases attack surface.

**OT12 — OT Security Incident Response**
- **Detection**: Deploy IDS/IPS (e.g., Suricata, Zeek) at network boundaries; monitor for anomalous traffic (e.g., unexpected Modbus writes).
- **Asset Inventory**: Maintain up-to-date inventory of all OT assets (PLCs, HMIs, servers) with IP/MAC, firmware, and roles.
- **Response Steps**: 
  1. Isolate compromised systems (disconnect from network, not from process).
  2. Preserve evidence (logs, memory).
  3. Analyze and contain (block malicious traffic, revoke VPN access).
  4. Coordinate with control room to ensure safe operations.
  5. Remediate (rebuild, patch, monitor).
- **Operator Role**: Operators are the eyes on the process—they can detect anomalies (e.g., unexpected valve movements) and can manually operate equipment if needed; they must be trained to report suspicious behavior.

**OT13 — HMI**
- **HMI**: Human-Machine Interface—graphical screens for operators to monitor and control processes (e.g., tank levels, temperatures).
- **Role**: Provides real-time visualization, alarms, and control commands.
- **Difference from engineering workstation**: HMI is for operators (runtime); engineering workstation is for engineers to program/configure controllers (development).

**OT14 — Historian**
- **Historian**: Time-series database for process data (e.g., temperatures, pressures, flow rates).
- **Importance**: Provides historical context for troubleshooting, optimization, and compliance reporting.
- **Plant Historian (Level 3)**: Collects data from control systems; high-resolution, short retention.
- **Enterprise Historian (Level 4)**: Aggregates data from multiple plants; lower resolution, longer retention for business analytics.

**OT15 — Ladder Logic**
- **Ladder Logic**: Graphical programming language for PLCs—resembles electrical relay diagrams.
- **Executed by**: PLCs (and some RTUs/DCS controllers).
- **Why dominant**: Standardized (IEC 61131-3), easy for electricians/engineers to understand, deterministic execution, and proven reliability over decades.

**OT16 — RTU vs PLC**
- **RTU**: Remote Terminal Unit—telemetry and control for remote sites; designed for low power, wide-area communication (e.g., radio, satellite).
- **PLC**: Local control with high-speed I/O; typically installed near the process.
- **When to use RTU**: For geographically distributed assets (e.g., pipelines, substations) where remote communication is primary; PLC for local, fast control.

**OT17 — Analog vs Digital Signals**
- **Analog**: Continuous signal (4-20mA, 0-10V) representing a variable (e.g., temperature, pressure).
- **Digital**: Discrete signal (0/1, on/off) for status or commands.
- **Why 4-20mA preferred**: 4mA represents zero (live zero)—can detect wire break (0mA); 0-20mA cannot distinguish zero from a broken wire; 4-20mA is also less affected by voltage drops.

**OT18 — OT Asset Inventory**
- **Importance**: You can't protect what you don't know; inventory is the foundation for risk assessment, monitoring, and incident response.
- **Discovery Tools**: Passive monitoring (e.g., Nozomi, Dragos) analyzes traffic without sending packets; active scanning (e.g., Nmap) sends probes.
- **Why active scanning is dangerous**: OT devices are often fragile; active scans can cause crashes, disrupt real-time control, or trigger safety shutdowns. Passive monitoring is safer.

**OT19 — MITRE ATT&CK for ICS**
- **Framework**: Maps adversary tactics and techniques specific to industrial control systems.
- **Tactics (5 examples)**:
  1. **Initial Access**—e.g., exploitation of internet-facing devices (T0883).
  2. **Execution**—e.g., malicious controller logic (T0831).
  3. **Persistence**—e.g., modify controller logic (T0839).
  4. **Lateral Movement**—e.g., remote service exploitation (T0866).
  5. **Impact**—e.g., loss of safety (T0882), damage to equipment (T0832).
- **Difference from enterprise ATT&CK**: ICS framework includes physical impact, controller-specific techniques, and safety consequences.
- **Use**: Map your OT environment to the framework to identify gaps (e.g., no monitoring for controller logic changes, no detection for unauthorized remote access).

**OT20 — Converged IT/OT SOC**
- **Log Collection**: Use passive collectors (e.g., span ports, industrial firewalls) to gather logs without disrupting operations; forward to SIEM via one-way gateway.
- **SIEM Integration**: Correlate OT logs (PLC events, alarms) with IT logs (VPN, AD) for cross-domain detection.
- **OT-specific Detection Rules**: Examples—unauthorized firmware change, unexpected Modbus write, new device on control network, abnormal traffic to historian.
- **Alert Triage**: IT analysts handle IT alerts; OT engineers handle OT alerts; joint escalation for cross-domain incidents.
- **Staffing**: Blend IT security analysts with OT engineers; train both on each other's domains.
- **False Positives**: OT environments have limited change windows; false positives can cause alert fatigue. Use context-aware rules (e.g., only alert on firmware changes during maintenance windows).
- **Firmware change alert**: Verify against change management records; if unauthorized, isolate the PLC, preserve logs, and investigate the source (e.g., engineering workstation compromise).
