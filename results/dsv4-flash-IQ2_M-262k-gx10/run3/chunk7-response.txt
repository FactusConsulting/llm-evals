## Application Architecture

**AA1** — A monolith is a single deployable application where all business logic, data access, and UI are packaged together. Microservices decompose the application into independently deployable services, each with its own data store and API. Three concrete problems microservices introduce that monoliths don't:
1. **Network latency and partial failure** — services communicate over the network, introducing latency, timeouts, and cascading failures.
2. **Distributed data consistency** — no ACID transactions across services; requires sagas, event sourcing, or eventual consistency.
3. **Operational complexity** — deployment, monitoring, tracing, and configuration across many services is significantly harder.

**AA2** — **Synchronous** communication: the caller blocks and waits for a response. Example: REST/HTTP or gRPC. **Asynchronous** communication: the caller sends a message and continues without waiting. Example: RabbitMQ, Kafka, or SQS. Synchronous is simpler and gives immediate feedback; asynchronous decouples services and handles bursts better.

**AA3** — An **API Gateway** is an L7 proxy focused on API management: routing, authentication, rate limiting, caching, and API versioning. A **reverse proxy** is a general-purpose L7 proxy that forwards traffic to backend servers, providing load balancing, SSL termination, and header manipulation. An API Gateway can replace a reverse proxy for HTTP/API traffic, but not entirely — reverse proxies handle non-HTTP protocols (WebSocket, TCP), static content, and lower-level traffic. In practice, API Gateways often sit behind or replace reverse proxies for API-only workloads.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a series of local transactions, each with a compensating action to undo it if a later step fails. **Choreography-based sagas** use events: each service listens for events and triggers the next step; no central coordinator. **Orchestration-based sagas** use a central orchestrator that commands each service and handles compensation. Choreography is appropriate for simple workflows with few services and loose coupling; orchestration is appropriate for complex workflows with many services, where centralized control and easier debugging are needed.

**AA5** — **CQRS** separates the read model (queries) from the write model (commands), often using different data stores or schemas. **Event Sourcing** stores state changes as an immutable event log, and the current state is derived by replaying events. They are paired because Event Sourcing provides a natural way to update read models (projections) and gives an audit trail. This combination solves problems that traditional CRUD struggles with: complex read queries that don't match the write model, high write contention, and the need for full auditability and temporal queries.

**AA6** — The **Circuit Breaker** pattern prevents a service from repeatedly calling a failing dependency. Three states: **Closed** (requests pass through), **Open** (fail fast, no requests pass), **Half-Open** (allow a few trial requests to test recovery). It differs from a simple retry with backoff because it stops all traffic to a failing service, preventing resource exhaustion and cascading failures. Use both together: retry with backoff for transient failures (e.g., 3 retries with exponential backoff), and a circuit breaker for prolonged failures (e.g., open after 5 consecutive failures). The circuit breaker wraps the retry logic.

**AA7** — Multi-tenant isolation models:
1. **Shared DB, shared schema** (row-level tenant ID): lowest cost, simplest operations, but poor security isolation (risk of SQL injection or bug leaking data), high noisy-neighbor risk (one tenant can consume all resources), and hard to scale per-tenant.
2. **Shared DB, separate schema per tenant**: moderate cost, better security (schema-level isolation), moderate operational complexity (schema management), noisy-neighbor risk still exists at the DB level.
3. **Separate DB per tenant**: highest cost, best security and isolation, no noisy-neighbor risk, but highest operational complexity (many DBs to manage, backup, monitor). Choose based on compliance needs, tenant size, and cost tolerance.

**AA8** — **Eventual consistency** means reads may return stale data but will converge over time. **Strong consistency** means reads always return the latest committed data. For an inventory system that must never oversell, you need **strong consistency** on the inventory count. Architecture: use a single-node database with atomic operations (e.g., PostgreSQL with `UPDATE inventory SET count = count - 1 WHERE id = ? AND count > 0`) or a distributed system with linearizable transactions (e.g., Spanner, or Redis with Lua scripts). At scale, use **optimistic locking** (version numbers), **atomic decrement with a check**, or **partitioning by product ID** to a single writer. For high throughput, use a queue to serialize inventory operations per product.

**AA9** — A **sidecar proxy** is a lightweight proxy deployed alongside each application instance, intercepting all traffic to and from the service. In **Istio**, Envoy proxies form the **data plane**, handling traffic, retries, and mTLS. The **control plane** (Pilot, Citadel, Mixer) configures the proxies, distributes certificates, and enforces policies. **mTLS between sidecars** provides service-to-service authentication and encryption at the network layer, independent of application-level TLS. This solves the problem of internal service-to-service traffic being unencrypted or unauthenticated, which application-level TLS often ignores (e.g., HTTP traffic between services that doesn't use TLS).

**AA10** — The **Strangler Fig pattern** incrementally replaces a legacy system with new services. For a .NET Framework monolith migrating to .NET 8 microservices: (1) Identify bounded contexts (e.g., auth, billing, inventory). (2) Extract one context at a time into a .NET 8 microservice, using an **anti-corruption layer** to translate between old and new models. (3) Use an **API Gateway/facade** to route traffic to the new service for that context. (4) Migrate data incrementally, using a shared database temporarily or a data migration service. (5) Once all contexts are extracted, decommission the monolith. This minimizes risk and allows continuous delivery.

**AA11** — The **12-Factor App** methodology defines best practices for cloud-native applications. Six key factors: (1) **Codebase** — one codebase, multiple deploys. (2) **Dependencies** — explicitly declare and isolate dependencies. (3) **Config** — store config in environment variables, not code. (4) **Backing services** — treat services as attached resources, swap easily. (5) **Build/release/run** — separate build from release from run. (6) **Processes** — stateless processes, no shared state. These matter because they enable portability, scalability, and maintainability in cloud environments where instances are ephemeral and auto-scaled.

**AA12** — **Event-driven (Kafka)** vs **Request-driven (REST/gRPC)**:
- **Coupling**: Event-driven is loosely coupled (services don't know each other); request-driven is tightly coupled.
- **Scalability**: Event-driven scales well for async workloads and multiple consumers; request-driven scales for synchronous request/response.
- **Debugging**: Request-driven is easier to trace (request-response); event-driven is harder (need distributed tracing).
- **Ordering**: Kafka guarantees per-partition ordering; REST/gRPC guarantees per-request ordering.
- **Failure handling**: Event-driven allows replay and retry; request-driven uses timeouts and retries.
Choose event-driven for decoupled, async, fan-out workflows; choose request-driven for simple CRUD, low-latency, and easy debugging.

**AA13** — A **load balancer** distributes traffic across multiple servers. **Layer 4** load balancing operates at the transport layer (TCP/UDP), routing based on IP and port, with no content awareness. **Layer 7** load balancing operates at the application layer (HTTP), routing based on URL, headers, cookies, or content. Layer 7 is required for path-based routing (e.g., `/api` to one backend, `/web` to another), cookie-based sticky sessions, and SSL termination.

**AA14** — A **message queue** (RabbitMQ) delivers messages to a single consumer, removes them after consumption, and supports complex routing (topics, headers). A **log-based broker** (Kafka) stores an append-only log, allows multiple consumers to read independently, supports replay, and is designed for event streaming. Pick RabbitMQ for task distribution and point-to-point messaging; pick Kafka for event sourcing, stream processing, and multiple consumer groups.

**AA15** — A **container** shares the host OS kernel and isolates processes via namespaces and cgroups; it's lightweight and starts in milliseconds. A **virtual machine** includes a full guest OS with virtualized hardware; it's heavier and provides stronger isolation. Containers are popular for microservices because they are portable, resource-efficient, fast to start, and easy to scale horizontally.

**AA16** — **Stateless services** don't store any state between requests; any instance can serve any request, so horizontal scaling is trivial (just add instances). **Stateful services** maintain state (e.g., session data, database state), requiring sticky sessions or shared storage, making scaling harder. Examples: stateless — a REST API that reads from a database; stateful — a database server or a WebSocket chat server.

**AA17** — An **ORM** maps database tables to objects in code. Examples: Hibernate (Java), Entity Framework (C#), SQLAlchemy (Python). Trade-offs: ORMs reduce boilerplate and SQL injection risk, but can be slower, hide query complexity, and cause N+1 problems. Raw SQL gives more control, better performance for complex queries, and full database-specific features, but requires more code and is harder to maintain.

**AA18** — The **Bulkhead pattern** isolates resources (thread pools, connections, memory) so that a failure in one service doesn't exhaust resources for others. In microservices, it relates to resource isolation: each service or dependency gets its own thread pool. Example: in a Java application, use separate `ExecutorService` for each downstream service (e.g., one for payment, one for inventory). If payment is slow, it only exhausts its own pool, not the inventory pool. Alternatively, deploy critical services in separate deployment groups (e.g., separate Kubernetes namespaces) to isolate failures.

**AA19** — **OT** (Operational Transformation) transforms operations to converge on a shared state; requires a central server for ordering and transformation; provides strong consistency but is complex to implement. **CRDTs** (Conflict-free Replicated Data Types) are mergeable data types that converge without a central server; simpler for offline support, but some operations (e.g., text editing) are harder to implement. For a system that must support offline editing, **CRDTs** are better because they don't require a central server, merge naturally, and handle offline edits gracefully. OT requires a central server for coordination, making offline support harder.

**AA20** — Distributed tracing challenges: **context propagation** uses W3C Trace Context or B3 headers to carry trace IDs across service calls. **Sampling** strategies: head-based (sample at the entry point) vs tail-based (sample after the trace is complete, using a collector). **Trace storage/querying**: Jaeger or Tempo store traces and provide query APIs. **Async messaging**: trace context must be propagated in message headers (e.g., Kafka headers) so the consumer can continue the trace. For Kafka, include the trace context in the message headers; the consumer extracts it and starts a new span, linking to the producer span. This ensures trace continuity across async boundaries.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 hypervisor** runs directly on hardware (bare-metal). Examples: VMware ESXi, KVM, Xen. **Type 2 hypervisor** runs on a host OS. Examples: VirtualBox, VMware Workstation. Type 1 is more efficient and stable for production; Type 2 is for development/testing.

**OP2** — **SAN** (Storage Area Network) provides block-level storage, accessed via Fibre Channel or iSCSI. Used for databases, high-performance workloads. **NAS** (Network Attached Storage) provides file-level storage, accessed via NFS or SMB. Used for file sharing, home directories, and general-purpose storage. Choose SAN for low-latency, high-throughput block access; choose NAS for simplicity and file sharing.

**OP3** — **3-tier network** (core/distribution/access) is hierarchical: access switches connect to distribution, distribution to core. East-west traffic (server-to-server) must traverse the core, creating bottlenecks and latency. **Leaf-spine** is a flat topology where every leaf switch connects to every spine switch, providing predictable latency and no bottlenecks. Leaf-spine solves the east-west traffic problem, scales better, and is preferred in modern data centers for high-bandwidth, low-latency workloads.

**OP4** — **Proxmox HA cluster** with shared storage: use 3+ nodes for quorum (majority). Shared storage options: **Ceph** (distributed, self-managing), **iSCSI** (SAN), **NFS** (NAS). Configure **fencing** (STONITH) to power off failed nodes. On node failure: the remaining nodes maintain quorum, and VMs are migrated to other nodes. For 2-node clusters, add a **QDevice** (third-party arbiter) for quorum. Ceph provides automatic failover and is recommended for HA.

**OP5** — **VLAN trunking** carries multiple VLANs over a single link using **802.1Q tagging**, which adds a VLAN ID to the Ethernet frame. On Linux with a single NIC on 3 VLANs: create VLAN subinterfaces (e.g., `ip link add link eth0 name eth0.10 type vlan id 10`), assign IPs to each subinterface, and configure the switch port as a trunk.

**OP6** — RAID levels: **RAID 1** (mirroring, 2 drives, 1-drive fault tolerance), **RAID 5** (striping with parity, 3+ drives, 1-drive fault tolerance), **RAID 6** (striping with double parity, 4+ drives, 2-drive fault tolerance), **RAID 10** (striped mirrors, 4+ drives, 1-drive fault tolerance per mirror), **RAID Z2** (ZFS, similar to RAID 6 but with checksums and variable block size). For a database server with 6 drives: choose **RAID 10** for best performance and fault tolerance (4 drives usable, 2-drive fault tolerance per mirror), or **RAID 6** for more capacity (4 drives usable, 2-drive fault tolerance) but slower writes. RAID 10 is recommended for databases due to write performance.

**OP7** — **DNS architecture** for 500-person enterprise: internal AD-integrated DNS servers for internal zones (e.g., `corp.example.com`), with recursive resolution for external names. DMZ DNS servers for public zones (e.g., `example.com`), with **split-horizon** (internal and external views). Configure **conditional forwarding** for internal zones (e.g., `corp.example.com` to AD DNS). **DNSSEC** on the external zone for security. When a laptop moves between office and VPN: the VPN client assigns an internal DNS server, so internal names resolve; when off VPN, the laptop uses the external DNS server, which doesn't resolve internal names (unless split-horizon is configured for VPN clients).

**OP8** — **PKI chain**: Root CA (offline, air-gapped) issues certificates to subordinate/issuing CAs, which issue end-entity certificates. **CRL** (Certificate Revocation List) is a periodically downloaded list; **OCSP** (Online Certificate Status Protocol) is a real-time check. **Certificate templates** define properties (e.g., server auth, client auth). **Auto-enrollment** via GPO for domain-joined machines. Consequences: a compromised **subordinate CA** can be revoked and replaced, limiting damage to that CA's issued certs; a compromised **root CA** invalidates the entire PKI, requiring rebuilding the trust chain and reissuing all certificates.

**OP9** — WAN options for hub-and-spoke: **MPLS** — reliable, low latency, but expensive and managed. **IPsec VPN** — cheap, but less reliable, higher latency, and more management. **SD-WAN** — cost-effective, uses multiple links (MPLS, broadband), centralized management, good for VoIP. **WireGuard mesh** — cheap, simple, but lacks enterprise features (centralized management, QoS). For 50 users/site with latency-sensitive VoIP, **SD-WAN** is recommended: it provides cost savings, reliability via multiple links, and centralized management.

**OP10** — **iDRAC/iLO/IPMI** are out-of-band management interfaces for remote server management (power control, console access, hardware monitoring). They are critical because they allow troubleshooting even when the OS is down. If exposed to the internet, they become a security risk: attackers can gain full remote control, install malware, or cause a denial of service. Always restrict access to management networks or VPN.

**OP11** — **LVM**: traditional logical volumes, snapshots are copy-on-write but can be slow and space-inefficient. **LVM-Thin**: thin provisioning, efficient snapshots, better for virtualization. **ZFS**: filesystem with volume management, efficient snapshots, checksums, compression. Use LVM for simple setups, LVM-Thin for virtualization environments, ZFS for data integrity and snapshot-heavy workloads.

**OP12** — **Ceph stretch cluster** for 2-site DR: configure **CRUSH rules** to place data across both sites (e.g., 2 replicas per site). Place **monitors** across sites (e.g., 2 in site A, 2 in site B, 1 tiebreaker in a third site). Network latency must be <100ms for replication. **Split-brain** occurs if both sites lose connection and each thinks it's primary; a **tiebreaker** (third site or monitor) is needed to maintain quorum. 2-site Ceph without a tiebreaker is bad because a network partition can cause split-brain, leading to data corruption.

**OP13** — **DHCP** (Dynamic Host Configuration Protocol) uses the **DORA** process: Discover (client broadcasts), Offer (server offers an IP), Request (client requests the offered IP), Acknowledge (server confirms). If the DHCP server is unavailable and a Windows client's lease expires, the client uses **APIPA** (169.254.x.x) and loses network connectivity (no DNS, no gateway).

**OP14** — A **managed switch** provides VLAN support, QoS, SNMP monitoring, port security, spanning tree, and remote management. An **unmanaged switch** is plug-and-play with no configuration. Enterprise environments need managed switches for VLAN segmentation, monitoring, security, and traffic prioritization.

**OP15** — **NTP** (Network Time Protocol) synchronizes clocks across servers. Accurate time is critical for log correlation, Kerberos authentication, database replication, and distributed consensus. Clock drift causes: Kerberos tickets fail (time skew), database replication conflicts, and distributed systems (e.g., Paxos/Raft) fail due to timestamp issues.

**OP16** — **Physical server**: bare metal, full hardware access, no virtualization overhead. **Virtual machine**: virtualized hardware, strong isolation, easy to manage. **Container**: OS-level virtualization, lightweight, shares host kernel. Run workloads on bare metal when you need maximum performance, specialized hardware (GPU, FPGA), or low-latency databases.

**OP17** — A **UPS** provides immediate power for short durations (batteries), bridging the gap until a **generator** starts (which provides long-term power via fuel). Both are needed because UPS covers the transition (seconds to minutes) and generator covers extended outages (hours to days). An **ATS** (Automatic Transfer Switch) automatically switches between utility power and generator power when utility fails.

**OP18** — **Active-passive clustering**: one node is active, the other is standby; failover promotes the standby. **Active-active clustering**: both nodes are active, sharing the load; failover redistributes traffic. For PostgreSQL HA with Pacemaker/Corosync: use **active-passive** (one primary, one standby). Configure **STONITH** (fencing) to power off the failed node, a **virtual IP** that moves to the standby on failover, and **failover behavior** where the standby promotes to primary and the virtual IP is reassigned.

**OP19** — **Backup/DR strategy** for 50 servers: follow the **3-2-1 rule** (3 copies, 2 different media, 1 offsite). Define **RPO/RTO** (e.g., RPO=1 hour, RTO=4 hours). Use **full backups** weekly, **incremental** daily, **differential** as needed. Use **deduplication** to reduce storage. Use **disk** for fast recovery, **tape** for archival, **cloud** for offsite. Implement **immutable backups** (WORM) to protect against ransomware. **Test restores** regularly. **Backup** is data recovery; **disaster recovery** is full system recovery (servers, network, applications).

**OP20** — **802.1X** port-based access control: the **supplicant** (client) authenticates to the **authenticator** (switch), which relays to the **authentication server** (RADIUS). **EAP methods**: EAP-TLS (certificate-based) vs PEAP (password with TLS tunnel). RADIUS validates credentials and returns a **dynamic VLAN assignment** (e.g., user VLAN vs guest VLAN). If authentication fails, the device is denied access or placed in a quarantine VLAN. **MAB** (MAC Authentication Bypass) uses the device's MAC address as credentials for devices that don't support 802.1X (e.g., printers, IoT devices), allowing them to be placed in a designated VLAN.
