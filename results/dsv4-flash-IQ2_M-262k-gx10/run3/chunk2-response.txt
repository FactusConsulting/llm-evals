## Kubernetes (20 questions)

### K1 — Easy
A **Deployment** manages stateless applications — pods are interchangeable, scaled horizontally, and updated via rolling updates. A **StatefulSet** manages stateful applications — each pod has a stable identity (ordinal index), stable network identity (DNS name), and stable storage (persistent volumes that persist across restarts). StatefulSets also guarantee ordering (e.g., scale-up/scale-down, rolling updates in order). Deployments are for stateless apps (web servers, APIs); StatefulSets for databases, message brokers, or any app needing stable identity/storage.

### K2 — Easy
A ClusterIP Service has a stable virtual IP. It selects pods via a label selector. The Service creates **Endpoints** (list of pod IPs matching the selector). **kube-proxy** on each node programs iptables/IPVS rules that DNAT the Service IP to a chosen pod IP. Traffic is load-balanced (round-robin or random) among healthy endpoints. When a pod is added/removed, the Endpoints object updates, and kube-proxy updates the rules accordingly.

### K3 — Medium
- **PersistentVolume (PV)**: cluster-level storage resource, provisioned by admin or dynamically via StorageClass. It's the actual storage (NFS, EBS, etc.).
- **PersistentVolumeClaim (PVC)**: a request for storage by a user/pod. It binds to a matching PV (based on capacity, access modes, storage class).
- **StorageClass**: defines how storage is provisioned dynamically (provisioner, parameters, reclaim policy). PVCs can reference a StorageClass to get dynamically provisioned PVs.

Relationship: PVC → binds to PV → PV uses StorageClass (if dynamic). Pods consume PVCs via volumes.

### K4 — Medium
Troubleshooting CrashLoopBackOff:
1. **Check pod logs**: `kubectl logs <pod> --previous` (last crashed container) — look for app errors, panic, missing config.
2. **Check events**: `kubectl describe pod <pod>` — look for ImagePullBackOff, OOMKilled, liveness probe failures, invalid mounts.
3. **Check resource limits**: if OOMKilled, increase memory limits or fix memory leak.
4. **Check startup/liveness probes**: if probe fails, adjust `initialDelaySeconds`, `periodSeconds`, or fix the app's readiness endpoint.
5. **Check config/secret mounts**: verify env vars, ConfigMaps, Secrets are correct.
6. **Check image/command**: verify the container image exists, entrypoint is correct, and the command doesn't exit immediately.

### K5 — Medium
**CoreDNS** is the cluster's DNS server. It provides service discovery — pods resolve Service names (e.g., `my-svc.my-ns.svc.cluster.local`) and external domains. It reads the cluster's DNS records (Services, Pods) and answers queries.

If CoreDNS pods are down:
- **Service DNS resolution fails** — pods can't resolve cluster-internal names.
- **External DNS resolution fails** — pods can't resolve external domains (unless they have a fallback in `/etc/resolv.conf`).
- Existing connections may continue, but new connections requiring DNS will fail.
- The cluster itself keeps running, but any app relying on DNS breaks.

### K6 — Hard
The Kubernetes scheduler uses a two-phase process:

1. **Filtering (feasibility)**: removes nodes that can't run the pod. Checks include:
   - **Resource fit**: node has enough CPU/memory/GPU after accounting for existing requests.
   - **Node affinity/anti-affinity**: matches labels.
   - **Taints/tolerations**: pod must tolerate node taints.
   - **Pod anti-affinity**: respects pod placement constraints.
   - **Port conflicts**: no existing pod uses the same host port.
   - **Volume zone/region**: node has the required volume zones.
   - **Node conditions**: node is Ready, not MemoryPressure, DiskPressure, etc.

2. **Scoring (ranking)**: assigns scores to feasible nodes. Factors:
   - **Resource fit**: least requested vs. most requested (spread vs. bin-pack policies).
   - **Node affinity weight**: higher for preferred matches.
   - **Pod anti-affinity weight**: higher for preferred constraints.
   - **Inter-pod affinity**: prefer nodes with related pods (e.g., co-location).
   - **Spreading**: distribute pods across zones/nodes for HA.
   - **Node age/health**: prefer newer, healthier nodes.

The node with the highest score wins. Ties are broken by random selection.

### K7 — Hard
**Scheduling**: The node has 4GB RAM, 3.5GB already requested. The pod requests 256Mi. 3.5GB + 256Mi = 3.75GB < 4GB, so the pod **will be scheduled** (assuming no other constraints). The scheduler only considers **requests**, not limits.

**Runtime**: If the pod uses 600Mi at runtime:
- The pod's **limit** is 512Mi. The kernel cgroup will enforce this limit. When the pod exceeds 512Mi, the kernel will reclaim memory (OOM-kill the container or throttle). The pod will be **OOMKilled** or experience memory pressure.
- The node has 4GB total, 3.5GB requested, so there's 500MB free. The pod using 600Mi exceeds its own limit, so it gets killed regardless of node free memory.

### K8 — Hard
Full lifecycle of a request through NGINX Ingress:

1. **External LB** (e.g., cloud LB or MetalLB) receives the request on port 80/443. It forwards to the **Ingress Controller** service (NodePort or LoadBalancer).
2. **Ingress Controller** (NGINX pod) receives the request. It reads the **Ingress resource** (rules, paths, TLS) to determine which backend Service to route to.
3. NGINX performs **L7 routing** (host/path matching) and proxies the request to the **Service** (ClusterIP) — e.g., `my-svc:80`.
4. The Service has **Endpoints** — a list of pod IPs. kube-proxy has programmed **iptables** rules for the Service IP.
5. NGINX resolves the Service DNS (via CoreDNS) to the ClusterIP, then the request hits the iptables rule.
6. **kube-proxy/iptables** DNATs the ClusterIP to a selected pod IP (random/round-robin).
7. The request reaches the **application pod** via the pod's network namespace. The pod's container receives the request, processes it, and returns the response back through the same path.

### K9 — Medium
A **NetworkPolicy** is a resource that controls traffic between pods, namespaces, and external endpoints at the L3/L4 layer (IP/port). It uses label selectors to define which pods are affected and which traffic is allowed.

**Default behavior**: If no NetworkPolicy exists, **all traffic is allowed** (no restrictions).

**When you apply one**: The policy becomes **additive** — it only adds allowed rules. However, once a pod is selected by any NetworkPolicy, **all traffic not explicitly allowed is denied** (default-deny). So applying a policy that selects certain pods changes their behavior from allow-all to deny-all-except-allowed.

### K10 — Medium
- **RollingUpdate**: gradually replaces old pods with new ones. The Deployment controller ensures availability (max unavailable, max surge). Zero downtime, but slower rollout.
- **Recreate**: terminates all old pods first, then creates new ones. There's a brief downtime window. 

**When to choose Recreate**: When the application cannot have multiple versions running simultaneously (e.g., due to incompatible schema changes, or when the app requires exclusive access to a resource like a database migration). Also useful for testing/development where downtime is acceptable.

### K11 — Easy
A **namespace** is a virtual partition of a Kubernetes cluster. It provides isolation, scoping, and resource quotas. It separates environments (dev/prod), teams, or applications.

**Default namespaces** in a new cluster:
- `default` — for user workloads.
- `kube-system` — for system components (kube-proxy, CoreDNS, etc.).
- `kube-public` — for public resources (cluster-wide).
- `kube-node-lease` — for node heartbeats/lease objects.

### K12 — Easy
`kubectl describe pod <name>` shows detailed information about a pod, including:
1. **Events** — recent lifecycle events (pulled images, probe failures, scheduling decisions).
2. **Resource limits/requests** — CPU/memory for each container.
3. **Environment variables** — env vars set for each container.
4. **Mounted volumes** — which volumes are mounted and their paths.
5. **Node and tolerations** — which node it's on and any tolerations.
6. **Container status** — detailed state (running, terminated, waiting) with reasons.

`kubectl get pod` only shows basic info: name, ready, status, restarts, age, IP, node.

### K13 — Easy
A **ConfigMap** stores configuration data (key-value pairs, files) separately from container images. It decouples config from code.

**Consumption methods**:
1. **Environment variables**: `envFrom` or `env` with `valueFrom.configMapKeyRef`.
2. **Volume mount**: mount the ConfigMap as a file/directory (e.g., `/etc/config/`).
3. **Command-line arguments**: use ConfigMap values in the container's command.
4. **ConfigMap as a file in a volume**: each key becomes a file in the mount path.

### K14 — Easy
- **ClusterIP**: internal-only virtual IP. Accessible only within the cluster. Default type.
- **NodePort**: exposes the Service on a static port on every node (e.g., 30000-32767). Accessible via `nodeIP:nodePort` from outside.
- **LoadBalancer**: uses cloud provider's LB (or MetalLB) to assign an external IP. Routes traffic to the Service (which is internally a NodePort/ClusterIP).

### K15 — Easy
A **DaemonSet** ensures that a copy of a pod runs on **every node** (or a subset via nodeSelector). It's used for node-level infrastructure.

**Use cases**:
- Logging agents (Fluentd, Filebeat).
- Monitoring agents (Node Exporter, Prometheus).
- Network plugins (CNI).
- kube-proxy itself.

**When to use DaemonSet instead of Deployment**: When you need a pod on every node (or specific nodes) — e.g., collecting node-level logs, managing node storage, or running a node-level cache. Deployments scale based on replicas, not node count.

### K16 — Medium
**Taints and tolerations**: Taints are applied to nodes to repel pods. Tolerations are applied to pods to allow them to schedule on tainted nodes. They use a key, value, and effect (NoSchedule, PreferNoSchedule, NoExecute).

**Node affinity**: attracts pods to nodes based on labels (e.g., `requiredDuringScheduling` or `preferredDuringScheduling`). It's a positive constraint.

**Differences**:
- Taints/tolerations are **repelling** (don't schedule unless tolerated).
- Node affinity is **attracting** (schedule on nodes with matching labels).
- They can be combined.

**Practical use cases**:
- **Taints/tolerations**: Dedicate nodes to specific workloads (e.g., GPU nodes tainted so only GPU workloads tolerate them). Prevent workloads from scheduling on master nodes.
- **Node affinity**: Prefer scheduling a pod on a node in the same zone as its database (for low latency). Spread pods across zones for HA.

### K17 — Medium
A **Kubernetes Operator** is a pattern that extends Kubernetes to manage a specific application or service. It's a custom controller that watches a **Custom Resource (CR)** and reconciles the cluster state to match the desired state in the CR.

**Difference from a standard controller**:
- Standard controllers (e.g., Deployment controller) manage built-in resources.
- Operators manage **custom resources** (e.g., `Postgres`, `Prometheus`, `Etcd`) and encode domain-specific operational knowledge (backups, upgrades, scaling, recovery).

**Problems solved**:
- Automates complex operational tasks (backups, failover, scaling).
- Encapsulates human operational knowledge into code.
- Provides declarative management for stateful/distributed systems.
- Enables self-healing and automated upgrades.

### K18 — Hard
**etcd consistency model**: etcd uses **Raft consensus**. It's a linearizable, strongly consistent key-value store. Writes require a quorum (majority) of etcd nodes to agree. Reads can be served from any node (with linearizable reads requiring quorum).

**Quorum loss**: If the cluster loses quorum (e.g., 2 of 3 nodes down), etcd cannot accept writes or reads (for linearizable reads). The Kubernetes API server fails, and the cluster becomes **read-only** or **unavailable**. Pods keep running, but no new scheduling, no updates, no scaling.

**Recovery from 2 of 3 nodes lost**:
1. **Stop the remaining etcd node** to prevent split-brain.
2. **Take a snapshot** of the remaining node's data (`etcdctl snapshot save`).
3. **Restore the snapshot** on a new etcd cluster (e.g., 3 new nodes) using `etcdctl snapshot restore`.
4. **Update the etcd member list** in the cluster (via `etcdctl member list` and `member add`).
5. **Restart the API server** pointing to the new etcd cluster.
6. **Remove the old dead members** from the etcd cluster.

### K19 — Hard
**RBAC** (Role-Based Access Control) in Kubernetes:
- **Role**: defines permissions (verbs on resources) within a **namespace**.
- **ClusterRole**: defines permissions cluster-wide (or across all namespaces).
- **RoleBinding**: binds a Role to a user/group/ServiceAccount **within a namespace**.
- **ClusterRoleBinding**: binds a ClusterRole (or Role) cluster-wide.

**Developer read-only access to pods and logs in a single namespace**:

```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: dev-pod-reader
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### K20 — Hard
**ndots issue**: Pods have `/etc/resolv.conf` with `ndots:5` by default. This means DNS resolution tries to resolve the name as a fully-qualified domain name (FQDN) first, then appends search domains (e.g., `default.svc.cluster.local`). For external domains like `example.com`, the resolver tries:
1. `example.com.` (as FQDN)
2. `example.com.default.svc.cluster.local.`
3. `example.com.svc.cluster.local.`
4. `example.com.cluster.local.`
5. `example.com.` (again)

Each failed query adds latency (especially if the DNS server is slow or the search domains don't exist). With 5 search domains, it can take 5+ round trips.

**Fix using `dnsConfig`**:
```yaml
spec:
  containers:
  - name: app
    image: myapp
  dnsConfig:
    ndots: 1
    searches:
    - default.svc.cluster.local
    - svc.cluster.local
    - cluster.local
```
With `ndots:1`, the resolver treats names with fewer than 1 dot as relative (appends search domains) and names with 1+ dots as FQDN. External domains like `example.com` are resolved directly, reducing DNS queries from 5 to 1.

## Development (20 questions)

### D1 — Easy
**Git rebase** rewrites history by replaying commits from one branch onto another, creating a linear history. **Git merge** creates a new merge commit that combines branches, preserving the original branch history.

**When to avoid rebasing**:
- On **public/shared branches** (e.g., `main`) — rebasing rewrites history, causing conflicts for other developers.
- When you need to preserve the exact commit history (e.g., for audit).
- When the branch has many commits that are hard to replay (conflicts).

### D2 — Easy
**TCP** (Transmission Control Protocol): connection-oriented, reliable, ordered, flow-controlled. Guarantees delivery. Used by: HTTP/HTTPS, FTP, SMTP, SSH.

**UDP** (User Datagram Protocol): connectionless, unreliable, unordered, no flow control. Faster but no guarantees. Used by: DNS, DHCP, VoIP, video streaming, gaming.

### D3 — Medium
A **race condition** occurs when multiple threads/processes access shared data concurrently, and the outcome depends on the timing/interleaving of operations. It leads to inconsistent or incorrect results.

**Concrete example (Python)**:
```python
import threading
counter = 0

def increment():
    global counter
    for _ in range(1000):
        temp = counter
        # context switch here
        counter = temp + 1

threads = [threading.Thread(target=increment) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)  # Not 10000, but some smaller number due to race
```
The read-modify-write sequence is not atomic, so multiple threads can read the same value and write back, losing increments.

### D4 — Medium
**Symmetric encryption**: same key for encryption and decryption. Fast, but key distribution is a problem. Examples: AES, DES.

**Asymmetric encryption**: public key for encryption, private key for decryption (or vice versa). Slower, but solves key distribution. Examples: RSA, ECC.

**In TLS**:
1. Client and server exchange **public keys** (certificates).
2. Client verifies the server's certificate (asymmetric).
3. Client generates a **pre-master secret**, encrypts it with the server's public key (asymmetric), and sends it.
4. Both derive a **session key** (symmetric) from the pre-master secret.
5. All subsequent data is encrypted with the **symmetric session key** (AES) for speed.

### D5 — Medium
A **container image layer** is a filesystem diff. Images are composed of multiple layers, each representing a change (e.g., a `RUN` command in a Dockerfile). Layers are read-only and shared across images.

**Layer caching**: Docker caches layers. If a layer hasn't changed, it's reused. This speeds up builds.

**Dockerfile best practices**:
- **Order commands from least to most frequently changing** (e.g., `apt-get install` before copying source code).
- **Combine related commands** into a single `RUN` to reduce layers.
- **Use `COPY` after installing dependencies** so the dependency layer is cached.
- **Use `.dockerignore`** to avoid invalidating the cache with unnecessary files.

### D6 — Medium
Troubleshooting intermittent HTTP 503 (in order):
1. **Check server logs** — look for errors, stack traces, or resource exhaustion.
2. **Check load balancer / reverse proxy logs** — see which backend is failing, response times.
3. **Check application health** — is the app crashing, restarting, or hitting memory/CPU limits?
4. **Check database/upstream dependencies** — connection pool exhaustion, slow queries, timeouts.
5. **Check network** — DNS issues, firewall, TLS handshake failures.
6. **Check capacity** — is the service scaling properly? Are there too many requests?

### D7 — Hard
**CAP theorem**: In a distributed system, you can only guarantee two of three: **Consistency** (all nodes see the same data), **Availability** (every request gets a response), **Partition tolerance** (system works despite network partitions). When a partition occurs, you must choose between C and A.

**CP system (chooses Consistency over Availability)**: **ZooKeeper** — during a partition, it stops accepting writes/reads to maintain consistency. Also **etcd**, **HBase**.

**AP system (chooses Availability over Consistency)**: **Cassandra** — during a partition, it continues accepting reads/writes, but may return stale data. Also **DynamoDB** (in some modes), **CouchDB**.

### D8 — Medium
**Horizontal scaling** (scale-out): add more machines/nodes to distribute load. **Vertical scaling** (scale-up): add more resources (CPU, RAM) to a single machine.

**Architectural patterns enabling horizontal scaling**:
- **Stateless services** — no session state stored on the server.
- **Load balancing** — distribute requests across instances.
- **Shared storage** — database, object storage, cache (Redis) for shared state.
- **Message queues** — decouple producers/consumers.
- **Microservices** — decompose into independently scalable services.
- **Auto-scaling** — dynamically add/remove instances based on load.

### D9 — Easy

**Set persistently across shell sessions on Linux**:
- Add to `~/.bashrc` (for interactive shells) or `~/.profile`:

  ```bash
  export MY_VAR=value
  ```
- Add to `~/.bash_profile` (for login shells).
- Add to `/etc/environment` (system-wide).
- Add to `/etc/profile.d/` (system-wide, shell-agnostic).

### D10 — Easy
**JSON** (JavaScript Object Notation): text-based, uses key-value pairs, arrays, objects. Strict syntax, no comments, no multi-line strings.

**YAML** (YAML Ain't Markup Language): human-friendly, uses indentation, supports comments, multi-line strings, and more types (anchors, aliases).

**Advantages**:

### D11 — Easy
A **REST API** (Representational State Transfer) is an architectural style for designing networked applications. It uses HTTP methods to perform operations on resources (identified by URLs).

- **GET**: retrieve a resource (read-only, no side effects).
- **POST**: create a new resource (or trigger an action).
- **PUT**: update/replace an existing resource (idempotent).
- **DELETE**: remove a resource.

### D12 — Easy
**Version pinning** means specifying exact versions of dependencies (e.g., `package.json` with `"express": "4.18.2"` or `requirements.txt` with `Django==4.2.1`).

**Importance for reproducible builds**:
- Ensures the same code builds the same way every time.
- Prevents unexpected changes from dependency updates (breaking changes, security vulnerabilities).
- Makes debugging easier (you know exactly which versions are running).
- Enables rollback to known-good states.

### D13 — Easy
**Compiled language**: source code is translated into machine code before execution. Examples: C, C++, Go, Rust.

**Interpreted language**: source code is executed line-by-line by an interpreter at runtime. Examples: Python, JavaScript, Ruby, PHP.

### D14 — Medium
A **reverse proxy** sits in front of backend servers, forwarding client requests to them. It hides the backend topology, provides load balancing, caching, SSL termination, and security.

A **forward proxy** sits in front of clients, forwarding their requests to the internet. It provides anonymity, content filtering, and access control.

**Common reverse proxies**:
- **NGINX**: used for load balancing, static file serving, caching, SSL termination.
- **HAProxy**: used for high-performance TCP/HTTP load balancing, health checks, and failover.

### D15 — Medium
A **deadlock** occurs when two or more threads/processes are blocked, each waiting for resources held by the other, so none can proceed.

**Four Coffman conditions** (must all hold):
1. **Mutual exclusion**: at least one resource is non-shareable.
2. **Hold and wait**: a process holds a resource while waiting for another.
3. **No preemption**: resources cannot be forcibly taken away.
4. **Circular wait**: a cycle of processes each waiting for the next's resource.

### D16 — Hard
**Eventual consistency**: a distributed system where updates propagate asynchronously, and if no new updates occur, all replicas will eventually converge to the same state. Reads may return stale data temporarily.

**Cassandra read-after-write consistency**: Cassandra uses tunable consistency levels. For read-after-write, you can use `QUORUM` for both read and write to ensure the read sees the latest write. Or use `QUORUM` write and `QUORUM` read.

**Tunable consistency levels**:
- `ONE`: any replica (fastest, may be stale).
- `QUORUM`: majority of replicas (stronger).
- `ALL`: all replicas (strongest, slowest).
- `LOCAL_QUORUM` / `LOCAL_ONE`: for multi-datacenter setups.
- `EACH_QUORUM`: quorum in each DC.

### D17 — Hard
**mTLS (mutual TLS)** is TLS where **both** client and server authenticate each other using certificates.

**Full handshake process**:
1. Client sends `ClientHello` (supported ciphers, TLS version).
2. Server responds with `ServerHello`, its **certificate**, and requests a client certificate (`CertificateRequest`).
3. Client verifies the server's certificate (against a CA).
4. Client sends its **certificate** and a `CertificateVerify` message (proving possession of the private key).
5. Server verifies the client's certificate.
6. Client sends `ClientKeyExchange` (pre-master secret encrypted with server's public key).
7. Both derive session keys.
8. Both send `Finished` messages (encrypted) to confirm the handshake.

**Where mTLS is used**:
- Service mesh (Istio, Linkerd) for inter-service communication.
- API gateways for client authentication.
- Zero-trust security models.
- Database connections (e.g., PostgreSQL with client certs).

### D18 — Hard
A **hash table** uses a hash function to map keys to indices in an array (buckets). 

**Collision resolution**:
- **Chaining**: each bucket is a linked list (or tree). Collisions are stored in the same bucket.
- **Open addressing**: on collision, probe the next slot (linear probing, quadratic probing, double hashing).

**Time complexity**:
- **Average**: O(1) for insertion, lookup, deletion (assuming good hash function and load factor).
- **Worst case**: O(n) — when all keys hash to the same bucket (chaining) or the table is nearly full (open addressing).

### D19 — Hard
The **circuit breaker pattern** prevents cascading failures in microservices. It wraps a remote call and monitors failures.

**Three states**:
1. **Closed**: requests flow normally. If failures exceed a threshold (e.g., 50% failure rate), the circuit opens.
2. **Open**: requests fail fast (without hitting the remote service). After a timeout (e.g., 30s), it moves to half-open.
3. **Half-open**: a few trial requests are allowed. If they succeed, the circuit closes. If they fail, it reopens.

**Relation to retry policies and exponential backoff**:
- Circuit breakers are a **higher-level** protection — they stop retries when the system is failing.
- Retry policies with exponential backoff are used **within** the closed state — they retry failed requests with increasing delays.
- When the circuit is open, retries are **not attempted** — they fail fast, preventing resource exhaustion.

### D20 — Hard
**Optimistic concurrency control**: assumes conflicts are rare. It doesn't lock resources; instead, it checks for conflicts at commit time (e.g., using a version number or timestamp). If a conflict is detected, the transaction is rolled back.

**Pessimistic concurrency control**: assumes conflicts are frequent. It locks resources (e.g., `SELECT FOR UPDATE`) to prevent other transactions from modifying them until the lock is released.

**When to choose each**:
- **Optimistic**: when conflicts are rare (e.g., read-heavy workloads, low contention). Good for web apps where transactions are short.
- **Pessimistic**: when conflicts are frequent (e.g., financial systems, inventory management). Good for long transactions or when data integrity is critical.

**Concrete examples**:
- **Optimistic**: `UPDATE accounts SET balance = balance - 100, version = version + 1 WHERE id = 1 AND version = 5;` — if the version doesn't match, the update fails.
- **Pessimistic**: `SELECT * FROM accounts WHERE id = 1 FOR UPDATE;` — locks the row until the transaction commits or rolls back.
