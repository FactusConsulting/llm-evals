## Go (20 questions)

### G1 — Easy: Slice vs Array
An array has a fixed size determined at compile time (`[5]int`), while a slice is a dynamic view into an array (`[]int`) with a length and capacity. Slices are the idiomatic choice for variable-length sequences. When you append to a slice that has reached its capacity, Go allocates a new, larger backing array (typically doubling capacity), copies the existing elements, and then appends the new element. The slice header is updated to point to the new array.

### G2 — Easy: `var x int` vs `x := 0`
`var x int` declares a variable with the zero value (0) and explicit type. `x := 0` uses short variable declaration, inferring the type from the literal (also `int`). You cannot use `:=` at package scope (only inside functions), cannot use it when the variable is already declared (unless at least one variable on the left is new), and cannot use it to declare a variable with a type that differs from the inferred type without explicit conversion.

### G3 — Medium: Goroutines and GMP
A goroutine is a lightweight, cooperatively-scheduled thread managed by the Go runtime, starting with a small stack (a few KB) that grows as needed. OS threads have large fixed stacks and are scheduled by the OS with expensive context switches. The GMP model: **G** (goroutine), **M** (OS thread/machine), **P** (processor/logical CPU). Each P has a local run queue of Gs; M executes Gs on a P. When a G blocks (e.g., on I/O), the M is released and another M picks up the P. This enables efficient multiplexing of millions of goroutines onto a few OS threads.

### G4 — Medium: Channels
Channels are typed conduits for goroutine communication. An **unbuffered** channel blocks the sender until a receiver is ready, and blocks the receiver until a sender is ready (synchronous). A **buffered** channel has a capacity; sends succeed if there's room, otherwise block until space frees up. Sending to a full buffered channel blocks the sender until another goroutine receives from it. Closing a channel signals that no more values will be sent; receivers get zero values after close.

### G5 — Medium: context package
The `context` package carries deadlines, cancellation signals, and request-scoped values across API boundaries. It's used to propagate cancellation to goroutines and prevent resource leaks. Minimal example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

req, err := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
if err != nil { /* handle */ }
resp, err := http.DefaultClient.Do(req)
if err != nil { /* handle timeout/cancel */ }
```

### G6 — Medium: Interface satisfaction
Go interfaces are satisfied **implicitly** — a type satisfies an interface if it implements all methods, with no explicit declaration. This differs from Java/C# where classes must explicitly declare `implements`. This enables duck-typing and makes it easy to create small, focused interfaces. The empty interface `interface{}` (or `any` in Go 1.18+) accepts any type. It's powerful for generic containers or unknown values, but dangerous because it bypasses type safety, requiring type assertions and causing runtime panics if misused.

### G7 — Hard: Memory model and goroutine visibility
The code is unsafe because there's no synchronization between the goroutine writing `data`/`ready` and the main goroutine reading them. Without a happens-before relationship, the compiler and CPU may reorder operations, so the main goroutine might see `ready = true` before `data = "hello"`, or never see the writes at all. Correct alternatives: use a `sync.Mutex`, a channel (e.g., `done := make(chan struct{})`), or `sync/atomic` with proper memory barriers. The Go memory model guarantees that a send on a channel happens-before the corresponding receive, and mutex unlock happens-before lock.

### G8 — Hard: Mutex vs RWMutex, sync.Map
`sync.Mutex` provides exclusive access; only one goroutine can hold the lock. `sync.RWMutex` allows multiple readers or a single writer. Use `RWMutex` when reads are frequent and writes are rare, as it reduces contention. `sync.Map` is optimized for cases where keys are written once and read many times, or when multiple goroutines access disjoint keys. It uses internal sharding and atomic operations, avoiding lock contention. Trade-offs: `sync.Map` has higher overhead for simple cases; a regular map with a mutex is simpler and faster for low contention. `RWMutex` has higher memory overhead than `Mutex` but better read concurrency.

### G9 — Hard: Go modules
Go modules are the dependency management system. `go.mod` declares the module path, Go version, and dependencies with their versions. `go.sum` contains cryptographic checksums of module content to verify integrity and prevent tampering. `go mod tidy` adds missing dependencies, removes unused ones, and updates `go.sum`. **Minimum Version Selection (MVS)** chooses the minimum version of each dependency that satisfies all transitive requirements — if module A requires B v1.2 and C requires B v1.5, MVS selects v1.5. This ensures reproducibility and avoids the "dependency hell" of version conflicts.

### G10 — Medium: defer
`defer` schedules a function call to run when the enclosing function returns, typically for cleanup (closing files, unlocking mutexes). Multiple defers execute in **LIFO order** (last deferred runs first). A common gotcha: deferring in a loop accumulates deferred calls until the function returns, not per-iteration. If you need per-iteration cleanup, wrap the loop body in a helper function or use a closure that runs immediately.

### G11 — Easy: Pointers
A pointer holds the memory address of a value. The zero value of a pointer is `nil`. You create a pointer to a struct literal with `&MyStruct{...}` or `new(MyStruct)`. Example: `p := &Person{Name: "Alice"}`. Pointers allow sharing values without copying and enable mutation through functions.

### G12 — Easy: init() function
`init()` runs automatically before `main()` (or before package usage), after all package-level variables are initialized. It's used for setup that can't be done in variable declarations. A package can have **multiple** `init()` functions (in the same file or across files). They execute in file order (by filename) and declaration order within a file, after dependency packages' `init()` functions. They cannot be called explicitly.

### G13 — Easy: make vs new
`new(T)` allocates zeroed memory and returns a pointer `*T` — it works with any type. `make(T, args)` only works with slices, maps, and channels, and returns an initialized (non-zero) value of that type. `make` is for types that need internal initialization (e.g., slice header, map hash buckets, channel buffer). You'd use `new` for scalar types or structs, `make` for the three built-in reference types.

### G14 — Easy: Error handling
Go uses explicit error returns. The `error` interface is `type error interface { Error() string }`. Idiomatic pattern: check `if err != nil` immediately after a call, handle or return it. `errors.Is(err, target)` checks if err wraps target (for sentinel errors), `errors.As(err, &target)` checks if err can be assigned to a specific error type. These are preferred over `==` because they respect wrapping with `%w` in `fmt.Errorf`.

### G15 — Easy: Composite types and zero values
- **map**: `map[K]V` — zero value is `nil` (can't be written to, must be initialized with `make` or literal)
- **slice**: `[]T` — zero value is `nil` (can be appended to, but `len` is 0)
- **channel**: `chan T` — zero value is `nil` (blocks forever on send/receive)
- **struct**: `struct{}` — zero value is a struct with all fields at their zero values

### G16 — Medium: Race conditions
A race condition occurs when multiple goroutines access the same variable concurrently, and at least one access is a write, without synchronization. The `-race` flag instruments the program with the race detector, which records memory accesses and detects conflicting unsynchronized accesses at runtime. Example:
```go
var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }() // race!
}
```
Fix with a mutex:
```go
var mu sync.Mutex
for i := 0; i < 1000; i++ {
    go func() { mu.Lock(); counter++; mu.Unlock() }()
}
```
Or with a channel: use a channel to send increments and a single goroutine to process them.

### G17 — Medium: select statement
`select` waits on multiple channel operations, choosing one that's ready. Unlike `switch` (which evaluates values), `select` blocks until one of its cases can proceed. If multiple cases are ready, it picks one **randomly** (to prevent starvation). You can implement a timeout:
```go
select {
case msg := <-ch:
    fmt.Println(msg)
case <-time.After(5 * time.Second):
    fmt.Println("timeout")
}
```

### G18 — Hard: Escape analysis
Escape analysis is a compiler optimization that determines whether a variable can be allocated on the stack or must "escape" to the heap. If a variable's address is returned, stored in a global, or passed to a function that might store it, it escapes. The compiler uses this to decide allocation. You can inspect with `go build -gcflags=-m` (or `-m=2` for more detail). It matters because stack allocation is nearly free (no GC pressure), while heap allocation requires garbage collection and can cause cache misses. Avoiding escapes (e.g., by using value receivers or not returning pointers) improves performance.

### G19 — Hard: Reflection
`reflect.Type` describes the type (e.g., name, kind, methods), while `reflect.Value` holds the actual value and allows inspection/modification. Reflection is slow (can be 10-100x slower than direct code) because it involves runtime type checks, interface boxing, and dynamic dispatch. It's justified for generic serialization (e.g., JSON), ORMs, testing frameworks, or when the type is unknown at compile time. For performance-critical paths, code generation (e.g., `go generate`) or generics (Go 1.18+) are preferred.

### G20 — Hard: go:embed
`go:embed` embeds files into the compiled binary at compile time. Syntax:
```go
//go:embed file.txt
var content string

//go:embed dir/*
var files embed.FS
```
It works for single files (into `string` or `[]byte`) or directories (into `embed.FS`). Limitations: files must be in the module (no `..` or absolute paths), patterns can't match directories recursively with `...` (only `*` for one level), and embedded files are read-only. `embed.FS` implements `fs.FS`, so it works with `io/fs` functions like `fs.ReadFile` and `fs.WalkDir`.

## Rust (20 questions)

### R1 — Easy: Ownership
Ownership rules: (1) Each value has a single owner; (2) When the owner goes out of scope, the value is dropped; (3) Ownership can be transferred (moved) but not borrowed implicitly. These rules ensure memory safety without a garbage collector — the compiler tracks ownership at compile time, preventing double-free, use-after-free, and dangling pointers.

### R2 — Easy: String vs &str
`String` is an owned, heap-allocated, growable UTF-8 string. `&str` is a borrowed string slice (a reference to a sequence of UTF-8 bytes). In function signatures, use `&str` for read-only access (most common), `String` when you need to own or modify the string, and `&mut String` for in-place mutation. `&str` is more flexible — it can be a slice of a `String`, a string literal, or a `&[u8]` converted with `from_utf8`.

### R3 — Medium: Borrowing and borrow checker
Borrowing allows using a value without taking ownership. Rules: (1) You can have many immutable references (`&T`) simultaneously; (2) You can have at most one mutable reference (`&mut T`) at a time; (3) You cannot have a mutable reference while immutable references exist. The borrow checker enforces these at compile time, preventing data races and dangling references. It also ensures references don't outlive the value they point to.

### R4 — Medium: Result and Option
`Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`). `Option<T>` represents presence (`Some(T)`) or absence (`None`). The `?` operator unwraps `Ok`/`Some` or returns the `Err`/`None` early from the function. Example:
```rust
use std::fs;
use std::io::Read;

fn read_file(path: &str) -> Result<String, std::io::Error> {
    let mut file = fs::File::open(path)?;
    let mut contents = String::new();
    file.read_to_string(&mut contents)?;
    Ok(contents)
}
```

### R5 — Medium: Box, Rc, Arc
- `Box<T>`: single owner, heap-allocated value. Used for recursive types, large data, or trait objects.
- `Rc<T>`: single-threaded reference-counted pointer. Multiple owners share the value; drops when last owner drops. Not `Send`/`Sync`.
- `Arc<T>`: atomic reference-counted pointer for multi-threaded sharing. Slightly slower due to atomic operations. Use `Rc` for single-threaded sharing, `Arc` for multi-threaded, `Box` for single ownership.

### R6 — Medium: Traits
Traits define shared behavior (like Go interfaces) but are more powerful: they can have associated types, generic parameters, and default methods. Go interfaces are structural (implicit), while Rust traits require explicit `impl` blocks. A **trait object** (`dyn Trait`) enables dynamic dispatch (like Go interfaces) — the concrete type is hidden behind a pointer. A **generic with trait bound** (`T: Trait`) uses static dispatch — the compiler generates specialized code for each type, which is faster (no vtable lookup) but increases binary size.

### R7 — Hard: Lifetimes
The function fails because the return type `&str` has no lifetime parameter — the compiler can't determine how long the returned reference lives. Fix:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This says the returned reference lives as long as the shorter of `x` and `y`. Lifetimes ensure references are always valid — the compiler checks that the return value doesn't outlive the inputs.

### R8 — Hard: Send and Sync
`Send` means a value can be transferred to another thread. `Sync` means a value can be safely shared across threads (accessed by reference). `Rc<T>` is not `Send` because the reference count is not atomic — if two threads drop the last `Rc` simultaneously, it could double-free. `Arc<T>` uses atomic operations for the count, making it `Send` and `Sync` (when `T` is). `Arc<T>` is safe because the atomic count ensures the value is dropped exactly once, and `T` must be `Send`/`Sync` for the whole `Arc` to be.

### R9 — Hard: async/await
Rust's async/await is based on `Future` — a state machine that can be polled. `async fn` returns a `Future`; `await` polls it until ready. The executor (e.g., Tokio) drives futures to completion, handling I/O events and scheduling. Unlike Go's goroutines (which are preemptively scheduled on OS threads), Rust futures are **cooperatively scheduled** — they only advance when polled. This means no runtime overhead for scheduling, but you must ensure futures yield (e.g., via `tokio::time::sleep`) to avoid blocking the executor. Rust's model gives more control (no hidden runtime) but requires more explicit management.

### R10 — Medium: unsafe
`unsafe` allows: (1) Dereferencing raw pointers (`*const T`, `*mut T`); (2) Calling unsafe functions (e.g., FFI to C); (3) Accessing/modifying mutable static variables; (4) Implementing `Send`/`Sync` manually; (5) Using inline assembly. Unsafe is justified when: interacting with hardware, FFI, or implementing safe abstractions that the compiler can't verify (e.g., `Vec`'s memory management). It's not a license to ignore safety — the unsafe code must uphold Rust's safety invariants.

### R11 — Easy: Pattern matching
`match` is exhaustive — the compiler requires all possible patterns to be covered. `if let` is a shorthand for matching a single pattern and ignoring the rest (e.g., `if let Some(x) = opt`). The compiler enforces exhaustiveness: if you miss a variant, it's a compile error. This prevents runtime panics from unhandled cases. `match` can also bind variables, use guards (`if` conditions), and destructure tuples/structs.

### R12 — Easy: Vec vs array
`Vec<T>` is a heap-allocated, growable sequence. `[T; N]` is a fixed-size array on the stack (or inline in a struct). When `Vec` exceeds its capacity, it allocates a new, larger buffer (typically doubling), copies elements, and deallocates the old buffer. Arrays have a compile-time size and can't grow. `Vec` is the idiomatic dynamic collection; arrays are for fixed-size data.

### R13 — Easy: Enums
Rust enums are **algebraic data types** — variants can carry data (like tagged unions). C/Java enums are just named constants. Rust enums enable exhaustive matching and prevent invalid states. `Option<T>` is an enum: `Some(T)` or `None`. Rust has no `null` because it eliminates the billion-dollar mistake — absence is explicit via `Option`, and the compiler forces you to handle it. This prevents null pointer dereferences at compile time.

### R14 — Easy: impl blocks
`impl` defines methods and associated functions for a type. Methods take `self` (by value), `&self` (immutable borrow), or `&mut self` (mutable borrow). `self` consumes the value (moves it), `&self` reads, `&mut self` mutates. Associated functions (e.g., `String::new()`) don't take `self` and are called with `::` — they're like static methods. `impl` can also define trait implementations (`impl Trait for Type`).

### R15 — Easy: derive macros
`#[derive(Debug, Clone, PartialEq)]` automatically generates trait implementations. Common ones: `Debug` (formatting with `{:?}`), `Clone` (deep copy), `PartialEq` (equality), `Eq` (total equality), `Hash`, `PartialOrd`/`Ord` (ordering), `Serialize`/`Deserialize` (via serde). You **cannot** derive a trait if the type contains fields that don't implement that trait (e.g., can't derive `Clone` if a field is `Rc<T>` without `Clone`), or if the trait requires manual implementation (e.g., `Display` for custom formatting).

### R16 — Medium: Cow
`Cow<'a, T>` (clone-on-write) is an enum: `Borrowed(&'a T)` or `Owned(T)`. It allows returning a borrowed value when possible, or an owned clone when needed. Useful when you might modify data — if it's borrowed, it clones; if it's owned, it mutates in place. Example:
```rust
fn normalize(s: &str) -> Cow<'_, str> {
    if s.contains(' ') {
        Cow::Owned(s.replace(' ', "_"))
    } else {
        Cow::Borrowed(s)
    }
}
```
This avoids allocation when no modification is needed.

### R17 — Medium: Module system
`mod` declares a module (inline or from a file), `use` brings items into scope, `pub` makes items public. In Rust 2015, modules map to files: `mod foo;` loads `foo.rs` or `foo/mod.rs`. In Rust 2018, the `mod.rs` convention was replaced — `mod foo;` loads `foo.rs` and submodules go in `foo/bar.rs` (no `mod.rs` needed). The 2018 edition also allows `use` paths to be more uniform and supports `crate::` for absolute paths.

### R18 — Hard: Pin
`Pin<T>` prevents the value from being moved out of its memory location. It's needed for **self-referential structs** — where a field points to another field within the same struct. If the struct is moved, the pointer becomes dangling. Async/await creates such structs (futures hold references to their own local variables across awaits), so futures are `Pin`ned before being polled. `Unpin` is a marker trait — types that are safe to move even when pinned (most types). `Pin<Box<dyn Future>>` is the standard way to store a future on the heap.

### R19 — Hard: Macros
Declarative macros (`macro_rules!`) match patterns and generate code — they're limited to pattern matching and token manipulation. Procedural macros (derive, attribute, function-like) run Rust code at compile time to transform the token stream — they're more powerful but require a separate crate. Hygiene rules: declarative macros are hygienic (local variables don't collide with caller's), but procedural macros are not fully hygienic — they can introduce items that may conflict. Macros enable metaprogramming, reducing boilerplate, but can increase compile time and binary size.

### R20 — Hard: Zero-cost abstractions
Zero-cost abstractions mean high-level constructs compile to the same machine code as hand-written low-level code. **Iterators** are compiled to efficient loops (no allocation, no virtual calls) via inlining and constant folding. **Generics** use monomorphization — the compiler generates specialized code for each concrete type, eliminating runtime dispatch. **Trait static dispatch** (`impl Trait` or generic bounds) resolves method calls at compile time, unlike `dyn Trait` which uses vtable lookup. This gives Rust the ergonomics of high-level languages with the performance of C — the compiler optimizes away the abstraction layers.
