## Application Architecture

**AA1** — A monolith is a single deployable application where all business logic, data access, and UI are packaged together. Microservices decompose the application into independently deployable services, each with its own data store and API. Three concrete problems microservices introduce that monoliths don't have: (1) **network latency and partial failures** — every service call is a remote call that can time out or fail, requiring retries, timeouts, and circuit breakers; (2) **distributed data consistency** — no single ACID transaction spans services, forcing patterns like Saga or eventual consistency; (3) **operational complexity** — deploying, monitoring, and debugging across many services requires sophisticated CI/CD, distributed tracing, and log aggregation.

**AA2** — **Synchronous** communication: the caller blocks and waits for a response before continuing. Example: REST/HTTP over JSON, or gRPC with unary calls. **Asynchronous** communication: the caller sends a message and continues processing; the receiver processes it later, possibly with a reply on a separate channel. Example: RabbitMQ or Kafka message queues, or JMS. Synchronous is simpler for request-response workflows; asynchronous decouples services, improves resilience, and handles bursts.

**AA3** — An **API Gateway** is a specialized reverse proxy that sits at the API layer, providing cross-cutting concerns: authentication, rate limiting, API versioning, request routing, protocol translation (e.g., REST→gRPC), and aggregation. A **reverse proxy** is a general-purpose L7 proxy that forwards HTTP/TCP traffic to backend servers, handling TLS termination, load balancing, and static content. An API Gateway **cannot fully replace** a reverse proxy because: (1) reverse proxies handle non-API traffic (WebSockets, raw TCP, static files, gRPC without HTTP/2 mapping); (2) API Gateways are often application-specific and don't provide generic L4/L7 features like caching, compression, or connection pooling; (3) in practice, you often need both — a reverse proxy (e.g., Nginx) in front of an API Gateway for TLS and routing.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a series of local transactions, each with a compensating action to undo it if a later step fails. **Choreography-based sagas**: each service publishes events and listens for others' events; there's no central coordinator. Pros: loose coupling, no single point of failure. Cons: hard to trace and test. **Orchestration-based sagas**: a central orchestrator (e.g., a Saga Execution Coordinator) commands each service step-by-step and handles compensation. Pros: easier to understand and maintain. Cons: central point of failure and coupling. Choreography suits simple workflows with few participants; orchestration suits complex workflows with many services, clear business logic, and need for centralized error handling.

**AA5** — **CQRS** separates the read model (queries) from the write model (commands), often using different data stores or schemas. **Event Sourcing** stores the state as an immutable sequence of events; the current state is derived by replaying events. Combined, they solve problems traditional CRUD doesn't: (1) **scalability** — reads and writes scale independently; (2) **auditability** — every change is an event, giving a complete audit trail; (3) **replayability** — you can rebuild state or project new read models from events; (4) **complex business logic** — events capture intent, not just state changes, enabling better domain modeling. The combination is powerful for systems with complex workflows, audit requirements, or need for temporal queries.

**AA6** — The **Circuit Breaker pattern** prevents cascading failures by failing fast when a downstream service is unhealthy. Three states: **Closed** (normal operation, requests pass), **Open** (fail fast, no requests pass), **Half-Open** (allow a few test requests to see if the service recovered). It differs from **retry with backoff**: retry keeps attempting the same operation, which can amplify load during an outage; a circuit breaker stops attempts entirely after a threshold. Use both together: retry with backoff for transient failures (e.g., network blips), circuit breaker for prolonged failures (e.g., service down). The circuit breaker can also be combined with retries inside the closed state.

**AA7** — Multi-tenant isolation models:
1. **Shared DB, shared schema (row-level tenant ID)**: lowest cost, simplest operations, but highest security risk (SQL injection or bug could leak tenant data), highest noisy-neighbor risk (one tenant's heavy query impacts all), and complex to implement row-level security.
2. **Shared DB, separate schema per tenant**: moderate cost, better logical isolation (schema separation), still shares DB resources (CPU, I/O), noisy-neighbor risk remains, but security is better (can restrict access per schema). Operational complexity increases (schema migrations per tenant).
3. **Separate DB per tenant**: highest cost (more DB instances), best security and isolation, no noisy-neighbor risk, but operational complexity is highest (many DBs to manage, backup, monitor). Cost scales linearly with tenants.
Trade-offs: cost decreases from 3→1, security and isolation increase from 1→3, operational complexity is highest for 3 (many instances) and 1 (complex row-level security). Choose based on compliance requirements, tenant size, and budget.

**AA8** — **Eventual consistency** means updates propagate asynchronously; reads may return stale data. **Strong consistency** guarantees that any read returns the most recent write. For an inventory system that must never oversell, you need **strong consistency** on the inventory count. Architecture: use a single source of truth — a relational database (PostgreSQL) with row-level locking (`SELECT FOR UPDATE`) or a Redis with atomic operations (`DECR` with check). At scale: use **optimistic locking** (version numbers) or **pessimistic locking** (row locks) on the inventory record. For high throughput, partition inventory by SKU and use a distributed lock (e.g., ZooKeeper) or a single-node Redis with Lua scripts for atomic decrement. Avoid eventual consistency for the inventory count itself; use it only for non-critical data (e.g., product descriptions).

**AA9** — A **sidecar proxy** is a lightweight proxy co-located with a service instance, handling all network communication to and from the service. In **Istio**, **Envoy** is the sidecar proxy that handles L7 traffic: load balancing, retries, TLS, circuit breaking, and telemetry. **Data plane**: the Envoy proxies that carry traffic between services. **Control plane**: Istio's Pilot (config distribution), Mixer (policy/telemetry), and Citadel (certificate management) — they configure and manage the data plane. **mTLS between sidecars** solves service-to-service authentication and encryption at the mesh level, independent of application-level TLS. It ensures that only authenticated services can communicate, prevents man-in-the-middle attacks, and provides identity-based authorization (e.g., service accounts). Application-level TLS only encrypts data; it doesn't provide identity verification between services.

**AA10** — The **Strangler Fig pattern** incrementally replaces a legacy monolith with new services. Concrete strategy for .NET Framework → .NET 8 microservices: (1) **Identify bounded contexts** — decompose the monolith into domains (e.g., orders, customers, billing). (2) **Extract one service at a time** — create a new .NET 8 microservice for one domain, with its own database. (3) **Use a facade** — put an API Gateway or reverse proxy in front of the monolith; route traffic for the extracted domain to the new service, all other traffic to the monolith. (4) **Migrate data** — copy data incrementally, use dual-write or event-driven sync during transition. (5) **Retire legacy code** — once all traffic is routed to new services, remove the old module. Repeat until the monolith is fully replaced. This minimizes risk by keeping the system running during migration.

**AA11** — The **12-Factor App** methodology defines best practices for building cloud-native, portable applications. Six key factors: (1) **Codebase** — one codebase, multiple deploys; (2) **Dependencies** — explicitly declare and isolate dependencies; (3) **Config** — store config in environment variables, not code; (4) **Backing services** — treat services (DB, cache) as attached resources, swap easily; (5) **Build/release/run** — strictly separate build, release, and run stages; (6) **Processes** — stateless processes, no shared state. Others: port binding, concurrency, disposability, dev/prod parity, logs, admin processes. These matter for cloud-native because they enable portability, scalability, and continuous delivery.

**AA12** — **Event-driven architecture (Kafka)** vs **request-driven (REST/gRPC)**:
- **Coupling**: Event-driven is loosely coupled — services don't know each other, only events. Request-driven is tightly coupled — caller knows the service's API.
- **Scalability**: Event-driven scales well for bursts and fan-out; request-driven scales with load balancers but can bottleneck on synchronous calls.
- **Debugging**: Request-driven is easier to trace (request-response); event-driven is harder — need to trace events across topics.
- **Ordering**: Kafka provides per-partition ordering; REST/gRPC provides natural request ordering but no global ordering.
- **Failure handling**: Event-driven uses retries, dead-letter queues, replay; request-driven uses retries, timeouts, circuit breakers.
Choose event-driven for decoupled, asynchronous, high-throughput systems (e.g., order processing, analytics). Choose request-driven for simple, synchronous workflows (e.g., CRUD APIs, user-facing operations).

**AA13** — A **load balancer** distributes incoming traffic across multiple backend servers to improve performance and availability. **Layer 4 (L4)** load balancing operates at the transport layer (TCP/UDP), forwarding connections based on IP and port, without inspecting content. **Layer 7 (L7)** load balancing operates at the application layer, inspecting HTTP headers, URLs, and cookies to route requests. L7 is required for: HTTP-based routing (e.g., `/api` → service A, `/web` → service B), sticky sessions based on cookies, TLS termination, and API gateway functionality.

**AA14** — A **message queue** (RabbitMQ) delivers messages to consumers, typically removing them after consumption; supports complex routing (topics, headers), acknowledgments, and dead-letter queues. A **log-based message broker** (Kafka) stores an append-only log; consumers read at their own offset and can replay messages; designed for high throughput and event streaming. Pick RabbitMQ for task distribution, RPC, or complex routing; pick Kafka for event sourcing, stream processing, data pipelines, and replayable event logs.

**AA15** — A **container** packages an application and its dependencies (libraries, binaries) into a lightweight, portable unit that shares the host OS kernel. A **virtual machine** includes a full guest OS, virtualized hardware, and is isolated at the hypervisor level. Containers are smaller, start faster, and use fewer resources. They're popular for microservices because they provide consistent environments, enable high density on a single host, and integrate well with orchestration (Kubernetes).

**AA16** — **Stateless services** don't store any session or user state between requests; each request is independent. **Stateful services** maintain state (e.g., user sessions, data) that persists across requests. Stateless services are easier to scale horizontally because any instance can handle any request — no need to share or replicate state; you can add/remove instances freely. Example: a stateless REST API that reads from a database; a stateful example: a database server or a WebSocket chat server that maintains connection state.

**AA17** — An **ORM** (Object-Relational Mapper) maps database tables to objects in code, allowing developers to work with data using language-native constructs instead of SQL. Examples: Hibernate (Java), Entity Framework (C#), SQLAlchemy (Python). Trade-offs: ORMs reduce boilerplate, prevent SQL injection, and provide portability, but can be slower (N+1 queries), hide performance issues, and make complex queries harder. Raw SQL gives full control, better performance for complex queries, and clearer optimization, but requires more code and is error-prone.

**AA18** — The **Bulkhead pattern** isolates resources (thread pools, connections, memory) so that a failure in one part of the system doesn't exhaust resources for others. In microservices, it prevents one slow service from consuming all threads/connections and causing cascading failures. Concrete implementation: use separate thread pools per service or per dependency (e.g., one pool for DB queries, one for external API calls). Or deploy services in separate containers/instances with CPU/memory limits. Example: in Java, create `ExecutorService` per downstream service with a bounded queue; if one service is slow, its pool fills up, but other services still have their own pools.

**AA19** — **Operational Transformation (OT)** and **CRDTs** are conflict-resolution strategies for collaborative editing. **OT** uses a central server that transforms operations to converge; it provides strong consistency, low latency (with server), but is complex to implement and requires a central coordinator. **CRDTs** are data structures that merge automatically; they support offline editing, are decentralized, and simpler to reason about, but can have higher memory overhead and eventual consistency (not strong). For a system that must support offline editing, **CRDTs** are better because they allow any replica to merge changes without a central server, and they naturally handle concurrent edits. OT requires a central server to resolve conflicts, making offline editing difficult.

**AA20** — Distributed tracing across polyglot microservices: **Context propagation** uses W3C Trace Context (`traceparent` header) or B3 headers to carry trace ID and parent span ID across service calls. **Sampling**: head-based sampling decides at the first request whether to trace; tail-based sampling decides after the trace is complete (e.g., sample only traces with errors). **Storage/querying**: Jaeger or Grafana Tempo store traces and provide query APIs. **Async messaging**: when a request passes through Kafka, the trace context must be propagated in the message headers (e.g., `traceparent` in Kafka record headers). The producer injects the context, the consumer extracts it and continues the trace. This ensures trace continuity across async boundaries. Challenges: polyglot requires language-agnostic headers, sampling decisions must be consistent across services, and async messages need explicit header propagation.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 hypervisor** (bare-metal) runs directly on hardware, providing VM isolation without a host OS. Examples: VMware ESXi, Microsoft Hyper-V (bare-metal mode), KVM (as a kernel module). **Type 2 hypervisor** (hosted) runs on top of an existing OS. Examples: Oracle VirtualBox, VMware Workstation, Parallels Desktop. Type 1 is used in production for performance and stability; Type 2 is for development/testing.

**OP2** — **SAN** (Storage Area Network) provides block-level storage over a dedicated network; it appears as raw disks to servers. Protocols: Fibre Channel, iSCSI. **NAS** (Network Attached Storage) provides file-level storage over the network; it appears as a file share. Protocols: NFS, SMB/CIFS. Use SAN for databases, virtual machine disks, and high-performance workloads; use NAS for file sharing, home directories, and application data that needs file semantics.

**OP3** — **3-tier network architecture**: core (routing, high-speed), distribution (policy, aggregation), access (end-user connectivity). It's hierarchical, with east-west traffic traversing multiple hops. **Leaf-spine** is a flat, two-tier architecture where every leaf (access) switch connects to every spine (core) switch. It solves the problem of **east-west traffic bottlenecks** and **oversubscription** in 3-tier — in 3-tier, traffic between servers on different access switches must go up to distribution and core, adding latency and limiting bandwidth. Leaf-spine provides predictable, low-latency, high-bandwidth connectivity with any-to-any communication.

**OP4** — **Proxmox HA cluster** architecture: **Node count**: at least 3 nodes for quorum (majority voting). **Quorum**: uses a vote-based system; a node needs majority to remain active. **Fencing**: STONITH (Shoot The Other Node In The Head) — a watchdog or IPMI/iLO to power off a failed node. **Shared storage**: Ceph (distributed, self-managing), iSCSI (central SAN), or NFS (shared filesystem). On node failure: the HA agent detects the loss, fences the node, and migrates VMs to surviving nodes. Ceph provides automatic data rebalancing; iSCSI/NFS require the storage to be highly available separately.

**OP5** — **VLAN trunking** carries multiple VLANs over a single link using **802.1Q tagging**, which inserts a 4-byte VLAN tag (including VLAN ID) into the Ethernet frame. To put a single NIC on 3 VLANs in Linux: create VLAN subinterfaces — `ip link add link eth0 name eth0.10 type vlan id 10`, `eth0.20`, `eth0.30` — and assign IP addresses to each. The switch port must be configured as a trunk port with allowed VLANs.

**OP6** — **RAID levels**: **RAID 1** mirrors data across 2 drives (fault tolerance, 50% capacity). **RAID 5** stripes data with parity across 3+ drives (1 drive failure, good capacity). **RAID 6** stripes with double parity across 4+ drives (2 drive failures). **RAID 10** mirrors and stripes (4+ drives, high performance, 2 drive failures). **RAID Z2** (ZFS) is similar to RAID 6 but uses variable block sizes and checksums. For a database server with 6 drives, **RAID 10** is best: it provides high performance (striping), fault tolerance (mirroring), and fast rebuilds. RAID 5/6 have write penalty and slower rebuilds; RAID 10 maximizes IOPS for database workloads.

**OP7** — **DNS architecture for 500-person enterprise**: Internal AD DNS servers are authoritative for `internal.corp` and resolve AD records. DMZ has public-facing services with external DNS. **Split-horizon DNS**: internal DNS returns internal IPs for internal names; external DNS returns public IPs. **Recursive resolvers** (internal) handle client queries; **forwarders** send unresolved queries to external resolvers; **conditional forwarding** sends queries for specific domains (e.g., `partner.com`) to partner DNS. When a laptop moves from office to VPN: on the office network, it uses internal DNS via DHCP; on VPN, it uses VPN-assigned DNS or internal DNS over the tunnel. The laptop's DNS resolver must be configured to use internal DNS when on VPN to resolve internal names.

**OP8** — **PKI chain of trust**: Root CA (offline, self-signed) → subordinate/issuing CA (online, signed by root) → end-entity certificates (signed by issuing CA). **CRL** (Certificate Revocation List) is a periodically published list of revoked certs; **OCSP** (Online Certificate Status Protocol) provides real-time revocation status. **Certificate templates** define attributes (e.g., server auth, client auth). **Auto-enrollment** uses Group Policy to automatically request and install certificates. **Compromised subordinate CA**: you can revoke its cert and reissue from the root; impact is limited to certs issued by that CA. **Compromised root CA**: the entire PKI is compromised — all certs must be revoked and reissued; you must rebuild the root and re-enroll all clients.

**OP9** — **WAN options for 5 remote offices**: **MPLS**: reliable, low latency, but expensive and rigid. **IPsec VPN over internet**: cost-effective, but latency and reliability depend on internet; management complexity is moderate. **SD-WAN**: uses internet but with intelligent path selection, application-aware routing, and centralized management; cost-effective, good for VoIP, but requires SD-WAN devices. **WireGuard mesh**: simple, secure, fast, but lacks enterprise features (centralized management, QoS). For 50 users per site with latency-sensitive VoIP, **SD-WAN** is best: it provides cost-effective, reliable connectivity with QoS for VoIP, centralized management, and failover across multiple links.

**OP10** — **iDRAC** (Dell), **iLO** (HPE), **IPMI** are out-of-band management interfaces that allow remote server management (power, console, sensors) even when the OS is down. They're critical for troubleshooting, firmware updates, and remote recovery. If exposed to the internet, they're a severe security risk: attackers can gain full control of the server (power cycle, console access, firmware compromise), leading to data theft or ransomware. Always restrict IPMI to management VLANs and require strong authentication.

**OP11** — **LVM** (Logical Volume Manager): traditional volume management with snapshots that are copy-on-write but can degrade performance. **LVM-Thin**: thin provisioning, efficient snapshots (also COW), better for large-scale virtualization. **ZFS**: filesystem with integrated volume management, checksums, and efficient snapshots (COW, space-efficient). Use LVM for simple volume management; LVM-Thin for thin provisioning and many snapshots; ZFS for data integrity, compression, and advanced snapshotting. Snapshot semantics: LVM snapshots are COW and can fill up; LVM-Thin snapshots are efficient but require thin pool; ZFS snapshots are instant, space-efficient, and can be rolled back.

**OP12** — **Ceph stretch cluster / DR strategy**: Use **CRUSH rules** to define data placement across two sites (e.g., `site1` and `site2`). **Monitor placement**: place an odd number of monitors across sites, with a tiebreaker (e.g., a third site or a monitor on a witness node). **Network latency**: Ceph requires low latency (<10ms) between sites for synchronous replication; otherwise, use async replication. **Split-brain problem**: if two sites lose connectivity, both may try to write; without a tiebreaker, data corruption can occur. **2-site Ceph is bad** because with 2 monitors (one per site), a network partition causes both sites to lose quorum (each has 1 of 2 votes). A tiebreaker (third monitor or witness) ensures one site retains quorum. For DR, use a 3-site setup or a tiebreaker, and replicate data asynchronously to a DR site.

**OP13** — **DHCP** (Dynamic Host Configuration Protocol) assigns IP addresses and network config. **DORA process**: Discover (client broadcasts), Offer (server offers an IP), Request (client requests the offered IP), Ack (server acknowledges). If the DHCP server is unavailable and a Windows client's lease expires, the client uses **APIPA** (Automatic Private IP Addressing) — it assigns itself an address in 169.254.0.0/16 and continues to retry DHCP periodically.

**OP14** — A **managed switch** supports configuration, monitoring, and advanced features: VLANs, QoS, link aggregation, SNMP, port security, spanning tree, and remote management. An **unmanaged switch** is plug-and-play with no configuration. In an enterprise, managed switches are essential for network segmentation (VLANs), traffic prioritization (QoS), monitoring (SNMP), and security (port security, 802.1X).

**OP15** — **NTP** (Network Time Protocol) synchronizes clocks across servers. Accurate time is critical for: log correlation (security and debugging), Kerberos authentication (time skew limits), database replication (timestamps), and distributed systems (ordering). Clock drift between servers causes: Kerberos tickets fail, logs are out of order, database conflicts, and distributed consensus issues (e.g., Paxos/Raft).

**OP16** — **Physical server**: bare metal, full hardware access, no virtualization overhead. **Virtual machine**: virtualized hardware, full OS, isolated, portable. **Container**: shares host OS kernel, lightweight, fast startup. Run workloads directly on bare metal when: you need maximum performance (HPC, GPU), specialized hardware (FPGA, InfiniBand), or legacy software that doesn't virtualize well. Otherwise, VMs/containers provide better utilization and management.

**OP17** — A **UPS** provides short-term battery backup to bridge power outages (minutes) and protect against surges. A **generator** provides long-term power (hours/days) using fuel. You need both: the UPS covers the gap between power loss and generator startup, and protects against flickers. An **ATS** (Automatic Transfer Switch) automatically switches the load between utility power and generator power, ensuring seamless transition.

**OP18** — **Active-passive clustering**: one node is active, the other is standby; failover is fast but the standby is idle. **Active-active clustering**: both nodes serve traffic; failover is more complex but provides load balancing. For PostgreSQL HA with Pacemaker/Corosync: configure **STONITH** (fencing) using IPMI or watchdog to power off a failed node. Use a **virtual IP** that floats between nodes. On failure: Pacemaker detects the loss, fences the failed node, promotes the standby (or surviving node) to primary, and moves the VIP. Failover behavior: the standby promotes to primary, the VIP is reassigned, and clients reconnect using the VIP.

**OP19** — **Backup strategy for 50 servers**: Follow the **3-2-1 rule** (3 copies, 2 different media, 1 offsite). Define **RPO** (recovery point objective, e.g., 15 minutes) and **RTO** (recovery time objective, e.g., 4 hours). Use **full backups** weekly, **incremental** daily, and **differential** as needed. Use **deduplication** to reduce storage. Store backups on **disk** (fast recovery), **tape** (long-term archive), and **cloud** (offsite). Use **immutable backups** (WORM or object lock) to protect against ransomware. **Test restores** regularly to ensure backups are valid. **Backup vs DR**: backup is copying data; disaster recovery is the full process of restoring systems, including infrastructure, configuration, and procedures.

**OP20** — **802.1X** port-based access control: **Supplicant** (client device) requests access; **authenticator** (switch) enforces port control; **authentication server** (RADIUS) validates credentials. **EAP methods**: **EAP-TLS** uses client certificates (strong, mutual auth); **PEAP** uses a server cert and tunnels inner authentication (e.g., MSCHAPv2). The switch sends the EAP request to the RADIUS server; on success, the RADIUS server can assign a **dynamic VLAN** based on policy. If authentication fails, the port is blocked (or placed in a guest VLAN). **MAB** (MAC Authentication Bypass) works by the switch sending the device's MAC address to the RADIUS server as the username/password; it's used for devices that don't support 802.1X (e.g., printers, IoT), providing a fallback based on MAC address whitelisting.
