## Cloud Infrastructure Architecture

**CL1 — Easy: IaaS vs PaaS vs SaaS**
- **IaaS**: Provider offers raw compute, storage, and networking. You manage OS, runtime, and apps. Example: AWS EC2.
- **PaaS**: Provider manages OS and runtime; you deploy apps. Example: Azure App Service.
- **SaaS**: Provider delivers fully managed software. Example: Microsoft 365.
Key difference: increasing provider responsibility from IaaS → PaaS → SaaS, decreasing customer control.

**CL2 — Easy: Shared Responsibility Model**
- **IaaS (EC2)**: Provider secures physical host, hypervisor, network. You secure guest OS, apps, data, access, patches.
- **Managed Kubernetes (EKS/AKS)**: Provider secures control plane, nodes, and underlying infra. You secure pods, containers, images, RBAC, secrets, and cluster policies.
- **SaaS (M365)**: Provider secures service, physical infra, and compliance. You secure user accounts, data classification, device compliance, and identity policies.
General rule: provider secures "of the cloud," customer secures "in the cloud."

**CL3 — Medium: VPC, Subnet, Security Group, NACL**
- **VPC**: Virtual private network boundary in cloud; logically isolated segment.
- **Subnet**: IP range within VPC; can be public or private; maps to availability zones.
- **Security Group (SG)**: Instance-level virtual firewall; stateful; allows only (no deny rules); evaluated per instance.
- **NACL**: Subnet-level firewall; stateless; supports allow/deny rules; evaluated in order.
Layering: VPC → subnets → NACLs (subnet boundary) + SGs (instance boundary). SG is stateful (return traffic auto-allowed); NACL is stateless (must explicitly allow return traffic). SG is first line for instances; NACL is a second layer for subnet-wide control.

**CL4 — Medium: Multi-Account Strategy**
- **Landing Zone**: Pre-configured baseline with accounts, IAM, and policies (e.g., AWS Control Tower, Azure Enterprise Scale).
- **Organizational Units (OUs)**: Hierarchical grouping (e.g., Dev, Prod, Security, Network) for policy inheritance.
- **Guardrails**: Preventive (SCP/Policy) and detective (Config/Policy) controls enforced across accounts.
- **Shared Networking**: Central hub account with Transit Gateway (AWS) or Hub-and-Spoke (Azure) for inter-VPC connectivity; avoids per-account VPNs.
- **Centralized Logging**: Aggregated CloudTrail/Flow Logs/Activity Logs into a central log archive account.
Single-account problems: no isolation for blast radius, no separation of duties, compliance violations, and inability to scale with teams.

**CL5 — Medium: Infrastructure as Code (IaC)**
- **Terraform/OpenTofu**: Declarative, multi-cloud, state-based; best for broad cloud-agnostic provisioning.
- **Pulumi**: Declarative/imperative with general-purpose languages (Python, Go); good for complex logic and code reuse.
- **CloudFormation/Bicep**: Native AWS/Azure; deep integration, but vendor-locked; Bicep is simpler than ARM/CFN.
- **Crossplane**: Control-plane-based IaC; Kubernetes-native; enables platform teams to expose APIs for app teams.
Choose: Terraform for multi-cloud and mature ecosystem; Pulumi for code-heavy teams; CloudFormation/Bicep for single-cloud deep integration; Crossplane for platform engineering and GitOps-style provisioning.

**CL6 — Medium: Autoscaling Patterns**
- **HPA**: Scales pod replicas based on CPU/memory/custom metrics; horizontal.
- **VPA**: Adjusts pod CPU/memory requests/limits; vertical; requires restart.
- **Cluster Autoscaler**: Adds/removes nodes when pods cannot be scheduled.
- **KEDA**: Event-driven autoscaler; scales based on queue length, Kafka lag, custom metrics; works with HPA.
Use KEDA over HPA when scaling is driven by external events (e.g., SQS queue depth, Prometheus metrics) rather than CPU/memory; HPA is for standard resource-based scaling.

**CL7 — Hard: Disaster Recovery Strategy**
- **RPO/RTO**: Define acceptable data loss (RPO) and downtime (RTO); e.g., RPO=15min, RTO=1hr.
- **Active-Active**: Both regions serve traffic; DNS routes to nearest; requires multi-region writes or sharding; complex but fast failover.
- **Active-Passive**: Primary serves; secondary standby; failover via DNS; simpler but slower.
- **Database Replication**: Sync replication (lower RPO, higher latency) vs async (higher RPO, lower latency); choose based on RPO.
- **DNS Failover**: Route53 health checks / Azure Traffic Manager; can be automated with failover policies.
- **State Management**: Use managed services (S3, Cosmos DB) with cross-region replication; avoid local state.
- **Cost**: Active-active doubles infra cost; warm standby reduces cost but increases failover time.
- **DR Patterns**: Pilot light (minimal standby, scale up on failover), warm standby (pre-provisioned but idle), multi-site active-active (both live).

**CL8 — Hard: GitOps Model**
- **GitOps**: Git is single source of truth for desired state; controller reconciles cluster to match Git.
- **ArgoCD vs FluxCD**: ArgoCD has richer UI, multi-cluster management, and app-level sync; Flux is more lightweight, integrates with Git providers, and has better multi-tenancy.
- **Secrets**: Use Sealed Secrets (encrypt secrets in Git), External Secrets Operator (fetch from Vault/AWS Secrets Manager), or Vault agent injection; never store plaintext in Git.
- **Drift**: Controller detects drift and reverts manual changes; can alert or auto-sync; manual changes are overwritten unless disabled.

**CL9 — Hard: Stateful Legacy App on Kubernetes**
- **StatefulSet**: Stable network identity and ordered deployment; each pod gets a unique name.
- **PV/PVC with Local Storage Class**: Use local SSDs for low latency; PVC binds to a specific node; use topology constraints to schedule pods on the same node.
- **Headless Service**: Provides stable DNS names for each pod; enables peer discovery.
- **Init Containers**: Run ordered startup scripts (e.g., wait for dependencies, configure files).
- **ConfigMaps as Volume Mounts**: Mount config files at exact paths; use subPath for specific files.
- **Pod Disruption Budgets**: Ensure minimum availability during voluntary disruptions; protect stateful pods.

**CL10 — Medium: Service Accounts vs Workload Identity vs IRSA**
- **Service Account (K8s)**: Kubernetes identity for pods; used for API access.
- **Workload Identity (GCP/Azure)**: Cloud identity mapped to K8s service account; allows cloud API access.
- **IRSA (AWS)**: IAM roles for service accounts; uses OIDC federation to map K8s SA to IAM role.
Mounting cloud credentials in pods is bad: credentials can be stolen, rotated poorly, and grant broad access. Workload identity federation uses OIDC to exchange K8s identity for cloud credentials, eliminating static secrets.

**CL11 — Medium: Object vs Block vs File Storage**
- **Object (S3/Blob)**: Key-value store for unstructured data; highly durable (11 nines), scalable; use for backups, media, analytics.
- **Block (EBS/Managed Disk)**: Raw disk attached to VMs; low latency; use for databases, OS disks.
- **File (EFS/Azure Files)**: Shared file system over NFS/SMB; use for shared app data, home directories.
Durability: Object (11 nines), Block (99.999% per AZ), File (similar to object). Availability: Object (99.99%), Block (99.99% per AZ), File (99.9%).

**CL12 — Hard: Zero-Trust for Kubernetes**
- **Network Policies**: Micro-segmentation at pod level; restrict east-west traffic.
- **Service Mesh (Istio/Linkerd)**: mTLS between pods; identity-based auth; observability.
- **Pod Identity**: Use workload identity (IRSA/Workload Identity) for cloud access; avoid static creds.
- **Admission Controllers (OPA/Kyverno)**: Enforce policies (e.g., no privileged containers, required labels).
- **Image Signing**: Sign images with cosign; verify signatures at admission.
- **Runtime Security (Falco)**: Detect anomalous syscalls, file access, and network behavior.
- **Secrets Management**: Use Vault/External Secrets; never store in Git.
Zero-trust differs from perimeter: assumes no implicit trust; every request is authenticated and authorized; no "inside" vs "outside."

**CL13 — Easy: CDN**
- **CDN**: Distributed edge servers that cache content closer to users; reduces latency and origin load.
- **How it works**: User requests → edge node → cache hit or miss → origin fetch → cache.
- **Examples**: AWS CloudFront, Azure CDN.
Use CDN for static content (images, videos, JS/CSS), API acceleration, and DDoS mitigation; serve directly from origin for dynamic, personalized, or low-traffic content.

**CL14 — Easy: Regions and Availability Zones**
- **Region**: Geographic area with multiple AZs (e.g., us-east-1).
- **AZ**: Isolated data center within a region; independent power/cooling/network.
Deploy across AZs for high availability (e.g., multi-AZ RDS, load-balanced instances). Zonal resources (e.g., EBS) are tied to one AZ; regional resources (e.g., S3, ELB) span AZs.

**CL15 — Easy: Managed Databases**
- **Managed DB (RDS, Cloud SQL, Azure SQL)**: Provider handles backups, patching, replication, monitoring, and failover.
- **On VM**: You handle all operational tasks (install, patch, backup, HA).
Managed DBs reduce admin overhead, provide built-in HA, and scale easily; but may have vendor lock-in and limited customization.

**CL16 — Easy: Cloud Identity Services**
- **IAM Users**: Individual accounts for people/services.
- **Groups**: Collections of users; policies applied to groups.
- **Roles**: Temporary credentials for services or federated users; assume via trust policies.
- **Policies**: JSON documents defining permissions (allow/deny).
Principle of least privilege: grant only required permissions; use roles over static keys; regularly audit and remove unused access.

**CL17 — Easy: Serverless Computing**
- **Serverless**: Run code without managing servers; pay per invocation; auto-scaling.
- **Examples**: AWS Lambda, Azure Functions, Google Cloud Functions.
- **Cold Starts**: Delay when a function is first invoked (container spin-up); matters for latency-sensitive apps.
Serverless is a poor fit for long-running processes, stateful workloads, or low-latency critical paths; better for event-driven, bursty, or short-lived tasks.

**CL18 — Medium: Kubernetes Ingress Options**
- **Ingress Resource**: Defines routing rules; implemented by controller (e.g., NGINX); TLS termination at controller.
- **Gateway API**: Newer, more expressive; supports HTTP, TCP, and service mesh; TLS termination at gateway.
- **Cloud LB Annotations**: Use cloud-specific annotations (e.g., AWS ALB) for L7 routing; TLS at LB.
- **Service Mesh Ingress Gateway**: Mesh-managed ingress (e.g., Istio Gateway); TLS termination at mesh edge; supports advanced routing.
Use Gateway API over Ingress for multi-protocol support, better namespace isolation, and future-proofing; traditional Ingress is simpler but limited.

**CL19 — Hard: Cost Optimization Strategy**
- **Reserved Instances/Savings Plans**: Commit for 1-3 years for up to 70% savings; use for steady-state workloads.
- **Spot/Preemptible**: Use for fault-tolerant, batch, or stateless workloads; up to 90% savings.
- **Right-Sizing**: Analyze utilization; downsize over-provisioned resources.
- **Storage Tiering**: Use S3 Intelligent-Tiering for auto-tiering; Archive for cold data.
- **Idle Detection**: Use tools (AWS Trusted Advisor, Azure Cost Advisor) to find idle resources; automate shutdown.
- **FinOps**: Establish cost ownership, tagging, and budgeting; implement showback/chargeback.
Tools: Cloud Cost Management (CloudHealth, FinOps platforms), tagging policies, budget alerts, and regular reviews.

**CL20 — Hard: Multi-Cloud Strategy**
- **Abstraction Layers**: Use Kubernetes for compute, Terraform for IaC, and cloud-agnostic APIs for storage/DB.
- **Networking**: VPN/interconnect between clouds; use service mesh for cross-cloud traffic.
- **Identity Federation**: Use OIDC/SAML to federate identities across clouds.
- **Trade-offs**: Multi-cloud adds complexity, latency, and cost; benefits include avoiding lock-in and resilience.
Multi-cloud is justified for regulatory requirements, disaster recovery, or leveraging best-of-breed services; unnecessary complexity for most workloads—single-cloud with good architecture is often better.

## OT Infrastructure Architecture

**OT1 — Easy: Purdue Model (ISA-95)**
- **Level 0**: Physical processes (sensors, actuators).
- **Level 1**: Basic control (PLCs, RTUs, DCS controllers).
- **Level 2**: Supervision (HMIs, SCADA servers, historians).
- **Level 3**: Operations management (MES, batch management, plant historian).
- **Level 4**: Business planning (ERP, enterprise systems).
- **Level 5**: (Sometimes added) Cloud/enterprise analytics.
The model segments OT into zones for security and control.

**OT2 — Easy: IT vs OT Networks**
- **IT**: Focus on data integrity, confidentiality, and availability; frequent patching; dynamic IPs; standard protocols.
- **OT**: Focus on safety, availability, and real-time control; patching can disrupt production; legacy protocols; long device lifecycles.
Standard IT patching can cause downtime, incompatibility with legacy systems, or safety issues; OT requires careful change management and testing.

**OT3 — Medium: DMZ/IDMZ**
- **IDMZ**: Industrial DMZ sits between IT (Level 4) and OT (Level 3); isolates traffic.
- **Allowed Traffic**: Only necessary protocols (e.g., HTTPS for remote access, MQTT for data) from IT to DMZ; OT to DMZ for data collection; no direct IT-to-control traffic.
- **Why direct Level 4 to Level 1 is dangerous**: A compromise in IT can directly reach control systems, bypassing security zones; DMZ acts as a buffer with strict rules.

**OT4 — Medium: OT Protocols**
- **Modbus TCP**: Level 1/2; industrial protocol for PLC communication; simple, insecure.
- **OPC UA**: Level 2/3; standardized data exchange; secure, platform-independent.
- **EtherNet/IP (CIP)**: Level 1/2; industrial Ethernet protocol; used for I/O and control.
- **PROFINET**: Level 1/2; industrial Ethernet for real-time control.
- **MQTT**: Level 3/4; lightweight pub/sub for IoT/cloud data; often used for telemetry.

**OT5 — Medium: Data Diode vs Firewall**
- **Data Diode**: Hardware device that allows one-way data transfer; physically prevents reverse traffic.
- **Firewall**: Two-way filtering; can be bypassed if misconfigured.
Use data diode for unidirectional data flows (e.g., sending OT data to IT) where reverse traffic is unacceptable; limitation: no return traffic, so no remote commands or updates.

**OT6 — Medium: SCADA Data Flow to Cloud**
- **Flow**: PLCs → OPC UA server (Level 2) → historian (Level 3) → edge gateway → MQTT broker → cloud ingestion.
- **Security Boundaries**: Place firewall between Level 2 and 3; use IDMZ for cloud connectivity; encrypt MQTT with TLS; authenticate devices.
- **Edge Gateway**: Aggregates and filters data; can buffer if cloud is unavailable.

**OT7 — Hard: IEC 62443 Zones and Conduits**
- **Zone**: Group of assets with similar security requirements; defined by function, risk, and trust.
- **Conduit**: Communication path between zones; controlled by firewall rules.
- **Design for Manufacturing Plant**:
  - Zone 1: Corporate network (Level 4) — low security.
  - Zone 2: Engineering workstations (Level 3) — medium security.
  - Zone 3: SCADA servers (Level 3) — high security.
  - Zone 4: PLCs (Level 1) — critical security.
  - Zone 5: SIS (Level 1) — highest security; isolated.
  - Conduits: Only allow specific protocols (e.g., OPC UA from SCADA to PLCs); block all others.

**OT8 — Hard: Network Segmentation for Manufacturing Plant**
- **VLAN Design**: Separate VLANs per production line, engineering, SCADA, and IT; assign IP subnets.
- **Firewall Placement**: Deploy firewalls between zones (e.g., IT/OT boundary, per line); use industrial firewalls.
- **Switch Architecture**: Use managed switches with VLAN support; segment at access layer.
- **Remote Access**: Use jump hosts with MFA and session recording; never direct VPN to HMIs.
- **Transition**: Phased approach—start with monitoring, then segment critical lines, test during maintenance windows; avoid disrupting production.

**OT9 — Hard: SIS vs BPCS**
- **BPCS**: Basic process control system; handles normal operations (e.g., temperature control).
- **SIS**: Safety instrumented system; prevents or mitigates hazardous events (e.g., emergency shutdown).
- **IEC 61511**: Standard for functional safety in process industries; requires SIS to be independent and reliable.
- **Isolation**: SIS must be air-gapped or isolated to prevent cyber attacks from affecting safety functions.
- **Ransomware on SIS**: Could disable safety shutdowns, leading to catastrophic accidents; must be isolated and monitored.

**OT10 — Medium: PLC vs DCS vs SCADA**
- **PLC**: Programmable logic controller; discrete control; used for small to medium automation.
- **DCS**: Distributed control system; integrated control for large continuous processes (e.g., chemical plants).
- **SCADA**: Supervisory control and data acquisition; monitors and controls remote assets; higher-level than PLC.
They can coexist: PLCs for local control, DCS for complex processes, SCADA for remote monitoring.

**OT11 — Medium: Remote Access to OT**
- **Architecture**: Use jump hosts (bastion) in DMZ; enforce MFA; record sessions; grant time-limited access.
- **Vendor Access**: Use vendor-specific accounts with least privilege; revoke after use.
- **Why RDP directly to HMI is unacceptable**: Exposes critical systems to network attacks; no audit trail; bypasses security controls.

**OT12 — Hard: Water Treatment Facility Incident Response**
- **Detection**: Deploy IDS (e.g., Suricata) on Level 3; monitor for anomalies; use asset inventory to baseline.
- **Response**: Isolate compromised vendor VPN; block traffic; preserve logs; coordinate with control room to maintain safe operations.
- **Operator Role**: Operators must continue monitoring processes; may need to switch to manual control if automation is compromised.
- **Plan**: Have an incident response plan with clear roles; test regularly; ensure safety systems are unaffected.

**OT13 — Easy: HMI**
- **HMI**: Human-Machine Interface; graphical display for operators to monitor and control processes.
- **Role**: Provides real-time data, alarms, and control inputs.
- **Difference from Engineering Workstation**: HMI is for operators; engineering workstation is for programmers to configure PLCs and systems.

**OT14 — Easy: Historian**
- **Historian**: Time-series database for process data (e.g., temperatures, pressures).
- **Importance**: Enables trend analysis, troubleshooting, and compliance.
- **Plant Historian (Level 3)**: Collects data from control systems; high-resolution.
- **Enterprise Historian (Level 4)**: Aggregates data from multiple plants for business analytics; lower resolution.

**OT15 — Easy: Ladder Logic**
- **Ladder Logic**: Graphical programming language for PLCs; resembles relay logic diagrams.
- **Executed by**: PLCs.
- **Why dominant**: Familiar to engineers; simple for discrete control; robust and proven; easy to troubleshoot.

**OT16 — Easy: RTU vs PLC**
- **RTU**: Remote Terminal Unit; used for remote monitoring and control; often in harsh environments; communicates over long distances.
- **PLC**: Local control; faster processing; more I/O.
- **RTU deployment**: Remote sites (e.g., pipelines, substations) where local control is minimal; PLC for local automation.

**OT17 — Easy: Analog vs Digital Signals**
- **Analog**: Continuous signals (4-20mA, 0-10V); represent variable measurements.
- **Digital**: Discrete signals (0/1); represent on/off states.
- **Why 4-20mA preferred**: 4mA represents zero; allows detection of wire break (0mA); less affected by voltage drops; standard for process instrumentation.

**OT18 — Medium: OT Asset Inventory**
- **Importance**: Foundation for security; you can't protect what you don't know.
- **Discovery Tools**: Passive monitoring (e.g., Nozomi, Dragos) to listen to traffic; active scanning (e.g., Nmap) to query devices.
- **Why active scanning is dangerous**: Can disrupt legacy devices, cause crashes, or trigger safety shutdowns; use passive first, active only with caution.

**OT19 — Hard: MITRE ATT&CK for ICS**
- **Tactics**: 
  - **Initial Access**: Exploit internet-facing devices (e.g., VPN compromise).
  - **Execution**: Malicious code on PLC (e.g., ladder logic injection).
  - **Persistence**: Modify controller firmware.
  - **Lateral Movement**: Pivot from IT to OT via unsegmented network.
  - **Impact**: Disrupt process (e.g., modify setpoints).
- **Difference from Enterprise**: ICS framework includes physical impact, safety, and controller-specific techniques.
- **Use**: Map defenses to tactics; identify gaps (e.g., no monitoring for firmware changes).

**OT20 — Hard: Converged IT/OT SOC**
- **Log Collection**: Use passive collectors (e.g., SPAN ports) to avoid impacting OT; forward to SIEM.
- **SIEM Integration**: Correlate OT logs with IT; use OT-specific parsers.
- **Detection Rules**: Create rules for unauthorized firmware changes, unexpected PLC writes, or abnormal traffic.
- **Alert Triage**: IT analysts handle IT alerts; OT engineers handle OT alerts; escalate to both for cross-domain.
- **False Positives**: OT environments have stable traffic; baseline to reduce noise; use context-aware rules.
- **Firmware Change Alert**: Verify with asset inventory; isolate affected device; check for unauthorized access; coordinate with plant operations; if malicious, initiate incident response and preserve evidence.
