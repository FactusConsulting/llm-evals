## Kubernetes (20 questions)

**K1 — Easy:** A **Deployment** is for stateless applications: pods are interchangeable, have random names, and share a single volume (if any). A **StatefulSet** is for stateful applications: each pod has a stable network identity (e.g., `pod-0`), stable persistent storage (each pod gets its own PVC), and supports ordered deployment/scaling (e.g., scale down from `N` to `0` one at a time).

**K2 — Easy:** A ClusterIP Service has a virtual IP (VIP) that is not a real endpoint. `kube-proxy` watches the Service's Endpoints (the list of matching pod IPs) and programs `iptables`/IPVS rules on every node. When a pod sends traffic to the VIP, the node's iptables rules DNAT the packet to a randomly selected pod IP from the Endpoints list, providing load balancing.

**K3 — Medium:** A **PersistentVolume (PV)** is a cluster-level storage resource (e.g., a NFS share, cloud disk) that exists independently of pods. A **PersistentVolumeClaim (PVC)** is a request for storage by a user/pod; it binds to a matching PV. A **StorageClass** enables dynamic provisioning: when a PVC references a StorageClass, the provisioner creates a new PV on demand (e.g., `gp2` on AWS). They relate as: PVC → StorageClass → dynamically created PV → mounted into a pod.

**K4 — Medium:** Troubleshooting CrashLoopBackOff:
1. **Check pod logs**: `kubectl logs <pod>` (or `--previous` for the last crashed container) to see application errors.
2. **Check events**: `kubectl describe pod <pod>` for OOMKilled, failed liveness/readiness probes, or image pull failures.
3. **Check resource limits**: If the container exceeds `limits.memory`, it gets OOMKilled; check `kubectl describe node` for pressure.
4. **Check configuration**: Verify ConfigMaps, Secrets, and env vars are correctly mounted (e.g., missing DB connection string).
5. **Check dependencies**: Test if the pod can reach a database or API endpoint (e.g., `kubectl exec` and curl).
6. **Check the container image/command**: Verify the entrypoint/command is correct and the image exists.

**K5 — Medium:** CoreDNS is the cluster's DNS server. It serves `Service` names (e.g., `my-svc.my-ns.svc.cluster.local`) and external DNS queries. If CoreDNS pods are down, pods cannot resolve cluster services by name (they may fall back to external DNS if configured, but internal service discovery breaks). Pods' `/etc/resolv.conf` points to CoreDNS; without it, DNS queries fail or time out, breaking most applications.

**K6 — Hard:** The Kubernetes scheduler uses a two-phase process:
- **Filtering (feasibility)**: Removes nodes that cannot run the pod. Checks include: node selector/affinity, taints/tolerations, resource requests (CPU/memory vs. allocatable), volume zone conflicts, and pod anti-affinity.
- **Scoring (priority)**: Ranks feasible nodes. Factors include: least requested resources (spreads load), node affinity/anti-affinity weights, pod spread across zones, and inter-pod affinity (e.g., co-locate with a cache).
- **Specific factors**: (1) **Resource requests** (CPU/memory), (2) **Node affinity/anti-affinity**, (3) **Taints/tolerations**, (4) **Data locality** (volume zones), (5) **Pod anti-affinity** (spread for HA).

**K7 — Hard:** Node has 4GB RAM, 3.5GB already requested. Pod requests 256Mi. 3.5GB + 256Mi ≈ 3.75GB < 4GB, so the pod **will be scheduled** (requests are used for scheduling, not limits). At runtime, if it uses 600Mi, it exceeds its `limits.memory` of 512Mi. Since memory is not compressible, the kernel will **OOMKill** the container (the pod will be terminated/restarted). CPU limits would cause throttling, but memory limits cause termination.

**K8 — Hard:** Full lifecycle:
1. **External LB** (e.g., cloud LB) forwards traffic to the NGINX ingress controller's NodePort or LoadBalancer service.
2. **Ingress controller** (NGINX pod) watches Ingress resources and configures NGINX to route based on host/path. It receives the request and forwards it to the Service's ClusterIP.
3. **Service** (ClusterIP) has a selector matching the app pods. `kube-proxy` watches the Service's Endpoints and programs iptables rules.
4. **Endpoints** object lists the current pod IPs. When a pod changes, Endpoints update.
5. **kube-proxy/iptables**: On the node, iptables DNAT rules translate the Service VIP to a specific pod IP (random selection).
6. **Application pod** receives the request via its container network namespace.

**K9 — Medium:** A **NetworkPolicy** controls traffic between pods, namespaces, and external endpoints at the IP/port level (implemented by CNI plugins like Calico). **Default behavior**: If no NetworkPolicy exists, all traffic is allowed (default-allow). When you apply a NetworkPolicy that selects certain pods, the default for those pods becomes **deny-all** for traffic not explicitly allowed by the policy (ingress and/or egress). Other pods not selected remain fully open.

**K10 — Medium:** **RollingUpdate** gradually replaces old pods with new ones (e.g., maxUnavailable: 25%), ensuring zero downtime. **Recreate** kills all old pods before creating new ones, causing downtime. Choose **Recreate** when: the application requires exclusive access to a resource (e.g., a database migration that can't run concurrently), or when a rolling update would cause incompatible versions to run simultaneously.

**K11 — Easy:** A namespace is a virtual cluster within a physical cluster, used to isolate resources (e.g., dev vs. prod). Default namespaces: `default` (for user workloads), `kube-system` (for system components), `kube-public` (publicly readable), and `kube-node-lease` (for node heartbeats).

**K12 — Easy:** `kubectl describe pod` shows detailed info not in `kubectl get pod`:
1. **Events** (recent lifecycle events like pulling images, probe failures).
2. **Labels/Annotations** and **owner references** (e.g., which ReplicaSet owns it).
3. **Resource limits/requests** and **node placement** (which node it runs on).
4. **Tolerations** and **node selectors**.
5. **Container details** (image, command, env vars, mount paths).

**K13 — Easy:** A **ConfigMap** stores configuration data (key-value pairs) separately from the container image. Pods consume it via:
1. **Environment variables** (e.g., `valueFrom: configMapKeyRef`).
2. **Volume mount** (mounted as files in a directory, e.g., `/etc/config/`).
3. **Command-line arguments** (using `$(VAR)` expansion).

**K14 — Easy:** **ClusterIP**: internal-only virtual IP, accessible only within the cluster. **NodePort**: exposes the service on a static port on every node (e.g., `30000-32767`), accessible externally via `nodeIP:nodePort`. **LoadBalancer**: uses the cloud provider's LB to route external traffic to the NodePort/ClusterIP (essentially a superset of NodePort).

**K15 — Easy:** A **DaemonSet** ensures that a copy of a pod runs on every node (or a subset). Use it for cluster-level agents like `kube-proxy`, log collectors (Fluentd), monitoring agents (Prometheus Node Exporter), or storage daemons (CSI drivers). A Deployment runs a specified number of replicas across the cluster, not necessarily one per node.

**K16 — Medium:** **Taints** are set on nodes to repel pods (e.g., `taint: dedicated=gpu`). **Tolerations** are set on pods to allow them to schedule on tainted nodes (e.g., `tolerations: - key: dedicated, operator: Exists`). **Node affinity** attracts pods to nodes (e.g., `requiredDuringScheduling: nodeSelector: disktype=ssd`). Taints/tolerations are for *exclusion* (dedicated nodes, dedicated GPU nodes), while affinity is for *inclusion* (prefer SSD nodes, co-locate with a cache).

**K17 — Medium:** A **Kubernetes Operator** is a custom controller that extends Kubernetes to manage a specific application (e.g., a database). It uses Custom Resource Definitions (CRDs) to define the desired state (e.g., `Postgres` CR) and continuously reconciles the actual state (e.g., creates/deletes pods, backups, upgrades). A **standard controller** (e.g., Deployment controller) manages built-in resources. The Operator pattern solves the problem of encoding domain-specific operational knowledge (backups, scaling, upgrades) into Kubernetes-native automation.

**K18 — Hard:** etcd uses **Raft consensus**. It requires a **quorum** (majority) of nodes to accept writes (e.g., 2/3 for a 3-node cluster). If quorum is lost (e.g., 2 of 3 nodes are down), the cluster **cannot accept writes** (to prevent split-brain), and reads may also fail (depending on configuration). Recovery: If 2 nodes are permanently lost, you must **restore from a snapshot** on the surviving node (or rebuild the cluster). Steps: stop etcd on the surviving node, restore the snapshot to a new data directory, and start a new single-node etcd cluster, then add new members.

**K19 — Hard:** RBAC uses four objects:
- **Role**: Namespace-scoped permissions (e.g., get pods in `dev`).
- **ClusterRole**: Cluster-wide permissions (e.g., list nodes).
- **RoleBinding**: Binds a Role to a user/SA within a namespace.
- **ClusterRoleBinding**: Binds a ClusterRole cluster-wide.

Manifests for a developer with read-only access to pods and logs in `dev` namespace:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: dev, name: dev-reader }
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: dev, name: dev-reader-binding }
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: dev-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:** Pods default to `ndots: 5` in `/etc/resolv.conf`. For an external domain like `example.com` (1 dot), the resolver tries `example.com.` first (1 query), then `example.com.<namespace>.svc.cluster.local`, `example.com.svc.cluster.local`, `example.com.cluster.local`, and `example.com.<node-domain>` — up to 5 queries before succeeding. This causes >5s delays. Fix: set `dnsConfig` in the pod spec:
```yaml
dnsConfig:
  options:
  - name: ndots
    value: "1"
```
This makes the resolver try `example.com.` directly, avoiding the search domain expansion.

## Development (20 questions)

**D1 — Easy:** **git merge** creates a new merge commit that combines histories, preserving the original branch commits. **git rebase** rewrites the branch's commits to be linear on top of the target branch (re-applies commits). Avoid rebasing when the branch is **shared/public** (e.g., pushed to a remote) because it rewrites history and causes divergence for other developers.

**D2 — Easy:** **TCP** is connection-oriented, reliable, ordered, and provides flow control (e.g., HTTP, FTP, SMTP). **UDP** is connectionless, unreliable, unordered, and low-latency (e.g., DNS, DHCP, VoIP, video streaming).

**D3 — Medium:** A **race condition** occurs when multiple threads/processes access shared data concurrently, and the outcome depends on the timing of execution. Example (Go):
```go
var counter int
func increment() {
    for i := 0; i < 1000; i++ {
        counter++ // Not atomic; read-modify-write race
    }
}
// Run two goroutines; final counter may be < 2000.
```

**D4 — Medium:** **Symmetric encryption** uses the same key for encryption and decryption (e.g., AES). **Asymmetric encryption** uses a public/private key pair (e.g., RSA). In TLS: the client and server use asymmetric encryption to exchange a session key (e.g., ECDHE/RSA), then use symmetric encryption (AES) for the bulk data transfer, providing speed and secure key exchange.

**D5 — Medium:** A **container image layer** is a filesystem change set created by each Dockerfile instruction (e.g., `RUN`, `COPY`). Layers are cached; if a layer is unchanged, it's reused. Best practices: order instructions from least to most frequently changing (e.g., `COPY` package files before `RUN install`), combine `RUN` commands to reduce layers, and use minimal base images to reduce cache invalidation.

**D6 — Medium:** Troubleshooting intermittent HTTP 503 (in order):
1. **Check load balancer health checks** — are backend instances failing?
2. **Check application logs** — look for panics, DB connection errors, or timeouts.
3. **Check backend dependencies** — database, cache, or external API latency/availability.
4. **Check resource exhaustion** — CPU, memory, file descriptors, or connection pool exhaustion.
5. **Check rate limiting / throttling** — is the API being rate-limited by a gateway?

**D7 — Hard:** The **CAP theorem** states a distributed system can only guarantee two of three: Consistency (all nodes see the same data), Availability (every request gets a response), Partition tolerance (system works despite network partitions). **CP system**: etcd or MongoDB (prefers consistency; during a partition, it may reject writes). **AP system**: Cassandra or DynamoDB (prefers availability; during a partition, it accepts writes and reconciles later).

**D8 — Medium:** **Horizontal scaling** adds more machines/nodes (e.g., more pods, more servers). **Vertical scaling** increases resources on existing machines (e.g., more CPU/RAM). Patterns enabling horizontal scaling: stateless services (no session state), load balancing, distributed databases (sharding), microservices architecture, and message queues for decoupling.

**D9 — Easy:** An **environment variable** is a key-value pair in the shell environment. To persist across sessions on Linux, add `export VAR=value` to `~/.bashrc` or `~/.profile` (or use `/etc/environment` for system-wide).

**D10 — Easy:** **JSON** is a strict, text-based data interchange format (no comments, double quotes). **YAML** is a human-readable serialization format that supports comments, indentation-based structure, and is often used for config files. JSON advantage: ubiquitous, easy to parse in any language. YAML advantage: readability and support for comments/anchors.

**D11 — Easy:** A **REST API** uses HTTP methods to perform operations on resources. **GET** retrieves a resource (read-only). **POST** creates a new resource. **PUT** updates/replaces an existing resource (idempotent). **DELETE** removes a resource.

**D12 — Easy:** **Version pinning** means specifying exact versions of dependencies (e.g., `package.json` with `"express": "4.18.2"`). It ensures reproducible builds by preventing unexpected changes from dependency updates, which can introduce breaking changes or security vulnerabilities.

**D13 — Easy:** **Compiled languages** are translated to machine code ahead of time (e.g., C, Go, Rust). **Interpreted languages** are executed line-by-line by an interpreter at runtime (e.g., Python, JavaScript, Ruby).

**D14 — Medium:** A **reverse proxy** sits in front of backend servers and forwards client requests to them (e.g., Nginx, HAProxy). A **forward proxy** sits in front of clients and forwards their requests to the internet (e.g., corporate proxy). Use cases: Nginx for load balancing and caching; HAProxy for TCP/HTTP load balancing and high availability.

**D15 — Medium:** A **deadlock** is when two or more threads wait indefinitely for each other's resources. The four Coffman conditions: (1) **Mutual exclusion** (resource is non-shareable), (2) **Hold and wait** (thread holds a resource while waiting for another), (3) **No preemption** (resources cannot be forcibly taken), (4) **Circular wait** (a cycle of threads waiting for each other).

**D16 — Hard:** **Eventual consistency** means that if no new updates occur, all replicas will eventually converge to the same value. Distributed databases like Cassandra handle read-after-write consistency via **tunable consistency levels**: `ONE` (fastest, may read stale), `QUORUM` (majority of replicas, ensures read-after-write if write also used QUORUM), `ALL` (strongest, slowest). For read-after-write, use `QUORUM` for both reads and writes.

**D17 — Hard:** **mTLS** (mutual TLS) requires both client and server to authenticate each other with certificates. Handshake: Client sends `ClientHello` → Server sends `ServerHello` + its certificate → Client verifies server cert → Client sends its own certificate → Server verifies client cert → Key exchange (e.g., ECDHE) → Symmetric keys established → Encrypted application data. mTLS is used in service meshes (Istio), zero-trust networks, and internal service-to-service communication.

**D18 — Hard:** A **hash table** uses a hash function to map keys to an array index (bucket). **Collision resolution**: **Chaining** stores multiple entries in a linked list per bucket; **Open addressing** probes the next available slot (e.g., linear probing). Time complexity: Average O(1) for insertion, lookup, deletion; Worst case O(n) when many collisions occur (e.g., all keys hash to the same bucket).

**D19 — Hard:** The **circuit breaker pattern** prevents cascading failures by stopping calls to a failing service. States: **Closed** (normal, requests pass), **Open** (failures exceed threshold, requests fail fast without hitting the service), **Half-open** (after a cooldown, a few trial requests are allowed; if they succeed, the circuit closes). It relates to retry policies: retries with exponential backoff are used in the closed state, but when the circuit is open, retries are stopped to avoid overwhelming the failing service.

**D20 — Hard:** **Optimistic concurrency control** assumes conflicts are rare; it uses a version number or timestamp to check if a record changed before committing (e.g., `UPDATE ... SET version = version + 1 WHERE version = ?`). **Pessimistic concurrency control** locks resources to prevent conflicts (e.g., `SELECT FOR UPDATE`). Choose optimistic for low contention (e.g., web apps with few writes), pessimistic for high contention or critical data (e.g., inventory management, financial transactions).
