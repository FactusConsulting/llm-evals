## Networking (20 questions)

### N1 — Easy: Layer 2 vs Layer 3 switch
A **Layer 2 switch** operates at the Data Link layer (OSI Layer 2). It forwards frames based on MAC addresses, learns MAC-to-port mappings from incoming frames, and does not inspect IP addresses. It provides VLAN segmentation and is limited to the same broadcast domain.

A **Layer 3 switch** operates at the Network layer (OSI Layer 3). It can route packets between subnets/VLANs based on IP addresses, using routing protocols (static routes, OSPF, etc.). It combines switching hardware with routing functionality, often implemented in hardware (ASICs) for high throughput.

**Key difference:** L2 switches forward by MAC; L3 switches route by IP. L3 switches are used for inter-VLAN routing and can replace traditional routers in many campus/data-center designs.

---

### N2 — Easy: Network/broadcast for 10.0.5.37/20
- **/20** → subnet mask `255.255.240.0` (20 network bits, 12 host bits).
- Convert 10.0.5.37 to binary: `00001010.00000000.00000101.00100101`.
- Network bits (first 20): `00001010.00000000.00000101.0010` → the last 4 bits of the third octet are host bits.
- **Network address:** 10.0.0.0 (all host bits zero).
- **Broadcast address:** 10.0.15.255 (all host bits one: 10.0.0.0 + 0.0.15.255).

### N3 — Medium: TCP three-way handshake and lost ACK
1. **SYN:** Client sends a SYN packet with an initial sequence number (ISN) to the server.
2. **SYN-ACK:** Server responds with SYN-ACK, acknowledging the client's ISN and sending its own ISN.
3. **ACK:** Client sends an ACK acknowledging the server's ISN. The connection is established.

**If the final ACK is lost:**
- The server has already established the connection (it received SYN and sent SYN-ACK), but the client hasn't confirmed.
- The server will retransmit the SYN-ACK (per TCP retransmission timers) until it receives the ACK or times out.
- The client, upon receiving the duplicate SYN-ACK, will resend the ACK.
- If the ACK is never received, the server eventually times out and closes the connection (no connection established from the server's perspective).

### N4 — Medium: SNAT vs DNAT
**SNAT (Source NAT):** Changes the source IP address of outgoing packets. Used for outbound traffic (e.g., internal hosts accessing the internet). The NAT gateway replaces the private source IP with a public IP.

**DNAT (Destination NAT):** Changes the destination IP address of incoming packets. Used for inbound traffic (e.g., port forwarding to an internal server). The NAT gateway replaces the public destination IP with a private internal IP.

**Examples:**
- **SNAT:** Internal host `192.168.1.10` sends a packet to `8.8.8.8`. The NAT gateway changes the source to `203.0.113.5` (public IP). Replies come back to the gateway, which reverses the mapping.
- **DNAT:** External host sends a packet to `203.0.113.5:80`. The NAT gateway changes the destination to `192.168.1.10:80` (internal web server).

### N5 — Medium: SSL certificate name mismatch — 3 causes
1. **Wrong domain in certificate:** The certificate was issued for `example.org` but the URL is `example.com`.
2. **Wildcard doesn't cover the hostname:** The certificate is `*.example.com` but the URL is `example.com` (wildcard doesn't match the bare domain) or `sub.example.com` (wildcard only matches one level).
3. **IP address or alias not in SAN:** The URL uses an IP address (e.g., `https://203.0.113.5`) or an alias (e.g., `https://myapp.internal`) that isn't listed in the certificate's Subject Alternative Name (SAN) field.

### N6 — Medium: VLAN vs VxLAN
**VLAN (802.1Q):**
- Layer 2 segmentation within a single broadcast domain.
- 12-bit VLAN ID → up to 4096 VLANs.
- Limited to a single physical network (or extended via trunking, but still bounded by Layer 2 reachability).
- Typically used within a single data center or campus.

**VxLAN (RFC 7348):**
- Layer 2 overlay over Layer 3 (UDP encapsulation, port 4789).
- 24-bit VNI → up to 16 million segments.
- Extends Layer 2 across Layer 3 networks (e.g., multi-data-center, cloud).
- Uses MAC-in-UDP encapsulation, allowing virtual networks to span physical boundaries.

**Choose VxLAN over VLAN when:**
- You need more than 4096 segments (multi-tenant cloud).
- You need Layer 2 extension across data centers or cloud regions.
- You need to leverage IP routing/ECMP for load balancing and redundancy.

### N7 — Hard: Asymmetric routing with two NICs
**Problem:** The host has:
- eth0: `10.0.0.5/24`, default gateway `10.0.0.1`
- eth1: `192.168.1.5/24`

Traffic arrives on eth1 from `192.168.1.0/24`. The host replies via eth0 because the **default route** points to `10.0.0.1` (eth0's gateway). The kernel uses the destination IP of the reply (e.g., `192.168.1.10`) and looks up the routing table; since there's no specific route for `192.168.1.0/24` via eth1 (only the default route), it sends the reply via eth0.

**Fix with policy-based routing:**
```bash
# Create a custom routing table (e.g., table 100)
ip rule add from 192.168.1.0/24 table 100

# Add routes to table 100
ip route add 192.168.1.0/24 dev eth1 table 100
ip route add default via 192.168.1.1 table 100   # if eth1 has a gateway

# Ensure the rule is applied before the main table
ip rule add from 192.168.1.0/24 table 100 priority 100
```
This forces traffic originating from `192.168.1.0/24` (i.e., received on eth1) to use eth1's routing table, ensuring symmetric routing.

### N8 — Hard: BGP path selection (in order of preference)
1. **Highest weight** (Cisco-specific, local to router).
2. **Highest local preference** (local to AS, used for outbound traffic).
3. **Prefer locally originated routes** (e.g., routes injected via `network` or `aggregate`).
4. **Shortest AS path** (fewest AS hops).
5. **Lowest origin type** (IGP < EGP < incomplete).
6. **Lowest MED** (multi-exit discriminator, used for inbound traffic).
7. **Prefer eBGP over iBGP** (external routes preferred over internal).
8. **Lowest IGP metric to next hop** (closest next hop).
9. **Longest match** (most specific prefix).
10. **Lowest router ID** (tie-breaker).

### N9 — Hard: MTU math for VxLAN over IPsec
- **Physical MTU:** 1500 bytes.
- **IPsec overhead:** ~50–60 bytes (ESP header 8 + IV 16 + padding ~2–258 + ESP trailer 2 + ICV 16). Assume **50 bytes** for a typical AES-GCM setup.
- **VxLAN overhead:** 50 bytes (outer Ethernet 14 + outer IP 20 + outer UDP 8 + VXLAN header 8).

**Total overhead:** 50 (IPsec) + 50 (VxLAN) = **100 bytes**.

**Maximum inner payload (inner IP packet):** 1500 − 100 = **1400 bytes**.

If the inner packet is TCP, the TCP payload is further reduced by the inner IP header (20) + TCP header (20) = 1360 bytes max TCP payload.

### N10 — Medium: ARP and Gratuitous ARP
**ARP (Address Resolution Protocol):** Resolves IP addresses to MAC addresses on a local network. A host broadcasts an ARP request ("Who has 10.0.0.1?") and the owner replies with its MAC address.

**Gratuitous ARP:** An ARP announcement sent proactively (without being prompted by a request). It solves:
- **Duplicate IP detection:** A host announces its IP to check if another host already uses it.
- **MAC address changes:** When a NIC's MAC changes (e.g., VM migration, failover), the host sends a gratuitous ARP to update other hosts' ARP caches.
- **Announcing a new IP:** When a host takes over an IP (e.g., in HA clusters), it announces the IP to update the network.

---

### N11 — Easy: Public vs Private IP
- **Public IP:** Globally routable on the internet, assigned by IANA/RIRs (ARIN, RIPE, APNIC, etc.).
- **Private IP:** Not routable on the internet, used internally within private networks. Must be translated by NAT to access the internet.

**RFC 1918 private ranges:**
- `10.0.0.0/8` (10.0.0.0 – 10.255.255.255)
- `172.16.0.0/12` (172.16.0.0 – 172.31.255.255)
- `192.168.0.0/16` (192.168.0.0 – 192.168.255.255)

---

### N12 — Easy: DNS, A, CNAME, AAAA
**DNS (Domain Name System):** Translates human-readable domain names (e.g., `example.com`) into IP addresses.

- **A record:** Maps a domain to an IPv4 address (e.g., `example.com → 93.184.216.34`).
- **AAAA record:** Maps a domain to an IPv6 address (e.g., `example.com → 2606:2800:220:1:248:1893:25c8:1946`).
- **CNAME record:** Alias that points one domain to another (canonical name). E.g., `www.example.com → example.com`. The target must be an A/AAAA record, not another CNAME.

---

### N13 — Easy: DHCP and DORA
**DHCP (Dynamic Host Configuration Protocol):** Automatically assigns IP addresses, subnet masks, gateways, DNS servers, and other network parameters to clients.

**DORA process:**
1. **Discover:** Client broadcasts `DHCPDISCOVER` to find available DHCP servers.
2. **Offer:** Server responds with `DHCPOFFER` (proposed IP, lease time, etc.).
3. **Request:** Client broadcasts `DHCPREQUEST` to accept the offer.
4. **Acknowledge:** Server sends `DHCPACK` confirming the lease.

---

### N14 — Easy: Hub, Switch, Router
- **Hub:** Operates at **Layer 1 (Physical)**. It broadcasts all incoming data to all ports. No intelligence; all devices share the same collision domain.
- **Switch:** Operates at **Layer 2 (Data Link)**. It forwards frames based on MAC addresses, learning MAC-to-port mappings. Provides dedicated bandwidth per port.
- **Router:** Operates at **Layer 3 (Network)**. It routes packets based on IP addresses, connecting different networks/subnets.

---

### N15 — Easy: Half-duplex vs Full-duplex
- **Half-duplex:** Communication in one direction at a time (e.g., walkie-talkie). A device can send or receive, but not simultaneously.
- **Full-duplex:** Simultaneous communication in both directions (e.g., telephone). A device can send and receive at the same time.

**Modern Ethernet** uses **full-duplex** (e.g., 100BASE-TX, 1000BASE-T) with dedicated transmit/receive pairs. Half-duplex is only used in legacy hubs or when auto-negotiation fails.

---

### N16 — Medium: TTL and traceroute
**TTL (Time to Live):** An 8-bit field in the IP header (IPv4) that limits how many hops a packet can traverse. Each router decrements TTL by 1; when TTL reaches 0, the router discards the packet and sends an ICMP Time Exceeded message back to the source. This prevents packets from looping indefinitely.

**Traceroute exploits TTL:**
- Sends packets with TTL=1 → the first router drops it and sends ICMP Time Exceeded (revealing hop 1).
- Sends packets with TTL=2 → the second router drops it (revealing hop 2).
- Continues incrementing TTL until the destination is reached or a max hop count is hit.
- Each ICMP reply reveals the IP address of each hop, mapping the network path.

---

### N17 — Medium: NAT gateway and NAT types
**NAT gateway:** A device (router/firewall) that translates private IP addresses to public IP addresses for internet access. It maintains a translation table to map connections.

- **Static NAT:** One-to-one mapping between a private IP and a public IP. Used for servers that need a fixed public address (e.g., a web server).
- **Dynamic NAT:** Maps a private IP to one of a pool of public IPs. The mapping is temporary and changes over time.
- **PAT (Port Address Translation):** Many-to-one mapping. Multiple private IPs share a single public IP, distinguished by different source ports. This is the most common form (e.g., home routers).

---

### N18 — Hard: ECMP and hashing
**ECMP (Equal-Cost Multi-Path):** Routing technique where traffic is distributed across multiple equal-cost paths to the same destination. Used in data centers and service provider networks for load balancing and redundancy.

**Hashing strategies:**
- **5-tuple hash:** Source IP, destination IP, source port, destination port, protocol. Provides per-flow load balancing.
- **3-tuple hash:** Source IP, destination IP, protocol (less granular).
- **2-tuple hash:** Source IP, destination IP (coarse, may cause collisions).

**Problems with asymmetric flows:**
- Stateful firewalls track connection state (e.g., NAT, session state). If packets of the same flow take different paths (asymmetric routing), the firewall may see only one direction and drop the other.
- **Solution:** Use consistent hashing (e.g., hash on 5-tuple) to ensure all packets of a flow take the same path, or use symmetric routing (all traffic for a flow goes through the same firewall).

---

### N19 — Hard: TCP window scaling
**Problem:** The TCP receive window is advertised in the TCP header as a 16-bit field, limiting it to 65,535 bytes (64KB). If the bandwidth-delay product (BDP) is 10MB (e.g., 1 Gbps link with 80ms RTT), the sender can only transmit 64KB before waiting for an ACK, severely limiting throughput.

**Solution — TCP window scaling (RFC 1323):**
- Adds a **window scale factor** (up to 14 bits) negotiated during the three-way handshake.
- The effective window size becomes `window_size << scale_factor` (up to 1GB).
- This allows the sender to fill the pipe by sending up to the BDP worth of data before needing an ACK.

**Example:** With a scale factor of 8, a window of 64KB becomes 64KB × 256 = 16MB, covering the 10MB BDP.

---

### N20 — Hard: 802.1Q trunk ports and Linux sub-interfaces
**802.1Q trunk ports:** A single physical link carries multiple VLANs. Each frame is tagged with a 4-byte 802.1Q header inserted after the source MAC address:
- **TPID** (0x8100) — indicates the frame is VLAN-tagged.
- **TCI** (Tag Control Information) — 3 bits priority, 1 bit CFI/DEI, 12 bits VLAN ID.

**Linux configuration for VLANs 10, 20, 30 on a single NIC (eth0):**
```bash
# Create VLAN sub-interfaces
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip link add link eth0 name eth0.30 type vlan id 30

# Bring them up and assign IPs
ip link set eth0.10 up
ip link set eth0.20 up
ip link set eth0.30 up
ip addr add 10.0.10.5/24 dev eth0.10
ip addr add 10.0.20.5/24 dev eth0.20
ip addr add 10.0.30.5/24 dev eth0.30
```
**Frame format on the wire:**
```
[Ethernet Header (14B)] [802.1Q Tag (4B)] [Ethertype (2B)] [IP Payload] [FCS (4B)]
```
The 802.1Q tag contains the VLAN ID (e.g., 10, 20, 30), allowing the switch to forward the frame to the correct VLAN.

## Linux (20 questions)

### L1 — Easy: Hard link vs symbolic link
- **Hard link:** A direct pointer to the same inode. It has the same inode number as the original file. Cannot span filesystems, cannot link directories. Deleting the original file does not break the hard link (the link still points to the inode).
- **Symbolic link (symlink):** A separate file that contains the path to the target. Can span filesystems, can link directories. Deleting the original file breaks the symlink (it becomes a dangling link).

---

### L2 — Easy: Find files larger than 100MB under /var/log
```bash
find /var/log -type f -size +100M
```
- `-type f` limits to files (not directories).
- `-size +100M` matches files larger than 100MB.

---

### L3 — Medium: Process in D state (uninterruptible sleep)
- **D state** means the process is in **uninterruptible sleep**, typically blocked on I/O (e.g., disk, NFS, kernel driver). The process cannot be interrupted by signals until the I/O completes.
- **Can you kill it with `kill -9`?** No. `kill -9` sends SIGKILL, but the kernel cannot deliver the signal until the process leaves the D state. The process is stuck in a kernel I/O wait. You must wait for the I/O to complete or reboot the system.

---

### L4 — Medium: cgroups v1 vs v2
- **cgroups v1:** Multiple hierarchies, each controller (CPU, memory, I/O) has its own tree. Complex to manage, inconsistent behavior, and limited delegation.
- **cgroups v2:** Unified hierarchy, all controllers in a single tree. Simpler, more consistent, supports delegation to unprivileged processes, and has better resource control (e.g., `io` controller).

**systemd prefers cgroups v2** because it provides a cleaner, unified API, supports delegation (e.g., to containers), and is the modern standard. systemd uses cgroups v2 by default on most modern distros (e.g., RHEL 8+, Ubuntu 20.04+).

---

### L5 — Medium: nftables vs iptables
- **nftables:** Modern replacement for iptables. Uses a single framework (`nf_tables`) with a simpler, more expressive syntax. Supports sets, maps, and concatenations. Better performance and easier to manage.
- **iptables:** Legacy framework (`ip_tables`). Uses separate tables (filter, nat, mangle) and chains. Complex and limited.

**Kernel handling:** Both can coexist in the kernel, but they use different frameworks (`nf_tables` vs `ip_tables`). You cannot use both for the same hook simultaneously (e.g., you can't have both nftables and iptables rules in the `INPUT` chain). You must choose one or migrate from iptables to nftables.

---

### L6 — Medium: df shows 100% but du totals less
**Most likely cause:** Deleted files still held open by processes. When a file is deleted but a process still has it open, the space is not released until the process closes the file. `df` shows the filesystem as full, but `du` doesn't see the deleted files.

**Diagnose:**
```bash
lsof +L1 /var/log   # List files with deleted links
lsof | grep deleted
```
The fix is to restart the process holding the file open.

---

### L7 — Hard: Linux boot process
1. **UEFI firmware:** Initializes hardware (CPU, RAM, storage), reads EFI variables, and loads the bootloader (e.g., GRUB) from the EFI System Partition (ESP).
2. **Bootloader (GRUB):** Loads the kernel (`vmlinuz`) and initramfs (`initrd`) into memory. GRUB may also load a configuration file (`grub.cfg`) and support booting multiple kernels.
3. **Kernel:** Decompresses itself, initializes hardware (via drivers), and mounts the initramfs as a temporary root filesystem.
4. **Initramfs:** Contains essential drivers and tools needed to mount the real root filesystem (e.g., storage drivers, LVM, encryption). The kernel runs `/init` from the initramfs.
5. **Root filesystem:** The initramfs mounts the real root filesystem (e.g., `/dev/sda2`) read-only, then remounts it read-write.
6. **systemd:** PID 1, the init system. It reads `/etc/systemd/system/default.target` (e.g., `multi-user.target` or `graphical.target`) and starts all required services (network, sshd, etc.).

---

### L8 — Hard: OOM killer with high buff/cache
**Why available can be low even with high buff/cache:**
- `available` = `free` + reclaimable `buff/cache`. If the cache is mostly **dirty pages** (not yet written to disk) or **pinned** (e.g., used by the kernel or active files), it cannot be reclaimed quickly.
- The OOM killer fires when the kernel determines there is insufficient **available** memory (not just free). If reclaimable cache is low or the kernel can't reclaim it fast enough, the OOM killer activates.

**Kernel tunables:**
- `vm.swappiness` — controls how aggressively the kernel swaps anonymous pages.
- `vm.min_free_kbytes` — reserves memory for the kernel.
- `vm.vfs_cache_pressure` — controls how aggressively the kernel reclaims inode/dentry caches.
- `vm.dirty_ratio` / `vm.dirty_background_ratio` — controls dirty page thresholds.

---

### L9 — Medium: `ip netns`
- `ip netns` creates and manages **network namespaces**, which provide isolated network stacks (interfaces, routing tables, firewall rules, etc.).
- **Used by container runtimes** (Docker, Podman, LXC) to give each container its own network namespace. The runtime creates a namespace, creates a virtual Ethernet pair (`veth`), and attaches one end to the container and the other to the host's bridge.

**Example:**
```bash
ip netns add ns1
ip netns exec ns1 ip link set lo up
ip link add veth0 type veth peer name veth1
ip link set veth1 netns ns1
```

---

### L10 — Medium: SIGTERM, SIGKILL, SIGQUIT
- **SIGTERM (15):** Graceful termination. The process can catch it, clean up, and exit. Used by `kill` by default.
- **SIGKILL (9):** Immediate termination. Cannot be caught, ignored, or handled. The kernel forcibly kills the process.
- **SIGQUIT (3):** Similar to SIGTERM but also generates a **core dump**. Can be caught and handled (e.g., to dump state).

**Which can be caught?** SIGTERM and SIGQUIT can be caught/handled. SIGKILL cannot be caught.

---

### L11 — Easy: stdout, stderr, stdin
- **stdin (0):** Standard input — data read by the program (e.g., keyboard input).
- **stdout (1):** Standard output — normal output from the program.
- **stderr (2):** Standard error — error messages and diagnostics.

**Redirect stderr to a file while displaying stdout on the terminal:**
```bash
command 2>error.log
```
- `2>` redirects stderr to `error.log`.
- stdout remains on the terminal.

### L12 — Easy: chmod 755
- `chmod 755` sets permissions: **7** (owner), **5** (group), **5** (others).
- **7 = rwx** (read, write, execute) — owner.
- **5 = r-x** (read, execute) — group.
- **5 = r-x** (read, execute) — others.

This is a common permission for executables and directories (e.g., `/usr/bin`).

---

### L13 — Easy: Root vs sudo
- **Root user:** The superuser with UID 0. Has unrestricted access to all system resources, files, and commands.
- **User with sudo privileges:** A regular user (e.g., UID 1000) who can run specific commands as root (or another user) via `sudo`. The user is still limited by the system's security policies (e.g., can't read other users' files unless granted via sudo).

**Key difference:** Root has full access; sudo users have limited, audited, and configurable access.

### L14 — Easy: Package manager
- **Package manager:** A tool for installing, updating, removing, and managing software packages (e.g., binaries, libraries, dependencies).
- **Debian/Ubuntu:** `apt` (or `apt-get`).
- **RHEL/Fedora:** `dnf` (or `yum` on older RHEL).

---

### L15 — Easy: /etc/fstab
- **`/etc/fstab`** (file system table) defines how filesystems are mounted at boot. Each entry specifies: device, mount point, filesystem type, options, dump, and fsck order.
- **If an entry is misconfigured:** The system may fail to boot (e.g., wrong device, invalid mount point), or the filesystem may not mount, or it may mount with wrong options (e.g., read-only instead of read-write). A misconfigured entry can cause a boot hang or a maintenance mode prompt.

### L16 — Medium: LVM
**LVM (Logical Volume Manager):** Provides flexible storage management by abstracting physical storage into logical volumes.

- **Physical Volume (PV):** A disk or partition (e.g., `/dev/sda1`) initialized for LVM.
- **Volume Group (VG):** A pool of PVs combined into a single storage pool.
- **Logical Volume (LV):** A virtual partition carved from a VG, used as a filesystem (e.g., `/dev/vg0/lv_home`).

**Extend a logical volume on a running system:**
```bash
# Extend the LV by 10GB
lvextend -L +10G /dev/vg0/lv_home

# Resize the filesystem (ext4)
resize2fs /dev/vg0/lv_home
```
For XFS: `xfs_growfs /dev/vg0/lv_home`.

---

### L17 — Hard: I/O schedulers
The Linux kernel's I/O scheduler decides the order of block device requests.

- **mq-deadline:** Guarantees a deadline for each request (read/write). Prevents starvation and ensures fairness. Good for SSDs and general-purpose workloads.
- **bfq (Budget Fair Queuing):** Provides per-process fairness and low latency. Good for interactive workloads (e.g., desktop, multimedia).
- **none:** No scheduling. The device (e.g., NVMe SSD) handles its own scheduling. Best for high-performance NVMe SSDs with many parallel queues.

**Change scheduler at runtime:**
```bash
echo bfq > /sys/block/sda/queue/scheduler
```
Verify with `cat /sys/block/sda/queue/scheduler`.

---

### L18 — Hard: High load average, low CPU
**Load average** measures the number of processes in the run queue plus processes in **uninterruptible sleep** (D state). I/O wait (e.g., disk, network) can inflate load average because processes blocked on I/O are counted.

**Diagnosis:**
- **CPU:** Check `top` or `mpstat` for `%us`, `%sy`, `%wa`. Low CPU usage suggests the bottleneck is not CPU.
- **Disk:** Use `iostat -x 1` to check `%util`, `await`, `svctm`. High `%util` or high `await` indicates disk I/O bottleneck.
- **Network:** Use `sar -n DEV 1` or `nload` to check network throughput. High packet drops or high utilization indicates network bottleneck.

**Conclusion:** If CPU is low but load is high, the bottleneck is likely I/O (disk or network). Use `vmstat 1` to see `r` (run queue) and `b` (blocked processes) columns.

---

### L19 — Hard: SELinux
**SELinux (Security-Enhanced Linux):** Enforces **Mandatory Access Control (MAC)**. Every process and file has a security context (e.g., `httpd_t`, `httpd_exec_t`). The kernel enforces policy rules that define which contexts can access which resources.

**Modes:**
- **Enforcing:** Policies are enforced; violations are denied and logged.
- **Permissive:** Policies are not enforced; violations are logged (for troubleshooting).
- **Disabled:** SELinux is turned off entirely.

**Troubleshoot a daemon failing to bind a non-standard port:**
1. Check the audit log: `grep -i denied /var/log/audit/audit.log`.
2. Use `ausearch -m avc -ts recent` to find recent denials.
3. Use `sealert -l <alert_id>` to get a human-readable explanation.
4. Adjust the policy: `semanage port -a -t http_port_t -p tcp 8080` (for a web server on port 8080).
5. Or set the daemon's context: `semanage fcontext -a -t httpd_t /path/to/daemon`.

---

### L20 — Hard: Page faults and THP
**Page faults:** When a process accesses memory that isn't in physical RAM, the kernel triggers a page fault.

- **Minor fault:** The page is already in memory (e.g., shared library, zeroed page) but not mapped into the process's address space. The kernel only updates the page table.
- **Major fault:** The page must be read from disk (e.g., swap, file-backed memory). This is slow and causes I/O.

**Transparent Huge Pages (THP):**
- Uses 2MB pages instead of 4KB pages, reducing TLB misses and improving performance for large memory workloads.
- **Effect on performance:** Can improve throughput for memory-intensive applications (e.g., databases, HPC). However, it can cause latency issues due to memory compaction (copying pages to make contiguous 2MB regions) and increased memory usage.

**When to disable THP:**
- For latency-sensitive applications (e.g., databases like MongoDB, Redis) where THP causes unpredictable latency spikes.
- When memory fragmentation is high, or the application has high allocation/deallocation churn.
- Disable with: `echo never > /sys/kernel/mm/transparent_hugepage/enabled` or via kernel boot parameter `transparent_hugepage=never`.
