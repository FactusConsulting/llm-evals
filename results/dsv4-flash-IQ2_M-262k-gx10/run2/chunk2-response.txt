## Kubernetes

**K1 — Easy:**  
A **Deployment** manages stateless applications: pods are interchangeable, have random names, and share ephemeral or PVC-backed storage without stable identity. A **StatefulSet** manages stateful applications: each pod has a stable ordinal identity (e.g., `web-0`), stable network DNS, and stable persistent storage (each pod gets its own PVC). StatefulSets also provide ordered deployment, scaling, and termination.

**K2 — Easy:**  
A ClusterIP Service uses a label selector to find matching pods and creates an Endpoints object listing their IPs. `kube-proxy` on each node watches the Service/Endpoints and programs iptables/IPVS rules. Traffic sent to the Service’s virtual IP is DNAT’d to one of the endpoint pod IPs, with load balancing (e.g., random or round-robin). Session affinity can pin a client to a specific pod.

**K3 — Medium:**  
- **PersistentVolume (PV)** is cluster-level storage provisioned by an admin or dynamically.  
- **PersistentVolumeClaim (PVC)** is a user request for storage; it binds to a PV that satisfies its size/access-mode requirements.  
- **StorageClass** defines a provisioner and parameters for dynamically creating PVs when a PVC requests it.  
Relationship: PVC → StorageClass → dynamically created PV → PVC binds → pod uses PVC as a volume.

**K4 — Medium:**  
Troubleshooting `CrashLoopBackOff`:
1. `kubectl describe pod` – check events, container status, exit codes, and probe failures.  
2. `kubectl logs <pod> --previous` – inspect last container logs for application errors.  
3. Check resource limits – if `OOMKilled`, increase memory or adjust requests/limits.  
4. Verify liveness/readiness probes – failing probes cause restarts.  
5. Validate ConfigMaps/Secrets – missing mounts or env vars cause startup failure.  
6. Check security context/permissions – e.g., running as non-root without required capabilities.  
7. Test dependencies (database, external service) – connection failures can crash the app.  
8. Inspect node resources – insufficient CPU/memory may prevent container startup.

**K5 — Medium:**  
CoreDNS is the cluster’s DNS server. It watches Kubernetes Services and Pods and answers DNS queries for cluster names (e.g., `service.namespace.svc.cluster.local`). It also forwards external DNS queries to upstream servers. If CoreDNS pods are down, all DNS resolution inside the cluster fails (unless pods have cached entries), breaking service discovery and external name resolution.

**K6 — Hard:**  
The Kubernetes scheduler uses a two-phase process:
- **Filtering (predicates):** removes nodes that cannot run the pod. Factors include: insufficient resources (CPU/memory requests), node affinity/anti-affinity, taints/tolerations, node selector, pod anti-affinity, volume zone conflicts, and node conditions (e.g., disk pressure).
- **Scoring (priorities):** ranks remaining nodes. Factors include: least requested resources (spread), balanced resource usage, affinity matching, topology spread, and node age.  
Specific factors considered: CPU/memory requests, pod affinity, node affinity, taints, local storage, and inter-pod anti-affinity.

**K7 — Hard:**  
Node has 4GB RAM, 3.5GB already requested → 0.5GB available. Pod requests 256Mi (0.25GB), which fits, so it **will be scheduled**. At runtime, if it uses 600Mi, it exceeds its 512Mi limit. The kernel OOM killer will terminate the container (or the process) because memory limits are enforced via cgroups; it cannot exceed the limit.

**K8 — Hard:**  
1. External LB (cloud) forwards traffic to the NGINX Ingress controller’s Service (NodePort or LoadBalancer).  
2. The Ingress controller pod receives the request and matches the Ingress rules (host/path) to a backend Service.  
3. It resolves the Service’s Endpoints (pod IPs) via the Kubernetes API and updates its NGINX config.  
4. The controller forwards the request directly to a pod IP (or via the Service ClusterIP).  
5. If via ClusterIP, `kube-proxy` programs iptables rules that DNAT to the endpoint pod IP.  
6. The application pod processes the request and returns the response through the same chain.

**K9 — Medium:**  
A **NetworkPolicy** defines allowed ingress/egress traffic to/from pods using label selectors, IP blocks, and ports. If no NetworkPolicy exists, **all traffic is allowed** (no isolation). When you apply a NetworkPolicy that selects certain pods, those pods become isolated: any traffic not explicitly allowed is denied. Policies are additive; multiple policies combine.

**K10 — Medium:**  
- **RollingUpdate:** gradually replaces old pods with new ones, keeping the service available; supports zero-downtime deployments and rollback.  
- **Recreate:** terminates all old pods before creating new ones, causing downtime.  
Choose **Recreate** when you cannot have two versions running simultaneously (e.g., a database schema change that is backward-incompatible) or for single-replica applications where availability is not critical.

**K11 — Easy:**  
A namespace is a virtual partition of a Kubernetes cluster used to isolate resources (objects, permissions, quotas). Default namespaces in a new cluster: `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

**K12 — Easy:**  
`kubectl describe pod` shows detailed information not shown by `kubectl get pod`, including:
- Recent events (e.g., scheduling, pulling images, probe failures).  
- Labels, annotations, and owner references.  
- Container status, image, command, and resource limits/requests.  
- Volume mounts, tolerations, node assignment, and pod IP.

**K13 — Easy:**  
A **ConfigMap** stores configuration data as key-value pairs. Pods consume it via:
1. **Environment variables** – `valueFrom.configMapKeyRef` injects a key as an env var.  
2. **Volume mount** – a `configMap` volume mounts files into the container filesystem.  
3. Command-line arguments or config files read from the mounted volume.

**K14 — Easy:**  
- **ClusterIP:** internal virtual IP, only accessible within the cluster.  
- **NodePort:** exposes the Service on a static port on every node, allowing external access via `nodeIP:nodePort`.  
- **LoadBalancer:** provisions an external cloud load balancer and routes traffic to the NodePort/ClusterIP.

**K15 — Easy:**  
A **DaemonSet** ensures a copy of a pod runs on every node (or a subset). Use it for cluster-level agents like logging (Fluentd), monitoring (Prometheus node exporter), or networking (kube-proxy). A **Deployment** runs multiple replicas across nodes for stateless services; DaemonSets are for node-specific infrastructure.

**K16 — Medium:**  
- **Taints** are applied to nodes to repel pods unless they have matching **tolerations**. They are a “do not schedule unless tolerated” mechanism.  
- **Node affinity** attracts pods to nodes based on labels (e.g., “prefer SSD nodes”).  
Use cases: taints for dedicated nodes (e.g., GPU-only nodes), affinity for co-locating services or placing workloads on specific hardware.

**K17 — Medium:**  
A **Kubernetes Operator** is a pattern that extends Kubernetes with custom controllers and Custom Resource Definitions (CRDs) to automate the lifecycle of a specific application (e.g., backups, upgrades, scaling). A standard controller watches built-in resources and reconciles state; an Operator encodes domain-specific operational knowledge (e.g., handling a database’s failover) into code, solving the problem of managing complex stateful applications.

**K18 — Hard:**  
etcd uses the **Raft consensus algorithm**, requiring a majority quorum (e.g., 2 of 3 nodes) for writes. If quorum is lost, the cluster cannot accept writes or maintain consistency; reads may return stale data or fail. If 2 of 3 etcd nodes are permanently lost, the remaining node cannot elect a leader. Recovery requires restoring from a **snapshot** to a new etcd cluster, or (as a last resort) starting the remaining node with `--force-new-cluster` to form a single-node cluster, then adding new members.

**K19 — Hard:**  
RBAC uses four objects:
- **Role:** permissions within a namespace.  
- **ClusterRole:** permissions cluster-wide (or across namespaces).  
- **RoleBinding:** binds a Role/ClusterRole to users/groups/ServiceAccounts within a namespace.  
- **ClusterRoleBinding:** binds a ClusterRole cluster-wide.  
For a developer with read-only access to pods and logs in namespace `dev`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: dev-pod-reader
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:**  
`ndots:5` in `/etc/resolv.conf` means the resolver tries to resolve a name as a fully-qualified domain name (FQDN) only if it contains at least 5 dots; otherwise, it appends search domains (e.g., `namespace.svc.cluster.local`). For an external domain like `example.com` (1 dot), the resolver tries `example.com.namespace.svc.cluster.local`, then `example.com.svc.cluster.local`, etc., causing multiple DNS queries and delays. Fix by setting `dnsConfig` in the pod spec:

```yaml
dnsConfig:
  options:
    - name: ndots
      value: "1"
```

This reduces search-domain attempts for external names.

## Development

**D1 — Easy:**  
`git merge` combines branches by creating a merge commit, preserving history. `git rebase` rewrites commits to create a linear history by replaying one branch’s commits onto another. Avoid rebasing shared/public branches because it rewrites history and can cause conflicts for other developers.

**D2 — Easy:**  
TCP is reliable, ordered, connection-oriented, and provides flow control; UDP is unreliable, connectionless, and faster. TCP protocols: HTTP, FTP. UDP protocols: DNS, DHCP, video streaming.

**D3 — Medium:**  
A race condition occurs when multiple threads access shared resources without synchronization, and the outcome depends on timing. Example in Go:

```go
var count int
func increment() {
    count++ // not atomic
}
// Two goroutines call increment() concurrently → lost update
```

**D4 — Medium:**  
Symmetric encryption uses the same key for encryption/decryption (fast, e.g., AES). Asymmetric uses a public/private key pair (slower, e.g., RSA). In TLS, asymmetric encryption is used to securely exchange a session key (or perform key exchange), then symmetric encryption is used for the actual data transfer.

**D5 — Medium:**  
A container image layer is a read-only filesystem change created by each Dockerfile instruction. Layers are stacked and cached. Layer caching means unchanged layers are reused, so best practices include: placing rarely-changing instructions (base image, dependencies) at the top, combining commands to reduce layers, and using specific base image tags to avoid cache invalidation.

**D6 — Medium:**  
For intermittent HTTP 503:
1. Check application/server logs for errors or stack traces.  
2. Check load balancer health checks and target group status.  
3. Monitor CPU/memory/disk usage on servers.  
4. Inspect database connection pool exhaustion or slow queries.  
5. Verify network latency and firewall rules.  
6. Check for rate limiting or throttling.  
7. Review dependencies (external APIs, message queues).

**D7 — Hard:**  
The CAP theorem states a distributed system can guarantee only two of: Consistency, Availability, and Partition tolerance. During a network partition, you must choose between consistency (CP) or availability (AP). CP example: ZooKeeper (refuses writes if quorum lost). AP example: Cassandra (accepts writes even if nodes are unreachable, later reconciles).

**D8 — Medium:**  
Horizontal scaling adds more machines/nodes to distribute load; vertical scaling increases resources (CPU/RAM) of an existing machine. Patterns enabling horizontal scaling: stateless services, load balancing, distributed databases, microservices, message queues, and auto-scaling.

**D9 — Easy:**  
An environment variable is a key-value pair in a process’s environment. To persist across shell sessions on Linux, add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `/etc/environment` (system-wide).

**D10 — Easy:**  
JSON is a strict, text-based data interchange format; YAML is a human-friendly serialization format with indentation and comments. JSON advantage: universally supported and machine-parseable. YAML advantage: readability and support for configuration files.

**D11 — Easy:**  
A REST API is an architectural style using HTTP. GET retrieves resources, POST creates new resources, PUT updates/replaces a resource, DELETE removes a resource. (PATCH partially updates.)

**D12 — Easy:**  
Version pinning means specifying exact versions of dependencies (e.g., `package.json` with `"express": "4.18.2"` or `requirements.txt` with `==`). It ensures reproducible builds by preventing unexpected changes from dependency updates.

**D13 — Easy:**  
A compiled language is translated to machine code before execution (e.g., C, Go). An interpreted language is executed line-by-line by an interpreter (e.g., Python, Ruby). Some languages (Java, C#) use a hybrid approach with bytecode and JIT compilation.

**D14 — Medium:**  
A reverse proxy sits in front of backend servers and forwards client requests to them; it provides load balancing, caching, SSL termination, and security. A forward proxy sits in front of clients and forwards their outbound requests (e.g., corporate web proxy). Common reverse proxies: Nginx (load balancing, static serving), HAProxy (high-availability TCP/HTTP proxy).

**D15 — Medium:**  
A deadlock is a situation where threads block forever, each waiting for resources held by another. The four Coffman conditions:  
1. Mutual exclusion (resource held exclusively).  
2. Hold and wait (thread holds a resource while waiting for another).  
3. No preemption (resources cannot be forcibly taken).  
4. Circular wait (a cycle of threads waiting for each other).

**D16 — Hard:**  
Eventual consistency means updates propagate asynchronously and replicas converge over time. Cassandra handles read-after-write consistency via tunable consistency levels: `ONE` (fast, may be stale), `QUORUM` (majority, ensures latest), `ALL` (strongest). Read repair and hinted handoff help convergence. Levels include `ANY`, `ONE`, `TWO`, `THREE`, `QUORUM`, `LOCAL_QUORUM`, `EACH_QUORUM`, `ALL`.

**D17 — Hard:**  
mTLS (mutual TLS) authenticates both client and server. Handshake:  
1. Client sends `ClientHello`.  
2. Server sends its certificate and requests a client certificate.  
3. Client verifies the server’s certificate (against CA).  
4. Client sends its certificate and a signed proof of possession.  
5. Server verifies the client’s certificate.  
6. Both derive a session key via key exchange (e.g., ECDHE).  
7. Encrypted data flows.  
mTLS is used in service meshes (Istio), zero-trust networks, and API gateways for strong identity verification.

**D18 — Hard:**  
A hash table uses a hash function to map keys to bucket indices. Collision resolution:  
- **Chaining:** each bucket holds a linked list; insert/lookup/delete traverse the list.  
- **Open addressing:** probes next slots (linear/quadratic probing) until empty.  
Average time complexity: O(1) for insert, lookup, delete. Worst case (all keys collide): O(n) for each operation.

**D19 — Hard:**  
A circuit breaker prevents cascading failures by stopping calls to a failing service. States:  
- **Closed:** requests pass normally; failures counted.  
- **Open:** after a threshold, requests fail fast without hitting the service.  
- **Half-open:** after a timeout, a few trial requests are allowed; if successful, circuit closes; if not, reopens.  
It relates to retry policies by preventing infinite retries; exponential backoff adds delays between retries, while the circuit breaker gives the service time to recover.

**D20 — Hard:**  
Optimistic concurrency assumes conflicts are rare: it uses version numbers or timestamps and checks at commit time (e.g., `UPDATE ... WHERE version = ?`). Pessimistic concurrency locks resources upfront (e.g., `SELECT FOR UPDATE`) to prevent conflicts. Choose optimistic for low-contention workloads (e.g., web apps) and pessimistic for high-contention or critical data (e.g., inventory systems). Example: optimistic uses `version` column; pessimistic uses `SELECT ... FOR UPDATE` to lock a row until transaction commits.
