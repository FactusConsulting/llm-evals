## Cloud Infrastructure Architecture

**CL1 — Easy: IaaS vs PaaS vs SaaS**
- **IaaS**: Provider supplies raw compute, storage, networking; you manage OS, middleware, apps. Example: AWS EC2.
- **PaaS**: Provider manages runtime, OS, middleware; you deploy apps. Example: Azure App Service.
- **SaaS**: Provider delivers fully managed software; you only configure. Example: Microsoft 365.

**CL2 — Easy: Shared Responsibility Model**
- **IaaS VMs**: Provider responsible for physical host, hypervisor, network, storage infrastructure. You responsible for guest OS, patches, applications, data, access.
- **Managed Kubernetes**: Provider handles control plane, worker node OS, kubelet, networking. You handle pods, containers, secrets, RBAC, application security.
- **SaaS (M365)**: Provider handles everything except your data, user identities, and client devices. You manage user accounts, data classification, compliance.

**CL3 — Medium: VPC, Subnet, Security Group, NACL**
- **VPC**: Virtual private network boundary in cloud; logically isolated network.
- **Subnet**: IP range within VPC; can be public or private; maps to availability zones.
- **Security Group**: Instance-level virtual firewall; stateful; allows only (no deny rules); evaluated per instance.
- **NACL**: Subnet-level firewall; stateless; supports allow/deny rules; evaluated in order.
- **Layering**: NACL filters traffic at subnet boundary first, then SG filters at instance level. SG is stateful (return traffic auto-allowed); NACL is stateless (must explicitly allow return traffic).

**CL4 — Medium: Multi-Account AWS/Azure Strategy**
- **Landing Zone**: Pre-configured baseline environment with identity, security, networking, logging.
- **Organizational Units (OUs)**: Hierarchical grouping of accounts (e.g., Dev, Prod, Security, Shared Services).
- **Guardrails**: Preventive/detective policies (SCPs in AWS, Azure Policy) enforcing compliance.
- **Shared Networking**: Transit Gateway (AWS) or Hub-and-Spoke (Azure) centralizes connectivity between VPCs/VNets and on-prem.
- **Centralized Logging**: Aggregated CloudTrail/GuardDuty or Azure Log Analytics into a security account.
- **Single-account problems**: No blast radius isolation, no billing separation, no environment isolation, shared IAM complexity, compliance risk.

**CL5 — Medium: Infrastructure as Code**
- **Terraform/OpenTofu**: Declarative, multi-cloud, state-based; mature ecosystem; best for multi-cloud or cloud-agnostic IaC.
- **Pulumi**: Declarative with general-purpose languages (Python, Go, TS); good for complex logic and code reuse.
- **CloudFormation/Bicep**: Native AWS/Azure; deep integration, rollback, drift detection; best for single-cloud shops.
- **Crossplane**: Control-plane-based IaC; Kubernetes-native; enables platform teams to expose cloud resources as APIs; best for internal platform engineering.
- **Choice**: Terraform for multi-cloud; CloudFormation/Bicep for single-cloud; Pulumi for code-heavy teams; Crossplane for platform teams building internal developer platforms.

**CL6 — Medium: Autoscaling Patterns**
- **HPA**: Scales pods based on CPU/memory/custom metrics; horizontal.
- **VPA**: Adjusts pod CPU/memory requests based on usage; vertical; requires restart.
- **Cluster Autoscaler**: Adds/removes worker nodes when pods can't schedule.
- **KEDA**: Event-driven autoscaler; scales based on queue length, Kafka lag, custom metrics; supports scale-to-zero.
- **KEDA over HPA**: When scaling is driven by external events (e.g., messages in queue) rather than CPU/memory; when you need scale-to-zero; when HPA's 15-second metric window is too slow.

**CL7 — Hard: Disaster Recovery Strategy**
- **RPO/RTO**: Define acceptable data loss (RPO) and downtime (RTO); e.g., RPO=15min, RTO=1hr.
- **Active-Active**: Both regions serve traffic; DNS routes to nearest; requires synchronous or near-sync DB replication; complex but fast failover.
- **Active-Passive**: Primary serves; standby has infra ready but no traffic; failover via DNS; simpler; lower cost.
- **Database Replication**: Sync replication (low RPO, latency penalty, distance-limited); async (higher RPO, no latency penalty, risk of data loss).
- **DNS Failover**: Route53 health checks + failover policy; Traffic Manager with priority routing; TTL impacts failover speed.
- **State Management**: Use managed services (S3, queues, caches) with cross-region replication; avoid sticky sessions or use distributed sessions.
- **Cost**: Active-active doubles running costs; warm standby reduces compute but keeps DB running; pilot light keeps minimal core running.
- **DR Modes**: Pilot light (minimal core ready, scale up on failover); warm standby (full infra running but no traffic); multi-site active-active (both serving).

**CL8 — Hard: GitOps Model**
- **GitOps**: Git is single source of truth for desired state; controller reconciles actual state to desired state.
- **ArgoCD vs FluxCD**: ArgoCD has richer UI, multi-cluster management, sync policies; Flux is more lightweight, integrates with Git providers, has image automation.
- **Secrets**: Sealed Secrets (encrypts secrets in Git); External Secrets Operator (fetches from cloud secret managers); Vault (dynamic secrets, rotation).
- **Drift**: GitOps controller detects drift and reverts manual changes; can be configured to alert or auto-remediate; manual changes are overwritten on next sync.

**CL9 — Hard: Stateful Legacy App on Kubernetes**
- **StatefulSet**: Stable network identity, ordered deployment/termination, stable storage.
- **PV/PVC with Local Storage Class**: Use local SSDs via local persistent volumes; avoid network storage for low latency.
- **Headless Service**: Provides stable DNS names for each pod; enables peer discovery.
- **Init Containers**: Handle ordered startup dependencies, config validation, pre-flight checks.
- **ConfigMaps as Volume Mounts**: Mount config files at exact paths; use subPath for specific file paths.
- **Pod Disruption Budgets**: Ensure minimum availability during voluntary disruptions; protect against eviction.
- **Additional**: Use readiness probes for ordered readiness; consider StatefulSet partition for rolling updates.

**CL10 — Medium: Service Accounts vs Workload Identity vs IRSA**
- **Service Account (K8s)**: Kubernetes identity for pods; used for API server auth.
- **Workload Identity (GCP/Azure)**: Cloud identity mapped to K8s service account; allows cloud API access.
- **IRSA (AWS)**: IAM role assumed by K8s service account via OIDC federation; grants AWS permissions.
- **Bad practice**: Mounting cloud credentials in pods—long-lived, hard to rotate, broad scope, risk of exfiltration.
- **Workload Identity Federation**: Uses OIDC to exchange K8s service account token for cloud IAM token; short-lived, scoped, no static credentials.

**CL11 — Medium: Object vs Block vs File Storage**
- **Object (S3/Blob)**: Key-value store; HTTP API; for static content, backups, data lakes; 11 nines durability (S3); availability 99.99%.
- **Block (EBS/Managed Disk)**: Raw disk attached to VM; low latency; for databases, OS disks; durability 99.999999% (EBS); availability 99.99%.
- **File (EFS/Azure Files)**: NFS/SMB; shared access; for shared app data, home directories; durability 99.999999%; availability 99.99%.
- **Use cases**: Object for static/immutable; block for single-VM DB; file for multi-VM shared access.

**CL12 — Hard: Zero-Trust Kubernetes**
- **Network Policies**: Micro-segmentation at pod level; allow only required east-west traffic.
- **Service Mesh (mTLS)**: Istio/Linkerd encrypts pod-to-pod traffic; identity-based authn/authz.
- **Pod Identity**: Workload identity federation; no static credentials.
- **Admission Controllers (OPA/Kyverno)**: Enforce policies (e.g., no privileged containers, required labels, image allowlists).
- **Image Signing**: Cosign/Notary verify image signatures before admission.
- **Runtime Security (Falco)**: Detects anomalous syscalls, file access, network behavior.
- **Secrets Management**: External Secrets Operator or Vault; no secrets in Git.
- **Difference from perimeter**: No implicit trust inside network; every request authenticated/authorized; continuous monitoring.

**CL13 — Easy: CDN**
- **CDN**: Distributed edge servers that cache content closer to users; reduces latency, origin load.
- **How it works**: DNS routes user to nearest PoP; edge caches static content; dynamic content proxied.
- **Services**: AWS CloudFront, Azure CDN.
- **When to use**: Static assets, video streaming, global distribution, DDoS mitigation. Not for highly dynamic personalized content or when origin is already close to users.

**CL14 — Easy: Regions and Availability Zones**
- **Regions**: Geographic areas with multiple AZs; e.g., us-east-1.
- **Availability Zones**: Isolated data centers within region; independent power/cooling/network.
- **Multi-AZ deployment**: High availability; tolerate AZ failure; for HA-critical workloads.
- **Zonal vs Regional**: Zonal resources (EBS, EC2) tied to one AZ; regional resources (S3, ELB, RDS multi-AZ) span AZs.

**CL15 — Easy: Managed Databases**
- **Managed DB (RDS, Cloud SQL, Azure SQL)**: Provider handles backups, patching, replication, failover, monitoring, scaling.
- **Self-managed VM DB**: You handle all operational tasks; more control, more effort.
- **Benefits**: Reduced ops burden, built-in HA, automated backups, security patches.

**CL16 — Easy: IAM and Least Privilege**
- **IAM Users**: Individual identities; can have access keys, passwords.
- **Groups**: Collections of users; policies attached to groups.
- **Roles**: Identity with permissions; assumed by users/services; temporary credentials.
- **Policies**: JSON documents defining permissions; attached to users/groups/roles.
- **Least Privilege**: Grant only minimum permissions needed; use scoped policies, deny by default, review regularly.

**CL17 — Easy: Serverless**
- **Serverless**: Run code without managing servers; pay per invocation; auto-scaling.
- **AWS Lambda / Azure Functions / GCP Functions**: Event-driven functions; similar concepts; differences in language support, integrations, limits.
- **Cold Starts**: Delay when initializing new function instance; impacts latency-sensitive apps.
- **Poor fit**: Long-running processes, stateful apps, low-latency critical paths, heavy compute, applications needing persistent connections.

**CL18 — Medium: Kubernetes Ingress Options**
- **Ingress Resource**: API object defining routing rules; implemented by controller (NGINX, Traefik); TLS termination at controller.
- **Gateway API**: Newer, more expressive; separates routing from implementation; supports HTTP, TLS, TCP; TLS termination at gateway.
- **Cloud LB Annotations**: Direct cloud LB (ALB/NLB) annotations; TLS termination at LB; less Kubernetes-native.
- **Service Mesh Ingress Gateway**: Istio/Linkerd gateway; mTLS, advanced routing, traffic management; TLS termination at mesh edge.
- **Gateway API over Ingress**: When you need multi-protocol, cross-namespace routing, richer policy, or vendor-neutral abstraction.

**CL19 — Hard: Cost Optimization**
- **Reserved Instances**: 1-3 year commitment; up to 72% savings; for steady-state workloads.
- **Savings Plans**: Flexible commitment; covers EC2, Lambda, Fargate; easier than RIs.
- **Spot/Preemptible**: Up to 90% savings; for fault-tolerant, stateless, batch workloads.
- **Right-sizing**: Match instance size to actual utilization; use CloudWatch/Compute Optimizer.
- **Storage Tiering**: S3 Intelligent-Tiering auto-moves data; Archive for cold data; lifecycle policies.
- **Idle Detection**: Find unattached volumes, idle instances, unused IPs; auto-terminate or notify.
- **FinOps**: Showback/chargeback by team; tagging; budget alerts; cost anomaly detection.
- **Tools**: AWS Cost Explorer, Budgets, Trusted Advisor; Azure Cost Management; Terraform cost estimation; Kubecost for K8s.

**CL20 — Hard: Multi-Cloud Strategy**
- **Abstraction Layers**: Terraform for IaC; Kubernetes for runtime; cloud-agnostic APIs (CNCF projects).
- **Kubernetes as Common Runtime**: Same container orchestration; but cloud-specific integrations (storage, LB, IAM) still differ.
- **Networking**: VPN/IPsec or dedicated interconnect between clouds; latency and bandwidth costs.
- **Identity Federation**: OIDC/SAML federation; consistent RBAC across clouds.
- **Trade-offs**: Multi-cloud adds complexity, latency, cost, skill requirements; theoretical benefits (no lock-in, best-of-breed) often outweighed by operational burden.
- **Justified when**: Regulatory data residency, disaster recovery across providers, avoiding single-vendor dependency for critical workloads.
- **Unnecessary when**: Single-cloud meets requirements; multi-cloud adds cost and complexity without clear benefit.

## OT Infrastructure Architecture

**OT1 — Easy: Purdue Model (ISA-95)**
- **Level 0**: Physical process (sensors, actuators).
- **Level 1**: Basic control (PLCs, RTUs, DCS controllers).
- **Level 2**: Supervision (HMI, SCADA servers, alarm management).
- **Level 3**: Operations management (historian, batch management, scheduling).
- **Level 4**: Business/enterprise (ERP, MES, corporate IT).
- **Level 5**: Enterprise network (internet, cloud, external partners).

**OT2 — Easy: IT vs OT Networks**
- **IT**: Data-centric; high availability; frequent patching; dynamic; standard protocols (TCP/IP, HTTP).
- **OT**: Process-centric; real-time deterministic; availability of process is critical; patching can disrupt production; legacy protocols; long asset lifecycles.
- **Why not standard patching**: OT systems cannot tolerate reboots; vendor validation required; patches may break control logic; change windows are rare; safety and production continuity take precedence.

**OT3 — Medium: Industrial DMZ (IDMZ)**
- **IDMZ**: Buffer zone between IT (Level 4) and OT (Level 3) networks; isolates traffic.
- **Allowed traffic**: Only necessary protocols (e.g., historian data replication, MES queries); typically from IT to DMZ and DMZ to OT; no direct IT-to-OT.
- **Direction**: IT can access DMZ; DMZ can access OT; IT cannot directly access OT.
- **Why direct IT-to-Level 1 is dangerous**: Malware from IT can propagate to control systems; no security controls; lack of protocol awareness; can cause safety incidents.

**OT4 — Medium: OT Protocols**
- **Modbus TCP**: Level 1-2; industrial protocol for PLC communication; simple, unencrypted.
- **OPC UA**: Level 2-3; standardized communication for industrial data; supports encryption, certificates.
- **EtherNet/IP (CIP)**: Level 1-2; industrial Ethernet protocol; used for I/O and control.
- **PROFINET**: Level 1-2; industrial Ethernet for automation; real-time communication.
- **MQTT**: Level 3-4; lightweight pub/sub for IoT/cloud; often used for telemetry to cloud.

**OT5 — Medium: Data Diode vs Firewall**
- **Data Diode**: Hardware device that allows one-way data transfer; physically prevents reverse traffic.
- **Firewall**: Filters traffic in both directions; can be bypassed by misconfiguration.
- **When to use data diode**: High-security environments (critical infrastructure, nuclear, defense); when data must flow one-way (e.g., historian to IT) and no return traffic is needed.
- **Limitation**: No return path; cannot be used for interactive protocols; requires application-level data transfer (e.g., file transfer, database replication).

**OT6 — Medium: SCADA to Cloud Data Flow**
- **Flow**: PLCs → SCADA/Historian (Level 2/3) → OPC UA server → Edge Gateway → MQTT broker → Cloud ingestion.
- **Security boundaries**: 
  - Between Level 2/3 and edge gateway: firewall/IDMZ.
  - Edge gateway: protocol conversion, data validation, local buffering.
  - Between edge and cloud: TLS, MQTT over secure port, cloud-side authentication.
  - Cloud: API gateway, data lake, analytics.
- **Key**: No direct cloud access from Level 1; all data flows through controlled gateway.

**OT7 — Hard: IEC 62443 Zones and Conduits**
- **Zone**: Group of assets with similar security requirements; defined by risk, function, trust.
- **Conduit**: Communication path between zones; carries specific protocols; secured by firewall/security controls.
- **Design for manufacturing plant**:
  - **Zone 1 (Corporate)**: IT network; high trust for business apps.
  - **Zone 2 (Engineering)**: Engineering workstations; access to PLCs; higher security.
  - **Zone 3 (SCADA)**: SCADA servers, historian; protected from IT.
  - **Zone 4 (Control)**: PLCs, HMIs; highest security; minimal external access.
  - **Zone 5 (SIS)**: Safety systems; air-gapped or highly isolated.
  - **Conduits**: Between zones, only specific protocols (e.g., Modbus TCP from SCADA to PLC); firewalls with allowlists.

**OT8 — Hard: Network Segmentation for 200 PLCs**
- **VLAN Design**: Separate VLANs per production line, per function (control, HMI, engineering, historian).
- **Firewall Placement**: Between IT and OT (IDMZ); between lines; between engineering and control.
- **Switch Architecture**: Layer 3 switches for inter-VLAN routing; redundant switches for HA.
- **Remote Access**: Jump host in DMZ; MFA; session recording; time-limited access; no direct VPN to control network.
- **Transition without stopping production**: Phased approach; create new VLANs in parallel; move devices during planned outages; use temporary ACLs; test thoroughly; maintain fallback.

**OT9 — Hard: SIS vs BPCS**
- **BPCS**: Basic Process Control System; handles normal operations; non-safety critical.
- **SIS**: Safety Instrumented System; independent; detects dangerous conditions and initiates safe shutdown; SIL-rated.
- **IEC 61511**: Functional safety standard for SIS; defines lifecycle, SIL levels, integrity requirements.
- **Why isolated**: SIS must remain functional even if BPCS fails; ransomware on SIS could prevent safety shutdowns, leading to catastrophic incidents.
- **Ransomware on SIS**: Could disable safety functions; cause loss of containment, explosions, or environmental release; operators may not be able to safely shut down.

**OT10 — Medium: PLC vs DCS vs SCADA**
- **PLC**: Programmable Logic Controller; discrete control; fast, deterministic; for individual machines.
- **DCS**: Distributed Control System; integrated control across plant; for continuous processes (chemical, refining).
- **SCADA**: Supervisory Control and Data Acquisition; monitors and controls geographically distributed assets; higher-level supervision.
- **Coexistence**: Yes; many plants use PLCs for local control, DCS for process control, SCADA for remote monitoring.

**OT11 — Medium: Remote Access to OT**
- **Architecture**: Jump host in DMZ; MFA; session recording; vendor access via time-limited accounts; approval workflow.
- **Why RDP directly to HMI is unacceptable**: No audit trail; no MFA; direct exposure of control network; risk of malware propagation; no session control.

**OT12 — Hard: Detection and Response for Compromised VPN**
- **Detection**: Network monitoring (IDS/Anomaly detection) on Level 3; asset inventory; baseline behavior; alert on unusual traffic.
- **Response**: Isolate compromised VPN appliance; revoke vendor access; contain lateral movement; preserve evidence; coordinate with control room.
- **Safe operations**: If threat actor is in Level 3, consider manual operation of critical processes; isolate Level 1/2 if possible; maintain safety systems.
- **Operator role**: Operators are first responders; they must maintain safe process control; report anomalies; follow procedures; may need to switch to manual mode.

**OT13 — Easy: HMI**
- **HMI**: Human-Machine Interface; graphical display for operators to monitor and control processes.
- **Role**: Provides real-time process data, alarms, control commands.
- **Difference from engineering workstation**: HMI is for operators (runtime); engineering workstation is for engineers (configuration, programming, maintenance).

**OT14 — Easy: Historian**
- **Historian**: Time-series database for process data; stores historical values, alarms, events.
- **Importance**: Enables trend analysis, troubleshooting, reporting, optimization.
- **Plant historian (Level 3)**: Local, high-resolution, real-time data.
- **Enterprise historian (Level 4)**: Aggregates data from multiple plants; lower resolution; for business analytics.

**OT15 — Easy: Ladder Logic**
- **Ladder Logic**: Graphical programming language for PLCs; resembles electrical relay diagrams.
- **Executed by**: PLCs (and some RTUs/DCS controllers).
- **Why dominant**: Familiar to electricians; simple to debug; standardized (IEC 61131-3); proven reliability; legacy expertise.

**OT16 — Easy: RTU vs PLC**
- **RTU**: Remote Terminal Unit; for remote, distributed sites; communicates via telemetry (radio, satellite, cellular); lower processing power.
- **PLC**: Local control; faster; more I/O; for local automation.
- **RTU environments**: Oil/gas pipelines, water distribution, remote monitoring; where central control is remote.

**OT17 — Easy: Analog vs Digital Signals**
- **Analog**: Continuous signal (4-20mA, 0-10V); represents variable process values (temperature, pressure).
- **Digital**: Discrete (0/1); represents on/off, limit switches, relay states.
- **Why 4-20mA preferred**: 4mA represents zero; can detect wire break (0mA); current loop less susceptible to voltage drops; standard for process instrumentation.

**OT18 — Medium: OT Asset Inventory**
- **Foundation**: You cannot protect what you don't know; asset inventory enables risk assessment, vulnerability management, incident response.
- **Passive monitoring**: Capture traffic, identify devices via MAC, protocols; no impact on operations.
- **Active scanning**: Probes devices; can disrupt legacy systems; dangerous in OT.
- **Why active scanning dangerous**: Legacy devices may crash on unexpected traffic; protocols are fragile; can cause production outages.

**OT19 — Hard: MITRE ATT&CK for ICS**
- **Framework**: Adversary tactics and techniques specific to industrial control systems.
- **Tactics and examples**:
  - **Initial Access**: Exploit internet-facing asset (e.g., VPN compromise).
  - **Execution**: Malicious OPC UA client (e.g., send commands to PLC).
  - **Persistence**: Modify controller logic (e.g., upload new ladder logic).
  - **Privilege Escalation**: Exploit engineering workstation (e.g., gain admin via service account).
  - **Evasion**: Disable alarms (e.g., tamper with alarm settings).
  - **Impact**: Damage to plant (e.g., override safety interlocks).
- **Difference from enterprise**: Focus on physical processes, controllers, safety; includes techniques like "loss of view" and "loss of control".
- **Use**: Map defenses to techniques; identify gaps; prioritize mitigations.

**OT20 — Hard: Converged IT/OT SOC**
- **Log collection**: Use passive collectors (SPAN ports, network taps); avoid agents on legacy devices; collect from historians, firewalls, IDS.
- **SIEM integration**: Forward OT logs to central SIEM; correlate with IT events.
- **OT-specific detection rules**: Monitor for unauthorized firmware changes, unexpected protocol usage, alarm floods, engineering workstation access.
- **Alert triage**: IT analysts triage initial alerts; escalate to OT engineers for validation; OT engineers have context on process impact.
- **False positives**: High in OT due to legacy protocols; use baselines and whitelisting; validate against asset inventory.
- **Firmware change alert**: Verify against change management records; if unauthorized, isolate device, preserve logs, assess impact, coordinate with operations for safe remediation.
