## Go (20 questions)

### G1 — Easy: Slice vs Array
An array in Go has a fixed size determined at compile time (`[5]int`), while a slice is a dynamically-sized view into an array (`[]int`). A slice is a struct with three fields: a pointer to the underlying array, a length, and a capacity. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array (typically doubling capacity), copies the existing elements, and then appends the new element. The slice's pointer is updated to point to the new array.

### G2 — Easy: `var x int` vs `x := 0`
`var x int` declares a variable with the zero value (0 for int), while `x := 0` uses short variable declaration, which infers the type from the value (also int) and assigns 0. You cannot use `:=` at package level (only inside functions), and you cannot use it when the variable is already declared in the same scope (it would be a compile error unless at least one variable on the left is new).

### G3 — Medium: Goroutines and GMP Model
A goroutine is a lightweight thread managed by the Go runtime, not the OS. It starts with a small stack (a few KB) that grows as needed, whereas OS threads have large fixed stacks (typically 1-8 MB). The Go scheduler uses the GMP model: G (goroutine), M (OS thread), P (processor/context). The scheduler multiplexes many goroutines onto fewer OS threads. When a goroutine blocks (e.g., on I/O), the scheduler moves it off the thread and runs other goroutines. This allows Go to handle hundreds of thousands of concurrent goroutines with low overhead.

### G4 — Medium: Channels
Channels are Go's mechanism for communication between goroutines. An unbuffered channel (`make(chan int)`) blocks the sender until a receiver is ready, and blocks the receiver until a sender is ready—it provides synchronous communication. A buffered channel (`make(chan int, 5)`) allows the sender to send up to the buffer size without blocking. When you send to a full buffered channel, the sender blocks until space becomes available (or until a receiver reads from it). Channels are typed and can be closed to signal that no more values will be sent.

### G5 — Medium: Context Package
The `context` package is used for carrying deadlines, cancellation signals, and request-scoped values across API boundaries. It's essential for controlling cancellation in HTTP servers, RPC clients, and other long-running operations. Minimal example:

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

req, err := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
if err != nil {
    log.Fatal(err)
}
resp, err := http.DefaultClient.Do(req)
if err != nil {
    log.Fatal(err) // Will be context.DeadlineExceeded if timeout
}
```

### G6 — Medium: Interface Satisfaction
Go interfaces are satisfied implicitly—a type satisfies an interface if it implements all the methods. Unlike Java/C# where you explicitly declare `implements`, Go uses structural typing. The empty interface `interface{}` (or `any` in Go 1.18+) accepts any type because every type implements zero methods. It's powerful for generic-like code but dangerous because it bypasses type safety, requiring type assertions or reflection to use the underlying value, which can lead to runtime panics if the type doesn't match expectations.

### G7 — Hard: Memory Model and Goroutine Visibility
The code is unsafe because Go's memory model does not guarantee that the goroutine's writes to `data` and `ready` will be visible to the main goroutine in the expected order. Without synchronization, the compiler and CPU may reorder operations, and the main goroutine may see `ready = true` before `data = "hello"` (or never see the writes at all). Correct alternatives:
1. Use a channel: `ch := make(chan string); go func() { ch <- "hello" }(); fmt.Println(<-ch)`
2. Use `sync.Mutex` to protect both variables
3. Use `sync.Once` or `sync.WaitGroup`
4. Use `atomic` operations for the flag and ensure proper memory ordering

### G8 — Hard: Mutex vs RWMutex, sync.Map
`sync.Mutex` provides exclusive access—only one goroutine can hold the lock at a time. `sync.RWMutex` allows multiple readers or a single writer. Use `RWMutex` when reads are frequent and writes are rare, as it allows concurrent reads without blocking. `sync.Map` is optimized for specific patterns: when keys are written once and read many times, or when goroutines access disjoint keys. It uses internal sharding and atomic operations to reduce contention. Performance trade-offs: `sync.Map` has higher overhead for simple operations compared to a mutex-protected map, but scales better under high contention. A regular map with a mutex is simpler and faster for low-contention scenarios.

### G9 — Hard: Go Modules
Go modules are the dependency management system. `go.mod` declares the module path, Go version, and dependencies with their versions. `go.sum` contains cryptographic checksums of the module contents to verify integrity and prevent tampering. `go mod tidy` adds missing dependencies, removes unused ones, and updates `go.sum`. Minimum Version Selection (MVS) means Go selects the minimum version of each dependency that satisfies all constraints from the module graph—it doesn't upgrade to the latest version unless required. This ensures reproducible builds and avoids unnecessary upgrades.

### G10 — Medium: Defer
`defer` schedules a function call to run when the enclosing function returns. Multiple defers execute in LIFO (last-in, first-out) order. A common gotcha with defer in a loop is that defers are not executed until the function returns, not at the end of each iteration. This can cause resource leaks (e.g., file handles) if you defer `Close()` inside a loop—all files stay open until the function exits. The fix is to wrap the defer in a helper function or use explicit closing.

### G11 — Easy: Pointers
A pointer in Go stores the memory address of a value. The zero value of a pointer is `nil`. You create a pointer to a struct literal using `&StructType{...}` or `new(StructType)`. Example: `p := &Person{Name: "Alice"}` creates a pointer to a Person struct. Pointers are used to share values and allow modification without copying.

### G12 — Easy: init() Function
`init()` runs automatically when a package is initialized, before `main()` runs. It's used for setup that can't be done with variable declarations. A package can have multiple `init()` functions (in the same file or across files). They execute in file order (as determined by the compiler) and within a file, in declaration order. Dependencies between packages are initialized first. `init()` cannot be called explicitly and cannot take parameters or return values.

### G13 — Easy: make vs new
`make` is used only for slices, maps, and channels—it initializes the internal data structure and returns a usable value. `new` allocates memory for a type and returns a pointer to the zeroed value. `new(T)` is equivalent to `&T{}` (zero value). `make` returns a non-pointer value (except for channels which are reference types), while `new` always returns a pointer. You can't use `make` on structs or basic types, and you can't use `new` on maps/slices/channels (it would return a nil pointer).

### G14 — Easy: Error Handling
Go uses explicit error returns. The `error` interface is `type error interface { Error() string }`. Idiomatic pattern: check if `err != nil` immediately after a call. `errors.Is(err, target)` checks if err matches a specific error value (works with wrapped errors), while `errors.As(err, &target)` checks if err is of a specific type. Using `==` only works for direct comparison without wrapping—it fails if the error has been wrapped with `%w` or `fmt.Errorf`.

### G15 — Easy: Composite Types and Zero Values
- Map: `map[K]V` — zero value is `nil` (can't be written to, must be initialized with `make`)
- Slice: `[]T` — zero value is `nil` (can be appended to, but len is 0)
- Channel: `chan T` — zero value is `nil` (blocks forever on send/receive)
- Struct: `struct{...}` — zero value is the zero value of each field

### G16 — Medium: Race Conditions
A race condition occurs when multiple goroutines access the same variable concurrently, and at least one access is a write. The `-race` flag instruments the code to detect data races at runtime—it tracks memory accesses and reports when conflicting accesses occur without synchronization. Example:

```go
var counter int
// Race: multiple goroutines increment without lock
go func() { counter++ }()
go func() { counter++ }()
```

Fix with mutex:
```go
var mu sync.Mutex
go func() { mu.Lock(); counter++; mu.Unlock() }()
go func() { mu.Lock(); counter++; mu.Unlock() }()
```

Or with a channel:
```go
ch := make(chan int, 1)
go func() { ch <- 1 }()
go func() { ch <- 1 }()
counter += <-ch + <-ch
```

### G17 — Medium: select Statement
`select` waits on multiple channel operations—it blocks until one of its cases can proceed. Unlike `switch` (which evaluates conditions), `select` is specifically for channel communication. When multiple cases are ready, Go picks one at random (to ensure fairness). You can implement a timeout:

```go
select {
case result := <-ch:
    fmt.Println(result)
case <-time.After(5 * time.Second):
    fmt.Println("timeout")
}
```

### G18 — Hard: Escape Analysis
Escape analysis is a compiler optimization that determines whether a variable can be allocated on the stack or must be moved to the heap. If a variable's address escapes the function (e.g., returned, stored in a global, passed to a function that stores it), it's allocated on the heap. You can inspect decisions with `go build -gcflags=-m` or `go tool compile -m`. This matters because heap allocation is more expensive (garbage collection overhead) and stack allocation is nearly free. Understanding escape analysis helps optimize hot paths by keeping allocations on the stack.

### G19 — Hard: Reflection
`reflect.Type` represents the type of a value (e.g., `int`, `struct{...}`), while `reflect.Value` represents the actual value and allows reading/writing it. Reflection is slow because it involves runtime type checks, interface boxing, and often allocation. It's justified for generic serialization (e.g., JSON marshaling), ORMs, and testing frameworks where code generation would be impractical. For performance-critical paths, code generation (e.g., `go generate`) or generics (Go 1.18+) are preferred.

### G20 — Hard: go:embed
`go:embed` embeds files into the compiled binary at compile time. Syntax: `//go:embed filename` for a single file, `//go:embed directory` for all files in a directory (recursively), or `//go:embed pattern` for glob patterns. It works with `string`, `[]byte`, or `fs.FS` types. Limitations: files must be in the module (no `..` paths), and you can't embed files that would be excluded by `.gitignore` (unless using `all:` prefix). When embedding a directory as `fs.FS`, you get a read-only file system that implements `io/fs.FS`, allowing standard file operations like `fs.ReadFile` and `fs.WalkDir`.

## Rust (20 questions)

### R1 — Easy: Ownership
Ownership is Rust's memory management system. Three rules:
1. Each value has an owner (the variable that owns it).
2. Only one owner at a time—when the owner goes out of scope, the value is dropped (freed).
3. When you move a value (assign to another variable, pass to a function), the original owner loses access.

This ensures memory safety without garbage collection.

### R2 — Easy: String vs &str
`String` is an owned, heap-allocated, growable UTF-8 string. `&str` is a borrowed string slice—a reference to a sequence of UTF-8 bytes without owning them. In function signatures, use `&str` for read-only access (most common), `String` when you need to modify or store the string, and `&mut String` when you need to modify the string in place. `&str` is more flexible because it can accept both `&str` and `&String` (via deref coercion).

### R3 — Medium: Borrowing and Borrow Checker
Borrowing allows using a value without taking ownership. Rules:
- You can have multiple shared references (`&T`) simultaneously.
- You can have at most one mutable reference (`&mut T`) at a time.
- You cannot have a mutable reference while shared references exist.

The borrow checker enforces these rules at compile time, preventing data races and use-after-free. It tracks the lifetimes of references and ensures they don't outlive the data they point to.

### R4 — Medium: Result and Option
`Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`). `Option<T>` represents a value that may be absent (`Some(T)` or `None`). The `?` operator:
- On `Result`: returns the `Ok` value or propagates the `Err` (converted via `From`) from the function.
- On `Option`: returns the `Some` value or returns `None` from the function.

Example:
```rust
use std::fs;
use std::io::Read;

fn read_file(path: &str) -> Result<String, std::io::Error> {
    let mut file = fs::File::open(path)?;
    let mut contents = String::new();
    file.read_to_string(&mut contents)?;
    Ok(contents)
}
```

### R5 — Medium: Box, Rc, Arc
- `Box<T>`: single owner, heap-allocated value. Used for recursive types, large data, or trait objects.
- `Rc<T>`: single-threaded reference counting—multiple owners share the value. Used for shared ownership within one thread.
- `Arc<T>`: atomic reference counting—thread-safe version of `Rc`. Used for shared ownership across threads.

Use `Box` when you need a single owner on the heap, `Rc` for shared ownership in one thread, `Arc` for shared ownership across threads.

### R6 — Medium: Traits
Traits define shared behavior (like Go interfaces). Unlike Go, Rust traits can have default implementations, associated types, and generic parameters. Trait objects (`dyn Trait`) are dynamically dispatched (like Go interfaces) and have a runtime cost. Generics with trait bounds (`T: Trait`) are statically dispatched—the compiler generates specialized code for each type, which is faster but increases binary size. Use `dyn Trait` for heterogeneous collections or when the concrete type is unknown; use generics for performance and flexibility.

### R7 — Hard: Lifetimes
The function fails because the compiler can't determine how long the returned reference lives—it doesn't know if `x` or `y` will be returned, so it can't verify the return value's lifetime. Fix with explicit lifetime parameters:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

This says both inputs and the output share the same lifetime `'a`, meaning the returned reference is valid as long as both inputs are valid.

### R8 — Hard: Send and Sync
- `Send`: a type can be safely transferred to another thread.
- `Sync`: a type can be safely shared across threads (accessed by reference).

`Rc<T>` is not `Send` because it uses non-atomic reference counting—if you sent it to another thread, the counts could become inconsistent. `Arc<T>` uses atomic operations for reference counting, making it `Send` and `Sync` (when `T` is `Send + Sync`). `Arc` is safe because the atomic increment/decrement ensures the count is correct even with concurrent access.

### R9 — Hard: async/await
Rust's async/await is based on `Future`—a state machine that can be polled. When you call an async function, it returns a `Future` that doesn't execute until polled. The executor (e.g., Tokio) polls futures and drives them to completion. Unlike Go's goroutines (which are preemptively scheduled by the runtime), Rust's async tasks are cooperatively scheduled—they must yield control explicitly (e.g., via `.await`). This gives Rust more control over memory and performance but requires an executor. Go's goroutines have a runtime-managed stack that grows, while Rust's futures are stackless (state machines stored on the heap).

### R10 — Medium: unsafe
`unsafe` allows operations that the compiler can't verify:
1. Dereference raw pointers (`*const T`, `*mut T`).
2. Call unsafe functions (e.g., FFI to C).
3. Access or modify mutable static variables.
4. Implement `Send`/`Sync` for types that don't automatically qualify.

Unsafe is justified for FFI, performance-critical low-level operations, and implementing safe abstractions over raw memory. It should be isolated in small, well-documented modules.

### R11 — Easy: Pattern Matching
Pattern matching destructures values and binds variables. `match` is exhaustive—the compiler requires all possible patterns to be covered. `if let` is a shorthand for matching a single pattern and ignoring the rest. Example:

```rust
match value {
    Some(x) => println!("{}", x),
    None => println!("none"),
}
```

The compiler enforces exhaustiveness—you must handle all variants of an enum or use a wildcard `_`.

### R12 — Easy: Vec vs Array
`Vec<T>` is a heap-allocated, growable sequence. `[T; N]` is a fixed-size array on the stack (or inline in other structures). When `Vec` exceeds its capacity, it allocates a new, larger buffer (typically doubling), copies elements, and deallocates the old buffer. `Vec` uses amortized O(1) push—most pushes are O(1), but occasional reallocation is O(n).

### R13 — Easy: Enums
Rust enums are algebraic data types—they can have variants with associated data (like tagged unions). C/Java enums are just named integer constants. Rust enums are more powerful:

```rust
enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
}
```

`Option<T>` is an enum with `Some(T)` and `None`. Rust doesn't have null because it eliminates the billion-dollar mistake—the absence of a value is explicit via `Option`, and the compiler forces you to handle both cases.

### R14 — Easy: impl Blocks
`impl` blocks define methods and associated functions for a type:
- `&self`: immutable borrow—can read but not modify.
- `&mut self`: mutable borrow—can modify.
- `self`: takes ownership (consumes the value).
- Associated functions (e.g., `String::new()`) don't take `self`—they're called with `Type::function()`.

Example:
```rust
impl Rectangle {
    fn area(&self) -> u32 { self.width * self.height }
    fn grow(&mut self) { self.width += 1; }
    fn consume(self) { /* self is moved */ }
    fn new(w: u32, h: u32) -> Rectangle { Rectangle { width: w, height: h } }
}
```

### R15 — Easy: derive Macro
`#[derive(...)]` automatically implements traits for a type. Common ones:
- `Debug`: formatting with `{:?}`
- `Clone`: deep copy
- `PartialEq`: equality comparison
- `Serialize`/`Deserialize` (from serde): JSON/other serialization

You cannot derive a trait if the type contains fields that don't implement that trait (e.g., can't derive `Clone` if a field is `Rc<T>` without `Clone`). You also can't derive traits that require manual implementation logic (e.g., `Display` often needs custom formatting).

### R16 — Medium: Cow
`Cow<'a, T>` (clone-on-write) is an enum that's either `Borrowed(&'a T)` or `Owned(T)`. It's useful when you have data that's usually borrowed but occasionally needs to be modified. Example:

```rust
use std::borrow::Cow;

fn process(input: &str) -> Cow<'_, str> {
    if input.contains("bad") {
        Cow::Owned(input.replace("bad", "good"))
    } else {
        Cow::Borrowed(input)
    }
}
```

This avoids allocating a new `String` when the input doesn't need modification—it just borrows the original.

### R17 — Medium: Module System
Rust's module system:
- `mod` declares a module (inline or in a file).
- `use` brings items into scope.
- `pub` makes items public (visible outside the module).

In Rust 2015, modules in files are declared with `mod foo;` where `foo` is `foo.rs` or `foo/mod.rs`. In Rust 2018, the file system mapping changed: `mod foo;` looks for `foo.rs` or `foo/mod.rs`, but submodules are placed in `foo/bar.rs` rather than `foo/bar/mod.rs`. The 2018 edition also allows `use` paths to be more uniform and supports `crate::` for absolute paths.

### R18 — Hard: Pin
`Pin<T>` prevents the value from being moved after it's pinned. It's needed for self-referential structs—where a struct contains a reference to its own field. If the struct is moved, the reference becomes invalid. Async/await uses `Pin` because futures are state machines that may contain self-references (e.g., a future that borrows a local variable). `Unpin` is a marker trait—types that implement `Unpin` can be moved even when pinned (most types). `Pin<Box<dyn Future>>` is the standard way to store a future that may be self-referential.

### R19 — Hard: Macros
- Declarative macros (`macro_rules!`) use pattern matching on syntax to generate code. They're hygienic—local variables are scoped to the macro invocation, preventing name collisions.
- Procedural macros operate on the token stream and can generate arbitrary code. Three types:
  - Derive macros: `#[derive(CustomTrait)]`
  - Attribute macros: `#[custom_attribute]`
  - Function-like macros: `custom_macro!()`

Procedural macros are more powerful but more complex—they run as compiler plugins. Hygiene rules: `macro_rules!` is hygienic for local variables, but procedural macros must be careful about name collisions since they generate code directly.

### R20 — Hard: Zero-Cost Abstractions
Zero-cost abstractions mean high-level constructs compile to the same machine code as hand-written low-level code:
- **Iterators**: `iter().map().filter().collect()` compiles to an optimized loop without allocation—the compiler inlines and eliminates intermediate steps.
- **Generics (monomorphization)**: `fn foo<T: Trait>(x: T)` generates specialized code for each concrete type—no runtime dispatch overhead.
- **Static dispatch**: `T: Trait` bounds are resolved at compile time, so there's no vtable lookup (unlike `dyn Trait`).

This achieves performance comparable to C because the compiler optimizes away the abstraction layers, leaving only the essential operations.
