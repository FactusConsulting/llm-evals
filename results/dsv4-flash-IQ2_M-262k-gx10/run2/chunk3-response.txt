## OpenTofu / Terraform

**T1** — `tofu plan` performs a dry-run: it compares current state against configuration and shows what will change, without modifying anything. `tofu apply` executes the changes from a plan (or generates a new one) and actually creates/updates/destroys resources.

**T2** — State is a JSON file that maps configuration resources to real cloud objects, storing metadata, dependencies, and attributes. Remote state is critical because it enables team collaboration, provides locking to prevent concurrent writes, protects against local disk loss, and supports CI/CD pipelines.

**T3** — `count` creates a fixed number of resources indexed by integers (0,1,2…). `for_each` creates resources from a map/set, keyed by strings. `for_each` is preferred when keys are meaningful, the set is dynamic, or you need to delete/insert items without reordering side effects.

**T4** — OpenTofu detects drift during `plan` by querying the provider API and comparing actual attributes to state. It will propose reverting the manual change to match configuration (unless `ignore_changes` is set). It does not auto-apply; you must run `tofu apply` to reconcile.

**T5** —
```hcl
resource "aws_instance" "web" {
  for_each      = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t2.micro"
  tags = { Name = each.key }
}
```

**T6** — `terraform_remote_state` reads another root module's state file directly; outputs are the standard module interface. The recommended alternative is to avoid cross-module state coupling entirely and use a shared data store (e.g., database, Consul, or object storage) for shared data. Remote state creates tight coupling, lock contention, and makes modules less reusable.

**T7** — The output is empty because OpenTofu evaluates outputs after the `null_resource` is created, but the `remote-exec` provisioner may not have finished writing the kubeconfig file when the output is read. Fix: add `depends_on` from the output to the `null_resource`, and use a `local-exec` provisioner (or `terraform_data` with a `file` provisioner) to fetch the kubeconfig after the remote command completes. Alternatively, use a `data` source that reads the file only after the resource is ready.

**T8** — `tofu import` imports existing infrastructure into state only; you must manually write matching configuration. Limitations: no config generation, error-prone for complex resources, and requires manual state mapping. The import block (1.5+) lets you declare imports in configuration, making them version-controlled, repeatable, and automatically handled during `plan`/`apply`.

**T9** — Input variables are parameters passed into a module to customize it (defined in `variable` blocks). Outputs are values a module exposes to callers (defined in `output` blocks). Inputs configure; outputs retrieve.

**T10** — A provider is a plugin that translates OpenTofu configuration into API calls for a cloud/API (e.g., AWS, Azure). Without `tofu init`, `tofu plan` fails because provider plugins are not installed.

**T11** — `.terraform.lock.hcl` records exact provider versions and checksums. Committing it ensures all users and CI use identical provider versions, guaranteeing reproducible runs and preventing unexpected upgrades.

**T12** — `tofu destroy` removes all resources in the state (or configuration). To destroy a single resource: `tofu destroy -target=resource_type.name` (e.g., `-target=aws_instance.web`).

**T13** — A data source reads existing information from an external system without creating/modifying anything. Example: `aws_ami` data source to fetch the latest AMI ID instead of hardcoding it—you're not creating the AMI, just reading it.

**T14** — `locals` are internal computed values within a module, not exposed to callers. `variable` blocks accept external input. Use locals for derived values (e.g., concatenating strings, transforming data) to avoid repetition; use variables when you need caller-provided parameters.

**T15** — `lifecycle` block customizes resource behavior:
- `create_before_destroy`: creates replacement before destroying old (zero-downtime VM replacement).
- `prevent_destroy`: blocks destruction (protect a database).
- `ignore_changes`: ignores specific attribute changes (e.g., auto-scaling tags) so OpenTofu doesn't revert external modifications.

**T16** — A `moved` block tells OpenTofu a resource moved from one address to another (e.g., `module.a.foo` → `module.b.foo`). It updates state to the new address without destroying/recreating, preserving resource identity during refactors.

**T17** — OpenTofu builds a dependency graph from references: implicit dependencies arise when one resource references another (e.g., `aws_instance` references `aws_security_group`). Explicit dependencies use `depends_on`. `depends_on` forces ordering and reduces parallelism because dependent resources can't run concurrently. Use it sparingly—it slows apply, adds unnecessary edges, and makes the graph harder to reason about.

**T18** — Strategies to reduce plan time (200+ resources):
1. `-refresh=false` — skips API refresh; faster but misses drift.
2. `-target` — limits plan to specific resources; faster but manual and may miss dependencies.
3. Increase `-parallelism` — more concurrent API calls; faster but risks rate limits.
4. Use `-state` with a local file — avoids remote state latency; but loses team sharing.
5. Combine `-refresh=false` with `-parallelism` — biggest speedup; tradeoff is drift detection loss.

**T19** — State locking uses a backend (e.g., DynamoDB for S3) to prevent concurrent writes. If a lock isn't released (CI crash), subsequent operations fail with a lock error. Manually break with `tofu force-unlock <lock_id>`. Risk: if another process is actually running, you can cause concurrent state corruption. Only break when certain no other process is active.

**T20** — Migration steps:
1. Create S3 bucket and DynamoDB table.
2. Update backend config in `terraform.tf` to `s3` with bucket, key, region, and DynamoDB table.
3. Run `tofu init -migrate-state` — copies local state to S3.
4. Verify state in S3 via `tofu state list` or checking the bucket.
5. Run `tofu plan` to confirm everything works.
6. Verify locking by running `tofu apply` and observing a lock entry in DynamoDB during the run.

## Ansible

**A1** — A playbook is a YAML file defining plays (hosts + tasks). A role is a reusable, organized package of tasks, handlers, variables, and files. A task is a single unit of work (e.g., install a package, copy a file).

**A2** — `ansible_facts` is a dictionary of system info gathered from targets (OS, IP, memory). Access OS family via `ansible_facts['os_family']` (or `ansible_os_family`).

**A3** — `command` executes without shell interpretation (no pipes/redirects). `shell` runs via the shell, enabling pipes/redirects. `raw` executes a raw SSH command without Python on the target. Use `command` for simple commands, `shell` for complex shell operations, `raw` for bootstrapping when Python isn't available.

**A4** — Ansible achieves idempotency by checking current state before acting. Idempotent: `apt: name=htop state=present` (no-op if installed). Not idempotent: `command: echo "hello" >> /tmp/file.txt` (appends every run).

**A5** —
```yaml
- name: Install htop on Debian
  apt: name=htop state=present
  when: ansible_os_family == "Debian"

- name: Install epel-release and htop on RedHat
  yum: name={{ item }} state=present
  loop:
    - epel-release
    - htop
  when: ansible_os_family == "RedHat"
```

**A6** — Variable precedence (lowest→highest): role defaults → group_vars → host_vars → play vars → set_fact/registered → extra_vars. Extra vars override everything; role defaults are the weakest.

**A7** — Use inventory groups: `[rke2_agents]` (all 50) and `[rke2_agents_first]` (first 3). Play 1 targets `rke2_agents_first` with `serial: 1` (or 3). Play 2 targets `rke2_agents` with `serial: 10` and uses `wait_for` to check the first 3 nodes are ready (e.g., port 6443) before deploying the rest.

**A8** — `ansible-vault` encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'secret' --name 'db_password'` and store the output in a vars file. The rest of the file remains plaintext.

**A9** — An inventory file defines hosts/groups Ansible manages. Static inventory is a simple INI/YAML file; dynamic inventory is a script/program that fetches hosts from an external source (cloud API, CMDB).

**A10** —
```bash
ansible webservers -m command -a "df -h"
```

**A11** — A handler is a task that runs only when notified (e.g., restart a service after config change). It differs from regular tasks because it doesn't run unless triggered. Trigger with `notify` in a task:
```yaml
- name: Update config
  copy: ...
  notify: restart nginx
```

**A12** — `ansible.cfg` is the main configuration file. Common settings: `inventory`, `remote_user`, `become`, `forks`, `host_key_checking`, `timeout`.

**A13** — `register` captures a task's output into a variable. Use it in subsequent tasks, e.g., `when: result.rc != 0` or `debug: var=result.stdout`.

**A14** — `include_tasks` dynamically includes tasks at runtime (evaluated when reached, supports conditionals based on facts). `import_tasks` statically imports at parse time (evaluated before play runs, cannot be conditional on runtime facts). Use `include_tasks` for runtime conditionals; `import_tasks` for static inclusion.

**A15** — Ansible Galaxy is a community hub for roles/collections. Create `requirements.yml` listing roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16** — Connection plugins define how Ansible connects. `ssh` connects via SSH to remote hosts (default). `local` runs tasks on the control node without SSH. `network_cli` connects to network devices (routers/switches). Use `ssh` for most hosts, `local` for local ops, `network_cli` for network gear.

**A17** — `delegate_to` runs a task on a specific host (e.g., localhost) instead of the target. `run_once` ensures a task runs only once per play. Example: generate a certificate on the control node using a remote host's IP—delegate to localhost with `run_once: true` to create it once.

**A18** — Performance strategies for 500 hosts:
1. Increase `forks` — more parallel SSH; risks control-node/network overload.
2. Enable pipelining — reduces SSH round trips; requires SSH support.
3. Use fact caching — skips fact gathering; facts may become stale.
4. Use Mitogen — reduces SSH overhead; adds complexity and compatibility concerns.
5. Use `serial` batches — reduces load but increases total time.

**A19** — Jinja2 templating: `{{ }}` outputs a value (variable substitution). `{% %}` is control flow (if/for). `{# #}` is a comment (not output). Template snippet:
```jinja2
upstream backend {
{% for server in backend_servers %}
    server {{ server }};  # {{ server }} health check
{% endfor %}
}
```

**A20** — Zero-downtime rolling deployment:
- Use `serial: 1` (or small batch) to deploy one server at a time.
- Pre-task: remove server from load balancer (via `uri` module calling LB API).
- Deploy the app.
- Post-task: re-register server to LB.
- Health check: use `uri` module to verify the app responds.
- Rollback: wrap deployment in `block`/`rescue`—on failure, run rollback tasks (redeploy previous version, re-register server).
```yaml
- hosts: webservers
  serial: 1
  tasks:
    - block:
        - name: Remove from LB
          uri: ...
        - name: Deploy app
          ...
        - name: Add to LB
          uri: ...
        - name: Health check
          uri: ...
      rescue:
        - name: Rollback
          ...
```
