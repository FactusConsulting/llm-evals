# Go

**G1 — Slice vs array**
An array `[N]T` is a fixed-size **value type**; its length is part of the type and it's copied on assignment/passing. A slice is a **header** (`pointer, len, cap`) referencing a backing array; it's dynamically sized and cheap to pass. When you `append` to a slice at full capacity, the runtime allocates a new backing array (roughly doubling for small caps, ~1.25× growth for large ones), copies the elements over, and returns a new slice header — which is why you must write `s = append(s, x)`. If the slice had spare capacity, `append` writes in place (which can surprise callers sharing the backing array).

**G2 — `var x int` vs `x := 0`**
`var x int` declares `x` with its zero value (`0`); `x := 0` is a short variable declaration whose type is inferred from the initializer (`int` here). You **cannot** use `:=`:
- At package scope (only `var`/`const`).
- Without an initializer.
- To redeclare a variable in the same scope (except that at least one new variable on the left side is allowed in multi-assignment: `a, err := f()` after `a` exists).
- For struct fields, parameters, or type declarations.

**G3 — Goroutines and the GMP scheduler**
A goroutine is a lightweight, runtime-managed coroutine: ~2 KB initial stack that grows/shrinks, cheap creation (hundreds of thousands are practical), multiplexed M:N onto OS threads. The GMP model: **G** (goroutine), **M** (OS thread), **P** (processor — a logical scheduling context holding a local run queue; `GOMAXPROCS` limits Ps). The scheduler work-steals between Ps, parks Ms blocked in syscalls, integrates network I/O via the netpoller, and (since Go 1.14) asynchronously preempts long-running goroutines via signals. Unlike OS threads, context switches are user-space and cheap.

**G4 — Channels**
A channel is a typed, concurrency-safe conduit. **Unbuffered**: send and receive rendezvous — both parties block until the other arrives (synchronous handoff, gives you "happens-before" guarantees). **Buffered**: has capacity `make(chan T, n)`; a send succeeds without a receiver while there's room. Sending to a **full** buffered channel blocks until a receiver drains space. Other rules: receiving from an empty channel blocks; sending to a closed channel panics; receiving from a closed channel yields the zero value with `v, ok := <-ch` giving `ok == false`; a nil channel blocks forever.

**G5 — context**
`context` carries deadlines, cancellation signals, and request-scoped values across API boundaries and goroutine trees. Cancellation propagates downward: cancelling a parent cancels children.

```go
func fetch(ctx context.Context, url string) ([]byte, error) {
    ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return nil, err
    }
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return nil, err // includes context.DeadlineExceeded on timeout
    }
    defer resp.Body.Close()
    return io.ReadAll(resp.Body)
}
```

**G6 — Interface satisfaction**
Go uses **structural typing**: a type satisfies an interface implicitly by implementing its method set — no `implements` declaration. Java/C# use nominal typing: you must explicitly declare implementation. This makes Go interfaces retrofittable (you can satisfy an interface you don't own). `interface{}` (alias `any`, Go 1.18) is satisfied by every type. Powerful: it enabled generic containers, `fmt`, JSON, etc. Dangerous: it erases all static type information — you recover values via type assertions (`v, ok := x.(T)`) that can panic, and mistakes surface at runtime instead of compile time. Prefer generics (Go 1.18+) where possible.

**G7 — Memory model / visibility**
The Go memory model only guarantees that a write in one goroutine is *observed* by a read in another if there is a **happens-before** edge created by synchronization (channel op, mutex, atomic). The example is a **data race**: there's no edge between `ready = true` and the read `for !ready {}`. Consequences are undefined: the compiler may hoist the load out of the loop (infinite loop), the CPU may serve a stale value, and even if `ready` is observed, the write to `data` may not be visible (no ordering guarantee between the two unsynchronized writes). Correct alternatives:
- **Channel**: `done := make(chan struct{}); go func(){ data = "hello"; close(done) }(); <-done` — or send `data` itself over the channel.
- **Mutex**: guard both variables with `sync.Mutex`.
- **Atomics** (Go 1.19+): `var ready atomic.Bool` — Go's atomics are sequentially consistent per the 2022 memory model revision, so `ready.Store(true)` after writing `data`, and `for !ready.Load() {}`, is correct.

**G8 — Mutex vs RWMutex vs sync.Map**
`sync.Mutex` is exclusive. `sync.RWMutex` allows many concurrent `RLock` holders or one writer; a pending writer blocks new readers (writer-starvation avoidance). Use RWMutex only when reads dominate and critical sections are non-trivial — it has higher constant cost and can hurt under write pressure. `sync.Map` keeps a lock-free read map (atomic loads) plus a dirty map promoted on misses; it's optimized for **stable keys after warm-up** (write-once, read-many) or disjoint goroutine key sets. Trade-offs: `sync.Map` is untyped (`any` keys/values), poor for write-heavy or read-modify-write workloads, and its API is limited; a plain `map[K]V` + `sync.RWMutex` is type-safe (especially with generics), simpler, and often faster under mixed workloads. Benchmark your actual pattern.

**G9 — Modules, go.mod/go.sum, MVS**
A module is a versioned unit of dependency management rooted at `go.mod`, which declares the module path, the Go language version, and direct requirements (`require github.com/x/y v1.2.3`). `go.sum` records **content hashes** of each dependency's module zip and go.mod (including indirect ones) so builds verify integrity — it's not a lock file of choices, it's a verification database. `go mod tidy` adds requirements for all imports actually used and removes unused ones, updating both files. **Minimum Version Selection**: starting from the main module's requirements, MVS walks each selected module's own required (minimum) versions; the selected version of each module is the **highest version explicitly required anywhere in the reachable graph** — never a newer one inferred from "latest compatible" semantics like npm. Result: reproducible builds, easy downgrades, and `go list -m all` shows the full build list.

**G10 — defer**
`defer` schedules a call to run when the **surrounding function** returns (arguments are evaluated immediately at the `defer` statement). Multiple defers run in **LIFO** order. Loop gotcha: defers accumulate until function exit — e.g., opening files in a loop and deferring `Close` leaks all of them until the function ends. Fix by wrapping each iteration's body in a function:

```go
for _, f := range files {
    func() {
        fh, err := os.Open(f)
        if err != nil { return }
        defer fh.Close()
        // ...
    }()
}
```

**G11 — Pointers**
A pointer holds the memory address of a value; `*T` is "pointer to T", dereferenced with `*p`, address taken with `&x`. The zero value of any pointer is `nil` (dereferencing nil panics). Pointer to a struct literal: `p := &Point{X: 1, Y: 2}` — composite literals are directly addressable. Methods with pointer receivers require addressable values or explicit pointers.

**G12 — init()**
`init()` runs automatically after package-level variable initialization and before `main()` (or before a test binary runs). Order: imported packages are initialized first (depth-first, dependencies before importers); within a package, files are processed in the order the build system presents them (alphabetical by filename in practice); within a file, multiple `init()` functions run top to bottom. A package may have any number of `init()` functions across files. Avoid heavy logic in `init()` — it makes errors hard to handle (init can't return errors) and complicates testing.

**G13 — make vs new**
`new(T)` works with **any** type: allocates zeroed memory and returns `*T`. `make` works only with **slices, maps, and channels**: it allocates *and initializes* their internal runtime structures and returns an initialized (non-pointer) value — e.g., `make([]int, 0, 10)`, `make(map[string]int)`, `make(chan int, 5)`. A `new(map[string]int)` gives you a pointer to a nil map — useless for writing.

**G14 — Errors**
Errors are values: `type error interface { Error() string }`, conventionally returned as the last result. Idiomatic check: `if err != nil { return fmt.Errorf("doing x: %w", err) }` — `%w` wraps, preserving the chain. `==` compares only the top-level error value, so it fails through wrapping. `errors.Is(err, target)` walks the unwrap chain checking identity/equality against a sentinel (`ErrNotFound`); `errors.As(err, &target)` walks the chain and sets `target` to the first error of a matching **type**, so you can extract structured errors (e.g., `*os.PathError`). Panic for programmer bugs, not expected failures.

**G15 — Composite types and zero values**
- **slice**: `nil` (len 0, cap 0; safe to `len`, `range`, `append`; indexing panics)
- **map**: `nil` (reads return zero values; writes panic — must `make` before writing)
- **channel**: `nil` (send/receive block forever)
- **struct**: each field set to its own zero value (e.g., `sync.Mutex{}` is ready to use — a key Go idiom)

**G16 — Race conditions and -race**
A data race: two goroutines access the same memory concurrently, at least one write, with no synchronization → undefined behavior.

```go
// RACE
var n int
for i := 0; i < 1000; i++ {
    go func() { n++ }() // unsynchronized read-modify-write
}

// Fix 1: mutex
var mu sync.Mutex
go func() { mu.Lock(); n++; mu.Unlock() }()

// Fix 2: channel — single owning goroutine
inc := make(chan int)
go func() { for range inc { n++ } }()
```

`-race` builds with ThreadSanitizer instrumentation: the compiler records memory accesses and the runtime checks whether accesses are ordered by happens-before edges. It detects races **at runtime when the racy code actually executes** (not statically), with ~5–10× CPU and memory overhead — use in tests/CI, not production.

**G17 — select**
`select` waits on multiple **channel operations** (send or receive), blocking until one can proceed; `default` makes it non-blocking. Unlike `switch`, cases are communications, may block, and there's no fallthrough. If **multiple cases are ready, one is chosen uniformly at random** — this prevents starvation and ordering bias. Timeout pattern:

```go
select {
case v := <-ch:
    use(v)
case <-time.After(2 * time.Second):
    return errors.New("timeout")
}
```

(Note: `time.After` in a loop leaks timers until fire; use `time.NewTimer` for long-lived loops.)

**G18 — Escape analysis**
Escape analysis decides whether a value can be proven to never outlive the frame that creates it → **stack** allocation (cheap bump, freed for free); otherwise → **heap** (GC-managed). Values escape when: a pointer to them is returned, stored in an interface, sent on a channel, captured by a closure that outlives the frame, or their size isn't compile-time known. Inspect with:

```
go build -gcflags='-m' ./...        # add -m -m for reasons
```

Output like `&x escapes to heap` vs `moved to heap: x`. It matters because heap allocations drive GC pressure and latency; hot-path code often restructures (value receivers, avoiding interface boxing, preallocating slices, `sync.Pool`) to keep allocations on the stack. Note the analysis is conservative — it may heap-allocate even when escape seems avoidable.

**G19 — reflect**
`reflect` inspects and manipulates values at runtime. `reflect.TypeOf(x)` gives a `reflect.Type` (static type metadata: kind, fields, methods); `reflect.ValueOf(x)` gives a `reflect.Value` (runtime value + type). Mutation requires addressability (`reflect.ValueOf(&x).Elem().CanSet()`); misuse panics. Costs: heavy boxing/allocation, 10–100× slower than direct code, defeats inlining and escape analysis, and loses type safety. Justified when you genuinely need runtime-driven behavior over arbitrary types: `encoding/json`, database drivers, ORMs, test frameworks. Prefer **generics** (Go 1.18+) for type-parameterized logic, or **code generation** (`go generate`, e.g., easyjson, stringer) when you need reflection-like flexibility with compile-time safety and speed.

**G20 — go:embed**
`//go:embed` embeds files into the binary at compile time. The directive sits above a package-level variable of type `string`, `[]byte`, or `embed.FS`:

```go
//go:embed version.txt
var version string

//go:embed static              // directory tree
//go:embed all:templates       // includes _ and . -prefixed files
var assets embed.FS
```

`embed.FS` implements `io/fs.FS` (plus `fs.ReadFileFS`, `fs.ReadDirFS`), so it composes with `fs.ReadFile`, `fs.WalkDir`, `template.ParseFS`, and `http.FileServer(http.FS(assets))`. Limitations: patterns can't reference parent directories or files outside the package's module; empty directories aren't embedded; files starting with `.` or `_` need the `all:` prefix; symlinks aren't followed; content is fixed at build time (grows binary size); variables must be at package scope with no initializer.

# Rust

**R1 — Ownership**
Ownership is Rust's memory-management model: no GC, no manual free — the compiler tracks it. Rules:
1. Every value has exactly one **owner**.
2. At any time, there is only **one** owner (assignment/passing **moves** ownership for non-`Copy` types).
3. When the owner goes out of scope, the value is **dropped** (`Drop` runs, memory freed).

**R2 — String vs &str**
`String` is an owned, heap-allocated, growable UTF-8 buffer. `&str` is a borrowed string slice — a `(ptr, len)` view into any UTF-8 data (a `String`, a `'static` literal, etc.). In signatures: take `&str` for read-only parameters (callers pass both `&String` via deref coercion and literals); return `String` when you create/own new data; return `&str` (with a lifetime tying it to the input) when returning a borrowed view. Rule of thumb: borrow at the boundaries, own at the edges.

**R3 — Borrowing and the borrow checker**
Borrowing lets you use a value without owning it. Rules: at any time you may have **either** any number of shared references `&T` **or** exactly one mutable reference `&mut T` — never both. Mutable references are also exclusive (no aliasing), which is what makes Rust data-race-free and enables aggressive optimization. The borrow checker enforces this at compile time; with non-lexical lifetimes, a borrow ends at its **last use**, not scope end. This statically prevents dangling pointers, iterator invalidation, and data races (interior mutability via `RefCell`/`Cell` moves some checks to runtime for single-threaded cases).

**R4 — Result, Option, and ?**
`Result<T, E>` models recoverable success/failure (`Ok`/`Err`); `Option<T>` models presence/absence (`Some`/`None`). The `?` operator on a `Result`/`Option` unwraps the success value, or returns early from the function, converting the error via `From::from` — so `?` composes with error conversion (`Box<dyn Error>`, custom errors via `thiserror`).

```rust
use std::fs;
use std::io;

fn read_config(path: &str) -> Result<String, io::Error> {
    let contents = fs::read_to_string(path)?; // io::Error propagates
    Ok(contents.trim().to_string())
}
```

**R5 — Box, Rc, Arc**
- `Box<T>`: single-owner heap allocation. Use for recursive types, large values, trait objects (`Box<dyn Trait>`).
- `Rc<T>`: single-threaded reference counting — multiple owners, cloned cheaply, deallocated when the last owner drops. Not `Send`/`Sync`. Use for shared structures in one thread (graphs, caches). For mutation, combine with `RefCell` (`Rc<RefCell<T>>`).
- `Arc<T>`: **atomic** reference counting — safe to share across threads (typically `Arc<Mutex<T>>` / `Arc<RwLock<T>>`). Slightly costlier than `Rc` due to atomic refcount ops.

**R6 — Traits, dyn Trait, and generics**
Traits define shared behavior with explicit `impl Trait for Type` blocks (vs Go's implicit structural satisfaction). Traits additionally support associated types/functions, generic bounds, default methods, and operator impls. **`dyn Trait`** (trait object): dynamic dispatch through a vtable, type erasure, allows heterogeneous collections (`Vec<Box<dyn Trait>>`), requires object safety, has one indirection per call. **`T: Trait`** (generic bound): static dispatch via monomorphization — zero runtime cost, inlinable, but generates code per concrete type (binary bloat) and each generic function instance is monomorphic. Default to generics; use `dyn` when you need heterogeneity or want to shrink code size.

**R7 — Lifetimes**
The function returns a reference, but the compiler can't tell whether it borrows from `x` or `y` — and the answer differs per call — so it can't guarantee the result outlives neither input's data. Lifetimes are annotations describing **relationships between reference lifetimes**; they don't change runtime behavior. Fix:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

This says: the result is valid only as long as **both** inputs are valid. The caller's borrow checker then rejects uses where either input dies too early.

**R8 — Send and Sync**
`Send`: a value can be **moved** to another thread. `Sync`: `&T` is `Send` — safe to share references across threads. These are auto traits, derived structurally. `Rc<T>` is neither: its reference count is a plain non-atomic integer, so two threads cloning/dropping concurrently would corrupt it — a data race. `Arc<T>` uses atomic increment/decrement for the count, making the count manipulation race-free; `Arc<T>` is `Send`/`Sync` only when `T: Send + Sync` (and interior-mutability types like `RefCell` opt out of `Sync`, pushing you to `Mutex`).

**R9 — async/await under the hood**
`async fn` compiles to a **state machine** implementing `Future`: `fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Output>`. Futures are **lazy** — nothing happens until polled. Each `await` is a suspension point where the state machine saves state and returns `Poll::Pending`, registering a `Waker`. An **executor** (Tokio, async-std) maintains a task queue: it polls tasks, and when a task's I/O isn't ready, the reactor (epoll/kqueue/IOCP) registers interest; the waker re-queues the task when readiness fires. Vs goroutines: Go's are **stackful**, preemptively scheduled by the runtime, and invisible in function signatures; Rust's are **stackless**, cooperative (yield only at `.await`), zero-cost when unused, and "colored" (async infects signatures) — but they integrate with no runtime/GC and give explicit suspension points.

**R10 — unsafe**
`unsafe` grants five extra abilities: (1) dereference raw pointers (`*const T`/`*mut T`), (2) call `unsafe` functions or FFI functions, (3) access or mutate `static mut`, (4) implement `unsafe` traits (e.g., `Send`, `Sync` manually), (5) access union fields. Justified for: FFI bindings, implementing fundamental data structures (the internals of `Vec`, `Rc`), performance-critical tricks, and hardware access. The contract: *you* uphold the invariants the compiler normally proves (aliasing, validity, initialization), and you encapsulate the unsafety behind a **safe** abstraction with a sound public API.

**R11 — Pattern matching**
Patterns destructure values: literals, enums (`Some(x)`), structs, tuples, ranges, `|` alternatives, bindings with `@`, guards with `if`. `match` tests a value against multiple patterns and is an expression; `if let` handles a single pattern (concise for "just the `Some` case"). The compiler enforces **exhaustiveness**: every possible case must be covered or you add a `_` wildcard — so adding a new enum variant is a compile error at every non-exhaustive match, which is a major refactoring safety net.

**R12 — Vec vs array**
`[T; N]` is a fixed-size array — length known at compile time, part of the type, lives inline (usually stack), a value type copied on assignment (if `T: Copy`). `Vec<T>` is a heap-allocated growable buffer: `(ptr, len, capacity)`. On `push` beyond capacity, `Vec` allocates a new buffer with (typically) **doubled** capacity, moves elements over, frees the old buffer — giving amortized O(1) push. Preallocate with `Vec::with_capacity(n)` to avoid repeated reallocations.

**R13 — Enums**
Rust enums are **sum types** (algebraic data types): variants can carry different data — `enum Shape { Circle { r: f64 }, Rect { w: f64, h: f64 } }`. C enums are named integers; Java enums are fixed object instances with uniform fields. Rust variants are distinct, pattern-matchable cases with per-variant payloads. `Option<T>` is `Some(T) | None` — the type-level replacement for null. Rust has no null because null is an untracked "absence" that any reference may carry (the billion-dollar mistake); with `Option`, absence is part of the type, and the compiler forces you to handle the `None` case before use.

**R14 — impl blocks**
`impl Type { ... }` defines inherent methods and associated functions. Receiver forms:
- `&self` — immutable borrow; read-only access.
- `&mut self` — exclusive mutable borrow; can mutate.
- `self` — takes ownership; consumes the value (e.g., `into_iter`, builder `build(self)`).

**Associated functions** have no `self` and are called with `::` — typically constructors and helpers: `String::new()`, `Vec::with_capacity(10)`. Separate `impl` blocks are allowed (common for generic-constraint-specific methods).

**R15 — derive**
`#[derive(...)]` auto-generates trait impls via a procedural macro. Commonly derived: `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, `PartialOrd`, `Ord`, `Hash`, `Default`; ecosystem traits like serde's `Serialize`/`Deserialize`. You **cannot** derive when:
- The trait has no derive macro available (e.g., `Display`, `Drop`, `Fn` — these need manual impls).
- A field's type doesn't implement the trait (the generated impl requires all field types to implement it).
- The generated bounds don't fit (generic structs get bounds on every type parameter, which may be too strict — write the impl manually with tighter bounds).
- You need custom semantics (e.g., case-insensitive equality).

**R16 — Cow<'a, T>**
`Cow<'a, T>` is `enum Cow { Borrowed(&'a T), Owned(<T as ToOwned>::Owned) }` — borrow by default, clone only when you must mutate or own. Ideal for functions that usually pass data through unchanged but occasionally transform it:

```rust
use std::borrow::Cow;

fn escape(s: &str) -> Cow<'_, str> {
    if !s.contains('&') {
        return Cow::Borrowed(s);          // zero allocation
    }
    Cow::Owned(s.replace('&', "&amp;"))   // allocate only when needed
}
```

Always returning `String` would allocate on every call; `Cow` makes the common no-op path allocation-free while keeping one return type.

**R17 — Module system**
- `mod foo;` declares a module — inline (`mod foo { ... }`) or loaded from `foo.rs`/`foo/mod.rs`; modules form a tree rooted at the crate.
- `use` creates a shortcut to paths in scope (`use crate::foo::Bar;`).
- `pub` controls visibility (`pub`, `pub(crate)`, `pub(super)`, `pub(in path)`); items are private by default.

Filesystem mapping: `src/foo.rs` is module `foo`; its children live in `src/foo/bar.rs` (or `src/foo/bar/mod.rs`). Edition changes: **2015** required `extern crate` declarations and had quirky path resolution (`mod.rs` mandatory, paths relative to root or current module). **2018** introduced uniform paths: `crate::` for absolute paths, no `extern crate` needed, and `src/foo.rs` + `src/foo/bar.rs` works without `mod.rs`.

**R18 — Pin**
`Pin<P>` wraps a pointer and guarantees the pointee **won't be moved again** until dropped (unless it's `Unpin`). Needed because `async fn` compiles to state machines that may hold **references into their own locals** (self-referential across suspension points) — moving such a struct would leave those internal pointers dangling → undefined behavior. That's why `Future::poll` takes `self: Pin<&mut Self>`: the executor promises not to move the future after first poll. **`Unpin`** is an auto trait meaning "moving is harmless" — true for almost all ordinary types (`i32`, `String`, `Vec`); only types that are self-referential (async futures, `async` blocks) are `!Unpin`. `!Unpin` values must be handled via pinning: `Box::pin(fut)`, the `pin!` macro, or `Pin::new_unchecked` in unsafe code.

**R19 — Macro system**
- **Declarative (`macro_rules!`)**: pattern-match on token trees and expand to code; written in the same style as `match`; great for repetition and small DSLs (`vec![]`).
- **Procedural**: Rust programs transforming `TokenStream → TokenStream`, compiled as separate crates (`proc-macro = true`). Three kinds: **derive** (generate impls for an annotated item, e.g., `#[derive(Serialize)]`), **attribute** (replace/annotate arbitrary items, e.g., `#[tokio::main]`), **function-like** (arbitrary token input, e.g., `sqlx::query!`).

**Hygiene**: `macro_rules!` is *partially* hygienic — local variables introduced inside the macro can't capture or collide with identifiers at the call site, but items and macro names are not hygienic. Procedural macros are **unhygienic**: they manipulate raw tokens, so generated identifiers can collide and authors must be careful (e.g., use `::std` paths, unique names).

**R20 — Zero-cost abstractions**
The principle (Stroustrup's, embraced by Rust): you don't pay for what you don't use, and abstractions compile to the same machine code as hand-written equivalents.
- **Iterators**: `iter().map().filter().sum()` is lazy; combinators fuse into a single loop, and aggressive inlining eliminates closure call overhead and often bounds checks — frequently *faster* than an index-based loop.
- **Generics + monomorphization**: generic functions are compiled separately for each concrete type used, so dispatch is static, calls inline, and there's no vtable or boxing — the abstraction exists only in the source. (Costs: compile time and binary size.)
- **Static trait dispatch**: `T: Trait` bounds resolve at compile time; dynamic dispatch (`dyn Trait`) is opt-in, not the default.
- Plus: no GC, no runtime, deterministic destruction (RAII), and the aliasing guarantees of the borrow checker enable optimizations (e.g., `noalias`) that C compilers can't assume.

The result: high-level, ergonomic code with performance comparable to hand-written C — and when you need to drop lower, `unsafe` is an explicit, auditable boundary rather than the default.
