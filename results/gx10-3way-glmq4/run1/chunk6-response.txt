# JavaScript / TypeScript

**JS1 — var/let/const & hoisting**
- `var`: function-scoped, hoisted and initialized to `undefined`, can be redeclared and reassigned.
- `let`: block-scoped, hoisted but **not initialized** — accessing before declaration throws `ReferenceError` (Temporal Dead Zone). Reassignable, not redeclarable.
- `const`: like `let` but must be initialized at declaration and cannot be reassigned (object *contents* are still mutable).
- **Hoisting**: during compilation, declarations are moved to the top of their scope. `var` gets `undefined`; `let`/`const` are hoisted but stay uninitialized (TDZ); function declarations are fully hoisted (body included); function expressions are not.

**JS2 — Event loop**
The event loop continuously checks: is the **call stack** empty? If yes, drain **all microtasks** (Promise callbacks, `queueMicrotask`, `MutationObserver`), then take **one macrotask** (`setTimeout`, `setInterval`, I/O, UI events), then drain microtasks again, then possibly render. This is why `Promise.resolve().then(...)` runs before `setTimeout(..., 0)` — microtasks always preempt the next macrotask. Long-running synchronous code blocks everything because the loop can't run while the stack is busy.

**JS3 — Closures**
A closure is a function that retains access to its lexical scope even after the outer function has returned.
```js
function counter() {
  let n = 0;
  return () => ++n;   // closes over n
}
```
**Classic bug:**
```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 3 3 3
```
All callbacks share one function-scoped `var i`, which is 3 by the time they run. **Fix:** use `let` (a fresh binding per iteration) or wrap in an IIFE: `((j) => setTimeout(() => console.log(j)))(i)`.

**JS4 — Promises & async/await**
A `Promise` is a state machine: pending → fulfilled/rejected. `async/await` is syntax sugar over promises: `await` pauses the async function (without blocking the thread) and resumes via a microtask. **Error handling:** promises use `.catch()` / `.then(onRejected)`; async/await uses `try/catch` around `await` (rejections become thrown exceptions). Unhandled rejections trigger `unhandledrejection`.
- `Promise.all`: resolves with all values, **rejects immediately** on the first rejection (other results lost).
- `Promise.allSettled`: always waits for all; returns `[{status:'fulfilled', value} | {status:'rejected', reason}]`. Use when you want every outcome (e.g., batch API calls). (Related: `race` = first settled, `any` = first fulfilled.)

**JS5 — interface vs type, discriminated unions**
- `interface`: object shapes only; can be `extends`-ed and `implements`-ed; supports **declaration merging** (redeclaration merges).
- `type`: can express unions, intersections, primitives, tuples, mapped/conditional types; no merging (redeclaration errors).
Use `interface` for public object contracts/classes; `type` for unions, utility types, and anything non-object.
**Discriminated union:** a union of object types sharing a literal "tag" field, enabling exhaustive narrowing:
```ts
type Shape = { kind: "circle"; r: number } | { kind: "rect"; w: number; h: number };
function area(s: Shape) {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "rect":   return s.w * s.h;
  }
}
```

**JS6 — Prototypal inheritance**
Every object has an internal `[[Prototype]]` link. Property lookup walks the chain (`obj → proto → proto… → null`). `Object.create(proto)` creates a new object with `proto` as its prototype (`Object.create(null)` makes a prototype-less dict). ES6 `class` is **syntactic sugar**: methods live on `Class.prototype`, `extends` sets `Child.prototype.__proto__ = Parent.prototype` and `Child.__proto__ = Parent` (for statics), and `super` delegates up the chain. It's delegation, not class-copying like Java.

**JS7 — `this` binding rules (priority order)**
1. **`new` binding** — `this` = the newly created object.
2. **Explicit binding** — `call`/`apply`/`bind` set `this` explicitly.
3. **Implicit binding** — `obj.fn()` → `this` = `obj` (the object left of the dot at call time).
4. **Default binding** — plain call: `undefined` in strict mode, `globalThis` otherwise.
Arrow functions ignore all of these — they capture `this` lexically. **`bind()`** returns a *new* permanently bound function; calling `bind`/`call`/`apply` on it again **cannot change its `this`**. Exception: `new` on a bound function overrides the bound `this` with the new instance.

**JS8 — WeakRef, FinalizationRegistry, WeakMap**
- `WeakRef` holds a reference that doesn't prevent GC; `ref.deref()` returns the target or `undefined` if collected. Use for caches/metadata where losing the value is acceptable.
- `FinalizationRegistry` registers a callback (with a cleanup token) to run *after* an object is collected. Timing is **non-deterministic** — never put correctness-critical logic in finalizers.
- `WeakMap` keys must be objects (or non-registered symbols) because GC tracks entries by **object identity/liveness**: when the key is unreachable, the entry is auto-removed. Primitives have no GC-observable identity, so the engine couldn't know when to drop the entry. This lets you attach metadata to objects without leaking memory.

**JS9 — V8 optimization**
Pipeline: Ignition (interpreter) → Sparkplug/Maglev (baseline/mid-tier) → **TurboFan** (optimizing).
- **Hidden classes (maps):** objects with the same shape share a hidden class; adding properties causes "transitions." Consistent shapes → fast property access.
- **Inline caching:** call sites cache (map, offset) pairs from previous accesses so repeated accesses skip lookups. Monomorphic (one shape) is fastest; megamorphic (many shapes) is slow.
- **Deoptimization:** when runtime reality contradicts compiled assumptions, TurboFan bails back to the interpreter.
**Deopt-inducing patterns:** changing object shape after creation (adding/deleting properties, different property order), `delete obj.x`, mixing element types in arrays, polymorphic function arguments/shapes, leaking `arguments`, `eval`/`with`, try/catch around hot code (historically). Fix: initialize all fields in the constructor, keep shapes consistent, keep call sites monomorphic.

**JS10 — Tree-shaking**
Tree-shaking is dead-code elimination over the **static module graph**. ES Modules have static, hoisted `import`/`export` declarations, so bundlers can parse the graph, mark live exports, and drop unused ones (aided by `"sideEffects": false` in package.json and `/*#__PURE__*/` annotations). **CommonJS can't be effectively tree-shaken** because `require()` is a runtime function call — targets can be dynamic/conditional, `exports` can be assigned arbitrarily at runtime, and side effects are undetectable statically. Bundlers must conservatively include whole CJS modules.

**JS11 — null vs undefined, ==/===, ?? and ?.**
- `undefined`: value not assigned / missing property / absent argument. `null`: deliberate "no value."
- `typeof null === "object"` (historic bug); `typeof undefined === "undefined"`.
- `null == undefined` → **true** (they're only loose-equal to each other); `null === undefined` → **false**.
- `??` (nullish coalescing): returns right side only when left is `null`/`undefined` — unlike `||`, which also triggers on `0`, `''`, `false`.
- `?.` (optional chaining): short-circuits to `undefined` if the left side is nullish (`a?.b`, `a?.()`, `a?.[k]`).

**JS12 — map/filter/reduce/flatMap**
- `map(fn)`: transforms each element → new array of same length.
- `filter(fn)`: keeps elements where predicate is truthy.
- `reduce(fn, init)`: folds array into one value. With `init`, accumulator starts at `init` and every element is processed. Without `init`, accumulator = `arr[0]` and iteration starts at index 1 (throws `TypeError` on an empty array).
- `flatMap(fn)`: `map` then flatten **one level**. Useful for one-to-many transforms and map-then-filter (return `[]` to drop items): `strs.flatMap(s => s.split(','))`.

**JS13 — Template literals & tagged templates**
Template literals (backticks) support interpolation `${expr}` and multiline strings. A **tagged template** calls a function with `(strings, ...values)` where `strings` is a frozen array (with a `.raw` property of unescaped text):
```js
const esc = s => String(s).replace(/[&<>"']/g,
  c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]));
function html(strings, ...vals) {
  return strings.reduce((out, s, i) => out + s + (i < vals.length ? esc(vals[i]) : ''), '');
}
html`<b>${userInput}</b>`; // userInput safely escaped
```
Same pattern powers SQL builders that turn `${value}` into parameter placeholders (`$1`) to prevent injection.

**JS14 — Destructuring**
```js
const { a, b = 10, c: renamed, deep: { x }, ...restObj } = obj;
const [first, , third, ...restArr] = arr;
```
- Object destructuring pulls properties by name; `c: renamed` renames; `b = 10` is a **default applied only when the value is `undefined`** (not `null`).
- Array destructuring is positional; holes skip elements.
- Rest (`...`) collects remaining properties/elements into a new object/array and **must be last**. Works in parameters, too: `function f({ name, age = 0 }) {}`.

**JS15 — for...in vs for...of**
- `for...in` iterates **enumerable string keys**, including inherited ones — for objects, not data.
- `for...of` iterates **values** of any iterable (arrays, strings, Maps, Sets, generators) via `Symbol.iterator`.
Avoid `for...in` on arrays: keys are strings (`"0"`, `"1"`), it walks the prototype chain (picks up anything added to `Array.prototype`), and it's slower. Use `for...of`, `forEach`, or index loops.

**JS16 — Generics, constraints, conditional types, infer**
```ts
// Generic + constraint (extends)
function get<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }

// Conditional type
type NonNullish<T> = T extends null | undefined ? never : T;

// infer — extract a type inside a pattern
type Unwrap<T> = T extends Promise<infer U> ? U : T;      // Unwrap<Promise<string>> = string
type Elem<T>   = T extends (infer E)[] ? E : never;        // Elem<number[]> = number
```
Constraints limit `T` to types with required members; conditional types choose types at compile time; `infer` declares a type variable to be solved by pattern matching (the basis of `ReturnType`, `Awaited`, etc.).

**JS17 — Module systems**
- **CommonJS**: `require()`/`module.exports` — runtime, synchronous, dynamic; the de facto Node legacy format.
- **ESM**: `import`/`export` — statically parsed, hoisted, async loading, **live bindings** (imports reflect reassignments), top-level `await`.
- **Node handling**: file extension + nearest `package.json` decide. `"type": "module"` makes `.js` files ESM; `.mjs` is always ESM, `.cjs` always CJS. ESM can `import` CJS (default export = `module.exports`, named exports via static analysis); CJS can load ESM only via dynamic `import()` (synchronous `require(esm)` exists only in very recent Node).

**JS18 — Structural typing, excess properties, extends vs satisfies, variance**
TypeScript compares **shapes**, not names: `{x: number}` is assignable to any type needing `{x: number}` regardless of declaration origin.
- **Excess property checks** apply only to *fresh object literals* directly assigned to a typed target — unknown properties error. Assigning via an intermediate variable bypasses the check (a known escape hatch).
- **`extends`** constrains/derives a type (erases to the constraint for checking). **`satisfies`** validates a value against a type **while preserving its inferred literal type**:
```ts
type Cfg = Record<string, string | number>;
const c = { port: 8080 } satisfies Cfg;  // c.port is still number, not string|number
```
- **Variance (TS 4.7+)**: `in`/`out` annotations on type parameters declare contravariant (input) / covariant (output) positions — e.g., `interface Producer<out T>` — improving correctness checks and editor hints for complex generic types.

**JS19 — Proxy & Reflect**
`Proxy` wraps a target and intercepts operations via traps (`get`, `set`, `has`, `deleteProperty`, `apply`, `construct`, …). `Reflect` exposes the default behavior for each trap, so you can intercept, do something, then delegate:
```js
function validate(obj, schema) {
  return new Proxy(obj, {
    set(target, prop, value, receiver) {
      if (schema[prop] && typeof value !== schema[prop])
        throw new TypeError(`${String(prop)} must be ${schema[prop]}`);
      return Reflect.set(target, prop, value, receiver);
    },
    get(target, prop, receiver) {
      console.log(`read ${String(prop)}`);
      return Reflect.get(target, prop, receiver);
    }
  });
}
```
This is the mechanism behind Vue 3 reactivity (track on `get`, trigger on `set`) and validation/logging layers. Function calls are intercepted with the `apply` trap.

**JS20 — SharedArrayBuffer & Atomics**
`SharedArrayBuffer` is a fixed-length raw byte buffer that can be **shared** between the main thread and Workers (`postMessage(worker, [sab])`) — both get views over the same memory (in browsers this requires cross-origin isolation via COOP/COEP headers). Plain concurrent reads/writes race, so `Atomics` provides:
- **Read-modify-write ops**: `add`, `sub`, `and/or/xor`, `exchange`, `compareExchange` (CAS — the basis of lock-free algorithms and mutexes).
- **Ordering guarantees**: atomic ops are **sequentially consistent**; plain (non-atomic) accesses may be reordered around them, so use `Atomics.load`/`store` as synchronization points for handoff.
- **`Atomics.wait(typedArray, index, expected, timeout)`**: blocks the current thread until the value at `index` changes from `expected`, someone calls `notify`, or timeout (futex-style). **Not allowed on the browser main thread** — workers only. **`Atomics.notify`** wakes `count` waiting threads. Typical pattern: a spin/sleep mutex or a work queue index guarded by `compareExchange`.

# Bash

**B1 — $@ vs $***
- Unquoted `$@` and `$*`: identical — expand to all positional params, then undergo word splitting (dangerous).
- `"$*"`: all params joined into **one string**, separated by the **first character of IFS** (default space).
- `"$@"`: each parameter stays a **separate word**, preserving original boundaries.
Rule: always use `"$@"` when forwarding arguments.

**B2 — set -euo pipefail**
- `-e`: exit immediately if a command fails (not inside `if`/`while` conditions, `&&`/`||` chains, or negated commands).
- `-u`: error on expansion of unset variables (catches typos like `$HOAST`).
- `-o pipefail`: a pipeline's exit status is the **rightmost non-zero** exit (normally only the last command's status matters).
Together: fail fast, fail loudly, don't let mid-pipeline failures hide.

**B3 — $( ) vs backticks; $(( )) vs expr**
- `$(command)` is preferred: **nestable**, predictable backslash handling; backticks can't nest cleanly and have confusing escaping rules.
- `$((expr))` is native shell arithmetic (no quoting/escaping issues, `$((1+2*3))`); `expr` is an external process, needs `expr 1 \* 2` escaping, and is slow. Use `$(( ))` (or `(( ))` for assignment/conditions).

**B4 — Process substitution**
`<(command)` runs the command and connects its output to a `/dev/fd/...` path (or FIFO), so a command that requires a *filename* can read a stream. Classic use:
```bash
diff <(sort file1) <(sort file2)
```
Also lets you feed a `while read` loop without a subshell: `while read -r line; do ...; done < <(grep pattern file)` — variables set inside survive.

**B5 — Iterating files safely**
```bash
for f in *; do            # globbing — no word splitting on the result
  [[ -e $f ]] || continue
  process "$f"            # always quote
done
# or, for recursion / null-safe streaming:
find . -type f -print0 | while IFS= read -r -d '' f; do process "$f"; done
```
`for f in $(ls)` is dangerous because command substitution undergoes **word splitting and glob expansion** — filenames with spaces break into multiple items, globs in filenames expand, and `ls` output shouldn't be parsed at all.

**B6 — Heredoc vs here-string**
- `<<EOF ... EOF`: feeds a multi-line block to stdin until the delimiter line.
- `<<<string`: feeds a single string (plus newline) to stdin: `grep root <<<"$line"`.
- `<<-EOF`: strips **leading tabs only** (not spaces) from the block, allowing indented scripts.

**B7 — Redirection order matters**
```bash
cmd > file 2>&1   # stdout → file; then stderr → wherever stdout points now (file). Both in file. ✔
cmd 2>&1 > file   # stderr → current stdout (terminal); then stdout → file. stderr still on terminal. ✘
cmd &> file       # bash shorthand: both → file (same as first form)
```
Redirections are processed **left to right**; `2>&1` duplicates *where fd 1 points at that moment*, not "fd 1 forever."

**B8 — Safe lock file**
```bash
#!/usr/bin/env bash
set -euo pipefail
LOCK=/tmp/myscript.lock

cleanup() { rm -rf "$LOCK"; }
trap cleanup EXIT
trap 'exit 143' TERM    # 128+15 → triggers EXIT trap
trap 'exit 130' INT

if ! mkdir "$LOCK" 2>/dev/null; then
  echo "Already running (pid $(cat "$LOCK/pid" 2>/dev/null || echo '?'))" >&2
  exit 1
fi
echo $$ > "$LOCK/pid"

# ... work ...
```
**Why `mkdir`:** the `mkdir` syscall is **atomic** — the kernel guarantees exactly one caller wins; there is no check-then-create race. `echo $$ > lockfile` is two steps (open/truncate then write) and always "succeeds," so two processes can both hold the lock. (Alternative: `set -C; : > lock` uses `O_EXCL`, but `mkdir` is simpler and cleanup via `rm -rf` is trivial.) The `exit N` in signal traps ensures the `EXIT` trap runs on SIGTERM/SIGINT.

**B9 — Quoting**
```bash
name="world"
echo 'hello $name'   # hello $name   — fully literal
echo "hello $name"   # hello world   — $, `, \, ! expand; spaces preserved
echo hello   $name   # hello world   — but unquoted $name would word-split/glob
```
Unquoted expansions split on IFS and expand globs — the root of most bash bugs. Quote everything unless you specifically need splitting/globbing.

**B10 — File tests, [ ] vs [[ ]]**
`-e` exists, `-f` regular file, `-d` directory, `-r`/`-w`/`-x` readable/writable/executable, `-s` non-empty, `-L` symlink.
```bash
[[ -d "$path" ]] && echo dir
```
- `[ ]` (POSIX `test`): plain command; variables undergo word splitting/globbing (must quote); `&&`/`||` unusable inside (use `-a`/`-o`).
- `[[ ]]` (bash keyword): no splitting/globbing, supports `&&`, `||`, `<`/`>` string comparison, unquoted pattern matching, and `=~` regex.

**B11 — $?, $$, $!, $#**
- `$?`: exit status of last command → error checking: `cmd || { echo fail; exit $?; }`.
- `$$`: current shell's PID → writing pidfiles, temp-file names.
- `$!`: PID of the most recent background job → `wait $!`, `kill $!`.
- `$#`: number of positional parameters → argument validation: `[[ $# -lt 1 ]] && usage`.

**B12 — Functions**
```bash
foo() {            # POSIX form
  local x=$1
  echo "result"    # stdout = "return value" via $()
  return 0         # exit status, 0–255
}
function foo { }   # bash keyword form — functionally identical
```
`foo() {}` is POSIX; `function foo {}` is a bash/ksh extension; both behave the same. **Returning values:** (1) `return N` sets the exit status (check with `$?`); (2) `echo`/`printf` to stdout, captured with `out=$(foo)`; (3) set globals; (4) namerefs (`declare -n`) for "by reference" output.

**B13 — PATH, command resolution, builtins**
`PATH` is a colon-separated list of directories searched **in order**; the first executable match runs. Resolution order: aliases → functions → builtins → PATH. Builtins (`cd`, `echo`, `read`) execute inside the shell process (no fork, can change shell state like `cd`); externals are separate binaries. Check with:
```bash
type -a ls     # shows all matches: alias / builtin / each PATH hit
command -v cd  # script-safe existence check
```
Bash caches resolved paths in a hash table (`hash -r` clears it after installing new binaries).

**B14 — trap**
```bash
trap 'cleanup; exit' EXIT        # runs on any shell exit
trap 'echo failed' ERR           # needs set -e or set -E (errtrace) to inherit in functions
trap 'graceful_stop' INT TERM
trap '' HUP                       # ignore a signal
trap - INT                        # reset to default
```
Bash **defers** trap execution until the current foreground command finishes. Signals arriving while a trap runs are queued; multiple pending signals execute one at a time (repeated identical signals may coalesce into one trap run). When a signal causes exit, the signal trap runs first, then the `EXIT` trap.

**B15 — xargs vs command substitution**
Command substitution embeds output into a command line — subject to word splitting, globbing, `ARG_MAX` limits, and trailing-newline stripping. `xargs` reads stdin and **builds argument lists**, batching items into as few invocations as possible:
```bash
find . -name '*.log' -print0 | xargs -0 -n 50 gzip      # null-safe, batched
find . -name '*.log' -print0 | xargs -0 -P 4 -n 1 gzip  # 4 parallel workers
```
`-print0`/`-0` handle filenames containing spaces **and newlines** (NUL is the only byte illegal in filenames). `-I{}` substitutes per-item (implies one item per line). xargs exits **123** if any invocation failed — check it for error propagation.

**B16 — Arrays & associative arrays**
```bash
arr=(a "b c" d)          # indexed, 0-based, sparse allowed
arr+=(e)                 # append
echo "${arr[@]}"         # iterate values (quoted!)
echo "${#arr[@]}"        # length
for v in "${arr[@]}"; do echo "$v"; done

declare -A h             # bash 4+; must declare
h[key1]="value 1"
h+=( [key2]=v2 )
for k in "${!h[@]}"; do echo "$k -> ${h[$k]}"; done
echo "${#h[@]}"
```
Indexed arrays are **ordered** with non-negative integer keys; associative arrays are **unordered** key→value maps with arbitrary string keys. Both use the same expansion idioms; `"$*"` vs `"$@"` semantics apply to arrays too.

**B17 — Subshell vs group command**
- `( ... )`: forks a **subshell** — a copy of the shell. Variable/`cd`/option changes are discarded; exit status is the subshell's last command. Useful for isolating side effects (`(cd dir && make)`).
- `{ ...; }`: runs in the **current shell** — changes persist; requires a space after `{` and a trailing `;`/newline.
**Piping into `while`:** each pipeline element runs in a subshell, so `cmd | while read...; count++ done` loses `count`. Fixes: `while ...; done < <(cmd)` (process substitution keeps the loop in the current shell), here-docs/files as input, or `shopt -s lastpipe` (bash 4.2+, with job control off).

**B18 — Signals & graceful shutdown**
- `SIGINT` (2): Ctrl-C from the terminal; catchable.
- `SIGTERM` (15): default `kill` — "please terminate"; catchable.
- `SIGHUP` (1): terminal hangup/closed (also a reload convention for daemons); catchable.
- `SIGKILL` (9): **cannot be caught, blocked, or ignored** — the kernel reaps the process; no cleanup possible.
Graceful pattern:
```bash
pids=()
cleanup() { kill "${pids[@]}" 2>/dev/null; wait; }
trap cleanup EXIT
trap 'exit 143' TERM INT
worker & pids+=($!)
wait   # reap children; propagate failures via $?
```
For whole trees, run the script in its own process group (`setsid`) and `kill -- -$$` to signal all children.

**B19 — Parallel log processing**
```bash
#!/usr/bin/env bash
set -euo pipefail
IN=$1; JOBS=4
WORK=$(mktemp -d); trap 'rm -rf "$WORK"' EXIT

split --numeric-suffixes=1 -n l/"$JOBS" "$IN" "$WORK/chunk."

process_chunk() {
  grep 'ERROR' "$1" | awk '{print $5}' | sort | uniq -c > "$1.out"
}
export -f process_chunk

find "$WORK" -name 'chunk.[0-9]*' ! -name '*.out' -print0 |
  xargs -0 -P "$JOBS" -n 1 -I{} bash -c 'process_chunk "$1"' _ {}

# error propagation: xargs exits 123 if any child failed
rc=$?; [[ $rc -eq 0 || $rc -eq 123 ]] || exit "$rc"

cat "$WORK"/chunk.*.out | sort -k2,2 | awk '{s[$2]+=$1} END {for (k in s) print s[k], k}' > results.txt
```
**Trade-offs:** parallelism helps only if work is CPU-bound or per-file overhead dominates; on one spinning disk, parallel reads can *hurt*. `split -n l/N` splits by lines (no broken records). **Error propagation:** check xargs' 123 exit code, or have each chunk write a `.status` file and verify all succeeded before merging. Numeric suffixes keep merge order deterministic.

**B20 — exec & FD manipulation & coprocesses**
- `exec cmd` **replaces** the shell process image — no return, no cleanup, the shell is gone. Used to hand off PID/signals (e.g., wrapper scripts: `exec realapp "$@"`).
- `exec` with only redirections changes the *current shell's* FDs:
```bash
exec 3>file      # open fd 3 for writing
echo hi >&3
exec 3>&-        # close fd 3
exec 3<&0        # duplicate stdin onto fd 3 (save/restore pattern)
```
- **Coprocess** runs a background command with bidirectional pipes:
```bash
coproc SQL { sqlite3 db.sqlite; }
echo "SELECT 1;" >&"${SQL[1]}"     # write to its stdin
read -r line <&"${SQL[0]}"         # read its stdout
```
Use when a helper program has expensive startup (DB CLIs, ssh connections, interpreters) and you need many request/response exchanges without respawning it.

# PowerShell

**PS1 — Write-Output vs Write-Host**
`Write-Output` writes to the **success stream (1)** — real pipeline objects that can be captured (`$x = ...`), filtered, and redirected. `Write-Host` writes to the **information stream (6)** (since v5) straight to the console — it is *not* captured by variable assignment and pollutes nothing in the pipeline, but it also can't be processed. Rule: functions should **output data** (`Write-Output`/implicit output) and reserve `Write-Host`/`Write-Information` for user-facing status messages.

**PS2 — Pipeline; ForEach-Object vs foreach**
The pipeline streams objects one at a time from cmdlet to cmdlet, enabling constant memory for large datasets. `ForEach-Object` is a **cmdlet**: works mid-pipeline, supports `-Begin/-Process/-End`, `-Parallel` (v7), and shorthand like `-MemberName`; uses `$_`. The `foreach` **statement** is a language construct: faster on in-memory collections, supports `break`/`continue` cleanly, but must materialize its collection and can't receive pipeline input directly. Use `foreach` for speed on arrays you already have; `ForEach-Object` for streaming pipelines and low memory.

**PS3 — [PSCustomObject] vs [hashtable]**
- `[PSCustomObject]`: **ordered** properties, clean member access, predictable JSON/CSV/format-table output, case-insensitive property names. Best for structured records and pipeline output.
- `[hashtable]`: key→value lookup (O(1)), unordered, keys case-insensitive by default; best for lookups/dictionaries. (`[ordered]@{}` gives an ordered dictionary.)
Convert: `[pscustomobject]$ht` (keys → properties); back: iterate `$obj.PSObject.Properties` and build a hashtable.

**PS4 — Error handling**
- **Terminating errors** stop execution and are caught by `try/catch` (cmdlet errors, `throw`, runtime exceptions).
- **Non-terminating errors** write to the error stream and execution **continues** — `catch` never sees them unless promoted.
- `-ErrorAction` (per cmdlet) overrides `$ErrorActionPreference` (scope-wide; default `Continue`). `-ErrorAction Stop` promotes a non-terminating error to terminating so `try/catch` works. `SilentlyContinue` suppresses but logs to `$Error`; `Ignore` suppresses entirely. Also useful: `-ErrorVariable`, `$Error[0]`, and `throw` for deliberate terminating errors.

**PS5 — Splatting**
```powershell
$params = @{
  Path     = 'C:\logs'
  Filter   = '*.log'
  Recurse  = $true
}
Get-ChildItem @params      # @ splats: each key binds to a parameter
```
`@params` binds each key as an individual named parameter; passing `$params` would try to bind the whole hashtable to a *single* parameter. Arrays can be splatted for positional parameters, and `$PSBoundParameters` can be re-splatted to forward parameters.

**PS6 — Remoting**
- `Invoke-Command -ComputerName`: one-off remote execution (one-to-many with `-ComputerName (Get-Content servers.txt)`); returns **deserialized** objects.
- `Enter-PSSession`: interactive remote shell (one-to-one), like SSH; `Exit-PSSession` to leave. Both build on **PSSessions** (`New-PSSession`).
- Protocol: **WS-Management (WinRM)** over HTTP 5985 / HTTPS 5986. PowerShell 6+/7 adds **SSH-based remoting** (`New-PSSession -HostName x -UserName y`, port 22), which is cross-platform and key-based.

**PS7 — Pipeline unrolling**
PowerShell **enumerates** collections a function emits. `$result = @(); $result += "one"; return $result` emits one string, which unrolls to a scalar — so `$x.GetType().Name` is **`String`**, not `Object[]`. If the function returns **0 items**, `$x` is `$null` and `$x.GetType()` throws ("You cannot call a method on a null-valued expression"). Correct patterns:
```powershell
$x = @(Get-Items)                       # caller guarantees array
# or inside the function:
$result = foreach ($i in 1..3) { $i }   # pipeline assignment collects output
return ,$result                          # comma prevents unrolling (or Write-Output -NoEnumerate)
```
Always code defensively: `@()` at the call site, and never assume a function returns an array.

**PS8 — Scriptblocks, remote execution, double-hop**
A `[scriptblock]` is an anonymous, reusable unit of PowerShell code (`& $sb` to invoke); a function is a named command with its own scope and parameter binding. Remotely: `Invoke-Command -ScriptBlock $sb -ArgumentList $a,$b` — the scriptblock is **serialized as text** and executed on the target; local variables are *not* captured (use `$using:a` or bind them via `param()` from `-ArgumentList`).
**Double-hop problem:** with NTLM/Kerberos, your credential authenticates you to machine A, but A cannot re-delegate it to machine B (network share, SQL, second remote call). Solutions: **CredSSP** (explicitly delegates credentials to the remote — powerful but a credential-theft risk; enable on client *and* server), **Kerberos constrained/resource-based delegation** (preferred), passing explicit credentials via `$using:` and `-Credential`, or gMSA service accounts.

**PS9 — @() and arrays**
`@(...)` is the **array subexpression operator** — it guarantees the result is an array (`@(Get-ChildItem)`), even for 0 or 1 items. `[array]` is just the type accelerator for `System.Array` (casts/constraints). Force a single result into an array: `@($x)` or `,$x` (unrolling-proof when returning). Indexing: `@()[0]` and `$null[0]` both return `$null` **silently** (no error); in PS3+ `$null.Count` returns `0` (special-cased), which can mask bugs — test with `if ($x)` or `$x.Count -gt 0` carefully.

**PS10 — Comparison operators**
`-eq`, `-ne`, `-gt/-lt/-ge/-le`, `-like` (wildcards `* ? []`), `-match` (regex; populates `$Matches`; on a collection it *filters* it), `-contains` (collection on the **left** contains value), `-in` (value on the **left** is in collection on the right). All are **case-insensitive** by default for strings; prefix `c` for case-sensitive: `-ceq`, `-clike`, `-cmatch`, `-ccontains`, `-cin` (and `i`-prefixed explicit insensitive forms exist).
```powershell
$list -contains 3    # collection -contains value
3 -in $list          # value -in collection
```

**PS11 — Modules**
A module is a reusable package of commands. **Script module** (`.psm1`): functions/workflows in a script file. **Manifest** (`.psd1`): metadata — `RootModule`, `ModuleVersion`, `FunctionsToExport`, `RequiredModules`, compatible PSEditions, dependencies. **Binary module**: compiled .NET assembly (`.dll`) exporting cmdlets written in C#. `Import-Module` loads the root module per the manifest and exports only what the manifest allows; **module autoloading** discovers commands in `$env:PSModulePath` on first use without explicit import.

**PS12 — String interpolation**
- `'...'`: fully literal, no interpolation.
- `"..."`: interpolates `$var` and property access `"$obj.Name"`; anything more complex needs a subexpression: `"$($obj.Name.ToUpper())"` — note `"$a[0]"` interpolates `$a` then literal `[0]`, so use `"$($a[0])"`.
- Here-strings for multiline: `@" ... "@` (interpolated) and `@' ... '@` (literal); the closing `"@` must be at line start. For complex formatting, prefer `-f` format operator.

**PS13 — Get-Member & object exploration**
`Get-Member` shows an object's type and members: pipe any object into it (`$proc | Get-Member`). Member types: **Property** (native .NET property via the adapter), **NoteProperty** (static value added by PowerShell — e.g., by `Select-Object` or `Add-Member`), plus AliasProperty/ScriptProperty/CodeProperty; **Methods** are invokable code. `Select-Object` **projects** — builds new objects with chosen properties (`Select-Object -First 5`, `-ExpandProperty`); `Where-Object` **filters** which objects pass through the pipeline.

**PS14 — PowerShell classes (v5+)**
Classes are real .NET types defined in PowerShell: constructors, methods, properties, inheritance (single, from PS or .NET classes), static members, `hidden`. **Limitations vs C#:** you cannot call cmdlets directly inside class methods (must wrap via `$ExecutionContext` or helper functions), you can *implement* existing interfaces but cannot *define* new ones, no generics, no pipeline integration (methods can't emit pipeline output naturally), limited parameter validation, and no support in older tooling. **Use classes** for structured state, DSC resources, type-safe helpers and overloads; **use functions** for pipeline-centric, admin-facing commands.

**PS15 — CmdletBinding & advanced functions**
`[CmdletBinding()]` turns a function into an **advanced function**: it gains common parameters (`-Verbose`, `-Debug`, `-ErrorAction`, `-WarningAction`), rejects unknown parameters, exposes `$PSCmdlet`, and enables parameter attributes (`[Parameter(Mandatory, Position=0, ParameterSetName='X', ValueFromPipeline)]`, `ValidateSet`, `ValidateNotNullOrEmpty`, …).
- `SupportsShouldProcess` adds `-WhatIf`/`-Confirm`; guard mutations with `if ($PSCmdlet.ShouldProcess($target, $action))`.
- `DefaultParameterSetName` disambiguates when parameters can't.
- `ValueFromPipeline` binds pipeline objects to a parameter.
- **`Begin`** runs once before input (setup), **`Process`** once *per pipeline object* (or once if no input), **`End`** once after (cleanup/final output).

**PS16 — Providers**
Providers expose heterogeneous data stores as hierarchical **drives** navigable with the same cmdlets. `Get-ChildItem` works on any provider implementing container/content cmdlets: `FileSystem` (files), `Registry` (`HKLM:\`, `HKCU:\` — keys as "items", values as item *properties*), `Certificate` (`Cert:\CurrentUser\My`), `Environment` (`env:`), `Variable`, `Function`. Registry-as-filesystem:
```powershell
Set-Location HKLM:\SOFTWARE\Microsoft
Get-ChildItem
Get-ItemProperty .\Windows\CurrentVersion   # read values
```
Discover with `Get-PSProvider` and `Get-PSDrive`.

**PS17 — Runspaces & parallelism**
A **runspace** is an isolated execution environment (its own session state); the console host runs one by default. `[runspace]::Create()` makes one; `[runspacepool]::CreateRunspacePool(min,max)` manages a reusable pool; `[powershell]::Create()` builds an invokable pipeline bound to a runspace (`AddScript`, `BeginInvoke`/`EndInvoke` with `IAsyncResult`). **Thread safety:** each runspace is single-threaded and objects aren't shared across runspaces — share state only via synchronized collections (`[hashtable]::Synchronized(@{})`).
- `ForEach-Object -Parallel` (PS7) manages runspaces for you: `$using:` for variables, `-ThrottleLimit` (default 5) — the easy path.
- Manual runspace pools give finer control (long-lived workers, custom initial session state) at the cost of boilerplate. Middle ground: `Start-ThreadJob` (runspace-based, much cheaper than `Start-Job`'s separate process).

**PS18 — PSScriptAnalyzer**
A static-analysis linter enforcing style and best practices: rules like `PSAvoidUsingCmdletAliases`, `PSAvoidUsingWriteHost`, `PSUseApprovedVerbs`, `PSAvoidUsingPlainTextForPassword`. **Severity levels:** Error, Warning, Information — configurable per rule. **Custom rules** ship as modules loaded via `CustomRulePath` (rule functions analyzing the AST). **Suppression:** `[Diagnostics.CodeAnalysis.SuppressMessageAttribute('PSAvoidUsingWriteHost', '')]` in code, or `ExcludeRules`/`IncludeRules` in a settings file (`Invoke-ScriptAnalyzer -Settings pssa.psd1`). **CI/CD:** run `Invoke-ScriptAnalyzer -Path . -Recurse -EnableExit` (non-zero exit on findings) in Azure DevOps/GitHub Actions gates; `Invoke-Formatter` auto-fixes style rules.

**PS19 — $using: vs -ArgumentList; serialization limits**
- `$using:` references **local variables** inside remote/scriptblock code — works with `Invoke-Command`, `Start-Job`, and `ForEach-Object -Parallel`. Values are captured (snapshotted) at invocation/job-creation time.
- `-ArgumentList` passes values **positionally** into the scriptblock's `param()` block (or `$args` if no param block); used with `Invoke-Command` and `Start-Job` (`ForEach-Object -Parallel` uses `$using:` instead).
- **Serialization:** objects crossing a remoting/job boundary are serialized (CLIXML in Windows PowerShell 5.1 remoting; PS7 uses its own serialization). You get **deserialized** objects: properties survive, **methods are gone**, and deeply nested structures are truncated by serialization **depth limits** — nested collections/objects beyond the depth get flattened or cut off. Consequences: `$file.Delete()` fails remotely; complex live objects (AD, WMI, FileInfo) should be re-fetched locally or reduced with `Select-Object` to the properties you actually need.

**PS20 — DSC**
DSC is declarative IaC: a **Configuration** (PowerShell-like keyword with `Node` blocks) compiles to **MOF** documents describing desired state; **Resources** are idempotent building blocks (`File`, `Registry`, `Service`, `WindowsFeature`, `Script`, plus community modules) that each implement `Get/Set/Test-TargetResource`. The **Local Configuration Manager (LCM)** is the on-node engine that applies MOFs and can continuously enforce them — its meta-configuration sets `ConfigurationMode` (`ApplyOnly`/`ApplyAndMonitor`/`ApplyAndAutoCorrect`), `RefreshMode` (`Push`/`Pull`), reboot behavior, and pull-server targets.
**Windows PowerShell vs PS7:** full DSC (LCM, MOF, pull server) exists only in **Windows PowerShell 5.1**; PowerShell 7 does not include the DSC engine. **DSC v3** is a separate, cross-platform, JSON-based tool (no LCM/MOF) that can invoke classic PS resources via adapters.
**Modern landscape:** in practice most organizations moved to **Terraform, Ansible, Pulumi, or Chef** for IaC; Azure's **machine configuration (guest configuration)** is the cloud-hosted evolution of DSC enforcement.
