## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the cluster upgrade shifted the namespace from the **Baseline** to the **Restricted** Pod Security Standard (PSS). Under **Baseline**, pods are allowed to run as root if the image specifies it. Under **Restricted**, the policy requires `runAsNonRoot: true` AND that the container does not run as the root user. Because the new base image (`chainguard/static`) defaults to `USER root` and the manifest lacks an explicit `runAsUser` (non-zero ID), the Kubelet attempts to start the container as root. The Restricted policy intercepts this and prevents the pod from starting, leading to a `CrashLoopBackOff` (or `CreateContainerConfigError`).

**SC1-B:**
```bash
kubectl get pods -A | grep CrashLoopBackOff | awk '{print $1 ":" $2}' | xargs -I {} sh -c "kubectl get pod ${{}% : *} -n ${{}#*: } -o json | jq '.items[0].spec.securityContext // .items[0].spec.containers[0].securityContext'"
```
*(Note: A more robust version using `jsonpath` for all pods:)*
```bash
kubectl get pods -A -o json | jq '.items[] | select(.status.containerStatuses[0].state.waiting.reason == "CrashLoopBackOff") | {ns: .metadata.namespace, name: .metadata.name, sc: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level fix:** Update the Dockerfile of the base image or the application image to include `USER 1000` (or any non-zero UID).
*   **Manifest fix:** Explicitly set `securityContext: { runAsUser: 1000, runAsNonRoot: true }` in the Deployment spec.
*   **CI Pipeline Gate:** Implement a **Kyverno** or **OPA Gatekeeper** policy in the CI pipeline (via `conftest`) that validates manifests against the Restricted PSS before merging.
*   **Rollout:** Use a `RollingUpdate` strategy. Since the issue is a security policy violation, the new pods will fail to start, and the old (healthy) pods will remain until the manifest/image is fixed, ensuring no downtime.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is caused by **asynchronous replication lag**. In cross-region RDS, the primary ships WAL (Write Ahead Log) logs to the replica asynchronously. At the moment of the outage, some transactions committed in `us-east-1` had not yet reached `eu-west-1`. Promoting the replica results in the loss of those "in-flight" transactions. To quantify the loss, I would compare the `pg_current_wal_lsn()` of the old primary (if accessible) with the `pg_last_wal_receive_lsn()` of the promoted replica.

**SC2-B:**
1.  **Import:** `terraform import aws_db_instance.primary <new_rds_instance_id>`
2.  **State Cleanup:** `terraform state rm aws_db_instance.old_primary`
3.  **Update:** Update the variable/hardcoded ARN in the `.tf` files to match the new instance.
4.  **Apply:** Run `terraform plan` to ensure no resources are being destroyed. Use `terraform apply -target=aws_db_instance.primary` to update the instance and its dependencies (SG, Route53) without touching unrelated infrastructure.

**SC2-C:**
*   **Architecture:** Replace PgBouncer with **RDS Proxy**, which handles failover more gracefully by maintaining application connections during primary promotion.
*   **DNS:** Use **Route53 Health Checks** with a CNAME record pointing to the current primary; the health check triggers a DNS flip to the DR endpoint.
*   **RPO < 1s:** I strongly recommend **Aurora Global Database**. It uses storage-level replication (dedicated replication fleet) rather than PostgreSQL streaming, reducing lag to typically < 1 second and providing faster promotion.
*   **Retry Logic:** Implement exponential backoff in the application layer to handle the 85ms latency and transient connection errors during the DNS propagation window.

## SC3 — Container Image Supply Chain Compromise

**SC3-A:**
1.  **Containment:** Do **not** delete the pods. Use `kubectl label pod <pod> status=quarantined` and update the NetworkPolicy to isolate the pod from the network while keeping it running.
2.  **Forensics:**
    *   **Process Tree:** `kubectl exec <pod> -- ps auxf` or use `kubectl debug` to run a sidecar with `sysdig` or `strace`.
    *   **Network:** `kubectl exec <pod> -- netstat -tupn` or `ss -atp`.
    *   **Filesystem:** `kubectl cp <pod>:/tmp/.x ./malware_sample` and `kubectl exec <pod> -- find / -mmin -60` to find recently modified files.

**SC3-B:**
```bash
# Simplified logic: Compare digests using skopeo
OLD_DIGEST=$(skopeo inspect docker://your-registry/api-gateway:v2.4.1 | jq '.Digest')
UPSTREAM_DIGEST=$(skopeo inspect docker://node:20-slim | jq '.Digest')

# List layers and flag anomalies
```

**SC3-C:**
*   **Pinning:** Use immutable digests (`node:20-slim@sha256:...`) instead of tags.
*   **Signing:** Use **Cosign** to sign images in the pipeline.
*   **Admission:** Use **Kyverno** to block any image that lacks a valid signature from the CI key.
*   **SBOM:** Generate a CycloneDX SBOM using **Syft** and store it in the registry.
*   **Notary v2:** Use Notary v2 (ORAS) to store signatures and metadata as OCI artifacts alongside the image, ensuring the registry itself enforces the integrity of the image.

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Sticky Sessions:** K8s pods are ephemeral. **Solution:** Move session state to an external Redis cluster.
2.  **Local NFS:** Pods cannot share local disk. **Solution:** Use an NFS CSI driver or migrate to S3/Object Storage.
3.  **Oracle DB:** Heavyweight and stateful. **Solution:** Keep Oracle external; connect via K8s `ExternalName` service.
4.  **IBM MQ:** Legacy protocol/state. **Solution:** Deploy IBM MQ on K8s using the official Operator or use a managed MQ bridge.
5.  **Bare Metal Performance:** Java 11 heap/GC tuning for container limits. **Solution:** Set `XX:MaxRAMPercentage` and define strict K8s resource requests/limits.

**SC4-B:**
```hcl
resource "storage_class" "nfs" {
  storage_provisioner = "nfs.csi.k8s.io"
  parameters = {
    server = var.nfs_server
    path   = var.export_path
}

resource "kubernetes_persistent_volume_claim" "uploads" {
  metadata { name = "uploads-pvc" }
  spec {
    access_modes = ["ReadWriteMany"] # Necessary because multiple pods must write uploads simultaneously
    resources { requests = { storage = var.capacity } }
    storage_class_name = "nfs"
  }
}
```

**SC4-C:**
*   **Phase 1 (Edge):** Deploy K8s Ingress. Route 1% of traffic to K8s, which proxies back to F5.
*   **Phase 2 (Read-Only):** Move read-only modules to K8s; they connect to the Oracle DB and NFS.
*   **Phase 3 (Full Cutover):** Move write-heavy modules and IBM MQ integration.
*   **Traffic Split:** Use **Istio Weighted Routing** or ALB Target Groups to shift traffic gradually.
*   **Rollback:** DNS flip back to F5.
*   **Go/No-Go:** p99 latency $\le$ 2s and 0% error rate increase.

## SC5 — Mysterious Latency Spike in Microservices

**SC5-A:**
1.  **Approach:** Check Istio `envoy_cluster_upstream_rq_time` (latency) and `envoy_cluster_upstream_cx_connect_timeout` (connection issues).
2.  **Tracing:** Use Jaeger to find the "gap" in the span. If the `checkout-service` span is long but the `inventory-service` internal span is short, the latency is in the network/proxy. If the `inventory-service` span is long, it's the app.
3.  **Envoy Metrics:** `upstream_rq_pending_overflow` indicates the proxy is queueing requests because the upstream is saturated.

**SC5-B:**
**SQL Diagnostic:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid, 
       blocking_activity.query AS blocking_query, blocked_activity.query AS blocked_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype 
  AND blocking_locks.database = blocked_locks.database AND blocking_locks.relation = blocked_locks.relation
JOIN pg_stat_activity blocked_activity ON blocked_locks.pid = blocked_activity.pid
JOIN pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid
WHERE NOT blocked_locks.granted;
```
**Go Circuit Breaker:**
```go
cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{Name: "inventory-service"})
body, err := cb.Execute(func() (interface{}, error) {
    return http.Get("http://inventory-service/stock")
})
```

**SC5-C:**
*   **CQRS:** Use a Read Replica for the reconciliation job to avoid locking the primary.
*   **Bulkhead:** Create separate DB connection pools for the API and the CronJob.
*   **Scheduling:** Stagger the CronJob to off-peak hours or use a queue-based reconciliation.
*   **K8s:** Set a `PriorityClass` for the checkout-service and a lower one for the CronJob. Use a `ResourceQuota` to cap the CronJob's CPU/RAM.

## SC6 — Zero-Trust Network Overhaul

**SC6-A:**
*   **Identity:** Deploy **SPIRE** (SPIFFE Runtime Environment). SPIRE issues short-lived SVIDs (X.509 certificates) to workloads regardless of location.
*   **Federation:** Use **OIDC Federation**. AWS workloads assume an IAM role; SPIRE maps that IAM role to a SPIFFE ID. The on-prem service trusts the SPIRE bundle, allowing the AWS workload to authenticate via mTLS without shared secrets.
*   **Azure/On-Prem:** Use Azure Workload Identity for Azure and a local PKI root for VMware, federated into the SPIRE trust bundle.

**SC6-B:**
```hcl
resource "aws_vpc_endpoint" "endpoints" {
  for_each = var.services # ["s3", "rds", "ecr"]
  vpc_id   = aws_vpc.main.id
  service_name = "com.amazonaws.${var.region}.vpce.${each.value}"
  vpc_endpoint_type = "Interface"
  subnet_ids = aws_subnet.private[*].id
  security_group_ids = [aws_security_group.endpoint_sg.id]
}
```

**SC6-C:**
*   **Direct Connect:** Best for consistent latency and high bandwidth (10Gbps+), but expensive.
*   **ECMP (VPN):** Increases bandwidth but doesn't solve the underlying latency/jitter of the public internet.
*   **Tailscale/Netbird:** Best for Zero Trust. It creates a WireGuard mesh. It removes the need for complex VPC routing and allows identity-based access (via OIDC) rather than IP-based rules.
*   **Routing:** Direct Connect requires BGP; Tailscale requires a lightweight agent on the node/pod.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
1.  **Manual Apply:** Bypasses CI, meaning the Git repo is no longer the "Source of Truth."
2.  **Helm Divergence:** Leads to "Configuration Drift," where production behaves differently than staging, making releases unpredictable.
3.  **Kubectl Edit:** Bypasses audit logs and version control.
**Danger:** Without state locking, two engineers running `tofu apply` simultaneously can corrupt the state file (race condition), leading to resource duplication or accidental deletion of production assets.

**SC7-B:**
```yaml
stages: [validate, plan, apply]
tofu_plan:
  stage: plan
  script:
    - tofu init -backend-config="dynamodb_table=terraform-lock"
    - tofu plan -out=tfplan
    - # Custom script to post tfplan to MR comment
tofu_apply:
  stage: apply
  when: manual
  environment: production
  script:
    - tofu apply tfplan
```

**SC7-C:**
*   **Drift Detection:** A scheduled GitLab job runs `tofu plan -detailed-exitcode`. If exit code is 2 (drift), it alerts the team.
*   **Blocking:** Use **Kyverno** to block `UPDATE` or `PATCH` requests on ConfigMaps in production unless the user is the CI ServiceAccount.
*   **Helm:** Use **Helmfile** with a `common-values.yaml` and `prod-values.yaml` override.
*   **RBAC:** Remove `cluster-admin` from humans; grant `view` only. Only the CI ServiceAccount gets `edit` permissions.

## SC8 — Observability Stack Scaling Failure

**SC8-A:**
1.  **Prometheus OOM:** High cardinality (8.2M series). Too many unique label combinations (e.g., user_id as a label).
2.  **Loki Drops:** Ingester saturation. The write path cannot keep up with the log volume.
3.  **Tempo Timeouts:** S3 query latency. Searching large trace blocks without efficient indexing.
4.  **Thanos Lag:** Compactor is CPU/IO bound, unable to merge blocks faster than they are created.
**Confirmation:** Check `prometheus_tsdb_head_series` and `loki_ingester_push_requests_total`.

**SC8-B:**
```bash
# Get top 20 metrics by series count
curl -s "http://prometheus:9090/api/v1/label/__name__/values" | jq '.data[]' | \
while read m; do 
  count=$(curl -s "http://prometheus:9090/api/v1/query?query=count({__name__=\"$m\"})" | jq '.data.result[0].value[1]')
  echo "$m $count"
done | sort -rnk2 | head -n 20 | column -t
```

**SC8-C:**
*   **Mimir/VictoriaMetrics:** Replace Prometheus to allow horizontal scaling of the read/write paths.
*   **Loki Microservices:** Separate `ingester`, `querier`, and `distributor` to scale independently.
*   **Tempo:** Use the **Parquet** storage format for faster S3 reads.
*   **Governance:** Implement **Relabeling** to drop high-cardinality labels at the edge.
*   **Chargeback:** Use `prometheus_tsdb_head_series` per namespace to calculate the "cost" per team and bill accordingly.

## SC9 — Securing a Public-Facing API After a Breach

**SC9-A:**
1.  **BOLA (API1):** User A accesses User B's data. **Fix:** Override `get_object` in DRF to check `request.user == obj.owner`.
2.  **Data Leakage (API3):** Internal fields exposed. **Fix:** Use a **Serializer** to explicitly define allowed fields.
3.  **No Rate Limit (API4):** Resource exhaustion/scraping. **Fix:** Implement `Django-ratelimit` or WAF rate limits.
4.  **Keys in URL (API7):** Log leakage. **Fix:** Move keys to `Authorization: Bearer <key>` header.

**DRF BOLA Fix:**
```python
def get_object(self, queryset=None):
    obj = super().get_object()
    if obj.owner != self.request.user:
        raise PermissionDenied("Not your record")
    return obj
```

**SC9-B:**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {
  # ... name, scope = "REGIONAL"
  rule {
    name = "RateLimit"
    priority = 1
    action { block {} }
    statement { rate_limit { limit = 100 } }
  }
  rule {
    name = "BlockApiKeyInUrl"
    priority = 2
    action { block {} }
    statement { byte_match_statement { field = "QUERY_STRING", positional_constraint = "CONTAINS", search_string = "api_key=" } }
  }
}
```

**SC9-C:**
*   **Auth:** Transition to **OAuth2/JWT** (short-lived).
*   **Gateway:** Deploy **Kong** for centralized rate-limiting and request transformation (stripping internal headers).
*   **Audit:** Enable **CloudTrail Data Events** for the ALB.
*   **Migration:** Support both API keys and JWTs for a 30-day window; log "Deprecated" warnings in the API response header to notify consumers to migrate.

## SC10 — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Architecture:** **Active-Passive with Cilium Cluster Mesh**. Active-Active is too risky for 200TB MinIO.
*   **RPO/RTO:** 12ms latency allows for **Synchronous Replication** for Postgres (RPO=0). 200TB MinIO requires **Asynchronous Site Replication** (RPO $\approx$ 15m).
*   **Stateful Strategy:**
    *   Postgres: Patroni + Streaming Replication.
    *   Redis: Sentinel with cross-site replicas.
    *   RabbitMQ: Federation/Shovel.
    *   MinIO: Site-to-Site Bucket Replication.

**SC10-B:**
```yaml
- name: Configure Patroni
  template:
    src: patroni.yml.j2
    dest: /etc/patroni.yml
  notify: restart patroni
# In template:
# synchronous_commit: "on"
# synchronous_standby_names: "dallas-node-1"
```

**SC10-C:**
1.  **Detection:** External health checks (e.g., Route53/GSLB) detect Chicago failure.
2.  **Sequence:** GSLB $\rightarrow$ Patroni Promote (Dallas) $\rightarrow$ Redis Sentinel Failover $\rightarrow$ RabbitMQ Federation switch $\rightarrow$ Update DNS.
3.  **Split-Brain:** Use a **Quorum-based Witness** (3rd site or cloud) to prevent two primaries.
4.  **Failback:** Re-sync Dallas $\rightarrow$ Chicago $\rightarrow$ Switch primary back $\rightarrow$ Update GSLB.
