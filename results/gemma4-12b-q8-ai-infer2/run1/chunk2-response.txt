## Kubernetes

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** manages stateless applications where pods are interchangeable; any pod can replace another without maintaining identity or specific ordering. A **StatefulSet** manages stateful applications (like databases) where each pod has a unique, persistent identity (e.g., `pod-0`, `pod-1`), stable network identifiers, and dedicated persistent storage that persists even if a pod is rescheduled.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
The Service provides a stable virtual IP (VIP). The `kube-proxy` component on each node manages internal routing rules (via iptables or IPVS). When traffic hits the ClusterIP, these rules intercept the packet and redirect it to one of the healthy Pod IPs listed in the Service's Endpoints object.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage provisioned by an administrator (the actual physical/cloud disk).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user (a "ticket" for resources).
*   **StorageClass:** A blueprint defining different types of storage (e.g., SSD vs. HDD) used to automatically provision PVs when a PVC is created.
*   **Relationship:** User creates a **PVC** $\rightarrow$ matches a **StorageClass** $\rightarrow$ Provisioner creates a **PV** $\rightarrow$ PVC binds to the PV.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps.**
1.  **Check Logs:** Run `kubectl logs <pod_name>` to see application-level errors (stack traces, connection timeouts).
2.  **Describe Pod:** Run `kubectl describe pod <pod_name>` to check for events like OOMKills, failed liveness probes, or image pull errors.
3.  **Resource Check:** Compare requested CPU/Memory against limits; look for memory leaks causing Out Of Memory (OOM) kills.
4.  **Configuration Audit:** Verify ConfigMaps and Secrets are correctly mounted and that environment variables match expected values.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS provides internal name resolution for services within the cluster (e.g., resolving `my-svc.default.svc.cluster.local`). If CoreDNS is down, pods cannot resolve service names or other internal hostnames, effectively breaking inter-service communication even if the network layer is functional.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on.**
The scheduler follows two main phases:
1.  **Filtering (Predicates):** It eliminates nodes that do not meet requirements (e.g., insufficient CPU/RAM, Taints without matching Tolerations, NodeSelectors).
2.  **Scoring (Priorities):** It ranks remaining nodes based on factors such as:
    *   **Least Requested Resources:** Favoring nodes with more free capacity.
    *   **Image Locality:** Preferring nodes that already have the container image cached.
    *   **Pod Topology:** Balancing pods across zones/nodes to ensure high availability.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
*   **Scheduling:** Yes, it will be scheduled because $256\text{ Mi}$ ($< 0.25\text{ GiB}$) is less than the available $0.5\text{ GiB}$ of unrequested space.
*   **Runtime:** If usage hits $600\text{ Mi}$, it exceeds the **limit** of $512\text{ Mi}$. The Kubernetes kubelet will trigger an **OOMKill**, terminating the container.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller.**
1.  External client sends request to the **External Load Balancer**.
2.  LB forwards traffic to the **Ingress Controller** (NGINX) Pod IP.
3.  NGINX parses the host/path against **Ingress Resources** rules.
4.  NGINX identifies the target **Service**.
5.  `kube-proxy` handles the routing from Service VIP to specific **Endpoints** (Pod IPs).
6.  The packet reaches the application **Pod**.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A NetworkPolicy acts as a pod-level firewall controlling ingress/egress traffic. By default, if no policy exists, all traffic is allowed (**Allow All**). When a policy is applied, it creates an "isolation" effect; only traffic explicitly permitted by the policy's selectors is allowed through.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old pods with new ones (default), ensuring zero downtime.
*   **Recreate:** Kills all existing pods before starting new ones, causing downtime.
*   **When to use Recreate:** Use this for applications that cannot run two versions simultaneously (e.g., apps sharing a singleton database or legacy systems that don't support concurrent versioning).

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A Namespace is a virtual cluster used to partition resources and provide isolation between teams or environments. Default namespaces include `default`, `kube-system`, `kube-public`, and `kube-node-scheduler`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
It provides detailed metadata about the pod state. It shows: **Events** (reasons for failure/success), **Container Status** (specific exit codes/restart counts), and **Resource Usage/Limits** details.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A ConfigMap stores non-confidential configuration data. Pods can consume them via:
1.  **Environment Variables:** Injected into the container environment.
2.  **Volume Mounts:** Mounted as files inside the container filesystem.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Internal only; reachable from within the cluster.
*   **NodePort:** Exposes service on a specific port on every node's IP.
*   **LoadBalancer:** Provisions an external load balancer (via cloud provider) to route traffic to the service.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A DaemonSet ensures that exactly one copy of a pod runs on every node in the cluster. Use this for infrastructure tasks like log collection (`Fluentd`), monitoring agents (`Prometheus Node Exporter`), or networking plugins.

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints/Tolerations:** Taints "repel" pods from nodes unless the pod has a matching Toleration ("Keep away"). *Use Case:* Dedicated GPU nodes where you want only ML workloads to land there.
*   **Affinity:** "Attracts" pods to certain nodes based on labels ("Pull towards"). *Use Case:* Ensuring a web-server pod always lands on a node with high-speed NVMe storage.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An Operator is a custom controller that encodes human operational knowledge (e.g., how to backup a database, handle failover, or scale shards). While standard controllers manage generic objects (Deployments), Operators manage complex stateful logic and lifecycle management for specific software.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
Etcd uses the **Raft consensus algorithm**, providing strong consistency. If quorum ($n/2 + 1$) is lost, the cluster becomes read-only; no new states can be committed. To recover from losing 2 out of 3 nodes (total loss of quorum), you must manually force a new cluster configuration on one remaining node to establish a new single-node quorum, then join new healthy nodes to restore redundancy.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
RBAC defines permissions based on identities.
*   **Role:** Permissions within a Namespace.
*   **ClusterRole:** Permissions across the whole Cluster.
*   **RoleBinding:** Links a user/group to a Role (Namespace scoped).
*   **ClusterRoleBinding:** Links a user/group to a ClusterRole (Cluster wide).

```yaml
# Example Manifests
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev-ns
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev-ns
  name: dev-user-binding
subjects:
- kind: User
  name: "developer-user"
  user: "dev-user"
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
The `ndots` setting determines how many dots are required in a name before trying an absolute path; if a name has fewer than $N$ dots (default 5), K8s appends search paths one by one. For every query, this creates multiple failed lookups before finding the right answer. Fix: Set `dnsConfig` with `ndots: 1` or use Fully Qualified Domain Names (FQDNs).

## Development

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
*   **Merge:** Combines two branches while preserving the entire history of both branches.
*   **Rebase:** Rewrites the project history by moving the base of your branch to a new starting point.
*   **Avoid Rebase:** Never rebase commits that have been pushed to a public shared repository, as it rewrites history and breaks other people's local clones.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP:** Connection-oriented, reliable, ensures order/delivery via handshakes and acknowledgments. *Examples:* HTTP, SSH.
*   **UDP:** Connectionless, fast, no guarantee of delivery. *Examples:* DNS, VoIP/Streaming.

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A race condition occurs when the output depends on the timing/sequence of uncontrollable events (e.g., multiple threads accessing shared memory).
*Example (Python):* Two threads reading a bank balance of \$100, both adding \$50 simultaneously; if they read at the same time, they might both write back \$150 instead of \$200 because neither saw the other's update.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric:** Same key for encryption/decryption (Fast - e.g., AES).
*   **Asymmetric:** Public key encrypts, Private key decrypts (Secure but slow - e.g., RSA/ECC).
*   **TLS Usage:** Asymmetric encryption is used during the **Handshake** to authenticate identities and securely exchange a "session key." Symmetric encryption uses that session key for the actual data transfer.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
Each instruction in a Dockerfile creates a new read-only layer. To optimize builds, you should put instructions that change least frequently (like `apt-get install`) at the top and those that change often (like `COPY . .`) at the bottom. This ensures that changes only invalidate subsequent layers, maximizing cache hits.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**
1.  **Logs:** Check application logs for specific errors or crashes.
2.  **Metrics:** Check CPU/Memory usage of the service pods to see if they are hitting limits.
3.  **Upstream Health:** Check if downstream dependencies (DBs, external APIs) are failing.
4.  **Load Balancer/Gateway:** Check connection limits or rate limiting on the ingress controller.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
CAP states a distributed system can only provide two out of three: Consistency, Availability, Partition Tolerance.
*   **CP Example:** **HBase** or **MongoDB** (prioritizes consistency; will stop responding if it cannot guarantee data accuracy during a partition).
*   **AP Example:** **Cassandra** or **DynamoDB** (prioritizes availability; allows writes even if nodes are disconnected, resolving conflicts later).

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical Scaling:** Adding more power (CPU, RAM) to an existing machine.
*   **Horizontal Scaling:** Adding more machines to the pool.
*   **Patterns:** Load Balancing, Sharding (Database partitioning), Microservices architecture, and Statelessness.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An environment variable is a dynamic value used by processes/applications. To persist it in Linux, add `export VAR_NAME="value"` to your shell configuration file like `.bashrc` or `.zshrc`.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
JSON is a lightweight data-interchange format using `{}` and `[]`. YAML is a human-friendly superset of JSON using indentation.
*   **JSON Advantage:** Extremely easy for machines to parse quickly.
*   **YAML Advantage:** Supports comments and complex multi-line strings easily.

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
REST is an architectural style for networked applications.
*   **GET:** Retrieve resource(s).
*   **POST:** Create new resource.
*   **PUT:** Update existing resource (replaces entire object).
*   **DELETE:** Remove resource.

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
Version pinning specifies exact versions of dependencies (e.g., `requests==2.31.0`). It ensures that every developer and CI/CD pipeline uses identical code, preventing "it works on my machine" errors caused by silent updates to sub-dependencies.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled:** Source code is translated into machine code before execution (Fast performance). *Examples:* C++, Go.
*   **Interpreted:** Code is executed line-by-line or via bytecode at runtime. *Examples:* Python, Ruby.

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
*   **Forward Proxy:** Sits in front of clients; hides client identity (e.g., corporate VPN).
*   **Reverse Proxy:** Sits in front of web servers; masks server identity and handles requests.
*   **Servers & Use Cases:** **Nginx** (Load balancing), **HAProxy** (High availability / SSL termination).

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A deadlock is when processes are stuck waiting for resources held by each other. The 4 Coffman conditions:
1.  Mutual Exclusion (Resource can't be shared).
2.  Hold and Wait (Process holds one resource while requesting another).
3.  No Preemption (Resources cannot be forcibly taken away).
4.  Circular Wait (Wait cycle exists).

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
Eventual consistency means that if no new updates are made, all reads will eventually return the last updated value. Cassandra uses "Quorum" logic ($R + W > \text{Replication Factor}$). Tunable levels include `ONE` (fastest, low consistency), `QUORUM` (majority nodes agree), and `ALL` (highest consistency, lowest availability).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
mTLS requires *both* parties to present certificates. In the handshake: Client sends cert $\rightarrow$ Server verifies; Server sends cert $\rightarrow$ Client verifies. Both verify signatures against a trusted Certificate Authority (CA) before establishing an encrypted tunnel. It is standard in **Service Mesh** architectures (e.g., Istio/Linkerd) for zero-trust security between microservices.

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
A Hash Table maps keys to indices using a hash function. 
*   **Chaining:** Store multiple items at one index via a linked list or tree.
*   **Open Addressing:** Find the next available slot (Linear Probing, Quadratic Probing, Double Hashing).
*   **Complexity:** Average $O(1)$ for all operations; Worst case $O(n)$ if many collisions occur at one bucket.

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
Circuit Breaker stops requests to a failing service to prevent "cascading" failure where every request hangs until resources are exhausted.
*   **Closed:** Normal operation.
*   **Open:** Service failed too much; fail fast immediately without calling the backend.
*   **Half-Open:** Periodically allow a few test requests to see if the service recovered.
It complements **Retries with Exponential Backoff**, which ensures that when we *do* retry, we don't overwhelm the recovering system by hammering it instantly.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features.**
*   **Optimistic:** Assumes conflicts are rare. Checks version/timestamp during write. Use for high-concurrency web apps (e.g., editing a wiki page). Feature: `version` column or Row Versioning.
*   **Pessimistic:** Locks the record upon reading so no one else can touch it. Use for financial transactions where accuracy is paramount. Feature: `SELECT FOR UPDATE`.
