## Application Architecture

**AA1 — Easy: What is the difference between a monolith and a microservices architecture? Name 3 concrete problems that microservices introduce that monoliths don't have.**
A **monolith** is a single unified unit where all components (UI, business logic, data access) are deployed together in one codebase. A **microservices** architecture decomposes these into independent services communicating over a network.
Problems introduced by microservices:
1.  **Distributed Tracing:** Difficulty tracking a request across multiple service boundaries.
2.  **Eventual Consistency:** Managing data integrity across distributed databases without ACID transactions.
3.  **Operational Complexity:** Increased overhead in deployment, monitoring, and networking (service discovery, load balancing).

**AA2 — Easy: Explain the difference between synchronous and asynchronous communication between services. Give an example technology for each.**
**Synchronous** communication requires the requester to wait for a response before proceeding (blocking). Example: **REST or gRPC**.
**Asynchronous** communication allows the requester to send a message/request and continue its work immediately; the response is handled later via a callback or polling. Example: **RabbitMQ or Apache Kafka**.

**AA3 — Medium: What is the difference between an API Gateway and a reverse proxy? Can an API Gateway replace a reverse proxy entirely? Why or why not?**
A **reverse proxy** primarily handles requests on behalf of servers (load balancing, SSL termination, caching). An **API Gateway** does all that plus higher-level logic like authentication, rate limiting, request transformation, and protocol translation. 
An API Gateway *can* replace a reverse proxy because it performs those functions, but you might choose a dedicated reverse proxy (like Nginx) if you only need high-performance traffic routing without complex application-layer logic.

**AA4 — Medium: Explain the Saga pattern for distributed transactions. What is the difference between choreography-based and orchestration-based sagas? When is each appropriate?**
The **Saga pattern** manages data consistency across microservices by executing a sequence of local transactions. If one fails, "compensating transactions" undo previous steps.
*   **Choreography:** Each service produces/consumes events and decides what to do next. Best for simple workflows with few services (decoupled).
*   **Orchestration:** A central "orchestrator" tells participants which operation to perform. Best for complex workflows where visibility into the state of the transaction is critical.

**AA5 — Medium: What is CQRS (Command Query Responsibility Segregation)? Why is it often paired with Event Sourcing? What problem does this combination solve that a traditional CRUD model doesn't?**
**CQRS** separates read operations (Queries) from write operations (Commands). It is paired with **Event Sourcing**, where every change is stored as a sequence of immutable events rather than just current state. 
This solves the **Read Side Bottleneck**: In CRUD, the database must be optimized for both writes and reads simultaneously. With CQRS + Event Sourcing, you can scale the Read side independently using specialized projections (e.g., an Elasticsearch index for search or a Redis cache for fast lookups) while keeping the Write side optimized for high-throughput ingestion.

**AA6 — Medium: Explain the Circuit Breaker pattern. What are the three states? How does it differ from a simple retry with backoff, and when would you use both together?**
The **Circuit Breaker** prevents a system from repeatedly trying to call a failing service, allowing the failing service time to recover.
States: **Closed** (Requests flow normally), **Open** (Requests fail immediately/fast-fail), **Half-Open** (Limited requests allowed to test if the service has recovered).
Difference: A **Retry with Backoff** keeps trying until success; a Circuit Breaker stops attempts entirely after a threshold. Use them together by wrapping a Retry inside a Circuit Breaker—the breaker protects the system from "hammering" a dead service during its downtime.

**AA7 — Hard: You're designing a multi-tenant SaaS platform. Compare the following tenant isolation models and their trade-offs across cost, security, operational complexity, and noisy-neighbor risk:**
1.  **Shared DB, Shared Schema (Row-level ID):** Lowest cost, lowest complexity. High noisy-neighbor risk; lower security (risk of data leakage via SQL injection or bugs).
2.  **Shared DB, Separate Schema per Tenant:** Moderate cost/complexity. Better security (logical separation); moderate noisy-neighbor risk (shared resources like connection pools).
3.  **Separate Database per Tenant:** Highest cost and highest operational complexity. Best security (physical/process isolation) and best protection against noisy neighbors (dedicated resources).

**AA8 — Hard: Explain the difference between eventual consistency and strong consistency. A product team wants their inventory system to never oversell. How would you architect this — what consistency model, what data store, and what patterns would you use at scale?**
*   **Strong Consistency:** Every read receives the most recent write. **Eventual Consistency:** Reads may return stale data for a period but will eventually converge.
To prevent overselling at scale: Use **Strong Consistency**. I would use a distributed SQL database that supports ACID transactions (e.g., **CockroachDB** or **Google Spanner**) or an RDBMS with strict locking. To handle high concurrency on specific items, implement **Distributed Locking** (via Redis/Redlock) or a **Reservation Pattern** where stock is "held" in a temporary state during checkout.

**AA9 — Medium: What is a sidecar proxy in a service mesh? Explain how Envoy works in an Istio deployment. What is the data plane vs control plane? What problem does mTLS between sidecars solve that application-level TLS doesn't?**
A **sidecar proxy** is a helper container running alongside every service instance to handle networking logic (retries, mtls, telemetry). 
In **Istio**, **Envoy** acts as the **Data Plane** (handling actual traffic), while Istio’s management components act as the **Control Plane** (configuring the proxies). 
**mTLS** between sidecars solves the "Zero Trust" problem by ensuring encryption and identity verification without requiring developers to write security code into each individual microservice.

**AA10 — Medium: Explain the Strangler Fig pattern. You have a legacy .NET Framework monolith and need to incrementally migrate to .NET 8 microservices. Describe a concrete migration strategy using this pattern.**
The **Strangler Fig** pattern involves building new functionality in microservices around the edges of the old system until the old system is eventually replaced.
Strategy:
1.  Identify a small, low-risk bounded context (e.g., Notification Service) within the .NET Framework app.
2.  Create a new .NET 8 microservice for this feature.
3.  Place an API Gateway/Proxy in front; route requests for Notifications to the new service, all other requests go to the Monolith.
4.  Repeat for more features until the Monolith has no remaining traffic.

**AA11 — Medium: What is the 12-Factor App methodology? Name at least 6 factors and explain why they matter for cloud-native deployments.**
A set of best practices for building scalable, portable apps. Factors include:
1.  **Codebase:** One codebase per service.
2.  **Dependencies:** Explicitly declare dependencies (no "it works on my machine").
3.  **Config:** Store config in environment variables (separation of code and config).
4.  **Backing Services:** Treat databases as attached resources.
5.  **Build, Release, Run:** Strict separation between build stages and execution.
6.  **Statelessness:** Ensure processes are stateless so they can be scaled horizontally instantly.
7.  **Concurrency:** Scale out by adding more instances.

**AA12 — Hard: Compare event-driven architecture using an event broker (Kafka) vs request-driven architecture using REST/gRPC. Cover: coupling, scalability, debugging complexity, ordering guarantees, and failure handling. When would you choose each?**
*   **Coupling:** Kafka = Loose (Pub/Sub); REST/gRPC = Tight (Point-to-point).
*   **Scalability:** Kafka scales better for high-throughput ingestion; gRPC is faster for low-latency point-to-point calls.
*   **Debugging:** Kafka is harder to trace across many consumers; REST/gRPC has clearer request/response flows.
*   **Ordering:** Kafka guarantees order within a partition; REST/gRPC relies on application logic.
*   **Failure Handling:** Kafka provides persistence (replayable events); REST requires complex retry/circuit breaker logic.
Choose **REST/gRPC** for synchronous user actions (e.g., Login). Choose **Kafka** for background processing or data pipelines (e.g., Order Processing).

**AA13 — Easy: What is a load balancer? Explain the difference between Layer 4 and Layer 7 load balancing. Give one use case where Layer 7 is required.**
A **Load Balancer** distributes incoming network traffic across multiple servers.
*   **Layer 4 (Transport):** Routes based on IP and Port. Fast, but "blind" to content.
*   **Layer 7 (Application):** Routes based on HTTP headers, cookies, or URL paths.
Use Case for L7: Routing `example.com/api` to an API cluster and `example.com/web` to a web server cluster.

**AA14 — Easy: What is a message queue? Explain the difference between a message queue (e.g., RabbitMQ) and a log-based message broker (e.g., Kafka). When would you pick one over the other?**
A **Message Queue** stores messages until they are consumed; once processed, they are usually deleted. **RabbitMQ** is a classic example.
A **Log-based Broker** treats messages as an append-only log of events that can be replayed by different consumers at different times. **Kafka** is the standard here.
Pick **RabbitMQ** for complex routing logic and per-message acknowledgments. Pick **Kafka** for high-throughput streaming, data replayability, and massive scale.

**AA15 — Easy: What is a container and how does it differ from a virtual machine? Why are containers popular for deploying microservices?**
A **Container** shares the host OS kernel but isolates the application process. A **VM** includes its own full guest OS and runs on a hypervisor. 
Containers are popular because they have much lower overhead (faster startup, smaller footprint), allowing developers to run many small services efficiently on a single host.

**AA16 — Easy: Explain the difference between stateless and stateful services. Why are stateless services easier to scale horizontally? Give an example of each.**
**Stateless** services do not store client context/data between requests (e.g., a "Calculate Tax" service). **Stateful** services maintain history or session data (e.g., a Database or a Chat Session).
Stateless services are easier to scale because any instance can handle any request; you don't need to worry about which specific server a user was connected to previously.

**AA17 — Easy: What is an ORM (Object-Relational Mapper)? Name two popular ORMs in different languages. What are the trade-offs of using an ORM vs writing raw SQL?**
An **ORM** maps database tables to objects in code. Examples: **Hibernate** (Java) and **Entity Framework** (.NET).
*   **Pros:** Faster development speed, handles boilerplate like connection pooling and migrations.
*   **Cons:** Can produce inefficient queries for complex joins; harder to optimize performance compared to hand-tuned Raw SQL.

**AA18 — Medium: Explain the Bulkhead pattern. How does it relate to resource isolation in a microservices architecture? Give a concrete example of how you would implement bulkheads using thread pools or separate deployment groups.**
The **Bulkhead** pattern isolates elements into pools so that if one fails, others continue to function (like ship compartments). 
In microservices, this prevents a single slow service from consuming all resources (threads/memory) of another.
Implementation: Use **separate thread pools** for different types of requests (e.g., "Search" gets its own pool, "Checkout" gets another); or deploy services on **separate clusters** so a crash in Service A doesn't take down Service B.

**AA19 — Hard: You are designing a real-time collaborative editing system (like Google Docs). Compare Operational Transformation (OT) and CRDTs (Conflict-free Replicated Data Types) as conflict resolution strategies. Cover: consistency guarantees, latency, complexity, and offline support. Which would you choose for a system that must support offline editing and why?**
*   **OT:** Centralized server resolves conflicts by transforming operations based on history. High complexity but very mature.
*   **CRDTs:** Mathematical structures where concurrent updates merge automatically without a central coordinator. Higher memory overhead but naturally supports peer-to-peer/offline sync.
For **offline editing**, I would choose **CRDTs**. They allow users to make local changes while disconnected; when they reconnect, the data merges mathematically without needing a complex reconciliation logic against a central state.

**AA20 — Hard: Explain the challenges of distributed tracing across a polyglot microservices ecosystem. Cover: context propagation (W3C Trace Context, B3), sampling strategies (head-based vs tail-based), trace storage and querying (Jaeger, Tempo), and how tracing interacts with asynchronous messaging. How do you ensure trace continuity when a request passes through Kafka?**
Challenges include maintaining trace IDs across different languages and protocols. 
1.  **Context Propagation:** Use standards like W3C Trace Context or B3 headers to pass `trace_id` between services.
2.  **Sampling:** Head-based samples at the start (saves cost); Tail-based keeps traces until completion (better for finding errors).
3.  **Tracing Async Messaging:** When passing through Kafka, the producer must inject the trace ID into the message header. The consumer then extracts it to continue the span. This ensures that even if there is a delay in processing, the "parent" and "child" spans remain linked in tools like Jaeger/Tempo.

## On-Premise Infrastructure Architecture

**OP1 — Easy: Explain the difference between a hypervisor Type 1 (bare-metal) and Type 2 (hosted). Give 2 examples of each.**
*   **Type 1:** Runs directly on physical hardware. Example: **ESXi, Proxmox (KVM)**.
*   **Type 2:** Runs as an application on top of an existing OS. Example: **VirtualBox, VMware Workstation**.

**OP2 — Easy: What is a SAN vs NAS? When would you use each? What protocols does each typically use?**
*   **SAN (Storage Area Network):** Block-level storage. Used for high-performance databases or clusters requiring low latency. Protocols: **iSCSI, Fibre Channel**.
*   **NAS (Network Attached Storage):** File-level storage. Used for shared file storage, backups, and home directories. Protocols: **NFS, SMB**.

**OP3 — Medium: Explain a 3-tier network architecture (core/distribution/access). Why is leaf-spine preferred in modern data centers? What problem does it solve that 3-tier doesn't?**
The 3-tier model was designed for North-South traffic (Client to Server). Modern apps have massive East-West traffic (Server to Server). Leaf-Spine provides predictable "any-to-any" latency by ensuring every leaf switch is exactly one hop away from any other leaf, eliminating the bottlenecks found in traditional distribution layers.

**OP4 — Medium: You need to design a highly available Proxmox cluster with shared storage. Describe the architecture covering: node count, quorum, fencing, shared storage options (Ceph, iSCSI, NFS), and what happens during a node failure.**
Architecture: Minimum 3 nodes (for Quorum). Use **Ceph** as distributed block storage. Implement **STONITH** (Shoot The Other Node In The Head) for fencing to prevent split-brain. If a node fails, Ceph re-replicates lost blocks; Corosync/Pacemaker detects the loss of heartbeat and fences the dead node while migrating its VMs to healthy nodes.

**OP5 — Medium: What is VLAN trunking? Explain 802.1Q tagging. A server has a single NIC but needs to be on 3 VLANs — how do you configure this on Linux?**
VLAN Trunking allows multiple VLANs to travel over a single physical link. **802.1Q** adds a tag to the Ethernet frame header identifying the VLAN ID. On Linux, use **Subinterfaces** (e.g., `eth0.10`, `eth0.20`) or a bridge with **VLAN aware** settings (`bridge-utils` / `iproute2`).

**OP6 — Medium: Explain the difference between RAID 1, RAID 5, RAID 6, RAID 10, and RAID Z2 (ZFS). You have 6 drives and need to balance performance, capacity, and fault tolerance for a database server — which do you choose and why?**
*   RAID 1: Mirroring (High safety, low capacity).
*   RAID 5: Striping + Parity (Good capacity, slow writes).
*   RAID 6: Double parity (Safe against 2 drive failures).
*   RAID 10: Mirroring + Striping (Best perf/safety mix).
*   RAID Z2: ZFS equivalent of RAID 6.
Choice: **RAID 10**. It provides the best IOPS for databases by avoiding the "parity write penalty" of RAID 5/6 while providing high redundancy.

**OP7 — Hard: Design a DNS architecture for a 500-person enterprise with: internal Active Directory, a DMZ with public-facing services, split-horizon DNS, and DNSSEC on the external zone. Cover: recursive resolvers, authoritative servers, forwarders, conditional forwarding, and what happens when a laptop moves between office and VPN.**
Architecture:
1.  Internal Recursive Resolvers handle employee queries.
2.  Split-Horizon: Internal records point to private IPs; External Authoritative servers provide public IPs.
3.  Conditional Forwarding: Send specific requests (e.g., `google.com`) to upstream forwarders.
4.  DNSSEC signs the public zones to prevent spoofing.
VPN behavior: The VPN client must be configured to use the corporate DNS server or have its local resolver pointed to the corporate IP so it can resolve internal names via the tunnel.

**OP8 — Hard: Explain the PKI chain of trust from root CA to end-entity certificate. You need to deploy an internal PKI for your organization. Cover: root CA (offline), subordinate/issuing CA, CRL vs OCSP, certificate templates, and auto-enrollment. What are the consequences of a compromised subordinate CA vs a compromised root CA?**
Chain: Root CA signs Subordinate CA -> Issuing CA signs End Entity certificates. 
Deployment: Keep **Root CA offline** (only used to sign subordinates). Use **OCSP** for real-time revocation checks. Use **Certificate Templates** to define permissions. Implement **Auto-enrollment** via Group Policy.
Consequences: A compromised **Subordinate CA** allows an attacker to issue fake certs for that branch only. A compromised **Root CA** compromises the entire trust anchor; every certificate in the org is now untrustworthy.

**OP9 — Hard: You're consolidating 5 remote offices into a hub-and-spoke WAN. Compare: MPLS, IPsec VPN over internet, SD-WAN, and WireGuard mesh. Cover: cost, reliability, latency, management complexity, and security posture. Which would you recommend for a company with 50 users per site and latency-sensitive VoIP?**
*   MPLS: Reliable, expensive, low latency.
*   IPsec: Cheap, variable latency, high overhead.
*   SD-WAN: Best balance—uses multiple paths, optimizes traffic based on app type.
*   WireGuard Mesh: High performance, easy setup.
Recommendation: **SD-WAN**. It provides path steering (sending VoIP over the best available link) and centralized management which is vital for 250 total users across sites.

**OP10 — Medium: What is iDRAC/iLO/IPMI? Why is out-of-band management critical? What happens if your IPMI interface is exposed to the internet?**
These are hardware controllers allowing access to power, console, and BIOS even when the OS is down. They are critical for remote troubleshooting and "unbricking" servers. If exposed to the internet, an attacker can gain full control of the server's physical hardware, including rebooting, wiping drives, or installing persistent rootkits at the firmware level.

**OP11 — Medium: Explain the difference between LVM, LVM-Thin, and ZFS. When would you use each? What are the snapshot semantics for each?**
*   LVM: Logical volume management; snapshots are "Copy-on-Write" but can be heavy. Good for standard Linux setups.
*   LVM-Thin: Allows over-provisioning of storage. Snapshots are very efficient as they only store changes. Best for virtualization environments with many small disks.
*   ZFS: File system + Volume Manager. Native snapshots (nearly zero cost). Use for high-integrity data where features like compression and RAID-Z are needed.

**OP12 — Hard: You have a 3-node Proxmox cluster with Ceph storage and need to survive a complete site failure. Design a stretch cluster or DR strategy. Cover: Ceph CRUSH rules, monitor placement, network latency requirements, and the split-brain problem. Why is 2-site Ceph generally a bad idea without a tiebreaker?**
Strategy: A **Stretch Cluster** requires 3 sites (or a 3rd site/witness) because Ceph needs an odd number of votes for quorum. To survive a full site failure, you'd need enough replicas across sites so that any one site can go dark while others maintain a majority. 
Why 2-sites fail: If Site A goes down, Site B cannot tell if it's alone or if Site A just lost connection. Both might try to take control ("Split-Brain"). A third "Witness" node in a 3rd location provides the tiebreaker.

**OP13 — Easy: What is DHCP and how does the DORA process work? What happens when a DHCP server is unavailable and a Windows client's lease expires?**
DHCP assigns IPs automatically via **DORA**: Discover (Client), Offer (Server), Request (Client), Acknowledge (Server).
If the server is down and a lease expires, the client will attempt to renew; failing that, it may continue using its current IP until it becomes invalid, then it will attempt to self-assign an APIPA address (`169.254.x.x`).

**OP14 — Easy: Explain the difference between a managed switch and an unmanaged switch. What features does a managed switch provide that are important in an enterprise environment?**
Unmanaged switches are "plug and play." Managed switches allow for configuration of **VLANs**, **QoS** (prioritizing VoIP traffic), **SNMP** monitoring, and **Port Security** (limiting which MAC addresses can connect).

**OP15 — Easy: What is NTP and why is accurate time synchronization critical in an on-premise environment? What can go wrong when clocks drift between servers in a cluster?**
NTP synchronizes system clocks over a network. Accurate time is vital for log correlation, Kerberos authentication (which fails if clocks differ by >5 mins), and database replication consistency. Clock drift causes logs to be out of order and can break security tokens/authentication.

**OP16 — Easy: What is the difference between a physical server, a virtual machine, and a container? When would you run a workload directly on bare metal instead of virtualizing it?**
*   Physical: Hardware only.
*   VM: Hypervisor abstracts hardware; OS runs on top.
*   Container: Shares Host Kernel; isolates processes.
Run on Bare Metal when you need maximum I/O performance (high-frequency trading), specific kernel tuning not allowed by hypervisors, or extremely high-performance GPU workloads.

**OP17 — Easy: Explain the difference between a UPS (Uninterruptible Power Supply) and a generator in a data center context. Why do you need both? What is the role of an ATS (Automatic Transfer Switch)?**
UPS provides immediate battery power during a blackout (seconds/minutes). A Generator provides long-term power (hours/days). You need both because a generator takes 30–60 seconds to start up—the UPS bridges that gap. The **ATS** automatically switches the building's power source from Grid to Generator.

**OP18 — Medium: Explain the difference between active-passive and active-active clustering for high availability. You have a pair of Linux servers running a PostgreSQL database — describe how you would implement HA using Pacemaker/Corosync, covering fencing (STONITH), virtual IPs, and failover behavior.**
Active-Passive: One node works, one waits. Active-Active: Both handle traffic simultaneously.
For Postgres: Use **Pacemaker/Corosync**. Configure a Virtual IP (VIP) that floats between nodes. Use **STONITH** to ensure only one node owns the VIP at once. If Node A fails, Corosync detects it, Pacemaker fences Node A (reboots it via IPMI), and moves the VIP to Node B.

**OP19 — Hard: You are designing the backup and recovery strategy for a 50-server on-premise environment. Cover: the 3-2-1 rule, RPO/RTO requirements, backup types (full/incremental/differential), deduplication, tape vs disk vs cloud offsite, immutable backups for ransomware protection, and how you test restores. What is the difference between backup and disaster recovery?**
*   **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite.
*   **Backup Types:** Full (all data), Incremental (changes since last backup), Differential (changes since last full).
*   **Deduplication:** Reduces storage by storing unique blocks only.
*   **Immutable Backups:** Write-Once-Read-Many (WORM) storage prevents ransomware from deleting backups.
*   **Testing:** Perform monthly "Restore Drills" to verify RTO/RPO targets.
Difference: Backup is about *data integrity*; Disaster Recovery (DR) is about *business continuity* (restoring services like networking, DNS, etc.).

**OP20 — Hard: Explain how 802.1X (port-based network access control) works in an enterprise wired network. Cover: the supplicant, authenticator, and authentication server roles; EAP methods (EAP-TLS vs PEAP); RADIUS; dynamic VLAN assignment; and what happens to a device that fails authentication. How does MAB (MAC Authentication Bypass) work for devices that don't support 802.1X?**
In **802.1X**: The **Supplicant** (client software) sends credentials to the **Authenticator** (switch), which forwards them to the **Authentication Server** (RADIUS).
*   **EAP-TLS:** Uses certificates (most secure). **PEAP:** Uses usernames/passwords over a TLS tunnel.
*   **Dynamic VLANs:** RADIUS tells the switch which VLAN to put the port on after successful auth.
If auth fails, the port is shut down or moved to a "Guest" VLAN.
**MAB** allows non-802.1X devices (like printers) by checking their MAC address against a whitelist in the RADIUS database.
