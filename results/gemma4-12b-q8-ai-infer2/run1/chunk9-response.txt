## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because they violate the **Restricted Pod Security Standard**. In the previous Baseline standard, `runAsNonRoot: true` was allowed even if a specific user wasn't defined (the container would default to its internal USER directive). However, the Restricted standard requires that any pod with `runAsNonRoot: true` must also have an explicit `runAsUser` or `runAsGroup` defined in the `securityContext`. Because the new base image defaults to `USER root`, and the manifest lacks an explicit non-root UID, Kubernetes rejects the pod creation/startup during the admission phase of the Restricted policy enforcement.

**SC1-B:** 
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[].restartCount > 0 and .status.containerStatuses[].state.waiting.reason == "CrashLoopBackOff" | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.template.spec.securityContext}'
```

**SC1-C:** 
*   **Image Fix:** Update the Dockerfile to include a specific non-root user (e.g., `USER 1000`).
*   **Manifest Change:** Explicitly set `runAsUser: 1000` in the Deployment spec’s `securityContext`.
*   **CI Gate:** Add a `kube-linter` or `checkov` step in the CI pipeline to validate Pod Security Standards before merging.
*   **Rollout:** Use a **Canary deployment** strategy. Deploy the updated version to a small subset of users first, verify health via Prometheus metrics, then perform a rolling update (`maxSurge: 25%`) to ensure zero downtime.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:** Stale data occurs because PostgreSQL asynchronous replication does not guarantee that all WAL (Write Ahead Log) records are applied to the replica before it is promoted. In cross-region setups, high latency often forces an "asynchronous" mode where the primary acknowledges writes before they reach the secondary. This creates a "replication lag." To quantify this window, I would check the `pg_last_xact_replay_timestamp()` on the replica vs. the current time and compare it against the last committed transaction timestamp on the primary.

**SC2-B:** 
To prevent Terraform from destroying/recreating resources, use the `import` block or command:
1.  Identify the new RDS ARN.
2.  Update the HCL to point to the new instance's attributes.
3.  Run: `tofu import aws_db_instance.primary <new_rds_id>`
4.  Use `tofu state rm` for the old resource if necessary.
5.  Update dependent resources by changing their IDs in the variables file and running `tofu plan` to ensure only updates occur.

**SC2-C:** 
*   **Connection Management:** Use **RDS Proxy** for better connection pooling and failover handling compared to PgBouncer, as RDS Proxy handles the DNS swap automatically during failover.
*   **Failover:** Implement **Route53 Health Checks** with a Failover Routing Policy (DNS level).
*   **Retry Logic:** Implement exponential backoff with jitter at the application layer.
*   **RPO:** To achieve RPO < 1s, I would recommend **Aurora Global Database**, which uses dedicated storage replication rather than standard streaming replication, providing much lower lag and faster cross-region promotion.

**SC4-A:**

2.  **NFS Mounts:** Solution: Use a CSI driver supporting ReadWriteMany (RWX).
3.  **Oracle 19c Connection:** Solution: Use a connection pooler (PgBouncer style) and ensure K8s egress allows DB access.
4.  **IBM MQ Integration:** Solution: Use a sidecar or dedicated service to bridge K8s to on-prem MQ via a VPN/DirectConnect.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:** Use **SPIFFE/SPIRE** to issue SVIDs (identities) to workloads. In AWS, map SPIRE identities to IAM roles via OIDC. For on-prem, use an SPIRE agent as a gateway. This allows a pod in AWS to present a signed JWT that is verified against the same root of trust as the on-prem service.

**SC6-B:** 
Use `for_each` over a list of services to create PrivateLink endpoints. Ensure Security Groups have no `0.0.0.0/0` rules and only allow traffic from specific VPC CIDRs or Transit Gateway IDs.

**SC6-C:** 
*   **Direct Connect:** Best for consistent bandwidth but high cost/lead time.
*   **ECMP VPN:** Good for redundancy; handles multiple tunnels across different paths.
*   **Tailscale/Netbird:** Easiest "Zero Trust" overlay; uses WireGuard for encryption and simplifies routing significantly by abstracting the underlying network.
*   **Recommendation:** Tailscale/Netbird for rapid deployment of zero-trust mesh, unless throughput exceeds 1Gbps consistently.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:** Manual applies cause **State Divergence**. Lack of locking causes **Race Conditions**: if two engineers apply simultaneously, one's changes can overwrite the other's, leading to corrupted state files (e.g., resource deletion). Direct edits bypass version control entirely, making it impossible to audit or replicate in staging.

**SC7-B:** Use GitLab CI with:
```yaml
deploy_prod:
  stage: deploy
  script:
    - tofu fmt -check
    - tofu validate
    - tofu plan -out=plan.tfstate
    - tofu apply -auto-approve plan.tfstate
  when: manual
  environment: production
```
Use a DynamoDB table as a backend lock provider in OpenTofu.

**SC7-C:** Run a scheduled `tofu plan` every hour; if the output is non-empty, alert Slack. Use an **Admission Controller** (Kyverno) to block any `kubectl edit` on critical resources except from the CI service account IP range. Structure Helm values using a "base" chart and environment-specific `values.yaml`.

## SC9 — Medium — Securing a Public-Facing API After a Breach

**SC9-A:** 
1.  **BOLA:** Violates Authorization principle. Fix: Check ownership (`user_id == current_user`).
2.  **Data Leakage:** Violates Least Privilege. Fix: Use Serializers to exclude internal fields.
3.  **No Rate Limiting:** Violates Availability. Fix: WAF rate limiting.
4.  **Keys in URL:** Violates Secure Transport. Fix: Move to `Authorization` header.

**SC9-B:** Configure AWS WAFv2 with an IP rate limit rule and a Geo-match rule using a variable `${allowed_countries}`. Add a regex match rule to block any request containing `?api_key=`.

**SC9-C:** Transition from API Keys to **OAuth2/OIDC**. Issue short-lived JWTs. Use an **API Gateway (Kong)** to handle the heavy lifting of auth, rate limiting, and logging so the Django app only handles business logic. Migrate by supporting both keys and JWTs simultaneously for a transition period before deprecating keys.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:** 
*   **Active-Passive:** Lower cost; RPO is limited by replication lag. Meet RTO by automating failover via DNS/GSLB.
*   **Active-Active:** Better RTO but complex state management. With 12ms latency, Active-Active is feasible for Redis/RabbitMQ if using multi-region clusters. For Postgres, use synchronous replication or Aurora Global Database.
*   **Replication:** Postgres (Streaming), Redis (Global Datastore/Sentinel), RabbitMQ (Shovel plugin), MinIO (Bucket Replication).

**SC10-B:** Ansible playbook would template `/etc/patroni.yml` with `synchronous_standby_names = "standby_dallas"`, set up etcd cluster across sites, and ensure `recovery_min_apply_lag` is tuned for the 12ms link.

**SC10-C:** 
1.  **Detection:** GSLB health check fails on Chicago endpoint.
2.  **DNS Failover:** Update Route53 to point to Dallas IP.
3.  **Promotion:** Patroni promotes Dallas primary.
4.  **State Sync:** MQ Shovel moves messages from pending in Chicago to Dallas.
5.  **MinIO:** Catch up via bucket replication.
6.  **Split-Brain Prevention:** Use a quorum-based DCS (etcd) that requires a majority of nodes to agree on who the leader is; since we only have two sites, a third "witness" node in a third region is required to break ties.
