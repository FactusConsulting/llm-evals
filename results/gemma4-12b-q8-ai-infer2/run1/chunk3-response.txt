## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` creates an execution plan by comparing the current state of the infrastructure with the desired configuration defined in the code; it shows what will be created, modified, or destroyed without making changes. `tofu apply` executes the actions proposed in the plan to reach the desired state.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file that maps real-world resources to the configuration blocks in your code. Remote state is critical because it allows teams to share a single source of truth (stored in S3, GCS, etc.), enabling collaboration and providing a mechanism for state locking to prevent concurrent modifications.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an index (0, 1, 2...) to replicate resources. `for_each` uses a map or set of strings/objects. `for_each` is preferred when creating multiple resources where items might be removed or reordered; using `count` can cause "index shifting" where deleting item #1 causes all subsequent items to shift indices, leading to unnecessary recreations.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This is known as "Configuration Drift." During the next `tofu plan`, OpenTofu performs a refresh by querying the cloud provider's API. It detects the discrepancy between the actual state and the desired configuration and proposes a plan to revert the manual change back to the defined configuration.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
variable "vm_names" {
  type    = set(string)
  default = ["web1", "web2", "web3"]
}

resource "null_resource" "vms" {
  for_each = toset(var.vm_names)
  name     = each.key
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads the entire state file of another project, which can be slow and tightly couples modules. Outputs are specific values exported from a module. The recommended alternative is using a shared Key-Value store (like AWS SSM Parameter Store or HashiCorp Consul), as it decouples the modules; Module B consumes a parameter rather than directly depending on Module A's state file.

**T7 — Hard: You have a module that provisions an RKE2 cluster... explain why [it fails] and how to fix it.**
The output is empty because `tofu plan/apply` happens before the provisioner finishes its execution. To fix this, ensure the downstream resources depend on the resource containing the output, but more importantly, use a pattern where the configuration is generated by a script and captured into a local file or variable that OpenTofu can read, or use a specialized module that handles the "wait" logic internally.

**T8 — Medium: What is tofu import, and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
Import brings existing infrastructure into management. The CLI command is manual and requires identifying every individual resource ID. The `import` block allows for declarative imports within your code, making it easier to manage multiple resources at once and keep the import process version-controlled.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a placeholder for values provided during runtime. An **Input Variable** is a value you provide *to* the configuration (e.g., instance size). An **Output Value** is a piece of information produced *by* the configuration (e.g., the IP address of the created VM).

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates OpenTofu's configuration into API calls for specific platforms (AWS, Azure, etc.). If you run `plan` without `init`, the command will fail because the necessary provider binaries have not been downloaded or initialized in the local directory.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It contains the exact versions and hashes of providers used in the project. Committing it ensures that every team member and CI/CD pipeline uses identical provider versions, preventing "it works on my machine" issues caused by minor provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` deletes all resources managed by the configuration. To target only one resource, use the `-target` flag: `tofu destroy -target=aws_instance.web_server`.

**T13 — Easy: What is a data source in OpenTofu? Give an example.**
A data source allows you to fetch information about existing infrastructure *without* managing it. Example: Fetching the ID of an existing VPC created by another team so you can reference its Subnet IDs in your own module.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are inputs provided by the user (external). Locals are internal values derived from other variables or logic within the module. Use `locals` for complex calculations, repeated strings, or formatting logic that doesn't need to be changed by the end-user.

**T15 — Medium: What is the lifecycle block in a resource? Explain create_before_destroy, prevent_destroy, and ignore_changes with a use case for each.**
The `lifecycle` block controls how OpenTofu handles specific actions on a resource.
- `create_before_destroy`: Create a new instance before deleting the old one (e.g., Blue/Green deployment).
- `prevent_destroy`: Error out if any action would delete the resource (e.g., production database).
- `ignore_changes`: Ignore updates to specific attributes (e.g., ignoring tags updated by an external autoscaling group).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has been renamed or relocated in the code configuration. It allows you to change the address of a resource in your `.tf` files while telling OpenTofu to update the state file mapping instead of destroying and recreating the physical infrastructure.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG) to determine execution order. **Implicit** dependencies are created automatically when one resource references an attribute of another. **Explicit** dependencies use the `depends_on` argument. `depends_on` forces a strict sequence; overusing it prevents OpenTofu from running independent tasks in parallel, which significantly slows down deployment times.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time.**
1. **State Splitting:** Break the project into smaller states/workspaces (reduces size of each refresh).
2. **Data Source Optimization:** Use data sources for lookups rather than complex module outputs.
3. **Module Granularity:** Reduce deep nesting of modules that require heavy recursive calculations.
4. **Targeted Plans:** Use `-target` or specific workspace logic to only plan what is necessary. *Tradeoff:* Complexity increases as you manage multiple state files instead of one.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released? How do you manually break a lock, and what are the risks?**
Locking prevents two people from applying changes simultaneously by creating a "lock" entry in the backend (e.g., DynamoDB). If a process crashes, the lock remains. You can break it using `tofu force-unlock <LOCK_ID>`. The risk is that if another person actually started an operation during the crash, breaking the lock could lead to state corruption.

**T20 — Hard: Describe the step-by-step process to migrate local state to S3 with DynamoDB locking.**
1. Define the new `backend` block in your code (S3 + DynamoDB table name).
2. Run `tofu init -migrate-state`. This copies the existing local `.tfstate` file into the S3 bucket.
3. Verify by running `tofu plan`; ensure it shows "No changes" (meaning the remote state matches your current config).
4. Confirm the S3 bucket contains the updated JSON state file.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
A **Task** is a single action (e.g., install a package). A **Role** is a structured collection of tasks, variables, and files organized for reusability. A **Playbook** is a list of plays that map hosts to roles/tasks.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
Ansible Facts are system information gathered automatically at the start of a play. You access the OS family using the variable `ansible_os_family` (e.g., `RedHat`, `Debian`).

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
- `command`: Runs the command directly (no shell features like pipes or redirects). Use for simple commands.
- `shell`: Runs through the system shell (`/bin/sh`). Use when you need pipes (`|`), wildcards, or environment variables.
- `raw`: Bypasses Python requirements on the target. Use only if the target machine doesn't have Python installed.

**A4 — Medium: How does Ansible handle idempotency? Give an example.**
Ansible checks the current state before executing a task; if the desired state matches reality, it does nothing. 
*Idempotent:* `apt: name=nginx state=present` (only installs if missing).
*NOT Idempotent:* `shell: echo "data" >> /file` (appends every time the playbook runs).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS family
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```

**A6 — Hard: Explain Ansible's variable precedence order.**
Precedence is complex, but generally: **Extra vars** (`-e`) > **Host vars** > **Group vars** > **Role defaults**. Specifically, `extra_vars` have the highest priority, while `role defaults` are overridden by almost everything else.

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this?**
Use the `serial` keyword at the play level. To ensure exactly 3 finish then others start, use two plays or group hosts into two groups (group1 with 3 hosts, group2 with 47). Alternatively, set `serial: 3`, which processes them in batches of 3. For a strict "first 3" requirement, split the inventory into two groups and run two separate plays.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
Ansible Vault encrypts files/variables for security. Use `ansible-vault encrypt_string "secret_value"` to get an encrypted string that can be pasted directly into a standard YAML file.

**A9 — Easy: What is an Ansible inventory file? Difference between static and dynamic?**
An inventory file lists the managed hosts. **Static** inventory is a manual list of IPs/hostnames in a file. **Dynamic** inventory uses a script or plugin to fetch host lists from cloud APIs (e.g., AWS EC2 tags) as they change in real-time.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
Handlers are tasks that only run when notified by another task (usually triggered by a change). They run at the end of the play. You trigger them using the `notify` keyword in a task.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
It is the global configuration file for Ansible. Common settings: `forks` (parallelism), `remote_user`, and `host_key_checking`.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
`register` saves the output of a task into a variable. Example: Registering `result` from a command; then access it via `{{ result.stdout }}` in the next task.

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other?**
- `import_tasks`: Static. Parsed at the start of the playbook. Faster but cannot be conditional.
- `include_tasks`: Dynamic. Parsed only when reached. Allows for logic/conditionals (`when`). Use `include_tasks` if your decision to run tasks depends on data gathered during the play.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Galaxy is a public repository for community-shared roles. Create a `requirements.yml` listing the role names and versions, then run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. Difference between ssh, local, and network_cli.**
Connection plugins define *how* Ansible talks to the host. **ssh** (default) uses SSH. **local** runs the task on the control node itself. **network_cli** connects to devices like switches using CLI commands instead of SSH/Python.

**A17 — Hard: Explain how delegate_to and run_once work. Give a practical example.**
- `delegate_to`: Runs a task on a different host than the one currently being processed (e.g., running a command on localhost).
- `run_once`: Ensures a task runs exactly once across all hosts in a group. 
Example: Updating an external Load Balancer's config based on info gathered from a remote web server; `delegate_to: localhost` and `run_once: true` ensures only one update call happens to the LB.

**A18 — Hard: You need to manage a fleet of 500 hosts... Identify at least 4 strategies to improve performance.**
1. **Forks:** Increase number of parallel processes (`forks`).
2. **Pipelining:** Reduces the number of SSH connections per task.
3. **Fact Caching:** Store facts in Redis/Memcached so they aren't re-gathered every play.
4. **Mitogen:** A plugin that replaces the standard Ansible execution engine with a faster, multiplexed connection system. *Tradeoff:* Mitogen can occasionally have compatibility issues with complex modules.

**A19 — Hard: Explain how Ansible Jinja2 templating works. Difference between {{ }}, {% %}, and {# #}? Write a template snippet for nginx upstream block.**
- `{{ }}`: Expression evaluation (variables).
- `{% %}`: Logic (loops, if statements).
- `{# #}`: Comments (not rendered).
Snippet:
```jinja2
upstream backend {
  {% for server in servers %}
  server {{ server.ip }};
  {% endfor %}
}
{# Health check comment #}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment across 20 servers using Ansible.**
Use `serial` to process hosts in small batches (e.g., `serial: 2`). Use a `block`/`rescue` structure: inside the `block`, perform the update; use the `uri` module to verify health. If the `uri` check fails or the task errors out, the `rescue` block triggers a rollback (reverting the version) and stops the play before it hits the next batch of servers.
