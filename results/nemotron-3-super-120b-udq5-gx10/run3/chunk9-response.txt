
**SC1-A**  
The cluster now enforces the **Restricted** Pod Security Standard (PSS). Restricted requires:  

* `runAsNonRoot: true` **and** an explicit non‑zero `runAsUser` (or `runAsGroup`).  
* No privileged containers, no `allowPrivilegeEscalation`, read‑only root FS, etc.  

When `runAsNonRoot: true` is set **without** `runAsUser`, Kubernetes falls back to the image’s `USER` directive. The rebuilt images use `cgr.dev/chainguard/static:latest`, which defaults to `USER root`. The container therefore starts as UID 0, violating the Restricted rule. The admission controller admits the pod (the rule is validated at creation time) but the container is immediately killed by the kubelet for running as root while `runAsNonRoot` is true, causing the container to exit with a non‑zero code and the pod to enter **CrashLoopBackOff**.  

Baseline PSS only required `runAsNonRoot: true` (it did not enforce an explicit non‑zero UID), so the same manifests passed before the upgrade.

**SC2-A**  
Promoting a cross‑region read replica creates a **new primary** that may be **behind** the former primary because Amazon RDS ships WAL asynchronously.  

* **Replication lag** – The replica only has applied WAL up to the last received LSN. Any writes committed on the old primary after that LSN are **not** present on the replica. When the replica is promoted, those missing writes are lost, so reads return stale (pre‑promotion) data for the missing window.  
* **WAL shipping** – RDS uses PostgreSQL streaming replication; WAL records are sent over the network to the replica and applied asynchronously. Across regions the round‑trip adds latency, increasing lag.  
* **Data‑loss scenarios** – If the primary fails before the replica has flushed the latest WAL, those transactions are lost forever (asynchronous replication). No guarantee of zero data loss.  

**How to quantify the loss window:**  
1. On the old primary (if still reachable) run: `SELECT pg_current_wal_lsn();` → LSNₚ.  
2. On the replica (before promotion) run: `SELECT pg_last_wal_received_lsn();` → LSNᵣ.  
3. The difference (`pg_wal_lsn_diff(LSNₚ, LSNᵣ)`) gives the amount of un‑replicated WAL; convert to time using the average WAL generation rate (e.g., `pg_wal_lsn_diff / pg_wal_insert_rate`).

**SC2-C**  
*Preferred design:* **Aurora Global Database** (PostgreSQL‑compatible) with a primary in us‑east‑1 and a secondary in eu‑west‑1.  

* Why it meets RPO < 1 s & RTO < 1 h:  
  * Storage‑based replication replicates changes in **sub‑second** (typically < 1 s) across regions.  
  * Failover is automatic: Aurora promotes the secondary within ~30 s; application can reconnect via the cluster endpoint.  
  * No data loss because the secondary is a **synchronous** copy of the storage layer.  

*If staying with standard RDS:*  
  * Deploy **RDS Proxy** (or AWS Lambda‑based connection pool) in each region to absorb connection churn.  
  * Use **Route53 health checks** with a failover routing policy: primary endpoint health‑checked; on failure, traffic shifts to the secondary endpoint.  
  * Application implements **exponential back‑off** and idempotent retries.  
  * For near‑real‑time replication, enable **RDS logical replication** or **AWS DMS** CDC to keep the replica within a few seconds; monitor `pg_last_wal_receive_lsn` lag.  

*Avoid PgBouncer alone* – it does not handle cross‑region failover; RDS Proxy integrates with Aurora’s automatic promotion and provides IAM authentication, TLS, and connection multiplexing.

**SC3-C**  
*Hardened pipeline*  

1. **Base image pinning** – In Dockerfile use `FROM node@sha256:<digest>` (no tags).  
2. **Image signing** – After `docker build`, run `cosign sign --key cosign.key <image>`; push the signature to the same registry (or a transparency log).  
3. **SBOM generation** – Run `syft <image> -o cyclonedx > sbom.xml` and attach as an attestation (`cosign attest`).  
4. **Admission controller** – Deploy **Kyverno** or **OPA Gatekeeper** policy that:  
   * Requires a valid Cosign signature (`cosign verify --key <pubkey>`).  
   * Enforces that the image’s base digest matches an allowed list (from a ConfigMap).  
   * Rejects images without an SBOM attestation.  
5. **CI gate** – Before pushing to the registry, run:  
   * `trivy image --severity HIGH,CRITICAL <image>` (fail on any).  
   * `cosign verify --key <pubkey> <image>` (fail if unsigned).  
   * `cosign attest verify --type sbom <image>` (fail if missing).  
6. **Notary v2** – Can be used as the trust root; Cosign signatures are stored in the OCI image format and can be verified by Notary v2 delegates, providing an additional layer of trust for environments that still rely on Notary.  

Result: any tampered base image or compromised build step will be blocked before the image reaches the cluster.

**SC4-A**  
| Blocker | Why it’s a problem in K8s | Solution |
|---------|--------------------------|----------|
| **1. In‑memory HTTP sessions** | Sessions are lost when a pod is rescheduled; sticky sessions cannot be guaranteed across nodes. | Move session store to an external, highly‑available store (Redis or DynamoDB). Use Spring Session Redis or similar. |
| **2. Local NFS mount for uploads** | PVCs with `ReadWriteOnce` cannot be shared; the app expects many pods to write to the same NFS export. | Provision an NFS‑CSI PV with `accessModes: ReadWriteMany` (see SC4‑B). |
| **3. On‑prem Oracle 19c** | Direct JDBC to an on‑prem DB creates latency, network‑tier coupling, and makes HA difficult. | Either keep Oracle behind a VPN/Direct Connect and use a **service mesh** (Istio) to route, or migrate to a cloud‑compatible Oracle (Amazon RDS for Oracle, Azure Database for Oracle) or a PostgreSQL compatible schema. |
| **4. IBM MQ coupling** | MQ client libraries often rely on native IPC or specific OS libraries; running them in a restricted container can fail. | Deploy MQ client as a **sidecar** (or use the MQ IBM Cloud offering) and expose via a localhost port; or use the MQ JMS bridge over TCP with proper TLS. |
| **5. Bare‑metal OS/hardware assumptions** | The monolith may rely on /dev devices, kernel modules, or specific sysctl settings not available in a default container. | Audit the app; containerize with necessary `securityContext` (privileged only if absolutely required) or use **hostPath**/`device` plugins for the few needed resources, then replace with cloud‑native equivalents where possible. |

**SC4-C** – Strangler Fig migration (3 phases)

| Phase | What moves | Traffic split | IBM MQ handling | Rollback |
|-------|------------|---------------|-----------------|----------|
| **1 – Read‑only front‑end** | Deploy a thin API gateway (Kong/Envoy) in front of the legacy F5. * **Error rate** (5xx) < 0.1 %  
* **99th‑percentile latency** ≤ baseline + 20 %  
* **Saturation** (CPU/Memory) < 80 % on K8s nodes  
* **MQ queue depth** stable (no back‑pressure growth)

*PostgreSQL lock diagnostic*  
```sql
SELECT
  blocked.pid        AS blocked_pid,
  blocking.pid       AS blocking_pid,
  blocked.usename    AS blocked_user,
  blocking.usename   AS blocking_user,
  blocked.query      AS blocked_query,
  blocking.query     AS blocking_query,
  now() - blocked.query_start AS blocked_duration
FROM pg_locks blocked
JOIN pg_stat_activity blocked_activity ON blocked.pid = blocked_activity.pid
JOIN pg_locks blocking ON blocked.locktype = blocking.locktype
    AND blocked.database IS NOT DISTINCT FROM blocking.database
    AND blocked.relation IS NOT DISTINCT FROM blocking.relation
    AND blocked.page IS NOT DISTINCT FROM blocking.page
    AND blocked.tuple IS NOT DISTINCT FROM blocking.tuple
    AND blocked.virtualxid IS NOT DISTINCT FROM blocking.virtualxid
    AND blocked.transactionid IS NOT DISTINCT FROM blocking.transactionid
    AND blocked.classid IS NOT DISTINCT FROM blocking.classid
    AND blocked.objid IS NOT DISTINCT FROM blocking.objid
    AND blocked.objsubid IS NOT DISTINCT FROM blocking.objsubid
    AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_activity ON blocking.pid = blocking_activity.pid
```

**SC5-C**  
*Architectural fixes*  

1. **CQRS** – Separate read model (served by checkout-service) from write model (handled by a dedicated writer service). Reconciliation jobs write to the write model; reads use a **read replica** (or a materialized view).  
2. **Read replica for reconciliation** – Deploy a PostgreSQL read‑only replica in the same AZ; point the CronJob to that replica’s connection string. Replication lag is typically < 1 s, acceptable for batch jobs.  
3. **Bulkhead isolation** – Limit the inventory-service’s DB pool: `db.SetMaxOpenConns(20)` and `db.SetMaxIdleConns(5)`. Use a separate connection pool for the CronJob (different service account) so it cannot exhaust the serving pool.  
4. **CronJob scheduling** – Run the reconciliation job at a low‑traffic window (e.g., 02:00 UTC) or use a **Kubernetes Job with a parallelism limit** (`parallelism: 1`) and a `backoffLimit`.  
5. **PodDisruptionBudgets** – For the inventory-service Deployment, set `maxUnavailable: 0` (or 1) to ensure the scheduler never evicts more than the allowed number during a node drain.  
6. **Resource quotas** – Create a namespace `batch-jobs` with a quota: `requests.cpu: 2`, `requests.memory: 4Gi`, `limits.cpu: 4`, `limits.memory: 8Gi`. Place the CronJob there; the scheduler will not allow it to consume more than its share, protecting the serving namespaces.  

Result: the reconciliation job can no longer starve the serving pods, eliminating the latency spike.

**SC6-A**  
*Identity & access layer*  

| Component | Role |
|-----------|------|
| **SPIFFE IDs** | Every workload (VM, container, function) gets a cryptographically verifiable X.509 SVID or JWT‑SVID from its local SPIRE agent. |
| **SPIRE Server** | Central trust root; runs in each environment (on‑prem vSphere, AWS, Azure) and federates via **inter‑server trust bundles** (exchanged periodically). |
| **AWS IAM Roles for Service Accounts (IRSA)** | Map a Kubernetes service account to an IAM role; the pod’s SPIRE agent can use the service account token to assume the role via OIDC federation. |
| **Azure Managed Identities + Workload Identity Federation** | Azure AD issues tokens to workloads that present a Kubernetes service account JWT; the SPIRE agent can exchange it for an Azure access token. |
| **On‑prem PKI** | Internal CA issues certificates to SPIRE agents; agents renew automatically. |
| **Federation** | Each SPIRE server exports its trust bundle (root CA) to the others; agents verify SVIDs issued anywhere in the federation. No shared secrets – only public keys. |

Result: a workload in AWS can present its SPIFFE SVID to an on‑prem service; the service validates the SVID against the federated trust bundle and grants access based on the SPIFFE ID (e.g., `spiffe://example.org/aws/prod/paymentsvc`).

**SC6-C** – Connectivity options  

| Option | Cost | Bandwidth | Encryption | Failover | Fit with Zero‑Trust |
|--------|------|-----------|------------|----------|---------------------|
| **AWS Direct Connect (DX)** | Higher port‑hour fee + data transfer | 1 Gbps–100 Gbps (dedicated) | MACsec (optional) + IPsec over DX | Can provision **multiple DX connections** with LACP for active‑active; BGP failover < 50 ms. | Provides a private, non‑internet path; still requires SPIFFE/SPIRE for workload auth – network location is not trusted. |
| **Second VPN + ECMP** | Low (VPN hourly) + data | 2 × 1 Gbps (aggregate ~2 Gbps) | IPsec (same as existing) | Two tunnels; ECMP spreads traffic; if one fails, traffic shifts to the other (convergence ~seconds). | Still relies on Internet‑based IPsec; zero‑trust auth remains at the workload layer. |
| **Hybrid mesh (Tailscale/Netbird)** | Low‑moderate (per‑node fee) | Limited by underlying internet; can burst to 1 Gbps+ per node | WireGuard (encrypted) | Mesh automatically reroutes; node failure triggers sub‑second reconnect. | Provides **service‑to‑service mutual TLS** via WireGuard; can be layered on top of SPIFFE for double‑defense, but adds another trust boundary. |

**Recommendation:** For a regulated, high‑throughput environment, **AWS Direct Connect** (dual‑link for redundancy) is the best fit – it gives deterministic, high bandwidth, low jitter, and keeps traffic off the public internet. Zero‑trust is enforced at the workload layer (SPIFFE/SPIRE, mTLS) regardless of the underlying link.

**Routing changes:**  
* With DX: advertise on‑prem routes via BGP to the DX GW; VPC route tables point to the TGW for inter‑VPC traffic.  
* With second VPN: add two VPN connections to the TGW, enable ECMP, adjust BGP weight.  
* With mesh: install the mesh agent on each workload; the mesh provides its own overlay CIDR; existing VPC routing remains for internet‑bound traffic, but service‑to‑service traffic goes via the mesh.

**SC7-A**  
*Drift sources & dangers*  

1. **Manual `tofu apply` from laptops** – No state locking → two concurrent runs can corrupt the state file (partial writes, lost resources). Result: resources may be created twice (duplicate) or deleted while still in use, causing outages or orphaned cloud assets.  
2. **Divergent Helm values** – Values edited outside Git mean the cluster no longer matches the repo; a later `helm upgrade` (or CI) will overwrite with stale values, wiping custom config (e.g., TLS certs, feature flags).  
3. **`kubectl edit` on ConfigMaps** – Changes bypass Git and CI; if the ConfigMap is later re‑applied from Helm, the edit is lost, causing configuration drift and potential mis‑behavior (e.g., wrong feature flags).  

All three break the **single source of truth** principle, making audits impossible and increasing the risk of configuration‑driven incidents.

```bash
#!/usr/bin/env bash
set -euo pipefail
PROM_URL="http://prometheus:9090"

# 1. Get all metric names

echo "Metric Name                | Series Count | Top Label (unique vals)"

for m in $METRICS; do
  # series count for this metric
  COUNT=$(curl -sG "$PROM_URL/api/v1/series" --data-urlencode "match[]=$m" | jq '.data | length')
  if [[ $COUNT -eq 0 ]]; then continue; fi

  # get label with most unique values for this metric
  # fetch a sample series to list its labels
  LABELS=$(curl -sG "$PROM_URL/api/v1/label" --data-urlencode "match[]=$m" | jq -r '.data[]')
  BEST_LABEL=""
  BEST_UNIQUE=0
  for lbl in $LABELS; do
    UNIQUE=$(curl -sG "$PROM_URL/api/v1/label/$lbl/values" --data-urlencode "match[]=$m" | jq '.data | length')
    if (( UNIQUE > BEST_UNIQUE )); then
      BEST_UNIQUE=$UNIQUE
      BEST_LABEL=$lbl
    fi
  done
  printf "%-26s | %12d | %s (%d)\n" "$m" "$COUNT" "$BEST_LABEL" "$BEST_UNIQUE"
```

**SC8-C** – Redesigned observability stack  

* **Metrics** – Replace Prometheus with a **Cortex/Mimir** cluster (horizontal scalability, multi‑tenant). Use **remote‑write** from agents; Mimir handles 50 M series with ~30 % less RAM per node due to chunk sharing. Enable **per‑tenant series limits** via Mimir’s `-limits.max-series-per-user`.  
* **Logs** – Deploy Loki in **microservices mode**: separate `distributor`, `ingester`, `querier`, `compactor` rings. Ingester count scaled to ingest rate; use **chunk target size** 1 MiB and `max_age` 12h to reduce memory. Enable **retention** and **index** stored in S3/GCS.  
* **Traces** – Tempo with **S3 backend** (instead of local). Use the `traceql` query language; enable **block compaction** and **index** stored in S3 for fast look‑ups. Set `max_block_bytes` to 256 MiB to keep query latency low.  
* **Cardinality governance** –  
  * Create a **recording rule** per team that drops high‑cardinality labels (e.g., `job`, `instance`) via `labeldrop`.  
  * Enforce via **Prometheus/Mimir** `scrape_config` `metric_relabel_configs` that drop or hash labels before ingestion.  
  * Alert on `sum by (team) (series_count)` exceeding a threshold.  
* **Chargeback** – Label every metric/log/trace with `team=` and `cost_center=`. Use Mimir/Loki/Tempo’s built‑in **usage reporting** (e.g., Mimir’s `-target-health-interval` and `store-gateway` metrics) to compute bytes stored per team. Export to a billing system (e.g., Cloudability) and show monthly cost per team.  

Result: the stack scales horizontally, cardinality is kept under control, and teams pay for the telemetry they generate.

**SC9-C** – Defense‑in‑depth & migration  

1. **Auth migration**  
   * Phase 1 – Dual‑auth: accept both `Authorization: Bearer <JWT>` **and** the legacy `api_key` query param.  
   * Phase 2 – Issue short‑lived JWTs (e.g., 15 min) via an OAuth2 authorization server (AWS Cognito or Keycloak). Store JWTs in HTTP‑only, Secure cookies or require the `Authorization` header.  
   * Phase 3 – After a grace period (2 weeks), disable the query‑param check and reject any request lacking a valid JWT.  
   * Use feature flags (`launchdarkly` or internal config) to roll back quickly if issues arise.  

2. **API gateway** – Place **AWS API Gateway** (REST or HTTP) in front of the ALB. Enable:  
   * **JWT authorizer** (Cognito user pool or Lambda authorizer) – validates signature, scopes, expiration.  
   * **Rate limiting** (burst & rate) at the gateway level.  
   * **Request/response transformation** (strip internal fields, add security headers).  
   * **WAF integration** (reuse the web ACL from SC9‑B).  

3. **Field‑level encryption** – For PII columns, use **AWS RDS encryption** + **application‑level encryption** with AWS KMS:  
   * Generate a data key per record, encrypt the field, store ciphertext + key ID.  
   * Libraries like `aws-encryption-sdk` or `PyNaCl` simplify this.  

4. **Audit & logging** – Enable **CloudTrail data events** on the API Gateway (or ALB) to capture `AuthorizationHeader`, `sourceIP`, `userAgent`. Forward logs to a SIEM for anomaly detection.  

5. **Monitoring** – Alert on spikes in `401/403` responses, sudden increase in request size, or JWT validation failures.  

This layered approach ensures that even if one control fails (e.g., a mis‑configured WAF), the others (JWT validation, field encryption, rate limiting) still protect the API.

|----------|-------------|--------------------------|-----------------------|----------------------|

**SC10-C** – Automated failover orchestration  

1. **Failure detection**  
   * Deploy a lightweight **heartbeat** (e.g., `blackbox_exporter` TCP probe) from a neutral monitoring VM (or CloudWatch) to the primary site’s VIP.  
   * Site is considered **down** if **≥ 3 consecutive failures** within 30 s (or loss of etcd quorum).  
   * Use **alertmanager** to fire a `SiteDown` alert.

2. **DNS failover**  
   * Use **Route53 latency‑based or failover routing policy** with health checks tied to the VIP.  
   * When health check fails, Route53 automatically switches the DNS A/AAAA record to the DR site’s VIP (TTL ≈ 30 s).  
   * For Istio multi‑cluster, also update a **ServiceEntry** or **VirtualService** weight to 0 % primary / 100 % secondary.

3. **Patroni promotion**  
   * Patroni watches etcd; loss of leader lease triggers automatic **leader election**.  
   * With `synchronous_standby_names='*'` and the standby already synced, the Dallas node becomes the new leader **without data loss**.  
   * Patroni writes the new leader’s endpoint to etcd; applications using the service DNS (which now points to DR) connect to the new primary.

4. **Redis Sentinel failover**  
   * Sentinel monitors the primary; upon failure, it promotes a replica and updates the published IP.  
   * Ensure Sentinel instances are deployed in both sites; cross‑site sentinel communication uses the same VPN/DX link.

5. **RabbitMQ**  
   * Use **quorum queues** (mirrored across nodes) or **federation** with `ack-mode=on-confirm`.  
   * When the primary site loses its nodes, the queues in the DR site continue to accept and acknowledge messages; producers reconnect via the updated DNS/VIP.  
   * Optional: enable **shovel** to pull any un‑acked messages from the failed site after it recovers.

6. **MinIO bucket replication**  
   * Replication is asynchronous but typically < 5 s over the 12 ms link.  
   * On failover, the DR MinIO already holds the most recent objects; any writes that occurred during the brief lag are queued and will be replicated once the primary site is back online (catch‑up mode).  
   * Monitor `mc admin info` replication lag; trigger alert if > 30 s.

7. **Update OpenTofu state**  
   * After the DR site is confirmed as primary, run a **one‑off** `terraform state replace-provider` or `terraform import` to point the `aws_db_instance`, `aws_elasticache_cluster`, etc., resources to the DR endpoints.  
   * Alternatively, keep the Terraform code **agnostic** to the actual endpoint by using a `data "aws_rds_cluster"` that reads the cluster identifier from a **SSM Parameter Store** updated by the failover script.  
   * The script writes the new primary’s ARN to the parameter; Terraform always reads the latest value, so no state mutation is needed.

8. **Split‑brain prevention**  
   * The etcd cluster (used by Patroni) is deployed with **odd number of nodes** (e.g., 3) and a **witness** in a third AZ or cloud region to maintain quorum.  
   * Patroni requires a majority of etcd nodes to elect a leader; if the link between sites partitions, only the side with etcd majority can promote, preventing two primaries.  
   * Additionally, enable **fencing** (e.g., `pg_rewind` or `STONITH`) if using a traditional Pacemaker setup; with Patroni+etcd, split‑brain is avoided by design.

9. **Failback (Chicago → Dallas)**  
   * Once Chicago is restored, **resync** the Chicago PostgreSQL as a standby:  
     * `patronictl -c /etc/patroni.yml pause` (if needed)  
     * `pg_basebackup` from the Dallas primary to bring Chicago up to date.  
   * After replication lag catches up to near‑zero, **trigger a planned switchover**:  
     * Patroni demotes Dallas to standby, promotes Chicago.  
     * DNS/Route53 health check flips back to Chicago after confirming the primary is healthy.  
   * Validate application health, then resume normal traffic.  

All steps can be scripted (Ansible + Shell) and triggered by the `SiteDown` alert via a webhook to an automation runner (e.g., GitLab Runner, Jenkins, or AWS Lambda). The entire failover—from detection to traffic shift—should complete well under the 1‑hour RTO, with RPO effectively zero due to synchronous PostgreSQL replication and near‑real‑time MinIO/Redis/RabbitMQ replication.
