
**AA1** – A monolith bundles all functionality into a single deployable unit; microservices split the system into independently deployable services that communicate over the network.  
*Three problems introduced by microservices:*  
1. **Network latency & partial failures** – calls become remote and can fail independently.  
2. **Data consistency** – transactions span services, requiring patterns like Sagas.  
3. **Operational overhead** – service discovery, monitoring, versioning, and deployment pipelines multiply.

**AA2** – Synchronous communication blocks the caller until a response is received (e.g., HTTP/REST, gRPC). Asynchronous communication lets the caller continue immediately, often via a message broker (e.g., RabbitMQ, Kafka).  

**AA3** – An API Gateway provides API‑specific features (authentication, rate limiting, request/response transformation, routing to multiple back‑ends, aggregation). A reverse proxy simply forwards traffic based on host/path and does TLS termination, load balancing, etc.  
An API Gateway can *replace* a reverse proxy only if you don’t need low‑level TCP/UDP load balancing or generic SSL offloading; otherwise you still need a reverse proxy (or a layer‑4 LB) in front of the gateway for those functions.

**AA4** – The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo it on failure.  
*Choreography*: services listen to events and trigger the next step; no central coordinator. Good for simple, short‑lived flows with few services.  
*Orchestration*: a dedicated saga orchestrator (or workflow engine) tells each service what to do and handles compensations. Preferred for complex, long‑running workflows needing visibility and centralized error handling.

**AA5** – CQRS separates read (query) and write (command) models, allowing each to be optimized independently. Paired with Event Sourcing, writes are stored as an immutable event log; the read model is built by projecting those events. This solves the “read‑after‑write inconsistency” and scaling problems of CRUD, providing auditability, temporal queries, and independent scaling of read vs. write workloads.

**AA6** – Circuit Breaker has three states: **Closed** (requests flow normally, failure count tracked), **Open** (short‑circuit, requests fail fast), **Half‑Open** (limited trial requests to test if service recovered). Unlike simple retry‑with‑backoff, it prevents hammering a failing service and gives it time to recover. Use both: retry for transient glitches, circuit breaker to stop retries when the service is persistently unhealthy.

**AA7** – Multi‑tenant isolation models:  

| Model | Cost | Security | Operational Complexity | Noisy‑Neighbor Risk |
|-------|------|----------|------------------------|---------------------|
| Shared DB, shared schema (row‑level tenant ID) | Lowest (single DB) | Moderate – relies on correct tenant‑ID filtering; bug can leak data | Low – simple schema, backups | High – one tenant’s heavy queries can affect others |
| Shared DB, separate schema per tenant | Moderate (more schemas) | Better – logical isolation; still shared storage | Moderate – schema migrations per tenant | Medium – still shares I/O/CPU |
| Separate DB per tenant | Highest (many DB instances) | Strongest – physical isolation | Highest – provisioning, monitoring, backups per tenant | Lowest – resources isolated per tenant |

Choose based on tenant count, sensitivity, and ops capacity.

**AA8** – *Eventual consistency*: replicas converge over time; reads may see stale data. *Strong consistency*: every read sees the latest write (linearizable).  
To never oversell inventory, use **strong consistency** (or at least read‑your‑writes) on the inventory entity. Architecture:  
- **Data store**: a strongly consistent, horizontally scalable DB (e.g., Google Cloud Spanner, CockroachDB, or a sharded MySQL with synchronous replication).  
- **Pattern**: use a **single‑writer per SKU** (e.g., allocate inventory via a reservation service that locks the row with `SELECT … FOR UPDATE` or uses a distributed lock).  
- **At scale**: shard by SKU/idempotent key, apply **optimistic concurrency** with version numbers, and fallback to a **Saga** for cross‑SKU reservations if needed.

**AA9** – A sidecar proxy runs alongside each service instance, handling all inbound/outbound traffic. In Istio, **Envoy** is the sidecar: it performs load balancing, TLS termination, retries, circuit breaking, telemetry, and policy enforcement.  
- **Data plane**: the set of Envoy proxies that actually forward traffic.  
- **Control plane**: Istiod (or similar) that configures Envoy via xDS APIs, distributes policies, and manages certificates.  
- **mTLS between sidecars** encrypts and authenticates service‑to‑service traffic at the infrastructure level, providing zero‑trust mutual authentication without requiring each app to implement TLS; application‑level TLS would still be needed for end‑to‑end security (e.g., protecting data at rest) but mTLS solves the problem of verifying identity and preventing man‑in‑the‑middle on the mesh.

**AA10** – Strangler Fig: gradually replace pieces of the legacy system by routing new functionality to the new system while keeping the old system alive.  
*Concrete migration for .NET Framework → .NET 8 microservices:*  
1. Deploy an API Gateway (e.g., Kong, Envoy) in front of the monolith.  
2. Identify a bounded context (e.g., “Order Management”). Build a new .NET 8 microservice that implements its API.  
3. Update the gateway to route `/orders/*` to the new service; fallback to monolith for any unimplemented endpoints.  
4. Write automated contract tests to ensure parity.  
5. Iteratively move more contexts (Customer, Product) following the same steps, decommissioning monolith routes as they’re replaced.  
6. Once all traffic is routed to microservices, retire the monolith.

**AA11** – 12‑Factor App methodology (key factors):  
1. **Codebase** – one repo, many deploys.  
2. **Dependencies** – explicit, isolated (e.g., via manifest files).  
3. **Config** – stored in environment, not code.  
4. **Backing services** – treat as attached resources (DB, queue).  
5. **Build, release, run** – strict separation.  
6. **Processes** – stateless, share‑nothing.  
7. **Port binding** – services export via port, not via injection.  
8. **Concurrency** – scale out via process model.  
9. **Disposability** – fast startup/shutdown, robust to SIGTERM.  
10. **Dev/prod parity** – keep environments similar.  
11. **Logs** – treat as event streams (stdout).  
12. **Admin processes** – run as one‑off tasks in same environment.  
These factors enable immutable, portable, observable, and easily scalable cloud‑native deployments.

**AA12** – Event‑driven (Kafka) vs request‑driven (REST/gRPC):  

| Aspect | Kafka (event broker) | REST/gRPC (request‑driven) |
|--------|----------------------|----------------------------|
| **Coupling** | Loose – producers/consumers only know topic schema | Tighter – caller knows endpoint & contract |
| **Scalability** | Horizontal scaling of consumers; high throughput | Scales via instance replication; limited by request‑response latency |
| **Debugging** | Harder – need to trace event flow, offsets | Simpler – request/response logs |
| **Ordering** | Per‑partition ordering guaranteed | No ordering across calls; depends on client |
| **Failure handling** | Retries via consumer groups; dead‑letter topics; replay possible | Retries with idempotency; circuit breakers; fallback responses |
| **When to choose** | High‑volume, asynchronous workflows, audit trails, eventual consistency, decoupled microservices | Low‑latency, request‑reply interactions, synchronous UI/APIs, strong consistency needs |

**AA13** – A load balancer distributes incoming traffic across multiple backend instances.  
- **Layer 4 (transport)**: works on TCP/UDP, makes decisions based on IP/port only (e.g., LVS, AWS NLB).  
- **Layer 7 (application)**: works on HTTP/HTTPS, can inspect headers, cookies, URL paths, and perform content‑based routing, SSL termination, authentication (e.g., HAProxy, NGINX, AWS ALB).  
*Layer 7 required* when you need path‑based routing (e.g., `/api` to one service, `/static` to another) or host‑based virtual hosting.

**AA14** – A message queue stores discrete messages for point‑to‑point delivery (often with acknowledgments). RabbitMQ is a traditional broker supporting exchanges, routing, and guaranteed delivery.  
A log‑based broker like Kafka treats topics as an immutable append‑only log; consumers read at their own offset, enabling replay and multiple independent consumers.  
Pick RabbitMQ for task queues, RPC‑style work distribution, and when you need per‑message acknowledgments and complex routing. Pick Kafka for high‑throughput event streaming, log aggregation, and scenarios where multiple consumers need the same stream with replay capability.

**AA15** – A container is a lightweight, isolated user‑space process that shares the host OS kernel but has its own filesystem, network, and PID namespaces. A VM virtualizes hardware, runs a full guest OS, and incurs higher overhead. Containers are popular for microservices because they start fast, use fewer resources, enable dense packing, and simplify CI/CD pipelines.

**AA16** – Stateless services store no client‑specific data between requests; any needed state is externalized (DB, cache). Stateful services keep data in memory or local disk (e.g., in‑process session store, distributed cache node). Stateless services scale horizontally because any instance can handle any request; stateful services require sticky sessions or state transfer.  
*Example*: Stateless – a REST API that reads/writes a database. Stateful – a WebSocket server that maintains per‑connection chat state in memory.

**AA17** – ORM maps object models to relational tables, allowing CRUD via language objects. Popular ORMs: **Hibernate** (Java), **Entity Framework** (.NET), **SQLAlchemy** (Python), **ActiveRecord** (Ruby).  
Trade‑offs: ORMs boost productivity, reduce boilerplate, and provide portability, but can generate inefficient queries, hide performance costs, and add complexity for advanced SQL features; raw SQL gives full control and performance but requires more manual mapping and boilerplate.

**AA18** – Bulkhead isolates resources (threads, connections, memory) so that failure in one component doesn’t exhaust resources needed by others. In microservices, you can assign separate thread pools or connection pools per downstream service, or deploy each service in its own container/pod with resource limits.  
*Concrete example*: In a Java service, create a dedicated `ExecutorService` with a fixed thread pool for calls to the payment gateway, and another for calls to the inventory service; if the payment gateway slows and fills its pool, the inventory calls still have threads available.

**AA19** – Operational Transformation (OT) vs CRDTs for real‑time collaborative editing:  

| Feature | OT | CRDTs |
|---------|----|-------|
| **Consistency** | Strong eventual consistency if transformation functions are correct; requires central server to order ops | Strong eventual consistency guaranteed by mathematical properties; no central ordering needed |
| **Latency** | Low latency when server is round‑trip; depends on server processing | Can be lower latency for peer‑to‑peer; ops applied locally then propagated |
| **Complexity** | High – need correct transformation functions for all op pairs, handling edge cases | Lower – pick a well‑studied CRDT (e.g., RGA, Yjs) and rely on its merge semantics |
| **Offline support** | Difficult – requires storing ops and replaying with transformation against missed ops | Natural – local edits merge cleanly when connectivity resumes |
| **Choice for offline editing** | **CRDTs** are preferable because they guarantee convergence without needing a central authority to transform conflicting ops, making offline work seamless. |

**AA20** – Distributed tracing challenges in polyglot microservices:  
- **Context propagation**: need to inject trace IDs (W3C Trace Context `traceparent`/`tracestate` or legacy B3) into in‑process logs and across network calls (HTTP headers, gRPC metadata, message broker payloads).  
- **Sampling**: head‑based sampling decides at start (simple, may miss rare errors); tail‑based sampling buffers spans and decides after seeing the whole trace (more accurate but needs storage).  
- **Storage & querying**: backends like Jaeger (UI, storage via Cassandra/ES) or Tempo (object storage) store traces; querying by service, operation, tags, latency.  
- **Asynchronous messaging**: when a request puts a message on Kafka, the producer must record a span and inject trace context into the message headers (Kafka headers). The consumer extracts it and starts a child span. Continuity is maintained if the broker does not strip headers.  
- **Ensuring continuity**: use instrumentation libraries (OpenTelemetry SDKs) that automatically propagate context for popular frameworks and Kafka clients; verify that headers are preserved end‑to‑end; use consistent sampling configuration across services; store traces in a centralized backend for cross‑service correlation.

**OP1** – Type 1 hypervisor runs directly on hardware (bare‑metal). Examples: VMware ESXi, Microsoft Hyper‑V Server, KVM (when loaded as kernel module). Type 2 runs atop a host OS. Examples: Oracle VirtualBox, VMware Workstation, Parallels Desktop.

**OP2** – SAN (Storage Area Network) provides block‑level storage over a dedicated Fibre Channel or iSCSI network; appears as local disks to servers. NAS (Network‑Attached Storage) provides file‑level storage via protocols like NFS or SMB/CIFS; appears as network shares. Use SAN for high‑performance block workloads (databases, VMs); use NAS for file sharing, backups, media repositories.

**OP3** – 3‑tier network: core (high‑speed backbone), distribution (aggregation, policy), access (edge to endpoints). Leaf‑spine replaces this with a two‑layer fabric: leaf switches connect to servers; spine switches provide full‑mesh inter‑leaf connectivity. Leaf‑spine eliminates oversubscription, provides predictable latency, and scales horizontally; 3‑tier suffers from bottlenecks at distribution layer and complex spanning‑tree.

**OP4** – HA Proxmox cluster design:  
- **Node count**: minimum 3 for quorum (2 + 1).  
- **Quorum**: achieved via corosync; > ½ nodes must agree.  
- **Fencing**: STONITH (e.g., IPMI, iLO, or shared‑storage fencing) to isolate a faulty node.  
- **Shared storage**: Ceph RBD (block) or CephFS (file) for VM images; alternatively iSCSI target or NFS with locking.  
- **Node failure**: corosync detects loss, fences the node via STONITH, VMs are HA‑restarted on remaining nodes; Ceph re‑replicates placement groups from the failed node’s OSDs.

**OP5** – VLAN trunking carries multiple VLANs over a single link using 802.1Q tagging (adds 4‑byte VLAN ID). To put a Linux server on 3 VLANs with one NIC: create VLAN sub‑interfaces, e.g., `ip link add link eth0 name eth0.10 type vlan id 10` (repeat for IDs 20,30), then assign IPs or bridge them as needed.

**OP6** – RAID levels:  
- **RAID 1**: mirror (2 × capacity, 1‑disk fault tolerance, read performance ↑).  
- **RAID 5**: striped with distributed parity (capacity = (N‑1)·size, 1‑disk fault tolerance, write penalty).  
- **RAID 6**: double parity (2‑disk fault tolerance, higher write penalty).  
- **RAID 10**: mirrored pairs then striped (capacity = (N/2)·size, 1‑disk fault tolerance per pair, good read/write).  
- **RAID Z2** (ZFS): similar to RAID 6 but with variable stripe width and self‑healing.  
For 6 drives and a DB needing performance + fault tolerance, **RAID 10** gives 3 × drive capacity, can survive loss of one drive per mirror (up to 3 drives if not same mirror), and provides excellent random I/O. Choose RAID 10 unless capacity is paramount, then consider RAID 6.

**OP7** – DNS architecture for 500‑person enterprise:  
- **Internal AD‑integrated DNS** (AD‑DS) hosts internal zone, provides secure dynamic updates, forwards external queries to forwarders.  
- **DMZ**: place external‑facing authoritative DNS servers (split‑horizon) in DMZ, hardened, with DNSSEC signed zone.  
- **Split‑horizon**: internal resolvers query internal AD DNS for internal names; external resolvers (or clients on VPN) query DMZ authoritative servers for public names.  
- **Recursive resolvers**: internal AD DNS servers (or dedicated internal resolvers) perform recursion for internal clients; they forward unknown zones to ISP resolvers or root hints.  
- **Forwarders**: internal DNS forwards to ISP or corporate DNS forwarders for efficiency.  
- **Conditional forwarding**: for partner domains, forward directly to partner’s DNS servers.  
- **DNSSEC**: sign the external zone; enable validation on internal resolvers if desired.  
- **Laptop moving**: when on LAN, uses internal AD DNS; when on VPN, still uses internal DNS via VPN‑provided DNS suffix or split‑tunnel; when off‑VPN, uses public resolvers (or ISP) which query the DNSSEC‑validated external authoritative servers.

**OP8** – PKI chain: Root CA (offline, self‑signed) → Subordinate/Issuing CA (online) → End‑entity certificate.  
- Deploy **offline root** (air‑gapped) kept in a safe; generate a subordinate CA with a limited lifespan (e.g., 5 years).  
- Use **CRL** (periodically published) or **OCSP** (real‑time) for revocation checking; prefer OCSP stapling for web services.  
- Define **certificate templates** (key usage, EKU, validity, CSP) in AD CS or similar.  
- Enable **auto‑enrollment** via Group Policy so machines/users get certs automatically.  
- **Compromised subordinate CA**: can issue fraudulent certs for its domain; impact limited to what that CA was authorized to issue; you can revoke the subordinate and re‑issue from root.  
- **Compromised root CA**: catastrophic – any cert chaining to it is trusted; you must rebuild the entire PKI, distribute new root, and revoke all existing certs.

**OP9** – Hub‑and‑spoke WAN comparison (50 users/site, latency‑sensitive VoIP):  

| Option | Cost | Reliability | Latency | Mgmt Complexity | Security |
|--------|------|-------------|---------|-----------------|----------|
| **MPLS** | High (leased circuits) | Carrier‑grade SLAs | Low‑moderate (depends on provider) | Low (provider manages) | Good (private MPLS cloud) |
| **IPsec VPN over Internet** | Low (internet) | Variable (ISP dependent) | Higher (internet path, possible jitter) | Medium (manage tunnels, keys) | Good if strong IPsec + proper firewall |
| **SD‑WAN** | Moderate (appliance/subscription) | Can bond multiple links (MPLS+Internet) for redundancy | Can optimize path, lower latency for VoIP via QoS | Higher (controller, policies) | Good (encryption, segmentation) |
| **WireGuard mesh** | Low (open source) | Depends on underlying internet links | Low (lightweight, low overhead) | Low‑Medium (mesh config, key mgmt) | Strong (modern crypto) but needs full mesh management |

**Recommendation**: For VoIP, prioritize low jitter and guaranteed QoS. **SD‑WAN** with a primary MPLS link for voice and a secondary Internet backup gives carrier‑grade QoS, failover, and centralized policy control while keeping cost reasonable. If budget is strict and you can tolerate best‑effort Internet, a well‑tuned IPsec VPN with QoS on the edge routers can work, but SD‑WAN is generally superior.

**OP10** – iDRAC (Dell), iLO (HP), IPMI (generic) provide out‑of‑band management: remote power control, console redirection, hardware health monitoring, firmware updates independent of OS. Critical because you can recover a hung server, reinstall OS, or diagnose hardware without needing network or OS access. Exposing IPMI to the internet is dangerous: attackers can bypass OS protections, power cycle, install malicious firmware, or steal credentials; it should be restricted to a management VLAN with strong authentication and, ideally, VPN access only.

**OP11** – LVM: logical volume manager on top of block devices; supports resizing, snapshots (copy‑on‑write). LVM‑Thin: thin provisioning; snapshots are also thin and share space with origin. ZFS: combined filesystem & volume manager; built‑in snapshots (readonly, instantaneous), clones, checksums, self‑healing.  
- Use **LVM** when you need flexible partitioning on traditional Linux and want simple snapshots.  
- Use **LVM‑Thin** when you want many snapshots with minimal space overhead (e.g., VM images).  
- Use **ZFS** when you need end‑to‑end data integrity, compression, deduplication, and advanced snapshot/clone workflows (e.g., storage appliances).  
Snapshot semantics: LVM snapshots are mutable (can be written to) and can degrade performance if overused; LVM‑Thin snapshots share blocks and are efficient; ZFS snapshots are immutable, instantaneous, and cheap in space.

**OP12** – Stretch cluster / DR for 3‑node Proxmox + Ceph:  
- Deploy Ceph monitors across sites (e.g., 2 monitors in site A, 1 in site B) with an odd total to avoid split‑brain.  
- Use **CRUSH rules** to place primary OSDs in site A, replicas in site B; set `crush_tunable` for optimal network latency (< 5 ms RTT ideal).  
- Ensure **network latency** between sites < 10 ms for Ceph heartbeats; higher latency increases recovery time and risk of false failures.  
- **Split‑brain**: if the link between sites fails and each side thinks it has quorum, both may allow writes leading to divergence. Prevent with a **tiebreaker** (e.g., a third site witness or a quorum daemon) or by using **Ceph’s `mon_allow_pool_delete` false and requiring a majority of monitors**.  
- 2‑site Ceph without tiebreaker is risky because a network partition can leave each side with half the monitors, causing no quorum or split‑brain if you force quorum via `ceph mon set`. Adding a lightweight witness node or using a third site resolves this.

**OP13** – DHCP process: **D**iscover → **O**ffer → **R**equest → **A**cknowledge (DORA). Client broadcasts DHCPDISCOVER; server offers IP; client requests; server acknowledges. If DHCP server unavailable and lease expires, Windows client will attempt to renew; after several failed attempts it will fall back to **APIPA** (169.254.x.x/16) address, causing loss of network connectivity beyond local link.

**OP14** – Managed switch provides CLI/GUI for configuring VLANs, STP, port security, QoS, link aggregation, monitoring (SNMP, syslog), and ACLs. Unmanaged switch is plug‑and‑play with no configuration; lacks these enterprise features, making it unsuitable for segmented, secure, or performance‑critical networks.

**OP15** – NTP (Network Time Protocol) synchronizes clocks to UTC with sub‑millisecond accuracy. Critical for authentication (Kerberos tickets), logging correlation, distributed transactions, and certificate validation. Clock drift can cause authentication failures, inconsistent logs, incorrect ordering of events in databases, and issues with time‑based policies (e.g., lockout, TTL expiration).

**OP16** – Physical server: bare metal hardware. Virtual machine: emulated hardware running a guest OS via hypervisor. Container: isolated user‑space process sharing host kernel. Run workloads on bare metal when you need maximum performance, specialized hardware (GPUs, FPGAs, NICs with SR‑IOV), deterministic latency, or when licensing/ support requires direct hardware access (e.g., certain databases, real‑time systems).

**OP17** – UPS provides instantaneous battery power to bridge short outages and allow graceful shutdown or generator start‑up. Generator supplies longer‑term power after UPS depletes. ATS automatically transfers load from utility to generator when it detects loss and back when utility returns. You need both: UPS handles the gap (seconds to minutes) while generator spins up; without UPS, load would drop during generator start‑up; without generator, UPS would exhaust quickly.

**OP18** – Active‑passive: one node handles traffic, standby waits; failover promotes standby. Active‑active: both nodes serve traffic, load‑shared; failover redirects traffic from failed node to survivor.  
For PostgreSQL HA with Pacemaker/Corosync:  
- Install `pcs`, `pacemaker`, `corosync`, `fence-agents` (e.g., IPMI).  
- Configure a **fencing device** (STONITH) for each node.  
- Create a **cluster resource** for the VIP (e.g., `ocf:heartbeat:IPaddr2`).  
- Create a **postgresql** resource (using `ocf:heartbeat:pgsql` or a custom script) that promotes a standby to primary on failure.  
- Set **colocation** constraints so VIP runs on same node as PostgreSQL master.  
- On failure, Corosync detects node loss, Pacemaker triggers STONITH to fence the node, then promotes the standby, moves VIP, and clients reconnect.

**OP19** – Backup & recovery strategy for 50‑server on‑prem:  
- Follow **3‑2‑1 rule**: 3 copies of data, on 2 different media, 1 offsite.  
- Define **RPO** (max data loss) and **RTO** (max downtime) per service (e.g., DB RPO = 15 min, RTO = 30 min).  
- Backup types: weekly **full**, daily **incremental** (or synthetic full), optionally **differential** for quicker restores.  
- Use **deduplication** (source or target) to reduce storage.  
- Media: **disk** (NAS/VTL) for fast restore, **tape** for long‑term archival, **cloud** (e.g., AWS Glacier) for offsite immutable copy.  
- Implement **immutable backups** (WORM, object lock) to protect against ransomware.  
- Regularly **test restores** (fire‑drill) and verify backup integrity (checksums, trial recoveries).  
- **Backup** = copying data for recovery; **Disaster Recovery** = broader plan including failover site, network, and procedures to resume operations after a catastrophic event.

**OP20** – 802.1X workflow:  
1. **Supplicant** (client) initiates EAPOL‑Start.  
2. **Authenticator** (switch port) responds with EAP‑Request/Identity.  
3. Supplicant sends EAP‑Response/Identity (username).  
4. Authenticator forwards to **Authentication Server** (RADIUS).  
5. RADIUS validates credentials (e.g., EAP‑TLS mutual certs, or PEAP/MSCHAPv2) and sends Access‑Accept/Reject.  
6. On Accept, authenticator **opens the port** (assigns VLAN, applies QoS).  
- **EAP‑TLS**: certificate‑based mutual auth; strongest but requires PKI.  
- **PEAP**: tunnels EAP inside TLS; server authenticates with cert, client authenticates via password (MSCHAPv2).  
- **Dynamic VLAN assignment**: RADIUS returns `Tunnel‑Private‑Group-ID` to place client in appropriate VLAN.  
- **Failed auth**: port remains in unauthorized state; traffic blocked; can be placed in a remediation VLAN.  
- **MAB (MAC Authentication Bypass)**: for devices that can’t run 802.1X (printers, IP phones), the switch uses the MAC address as username/password sent to RADIUS; if MAC is allowed, port is authorized. MAB is less secure (MAC spoofing possible) and should be combined with port security or used only on trusted endpoints.
