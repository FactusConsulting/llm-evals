
**Kubernetes**

**K1** – A **Deployment** manages stateless replicas; it creates identical Pods, can scale up/down, and supports rolling updates. A **StatefulSet** manages stateful workloads: each Pod gets a stable, unique network identity (`<name>-<ordinal>`) and stable persistent storage (via volumeClaimTemplates). Pods are created, scaled, and deleted in ordinal order, and they retain their identity across rescheduling.

**K2** – A `ClusterIP` Service allocates a virtual IP (cluster‑internal). kube‑proxy (in iptables or IPVS mode) installs rules that DNAT traffic destined for that VIP to the set of Endpoint IPs (the Pods). The packet is then routed normally to the selected Pod; return traffic follows the reverse path.

**K3** –  
- **PersistentVolume (PV)**: cluster‑level storage resource (e.g., NFS disk) with capacity and access modes, provisioned statically or dynamically.  
- **PersistentVolumeClaim (PVC)**: a user’s request for storage; binds to a PV that satisfies size/access mode.  
- **StorageClass**: defines a *class* of storage (provisioner, parameters, reclaimPolicy). When a PVC specifies a `storageClassName`, the control plane dynamically provisions a PV using that class.  
Relation: PVC → binds to PV → PV may be dynamically created by StorageClass.

**K4** – Troubleshooting `CrashLoopBackOff` (≥4 checks):  
1. `kubectl logs <pod>` – see why the container exits.  
2. `kubectl describe pod <pod>` – check events, restarts, image pull errors, OOMKilled.  
3. Verify the container command/entrypoint and args (mis‑specified script).  
4. Check resource limits (OOM due to low memory limit).  
5. Look at ConfigMap/Secret mounts (missing keys cause app failure).  
6. Examine host‑node logs (kubelet, container runtime) if needed.

**K5** – CoreDNS provides cluster‑internal DNS service (A/AAAA/SRV records for Services, Pods, external names). If CoreDNS pods are down, internal name resolution fails; pods cannot resolve Service names or external domains (unless they use `hostNetwork` or custom DNS). External resolution may still work via `/etc/resolv.conf` fallback if `ndots` settings allow direct upstream queries, but internal service discovery breaks.

**K6** – Scheduler pipeline:  
1. **Filtering (Predicates)** – eliminate nodes that cannot satisfy hard requirements:  
   - Node affinity/taint‑tolerations.  
   - Resource requests (CPU, memory) vs. allocatable.  
   - Pod‑node selector, volume binding (if PV required).  
2. **Scoring (Priorities)** – rank remaining nodes:  
   - Resource utilization (prefer less‑used nodes).  
   - Affinity scores (preferred node affinity, inter‑pod affinity/anti‑affinity).  
   - Image locality (prefer nodes already having the container image).  
   - Taint tolerance (prefer untainted nodes).  
3. Select node with highest score (break ties randomly).  

**K7** – Node has 4 GB RAM, 3.5 GB already requested → 0.5 GB free.  
- Pod requests 256 Mi (< 0.5 GB) → **schedulable**.  
- Limits 512 Mi > request; if the pod tries to use 600 Mi, it exceeds its limit → the container is **OOMKilled** (kernel OOM or cgroup limit) and restarted, leading to CrashLoopBackOff if the app keeps exceeding the limit.

**K8** – Request flow (NGINX Ingress Controller):  
1. Client → external Load Balancer (cloud LB or bare‑metal) → forwards to NodePort/HostPort of the Ingress controller Service.  
2. Service (type LoadBalancer/NodePort) → kube‑proxy DNAT → Ingress controller Pods.  
3. Ingress controller (NGINX) receives HTTP request, matches host/path against Ingress rules, selects backend Service.  
4. Controller performs upstream load balancing (round‑robin/least‑conn) to the Service’s ClusterIP.  
5. Service’s ClusterIP → kube‑proxy (iptables/IPVS) → selects an Endpoint (Pod IP).  
6. Packet reaches Pod; NGINX (as proxy) forwards to the application container listening on its port.  
Response traverses the same path in reverse.

**K9** – A **NetworkPolicy** defines ingress/egress rules for Pods selected by `podSelector`.  
- If no NetworkPolicy exists in a namespace, **all traffic is allowed** (default allow).  
- Applying a policy that selects certain pods **isolates** those pods: only traffic matching the policy’s `ingress`/`egress` rules is allowed; all other traffic is dropped. Non‑selected pods remain unaffected (still default allow unless other policies select them).

**K10** –  
- **RollingUpdate**: creates new Pods gradually, terminating old ones, ensuring availability; maxSurge/maxUnavailable control pace.  
- **Recreate**: kills all existing Pods, then creates new ones → downtime.  
Choose **Recreate** when the application cannot tolerate multiple versions running simultaneously (e.g., schema migrations that are not backward‑compatible, or when using a shared volume that cannot be mounted by two versions).

**K11** – A **Namespace** is a logical cluster partition for naming, RBAC, and resource quotas. Default namespaces in a fresh cluster: `default`, `kube-system` (control‑plane components), `kube-public` (cluster‑wide info, readable by all), `kube-node-lease` (node heartbeats), and optionally `kube-node-lease` (in newer versions).

**K12** – `kubectl describe pod <name>` shows:  
1. Events (why it was scheduled, restarted, etc.).  
2. Containers’ state, ready/restart counts, and container IDs.  
3. Mounted volumes, ConfigMap/Secret references, and environment variables.  
4. Node name, IP, QoS class, and tolerations/affinities.  
These are not in the simple `kubectl get pod` output.

**K13** – A **ConfigMap** holds key‑value data. Pods can consume it:  
1. As **environment variables** (`envFrom` or `env.valueFrom.configMapKeyRef`).  
2. As **files** mounted into a volume (`volumes.configMap` → `volumeMounts`).  
(Also可用作命令行参数通过`$(VAR)` substitution.)

**K14** –  
- **ClusterIP**: internal virtual IP, only reachable inside the cluster.  
- **NodePort**: same as ClusterIP plus a static port on each Node’s IP (`<NodeIP>:<NodePort>`) that forwards to the Service.  
- **LoadBalancer**: provisions an external LB (cloud) that forwards to the NodePort/ClusterIP; provides a single external IP.

**K15** – A **DaemonSet** ensures a copy of a Pod runs on **every** (or selected) Node. Use when you need a node‑level agent: log collector (fluentd), node monitoring (Prometheus node‑exporter), CNI plugins, or kube‑proxy.

**K16** –  
- **Taints** are applied to Nodes; they repel Pods unless the Pod has a matching **toleration**.  
- **Tolerations** let a Pod schedule onto a tainted node.  
- **Node affinity** is a *soft* (preferred) or *hard* (required) attraction to nodes based on labels; it does not repel.  
Use case:  
  - *Taints/tolerations*: reserve a set of GPU nodes for ML workloads (`nvidia.com/gpu=present:NoSchedule`) and tolerate only those Pods needing GPUs.  
  - *Node affinity*: schedule a caching Pod onto nodes with SSD disks (`nodeSelector` or `affinity.nodeAffinity` preferring `disk-type=ssd`).

**K17** – A **Kubernetes Operator** is a domain‑specific controller that extends the API with Custom Resources (CRDs) and encapsulates operational knowledge (backup, upgrade, scaling) for a stateful application.  
- Differs from a standard controller (e.g., Deployment controller) because it manages *application‑specific* lifecycle beyond generic stateless scaling.  
- Solves problems: complex stateful apps (databases, caches), automated backups/failover, version upgrades, and providing a declarative, Kubernetes‑native way to operate them.

**K18** – etcd uses the **Raft consensus algorithm**: strong consistency, linearizable reads/writes; a quorum is `⌊N/2⌋+1` nodes.  
- If quorum is lost (e.g., 2/3 nodes down), the cluster cannot elect a leader → no writes, reads may stall; the API server loses access to stored state.  
- Recovery with 2/3 permanently lost:  
  1. Stop the remaining etcd member.  
  2. Restore from a recent etcd snapshot (etcdctl snapshot save/restore).  
  3. Initialize a new 3‑node cluster using the restored data (`--initial-cluster` and `--initial-cluster-state=new`).  
  4. Update API server endpoints to point to the new etcd cluster and restart control plane components.

**K19** – RBAC flow:  
- **Role** / **ClusterRole**: define a set of rules (apiGroups, resources, verbs).  
- **RoleBinding** / **ClusterRoleBinding**: bind a Role/ClusterRole to a Subject (user, group, serviceaccount) within a namespace (RoleBinding) or cluster‑wide (ClusterRoleBinding).  
For a developer needing **read‑only access to pods and logs** in namespace `dev`:  

```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list", "watch"]

# RoleBinding (bind to a user, e.g., alice)
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader-binding
  namespace: dev
subjects:
- kind: User
  name: alice   # replace with actual user or serviceaccount
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** – `/etc/resolv.conf` contains `ndots:<N>`; if a name has fewer than N dots, the resolver appends the search list domains before trying the name as‑is, causing extra DNS queries (and delays) for short names.  
Fix: set a lower `ndots` or provide a custom DNS config in the pod spec:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  dnsPolicy: None          # don't inherit cluster DNS
  dnsConfig:
    nameservers:
    - 10.96.0.10           # cluster DNS (CoreDNS) IP
    searches:
    - mynamespace.svc.cluster.local
    - svc.cluster.local
    - cluster.local
    options:
    - name: ndots
      value: "1"           # try name as-is after 1 dot
  containers:
  - name: app
    image: myapp
```

**Development**

**D1** – `git merge` creates a new merge commit that joins two histories, preserving the exact branch topology. `git rebase` rewrites the current branch’s commits onto the tip of another branch, producing a linear history.  
Avoid rebasing when:  
- The branch is public/shared (others have based work on it).  
- You need to preserve the original merge context or signed commits.  
- You rely on reflog history for audit.

**D2** – TCP: connection‑oriented, reliable, ordered, flow‑controlled (used by HTTP, SSH). UDP: connectionless, best‑effort, no ordering/retransmission (used by DNS queries, VoIP/RTP, DHCP).

**D3** – Race condition: outcome depends on the timing of uncontrollable events. Example (Go): two goroutines increment a shared integer without synchronization:

```go
var counter int
func inc() { counter++ }
go inc(); go inc(); // final value may be 1 instead of 2
```

**D4** – Symmetric encryption uses the same secret key for both encryption and decryption (fast; e.g., AES). Asymmetric encryption uses a key pair (public/private); data encrypted with public key can only be decrypted with private key (used for key exchange, signatures). In TLS: asymmetric handshake exchanges a premaster secret, then symmetric keys (AES‑GCM) encrypt the bulk traffic.

**D5** – A Docker image layer is a read‑only filesystem snapshot resulting from a Dockerfile instruction. Layer caching lets Docker reuse unchanged layers when rebuilding, speeding up builds. Best practices: put infrequently changing steps (e.g., `FROM`, package installs) early; copy application code last; combine related `RUN` commands to reduce layers.

**D6** – Intermittent 503 (Service Unavailable) checklist (ordered by likelihood):  
1. **Backend health** – are application instances crashing or overloaded? Check logs, metrics, restart loops.  
2. **Load balancer / ingress** – is it marking backends unhealthy? Verify health‑check paths and thresholds.  
3. **Resource exhaustion** – CPU, memory, file descriptors, or connection limits on the app or OS.  
4. **Dependency timeouts** – downstream DB, cache, or external API slowing down or returning errors, causing the app to fail to respond within its timeout.  
5. **Network issues** – packet loss, high latency between LB and pods.  
6. **Configuration drift** – mis‑configured thread pools, queue sizes, or circuit‑breaker thresholds.

**D7** – CAP theorem: a distributed data store can guarantee at most two of Consistency, Availability, Partition tolerance.  
- **CP** (Consistent + Partition‑tolerant): e.g., **etcd** or **ZooKeeper** – they sacrifice availability during a partition to keep data consistent.  
- **AP** (Available + Partition‑tolerant): e.g., **Cassandra** or **DynamoDB** (with eventual consistency) – they remain writable/readable during partitions, accepting temporary inconsistency.

**D8** – Horizontal scaling: add more nodes/instances; vertical scaling: increase resources (CPU/RAM) of an existing node. Patterns enabling horizontal scaling: stateless services, sharding/partitioning, consistent hashing, stateless front‑ends with shared-nothing architecture, and using load balancers or service meshes.

**D9** – An environment variable is a key‑value pair inherited by processes. To persist across sessions on Linux, add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `/etc/environment` (for system‑wide), then `source` the file or restart the shell.

**D10** – JSON: lightweight, widely supported, maps directly to objects in many languages; advantage: universal parsing libraries, native in browsers. YAML: human‑friendly syntax, supports comments, complex data structures (anchors, aliases); advantage: easier to read/write configuration files.

**D11** – REST API: architectural style using HTTP verbs to manipulate resources.  
- **GET**: retrieve a representation (safe, idempotent).  
- **POST**: create a subordinate resource or trigger an action (not idempotent).  
- **PUT**: replace an existing resource with the provided representation (idempotent).  
- **DELETE**: remove a resource (idempotent).

**D12** – Version pinning: locking dependencies to exact versions (e.g., `package==1.2.3` in `requirements.txt` or `package.json` `"package": "1.2.3"`). Important for reproducible builds because it prevents unexpected upgrades that could introduce breaking changes or bugs.

**D13** – Compiled language: source code translated to machine code before execution (e.g., C, Go). Interpreted language: executed line‑by‑line by an interpreter at runtime (e.g., Python, JavaScript). Some languages use both (Java compiled to bytecode then interpreted/JIT).

**D14** – Reverse proxy: sits in front of servers, receives client requests, forwards to backend, returns response (hides backend topology). Forward proxy: sits between client and internet, forwards client requests outward (used for filtering, caching). Examples:  
- **NGINX** (reverse) – load balancing, TLS termination for web apps.  
- **HAProxy** (reverse) – high‑performance TCP/HTTP load balancing.  
Forward proxy examples: **Squid** (caching web proxy), **tinyproxy**.

**D15** – Deadlock: two or more processes each hold a resource and wait for another held by another, forming a circular wait. Coffman conditions:  
1. Mutual exclusion (resources non‑shareable).  
2. Hold and wait (process holds ≥1 resource and waits for another).  
3. No preemption (resources cannot be forcibly taken).  
4. Circular wait (closed chain of processes each waiting for the next’s resource).  
All four must hold simultaneously.

**D16** – Eventual consistency: after updates stop, all replicas converge to the same state. Cassandra achieves read‑after‑write consistency via tunable levels:  
- **CL=ONE** (write to one replica, read from one) – low latency, possible stale read.  
- **CL=QUORUM** (write/read to majority) – strong consistency if `R + W > N`.  
- **CL=ALL** – all replicas must acknowledge.  
To get read‑after‑write, use `QUORUM` for both write and read, or `WRITE=QUORUM, READ=ONE` with `read_repair_chance` high.

**D17** – mTLS (mutual TLS): both parties present certificates verified against trusted CAs. Handshake:  
1. ClientHello → ServerHello (certificate, cipher).  
2. Server sends its certificate; client validates it.  
3. Server requests client certificate (`CertificateRequest`).  
4. Client sends its certificate; server validates it.  
5. Exchange of key material (premaster secret) → symmetric keys.  
6. Finished messages encrypted with symmetric keys.  
Used for service‑to‑service authentication (Istio, Zero Trust), API gateways, etcd peer communication, and SSH‑like bastion hosts.

**D18** – Hash table: array of buckets; hash function maps key to index. Collision resolution:  
- **Chaining**: each bucket holds a linked list (or dynamic array) of entries sharing the hash.  
- **Open addressing**: on collision, probe next slot (linear, quadratic, double hashing) until empty.  
Average‑case time: **O(1)** for insert/lookup/delete. Worst‑case (all keys hash to same bucket): **O(n)** for chaining; **O(n)** for open addressing if table becomes full and probing scans many slots.

**D19** – Circuit breaker pattern: monitors calls to a remote service.  
- **Closed**: calls pass through; failure count tracked; if exceeds threshold, trips to **Open**.  
- **Open**: calls fail fast (no network call); after timeout, moves to **Half‑Open**.  
- **Half‑Open**: allows a trial request; if success, reset to **Closed**; if failure, return to **Open**.  
Prevents cascading failures by stopping traffic to a failing service, giving it time to recover. Works with retry policies: retries are attempted only when breaker is Closed; exponential backoff spaces retries to avoid overwhelming the service.

**D20** – Optimistic concurrency: assumes conflicts rare; transaction proceeds, then at commit checks if data changed (e.g., via row version/timestamp). If changed, abort and retry. Good for high‑read, low‑write workloads.  
Pessimistic concurrency: locks data upfront (e.g., `SELECT FOR UPDATE`) to prevent others from modifying it during the transaction. Suitable when conflicts are likely.  
Example (PostgreSQL):  
- Optimistic: table has `version int`; UPDATE … SET version = version+1 WHERE id = $1 AND version = $2; if affected rows = 0 → retry.  
- Pessimistic: `BEGIN; SELECT * FROM accounts WHERE id = $1 FOR UPDATE; … UPDATE …; COMMIT;` holds lock until transaction ends.
