
**G1** – A Go array has a fixed size that is part of its type (`[N]T`). A slice is a descriptor (`ptr`, `len`, `cap`) that references an underlying array and can grow/shrink. When `append` exceeds the slice’s capacity, Go allocates a new, larger backing array (typically doubling), copies the old elements, and returns a slice pointing to the new array.

**G2** – `var x int` declares a variable with explicit type and zero‑initializes it; `x := 0` is a short variable declaration that infers the type from the initializer and can only be used inside a function. `:=` cannot be used at package level or to redeclare a variable in the same block without at least one new variable.

**G3** – A goroutine is a lightweight user‑space thread managed by the Go runtime. It starts with a small stack (~2 KB) that grows/shrinks as needed. The Go scheduler (GMP model) maps many goroutines (G) onto a smaller number of OS threads (M) via a pool of logical processors (P). The scheduler preemptively runs goroutines, handles syscalls, and balances work across Ps.

**G4** – A channel is a typed conduit for communication; sends and receives block until the other side is ready. An unbuffered channel (`make(chan T)`) has capacity 0 and synchronizes sender/receiver. A buffered channel (`make(chan T, n)`) holds up to `n` values without blocking. Sending to a full buffered channel blocks until space is freed (or the send is cancelled via select/context).

**G5** – `context` carries cancellation signals, deadlines, and request‑scoped values across API boundaries. Minimal timeout example:

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "https://example.com", nil)
resp, err := http.DefaultClient.Do(req)
// ctx.Done() will be closed after 2 s, cancelling the request
```

**G6** – Go interfaces are satisfied implicitly: any type that implements all methods of the interface satisfies it, no explicit `implements` keyword. Unlike Java/C#, there is no inheritance hierarchy; you can satisfy multiple interfaces independently. `interface{}` (or `any` in Go 1.18) is the empty interface that matches any type; it’s powerful for generic containers but loses compile‑time type safety, requiring type assertions or reflection to use the value.

**G7** – The code has a data race: writes to `data` and `ready` in the goroutine may not be visible to the main goroutine due to lack of synchronization; the compiler/CPU may reorder stores. Safe alternatives: use a channel to signal completion, or protect the variables with `sync.Mutex`/`sync.RWMutex`, or use `sync/atomic` for the flag.

```go
var ready chan struct{}
go func() {
    data = "hello"
    close(ready) // signals completion
}()
<-ready
fmt.Println(data)
```

**G8** – `sync.Mutex` provides exclusive lock; `sync.RWMutex` allows many concurrent readers or a single writer. Use RWMutex when reads vastly outnumber writes. `sync.Map` is a concurrent map optimized for many reads and occasional writes (e.g., caches); it avoids lock contention but has higher overhead for write‑heavy workloads and lacks range‑delete semantics of a regular map.

**G9** – Go modules are versioned dependency collections defined by `go.mod` (module path, Go version, require/replace directives). `go.sum` contains cryptographic checksums of specific module versions to guarantee integrity. `go mod tidy` adds missing dependencies, removes unused ones, and ensures `go.mod`/`go.sum` match the actual build list. MVS selects, for each module, the highest version that satisfies all version constraints (minimum sufficient version) to avoid diamond‑dependency upgrades.

**G10** – `defer` schedules a function call to run after the surrounding function returns, in LIFO order. Multiple defers execute in reverse order of their appearance. A common gotcha: defer inside a loop captures loop variables by reference; if the variable changes each iteration, all defers may see the final value. Solution: create a new variable or use a lambda with parameters.

```go
for i := 0; i < 3; i++ {
    defer func(i int) { fmt.Println(i) }(i) // capture by value
}
```

**G11** – A pointer holds the memory address of a variable. Its zero value is `nil`. To point to a struct literal: `p := &MyStruct{Field: value}` or `var p *MyStruct = &MyStruct{}`.

**G12** – `init()` runs automatically after package imports are resolved and before `main.main` (or test main). A package may have many `init` functions; they execute in the order they appear in the source files, with file order determined by lexical order of file names within the package.

**G13** – `new(T)` allocates zeroed storage for type `T` and returns `*T`. It works for any type. `make(T, args)` creates initialized slices, maps, or channels (and returns the type itself, not a pointer) because these types require runtime data structures beyond raw memory.

**G14** – The `error` interface is `type error interface { Error() string }`. Idiomatically: `if err != nil { … }`. `errors.Is(err, target)` checks if `err` or any wrapped error equals `target`. `errors.As(err, &target)` finds the first error matching `target` type and assigns it; both work with wrapped errors (`%w`) whereas `==` only matches the exact error value.

**G15** – Built‑in composite types: array, slice, map, channel, struct, function, interface. Zero values: array → each element zeroed; slice → `nil`; map → `nil`; channel → `nil`; struct → each field zeroed; function → `nil`; interface → `nil`.

**G16** – A race condition occurs when two goroutines access shared memory concurrently, at least one access is a write, and no synchronization orders them. The `-race` flag instruments the code to detect such accesses. Example:

```go
var counter int
go func() { counter++ }()
go func() { counter++ }()
time.Sleep(time.Second)
fmt.Println(counter) // may be 1
```

Fix with mutex:

```go
var mu sync.Mutex
go func() { mu.Lock(); counter++; mu.Unlock() }()
go func() { mu.Lock(); counter++; mu.Unlock() }()
```

Or use a channel to serialize increments.

**G17** – `select` waits on multiple channel operations; it picks one ready case pseudo‑randomly. Unlike `switch`, which evaluates expressions, `select` only works on channel sends/receives (and a default). If multiple cases are ready, one is chosen at random. Timeout example:

```go
select {
case msg := <-ch:
    fmt.Println(msg)
case <-time.After(500 * time.Millisecond):
    fmt.Println("timeout")
}
```

**G18** – Escape analysis determines whether a variable’s lifetime exceeds the function scope; if it does, the variable is allocated on the heap, otherwise on the stack. The compiler examines assignments, returns, and storage in globals or heap‑reachable data. Use `go build -gcflags="-m -m"` to see escape decisions. Stack allocation is cheaper (no GC pressure) and improves locality.

**G19** – `reflect.Type` describes the static type; `reflect.Value` holds a concrete value and lets you read/write fields, call methods, etc. Reflection is slow (type lookups, indirect calls) and inhibits optimizations; use it only when static typing cannot express the need (e.g., generic serialization, ORM). Code generation (e.g., `go generate`) often provides zero‑overhead alternatives.

**G20** – `go:embed` tells the Go toolchain to embed files or directories into the binary at compile time. Usage:

```go
//go:embed logo.png
var logo []byte

//go:embed templates/*
var tmpl embed.FS
```

For a single file you get a `[]byte` or `string`; for a directory you get an `embed.FS` implementing `io/fs.FS`. Limitations: only works with files present at build time, cannot embed symlinks or files excluded by `.goignore`, and the embedded data increases binary size. The resulting `embed.FS` can be used with `io/fs` APIs like `fs.Sub`, `http.FS`, etc.

---

**R1** – Ownership means each value has a single owner responsible for freeing it when the owner goes out of scope. Rules: 1) Each value has exactly one owner. 2) When the owner goes out of scope, the value is dropped. 3) Ownership can be moved (or copied for `Copy` types) but not duplicated; after a move the source is invalidated.

**R2** – `String` is an owned, heap‑allocated UTF‑8 buffer (`Vec<u8>`) with capacity and length. `&str` is an immutable borrowed view (pointer+length) into UTF‑8 data, often a string literal or slice of a `String`. Use `String` when you need to own/modify the text; use `&str` in function signatures to accept both owned and borrowed strings without allocation.

**R3** – Borrowing lets you create references (`&T` shared, `&mut T` mutable) to data without taking ownership. Rules: at any time you may have either any number of shared references **or** exactly one mutable reference, but not both. References must not outlive the data they refer to (enforced by lifetimes).

**R4** – `Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`). `Option<T>` represents presence (`Some(T)`) or absence (`None`). The `?` operator propagates errors: if the operand is `Err(e)`, return `Err(e)` from the enclosing function; otherwise unwrap the `Ok` value. Example file reader:

```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    let mut f = std::fs::File::open(path)?;
    let mut s = String::new();
    f.read_to_string(&mut s)?;
    Ok(s)
}
```

**R5** – `Box<T>` owns a heap allocation with a single owner (unique pointer). `Rc<T>` is a reference‑counted pointer for single‑threaded shared ownership. `Arc<T>` is an atomically reference‑counted pointer for thread‑shared ownership. Use `Box` when you need exclusive ownership; `Rc` for shared read‑only data in one thread; `Arc` when data may be accessed from multiple threads.

**R6** – Traits define shared behavior (like interfaces). A generic `T: Trait` is monomorphized per concrete type, giving static dispatch and zero overhead. A trait object `dyn Trait` erases the concrete type, storing a pointer to a vtable; calls are dispatched dynamically (indirect). Use generics for performance; use trait objects when you need heterogeneous collections.

**R7** – The function lacks a lifetime parameter, so the compiler cannot guarantee the returned reference lives long enough. Fix by adding an explicit lifetime:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Now the returned reference is tied to the lifetime of both inputs.

**R8** – `Send` means the type can be transferred to another thread; `Sync` means it is safe for multiple threads to hold `&T` simultaneously. `Rc<T>` uses non‑atomic reference counts, so moving it between threads could cause data races → not `Send`/`Sync`. `Arc<T>` uses atomic increments/decrements, making it both `Send` and `Sync`.

**R9** – `async fn` returns a type that implements `Future`. A `Future` is a state machine that yields control when awaiting another future; it does not run until polled by an executor. Executors (e.g., Tokio’s thread‑pool or current‑thread scheduler) drive futures to completion. Unlike Go’s goroutines (which are multiplexed onto OS threads by the runtime and can be preempted at any point), Rust’s async tasks are cooperative: they only yield at `.await` points, giving fine‑grained control but requiring an executor.

**R10** – `unsafe` lets you: 1) dereference raw pointers (`*const T`, `*mut T`); 2) call functions or methods marked `unsafe`; 3) implement or access `unsafe` traits; 4) mutate static variables; 5) access fields of unions. It’s justified when you have proven safety invariants that the compiler cannot check (e.g., FFI, data structures needing raw pointers, performance‑critical low‑level code).

**R11** – Pattern matching deconstructs values to bind variables. `match` is exhaustive and can have many arms; `if let` matches a single pattern and lets you omit handling other cases. The compiler enforces that all possible values of the type are covered in a `match` (unless `_` wildcard is used).

**R12** – `Vec<T>` is a growable, heap‑allocated buffer; `[T; N]` is a fixed‑size array stored inline. When `Vec` exceeds its capacity, it allocates a new buffer (typically 2×), copies/moves existing elements, and frees the old buffer.

**R13** – Enums are algebraic data types that can hold data in each variant, unlike C/Java enums which are just integer constants. `Option<T>` is defined as `enum Option<T> { Some(T), None }`, providing a safe way to express absence without null pointers.

**R14** – An `impl block` defines methods and associated functions for a type. `&self` → read‑only borrow; `&mut self` → mutable borrow; `self` → takes ownership (move). Associated functions have no `self` parameter (e.g., `String::new()`) and act like constructors or namespaced functions.

**R15** – `derive` macro automatically generates trait implementations based on the struct/enum definition. Commonly derived: `Debug`, `Clone`, `PartialEq`, `Eq`, `Hash`, `Default`, `Serialize`/`Deserialize` (via serde). You cannot derive traits that require custom logic (e.g., `Display`, `From`, or traits with generic associated types) unless you provide a custom macro or implement manually.

**R16** – `Cow<'a, T>` (clone‑on‑write) holds either borrowed data (`&'a T`) or owned data (`T`). It avoids cloning when you only need to read; if you must mutate, it clones on demand. Example: processing input that may be a string literal or a `String`; you can work with `Cow<str>` and only allocate when you need to change the content.

**R17** – Modules form a hierarchy; `mod foo;` declares a submodule, `use` brings names into scope, `pub` controls visibility. The file system mirrors the module tree: `src/foo.rs` or `src/foo/mod.rs`. Rust 2018 simplified paths: you can use `crate::`, `super::`, or external crate names directly without needing `extern crate`; `use` can now import from the root with `use crate::foo;`.

**R18** – `Pin<T>` guarantees that the value it points to will not be moved in memory, which is required for self‑referential structs (e.g., async futures that store pointers to their own fields). `Unpin` is an auto‑trait indicating a type does not rely on being pinned; most types are `Unpin`. Pinning is used by the async machinery to safely poll futures that may contain self‑references.

**R19** – Declarative macros (`macro_rules!`) match token trees and generate code; they are hygienic (identifiers are scoped to the macro definition unless explicitly exported). Procedural macros come in three flavors: `#[derive]` (attribute-like), attribute macros (`#[attr]`), and function‑like macros (`macro!()`). They operate on the token stream after parsing and can inspect and transform AST nodes; they also follow hygiene rules but can break them with explicit `#[proc_macro]` escapes.

**R20** – Zero‑cost abstractions mean that using high‑level constructs incurs no runtime overhead compared to hand‑written low‑level code. Iterators are lazy and compile down to tight loops via inlining; generics are monomorphized, producing a copy of the function per concrete type (no vtable); trait static dispatch uses direct calls (monomorphized) when the concrete type is known, achieving C‑like performance while providing safety and ergonomics.
