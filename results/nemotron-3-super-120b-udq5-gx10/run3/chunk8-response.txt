
**CL1** – IaaS provides raw compute, storage, and networking (you manage OS, middleware, apps). Example: AWS EC2.  
PaaS supplies a managed platform for developing/run‑time (you manage code & data). Example: Azure App Service.  
SaaS delivers a complete application accessed over the network (provider manages everything). Example: Microsoft 365.

**CL2** – Shared Responsibility Model splits security duties:  
- **IaaS VMs** – Provider secures hypervisor, physical host, network; you secure OS, patches, apps, data, IAM.  
- **Managed Kubernetes (EKS/AKS/GKE)** – Provider secures control plane, underlying nodes’ OS patches, node‑level networking; you secure cluster configuration, workloads, RBAC, container images, secrets.  
- **SaaS (M365)** – Provider secures infrastructure, platform, application; you secure your data, user access, device compliance, configuration of tenant‑level settings.

**CL3** –  
- **VPC** – Isolated virtual network (CIDR) that spans an entire region.  
- **Subnet** – Sub‑range of a VPC CIDR confined to a single Availability Zone; hosts resources.  
- **Security Group (SG)** – Stateful firewall attached to ENI/instance; allows/denies traffic based on rules; return traffic automatically allowed.  
- **Network ACL (NACL)** – Stateless subnet‑level firewall; evaluates inbound/outbound rules separately; needs explicit rules for both directions.  
Layering: Traffic first hits VPC routing → NACL (stateless) → SG (stateful) → instance. Stateful filtering (SG) tracks connection state; stateless (NACL) treats each packet independently.

**CL4** – Multi‑account strategy:  
- **Landing zone** – Pre‑built, secure baseline (OU structure, SCPs, IAM baseline, logging, networking) for new accounts.  
- **Organizational Units (OUs)** – Group accounts by function (e.g., prod, dev, security) to apply SCPs uniformly.  
- **Guardrails** – SCPs, IAM policies, Config rules, Service Catalog that enforce compliance (e.g., no public S3, mandatory encryption).  
- **Shared networking** – Transit Gateway (AWS) or Azure Hub‑and‑Spoke VNet peering with a central hub for inter‑account/VNet traffic, DNS, and inspection.  
- **Centralized logging** – Aggregate CloudTrail/Activity Log, VPC Flow Logs, and Azure Monitor logs into a security‑account S3/Log Analytics workspace with immutable retention.  
Single‑account problems: blast‑radius of misconfigurations, difficulty applying least‑privilege at scale, limited ability to isolate workloads, complex billing/showback, and harder to enforce distinct security baselines.

**CL5** – IaC tools:  
- **Terraform/OpenTofu** – Cloud‑agnostic, declarative HCL, large provider ecosystem; choose when you need multi‑cloud or want a mature community.  
- **Pulumi** – Same declarative/imperative approach but using general‑purpose languages (TS, Python, Go); choose when developers prefer code‑first and want tight integration with app code.  
- **CloudFormation (AWS) / Bicep (Azure)** – Native, tightly integrated, supports drift detection; choose for single‑cloud, deep service support, and when you want no extra CLI.  
- **Crossplane** – Kubernetes‑native control plane that provisions cloud resources via CRDs; choose when you already run workloads on K8s and want to manage infra via the same API (GitOps‑friendly).  

**CL6** – Autoscaling patterns:  
- **HPA** – Scales pod replicas based on CPU/memory or custom metrics; good for stateless workloads.  
- **VPA** – Adjusts pod resource requests/limits (vertical) based on usage; useful for workloads with unpredictable resource needs but cannot change replica count.  
- **Cluster Autoscaler** – Adds/removes worker nodes when pods cannot be scheduled or nodes are underutilized; works with HPA/VPA.  
- **KEDA** – Event‑driven scaling (e.g., queue length, HTTP requests, Prometheus); scales to zero and works alongside HPA.  
Use KEDA over HPA when scaling is triggered by external events (queues, streams, custom metrics) rather than pod‑level resource utilization, or when you need to scale to zero for sporadic workloads.

**CL7** – DR design (two regions):  
- Define **RPO** (max data loss) and **RTO** (max downtime).  
- **Active‑Active** – Both regions serve traffic; data replicated synchronously (or near‑sync) → lowest RPO/RTO but higher cost.  
- **Active‑Passive** – Primary region serves; standby region warmed up (pilot light/warm standby) → lower cost, higher RTO.  
- **Database replication** – Sync (e.g., Aurora Global DB, SQL Always On) for zero‑loss RPO; Async (e.g., read replica, log shipping) for higher RPO but lower latency/cost.  
- **DNS failover** – Route 53 health checks + latency‑based routing or Azure Traffic Manager with endpoint monitoring; TTL low enough for fast cut‑over.  
- **State management** – Use shared object storage (S3/Blob) for static assets; replicate stateful services (e.g., DynamoDB Global Tables, Cosmos DB) or use backup/restore pipelines.  
- **Cost** – Active‑active ≈ 2× runtime; pilot light ≈ 1.2× (only essential services running); warm standby ≈ 1.5×.  
- **Pilot light** – Core services (DB, DNS) running minimally; can scale up quickly.  
- **Warm standby** – Full stack running but at reduced capacity (e.g., smaller instances).  
- **Multi‑site active‑active** – Full capacity in both regions, traffic split; highest cost, lowest RPO/RTO.

**CL8** – GitOps: Git repo is the single source of truth; operators continuously reconcile cluster state to match Git.  
- **ArgoCD** – UI‑rich, supports multiple clusters, progressive rollout, health assessments, hook‑based sync.  
- **FluxCD** – Lightweight, CNCF‑graduated, uses Kustomize/Helm controllers, integrates with Flux v2 source controller.  
- **Secrets** – Store encrypted (Sealed Secrets, SOPS) or use External Secrets Operator/Vault to fetch secrets at runtime; never commit plaintext.  
- **Drift** – If someone makes a manual change, the operator detects mismatch and either re‑applies Git state (auto‑sync) or alerts; policy can be set to “auto‑prune” or “manual approve”.

**CL9** – Migrating stateful legacy app to K8s:  
- **StatefulSet** – Guarantees ordered, unique pod identity (ordinal) and stable network IDs.  
- **PV/PVC with local storage class** – Use CSI local‑volume provisioner (e.g., Local Path Provider) to bind pods to specific node disks for low latency; set `volumeBindingMode: WaitForFirstConsumer`.  
- **Headless Service** – `clusterIP: None` gives each pod a DNS `<pod-name>.<service>.<namespace>.svc.cluster.local` for direct pod‑to‑pod communication.  
- **Init Containers** – Run before app container to copy config files, perform schema migrations, or wait for dependencies.  
- **ConfigMaps as volume mounts** – Externalize config files; mount at required paths (`/etc/app/config.yaml`).  
- **Pod Disruption Budgets (PDB)** – Ensure minimum available pods during voluntary disruptions (e.g., `minAvailable: 2` for a 3‑replica set).  
- Additionally, consider `terminationGracePeriodSeconds` for graceful shutdown and `preStop` hook to flush data.

**CL10** –  
- **Service Account** – K8s identity for pods; tokens projected automatically; limited to cluster RBAC.  
- **Workload Identity** – Cloud‑provider mechanism that lets a K8s service account assume an IAM role/managed identity without storing credentials (e.g., AWS IAM Roles for Service Accounts, Azure Workload Identity).  
- **IRSA (IAM Roles for Service Accounts)** – AWS‑specific implementation of workload identity using OIDC federation between EKS and IAM.  
Mounting cloud credentials in a pod is bad because they become exposed to any process in the container, can be leaked via logs or images, and violate least‑privilege and secret‑management best practices.  
Workload identity federation solves this by using short‑lived tokens issued via OIDC/JWT exchange; the pod never sees long‑lived secret keys.

**CL11** –  
- **Object Storage (S3/Blob)** – Stores unstructured data as objects via HTTP API; ideal for backups, media, static web, data lakes; durability 11‑9’s (99.999999999%), availability typically 99.9‑99.99% (depending on class).  
- **Block Storage (EBS/Managed Disk)** – Raw block volumes attached to VMs; low‑latency random I/O for databases, boot disks; durability via replication within AZ; availability tied to underlying infrastructure (usually 99.9‑99.95%).  
- **File Storage (EFS/Azure Files)** – Network file system (NFS/SMB) shared across many instances; suitable for lift‑and‑shift apps, home directories, container volumes; durability similar to object storage; availability 99.9% (regional) or higher with zone‑redundant options.  

**CL12** – Zero‑trust K8s network:  
- **Network Policies** – Whitelist ingress/egress at pod namespace level (default deny).  
- **Service Mesh (Istio/Linkerd)** – Enforce mTLS between services, fine‑grained authorization policies, telemetry.  
- **Pod Identity** – Workload identity/IAM roles for service accounts to grant least‑privilege cloud access.  
- **Admission Controllers** – OPA/Gatekeeper or Kyverno to enforce policies (e.g., disallow privileged containers, require image signatures).  
- **Image Signing & Verification** – Cosign or Notary; admission controller blocks unsigned images.  
- **Runtime Security** – Falco or Tetragon to detect anomalous syscalls, file writes, privilege escalation.  
- **Secrets Management** – External Secrets Operator/Vault CSI driver; secrets injected as ephemeral volumes, never in etcd plaintext.  
Differs from perimeter model: trust is never assumed based on network location; every communication is authenticated, authorized, and encrypted; security follows the workload wherever it runs.

**CL13** – CDN caches static/content at edge POPs; requests routed to nearest edge; origin fetches on miss. Cloud‑native examples: Amazon CloudFront, Azure Front Door (or Azure CDN). Use CDN for globally distributed static assets, video streaming, API acceleration; serve directly from origin when latency is low (same region) or when you need full control over caching/compression logic.

**CL14** – **Region** – Geographically isolated area with multiple AZs; **Availability Zone** – One or more discrete data centers with independent power, cooling, networking. Deploy across AZs to survive AZ‑level failures (power, network). **Zonal resources** (e.g., EC2 instance, managed disk) are tied to a specific AZ; **regional resources** (e.g., S3, VPC, RDS multi‑AZ) span AZs and provide higher availability.

**CL15** – Managed DB service (RDS, Cloud SQL, Azure SQL) handles provisioning, patching, backups, HA, monitoring, scaling, and security baseline. You manage schema, query tuning, application‑level access, and data modeling; you still design indexes, write queries, and manage performance tuning.

**CL16** – IAM **Users** (long‑term credentials), **Groups** (collection of users for policy attachment), **Roles** (temporary permissions assumed by entities), **Policies** (JSON documents defining allow/deny actions). Principle of Least Privilege: grant only the permissions needed to perform a task. Apply by: start with no permissions, add granular policies per job function, use policy conditions (e.g., source IP, MFA), regularly review unused permissions via IAM Access Analyzer, and enforce via SCPs or Azure Policy.

**CL17** – Serverless: run code in response to events without managing servers.  
- **AWS Lambda** – Supports many languages, 15‑min max execution, integrates with API Gateway, SQS, etc.  
- **Azure Functions** – Similar, with consumption & premium plans, Durable Functions for orchestration.  
- **Google Cloud Functions** – Event‑driven, supports HTTP, Cloud Pub/Sub, Cloud Storage triggers.  
**Cold starts** – Latency incurred when a new execution environment is spun up (container image download, runtime init). Matter for latency‑sensitive APIs; mitigated by provisioned concurrency (Lambda), premium plan (Functions), or keeping functions warm. Serverless is a poor fit for long‑running, high‑CPU workloads, applications needing persistent in‑process state, or when you need fine‑grained control over the OS/runtime.

**CL18** – Ingress options:  
- **Ingress Resource** – Simple HTTP(S) routing via Ingress controller (NGINX, Traefik); TLS termination at controller.  
- **Gateway API** – More expressive, role‑based (Gateway, HTTPRoute, TLSRoute); supports multi‑protocol, better extensibility; TLS termination at Gateway or attached HTTPRoute.  
- **Cloud Load Balancer Annotations** – Provider‑specific (e.g., `service.beta.kubernetes.io/aws-load-balancer-ssl-cert`) – TLS terminated at the LB before reaching pods.  
- **Service Mesh Ingress Gateways** – Envoy‑based gateway (Istio IngressGateway) – TLS terminated at mesh, then mTLS to services.  
Use Gateway API when you need advanced traffic splitting, multi‑protocol support, or want a standardized, extensible API that works across controllers; otherwise classic Ingress suffices for simple HTTP(S).

**CL19** – Cost‑optimization for $80k/mo:  
1. **Reserved Instances / Savings Plans** – Commit to 1‑3 yr usage for steady‑state workloads (e.g., baseline EC2, RDS).  
2. **Spot/Preemptible** – Use for fault‑tolerant batch, CI/CD, stateless workers; combine with capacity‑rebalancing.  
3. **Right‑sizing** – Use Compute Optimizer, Trusted Advisor, or Azure Advisor to downsize over‑provisioned instances; leverage autoscaling policies.  
4. **Storage Tiering** – Move infrequent data to S3 Intelligent‑Tiering → Glacier Deep Archive; Azure Cool/Archive tiers.  
5. **Idle Detection** – Tag resources, use AWS Lambda/Functions to stop dev environments after hours; Azure Automation to deallocate VMs.  
6. **FinOps Practices** – Establish cost‑allocation tags, monthly budget alerts, chargeback/showback reports; hold regular cost‑review meetings.  
7. **Tools** – AWS Cost Explorer + Budgets, Azure Cost Management + Advisor, Terraform Cloud/Enterprise for drift‑cost checks, Kubecost for K8s, Cloudability or Spot.io for recommendation engine.  
Process: tag everything → ingest into central dashboard → set budgets → automate rightsizing → review savings → iterate.

**CL20** – Multi‑cloud design to avoid lock‑in:  
- **Abstraction Layer** – Use Kubernetes as the common runtime; package apps via Helm charts or Operators that are cloud‑agnostic.  
- **IaC Portability** – Terraform (or OpenTofu) with providers for AWS and Azure; keep state in a remote backend (e.g., HashiCorp Consul) and use workspaces per cloud.  
- **Networking** – Site‑to‑site VPN or Azure ExpressRoute/AWS Direct Connect + Transit Gateway ↔ Azure Virtual WAN for encrypted inter‑cloud traffic; use Cloud‑native DNS (Route 53 + Azure DNS) with global load balancer (e.g., F5 Multi‑Cloud or Istio multicluster).  
- **Identity Federation** – Deploy Azure AD/WS‑Fed or AWS IAM Identity Center; map groups to cloud roles via SAML/OIDC; enable just‑in‑time access.  
- **Trade‑offs** – Increased operational overhead (dual‑skill set, separate billing, networking latency), potential for inconsistent services, higher cost for data transfer. Benefits: risk mitigation, ability to leverage best‑of‑breed services, compliance with data‑sovereignty rules.  
Multi‑cloud justified when: regulatory constraints require data in specific jurisdictions, you need best‑of‑breed services (e.g., AWS ML + Azure Analytics), or you have a strong mandate to avoid vendor lock‑in. Unnecessary when workloads are homogeneous, you can achieve required redundancy within a single cloud via multi‑region, and the added complexity outweighs benefits.

**OT1** – Purdue Model (ISA‑95) levels:  
0 – **Process Control** (sensors, actuators, PLCs).  
1 – **Basic Process Control** (PLC/DCS control loops, RTUs).  
2 – **Area Supervisory Control** (SCADA HMIs, engineering workstations).  
3 – **Site‑Level Operations & Management** (MES, production scheduling, historian).  
4 – **Business Planning & Logistics** (ERP, supply‑chain, corporate IT).  
5 – **Enterprise** (corporate strategy, finance, external partners).  
(At least four described above.)

**OT2** – IT networks focus on data, frequent patching, and standard OS; OT networks prioritize deterministic, real‑time control of physical processes. Patching OT can introduce latency, require downtime, or break certified firmware; many OT devices lack patch mechanisms or have long validation cycles, so applying IT‑style patches risks safety and availability.

**OT3** – **IDMZ (Industrial DMZ)** sits between IT (Level 4) and OT (Levels 0‑3). Allowed traffic: typically outbound from OT to IT for monitoring/data (e.g., historian → IT analytics) and inbound from IT to OT only for tightly controlled management (e.g., patch distribution, time sync) via authenticated, inspected proxies. Direct Level 4 → Level 1 is dangerous because it bypasses multiple security layers, exposing real‑time control loops to IT threats (malware, ransomware) that could manipulate actuators or cause process upsets.

**OT4** – Protocols & Purdue level:  
1. **Modbus TCP** – Primarily Level 0/1 (sensor/actuator communication, PLC‑to‑PLC).  
2. **OPC UA** – Spans Levels 1‑3 (device‑to‑SCADA, historian, MES); provides secure, information‑model‑based access.  
3. **OPC UA (continued)** – Also used at Level 4 for IT‑OT integration when secured via firewalls/gateways.  
4. **EtherNet/IP (CIP)** – Level 0/1 (industrial Ethernet for I/O, motion control).  
5. **PROFINET** – Level 0/1 (real‑time I/O, drives, PLC‑to‑PLC).  
6. **MQTT** – Often Level 2‑3 (edge gateway to cloud/IIoT broker) for telemetry; can cross into Level 4 for enterprise ingestion.

**OT5** – **Data diode** – Hardware enforces one‑way flow (e.g., OT → IT) using optical isolation; prevents any inbound traffic. Use when you need guaranteed isolation (e.g., sending sensor data to a corporate analytics system while ensuring no cyber‑path back to OT). Limitation: cannot support protocols requiring bidirectional handshakes (e.g., TCP ACK, request‑reply) without application‑level proxies; less flexible than a firewall which can inspect and allow controlled bidirectional traffic.

**OT6** – Data flow:  
SCADA → Historian (Level 3) → OPC UA Server (exposes tags) → Edge Gateway (runs OPC UA client + MQTT publisher) → MQTT Broker (in DMZ or cloud edge) → Cloud Ingestion (e.g., IoT Hub, Kinesis).  
Security boundaries:  
- Historian to OPC UA server inside OT LAN (firewalled).  
- Edge gateway placed in IDMZ; only outbound MQTT (or HTTPS) allowed to cloud; inbound strictly limited to management (e.g., config updates) via mutual TLS.  
- Cloud side ingests via TLS‑encrypted endpoint; no inbound OT‑initiated connections allowed.

**OT7** – IEC 62443 defines **Security Zones** (groups of assets with common security requirements) and **Conduits** (communication paths between zones).  
- **Zone** = set of devices sharing same risk profile (e.g., all PLCs on a line).  
- **Conduit** = defined conduit (firewall, router, VLAN) that enforces policy between zones.  
Design for plant:  
- **Zone A** – Corporate IT (Level 4/5).  
- **Zone B** – Engineering workstations (Level 3).  
- **Zone C** – SCADA servers & historian (Level 3).  
- **Zone D** – PLCs & I/O (Levels 0‑1 per line).  
- **Zone E** – Safety Instrumented Systems (SIS) (isolated).  
Conduits:  
- IT ↔ Engineering (firewall with strict allow‑list, e.g., WSUS, time).  
- Engineering ↔ SCADA (firewall, allow OPC UA, historian sync).  
- SCADA ↔ PLCs (unidirectional diode or firewall allowing only read‑only tags from PLC to SCADA, no write unless authenticated).  
- SIS isolated: air‑gap or diode allowing only safety‑status signals out, no inbound IT/OT traffic.

**OT8** – Segmentation strategy for 200 PLCs, 30 HMIs, SCADA, historian:  
- **VLAN design**:  
  - VLAN 10 – PLC Line 1 (50 PLCs).  
  - VLAN 11 – PLC Line 2 (50 PLCs).  
  - VLAN 12 – PLC Line 3 (50 PLCs).  
  - VLAN 13 – PLC Line 4 (50 PLCs).  
  - VLAN 20 – HMIs (30) – each line’s HMI in its line VLAN or a dedicated HMI VLAN with inter‑VLAN routing via firewall.  
  - VLAN 30 – SCADA servers.  
  - VLAN 31 – Historian.  
  - VLAN 40 – Management/Engineering workstations.  
  - VLAN 99 – IDMZ (edge gateways, VPN concentrators).  
- **Firewall placement**:  
  - Perimeter firewall between corporate IT and IDMZ.  
  - Internal firewalls (or ACLs on L3 switches) between each PLC VLAN and the SCADA/historian VLANs, enforcing whitelisted protocols (Modbus TCP, OPC UA) and direction (PLC→SCADA read, SCADA→PLC write only for authenticated commands).  
  - Separate firewall for historian ↔ corporate analytics (allow outbound only).  
- **Switch architecture**: Use industrial‑grade Layer 3 switches with ACLs, spanning‑tree disabled, and redundant uplinks to core. Enable port security, 802.1X where possible.  
- **Vendor remote access**: Place a hardened jump‑host/bastion in the IDMZ; vendors connect via MFA‑protected VPN to the jump‑host, then jump to specific PLC/HMI VLANs via jump‑host with time‑limited, session‑recorded SSH/RDP. No direct corporate‑to‑PLC routing.  
- **Transition without stopping production**:  
  1. Build new VLANs and firewall rules in shadow mode (monitor only).  
  2. Gradually move one line’s PLCs to its VLAN during a scheduled maintenance window, keeping old VLAN active as fallback.  
  3. Verify connectivity, then decommission old VLAN. Repeat line‑by‑line.  
  4. Use temporary “allow‑all” rules with logging to catch missed traffic, then tighten.

**OT9** – **SIS** (Safety Instrumented System) executes safety‑critical functions (e.g., emergency shutdown) independent of BPCS (Basic Process Control System) which handles normal regulation. IEC 61511 defines safety lifecycle for SIS in the process industry. SIS network must be air‑gapped or strictly isolated because any compromise could prevent safety actions or trigger false trips, leading to hazardous conditions. If ransomware reaches SIS, it could block safety logic, cause unsafe state, or trigger spurious shutdowns, potentially resulting in equipment damage, environmental release, or personnel injury.

**OT10** – **PLC** – Programmable Logic Controller for discrete or simple process control (ladder logic, structured text). **DCS** – Distributed Control System, integrates many controllers, HMIs, and engineering stations for large continuous processes (e.g., refineries). **SCADA** – Supervisory Control and Data Acquisition, provides high‑level monitoring, data acquisition, and limited control over geographically dispersed sites. They can coexist: PLCs handle low‑level I/O, DCS coordinates multiple PLCs for complex continuous processes, SCADA oversees multiple DCS/PLC sites and provides enterprise visibility.

**OT11** – Remote access architecture:  
- **Jump host/bastion** in IDMZ with MFA, hardened OS, limited to necessary protocols.  
- **Session recording & audit** (e.g., via tlog, Syslog).  
- **Vendor‑specific accounts** with just‑in‑time (JIT) elevation, time‑limited (e.g., 2‑hour windows).  
- **No direct RDP from corporate to HMI** because it bypasses IDMZ controls, exposes HMIs to corporate malware, and provides a potential pivot into OT control plane.  
- Use **VPN with split‑tunnel** only to the jump‑host; enforce least‑privilege RBAC on the jump‑host; log all commands.

**OT12** – Detection & response for water‑treatment plant (nation‑state via compromised vendor VPN):  
- **Network monitoring**: Deploy passive IDS/IPS (e.g., Zeek, Snort) on IDMZ and OT VLANs; use anomaly detection (baseline Modbus/OPC UA traffic) to spot unusual reads/writes or new connections.  
- **Asset inventory**: Maintain automated, passive discovery (LLDP, ARP, MAC‑OUI) plus manual validation; tag each device with criticality.  
- **IR steps**:  
  1. Containment – isolate affected VLAN at firewall, block vendor VPN traffic, quarantine jump‑host.  
  2. Evidence collection – capture netflow, PCAP, logs from firewall, IDS, historian.  
  3. Eradication – remove malicious VPN credentials, reset vendor credentials, patch VPN appliance.  
  4. Recovery – restore from known‑good backups, verify integrity of PLC/HMI firmware.  
  5. Post‑incident review – update policies, improve vendor vetting.  
- **Coordination**: SOC alerts control room; control room verifies process status via HMIs; if safe, they can initiate manual safe‑shutdown while OT team isolates.  
- **Plant operator role**: Verify physical process indicators (pressure, flow, temperature) match HMI readings; if discrepancy, initiate manual safe‑state procedures; communicate status to OT and IT teams.

**OT13** – **HMI** (Human‑Machine Interface) is the graphical interface operators use to monitor and control a process (display alarms, setpoints, trends). It runs on a Windows/Linux workstation or panel PC. An **engineering workstation** is used for configuration, programming, and diagnostics (e.g., loading ladder logic, updating firmware) and typically has higher privileges and development tools; HMIs are runtime‑focused, engineering workstations are design‑focused.

**OT14** – **Historian** is a time‑series database that continuously logs process variables from PLCs/SCADA for performance analysis, compliance, and optimization. **Plant historian** (Level 3) stores high‑resolution data for a single site/facility. **Enterprise historian** (Level 4) aggregates data from multiple plants, often with lower resolution, for corporate reporting, KPIs, and cross‑site analytics.

**OT15** – **Ladder logic** is a graphical programming language resembling electrical relay diagrams; executed by a PLC’s runtime engine. It remains dominant because it’s intuitive for electricians, easy to troubleshoot, deterministic, and supported by virtually all PLC vendors; legacy code bases and training inertia keep it prevalent despite newer IEC 61131‑3 languages.

**OT16** – **RTU** (Remote Terminal Unit) is a rugged, often solar‑powered device that acquires sensor data and communicates over long‑range, low‑bandwidth links (cellular, satellite, radio). Unlike a PLC, an RTU typically lacks complex logic execution; it focuses on data acquisition and simple control (e.g., setpoint adjustment). Deploy RTUs in geographically dispersed, harsh environments (pipelines, water reservoirs, oil rigs) where power and communication infrastructure are limited.

**OT17** – Analog signals represent continuous values (4‑20 mA, 0‑10 V). Digital signals are discrete on/off. **4‑20 mA** is preferred because the live zero (4 mA) allows detection of wire breaks (0 mA indicates fault) and provides better noise immunity; 0‑20 mA cannot distinguish a broken wire from a legitimate zero signal.

**OT18** – Asset inventory is foundational because you cannot protect what you don’t know. Discovery techniques:  
- **Passive network monitoring** (port‑mirroring, TAPs) to see MAC/IP traffic, protocol fingerprints.  
- **Active scanning** (SNMP, Modbus polls, ARP sweeps) – risky because it can generate traffic that interferes with real‑time control, cause PLCs to enter fault state, or trigger safety trips. Hence active scanning is used only in maintenance windows or with very low‑rate, non‑intrusive probes.

**OT19** – MITRE ATT&CK for ICS tactics (examples):  
1. **Initial Access** – *Exploit Public‑Facing Application* (e.g., vulnerable OPC UA web interface).  
2. **Execution** – *Command‑Line Interface* (abusing `cmd.exe` on engineering workstation).  
3. **Persistence** – *Modify Controller Logic* (injecting malicious ladder logic).  
4. **Privilege Escalation** – *Exploit Vulnerability in PLC Firmware*.  
5. **Defense Evasion** – *Indirect Command Execution* (using legitimate admin tools to hide malicious activity).  
6. **Discovery** – *Network Sniffing* (capturing ICS traffic to map topology).  
7. **Lateral Movement** – *Remote Services* (using SMB/RDP to move from IT to OT).  
8. **Collection** – *Screen Capture* (grabbing HMI displays).  
9. **Command and Control** – *Standard Application Layer Protocol* (MQTT over TLS to C2 server).  
10. **Inhibit Response Function** – *Modify Safety System* (altering SIS logic to block trips).  
Differs from enterprise ATT&CK by focusing on OT‑specific assets (PLCs, RTUs, safety systems) and impact on physical processes. Use it to map existing controls, identify missing detections (e.g., no logic‑integrity monitoring), and prioritize mitigations like code signing, network segmentation, and SIS isolation.

**OT20** – Converged IT/OT SOC for 3 sites:  
- **Log collection**: Deploy lightweight agents (e.g., OSSEC, Wazuh) on engineering workstations and historians; use syslog forwarding from firewalls/IDS; for PLCs/HMIs, rely on passive network taps that feed NetFlow/IPFIX and protocol‑specific logs (OPC UA, Modbus) to a central collector; ensure collection is passive and does not add latency.  
- **SIEM**: Centralized (e.g., Splunk, Azure Sentinel, QRadar) with parsers for ICS protocols; normalize timestamps (UTC).  
- **OT‑specific detection rules**:  
  - Unexpected write to safety‑critical register.  
  - Change in ladder logic checksum (hash comparison against baseline).  
  - Sustained scan of Modbus addresses from an IT subnet.  
  - Authentication failure spikes on jump‑host.  
  - Outbound MQTT to unknown broker.  
- **Alert triage workflow**: Tier‑1 analyst (IT) validates alert, enriches with asset context; if OT‑relevant, escalates to Tier‑2 OT engineer who checks process impact via HMI/historian; joint decision on containment.  
- **Staffing**: Mix of SOC analysts (IT) and OT engineers (control‑system specialists); cross‑train on basics of each domain.  
- **False positives**: Common due to noisy OT protocols; mitigate by baselining normal traffic, using anomaly thresholds, and requiring correlation (e.g., network anomaly + logic change).  
- **Handling unauthorized firmware change on PLC**: Alert triggers; OT engineer verifies firmware hash against approved baseline; if unauthorized, initiates containment (isolate PLC VLAN), notifies control room to prepare for possible manual override, rolls back to known‑good firmware from secure repository, and logs incident for post‑mortem review.
