
**AA1** – Monolith vs. Microservices  
- **Monolith:** Single deployable unit; all components share the same process, memory space, and database schema.  
- **Microservices:** Independently deployable services, each with its own process, often its own datastore, communicating over network APIs.  

**Three problems introduced by microservices that monoliths don’t have:**  
1. **Network latency & partial failures** – inter‑service calls add latency and can fail independently.  
2. **Data consistency challenges** – distributed transactions are harder; you often need eventual consistency or sagas.  
3. **Operational overhead** – service discovery, versioning, monitoring, logging, and deployment pipelines become more complex.

---

**AA2** – Synchronous vs. Asynchronous communication  
- **Synchronous:** Caller blocks until the callee returns a response (request‑reply). Example: HTTP/REST or gRPC call.  
- **Asynchronous:** Caller sends a message and continues; the receiver processes it later. Example: publishing to a message queue (RabbitMQ) or a log‑based broker (Kafka).  

---

**AA3** – API Gateway vs. Reverse Proxy  
- **Reverse Proxy:** Primarily terminates TLS, does load balancing, SSL offloading, and simple path‑based routing; works at L4/L7 but generally unaware of API semantics.  
- **API Gateway:** A specialized reverse proxy that adds API‑centric features: authentication/authorization, rate limiting, request/response transformation, aggregation, caching, and analytics.  

**Can an API Gateway replace a reverse proxy entirely?**  
Yes, for most north‑south traffic because it performs all reverse‑proxy functions plus API‑specific logic. However, you may still keep a plain reverse proxy (e.g., NGINX) in front of the gateway for DDoS mitigation, TCP‑level load balancing, or to handle non‑HTTP protocols (e.g., raw TCP, WebSocket upgrades) that the gateway doesn’t support.

---

**AA4** – Saga pattern  
A saga is a sequence of local transactions where each step has a compensating transaction to undo it if a later step fails, achieving eventual consistency across services.  

- **Choreography‑based:** Services listen to events and trigger the next step or compensating action autonomously (no central coordinator).  
- **Orchestration‑based:** A dedicated orchestrator (workflow engine) tells each service what to do and when to invoke compensations.  

**When to use each:**  
- Use **choreography** for simple, short‑lived sagas with few participants and when you want low coupling and no single point of failure.  
- Use **orchestration** for complex, long‑running workflows, when you need centralized monitoring, retry policies, or dynamic routing.

---

**AA5** – CQRS & Event Sourcing  
- **CQRS:** Separates the write model (commands) from the read model (queries). Writes update a command‑side store; reads are served from optimized read‑side projections.  
- **Often paired with Event Sourcing:** The write model stores a sequence of events (the source of truth); read models are built by projecting those events.  

**Problem solved vs. traditional CRUD:**  
CRUD couples reads and writes to the same representation, causing contention and limiting scalability. CQRS+Event Sourcing lets you scale reads independently, audit every change, rebuild read models for new queries, and handle high‑write workloads without locking read paths.

---

**AA6** – Circuit Breaker  
- **States:**  
  1. **Closed:** Requests flow normally; failure count is tracked.  
  2. **Open:** After a threshold of failures, the breaker trips and short‑circuits requests (returns error/fast‑fail).  
  3. **Half‑Open:** After a timeout, a limited number of trial requests are allowed; if they succeed, breaker closes; otherwise it reopens.  

- **Difference from simple retry:** A retry blindly re‑attempts; a circuit breaker stops sending traffic when the downstream is unhealthy, preventing overload and giving it time to recover.  

- **Using both together:** Apply retries for transient, short‑lived faults (e.g., brief network glitch) while the circuit breaker protects against prolonged outages. Typical pattern: attempt a request → if fails, retry with back‑off → if retries exceed limit, let the circuit breaker open.

**AA7** – Multi‑tenant SaaS isolation models  

| Model | Cost | Security | Operational Complexity | Noisy‑Neighbor Risk |
|-------|------|----------|------------------------|----------------------|
| **1. Shared DB, shared schema (row‑level tenant ID)** | Lowest (single DB, minimal admin) | Moderate – relies on correct tenant‑ID filtering; bugs can leak data. | Low – simple schema, backups, migrations. | High – one tenant’s heavy queries can affect others; need query throttling. |
| **2. Shared DB, separate schema per tenant** | Medium (more schemas, more objects) | Higher – logical isolation; mis‑routing still possible but less likely. | Medium – schema migrations must be applied per tenant; more moving parts. | Medium – still shares CPU/I/O; can mitigate with resource governor. |
| **3. Separate DB per tenant** | Highest (provisioned per tenant) | Highest – physical isolation; breach limited to one DB. | Highest – manage many DB instances, backups, patches, monitoring. | Lowest – each tenant gets dedicated resources; noisy neighbor eliminated. |

**Trade‑off summary:** Choose model 1 for cost‑sensitive, low‑risk apps; model 2 when you need stronger logical isolation but still want shared infrastructure; model 3 for regulated, high‑value tenants where isolation outweighs cost.

**AA8** – Eventual vs. Strong consistency & inventory system  

- **Strong consistency:** Every read sees the most recent write; ACID transactions across nodes.  
- **Eventual consistency:** Updates propagate asynchronously; reads may see stale data temporarily but converge.  

**Inventory system that must never oversell:**  
- **Consistency model:** Strong consistency (or at least *read‑your‑writes* + *linearizable* inventory decrement).  
- **Data store:** A CP‑oriented distributed database that supports transactions, e.g., Google Cloud Spanner, CockroachDB, or a sharded PostgreSQL with synchronous replication (or a single‑node DB with read replicas for reporting only).  
- **Patterns:**  
  1. **Reserve‑then‑commit** (two‑phase): Reserve stock in a transaction, then confirm order; if payment fails, release reservation.  
  2. **Idempotent deduplication** using a unique order‑id key to prevent double‑decrement.  
  3. **Optimistic locking** (version column) on the inventory row to detect concurrent sells.  
  4. **Fallback to event‑sourced ledger** for audit, but the primary decrement remains strongly consistent.  

At scale, you can shard inventory by product ID or SKU, keeping each shard strongly consistent, and route requests to the appropriate shard.

---

**AA9** – Sidecar proxy in a service mesh (Envoy in Istio)  

- **Sidecar proxy:** A lightweight proxy deployed alongside each service instance (same pod) that intercepts all inbound/outbound traffic, applying mesh policies (mTLS, traffic shifting, observability).  
- **Envoy in Istio:** Envoy runs as the sidecar; Istio’s control plane (Pilot, Citadel, Galley) configures Envoy via xDS APIs (routes, clusters, listeners, security). Envoy does L7 filtering, load balancing, retries, timeouts, and telemetry.  
- **Data plane vs. control plane:**  
  - **Data plane:** The set of sidecar proxies (Envoy) that actually process traffic.  
  - **Control plane:** Istio components that generate and distribute configuration to the data plane, enforce policies, and collect telemetry.  
- **mTLS between sidecars vs. application‑level TLS:**  
  - **Sidecar mTLS:** Transparent, automatic mutual TLS between proxies; services need not handle certificates or TLS termination. Provides per‑service identity, zero‑trust network, and easy rotation.  
  - **Application‑level TLS:** Requires each service to manage certs, handshakes, and possibly terminates TLS at the app layer; more complex, harder to rotate, and doesn’t give uniform policy enforcement across services.  

Thus, sidecar mTLS solves the problem of securing service‑to‑service communication without burdening application code.

**AA10** – Strangler Fig pattern for .NET Framework → .NET 8 microservices  

1. **Identify a bounded context** (e.g., “Order Management”) in the monolith that can be extracted.  
2. **Create a new .NET 8 microservice** that implements the same functionality, exposing its API (REST/gRPC).  
3. **Route traffic:** Place an API gateway or reverse proxy in front of the monolith. Initially, all requests go to the monolith.  
4. **Strangle:** For the chosen context, configure the gateway to proxy requests to the new microservice instead of the monolith.  
5. **Implement anti‑corruption layer** (if needed) to translate between monolith’s internal data model and the microservice’s contracts.  
6. **Monitor & cut over:** Verify correctness, performance, and observability. Once confident, decommission the corresponding code/modules from the monolith.  
7. **Repeat** for other bounded contexts until the monolith is fully strangled.  

Key practices: feature toggles, database per service (or shared DB with schema per service during transition), contract testing, and automated CI/CD for both monolith and microservice.

---

**AA11** – 12‑Factor App methodology (6 factors)  

1. **Codebase:** One codebase tracked in version control, many deploys.  
2. **Dependencies:** Explicitly declare and isolate dependencies (e.g., via manifest files).  
3. **Config:** Store configuration in environment variables, not in code.  
4. **Backing services:** Treat databases, queues, etc., as attached resources accessed via URL/credentials.  
5. **Build, release, run:** Strictly separate stages; each release is immutable.  
6. **Processes:** Execute the app as one or more stateless processes; any persisted data goes to backing services.  

*Why they matter:* They promote portability, scalability, and resilience in cloud‑native environments by eliminating hidden assumptions about the runtime environment.

**AA12** – Event‑driven (Kafka) vs. Request‑driven (REST/gRPC)  

| Aspect | Kafka‑based EDA | REST/gRPC Request‑driven |
|--------|----------------|--------------------------|
| **Coupling** | Loose: producers/consumers only know topic schema. | Tighter: caller must know endpoint and contract; versioning needed. |
| **Scalability** | Horizontal scaling of consumers; high throughput; natural back‑pressure. | Scales via load balancers; each request consumes a connection; can become bottleneck under bursty load. |
| **Debugging complexity** | Harder: need to trace event flow across topics, handle out‑of‑order, replay. | Simpler: request‑response logs; easier to correlate with IDs. |
| **Ordering guarantees** | Per‑partition ordering; can guarantee order if keyed correctly. | No inherent ordering; each request independent. |
| **Failure handling** | Consumer can pause, commit offsets later; dead‑letter topics for poison messages. | Retries with exponential back‑off; circuit breaker; need idempotency. |
| **When to choose** | High‑volume, decoupled workflows, event sourcing, audit trails, real‑time analytics, fan‑out to many consumers. | Synchronous user‑facing APIs, CRUD operations, low‑latency request/response, when immediate response is required. |

---

**AA13** – Load balancer & L4 vs L7  

- **Load balancer:** Device that distributes incoming client requests across multiple backend servers to improve availability and performance.  
- **Layer 4 (Transport):** Works on TCP/UDP; makes decisions based on IP address and port (e.g., round‑robin, least connections). No insight into application data.  
- **Layer 7 (Application):** Works on HTTP/HTTPS; can inspect URLs, headers, cookies, and make routing decisions (e.g., path‑based, host‑based, cookie‑based affinity).  

**Use case requiring L7:** Path‑based routing to different microservices (e.g., `/api/users` → user service, `/api/orders` → order service) or implementing HTTP‑level features like SSL termination, request/response modification, or WAF rules.

---

**AA14** – Message queue vs. log‑based broker  

- **Message queue (RabbitMQ):** Traditional broker; messages are removed after acknowledgment; supports point‑to‑point and publish/subscribe with flexible routing (exchanges, bindings). Good for task distribution, RPC‑style patterns, and when you need explicit acknowledgment and per‑message ordering.  
- **Log‑based broker (Kafka):** Immutable, append‑only log; consumers read at their own offset; messages retained for a configurable time. Designed for high‑throughput streaming, replay, and multiple independent consumers.  

**Pick RabbitMQ when:** You need complex routing, per‑message acknowledgments, low‑latency task queues, or request‑reply patterns.  
**Pick Kafka when:** You need high‑volume event streaming, log‑like replay, multiple consumer groups, or durable audit trails.

---

**AA15** – Container vs. VM  

- **Container:** Isolated user‑space process sharing the host OS kernel; packages app + dependencies; starts in seconds; lightweight (MBs).  
- **Virtual Machine:** Full guest OS with its own kernel, running on a hypervisor; heavier (GBs), slower boot, stronger isolation.  

**Why containers popular for microservices:** Fast startup, high density, easy image versioning, consistent dev/prod environments, and seamless integration with orchestration platforms (Kubernetes, Docker Swarm).

---

**AA16** – Stateless vs. Stateful services  

- **Stateless:** No persistent client‑specific data stored between requests; any instance can handle any request. Example: a REST API that reads/writes only to a shared database.  
- **Stateful:** Maintains client‑specific data in memory or local disk between requests (e.g., a chat server keeping websocket sessions, or an in‑memory cache).  

**Stateless easier to scale horizontally:** Because adding more instances doesn’t require state transfer or synchronization; load balancer can distribute requests arbitrarily.  

**Example:** Stateless – payment processing service; Stateful – gaming server holding player positions.

---

**AA17** – ORM  

- **ORM (Object‑Relational Mapper):** Library that maps application objects to relational database tables, allowing CRUD operations via object‑oriented code.  
- **Popular ORMs:**  
  - **Java:** Hibernate  
  - **Python:** SQLAlchemy (or Django ORM)  
  - **.NET:** Entity Framework Core  
  - **Node.js:** Sequelize / TypeORM  

**Trade‑offs vs. raw SQL:**  
- **Pros:** Faster development, reduced boilerplate, portable across DBs, lazy loading, change tracking.  
- **Cons:** Potential performance overhead, opaque SQL generation, learning curve, difficulty tuning complex queries, risk of N+1 selects.

---

**AA18** – Bulkhead pattern  

- **Bulkhead:** Isolates critical resources (threads, connections, memory) into separate pools so that failure or overload in one pool doesn’t exhaust resources needed by others.  
- **Relation to microservices:** Prevents a misbehaving downstream service from consuming all threads/connection pools of a caller, thereby protecting other services.  

**Concrete implementation:**  
- **Thread‑pool bulkhead:** Define separate `ExecutorService` pools per downstream service (e.g., 10 threads for Service A, 5 for Service B). Call each service using its dedicated pool; if Service A blocks, Service B’s pool remains available.  
- **Deployment‑group bulkhead:** Deploy instances of a service in separate VMs or Kubernetes namespaces with distinct resource limits (CPU/memory). A noisy neighbor in one namespace cannot starve the other.  

---

**AA19** – Real‑time collaborative editing: OT vs. CRDT  

| Aspect | Operational Transformation (OT) | Conflict‑free Replicated Data Types (CRDT) |
|--------|--------------------------------|-------------------------------------------|
| **Consistency guarantees** | Strong eventual consistency if transformation functions are correct and ordered; requires reliable sequencing (often via central server). | Strong eventual consistency guaranteed by mathematical properties (commutativity, associativity, idempotency) regardless of delivery order. |
| **Latency** | Low latency when using a central server that sequences ops; can increase latency if waiting for acknowledgments. | Can achieve low latency with peer‑to‑peer; no need to wait for central ordering, but may need extra metadata (vector clocks). |
| **Complexity** | High: must implement correct transformation functions for each operation type; easy to get wrong leading to divergence. | Lower for simple data types (counters, sets, registers, sequences); more complex for rich text but libraries exist (Yjs, Automerge). |
| **Offline support** | Requires storing ops and replaying them upon reconnection; must guarantee that the server can re‑apply transforms correctly. | Naturally supports offline: local changes merge automatically when connectivity resumes; no need for central sequencing. |
| **Choice for offline editing** | **CRDTs** are preferable because they guarantee convergence without relying on a central sequencer, making offline work seamless. |

Thus, for a system that must support offline editing, choose a CRDT‑based approach (e.g., Yjs for rich text).

**AA20** – Distributed tracing challenges in polyglot microservices  

- **Context propagation:** Need to inject trace IDs into every outbound request/message. Standards: W3C Trace Context (`traceparent`, `tracestate`) and legacy B3 headers. Libraries (OpenTelemetry, Jaeger client, Zipkin) must be used in each language.  
- **Sampling strategies:**  
  - **Head‑based:** Decision made at the start of a trace (e.g., sample 10 % of all requests). Low overhead but may miss rare error paths.  
  - **Tail‑based:** Decision made after seeing the full trace (e.g., keep traces with errors or high latency). Higher storage/compute cost but captures interesting traces.  
- **Trace storage & querying:** Backends like Jaeger (Cassandra/Elasticsearch), Tempo (object store + Loki), or Zipkin. Must support high write throughput, indexing by trace ID, service name, timestamps, and attributes for fast queries.  
- **Interaction with async messaging:** When a message goes through a broker (Kafka, RabbitMQ), the producer must inject trace context into message headers; the consumer extracts it and starts a new span. Continuity relies on the broker preserving headers (Kafka does).  
- **Ensuring trace continuity through Kafka:**  
  1. Producer creates a span, injects `traceparent` into the Kafka record’s headers.  
  2. Record is written to the topic; headers are retained unchanged.  
  3. Consumer reads the record, extracts headers, creates a child span linked to the producer’s span.  
  4. If using Kafka Streams or KSQL, ensure the library forwards headers.  
  5. For exactly‑once semantics, ensure the trace context is part of the message payload or headers so that reprocessing doesn’t create duplicate spans.  

Additional challenges: correlating logs with traces, handling high cardinality tags, and avoiding sampling bias in polyglot environments where instrumentation maturity varies.

## On‑Premise Infrastructure Architecture

**OP1** – Hypervisor types  

- **Type 1 (bare‑metal):** Runs directly on hardware. Examples: VMware ESXi, Microsoft Hyper‑V Server, Xen, KVM (when hosted on a minimal Linux).  
- **Type 2 (hosted):** Runs as an application on a conventional OS. Examples: VMware Workstation/Fusion, Oracle VirtualBox, Parallels Desktop.  

---

**OP2** – SAN vs NAS  

- **SAN (Storage Area Network):** Block‑level storage accessed over a dedicated network (usually Fibre Channel or iSCSI). Appears to servers as local disks. Used for databases, VMFS, high‑performance workloads.  
- **NAS (Network‑Attached Storage):** File‑level storage accessed via standard file protocols (NFS, SMB/CIFS). Appears as a network share. Used for user home directories, media archives, backup targets.  

**When to use each:** SAN for low‑latency block access (e.g., OLTP databases, virtual machine disks). NAS for simple file sharing, heterogeneous client access, and when you want built‑in file‑system features (snapshots, quotas).

---

**OP3** – 3‑tier network vs leaf‑spine  

- **3‑tier (core/distribution/access):** Hierarchical design; access switches connect to distribution, which aggregates to core. Suffers from oversubscription and longer east‑west paths as traffic must traverse multiple layers.  
- **Leaf‑spine:** Two‑layer fabric; every leaf (access) switch connects to every spine (core). Provides non‑blocking, predictable latency, and equal‑cost multipath (ECMP) for east‑west traffic. Solves the “traffic hairpin” problem and scales better with modern server‑to‑server traffic patterns.  

---

**OP4** – HA Proxmox cluster with shared storage  

- **Node count:** Minimum 3 nodes for quorum (allows loss of 1 node). For higher fault tolerance, 5 nodes (tolerates 2 failures).  
- **Quorum:** Proxmox uses corosync; quorum = (N/2)+1 votes. With 3 nodes, quorum = 2; with 5 nodes, quorum = 3.  
- **Fencing (STONITH):** Essential to isolate a failed node; can be implemented via IPMI/iLO, APC PDU, or shared‑storage fencing (e.g., SCSI‑3 persistent reservations). Prevents split‑brain.  
- **Shared storage options:**  
  - **Ceph RADOS block devices (RBD)** – scalable, self‑healing, integrates with Proxmox via Ceph client.  
  - **iSCSI target** – simpler, but requires external storage array or Linux‑iSCSI target; multipath for redundancy.  
  - **NFS** – easy to set up; suitable for less‑I/O‑intensive workloads; ensure NFSv4 with locking and reliable network.  
- **During node failure:** Corosync detects loss, quorum re‑evaluates. If quorum remains, VMs/CTs on the failed node are migrated (if HA enabled) to other nodes; fencing ensures the failed node is powered off or its storage access revoked to prevent dual‑write.  

---

**OP5** – VLAN trunking & 802.1Q  

- **802.1Q tagging:** Adds a 4‑byte VLAN ID field to Ethernet frames; allows multiple VLANs to share a single physical link (trunk).  
- **Single NIC on 3 VLANs (Linux):**  
  1. Create VLAN sub‑interfaces: `ip link add link eth0 name eth0.10 type vlan id 10` (repeat for IDs 20,30).  
  2. Bring them up: `ip link set dev eth0.10 up` etc.  
  3. Assign IP addresses or bridge them as needed.  
  4. Ensure the physical switch port is configured as a trunk allowing those VLANs.  

---

**OP6** – RAID levels & choice for 6‑drive DB server  

- **RAID 1:** Mirrored pair; 2 drives → 50 % capacity, can survive 1 drive failure per mirror.  
- **RAID 5:** Striping with distributed parity; needs ≥3 drives; capacity = (N‑1)*size; survives 1 drive failure.  
- **RAID 6:** Double parity; survives 2 drive failures; capacity = (N‑2)*size.  
- **RAID 10 (1+0):** Mirrored pairs then striped; needs even # drives ≥4; capacity = (N/2)*size; survives up to N/2 failures if no mirror loses both drives.  
- **RAID Z2 (ZFS):** Similar to RAID 6 but with variable stripe width and self‑healing; survives 2 drive failures.  

**For 6 drives, balancing performance, capacity, fault tolerance:** Choose **RAID 10** (3 mirrored pairs).  
- Capacity = 3 × drive size (50 % raw).  
- Read performance ~ sum of all drives (striping across mirrors).  
- Write performance ~ half of raw (due to mirroring).  
- Can tolerate up to 3 drive failures as long as no mirrored pair loses both drives.  
If you need higher capacity and can accept slightly lower write performance, **RAID 6** gives 4 × drive size capacity and survives any two failures, but write penalty is higher due to double parity. For a DB where read‑heavy and latency matter, RAID 10 is usually preferred.

**OP7** – DNS architecture for 500‑person enterprise  

- **Internal AD‑integrated DNS:**  
  - Deploy two AD‑integrated DNS servers (Domain Controllers) as primary/secondary for the internal zone (e.g., `corp.example.com`).  
  - They serve as authoritative for internal records and forward unresolved queries to external forwarders.  
- **External (DMZ) DNS:**  
  - Two hardened DNS servers in the DMZ, authoritative for the public zone (`example.com`).  
  - Enable DNSSEC signing on this zone; keep the private key offline, publish DS record at the registrar.  
  - Configure them as recursive resolvers only for internal clients (or disable recursion and rely on internal DNS for resolution).  
- **Split‑horizon:**  
  - Internal DNS returns private IPs for internal services (e.g., `web.corp.example.com → 10.0.5.10`).  
  - External DNS returns public IPs for the same name (e.g., `web.example.com → 203.0.113.10`).  
  - Achieved by having separate zone files or using DNS views (BIND) or Azure DNS private/public zones.  
- **Forwarders & conditional forwarding:**  
  - Internal DNS forwards non‑internal queries to ISP resolvers or to the external DNS servers (if you want DMZ to handle external resolution).  
  - Conditional forwarding for partner domains: forward `partner.com` to partner’s DNS servers.  
- **DNSSEC:**  
  - Sign the external zone with a ZSK/KSK; rotate keys regularly; publish DS record.  
  - Internal zone may also be signed if you want end‑to‑end validation inside the corporate network.  
- **Laptop moving between office & VPN:**  
  - When on LAN, laptop uses internal DNS (DHCP‑provided).  
  - When on VPN, the VPN client pushes the internal DNS servers (or the internal domain’s search suffix) so queries for internal names resolve via the tunnel; external names go via the VPN’s DNS or split‑tunnel to public resolvers.  
  - Ensure split‑DNS config prevents DNS leaks.

**OP8** – PKI chain of trust & internal PKI deployment  

- **Chain of trust:** Root CA (self‑signed, offline) → Subordinate/Issuing CA (signed by root) → End‑entity certificate (signed by issuing CA). Trust is established when a verifier validates each signature up to a trusted root.  
- **Internal PKI deployment steps:**  
  1. **Root CA:** Generate offline, store private key in HSM or air‑gapped machine; create a self‑signed cert with long validity (e.g., 20 years).  
  2. **Subordinate/Issuing CA:** Online, connected to services; generate key pair, create CSR, have root CA sign it → issuing CA cert.  
  3. **CRL vs OCSP:** Publish CRLs regularly (e.g., every 24 h) to an accessible HTTP location; optionally enable OCSP responder for real‑time revocation checks.  
  4. **Certificate templates:** Define templates for different purposes (e.g., Web Server, Client Auth, Code Signing) with appropriate key usage, EKU, validity periods, and renewal settings.  
  5. **Auto‑enrollment:** Use Group Policy (Windows) or certmgr/autocert scripts to request and renew certificates automatically from the issuing CA.  
- **Consequences of compromise:**  
  - **Compromised subordinate CA:** Attacker can issue fraudulent certs for any purpose allowed by that CA’s template, but trust is limited to the subtree; you can revoke the subordinate CA’s cert and re‑issue a new one, limiting impact.  
  - **Compromised root CA:** Attacker can create a new subordinate CA that chains to the trusted root, effectively undermining the entire PKI; all issued certs become suspect, requiring a full root key replacement and re‑issuance of all downstream certs (high operational cost).  

Thus, keep the root CA strictly offline and protect it with HSMs, air‑gap, and strict procedural controls.

**OP9** – Hub‑and‑spoke WAN comparison (50 users/site, latency‑sensitive VoIP)  

| Technology | Cost | Reliability | Latency | Management Complexity | Security Posture | Verdict for VoIP |
|------------|------|-------------|---------|-----------------------|------------------|------------------|
| **MPLS** | High (leased circuits) | Carrier‑grade SLAs, high reliability | Low‑moderate (depends on provider) | Low (provider manages) | Good (private backbone) | Strong choice if budget allows; provides QoS guarantees. |
| **IPsec VPN over Internet** | Low‑moderate (internet bandwidth) | Depends on ISP redundancy; can add multiple ISP links for failover | Variable (internet latency + encryption overhead) | Moderate (manage tunnels, keys, routing) | Good (strong encryption) | Acceptable with QoS‑aware ISP and proper traffic shaping; jitter may be higher. |
| **SD‑WAN** | Moderate (subscription + hardware) | Can bond multiple links (MPLS, broadband, LTE) for redundancy; dynamic path selection | Low‑moderate (intelligent routing can pick lowest‑latency path) | Moderate‑high (central orchestrator, policies) | Good (encrypts traffic, integrates firewall) | Often best balance: provides application‑aware routing, QoS, and failover for VoIP. |
| **WireGuard mesh** | Low (open‑source, minimal hardware) | Depends on underlying internet links; each site‑to‑site tunnel is independent | Low (WireGuard is lightweight, low CPU overhead) | Low‑moderate (mesh key management, but scripts can automate) | Good (modern cryptography) | Viable for small scale; lacks built‑in QoS/policy controls; you’d need to add traffic shaping at each site. |

**Recommendation:** For 50 users per site with latency‑sensitive VoIP, **SD‑WAN** offers the best trade‑off: you can retain a low‑cost broadband link for primary traffic, supplement with an MPLS or LTE backup for redundancy, and enforce VoIP‑specific QoS policies centrally. If budget is no constraint and you need carrier‑grade guarantees, MPLS remains a solid alternative.

**OP10** – iDRAC/iLO/IPMI  

- **iDRAC (Dell), iLO (HP), IPMI (industry standard):** Out‑of‑band management controllers providing remote console, power control, hardware health monitoring, and firmware updates independent of the host OS.  
- **Why critical:** Allows administrators to recover a hung server, reinstall OS, or diagnose hardware without needing physical access or relying on the host’s network stack.  
- **If IPMI exposed to Internet:** Attackers can gain full remote control (power cycle, reset, install malicious firmware), leading to denial of service, data theft, or persistent compromise. Must be placed on a segregated management VLAN, firewalled, and accessed only via VPN or jump host with strong authentication and MFA.

**OP11** – LVM, LVM‑Thin, ZFS  

- **LVM (Logical Volume Manager):** Linear mapping of physical extents to logical volumes; supports resizing, snapshots (copy‑on‑write), and striping. Snapshots are read‑only by default; writable snapshots require extra space.  
- **LVM‑Thin:** Thin provisioning; logical volumes allocate blocks only when written. Snapshots are also thin and share blocks with the origin; efficient for many snapshots but requires monitoring of pool usage to avoid out‑of‑space conditions.  
- **ZFS:** Combined file system and volume manager; uses copy‑on‑write transactional model; built‑in snapshots (instantaneous, immutable), clones, compression, deduplication, and self‑healing via checksums. Snapshots are lightweight and unlimited; can be sent/received for replication.  

**When to use each:**  
- **LVM:** Traditional Linux environments needing flexible partition resizing; when you don’t need advanced data integrity features.  
- **LVM‑Thin:** Workloads with many short‑lived snapshots (e.g., CI/CD, VM templates) where storage efficiency matters.  
- **ZFS:** When you require end‑to‑end checksums, built‑in repair, snapshots/replication, and integrated volume management (e.g., NAS, backup servers, high‑value storage).  

**Snapshot semantics:**  
- LVM: Copy‑on‑write; snapshot size grows as changes occur; can become invalid if snapshot fills.  
- LVM‑Thin: Similar COW but draws from a thin pool; pool must have free space.  
- ZFS: Immutable reference to filesystem state; no space overhead until blocks are changed; safe to keep indefinitely.

**OP12** – Stretch cluster / DR for 3‑node Proxmox + Ceph  

- **Goal:** Survive loss of an entire site (e.g., power, network).  
- **Design options:**  
  1. **True stretch cluster:** Run Ceph monitors and OSDs across two sites; require a tie‑breaker (third monitor or arbiter) to avoid split‑brain when inter‑site link fails.  
  2. **Active‑passive DR:** Keep primary site running Ceph; replicate data asynchronously to a secondary site using Ceph’s `mirroring` or `rbd-mirror`; failover by promoting secondary.  
- **Ceph CRUSH rules:** Define a rule that places primary copies in Site A and replicas in Site B (e.g., `step take siteA step chooseleaf firstn 0 type host step emit`). Ensure enough OSDs per site to meet the desired replication size (e.g., `size 2` → one copy each site).  
- **Monitor placement:** For a stretch cluster, you need an odd number of monitors; typical layout: 2 monitors in Site A, 1 monitor in Site B (or vice‑versa) plus a lightweight monitor/arbiter in a third location (cloud) to act as tie‑breaker.  
- **Network latency requirements:** Ceph expects monitor‑to‑monitor RTT < 5 ms for tight quorum; OSD‑to‑OSD latency can be higher (10‑20 ms) but affects recovery speed. For DR, asynchronous replication tolerates higher latency (50‑100 ms).  
- **Split‑brain problem:** If the inter‑site link fails and each site believes it has quorum, both may allow writes, causing divergent data. Prevent by:  
  - Ensuring quorum requires a majority of monitors *including* the tie‑breaker.  
  - Using Ceph’s `min_size` and `full`/`nearfull` ratios to halt writes when connectivity degraded.  
  - Implementing a fencing/STONITH mechanism that powers down the losing site’s monitors.  
- **Why 2‑site Ceph without tie‑breaker is bad:** With an even number of monitors, a network partition can leave each side with exactly half the votes → no side reaches quorum → cluster blocks; or if you allow writes with `noout`/`nobackfill`, each side may diverge, causing split‑brain. A third monitor/arbiter breaks the tie.

**OP13** – DHCP & DORA  

- **DHCP (Dynamic Host Configuration Protocol):** Allows clients to obtain IP address, subnet mask, gateway, DNS, etc., from a server.  
- **DORA process:**  
  1. **Discover:** Client broadcasts DHCPDISCOREQ.  
  2. **Offer:** Server replies with DHCPOFFER (IP lease).  
  3. **Request:** Client broadcasts DHCPREQUEST requesting the offered address.  
  4. **Acknowledge:** Server sends DHCPACK, finalizing lease.  
- **When DHCP server unavailable & lease expires (Windows):**  
  - Client attempts to renew at 50 % of lease time; if no response, it rebinds at 87.5 %.  
  - If still no server, the client will eventually lose its lease, revert to APIPA (169.254.x.x) if configured, or lose network connectivity until a DHCP server is reachable or a static address is set.

**OP14** – Managed vs. unmanaged switch  

- **Managed switch:** Provides CLI/GUI for configuration: VLANs, port‑based QoS, link aggregation (LACP), STP/RSTP, port security, SNMP monitoring, mirroring, ACLs, and firmware upgrades. Essential for enterprise networks needing traffic segmentation, redundancy, and visibility.  
- **Unmanaged switch:** Plug‑and‑play; no configuration options; forwards frames based on MAC learning only. Suitable for small workgroups or temporary connections where simplicity is valued over control.

**OP15** – NTP & importance of time sync  

- **NTP (Network Time Protocol):** Synchronizes clocks of devices to a reference time source (e.g., GPS, atomic clocks) with sub‑millisecond accuracy on LANs.  
- **Why critical:**  
  - Authentication protocols (Kerberos, TLS) rely on time windows; skew can cause replay attacks or authentication failures.  
  - Distributed systems (databases, clusters) use timestamps for ordering transactions, conflict resolution, and log correlation.  
  - Scheduled jobs (cron, backup windows) depend on correct time.  
- **What can go wrong with drift:**  
  - Kerberos authentication fails (default skew 5 min).  
  - Database replication may apply changes out of order, leading to inconsistencies.  
  - Log analysis becomes impossible due to mismatched timestamps.  
  - Certificate validity checks may incorrectly treat certs as expired or not yet valid.

**OP16** – Physical server, VM, container  

- **Physical server:** Bare‑metal hardware running an OS directly.  
- **Virtual machine:** Emulated hardware running a guest OS via a hypervisor; provides strong isolation but higher overhead.  
- **Container:** Isolated user‑space process sharing host OS kernel; lightweight, fast start‑up.  
- **Run workload on bare metal when:**  
  - Need maximum performance (e.g., HPC, low‑latency trading).  
  - Require direct access to hardware features (GPUs, NICs, specialized instructions) that virtualization may hinder.  
  - Have strict licensing or compliance that forbids virtualization.  
  - The workload is a monolithic, stateful app where the overhead of a VM/container isn’t justified.

**OP17** – UPS vs. generator & ATS  

- **UPS (Uninterruptible Power Supply):** Provides instantaneous battery power (typically seconds to minutes) to bridge the gap between power loss and generator start‑up; also conditions power (surge protection, voltage regulation).  
- **Generator:** Produces AC power from fuel (diesel, natural gas) for extended outages (minutes to days).  
- **Why both needed:** UPS handles the immediate loss and provides clean power while the generator ramps up; generator supplies sustained power for long outages.  
- **ATS (Automatic Transfer Switch):** Detects loss of utility power, signals the generator to start, and automatically transfers load from utility to generator (and back when utility returns). Prevents manual switching and ensures seamless transition.

**OP18** – Active‑passive vs. active‑active clustering (Linux + PostgreSQL via Pacemaker/Corosync)  

- **Active‑passive:** One node runs the PostgreSQL primary; the other is a hot standby (receives WAL via streaming replication) but does not accept writes. On failure, Pacemaker promotes the standby to primary, moves the virtual IP (VIP), and fences the failed node.  
- **Active‑active:** Both nodes can accept writes (requires multi‑master or shared‑storage solution); more complex due to conflict handling. Rarely used for PostgreSQL without extensions like BDR or Citus.  

**Implementation (active‑passive):**  
1. Install Corosync & Pacemaker on both nodes.  
2. Configure shared storage (e.g., DRBD, iSCSI LUN, or Ceph RBD) for PostgreSQL data directory.  
3. Create a primitive resource: `ocf:heartbeat:pgsql` (or `systemd:postgresql`) with `meta is-managed=true`.  
4. Add a clone or master/slave resource for replication if using streaming replication; otherwise rely on shared storage.  
5. Configure a virtual IP resource (`ocf:heartbeat:IPaddr2`) that follows the master.  
6. Set fencing (STONITH) using IPMI/iLO or APC PDU.  
7. Define constraints: the VIP must run on the same node as the PostgreSQL master.  
8. Enable `property stonith-enabled=true` and `no-quorum-policy=ignore` (if only two nodes, use a quorum device).  
9. On node failure, Corosync detects loss, Pacemaker fences the failed node, promotes the standby, moves VIP, and clients reconnect via the VIP.

**OP19** – Backup & recovery strategy for 50‑server on‑prem environment  

- **3‑2‑1 rule:** Keep at least 3 copies of data, on 2 different media, with 1 copy off‑site.  
- **RPO/RTO:** Define per‑application (e.g., critical DB: RPO = 15 min, RTO = 30 min; file servers: RPO = 4 h, RTO = 4 h).  
- **Backup types:**  
  - **Full:** Baseline copy (weekly).  
  - **Incremental:** Changes since last backup (daily).  
  - **Differential:** Changes since last full (daily, larger than incremental but simpler restore).  
- **Deduplication:** Use source‑ or target‑based dedup to reduce storage (e.g., Veeam, Dell EMC Data Domain).  
- **Media:**  
  - **Disk:** Fast restore, suitable for recent backups (NAS/SAN with snapshots).  
  - **Tape:** Cost‑effective for long‑term archival, offline, air‑gap.  
  - **Cloud offsite:** Immutable object storage (AWS S3 Object Lock, Azure Immutable Blob) for off‑site copy.  
- **Immutable backups:** Enable WORM (Write Once Read Many) or object‑lock to protect against ransomware; ensures backups cannot be altered or deleted within retention period.  
- **Testing restores:** Schedule regular restore drills (e.g., monthly) – verify backup integrity, test application recovery, measure actual RTO.  
- **Difference between backup and disaster recovery:**  
  - **Backup:** Copy of data for point‑in‑time recovery; focuses on data loss prevention.  
  - **Disaster Recovery (DR):** Broader plan covering how to resume IT operations after a catastrophic site loss – includes failover infrastructure, network, power, and procedures, not just data restoration.

**OP20** – 802.1X port‑based network access control  

- **Components:**  
  - **Supplicant:** Client software (e.g., Windows, wpa_supplicant) that initiates authentication.  
  - **Authenticator:** Network switch or AP that blocks/unblocks the port based on authentication result.  
  - **Authentication Server:** RADIUS server (e.g., FreeRADIUS, Microsoft NPS) that validates credentials.  
- **Process:**  
  1. Port starts in **unauthorized** state (only EAPOL allowed).  
  2. Supplicant sends EAP‑Start → Authenticator forwards to RADIUS as Access‑Request.  
  3. RADIUS verifies credentials (via EAP method) and replies Access‑Accept/Reject.  
  4. Authenticator sets port to **authorized** (or keeps unauthorized) and allows normal traffic.  
- **EAP methods:**  
  - **EAP‑TLS:** Mutual certificate‑based auth; strongest, requires client and server certs.  
  - **PEAP:** Server‑side cert, client authenticates via MS‑CHAPv2 inside TLS tunnel; common for password‑based auth.  
- **Dynamic VLAN assignment:** RADIUS can return a `Tunnel-Private-Group-ID` attribute; the switch places the port in that VLAN after successful auth.  
- **Failed authentication:** Port remains unauthorized; only EAPOL traffic allowed; client may retry or be placed in a guest VLAN if configured.  
- **MAB (MAC Authentication Bypass):** For devices that can’t run 802.1X (printers, IP phones), the switch treats the MAC address as username/password and sends an Access‑Request to RADIUS. If MAC is allowed, port is authorized; otherwise remains unauthorized or placed in a restricted VLAN.  
- **Security considerations:** Ensure RADIUS shared secret is strong, use server certificates to prevent rogue RADIUS, and enable MAC address lockdown or port security to mitigate MAC spoofing.
