
**CL1** – IaaS provides raw compute, storage, and networking (you manage OS, middleware, apps). Example: AWS EC2.  
PaaS offers a managed platform for developing, running, and scaling apps (you manage code and data). Example: Azure App Service.  
SaaS delivers fully managed applications over the internet (you only configure usage). Example: Microsoft 365.

**CL2** – Shared Responsibility Model splits security duties:  
- **IaaS VMs** – Provider secures hypervisor, physical host, network; you secure OS, patches, apps, data, IAM.  
- **Managed Kubernetes** – Provider secures control plane, underlying nodes, and node OS; you secure cluster configuration, workloads, images, RBAC, secrets.  
- **SaaS (M365)** – Provider secures everything except your data and user access; you manage identity, data classification, device compliance, and configuration of tenant settings.

**CL3** –  
- **VPC** – Isolated virtual network (CIDR) that you create.  
- **Subnet** – Sub‑range of a VPC CIDR; lives in a single AZ; resources attach to it.  
- **Security Group** – Stateful firewall attached to ENIs (instance‑level); allows/denies traffic; return traffic automatically allowed.  
- **NACL** – Stateless subnet‑level firewall; evaluates inbound and outbound rules separately; numbered rule order matters.  
Layering: Traffic first hits NACL (stateless), then Security Group (stateful) before reaching the instance. Stateful means the firewall tracks connection state and allows reply packets; stateless treats each packet independently.

**CL4** – Landing zone: a pre‑built, secure, multi‑account foundation (OU structure, baseline policies, networking, logging). Organizational Units (OUs) group accounts by function (e.g., prod, dev, security). Guardrails are SCPs (AWS) or Policy definitions (Azure) that enforce compliance (e.g., deny public S3, require encryption). Shared networking uses Transit Gateway (AWS) or Azure Hub‑and‑Spoke to interconnect VPCs/VNets centrally, reducing mesh complexity. Centralized logging aggregates CloudTrail/Audit logs, VPC Flow Logs, and Azure Monitor into a single SIEM/log store. Single‑account approach is problematic because it blasts blast radius, complicates least‑privilege IAM, makes cost allocation hard, and hinders blast‑radius containment and regulatory separation.

**CL5** – IaC: managing infrastructure via declarative/imperative code.  
- **Terraform/OpenTofu** – Cloud‑agnostic, state‑based, HCL; great for multi‑cloud and complex dependencies.  
- **Pulumi** – Uses general‑purpose languages (TS, Python, Go); good when you want programming constructs and existing SDKs.  
- **CloudFormation (AWS) / Bicep (Azure)** – Native, tightly integrated, no state file; best for single‑cloud, deep service support.  
- **Crossplane** – Extends Kubernetes to provision cloud resources via CRDs; ideal when you already run workloads on K8s and want a unified control plane.  
Choose Terraform for multi‑cloud or community modules; Pulumi for developer‑friendly code; CloudFormation/Bicep for pure‑cloud native simplicity; Crossplane for GitOps‑driven, K8s‑centric provisioning.

**CL6** –  
- **HPA** – Scales pod replicas based on CPU/memory or custom metrics.  
- **VPA** – Adjusts pod resource requests/limits (vertical scaling) while keeping replica count stable.  
- **Cluster Autoscaler** – Adds/removes worker nodes to accommodate pod scheduling needs.  
- **KEDA** – Event‑driven autoscaling (e.g., queue length, HTTP traffic, cron) that works alongside HPA; scales to zero when no events.  
Use KEDA when scaling is triggered by external events (queues, streams, HTTP) rather than resource utilization, or when you need to scale to zero for cost savings.

**CL7** – DR design: Define RPO (max data loss) and RTO (max downtime).  
- **Active‑Active** – Both regions serve traffic; data replicated synchronously (or near‑sync) for zero RPO; higher cost.  
- **Active‑Passive** – Primary region serves; standby region warmed up; async replication; lower cost, higher RTO.  
Database replication: Sync (e.g., Aurora Global Database with low‑latency commit) for zero RPO; Async (standard read replica) for acceptable RPO. DNS failover via Route 53 health checks or Azure Traffic Manager with latency‑based routing. State management: keep application state externalized (e.g., DynamoDB, Cosmos DB) or use distributed caches. Cost: active‑active doubles compute/storage; pilot light runs minimal services (just DB and DNS); warm standby runs a scaled‑down version; multi‑site active‑active runs full prod in both regions.  
- **Pilot Light** – Core services (DB, DNS) running; can quickly scale out.  
- **Warm Standby** – Reduced‑scale version of app running; can scale up fast.  
- **Multi‑Site Active‑Active** – Full capacity in both regions; traffic split.

**CL8** – GitOps: declarative state stored in Git; operators continuously reconcile cluster to match Git.  
- **ArgoCD** – UI‑rich, supports multiple clusters, sync waves, health assessments.  
- **FluxCD** – CNCF‑graduated, lightweight, uses Kustomize/Helm controllers; integrates with Flux v2 source controller.  
Secrets: Sealed Secrets (encrypt secret → sealed secret stored in Git, decrypted by controller), External Secrets Operator (fetches from Vault/AWS Secrets Manager), or Vault Agent sidecar.  
Drift: If someone makes a manual change, the operator detects divergence on next reconciliation and either reverts (if sync policy set to auto) or alerts; manual changes are overwritten unless excluded via ignore rules.

**CL9** – Stateful legacy app on K8s:  
- Use **StatefulSet** for stable network IDs and ordered pod startup/termination.  
- Define a **Local PV** (node‑affinitied) with a **StorageClass** that provisions hostPath or local‑persistent‑volume; bind via **PVC** with `volumeBindingMode: WaitForFirstConsumer`.  
- **Headless Service** (`clusterIP: None`) gives each pod a DNS `<pod-name>.<svc>.<namespace>.svc.cluster.local`.  
- **Init Containers** to copy config files into the PV or perform schema migrations before app starts.  
- **ConfigMap** mounted as volume (or env) for non‑secret config; update triggers pod restart via rollout strategy.  
- **PodDisruptionBudget** (e.g., `minAvailable: 2`) to protect against voluntary evictions.  
- Set `terminationGracePeriodSeconds` for orderly shutdown; use `preStop` hook to flush data.

**CL10** –  
- **Service Account** – K8s identity for pods; used for RBAC inside cluster.  
- **Workload Identity** – Cloud‑provider identity attached to a workload (e.g., Azure Workload Identity, AWS IAM Roles for Service Accounts).  
- **IRSA** – AWS feature that binds an IAM role to a K8s service account via OIDC federation; pods assume the role via token projection.  
Mounting raw credentials (access keys) in a pod is bad because they’re exposed to any container in the pod, can be leaked via logs/images, and are hard to rotate. Workload Identity Federation uses short‑lived tokens issued by the cloud provider’s OIDC endpoint, eliminating long‑lived secrets and enabling least‑privilege, auditable access.

**CL11** –  
- **Object Storage (S3/Blob)** – Stores unstructured data as objects; high durability (11‑9’s), eventual consistency (now strong read-after-write for PUTS); ideal for backups, media, logs, static sites.  
- **Block Storage (EBS/Managed Disk)** – Raw block volumes attached to VMs; low‑latency IOPS; durability via replication within AZ; used for databases, OS disks.  
- **File Storage (EFS/Azure Files)** – Network file system (NFS/SMB) shared across many instances; durability similar to object; used for shared configs, home dirs, lift‑and‑shift apps requiring POSIX.  
Durability/Availability: S3/Blob 99.999999999% (11‑9) durability, 99.99% availability; EBS 99.8‑99.9% AZ‑level durability; EFS 99.99% durability, 99.9% availability.

**CL12** – Zero‑Trust K8s:  
- **Network Policies** – Whitelist ingress/egress per namespace; default deny.  
- **Service Mesh (Istio/Linkerd)** – mTLS between pods, fine‑grained authz, telemetry.  
- **Pod Identity** – Workload identity or service account token projection to avoid cloud creds in pods.  
- **Admission Controllers** – OPA/Gatekeeper or Kyverno enforce policies (image source, privileged containers, hostPath).  
- **Image Signing & Verification** – Cosign or Notary; admission controller blocks unsigned images.  
- **Runtime Security** – Falco detects anomalous syscalls (e.g., spawning shell, reading /etc/shadow).  
- **Secrets Management** – External Secrets Operator or Vault Agent; secrets never at rest in etcd unencrypted (enable encryption at rest).  
Differs from perimeter model: trust is never assumed based on network location; every request is authenticated, authorized, and encrypted; micro‑segmentation replaces VLAN/firewall zones.

**CL13** – CDN caches static/content at edge POPs; requests routed to nearest node; reduces latency and origin load. Cloud‑native: Amazon CloudFront, Azure Front Door (or Azure CDN). Use CDN for globally distributed static assets, video streaming, API acceleration; serve directly from origin when latency is low (same region) or when you need full control over caching headers and dynamic content.

**CL14** – **Region** – Geographically isolated area with multiple AZs (e.g., us‑east‑1). **Availability Zone** – One or more discrete data centers with independent power, cooling, networking within a region. Deploy across AZs for fault tolerance (AZ‑level outage). **Zonal resources** (e.g., EC2 instance, zonal EBS) are tied to a single AZ; **regional resources** (e.g., S3, DynamoDB, regional VPC) span AZs and survive AZ failure.

**CL15** – Managed DB (RDS, Cloud SQL, Azure SQL) – Provider handles provisioning, patching, backups, HA, scaling, monitoring, and failover. You manage schema, queries, indexing, application‑level tuning, and access control. Running DB on VM you’d do all OS patching, storage management, replication setup, backups, and HA yourself.

**CL16** – Cloud IAM: **Users** (individual identities), **Groups** (collection of users), **Roles** (set of permissions assumable by users/services), **Policies** (JSON documents defining allow/deny actions). Principle of Least Privilege: grant only the permissions needed for a specific task. Apply by: start with deny‑all, add fine‑grained policies per role/group, use policy simulation, regularly review unused permissions, enforce via SCPs or Azure Policy.

**CL17** – Serverless: run code in response to events without managing servers. AWS Lambda, Azure Functions, Google Cloud Functions. **Cold start** – latency incurred when a new execution environment is spun up (container init, runtime load). Matters for latency‑sensitive sync calls; mitigated by provisioned concurrency, keep‑warm triggers, or choosing languages with fast init. Poor fit for long‑running, high‑CPU, or stateful workloads needing persistent connections or GPUs.

**CL18** – Ingress options:  
- **Ingress Resource** – Simple HTTP(S) routing via Ingress controller (NGINX, Traefik); TLS termination at controller.  
- **Gateway API** – More expressive, role‑based (GatewayClass, Gateway, HTTPRoute); supports multiple protocols, better extensibility.  
- **Cloud Load Balancer Annotations** – Provider‑specific LB (AWS ALB, Azure App Gateway) configured via service annotations; TLS terminated at LB.  
- **Service Mesh Ingress Gateway** – Envoy‑based gateway (Istio IngressGateway) does mTLS, traffic mgmt, observability.  
Use Gateway API when you need advanced traffic splitting, multi‑protocol, or want a vendor‑neutral spec; otherwise classic Ingress suffices for simple HTTP.

**CL19** – Cost‑optimization for $80k/mo:  
- **Reserved Instances / Savings Plans** – Commit to 1‑3 yr usage for steady baseline workloads (up to 72% savings).  
- **Spot/Preemptible** – Use for fault‑tolerant batch, CI, stateless workers (up to 90% savings).  
- **Right‑sizing** – Use CloudWatch/Azure Monitor metrics, Trusted Advisor, or third‑party tools (Cloudability, Harness) to downsize over‑provisioned instances.  
- **Storage Tiering** – Move infrequent data to S3 Intelligent‑Tiering → Glacier Deep Archive; Azure Cool/Archive tiers.  
- **Idle Detection** – Tag resources, use AWS Lambda/Azure Functions to stop dev environments after hours, schedule autoscaling groups to zero.  
- **FinOps** – Establish cost centers, showback/chargeback dashboards (AWS Cost Explorer + Tags, Azure Cost Management), set budgets alerts, conduct weekly reviews.  
- **Tools** – AWS Cost Explorer, Azure Cost Management, CloudHealth, Kubecost (for K8s), Terraform Sentinel/OPA for policy‑as‑code cost guards.  
Process: tagging strategy, automated budget alerts, monthly review meetings, rightsizing pipelines, spot‑instance interruption handling.

**CL20** – Multi‑cloud design to avoid lock‑in:  
- **Abstraction Layer** – Use Kubernetes as common runtime; package apps via Helm charts; keep cloud‑specific configs in values files.  
- **IaC Portability** – Terraform (or OpenTofu) with providers for AWS & Azure; keep modules cloud‑agnostic where possible.  
- **Networking** – Site‑to‑site VPN or Azure ExpressRoute/AWS Direct Connect + Transit Gateway/VPC peering to interconnect VPCs/VNets; use Cloud‑agnostic service mesh (Istio) for cross‑cluster traffic.  
- **Identity Federation** – Deploy Azure AD / AWS IAM Identity Center with SAML/OIDC federation; workloads use OIDC tokens to assume cloud roles via workload identity.  
- **Trade‑offs** – Increased operational overhead (dual‑skill set, duplicated networking, inconsistent service features), potential latency, higher cost for data transfer, complexity in compliance.  
- **Justified** when regulatory, risk‑mitigation, or negotiating leverage demands true vendor independence, or when you need best‑of‑breed services (e.g., AWS ML + Azure SAP).  
- **Unnecessary** when workloads are homogeneous, you can achieve portability via containers/K8s alone, or the added complexity outweighs lock‑in risk.

**OT1** – Purdue Model (ISA‑95) levels:  
0 – **Process Control** (sensors, actuators, PLC I/O).  
1 – **Basic Process Control** (PLC/DCS control loops).  
2 – **Supervisory Control** (SCADA/HMI, historian).  
3 – **Manufacturing Operations** (MES, production scheduling).  
4 – **Business Planning & Logistics** (ERP, supply chain).  
5 – **Enterprise** (corporate network, email, internet).

**OT2** – IT networks are business‑focused, frequently patched; OT networks prioritize availability, deterministic timing, and legacy equipment. Patching can cause downtime, break real‑time loops, or require recertification; many OT devices lack patch mechanisms or have long validation cycles.

**OT3** – Industrial DMZ (IDMZ) sits between IT (Level 4) and OT (Levels 0‑3). Allowed traffic: narrowly defined protocols (e.g., OPC UA read‑only, historian data push) from OT→IT for monitoring; IT→OT only for authenticated management (e.g., firmware updates) via jump host. Direct Level 4→Level 1 is dangerous because it bypasses security controls, exposing real‑time controllers to IT threats (malware, ransomware) that could disrupt safety‑critical processes.

**OT4** –  
1. **Modbus TCP** – Simple request/response; Level 1‑2 (PLC/RTU to SCADA).  
2. **OPC UA** – Service‑oriented, secure; Level 2‑3 (SCADA, MES, historian).  
3. **EtherNet/IP (CIP)** – Real‑time I/O; Level 1‑2 (PLC to I/O devices, drives).  
4. **PROFINET** – Ethernet‑based, real‑time; Level 1‑2 (PLC/I/O, drives).  
5. **MQTT** – Lightweight publish/subscribe; Level 2‑3 (edge gateway to cloud/ historian) for telemetry.

**OT5** – Data diode: hardware enforces one‑way flow (e.g., OT→IT) using optical isolation; cannot be bypassed by software. Use when you need guaranteed no‑inbound path (e.g., sending sensor data to corporate analytics). Limitation: no bidirectional communication, so you cannot receive commands or acknowledgments; must rely on out‑of‑band mechanisms for control.

**OT6** – Data flow: PLC/RTU → Local Historian (Level 2) → OPC UA Server (Level 2) → MQTT Broker on Edge Gateway (Level 3) → Secure TLS → Cloud Ingestion (e.g., IoT Hub, Kinesis). Security boundaries: OT LAN → IDMZ (firewall allowing only OPC UA/MQTT out) → Cloud VPC (ingress only via private endpoint or VPN). No inbound from cloud to OT except via authenticated, limited‑scope reverse tunnel if needed.

**OT7** – IEC 62443 zones: logical grouping of assets with similar security requirements; conduits are the communication paths between zones.  
Design example:  
- **Zone 0** – Corporate IT (Levels 4‑5).  
- **Zone 1** – Engineering Workstations (Level 3).  
- **Zone 2** – SCADA Servers & Historian (Level 3).  
- **Zone 3** – PLCs & Safety Instrumented Systems (Levels 0‑2).  
Conduits:  
- IT↔Engineering (controlled via jump host, MFA).  
- Engineering↔SCADA (OPC UA, authenticated).  
- SCADA↔PLC/SIS (Modbus TCP/OPC UA, whitelisted, possibly via data diode for safety‑critical).  
SIS often placed in its own sub‑zone with air‑gap or strict conduit to BPCS.

**OT8** – Segmentation strategy:  
- **VLANs**: VLAN 10 Corporate IT, VLAN 20 Engineering, VLAN 30 SCADA/Historian, VLAN 40 PLC Line 1, VLAN 41 Line 2, VLAN 42 Line 3, VLAN 43 Line 4, VLAN 50 Safety‑Instrumented (SIS).  
- **Firewalls**: Place next‑gen firewalls between each VLAN pair (or use VRFs/L3 switches with ACLs). Enforce east‑west policies: only required protocols (OPC UA, Modbus) allowed.  
- **Switch Architecture**: Layer‑3 core switch with VLAN routing; access switches per line; enable port security, 802.1X where possible.  
- **Remote Access**: VPN terminates at IDMZ firewall; jump host with MFA; no direct vendor VPN to PLC VLAN.  
- **Transition**: Use phased cut‑over – duplicate VLANs, run parallel traffic, validate, then migrate devices during maintenance windows; use network taps for visibility.

**OT9** – SIS executes safety‑instrumented functions (SIF) to bring process to safe state on fault; BPCS handles normal control. IEC 61511 defines safety lifecycle for SIS in process industry. SIS network must be isolated/air‑gapped because any compromise could prevent safety shutdown, leading to catastrophic release. Ransomware reaching SIS could block safety logic, inhibit emergency shutdown, or cause false safe‑state triggers, risking injury, environmental damage, or production loss.

**OT10** – PLC: programmable logic controller for discrete or process control, rugged, real‑time. DCS: distributed control system, integrates many controllers with centralized supervisory control, used for large continuous processes. SCADA: supervisory layer that aggregates data from multiple PLCs/DCSs, provides HMIs, historian, and alarm management. They can coexist: PLCs/DCSs do low‑level control; SCADA provides plant‑wide visibility and coordination.

**OT11** – Remote access architecture:  
- MFA‑protected VPN terminating at IDMZ.  
- Jump host (bastion) with hardened OS, session recording, limited to admin accounts.  
- Time‑limited, just‑in‑time (JIT) credentials via PAM solution.  
- Vendor access via separate portal with scoped tokens, no direct RDP to HMI.  
Direct RDP from corporate to HMI is unacceptable because it bypasses segmentation, exposes HMI to IT threats, and lacks audit/tamper protection.

**OT12** – Detection & Response for compromised vendor VPN:  
- **Network Monitoring**: Deploy IDS/IPS (e.g., Snort, Zeek) and passive NetFlow/IPFIX sensors at Level 3 ingress/egress; look for anomalous SMB, unusual internal scans, beaconing to C2.  
- **Asset Inventory**: Maintain CMDB of all Level 3 devices; use passive scanning to detect new or changed MAC/IP.  
- **IR Steps**: 1) Isolate affected VPN segment at firewall; 2) Collect volatile memory from jump host; 3) Preserve logs (VPN, firewall, IDS); 4) Notify control room; 5) If SIS potentially impacted, initiate safe‑shutdown procedures per SIS safety manual; 6) Remediate (patch VPN, rotate credentials, re‑image jump host).  
- **Operator Role**: Confirm process state, execute manual overrides if needed, communicate status to response team, avoid actions that could interfere with containment.  
- **Safe Operations**: Keep SIS in its isolated zone; if any indication of SIS reach, trigger manual safety shutdown before attempting network containment.

**OT13** – HMI: graphical interface for operators to visualize process data, issue commands, acknowledge alarms. Differs from engineering workstation which is used for configuration, programming, and diagnostics; HMIs are runtime‑focused, often read‑only for safety‑critical commands.

**OT14** – Historian: time‑series database that compresses and stores process data for trending, reporting, and analysis. Plant Historian (Level 3) stores high‑resolution data from local controllers; Enterprise Historian (Level 4) aggregates data from multiple plants/sites for corporate KPIs, often with lower resolution and longer retention.

**OT15** – Ladder Logic: graphical programming language resembling electrical relay diagrams; executed by PLCs (or soft‑PLCs). Remains dominant due to intuitiveness for electricians, deterministic execution, wide tool support, and legacy code base.

**OT16** – RTU: Remote Terminal Unit, ruggedized, often used for wide‑area telemetry (SCADA over radio, cellular, satellite); typically has built‑in communication protocols and limited local logic. PLC is more suited for localized, high‑speed I/O and complex logic. Deploy RTUs in pipelines, water distribution, oil/gas fields where devices are far apart and communication bandwidth is limited.

**OT17** – Analog signals: continuous current/voltage (4‑20 mA, 0‑10 V) representing process variables; digital signals are discrete on/off (e.g., limit switch). 4‑20 mA preferred because live zero (4 mA) allows detection of wire break (0 mA) vs signal; provides power to loop devices and better noise immunity.

**OT18** – OT asset inventory foundation: knowing what exists enables vulnerability management, segmentation, and monitoring. Techniques: passive network monitoring (port‑mirroring, NetFlow, protocol decoders) to see traffic without impact; active scanning (SNMP, ICMP, ARP) can discover but may cause traffic storms or trigger safety interlocks, so used sparingly during maintenance windows. Combine with manual walk‑downs and vendor documentation.

**OT19** – MITRE ATT&CK for ICS tactics (examples):  
1. **Initial Access** – Exploit public‑facing application (e.g., vulnerable HMI web interface).  
2. **Execution** – Command‑line interface via SSH on engineering workstation.  
3. **Persistence** – Modify startup scripts on PLC (e.g., add malicious ladder logic).  
4. **Privilege Escalation** – Abuse Windows service running as SYSTEM on SCADA server.  
5. **Defense Evasion** – Obfuscate malicious files using alternate data streams.  
6. **Credential Access** – Harvest credentials from memory dump of historian server.  
7. **Discovery** – Network sniffing of Modbus traffic to map topology.  
8. **Lateral Movement** – Use legitimate remote administration tools (RDP) to jump from IT to OT.  
9. **Collection** – Archive historian data via scheduled transfer.  
10. **Exfiltration** – Exfiltrate stolen IP via DNS tunneling.  
Differs from enterprise ATT&CK by focusing on OT‑specific protocols, safety systems, and impact on physical processes. Use it to map existing controls, identify gaps (e.g., lack of authentication on Modbus), and prioritize mitigations.

**OT20** – Converged IT/OT SOC design:  
- **Log Collection**: Deploy lightweight agents (e.g., OSSEC, Wazuh) on engineering workstations; use syslog forwarders from historians, firewalls, IDS; employ edge gateways to pull OPC UA/MQTT metrics via MQTT bridge; ensure collection does not introduce latency (use UDP/TCP with rate limiting).  
- **SIEM Integration**: Forward normalized logs to central SIEM (Splunk, Azure Sentinel, QRadar) via secure channel; tag with OT asset IDs.  
- **Detection Rules**: Create OT‑specific signatures (e.g., unexpected Modbus function code, ladder logic change, unauthorized firmware version, spikes in process variables).  
- **Triage Workflow**: Tier 1 analysts filter noise; Tier 2 OT engineers validate impact on process; Tier 3 incident response leads containment.  
- **Staffing**: Blend – SOC analysts for IT telemetry, OT engineers for process knowledge; cross‑train on each other’s domains.  
- **False Positives**: Baseline normal process behavior; use anomaly detection with thresholds tuned to process dynamics; employ whitelisting of known maintenance windows.  
- **Unauthorized Firmware Change Alert**: 1) Verify hash against approved baseline; 2) If confirmed, isolate affected PLC via network policy or physical disconnect; 3) Initiate safe‑state procedure per SIS if safety‑critical; 4) Forensic capture of firmware image; 5) Notify vendor, apply patch, re‑image PLC from trusted source; 6) Update inventory and change‑management records.
