
**Kubernetes**

**K1** – A **Deployment** manages stateless replicas; it creates identical Pods, can scale up/down, and uses rolling updates. A **StatefulSet** manages stateful workloads, giving each Pod a stable, unique network identity (`<name>-<ordinal>`) and stable persistent storage via volumeClaimTemplates; it enforces ordered deployment, scaling, and deletion.

**K2** – A `ClusterIP` Service gets a virtual IP inside the cluster’s service CIDR. kube‑proxy (via iptables or IPVS) installs rules that DNAT traffic destined for that IP:port to the set of endpoint IPs (the Pods). The packet is then routed normally to the node hosting the selected endpoint.

**K3** – **PersistentVolume (PV)** is a cluster‑wide storage resource (e.g., NFS disk) provisioned by an admin. **PersistentVolumeClaim (PVC)** is a user’s request for storage (size, access modes). A **StorageClass** defines a class of storage (provisioner, parameters, reclaimPolicy) enabling dynamic provisioning; when a PVC references a StorageClass, the control plane automatically creates a matching PV.

**K4** – Troubleshooting CrashLoopBackOff (≥4 checks):
1. `kubectl logs <pod>` – see why the container exits.
2. `kubectl describe pod <pod>` – check events, restarts, image pull errors, OOMKilled.
3. Verify the container’s entrypoint/command and required config/files exist (ConfigMap/Secret mounts).
4. Check resource limits (OOM) via `kubectl top pod` or node metrics.
5. (Optional) Run the image locally with same command to reproduce.

**K5** – CoreDNS provides cluster‑internal DNS service (A/AAAA/SRV records for Services, Pods, etc.). If all CoreDNS pods are down, internal name resolution fails; external resolution may still work if nodes have `/etc/resolv.conf` pointing to external DNS, but service discovery (`<svc>.<ns>.svc.cluster.local`) will not resolve.

**K6** – Scheduler process:
1. **Filtering** – eliminate nodes that fail hard constraints (node affinity, taints, pod‑node resource requests, volume zones, pod‑tolerations, etc.).
2. **Scoring** – each remaining node gets a score based on soft constraints; factors include:
   - **Resource availability** (CPU/Memory free – favors nodes with more free resources).
   - **Node affinity/anti‑affinity scores** (preferred scheduling).
   - **Inter‑pod affinity/anti‑affinity** (spread or co‑locate pods).
   - **Image locality** (prefer nodes already having the container image layers).
   - **Taint tolerance** (nodes with fewer taints preferred).
3. The node with the highest total score is chosen.

**K7** – Requests: 256 Mi, Limits: 512 Mi. Node has 4 GiB RAM, 3.5 GiB already requested → free = 512 Mi. The pod’s request (256 Mi) fits, so it **will be scheduled**. At runtime, if the container tries to use 600 Mi (> limit), the kubelet will **OOM‑kill** the container (since it exceeds the limit) and restart it according to the restart policy.

**K8** – Request flow (NGINX Ingress Controller):
1. Client → external Load Balancer (cloud LB or bare‑metal) → LB forwards to node’s port (usually 80/443) where the NGINX ingress controller Pod runs (via Service type LoadBalancer/NodePort).
2. NGINX receives HTTP request, matches host/path to an **Ingress** rule.
3. NGINX looks up the corresponding **Service** (ClusterIP) defined in the Ingress backend.
4. NGINX performs **service lookup** via Kubernetes API (or its internal cache) to get the Service’s ClusterIP and port.
5. NGINX uses **kube‑proxy/iptables** (or IPVS) on the node to translate the ClusterIP:port to one of the Service’s **Endpoints** (Pod IPs).
6. Packet is sent to the selected Pod; the Pod’s container processes the request and returns the response back through the same path.

**K9** – A **NetworkPolicy** defines ingress/egress rules for Pods selected by `podSelector`. If no NetworkPolicy exists in a namespace, traffic is **unrestricted** (allow all). Applying a policy that selects certain pods isolates them: only traffic matching the policy’s `ingress`/`egress` rules is allowed; all other traffic to/from those pods is dropped.

**K10** – **RollingUpdate** creates a new ReplicaSet with the updated template, gradually replaces old Pods (maxSurge/maxUnavailable). **Recreate** kills all existing Pods before creating new ones (downtime). Choose Recreate when the application cannot run multiple versions simultaneously (e.g., requires exclusive access to a shared resource, or needs a clean DB schema migration that can’t tolerate mixed versions).

**K11** – A **Namespace** is a logical partition for cluster resources, providing scope for names and enabling RBAC/resource quotas. Default namespaces in a fresh cluster: `default`, `kube-system` (control‑plane components), `kube-public` (read‑only for all users, e.g., cluster info), `kube-node-lease` (node heartbeats).

**K12** – `kubectl describe pod <name>` shows:
1. **Events** (scheduling, image pull, container start failures).
2. **Containers’ state** (ready, restart count, last termination reason).
3. **Mounted volumes** (ConfigMap/Secret/PV details, paths).
4. **Node** the pod is running on, **QoS class**, **tolerations**, **labels/annotations** (not in `kubectl get pod`).

**K13** – A **ConfigMap** holds key‑value data. Pods can consume it:
1. As **environment variables** (`envFrom` or `env.valueFrom.configMapKeyRef`).
2. As **files** mounted into a volume (`volumes.configMap` → `volumeMounts`).

**K14** – 
- **ClusterIP**: internal virtual IP, only reachable inside the cluster.
- **NodePort**: same as ClusterIP plus a static port on each node’s IP (`<NodeIP>:<NodePort>`) that forwards to the service.
- **LoadBalancer**: provisions an external cloud LB (or metal LB) that forwards to the NodePort/ClusterIP; provides a single external IP.

**K15** – A **DaemonSet** ensures a copy of a Pod runs on **every** (or selected) node. Use when you need a node‑level agent: log collectors (fluentd), node monitors (Prometheus node‑exporter), CNI plugins, or kube‑proxy.

**K16** – 
- **Taints** are applied to nodes; they repel pods unless the pod has a matching **toleration**. 
- **Tolerations** are set on pods to allow them to schedule on tainted nodes. 
- **Node affinity** (required/preferred) attracts pods to nodes with specific labels; it’s a soft/hard preference, not a repellent. 
*Use case*: Taint a node with `dedicated=gpu:NoSchedule` and tolerate only GPU‑needing pods → reserve GPU nodes. Use node affinity to schedule a caching pod on nodes with `ssd=true` for better performance.

**K17** – An **Operator** is a Kubernetes controller that extends the API with custom resources (CRDs) to manage complex stateful applications (e.g., databases, caches). Unlike a generic controller that watches built‑in kinds, an Operator encodes domain‑specific operational knowledge (backup, upgrade, scaling, failure detection) in the controller logic. It solves the problem of automating lifecycle tasks that would otherwise require manual scripts or Helm hooks.

**K18** – etcd uses the **Raft consensus algorithm**, providing **strong consistency** (linearizable reads/writes) as long as a majority (quorum) of nodes are healthy. If quorum is lost (< ½ + 1 nodes), the cluster cannot commit new changes; reads may still succeed if configured for stale reads, but writes are blocked.  
If 2 of 3 etcd nodes are permanently lost, you have no quorum. Recovery steps:
1. Stop the API server and controller manager.
2. Etcd: create a new single‑node cluster from the remaining good node’s data (`etcdctl snapshot restore`).
3. Update the cluster’s initial cluster list to include only the restored node.
4. Start etcd, then restart API server, scheduler, controller manager.
5. Re‑add new etcd members to regain a 3‑node quorum, using `etcdctl member add`.

**K19** – RBAC basics: 
- **Role** / **ClusterRole** define a set of rules (apiGroups, resources, verbs). 
- **RoleBinding** binds a Role to users/groups/serviceAccounts **within a namespace**. 
- **ClusterRoleBinding** binds a ClusterRole **cluster‑wide** (or to a namespace via `subjects.namespace`).  

*Read‑only access to pods and logs in namespace `dev`*:

```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-log-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list", "watch"]

# RoleBinding (bind to a user, e.g., alice)
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-log-binding
  namespace: dev
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-log-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** – In `/etc/resolv.conf`, `ndots:X` tells the resolver to treat a name with ≥ X dots as absolute and try it first; otherwise it appends search domains. A low `ndots` (default 5) causes many single‑label names (e.g., `mongodb`) to be queried as `mongodb.<search>.`, `mongodb.<search2>.`, etc., generating extra DNS traffic and latency.  
Fix: set a higher `ndots` in the pod’s `dnsConfig` so the resolver treats the name as absolute sooner, or provide a proper search list. Example:

```yaml
dnsConfig:
  ndots: 5   # or 1 if you want to avoid search suffixes entirely
  searches: ["my.svc.cluster.local"]  # optional, limit search domains
```

**Development**

**D1** – `git merge` creates a new merge commit that joins two histories, preserving the exact branch topology. `git rebase` rewrites the committing branch’s commits onto the tip of the target branch, producing a linear history. Avoid rebasing when the branch is public/shared, as it rewrites commits that others may have based work on, causing confusion and requiring force‑pushes.

**D2** – **TCP** is connection‑oriented, reliable, ordered, with flow‑control and retransmission (used by HTTP, SSH). **UDP** is connectionless, best‑effort, no ordering or retransmission (used by DNS queries, VoIP/RTP, streaming media).  

**D3** – A **race condition** occurs when the outcome depends on the timing of uncontrollable events. Example (Go): two goroutines increment a shared variable `cnt++` without synchronization; depending on interleaving, the final value may be 1 instead of 2.

**D4** – **Symmetric encryption** uses the same secret key for both encryption and decryption (fast; e.g., AES). **Asymmetric encryption** uses a key pair (public/private); data encrypted with the public key can only be decrypted with the private key (used for key exchange). In TLS, the client and server perform an asymmetric handshake to exchange a symmetric session key, then use symmetric encryption for bulk data.

**D5** – A **container image layer** is a read‑only filesystem diff created by each Dockerfile instruction (FROM, RUN, COPY, etc.). Layer caching lets Docker reuse unchanged layers when rebuilding, speeding up builds. Best practices: order instructions from least to most frequently changed, combine multiple RUN steps, and use `.dockerignore` to avoid copying unnecessary files.

**D6** – Intermittent 503 (Service Unavailable) checklist (ordered):
1. **Check application logs** for errors, panics, or graceful shutdowns.
2. **Verify backend health** (e.g., DB, cache) – is a dependency returning errors or timing out?
3. **Inspect resource usage** (CPU, memory, file descriptors) – is the host hitting limits causing the app to reject connections?
4. **Look at load‑balancer / reverse proxy** – are health checks marking instances unhealthy?
5. (Optional) Examine recent deployments or config changes that could have introduced a bug.

**D7** – **CAP theorem**: a distributed data store can guarantee at most two of Consistency, Availability, Partition tolerance.  
- **CP example**: **Google Spanner** (or etcd) – sacrifices availability during network partitions to maintain strong consistency.  
- **AP example**: **Apache Cassandra** – remains available and partition‑tolerant, offering tunable consistency (eventual by default).

**D8** – **Horizontal scaling** adds more nodes/instances; **vertical scaling** adds resources (CPU/RAM) to an existing node. Patterns enabling horizontal scaling: stateless services, sharding/partitioning, consistent hashing, load‑balancing, stateless front‑ends, and using shared-nothing architectures.

**D9** – An **environment variable** is a key‑value pair available to a process’s environment. To persist across sessions on Linux, add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `/etc/environment` (for system‑wide), then `source` the file or restart the shell.

**D10** – **JSON** (JavaScript Object Notation) is a lightweight data‑interchange format; maps directly to objects/arrays, widely supported in web APIs. **YAML** (YAML Ain’t Markup Language) is a superset of JSON, emphasizes readability with indentation, supports comments and complex types. Advantage: JSON – simplicity and universal parsing; YAML – human‑friendly configuration (e.g., Kubernetes manifests).

**D11** – A **REST API** uses HTTP methods to perform CRUD on resources identified by URIs.  
- **GET** – retrieve a representation (safe, idempotent).  
- **POST** – create a new subordinate resource (not idempotent).  
- **PUT** – replace an existing resource or create if known URI (idempotent).  
- **DELETE** – remove a resource (idempotent).

**D12** – **Version pinning** locks dependencies to exact versions (e.g., `package==1.2.3` in `requirements.txt` or `package.json`). It ensures reproducible builds by preventing automatic upgrades that could introduce breaking changes or behavior shifts.

**D13** – **Compiled languages** translate source to machine code before execution (e.g., C, Go). **Interpreted languages** are executed line‑by‑line by an interpreter at runtime (e.g., Python, JavaScript). Some languages use both (Java compiled to bytecode, then interpreted/JIT‑compiled).

**D14** – A **reverse proxy** sits in front of servers, accepting client requests and forwarding them to backend services (provides TLS termination, load‑balancing, caching). A **forward proxy** sits between clients and the internet, forwarding client requests outward (used for filtering, anonymity). Common reverse proxies: **NGINX** (load‑balancing, SSL termination) and **Envoy** (service‑mesh sidecar). Use cases: NGINX for serving static sites + proxying to app servers; Envoy for observability and traffic management in microservices.

**D15** – A **deadlock** occurs when two or more processes are each waiting for a resource held by another, forming a circular wait. **Coffman conditions** (all must hold):
1. Mutual exclusion – at least one resource non‑shareable.
2. Hold and wait – processes hold resources while requesting others.
3. No preemption – resources cannot be forcibly taken.
4. Circular wait – a closed chain of processes each waiting for the next’s resource.

**D16** – **Eventual consistency** guarantees that, if no new updates are made, all replicas will converge to the same value after some delay. **Cassandra** achieves read‑after‑write consistency via tunable levels: you can specify a consistency level (e.g., `QUORUM`) for reads and writes; setting read and write levels such that `R + W > N` (where N is replication factor) ensures strong consistency; lower values give eventual consistency. Levels: `ANY`, `ONE`, `TWO`, `THREE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`, `EACH_QUORUM`, `SERIAL`, `LOCAL_SERIAL`.

**D17** – **mTLS** (mutual TLS) requires both client and server to present certificates verified against each other’s trusted CAs. Handshake:
1. Client → Server: `ClientHello` (supported versions, cipher suites).
2. Server → Client: `ServerHello`, certificate, optional `CertificateRequest` (asks for client cert).
3. Client validates server cert, then sends its own certificate (if requested) and a `CertificateVerify`.
4. Both sides exchange `Finished` messages after deriving symmetric keys from the pre‑master secret.
5. Encrypted application data flows.  
mTLS is used for service‑to‑service authentication (Istio, Linkerd), zero‑trust networks, API gateways, and securing etcd or database connections.

**D18** – A **hash table** stores key‑value pairs in an array of buckets; the hash function maps a key to an index. Collisions occur when two keys hash to same bucket.  
- **Chaining**: each bucket holds a linked list (or dynamic array) of entries; lookup walks the list.  
- **Open addressing**: on collision, probe successive slots (linear, quadratic, double hashing) until an empty slot is found.  
Average‑case time: **O(1)** for insert, lookup, delete. Worst‑case (all keys collide): **O(n)** for chaining; for open addressing, worst‑case also **O(n)** (when table is full or probing sequence cycles).

**D19** – **Circuit Breaker** pattern wraps a remote call. States:
- **Closed**: calls pass through; failure count tracked; if failures exceed threshold, transition to **Open**.
- **Open**: calls fail fast (no remote call); after a timeout, move to **Half‑Open**.
- **Half‑Open**: allow a trial call; if success, reset to **Closed**; if failure, go back to **Open**.  
It prevents cascading failures by stopping traffic to a failing service, giving it time to recover. Works well with retry policies: retries are attempted only when the breaker is Closed or Half‑Open; exponential backoff spaces out retries to avoid overwhelming the service.

**D20** – **Optimistic concurrency control (OCC)** assumes conflicts are rare; transactions proceed without locking, and at commit time they check for conflicts (e.g., via row version/timestamp). If a conflict is detected, the transaction aborts and retries. **Pessimistic concurrency control (PCC)** locks resources upfront (e.g., `SELECT FOR UPDATE`) to prevent others from modifying them until the transaction ends.  
Choose OCC for high‑read, low‑write workloads (e.g., caching layers) where aborts are cheap. Choose PCC when conflicts are frequent or when long‑running transactions need strong isolation (e.g., banking transfers).  
Example (PostgreSQL):
- OCC: `UPDATE accounts SET balance = balance - 10 WHERE id = 1 AND version = 5;` then increment version; if no rows updated, retry.
- PCC: `BEGIN; SELECT * FROM accounts WHERE id = 1 FOR UPDATE; UPDATE accounts SET balance = balance - 10 WHERE id = 1; COMMIT;` (locks the row for the transaction duration).
