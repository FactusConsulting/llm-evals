
**AA1** – A monolith bundles all application components (UI, business logic, data access) into a single deployable unit, sharing memory and process space. Microservices split the system into independently deployable services that communicate over the network.  
*Three problems introduced by microservices that monoliths don’t have:*  
1. **Network latency & partial failures** – inter‑service calls add latency and can fail independently.  
2. **Data consistency challenges** – each service owns its data; maintaining ACID transactions across services requires patterns like Sagas.  
3. **Operational overhead** – you must manage service discovery, versioning, monitoring, logging, and deployment pipelines for many services.

**AA2** – *Synchronous* communication blocks the caller until a response is received (request‑reply). Example: HTTP/REST or gRPC call.  
*Asynchronous* communication lets the caller continue immediately; the receiver processes the message later. Example: publishing to a message queue (RabbitMQ) or a log‑based broker (Kafka) and consuming later.

**AA3** – An **API Gateway** is a specialized reverse proxy that adds API‑centric features: request/response transformation, authentication/authorization, rate limiting, throttling, API composition, and analytics. A **reverse proxy** (e.g., NGINX, HAProxy) primarily does load balancing, SSL termination, and simple routing.  
An API Gateway can *replace* a basic reverse proxy for API traffic, but not for all use‑cases: if you need generic TCP/UDP load balancing, L4 routing, or non‑HTTP protocols, a plain reverse proxy (or L4 load balancer) is still required.

**AA4** – The **Saga** pattern breaks a distributed transaction into a sequence of local transactions, each with a compensating action to undo it if later steps fail.  
*Choreography‑based*: services listen to events and trigger the next step or compensating action; no central coordinator. Good for simple workflows with few services and when you want low coupling.  
*Orchestration‑based*: a dedicated orchestrator (workflow engine) tells each service what to do and when to compensate. Preferred for complex, long‑running workflows, strict ordering, or when you need visibility and retry policies.

**AA5** – **CQRS** separates the *write* model (commands) from the *read* model (queries). Reads can be served from denormalized, optimized views while writes go to the authoritative store.  
It is often paired with **Event Sourcing** because events are the immutable source of truth; the read model can be rebuilt by replaying events, guaranteeing eventual consistency between write and read sides.  
Together they solve the *read‑write contention* and *complex querying* problems of a traditional CRUD model: writes stay simple and fast, while reads can be scaled and tailored without affecting write performance.

**AA6** – **Circuit Breaker** has three states:  
1. **Closed** – calls flow normally; failure count is tracked.  
2. **Open** – after a threshold, calls are short‑circuited and fail fast.  
3. **Half‑Open** – after a timeout, a trial call is allowed; success closes the breaker, failure re‑opens it.  
Unlike a simple retry with backoff (which keeps trying the same failing operation), a circuit breaker stops the traffic to give the failing service time to recover. Use both together: retry for transient glitches, circuit breaker to prevent cascading failures when retries would exacerbate the problem.

**AA7** – *Tenant isolation models* (cost, security, ops complexity, noisy‑neighbor risk):

| Model | Cost | Security | Operational Complexity | Noisy‑Neighbor Risk |
|-------|------|----------|------------------------|----------------------|
| **Shared DB, shared schema** (row‑level tenant ID) | Lowest (single DB, minimal storage) | Moderate – relies on correct tenant‑ID filtering; bugs can leak data. | Low – simple schema, backups, migrations. | High – one tenant’s heavy queries can affect others; resource contention. |
| **Shared DB, separate schema per tenant** | Medium (more schemas, slightly more storage) | Higher – schema isolation reduces accidental cross‑tenant access. | Medium – need to manage many schemas (migrations, backups). | Medium – still shares compute/storage; noisy neighbor mitigated by schema‑level quotas but not eliminated. |
| **Separate DB per tenant** | Highest (provisioned per tenant) | Highest – physical/logical isolation; breach limited to one tenant. | Highest – many DB instances to monitor, patch, backup. | Lowest – each tenant gets dedicated resources; noisy neighbor eliminated (subject to host‑level contention). |

**AA8** – *Eventual consistency* allows temporary divergence; reads may see stale data. *Strong consistency* guarantees that after a write, all subsequent reads see that write (linearizability).  
To **never oversell inventory**, you need strong consistency on the inventory count. Architecture:  
- **Consistency model:** Strong (linearizable) writes.  
- **Data store:** A strongly consistent, horizontally scalable store such as Google Cloud Spanner, CockroachDB, or a relational DB with synchronous replication (e.g., PostgreSQL with synchronous standby).  
- **Patterns at scale:** Use the **Transactional Outbox** or **Event Sourcing with a single writer** to ensure inventory updates are atomic; employ **optimistic locking** or **compare‑and‑set** on the stock field; front‑end validates stock before order placement, and the order service decrements stock within the same transaction. For read‑heavy workloads, maintain a **read‑replica** for non‑critical queries but route inventory‑check reads to the primary.

**AA9** – A **sidecar proxy** runs alongside each service instance, handling all inbound/outbound network traffic (observability, security, traffic management). In **Istio**, the sidecar is **Envoy**, which performs L4/L7 filtering, TLS termination, retries, circuit breaking, and telemetry reporting to Istio’s control plane (Pilot, Citadel, Galley).  
- **Data plane:** The collection of Envoy proxies that actually forward traffic.  
- **Control plane:** Istio components that configure the proxies (policy distribution, service discovery, certificate rotation).  
**mTLS between sidecars** encrypts and authenticates service‑to‑service traffic at the infrastructure level, providing zero‑trust mutual authentication without requiring each application to implement TLS. Application‑level TLS only secures the payload; sidecar mTLS also protects metadata (headers, trailers) and enables fine‑grained authorization policies based on service identity.

**AA10** – **Strangler Fig** gradually replaces pieces of a legacy system by routing new functionality to the new system while keeping the old system alive.  
*Migration strategy for .NET Framework → .NET 8 microservices:*  
1. **Facade layer:** Deploy an API Gateway (e.g., Kong, Envoy) in front of the monolith.  
2. **Identify bounded contexts:** Split the monolith into logical domains (e.g., Orders, Customers, Inventory).  
3. **Strangle one domain:** Build a new .NET 8 microservice for that domain, expose its API via the gateway, and route traffic for that domain to the new service (using path‑based or header‑based rules).  
4. **Data sync:** Use change‑data‑capture (Debezium) or dual‑write to keep the legacy DB and new service DB in sync during cut‑over.  
5. **Retire:** Once traffic is fully shifted, decommission the corresponding monolith code and DB tables.  
6. **Repeat** for each domain until the monolith is strangled away.

**AA11** – **12‑Factor App** (key factors):  
1. **Codebase** – one codebase tracked in version control, many deploys.  
2. **Dependencies** – explicitly declare and isolate dependencies (e.g., via manifest files).  
3. **Config** – store config in environment variables, not in code.  
4. **Backing services** – treat databases, queues, etc., as attached resources via URLs.  
5. **Build, release, run** – strictly separate stages; immutable releases.  
6. **Processes** – execute the app as one or more stateless processes.  
7. **Port binding** – export services via port binding; no reliance on injected servers.  
8. **Concurrency** – scale out via process model (e.g., multiple worker types).  
9. **Disposability** – fast startup and graceful shutdown for robustness.  
10. **Dev/prod parity** – keep environments similar to reduce “works on my machine”.  
11. **Logs** – treat logs as event streams; output to stdout, let the environment route them.  
12. **Admin processes** – run admin/management tasks as one‑off processes in the same environment.  
These factors enable immutable, scalable, observable, and easily replaceable cloud‑native services.

**AA12** – *Event‑driven (Kafka) vs Request‑driven (REST/gRPC)*  

| Aspect | Kafka‑based EDA | REST/gRPC Request‑driven |
|--------|----------------|--------------------------|
| **Coupling** | Loose: producers/consumers only know topic schema. | Tighter: caller must know endpoint, version, and contract. |
| **Scalability** | Horizontal scaling of consumers; high throughput; decoupled peaks. | Scales per service; can become bottleneck if many sync calls. |
| **Debugging complexity** | Harder: need to trace across topics, offsets, and consumer groups; eventual consistency obscures causality. | Easier: request‑reply trace follows call stack; synchronous errors surface immediately. |
| **Ordering guarantees** | Per‑partition ordering; cross‑partition requires extra effort. | Strong ordering per request (if using HTTP/2 or gRPC). |
| **Failure handling** | Consumer can retry, dead‑letter topics; system continues despite producer failure. | Caller must handle timeouts, retries, circuit breakers; failure propagates upstream. |
| **When to choose** | High‑volume, asynchronous workflows, event sourcing, audit trails, decoupled micro‑services, need for replayability. | Low‑latency, request‑reply interactions, CRUD‑style APIs, synchronous transactions, when immediate response is required. |

**AA13** – A **load balancer** distributes incoming client requests across multiple backend instances to improve availability and performance.  
- **Layer 4 (Transport)** works on TCP/UDP packets (IP + port); makes decisions based on source/destination IP and port, no insight into application data.  
- **Layer 7 (Application)** works on HTTP/HTTPS (or other L7 protocols); can inspect URLs, headers, cookies, and make routing decisions based on content.  
*Use case requiring L7:* **Path‑based routing** (e.g., sending `/api/*` to an API cluster and `/static/*` to a CDN) or **host‑based virtual hosting** (multiple domains on same IP).

**AA14** – A **message queue** (e.g., RabbitMQ) stores discrete messages; consumers acknowledge receipt, and messages are typically removed after processing. A **log‑based broker** (e.g., Kafka) treats the log as an immutable, append‑only sequence; consumers track offsets and can replay messages.  
*Pick RabbitMQ* when you need traditional queuing semantics, complex routing, priority queues, or request‑reply patterns.  
*Pick Kafka* when you need high‑throughput event streaming, log compaction, replayability, or multiple independent consumers of the same data stream.

**AA15** – A **container** is a lightweight, isolated user‑space process that packages an application and its dependencies, sharing the host OS kernel. A **virtual machine** includes a full guest OS, hypervisor, and virtualized hardware, making it heavier. Containers are popular for microservices because they start fast, use minimal resources, enable dense packing, and simplify CI/CD pipelines (image‑based deployment).

**AA16** – **Stateless services** retain no client‑specific data between requests; state is stored externally (DB, cache). **Stateful services** keep data in memory or local disk (e.g., session store, in‑memory cache). Stateless services are easier to scale horizontally because any instance can handle any request; no need to replicate or synchronize local state.  
*Example stateless:* a REST API service that reads/writes a database.  
*Example stateful:* a WebSocket server that maintains per‑connection chat state, or an in‑memory caching layer like Redis (though Redis can be clustered, the basic node is stateful).

**AA17** – An **ORM** maps object‑oriented models to relational tables, handling CRUD operations via language‑native objects.  
- **Java:** Hibernate (or Spring Data JPA).  
- **Python:** SQLAlchemy (or Django ORM).  
*Trade‑offs vs raw SQL:*  
- **Pros:** productivity, reduced boilerplate, database‑agnostic code, automatic lazy loading, type safety.  
- **Cons:** performance overhead, opaque SQL generation, difficulty tuning complex queries, leaky abstractions, learning curve.

**AA18** – The **Bulkhead** pattern isolates resources (threads, connections, memory) so that failure or heavy load in one component doesn’t exhaust resources needed by others.  
*Relation to microservices:* prevents a “noisy neighbor” service from starving thread pools or connection pools of other services.  
*Concrete example:*  
- Assign each service its own **dedicated thread pool** (e.g., using Java’s `ExecutorService` with a fixed size).  
- Or deploy each service in its own **Kubernetes namespace** with resource limits/requests (CPU/memory) – a deployment‑level bulkhead.  
If a service experiences a spike and exhausts its thread pool, only its own requests are queued/rejected; other services continue unaffected.

**AA19** – *Operational Transformation (OT)* transforms operations based on concurrent operations to achieve convergence; requires a central server to serialize and transform ops. *CRDTs* are data structures that guarantee convergence regardless of delivery order, using mathematical properties (commutativity, associativity, idempotence).  

| Aspect | OT | CRDT |
|--------|----|------|
| **Consistency** | Strong (if server correctly transforms) – eventual if network partitions. | Eventual strong convergence; no central sequencer needed. |
| **Latency** | Low latency when server is close; extra round‑trip for transformation. | Can be lower (local apply then propagate) but may need anti‑entropy for convergence. |
| **Complexity** | High: need transformation functions for each op type, handling edge cases. | Lower: pick a well‑studied CRDT (e.g., G‑Counter, LWW‑Element‑Set, RGA). |
| **Offline support** | Poor: requires server to generate transforms; offline edits must be buffered and later sent, risking conflicts. | Excellent: local edits apply to replica; sync later merges automatically. |
| **Choice for offline editing** | **CRDTs** – they allow divergent replicas to merge without coordination, making offline work safe and simple. |

**AA20** – Challenges in distributed tracing across polyglot microservices:  
- **Context propagation:** Need to inject trace IDs (W3C Trace Context `traceparent`/`tracestate` or legacy B3) into in‑process logs and outgoing messages (HTTP headers, gRPC metadata, message broker headers). Libraries (OpenTelemetry, Jaeger client) automate this.  
- **Sampling strategies:** *Head‑based* decides at start (e.g., 1 % of requests) – low overhead but may miss rare errors. *Tail‑based* buffers spans and decides after seeing the whole trace (e.g., based on error status or latency) – higher storage/compute but captures interesting traces.  
- **Trace storage & querying:** Backends like Jaeger (Cassandra/Elasticsearch), Tempo (object store), or Zipkin. Must support high‑cardinality tags (traceID, spanID, service.name) and fast look‑ups by traceID, duration, attributes.  
- **Interaction with async messaging:** When a request publishes to Kafka, the producer must inject trace context into the message headers; the consumer extracts it and starts a new span (or continues as a child). If the broker doesn’t preserve headers, continuity breaks.  
- **Ensuring continuity through Kafka:** Use **OpenTelemetry Kafka instrumentation** (or manually) to add `traceparent`/`tracestate` to the record’s headers. On the consumer side, read those headers and set them as the parent context before creating spans for processing. If using a schema registry, ensure headers are not stripped. End‑to‑end trace will show: client → service A (producer) → Kafka → service B (consumer) → …  

**OP1** – *Type 1 (bare‑metal) hypervisor* runs directly on hardware; examples: VMware ESXi, Microsoft Hyper‑V Server, KVM (when loaded as kernel module). *Type 2 (hosted) hypervisor* runs atop a host OS; examples: Oracle VirtualBox, VMware Workstation, Parallels Desktop.  

**OP2** – **SAN (Storage Area Network)** provides block‑level storage over a dedicated high‑speed network (Fibre Channel, iSCSI, FCoE). Used for databases, VMs needing low latency and high IOPS. **NAS (Network‑Attached Storage)** offers file‑level storage via protocols like NFS, SMB/CIFS, AFP. Used for shared file shares, backups, media repositories.  

**OP3** – *3‑tier network*: core (high‑speed backbone), distribution (aggregation, policy), access (edge to end devices). *Leaf‑spine* replaces the distribution tier with a full‑mesh of spine switches; every leaf connects to every spine. It solves the **oversubscription and predictable latency** problem of 3‑tier: any leaf‑to‑leaf path is exactly two hops, providing uniform bandwidth and simplifying ECMP load‑balancing.  

**OP4** – HA Proxmox cluster design:  
- **Node count:** Minimum 3 nodes for quorum (2 + 1).  
- **Quorum:** Uses corosync; cluster stays operational if > ½ nodes are alive.  
- **Fencing (STONITH):** Configure a power‑management device (IPMI, iLO, iDRAC, or APC PDU) to isolate a failed node.  
- **Shared storage options:** Ceph RBD (via CephFS or RBD), iSCSI target (e.g., LIO), or NFS export (with locking). Ceph preferred for self‑healing and scalability.  
- **Node failure:** Corosync detects loss; fencing cuts power to the failed node; remaining nodes regain quorum, VMs are migrated/restarted on healthy nodes via HA manager.  

**OP5** – *VLAN trunking* carries multiple VLANs over a single link by tagging frames. *802.1Q* adds a 4‑byte tag (TPID 0x8100, PRI, CFI, VLAN ID). To put a server with one NIC on three VLANs on Linux:  
```bash
# Create VLAN sub‑interfaces
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip link add link eth0 name eth0.30 type vlan id 30
# Bring up and assign IPs
ip addr add 192.168.10.5/24 dev eth0.10
ip addr add 192.168.20.5/24 dev eth0.20
ip addr add 192.168.30.5/24 dev eth0.30
ip link set up dev eth0.10 eth0.20 eth0.30
```  
(Optionally configure via `/etc/network/interfaces` or Netplan.)

**OP6** – RAID levels (6 drives):  
- **RAID 1:** mirror (2‑way) → 2 TB usable (if 2 TB drives), can survive 1 disk failure, read‑performance ~2×, write ~1×.  
- **RAID 5:** single parity → 5 TB usable, survives 1 disk failure, read good, write penalty (parity calc).  
- **RAID 6:** double parity → 4 TB usable, survives 2 failures, higher write penalty.  
- **RAID 10:** 1+0 (mirrored stripes) → 3 TB usable (3 mirrors), survives 1 failure per mirror (up to 3 total if not same mirror), best read/write performance.  
- **RAID Z2** (ZFS): double‑parity RAID‑Z → 4 TB usable, survives 2 failures, built‑in checksums, self‑healing.  

*Choice for a database server:* **RAID 10** gives the best blend of performance (high IOPS, low latency) and fault tolerance (can lose any single drive, and even multiple drives as long as not both from same mirror). With 6 drives you get 3 TB usable and strong random‑read/write performance crucial for DB workloads.  

**OP7** – DNS architecture for 500‑person enterprise:  
- **Internal AD‑integrated DNS:** AD‑integrated primary zone for `corp.example.com`, stored in AD, replicated via AD replication. Domain controllers act as DNS servers; they also forward external queries.  
- **Split‑horizon:** Two views: internal (serves AD zone + internal records) and external (public‑facing zone `example.com`). Implement via BIND views or Windows DNS zone scopes.  
- **External authoritative servers:** Two hardened DNS servers in the DMZ, secondary‑only (or primary with AXFR from internal) serving the public zone, DNSSEC‑signed.  
- **Recursive resolvers:** Internal DNS servers (AD DCs) provide recursion for clients; they forward unknown queries to ISP resolvers or to a forwarding DNS pair in the DMZ.  
- **Forwarders/Conditional forwarding:** Internal DNS forwards all non‑corp queries to ISP DNS; conditional forward for partner domains to partner’s DNS servers.  
- **DNSSEC:** Enable on external zone; generate KSK/ZSK, publish DS record to registrar, configure NSEC3. Internal zone may be unsigned (or signed if desired).  
- **Laptop moving between office & VPN:** When on LAN, client uses internal DNS (DHCP‑provided). When on VPN, the VPN client pushes the internal DNS servers (or split‑DNS) so queries for `corp.*` go internal, others go to public resolvers; split‑horizon ensures correct answers.  

**OP8** – PKI chain of trust: Root CA (offline, self‑signed) → Subordinate/Issuing CA (online) → End‑entity certificate (server, client, code‑signing).  
- **Root CA:** kept offline, used only to sign subordinate CAs; its compromise invalidates the whole PKI.  
- **Subordinate CA:** issues certs; can be renewed/revoked without affecting root.  
- **CRL vs OCSP:** CRL is a periodically published list of revoked certs; OCSP provides real‑time revocation status via responder.  
- **Certificate templates:** Define key usage, validity, renewal, CSP settings (e.g., Web Server, Client Auth, Code Signing).  
- **Auto‑enrollment:** Use Group Policy (Windows) or certmgr scripts to request/renew certs from subordinate CA automatically.  
- **Consequences:** Compromised **subordinate CA** → attacker can issue fraudulent certs for its scope; you can revoke the subordinate CA and re‑issue from root, limiting impact. Compromised **root CA** → attacker can create trusted subordinate CAs; you must destroy the root and re‑issue a new PKI, affecting all issued certs (massive re‑issuance).  

**OP9** – Hub‑and‑spoke WAN comparison (5 sites, 50 users each, latency‑sensitive VoIP):  

| Option | Cost | Reliability | Latency | Mgmt Complexity | Security |
|--------|------|-------------|---------|-----------------|----------|
| **MPLS** | High (leased circuits) | Carrier‑grade SLA, low jitter | Low‑moderate (depends on provider) | Low (provider manages) | Good (private MPLS cloud) |
| **IPsec VPN over Internet** | Low‑moderate (ISP broadband) | Depends on ISP redundancy; can add dual‑ISP | Variable (Internet latency, possible jitter) | Moderate (manage tunnels, keys) | Strong if AES‑256 + proper DH groups |
| **SD‑WAN** | Moderate (hardware/software + broadband) | Can bond multiple links, dynamic path selection, SLA‑aware | Low‑moderate (chooses best path) | Higher (controller, policies) | Good (encryption, segmentation) |
| **WireGuard mesh** | Low (software only) | Relies on underlying Internet links; each site‑to‑site tunnel | Low (WireGuard is lightweight, low overhead) | Low‑moderate (mesh key management) | Strong (modern crypto, minimal attack surface) |

**Recommendation:** For VoIP, **MPLS** offers the most predictable low latency and jitter, worth the cost if budget allows. If cost is a concern, a **SD‑WAN** solution with dual‑ISP links and QoS policies can approximate MPLS performance while providing better flexibility and lower OPEX. Pure IPsec VPN is acceptable if you can tolerate occasional jitter; WireGuard mesh is simplest but may suffer from inconsistent latency across hops without intelligent path selection.  

**OP10** – **iDRAC (Dell), iLO (HP), IPMI** are out‑of‑band management controllers providing remote power control, console redirection, hardware health monitoring, and firmware updates independent of the OS. OOB is critical because you can recover a hung or powered‑off host, reinstall OS, or diagnose hardware without needing network or OS access.  
If the IPMI interface is exposed to the Internet, attackers can attempt brute‑force login, exploit vulnerabilities (e.g., default credentials, CVE‑2020‑xxxx), gain full control of the server (power cycle, install malicious firmware, sniff traffic), leading to complete compromise.  

**OP11** – **LVM** (Logical Volume Manager) creates flexible logical volumes on top of physical partitions; supports resizing, snapshots (via LVM snapshot – copy‑on‑write, read‑only while snapshot exists). **LVM‑Thin** provisions thin‑pooled volumes; snapshots are also copy‑on‑write but allow over‑allocation and efficient space usage for many snapshots. **ZFS** combines volume management and filesystem; snapshots are instantaneous, read‑only, and use copy‑on‑write with no performance impact; clones are writable snapshots.  
- Use **LVM** when you need traditional Linux volume management with simple snapshots.  
- Use **LVM‑Thin** when you want many snapshots or thin provisioning (e.g., VM images).  
- Use **ZFS** when you need end‑to‑end checksums, self‑healing, built‑in RAID‑Z, and powerful snapshot/clone workflows (e.g., file servers, backup appliances).  

**OP12** – Surviving a complete site failure with a 3‑node Proxmox + Ceph cluster:  
- **Stretch cluster / DR approach:** Deploy Ceph monitors (MOS) across sites with an odd number (e.g., 3 monitors: 2 at primary site, 1 at DR site) and use a **tiebreaker** (e.g., a lightweight witness node or Ceph’s `mon_allow_pool_delete` with `mon_warn_on_lag_ratio`).  
- **CRUSH rules:** Define a replicated rule (`size=2`, `min_size=1`) with a `failure-domain=host` and a `step chooseleaf firstn 0 type rack` that prefers storing copies in different racks/sites. For DR, set a rule that stores one copy locally and the other remotely.  
- **Network latency:** Keep inter‑site RTT < 5 ms for synchronous replication (Ceph’s `msgr2` with `tcp_nodelay`). If higher, consider asynchronous DR (CephFS mirroring or RBD mirroring) with a small RPO.  
- **Split‑brain prevention:** With an even number of monitors and no tiebreaker, a network partition can cause two subsets each thinking they have quorum → split‑brain. Adding a third monitor at a third location or a witness ensures only one side can achieve quorum.  
- **Why 2‑site Ceph is bad without tiebreaker:** Two sites can each see half the monitors; neither reaches quorum, leading to stalled I/O or, if they incorrectly form quorum, divergent data (split‑brain). A tiebreaker (third monitor or witness) breaks the tie.  

**OP13** – **DHCP** process (DORA):  
1. **Discover** – client broadcasts DHCPDISCOVER.  
2. **Offer** – server replies DHCPOFFER with IP lease.  
3. **Request** – client broadcasts DHCPREQUEST for offered IP.  
4. **Acknowledge** – server sends DHCPACK; lease begins.  
If the DHCP server becomes unavailable and a Windows client’s lease expires, the client will attempt to renew at 50 % of the lease time; failing that, it will rebind at 87.5 %. If no response, it will **APIPA** (self‑assign 169.254.x.x/16) after the lease expires, resulting in limited local‑only connectivity until a DHCP server is reachable.  

**OP14** – **Managed switch** provides CLI/GUI for configuration: VLANs, trunking, port‑security, STP/RSTP, QoS, PoE control, link aggregation (LACP), SNMP, RMON, ACLs, port mirroring. **Unmanaged switch** is plug‑and‑play with no configurability. Enterprise needs managed switches for traffic segmentation, loop prevention, performance policing, and monitoring.  

**OP15** – **NTP** synchronizes clocks to UTC (or a reference). Accurate time is vital for: authentication protocols (Kerberos, TLS timestamps), logging correlation, distributed transactions, database replication, and security audits. Clock drift can cause: failed Kerberos tickets, inconsistent log ordering (hindering forensics), premature certificate expiration/validation, and database replication conflicts (e.g., conflicting write timestamps leading to data loss).  

**OP16** – **Physical server:** bare metal hardware running OS directly. **Virtual machine:** guest OS running on a hypervisor, sharing hardware via virtual devices. **Container:** isolated user‑space process sharing host kernel.  
Run workload on bare metal when you need: maximum performance (e.g., HPC, DPDK, real‑time), specialized hardware (GPUs, FPGAs, NICs with SR‑IOV), or strict compliance that forbids virtualization layers.  

**OP17** – **UPS** provides instantaneous battery power to bridge short outages and allow graceful shutdown or generator start‑up. **Generator** supplies longer‑term power (minutes to days) but has a start‑up delay (seconds to minutes). You need both: UPS covers the gap until the generator reaches full output, protecting against power sags and providing clean power. **ATS (Automatic Transfer Switch)** automatically switches load from utility to generator when it detects loss of mains, and back when utility returns, ensuring seamless transfer without manual intervention.  

**OP18** – *Active‑passive*: one node handles traffic; the other stands by, taking over on failure. *Active‑active*: both nodes serve traffic simultaneously, sharing load.  
For a PostgreSQL pair using **Pacemaker/Corosync**:  
1. **Resources:** `clone` for `pgsql` (or use `ocf:heartbeat:pgsql`).  
2. **Fencing (STONITH):** Configure IPMI/iLO or APC PDU to power‑off the unhealthy node.  
3. **Virtual IP (VIP):** Assign a floating IP via `ocf:heartbeat:IPaddr2` resource; Pacemaker moves VIP to the active node.  
4. **Behavior:** On node failure, Corosync detects loss, Pacemaker triggers STONITH to fence the dead node, then promotes the standby PostgreSQL (if using streaming replication with synchronous mode) and moves the VIP to it. Clients reconnect to the VIP and continue with minimal downtime.  

**OP19** – Backup & recovery strategy for 50‑server on‑premise:  
- **3‑2‑1 rule:** Keep at least 3 copies of data, on 2 different media, with 1 copy off‑site.  
- **RPO/RTO:** Define per application (e.g., critical DB: RPO = 15 min, RTO = 30 min; file servers: RPO = 4 h, RTO = 2 h).  
- **Backup types:** Weekly full + daily incremental (or forever‑incremental with synthetic full). Use **deduplication** at source or target to reduce storage.  
- **Media:** Disk (NAS/SAN) for fast restore; tape (LTO‑9) for long‑term archival/off‑site; cloud (e.g., AWS Glacier, Azure Blob) for off‑site copy.  
- **Immutable backups:** Use WORM tape, object lock (S3 Object Lock), or immutable snapshots (ZFS, NetApp SnapLock) to protect against ransomware.  
- **Testing:** Schedule regular restore drills (quarterly) – verify backup integrity, test bare‑metal restore, validate application functionality.  
- **Difference:** *Backup* is the process of copying data for recovery; *Disaster Recovery* (DR) encompasses the broader plan to resume operations after a catastrophic event, including failover sites, network, and application restoration.  

**OP20** – **802.1X** workflow:  
1. **Supplicant** (client device) initiates EAPOL‑Start.  
2. **Authenticator** (switch port) responds with EAP‑Request/Identity.  
3. Supplicant sends EAP‑Response/Identity.  
4. Authenticator forwards to **Authentication Server** (RADIUS).  
5. RADIUS validates credentials (e.g., EAP‑TLS certificates, PEAP/MSCHAPv2) and sends Access‑Accept/Reject.  
6. On Accept, authenticator opens the port (assigns VLAN, applies QoS).  
- **EAP methods:** *EAP‑TLS* (mutual cert‑based, strongest); *PEAP* (TLS tunnel + inner MSCHAPv2 or GTC).  
- **RADIUS** handles policy, VLAN assignment via `Filter-Id` or `Tunnel-Private-Group-ID`.  
- **Failed auth:** Port remains in unauthorized state; traffic is blocked (or placed in a guest VLAN if configured).  
- **MAB (MAC Authentication Bypass):** For devices that can’t run 802.1X (e.g., printers, IP phones), the switch treats the MAC address as the username in a RADIUS request; if the MAC is allowed in the RADIUS database, the port is authorized (often with a restricted VLAN). MAB is less secure (MAC spoofing possible) and should be combined with port‑security or used only on trusted endpoints.
