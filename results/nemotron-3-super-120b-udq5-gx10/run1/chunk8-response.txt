
**CL1** – IaaS provides raw compute, storage, and networking (you manage OS, middleware, apps). Example: AWS EC2. PaaS offers a managed platform for developing/run‑time apps (you manage code & data). Example: Azure App Service. SaaS delivers fully managed end‑user applications (you only configure usage). Example: Microsoft 365.

**CL2** – Shared Responsibility Model splits security duties:  
- **IaaS VMs** – Provider secures physical host, hypervisor, and network; you secure OS, patches, apps, data, IAM, firewall rules.  
- **Managed Kubernetes** – Provider secures control plane, underlying nodes, and platform services; you secure container images, pod RBAC, network policies, secrets, and application code.  
- **SaaS (M365)** – Provider secures everything except your data, user access, and configuration; you manage identity, data classification, device compliance, and user‑level settings.

**CL3** – VPC = isolated virtual network; Subnet = IP range inside a VPC (can be public/private); Security Group = stateful firewall attached to ENIs (allow rules only, evaluated per‑traffic flow); NACL = stateless subnet‑level firewall (allow/deny rules, evaluated in order, both inbound & outbound). Layering: traffic first hits NACL (stateless), then Security Group (stateful) at the instance ENI. Stateful tracking remembers connection state; stateless treats each packet independently.

**CL4** – Landing zone = pre‑built, secure, multi‑account foundation (OU structure, baseline policies, networking, logging). Organizational Units group accounts by function (e.g., prod, dev, shared). Guardrails = SCPs (AWS) or Policy definitions (Azure) that enforce compliance (encryption, tagging, no public S3). Shared networking: AWS Transit Gateway or Azure Hub‑and‑Spoke connects VPCs/VNets centrally, enabling hub‑spoke routing and centralized inspection. Centralized logging aggregates CloudTrail/Audit logs, VPC Flow Logs, etc., into a SIEM. Single‑account approach lacks isolation, blast‑radius containment, granular billing, and policy enforcement, making security and cost management harder.

**CL5** – IaC = managing infrastructure via declarative/imperative code.  
- **Terraform/OpenTofu**: cloud‑agnostic, state‑driven, HCL; best for multi‑cloud, complex dependencies.  
- **Pulumi**: uses general‑purpose languages (TS, Python, Go); good when teams prefer code over DSL.  
- **CloudFormation/Bicep**: native to AWS/Azure, tight service integration, no state file; ideal for single‑cloud, rapid deployment.  
- **Crossplane**: extends Kubernetes to provision cloud resources via CRDs; choose when you want infrastructure managed as Kubernetes workloads (GitOps‑friendly).  

**CL6** – HPA scales pod replicas based on CPU/memory/custom metrics. VPA adjusts pod resource requests/limits (vertical scaling). Cluster Autoscaler adds/removes worker nodes based on pod scheduling needs. KEDA drives scaling based on event sources (queues, streams, HTTP) via ScaledObjects; use KEDA when workload is event‑driven and not well‑represented by CPU/memory (e.g., Kafka lag, RabbitMQ queue length).

**CL7** – DR design: define RPO (max data loss) and RTO (max downtime). Active‑active: both regions serve traffic; data replicated synchronously (low RPO) or async with conflict resolution. Active‑passive: primary region hot, standby warm/cold; failover via DNS (Route53 latency‑based or health‑check, Azure Traffic Manager). State management: use multi‑master DB (Aurora Global DB, Cosmos DB) for sync, or async read replicas with promotion scripts. Cost: active‑active higher (duplicate compute), active‑passive lower (standby idle). Pilot light: minimal core services running; warm standby: scaled‑down but ready; multi‑site active‑active: full capacity in both sites.

**CL8** – GitOps: declarative state stored in Git; operators continuously reconcile cluster to match Git. ArgoCD: UI‑rich, supports multiple clusters, health assessment, automated sync; FluxCD: lightweight, CNCF‑graduated, uses Kubernetes controllers, integrates with Flux v2. Secrets: store encrypted (Sealed Secrets, SOPS) or use External Secrets Operator/Vault to fetch dynamic secrets at runtime. Drift: manual changes cause reconciliation loop to either revert (if sync policy set) or alert; operators can be configured to warn, auto‑correct, or require manual approval.

**CL9** – Stateful legacy app on K8s:  
- **StatefulSet** provides stable network IDs, ordered pod startup/shutdown, and stable storage.  
- **Local PV/PVC** with a LocalVolumeProvisioner storage class (node‑affinity) for low‑latency disk.  
- **Headless Service** (clusterIP=None) gives each pod a DNS‑resolvable hostname.  
- **Init Containers** to copy config files into the PV or wait for dependencies.  
- **ConfigMaps** mounted as volumes for externalized config (if not baked).  
- **PodDisruptionBudget** (minAvailable=1) to avoid simultaneous evictions during upgrades.  
- Use **nodeSelector/taints/tolerations** to keep pods on specific nodes with local storage.

**CL10** – Service Account = K8s identity for pods; Workload Identity = cloud‑provider identity bound to a K8s service account (e.g., AWS IAM Role for Service Account – IRSA, Azure Workload Identity). Mounting long‑lived credentials in a pod is bad because they can be leaked via volume mounts, exec, or image layers, and are hard to rotate. Workload Identity Federation uses OIDC trust: the cloud provider trusts the K8s token issuer, exchanges it for short‑lived cloud tokens, eliminating static secrets.

**CL11** – Object Storage (S3/Blob): immutable, HTTP‑API, high durability (11‑9’s), ideal for backups, media, static sites. Block Storage (EBS/Managed Disk): raw volumes attached to VMs, low‑latency IOPS, suitable for databases, boot disks. File Storage (EFS/Azure Files): NFS/SMB shared file system, POSIX semantics, good for lift‑and‑shift apps, home directories, containers needing shared durability. Durability: object > file > block (block durability depends on underlying storage but typically 99.9%‑99.99%). Availability: object & file are regionally/zonal redundant; block is AZ‑resilient but requires manual replication for multi‑AZ.

**CL12** – Zero‑trust K8s:  
- **Network Policies** enforce least‑privilege pod‑to‑pod traffic (default deny).  
- **Service Mesh (Istio/Linkerd)** with mTLS encrypts service‑to‑service traffic, provides fine‑grained authz.  
- **Pod Identity** (IRSA, Workload Identity) removes cloud creds from pods.  
- **Admission Controllers** (OPA/Gatekeeper, Kyverno) validate images, enforce policies (runAsNonRoot, readOnlyRootFS).  
- **Image Signing** (Cosign, Notary) and admission checks ensure only trusted images run.  
- **Runtime Security** (Falco, Tracee) detects anomalous syscalls, file writes, privilege escalation.  
- **Secrets Management** (External Secrets Operator, Vault CSI driver) injects short‑lived secrets.  
Differs from perimeter model: trust is never assumed based on network location; every request is authenticated, authorized, and encrypted, and workloads are isolated even if an attacker breaches the outer network.

**CL13** – CDN caches static/content at edge POPs, reducing latency and origin load. Works via DNS‑based request routing to nearest edge; edge serves cached copy or fetches from origin on miss. Cloud‑native CDNs: AWS CloudFront, Azure CDN (Microsoft). Use CDN for globally distributed static assets, video streaming, API acceleration; serve directly from origin when traffic is low, latency‑insensitive, or you need full control over caching headers (e.g., dynamic personalized pages).

**CL14** – Region = geographic area containing multiple AZs; AZ = isolated data center with independent power, cooling, networking. Deploy across AZs for fault tolerance (AZ failure doesn’t take down service). Zonal resources tied to a specific AZ (e.g., EC2 instance, managed disk); regional resources span AZs (e.g., S3, RDS multi‑AZ, VPC). Regional services provide higher availability; zonal resources give lower latency but need manual replication for HA.

**CL15** – Managed DB (RDS, Cloud SQL, Azure SQL) offloads provisioning, patching, backups, HA, scaling, monitoring. You still manage schema, queries, indexing, application‑level tuning, and access control. Running DB on VM gives full control but you must handle all OS/patch/backup/replication tasks.

**CL16** – IAM Users = long‑term credentials for people; Groups = collections of users for policy attachment; Roles = assumable identities (by services, users, or external accounts) with temporary credentials; Policies = JSON documents defining allowed/denied actions. Principle of Least Privilege: grant only the permissions needed to perform a task. Apply by: start with no permissions, add granular policies per job function, use policy simulation, regularly review unused permissions, enforce via SCPs/deny lists, and use IAM Access Analyzer.

**CL17** – Serverless = run code without managing servers; provider handles scaling, patching, billing per execution. AWS Lambda, Azure Functions, GCP Cloud Functions. Cold start = latency incurred when a new container instance is initialized (runtime, dependencies). Matters for latency‑sensitive sync requests. Poor fit for long‑running, high‑CPU, or stateful workloads needing persistent connections, or when execution time regularly exceeds provider limits (e.g., 15 min Lambda).

**CL18** – Ingress Resource: simple HTTP(S) routing via Ingress controller (NGINX, ALB). Gateway API: newer, role‑based, extensible model (Gateway, HTTPRoute) supporting multiple protocols, better separation of concerns. Cloud Load Balancer Annotations: provider‑specific (e.g., service.beta.kubernetes.io/aws-load-balancer-ingress) to create NLB/ALB directly. Service Mesh Ingress Gateways (Istio IngressGateway): terminate TLS at mesh edge, apply mTLS inside, enable observability. TLS termination: Ingress controller or cloud LB terminates TLS; Gateway API can delegate to same; mesh ingress does TLS termination then re‑encrypts for internal mTLS. Use Gateway API when you need multi‑protocol, advanced traffic splitting, or want a vendor‑neutral, extensible API over the legacy Ingress.

**CL19** – Cost‑optimization for $80k/mo:  
- **Reserved Instances/Savings Plans**: commit to 1‑3 yr for steady workloads (compute‑optimized, memory‑optimized).  
- **Spot/Preemptible**: use for fault‑tolerant batch, CI/CD, workloads with checkpointing.  
- **Right‑size**: use CloudWatch/Azure Monitor metrics, Trusted Advisor, or third‑party (CloudHealth, Kubecost) to downsize over‑provisioned instances.  
- **Storage Tiering**: S3 Intelligent‑Tiering for unknown access patterns, Glacier/Archive for infrequent data; Azure Cool/Archive tiers.  
- **Idle Detection**: schedule shutdown of dev/test, use auto‑stop policies, identify unattached EBS disks, unused snapshots.  
- **FinOps**: establish cost allocation tags, showback/chargeback per team, monthly budget alerts, governance policies (e.g., deny public S3).  
- **Tools**: AWS Cost Explorer/Azure Cost Management + Budgets, Cloudability, Harness Cloud Cost Management, Prometheus + Grafana for usage metrics, automated remediation via Lambda/Functions. Processes: weekly cost review, tag enforcement via CI, automated rightsizing pipelines, reservation purchasing automation.

**CL20** – Multi‑cloud design to avoid lock‑in:  
- **Abstraction Layer**: Kubernetes as common runtime; deploy workloads via Helm charts/Kustomize.  
- **IaC Portability**: Terraform/OpenTofu modules with provider‑agnostic variables; use Terraform Cloud/Enterprise for state locking.  
- **Networking**: AWS‑Azure VPN or Azure ExpressRoute + AWS Direct Connect (or third‑party interconnect) to create encrypted transit VPC/VNet; use Transit Gateway ↔ Hub‑and‑Spoke for hub‑spoke connectivity.  
- **Identity Federation**: Azure AD ↔ AWS IAM via SAML/OIDC; use workload identity federation for cloud‑to‑cloud access.  
- **Trade‑offs**: increased operational overhead (dual‑skill set, separate billing, compliance), latency from interconnect, complexity in data consistency, and tooling gaps. Benefits: risk mitigation, negotiating power, ability to leverage best‑of‑breed services.  
- **Justified** when: regulatory/data‑sovereignty requires geographic distribution, you need specific services only on one cloud, or you want active‑active failover across providers.  
- **Unnecessary** when workloads are homogeneous, you can achieve HA within a single provider, or the added complexity outweighs risk reduction.

**OT1** – Purdue Model (ISA‑95) Levels:  
0 – Physical Process (sensors, actuators).  
1 – Basic Control (PLCs, RTUs, DCS I/O).  
2 – Area Control/Supervisory (SCADA HMIs, engineering workstations).  
3 – Site Operations (MES, production scheduling, historians).  
4 – Enterprise Planning (ERP, business systems).  
5 – Corporate/External (cloud, partners, internet).  

**OT2** – IT networks prioritize confidentiality, frequent patching, and rapid change; OT networks prioritize availability, safety, and deterministic timing. Standard IT patching can cause downtime, break real‑time loops, or require re‑qualification; OT systems often run legacy OS/firmware where patches aren’t available or would invalidate certifications.

**OT3** – Industrial DMZ (IDMZ) sits between IT (Level 4) and OT (Levels 0‑3). Allowed traffic: read‑only historian data, time synchronization (NTP), authenticated management commands (e.g., firmware upload) from IT → OT, and limited OT‑to‑IT alerts/logs. Direction: primarily IT→OT for monitoring/control, OT→IT for telemetry. Direct Level 4→Level 1 is dangerous because it bypasses safety and integrity checks, exposing PLCs to IT‑based malware or misconfiguration that could cause physical harm.

**OT4** – Protocols & Purdue placement:  
1. **Modbus TCP** – Level 1/2 (PLC/RTU communication, simple request/response).  
2. **OPC UA** – Level 2‑3 (SCADA/HMI to historian, MES; provides security, modeling).  
3. **EtherNet/IP (CIP)** – Level 1‑2 (industrial Ethernet for I/O, motion control).  
4. **PROFINET** – Level 1‑2 (real‑time I/O, drives, safety over PROFIsafe).  
5. **MQTT** – Level 3‑4 (lightweight publish/subscribe for telemetry to historians, cloud, MES).  

**OT5** – Data diode = hardware enforces one‑way flow (e.g., OT→IT only) using optical isolation; cannot be bypassed by software. Use when you need guaranteed exfiltration protection (e.g., sending sensor data to cloud while preventing any inbound command). Limitation: no bidirectional communication, so you cannot receive configurations, alerts, or remote commands; you must rely on out‑of‑band channels for control.

**OT6** – Data flow: PLC/RTU → Local Historian (Level 2) → OPC UA Server (Level 3) aggregates/tags → Edge Gateway runs MQTT broker (or directly publishes) → MQTT over TLS to Cloud Ingestion (e.g., IoT Hub, Kinesis). Security boundaries: historian ↔ OPC UA server (firewall allowing only OPC UA), edge gateway ↔ cloud (mutual TLS, restricted topics), and edge gateway ↔ OT network (strict egress only, no inbound from cloud except for management). Keep OT side isolated; edge gateway sits in IDMZ.

**OT7** – IEC 62443 zones = groups of assets with similar security requirements; conduits = defined communication paths between zones.  
- **Zone 0**: Corporate IT (Levels 4‑5).  
- **Zone 1**: Engineering workstations (Level 3).  
- **Zone 2**: SCADA servers & historian (Level 3).  
- **Zone 3**: PLCs & safety I/O (Level 1‑2).  
- **Zone 4**: Safety Instrumented Systems (SIS) – isolated.  
Conduits:  
- Corporate ↔ Engineering (controlled file share, VPN).  
- Engineering ↔ SCADA (OPC UA, HTTPS).  
- SCADA ↔ PLCs (Modbus TCP, EtherNet/IP, with whitelist).  
- PLCs ↔ SIS (none or safety‑only conduit, often air‑gapped).  
Design: place firewalls/IDS at each conduit, enforce least‑privilege, use data diodes for SIS outbound telemetry if needed.

**OT8** – Segmentation strategy for flat L2:  
- **VLANs**: VLAN10 Corporate IT, VLAN20 Engineering, VLAN30 SCADA/Historian, VLAN40 PLC Line 1, VLAN41 Line 2, VLAN42 Line 3, VLAN43 Line 4, VLAN50 HMIs, VLAN60 SIS (isolated).  
- **Switch Architecture**: Layer‑3 core switch (or router) with ACLs between VLANs; access switches per zone with port‑security, 802.1X.  
- **Firewalls**: Next‑gen firewall at each major conduit (IT↔Engineering, Engineering↔SCADA, SCADA↔PLC VLANs).  
- **Remote Access**: VPN jump host in IDMZ with MFA, time‑limited, session‑recording; no direct RDP to HMIs.  
- **Transition**: Phase‑wise – first deploy VLANs and ACLs in maintenance windows, move devices gradually, monitor traffic, keep legacy L2 fallback until cut‑over complete, use temporary “allow‑list” rules to avoid production stop.

**OT9** – SIS executes safety‑critical logic (e.g., emergency shutdown) independent of BPCS which handles normal process control. IEC 61511 defines functional safety lifecycle for SIS in the process industry. SIS network must be air‑gapped or isolated because any compromise could disable safety functions, leading to hazardous conditions. Ransomware reaching SIS could lock or corrupt safety logic, causing failure to actuate shutdowns → potential injury, environmental release, or equipment damage.

**OT10** – PLC = programmable logic controller for discrete/fast I/O; DCS = distributed control system for large‑scale, continuous processes with integrated control, historians, and redundancy; SCADA = supervisory layer for data acquisition, visualization, and high‑level control across sites. They can coexist: PLCs handle machine‑level control, DCS manages plant‑wide loops, SCADA provides HMIs and historian aggregation.  

**OT11** – Remote access architecture:  
- Jump host/bastion in IDMZ with hardened OS, MFA, and just‑in‑time (JIT) access.  
- All sessions brokered via PAM solution, recording keystrokes & screen.  
- Vendor access limited to specific IP/port, time‑bound, with disposable credentials.  
- No direct RDP from corporate to HMI; instead, vendor connects to jump host, then to HMI via approved protocol (e.g., VNC over TLS) with least‑privilege account.  
- Use network‑level restrictions (firewall rules) to allow only jump host → OT VLANs.

**OT12** – Detection & Response for compromised vendor VPN (Level 3):  
- **Network Monitoring**: Deploy IDS/IPS (e.g., Snort, Zeek) on IDMZ and OT VLANs; enable NetFlow/IPFIX and anomaly detection (baseline of Modbus/OPC UA traffic).  
- **Asset Inventory**: Maintain CMDB with MAC/IP, firmware version, last seen; use passive scanning to keep it current.  
- **IR Steps**: 1) Isolate affected VPN segment (disable VPN, block source IP). 2) Quarantine compromised Level 3 assets (move to quarantine VLAN). 3) Conduct forensic memory/disk capture. 4) Reset credentials, rotate keys, patch VPN appliance. 5) Validate integrity of historian/OPC UA servers. 6) Restore from known‑good backups if needed.  
- **Control Room Coordination**: Provide real‑time status, advise operators to switch to manual control if safety functions suspect.  
- **Operator Role**: Monitor alarms, verify process values, execute manual overrides per SOP, report anomalies to SOC.  
- **Safe Operations**: Keep SIS isolated; if any SIS alarm triggers, follow emergency shutdown procedures regardless of cyber event.

**OT13** – HMI = Human‑Machine Interface; provides visualization, alarming, and limited control (setpoints, start/stop) for operators. Differs from engineering workstation which is used for configuration, programming, firmware updates, and diagnostics; HMIs are runtime‑focused, often locked down, while engineering workstations have full development tools.

**OT14** – Historian = time‑series database that stores process data for analysis, reporting, and compliance. Plant Historian (Level 3) aggregates data from local controllers/HMIs for site‑level KPIs. Enterprise Historian (Level 4) consolidates data from multiple plants, feeds ERP/BI systems, and supports corporate‑level analytics. Enterprise historian typically has higher retention, broader data model, and stricter security.

**OT15** – Ladder Logic = graphical programming language resembling electrical relay diagrams; executed by PLCs (or soft‑PLCs). Remains dominant because it’s intuitive for electricians, deterministic, easy to troubleshoot, and supported by virtually all PLC vendors; legacy code bases and training reinforce its use.

**OT16** – RTU = Remote Terminal Unit, a ruggedized, often wireless‑capable controller for geographically dispersed assets (pipelines, water tanks). Differs from PLC: RTUs emphasize low power, built‑in radio/cellular, and often support IEC 60870‑5‑104 or DNP3; PLCs are typically LAN‑based, higher I/O density, and used in factories. Deploy RTUs in SCADA‑wide, outdoor, or low‑bandwidth environments.

**OT17** – Analog signals represent continuous values (4‑20 mA, 0‑10 V); digital signals are discrete on/off. 4‑20 mA preferred because live zero (4 mA) allows detection of wire break (0 mA) vs signal, provides noise immunity, and permits powering loop‑powered devices over same pair.

**OT18** – OT asset inventory = comprehensive list of all hardware, firmware, software, and network endpoints; foundation for risk assessment, patch management, and segmentation. Discovery: passive network monitoring (listen to ARP, Modbus, OPC UA) and active scanning (SNMP, ICMP, TCP probes) – active scanning risky because it can trigger safety faults or disrupt real‑time loops; thus use passive first, limited active in maintenance windows.

**OT19** – MITRE ATT&CK for ICS Tactics (examples):  
1. **Initial Access** – Exploit public‑facing application (e.g., vulnerable HMI web portal).  
2. **Execution** – Command‑line interface via SSH on engineering workstation.  
3. **Persistence** – Modify PLC startup script to load malicious ladder logic.  
4. **Privilege Escalation** – Abuse Windows service running as SYSTEM on SCADA server.  
5. **Defense Evasion** – Obfuscate malicious code within legitimate function blocks.  
6. **Credential Access** – Harvest credentials from clear‑text configuration files.  
7. **Discovery** – Scan internal network for Modbus devices using custom scripts.  
8. **Lateral Movement** – Use stolen credentials to hop from engineering workstation to PLC via OPC UA.  
9. **Collection** – Archive historian data via scheduled FTP transfer.  
10. **Exfiltration** – Send stolen data over DNS tunneling to C2.  
Differs from enterprise ATT&CK by focusing on OT‑specific protocols, safety systems, and impact on physical processes. Use it to map existing controls, identify gaps (e.g., lack of authentication on Modbus), and prioritize mitigations like network segmentation, protocol authentication, and application whitelisting.

**OT20** – Converged IT/OT SOC design:  
- **Log Collection**: Deploy lightweight agents (e.g., OSSEC, Wazuh) on engineering workstations and historians; use syslog forwarders from firewalls/IDS; pull OPC UA audit logs via MQTT; avoid agents on PLCs (use network‑based monitoring).  
- **SIEM Integration**: Normalize logs to common schema (CEF/JSON); enrich with asset context (IP→device type, firmware).  
- **OT‑Specific Detection Rules**: Look for anomalous Modbus function codes, unexpected OPC UA node writes, ladder logic changes, spikes in historian write rates, unauthorized firmware version strings.  
- **Alert Triage Workflow**: Tier‑1 analyst validates (checks asset criticality, time‑of‑day); Tier‑2 OT engineer reviews process impact; Tier‑3 incident lead decides containment (isolate VLAN, engage SIS manual override).  
- **Staffing**: Blend – SOC analysts for IT log correlation, OT engineers for process knowledge; cross‑train on basics of each domain.  
- **False Positives**: Baseline normal OT traffic (e.g., periodic historian writes); use temporal whitelisting; require multiple correlated events before escalation.  
- **Unauthorized Firmware Change on PLC**: Alert triggers; SOC verifies signature mismatch; OT engineer confirms via out‑of‑band (serial console) that PLC is in safe state; if unauthorized, isolate PLC VLAN, roll back to known‑good firmware from secure repository, conduct forensic review, and update change‑management process to require signed firmware and MFA for any future updates.
