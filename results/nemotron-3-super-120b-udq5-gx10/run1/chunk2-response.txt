
**Kubernetes**

**K1** – A **Deployment** manages stateless replicas; it creates identical Pods, can scale up/down, and uses rolling updates. A **StatefulSet** manages stateful workloads, giving each Pod a stable, unique network identity (`<name>-<ordinal>`) and persistent storage that survives rescheduling. Deployments treat Pods as interchangeable; StatefulSets preserve ordering and identity.

**K2** – A `ClusterIP` Service gets a virtual IP inside the cluster. kube‑proxy (via iptables or IPVS) installs rules that DNAT traffic destined for that IP:port to one of the Service’s Endpoint IPs (the Pods). The packet is then routed normally to the selected Pod.

**K3** – **PersistentVolume (PV)** – cluster‑wide storage resource (e.g., NFS disk) provisioned by admin. **PersistentVolumeClaim (PVC)** – user’s request for storage (size, access modes). **StorageClass** – defines a class of storage (provisioner, parameters, reclaimPolicy) enabling dynamic provisioning. A PVC binds to a PV that matches its requirements; if no matching PV exists and a StorageClass is specified, the provisioner creates a PV automatically.

**K4** – Troubleshooting `CrashLoopBackOff`:
1. `kubectl logs <pod>` – see why the container exits.
2. `kubectl describe pod <pod>` – check events, restarts, image pull errors.
3. Verify the container command/entrypoint and required config/secrets exist.
4. Check resource limits (OOMKilled) via `kubectl get pod` or metrics.
5. (Optional) Run the image locally to reproduce the failure.

**K5** – CoreDNS provides cluster‑internal DNS service (A/AAAA/SRV records for Services, Pods, etc.). If all CoreDNS pods are down, Pods cannot resolve internal names; external DNS may still work if `/etc/resolv.conf` includes an upstream server, but service discovery fails.

**K6** – Scheduler:
1. **Filtering** – eliminates nodes that fail hard constraints (node affinity, taints, resource requests, pod‑node selector, volume zones, etc.).
2. **Scoring** – each remaining node gets a score based on soft constraints: resource utilization (least‑requested/priority), image locality, inter‑pod affinity/anti‑affinity, node label preferences, etc.
3. The node with the highest total score is chosen.  
   *Three specific factors*: (a) available CPU/memory vs. requests, (b) pod affinity/anti‑affinity rules, (c) node label/taint preferences (e.g., prefer nodes with `dedicated=gpu`).

**K7** – Requests: 256 Mi, Limits: 512 Mi. Node has 4 GB RAM, 3.5 GB already requested → free requestable memory = 512 Mi. Since the pod’s request (256 Mi) ≤ free (512 Mi), the scheduler **will place** it. At runtime, if the pod tries to use 600 Mi (> limit), the container will be **OOMKilled** (kernel kills it for exceeding its cgroup limit) and restarted according to its restartPolicy.

**K8** – Request flow (NGINX Ingress Controller):
1. Client → external Load Balancer (cloud LB or bare‑metal) → LB forwards to NodePort/HostPort of NGINX ingress controller pods.
2. NGINX receives HTTP request, matches host/path to an Ingress rule.
3. NGINX looks up the Service name/port from the Ingress backend.
4. NGINX performs DNS‑style resolution via kube‑dns to get the Service’s ClusterIP.
5. NGINX load‑balances to an Endpoint IP (Pod) using its own upstream round‑robin/least‑conn.
6. Packet reaches node; kube‑proxy (iptables/IPVS) DNATs the Service IP to the selected Pod’s IP.
7. Packet delivered to Pod’s container; application processes request and returns response back the same path.

**K9** – A **NetworkPolicy** defines ingress/egress rules for Pods selected by `podSelector`. If no NetworkPolicy exists in a namespace, traffic is **allow‑all** (no isolation). Applying a policy that selects certain pods isolates those pods: only traffic matching the policy’s `ingress`/`egress` sections is allowed; all other traffic is dropped.

**K10** – **RollingUpdate** creates new Pods gradually while terminating old ones, maintaining availability. **Recreate** kills all existing Pods before creating new ones, causing downtime. Choose Recreate when the app cannot run multiple versions simultaneously (e.g., requires exclusive access to a non‑shared volume or a singleton leader election that would break with dual instances).

**K11** – A **namespace** is a logical cluster partition for naming, RBAC, and resource quotas. Default namespaces in a fresh cluster: `default`, `kube-system` (control‑plane components), `kube-public` (cluster‑wide readable data), `kube-node-lease` (node heartbeats), and optionally `kube-node-lease` (depending on version).

**K12** – `kubectl describe pod <name>` shows:
1. Events (why it was scheduled, restarted, etc.).
2. Containers’ state, ready/restart counts, and container IDs.
3. Mounted volumes, environment variables, and image pull secrets.
4. Node name, IP, QoS class, and tolerations/affinities.
(These are not in the simple `kubectl get pod` output.)

**K13** – A **ConfigMap** holds key‑value data. Pods can consume it:
1. As **environment variables** (`envFrom` or `env.valueFrom.configMapKeyRef`).
2. As **files** mounted into a volume (`volumes.configMap` → `volumeMounts`).

**K14** – 
- **ClusterIP**: internal virtual IP, only reachable inside the cluster.
- **NodePort**: same as ClusterIP plus a static port on each Node’s IP (`<NodeIP>:<NodePort>`) that forwards to the Service.
- **LoadBalancer**: provisions an external cloud LB (or metal LB) that forwards to the NodePort/ClusterIP; provides a single external IP.

**K15** – A **DaemonSet** ensures a copy of a Pod runs on every (or selected) Node. Use when you need a node‑level agent: log collector (fluentd), node monitor (Prometheus node‑exporter), or CNI plugin. Unlike a Deployment, DaemonSet does not manage replica count based on demand; it’s tied to node presence.

**K16** – 
- **Taints** are applied to Nodes; they repel Pods that do not tolerate them. **Tolerations** are set on Pods to allow scheduling onto tainted nodes.
- **Node affinity** is a soft/hard rule that attracts Pods to nodes with specific labels; it does not repel.
- *Use case for taints/tolerations*: reserve GPU nodes for ML workloads (`nvidia.com/gpu=present:NoSchedule`) and tolerate only those Pods needing GPUs.
- *Use case for node affinity*: schedule a caching Pod onto nodes with SSD disks (`nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution.matchExpressions`).

**K17** – A **Kubernetes Operator** is a custom controller that extends the API with a Custom Resource (CR) and encapsulates domain‑specific operational knowledge (e.g., backup, scaling, upgrades). Unlike a generic controller (like Deployment controller), an Operator manages complex stateful applications by reconciling the CR’s desired status, often using Helm charts, scripts, or external tools.

**K18** – etcd uses the **Raft consensus algorithm**, providing strong linearizable consistency: a committed entry is replicated to a majority (quorum) of nodes and is durable. If quorum is lost (< ½ + 1 nodes), the cluster cannot elect a leader or commit new entries → API server becomes read‑only, no new objects can be created.  
*Recovery with 2/3 nodes permanently lost*: restore from a recent etcd snapshot (etcdctl snapshot save/restore) onto a new set of 3 nodes, then update the API server’s `--etcd-servers` to point to the new cluster, and restart control‑plane components.

**K19** – RBAC flow:  
- **Role** / **ClusterRole** define a set of rules (apiGroups, resources, verbs).  
- **RoleBinding** binds a Role to users/groups/serviceAccounts **within a namespace**.  
- **ClusterRoleBinding** binds a ClusterRole cluster‑wide or to a namespace.  

*Read‑only access to pods and logs in namespace `dev`*:

```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-log-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: [pods, pod/log]
  verbs: [get, list, watch]

# RoleBinding (bind to a user, e.g., alice)
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-log-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20** – `/etc/resolv.conf` contains `ndots: X`. Resolver treats a name with fewer than X dots as a relative name and appends the search list (e.g., `svc.cluster.local.`) before trying the name as‑is. High `ndots` causes many unnecessary DNS queries for short names (like `kafka`), adding latency.  
Fix: set a lower `ndots` via pod’s `dnsConfig`:

```yaml
dnsConfig:
  ndots: 2          # default is 5 in many images
  nameservers:
  - 10.96.0.10      # cluster DNS (CoreDNS)
  searches:
  - dev.svc.cluster.local
  - svc.cluster.local
  - cluster.local
```

**Development**

**D1** – `git merge` creates a merge commit that preserves the history of both branches; `git rebase` rewrites the current branch’s commits onto the tip of the target branch, producing a linear history. Avoid rebasing on public/shared branches because it rewrites commit hashes, causing confusion and requiring force‑pushes that can overwrite others’ work.

**D2** – **TCP** is connection‑oriented, reliable, ordered, with flow‑control and retransmission (used by HTTP, SSH). **UDP** is connectionless, best‑effort, no ordering or retransmission (used by DNS queries, VoIP/RTP, streaming media).  

**D3** – A **race condition** occurs when the outcome depends on the timing of uncontrollable events. Example (Go): two goroutines increment a shared integer without synchronization; the final value may be less than expected because both read the same stale value, increment, and write back.

**D4** – **Symmetric encryption** uses the same secret key for both encryption and decryption (fast, used for bulk data). **Asymmetric encryption** uses a public/private key pair (slow, used for key exchange and signatures). In TLS: the server’s public key encrypts a randomly generated premaster secret; the premaster secret is then used to derive symmetric session keys for encrypting application data.

**D5** – A **container image layer** is a read‑only filesystem diff created by each Dockerfile instruction. Layer caching lets Docker reuse unchanged layers when rebuilding, speeding up builds. Best practices: put infrequently changing instructions (e.g., `FROM`, package installs) early, and frequently changing code near the end to minimize cache busting.

**D6** – Intermittent 503 (Service Unavailable) checklist (ordered by likelihood):
1. **Backend health** – are application instances crashing or overloaded? Check logs, metrics, restart loops.
2. **Load balancer / ingress health checks** – misconfigured probes marking healthy nodes as unhealthy.
3. **Resource exhaustion** – CPU/memory limits causing throttling or OOMKills.
4. **Dependency timeouts** – downstream DB or external service slow/hanging, causing request handlers to timeout and return 503.
5. (Optional) **Rate limiting / throttling** – API gateway or service mesh returning 503 due to burst limits.

**D7** – **CAP theorem**: a distributed data store can guarantee at most two of Consistency, Availability, Partition tolerance.  
- **CP** example: **etcd** or **ZooKeeper** – they stay consistent and partition‑tolerant, becoming unavailable during a network partition.  
- **AP** example: **Apache Cassandra** – remains available and partition‑tolerant, offering tunable consistency (may return stale reads).

**D8** – **Horizontal scaling** adds more nodes/instances; **vertical scaling** adds resources to a single instance. Patterns enabling horizontal scaling: stateless services, sharding/partitioning, consistent hashing, stateless front‑ends with shared-nothing architecture, and using load balancers or service meshes to distribute traffic.

**D9** – An **environment variable** is a key‑value pair available to a process’s environment. To persist across sessions on Linux, add `export VAR=value` to `~/.bashrc`, `~/.profile`, or `/etc/environment` (for system‑wide), then `source` the file or restart the shell.

**D10** – **JSON** (JavaScript Object Notation) is a lightweight, language‑independent data interchange format; maps directly to objects/arrays. **YAML** is a superset of JSON, emphasizing readability with indentation‑based structure and supports comments, complex types (anchors, aliases). Advantage of JSON: universal parsing libraries, strict schema, widely used in APIs. Advantage of YAML: easier to read/write configuration files, supports comments and reusable anchors.

**D11** – A **REST API** uses HTTP methods to perform CRUD on resources identified by URIs.  
- **GET** – retrieve a representation (safe, idempotent).  
- **POST** – create a subordinate resource or trigger an action (not idempotent).  
- **PUT** – replace an existing resource or create if known URI (idempotent).  
- **DELETE** – remove a resource (idempotent).

**D12** – **Version pinning** locks dependencies to exact versions (e.g., `package==1.2.3` in `requirements.txt` or `package.json`). It ensures reproducible builds by preventing automatic upgrades that could introduce breaking changes or behavior drift.

**D13** – **Compiled languages** translate source to machine code before execution (e.g., C, Rust). **Interpreted languages** execute source directly via an interpreter at runtime (e.g., Python, JavaScript). Some languages use both (Java compiled to bytecode, then interpreted/JIT‑compiled by JVM).

**D14** – A **reverse proxy** sits in front of servers, accepting client requests and forwarding them to backend services (e.g., NGINX, Envoy). A **forward proxy** sits between clients and the internet, forwarding client requests outward (e.g., Squid, corporate proxy).  
- Reverse proxy use: TLS termination, load balancing, caching, WAF (NGINX).  
- Forward proxy use: outbound internet access control, caching, anonymization (Squid).

**D15** – A **deadlock** is a permanent blocking of two or more processes, each waiting for a resource held by another. **Coffman conditions** (all must hold):
1. Mutual exclusion – at least one resource non‑shareable.
2. Hold and wait – processes hold resources while waiting for others.
3. No preemption – resources cannot be forcibly taken.
4. Circular wait – a closed chain of processes each waiting for a resource held by the next.

**D16** – **Eventual consistency**: after a write, all replicas will converge to the same value given enough time and no further writes. **Cassandra** achieves this via gossip‑based anti‑entropy and read‑repair. Tunable consistency levels: `ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`, `EACH_QUORUM`, `SERIAL`, `LOCAL_SERIAL`. For read‑after‑write, you can use `QUORUM` reads/writes or `CL=ALL` for strong consistency, or use `CL=ONE` with `read_repair_chance=1.0` to improve freshness.

**D17** – **mTLS** (mutual TLS) requires both parties to present certificates verified against a trusted CA. Handshake steps:
1. Client → Server: `ClientHello` (supported versions, cipher suites).
2. Server → Client: `ServerHello`, certificate, optional `CertificateRequest` (asking for client cert).
3. (If requested) Client → Server: client certificate, `CertificateVerify`.
4. Both sides exchange `Finished` messages after deriving symmetric keys from the premaster secret (encrypted with server’s public key).
5. Application data is encrypted with the negotiated symmetric keys.  
Commonly used for service‑to‑service authentication in zero‑trust networks, API gateways, and securing etcd or database clusters.

**D18** – A **hash table** stores key‑value pairs in an array of buckets; the hash function maps a key to an index. Collisions occur when two keys hash to the same bucket.  
- **Chaining**: each bucket holds a linked list (or dynamic array) of entries; lookup/insert/delete traverse the list.  
- **Open addressing**: on collision, probe successive slots (linear, quadratic, double hashing) until an empty slot is found.  
Average‑case time complexity: **O(1)** for insert, lookup, delete. Worst‑case (all keys collide): **O(n)** for chaining; **O(n)** for open addressing (if table becomes full or clustering worsens).

**D19** – **Circuit Breaker** pattern wraps a remote call. States:
- **Closed**: calls pass through; failure count tracked; if failures exceed threshold, switch to **Open**.
- **Open**: calls fail fast (return error or fallback) without invoking the remote service; after a timeout, move to **Half‑Open**.
- **Half‑Open**: allow a limited trial call; if success, reset to **Closed**; if failure, return to **Open**.  
It prevents cascading failures by stopping traffic to a failing service, giving it time to recover. Works well with retry policies: retries are attempted only when the breaker is Closed or Half‑Open; exponential backoff can be applied between retry attempts to avoid overwhelming the service.

**D20** – **Optimistic concurrency control (OCC)** assumes conflicts are rare; transactions proceed without locking, and at commit time they check for conflicts (e.g., via row version/timestamp). If a conflict is detected, the transaction aborts and retries. **Pessimistic concurrency control (PCC)** locks resources upfront (e.g., `SELECT FOR UPDATE`) to prevent others from modifying them until the transaction ends.  
- Choose **OCC** for high‑read, low‑write workloads where lock overhead is undesirable (e.g., caching layers, document stores).  
- Choose **PCC** when conflicts are frequent or strict serializability is required (e.g., banking transfers).  
Example (PostgreSQL OCC): table with `version int` column; `UPDATE … SET version = version+1 WHERE id = $1 AND version = $2;` – if no rows updated, another transaction changed the row, so retry.  
Example (PCC): `BEGIN; SELECT * FROM accounts WHERE id = $1 FOR UPDATE; … UPDATE accounts SET balance = … WHERE id = $1; COMMIT;` – the lock prevents concurrent updates on the same row.
