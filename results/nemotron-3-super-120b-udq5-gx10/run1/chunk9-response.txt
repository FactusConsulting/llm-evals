
**SC1-A**  
The pods are failing because the namespace now enforces the **Restricted** Pod Security Standard (PSS). Restricted requires:  

* `runAsNonRoot: true` **and** an explicit non‑zero `runAsUser` (or `runAsGroup`).  
* No privileged containers, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, etc.  

Your containers have `securityContext.runAsNonRoot: true` **but no `runAsUser` set**. The base image `cgr.dev/chainguard/static:latest` defaults to `USER root` (UID 0). When the pod is admitted, the Kubelet sees a conflict: the image says “run as root” while the PSP says “must run as non‑root with an explicit non‑zero UID”. The Kubelet therefore refuses to start the container; the container exits immediately, causing CrashLoopBackOff.  

Under the previous **Baseline** PSS, only `runAsNonRoot: true` was required; the Kubelet would accept an image that defaulted to root (it would still run as root, which Baseline allowed). The upgrade tightened the rule, exposing the mismatch.

**SC2-A**  
Promoting a cross‑region read replica does **not** guarantee that all WAL generated on the primary has been applied. PostgreSQL ships WAL asynchronously; the replica may lag behind the primary by seconds to minutes (or more under heavy load). When you promote, any WAL not yet replayed is lost, causing:  

* **Stale reads** – the new primary reflects the state at the moment of promotion, missing recent commits.  
* **Potential data loss** – transactions that were committed on the primary but not yet replicated are gone unless you have synchronous replication or a logical replication slot with `synchronous_standby_names`.  

**What to check:**  

```sql
-- replica lag in bytes
SELECT pg_last_wal_receive_lsn() - pg_last_wal_replay_lsn() AS replay_lag_bytes;
-- time‑based lag (approx)
SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp())) AS replay_lag_sec;
-- current WAL location on primary (if you can still connect)
SELECT pg_current_wal_insert_lsn();
```
Compare the primary’s insert LSN with the replica’s replay LSN; the difference is the data‑loss window. Also inspect `pg_stat_replication` on the primary for the replica’s `state` and `sync_state`.

**SC2-C**  
**Future‑proof architecture**

* **Primary‑DR database:** Use **Amazon Aurora Global Database** (or Aurora PostgreSQL with cross‑region read replicas). Aurora’s storage‑based replication replicates changes in < 1 second, giving RPO ≈ 0 s and automatic failover with RTO < 30 s.  
* **Connection management:** Replace PgBouncer with **RDS Proxy** (or keep PgBouncer but point it at the Aurora endpoint). RDS Proxy automatically redirects to the new writer after failover and handles connection pooling, reducing login‑retry errors.  
* **DNS failover:** Use **Route 53 health‑checked latency‑based or failover routing** pointing to the Aurora cluster endpoint; health checks detect writer loss and switch DNS within ~30 s.  
* **Application retry:** Implement exponential back‑off with jitter and idempotent retries (e.g., using a library like `retry-go` or Spring Retry).  
* **RPO < 1 s:** Aurora’s storage replication meets this; if you stay with standard RDS, enable **synchronous commit** to a cross‑region standby (`synchronous_standby_names = '*'`) and monitor `pg_stat_replication.sync_state = 'sync'`.  

**Verdict:** Aurora Global Database is the simplest way to achieve sub‑second RPO and fast RTO without custom replication scripts; it also removes the need for manual promotion and reduces operational complexity.

**SC3-C** – Hardened CI/CD pipeline

1. **Base image pinning** – reference by digest, not tag: `FROM node@sha256:<digest>`.  
2. **Image signing** – after `docker build`, run `cosign sign --key cosign.key <image>`; push the signature to the same registry (or an OCI artifact).  
3. **Admission controller** – deploy Kyverno (or OPA Gatekeeper) policy that requires a valid Cosign signature for any image pulled from the ECR repo; block unsigned images at admission.  
4. **SBOM generation** – in the CI step, run `syft <image> -o cyclonedx > sbom.xml` and upload the SBOM as an attestation (cosign attach‑sbom).  
5. **Notary v2** – optionally push the image to a Notary v2 server; the admission controller can also verify the Notary TUF metadata.  
6. **Pipeline gates** –  
   * `docker build` → `cosign sign` → `cosign verify` (local) → push.  
   * `kubectl apply` → admission controller validates signature & SBOM presence.  
   * Any failure aborts the deployment.  

This chain guarantees that only signed, SBOM‑attested, digest‑pinned images can run in the cluster, preventing the use of a tampered base image or a compromised build step.

**SC4-B** – OpenTofu module for NFS storage

```hcl
variable "nfs_server" {
  description = "NFS server hostname or IP"
  type        = string
}
variable "nfs_export" {
  description = "Exported path on the NFS server"
  type        = string
}

  description = "Size of the PV (e.g., 100Gi)"

}

    name = "nfs-sc"
  }

  parameters = {
    server = var.nfs_server
    share  = var.nfs_export
  }
  reclaim_policy = "Delete"
}

resource "kubernetes_persistent_volume" "nfs_pv" {
  metadata {
    name = "nfs-pv-${var.nfs_export}"
  }
  spec {
    storage_class_name = kubernetes_storage_class.nfs.metadata[0].name
    access_modes       = ["ReadWriteMany"]
    capacity {
      storage = var.storage_size
    }
    nfs {
      server = var.nfs_server
      path   = var.nfs_export
      read_only = false
    }
  }
}

resource "kubernetes_persistent_volume_claim" "nfs_pvc" {
  metadata {
    name = "nfs-pvc"
  }
  spec {
    storage_class_name = kubernetes_storage_class.nfs.metadata[0].name
    access_modes       = ["ReadWriteMany"]
    resources {
      requests {
        storage = var.storage_size
      }
    }
  }
}
```

**Why `ReadWriteMany`?**  
Multiple application pods (e.g., several replicas of the monolith) need to **read and write** the same upload directory concurrently. `ReadWriteMany` allows the volume to be mounted by many pods simultaneously, which `ReadWriteOnce` cannot provide.

**SC5-A** – Systematic debugging workflow

1. **Istio metrics** (via Prometheus):  
   * `istio_proxy_inbound_latency_seconds_bucket` – latency entering the pod.  
   * `istio_proxy_outbound_latency_seconds_bucket` – latency leaving the pod toward upstream.  
   * `istio_proxy_inbound_request_total` / `outbound_request_total` – request counts.  
   * `istio_proxy_inbound_connection_reset_total` – reset spikes.  
2. **Kubernetes**: `kubectl top pods`, logs (`kubectl logs -f <pod>`), check for restarts, OOMKilled.  
3. **Application logs**: look for DB connection errors, pool exhaustion warnings.  
4. **Distributed tracing (Jaeger/Zipkin)**:  
   * Start a trace at the ingress gateway, follow the span to `checkout-service → inventory-service`.  
   * If the gap appears **between** the client span and the server span, the latency is in the network/sidecar.  
   * If the server span itself is long, the delay is inside the inventory‑service application (or its DB).  
5. **Envoy‑specific stats** (accessible via `stats` endpoint or Prometheus):  
   * `cluster.<name>.upstream_rq_pending_active` – number of requests waiting for a connection (proxy queueing).  
   * `cluster.<name>.upstream_rq_retry` – retries due to 5xx/timeouts.  
   * `listener.downstream_cx_total` & `listener.downstream_cx_rx_bytes_total` – baseline traffic.  
   * A high `upstream_rq_pending_active` with low upstream latency indicates **proxy‑side queueing** (e.g., connection‑pool exhaustion).  
   * Low pending but high `upstream_rq_time` indicates **upstream service latency** (DB lock).

**SC5-B** – SQL diagnostic & Go circuit breaker

**PostgreSQL lock query**

```sql
SELECT
  blocked.pid        AS blocked_pid,
  blocking.pid       AS blocking_pid,
  blocked.usename    AS blocked_user,
  blocking.usename   AS blocking_user,
  blocked.query      AS blocked_query,
  blocking.query     AS blocking_query,
  age(now(), blocked.query_start) AS blocked_duration
FROM pg_locks blocked
JOIN pg_stat_activity blocked_activity ON blocked.pid = blocked_activity.pid
JOIN pg_locks blocking ON
  blocked.locktype = blocking.locktype
  AND blocked.database IS NOT DISTINCT FROM blocking.database
  AND blocked.relation IS NOT DISTINCT FROM blocking.relation
  AND blocked.page IS NOT DISTINCT FROM blocking.page
  AND blocked.tuple IS NOT DISTINCT FROM blocking.tuple
  AND blocked.virtualxid IS NOT DISTINCT FROM blocking.virtualxid
  AND blocked.transactionid IS NOT DISTINCT FROM blocking.transactionid
  AND blocked.classid IS NOT DISTINCT FROM blocking.classid
  AND blocked.objid IS NOT DISTINCT FROM blocking.objid
  AND blocked.objsubid IS NOT DISTINCT FROM blocking.objsubid
  AND blocked.pid != blocking.pid
JOIN pg_stat_activity blocking_activity ON blocking.pid = blocking_activity.pid
WHERE NOT blocked.granted;
```

	})
	if err != nil {

	}

**SC5-C** – Architectural fix to eliminate the problem

* **CQRS** – Separate read model (served by checkout‑service) from write model (handled by a dedicated writer service). Reconciliation jobs write to the write model; reads use a **read replica** that is never blocked by write locks.  
* **Read replica for reconciliation** – Provision a PostgreSQL standby (or use Aurora replica) whose sole purpose is to run the nightly inventory‑reconciliation CronJob. Because it’s asynchronous, the primary remains free for OLTP traffic.  
* **Bulkhead isolation** – Create two distinct connection pools in the application: one for the read path (size = X) and one for the write/reconciliation path (size = Y). Use a library like `uber-go/ratelimit` or configure the DB driver’s pool limits per service.  
* **CronJob scheduling** – Move the reconciliation job to an off‑peak window (e.g., 02:00‑04:00 UTC) or make it **incremental** (process only changed rows) so it holds locks for a fraction of a second.  
* **Kubernetes safeguards**  
  * **PodDisruptionBudget** for the reconciliation Job: `maxUnavailable: 1` ensures at most one replica of the job runs at a time, preventing a storm of simultaneous jobs.  
  * **ResourceQuota** on the namespace: limit CPU/memory that Jobs can consume (e.g., `requests.cpu: 2`, `limits.cpu: 4`) so they cannot starve the Deployment pods.  
  * Optionally, assign the CronJob to a **different node pool** (taint/toleration) so it never competes for the same node resources as the serving pods.  

With these changes, the reconciliation workload can no longer exhaust the primary DB’s connection pool or cause lock contention that spikes user‑facing latency.

**SC6-A** – Identity & access layer for zero‑trust

* **Workload identity:** Deploy **SPIRE** server agents in each environment (on‑prem vSphere, AWS, Azure). Each workload (pod, VM, container) receives a **SPIFFE ID** (e.g., `spiffe://example.org/workload/api-gateway`) and an **X.509 SVID** or JWT token via the SPIRE Agent.  
* **Federation:**  
  * **AWS:** Configure the SPIRE Server to trust AWS IAM Roles for Service Accounts (IRSA) via OIDC federation; workloads in EKS can exchange their AWS IAM role token for a SVID.  
  * **Azure:** Use Azure Managed Identity federation – the SPIRE Server trusts Azure AD tokens issued to managed identities; workloads in AKS/ACI obtain a SVID after presenting the managed‑identity token.  
  * **On‑prem:** The on‑prem SPIRE Server runs a **CA** that issues SVIDs; workloads authenticate using client certificates or token‑based auth to the on‑prem PKI.  
* **Cross‑environment trust:** Each SPIRE Server publishes its **trust bundle** (public keys of intermediates). Servers exchange bundles, allowing a workload in AWS to verify a SVID issued by the on‑prem SPIRE Server (and vice‑versa).  
* **Authorization:** Use the SPIFFE ID as the principal in service‑to‑service policies (e.g., Istio AuthorizationPolicy, Kong ACL, or AWS App Mesh). Policies grant `spiffe://.../service-a` → `spiffe://.../service-b` on specific ports/methods.  
* **Human identities:** Continue using corporate IdP (Azure AD) for user access; map groups to Kubernetes RBAC or AWS IAM roles via OIDC/SAML. No shared secrets; all authentication is based on verifiable tokens or mTLS.

**SC6-C** – Comparing connectivity options

| Option | Bandwidth | Cost | Encryption | Failover / Resilience | Fit with Zero‑Trust |
|--------|-----------|------|------------|-----------------------|---------------------|
| **AWS Direct Connect (DX)** | 1 Gbps–100 Gbps dedicated port (can bundle) | Higher (port fee + data transfer) | MACsec (layer‑2) + optional IPsec over DX | Requires redundant DX connections (two separate locations) for HA; can use BGP for active‑active. | Provides a **private, non‑internet** path – ideal for zero‑trust because traffic never traverses the public internet; you still enforce mTLS/auth at the service layer. |
| **Second VPN tunnel + ECMP** | Aggregates ~2 Gbps (if both tunnels usable) | Lower (VPN hourly + data) | IPsec (same as existing) | Automatic load‑balancing across tunnels; if one fails, traffic shifts to the other (still IPsec). | Still traverses the public internet, but you can enforce zero‑trust at the service layer (mTLS, SPIFFE). Simpler to implement, but relies on Internet reliability. |
| **Overlay mesh (Tailscale/Netbird)** | Limited by underlying ISP; typically 100 Mbps‑1 Gbps per node; can scale with many nodes. | Low ( SaaS or self‑hosted) | WireGuard (strong encryption) | Mesh automatically re‑routes; each node maintains multiple paths; high resilience. | Provides **identity‑based** networking (each node gets a IP based on its identity). Fits zero‑trust well because access is governed by node identity, but may not meet the throughput needed for large bulk data transfers (e.g., DB replication). |

**Routing changes needed**

* **DX:** Attach the DX gateway to a **Transit Gateway** or directly to the VPC; propagate routes via BGP. On‑prem routers advertise the corporate network; VPC route tables point to the DX GW for the on‑prem CIDR.  
* **Second VPN:** Create a second `aws_vpn_connection` with identical static routes; enable ECMP on the VPC route table (or use TGW with equal‑cost paths).  
* **Mesh:** Deploy the mesh agent on each workload (EC2, EKS nodes, on‑prem VMs). The mesh creates a virtual interface (e.g., `tailscale0`) with its own IP subnet; you then configure service‑to‑service policies based on those mesh IPs, removing reliance on VPC CIDR for trust.

For a high‑throughput, low‑latency, and operationally simple zero‑trust backbone, **Direct Connect with redundant links** is the best fit; the second VPN is a good fallback if DX cost is prohibitive; mesh is useful for dynamic, developer‑focused environments but not for bulk data replication.

**SC7-A** – Drift sources & dangers

| Source | How it happened | Why it’s dangerous |
|--------|----------------|--------------------|
| **Manual `tofu apply` from laptops** | Engineers ran `tofu apply` directly against the shared S3 state without locking. | Concurrent edits can corrupt the state file (partial writes, lost resources). If state is overwritten, Terraform/OpenTofu may try to recreate existing resources (causing API limits, extra cost) or delete them unintentionally. |
| **Divergent Helm values (staging/prod)** | Values files edited outside Git (e.g., via Helm upgrade `--set` or direct edits). | The cluster drifts from the declared configuration; future Git‑based deploys may overwrite or conflict with the manual changes, leading to unpredictable behavior or silent configuration loss. |
| **`kubectl edit` on ConfigMaps/Secrets** | Admins changed live objects bypassing Git. | Changes are not version‑controlled; they disappear on the next Git‑driven apply (if the resource is managed by Helm/OpenTofu) or cause drift that is hard to audit, leading to configuration‑drift incidents and compliance violations. |

**State‑locking race condition:** Without a lock, two simultaneous `tofu apply` commands can both read the same state, each plan based on stale info, then both attempt to write. The second write overwrites the first, potentially leaving resources in a half‑created state or causing duplicate creations (e.g., two load balancers with the same name). This can produce API throttling, incomplete resources, or orphaned objects.

**SC8-A** – Symptom diagnosis

| Symptom | Likely root cause | Key metrics to verify |
|---------|-------------------|-----------------------|
| **Prometheus OOM every 4 h (64 GB RAM)** | **High cardinality** → many time‑series cause the TSDB head to grow beyond memory. 8.2 M series is well above typical safe limits (~1 M series for 64 GB). | `prometheus_tsdb_head_series`, `prometheus_tsdb_head_chunks_memory_bytes`, `prometheus_tsdb_wal_fsync_duration_seconds_sum`. Look for spikes in series count before OOM. |
| **Loki ingester dropping 15 % of log lines** | Ingester overload → cannot keep up with incoming log rate; likely due to high label cardinality or insufficient ingester replicas. | `loki_ingester_bytes_received_total`, `loki_ingester_failed_to_push_lines_total`, `loki_ingester_inflight_requests`, `loki_ingester_flush_duration_seconds_sum`. High `failed_to_push_lines` indicates drops. |
| **Tempo queries >2 h timeout** | Backend storage or querier overloaded; traces older than 2 h are likely stored in slower/cheaper storage (e.g., local disk) causing high latency. | `tempo_querier_request_duration_seconds_bucket` (look at >2h bucket), `tempo_compactor_completed_buckets_total` (low), `tempo_distributor_push_duration_seconds_sum`. |
| **Thanos compactor 3 days behind** | Insufficient compaction resources (CPU, I/O) relative to incoming block rate; the compactor cannot keep up with the 500 GB/week growth. | `thanos_compactor_compactions_total`, `thanos_compactor_failed_compactions_total`, `thanos_compactor_compaction_duration_seconds_sum`, `thanos_store_gate_series_count`. Rising `failed_compactions` or ever‑increasing `compaction_duration` signals bottleneck. |

**High cardinality explanation:** Each unique combination of metric name + label set creates a separate time series. With many high‑cardinality labels (e.g., `request_id`, `user_id`, `pod_ip`, `container_id`) the series count explodes, consuming memory for the in‑memory index and WAL.  

**Identify top offenders:**  
```bash

jq -r '.data[]' |
while read m; do
  cnt=$(curl -sG "http://prometheus:9090/api/v1/series" --data-urlencode "match[]=${m}" | jq '.data | length')
  echo "$cnt $m"
done | sort -nr | head -20
```
Then for the top metric, examine its label cardinality similarly.

**SC8-B** – Bash cardinality report script

```bash
#!/usr/bin/env bash
set -euo pipefail

PROM_URL="http://prometheus:9090"

# 1. Get all metric names
metric_names=$(curl -s "${PROM_URL}/api/v1/label/__name__/values" | jq -r '.data[]')

echo "Metric Name                | Series Count | Top Label (unique values)"
echo "---------------------------|--------------|--------------------------"

for m in $metric_names; do
  # series count for this metric
  series_cnt=$(curl -sG "${PROM_URL}/api/v1/series" \
    --data-urlencode "match[]=${m}" | jq '.data | length')

  # if series count is zero, skip label inspection
  if [[ $series_cnt -eq 0 ]]; then
    top_label="N/A"
    top_cnt=0
  else
    # get label names for this metric
    label_names=$(curl -sG "${PROM_URL}/api/v1/label/${m}/values" | jq -r '.data[]' 2>/dev/null || true)
    max_label=""
    max_cnt=0
    for lbl in $label_names; do
      # count distinct values for this label
      vals=$(curl -sG "${PROM_URL}/api/v1/label/${lbl}/values" \
        --data-urlencode "match[]=${m}" | jq '.data | length')
      if (( vals > max_cnt )); then
        max_cnt=$vals
        max_label=$lbl
      fi
    done
    top_label="${max_label:-none}"
    top_cnt=$max_cnt
  fi

  printf "%-26s | %-12d | %-20s (%d)\n" "$m" "$series_cnt" "$top_label" "$top_cnt"
done | sort -k3 -nr
```

The script prints a table suitable for copying into Slack, showing each metric, its series count, and the label with the most distinct values (helping spot high‑cardinality culprits).

**SC8-C** – Redesigned observability architecture (target 50 M series, 200 teams)

1. **Metrics** – Replace Prometheus with a **Cortex/Mimir** cluster (horizontal, scalable, multi‑tenant).  
   * Each team gets a dedicated tenant ID; Mimir isolates storage and query paths.  
   * Enable **ingester replication factor = 3** for durability.  
   * Use **compacting and storage** on cheap object storage (S3/GCS) with a **block size** tuned for low write amplification.  
   * Enforce per‑team cardinality limits via **recording rules** that drop or aggregate high‑cardinality labels, and via **relabeling configs** at the scraper level (drop `pod_ip`, `request_id`, etc.).  

2. **Logs** – Deploy **Loki in microservices mode**: separate **write** (ingester) and **read** (querier) rings.  
   * Ingester replicas scale with ingest rate; each ingester writes chunks to object storage.  
   * Use **chunk target size** ~1 MiB and **max age** 1h to keep memory bounded.  
   * Apply **label dropping** at the promoter stage (remove `request_id`, `trace_id`).  

3. **Traces** – Run **Tempo** with a **S3-backed backend** (instead of local disk).  
   * Enable **traceQL** and **block storage** (e.g., 10 MB blocks) for efficient retrieval of older traces.  
   * Configure **querier** and **distributor** with sufficient replicas; enable **compression** (snappy/zstd).  

4. **Governance & chargeback**  
   * Every metric/log/trace is tagged with a **team label** (e.g., `team=frontend`).  
   * Use Mimir/Loki/Tempo’s built‑in **usage reporting** (via `/api/v1/label/team/values` and corresponding series/byte counts) to compute storage and query cost per team.  
   * Integrate with a cost‑allocation tool (e.g., Cloudability, custom billing) to invoice teams based on their consumption.  
   * Enforce **soft limits** via alerting: if a team exceeds its allocated series budget, fire a warning and automatically apply stricter relabeling (drop additional labels) via a sync job that updates the scraper configs.  

5. **Observability pipeline** – Use a **collector** (OpenTelemetry or Fluent Bit) that receives data from services, applies **attribute filtering** (based on allow‑list per team), then forwards to the appropriate backend (Mimir, Loki, Tempo). This keeps the backends clean and ensures that only approved telemetry reaches storage.

With this split‑stack, each team’s telemetry is isolated, cardinality is kept under control, and costs are directly attributable, allowing the platform to scale to 50 M series and hundreds of teams without OOM or query timeouts.

**SC9-C** – Defense‑in‑depth architecture

1. **Authentication**  
   * Rotate all existing API keys; issue new short‑lived JWTs via an OAuth2 Authorization Server (e.g., Auth0, AWS Cognito, or internal Keycloak).  
   * Require `Authorization: Bearer <jwt>` header; validate signature and claims (`sub`, `aud`, `exp`, `scope`).  
   * Keep a **grace period** where both API key (header) and JWT are accepted, then retire keys after a configurable window (e.g., 30 days).  

2. **API Gateway** – Place **AWS API Gateway** (or Kong) in front of the ALB.  
   * Enable **JWT authorizer** (Cognito/JWT) at the gateway level.  
   * Configure **usage plans** with per‑API‑key or per‑JWT rate limits and quotas.  
   * Use **request/response transformation** to strip internal fields, enforce content‑type, and add security headers (`X‑Content‑Type‑Options`, `Strict‑Transport‑Security`).  

3. **WAF** – As defined in SC9‑B (rate‑limit, query‑string block, managed rules, geo‑match).  

4. **Logging & Auditing**  
   * Enable **CloudTrail data events** on the API Gateway (or ALB) to capture every request/response with user identity from the JWT.  
   * Forward logs to a secure SIEM (e.g., Splunk, Elastic) with retention for forensic analysis.  

5. **Data‑level protection**  
   * Enable **field‑level encryption** for PII columns in the database (AWS RDS PostgreSQL `pgcrypto` or AWS KMS‑encrypted columns).  
   * Application decrypts only when needed; ciphertext never leaves the DB in plaintext.  

6. **Deployment & rollout**  
   * Deploy the new OAuth2/JWT flow alongside the legacy API key authentication (dual‑auth mode).  
   * Monitor usage metrics (percentage of requests using JWT).  
   * After a safe period (e.g., 2 weeks), disable API key auth via a feature flag or by removing the middleware.  
   * Provide SDKs/docs to consumers; offer a migration guide and a deprecation timeline.  

This layered approach ensures that even if one control fails (e.g., a JWT is stolen), other controls (WAF rate‑limit, field encryption, least‑privilege IAM) limit the impact.

**SC10-A** – Multi‑cluster DR comparison

| Approach | How it works | RPO feasibility (15 min) | RTO feasibility (1 h) | Comments on 200 TB MinIO |
|----------|--------------|--------------------------|-----------------------|--------------------------|
| **Active‑Passive + Velero** | Periodic Velero backups of etcd + PVCs; restore on DR cluster when needed. | Backup interval determines RPO. To meet 15 min, you’d need **continuous** Velero snapshots (e.g., every 5 min) – Velero can do this but restore time depends on data transfer. Restoring 200 TB MinIO over 10 Gbps ≈ 44 h → **RTO >> 1 h**. | Not acceptable for large object store. Velero works well for etcd & small PVCs, but not for bulk object storage. |
| **Active‑Active (service‑mesh)** | Both clusters run workloads simultaneously; stateful components are replicated synchronously or near‑synchronously across sites. | **PostgreSQL** – Patroni with synchronous commit → RPO ≈ 0 s. <br>**Redis** – Redis Enterprise CRDT or Redis‑Sentinel with active‑active geo‑replication → sub‑second RPO. <br>**RabbitMQ** – Federation with mirrored queues → near‑real‑time (< 1 s). <br>**MinIO** – Site‑replication (async) but can be tuned for < 5 s latency over 10 Gbps; with WAN‑optimized replication you can achieve **RPO < 15 s**. | Failover is essentially DNS switch + automatic promotion of primaries; **RTO ≈ seconds‑to‑minutes** (DNS TTL + service‑mesh re‑routing). Well within 1 h. | Active‑Active meets both RPO/RTO if you use synchronous/near‑synchronous replication for the stateful stores and a fast site‑replication for MinIO. |

**Conclusion:**  
*Active‑Active with a service mesh (Istio multi‑cluster or Cilium Cluster Mesh) is the only viable option to satisfy RPO ≤ 15 min and RTO ≤ 1 h given the 200 TB MinIO dataset.* Velero‑based passive DR would fail the RTO due to the massive restore window.

**SC10-C** – Automated failover orchestration

1. **Failure detection**  
   * Deploy a **heartbeat** service (e.g., `blackbox_exporter` TCP probe or a simple `keepalived` VRRP) in each site that checks:  
     - VPN tunnel status (BGP peer up).  
     - API server health (`/readyz` on the Kubernetes API).  
     - Patroni leader status via `curl http://<patroni>:8008/leader`.  
   * If **any** of the following persists > 30 s: VPN down, Kubernetes API unreachable, Patroni reports no leader → trigger site‑down event.  
   * Use a **quorum** (etcd or Consul) to avoid false positives: require at least 2/3 of sites to agree.

2. **DNS failover**  
   * Use **Route 53** (or equivalent) with a **failover routing policy** (primary = Chicago, secondary = Dallas). Health checks point to the site’s Virtual IP or Ingress controller.  
   * TTL set to **30 s** (or lower) so clients re‑resolve quickly after failover.

3. **Patroni promotion**  
   * The Patroni leader in Dallas automatically detects loss of the Chicago leader (via etcd lease) and promotes itself to leader (synchronous commit ensures no data loss).  
   * Verify with `curl http://patroni-dallas:8008/leader`.

4. **Redis Sentinel failover**  
   * Sentinel monitors the primary; upon loss, it promotes a replica and reconfigures clients.  
   * Ensure `down-after-milliseconds` and `failover-timeout` are tuned (< 10 s) to meet RTO.

5. **RabbitMQ**  
   * Use **federation** or **shovel** with **policy ha-mode: all** and **automatic-health-checks**.  
   * When the primary node disappears, the federated link from the DR site begins consuming messages; mirrored queues ensure no loss.  
   * Enable **prometheus rabbitmq_exporter** to alert on unsynced nodes.

6. **MinIO site replication**  
   * MinIO is configured with **remote site replication** (active‑passive) using the `mc admin bucket remote add` command.  
   * The replication agent continuously syncs objects; lag is monitored via `mc admin info`.  
   * Upon site failure, the DR site continues serving reads/writes; any objects not yet replicated are queued and will be pushed once the link recovers (ensuring eventual consistency; with 10 Gbps and WAN‑optimized sync, lag stays < 15 s).

7. **Update OpenTofu/Terraform state**  
   * After promotion, run a **targeted refresh**: `terraform refresh -target=aws_rds_cluster.primary` (or the equivalent Kubernetes resources) to reconcile state with the new endpoints.  
   * If using a **Terraform workspace** per site, simply switch the workspace to `dr` and run `terraform apply` to update any site‑specific resources (e.g., DNS records, SG rules).  
   * No destroy/recreate is needed because the underlying ARNs/IDs stay the same (the promoted replica retains its identifier).

8. **Split‑brain prevention**  
   * The **etcd** (or Consul) cluster used as the DCS for Patroni requires a majority quorum; with two sites you add a **witness** node in a third location (or use a tie‑breaker).  
   * This ensures only one side can achieve leader status when the link is partitioned.  
   * Additionally, enable **fencing** (e.g., `stonith` via IPMI or cloud provider API) to power‑off the losing side if dual‑primary is detected.

9. **Failback (Chicago recovery)**  
   * Once Chicago’s infrastructure is healthy, re‑establish the VPN and verify etcd quorum.  
   * Patroni will automatically **re‑sync** the former primary as a standby (streaming replication).  
   * When lag catches up to zero (checked via `pg_stat_replication`), you can **swap** the leader back: either let Patroni do an automatic failover (if you set `synchronous_standby_names` to favor Chicago) or manually trigger a failover via `patronictl failover`.  
   * Update DNS failover policy back to primary=Chicago after confirming health and replication lag < threshold.  
   * Monitor application metrics and run smoke tests before declaring full cutback.

This orchestration yields **sub‑second detection**, **DNS‑based client redirection within ~30 s**, **near‑instantaneous promotion of stateful layers**, and **eventual consistency for object storage**, comfortably meeting the 15‑minute RPO and 1‑hour RTO requirements.
