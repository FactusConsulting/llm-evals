## Cloud Infrastructure Architecture

**CL1** — **IaaS** (Infrastructure as a Service) provides raw computing resources (VMs, storage, networking); you manage the OS and apps. **PaaS** (Platform as a Service) provides a framework for developers to deploy code without managing underlying infrastructure. **SaaS** (Software as a Service) provides a finished application over the internet. *Examples: AWS EC2 (IaaS), Google App Engine (PaaS), Microsoft 365 (SaaS).*

**CL2** — The provider manages the physical infrastructure (hardware, cooling, physical security).
- **IaaS VMs:** Provider manages hardware/hypervisor; You manage OS, middleware, runtime, and data.
- **Managed Kubernetes:** Provider manages the Control Plane and Master nodes; You manage worker nodes, pods, and configurations.
- **SaaS (M365):** Provider manages almost everything; You manage user access, data, and device configuration.

**CL3** — **VPC:** Isolated private network. **Subnet:** A range of IP addresses within a VPC. **Security Group:** Statefull firewall for instances (host-level). **NACL:** Stateless firewall for subnets (network-level).
*Layering:* Traffic hits NACL (Inbound) $\rightarrow$ Security Group $\rightarrow$ Instance $\rightarrow$ Security Group (Outbound) $\rightarrow$ NACL (Outbound).
*Stateful:* Remembers connection state (if inbound is allowed, outbound is automatically allowed). *Stateless:* Every packet is evaluated independently.

**CL4** — **Landing Zone:** A pre-configured, multi-account environment with baseline security. **OUs:** Grouping accounts by function (Prod, Dev, Shared). **Guardrails:** Service Control Policies (SCPs) to prevent non-compliant actions. **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) connects VPCs/VNets to a central hub. **Centralized Logging:** Sending all logs (CloudTrail, Flow Logs) to a dedicated security account.
*Single-account problem:* Lack of blast radius isolation, difficult permission management (IAM limits), and lack of organizational structure.

**CL5** — **IaC:** Managing infrastructure via machine-readable files.
- **Terraform/OpenTofu:** Provider-agnostic, HCL language, state-file based. *Best for multi-cloud.*
- **Pulumi:** General-purpose languages (Python, TS). *Best for complex logic/dev-centric teams.*
- **CloudFormation/Bicep:** Native to AWS/Azure. *Best for deep integration with native features.*
- **Crossplane:** Kubernetes-native IaC. *Best for teams already running everything on K8s.*

**CL6** — **HPA:** Scales pods based on CPU/RAM. **VPA:** Adjusts pod resource limits/requests. **Cluster Autoscaler:** Adds/removes physical nodes. **KEDA:** Event-driven autoscaling (e.g., scale based on RabbitMQ queue length).
*KEDA vs HPA:* Use KEDA when scaling needs to be triggered by external metrics (queues, streams, databases) rather than just resource consumption.

**CL7** — **RPO:** Max data loss; **RTO:** Max downtime.
- **Active-Active:** Traffic to both regions; lowest RTO/RPO; highest cost/complexity.
- **Active-Passive:** Traffic to one; failover to second.
- **Replication:** Sync (zero data loss, high latency) vs Async (low latency, potential data loss).
- **DNS:** Route53/Traffic Manager health checks for automated failover.
- **DR Types:** *Pilot Light* (only DB running); *Warm Standby* (scaled-down version of app running); *Multi-site Active-Active* (full capacity in both).

**CL8** — **GitOps:** Infrastructure state is defined in Git; automated agents sync the cluster to that state.
- **ArgoCD:** Pull-based, UI-heavy, great for K8s. **FluxCD:** Pull-based, CLI-centric, highly modular.
- **Secrets:** *Sealed Secrets* (encrypted in Git), *External Secrets* (pulls from Vault/AWS SM), *Vault* (centralized secret engine).
- **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and overwrites the manual change to match the Git "Source of Truth."

**CL9** — **StatefulSet:** Ensures stable network IDs and ordered deployment. **PV/PVC with Local Storage:** Provides low-latency NVMe/SSD access. **Headless Service:** Allows direct pod IP access for peer discovery. **Init Containers:** Run setup scripts (config checks) before the app starts. **ConfigMaps:** Mounted as volumes for config files. **PDBs:** Ensure a minimum number of pods remain available during updates.

**CL10** — **Service Account:** Identity for a process/pod. **Workload Identity:** General term for non-human identity. **IRSA:** AWS-specific way to map a K8s Service Account to an IAM Role.
*Bad Practice:* Mounting static JSON keys in pods risks theft if the pod is compromised. *Workload Identity Federation:* Uses OIDC to exchange a K8s token for a short-lived cloud provider token, eliminating long-lived secrets.

**CL11** — **Object (S3):** Key-value storage for unstructured data (images, logs). High durability (11 9s). **Block (EBS):** Raw volumes for OS/Databases. Low latency, high IOPS. **File (EFS):** Shared filesystem for multiple instances.
*Use Case:* S3 for backups, EBS for DBs, EFS for shared web assets/home directories.

**CL12** — **Zero-Trust:** "Never trust, always verify."
- **Network Policies:** L3/L4 pod isolation. **Service Mesh (Istio/Linkerd):** mTLS for L7 encryption/identity. **Pod Identity:** Unique identities per pod. **Admission Controllers:** Policy enforcement (OPA). **Image Signing:** Cosign/Notary. **Runtime Security:** Falco for syscall monitoring. **Secrets:** HashiCorp Vault.
*Difference:* Traditional security relies on a "hard shell" (firewall) and "soft center." Zero-trust assumes the network is already compromised and requires identity-based auth for every request.

**CL13** — **CDN:** A distributed network of proxy servers that cache content closer to users.
*How it works:* User requests content $\rightarrow$ Edge server checks cache $\rightarrow$ If miss, fetches from origin and caches.
*Services:* CloudFront, Cloudflare. *Use CDN when:* You have high-traffic static assets or need to reduce latency for global users.

**CL14** — **Region:** A geographic area (e.g., us-east-1). **Availability Zone (AZ):** One or more discrete data centers within a region.
*Why Multi-AZ:* Protects against data center failure (power, fire, flood).
*Zonal vs Regional:* Zonal resources (EC2, EBS) are tied to one AZ. Regional resources (S3, DynamoDB, IAM) are replicated across all AZs automatically.

**CL15** — **Managed Database:** A service where the provider handles patching, backups, high availability, and scaling.
*Operational Tasks:* Provider handles OS patching, DB engine updates, automated failover, point-in-time recovery, and hardware maintenance. You only manage schema, queries, and user permissions.

**CL16** — **Users:** People. **Groups:** Collections of users. **Roles:** Temporary identities for services/applications. **Policies:** JSON documents defining permissions.
*Least Privilege:* Grant only the minimum permissions required to perform a task. *Application:* Use Roles for EC2/Lambda instead of Users; use scoped policies (e.g., `s3:PutObject` only on one specific bucket).

**CL17** — **Serverless:** Event-driven execution where the provider manages all infrastructure.
- **Lambda/Functions:** Similar, but differ in execution limits, triggers, and pricing.
- **Cold Starts:** Latency when a function is invoked after being idle (container must spin up). Matters for real-time APIs.
- **Poor Fit:** Long-running processes (>15 mins), high-frequency constant traffic (cheaper on VMs), or apps requiring specific OS kernels.

**CL18** — **Ingress:** Standard K8s resource for L7 routing. **Gateway API:** The successor to Ingress, offering more expressive routing (multitenancy, traffic splitting). **Cloud LB Annotations:** Direct integration with AWS NLB/ALB. **Service Mesh Gateway:** Handles mTLS and advanced traffic shaping.
*TLS Termination:* Ingress/Gateway usually terminates TLS at the edge. Service Mesh can terminate it at the sidecar.
*Gateway API vs Ingress:* Use Gateway API for complex routing, multiple hosts/ports on one IP, and better separation of concerns (Infrastructure vs App teams).

**CL19** — **Strategy:**
- **Savings Plans/RIs:** For predictable, baseline workloads. **Spot:** For fault-tolerant, batch processing.
- **Right-sizing:** Use CloudWatch/Azure Monitor to downsize over-provisioned instances.
- **Storage Tiering:** Move old logs to S3 Glacier.
- **FinOps:** Implement "Showback" (reporting costs to teams) and "Chargeback" (billing teams).
- **Tools:** AWS Cost Explorer, CloudHealth, or Kubecost for K8s visibility.

**CL20** — **Multi-cloud Strategy:**
- **Abstraction:** Use Kubernetes as the common compute layer.
- **IaC:** Use Terraform to manage both providers.
- **Networking:** Site-to-Site VPN or Megaport/Equinix Fabric for interconnect.
- **Identity:** Use OIDC/SAML for federated identity.
- **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs.
- **Justification:** Only justified for regulatory compliance, extreme high availability, or specific "best-of-breed" service requirements. Otherwise, it is unnecessary complexity.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** A structural model for ICS network segmentation.
- **Level 0:** Physical Process (Sensors, Actuators).
- **Level 1:** Basic Control (PLCs, RTUs).
- **Level 2:** Area Control (HMIs, SCADA).
- **Level 3:** Site Operations (Historians, Engineering Workstations).
- **Level 4/5:** Enterprise Network (Business IT, Internet).

**OT2** — **IT:** Focuses on Confidentiality, Integrity, Availability (CIA). **OT:** Focuses on Safety, Reliability, Availability (AIC).
*Patching:* You cannot patch OT systems frequently because they require 99.999% uptime. A reboot could stop a production line or cause a physical safety hazard.

**OT3** — **IDMZ:** A buffer zone between IT and OT.
*Traffic:* Only proxied traffic (e.g., Historian data, Jump Host sessions) should cross.
*Direction:* Generally, OT should never initiate a connection to IT.
*Danger:* Direct Level 4 to Level 1 connectivity allows a compromised office laptop to send a "Stop" command directly to a PLC, bypassing all security controls.

**OT4** — **1. Modbus TCP:** Level 1 (Control). **2. OPC UA:** Level 2/3 (SCADA/Historian). **3. EtherNet/IP:** Level 1 (Control). **4. PROFINET:** Level 1 (Control). **5. MQTT:** Level 3/4 (Data transport to Cloud/Enterprise).

**OT5** — **Firewall:** Software-based, allows bidirectional traffic based on rules. **Data Diode:** Hardware-based, physically allows data to flow in only one direction (e.g., OT $\rightarrow$ IT).
*Use Case:* Use a diode for high-security environments where you must ensure no signal can ever return to the control network.
*Limitation:* Diodes break TCP handshakes; they are "one-way" and cannot support standard two-way communication.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server (Level 2) $\rightarrow$ Edge Gateway (Level 3) $\rightarrow$ MQTT Broker (Level 3) $\rightarrow$ Cloud Ingestion.
*Boundaries:* Place a firewall between Level 3 and Level 4. Place an IDMZ between the Edge Gateway and the Cloud. Use a Data Diode if the cloud connection is high-risk.

**OT7** — **Zones:** Group of assets with similar security requirements. **Conduits:** Defined paths for communication between zones.
*Design:*
- **Zone 1:** Corporate (IT).
- **Zone 2:** Engineering (Workstations).
- **Zone 3:** Control (SCADA/HMIs).
- **Zone 4:** Process (PLCs).
- **Zone 5:** Safety (SIS).
*Conduits:* Firewalls/Diodes between every zone. SIS must have a dedicated conduit to the control room only.

**OT8** — **Strategy:**
- **VLANs:** Separate Production Lines, HMIs, and SCADA.
- **Firewalls:** Place Industrial Firewalls between the IDMZ and the Plant Floor.
- **Switching:** Use managed industrial switches with Port Security.
- **Remote Access:** Use a Jump Host in the IDMZ with MFA.
- **Transition:** Implement "Parallel Infrastructure." Build the new segmented network and migrate one production line at a time during scheduled maintenance windows.

**OT9** — **SIS:** Independent system to take the plant to a safe state in emergencies. **BPCS:** Day-to-day control. **IEC 61511:** Standard for functional safety.
*Isolation:* SIS must be isolated because if a BPCS/IT compromise allows an attacker to disable the SIS, they can cause physical destruction or loss of life.
*Ransomware:* If it reaches the SIS, the plant loses its "emergency brake," potentially leading to catastrophic physical failure.

**OT10** — **PLC:** Localized control of a specific machine/process. **DCS:** Distributed control of a large, continuous process (e.g., Oil Refinery). **SCADA:** Supervisory control over geographically dispersed assets (e.g., Water Grid).
*Coexistence:* Yes, they often coexist. A refinery might use a DCS for the main process and PLCs for specific sub-systems.

**OT11** — **Architecture:** Corporate $\rightarrow$ MFA $\rightarrow$ VPN $\rightarrow$ IDMZ Jump Host $\rightarrow$ OT Network.
*Requirements:* Session recording (for auditing), time-limited access (Just-in-Time), and vendor-specific accounts.
*Why no RDP:* Direct RDP allows an attacker to bypass the IDMZ and gain direct control of the HMI, which can be used to manipulate physical processes.

**OT12** — **Detection:** Deploy passive IDS (e.g., Dragos, Nozomi) to monitor for anomalous Modbus/S7 traffic.
**Response:** 1. Identify the compromised VPN endpoint. 2. Isolate the affected Level 3 segment. 3. Coordinate with operators to switch to manual control if necessary. 4. Verify SIS integrity.
*Operator Role:* The operator is the "Human in the Loop." They must verify that the cyber-incident isn't causing a physical process deviation and can initiate manual emergency shutdowns.

**OT13** — **HMI:** A dashboard for operators to monitor and control the process (e.g., "Start Pump" button).
*Difference:* An **Engineering Workstation** is used to program the PLCs and configure the network; it has much higher privileges and is usually kept offline or in a highly restricted zone.

**OT14** — **Historian:** A database optimized for time-series data (pressure, temp over time).
*Importance:* Used for trend analysis, regulatory reporting, and process optimization.
*Plant vs. Enterprise:* Plant Historian (Level 3) stores high-frequency raw data for local control. Enterprise Historian (Level 4) stores aggregated, filtered data for business KPIs and long-term storage.

**OT15** — **Ladder Logic:** A programming language that resembles electrical relay logic diagrams.
*Device:* Executed by a **PLC**.
*Dominance:* It is intuitive for electricians/technicians to troubleshoot, and it has been the industry standard for 40+ years, making it highly reliable and well-understood.

**OT16** — **RTU:** A ruggedized device that collects data from remote locations (e.g., a pipeline 50 miles away).
*Difference:* RTUs are designed for low-bandwidth, long-distance communication and harsh environments; PLCs are designed for high-speed, local machine control.
*Deployment:* RTUs are used in oil/gas pipelines, water distribution, and power grids.

**OT17** — **Analog:** Continuous values (e.g., 4-20mA). **Digital:** On/Off states (e.g., 0V/24V).
*Why 4-20mA:* The "4mA" represents a "Live Zero." If the wire breaks, the signal drops to 0mA, allowing the system to detect a "Wire Break" fault. If 0-20mA were used, a broken wire would look like a valid "Zero" reading.

**OT18** — **Asset Inventory:** You cannot protect what you don't know exists.
*Tools:* **Passive Monitoring** (sniffing traffic) is preferred as it has zero impact on the process. **Active Scanning** (pinging/querying) is dangerous because old PLCs can crash when receiving unexpected packets.

**OT19** — **MITRE ATT&CK for ICS:**
- **Inhibit Response Function:** (e.g., "Disable Safety System").
- **Impair Process Control:** (e.g., "Modify PLC Logic").
- **Persistence:** (e.g., "Modify Firmware").
- **Discovery:** (e.g., "Network Scanning").
- **Initial Access:** (e.g., "Spearphishing").
*Difference:* ICS focuses on physical impact (kinetic effects). Use it to map "Conduits" and identify where you lack visibility into PLC logic changes.

**OT20** — **SOC Design:**
- **Log Collection:** Use unidirectional gateways or passive taps to send logs to the SIEM without allowing any traffic back into the OT network.
- **Staffing:** Need "OT-aware" analysts who understand that a "PLC Stop" command might be a legitimate maintenance action, not an attack.
- **Firmware Alert:** If unauthorized firmware is detected, the SOC must immediately notify the Plant Manager. The response is *not* to automatically block the port (which could crash the process), but to initiate a physical inspection and manual override.
