## Application Architecture

**AA1 — Easy:** A monolith is a single unified unit where all components (UI, business logic, data access) share the same memory and resources. Microservices decompose the application into small, independent services communicating over a network.
*Problems introduced by microservices:* 1. Network latency/reliability issues. 2. Distributed transaction complexity (data consistency). 3. Operational overhead (monitoring, deployment, and service discovery).

**AA2 — Easy:** Synchronous communication requires the requester to wait for a response before proceeding (e.g., HTTP/REST). Asynchronous communication allows the requester to continue immediately after sending a message (e.g., RabbitMQ/Kafka).

**AA3 — Medium:** A reverse proxy sits in front of web servers to handle load balancing, SSL termination, and caching (e.g., Nginx). An API Gateway is an application-layer proxy that adds features like authentication, rate limiting, and request transformation.
*Can it replace a reverse proxy?* Technically yes, as an API Gateway is a specialized reverse proxy, but it is often overkill for simple load balancing where a lightweight reverse proxy is more efficient.

**AA4 — Medium:** The Saga pattern manages distributed transactions by executing a sequence of local transactions. If one fails, it executes "compensating transactions" to undo previous steps.
*Choreography:* Each service produces/consumes events; no central coordinator (best for simple workflows).
*Orchestration:* A central "orchestrator" tells each service what to do (best for complex, long-running workflows).

**AA5 — Medium:** CQRS separates read operations (Queries) from write operations (Commands). It is paired with Event Sourcing because Event Sourcing stores the state as a sequence of events; CQRS allows you to project those events into optimized read models (e.g., a SQL table for search, an ElasticSearch index for filtering).
*Problem solved:* It solves the "impedance mismatch" where a single database schema struggles to be optimized for both high-speed writes and complex, multi-join reads.

**AA6 — Medium:** A Circuit Breaker prevents a system from repeatedly trying to execute an operation that is likely to fail.
*States:* Closed (normal), Open (failing, requests blocked), Half-Open (testing if the service is back).
*Difference:* Retries with backoff keep trying a failing request; Circuit Breakers stop the attempts entirely to allow the downstream service to recover. Use both by using a Circuit Breaker to "trip" and a Retry with Backoff for transient blips within the "Closed" state.

**AA7 — Hard:**
1. **Shared DB/Schema:** *Cost:* Lowest. *Security:* Weakest (logical isolation only). *Complexity:* Low. *Noisy Neighbor:* High.
2. **Shared DB/Separate Schema:** *Cost:* Medium. *Security:* Better (schema-level permissions). *Complexity:* Medium. *Noisy Neighbor:* Medium.
3. **Separate DB:** *Cost:* Highest. *Security:* Best (physical isolation). *Complexity:* High (migration/backups). *Noisy Neighbor:* Lowest.

**AA8 — Hard:** Strong consistency ensures all nodes see the same data at the same time; eventual consistency allows nodes to be temporarily out of sync.
*Inventory Architecture:* Use **Strong Consistency**. Use a distributed SQL database (e.g., CockroachDB or Google Spanner) or a relational DB with strict ACID properties. Use the **Reservation Pattern**: "Lock" the inventory in a pending state during the checkout process before final confirmation.

**AA9 — Hard:** A sidecar proxy runs alongside the application container in the same pod/host. In Istio, **Envoy** acts as the data plane (handling actual traffic), while **Istiod** is the control plane (managing configuration/certificates).
*mTLS vs App-level TLS:* Sidecar mTLS provides "Zero Trust" by encrypting all traffic between services automatically without the application code needing to manage certificates or trust stores.

**AA10 — Medium:** Strangler Fig involves placing a proxy (like Nginx or an API Gateway) in front of the monolith. New features are built as .NET 8 microservices. Traffic is routed to the new service for specific endpoints, while the rest goes to the monolith. Over time, the monolith "shrinks" until it can be decommissioned.

**AA11 — Medium:** 12-Factor App: 1. Codebase, 2. Dependencies, 3. Config, 4. Backing Services, 5. Build/Release/Run, 6. Processes, 7. Port Binding, 8. Concurrency, 9. Disposability, 10. Dev/Prod Parity, 11. Logs, 12. Processes.
*Why they matter:* They ensure applications are portable, scalable, and resilient in dynamic cloud environments (e.g., Config separation allows the same image to run in Dev and Prod).

**AA12 — Hard:**
*Coupling:* Event-driven is loosely coupled; Request-driven is tightly coupled.
*Scalability:* Event-driven scales better for high-throughput/asynchronous tasks.
*Debugging:* Request-driven is easier to trace; Event-driven is harder (distributed state).
*Ordering:* Kafka guarantees ordering within a partition; REST/gRPC does not inherently guarantee order across multiple requests.
*Failure:* Event-driven has built-in persistence (retries via queue); Request-driven requires complex retry logic.
*Choice:* Use Request-driven for UI-facing actions (immediate feedback); Event-driven for background processing (emails, analytics).

**AA13 — Easy:** A load balancer distributes incoming traffic across multiple servers.
*Layer 4:* Operates at the Transport layer (TCP/UDP). Fast, but doesn't see URLs/Headers.
*Layer 7:* Operates at the Application layer (HTTP/HTTPS). Can route based on URL paths, cookies, or headers.
*Use Case:* Routing `example.com/api` to one cluster and `example.com/web` to another.

**AA14 — Easy:** A message queue stores messages until a consumer processes them (Point-to-Point). A log-based broker (Kafka) stores messages as an append-only log that can be replayed.
*Pick MQ:* When you need complex routing, individual message acknowledgments, and "delete on read" behavior.
*Pick Kafka:* When you need high throughput, message replayability, and multiple consumers reading the same stream.

**AA15 — Easy:** A container shares the host OS kernel and isolates the application process. A VM includes a full guest OS.
*Popularity:* Containers are lightweight, start in milliseconds, and ensure "it works on my machine" consistency across environments.

**AA16 — Easy:** Stateless services do not store client data (session/state) locally; every request contains all info needed. Stateful services store data (e.g., a database or a game server).
*Scaling:* Stateless is easier because any instance can handle any request.
*Examples:* Stateless: A REST API. Stateful: A Redis instance or a WebSocket server.

**AA17 — Easy:** An ORM maps database tables to objects in code. Examples: Hibernate (Java), SQLAlchemy (Python).
*Trade-offs:* ORMs provide speed of development and abstraction; Raw SQL provides maximum performance, precise control over complex joins, and easier optimization.

**AA18 — Medium:** The Bulkhead pattern isolates resources so that a failure in one part of the system doesn't exhaust resources for the rest.
*Implementation:* Use separate thread pools for different downstream services (e.g., Service A gets 10 threads, Service B gets 10 threads). If Service B hangs, Service A still has its threads available.

**AA19 — Hard:**
*OT:* Transforms operations based on concurrent edits. Good for low latency but very complex to implement for many users.
*CRDTs:* Data structures that merge automatically without a central coordinator. Better for offline support and high availability.
*Choice:* For offline editing, **CRDTs** are superior because they allow users to make changes independently and merge them mathematically without needing a constant connection to a central "truth" server to resolve conflicts.

**AA20 — Hard:**
*Context Propagation:* Passing Trace IDs through headers (W3C Trace Context).
*Sampling:* Head-based (decide at start) is cheaper; Tail-based (decide at end) is better for capturing errors/high-latency traces.
*Kafka Continuity:* Inject the Trace ID into the Kafka message header. The consumer must extract this header and start a new span linked to the producer's span.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** Type 1 runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V). Type 2 runs on an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2 — Easy:** SAN (Storage Area Network) provides block-level storage (like a local disk over a network). NAS (Network Attached Storage) provides file-level storage.
*Use Case:* SAN for databases (high performance); NAS for file shares/media.
*Protocols:* SAN (Fibre Channel, iSCSI); NAS (NFS, SMB).

**OP3 — Medium:** 3-tier: Core (high-speed switching), Distribution (policy/routing), Access (end-device connection).
*Leaf-Spine:* Every Leaf switch connects to every Spine switch.
*Problem solved:* It provides predictable, low-latency "east-west" traffic (server-to-server) and eliminates the STP (Spanning Tree Protocol) bottlenecks found in 3-tier designs.

**OP4 — Medium:**
*Nodes:* Minimum 3 for quorum.
*Quorum:* Majority vote to prevent split-brain.
*Fencing:* STONITH (Shoot The Other Node In The Head) to power off failed nodes.
*Storage:* Ceph (distributed) or iSCSI (centralized).
*Failure:* If a node fails, the cluster detects it, fences the node, and the remaining nodes re-mount the shared storage/re-start VMs.

**OP5 — Medium:** VLAN trunking allows multiple VLANs to travel over one physical link. 802.1Q adds a "tag" to the Ethernet frame.
*Linux Config:* Use "Router on a Stick" or sub-interfaces (e.g., `eth0.10`, `eth0.20`) using the `ip link` command or Netplan/NetworkManager.

**OP6 — Medium:** RAID 1 (Mirror), 5 (Parity), 6 (Dual Parity), 10 (Mirror+Stripe), Z2 (ZFS Dual Parity).
*Choice:* **RAID 10**. With 6 drives, RAID 10 provides the best balance of high IOPS (striping) and fast rebuild times (mirroring) for a database, though it sacrifices 50% capacity.

**OP7 — Hard:**
*Architecture:* Internal AD DNS servers (Authoritative) -> Forwarders -> External DNS (Google/Cloudflare).
*Split-Horizon:* Internal users see `internal.corp`, external see `public.com`.
*VPN:* Use Conditional Forwarding; the VPN gateway forwards internal queries to the corporate DNS.
*DNSSEC:* Signs the external zone to prevent spoofing.

**OP8 — Hard:** Root CA (Offline) signs Subordinate CA, which signs End-Entity certificates.
*CRL:* List of revoked certs. *OCSP:* Real-time check of revocation.
*Compromise:* Root CA compromise = total trust collapse (must re-issue everything). Subordinate CA compromise = only certificates issued by that specific CA are untrusted.

**OP9 — Hard:**
*Comparison:* MPLS (Reliable/Expensive), IPsec (Cheap/Variable), SD-WAN (Smart/Managed), WireGuard (Fast/Modern).
*Recommendation:* **SD-WAN**. It allows for path selection (sending VoIP over the best path), handles 50 users easily, and provides centralized management for multiple sites.

**OP10 — Medium:** Out-of-band (OOB) management allows access to a server's hardware (power, console) even if the OS is crashed.
*Risk:* If exposed to the internet, an attacker can gain full hardware control (reboot, wipe disks, install keyloggers). It must be behind a VPN or a management VLAN.

**OP11 — Medium:**
*LVM:* Logical Volume Management (flexible partitions).
*LVM-Thin:* Allows over-provisioning and snapshots.
*ZFS:* Combined filesystem and volume manager (Copy-on-Write).
*Snapshots:* LVM-Thin (fast, space-efficient), ZFS (atomic, consistent, high-performance). Use ZFS for data integrity; LVM for general volume flexibility.

**OP12 — Hard:**
*Strategy:* Stretch cluster with a 3rd site (Witness/Tiebreaker).
*CRUSH:* Define rules to ensure data replicas are on different sites.
*Latency:* Ceph requires <10ms RTT for synchronous writes.
*Split-Brain:* Without a 3rd site/witness, if the link between Site A and B breaks, both might try to become "Primary," causing data corruption.

**OP13 — Easy:** DHCP assigns IP addresses automatically. DORA: Discover, Offer, Request, Acknowledge.
*Failure:* If the server is down and the lease expires, the client will lose its IP and attempt to renew; if it fails, it may drop off the network or attempt to self-assign an APIPA address (169.254.x.x).

**OP14 — Easy:** Managed switches allow configuration (VLANs, QoS, Port Mirroring, SNMP). Unmanaged are "plug and play."
*Enterprise Importance:* VLANs for security, QoS for prioritizing VoIP/Video, and Port Mirroring for troubleshooting/IDS.

**OP15 — Easy:** NTP synchronizes clocks.
*Criticality:* Logs become useless if timestamps don't match; Kerberos authentication fails if clocks drift >5 mins; database clusters may experience "clock skew" errors during replication.

**OP16 — Easy:** Physical (Hardware), VM (Hardware abstraction), Container (OS abstraction).
*Bare Metal:* Use for high-performance computing (HPC), heavy databases with high IOPS requirements, or workloads where hypervisor overhead is unacceptable.

**OP17 — Easy:** UPS provides immediate battery power (seconds/minutes); Generator provides long-term power (hours).
*ATS:* Automatically switches the power source from the grid to the generator when the UPS detects a power loss.

**OP18 — Medium:** Active-Passive (one standby) vs Active-Active (both serve traffic).
*PostgreSQL HA:* Use Pacemaker/Corosync. Corosync handles cluster membership; Pacemaker manages resources. Use STONITH to ensure a failed node is actually off before promoting the standby to avoid split-brain.

**OP19 — Hard:**
*3-2-1:* 3 copies, 2 media types, 1 offsite.
*RPO/RTO:* RPO (how much data can we lose?), RTO (how fast must we be back up?).
*Immutable:* Backups that cannot be deleted/encrypted by ransomware (e.g., S3 Object Lock).
*Difference:* Backup is a copy of data; Disaster Recovery (DR) is the *process* and infrastructure to restore operations after a catastrophe.

**OP20 — Hard:** 802.1X uses a Supplicant (client), Authenticator (switch), and Auth Server (RADIUS).
*EAP-TLS:* Certificate-based (most secure). *PEAP:* Username/Password.
*MAB:* If a device (like a printer) doesn't have an 802.1X supplicant, the switch sends the MAC address to RADIUS; if the MAC is in the allowed list, it's granted access.
