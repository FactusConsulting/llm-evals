## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` is a dry-run operation. It compares the current state against the configuration files and outputs the actions (create, update, delete) that will be taken without making any changes. `tofu apply` executes those actions to reach the desired state.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file that maps real-world resources to your configuration. It tracks metadata, dependencies, and current attributes. Remote state is critical for team collaboration because it provides a "single source of truth," prevents state conflicts (via locking), and ensures that multiple engineers/CI pipelines are working against the same infrastructure.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an integer index to replicate resources. `for_each` uses a map or set of strings to create resources. `for_each` is preferred because it allows you to reference specific instances by a logical key (e.g., `vm["web1"]`) rather than an index (e.g., `vm[0]`). If you remove an item from the middle of a `count` list, all subsequent resources are shifted and destroyed/recreated; `for_each` avoids this.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This is known as "Configuration Drift." During the next `tofu plan`, OpenTofu performs a "refresh" by querying the cloud provider's API. It compares the API response to the state file. If they differ, OpenTofu identifies the drift and proposes an update to bring the resource back into alignment with the configuration.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
variable "vm_names" {
  type    = set(string)
  default = ["web1", "web2", "web3"]
}

resource "aws_instance" "vm" {
  for_each = toset(var.vm_names)
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads the entire state file of another workspace, which can be slow and exposes unnecessary data. Using `outputs` is cleaner but requires the modules to be tightly coupled. The recommended alternative is **Data Sharing via a common State/Key-Value store (like SSM Parameter Store or Consul)** or **Module Composition**, where a single root module calls both sub-modules, passing outputs from one as inputs to the other. This maintains loose coupling and better security.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
**Why:** `remote-exec` runs after the resource is created, but OpenTofu evaluates outputs during the plan/apply phase. If the script hasn't finished or the file isn't written yet, the output is null.
**Fix:** Use a `local-exec` or `remote-exec` inside a `provisioner` block, but more reliably, use a **`local_file` resource** to read the kubeconfig into a file, and then use a **`data` source** or a **`file` resource** to pass that content. Alternatively, ensure the resource producing the config is explicitly linked via a dependency, but the best practice is to avoid `null_resource` for data passing; use a dedicated resource that manages the file.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` brings existing infrastructure into the state file via the CLI. Limitations include manual typing of IDs and the fact that it doesn't generate the HCL code for you. The `import` block (1.5+) allows you to declare the import in code. It allows for "planned imports" where `tofu plan` shows exactly what will happen, and it supports `moved` blocks to simplify the transition.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a placeholder for dynamic values. An **input variable** is a value provided to the configuration (like a VM size). An **output** is a value returned by the configuration after execution (like a Load Balancer's DNS name) to be used by other modules or displayed to the user.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates OpenTofu configuration into API calls for a specific service (AWS, Azure, GCP, etc.). If you run `plan` without `init`, OpenTofu will fail because it hasn't downloaded the necessary provider binaries or initialized the backend configuration.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It is the Dependency Lock File. It records the exact versions and hashes of the providers used. Committing it ensures that every team member and CI/CD runner uses the exact same provider versions, preventing "it works on my machine" errors caused by provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the configuration. To target a single resource, use the `-target` flag: `tofu destroy -target=aws_instance.web_server`.

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source allows you to fetch information from the cloud provider without managing that resource. Example: Fetching the latest Amazon Linux AMI ID. You don't want to manage the AMI (managed resource), you just want to know its ID (data source) to use in your VM configuration.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are inputs provided by the user/environment. Locals are internal constants/expressions used to simplify logic within a module. Use `locals` for values derived from other variables (e.g., constructing a complex naming convention) or for values that should not be changed by the user.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block modifies the behavior of resource creation/destruction.
1. `create_before_destroy`: Ensures a new resource is up before the old one is deleted (e.g., replacing a Load Balancer).
2. `prevent_destroy`: Hard error if an action would delete the resource (e.g., a production database).
3. `ignore_changes`: Prevents OpenTofu from trying to "fix" changes made by external processes (e.g., ignoring tags added by an automated security scanner).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module/address in the code. It updates the state file mapping without actually deleting and recreating the physical infrastructure.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG) of resources.
- **Implicit:** Created when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`).
- **Explicit:** Created using the `depends_on` meta-argument.
`depends_on` forces a specific order but limits parallelism because OpenTofu cannot start the dependent resource until the parent is fully finished. It should be used sparingly because implicit dependencies are cleaner and allow OpenTofu to optimize the execution order automatically.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1. **State Splitting:** Break the state into multiple smaller states (e.g., Network, DB, App). *Tradeoff: Harder to manage cross-state dependencies.*
2. **Targeted Plans:** Use `-target` to plan only specific components. *Tradeoff: Risk of missing side effects/dependencies.*
3. **Provider Caching:** Ensure providers are cached locally. *Tradeoff: Minimal, but requires disk space.*
4. **Use Data Sources:** Instead of managing everything in one state, use data sources to reference existing infra. *Tradeoff: Less "Infrastructure as Code" visibility for those external resources.*

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**
Locking prevents two processes from modifying the state simultaneously. If a process crashes, the lock remains in the backend (e.g., a DynamoDB entry). You can break it using `tofu force-unlock <LOCK_ID>`. **Risks:** If the process is actually still running or partially finished, force-unlocking can lead to state corruption or duplicate resource creation.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.**
1. Create the S3 bucket and DynamoDB table for locking.
2. Configure the `backend "s3"` block in the code.
3. Run `tofu init`. OpenTofu will detect the change and ask to migrate the state.
4. Confirm the migration. OpenTofu will copy the local state to S3.
5. **Verification:** Run `tofu plan`. If it shows "No changes" (assuming code matches state), the migration was successful. The local state file remains but is no longer used.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
- **Task:** A single action (e.g., "install nginx").
- **Playbook:** A list of plays that group tasks together to be run on specific hosts.
- **Role:** A structured way to group tasks, variables, files, and templates into a reusable component.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary of system information gathered by Ansible at the start of a play. You access the OS family using `ansible_facts['os_family']` (e.g., "Debian" or "RedHat").

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
- `command`: Executes a command without a shell (no pipes, redirects, or environment variables). Safest.
- `shell`: Executes a command through the system shell (allows `|`, `>`, `&&`). Use when shell features are needed.
- `raw`: Executes a command via SSH without requiring Python on the target. Use for bootstrapping or very basic systems.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means a task only makes changes if the system is not in the desired state.
- **Idempotent:** `apt: name=nginx state=present` (checks if installed first).
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file` (appends every time the playbook runs).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS
  block:
    - name: Install htop on Debian
      apt: name=htop state=present
      when: ansible_os_family == "Debian"

    - name: Install epel and htop on RedHat
      yum:
        name: [epel-release, htop]
        state: present
      when: ansible_os_family == "RedHat"
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
(Lowest to Highest)
1. Role defaults
2. Inventory (group_vars, host_vars)
3. Playbook variables
4. `set_fact`
5. Extra vars (`-e`) - **Highest priority.**

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**
Use `serial: 3` in the play to ensure only 3 hosts are processed at a time. Group the 50 nodes in an inventory group. Use the `wait_for` module if you need to ensure a specific port (like the K8s API) is open on those 3 nodes before the next batch begins.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` is used to encrypt sensitive data (passwords, keys). To encrypt a single variable, use the `ansible-vault encrypt_string` command to generate an encrypted block, then paste that block into your `vars.yml` file.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory file lists the hosts and groups of servers to manage.
- **Static:** A manual list of IP addresses/hostnames in a file.
- **Dynamic:** A script or plugin that queries a cloud provider (AWS/Azure) to generate the list in real-time.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a task that only runs when "notified" by another task. Unlike regular tasks, they only run once at the end of the play, even if notified multiple times. Triggered by `notify: restart_service`.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
It is the configuration file for Ansible. Common settings: `remote_ interpreters`, `inventory`, and `forks`.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
`register` saves the output of a task into a variable.
Example:
```yaml
- name: Run command
  command: uptime
  register: uptime_output
- name: Print output
  debug: msg="{{ uptime_output.stdout }}"
```

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
- `import_tasks`: Static. Processed at the start of the play. Cannot be used with `when` on the import itself.
- `include_tasks`: Dynamic. Processed at runtime. Can be used with `when` to conditionally include a file.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Ansible Galaxy is a public repository for sharing roles and collections. To use `requirements.yml`, run `ansible-galaxy -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins determine how Ansible connects to the target.
- `ssh`: Standard remote execution over SSH.
- `local`: Runs the command on the control node (e.g., updating local packages).
- `network_cli`: Executes commands via a CLI (e.g., interacting with a Cisco switch via `conf t`).

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
- `delegate_to`: Runs a task on a different host than the current one in the loop.
- `run_once`: Ensures a task runs only once even if the play is targeting multiple hosts.
**Example:** Gathering a public IP from a web server and then running a task on `localhost` to update a DNS record using that IP.
```yaml
- name: Get IP
  shell: curl -s ifconfig.me
  register: remote_ip
- name: Update DNS
  command: update_dns {{ remote_ip.stdout }}
  delegate_to: localhost
  run_once: true
```

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs.**
1. **Forks:** Increase `forks` in `ansible.cfg` to run more tasks in parallel. *Tradeoff: Higher CPU/Memory on control node.*
2. **Pipelining:** Enable `pipelining` to reduce the number of SSH connections. *Tradeoff: Requires specific SSH config.*
3. **Fact Caching:** Use Redis/Memcached to store facts so they aren't re-gathered every run. *Tradeoff: Risk of stale data.*
4. **Mitogen:** Use the Mitogen plugin to replace the standard SSH execution engine. *Tradeoff: Third-party dependency.*

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
- `{{ }}`: Expressions (variables/math).
- `{% %}`: Statements (loops, if-statements).
- `{# #}`: Comments (ignored by Ansible).
**Snippet:**
```nginx
upstream backend {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }} comment "Health check: {{ server.name }}";
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, and health checks with uri module, and rollback strategy on failure using block/rescue.**
1. **Serial:** Use `serial: 2` to update 2 servers at a time.
2. **Pre-task:** Use `uri` module to remove the server from the Load Balancer (LB).
3. **Deployment:** Run the update tasks.
4. **Health Check:** Use `uri` module to verify the app returns `200 OK`.
5. **Post-task:** Re-add the server to the LB.
6. **Rollback:** Wrap the deployment in a `block`. In the `rescue` block, if the health check fails, trigger a task to redeploy the previous version and notify the team.
