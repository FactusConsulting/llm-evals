### SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the **Restricted Pod Security Standard** prohibits containers from running as the `root` user. In the previous **Baseline** standard, containers could run as root by default. Because the new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root` and the manifests lack an explicit `runAsUser`, the pods attempt to start as root. The Restricted policy detects this violation and prevents the container from starting, leading to `CrashLoopBackOff`.

**SC1-B:**
```bash
kubectl get pods --all-namespaces -o json | jq -r '.items[] | select(.status.containerStatuses[].state.waiting.reason=="CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level:** Update the Dockerfile to include a non-root user and `USER <uid>`.
*   **Manifest:** Add `securityContext: { runAsUser: 1000, runAsGroup: 3000, fsGroup: 2000 }` to the Pod spec.
*   **CI Gate:** Add a `conftest` or `kube-linter` step in the pipeline to validate manifests against the Restricted PSA.
*   **Rollout:** Use a **Canary deployment** (e.g., Argo Rollouts). Deploy the fixed version to 10% of traffic, monitor error rates, then scale up.

### SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data occurs because RDS cross-region replicas use **asynchronous replication**. There is a non-zero "replication lag" where transactions committed in `us-east-1` haven't reached `eu-west-1` before the promotion. To quantify data loss, check the `ReplicaLag` metric in CloudWatch and compare the `LSN` (Log Sequence Number) of the last committed transaction in the old primary vs. the new primary.

**SC2-B:**
1. `tofu import aws_db_instance.promoted_replica <RDS_INSTANCE_ID>`
2. Update the HCL to point all resources to the new instance's attributes (or use a variable).
3. `tofu plan` (Verify no "destroy" actions).
4. `tofu apply`
5. `tofu destroy` the old instance (once confirmed decommissioned).

**SC2-C:**
*   **Proxy:** Use **RDS Proxy** for connection pooling (handles failover/pooling better than PgBouncer in managed RDS).
*   **DNS:** Use **Route53 Failover Routing** with health checks.
*   **RPO < 1s:** Use **Aurora Global Database** (storage-level replication is faster/more reliable than standard RDS streaming).
*   **Retry:** Implement exponential backoff in the application.

### SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1. **Local Sessions:** Solution: Move to Redis/Memcached for distributed sessions.
2. **Local NFS:** Solution: Use a CSI driver (EFS/Filestore) with `ReadWriteMany`.
3. **Oracle DB:** Solution: Use a managed DB (RDS) or a Sidecar/Service for connectivity.
4. **IBM MQ:** Solution: Use a dedicated MQ cluster with a persistent connection pool.
5. **Java 11 Memory:** Solution: Configure `Xmx` and `Xms` correctly with K8s `resources.limits`.

**SC4-B:**
```hcl
resource "kubernetes_storage_class" "nfs" {
  metadata { name = "nfs-sc" }
  provisioner = "kubernetes.io/no-provisioner" # Or specific CSI
  parameters = { mount_options = "hard,bg" }
}
# ReadWriteMany is required because multiple pods (replicas) 
# need to access the same upload directory simultaneously.
```

**SC4-C:**
*   **Phase 1:** Move the "Uploads" functionality to K8s (NFS).
*   **Phase 2:** Move "Session Management" to Redis.
*   **Phase 3:** Move the core API logic.
*   **Traffic:** Use **F5 Local Traffic Manager** to split traffic by URL path (e.g., `/api/v2` to K8s).
*   **Rollback:** If p99 latency > 3s or 5xx errors > 1%, flip F5 weights back to 100% legacy.

### SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:**
*   **Identity:** Deploy **SPIRE** agents on all nodes (AWS, Azure, On-prem).
*   **Federation:** Use SPIRE's **Bundle** feature to share trust roots. AWS workloads use IAM Roles to authenticate to the SPIRE server, which issues a SVID (SPIFFE Verifiable Identity Document).

**SC6-B:**
```hcl
resource "aws_transit_gateway" "main" { ... }
resource "aws_ec2_transit_gateway_vpc_attachment" "vpc" { ... }

  for_each = toset(var.services)

}
```

**SC6-C:**
*   **Direct Connect:** Best for consistent, high-bandwidth, low-latency (lowest cost per bit at scale).

*   **Tailscale/Netbird:** Best for "Overlay" zero-trust; handles NAT traversal and identity-based routing natively.
*   **Routing:** Direct Connect requires BGP; Tailscale requires a coordination server/headscale.

### SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:**
*   **Manual Apply:** Bypasses CI checks; state becomes "truth" but code is "lie."
*   **No Locking:** Two engineers running `apply` simultaneously can corrupt the S3 state file (partial writes).
*   **Direct Edit:** Changes are lost on the next `tofu apply` (overwritten by Git state).

**SC7-B:**
```yaml
deploy_prod:
  stage: deploy
  script:
    - tofu fmt -check
    - tofu plan -out=prod.tfplan
    - tofu apply -auto-approve prod.tfplan
  when: manual
  environment: production
  variables:
    LOCK_TABLE: "tofu_locks"
```

**SC7-C:**
*   **Drift Detection:** A scheduled GitLab job running `tofu plan -detailed-exitcode` every hour.
*   **Admission:** **Kyverno** policy to block `UPDATE` on ConfigMaps unless the user is `system:serviceaccount:ci-namespace:gitlab-runner`.
*   **Helm:** Use **Helmfile** with `values.yaml` (base) + `values-prod.yaml` (overrides).
*   **RBAC:** Remove `edit` permissions from humans; only the CI Runner's ServiceAccount has `cluster-admin`.

### SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:**
*   **Prometheus OOM:** High cardinality (too many unique label combinations). Check `count(count by (__name__) ({__name__=~".+"}))`.
*   **Loki Drops:** Ingester buffer full. Check `loki_ingester_head_block_duration_seconds`.
*   **Tempo Timeouts:** Querying too many blocks or slow S3 retrieval. Check `tempo_query_duration_seconds`.
*   **Thanos Lag:** Compactor is bottlenecked by S3 IOPS or CPU. Check `thanos_compactor_blocks_pending`.

**SC8-B:**
```bash
# Simplified logic:
curl -s "http://prometheus:9090/api/v1/label/__name__/values" | jq '.data | keys | length'
# Then query top 20:
curl -s "http://prometheus:9090/api/v1/query?query=topk(20, count by (__name__) (count(__name__)))" | jq .
```

**SC8-C:**
*   **Mimir:** Handles massive cardinality via distributed architecture.
*   **Loki Microservices:** Separate "Write" (Ingesters) and "Read" (Queriers) paths.
*   **Governance:** Use **Recording Rules** to aggregate high-cardinality metrics into low-cardinality ones.
*   **Chargeback:** Use `label_replace` to inject `team_id` into all metrics; query Prometheus for `sum(count_over_time(...))` grouped by `team_id`.

**SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform**

**SC10-A:**
*   **Architecture:** **Active-Passive** with **Velero** is safer for RPO/RTO given 200TB of data (replication of 200TB over 12ms latency is heavy).
*   **RPO/RTO:** 15m RPO is achievable with **MinIO Site Replication**. 1h RTO is achievable with automated DNS failover.
*   **Stateful:** PostgreSQL (Patroni/Streaming), Redis (Sentinel), RabbitMQ (Federation), MinIO (Active-Passive Replication).

**SC10-B:**
```yaml
- name: Configure Patroni
  template:
    src: patroni.yml.j2
    dest: /etc/patroni.yml
  vars:
    synchronous_standby_names: "{" {replica_1}"
    replication_slots: true
  notify: Restart Patroni
```

**SC10-C:**
1. **Detection:** Route53 Health Checks + Prometheus Alertmanager.
2. **Failover:** 
    *   Route53 updates DNS to Dallas.
    *   Patroni promotes Dallas primary.
    *   Redis Sentinel elects new master in Dallas.
    *   RabbitMQ Federation redirects traffic.
3. **Split-Brain:** Use a **Quorum-based** DCS (etcd) across 3 sites (Chicago, Dallas, and a 3rd "Witness" site) to ensure only one site can be primary.
4. **Failback:** Stop Dallas traffic -> Sync data back to Chicago -> Promote Chicago -> Update DNS.
