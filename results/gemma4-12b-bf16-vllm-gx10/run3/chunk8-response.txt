## Cloud Infrastructure Architecture

**CL1** — **IaaS** (Infrastructure as a Service) provides raw computing resources (VMs, storage, networking); you manage the OS and apps. **PaaS** (Platform as a Service) provides a framework for developers to deploy code without managing underlying infra. **SaaS** (Software as a Service) is a finished software product delivered over the web. *Examples: AWS EC2 (IaaS), Google App Engine (PaaS), Microsoft 365 (SaaS).*

**CL2** — The provider manages the physical "Security of the Cloud" (hardware, global infra). You manage "Security in the Cloud" (data, OS, config).
*   **IaaS VMs:** Provider manages hardware/hypervisor; You manage OS, patching, and apps.
*   **Managed K8s:** Provider manages the Control Plane; You manage worker nodes, pods, and networking.
*   **SaaS (M365):** Provider manages almost everything; You manage user identities, data permissions, and device endpoints.

**CL3** — **VPC:** Isolated private network. **Subnet:** Range of IP addresses within a VPC. **Security Group:** Statefull firewall for instances (allow/deny rules). **NACL:** Stateless firewall for subnets.
*   **Layering:** VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group.
*   **Stateful:** Remembers return traffic (SG). **Stateless:** Every packet is evaluated individually (NACL).

**CL4** — **Landing Zone:** A pre-configured multi-account environment with baseline security. **OUs:** Grouping accounts by function (Prod, Dev, Shared). **Guardrails:** Service Control Policies (SCPs) to prevent non-compliant actions. **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) connects VPCs/VNets to a central hub. **Centralized Logging:** Sending all logs to a dedicated "Log Archive" account.
*   **Single-account problem:** Lack of blast radius isolation, hitting service limits, and difficulty in granular IAM permissioning.

**CL5** — **IaC:** Managing infra via machine-readable files.
*   **Terraform/OpenTofu:** Provider-agnostic, HCL language, state-file based. Best for multi-cloud.
*   **Pulumi:** General-purpose languages (Python, TS). Best for complex logic/loops.
*   **CloudFormation/Bicep:** Native to AWS/Azure. Best for deep integration with native features.
*   **Crossplane:** Kubernetes-native IaC. Best for managing cloud resources via K8s APIs.

**CL6** — **HPA:** Scales pods based on CPU/RAM. **VPA:** Adjusts pod resource limits/requests. **Cluster Autoscaler:** Adds/removes physical nodes. **KEDA:** Event-driven scaling (e.g., scale based on RabbitMQ queue length).
*   **KEDA vs HPA:** Use KEDA when scaling based on external metrics (queues, streams, DB sizes) that HPA cannot natively "see."

**CL7** — **RPO:** Max data loss; **RTO:** Max downtime.
*   **Active-Active:** Traffic to both regions (lowest RTO/RPO, highest cost).
*   **Active-Passive:** Standby region (lower cost, higher RTO).
*   **Replication:** Sync (zero data loss, high latency) vs Async (low latency, potential data loss).
*   **DNS:** Route53/Traffic Manager health checks for failover.
*   **DR Types:** *Pilot Light* (only DB running), *Warm Standby* (scaled-down app running), *Multi-site Active-Active* (full capacity in both).

**CL8** — **GitOps:** Infrastructure state is defined in Git; automated agents sync the cluster.
*   **ArgoCD vs FluxCD:** ArgoCD has a rich UI and "pull" model; FluxCD is more "git-native" and lightweight.
*   **Secrets:** *Sealed Secrets* (encrypted in Git), *External Secrets* (pulls from Vault/AWS SM), *Vault* (centralized secret engine).
*   **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and overwrites the manual change to match Git.

**CL9** — **StatefulSet:** Ensures stable network IDs and ordered deployment. **PV/PVC with Local Storage:** Provides low-latency NVMe/SSD access. **Headless Service:** Allows direct pod IP access for peer discovery. **Init Containers:** Run pre-flight checks or config setup. **ConfigMaps:** Mounted as volumes for config files. **PDBs:** Ensure a minimum number of pods remain available during updates.

**CL10** — **Service Account:** Identity for a K8s pod. **Workload Identity:** Cloud-native identity for a specific workload. **IRSA:** AWS-specific way to map K8s Service Accounts to IAM Roles.
*   **Bad Practice:** Mounting static JSON keys in pods (risk of theft).
*   **Workload Identity Federation:** Uses OIDC to exchange a K8s token for a short-lived cloud provider token, eliminating long-lived secrets.

**CL11** — **Object (S3):** Key-value storage for unstructured data (images, logs). High durability (11 9s). **Block (EBS):** Raw volumes for OS/Databases. Low latency. **File (EFS):** Shared filesystem for multiple instances.
*   **Durability:** Object storage usually offers highest durability; Block is tied to a specific instance/zone.

**CL12** — **Zero-Trust:** "Never trust, always verify."
*   **Components:** Network Policies (L3/4), Service Mesh (mTLS/L7), Pod Identity (no shared keys), OPA/Kyverno (policy enforcement), Image Signing (Cosign), Falco (runtime threat detection).
*   **Difference:** Traditional security relies on a "hard shell" (firewall) and "soft center." Zero-trust assumes the network is already compromised and requires identity-based auth for every request.

**CL13** — **CDN:** A distributed network of proxy servers that cache content closer to users.
*   **Services:** CloudFront, Akamai.
*   **Use Case:** Use a CDN for static assets (images, JS, video) to reduce latency and origin load. Serve directly from origin for dynamic, personalized content that cannot be cached.

**CL14** — **Region:** A geographic area (e.g., us-east-1). **Availability Zone (AZ):** One or more discrete data centers within a region.
*   **Multi-AZ:** Protects against data center failure (power, fire).
*   **Zonal vs Regional:** Zonal resources (EC2, EBS) are tied to one AZ; Regional resources (S3, DynamoDB) are replicated across all AZs automatically.

**CL15** — **Managed Database:** A service where the provider handles patching, backups, high availability, and scaling.
*   **Tasks handled:** OS patching, automated backups, multi-AZ failover, storage auto-scaling, and point-in-time recovery.

**CL16** — **Users:** People. **Groups:** Collections of users. **Roles:** Temporary identities for services/apps. **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply by using Roles instead of Users for apps and scoping policies to specific resources (e.g., "Only allow access to S3 bucket X").

**CL17** — **Serverless:** Event-driven execution where the provider manages all infrastructure.
*   **Comparison:** Lambda (AWS), Functions (Azure/GCP).
*   **Cold Starts:** Latency when a function is invoked after being idle (container must spin up).
*   **Poor Fit:** Long-running processes (>15 mins), high-frequency low-latency requirements, or very large memory footprints.

**CL18** — **Ingress:** Standard K8s resource for L7 routing. **Gateway API:** The successor to Ingress, offering more expressive routing (multitenancy, traffic splitting). **Cloud LB Annotations:** Direct integration with AWS/Azure LB. **Service Mesh:** (Istio/Linkerd) handles L7 routing with advanced mTLS/retries.
*   **TLS:** Ingress/Gateway usually terminates TLS at the entry point. Service Mesh can provide end-to-end mTLS between pods.
*   **Gateway API vs Ingress:** Use Gateway API for complex routing, multiple hosts, and better separation of concerns (Infrastructure vs App teams).

**CL19** — **Strategy:**
*   **Savings Plans/RIs:** For predictable baseline workloads. **Spot:** For fault-tolerant, batch jobs.
*   **Right-sizing:** Use CloudWatch/Azure Monitor to downsize over-provisioned VMs.
*   **Storage Tiering:** Move old logs to S3 Glacier/Archive.
*   **FinOps:** Implement "Showback" (reporting costs to teams) and "Chargeback" (billing teams).
*   **Tools:** AWS Cost Explorer, CloudHealth, or Kubecost for K8s.

**CL20** — **Multi-Cloud Strategy:**
*   **Abstraction:** Use Kubernetes as the common compute layer.
*   **IaC:** Use Terraform to manage both providers.
*   **Networking:** Site-to-Site VPN or DirectConnect/ExpressRoute.
*   **Identity:** Use OIDC/SAML for federated identity.
*   **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs.
*   **Justification:** Only justified for regulatory compliance, extreme high availability, or specific "best-of-breed" features. Otherwise, it is unnecessary complexity.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** A structural model for ICS network segmentation.
*   **Level 0:** Physical Process (Sensors, Actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Area Control (HMIs, SCADA).
*   **Level 3:** Site Operations (Historians, Engineering Workstations).
*   **Level 4/5:** Enterprise Network (IT, ERP, Internet).

**OT2** — **IT:** Focuses on Confidentiality, Integrity, Availability (CIA). **OT:** Focuses on Safety, Reliability, Availability (AIC).
*   **Patching:** You cannot reboot a PLC or a production line controller for a patch without stopping production. OT systems often run on legacy OSs that are incompatible with modern IT security agents.

**OT3** — **IDMZ:** A buffer zone between IT and OT.
*   **Traffic:** Only proxied/mediated traffic (e.g., Historian replication, Jump Host access).
*   **Direction:** Strictly controlled.
*   **Danger:** Direct Level 4 to Level 1 connectivity allows a compromised office laptop to send "Stop" commands directly to a turbine or valve, bypassing all safety checks.

**OT4** — **1. Modbus TCP:** Level 1 (Control). **2. OPC UA:** Level 2/3 (SCADA/Historian). **3. EtherNet/IP:** Level 1 (Control). **4. PROFINET:** Level 1 (Control). **5. MQTT:** Level 3/4 (Data transport to Cloud/Enterprise).

**OT5** — **Data Diode:** A hardware device allowing data to flow in only one direction (physically impossible to send back). **Firewall:** Software-based, allows two-way traffic based on rules.
*   **Use Diode:** When moving data from a high-security OT zone to a lower-security IT zone where zero risk of inbound command injection is required.
*   **Limitation:** Diode prevents any handshake/acknowledgment (TCP fails), making it harder to configure.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (Protocol Conversion) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Boundaries:** Place a firewall between Level 3 and Level 4. Place an IDMZ between the Edge Gateway and the Corporate Network.

**OT7** — **Zones:** Grouping of assets with similar security requirements. **Conduits:** The communication paths between zones.
*   **Model:**
    *   *Zone A (Corporate):* Office PCs.
    *   *Zone B (Engineering):* Workstations.
    *   *Zone C (Control):* SCADA/HMIs.
    *   *Zone D (Process):* PLCs.
    *   *Zone E (Safety):* SIS.
    *   *Conduits:* Firewalls/Diodes between each zone. SIS must have a dedicated conduit to the process but no conduit to the Corporate network.

**OT8** — **Strategy:**
*   **VLANs:** Segment by production line and function (HMI, PLC, Historian).
*   **Firewalls:** Place Industrial Firewalls between production lines and the SCADA core.
*   **Remote Access:** Use a Jump Host in the IDMZ with MFA.
*   **Transition:** Use a "Parallel Build" approach—build the new segmented network and migrate one production line at a time during scheduled maintenance windows.

**OT9** — **SIS:** Independent system to take the plant to a safe state in emergencies. **BPCS:** Day-to-day control. **IEC 61511:** Standard for functional safety.
*   **Isolation:** If a ransomware attack hits the BPCS, the plant might stop, but the SIS must remain functional to prevent an explosion/leak. If the SIS is networked, a cyber-attack could disable the "emergency brake," leading to catastrophic physical failure.

**OT10** — **PLC:** Localized control of a specific machine/process. **DCS:** Distributed control of a large, continuous process (e.g., Oil Refinery). **SCADA:** Supervisory control over geographically dispersed assets (e.g., Water Grid).
*   **Coexistence:** Yes, they often coexist; a DCS might manage the refinery core while PLCs manage individual pumps.

**OT11** — **Architecture:** Corporate $\rightarrow$ MFA $\rightarrow$ VPN $\rightarrow$ IDMZ Jump Host $\rightarrow$ OT Network.
*   **Requirements:** Session recording (for auditing), time-limited access (Just-in-Time), and vendor-specific accounts.
*   **Why no RDP?** Direct RDP allows an attacker to bypass the IDMZ and move laterally directly into the control environment.

**OT12** — **Plan:**
1.  **Detection:** Deploy passive IDS (e.g., Dragos, Nozomi) to identify anomalous traffic in Level 3.
2.  **Inventory:** Cross-reference current traffic against the known asset list.
3.  **Response:** Isolate the compromised segment by updating firewall rules.
4.  **Coordination:** Notify the Control Room immediately; they decide if a manual shutdown is needed.
5.  **Operator Role:** The operator is the ultimate authority on safety. They must verify that cyber-actions do not cause physical instability.

**OT13** — **HMI:** A dashboard for operators to monitor and control the process (e.g., "Start Pump" button).
*   **Difference:** An **Engineering Workstation** is used to program the PLCs and configure the logic; it is not for daily operation.

**OT14** — **Historian:** A database for time-series process data (temperature, pressure over time).
*   **Plant Historian (L3):** High-resolution, local data for real-time optimization.
*   **Enterprise Historian (L4):** Aggregated, lower-resolution data for long-term business reporting and KPIs.

**OT15** — **Ladder Logic:** A programming language resembling electrical relay logic diagrams.
*   **Device:** PLC.
*   **Dominance:** It is intuitive for electricians/technicians to troubleshoot, and it has been the industry standard for 40+ years, making it highly reliable and well-understood.

**OT16** — **RTU:** A ruggedized device for remote telemetry (e.g., a remote pipeline valve).
*   **Difference:** RTUs are designed for low-bandwidth, long-distance communication and harsh environments; PLCs are for high-speed, complex logic in a factory.
*   **Deployment:** RTUs are used in oil/gas pipelines, water treatment, and power grids.

**OT17** — **Analog:** Continuous values (e.g., 4-20mA). **Digital:** On/Off states (e.g., 0 or 1).
*   **4-20mA vs 0-20mA:** 4mA is the "Live Zero." If the wire breaks, the signal drops to 0mA, which the system recognizes as a "Fault." If it were 0-20mA, a broken wire would look like a "Zero" reading, which could be a valid process value.

**OT18** — **Asset Inventory:** You cannot protect what you don't know exists.
*   **Tools:** Passive monitoring (listening to traffic) is safest. Active scanning (pinging/polling) can crash older PLCs.
*   **Danger of Active Scanning:** Legacy OT stacks are fragile; a simple Nmap scan can cause a PLC to reboot or enter a "Stop" state.

**OT19** — **MITRE ATT&CK for ICS:**
1.  **Inhibition of Response Function:** (e.g., Modifying safety logic).
2.  **Impair Process Control:** (e.g., Changing setpoints).
3.  **Persistence:** (e.g., Creating new accounts on HMIs).
4.  **Discovery:** (e.g., Network scanning).
5.  **Initial Access:** (e.g., Exploiting a VPN).
*   **Difference:** ICS focuses on physical impact (e.g., "Loss of Control"). Enterprise focuses on data theft. Use it to map "Conduits" and identify where you lack visibility.

**OT20** — **Converged SOC:**
*   **Log Collection:** Use unidirectional gateways or "Data Diode" style collectors to pull logs from OT without allowing inbound traffic.
*   **Staffing:** IT analysts handle the "Alert," but an OT Engineer must "Validate" the impact before any action is taken.
*   **Firmware Alert:** Treat as a Critical Incident. Isolate the PLC, check the hash against the known good version, and perform a manual forensic check of the logic.
