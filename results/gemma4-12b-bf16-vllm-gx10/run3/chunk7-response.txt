## Application Architecture

**AA1 — Easy:** A **monolith** is a single unified unit where all components (UI, business logic, data access) share the same memory space and codebase. **Microservices** decompose the application into small, independent services communicating over a network.
*3 Problems introduced by microservices:* 1. Network latency/reliability issues. 2. Distributed transaction complexity (data consistency). 3. Operational overhead (monitoring, deployment, and service discovery).

**AA2 — Easy:** **Synchronous** communication requires the requester to wait for a response before proceeding (e.g., **HTTP/REST**). **Asynchronous** communication allows the requester to continue immediately after sending a message (e.g., **RabbitMQ** or **Kafka**).

**AA3 — Medium:** A **reverse proxy** (e.g., Nginx) sits in front of web servers to handle load balancing, SSL termination, and caching. An **API Gateway** is a specialized reverse proxy that adds application-level features like authentication, rate limiting, request transformation, and protocol translation.
*Can it replace a reverse proxy?* Technically yes, but it is often inefficient to use a heavy API Gateway for simple tasks like basic load balancing or high-throughput caching where a lightweight reverse proxy excels.

**AA4 — Medium:** The **Saga pattern** manages distributed transactions by executing a sequence of local transactions; if one fails, it executes "compensating transactions" to undo previous steps.
*   **Choreography:** Each service produces/consumes events; no central coordinator. Best for simple workflows with few participants.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows where visibility and centralized logic are required.

**AA5 — Medium:** **CQRS** separates read operations (Queries) from write operations (Commands). It is paired with **Event Sourcing** because Event Sourcing stores the state as a sequence of events; CQRS allows you to project those events into different "read models" optimized for specific queries.
*Problem solved:* It solves the "impedance mismatch" where a single database schema struggles to be optimized for both high-speed writes and complex, multi-dimensional reads simultaneously.

**AA6 — Medium:** A **Circuit Breaker** prevents a system from repeatedly trying to execute an operation that is likely to fail.
*States:* 1. **Closed** (Normal operation). 2. **Open** (Fails fast immediately). 3. **Half-Open** (Allows a limited number of test requests to see if the service recovered).
*Difference:* A retry with backoff keeps trying a failing request; a circuit breaker stops trying entirely to allow the downstream service to recover. Use both by wrapping a retry logic inside a circuit breaker.

**AA7 — Hard:**
1. **Shared DB, Shared Schema:** *Cost:* Lowest. *Security:* Weakest (logical isolation only). *Complexity:* Low. *Noisy Neighbor:* High.
2. **Shared DB, Separate Schema:** *Cost:* Medium. *Security:* Better (schema-level permissions). *Complexity:* Medium. *Noisy Neighbor:* Medium (resource contention at DB level).
3. **Separate DB per Tenant:** *Cost:* Highest. *Security:* Best (physical isolation). *Complexity:* High (managing many DBs). *Noisy Neighbor:* Lowest (dedicated resources).

**AA8 — Hard:** **Strong consistency** ensures all nodes see the same data at the same time; **Eventual consistency** guarantees that, given enough time, all nodes will converge.
*Inventory Architecture:* Use **Strong Consistency**. Use a distributed SQL database (e.g., **CockroachDB** or **Google Spanner**) or a relational DB with strict ACID properties. Use the **Reservation Pattern** (lock the item in a "pending" state) and **Distributed Locking** (via Redis/Etcd) to ensure no overselling at scale.

**AA9 — Hard:** A **sidecar proxy** runs alongside an application container in the same pod/host to handle networking. In **Istio**, **Envoy** acts as the sidecar.
*Data Plane:* The proxies (Envoy) handling actual traffic. *Control Plane:* The management layer (Istio) pushing configurations to proxies.
*mTLS:* Application-level TLS requires managing certificates inside the app code. Sidecar mTLS handles encryption/identity at the infrastructure layer, ensuring "zero trust" without changing application code.

**AA10 — Medium:** **Strangler Fig** involves placing a proxy in front of the monolith and routing new features to microservices while slowly migrating old features.
*Strategy:* 1. Place an API Gateway/Proxy in front of the .NET Framework app. 2. Identify a low-risk module (e.g., "Notifications"). 3. Build it in .NET 8. 4. Update the proxy to route "/notifications" to the new service. 5. Repeat until the monolith is "strangled" and can be decommissioned.

**AA11 — Medium:** 12-Factor App methodology for cloud-native apps: 1. Codebase, 2. Dependencies, 3. Config, 4. Backing services, 5. Build/Release/Run, 6. Processes, 7. Port binding, 8. Concurrency, 9. Disposability, 10. Dev/Prod parity, 11. Logs, 12. Admin processes.
*Why they matter:* They ensure apps are portable, scalable, and resilient by enforcing strict separation of concerns (e.g., config from code).

**AA12 — Hard:**
*   **Coupling:** Event-driven (Kafka) is loosely coupled; Request-driven (REST/gRPC) is tightly coupled.
*   **Scalability:** Kafka scales better for high-throughput writes; REST/gRPC is better for immediate request-response.
*   **Debugging:** Kafka is harder (tracing events across brokers); REST/gRPC is easier (linear stack traces).
*   **Ordering:** Kafka guarantees ordering within a partition; REST/gRPC has no inherent ordering across requests.
*   **Failure:** Kafka provides persistence (replayability); REST/gRPC requires immediate retries or DLQs.
*   *Choice:* Use Kafka for high-volume telemetry/async tasks; use gRPC for low-latency internal service communication.

**AA13 — Easy:** A **Load Balancer** distributes incoming traffic across multiple servers.
*Layer 4:* Operates at the Transport layer (TCP/UDP); looks at IP/Port.
*Layer 7:* Operates at the Application layer (HTTP/HTTPS); looks at URLs, headers, cookies.
*Use Case:* Layer 7 is required for **Path-based routing** (e.g., routing `/api` to one cluster and `/images` to another).

**AA14 — Easy:** A **Message Queue** (RabbitMQ) stores messages until a consumer processes them (usually one-to-one). A **Log-based Broker** (Kafka) stores messages as an append-only log (one-to-many, replayable).
*Pick:* RabbitMQ for complex routing and per-message acknowledgments; Kafka for high-throughput stream processing and data retention.

**AA15 — Easy:** A **Container** shares the host OS kernel and isolates the application process. A **VM** includes a full guest OS and runs on a hypervisor.
*Why containers?* They are lightweight, start instantly, and ensure "write once, run anywhere" consistency across environments.

**AA16 — Easy:** **Stateless** services do not store client data between requests (e.g., a REST API). **Stateful** services maintain state (e.g., a database or a game server).
*Scaling:* Stateless services are easier to scale horizontally because any instance can handle any request.
*Example:* Stateless = Auth Service; Stateful = Redis Cache.

**AA17 — Easy:** An **ORM** maps database tables to objects in code. Examples: **Hibernate** (Java), **Entity Framework** (C#).
*Trade-offs:* ORMs increase developer productivity and prevent SQL injection; Raw SQL offers better performance for complex joins and finer control over execution plans.

**AA18 — Medium:** The **Bulkhead pattern** isolates resources so that a failure in one part of the system doesn't exhaust resources for the rest.
*Implementation:* Use **separate thread pools** for different downstream services (e.g., Service A gets 10 threads, Service B gets 10 threads). If Service B hangs, Service A still has its 10 threads available.

**AA19 — Hard:**
*   **OT:** Transforms operations to maintain consistency (Google Docs). High complexity, requires a central server to order operations.
*   **CRDTs:** Data structures that merge automatically (Figma). Lower complexity for merging, but higher memory overhead.
*   *Offline Support:* **CRDTs** are superior for offline editing because they allow local updates to merge seamlessly without a central "truth" coordinator to re-sequence operations.

**AA20 — Hard:**
*   **Context Propagation:** Use W3C Trace Context headers to pass `trace-id` across boundaries.
*   **Sampling:** Head-based (decide at start) is cheaper; Tail-based (decide at end) captures more errors/latencies but is expensive.
*   **Kafka Continuity:** Inject the `trace-id` into the Kafka message header. The consumer must extract this header to start its new span, linking the producer and consumer traces.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** **Type 1** runs directly on hardware (e.g., **ESXi, Xen**). **Type 2** runs on top of an OS (e.g., **VirtualBox, VMware Workstation**).

**OP2 — Easy:** **SAN** (Storage Area Network) provides block-level storage (like a local disk over a network); used for high-performance DBs. **NAS** (Network Attached Storage) provides file-level storage; used for shared files.
*Protocols:* SAN (Fibre Channel, iSCSI); NAS (NFS, SMB).

**OP3 — Medium:** **3-Tier** (Core/Distribution/Access) is hierarchical. **Leaf-Spine** is a two-tier architecture where every leaf switch connects to every spine switch.
*Problem solved:* Leaf-Spine provides predictable, low-latency "east-west" traffic (server-to-server), which is the dominant traffic pattern in modern data centers, whereas 3-tier can create bottlenecks at the core.

**OP4 — Medium:**
*   **Nodes:** Minimum 3 for quorum.
*   **Quorum:** Majority vote to prevent split-brain.
*   **Fencing:** STONITH (Shoot The Other Node In The Head) to power off failed nodes.
*   **Storage:** **Ceph** (Software Defined) or **iSCSI** (Block).
*   **Failure:** If a node fails, the cluster detects loss of heartbeat, fences the node, and the remaining nodes re-mount the shared storage/re-start VMs.

**OP5 — Medium:** **VLAN Trunking** allows multiple VLANs to travel over one physical link. **802.1Q** adds a tag to the Ethernet frame.
*Linux Config:* Use **802.1q** kernel module and create sub-interfaces (e.g., `eth0.10`, `eth0.20`) using `ip link` or Netplan.

**OP6 — Medium:**
*   RAID 1: Mirroring.
*   RAID 5: Striping + 1 parity (Fast read, slow write).
*   RAID 6: Striping + 2 parity (Can lose 2 drives).
*   RAID 10: Mirroring + Striping (Best performance/redundancy).
*   RAID Z2: ZFS equivalent of RAID 6.
*   *Choice:* **RAID 10**. For a database, you need the highest IOPS and fastest rebuild times, which RAID 10 provides over parity-based systems.

**OP7 — Hard:**
*   **Internal:** AD-integrated DNS for internal records.
*   **DMZ:** Authoritative servers for public records.
*   **Split-Horizon:** Internal users get internal IPs; external users get public IPs for the same hostname.
*   **VPN/Laptop:** Use **Conditional Forwarding** or **VPN DNS Suffixes** to ensure the laptop queries the internal DNS server when connected to the VPN.

**OP8 — Hard:** **Root CA** (Offline) signs **Subordinate CA**, which signs **End-Entity** certs.
*   **CRL:** List of revoked certs. **OCSP:** Real-time check of revocation.
*   **Compromise:** A compromised **Subordinate CA** allows an attacker to issue certs for your domain. A compromised **Root CA** destroys the entire trust chain; every certificate issued by any subordinate becomes untrustworthy.

**OP9 — Hard:**
*   **MPLS:** Reliable, expensive, provider-managed.
*   **IPsec:** Cheap, high overhead, complex to manage at scale.
*   **SD-WAN:** Orchestrated path selection, easy management.
*   **WireGuard:** High performance, modern crypto.
*   *Recommendation:* **SD-WAN**. It provides the best balance of management (centralized policy) and performance (dynamic path selection for VoIP) for 5 sites.

**OP10 — Medium:** **iDRAC/iLO/IPMI** are hardware management controllers. **Out-of-band** allows management even if the OS is crashed or the server is off.
*Risk:* If exposed to the internet, an attacker can gain full hardware control (reboot, wipe drives, change BIOS), effectively owning the physical machine.

**OP11 — Medium:**
*   **LVM:** Logical Volume Management (standard Linux).
*   **LVM-Thin:** Allows over-provisioning and thin snapshots (only stores changes).
*   **ZFS:** Combined file system and volume manager with built-in RAID and compression.
*   *Snapshots:* LVM-Thin is "Copy-on-Write" (efficient); ZFS is "Redirect-on-Write" (highly consistent).

**OP12 — Hard:**
*   **Strategy:** Use a **3-site stretch cluster** (or 2 sites + a 3rd "witness" site).
*   **CRUSH Rules:** Ensure data replicas are placed in different physical locations.
*   **Latency:** Ceph requires <10ms RTT for synchronous writes.
*   **Split-Brain:** 2-site Ceph is dangerous because if the link breaks, both sites might think they are the primary, leading to data corruption. A 3rd site (witness) provides the tie-breaking vote.

**OP13 — Easy:** **DHCP** assigns IPs automatically. **DORA:** Discover, Offer, Request, Acknowledge.
*Failure:* If the server is down and the lease expires, the Windows client will fail to renew and will eventually drop its IP, losing network connectivity.

**OP14 — Easy:** **Managed** switches allow VLANs, Link Aggregation (LACP), QoS, and SNMP monitoring. **Unmanaged** are "plug and play" with no configuration. Managed switches are essential for security and traffic prioritization in enterprises.

**OP15 — Easy:** **NTP** synchronizes clocks.
*Criticality:* In a cluster, clocks must be synced for **log correlation**, **Kerberos authentication**, and **distributed database timestamps**. If clocks drift, Kerberos tickets may be rejected as "expired" or "from the future."

**OP16 — Easy:**
*   **Physical:** Hardware.
*   **VM:** Hardware abstraction (Hypervisor).
*   **Container:** OS abstraction (Shared Kernel).
*   *Bare Metal:* Use for high-performance computing (HPC), heavy databases with specific NVMe tuning, or workloads where hypervisor overhead is unacceptable.

**OP17 — Easy:** **UPS** provides immediate battery power during a power flick/outage. **Generator** provides long-term power.
*ATS:* Automatically switches the building's power source from the grid to the generator when the UPS detects a failure.

**OP18 — Medium:** **Active-Passive:** One node works, one waits. **Active-Active:** Both nodes handle traffic.
*PostgreSQL HA:* Use **Pacemaker/Corosync**. **STONITH** ensures that if a node hangs, it is physically rebooted. A **Virtual IP (VIP)** floats between nodes; if the primary fails, Pacemaker moves the VIP to the standby.

**OP19 — Hard:**
*   **3-2-1:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** RPO (how much data can we lose?); RTO (how fast must we be back up?).
*   **Immutable:** Backups stored in a "Write Once Read Many" (WORM) state to prevent ransomware from deleting them.
*   **Difference:** **Backup** is a copy of data for recovery; **Disaster Recovery (DR)** is the entire plan (people, processes, infrastructure) to resume operations after a catastrophe.

**OP20 — Hard:** **802.1X** uses **Supplicant** (client), **Authenticator** (switch), and **Authentication Server** (RADIUS).
*   **EAP-TLS:** Certificate-based (most secure). **PEAP:** Username/Password.
*   **Dynamic VLAN:** RADIUS tells the switch which VLAN to put the port in based on the user's identity.
*   **MAB:** If a device (like a printer) doesn't have an 802.1X supplicant, the switch sends its MAC address to RADIUS to check against a whitelist.
