## Cloud Infrastructure Architecture

**CL1 — Easy:** 
*   **IaaS (Infrastructure as a Service):** Provides raw computing resources (VMs, storage, networking). You manage the OS and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to deploy apps without managing underlying infrastructure (OS, runtime). *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Provides a finished software product over the internet. *Example: Microsoft 365.*

**CL2 — Easy:** 
The provider manages the physical infrastructure (hardware, cooling, physical security). The user manages everything from the OS upward.
*   **IaaS VMs:** Provider: Physical host/Hypervisor. You: OS, Middleware, Runtime, Data, Apps.
*   **Managed Kubernetes (EKS/GKE):** Provider: Control plane, Master nodes. You: Worker nodes, Pods, Networking, Data.
*   **SaaS (M365):** Provider: Almost everything. You: Data, User Access, Configuration.

**CL3 — Medium:** 
*   **VPC:** A private, isolated logical network in the cloud.
*   **Subnet:** A range of IP addresses within a VPC (Public/Private).
*   **Security Group:** A stateful firewall for instances (allows/denies traffic to specific ports).
*   **NACL:** A stateless firewall for subnets (acts as a secondary layer of defense).
*   **Layering:** VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group.
*   **Stateful vs. Stateless:** Stateful (Security Group) remembers the connection; if you allow inbound, outbound is automatically allowed. Stateless (NACL) requires explicit rules for both directions.

**CL4 — Medium:** 
*   **Landing Zone:** A pre-configured, multi-account environment with baseline security/governance.
*   **OUs:** Grouping accounts by function (Prod, Dev, Shared Services).
*   **Guardrails:** Service Control Policies (SCPs) or Azure Policies to prevent non-compliant actions.
*   **Shared Networking:** Using Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize egress/ingress and inspection.
*   **Centralized Logging:** Sending all logs (CloudTrail, Flow Logs) to a dedicated "Log Archive" account.
*   **Single-account Problem:** Risk of "blast radius" (one breach affects everything), lack of granular permissions, and hitting service limits.

**CL5 — Medium:** 
IaC is managing infrastructure via machine-readable files.
*   **Terraform/OpenTofu:** Provider-agnostic, HCL language, state-file based. *Best for multi-cloud.*
*   **Pulumi:** Infrastructure as Code using general-purpose languages (Python, TS). *Best for dev-heavy teams.*
*   **CloudFormation/Bicep:** Native to AWS/Azure. *Best for deep integration with native features.*
*   **Crossplane:** Kubernetes-native IaC. *Best for teams already running everything on K8s.*

**CL6 — Medium:** 
*   **HPA:** Scales number of Pods based on CPU/RAM.
*   **VPA:** Scales the CPU/RAM limits of existing Pods.
*   **Cluster Autoscaler:** Scales the number of physical/virtual nodes in the cluster.
*   **KEDA:** Event-driven autoscaling (e.g., scale based on RabbitMQ queue length or Prometheus metrics).
*   **KEDA vs. HPA:** Use KEDA when scaling needs to be triggered by external events (queues, streams) rather than just internal resource metrics.

**CL7 — Hard:** 
*   **RPO/RTO:** Recovery Point Objective (data loss limit) / Recovery Time Objective (downtime limit).
*   **Active-Active:** Traffic to both regions simultaneously. Lowest RTO/RPO, highest cost.
*   **Active-Passive:** Traffic to one, failover to second.
*   **DB Replication:** Sync (Zero RPO, high latency) vs. Async (Low latency, potential data loss).
*   **DNS Failover:** Route53/Traffic Manager health checks to route traffic to the healthy region.
*   **State Management:** Use global databases (DynamoDB Global Tables, Aurora Global) or external caches (Redis).
*   **DR Types:** 
    *   **Pilot Light:** Only DB is live; app servers start on failover.
    *   **Warm Standby:** Scaled-down version of the app is always running.
    *   **Multi-site Active-Active:** Full capacity in both regions.

**CL8 — Hard:** 
GitOps is the practice of using Git as the "Source of Truth" for infrastructure/apps.
*   **ArgoCD vs. FluxCD:** ArgoCD has a rich UI and "Application" controller; Flux is more "Git-native" and modular.
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (pulls from Vault/AWS SM), or Vault (direct injection).
*   **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and automatically overwrites the manual change to match the Git state.

**CL9 — Hard:** 
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC with Local Storage:** Use `local` storage class for low-latency NVMe/SSD access.
*   **Headless Service:** Provides direct Pod IPs for peer discovery.
*   **Init Containers:** Run pre-flight checks or config migrations.
*   **ConfigMaps:** Mounted as volumes to specific paths (e.g., `/etc/app/config`).
*   **Pod Disruption Budgets (PDB):** Ensures a minimum number of replicas remain available during voluntary disruptions (upgrades).

**CL10 — Medium:** 
*   **Service Account:** Identity for a process/pod within K8s.
*   **Workload Identity:** Cloud-native identity for a specific workload.
*   **IRSA:** AWS-specific way to map a K8s Service Account to an IAM Role.
*   **Why no credentials?** Hardcoded keys are easily stolen.
*   **Workload Identity Federation:** Allows K8s pods to assume cloud roles via OIDC, eliminating the need for long-lived secrets.

**CL11 — Medium:** 
*   **Object (S3/Blob):** Unstructured data (images, logs). High durability (11 9s), cheap.
*   **Block (EBS/Managed Disk):** Raw volumes for OS/Databases. Low latency, high IOPS.
*   **File (EFS/Azure Files):** Shared filesystem (NFS/SMB). Multiple pods can read/write simultaneously.
*   **Durability:** Object storage usually offers highest durability; Block is tied to the availability of the instance/zone.

**CL12 — Hard:** 
*   **Network Policies:** L3/L4 isolation between namespaces/pods.
*   **Service Mesh (Istio/Linkerd):** mTLS for L7 encryption and identity-based auth.
*   **Pod Identity:** Assigning unique identities to every pod.
*   **Admission Controllers:** OPA/Kyverno to enforce "no root" or "signed images only."
*   **Image Signing:** Cosign/Notary to ensure only trusted code runs.
*   **Runtime Security:** Falco to detect syscall anomalies (e.g., shell spawned in container).
*   **Secrets:** HashiCorp Vault or AWS Secrets Manager injected via CSI driver.
*   **Difference:** Traditional security is "M&M" (Hard shell, soft center). Zero Trust assumes the network is already compromised; every request must be authenticated and authorized.

**CL13 — Easy:** 
*   **CDN:** A distributed network of proxy servers that cache content closer to users.
*   **How it works:** User requests content $\rightarrow$ Edge server checks cache $\rightarrow$ If miss, fetches from Origin $\rightarrow$ Caches and serves.
*   **Services:** AWS CloudFront, Azure CDN.
*   **CDN vs. Origin:** Use CDN for static assets (images, JS) or high-traffic global content. Serve from Origin for dynamic, personalized, or highly sensitive data.

**CL14 — Easy:** 
*   **Region:** A geographic area (e.g., us-east-1).
*   **Availability Zone (AZ):** One or more discrete data centers within a region.
*   **Why Multi-AZ?** Protects against data center failure (power, fire, flood).
*   **Zonal vs. Regional:** Zonal resources (EC2, EBS) are tied to one AZ. Regional resources (S3, DynamoDB, IAM) are replicated across all AZs automatically.

**CL15 — Easy:** 
*   **Managed DB:** A service where the provider handles patching, backups, high availability, and scaling.
*   **Operational Tasks:** Provider handles OS patching, DB engine updates, automated backups, failover, and hardware maintenance. You only manage schemas, queries, and user permissions.

**CL16 — Easy:** 
*   **Users:** People/External entities.
*   **Groups:** Collections of users.
*   **Roles:** Identities for services/applications (temporary).
*   **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. *Application:* Use roles instead of users for apps, and scope policies to specific resources (e.g., "Allow S3:PutObject only on Bucket-X").

**CL17 — Easy:** 
*   **Serverless:** Execution of code without managing servers.
*   **Comparison:** All three are FaaS (Function as a Service). AWS Lambda is the market leader; Azure Functions has great integration with .NET; GCF is strong for container-based functions.
*   **Cold Starts:** Latency when a function is invoked after being idle (container initialization).
*   **Poor Fit:** Long-running processes (over 15 mins), high-frequency low-latency trading, or heavy constant compute (cheaper on EC2).

**CL18 — Medium:** 
*   **Ingress Resource:** Standard K8s object for L7 routing.
*   **Gateway API:** The successor to Ingress; more expressive (multi-tenant, advanced routing).
*   **Cloud LB Annotations:** Direct integration with AWS ALB/NLB.
*   **Service Mesh Gateway:** Handles mTLS and complex traffic splitting.
*   **TLS Termination:** Ingress/Gateway usually terminates TLS at the edge. Service Mesh can terminate it at the sidecar.
*   **Gateway API vs. Ingress:** Use Gateway API for complex routing, traffic mirroring, or when you need to separate infrastructure concerns from application routing.

**CL19 — Hard:** 
*   **Savings Plans/RIs:** Commit to spend/usage for 1-3 years (best for steady-state).
*   **Spot:** Excess capacity at 90% discount (best for stateless/batch).
*   **Right-sizing:** Matching instance size to actual CPU/RAM utilization.
*   **Storage Tiering:** Moving old data to S3 Glacier/Archive.
*   **FinOps:** Culture of accountability.
*   **Showback/Chargeback:** Tagging resources by "Cost Center" to bill departments.
*   **Tools:** AWS Cost Explorer, CloudHealth, or Kubecost for K8s.

**CL20 — Hard:** 
*   **Abstraction:** Use Kubernetes as the "Cloud OS" to standardize deployments.
*   **IaC:** Terraform for consistent resource provisioning.
*   **Networking:** Site-to-Site VPN or Megaport/Equinix Fabric for low-latency interconnect.
*   **Identity:** OIDC/SAML federation (e.g., Okta) to provide single sign-on across clouds.
*   **Trade-offs:** Multi-cloud increases complexity, networking costs, and "lowest common denominator" feature usage.
*   **Justification:** Justified for regulatory compliance, extreme high availability, or specific feature requirements (e.g., Azure AI + AWS S3). Unnecessary for most startups/mid-size firms.

## OT Infrastructure Architecture

**OT1 — Easy:** 
The Purdue Model is a structural model for ICS network segmentation.
*   **Level 0:** Physical Process (Sensors, Actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Area Control (HMIs, SCADA).
*   **Level 3:** Site Operations (Historians, Engineering Workstations).
*   **Level 4:** Enterprise Network (Business IT, Email).
*   **Level 5:** Corporate/External (Internet, Cloud).

**OT2 — Easy:** 
*   **IT:** Focuses on Confidentiality, Integrity, Availability (CIA). High change frequency.
*   **OT:** Focuses on Availability, Integrity, Safety (AIS). Low change frequency.
*   **Patching:** You cannot reboot a PLC or a production line for a "Patch Tuesday" update without stopping production. OT requires scheduled maintenance windows and rigorous testing.

**OT3 — Medium:** 
*   **IDMZ:** A buffer zone between IT (Level 4) and OT (Level 3).
*   **Traffic:** Only proxied/mediated traffic (e.g., Historian replication, Jump Host access).
*   **Direction:** Strictly controlled. No direct Level 4 $\rightarrow$ Level 1.
*   **Danger:** Direct connectivity allows a compromised office laptop to send a "Stop" command directly to a turbine or chemical mixer.

**OT4 — Medium:** 
1.  **Modbus TCP:** Level 1 (Fieldbus/Control).
2.  **OPC UA:** Level 2/3 (M2M communication/SCADA).
3.  **EtherNet/IP:** Level 1 (Industrial Ethernet).
4.  **PROFINET:** Level 1 (Industrial Ethernet).
5.  **MQTT:** Level 3/4 (IoT/Cloud reporting).

**OT5 — Medium:** 
*   **Firewall:** Software-based, inspects packets, allows two-way communication (bi-directional).
*   **Data Diode:** Hardware-based, physically allows data to flow in only one direction (unidirectional).
*   **Use Case:** Use a diode for pushing data from a high-security nuclear/power plant to a monitoring center where no return path is ever needed.
*   **Limitation:** Diodes cannot handle TCP handshakes (no ACKs), making them harder to configure for standard protocols.

**OT6 — Medium:** 
*   **Flow:** PLC $\rightarrow$ OPC UA Server (Level 2) $\rightarrow$ Edge Gateway (Level 3) $\rightarrow$ MQTT Broker (Level 3) $\rightarrow$ Cloud Ingestion.
*   **Boundaries:** 
    1.  IDMZ between Level 3 and Level 4.
    2.  Firewall/Diode between Edge Gateway and the Internet.
    3.  VPN/TLS for the MQTT tunnel to the cloud.

**OT7 — Hard:** 
*   **Zone:** A grouping of assets with similar security requirements (e.g., "PLC Zone").
*   **Conduit:** A communication path between zones (e.g., "Firewall between PLC Zone and HMI Zone").
*   **Design:**
    *   **Zone 1:** Corporate (Level 4).
    *   **Zone 2:** Engineering Workstations (Level 3).
    *   **Zone 3:** SCADA/Historian (Level 3).
    *   **Zone 4:** PLCs (Level 1).
    *   **Zone 5:** SIS (Isolated).
    *   **Conduits:** Firewalls/Diodes between every zone. SIS must have a dedicated conduit to the operator, but no conduit to the Corporate zone.

**OT8 — Hard:** 
*   **VLANs:** Segment by production line (Line 1, Line 2, etc.) and function (HMI, PLC, Safety).
*   **Firewalls:** Place an Industrial Firewall between the IDMZ and the Plant Floor.
*   **Switching:** Use managed industrial switches with Port Security.
*   **Remote Access:** VPN $\rightarrow$ Jump Host in IDMZ $\rightarrow$ MFA $\rightarrow$ Engineering Workstation.
*   **Transition:** Use a "Parallel Build" strategy. Build the new segmented network, migrate one production line at a time during scheduled downtime, and decommission the flat network.

**OT9 — Hard:** 
*   **BPCS:** Controls the process (e.g., keeping a tank at 50 degrees).
*   **SIS:** Protects life/environment (e.g., shutting down the tank if it hits 100 degrees).
*   **IEC 61511:** The standard for functional safety in process industries.
*   **Isolation:** SIS must be air-gapped because if a ransomware attack hits the BPCS and the SIS is connected, the attacker could disable the safety shut-offs, leading to a catastrophic explosion.

**OT10 — Medium:** 
*   **PLC:** Small, dedicated controller for specific tasks (e.g., a conveyor belt).
*   **DCS:** Distributed Control System for large, continuous processes (e.g., an oil refinery).
*   **SCADA:** Supervisory system for geographically dispersed assets (e.g., a water utility).
*   **Coexistence:** Yes, they often work together (DCS for the plant, SCADA for the remote pumps, PLCs for the local valves).

**OT11 — Medium:** 
*   **Architecture:** Corporate $\rightarrow$ VPN $\rightarrow$ Jump Host (IDMZ) $\rightarrow$ MFA $\rightarrow$ Session Recording $\rightarrow$ Target HMI.
*   **Why no direct RDP:** Direct RDP allows an attacker to bypass all intermediate security controls and move laterally directly into the control network.

**OT12 — Hard:** 
*   **Detection:** Deploy passive IDS (e.g., Dragos, Nozomi) to monitor for anomalous Modbus/S7comm traffic.
*   **Inventory:** Cross-reference current traffic against a known asset list.
*   **Response:** 
    1.  Isolate the compromised VPN segment.
    2.  Switch to manual override/local control where possible.
    3.  Coordinate with the Control Room to ensure "Safe State."
    4.  Identify the "Patient Zero" workstation.
*   **Operator Role:** The operator is the ultimate authority. They decide if a cyber-action is safe to perform. If a process is unstable, the operator may choose to keep the system running despite the threat to prevent physical damage.

**OT13 — Easy:** 
*   **HMI:** A screen/dashboard for operators to see process values (temp, pressure) and issue commands (Start/Stop).
*   **Difference:** An Engineering Workstation is used to *program* the PLCs and configure the logic; an HMI is for *running* the process.

**OT14 — Easy:** 
*   **Historian:** A database optimized for time-series data (tags over time).
*   **Importance:** Used for trend analysis, regulatory reporting, and troubleshooting.
*   **Plant vs. Enterprise:** Plant Historian (Level 3) stores high-frequency raw data (millisecond resolution). Enterprise Historian (Level 4) stores aggregated, low-frequency data for business KPIs.

**OT15 — Easy:** 
*   **Ladder Logic:** A programming language that looks like electrical relay diagrams.
*   **Device:** PLC.
*   **Dominance:** It is intuitive for electricians/technicians to troubleshoot visually, and it has been the standard for 40+ years.

**OT16 — Easy:** 
*   **RTU:** Remote Terminal Unit.
*   **Difference:** RTUs are designed for low-bandwidth, long-distance communication (radio, cellular) and harsh environments. PLCs are for high-speed, local control.
*   **Deployment:** RTUs are used in oil pipelines, water towers, and remote substations.

**OT17 — Easy:** 
*   **Analog:** Continuous values (e.g., 4-20mA represents 0-100% pressure).
*   **Digital:** On/Off states (e.g., 24V = On, 0V = Off).
*   **4-20mA vs 0-20mA:** 4mA is the "Live Zero." If the wire breaks, the signal drops to 0mA, which the system recognizes as a "Fault." If it were 0-20mA, a broken wire would look like a "Zero" reading, which could be a valid process value.

**OT18 — Medium:** 
*   **Asset Inventory:** You cannot protect what you don't know exists.
*   **Tools:** Passive monitoring (listening to traffic) is safest. Active scanning (pinging/querying) is used for discovery.
*   **Danger of Active Scanning:** Old PLCs have fragile TCP/IP stacks. A simple Nmap scan can crash a PLC, causing a production line to stop or a valve to fail.

**OT19 — Hard:** 
*   **Tactics:** 
    1.  **Persistence:** (e.g., Modifying PLC firmware).
    2.  **Discovery:** (e.g., Network scanning).
    3.  **Inhibition of Response:** (e.g., Disabling alarms).
    4.  **Impair Process Control:** (e.g., Changing setpoints).
    5.  **Impact:** (e.g., Physical destruction).
*   **Difference:** Enterprise ATT&CK focuses on data theft/malware; ICS focuses on physical process disruption and safety.
*   **Assessment:** Map your current controls (firewalls, IDS) against the techniques in the ICS matrix to find "blind spots."

**OT20 — Hard:** 
*   **Log Collection:** Use unidirectional gateways or "Data Diode" style collectors to push logs to the SIEM without allowing any inbound traffic to the OT network.
*   **Staffing:** A "Hybrid" team. IT analysts handle the SIEM/Log ingestion; OT engineers provide context (e.g., "Is this PLC restart normal for maintenance?").
*   **False Positives:** OT environments are noisy. Use "Allow-listing" for known industrial protocols.
*   **Unauthorized Firmware Alert:** 
    1.  Immediately notify the Plant Manager.
    2.  Verify if a maintenance window was scheduled.
    3.  If not, isolate the engineering workstation that pushed the change.
    4.  Perform a forensic hash check on the PLC firmware.
    5.  Do not reboot the PLC until the safety impact is assessed.
