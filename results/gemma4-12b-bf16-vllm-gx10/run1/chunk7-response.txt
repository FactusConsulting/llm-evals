## Application Architecture

**AA1 — Easy:** A monolith is a single unified unit where all components (UI, business logic, data access) share the same memory space and codebase. Microservices decompose the application into small, independent services communicating over a network.
*Problems introduced by microservices:* 1. Network latency/reliability issues. 2. Distributed transaction complexity (data consistency). 3. Operational overhead (monitoring, deployment, and service discovery).

**AA2 — Easy:** Synchronous communication requires the requester to wait for a response before proceeding (e.g., HTTP/REST). Asynchronous communication allows the requester to continue immediately after sending a message (e.g., RabbitMQ/Kafka).
*Technologies:* Sync: gRPC/REST. Async: RabbitMQ/Apache Kafka.

**AA3 — Medium:** A reverse proxy sits in front of web servers to handle load balancing, SSL termination, and caching (e.g., Nginx). An API Gateway is an application-layer proxy that adds features like authentication, rate limiting, request transformation, and orchestration.
*Replacement:* An API Gateway can replace a reverse proxy for most web-facing needs, but a dedicated reverse proxy is often more performant for high-throughput, low-level traffic routing where complex logic isn't needed.

**AA4 — Medium:** The Saga pattern manages distributed transactions by breaking them into a sequence of local transactions. Each local transaction updates the database and publishes an event to trigger the next. If one fails, "compensating transactions" undo previous steps.
*Choreography:* Services exchange events without a central controller (decentralized). Best for simple workflows.
*Orchestration:* A central "orchestrator" tells services what to do. Best for complex workflows with many steps.

**AA5 — Medium:** CQRS separates read operations (Queries) from write operations (Commands). It is paired with Event Sourcing because Event Sourcing stores the state as a sequence of immutable events; CQRS then projects these events into different "read models" optimized for specific queries.
*Problem solved:* It solves the "impedance mismatch" where a single database schema struggles to be optimized for both high-speed writes and complex, multi-join reads simultaneously.

**AA6 — Medium:** A Circuit Breaker prevents a service from repeatedly trying to call a failing downstream service.
*States:* 1. Closed (requests flow). 2. Open (requests fail immediately). 3. Half-Open (limited requests allowed to test recovery).
*Difference:* Retries with backoff keep trying a failing service (potentially worsening a "retry storm"). A Circuit Breaker stops the calls entirely to allow the downstream service to recover. Use both by using a Circuit Breaker to stop the flow and Retries for transient network blips.

**AA7 — Hard:**
1. **Shared DB, Shared Schema:** *Cost:* Lowest. *Security:* Weakest (logic-based isolation). *Complexity:* Low. *Noisy Neighbor:* High.
2. **Shared DB, Separate Schema:** *Cost:* Medium. *Security:* Better (logical separation). *Complexity:* Medium. *Noisy Neighbor:* Medium (resource contention at DB level).
3. **Separate DB per Tenant:** *Cost:* Highest. *Security:* Best (physical isolation). *Complexity:* High (migration/scaling management). *Noisy Neighbor:* Lowest.

**AA8 — Hard:** Strong consistency ensures all nodes see the same data at the same time; eventual consistency allows nodes to be temporarily out of sync.
*Inventory Architecture:* Use **Strong Consistency**. Use a distributed SQL database (e.g., CockroachDB or Google Spanner) or a relational DB with strict ACID properties. Use the **Reservation Pattern**: "Reserve" stock in a transaction, then asynchronously confirm the order. At scale, use sharded databases based on ProductID to maintain high throughput.

**AA9 — Hard:** A sidecar proxy runs alongside an application container to handle networking (mTLS, retries, telemetry). In Istio, **Envoy** is the data plane (handles actual traffic), and **Istiod** is the control plane (manages configuration/certificates).
*mTLS:* Application-level TLS requires managing certs in every app's code. Sidecar mTLS handles this at the infrastructure layer, ensuring all "east-west" traffic is encrypted and authenticated without developer intervention.

**AA10 — Medium:** Strangler Fig involves placing a proxy (like Nginx or an API Gateway) in front of the monolith. New features are built as .NET 8 microservices. Existing features are migrated one by one to microservices. The proxy routes traffic to the new service for migrated features and the monolith for the rest, until the monolith is "strangled" and can be decommissioned.

**AA11 — Medium:** 12-Factor App is a methodology for building SaaS apps. 6 Factors: 1. Codebase (one repo). 2. Dependencies (explicitly declared). 3. Config (env vars). 4. Backing Services (attachable resources). 5. Build, Release, Run (separation). 6. Processes (stateless). These matter because they ensure portability, scalability, and ease of deployment in containerized/cloud environments.

**AA12 — Hard:**
*Coupling:* Event-driven (ED) is loosely coupled; Request-driven (RD) is tightly coupled.
*Scalability:* ED scales better for high-volume writes (buffering).
*Debugging:* RD is easier (linear stack trace); ED is harder (distributed traces).
*Ordering:* Kafka guarantees ordering per partition; REST/gRPC does not inherently.
*Failure:* ED provides "durability" (message stays in queue); RD requires immediate handling or manual retry logic.
*Choice:* Use RD for synchronous UI actions (e.g., Login). Use ED for background processing (e.g., Order Processing).

**AA13 — Easy:** A load balancer distributes incoming traffic across multiple servers.
*Layer 4:* Routes based on IP/Port (fast, no inspection).
*Layer 7:* Routes based on HTTP headers, cookies, or URL paths (slower, but smarter).
*L7 Use Case:* Routing `/api/v1/users` to Service A and `/api/v1/orders` to Service B.

**AA14 — Easy:** A message queue (RabbitMQ) stores messages until a consumer processes them (point-to-point). A log-based broker (Kafka) stores messages as an append-only log that can be replayed by multiple consumers.
*Pick:* RabbitMQ for complex routing and per-message acknowledgments. Kafka for high-throughput streaming and data replayability.

**AA15 — Easy:** A container isolates an application and its dependencies (libraries, binaries) into a package. A VM isolates an entire OS on top of a hypervisor.
*Popularity:* Containers are lightweight, start in seconds, and ensure "it works on my machine" consistency across environments.

**AA16 — Easy:** Stateless services do not store client data (session, state) locally; every request contains all info needed. Stateful services store data (e.g., a game server or a DB).
*Scaling:* Stateless services are easier to scale because any instance can handle any request.
*Examples:* Stateless: Web API. Stateful: Redis or a WebSocket server.

**AA17 — Easy:** An ORM maps database tables to objects in code. Examples: Hibernate (Java), SQLAlchemy (Python).
*Trade-offs:* ORMs provide speed of development and abstraction. Raw SQL provides maximum performance, precise control over complex joins, and easier optimization.

**AA18 — Medium:** The Bulkhead pattern isolates resources so that a failure in one part of the system doesn't exhaust resources for the rest (like hulls of a ship).
*Implementation:* Use separate thread pools for different downstream services (e.g., Service A gets 10 threads, Service B gets 10 threads). If Service B hangs, Service A's threads remain available.

**AA19 — Hard:**
*OT:* Transforms operations based on concurrent edits. High complexity, requires a central server to order operations.
*CRDTs:* Data structures that merge automatically without a central coordinator. Higher memory/storage overhead.
*Offline:* **CRDTs** are superior for offline editing because they allow for decentralized merging once the client reconnects without needing to "re-sync" a linear history from a server.

**AA20 — Hard:** Challenges: 1. Context propagation (ensuring TraceID travels across headers). 2. Sampling (Tail-based is better for capturing errors but harder to manage). 3. Async tracing (Kafka headers must carry the context).
*Kafka Continuity:* Inject the W3C Trace Context into the Kafka message headers. The consumer must extract this header and start a new span linked to the producer's span.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** Type 1 (Bare-metal) runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V). Type 2 (Hosted) runs on an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2 — Easy:** SAN (Storage Area Network) provides block-level storage (like a local drive) over a dedicated network (Fibre Channel/iSCSI). NAS (Network Attached Storage) provides file-level storage (like a shared folder) over Ethernet (NFS/SMB).
*Use:* SAN for high-performance DBs; NAS for shared files/media.

**OP3 — Medium:** 3-tier (Core/Distribution/Access) is hierarchical. Leaf-Spine is a two-tier architecture where every leaf switch connects to every spine switch.
*Problem solved:* Leaf-Spine provides predictable, low-latency "east-west" traffic (server-to-server), which is the dominant traffic pattern in modern data centers, whereas 3-tier can create bottlenecks at the core.

**OP4 — Medium:**
*Architecture:* 3 nodes (minimum for quorum).
*Quorum:* 2 out of 3 nodes must agree.
*Fencing:* STONITH (Shoot The Other Node In The Head) to power off a failed node.
*Storage:* Ceph (distributed) or iSCSI (centralized).
*Failure:* If a node fails, the remaining 2 maintain quorum; the storage remains available; the VM is restarted on a healthy node.

**OP5 — Medium:** VLAN trunking allows multiple VLANs to travel over one physical link. 802.1Q adds a "tag" to the Ethernet frame identifying the VLAN ID.
*Linux Config:* Use "Router on a Stick" or sub-interfaces (e.g., `eth0.10`, `eth0.20`) using the `8021q` kernel module.

**OP6 — Medium:** RAID 1 (Mirror), 5 (Parity), 6 (Dual Parity), 10 (Mirror+Stripe), RAID Z2 (ZFS dual parity).
*Choice:* **RAID 10**. For a database, you need the highest IOPS and fastest rebuild times. RAID 10 provides the best balance of performance and fault tolerance for high-write workloads.

**OP7 — Hard:**
*Architecture:* Internal AD DS for local users. DMZ with public-facing servers.
*Split-Horizon:* Internal DNS resolves `internal.corp` to private IPs; External DNS resolves it to public IPs.
*VPN:* Use Conditional Forwarders. When a laptop moves to VPN, the VPN gateway provides the DNS server IP; the server recognizes the internal domain and routes queries to the internal DNS.
*DNSSEC:* Signs the external zone to prevent spoofing.

**OP8 — Hard:** Root CA (Offline) signs Subordinate CA. Subordinate CA signs End-Entity certs.
*CRL:* List of revoked certs. *OCSP:* Real-time check of revocation status.
*Compromise:* Root CA compromise is catastrophic (entire PKI is untrusted). Subordinate CA compromise is manageable (revoke the subordinate cert and issue a new one).

**OP9 — Hard:**
*Comparison:* MPLS (Reliable/Expensive), IPsec (Cheap/Variable), SD-WAN (Smart/Managed), WireGuard (Fast/Modern).
*Recommendation:* **SD-WAN**. It allows for "path steering" (sending VoIP over the most stable link) and provides centralized management for 5 sites while being more cost-effective than pure MPLS.

**OP10 — Medium:** Out-of-band (OOB) management allows access to the server (power, console) even if the OS is crashed or the network is down.
*Risk:* If exposed to the internet, an attacker can gain full hardware control (reboot, wipe drives, install rootkits). It must be behind a VPN or a strict firewall.

**OP11 — Medium:** LVM (Logical Volume Manager) is standard block management. LVM-Thin allows over-provisioning and snapshots. ZFS is a combined file system and volume manager.
*Snapshots:* LVM-Thin is "Copy-on-Write" (efficient). ZFS is "Redirect-on-Write" (highly consistent). Use ZFS for data integrity/RAID-Z; LVM for standard Linux volume flexibility.

**OP12 — Hard:**
*Strategy:* 3-site "Stretch Cluster" or 2-site with a 3rd-site "Witness" (Quorum).
*Ceph:* Use CRUSH rules to ensure replicas are on different sites.
*Latency:* Must be <10ms for synchronous replication.
*Split-brain:* Without a 3rd site (tiebreaker), if the link between Site A and B breaks, both might try to become "Primary." A 3rd site provides the "vote" to decide who stays up.

**OP13 — Easy:** DHCP assigns IPs automatically. DORA: Discover, Offer, Request, Acknowledge.
*Failure:* If the server is down and the lease expires, the client loses its IP and cannot communicate. Windows will attempt to self-assign an APIPA address (169.254.x.x).

**OP14 — Easy:** Managed switches allow configuration (VLANs, QoS, Spanning Tree, SNMP). Unmanaged are "plug and play."
*Enterprise Importance:* VLANs for security, QoS for prioritizing VoIP/Video, and Spanning Tree to prevent network loops.

**OP15 — Easy:** NTP synchronizes clocks.
*Criticality:* Logs become useless if timestamps don't match. In clusters, clock drift can break Kerberos authentication, cause database "out of order" errors, or trigger false failovers in high-availability heartbeats.

**OP16 — Easy:** Physical (Hardware), VM (Virtualized OS), Container (Isolated Process).
*Bare Metal:* Use for high-performance computing (HPC), heavy databases with high IOPS requirements, or workloads where hypervisor overhead is unacceptable.

**OP17 — Easy:** UPS provides immediate battery power during a blackout (seconds/minutes). Generator provides long-term power.
*ATS:* Automatically switches the building's power source from the grid to the generator when the UPS detects a power loss.

**OP18 — Medium:** Active-Passive (one standby) vs Active-Active (both serve traffic).
*PostgreSQL HA:* Use Pacemaker/Corosync. Corosync handles cluster membership (heartbeats). Pacemaker manages the resources (Virtual IP, Postgres service). STONITH ensures that if a node hangs, it is physically powered off to prevent data corruption.

**OP19 — Hard:**
*3-2-1:* 3 copies, 2 media types, 1 offsite.
*RPO/RTO:* RPO (how much data can we lose?); RTO (how fast must we be back up?).
*Immutable:* Use S3 Object Lock or hardened Linux repos to prevent ransomware from deleting backups.
*Difference:* Backup is a copy of data; Disaster Recovery (DR) is the *process* and infrastructure to restore operations after a catastrophe.

**OP20 — Hard:** 802.1X uses a Supplicant (client), Authenticator (switch), and Auth Server (RADIUS).
*EAP-TLS:* Certificate-based (most secure). *PEAP:* Username/Password.
*Dynamic VLAN:* RADIUS tells the switch which VLAN to put the port in after successful auth.
*MAB:* If a device (like a printer) doesn't have an 802.1X supplicant, the switch sends the MAC address to RADIUS to check against a whitelist.
