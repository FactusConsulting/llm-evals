## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` is a dry-run operation. It compares the current state with the configuration files and outputs the actions OpenTofu will take (create, update, delete) without making changes. `tofu apply` executes those actions to reach the desired state.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file that maps real-world resources to your configuration. It tracks metadata, dependencies, and current attributes. Remote state is critical for team collaboration and CI/CD because it provides a "single source of truth," prevents state corruption from concurrent writes, and enables state locking.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an integer index to create multiple resources. `for_each` uses a map or set of strings. `for_each` is preferred because it allows you to reference specific instances by a logical key (e.g., `vm["web1"]`) rather than an index (`vm[0]`). If you remove an item from the middle of a `count` list, all subsequent resources are destroyed and recreated; `for_each` avoids this.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This is known as "Configuration Drift." During the next `tofu plan`, OpenTofu performs a "refresh" by querying the cloud provider's API. It compares the API response to the state file. If they differ, OpenTofu identifies the drift and proposes an update to bring the resource back into alignment with the code.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
variable "vm_names" {
  type    = set(string)
  default = ["web1", "web2", "web3"]
}

resource "aws_instance" "vm" {
  for_each = toset(var.vm_names)
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads the entire state file of another workspace, which can be slow and exposes unnecessary data. Using `outputs` is cleaner but requires the state to be accessible. The recommended alternative is **Data Sharing via a common SSM Parameter Store, Consul, or a dedicated "Shared Services" module** that outputs values to a shared key-value store. This decouples the modules and prevents one module's state structure from breaking another.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
**Why:** `remote-exec` runs during the "Apply" phase, but OpenTofu evaluates outputs to determine dependencies. If the output is defined as a local variable or a file path that hasn't been written yet, the dependency isn't strictly enforced by the graph.
**Fix:** Use a `local_file` resource to write the kubeconfig to disk, and have the output reference that resource. Alternatively, use a `time_sleep` resource to ensure the remote execution finishes, or use a `data` source to read the file only after the provisioner completes.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` brings existing infrastructure into the state file via the CLI. Limitations include manual typing of IDs and the fact that it doesn't generate the HCL code for you. The `import` block allows you to declare the import in code; it allows for "planned" imports, supports multiple resources in one plan, and can be used with `tofu plan` to see what will happen before committing to the import.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a placeholder for data. An **input variable** is a value provided to the configuration (like a user-defined parameter). An **output** is a value returned by the configuration after execution (like a Load Balancer's DNS name) to be used by other modules or humans.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates OpenTofu's configuration into API calls for a specific service (AWS, Azure, Docker, etc.). If you run `plan` without `init`, OpenTofu will fail because it hasn't downloaded the necessary provider binaries or initialized the backend.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It is the Dependency Lock File. It records the exact versions and hashes of the providers used. Committing it ensures that every team member and CI/CD runner uses the exact same provider versions, preventing "it works on my machine" errors caused by provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the configuration. To target a single resource, use the `-target` flag: `tofu destroy -target=aws_instance.web_server`.

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source allows you to fetch information from an existing infrastructure that you do not manage via the current OpenTofu configuration. Example: Fetching the latest Amazon Linux AMI ID or looking up an existing VPC ID to place a new subnet inside it.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are for inputs provided by the user/environment. Locals are for internal logic, constants, or complex transformations within a module. Use `locals` to keep your code DRY (Don't Repeat Yourself) by calculating a value once and reusing it multiple times in the configuration.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block modifies the behavior of resource management.
1. `create_before_destroy`: Ensures a new resource is up before the old one is deleted (e.g., replacing a Load Balancer).
2. `prevent_destroy`: Hard error if an action would delete the resource (e.g., a production database).
3. `ignore_changes`: Prevents OpenTofu from updating a specific attribute (e.g., ignoring tags added by an external autoscaling group).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module/address in the code. It updates the state file mapping without actually deleting and recreating the physical infrastructure.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG) of resources.
- **Implicit:** Created when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`).
- **Explicit:** Created using the `depends_on` meta-argument.
`depends_on` forces a sequence, which reduces parallelism. It should be used sparingly because OpenTofu is usually smart enough to infer dependencies; overusing it slows down execution and makes the graph harder to debug.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1. **State Splitting:** Break the project into smaller state files (e.g., Network, DB, App). *Tradeoff: Harder to manage cross-state dependencies.*
2. **Targeted Plans:** Use `-target` to plan only specific components. *Tradeoff: Risk of missing side effects.*
3. **Provider Optimization:** Use specific regions/endpoints to limit API scope. *Tradeoff: Configuration complexity.*
4. **Remote State Caching:** Use a faster backend or optimize data source calls. *Tradeoff: Infrastructure cost/complexity.*

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**
Locking prevents two processes from modifying the state simultaneously. If a process crashes, the lock remains in the backend (e.g., a DynamoDB entry). You can break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually running, force-unlocking will cause state corruption or concurrent write errors.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.**
1. Create the S3 bucket and DynamoDB table.
2. Configure the `backend "s3"` block in the code.
3. Run `tofu init`. OpenTofu will detect the change and ask to migrate the state.
4. OpenTofu copies the local `terraform.tfstate` to S3.
5. **Verification:** Run `tofu plan`. If it shows "No changes," the state was migrated correctly. Check the S3 bucket to ensure the file exists.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
- **Task:** A single unit of work (e.g., "install nginx").
- **Playbook:** A list of plays that group tasks together to be executed on specific hosts.
- **Role:** A structured way to group tasks, variables, files, and templates into a reusable component.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary of system information gathered by the `setup` module. You access the OS family using `ansible_facts['os_family']` or the shorthand `ansible_os_family`.

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
- `command`: Executes a command directly (no shell features like pipes `|` or redirects `>`). Safest.
- `shell`: Executes via the system shell (supports pipes, variables, redirects). Use when shell features are needed.
- `raw`: Executes via SSH without requiring Python on the target. Use for initial bootstrapping or very minimal systems.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Ansible ensures idempotency by checking the current state before acting.
- **Idempotent:** `apt: name=nginx state=present` (only installs if not present).
- **NOT Idempotent:** `shell: echo "data" >> /file` (appends every time the playbook runs).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS
  block:
    - name: Install htop on Debian
      apt: name=htop state=present
      when: ansible_os_family == "Debian"

    - name: Install epel and htop on RedHat
      yum:
        name: [epel-release, htop]
        state: present
      when: ansible_os_family == "RedHat"
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
(Lowest to Highest)
1. Role defaults
2. Inventory (group_vars, host_vars)
3. Playbook variables
4. `set_fact`
5. Extra vars (`-e`) - **Highest priority.**

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**
Use `serial: 3` in the play to ensure only 3 hosts are processed at a time. Group the 50 nodes into a group (e.g., `[rke2_agents]`). Use the `wait_for` module if a specific service must be reachable on those 3 nodes before the next batch begins.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` encrypts sensitive data. To encrypt a single variable, use the `ansible-vault encrypt_string` command to generate an encrypted block, then paste that block into your `vars.yml` file.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory file lists the hosts and groups of managed machines.
- **Static:** A manual list of IP addresses/hostnames (e.g., `hosts.ini`).
- **Dynamic:** A script or plugin that queries a cloud provider (AWS/Azure) to generate the list in real-time.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a task that only runs when "notified" by another task. Unlike regular tasks, they only run once at the end of the play, regardless of how many times they were notified. Triggered using the `notify` keyword.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
It is the configuration file for Ansible. Common settings: `remote_ interpreters`, `inventory`, and `forks`.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
`register` saves the output of a task into a variable. You access it in the next task using the variable name (e.g., `{{ result.stdout }}`).

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
- `import_tasks`: Static. Processed at the start of the play. Cannot be used with `when` on the import itself.
- `include_tasks`: Dynamic. Processed at runtime. Can be used with `when` to conditionally include a file.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Galaxy is a public repository for Ansible roles and collections. To use `requirements.yml`, run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins determine how Ansible communicates with the target.
- `ssh`: Standard remote execution via SSH.
- `local`: Executes tasks on the control node (e.g., updating local files).
- `network_cli`: Executes commands via a CLI (e.g., interacting with a Cisco switch via `conf t`).

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
- `delegate_to`: Runs a task on a different host than the current one in the loop.
- `run_once`: Ensures a task runs only once even if the play is targeting multiple hosts.
**Example:** Gather a public IP from a remote web server, then use `delegate_to: localhost` and `run_once: true` to update a DNS record on the control node.

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs.**
1. **Forks:** Increase `forks` in `ansible.cfg` to run more tasks in parallel. *Tradeoff: Higher CPU/Memory on control node.*
2. **Pipelining:** Enable `pipelining` to reduce the number of SSH connections. *Tradeoff: Requires specific SSH config.*
3. **Fact Caching:** Use Redis/Memcached to store facts. *Tradeoff: Complexity of managing a cache.*
4. **Mitogen:** Use the Mitogen plugin for faster execution. *Tradeoff: Third-party dependency.*

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
- `{{ }}`: Expressions (outputting values).
- `{% %}`: Statements (loops, if-statements).
- `{# #}`: Comments (ignored by Ansible).
**Snippet:**
```jinja2
upstream backend_servers {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }} comment "Health check: {{ server.name }}";
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, and health checks with uri module, and rollback strategy on failure using block/rescue.**
1. Use `serial: 2` to update 2 servers at a time.
2. **Pre-task:** Use `uri` module to remove the server from the Load Balancer (LB).
3. **Deployment:** Update the app code/service.
4. **Health Check:** Use `uri` module to verify the app returns `200 OK`.
5. **Post-task:** Re-add the server to the LB.
6. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, if the health check fails, trigger a task to redeploy the previous version and notify the team.
