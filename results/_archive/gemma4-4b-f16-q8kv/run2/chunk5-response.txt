**Go Questions**

G1: An array has a fixed size defined at compile time (e.g., `[5]int`), while a slice is a dynamically sized, flexible view into an underlying array. When appending to a slice that reaches capacity, Go allocates a new, larger underlying array (usually doubling the capacity), copies the existing elements, and then appends the new element.

G2: `var x int` declares a variable `x` and initializes it to its zero value (0 for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when redeclaring a variable within the same scope, or when declaring a variable outside of a function body (at the package level).

G3: A goroutine is a lightweight, independently executing function managed by the Go runtime, not the OS. It is much cheaper than an OS thread (requiring only a few KB of stack space vs. MBs). The Go scheduler (GMP model) maps many goroutines (G) onto a smaller pool of OS threads (M), managed by a set of logical processors (P). This allows Go to efficiently utilize multi-core CPUs while managing concurrency overhead.

G4: Channels are typed conduits through which you can send and receive values between goroutines, enforcing synchronization. An unbuffered channel requires both the sender and receiver to be ready simultaneously for the communication to proceed (rendezvous). A buffered channel has a fixed capacity; sends block only when the buffer is full, and receives block only when the buffer is empty. Sending to a full buffered channel causes the sending goroutine to block until a receiver frees up a slot.

G5: The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines.
Example:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // Always call cancel to release resources

req, err := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
// ... proceed with client.Do(req)
```

G6: Go uses implicit interface satisfaction: a type satisfies an interface if it implements all the methods defined by that interface, without needing to explicitly declare it. This differs from Java/C# where explicit implementation is often required. The empty interface `interface{}` (or `any`) can hold a value of any type. It is powerful because it allows for maximum flexibility (e.g., generic functions), but it is dangerous because it requires runtime type assertions or type switches to use the underlying value, leading to potential runtime panics if the type is incorrect.

G7: This is unsafe due to data races. Go's memory model guarantees that writes to shared variables are visible across goroutines *only* if synchronization primitives (like channels or mutexes) are used. The write to `data` and `ready` happens concurrently without synchronization. The loop `for !ready {}` spins, potentially reading a stale, uninitialized value of `ready` from a CPU cache, leading to an infinite loop or incorrect output. The correct alternatives are: 1) Using a channel to signal completion (`<-doneChan`), or 2) Using a `sync.WaitGroup` or `sync.Mutex` to protect access.

G8: `sync.Mutex` provides exclusive locking, ensuring only one goroutine can hold the lock at a time (read or write). `sync.RWMutex` allows multiple readers to access the resource concurrently (`RLock`/`RUnlock`), but requires exclusive access for writers (`Lock`/`Unlock`). Use `sync.Map` when you have a high volume of concurrent reads and writes to a map where keys are frequently added or deleted, as it is optimized for concurrent access without requiring external locking. Use a regular map with a mutex when the access pattern is more complex, or when the overhead of `sync.Map` is not justified. Performance trade-offs: `RWMutex` is faster for read-heavy workloads; `sync.Map` avoids explicit locking overhead but can have higher overhead for simple, single-key operations.

G9: Go modules manage dependencies. `go.mod` lists the required modules and their version constraints (e.g., `require github.com/pkg/errors v0.9.1`). `go.sum` contains cryptographic checksums for the exact content of every dependency listed in `go.mod`, ensuring build reproducibility and integrity. `go mod tidy` cleans up the module file by adding missing dependencies and removing unused ones. MVS (Minimum Version Selection) is an algorithm that selects the highest possible version of a dependency that satisfies all version constraints specified in the `go.mod` file, ensuring the most up-to-date, compatible code is used.

G10: A `defer` statement schedules a function call to be executed just before the surrounding function returns. Multiple defers execute in Last-In, First-Out (LIFO) order. A common gotcha in a loop is that if the deferred function captures a loop variable by reference, all deferred calls will reference the *final* value of that loop variable after the loop completes, not the value it held during each iteration.

G11: A pointer in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

G12: The `init()` function is a special function that runs automatically before the `main` function (or before any other code in the package) is executed. It runs exactly once per package initialization. A package can have multiple `init()` functions; they execute sequentially in the order they appear in the source code.

G13: `make` is used to initialize built-in reference types (slices, maps, channels). It allocates and returns a usable, initialized structure. `new` allocates memory for a value of a specified type and returns a pointer to the zero-initialized value of that type. `make` works with slices, maps, and channels; `new` works with any type.

G14: Error handling in Go is explicit and idiomatic, relying on returning an `error` type as the last return value. The `error` interface is a built-in interface with a single method: `Error() string`. The idiomatic pattern is `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain contains a specific sentinel error value. `errors.As(err, &target)` checks if the error chain contains a value that matches a specific type, allowing you to extract structured error information.

G15:
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be written to until initialized with `make`).
*   **Slice:** `[]Type`. Zero value: `nil` (a slice header pointing to a nil underlying array).
*   **Channel:** `chan Type`. Zero value: `nil` (a channel header pointing to a nil channel).
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.

G16: A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization mechanism. The `-race` flag instruments the Go runtime to detect these unsynchronized concurrent memory accesses. Example: Two goroutines incrementing a shared counter without a mutex. Fix: Use `sync.Mutex` to wrap the increment operation, or use atomic operations (`sync/atomic`).

G17: The `select` statement waits on multiple communication operations (channel receives/sends) simultaneously. It differs from `switch` because `select` is specifically designed for concurrency and channel operations. When multiple cases are ready, `select` chooses one pseudo-randomly. A timeout is implemented by adding a `time.After(duration)` channel case to the `select` block.

G18: Escape analysis is a compiler optimization that determines whether a variable's data should be allocated on the stack (fast, automatic cleanup) or the heap (slower, managed by the garbage collector). The compiler decides based on how long the variable's lifetime is expected to exceed the scope of the function call. You can inspect this using the `-m` flag during compilation. It matters because stack allocation is significantly faster than heap allocation due to avoiding GC overhead and pointer indirection.

G19: The `reflect` package allows a program to inspect and manipulate its own structure (types, values, methods) at runtime. `reflect.Type` describes the structure of a value (e.g., "this is a struct with two fields"). `reflect.Value` holds the actual runtime data of a value. Reflection incurs significant performance costs because the compiler cannot optimize calls involving reflection; it must perform dynamic lookups at runtime. Reflection is justified when building generic frameworks, serialization libraries, or tools that must operate on arbitrary types, whereas code generation is preferred for performance-critical paths.

G20: The `go:embed` directive allows embedding files or directories directly into a Go binary as assets. It works by instructing the compiler to read the specified path and make its contents available as a variable of type `embed.FS` (or `string`/`[]byte`). For directories, it creates an in-memory file system representation. Limitations include that it only works at compile time. It interacts with `io/fs.FS` by providing a concrete implementation of that interface, allowing standard library functions designed for file systems to read embedded assets without touching the disk.

**Rust Questions**

R1: Ownership is Rust's system for managing memory safety without a garbage collector. It dictates that every value in Rust has a single variable that is its *owner*. The three rules are: 1) Each value has one owner. 2) When the owner goes out of scope, the value is dropped (memory is freed). 3) Ownership can be transferred (moved) from one variable to another.

R2: `String` is a heap-allocated, growable, mutable string type (owned data). `&str` is a string slice—a borrowed, immutable view into string data (either owned or static). Use `String` when you need to own and modify the string data (e.g., building a string in a loop). Use `&str` in function signatures when you only need to read the string data, as it avoids unnecessary heap allocations and is more flexible.

R3: Borrowing allows you to refer to data without taking ownership. The borrow checker enforces rules: 1) You can have any number of immutable references (`&T`) to a piece of data simultaneously (shared access). 2) You can have *only one* mutable reference (`&mut T`) to a piece of data at any given time (exclusive access). This prevents data races at compile time.

R4: `Option<T>` is an enum representing the presence or absence of a value: `Some(T)` or `None`. `Result<T, E>` is an enum representing success or failure: `Ok(T)` or `Err(E)`. The `?` operator is syntactic sugar for propagating errors or unwrapping `Option`s. If the expression evaluates to `Ok(T)`, it unwraps `T` and continues. If it evaluates to `Err(E)`, it immediately returns `Err(E)` from the current function.
Example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> io::Result<String> {
    let mut file = File::open(path)?; // Propagates io::Error if file not found
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates io::Error if read fails
    Ok(contents)
}
```

R5:
*   **`Box<T>`:** A smart pointer that allocates data on the heap. Used when you need to put a type behind a trait object or when the size of a type is unknown at compile time (recursive types). It owns the data.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data on the heap. It keeps a count; the data is dropped only when the last `Rc` pointer goes out of scope. Used for single-threaded shared ownership.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>` but uses atomic operations for reference counting, making it safe to share ownership across multiple threads.

R6: Traits define shared behavior (like interfaces). They specify a set of methods that a type must implement. They compare to Go interfaces in that they define *what* a type can do, but Rust traits are often used for generic programming (compile-time polymorphism). A trait object (`dyn Trait`) is a dynamically dispatched pointer (like an interface in Go) that holds any type implementing the trait. A generic with a trait bound (`T: Trait`) uses static dispatch, meaning the compiler generates specialized code for each concrete type used, resulting in zero runtime overhead.

R7: Lifetimes (`'a`) ensure that references remain valid for as long as they are used. The function fails because the returned reference (`&str`) might point to a string slice (`x` or `y`) that goes out of scope when `longest` returns. The fix is to annotate the return lifetime:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
This tells the compiler that the returned reference will live no longer than the shortest lifetime of its inputs (`x` and `y`).

R8: `Send` means a type can be safely transferred (moved) to another thread. `Sync` means a type can be safely referenced across threads (i.e., `&T` where `T: Sync` is safe to share). You cannot send an `Rc<T>` across threads because its internal reference counter is not atomic, leading to race conditions during counting. `Arc<T>` is safe for concurrent use because its reference counting mechanism uses atomic CPU instructions, ensuring thread-safe increments and decrements.

R9: Rust's async/await is built on the concept of `Future`s. A `Future` is a trait representing a value that *might* be available later. When you call an async function, it returns a `Future` immediately, without blocking the thread. The executor (like Tokio) polls this `Future` repeatedly. If the future is not ready, the executor parks the task and moves on to poll other ready futures. This differs from Go's goroutines because Rust's async is *cooperative* (tasks yield control explicitly via `await`), whereas Go's goroutines are *preemptive* (the scheduler interrupts them).

R10: `unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. Three things you can do: 1) Dereference raw pointers (`*const T`, `*mut T`). 2) Call `unsafe` functions (FFI). 3) Access or modify mutable static variables. Unsafe code is justified only when interfacing with external C libraries (FFI), implementing highly optimized data structures, or when the programmer can mathematically prove that the safety invariants will be maintained.

R11: Pattern matching uses the `match` keyword to compare a value against a series of patterns. `if let` is syntactic sugar used to conditionally destructure a value if it matches a specific pattern, executing a block only if the match succeeds. `match` is exhaustive; the compiler forces you to handle every possible variant of the enum or pattern, preventing runtime errors from unhandled cases.

R12: `Vec<T>` is a dynamically sized, heap-allocated, growable collection. An array `[T; N]` has a fixed size `N` known at compile time and is typically allocated on the stack. When `Vec` pushes elements beyond its current capacity, it allocates a new, larger contiguous block of memory (often doubling the capacity), copies all existing elements to the new block, and then adds the new element.

R13: Enums in Rust are powerful algebraic data types that can hold different types of data in their variants (unlike C/Java enums which are usually just integer constants). `Option<T>` is an enum variant of `Some(T)` or `None`. Rust does not have null because `None` (or `Err`) explicitly models the *absence* of a value as a valid, type-safe state, forcing the programmer to handle that case explicitly.

R14: The `impl` block defines methods and associated functions for a specific type.
*   `&self`: Borrows the instance immutably; methods can read the data but not change it.
*   `&mut self`: Borrows the instance mutably; methods can read and modify the data.
*   `self`: Takes ownership of the instance; the method consumes the instance (often used for consuming/transforming the object).
Associated functions (like `String::new()`) are functions associated with the type but do not operate on a specific instance; they are called using the type name.

R15: A derive macro automatically implements standard traits for a struct or enum based on its definition. Examples: `#[derive(Debug)]` allows printing the struct nicely; `#[derive(Clone)]` allows deep copying; `#[derive(PartialEq)]` allows comparison (`==`); `#[derive(Serialize)]` allows serialization (requires external crates like Serde). You cannot derive a trait if the type contains fields that do not implement the required trait (e.g., if a field is a raw pointer that doesn't implement `Clone`).

R16: `Cow<'a, T>` (Clone On Write) is a smart pointer that can hold either an owned value (`T`) or a borrowed reference (`&'a T`). It is useful when you receive data that might need modification, but you want to avoid an allocation if the data is never changed. If the data is immutable, it holds a reference (zero cost). If a mutation is required, it clones the data into an owned state (`T`) and performs the write.

R17: Rust's module system organizes code hierarchically. `mod` declares a module (which can map to a file or a block). `use` brings items from a module into the current scope for easier access. `pub` makes items accessible outside the current module. The file system maps to modules: a file named `foo.rs` typically defines the `foo` module. The 2018 edition introduced significant changes, notably allowing modules to be defined in separate files (e.g., `mod foo;` in `lib.rs` pointing to `foo.rs`) and improving the module resolution path.

R18: `Pin<T>` is a wrapper that guarantees that a value `T` will not be moved in memory after it has been pinned. This is crucial for self-referential structs (where a part of the struct holds a pointer to another part of the *same* struct) because moving the struct would invalidate the internal pointer. In async/await, `Pin` ensures that the state machine generated by the compiler remains stable in memory across `.await` points, allowing the executor to safely resume execution. `Unpin` is a marker trait indicating that a type *can* be safely moved.

R19: Declarative macros (`macro_rules!`) are pattern-matching macros that operate on tokens, similar to a sophisticated `match` statement. Procedural macros (derive, attribute, function-like) are custom macros written as separate crates that *write* Rust code. They are far more powerful. Hygiene rules prevent macro expansions from accidentally capturing or interfering with local variables defined within the scope where the macro is used, ensuring that the generated code is isolated and correct.

R20: Zero-cost abstractions mean that high-level language features (like generics and iterators) compile down to machine code that is as fast as if the programmer had written the equivalent low-level C code manually. This is achieved primarily through **monomorphization** (generics): the compiler generates a unique, specialized version of the code for every concrete type used, eliminating runtime type checks. **Trait static dispatch** (used with generics) resolves method calls at compile time, avoiding the overhead of virtual function tables (v-tables) associated with dynamic dispatch.
