**DN1**
**Class:** A reference type. Instances are allocated on the managed heap, and variables hold a reference (pointer) to the object. Classes support inheritance and complex behavior.
**Struct:** A value type. Instances are typically allocated on the stack (or inline within containing types). Structs are best for small, simple data aggregates where copying the value is cheap and intended.
**When to use a struct:** When the type represents a small, immutable value (e.g., a point, a color, a coordinate) and you want to avoid heap allocation overhead.

**DN2**
**IEnumerable<T>:** Represents a sequence that can be iterated over. It supports *deferred execution*; the query logic is not executed until the consumer starts iterating (e.g., in a `foreach` loop). It operates in memory.
**IQueryable<T>:** Represents an expression tree that describes a query. It allows the query to be translated into a provider-specific query language (like SQL) and executed remotely (e.g., against a database).
**Distinction:** Using `IQueryable<T>` allows filtering and projection to happen on the database server, minimizing data transfer. Converting it to `IEnumerable<T>` (e.g., using `.ToList()`) forces immediate execution and pulls all data into memory.

**DN3**
**Async/Await:** C# uses the `async` keyword to mark a method that can pause execution without blocking the thread, and `await` to suspend execution until an asynchronous operation completes. The compiler transforms this into a state machine that manages the continuation of the method.
**Task vs ValueTask:**
*   **Task:** Represents an asynchronous operation that might involve heap allocation (it's a reference type).
*   **ValueTask:** A struct that can represent an asynchronous operation. It avoids heap allocation when the operation completes synchronously or is very small, offering performance benefits.
**When to use ValueTask:** When you anticipate that the asynchronous operation might frequently complete synchronously, thus avoiding the overhead of allocating a `Task` object on the heap.

**DN4**
**Dependency Injection (DI):** A design pattern where components receive their dependencies from an external source (the DI Container) rather than creating them internally. This promotes loose coupling and testability.
**Service Lifetimes:**
1.  **Transient:** A new instance is created every single time it is requested.
2.  **Scoped:** A single instance is created per scope (e.g., per HTTP request in ASP.NET Core).
3.  **Singleton:** A single instance is created for the entire application lifetime.
**Bug:** Injecting a Scoped service into a Singleton service. The Singleton resolves the Scoped service once during its own construction. This single instance of the Scoped service is then held by the Singleton for the entire application lifetime, violating the intended per-request scope and leading to potential concurrency or state leakage bugs.

**DN5**
**string:** An immutable sequence of characters. Operations on strings (like concatenation or substring extraction) always result in the creation of a new string object in memory.
**ReadOnlySpan<char>:** A type that provides a safe, high-performance, stack-allocated *view* over a contiguous block of memory (like a string's underlying buffer). It does not copy the data.
**When to use Span<T>:** When performing high-performance string manipulation, parsing, or buffer processing where minimizing heap allocations is critical. It allows you to work with string segments without creating intermediate string objects.

**DN6**
**Garbage Collector (GC):** An automatic memory management system in .NET that tracks and reclaims memory occupied by objects that are no longer reachable by the application.
**Generations:** The GC divides managed heap memory into generations to optimize collection frequency:
*   **Gen 0:** Where short-lived objects are allocated. Collected most frequently.
*   **Gen 1:** Acts as a buffer between Gen 0 and Gen 2.
*   **Gen 2:** Where long-lived objects reside. Collected least frequently.
**Large Object Heap (LOH):** A separate area of the heap reserved for objects larger than a certain threshold (typically 85KB). Objects here are not compacted by the GC, which can lead to memory fragmentation.
**IDisposable:** Implements the `IDisposable` interface to allow deterministic cleanup of *unmanaged* resources (e.g., file handles, network sockets, database connections). The GC only handles *managed* memory; `IDisposable` ensures resources that require explicit release are freed immediately via the `using` statement.

**DN7**
**ConfigureAwait(false):** When used on an awaitable, it tells the runtime *not* to capture the current `SynchronizationContext`.
**Default Behavior:** By default, the runtime attempts to resume the continuation of the method on the original context (e.g., the UI thread in WPF/WinForms).
**When to use it:** In library code or background services where you do not need to resume on the original context. This prevents potential deadlocks and reduces overhead by avoiding context switching.
**When NOT to use it:** In UI code where the continuation *must* run back on the UI thread to safely update UI elements.
**SynchronizationContext:** This object captures the context (like the UI thread affinity) when an `await` is encountered. `ConfigureAwait(false)` bypasses this capture mechanism.

**DN8**
**Primary Constructors:** Allows defining constructor parameters directly in the class signature, which can then be used to initialize properties.
**Collection Expressions:** A concise syntax (`[]`, `{}`) for creating collections (lists, dictionaries, sets) in a single expression.
**FrozenDictionary:** A dictionary that is immutable after creation, providing thread-safe, read-only access.
**Example (Primary Constructor with DI):**
```csharp
public class UserService(ILogger<UserService> logger)
{
    private readonly ILogger<UserService> _logger = logger;
    public void LogUserActivity(string user) => _logger.LogInformation($"User {user} logged in.");
}
// In Program.cs:
builder.Services.AddScoped<UserService>();
```

**DN9**
**Diagnosis:** The likely cause is that the `DbContext` instance is being shared across multiple concurrent requests or threads without proper isolation. `DbContext` is **not thread-safe** and is designed to be scoped to a single unit of work (usually one HTTP request). High concurrency causes multiple threads to attempt to modify the same context state simultaneously, leading to race conditions and `ObjectDisposedException` when the context is prematurely disposed or accessed concurrently.
**Fix:** Ensure that the `DbContext` is registered with a **Scoped** lifetime in the DI container. This guarantees that a new, isolated instance is created for every incoming request, and that instance is disposed of correctly when the request finishes.

**DN10**
**Class:** A reference type that uses reference equality by default. It is mutable and designed for complex objects.
**Record:** A reference type designed for modeling immutable data. It automatically provides value equality semantics (two records are equal if all their properties are equal, regardless of memory location).
**Record Struct:** A value type that combines the immutability and value equality of a record with the stack allocation benefits of a struct.
**Choice:** Use **Record** when modeling data transfer objects (DTOs) or entities where immutability and value equality are desired. Use **Class** when modeling complex entities that require mutable state or inheritance hierarchies. Use **Record Struct** for small, immutable value types.

**DN11**
**ref:** Passes the variable by reference, allowing the method to modify the original variable. The variable *must* be initialized before being passed to the method.
**out:** Passes the variable by reference, but the method is responsible for assigning a value to it before returning. The variable does *not* need to be initialized before being passed.
**in:** Passes the variable by reference, but guarantees that the method will only read the value (read-only reference). This is used for performance optimization when passing large structs.
**Usage:** Use `ref` when you need to read and write to an existing variable. Use `out` when the method is responsible for producing the result. Use `in` when you need high-performance read-only access to a large structure.

**DN12**
**Nullable Reference Types (NRTs):** Enabled via `#nullable enable`. The compiler tracks whether a reference type variable *might* be null. If a variable is declared as `string?`, the compiler warns if you try to use it without checking for null, enforcing null safety at compile time.
**Nullable Value Types (`int?`):** These are actual types (`Nullable<int>`) that wrap a value type. They can hold a value or the special `null` state at runtime.
**Difference:** NRTs are a *compile-time* safety feature for reference types; Nullable value types are a *runtime* feature that allows value types to represent the absence of a value.

**DN13**
**LINQ (Language Integrated Query):** A set of features in C# that allows developers to write queries against various data sources (collections, databases, XML) using a unified syntax.
**Method Syntax:** Uses extension methods (fluent API). Example: `list.Where(x => x.Age > 30).OrderBy(x => x.Name)`.
**Query Syntax:** Uses SQL-like syntax. Example: `from x in list where x.Age > 30 orderby x.Name`.
**Deferred Execution:** The query expression itself is not executed immediately when written. It is only executed when the results are enumerated (e.g., when calling `.ToList()`, `.ToArray()`, or iterating over the result).

**DN14**
**Generic Constraints:** Rules placed on type parameters (`T`) to restrict the types that can be used when instantiating a generic class or method.
*   **`where T : class`:** T must be a reference type.
*   **`where T : struct`:** T must be a value type.
*   **`where T : new()`:** T must have a public parameterless constructor.
*   **`where T : IComparable<T>`:** T must implement the `IComparable<T>` interface, allowing instances of T to be compared to each other.
**Combining Constraints:** You combine them using the `and` keyword (e.g., `where T : class, new(), IComparable<T>`) to ensure the type meets all specified requirements simultaneously.

**DN15**
**Abstract Class:** A class that cannot be instantiated directly. It can contain both abstract members (methods/properties without implementation) and concrete members (fully implemented methods). It is used to provide a common base implementation and structure for derived classes.
**Interface:** A contract that defines a set of methods and properties that implementing classes *must* adhere to. It defines *what* a class can do, not *how* it does it.
**Default Interface Methods (C# 8+):** This feature allows interfaces to include method implementations. This blurs the line by allowing interfaces to provide default behavior, making them more useful for backward compatibility or providing baseline functionality without forcing all implementers to rewrite code.

**DN16**
**Middleware Pipeline:** A series of software components (middleware) that process HTTP requests and responses sequentially in ASP.NET Core. Each middleware component can inspect, modify, or terminate the request/response cycle.
**`app.Use()`:** Registers standard middleware components (e.g., Authentication, Routing, Static Files). These are typically executed in sequence.
**`app.Map()`:** Maps a specific route or path segment to a specific endpoint or handler, effectively branching the pipeline.
**`app.Run()`:** Terminates the pipeline for the current request, usually used as the final endpoint handler.
**Ordering:** Order is critical. For example, Authentication middleware must run *before* Authorization middleware.
**Exception Handling:** Exception middleware is typically placed near the beginning of the pipeline. If any downstream middleware throws an exception, the request is caught by this middleware, allowing it to format a standardized error response (e.g., HTTP 500) instead of letting the raw exception bubble up.

**DN17**
**Channel<T>:** A high-performance, asynchronous, thread-safe queue provided by `System.Threading.Channels`. It is designed for producer-consumer scenarios in asynchronous applications.
**Comparison to BlockingCollection<T>:** `BlockingCollection<T>` is synchronous and thread-safe, often used in older multi-threaded blocking scenarios. `Channel<T>` is asynchronous (`await` based) and integrates seamlessly with `async/await`.
**Bounded Channel Backpressure:** A bounded channel has a fixed capacity. If the producer attempts to write to a full bounded channel, the `await channel.Writer.WriteAsync(item)` call will asynchronously block (backpressure) until a consumer reads an item, freeing up space.

**DN18**
**Source Generators:** A feature in the C# compiler that allows developers to write code that generates other C# source code *during* the compilation process.
**Difference from Reflection/IL Weaving:**
*   **Reflection:** Inspects types and metadata *at runtime*. Slow.
*   **IL Weaving:** Modifies the Intermediate Language (IL) *after* compilation. Complex and invasive.
*   **Source Generators:** Generate clean, standard C# source code *before* compilation, allowing the compiler to process it normally. This is faster and safer.
**Incremental Generator:** A generator that tracks which source files or inputs have changed. It only regenerates the output code if the relevant inputs have been modified, drastically speeding up build times compared to a standard generator that re-runs entirely on every build.

**DN19**
**TPL Dataflow:** A library for building asynchronous, data-flow pipelines. It allows developers to chain processing blocks together to handle streams of data efficiently.
**ActionBlock:** Executes an action (a delegate) on incoming messages. It is designed for executing work items asynchronously.
**TransformBlock:** Receives an input message, applies a transformation function to it, and outputs the result. It is used for data manipulation within the pipeline.
**BufferBlock:** Acts as a queue. It buffers incoming messages until a downstream block is ready to process them.
**Comparison to Channels:** Channels are a low-level, stream-based queue mechanism. TPL Dataflow is a higher-level abstraction that provides pre-built, interconnected processing *blocks* (like a specialized assembly line) for complex pipeline orchestration.

**DN20**
**Minimal APIs:** A lightweight, modern approach in ASP.NET Core where HTTP endpoints are defined directly using lambda expressions within the `Program.cs` file, bypassing the need for traditional MVC controllers.
**Differences from Controllers:**
*   **Controllers:** Provide structure, separation of concerns, and are ideal for large, complex business logic.
*   **Minimal APIs:** Are highly concise and ideal for simple microservices or rapid prototyping.
**Trade-offs:**
*   **Testability:** Controllers often offer clearer boundaries for unit testing complex logic. Minimal APIs can sometimes blur the line between routing and business logic.
*   **Middleware:** Both support middleware, but controllers integrate more naturally with established MVC patterns.
*   **OpenAPI Support:** Both can support OpenAPI, but Minimal APIs require explicit configuration to generate the schema.
**Route Groups and Endpoint Filters:** Route groups allow applying common middleware or configuration (like versioning or authorization policies) to a set of related endpoints. Endpoint filters allow executing logic (like logging or validation) immediately before or after an endpoint executes, regardless of the endpoint's internal code.

**P1**
**List:** A mutable, ordered sequence of items. Items can be added, removed, or changed after creation.
**Tuple:** An immutable, ordered collection of items. Once created, its contents cannot be changed.
**Set:** An unordered collection of unique items. It is mutable.
**Frozenset:** An immutable version of a set. Because it is immutable, it can be used as an element within another set or as a dictionary key.

**P2**
**GIL (Global Interpreter Lock):** A mutex that protects access to Python objects, ensuring that only one thread executes Python bytecode at any given time within a single process.
**Workloads Affected:** CPU-bound tasks (heavy computation) are severely limited because threads spend most of their time waiting for the GIL to be released, leading to little to no true parallel execution.
**Workarounds:**
1.  **`multiprocessing`:** Uses separate OS processes, each with its own Python interpreter and memory space, thus bypassing the GIL. Ideal for CPU-bound tasks.
2.  **`asyncio`:** Ideal for I/O-bound tasks (network requests, disk reads). It uses cooperative multitasking within a single thread, yielding control during waiting periods, which is efficient without needing multiple threads.

**P3**
**Shallow Copy:** Creates a new container object, but populates it with *references* to the objects found in the original. If the original and the copy contain nested mutable objects (like lists within a list), modifying the nested object in the copy will also modify it in the original, as they point to the same memory.
**Deep Copy:** Recursively creates entirely new copies of all objects found in the original structure, ensuring the copy is completely independent of the original.
**Example of Shallow Copy Failure:**
```python
original = [{'value': 1}]
shallow_copy = original.copy() # Shallow copy
shallow_copy[0]['value'] = 99 # Modifying the nested dict
print(original[0]['value']) # Output: 99 (Original was modified)
```

**P4**
**Decorators:** Syntactic sugar in Python that allows a function to be wrapped by another function (the decorator). The decorator takes a function as input, adds functionality around it, and returns the modified function.
**Timing Decorator Example:**
```python
import time
from functools import wraps

def timing_decorator(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start_time = time.time()
        result = func(*args, **kwargs)
        end_time = time.time()
        print(f"Function {func.__name__} executed in {end_time - start_time:.4f} seconds.")
        return result
    return wrapper

@timing_decorator
def slow_function(n):
    sum(i*i for i in range(n))

slow_function(1000000)
```

**P5**
**Generators and `yield`:** A generator is a special type of iterator that produces values one at a time, on demand, using the `yield` keyword. Instead of building the entire result set in memory, it pauses execution and returns a value, resuming from that exact point when the next value is requested. This makes them extremely memory efficient for large datasets.
**Difference from Returning a List:** Returning a list forces the entire dataset to be computed and stored in memory immediately. Generators compute and yield values lazily.
**`yield from`:** This delegates the iteration to a sub-generator. It allows a generator function to delegate part of its work to another generator, effectively chaining generators together seamlessly.

**P6**
**Asyncio Event Loop:** The core mechanism of `asyncio`. It is a single-threaded loop that manages and schedules coroutines (async functions). When a coroutine encounters an `await` (indicating an I/O wait), it yields control back to the event loop, allowing the loop to switch context and run other ready coroutines instead of blocking the thread.
**Function Differences:**
*   `asyncio.run(coro)`: Runs the top-level coroutine and manages the event loop lifecycle (starts and stops it).
*   `asyncio.gather(*coros)`: Runs multiple awaitables concurrently and waits for all of them to complete, returning a list of their results.
*   `asyncio.create_task(coro)`: Schedules a coroutine to run concurrently on the event loop immediately, returning a `Task` object that can be awaited later.
**Why `time.sleep()` fails:** `time.sleep()` is a *blocking* call. When called inside an `async` function, it halts the entire thread, which means it halts the single-threaded event loop, preventing *any* other scheduled coroutines from running until the sleep is over. You must use `await asyncio.sleep(delay)` instead, which is a non-blocking yield point.

**P7**
**MRO (Method Resolution Order):** The algorithm Python uses to determine the order in which base classes are searched when looking up a method or attribute in a class hierarchy.
**Algorithm:** Python 3 uses the **C3 Linearization Algorithm**. This algorithm ensures that the MRO is consistent, deterministic, and respects the local precedence order (the order classes are listed in the inheritance tuple).
**Diamond Inheritance:** When a class inherits from two classes that share a common ancestor (the diamond shape), C3 ensures that the common ancestor is listed only once in the MRO, and the order respects the inheritance path.
**Output Explanation:** `D` inherits from `B` and `C`. `B` inherits from `A`. `C` inherits from `A`. The MRO for `D` will be `(D, B, C, A, object)`. When `D().who()` is called, Python checks `D`, then `B` (which inherits from `A`), then `C`. Since `C` defines `who()`, that method is found and executed, returning `"C"`.

**P8**
**Metaclass:** The "class of a class." A metaclass controls *how* a class itself is created. When you define `class MyClass(metaclass=MyMeta):`, the metaclass is responsible for building the `MyClass` object.
**`__init_subclass__` vs Metaclass:**
*   **Metaclass:** Intervenes at the *class creation* level (before the class object exists). It fundamentally changes the structure or behavior of the class definition itself.
*   **`__init_subclass__`:** A class method that runs *after* a subclass has been created. It is used for configuration, registration, or modifying the subclass's attributes post-creation.
**Practical Use Cases:**
*   **Metaclass:** Enforcing API structure (e.g., ensuring every class inheriting from a base API class has specific required methods defined).
*   **`__init_subclass__`:** Automatically registering all subclasses into a central registry (e.g., a plugin system where subclasses are discovered and registered upon definition).

**P9**
**Threading:** Uses threads within a single process. Threads share the same memory space. Best for **I/O-bound** tasks (waiting for network/disk) where the GIL is released during waiting periods. Limited by the GIL for CPU-bound work.
**Multiprocessing:** Uses separate OS processes. Each process has its own memory space and interpreter, completely bypassing the GIL. Best for **CPU-bound** tasks (heavy calculation).
**Concurrent.futures:** A high-level abstraction layer that provides a unified interface (`Executor`) to manage both thread pools and process pools, abstracting away the low-level details of `threading` vs `multiprocessing`.
**Serialization Implications:** When using `multiprocessing`, data must be passed between processes via Inter-Process Communication (IPC). This requires **pickling** (serialization) to convert Python objects into a byte stream that can be sent across process boundaries, and then unpickling them on the receiving end.

**P10**
**`__slots__`:** A class attribute that explicitly declares the attributes an instance of the class will have. By defining slots, Python skips the creation of the instance's internal `__dict__` attribute.
**When to use it:** When creating classes that are instantiated millions of times (e.g., data points, nodes in a graph) where memory footprint is critical.
**What it prevents:** It prevents the instance from dynamically adding new attributes after initialization.
**Memory Impact:** It significantly reduces memory consumption per instance because the overhead of the instance dictionary (`__dict__`) is eliminated.

**P11**
**Virtual Environment:** An isolated directory containing a specific Python interpreter and its own set of installed packages. It prevents dependency conflicts between different projects on the same machine.
**Why use one:** To ensure that Project A, which requires Django 2.0, does not break Project B, which requires Django 4.0.
**Differences:**
*   **`venv`:** The standard, built-in module in Python 3. Used for creating lightweight, standard virtual environments.
*   **`virtualenv`:** An older, third-party tool that offers more features and compatibility across different Python versions than the standard `venv`.
*   **`conda`:** A comprehensive package and environment manager (often used in data science). It manages not just Python packages but also non-Python dependencies (like specific versions of CUDA or R libraries).

**P12**
**Comprehensions:** Concise, readable syntax for creating collections based on existing iterables.
*   **List Comprehension:** `[x * 2 for x in numbers if x > 0]`
*   **Dict Comprehension:** `{k: v*2 for k, v in items.items()}`
*   **Set Comprehension:** `{x for x in numbers}`
**Relation to map() and filter():** Comprehensions are syntactic sugar that combine the functionality of `map()` (transformation) and `filter()` (selection) into a single, readable line.
**Preference:** Comprehensions are generally preferred in modern Python because they are more idiomatic, often faster, and significantly clearer than chaining `map()` and `filter()` calls.

**P13**
**`==` vs `is`:**
*   `==` (Equality): Compares the *values* of two objects. It calls the object's `__eq__` method.
*   `is` (Identity): Compares the *identity* of two objects. It checks if both variables point to the exact same object in memory (i.e., if they have the same `id()`).
**Object Interning:** A memory optimization technique where Python pre-allocates and caches small, immutable objects (like small integers, e.g., -5 to 256, and short strings).
**Why `a is b` returns True:** When Python sees `a = 10` and `b = 10`, it often reuses the same object instance for both `a` and `b` because 10 is within the interned range, meaning they share the same memory address.

**P14**
**`*args`:** Collects any number of positional arguments passed to a function into a **tuple**.
**`**kwargs`:** Collects any number of keyword arguments passed to a function into a **dictionary**.
**Positional-Only (`/`):** Arguments listed before `/` *must* be passed by position and cannot be passed using a keyword argument name.
**Keyword-Only (`*`):** Arguments listed after `*` *must* be passed using their keyword name; positional arguments are not allowed for them.
**Example:** `def func(a, b, /, c, *, d):`
*   `a` and `b` must be positional.
*   `c` can be positional or keyword.
*   `d` must be keyword.

**P15**
**Context Managers (`with` statement):** A mechanism that guarantees that setup actions are performed before a block of code runs, and corresponding teardown actions are performed afterward, even if errors occur within the block.
**`__enter__/__exit__`:** Implementing these methods in a class makes it a context manager. `__enter__` runs on entry (returns the resource), and `__exit__` runs on exit (handles cleanup).
**`@contextmanager`:** A simpler way to create a context manager using a generator function. The code before `yield` is the setup, and the code after `yield` is the teardown.
**Example (Beyond File Handling):** Managing a database transaction.
```python
from contextlib import contextmanager

@contextmanager
def db_transaction():
    conn = connect_to_db()
    try:
        yield conn # Setup complete, yield connection
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close() # Teardown
```

**P16**
**Type Hinting:** The practice of adding optional type annotations to variables, function parameters, and return values in Python. It does not change runtime behavior but allows external static analysis tools to check for type errors.
**Key Types:**
*   **`typing.Union[A, B]`:** Indicates a variable can be of type A OR type B.
*   **`typing.Optional[A]`:** Shorthand for `Union[A, None]`. Indicates the variable can be A or None.
*   **`typing.Literal[value]`:** Restricts a variable to only accept a specific, fixed value (e.g., `Literal["read", "write"]`).
*   **`typing.TypeVar`:** A placeholder used to define generic types, similar to generics in C#.
*   **`typing.Protocol`:** Defines structural typing (duck typing). A class conforms to a Protocol if it implements the required methods/attributes, regardless of explicit inheritance.
**Static Analysis:** Tools like Mypy or Pyright read these hints and build a type graph of the code. They then traverse this graph to statically verify that operations are only performed on types that support those operations, catching bugs before execution.

**P17**
**Data Model (Dunder Methods):** Special methods (prefixed and suffixed with double underscores, e.g., `__init__`) that define how Python objects interact with built-in language features.
**`__repr__` vs `__str__`:**
*   `__repr__`: The "official" string representation, intended for developers. It should ideally be unambiguous and allow recreation of the object (e.g., `ClassName(arg1=value1)`).
*   `__str__`: The "informal" string representation, intended for end-users (should be readable).
**`__eq__` vs `__hash__`:**
*   `__eq__`: Defines value equality (when `a == b` is true).
*   `__hash__`: Returns an integer hash value used by hash-based collections (sets and dictionaries) to quickly locate items.
**Consequence of Missing `__hash__`:** If you define `__eq__` to override the default object equality, you *must* also define `__hash__` consistently. If you define `__eq__` but not `__hash__`, Python will raise a `TypeError` if you try to use that object as a key in a dictionary or add it to a set, because the hash value would be unpredictable.

**P18**
**Descriptors:** Objects that define how attribute access (getting, setting, or deleting) works for other objects. They implement the descriptor protocol.
**Descriptor Protocol:**
*   `__get__(self, instance, owner)`: Called when the attribute is accessed.
*   `__set__(self, instance, value)`: Called when the attribute is assigned a value.
*   `__delete__(self, instance)`: Called when the attribute is deleted.
**Usage by Built-ins:**
*   **Property:** A descriptor that controls attribute access, allowing you to run methods instead of accessing raw data.
*   **classmethod:** A descriptor that binds a method to the class rather than the instance.
*   **staticmethod:** A descriptor that binds a method to the class but ensures it is called without a reference to the class or instance.

**P19**
**Import System:** The mechanism Python uses to locate and load modules (code files).
**Relative vs Absolute Imports:**
*   **Absolute:** Imports start from the root of the Python path (e.g., `import package_name.module`).
*   **Relative:** Imports reference modules relative to the current package location (e.g., `from . import sibling_module` or `from ..utils import helper`).
**System Components:**
*   **`sys.path`:** A list of directories that Python searches when an `import` statement is executed.
*   **`PYTHONPATH`:** An environment variable that adds directories to `sys.path` before the script runs.
*   **`__init__.py`:** Historically, this file marked a directory as a Python package, allowing imports from it. (Less critical in modern namespace packages).
*   **Namespace Packages:** Allow a single package to be split across multiple directories/packages without requiring an `__init__.py` in every subdirectory.
**Finder and Loader:** A **Finder** is responsible for locating the module (finding the file path). A **Loader** is responsible for loading the module object from that path and executing its code.

**P20**
**Dataclasses:** A decorator (`@dataclass`) that automatically generates boilerplate methods (like `__init__`, `__repr__`, `__eq__`) for classes primarily used to hold data.
**Comparison to attrs and Pydantic:**
*   **`attrs`:** Similar to dataclasses, focuses on reducing boilerplate and providing robust object construction.
*   **Pydantic:** Focuses heavily on **runtime data validation** and serialization/deserialization using Python type hints.
**Features:**
*   **`__post_init__`:** A method that runs immediately after the standard `__init__` method completes, allowing for post-construction logic (e.g., calculating a derived field).
*   **Field Factories:** Allows defining default values that are computed dynamically rather than being static constants.
*   **Frozen Dataclasses:** Setting `frozen=True` makes the instance immutable, similar to a `typing.Final` object.
**When to choose Pydantic:** Choose Pydantic when the data coming into your system (e.g., from an API request body) *must* conform to a strict schema, and you need automatic validation, coercion, and serialization capabilities. Dataclasses are better when the object is purely an internal, trusted data structure.
