K1 — A Deployment manages the desired state of replicated Pods, ensuring updates are rolled out gracefully. A StatefulSet manages stateful applications, providing stable, unique network identifiers and persistent storage for each Pod instance (e.g., database primary/replica).

K2 — A ClusterIP assigns a stable, internal virtual IP address to the Service. `kube-proxy` running on every node watches the Kubernetes API for Service and Endpoint changes. It configures the node's networking rules (usually via iptables or IPVS) to intercept traffic destined for the ClusterIP and redirect it to one of the healthy Pod IPs backing that Service.

K3 — **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator or dynamically. It is the actual storage resource. **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a request object that binds to an available PV that meets its requirements (size, access mode). **StorageClass:** A class of storage that defines *how* the PV should be dynamically provisioned (e.g., using AWS EBS, NFS, or local storage). They relate as: PVC requests storage $\rightarrow$ StorageClass dictates the type $\rightarrow$ PV is provisioned and bound to the PVC.

K4 — 1. **Check Pod Events:** Use `kubectl describe pod <name>` to check the `Events` section for specific failure reasons (e.g., ImagePullBackOff, CrashLoopBackOff details). 2. **Check Logs:** Use `kubectl logs <pod-name>` to see the application's stdout/stderr output leading up to the crash. 3. **Check Resource Limits:** Verify the Pod spec for CPU/Memory limits. If the crash is due to exceeding limits, the container will be OOMKilled or CPU throttled. 4. **Check Image/Config:** Ensure the container image exists, is accessible, and the configuration files (ConfigMaps/Secrets) are correctly mounted and accessible by the application.

K5 — CoreDNS acts as the cluster's internal DNS service, translating Kubernetes Service names (e.g., `my-service.my-namespace.svc.cluster.local`) into the cluster's internal ClusterIPs. If CoreDNS pods are down, internal DNS resolution fails entirely. Pods cannot resolve other services within the cluster by name, leading to connection timeouts and application failures, although external DNS resolution might still function if the node's underlying `/etc/resolv.conf` is configured correctly.

K6 — The scheduler uses a two-phase process: **Filtering** (Predicates) and **Scoring** (Priorities).
1. **Filtering (Predicates):** Determines which nodes are *eligible* to run the pod. If a node fails any predicate check, it is eliminated. Examples include: checking resource availability (CPU/Memory), checking node selectors, and checking taints/tolerations.
2. **Scoring (Priorities):** Ranks the remaining eligible nodes. The scheduler assigns a score to each node based on various factors, and the node with the highest score is chosen.
Specific factors considered include:
    *   **Least Requested Priority:** Preferring nodes with the most available resources.
    *   **Node Affinity/Anti-Affinity:** Matching the pod's desired placement rules.
    *   **Volume Zone/Topology Spread:** Ensuring pods are spread across different failure domains or zones.

K7 — **Scheduling:** Yes, the pod *will* be scheduled, provided the node has enough *available* capacity after accounting for existing requests. The scheduler only checks against *requests*, not limits. Available RAM = 4GB - 3.5GB = 0.5GB. The pod requests 256Mi, which is less than 0.5GB.
**Runtime Behavior:** If the pod uses 600Mi at runtime, it will exceed its defined limit (512Mi). The Kubernetes Kubelet will enforce this limit, and the container runtime will terminate the process, resulting in the pod entering a `OOMKilled` state.

K8 — 1. **External LB:** The external load balancer (e.g., AWS ELB, GCP LB) receives traffic on a public IP/port and forwards it to the Ingress Controller node(s). 2. **Ingress Controller:** The controller (e.g., NGINX) receives the request, inspects the host/path rules defined in the Ingress resource, and determines which backend Service should handle the request. 3. **Service:** The Ingress Controller forwards the request to the Service's ClusterIP. 4. **Endpoints:** The Service object maintains an Endpoints object, which lists the actual IP addresses of all healthy Pods backing that Service. The Service abstraction uses this list. 5. **kube-proxy/iptables:** `kube-proxy` on the node intercepts traffic destined for the Service ClusterIP and uses iptables rules to randomly or round-robin select one of the healthy Pod IPs from the Endpoints object, forwarding the packet directly to the target Pod.

K9 — A NetworkPolicy is a Kubernetes resource that defines rules about how groups of Pods are allowed to communicate with each other and with external network endpoints. If no NetworkPolicy exists in a namespace, the default behavior is **allow-all** (all ingress and egress traffic is permitted). When you apply a NetworkPolicy that selects certain pods, the default behavior changes to **default deny** for traffic not explicitly allowed by the policy.

K10 — **RollingUpdate:** Updates are performed gradually by creating new ReplicaSets and slowly scaling down the old ones while scaling up the new ones. This allows for zero-downtime deployments. **Recreate:** The old Pods are terminated completely before the new Pods are created. This results in downtime proportional to the time it takes to spin up the new replicas. You would choose Recreate only when the application cannot handle traffic during a transition period, or when the change is so fundamental that a clean restart is required (e.g., changing the underlying OS image).

K11 — A namespace is a mechanism for partitioning cluster resources across multiple virtual clusters within a single physical cluster. It provides scope isolation for names, preventing naming collisions. Default namespaces include: `default` (for general workloads), `kube-system` (for core Kubernetes components like DNS and scheduler), and `kube-public` (for publicly accessible resources).

K12 — `kubectl describe pod <name>` provides a detailed status report of the Pod, including: 1. **Events:** A chronological log of actions taken on the pod (e.g., scheduling, pulling image, starting container). 2. **Conditions:** The current state of the pod (e.g., Running, Pending, Succeeded) and why it is in that state. 3. **Resource Usage/Limits:** Detailed information on requested and limited CPU/Memory resources assigned to the containers.

K13 — A ConfigMap is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) in key-value pairs. A pod can consume it in two primary ways: 1. **As Environment Variables:** By mounting the ConfigMap data directly into the container's environment variables. 2. **As Volume Mounts:** By mounting the ConfigMap as a file system volume inside the container, allowing the application to read configuration files directly.

K14 — **ClusterIP:** Exposes the Service internally within the cluster using a stable virtual IP. Only reachable from within the cluster. **NodePort:** Exposes the Service on a specific port on *every* Node's IP address. This allows external access via `<NodeIP>:<NodePort>`. **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes external traffic to the Service's nodes.

K15 — A DaemonSet ensures that a copy of a specific Pod runs on *every* (or a selected subset of) eligible Node in the cluster. You use it when you need a cluster-level service that must run locally on every node, such as log collectors (Fluentd/Logstash), node monitoring agents (Prometheus Node Exporter), or network plugins.

K16 — **Taints and Tolerations:** Taints are applied to Nodes to *repel* Pods. A Pod must have a matching Toleration to be scheduled onto a tainted Node. **Node Affinity:** Is a scheduling preference that *attracts* Pods to specific Nodes (e.g., "only schedule this pod on nodes labeled 'gpu'"). **Difference:** Taints/Tolerations are a hard mechanism for exclusion/inclusion, whereas Affinity is a soft preference used by the scheduler to guide placement.
*   *Taints Use Case:* Preventing general workloads from running on a dedicated GPU node.
*   *Affinity Use Case:* Ensuring a database replica Pod is scheduled on a node that is geographically close to the primary database Pod.

K17 — A Kubernetes Operator is a method of packaging, deploying, and managing a complex application. It extends the Kubernetes API by defining custom resources (CRDs) and implementing a control loop that watches the state of that custom resource. It differs from a standard controller because it encapsulates deep, domain-specific operational knowledge (e.g., backup procedures, failover logic, scaling specific database clusters) that a generic controller cannot handle. The Operator pattern solves the problem of automating complex, human-driven operational tasks.

K18 — Kubernetes uses the **Raft consensus algorithm** for etcd. Raft ensures strong consistency by requiring a majority (quorum) of nodes to agree on any write operation before it is committed. If the etcd quorum is lost (e.g., 2 out of 3 nodes fail), the cluster cannot achieve consensus, and the API server will become unavailable for writes, effectively halting cluster state changes. Recovering from 2 out of 3 nodes being permanently lost is impossible because the remaining single node cannot form a quorum, and the cluster state is effectively lost/unreachable.

K19 — RBAC (Role-Based Access Control) governs who can do what to which resources. **Role:** Defines a set of permissions (verbs like `get`, `list`, `create`) scoped to a specific namespace. **ClusterRole:** Defines a set of permissions scoped across the entire cluster (cluster-wide). **RoleBinding:** Binds a specific Role to a specific User/Group within a specific namespace. **ClusterRoleBinding:** Binds a specific ClusterRole to a specific User/Group cluster-wide.
*RBAC Manifests for Read-Only Pod/Log Access in 'my-namespace':*
```yaml
# 1. Define the permissions (Role)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# 2. Bind the permissions to a user/group (RoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: my-namespace
subjects:
- kind: User
  name: developer-user # Replace with actual user/group
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — When external DNS resolution is slow, it often indicates excessive recursive queries. The `ndots` setting in `/etc/resolv.conf` dictates how many dots (`.`) a DNS resolver must encounter before it performs a recursive query to the root hints. If `ndots` is set too low (e.g., 1), the resolver will attempt to resolve the entire FQDN (e.g., `www.example.com`) against the local search domains first, even if the domain is known to be external. This forces many unnecessary iterative queries. To fix this, you use `dnsConfig` in the Pod spec to override the default DNS settings, explicitly setting `ndots` to a higher value (e.g., 5) or providing a specific `nameservers` list that handles external resolution efficiently.

D1 — **git merge** integrates changes from one branch into another by creating a new "merge commit," preserving the history of both branches. **git rebase** rewrites history by moving or combining a sequence of commits to a new base commit, resulting in a cleaner, linear history. You should avoid rebasing commits that have already been pushed to a shared, public repository, as rewriting shared history causes significant synchronization problems for collaborators.

D2 — **TCP (Transmission Control Protocol):** Connection-oriented. It establishes a reliable, ordered, and error-checked connection before data transfer (three-way handshake). Protocols: HTTP(S), FTP. **UDP (User Datagram Protocol):** Connectionless. It sends packets without establishing a formal connection, prioritizing speed over guaranteed delivery. Protocols: DNS, VoIP.

D3 — A race condition occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared mutable state. **Example:** Two threads simultaneously try to increment a shared counter variable initialized to 0. Thread A reads 0, Thread B reads 0. Thread A calculates 1 and writes 1. Thread B calculates 1 and writes 1. The expected result is 2, but the actual result is 1 because the operations overlapped.

D4 — **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is fast and used for encrypting the bulk data. **Asymmetric Encryption:** Uses a pair of mathematically linked keys: a public key (for encryption, shared widely) and a private key (for decryption, kept secret). It is computationally intensive and used primarily for secure key exchange.
**TLS Usage:** Asymmetric encryption (RSA/ECC) is used during the initial handshake to securely exchange a temporary, random symmetric session key. Once the key is exchanged, symmetric encryption is used for the high-speed transfer of application data.

D5 — A container image layer is a read-only, immutable filesystem layer that stores the changes made during a specific instruction in the Dockerfile. Each instruction (e.g., `RUN`, `COPY`) creates a new layer on top of the previous one. Layer caching is crucial: if a layer's instruction and its context (files) have not changed since the last build, Docker reuses the cached layer, drastically speeding up subsequent builds. Best practice dictates placing instructions that change infrequently (like installing OS packages) early in the Dockerfile, and instructions that change often (like copying application code) later.

D6 — 1. **Check Application Logs:** Look for specific errors (stack traces, exceptions) indicating why the service is failing or timing out. 2. **Check Dependencies:** Verify connectivity and health of external services (databases, caches, microservices) the API relies on. 3. **Check Resource Saturation:** Monitor CPU/Memory usage on the API server instances to see if they are being throttled or are running out of memory. 4. **Check Network/Load Balancer:** Verify the load balancer health checks are passing and that network latency between the LB and the service is acceptable.

D7 — The CAP theorem states that a distributed data store can only guarantee two out of three properties simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest write), and **Partition Tolerance** (the system continues to operate despite arbitrary message loss or failure of part of the system).
*   **CP System (Consistency over Availability):** Systems like traditional relational databases (e.g., PostgreSQL cluster) often choose CP. If a network partition occurs, the system will refuse requests to the minority side of the partition to prevent inconsistent reads.
*   **AP System (Availability over Consistency):** Systems like Cassandra or DynamoDB choose AP. During a partition, nodes continue to accept reads and writes, ensuring availability, but data might temporarily diverge until the partition heals (eventual consistency).

D8 — **Horizontal Scaling (Scaling Out):** Increasing the number of instances (replicas) of an application to handle more load. This is achieved by adding more commodity servers/pods. **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) allocated to an *existing* instance.
Architectural patterns enabling horizontal scaling include: **Statelessness** (ensuring no session data is tied to a single instance), **Load Balancing** (distributing traffic evenly across many instances), and **Microservices** (breaking the application into small, independently scalable services).

D9 — An environment variable is a dynamic named value that can affect the way running processes will behave on a computer. To set one that persists across shell sessions on Linux, you must add the export command (e.g., `export MY_VAR="value"`) to your shell's startup configuration file, typically `~/.bashrc` or `~/.zshrc`, and then run `source ~/.bashrc`.

D10 — **JSON (JavaScript Object Notation):** A lightweight data-interchange format using key-value pairs and arrays. Advantage: Extremely easy for JavaScript/web clients to parse natively. **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that relies heavily on indentation. Advantage: Highly readable and concise for configuration files. JSON uses braces `{}` and quotes `""`; YAML uses indentation and colons `:`.

D11 — A REST (Representational State Transfer) API is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD (Create, Read, Update, Delete) operations on resources identified by URLs.
*   **GET:** Retrieves a representation of a resource (Read). Should be idempotent and safe (no side effects).
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource (Create). Not idempotent.
*   **PUT:** Replaces all current representations of the target resource with the request payload (Update/Replace). Idempotent.
*   **DELETE:** Removes the specified resource (Delete). Idempotent.

D12 — Version pinning is the practice of explicitly defining the exact version number of a dependency (e.g., `library@1.2.3`) rather than using a broad range (e.g., `library@^1.0.0`). It is vital for reproducible builds because it guarantees that the build environment will use the exact same dependency code every time, preventing unexpected runtime failures caused by upstream library authors making breaking changes in minor or patch releases.

D13 — **Compiled Language:** Source code is translated entirely into machine code (or bytecode) by a compiler *before* execution. Examples: C++, Go. **Interpreted Language:** Source code is read and executed line-by-line by an interpreter *during* runtime. Examples: Python, JavaScript.

D14 — **Reverse Proxy:** Sits in front of one or more web servers and forwards client requests to them. It acts as an intermediary for the *server*. **Forward Proxy:** Sits in front of a client and forwards client requests to the internet. It acts as an intermediary for the *client*.
*   **Nginx:** Common reverse proxy. Use case: SSL termination and load balancing across multiple application servers.
*   **HAProxy:** Common reverse proxy. Use case: High-performance, sophisticated traffic routing based on complex health checks and session persistence.

D15 — A deadlock is a situation where two or more competing actions are waiting for the other to finish, resulting in a permanent standstill. The four necessary conditions (Coffman conditions) are:
1. **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2. **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3. **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily.
4. **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

D16 — Eventual consistency is a consistency model where, if no new updates are made to a given data item, all reads will eventually return the last updated value. Distributed databases like Cassandra handle read-after-write consistency by using **Quorum**. A write operation must be acknowledged by $W$ replicas, and a read operation must query $R$ replicas. If $W + R > N$ (where $N$ is the total number of replicas), strong consistency is achieved. Tunable consistency levels allow the developer to choose $W$ and $R$ based on the required trade-off between latency and data freshness.

D17 — mTLS (mutual TLS) requires *both* the client and the server to authenticate each other using digital certificates during the TLS handshake. The process is: 1. Client initiates connection. 2. Server sends its certificate. 3. Client verifies the server's certificate against its trusted CA list. 4. Server requests the client's certificate. 5. Client sends its certificate. 6. Server verifies the client's certificate against its trusted CA list. 7. If both validations pass, a secure, encrypted channel is established. mTLS is commonly used in service meshes (like Istio) and secure microservice communication to ensure zero-trust networking.

D18 — A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an array. **Collision Resolution:**
*   **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hash to that index.
*   **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing).
**Time Complexity:**
*   Average Case (Good Hash Function/Low Load): Insertion, Lookup, Deletion are $O(1)$.
*   Worst Case (All keys hash to the same bucket): Insertion, Lookup, Deletion are $O(n)$.

D19 — The circuit breaker pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing microservice), thereby preventing resource exhaustion and cascading failures across the entire system.
*   **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the breaker trips to Open.
*   **Open:** Requests are immediately rejected without attempting the call, failing fast. After a timeout, the breaker moves to Half-Open.
*   **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker closes; if they fail, it returns to Open.
This pattern complements retry policies by preventing the system from overwhelming a struggling dependency, while exponential backoff ensures that retries are spaced out to give the failing service time to recover.

D20 — **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data record *before* any modification or read that could lead to a conflict. This guarantees data integrity but can severely reduce concurrency and throughput. *Example:* Using `SELECT ... FOR UPDATE` in SQL to lock a row immediately upon reading it.
**Optimistic Concurrency Control:** Assumes conflicts are rare. It allows multiple transactions to read the data concurrently. Before committing, it checks if the data has been modified by another transaction since it was read (usually via a version number or timestamp). If the version has changed, the transaction fails and must be retried. *Example:* Using a `version` column in the database and including it in the `WHERE` clause of the `UPDATE` statement.
