**OpenTofu / Terraform**

T1 — **tofu plan** generates an execution plan, showing exactly what actions (create, update, delete) OpenTofu intends to perform without making any changes to the infrastructure. **tofu apply** executes the plan, making the actual changes to the cloud resources based on the generated plan.

T2 — State is a mapping file (usually stored remotely) that records the real-world state of the infrastructure resources managed by OpenTofu, linking the configuration in HCL to the actual IDs and attributes in the cloud. Remote state is crucial because it provides a single source of truth, enables collaboration among team members, and ensures state persistence across runs, preventing configuration drift and data loss.

T3 — **`count`** creates multiple identical instances of a resource based on an integer value (e.g., `count = 3`). **`for_each`** creates multiple instances based on the elements of a map or a set (e.g., `for_each = toset(["a", "b"])`). `for_each` is preferred when the instances need to be uniquely identifiable by a specific key or name, as it allows referencing the instance by its key (e.g., `each.key`), whereas `count` only allows referencing by index (e.g., `count.index`).

T4 — If a resource is manually changed outside of OpenTofu, the next `tofu plan` will detect this discrepancy. OpenTofu compares the desired state (in HCL) with the actual state (read from the cloud provider via the state file). It will report a "drift" and propose an action (usually an update) to reconcile the actual state with the desired state, or it may flag the change as an unmanaged drift if the change is outside the scope of the configuration.

T5 — ```hcl
resource "aws_instance" "vm" {
  count = 3
  ami           = "ami-0abcdef1234567890" # Example AMI
  instance_type = "t2.micro"

  tags = {
    Name = "web-${count.index + 1}"
  }
}
```

T6 — **`terraform_remote_state` data source** is used to read the state file of *another* remote backend (e.g., reading the output of a module deployed to a different S3 bucket). **Output values** are used to expose specific attributes from the *current* module's resources to consumers (e.g., exposing an IP address). The recommended alternative for sharing data between root modules is to use **module outputs** combined with **module inputs**. This keeps the dependency explicit, localizes the data flow, and avoids coupling the root modules to the specific backend configuration of another module.

T7 — This is a classic race condition. The `null_resource` with the `remote-exec` provisioner runs *during* the apply phase, but the output value is only finalized *after* the resource is fully provisioned and the provisioner has completed. If the dependent resource tries to read this output immediately, the value might not be available yet, leading to an empty or null value. The fix is to use an **explicit dependency** via `depends_on` on the dependent resource, ensuring it only runs *after* the `null_resource` has successfully completed its provisioner.

T8 — `tofu import` allows you to bring existing, manually created infrastructure resources under the management of OpenTofu without having to write the configuration code first. Its limitation is that it only imports the *current* state; it does not automatically generate the corresponding HCL configuration. The import block (1.5+) improves this by allowing you to specify the resource type and local name *within* the configuration file, making the import process declarative and tying the state directly to the configuration structure from the start.

T9 — A **variable** is a placeholder for input data that allows the configuration to be reusable and parameterized (e.g., defining a region or instance size). An **output** is a value exposed by a module or configuration that allows other parts of the infrastructure (or users) to retrieve information about the deployed resources (e.g., the public IP address of a load balancer).

T10 — A **provider** is a plugin that OpenTofu uses to interact with a specific API or service (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without `tofu init`, OpenTofu will fail because it has not downloaded or configured the necessary provider plugins specified in the configuration, meaning it cannot communicate with the target cloud API.

T11 — The `.terraform.lock.hcl` file records the exact versions and checksums of every provider and module dependency used in the configuration. It should be committed to version control to ensure that every developer and every CI/CD pipeline uses the *exact same* dependency versions, guaranteeing reproducible builds and preventing unexpected behavior caused by upstream provider updates.

T12 — `tofu destroy` tears down all resources managed by the current state file. To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web_server`).

T13 — A **data source** allows OpenTofu to fetch information about existing infrastructure or external data that is *not* managed by the current configuration. Example: Using a `aws_ami` data source to look up the latest Amazon Linux 2 AMI ID, rather than hardcoding it, ensuring the configuration always uses the most current image.

T14 — **Variables** are used for external, user-provided inputs (e.g., `variable "instance_count" {}`). **Locals** are used for internal, derived values *within* the configuration itself (e.g., calculating a subnet CIDR block based on two input variables). Use locals when the value is derived from other configuration elements, ensuring cleaner, self-contained logic within the module, rather than cluttering the input interface with intermediate calculations.

T15 — The **lifecycle block** controls how OpenTofu manages the resource's lifecycle.
*   **`create_before_destroy`**: Ensures a new resource is created successfully *before* the old one is destroyed, preventing downtime during replacement (use case: replacing a database instance).
*   **`prevent_destroy`**: Prevents the resource from being deleted via `tofu destroy` or `tofu apply` (use case: critical production resources like a primary database).
*   **`ignore_changes`**: Tells OpenTofu to ignore specific attributes that might be modified manually or by external processes (use case: ignoring a `last_modified_date` attribute that the cloud provider updates automatically).

T16 — A **moved block** is a directive used within the configuration to tell OpenTofu that a resource has been logically relocated (e.g., moved from one module to another, or renamed) but that its underlying identity (its state) must be preserved. This allows refactoring the code structure without forcing OpenTofu to destroy and recreate the resource, thus avoiding service interruption.

T17 — OpenTofu builds a **dependency graph** by analyzing resource references. **Implicit dependencies** occur when one resource references an attribute of another (e.g., `subnet_id = aws_vpc.main.default_subnet_id`). OpenTofu automatically infers this dependency. **Explicit dependencies** are declared using `depends_on`. `depends_on` forces a specific execution order regardless of attribute references. Using it sparingly is crucial because it can break OpenTofu's ability to parallelize operations; if dependencies are over-declared, the plan runs sequentially, drastically increasing execution time.

T18 — 1. **Modularization:** Break the 200+ resources into smaller, independent modules. This allows OpenTofu to plan and apply modules in parallel. 2. **Targeting/Filtering:** Use `-target` judiciously during testing or maintenance to only plan/apply specific, small subsets of resources. 3. **State Splitting:** If possible, split the monolithic state file into multiple, smaller state files based on functional domains (e.g., networking state, compute state). 4. **Provider Optimization:** Review provider configurations to ensure they are not performing unnecessary polling or complex lookups on every run. *Tradeoff:* Modularization adds complexity in managing module interfaces and dependencies.

T19 — State locking ensures that only one operation (plan or apply) can modify the state file at any given time, preventing concurrent writes that could corrupt the state. If a lock is not released (e.g., CI pipeline crash), the state file remains locked, causing all subsequent operations to fail with a "state is locked" error. To manually break a lock, you typically use a provider-specific CLI command (e.g., `aws sts assume-role` or specific backend commands) to force the lock release. The risk is high: if the lock is broken while an operation is *actually* running, it can lead to severe state corruption.

T20 — **Step 1: Backup:** Download the current local state file (`terraform state pull`) and store it securely. **Step 2: Configure Backend:** Update the OpenTofu configuration (`backend "s3" {}`) to point to the target S3 bucket, DynamoDB table (for locking), and region. **Step 3: Migrate State:** Run `tofu state push` (or use the specific backend migration command if available/necessary). This uploads the local state to the remote backend. **Step 4: Verification:** Run `tofu plan`. If the plan executes successfully and shows no drift, the migration is successful. The old local state file can then be deleted.

**Ansible**

A1 — A **playbook** is a YAML file that defines a set of desired states (the overall workflow). A **role** is a standardized, reusable structure within a playbook that groups related tasks, handlers, variables, and templates (e.g., a `webserver` role). A **task** is a single action within a playbook or role, defining *what* should be done (e.g., "ensure Nginx is installed").

A2 — `ansible_facts` is a dictionary containing system information gathered by Ansible about the target host during the connection phase (e.g., OS distribution, memory, network interfaces). To access the OS family, you would use `ansible_facts['os_family']`.

A3 — **`command`** executes a simple command string directly on the remote host, treating it as a shell command without shell features (like pipes or redirection). **`shell`** executes a command through the host's shell (e.g., `/bin/bash`), allowing complex shell scripting. **`raw`** is similar to `command` but is used when you are executing commands directly on the control node itself, not the remote host. Use `command` for simple, atomic operations; use `shell` for complex scripting; use `raw` for control node execution.

A4 — Idempotency means that running a task multiple times yields the same result as running it once; the system state does not change after the first successful run.
*   **Idempotent Example:** `ansible.builtin.package: name=nginx state=present` (Ansible checks if Nginx is installed; if so, it does nothing).
*   **Non-Idempotent Example:** `ansible.builtin.command: echo "Hello" >> /tmp/log.txt` (This command appends "Hello" every time it runs).

A5 — ```yaml
- name: Install specific packages based on OS
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
```

A6 — The variable precedence order (highest to lowest priority) is:
1.  `--extra-vars` (CLI overrides)
2.  `host_vars` (Host-specific variables)
3.  `group_vars` (Group-specific variables)
4.  `role_vars` (Variables defined within a specific role)
5.  `defaults` (Variables defined in the role's `defaults/main.yml`)
6.  `vars` (Variables defined in the playbook/role scope)

A7 — This requires a combination of inventory grouping, `serial`, and potentially `wait_for` if the RKE2 agent needs to signal readiness.
1.  **Inventory:** Define groups: `[initial_nodes]` (the first 3) and `[remaining_nodes]` (the other 47).
2.  **Playbook Structure:** Use `serial: 3` on the play targeting `[initial_nodes]`.
3.  **Execution Flow:** Run the play targeting `[initial_nodes]`. Once complete, run a second play targeting `[remaining_nodes]` with `serial: 10` (or whatever batch size is desired). `wait_for` can be used within the tasks to pause until a specific service port is open on the node before proceeding.

A8 — `ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible configuration files. To encrypt a single variable without encrypting the entire file, you must use the vault mechanism to encrypt *only* that specific variable definition within the `vars` file, often by using the vault password when loading the file, or by using the `ansible-vault encrypt` command on the specific line/block.

A9 — An **inventory file** lists the hosts that Ansible will manage, grouping them logically (e.g., `[webservers]`, `[databases]`). A **static inventory** is a manually defined file (e.g., `hosts.ini`). A **dynamic inventory** is a script or plugin that generates the inventory list on the fly by querying an external source, such as AWS EC2, VMware vCenter, or a CMDB.

A10 — ```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

A11 — A **handler** is a special task that is only executed when explicitly notified by another task. It is designed for actions that should only run *after* a change has occurred (e.g., restarting a service). It differs from a regular task because it is not executed sequentially; it is queued and run only once at the end of the play if notified. You trigger a handler using the `notify:` keyword in a task.

A12 — The `ansible.cfg` file configures Ansible's behavior globally for a project. Common settings include:
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Defines the default SSH user to connect as.
3.  `host_key_checking`: Controls whether Ansible verifies the host's SSH key (set to `False` for convenience, but discouraged in production).

A13 — The `register` keyword captures the return value of a task (stdout, stderr, return code, etc.) and stores it in a variable. You use the registered variable in a subsequent task by referencing it using the dot notation (e.g., `{{ result.stdout }}`).
*Example:* `register: check_disk` followed by `debug: var: "{{ check_disk.stdout }}"`.

A14 — **`include_tasks`** reads and executes tasks from a specified file *within the current playbook structure*. **`import_tasks`** reads and executes tasks from a specified file and *stops* execution of the current playbook until the imported file is complete. Use `import_tasks` for modularizing large, self-contained components (like roles). Use `include_tasks` when you need to conditionally include or override tasks based on runtime logic within the main playbook.

A15 — Ansible Galaxy is a community repository where users share reusable Ansible content (roles, collections, plugins). You use a `requirements.yml` file to declare dependencies. The command `ansible-galaxy install -r requirements.yml` reads this file and automatically downloads and installs all specified roles and collections into the local Ansible Galaxy cache.

A16 — Connection plugins define *how* Ansible connects to the target host.
*   **`ssh`**: The standard, most common method; uses SSH to execute commands remotely.
*   **`local`**: Executes tasks directly on the Ansible control node itself (no network connection needed).
*   **`network_cli`**: Used for managing network devices (routers, switches) via CLI protocols (like Telnet or SSH, but specialized for network gear).

A17 — **`delegate_to`** forces a task to run on a host *other than* the one defined in the play's inventory. **`run_once`** ensures that a task, even if run across multiple hosts, executes only one time across the entire managed group.
*Practical Example:* You want to gather the list of all public IPs from 50 remote web servers, but you only want to write this list to a central configuration file on the control node. You would run the gathering task on all hosts, but delegate the final writing task to `localhost` using `delegate_to: localhost` and `run_once: true`.

A18 — 1. **Increase Forks:** Increase the `forks` setting in `ansible.cfg` to run more hosts in parallel (Tradeoff: Increased resource usage on the control node). 2. **Pipelining:** Use pipelining to send multiple commands to a single remote host in one SSH session, reducing connection overhead (Tradeoff: Can complicate error handling). 3. **Fact Caching:** Use `fact_caching` to store gathered facts locally or remotely, preventing Ansible from re-running expensive fact-gathering modules on every run (Tradeoff: Requires persistent storage). 4. **Mitogen/Tower/AWX:** Use a dedicated automation controller to manage job scheduling, concurrency, and state across hundreds of hosts (Tradeoff: Significant infrastructure overhead).

A19 — Jinja2 templating allows dynamic content generation.
*   **`{{ variable }}`**: Used for outputting the value of a variable.
*   **`{% control_structure %}`**: Used for control flow logic (loops, conditionals, assignments).
*   **`{# comment #}`**: Used for comments that are stripped from the final rendered output.
*Snippet:* ```nginx
upstream backend_servers {
{% for server in backend_list %}
    server {{ server.ip }}:{{ server.port }}; # Health check target
{% endfor %}
}
```

A20 — This requires a controlled, phased approach:
1.  **Serial Batches:** Use `serial: 5` (or similar) in the play to ensure only 5 servers are updated at a time.
2.  **Pre-Task (LB Registration):** Before updating the batch, run a task that uses the `uri` module to register the current batch of servers with the load balancer, marking them as healthy.
3.  **Update Task:** Run the configuration update task (e.g., deploying the new code).
4.  **Health Check Task:** After deployment, run a task using `uri` to actively check the health endpoint of the newly updated servers. If the check fails, the play should fail immediately.
5.  **Post-Task (LB Deregistration):** If the health check passes, run a task to mark the servers as healthy in the LB. If the health check fails, the `block/rescue` structure catches the failure, and the `rescue` block executes a task to *deregister* the servers from the LB, effectively rolling back the traffic shift before the next batch starts.
