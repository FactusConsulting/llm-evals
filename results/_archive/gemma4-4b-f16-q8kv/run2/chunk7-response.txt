JS1 — `var` is function-scoped and hoisted (initialized as `undefined`). `let` and `const` are block-scoped and are hoisted but remain in the Temporal Dead Zone (TDZ) until declaration. Hoisting is JavaScript's behavior of moving declarations to the top of their scope during compilation, but only the declaration, not the assignment.

JS2 — The Event Loop is the mechanism that manages the execution of code, ensuring non-blocking I/O in JavaScript. The Call Stack executes synchronous code. When asynchronous operations (like network requests or timers) complete, their callbacks are placed into queues. The Event Loop continuously checks if the Call Stack is empty; if it is, it pulls tasks from the queues. Microtasks (e.g., Promise callbacks) are prioritized and drained completely before the Event Loop checks the Macrotask Queue (e.g., `setTimeout`, I/O).

JS3 — A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). Practically, it allows an inner function to access variables from its outer function even after the outer function has finished executing. The classic for loop closure bug occurs because the loop variable (`i`) is shared across all iterations; when the callbacks execute, `i` has reached its final value. The fix is to use `let` in the loop declaration (`for (let i = 0; ...)`), which creates a new binding for `i` in each iteration.

JS4 — A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. `async/await` is syntactic sugar built on top of Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()` or `try...catch` blocks around `await`. `Promise.all()` rejects immediately if *any* input promise rejects. `Promise.allSettled()` waits for *all* input promises to either fulfill or reject, returning an array of status objects describing the outcome of each.

JS5 — An `interface` in TypeScript defines a contract—a shape that an object must adhere to. It is purely a compile-time construct and cannot be instantiated. A `type` alias can define unions, intersections, primitives, or complex object shapes. Use `interface` when defining object shapes that might be extended (declaration merging). Use `type` when defining unions, tuples, or complex mapped types. Discriminated unions are a union type where each member has a common, literal property (the "discriminant"). This allows TypeScript to narrow down the type safely using a `switch` statement based on that property's value.

JS6 — Prototypal inheritance means that objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. `Object.create(proto)` creates a new object whose internal `[[Prototype]]` link points directly to the specified `proto` object. ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance mechanism; they provide a cleaner, more familiar syntax for defining constructor functions and prototype chains without changing how inheritance fundamentally works under the hood.

JS7 — The `this` keyword refers to the object that is currently executing the function. The binding rules, in priority order, are: 1. `new` binding (when called with `new`). 2. Explicit binding (`.call()`, `.apply()`, `.bind()`). 3. Implicit binding (when called as a method on an object). 4. Default binding (when called globally/in strict mode, `this` is `undefined` or the global object). `bind()` returns a *new* function with the specified `this` context permanently bound to it. Yes, you can re-bind the returned function, but the original function's context is fixed by the first binding.

JS8 — `WeakRef` provides a weak reference to an object, meaning the garbage collector can reclaim the object even if a `WeakRef` points to it. `FinalizationRegistry` allows you to register a callback function that will be executed *after* the associated object has been garbage collected. They are used to perform cleanup or logging on objects without preventing them from being collected. WeakMap keys must be objects because primitive values (like strings or numbers) are compared by value, which would prevent the garbage collector from ever seeing the key as "unreferenced."

JS9 — V8 optimizes JS using several techniques. **Hidden Classes** (or Maps) allow V8 to represent objects with the same structure (same property order/types) using a single internal structure, avoiding the overhead of dynamic property lookups. **Inline Caching** stores the expected type/shape of an object at the call site, allowing subsequent accesses to be extremely fast if the assumption holds. **Deoptimization** occurs when V8's assumptions (e.g., an object always having a specific shape) are violated at runtime. Coding patterns that cause deoptimization include dynamically adding/deleting properties, changing the type of a property, or using highly dynamic control flow (e.g., heavy use of `eval`).

JS10 — Tree-shaking is a dead code elimination technique used by bundlers (like Webpack/Rollup) to eliminate unused exports from the final bundle. It works effectively with ES Modules (`import`/`export`) because ES Modules are static; the bundler can analyze the dependency graph at compile time to see exactly which exports are imported and used. CommonJS (`require()`) is dynamic; since `require()` can be called conditionally or based on runtime variables, the bundler cannot statically determine all dependencies, making effective tree-shaking impossible.

JS11 — `null` represents the intentional absence of any object value (a deliberate assignment of "no value"). `undefined` means a variable has been declared but has not yet been assigned a value. `==` performs type coercion before comparison (e.g., `0 == false` is true). `===` performs strict equality, requiring both value and type to match (e.g., `0 === false` is false). Nullish coalescing (`??`) returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. Optional chaining (`?.`) allows safe navigation through nested object properties without throwing an error if an intermediate property is `null` or `undefined`.

JS12 — `map()` creates a new array by applying a function to every element of the original array, returning a new array of the same length. `filter()` creates a new array containing only the elements for which the provided testing function returns `true`. `reduce()` executes a reducer function on each element, resulting in a single output value. With an initial value, `reduce()` starts the accumulation process with that value, ensuring the callback runs at least once, even on an empty array. `flatMap()` is useful when you need to map over an array and then flatten the result by one level (e.g., mapping an array of items to an array of sub-items, and then flattening the resulting array of arrays).

JS13 — Template literals (backticks ``) allow for embedded expressions and multi-line strings. They enable interpolation using `${expression}`. Tagged templates allow a function to be executed *before* the string is constructed. The function receives the string parts (the static text) and the interpolated values as separate arguments. Example: For HTML escaping, a tag function could iterate over the values and wrap them in HTML entity encoding before joining them back into the final string.

JS14 — Destructuring is a syntax that allows you to unpack values from arrays or properties from objects into distinct variables. **Object destructuring** pulls properties out of an object (`const { name, age } = user;`). **Array destructuring** pulls elements out of an array (`const [first, second] = arr;`). **Default values** allow you to assign a fallback if a property/element is missing (`const { age = 30 } = user;`). **Renaming** allows you to assign the extracted value to a different variable name (`const { name: fullName } = user;`). The **rest operator (`...`)** collects all remaining, un-destructured properties/elements into a new array or object.

JS15 — `for...in` iterates over the *enumerable properties* of an object, including inherited ones (though usually only own properties are relevant). `for...of` iterates over the *values* of an iterable object (like Arrays, Maps, Sets). You should avoid `for...in` on arrays because it iterates over keys (indices) as strings, and it can iterate over non-index properties added to the array object, leading to unpredictable iteration order and behavior.

JS16 — Generics allow you to write reusable components that can work over a variety of types rather than a single one. **Generic Constraints (`extends`)** restrict the types that can be used with a generic parameter, ensuring they possess certain properties (e.g., `function identity<T extends { length: number }>(arg: T): T`). **Conditional Types** allow types to be determined based on a condition (`T extends U ? X : Y`). If `T` extends `U`, the resulting type is `X`; otherwise, it is `Y`. The **`infer` keyword** is used within conditional types to capture a type that matches a pattern (e.g., `type MyArray = Array<infer E>`).

JS17 — The module system defines how code is organized and how dependencies are managed. **CommonJS** (Node.js standard) uses synchronous `require()` to import and `module.exports` to export. **ES Modules** (standardized JS) use static `import` and `export`. Node.js supports both, often based on file extensions or configuration. Setting `"type": "module"` in `package.json` tells Node.js to treat `.js` files as ES Modules, enabling native `import`/`export` syntax.

JS18 — TypeScript uses a structural type system, meaning type compatibility is determined by the *shape* of the object, not its explicit declaration hierarchy. **Excess property checks** ensure that an object passed to a function or assigned to a type does not contain properties that are not defined in that type. They apply when strict checks are enabled. The difference between `extends` and `satisfies` is that `extends` enforces that the type *is* the base type (structural inheritance), while `satisfies` checks that the type *conforms* to the shape of the base type without changing the original type's structure. Variance (`in`/`out`) describes how subtyping relationships behave when used as input (`in`) or output (`out`) in generic functions, allowing for safe covariance/contravariance.

JS19 — `Proxy` is an object that wraps another object (the target) and allows you to intercept fundamental operations like property lookups, assignments, function calls, and enumeration. `Reflect` is an API that provides methods corresponding to the operations that a Proxy intercepts. You use `Proxy` to define the interception logic (e.g., `set: (target, prop, value) => { /* validation logic */ }`), and `Reflect` to perform the actual operation if needed (e.g., `Reflect.set(target, prop, value)`). A practical example is creating a reactive data store where setting a property triggers a notification event.

JS20 — `SharedArrayBuffer` is a low-level memory buffer that can be shared directly between multiple threads (like Web Workers). `Atomics` provides methods to perform atomic operations (read-modify-write) on the integer values stored within that shared memory. This prevents race conditions. Web Workers communicate by sharing this memory block. Ordering guarantees are provided by the atomic operations themselves, ensuring that operations appear to happen sequentially to all threads. `Atomics.wait(typedArray, index, expectedValue)` pauses the thread until notified or a timeout occurs. `Atomics.notify()` wakes up waiting threads.

B1 — `$@` expands to all positional parameters as separate, quoted arguments (e.g., `"$1" "$2"`). `*` expands to all positional parameters as a single string, separated by the first character of the IFS (Internal Field Separator). `"$@"` expands to each argument quoted individually, preserving spaces. `"$*"` expands to all arguments as a single string, quoted if IFS is set correctly, but generally treated as one block.

B2 — `set -e`: Exit immediately if a command exits with a non-zero status (error). `set -u`: Treat unset variables as an error and exit immediately. `set -o pipefail`: Causes a pipeline to return the exit status of the last command to exit with a non-zero status, rather than just the final command.

B3 — `$(command)` (Command Substitution) executes the `command` and substitutes its standard output into the current command line. `command` executes the command directly. `((expression))` performs arithmetic evaluation within bash. `expr` is an external utility that evaluates expressions, often requiring explicit spacing around operators.

B4 — Process substitution (`<(command)`) runs a command and makes its standard output available as a temporary file path that the current shell can read from. This is useful when a command needs to be treated as a file argument. Example: `diff <(ls -1 | sort) <(ls -1 | sort -r)` compares the output of two separate, piped commands as if they were two distinct files.

B5 — You must use quoting and iteration over a glob pattern: `for f in *; do ... done`. The dangerous `for f in $(ls)` fails because `ls` splits filenames based on the IFS (space, tab, newline). If a filename is `My File.txt`, it becomes two separate tokens (`My` and `File.txt`), causing the loop to process two incorrect items.

B6 — A here document (`<<EOF`) reads multiple lines of input until it encounters the delimiter (`EOF`) on a line by itself. A here string (`<<<`) passes a single line of input to a command. `<<-EOF` (here document with tab expansion) treats leading tabs in the input lines as whitespace characters, preventing them from being interpreted as literal tabs.

B7 — 1. `cmd > file 2>&1`: Redirect stdout to `file`, then redirect stderr (2) to the same location as stdout (1). This is the standard, safe way. 2. `cmd 2>&1 > file`: Redirect stderr (2) to stdout (1) *first*, and then redirect stdout (1) to `file`. If `cmd` writes to stderr before the redirection happens, that output is lost. 3. `cmd &> file`: (Bash 4+) Redirects both stdout and stderr to `file` simultaneously.

B8 — A robust lock function uses `mkdir` because it is atomic across most filesystems.
```bash
LOCK_DIR="/tmp/my_script.lock"
function acquire_lock() {
    if mkdir "$LOCK_DIR" 2>/dev/null; then
        echo "Lock acquired."
        trap "rmdir '$LOCK_DIR'" EXIT TERM INT
        return 0
    else
        echo "Could not acquire lock."
        return 1
    fi
}
# ... use lock ...
```
`mkdir` is preferred because if two processes try to create the directory simultaneously, only one will succeed atomically; the other will fail immediately, preventing race conditions that might occur with file creation (`touch`).

B9 — **Single quotes (`'...'`)**: Literal interpretation. No variable expansion, no command substitution. Example: `echo 'Hello $USER'` outputs `Hello $USER`. **Double quotes (`"..."`)**: Allows variable expansion and command substitution. Example: `echo "Hello $USER"` outputs `Hello [username]`. **No quotes**: Word splitting and pathname expansion occur immediately. Example: `echo $USER` (if username has spaces, it splits).

B10 — File existence: `[ -f file ]` (is a regular file), `[ -d dir ]` (is a directory). Readability: `[ -r file ]`. `[ ]` is an alias for the `test` command. `[[ ]]` is a Bash keyword that supports advanced features like regex matching (`=~`) and works better with word splitting, making it generally preferred in modern scripts.

B11 — `$?`: Exit status of the most recently executed foreground command (0=success). `$$`: The Process ID (PID) of the current shell. `$!`: The PID of the most recently backgrounded command. `$#`: The number of positional arguments passed to the script/function. Use case: `$?` for error checking; `$$` for PID logging/locking.

B12 — Functions are defined using `function name {}` or `name() {}`. Both are functionally equivalent in modern Bash. To return values, functions typically print the result to standard output, and the caller captures it using command substitution: `result=$(my_function arg1)`.

B13 — The `PATH` environment variable is a colon-separated list of directories that the shell searches sequentially when a command is invoked without a full path. Bash resolves commands by checking each directory in `PATH` for an executable file matching the command name. A **builtin** command is implemented directly within the shell (e.g., `cd`, `echo`) and is faster. An **external command** is a separate executable file (e.g., `grep`, `ls`). You can check using `type command_name`.

B14 — `trap` allows you to specify commands to run when the shell receives a specific signal. You set handlers like `trap 'cleanup_function' EXIT` (runs on normal exit), `trap 'cleanup_function' INT` (Ctrl+C), `trap 'cleanup_function' TERM` (graceful termination), and `trap 'cleanup_function' ERR` (on command failure). Execution order is generally determined by the signal received, but `EXIT` handlers run regardless of how the script terminates.

B15 — `xargs` takes standard input and builds and executes command lines from it. Command substitution (`$(...)`) executes a command and substitutes its output *once*. `xargs` is superior for processing lists because it handles input streams efficiently. To handle spaces/newlines safely: `find . -print0 | xargs -0 -I {} your_command {}`. `-0` tells `xargs` to expect null-delimited input. `-P` specifies the number of parallel processes to run.

B16 — **Indexed Arrays**: Ordered lists accessed by integer indices (e.g., `my_array[0]`). Declared: `my_array=(item1 item2)`. Appending: `my_array+=(item3)`. Iterating: `for item in "${my_array[@]}"; do ...`. Length: `${#my_array[@]}`. **Associative Arrays**: Key-value maps accessed by string keys (e.g., `my_map[name]="Alice"`). Declared: `declare -A my_map`. Iterating: `for key in "${!my_map[@]}"; do ...`. Length: `${#my_map[@]}`.

B17 — A **subshell (`(...)`)** executes commands in a separate, isolated process. Any variables modified inside the subshell are lost when it exits. A **group command (`{ ...; }`)** executes commands in the *current* shell environment. Variables modified inside a group command persist. Piping into a `while` loop creates a subshell for the loop body; thus, any variable changes made inside the loop body are lost when the loop iteration finishes, unless explicitly handled (e.g., using `while IFS= read -r line; do ... done`).

B18 — Bash handles signals by interrupting the running process. **SIGINT** (Interrupt, Ctrl+C) is usually handled gracefully. **SIGTERM** (Terminate) is a polite request to shut down. **SIGHUP** (Hangup) is often sent when a controlling terminal closes. **SIGKILL** (Kill) cannot be caught or ignored; the kernel terminates the process immediately. For graceful shutdown, use `trap` to catch `SIGINT` and `SIGTERM`, allowing the script to finish current tasks before exiting.

B19 — This requires splitting, parallel processing, and merging.
1. **Split:** `split -l 1000 logfile.log chunk_` (splits into 1000-line files).
2. **Process (Parallel):** `find . -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c 'process_chunk "$@"' _ {}` (where `process_chunk` is the function).
3. **Merge:** `cat chunk_*_processed.log > final_output.log`.
Performance trade-offs: Parallelism increases throughput but adds overhead from process creation and inter-process communication. Error propagation is tricky; you must check the exit code of the `xargs` command or check the return status of the function within the parallel job.

B20 — `exec command` replaces the current shell process entirely with the new command; it does not spawn a child process. This is useful for resource management. `exec 3>file` opens file descriptor 3 and redirects it to `file`. `exec 3>&-` closes file descriptor 3. A **coprocess** allows a parent shell to run a background process and communicate with it using named pipes (FIFOs) or file descriptors, allowing bidirectional, synchronous-like communication within the same shell session, which is useful for complex, stateful interactions that don't require full process isolation.

PS1 — `Write-Output` sends objects down the pipeline, allowing subsequent cmdlets to process them. `Write-Host` writes directly to the console, bypassing the pipeline. This distinction is crucial because if you use `Write-Host`, the object is not passed to the next cmdlet, and it cannot be filtered or manipulated by pipeline cmdlets.

PS2 — The PowerShell pipeline passes objects from one cmdlet to the next. `ForEach-Object` (alias `%`) is a cmdlet designed to process pipeline objects. The `foreach` statement is a language construct used for iterating over collections (arrays, lists) *within* a script block, not for processing the pipeline stream itself. Use `ForEach-Object` for pipeline processing; use `foreach` for iterating over local variables/collections.

PS3 — `[PSCustomObject]` creates an object with properties defined on the fly, ideal for structured output that needs to flow through the pipeline. `[hashtable]` is a key-value collection, similar to a dictionary, but is less structured for pipeline consumption. Convert: `[PSCustomObject]@{Name="A"; Age=30}` is already an object. To convert a hashtable to an object: `[PSCustomObject]@{Name = $ht.Name; Age = $ht.Age}` (or use `[PSCustomObject]@{...}` syntax).

PS4 — **Terminating errors** stop the current script block or pipeline execution immediately (e.g., file not found when using `-ErrorAction Stop`). **Non-terminating errors** are warnings that allow execution to continue. `-ErrorAction` controls how a specific command handles errors (e.g., `SilentlyContinue`, `Stop`). `$ErrorActionPreference` sets the default behavior for the entire session. `try/catch` blocks catch errors based on the `$ErrorActionPreference` setting.

PS5 — Splatting (`@params`) is a feature that allows you to pass a hashtable as a set of named parameters to a cmdlet. This makes scripts cleaner and allows parameters to be defined dynamically. Example: `Get-Service @params`, where `@params` is a hashtable like `@{'Name'='Spooler'; 'Status'='Running'}`. It differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named arguments.

PS6 — **Invoke-Command -ComputerName** executes a script block remotely on a specified machine, running the code *on* the remote system. **Enter-PSSession** establishes an interactive, persistent remote shell session on the target machine. Both rely on **WinRM** (Windows Remote Management) for Windows environments. While SSH is used for PowerShell Core/7+ on Linux/macOS, WinRM is the primary protocol for traditional Windows PowerShell remoting.

PS7 — The function returns an empty array (`@()`). When PowerShell processes this empty array, it treats it as an empty collection. When you access `$x.GetType().Name`, it returns `System.Object` because the variable `$x` holds the empty array object. The correct pattern is to ensure the function returns objects that are *not* empty, or to explicitly check if the returned collection is empty before attempting to access properties that might fail.

PS8 — A **scriptblock** is a block of code that can be passed as an argument to a function or cmdlet. A **function** is a named block of code that can be called. You pass a scriptblock using the `-ScriptBlock` parameter. The **double-hop problem** occurs when running code remotely where the remote session inherits the local environment's variables, which might not be available or correctly serialized. This is solved by using `Invoke-Command -ArgumentList` to explicitly pass required variables, or by using CredSSP for more complex authentication/session management.

PS9 — `@()` creates an empty array object. `[array]` is the type accelerator used to explicitly cast a variable to an array type. To force a single result into an array, wrap it: `1 | Select-Object -First 1` or `1,`. Indexing `$null` results in an error. Indexing an empty array (`@()`) results in `$null`.

PS10 — `-eq` (equals), `-ne` (not equal), `-like` (wildcard matching, uses `*` and `?`), `-match` (regex matching), `-contains` (checks if a specific item exists in an array), `-in` (checks if a value exists within a list of values). Case-sensitive variants (`-ceq`, `-clike`, etc.) enforce case matching. The difference between `-contains` and `-in` is that `-contains` checks if a *single item* is present in an array, whereas `-in` checks if a value matches *any* item in a list of values.

PS11 — A **module** is a container for related cmdlets, functions, and variables. A **script module (.psm1)** is a script file that defines the module's contents. A **manifest module (.psd1)** is a metadata file that describes the module (version, dependencies, required PowerShell version). A **binary module** is a compiled module. `Import-Module` loads the module's definitions into the current session's scope, making its contents available.

PS12 — String interpolation uses double quotes (`"..."`). Expressions are included using `$()` or `${expression}`. Single quotes (`'...'`) treat everything literally. A **here-string (`@"...@"@`)** is a multi-line string literal that supports interpolation and is useful for embedding large blocks of text or code without needing to escape quotes.

PS13 — `Get-Member` returns a collection of objects describing the properties and methods available on a specified object. **Properties** are data fields (read/write). **Methods** are functions associated with the object that can be called. **NoteProperties** are properties that are not standard members but are attached via attributes or metadata. `Select-Object` *chooses* which properties to output. `Where-Object` *filters* the objects based on a condition.

PS14 — PowerShell classes (v5+) are object-oriented constructs that allow defining custom types. They differ from C# classes in that they are more dynamic and often rely heavily on pipeline input. Limitations include less strict enforcement of interfaces compared to C#, and constructors are often handled via parameter sets. Use a **function** when the logic is procedural and stateless. Use a **class** when you need to model a complex entity with state (properties) and associated behavior (methods).

PS15 — `CmdletBinding()` is an attribute that enables advanced function features, allowing the function to behave like a native cmdlet (e.g., accepting pipeline input, having parameters). `SupportsShouldProcess` allows the cmdlet to check if the user wants to perform a destructive action (e.g., `WhatIf`). `DefaultParameterSetName` sets the default set of parameters used. `ValueFromPipeline` tells the cmdlet to accept input objects from the pipeline. **Begin** runs before processing starts. **Process** runs for each incoming pipeline object. **End** runs after all objects have been processed.

PS16 — Providers are objects that allow cmdlets like `Get-ChildItem` to interact with different types of data sources using a unified interface. The `FileSystem` provider accesses local drives. The `Registry` provider allows you to navigate the Windows Registry structure using paths like `HKLM:\Software\Microsoft`. The `Certificate` provider accesses stored certificates. You access the registry like a file system by using the provider name in the path: `Get-ChildItem -Path Registry:\HKLM\Software`.

PS17 — A **runspace** is an execution context that hosts PowerShell code. A **runspacepool** manages a collection of runspaces, allowing for efficient reuse. A **[powershell] object** is the wrapper used to interact with the PowerShell engine itself. `ForEach-Object -Parallel` (v7+) uses the runspacepool internally to execute script blocks concurrently across multiple threads. Manual runspace management is required for fine-grained control over thread lifecycle and resource allocation.

PS18 — PSScriptAnalyzer is a static code analysis tool that enforces best practices and coding standards in PowerShell scripts. It uses **rules** (e.g., "Do not use global variables") which have associated **severity levels** (e.g., Warning, Error). You suppress rules using `#Requires -Warning` or specific analyzer directives. It integrates into CI/CD by running as a pre-commit or build step, failing the build if critical rules are violated.

PS19 — `$using:` scope allows variables defined in the parent scope (the calling script) to be safely accessed by child processes (like background jobs or parallel `ForEach-Object`) without needing to serialize the entire object. `$args/-ArgumentList` passes explicit, serialized arguments to a remote session or job. Serialization limits (CLIXML depth) restrict the complexity of objects that can be passed across process boundaries; deeply nested or circular references can cause failures.

PS20 — Desired State Configuration (DSC) is a management framework that allows administrators to define the *desired state* of a system (e.g., "IIS must be installed and running") rather than writing procedural steps to achieve it. **Configurations** define the desired state. **Resources** are the specific components (e.g., `Service`, `File`) that implement the logic to reach that state. The **Local Configuration Manager (LCM)** is the engine that reads the configuration and ensures the system matches the desired state. In modern IaC, DSC concepts are often replaced or augmented by tools like Ansible, Chef, or Terraform, which provide broader orchestration capabilities.
