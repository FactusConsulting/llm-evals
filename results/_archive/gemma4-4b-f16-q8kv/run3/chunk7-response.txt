JS1 — `var` is function-scoped and subject to hoisting (initialized as `undefined`). `let` and `const` are block-scoped. Hoisting moves declarations to the top of their scope, but `let`/`const` are not initialized, leading to the Temporal Dead Zone (TDZ) if accessed before declaration.
JS2 — The Event Loop is the mechanism that monitors the Call Stack and the various queues (Microtask and Macrotask) to decide which task to execute next. The Call Stack executes synchronous code. When the stack is empty, the Event Loop checks the Microtask Queue (e.g., Promises, `queueMicrotask`) and empties it completely before checking the Macrotask Queue (e.g., `setTimeout`, I/O).
JS3 — A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). Example: `function outer() { let count = 0; return function() { count++; return count; }; }`. The classic bug occurs in `for` loops where the returned function references the *same* final `i` value from the loop's scope. Fix: Use `let` in the loop declaration (`for (let i = 0; ...)`), which creates a new binding for `i` in each iteration.
JS4 — A Promise represents the eventual completion (or failure) of an asynchronous operation. `async/await` is syntactic sugar built on Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()` or `try/catch` around `await`. `Promise.all` rejects immediately if *any* input promise rejects. `Promise.allSettled` waits for *all* promises to either fulfill or reject, returning an array describing the outcome of each.
JS5 — **Interface** defines a contract (a set of methods/properties) that an object must adhere to; it describes *what* an object looks like. **Type** describes the shape and constraints of data; it can describe primitive types, unions, or complex structures. Use **Interface** when defining API contracts or ensuring structural compatibility across different classes/objects. Use **Type** for complex data shapes, utility types, or when defining unions/intersections. Discriminated unions are unions where one member has a literal property (the "discriminant") that allows TypeScript to narrow the type safely using `switch` statements.
JS6 — Prototypal inheritance means objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. `Object.create(proto)` creates a new object whose internal `[[Prototype]]` link points directly to `proto`. ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance mechanism; they provide a cleaner, more familiar syntax for defining constructor functions and prototype chains.
JS7 — `this` refers to the object that is currently executing the function. The binding rules (in priority order) are: 1. `new` binding (when called with `new`). 2. Explicit binding (`.call()`, `.apply()`, `.bind()`). 3. Implicit binding (when called as a method on an object). 4. Default binding (when called globally/in strict mode, `this` is `undefined` or the global object). `bind()` returns a *new* function with the context permanently set; this new function can be bound again, but the original function's context is fixed by the first binding.
JS8 — **WeakRef** holds a weak reference to an object. If the object is garbage collected, the `WeakRef` automatically becomes `deref()`-able to `undefined` without preventing GC. **FinalizationRegistry** allows you to register a callback function that will be executed *after* the associated target object has been garbage collected. Use them to manage resources tied to objects without creating memory leaks (e.g., cleaning up event listeners on DOM elements that are about to be removed). WeakMap keys must be objects because primitives (like strings or numbers) are compared by value, which would prevent the GC from ever recognizing that the key is no longer referenced elsewhere.
JS9 — V8 optimizes JS using several techniques. **Hidden Classes** (or Maps) allow V8 to represent objects with the same structure efficiently, avoiding the need to store property metadata for every single instance. **Inline Caching (IC)** stores the type and location of frequently accessed properties directly in the machine code, speeding up lookups. **Deoptimization** occurs when V8's assumptions about an object's structure (e.g., assuming a property will always be present or always be of a certain type) are violated at runtime. Coding patterns causing deoptimization include dynamic property addition/deletion, using `eval()`, or changing the structure of objects frequently.
JS10 — Tree-shaking is a dead code elimination technique used by bundlers (like Webpack/Rollup) to eliminate unused exports from modules. It works effectively with ES Modules because `import`/`export` statements are static and analyzable by the bundler *before* runtime. CommonJS (`require()`) is dynamic; since `require('module')` can be called conditionally or based on runtime variables, the bundler cannot statically determine which exports are actually used, making effective tree-shaking impossible.
JS11 — `null` is an intentional absence of any object value (a deliberate assignment). `undefined` means a variable has been declared but has not yet been assigned a value. `==` performs type coercion before comparison (e.g., `0 == false` is true). `===` checks for strict equality, requiring both value and type to match. `??` (Nullish Coalescing) returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. `?.` (Optional Chaining) allows safe navigation through nested objects; it stops and returns `undefined` if any part of the chain is `null` or `undefined`.
JS12 — `map()` creates a new array by applying a function to every element of the original array, returning a new array of the same length. `filter()` creates a new array containing only elements for which the provided testing function returns `true`. `reduce()` executes a reducer function on each element, resulting in a single output value. With an initial value, `reduce()` starts the accumulation process with that value, ensuring the callback runs at least once, even on an empty array. `flatMap()` maps each element using a mapping function, and then flattens the result into a new array by one level. It is useful when mapping results might produce arrays themselves (e.g., mapping a list of items to lists of their sub-components).
JS13 — Template literals (backticks ``) allow embedding expressions directly into strings using `${expression}`. Tagged templates allow a function to intercept and process the string parts and the interpolated values before the final string is constructed. Example (HTML Escaping): `const escapeHtml = (strings, ...values) => { let result = strings[0]; for (let i = 0; i < values.length; i++) { result += escape(values[i]) + strings[i + 1]; } return result; }; const html = escapeHtml`Hello ${name}``;`
JS14 — Destructuring is a syntax that allows unpacking values from arrays or properties from objects into distinct variables. **Object Destructuring** pulls properties out based on keys: `const { name, age } = user;`. **Array Destructuring** pulls values based on position: `const [first, second] = arr;`. **Default Values** provide fallback values if a property/element is missing: `const { age = 30 } = user;`. **Renaming** allows assigning the extracted value to a different variable name: `const { name: fullName } = user;`. The **Rest Operator (`...`)** collects all remaining, un-destructured properties/elements into a new array or object.
JS15 — `for...in` iterates over the *enumerable properties* of an object, including inherited ones (unless filtered). `for...of` iterates over the *values* of an iterable object (like Arrays, Maps, Sets). You should avoid `for...in` on arrays because it iterates over keys (indices) as strings, and it can iterate over non-index properties added to the array object, leading to unpredictable iteration order and behavior.
JS16 — **Generics** allow you to write reusable code that can work over a variety of types rather than a single one, while maintaining type safety. **Generic Constraints (`extends`)** restrict the types that can be used with a generic parameter, ensuring they possess certain properties. Example: `function identity<T extends { length: number }>(arg: T): T { return arg; }`. **Conditional Types** allow types to be determined based on a condition. Example: `type IsString<T> = T extends string ? true : false;`. **Infer** is used to infer the type of a variable or function return type based on its usage. Example: `let x = 10; type X = infer<typeof x>; // X is number`.
JS17 — The module system defines how code dependencies are managed. **CommonJS** (Node.js standard) uses synchronous `require()` to import and `module.exports` to export. **ES Modules** (standardized JS) uses static `import`/`export`. Node.js supports both; `.js` files default to CommonJS unless `"type": "module"` is set in `package.json`, which forces ES Module interpretation.
JS18 — TypeScript uses a **structural type system**, meaning two types are considered compatible if they have the same structure (shape), regardless of their declared name. **Excess Property Checks** ensure that an object passed to a function or assigned to a type does not contain properties that are *not* defined in that type. They apply when the structure is being checked against a known type. **`extends`** enforces that the derived type *must* have all properties of the base type. **`satisfies`** checks that the type *conforms* to the shape of the type argument, but it does not enforce that the type *is* that shape (it's a structural check without inheritance). **Variance** describes how subtyping relationships behave with generics: `in` (contravariant) means the type can be used as an input parameter (e.g., `string` can be used where `object` is expected). `out` (covariant) means the type can be used as an output return value (e.g., `string` can be returned where `object` is expected).
JS19 — **Proxy** is an object that wraps another object, allowing you to intercept fundamental operations (like property lookups, assignments, function calls) via "traps." **Reflect** is an API that provides methods to perform these operations in a standardized, reflective way, often used *inside* a Proxy handler. Example: To log every time a property is set: `const handler = { set(target, property, value) { console.log(\`Setting \${property} to \${value}\`); return Reflect.set(target, property, value); } }; const proxy = new Proxy(data, handler);`
JS20 — **SharedArrayBuffer** provides a way to share raw binary data memory between different execution contexts (like Web Workers). **Atomics** provides methods to perform atomic operations (read-modify-write) on the integer values stored within a `SharedArrayBuffer`. This prevents race conditions when multiple threads access the same memory location. Ordering guarantees are provided by the atomic operations themselves. `Atomics.wait(typedArray, index, expectedValue)` pauses the thread until another thread calls `Atomics.notify()` on that index, signaling a change.

B1 — `$@` expands to all positional parameters as separate, quoted arguments (safe for spaces). `*` expands to all positional parameters as a single string, separated by the first character of the IFS (Internal Field Separator). `"$@"` expands to all arguments, each quoted individually. `"$*"` expands to all arguments as a single string, quoted if IFS is set correctly, but generally less safe than `"$@"`.
B2 — `set -e`: Exit immediately if a command exits with a non-zero status. `set -u`: Treat unset variables as an error and exit immediately. `set -o pipefail`: Causes a pipeline to return the exit status of the last command to exit with a non-zero status, rather than just the final command.
B3 — `$(command)` (Command Substitution) executes `command` and substitutes its standard output into the current command line. `command` executes the command directly. `((expression))` performs arithmetic evaluation within bash. `expr` is an external utility that evaluates expressions, often requiring spaces around operators.
B4 — Process substitution (`<(command)`) runs a command in the background and makes its standard output available as a temporary file path that the current shell can read, allowing it to be used as an argument to another command. Example: `diff <(ls -1 | sort) <(ls -1 | sort -r)`. This allows `diff` to compare the output of two separate, concurrently running commands as if they were two distinct files.
B5 — Use quoting and globbing: `for f in *; do ... done` or, more robustly, use `find . -print0 | while IFS= read -r -d $'\0' f; do ... done`. `for f in $(ls)` is dangerous because `ls` splits filenames based on the IFS (usually space/tab), causing filenames containing spaces to be treated as multiple separate arguments.
B6 — A **here document (`<<EOF`)** reads multiple lines of input until it encounters the delimiter (`EOF`) on a line by itself. A **here string (`<<<`)** passes a single line of input to a command. `<<-EOF` (here document with leading tab removal) treats any line starting with a tab character as if the tab were not there, effectively stripping leading tabs from the input lines.
B7 — 1. `cmd > file 2>&1`: Redirect stdout to `file`, then redirect stderr (2) to the same location as stdout (1). This is the standard, safe way to redirect both streams to one file. 2. `cmd 2>&1 > file`: Redirect stderr (2) to stdout (1) *first*, and *then* redirect stdout (1) to `file`. If `file` doesn't exist, the redirection to `file` happens *before* stderr is redirected, meaning stderr might still go to the terminal. 3. `cmd &> file`: (Bash 4+) A shorthand that redirects both stdout and stderr to `file` simultaneously.
B8 — Use `mkdir /tmp/lockfile_name` and check its exit status. If successful, the lock is acquired. Use `trap 'rmdir /tmp/lockfile_name' EXIT INT TERM` to ensure cleanup. `mkdir` is preferred because it is an atomic operation on most filesystems; if the directory already exists, `mkdir` fails (or succeeds depending on flags), but if it succeeds, it guarantees exclusive creation, preventing two processes from simultaneously creating the lock file.
B9 — **Single quotes (`'...'`)**: Literal interpretation. No variable expansion, no command substitution. Example: `echo 'Hello $USER'`. Output: `Hello $USER`. **Double quotes (`"..."`)**: Allows variable expansion (`$VAR`) and command substitution (`$(cmd)`). Example: `echo "Hello $USER"`. Output: `Hello [username]`. **No quotes**: Word splitting and pathname expansion occur immediately. Example: `echo $VAR` (if $VAR is "a b"). Output: `a b` (two arguments).
B10 — File existence: `[ -f file ]` (is a regular file), `[ -d dir ]` (is a directory). Readability: `[ -r file ]`. `[ ]` is an alias for the `test` command. `[[ ]]` is a keyword in bash (Bash specific) that supports advanced features like regex matching (`=~`) and works better with word splitting, making it generally preferred for complex tests.
B11 — `$?`: Exit status of the most recently executed foreground command (0=success). `$$`: The Process ID (PID) of the current shell. `$!`: The PID of the most recently backgrounded command. `$#`: The number of positional parameters passed to the script/function.
B12 — Definition: `my_func() { echo "Hello"; }` or `function my_func { echo "Hello"; }`. Both are functionally equivalent in modern bash. Return values are typically passed back via standard output, which the caller captures: `result=$(my_func)`. The function itself returns an exit code (0-255) via `$?`.
B13 — `PATH` is a colon-separated list of directories that the shell searches sequentially when a command is invoked. Bash resolves commands by checking if the command name matches a builtin first; if not, it iterates through every directory listed in `$PATH`, looking for an executable file with that name. A **builtin** is a command implemented directly inside the shell (e.g., `cd`, `echo`). An **external command** is a separate executable file in the filesystem (e.g., `grep`, `ls`). Check: `type command_name`.
B14 — `trap` allows you to specify commands to run when the shell receives a specific signal. `trap 'cleanup_function' EXIT`: Runs cleanup when the script exits normally. `trap 'cleanup_function' ERR`: Runs when a command exits with a non-zero status. `trap 'cleanup_function' INT` (Ctrl+C) or `TERM` (kill): Handles termination signals gracefully. Execution order: Signals are handled sequentially based on the trap definitions, but if multiple signals arrive simultaneously, the OS determines the order, though `EXIT` is usually the final cleanup hook.
B15 — **Command Substitution** (`$(cmd)`) runs a command and substitutes its output into the current command line. **xargs** takes standard input (usually from a pipe) and builds and executes command lines from that input. `find . -print0 | xargs -0 -I {} rm {}` safely handles spaces/newlines by using null termination (`-print0` and `-0`). `xargs -P N` runs up to $N$ processes in parallel, significantly speeding up I/O-bound tasks.
B16 — **Indexed Arrays**: Ordered lists accessed by integer indices (e.g., `arr[0]`). Declaration: `arr=(a b c)`. Append: `arr+=(d)`. Iterate: `for item in "${arr[@]}"; do ...`. Length: `${#arr[@]}`. **Associative Arrays**: Key-value maps accessed by string keys (e.g., `map[key]`). Declaration: `declare -A map`. Append: `map[new_key]=value`. Iterate: `for key in "${!map[@]}"; do echo "${key}: ${map[$key]}"; done`. Length: `${#map[@]}`.
B17 — A **subshell (`(...)`)** executes commands in a separate, isolated process. Any variables set or modified inside the subshell are lost when it exits. A **group command (`{ ...; }`)** executes commands in the *current* shell process. Variables modified inside are visible outside. Piping into a `while` loop (`while read line; do ... done < file`) runs the loop in a subshell, meaning any variable changes made inside the loop body are lost when the loop finishes.
B18 — Bash handles signals by intercepting them via `trap`. **SIGINT** (Interrupt, Ctrl+C): Used for user interruption. **SIGTERM** (Terminate): The standard, polite request for a process to shut down gracefully. **SIGHUP** (Hangup): Often sent when a controlling terminal closes; used to signal configuration reload. **SIGKILL** (Kill): Cannot be caught or ignored; the kernel immediately terminates the process. Graceful shutdown requires trapping `SIGTERM` and `SIGINT`, allowing the script to finish current tasks, clean up resources, and then exit cleanly.
B19 — Script structure: 1. `find . -name "*.log" -print0 | xargs -0 -P 4 -I {} bash -c 'process_file "$@"' _ {}`. 2. `process_file` function handles the heavy lifting (e.g., parsing, transformation). 3. After parallel processing, use `cat results_*.tmp | sort > final_output.log`. Performance trade-offs: Parallelism speeds up CPU-bound tasks but introduces overhead from process creation and I/O contention. Error propagation: Use `set -e` within the processing function, and check the exit code of the `xargs` command, or use `trap` within the worker script to capture and report failures.
B20 — `exec` replaces the current shell process image with a new command, meaning the shell itself is replaced; it does not spawn a child process. It is used for resource management: `exec 3>file` opens file descriptor 3 and redirects it to `file`. `exec 3>&-` closes file descriptor 3. A **coprocess** allows a parent shell to communicate with a child process using named pipes (FIFOs) for bidirectional, persistent communication, unlike simple pipes which are unidirectional. Use a coprocess when you need a long-running background task that needs to send status updates or receive commands from the parent shell.

PS1 — `Write-Output` sends objects down the pipeline, allowing subsequent cmdlets to process them. `Write-Host` writes directly to the console, bypassing the pipeline. This distinction matters because if you use `Write-Host`, the object is not passed to the next cmdlet, and it cannot be captured or manipulated by pipeline logic.
PS2 — The pipeline passes objects from the output of one cmdlet to the input of the next. `ForEach-Object` (alias `%`) is a cmdlet designed to process pipeline objects. The `foreach` statement is a language construct used for iterating over collections (arrays, lists) *within* a script block, not for processing pipeline streams. Use `ForEach-Object` when processing streamed input; use `foreach` when iterating over an already loaded collection.
PS3 — **[PSCustomObject]** creates a lightweight, dynamic object structure, ideal for creating structured output that can be easily piped and consumed by other cmdlets. **[hashtable]** is a key-value map structure, useful for configuration or temporary data storage. Conversion: `[PSCustomObject]@{Key = $hashtable.Value}` or `$hashtable | ConvertTo-Object`.
PS4 — **Terminating errors** stop the current script block or cmdlet execution immediately (e.g., file not found when required). **Non-terminating errors** are warnings or informational messages that allow execution to continue. `-ErrorAction Stop` forces a non-terminating error to become terminating. `$ErrorActionPreference` sets the default behavior for the current scope. `try/catch` allows you to explicitly catch terminating errors, allowing you to handle them without stopping the entire script.
PS5 — **Splatting (`@params`)** is the practice of passing a hashtable as a set of named parameters to a cmdlet. It allows you to define parameters in a separate variable, making scripts cleaner and reusable. Example: `$params = @{Path = "C:\Logs"; LogLevel = "Verbose"}`. `Invoke-Command -ComputerName ServerA @params`. This differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named arguments recognized by the cmdlet.
PS6 — **Invoke-Command -ComputerName** executes a script block on a remote machine, returning the results to the local session. **Enter-PSSession** establishes an interactive, persistent remote session, allowing you to run commands directly on the remote machine as if you were logged in. It typically uses **WinRM** (Windows Remote Management) over HTTP/HTTPS. While SSH is used for PowerShell Core/7+ on Linux/macOS, WinRM is the primary protocol for Windows-to-Windows remoting.
PS7 — The function returns an empty array (`@()`). Because PowerShell treats the return value as an array, the type is `System.Object[]`. When you access `$x.GetType().Name`, you get `Object[]`. The correct pattern is to ensure the function *yields* objects or returns a collection that is explicitly typed, or, if returning nothing, simply let the function finish without an explicit return statement, allowing the pipeline to handle the lack of output gracefully.
PS8 — A **[scriptblock]** is a block of code that can be passed as an argument to a cmdlet or function. A **function** is a named, reusable block of code with defined parameters and scope. To pass a scriptblock remotely, you must serialize it. The **double-hop problem** occurs when a scriptblock defined locally needs to access a variable from the local scope while running remotely. This is solved by using `Invoke-Command -ArgumentList` to pass the variable's *value* or by using `$using:` scope modifier within the scriptblock to reference the local variable.
PS9 — `@()` creates an empty array object. `[array]` is a type accelerator used to explicitly cast a variable to an array type. To force a single result into an array, wrap it: `@[single_object]`. Indexing `$null` throws a terminating error. Indexing an empty array (`@()`) returns `$null` without error.
PS10 — `-eq` (equals), `-ne` (not equals), `-like` (wildcard match, case-insensitive), `-match` (regex match, case-insensitive), `-contains` (checks if an array contains a specific element), `-in` (checks if a value is present in a list/array). Case-sensitive variants (`-ceq`, `-clike`, etc.) enforce case matching. Difference: `-contains` checks if the *exact element* exists in the collection; `-in` checks if the value matches any item in the collection (often used interchangeably with `-contains` for simple lists, but `-in` is more versatile).
PS11 — A **module** is a collection of related cmdlets, functions, and variables. A **script module (.psm1)** is a script file that defines the module's contents. A **manifest module (.psd1)** is a metadata file that describes the module (version, dependencies, required PowerShell version). A **binary module** is compiled code. `Import-Module` loads the module's definitions into the current session's scope, making its contents available.
PS12 — String interpolation uses double quotes (`"..."`). Single quotes (`'...'`) treat everything literally. Expressions are included using `$()` or `${expression}`. A **here-string (`@"`...`"@`)** allows multi-line strings that support interpolation, similar to template literals in JS, without needing to escape newlines.
PS13 — `Get-Member` returns a collection of objects describing the type of the input object. It shows **Properties** (data fields), **Methods** (executable functions), and **NoteProperties** (metadata). `Select-Object` chooses which properties to *output* from an object. `Where-Object` filters the input stream, only passing objects that satisfy a specified condition (a predicate).
PS14 — PowerShell classes are object-oriented constructs that support encapsulation, inheritance, and methods, similar to C# classes, but they are generally less strictly typed than C# classes. Limitations include less rigid enforcement of interfaces compared to C#. You use a **class** when you need to model a complex entity with state and behavior (e.g., a `User` object). You use a **function** when you need a reusable block of logic that operates on input data without maintaining persistent state.
PS15 — **CmdletBinding** is a feature that allows a function to behave like a full-fledged cmdlet, automatically inheriting features like parameter validation, common parameters (`-Verbose`, `-ErrorAction`), and pipeline support. `SupportsShouldProcess` enables the `-WhatIf` parameter. `DefaultParameterSetName` sets the default set of parameters used. `ValueFromPipeline` allows the cmdlet to accept input objects via the pipeline. **Begin/Process/End** blocks define lifecycle stages: `Begin` runs once before processing starts; `Process` runs for each incoming pipeline object; `End` runs once after all objects have been processed.
PS16 — Providers are objects that allow cmdlets like `Get-ChildItem` to interact with different types of data sources using a unified interface. The `FileSystem` provider accesses local drives. The `Registry` provider allows you to navigate the Windows Registry structure using paths like `HKLM:\Software\Microsoft`. The `Certificate` provider accesses stored certificates. You access the registry like a file system by using the provider drive letter syntax (e.g., `Get-ChildItem -Path Registry:\HKLM\Software`).
PS17 — A **[runspace]** is an execution context that hosts PowerShell code. A **[runspacepool]** manages a collection of runspaces, allowing for efficient reuse of execution contexts. A **[powershell]** object is the executable instance. `ForEach-Object -Parallel` (v7+) uses the runspace pool internally to execute script blocks concurrently across multiple threads/processes. Manual runspace management is necessary for complex, long-running, or highly customized parallel operations where the built-in parallel feature is insufficient.
PS18 — **PSScriptAnalyzer** is a static code analysis tool that checks PowerShell scripts against a defined set of best practices and coding standards. It uses **rules** (e.g., "Do not use global variables") which have associated **severity levels** (e.g., Warning, Error, Critical). You suppress rules using `#Requires -Warning` or specific analyzer directives. It integrates into CI/CD by running as a pre-commit or build step, failing the pipeline if critical rules are violated.
PS19 — **$using:** scope allows variables defined in the *parent* scope (the calling script) to be safely accessed by child processes (like background jobs or parallel `ForEach-Object`) during serialization. **$args/-ArgumentList** passes values explicitly as parameters to the remote/child process. Serialization limits (CLIXML depth) restrict the complexity and depth of objects that can be passed across process boundaries; very large or deeply nested custom objects may fail to serialize correctly, requiring manual data flattening or serialization (e.g., to JSON) before passing.
PS20 — **Desired State Configuration (DSC)** is a management framework that enables you to define the *desired state* of a system (e.g., "IIS must be installed and running," "Registry key X must have value Y") and ensures the system continuously conforms to that state. **Configurations** define the desired state. **Resources** are the specific components that implement the logic to achieve a state (e.g., the `Service` resource ensures a service is running). The **Local Configuration Manager (LCM)** is the engine that reads the configuration and enforces the state on the target node. In modern IaC, DSC has been largely superseded by tools like Ansible, Chef, and Terraform, which offer broader orchestration capabilities.
