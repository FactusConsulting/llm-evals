**Cloud Infrastructure Architecture**

CL1 — IaaS provides raw compute resources (VMs, storage); PaaS provides a platform for building and deploying applications (databases, runtime environments); SaaS provides ready-to-use software (e.g., M365). Examples: IaaS (AWS EC2), PaaS (Azure App Service), SaaS (Salesforce).

CL2 — The Shared Responsibility Model dictates that the cloud provider secures the *cloud itself*, while the customer secures *in the cloud*.
*   **IaaS VMs:** Provider secures the physical hardware, networking, and hypervisor. Customer secures the OS, applications, data, and configuration.
*   **Managed Kubernetes:** Provider secures the control plane (master nodes, API server). Customer secures the application workloads, container images, and configuration within the cluster.
*   **SaaS (M365):** Provider is responsible for nearly everything (application, infrastructure, data security, patching). Customer is responsible primarily for user access management and data classification/usage.

CL3 — **VPC** is the isolated virtual network boundary. **Subnets** are IP ranges within the VPC, typically tied to an Availability Zone. **Security Groups** act as stateful, instance-level firewalls (allow/deny rules applied to the NIC). **NACLs** act as stateless, subnet-level firewalls (allow/deny rules applied to the entire subnet). They layer: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group. Stateful means return traffic is automatically allowed; stateless requires explicit rules for both inbound and outbound traffic.

CL4 — A **Landing Zone** is a pre-configured, secure, and compliant foundational environment (accounts, networking, governance) for cloud adoption. **Organizational Units (OUs)** group accounts by function (e.g., Production, Development, Security). **Guardrails** are automated policies (e.g., SCPs, Azure Policy) enforcing compliance. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes connectivity and security inspection. Centralized logging aggregates audit trails across all accounts. A single-account approach fails due to lack of blast radius containment, governance sprawl, and difficulty enforcing consistent security policies across diverse workloads.

CL5 — **Infrastructure as Code (IaC)** is managing and provisioning infrastructure through machine-readable definition files rather than manual processes.
*   **Terraform/OpenTofu:** Multi-cloud, declarative, state-driven. Best for broad infrastructure provisioning across many providers.
*   **Pulumi:** Uses general-purpose programming languages (Python, Go) to define infrastructure. Best when complex logic or existing codebases need to drive infrastructure.
*   **CloudFormation/Bicep:** Cloud-native, declarative. Best for deep integration and leveraging specific, proprietary cloud features within one provider.
*   **Crossplane:** Kubernetes-native control plane that abstracts cloud APIs into Kubernetes resources. Best for achieving true multi-cloud abstraction using Kubernetes primitives.

CL6 — **HPA** scales based on metrics (CPU/memory/custom) *within* a deployment. **VPA** recommends or automatically adjusts the resource *requests/limits* for a pod. **Cluster Autoscaler** scales the underlying *node count* based on pending pods. **KEDA** (Kubernetes Event-driven Autoscaling) scales based on external event sources (e.g., Kafka queue depth, SQS messages, Prometheus metrics). Use KEDA over HPA when scaling needs to be driven by external asynchronous events rather than just internal resource utilization.

CL7 — **RPO (Recovery Point Objective):** Max acceptable data loss. **RTO (Recovery Time Objective):** Max acceptable downtime.
*   **Active-Passive:** One region handles traffic; the other is a standby. Lower cost, higher RTO.
*   **Active-Active:** Both regions handle traffic simultaneously. Highest cost, lowest RTO.
*   **Pilot Light:** Minimal infrastructure running in the DR region (e.g., small database replica). Low cost, moderate RTO.
*   **Warm Standby:** A scaled-down, running version of the application stack in the DR region. Moderate cost, low RTO.
*   **Multi-site Active-Active:** Full, scaled-out deployment in both regions. Highest cost, near-zero RTO.
*   **Database Replication:** Synchronous replication ensures zero data loss (high latency impact); Asynchronous replication allows for lower latency but risks minor data loss upon failover.
*   **DNS Failover:** Route53/Traffic Manager directs traffic to the healthy region endpoint based on health checks.

CL8 — **GitOps** uses Git as the single source of truth for declarative infrastructure and application state. CI pipelines push changes to Git; CD agents (ArgoCD/FluxCD) continuously monitor Git and reconcile the cluster state to match the repository.
*   **ArgoCD:** Focuses on continuous synchronization and visualization of the desired state vs. actual state.
*   **FluxCD:** Focuses on a pull-based, Git-centric approach, often integrating deeply with GitOps workflows.
*   **Secrets Handling:** Secrets should *never* be stored in plain text in Git. Solutions include **Sealed Secrets** (encrypting secrets using a cluster-specific public key), **External Secrets Operator** (pulling secrets from external vaults like HashiCorp Vault), or direct integration with Vault.
*   **Drift:** If a manual change occurs, the GitOps agent detects the discrepancy (drift) and automatically reverts the cluster state back to match the configuration defined in Git, enforcing the desired state.

CL9 — **StatefulSet:** Ensures ordered deployment, scaling, and stable network identities for stateful applications. **PV/PVC:** Persistent Volume/Claim defines the storage abstraction. Use a **Local Storage Class** to provision storage directly on the node where the pod runs, ensuring low latency. **Headless Service:** Provides DNS records for individual pods, allowing the StatefulSet to address pods by stable hostname. **Init Containers:** Run pre-startup tasks, such as provisioning configuration files or waiting for external dependencies. **ConfigMaps:** Used to inject configuration data as volume mounts into the pod filesystem. **Pod Disruption Budgets (PDBs):** Ensures that a minimum number of replicas remain available during voluntary disruptions (e.g., node maintenance).

CL10 — **Service Account:** An identity used by a pod *inside* a Kubernetes cluster to interact with the cluster's API. **Workload Identity:** A mechanism (often cloud-specific) that allows a workload (like a pod) to assume a cloud provider's IAM role directly. **IRSA (IAM Roles for Service Accounts):** AWS implementation of Workload Identity, mapping a specific Kubernetes Service Account to an AWS IAM Role. Mounting credentials directly is bad practice because it requires storing long-lived, static secrets (keys/tokens) within the container image or environment variables, creating a high-risk attack vector if the container is compromised. Workload identity federation solves this by allowing the cloud provider to issue short-lived, temporary credentials directly to the pod based on its verified identity.

CL11 — **Object Storage (S3/Blob):** Stores unstructured data (files, backups, images) accessed via HTTP API. High durability (11 nines) and high availability. Best for static assets, data lakes. **Block Storage (EBS/Managed Disk):** Provides persistent, high-performance, raw block devices attached to a single VM instance. Best for OS disks, databases requiring low-latency I/O. **File Storage (EFS/Azure Files):** Provides a shared, network-mounted file system accessible by multiple compute instances concurrently. Best for shared configuration files or content management systems.

CL12 — A Zero-Trust architecture operates on the principle of "never trust, always verify," regardless of location.
*   **Network Policies:** Define micro-segmentation rules, restricting pod-to-pod communication based on labels.
*   **Service Mesh (mTLS):** Enforces mutual TLS authentication between all services, ensuring all communication is encrypted and authenticated at the application layer.
*   **Pod Identity:** Verifies the identity of the pod before granting access to resources or services.
*   **Admission Controllers (OPA/Kyverno):** Enforce policy checks *before* resources are created or modified (e.g., ensuring all deployments use specific security contexts).
*   **Image Signing/Verification:** Ensures that only cryptographically verified, trusted container images are allowed to run.
*   **Runtime Security (Falco):** Monitors kernel system calls to detect anomalous behavior (e.g., shell execution inside a web server container).
*   **Difference:** Traditional perimeter security trusts anything *inside* the firewall. Zero Trust assumes the network is hostile and verifies every single request, user, and workload identity.

CL13 — A **CDN (Content Delivery Network)** is a globally distributed network of proxy servers and data centers designed to cache static and dynamic content closer to the end-user. It works by routing user requests to the nearest edge location (Point of Presence or PoP) that holds a cached copy of the content. Use a CDN when serving high-volume, geographically distributed static assets (images, JS, CSS) to reduce latency and offload traffic from the origin server. Use the origin server when content is highly dynamic, requires real-time database lookups, or is sensitive and cannot be cached publicly.

CL14 — **Regions** are large, geographically distinct areas (e.g., US-East-1). **Availability Zones (AZs)** are isolated data centers within a Region, physically separated from each other with independent power, cooling, and networking. Deploying across multiple AZs ensures high availability; if one AZ suffers a localized outage (power failure, fire), resources in other AZs remain operational. Zonal resources are tied to a single AZ; Regional resources span multiple AZs, providing inherent fault tolerance.

CL15 — A **Managed Database Service** abstracts away the operational burden of database administration. The cloud provider handles tasks like patching the OS and database engine, automated backups, high availability failover (automatic promotion of replicas), monitoring, and scaling infrastructure. This frees the user to focus solely on schema design, query optimization, and data integrity.

CL16 — **IAM Users** are human identities with credentials. **Groups** are collections of users. **Roles** are identities that can be assumed by services or users without permanent credentials. **Policies** are JSON documents defining permissions (what actions are allowed on which resources). **Principle of Least Privilege (PoLP):** Granting an entity (user, role, service) only the minimum permissions necessary to perform its required function, and nothing more. Application: Instead of giving a developer admin access, grant them a role that only allows read/write access to the specific S3 bucket required for their project.

CL17 — **Serverless Computing** is a cloud execution model where the cloud provider dynamically manages the allocation and provisioning of servers. Developers upload code (functions), and the provider runs it only when triggered by an event. **Cold Starts** occur when a function has not been invoked recently; the provider must initialize the execution environment, leading to latency. This matters because it adds unpredictable delay to the first request. Serverless is a poor fit for applications requiring extremely low, consistent latency (e.g., high-frequency trading) or for long-running, predictable background jobs that are always active.

CL18 — **Ingress Resource:** A Kubernetes object that defines rules for routing external HTTP/S traffic to services, typically managed by an Ingress Controller (like Nginx). **Gateway API:** A newer, more flexible standard that extends Ingress, allowing for more granular control over traffic routing, policy enforcement, and multi-tenancy. **Cloud Load Balancer Annotations:** Using specific annotations on a Service object to instruct the cloud provider's native load balancer how to configure itself. **Service Mesh Ingress Gateways:** The ingress point provided by the service mesh (e.g., Istio Ingress Gateway), which handles routing, policy, and mTLS termination before traffic enters the mesh. **TLS Termination:** Can occur at the Load Balancer (L4/L7), the Ingress Controller, or the Service Mesh Gateway. Use Gateway API over Ingress when complex routing, traffic splitting (canary deployments), or advanced policy enforcement is required beyond simple path-based routing.

CL19 — A $80k/month spend requires a FinOps culture.
*   **Commitment Strategy:** Use **Reserved Instances (RIs)** or **Savings Plans** for predictable, steady-state workloads (e.g., core databases, baseline compute) for deep discounts. Use **Spot/Preemptible Instances** for fault-tolerant, stateless workloads (e.g., batch processing, CI/CD runners) to achieve massive savings.
*   **Optimization:** **Right-sizing** involves continuously monitoring utilization metrics to downgrade over-provisioned VMs. **Storage Tiering** moves infrequently accessed data to cheaper tiers (e.g., S3 Intelligent-Tiering automatically manages transitions).
*   **Visibility:** Implement **Showback** (showing teams their usage costs) and **Chargeback** (billing teams for usage). Tools like CloudHealth or native cloud cost explorers are essential.
*   **Process:** Establish a weekly cost review meeting involving engineering and finance to review anomalies and commitment utilization.

CL20 — A multi-cloud strategy aims to mitigate vendor lock-in and leverage best-of-breed services.
*   **Abstraction Layers:** Use Kubernetes as the primary runtime abstraction layer, allowing the same containerized application to run on EKS, AKS, or GKE.
*   **IaC Portability:** Use Terraform/OpenTofu to define infrastructure in a provider-agnostic manner, minimizing provider-specific code.
*   **Networking:** Establish secure, high-throughput connectivity between clouds using VPNs or dedicated interconnects (e.g., AWS Direct Connect to Azure ExpressRoute).
*   **Identity Federation:** Use a central Identity Provider (IdP) like Okta or Azure AD to federate identities across both AWS IAM and Azure AD, ensuring users have one identity for both clouds.
*   **Trade-offs:** The theoretical benefit is resilience and negotiation leverage. The real-world trade-off is massive operational complexity, increased latency due to cross-cloud networking, and the need for specialized engineers proficient in two complex ecosystems. Multi-cloud is justified when regulatory compliance demands it, or when a single vendor lacks a critical, unique service required by the business.

**OT Infrastructure Architecture**

OT1 — The **Purdue Model (ISA-95)** is a hierarchical reference model for industrial control systems, segmenting the enterprise and control layers.
*   **Level 0 (Process):** Physical sensors and actuators (e.g., temperature probes, valves).
*   **Level 1 (Basic Control):** Controllers that directly monitor and control physical processes (e.g., PLCs, RTUs).
*   **Level 2 (Supervisory Control):** HMIs and SCADA systems that monitor and manage Level 1 devices.
*   **Level 3 (Site Operations):** Manufacturing execution systems (MES) and plant historians.
*   **Level 4 (Enterprise Business):** ERP systems and business planning software.

OT2 — **IT networks** focus on data throughput, availability, and rapid patching cycles (e.g., Windows updates). **OT networks** focus on deterministic operation, safety, and continuous uptime. Standard IT patching is dangerous in OT because an unexpected reboot or software update can cause physical process disruption, leading to equipment damage, safety hazards, or production halts. OT systems often run legacy, proprietary operating systems that cannot be easily patched.

OT3 — The **Industrial DMZ (IDMZ)** acts as a buffer zone between the enterprise IT network (Level 4) and the control network (Level 3/2). It hosts intermediary services (e.g., data historians, patch servers, jump hosts) that broker communication. Traffic should flow *from* IT *to* OT (e.g., data requests, patch downloads) but must be strictly controlled and often unidirectional. Direct connectivity from Level 4 to Level 1 is dangerous because a compromised IT workstation could directly issue malicious commands to PLCs, bypassing all control logic and safety mechanisms.

OT4 —
1.  **Modbus TCP:** A simple, widely used serial protocol adapted for TCP/IP. Typically operates at Level 1/2.
2.  **OPC UA:** A platform-independent, secure, service-oriented architecture for industrial data exchange. Operates across Levels 2, 3, and 4.
3.  **EtherNet/IP (CIP):** A common industrial Ethernet protocol used heavily in Rockwell/Allen-Bradley environments. Operates at Level 1/2.
4.  **PROFINET:** A high-speed, real-time industrial Ethernet protocol, common in Siemens environments. Operates at Level 1/2.
5.  **MQTT:** A lightweight, publish/subscribe messaging protocol ideal for constrained devices and IoT data transmission. Used heavily at the Edge (Level 2/3 boundary).

OT5 — A **Firewall** inspects network packets based on rules (IP, port, protocol) and can block malicious traffic. A **Data Diode** is a hardware device that physically enforces unidirectional data flow (one-way). You use a data diode when absolute assurance is required that data *cannot* flow backward (e.g., sending critical process data to the cloud while preventing any remote command injection). The limitation is that it cannot inspect or filter traffic; it only allows flow in one direction.

OT6 — **Data Flow:** Level 1/2 $\rightarrow$ PLC/SCADA $\rightarrow$ OPC UA Server (collects data) $\rightarrow$ Edge Gateway (translates/buffers) $\rightarrow$ MQTT Broker (publishes data) $\rightarrow$ Cloud Ingestion Platform. **Security Boundaries:** Boundaries must be placed at the IDMZ (between Level 3 and the Edge Gateway) and at the Edge Gateway itself, ensuring the cloud platform never directly communicates with the Level 1/2 control network.

OT7 — **IEC 62443** defines security requirements based on **Zones** (groupings of assets with common security requirements) and **Conduits** (the communication paths between zones). A **Zone** is defined by its security level and the assets it contains (e.g., "PLC Control Zone"). A **Conduit** is the logical or physical connection path between two zones, which must be secured by a firewall or gateway.
*   **Model Design:**
    *   *Corporate Zone (L4):* ERP, Business Systems.
    *   *IDMZ Zone:* Data Historian, Patch Server.
    *   *SCADA Zone (L3):* SCADA Servers, Engineering Workstations.
    *   *Control Zone (L2):* HMIs, PLCs.
    *   *SIS Zone (L1/Safety):* Safety Instrumented Systems (must be the most isolated).
    *   Conduits must be strictly controlled (e.g., only OPC UA traffic allowed from SCADA Zone to IDMZ Zone).

OT8 — **Segmentation Strategy:** Implement VLANs to logically separate functions (e.g., VLAN 10: PLCs, VLAN 20: HMIs, VLAN 30: SCADA Servers, VLAN 99: Management). Place industrial firewalls/Layer 3 switches at the boundaries between these VLANs. The switch architecture should be hierarchical (Core $\rightarrow$ Aggregation $\rightarrow$ Access). **Remote Access:** Must terminate in the IDMZ via a hardened jump host with MFA. **Transition:** Implement segmentation in phases, starting with non-critical lines, using passive monitoring first, and only enforcing firewall rules after extensive testing in a staging environment to ensure zero production impact.

OT9 — **BPCS (Basic Process Control System):** Controls the normal, intended operation of the process (e.g., maintaining temperature setpoints). **SIS (Safety Instrumented System):** An independent, separate system designed solely to monitor for hazardous conditions and bring the process to a safe state if limits are exceeded, regardless of the BPCS state. **IEC 61511:** The functional safety standard that dictates the lifecycle and integrity requirements for SIS. The SIS must be isolated because its function is safety; if a ransomware attack compromises the BPCS, the SIS must remain operational and unaffected to prevent catastrophic failure.

OT10 — **PLC (Programmable Logic Controller):** A ruggedized, discrete controller designed for real-time, deterministic control of specific I/O points (Level 1). **DCS (Distributed Control System):** A large, integrated system designed for complex, continuous processes (e.g., chemical plants), offering high redundancy and centralized control across many controllers. **SCADA (Supervisory Control and Data Acquisition):** A high-level system (Level 2/3) that collects data from PLCs/RTUs and provides a human interface for monitoring and supervisory control. They can coexist; PLCs/RTUs execute the control logic, while SCADA monitors and commands them.

OT11 — Remote access must be architected via a **Jump Host** located in the IDMZ. The user connects to the jump host, authenticates via **MFA**, and then initiates a session to the target OT asset. **Session Recording** is mandatory for auditing. Access must be **time-limited** and require explicit approval. RDP directly to an HMI from the corporate network is unacceptable because it bypasses all security controls, exposes the control network directly to the enterprise network, and provides an unmonitored path for lateral movement.

OT12 — **Detection & Response:**
1.  **Monitoring:** Deploy passive network monitoring (IDS/Anomaly Detection) sensors in the Level 3 network to baseline normal PLC/SCADA traffic patterns.
2.  **Asset Inventory:** Immediately verify the compromised vendor VPN appliance and map all connected assets.
3.  **Response:** Isolate the compromised segment (e.g., firewall rule blocking the vendor VPN subnet from Level 3). Do *not* immediately shut down processes.
4.  **Coordination:** Engage the control room operator to monitor process variables manually and confirm the threat actor's activity is not impacting physical safety.
5.  **Containment:** If the threat actor attempts to move laterally, use network segmentation to quarantine the affected zone.
*   **Operator Role:** The plant operator is the ultimate safety authority. They must maintain manual control and confirm that any isolation or response action does not compromise the physical safety or operational integrity of the facility.

OT13 — An **HMI (Human-Machine Interface)** is the graphical interface that allows human operators to monitor the status of industrial processes (e.g., viewing tank levels, pump status) and issue high-level commands (e.g., start/stop a pump). It differs from an **Engineering Workstation** because the HMI is designed for continuous, real-time operational monitoring by operators, whereas the Engineering Workstation is used by technicians to program, configure, and troubleshoot the underlying PLCs.

OT14 — A **Historian** is a time-series database specifically designed to record, store, and manage vast amounts of process data (e.g., temperature readings, flow rates) over long periods. It is crucial for trend analysis, regulatory compliance, and root cause analysis. A **Plant Historian (Level 3)** stores high-frequency, granular data specific to that physical site. An **Enterprise Historian (Level 4)** aggregates, summarizes, and stores this data from multiple plants for long-term business intelligence and corporate reporting.

OT15 — **Ladder Logic** is a graphical programming language that mimics the relay logic circuits used in older electrical control panels. It is executed by a **PLC**. It remains dominant because it is highly intuitive for electricians and control engineers, directly mapping to physical wiring diagrams, making troubleshooting straightforward even decades later.

OT16 — An **RTU (Remote Terminal Unit)** is a microprocessor-controlled electronic device designed to interface with remote sensors and actuators in geographically dispersed locations. It differs from a PLC primarily in its ruggedness and deployment environment; RTUs are often used in harsh, remote, or distributed environments (e.g., pipelines, remote substations) where a centralized PLC rack is impractical, while PLCs are typically used in centralized control panels.

OT17 — **Analog Signals** (4-20mA, 0-10V) represent continuous physical measurements (e.g., pressure, temperature). **Digital Signals** represent discrete states (e.g., ON/OFF, valve open/closed). **4-20mA is preferred over 0-20mA** because the 4mA signal provides a "live zero" or "fault detection" signal. If the current drops to 0mA, the receiving device knows the wire is broken or the sensor has failed, whereas a 0mA signal in a 0-20mA system could mean the process variable is genuinely zero.

OT18 — **OT Asset Inventory** is a comprehensive, accurate database of every device (PLC, HMI, sensor, network switch) on the control network, including firmware versions, communication protocols, and physical location. It is the foundation because you cannot secure what you do not know exists. **Passive Monitoring** involves listening to network traffic (SPAN ports) to discover assets and protocols without sending any packets. **Active Scanning** involves sending probes (like Nmap) to discover assets. Active scanning is dangerous because many legacy OT devices are not designed to handle unexpected network traffic and can crash, reboot, or enter an unstable state.

OT19 — **MITRE ATT&CK for ICS** is a knowledge base of adversary tactics and techniques specific to Industrial Control Systems. It maps the cyber kill chain to OT environments.
*   **Tactics & Examples:**
    1.  **Initial Access:** (e.g., Spearphishing Link)
    2.  **Inhibit Response Function:** (e.g., Manipulate Safety System)
    3.  **Impact:** (e.g., Denial of Control)
    4.  **Collection:** (e.g., Gather System Information)
    5.  **Command and Control:** (e.g., Remote Access Tool)
*   **Difference:** Enterprise ATT&CK focuses on IT goals (data theft, ransomware). ICS ATT&CK focuses on operational goals (process disruption, safety compromise). You use it to assess gaps by mapping your current defenses against known adversary techniques relevant to your specific industrial process.

OT20 — **Converged IT/OT SOC:**
*   **Log Collection:** Use passive network monitoring (e.g., network taps feeding an IDS) to capture OT protocol traffic (Modbus, OPC UA) without actively querying the PLCs. Forward metadata and alerts, not raw control traffic, to the SIEM.
*   **SIEM Integration:** Ingest IT logs (AD, firewalls) and OT metadata/alerts into the SIEM.
*   **Detection Rules:** Develop OT-specific rules: e.g., "PLC X received a firmware upload command outside of maintenance window," or "Unusual Modbus write command detected on critical register."
*   **Triage:** Establish a tiered workflow: L1 IT analysts handle standard alerts; L2/L3 analysts (who must have OT engineering knowledge) handle OT alerts.
*   **False Positives:** Acknowledge that OT environments are noisy. Baseline normal operations rigorously to tune rules, prioritizing alerts that indicate unauthorized *control* changes over simple communication errors.
*   **Firmware Change Alert:** This is a high-severity alert. The workflow must immediately trigger a Level 2 OT engineer to verify the change against the approved change management system before any action is taken, ensuring the change was authorized and safe.
