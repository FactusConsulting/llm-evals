T1 — The `tofu plan` command generates an execution plan, showing exactly what actions (create, update, delete) OpenTofu intends to perform without making any changes to the infrastructure. `tofu apply` executes the plan, making the actual changes to the cloud resources based on the generated plan.

T2 — State is a file (usually stored remotely) that maps the real-world infrastructure resources to the configuration defined in the OpenTofu code. It tracks the IDs, attributes, and current state of every resource managed by the configuration. Remote state is crucial because it provides a single source of truth, enables collaboration among team members, and ensures state persistence across runs, preventing configuration drift and accidental resource loss.

T3 — `count` creates multiple identical instances of a resource based on an integer value. `for_each` creates multiple instances based on the keys/values of a map or set. `for_each` is preferred when the instances need to be uniquely identifiable or when the configuration logic depends on specific names/keys, as it allows referencing the instance by its key (e.g., `each.key`), whereas `count` only allows referencing by index (e.g., `count.index`).

T4 — This is known as configuration drift. OpenTofu detects this drift during the `tofu plan` phase by comparing the desired state (in code) against the actual state (read from the cloud provider API). It will report the discrepancy and propose an update plan to reconcile the actual state with the desired state, effectively overwriting the manual change.

T5 — ```hcl
resource "aws_instance" "vm" {
  count = 3
  ami           = "ami-0abcdef1234567890" # Example AMI
  instance_type = "t2.micro"

  tags = {
    Name = "web-${count.index + 1}"
  }
}
```

T6 — A `terraform_remote_state` data source is used to *read* the state file of another, already existing OpenTofu configuration (e.g., reading the output of a networking module from a separate root module). Output values are used to *export* data from the current module/root configuration to be consumed by other modules or users. The recommended alternative is to use **module outputs** combined with **module inputs**. This keeps the data flow explicit, enforces dependency management via the module structure, and avoids coupling the root modules to the internal state structure of another configuration.

T7 — This is a classic race condition. The `null_resource` provisioner runs *before* the dependent resources are fully configured or ready to consume the output. The provisioner executes, but the kubeconfig output (which relies on the cluster being fully provisioned) is not yet populated or available in the state. The fix is to use an **explicit dependency** via `depends_on` on the dependent resources, ensuring they only run *after* the `null_resource` has successfully completed its remote execution and populated the necessary outputs.

T8 — `tofu import` allows you to bring existing, manually provisioned infrastructure resources under the management of OpenTofu without writing the configuration code first. Its limitation is that it only imports the *current* state; it does not automatically generate the HCL code. The import block (1.5+) improves this by allowing you to define the resource type and local configuration *alongside* the import address, providing immediate context and validation for the resource being imported.

T9 — A **variable** is a placeholder for input data that allows the configuration to be reusable and parameterized (e.g., defining a region or instance size). An **output** is a value that is exported from a module or root configuration, allowing other parts of the infrastructure or users to retrieve information generated by the configuration (e.g., the public IP address of a created VM).

T10 — A provider is a plugin that enables OpenTofu to interact with a specific API or service (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without `tofu init`, OpenTofu will fail because it has not downloaded or configured the necessary provider plugins defined in the configuration, meaning it doesn't know *how* to communicate with the target infrastructure.

T11 — The `.terraform.lock.hcl` file pins the exact versions of all providers and modules used in the configuration. It ensures that every team member and CI/CD pipeline uses the identical, tested dependency versions, preventing unexpected behavior or breakage caused by upstream provider updates. It must be committed to version control to guarantee environment consistency.

T12 — `tofu destroy` tears down all resources managed by the current state file. To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web1`).

T13 — A data source allows OpenTofu to fetch information about existing infrastructure or external data that is *not* managed by the current configuration. Example: Using a `aws_ami` data source to look up the latest Amazon Linux 2 AMI ID, rather than hardcoding a potentially outdated ID into a resource block.

T14 — **Variables** are inputs provided to the configuration, typically defined in `variables.tf` and supplied via CLI flags or `.tfvars` files. **Locals** are variables defined *within* a specific configuration file or module to store intermediate, derived values used only within that scope. Use locals when you need to perform calculations, string manipulations, or combine existing variables/outputs to create a clean, reusable value *before* it is passed to a resource block.

T15 — The lifecycle block controls how OpenTofu manages the resource during its lifecycle.
*   `create_before_destroy`: Creates a new replacement resource *before* destroying the old one, ensuring zero downtime during updates.
*   `prevent_destroy`: Prevents the resource from being deleted via `tofu destroy` or updates that would result in deletion.
*   `ignore_changes`: Tells OpenTofu to ignore specific attributes that might be manually changed outside of OpenTofu, preventing drift detection errors for those fields.

T16 — A moved block is a feature that allows you to refactor the structure of your configuration (e.g., moving a resource from one module to another, or renaming a resource) without forcing OpenTofu to destroy and recreate the underlying cloud resource. It tells the state file to logically map the old resource address to the new one, preserving the resource identity.

T17 — OpenTofu builds a Directed Acyclic Graph (DAG) of all resources, where nodes are resources and edges represent dependencies. **Implicit dependencies** are automatically inferred when one resource references an attribute of another (e.g., an EC2 instance referencing a Security Group ID). **Explicit dependencies** are defined using `depends_on`. `depends_on` forces a specific execution order, which can negatively affect parallelism because it forces sequential execution where the provider might otherwise run tasks concurrently. It should be used sparingly, only when implicit dependencies are insufficient.

T18 — 1. **Modularization:** Break the 200+ resources into smaller, focused modules. This allows OpenTofu to parallelize operations across independent modules. 2. **Targeting/Filtering:** Use `-target` judiciously during development/testing to run only necessary changes, though this is not scalable for production plans. 3. **State Splitting:** If resources are logically independent (e.g., networking vs. compute), split them into separate state files/workspaces. 4. **Provider Optimization:** Review provider configurations for unnecessary polling or complex API calls. *Tradeoff:* Modularization adds complexity to module interfaces; State Splitting increases operational overhead.

T19 — State locking ensures that only one operation (plan or apply) can modify the state file at any given time, preventing concurrent writes that could corrupt the state. If a lock is not released (e.g., CI crash), the state remains locked, causing subsequent operations to hang indefinitely. To manually break a lock, you use the backend-specific unlock command (e.g., `terraform force-unlock`). The risk is that if another process *is* running and hasn't finished, breaking the lock will lead to a state corruption race condition.

T20 — 1. **Configure Backend:** Update the `backend` block in the root module to point to the S3 bucket, specifying the DynamoDB table name for locking. 2. **Initialize:** Run `tofu init`. OpenTofu will detect the backend change and prompt you to migrate the existing state. 3. **Migration:** Confirm the migration. OpenTofu will copy the contents of the local state file into the new remote S3 bucket and register the lock mechanism with DynamoDB. 4. **Verification:** Run `tofu plan`. If successful, the plan will execute against the remote state, confirming the migration was successful and the lock is active.

A1 — A **playbook** is a YAML file that describes the desired state of your infrastructure, containing a list of plays, where each play targets a group of hosts and contains tasks. A **role** is a standardized, reusable structure that groups related tasks, handlers, variables, and templates, promoting organization. A **task** is a single action within a playbook (e.g., "install Nginx," "copy configuration file") that uses a specific Ansible module.

A2 — `ansible_facts` is a dictionary containing system information gathered from the target host during the connection phase (e.g., OS version, memory, network interfaces). To access the OS family, you would use `ansible_facts['os_family']`.

A3 — **`command`**: Executes a raw command string directly on the remote host. It is the lowest level and does not check for idempotency. **`shell`**: Executes commands through the host's shell (e.g., Bash). It is necessary for piping (`|`) or shell features, but still not inherently idempotent. **`raw`**: Similar to `command` but used when connecting via network protocols other than SSH (e.g., Telnet, SSH over a specific port). Use `command` for simple, idempotent actions (like package installation via `apt`), `shell` when complex shell logic is required, and `raw` for non-SSH connections.

A4 — Idempotency means that running the same task multiple times yields the same result without causing unintended side effects after the first successful run.
*   **Idempotent Example:** Using the `ansible.builtin.package` module to install `nginx`. If Nginx is installed, the module reports "ok" (no change); if not, it installs it and reports "changed."
*   **Non-Idempotent Example:** Using the `ansible.builtin.command` module to run `echo "Hello" >> /tmp/log.txt`. Running this command twice will append "Hello" twice, changing the state each time.

A5 — ```yaml
- name: Install web server components based on OS
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family == 'Debian' or ansible_os_family == 'RedHat'
```

A6 — The precedence order (highest to lowest) is:
1.  `--extra-vars` (CLI overrides)
2.  `host_vars` (Specific host variables)
3.  `group_vars` (Variables defined for a specific group)
4.  `role_vars` (Variables defined within a role)
5.  `defaults` (Variables defined in the role's `defaults/main.yml`)
6.  Inventory variables (Lowest priority)

A7 — This requires a combination of inventory grouping, `serial`, and potentially `wait_for` if the RKE2 agent needs to signal readiness.
1.  **Inventory:** Define groups: `[initial_nodes: node1 node2 node3]` and `[remaining_nodes: node4 ... node50]`.
2.  **Playbook Structure:** Use `serial: 3` on the play targeting `initial_nodes`.
3.  **Execution:** Run the playbook. Ansible will process the first 3 nodes. Once those 3 are complete, the play will proceed to the next batch (or the next play targeting `remaining_nodes` if structured that way). `wait_for` can be used within the tasks to ensure the service is listening before proceeding to the next step.

A8 — `ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys, secrets) within Ansible files. To encrypt a single variable, you use the vault mechanism when defining the variable in a file (e.g., `secrets.yml`) and then use the vault password when running the playbook: `ansible-playbook site.yml --ask-vault-pass`. The variable itself is encrypted using the vault key.

A9 — An inventory file defines the hosts (servers) that Ansible will manage and groups them logically. A **static inventory** is manually defined in a file (e.g., `hosts.ini`). A **dynamic inventory** is generated on the fly by a script or plugin that queries an external source (like AWS EC2, VMware vCenter, or a CMDB) to discover and update the list of hosts before each run.

A10 — ```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

A11 — A **handler** is a special task that is only executed when explicitly notified by another task. It is designed for actions that should only run *after* a change has occurred (e.g., restarting a service). It differs from a regular task because it is not run sequentially; it is queued and executed only when triggered. A handler is triggered using the `notify` keyword in a task: `tasks: - name: Change config - ansible.builtin.copy: ... notify: restart nginx`.

A12 — The `ansible.cfg` file configures the behavior of Ansible itself, overriding defaults. Common settings include:
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Sets the default SSH user to connect as.
3.  `host_key_checking`: Controls whether Ansible verifies the host's SSH key (set to `False` for automation convenience, but risky).

A13 — The `register` keyword captures the return value of a task (the result, stdout, error, etc.) and stores it in a variable. You use this registered variable in a subsequent task by referencing it (e.g., `{{ result_of_task.stdout }}`).
Example: `tasks: - name: Get IP - ansible.builtin.command: ip addr show eth0 register: ip_info` followed by `tasks: - name: Use IP - debug: var: "{{ ip_info.stdout }}"`.

A14 — **`include_tasks`**: Reads and executes tasks from a file *during* the playbook parsing phase. It is generally used for including small, specific task lists. **`import_tasks`**: Reads and executes tasks from a file *after* the playbook has been parsed. It is better for large, complex task sets or roles. `import_tasks` is preferred for conditional evaluation because it allows the imported file to be evaluated against the current playbook's variables before execution.

A15 — Ansible Galaxy is a community repository where users share reusable Ansible content, primarily roles and collections. You use a `requirements.yml` file to declare dependencies. The file lists the required roles/collections and their versions:
```yaml
---
roles:
  - name: nginx
    src: https://galaxy.ansible.com/nginx
    version: 2.1.0
collections:
  - name: community.general
    version: 5.0.0
```
You then install them using `ansible-galaxy install -r requirements.yml`.

A16 — Connection plugins define *how* Ansible connects to the target host.
*   **`ssh`**: The default. Uses SSH to execute commands remotely. Best for Linux/Unix targets.
*   **`local`**: Executes tasks directly on the Ansible control node itself, without connecting to a remote host. Used for local file manipulation or running scripts on the machine running Ansible.
*   **`network_cli`**: Used for managing network devices (routers, switches) via CLI protocols (like Telnet or SSH CLI mode).
Use `ssh` for servers, `local` for control node tasks, and `network_cli` for infrastructure hardware.

A17 — **`delegate_to`**: Forces a task to run on a host *other than* the one defined in the play's inventory. You can delegate to a specific host, a group, or even `localhost`. **`run_once`**: Ensures that a task, even if targeted at multiple hosts, is executed only once across the entire managed inventory.
*   **Practical Example:** You need to gather the list of all active load balancers from a remote AWS host (`delegate_to: localhost`) and then use that list to update a configuration file on the Ansible control node (`run_once: true`).

A18 — 1. **Increase Forks:** Increase the `forks` setting in `ansible.cfg` to run more hosts in parallel (Tradeoff: Increased resource usage on the control node). 2. **Fact Caching:** Use `ansible.builtin.setup` with caching to avoid re-gathering facts on every run (Tradeoff: Requires a persistent cache backend). 3. **Pipelining:** Use pipelining (if supported by the connection plugin) to send multiple commands over a single connection (Tradeoff: Can complicate error handling). 4. **Mitogen/Tower:** Use a dedicated automation controller (like Ansible Tower/AWX) which manages job scheduling, concurrency, and state much more efficiently than raw CLI runs.

A19 — Jinja2 templating allows dynamic content generation.
*   `{{ variable }}`: Used for outputting the value of a variable.
*   `{% control_structure %}`: Used for control flow logic (loops, conditionals, assignments).
*   `{# comment #}`: Used for comments that are stripped from the final rendered output.
**Snippet:**
```jinja2
{% for server in backend_servers %}
upstream backend_servers {
    server {{ server.host }}:{{ server.port }};
    server {{ server.host }}:{{ server.port }}; # Health check target
}
{% endfor %}
```

A20 — This requires a controlled, iterative process:
1.  **Serial Batches:** Use `serial: 5` (or similar) in the play to ensure only 5 servers are updated at a time.
2.  **Pre-Task (LB Registration):** Before updating a batch, use the `uri` module (or cloud provider module) to register the current batch of servers with the load balancer.
3.  **Update Task:** Apply the configuration change (e.g., using `template` module).
4.  **Health Check:** After configuration, use the `uri` module to perform a health check against the newly configured server. If it fails, the task fails, triggering the `rescue` block.
5.  **Post-Task (LB Deregistration):** If the health check passes, deregister the old configuration (if applicable) and ensure the new configuration is active.
6.  **Rollback Strategy:** Wrap the core update logic in a `block`/`rescue` structure. If any task within the `block` fails (e.g., health check fails), the `rescue` block executes, which contains tasks to revert the configuration or deregister the server from the load balancer, ensuring the fleet remains stable.
