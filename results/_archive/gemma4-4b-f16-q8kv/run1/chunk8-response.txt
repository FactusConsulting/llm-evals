AA1 — A monolith is a single, tightly coupled application where all business logic resides in one codebase. Microservices architecture decomposes the application into a collection of small, independent, loosely coupled services, each running its own process and communicating via APIs.
Problems microservices introduce:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication.
2. **Operational Overhead:** Requires sophisticated CI/CD, monitoring, and orchestration (e.g., Kubernetes).
3. **Data Consistency:** Managing transactions across multiple independent databases (distributed transactions).

AA2 — **Synchronous communication** requires the caller to wait for an immediate response from the service it calls. Example: REST API call (HTTP GET/POST). **Asynchronous communication** involves sending a message or event without expecting an immediate reply; the sender continues processing. Example: Kafka or RabbitMQ.

AA3 — A **Reverse Proxy** sits in front of one or more servers, routing external client requests to the appropriate internal service based on rules (e.g., load balancing, SSL termination). An **API Gateway** is a specialized reverse proxy that adds business logic, such as request routing, authentication/authorization, rate limiting, protocol translation, and request aggregation, specifically tailored for client consumption. An API Gateway *can* replace a reverse proxy entirely if the proxy's function is purely routing/load balancing, but it adds significant application-level features that a basic reverse proxy lacks.

AA4 — The **Saga pattern** is a sequence of local transactions where each transaction updates the database and publishes an event to trigger the next step. If a step fails, the Saga executes compensating transactions to undo the preceding changes, maintaining data consistency across services.
*   **Choreography-based:** Services communicate by producing and consuming events without a central coordinator. Appropriate when the workflow is simple, decentralized, and services are highly autonomous.
*   **Orchestration-based:** A dedicated service (the orchestrator) manages the workflow, telling each participant service what local transaction to execute. Appropriate for complex workflows requiring centralized control, monitoring, and easier failure handling.

AA5 — **CQRS** separates the model used for updating data (Commands) from the model used for reading data (Queries). This allows independent scaling and optimization of read and write paths. It is often paired with **Event Sourcing** because Event Sourcing stores the state of the application as a sequence of immutable events. This combination solves the problem of complex state management in traditional CRUD by providing a complete, auditable history of *how* the state was reached, allowing for powerful temporal queries and rebuilding state projections (read models) from the event stream.

AA6 — The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service).
The three states are: **Closed** (normal operation), **Open** (requests fail fast immediately without calling the service), and **Half-Open** (a limited number of test requests are allowed through to check if the service has recovered).
It differs from a simple retry with backoff because retry attempts continue hammering a failing service, potentially worsening its state. The Circuit Breaker *stops* the hammering. They are used together: the Circuit Breaker prevents cascading failures, and when the circuit is closed, retries with backoff can be used for transient network glitches.

AA7 — **1. Shared DB, Shared Schema (Row-level Tenant ID):**
*   *Cost:* Lowest (shared infrastructure).
*   *Security:* Moderate (relies heavily on application logic/query filtering).
*   *Operational Complexity:* Low.
*   *Noisy-Neighbor Risk:* High (a heavy tenant can impact all others).
**2. Shared DB, Separate Schema per Tenant:**
*   *Cost:* Low to Moderate.
*   *Security:* High (database permissions isolate tenants).
*   *Operational Complexity:* Moderate (schema management overhead).
*   *Noisy-Neighbor Risk:* Moderate (resource contention within the DB instance).
**3. Separate DB per Tenant:**
*   *Cost:* Highest (N databases).
*   *Security:* Highest (complete isolation).
*   *Operational Complexity:* Highest (managing N instances).
*   *Noisy-Neighbor Risk:* Lowest (complete isolation).

AA8 — **Strong Consistency** guarantees that once a write operation is acknowledged, all subsequent read operations will immediately see that write. **Eventual Consistency** guarantees that if no new updates are made to a data item, eventually all accesses to that item will return the last updated value, but there is a window where reads might return stale data.
To prevent overselling inventory (a critical business invariant), **Strong Consistency** is required for the inventory decrement operation.
*   **Consistency Model:** Strong Consistency (or Linearizability).
*   **Data Store:** A strongly consistent, transactional database (e.g., PostgreSQL, CockroachDB, or a distributed SQL database).
*   **Patterns:** Use pessimistic locking or atomic database transactions (e.g., `UPDATE inventory SET stock = stock - 1 WHERE item_id = X AND stock >= 1`). At scale, this often means sharding the inventory by item ID and ensuring the shard itself maintains strong consistency.

AA9 — A **sidecar proxy** is a small, dedicated proxy container deployed alongside every instance of a service container in a deployment (e.g., in Kubernetes). It intercepts all inbound and outbound network traffic for the main application container.
In **Istio**, Envoy is the proxy deployed as the sidecar. It handles service mesh functions like traffic routing, telemetry collection, and security enforcement.
*   **Data Plane:** The set of proxies (Envoy sidecars) that handle the actual network traffic (L4/L7 forwarding).
*   **Control Plane:** The management layer (e.g., Istiod) that configures and manages the data plane proxies, pushing routing rules, policies, and certificates to them.
mTLS between sidecars solves the problem of *untrusted network hops*. Application-level TLS requires the application code to manage certificates and handshake logic. Sidecar mTLS handles mutual authentication and encryption transparently at the network layer, ensuring that only authenticated services can communicate, regardless of the application's internal logic.

AA10 — The **Strangler Fig pattern** involves gradually replacing specific functionalities of a legacy system with new services, routing traffic away from the old system piece by piece until the monolith is "strangled" and can be retired.
**Migration Strategy:**
1. **Identify Seams:** Identify a bounded context in the monolith (e.g., User Profile Management).
2. **Build New Service:** Develop the new User Profile service in .NET 8.
3. **Implement Facade/Proxy:** Place an API Gateway in front of the monolith.
4. **Reroute Traffic:** Configure the Gateway to route all `/api/v2/users/*` requests to the new .NET 8 service, while all other requests continue to the monolith.
5. **Data Synchronization:** Implement a mechanism (e.g., Change Data Capture or dual writes) to keep the new service's data synchronized with the monolith's database during the transition.
6. **Iterate:** Repeat for the next bounded context until the monolith is empty.

AA11 — The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable, and resilient software-as-a-service applications.
Six factors and their importance:
1. **Codebase:** One codebase tracked in revision control, many deploys. (Ensures consistency across environments).
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures reproducibility).
3. **Config:** Store configuration in the environment. (Decouples code from deployment environment).
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. (Allows easy swapping of infrastructure).
5. **Build, Release, Run:** Strictly separate build, release, and run stages. (Enables immutable deployments).
6. **Processes:** Execute the application as one or more stateless processes. (Essential for horizontal scaling).

AA12 — **Event-Driven Architecture (Kafka):**
*   *Coupling:* Loose (services only need to know the event schema, not the consumers).
*   *Scalability:* High (consumers can scale independently by reading partitions).
*   *Debugging Complexity:* High (tracing the flow across many asynchronous hops is difficult).
*   *Ordering Guarantees:* Guaranteed within a partition.
*   *Failure Handling:* High resilience; events are persisted and can be replayed.
*   **Request-Driven Architecture (REST/gRPC):**
*   *Coupling:* Tighter (caller must know the service endpoint and contract).
*   *Scalability:* Moderate (scaling is tied to request volume and synchronous dependencies).
*   *Debugging Complexity:* Low (clear request/response chain).
*   *Ordering Guarantees:* Guaranteed by the synchronous call sequence.
*   *Failure Handling:* Requires explicit patterns (Circuit Breaker, Retries).
*   **Choice:** Choose **Event-Driven** when high decoupling, resilience to downstream failure, and auditability (event history) are paramount (e.g., order processing). Choose **Request-Driven** when an immediate response is required (e.g., user login validation).

AA13 — A **Load Balancer** distributes incoming network traffic across a group of backend servers to ensure no single server is overwhelmed, maximizing throughput and availability.
*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It routes traffic based on IP addresses and port numbers. It is fast because it does not inspect the payload.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (headers, URLs, cookies) to make routing decisions.
*   **Use Case for L7:** Content-based routing (e.g., routing `/images/*` to an image CDN service, but routing `/api/v1/*` to the backend microservice cluster).

AA14 — A **Message Queue** (e.g., RabbitMQ) is a point-to-point or publish/subscribe system designed for reliable task distribution. Messages are consumed and *removed* from the queue by a consumer.
A **Log-Based Message Broker** (e.g., Kafka) is a distributed commit log. Messages are appended to topics and are *retained* for a configurable period, allowing multiple consumers to read the same data stream independently and replay past events.
**When to pick one:** Pick a **Message Queue** for transient task execution where the message should only be processed once (e.g., sending an email notification). Pick a **Log-Based Broker** for stream processing, event sourcing, or when multiple services need to react to the same historical data (e.g., tracking user activity).

AA15 — A **Container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, and libraries. It shares the host OS kernel. A **Virtual Machine (VM)** virtualizes the entire hardware stack, including its own guest OS.
Containers are popular because they offer high density, fast startup times, and environmental consistency ("it runs the same everywhere") without the heavy overhead of booting a full OS for every instance, making them ideal for microservices deployment.

AA16 — A **Stateless Service** does not retain any client session data or state between requests. Every request from the client contains all the necessary information for the service to fulfill it. A **Stateful Service** retains data across multiple requests (e.g., user session data, database connections).
Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance, as no instance holds unique session information that would need to be maintained or synchronized across the cluster.
*   *Stateless Example:* A REST API endpoint that processes a single, self-contained calculation.
*   *Stateful Example:* A Redis cache server or a primary database instance.

AA17 — An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using object-oriented paradigms (classes and objects) instead of writing raw SQL queries.
*   *Popular ORMs:* Hibernate (Java), SQLAlchemy (Python).
*   *Trade-offs:*
    *   **ORM Pros:** Increased developer productivity, database portability (less vendor lock-in), abstraction from SQL syntax.
    *   **ORM Cons:** Performance overhead (due to abstraction layers), the "N+1 query problem," and difficulty in optimizing complex, highly specific database operations compared to hand-tuned SQL.

AA18 — The **Bulkhead pattern** isolates components or resources so that the failure or overload of one component does not cascade and bring down the entire system. It partitions resources into isolated pools, much like watertight compartments in a ship.
It relates to resource isolation by ensuring that a failure in Service A (e.g., exhausting its thread pool) cannot consume the resources needed by Service B.
**Implementation Example:** Using separate thread pools for different downstream calls. If Service A calls three external APIs (A1, A2, A3), instead of using one shared thread pool, you allocate a dedicated, limited thread pool for A1, another for A2, and another for A3. If A1 becomes slow and saturates its pool, A2 and A3 remain unaffected.

AA19 — **Operational Transformation (OT):** A mathematical algorithm that transforms concurrent edits made by different users into a consistent state. It operates on the *operations* (e.g., "insert 'A' at index 5") rather than the document state itself.
**Conflict-free Replicated Data Types (CRDTs):** Data structures designed such that concurrent updates can be merged mathematically without requiring coordination or complex transformation logic, resulting in a convergent state regardless of the order of arrival.
*   *Consistency Guarantees:* OT aims for strong consistency via transformation logic; CRDTs aim for eventual consistency via mathematical convergence.
*   *Latency:* OT can introduce higher latency due to the transformation calculation. CRDTs are generally low latency.
*   *Complexity:* OT is mathematically complex to implement correctly. CRDTs are complex to design but simpler to operate once implemented.
*   *Offline Support:* Both support offline editing, but CRDTs are inherently better suited for merging divergent states without a central server intervention.
**Choice:** I would choose **CRDTs**. For a system that *must* support robust offline editing, CRDTs provide a mathematically sound, decentralized mechanism for merging changes without requiring complex, real-time server-side transformation logic, leading to a more resilient user experience.

AA20 — **Challenges in Polyglot Tracing:**
1. **Context Propagation:** Ensuring the unique trace ID and span ID are passed across service boundaries. This requires standardized headers (e.g., W3C Trace Context or B3 headers) to be injected into every request/message.
2. **Sampling Strategies:** Deciding which requests to trace. **Head-based sampling** decides whether to trace at the entry point (e.g., 1% of requests). **Tail-based sampling** waits until the entire trace is complete to decide whether to keep it, offering higher fidelity but requiring more infrastructure.
3. **Storage/Querying:** Using specialized backends like Jaeger or Tempo to ingest, index, and visualize the massive volume of trace data.
4. **Asynchronous Messaging (Kafka):** The challenge is maintaining continuity. When a request enters Kafka, the trace context must be serialized into the message headers. The consuming service must then extract this context and start a *new child span* linked to the original trace ID, ensuring the trace continues across the queue boundary.

OP1 — **Type 1 (Bare-Metal) Hypervisor:** Runs directly on the host hardware, managing hardware resources and hosting VMs. It offers near-native performance. Examples: VMware ESXi, Microsoft Hyper-V (when run directly).
**Type 2 (Hosted) Hypervisor:** Runs as an application *on top* of a conventional host operating system. It introduces overhead due to the host OS layer. Examples: VMware Workstation, Oracle VirtualBox.

OP2 — **SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. The server sees the storage as a local disk volume. Protocols: Fibre Channel (FC), iSCSI. Used for high-performance transactional databases.
**NAS (Network Attached Storage):** A file-level storage device accessible over a standard network (LAN). The server mounts the storage as a shared folder. Protocols: NFS, SMB/CIFS. Used for file shares, backups, and general data storage.

OP3 — **3-Tier Architecture:**
1. **Access Layer:** Connects end-user devices (switches, endpoints).
2. **Distribution Layer:** Aggregates traffic from the access layer, handles policy enforcement, and routing between VLANs.
3. **Core Layer:** High-speed backbone responsible only for fast packet switching between distribution blocks.
**Leaf-Spine Preference:** Leaf-Spine (Clos network) replaces the hierarchical 3-tier model. It creates a non-blocking, predictable, and highly scalable fabric. It solves the **bottleneck problem** of the 3-tier model, where traffic between two servers in the same access block must traverse up to the distribution layer and back down, creating latency and limiting east-west bandwidth.

OP4 — **Architecture:**
*   **Node Count:** Minimum 3 nodes for quorum.
*   **Quorum:** Achieved via Corosync/Pacemaker consensus mechanism.
*   **Fencing (STONITH):** Essential. A mechanism (e.g., IPMI power cycle, network isolation) to forcibly shut down a failed node to prevent split-brain scenarios.
*   **Shared Storage:** Ceph is ideal for modern, software-defined clusters.
*   **Failure Scenario:** If one node fails, the remaining nodes maintain quorum. The cluster manager (Pacemaker) detects the failure, marks the node as down, and automatically migrates the virtual machine resources (including storage access) to the surviving nodes.

OP5 — **VLAN Trunking:** The process of allowing traffic from multiple VLANs to traverse a single physical link (trunk port).
**802.1Q Tagging:** The standard protocol used for trunking. It inserts a 4-byte tag into the Ethernet frame header, containing a specific VLAN ID (VID) that tells the receiving switch which VLAN the frame belongs to.
**Linux Configuration:** Use `ip link` and `vlan` devices. You create a virtual interface (e.g., `eth0.10`, `eth0.20`, `eth0.30`) for each VLAN ID, bind it to the physical NIC (`eth0`), and then assign IP addresses and routes to each virtual interface.

OP6 — **RAID Types:**
*   **RAID 1 (Mirroring):** Duplicates data across two or more drives. High read performance, 50% capacity loss. Fault tolerance: 1 drive.
*   **RAID 5 (Striping with Parity):** Stripes data and parity across drives. Good balance. Fault tolerance: 1 drive.
*   **RAID 6 (Striping with Dual Parity):** Stripes data and two independent parity blocks. Higher fault tolerance. Fault tolerance: 2 drives.
*   **RAID 10 (Mirroring + Striping):** Stripes data across mirrored pairs. Excellent performance and fault tolerance. Capacity loss: 50%.
*   **RAID Z2 (ZFS):** Similar to RAID 6, using multiple parity blocks across a pool.
**Choice for Database Server (6 drives):** **RAID 10**. While RAID 6 offers better capacity utilization, RAID 10 provides superior, predictable I/O performance (crucial for databases) and excellent fault tolerance, as the failure of one drive in a mirrored pair does not impact the other mirror.

OP7 — **DNS Architecture:**
*   **Internal AD:** Uses internal DNS servers configured as authoritative for internal zones, often integrated with AD.
*   **Recursive Resolvers:** Internal DNS servers that query external/authoritative servers on behalf of clients.
*   **Forwarders:** Internal DNS servers configured to forward specific external queries to trusted public DNS providers (e.g., 8.8.8.8).
*   **Authoritative Servers:** Servers holding the actual zone files (e.g., the public-facing DMZ servers).
*   **Split-Horizon DNS:** Two different sets of records are served based on the client's location (internal vs. external).
*   **Conditional Forwarding:** Used to direct queries for specific domains (e.g., `corp.local`) to a specific internal DNS server, while others go to public forwarders.
*   **Laptop Movement:** When the laptop moves to the office, it receives the internal DNS server IP via DHCP, resolving internal names correctly. When it moves to the VPN, the VPN client routes DNS queries through the corporate DNS servers, maintaining the split-horizon resolution. DNSSEC is applied to the external zone to cryptographically verify the authenticity of public records.

OP8 — **PKI Chain of Trust:** The trust flows from the **Root CA** (the ultimate, self-signed trust anchor) down through one or more **Subordinate/Issuing CAs** to the **End-Entity Certificate** (the server/user certificate).
*   **Root CA:** Must be kept offline (air-gapped) to prevent compromise.
*   **Subordinate CA:** Used for day-to-day signing. It is signed by the Root CA.
*   **CRL (Certificate Revocation List):** A list published periodically by the CA containing serial numbers of revoked certificates.
*   **OCSP (Online Certificate Status Protocol):** A real-time query mechanism where a client asks the CA if a specific certificate is valid *right now*. OCSP is generally preferred for faster revocation checks.
*   **Certificate Templates:** Define the rules (e.g., key length, allowed usage, validity period) for different types of certificates (e.g., Web Server vs. Client).
*   **Auto-Enrollment:** Automated process where clients request and receive certificates from the Issuing CA without manual intervention.
**Consequences:**
*   **Compromised Subordinate CA:** Allows an attacker to issue fraudulent certificates for internal services, but the Root CA remains secure, allowing the organization to revoke the subordinate CA and issue a new one.
*   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, its compromise allows an attacker to issue *any* valid certificate, rendering the entire internal PKI untrustworthy.

OP9 — **Hub-and-Spoke WAN Consolidation:**
*   **MPLS:** High reliability, guaranteed QoS, excellent SLA. High cost, complex setup.
*   **IPsec VPN over Internet:** Low cost, moderate reliability (dependent on ISP), moderate latency. Security is strong if configured correctly. Management complexity is moderate.
*   **SD-WAN:** High flexibility, intelligent path selection (choosing the best link based on real-time metrics), good reliability. Moderate cost, lower management complexity than MPLS.
*   **WireGuard Mesh:** Very low overhead, high performance, simple to deploy. Reliability depends entirely on the underlying internet links.
**Recommendation:** **SD-WAN**. For a company with 50 users per site and latency-sensitive VoIP, SD-WAN provides the necessary intelligence to dynamically steer VoIP traffic over the lowest-latency path (potentially prioritizing a dedicated link or a specific ISP connection) while maintaining cost efficiency compared to MPLS, and offering better reliability than a pure IPsec mesh.

OP10 — **iDRAC/iLO/IPMI:** These are hardware management interfaces built into servers that allow administrators to monitor, manage, and control the server hardware (power cycling, remote console access, sensor monitoring) *independent* of the operating system running on the server.
**Out-of-Band Management Criticality:** It is critical because if the OS crashes, the network stack fails, or the server is powered off, you still need a way to access the machine to diagnose or recover it.
**Internet Exposure Risk:** If exposed, an attacker could gain full physical control over the server hardware (e.g., forcing reboots, accessing the console, potentially exploiting firmware vulnerabilities), bypassing all OS-level security controls.

OP11 — **LVM (Logical Volume Manager):** A software layer that abstracts physical disks into flexible logical volumes. Used for volume management and resizing partitions dynamically. Snapshot semantics are typically *crash-consistent* (captures the state at a specific moment, but data structures might be mid-write).
**LVM-Thin:** An extension of LVM that allows for thin provisioning, meaning you can allocate more logical space than you have physical space, and only consume physical space as data is written. Snapshot semantics are also crash-consistent.
**ZFS:** A complete file system and volume manager. It manages storage pools, volumes, and snapshots natively. Snapshot semantics are *transactional* (copy-on-write), meaning they are application-consistent and highly reliable.
**Usage:** Use **LVM** for simple volume resizing. Use **LVM-Thin** when you need to over-provision storage capacity. Use **ZFS** when data integrity, advanced features (checksumming, self-healing), and application-consistent snapshots are paramount.

OP12 — **Stretch Cluster/DR Strategy:** To survive a complete site failure, the cluster must span two geographically distant sites (Site A and Site B).
*   **Ceph CRUSH Rules:** Must be configured to ensure data replicas are placed across different failure domains (racks, data centers). For a stretch cluster, the CRUSH rules must be aware of the two distinct sites.
*   **Monitor Placement:** Monitors must be distributed across both sites to maintain quorum even if one site loses connectivity.
*   **Network Latency:** This is the biggest challenge. High latency (e.g., >100ms) severely impacts Ceph's internal replication and heartbeat mechanisms, potentially causing performance degradation or false failures.
*   **Split-Brain Problem:** If the network link between Site A and Site B fails, both sites might believe the other is down and attempt to take over leadership or write data simultaneously. This leads to data divergence. **2-site Ceph is generally bad without a tiebreaker** because without a third, independent witness (a tiebreaker quorum node), the two sites cannot agree on the cluster state, leading to split-brain.

OP13 — **DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses and other network configuration parameters (subnet mask, gateway, DNS) to devices on a network.
**DORA Process:**
1. **Discover:** Client broadcasts a DHCP Discover message looking for a server.
2. **Offer:** Server replies with a DHCP Offer, proposing an IP address and lease terms.
3. **Request:** Client broadcasts a DHCP Request, formally accepting the offered IP address.
4. **Acknowledge:** Server replies with a DHCP ACK, finalizing the lease assignment.
**Server Unavailable:** If the server is unavailable and the lease expires, the client will attempt to renew the lease (using DHCP Request) before it expires. If renewal fails, the client will eventually stop using the old IP address and attempt to re-discover a new server, potentially failing to connect to the network until a server becomes available.

OP14 — **Unmanaged Switch:** A plug-and-play device that operates at Layer 2. It learns MAC addresses and forwards frames based on those addresses without any configuration options. It is simple and inexpensive.
**Managed Switch:** A configurable device that allows administrators to control network traffic flow, security, and performance.
**Enterprise Features:** VLAN segmentation (isolating traffic), Quality of Service (QoS) prioritization (ensuring VoIP packets get priority), Port Mirroring (for monitoring/troubleshooting), and Link Aggregation (LAG/LACP) for increased bandwidth and redundancy.

OP15 — **NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.
**Criticality:** Accurate time is vital for distributed systems because many operations rely on timestamps for ordering, logging, and security.
**Consequences of Clock Drift:**
1. **Log Inconsistencies:** Logs from different servers cannot be reliably correlated to reconstruct an event timeline.
2. **Security Failures:** Kerberos authentication and certificate validation rely heavily on synchronized time; drift causes authentication failures.
3. **Data Corruption:** In clustered databases or distributed transactions, time-based ordering can lead to incorrect state transitions or data corruption.

OP16 — **Physical Server:** A dedicated, tangible piece of hardware running an operating system directly on the metal.
**Virtual Machine (VM):** An emulation of a complete computer system, running on a hypervisor. It includes its own virtual hardware and guest OS.
**Container:** A lightweight, isolated process environment that shares the host OS kernel. It only packages the application and its dependencies, not a full OS.
**Bare Metal Use Case:** Running workloads directly on bare metal is chosen when absolute, maximum performance is required, or when the workload has extremely low latency requirements that the virtualization layer (hypervisor overhead) cannot tolerate (e.g., high-frequency trading, specialized hardware acceleration).

OP17 — **UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power when utility power fails, bridging the gap until a generator starts or the system can safely shut down.
**Generator:** Provides long-term, sustained power during extended utility outages.
**Why both:** The UPS handles the immediate, instantaneous transition (milliseconds) required to prevent data loss or hardware damage during the switchover, while the generator provides the necessary power for hours or days.
**ATS (Automatic Transfer Switch):** A device that monitors the utility power source. When utility power fails, the ATS automatically switches the load from the utility source to the generator source (or UPS source), ensuring seamless power delivery.

OP18 — **Active-Passive Clustering:** One node (Active) handles all workload, while the other node (Passive/Standby) remains idle, constantly monitoring the active node. If the active node fails, the passive node takes over the workload.
**Active-Active Clustering:** Both nodes actively handle portions of the workload simultaneously. This provides higher resource utilization but requires complex mechanisms (like distributed locking) to prevent data corruption.
**PostgreSQL HA Implementation (Pacemaker/Corosync):**
1. **Corosync:** Provides the cluster communication and membership service.
2. **Pacemaker:** The resource manager that monitors the state of the PostgreSQL service.
3. **Fencing (STONITH):** Crucial. If the cluster suspects a node is "stuck" (split-brain), STONITH forces that node offline (e.g., via IPMI) to ensure only one node can write to the database.
4. **Virtual IPs (VIPs):** A single, floating IP address is assigned to the PostgreSQL service. Pacemaker ensures this VIP is only active on the node currently running the database.
5. **Failover:** If the active node fails, Pacemaker detects the failure (via Corosync), executes STONITH on the failed node, and then starts the PostgreSQL service on the passive node, moving the VIP to the new active node.

OP19 — **3-2-1 Rule:** Maintain **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.
**RPO (Recovery Point Objective):** The maximum acceptable amount of data loss measured in time (e.g., 1 hour). Dictates backup frequency.
**RTO (Recovery Time Objective):** The maximum acceptable downtime measured in time (e.g., 4 hours). Dictates recovery speed and infrastructure readiness.
**Backup Types:**
*   **Full:** Copies all selected data. Slowest, largest.
*   **Incremental:** Copies only data that has changed since the *last* backup of any type. Fastest, smallest.
*   **Differential:** Copies all data that has changed since the *last full* backup. Faster than full, but grows larger than incremental.
**Deduplication:** Reduces storage footprint by identifying and storing only unique data blocks, saving space.
**Offsite Storage:** Tape (air-gapped, slow recovery), Disk (faster recovery, requires offsite hardware), Cloud (scalable, geographically dispersed).
**Immutable Backups:** Backups that cannot be modified or deleted for a set period, protecting them from ransomware encryption/deletion.
**Testing Restores:** The most critical step. Regularly performing full, end-to-end test restores to validate RTO/RPO assumptions and ensure data integrity.
**Backup vs. DR:** **Backup** is the process of creating copies of data. **Disaster Recovery (DR)** is the comprehensive plan and process of restoring the *entire business operation* (including applications, network, and data) following a catastrophic event.

OP20 — **802.1X (Port-Based NAC):** A standard that controls which devices can connect to a wired network port.
*   **Supplicant:** The client device (e.g., laptop) requesting network access.
*   **Authenticator:** The network switch/access point that enforces the policy and mediates the connection.
*   **Authentication Server:** The central authority (usually RADIUS) that verifies the supplicant's credentials.
*   **EAP Methods:** **EAP-TLS** uses digital certificates for mutual authentication (strongest). **PEAP** encapsulates authentication within a TLS tunnel, often using username/password (less strong but common).
*   **RADIUS:** The protocol used by the Authenticator to communicate authentication requests and responses to the Authentication Server.
*   **Dynamic VLAN Assignment:** Upon successful authentication, the RADIUS server instructs the switch (Authenticator) to place the supplicant into a specific, authorized VLAN.
*   **Failure:** If authentication fails, the switch places the port into an unauthorized state (e.g., a restricted VLAN with no access, or shuts the port down entirely).
**MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., printers, IP phones). The switch sends the device's MAC address to the RADIUS server, which checks a pre-approved list of MAC addresses to grant access without a full EAP exchange.
