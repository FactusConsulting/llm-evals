K1 — A **Deployment** manages stateless applications, ensuring a specified number of identical replicas are running and handling updates via rolling replacements. A **StatefulSet** manages stateful applications, providing stable, unique network identifiers and persistent storage guarantees for each pod (e.g., databases).

K2 — A ClusterIP assigns a stable, internal virtual IP address to the Service. When traffic hits this IP, `kube-proxy` (running on every node) intercepts the traffic and uses iptables or IPVS rules to load balance requests across the healthy backend Pods associated with that Service.

K3 — **PersistentVolume (PV)** is a piece of storage in the cluster provisioned by an administrator or dynamically. It is the actual storage resource. **PersistentVolumeClaim (PVC)** is a request for storage made by a user/application, specifying required size and access mode. **StorageClass** is a class of storage that defines *how* the PV should be dynamically provisioned (e.g., using AWS EBS or NFS). The PVC binds to a PV that matches its requirements, often using a StorageClass to automate the PV creation.

K4 — 1. **Check Pod Events:** Use `kubectl describe pod <name>` to look for specific failure reasons (e.g., ImagePullBackOff, CrashLoopBackOff reason). 2. **Check Logs:** Use `kubectl logs <pod-name>` to see the application-level error that caused the crash. 3. **Check Resource Limits:** Verify the pod's resource requests/limits in the YAML to ensure it isn't being killed by OOMKilled or CPU throttling. 4. **Check Image/Config:** Ensure the container image exists, is accessible, and the configuration files (ConfigMaps/Secrets) are correctly mounted.

K5 — CoreDNS acts as the cluster's internal DNS service, translating Kubernetes Service names (e.g., `my-service.my-namespace.svc.cluster.local`) into the cluster's internal ClusterIPs. If CoreDNS pods are down, internal DNS resolution fails entirely; pods cannot find other services by name, leading to application connectivity failures within the cluster.

K6 — The scheduler uses a two-phase process:
1. **Filtering (Predicates):** It first filters out nodes that *cannot* run the pod based on hard constraints (e.g., resource availability, node selector matching, taints/tolerations).
2. **Scoring (Priorities):** From the remaining viable nodes, it scores them based on soft preferences.
Specific factors considered include:
*   **Resource Utilization:** Preferring nodes that are less utilized to balance load.
*   **Node Affinity/Anti-Affinity:** Respecting rules to keep pods together or spread them out.
*   **Least Requested Priority:** Preferring nodes that have the fewest resources already requested.

K7 — **Scheduling:** Yes, the pod *will* be scheduled, provided the node has enough *available* capacity after accounting for the 3.5GB already requested. The scheduler only checks against *requests*, not limits. **Runtime Behavior:** If the pod uses 600Mi, it will exceed its limit (512Mi). The Kubelet will enforce the limit, and the container runtime will terminate the process, resulting in the pod being restarted (likely leading to CrashLoopBackOff).

K8 — 1. **External LB:** The external load balancer receives the request and forwards it to the Ingress Controller node(s). 2. **Ingress Controller:** The controller (e.g., NGINX) receives the request, inspects the host/path rules defined in the Ingress resource, and determines the target Service. 3. **Service:** The Service acts as a stable abstraction layer, routing the traffic internally to the correct set of Pods. 4. **Endpoints:** The Service consults the Endpoints object, which maintains a list of the actual IP addresses of the healthy Pods backing the Service. 5. **kube-proxy/iptables:** `kube-proxy` programs iptables rules on the node. When the traffic hits the Service IP, iptables redirects it to one of the healthy Pod IPs, completing the path to the application.

K9 — A **NetworkPolicy** defines rules about which pods are allowed to communicate with which other pods (ingress) or external endpoints (egress). If no NetworkPolicy exists in a namespace, the default behavior is **allow-all** (all traffic is permitted). When a policy is applied, the default behavior effectively changes to **default-deny** for the traffic types specified in the policy, meaning only traffic explicitly allowed by the policy will pass.

K10 — **RollingUpdate:** Updates gradually replace old pods with new ones, maintaining service availability and zero downtime. It defines parameters like `maxSurge` (how many extra pods can be created) and `maxUnavailable` (how many old pods can be down). **Recreate:** Terminates all existing pods before creating the new version. This results in downtime proportional to the time it takes to spin up the new pods. You would choose **Recreate** only when the application cannot handle traffic during a transition period, or if the update requires a complete, clean state reset.

K11 — A **namespace** is a mechanism for partitioning cluster resources across multiple virtual clusters within a single physical cluster. It provides scope isolation for names, resources, and policies. Default namespaces include `default` (for general workloads), `kube-system` (for cluster components like DNS and scheduler), and `kube-public` (for publicly accessible resources).

K12 — `kubectl describe pod <name>` provides detailed metadata and status information that `kubectl get pod` omits. It shows: 1. **Events:** A chronological log of actions taken on the pod (e.g., scheduling, pulling image, failing health checks). 2. **Container Status Details:** Specific exit codes, restart counts, and detailed state transitions for each container. 3. **Resource Requests/Limits:** The exact resource allocation defined for the pod.

K13 — A **ConfigMap** is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) in key-value pairs. A pod can consume it in two primary ways: 1. **As Environment Variables:** Injecting keys/values directly into the container's environment. 2. **As Mounted Volumes:** Mounting the ConfigMap as a file system volume inside the container, allowing the application to read configuration files.

K14 — **ClusterIP:** Exposes the Service internally within the cluster using a stable virtual IP. Only reachable from within the cluster. **NodePort:** Exposes the Service on a specific port on *every* Node's IP address. This allows external access without an external load balancer, but the port must be manually chosen. **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes traffic to the Service's nodes, providing a stable, external IP address.

K15 — A **DaemonSet** ensures that a copy of a specific pod runs on *every* (or a selected subset of) nodes in the cluster. You use it when you need a system-level agent or service running locally on every machine, such as a log collector (Fluentd), a node monitoring agent, or a network plugin.

K16 — **Taints** are properties applied to a Node that repel pods. A pod must have a matching **Toleration** to be scheduled onto a tainted node. **Node Affinity** is a scheduling preference that *attracts* or *repels* pods based on node labels, but it does not prevent scheduling. **Use Case:** Taint: Dedicating a node to GPU workloads by tainting it and requiring GPU pods to tolerate that taint. Affinity: Ensuring a database pod is scheduled only on nodes labeled `disk-type: ssd`.

K17 — A **Kubernetes Operator** is a method of packaging, deploying, and managing a complex application. It extends the Kubernetes API by defining custom resources (CRDs) and implementing a control loop that watches the state of that custom resource. It differs from a standard controller because it encapsulates deep, domain-specific operational knowledge (e.g., database backups, failover procedures) that a generic controller cannot handle. It solves the problem of automating complex, human-driven operational tasks.

K18 — Kubernetes uses **etcd**, which relies on the **Raft consensus algorithm**. Raft ensures that all nodes agree on the state of the cluster (the desired state). If the etcd quorum (majority, e.g., 2 out of 3) is lost, the cluster cannot achieve consensus, and the control plane becomes unavailable, leading to scheduling failures and inability to update state. If 2 out of 3 nodes are permanently lost, the cluster loses its quorum and cannot function until a replacement node is added and bootstrapped to restore the majority.

K19 — **RBAC (Role-Based Access Control)** defines permissions based on roles. A **Role** defines a set of permissions (verbs on resources) within a specific namespace. A **ClusterRole** defines permissions across the entire cluster. A **RoleBinding** links a user/group to a Role within a specific namespace. A **ClusterRoleBinding** links a user/group to a ClusterRole cluster-wide.
*RBAC Manifests for Read-Only Pod/Logs in one namespace:*
```yaml
# 1. Define the permissions (Role)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# 2. Bind the permissions to a user/group (RoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-only-binding
  namespace: my-namespace
subjects:
- kind: User
  name: developer-user # Replace with actual user/group
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — **ndots** specifies the number of DNS dots in a domain name that the pod's resolver should treat as the root of the search path. If `ndots` is too low (e.g., 1), and the pod queries an external domain like `api.example.com`, the resolver might incorrectly assume the query is for a subdomain of the cluster's internal domain (e.g., `api.example.com.svc.cluster.local`), leading to excessive, unnecessary recursive queries against the cluster's internal DNS servers. To fix this, you use `dnsConfig` in the pod spec, setting `options` to explicitly define the search domain or setting `ndots` to a higher value (e.g., 5) to force the resolver to treat the query as fully qualified.

D1 — **git merge** integrates changes by creating a new "merge commit" that combines the histories of two branches. **git rebase** rewrites history by moving or combining a sequence of commits to a new base commit, resulting in a cleaner, linear history. You should avoid rebasing commits that have already been pushed to a shared, public repository, as rewriting shared history causes significant synchronization problems for collaborators.

D2 — **TCP (Transmission Control Protocol)** is connection-oriented, reliable, and guarantees ordered delivery through acknowledgments and retransmissions. Protocols: HTTP/1.1, FTP. **UDP (User Datagram Protocol)** is connectionless, unreliable, and faster because it sends packets without establishing a formal connection. Protocols: DNS, VoIP.

D3 — A race condition occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data. **Example:** Two threads simultaneously try to increment a shared counter variable initialized to 0. Thread A reads 0. Thread B reads 0. Thread A calculates 1 and writes 1. Thread B calculates 1 and writes 1. The expected result is 2, but the actual result is 1 because the operations overlapped.

D4 — **Symmetric encryption** uses a single, shared secret key for both encryption and decryption (e.g., AES). **Asymmetric encryption** uses a pair of mathematically linked keys: a public key (for encryption, shared widely) and a private key (for decryption, kept secret). In **TLS**, asymmetric encryption (like RSA or ECC) is used during the initial handshake to securely exchange a temporary, random **symmetric session key**. This session key is then used for the high-speed, bulk encryption of all subsequent data transfer.

D5 — A container image layer is a read-only, immutable filesystem layer that stores the changes made during a specific instruction in the Dockerfile. **Layer caching** allows Docker to reuse previously built layers if the instruction and its context haven't changed. This is a best practice because placing instructions that change frequently (like `COPY . .`) *after* instructions that change rarely (like `FROM` or installing OS packages) maximizes cache hits, drastically speeding up build times.

D6 — 1. **Check Application Logs:** Look for specific exceptions, timeouts, or high error rates in the application logs. 2. **Check Dependencies:** Verify the health and latency of external services (databases, caches, microservices) the API relies on. 3. **Check Resource Utilization:** Monitor CPU/Memory usage of the API pods; intermittent 503s often indicate throttling or resource exhaustion. 4. **Check Service Mesh/Load Balancer:** Inspect the ingress/service logs to see if the traffic is reaching the pods or if the load balancer is failing health checks.

D7 — The **CAP Theorem** states that a distributed data store can only guarantee two out of three properties simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest data), and **Partition Tolerance** (the system continues to operate despite network failures between nodes).
*   **CP System (Consistency over Availability):** Systems like traditional relational databases (e.g., PostgreSQL cluster) prioritize data correctness. If a network partition occurs, the system may refuse requests to the minority side to prevent inconsistent writes.
*   **AP System (Availability over Consistency):** Systems like Cassandra prioritize uptime. If a partition occurs, nodes continue accepting writes, leading to temporary data divergence that must be resolved later.

D8 — **Horizontal Scaling (Scaling Out):** Increasing the number of instances (replicas) of an application to handle more load. This is achieved by adding more machines/pods. **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) allocated to an *existing* instance. Architectural patterns enabling horizontal scaling include **Stateless Design** (ensuring no session data is tied to a single instance) and **Load Balancing**.

D9 — An **environment variable** is a dynamic named value that can affect the way running processes will behave on a computer. On Linux, to set a variable that persists across shell sessions, you must add the export command (e.g., `export MY_VAR="value"`) to your shell configuration file, such as `~/.bashrc` or `~/.zshrc`, and then source the file (`source ~/.bashrc`).

D10 — **JSON (JavaScript Object Notation)** uses key-value pairs and is strictly defined by braces `{}` and brackets `[]`. **YAML (YAML Ain't Markup Language)** uses indentation and hyphens `-` to denote structure. **JSON Advantage:** Universally supported by nearly all programming languages and is very strict/easy to parse programmatically. **YAML Advantage:** Highly human-readable due to its reliance on whitespace indentation, making it ideal for configuration files.

D11 — A **REST API (Representational State Transfer)** is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources identified by URLs.
*   **GET:** Retrieves a representation of a resource (Read).
*   **POST:** Submits data to a specified resource, often creating a new resource (Create).
*   **PUT:** Replaces all current representations of the target resource with the request payload (Update/Replace).
*   **DELETE:** Removes the specified resource (Delete).

D12 — **Version pinning** is the practice of explicitly locking a dependency to a specific, immutable version number (e.g., `library@1.2.3` instead of `library@latest`). It is crucial for reproducible builds because it guarantees that the build environment will always use the exact same code, preventing unexpected runtime failures caused by upstream library authors making breaking changes in newer, unpinned versions.

D13 — A **compiled language** is translated entirely into machine code (or bytecode) by a compiler *before* execution. Examples: C++, Go. An **interpreted language** is executed line-by-line by an interpreter program *during* runtime. Examples: Python, JavaScript.

D14 — A **reverse proxy** sits in front of one or more web servers and forwards client requests to them. It acts on behalf of the server, hiding the internal structure. A **forward proxy** sits in front of a client and forwards requests on behalf of the client to the internet.
*   **Nginx (Reverse Proxy):** Use case: Load balancing traffic across multiple application servers.
*   **HAProxy (Reverse Proxy):** Use case: High-availability traffic distribution and sophisticated health checking.

D15 — A **deadlock** is a situation where two or more competing actions are each waiting for the other to finish, resulting in a permanent standstill. The four necessary conditions (Coffman conditions) are: 1. **Mutual Exclusion:** At least one resource must be held in a non-sharable mode. 2. **Hold and Wait:** A process holds at least one resource while waiting to acquire additional resources held by other processes. 3. **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily. 4. **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

D16 — **Eventual consistency** is a consistency model where, if no new updates are made to a given data item, all reads will eventually return the last updated value. It prioritizes availability over immediate consistency. Cassandra handles read-after-write consistency by using **Quorum**. When writing, the system requires a write quorum ($W$) of replicas to acknowledge the write. When reading, it requires a read quorum ($R$). If $W + R > N$ (where $N$ is the total number of replicas), the system guarantees that the read operation will overlap with at least one node that received the latest write, ensuring strong consistency for that specific read/write pair.

D17 — **mTLS (mutual TLS)** is a security protocol where *both* the client and the server authenticate each other using digital certificates during the TLS handshake. Unlike standard TLS (where only the server proves its identity to the client), mTLS requires the client to present a valid certificate signed by a trusted Certificate Authority (CA) recognized by the server. The full handshake involves: 1. Client Hello. 2. Server sends certificate and requests client certificate. 3. Client sends certificate and proves possession of the private key (signing a challenge). 4. Server verifies client certificate. 5. Server sends its certificate. 6. Client verifies server certificate. 7. Secure session established. It is commonly used in service meshes (like Istio) for securing east-west traffic between microservices.

D18 — A **hash table** maps keys to values using a hash function that converts the key into an index (hash code) in an array. **Collision resolution** handles when two different keys map to the same index.
*   **Chaining:** Each array slot points to a linked list (or dynamic array) containing all elements that hash to that index.
*   **Open Addressing:** If a slot is full, the algorithm probes for the next available slot in the array (e.g., linear probing, quadratic probing).
*   **Time Complexity:** Average Case: Insertion, Lookup, Deletion are $O(1)$. Worst Case: If all keys collide into one bucket (or the table is poorly sized), complexity degrades to $O(n)$.

D19 — The **circuit breaker pattern** is a design pattern used in microservices to detect failures in a remote service and prevent an application from repeatedly trying to execute an operation that is likely to fail. It prevents cascading failures.
*   **Closed:** Normal operation. Requests pass through to the service. If failures exceed a threshold, the breaker trips to Open.
*   **Open:** Requests are immediately rejected by the breaker without attempting to call the failing service, allowing the downstream service time to recover.
*   **Half-Open:** After a timeout in the Open state, the breaker allows a small number of test requests through. If these succeed, the breaker closes; if they fail, it returns to Open.
It relates to **retry policies** by preventing aggressive retries during a failure storm, which would overwhelm the struggling service. **Exponential backoff** is used to increase the delay between retries, giving the service more time to recover.

D20 — **Pessimistic Concurrency Control** assumes conflicts are likely. It prevents conflicts by acquiring locks on data *before* accessing it. If a transaction needs to update a row, it locks that row immediately, preventing any other transaction from reading or writing it until the lock is released. **Example:** Using `SELECT FOR UPDATE` in SQL. **Optimistic Concurrency Control** assumes conflicts are rare. Transactions proceed without locks, but before committing, they check if the data they read has been modified by another transaction. If it has, the transaction fails and must be retried. **Example:** Using version numbers or timestamps on a row; the update query includes a `WHERE version = [original_version]`. You choose **Pessimistic** for high-contention data (e.g., inventory counts) and **Optimistic** for low-contention data (e.g., user profile updates).
