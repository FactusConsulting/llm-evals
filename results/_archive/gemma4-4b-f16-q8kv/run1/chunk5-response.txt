**G1**
A Go **array** has a fixed size defined at compile time (e.g., `[5]int`). A **slice** is a dynamically sized, flexible view into an underlying array. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array, copies the existing elements and the new element(s) into it, and updates the slice header to point to the new array.

**G2**
`var x int` declares a variable `x` and initializes it to its zero value (which is `0` for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when redeclaring a variable within the same scope, or when assigning a value to an already declared variable (e.g., `x = 5` is correct, but `x := 5` would cause a compile error).

**G3**
A **goroutine** is a lightweight, independently executing function managed by the Go runtime. It is much cheaper than an OS thread because it requires very little stack space (starting small, growing as needed). The **Go scheduler (GMP model)** maps goroutines (G) onto OS threads (M) using a pool of logical processors (P). The scheduler efficiently multiplexes many goroutines onto a smaller number of OS threads, allowing Go programs to handle massive concurrency with low overhead.

**G4**
Channels are typed conduits through which you can send and receive values between goroutines, enabling safe communication.
*   **Unbuffered Channel:** Requires both the sender and receiver to be ready simultaneously for the communication to proceed (synchronous rendezvous).
*   **Buffered Channel:** Has a fixed capacity. Sending blocks only when the buffer is full; receiving blocks only when the buffer is empty.
When sending to a full buffered channel, the sending goroutine blocks until another goroutine receives a value, freeing up space in the buffer.

**G5**
The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. This is crucial for managing the lifecycle of concurrent operations.
Example:
```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"
)

func main() {
	// Create a context that automatically cancels after 2 seconds
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel() // Always call cancel to release resources

	req, _ := http.NewRequestWithContext(ctx, "GET", "http://slowapi.com/data", nil)
	
	// The HTTP client respects the context timeout
	client := http.Client{}
	resp, err := client.Do(req)
	
	if err != nil {
		fmt.Println("Request failed or timed out:", err)
	} else {
		resp.Body.Close()
		fmt.Println("Request succeeded.")
	}
}
```

**G6**
Go's interface satisfaction is **implicit** (structural typing). A type satisfies an interface simply by implementing all the methods defined in that interface; there is no explicit `implements` keyword. This differs from Java/C# where interfaces must be explicitly declared.
The empty interface `interface{}` (or `any` in Go 1.18+) can hold a value of *any* type. It is powerful because it allows for maximum flexibility (e.g., generic functions that accept anything). It is dangerous because using it requires **type assertion** or **type switching** to access the underlying data, which can lead to runtime panics if the assertion is incorrect.

**G7**
This code is unsafe due to a **data race**. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading `ready` and then `data`. Go's memory model guarantees that writes are visible to other goroutines *only* if synchronization primitives (like channels or mutexes) are used. The compiler/runtime does not guarantee that the write to `data` happens *before* the write to `ready` is visible, or that the main goroutine sees the updated `data` after seeing `ready = true`.
**Correct Alternatives:**
1.  **Channels:** Send a signal on a channel when done, and receive it in the main goroutine.
2.  **Mutex:** Protect both `data` and `ready` with a `sync.Mutex`.

**G8**
*   **`sync.Mutex`:** Provides exclusive locking. Only one goroutine can hold the lock at a time (read or write).
*   **`sync.RWMutex`:** Allows multiple readers to access the data concurrently (`RLock`), but requires exclusive access for writers (`Lock`).
**`sync.Map` vs. Map + Mutex:**
*   **Map + Mutex:** Generally faster for high-contention scenarios where writes are frequent, as the mutex overhead is predictable.
*   **`sync.Map`:** Optimized for scenarios where keys are written once and read many times (read-heavy workloads), as it avoids locking the entire map structure for every read operation.
**Trade-offs:** `sync.Map` has higher overhead for writes compared to a standard map protected by a mutex.

**G9**
**Go Modules** are Go's dependency management system. They define the project's dependencies and version constraints.
*   **`go.mod`:** Lists the module path and the required dependencies along with their version constraints (e.g., `require github.com/pkg/errors v0.9.1`).
*   **`go.sum`:** Contains cryptographic checksums for the exact versions of the dependencies listed in `go.mod`. This ensures that the downloaded code has not been tampered with.
**`go mod tidy`** cleans up the `go.mod` and `go.sum` files by adding any missing required dependencies and removing any dependencies that are no longer used in the source code.
**MVS (Minimum Version Selection):** It is an algorithm used to select the highest possible version of a dependency that still satisfies all version constraints specified in the `go.mod` file, ensuring compatibility while allowing for the latest features.

**G10**
A `defer` statement schedules a function call to be executed just before the surrounding function returns.
**Execution Order:** Defers are executed in **Last-In, First-Out (LIFO)** order.
**Gotcha in a Loop:** If a `defer` statement captures a loop variable by reference (i.e., it captures the variable itself, not its value at the time of deferral), all deferred functions will execute using the *final* value of that loop variable after the loop completes.

**G11**
A **pointer** in Go is a variable that stores the memory address of another variable.
The zero value of a pointer is `nil`, meaning it points to no valid memory address.
To create a pointer to a struct literal:
```go
type Point struct { X, Y int }
p := Point{X: 10, Y: 20}
ptr := &p // The '&' operator takes the address of p
```

**G12**
The `init()` function is a special function that runs automatically before the `main` function (or before any other code in the package) is executed. It is used for package-level initialization tasks, such as setting up global variables or registering drivers.
A package **can** have multiple `init()` functions. They execute sequentially, in the order they appear in the source code files.

**G13**
*   **`make`:** Used to initialize and return a value of a **reference type** (slice, map, or channel). It allocates the underlying data structure. Example: `make([]int, 5)` or `make(map[string]int)`.
*   **`new`:** Used to allocate memory for a value of any type and return a pointer to the zero value of that type. It does *not* initialize the structure itself. Example: `new(int)` returns a pointer to an integer initialized to `0`.

**G14**
Error handling in Go is explicit and relies on returning an `error` type as the last return value from functions that might fail. The `error` interface is a built-in interface with a single method: `Error() string`.
The idiomatic pattern is: `if err != nil { return err }`.
*   **`errors.Is(err, target)`:** Checks if the error chain contains a specific sentinel error value (e.g., checking if an error is specifically `io.EOF`).
*   **`errors.As(err, &target)`:** Checks if the error chain contains a value that matches a specific type, allowing you to extract structured error information into a variable (`target`).
*   **`==`:** Only checks for exact pointer equality, which is rarely useful for checking error types or specific conditions.

**G15**
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be written to until initialized with `make`).
*   **Slice:** `[]Type`. Zero value: `nil` (a slice header pointing to a nil underlying array).
*   **Channel:** `chan Type`. Zero value: `nil` (a channel header pointing to no underlying channel).
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values (e.g., `0` for integers, `""` for strings).

**G16**
A **race condition** occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization mechanism to order the accesses. The outcome depends on the unpredictable timing of the scheduler.
The **`-race` flag** instruments the Go runtime to detect these data races during execution, printing warnings when concurrent, unsynchronized memory access is detected.
**Example Fix (Mutex):**
```go
var data int
var mu sync.Mutex

func increment() {
    mu.Lock()
    data++ // Protected access
    mu.Unlock()
}
```

**G17**
The `select` statement allows a goroutine to wait on multiple communication operations (channel receives or sends) simultaneously. It is Go's concurrency equivalent of `switch` for channels.
When multiple cases are ready, `select` chooses one **randomly** to ensure fairness among competing channels.
To implement a timeout, you use a `time.After` channel:
```go
select {
case msg := <-ch1:
    // Handle message from ch1
case <-time.After(5 * time.Second):
    // Timeout occurred
    fmt.Println("Operation timed out")
}
```

**G18**
**Escape analysis** is a compiler optimization that determines whether a variable's data should be allocated on the **stack** or the **heap**.
*   **Stack Allocation:** Fast, automatic cleanup when the function returns. Used for local variables whose lifetime is strictly confined to the function call.
*   **Heap Allocation:** Slower, requires garbage collection. Used for variables whose lifetime extends beyond the function call (e.g., if they are returned from the function or stored in a global/long-lived structure).
The compiler decides based on the variable's usage and scope. You can inspect this using the `-gcflags="-m"` flag. It matters because heap allocation introduces GC overhead, while stack allocation is extremely fast.

**G19**
The `reflect` package allows a program to inspect and manipulate its own structure (types, values, methods) at runtime.
*   **`reflect.Type`:** Represents the *type* information of a value (e.g., `int`, `*MyStruct`). It is immutable.
*   **`reflect.Value`:** Represents the *actual value* of a variable at runtime. It can be modified.
**Performance Costs:** Reflection is significantly slower than static code because the compiler cannot optimize the access paths; the runtime must perform dynamic lookups.
**Justification:** Reflection is justified when writing generic frameworks, serialization libraries, or tools that must operate on arbitrary, unknown types at runtime. For standard application logic, it should be avoided in favor of static generics or code generation.

**G20**
The `go:embed` directive allows embedding files or directories directly into a Go binary as assets. This is useful for bundling static resources (like configuration files, templates, or images) without needing external file system access at runtime.
*   **Single Files/Directories:** You specify the path, and the compiler embeds the content into a variable of type `embed.FS`.
*   **File Systems:** It creates an `embed.FS` interface, which implements `fs.FS`, allowing you to treat the embedded content as a virtual file system.
**Limitations:** It only works for static assets known at compile time.
**Interaction with `io/fs.FS`:** The `go:embed` directive produces a variable that satisfies the `fs.FS` interface, allowing standard library functions designed to read from an `fs.FS` (like `http.FileServer`) to seamlessly read the embedded assets.

**R1**
**Ownership** is Rust's core memory management concept. It dictates that every value in Rust has a single variable that is its *owner*. When the owner goes out of scope, the value is automatically dropped (memory is freed).
The three rules are:
1.  Each value in Rust has a variable that’s called its owner.
2.  There can only be one owner at a time.
3.  When the owner goes out of scope, the value is dropped.

**R2**
*   **`String`:** A heap-allocated, growable, owned, UTF-8 encoded string type. It owns its data. Use it when you need to modify or own the string data.
*   **`&str`:** A string slice; a borrowed, immutable view into string data (which might be stored in the binary or on the heap). Use it in function signatures when you only need to read the string data without taking ownership or modifying it.

**R3**
**Borrowing** allows you to refer to a value without taking ownership of it. The **borrow checker** enforces Rust's rules to guarantee memory safety at compile time.
*   **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously. You can have many readers.
*   **Mutable Reference (`&mut T`):** Allows exactly one mutable reference to the data at any given time. This prevents data races by ensuring exclusive write access.
The core rule is: You can have *either* one mutable reference *or* any number of immutable references, but not both simultaneously.

**R4**
*   **`Option<T>`:** An enum representing the presence or absence of a value. It is either `Some(T)` (contains a value) or `None` (contains no value). It is Rust's idiomatic replacement for `null`.
*   **`Result<T, E>`:** An enum representing the outcome of an operation. It is either `Ok(T)` (success, containing a value of type T) or `Err(E)` (failure, containing an error of type E).
The **`?` operator** is syntactic sugar for propagating errors. If the expression on the left of `?` is `Ok(T)`, it unwraps the value `T`. If it is `Err(E)`, it immediately returns the error `E` from the current function.
Example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> io::Result<String> {
    let mut file = File::open(path)?; // Propagates error if file cannot be opened
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates error if reading fails
    Ok(contents)
}
```

**R5**
These smart pointers manage heap allocation and reference counting:
*   **`Box<T>`:** A smart pointer that allocates data on the heap. It is used for single ownership (like a traditional pointer) and is the simplest heap allocation mechanism.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data on the heap. It keeps a count; the data is dropped only when the last `Rc` pointing to it is dropped. Used for single-threaded shared ownership.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>`, but its reference counting operations are atomic, making it safe to share ownership across multiple threads.

**R6**
**Traits** define shared behavior (a set of methods) that types can implement. They are Rust's mechanism for polymorphism.
**Comparison to Go Interfaces:** Traits are more powerful than Go interfaces because they can define *default implementations* for methods, and they can be used to constrain generics. Go interfaces are purely structural contracts.
*   **Trait Object (`dyn Trait`):** A dynamically dispatched trait object. It holds a pointer to data and a pointer to the V-table, allowing you to treat different types that implement the trait uniformly at runtime (similar to an interface in Go).
*   **Generic with Trait Bound (`T: Trait`):** A statically dispatched generic. The compiler generates specialized code for every concrete type used, resulting in zero runtime overhead (monomorphization).

The returned reference must live as long as the *shortest* lifetime of the input references (`x` or `y`). If the function returns a reference to `x`, but `x` goes out of scope when `longest` returns, the reference becomes a dangling pointer.

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {

}
```

**R8**
*   **`Send`:** A marker trait indicating that a type can be safely *sent* (transferred ownership) across thread boundaries.
*   **`Sync`:** A marker trait indicating that a type can be safely *shared* between threads (i.e., it is safe to have multiple immutable references to it across threads).
You cannot send an `Rc<T>` across threads because its internal reference counter is not atomic, leading to race conditions during counting. **`Arc<T>`** is safe for concurrent use because its reference counting mechanism uses atomic operations, ensuring that the count is updated safely even when multiple threads are simultaneously dropping or cloning the pointer.

**R9**
Rust's `async/await` is built on the concept of **Futures**. A `Future` is a trait representing a value that *might* be available at some point in the future. It is essentially a state machine that knows how to poll itself until it completes.
The **executor** (like Tokio or async-std) is the runtime environment. It takes a `Future` and repeatedly "polls" it. If the future is not ready, the executor suspends it and moves on to poll other ready futures, only resuming the suspended future when the necessary I/O or event occurs.
**Difference from Goroutines:** Goroutines are managed by a runtime scheduler that multiplexes lightweight threads onto OS threads. Rust Futures are *cooperative* multitasking; the task must explicitly yield control (by returning `Poll::Pending`) for the executor to switch context.

**R10**
`unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. This is necessary when interacting with low-level hardware, FFI (Foreign Function Interface), or implementing highly optimized data structures.
Three things you can do in `unsafe`:
1.  Dereference a raw pointer (`*const T` or `*mut T`).
2.  Call an `unsafe` function or intrinsic.
3.  Access or modify a mutable static variable.
Unsafe code is justified only when the programmer can *prove* mathematically or logically that the operation maintains memory safety invariants, usually for performance or interoperability reasons.

**R11**
**Pattern matching** uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches.
`if let` is syntactic sugar used for matching a single, specific pattern and immediately executing a block if it matches, otherwise ignoring it.
The compiler enforces **exhaustiveness** in `match` statements. This means you must provide a pattern (usually `_` or a specific variant) that covers *every possible variant* of the enum or type being matched, preventing runtime errors due to unhandled cases.

**R12**
*   **`Vec<T>`:** A dynamically sized, heap-allocated, growable collection. It manages its own memory, automatically reallocating and copying data when capacity is exceeded.
*   **Array `[T; N]`:** A fixed-size collection allocated on the stack (if small enough) or inline. Its size `N` is known at compile time and cannot change.
When `Vec<T>` is pushed beyond capacity, it typically allocates a new underlying array, usually doubling its capacity, copies all existing elements to the new location, and then deallocates the old array.

**R13**
**Enums** in Rust are powerful algebraic data types that can hold different types of data depending on which variant they are in. Unlike C/Java enums (which are often just integer constants), Rust enums can be complex structures.
**`Option<T>`** is an enum with two variants: `Some(T)` and `None`. Rust avoids `null` because `null` is an ambiguous concept in memory management; `Option<T>` forces the programmer to explicitly handle the "no value" case at compile time, eliminating null pointer dereferences.

**R14**
An **`impl` block** is used to define methods and associated functions for a specific type.
*   **`&self`:** Takes an immutable reference to the instance. Used for methods that only read the data (e.g., `my_string.len()`).
*   **`&mut self`:** Takes a mutable reference. Used for methods that need to change the instance's state (e.g., `my_string.push_str(...)`).
*   **`self`:** Takes ownership of the instance. Used when the method consumes the instance (e.g., `my_string.into_bytes()`).
**Associated Functions:** Functions defined within an `impl` block that do not take `self` as an argument (e.g., `String::new()`). They are called using the type name, not an instance.

**R15**
A **derive macro** is a procedural macro that automatically implements standard traits for a struct or enum based on its definition.
Commonly derived traits:
*   `Debug`: Allows printing the value using `{:?}`.
*   `Clone`: Allows creating deep copies of the value.
*   `PartialEq`/`Eq`: Allows comparison using `==` and `!=`.
*   `Serialize`/`Deserialize`: Used by serialization libraries (like Serde).
You cannot derive a trait if the type does not meet the trait's requirements. For example, you cannot derive `Eq` if you have not also derived `PartialEq`, as `Eq` requires total equality.

**R16**
**`Cow<'a, T>` (Clone On Write)** is a smart type that can hold either an owned value (`T`) or a borrowed reference (`&'a T`).
It is useful when you frequently receive data that you might need to modify, but most of the time you only need to read it.
**Example:** If a function receives a string slice (`&str`) but sometimes needs to modify it, using `Cow<'_, str>` allows the function to operate on the borrowed slice most of the time (zero allocation). Only when a modification is actually required does it perform a copy (the "write" part), converting the `Cow` into an owned `String`.

**R17**
Rust's module system organizes code into hierarchical units.
*   **`mod`:** Declares a module, which can contain items or other modules.
*   **`use`:** Brings items (functions, structs) from a module into the current scope, allowing you to refer to them without the full path.
*   **`pub`:** Makes an item publicly accessible outside of its defining module.
The file system maps to modules: a file named `foo.rs` typically defines the `foo` module.
The major change between Rust 2015 and 2018 was the introduction of **path-based modules** (allowing modules to be defined by directory structure, not just by `.rs` files), leading to a more flexible and scalable module organization.

**R18**
**`Pin<T>`** is a wrapper type used to guarantee that a value `T` will not be moved in memory after it has been pinned.
It is needed because certain types, particularly those involved in asynchronous operations (like `Future`s), must maintain a stable memory location throughout their execution. If a `Future` were moved, its internal state (which might hold pointers to itself or other data) would become invalid.
**`Unpin`** is a marker trait. If a type implements `Unpin`, it means it is safe to move it in memory. If it does *not* implement `Unpin`, it must be wrapped in `Pin` to prevent movement.

**R19**
Rust's macro system allows code generation at compile time.
*   **Declarative Macros (`macro_rules!`):** These are pattern-matching macros. They operate by matching input tokens against defined patterns and then substituting those patterns with predefined code blocks. They are simpler and operate on token streams.
*   **Procedural Macros (derive, attribute, function-like):** These are more powerful. They are actual Rust code that runs during compilation.
    *   *Derive:* Automatically implements traits (e.g., `#[derive(Debug)]`).
    *   *Attribute:* Modifies the syntax of an item (e.g., `#[tokio::main]`).
    *   *Function-like:* Act like regular functions but operate on tokens (e.g., `vec![]`).
**Hygiene Rules:** These rules prevent macro expansion from accidentally capturing or interfering with local variables or identifiers defined within the scope where the macro is used, ensuring that the generated code is contextually correct.

**R20**
**Zero-cost abstractions** mean that high-level language features (like generics or iterators) compile down to machine code that is as fast as if the programmer had written the equivalent low-level C code manually, without incurring runtime performance penalties.
*   **Generics (Monomorphization):** When you use a generic type `T`, the compiler generates a specific, concrete version of the code for every type `T` used (e.g., one version for `i32`, one for `String`). This avoids the need for runtime type checking or dynamic dispatch overhead.
*   **Iterators:** Rust iterators are implemented as traits. When used, they are often optimized via monomorphization, allowing the compiler to inline the loop logic directly, resulting in highly efficient, loop-like code without the overhead of virtual function calls.
*   **Trait Static Dispatch:** When a trait method is called on a generic type, the compiler knows the exact concrete type at compile time and calls the specific implementation directly, avoiding the runtime lookup cost associated with dynamic dispatch (like `dyn Trait`).
