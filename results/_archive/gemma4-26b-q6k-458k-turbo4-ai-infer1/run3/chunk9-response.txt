## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the transition from `Baseline` to `Restricted` Pod Security Standard (PSS) enforces stricter requirements on the `securityContext`. While `runAsNonRoot: true` is present, the `Restricted` policy requires that a non-zero `runAsUser` be explicitly defined in the pod or container spec to prevent the container from defaulting to `root`. Since the new Chainguard base image defaults to `USER root` and the manifest lacks an explicit `runAsUser`, Kubernetes attempts to run the container as root, which violates the `Restricted` policy, causing the container to fail to start.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[]?.state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}''
```

**SC1-C:**
*   **Image-level:** Explicitly set `USER 1000` (or any non-zero UID) in the Dockerfile.
*   **Manifest:** Add `securityContext: { runAsNonRoot: true, runAsUser: 1000 }` to the Deployment spec.
*   **CI Pipeline:** Add a `conftest` or `kyverno` step to scan manifests for missing `runAsUser` and a container image scanner to flag images defaulting to `root`.
*   **Rollout:** Perform a `kubectl rollout restart deployment/<name>` to trigger a rolling update. Since the fix is in the manifest/image, the new pods will satisfy the `Restricted` policy, ensuring zero downtime.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data occurs because RDS cross-region replication is **asynchronous**. When the replica is promoted, any WAL (Write Ahead Log) records that were in transit from `us-east-1` to `eu-west-1` but not yet applied are lost or delayed. This creates a "replication lag" window. To quantify the data loss, I would check the `pg_last_xact_replay_timestamp()` on the new primary and compare it to the last known transaction time from the old primary.

**SC2-B:**
1.  **Remove from state:** `tofu state rm aws_db_instance.old_instance` (assuming the resource name).
2.  **Import new instance:** `tofu import aws_db_instance.new_primary <new-rds-arn>`.
3.  **Update Code:** Update the ARN in the Terraform files to point to the new instance.
4.  **Apply:** `tofu apply` to update dependent Security Groups, Route53 records, and Parameter Groups to point to the new ARN.

**SC2-C:**
*   **Architecture:** Use **Amazon Aurora Global Database**. It uses storage-level replication which is significantly faster and has lower RPO than standard RDS asynchronous replication.
*   **Connection Management:** Use **RDS Proxy** instead of PgBouncer for better integration with AWS IAM and automated failover handling.
*   **Failover:** Implement **Route53 Health Checks** with a CNAME record pointing to the Aurora cluster endpoint to automate DNS failover.
*   **Application:** Implement exponential backoff and circuit breaking in the application code.
*   **RPO < 1s:** Aurora Global Database is the only way to reliably achieve this across regions via storage-level replication.

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Local Sessions:** Problem: K8s pods are ephemeral. Solution: Move sessions to **Redis**.
2.  **Local NFS (/data/uploads):** Problem: Pods need shared access to files. Solution: Use a **CSI driver for NFS** with `ReadWriteMany` access.
3.  **Oracle/IBM MQ:** Problem: Hardcoded on-prem IPs. Solution: Use **Kubernetes Services/ExternalName** or an Egress Gateway.
4.  **Bare-metal Performance:** Problem: Java monoliths need specific tuning. Solution: Define strict **Resource Requests/Limits** and use **Guaranteed QoS class**.
5.  **Sticky Sessions:** Problem: F5 logic doesn't exist in K8s. Solution: Use **Ingress Controller (Nginx/ALB)** with session affinity enabled.

**SC4-B:**
```hcl
resource "kubernetes_storage_class" "nfs_csi" {
  metadata { name = "nfs-csi" }
  storage_provisioner = "nfs.csi.k8s.io"
  reclaim_policy     = "Retain"
}

resource "kubernetes_persistent_volume" "nfs_pv" {
  metadata { name = "nfs-pv" }
  spec {
    capacity = { storage = "100Gi" }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source {
      nfs {
        server = var.nfs_server_address
        path   = var.nfs_export_path
      }
    }
  }
}

resource "kubernetes_persistent_volume_claim" "nfs_pvc" {
  metadata { name = "nfs-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    storage_class = "nfs-csi"
    resources { requests = { storage = var.storage_capacity } }
  }
}
```
*Note: `ReadWriteMany` is necessary because multiple replicas of the monolith must simultaneously read/write to the same upload directory.*

**SC4-C:**
*   **Phase 1:** Move the frontend/API layer to K8s (Stateless). Traffic split via F5 (Weight-based).
*   **Phase 2:** Move the session management to Redis.
*   **Phase 3:** Move the data/MQ integration.
*   **Rollback:** If a phase fails, update F5 weights back to 100% legacy.
*   **Metrics:** Error rates (5xx), Latency (p99), and DB connection pool saturation.

## SC5 — Mysterious Latency Spike in Microservices

**SC5-A:**
*   **Approach:** Check Istio `istio_request_duration_milliseconds` for the `checkout-service`.
*   **Tracing:** Use **Jaeger** to see if the span for `inventory-service` is long. If the span starts at the proxy and ends at the app, it's the app.
*   **Envoy Metrics:** Check `upstream_rq_pending_overflow` (queueing) vs `upstream_rq_time` (actual service processing).

**SC5-B:**
**SQL:**
```sql
SELECT pid, now() - query_start AS duration, query, state, wait_event, wait_event_type
FROM pg_stat_activity
WHERE state != 'idle' AND wait_event IS NOT NULL;
-- To find blockers:
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid,
       blocked_activity.query AS blocked_query, blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_locks.pid = blocked_activity.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid
WHERE NOT blocked_locks.granted;
```
**Go (Circuit Breaker):**
```go
var cb = gobreaker.NewCircuitBreaker(gobreaker.Settings{Name: "inventory-service"})
// ... inside call function

    return client.Get(inventoryURL)

```

**SC5-C:**
*   **CQRS:** Separate the reconciliation (Write) from the checkout (Read).
*   **Read Replica:** Run the CronJob against a read-only replica.
*   **Bulkhead:** Use separate connection pools for the reconciliation job and the API.
*   **K8s:** Use **Resource Quotas** to limit the CronJob's CPU/Mem and **PDBs** to ensure the `inventory-service` always has minimum available pods.

## SC6 — Zero-Trust Network Overhaul

**SC6-A:**
Use **SPIFFE/SPIRE** to issue short-lived SVIDs (X.509 certificates) to every workload. For AWS, use **IAM Roles for Service Accounts (IRSA)**. For Azure, use **Managed Identities**. Federate these using **OIDC** so an AWS workload can present its SPIFFE ID to an on-prem service, which validates it against a trusted Root CA via a shared trust bundle.

**SC6-B:**
```hcl
resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }

resource "aws_ec2_transit_gateway" "tgw" {}

resource "aws_vpc_endpoint" "endpoints" {
  for_each = toset(["s3", "ecr.api", "rds"])
  vpc_id     = aws_vpc.main.id
  service_name = "${each.key}.amazonaws.com"
  vpc_endpoint_type = "Interface"
}

resource "aws_security_group" "default_deny" {
  vpc_id = aws_vpc.main.id
  egress {
    from_port = 0
    to_port = 0
    protocol = "-1"
    cidr_blocks = ["0.0.0.0/0"] # Default deny is handled by lack of ingress rules
  }
}
```

**SC6-C:**
*   **Direct Connect:** Best for performance/predictability, highest cost.
*   **Second VPN + ECMP:** Best for cost/bandwidth, complex routing.
*   **Tailscale/Netbird:** Best for ease of use/Zero-Trust, adds overlay latency.
*   **Recommendation:** For a large enterprise, **Direct Connect** is preferred for the backbone, supplemented by a mesh (Tailscale) for developer/remote access.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
1.  **Manual Apply:** Bypasses GitOps, creating "shadow" infrastructure.
2.  **Divergent Helm Values:** Makes deployments non-deterministic.
3.  **kubectl edit:** Creates drift between the live state and the source of truth.
**No State Locking:** If two engineers run `apply` simultaneously, the state file can be corrupted, leading to partial resource creation or accidental destruction of critical resources.

**SC7-B:**
```yaml
stages: [fmt, validate, plan, apply]

job_fmt:
  stage: fmt
  script: [tofu fmt -check]

job_plan:
  stage: plan
  script: [tofu plan -out=tfplan]
  artifacts: { paths: [tfplan] }

job_apply:
  stage: apply
  script: [tofu apply tfplan]
  when: manual
  environment: production
```
*Note: Use `backend "s3" { dynamodb_table = "tofu-lock" }` for locking.*

**SC7-C:**
*   **Drift Detection:** Schedule a GitLab CI job to run `tofu plan` every hour and alert on non-empty diffs.
*   **Block kubectl edit:** Use **Kyverno** to deny `UPDATE` requests on ConfigMaps/Secrets unless the user is the `system:serviceaccount:cicd:tofu-runner`.
*   **Structure:** Use **Kustomize** to define a `base/` and `overlays/prod/` to manage environment-specific values.
*   **RBAC:** AWS IAM: CI Service Account has `AdministratorAccess`; Humans have `ReadOnlyAccess`. K8s: Humans have `view` role; CI has `cluster-admin`.

## SC8 — Observability Stack Scaling Failure

**SC8-A:**
1.  **Prometheus OOM:** High cardinality/churn. Check `prometheus_tsdb_head_series`.
2.  **Loki Drops:** Ingester saturation. Check `loki_ingester_bytes_received_total`.
3.  **Tempo Timeouts:** Query complexity/S3 latency. Check `tempo_query_duration_seconds`.
4.  **Thanos Lag:** Compactor resource starvation. Check `thanos_compactor_compaction_duration_seconds`.
**High Cardinality:** Too many unique label combinations. Identify via `topk(10, count by (__name__) ({__name__!=""}))`.

**SC8-B:**
```bash
#!/bin/bash
echo -e "Metric_Name\t\tSeries_Count"
echo -e "------------------------------------"
# Get top 20 metrics by series count
curl -s "http://prometheus:9090/api/v1/query?query=count({__name__!=\"\"}) by (__name__)" | \
jq -r '.data.result[] | "\(.metric.__name__)\t\(.value[0])"' | sort -rnk2 | head -n 20
```

**SC8-C:**
*   **Architecture:** Use **Mimir** (horizontal scaling of Prometheus).
*   **Loki:** Deploy in **Microservices mode** (separate ingesters, queriers, distributors).
*   **Tempo:** Use S3 as the primary backend for all blocks.
*   **Governance:** Implement **Relabeling** to drop high-cardinality labels (e.g., `user_id`) and use **Recording Rules** to pre-calculate expensive queries.
*   **Chargeback:** Use Mimir/Prometheus labels to track usage per `team_id` and export to a billing dashboard.

## SC9 — Securing a Public-Facing API After a Breach

**SC9-A:**
1.  **BOLA:** (OWASP API1). Fix: Implement object-level permission checks in Django (e.g., `PermissionClass`).
2.  **Data Leakage:** (OWASP API3). Fix: Use **Serializers** to explicitly define allowed fields.
3.  **No Rate Limit:** (OWASP API4). Fix: Implement **AWS WAF** or middleware rate limiting.
4.  **API Key in URL:** (OWASP API2). Fix: Move keys to `Authorization: Bearer <key>` header.

**SC9-B:**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {
  name = "api-waf"
  default_action { allow {} }
  rule {
    name = "RateLimit"
    priority = 1
    action { block {} }
    statement {
      rate_based_statement {
        limit = 100
        aggregate_key_type = "IP"
      }
    }
  }
  rule {
    name = "BlockKeysInQuery"
    priority = 2
    action { block {} }
    statement {
      query_string_match_statement {
        search_string = "api_key="
      }
    }
  }
}
```

**SC9-C:**
*   **Auth:** Move to **OAuth2/OIDC** with JWTs.
*   **Gateway:** Place **AWS API Gateway** in front of the ALB for centralized rate-limiting and auth.
*   **Auditing:** Enable **CloudTrail Data Events** for S3/Lambda/API access.
*   **Encryption:** Use **Field-level encryption** (AES-256) for PII before it hits the DB.
*   **Migration:** Issue new JWTs; allow both API keys and JWTs for a 30-day grace period, then deprecate keys.

## SC10 — Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Architecture:** **Active-Passive** with Velero is safer for data integrity. Active-Active with Cilium Cluster Mesh is better for latency but harder to manage for stateful consistency.
*   **RPO/RTO:** 12ms latency is fine for async replication. 200TB MinIO requires **MinIO Site Replication** (asynchronous) to meet RPO.
*   **Replication:**
    *   **Postgres:** Patroni with synchronous replication (if RPO allows) or async.
    *   **Redis:** Redis Sentinel with cross-site replication.
    *   **RabbitMQ:** Federation/Shovel.
    *   **MinIO:** Site-to-site bucket replication.

**SC10-B:**
```yaml
- name: configure_patroni
  hosts: db_servers
  tasks:
    - name: template_patroni_config
      template:
        src: patroni.yml.j2
        dest: /etc/patroni/patroni.yml
      notify: restart_patroni
    - name: ensure_patroni_running
      service:
        name: patroni
        state: started
```

**SC10-C:**
1.  **Detection:** Monitor site health via external probes (Route53/GSLB).
2.  **Failover Sequence:**
    *   Detect Chicago down $\rightarrow$ Trigger DNS update (GSLB) $\rightarrow$ Patroni promotes Dallas $\rightarrow$ Redis Sentinel promotes $\rightarrow$ RabbitMQ Federation redirects $\rightarrow$ MinIO sync resumes.
3.  **Split-Brain:** Use a **Quorum-based DCS (etcd)** to ensure only one site can be "Primary."
4.  **Failback:** Re-provision Chicago as a standby, sync data, then flip DNS back.
