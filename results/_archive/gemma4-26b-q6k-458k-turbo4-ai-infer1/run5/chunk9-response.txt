## SC1
**SC1-A:** The pods are failing because of a conflict between the Kubernetes Pod Security Standard (PSS) and the container image configuration. Under the **Restricted** PSS, `runAsNonRoot: true` requires that the container must not run as UID 0 (root). While the manifest specifies `runAsNonRoot: true`, the new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root` (UID 0) in its metadata. Since no explicit `runAsUser` was provided in the `securityContext`, Kubernetes attempts to run the container as the image's default user (root), which violates the Restricted policy. In the **Baseline** profile, this was allowed because it didn't strictly enforce the non-root requirement unless explicitly requested, but the upgrade to Restricted turned this into a hard enforcement.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}''
```

**SC1-C:**
*   **Image-level fix:** Update the Dockerfile to include `USER 10001` (or any non-zero UID) to ensure the image metadata complies with non-root requirements.
*   **Manifest changes:** Explicitly set `securityContext.runAsUser: 10001` and `securityContext.runAsGroup: 10001` in all deployment manifests.
*   **CI Pipeline Gate:** Implement a step using `container-diff` or `trivy` to inspect image metadata and fail the build if the `User` field is `0` or if the image lacks a non-root user definition.
*   **Rollout:** Perform a Rolling Update (`kubectl rollout restart`) to replace old pods with the fixed images/manifests, ensuring `maxUnavailable: 0` to maintain availability.

## SC2
**SC2-A:** The stale data is caused by **asynchronous replication lag**. In standard RDS cross-region setups, replication is asynchronous; the primary commits the transaction locally before the WAL (Write Ahead Log) is shipped and applied to the replica. If the primary fails, any WAL segments not yet received by the replica represent data loss (RPO > 0). To quantify the window, I would check `pg_stat_replication` on the primary (before failure) or check the `last_wal_receive_location` vs `last_wal_replay_location` on the promoted replica.

**SC2-B:**
1.  **Remove from state:** `tofu state rm aws_db_instance.primary_db` (to prevent TF from trying to delete the old instance).
2.  **Update Code:** Update the ARN in the Terraform variables/resources to point to the new promoted instance's ARN.
3.  **Import:** `tofu import aws_db_instance.primary_db <new_instance_identifier>`.
4.  **Sync Dependencies:** Run `tofu apply` to update Security Groups, Route53, and Parameter Groups to point to the new ARN.

**SC2-C:**
*   **Architecture:** Use **Amazon Aurora Global Database**. It uses storage-level replication with latency typically < 1 second, providing much lower RPO than standard RDS.
*   **Connection Management:** Use **RDS Proxy** instead of PgBouncer for better integration with AWS IAM and faster failover/connection pooling during transitions.
*   **DNS:** Use **Route53 CNAME records** with health checks that point to a secondary record, allowing automated DNS failover.
*   **App Logic:** Implement exponential backoff and jitter in the application's connection logic.
*   **RPO < 1s:** Aurora Global Database is the only standard RDS option that achieves this via physical storage replication rather than logical/streaming WAL shipping.

## SC4
**SC4-A:**
1.  **Sticky Sessions:** K8s is ephemeral; local memory sessions fail on pod restart. *Solution:* Move sessions to Redis.
2.  **Local NFS:** K8s pods are transient; `/data/uploads` won't persist. *Solution:* Use a CSI driver (EFS/Azure Files) with `ReadWriteMany`.
3.  **Oracle 19c:** Hard to run Oracle in a container. *Solution:* Keep it external or use an Oracle Operator.
4.  **IBM MQ:** Legacy protocols often struggle with K8s networking/service mesh. *Solution:* Use a sidecar proxy to handle MQ connectivity.
5.  **Monolith Size:** Large Java apps have slow startup/high memory. *Solution:* Set strict `requests/limits` and use `startupProbes`.

**SC4-C:**
*   **Phase 1:** Deploy a "Proxy" layer. Use the F5 to route 5% of traffic to a K8s-based "Edge" service that handles auth/routing but calls the legacy monolith via internal network.
*   **Phase 2:** Extract the "Upload" and "Session" services. Move them to K8s using Redis/S3.
*   **Phase 3:** Move the core logic.
*   **Cutover:** Use the F5 to shift traffic weight from the legacy IP to the K8s Ingress.
*   **IBM MQ:** Use a dedicated "Integration Service" in K8s that acts as a bridge.
*   **Metrics:** Error rates (5xx), Latency (p99), and DB connection counts.

## SC6
**SC6-A:**
*   **Identity:** Use **SPIFFE/SPIRE** to issue short-lived SVIDs (X.509 certs) to every workload.
*   **Federation:** Use **OIDC Federation**. AWS IAM Roles for Service Accounts (IRSA) allows K8s pods to assume AWS roles. For on-prem, use an **OIDC provider** that bridges the on-prem PKI with AWS/Azure. SPIRE can federate identities by trusting the OIDC issuer of the other environment.

**SC6-C:**
*   **Direct Connect:** High cost, highest bandwidth, lowest latency, best for predictable heavy traffic.
*   **Second VPN + ECMP:** Cheaper, provides redundancy, but limited by VPN overhead/latency.
*   **Hybrid Mesh (Tailscale):** Easiest to manage, uses WireGuard, works over any internet connection, fits Zero-Trust perfectly via identity-based routing.
*   **Recommendation:** For a Zero-Trust mandate, a **Hybrid Mesh** is superior as it abstracts the network layer into an identity layer.
