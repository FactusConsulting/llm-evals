## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A**
The pods are failing because the cluster's transition from **Baseline** to **Restricted** Pod Security Standards (PSS) enforces stricter security constraints. Specifically, the Restricted profile requires that containers do not run as root. While the pods have `securityContext.runAsNonRoot: true`, they lack an explicit `runAsUser` ID. Because the new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root` (UID 0), the Kubelet attempts to start the container as root. The Restricted PSS detects this violation and prevents the container from starting, resulting in `CrashLoopBackOff`. In the Baseline profile, this was permitted, but Restricted requires a non-zero UID to be explicitly defined in the `securityContext`.

**SC1-B**
```bash
kubectl get pods -A -o json | jq -c '.items[] | select(.status.containerStatuses[].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C**
*   **Image-level fix:** Update the Dockerfile to include `USER 1000` (or any non-zero UID) to ensure the image is non-root by default.
*   **Manifest changes:** Explicitly set `runAsUser: 1000` and `runAsGroup: 3000` in the `securityContext` of the Deployment manifest.
*   **CI Pipeline Gate:** Implement a `hadolint` check in the CI pipeline to catch `USER root` instructions and a `trivy` or `kube-linter` scan to verify `securityContext` compliance before the image is pushed.
*   **Rollout:** Perform a `kubectl rollout restart deployment/<name>` using a `RollingUpdate` strategy to replace pods one-by-one, ensuring availability.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A**
The stale data is caused by **asynchronous replication lag**. In standard RDS cross-region replication, WAL (Write Ahead Log) records are shipped from the primary to the replica asynchronously to avoid penalizing primary write latency. When the replica is promoted, any WAL records that were in flight but not yet applied to the replica are lost, creating a "data gap." To quantify this, I would check the `ReplicaLag` metric in CloudWatch or run `SELECT now() - pg_last_xact_replay_timestamp();` on the promoted instance to see the timestamp of the last applied transaction.

**SC2-B**
1.  **Identify:** Use `terraform state list` to find the old instance and the new promoted instance.
2.  **Remove old state:** `terraform state rm aws_db_instance.old_primary`.
3.  **Import new instance:** `terraform import aws_db_instance.new_primary <new-db-instance-id>`.
4.  **Update Code:** Update the HCL to point to the new ARN/Identifier.
5.  **Dependency Update:** Update all `aws_db_instance` references in Security Groups and Route53.
6.  **Apply:** Run `terraform apply` to reconcile the state without recreation (since the resource is now "managed" by the new ID).

**SC2-C**
*   **Architecture:** Use **Amazon Aurora Global Database**. It uses storage-level replication which is significantly faster than RDS asynchronous WAL shipping, offering RPO of < 1 second.
*   **Connection Management:** Use **RDS Proxy** to handle connection pooling and provide a single endpoint that can be re-routed during failover, reducing application-side connection errors.
*   **DNS:** Use **Route53 Failover Routing policies** with health checks pointing to the regional endpoints.
*   **App Logic:** Implement exponential backoff and jitter in the application's connection retry logic.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A**
1.  **Sticky Sessions:** K8s LoadBalancers are typically round-robin. **Solution:** Use an Ingress controller with session affinity or move sessions to a distributed cache like Redis.
2.  **Local NFS Writes:** K8s pods are ephemeral. **Solution:** Use a CSI driver for the existing NFS or migrate to AWS EFS/Azure Files.
3.  **Oracle/Mainframe Connectivity:** Network latency/firewalls. **Solution:** Use a dedicated VPC/Subnet with high-speed interconnects (Direct Connect) and ensure K8s egress allows the specific ports.
4.  **Local Memory Sessions:** Pod restarts wipe data. **Solution:** Externalize state to a managed DB/Cache.
5.  **IBM MQ Integration:** Monolith expects a persistent connection. **Solution:** Use a Sidecar pattern or a dedicated MQ Bridge service.

**SC4-B**
```hcl
variable "nfs_server" { type = string }
variable "nfs_path" { type = string }
variable "storage_capacity" { type = string }

resource "kubernetes_storage_class" "nfs_csi" {
  metadata { name = "nfs-sc" }
  provisioner = "nfs.csi.k8s.io"
  parameters = {
    server = var.nfs_server
    share  = var.nfs_path
  }
}

resource "kubernetes_persistent_volume" "legacy_pv" {
  metadata { name = "legacy-pv" }
  spec {
    capacity = { storage = var.storage_capacity }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source {
      nfs {
        server = var.nfs_server
        path  = var.nfs_path
      }
    }
  }
}

resource "kubernetes_persistent_volume_claim" "legacy_pvc" {
  metadata { name = "legacy-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    resources { requests = { storage = var.storage_capacity } }
    storage_class = "nfs-sc"
  }
}
```
*Note: `ReadWriteMany` (RWX) is necessary because multiple pods (replicas) of the monolith need to access the same `/data/uploads` directory simultaneously.*

**SC4-C**
1.  **Phase 1 (Proxy):** Deploy the app to K8s but keep the DB/MQ on-prem. Use F5 to route 5% of traffic to K8s Ingress.
2.  **Phase 2 (Data Migration):** Move files to EFS/NFS-CSI. Use a data sync tool for the Oracle DB.
3.  **Phase 3 (Full Cutover):** Move MQ integration to K8s-native services.
*   **Rollback:** If latency > threshold, update F5 weight to 0% for K8s.
*   **Metrics:** Error rate, p99 latency, and DB connection count.

## SC6 — Hard — Zero-Trust Network Overhaul

**SC6-A**
Use **SPIFFE/SPIRE** to issue short-lived SVIDs (X.509 certificates) to every workload. Federate identities by using an **OIDC provider** (like AWS IAM or Azure AD) as the root of trust. A workload in AWS can present its IAM role to a SPIRE server, which validates it and issues a certificate that the on-prem service trusts via a shared Root CA.

**SC6-B**
```hcl
resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }

resource "aws_transit_gateway" "tgw" { }

resource "aws_vpc_endpoint" "endpoints" {
  for_each = toset(["s3", "ecr.api", "rds"])
  service_name       = "${each.key}.amazonaws.com"
  vpc_id             = aws_vpc.main.id
  vpc_endpoint_type   = "Interface"
}

resource "aws_security_group" "zero_trust_sg" {
  vpc_id = aws_vpc.main.id
  ingress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = [] # Default Deny
  }
}
```

**SC6-C**
*   **Direct Connect:** Best for performance/predictability; highest cost.
*   **VPN + ECMP:** Cheaper; uses multiple tunnels to increase bandwidth via Equal-Cost Multi-Path routing.
*   **Hybrid Mesh (Tailscale):** Easiest to manage; uses Wireguard; creates a flat overlay network.
*   **Recommendation:** For Zero-Trust, a **Hybrid Mesh** is superior as it provides identity-based encryption (mTLS) at the application layer regardless of the underlying transport.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A**
*   **Manual Apply:** Causes "State Drift." If two engineers run `apply` simultaneously, the state file can become corrupted or partially updated (Race Condition).
*   **Diverged Values:** Leads to "Configuration Drift," where the environment doesn't match the source of truth.
*   **kubectl edit:** Causes "Runtime Drift," where the live state is different from Git, making the next `tofu apply` unpredictable.

**SC7-B**
```yaml
stages: [validate, plan, apply]

validate:
  stage: validate
  script:
    - tofu fmt -check
    - tofu validate

plan:
  stage: plan
  script:
    - tofu plan -out=tfplan
    - echo "Plan generated"
  artifacts:
    paths: [tfplan]

apply:
  stage: apply
  script:
    - tofu apply tfplan
  when: manual
  environment: production
```
*Note: Use a DynamoDB table in the `backend` configuration for state locking.*

**SC7-C**
*   **Detection:** Run a scheduled GitLab job that executes `tofu plan -detailed-exitcode`. If it returns `2` (drift detected), alert the team.
*   **Prevention:** Use **OPA Gatekeeper** to reject `kubectl edit` requests that don't match a specific schema.
*   **Structure:** Use **Kustomize** to have a `base/` directory and `overlays/prod/` for environment-specific overrides.
*   **RBAC:** In AWS, remove `AdministratorAccess` from users and grant `AdministratorAccess` only to the CI/CD Service Account.

## SC9 — Securing a Public-Facing API After a Breach

**SC9-A**
1.  **BOLA:** (OWASP API1) - Unauthorized access to objects. **Fix:** Implement object-level permission checks.
2.  **Excessive Data Exposure:** (OWASP API3) - Returning internal fields. **Fix:** Use Serializers/DTOs to filter fields.
3.  **No Rate Limiting:** (OWASP API4) - DoS/Scraping. **Fix:** Implement WAF/Gateway rate limits.
4.  **API Keys in URL:** (OWASP API2) - Sensitive data in logs. **Fix:** Move keys to `Authorization` headers.

```python
from rest_framework import permissions

class IsOwnerOrReadOnly(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:
            return True
        return obj.owner == request.user
```

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A**
*   **Architecture:** **Active-Passive with Velero** is safer for the 200TB MinIO data (using MinIO Site Replication). **Active-Active with Cilium Cluster Mesh** is better for the K8s services to provide seamless traffic shifting.
*   **RPO/RTO:** 12ms latency allows for **Synchronous Replication** for PostgreSQL (Patroni) to meet RPO=0. 200TB MinIO will require asynchronous background replication to meet RTO.

**SC10-B**
```yaml
# patroni.yml snippet
scope: postgres
name: postgres-primary
etcd:
  hosts: ["etcd-chicago:2379", "etcd-dallas:2379"]
postgresql:
  parameters:
    synchronous_commit: "on"
    synchronous_standby_names: "postgres-dallas"
  replication:
    username: replicator
    password: password
```

**SC10-C**
1.  **Detection:** Use a quorum-based monitor (e.g., Patroni + etcd) to detect site failure.
2.  **Failover Sequence:** 
    *   Patroni promotes Dallas standby $\rightarrow$ 
    *   Redis Sentinel promotes Dallas replica $\rightarrow$ 
    *   RabbitMQ Federation switches to Dallas nodes $\rightarrow$ 
    *   GSLB/Route53 updates DNS to point to Dallas ALB.
3.  **Split-Brain:** Use **Fencing/STONITH** or a strict quorum (etcd) to ensure only one primary exists.
4.  **Failback:** Re-provision Chicago as a standby, sync data, then perform a controlled switchover.
