## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the **Restricted Pod Security Standard** requires that `runAsNonRoot` be `true` **AND** that a non-zero `runAsUser` be explicitly defined in the `securityContext`. While the `Baseline` standard allowed containers to run as root if they didn't explicitly violate other rules, `Restricted` enforces that the container must not run as UID 0. The new base image (`chainguard/static`) defaults to `USER root`. Since the manifest lacks `runAsUser`, Kubernetes attempts to start the container as root, which violates the `runAsNonRoot: true` policy, causing the Kubelet to reject the container start.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq '.items[] | select(.status.containerStatuses[].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level fix:** Update the Dockerfile to include `USER 1000` (or any non-zero UID) to ensure the image defaults to a non-root user.
*   **Manifest changes:** Explicitly set `securityContext.runAsUser: 1000` and `securityContext.fsGroup: 1000` in the Deployment spec.
*   **CI Pipeline Gate:** Add a `hadolint` or `trivy` scan step to the pipeline to detect `USER root` instructions in Dockerfiles.
*   **Rollout:** Perform a **Rolling Update** with `strategy: type: RollingUpdate` and `maxUnavailable: 0` to ensure new, fixed pods are healthy before old ones are terminated.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is caused by **Asynchronous Replication**. In cross-region setups, PostgreSQL uses asynchronous streaming replication to avoid the massive latency penalty of waiting for a cross-region ACK. When the primary fails, any WAL (Write Ahead Log) records that were in flight but not yet received by the `eu-west-1` replica are lost. To quantify the data loss window, I would check the `pg_stat_replication` view on the old primary (if accessible) or compare the `last_wal_receive_lsn` on the replica against the last known transaction ID from the application logs.

**SC2-B:**
1.  **Remove from state:** `tofu state rm aws_db_instance.old_primary_arn`
2.  **Update Code:** Change the hardcoded ARN in the Terraform files to the new ARN of the promoted instance.
3.  **Import:** `tofu import aws_db_instance.new_primary <new_instance_identifier>`
4.  **Apply:** `tofu apply` to reconcile security groups and Route53 records to point to the new instance.

**SC2-C:**
*   **Architecture:** Use **Amazon Aurora Global Database**. It uses storage-level replication which is significantly faster and has lower RPO than standard RDS streaming.
*   **Connection Management:** Use **RDS Proxy** to handle connection pooling and transparent failover, reducing the "login retry" errors seen in PgBouncer.
*   **Failover:** Use **Route53 Health Checks** with a CNAME record pointing to the Aurora cluster endpoint.
*   **RPO < 1s:** Aurora Global Database provides RPO < 1 second via its dedicated replication layer.
*   **Application:** Implement exponential backoff and jitter in the application's connection logic.

## SC3 — Medium — Container Image Supply Chain Compromise

**SC3-A:**
*   **Containment:** Do **not** delete the pod. Use `kubectl label` to move it to an "isolated" network policy that denies all ingress/egress.
*   **Forensics:**

    *   **Network:** `kubectl exec <pod> -- netstat -antp` or `ss -antp`.
    *   **Filesystem:** `kubectl cp` the `/tmp` directory or use `docker diff` (if on node) to see changed files.

**SC3-B:**

echo "Comparing $IMAGE against $BASE_IMAGE..."

**SC3-C:**
*   **Signing:** Use **Cosign** to sign images after the build.

*   **SBOM:** Generate a **CycloneDX** SBOM during build and attach it to the image using Cosign.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Local Sessions:** Kubernetes pods are ephemeral; local memory sessions vanish on restart. *Solution: Move sessions to Redis.*
2.  **Local NFS:** Kubernetes requires networked storage for persistence. *Solution: Use a CSI driver for NFS/EFS.*
3.  **Oracle DB:** High latency/connectivity issues in containers. *Solution: Use a dedicated Database Operator or external service.*
4.  **IBM MQ:** Legacy protocols often require specific network/security configs. *Solution: Use a Sidecar proxy or dedicated gateway.*
5.  **F5 Sticky Sessions:** K8s Ingress/Service handles load balancing differently. *Solution: Use an Ingress Controller (NGINX/Istio) with session affinity.*

**SC4-B:**
```hcl
variable "nfs_server" { type = string }
variable "nfs_path" { type = string }
variable "storage_capacity" { type = string }

resource "kubernetes_storage_class" "nfs_sc" {
  metadata { name = "nfs-client" }
  provisioner = "nfs.csi.k8s.io"
  parameters = {
    server = var.nfs_server
    share  = var.nfs_path
  }
}

resource "kubernetes_persistent_volume" "data_pv" {
  metadata { name = "monolith-pv" }
  spec {
    capacity = { storage = var.storage_capacity }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source {
      nfs {
        server = var.nfs_server
        path   = var.nfs_path
      }
    }
  }
}

resource "kubernetes_persistent_volume_claim" "data_pvc" {
  metadata { name = "monolith-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    resources { requests = { storage = var.storage_capacity } }
    storage_class = "nfs-client"
  }
}
```
*Note: `ReadWriteMany` (RWX) is necessary because multiple replicas of the monolith must access the same shared file storage simultaneously.*

**SC4-C:**
*   **Phase 1:** Deploy the app to K8s in "Shadow Mode" (traffic mirrored via F5 to K8s, but K8s responses are discarded).
*   **Phase 2:** Move stateless components (API/Web) to K8s, keeping the DB and MQ on-prem. Use the F5 to split traffic (e.g., 10% to K8s).
*   **Phase 3:** Move stateful components (NFS/DB) to K8s/Cloud.
*   **Cutover:** Update F5 to point 100% to K8s Ingress.
*   **Rollback:** Revert F5 weight to 100% legacy.
*   **Metrics:** Error rates (5xx), Latency (p99), and DB connection counts.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A:**
*   **Metrics:** Check `istio_request_duration_milliseconds_bucket` for the `checkout-service`.
*   **Tracing:** Use **Jaeger** to see if the span for `inventory-service` is the one consuming the time.
*   **Envoy Metrics:** Check `envoy_cluster_upstream_rq_time` (upstream latency) vs `envoy_cluster_upstream_cx_connect_timeout` (connection issues). If `upstream_rq_time` is high, the issue is the service; if `upstream_rq_pending_overflow` is high, it's proxy-level queueing.

**SC5-B:**
**SQL:**
```sql
SELECT pid, now() - query_start AS duration, query, wait_event, state 
FROM pg_stat_activity 
WHERE wait_event IS NOT NULL AND state = 'active';
```
**Go (Circuit Breaker):**
```go
var cb = gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name: "inventory-service",
    MaxRequests: 3,
    Interval: 5 * time.Second,
    Timeout: 30 * time.Second,
})

func CallInventory() {
    _, err := cb.Execute(func() (interface{}, error) {
        return client.GetInventory()
    })
}
```

**SC5-C:**
*   **CQRS:** Separate the `inventory-reconciliation` (Write/Heavy) from the `get-stock` (Read/Light) path.
*   **Read Replica:** Run the CronJob against a read-only replica to prevent locking the primary.
*   **Bulkhead:** Use a dedicated connection pool for the CronJob.
*   **K8s:** Use `PodDisruptionBudgets` to ensure serving pods stay up and `ResourceQuotas` to prevent the CronJob from consuming all node CPU/Mem.

## SC6 — Hard — Zero-Trust Network Overhaul

**SC6-A:**
Implement **SPIFFE/SPIRE** to issue short-lived SVIDs (identity documents) to every workload. Federate identities by using **AWS IAM Roles for Service Accounts (IRSA)** and **Azure Managed Identities**, then use an OIDC provider to allow the on-prem SPIRE server to trust AWS/Azure identity tokens.

**SC6-B:**
```hcl
resource "aws_ec2_transit_gateway" "main" { ... }

resource "aws_vpc_endpoint" "s3" {
  for_each = toset(["s3", "ecr.api", "rds"])
  vpc_id     = aws_vpc.main.id
  service_name = "${each.value}.amazonaws.com"
  vpc_endpoint_type = "Interface"
}

resource "aws_security_group" "zero_trust_sg" {
  ingress {
    from_port = 0
    to_port   = 0
    protocol  = "-1"
    # Default deny is implicit in AWS SGs, but we explicitly 
    # only allow known SPIFFE-authenticated traffic via app-level mTLS
  }
}
```

**SC6-C:**
*   **Direct Connect:** Best for predictable, high-bandwidth, low-latency. High cost.
*   **Second VPN + ECMP:** Good for redundancy, but doesn't solve the bandwidth bottleneck of a single tunnel.
*   **Hybrid Mesh (Tailscale):** Best for Zero-Trust. It creates an overlay network where every node has a stable identity, regardless of physical location.
*   **Recommendation:** Use **Direct Connect** for the backbone and **Tailscale/WireGuard** for the zero-trust overlay.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:**
*   **Manual Apply:** Causes "State Drift." The Git repo no longer represents reality.
*   **Divergent Helm:** Makes testing in Staging useless because Production is a "snowflake."
*   **kubectl edit:** Bypasses all CI/CD logic and audit trails.
*   **No Locking:** Two engineers running `tofu apply` simultaneously can cause **State Corruption**, where the state file is partially written or contains conflicting resource mappings, leading to accidental deletion of resources.

**SC7-B:**
```yaml
# .gitlab-ci.yml
stages: [validate, plan, apply]

validate:
  stage: validate
  script:
    - tofu fmt -check
    - tofu validate

plan:
  stage: plan
  script:
    - tofu plan -out=tfplan
  artifacts:
    paths: [tfplan]

apply:
  stage: apply
  script:
    - tofu apply tfplan
  when: manual
  environment: production
```
*(Note: Use `backend "s3" { dynamodb_table = "tofu-lock" }` in the config).*

**SC7-C:**
*   **Detection:** Schedule a `tofu plan` job every hour in CI; if `plan` shows changes, alert the team.
*   **Prevention:** Use **Kyverno** to block `kubectl edit` on production namespaces for all users except the CI Service Account.
*   **Structure:** Use **Helmfile** to define a `values.yaml` base and environment-specific `values-prod.yaml` overrides.
*   **RBAC:** In AWS, restrict S3/DynamoDB access to the CI IAM Role. In K8s, use RBAC to grant `edit` permissions only to the CI ServiceAccount.

## SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:**
*   **Prometheus OOM:** High cardinality (too many unique label combinations). Check `prometheus_tsdb_head_series`.
*   **Loki Drops:** Ingester is overwhelmed. Check `loki_ingester_bytes_received_total` vs `loki_ingester_dropped_lines_total`.
*   **Tempo Timeouts:** Querying too much data from S3 or unindexed labels.
*   **Thanos Lag:** Compactor cannot keep up with the ingestion rate. Check `thanos_compactor_compaction_duration_seconds`.

**SC8-B:**
```bash
#!/bin/bash
echo -e "Metric_Name\t\tSeries_Count"
echo "------------------------------------"
# Get total unique metric names
TOTAL=$(curl -s http://prometheus:9090/api/v1/label/__name__/values | jq '.data | length')
echo "Total Metrics: $TOTAL"

# Top 20 metrics (requires querying the series count)
curl -s http://prometheus:9090/api/v1/query?query='count by (__name__) ({__name__=~".+"})' | \
jq -r '.data.result[] | "\(.metric.__name__)\t\(.value[0])"' | sort -k2 -rn | head -n 20
```

**SC8-C:**
*   **Architecture:** Move to **Mimir** (for Prometheus-compatible scaling) or **VictoriaMetrics**.
*   **Loki:** Deploy in **Microservices mode** (separate `querier`, `ingester`, `distributor`).
*   **Tempo:** Use a dedicated S3 backend with heavy indexing.
*   **Governance:** Implement **Relabeling** to drop high-cardinality labels (like `user_id`) before they hit Prometheus.
*   **Chargeback:** Use Prometheus `recording_rules` to aggregate metrics per `team_id` label and export the sum to a billing dashboard.

## SC9 — Medium — Securing a Public-Facing API After a Breach

**SC9-A:**
1.  **BOLA (OWASP API1):** User accesses other's data. *Fix: Implement object-level checks.*
2.  **Excessive Data Exposure (OWASP API3):** Returning internal fields. *Fix: Use Serializers/DTOs.*
3.  **No Rate Limiting (OWASP API4):** Resource exhaustion. *Fix: WAF/API Gateway limits.*
4.  **API Keys in URL (OWASP API2):** Keys logged in plain text. *Fix: Move to Authorization Header.*

**Django BOLA Fix:**
```python
from rest_framework import permissions

class IsOwnerOrReadOnly(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.owner == request.user
```

**SC9-C:**
*   **Defense-in-Depth:** Use **OAuth2/OIDC** with JWTs.

*   **Gateway:** Place **AWS API Gateway** in front to handle centralized auth and rate-limiting.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Architecture:** **Active-Passive** is safer for RTO/RPO compliance here. Active-Active with 12ms latency and 200TB of data makes synchronous consistency nearly impossible without massive performance degradation.
*   **Replication:**
    *   **PostgreSQL:** Patroni with `synchronous_commit: on` (for RPO 0) or `remote_write` (for RPO < 15m).
    *   **Redis:** Redis Sentinel with cross-site replication.
    *   **MinIO:** Site-to-site bucket replication.

**SC10-B:**
```yaml
- name: Configure Patroni
  hosts: postgres_nodes
  tasks:
    - name: Install Patroni
      apt: name=patroni state=present
    - name: Template Patroni Config
      template:
        src: patroni.yml.j2
        dest: /etc/patroni/patroni.yml
      notify: restart patroni
  handlers:
    - name: restart patroni
      service: name=patroni state=restarted
```
*(In `patroni.yml.j2`, set `synchronous_standby_names: 'localhost, standby_node_in_dallas'`)*.

**SC10-C:**
1.  **Detection:** External health check (e.g., Route53/GSLB) monitors the Chicago endpoint.
2.  **Promotion:** Patroni detects leader loss $\rightarrow$ promotes Dallas standby $\rightarrow$ Dallas becomes Primary.
3.  **DNS:** GSLB updates to point to Dallas IP.
4.  **Stateful Sync:** MinIO and RabbitMQ catch up via asynchronous replication.
5.  **Split-Brain:** Use a **Quorum-based DCS (etcd)** across three sites (Chicago, Dallas, and a lightweight Witness in a 3rd zone) to prevent two nodes from claiming leadership.
6.  **Failback:** Re-provision Chicago as a replica of Dallas, sync data, then perform a controlled switchover.
