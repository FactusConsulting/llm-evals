## Application Architecture

**AA1** — A monolith is a single, unified deployment unit where all functions reside in one codebase. Microservices are a collection of small, independent, loosely coupled services. 
*Problems introduced by microservices:* 1. Network latency/complexity, 2. Distributed data consistency (Sagas), 3. Operational overhead (observability/deployment).

**AA2** — Synchronous: The client waits for a response before proceeding (e.g., HTTP/REST). Asynchronous: The client sends a message and continues without waiting (e.g., RabbitMQ/AMQP).

**AA3** — A reverse proxy sits in front of web servers to handle load balancing/SSL. An API Gateway is application-aware, handling routing, authentication, rate limiting, and orchestration. An API Gateway can replace a reverse proxy, but a simple reverse proxy is often more performant for basic tasks.

**AA4** — Saga manages distributed transactions via a sequence of local transactions. 
*Choreography:* Decentralized; services emit events that trigger other services. Best for simple workflows. 
*Orchestration:* Centralized; a "manager" tells each service what to do. Best for complex, multi-step workflows.

**AA5** — CQRS separates the data models for reading (Queries) from writing (Commands). It is paired with Event Sourcing (storing state as a sequence of events) to ensure the read model can be rebuilt from the event log. This solves the problem of "state loss" in traditional CRUD, providing a perfect audit log and the ability to reconstruct state at any point in time.

**AA6** — Circuit Breaker prevents a service from repeatedly trying an operation that is likely to fail. 
*States:* Closed (normal), Open (failing, stops requests), Half-Open (testing if service recovered). 
*Difference:* Retry handles transient blips; Circuit Breaker handles systemic failures. Use both: Retry for a single request, Circuit Breaker to protect the system from a failing dependency.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, lowest security (data leakage risk), highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Medium cost, medium security, medium noisy-neighbor risk.
3. **Separate DB:** Highest cost, highest security (physical isolation), lowest noisy-neighbor risk.

**AA8** — Strong consistency ensures all reads see the latest write; eventual consistency allows temporary divergence. 
*Inventory Architecture:* Use **Strong Consistency**. Use an RDBMS (Postgres) with **ACID** properties. Implement **Pessimistic Locking** or a distributed lock (Redis/Etcd) to ensure a single source of truth for stock levels during high concurrency.

**AA9** — A sidecar (Envoy) is a helper container running alongside the app. In Istio, Envoy handles the data plane (traffic), while Istio's control plane (Istiod) manages configuration. mTLS between sidecars provides identity-based encryption and authentication, which application-level TLS lacks because it doesn't provide centralized, automated certificate management and identity verification at the infrastructure layer.

**AA10** — Strangler Fig: Incrementally replace functionality. 
*Strategy:* 1. Place an API Gateway/Proxy in front of the .NET monolith. 2. Identify a bounded context (e.g., "Billing"). 3. Build "Billing" as a new .NET 8 microservice. 4. Update the Gateway to route `/billing` traffic to the new service while everything else goes to the monolith. 5. Repeat until the monolith is "strangled."

**AA11** — 1. Codebase (one repo per service), 2. Dependencies (explicitly declared), 3. Config (stored in environment), 4. Backing services (treated as attached resources), 5. Processes (stateless), 6. Disposability (fast startup/shutdown). These ensure portability and scalability in cloud environments.

**AA12** — 
*Kafka (Event):* High decoupling, massive scale, complex debugging, strict ordering within partitions, async. 
*REST (Request):* High coupling, lower scale, easy debugging, synchronous. 
*Choice:* Use Kafka for high-throughput, asynchronous background tasks; use REST/gRPC for real-time, request-response user interactions.

**AA13** — A load balancer distributes incoming traffic across multiple servers. 
*L4:* Operates at Transport layer (IP/Port). 
*L7:* Operates at Application layer (HTTP headers/URL). 
*Use case:* Path-based routing (e.g., `/api` goes to Service A, `/static` to Service B).

**AA14** — A message queue (RabbitMQ) focuses on delivering messages to consumers and deleting them once processed (transient). A log-based broker (Kafka) persists messages in an append-only log (durable/replayable). Pick RabbitMQ for complex routing/task queues; pick Kafka for high-throughput stream processing and event replay.

**AA15** — A container shares the host OS kernel (lightweight); a VM includes a full guest OS and hypervisor (heavy). Containers are popular because they are fast to start, use fewer resources, and ensure environment parity.

**AA16** — Stateless: Service holds no client data between requests (e.g., a math API). Stateful: Service maintains context (e.g., a database). Stateless services scale horizontally easily because any instance can handle any request without needing to sync local data.

**AA17** — An ORM maps code objects to database tables. Examples: Hibernate (Java), Entity Framework (.NET). *Trade-offs:* ORMs increase development speed but can introduce performance overhead and "N+1" query problems compared to optimized raw SQL.

**AA18** — Bulkhead pattern isolates failures to prevent cascading. 
*Implementation:* Use separate thread pools for different downstream services so one slow service doesn't exhaust all threads. Alternatively, use separate deployment groups (clusters) for critical vs. non-critical services.

**AA19** — OT (Operational Transformation) relies on a central server to transform operations to maintain consistency. CRDTs (Conflict-free Replicated Data Types) use mathematical properties to allow local updates that eventually converge without a central coordinator. 
*Choice:* **CRDTs** for offline editing, as they allow local progress and seamless merging when connectivity returns.

**AA20** — Challenges: Maintaining a single TraceID across services. 
*Context Propagation:* Using headers (W3C Trace Context/B3). 
*Sampling:* Head-based (decide at start) vs. Tail-based (decide after seeing the whole trace). 
*Kafka:* You must inject the trace context into the Kafka message headers to maintain continuity.

## On-Premise Infrastructure Architecture

**OP1** — Type 1: Runs directly on hardware (ESXi, Xen). Type 2: Runs on an OS (VirtualBox, VMware Workstation).

**OP2** — SAN (Storage Area Network): Block-level (Fibre Channel/iSCSI), used for high-perf DBs. NAS (Network Attached Storage): File-level (NFS/SMB), used for shared file storage.

**OP3** — 3-tier: Core $\rightarrow$ Distribution $\rightarrow$ Access. Leaf-Spine: Every Leaf connects to every Spine. It solves the "East-West" traffic bottleneck by providing predictable, low-latency paths between servers.

**OP4** — 3+ nodes for quorum. Use Ceph for distributed storage. Fencing (STONITH) is required to kill a non-responsive node to prevent data corruption. On node failure, the cluster detects loss of quorum/heartbeat and restarts VMs on healthy nodes.

**OP5** — 802.1Q adds a tag to the Ethernet frame. On Linux, use sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — 1 (Mirror), 5 (Parity, 1 disk loss), 6 (Double parity, 2 disk loss), 10 (Striped mirrors), Z2 (ZFS double parity). For a database: **RAID 10** (best performance and redundancy).

**OP7** — Internal AD handles users. DMZ hosts public services. Split-horizon: Internal users get private IPs; external users get public IPs. DNSSEC signs zones. When a laptop moves to VPN, it queries the internal recursive resolver via the VPN tunnel.

**OP8** — Root CA (Offline/Master) $\rightarrow$ Subordinate CA (Issuing) $\rightarrow$ End-entity. CRL/OCSP handles revocation. Compromised Subordinate: Revoke its cert. Compromised Root: Total PKI rebuild required.

**OP9** — MPLS (Reliable/Expensive), IPsec (Cheap/Internet), SD-WAN (Smart/Hybrid), WireGuard (Fast/Mesh). For VoIP: **SD-WAN** (prioritizes traffic and manages multiple paths).

**OP10** — Out-of-band management (IPMI/iDRAC) allows hardware access even if the OS is down. If exposed to the internet, it is a massive security risk (potential for remote hardware takeover).

**OP11** — LVM: Logical volumes on top of physical disks. LVM-Thin: Space-efficient (allocates on demand). ZFS: Copy-on-write, integrated volume manager/filesystem. ZFS snapshots are near-instant (pointer-based).

**OP12** — Use Ceph with CRUSH rules to ensure replicas are on different racks/sites. A 2-site Ceph cluster is dangerous because if the link breaks, neither side has quorum (split-brain). You need a 3rd site or a "witness" node to act as a tiebreaker.

**OP13** — DORA: Discover, Offer, Request, Acknowledge. If the server is down and lease expires, the client uses APIPA (169.254.x.x).

**OP14** — Managed switches allow VLANs, SNMP, and Spanning Tree Protocol (STP). Unmanaged switches are "plug-and-play" with no configuration.

**OP15** — NTP synchronizes clocks. Drift causes: Kerberos authentication failures, log correlation errors, and database transaction inconsistencies.

**OP16** — Physical (Hardware), VM (Hypervisor-based), Container (OS-level). Run high-performance DBs or GPU workloads on **bare metal** to avoid virtualization overhead.

**OP17** — UPS provides short-term battery power; Generator provides long-term power. An ATS (Automatic Transfer Switch) switches the load from UPS/Mains to the Generator.

**OP18** — Active-Passive: One standby. Active-Active: Both serve traffic. In Pacemaker/Corosync: Use a Virtual IP (VIP) that moves to the healthy node. Use STONITH (fencing) to ensure the failed node is truly powered off before the standby takes over.

**OP19** — 3-2-1: 3 copies, 2 media, 1 offsite. RPO (Data loss window), RTO (Downtime window). Use immutable backups (WORM) for ransomware. Backup is data copying; Disaster Recovery is the plan to restore business operations.

**OP20** — Supplicant (Client), Authenticator (Switch), Auth Server (RADIUS). EAP-TLS (Certificates) is most secure; PEAP (Password) is common. MAB (MAC Authentication Bypass) allows non-802.1X devices (printers) to connect based on their MAC address.
