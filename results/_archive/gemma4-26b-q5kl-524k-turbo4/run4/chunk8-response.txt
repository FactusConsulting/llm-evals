## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw computing resources (VMs, storage, networks). Example: AWS EC2. **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy without managing OS/runtime. Example: AWS Elastic Beanstalk. **SaaS (Software as a Service):** Fully managed software delivered over the web. Example: Microsoft 365.

**CL2** — The provider is responsible for the "Security **of** the Cloud" (physical, hardware, hypervisor); the user is responsible for "Security **in** the Cloud" (data, IAM, OS).
* **IaaS VMs:** Provider handles hardware/hypervisor; You handle OS, middleware, and apps.
* **Managed Kubernetes:** Provider handles Control Plane; You handle worker nodes, pods, and data.
* **SaaS (M365):** Provider handles almost everything; You handle data, user access, and endpoint security.

**CL3** — **VPC:** A private, isolated virtual network. **Subnet:** A range of IP addresses within a VPC. **Security Group (SG):** A virtual firewall for *instances* (stateful). **NACL:** A firewall for *subnets* (stateless). 
* **Layering:** VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group $\rightarrow$ Instance.
* **Stateful (SG):** If you allow inbound traffic, outbound response is automatically allowed. 
* **Stateless (NACL):** You must explicitly define both inbound and outbound rules.

**CL4** — **Landing Zone:** A pre-configured, multi-account environment following best practices. **OUs (Organizational Units):** Logical groupings of accounts (e.g., Prod, Dev, Security). **Guardrails:** Service Control Policies (SCPs) that restrict actions. **Shared Networking:** Using a Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize traffic. **Centralized Logging:** Aggregating logs (S3/Log Analytics) into a dedicated security account. **Single-account problem:** High blast radius, hitting service limits, and lack of administrative isolation.

**CL5** — **IaC:** Managing infrastructure via machine-readable files.
* **Terraform/OpenTofu:** HCL-based, provider-agnostic, industry standard. Use for multi-cloud/complex state.
* **Pulumi:** Uses general-purpose languages (Python, TS). Use when developers want to use familiar programming constructs.
* **CloudFormation/Bicep:** Cloud-native (AWS/Azure). Use for deep, zero-day integration with specific cloud features.
* **Crossplane:** K8s-native IaC. Use when you want to manage cloud resources via K8s APIs (Control Plane approach).

**CL6** — **HPA:** Scales pods based on CPU/RAM. **VPA:** Adjusts pod resource requests/limits. **Cluster Autoscaler:** Adds/removes nodes (VMs) to the cluster. **KEDA:** Event-driven autoscaling. **Use KEDA over HPA** when scaling needs to be triggered by external events (e.g., message queue depth in Kafka/RabbitMQ) rather than just resource metrics.

**CL7** — **RPO (Recovery Point Objective):** Max data loss. **RTO (Recovery Time Objective):** Max downtime.
* **Active-Active:** Both regions serve traffic; zero/near-zero RTO/RPO; highest cost.
* **Active-Passive:** One region is standby. **Pilot Light:** Minimal version of services running (DB only). **Warm Standby:** Scaled-down version of full stack. **Multi-site:** Full capacity in both.
* **Replication:** **Sync** (Zero loss, high latency) vs **Async** (Low latency, potential data loss).
* **DNS:** Route53/Traffic Manager handles the failover routing.

**CL8** — **GitOps:** Using Git as the single source of truth for desired state. **ArgoCD** (Pull-based, K8s-native, focuses on application sync) vs **FluxCD** (Pull-based, lightweight, modular). **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault/AWS SM), or **Vault** (centralized). **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and automatically reverts the environment to match the Git state.

**CL9** — **StatefulSet:** Provides stable network IDs and persistent storage mapping. **PV/PVC:** Use a `local-storage` class for low-latency NVMe/SSD. **Headless Service:** Allows direct pod-to-pod communication via DNS. **Init Containers:** Used to run setup scripts/config before the main app starts. **ConfigMaps:** Mounted as volumes to provide specific file paths. **Pod Disruption Budget (PDB):** Ensures a minimum number of pods remain available during maintenance.

**CL10** — **Service Account:** K8s internal identity. **Workload Identity/IRSA:** Mapping a K8s Service Account to a Cloud IAM Role. **Bad Practice:** Mounting long-lived credentials (JSON keys) in pods risks exposure if a pod is compromised. **Workload Identity Federation** uses OIDC to exchange a K8s token for a short-lived cloud token, eliminating static secrets.

**CL11** — **Object (S3/Blob):** Unstructured data, high durability (11 nines), accessed via API. **Block (EBS/Managed Disk):** Attached to a single VM, low latency, used for OS/DBs. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB) accessible by multiple instances. **Durability:** Object storage is highest; Block is medium; File is medium.

**CL12** — **Zero-Trust:** "Never trust, always verify." 
* **Network Policies:** L3/L4 pod-to-pod isolation. 
* **Service Mesh (mTLS):** L7 identity and encryption. 
* **Admission Controllers (OPA/Kyverno):** Enforce policy before resources are created. 
* **Image Signing:** Ensures only trusted images run. 
* **Falco:** Detects runtime anomalies. 
* **Difference:** Traditional security relies on a "hard shell" (perimeter) and "soft center"; Zero-Trust assumes the perimeter is already breached.

**CL13** — **CDN:** A distributed network of proxy servers that caches content closer to users. **Services:** AWS CloudFront, Azure Front Door. **Use CDN** for static assets (images, JS, CSS) to reduce latency and origin load. **Use Origin** for dynamic, non-cacheable, or highly sensitive data.

**CL14** — **Region:** A geographic area containing multiple AZs. **Availability Zone (AZ):** One or more discrete data centers. **Multi-AZ:** Protects against data center failure. **Zonal:** Resource lives in one AZ. **Regional:** Resource (like S3) is replicated across multiple AZs automatically.

**CL15** — **Managed DB:** Provider handles patching, backups, hardware, and high availability. **User handles:** Schema design, query optimization, and application-level logic.

**CL16** — **IAM:** **Users** (individuals), **Groups** (collections of users), **Roles** (temporary identities for services), **Policies** (JSON permission documents). **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply via granular IAM policies and scoped roles.

**CL17** — **Serverless:** Event-driven execution without managing servers. **Lambda/Functions:** Scale to zero, pay-per-use. **Cold Starts:** Latency incurred when a function is invoked after being idle (initializing the runtime). **Poor fit:** Long-running processes, high-performance computing, or constant high-load workloads.

**CL18** — **Ingress:** L7 routing. **Gateway API:** Next-gen, role-oriented (Infrastructure vs Application). **Cloud LB:** L4/L7 entry points. **Service Mesh Ingress:** Handles mTLS and complex L7 routing. **TLS Termination:** Can happen at the Cloud LB (edge), Ingress Controller (L7), or Service Mesh (sidecar). **Gateway API** is preferred for its improved separation of concerns between infrastructure and application teams.

**CL19** — **Optimization:** **RI/Savings Plans** (Commitment-based), **Spot** (Cheap, interruptible), **Right-sizing** (matching capacity to demand). **Storage Tiering:** Moving old data to Archive/Glacier. **FinOps:** Implementing culture of cost-awareness. **Tools:** AWS Cost Explorer, Azure Cost Management. **Models:** Showback (reporting usage) and Chargeback (billing departments).

**CL20** — **Multi-cloud:** Use **Kubernetes** as the abstraction layer. Use **Terraform** for IaC. Use **VPN/Interconnect** for networking. Use **Identity Federation** (OIDC) to bridge IAM. **Trade-offs:** Multi-cloud increases complexity and cost significantly. **Justification:** Only when regulatory requirements demand it or when specific high-value services are unique to one provider.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** 
* **Level 0:** Physical process (sensors/actuators). 
* **Level 1:** Basic Control (PLCs). 
* **Level 2:** Supervisory Control (HMI/SCADA). 
* **Level 3:** Site Operations (Historian). 
* **Level 4/5:** Business/Enterprise (ERP/Cloud).

**OT2** — **IT:** Focuses on Confidentiality/Integrity. **OT:** Focuses on Availability/Safety. **Patching:** OT systems require extreme stability; standard IT patching can cause unplanned downtime or crash sensitive legacy controllers.

**OT3** — **IDMZ:** A buffer zone between IT and OT. **Traffic:** Only specific, inspected data (e.g., via a proxy or data historian) should cross. **Danger:** Direct L4-to-L1 connectivity allows a compromised IT workstation to directly manipulate physical processes.

**OT4** — 1. **Modbus TCP:** L1/L2. 2. **OPC UA:** L2/L3 (Secure/Standardized). 3. **EtherNet/IP:** L1/L2. 4. **PROFINET:** L1/L2. 5. **MQTT:** L3/L4 (Edge-to-Cloud).

**OT5** — **Data Diode:** Physical hardware ensuring one-way data flow (unidirectional). **Firewall:** Software-based, bidirectional (though rules can be one-way). **Use Diode** for high-security air-gap requirements where no return path must exist. **Limitation:** Firewalls are susceptible to software misconfiguration/vulnerabilities.

**OT6** — **Flow:** Sensor $\rightarrow$ PLC $\rightarrow$ SCADA/Historian $\rightarrow$ Edge Gateway (with MQTT) $\rightarrow$ Cloud Ingestion. **Security:** Place the IDMZ between the SCADA/Historian and the Edge Gateway.

**OT7** — **Zones:** Logical groupings of assets with similar security requirements. **Conduits:** Communication paths between zones. **Model:** Corporate (Zone 1) $\rightarrow$ IDMZ (Zone 2) $\rightarrow$ SCADA (Zone 3) $\rightarrow$ Control/PLC (Zone 4) $\rightarrow$ SIS (Isolated Zone).

**OT8** — **Strategy:** Segment production lines into separate VLANs. Place firewalls between lines and between SCADA and PLCs. Use a Jump Host in the IDMZ for vendor access. **Transition:** Implement in parallel (shadow mode) to monitor traffic before enforcing blocks, ensuring no production impact.

**OT9** — **SIS:** Independent safety system to prevent catastrophe. **BPCS:** The standard control loop. **IEC 61511:** Standard for functional safety. **Isolation:** SIS must be isolated to prevent a single compromise from disabling both control and safety. **Ransomware:** If it reaches SIS, it could prevent emergency shutdowns, leading to physical destruction.

**OT10** — **PLC:** Local, discrete logic. **DCS:** Integrated, plant-wide process control. **SCADA:** Supervisory, distributed monitoring. They can coexist; SCADA often sits above PLCs/DCS.

**OT11** — **Architecture:** Use Jump Hosts with MFA and session recording. **Access:** Time-limited, "just-in-time" access. **Unacceptable:** Direct RDP from IT to HMI bypasses all inspection and creates a massive attack surface.

**OT12** — **Plan:** 1. **Detect:** Use IDS for anomaly detection. 2. **Isolate:** Sever the VPN/IDMZ connection. 3. **Coordinate:** Alert the control room immediately. 4. **Operator Role:** The operator's priority is maintaining a "Safe State" (manual override/emergency stop) while IT handles the digital threat.

**OT13** — **HMI:** A visual interface for operators to monitor/control processes. **Engineering Workstation:** Used for programming/configuring PLCs/controllers.

**OT14** — **Historian:** A database for time-series process data. **Plant Historian (L3):** Real-time, high-resolution. **Enterprise Historian (L4):** Aggregated, long-term trends for business analysis.

**OT15** — **Ladder Logic:** A graphical programming language resembling electrical relay diagrams. Executed by **PLCs**. It remains dominant due to its intuitive nature for electricians and high reliability.

**OT16** — **RTU:** Designed for long-distance, remote telemetry (e.g., water/oil pipelines). **PLC:** Designed for high-speed, local, discrete control.

**OT17** — **Analog:** Continuous (4-20mA). **Digital:** Discrete (On/Off). **4-20mA** is preferred because a "Live Zero" (4mA) allows the system to distinguish between a "zero reading" and a "broken wire" (0mA).

**OT18** — **Inventory:** Knowing every device is the foundation of security. **Techniques:** Passive monitoring (listening to traffic) is preferred. **Active scanning** is dangerous because it can overwhelm legacy PLC CPUs and cause them to crash.

**OT19** — **MITRE ATT&CK for ICS:** Focuses on physical impact. **Tactics:** 1. Inhibit Response (e.g., disabling alarms). 2. Impair Control (e.g., changing setpoints). 3. Impair Process (e.g., stopping a pump). 4. Denial of View (e.g., freezing HMI). 5. Loss of Safety (e.g., disabling SIS). **Difference:** It maps techniques specifically to industrial processes rather than just IT data theft.

**OT20** — **SOC Design:** Use passive network taps for log collection. **Integration:** Feed OT logs into a SIEM with OT-specific rules (e.g., "New PLC firmware detected"). **Triage:** Alerts must be vetted by OT engineers to avoid false positives that trigger unnecessary shutdowns. **Firmware Alert:** Treat as a critical incident; isolate the PLC and verify integrity via manual inspection.
