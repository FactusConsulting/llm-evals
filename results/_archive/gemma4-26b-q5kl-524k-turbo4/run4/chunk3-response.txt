## OpenTofu / Terraform

**T1** — `tofu plan` creates an execution plan, showing what changes (add, change, destroy) will occur without actually making changes. `tofu apply` executes those changes to reach the desired state.

**T2** — State is a JSON file mapping your configuration to real-world resource IDs. Remote state (stored in S3, GCS, etc.) is critical for team collaboration, providing a "single source of truth" and enabling state locking to prevent concurrent modifications.

**T3** — `count` uses an index (0, 1, 2...), making it risky for deletions (deleting index 0 shifts all others). `for_each` uses a map or set of strings, making it stable because resources are identified by keys rather than position. `for_each` is preferred when managing collections where items might be added or removed from the middle.

**T4** — This is "drift." During the next `tofu plan`, OpenTofu performs a "refresh" (querying the cloud API), detects the discrepancy between the real-world state and the state file, and proposes changes to revert the resource to the configuration's desired state.

**T5**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-xxxxxx"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6** — `terraform_remote_state` reads the entire state file of another workspace, creating tight coupling. The recommended alternative is using **Outputs** from one module and passing them as **Inputs** to another, or using **Data Sources** to fetch specific information. This promotes loose coupling and better security.

**T7** — This is a race condition. The `null_resource` is considered "complete" once the provisioner finishes, but if the output is being used by another resource that starts its own lifecycle before the RKE2 API is fully responsive, it fails. **Fix:** Use `depends_on` in the dependent resource to point to the `null_resource`, or use a `data` source that polls for the resource's readiness.

**T8** — `tofu import` brings existing infrastructure under management. Its limitation is that it only updates the state, not the code. The `import` **block** (1.5+) is declarative; you write the block in your code, run a plan to see what will be imported, and then apply. This allows for a "plan-first" workflow for imports.

**T9** — A `variable` is an input to a module (like a function argument). An `output` is a value exported by a module (like a return value).

**T10** — A provider is a plugin that translates OpenTofu code into API calls for a specific platform (AWS, Azure, etc.). If you run `plan` without `init`, OpenTofu will fail because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11** — The `.terraform.lock.hcl` file records the exact versions and hashes of providers used. It should be committed to ensure every environment (Dev, Staging, Prod) uses the identical provider versions, preventing "it works on my machine" issues.

**T12** — `tofu destroy` removes all resources managed by the current state. To target a single resource: `tofu destroy -target=aws_instance.my_vm`.

**T13** — A data source allows you to fetch information from resources *not* managed by your current OpenTofu code. Example: Using `data "aws_ami" "latest"` to find the newest Ubuntu image ID instead of hardcoding it.

**T14** — `variable` blocks are for external inputs (user-provided). `locals` are for internal logic (calculated values). Use `locals` when you need to perform string interpolation, math, or complex logic that shouldn't be exposed as an input.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
- `prevent_destroy`: Prevents accidental deletion of critical resources (e.g., a production DB).
- `ignore_changes`: Tells OpenTofu to ignore specific attributes (e.g., if an Auto Scaling Group changes a tag automatically).

**T16** — The `moved` block allows you to rename a resource or move it into a module in your code without OpenTofu thinking it needs to destroy the old one and create a new one. It updates the state mapping instead.

**T17** — OpenTofu builds a Directed Acyclic Graph (DAG). **Implicit dependencies** occur when one resource references another's attribute. **Explicit dependencies** use `depends_on`. `depends_on` forces serial execution, which reduces parallelism. It should be used sparingly because it can significantly slow down execution by breaking the graph's ability to run independent tasks concurrently.

**T18** — 
1. **State Splitting:** Break a monolithic state into smaller, decoupled states (reduces refresh time).
2. **`-refresh=false`:** Skips the API refresh during plan (faster, but risks inaccuracy).
3. **`-target`:** Only plan specific resources (useful for debugging).
4. **Modularization:** Reducing the number of resources per state file to minimize the graph size.

**T19** — State locking prevents two users/processes from writing to the state simultaneously. If a CI pipeline crashes, the lock remains. You break it with `tofu force-unlock <LOCK_ID>`. **Risk:** If you force-unlock while another process is actually writing, you risk **state corruption**.

**T20** — 
1. Add the `backend "s3" { ... }` block to your code.
2. Run `tofu init`. OpenTofu will detect the change and ask to migrate the state.
3. Confirm the migration.
4. **Verify:** Run `tofu state list` to ensure all resources are present and `tofu plan` to ensure no unexpected changes are pending.

## Ansible

**A1** — A **Task** is a single action. A **Playbook** is a collection of plays (mapping hosts to tasks). A **Role** is a structured, reusable collection of tasks, variables, and files.

**A2** — `ansible_facts` is a dictionary of system information gathered by Ansible. Access the OS family via `ansible_facts['os_family']`.

**A3** — `command` executes a command without a shell (more secure). `shell` executes via `/bin/sh` (allows pipes/redirects). `raw` executes via direct SSH without requiring Python on the target.

**A4** — Idempotency means running a task multiple times results in the same state. 
- **Idempotent:** `apt: name=nginx state=present`.
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file`.

**A5**
```yaml
- name: Install htp
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel and htop on RedHat
  yum:
    name: [epel-release, htop]
    state: present
  when: ansible_os_family == "RedHat"
```

**A6** — Order (lowest to highest): `role defaults` < `group_vars` < `host_vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process in batches. To ensure the first 3 finish before the rest, you could use a separate play or a `wait_for` task, but `serial` is the standard way to control concurrency.

**A8** — `ansible-vault` encrypts files/vars. To encrypt a single variable, use `ansible-vault encrypt_string 'my_secret_password' --name 'password'`.

**A9** — An **Inventory** is a list of managed hosts. **Static** is a hardcoded file; **Dynamic** is a script/plugin that queries a cloud provider (AWS/GCP) to get a real-time list.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **Handler** is a special task that only runs if notified by another task via the `notify` keyword. It runs at the end of the play.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory`, `remote_user`, and `forks`.

**A13** — `register` saves the output of a task into a variable. Example: `register: result`, then use `{{ result.stdout }}` in the next task.

**A14** — `import_tasks` is static (processed when the playbook is parsed). `include_tasks` is dynamic (processed at runtime). `include_tasks` allows for conditional execution of the entire task file.

**A15** — **Ansible Galaxy** is a public hub for roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16** — `ssh` is the default (uses SSH to run Python). `local` runs tasks on the control node. `network_cli` is used for network devices (switches/routers) that don't have Python.

**A17** — `delegate_to` runs a task on a different host. `run_once` ensures a task runs only once per play. 
**Example:** `delegate_to: localhost`, `run_once: true`, `tasks: [ name: "Log success to local file" ]`.

**A18** — 
1. **Forks:** Increase `forks` in `ansible.cfg` to run more tasks in parallel.
2. **Pipelining:** Enable `pipelining = True` to reduce SSH connections.
3. **Fact Caching:** Use a Redis/JSON cache for facts to avoid re-gathering.
4. **Mitogen:** Use the Mitogen plugin to optimize SSH execution.

**A19** — `{{ }}` is for expressions/variables; `{% %}` is for control logic (loops/ifs); `{# #}` is for comments.
```jinja2
upstream nginx_backend {
{% for server in backend_servers %}
  server {{ server }}; # Health check: {{ server }}
{% endfor %}
}
```

**A20** — 
1. Use `serial: 5` to roll through 20 servers in 4 batches.
2. **Pre-task:** Use `uri` module to remove the server from the Load Balancer.
3. **Task:** Perform the update.
4. **Post-task:** Use `uri` module to check the app health.
5. **Rollback:** Wrap the update in a `block`. In the `rescue` section, revert the version or notify the LB to keep the server out of rotation.
