## Application Architecture

**AA1** — A **monolith** is a single, unified deployment unit where all functions reside in one codebase. **Microservices** are a collection of loosely coupled, independently deployable services. 
*Problems introduced by microservices:* 1. Network latency/complexity, 2. Distributed data consistency (no ACID across services), 3. Observability challenges (tracing a single request across many hops).

**AA2** — **Synchronous** communication requires the caller to wait for a response (e.g., **HTTP/REST**). **Asynchronous** communication allows the caller to proceed without waiting (e.g., **RabbitMQ/Message Queues**).

**AA3** — A **reverse proxy** sits in front of servers to handle load balancing and SSL termination. An **API Gateway** adds application-level logic (auth, rate limiting, request transformation). An API Gateway can replace a reverse proxy for external traffic, but a reverse proxy is often still used internally for simple, high-performance routing.

**AA4** — The **Saga pattern** manages distributed transactions via a sequence of local transactions. 
* **Choreography:** Each service produces/listens to events; no central controller. Best for simple workflows. 
* **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex, multi-step business logic.

**AA5** — **CQRS** separates read and write models. It is paired with **Event Sourcing** (storing state as a sequence of events) because CQRS needs a way to rebuild the read model from the source of truth. This solves the problem of high-contention on a single database model by allowing optimized read views.

**AA6** — The **Circuit Breaker** prevents a failing service from dragging down the whole system. 
* **States:** **Closed** (requests flow), **Open** (requests fail immediately), **Half-Open** (testing if the service recovered). 
* **Difference:** Retry handles transient blips; Circuit Breaker handles systemic failure. Use **Retry** for short-lived errors and **Circuit Breaker** to stop the bleeding during an outage.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, lowest security, highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Medium cost, medium security, medium noisy-neighbor risk.
3. **Separate DB:** Highest cost, highest security, lowest noisy-neighbor risk.

**AA8** — **Strong consistency** ensures all nodes see the same data simultaneously; **Eventual consistency** guarantees data will converge given time. 
* **Inventory Architecture:** Use **Strong Consistency** via an RDBMS (e.g., **PostgreSQL**) with **Pessimistic Locking** or a distributed lock manager (e.g., **Redis/Etcd**) to ensure a single source of truth for stock levels.

**AA9** — A **sidecar proxy** (like Envoy) runs alongside the application container to handle networking. In **Istio**, Envoy is the **Data Plane** (handles actual traffic), while Istio is the **Control Plane** (manages configuration). **mTLS** between sidecars provides identity and encryption, solving the "man-in-the-middle" risk that application-level TLS (which requires manual code changes) might miss or misconfigure.

**AA10** — The **Strangler Fig** pattern involves placing a proxy in front of the monolith and incrementally routing specific endpoints to new .NET 8 microservices. 
* **Strategy:** 1. Identify a bounded context. 2. Build the new service in .NET 8. 3. Update the proxy to route that specific path to the new service. 4. Repeat until the monolith is "strangled."

**AA11** — 12-Factor methodology: **Codebase** (one repo per app), **Dependencies** (explicit declaration), **Config** (stored in environment), **Backing services** (treated as attached resources), **Build/Release/Run** (strict separation), **Processes** (stateless), **Port binding** (self-contained), **Concurrency** (scale via process model), **Disposability** (fast startup/shutdown), **Dev/Prod parity** (keep environments similar), **Logs** (treat as event streams), **Admin processes** (run as one-off tasks).

**AA12** — 
* **Kafka (Event):** High decoupling, high scalability, complex debugging, strict ordering via partitions, high resilience.
* **REST/gRPC (Request):** Tight coupling, lower scalability, easy debugging, no inherent ordering, immediate failure feedback.
* **Choice:** Use Kafka for high-throughput, asynchronous background tasks; use REST/gRPC for real-time, synchronous user-facing requests.

**AA13** — A **load balancer** distributes traffic across multiple servers. **Layer 4** (Transport) routes based on IP/Port. **Layer 7** (Application) routes based on HTTP headers/paths. **Use case:** Routing `/api/v1` to one cluster and `/static` to another.

**AA14** — A **message queue** (RabbitMQ) is designed for point-to-point task distribution (once consumed, it's gone). A **log-based broker** (Kafka) is an append-only log where messages persist and can be replayed. Pick RabbitMQ for complex routing/task queues; pick Kafka for high-throughput stream processing.

**AA15** — A **container** shares the host OS kernel, making it lightweight. A **VM** includes a full guest OS and a hypervisor. Containers are popular because they are fast to start, use fewer resources, and ensure environment consistency.

**AA16** — **Stateless** services do not store client data locally (e.g., a Web API). **Stateful** services maintain data (e.g., a Database). Stateless services scale horizontally easily because any instance can handle any request.

**AA17** — An **ORM** maps database tables to programming objects. Examples: **Hibernate** (Java), **Entity Framework** (.NET). **Trade-offs:** ORMs increase productivity but can introduce performance overhead and "N+1" query problems compared to raw SQL.

**AA18** — The **Bulkhead pattern** isolates components so one failure doesn't sink the whole system. 
* **Implementation:** Use separate **thread pools** for different service calls or deploy services into **separate hardware/clusters** so a resource leak in one doesn't starve the others.

**AA19** — **OT** requires a central server to resolve conflicts; **CRDTs** allow decentralized, mathematical convergence. 
* **Choice:** For **offline editing**, choose **CRDTs** because they allow users to make changes locally and merge them seamlessly when they reconnect without needing a central authority to arbitrate every single operation.

**AA20** — Challenges include maintaining a single **TraceID** across services. 
* **Context Propagation:** Use **W3C Trace Context** or **B3** headers. 
* **Sampling:** **Head-based** (decide at the start) vs **Tail-based** (decide after the trace completes, e.g., keep only errors). 
* **Kafka:** To ensure continuity, the producer must inject the trace context into the **Kafka message headers**, which the consumer then extracts to continue the span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., **ESXi, Proxmox**). **Type 2 (Hosted):** Runs on top of an OS (e.g., **VirtualBox, VMware Workstation**).

**OP2** — **SAN (Storage Area Network):** Block-level storage (e.g., **iSCSI, Fibre Channel**). **NAS (Network Attached Storage):** File-level storage (e.g., **NFS, SMB**). Use SAN for databases/VM disks; NAS for shared files/documents.

**OP3** — **3-tier** is hierarchical (Core/Dist/Access). **Leaf-Spine** is a two-layer mesh where every Leaf connects to every Spine. It solves the "East-West" traffic bottleneck by providing predictable, low-latency paths between servers.

**OP4** — A HA Proxmox cluster needs **3+ nodes** for quorum. **Fencing (STONITH)** is used to kill a non-responsive node to prevent data corruption. **Shared storage** (Ceph/iSCSI) allows VMs to migrate. On node failure, the cluster detects the loss of heartbeat, fences the node, and restarts the VMs on remaining healthy nodes.

**OP5** — **VLAN trunking** allows multiple VLANs over one link using **802.1Q** tags. On Linux, configure sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — **RAID 1** (Mirror), **5** (Parity, 1 drive loss), **6** (Double parity, 2 drives), **10** (Mirror + Stripe), **Z2** (ZFS parity). For a 6-drive DB: **RAID 10** is best for performance and fault tolerance.

**OP7** — **Internal AD** handles local auth. **DMZ** hosts public services. **Split-horizon** provides different IPs for the same domain depending on whether the request is internal or external. **DNSSEC** signs records to prevent spoofing. **VPN** users use the internal recursive resolver via the tunnel.

**OP8** — **Root CA** (Offline/Master) $\rightarrow$ **Subordinate CA** (Issuing) $\rightarrow$ **End-entity**. **CRL** is a list of revoked certs; **OCSP** is a real-time check. **Compromised Subordinate:** Only that branch is untrusted. **Compromised Root:** The entire PKI is dead and must be rebuilt.

**OP9** — **MPLS** (Reliable/Expensive), **IPsec** (Cheap/Internet), **SD-WAN** (Smart/Hybrid), **WireGuard** (Fast/Mesh). For **VoIP**, I recommend **SD-WAN** because it can prioritize traffic and manage multiple paths (e.g., MPLS + Internet) to ensure low latency.

**OP10** — **IPMI/iDRAC** provides out-of-band management (accessing hardware even if the OS is crashed). If exposed to the internet, an attacker could gain full hardware control, wipe drives, or intercept data.

**OP11** — **LVM** (Logical volumes), **LVM-Thin** (Space-efficient/over-provisioning), **ZFS** (Copy-on-Write filesystem). LVM snapshots are metadata-based; ZFS snapshots are atomic and part of the filesystem structure.

**OP12** — A **stretch cluster** needs a 3rd site or a "witness" to prevent **split-brain** (where two sites think they are primary). 2-site Ceph is dangerous because if the link breaks, neither side has a majority (quorum), causing both to stop.

**OP13** — **DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge. If the server is down, a Windows client uses **APIPA** (169.254.x.x).

**OP14** — **Managed switches** allow VLANs, SNMP, and Spanning Tree. **Unmanaged** are plug-and-play. Managed is essential for security and traffic control.

**OP15** — **NTP** ensures time sync. Clock drift causes: Log correlation failure, Kerberos/Auth failures, and database transaction errors.

**OP16** — **Physical** (Hardware), **VM** (OS abstraction), **Container** (App abstraction). Run on **bare metal** for high-performance workloads like heavy databases or GPU tasks to avoid hypervisor overhead.

**OP17** — **UPS** provides short-term battery power; **Generator** provides long-term power. An **ATS** automatically switches the load to the generator when utility power fails.

**OP18** — **Active-Passive** (one standby); **Active-Active** (both active). **Pacemaker/Corosync** manages the cluster. **Fencing (STONITH)** ensures a failed node is truly dead before the standby takes over the **Virtual IP**.

**OP19** — **3-2-1 Rule:** 3 copies, 2 media, 1 offsite. **RPO** (max data loss), **RTO** (max downtime). **Immutable backups** prevent ransomware from deleting backups. **Backup** is data copying; **Disaster Recovery** is the plan to restore operations.

**OP20** — **802.1X:** **Supplicant** (client) $\rightarrow$ **Authenticator** (switch) $\rightarrow$ **Auth Server** (RADIUS). **EAP-TLS** uses certificates; **PEAP** uses passwords. **MAB** allows non-802.1X devices (like printers) to connect by authenticating their **MAC address**.
