## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw computing resources (VMs, storage, networks). You manage the OS and apps. *Example: AWS EC2.* **PaaS (Platform as a Service):** Provides a platform for deploying code without managing underlying OS/hardware. *Example: Google App Engine.* **SaaS (Software as a Service):** Fully managed software delivered over the web. *Example: Microsoft 365.*

**CL2** — In the **Shared Responsibility Model**, the provider is responsible for "Security **of** the Cloud" (hardware, global infra), and the customer is responsible for "Security **in** the Cloud" (data, IAM, OS).
* **IaaS VMs:** Provider manages hardware/hypervisor; You manage OS, middleware, and data.
* **Managed Kubernetes:** Provider manages Control Plane (API server, etcd); You manage worker nodes (if not Fargate/Autopilot), pods, and data.
* **SaaS (M365):** Provider manages everything except your data and user access/identity.

**CL3** — **VPC:** A logically isolated virtual network. **Subnet:** A range of IP addresses within a VPC. **Security Group (SG):** A stateful firewall at the instance/NIC level. **NACL:** A stateless firewall at the subnet level. **Layering:** Traffic flows through NACL (subnet boundary) $\rightarrow$ SG (instance boundary). **Stateful (SG):** If an inbound request is allowed, the return traffic is automatically allowed. **Stateless (NACL):** You must explicitly define both inbound and outbound rules.

**CL4** — A **Landing Zone** is a pre-configured, multi-account environment providing a foundation for scale. **Organizational Units (OUs)** group accounts by function (e.g., Prod, Dev, Security). **Guardrails** (like AWS SCPs) enforce policy limits. **Shared Networking** uses a **Hub-and-Spoke** model (Transit Gateway/Azure Virtual WAN) to centralize inspection and connectivity. **Centralized Logging** ensures audit trails are sent to a dedicated security account. A **single-account approach** is problematic due to massive blast radius, lack of isolation, and hitting service limits.

**CL5** — **IaC** is managing infrastructure via machine-readable definition files.
* **Terraform/OpenTofu:** Declarative, HCL-based, best for multi-cloud/provider-agnostic workflows.
* **Pulumi:** Uses general-purpose languages (Python, TS); best for developers wanting programmatic logic.
* **CloudFormation/Bicep:** Cloud-native (AWS/Azure); best for deep, immediate integration with provider-specific features.
* **Crossplane:** K8s-native; best for managing cloud resources via Kubernetes CRDs (Control Plane approach).

**CL6** — **HPA:** Scales the number of pods based on CPU/Memory. **VPA:** Adjusts the CPU/Memory *size* of existing pods. **Cluster Autoscaler:** Adds/removes worker nodes to the cluster. **KEDA:** Event-driven autoscaling (e.g., scale based on RabbitMQ queue depth). Use **KEDA** over HPA when scaling needs to be triggered by external metrics (Kafka, SQL, etc.) rather than just resource utilization.

**CL7** — **RPO (Recovery Point Objective):** Max data loss allowed. **RTO (Recovery Time Objective):** Max downtime allowed.
* **Active-Active:** Workloads run in both regions; zero/near-zero RTO/RPO; highest cost.
* **Active-Passive:** One region is standby. **Warm Standby:** Scaled-down version running; **Pilot Light:** Only data/core services running.
* **Replication:** **Sync** (no data loss, high latency) vs. **Async** (potential data loss, low latency).
* **DNS Failover:** Route53/Traffic Manager redirects traffic to the healthy region.
* **State Management:** Requires global databases (DynamoDB Global Tables/CosmosDB) to ensure data consistency.

**CL8** — **GitOps** uses Git as the single source of truth for both infra and apps. **ArgoCD** and **FluxCD** are pull-based controllers that sync the cluster state to the Git state. **Secrets:** Handled via **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (syncs from AWS Secrets Mgr/Vault), or **HashiCorp Vault**. **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and automatically reverts the cluster to the Git-defined state.

**CL9** — **StatefulSet** provides stable network IDs and ordered deployment. **PV/PVC** with a **Local Storage Class** provides low-latency, node-local disks. A **Headless Service** allows direct pod-to-pod communication via DNS. **Init Containers** prepare the filesystem/environment before the main app starts. **ConfigMaps** are mounted as volumes for specific file paths. **Pod Disruption Budgets (PDB)** ensure a minimum number of pods remain available during maintenance.

**CL10** — **Service Account:** Local to K8s. **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role via OIDC. **Why avoid mounting credentials?** Hardcoded keys in pods are easily stolen and lack rotation. **Workload Identity Federation** solves this by using short-lived, identity-based tokens, eliminating the need for long-lived secrets.

**CL11** — **Object (S3/Blob):** Unstructured data (images, logs); highly durable/scalable. **Block (EBS/Managed Disk):** High-performance disk for VMs/DBs; low latency. **File (EFS/Azure Files):** Shared filesystem for multiple instances. **Durability/Availability:** Object storage offers highest durability ($11$ 9s); Block/File depends on the specific tier and replication settings.

**CL12** — **Zero-Trust** assumes the network is compromised. **Network Policies** restrict L3/L4 traffic between pods. **Service Mesh (Istio/Linkerd)** provides L7 security and **mTLS** for encrypted pod-to-pod communication. **Admission Controllers (OPA/Kyverno)** enforce policy (e.g., "no root containers"). **Image Signing** ensures only trusted code runs. **Falco** provides runtime threat detection. Unlike perimeter models, Zero-Trust focuses on **Identity** rather than IP/Location.

**CL13** — **CDN** is a distributed network of edge servers that cache content closer to users. **Services:** AWS CloudFront, Azure Front Door. Use a CDN for static assets (images, JS) to reduce latency and origin load; serve directly from origin for highly dynamic, non-cacheable data.

**CL14** — **Region:** A geographic area containing multiple AZs. **Availability Zone (AZ):** One or more isolated data centers within a region. **Multi-AZ** deployment protects against data center failure. **Zonal resources** (e.g., a specific EBS volume) are tied to one AZ; **Regional resources** (e.g., S3) are available across the whole region.

**CL15** — **Managed DB (RDS/Cloud SQL):** The provider handles patching, automated backups, high availability (multi-AZ), and hardware scaling. On a **VM**, you are responsible for the OS, DB installation, patching, and manual failover configuration.

**CL16** — **IAM Users:** Individual identities. **Groups:** Collections of users. **Roles:** Temporary identities assumed by users/services. **Policies:** JSON documents defining permissions. **Least Privilege:** Granting only the minimum permissions required for a task (e.g., a service can only `Read` from one specific S3 bucket).

**CL17** — **Serverless:** Event-driven execution without managing servers (Lambda/Functions). **Cold Starts:** Latency incurred when a function is invoked after being idle (container spin-up). **Poor fit:** Long-running processes, high-performance computing requiring constant CPU, or workloads with highly predictable, constant traffic.

**CL18** — **Ingress Resource:** Standard K8s L7 routing. **Gateway API:** Next-gen, more expressive, role-oriented (Infrastructure vs. Application). **Cloud LB Annotations:** Use cloud-native L4/L7 balancers. **Service Mesh Ingress:** Handles complex routing/mTLS at the edge. **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Sidecar (Mesh). Use **Gateway API** for complex, multi-tenant environments requiring fine-grained control.

**CL19** — **Optimization:** **Reserved Instances/Savings Plans** (commit to usage for discounts); **Spot/Preemptible** (cheap, but can be reclaimed); **Right-sizing** (matching instance size to load); **Storage Tiering** (moving old data to Archive/Glacier). **FinOps:** Implement **Showback** (reporting costs to teams) and **Chargeback** (billing teams). **Tools:** AWS Cost Explorer, Azure Cost Management, or CloudHealth.

**CL20** — **Multi-cloud Strategy:** Use **Kubernetes** as the abstraction layer, **Terraform** for IaC, and **VPN/Interconnect** for networking. **Identity Federation** (OIDC) allows seamless access. **Trade-offs:** Multi-cloud avoids lock-in but introduces massive operational complexity and data egress costs. It is justified for high availability/compliance; it is unnecessary for most startups.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** A framework for ICS security. **L0:** Physical process (sensors/actuators). **L1:** Basic Control (PLCs). **L2:** Supervisory Control (HMI/SCADA). **L3:** Site Operations (Historians). **L4:** Business/Enterprise (IT). **L5:** External/Cloud.

**OT2** — **IT** focuses on **Confidentiality** (data privacy); **OT** focuses on **Availability and Safety** (process uptime). You cannot apply standard IT patching to OT because updates can cause unexpected downtime or trigger safety shutdowns in sensitive real-time processes.

**OT3** — **IDMZ (Industrial DMZ):** A buffer zone between L3 and L4. Only specific, inspected traffic (e.g., MQTT, HTTPS) should pass via proxies. **Direct L4 $\rightarrow$ L1 connectivity** is dangerous because a compromised IT workstation could directly manipulate physical machinery, bypassing all safety controls.

**OT4** — **1. Modbus TCP:** L1/L2 (Fieldbus/Control). **2. OPC UA:** L2/L3 (Interoperability/Supervisory). **3. EtherNet/IP:** L1/L2 (Real-time control). **4. PROFINET:** L1/L2 (High-speed industrial Ethernet). **5. MQTT:** L3/L4 (Edge-to-Cloud telemetry).

**OT5** — A **Data Diode** is a hardware device that allows data to flow in only one direction (physically impossible to go back). A **Firewall** is software-based and allows two-way communication. Use a **Hardware Diode** for high-security segments where data must leave (e.g., to a cloud historian) but no commands can ever enter.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway $\rightarrow$ Cloud. **Security Boundaries:** Place a firewall/IDMZ between the OT network (L3) and the IT network (L4). The Edge Gateway should reside in the IDMZ.

**OT7** — **Zones:** Logical groupings of assets with similar security requirements. **Conduits:** The communication paths between zones. **Model:** Corporate (Zone 1) $\rightarrow$ IDMZ (Zone 2) $\rightarrow$ SCADA (Zone 3) $\rightarrow$ PLC (Zone 4) $\rightarrow$ SIS (Isolated Zone).

**OT8** — **Strategy:** Implement **VLANs** to segment production lines. Place **Industrial Firewalls** between lines. Use a **Jump Host** in the IDMZ for vendor access. **Transition:** Use "Passive Monitoring" (SPAN/TAP) first to map traffic, then implement rules incrementally to avoid production stops.

**OT9** — **SIS (Safety Instrumented System):** Independent system designed to prevent catastrophic failure. **BPCS (Basic Process Control System):** Mancomes the daily process. **IEC 61511:** Standard for functional safety. **SIS must be isolated** because if a ransomware attack hits the BPCS, the SIS must still function to shut down the plant safely.

**OT10** — **PLC:** Localized, high-speed logic. **DCS:** Distributed, plant-wide process control. **SCADA:** Supervisory, often remote/geographically dispersed. They can coexist; a DCS might manage a specific process while SCADA monitors the whole site.

**OT11** — **Architecture:** Use a **Jump Host** in the IDMZ with **MFA**. All sessions must be **recorded**. Access must be **time-limited** and granted via a "request-approve" workflow. **Direct RDP to HMI** is unacceptable as it bypasses all perimeter controls and exposes the control interface to the IT network.

**OT12** — **Plan:** 1. **Detection:** Use OT-specific IDS to find anomalies. 2. **Inventory:** Identify the compromised asset. 3. **Response:** Isolate the segment via firewall/switch. 4. **Coordination:** Inform the control room immediately. **Operator Role:** The operator's priority is **Safe State** (manual shutdown) over digital forensics.

**OT13** — **HMI:** A visual interface for operators to interact with the process. An **Engineering Workstation** is used for configuring/programming the PLCs/controllers, whereas an HMI is for monitoring/control.

**OT14** — **Historian:** A database that logs time-series process data. **Plant Historian (L3):** Local, high-speed, stores granular data. **Enterprise Historian (L4):** Aggregates data from multiple sites for business analytics.

**OT15** — **Ladder Logic** is a graphical programming language. It is executed by a **PLC**. It remains dominant due to its intuitive, visual nature (mimicking electrical relay diagrams) and its extreme reliability/simplicity.

**OT16** — **RTU (Remote Terminal Unit):** Designed for long-distance, low-power, or harsh environments (e.g., water/oil pipelines). **PLC:** Designed for high-speed, local, high-density logic. RTUs are better for distributed, remote telemetry.

**OT17** — **Analog (4-20mA):** Continuous signal. **Digital:** On/Off. **4-20mA** is preferred because if the wire breaks, the signal drops to **0mA**, allowing the system to detect a "fault" (Live Zero), whereas 0-20mA cannot distinguish between a zero reading and a broken wire.

**OT18** — **Inventory** is the foundation because you cannot protect what you don't know exists. **Passive Monitoring** (sniffing traffic) is safe. **Active Scanning** (sending probes) is **dangerous** because it can crash older, fragile PLC network stacks.

**OT19** — **MITRE ATT&CK for ICS:** Focuses on physical impact. **Tactics:** 1. *Inhibit Response Function*. 2. *Impair Process Control*. 3. *Impair Control*. 4. *Loss of Safety*. 5. *Loss of Availability*. **Difference:** Enterprise ATT&CK focuses on data theft; ICS ATT&CK focuses on physical manipulation.

**OT20** — **Converged SOC:** Use **Passive Network Monitoring** (to avoid crashing PLCs). Integrate logs into a **SIEM** with OT-specific rules (e.g., "New MAC address on PLC network"). **Staffing:** IT analysts handle the network/security; OT engineers handle the process impact. **Unauthorized Firmware Change:** Treat as a critical incident; immediately move to manual/safe mode and isolate the PLC.
