## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because of a conflict between the **Restricted Pod Security Standard (PSS)** and the container image configuration. Under the **Baseline** profile, Kubernetes allows containers to run as root if not explicitly forbidden. However, the **Restricted** profile enforces that `runAsNonRoot: true` must be satisfied. Because the new base image (`chainguard/static`) defaults to `USER root` and the Pod spec does not provide an explicit `runAsUser` (e.g., `runAsUser: 1000`), the Kubelet attempts to start the container as UID 0. The Kubelet checks the `runAsNonRoot` flag, sees the effective UID is 0, and refuses to start the container, resulting in `CrashLoopBackOff`.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -c '.items[] | select(.status.containerStatuses[].state.waiting.reason=="CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level fix:** Rebuild images to include a non-root `USER` directive (e.g., `USER 10001`) in the Dockerfile.
*   **Manifest changes:** Explicitly set `securityContext.runAsUser: 10001` and `securityContext.runAsGroup: 10001` in the Deployment templates.
*   **CI Pipeline Gate:** Implement a `conftest` or `checkov` step in CI that scans Helm charts/manifests for `runAsNonRoot: true` paired with a missing `runAsUser`.
*   **Rollout:** Perform a **RollingUpdate** deployment. Since the pods are in `CrashLoopBackOff`, the deployment controller will attempt to replace them with the new spec. Ensure `maxUnavailable` is set to 0 to maintain capacity during the fix.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is caused by **Asynchronous Replication**. In cross-region setups, the primary sends WAL (Write Ahead Log) records to the replica. There is a non-zero delay (replication lag) between a commit on the primary and its application on the replica. When you promote the replica, any transactions that were in flight but not yet received/applied are lost. To quantify the window, check the `pg_last_xact_replay_timestamp()` on the replica vs. the last commit timestamp on the primary, or monitor `pg_stat_replication` lag metrics.

**SC2-B:**
1.  **Identify:** Find the new ARN of the promoted instance.
2.  **Import:** `terraform import aws_db_instance.promoted_replica <new_arn>`
3.  **Update Code:** Change the hardcoded ARNs in your `.tf` files to the new ARN.
4.  **Detach/Remove:** Remove the old instance resource from code (or use `terraform state rm aws_db_instance.old_instance`).
5.  **Dependency Update:** Update Route53 CNAMEs or RDS Proxy endpoints to point to the new ARN.
6.  **Apply:** `terraform apply` to reconcile the state.

**SC2-C:**
*   **Architecture:** Use **Aurora Global Database**. It uses storage-level replication which is significantly faster and has lower RPO than standard RDS asynchronous streaming.
*   **Connection Management:** Use **RDS Proxy** to handle connection pooling and transparently manage failover/reconnects.
*   **DNS:** Use **Route53 Health Checks** with a CNAME record that points to the current primary; during failover, update the CNAME to the new primary.
*   **App Logic:** Implement exponential backoff retries in the application.
*   **RPO < 1s:** Aurora Global Database provides RPO < 1 second via its dedicated replication protocol.

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Sticky Sessions:** K8s Services are load-balanced. **Solution:** Use an Ingress Controller (NGINX) with `nginx.ingress.kubernetes.io/affinity: "cookie"`.
2.  **Local NFS Mount:** K8s pods are ephemeral. **Solution:** Use a CSI driver for your NFS provider to mount the same volume to all pods.
3.  **Oracle DB:** High-latency/Complex connectivity. **Solution:** Use an ExternalName service or a Service with Endpoints pointing to the Oracle IP.
4.  **IBM MQ:** Stateful/Protocol-specific. **Solution:** Use a dedicated MQ connector/sidecar or ensure the K8s network allows the specific MQ protocol.
5.  **Local Memory Sessions:** **Solution:** Refactor the app to use an external Redis/Memcached for session storage.

**SC4-B:**
```hcl
variable "nfs_server" { type = string }
variable "nfs_path" { type = string }
variable "storage_capacity" { type = string }

resource "kubernetes_csi_storage_class" "nfs_sc" {
  provisioner = "nfs.csi.k8s.io"
  parameters = {
    server = var.nfs_server
    share  = var.nfs_path
  }
}

resource "kubernetes_persistent_volume" "nfs_pv" {
  metadata { name = "nfs-pv" }
  spec {
    capacity = { storage = var.storage_capacity }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source {
      nfs {
        server = var.nfs_server
        path   = var.nfs_path
      }
    }
  }
}

resource "kubernetes_persistent_volume_claim" "nfs_pvc" {
  metadata { name = "nfs-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    resources { requests = { storage = var.storage_capacity } }
    storage_class_name = "nfs-sc"
  }
}
```
*Note: `ReadWriteMany` (RWX) is necessary because multiple pods (replicas of the monolith) need to read/write to the same `/data/uploads` directory simultaneously.*

**SC4-C:**
1.  **Phase 1 (Shadowing):** Deploy the app to K8s. Use the F5 to mirror a percentage of traffic to K8s (read-only). Monitor latency/errors.
2.  **Phase 2 (Canary):** Shift 10% of write traffic to K8s. Use the F5 to route specific paths.
3.  **Phase 3 (Full Cutover):** Move all traffic to K8s.
*   **IBM MQ:** Use a hybrid connectivity model (Direct Connect/VPN) to ensure K8s can reach the mainframe.
*   **Rollback:** If Phase 2 fails, update F5 weights back to 100% Bare Metal.
*   **Metrics:** Error rate < 0.1%, p99 latency < 2s, and DB connection stability.

## SC5 — Mysterious Latency Spike

**SC5-A:**
*   **Approach:** Check Istio `istio_request_duration_milliseconds` (Envoy sidecar) vs. Application logs.
*   **Distributed Tracing:** Use **Jaeger**. If the span for `inventory-service` is long, the issue is the service. If the span between `checkout` and `inventory` is long but the service span is short, the issue is the **Envoy proxy/network**.
*   **Envoy Metrics:** Check `envoy_cluster_upstream_rq_pending_total` (queueing) and `envoy_cluster_upstream_cx_connect_fail`.

**SC5-B:**
**SQL:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid,
       blocked_activity.query AS blocked_query, blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_locks.pid = blocked_activity.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid
WHERE NOT blocked_locks.granted;
```
**Go (Circuit Breaker):**

```go
cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{Name: "inventory-service"})
```

**SC5-C:**

*   **Bulkhead:** Use a dedicated connection pool for the CronJob so it cannot exhaust the API's pool.
*   **K8s:** Use `PodDisruptionBudgets` to ensure a minimum number of serving pods are always available and `ResourceQuotas` to limit the CronJob's CPU/Memory.

## SC6 — Zero-Trust Network Overhaul

**SC6-A:**
Use **SPIFFE/SPIRE** to issue SVIDs (X.509 certificates) to every workload.
*   **Federation:** Use **SPIRE Federation**. The AWS SPIRE server and On-prem SPIRE server exchange trust bundles. A workload in AWS presents its SVID; the on-prem service validates it against the federated trust bundle.
*   **Cloud Integration:** Map SPIFFE IDs to AWS IAM Roles via **IAM Roles for Service Accounts (IRSA)** and Azure Managed Identities.

**SC6-B:**
```hcl
resource "aws_transit_gateway" "main" { ... }

resource "aws_vpc" "prod" {
  cidr_block = "10.0.0.0/16"
  # No public subnets
}

variable "private_link_services" { type = list(string) }

resource "aws_vpc_endpoint" "endpoints" {
  for_each = toset(var.private_link_services)
  vpc_id   = aws_vpc.prod.id
  service_name = each.value
  vpc_endpoint_type = "Interface"
  subnet_ids = [aws_subnet.private.id]
}

resource "aws_security_group" "deny_all" {
  ingress { from_port = 0; to_port = 0; protocol = "-1"; cidr_blocks = [] } # Default Deny
}
```

**SC6-C:**
*   **Direct Connect:** Highest bandwidth, lowest latency, most expensive. Best for massive data.
*   **Second VPN + ECMP:** Cheaper, provides redundancy, but higher latency/jitter than DX.
*   **Hybrid Mesh (Tailscale):** Easiest to manage, uses WireGuard, but adds overhead.
*   **Recommendation:** For a Zero-Trust model, **Direct Connect** combined with a **Service Mesh (Cilium/Istio)** is best. It provides a private, high-speed path while the mesh handles the identity-based encryption.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
1.  **Manual Apply:** Bypasses CI/CD, creating "shadow" infrastructure.
2.  **Helm Divergence:** Makes environments non-reproducible.
3.  **kubectl edit:** Causes "Configuration Drift" where the source of truth (Git) is no longer accurate.
*   **Risks:** Running `tofu apply` without locking can lead to **State Corruption** or race conditions where two processes attempt to modify the same resource, leading to partial/broken infrastructure.

**SC7-B:**
```yaml
stages:
  - validate
  - plan
  - apply

validate:
  stage: validate
  script:
    - tofu fmt -check
    - tofu validate

plan:
  stage: plan
  script:
    - tofu plan -out=tfplan
    - tofu plan -attach-to-mr # Pseudo-code for MR comment
  artifacts:
    paths: [tfplan]

apply_prod:
  stage: apply
  script:
    - tofu apply tfplan
  when: manual
  environment: production
```
*Note: Use `backend "s3" { dynamodb_table = "terraform-lock" }` in the configuration.*

**SC7-C:**
*   **Drift Detection:** Schedule a GitLab CI job to run `tofu plan -detailed-exitcode` every hour.
*   **Admission Control:** Use **OPA Gatekeeper** to reject `kubectl edit` on specific `kind: ConfigMap` if they don't match a specific label.
*   **Structure:** Use **Kustomize** to have a `base/` directory and `overlays/prod/` for environment-specific overrides.
*   **RBAC:** In AWS, restrict `s3:PutObject` on the state bucket to the CI Service Account. In K8s, remove `edit` permissions from all users, leaving only `get/list/watch`.

```python
# DRF Object-level permission
from rest_framework import permissions

class IsOwnerOrReadOnly(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
```

## SC10 — Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Active-Passive (Velero):** RTO is high (time to restore 200TB). RPO is 15m (if backups are frequent).
*   **Active-Active (Cilium Mesh):** RTO is near zero. RPO depends on replication.
*   **Replication Strategy:**
    *   **PostgreSQL:** Patroni with synchronous replication (for RPO=0) or asynchronous (for performance).
    *   **Redis:** Redis Sentinel with cross-region replication.
    *   **MinIO:** MinIO Site Replication (Bucket Replication).

**SC10-B:**
```yaml
- name: configure_patroni
  hosts: db_nodes
  tasks:
    - name: Install Patroni
      apt: name=patroni state=present
    - name: Template Patroni Config
      template:
        src: patroni.yml.j2
        dest: /etc/patroni/patroni.yml
      notify: restart_patroni

  handlers:
    - name: restart_patroni
      service: name=patroni state=restarted
```
*(In `patroni.yml`, set `synchronous_commit: on` and `synchronous_standby_names: '*'` to ensure zero data loss).*

**SC10-C:**
1.  **Detection:** Use a quorum-based monitor (e.g., Consul or a 3rd party health checker).
2.  **Sequence:**
    *   Detect Chicago failure $\rightarrow$ Route53/GSLB updates to Dallas $\rightarrow$ Patroni promotes Dallas $\rightarrow$ Redis Sentinel promotes Dallas $\rightarrow$ MinIO syncs remaining bits.
3.  **Split-Brain:** Use a "Tie-breaker" node in a 3rd region or a strict quorum requirement in etcd.
4.  **Failback:** Once Chicago is up, it must join as a **Replica** first, sync all data, and only then be promoted back to Primary via a controlled switchover.
