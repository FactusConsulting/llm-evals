## OpenTofu / Terraform

**T1** — `tofu plan` is a "dry run" that performs a refresh of the state and compares it against the current configuration to show what actions (create, update, destroy) will be taken. `tofu apply` executes those planned actions to reach the desired state.

**T2** — State is a JSON file mapping your configuration to real-world resources. Remote state is stored in a shared backend (like S3 or Consul), which is critical for team collaboration to ensure a single source of truth and to prevent state corruption via file locking.

**T3** — `count` uses an integer index (0, 1, 2...), making it risky when removing items from the middle of a list (it causes shifts/recreations). `for_each` uses a map or set of strings, making it stable because resources are identified by unique keys rather than indices. Use `for_each` for collections of varying items.

**T4** — OpenTofu detects this during the "refresh" phase of a `plan`. It compares the real-world API response with the state file. If they differ, it marks the resource as "drifted" and proposes changes in the plan to reconcile the state.

**T5**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-xxxxxx"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6** — `terraform_remote_state` reads the state file of another workspace. Output values are the mechanism by which a module exposes data. The recommended alternative is to use **Data Sources** to query existing infrastructure or to pass outputs directly between modules in a single root configuration to avoid the tight coupling and security risks of reading raw state files.

**T7** — The `null_resource` output is only populated *after* the provisioner completes. If a dependent resource tries to read that output during the same apply cycle before the provisioner finishes, it receives an empty value. **Fix:** Ensure the dependent resource has an explicit `depends_on = [null_resource.example]` to force correct ordering.

**T8** — `tofu import` is a CLI command to bring existing infra into state. Its limitation is that it is imperative and manual. The `import` block (introduced in 1.5+) is **declarative**: you define the resource in your code first, and OpenTofu handles the mapping during `plan/apply`, making it easier to manage via version control and CI/CD.

**T9** — A `variable` is an input parameter used to customize a module. An `output` is a value exported by a module to be used by other modules or the CLI.

**T10** — A provider is a plugin that translates OpenTofu code into API calls (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, it will fail because the provider binaries have not been downloaded to the `.terraform` directory.

**T11** — The `.terraform.lock.hcl` file records the specific versions and hashes of providers used. It should be committed to version control to ensure "reproducible builds," meaning every engineer and CI runner uses the exact same provider versions.

**T12** — `tofu destroy` removes all resources managed by the current state. To target a single resource: `tofu destroy -target=aws_instance.web_server`.

**T13** — A data source is a read-only operation to fetch information from the provider. **Example:** Using `data "aws_vpc" "selected" {}` to get the ID of an existing VPC that was created outside of your current OpenTofu project.

**T14** — `variable` blocks are for external inputs (user-provided). `locals` are for internal, derived values (logic/constants). Use `locals` when you need to perform string manipulation or complex logic that shouldn't be exposed as an input to the module.

**T15** — Inside a `lifecycle` block:
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
- `prevent_destroy`: Prevents accidental deletion of critical resources (e.g., a production DB).
- `ignore_changes`: Tells OpenTofu to ignore specific attributes (e.g., tags added by an external process) during updates.

**T16** — The `moved` block allows you to rename a resource or move it into a module within your code. It tells OpenTofu: "The resource previously at `address_a` is now at `address_b`," preventing the destruction and recreation of the actual physical resource.

**T17** — The dependency graph is built by analyzing resource references. **Implicit** dependencies occur when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit** dependencies use `depends_on`. `depends_on` forces a sequence but breaks parallelism, slowing down the graph. Use it sparingly to avoid creating a "bottleneck" where everything waits for one resource.

**T18** — 
1. **Increase Parallelism:** Use `-parallelism=n` (higher `n` speeds up independent resources but risks API rate limiting).
2. **State Splitting:** Break a monolithic state into smaller, decoupled state files (reduces the graph size per run).
3. **Targeted Refreshes:** Use `-refresh=false` (skips API calls for all resources, significantly faster, but risks acting on stale data).
4. **Reduce Provider Calls:** Use `data` sources or `locals` to avoid deep nesting of resource dependencies.

**T19** — State locking prevents two users from running `apply` simultaneously. If a crash occurs, a `.lock` file remains in the backend. You can break it with `tofu force-unlock <LOCK_ID>`. **Risk:** If you unlock while another process is actually writing, you will corrupt the state file.

**T20** — 
1. Copy your current `terraform.tfstate` to a backup.
2. Update your backend configuration block to point to S3 and DynamoDB.
3. Run `tofu init`. OpenTofu will detect the change and ask to migrate the state.
4. Run `tofu init -migrate-state`.
5. Run `tofu plan` to ensure the state is identical.
6. Verify by checking the S3 bucket for the `.tfstate` file and the DynamoDB table for the lock entry.

## Ansible

**A1** — A **Task** is a single action; a **Role** is a structured collection of tasks, variables, and files; a **Playbook** is the orchestration file that maps hosts to roles/tasks.

**A2** — `ansible_facts` is a dictionary of system information. Access the OS family via `ansible_facts['os_family']`.

**A3** — `command` runs a command without a shell environment (fast/safe). `shell` runs via `/bin/sh` (allows pipes/redirects). `raw` sends a command via SSH without requiring Python on the target (used for bootstrapping).

**A4** — Idempotency means running a task multiple times results in the same state. 
- **Idempotent:** `apt: name=nginx state=present` (only installs if missing).
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file` (appends every time).

**A5**
```yaml
- name: Install web tools
  package:
    name: "{{ (ansible_os_family == 'Debian') | ternary('htop', 'epel-release,htop') }}"
    state: present
```

**A6** — (Lowest to Highest): `role defaults` < `group_vars` < `host_vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process in batches of 3. To ensure the first 3 finish before the rest, you can use a `wait_for` task or a `block` with a `pause` to ensure the cluster is ready before the next batch starts.

**A8** — `ansible-vault` encrypts files. To encrypt a single variable, use `ansible-vault encrypt_string 'my_secret_password' --name 'db_password'`.

**A9** — An **Inventory** is a list of managed hosts. **Static** is a hardcoded file; **Dynamic** uses a script or plugin to query a cloud provider (e.g., AWS EC2) for the current list of hosts.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **Handler** is a special task that only runs if a task notifies it via the `notify` keyword. It only runs at the end of a play if a task reports a `changed` status.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory`, `remote_user`, and `forks`.

**A13** — `register` saves the output of a task into a variable. You can then use `when: my_var.rc == 0` to check the return code.

**A14** — `import_tasks` is static (processed when the playbook is parsed). `include_tasks` is dynamic (processed at runtime). `include_tasks` allows for conditional logic (e.g., `when` on the include itself), whereas `import_tasks` evaluates conditions on every task inside the file.

**A15** — **Ansible Galaxy** is a public hub for roles/collections. Use a `requirements.yml` file containing `roles:` or `collections:` and run `ansible-galaxy install -r requirements.yml`.

**A16** — `ssh` is the default (uses SSH). `local` runs tasks on the control node. `network_cli` is used for network devices (switches/routers) that don't support Python.

**A17** — `delegate_to` runs a task on a different host. `run_once` ensures a task runs only once per play. 
**Example:**
```yaml
- name: Get local info
  shell: uptime
  register: uptime_out
  delegate_to: localhost
  run_once: true
```

**A18** — 
1. **Forks:** Increase `forks` in `ansible.cfg` to run more tasks in parallel.
2. **Pipelining:** Enable `pipelining = True` to reduce SSH connections.
3. **Fact Caching:** Use a Redis/JSON cache to avoid re-gathering facts every time.
4. **Mitogen:** Use the Mitogen strategy plugin to significantly speed up execution via optimized SSH multiplexing.

**A19** — `{{ }}` is for expressions; `{% %}` is for logic (loops/ifs); `{# #}` is for comments.
```jinja2
upstream backend_servers {
{% for server in backend_list %}
    server {{ server.ip }}; # Health check: {{ server.status }}
{% endfor %}
}
```

**A20** — 
1. Set `serial: 1` (or a small batch).
2. **Pre-task:** Use `uri` to remove the current server from the Load Balancer.
3. **Task:** Update the application code.
4. **Post-task:** Use `uri` to perform a health check on the local server.
5. **Rollback:** Wrap the deployment in a `block`. If a task fails, the `rescue` block triggers, which uses `uri` to re-add the old version and notifies the LB.
