## Cloud Infrastructure Architecture

**CL1** — **IaaS** (Infrastructure as a Service) provides raw computing resources (VMs, storage, networks); e.g., AWS EC2. **PaaS** (Platform as a Service) provides a framework for developers to build/deploy apps without managing underlying OS/hardware; e.g., Azure App Service. **SaaS** (Software as a Service) provides a complete software product managed by the provider; e.g., Google Workspace.

**CL2** — The provider is responsible for the security *of* the cloud (physical, hardware, hypervisor). The user is responsible for security *in* the cloud (data, OS, config). 
* **IaaS VMs:** Provider handles hardware/hypervisor; User handles OS, patching, and apps. 
* **Managed Kubernetes:** Provider handles Control Plane; User handles Pods, data, and node configurations. 
* **SaaS (M365):** Provider handles almost everything; User handles identity and data access.

**CL3** — A **VPC** is a private virtual network. A **Subnet** is a range of IP addresses within a VPC. A **Security Group (SG)** is a stateful firewall at the instance level. A **NACL** is a stateless firewall at the subnet level. They layer as: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group $\rightarrow$ Instance. **Stateful** (SG) remembers connection states (allows return traffic automatically); **Stateless** (NACL) requires explicit rules for both inbound and outbound traffic.

**CL4** — A **Landing Zone** is a pre-configured, multi-account environment. **Organizational Units (OUs)** group accounts by function (e.g., Prod, Dev). **Guardrails** (Service Control Policies) enforce security boundaries. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes traffic between VPCs. A **single-account approach** is problematic due to limited service quotas, increased blast radius during breaches, and lack of environment isolation.

**CL5** — **IaC** is managing infrastructure via machine-readable files. 
* **Terraform/OpenTofu:** Provider-agnostic, uses HCL, stateful. Best for multi-cloud.
* **Pulumi:** Uses general-purpose languages (Python, TS). Best for dev-centric teams.
* **CloudFormation/Bicep:** Cloud-native (AWS/Azure). Best for deep integration with a single provider.
* **Crossplane:** K8s-native; manages cloud resources via K8s CRDs. Best for K8s-centric infrastructure.

**CL6** — **HPA** scales Pods based on CPU/RAM. **VPA** adjusts Pod resource requests/limits. **Cluster Autoscaler** adds/removes Nodes. **KEDA** is event-driven (e.g., scales based on Kafka lag). Use **KEDA** when scaling needs to be triggered by external metrics rather than just resource utilization.

**CL7** — **RPO** (Recovery Point Objective) is max data loss; **RTO** (Recovery Time Objective) is max downtime. **Active-Active** (both regions live, zero RTO) is most expensive. **Active-Passive** (one standby) is cheaper. **Sync replication** (no data loss, high latency) vs. **Async** (low latency, potential loss). **DNS (Route53/Traffic Manager)** handles failover. 
* **Pilot Light:** Minimal core services running. 
* **Warm Standby:** Scaled-down version of full environment. 
* **Multi-site Active-Active:** Full capacity in both regions.

**CL8** — **GitOps** uses Git as the single source of truth for state. **ArgoCD** and **FluxCD** are both pull-based controllers that sync Git to K8s. **Secrets** are handled via **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault/AWS SM), or **Vault**. If a manual change occurs, the GitOps controller detects the **drift** and automatically reverts the cluster to match the Git state.

**CL9** — Use a **StatefulSet** for stable network IDs and ordered startup. Use **PV/PVC** with a **Local Storage Class** for low latency. Use a **Headless Service** to allow direct Pod IP addressing. Use **Init Containers** to prepare the filesystem/config files. Mount **ConfigMaps** as volumes for specific paths. Implement a **Pod Disruption Budget (PDB)** to ensure a minimum number of pods remain available during maintenance.

**CL10** — **Service Account** is a K8s-native identity. **Workload Identity** is the cloud-native mapping of K8s identities to cloud roles. **IRSA** is the AWS implementation. Mounting long-lived credentials (JSON keys) in a Pod is bad because they can be stolen. **Workload Identity Federation** uses OIDC to exchange a short-lived K8s token for a cloud IAM role, eliminating static secrets.

**CL11** — **Object (S3/Blob):** Unstructured data, high durability (11 nines), accessed via API. **Block (EBS/Managed Disk):** High-performance, attached to a single VM, used for OS/DBs. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB) accessible by multiple instances. Use Object for backups/media, Block for databases, and File for shared configuration/home directories.

**CL12** — **Zero-Trust** assumes no implicit trust. **Architecture:** Use **Network Policies** (L3/L4 isolation), **Service Mesh** (mTLS for L7 identity), **Pod Identity** (Workload identity), **Admission Controllers** (OPA/Kyverno for policy), **Image Signing** (Cosign), and **Runtime Security** (Falco for anomaly detection). Unlike perimeter security (which trusts the "inside"), Zero-Trust verifies every request regardless of origin.

**CL13** — A **CDN** caches content at edge locations closer to users to reduce latency. Services: **AWS CloudFront**, **Azure Front Door**. Use a CDN for static assets (images, JS) or global content delivery; serve directly from origin only when content is highly dynamic or unique to a single user.

**CL14** — **Regions** are geographic areas; **Availability Zones (AZs)** are isolated data centers within a region. Deploy across multiple AZs to protect against a single data center failure. **Zonal** resources live in one AZ; **Regional** resources (like S3) are replicated across the entire region.

**CL15** — A **Managed Database** (RDS/Cloud SQL) handles patching, backups, high availability, and hardware provisioning. On a **VM**, you must manually manage the OS, DB engine, backups, and scaling.

**CL16** — **IAM Users** (individuals), **Groups** (collections of users), **Roles** (temporary identities), and **Policies** (permission definitions). **Least Privilege** means granting only the minimum permissions required to perform a task, applied via granular IAM policies.

**CL17** — **Serverless** is event-driven compute without server management. **Lambda/Functions** scale automatically. **Cold Starts** are the latency experienced when a function is invoked after being idle (initializing the runtime). Serverless is a poor fit for long-running, high-compute, or highly predictable, constant-load workloads.

**CL18** — **Ingress** is a K8s resource for L7 routing. **Gateway API** is the modern, role-oriented evolution of Ingress. **Cloud LB** handles L4/L7 at the infrastructure level. **Service Mesh Ingress** handles L7/mTLS. **TLS termination** happens at the LB or Ingress Controller. Use **Gateway API** for complex, multi-tenant environments requiring better separation of concerns between infrastructure and application teams.

**CL19** — Use **Reserved Instances/Savings Plans** for predictable loads; **Spot/Preemptible** for fault-tolerant/batch jobs. **Right-sizing** ensures instances match actual usage. **Storage Tiering** moves old data to Archive (Glacier). **FinOps** involves using tools like **AWS Cost Explorer** or **CloudHealth** to implement **showback** (reporting costs to teams) or **chargeback** (billing teams directly).

**CL20** — Use **Kubernetes** as an abstraction layer and **Terraform** for IaC. Use **VPN/Interconnect** for networking. **Identity Federation** (OIDC) links cloud identities. **Multi-cloud** is justified for extreme high availability or regulatory compliance, but it adds significant complexity in networking, egress costs, and operational overhead.

## OT Infrastructure Architecture

**OT1** — The **Purdue Model** organizes industrial systems: **L0** (Physical process/sensors), **L1** (PLCs/Controllers), **L2** (SCADA/HMI), **L3** (Site operations/Historian), **L4** (Business/ERP), **L5** (Enterprise).

**OT2** — **IT** focuses on data confidentiality; **OT** focuses on safety and availability. You cannot apply standard IT patching to OT because unexpected reboots or latency can cause physical damage or safety hazards in real-time processes.

**OT3** — An **IDMZ** acts as a buffer between L3 and L4. Only specific, inspected traffic (e.g., Historian data sync) should cross. Traffic should generally flow **outbound** from OT to IT. Direct L4-to-L1 connectivity is dangerous as it bypasses all security controls and safety layers.

**OT4** — 1. **Modbus TCP** (L1/L2), 2. **OPC UA** (L2/L3), 3. **EtherNet/IP** (L1/L2), 4. **PROFINET** (L1), 5. **MQTT** (L3/L4/Cloud).

**OT5** — A **Data Diode** is a hardware device that physically allows data to flow in only one direction. A **Firewall** is software-based and bidirectional. Use a **Data Diode** for high-security air-gaps where physical impossibility of reverse flow is required.

**OT6** — **Flow:** Sensor $\rightarrow$ PLC (L1) $\rightarrow$ SCADA (L2) $\rightarrow$ Historian (L3) $\rightarrow$ Edge Gateway (L3/L4) $\rightarrow$ Cloud. Security boundaries should be placed at the **IDMZ** between L3 and L4.

**OT7** — A **Zone** is a group of assets with similar security requirements. A **Conduit** is the communication path between zones. **Model:** Corporate (L4) $\rightarrow$ IDMZ $\rightarrow$ Engineering (L3) $\rightarrow$ SCADA (L2) $\rightarrow$ PLC (L1). **SIS** should be in its own isolated zone.

**OT8** — Use **VLANs** to segment production lines. Place a **Firewall** between L3 and L2. Use a **Jump Host** for remote access. To transition without stopping production, use **Passive Monitoring** first to map traffic, then implement rules in "log-only" mode before enforcing.

**OT9** — **SIS** (Safety Instrumented System) is for emergency shutdown; **BPCS** (Basic Process Control System) is for normal operations. **IEC 61511** governs functional safety. SIS must be isolated because if a ransomware attack reaches the SIS, it could disable the safety shutdown, leading to catastrophic physical failure.

**OT10** — **PLC** (Single device/logic), **DCS** (Distributed, plant-wide control), **SCADA** (Supervisory, wide-area). They can coexist: PLCs are the components within a DCS or SCADA system.

**OT11** — Use **Jump Hosts** with **MFA** and **Session Recording**. Access must be **time-limited** and strictly audited. Direct RDP to an HMI is unacceptable as it exposes the control interface to the entire network.

**OT12** — **Plan:** Deploy **IDS** for anomaly detection; perform **Asset Inventory** to find unauthorized devices; **Isolate** the L3 network; **Coordinate** with the control room to ensure the process remains in a "safe state." The **Plant Operator** must be involved to manually manage the physical process if digital controls are compromised.

**OT13** — An **HMI** is a visual interface for operators to interact with the process. An **Engineering Workstation** is used for programming and configuring the PLCs/controllers.

**OT14** — A **Historian** records time-series process data. A **Plant Historian (L3)** is for real-time local operations; an **Enterprise Historian (L4)** is for aggregated business analytics.

**OT15** — **Ladder Logic** is a graphical programming language executed by a **PLC**. It remains dominant because it is intuitive for electrical engineers and highly deterministic for real-time logic.

**OT16** — An **RTU** (Remote Terminal Unit) is used for long-distance telemetry (e.g., water/oil pipelines) in remote environments; a **PLC** is used for high-speed, local factory floor control.

**OT17** — **Analog** (continuous) vs. **Digital** (on/off). **4-20mA** is preferred because the 4mA "live zero" allows the system to detect a wire break (if signal drops to 0mA).

**OT18** — **Asset Inventory** is the foundation of OT security. Use **Passive Monitoring** (listening to traffic) to avoid disruption. **Active Scanning** is dangerous because it can crash sensitive, legacy OT devices.

**OT19** — **MITRE ATT&CK for ICS** focuses on physical impact. **Tactics:** Impair Process Control, Inhibit Response Function, etc. It differs from Enterprise by focusing on the physical consequences of cyber actions. Use it to map gaps in your physical safety/control layers.

**OT20** — **SOC Design:** Collect logs via **Passive Taps** to avoid impacting real-time traffic. Integrate into a **SIEM** with OT-specific rules. **Staffing** requires both IT security analysts and OT engineers. An **unauthorized firmware change** on a PLC is a critical alert requiring immediate physical verification and isolation.
