## Application Architecture

**AA1** — A **monolith** is a single, unified deployment unit where all components share memory and resources. **Microservices** decompose the application into independent, loosely coupled services. 
*Three problems introduced by microservices:* 1. Network latency/reliability (inter-service calls), 2. Distributed data consistency (no global ACID transactions), 3. Operational complexity (observability, service discovery, and deployment overhead).

**AA2** — **Synchronous** communication requires the caller to wait for a response before proceeding (e.g., **HTTP/REST**). **Asynchronous** communication allows the caller to continue immediately, handling the response later (e.g., **RabbitMQ/Message Queues**).

**AA3** — A **reverse proxy** sits in front of servers to handle load balancing and SSL termination. An **API Gateway** adds application-level logic: rate limiting, authentication, and request routing. An API Gateway can replace a reverse proxy, but in high-scale architectures, they are often layered (Proxy for L4/L7 traffic, Gateway for business logic).

**AA4** — The **Saga pattern** manages distributed transactions via a sequence of local transactions. 
*   **Choreography:** Decentralized; services emit events, and others react (best for simple workflows). 
*   **Orchestration:** Centralized; a "manager" service tells others what to do (best for complex, multi-step workflows).

**AA5** — **CQRS** separates the data models for reading (Query) from writing (Command). It is paired with **Event Sourcing** (storing state as a sequence of immutable events) because CQRS allows the "Read" model to be a highly optimized projection of the event log. This solves the "impedance mismatch" where a single model cannot efficiently handle both complex writes and high-volume, diverse reads.

**AA6** — The **Circuit Breaker** prevents a service from repeatedly trying an operation that is likely to fail. 
*   **States:** **Closed** (normal), **Open** (failing, requests blocked), **Half-Open** (testing if the service recovered). 
*   **Difference:** A **retry** handles transient blips; a **circuit breaker** handles sustained outages to prevent cascading failure. Use both together: Retry for a single failed request, but trip the Circuit Breaker if retries consistently fail.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, lowest security, highest noisy-neighbor risk (one tenant can hog DB resources).
2. **Shared DB/Separate Schema:** Medium cost/complexity; provides logical isolation.
3. **Separate DB:** Highest cost, highest security, lowest noisy-neighbor risk (physical isolation).

**AA8** — **Strong consistency** ensures all reads return the latest write; **eventual consistency** allows temporary divergence. 
*   **Inventory Architecture:** Use **Strong Consistency**. 
*   **Data Store:** A relational database (e.g., **PostgreSQL**) with ACID compliance. 
*   **Pattern:** Use **Pessimistic Locking** or a distributed lock (e.g., **Redis/Etcd**) during the transaction to prevent race conditions.

**AA9** — A **sidecar** is a helper container running alongside the app container. In **Istio**, **Envoy** acts as the sidecar proxy. 
*   **Data Plane:** The Envoy proxies handling actual traffic. 
*   **Control Plane:** Istio (istiod) managing configuration and policy. 
*   **mTLS:** Solves identity and encryption at the transport layer without requiring the application to manage certificates or handle handshake logic.

**AA10** — The **Strangler Fig** pattern involves placing a proxy/gateway in front of the monolith. 
*   **Strategy:** 1. Identify a bounded context (e.g., "Billing"). 2. Build the new service in **.NET 8**. 3. Route "Billing" traffic via the proxy to the new service. 4. Repeat for other modules until the monolith is "strangled" and can be decommissioned.

**AA11** — The **12-Factor App** ensures cloud-native portability. 
1. **Codebase:** One repo per app. 2. **Dependencies:** Explicitly declare/isolate. 3. **Config:** Store in environment variables. 4. **Backing Services:** Treat DBs/Queues as attached resources. 5. **Processes:** Stateless and ephemeral. 6. **Disposability:** Fast startup/graceful shutdown.

**AA12** — 
*   **Kafka (Event-driven):** High decoupling, massive scale, complex debugging (asynchronous), high ordering guarantees (within partitions), complex failure handling (retries/DLQs). 
*   **REST/gRPC (Request-driven):** Tight coupling, lower scale, easy debugging (synchronous), strict ordering, simpler failure handling. 
*   **Choice:** Use Kafka for high-throughput stream processing; REST/gRPC for real-time user-facing interactions.

**AA13** — A **load balancer** distributes traffic across multiple servers. 
*   **Layer 4:** Operates at the transport layer (TCP/UDP); fast, no inspection of payload. 
*   **Layer 7:** Operates at the application layer (HTTP); can route based on URL, headers, or cookies. 
*   **Use Case:** Routing `/api/v1` to one cluster and `/api/v2` to another.

**AA14** — A **Message Queue** (RabbitMQ) is designed for task distribution; once a message is consumed, it is deleted. A **Log-based Broker** (Kafka) is a persistent append-only log; messages stay after consumption. 
*   **Pick MQ** for worker queues/task processing. 
*   **Pick Kafka** for event streaming/replayability/analytics.

**AA15** — A **container** shares the host OS kernel, making it lightweight and fast. A **VM** includes a full guest OS and a hypervisor. Containers are popular because they offer high density, rapid startup, and consistent environments.

**AA16** — **Stateless** services do not store client data locally (e.g., a calculator API). **Stateful** services maintain data between requests (e.g., a database). Stateless services scale horizontally easily because any instance can handle any request without needing to sync local state.

**AA17** — An **ORM** maps code objects to database tables. 
*   **Examples:** **Entity Framework** (.NET), **Hibernate** (Java). 
*   **Trade-offs:** ORMs increase developer productivity but can introduce performance overhead and "N+1" query problems compared to optimized raw SQL.

**AA18** — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function. 
*   **Implementation:** Use separate **thread pools** for different downstream service calls. If Service A hangs, its thread pool fills up, but Service B's thread pool remains available.

**AA19** — **OT (Operational Transformation)** requires a central server to resolve conflicts by transforming operations. **CRDTs** allow mathematical convergence without a central authority. 
*   **Choice for Offline:** **CRDTs** are superior for offline editing because they allow local changes to be merged deterministically once connectivity is restored without needing a central coordinator to "re-base" every operation.

**AA20** — **Distributed Tracing** tracks a request across services. 
*   **Context Propagation:** Passing IDs (W3C Trace Context/B3) through headers. 
*   **Sampling:** **Head-based** (decide at start) vs **Tail-based** (decide after the trace completes, e.g., keep only errors). 
*   **Kafka:** To ensure continuity, the producer must inject trace headers into the Kafka message headers, which the consumer then extracts to continue the span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., **ESXi, Xen**). **Type 2 (Hosted):** Runs on an OS (e.g., **VirtualBox, VMware Workstation**).

**OP2** — **SAN (Storage Area Network):** Block-level storage, high-speed, used for databases (Protocols: **Fibre Channel, iSCSI**). **NAS (Network Attached Storage):** File-level storage, used for shared files (Protocols: **NFS, SMB**).

**OP3** — **3-tier:** Core $\rightarrow$ Distribution $\rightarrow$ Access. **Leaf-Spine:** A two-layer fabric where every Leaf connects to every Spine. Leaf-Spine is preferred in modern DCs because it provides predictable latency and high bandwidth for "East-West" (server-to-server) traffic.

**OP4** — **Architecture:** 3+ nodes for quorum. **Storage:** Ceph (distributed) or iSCSI (centralized). **Fencing:** Use **STONITH** (Shoot The Other Node In The Head) to power off a failed node. **Failure:** If a node fails, the cluster loses quorum/heartbeat; the fencing agent kills the node, and the remaining nodes restart the VMs on healthy nodes.

**OP5** — **VLAN Trunking** allows multiple VLANs over one link using **802.1Q** tags. On Linux, configure this via sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — **RAID 1** (Mirror), **5** (Parity, 1 drive loss), **6** (Double parity, 2 drives loss), **10** (Striped Mirror), **Z2** (ZFS double parity). 
*   **Choice for DB:** **RAID 10**. It provides the best balance of high IOPS (performance) and redundancy (fault tolerance).

**OP7** — **Architecture:** Internal AD handles local auth. **Split-horizon:** Internal users get internal IPs; external users get public IPs for the same domain. **DMZ:** Hosts public services. **DNSSEC** signs zones to prevent spoofing. **Movement:** When moving from Office to VPN, the client uses the VPN's DNS resolvers (conditional forwarding) to reach internal resources.

**OP8** — **Chain:** Root CA (Offline/Self-signed) $\rightarrow$ Subordinate CA (Online/Issuing) $\rightarrow$ End-entity. **Revocation:** **CRL** (list of revoked certs) or **OCSP** (real-time check). **Compromise:** A compromised Subordinate CA can be revoked by the Root; a compromised Root CA requires rebuilding the entire trust anchor for the organization.

**OP9** — **MPLS:** High cost, high reliability. **IPsec:** Low cost, variable reliability. **SD-WAN:** Intelligent routing over multiple links. **WireGuard:** Fast, modern mesh. 
*   **Recommendation:** **SD-WAN** with a mix of MPLS (for VoIP priority) and Internet (for general traffic) provides the best balance of cost and latency management.

**OP10** — **iDRAC/iLO/IPMI** are out-of-band management interfaces. They are critical for remote power cycling/recovery. If exposed to the internet, an attacker can gain full hardware-level control of your servers.

**OP11** — **LVM:** Logical volume management. **LVM-Thin:** Space-efficient, uses snapshots/thin provisioning. **ZFS:** Integrated filesystem/volume manager with Copy-on-Write. 
*   **Snapshots:** LVM/LVM-Thin use pointers; ZFS uses CoW (Copy-on-Write) which is highly efficient for data integrity.

**OP12** — **Strategy:** A **Stretch Cluster** across two sites. **Ceph:** Requires a "witness" node in a 3rd site to prevent **Split-Brain** (where both sites think they are the master). 2-site Ceph is dangerous because if the link breaks, both sides might try to claim ownership, causing data corruption.

**OP13** — **DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge. If the server is unavailable and the lease expires, the client assigns itself an **APIPA** address (169.254.x.x).

**OP14** — **Managed switches** allow VLANs, SNMP, Spanning Tree, and Port Security. **Unmanaged** are "dumb" plug-and-play devices. Managed switches are essential for enterprise security and traffic segmentation.

**OP15** — **NTP** synchronizes clocks. Clock drift causes authentication failures (Kerberos), broken logs, and database replication errors in distributed systems.

**OP16** — **Physical:** Hardware. **VM:** Virtualized hardware. **Container:** Virtualized OS. Run workloads on **Bare Metal** for high-performance/low-latency needs (e.g., high-frequency trading or massive databases) to avoid hypervisor overhead.

**OP17** — **UPS** provides short-term battery power for graceful shutdowns. **Generator** provides long-term power. An **ATS (Automatic Transfer Switch)** detects power loss and switches the load from the utility to the generator.

**OP18** — **Active-Passive:** One node is standby. **Active-Active:** Both handle traffic. 
*   **HA Implementation:** Use **Pacemaker** to manage a **Virtual IP (VIP)**. If the primary node fails, Corosync detects it, Pacemaker triggers **STONITH** to kill the failed node, and moves the VIP to the secondary node.

**OP19** — **3-2-1 Rule:** 3 copies, 2 different media, 1 offsite. 
*   **RPO (Recovery Point Objective):** Max tolerable data loss. 
*   **RTO (Recovery Time Objective):** Max tolerable downtime. 
*   **Immutable Backups:** Essential for ransomware protection. 
*   **Backup vs DR:** Backup is the *data*; Disaster Recovery is the *process* of restoring operations.

**OP20** — **802.1X:** **Supplicant** (client), **Authenticator** (switch), **Auth Server** (RADIUS). **EAP-TLS** uses certificates; **PEAP** uses passwords. **Dynamic VLAN assignment** places users in specific VLANs based on RADIUS attributes. **MAB (MAC Authentication Bypass)** allows non-802.1X devices (like printers) to connect based on their MAC address.
