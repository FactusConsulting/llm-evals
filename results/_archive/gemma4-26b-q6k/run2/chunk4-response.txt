## OpenTofu / Terraform

**T1** — `tofu plan` creates an execution plan by comparing the current state against the desired configuration, showing what will be added, changed, or destroyed without making changes. `tofu apply` executes that plan to reach the desired state.

**T2** — State is a JSON file that maps real-world resources to your configuration. Remote state is critical for team collaboration (shared source of truth), security (storing sensitive data outside local machines), and state locking (preventing concurrent modifications).

**T3** — `count` uses an integer index, making it difficult to remove items from the middle of a list without shifting indices. `for_each` uses a map or set of strings, allowing you to add/remove specific keys without affecting others. `for_each` is preferred when managing resources that have unique identifiers.

**T4** — This is "configuration drift." During the next `plan`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy between the real-world resource and the state file, then proposes changes to bring the resource back in line with the configuration.

**T5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

**T6** — `terraform_remote_state` reads the entire state file of another module, which can be a security risk (exposing all data) and creates tight coupling. The recommended alternative is using **Outputs** from the source module and passing them as **Inputs** to the consumer module, or using a dedicated service discovery mechanism.

**T7** — The `null_resource` and its provisioner run during the "apply" phase, but the output value is often calculated before the provisioner completes or the resource is fully "ready" in the eyes of the provider. To fix, ensure the dependent resource has an explicit `depends_on = [null_resource.example]` and ensure the output is derived from a resource that only exists once the provisioner succeeds.

**T8** — `import` brings existing infrastructure under management. Limitations include the fact that it doesn't generate code (it only updates state) and requires manual configuration matching. The `import` block (1.5+) allows you to define imports declaratively in code, enabling `tofu plan` to show what will happen before the import is finalized, making it safer and more repeatable.

**T9** — A **variable** is an input parameter used to make configurations dynamic. An **output** is a value returned by a module to be used by other modules or the CLI.

**T10** — A **provider** is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, the command will fail because the provider binaries have not been downloaded to the `.terraform` directory.

**T11** — It contains the specific versions and hashes of the providers used. It should be committed to ensure all team members and CI/CD pipelines use the exact same provider versions, preventing "works on my machine" issues.

**T12** — `tofu destroy` removes all resources managed by the current state. To target a single resource, use the `-target` flag: `tofu destroy -target=resource_type.resource_name`.

**T13** — A **data source** allows you to fetch information from existing infrastructure that is *not* managed by your current OpenTofu code. Example: Fetching an existing VPC ID by its name tag to use in a subnet resource.

**T14** — **Variables** are external inputs (passed at runtime). **Locals** are internal constants/expressions used to simplify code or avoid repetition. Use `locals` for complex logic or derived values that should not be changed by the user.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
- `prevent_destroy`: Stops accidental deletion of critical resources.
- `ignore_changes`: Tells OpenTofu to ignore updates to specific attributes (useful when an external process, like an Auto Scaling Group, modifies a resource).

**T16** — A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module in the code. This allows OpenTofu to update the state file to reflect the new address without destroying and recreating the actual physical resource.

**T17** — The dependency graph is a Directed Acyclic Graph (DAG). **Implicit dependencies** are created when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are created via `depends_on`. `depends_on` can reduce parallelism because it forces a strict order, potentially slowing down the apply process. It should be used sparingly to avoid unnecessary bottlenecks.

**T18** 
1. **State Splitting**: Break large monolithic states into smaller, decoupled workspaces (Tradeoff: increased complexity in passing data).
2. **Targeted Applies**: Use `-target` for specific fixes (Tradeoff: can lead to state inconsistency if overused).
3. **Reduce Resource Count**: Use more efficient logic or fewer resources (Tradeoff: may limit infrastructure granularity).
4. **Provider Optimization**: Ensure providers are up to date and use minimal data sources (Tradeoff: requires constant maintenance).

**T19** — State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a process crashes, the lock remains. You can manually break it using `tofu force-unlock <LOCK_ID>`. **Risk**: If another process is actually still running, manual unlocking can lead to state corruption.

**T20** 
1. Configure the new `backend "s3"` block in your code.
2. Run `tofu init`. OpenTofu will detect the local state and ask if you want to migrate it to the new backend.
3. Type `yes` to initiate the migration.
4. OpenTofu copies the local `.tfstate` to S3 and configures the DynamoDB table for locking.
5. **Verification**: Check the S3 bucket for the `.tfstate` file and attempt a `tofu plan` to ensure it can read the remote state successfully.

## Ansible

**A1** — A **task** is a single action (e.g., installing a package). A **playbook** is a collection of plays that map tasks to hosts. A **role** is a structured, reusable way to bundle tasks, variables, files, and templates.

**A2** — `ansible_facts` is a dictionary of system information gathered by Ansible. You access the OS family via `ansible_facts['os_family']`.

**A3** — `command` executes a command without a shell (more secure, no environment variable expansion). `shell` runs through `/bin/sh` (allows pipes, redirects, and variables). `raw` executes a command without even needing Python installed on the target (used for bootstrapping).

**A4** — Idempotency means running a task multiple times results in the same state. 
- **Idempotent**: `apt: name=nginx state=present` (if installed, does nothing).
- **NOT Idempotent**: `shell: echo "hello" >> /tmp/file.txt` (appends a new line every time it runs).

**A5**
```yaml
- name: Install htop
  package:
    name: "{{ 'epel-release' if ansible_os_family == 'RedHat' else 'htop' }}"
    state: present
  when: ansible_os_family == 'RedHat" or ansible_os_family == "Debian"
# Note: A more precise way is using two tasks or a conditional on the package name.
```

**A6** — Priority (lowest to highest): `role defaults` < `group_vars` < `host_vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process 3 nodes at a time. To ensure the first 3 are "ready" before the rest, use a `wait_for` task or a `pause` task within the play, or use a separate play for the first 3 nodes.

**A8** — `ansible-vault` encrypts files. To encrypt a single variable, you can use the `!vault` tag in a YAML file or use a separate encrypted vars file and include it in your playbook.

**A9** — An **inventory** lists the hosts to manage. A **static inventory** is a hardcoded file (INI/YAML). A **dynamic inventory** is a script or plugin that queries a cloud provider (AWS/GCP) to get a real-time list of hosts.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **handler** is a task that only runs when "notified" by another task. It differs because it only runs once at the end of a play, even if notified multiple times. Trigger it using `notify: name_of_handler`.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory` path, `remote_user`, and `forks` (number of parallel processes).

**A13** — `register` saves the output of a task into a variable. You use it in a subsequent task via `when: result_variable.rc == 0`.

**A14** — `import_tasks` is **static** (processed when the playbook is parsed); `include_tasks` is **dynamic** (processed when the task is reached). `include_tasks` allows for conditional inclusion of entire files, whereas `import_tasks` evaluates conditionals on a per-task basis.

**A15** — **Ansible Galaxy** is a hub for sharing roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16** — **Connection plugins** define how Ansible communicates. `ssh` is the standard for Linux. `local` runs tasks on the control node. `network_cli` is used for network devices (switches/routers) that use specialized CLI interfaces.

**A17** — `delegate_to` runs a task on a different host than the current one. `run_once` ensures a task runs only once for the whole play. 
*Example*: `shell: command` on `localhost` with `delegate_to: localhost` and `run_once: true` to create a directory on the control node based on a variable gathered from a remote host.

**A18** 
1. **Forks**: Increase `forks` in `ansible.cfg` to run more parallel processes (Tradeoff: higher CPU/RAM usage on control node).
2. **Pipelining**: Enable `pipelining = True` to reduce SSH connections (Tradeoff: requires `requiretty` to be disabled on targets).
3. **Fact Caching**: Use Redis/JSON files to store facts (Tradeoff: complexity in managing the cache).
4. **Mitogen**: Use the Mitogen plugin for highly optimized execution (Tradeoff: requires installing a plugin).

**A19** — `{{ }}` is for interpolation (variables). `{% %}` is for control logic (loops/ifs). `{# #}` is for comments.
```jinja2
upstream nginx_backend {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; # Health check: {{ server.status }}
{% endfor %}
}
```

**A20** — 
1. Use `serial: 1` or `serial: 5` to roll through the 20 servers in batches.
2. **Pre-task**: Use `uri` module to remove the server from the Load Balancer.
3. **Deployment**: Perform the update.
4. **Post-task**: Use `uri` module to perform a health check on the local service.
5. **Re-entry**: Add the server back to the Load Balancer.
6. **Rollback**: Wrap the deployment in a `block`. If a task fails, use `rescue` to run a task that reverts the version and re-adds the server to the LB.
