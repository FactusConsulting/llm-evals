T1 — `tofu plan` generates an execution plan, showing what actions (create, update, delete) will be taken to reach the desired state without making changes. `tofu apply` executes those planned actions to modify real-world infrastructure.

T2 — State is a JSON file mapping your configuration to real-world resources. Remote state (stored in S3, GCS, etc.) is critical for team collaboration, providing a "single source of truth" and enabling state locking to prevent concurrent modifications.

T3 — `count` uses an integer index (0, 1, 2...), making it difficult to remove items from the middle of a list without shifting indices. `for_each` uses a map or set of strings, allowing you to add/remove specific items without affecting others. `for_each` is preferred for managing collections of distinct resources.

T4 — This is "configuration drift." During the next `tofu plan`, OpenTofu refreshes its state by querying the provider API. It detects the discrepancy between the real-world state and the state file, then proposes changes to bring the resource back into alignment with your code.

T5 — 
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  tags = { Name = each.value }
  # ... other required arguments
}
```

T6 — `terraform_remote_state` reads the entire state file of another module, which can be a security risk (exposing all secrets) and creates tight coupling. The recommended alternative is using **Outputs** from the producer module and consuming them via a module call or a dedicated data source, or better yet, using a service registry/SSM Parameter Store to decouple state.

T7 — This is a race condition. The `null_resource` completes its execution, but the output is not "ready" or the provider hasn't refreshed the state before the dependent resource attempts to read it. **Fix:** Use a `depends_on` in the dependent resource pointing to the `null_resource`, or use a `local-exec` provisioner that waits for a specific file/state to exist.

T8 — `import` brings existing infrastructure under Tofu management. Limitations: it doesn't generate code; you must write the HCL manually. The `import` block (1.5+) improves this by allowing you to declare the import in code, which can then be used with `tofu plan -generate-config-out=...` to automatically generate the HCL.

T9 — A **variable** is an input parameter for a module. An **output** is a value returned by a module. Variables allow for customization; outputs allow for data sharing.

T10 — A provider is a plugin that translates HCL into API calls for a specific platform (AWS, Azure, etc.). If you run `tofu plan` without `tofu init`, Tofu will fail because it hasn't downloaded the necessary provider binaries.

T11 — It is the dependency lock file that records the exact versions and hashes of providers used. It should be committed to ensure all team members and CI/CD pipelines use identical provider versions, preventing "works on my machine" issues.

T12 — `tofu destroy` removes all resources managed by the current state. To target a single resource, use the `-target` flag: `tofu destroy -target=aws_instance.web_server`.

T13 — A data source allows you to fetch information from existing infrastructure that is *not* managed by your current Tofu code. Example: Fetching an existing VPC ID or an AMI ID by name rather than creating a new one.

T14 — `variable` blocks are external inputs (passed via CLI, `.tfvars`, or env vars). `locals` are internal constants/computed values. Use `locals` for complex logic, repeated expressions, or to avoid hardcoding values that shouldn't be changed by the user.

T15 — 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
- `prevent_destroy`: Stops Tofu from destroying a resource (protects critical DBs).
- `ignore_changes`: Tells Tofu to ignore specific attribute updates (useful when an external process, like an Auto Scaling Group, modifies a resource).

T16 — A `moved` block tells Tofu that a resource has been renamed or moved to a different module in the code. This allows Tofu to update the state file's address without destroying and recreating the actual physical resource.

T17 — Tofu builds a Directed Acyclic Graph (DAG). **Implicit dependencies** occur when one resource references another's attribute (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** use `depends_on`. `depends_on` forces Tofu to wait, reducing parallelism; it should be used sparingly because it can hide architectural flaws and slow down execution.

T18 — 
1. **State Splitting:** Break large monolithic states into smaller, decoupled workspaces (Tradeoff: increased complexity in cross-state communication).
2. **Targeted Refactoring:** Use `moved` blocks to organize code (Tradeoff: requires careful state management).
3. **Reduce Refreshing:** Use `-refresh=false` (Tradeoff: risk of acting on stale data).
4. **Provider Optimization:** Minimize the number of resources/providers per state (Tradeoff: architectural overhead).

T19 — Tofu uses a lock file (e.g., a DynamoDB entry) to prevent concurrent writes. If a pipeline crashes, the lock remains. You can manually break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If a process is *actually* still running, force-unlocking can lead to state corruption or resource duplication.

T20 — 
1. Create the S3 bucket and DynamoDB table.
2. Update the `backend "s3" {}` block in your code.
3. Run `tofu init`. Tofu will detect the local state and ask if you want to migrate it to the new backend.
4. Type `yes`. Tofu uploads the local `.tfstate` to S3.
5. **Verify:** Check the S3 bucket for the `.tfstate` file and run `tofu plan` to ensure "No changes" are detected.

A1 — A **task** is a single action (e.g., installing a package). A **playbook** is a collection of plays that map tasks to hosts. A **role** is a structured, reusable collection of tasks, variables, and templates.

A2 — `ansible_facts` is a dictionary of system information gathered by Ansible. Access the OS family via `ansible_facts['os_family']` or simply `ansible_os_family`.

A3 — `command` executes a command without a shell (safer, no shell expansion). `shell` runs through `/bin/sh` (allows pipes, redirects, variables). `raw` bypasses Python entirely (used for bootstrapping systems where Python isn't installed).

A4 — Idempotency means running a task multiple times results in the same state. 
- **Idempotent:** `apt: name=nginx state=present` (if installed, does nothing).
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file.txt` (appends a line every single time).

A5 — 
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel and htop on RedHat
  yum:
    name: "{{ item }}"
    state: present
  loop: [epel-release, htop]
  when: ansible_os_family == "RedHat"
```

A6 — `extra_vars` (highest) > `set_fact` > `host_vars` > `group_vars` > `role defaults` (lowest).

A7 — Use `serial: 3` in the playbook to process 3 hosts at a time. Use `wait_for` to ensure the RKE2 service is listening on a port before moving to the next batch. Use inventory groups to separate the "seed" nodes from the rest.

A8 — `ansible-vault` encrypts files/variables. To encrypt a single variable, you can use `ansible-vault encrypt_string 'my_secret_password' --name 'db_password'`, then paste the resulting block into your vars file.

A9 — An **inventory** is a list of managed hosts. **Static** is a hardcoded file (INI/YAML). **Dynamic** is a script or plugin that queries a cloud provider (AWS/GCP) to get a real-time list of hosts.

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A **handler** is a special task that only runs if a task notifies it (via `notify`). Unlike regular tasks, they run at the end of a play. Trigger it using the `notify` keyword in a task.

A12 — `ansible.cfg` configures Ansible behavior. Common settings: `inventory` (path to inventory), `remote_user` (default SSH user), and `forks` (number of parallel processes).

A13 — `register` saves the output of a task into a variable. You can then use that variable in a `when` clause or a `debug` task: `when: result.rc == 0`.

A14 — `import_tasks` is **static** (processed at playbook parsing time); it cannot use loops or conditionals on the include itself. `include_tasks` is **dynamic** (processed at runtime); it allows for loops and conditional inclusion.

A15 — **Ansible Galaxy** is a hub for sharing roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

A16 — **ssh** is the default (uses SSH to run Python). **local** runs tasks on the control node itself. **network_cli** is used for network devices (Cisco/Arista) that don't support Python and require specific CLI interaction.

A17 — `delegate_to` runs a task on a different host than the current one. `run_once` ensures a task runs only once for the entire play. **Example:** To create a backup on the control node before updating a remote DB: `delegate_to: localhost` and `run_once: true`.

A18 — 
1. **Forks:** Increase `forks` in `ansible.cfg` (Tradeoff: higher CPU/RAM on control node).
2. **Pipelining:** Enable `pipelining = True` to reduce SSH connections (Tradeoff: requires `requiretty` to be disabled on target).
3. **Fact Caching:** Use Redis/JSON for facts (Tradeoff: complexity of managing a cache server).
4. **Mitogen:** Use the Mitogen plugin (Tradeoff: highly efficient but requires specific environment compatibility).

A19 — `{{ }}` is for expressions; `{% %}` is for control logic (loops/ifs); `{# #}` is for comments.
```jinja2
{% for server in backends %}
upstream backend_cluster {
    server {{ server.ip }}:{{ server.port }}; # Health check: {{ server.status }}
}
{% endfor %}
```

A20 — 
1. Use `serial: 1` or `serial: 5` to process servers in batches.
2. **Pre-task:** Use `uri` module to check health, then a task to remove the host from the Load Balancer.
3. **Main Task:** Deploy the app.
4. **Post-task:** Use `uri` to verify the app is healthy, then re-add to the Load Balancer.
5. **Rollback:** Wrap the deployment in a `block`. If a task fails, use `rescue` to run a task that restores the previous version.
