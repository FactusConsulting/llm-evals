AA1 — A **monolith** is a single, unified unit where all business logic, data access, and UI components are packaged together. **Microservices** decompose the application into small, independent services communicating over a network.
**3 Problems introduced by microservices:**
1. **Network Latency/Complexity:** Moving from in-memory calls to RPC/HTTP adds overhead and failure modes.
2. **Data Consistency:** Maintaining integrity across distributed databases (no more ACID transactions across services).
3. **Observability Challenges:** Tracing a single request through dozens of services requires complex distributed tracing.

AA2 — **Synchronous:** The client sends a request and waits (blocks) for a response before continuing. Example: **REST/HTTP**.
**Asynchronous:** The client sends a message/request and continues its work without waiting for an immediate response. Example: **RabbitMQ/AMQP**.

AA3 — An **API Gateway** provides high-level application logic (authentication, rate limiting, request transformation, orchestration). A **reverse proxy** (like Nginx) primarily handles traffic routing, SSL termination, and load balancing at the transport/network level.
**Can it replace?** Not entirely. While modern gateways can do everything a proxy does, a dedicated reverse proxy is often more performant for low-level tasks (like serving static files or simple load balancing) without the overhead of application-layer logic.

AA4 — The **Saga pattern** manages data consistency in distributed systems by breaking a large transaction into a sequence of local transactions. Each local transaction updates the database and triggers the next step.
**Choreography:** Services exchange events without a central controller. Each service "knows" what to do when it hears an event. *Best for: Simple workflows with few services.*
**Orchestration:** A central "orchestrator" tells each service what to do and manages the state machine. *Best for: Complex workflows with many steps or centralized business logic.*

AA5 — **CQRS** separates the models for reading data (Queries) from the models for updating data (Commands).
**Pairing with Event Sourcing:** Event Sourcing stores the state as a sequence of immutable events rather than the current "snapshot." CQRS is paired with it because the "Write" model (Event Store) is highly optimized for appending events, while the "Read" model (Projections) is optimized for complex queries.
**Problem solved:** It solves the performance bottleneck of trying to use a single schema for both high-speed writes and complex, diverse read requirements.

AA6 — The **Circuit Breaker** prevents a system from repeatedly trying an operation that is likely to fail.
**States:** 1. **Closed** (requests flow normally), 2. **Open** (requests fail immediately), 3. **Half-Open** (limited requests allowed to test if the service has recovered).
**Difference:** A **retry with backoff** assumes the failure is transient and tries again. A **circuit breaker** assumes the system is overwhelmed and stops all attempts to allow it to recover.
**Usage:** Use them together by having the circuit breaker trip when the error rate is too high, and using retries only when the circuit is "Closed."

AA7 — 
1. **Shared DB/Schema:** *Cost:* Lowest. *Security:* Weakest (risk of data leakage). *Complexity:* Low. *Noisy-neighbor:* High (one tenant's query can slow all).
2. **Shared DB/Separate Schema:** *Cost:* Medium. *Security:* Moderate (schema-level isolation). *Complexity:* Medium. *Noisy-neighbor:* Moderate.
3. **Separate DB:** *Cost:* Highest. *Security:* Strongest (physical isolation). *Complexity:* High (managing migrations across many DBs). *Noisy-neighbor:* Lowest.

AA8 — **Eventual Consistency:** Data will be consistent "eventually," but reads might return stale data temporarily. **Strong Consistency:** A read is guaranteed to return the most recent write.
**Architecture:** To prevent overselling, use **Strong Consistency**.
**Stack:** A relational database (e.g., **PostgreSQL**) with ACID properties.
**Pattern:** Use **Pessimistic Locking** (SELECT FOR UPDATE) on the inventory row during the transaction to ensure no two processes can decrement the same stock simultaneously.

AA9 — A **sidecar proxy** is a helper process running alongside the main application container to handle networking tasks. In **Istio**, **Envoy** acts as the sidecar.
**Data Plane:** The Envoy proxies that handle actual traffic. **Control Plane:** Istio (istiod) which manages and configures the proxies.
**mTLS:** mTLS provides identity-based encryption and authentication between services. Unlike application-level TLS, it is transparent to the developer and ensures that even if the network is compromised, service-to-service communication is authenticated and encrypted.

AA10 — The **Strangler Fig** pattern involves placing a proxy in front of the monolith and gradually routing specific functionalities to new microservices until the monolith is "strangled" and can be decommissioned.
**Strategy:** 
1. Deploy an API Gateway/Proxy in front of the .NET Framework monolith.
2. Identify a low-risk module (e.g., "Notification Service").
3. Build that module in .NET 8.
4. Update the Gateway to route `/api/notifications` to the new service while everything else goes to the monolith.
5. Repeat for all modules until the monolith is empty.

AA11 — The **12-Factor App** is a methodology for building SaaS/Cloud-native apps.
1. **Codebase:** One repo, many deploys (ensures parity).
2. **Dependencies:** Explicitly declare/isolate (prevents "it works on my machine").
3. **Config:** Store in environment (security/portability).
4. **Backing Services:** Treat as attached resources (flexibility).
5. **Build, Release, Run:** Strict separation (stability).
6. **Processes:** Stateless (horizontal scalability).

AA12 — 
**Event-Driven (Kafka):** High scalability, loose coupling, asynchronous. *Cons:* High debugging complexity, eventual consistency, complex ordering guarantees. *Use when:* High throughput, many consumers, or decoupling producers from consumers.
**Request-Driven (REST/gRPC):** Tight coupling, synchronous, easy to debug. *Cons:* Harder to scale under heavy load, cascading failures. *Use when:* Immediate response is needed (e.g., UI requests) or simple CRUD operations.

AA13 — A **load balancer** distributes incoming network traffic across multiple servers.
**Layer 4:** Operates at the Transport layer (TCP/UDP); routes based on IP and Port.
**Layer 7:** Operates at the Application layer (HTTP/HTTPS); routes based on URL, Headers, or Cookies.
**Use Case:** Routing traffic to different microservices based on the URL path (e.g., `/users` vs `/orders`).

AA14 — A **message queue** (RabbitMQ) is designed for task distribution; once a message is consumed and acknowledged, it is deleted. A **log-based broker** (Kafka) is a distributed append-only log; messages persist after consumption, allowing "replayability."
**Pick RabbitMQ for:** Complex routing, individual message acknowledgments, and task queues.
**Pick Kafka for:** High-throughput stream processing, event sourcing, and replaying historical data.

AA15 — A **container** is a lightweight, isolated user-space environment that shares the host OS kernel. A **VM** includes a full guest OS and runs on a hypervisor.
**Popularity:** Containers are popular because they are much faster to start, use significantly less RAM/CPU than VMs, and provide consistent environments across dev/prod.

AA16 — **Stateless:** The service does not store client data locally; every request contains all info needed to process it. **Stateful:** The service stores data (e.g., a local session file) that must be available for subsequent requests.
**Scaling:** Stateless services are easier to scale because any instance can handle any request; you just add more instances behind a load balancer.
**Examples:** Stateless: A math calculation API. Stateful: A database or a legacy session-based web app.

AA17 — An **ORM** maps database tables to programming objects.
**Examples:** **Hibernate** (Java), **Entity Framework** (C#).
**Trade-offs:** ORMs increase developer productivity and provide security (SQL injection protection), but they can generate highly inefficient, "N+1" query patterns that are difficult to optimize compared to hand-written SQL.

AA18 — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function (like the compartments of a ship).
**Implementation:** 
1. **Thread Pools:** Assign a specific thread pool to a specific downstream service. If that service hangs, only that pool exhausts; the rest of the app remains responsive.
2. **Deployment Groups:** Deploy "Service A" and "Service B" on entirely separate clusters/nodes so a resource leak in A doesn't crash B.

AA19 — **OT:** Centralized approach where a server resolves conflicts by transforming operations. **CRDTs:** Decentralized approach where data structures are mathematically designed so that concurrent updates always converge to the same state without a central coordinator.
**Comparison:** OT is complex to implement and requires a central server. CRDTs are more complex mathematically but handle peer-to-peer and offline scenarios much better.
**Choice:** For **offline editing**, I would choose **CRDTs**. They allow users to make changes locally and merge them seamlessly when they reconnect, without needing a server to "rebase" their changes.

AA20 — **Challenges:** Maintaining a single trace ID across different protocols and languages.
**Context Propagation:** Using headers (W3C Trace Context or B3) to pass the TraceID.
**Sampling:** **Head-based** (decide at the start of the request) vs **Tail-based** (decide after the trace is complete, e.g., keep all traces that resulted in an error).
**Kafka Continuity:** To ensure continuity, the producer must inject the trace context into the **Kafka Message Headers**. The consumer then extracts this header to start its own span as a child of the producer's span.

OP1 — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., **VMware ESXi, Xen**). **Type 2 (Hosted):** Runs on top of an OS (e.g., **Oracle VirtualBox, VMware Workstation**).

OP2 — **SAN (Storage Area Network):** Block-level storage (appears as a local disk). Use for databases/VMs. Protocols: **Fibre Channel, iSCSI**.
**NAS (Network Attached Storage):** File-level storage (appears as a network share). Use for file sharing/backups. Protocols: **NFS, SMB/CIFS**.

OP3 — **3-Tier:** Core (high-speed switching), Distribution (policy/routing), Access (connecting end devices).
**Leaf-Spine:** A two-tier architecture where every Leaf switch connects to every Spine switch.
**Problem solved:** It provides predictable, low-latency "any-to-any" connectivity and eliminates the bottleneck/blocking issues of the Spanning Tree Protocol (STP) found in 3-tier designs.

OP4 — **Architecture:** Minimum 3 nodes for quorum.
**Quorum:** Ensures a majority of nodes agree on state to prevent split-brain.
**Fencing:** Using STONITH (Shoot The Other Node In The Head) to power off a rogue node.
**Storage:** **Ceph** is preferred for high availability as it distributes data across nodes.
**Failure:** If a node fails, the cluster detects the loss of heartbeat, the remaining nodes maintain quorum, and the VMs/services are automatically restarted on the surviving nodes.

OP5 — **VLAN Trunking:** A single physical link carrying multiple VLANs. **802.1Q:** The standard for adding a "tag" to the Ethernet frame header to identify the VLAN.
**Linux Config:** Use **8021q kernel module** and create sub-interfaces (e.g., `eth0.10`, `eth0.20`, `eth0.30`) using `ip link` or `nmcli`.

OP6 — **RAID 1:** Mirroring. **RAID 5:** Striping + 1 parity. **RAID 6:** Striping + 2 parity. **RAID 10:** Mirroring + Striping. **RAID Z2:** ZFS equivalent of RAID 6.
**Choice:** For a database, choose **RAID 10**. It provides the best performance (no parity calculation overhead) and high fault tolerance (can lose multiple drives as long as they aren't in the same mirror set).

OP7 — **Architecture:**
- **Internal AD:** Uses internal DNS zones.
- **DMZ:** Uses authoritative servers for public records.
- **Split-Horizon:** Different DNS responses for internal vs. external queries.
- **DNSSEC:** Digitally signs records to prevent spoofing.
- **Flow:** A laptop on-site uses internal recursive resolvers. When on VPN, it uses the same resolvers via the tunnel. If it moves to a coffee shop, it uses public DNS (like 8.8.8.8), losing access to internal zones unless a DNS-over-HTTPS/VPN setup is used.

OP8 — **Chain:** Root CA (Self-signed) $\rightarrow$ Subordinate CA (signed by Root) $\rightarrow$ End-entity (signed by Subordinate).
**Management:** Root CA must be **offline** to prevent total compromise. **CRL/OCSP** are used to check if certificates are revoked.
**Compromise:** A compromised **Subordinate CA** allows an attacker to issue fake certs for that branch, but the Root can revoke the Subordinate. A compromised **Root CA** destroys the entire trust foundation; every certificate in the organization is now untrusted.

OP9 — **Comparison:** **MPLS** (High cost, high reliability, low latency, private). **IPsec VPN** (Low cost, relies on internet, variable latency). **SD-WAN** (Smart routing, manages multiple links). **WireGuard** (Fast, modern, mesh-capable).
**Recommendation:** For 50 users/site with VoIP, **SD-WAN** is best. It can combine a cheap internet link with a reliable MPLS link, prioritizing VoIP traffic over the most stable path.

OP10 — **iDRAC/iLO/IPMI:** Out-of-band management interfaces that allow hardware control (power, BIOS, console) even if the OS is crashed.
**Criticality:** Allows remote recovery without physical presence.
**Risk:** If exposed to the internet, an attacker can gain full control of the hardware, wipe drives, or shut down the server.

OP11 — **LVM:** Logical volume management for flexible partitioning. **LVM-Thin:** Allows over-provisioning of space. **ZFS:** A combined file system and volume manager with built-in RAID/snapshots.
**Snapshots:** LVM uses "copy-on-write" (can be slow). ZFS uses "redirect-on-write" (highly efficient, near-instant). Use ZFS for data integrity and ZFS/LVM-Thin for space efficiency.

OP12 — **Design:** A **Stretch Cluster** across two sites.
**Ceph:** Use **CRUSH rules** to ensure replicas are placed in different physical racks/sites.
**Requirements:** Requires very low latency (usually <5ms RTT) for synchronous replication.
**Split-brain:** If the link breaks, both sites might think they are the master.
**2-site issue:** Without a **third site (tiebreaker/witness)** to provide quorum, the cluster cannot safely decide which site should stay active during a partition.

OP13 — **DORA:** **D**iscover (Client), **O**ffer (Server), **R**equest (Client), **A**cknowledge (Server).
**Failure:** If the DHCP server is down and the lease expires, the client will eventually fall back to an **APIPA** address (169.254.x.x), which provides no internet/network access.

OP14 — **Unmanaged:** Plug-and-play, no configuration. **Managed:** Supports VLANs, Spanning Tree, SNMP, and Port Security.
**Enterprise Importance:** Managed switches are essential for segmenting traffic (VLANs), monitoring network health (SNMP), and preventing loops (STP).

OP15 — **NTP:** Network Time Protocol.
**Criticality:** Essential for log correlation, Kerberos authentication (which fails if clocks drift >5 mins), and database transaction ordering.
**Drift:** Can cause security certificate failures and broken distributed logs.

OP16 — **Physical:** Direct hardware access. **VM:** Hardware abstraction via hypervisor. **Container:** OS abstraction via kernel namespaces.
**Bare Metal Use Case:** High-performance computing (HPC), massive databases, or workloads where the hypervisor overhead (even if minimal) is unacceptable.

OP17 — **UPS:** Provides immediate battery power for short durations to allow graceful shutdown or bridge the gap to a generator. **Generator:** Provides long-term power.
**ATS (Automatic Transfer Switch):** Automatically switches the power source from the utility to the generator when it detects a failure. You need both to ensure both immediate and long-term availability.

OP18 — **Active-Passive:** One server is idle/standby. **Active-Active:** Both servers handle traffic.
**PostgreSQL HA:** Use **Pacemaker/Corosync** to manage the cluster state. **Fencing (STONITH)** ensures the "dead" node is truly powered off before the standby takes over the IP. **Virtual IP (VIP)** is moved to the active node so clients don't need to change connection strings.

OP19 — **3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
**RPO/RTO:** RPO (how much data you can lose); RTO (how long it takes to recover).
**Types:** Full (all), Incremental (changes since last backup), Differential (changes since last full).
**Immutable Backups:** Write-once-read-many (WORM) storage to prevent ransomware from deleting backups.
**Backup vs DR:** Backup is the *data*; Disaster Recovery is the *process/infrastructure* to restore service.

OP20 — **Roles:** **Supplicant** (Client), **Authenticator** (Switch), **Authentication Server** (RADIUS).
**Methods:** **EAP-TLS** (Certificate-based, very secure) vs **PEAP** (Username/Password inside a TLS tunnel).
**Dynamic VLAN:** RADIUS tells the switch which VLAN to assign to the port upon successful login.
**MAB:** The switch checks the device's MAC address against a whitelist in RADIUS; it's less secure because MACs can be spoofed.
