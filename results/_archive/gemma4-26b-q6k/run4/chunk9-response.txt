### SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because of a conflict between the `securityContext.runAsNonRoot: true` directive and the container image's default user. In Kubernetes, `runAsNonRoot: true` forces the Kubelet to validate that the container image does not default to UID 0 (root). The new `chainguard/static:latest` image defaults to `USER root`. When the Kubelet attempts to start the container, it sees the root user and refuses to run it to satisfy the `runAsNonRoot` constraint. The transition from **Baseline** to **Restricted** PSS (Pod Security Standards) enforces stricter controls; while Baseline allows some root-related configurations, Restricted mandates that the container must run as a non-root user. Since no `runAsUser` was explicitly set in the manifest to override the image default, the Kubelet enforces the image's default (root), which violates the policy.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level fix:** Rebuild images to explicitly include `USER 1000` (or any non-zero UID) in the Dockerfile.
*   **Manifest changes:** Add `securityContext.runAsUser: <non-zero-uid>` to the deployment templates to ensure compliance regardless of image defaults.
*   **CI Pipeline Gate:** Implement a "Policy-as-Code" check using `conftest` or `kube-linter` in the CI pipeline to scan manifests for `runAsNonRoot: true` without a corresponding `runAsUser`.
*   **Rollout:** Perform a `kubectl rollout undo` to the previous working image version for immediate recovery, then execute a rolling update with the fixed images.

### SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is due to **asynchronous replication**. In cross-region setups, PostgreSQL typically uses asynchronous streaming replication to avoid the massive latency penalty of waiting for an ACK from a distant region. The "stale data" represents the **Replication Lag**—the delta between the last WAL (Write Ahead Log) sent from `us-east-1` and the last WAL applied in `eu-west-1`. To quantify the data loss window, I would check the `pg_stat_replication` view on the primary (for lag bytes/time) and `pg_last_xact_replay_timestamp()` on the replica.

**SC2-B:**
1.  **Import the new instance:** `tofu import aws_db_instance.new_primary <new-instance-id>`.
2.  **Update references:** Update the ARN in the Terraform code.
3.  **Handle the old instance:** Use `terraform state rm aws_db_instance.old_primary` to remove it from state without destroying it, then manually delete the old instance in AWS.
4.  **Dependency update:** Run `tofu apply` to update Security Groups and Route53 records to point to the new ARN.

**SC2-C:**
*   **Architecture:** Use **Aurora Global Database**. It uses storage-level replication which is significantly faster and more consistent than standard RDS streaming replication, offering lower RPO.
*   **Connection Management:** Use **RDS Proxy** for better connection pooling and faster failover handling than PgBouncer in this context.
*   **Failover:** Use **Route53 CNAME/Alias records** with health checks to automate DNS redirection.
*   **RPO < 1s:** Requires **Synchronous Replication** (which increases latency) or **Aurora Global Database** with optimized physical replication.

### SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Sticky Sessions:** K8s Services are ephemeral; use **Ingress-Nginx/ALB with Cookie-based affinity**.
2.  **Local File Storage:** K8s pods are transient; replace local NFS with a **CSI driver (e.g., AWS EFS or Azure Files)**.
3.  **In-Memory Sessions:** Move sessions to an external **Redis/Memcached** cluster.
4.  **Mainframe/IBM MQ:** Use a **Sidecar container** or a dedicated "Bridge Service" to handle protocol translation.
5.  **Oracle DB:** Use a **Service/Endpoint** abstraction so the app doesn't care if the DB is on-prem or in the cloud.

**SC4-B:**
```hcl
resource "kubernetes_storage_class" "nfs_sc" {
  metadata { name = "nfs-storage" }
  storage_provisioner = "nfs.csi.k8s.io"
}

resource "kubernetes_persistent_volume" "nfs_pv" {
  metadata { name = "nfs-pv" }
  spec {
    capacity = { size = var.capacity }
    access_modes = ["ReadWriteMany"]
    persistent_volume_source {
      nfs {
        server = var.nfs_server
        path   = var.export_path
      }
    }
  }
}

resource "kubernetes_persistent_volume_claim" "nfs_pvc" {
  metadata { name = "nfs-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    resources { requests = { storage = var.capacity } }
    storage_class_name = "nfs-storage"
  }
}
```
*Note: `ReadWriteMany` (RWX) is required because multiple pods (replicas) must access the same shared file storage simultaneously.*

**SC4-C:**
1.  **Phase 1 (Preparation):** Containerize the app, move sessions to Redis, and set up K8s networking.
2.  **Phase 2 (Hybrid):** Deploy to K8s but keep the DB on-prem. Use the F5 to route 5% of traffic to K8s via a "Canary" path.
3.  **Phase 3 (Full Migration):** Move the DB to the cloud/K8s.
*   **Traffic Split:** Use the F5 to split traffic between the legacy bare-metal VIP and the K8s Ingress VIP.
*   **Rollback:** If latency spikes, update F5 weights back to 100% legacy.
*   **Metrics:** Success is defined by p99 latency < 2s and error rate < 0.1%.

### SC6 — Zero-Trust Network Overhaul

**SC6-A:**
*   **Identity:** Implement **SPIFFE/SPIRE** to issue short-lived SVIDs (X.509 certificates) to every workload.
*   **Federation:** Use **OIDC Federation**. AWS IAM Roles for Service Accounts (IRSA) can be mapped to SPIFFE identities. For on-prem, use a **SPIRE Agent** that integrates with the local PKI to issue identities that are trusted by the AWS/Azure OIDC providers.

**SC6-B:**
```hcl
resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }

resource "aws_transit_gateway" "tgw" { enable_automatically_accept_shared_attachments = true }

resource "aws_vpc_endpoint" "endpoints" {
  for_each           = var.service_list
  service_name       = each.value
  vpc_id              = aws_vpc.main.id
  vpc_endpoint_type    = "Interface"
  subnet_ids           = var.private_subnets
}

resource "aws_security_group" "zero_trust_sg" {
  ingress { from_port = 0; to_port = 0; protocol = "-1"; self = true } # Default deny logic handled by lack of rules
}
```

**SC6-C:**
*   **Direct Connect:** Best for high bandwidth/low latency, but highest cost.
*   **ECMP (Dual VPN):** Cheaper, provides redundancy, but limited by single-tunnel throughput.
*   **Tailscale/Mesh:** Best for Zero-Trust (identity-based), but adds overlay complexity.
*   **Recommendation:** **Direct Connect** for the core backbone, combined with a **Service Mesh (Cilium/Istio)** for identity-based encryption (mTLS) to satisfy the Zero-Trust mandate.

### SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
*   **Drift Sources:** Manual `tofu apply` bypasses CI testing; Helm divergence causes "works in staging, fails in prod"; `kubectl edit` creates "ghost" configurations.
*   **Risks:** Running `tofu apply` without locking causes **State Corruption** (two processes writing to S3 simultaneously). This can lead to partial resource creation or accidental deletion of live resources.

**SC7-B:**

```yaml
  script:
    - tofu fmt -check
    - tofu validate

plan:
  script:
    - tofu plan -out=tfplan
    - # Logic to post plan to MR comment via GitLab API
  artifacts: { paths: [tfplan] }

apply_prod:
  stage: apply
  environment: production
  when: manual
  script:
    - tofu apply tfplan
  backend_config:
    # Use S3 with DynamoDB for locking
```

**SC7-C:**
*   **Detection:** Schedule a `tofu plan -detailed-exitcode` job in GitLab every hour.
*   **Prevention:** Use **Kyverno** to block `kubectl edit` on critical resources.
*   **Structure:** Use **Kustomize** to define a `base` and use `overlays/production` for environment-specific patches.
*   **RBAC:** Restrict AWS IAM and K8s RBAC so only the **GitLab Runner Service Account** has `Write` permissions.

### SC10 — Multi-Cluster Disaster Recovery

**SC10-A:**
*   **Active-Passive (Velero):** RTO is high (time to pull 200TB from S3). RPO depends on backup frequency.
*   **Active-Active (Cilium Mesh):** Best for RTO/RPO.
*   **Replication:**
    *   **PostgreSQL:** Patroni with synchronous replication for RPO=0.
    *   **MinIO:** Use **Site Replication** (asynchronous) for the 200TB.
    *   **RabbitMQ:** Use **Federation** or **Shovel** plugin.

**SC10-B:**
```yaml
- name: configure_patroni
  hosts: db_servers
  tasks:
    - name: Install Patroni
      apt: name=patroni state=present
    - name: Template Patroni Config
      template:
        src: patroni.yml.j2
        dest: /etc/patroni/patroni.yml
      notify: restart patroni

  handlers:
    - name: restart patroni
      service: name=patroni state=restarted
```

**SC10-C:**
1.  **Detection:** Monitor Patroni/etcd health. If Chicago is unreachable for > 30s, trigger failover.
2.  **Sequence:** 
    *   Promote Dallas PostgreSQL (Patroni).
    *   Update Route53/GSLB to point to Dallas.
    *   Promote Redis Sentinel in Dallas.
    *   Re-route RabbitMQ traffic.
3.  **Split-Brain:** Use **Fencing (STONITH)** to ensure the Chicago node is truly dead before promoting Dallas.
4.  **Failback:** Re-provision Chicago as a *replica* of Dallas first, then perform a controlled switchover.
