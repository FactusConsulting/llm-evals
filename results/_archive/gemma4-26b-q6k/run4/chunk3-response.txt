## OpenTofu / Terraform

**T1** — `tofu plan` generates an execution plan, showing what actions (create, update, delete) will be taken to reach the desired state without actually making changes. `tofu apply` executes those planned actions to modify real-world infrastructure.

**T2** — State is a JSON file that maps your configuration to real-world resources. Remote state (stored in S3, GCS, etc.) is critical for team collaboration, providing a "single source of truth" and enabling state locking to prevent concurrent writes.

**T3** — `count` uses an integer to create $N$ instances; it is index-based, meaning removing item 0 shifts all subsequent indices, causing resource recreation. `for_each` uses a map or set; it is key-based, making it much safer for adding/removing specific items without affecting others. Use `for_each` for collections of varying items.

**T4** — This is "configuration drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the cloud provider API. It detects the discrepancy between the actual state and the state file, then proposes changes to revert the manual modification to match the configuration.

**T5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

**T6** — `terraform_remote_state` reads the state file of another workspace directly. This creates tight coupling and security risks (accessing raw state). The recommended alternative is using **Outputs** from the producer module and consuming them via **Data Sources** or passing them as inputs to the consumer module, which promotes loose coupling.

**T7** — The `null_resource` runs during the apply phase, but if the `remote-exec` fails or hasn't finished writing the file to disk before the output is read, the output is empty. **Fix:** Use a `local_file` data source or a `null_resource` with a `local-exec` that waits for the file to exist, or use a `check` block/`depends_on` to ensure the file is fully written before the output is accessed.

**T8** — `tofu import` brings existing infrastructure under management. Limitations: It only updates the state file; it does not write the `.tf` code for you. The `import` block (1.5+) is superior because it allows you to define the import in code, making it repeatable, versionable, and capable of generating the necessary configuration via `tofu plan -generate-config-out`.

**T9** — A **variable** is an input parameter for your module. **Input variables** allow users to pass values into the configuration. **Outputs** are return values that expose information (like an IP address) from a module to the caller.

**T10** — A **provider** is a plugin that enables OpenTofu to interact with specific APIs (AWS, Azure, etc.). If you run `tofu plan` without `tofu init`, it will fail because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11** — The `.terraform.lock.hcl` file records the specific versions and hashes of providers used. It should be committed to ensure "reproducible builds," meaning every team member and CI/CD runner uses the exact same provider versions.

**T12** — `tofu destroy` removes all resources managed by the current configuration. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

**T13** — A **data source** allows you to fetch information from existing infrastructure not managed by your current OpenTofu code. Example: Using a `data "aws_ami"` block to find the latest Amazon Linux 2 ID instead of hardcoding an AMI ID.

**T14** — **Variables** are external inputs (provided by the user). **Locals** are internal constants/expressions (defined by the author). Use `locals` for complex logic, derived values, or to avoid repetition within a module; use `variables` for values that must change per environment/user.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
- `prevent_destroy`: Stops OpenTofu from deleting a resource (useful for production databases).
- `ignore_changes`: Tells OpenTofu to ignore specific attribute updates (useful when an external process, like an Autoscaling Group, modifies a resource).

**T16** — A `moved` block allows you to rename a resource or move it into a module in the code without OpenTofu thinking the old resource was deleted and a new one was created. It updates the state mapping instead of the physical infrastructure.

**T17** — The dependency graph is a Directed Acyclic Graph (DAG). **Implicit dependencies** are created when one resource references another's attribute. **Explicit dependencies** are created via `depends_on`. `depends_on` forces a specific order but can hinder parallelism by creating bottlenecks; use it only when a dependency isn't captured by an attribute reference.

**T18** — 
1. **Targeted Refactoring:** Break the large state into multiple smaller state files/workspaces (Tradeoff: increased complexity).
2. **Reduce Refreshing:** Use `-refresh=false` (Tradeoff: risk of acting on stale data).
3. **Parallelism Tuning:** Increase `-parallelism` (Tradeoff: may hit API rate limits).
4. **State Splitting:** Use `data` sources to reference resources in other states (Tradeoff: more complex architecture).

**T19** — State locking prevents two users from running `apply` simultaneously. If a CI crashes, the lock remains in the backend (e.g., DynamoDB). You break it with `tofu force-unlock <LOCK_ID>`. **Risk:** If you force unlock while an actual process is running, you risk state corruption.

**T20** — 
1. Create a new `backend` block in your `.tf` files.
2. Run `tofu init`. OpenTofu will detect the change and ask to migrate the state.
3. Confirm the migration.
4. OpenTofu copies the local `.tfstate` to the S3 bucket and creates the DynamoDB table for locking.
5. **Verify:** Check the S3 bucket for the `.tfstate` file and run `tofu plan` to ensure no changes are pending.

## Ansible

**A1** — A **task** is a single action. A **playbook** is a collection of plays (sequences of tasks). A **role** is a structured way to bundle tasks, variables, and templates into a reusable unit.

**A2** — `ansible_facts` is a dictionary of system information gathered by Ansible. Access the OS family via `ansible_facts['os_family']` or `ansible_os_family`.

**A3** — `command` runs a raw command without shell processing (safest). `shell` runs through `/bin/sh` (allows pipes/redirects). `raw` bypasses Python and runs via SSH directly (used when Python isn't installed on the target).

**A4** — Idempotency means running a task multiple times results in the same state. 
- **Idempotent:** `apt: name=htop state=present`.
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file.txt` (appends every time).

**A5**
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian" or ansible_os_family == "RedHat"
```
*(Note: For a single task file, you'd use conditional logic or `block` with `when` statements).*

**A6** — Order (lowest to highest): `role defaults` < `group_vars` < `host_vars` < `playbook vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process nodes in batches of 3. Use `wait_for` in a task to ensure the first batch is reachable/ready before proceeding. Use `delegate_to` or a specific inventory group to manage the sequence.

**A8** — `ansible-vault` encrypts files. To encrypt a single variable, you can use a separate `vars` file that is encrypted, or use the `!vault` syntax within a file, though typically you encrypt the entire file for simplicity.

**A9** — An **inventory** is a list of managed hosts. **Static** is a hardcoded file/list. **Dynamic** is a script/plugin that queries a cloud provider (AWS/GCP) to get the current list of hosts.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **handler** is a special task that only runs if notified by another task that a change occurred. You trigger it using the `notify` keyword.

**A12** — `ansible.cfg` configures Ansible behavior. Settings: `inventory` path, `remote_user`, and `forks`.

**A13** — `register` saves the output of a task into a variable. You use it via `{{ variable_name }}` in subsequent tasks (e.g., `when: variable_name.rc == 0`).

**A14** — `import_tasks` is static (processed at parse time). `include_tasks` is dynamic (processed at runtime). `include_tasks` allows for conditional evaluation of the included file itself.

**A15** — Galaxy is a hub for roles/collections. Use `requirements.yml` containing `roles:` and `collections:` lists, then run `ansible-galaxy install -r requirements.yml`.

**A16** — `ssh` uses standard SSH. `local` runs on the control node. `network_cli` is used for network devices (switches/routers) that don't support Python.

**A17** — `delegate_to` runs a task on a different host. `run_once` ensures a task runs only once for the whole play. 
**Example:**
```yaml
- name: Get info from remote
  shell: uptime
  register: remote_uptime
- name: Log to local
  shell: echo "{{ remote_uptime.stdout }}" >> local_log.txt
  delegate_to: localhost
  run_once: true
```

**A18** — 
1. **Forks:** Increase `forks` in `ansible.cfg` (Tradeoff: CPU/RAM on control node).
2. **Pipelining:** Enable `pipelining = True` (Tradeoff: Requires `requiretty` disabled in SSH).
3. **Fact Caching:** Use a Redis/JSON cache for facts (Tradeoff: Complexity).
4. **Mitogen:** Use the Mitogen plugin (Tradeoff: Third-party dependency).

**A19** — `{{ }}` is for expressions/variables. `{% %}` is for control logic (loops/ifs). `{# #}` is for comments.
```jinja2
upstream backend_servers {
{% for server in backend_list %}
  server {{ server.ip }}; # {{ server.comment }}
{% endfor %}
}
```

**A20** — 
1. Set `serial: 1` (or a small batch).
2. **Pre-task:** Remove server from Load Balancer (using `uri` module).
3. **Task:** Update application.
4. **Post-task:** Health check using `uri` module. If fails, trigger `rescue` block to rollback.
5. **Rollback:** In `rescue`, re-install previous version and re-add to LB.
