## Cloud Infrastructure Architecture

**CL1** — **IaaS** (Infrastructure as a Service) provides raw compute, storage, and networking (e.g., AWS EC2). **PaaS** (Platform as a Service) provides a framework for developers to build/deploy apps without managing OS/runtime (e.g., Azure App Service). **SaaS** (Software as a Service) provides a complete, ready-to-use application (e.g., M365).

**CL2** — The provider manages the underlying hardware, virtualization, and physical security.
* **IaaS VMs:** Provider manages hardware/hypervisor; You manage OS, middleware, apps, and data.
* **Managed K8s:** Provider manages Control Plane; You manage worker nodes (if not serverless), pods, and configurations.
* **SaaS:** Provider manages everything; You manage only your data and user access.

**CL3** — A **VPC** is a private isolated network. A **Subnet** is a range of IP addresses within a VPC. A **Security Group** acts as a virtual firewall for instances (stateful). A **NACL** is a firewall for subnets (stateless). They layer as: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Instance $\rightarrow$ Security Group. **Stateful** (SG) remembers connection state (allows return traffic automatically); **Stateless** (NACL) requires explicit rules for both inbound and outbound traffic.

**CL4** — A **Landing Zone** is a pre-configured, multi-account environment. **Organizational Units (OUs)** group accounts for policy application. **Guardrails** (SCP/Azure Policy) enforce compliance. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes egress/ingress. A **single-account approach** is problematic due to "blast radius" (one breach affects everything), lack of isolation for dev/prod, and difficulty in granular billing/permission management.

**CL5** — **IaC** is managing infrastructure via machine-readable files.
* **Terraform/OpenTofu:** Declarative, provider-agnostic, massive ecosystem. Best for multi-cloud.
* **Pulumi:** Uses general-purpose languages (Python, TS). Best for devs who want programmatic logic.
* **CloudFormation/Bicep:** Cloud-specific (AWS/Azure). Best for deep, native integration.
* **Crossplane:** Kubernetes-native IaC. Best for managing cloud resources via K8s CRDs.

**CL6** — **HPA** scales pods based CPU/RAM. **VPA** scales pod resource requests/limits. **Cluster Autoscaler** adds/removes nodes. **KEDA** is event-driven (e.g., scale based on Kafka lag). Use **KEDA** over HPA when scaling depends on external triggers (message queues, database metrics) rather than just resource utilization.

**CL7** — **RPO** (Recovery Point Objective) is data loss tolerance; **RTO** (Recovery Time Objective) is downtime tolerance. **Active-Active** (both regions live) provides lowest RTO/RPO but highest cost. **Active-Passive** (one standby) is cheaper. **Sync replication** (zero data loss, high latency) vs **Async** (low latency, potential data loss). **Pilot Light** (minimal core services running), **Warm Standby** (scaled-down version of full stack), **Multi-site Active-Active** (full capacity in both).

**CL8** — **GitOps** uses Git as the single source of truth for desired state. **ArgoCD** (pull-based, UI-heavy) vs **FluxCD** (pull-based, lightweight/CLI-focused). **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault/AWS SM), or **Vault** (direct injection). **Drift:** GitOps controllers detect the difference and automatically overwrite manual changes to match the Git state.

**CL9** — Use a **StatefulSet** for stable network IDs and ordered startup. Use **PV/PVC** with a **Local Persistent Volume** storage class for low latency. Use a **Headless Service** for direct pod-to-pod communication. Use **Init Containers** to prepare the filesystem. Use **ConfigMaps** mounted as volumes for config files. Use **Pod Disruption Budgets** to ensure availability during maintenance.

**CL10** — **Service Account** is a K8s identity. **Workload Identity/IRSA** maps a K8s Service Account to a Cloud IAM Role. **Mounting static credentials** (JSON keys) is bad because keys can be stolen/leaked. **Workload Identity Federation** uses OIDC to allow the cloud provider to trust the K8s identity, exchanging a short-lived token for cloud access without long-lived secrets.

**CL11** — **Object (S3/Blob):** Unstructured data, high durability ($11\times9$s), accessed via API. **Block (EBS):** Low-latency volumes for OS/DBs, attached to one instance. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB) accessible by many instances. Use Object for backups/media, Block for databases, File for shared configs/home dirs.

**CL12** — **Zero-Trust:** "Never trust, always verify." Use **Network Policies** (L3/L4 isolation), **Service Mesh (mTLS)** for L7 identity/encryption, **Pod Identity** for cloud access, **Admission Controllers** to enforce policy, **Image Signing** to ensure provenance, and **Falco** for runtime anomaly detection. Unlike perimeter models, Zero-Trust assumes the network is already breached and requires identity verification at every hop.

**CL13** — A **CDN** caches content at edge locations closer to users. Services: **AWS CloudFront / Azure Front Door**. Use a CDN for static assets/global users to reduce latency and origin load; use the origin directly for highly dynamic/private data where caching is impossible.

**CL14** — **Regions** are geographic areas; **Availability Zones (AZs)** are isolated data centers within a region. Deploy across multiple AZs to protect against a single data center failure. **Zonal resources** (e.g., an EBS volume) live in one AZ; **Regional resources** (e.g., S3) are available across the whole region.

**CL15** — A **Managed DB** handles patching, backups, hardware provisioning, and high availability. You handle schema design, query optimization, and user access.

**CL16** — **IAM Users** (people), **Groups** (collections of users), **Roles** (temporary identities for services/users), **Policies** (JSON permissions). **Least Privilege** means granting only the minimum permissions required to perform a task.

**CL17** — **Serverless** is event-driven compute (no server management). **Lambda/Functions** scale automatically. **Cold Starts** are the latency delay when a function is invoked after being idle. Serverless is a **poor fit** for long-running processes or high-performance computing with consistent, heavy loads.

**CL18** — **Ingress** is a K8s resource for L7 routing. **Gateway API** is the modern successor, offering better role separation (infra vs app). **Cloud LB Annotations** trigger cloud-native LBs. **Service Mesh Ingress** handles traffic at the mesh edge. **TLS Termination** can happen at the LB (edge), Ingress Controller, or the Pod (mTLS). Use **Gateway API** for complex, multi-tenant routing requirements.

**CL19** — Use **Reserved Instances/Savings Plans** for predictable loads. Use **Spot Instances** for stateless/batch workloads. **Right-size** instances using monitoring. Use **S3 Intelligent-Tiering** for storage. Implement **FinOps** (tagging, monthly reviews). Use **Showback** (reporting costs to teams) or **Chargeback** (billing teams directly) to drive accountability.

**CL20** — **Multi-cloud** uses **Kubernetes** as an abstraction layer and **Terraform** for IaC. Use **VPN/Interconnect** for networking and **OIDC/SAML** for identity. **Trade-offs:** Multi-cloud increases complexity and egress costs significantly. It is justified for high availability/regulatory needs, but often unnecessary for simple workload portability.

## OT Infrastructure Architecture

**OT1** — **Purdue Model (ISA-95):**
* **Level 0:** Physical process (sensors/actuators).
* **Level 1:** Basic Control (PLCs).
* **Level 2:** Supervisory Control (HMI/SCADA).
* **Level 3:** Site Operations (Historians/MES).
* **Level 4/5:** Enterprise/Business (IT/ERP).

**OT2** — **IT** focuses on Data Confidentiality; **OT** focuses on Availability/Safety. You cannot use standard IT patching because OT systems are sensitive to latency/jitter, and patching can cause unplanned downtime or "brick" legacy hardware that requires validated vendor testing.

**OT3** — An **IDMZ** separates IT (L4) from OT (L3). It acts as a buffer. Only specific, inspected traffic (e.g., via a proxy or jump host) should cross. Direct L4-to-L1 connectivity is dangerous because a compromised IT workstation could directly send malicious commands to a PLC, bypassing all safety controls.

**OT4** — 1. **Modbus TCP** (L1/L2), 2. **OPC UA** (L2/L3), 3. **EtherNet/IP** (L1/L2), 4. **PROFINET** (L1/L2), 5. **MQTT** (L3/L4/Cloud).

**OT5** — A **Firewall** is software-based and allows bidirectional traffic based on rules. A **Data Diode** is a hardware device allowing only one-way physical data flow. Use a diode for high-security segments (e.g., sending logs to IT) where you must guarantee no inbound commands can reach the OT side.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. **Security Boundaries:** Place a firewall/IDMZ between the SCADA/Historian and the Edge Gateway.

**OT7** — **Zones** are groupings of assets with similar security requirements. **Conduits** are the communication paths between zones. **Model:** [Corporate (L4)] $\rightarrow$ [IDMZ] $\rightarrow$ [SCADA/Engineering (L3)] $\rightarrow$ [Control (L2/L1)] $\rightarrow$ [Safety (SIS - isolated)].

**OT8** — **Strategy:** Implement VLANs for each production line. Place a firewall between L3 and L2. Use a "Cell/Area" architecture. For transition: Use a "tap" or mirror port to monitor traffic first, then implement segmentation line-by-line during scheduled maintenance windows.

**OT9** — **SIS** is for emergency shutdown; **BPCS** is for normal process control. **IEC 61511** is the functional safety standard. SIS must be isolated because if a ransomware attack hits the BPCS, the SIS must remain functional to prevent a physical catastrophe.

**OT10** — **PLC:** Local logic controller. **DCS:** Distributed control for large plants (integrated). **SCADA:** Supervisory system for geographically dispersed assets. They can coexist; SCADA often sits on top of PLCs.

**OT11** — Use **Jump Hosts** in the IDMZ with **MFA**. Use **Session Recording** for auditing. **Vendor access** should be "on-demand" and time-limited. Direct RDP from IT to HMI is unacceptable as it bypasses the IDMZ and provides a direct path for lateral movement.

**OT12** — **Plan:** 1. Isolate the VPN. 2. Use **Passive IDS** to detect anomalies. 3. Verify asset integrity. 4. **Response:** Coordinate with the control room to move to a "safe state." **Operator Role:** The operator manages the physical process safety; the security team manages the digital containment.

**OT13** — **HMI** is the visual interface for operators to interact with the process. An **Engineering Workstation** is used for programming/configuring PLCs/controllers.

**OT14** — A **Historian** records time-series process data. **Plant Historian (L3)** is for real-time operational visibility; **Enterprise Historian (L4)** is for long-term business analytics/reporting.

**OT15** — **Ladder Logic** is a graphical programming language used by **PLCs**. It remains dominant because it mimics electrical relay diagrams, making it intuitive for electricians/engineers.

**OT16** — **RTU** is used for remote, low-power, or geographically dispersed sites (e.g., water towers). **PLCs** are used for high-speed, localized factory automation.

**OT17** — **Analog** (continuous) vs **Digital** (on/off). **4-20mA** is preferred because if a wire breaks, the signal drops to 0mA (detectable as a fault), whereas 0-20mA would look like a valid "zero" reading.

**OT18** — **Inventory** is the foundation because you cannot protect what you don't know exists. **Passive monitoring** (sniffing traffic) is preferred; **Active scanning** is dangerous because it can crash sensitive, older OT devices.

**OT19** — **MITRE ATT&CK for ICS:** 1. **Inhibit Response Function** (e.g., disabling alarms), 2. **Impair Process Control** (e.g., changing setpoints), 3. **Loss of Safety** (e.g., disabling SIS), 4. **Impair Control** (e.g., DoS on PLC), 5. **Inhibit Control** (e.g., Man-in-the-middle). It differs by focusing on physical process impact rather than just data theft.

**OT20** — **SOC Design:** Use **Passive Network Monitoring** (e.g., Claroty/Nozomi) to avoid impacting real-time traffic. Integrate with SIEM. **Staffing:** IT analysts handle the network/OS alerts; OT engineers validate if a "firmware change" is a legitimate maintenance task or an attack. **Unauthorized firmware change:** Treat as a high-priority incident; isolate the device and verify the physical process state immediately.
