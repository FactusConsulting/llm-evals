## Application Architecture

**AA1** — A **Monolith** is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. **Microservices** decompose this into small, independent services communicating over a network.
*   **3 Problems introduced by Microservices:** 1. Network latency/unreliability; 2. Distributed data consistency (no ACID across services); 3. Operational complexity (observability, deployment, service discovery).

**AA2** — **Synchronous:** The caller waits for a response before proceeding (e.g., REST/HTTP). **Asynchronous:** The caller sends a message and continues immediately (e.g., RabbitMQ/AMQP).

**AA3** — An **API Gateway** handles application-level concerns (auth, rate limiting, routing, transformation). A **Reverse Proxy** handles network-level concerns (SSL termination, load balancing, caching). An API Gateway *cannot* replace a reverse proxy entirely because it lacks the low-level network optimization and protocol handling efficiency of a dedicated proxy, though modern gateways often incorporate proxy features.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions.
*   **Choreography:** Services exchange events; each service knows what to do next (decentralized). Best for simple workflows.
*   **Orchestration:** A central controller tells services what to do (centralized). Best for complex workflows with many steps.

**AA5** — **CQRS** separates read (Query) and write (Command) models. It is paired with **Event Sourcing** (storing state as a sequence of events) because Event Sourcing provides the "source of truth" needed to rebuild the read models. This solves the problem of "impedance mismatch" between complex write logic and optimized read requirements.

**AA6** — The **Circuit Breaker** prevents a failing service from cascading.
*   **States:** Closed (requests flow), Open (requests fail fast), Half-Open (testing if service recovered).
*   **Difference:** Retry handles transient blips; Circuit Breaker handles systemic failure. Use **both** by wrapping a retry logic *inside* a circuit breaker; if retries fail repeatedly, the breaker trips to protect the system.

**AA7** —
1.  **Shared DB/Shared Schema:** Lowest cost, highest density, highest security risk (data leakage), highest noisy-neighbor risk.
2.  **Shared DB/Separate Schema:** Moderate cost/complexity, better security (logical isolation), moderate noisy-neighbor risk.
3.  **Separate DB:** Highest cost/complexity, highest security (physical isolation), lowest noisy-neighbor risk.

**AA8** — **Strong consistency** ensures all reads see the latest write. **Eventual consistency** allows temporary divergence.
*   **Architecture:** Use **Strong Consistency** for inventory. Use a relational database (e.g., PostgreSQL) with **ACID** transactions and **Pessimistic Locking** (SELECT FOR UPDATE) or **Distributed Locks** (Redis/Etcd) to ensure a single source of truth for stock levels.

**AA9** — A **Sidecar** is a helper process running alongside a service. In **Istio**, **Envoy** acts as the sidecar (Data Plane) that intercepts all traffic. The **Control Plane** (Istiod) manages configuration and pushes policies to Envoy. **mTLS** between sidecars solves the problem of "identity" and "encryption in transit" within the internal network, which application-level TLS doesn't handle centrally/automatically.

**AA10** — **Strangler Fig:** Incrementally replace functionality.
*   **Strategy:** 1. Place an API Gateway in front of the .NET monolith. 2. Identify a single bounded context (e.g., "Billing"). 3. Build "Billing" in .NET 8. 4. Route "Billing" traffic through the Gateway to the new service. 5. Repeat until the monolith is "strangled."

**AA11** — **12-Factor App:** 1. Codebase, 2. Dependencies, 3. Config, 4. Backing services, 5. Build/Release/Run, 6. Processes, 7. Port binding, 8. Concurrency, 9. Disposability, 10. Dev/prod parity, 11. Build/release/run, 12. Admin processes. They ensure portability, scalability, and automation in cloud environments.

**AA12** —
*   **Kafka (Event-driven):** High throughput, decoupled, high scalability, complex debugging, strong ordering (per partition), handles spikes well.
*   **REST/gRPC (Request-driven):** Low latency, tight coupling, harder to scale for massive bursts, easier debugging, immediate feedback.
*   **Choice:** Use Kafka for background/asynchronous tasks (e.g., email, analytics); use REST/gRPC for user-facing, real-time requests.

**AA13** — A **Load Balancer** distributes traffic across multiple servers. **L4 (Transport):** Routes based on IP/Port (TCP/UDP). **L7 (Application):** Routes based on HTTP headers/paths/cookies. **Use Case:** Routing `/api/v1` to one service and `/static` to another.

**AA14** — A **Message Queue** (RabbitMQ) is for task distribution (once a message is consumed, it's gone). A **Log-based Broker** (Kafka) is a persistent append-only log (messages stay after consumption). Pick RabbitMQ for complex routing/tasking; pick Kafka for high-throughput stream processing/replayability.

**AA15** — A **Container** is an isolated user-space process sharing the host OS kernel. A **VM** includes a full guest OS. Containers are popular because they are lightweight, start instantly, and provide high density.

**AA16** — **Stateless:** No data is stored locally (e.g., a math API). **Stateful:** Stores data locally (e.g., a database). Stateless services scale horizontally easily because any instance can handle any request.

**AA17** — **ORM** maps code objects to DB tables. Examples: **Hibernate** (Java), **Entity Framework** (.NET). **Trade-offs:** ORMs increase developer velocity but can produce inefficient SQL; Raw SQL is faster/more precise but harder to maintain and prone to injection if not careful.

**AA18** — **Bulkhead pattern** isolates elements to prevent a single failure from taking down the whole system.
*   **Implementation:** Use separate **Thread Pools** for different service calls so a slow downstream service doesn't exhaust all threads; or use **Separate Deployment Groups** (separate clusters) for critical vs. non-critical services.

**AA19** — **OT** requires a central server to resolve conflicts (complex, high latency). **CRDTs** allow local updates that mathematically converge (low latency, great offline support). **Choice:** **CRDTs** for offline support, as they allow users to edit locally and merge seamlessly upon reconnection without a central arbiter.

**AA20** — **Challenges:** Propagating IDs across boundaries. **Context Propagation:** Using headers (W3C/B3) to pass TraceIDs. **Sampling:** Head-based (decide at start) vs. Tail-based (decide after seeing the whole trace). **Kafka:** Inject trace context into the message header. **Continuity:** The consumer must extract the header and start a new span linked to the producer's span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1:** Runs directly on hardware (e.g., VMware ESXi, Proxmox). **Type 2:** Runs on an OS (e.g., VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network):** Block-level storage (Fibre Channel/iSCSI) for high-performance DBs. **NAS (Network Attached Storage):** File-level storage (NFS/SMB) for shared files/documents.

**OP3** — **3-Tier:** Core $\rightarrow$ Distribution $\rightarrow$ Access. **Leaf-Spine:** Every leaf connects to every spine. It solves the "East-West" traffic bottleneck by providing predictable, low-latency paths between servers.

**OP4** — **Proxmox HA:** Requires $\ge 3$ nodes for quorum. **Fencing:** Use STONITH (Shoot The Other Node In The Head) via IPMI to prevent split-brain. **Storage:** Ceph (distributed) or iSCSI/NFS (centralized). **Failure:** If a node fails, the cluster detects loss of heartbeat, fences the node, and restarts VMs on surviving nodes.

**OP5** — **VLAN Trunking:** Carrying multiple VLANs over one link. **802.1Q:** Adds a tag to the Ethernet frame. **Linux Config:** Use sub-interfaces (e.g., `eth0.10`, `eth0.20`, `eth0.30`) to assign different VLAN IDs to the same physical NIC.

**OP6** — **RAID 1** (Mirror), **5** (Parity, min 3 drives), **6** (Double parity, min 4 drives), **10** (Mirror + Stripe). **Z2** (ZFS double parity). **Choice:** **RAID 10** for a database (best performance/IOPS) or **RAID 6/Z2** if capacity/fault tolerance is prioritized over write speed.

**OP7** — **Architecture:** Internal AD handles local auth. **DMZ** hosts public services. **Split-horizon:** Different DNS responses for internal vs. external queries. **DNSSEC** signs zones. **Laptop movement:** Use a VPN to reach internal resolvers; if on-site, use local DHCP-assigned DNS.

**OP8** — **Chain:** Root CA (Self-signed) $\rightarrow$ Subordinate CA (signed by Root) $\rightarrow$ End-entity. **PKI:** Root CA must be **offline**. **CRL/OCSP** check revocation. **Compromised Subordinate:** Can issue fake certs but Root is safe. **Compromised Root:** Total catastrophe; entire PKI must be rebuilt.

**OP9** — **MPLS:** High cost/reliability/low latency. **IPsec:** Low cost/high latency/internet-dependent. **SD-WAN:** Flexible/intelligent routing. **WireGuard:** Fast/secure mesh. **Recommendation:** **SD-WAN** for a balance of cost and reliability, using multiple internet links for VoIP redundancy.

**OP10** — **iDRAC/iLO/IPMI:** Out-of-band management (independent of OS). **Criticality:** Allows access if the OS crashes. **Exposure:** If exposed to the internet, it's a massive security risk (remote takeover).

**OP11** — **LVM:** Logical volume management (standard). **LVM-Thin:** Space-efficient (allocates on demand). **ZFS:** Copy-on-write, integrated volume manager/filesystem. **Snapshots:** LVM uses COW/metadata; ZFS uses COW at the filesystem level (extremely efficient).

**OP12** — **Stretch Cluster:** Requires low latency ($<5\text{ms}$ RTT). **Ceph:** Use CRUSH rules to ensure replicas are in different sites. **Split-brain:** Use a third site/witness for quorum. **2-site Ceph:** Bad because if the link breaks, both sites think they are the master (split-brain).

**OP13** — **DORA:** Discover, Offer, Request, Acknowledge. **Expired Lease:** Client attempts to renew; if server is down, it uses the current lease until it expires, then loses connectivity.

**OP14** — **Unmanaged:** Plug-and-play. **Managed:** Supports VLANs, Spanning Tree (STP), SNMP, and ACLs, essential for security and traffic control.

**OP15** — **NTP:** Syncs clocks. **Criticality:** Essential for logs, Kerberos/AD auth, and database consistency. **Drift:** Can break authentication and cause timestamped data corruption.

**OP16** — **Physical:** Full hardware. **VM:** Hardware abstraction. **Container:** OS abstraction. **Bare Metal:** Use for high-performance workloads (e.g., heavy DBs, GPU processing) to avoid hypervisor overhead.

**OP17** — **UPS:** Short-term battery. **Generator:** Long-term power. **ATS:** Switches the load from utility to generator automatically. You need both: UPS bridges the gap during the generator startup.

**OP18** — **Active-Passive:** One standby. **Active-Active:** Both serve traffic. **PostgreSQL HA:** Use **Pacemaker/Corosync** to manage a **Virtual IP (VIP)**. If the master fails, Pacemaker uses **STONITH** to kill the old master and moves the VIP to the standby.

**OP19** — **3-2-1:** 3 copies, 2 media, 1 offsite. **RPO/RTO:** RPO (data loss limit), RTO (downtime limit). **Immutable backups:** Protect against ransomware. **Backup vs DR:** Backup is data preservation; DR is the ability to restore service/infrastructure.

**OP20** — **802.1X:** **Supplicant** (device), **Authenticator** (switch), **Auth Server** (RADIUS). **EAP-TLS** (Certificates) is more secure than **PEAP** (Username/Pass). **Dynamic VLAN:** RADIUS returns a VLAN ID to the switch. **MAB:** Uses the device's MAC address as a fallback for "dumb" devices.
