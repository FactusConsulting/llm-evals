T1 — `tofu plan` creates an execution plan by comparing the current state to the configuration, showing what will be added, changed, or destroyed. `tofu apply` executes that plan to reach the desired state.

T2 — State is a JSON file that maps real-world resources to your configuration. Remote state is important for team collaboration (shared source of truth), state locking (preventing concurrent writes), and security (storing sensitive data outside local machines).

T3 — `count` uses an integer index, making it difficult to remove items from the middle of a list without causing shifts/recreations. `for_each` uses a map or set of strings, allowing you to add/remove specific items without affecting others. `for_each` is preferred for managing collections of resources where identity matters.

T4 — This is "configuration drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy between the actual cloud state and the recorded state, then proposes changes to bring the resource back in line with the configuration.

T5 — 
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

T6 — `terraform_remote_state` reads the entire state file of another module, which is a security risk and creates tight coupling. Output values are cleaner but require the modules to be called in the same configuration. The recommended alternative is passing outputs as inputs to the dependent module, or using a dedicated Service Discovery/KV store (like Consul) to decouple them.

T7 — The `null_resource` is being evaluated, but the `remote-exec` provisioner runs during the *apply* phase, not the *plan* phase. The output is calculated before the provisioner has actually finished writing the file to the target. **Fix:** Use a `local_file` resource or a `null_resource` with a `trigger` that depends on the completion of the provisioner, or better, use a native provider resource that handles the configuration file.

T8 — `import` brings existing infrastructure under OpenTofu management. Limitations include the need to manually write the HCL code to match the imported resource. The `import` block (1.5+) allows you to define the import declaratively in code, enabling `tofu plan` to generate the necessary HCL for you, making the process repeatable and easier to review.

T9 — A variable is an input parameter for a module. An `input variable` allows users to customize the configuration; an `output` exposes information from the module to the caller.

T10 — A provider is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS). If you run `tofu plan` without `tofu init`, OpenTofu will fail because it hasn't downloaded the necessary provider binaries.

T11 — It contains the specific versions and hashes of providers used. It should be committed to ensure all team members and CI/CD pipelines use the exact same provider versions, preventing "works on my machine" issues.

T12 — `tofu destroy` removes all resources managed by the current configuration. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

T13 — A data source is a way to fetch information from existing infrastructure that is *not* managed by the current OpenTofu configuration. Example: Fetching an existing VPC ID or an AMI ID using `data "aws_ami" "example"`.

T14 — `variable` blocks are for external inputs (parameters). `locals` are for internal logic/transformations (constants or derived values). Use `locals` to avoid repetition (DRY) and to perform complex string manipulations or logic that shouldn't be exposed as an input.

T15 — `lifecycle` controls resource behavior:
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
- `prevent_destroy`: Stops accidental deletion of critical resources.
- `ignore_changes`: Tells OpenTofu to ignore updates to specific attributes (useful when external processes/autoscaling modify a resource).

T16 — A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module in the code. This allows OpenTofu to update the state file without destroying and recreating the actual physical resource.

T17 — OpenTofu builds a Directed Acyclic Graph (DAG). **Implicit dependencies** occur when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are defined via `depends_on`. `depends_on` forces a specific order, reducing parallelism. It should be used sparingly because it can create bottlenecks and hide architectural flaws.

T18 — 
1. **State Splitting:** Break large states into smaller, decoupled workspaces (Tradeoff: increased complexity in passing outputs).
2. **Targeted Plans:** Use `-target` for specific changes (Tradeoff: ignores dependencies/drift in other areas).
3. **Reduce Refreshing:** Use `-refresh=false` (Tradeoff: risks applying changes against stale data).
4. **Provider Optimization:** Minimize the number of resources/providers per state (Tradeoff: requires architectural refactoring).

T19 — State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a process crashes, the lock remains. You can manually break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually running, you risk state corruption and resource duplication.

T20 — 
1. **Configure Backend:** Update the `terraform` block with `s3` and `dynamodb_table` settings.
2. **Run Init:** Run `tofu init`. OpenTofu will detect the change from local to remote and prompt you to migrate the state.
3. **Confirm Migration:** Type `yes` to copy the local state to S3.
4. **Verify:** Check the S3 bucket for the `.tfstate` file and run `tofu plan` to ensure no unexpected changes are detected.

A1 — **Playbook:** The high-level script defining the automation. **Role:** A structured collection of tasks, variables, and files for reuse. **Task:** A single unit of work (e.g., installing a package).

A2 — `ansible_facts` is a dictionary of system information gathered by Ansible. Access OS family via `ansible_facts['os_family']` or `{{ ansible_os_family }}`.

A3 — `command`: Executes a command without a shell (safer, no environment variables/pipes). `shell`: Executes via `/bin/sh` (allows pipes, redirects, and environment variables). `raw`: Executes via SSH without needing Python on the target (used for bootstrapping).

A4 — Idempotency means running a task multiple times results in the same state. 
- **Idempotent:** `apt: name=nginx state=present` (if installed, does nothing).
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file.txt` (appends a new line every time it runs).

A5 — 
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}" # Note: logic for epel-release would be a separate task
  # Better approach:
  block:
    - name: Install for Debian
      apt: name=htop state=present
      when: ansible_os_family == "Debian"
    - name: Install for RedHat
      yum: name={{ item }} state=present
      loop: [epel-release, htop]
      when: ansible_os_family == "RedHat"
```

A6 — `extra_vars` (highest) > `set_fact` > `role defaults` (lowest). `group_vars` and `host_vars` sit in the middle, with `host_vars` overriding `group_vars`.

A7 — Use `serial: 3` in the playbook to process 3 nodes at a time. Use an inventory group for the agents. Use the `wait_for` module to ensure the RKE2 service is listening on a specific port before moving to the next batch.

A8 — `ansible-vault` encrypts files/variables. To encrypt a single variable, you can use `ansible-vault encrypt_string 'my_secret_value' --name 'my_var'`, then paste the resulting block into your vars file.

A9 — **Inventory:** A list of managed hosts. **Static:** A hardcoded file (INI/YAML). **Dynamic:** A script or plugin that queries a cloud provider (AWS/GCP) to fetch the current list of hosts.

A10 — `ansible webservers -m shell -a "df -h"`

A11 — A **handler** is a task that only runs when notified by another task. It differs from a regular task because it only executes once at the end of the play, even if notified multiple times. Trigger it using `notify: <handler_name>`.

A12 — `ansible.cfg` configures Ansible behavior. Common settings: `inventory`, `remote_user`, and `forks`.

A13 — `register` captures the output of a task into a variable. You can then use that variable in a `when` clause or a subsequent task (e.g., `when: result.rc == 0`).

A14 — `import_tasks` is **static** (processed at parse time); it behaves like a copy-paste. `include_tasks` is **dynamic** (processed at runtime); it allows for loops and conditionals. `include_tasks` is better for flexibility, but `import_tasks` is better for performance and predictable error checking.

A15 — **Ansible Galaxy** is a hub for sharing roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

A16 — **ssh:** Standard remote execution via SSH. **local:** Executes tasks on the control node itself. **network_cli:** Used for network devices (switches/routers) that don't have Python; it uses a specialized CLI-based interaction.

A17 — `delegate_to` runs a task on a different host than the current target. `run_once` ensures a task runs only once for the entire play. 
**Example:** 
```yaml
- name: Register node in central DB
  shell: "register_node.sh {{ ansible_host }}"
  delegate_to: localhost
  run_once: true
```

A18 — 
1. **Forks:** Increase `forks` in `ansible.cfg` to run more tasks in parallel (Tradeoff: higher CPU/RAM on control node).
2. **Pipelining:** Enable `pipelining = True` to reduce SSH connections (Tradeoff: requires `requiretty` to be disabled on targets).
3. **Fact Caching:** Use Redis/Memcached to store facts (Tradeoff: complexity of managing a cache server).
4. **Mitogen:** Use the Mitogen plugin for highly optimized SSH execution (Tradeoff: third-party dependency).

A19 — `{{ }}` is for expressions/variables. `{% %}` is for control logic (loops/ifs). `{# #}` is for comments.
```jinja2
upstream backend_servers {
{% for server in backend_list %}
    server {{ server }}; # Health check enabled
{% endfor %}
}
```

A20 — 
1. **Serial:** Use `serial: 4` to deploy in batches of 4.
2. **Pre-task:** Use `uri` module to remove the server from the Load Balancer.
3. **Deployment:** Perform the update.
4. **Post-task:** Use `uri` module to perform a health check on the local app. If successful, re-add to LB.
5. **Rollback:** Wrap the deployment in a `block`. If a task fails, the `rescue` block triggers a rollback (e.g., re-installing the previous version) and notifies the team.
