AA1 — A monolith is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. Microservices decompose this into small, independent services communicating over a network. 
**3 Problems introduced by microservices:** 1) Network latency/unreliability, 2) Distributed data consistency (no more ACID transactions across services), 3) Operational complexity (observability, deployment, and service discovery).

AA2 — **Synchronous:** The client sends a request and waits (blocks) for a response. Example: REST/HTTP. **Asynchronous:** The client sends a message/request and continues its work without waiting for an immediate response. Example: RabbitMQ/AMQP.

AA3 — An **API Gateway** is application-aware; it handles high-level concerns like authentication, rate limiting, request transformation, and orchestration. A **reverse proxy** (like Nginx) primarily handles traffic routing, SSL termination, and load balancing at the network/transport layer. 
**Can it replace?** Not entirely. While modern gateways can do proxying, a dedicated reverse proxy is often more efficient for low-level tasks (like static file serving or simple TCP routing) without the overhead of application-layer logic.

AA4 — The **Saga pattern** manages distributed transactions by a sequence of local transactions. Each local transaction updates the database and triggers the next step. 
**Choreography:** Services exchange events without a central controller (decentralized). Best for simple workflows. 
**Orchestration:** A central "orchestrator" tells each service what to do (centralized). Best for complex workflows with many steps.

AA5 — **CQRS** separates read operations (Queries) from write operations (Commands). It is often paired with **Event Sourcing** (storing state as a sequence of events rather than current state) because the event log provides a perfect audit trail for the "Command" side and can be projected into optimized "Read" models. This solves the problem of complex data models trying to serve both high-performance writes and complex, diverse read requirements simultaneously.

AA6 — The **Circuit Breaker** prevents a system from repeatedly trying an operation that is likely to fail. 
**States:** 1) **Closed** (requests flow normally), 2) **Open** (requests fail immediately), 3) **Half-Open** (limited requests allowed to test if the service recovered). 
**Difference:** A **retry with backoff** assumes a transient failure and tries again; a **circuit breaker** assumes a systemic failure and stops trying to protect the caller and the callee. Use them together by using a circuit breaker to "trip" when retries consistently fail.

AA7 — 
1. **Shared DB/Schema:** Lowest cost, highest density, but highest security risk (data leakage) and highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Balanced cost/security. Better isolation than row-level, but still shares DB resources (CPU/RAM).
3. **Separate DB:** Highest cost and operational complexity, but highest security and lowest noisy-neighbor risk.

AA8 — **Eventual consistency** means data will be consistent across all nodes "eventually" (e.g., DNS). **Strong consistency** ensures all reads return the latest write immediately. 
**Architecture:** For inventory, use **Strong Consistency**. Use a distributed SQL database (e.g., CockroachDB) or a RDBMS with strict ACID properties. Use the **Reservation Pattern**: when a user adds to cart, "reserve" the item in a pending state to prevent overselling before the final transaction.

AA9 — A **sidecar proxy** (like Envoy) runs alongside the application container to handle networking. In **Istio**, Envoy is the **Data Plane** (handles actual traffic), while Istio's control plane (Istiod) manages configuration and certificates. **mTLS** between sidecars solves the problem of identity and encryption; application-level TLS is harder to manage, rotate, and implement consistently across a polyglot environment.

AA10 — The **Strangler Fig pattern** involves placing a proxy in front of the monolith and routing new/migrated functionality to the new microservices. 
**Strategy:** 1) Deploy an API Gateway/Proxy. 2) Identify a low-risk bounded context (e.g., "Notifications"). 3) Build that context in .NET 8. 4) Route "Notification" traffic from the proxy to the new service. 5) Repeat until the .NET Framework monolith is "strangled" and can be decommissioned.

AA11 — The **12-Factor App** ensures cloud-native readiness. 
1. **Codebase:** One repo per service. 2. **Dependencies:** Explicitly declare them. 3. **Config:** Store in environment variables. 4. **Backing services:** Treat them as attached resources. 5. **Build, release, run:** Strict separation of stages. 6. **Processes:** Statelessness. 
These matter because they enable automated deployment, scalability, and portability across cloud providers.

AA12 — 
- **Kafka (Event-driven):** High scalability, loose coupling, high debugging complexity, excellent for "fire and forget" or many consumers. Guarantees ordering within a partition.
- **REST/gRPC (Request-driven):** Tight coupling, lower scalability (synchronous), easier debugging, immediate feedback. 
**Choose Kafka** for high-throughput, asynchronous workflows (e.g., analytics). **Choose REST/gRPC** for real-time user-facing requests where an immediate response is required.

AA13 — A **load balancer** distributes incoming network traffic across multiple servers. **Layer 4** (Transport) routes based on IP and Port (TCP/UDP). **Layer 7** (Application) routes based on HTTP headers, cookies, or URL paths. **Use case for L7:** Routing `/api/v1/users` to one service and `/api/v1/orders` to another.

AA14 — A **message queue** (RabbitMQ) stores messages until a consumer processes them (often deleted after). A **log-based broker** (Kafka) appends messages to a persistent log that can be replayed by multiple consumers. 
**Pick RabbitMQ** for complex routing and individual message acknowledgment. **Pick Kafka** for high-throughput stream processing and event replayability.

AA15 — A **container** is an isolated user-space process sharing the host OS kernel. A **VM** includes a full guest OS and a hypervisor. Containers are popular because they are lightweight, start instantly, and ensure "it works on my machine" consistency across environments.

AA16 — **Stateless:** Does not store client data between requests (e.g., a math API). **Stateful:** Stores data/context (e.g., a database). Stateless services are easier to scale because any instance can handle any request; you just spin up more.

AA17 — An **ORM** maps database tables to programming objects. Examples: **Hibernate** (Java), **Entity Framework** (C#). 
**Trade-offs:** ORMs increase developer productivity and security (SQL injection protection) but can lead to inefficient "N+1" queries and performance overhead compared to optimized raw SQL.

AA18 — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function. 
**Implementation:** Use separate **thread pools** for different service calls (e.g., one pool for the "Payment" service, one for "Search"). If the Payment service hangs, it only exhausts its own thread pool, leaving the Search service responsive.

AA19 — **OT** requires a central server to resolve conflicts by transforming operations. **CRDTs** are mathematically designed so that concurrent updates can be merged without a central server. 
**Choice:** For **offline support**, choose **CRDTs**. They allow users to make changes locally and merge them seamlessly when they reconnect, whereas OT's reliance on a central server makes offline reconciliation extremely difficult.

AA20 — **Context Propagation:** Passing a unique ID (Trace ID) through headers (W3C Trace Context). **Sampling:** Head-based (decide at start) vs Tail-based (decide after seeing the whole trace, better for catching errors). **Asynchronous:** To ensure continuity in Kafka, the producer must inject the trace context into the Kafka message headers so the consumer can extract it and continue the span.

OP1 — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., VMware ESXi, Xen). **Type 2 (Hosted):** Runs on an OS (e.g., Oracle VirtualBox, VMware Workstation).

OP2 — **SAN (Storage Area Network):** Block-level storage (e.g., iSCSI, Fibre Channel) used for databases/VMs. **NAS (Network Attached Storage):** File-level storage (e.g., NFS, SMB) used for shared files/folders.

OP3 — **3-tier:** Core, Distribution, Access. **Leaf-Spine:** A two-tier architecture where every leaf switch connects to every spine switch. It solves the "east-west" traffic bottleneck and provides predictable latency/bandwidth in modern data centers.

OP4 — **Architecture:** Minimum 3 nodes for quorum. Use **Ceph** for shared storage. Use **Fencing (STONITH)** to prevent split-brain. If a node fails, the cluster detects the loss of quorum/heartbeat, the remaining nodes elect a new leader, and the storage/VMs are restarted on healthy nodes.

OP5 — **VLAN Trunking** allows multiple VLANs to travel over one link using **802.1Q tagging** (adding a VLAN ID to the frame). On Linux, use **sub-interfaces** (e.g., `eth0.10`, `eth0.20`) via `ip link` or Netplan.

OP6 — **RAID 1** (Mirroring), **5** (Parity, 1 drive loss), **6** (Double parity, 2 drive loss), **10** (Striped Mirrors), **Z2** (ZFS equivalent of RAID 6). 
**Choice:** **RAID 10** for a database. It provides the best performance (no parity calculation overhead) and high fault tolerance.

OP7 — Use **Split-horizon DNS** to serve different IPs for internal vs external queries. **Recursive resolvers** handle client queries; **Authoritative servers** hold the zones. **Conditional forwarding** sends specific domains to specific servers. **DNSSEC** adds digital signatures to prevent spoofing. A laptop moving to VPN would use the internal DNS via the VPN tunnel.

OP8 — **Chain:** Root CA $\rightarrow$ Subordinate CA $\rightarrow$ End-entity. **Deployment:** Root CA must be **offline**. Use **Subordinate CAs** for daily signing. **CRL/OCSP** check for revoked certs. **Compromised Subordinate:** Only that branch is invalid. **Compromised Root:** The entire PKI is dead and must be rebuilt.

OP9 — **Recommendation:** **SD-WAN** or **WireGuard mesh**. For 50 users/site with VoIP, SD-WAN provides path selection (prioritizing VoIP over internet/MPLS) and better management. MPLS is reliable but expensive; IPsec is cheap but high latency.

OP10 — **iDRAC/iLO/IPMI** provides remote hardware management (power, BIOS, console). It is critical for "lights-out" data centers. If exposed to the internet, an attacker can gain full control of the hardware, bypass the OS, and wipe the server.

OP11 — **LVM:** Logical volume management (flexible resizing). **LVM-Thin:** Allows over-provisioning. **ZFS:** Combined file system and volume manager with copy-on-write. **Snapshots:** LVM/LVM-Thin are "pointer-based" (can be slow if many exist); ZFS uses copy-on-write (extremely efficient).

OP12 — **Stretch Cluster:** Requires low-latency links (<5ms). Use **Ceph CRUSH rules** to ensure data replicas are spread across sites. Use a **third site (Tiebreaker/Witness)** to prevent split-brain. 2-site without a tiebreaker is dangerous because if the link breaks, both sites might think they are the master.

OP13 — **DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge. If the server is unavailable, the client uses an **APIPA** address (169.254.x.x).

OP14 — **Managed switches** allow configuration of VLANs, Spanning Tree (STP), SNMP, and Port Security. **Unmanaged** are "plug-and-play" and offer no visibility or control.

OP15 — **NTP** ensures all logs and authentication (Kerberos) are synchronized. If clocks drift, distributed databases fail to order events correctly, and security protocols like Kerberos will reject logins.

OP16 — **Physical:** Hardware. **VM:** Hardware + OS. **Container:** OS + App. Run on **Bare Metal** for high-performance workloads (e.g., heavy databases or high-frequency trading) to avoid hypervisor overhead.

OP17 — **UPS** provides immediate battery power for short durations; **Generator** provides long-term power. An **ATS** automatically switches the load from utility to generator when it detects a failure.

OP18 — **Active-Passive:** One node is standby. **Active-Active:** Both nodes handle traffic. 
**PostgreSQL HA:** Use **Pacemaker/Corosync** to manage a **Virtual IP (VIP)**. If the primary fails, Corosync detects it, Pacemaker executes **STONITH** (fencing) to kill the old node, and moves the VIP to the standby node.

OP19 — **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite. **RPO** (data loss window) and **RTO** (downtime window). **Immutable backups** (WORM) protect against ransomware. **Backup** is copying data; **Disaster Recovery** is the plan/process to restore operations.

OP20 — **802.1X:** **Supplicant** (device), **Authenticator** (switch), **Authentication Server** (RADIUS). **EAP-TLS** uses certificates (strongest); **PEAP** uses usernames/passwords. **Dynamic VLAN assignment** places users in specific VLANs based on their identity. **MAB** allows non-802.1X devices (printers) to connect by checking their MAC address against a whitelist.
