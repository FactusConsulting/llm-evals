## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking (e.g., AWS EC2). **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying OS/runtime (e.g., Azure App Service). **SaaS (Software as a Service):** Fully functional software delivered via web (e.g., Microsoft 365).

**CL2** — The provider is responsible for the "security *of* the cloud" (hardware, global infrastructure); the customer is responsible for "security *in* the cloud" (data, IAM, OS configuration).
* **IaaS VMs:** Provider manages hardware/hypervisor; You manage OS, patching, and apps.
* **Managed Kubernetes:** Provider manages control plane; You manage worker nodes, pods, and network policies.
* **SaaS (M365):** Provider manages almost everything; You manage user access, data classification, and device security.

**CL3** — **VPC:** A private isolated network. **Subnet:** A range of IP addresses within a VPC. **Security Group (SG):** A virtual firewall for *instances* (stateful). **NACL:** A firewall for *subnets* (stateless). They layer from VPC $\rightarrow$ Subnet $\rightarrow$ Instance. **Stateful (SG):** If you allow inbound traffic, outbound response is automatically allowed. **Stateless (NACL):** You must explicitly define both inbound and outbound rules for traffic to flow.

**CL4** — A **Landing Zone** is a pre-configured, multi-account environment following best practices. **OUs (Organizational Units)** group accounts by function (e.g., Prod, Dev). **Guardrails** are automated policies (SCPs) to prevent non-compliance. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes connectivity to reduce complexity. **Centralized Logging** ensures auditability across all accounts. A **single-account approach** is problematic due to "blast radius" (one error affects everything), difficulty in granular billing, and lack of isolation between environments.

**CL5** — **IaC** is managing infrastructure via machine-readable files.
* **Terraform/OpenTofu:** Declarative, provider-agnostic, massive ecosystem. Best for multi-cloud.
* **Pulumi:** Uses general-purpose languages (Python, Go). Best for devs who want loops/logic.
* **CloudFormation/Bicep:** Native to AWS/Azure. Best for deep, seamless integration with provider-specific features.
* **Crossplane:** Kubernetes-native IaC. Best if you want to manage cloud resources via K8s APIs.

**CL6** — **HPA:** Scales pods based on CPU/RAM. **VPA:** Adjusts pod resource requests/limits. **Cluster Autoscaler:** Adds/removes VM nodes to the cluster. **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag or RabbitMQ queue depth). Use **KEDA** over HPA when scaling needs to be triggered by external event metrics rather than just resource utilization.

**CL7** — **RPO (Recovery Point Objective):** Max data loss allowed. **RTO (Recovery Time Objective):** Max downtime allowed.
* **Active-Active:** Traffic split across regions; zero downtime; highest cost; complex state sync.
* **Active-Passive:** One region idle; lower cost; requires DNS failover (Route53).
* **Pilot Light:** Minimal version of services always running (e.g., DB only); data is synced; fast recovery.
* **Warm Standby:** Scaled-down version of the full stack is running; faster than pilot light; more expensive.
* **Multi-site Active-Active:** Full capacity in both regions; lowest RTO/RPO; highest cost.
* **State Management:** Use global databases (DynamoDB Global Tables) for sync replication; async for lower latency/higher cost.

**CL8** — **GitOps** uses Git as the "single source of truth" for desired state. **ArgoCD** (pull-based, UI-heavy) vs. **FluxCD** (lightweight, CLI-focused). **Secrets:** Use **External Secrets Operator** to pull from AWS Secrets Manager/Vault, or **Sealed Secrets** to store encrypted secrets in Git. **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and automatically overwrites the manual change to match the Git state.

**CL9** — Use a **StatefulSet** to ensure stable network IDs and ordered deployment. Use **Local Persistent Volumes** with a local storage class for low latency. Use a **Headless Service** for direct pod-to-pod communication. Use **Init Containers** to prepare the filesystem or fetch configs. Mount **ConfigMaps** as volumes to specific paths. Implement a **Pod Disruption Budget (PDB)** to ensure availability during maintenance.

**CL10** — **Service Account:** K8s identity. **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role. **Bad Practice:** Mounting long-lived credentials (JSON keys) in pods risks exposure if a pod is breached. **Workload Identity Federation** solves this by using short-lived, OIDC-based tokens to exchange K8s identity for cloud permissions without static keys.

**CL11** — **Object (S3/Blob):** Unstructured data, highly durable (11 9s), accessed via API. **Block (EBS):** Low-latency disk for VMs, high performance. **File (EFS/Azure Files):** Shared filesystem for multiple instances (NFS/SMB). Use Object for backups/media, Block for DBs/OS, and File for shared config/home directories.

**CL12** — **Zero-Trust:** "Never trust, always verify." **Architecture:** Use **Network Policies** for micro-segmentation, a **Service Mesh (Istio/Linkerd)** for mTLS (identity-based encryption), **Admission Controllers (OPA)** to enforce policy, **Image Signing (Cosign)** to ensure provenance, and **Falco** for runtime threat detection. Unlike perimeter security (firewalls), Zero-Trust assumes the network is already breached and secures every individual interaction.

**CL13** — **CDN** caches content at edge locations closer to users to reduce latency. Services: **CloudFront (AWS)** or **Azure CDN**. Use a CDN for static assets (images, JS, CSS) or high-traffic web content to offload the origin server and improve global performance.

**CL14** — **Regions:** Geographic areas (e.g., us-east-1). **Availability Zones (AZs):** Isolated data centers within a region. Deploy across multiple AZs to protect against a single data center failure. **Zonal resources** (e.g., an EBS volume) live in one AZ; **Regional resources** (e.g., an S3 bucket) are available across the whole region.

**CL15** — **Managed DB (RDS):** Cloud provider handles patching, backups, hardware, and high availability. **Self-managed (VM):** You handle everything. Managed services reduce operational overhead and "undifferentiated heavy lifting."

**CL16** — **IAM User:** Individual person. **Group:** Collection of users. **Role:** Temporary identity assumed by users/services. **Policy:** JSON document defining permissions. **Least Privilege:** Granting only the minimum permissions required for a task (e.g., `s3:GetObject` instead of `s3:*`).

**CL17** — **Serverless:** Running code without managing servers. **Lambda/Functions:** Event-driven execution. **Cold Start:** Latency when a function is invoked after being idle (container spin-up). **Poor fit:** Long-running processes, high-performance computing, or applications requiring constant low-latency response.

**CL18** — **Ingress:** Basic L7 routing. **Gateway API:** Next-gen, role-oriented (Infrastructure vs. App dev). **Cloud LB Annotations:** Triggers a cloud provider's LB (e.g., ALB). **Service Mesh Ingress:** Handles complex traffic routing/mTLS. **TLS Termination:** Can happen at the Cloud LB, Ingress Controller, or Service Mesh. **Gateway API** is preferred for its improved expressiveness and separation of concerns.

**CL19** — **Strategy:** Use **Reserved Instances/Savings Plans** for predictable workloads; **Spot** for stateless/batch; **Right-sizing** via tools like AWS Compute Optimizer. **Storage:** Move old data to **S3 Glacier**. **FinOps:** Implement **Tagging** for cost allocation. Use **Showback** (reporting costs to teams) or **Chargeback** (billing teams directly). Tools: AWS Cost Explorer, CloudHealth, or Kubecost.

**CL20** — **Strategy:** Use **Kubernetes** as the abstraction layer for compute, **Terraform** for IaC, and **Terraform Cloud/Pulumi** for multi-cloud orchestration. Use **VPN/Direct Connect** for cross-cloud networking and **OIDC/SAML** for identity federation. **Trade-off:** Multi-cloud increases complexity and cost but prevents vendor lock-in. It is justified for extreme high availability or regulatory requirements, but often unnecessary for most startups.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** A framework for ICS security. **Level 0:** Physical process (sensors/actuators). **Level 1:** Basic control (PLCs). **Level 2:** Area supervisory control (HMIs/SCADA). **Level 3:** Site-wide operations (Historians). **Level 4/5:** Enterprise/Corporate network.

**OT2** — **IT** focuses on Data Confidentiality; **OT** focuses on Process Availability and Safety. You cannot use standard IT patching because a reboot or high CPU usage could cause a physical process to fail, leading to equipment damage or injury.

**OT3** — An **IDMZ** acts as a buffer. Traffic should be strictly controlled (e.g., via a proxy or data historian). Only specific, inspected traffic (e.g., MQTT or OPC UA) should pass. Direct connectivity from L4 to L1 is dangerous because a single compromised workstation could directly manipulate physical hardware.

**OT4** — 1. **Modbus TCP:** L1/L2 (Fieldbus/Control). 2. **OPC UA:** L2/L3 (Supervisory/Data exchange). 3. **EtherNet/IP:** L1/L2 (Control). 4. **PROFINET:** L1/L2 (Real-time control). 5. **MQTT:** L3/L4 (Edge-to-Cloud/Telemetry).

**OT5** — A **Data Diode** is a hardware device that allows data to flow in only one direction (physically impossible to go back). A **Firewall** is software-based and bidirectional. Use a diode for high-security "one-way" telemetry. A firewall is more flexible but can be misconfigured or bypassed via software exploits.

**OT6** — **Flow:** Sensor $\rightarrow$ PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway (MQTT) $\rightarrow$ Cloud Ingestion. **Security Boundary:** Place the IDMZ between the Historian (L3) and the Edge Gateway (L4/Cloud).

**OT7** — A **Zone** is a grouping of assets with similar security requirements. A **Conduit** is the communication path between zones. **Model:** [Corporate Zone] $\rightarrow$ (Conduit) $\rightarrow$ [IDMZ] $\rightarrow$ (Conduit) $\rightarrow$ [SCADA Zone] $\rightarrow$ (Conduit) $\rightarrow$ [PLC Zone] $\rightarrow$ (Conduit) $\rightarrow$ [SIS Zone (Isolated)].

**OT8** — **Strategy:** Implement VLANs to segment production lines. Place industrial firewalls between lines. Use a managed switch architecture. For **Remote Access**, use a secure VPN into an IDMZ jump host. **Transition:** Use "Passive Monitoring" first to map the network, then implement segmentation line-by-line during scheduled maintenance windows.

**OT9** — **SIS** is the independent safety layer (e.g., emergency shutdown); **BPCS** is the standard control layer. **IEC 61511** is the functional safety standard. SIS must be isolated to prevent a single failure (or cyberattack) from disabling both control and safety. If ransomware hits the SIS, it could prevent an emergency shutdown during a physical crisis, leading to catastrophe.

**OT10** — **PLC:** Logic for a single machine. **DCS (Distributed Control System):** Large-scale, integrated control for continuous processes (e.g., oil refinery). **SCADA:** Supervisory control for geographically dispersed assets. They can coexist; SCADA often supervises multiple DCS/PLC sites.

**OT11** — Use **Jump Hosts** in an IDMZ, enforce **MFA**, and use **Session Recording** for auditing. **Vendor Access** must be time-limited and "on-demand." Direct RDP to an HMI is unacceptable because it bypasses all monitoring and provides a direct path for lateral movement.

**OT12** — **Detection:** Deploy an OT-specific IDS (e.g., Nozomi, Dragos) to monitor L3 traffic for anomalies. **Response:** Isolate the compromised VPN segment. **Coordination:** Work with the plant operator to ensure the process is in a "Safe State" before disconnecting network segments. The **Operator** is the ultimate authority on whether a cyber-action will cause a physical hazard.

**OT13** — **HMI** is the visual interface for operators to interact with the process. An **Engineering Workstation** is used to program/configure PLCs and logic; it is a much higher-privilege device.

**OT14** — A **Historian** is a database that records time-series process data. **Plant Historian (L3):** High-resolution, local data for real-time control. **Enterprise Historian (L4):** Aggregated, lower-resolution data for business analytics.

**OT15** — **Ladder Logic** is a graphical programming language resembling electrical relay diagrams. It is executed by a **PLC**. It remains dominant because it is intuitive for electricians and engineers trained in traditional control systems.

**OT16** — An **RTU** is designed for long-distance, low-bandwidth communication (e.g., remote pipelines/water stations). **PLCs** are designed for high-speed, local logic. RTUs are better for harsh, remote environments with intermittent connectivity.

**OT17** — **Analog (4-20mA):** Continuous variable. **Digital:** On/Off. **4-20mA** is preferred because a "0mA" reading indicates a broken wire (fail-safe), whereas 0-20mA cannot distinguish between a zero reading and a wire fault.

**OT18** — **Inventory** is knowing every device to manage risk. **Techniques:** **Passive Monitoring** (sniffing traffic) is safe; **Active Scanning** (pinging/probing) is dangerous because it can crash older, sensitive OT devices.

**OT19** — **MITRE ATT&CK for ICS:** 1. **Inhibit Response Function** (e.g., disabling an alarm). 2. **Impair Process Control** (e.g., changing setpoints). 3. **Impair Process Safety** (e.g., disabling SIS). 4. **Damage to Property** (e.g., over-pressurizing a tank). 5. **Loss of View** (e.g., freezing HMI screens). It differs from Enterprise by focusing on physical consequences. Use it to map your current visibility against known ICS attack patterns.

**OT20** — **SOC Design:** Use passive sensors to feed an **OT-specific SIEM**. **Triage:** Alerts must be vetted by an **OT Engineer** to ensure they aren't false positives caused by normal process changes. **Firmware Alert:** Treat as a critical incident; immediately isolate the PLC, verify the physical process state with the operator, and check the "Golden Image" against the current firmware.
