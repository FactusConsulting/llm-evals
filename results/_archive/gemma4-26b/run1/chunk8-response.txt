## Cloud Infrastructure Architecture

**CL1**
*   **IaaS (Infrastructure as a Service):** Provides raw computing resources (VMs, storage, networking). You manage the OS, middleware, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying infrastructure. *Example: Google App Engine.*
*   **SaaS (Software as/a Service):** Fully functional software delivered via the web. The provider manages everything. *Example: Salesforce.*

**CL2**
The provider manages the security **of** the cloud (hardware, global infra); the customer manages security **in** the cloud (data, IAM, configs).
*   **IaaS VMs:** Provider manages physical host/hypervisor; You manage OS, patching, and firewall rules.
*   **Managed Kubernetes:** Provider manages Control Plane; You manage worker nodes (if not serverless), container images, and Network Policies.
*   **SaaS (M365):** Provider manages everything including the app; You manage identity (users), data classification, and access permissions.

**CL3**
*   **VPC:** A private, isolated virtual network.
*   **Subnet:** A range of IP addresses within a VPC (Public or Private).
*   **Security Group (SG):** A virtual firewall for **instances** (stateful).
*   **NACL:** A firewall for **subnets** (stateless).
*   **Layering:** Traffic enters the VPC $\rightarrow$ hits the NACL (subnet level) $\rightarrow$ hits the SG (instance level).
*   **Stateful vs. Stateless:** SGs are **stateful** (if you allow inbound port 80, outbound response is automatically allowed). NACLs are **stateless** (you must explicitly define both inbound and outbound rules for a flow to work).

**CL4**
*   **Landing Zone:** A pre-configured, multi-account environment with baseline security/compliance.
*   **Organizational Units (OUs):** Logical groupings of accounts (e.g., Prod, Dev, Security) to apply hierarchical policies.
*   **Guardrails:** Service Control Policies (SCPs) that restrict actions (e.g., "Prevent disabling CloudTrail").
*   **Shared Networking:** Using Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize inspection/egress via a "Hub" VPC/VNet, reducing complexity.
*   **Centralized Logging:** Aggregating logs (CloudTrail, VPC Flow) into a dedicated, immutable Security account.
*   **Why not single-account?** Single-accounts lack blast radius isolation, hit API rate limits faster, and make granular billing/permission management difficult.

**CL5**
*   **Terraform/OpenTofu:** Declarative, provider-agnostic (HCL). Best for multi-cloud/standard infra.
*   **Pulumi:** Uses general-purpose languages (Python, TS). Best for developers who want loops/logic/testing frameworks.
*   **CloudFormation/Bicep:** Cloud-native (AWS/Azure). Best for deep integration with provider-specific features and zero-dependency deployment.
*   **Crossplane:** Kubernetes-native (Control Plane). Best for managing cloud resources as K8s objects (GitOps-friendly).

**CL6**
*   **HPA:** Scales number of pods based on CPU/RAM/Custom metrics.
*   **VPA:** Adjusts CPU/RAM requests/limits of existing pods.
*   **Cluster Autoscaler:** Adds/removes physical nodes to the cluster.
*   **KEDA:** Event-driven autoscaling (e.g., scale pods based on Kafka lag or RabbitMQ queue depth).
*   **Use KEDA over HPA** when scaling is triggered by external event sources (queues, streams) rather than just resource utilization.

**CL7**
*   **RPO/RTO:** RPO (data loss tolerance); RTO (downtime tolerance).
*   **Active-Active:** Both regions serve traffic; zero/low RTO. **Active-Passive:** One region is standby; higher RTO.
*   **Replication:** **Sync** (no data loss, high latency/distance limit) vs. **Async** (low latency, risk of data loss).
*   **DNS:** Route53/Traffic Manager uses health checks to reroute traffic.
*   **State:** Must replicate DBs and use global storage (e.g., S3 Cross-Region Replication).
*   **DR Types:**
    *   **Pilot Light:** Core data is live; compute is off/minimal.
    *   **Warm Standby:** Scaled-down version of the app is always running.
    *   **Multi-site Active-Active:** Full capacity in both regions; highest cost.

**CL8**
*   **GitOps:** Git is the "Single Source of Truth." Changes to Git trigger automated deployment.
*   **ArgoCD vs. FluxCD:** ArgoCD provides a rich UI and multi-cluster management; FluxCD is more lightweight, "pull-based" and follows a more minimalist K8s-native approach.
*   **Secrets:** Use **External Secrets Operator** (fetches from AWS Secrets Manager/Vault) or **Sealed Secrets** (encrypted in Git).
*   **Drift:** GitOps controllers detect the difference between Git and Cluster and automatically "self-heal" by overwriting the manual change to match Git.

**CL9**
*   **StatefulSet:** Ensures pods have stable identities and ordered deployment.
*   **PV/PVC (Local):** Use a `Local Persistent Volume` class for low-latency NVMe/SSD access.
*   **Headless Service:** Provides DNS records for individual pod IPs (required for peer discovery).
*   **Init Containers:** Run setup scripts (e.g., configuring filesystem paths) before the main app starts.
*   **ConfigMaps:** Mounted as volumes to inject files into specific paths.
*   **Pod Disruption Budget (PDB):** Ensures a minimum number of pods remain available during maintenance/upgrades.

**CL10**
*   **Service Account:** K8s identity for a pod.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role.
*   **Bad Practice:** Hardcoding credentials in a pod or using long-lived Secret keys. If a pod is compromised, the attacker has permanent cloud access.
*   **Solution:** Workload Identity uses OIDC/Federation. The pod exchanges a K8s-signed token for a short-lived cloud STS token, eliminating the need for static secrets.

**CL11**
*   **Object (S3):** Unstructured data (images, logs). High durability ($11$ 9s). Use for backups/media.
*   **Block (EBS):** Raw volumes for OS/Databases. Low latency. Use for high-performance DBs.
*   **File (EFS):** Shared filesystem (NFS). Use for shared config/media across multiple pods.
*   **Guarantees:** Object/File are typically regional; Block is zonal.

**CL12**
*   **Zero-Trust K8s:**
    *   **Network Policies:** L3/L4 isolation (deny-all by default).
    *   **Service Mesh (Istio/Linkerd):** mTLS for L7 encryption and identity.
    *   **Admission Controllers (OPA):** Enforce policy (e.g., "No privileged containers").
    *   **Runtime (Falco):** Detect syscall anomalies.
    *   **Image Signing (Cosign):** Ensure only verified images run.
*   **Difference:** Traditional security relies on a "hard shell" (perimeter). Zero-Trust assumes the network is breached and verifies every request/identity regardless of location.

**CL13**
*   **CDN:** A distributed network of proxy servers that caches content closer to users.
*   **How:** User requests $\rightarrow$ Edge Location $\rightarrow$ Cache Hit (fast) or Origin Fetch (slow).
*   **Services:** AWS CloudFront, Azure CDN.
*   **Use Case:** Use CDN for static assets (JS, CSS, Images) to reduce latency/origin load. Use Origin directly for dynamic, highly personalized, or real-time data.

**CL14**
*   **Region:** A geographic area containing multiple AZs.
*   **AZ:** One or more discrete data centers with redundant power/networking.
*   **Why Multi-AZ?** To protect against a single data center failure (e.g., fire, flood).
*   **Zonal vs. Regional:** Zonal resources (EBS) exist in one AZ; Regional resources (S3, IAM) are available across the whole region.

**CL15**
*   **Managed DB:** RDS/Cloud SQL.
*   **Provider handles:** Patching, backups, high availability (multi-AZ), hardware scaling, and OS maintenance.
*   **You handle:** Schema design, query optimization, user permissions, and application-level logic.

**CL16**
*   **IAM User:** Permanent identity for a person/app.
*   **Group:** Collection of users for easier permission management.
*   **Role:** Temporary identity assumed by a service or user.
*   **Policy:** JSON document defining permissions.
*   **Least Privilege:** Grant only the minimum permissions required for a task. Apply via granular IAM policies and scoped-down resource permissions.

**CL17**
*   **Serverless:** Event-driven execution without managing servers.
*   **Comparison:** Lambda (AWS), Azure Functions, GCF (Google).
*   **Cold Start:** Latency incurred when a new function instance is initialized. Matters for latency-sensitive APIs.
*   **Poor Fit:** Long-running processes (e.g., video encoding), high-frequency/constant-load workloads (too expensive), or apps requiring low-latency persistent connections (WebSockets).

**CL18**
*   **Ingress:** L7 rule-based routing (Host/Path).
*   **Gateway API:** Next-gen, more expressive, separates infra (Gateway) from app (HTTPRoute) management.
*   **Cloud LB Annotations:** Triggers the creation of an AWS/Azure Load Balancer.
*   **Service Mesh Ingress:** Handles complex L7 logic (retries, mTLS) at the edge.
*   **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Service Mesh.
*   **Use Gateway API** when you need more granular control over traffic splitting and cross-team management of networking resources.

**CL19**
*   **Strategy:**
    *   **Savings/Reserved:** Commit to 1-3 years for deep discounts (Compute/RDS).
    *   **Spot:** Use for stateless/batch workloads (up to 90% savings).
    *   **Right-sizing:** Use tools to match instance size to actual CPU/RAM usage.
    /   **Storage Tiering:** Move old logs to Glacier/Archive.
    *   **FinOps:** Implement **Tagging** for cost allocation. Use **Showback** (reporting) or **Chargeback** (billing) to hold teams accountable.
    *   **Tools:** AWS Cost Explorer, CloudHealth, or Kubecost.

**CL20**
*   **Strategy:** Use **Kubernetes** as the abstraction for compute, **Terraform** for infra, and **S3-compatible** storage.
*   **Networking:** Use VPN or Direct Connect/ExpressRoute to link clouds.
*   **Identity:** Use OIDC/SAML federation so one identity works across both.
*   **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs.
*   **Justification:** Use it if you have strict regulatory requirements (sovereignty) or need specific services only available in one cloud. Avoid it if you are a small team; the "complexity tax" often outweighs the "lock-in" risk.

## OT Infrastructure Architecture

**OT1**
The Purdue Model segments industrial networks:
*   **Level 0:** Physical process (sensors, motors).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Supervisory Control (HMI, SCADA).
*   **Level 3:** Site Operations (Historian, MES).
*   **Level 4/5:** Enterprise/Business (ERP, Office IT).

**OT2**
*   **Difference:** IT focuses on Data Confidentiality/Integrity; OT focuses on **Availability/Safety/Real-time**.
*   **Patching:** Standard IT patches can cause reboots or latency spikes, which in OT could lead to physical damage or unsafe machine states.

**OT3**
*   **IDMZ:** A buffer zone between L4 and L3.
*   **Traffic:** Only strictly defined, inspected traffic (e.g., Historian replication) should cross.
*   **Direction:** One-way or highly controlled.
*   **Danger:** Direct L4 $\to$ L1 connectivity allows a compromised office laptop to send "Stop" commands directly to a PLC, bypassing all monitoring.

**OT4**
1.  **Modbus TCP:** Level 1/2 (Control/Supervisory).
2.  **OPC UA:** Level 2/3 (Interoperability/Data aggregation).
3.  **EtherNet/IP (CIP):** Level 1/2 (Real-time control).
4.  **PROFINET:** Level 1/2 (High-speed automation).
5.  **MQTT:** Level 3/Cloud (Telemetry/Edge-to-Cloud).

**OT5**
*   **Data Diode:** Hardware-based, physically allows data to flow in only one direction (light/fiber).
*   **Firewall:** Software-based, allows bidirectional communication based on rules.
*   **Use Case:** Use a diode for high-security environments (Nuclear/Power) where you must ensure no commands can ever reach the control network from the outside.
*   **Limitation:** A diode prevents "handshakes" (TCP), making it much harder to use standard protocols like HTTP/SQL.

**OT6**
*   **Flow:** Sensors $\to$ PLC (L1) $\to$ OPC UA Server (L2) $\to$ Historian (L3) $\to$ Edge Gateway (L3.5) $\to$ MQTT Broker (Cloud).
*   **Boundaries:** Place a firewall/IDMZ between L3 and L4. Use an Edge Gateway to terminate the OT connection and initiate a new, outbound-only connection to the cloud.

**OT7**
*   **Zone:** A logical grouping of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Model:**
    *   **Zone 1 (Safety):** SIS (Isolated).
    *   **Zone 2 (Control):** PLCs/SCADA.
    *   **Zone 3 (Engineering):** Workstations.
    *   **Zone 4 (Enterprise):** Corporate.
    *   **Conduits:** Firewalls/DPI (Deep Packet Inspection) between each zone.

**OT8**
*   **Strategy:**
    1.  **VLANs:** Segment by production line.
    2.  **Firewalls:** Place industrial firewalls between lines.
    3.  **Transition:** Use "Mirror Ports" (SPAN) to monitor existing traffic without interrupting it. Implement one line at a time during scheduled maintenance windows.
    4.  **Remote Access:** Use a Jump Host in the IDMZ with MFA.

**OT9**
*   **SIS vs. BPCS:** SIS is the "emergency brake" (safety-only); BPCS is the "driver" (manages the process).
*   **IEC 61511:** Standard for functional safety in the process industry.
*   **Isolation:** If SIS is connected to IT, ransomware could disable the safety shutdown, leading to explosions/leaks.
*   **Ransomware:** If SIS is compromised, the plant must enter an immediate manual emergency shutdown.

**OT10**
*   **PLC:** Logic-based controller for specific tasks.
*   **DCS:** Distributed control for large, continuous processes (e.g., oil refinery).
*   **SCADA:** High-level supervisory system for geographically dispersed assets.
*   **Coexistence:** Yes, they often work together (SCADA supervises PLCs).

**OT11**
*   **Architecture:** Users $\to$ VPN $\to$ **Jump Host (in IDMZ)** $\to$ MFA $\to$ Session Recording $\to$ OT Asset.
*   **Why not RDP to HMI?** Direct RDP bypasses all inspection, allows lateral movement, and exposes the HMI (often unpatched) to the internet/corporate network.

**OT12**
*   **Plan:**
    1.  **Detection:** Use IDS to flag unusual L3 traffic.
    2.  **Response:** Isolate the compromised VPN segment.
    3.  **Coordination:** Notify the Control Room; do **not** kill processes without operator consent.
    4.  **Operator Role:** The operator is the final authority; they decide if the process is safe to continue or if an emergency shutdown is required.

**OT13**
*   **HMI:** A dashboard for operators to monitor/interact with the process.
*   **Engineering Workstation:** A high-privilege machine used to program/configure PLCs.

**OT14**
*   **Historian:** A database for time-series process data.
*   **Importance:** Essential for auditing, compliance, and troubleshooting.
*   **Difference:** **Plant Historian** (L3) stores high-resolution, real-time data; **Enterprise Historian** (L4) stores aggregated, long-term trends for business decisions.

**OT15**
*   **Ladder Logic:** A graphical programming language resembling electrical relay diagrams.
*   **Why dominant?** It is intuitive for electricians/enginefering staff and maps directly to physical relay-based control logic.

**OT16**
*   **RTU:** Designed for remote, low-power, long-distance communication (e.g., pipelines).
*   **Difference:** RTUs are better at handling varied communication protocols and intermittent connectivity than PLCs.
*   **Environment:** Remote telemetry, oil/gas pipelines, water distribution.

**OT17**
*   **Analog vs. Digital:** Analog is a continuous range; Digital is discrete (On/Off).
*   **4-20mA vs. 0-20mA:** 4-20mA is preferred because a "0mA" reading indicates a broken wire (fault detection), whereas 0mA in a 0-20mA system could just mean "zero value."

**OT18**
*   **Inventory:** You cannot protect what you cannot see.
*   **Techniques:** **Passive Monitoring** (listening to traffic) is safe; **Active Scanning** (pinging/querying) can crash sensitive, older PLCs.
*   **Danger:** Active scanning can overwhelm the limited CPU/network stacks of legacy OT devices, causing them to stop controlling the process.

**OT19**
*   **MITRE ATT&CK for ICS:**
    1.  **Inhibit Response Function:** (e.g., disabling alarms).
    2.  **Impair Process Control:** (e.g., changing setpoints).
    3.  **Loss of Safety:** (e.g., disabling SIS).
    4.  **Damage to Property:** (e.g., physical destruction).
    5.  **Inhibit Control:** (e.g., DoS on PLC).
*   **Difference:** Enterprise focuses on data theft; ICS focuses on physical process disruption. Use it to map your visibility gaps (e.g., "Do we have logs for L1-to-L2 traffic?").

**OT20**
*   **Design:**
    *   **Collection:** Use passive network taps/SPAN ports to avoid impacting real-time traffic.
    *   **Integration:** Forward logs to a central SIEM.
    *   **Rules:** Look for "New MAC address on L2" or "Unauthorized S7comm write."
    *   **Triage:** IT analysts handle L4 alerts; OT engineers handle L1/L2 alerts.
    *   **False Positives:** High in OT due to legacy protocols.
    *   **PLC Firmware Alert:** Treat as a **Critical Incident**. Isolate the PLC, check the engineering workstation for unauthorized access, and verify the physical process integrity with the plant operator.
