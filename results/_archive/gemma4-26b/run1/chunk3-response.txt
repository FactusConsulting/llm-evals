## OpenTofu / Terraform

**T1**
`tofu plan` is a dry run that compares the current state against the desired configuration and shows what actions (create, update, delete) will be taken. `tofu apply` executes those actions to reach the desired state.

**T2**
State is a JSON file that maps real-world resources to your configuration. Remote state (stored in S3, GCS, etc.) is critical for team collaboration, providing a single source of truth, enabling state locking to prevent concurrent writes, and ensuring persistence.

**T3**
`count` uses an integer index, making it difficult to remove items from the middle of a list without shifting indices (causing resource recreation). `for_each` uses a map or set of strings. `for_each` is preferred when managing collections of resources where you need to add/remove specific elements without affecting others.

**T4**
This is "configuration drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy between the actual cloud state and the state file, then proposes a plan to revert the manual change or update the state to match.

**T/5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.value
}
```

**T6**
`terraform_remote_state` reads the entire state file of another workspace, which can expose sensitive data and creates tight coupling. The recommended alternative is using **Outputs** from the producer module and passing them as **Inputs** to the consumer module. This enforces a clean interface and follows the principle of least privilege.

**T7**
The `kubeconfig` output is calculated during the plan/apply phase. However, `remote-exec` runs during the *apply* phase. On the first run, the output value is not yet available to the state for dependent resources to consume. **Fix:** Use a `null_resource` with a `triggers` block that depends on the VM creation, and ensure the output is only evaluated after the provisioner completes. Alternatively, use a `local-exec` to write the file to a known path that subsequent resources can read.

**T8**
`tofu import` brings existing infrastructure into management by mapping a real ID to a resource address. **Limitations:** It does not generate the HCL code for you; you must write the configuration manually. The `import` block (1.5+) is superior because it is declarative, allows for easier code reviews via PRs, and can be used with `tofu plan` to preview the import before execution.

**T9**
A **variable** (input) is a parameter passed *into* a module to make it reusable. An **output** is a value exported *from* a module to be used by other modules or the CLI.

**T10**
A provider is a plugin that translates OpenTofu HCL into API calls for a specific service (e.g., AWS, Azure). If you run `tofu plan` without `tophi init`, OpenTofu will fail because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11**
The `.terraform.lock.hcl` file records the exact versions and hashes of the providers used. It should be committed to version control to ensure that every environment (Dev, Prod, CI/CD) uses the identical provider version, preventing "it works on my machine" dependency issues.

**T12**
`tofu destroy` removes all resources managed by the current configuration. To target a single resource, use the `-target` flag: `tofu destroy -target=resource_type.resource_name`.

**T13**
A data source allows you to fetch information from existing infrastructure not managed by your current OpenTofu configuration. **Example:** Fetching the latest Amazon Linux 2 AMI ID from the AWS marketplace to use in an EC2 resource.

**T14**
`variable` blocks define inputs provided by the user. `locals` blocks define internal, reusable logic/constants within the module. Use `locals` for complex transformations or derived values (e._g., `name = "${var.env}-${var.project}"`) to avoid repeating logic across multiple resources.

**T15**
*   `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
*   `prevent_destroy`: Prevents OpenTofu from deleting a resource (useful for critical databases).
*   `ignore_changes`: Tells OpenTofu to ignore updates to specific attributes (useful when an external process, like an Auto Scaling Group, modifies a resource).

**T16**
A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module/address in the code. This allows OpenTofu to update the state file without destroying and recreating the actual physical resource.

**T17**
OpenTofu builds a Directed Acyclic Graph (DAG). **Implicit dependencies** are created when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are defined via `depends_on`. `depends_on` can limit parallelism by forcing a resource to wait, which can slow down execution. Use it sparingly, only when a dependency exists that isn't captured by attribute references.

**T18**
1.  **Reduce State Size:** Split large monolithic states into smaller, decoupled state files (Tradeoff: increased complexity in managing cross-state dependencies).
2.  **Targeted Plans:** Use `-target` for specific changes (Tradeoff: risky, as it ignores the rest of the graph).
3.  **Reduce Data Sources:** Minimize the number of external API calls/data lookups (Tradeoff: less dynamic configuration).
4.  **Parallelism Tuning:** Adjust `-parallelism` (Tradeoff: higher values can hit provider API rate limits).

**T19**
State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a pipeline crashes, the lock remains. You can manually break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If a process is *actually* still running, force-unlocking can lead to state corruption or duplicate resource creation.

**t20**
1.  **Prepare:** Create an S3 bucket and a DynamoDB table (for locking).
2.  **Configure:** Update the `terraform` block in your code with the new `backend "s3"` configuration.
3.  **Migrate:** Run `tofu init`. OpenTofu will detect the change from local to remote and ask if you want to migrate the existing state. Type `yes`.
4.  **Verify:** Check the S3 bucket for the `.tfstate` file and run `tofu plan` to ensure no unexpected changes are detected.

## Ansible

**A1**
A **task** is a single action (e.g., installing a package). A **playbook** is a collection of plays that map tasks to hosts. A **role** is a structured, reusable collection of tasks, variables, and templates.

**A2**
`ansible_facts` is a dictionary of system information gathered by Ansible. To access the OS family, use `{{ ansible_facts['os_family'] }}`.

**

**A3**
*   `command`: Executes a command; does not support shell features like pipes or redirects. Use for simple, safe commands.
*   `shell`: Executes via `/bin/sh`; supports pipes, redirects, and environment variables. Use when complex shell logic is needed.
*   `raw`: Executes a command via SSH without needing Python on the target. Use for bootstrapping a new node.

**A4**
Idempotency means running a task multiple times results in the same state.
*   **Idempotent:** `apt: name=nginx state=present` (If installed, does nothing).
*   **NOT Idempotent:** `shell: echo "config" >> /etc/file` (Appends a new line every single time).

**A5**
```yaml
- name: Install htop
  package:
    name: "{{ 'epel-release' if ansible_os_family == 'RedHat' else 'htop' }}"
    state: present
  when: ansible_os_family == 'RedHat'
# Note: To do this in a single task file for both, you'd use a conditional or a loop.
```
*Refined approach:*
```yaml
- name: Install htop on Debian
  apt: name=htop state=present
  when: ansible_os_family == "Debian"

- name: Install htop on RedHat
  yum: name=htop state=present
  when: ansible_os_family == "RedHat"
```

**A6**
Priority (Lowest to Highest): `role defaults` < `inventory group_vars` < `inventory host_vars` < `playbook vars` < `role vars` < `task vars` < `set_fact` < `extra_vars`.

**A7**
Use `serial: 3` in the play to process 3 nodes at a time. Use a `wait_for` task or a `pause` task to ensure the first batch completes their service startup before the next batch begins.

**A8**
You can use `ansible-vault encrypt_string 'my_secret_password'` to encrypt a single string. You then paste that encrypted block into your variable file. This keeps the rest of the file human-readable.

**A9**
An **inventory** is a list of managed hosts. A **static inventory** is a fixed file (INI/YAML). A **dynamic inventory** is a script or plugin that queries a cloud provider (AWS/GCP) to fetch the current list of active instances.

**A10**
`ansible webservers -m shell -a "df -h"`

**A11**
A **handler** is a special task that only runs when "notified" by another task. You trigger it using the `notify` keyword in a task. Handlers are used for actions that should only happen once per play (e.le., restarting a service after a config change).

**A12**
`ansible.cfg` configures the Ansible execution environment. Common settings: `inventory` (path to inventory), `remote_user` (default user for SSH), and `forks` (number of parallel processes).

**A13**
`register` captures the output of a task into a variable. You can then use `{{ variable_name.stdout }}` in a subsequent task to perform logic based on that output.

**A14**
`import_tasks` is **static** (processed at parse time); `include_tasks` is **dynamic** (processed during runtime). Use `include_tasks` if you need to use a variable to determine which file to load. `import_tasks` is better for performance and allows for easier use of `when` statements on the tasks themselves.

**A15**
Ansible Galaxy is a public repository for Ansible roles/collections. You use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16**
*   `ssh`: Uses standard SSH (default). Best for Linux servers.
*   `local`: Executes tasks on the control node itself. Best for managing local files or triggering local scripts.
*   `network_cli`: Uses specialized SSH connections for network devices (Cisco/Arista). Best for managing switches/routers.

**A17**
`delegate_to` runs a task on a different host than the one in the current play. `run_once` ensures the task executes only once for the whole play.
*Example:*
```yaml
- name: Register node in Consul
  community.general.consul_service:
    name: "{{ inventory_hostname }}"
  delegate_to: localhost
  run_once: true
```

**A18**
1.  **Forks:** Increase `forks` in `ansible.cfg` to run more parallel connections (Tradeoff: higher CPU/RAM on control node).
2.  **Pipelining:** Enable `piputing = True` in `ansible.cfg` to reduce SSH overhead (Tradeoff: requires `requiretty` to be disabled on target).
3.  **Fact Caching:** Use Redis/Memcached to store facts so they aren't re-gathered every time (Tradeoff: requires managing a cache server).
4.  **Mitogen:** Use the Mitogen plugin to replace the standard SSH execution engine (Tradeoff: adds a dependency to the control node).

**A19**
*   `{{ }}`: Variable interpolation.
*   `{% %}`: Control structures (loops, conditionals).
*   `{# #}`: Comments.

*Template Snippet:*
```jinja2
upstream backend_servers {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }} {% if server.healthy %} # Healthy {% else %} # Unhealthy {% endif %}
{% endfor %}
}
```

**A20**
1.  **Batching:** Use `serial: 1` or `serial: 5` to update servers in small groups.
2.  **Pre-task:** Use `uri` module to check the health of the app; if it fails, stop the play.
3.  **Deployment:** Update the code/package on the host.
4.  **Post-task:** Use `uri` module to verify the local service is responding.
5.  **Load Balancer:** Use a task to remove the host from the LB before the update and add it back after.
6.  **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, write tasks to revert the package version or configuration and re-add the host to the LB.
