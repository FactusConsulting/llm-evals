## Application Architecture

**AA1**
A **monolith** is a single-tier software application where all components (UI, business logic, data access) are bundled into one codebase and deployment unit. **Microservices** decompose this into a collection of small, independent services communicating via APIs.
**3 Problems introduced by microservices:**
1. **Distributed Complexity:** Managing network latency, partial failures, and distributed tracing.
2. **Data Consistency:** Moving from ACID transactions to eventual consistency (Saga pattern).
3. **Operational Overhead:** Increased complexity in deployment, monitoring, and service discovery.

**AA2**
**Synchronous:** The client sends a request and waits (blocks) for a response before proceeding. Example: **REST/HTTP**.
**Asynchronous:** The client sends a message/event and continues its work without waiting for an immediate response. Example: **RabbitMQ/Kafka**.

**AA3**
An **API Gateway** handles application-level concerns: authentication, rate limiting, request transformation, and routing. A **Reverse Proxy** handles network-level concerns: SSL termination, load balancing, and caching.
**Can it replace?** Not entirely. While a modern Gateway (like Kong or Envoy) can perform reverse proxy tasks, a reverse proxy is often used for simpler, lower-latency edge tasks (like Nginx) without the heavy overhead of API management logic.

**AA4**
The **Saga pattern** manages data consistency in distributed systems by using a sequence of local transactions.
* **Choreography:** Each service produces and listens to events; there is no central controller. Best for simple workflows with few services.
- **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows with many steps.
**Appropriateness:** Use choreography for decoupled, high-scale, simple flows. Use orchestration when you need centralized logic, visibility, and complex error handling/compensation.

**AA5**
**CQRS** separates the models for updating data (Commands) from the models for reading data (Queries).
**Pairing with Event Sourcing:** Event Sourcing stores the state as a sequence of events rather than just the current snapshot.
**Problem solved:** It solves the "impedance mismatch" and performance bottlenecks of CRUD by allowing the read model to be optimized (e.g., a flattened NoSQL view) for high-speed queries, while the write model remains strictly validated and append-only.

**AA6**
The **Circuit Breaker** prevents a failing service from causing cascading failures.
**Three States:**
1. **Closed:** Requests flow normally.
2. **Open:** Requests fail fast immediately without hitting the target service.
3. **Half-Open:** A limited number of test requests are sent to check if the service has recovered.
**Difference from Retry:** Retry handles transient blips; Circuit Breaker handles persistent failures. Use them together by retrying a few times, but if the failure persists, "trip" the circuit to stop the retries from overwhelming the downstream service.

**AA7**
1. **Shared DB, Shared Schema:**
   - *Cost:* Lowest (high density).
   - *Security:* Weakest (risk of SQL injection leaking other tenants).
   - *Complexity:* Low.
   - *Noisy Neighbor:* High (one tenant's heavy query affects all).
2. **Shared DB, Separate Schema:**
   - *Cost:* Medium.
   - *Security:* Better (logical separation).
   - *Complexity:* Medium (managing migrations across schemas).
   - *Noisy Neighbor:* Medium.
3. **Separate DB per Tenant:**
   - *Cost:* Highest (resource overhead per DB instance).
   - *Security:* Strongest (physical isolation).
   - *Complexity:* High (infrastructure management).
   - *Noisy Neighbor:* Lowest (isolated resources).

**AA8**
**Strong Consistency:** All reads return the most recent write (e./g., SQL).
**Eventual Consistency:** Reads will eventually see the latest write, but may see stale data temporarily (e.g., DynamoDB).
**Architecture for Inventory:** Use **Strong Consistency**.
**Data Store:** A distributed SQL database (e.g., CockroachDB) or a RDBMS with distributed locking.
**Patterns:** Use **Distributed Locking** (Redis/Redlock) or **Atomic Increments** at the database level to ensure the decrement operation fails if `quantity < 1`. At scale, use **Partitioning/Sharding** by product ID to ensure high throughput while maintaining local ACID properties.

**AA9**
A **sidecar proxy** is a helper container running alongside the application container in the same pod/host.
**Istio/Envoy:** Istio is the **Control Plane** (manages configuration/policy); Envoy is the **Data Plane** (the sidecars that actually intercept and route traffic).
**mTLS:** Solves the "identity" problem. Application-level TLS encrypts data but doesn't provide cryptographically verifiable service identity or automated certificate rotation/management provided by the mesh.

**AA10**
**Strangler Fig Pattern:** Incrementally replace legacy functionality with new services until the old system is "strangled."
**Strategy:**
1. Place an API Gateway/Proxy in front of the .NET Framework monolith.
2. Identify a single bounded context (e.g., "User Profile").
3. Build the new service in .NET 8.
4. Update the Gateway to route "User Profile" traffic to the new service, while all other traffic goes to the monolith.
5. Repeat for other modules until the monolith can be decommissioned.

**AA11**
The 12-Factor App is a methodology for building SaaS/Cloud-native apps.
1. **Codebase:** One repo per app (ensures consistency).
2. **Dependencies:** Explicitly declare/isolate (prevents "works on my machine").
3. **Config:** Store config in environment variables (allows same build in Dev/Prod).
4. **Backing Services:** Treat DBs/Queues as attached resources (allows easy swapping).
5. **Build, Release, Run:** Strict separation (ensures traceability).
6. **Processes:** Stateless (allows horizontal scaling).
*Why they matter:* They ensure portability, scalability, and resilience in ephemeral cloud environments.

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :---/t Coupling | Very Low (Decoupled) | High (Direct dependency) |
| **Scalability** | High (Consumer groups) | Moderate (Requires LB) |
| **Debugging** | High (Hard to trace flow) | Low (Direct request/response) |
| **Ordering** | Guaranteed (within partition) | Not guaranteed |
| **Failure** | Resilient (Retries via logs) | Harder (Requires retries/circuit breakers) |

**Choice:** Use **REST/gRPC** for real-time, low-latency user-facing actions. Use **Kafka** for background processing, data pipelines, and cross-domain notifications.

**AA13**
A **Load Balancer** distributes incoming network traffic across multiple servers.
**Layer 4 (Transport):** Routes based on IP and Port (TCP/UDP). Fast, but "blind" to content.
**Layer 7 (Application):** Routes based on HTTP headers, cookies, or URL paths.
**Use Case:** **A/B Testing** or **Blue/Green Deployment** where you need to route traffic to different versions of a service based on a specific HTTP header or cookie.

**AA1/14**
A **Message Queue** is a buffer that holds messages until a consumer processes them.
**RabbitMQ (Queue):** Focuses on complex routing and immediate delivery/deletion after consumption. Best for task distribution.
**Kafka (Log-based):** An append-only log where messages persist for a set time. Consumers can "replay" the log. Best for high-throughput stream processing and event sourcing.
**Choice:** Pick **RabbitMQ** for simple, reliable tasking. Pick **Kafka** for high-volume data streaming and event replayability.

**AA15**
A **Container** is an isolated user-space environment sharing the host OS kernel. A **VM** includes a full guest OS and a hypervisor.
**Why popular:** Containers are lightweight, start instantly, and package all dependencies, making them ideal for the "immutable infrastructure" required by microservices.

**AA16**
**Stateless:** Does not store client data between requests (e.g., a REST API).
**Stateful:** Remembers client context (e.e., a shopping cart in a local session).
**Scaling:** Stateless services are easier to scale because any instance can handle any request; you don't need "sticky sessions" or complex data synchronization between instances.

**AA17**
**ORM:** A technique to map database tables to objects in code.
**Examples:** **Hibernate** (Java), **Entity Framework Core** (.NET).
**Trade-offs:**
- **Pros:** Faster development, type safety, prevents SQL injection, easier migrations.
- **Cons:** "N+1" query problems, abstraction overhead, difficulty in writing highly optimized complex SQL.

**AA18**
The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function.
**Relation to Microservices:** It prevents a single failing downstream service from consuming all resources (threads/memory) of the caller.
**Implementation:**
- **Thread Pools:** Assign a dedicated thread pool to each downstream dependency. If Service A hangs, only its pool exhausts; Service B's pool remains available.
- **Deployment Groups:** Deploy "Critical" and "Non-critical" services on separate hardware/clusters.

**AA19**
**OT (Operational Transformation):** Transforms the index of an operation based on previous operations. High complexity, requires a central server to order operations.
**CRDT (Conflict-free Replicated Data Type):** Data structures that can be updated independently and merged mathematically without conflicts.
**Comparison:**
- **Consistency:** OT is easier to keep "strong" via a central server; CRDT is inherently eventually consistent.
- **Latency:** CRDT is better for peer-to-peer/low latency.
- **Complexity:** OT is very hard to implement for complex types.
**Choice for Offline Editing:** **CRDT**. Because CRDTs are designed for asynchronous merging, a user can make changes offline and sync them later without the server needing to "re-calculate" every single historical operation index.

**AA20**
**Challenges:** Context must be passed through every hop (headers).
**Context Propagation:** Using **W3C Trace Context** (standardized headers) or **B3** (Zipkin).
**Sampling:** **Head-based** (decide at the start of the request) vs. **Tail-based** (decide after the trace is complete, allowing you to keep all "error" traces).
**Storage:** **Jaeger** or **Grafio Tempo**.
**Asynchronous (Kafka):** To ensure continuity, the producer must inject the `traceparent` into the **Kafka Message Header**. The consumer must then extract this header to start its own span as a child of the producer's span.

## On-Premise Infrastructure Architecture

**OP1**
**Type 1 (Bare-metal):** Runs directly on hardware (e.g., **VMware ESXi, Xen**). High performance.
**Type 2 (Hosted):** Runs on top of an OS (e.g., **Oracle VirtualBox, VMware Workstation**). Easier to use but higher overhead.

**OP2**
**SAN (Storage Area Network):** Block-level storage (e.g., Fibre Channel). Used for databases/VM disks. Protocol: **FC, iSCSI**.
**NAS (Network Attached Storage):** File-level storage (e.g., SMB/NFS). Used for shared files/documents. Protocol: **NFS, SMB/CIFS**.

**OP3**
**3-Tier:** Core, Distribution, Access.
**Leaf-Spine:** A two-tier architecture where every Leaf switch connects to every Spine switch.
**Problem Solved:** 3-tier suffers from high latency and "north-south" bottlenecks. Leaf-Spine provides predictable, low-latency "east-west" traffic (server-to-server), which is critical for modern distributed workloads (like Ceph or vMotion).

**OP4**
**Architecture:** Minimum 3 nodes for quorum.
**Quorum:** Use a "witness" or third site to prevent split-brain.
**Fencing:** Use **STONITH** (Shoot The Other Node In The Head) via IPMI/iDRAC to ensure a failed node is truly dead before another takes its resources.
**Storage:** **Ceph** (distributed block) is preferred for high availability.
**Failure:** If a node fails, the cluster detects loss of heartbeat, fences the node, and the remaining nodes re-run the Ceph/VM recovery process to re-map the data.

**OP5**
**VLAN Trunking:** Carrying multiple VLANs over a single physical link.
**802.1Q:** Adds a 4-byte "tag" to the Ethernet frame header containing the VLAN ID.
**Linux Config:** Use `vconfig` or `ip link`. Example: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6**
**RAID 1:** Mirroring (High safety, low capacity).
**RAID 5:** Parity (Good capacity, slow writes, 1-drive failure).
**RAID 6:** Dual Parity (2-drive failure).
**RAID 10:** Mirror + Stripe (High performance/safety, expensive).
**RAID Z2:** ZFS equivalent of RAID 6.
**Choice for DB:** **RAID 10**. Databases require high IOPS (striping) and high reliability (mirroring). It provides the best performance for random writes.

**OP7**
**Architecture:**
- **Internal AD:** Uses local DNS servers.
- **DMZ:** Separate subnet with public-facing DNS.
- **Split-Horizon:** Different DNS responses for internal vs. external queries (e.g., `app.corp` resolves to private IP internally, but doesn't exist externally).
- **DNSSEC:** Digitally signs zones to prevent spoofing.
- **Movement:** Use **Conditional Forwarders** for specific domains. When a user moves to VPN, the VPN concentrator pushes DNS settings to the client, ensuring they use the enterprise resolvers.

**OP8**
**Chain of Trust:** Root CA $\rightarrow$ Intermediate/Subordinate CA $\rightarrow$ End-Entity.
**Deployment:** Root CA stays **offline** (air-gapped). Subordinate CAs issue certificates.
**CRL vs OCSP:** **CRL** is a list of revoked certs (can get large); **OCSP** is a real-able check for a specific cert (faster/more efficient).
**Consequences:** A compromised **Subordinate CA** can be revoked by the Root. A compromised **Root CA** destroys the entire trust anchor; you must manually redistribute a new Root to every device in the org.

**OP9**
- **MPLS:** High cost, high reliability, low latency, complex.
- **IPsec VPN:** Low cost, relies on internet stability, higher latency.
- **SD-WAN:** Intelligent path selection, easy management, medium cost.
- **WireGuard:** Extremely fast/secure, but requires mesh management.
**Recommendation:** **SD-WAN**. It can bond MPLS and Internet links, prioritizing VoIP traffic over the most stable path, providing the best balance of cost and performance for 50-user sites.

**OP10**
**iDRAC/iLO/IPMI:** Out-of-band (OOB) management allows hardware control even if the OS is crashed.
**Criticality:** Allows remote power cycling, BIOS config, and OS reinstallation.
**Risk:** If exposed to the internet, attackers can gain full hardware control, wipe disks, or install firmware-level rootkits.

**OP11**
**LVM:** Logical volume management on top of physical disks.
**LVM-Thin:** Allows over-provisioning; space is only consumed when data is written.
**ZFS:** Integrated file system and volume manager with built-in RAID/Copy-on-Write.
**Snapshots:** LVM snapshots are "copy-on-write" (can degrade performance over time). ZFS snapshots are near-instant and extremely efficient due to the CoW architecture. Use **ZFS** for data integrity/bit-rot protection; use **LVM** for simple disk resizing.

**OP12**
**Design:** Use a **3-site** setup or a **2-site + Witness** setup.
**Ceph CRUSH:** Define rules to ensure replicas are placed in different failure domains (different racks/sites).
**Latency:** Sites must have low latency (usually <10ms RTT) for synchronous replication.
**Split-Brain:** If the link breaks, both sites might think they are primary. A **Tiebreaker/Witness** node in a 3rd site is mandatory to maintain quorum.
**Why 2-site is bad:** Without a tiebreaker, if the link fails, neither side can safely assume leadership without risking data corruption (split-sink).

**OP13**
**DORA:** **D**iscover (Client broadcast), **O**ffer (Server response), **R**equest (Client accepts), **A**cknowledge (Server confirms).
**Failure:** If the server is unavailable, the client will eventually fail to renew. The client will then attempt to use an APIPA address (169.254.x.x) and lose network connectivity.

**OP14**
**Unmanaged:** Plug-and-play, no configuration, no visibility.
**Managed:** Supports VLANs, Spanning Tree (STP), SNMP, Port Security, and ACLs.
**Enterprise Importance:** Essential for segmenting guest/corporate traffic, monitoring for loops, and detecting unauthorized device connections.

**OP15**
**NTP:** Network Time Protocol.
**Criticality:** Essential for log correlation (forensics), Kerberos authentication (time skew kills logins), and database transaction ordering.
**Drift:** If clocks drift, distributed databases may experience "causal" errors, and SSL/TLS certificate validation may fail.

**OP16**
**Physical Server:** Dedicated hardware.
**VM:** Hardware-level abstraction.
**Container:** OS-level abstraction.
**Bare Metal Use Case:** High-performance computing (HPC), heavy database workloads, or applications requiring direct access to specialized hardware (e/g., GPUs/FPGA) where hypervisor overhead is unacceptable.

**OP17**
**UPS:** Provides immediate battery power to bridge the gap until the generator starts and handles voltage sags.
**Generator:** Provides long-term power for extended outages.
**ATS (Automatic Transfer Switch):** Automatically switches the building's power source from the utility grid to the generator when a failure is detected.

**OP18**
**Active-Passive:** One node handles traffic; the other is standby.
**Active-Active:** Both nodes handle traffic simultaneously.
**PostgreSQL HA:**
1. **Pacemaker/Corosync:** Manages the cluster state and heartbeat.
2. **Virtual IP (VIP):** A single IP that moves to the active node.
3. **Fencing (STONITH):** If the passive node loses contact with the active node, it uses IPMI to power off the active node to prevent two nodes from writing to the same disk.
4. **Failover:** When the active node fails, Pacenter promotes the passive node and migrates the VIP.

**OP19**
**3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
**RPO/RTO:** **RPO** (Recovery Point Objective) is how much data you can afford to lose (time since last backup). **RTO** (Recovery Time Objective) is how long it takes to get back online.
**Backup Types:** **Full** (all data), **Incremental** (changes since last backup), **Differential** (changes since last full).
**Strategy:** Use **Deduplication** to save space. Use **Immutable Backups** (S3 Object Lock) to prevent ransomware from deleting backups. **Test restores** regularly; a backup is useless if it cannot be restored.
**Backup vs DR:** Backup is the *data*; Disaster Recovery is the *process/infrastructure* to restore operations.

**OP20**
**802.1X Roles:**
- **Supplicant:** The client device.
- **Authenticator:** The switch.
- **Authentication Server:** The RADIUS server.
**Methods:** **EAP-TLS** (Certificate-based, very secure) vs. **PEAP** (Username/Password, easier to deploy).
**RADIUS:** Validates credentials and returns attributes (like a VLAN ID) to the switch.
**Dynamic VLAN:** The switch moves the port into a specific VLAN based on the user's identity.
**Failure:** If authentication fails, the port is typically moved to a "Guest" VLAN or shut down entirely.
**MAB (MAC Authentication Bypass):** For "dumb" devices (printers/IoT), the RADIUS server checks the MAC address against a whitelist. It is less secure as MAC addresses can be spoofed.
