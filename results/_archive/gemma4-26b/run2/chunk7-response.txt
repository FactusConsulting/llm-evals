### Application Architecture

**AA1**
A **monolith** is a single-tier software application where all components (UI, business logic, data access) are bundled into one codebase and deployment unit. **Microservices** decompose this into a collection of small, independent services communicating via network protocols.
**3 Problems introduced by microservices:**
1. **Network Latency/Complexity:** Inter-service calls add overhead and potential points of failure.
2. **Distributed Tracing/Observability:** Debugging a single request across multiple services is significantly harder.
3. **Data Consistency:** Maintaining ACID properties across distributed databases requires complex patterns (e.g., Sagas).

**AA2**
**Synchronous:** The client sends a request and waits (blocks) for a response before proceeding. *Example: REST over HTTP.*
**Asynchronous:** The client sends a message and continues its work without waiting for an immediate response. *Example: RabbitMQ (Message Queuing).*

**AA3**
An **API Gateway** handles application-level concerns: authentication, rate limiting, request transformation, and routing. A **Reverse Proxy** (like Nginx) handles network-level concerns: SSL termination, load balancing, and caching.
An API Gateway **cannot** replace a reverse proxy entirely because reverse proxies are often more efficient at low-level TCP/TLS handling and are often used to protect the Gateway itself.

**AA4**
The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. Each local transaction updates the database and triggers the next step.
*   **Choreography:** Each service produces and listens to events. There is no central controller. *Best for: Simple workflows with few services.*
*   **Orchestration:** A central "orchestrator" tells each service what to do. *Best for: Complex workflows with many steps and centralized logic.*

**AA5**
**CQRS** separates the models for reading data (Queries) from the models for updating data (Commands).
It is paired with **Event Sourcing** because Event Sourcing stores the state as a sequence of events. This allows the "Read" side to build optimized projections (materialized views) from the event log.
**Problem solved:** It eliminates the performance bottleneck of complex joins and locking in traditional CRUD models when dealing with high-scale, read-heavy, or audit-heavy workloads.

**AA6**
The **Circuit Breaker** prevents a service from repeatedly trying to execute an operation that is likely to fail.
**Three States:**
1. **Closed:** Requests flow normally.
2. **Open:** Requests fail immediately without calling the service.
3. **Half-Open:** A limited number of test requests are allowed to check if the service has recovered.
**Difference from Retry:** Retry handles transient blips; Circuit Breaker handles systemic failure. Use **both** together: Retry for a single failed packet, but trip the Circuit Breaker if the retries continue to fail, preventing "retry storms."

**AA7**
1. **Shared DB, Shared Schema:** *Cost: Low; Security: Low (risk of data leaks); Complexity: Low; Noisy-Neighbor: High.*
2. **Shared DB, Separate Schema:** *Cost: Medium; Security: Medium; Complexity: Medium; Noisy-Neighbor: Medium.*
3. **Separate DB per Tenant:** *Cost: High; Security: High (physical isolation); Complexity: High; No/Low Noisy-Neighbor.*

**AA8**
**Eventual Consistency:** Data will become consistent across all nodes given enough time.
**Strong Consistency:** All nodes see the same data at the same time.
**Architecture for Inventory:** Use **Strong Consistency**.
**Data Store:** A distributed SQL database (e.g., CockroachDB) or a strongly consistent NoSQL (e.g., DynamoDB with consistent reads).
**Patterns:** Use **Distributed Locking** (via Redis/Etcd) or **Atomic Increments** at the database level to ensure a decrement operation fails if the count is zero.

**AA9**
A **sidecar proxy** is a helper container (e.g., Envoy) running alongside the application container in the same pod.
**Istio/Envoy:** The **Control Plane** (Istiod) manages configuration and certificates; the **Data Plane** (Envoy sidecars) intercepts all network traffic.
**mTLS vs. App-level TLS:** mTLS provides **identity-based** authentication and automatic certificate rotation/management, whereas app-level TLS requires manual certificate management within the application code and doesn't provide service-to-service identity verification.

**AA10**
**Strangler Fig Pattern:** Incrementally replace specific functionalities of the monolith with new microservices until the monolith is "strangled" and can be decommission/decommissioned.
**Strategy:**
1. Place an API Gateway/Reverse Proxy in front of the .NET Framework monolith.
2. Identify a single, low-risk module (e.g., "Email Notifications").
3. Build the new version in .NET 8.
4. Update the Gateway to route "Email" traffic to the new service while everything else goes to the monolith.
5. Repeat for more complex modules until the monolith is empty.

**AA11**
The **12-Factor App** provides principles for building cloud-native apps.
1. **Codebase:** One repo, many deploys (ensures consistency).
2. **Dependencies:** Explicitly declare and isolate (prevents "it works on my machine").
3. **Config:** Store config in the environment (allows same build in Dev/Prod).
4. **Backing Services:** Treat DBs/Queues as attached resources (allows easy swapping).
5. **Statelessness:** Processes are stateless (allows horizontal scaling).
6. **Logs:** Treat logs as event streams (simplifies observability).

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Producer doesn't know Consumer) | Tight (Caller knows Callee) |
| **Scalability** | High (Consumer groups can scale) | Moderate (Limited by server capacity) |
| **Debugging** | High Complexity (Asynchronous flow) | Low Complexity (Direct request/response) |
| **Ordering** | Guaranteed within a partition | Not guaranteed across requests |
| **Failure** | Retriable via offsets/dead-letter queues | Requires client-side retry logic |
**Choice:** Use **REST/gRPC** for real-time, low-latency user interactions. Use **Kafka** for background processing, data pipelines, and decoupling high-throughput systems.

**AA13**
A **Load Balancer** distributes incoming network traffic across a group of backend servers.
**Layer 4 (Transport):** Routes based on IP and Port (TCP/UDP).
**Layer 7 (Application):** Routes based on HTTP headers, cookies, or URL paths.
**Use Case:** Routing `example.com/api` to one service and `example/static` to another.

**AA14**
A **Message Queue** (RabbitMQ) is designed for task distribution; once a message is consumed, it is typically deleted. A **Log-based Broker** (Kafka) is an append-only log where messages persist and can be replayed by multiple consumers.
**Pick RabbitMQ** for complex routing logic and immediate task execution.
**Pick Kafka** for high-throughput stream processing and event replayability.

**AA15**
A **Container** is a lightweight, isolated user-space environment sharing the host OS kernel. A **VM** includes a full guest OS and a hypervisor.
**Popularity:** Containers are popular because they are much faster to start, use significantly less RAM/CPU, and provide high density for microservices.

**AA16**
**Stateless:** The service does not store client data between requests (e.g., a JWT-based Auth service).
**Stateful:** The service maintains session data or local state (e.g., a database or a shopping cart service).
**Scaling:** Stateless services are easier to scale because any instance can handle any request; there is no "sticky session" requirement or need to synchronize local memory.

**AA17**
An **ORM** maps database tables to objects in code.
**Examples:** Hibernate (Java), Entity Framework (.NET).
**Trade-offs:**
*   **Pros:** Faster development, type safety, protection against SQL injection.
*   **Cons:** "N+1" query problems, abstraction leakage, and difficulty in optimizing complex, high-performance queries.

**AA18**
The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function.
**Implementation:**
*   **Thread Pools:** Assign a specific thread pool to "Service A" calls. If Service A hangs, it only exhausts its own pool, leaving the rest of the application responsive.
*   **Deployment Groups:** Deploy "Critical Service" and "Non-critical Service" on separate clusters/nodes so a resource leak in one doesn't crash the other.

**AA19**
**OT (Operational Transformation):** Transforms the index of operations to maintain consistency. Requires a central server to coordinate.
**CRDT (Conflict-free Replicated Data Type):** Data structures that can be updated independently and merged deterministically without a central server.
**Comparison:**
*   **OT:** Lower latency for simple edits, but extremely high complexity to implement for all edge cases.
*   **CRDT:** Higher memory/bandwidth overhead, but much simpler to implement for distributed systems.
**Choice for Offline Editing:** **CRDT**. Since there is no central server to "transform" operations while offline, CRDTs allow the local state to merge seamlessly with the server once the connection is restored.

**AA20**
**Challenges:** Maintaining a single `trace_id` across different languages and protocols.
**Context Propagation:** Using headers like `traceparent` (W3C) or `X-B3-TraceId` to pass IDs.
**Sampling:** **Head-based** (decide to trace at the start) vs. **Tail-based** (dec/ide after seeing the whole trace, e.g., to capture errors).
**Storage:** Jaeger/Tempo use indexed storage to allow querying by service or error.
**Kafka Continuity:** To ensure continuity, the producer must inject the trace context into the **Kafka Message Headers**. The consumer then extracts this header to continue the span.

### On-Premise Infrastructure Architecture

**OP1**
**Type 1 (Bare-metal):** Runs directly on hardware (e.g., VMware ESXi, Xen).
**Type 2 (Hosted):** Runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2**
**SAN (Storage Area Network):** Block-level storage, high performance, used for databases/VM disks. *Protocols: Fibre Channel, iSCSI.*
**NAS (Network Attached Storage):** File-level storage, easier to manage, used for shared files/documents. *Protocols: NFS, SMB/CIFS.*

**OP3**
**3-Tier:** Core, Distribution, Access.
**Leaf-Spine:** A two-tier architecture where every Leaf switch connects to every Spine switch.
**Problem Solved:** It provides predictable, low-latency "any-to-any" connectivity and eliminates the bottleneck/congestion found in the Spanning Tree Protocol (STP) used in 3-tier architectures.

**OP4**
**Architecture:** Minimum 3 nodes for quorum.
**Quorum:** Ensures a majority of nodes are alive to prevent split-brain.
**Fencing:** (e.g., STONITH) to kill a rogue node.
**Storage:** Ceph (distributed) is ideal for Proxmox.
**Failure:** If a node fails, the cluster detects loss of quorum/heartbeat, the remaining nodes elect a new leader, and VMs are restarted on surviving nodes using shared storage.

**OP5**
**VLAN Trunking:** Carrying multiple VLANs over a single link using **802.1Q tagging** (adding a VLAN ID to the Ethernet frame).
**Linux Configuration:** Use `ip link` to create sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6**
**RAID Types:** 1 (Mirror), 5 (Parity, 1 drive loss), 6 (Double Parity, 2 drives loss), 10 (Mirror + Stripe), Z2 (ZFS parity, 2 drives loss).
**Choice for Database:** **RAID 10**. It provides the best write performance (no parity calculation) and high fault tolerance, which is critical for database IOPS.

**OP7**
**Architecture:**
*   **Internal AD:** Uses internal DNS servers.
*   **DMZ:** Separate network segment with public-facing authoritative servers.
*   **Split-Horizon:** Different DNS responses for internal vs. external queries.
*   **DNSSEC:** Cryptographically signs records to prevent spoofing.
*   / **Process:** A laptop on VPN uses a **Conditional Forwarder** to resolve internal names. When moving to the office, it uses the local **Recursive Resolver**.

**OP8**
**Chain of Trust:** Root CA (Self-signed, highly secure) $\rightarrow$ Subordinate CA (Intermediate) $\rightarrow$ End-entity (Server/User cert).
**Revocation:** **CRL** (List of revoked certs) vs. **OCSP** (Real-time check).
**Deployment:** Use **Certificate Templates** and **Auto-enrollment** via Group Policy.
**Compromise:** A compromised **Subordinate CA** only affects its branch; a compromised **Root CA** invalidates the entire organization's trust.

**OP9**
**Comparison:**
*   **MPLS:** High cost, high reliability, low latency, complex.
*   **IPsec VPN:** Low cost, relies on internet stability, higher latency.
*   **SD-WAN:** Intelligent path selection, easy management, moderate cost.
*   **WireGuard:** High performance, modern, but requires manual mesh management.
**Recommendation:** **SD-WAN**. It can bond MPLS and Internet links, providing the reliability needed for VoIP while being easier to manage for 5 remote sites.

**OP10**
**iDRAC/iLO/IPMI:** Out-of-band management interfaces.
**Criticality:** Allows hardware-level control (power, BIOS, console) even if the OS is crashed or the network is down.
**Risk:** If exposed to the internet, attackers can gain full control of the physical server, bypass OS security, and perform "brick" attacks.

**OP11**
**LVM:** Traditional volume management.
**LVM-Thin:** Allows over-provisioning; space is only consumed when data is written.
**ZFS:** Integrated filesystem and volume manager with Copy-on-Write.
**Snapshots:** LVM snapshots are "copy-on-write" (can be slow); ZFS snapshots are near-instant and highly efficient due to the filesystem architecture.

**OP12**
**Design:** Use a **3-site** setup or a **2-site + Witness** (Tiebreaker) setup.
**Ceph:** Use **CRUSH rules** to ensure replicas are stored in different sites.
**Split-Brain:** If the link between sites breaks, both sites might try to claim ownership of data.
**Why 2-site is bad:** Without a third "witness" node, a network partition makes it impossible to reach a majority (quorum), leading to the cluster freezing to prevent data corruption.

**OP13**
**DORA:** **D**iscover (Client), **O**ffer (Server), **R**equest (Client), **A**cknowledge (Server).
**Failure:** If the DHCP server is down, the client will eventually fall back to an **APIPA** address (169.254.x.x), which provides no internet/network access.

**OP14**
**Unmanaged:** Plug-and-play, no configuration, no visibility.
**Managed:** Supports VLANs, Spanning Tree, SNMP, and Port Security.
**Enterprise Importance:** Essential for segmenting traffic (VLANs), monitoring for loops, and enforcing security (802.1X).

**OP15**
**NTP:** Network Time Protocol.
**Criticality:** Essential for log correlation, Kerberos authentication (which fails if clocks drift > 5 mins), and database transaction ordering.
**Drift:** Can cause authentication failures, broken backups, and "impossible"-looking logs during incident response.

**OP16**
**Physical Server:** Dedicated hardware.
**VM:** Hardware-level abstraction.
**Container:** OS-level abstraction.
**Use Bare Metal when:** The workload requires direct hardware access (e.g., high-performance GPU/FPGA), extreme low-latency, or maximum throughput (e.g., high-frequency trading).

**OP17**
**UPS:** Provides immediate battery power to bridge the gap until the generator starts and prevents hardware damage from sudden power loss.
**Generator:** Provides long-term power for extended outages.
**ATS (Automatic Transfer Switch):** Automatically switches the power source from the utility to the generator when a failure is detected.

**OP1/18**
**Active-Passive:** One node handles traffic; the other waits.
**Active-Active:** Both nodes handle traffic simultaneously.
**PostgreSQL HA:** Use **Pacemaker/Corosync** to monitor the DB. If the primary fails, the cluster uses **STONITH** (Shoot The Other Node In The Head) to ensure the old primary is truly dead, then moves the **Virtual IP (VIP)** to the standby node and promotes it to primary.

**OP19**
**3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
**RPO/RTO:** **RPO** (Recovery Point Objective - how much data loss is acceptable); **RTO** (Recovery Time Objective - how long can we be down).
**Backup vs. DR:** **Backup** is the data itself; **Disaster Recovery** is the entire process/infrastructure to restore operations.
**Strategy:** Use **Immutable Backups** (WORM - Write Once Read Many) to prevent ransomware from deleting backups. Test restores regularly via automated scripts.

**OP20**
**Roles:** **Supplicant** (Client), **Authenticator** (Switch), **Authentication Server** (RADIUS).
**Methods:** **EAP-TLS** (Certificate-based, very secure) vs. **PEAP** (Username/Password, easier to deploy).
**Failure:** The port is placed in a "Guest" VLAN or blocked entirely.
**MAB:** The switch checks the device's MAC address against a whitelist in the RADIUS server; it is less secure because MAC addresses can be spoofed.
