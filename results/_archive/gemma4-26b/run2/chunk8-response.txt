## Cloud Infrastructure Architecture

**CL1**
*   **IaaS (Infrastructure as a Service):** Provides raw computing resources (servers, storage, networking). You manage the OS, middleware, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying infrastructure. *Example: Google App Engine.*
*   **SaaS (Software as/as a Service):** Fully managed software delivered via the web. You only manage data/configuration. *Example: Salesforce.*

**CL2**
The provider is responsible for the security **of** the cloud (hardware, global infra); the customer is responsible for security **in** the cloud (data, IAM, configs).
*   **IaaS VMs:** Provider manages hypervisor/hardware; You manage OS, patching, and firewall rules.
*   **Managed Kubernetes:** Provider manages Control Plane/Nodes; You manage Pods, Network Policies, and RBAC.
*   **SaaS (M365):** Provider manages almost everything; You manage Identity, Access, and Data Governance.

**CL3**
*   **VPC:** A private, isolated virtual network.
*   **Subnet:** A range of IP addresses within a VPC (Public or Private).
*   **Security Group (SG):** A virtual firewall for *instances* (stateful).
*   **NACL:** A firewall for *subnets* (stateless).
*   **Layering:** Traffic enters the VPC $\rightarrow$ hits the NACL (subnet boundary) $\rightarrow$ hits the SG (instance boundary).
*   **Stateful vs. Stateless:** A **Stateful** SG remembers outbound requests and automatically allows the return traffic. A **Stateless** NACL requires explicit inbound *and* outbound rules for every connection.

**CL4**
*   **Landing Zone:** A pre-configured, multi-account environment with foundational security/networking.
*   **Organizational Units (OUs):** Logical groupings of accounts (e.g., Prod, Dev, Security) to apply hierarchical policies.
*   **Guardrails:** Service Control Policies (SCPs) that restrict actions (e.g., "Deny ability to disable CloudTrail").
*   **Shared Networking:** Using Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize inspection/egress via a "Hub" VPC/VNet, reducing complexity.
*   **Centralized Logging:** Aggregating logs (CloudTrail, VPC Flow Logs) into a dedicated, immutable security account.
*   **Single-account problem:** Blast radius is too large; no way to isolate workloads; difficult to manage quotas/limits; hard to implement granular billing/governance.

**CL5**
*   **Terraform/OpenTofu:** Declarative, provider-agnostic, HCL language. *Use for: Multi-cloud/Standard infra.*
*   **Pulumi:** Uses general-purpose languages (Python, Go, TS). *Use for: Developers who want "Infrastructure as Software."*
*   **CloudFormation/Bicep:** Cloud-native (AWS/Azure). *Use for: Deep integration with specific cloud features/simplicity.*
*   **Crossplane:** Kubernetes-native (Control Plane). *Use for: Managing cloud resources via K8s APIs/GitOps.*

**CL6**
*   **HPA:** Scales number of Pods based on CPU/RAM.
*   **VPA:** Increases/decreases CPU/RAM resources of existing Pods.
*   **Cluster Autoscaler:** Adds/removes Nodes (VMs) to the cluster.
*   **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag or RabbitMQ queue depth).
*   **KEDA vs HPA:** Use KEDA when scaling is triggered by external event metrics (e.g., message queue length) rather than just resource utilization.

**CL7**
*   **RPO/RTO:** RPO (Recovery Point Objective) is max data loss; RTO (Recovery Time Objective) is max downtime.
*   **Active-Active:** Both regions serve traffic; zero downtime, high cost.
*   **Active-Passive:** One region is standby; requires failover time.
*   **Replication:** **Sync** (no data loss, high latency) vs. **Async** (low latency, potential data loss).
*   **DNS:** Route53/Traffic Manager routes users to the healthy region.
*   **State:** Must be replicated (e.g., Aurora Global DB) or externalized (S3).
*   **DR Types:**
    *   **Pilot Light:** Core data is live; compute is off/minimal.
    *   **Warm Standby:** Scaled-down version of the app is always running.
    *   **Multi-site Active-Active:** Full capacity in both regions.

**CL8**
*   **GitOps:** Git is the "Single Source of Truth." Changes to Git trigger automated deployment.
*   **ArgoCD vs FluxCD:** ArgoCD provides a UI and multi-tenant management; FluxCD is more lightweight and follows a "controller" pattern.
*   **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (pulls from AWS Secrets Mgr), or **Vault** (centralized management).
*   **Drift:** If manual changes occur, the GitOps controller detects the difference and automatically "reverts" the cluster to match the Git state.

**CL9**
*   **StatefulSet:** Ensures Pods have stable identities and ordered startup/shutdown.
*   **PV/PVC (Local Storage):** Use `Local Persistent Volumes` for low-latency disk access.
*   **Headless Service:** Provides stable DNS entries for each Pod (required for peer discovery).
*   **Init Containers:** Run setup tasks (e.g., configuring files) before the main app starts.
*   **ConfigMaps:** Mounted as volumes to specific paths to inject configuration.
*   **Pod Disruption Budget (PDB):** Ensures a minimum number of replicas remain available during voluntary disruptions (e.g., node drains).

**CL10**
*   **Service Account:** Identity for a Pod within K8s.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role.
*   **Bad Practice:** Hardcoding/mounting long-lived IAM credentials (Access Keys) in a Pod. If the Pod is compromised, the attacker has permanent cloud access.
*   **Solution:** Workload Identity uses OIDC federation. The Pod exchanges a K8s token for a short-lived cloud STS token, eliminating static secrets.

**CL11**
*   **Object (S3):** Unstructured data, massive scale, via API. *Use: Media, backups.*
*   **Block (EBS):** Raw disk for VMs. *Use: Databases, OS drives.*
*   **File (EFS):** Shared filesystem (NFS/SMB) for multiple instances. *Use: Shared config, CMS.*
*   **Durability/Availability:** Object storage usually offers 99.999999999% (11 9's) durability; Block/File storage focus more on availability/latency.

**CL1/12**
*   **Zero-Trust Architecture:** "Never trust, always verify."
*   **Components:**
    *   **Network Policies:** Micro-segmentation (L3/L4).
    *   **Service Mesh (Istio/Linkerd):** mTLS for encrypted, authenticated Pod-to-Pod communication.
    *   **Admission Controllers (OPA):** Enforce policy (e.g., "No privileged containers").
    *   **Image Signing (Cosign):** Verify container provenance.
    *   **Runtime Security (Falco):** Detect anomalous syscalls.
*   **Difference:** Traditional security relies on a "hard perimeter" (firewall); Zero-Trust assumes the network is already breached and secures every individual workload.

**CL13**
*   **CDN:** A distributed network of proxy servers that cache content closer to users.
*   **How:** User requests content $\rightarrow$ DNS routes to nearest Edge Location $\rightarrow$ Edge serves cached content or fetches from Origin.
*   **Services:** AWS CloudFront, Azure Front Door.
*   **CDN vs Origin:** Use CDN for static assets (images, JS) to reduce latency and origin load. Use Origin directly for highly dynamic, personalized, or real-time data.

**CL14**
*   **Region:** A geographic area containing multiple AZs.
*   **Availability Zone (AZ):** One or more discrete data centers with redundant power/networking.
*   **Why Multi-AZ:** To protect against a single data center failure (fire, flood, power outage).
*   **Zonal vs Regional:** A Zonal resource (EBS) exists in one AZ; a Regional resource (S3) is replicated across the entire region.

**CL15**
*   **Managed DB:** A service where the provider manages the underlying infrastructure.
*   **Provider handles:** Patching, backups, high availability, scaling, and hardware maintenance.
*   **You handle:** Schema design, query optimization, and user access control.

**CL16**
*   **IAM Users:** Permanent identities for people/apps.
*   **Groups:** Collections of users with shared permissions.
*   **Roles:** Temporary identities assumed by entities (EC2, Lambda).
*   **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply via granular IAM policies and regular access reviews.

**CL17**
*   **Serverless:** Event-driven execution without managing servers.
*   **Comparison:** AWS Lambda, Azure Functions, and GCF are functionally similar (trigger-based).
*   **Cold Starts:** The latency incurred when a new function instance is initialized. Matters for latency-sensitive APIs.
*   **Poor Fit:** Long-running processes (e.g., video encoding), high-frequency/constant-load workloads (too expensive), or apps requiring low-latency/stateful connections.

**CL18**
*   **Ingress Resource:** Standard K8s object for L7 routing (HTTP/HTTPS).
*   **Gateway API:** Next-gen, more expressive, separates infrastructure (Gateway) from routing (HTTPRoute).
*   **Cloud LB Annotations:** Tells the cloud provider to provision an external LB (e.g., NLB/ALB) to point to the service.
*   **Service Mesh Ingress:** The entry point is a mesh gateway (e.g., Istio Ingress) that handles mTLS and advanced traffic splitting.
*   **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Pod itself.
*   **Gateway API vs Ingress:** Use Gateway API for complex, multi-tenant routing requirements and better separation of concerns between platform and app teams.

**CL19**
*   **Strategy:**
    *   **Savings/Reserved:** Commit to usage for 1-3 years for deep discounts.
    *   **Spot:** Use for fault-tolerant, batch workloads (up to 90% discount).
    *   **Right-sizing:** Use tools (AWS Compute Optimizer) to match instance size to actual usage.
    *   **Storage Tiering:** Move old data to Glacier/Archive.
    *   **FinOps:** Implement "Tagging" for cost allocation.
*   **Tools:** AWS Cost Explorer, CloudHealth, or Kubecost.
*   **Models:** **Showback** (reporting costs to teams) vs. **Chargeback** (actually billing departments).

**CL20**
*   **Strategy:** Use Kubernetes (runtime), Terraform (IaC), and S3-compatible storage to create an abstraction layer.
*   **Networking:** Use VPN or DirectConnect/ExpressRoute to link clouds.
*   **Identity:** Use OIDC/SAML for federated identity.
*   **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs.
*   **Justification:** Multi-cloud is justified for extreme high availability or regulatory requirements; it is unnecessary complexity for most standard enterprise workloads.

## OT Infrastructure Architecture

**OT1**
The Purdue Model segments industrial networks into levels:
*   **Level 0:** Physical process (sensors, actuators).
*   **Level 1:** Basic control (PLCs, RTUs).
*   **Level 2:** Supervisory control (HMI, SCADA).
*   **Level 3:** Site operations (Historian, MES).
*   **Level 4/5:** Enterprise/Corporate (ERP, Office IT).

**OT2**
*   **Difference:** IT focuses on Data Confidentiality; OT focuses on Process Availability and Safety.
*   **Patching:** You cannot patch OT systems like IT because a reboot or a momentary loss of communication could cause physical damage, chemical spills, or safety hazards.

**OT3**
*   **IDMZ:** A buffer zone between IT and OT.
*   **Traffic:** Only strictly defined, inspected traffic (e.g., Historian replication) should cross. Direction should be "Push" from OT to IT (never allow IT to initiate connections to OT).
*   **Danger:** Direct connectivity allows a compromised office laptop to send malicious commands directly to a PLC, bypassing all industrial security controls.

**OT4**
1.  **Modbus TCP:** Level 1/2 (Fieldbus/Control).
2.  **OPC UA:** Level 2/3 (Interoperability/Supervisory).
3.  **EtherNet/IP (CIP):** Level 1/2 (Control/I/O).
4.  **PROFINET:** Level 1/2 (Real-time control).
5.  **MQTT:** Level 3/Cloud (Telemetry/Edge-to-Cloud).

**OT5**
*   **Data Diode:** Hardware-based, physically allows data to flow in only one direction (unidirectional).
*   **Firewall:** Software-based, allows bidirectional communication based on rules.
*   **Use Case:** Use a diode for high-security environments (nuclear, power) where you must ensure no command can ever reach the OT side.
*   **Limitation:** A diode prevents "handshaking" or TCP acknowledgments, making it much harder to use standard protocols like HTTP/TCP.

**OT6**
*   **Flow:** Sensors $\rightarrow$ PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (MQTT) $\rightarrow$ Cloud Ingestion.
*   **Boundaries:** Place a firewall/IDMZ between Level 3 (Site) and Level 4 (Enterprise). The Edge Gateway should sit in the DMZ, acting as a proxy.

**OT7**
*   **Zone:** A grouping of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Model:**
    *   **Zone 1 (Safety):** SIS (Isolated).
    *   **Zone 2 (Control):** PLCs/SCADA (Strictly controlled conduits).
    *   **Zone 3 (Operations):** Engineering/Historian.
    *   **Zone 4 (Corporate):** IT/ERP.
    *   **Conduits:** Firewalls/Diodes between each zone.

**OT8**
*   **Strategy:** Implement VLANs for each production line.
*   **Architecture:** Use a "Collapsed Core" or "Spine-Leaf" with industrial switches.
*   **Segmentation:** Place a firewall between the production VLANs and the plant-wide SCADA/Historian VLAN.
*   **Transition:** Use "Monitor Mode" (SPAN/TAP) first to map traffic without blocking, then implement ACLs incrementally.
*   **Remote Access:** Use a Jump Host in the IDMZ with MFA.

**OT9**
*   **SIS vs BPCS:** SIS is the "emergency brake" (safety); BPCS is the "driver" (control).
*   **IEC 61511:** Standard for functional safety in the process industry.
*   **Isolation:** SIS must be isolated because if the BPCS is compromised, the attacker could manipulate the process to a dangerous state; the SIS must remain uncompromable to shut it down safely.
*   **Ransomware:** If SIS is hit, you lose the ability to safely stop the process, potentially leading to catastrophic physical failure.

**OT10**
*   **PLC:** Logic-based controller for specific tasks (Level 1).
*   **DCS:** Distributed control for large, continuous processes (Level 2).
*   **SCADA:** Supervisory system for monitoring geographically dispersed assets (Level 2/3).
*   **Coexistence:** Yes, they often coexist (e.g., SCADA monitors multiple PLC-driven lines).

**OT11**
*   **Architecture:** Use a Jump Host in the IDMZ.
*   **Controls:** MFA is mandatory; session recording (e.g., CyberArk) for auditing; time-limited/Just-in-Time (JIT) access; no direct RDP from IT to HMI.

**OT12**
*   **Detection:** Use IDS (e.g., Dragos, Nozomi) to spot anomalous industrial protocols.
*   **Response:** 1. Verify alert $\rightarrow$ 2. Isolate the VPN/IDMZ $\rightarrow$ 3. Switch to manual/local control $\rightarrow$ 4. Forensic analysis.
*   **Operator Role:** The operator is the "human sensor." They must monitor for physical process deviations (pressure/temp) that indicate a cyber-attack.

**OT13**
*   **HMI:** A dashboard for operators to view and interact with the process.
*   **Difference:** An Engineering Workstation is used to *program* and *configure* the PLCs/logic; an HMI is used to *monitor* the running process.

**OT14**
*   **Historian:** A database that records time-series process data.
*   **Importance:** Essential for auditing, regulatory compliance, and trend analysis.
*   **Difference:** Plant Historian (Level 3) stores high-resolution, real-time data; Enterprise Historian (Level 4) stores aggregated, long-term data for business decisions.

**OT15**
*   **Ladder Logic:** A graphical programming language resembling electrical relay diagrams.
*   **Why dominant:** It is intuitive for electricians/engineers trained in physical relay logic and is highly deterministic.

**OT16**
*   **RTU:** A device used to connect remote sensors to a SCADA system, often in harsh/remote locations.
*   **Difference:** PLCs are more "logic-heavy" and localized; RTUs are "communication-heavy" and designed for low-power/remote telemetry.
*   **Environment:** RTUs are used in pipelines, power grids, and water pumping stations.

**OT17**
*   **Analog:** Continuous signal (e.g., 4-20mA).
*   **Digital:** Discrete (On/Off).
*   **4-20mA vs 0-20mA:** 4-20mA is preferred because if the wire breaks, the signal drops to 0mA, which is detectable as a "fault" (Live Zero). In 0-20mA, a 0mA reading could be a valid measurement or a broken wire.

**OT18**
*   **Inventory:** You cannot protect what you cannot see.
*   **Techniques:** **Passive Monitoring** (listening to traffic) is safe; **Active Scanning** (pinging/probing) can crash sensitive, older PLCs.
*   **Danger:** Active scanning can overwhelm the limited CPU/Network stacks of legacy OT devices, causing them to stop functioning.

**OT19**
*   **MITRE ATT&CK for ICS:**
    1.  **Inhibit Response Function:** (e.g., Manipulating HMI).
    2.  **Impair Process Control:** (e.g., Modifying PLC logic).
    4.  **Loss of Safety:** (e.g., Disabling SIS).
    5.  **Inhibit Control:** (e.g., DoS on Controller).
*   **Difference:** The ICS matrix focuses on physical impact/consequences, whereas Enterprise focuses on data theft/exfiltration. Use it to map your visibility gaps (e.g., "Do we have detection for unauthorized PLC writes?").

**OT20**
*   **SOC Design:** Use passive network taps to feed a SIEM.
*   **Detection:** Focus on "Protocol Anomalies" (e._g., unexpected Modbus function codes).
*   **Triage:** High-priority alerts must involve OT Engineers to verify if the "anomaly" is a physical process change or a cyber attack.
*   **False Positives:** High in OT due to maintenance/reconfiguration.
*   **Firmware Alert:** Treat as a "Critical" incident. Isolate the PLC, check the "Golden Image" in the engineering workstation, and verify if any authorized maintenance was scheduled.
