## Cloud Infrastructure Architecture

**CL1**
*   **IaaS (Infrastructure as a Service):** Provides raw computing resources (servers, storage, networking). You manage the OS, middleware, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying infrastructure. *Example: Google App Engine.*
*   **SaaS (Software as/as a Service):** Fully managed software delivered via the web. You only manage data/configuration. *Example: Salesforce.*

**CL2**
The provider is responsible for the security **of** the cloud (hardware, global infra); the customer is responsible for security **in** the cloud (data, IAM, configs).
*   **IaaS VMs:** Provider manages hypervisor/hardware; You manage OS, patching, and firewall rules.
*   **Managed Kubernetes:** Provider manages Control Plane/Nodes; You manage Pods, Network Policies, and RBAC.
*   **SaaS (M365):** Provider manages almost everything; You manage Identity, Access, and Data Governance.

**CL3**
*   **VPC:** A private, isolated virtual network.
*   **Subnet:** A range of IP addresses within a VPC (Public or Private).
*   **Security Group (SG):** A virtual firewall for *instances* (stateful).
*   **NACL:** A firewall for *subnets* (stateless).
*   **Layering:** Traffic enters the VPC $\rightarrow$ hits the NACL (subnet level) $\rightarrow$ hits the SG (instance level).
*   **Stateful vs. Stateless:** Stateful (SG) remembers connections; if you allow port 80 in, outbound response is automatically allowed. Stateless (NACL) requires explicit inbound *and* outbound rules for every flow.

**CL4**
*   **Landing Zone:** A pre-configured, multi-account environment with foundational security/logging.
*   **Organizational Units (OU):** Logical groupings of accounts (e.g., Prod, Dev, Security) to apply policies.
*   **Guardrails:** Service Control Policies (SCPs) that restrict actions (e.g., "Deny region: us-east-2").
*   **Shared Networking:** Using Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize inspection/egress via a single firewall/inspection VPC.
*   **Centralized Logging:** Aggregating logs (CloudTrail, VPC Flow) into a dedicated, immutable security account.
*   **Single-account problem:** Blast radius is too large; noisy neighbors; difficult to enforce granular IAM; no clear separation of billing/audit.

**CL5**
*   **Terraform/OpenTofu:** Declarative, provider-agnostic, state-managed. *Use: Multi-cloud/Standard infra.*
*   **Pulumi:** Uses general-purpose languages (Python, Go, TS). *Use: Complex logic/Software engineers.*
*   **CloudFormation/Bicep:** Native to AWS/Azure. *Use: Deep integration with provider-specific features.*
*   **Crossplane:** Kubernetes-native; manages infra via K8s CRDs. *Use: Managing infra via K8s control plane.*

**CL6**
*   **HPA:** Scales number of Pods based on CPU/RAM.
*   **VPA:** Increases/decreases CPU/RAM resources of existing Pods.
*   **Cluster Autoscaler:** Adds/removes actual VM nodes to the cluster.
*   **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag or RabbitMQ queue depth).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external event sources (message queues, databases) rather than just resource metrics.

**CL7**
*   **RPO/RTO:** RPO (Recovery Point Objective) = max data loss; RTO (Recovery Time Objective) = max downtime.
*   **Active-Active:** Both regions serve traffic; zero RTO/RPO; highest cost.
*   **Active-Passive:** One region waits; higher RTO.
*   **Replication:** Sync (zero loss, high latency) vs. Async (potential loss, low latency).
*   **DNS:** Route53/Traffic Manager routes users to the healthy region.
*   **State:** Use global databases (DynamoDB Global Tables) or replicated storage.
*   **DR Types:**
    *   **Pilot Light:** Core data is live; compute is off/minimal.
    *   **Warm Standby:** Scaled-down version of the app is always running.
    *   **Multi-site Active-Active:** Full capacity in both regions.

**CL8**
GitOps uses Git as the "Single Source of Truth."
*   **ArgoCD vs FluxCD:** ArgoCD has a rich UI and is great for K8s-centric teams; FluxCD is more lightweight and follows a "controller" pattern.
*   **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from AWS Secrets Mgr), or **Vault** (centralized).
*   **Drift:** GitOps controllers detect the difference between Git and Cluster and automatically "self-heal" by overwriting the manual change to match Git.

**CL9**
*   **StatefulSet:** Ensures stable network ID and ordered deployment.
*   **PV/PVC (Local Storage):** Use `Local Persistent Volumes` for low-latency disk access.
*   **Headless Service:** Allows direct Pod-to-Pod communication via DNS (no Load Balancer).
*   **Init Containers:** Run setup scripts (e.g., configuring filesystem paths) before the main app starts.
*   **ConfigMaps:** Mounted as volumes to inject files into specific paths.
*   **Pod Disruption Budget (PDB):** Ensures a minimum number of replicas remain available during maintenance.

**CL10**
*   **Service Account:** K8s identity for a Pod.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role.
*   **Bad Practice:** Hardcoding AWS Access Keys in a Pod allows anyone with Pod access to steal them.
*   **Solution:** Workload Identity uses OIDC federation; the Pod exchanges a K8s token for a short-lived cloud token, eliminating long-lived credentials.

**CL11**
*   **Object (S3):** Unstructured data, web-accessible, massive scale. *Use: Images, backups.*
*   **Block (EBS):** Raw disk for VMs. *Use: Databases, OS drives.*
*   **File (EFS):** Shared filesystem for multiple instances. *Use: Shared config, CMS.*
*   **Guarantees:** High durability (11 9's) for Object; high availability for Block/File.

**CL12**
*   **Zero-Trust K8s:**
    *   **Network Policies:** L3/L4 isolation (deny-all by default).
    *   **Service Mesh (Istio/Linkerd):** mTLS for L7 encryption and identity.
    *   **Admission Controllers (OPA):** Enforce policies (e.g., "No privileged containers").
    *   **Image Signing (Cosign):** Ensure only verified images run.
    *   **Runtime Security (Falco):** Detect anomalous syscalls (e.g., shell spawned in container).
*   **Difference:** Traditional security relies on a "hard perimeter" (firewall); Zero-Trust assumes the network is compromised and verifies every request/identity.

**CL13**
*   **CDN:** A distributed network of proxy servers that caches content closer to users.
*   **Services:** AWS CloudFront, Azure Front Door.
/
*   **Use Case:** Use CDN for static assets (images, JS) to reduce latency and origin load. Serve directly from origin for highly dynamic, personalized, or sensitive data.

**CL14**
*   **Regions:** Geographic areas (e.g., us-east-1).
*   **AZs:** Isolated locations within a region.
*   **Why Multi-AZ?** To protect against a single data center failure (power/cooling).
*   **Zonal vs Regional:** Zonal resources (EBS) live in one AZ; Regional resources (S3) are accessible across the whole region.

**CL15**
*   **Managed DB:** RDS, Cloud SQL.
*   **Provider handles:** Patching, backups, high availability, hardware scaling, and replication.
*   **You handle:** Schema design, query optimization, and user access control.

**CL16**
*   **IAM:** Users (people), Groups (collections of users), Roles (identities assumed by entities), Policies (JSON permissions).
*   **Least Privilege:** Grant only the minimum permissions required for a task. Apply via granular IAM policies and scoped-down resource ARNs.

**CL17**
*   **Serverless:** Event-driven, no server management. (Lambda, Azure Functions).
*   **Cold Starts:** Latency incurred when a new function instance is initialized.
*   **Poor Fit:** Long-running processes, heavy computational tasks, or applications requiring constant low-latency response (where cold starts are unacceptable).

**CL18**
*   **Ingress:** Basic L7 routing (path/host).
*   **Gateway API:** Next-gen, more expressive, separates infra-admin from app-developer.
*   **Cloud LB Annotations:** Uses cloud-specific features (e.g., AWS ALB Ingress Controller).
*   **Service Mesh Gateway:** Handles L7 traffic/mTLS.
*   **TLS Termination:** Can happen at the Cloud LB, Ingress Controller, or Service Mesh.
*   **Use Gateway API:** When you need complex routing, traffic splitting, or multi-tenant management.

**CL19**
*   **Strategy:**
    *   **Savings Plans/RI:** Commit to usage for lower rates.
    *   **Spot:** Use for stateless/batch workloads (huge savings).
    *   **Right-sizing:** Use tools (AWS Compute Optimizer) to downsize over-provisioned VMs.
    *   **Storage Tiering:** Move old data to Glacier/Archive.
    *   **FinOps:** Implement "Tagging" for cost allocation.
    *   **Showback/Chargeback:** Report costs back to specific departments to drive accountability.
*   **Tools:** AWS Cost Explorer, CloudHealth, or Kubecost.

**CL20**
*   **Strategy:** Use Kubernetes (EKS/AKS) as the abstraction. Use Terraform for IaC.
*   **Networking:** Site-to-Site VPN or DirectConnect/ExpressRoute.
*   **Identity:** OIDC/SAML federation.
*   **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs.
*   **Justification:** Necessary for extreme regulatory requirements or high-availability across providers. Unnecessary if you just want "cloud-agnostic" but can achieve it via containers on a single provider.

## OT Infrastructure Architecture

**OT1**
*   **Level 0:** Physical process (sensors, actuators).
*   **Level 1:** Control (PLCs, RTUs).
*   **Level 2:** Supervisory (HMI, SCADA).
*   **Level 3:** Operations (Historian, MES).
*   **Level 4/5:** Enterprise (ERP, Corporate IT).

**OT2**
*   **Difference:** IT focuses on Data Confidentiality; OT focuses on Availability and Safety.
*   **Patching:** OT systems often have "uptime-critical" requirements and legacy software that cannot be rebooted or might break due to sensitive timing/protocols.

**OT3**
*   **IDMZ:** A buffer zone between IT and OT.
*   **Traffic:** Only allow specific, inspected traffic (e.g., Historian replication) from OT $\rightarrow$ IT.
*   **Danger:** Direct L4 $\rightarrow$ L1 connectivity allows a compromised corporate laptop to send malicious commands directly to a PLC, bypassing all monitoring.

**OT4**
1.  **Modbus TCP:** Level 1/2 (Fieldbus/Control).
2.  **OPC UA:** Level 2/3 (Interoperability/Supervisory).
3.  **EtherNet/IP:** Level 1 (Real-time control).
4.  **PROFINET:** Level 1 (Real-time control).
5.  **MQTT:** Level 3/4 (Cloud/Edge telemetry).

**OT5**
*   **Data Diode:** Hardware-based, physically allows data to flow in only one direction (unidirectional).
*   **Use Case:** Sending sensor data to the cloud without any physical path for a return command.
*   **Limitation:** No TCP handshakes or acknowledgments can return, making it difficult for standard protocols.

**OT6**
*   **Flow:** Sensor $\rightarrow$ PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (MQTT) $\rightarrow$ Cloud Ingestion.
*   **Boundaries:** Place a firewall/IDMZ between the Edge Gateway and the Corporate network.

**OT7**
*   **Zone:** A grouping of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Model:**
    *   **Zone 1 (Safety):** SIS (Isolated).
    *   **Zone 2 (Control):** PLCs/HMIs (Protected by conduit).
    *   **Zone 3 (Operations):** SCADA/Historian.
    *   **Zone 4 (Corporate):** ERP/Email.
    *   **Conduits:** Firewalls/DPI between all zones.

**OT8**
*   **Strategy:**
    1.  **Phase 1:** Implement VLANs on existing switches.
    2.  **Phase 2:** Deploy Industrial Firewalls at the cell level.
    3.  **Phase 3:** Use "Transparent Mode" firewalls to avoid IP changes.
    4.  **Remote Access:** Use a Jump Host in the IDMZ with MFA.
    5.  **Transition:** Use a "Parallel" deployment—build the new network alongside the old and migrate one line at a time during scheduled downtime.

**OT9**
*   **SIS vs BPCS:** SIS is the "emergency brake" (safety); BPCS is the "driver" (process control).
*   **IEC 61511:** Standard for functional safety in the process industry.
*   **Isolation:** If SIS is connected to IT, ransomware could disable the safety shutdown, leading to physical catastrophe (explosion/leak).

**OT10**
*   **PLC:** Logic-based controller for specific machines.
*   **DCS:** Distributed control for large, continuous processes (e.g., oil refinery).
*   **SCADA:** Supervisory system for geographically dispersed assets.
*   **Coexistence:** Yes, they often work together in a hierarchy.

**OT11**
*   **Architecture:** Use a Jump Host in the IDMZ. Require MFA. Use Session Recording (e.g., CyberArk). Access must be "Just-in-Time" (JIT).
*   **Why not RDP to HMI?** Direct RDP exposes the HMI to the corporate network; if a user clicks a phishing link, the attacker has direct control of the process.

**OT12**
*   **Plan:**
    1.  **Detection:** Use IDS (e.g., Dragos/Nozomi) to flag anomalous traffic.
    2.  **Response:** Isolate the compromised VPN segment.
    3.  **Coordination:** Notify the operator; they must decide if the process can continue or needs an emergency shutdown.
    4.  **Role of Operator:** The operator is the "human-in-the-loop" who manages physical safety and decides when to transition to manual control.

**OT13**
*   **HMI:** A dashboard for operators to view and interact with the process.
*   **Engineering Workstation:** A high-privilege machine used to program PLCs and change logic.

**OT14**
*   **Historian:** A database that stores time-series process data.
*   **Importance:** Essential for auditing, regulatory compliance, and trend analysis.
*   **Difference:** Plant Historian (L3) stores high-resolution, real-time data; Enterprise Historian (L4) stores aggregated, long-term data for business decisions.

**OT15**
*   **Ladder Logic:** A graphical programming language representing electrical relay logic.
*   **Why dominant?** It is intuitive for electricians/engineators and maps directly to physical relay-based hardware.

**OT16**
*   **RTU:** A device used for long-distance, low-bandwidth telemetry (e.g., remote pipelines).
*   **Difference:** PLCs are for high-speed, local logic; RTUs are for rugged, remote, intermittent communication.

**OT17**
*   **Analog vs Digital:** Analog is a continuous signal; Digital is discrete (on/off).
*   **4-20mA:** Preferred because if the wire breaks, the signal drops to 0mA (detectable as a fault), whereas 0-20mA could be mistaken for a valid "zero" reading.

**OT18**
*   **Foundation:** You cannot protect what you cannot see.
*   **Techniques:** **Passive Monitoring** (sniffing traffic) is safe; **Active Scanning** (pinging/polling) can crash sensitive, older PLCs.

**OT19**
*   **MITRE ATT&CK for ICS:**
    1.  **Inhibit Response Function:** (e.g., disabling alarms).
    2.  **Impair Process Control:** (e.g., changing setpoints).
    3.  **Loss of Safety:** (e.g., disabling SIS).
    4.  **Damage to Physical Equipment:** (e.g., over-pressurizing).
    5.  **Inhibit Control:** (e.g., DoS on PLC).
*   **Difference:** Focuses on physical impact/consequences rather than just data theft. Use it to map your visibility gaps (e.g., "Do we have visibility into Level 1 protocol changes?").

**OT20**
*   **Design:**
    *   **Collection:** Use passive network taps/SPAN ports to avoid latency.
    *   **Integration:** Forward logs to a central SIEM via the IDMZ.
    *   **Detection:** Use OT-specific signatures (e.g., "S7comm Write Request").
    *   **Triage:** IT analysts handle the "network" side; OT engineers handle the "process" side.
    *   **False Positives:** High in OT due to unusual (but valid) maintenance windows.
    *   **Firmware Alert:** Treat as a Critical Incident. Immediately isolate the PLC, check the "Golden Image" in the engineering workstation, and verify the change window with the plant manager.
