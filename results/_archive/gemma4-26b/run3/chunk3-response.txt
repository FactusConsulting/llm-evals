## OpenTofu / Terraform

**T1**
`tofu plan` performs a dry run, comparing the current state against the desired configuration and generating an execution plan. `tofu apply` executes that plan to reach the desired state, making actual changes to the infrastructure.

**T2**
State is a JSON file that maps real-world resources to your configuration and tracks metadata (dependencies, resource IDs). Remote state is critical for team collaboration, as it provides a single source of truth, enables state locking to prevent concurrent writes, and keeps sensitive data out of local machines.

**T3**
`count` uses an integer to create multiple resources; if you remove an item from the middle of a list, it causes a cascade of resource recreations. `for_each` uses a map or set; it identifies resources by specific keys. `for_each` is preferred when managing collections where items might be added or removed from the middle, as it maintains stable resource addresses.

**T4**
This is "configuration drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy between the actual cloud state and the state file. It will then propose a plan to revert the manual change (to match the code) or update the state (if you manually update the code).

**T/5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.value
}
```

**T6**
`terraform_remote_state` reads the entire state file of another workspace, which can expose sensitive data and creates tight coupling. `output` values allow you to expose only specific, necessary data. The recommended alternative is using a shared configuration or a dedicated "SSM/Parameter Store" approach where the producer writes values to a registry, and the consumer reads them, decoupling the state files.

**T7**
The `null_resource` provisioner runs during the "apply" phase, but the output is calculated during the "plan/apply" phase. If the `kubeconfig` is generated by a script in `remote-exec`, the value doesn't exist in the state until the provisioner finishes. To fix, use a `local_file` resource to write the output to a file, or use a `null_resource` with a `triggers` block that depends on the completion of the exec, and ensure the output is derived from a persistent source (like a file or cloud secret) rather than an in-memory variable.

**T8**
`import` brings existing infrastructure under OpenTofu management by mapping a real ID to a resource address in code. Limitations: It doesn't generate the code for you (historically) and requires manual configuration. The `import` block (1.5+) is declarative; it allows you to define the import in the code itself, making it partable, reviewable via PR, and easier to manage in CI/CD.

**T9**
A `variable` is an input parameter used to make configurations dynamic. An `output` is a return value used to export information from a module. Variables drive the configuration; outputs provide data to the caller.

**T10**
A provider is a plugin that translates OpenTofu API calls into cloud provider API calls (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, the command will fail because the provider binaries and plugins have not been downloaded to the `.terraform` directory.

**T11**
The `.terraform.lock.hcl` file contains the specific versions and hashes of the providers used. It should be committed to version control to ensure that every environment (Dev, Prod, CI/s) uses the exact same provider versions, preventing "it works on my machine" issues caused by unexpected provider updates.

**T12**
`tofu destroy` removes all resources managed by the current configuration. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

**T13**
A data source allows you to fetch information from existing infrastructure that is *not* managed by your current OpenTofu code. Example: Fetching the ID of a pre-existing VPC or a specific AMI ID from the AWS marketplace.

**T14**
`variables` are inputs provided by the user at runtime. `locals` are internal constants or computed values derived from other variables or logic. Use `locals` for complex transformations, repeated logic, or to avoid hardcoding values that are derived from inputs, keeping the `variable` blocks clean and simple.

**T15**
`lifecycle` controls resource behavior during updates.
- `create_before_destroy`: Creates the new resource before deleting the old one (use case: zero-downtime replacement of a Load Balancer).
- `prevent_destroy`: Stops OpenTofu from destroying a resource (use case: protecting a production database).
- `ignore_changes`: Tells OpenTofu to ignore updates to specific attributes (use case: ignoring tags added by an external security scanner).

**T16**
A `moved` block tells OpenTofu that a resource has changed its address (e.g., moved from the root module into a child module) without actually destroying and recreating it. This allows for safe refactoring of large codebases.

**T17**
OpenTofu builds a Directed Acyclic Graph (DAG). **Implicit dependencies** are created when one resource references the attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are created via `depends_on`. `depends_on` forces a specific order but limits parallelism because it prevents OpenToli from calculating that resources can be created simultaneously. Use it only when a dependency exists that OpenTofu cannot "see" through attribute references.

**T18**
1. **Reduce State Size**: Split large monolithic states into smaller, decoupled state files (Tradeoff: increased complexity in managing dependencies).
2. **Targeted Plans**: Use `-target` for specific changes (Tradeoff: risks missing side effects in the wider infrastructure).
3. **Minimize Data Sources**: Reduce the number of `data` lookups (Tradeoff: may require manual updates to IDs).
4. **Refactor Modules**: Use smaller, more focused modules (Tradeoff: requires more architectural planning).

**T19**
State locking prevents two users/processes from running `apply` simultaneously, which would corrupt the state. If a lock is not released (e.g., a crash), the state file remains "locked." You can manually break it using `tofu force-unlock <LOCK_ID>`. **Risk**: If you force unlock while another process is actually running, you will almost certainly corrupt the state file.

**T/20**
1. Ensure the new S3 bucket and DynamoDB table exist.
2. Update the `backend` block in your configuration to point to the new S3 bucket and DynamoDB table.
3. Run `tofu init`. OpenTofu will detect the change and ask if you want to migrate the existing state to the new backend.
4. Confirm the migration.
5. Verify by checking the S3 bucket for the `.tfstate` file and ensuring the DynamoDB lock table is being populated.

## Ansible

**A1**
A **task** is a single action (e.g., installing a package). A **playbook** is a collection of plays that maps tasks to hosts. A **role** is a structured, reusable collection of tasks, variables, files, and templates.

**A2**
`ansible_facts` is a dictionary of system information gathered by Ansible. To access the OS family, use `{{ ansible_facts['os_family'] }}` (or `{{ ansible_os_family }}` in older versions).

**A3**
- `command`: Executes a command on the remote node; does not process through a shell (no pipes/redirects). Use for simple, safe commands.
- `shell`: Executes a command through `/bin/sh`; supports pipes, redirects, and environment variables. Use when shell features are needed.
- `raw`: Executes a command via a raw SSH connection without needing Python on the target. Use for bootstrapping minimal nodes.

**A4**
Idempotency means running a task multiple times results in the same state without unintended changes.
- **Idempotent**: `apt: name=nginx state=present` (If installed, does nothing).
- **NOT Idempotent**: `shell: echo "config_line" >> /etc/config"` (Every run appends a new line).

**A5**
```yaml
- name: Install htop
  apt: name=htop state=present
  when: ansible_os_family == "Debian"

- name: Install htop on RedHat
  yum: name=htop state=present
  when: ansible_os_family == "RedHat"
```

**A6**
Priority (lowest to highest): `role defaults` < `group_vars` < `host_vars` < `set_fact` < `extra_vars`.

**A7**
Use `serial: 3` in the playbook to process only 3 hosts at a time. To ensure the first 3 are a specific group, use `wait_for` or a `pre_task` that checks for the presence of a specific service/file on those nodes before proceeding to the next batch.

**A8**
You can use `!vault` syntax within a YAML file to encrypt only specific strings, though it is more common to encrypt the whole file. To encrypt a single variable, you would typically use a separate encrypted file and include it via `vars_files`.

**A9**
An **inventory** is a list of managed hosts. A **static inventory** is a hardcoded list of hosts/groups. A **dynamic inventory** is a script or plugin that queries a cloud provider (like AWS) to generate the host list in real-time.

**A10**
`ansible webservers -m shell -a "df -h"`

**A11**
A **handler** is a special task that only runs when "notified" by another task. It differs from a regular task because it only executes once at the end of the play, regardless of how many tasks notified it. Trigger it using `notify: name_of_handler`.

**A12**
`ansible.cfg` configures Ansible behavior. Common settings:
1. `inventory`: Path to the inventory file.
2. `remote_user`: The user to connect as.
3. `forks`: Number of parallel processes to use.

**A13**
`register` captures the output of a task into a variable. You can then use `{{ variable_name }}` in subsequent tasks to perform conditional logic (e.g., `when: result.rc == 0`) or parse the output.

**A14**
`include_tasks` is **dynamic** (evaluated at runtime); it allows for loops and conditional inclusion. `import_tasks` is **static** (evaluated during parsing); it is more efficient but cannot be used with loops. `include_tasks` is better for complex logic; `import_tasks` is better for simple, predictable structures.

**A15**
**Ansible Galaxy** is a hub for sharing Ansible content. To use a `requirements.yml`, run `ansible-galaxy install -r requirements.yml`. This will download the roles/collections listed in the file.

**A16**
- `ssh`: Uses standard SSH to execute Python modules on the remote host (default).
- `local`: Executes tasks on the control node itself.
- `network_cli`: Uses a specialized connection for network devices (switches/routers) that do not have Python installed.

**A17**
`delegate_to` runs a task on a different host than the target. `run_once` ensures the task executes only once for the entire play.
*Example*:
```yaml
- name: Register node IP in central DB
  shell: "curl -X POST http://db/register/{{ ansible_default_ipv4.address }}"
  delegate_to: localhost
  run_once: true
```

**A18**
1. **Forks**: Increase `forks` in `ansible.cfg` to run more parallel connections (Tradeoff: higher CPU/RAM on control node).
2. **Pipelining**: Enable `piputing = True` to reduce SSH overhead (Tradeoff: requires `requiretty` to be disabled on target).
3. **Fact Caching**: Use a Redis/Memcached backend for facts (Tradeoff: adds infrastructure complexity).
4. **Mitogen**: Use the Mitogen plugin for a highly optimized SSH implementation (Tradeoff: requires installing a plugin on the control node).

**A19**
- `{{ }}`: Variable interpolation/expression.
- `{% %}`: Control structures (loops, conditionals).
- `{# #}`: Comments.
*Snippet*:
```jinja2
upstream backend_servers {
{% for server in backend_list %}
    server {{ server.ip }}:{{ server.port }} # Health check: {{ server.status }}
{% endfor %}
}
```

**A20**
1. **Batching**: Use `serial: 5` to update 5 servers at a time.
2. **Pre-task**: Use `uri` module to remove the server from the Load Balancer.
3. **Deployment**: Run the application update tasks.
4. **Health Check**: Use `uri` module to poll the `/health` endpoint of the app.
5. **Post-task**: Re-add the server to the Load Balancer.
6. **Error Handling**: Wrap the deployment in a `block`. Use `rescue` to trigger a rollback (e.g., re-deploying the previous version) if the health check fails.
