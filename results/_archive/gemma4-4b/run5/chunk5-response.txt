**DN1** — A `class` is a reference type, allocated on the heap, and supports inheritance and polymorphism. A `struct` is a value type, allocated on the stack (or inline within a containing type), and is optimized for small data structures. Use a `struct` when the type represents a small, immutable value (e.g., a point, color, or coordinate) and copying it is cheap.

**DN2** — `IEnumerable<T>` represents a sequence that can be iterated over lazily (pull-based). `IQueryable<T>` represents an expression tree that can be translated into an external query language (like SQL) and executed remotely (push-based). The distinction matters because `IEnumerable<T>` executes the query locally in memory after fetching all data, while `IQueryable<T>` allows the database provider to execute the filtering, sorting, and projection on the server, minimizing data transfer.

**DN3** — `async/await` allows asynchronous code to be written in a synchronous-looking style by pausing execution until an awaited `Task` completes, without blocking the thread. A `Task` represents an asynchronous operation that might return a value or throw an exception. A `ValueTask<T>` is a struct optimization used when the result is often available synchronously (i.e., the operation completes immediately). Use `ValueTask<T>` when you expect the operation to complete synchronously most of the time, as it avoids heap allocation associated with `Task<T>`.

**DN4** — Dependency Injection (DI) is a design pattern where components receive their dependencies from an external source (the container) rather than creating them internally. The lifetimes are: **Transient** (a new instance is created every time it is requested), **Scoped** (a single instance is created per scope, typically per HTTP request), and **Singleton** (a single instance is created for the entire application lifetime). A common bug is injecting a Scoped service (e.g., `DbContext`) into a Singleton service; the Singleton holds a reference to the Scoped instance, causing the Scoped instance to live for the entire application lifetime, violating the intended request-specific scope and leading to concurrency issues or incorrect state sharing.

**DN5** — `string` is an immutable reference type in C# that stores UTF-16 characters, involving overhead for object management. `ReadOnlySpan<char>` is a stack-allocated, memory-safe view over a contiguous block of memory (like a string's internal buffer). Use `Span<T>` (or `ReadOnlySpan<T>`) for high-performance string processing, parsing, and manipulation when you need to avoid heap allocations and work directly with underlying memory buffers, especially in hot paths.

**DN6** — The .NET GC is a generational, tracing garbage collector. **Gen 0** holds short-lived objects; collections here are frequent and fast. **Gen 1** acts as a buffer between Gen 0 and Gen 2. **Gen 2** holds long-lived objects; collections here are less frequent and more expensive. The **Large Object Heap (LOH)** stores objects larger than a threshold (typically 85KB). The GC cannot compact the LOH efficiently, leading to fragmentation. `IDisposable` implements the Dispose pattern, allowing deterministic cleanup of unmanaged resources (like file handles or network sockets) *before* the GC runs, which is necessary because the GC only manages managed memory, not external resources.

**DN7** — `ConfigureAwait(false)` tells the runtime that the continuation of the asynchronous method does not need to resume on the original `SynchronizationContext`. By default, the runtime tries to capture the context (e.g., the UI thread context) to ensure thread affinity. Using `ConfigureAwait(false)` prevents this context capture, which is crucial in library code or high-throughput services to avoid deadlocks and improve performance by allowing the continuation to run on any available thread pool thread. You should use it when writing library code or in high-concurrency backend services; you should *not* use it when writing UI code where context preservation is necessary.

**DN8** — **Primary Constructors** allow defining constructor parameters directly in the class signature (e.g., `class Service(ILogger logger)`). **Collection Expressions** (`[int]`, `[string]`) provide concise syntax for creating collections. **FrozenDictionary** is an immutable dictionary optimized for read-only access.
*Example:*
```csharp
public class UserService(ILogger<UserService> logger)
{
    public void LogUser(int id) => logger.LogInformation($"User {id} processed.");
}
// Usage in Program.cs:
builder.Services.AddScoped<UserService>();
```

**DN9** — The likely cause is that the `DbContext` is being treated as a Singleton or is being shared across multiple concurrent requests/tasks. EF Core's `DbContext` is *not* thread-safe and must be scoped per unit of work (i.e., per HTTP request). The fix is to ensure the `DbContext` is registered with a **Scoped** lifetime in the DI container. High concurrency exposes this race condition when multiple threads attempt to modify the same shared, non-thread-safe context instance simultaneously.

**DN10** — A `class` is a reference type, mutable by default, and designed for object-oriented inheritance. A `record` is a reference type optimized for immutability and value equality. It automatically provides `Equals()`, `GetHashCode()`, and `ToString()` based on its properties. A `record struct` is a value type that benefits from record semantics (value equality). Choose a `class` when identity matters (e.g., a database entity instance). Choose a `record` when value equality matters (e.g., DTOs, configuration objects).

**DN11** — **`ref`**: Passes the variable by reference, allowing the method to modify the original variable's value. The variable must be initialized before the call. **`out`**: Passes the variable by reference, allowing the method to assign a value to it. The variable does *not* need to be initialized before the call, and the method *must* assign a value to it before returning. **`in`**: Passes the variable by reference but guarantees that the method cannot modify the original variable's value (read-only reference). Use `in` for performance when passing large structs that you only need to read.

**DN12** — Nullable Reference Types (NRTs) use the `?` annotation (e.g., `string?`) to inform the compiler that a reference type might be null, enabling compile-time null checking. Nullable Value Types (e.g., `int?`) are structs that wrap a value type and can hold `null`. The difference is that NRTs deal with reference types (objects), while nullable value types deal with primitive types. Enabling NRTs forces developers to explicitly handle nullability, reducing runtime `NullReferenceException` errors.

**DN13** — **LINQ** (Language Integrated Query) is a set of features that allows querying data from various sources (collections, databases, XML) using a unified syntax. **Method Syntax** uses extension methods (`list.Where(x => x > 5)`). **Query Syntax** uses SQL-like syntax (`from x in list where x > 5`). **Deferred Execution** means that the query is not executed when it is defined, but only when the results are iterated over (e.g., in a `foreach` loop or when calling `.ToList()`).

**DN14** — Generic constraints restrict the types that can be used as type arguments for a generic type. `where T : class` requires T to be a reference type. `where T : struct` requires T to be a value type. `where T : new()` requires T to have a public parameterless constructor. `where T : IComparable<T>` requires T to implement the specified interface, allowing comparison operations. You combine constraints when the generic type needs to satisfy multiple requirements simultaneously (e.g., `where T : class, new(), IComparable<T>`).

**DN15** — An **abstract class** can contain both abstract (unimplemented) and concrete (implemented) methods, and it can define state (fields). It enforces an "is-a" relationship and allows subclasses to inherit implementation. An **interface** defines a contract—a set of methods/properties that implementing classes *must* adhere to, without providing any implementation details. Default interface methods (C# 8+) allow interfaces to provide default implementations, blurring the line by allowing interfaces to offer some concrete behavior, but the core distinction remains: abstract classes can hold state and inherit implementation; interfaces define pure contracts.

**DN16** — The middleware pipeline is a series of software components that process HTTP requests and responses sequentially in ASP.NET Core. **`app.Use()`** registers middleware that executes for every request (e.g., authentication, routing). **`app.Map()`** registers endpoints or sub-pipelines for specific routes. **`app.Run()`** terminates the pipeline, typically used for simple, single-purpose applications. Ordering is critical; middleware executes in the order it is added. Exception handling middleware must be placed *before* other application logic to catch errors that occur downstream.

**DN17** — `Channel<T>` is a type-safe, asynchronous stream abstraction provided in `System.Threading.Channels`. It is designed for producer-consumer scenarios. `BlockingCollection<T>` is a thread-safe collection designed for synchronous producer-consumer patterns, often blocking threads when full or empty. Bounded channels enforce **backpressure**: if the consumer is slow, the channel fills up, and the producer attempting to write to the bounded channel will asynchronously await until space becomes available, preventing resource exhaustion.

**DN18** — **Source Generators** are compile-time code generators that inspect the syntax tree of the source code during compilation and generate new C# source files based on patterns. They differ from **Reflection** (runtime inspection) and **IL Weaving** (post-compilation modification) by operating *before* the final compilation step. An **incremental generator** is preferred because it only regenerates the code files that are affected by changes in the source code, drastically speeding up build times compared to regenerating everything.

**DN19** — **TPL Dataflow** provides building blocks for creating complex, asynchronous data processing pipelines. **`ActionBlock`** executes an action (a side effect) asynchronously. **`TransformBlock`** executes an action that transforms input data into output data. **`BufferBlock`** acts as a queue, buffering incoming messages until they are processed. Dataflow is excellent for structured, complex pipelines where data flows sequentially through stages. Channels are generally simpler, focusing on asynchronous message passing between two endpoints (producer/consumer) without the complex internal state management of Dataflow blocks.

**DN20** — **Minimal APIs** are lightweight endpoints defined directly in the `Program.cs` file using lambda expressions (e.g., `app.MapGet("/hello", () => "Hello World")`). They differ from controller-based APIs by eliminating the need for controllers, actions, and routing attributes, resulting in less boilerplate. Trade-offs: Minimal APIs are faster to develop and have less overhead, but they can become less organized and harder to test in very large applications compared to structured controllers. Middleware and OpenAPI support are available but require explicit configuration. Route groups and endpoint filters allow grouping related endpoints and applying cross-cutting concerns (like authorization) to those groups.

**P1** — A **list** (`[]`) is mutable and ordered, allowing element modification and insertion. A **tuple** (`()`) is immutable and ordered, often used to return multiple fixed values from a function. A **set** (`{}`) is an unordered collection of unique, mutable elements. A **frozenset** is an immutable version of a set, meaning its contents cannot be changed after creation, making it hashable and usable as a dictionary key.

**P2** — The **GIL (Global Interpreter Lock)** is a mutex that protects access to Python objects, ensuring that only one thread executes Python bytecode at any given time within a single process. It affects CPU-bound workloads (heavy computation) because threads cannot run truly in parallel. Workarounds include using the `multiprocessing` module (which spawns separate processes, bypassing the GIL) or using asynchronous I/O (`asyncio`) for I/O-bound tasks.

**P3** — **Shallow copy** creates a new container object, but it populates the new container with *references* to the objects found in the original. If those referenced objects are mutable, changing them in the copy will also change them in the original. **Deep copy** recursively creates entirely new copies of all objects, including nested mutable objects.
*Example:* If `list_a = [1, [2]]` and you shallow copy it, both lists point to the same inner list `[2]`. Modifying `list_a[1]` affects the copy. A deep copy creates a new inner list.

**P4** — Decorators are syntactic sugar that allows you to wrap a function or class with another function to modify or enhance its behavior without permanently altering its source code. They take a function as input and return a new function.
*Example Decorator:*
```python
import time
from functools import wraps

def timing_decorator(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start_time = time.time()
        result = func(*args, **kwargs)
        end_time = time.time()
        print(f"Function {func.__name__} executed in {end_time - start_time:.4f} seconds.")
        return result
    return wrapper

@timing_decorator
def heavy_computation(n):
    sum(i*i for i in range(n))
```

**P5** — **Generators** are functions that use the `yield` keyword to produce a sequence of results one at a time, pausing their state between yields. They are memory efficient because they calculate and return values on demand, rather than building the entire sequence in memory. **`yield from`** delegates iteration to a sub-generator, allowing the parent generator to yield all values produced by the sub-generator transparently.
*Difference:* Returning a list computes and stores all results immediately; yielding computes and returns results lazily.

**P6** — The **asyncio event loop** is the core mechanism that manages and executes asynchronous tasks in Python. It monitors I/O operations and switches context between tasks when one is waiting for an external event (like network data), allowing a single thread to manage many concurrent operations efficiently.
*Differences:* `asyncio.run()` starts and manages the event loop for the top-level coroutine. `asyncio.gather()` runs multiple awaitables concurrently and waits for all of them to complete. `asyncio.create_task()` schedules a coroutine to run concurrently on the event loop immediately. You cannot call `time.sleep()` inside an `async` function because `time.sleep()` is a blocking call that halts the entire thread, preventing the event loop from switching context to other waiting tasks. You must use `await asyncio.sleep(delay)` instead.

**P7** — **MRO (Method Resolution Order)** dictates the order in which Python searches the inheritance hierarchy to find a method or attribute. Python 3 uses the **C3 Linearization Algorithm**, which ensures a consistent, predictable, and monotonic search order that respects the local precedence order while avoiding cycles.
*Diamond Inheritance:* The order is determined by the sequence in the class definition: `D` inherits from `B` then `C`. Since `B` inherits from `A`, the search path is $D \rightarrow B \rightarrow A \rightarrow C \rightarrow \text{object}$. When `D().who()` is called, Python finds `who` in `B`'s hierarchy, which leads to `A`. Since `A` defines `who`, that method is called. The output is `"A"`.

**P8** — A **metaclass** is the "class of a class"—it controls how a class itself is created. You use metaclasses for deep, structural modifications to classes (e.g., automatically registering all subclasses, enforcing API contracts across an entire hierarchy). **`__init_subclass__`** is a class method available since Python 3.6 that runs *after* a subclass has been created but *before* it is fully initialized. Use `__init_subclass__` for simpler, localized modifications or setup within a specific inheritance chain (e.g., setting default attributes on all subclasses).
*Use Case:* Metaclass: Creating an ORM where every model class automatically gets a `_table_name` attribute based on its name. `__init_subclass__`: Automatically adding a logging hook to every subclass of a base service.

**P9** — **Threading** uses threads within the same process; best for I/O-bound tasks (waiting). **Multiprocessing** uses separate processes; best for CPU-bound tasks (true parallelism, bypassing GIL). **`concurrent.futures`** provides a high-level interface (like `ThreadPoolExecutor` or `ProcessPoolExecutor`) to manage both threading and multiprocessing pools easily.
*Serialization:* Multiprocessing requires data passed between processes to be serialized (pickled) because processes do not share memory space. This serialization/deserialization overhead can be significant for large objects.

**P10** — `__slots__` is a class attribute that tells Python not to use a dynamic dictionary (`__dict__`) to store instance attributes. Instead, it reserves a fixed, predefined set of slots for attributes. Use it when creating classes with many instances where memory footprint is critical (e.g., large collections of small objects). It prevents the creation of `__dict__`, significantly reducing memory overhead, but it also prevents the ability to dynamically add new attributes to instances after creation.

**P11** — A **virtual environment** is an isolated directory containing a specific Python interpreter and its own set of installed packages. You should use one to prevent dependency conflicts between different projects (e.g., Project A needs Django 2, Project B needs Django 4). **`venv`** is the standard library module for creating lightweight virtual environments. **`virtualenv`** is an older, more feature-rich third-party tool. **`conda`** is a package and environment manager primarily used in data science, which manages not just Python packages but also non-Python dependencies (like compilers or specific C libraries).

**P12** — **Comprehensions** (list, dict, set) provide a concise, readable syntax for creating collections based on an iterable, often involving filtering or transformation. They are generally preferred over explicit `for` loops for brevity and performance.
*Relation to map/filter:* List comprehensions combine the functionality of `map()` (transformation) and `filter()` (filtering) into one line.
*Preference:* Use comprehensions over `map()`/`filter()` when the logic is simple and readable. Use `map()`/`filter()` when the transformation/filtering logic is complex and needs to be abstracted into a separate function.

**P13** — **`==`** checks for *value equality* (do the contents of the objects represent the same data?). **`is`** checks for *identity* (are they the exact same object in memory, i.e., do they share the same ID?). **Object interning** is an optimization where Python pre-allocates and reuses immutable objects (like small integers, short strings) to save memory. Small integers (typically -5 to 256) are interned, which is why `a is b` might be true for small numbers, even if they are technically different objects.

**P14** — **`*args`** collects an arbitrary number of positional arguments into a tuple. **`**kwargs`** collects an arbitrary number of keyword arguments into a dictionary.
*Parameter Markers:* **Positional-only (`/`)** forces arguments to be passed by position only (e.g., `def func(a, b, /):`). **Keyword-only (`*`)** forces subsequent arguments to be passed using their keyword name (e.g., `def func(*, c, d):`). This provides strict control over how functions are called, improving API clarity.

**P15** — **Context managers** use the `with` statement to ensure that setup and teardown actions are executed reliably, even if errors occur. The setup logic goes in `__enter__`, and the cleanup logic goes in `__exit__`.
*Example (Non-file):* Managing a database connection pool. `__enter__` acquires a connection from the pool; `__exit__` ensures the connection is returned to the pool, regardless of whether the block succeeded or failed.
*Alternative:* The `@contextmanager` decorator from `contextlib` allows you to write a context manager using a generator function, making the code much cleaner than manually defining `__enter__` and `__exit__`.

**P16** — **Type hinting** uses annotations (e.g., `def func(x: int) -> str:`) to indicate the expected types for variables, function arguments, and return values, enabling static analysis.
*Types:* `typing.Union[A, B]` specifies a value can be type A or type B. `Optional[T]` is shorthand for `Union[T, None]`. `Literal["A", "B"]` restricts a variable to only those specific literal values. `TypeVar` allows defining generic type variables. `Protocol` defines a structural contract (duck typing) without requiring explicit inheritance.
*Static Analysis:* Tools like Mypy or Pyright read these hints to check for type mismatches *before* runtime, catching bugs early.

**P17** — The **data model** (dunder methods) defines how Python objects behave. **`__repr__`** should return an unambiguous, developer-friendly string representation (ideally one that could recreate the object). **`__str__`** should return a readable, end-user friendly string. **`__eq__`** defines equality comparison (`==`). **`__hash__`** defines how an object is mapped to an integer for use in sets or dictionary keys. If you define `__eq__` but not `__hash__`, Python will raise a `TypeError` when you try to use that object in a set or as a dictionary key, because the hash value must be consistent for equal objects. **`__getattr__`** is called only when an attribute is *not* found normally; **`__getattribute__`** is called for *every* attribute access.

**P18** — **Descriptors** are objects that define how attribute access (getting, setting, deleting) works for another object. They implement the descriptor protocol: `__get__`, `__set__`, and `__delete__`.
*Usage:* `property` is a descriptor that wraps a method to allow it to be accessed like an attribute (get/set). `classmethod` and `staticmethod` are specialized descriptors that alter how methods are bound to the class or instance, respectively. They use the descriptor protocol internally to intercept and manage method calls.

**P19** — Python's import system searches paths defined in `sys.path`. **Absolute imports** start from the top-level package directory (e.g., `import mypackage.module`). **Relative imports** reference modules relative to the current package (e.g., `from . import sibling_module`).
*Components:* `sys.path` is the list of directories Python searches. `PYTHONPATH` is an environment variable that adds directories to `sys.path`. `__init__.py` signals to Python that a directory should be treated as a package. **Namespace packages** allow packages to be split across multiple directories without needing an `__init__.py`. A **finder** is responsible for locating a module (e.g., finding `requests`). A **loader** is responsible for loading the module's code into memory.

**P20** — **Dataclasses** are a decorator (`@dataclass`) that automatically generates boilerplate methods like `__init__`, `__repr__`, `__eq__`, etc., based on type-hinted class attributes. **`attrs`** is a mature, highly configurable library for the same purpose. **Pydantic** is a data validation library that uses type hints to enforce strict data schemas, performing runtime validation and serialization/deserialization (often used with APIs).
*Features:* `__post_init__` runs custom logic after the standard `__init__` completes. Field factories allow complex default values. `frozen=True` makes the dataclass immutable.
*Choice:* Choose **Pydantic** when you need robust runtime data validation, serialization (e.g., converting JSON to Python objects), and strict schema enforcement (critical for API contracts). Choose **dataclasses** when you primarily need boilerplate reduction for simple, internal data structures where runtime validation is not the primary concern.
