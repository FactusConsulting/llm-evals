**AA1**
The monolith is a single, tightly coupled application where all business logic resides in one codebase. Microservices are a collection of small, independent services, each running its own process and communicating via lightweight mechanisms.
Problems microservices introduce:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication.
2. **Operational Overhead:** Increased complexity in deployment, monitoring, and logging across dozens of services.
3. **Data Consistency:** Managing transactions across multiple independent databases (distributed transactions).

**AA2**
**Synchronous communication** requires the calling service to wait for an immediate response from the called service before proceeding (e.g., HTTP request/response). *Example: REST/gRPC.*
**Asynchronous communication** involves sending a message or event without waiting for an immediate response; the sender continues processing while the receiver handles the message later. *Example: Kafka/RabbitMQ.*

**AA3**
A **Reverse Proxy** sits in front of one or more servers, routing external client requests to the appropriate internal server based on rules (e.g., load balancing, SSL termination). An **API Gateway** is a specialized reverse proxy that adds business logic, such as request routing, authentication/authorization, rate limiting, request transformation, and protocol translation, specifically for APIs.
No, an API Gateway cannot entirely replace a reverse proxy. While an API Gateway *is* a type of reverse proxy, a general reverse proxy handles basic traffic routing and load balancing, whereas an API Gateway adds the crucial layer of API management and business logic enforcement.

**AA4**
The **Saga pattern** is a sequence of local transactions where each transaction updates the database and publishes an event to trigger the next step. If any step fails, the Saga executes compensating transactions to undo the preceding changes, maintaining data consistency across services.
*   **Choreography-based:** Services communicate by producing and consuming events without a central coordinator. Each service knows what to do upon receiving a specific event. Appropriate when the workflow is simple, decentralized, and loosely coupled.
*   **Orchestration-based:** A dedicated service (the orchestrator) manages the workflow, sending commands to participant services and handling the sequence and failure logic. Appropriate when the workflow is complex, long-running, or requires centralized visibility and control.

**AA5**
**CQRS (Command Query Responsibility Segregation)** separates the model used for updating data (Commands) from the model used for reading data (Queries). Commands modify state; Queries retrieve state.
It is often paired with **Event Sourcing (ES)** because ES stores the state of the system as a sequence of immutable events. The Command side writes events to the event store, and the Query side subscribes to these events to build optimized, denormalized read models (projections).
This combination solves the problem of needing highly optimized read paths without compromising transactional integrity on the write path. A traditional CRUD model forces the read and write models to share the same schema, leading to complex joins and performance bottlenecks when read patterns diverge significantly from write patterns.

**AA6**
The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service).
The three states are:
1. **Closed:** Requests pass through normally. If failures exceed a threshold, the breaker trips to Open.
2. **Open:** Requests are immediately rejected without attempting the call, failing fast, allowing the downstream service time to recover.
3. **Half-Open:** After a timeout, a limited number of test requests are allowed through. If they succeed, the breaker moves to Closed; if they fail, it returns to Open.
It differs from simple retry with backoff because retry attempts continue hammering a failing service, potentially exacerbating the failure (cascading failure). You use both together: the Circuit Breaker prevents the initial flood of requests, and the retry mechanism handles transient, expected failures within the Closed state.

**AA8**
**Strong Consistency** guarantees that any read operation returns the result of the most recent successful write operation across all replicas immediately. **Eventual Consistency** guarantees that if no new updates are made to a data item, eventually all reads will return the last updated value, but there is a period of inconsistency.
To prevent overselling inventory (a critical business constraint), you must enforce **Strong Consistency** for the inventory count.
*   **Data Store:** A strongly consistent, transactional database (e.g., PostgreSQL with strong ACID guarantees, or a distributed SQL database like CockroachDB).
*   **Patterns:** Use pessimistic locking or atomic database transactions during the checkout/reservation process. When scaling, use a dedicated, highly consistent inventory service that acts as the single source of truth for stock levels, potentially leveraging distributed locks or consensus algorithms (like Raft/Paxos) if the service itself is distributed.

**AA9**
A **sidecar proxy** is a small, dedicated proxy container deployed alongside every service instance in a pod. It handles all network traffic (inbound and outbound) for the main application container.
In an Istio deployment, **Envoy** is the high-performance L7 proxy deployed as the sidecar. It intercepts all network traffic, applying policies defined by Istio.
*   **Data Plane:** The set of proxies (Envoy sidecars) that handles the actual traffic routing, encryption, and policy enforcement.
*   **Control Plane:** The management layer (e.g., Istiod) that configures and manages the data plane proxies, pushing routing rules, security policies, and telemetry configurations to them.
mTLS between sidecars solves the problem of ensuring **mutual authentication and encryption** between services *at the network level*, regardless of the application code. Application-level TLS requires developers to implement certificate management and handshake logic in every service, whereas the sidecar handles this transparently, enforcing zero-trust networking automatically.

**AA10**
The **Strangler Fig pattern** involves gradually replacing specific functionalities of a legacy system by building new services around it. New functionality is built as microservices, and traffic is incrementally rerouted from the monolith to these new services until the monolith can be "strangled" and retired.
**Migration Strategy:**
1. **Identify Seams:** Identify a low-risk, bounded context in the monolith (e.g., User Profile Management).
2. **Build New Service:** Implement the User Profile service in .NET 8, exposing a clean API.
3. **Implement Facade/Proxy:** Place an API Gateway in front of the monolith.
4. **Reroute Traffic:** Configure the Gateway to route all `/api/user-profile/*` requests to the new .NET 8 service. All other requests continue to the monolith.
5. **Data Synchronization:** Implement a mechanism (e.g., Change Data Capture or event publishing from the monolith) to keep the new service's data store synchronized with the monolith's database during the transition.
6. **Iterate:** Repeat the process for the next bounded context until the monolith is empty.

**AA11**
The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable, and resilient software-as-a-service applications.
Six factors and their importance:
1. **Codebase:** One codebase tracked in revision control, many deploys. (Ensures consistency across environments.)
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures reproducible builds.)
3. **Config:** Store configuration in the environment. (Decouples code from environment-specific settings like database credentials.)
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. (Allows easy swapping of data stores.)
5. **Build, Release, Run:** Strictly separate build, deployment, and execution stages. (Enables CI/CD pipelines.)
6. **Processes:** Execute the application as one or more stateless processes. (Crucial for horizontal scaling; state must be externalized to backing services.)

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Services only know the event contract) | Tight (Caller must know the callee's interface/location) |
| **Scalability** | High (Consumers can scale independently based on topic load) | Moderate (Scaling requires load balancing and service discovery) |
| **Debugging Complexity** | High (Tracing flow across asynchronous boundaries is difficult) | Low (Synchronous stack trace is straightforward) |
| **Ordering Guarantees** | Guaranteed within a partition/topic. | Guaranteed by the request/response sequence. |
| **Failure Handling** | Durable; messages persist until consumed; consumers can retry. | Immediate failure response; requires client-side retry logic. |

**Choice:**
*   **Choose Event-Driven:** When high decoupling, high throughput, and asynchronous processing are paramount (e.g., order processing, logging, notifications).
*   **Choose Request-Driven:** When an immediate, synchronous response is required to complete a user workflow (e.g., user login, fetching a specific resource).

**AA13**
A **Load Balancer** distributes incoming network traffic across a group of backend servers to ensure no single server is overwhelmed, thereby maximizing throughput and availability.
*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It routes traffic based on IP addresses and port numbers. It is fast because it does not inspect the content of the packet.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (headers, URL path, cookies) to make routing decisions.
**Use Case for Layer 7:** Routing traffic to different microservices based on the URL path (e.g., routing `/api/v1/users` to the User Service and `/api/v1/orders` to the Order Service).

**AA14**
A **Message Queue** (e.g., RabbitMQ) is a point-to-point or publish/subscribe system designed for reliable message delivery. Messages are typically consumed and then *removed* from the queue. It focuses on task distribution and guaranteed delivery.
A **Log-Based Message Broker** (e.g., Kafka) is a distributed commit log. Messages are appended to topics and are *retained* for a configurable period. Consumers read from the log at their own pace and can replay past events.
**When to pick one over the other:**
*   **Message Queue:** When you need a task to be processed exactly once and then discarded (e.g., sending a single email notification).
*   **Log-Based Broker:** When you need event sourcing, stream processing, or the ability for multiple, independent services to read the same historical stream of events (e.g., tracking all state changes in a system).

**AA15**
A **Container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and settings. It shares the host OS kernel with other containers.
A **Virtual Machine (VM)** virtualizes the entire hardware stack, including the CPU, memory, disk, and network interface, running its own full guest OS on top of a hypervisor.
Containers are popular because they offer high density, fast startup times, and portability. They abstract the application from the underlying OS, ensuring the environment is consistent from development to production, while consuming far fewer resources than a full VM.

**AA16**
**Stateless services** do not retain any session-specific data between requests. Every request from a client to the service must contain all the necessary information for the service to fulfill it.
**Stateful services** retain data across multiple requests (e.g., session state, in-memory caches).
Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance, as no instance holds unique session data that must be maintained.
*   **Stateless Example:** A REST API endpoint that processes a calculation based on input parameters.
*   **Stateful Example:** A Redis cache server or a traditional relational database instance.

**AA17**
An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using object-oriented paradigms (objects, classes) instead of writing raw SQL queries. It maps database tables to classes and rows to objects.
*   **Popular ORMs:** Entity Framework (.NET/C#), Hibernate (Java).
Trade-offs:
*   **Pros (ORM):** Increased developer productivity, type safety, abstraction from specific SQL dialects, easier refactoring.
*   **Cons (ORM):** Performance overhead due to object-relational impedance mismatch, potential for generating inefficient SQL (N+1 query problems), and difficulty handling highly complex, vendor-specific SQL features.

**AA18**
The **Bulkhead pattern** isolates components of an application so that the failure or resource exhaustion in one component does not cascade and bring down the entire system. It partitions resources (like thread pools, connection pools, or memory) into isolated compartments.
It relates to resource isolation by ensuring that if one service dependency becomes slow or fails, it only consumes the resources allocated to its specific bulkhead, leaving resources available for other, healthy services.
**Implementation Example:** If Service A calls Service B and Service C, you would implement two separate, limited thread pools (bulkheads). If Service B starts timing out and consuming all threads in its dedicated pool, Service C's pool remains unaffected and can continue processing requests successfully.

**AA19**
| Feature | Operational Transformation (OT) | Conflict-free Replicated Data Types (CRDTs) |
| :--- | :--- | :--- |
| **Consistency** | Strong (Requires centralized coordination/server authority) | Eventual (Converges mathematically without coordination) |
| **Latency** | Higher (Requires round-trip communication for transformation) | Lower (Operations can be applied locally immediately) |
| **Complexity** | High (Complex transformation algorithms, difficult to implement correctly) | Medium (Mathematical rigor, but simpler application logic) |
| **Offline Support** | Poor (Requires server synchronization to resolve conflicts) | Excellent (Operations are commutative and associative) |

I would choose **CRDTs**. For a system that *must* support offline editing, CRDTs are superior because they guarantee that operations applied locally while offline can be merged deterministically with operations from other clients once connectivity is restored, without needing a central server to mediate the conflict resolution.

**AA20**
**Challenges in Polyglot Tracing:**
1. **Context Propagation:** Ensuring the unique trace ID and span ID are passed correctly across service boundaries, especially when languages or protocols change. Standards like **W3C Trace Context** or **B3** headers must be consistently injected and extracted by every service.
2. **Sampling:** Deciding which requests to trace. **Head-based sampling** decides whether to trace at the entry point (e.g., 1% of requests). **Tail-based sampling** waits until the entire trace is complete to decide whether to keep it, which is more accurate but requires buffering all traces.
3. **Storage/Querying:** Using specialized backends like **Jaeger** or **Tempo** to store trace spans and provide a UI for visualizing the request flow.
4. **Asynchronous Messaging:** Tracing continuity is broken when a request hands off to a message queue.
**Ensuring Trace Continuity with Kafka:** When a service publishes a message to Kafka, the trace context (Trace ID, Parent Span ID) must be injected into the message headers. The consuming service must then extract these headers upon receipt and use the received Trace ID as the parent for its new span, thus linking the asynchronous work back to the original request.

**OP1**
A **Type 1 (Bare-Metal) Hypervisor** runs directly on the host hardware, managing the hardware resources and hosting the VMs. It offers near-native performance. *Examples: VMware ESXi, Microsoft Hyper-V.*
A **Type 2 (Hosted) Hypervisor** runs as an application *on top* of a conventional host operating system. It relies on the host OS for hardware access. *Examples: VMware Workstation, Oracle VirtualBox.*

**OP2**
**SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. The server sees the storage as a local disk volume. *Protocols: Fibre Channel (FC), iSCSI.* Used for high-performance, mission-critical applications like databases.
**NAS (Network Attached Storage):** A file-level storage device accessible over the standard network. The server accesses files via a network share. *Protocols: NFS, SMB/CIFS.* Used for file sharing, backups, and general data storage.

**OP3**
**3-Tier Architecture:**
1. **Access Layer:** Connects end-user devices (switches, access points).
2. **Distribution Layer:** Aggregates traffic from the Access layer, enforces policy, and provides routing boundaries.
3. **Core Layer:** High-speed backbone responsible only for fast packet switching between distribution blocks.
**Leaf-Spine Preference:** Leaf-Spine (Clos network) replaces the traditional hierarchy. It creates a non-blocking, predictable, low-latency fabric. It solves the **bottleneck problem** of the 3-tier model, where traffic between two servers in the same access block must traverse up to the distribution layer and back down, introducing latency and limiting east-west bandwidth.

**OP4**
**Architecture:**
*   **Node Count:** Minimum 3 nodes for quorum.
*   **Quorum:** Achieved via Corosync/Pacemaker, ensuring a majority of nodes must agree on the cluster state.
*   **Fencing (STONITH):** Essential mechanism to forcibly power off a failed node to prevent split-brain scenarios.
*   **Shared Storage:** Ceph is ideal for modern, software-defined clustering.
*   **Failure Scenario:** If one node fails, the remaining nodes maintain quorum. The cluster manager detects the failure, marks the node as down, and automatically migrates the virtual machines (VMs) or services running on the failed node to the remaining healthy nodes, using the shared Ceph storage.

**OP5**
**VLAN Trunking:** A mechanism that allows multiple VLANs to be carried over a single physical link (trunk port).
**802.1Q Tagging:** This standard adds a 4-byte tag header to the Ethernet frame, specifying which VLAN the frame belongs to. This tag allows switches to correctly route the frame to the intended VLAN.
**Linux Configuration:** You configure the physical NIC to be in a "trunking" mode (or use bonding/teaming). Then, you create separate virtual interfaces (e.g., `eth0.10`, `eth0.20`, `eth0.30`) for each VLAN ID (10, 20, 30). You assign the IP address and network configuration to these virtual interfaces, not the physical interface.

**OP6**
*   **RAID 1:** Mirroring. Duplicates data across two drives. High redundancy, 50% capacity loss.
*   **RAID 5:** Striping with distributed parity. Can survive one drive failure. Good balance of capacity/fault tolerance.
*   **RAID 6:** Striping with double distributed parity. Can survive two drive failures. Higher overhead than RAID 5, better fault tolerance.
*   **RAID 10:** Striping across mirrored pairs. Excellent performance and high fault tolerance (can lose multiple drives as long as they aren't in the same mirror set).
*   **RAID Z2 (ZFS):** Similar to RAID 6, using parity across multiple disks, offering high fault tolerance.
**Choice:** For a database server requiring high performance, capacity, and fault tolerance, **RAID 10** is usually the best choice. It provides excellent read/write performance due to striping and high redundancy because the failure of two drives is unlikely to occur in the same mirrored pair.

**OP7**
**Architecture Components:**
*   **Internal AD:** Serves as the primary identity source.
*   **Recursive Resolvers (Internal):** Servers within the internal network that handle DNS queries from clients. They forward external queries to the public DNS servers and handle internal queries locally.
*   **Authoritative Servers (Internal/External):** Servers holding the actual zone files. Internal servers are authoritative for internal domains; external servers are authoritative for public domains.
*   **Forwarders:** The internal resolvers forward external queries to trusted public DNS servers (e.g., Google DNS).
*   **Conditional Forwarding:** Used to direct queries for specific domains (e.g., `partner.com`) to a specific, dedicated DNS server, bypassing the general forwarders.
*   **Split-Horizon DNS:** Maintaining different records for the same hostname based on the client's location (e.g., internal IP vs. public IP).
*   **DNSSEC:** Applied to the external zone to cryptographically sign records, ensuring data integrity and preventing cache poisoning.
**Laptop Movement:** When a laptop moves from the office (on the internal network) to the VPN, the internal recursive resolvers must be configured to handle the VPN tunnel traffic correctly, ensuring that the laptop queries the internal DNS servers first, which then correctly resolve internal hostnames via the VPN path.

**OP8**
**PKI Chain of Trust:**
1. **Root CA:** The ultimate trust anchor. It is self-signed and kept offline (air-gapped) for maximum security. It signs the subordinate CA certificate.
2. **Subordinate/Issuing CA:** This CA is online and performs the day-to-day signing of end-entity certificates (servers, users). It is signed by the Root CA.
3. **End-Entity Certificate:** The certificate issued to the actual resource (e.g., a web server).
The chain is validated by checking the end-entity certificate against the Issuing CA certificate, and the Issuing CA certificate against the Root CA certificate.
**CRL vs OCSP:**
*   **CRL (Certificate Revocation List):** A list published periodically by the CA containing serial numbers of revoked certificates. Clients must download and check this list.
*   **OCSP (Online Certificate Status Protocol):** A real-time query service where the client asks the CA, "Is this specific certificate valid?"
**Consequences of Compromise:**
*   **Compromised Subordinate CA:** High impact. An attacker can issue fraudulent certificates for internal services, but the damage is contained because the Root CA remains secure and can revoke the subordinate CA's certificate.
*   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, an attacker can issue fraudulent certificates that are trusted by *every* system in the organization, completely undermining the entire PKI trust model.

It intelligently monitors multiple links (MPLS, broadband) and steers latency-sensitive traffic (VoIP) over the best available path, offering better reliability and lower latency than standard IPsec VPNs, while being significantly cheaper and more flexible than MPLS.

**OP10**
**iDRAC/iLO/IPMI:** These are hardware-level management interfaces built into servers that allow administrators to remotely monitor, manage, and control the server hardware (power cycling, viewing sensor data, accessing the console) independent of the operating system running on the server.
**Out-of-Band Management Criticality:** It is critical because if the OS or the primary network stack fails, you still need a way to access the server to diagnose the problem, reboot it, or repair it.
**Internet Exposure Risk:** If the IPMI interface is exposed to the internet, it becomes a massive security vulnerability. An attacker could gain full, low-level control over the physical server hardware, potentially bypassing OS security controls, installing malware, or causing denial of service.

**OP11**
*   **LVM (Logical Volume Manager):** A software layer that abstracts physical storage into flexible logical volumes. It is used for volume management, resizing, and snapshotting, but it operates at the block level.
*   **LVM-Thin:** An extension of LVM that allows for thin provisioning, meaning you can allocate more logical space than you physically have, and only consume physical space as data is written.
*   **ZFS:** A comprehensive file system and volume manager that integrates storage management, data integrity checks (checksumming), and volume management into one system.
**Use Cases:**
*   **LVM:** General volume resizing and abstraction on Linux.
*   **LVM-Thin:** Environments where storage efficiency is critical and you need to over-provision space.
*   **ZFS:** High-integrity environments (databases, archival) where data corruption must be prevented via checksumming.
**Snapshot Semantics:**
*   **LVM:** Snapshots are typically copy-on-write (CoW) or write-in-place, depending on the implementation, and are generally block-level.
*   **LVM-Thin:** Uses CoW.
*   **ZFS:** Uses CoW inherently. Snapshots are extremely fast and space-efficient because they only store the delta blocks that have changed since the snapshot was taken.

**OP12**
**DR Strategy (Site Failure):** A 3-node cluster cannot survive a complete site failure (which implies losing 3 nodes). To survive a site failure, you need a geographically dispersed cluster, typically requiring at least 5 nodes spread across two sites (e.g., 3 nodes in Site A, 2 nodes in Site B).
**Ceph CRUSH Rules:** CRUSH rules must be configured to understand the topology (Site A, Site B) and ensure that replicas are placed across different failure domains (i.e., replicas for the same object must reside in different sites).
**Monitor Placement:** Monitors must be placed in both sites to maintain quorum across the geographical distance.
**Network Latency:** High latency between sites severely impacts cluster performance and consensus algorithms.
**Split-Brain Problem:** This occurs when network partitioning causes two or more parts of the cluster to independently believe they are the sole surviving cluster, leading to conflicting writes.
**2-Site Ceph Issue:** A 2-site Ceph cluster is generally bad without a tiebreaker because if the link between the two sites fails, both sites lose quorum (they each have only 1 monitor), and the cluster halts writes entirely, leading to an outage.

**OP13**
**DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses, subnet masks, default gateways, and DNS server information to devices on a network.
**DORA Process:**
1. **Discover:** Client broadcasts a DHCP Discover message looking for a server.
2. **Offer:** Server responds with a DHCP Offer, proposing an IP address lease.
3. **Request:** Client broadcasts a DHCP Request, formally accepting the offered lease.
4. **Acknowledge:** Server sends a DHCP ACK, confirming the lease and providing lease duration.
**Server Unavailable:** If a Windows client's lease expires and the DHCP server is unavailable, the client will continue using its old IP address until the lease time expires or it attempts to renew. If renewal fails, the client will eventually attempt to re-discover a server. If no server is found, the client will likely fail to communicate on the network or revert to an APIPA (Automatic Private IP Addressing) address.

**OP14**
**Unmanaged Switch:** A simple, plug-and-play switch that operates purely at Layer 2 (MAC addresses). It forwards frames based on learned MAC addresses without any configuration options. It is suitable for small, simple networks.
**Managed Switch:** A switch that allows administrators to configure and control its behavior using a management interface (CLI/Web GUI).
**Enterprise Features:** Managed switches provide critical features like:
*   **VLAN Tagging/Trunking:** Segmenting broadcast domains.
*   **QoS (Quality of Service):** Prioritizing critical traffic (like VoIP).
*   **Port Mirroring:** Monitoring traffic on specific ports for troubleshooting.
*   **Security Features:** 802.1X authentication and port security.

**OP15**
**NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.
**Criticality:** Accurate time synchronization is vital for:
1. **Log Correlation:** Tracing events across distributed systems requires logs to be ordered chronologically.
2. **Security:** Kerberos authentication and certificate validation rely heavily on synchronized time.
3. **Clustering:** State synchronization and failover mechanisms (like Pacemaker) depend on consistent time stamps.
**Clock Drift Consequences:** If clocks drift, distributed transactions can fail due to timestamp mismatches, security tokens can be rejected as expired prematurely, and cluster failover logic can trigger incorrectly, leading to service instability or data corruption.

**OP16**
*   **Physical Server:** The actual, tangible hardware machine (CPU, RAM, NICs).
*   **Virtual Machine (VM):** A software emulation of a physical computer, running a full guest OS, managed by a hypervisor. It virtualizes the hardware.
*   **Container:** A lightweight, isolated process environment that packages an application and its dependencies, sharing the host OS kernel. It virtualizes the OS layer, not the hardware.
**Bare Metal Use Case:** You run a workload directly on bare metal when absolute, maximum performance is required, or when the workload has extremely low overhead requirements (e.g., high-frequency trading, specialized hardware drivers, or when the hypervisor/container runtime itself introduces unacceptable latency).

**OP17**
**UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power to bridge the gap between a utility power failure and the activation of a generator. It protects against short outages and power spikes.
**Generator:** Provides long-term, sustained power during extended utility outages.
**Why both:** The UPS handles the immediate transition and short-term stability, ensuring servers don't crash during the switchover. The generator provides the necessary power supply for the duration of the outage.
**ATS (Automatic Transfer Switch):** A device that automatically detects the loss of utility power and switches the electrical load from the utility source to the generator source, and vice versa, ensuring seamless power delivery.

**OP18**
**Active-Passive Clustering:** One server (Active) handles all traffic and processing; the second server (Passive/Standby) remains idle, constantly monitoring the Active node. If the Active node fails, the Passive node takes over the workload.
**Active-Active Clustering:** Both servers actively handle traffic simultaneously. Load balancing distributes requests across both nodes, increasing overall capacity.
**HA Implementation (Pacemaker/Corosync):**
1. **Corosync:** Provides the cluster communication and membership service, ensuring all nodes agree on the cluster state.
2. **Pacemaker:** The resource manager that monitors the health of the PostgreSQL service.
3. **Fencing (STONITH):** Crucial. If the cluster suspects a node is hung (not failed), STONITH (Shoot The Other Node In The Head) uses an external mechanism (e.g., IPMI, power controller) to forcibly power off the suspected node, preventing split-brain.
4. **Virtual IPs (VIP):** A single, floating IP address is assigned to the cluster resource. Pacemaker ensures this VIP is only active on the node currently running the PostgreSQL service.
**Failover Behavior:** If the Active node fails, Corosync notifies Pacemaker. Pacemaker executes the failover script, ensuring STONITH has isolated the failed node, then moves the VIP and starts the PostgreSQL service on the Passive node.

**OP19**
**3-2-1 Rule:** Maintain at least **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.
**RPO (Recovery Point Objective):** The maximum acceptable amount of data loss (e.g., 1 hour). Dictates backup frequency.
**RTO (Recovery Time Objective):** The maximum acceptable downtime after a disaster. Dictates recovery speed and infrastructure readiness.
**Backup Types:**
*   **Full:** Copies all selected data. Slowest, largest backup.
*   **Incremental:** Copies only data that has changed since the *last* backup of any type. Fastest, smallest backup.
*   **Differential:** Copies all data that has changed since the *last full* backup. Faster than full, but grows larger over time.
**Deduplication:** Reduces storage footprint by identifying and eliminating redundant copies of data blocks.
**Offsite Storage:** Tape (air-gapped, slow recovery), Disk (faster recovery, requires remote site), Cloud (flexible, scalable).
**Immutable Backups:** Backups that cannot be modified, deleted, or encrypted by ransomware or malicious actors, providing a clean recovery point.
**Backup vs. DR:** **Backup** is the process of creating copies of data. **Disaster Recovery (DR)** is the comprehensive plan and process of restoring business operations and data availability after a disruptive event.
**Testing Restores:** Must be performed regularly (at least quarterly) in a non-production environment to validate RTO/RPO targets and ensure the backup chain is valid.

**OP20**
**802.1X (Port-Based Network Access Control):** A standard that controls which devices can connect to a wired network port.
*   **Supplicant:** The client device (e.g., laptop) requesting access.
*   **Authenticator:** The network switch/port that enforces the policy and mediates the connection.
*   **Authentication Server:** The central server (usually RADIUS) that verifies the supplicant's credentials.
**EAP Methods:**
*   **EAP-TLS:** Uses digital certificates for mutual authentication (client proves identity to server, server proves identity to client). Highly secure.
*   **PEAP:** Encapsulates authentication within a TLS tunnel, often using username/password credentials inside the tunnel. Easier to deploy than EAP-TLS.
**RADIUS:** The protocol used by the Authenticator to communicate authentication requests and responses to the Authentication Server.
**Dynamic VLAN Assignment:** The RADIUS server can instruct the switch (Authenticator) to place the authenticated user into a specific VLAN based on their role (e.g., "Guest" VLAN vs. "Developer" VLAN).
**Failed Authentication:** If a device fails authentication, the switch port is placed into an unauthorized state (often a restricted VLAN or completely shut down) until valid credentials are provided.
**MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., printers, IP phones). The switch sends the device's MAC address to the RADIUS server, which checks the MAC against a pre-approved list and grants access based on that identity.
