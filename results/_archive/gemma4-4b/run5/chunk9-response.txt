**SC1-A**
The pods are failing because the Kubernetes cluster upgrade enforced the **Restricted Pod Security Standard (PSS)** at the namespace level. The PSS dictates strict security constraints. The failing pods have `securityContext.runAsNonRoot: true`, which mandates that the process must not run as the root user (UID 0). However, the new base image (`cgr.dev/chainguard/static:latest`) defaults its `USER` directive to `root` within the Dockerfile. When the container starts, the process attempts to run as root, violating the `runAsNonRoot: true` constraint enforced by the Restricted PSS. The change from Baseline (which was more permissive) to Restricted enforcement is the direct cause, as Restricted explicitly forbids running as root unless explicitly overridden with a non-root UID.

**SC1-B**

kubectl get pods --all-namespaces -o json | jq -r '.items[] | select(.status.phase == "CrashLoopBackOff") | "\(.metadata.namespace) \(.metadata.name) \(.spec.securityContext)"'

**SC1-C**
**Immediate Fix (Outage Mitigation):**
1.  **Image-Level Fix:** Rebuild the Go and Python services, explicitly setting the `USER` directive in their Dockerfiles to a non-root user (e.g., `USER appuser`) and ensuring that user has the necessary file permissions.
2.  **Kubernetes Manifest Change:** For immediate rollback, temporarily patch the failing deployments to remove `securityContext.runAsNonRoot: true` (if the image fix is delayed) or, preferably, explicitly define a non-root `runAsUser` UID in the manifest to match the image's intended user.
3.  **CI Pipeline Gate:** Implement a static analysis step (e.g., using Trivy or Hadolint) in the CI pipeline that scans the Dockerfile for `USER root` directives when `runAsNonRoot: true` is present in the target Kubernetes manifest, failing the build if the mismatch is detected.

**Zero-Downtime Rollout:** Use a rolling update strategy (`kubectl rollout restart deployment/<name>`) after applying the manifest changes. Kubernetes will gradually replace old pods with new, compliant pods, maintaining service availability.

**SC2-A**
The stale data issue arises because the promotion of the read replica to primary likely occurred while the replication was **asynchronous**. Asynchronous replication means the primary (us-east-1) commits transactions locally and sends Write-Ahead Log (WAL) records to the replica (eu-west-1) without waiting for confirmation. If the outage occurred before the last few transactions were shipped, those transactions are lost.

**Replication Lag Implication:** When the replica is promoted, it becomes the new primary, but it only contains the data up to the last successfully received WAL segment. Any transactions committed on the old primary after the last successful WAL shipment are permanently lost, leading to stale reads.

**WAL Shipping:** PostgreSQL streaming replication ships WAL records over the network. In cross-region setups, this is inherently susceptible to network latency and transient failures. Asynchronous replication prioritizes low write latency on the primary by not blocking for remote acknowledgment.

**Data Loss Scenarios:** Data loss occurs if the primary fails before the WAL records are flushed and applied to the replica.

**Quantifying Data Loss:** Check the `pg_stat_replication` view on the *old* primary (if accessible) or examine the WAL archive logs/logs on the *new* primary to determine the last applied WAL segment LSN (Log Sequence Number) and compare it to the LSN of the last committed transaction on the old primary.

**SC2-B**
The goal is to transition the promoted replica into the Terraform state without destroying the old resource.

1.  **Import the Promoted Replica:** Since the replica was promoted, it is now a standalone instance. You must import it using its new ARN/identifier.

If the old instance was referenced directly in other resources, those resources must be updated in the HCL to point to the new instance ID/ARN.

**SC2-C**
**Architecture Design:**
*   **Connection Management:** Use **RDS Proxy** in the primary region (us-east-1) and potentially in the DR region. RDS Proxy handles connection pooling, multiplexing, and automatic failover detection, significantly reducing the load on PgBouncer and mitigating connection exhaustion during failover events.
*   **DNS Failover:** Implement **Route53 Health Checks** targeting the application endpoints in both regions. Use weighted or latency-based routing, configured to shift 100% traffic to the DR region upon health check failure in the primary.
*   **Application Logic:** Implement **exponential backoff and jitter** retry logic in the application layer for transient database connection errors.
*   **RPO < 1 Second:** To achieve this, you must use **Synchronous Replication** or a service designed for near-zero RPO.

**Aurora Global Database Recommendation:** Yes, I strongly recommend **Aurora Global Database**. It is specifically designed for low-latency, cross-region disaster recovery. It uses dedicated infrastructure to maintain replication lag typically under one second, far surpassing standard RDS cross-region read replica capabilities, and simplifies the failover process significantly compared to manual promotion.

**SC3-C**
**Hardened CI/CD Pipeline Architecture:**
1.  **Base Image Pinning:** Never use tags (`node:20-slim`). Always pin base images by their immutable **digest** (e.g., `node@sha256:xyz...`). This ensures that the build always uses the exact, verified content.
2.  **Image Signing (Cosign/Sigstore):** After a successful build, the image must be cryptographically signed using Cosign. The signature (attestation) is stored alongside the image in ECR.
3.  **SBOM Generation:** Generate a Software Bill of Materials (SBOM) using tools like Syft or CycloneDX during the build. This lists all dependencies and their versions, providing transparency.
4.  **Admission Control Enforcement:** Deploy an admission controller (e.g., **Kyverno** or **OPA Gatekeeper**) in the Kubernetes cluster. This controller must be configured to:
    *   Reject any Pod creation request unless the image reference is accompanied by a valid signature verified against a trusted public key (Sigstore verification).
    *   Enforce that the image digest matches a known-good digest list.
5.  **Notary v2:** Notary v2 (or its modern implementation via Sigstore) provides the framework for signing and verifying artifacts. It ensures that the image pushed to ECR is the exact artifact that passed all security checks in CI, preventing runtime substitution or tampering.

**SC4-C**
**Phased Migration Plan (Strangler Fig Pattern):**

**Phase 1: Data and File Migration (Shadowing)**
*   **What Moves:** File uploads (`/data/uploads`) and session state (if externalized).
*   **Mechanism:** Deploy the monolith in Kubernetes, but configure it to write files to the new NFS PV (using the PVC from SC4-B). The F5 load balancer continues routing 100% of traffic to the legacy servers. The K8s deployment runs in "shadow mode," processing requests but not serving the primary traffic.
*   **Cutover:** None yet. Validation only.
*   **Rollback:** If K8s pods fail, traffic remains 100% on F5.

**Phase 2: Service Strangling (Traffic Splitting)**
*   **What Moves:** Non-critical API endpoints (e.g., product catalog lookup, user profile viewing).
*   **Mechanism:** Introduce an **Ingress Controller** (e.g., NGINX or Istio Gateway) in front of the K8s cluster. Use the F5 BIG-IP to route a small percentage of traffic (e.g., 5%) to the new K8s Ingress endpoint. The monolith in K8s handles these specific endpoints, while the legacy monolith handles the rest.
*   **MQ Handling:** The MQ Adapter microservice (from SC4-A) is deployed in K8s, allowing the new services to communicate with the mainframe via the adapter, while the legacy monolith continues using its direct MQ connection.
*   **Cutover:** Gradually increase traffic split (5% $\rightarrow$ 25% $\rightarrow$ 50%).
*   **Rollback:** If error rates spike, immediately revert the F5 routing rule to 100% legacy.

**Phase 3: Core Migration and Decommissioning**
*   **What Moves:** Core transactional endpoints (checkout, order placement) and the database connection.
*   **Mechanism:** Once confidence is high, shift 100% of traffic to the K8s Ingress. The final step is migrating the Oracle DB to a cloud-native, managed service (e.g., RDS). The legacy monolith is then decommissioned.
*   **Cutover:** Final DNS/Load Balancer switch.
*   **Rollback:** If the new DB fails, the K8s application can be quickly reconfigured (via ConfigMap/EnvVar change) to point back to the legacy Oracle endpoint, while the F5 remains active as a warm standby.

**Go/No-Go Metrics:**
*   **Phase 1:** Error rate (0%), Latency (P99 within 10% of baseline), File integrity checks.
*   **Phase 2:** Error rate (0%), Latency (P99 within 10% of baseline), Resource utilization (CPU/Memory stable).
*   **Phase 3:** Business transaction success rate (100%), Latency (P99 within 5% of baseline).

**SC5-A**
**Systematic Debugging Approach:**
1.  **Istio/Envoy Metrics:** Examine the `istio_request_duration_milliseconds` metric, specifically filtering for the `checkout-service` $\rightarrow$ `inventory-service` path. Look at the `proxy_upstream_rq_time` vs. `proxy_rq_time`.
    *   If `proxy_upstream_rq_time` is high, the latency is in the `inventory-service` application or its dependencies (DB).
    *   If `proxy_rq_time` is high but `proxy_upstream_rq_time` is low, the latency is in the sidecar proxy (Envoy) itself (e.g., queueing, resource contention).
2.  **Kubernetes Metrics:** Check the resource utilization (CPU throttling, memory pressure) of the `inventory-service` pods during the spike. Even if average usage is low, CPU throttling can cause massive latency spikes.
3.  **Application Logs:** Review logs from `inventory-service` during the spike for database connection errors, lock waits, or long-running query logs.
4.  **Distributed Tracing (Jaeger/Zipkin):** Trace a request path during the spike. The trace visualization will clearly show the time spent in the network hop, the time spent in the sidecar proxy, and the time spent executing code within the `inventory-service`. This pinpoints the exact function call causing the delay.

**Envoy Metrics for Distinction:**
*   **Proxy-level Queueing:** Look at metrics like `istio_request_queue_depth` or `envoy_server_rq_queue_utilization`. High values indicate the proxy is waiting for resources or upstream connections.
*   **Upstream Service Latency:** Look at `istio_request_duration_milliseconds` aggregated by the upstream service name. A high value here confirms the service is slow, not the network hop.

**PostgreSQL Lock Diagnostic Query:**
```sql
SELECT
    a.pid AS blocking_pid,
    a.usename AS blocking_user,
    a.query AS blocking_query,
    pg_blocking_pids(a.pid) AS blocked_pids,
    b.pid AS waiting_pid,
    b.usename AS waiting_user,
    b.query AS waiting_query,
    pg_locks.mode AS lock_mode,
    pg_locks.relation::regclass AS locked_table
FROM
    pg_stat_activity a
JOIN
    pg_locks ON a.pid = pg_locks.pid AND pg_locks.granted = true
JOIN
    pg_stat_activity b ON b.pid = ANY(pg_blocking_pids(a.pid))
JOIN
    pg_locks ON pg_locks.pid = b.pid AND pg_locks.granted = false
WHERE
    pg_locks.granted = true;
```

**SC5-C**
**Architectural Solution:**
1.  **CQRS (Command Query Responsibility Segregation):** Separate the read path from the write/reconciliation path. The reconciliation job (write path) updates the master database, while the checkout service reads from a highly optimized, eventually consistent read replica or a dedicated materialized view optimized for fast reads.
2.  **Read Replica for Reconciliation:** Schedule the heavy reconciliation job to run against a dedicated, isolated read replica instance. This prevents the reconciliation queries from holding locks on the primary database used by the checkout service.
3.  **Bulkhead Isolation:** Implement connection pool isolation. Instead of one large pool, maintain separate pools for different service functions (e.g., one pool for high-priority checkout reads, another for low-priority background tasks). If the reconciliation job exhausts its dedicated pool, it will not starve the critical checkout pool.
4.  **CronJob Scheduling:** Adjust the CronJob to run during off-peak hours (e.g., 03:00 UTC) when traffic is minimal, rather than during the peak 14:00 UTC window.

**Kubernetes Resource Governance:**
*   **PodDisruptionBudgets (PDBs):** Define PDBs for the serving pods (`checkout-service`, etc.) to ensure that during voluntary disruptions (like node maintenance), a minimum number of replicas remain available, preventing service degradation.
*   **Resource Quotas:** Apply Resource Quotas to the namespace hosting the CronJob. This limits the total CPU/Memory the CronJob can consume, preventing it from monopolizing node resources and starving the serving pods.

**SC6-A**
**Identity and Access Layer Design:**
The core principle is to replace network location trust with cryptographically verifiable workload identity.

**Machine Identity Implementation:**
*   **SPIFFE/SPIRE:** This is the standard solution. SPIRE agents run on every host (VMware, AWS EC2, Azure VM). They attest the workload's identity (e.g., Kubernetes Service Account, AWS IAM Role, Azure Managed Identity) and issue a verifiable X.509 certificate (SVID) conforming to the SPIFFE standard.
*   **AWS IAM Roles:** Workloads running on EC2/EKS assume IAM roles. SPIRE can be configured to attest these roles, mapping the AWS identity to a SPIFFE ID.
*   **Azure Managed Identities:** Azure workloads use Managed Identities. SPIRE attests these identities, linking them to the Azure identity plane.
*   **On-Prem PKI:** The on-prem environment uses its existing PKI infrastructure, which can be integrated with SPIRE as an external authenticator to issue SVIDs for legacy workloads.

**Identity Federation:**
Federation is achieved by using a central trust anchor (the SPIRE Server).
1.  **Workload in AWS:** The AWS workload authenticates to the SPIRE Server using its IAM role credentials. SPIRE issues a certificate (SVID) tied to its SPIFFE ID (e.g., `spiffe://aws.corp/service/checkout`).
2.  **Service On-Prem:** The on-prem service (e.g., a microservice) is configured to trust the SPIRE Root CA. When the AWS workload calls the on-prem service, it presents its SVID. The on-prem service validates the certificate against the trusted CA, verifying the identity (`spiffe://aws.corp/service/checkout`) without needing shared secrets or IP knowledge.

**SC6-C**
| Option | Cost | Bandwidth | Encryption | Failover | Zero-Trust Fit | Routing Changes |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Direct Connect** | High (Port/Data Transfer) | Very High (Dedicated) | Physical/VPN Tunnel | High (Dedicated Link) | Excellent (Stable, predictable path) | Static routing via BGP to TGW. |

**Recommendation:** For a strict Zero-Trust mandate, **Tailscale/Netbird** is superior. It enforces identity-based access (like SPIFFE) at the application layer, making the underlying network topology irrelevant.

**Routing Architecture Changes:**
*   **Direct Connect:** Requires configuring BGP peering between the on-prem router and the AWS Direct Connect Gateway, advertising specific CIDR blocks into the TGW.
*   **ECMP VPN:** Requires configuring multiple VPN tunnels to the TGW, using BGP to advertise routes learned from each tunnel, allowing the TGW to load balance traffic across the tunnels.
*   **Tailscale/Netbird:** The routing architecture shifts from IP-based routing to **overlay routing**. The application nodes run the client, and the mesh handles the routing, effectively creating a virtual, encrypted network fabric over the existing internet/VPN connections.

**SC7-A**
**Drift Source Analysis:**
1.  **Manual `tofu apply` from Laptops:** This bypasses the centralized CI/CD process and the state locking mechanism. The engineer applies changes directly to the remote infrastructure, updating the S3 state file without the pipeline's oversight. This is dangerous because the state file becomes inconsistent with the intended Git definition, leading to unpredictable future deployments.
2.  **Diverged Helm Values Files:** If values files are manually edited outside of Git, the Git repository no longer represents the true desired state of the cluster. Future automated deployments will overwrite these manual changes, or the application will run in an unknown configuration state.
3.  **Direct `kubectl edit` on ConfigMaps:** This is the most dangerous form of drift. It modifies the live cluster state directly. Since the CI/CD pipeline only manages the *desired* state in Git, the next `tofu apply` or Helm upgrade will detect this manual change and potentially revert it, or worse, fail if the change is incompatible with the IaC definition.

**State Locking Without Locking:** If two engineers run `tofu apply` simultaneously, they both read the same state file. Both calculate their plan based on the same initial state. The first one succeeds and writes the new state. The second one then applies its changes against the *old* state, leading to a **race condition**. The second apply will likely fail with a conflict error, or worse, overwrite the first engineer's changes, resulting in data loss or infrastructure corruption.

**SC8-C**
**Redesigned Observability Architecture:**
1.  **Metrics Backend (Mimir/VictoriaMetrics):** Replace Prometheus with **Mimir** (or VictoriaMetrics). Mimir is designed for massive scale, offering horizontal scalability, multi-tenancy, and decoupled storage. It handles high cardinality much better by allowing intelligent sampling and aggregation at the ingestion layer.
2.  **Loki Deployment (Microservices Mode):** Deploy Loki in microservices mode. Instead of one large ingester, deploy smaller, dedicated ingester/querier pods per team or service group. This isolates failure domains and allows teams to manage their own ingestion quotas.
3.  **Tempo Backend:** Switch Tempo to use a dedicated, highly available, S3-backed storage backend (e.g., using Thanos/Mimir's storage layer). This decouples trace storage from the query service, allowing for petabyte-scale, long-term retention without impacting query performance.
4.  **Governance Model (Cardinality Limits):**
    *   **Recording Rules:** Implement aggressive recording rules in Mimir to pre-aggregate high-volume, high-cardinality metrics (e.g., aggregate per minute instead of per second).
    *   **Relabeling Configs:** Use Mimir's ingestion pipeline to enforce strict relabeling rules, dropping or summarizing metrics that exceed predefined cardinality thresholds per namespace/team.

**Chargeback Implementation:**
Implement a **Telemetry Quota Service**. This service monitors the ingestion rate (series count, data volume) for each team's namespace. When a team exceeds its allocated quota, the service triggers an alert and, if configured, applies a throttling rule (e.g., dropping non-essential metrics) via the Mimir ingestion pipeline. The cost is calculated based on the volume of data ingested above the baseline quota, which is then mapped to the team's operational budget.

**SC10-A**
**Multi-Cluster Architecture Comparison:**

| Feature | Active-Passive (Velero) | Active-Active (Service Mesh) |
| :--- | :--- | :--- |
| **RPO/RTO Feasibility** | RPO $\approx$ Backup Frequency (Minutes/Hours). RTO $\approx$ Restore Time (Hours). | RPO $\approx$ Replication Lag (Seconds). RTO $\approx$ DNS TTL/Service Mesh Failover Time (Seconds). |
| **12ms Latency Impact** | Minimal impact on backup/restore process itself, but application writes must be synchronous to the primary. | Minimal impact, as the mesh handles routing and health checks across the low-latency link. |
| **200TB MinIO** | Requires asynchronous replication (e.g., MinIO replication features) followed by a large restore operation during failover. | Requires continuous, synchronous/asynchronous replication across sites. |
| **Stateful Component Replication** | **PostgreSQL:** Patroni/Streaming Replication (Synchronous). **Redis:** Sentinel/Cluster Replication. **RabbitMQ:** Mirroring/Federation. **MinIO:** Cross-region replication. | **PostgreSQL:** Patroni/Streaming Replication (Synchronous). **Redis:** Cluster Replication. **RabbitMQ:** Mirroring/Federation. **MinIO:** Cross-region replication. |

**Conclusion:** To meet RPO $\le 15$ minutes and RTO $\le 1$ hour, **Active-Active with a Service Mesh** is the superior design. Active-Passive restoration of 200TB of data and complex stateful services within 1 hour is extremely risky. Active-Active ensures continuous data synchronization and near-instantaneous traffic redirection.

**SC10-C**
**Automated Failover Orchestration Sequence:**

1.  **Failure Detection:**
    *   **Monitoring:** Prometheus/Alertmanager monitors the health of the Chicago primary (e.g., connection latency, replication lag, Patroni status).
    *   **Site Down Definition:** A site is considered "down" if the primary fails to respond to health checks (e.g., 3 consecutive failed pings/API calls) *and* the replication lag exceeds a critical threshold (e.g., 5 minutes).
2.  **Patroni Promotion:** Alertmanager triggers the Patroni cluster (via an external script/operator) to initiate a failover. Patroni detects the primary failure via etcd and automatically promotes the Dallas standby to primary.
3.  **DNS Failover (GSLB):** The GSLB (Global Server Load Balancer) health checks detect the Chicago site failure. The GSLB automatically updates the DNS record (e.g., `db.insurance.com`) to point 100% of traffic to the Dallas endpoint.
4.  **Stateful Component Failover:**
    *   **Redis Sentinel:** Sentinel detects the primary failure and promotes the Dallas replica.
    *   **RabbitMQ:** The cluster configuration is updated (via Ansible/Operator) to point consumers to the new primary cluster in Dallas, leveraging queue mirroring.
    *   **MinIO:** The application layer is configured to switch its write endpoint to the Dallas MinIO cluster, which has been continuously replicating data from Chicago.
5.  **OpenTofu State Update:** A final, automated step runs a specialized script that uses the AWS/Cloud provider API to update the resource references in the Terraform state file, reflecting the new primary region/endpoint.

**Split-Brain Handling:**
Split-brain occurs if both sites believe they are the primary. Patroni prevents this by using **etcd (DCS)**. Only the node that successfully acquires the lock in etcd can be elected primary. If network partitioning occurs, the minority side loses the lock and remains a standby, preventing divergent writes.

**Failback Procedure:**
1.  **Chicago Recovery:** Once Chicago is stable, it is brought back online as a *new standby* in Dallas's cluster.
2.  **Re-synchronization:** The Dallas primary streams WAL records back to the recovered Chicago standby until it is fully caught up.
3.  **Planned Switchover:** A controlled, planned switchover is executed (not a failover). The Dallas primary initiates a graceful handover to Chicago, ensuring zero data loss, and the GSLB is updated to point traffic back to Chicago.
