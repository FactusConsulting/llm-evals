**Kubernetes Questions**

K1 — A Deployment manages stateless applications by providing declarative updates for Pods and ReplicaSets. It ensures a specified number of identical replicas are running. A StatefulSet manages stateful applications, providing stable, unique network identifiers and persistent storage for each replica, ensuring ordered deployment and scaling.

K2 — A ClusterIP Service exposes the Service internally within the cluster using a stable virtual IP (ClusterIP). When a pod targets this Service, the Service's associated `kube-proxy` (running on every node) intercepts the traffic. `kube-proxy` uses iptables or IPVS rules to load balance incoming traffic from the ClusterIP to one of the healthy backing Pod IPs.

K3 — **PersistentVolume (PV):** A cluster resource representing a piece of storage provisioned in the cluster (e.g., an AWS EBS volume). It is a cluster administrator resource. **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a namespace resource that requests a specific size and access mode from the cluster. **StorageClass:** A controller that defines "classes" of storage (e.g., fast SSD, slow HDD). It dictates how PVs are dynamically provisioned when a PVC requests storage. They relate because a PVC binds to a PV, and the StorageClass dictates how the PV is created dynamically.

K4 — 1. **Check Pod Events:** Use `kubectl describe pod <name>` to check the `Events` section for specific failure reasons (e.g., ImagePullBackOff, CrashLoopBackOff reason). 2. **Check Logs:** Use `kubectl logs <name>` to see the application's stdout/stderr output leading up to the crash. 3. **Check Resource Limits:** Verify the pod's resource requests/limits against the node's available capacity to rule out OOMKilled or CPU throttling. 4. **Check Image/Config:** Ensure the container image exists, is correct, and that any mounted ConfigMaps/Secrets are accessible and correctly formatted.

K5 — CoreDNS acts as the cluster's internal DNS service, translating service names (e.g., `my-service.my-namespace.svc.cluster.local`) and pod names into cluster IP addresses. If CoreDNS pods are down, DNS resolution fails entirely. Pods cannot resolve service names or other internal cluster resources, leading to connection timeouts and application failures within the cluster.

K6 — The scheduler uses a two-phase process: **Filtering** and **Scoring**.
1. **Filtering (Predicates):** The scheduler first filters out nodes that cannot possibly run the pod based on hard constraints (e.g., resource availability, node selector matching, volume attachment requirements).
2. **Scoring (Priorities):** For the remaining viable nodes, the scheduler scores them based on various priorities.
Specific factors considered include:
1. **Resource Utilization:** Preferring nodes that are less utilized to balance the load.
2. **Node Affinity/Anti-Affinity:** Adhering to user-defined rules to keep pods together or spread them out.
3. **Taints and Tolerations:** Ensuring the node has no taints that the pod does not tolerate.

K7 — **Scheduling:** Yes, the pod *will* be scheduled initially. Kubernetes scheduling primarily checks *requests* against available capacity. The node has 4GB total; 3.5GB is requested. The pod requests 256Mi. Total requested = 3.5GB + 0.256GB = 3.756GB. Since 3.756GB < 4GB, it fits. **Runtime Usage:** If it uses 600Mi, it will exceed its `limits.memory` (512Mi). The Kubelet on the node will enforce the limit, and the container runtime will terminate the pod, resulting in an `OOMKilled` status.

K8 — 1. **External LB:** The external load balancer (e.g., AWS ELB, GCP Load Balancer) receives external traffic and forwards it to the Ingress Controller node's NodePort or IP. 2. **Ingress Controller:** The NGINX controller receives the request, inspects the Ingress resource rules (host/path), and determines the target Service. 3. **Service:** The Ingress Controller forwards the request to the ClusterIP of the target Service. 4. **Endpoints:** The Service object maintains an Endpoints object, which lists the actual IP addresses of the healthy backing Pods. The Service uses this list for load balancing. 5. **kube-proxy/iptables:** `kube-proxy` on the node intercepts the traffic destined for the Service ClusterIP and uses iptables rules to randomly select one of the Pod IPs from the Endpoints object, forwarding the packet directly to the application Pod.

K9 — A NetworkPolicy defines rules about how groups of pods are allowed to communicate with each other and with external network endpoints. If no NetworkPolicy exists in a namespace, the default behavior is "allow all" ingress and egress traffic. When you apply a NetworkPolicy that selects certain pods, the default behavior changes to "deny all" ingress/egress for those selected pods, unless explicitly allowed by another policy.

K10 — **RollingUpdate:** Gradually replaces old versions with new ones by creating new pods and terminating old ones incrementally. This ensures zero downtime. **Recreate:** Terminates all existing pods before creating the new version. This results in downtime during the update process. You would choose Recreate only when the application cannot handle traffic during a transition period, or when the change requires a clean, complete restart (e.g., database schema migration that requires a full application restart).

K11 — A namespace is a mechanism to partition cluster resources across multiple virtual clusters within a single physical cluster. It provides scope for names, policies, and resource quotas. Default namespaces include `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

K12 — `kubectl describe pod <name>` provides a detailed status report, including: 1. **Events:** A chronological log of actions taken on the pod (e.g., scheduling, pulling image, starting container). 2. **Container Status Details:** Specific exit codes, restart counts, and detailed reasons for termination. 3. **Resource Requests/Limits:** A clear breakdown of the requested and limited resources for each container.

K13 — A ConfigMap is an API object used to store non-confidential configuration data in key-value pairs. A pod can consume it in two primary ways: 1. **As Environment Variables:** Injecting the key-value pairs directly into the container's environment. 2. **As Mounted Volumes:** Mounting the ConfigMap as a file system volume inside the container, allowing the application to read configuration files.

K14 — **ClusterIP:** Exposes the Service internally within the cluster using a stable virtual IP. Only reachable from within the cluster. **NodePort:** Exposes the Service on a specific port on *every* node in the cluster. This allows external access via `<NodeIP>:<NodePort>`. **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes external traffic to the Service's nodes.

K15 — A DaemonSet ensures that a copy of a specific pod runs on *every* (or a selected subset of) eligible nodes in the cluster. You use it when you need a service that must run locally on every node, such as a log collector (Fluentd), monitoring agent (Prometheus Node Exporter), or network plugin. A Deployment is used for stateless applications that need a specific, fixed number of replicas, regardless of the node count.

K16 — **Taints:** A property applied to a Node that repels (prevents) pods from being scheduled onto it unless the pod explicitly tolerates the taint. **Tolerations:** A property applied to a Pod that allows it to be scheduled onto a Node that has a matching taint. **Node Affinity:** A scheduling constraint that *attracts* or *repels* pods based on labels, but does not prevent scheduling outright. **Practical Use Cases:** Taint/Toleration: Isolating a GPU node for ML workloads. Node Affinity: Ensuring all database replicas are scheduled on nodes labeled `disk-type: ssd`.

K17 — A Kubernetes Operator is a method of packaging, deploying, and managing a complex application. It extends the Kubernetes API by embedding domain-specific knowledge (control loops) into a custom controller. Unlike a standard controller (which manages simple state transitions, e.g., "ensure 3 replicas exist"), an Operator understands the *operational lifecycle* of an application (e.g., "perform a rolling database upgrade, then run migrations, then verify health"). It solves the problem of managing complex, stateful, and human-driven operational tasks automatically.

K18 — Kubernetes uses **Raft** for consensus, which is a strong consistency model. Raft ensures that all nodes agree on the sequence of operations (the log). If the etcd quorum (majority, typically $N/2 + 1$) is lost, the cluster cannot achieve consensus, and writes will halt, effectively freezing the cluster state until quorum is restored. If 2 out of 3 nodes are permanently lost, the remaining 1 node cannot form a quorum (needs 2), and the cluster is permanently unavailable for writes until a new node is added and elected.

K19 — RBAC controls authorization within the cluster. **Role:** Defines a set of permissions (verbs like `get`, `list`, `create`) for resources within a specific namespace. **ClusterRole:** Defines a set of permissions across the entire cluster (cluster-wide resources). **RoleBinding:** Binds a Role to a specific user/group within a specific namespace. **ClusterRoleBinding:** Binds a ClusterRole to a specific user/group cluster-wide.
*Manifests for read-only access to pods/logs in `my-namespace`:*
```yaml
# 1. Define the permissions (Role)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
---
# 2. Bind the permissions to a user/group (RoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-reader-binding
  namespace: my-namespace
subjects:
- kind: User
  name: developer-user # Replace with actual user/group
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` specifies the number of DNS dots (periods) that the resolver should follow before assuming the domain name is fully qualified (FQDN). If `ndots` is set too low (e.g., 1), the resolver might incorrectly assume a short name like `my-service` is a fully qualified domain name (e.g., `my-service.cluster.local`) and perform unnecessary lookups for every internal service name, leading to excessive DNS query overhead. To fix this, you can use `dnsConfig` in the pod spec to explicitly set `ndots: 5` (or a value matching the cluster's domain structure), forcing the resolver to query the cluster DNS server only when the name matches the full domain structure.

**Development Questions**

D1 — **Git Merge:** Combines two branches by creating a new "merge commit" that has two parents. It preserves the history of both branches exactly as they were. **Git Rebase:** Rewrites history by taking the commits from one branch and reapplying them one-by-one onto the tip of another branch. It creates a linear, cleaner history. You should avoid rebasing commits that have already been pushed to a shared, public repository, as rewriting shared history causes significant synchronization problems for collaborators.

D2 — **TCP (Transmission Control Protocol):** Connection-oriented, reliable, ordered delivery. It uses a three-way handshake to establish a connection. Protocols: HTTP/HTTPS, FTP. **UDP (User Datagram Protocol):** Connectionless, unreliable, fast. It sends packets without establishing a formal connection. Protocols: DNS, VoIP.

D3 — A race condition occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data. **Example:** Two threads simultaneously read a bank account balance ($1000). Thread A calculates a withdrawal of $100 (New Balance = $900). Thread B calculates a withdrawal of $200 (New Balance = $800). If Thread A writes $900, and then Thread B writes $800, the final balance is $800, even though $300 was withdrawn, resulting in a lost update.

D4 — **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is fast. **Asymmetric Encryption:** Uses a pair of keys: a public key (shared widely for encryption) and a private key (kept secret for decryption) (e.g., RSA). It is computationally intensive. **TLS Usage:** TLS uses asymmetric encryption during the initial handshake to securely exchange a temporary, random symmetric session key. Once the key is exchanged, all subsequent bulk data transfer is encrypted using the much faster symmetric algorithm.

D5 — A container image layer is a read-only, immutable filesystem layer that stores the changes made during a specific instruction in the Dockerfile. Layer caching is crucial because Docker builds layers sequentially. If an instruction (and its preceding layers) has not changed since the last build, Docker reuses the cached layer, drastically speeding up the build process. Best practice dictates placing instructions that change infrequently (like installing OS packages) near the top, and volatile instructions (like copying source code) near the bottom to maximize cache hits.

D6 — 1. **Check Monitoring/Metrics:** Review APM/Prometheus dashboards for error rates, latency spikes, and resource saturation (CPU/Memory) on the API service. 2. **Check Logs:** Examine application logs for specific exceptions, database connection failures, or upstream service timeouts occurring around the 503 events. 3. **Check Dependencies:** Verify the health and latency of any downstream services (database, cache, microservices) the API relies on. 4. **Check Resource Limits:** Ensure the API container has sufficient CPU/Memory limits defined in Kubernetes to prevent throttling or OOMKilled events.

D7 — The **CAP Theorem** states that a distributed data store can only guarantee two out of three properties simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without failure), and **Partition Tolerance** (the system continues to operate despite network failures between nodes).
*   **CP (Consistency & Partition Tolerance):** Systems prioritize data correctness over uptime during a network split. Example: Traditional relational databases (e.g., PostgreSQL cluster) configured for strong consistency.
*   **AP (Availability & Partition Tolerance):** Systems prioritize responding to requests even if data might be temporarily stale. Example: Cassandra or DynamoDB, which allow writes to succeed even if replication to all nodes fails temporarily.

D8 — **Horizontal Scaling (Scaling Out):** Adding more instances (nodes or pods) of the application to distribute the load. This is preferred for handling massive traffic increases. **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) allocated to an existing instance.
Architectural patterns enabling horizontal scaling include: **Statelessness** (ensuring no session data is tied to a specific instance), **Load Balancing** (distributing traffic across many instances), and **Microservices** (breaking the application into smaller, independently scalable services).

D9 — An environment variable is a dynamic named value that can affect the way running processes behave on a computer. To set one that persists across shell sessions on Linux, you must add the export command (e.g., `export MY_VAR="value"`) to your shell's startup file, typically `~/.bashrc` or `~/.zshrc`, and then run `source ~/.bashrc`.

D10 — **JSON (JavaScript Object Notation):** A lightweight data-interchange format using key-value pairs and arrays. Advantage: Highly native to JavaScript environments, making parsing extremely fast. **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that uses indentation to denote structure. Advantage: Excellent readability, making it ideal for configuration files (like Kubernetes manifests).

D11 — A REST (Representational State Transfer) API is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources.
*   **GET:** Retrieves a representation of a resource (Read). Should be idempotent and safe (no side effects).
*   **POST:** Submits data to a specified resource, often creating a new resource (Create).
*   **PUT:** Replaces an entire existing resource at a known URI (Update/Replace). It is idempotent.
*   **DELETE:** Removes the specified resource (Delete).

D12 — Version pinning is the practice of explicitly locking down the exact version number of every dependency (library, package) used in a project (e.g., `library-x@1.2.3` instead of `library-x@^1.2.0`). It is crucial for reproducible builds because it guarantees that the build environment will always use the exact same code, preventing unexpected runtime failures caused by upstream library authors making breaking changes in minor or patch releases.

D13 — **Compiled Language:** Source code is translated directly into machine code (binary executable) by a compiler *before* execution. Examples: C++, Go. **Interpreted Language:** Source code is read and executed line-by-line at runtime by an interpreter. Examples: Python, JavaScript.

D14 — **Reverse Proxy:** Sits in front of one or more web servers and forwards client requests to them. It acts as an intermediary, hiding the backend server structure from the client. **Forward Proxy:** Sits in front of clients and acts as an intermediary to forward requests *on behalf of* the clients (often used for anonymity or caching).
*   **Nginx:** Common reverse proxy. Use Case: Serving static assets and load balancing traffic across multiple application servers.
*   **HAProxy:** Common reverse proxy. Use Case: High-performance TCP/HTTP load balancing, especially for complex routing rules.

D15 — A deadlock is a state in a system where two or more competing actions are each waiting for the other to finish, resulting in a permanent standstill. The four Coffman conditions required for a deadlock are:
1. **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2. **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3. **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily.
4. **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

D16 — **Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. The system prioritizes availability and partition tolerance over immediate consistency. Cassandra handles read-after-write consistency by using tunable consistency levels (e.g., QUORUM). If a write is acknowledged by $W$ replicas and a read requires $R$ replicas, setting $W + R > N$ (where $N$ is the replication factor) guarantees strong consistency for that specific read/write operation, effectively overcoming eventual consistency for that transaction.

D17 — **mTLS (Mutual TLS):** An extension of standard TLS where *both* the client and the server authenticate each other using digital certificates. In standard TLS, only the client verifies the server's identity. In mTLS, the server verifies the client's identity using a client certificate presented during the handshake. The full handshake involves: 1. Client Hello $\rightarrow$ Server Hello. 2. Server sends its certificate $\rightarrow$ Client verifies it. 3. Client sends its certificate $\rightarrow$ Server verifies it. 4. Both exchange and verify cryptographic keys. mTLS is commonly used in service meshes (like Istio) and secure microservice communication where strict identity verification between services is mandatory.

D18 — A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an array. **Collision Resolution:**
1. **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hash to that index.
2. **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing).
**Time Complexity:**
*   **Average Case (Good Hash Function):** Insertion, Lookup, Deletion are $O(1)$.
*   **Worst Case (All keys hash to the same bucket):** Insertion, Lookup, Deletion are $O(N)$ (equivalent to traversing a linked list).

D19 — The Circuit Breaker pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing microservice). It monitors calls and, upon detecting a threshold of failures, "trips" the circuit, immediately failing subsequent calls without attempting the network request.
*   **Closed:** Normal operation. Requests pass through. Failures are counted.
*   **Open:** After too many failures, the circuit opens. All subsequent requests fail immediately (fail-fast) without hitting the downstream service, allowing it time to recover.
*   **Half-Open:** After a timeout in the Open state, the circuit allows a small number of test requests through. If they succeed, the circuit closes; if they fail, it returns to Open.
This prevents cascade failures by stopping the client from overwhelming an already struggling service. It relates to exponential backoff by ensuring that when the circuit is Open, the client waits for an increasing period before attempting the Half-Open state.

D20 — **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the required resources (rows/records) immediately upon reading them, preventing any other transaction from modifying them until the current transaction commits or rolls back. (Example: `SELECT * FROM users WHERE id=1 FOR UPDATE`). Chosen when data integrity is paramount and contention is expected. **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read (often using version numbers or timestamps). If a conflict is detected, the transaction is rolled back and must be retried. Chosen when contention is low and locking overhead is undesirable.
