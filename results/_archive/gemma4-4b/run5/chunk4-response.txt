**G1**
A Go **array** has a fixed size defined at compile time (e.g., `[5]int`). A **slice** is a dynamically sized, flexible view into an underlying array. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array, copies the existing elements and the new element(s) into the new array, and updates the slice header to point to this new array.

**G2**
`var x int` declares a variable `x` and initializes it to its zero value (which is `0` for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when declaring a variable in a scope where it has already been declared, or when you are explicitly declaring multiple variables using `var` syntax.

**G3**
A **goroutine** is a lightweight, independently executing function managed by the Go runtime. It is much cheaper than an OS thread because it has a very small stack (starting typically at 2KB) and context switching is handled entirely in user space by the Go runtime, not the OS kernel. The **Go scheduler (GMP model)** maps Goroutines (G) onto OS threads (M) using a pool of logical processors (P). The scheduler multiplexes many Goroutines onto a smaller number of OS threads, efficiently managing concurrency without the overhead of kernel context switching.

**G4**
Channels are typed conduits through which you can send and receive values between goroutines, providing a safe way for concurrent communication ("Don't communicate by sharing memory; share memory by communicating").
*   **Unbuffered Channel:** Requires both the sender and receiver to be ready at the exact moment of communication (synchronous rendezvous). Sending blocks until a receiver is ready, and vice versa.
*   **Buffered Channel:** Has a fixed capacity. Sending blocks only when the buffer is full; receiving blocks only when the buffer is empty.
When sending to a full buffered channel, the sending goroutine blocks until a receiver reads a value from the channel, freeing up space.

**G5**
The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. This is crucial for managing the lifecycle of concurrent operations, preventing resource leaks, and ensuring timely termination of long-running tasks.
Example:
```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"
)

func main() {
	// Create a context that automatically cancels after 2 seconds
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel() // Always call cancel to release resources

	req, err := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
	if err != nil {
		fmt.Println("Error creating request:", err)
		return
	}

	client := &http.Client{}
	resp, err := client.Do(req)
	if err != nil {
		// This error will often be context.DeadlineExceeded if the timeout hits
		fmt.Println("Request failed:", err)
	} else {
		resp.Body.Close()
	}
}
```

**G6**
Go's interface satisfaction model is **implicit** (or structural). A type satisfies an interface simply by implementing all the methods declared in that interface; there is no explicit `implements` keyword required. This differs from Java/C# where explicit declaration is often necessary.
The **empty interface `interface{}` (or `any` in Go 1.18+)** can hold a value of any type. It is powerful because it allows for maximum flexibility (e.g., generic storage or dynamic dispatch). It is dangerous because the compiler loses all type information, forcing runtime type assertions (`value.(Type)`) and potentially leading to runtime panics if the assertion is incorrect.

**G7**
This code is unsafe due to **data races**. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading `ready` and then reading `data`. Since there is no synchronization mechanism, the compiler/runtime cannot guarantee that the write operation from the goroutine is visible to the main goroutine before the loop condition is checked. The main goroutine might read the initial zero value of `ready` (`false`) indefinitely, or read a partially written value of `data`.
Correct alternatives include:
1.  **Mutex:** Using `sync.Mutex` to protect access to both `ready` and `data`.
2.  **Channels:** Sending a signal on a channel from the goroutine once the work is done, and receiving that signal in the main goroutine.

**G8**
*   **`sync.Mutex`:** A mutual exclusion lock. Only one goroutine can hold the lock at any given time, providing exclusive access for both reads and writes.
*   **`sync.RWMutex`:** A Read-Write Mutex. It allows multiple readers to hold the lock simultaneously (`RLock`), but requires exclusive access for writers (`Lock`).
**`sync.Map` vs. Map + Mutex:**
*   **Map + Mutex:** Generally faster for high-contention scenarios where writes are frequent, as the mutex overhead is predictable.
*   **`sync.Map`:** Optimized for scenarios where keys are written once but read many times (read-heavy workloads). It avoids locking the entire map structure for every read, offering better concurrency for reads, but it can have higher overhead for writes compared to a well-managed mutex.

**G9**
**Go Modules** are Go's dependency management system. They define the project's dependencies and versions, allowing reproducible builds.
*   **`go.mod`:** Declares the module path, the required Go version, and the direct dependencies (module path and required version) of the project.
*   **`go.sum`:** Contains cryptographic checksums (hashes) of the exact content of every dependency and its transitive dependencies listed in `go.mod`. This ensures that the downloaded code has not been tampered with.
**`go mod tidy`** cleans up the `go.mod` and `go.sum` files by adding any missing dependencies required by the source code and removing any dependencies that are no longer used.
**Minimum Version Selection (MVS):** MVS is an algorithm used by Go to select the highest possible version of a dependency that satisfies all version constraints specified in the `go.mod` file, ensuring that the dependency graph is consistent and uses the latest compatible versions.

**G10**
The `defer` statement schedules a function call to be executed immediately before the surrounding function returns.
Multiple defers execute in **Last-In, First-Out (LIFO)** order.
A common gotcha with `defer` in a loop is capturing the loop variable by reference. If the deferred function uses the loop variable, it will execute using the *final* value of that variable after the loop has completed, not the value it held during that specific iteration.

**G11**
A **pointer** in Go is a variable that stores the memory address of another variable. It allows you to indirectly access and modify the data stored at that address.
The zero value of a pointer is `nil`, which indicates that the pointer does not point to any valid memory address.
To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12**
The `init()` function is a special function that runs automatically when a package is initialized, before `main()` runs. It is used for setup tasks, such as initializing global variables or registering drivers.
A package can have multiple `init()` functions. They execute sequentially, in the order they appear in the source code files, ensuring that dependencies are initialized correctly before the main execution begins.

**G13**
*   **`make`:** Used to initialize reference types (slices, maps, channels). It allocates the underlying data structure and returns a usable instance. Example: `make([]int, 10)` or `make(map[string]int)`.
*   **`new`:** Used to allocate memory for a value of a specific type and return a pointer to the zero-initialized value of that type. It does not initialize the contents. Example: `new(MyStruct)` returns `*MyStruct` initialized to zero values.

**G14**
Error handling in Go is explicit and relies on returning errors as values. The **error interface** is defined as `type error interface { Error() string }`.
The idiomatic pattern is to check the returned error immediately after the function call: `if err != nil { return err }`.
*   `errors.Is(err, target)`: Checks if the error chain contains a specific sentinel error value (e.g., checking if an I/O error is specifically `io.EOF`).
*   `errors.As(err, &target)`: Checks if the error chain contains a value that matches a specific type, allowing you to extract structured error information into the `target` variable. This differs from `==` because `==` only checks for exact pointer equality, which is rarely useful for errors.

**G15**
*   **Map:** A collection of key-value pairs. Zero value: `nil` (cannot be written to until initialized with `make`).
*   **Slice:** A dynamically sized, contiguous sequence of elements. Zero value: `nil` (a slice header pointing to a nil underlying array).
*   **Channel:** A typed conduit for communication between goroutines. Zero value: `nil` (a channel that cannot be used for sending or receiving).
*   **Struct:** A composite type grouping fields of different types. Zero value: All fields are set to their respective zero values.

**G16**
A **race condition** occurs when two or more goroutines access the same memory location concurrently, and at least one of those accesses is a write, without any synchronization mechanism in place. The outcome depends on the unpredictable timing of the scheduler, leading to non-deterministic bugs.
The `-race` flag instruments the Go runtime to detect these data races during execution.
Example Data Race (Fix using Mutex):
```go
var counter int
var mu sync.Mutex

go func() {
    for i := 0; i < 1000; i++ {
        mu.Lock()
        counter++ // Race condition here
        mu.Unlock()
    }
}()
// ... wait for goroutine ...
```

**G17**
The `select` statement allows a goroutine to wait on multiple communication operations (channel operations) simultaneously. It is Go's mechanism for handling concurrency choices, analogous to `switch` but for channels.
When multiple cases are ready, `select` chooses one of them **randomly** to ensure fairness and prevent starvation.
To implement a timeout, you use `context.WithTimeout` or create a dedicated timer channel:
```go
select {
case msg := <-ch1:
    // Handle message from ch1
case <-time.After(5 * time.Second): // Timeout case
    fmt.Println("Operation timed out")
case msg := <-ch2:
    // Handle message from ch2
}
```

**G18**
**Escape analysis** is a compiler optimization that determines whether a variable's data should be allocated on the stack or the heap. If the compiler can prove that a variable's lifetime is confined to the current function call, it allocates it on the stack (fast). If the variable must outlive the function call (e.g., it is returned from the function or stored in a global structure), it must be allocated on the heap.
The compiler uses data flow analysis to track references. You can inspect these decisions using the `-m` flag during compilation. It matters for performance because stack allocation/deallocation is significantly faster than heap allocation/garbage collection.

**G19**
The `reflect` package allows a program to inspect and manipulate its own structure (types, values, methods) at runtime.
*   **`reflect.Type`:** Represents the metadata of a type (e.g., its name, fields, methods). It describes *what* the data is.
*   **`reflect.Value`:** Represents the actual value of a variable at runtime. It describes *the data itself*.
Reflection incurs significant performance costs because the compiler cannot optimize calls involving reflection; it must perform dynamic lookups and type checks at runtime. Reflection is justified when building generic frameworks, serialization libraries, or tools that must operate on arbitrary types, whereas code generation is preferred for performance-critical paths.

**G20**
The `go:embed` directive allows embedding files or directories directly into a Go binary as byte slices or file systems, eliminating the need for runtime file I/O for static assets.
*   **Single Files:** `//go:embed data.txt` embeds the content as `[]byte`.
*   **Directories:** `//go:embed assets` embeds the entire directory structure.
*   **File Systems:** `//go:embed fs` embeds the directory structure as an `fs.FS` interface, allowing standard Go I/O functions to read the embedded content as if it were on disk.
Limitations include the size of the binary (embedding large assets increases binary size) and the fact that the embedded content is static and cannot be modified at runtime without complex workarounds. It integrates seamlessly with `io/fs.FS` by providing an implementation of that interface.

**R1**
**Ownership** is Rust's core memory management concept. It dictates that every value in Rust has a single variable that is its *owner*. When the owner goes out of scope, the value is automatically dropped (memory is freed).
The three rules are:
1.  Each value in Rust has a single owner.
2.  When the owner goes out of scope, the value is dropped.
3.  Ownership can be transferred (moved) from one variable to another.

**R2**
*   **`String`:** An owned, heap-allocated, growable, mutable UTF-8 string type. Use it when you need to modify the string content or own the data.
*   **`&str`:** A string slice; a borrowed, immutable view into a string (which could be a `String` or a string literal). Use it in function signatures when you only need to read the string data without taking ownership or modifying it, as it avoids unnecessary heap allocations.

**R3**
**Borrowing** allows you to refer to a value without taking ownership of it. The **borrow checker** enforces Rust's rules to guarantee memory safety at compile time.
*   **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously. You can have many `&T` references active at once.
*   **Mutable Reference (`&mut T`):** Allows exactly one mutable reference to the data at any given time. This enforces the rule that you cannot have a mutable reference while any other reference (mutable or immutable) exists to prevent data races.

**R4**
*   **`Result<T, E>`:** An enum representing the outcome of an operation that might fail. It is either `Ok(T)` (success, containing type `T`) or `Err(E)` (failure, containing error type `E`).
*   **`Option<T>`:** An enum representing the presence or absence of a value. It is either `Some(T)` (value is present) or `None` (value is absent).
The **`?` operator** is syntactic sugar for propagating errors. If the expression it is applied to returns an `Err(E)`, the `?` operator immediately returns that error from the current function. If it returns `Ok(T)`, it unwraps the value `T` and continues execution.
File reading example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> Result<String, io::Error> {
    let mut file = File::open(path)?; // Propagates error if file cannot be opened
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates error if reading fails
    Ok(contents)
}
```

**R5**
These smart pointers manage heap allocation and reference counting:
*   **`Box<T>`:** A smart pointer that allocates data on the heap. It owns the data and is used when you need to put a type on the heap (e.g., recursive data structures or trait objects). It has a fixed, single owner.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data. It increments a counter when cloned and decrements it when dropped. Used for shared, immutable ownership within a single thread.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>`, but uses atomic operations for reference counting, making it safe to share ownership across multiple threads.

**R6**
**Traits** define shared behavior (a set of methods) that types can implement. They are Rust's mechanism for polymorphism.
*   **Comparison to Go Interfaces:** Traits are more powerful than Go interfaces because they can define default implementations and can be used to constrain generics. Go interfaces are purely structural contracts.
*   **Trait Object (`dyn Trait`):** A dynamically dispatched trait object. It is a pointer (usually `Box<dyn Trait>`) that holds a value of *any* type that implements the trait. This requires dynamic dispatch (runtime overhead).
*   **Generic with Trait Bound (`T: Trait`):** A statically dispatched generic. The compiler generates specialized code for every concrete type `T` used, resulting in zero runtime overhead (monomorphization). This is generally preferred for performance.

**R7**
The code fails to compile because the return type `&str` must live as long as the input references (`x` and `y`). The compiler cannot guarantee that the shorter string slice returned will remain valid after the `longest` function returns, as the original strings (`x` and `y`) might go out of scope.
Fix: You must introduce a lifetime annotation `'a` to tie the lifetime of the return value to the lifetimes of the input references:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

**R8**
*   **`Send`:** A marker trait indicating that a type can be safely transferred (sent) across thread boundaries.
*   **`Sync`:** A marker trait indicating that a type can be safely shared between threads (i.e., it is safe to have multiple immutable references to it across threads).
You cannot send an `Rc<T>` across threads because its internal reference counter is not atomic; multiple threads modifying the counter concurrently would lead to a data race.
**`Arc<T>`** is safe for concurrent use because its reference counting mechanism uses atomic CPU instructions, ensuring that the counter updates are thread-safe.

**R9**
Rust's `async/await` is built on top of the `Future` trait. A **`Future`** is a trait representing a value that may not be available yet. It is essentially a state machine that knows how to poll for completion.
The **executor** (e.g., Tokio, async-std) is the runtime responsible for driving these futures. It polls the futures, checking if they are ready to make progress. If a future is not ready, the executor suspends it and moves on to poll other ready futures, avoiding blocking the OS thread.
This differs from Go's goroutines because Go's scheduler manages lightweight threads that are preemptively scheduled by the runtime. Rust's `async/await` relies on cooperative multitasking; a future must explicitly yield control (by returning `Poll::Pending`) for the executor to switch to another task.

**R10**
`unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. This is necessary when interacting with low-level hardware, FFI (Foreign Function Interface), or implementing highly optimized data structures where the compiler cannot prove safety.
Three things you can do in `unsafe`:
1.  Dereference raw pointers (`*const T`, `*mut T`).
2.  Call `unsafe` functions or methods.
3.  Access or modify mutable static variables.
Unsafe code is justified only when the programmer can provide a formal, verifiable proof (usually through invariants and careful design) that the code maintains memory safety, concurrency safety, and type safety, even though the compiler cannot check it.

**R11**
**Pattern matching** allows you to compare a value against a series of patterns and execute code based on which pattern matches.
`match` is exhaustive; the compiler forces you to handle every possible variant of the enum or type, preventing runtime errors from unhandled cases.
`if let` is syntactic sugar for matching only one specific pattern. It is used when you only care about one specific case and want to avoid the boilerplate of a full `match` block.

**R12**
*   **`Vec<T>`:** A dynamically sized, heap-allocated, growable array. It manages its own capacity and automatically reallocates and copies data when capacity is exceeded.
*   **Array `[T; N]`:** A fixed-size, stack-allocated collection whose size `N` must be known at compile time.
When `Vec<T>` is pushed beyond its current capacity, it allocates a new, larger contiguous block of memory (often doubling the capacity), copies all existing elements from the old memory location to the new one, and then deallocates the old memory.

**R13**
**Enums** in Rust are powerful algebraic data types that can hold different types of data in different variants. Unlike C/Java enums (which are often just integer constants), Rust enums can be complex structures.
**`Option<T>`** is an enum defined as `enum Option<T> { None, Some(T) }`. Rust does not have `null` because `None` serves the exact same purpose—it is a type-safe way to represent the absence of a value, forcing the programmer to explicitly handle the `None` case via pattern matching or methods like `unwrap_or`.

**R14**
The **`impl` block** is used to define implementations of traits for a specific type, or to define methods and associated functions for a struct or enum.
*   **`&self`:** Borrows the instance immutably. Used for methods that only read data (e.g., `len()`).
*   **`&mut self`:** Borrows the instance mutably. Used for methods that modify the instance's state (e.g., `push()`).
*   **`self`:** Takes ownership of the instance. Used when the method consumes the instance (e.g., `into_inner()`).
**Associated functions** (like `String::new()`) are functions defined within an `impl` block that do not take `self` as an argument. They are called directly on the type name, not on an instance.

**R15**
A **derive macro** is a procedural macro that automatically implements standard traits for a struct or enum based on its structure.
Commonly derived traits:
*   `Debug`: Allows printing the value using `{:?}`.
*   `Clone`: Allows creating a deep copy of the value.
*   `PartialEq`/`Eq`: Allows comparison using `==` and `!=`.
*   `Serialize`/`Deserialize`: Used by serialization libraries (like Serde) to convert the type to/from formats like JSON.
You cannot derive a trait if the type does not meet the trait's requirements. For example, you cannot derive `Eq` if you have not also derived `PartialEq` and if the type contains non-comparable elements.

**R16**
**`Cow<'a, T>` (Clone on Write)** is a smart type that allows a value to be either borrowed (`&T`) or owned (`T`). It acts as a wrapper that defaults to a borrowed state.
It is useful when you frequently receive data that you might need to modify, but most of the time you only need to read it. Instead of always cloning the data upon receipt (which is expensive), `Cow` holds a reference. Only when a mutation is attempted does it perform an allocation and clone the data internally, thus avoiding unnecessary allocations in read-heavy scenarios.

**R17**
Rust's module system organizes code into hierarchical units.
*   **`mod`:** Declares a module, which can contain other modules or items.
*   **`use`:** Brings items (functions, structs) from another module into the current scope, allowing you to refer to them without the full path.
*   **`pub`:** Makes an item publicly accessible outside of its defining module.
The file system maps to modules: a file named `foo.rs` defines the `foo` module. A directory named `foo/` defines the `foo` module, and its `mod.rs` (or `foo.rs` in modern Rust) acts as the module root.
The major change between Rust 2015 and 2018 was the introduction of **path-based module resolution**, allowing modules to be defined in arbitrary files without needing to be strictly nested in the file system structure.

**R18**
**`Pin<T>`** is a wrapper that guarantees that a value `T` behind it will not be moved in memory for the duration of its lifetime. This is crucial because certain types, particularly those involved in asynchronous operations, rely on having a stable memory address to function correctly.
It relates to **self-referential structs** (structs that contain a pointer to one of their own fields) because if the struct moves in memory, the internal pointer becomes invalid.
**`Unpin`** is a marker trait indicating that a type *can* be safely moved. If a type does not implement `Unpin`, it must be pinned using `Pin<T>` to prevent its memory location from changing, which is necessary for futures to maintain their internal state correctly across `.await` points.

**R19**
Rust's macro system allows metaprogramming—writing code that writes code.
*   **Declarative Macros (`macro_rules!`):** These are pattern-matching macros. They operate by matching input tokens against defined patterns and substituting them with corresponding output tokens. They are simpler and operate at compile time based on syntax.
*   **Procedural Macros:** These are functions that take Rust code (as tokens) as input and output new Rust code (as tokens). They are more powerful and are used for `derive` (implementing traits automatically) and attribute macros.
**Hygiene rules** ensure that identifiers used inside a macro do not accidentally capture or conflict with identifiers in the surrounding scope, preventing unintended side effects when the macro expands the code.

**R20**
**Zero-cost abstractions** mean that high-level language features (like generics or iterators) compile down to machine code that is as efficient as if the programmer had written the equivalent low-level code manually (like C).
*   **Generics (Monomorphization):** When you use generics (e.g., `Vec<T>`), the compiler generates a specific, concrete version of the code for every type `T` used (e.g., `Vec<i32>`, `Vec<String>`). This avoids runtime type checking overhead.
*   **Trait Static Dispatch:** When a trait method is called on a generic type, the compiler knows the exact concrete type at compile time and calls the specific implementation directly, avoiding the overhead of virtual function tables (dynamic dispatch).
*   **Iterators:** Rust iterators are zero-cost because they are implemented as structs that hold state and implement the `Iterator` trait. The compiler optimizes the loop structure to be highly efficient, often compiling down to simple pointer arithmetic and loop control, matching manual C-style loops.
