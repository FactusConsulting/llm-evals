**Kubernetes Answers**

K1 — A Deployment manages stateless applications, ensuring a specified number of identical replicas are running and handling updates via rolling updates. A StatefulSet manages stateful applications, providing stable, unique network identifiers and persistent storage for each pod, ensuring ordered deployment and scaling.

K2 — A ClusterIP Service exposes the Service internally within the cluster using a stable virtual IP (ClusterIP). When a pod targets this Service, `kube-proxy` (running on each node) intercepts traffic destined for the ClusterIP and uses iptables or IPVS rules to randomly select a healthy backend pod IP and port to forward the traffic to.

K3 — **PersistentVolume (PV):** A cluster resource representing a piece of physical storage provisioned in the cluster (e.g., an AWS EBS volume). It is cluster-wide. **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a namespace-scoped object that requests a specific size and access mode from the cluster. **StorageClass:** A definition that dictates *how* storage should be dynamically provisioned (e.g., specifying the type of cloud disk or storage provisioner). They relate because a PVC requests storage, and the StorageClass tells the cluster how to fulfill that request by binding it to an available PV.

K4 — 1. **Check Pod Events:** Use `kubectl describe pod <name>` to check the `Events` section for specific failure reasons (e.g., ImagePullBackOff, CrashLoopBackOff reason). 2. **Check Logs:** Use `kubectl logs <name>` to see the application's output leading up to the crash. 3. **Check Resource Limits:** Verify if the pod is exceeding its defined memory or CPU limits, causing the Kubelet to terminate it (OOMKilled). 4. **Check Image/Configuration:** Ensure the container image exists, is correct, and that the command/entrypoint specified in the Dockerfile/Pod spec is valid and executable.

K5 — CoreDNS acts as the cluster's internal DNS service, translating service names (e.g., `my-service.my-namespace.svc.cluster.local`) and pod IP addresses into resolvable addresses. If CoreDNS pods are down, DNS resolution for internal services and external domains will fail, resulting in connection timeouts or "Name resolution failed" errors for any application attempting to communicate using service names.

K6 — The scheduler uses a two-phase process: **Filtering** and **Scoring**.
1. **Filtering (Predicates):** The scheduler first filters out nodes that *cannot* run the pod based on hard constraints (e.g., insufficient CPU/Memory, node taints that the pod does not tolerate).
2. **Scoring (Priorities):** For the remaining eligible nodes, the scheduler scores them based on various factors to determine the "best" fit.
Specific factors considered include:
1. **Resource Utilization:** Preferring nodes with available capacity that align well with the pod's requested resources.
2. **Node Affinity/Anti-Affinity:** Respecting rules that dictate where the pod should or should not run relative to other pods.
3. **Least Requested Priority:** Preferring nodes that are less utilized or have lower resource requests already assigned, promoting better distribution.

K7 — **Scheduling:** Yes, the pod will likely be scheduled. The scheduler primarily checks *requested* resources against *available* resources. The node has 4GB total. 3.5GB is requested. Available capacity is 0.5GB. The pod requests 256Mi. Since 256Mi < 0.5GB, it passes the initial scheduling check. **Runtime Behavior:** If the pod uses 600Mi at runtime, it will exceed its limit (512Mi). The Kubelet will enforce the limit, and the container runtime will terminate the process, resulting in the pod entering a CrashLoopBackOff state due to an Out-Of-Memory (OOM) kill.

K8 — 1. **External LB:** An external Load Balancer (e.g., AWS ELB, GCP LB) receives the external traffic and forwards it to the NodePort or host IP of the Ingress Controller node. 2. **Ingress Controller:** The NGINX controller (running as a pod) receives the traffic. It inspects the host header and path defined in the Ingress resource rules. 3. **Service:** The Ingress Controller routes the traffic to the ClusterIP Service associated with the application. 4. **Endpoints:** The Service object maintains an Endpoints object, which lists the actual IP addresses of the healthy backend pods. The Service uses this list to select a target pod. 5. **kube-proxy/iptables:** `kube-proxy` on the node intercepts the traffic destined for the Service ClusterIP. It uses iptables rules to perform DNAT (Destination Network Address Translation), rewriting the destination IP/port to the actual IP/port of a selected backend pod, finally delivering the request to the application pod.

K9 — A NetworkPolicy defines rules about how groups of pods are allowed to communicate with each other and with external network endpoints. If no NetworkPolicy exists in a namespace, the default behavior is "allow all" ingress and egress traffic. When a NetworkPolicy is applied, the default behavior changes to "deny all" ingress and egress traffic for the selected pods, unless explicitly permitted by a rule in the policy.

K10 — **RollingUpdate:** Gradually replaces old versions of pods with new versions. It maintains availability by ensuring a minimum number of old and new pods are running concurrently during the transition. **Recreate:** Terminates all existing pods of the old version before creating any new pods of the new version. **Choose Recreate:** You would choose Recreate only if the application is completely stateless, has no dependencies on existing connections, and if a brief period of complete downtime is acceptable, as it guarantees a clean slate for the new version.

K11 — A namespace is a mechanism for partitioning cluster resources, providing scope for names and access control. It allows multiple users or teams to share a physical cluster without interfering with each other's resources. Default namespaces include `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

K12 — `kubectl describe pod <name>` provides a detailed status report of the pod, including metadata, current state, resource requests/limits, container statuses, and most importantly, the **Events** log. Information it shows that `kubectl get pod` does not include: 1. Detailed container status (e.g., restart count, last state). 2. Resource requests and limits assigned to the pod. 3. The sequence of events (scheduling, pulling image, readiness checks) that have occurred for the pod.

K13 — A ConfigMap is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) in key-value pairs, decoupling configuration from the container image. Pods can consume it in two ways: 1. **As Environment Variables:** Injecting keys/values directly into the container's environment. 2. **As Mounted Volumes:** Mounting the ConfigMap as a file system volume inside the container, allowing the application to read configuration files.

K14 — **ClusterIP:** Exposes the Service internally within the cluster using a stable virtual IP. Only reachable from within the cluster. **NodePort:** Exposes the Service on a specific port on *every* node in the cluster. External traffic can reach the service via `<NodeIP>:<NodePort>`. **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes external traffic directly to the Service's ClusterIP, providing a stable external endpoint.

K15 — A DaemonSet ensures that a copy of a pod runs on *every* (or a specified subset of) eligible nodes in the cluster. You use it when you need a service that must run locally on every node, such as a log collector (Fluentd), a node monitoring agent, or a network plugin, rather than a centralized service that handles requests.

K16 — **Taints:** A property applied to a Node that repels (prevents) pods from being scheduled onto it unless the pod explicitly tolerates the taint. **Tolerations:** A property applied to a Pod that allows it to be scheduled onto a Node that has a matching taint. **Node Affinity:** A scheduling rule that *attracts* or *repels* pods based on node labels, allowing scheduling even if no taint is present. **Use Cases:** Taint/Toleration: Isolating a node for critical, specialized workloads (e.g., GPU nodes). Node Affinity: Ensuring a database pod always runs on a node labeled `disk-type: ssd`.

K17 — A Kubernetes Operator is a method of packaging, deploying, and managing a complex application. It extends the Kubernetes API by embedding domain-specific knowledge into a custom controller. Unlike a standard controller (which manages the desired state of a simple resource like a Deployment), an Operator understands the *operational lifecycle* of a complex application (e.g., database failover, backup scheduling, scaling based on load) and automatically performs the necessary human-like remediation actions.

K18 — Kubernetes uses **Raft** (or a Raft-like consensus algorithm) for etcd. Raft ensures strong consistency by requiring a majority (quorum) of nodes to agree on a transaction before it is committed. If the etcd quorum is lost (e.g., 2 out of 3 nodes fail), the cluster cannot achieve consensus, and all write operations (including API server updates) will halt, effectively freezing the cluster state. To recover from 2 out of 3 nodes being permanently lost, the cluster is unrecoverable in its current configuration, as the quorum (majority) cannot be re-established. A new etcd cluster must be bootstrapped with a new majority set.

K19 — RBAC controls authorization, defining *who* (User/ServiceAccount) can do *what* (Verb) to *which* resources (Resource) in *which* scope (Namespace/Cluster). **Role:** Defines permissions within a specific namespace. **ClusterRole:** Defines permissions across the entire cluster. **RoleBinding:** Binds a Role to a Subject (User/ServiceAccount) within a specific namespace. **ClusterRoleBinding:** Binds a ClusterRole to a Subject across the entire cluster.
*Manifests for read-only access to pods and logs in `my-namespace`:*
```yaml
# 1. Define the Role (Permissions)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
---
# 2. Bind the Role to a User/ServiceAccount (Authorization)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-reader-binding
  namespace: my-namespace
subjects:
- kind: User
  name: developer-user # Replace with actual user/service account
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` specifies the number of dots in a Fully Qualified Domain Name (FQDN) that the pod's DNS resolver should attempt to resolve before giving up. If `ndots` is set too high (e.g., 10), and the pod tries to resolve a short name like `api`, the resolver will attempt to resolve `api.a.b.c.d.e.f.g.h.i.api` (10 dots), which is likely non-existent, leading to excessive, slow DNS queries. To fix this, you can use `dnsConfig` in the pod spec to explicitly set `options.ndots: 1`, telling the resolver to only attempt resolution for names matching the domain's structure.

**Development Answers**

D1 — **Git Merge:** Combines two branches by creating a new "merge commit" that has two parents. It preserves the full history of both branches. **Git Rebase:** Rewrites history by moving or combining a sequence of commits to a new base commit. It makes the history linear and cleaner. **Avoid Rebasing:** Avoid rebasing commits that have already been pushed to a shared, public repository, as rewriting shared history forces collaborators to perform complex recovery operations.

D2 — **TCP (Transmission Control Protocol):** Connection-oriented, reliable, ordered delivery. It uses a three-way handshake to establish a connection. *Protocols: HTTP/HTTPS, FTP.* **UDP (User Datagram Protocol):** Connectionless, unreliable, best-effort delivery. It sends packets without prior negotiation. *Protocols: DNS, VoIP.*

D3 — A race condition occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data. **Example:** Two threads simultaneously read a bank account balance ($1000). Both threads calculate a withdrawal of $100. Both threads write back the new balance ($900). The correct final balance should be $800, but because the reads happened before the writes, one withdrawal is lost.

D4 — **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is fast. **Asymmetric Encryption:** Uses a pair of keys: a public key (for encryption, shared widely) and a private key (for decryption, kept secret). It is computationally intensive. **TLS Usage:** Asymmetric encryption (RSA/ECC) is used during the initial handshake to securely exchange a symmetric session key. Once the key is exchanged, symmetric encryption is used for the bulk data transfer because it is much faster.

D5 — A container image layer is a read-only, immutable snapshot of the filesystem state created by each instruction in the Dockerfile. Layer caching is crucial because Docker builds layers sequentially. If an instruction (e.g., `RUN apt-get update`) hasn't changed, Docker reuses the cached layer, significantly speeding up subsequent builds. Best practice dictates placing instructions that change infrequently (like installing OS dependencies) early in the Dockerfile.

D6 — 1. **Check Application Logs:** Look for specific exceptions, timeouts, or resource exhaustion errors in the application logs. 2. **Check Service Health/Metrics:** Verify the API service's health endpoints and monitor latency/error rates (e.g., using Prometheus/Grafana). 3. **Check Dependencies:** Verify if the API relies on external services (DB, cache) and if those dependencies are healthy and responsive. 4. **Check Resource Saturation:** Check the CPU/Memory usage of the API pods to see if they are being throttled or are running out of memory.

D7 — **CAP Theorem:** States that a distributed data store can only guarantee two out of three properties simultaneously: **C**onsistency (every read receives the most recent write), **A**vailability (every request receives a response, without guarantee that it is the most recent write), and **P**artition Tolerance (the system continues to operate despite network partitions).
*   **CP System (Consistency over Availability):** Systems like traditional relational databases (e.g., PostgreSQL cluster) often choose CP. If a partition occurs, the system stops accepting writes/reads on the minority side to prevent inconsistent data.
*   **AP System (Availability over Consistency):** Systems like Cassandra or DynamoDB choose AP. During a partition, nodes continue to accept reads/writes, accepting that some data might be temporarily stale until the partition heals.

D8 — **Horizontal Scaling (Scaling Out):** Adding more instances (nodes/pods) of the application to distribute the load. This is preferred for stateless services as it offers near-linear scalability. **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) allocated to an existing instance. This is limited by the maximum capacity of the underlying hardware. **Architectural Patterns:** Load Balancers, Microservices architecture, and Stateless design patterns enable horizontal scaling.

D9 — An environment variable is a dynamic named value that can affect the way running processes will behave on a computer. On Linux, to set a variable that persists across shell sessions, you must add the definition (e.g., `export MY_VAR="value"`) to your shell configuration file, such as `~/.bashrc` or `~/.zshrc`, and then source the file (`source ~/.bashrc`).

D10 — **JSON (JavaScript Object Notation):** A lightweight data-interchange format using key-value pairs and arrays. *Advantage: Native compatibility with JavaScript.* **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that uses indentation to denote structure. *Advantage: Highly readable and concise for configuration.*

D11 — A REST (Representational State Transfer) API is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources.
*   **GET:** Retrieves a resource or a collection of resources (Read). It should be idempotent and safe.
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource (Create).
*   **PUT:** Replaces an entire resource at a known URI. It is idempotent.
*   **DELETE:** Removes a specified resource (Delete).

D12 — Version pinning is the practice of explicitly specifying the exact version number of a dependency (e.g., `library==1.2.3`) rather than using a broad range (e.g., `library>=1.0`). It is vital for reproducible builds because it guarantees that the build environment will always use the exact same code, preventing unexpected breakage caused by upstream library authors making breaking changes in minor or patch releases.

D13 — **Compiled Language:** Source code is translated entirely into machine code (or bytecode) by a compiler *before* execution. *Examples: C++, Go.* **Interpreted Language:** Source code is read and executed line-by-line at runtime by an interpreter. *Examples: Python, JavaScript.*

D14 — **Reverse Proxy:** Sits in front of one or more web servers and forwards client requests to them. It shields the backend servers from direct client exposure. **Forward Proxy:** Sits in front of a client (user) and forwards requests on behalf of the client to the internet. **Servers/Use Cases:** 1. **NGINX/HAProxy (Reverse Proxy):** Used for load balancing, SSL termination, and caching. 2. **Squid (Forward Proxy):** Used by corporate networks to cache external web traffic and filter content.

D15 — A deadlock is a state in a concurrent system where two or more competing actions are each waiting for the other to finish, resulting in a permanent standstill. The four necessary conditions (Coffman conditions) are:
1. **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2. **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3. **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily.
4. **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

D16 — **Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, all reads will eventually return the last updated value, though there may be a period of inconsistency immediately following a write. Cassandra handles read-after-write consistency by using tunable consistency levels (e.g., `QUORUM`). If a write is acknowledged by a quorum of replicas, subsequent reads configured to also query a quorum are highly likely to see the latest write. Tunable levels include: `ONE` (fastest, least consistent), `QUORUM` (majority, balanced), and `ALL` (slowest, most consistent).

D17 — **mTLS (Mutual TLS):** An extension of standard TLS where *both* the client and the server authenticate each other using digital certificates, rather than just the server authenticating to the client. **Handshake Process:** 1. Client initiates connection. 2. Server sends its certificate. 3. Client verifies the server certificate. 4. Server requests the client certificate. 5. Client sends its certificate. 6. Server verifies the client certificate against its trusted CAs. 7. If both are verified, a symmetric session key is established. **Use Case:** Securing service-to-service communication in a zero-trust microservices architecture (e.g., using a service mesh like Istio).

D18 — A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an array. **Collision Resolution:**
*   **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hash to that index.
*   **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing).
**Time Complexity:**
*   **Average Case (Insertion, Lookup, Deletion):** $O(1)$ (assuming a good hash function and low load factor).
*   **Worst Case (Insertion, Lookup, Deletion):** $O(n)$ (when all keys hash to the same bucket, degenerating into a linked list traversal).

D19 — The circuit breaker pattern monitors calls to a remote service. If the failure rate exceeds a defined threshold, the circuit "trips" and stops sending requests to the failing service immediately, failing fast instead of waiting for timeouts. This prevents the calling service from being overwhelmed while the downstream service recovers, stopping cascade failures. **States:** 1. **Closed:** Normal operation; requests pass through. 2. **Open:** Failure threshold reached; requests are immediately rejected without calling the service. 3. **Half-Open:** After a timeout in the Open state, a few test requests are allowed through; if they succeed, the circuit closes; if they fail, it returns to Open. **Relation to Retries:** Circuit breakers prevent excessive retries during a failure storm. Exponential backoff is used *within* the closed/half-open state to space out retries, preventing the client from hammering a struggling service.

D20 — **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data item *before* the transaction reads or modifies it, preventing other transactions from accessing it until the lock is released. *When to choose:* High-contention environments where data integrity is paramount (e.g., financial transfers). *Example:* Using `SELECT ... FOR UPDATE` in SQL. **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read. If a conflict is detected, the transaction is rolled back and retried. *When to choose:* Low-contention environments where locking overhead would severely degrade performance. *Example:* Using version numbers or timestamps in the `WHERE` clause during an update (`UPDATE table SET value=X, version=version+1 WHERE id=Y AND version=Z`).
