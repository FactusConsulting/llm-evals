## Go Answers

G1 — The difference is that an **array** has a fixed size defined at compile time (e.g., `[5]int`), while a **slice** is a dynamically sized, flexible view into an underlying array. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array (typically doubling the capacity), copies the existing elements to the new array, and updates the slice header to point to the new memory location.

G2 — `var x int` declares a variable `x` and initializes it to its zero value (0 for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when redeclaring a variable within the same scope, or when declaring a variable outside of a function body (at the package level).

G3 — A **goroutine** is a lightweight, independently executing function managed by the Go runtime, not the OS. It is much cheaper than an OS thread because it requires very little stack space (starting small, growing as needed). The **Go scheduler (GMP model)** maps Goroutines (G) onto OS threads (M) using a pool of logical processors (P). The scheduler multiplexes many Gs onto a smaller set of Ms, efficiently managing context switching without the overhead of OS kernel calls.

G4 — Channels are typed conduits through which you can send and receive values between goroutines, providing synchronized communication. An **unbuffered channel** requires both the sender and receiver to be ready simultaneously for the communication to proceed (synchronous rendezvous). A **buffered channel** allows a specified number of values to be sent without an immediate receiver being present. When sending to a full buffered channel, the sender goroutine blocks until a receiver frees up a slot.

G5 — The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. This is crucial for managing the lifecycle of requests.
Example:
```go
import (
    "context"
    "net/http"
    "time"
)

func makeRequestWithTimeout() {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel() // Always call cancel to release resources

    req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
    client := &http.Client{}
    resp, err := client.Do(req)
    // Handle context cancellation error here if the timeout occurred
}
```

G6 — Go uses **implicit interface satisfaction**. A type satisfies an interface simply by implementing all the methods defined in that interface; there is no explicit declaration required (unlike Java/C# where you must `implements` an interface). The **empty interface `interface{}` (or `any`)** can hold a value of *any* type. It is powerful because it allows for maximum flexibility (e.g., generic data structures), but dangerous because the compiler loses all type information, requiring type assertions or type switches at runtime, which can panic if the assertion is incorrect.

G7 — This is unsafe due to **data races**. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading `ready` and `data`. Go's memory model guarantees that writes are visible to other goroutines only if synchronization primitives (like channels or mutexes) are used. The loop `for !ready {}` spins indefinitely (busy waiting) until the write happens, but without synchronization, the compiler/CPU might reorder memory operations, meaning the main goroutine might read a stale value of `ready` or `data`.
**Correct Alternatives:**
1. **Channels:** Send a signal on a channel when the data is ready.
2. **Mutex:** Protect access to `ready` and `data` using `sync.Mutex`.

G8 — `sync.Mutex` provides exclusive locking (only one goroutine can hold the lock at a time, read or write). `sync.RWMutex` allows multiple readers to hold the lock concurrently (`RLock`), but requires exclusive access for writers (`Lock`). Use `sync.Map` when you have a high volume of concurrent reads and writes, and the keys are dynamic, as it is optimized for concurrent access without requiring external locking on the map structure itself. Use a regular map with a mutex when the access pattern is complex, or when you need transactional integrity over the entire map structure, as `sync.Map` can have higher overhead for simple operations.

G9 — **Go modules** manage dependencies for Go projects. `go.mod` lists the required modules and their version constraints. `go.sum` contains cryptographic checksums for the exact content of every dependency listed in `go.mod`, ensuring build reproducibility and integrity. `go mod tidy` cleans up `go.mod` and `go.sum` by adding missing dependencies and removing unused ones. **Minimum Version Selection (MVS)** is an algorithm that selects the highest possible version of a dependency that satisfies all constraints specified in the module graph, ensuring the dependency is as modern as possible while remaining compatible.

G10 — A `defer` statement schedules a function call to run immediately before the surrounding function returns. Multiple defers execute in **Last-In, First-Out (LIFO)** order. A common gotcha in a loop is capturing the loop variable by reference. If you defer a function that uses the loop variable, the deferred function will execute *after* the loop finishes, and it will use the final value of the loop variable, not the value it had during that specific iteration.

G11 — A **pointer** in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

G12 — The `init()` function is a special function that runs automatically before the `main` function in a package. It is used for package-level initialization logic. A package can have multiple `init()` functions; they execute sequentially in the order they appear in the source code.

G13 — `make` is used to initialize built-in reference types (slices, maps, channels). It allocates and returns a pointer to the initialized data structure. `new` allocates memory for a value of a specified type and returns a pointer to the zero value of that type. `make` requires arguments defining the initial size/capacity; `new` does not.

G14 — Error handling in Go is explicit, relying on returning an `error` type as the last return value. The `error` interface is a built-in interface defined as `type error interface { Error() string }`. The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain contains a specific sentinel error value. `errors.As(err, &target)` checks if the error chain contains a value that matches a specific type, allowing you to extract structured error details.

G15 — **Map:** `map[KeyType]ValueType`. Zero value: `nil`. **Slice:** `[]Type`. Zero value: `nil` (a nil slice is valid and has length 0). **Channel:** `chan Type`. Zero value: `nil`. **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.
G16 — A **race condition** occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, leading to unpredictable results. The `-race` flag instruments the Go runtime to detect these data races during execution.
Example: Two goroutines incrementing a shared counter without synchronization.
Fix: Use `sync.Mutex` to wrap the increment operation, ensuring only one goroutine modifies the counter at a time.

G17 — The `select` statement waits on multiple communication operations (channel receives/sends). It differs from `switch` because `select` is specifically designed for concurrency and blocking on channel operations. When multiple cases are ready, `select` chooses one **randomly** to ensure fairness. A timeout is implemented by using `select` with a `time.After` channel:
```go
select {
case msg := <-ch:
    // Received message
case <-time.After(5 * time.Second):
    // Timeout occurred
}
```

G18 — **Escape analysis** is the process by which the Go compiler determines whether a variable should be allocated on the stack (fast, automatic cleanup) or the heap (slower, managed by the garbage collector). The compiler analyzes the variable's lifetime and usage. If a variable's address escapes the function scope (i.e., it is returned, stored in a global variable, or passed to a goroutine), it must be allocated on the heap. You can inspect this using the `-m` flag during compilation. It matters because heap allocation involves GC overhead, while stack allocation is extremely fast.

G19 — The `reflect` package allows inspecting and manipulating variables whose types are not known until runtime. `reflect.Type` describes the structure of a type (its name, fields, methods), while `reflect.Value` represents the actual value of a variable at runtime. Reflection incurs significant performance costs because the compiler cannot optimize code paths based on static types. Reflection is justified when building generic frameworks, serialization libraries, or tools where the structure of the data is dynamic; otherwise, static typing and code generation are preferred.

G20 — The `go:embed` directive allows embedding files or directories directly into a Go binary as byte slices or file systems. It works by instructing the compiler to read the specified path at build time and embed the content. For single files, it embeds the content directly. For directories or file systems, it embeds them as an `fs.FS` interface. Limitations include the size of the resulting binary and the complexity of accessing embedded resources. It interacts with `io/fs.FS` by providing a concrete implementation of that interface containing the embedded data.

## Rust Answers

R1 — **Ownership** is Rust's core memory management concept. It dictates that every value in Rust has a single variable that is its *owner*. When the owner goes out of scope, the value is automatically dropped (memory is freed).
The three rules are:
1. Each value has a single owner.
2. When the owner goes out of scope, the value is dropped.
3. Data can have multiple *references* (borrows), but only one *mutable* reference at a time.

R2 — **`String`** is a heap-allocated, growable, mutable, owned string type (like `std::string` in C++). **`&str`** is a string slice—a borrowed, immutable reference to a sequence of UTF-8 bytes, typically stored in the static data segment or on the stack. Use `String` when you need to own, modify, or build a string. Use `&str` in function signatures when you only need to read the string data, as it avoids unnecessary heap allocations.

R3 — **Borrowing** allows you to refer to data without taking ownership of it. The **borrow checker** enforces Rust's ownership rules at compile time to guarantee memory safety without a garbage collector.
*   **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously. You can have many `&T` references active at once.
*   **Mutable Reference (`&mut T`):** Allows exactly one mutable reference to the data at any given time. This prevents data races by ensuring exclusive write access.

R4 — **`Result<T, E>`** is an enum representing a computation that might succeed (`Ok(T)`) or fail (`Err(E)`). **`Option<T>`** is an enum representing a value that might be present (`Some(T)`) or absent (`None`). The **`?` operator** is syntactic sugar for propagating errors. If the expression it operates on is `Err(E)`, the `?` operator immediately returns that error from the current function. If it is `Ok(T)`, it unwraps the value `T` and continues execution.
Example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> Result<String, io::Error> {
    let mut file = File::open(path)?; // Propagates error if file cannot be opened
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates error if reading fails
    Ok(contents)
}
```

R5 — All three manage shared ownership, but differ in how they handle reference counting and thread safety:
*   **`Box<T>`:** A smart pointer that allocates data on the heap. It provides *unique* ownership. Use it when you need to put a type on the heap to avoid stack overflow or when implementing recursive data structures.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data on the heap. It uses atomic reference counting, but it is **not thread-safe**. Use it for single-threaded shared ownership.
*   **`Arc<T>` (Atomic Reference Counted):** Like `Rc<T>`, but uses atomic operations for reference counting, making it **thread-safe**. Use it when sharing ownership across threads.

R6 — **Traits** define shared behavior (a set of methods) that types can implement. They are Rust's mechanism for polymorphism. They are similar to Go interfaces in that they define a contract.
*   **Trait Object (`dyn Trait`):** A dynamically dispatched trait object. It holds a pointer to a value that implements the trait, allowing you to treat different concrete types uniformly at runtime (similar to an interface variable in Go).
*   **Generic with Trait Bound (`T: Trait`):** A statically dispatched generic parameter. The compiler knows the concrete type `T` at compile time, allowing for monomorphization and zero-cost abstraction. This is generally preferred over trait objects for performance.

R7 — This fails because the compiler cannot guarantee that the returned reference (`&str`) will remain valid as long as the caller uses it. The reference points into `x` or `y`, which are local variables within `longest` and are dropped when the function returns. This is a **lifetime error**.
Fix: We must annotate the return type with a lifetime parameter that ties the returned reference to the input references:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```
The `'a` ensures the returned reference lives at least as long as the shorter of the two input references.

R8 — **`Send`** means a type can be safely transferred (sent) across thread boundaries. **`Sync`** means a type can be safely referenced across thread boundaries (i.e., `&T` where `T: Sync` is safe to share between threads).
You cannot send an `Rc<T>` across threads because its internal reference counter is not atomic, leading to potential race conditions during counting. `Arc<T>` is safe for concurrent use because its reference counter is implemented using atomic operations, ensuring thread-safe increments and decrements.

R9 — Rust's `async/await` is built on the concept of **Futures**. A `Future` is a trait representing a value that *might* be available in the future. It is essentially a state machine that knows how to poll itself until it completes. The **executor** (like Tokio or async-std) is the runtime responsible for driving these futures. It polls the futures, executing the necessary code when the future signals it is ready (e.g., when I/O completes). This differs from Go's goroutines because Rust futures are *not* preemptively scheduled threads; they are cooperative tasks that yield control back to the executor when they await an operation.

R10 — **`unsafe`** allows Rust programmers to bypass the compile-time safety guarantees of the borrow checker. It grants access to low-level operations that require manual memory management or pointer manipulation. Three things you can do: dereference raw pointers, call `unsafe` functions, and access mutable static variables. Unsafe code is justified only when implementing highly optimized libraries, FFI (Foreign Function Interface) bindings, or when interfacing with hardware/OS APIs where Rust's safety guarantees are insufficient.

R11 — **Pattern matching** uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches. `if let` is syntactic sugar for matching a single, specific pattern and unwrapping it if it matches. `match` is more powerful because it can handle multiple patterns, guards (`if` conditions), and is exhaustive. The compiler enforces **exhaustiveness** by requiring that the `match` expression covers every possible variant of the enum or type being matched, preventing runtime errors from unhandled cases.

R12 — **`[T; N]`** is a fixed-size array whose size $N$ is known at compile time. **`Vec<T>`** is a dynamically sized, heap-allocated vector. When `Vec<T>` is pushed beyond its current capacity, it allocates a new, larger contiguous block of memory (often doubling the capacity), copies all existing elements to the new block, and deallocates the old block.

R13 — **Enums** in Rust are powerful algebraic data types that can hold different data types for each variant. Unlike C/Java enums, Rust enums can have associated data (e.g., `enum Message { Quit, Data(i32) }`). **`Option<T>`** is an enum with two variants: `Some(T)` (contains a value) and `None` (contains no value). Rust avoids null by using `Option<T>`, forcing the programmer to explicitly handle the absence of a value at compile time, eliminating null pointer exceptions.

R14 — The **`impl` block** is used to define methods and associated functions for a specific type.
*   **`&self`:** Borrows the instance immutably. Used for read-only operations.
*   **`&mut self`:** Borrows the instance mutably. Used for operations that modify the instance's state.
*   **`self`:** Takes ownership of the instance. Used when the method consumes the instance (e.g., `String::into_bytes()`).
**Associated functions** (like `String::new()`) are functions defined within the `impl` block that do not take `self` as an argument; they are called directly on the type name.

R15 — A **derive macro** is a procedural macro that automatically implements standard traits for a struct or enum based on its structure. Examples: `#[derive(Debug)]` allows printing the struct using `{:#?}`; `#[derive(Clone)]` implements deep copying; `#[derive(PartialEq)]` implements equality checks. You cannot derive a trait if the type does not meet the trait's requirements (e.g., you cannot derive `Clone` if the type contains a non-cloneable resource).

R16 — **`Cow<'a, T>` (Clone on Write)** is a smart pointer that can hold either an owned value (`T`) or a borrowed reference (`&'a T`). It is useful when you receive data that might need modification, but you want to avoid allocating a new copy if no modification is necessary. If you only read the data, it uses the cheap reference. If you mutate it, it clones the data internally, thus performing the "clone on write."

R17 — Rust's module system organizes code hierarchically. **`mod`** declares a module (which can be a file or an inline block). **`use`** brings items from a module into the current scope, allowing you to refer to them without qualification. **`pub`** makes items accessible outside the current module. The file system maps to modules: a file named `foo.rs` is typically treated as the `foo` module. The major change in Rust 2018 was the introduction of **path-based modules**, allowing modules to be defined by their location in the file system rather than just by explicit `mod` declarations.

R18 — **`Pin<T>`** is a wrapper that guarantees that a value `T` will not be moved in memory after it has been pinned. This is critical for types that contain self-references (where a part of the struct points back to another part of the same struct) or for async state machines. If a future is moved in memory, its internal pointers become invalid. **`Unpin`** is a marker trait indicating that a type *can* be safely moved. Pinning is necessary when the type's internal structure relies on its memory address remaining constant throughout its execution lifetime.

R19 — **Declarative macros (`macro_rules!`)** are pattern-matching macros that operate on token trees (like a sophisticated `match` statement). **Procedural macros** (derive, attribute, function-like) are complex macros written as separate Rust functions that take tokens, analyze them, and generate new Rust code. **Hygiene rules** prevent macro expansion from accidentally capturing or interfering with identifiers defined in the scope where the macro is used, ensuring that generated code is locally scoped and safe.

R20 — **Zero-cost abstractions** mean that high-level language features (like generics or iterators) compile down to machine code that is as fast as if the programmer had written the equivalent low-level code manually (e.g., C). This is achieved primarily through **monomorphization** (generics), where the compiler generates a specialized version of the code for every concrete type used, eliminating runtime overhead. **Trait static dispatch** (using generics) resolves method calls at compile time, avoiding the dynamic dispatch overhead associated with virtual tables, thus achieving C-like performance while retaining high-level ergonomic safety.
