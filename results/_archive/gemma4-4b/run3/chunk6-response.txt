**JS1**
The difference is scope and mutability. `var` is function-scoped and hoisted, allowing redeclaration. `let` is block-scoped and can be reassigned. `const` is block-scoped and must be initialized, and its binding cannot be reassigned (though object/array contents can be mutated). Hoisting is JavaScript's behavior of moving declarations (but not initializations) to the top of their scope during compilation.

**JS2**
The Event Loop is the mechanism that monitors the Call Stack and the various queues (Microtask and Macrotask) to determine which task to execute next, preventing blocking I/O operations in a single-threaded environment. The Call Stack executes synchronous code. When an asynchronous operation completes (e.g., a network request), its callback is placed in a queue. The Event Loop prioritizes the Microtask Queue (e.g., Promises, `queueMicrotask`) over the Macrotask Queue (e.g., `setTimeout`, I/O).

**JS3**
A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). Practically, it allows an inner function to access variables from its outer function even after the outer function has finished executing. The classic for loop closure bug occurs because the loop variable (`i`) is shared across all iterations; when the callbacks execute, `i` has already reached its final value. The fix is to use `let` in the loop declaration (`for (let i = 0; ...)`), which creates a new binding for `i` in each iteration.

**JS4**
A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. `async/await` is syntactic sugar built on top of Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()`, while with `async/await`, standard `try...catch` blocks are used. `Promise.all()` rejects immediately if *any* input promise rejects. `Promise.allSettled()` waits until *all* input promises have either fulfilled or rejected, returning an array describing the outcome of each.

**JS5**
An `interface` in TypeScript defines a contract—a shape that an object must adhere to. It is purely structural and is erased during compilation. A `type` alias creates a new type based on existing types, which can represent primitives, unions, tuples, or complex object shapes. Use `interface` for defining object shapes (especially when declaration merging is desired). Use `type` for unions, intersections, or aliasing complex types. Discriminated unions are unions where each member has a common, literal property (the "discriminant"). This allows TypeScript to narrow the type safely using a `switch` statement based on that property's value.

**JS6**
Prototypal inheritance means objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. `Object.create(proto)` creates a new object whose internal `[[Prototype]]` link points directly to the provided `proto` object. ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance model; they provide a cleaner, more familiar syntax (like classical inheritance) but fundamentally operate using prototypes under the hood.

**JS7**
The `this` keyword refers to the object that is currently executing the function. Its value is determined dynamically based on *how* the function is called. The 4 binding rules in priority order are: 1. `new` binding (constructor call), 2. Explicit binding (`.call()`, `.apply()`, `.bind()`), 3. Implicit binding (method call on an object), 4. Default binding (global object/undefined in strict mode). `bind()` returns a *new* function with the specified `this` context permanently bound. Yes, you can re-bind the returned function.

**JS8**
`WeakRef` holds a weak reference to an object, meaning it does not prevent the garbage collector (GC) from collecting the object if no other strong references exist. `FinalizationRegistry` allows you to register a callback function that will be executed *after* the associated object has been garbage collected. They are used for managing resources or performing cleanup tasks on objects that are about to be destroyed without creating memory leaks. WeakMap keys must be objects because the GC only tracks strong references; if a key were a primitive, the GC would treat it as a strong reference, preventing the associated object from being collected.

**JS9**
V8 optimizes JavaScript by compiling code into highly efficient machine code. **Hidden Classes** (or Maps) allow V8 to track the shape (structure) of objects. When an object's shape is consistent, V8 can use a hidden class to access properties directly via an offset, avoiding slow property lookups. **Inline Caching** stores the result of recent property lookups directly in the machine code, speeding up subsequent accesses. **Deoptimization** occurs when V8's assumptions (e.g., that an object will always have the same shape or type) are violated. Coding patterns that cause deoptimization include dynamic property addition/deletion, frequent type changes on the same variable, or heavy use of `eval()`.

**JS10**
Tree-shaking is a dead code elimination technique used by bundlers (like Webpack or Rollup) to eliminate unused exports from modules. It works by analyzing the static `import`/`export` structure of ES Modules. Since ES Modules are static, the bundler can trace exactly which exported functions/variables are actually imported and used. CommonJS (`require`/`module.exports`) is difficult to tree-shake because `require()` is a dynamic function call, meaning the bundler cannot statically determine which modules are being loaded at runtime.

**JS11**
`null` represents the intentional absence of any object value (a deliberate null assignment). `undefined` means a variable has been declared but has not yet been assigned a value, or a function did not explicitly return anything. `==` performs type coercion before comparison (e.g., `null == undefined` is true). `===` performs strict equality, requiring both value and type to match. Nullish coalescing (`??`) returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. Optional chaining (`?.`) allows safe navigation through nested object properties without throwing an error if an intermediate property is `null` or `undefined`.

**JS12**
`map()` creates a new array by applying a function to every element of the original array, returning a new array of the same length. `filter()` creates a new array containing only elements for which the provided testing function returns `true`. `reduce()` executes a reducer function on each element, resulting in a single output value. With an initial value, `reduce()` starts the accumulation process with that value, ensuring the function runs at least once, even on an empty array. `flatMap()` maps each element using a function and then flattens the result into a new array (equivalent to `map` followed by `flat(1)`). It is useful when mapping results might produce arrays themselves, and you want a single, flat result.

**JS13**
Template literals (backticks ``) allow for string interpolation and multi-line strings using `${expression}` syntax. Tagged templates allow a function to be executed before the template literal is converted to a string. The function receives the array of interpolated values and the array of literal strings. Example (HTML Escaping):
```javascript
const escapeHtml = (strings, ...values) => {
  let result = strings[0];
  values.forEach((value, i) => {
    const escaped = String(value).replace(/[&<>"']/g, function(match) {
      return { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' }[match];
    });
    result += escaped + strings[i + 1];
  });
  return result;
};
const safeHtml = escapeHtml`<h1>Hello ${'<script>alert("XSS")</script>'}</h1>`;
```

**JS14**
Destructuring is a syntax that allows you to unpack values from arrays or properties from objects into distinct variables. **Object destructuring** pulls properties out of an object (`const { name, age } = user;`). **Array destructuring** pulls elements out of an array (`const [first, second] = arr;`). Default values allow you to assign a fallback if a property/element is missing (`const { age = 30 } = user;`). Renaming allows you to assign the extracted value to a different variable name (`const { name: fullName } = user;`). The rest operator (`...`) collects all remaining, un-destructured properties/elements into a new array or object.

**JS15**
`for...in` iterates over the *enumerable properties* of an object, including inherited enumerable properties. `for...of` iterates over the *values* of an iterable object (like Arrays, Strings, Maps, Sets). You should avoid `for...in` on arrays because it iterates over keys (indices) as strings, and it can iterate over non-index properties added to the array object, leading to unpredictable iteration order and potential bugs.

**JS16**
Generics allow you to write reusable components that can work over a variety of types while maintaining type safety. **Generic Constraints (`extends`)** restrict the types that can be used with a generic parameter, ensuring they possess certain properties or implement certain interfaces (e.g., `function identity<T extends { id: number }>(arg: T): T`). **Conditional Types** allow for type-level branching based on a condition (e.g., `type IsString<T> = T extends string ? true : false;`). **`infer`** allows TypeScript to deduce a type from a pattern during conditional type checking (e.g., `type UnwrapArray<T> = T extends (infer U)[] ? U : T;`).

**JS17**
The module system defines how code dependencies are managed. **CommonJS** (Node.js standard) uses synchronous `require()` to load modules and `module.exports` to expose them. **ES Modules** (standardized JS) use static `import`/`export` syntax. Node.js supports both; files ending in `.mjs` or using `"type": "module"` in `package.json` use ES Modules. The `"type": "module"` field tells Node.js to treat `.js` files in that project as ES Modules, enabling native `import`/`export` syntax.

**JS18**
TypeScript uses a structural type system, meaning two types are considered compatible if they have the same structure (the same properties with compatible types), regardless of their declared name. **Excess property checks** ensure that an object passed to a function or assigned to a type does not contain properties that are not defined in that type. They apply when assigning an object literal to a type definition. `extends` enforces that the derived type *must* have all properties of the base type. `satisfies` checks that the object *conforms* to the type structure without forcing the object to *be* that type, allowing extra properties. Variance (`in`/`out`) describes how subtyping behaves with generics: `in` (contravariant) means the type accepts more inputs (e.g., function arguments); `out` (covariant) means the type produces more outputs (e.g., function return values).

**JS19**
`Proxy` allows you to intercept fundamental operations on an object (like property lookups, assignments, function calls) by wrapping the target object with a handler object. `Reflect` provides methods that mirror the built-in operations that a Proxy handler can intercept. For example, to validate input, you can intercept the `set` trap in the Proxy handler to check if the assigned value meets criteria before it modifies the target object. This is used for validation, logging, or creating reactive data stores.

**JS20**
`SharedArrayBuffer` provides a way to share raw binary data memory between different execution contexts (like Web Workers). `Atomics` provides methods to perform atomic operations (read-modify-write) on the integer values stored within a `SharedArrayBuffer`. This is crucial for synchronization in multi-threaded environments. Web Workers communicate by sharing this memory buffer. Ordering guarantees are provided by `Atomics` operations, ensuring that memory writes are visible across threads in a defined sequence. `Atomics.wait()` pauses a thread until a specific memory location changes, and `Atomics.notify()` wakes up waiting threads.

## Bash (20 questions)

**B1**
`$@` expands to all positional parameters, treating each parameter as a separate, quoted word. `*` expands to all positional parameters, treating them as a single, space-separated string. `"$@"` ensures that each argument is treated as a distinct, quoted argument, preserving spaces. `"$*"` treats all arguments as a single string, separated by the first character of the IFS (Internal Field Separator).

**B2**
`set -euo pipefail` sets strict error handling:
*   `-e` (errexit): Causes the script to exit immediately if any command exits with a non-zero status.
*   `-u` (nounset): Causes the script to exit immediately if an unset variable is used.
*   `-o pipefail`: Causes a pipeline to return a non-zero status if any command in the pipeline fails, not just the last one.

**B3**
`$(command)` (Command Substitution) executes the `command` and substitutes its standard output into the current command line. `command` executes the command directly. `((expression))` performs arithmetic evaluation within Bash. `expr` is an external utility that evaluates expressions, often requiring explicit spacing around operators.

**B4**
Process substitution (`<(command)`) runs a command and makes its standard output available as a temporary file path that the current shell can read from. This is useful when a command needs to be treated as a file argument. Example: `diff <(ls -1) <(ls -1 --sort=time)`. This compares the output of two separate `ls` commands as if they were two distinct files.

**B5**
The safest way is to use `find` combined with `while read -r` or `find ... -print0 | xargs -0`. `for f in $(ls)` is dangerous because `ls` outputs filenames separated by newlines and spaces. If a filename contains a space, `for` treats it as two separate items. Using `find ... -print0` outputs null-terminated strings, which `xargs -0` correctly interprets as single, complete filenames.

**B6**
A here document (`<<EOF`) reads multiple lines of input from standard input until it encounters the delimiter (`EOF`). A here string (`<<<`) passes a single string argument to a command via standard input. `<<-EOF` (here document with tab expansion) treats leading tabs in the document body as spaces, effectively stripping leading tabs from the input lines.

**B7**
1. `cmd > file 2>&1`: Redirects stdout (`> file`) first, then redirects stderr (`2`) to the same location as stdout (`&1`). Both stdout and stderr go to `file`.
2. `cmd 2>&1 > file`: Redirects stderr (`2`) to stdout (`&1`) *first*. Then, stdout (`> file`) is redirected. Since stderr was already pointed to stdout, both streams end up going to `file`.
3. `cmd &> file`: This is a shorthand (Bash 4+) that redirects both stdout and stderr to `file` simultaneously.
The first two produce the same result (both streams go to `file`) because the redirection order in the second case correctly sets up the target before redirecting stdout.

**B8**
```bash
lockfile="/tmp/my_script.lock"
function acquire_lock() {
    # Use mkdir for atomic creation of a directory
    if mkdir "$lockfile" 2>/dev/null; then
        echo "Lock acquired."
        return 0
    else
        echo "Lock already held."
        return 1
    fi
}
function release_lock() {
    rmdir "$lockfile" 2>/dev/null
}
trap release_lock EXIT SIGINT SIGTERM
acquire_lock
# ... script logic ...
```
`mkdir` is preferred because the operation is atomic at the filesystem level; only one process can successfully create a directory at a time. If the script is killed, the `trap release_lock EXIT` ensures the cleanup function runs, removing the directory.

**B9**
*   **Single Quotes (`'...'`):** Literal interpretation. No variable expansion or command substitution occurs.
*   **Double Quotes (`"..."`):** Allows variable expansion (`$var`) and command substitution (`$(cmd)`), but still respects escaping (`\"`).
*   **No Quotes:** Word splitting and pathname expansion occur. If a variable contains spaces, it will be split into multiple arguments.
Example: `VAR="Hello World"`.
`echo 'VAR'` -> `VAR`
`echo "VAR"` -> `Hello World`
`echo $VAR` -> `Hello World` (if unquoted, it's the same, but if it were `echo $VAR`, it would be split if IFS was default).

**B10**
*   `[ file ]`: The standard `test` command. It is POSIX compliant and generally safer for scripting.
*   `[[ file ]]`: Bash keyword expansion. It is more powerful, supports regex matching, and handles word splitting/globbing differently.
Checks:
*   File exists: `[ -f file ]` or `[[ -f file ]]`
*   Is a directory: `[ -d file ]` or `[[ -d file ]]`
*   Readable: `[ -r file ]` or `[[ -r file ]]`

**B11**
*   `$?`: The exit status of the most recently executed foreground command (0 for success, non-zero for failure).
*   `$$`: The Process ID (PID) of the current shell.
*   `$!`: The PID of the most recently backgrounded job.
*   `$#`: The number of positional arguments passed to the current script/function.
Use Case: `$?` to check if `grep` succeeded; `$$` to log the process ID for debugging; `$!` to monitor a background worker; `$#` to validate required arguments.

**B12**
Functions are defined using `name() { ... }` or `function name { ... }`. Both are functionally equivalent in modern Bash, but `name() {}` is generally preferred for brevity. To return values, functions typically print the result to stdout, which the caller captures using command substitution: `result=$(my_function arg1)`. Bash functions do not have a formal return type mechanism like C; they return an exit code (0-255) via `$?`.

**B13**
The `PATH` environment variable is a colon-separated list of directories that the shell searches sequentially when a command is executed. Bash resolves commands by checking if the command name matches a file name in any directory listed in `$PATH`. A **builtin command** is a command implemented directly within the shell itself (e.g., `cd`, `echo`). An **external command** is a separate executable file located in a directory listed in `$PATH` (e.g., `grep`, `ls`). You can check which is used by running `type command_name`.

**B14**
`trap` is a shell built-in command used to catch and handle signals sent to the shell or script. You set up handlers using `trap 'command' SIGNAL`.
*   `EXIT`: Runs when the script exits, regardless of how it exits.
*   `ERR`: Runs when a command exits with a non-zero status (if `set -e` is active).
*   `INT`: Interrupt signal (Ctrl+C).
*   `TERM`: Termination signal (sent by `kill`).
Execution order: Signals are generally handled in the order they are received, but `EXIT` is guaranteed to run upon termination. If multiple signals arrive rapidly, the shell processes them sequentially based on its internal signal handling logic.

**B15**
`xargs` takes standard input and builds and executes command lines from it. Command substitution (`$(cmd)`) executes a command and substitutes its output *as arguments* to another command. `xargs` is superior for large inputs because it batches arguments, preventing command line length limits. To handle spaces/newlines safely: `find . -type f -print0 | xargs -0 -I {} your_command {}`. `-0` tells `xargs` to expect null-terminated input. `-P N` specifies the number of parallel processes to run.

**B16**
**Arrays:** Indexed collections (0, 1, 2...). Declared: `my_array=(item1 item2)`. Append: `my_array+=("new_item")`. Iterate: `for item in "${my_array[@]}"; do ...`. Length: `${#my_array[@]}`.
**Associative Arrays (Maps):** Key-value collections. Declared: `declare -A my_map`. Set: `my_map[key]="value"`. Iterate: `for key in "${!my_map[@]}"; do echo "${my_map[$key]}"; done`. Length: `${#my_map[@]}`.
Difference: Arrays use integer indices; associative arrays use arbitrary string keys.

**B17**
A **subshell (`(...)`)** executes commands in a separate, child process. Any variables modified inside the subshell are lost when it exits, and its exit code is returned to the parent. A **group command (`{ ...; }`)** executes commands in the *current* shell environment. Variables modified inside persist in the parent shell. Piping into a `while` loop runs the loop body in a subshell (unless using process substitution), meaning any variable changes made inside the loop body are lost when the loop iteration finishes, as the subshell exits.

**B18**
Bash handles signals by mapping them to specific actions.
*   `SIGINT`: Interrupt (usually Ctrl+C).
*   `SIGTERM`: Termination request (graceful shutdown).
*   `SIGHUP`: Hangup (often used to tell a daemon to reload configuration).
*   `SIGKILL`: Immediate, uncatchable termination (cannot be ignored).
For graceful shutdown, use `trap` to catch `SIGTERM` and `SIGINT`. Inside the trap handler, you must explicitly signal background processes (e.g., using `kill %1`) to stop gracefully before the main script exits.

**B19**
```bash
# 1. Split the file into chunks (e.g., 1000 lines each)
split -l 1000 large_log.txt chunk_

# 2. Define the processing function
process_chunk() {
    local chunk_file="$1"
    # Simulate heavy processing
    grep "ERROR" "$chunk_file" | wc -l > "results_$(basename "$chunk_file").txt"
}

# 3. Process chunks in parallel
find . -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c 'process_chunk "$@"' _ {}

# 4. Merge results
cat results_*.txt > final_summary.txt
```
**Trade-offs:** Parallel processing drastically reduces wall-clock time for I/O-bound tasks. However, it increases CPU overhead, context switching costs, and complexity in synchronization. **Error Propagation:** To handle errors, the processing function must explicitly check the exit status of its internal commands (e.g., `if ! grep ...; then echo "Error processing $chunk_file" >&2; exit 1; fi`). The parent `xargs` job will only fail if the wrapper script exits non-zero.

**B20**
`exec` replaces the current shell process image with a new program, meaning the shell itself is replaced; it does not spawn a new child process. If you run a command normally, the shell remains active. `exec 3>file` opens file descriptor 3 and associates it with `file`. `exec 3>&-` closes file descriptor 3. A **coprocess** allows a parent shell to communicate with a child process using named pipes (FIFOs) for bidirectional communication, allowing the parent to monitor and interact with the child's execution state without blocking on standard I/O. Use a coprocess when you need continuous, structured, bidirectional communication with a long-running background task.

## PowerShell (20 questions)

**PS1**
`Write-Output` sends objects down the pipeline, allowing them to be processed by subsequent cmdlets. This is the standard, pipeline-friendly way to output data. `Write-Host` writes directly to the console host, bypassing the pipeline. This distinction matters because if you use `Write-Host`, the object is not passed to the next cmdlet, and it cannot be captured or manipulated by pipeline logic.

**PS2**
The PowerShell pipeline passes objects from one cmdlet to the next. `ForEach-Object` (alias `%`) is a cmdlet designed to process objects coming through the pipeline. The `foreach` statement is a language construct used for iterating over collections (arrays, lists) *within* a script block or function, not for processing pipeline input. Use `ForEach-Object` when processing pipeline streams; use `foreach` when iterating over a local collection.

**PS3**
`[PSCustomObject]` creates a lightweight, dynamic object with properties defined at runtime, ideal for structuring data returned from a function or script. `[hashtable]` is a dictionary-like collection where keys map to values. Use `[PSCustomObject]` when you need strongly typed, named properties for structured output. Use `[hashtable]` when you need a flexible, key-value lookup structure, often for configuration or dynamic data mapping. Conversion: `[PSCustomObject]@{Key = $hashtable.Value}` or `$hashtable | ConvertTo-Object`.

**PS4**
PowerShell distinguishes between **Terminating Errors** (which stop script execution unless handled) and **Non-Terminating Errors** (which are logged but allow execution to continue). `-ErrorAction` modifies how a specific cmdlet handles errors (e.g., `Stop`, `Continue`, `SilentlyContinue`). `$ErrorActionPreference` sets the default behavior for the entire session. `try/catch` allows you to explicitly trap terminating errors. If an error is non-terminating, `try/catch` might not catch it unless the preference is set to `Stop`.

**PS5**
Splatting (`@params`) is the practice of passing a hashtable containing parameter names as keys and values as values to a cmdlet. This allows you to pass a set of parameters dynamically, often loaded from a configuration file. Example: `$params = @{ -ComputerName "ServerA"; -Credential (Get-Credential) }` followed by `Invoke-Command @params`. This differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named parameters for the target cmdlet.

**PS6**
PowerShell Remoting allows management of remote systems. `Invoke-Command -ComputerName` executes a script block on a remote machine and returns the results to the local session. `Enter-PSSession` establishes an interactive, persistent connection to the remote machine, allowing you to run commands as if you were logged in. Both rely on **WinRM** (Windows Remote Management) for Windows targets. While SSH is used for Linux/Unix targets, WinRM is the native protocol for Windows PowerShell remoting.

**PS7**
The issue arises because PowerShell's pipeline implicitly treats the return value of a function as the object(s) it outputs. If the function returns an array (`$result += "one"`), that array is outputted. If the function returns nothing (or an empty array), it outputs nothing. When you assign the result to `$x`, `$x` becomes an array containing the output objects. If the function returns 0 items, `$x` is an empty array (`@()`). The correct pattern is to use `return` to explicitly output objects, or use `Write-Output` inside the function body to push objects to the pipeline.

**PS8**
A `[scriptblock]` is a block of code that can be passed as a parameter to a cmdlet or function; it is a callable unit of code. A function is a named, reusable block of code that can accept parameters and return values. You pass a scriptblock to a remote session using the `-ScriptBlock` parameter of `Invoke-Command`. The **double-hop problem** occurs when variables defined locally need to be accessed remotely; they are not automatically serialized. You solve this by using `Invoke-Command -ArgumentList` to explicitly pass variables into the remote scope, or by using `$using:` scope modifier.

**PS9**
`@()` creates an empty array object. `[array]` is a type accelerator used to explicitly cast a variable to an array type. To force a single result into an array, wrap it: `@[MyObject]`. Indexing into `$null` throws a terminating error. Indexing into an empty array (`@()`) returns `$null` without error.

**PS10**
*   `-eq`: Equality (case-insensitive).
*   `-ne`: Not equal (case-insensitive).
*   `-like`: Wildcard matching using `*` and `?` (case-insensitive by default).
*   `-match`: Regular expression matching (case-insensitive by default).
*   `-contains`: Checks if a collection contains a specific *value*.
*   `-in`: Checks if a value is present within a list of values.
Case-sensitive variants (`-ceq`, `-clike`, etc.) force the comparison to respect casing. `-contains` checks for membership in a collection; `-in` checks if a single item is present in a list.

**PS11**
A PowerShell module is a container for cmdlets, functions, variables, and types. A **script module (.psm1)** is a script file that defines the module's contents. A **manifest module (.psd1)** is a metadata file that describes the module (version, dependencies, required PowerShell version). A **binary module** contains compiled code (e.g., C# assemblies). `Import-Module` loads the module's definitions into the current session's scope, making its cmdlets and functions available.

**PS12**
String interpolation allows embedding expressions directly into a string using double quotes (`"`). The difference is that double quotes allow variable expansion and expression evaluation, while single quotes (`'...'`) treat the content literally. To include expressions, use `$()` syntax within double quotes: `"The value is $($myVariable * 2)"`. A here-string (`@"..."@`) is a multi-line string literal that preserves formatting and allows interpolation, similar to template literals in JS.

**PS13**
`Get-Member` returns the properties, methods, and events available on an object. It is used to inspect the structure of objects flowing through the pipeline. **Properties** are data fields (values). **Methods** are functions that can be called on the object. **NoteProperties** are properties that are not part of the object's core structure but are metadata. `Select-Object` selects specific properties to output. `Where-Object` filters the input objects based on a condition (a predicate).

**PS14**
PowerShell classes (v5+) allow object-oriented programming similar to C#. They differ from C# classes primarily because they are designed to integrate seamlessly with the .NET framework and PowerShell's dynamic nature. Limitations include that while they support inheritance, the integration with PowerShell's pipeline and dynamic typing can sometimes be less rigid than pure C#. Use a class when you need to model complex, stateful entities with defined behavior (e.g., a `User` object). Use a function when the logic is stateless or purely procedural.

**PS15**
`CmdletBinding()` enables advanced function features, allowing a function to behave like a full cmdlet (e.g., accepting common parameters like `-Verbose`, `-Debug`). `SupportsShouldProcess` allows the cmdlet to prompt the user before performing a destructive action (e.g., "Are you sure you want to delete X?"). `DefaultParameterSetName` sets the default set of parameters used. `ValueFromPipeline` allows the cmdlet to accept input objects from the pipeline and process them. The blocks execute in order: `Begin` (setup), `Process` (handles each pipeline object), `End` (cleanup).

**PS16**
The providers system allows PowerShell to treat different types of data sources (like the File System, Registry, or Environment Variables) as if they were objects accessible via the `Get-ChildItem` cmdlet. `Get-ChildItem` abstracts the underlying access mechanism. To access the registry like a file system, you use the `Registry` provider: `Get-ChildItem -Path "HKLM:\Software"`.

**PS17**
A **[runspace]** is an execution context that hosts PowerShell code. A **[runspacepool]** manages a collection of runspaces, allowing for efficient reuse of execution contexts. A **[powershell]** object represents the PowerShell engine itself. For parallel execution, `ForEach-Object -Parallel` (v7+) uses the runspace pool internally to execute script blocks concurrently. Manual runspace management is necessary for complex, long-running parallel tasks where you need fine-grained control over thread synchronization and resource allocation, whereas `-Parallel` is simpler for standard data parallelism.

**PS18**
PSScriptAnalyzer is a static code analysis tool that enforces coding standards and best practices in PowerShell scripts. It checks for adherence to rulesets (e.g., Microsoft's recommended style). **Rules** are specific checks (e.g., "Do not use global variables"). **Severity levels** (Error, Warning, Information) dictate how critical the violation is. **PS19**
The `$using:` scope allows variables defined in the parent scope to be accessed by child processes (like background jobs or `ForEach-Object -Parallel`) without needing to serialize them. `$args/-ArgumentList` is used to explicitly pass variables into a remote session or job. Serialization limits (CLIXML depth) restrict the complexity of objects that can be passed across process boundaries. Complex objects (like deeply nested custom classes) can hit these limits, causing serialization failures, requiring manual serialization (e.g., to JSON) before passing them.

**PS20**
Desired State Configuration (DSC) is a management framework that allows administrators to define the desired configuration state of a system (e.g., "IIS must be installed and running"). **Configurations** define the desired state. **Resources** are the specific components that enforce the state (e.g., the `Service` resource ensures a service is running). The **Local Configuration Manager (LCM)** is the engine that reads the configuration and ensures the system matches the desired state by applying or correcting resources. In modern IaC, DSC has largely been superseded by cloud-native tools like Terraform or Ansible, which offer broader orchestration capabilities.
