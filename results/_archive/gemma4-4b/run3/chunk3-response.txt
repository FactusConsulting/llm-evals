## OpenTofu / Terraform (20 questions)

T1 — Easy: What is the difference between tofu plan and tofu apply?
**T1:** `tofu plan` calculates the difference between the desired state defined in the configuration files and the current actual state recorded in the state file. It outputs an execution plan detailing exactly what actions (create, update, delete) will be taken, but it does not make any changes. `tofu apply` executes the plan, applying the calculated changes to the infrastructure, thus modifying the real-world resources and updating the state file.

T2 — Easy: What is state in OpenTofu, and why is remote state important?
**T2:** State is a mapping file that records the real-world infrastructure resources managed by OpenTofu, including their attributes, IDs, and dependencies. Remote state (e.g., stored in S3 or Azure Blob Storage) is crucial because it centralizes this state, allowing multiple team members or CI/CD pipelines to safely collaborate on the same infrastructure without overwriting each other's work, and it enables state locking to prevent concurrent modifications.

T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?
**T3:** `count` creates multiple instances of a resource based on an integer value (e.g., `count = 3`). All instances are treated identically, and they are referenced using an index (e.g., `resource.name[0]`). `for_each` creates multiple instances based on the elements of a map or a set of strings/objects. Each instance is referenced by a unique key (e.g., `resource.name["web1"]`). `for_each` is preferred when the instances need to be differentiated by a unique identifier (like a name or environment tag), as it makes the configuration more robust to reordering or deletion of specific instances.

T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
**T4:** OpenTofu detects this drift during the `tofu plan` phase. It performs a refresh operation, querying the cloud provider API to fetch the current actual state of the resource. It then compares this actual state against the state recorded in the state file and the desired state in the configuration. If a discrepancy is found, the plan will show a change (often an update) that would revert the manual change back to the configuration's definition, or it may flag the resource as needing manual intervention depending on the resource type and provider logic.

T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
**T5:**
```hcl
resource "aws_instance" "web_vm" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-0abcdef1234567890"
  instance_type = "t2.micro"

  tags = {
    Name = each.key
  }
}
```

T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
**T6:** An **output value** is a value explicitly defined and exported by a module or root module. A `terraform_remote_state` **data source** is used to read the state file of *another* existing infrastructure deployment (often managed by a different module or team) to retrieve specific attributes (like an ARN or ID). The recommended alternative for sharing configuration data *between* modules that are part of the same deployment is passing values via **input variables**. This is preferred because it keeps the dependency explicit in the configuration, avoids coupling modules to the state file structure, and maintains better modularity and testability.

T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
**T7:** The failure occurs because OpenTofu's dependency graph executes resources in parallel or sequentially based on explicit dependencies. When a `null_resource` uses a `remote-exec` provisioner, the output value (like the kubeconfig) is only populated *after* the provisioner successfully runs. If a dependent resource tries to read this output immediately, the value is still empty or null during the initial plan/apply phase. The fix is to use an **explicit dependency** using `depends_on` on the dependent resource, ensuring it only runs *after* the `null_resource` has completed its provisioning and populated its outputs.

T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
**T8:** `tofu import` allows you to bring existing, manually provisioned infrastructure resources under the management of OpenTofu without having to write the configuration code first. Its limitation is that it only imports the *current* state; it does not automatically generate the corresponding HCL configuration code. The import block (introduced in later versions) improves this by allowing the user to define the resource type and local name *alongside* the import address in the configuration file, which is cleaner and allows for immediate configuration refinement after the import.

T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
**T9:** A **variable** (input) is a placeholder defined in the configuration that allows users to pass dynamic values into the module or root configuration at runtime (e.g., `var.instance_count`). An **output** is a value explicitly exported by a module or resource that allows other parts of the configuration (or external users) to retrieve information generated during the deployment (e.g., the public IP address of a created VM).

T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
**T10:** A provider is a plugin that enables OpenTofu to interact with a specific API or service (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without running `tofu init` first, OpenTofu will fail immediately because it cannot locate or download the necessary provider plugins specified in the configuration. `tofu init` is responsible for initializing the working directory, downloading required providers, and setting up backend configurations.

T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
**T11:** The `.terraform.lock.hcl` file records the exact versions and checksums of every provider and module dependency used in the configuration. It should be committed to version control to ensure **reproducibility**. By locking dependencies, every team member and every CI/CD run uses the exact same provider binaries, preventing unexpected behavior caused by upstream provider updates or breaking changes.

T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
**T12:** `tofu destroy` tears down all infrastructure resources managed by the current state file. To target a single resource, you must use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web_vm["web1"]`).

T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
**T13:** A data source is a mechanism used to fetch information about existing infrastructure or external data that is *not* managed by the current OpenTofu configuration. Example: Using a `aws_ami` data source to look up the latest Amazon Machine Image ID for a specific region. You use it instead of a managed resource when you need to reference an existing resource (like a pre-existing VPC ID or a public DNS record) without OpenTofu being responsible for creating or managing its lifecycle.

T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
**T14:** **Variable blocks** (`variable "name" {}`) define inputs that must be provided externally to the module or root configuration. **Locals** (`locals { ... }`) define local, internal values derived from inputs, other locals, or resource attributes *within* the configuration itself. You should use locals when you need to perform complex transformations, calculations, or create reusable intermediate values (like constructing a complex map or joining strings) based on existing inputs, rather than exposing that intermediate logic as an external input variable.

T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
**T15:** The lifecycle block controls how OpenTofu manages resource replacement and destruction.
*   **`create_before_destroy`**: Ensures the new resource is created successfully *before* the old resource is destroyed. Use case: Database migrations or load balancer swaps where downtime must be zero.
*   **`prevent_destroy`**: Prevents the resource from being deleted via `tofu destroy` or `tofu apply` if the configuration attempts to remove it. Use case: Critical, manually configured resources that should never be accidentally deleted by automation.
*   **`ignore_changes`**: Tells OpenTofu to ignore specific attributes when calculating drift or applying changes. Use case: When an attribute (like a `last_modified_date` or a specific tag) is managed manually outside of OpenTofu, and you don't want OpenTofu to attempt to revert that manual change.

T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
**T16:** A `moved` block is a configuration directive used during refactoring. It explicitly tells OpenTofu how to map the old resource address to the new resource address. When you rename a resource or move it to a different module, the `moved` block ensures that OpenTofu understands the relationship between the old and new resource definitions. This allows OpenTofu to perform a state migration internally, preserving the resource's identity and preventing unnecessary destruction and recreation during the refactoring process.

T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
**T17:** OpenTofu builds a Directed Acyclic Graph (DAG) where nodes are resources and edges represent dependencies. **Implicit dependencies** are automatically inferred when one resource references an attribute of another (e.g., using `aws_vpc.main.id` in an `aws_subnet` resource). **Explicit dependencies** are declared using `depends_on`. Implicit dependencies allow OpenTofu to maximize parallelism by running independent resources concurrently. Using `depends_on` forces sequential execution, which reduces parallelism and increases plan time. It should be used sparingly, only when implicit dependencies are insufficient (e.g., when a resource needs to wait for a side effect of another resource, not just an attribute value).

T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
**T18:**
1.  **Modularization:** Break large configurations into smaller, focused modules. *Tradeoff: Increased complexity in managing module dependencies and state.*
2.  **Targeted Operations:** Use `tofu plan -target=...` to only plan changes for specific, smaller components. *Tradeoff: Requires careful management; risks missing dependencies if targets are too narrow.*
3.  **State Splitting/Workspaces:** Separate related resources into different state files or workspaces. *Tradeoff: Increases operational overhead; requires careful management of cross-state references.*
4.  **Provider Optimization/Caching:** Ensure providers are configured efficiently and leverage caching mechanisms where available. *Tradeoff: May require specific provider configuration changes and might not solve fundamental dependency bottlenecks.*

T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
**T19:** State locking ensures that only one operation (plan or apply) can modify the state file at any given time, preventing race conditions. It is typically implemented via a backend mechanism (like DynamoDB or S3 object locking). If a lock is not released (e.g., due to a crash), the state remains locked indefinitely. To manually break a lock, you use the backend-specific CLI command (e.g., `terraform force-unlock`). The risk is that if the lock is broken while another process is actively modifying the state, the state file can become corrupted, leading to unpredictable infrastructure state or data loss.

T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
**T20:**
1.  **Configure Backend:** Update the configuration to define the new S3 backend block, including the bucket name, region, and DynamoDB table name for locking.
2.  **Initialize:** Run `tofu init`. OpenTofu will detect the new backend configuration.
3.  **Migrate State:** Run `tofu state push` (or use the specific backend migration command if available/necessary). This uploads the contents of the local state file to the remote S3 bucket.
4.  **Verification:** Run `tofu plan`. If successful, OpenTofu will connect to the remote backend, read the state, and generate a plan based on the remote state, confirming the migration was successful and the lock mechanism is active. The local state file can then be safely deleted.

## Ansible (20 questions)

A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?
**A1:** A **Playbook** is a YAML file that defines a set of plays, which dictate the overall execution flow, target hosts, and which roles/tasks to run. A **Role** is a standardized, reusable structure that groups related tasks, handlers, variables, and templates into a cohesive unit (e.g., a `webserver` role). A **Task** is a specific action within a playbook or role, defining *what* needs to be done (e.g., `apt: name=nginx state=present`).

A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?
**A2:** `ansible_facts` is a dictionary containing gathered information about the target host (OS version, memory, network interfaces, etc.), collected by the `setup` module. To access the OS family, you would use the variable `ansible_facts['os_family']`.

A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
**A3:**
*   **`command`:** Executes a command directly. It does not process shell features like pipes (`|`), redirection (`>`), or environment variables. Use it for simple, non-shell-dependent commands.
*   **`shell`:** Executes a command through the system's shell (e.g., `/bin/sh`). It supports shell features like pipes and redirection. Use it when complex shell scripting logic is required.
*   **`raw`:** Executes a command directly on the remote machine without invoking the local shell interpreter. It is similar to `command` but is often used when you need to execute a command that is inherently non-shell-dependent but requires direct execution.

A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
**A4:** Idempotency means that running the same task multiple times yields the same result without causing unintended side effects after the first successful run. Ansible achieves this by using modules that check the current state before making changes.
*   **Idempotent Example:** `ansible.builtin.package: name=nginx state=present`. If Nginx is installed, Ansible does nothing; if not, it installs it.
*   **Non-Idempotent Example:** `ansible.builtin.command: echo "Hello" >> /tmp/log.txt`. Running this task repeatedly will append "Hello" to the file every time, changing the state each time.

A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.
**A5:**
```yaml
- name: Install htop based on OS family
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_facts['os_family'] == 'Debian' else 'htop' }}"
    state: present
  when: ansible_facts['os_family'] == 'Debian'
  become: yes
- name: Install EPEL and htop on RedHat
  ansible.builtin.package:
    name:
      - epel-release
      - htop
    state: present
  when: ansible_facts['os_family'] == 'RedHat'
  become: yes
```

A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
**A6:** Ansible resolves variables based on a strict precedence order, where later definitions override earlier ones. The general order (highest priority listed last) is:
1.  **Role Defaults:** Variables defined within the role structure.
2.  **Inventory Variables:** Variables defined in `group_vars` or `host_vars`.
3.  **Extra Variables:** Variables passed at runtime via the `-e` flag or `extra_vars` in the command line.
4.  **`set_fact`:** Variables set dynamically during playbook execution.
*Note: Variables defined directly in the playbook itself usually have higher precedence than role defaults.*

A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
**A7:** This requires using the `serial` keyword in the play definition combined with inventory grouping.
1.  **Inventory:** Define groups: `group_A` (3 nodes) and `group_B` (47 nodes).
2.  **Playbook Structure:**
    ```yaml
    - name: Deploy RKE2 Agents
      hosts: all
      serial: 3  # Process 3 hosts at a time
      tasks:
        # ... RKE2 installation tasks ...
    ```
3.  **Execution Flow:** Ansible will run the play against `group_A` (3 hosts). Once those 3 hosts complete successfully, Ansible will automatically proceed to the next batch of 3, until all 50 hosts are processed. If you needed a hard wait, you could use `wait_for` on the initial group, but `serial` handles the batching requirement directly.

A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
**A8:** `ansible-vault` is a utility that encrypts sensitive data (passwords, API keys) within Ansible files using strong encryption. To encrypt a single variable without encrypting the entire file, you must use the vault syntax directly on that variable definition within the YAML file, typically by prefixing it with the vault marker (e.g., `{{ vault_password }}` or using the vault file structure). The vault utility then handles the encryption/decryption based on the provided vault password.

A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
**A9:** An inventory file defines the hosts (servers) that Ansible will manage and groups them logically.
*   **Static Inventory:** A manually maintained file (INI or YAML format) where hosts and groups are hardcoded by the administrator.
*   **Dynamic Inventory:** A script or plugin that connects to a source (like AWS, Azure, or a CMDB) at runtime to generate the inventory list. This is preferred for large, ephemeral, or cloud-native environments as it ensures the inventory is always up-to-date.

A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?
**A10:**
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
**A11:** A handler is a special task that is only executed when explicitly notified by another task. Unlike a regular task, handlers are not run sequentially during the main task execution flow; they are queued. This prevents unnecessary restarts. A task triggers a handler using the `notify` keyword (e.g., `notify: restart nginx`). The handler itself must be defined in the `handlers:` section of the playbook.

A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
**A12:** The `ansible.cfg` file is a configuration file that controls the behavior of Ansible itself, overriding default settings. Common settings include:
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Defines the default SSH user to connect as.
3.  `host_key_checking`: Controls whether Ansible verifies the host keys during connection (e.g., `False` for automation environments).

A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
**A13:** The `register` keyword captures the entire return value (stdout, stderr, changed status, etc.) of a task into a variable. This variable can then be accessed and used in subsequent tasks using Jinja2 templating (e.g., `{{ registered_variable.stdout }}`).
Example: `register: web_status` followed by `debug: var: "{{ web_status.stdout }}"`.

A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
**A14:**
*   **`import_tasks`:** Reads the tasks from the specified file *before* the playbook execution begins. The imported tasks are loaded into the playbook's scope and are evaluated immediately.
*   **`include_tasks`:** Reads the tasks from the specified file *during* playbook execution. The tasks are executed dynamically when the `include_tasks` line is reached.
`include_tasks` is preferred when you need to conditionally evaluate tasks based on runtime variables, as it allows the playbook to decide whether to execute the included tasks at that specific point in the run.

A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
**A15:** Ansible Galaxy is a community repository where users share reusable Ansible roles and collections. To install roles/collections defined in a `requirements.yml` file, you use the command:
```bash
ansible-galaxy install -r requirements.yml
```
This command reads the file, which lists the required roles/collections and their specific versions, and downloads/installs them into the local Ansible path, making them available for use in playbooks.

A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
**A16:** Connection plugins define the protocol Ansible uses to communicate with the target host.
*   **`ssh`:** The default. Used for managing remote Linux/Unix servers over SSH.
*   **`local`:** Used when the target host is the Ansible control node itself. Useful for running local scripts or managing the control machine.
*   **`network_cli`:** Used for managing network devices (routers, switches) that typically use CLI protocols (like Telnet or SSH) but require specific parsing logic.
Use `network_cli` when managing infrastructure that is not a standard OS server.

A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
**A17:**
*   **`delegate_to`:** Allows a task to be executed on a host other than the one specified in the play's `hosts:` directive. You can delegate to a specific remote host, a group, or `localhost`.
*   **`run_once`:** When used with `delegate_to: localhost`, it ensures that the task runs only one time across the entire execution, even if multiple hosts are targeted.
**Example:** To gather all public IPs from 50 web servers and then write a summary report on the control node:
```yaml
- name: Gather IPs and write report
  hosts: webservers
  tasks:
    - name: Get IP address
      ansible.builtin.setup:
        gather_subset: [network]
      register: host_info
    - name: Write summary report (runs only once on localhost)
      ansible.builtin.lineinfile:
        path: /tmp/ip_summary.txt
        line: "IP: {{ host_info.ansible_default_ipv4.address }}"
      delegate_to: localhost
      run_once: true
```

A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
**A18:**
1.  **Increase `forks`:** Increase the number of parallel connections Ansible makes. *Tradeoff: Increased load on the control node and target hosts; requires sufficient network bandwidth.*
2.  **Pipelining:** Use pipelining (if supported by the connection plugin) to send multiple commands over a single SSH connection. *Tradeoff: Can complicate error handling and state management.*
3.  **Fact Caching:** Use the `ansible_facts_cache` module or configuration to cache gathered facts across multiple runs. *Tradeoff: Requires a shared, accessible cache location (e.g., Redis) and introduces a dependency on that cache service.*
4.  **Mitogen/Parallel Execution:** Use tools like Mitogen or custom parallel execution frameworks to run independent plays/roles concurrently. *Tradeoff: Significantly increases architectural complexity and requires careful dependency management to avoid race conditions.*

A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
**A19:** Jinja2 is the templating engine used by Ansible.
*   **`{{ variable }}` (Variable Expression):** Used to output the value of a variable.
*   **`{% statement %}` (Control Structure):** Used for logic, such as loops (`for`), conditionals (`if/else`), and assignments.
*   **`{# comment #}` (Comment):** Used to add comments that are completely stripped out during rendering.
**Snippet:**
```nginx
upstream backend_servers {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; # Health check target: {{ server.name }}
{% endfor %}
}
```

A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
**A20:**
1.  **Serial Batches:** Use `serial: 4` (or similar) in the play to ensure only 4 servers are updated at a time, maintaining service availability.
2.  **Pre-Task (Drain):** Before updating a batch, use a task to signal the Load Balancer (LB) to drain traffic from the target servers (e.g., updating an LB target group membership).
3.  **Deployment Task:** Run the application deployment tasks.
4.  **Health Check:** After deployment, use the `uri` module to perform a health check against the newly deployed service on the target server.
5.  **Post-Task (Register):** If the health check passes, use a task to register the server back into the LB target group.
6.  **Rollback Strategy:** Wrap the deployment and health check sequence in a `block`/`rescue` structure. If the health check fails, the `rescue` block executes, which contains the logic to immediately revert the changes (e.g., redeploy the old version or re-register the server to the old configuration) and potentially notify an alert system.
