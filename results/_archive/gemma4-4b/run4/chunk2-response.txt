**Kubernetes Questions**

K1 — A Deployment manages stateless applications, ensuring a specified number of identical replicas are running and handling updates via rolling updates. A StatefulSet manages stateful applications, providing stable, unique network identifiers and persistent storage for each pod, crucial for databases or message queues.

K2 — A ClusterIP Service exposes the service internally within the cluster using a stable virtual IP (ClusterIP). When traffic hits this IP, `kube-proxy` (running on every node) intercepts the traffic and uses iptables or IPVS rules to randomly select a healthy backend pod IP and port, forwarding the packet to that pod.

K3 — A **PersistentVolume (PV)** is a piece of storage in the cluster provisioned by an administrator or dynamically. It is the actual storage resource. A **PersistentVolumeClaim (PVC)** is a request for storage made by a user/pod, specifying required size and access mode. A **StorageClass** is a class of storage that defines the "how"—it dictates the underlying provisioner (e.g., AWS EBS, NFS) and the quality of service (e.g., fast SSD vs. slow HDD). They relate because a PVC requests storage, and the StorageClass tells the system *how* to fulfill that request by binding it to an available PV.

K4 — 1. **Check Pod Events:** Use `kubectl describe pod <name>` to check the `Events` section for specific failure reasons (e.g., ImagePullBackOff, CrashLoopBackOff reason). 2. **Check Logs:** Use `kubectl logs <name>` to see the application's stdout/stderr output to identify application-level errors causing the crash. 3. **Check Resource Limits:** Verify the pod's resource requests/limits against the node's available capacity to rule out OOMKilled or CPU throttling. 4. **Check Image/Configuration:** Verify the container image path is correct and that the ConfigMaps/Secrets mounted are valid and accessible.

K5 — CoreDNS acts as the cluster's internal DNS service, translating service names (e.g., `my-service.mynamespace.svc.cluster.local`) and pod IP addresses into resolvable names. If CoreDNS pods are down, DNS resolution fails entirely. Pods cannot resolve service names or external domain names, leading to connection timeouts and application failures within the cluster.

K6 — The scheduler uses a two-phase process: **Filtering** and **Scoring**.
1. **Filtering (Predicates):** The scheduler first filters out nodes that *cannot* run the pod based on hard constraints (e.g., resource availability, node selectors, taints/tolerations).
2. **Scoring (Priorities):** For the remaining viable nodes, it scores them based on soft preferences.
Specific factors considered include:
1. **Resource Utilization:** Preferring nodes with lower current utilization to balance load.
2. **Node Affinity/Anti-Affinity:** Placing pods near or far from specific nodes/other pods.
3. **Pod Topology Spread Constraints:** Distributing pods evenly across different failure domains (e.g., different availability zones).

K7 — **Scheduling:** Yes, the pod will likely be scheduled, provided the node has enough *available* capacity after accounting for existing requests. The scheduler primarily checks if `(3.5GB requested + 256Mi requested)` is less than `4GB total`. If the node has 512Mi free, it schedules.
**Runtime Behavior:** If the pod uses 600Mi, it will exceed its `limits.memory` (512Mi). The Kubelet on the node will enforce the limit, and the container runtime will terminate the process, resulting in an **OOMKilled** status, causing the pod to restart (potentially into CrashLoopBackOff).

K8 — 1. **External LB:** The external load balancer (e.g., AWS ELB) receives the external request and routes it to the IP address of the Ingress Controller node. 2. **Ingress Controller:** The NGINX controller receives the request, inspects the Ingress resource rules (host/path matching), and determines the target Service. 3. **Service:** The Ingress Controller forwards the request to the ClusterIP of the target Service. 4. **Endpoints:** The Service object consults the Endpoints object, which lists the actual IP addresses of the healthy backend pods. 5. **kube-proxy/iptables:** `kube-proxy` uses iptables rules on the node to intercept traffic destined for the Service ClusterIP and redirects it directly to one of the healthy backend pod IPs.

K9 — A NetworkPolicy defines rules that specify how groups of pods are allowed to communicate with each other and with external network endpoints. If no NetworkPolicy exists in a namespace, the default behavior is **"allow all"** ingress and egress traffic. When you apply a NetworkPolicy that selects certain pods, the default behavior changes to **"deny all"** ingress/egress for those selected pods, unless explicitly allowed by another policy.

K10 — **RollingUpdate:** Gradually replaces old versions of pods with new versions, ensuring a minimum number of available replicas are always running during the transition. It provides zero-downtime updates. **Recreate:** Terminates all existing pods of the deployment, waits for them to terminate, and then creates all new pods. You would choose Recreate only when the application state is entirely ephemeral, or when the change is so fundamental (e.g., changing the underlying OS image) that a graceful transition is impossible or undesirable.

K11 — A namespace is a mechanism for partitioning cluster resources across multiple virtual clusters within a single physical cluster. It provides scope isolation for names, policies, and resource quotas. Default namespaces include: `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

K12 — `kubectl describe pod <name>` provides a detailed status report, including: 1. **Events:** A chronological log of actions taken on the pod (scheduling, pulling images, errors). 2. **Container Status:** Detailed status of each container (e.g., restart count, last state). 3. **Resource Requests/Limits:** Explicitly lists the requested and limited resources for the pod.

K13 — A ConfigMap is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) that can be injected into pods.
Methods to consume it: 1. **Environment Variables:** Mounting the ConfigMap as environment variables in the pod spec. 2. **Volume Mounts:** Mounting the ConfigMap as a file volume inside the container filesystem.

K14 — **ClusterIP:** Exposes the Service only internally within the cluster using a virtual IP. **NodePort:** Exposes the Service on a specific port on *every* node's IP address, allowing external access via `<NodeIP>:<NodePort>`. **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes traffic to the Service's nodes.

K15 — A DaemonSet ensures that a copy of a pod runs on *every* (or a specified subset of) eligible node in the cluster. You use it when you need a service that must run locally on every node, such as log collectors (Fluentd), monitoring agents (Prometheus Node Exporter), or network plugins. A Deployment is used for stateless applications that scale horizontally across a defined set of nodes.

K16 — **Taints** repel pods from a node (e.g., `dedicated=gpu:NoSchedule`). **Tolerations** are applied to pods to allow them to be scheduled onto nodes that have matching taints. **Node Affinity** is a scheduling preference that dictates *where* a pod *should* run (e.g., "must run on nodes labeled 'region: us-west'"). Taints/Tolerations are about *exclusion* based on node state; Affinity is about *preference* based on node labels.
*Use Case (Taint/Toleration):* Isolating a GPU node for ML workloads.
*Use Case (Affinity):* Ensuring all database replicas run within the same availability zone.

K17 — A Kubernetes Operator is a method of packaging, deploying, and managing a complex application (like a database cluster) using custom controllers. It differs from a standard controller because it encapsulates *domain-specific knowledge* (e.g., "if the primary database fails, promote the replica and update the connection string"). The Operator pattern solves the problem of managing complex, stateful applications that require sophisticated, human-like operational logic beyond simple scaling or self-healing.

K18 — Kubernetes uses **Raft** (a consensus algorithm built on Paxos) for etcd consistency. Raft ensures that a majority (quorum) of nodes agree on the state before any write is committed. If the quorum is lost (e.g., 2 out of 3 nodes fail), the cluster enters a read-only or unavailable state because it cannot guarantee data consistency. Recovery from 2/3 permanent loss is impossible; the cluster requires at least a majority (2/3) to function. If 2 are lost, the remaining 1 cannot form a quorum.

K19 — RBAC controls authorization—what users/service accounts can do. **Role** defines permissions (e.g., `get`, `list`) within a specific namespace. **ClusterRole** defines permissions cluster-wide. **RoleBinding** binds a Role to a subject (user/SA) within a namespace. **ClusterRoleBinding** binds a ClusterRole to a subject cluster-wide.
*Manifests for read-only pod/log access in `my-namespace`:*
```yaml
# 1. Define the Role (Permissions)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-namespace
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# 2. Bind the Role to a User/Group (Subject)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-only-binding
  namespace: my-namespace
subjects:
- kind: User
  name: developer-user # Replace with actual user identity
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

K20 — `ndots` specifies the number of DNS dots (periods) that the resolver should follow before giving up on an external domain query. If `ndots` is too high (e.g., 5), and the pod tries to resolve `api.example.com`, the resolver might first try to resolve the entire FQDN (`api.example.com`) locally within the cluster's internal DNS servers, which will fail, causing unnecessary latency before it falls back to external resolution. To fix this, you use `dnsConfig` in the pod spec to set `ndots: 1`, instructing the pod to only try resolving the domain locally if it contains at least one dot, forcing faster external lookups.

**Development Questions**

D1 — **git merge** integrates changes by creating a new "merge commit" that combines the histories of two branches. **git rebase** rewrites history by moving the entire feature branch onto the tip of the target branch, creating a linear history. You should avoid rebasing commits that have already been pushed to a shared, public repository, as rewriting shared history forces collaborators to perform complex recovery operations.

D2 — **TCP (Transmission Control Protocol)** is connection-oriented, reliable, and guarantees ordered delivery via acknowledgments and retransmissions. Protocols using TCP: HTTP/HTTPS, FTP. **UDP (User Datagram Protocol)** is connectionless, unreliable, and sends packets without guarantees of delivery or order. Protocols using UDP: DNS, NTP, VoIP.

D3 — A race condition occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads accessing and modifying shared data.
*Example:* Two threads simultaneously check if a bank account balance is greater than $100. Both threads see $150. Both threads proceed to withdraw $100. Both succeed, resulting in a final balance of $50, even though only one withdrawal should have been allowed.

D4 — **Symmetric encryption** uses a single, shared secret key for both encryption and decryption (e.g., AES). **Asymmetric encryption** uses a pair of keys: a public key (for encryption, shared widely) and a private key (for decryption, kept secret).
*TLS Usage:* Asymmetric encryption (RSA/ECC) is used during the initial handshake to securely exchange a temporary, random **symmetric session key**. Once the session key is established, all subsequent bulk data transfer is encrypted using the much faster symmetric algorithm.

D5 — A container image layer is a read-only, immutable filesystem layer created when a command in a Dockerfile executes. Each instruction (e.g., `RUN`, `COPY`) creates a new layer on top of the previous one. Layer caching is crucial: if a layer's instruction and context have not changed since the last build, Docker reuses the cached layer, drastically speeding up subsequent builds. Best practice dictates placing stable, infrequently changing instructions (like `FROM` or installing base dependencies) at the top, and volatile instructions (like `COPY . .`) near the bottom to maximize cache hits.

D6 — 1. **Check Application Logs:** Look for specific exceptions, database connection timeouts, or internal service errors (the root cause). 2. **Check Resource Utilization:** Monitor CPU/Memory usage on the application pods; high utilization can lead to throttling or OOMKills, causing 503s. 3. **Check Dependencies/Downstream Services:** Verify that all services the API relies on (DB, cache, other microservices) are healthy and responsive. 4. **Check Ingress/Service Mesh:** Verify the ingress controller and service routing rules are correct and not overloaded or misconfigured.

D7 — The **CAP Theorem** states that a distributed data store can only simultaneously guarantee two out of three properties: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee of correctness), and **Partition Tolerance** (the system continues to operate despite network failures between nodes).
*CP Example:* Traditional relational databases (e.g., PostgreSQL cluster with synchronous replication). If a network partition occurs, the system sacrifices availability to ensure consistency.
*AP Example:* Cassandra or DynamoDB. If a network partition occurs, the system remains available, allowing writes/reads, but data might temporarily diverge until the partition heals.

D8 — **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) allocated to an *existing* instance. **Horizontal Scaling (Scaling Out):** Adding *more* instances (replicas) of the application behind a load balancer.
Architectural patterns enabling horizontal scaling include: **Statelessness** (ensuring no session data is tied to a specific instance), **Microservices Architecture** (breaking the monolith into independent, scalable units), and **Load Balancing** (distributing traffic evenly across replicas).

D9 — An environment variable is a dynamic named value that can affect the way running processes behave on a computer. On Linux, you set a persistent variable by adding the assignment command (e.g., `export MY_VAR="value"`) to your shell's startup file, typically `~/.bashrc` or `~/.zshrc`, and then sourcing the file (`source ~/.bashrc`).

D10 — **JSON (JavaScript Object Notation)** is a lightweight data-interchange format using key-value pairs and arrays. **YAML (YAML Ain't Markup Language)** is a human-readable data serialization standard that uses indentation to denote structure.
*Advantage JSON:* Universally supported by nearly all programming languages and APIs.
*Advantage YAML:* Highly readable and concise for configuration files (like Kubernetes manifests).

D11 — A REST API (Representational State Transfer) is an architectural style for designing networked applications, typically using HTTP methods to perform CRUD operations on resources.
*GET:* Retrieves a resource or a collection of resources (Read).
*POST:* Submits data to a specified resource, often creating a new resource (Create).
*PUT:* Replaces an entire existing resource with new data (Update/Replace).
*DELETE:* Removes a specified resource (Delete).

D12 — Version pinning is the practice of explicitly specifying the exact version of a dependency (e.g., `library@1.2.3`) rather than using a broad range (e.g., `library@^1.0.0`). It is vital for reproducible builds because it guarantees that the build environment will use the exact same code, preventing unexpected runtime bugs caused by upstream library authors making breaking changes in minor or patch releases.

D13 — **Compiled Language:** Source code is translated directly into machine code (binary) by a compiler *before* execution. Examples: C++, Go, Rust. **Interpreted Language:** Source code is read and executed line-by-line at runtime by an interpreter. Examples: Python, JavaScript.

D14 — A **Reverse Proxy** sits in front of one or more web servers, intercepting client requests. It forwards the request to the appropriate backend server and returns the response to the client. It hides the backend infrastructure. A **Forward Proxy** sits in front of a client, acting as an intermediary to forward requests *from* the client to the internet, often used for anonymity or caching.
*Common Servers:* NGINX (used for load balancing, SSL termination, caching) and HAProxy (used for high-performance TCP/HTTP load balancing).

D15 — A deadlock is a state where two or more competing actions are each waiting for the other to finish, resulting in a permanent standstill.
The four Coffman conditions required for a deadlock are:
1. **Mutual Exclusion:** Resources cannot be shared; only one process can use a resource at a time.
2. **Hold and Wait:** A process is holding at least one resource while waiting to acquire additional resources held by other processes.
3. **No Preemption:** A resource cannot be forcibly taken away from a process; it must be released voluntarily.
4. **Circular Wait:** A set of processes exists where each process is waiting for a resource held by the next process in the set.

D16 — **Eventual Consistency** is a consistency model where, if no new updates are made to a given data item, all reads will eventually return the last written value, though not necessarily immediately after the write. Cassandra handles read-after-write consistency by allowing tunable consistency levels (e.g., `QUORUM`). A write operation might require acknowledgment from $W$ replicas, and a read operation might require responses from $R$ replicas. If $W + R > N$ (where $N$ is the replication factor), strong consistency is achieved. Tunable levels include `ONE` (fastest, least consistent) and `ALL` (slowest, most consistent).

D17 — **mTLS (Mutual TLS)** requires both the client and the server to authenticate each other using digital certificates. The handshake involves: 1. Client connects to Server. 2. Server sends its certificate to the Client. 3. Client verifies the Server's certificate against its trusted CAs. 4. Server requests the Client's certificate. 5. Client sends its certificate to the Server. 6. Server verifies the Client's certificate against its trusted CAs. 7. Both parties exchange keys and establish a secure, authenticated session. mTLS is commonly used in service meshes (like Istio) for securing east-west traffic between microservices.

D18 — A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an array.
*Collision Resolution:*
1. **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hash to that index.
2. **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array (e.g., linear probing, quadratic probing).
*Time Complexity:*
*   Average Case (Good Hash Function): Insertion, Lookup, Deletion are $O(1)$.
*   Worst Case (All keys hash to one bucket): Insertion, Lookup, Deletion are $O(n)$.

D19 — The Circuit Breaker pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing microservice), thereby preventing resource exhaustion and cascading failures across the system.
*States:*
1. **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the breaker trips to Open.
2. **Open:** Requests are immediately rejected without attempting the call, failing fast. After a timeout, it transitions to Half-Open.
3. **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker closes; if they fail, it returns to Open.
*Relation to Retries:* Circuit breakers act as a high-level safety net. Retries and exponential backoff are low-level strategies used *within* the closed state to handle transient errors, but the circuit breaker prevents the system from hammering a service that is fundamentally down.

D20 — **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data resource *before* the transaction reads or modifies it, preventing other transactions from accessing it until the lock is released. (Example: `SELECT ... FOR UPDATE` in SQL). Choose this when data integrity is paramount and contention is expected.
**Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read (often using version numbers or timestamps). If a conflict is detected, the transaction is rolled back and retried. Choose this when contention is low and locking overhead is undesirable.
