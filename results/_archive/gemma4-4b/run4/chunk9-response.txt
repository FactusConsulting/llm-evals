**SC1-A**
The pods are failing because the Kubernetes cluster upgrade enforced the **Restricted Pod Security Standard (PSS)**, which is stricter than the previous Baseline. The Restricted PSS mandates that containers must run as a non-root user. The failing pods have `securityContext.runAsNonRoot: true`, which signals the intent to run as non-root, but they lack an explicit `securityContext.runAsUser` directive. When the container image (`cgr.dev/chainguard/static:latest`) defaults its `USER` instruction to `root` in its Dockerfile, the container runtime attempts to run the process as root. The Kubernetes admission controller, enforcing the Restricted PSS, detects this conflict (attempting to run as root when non-root is required) and prevents the pod from starting, resulting in a `CrashLoopBackOff` state.

**SC1-C**
**Immediate Fix:** Update the failing microservice Dockerfiles to explicitly set the user ID matching the non-root requirement, e.g., `USER 1000` or `USER nonrootuser`.
**Manifest Change:** Ensure the Kubernetes deployment manifests explicitly define `securityContext.runAsUser` in the container spec, overriding the image default, e.g., `securityContext: { runAsNonRoot: true, runAsUser: 1000 }`.
**CI Pipeline Gate:** Implement a static analysis step (e.g., using Trivy or Hadolint) in the CI pipeline that scans the Dockerfile for the `USER` instruction and verifies that it is either explicitly set to a non-root UID or that the base image is configured to default to a non-root user.
**Zero-Downtime Rollout:** Use a rolling update strategy (`maxSurge: 25%`, `maxUnavailable: 25%`) in the Kubernetes Deployment manifest. The new image/manifest will be deployed gradually, allowing old, healthy pods to terminate only after the new pods pass readiness and liveness checks.

**SC2-A**
The stale data issue arises because the promotion of the read replica was likely **asynchronous**. PostgreSQL streaming replication ships Write-Ahead Logs (WAL) from the primary to the replica. If the replica was lagging (even slightly) when promoted, any transactions committed on the old primary but not yet shipped/applied to the replica will be lost.
**Replication Lag Implication:** Promoting a replica means it becomes the source of truth. If it was behind, it lacks the most recent committed transactions.
**WAL Shipping:** PostgreSQL uses WAL shipping to stream transaction logs. In asynchronous replication, the primary commits the transaction and immediately acknowledges it to the client *before* confirming the WAL has been received and applied by the replica.
**Data Loss Scenarios:** Data loss occurs if the primary fails before the WAL segment containing the latest committed transactions has been successfully transferred and applied to the replica.
**Quantifying Data Loss:** Check the `pg_stat_replication` view on the *old* primary (if accessible) to see the `flush_lsn` and `replay_lsn` difference, or check the replica's `pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()` against the primary's current LSN.

**SC2-B**

**SC5-C**
**Architectural Solution:**
1.  **CQRS (Command Query Responsibility Segregation):** Separate the read path from the write/reconciliation path. The reconciliation job (write/update) runs against the primary database. The checkout service (read) queries a dedicated, highly optimized read replica or a materialized view optimized for fast reads.
2.  **Read Replica Usage:** Schedule the heavy inventory reconciliation CronJob to run against the dedicated read replica, preventing lock contention on the primary database used by live transactions.
3.  **Bulkhead Isolation:** Implement connection pool isolation. Use separate connection pools in the `checkout-service` for different downstream services (e.g., one pool for Inventory, one for Payment). If the Inventory pool exhausts its connections due to contention, it will only affect the inventory calls, not the payment calls.
4.  **CronJob Scheduling:** Adjust the CronJob to run during off-peak hours (e.g., 03:00 UTC) when transaction volume is lowest, minimizing impact.
5.  **Resource Governance:**
    *   **PodDisruptionBudgets (PDB):** Define a PDB for the serving pods of `inventory-service` to ensure that during voluntary disruptions (like node maintenance), at least $N$ replicas remain available, preventing service degradation.
    *   **Resource Quotas:** Apply a `ResourceQuota` to the namespace hosting the CronJob. This quota limits the total CPU/Memory the CronJob can consume, preventing it from starving the serving pods of the same service.

**SC6-A**
**Identity and Access Layer Design:**
**Machine Identity (Workloads):**
*   **SPIFFE/SPIRE:** This is the core solution. SPIRE agents run on every host/node in all environments (VMware, AWS, Azure). They attest the workload's identity (e.g., Kubernetes Service Account, EC2 Instance Role, VM tag) and issue a verifiable X.509 certificate (SVID) conforming to the SPIFFE standard.
*   **AWS IAM Roles:** SPIRE can be configured to trust AWS IAM roles. An EC2 instance assumes its role, and SPIRE validates this assumption to issue a workload identity.
*   **Azure Managed Identities:** SPIRE agents can integrate with Azure AD to attest the identity of workloads running on Azure VMs, issuing SPIFFE IDs.
*   **On-Prem PKI:** The on-prem environment uses its existing PKI, which is integrated into the SPIRE server as a trusted issuer.
**Federation:**
The SPIRE Server acts as the central trust anchor. Workloads in AWS, Azure, and On-Prem all authenticate to the central SPIRE Server using their native identity mechanisms (IAM, Managed Identity, PKI). The SPIRE Server then issues a standardized SPIFFE ID (e.g., `spiffe://mycorp.com/aws/service-a`). Services communicate using mutual TLS (mTLS) authenticated by these SPIFFE certificates, allowing a service in AWS to present its SPIFFE ID to an on-prem service, which validates the ID against the central SPIRE trust bundle, achieving identity-based trust regardless of network location.

**SC7-A**
**Drift Source Analysis:**
1.  **Manual `tofu apply` from Laptops:** This bypasses the centralized CI/CD pipeline and the state locking mechanism. The engineer applies changes directly to the remote infrastructure, modifying the actual state without updating the source-of-truth Git repository or the state file.
2.  **Diverged Helm Values Files:** When values files are edited manually outside of Git (e.g., `helm upgrade --set`), the configuration in the cluster diverges from the configuration defined in the Git repository.
3.  **Direct `kubectl edit`:** This is the most dangerous form of drift. It modifies the live Kubernetes object (e.g., ConfigMap) directly in the API server. The Git repository and the CI/CD system are unaware of this change, leading to configuration drift between the desired state (Git) and the actual state (Cluster).

**Dangers of No State Locking:**
If two engineers run `tofu apply` simultaneously, both will read the same current state file. Both will calculate their desired changes based on that old state. When the first engineer writes their changes, the second engineer's subsequent write will overwrite the first engineer's changes, leading to **lost updates** and unpredictable infrastructure state.

**Diagnosis:**
1.  **Prometheus OOM-Killed:** **Root Cause:** High Cardinality. Each unique combination of metric name and label values creates a new time series. With 8.2 million series, the memory required to store and process these labels (especially if labels are dynamic, like request IDs) exceeds the 64GB limit.
    *   **Confirmation:** Query `sum(rate(up{job="prometheus"}[5m]))` and examine the Prometheus metrics endpoint for internal memory usage metrics.
    *   **High Cardinality Identification:** Use the Prometheus API endpoint `/api/v1/label/__name__/values` to list all unique label values for a given metric.
2.  **Loki Drops:** **Root Cause:** Ingester Overload/Backpressure. The ingestion rate exceeds the capacity of the ingester pods, causing the queue to fill and drop logs.
    *   **Confirmation:** Check Loki ingester metrics for `dropped_logs_total` and monitor the queue depth metric.
3.  **Tempo Timeouts:** **Root Cause:** Backend/Compactor Lag. Tempo relies on the backend (S3) and the Thanos compactor. If the compactor is 3 days behind, older traces are not indexed or available for querying, leading to timeouts.
    *   **Confirmation:** Check Thanos component metrics for compaction lag time and S3 upload latency.
4.  **Thanos Compactor Lag:** **Root Cause:** I/O or CPU Saturation. Compaction is an intensive I/O and CPU operation. The sheer volume (14TB growing at 500GB/week) is overwhelming the dedicated cluster's resources.
    *   **Confirmation:** Monitor the CPU/Disk I/O utilization of the Thanos compactor pods.

**SC8-C**
**Redesigned Observability Architecture:**
1.  **Metrics Backend (Mimir/VictoriaMetrics):** Replace Prometheus with **Mimir** (or VictoriaMetrics). Mimir is designed for massive scale, offering horizontally scalable, multi-tenant storage and query capabilities. It decouples the ingestion/query layer from the storage layer, allowing it to handle 50 million series efficiently.
2.  **Loki Deployment (Microservices Mode):** Deploy Loki in microservices mode. Instead of one large ingester, use smaller, dedicated ingester pods per team or per service. This limits the blast radius of ingestion failures and allows for targeted scaling.
3.  **Tempo Backend:** Switch Tempo to use a dedicated, highly available, S3-backed storage backend (e.g., using the Thanos/Mimir storage layer). This offloads the trace storage from the local cluster resources, allowing Tempo to focus purely on indexing and querying.
4.  **Cardinality Governance:**
    *   **Recording Rules:** Implement aggressive recording rules in Mimir to pre-aggregate high-cardinality metrics into lower-cardinality summaries (e.g., instead of tracking every unique user ID request, track `count_by_user_type`).
    *   **Relabeling Configs:** Use Mimir's configuration to enforce strict relabeling rules, dropping or aggregating labels that are deemed too high-cardinality (e.g., dropping request IDs unless explicitly required for debugging).
5.  **Chargeback Model:** Implement a **Tagging/Labeling** system tied to the Mimir/Loki ingestion pipeline. Every metric/log must be tagged with a `team_id`. Mimir/Loki can then expose metrics like `total_series_per_team`. A separate billing service queries these metrics, calculates the cost based on the volume of data ingested by each `team_id`, and charges the respective team.

**SC9-C**
**Defense-in-Depth Architecture:**
1.  **Authentication Migration:**
    *   **API Gateway:** Introduce an API Gateway (e.g., AWS API Gateway or Kong) in front of the ALB. This gateway handles the initial request validation, rate limiting, and authentication token validation *before* the request hits the application.
    *   **Header Migration:** Update all clients to pass credentials via the `Authorization` header.
    *   **Key Rotation:** Immediately revoke all existing API keys and issue new, short-lived tokens.
2.  **OAuth2/JWT Implementation:** Replace static API keys with OAuth2 flows. The API Gateway validates the incoming JWT signature and expiration time. The JWT payload contains the user/client identity, which is then passed to the Django application for fine-grained authorization checks (BOLA).
3.  **Auditing:** Enable **CloudTrail Data Events** for the underlying database (RDS). This logs every read/write operation, providing an immutable audit trail of who accessed what data, which is critical for compliance.
4.  **Field-Level Encryption (FLE):** For PII fields (e.g., SSN, internal notes), implement FLE at the application layer *before* writing to the database. The application encrypts the data using a KMS-managed key. The database stores the ciphertext, and only the application, possessing the decryption key, can read the plaintext.

**Migration Strategy (API Key $\rightarrow$ OAuth2):**
1.  **Dual Support:** Deploy the new API Gateway/OAuth2 flow alongside the existing ALB/API Key flow.
2.  **Phased Rollout:** For a defined period, the API Gateway accepts *both* API Key authentication (for legacy consumers) and JWT authentication (for new consumers).
3.  **Deprecation:** Announce a deprecation timeline. Once the majority of consumers have migrated to OAuth2, the API Gateway is configured to reject all requests using the old API key mechanism.

**SC10-A**
**Multi-Cluster Architecture Comparison:**

| Feature | Active-Passive (Velero) | Active-Active (Service Mesh) |
| :--- | :--- | :--- |
| **RPO/RTO Feasibility** | **RPO:** Dependent on backup frequency (e.g., 15 min). **RTO:** Dependent on restore time (can be slow for 200TB). | **RPO:** Near Zero (Continuous replication). **RTO:** Near Zero (Traffic shift). |
| **Latency Impact (12ms)** | Minimal impact on backup/restore process. | Minimal impact on synchronous replication traffic. |
| **200TB MinIO** | Requires a massive, asynchronous backup/restore job, potentially exceeding the 15-min RPO if the restore is slow. | Requires synchronous or near-synchronous cross-region replication setup for MinIO. |
| **PostgreSQL/Redis/RabbitMQ** | Requires continuous streaming replication (Patroni/Sentinel) to maintain state synchronization. | Requires multi-master or active-active clustering (e.g., Patroni with multi-site configuration). |

**Recommendation:** **Active-Active with a Service Mesh (Istio/Cilium Cluster Mesh)** is the only architecture that reliably meets the RPO of 15 minutes and RTO of 1 hour for all stateful components, especially given the 200TB data volume.

**Replication Strategy:**
*   **PostgreSQL:** Patroni configured for synchronous replication across Chicago (Primary) and Dallas (Standby).
*   **Redis:** Redis Sentinel configured with quorum across both sites, enabling automatic failover.
*   **RabbitMQ:** Use RabbitMQ Federation or Mirroring to ensure queues are replicated between the clusters.
*   **MinIO:** Implement MinIO's built-in **Object Replication** feature, configured to asynchronously replicate buckets from the Chicago site to the Dallas site.

**SC10-C**
**Automated Failover Orchestration Sequence:**

1.  **Failure Detection:**
    *   **Site Down:** Global monitoring (e.g., synthetic transactions, external health checks) detects failure of the Chicago site's ingress/load balancer.
    *   **Component Failure:** Patroni's DCS (etcd) detects the primary node is unreachable.
2.  **Patroni Promotion:** Patroni in Dallas detects the primary failure, initiates an election, and promotes the Dallas standby to the new primary. This is automatic via Patroni/etcd.
3.  **Redis Sentinel Failover:** Sentinel detects the primary Redis instance is down and automatically promotes the Dallas replica to primary.
4.  **RabbitMQ Mirroring:** The cluster manager (or manual trigger) ensures that queue mirroring is active, and the Dallas cluster takes over as the authoritative mirror.
5.  **MinIO Replication Catch-up:** The application layer or a dedicated script verifies that the Dallas MinIO site has successfully caught up on all replicated objects from Chicago before traffic is routed.
6.  **DNS Failover (GSLB):** The GSLB service (e.g., Route53 with health checks) detects the Chicago endpoint failure and automatically shifts 100% of traffic to the Dallas endpoint.
7.  **OpenTofu State Update:** A post-failover script runs `tofu apply` (or a specific state update command) to update the infrastructure state file, reflecting that the Dallas region is now the primary production endpoint.

**Split-Brain Handling:**
Split-brain is prevented by the **Distributed Configuration Store (DCS)** (etcd). Patroni requires a quorum of etcd nodes to elect a primary. If the Chicago site loses quorum, it cannot maintain primary status, forcing it into a standby/read-only mode, preventing it from accepting writes while Dallas is promoted.

**Failback Procedure:**
1.  **Chicago Recovery:** Once Chicago is stable, it is brought back online as a *new* standby replica, pointing to the Dallas primary.
2.  **Data Sync:** Allow Chicago to fully sync all WALs and object replication from Dallas.
3.  **Planned Switchover:** Schedule a maintenance window. Use Patroni's controlled switchover feature to gracefully demote the Dallas primary and promote Chicago back to primary.
4.  **DNS Update:** Update GSLB to point traffic back to Chicago.
5.  **State Update:** Run `tofu apply` to reflect the Chicago primary status in the state file.
