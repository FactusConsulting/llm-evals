G1 — A slice is a dynamically sized, flexible view into an underlying array. An array has a fixed size defined at compile time. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array (typically doubling the capacity), copies the existing elements to the new array, and then appends the new element.

G2 — `var x int` declares a variable `x` and initializes it to its zero value (0 for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when you are assigning a value to a variable that has already been declared in the current scope (e.g., `x = 5` is correct, but `x := 5` would cause a redeclaration error).

G3 — A goroutine is a lightweight, independently executing function managed by the Go runtime, not the OS. It is much cheaper than an OS thread because it requires very little stack space (starting small and growing dynamically). The Go scheduler (GMP model) maps many goroutines (G) onto a smaller pool of OS threads (M), managed by a set of logical processors (P). The scheduler efficiently multiplexes goroutines onto available OS threads, allowing for massive concurrency with low overhead.

G4 — Channels are typed conduits through which you can send and receive values between goroutines. An **unbuffered channel** requires both the sender and receiver to be ready at the time of communication (synchronous rendezvous). A **buffered channel** has a fixed capacity; sends are blocked only when the buffer is full, and receives are blocked only when the buffer is empty. When sending to a full buffered channel, the sending goroutine blocks until a receiver frees up a slot.

G5 — The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. This is crucial for managing the lifecycle of concurrent operations.
Example:
```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"
)

func main() {
	// Create a context that automatically cancels after 2 seconds
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel() // Always call cancel to release resources

	req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com/slow", nil)
	client := http.Client{}
	resp, err := client.Do(req)

	if err != nil {
		// Check if the error was due to context cancellation/timeout
		if ctx.Err() == context.DeadlineExceeded {
			fmt.Println("Request timed out.")
		} else {
			fmt.Println("Error:", err)
		}
		return
	}
	defer resp.Body.Close()
	fmt.Println("Request successful.")
}
```

G6 — Go uses implicit interface satisfaction (structural typing). A type satisfies an interface simply by implementing all the methods declared in that interface; there is no explicit declaration required (unlike Java/C# where you must `implements` an interface). The empty interface `interface{}` (or `any` in Go 1.18+) can hold a value of any type. It is powerful because it allows for maximum flexibility (polymorphism without inheritance), but it is dangerous because it forces runtime type assertions, losing compile-time type safety and potentially leading to runtime panics if the type is incorrect.

G7 — This is unsafe due to data races. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading `ready` and then reading `data`. Since there is no synchronization mechanism, the main goroutine might read `ready` as `true` before the write to `data` has become visible to it, leading to reading an uninitialized or stale value of `data`.
Correct alternatives include:
1. **Mutex:** Protecting access to both variables with `sync.Mutex`.
2. **Channel:** Sending a signal (e.g., a struct containing both `data` and `ready`) over a channel to synchronize the main goroutine.

G8 — `sync.Mutex` provides mutual exclusion, allowing only one goroutine to hold the lock at a time (exclusive access). `sync.RWMutex` allows multiple readers to hold the lock simultaneously (`RLock`) but requires exclusive access for writers (`Lock`).
Use `sync.Map` when you have a map where keys are frequently written to by different goroutines, and you want to avoid the overhead of locking a standard map for every read/write operation, especially if reads vastly outnumber writes.
**Trade-offs:** `sync.Mutex` is simpler and generally faster for low contention. `sync.RWMutex` is better for read-heavy workloads. `sync.Map` has higher overhead than a mutex-protected map for simple operations but can perform better under extreme concurrent access patterns where contention on a single lock is high.

G9 — Go modules manage dependencies. `go.mod` lists the required modules and their version constraints. `go.sum` contains cryptographic checksums for the exact content of every dependency listed in `go.mod`, ensuring build reproducibility and integrity. `go mod tidy` cleans up the `go.mod` and `go.sum` files by adding any missing dependencies required by the code and removing any dependencies that are no longer used. Minimum Version Selection (MVS) is an algorithm used by Go to select the highest possible version of a dependency that satisfies all version constraints specified in the module files, while ensuring compatibility.

G10 — A `defer` statement schedules a function call to be executed just before the surrounding function returns. If multiple `defer` statements exist, they execute in Last-In, First-Out (LIFO) order. A common gotcha in a loop is capturing the loop variable by reference (or closure capture). If you defer a function that references the loop variable, the deferred function will execute *after* the loop finishes, and it will use the final value of the loop variable, not the value from the iteration when the defer was scheduled.

G11 — A pointer in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`, which indicates that it points to no valid memory location. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

G12 — The `init()` function is a special function that runs automatically before the `main` function in a package. It is used for package-level setup, such as initializing global variables or registering drivers. A package can have multiple `init()` functions, and they execute sequentially in the order they appear in the source code files.

G13 — `make` is used to initialize built-in reference types (slices, maps, channels). It allocates the necessary underlying data structure and returns a usable instance. `new` allocates memory for a value of a specified type and returns a pointer to the zero-initialized value of that type. `make` works with slices, maps, and channels; `new` works with any type.

G14 — Error handling in Go is explicit; functions typically return an `error` type as the last return value. The `error` interface is an interface with a single method: `Error() string`. The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain contains a specific sentinel error value. `errors.As(err, &target)` checks if the error chain contains a value that matches a specific type, allowing you to extract structured error details.

G15 — **Map:** A collection of key-value pairs. Zero value: `nil` (cannot be written to until initialized). **Slice:** A dynamically sized, contiguous sequence of elements. Zero value: `nil` (a nil slice). **Channel:** A typed conduit for communication. Zero value: `nil` (cannot be used until initialized). **Struct:** A composite data type grouping fields. Zero value: all fields set to their respective zero values.

G16 — A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization mechanism. The `-race` flag instruments the Go runtime to detect these data races during execution.
Example Data Race: Two goroutines incrementing a shared counter without a lock.
Fix using Mutex: Wrap the increment operation in `mu.Lock()` and `mu.Unlock()`.
Fix using Channel: Send the increment request over a channel to a single dedicated goroutine that manages the counter state sequentially.

G17 — The `select` statement waits on multiple communication operations (channel sends or receives). It differs from `switch` because `select` is specifically designed for concurrency and channel operations. When multiple cases are ready, `select` chooses one pseudo-randomly. A timeout is implemented by including a `time.After(duration)` channel case in the `select` block.

G18 — Escape analysis is the process by which the Go compiler determines whether a variable should be allocated on the stack (fast, local memory) or the heap (managed memory, requiring garbage collection). The compiler analyzes the variable's lifetime and how it is referenced. If a variable's address escapes the function scope (i.e., it is returned, stored in a global variable, or sent across a channel), it must be allocated on the heap. You can inspect this using the `-gcflags="-m"` flag. It matters because heap allocation involves overhead (GC tracking, pointer indirection), while stack allocation is extremely fast.

G19 — The `reflect` package allows a program to inspect and manipulate its own structure (types, values, methods) at runtime. `reflect.Type` describes the structure of a type (e.g., "this is a struct with fields X, Y"). `reflect.Value` represents a concrete value of a type. Reflection incurs significant performance costs because the compiler cannot optimize the code path; it must perform dynamic lookups at runtime. Reflection is justified for generic serialization/deserialization libraries or dynamic plugin systems, but code generation is preferred for performance-critical paths.

G20 — The `go:embed` directive allows embedding files or directories directly into a Go binary as byte slices or file systems, effectively bundling static assets. For single files, it embeds the content as `[]byte`. For directories or file systems, it embeds them as `fs.FS`. Limitations include the size of the binary and the complexity of handling dynamic file paths. It interacts with `io/fs.FS` by providing an in-memory file system implementation that can be passed to functions expecting an `fs.FS` interface.

R1 — Ownership is Rust's system for managing memory safety without a garbage collector. It ensures that every piece of data has exactly one owner at any given time. The three rules are: 1) Each value in Rust has a variable that is its owner. 2) There can only be one owner at a time. 3) When the owner goes out of scope, the value is dropped (memory is freed).

R2 — `String` is a heap-allocated, growable, mutable UTF-8 string type. `&str` is a string slice, which is a borrowed, immutable view into string data (either owned by a `String` or embedded in the binary). Use `&str` in function signatures when you only need to read the string data (most common for efficiency). Use `String` when you need to own, modify, or build a string dynamically.

R3 — Borrowing allows you to refer to data without taking ownership of it. The borrow checker enforces rules to prevent data races at compile time.
*   **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously.
*   **Mutable Reference (`&mut T`):** Allows only one mutable reference to the data at any given time.
The core rule is: You can have *either* any number of shared references *or* exactly one mutable reference, but not both simultaneously.

R4 — `Option<T>` is an enum representing the presence or absence of a value: `Some(T)` or `None`. `Result<T, E>` is an enum representing success or failure: `Ok(T)` or `Err(E)`. The `?` operator is syntactic sugar for propagating errors or unwrapping `Option`s. If the expression evaluates to `Err(E)`, the function immediately returns that error. If it evaluates to `Ok(T)`, it unwraps the value `T` and continues execution.
Example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> Result<String, io::Error> {
    let mut file = File::open(path)?; // Propagates io::Error if file cannot be opened
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates io::Error if read fails
    Ok(contents)
}
```

R5 — **Box<T>:** A smart pointer that allocates data on the heap and provides a fixed-size pointer to it. Used when the size of a type is unknown at compile time (e.g., recursive data structures). **Rc<T> (Reference Counted):** Allows multiple owners of the same data on the heap. It keeps a count; the data is dropped only when the last `Rc` goes out of scope. Used for shared, immutable ownership. **Arc<T> (Atomic Reference Counted):** Similar to `Rc<T>` but uses atomic operations for reference counting, making it safe to share across threads (thread-safe).

R6 — Traits define shared behavior (like interfaces). They specify a set of methods that a type must implement. They compare to Go interfaces in that they define a contract.
*   **Trait Object (`dyn Trait`):** A dynamically dispatched pointer (like `Box<dyn Trait>`). The concrete type is determined at runtime. This is used when you need a collection of different types that all implement the same trait.
*   **Generic with Trait Bound (`T: Trait`):** A statically dispatched generic parameter. The compiler knows the concrete type at compile time, allowing for monomorphization and zero-cost abstraction. This is generally preferred for performance.

R7 — The code fails because the return type `&str` implies that the returned slice must live as long as the caller needs it. However, the slice returned (`x` or `y`) is borrowed from the input parameters, which are local to the `longest` function. When `longest` returns, those inputs go out of scope, and the returned reference becomes a dangling pointer.
Fix: You must use lifetimes to tell the compiler that the returned reference is valid for the duration of the shorter of the two input references.
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

R8 — **Send:** A trait indicating that a type can be safely transferred (sent) across thread boundaries. **Sync:** A trait indicating that a type can be safely shared between threads (i.e., it is safe to have multiple immutable references to it across threads).
You cannot send an `Rc<T>` across threads because its internal reference counter is not atomic, leading to race conditions when multiple threads try to increment/decrement the count simultaneously. `Arc<T>` is safe for concurrent use because it wraps the reference count in atomic primitives, ensuring thread-safe modification of the count.

R9 — Rust's async/await is built on the `Future` trait. A `Future` represents a value that *might* be available later. When an `async` function is called, it returns a `Future` immediately, without blocking the thread. The `await` keyword pauses the execution of the current task until the awaited `Future` completes, yielding control back to the executor. The **executor** (e.g., Tokio, async-std) is the runtime responsible for polling these futures—it drives the state machine of the futures, resuming them only when the underlying I/O or operation completes, thus achieving concurrency without OS threads per task. This differs from Go's goroutines because Rust futures are *cooperative* (they must explicitly yield control via `.await`), whereas Go goroutines are *preemptive* (the scheduler can interrupt them).

R10 — `unsafe` allows programmers to bypass Rust's compile-time safety guarantees. It is used when interacting with foreign code (FFI), implementing low-level data structures, or when performance requires direct memory manipulation. Three things you can do in `unsafe` include: 1) Dereference raw pointers (`*const T`, `*mut T`). 2) Call `unsafe` functions or methods. 3) Access or modify mutable static variables. Unsafe code is justified only when the programmer can prove, through rigorous reasoning, that the memory safety invariants will be maintained, typically for performance or interoperability.

R11 — Pattern matching uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches. `if let` is syntactic sugar used to conditionally destructure a value if it matches a specific pattern, but it only handles one case. `match` is exhaustive; the compiler forces you to handle every possible variant of the type (e.g., both `Some` and `None` for `Option`), preventing runtime errors from unhandled states.

R12 — `Vec<T>` is a dynamically sized, heap-allocated, growable array. An array `[T; N]` has a fixed size `N` known at compile time and is typically allocated on the stack if small enough. When `Vec` pushes elements beyond its current capacity, it allocates a new, larger contiguous block of memory (usually doubling the capacity), copies all existing elements to the new block, and then adds the new element.

R13 — Rust enums are powerful algebraic data types that can hold different types of data for each variant, unlike C/Java enums which are usually simple integer constants. `Option<T>` is an enum variant that explicitly models the possibility of absence (`None`), which is Rust's idiomatic replacement for null pointers, forcing the programmer to handle the absence case explicitly at compile time.

R14 — The `impl` block defines methods and associated functions for a specific type.
*   `&self`: Takes an immutable reference; methods can read the data but not change it.
*   `&mut self`: Takes a mutable reference; methods can read and modify the data.
*   `self`: Takes ownership of the instance; the method consumes the instance (used for consuming operations).
Associated functions (like `String::new()`) are functions associated with the type but do not operate on a specific instance; they are called using the type name itself.

R15 — A derive macro is a procedural macro that automatically implements standard traits for a struct or enum based on its structure. Examples include `#[derive(Debug)]` (allows printing via `{:#?}`), `#[derive(Clone)]` (implements deep copying), `#[derive(PartialEq)]` (implements equality comparison), and `#[derive(Serialize)]` (used by Serde for serialization). You cannot derive a trait if the type contains fields that do not implement the required trait (e.g., you cannot derive `Clone` if one of your fields is a raw pointer).

R16 — `Cow<'a, T>` (Clone On Write) is an enum that can hold either an owned value (`T`) or a borrowed reference (`&'a T`). It is useful when you initially receive data as a reference but might need to modify it later. If you only read the data, you use the cheap reference. If you need to mutate it, `Cow` automatically clones the borrowed data into an owned version, performs the mutation, and returns the owned version. This avoids unnecessary allocations when the data is only read.

R17 — The module system organizes code into logical units. `mod` declares a module (which can be a file or a directory). `use` brings items from a module into the current scope, allowing you to refer to them without the full path. `pub` makes items (functions, structs, etc.) visible outside the current module. The file system maps to modules: a file named `foo.rs` typically defines the `foo` module. The major change in Rust 2018 was the introduction of explicit module paths and the ability to define modules within files, leading to a more structured and predictable module hierarchy.

R18 — `Pin<T>` is a wrapper that guarantees that the data pointed to by `T` will not be moved in memory for the duration of its lifetime. This is crucial for types that contain self-references (where a part of the struct points back to another part of the same struct) or for async tasks. If a struct containing a `Future` is moved, the internal pointers become invalid. `Unpin` is a marker trait indicating that a type is safe to move; if a type does not implement `Unpin`, it must be pinned to ensure its memory location remains stable while it is being polled by the executor.

R19 — **Declarative Macros (`macro_rules!`):** These are pattern-matching macros that operate on tokens (syntactic structure). They are like sophisticated text substitution rules. **Procedural Macros:** These are functions that operate on the Abstract Syntax Tree (AST) of the code. They are more powerful and are used for deriving traits (`#[derive]`), attribute macros (`#[my_attr]`), and function-like macros. **Hygiene Rules** prevent macro expansion from accidentally capturing or interfering with identifiers defined inside the code where the macro is being used, ensuring that the macro's generated code is isolated and safe.

R20 — Zero-cost abstractions mean that high-level language features (like generics and iterators) compile down to machine code that is as fast as if the programmer had written the low-level, hand-optimized code directly in C.
*   **Generics (Monomorphization):** When you use a generic type `T`, the compiler generates a specialized version of the code for every concrete type used (e.g., one version for `Vec<i32>` and another for `Vec<String>`). This avoids runtime type checks.
*   **Trait Static Dispatch:** Instead of using dynamic lookups (like virtual function tables), the compiler resolves which method to call at compile time based on the trait implementation, resulting in direct function calls.
*   **Iterators:** Rust iterators are zero-cost because they are implemented as state machines that are composed using function calls, not by allocating intermediate collections.

R1 — Ownership is Rust's memory management system ensuring memory safety without a garbage collector. The three rules are: 1) Every value has a single owner. 2) When the owner goes out of scope, the value is dropped (memory is freed). 3) Ownership can be transferred (moved) or shared via references.

R2 — `String` is a heap-allocated, mutable, owned string type. `&str` is a string slice, which is an immutable, borrowed view into string data. Use `&str` in function signatures when you only need to read the data (most efficient). Use `String` when you need to own or modify the string data.

R3 — Borrowing allows temporary, safe access to data. The borrow checker enforces rules to prevent data races: You can have multiple immutable references (`&T`) simultaneously, OR exactly one mutable reference (`&mut T`) at any given time. This prevents simultaneous reading and writing, or simultaneous writing by multiple parties.

R4 — `Option<T>` is an enum: `Some(T)` or `None`. `Result<T, E>` is an enum: `Ok(T)` or `Err(E)`. The `?` operator propagates errors or unwraps values. If the expression is `Err(E)`, the function immediately returns `Err(E)`. If it is `Ok(T)`, it unwraps `T` and continues.

R5 — **Box<T>:** Heap allocation for a single value, used when size is unknown at compile time. **Rc<T>:** Reference counting for shared, immutable ownership on the heap. **Arc<T>:** Atomic reference counting, making `Rc<T>` thread-safe for sharing across threads.

R6 — Traits define shared behavior, similar to Go interfaces. A **Trait Object (`dyn Trait`)** is a dynamically dispatched pointer that holds any type implementing the trait; the specific type is resolved at runtime. A **Generic with Trait Bound (`T: Trait`)** is a statically dispatched generic parameter; the compiler knows the concrete type at compile time, enabling zero-cost abstraction.

R7 — The code fails because the returned reference (`&str`) borrows from the input parameters (`x` and `y`), which are local variables within `longest`. When `longest` returns, these inputs are dropped, leaving the returned reference dangling. The fix is to introduce a lifetime parameter (`'a`) on the function signature and apply it to the inputs and the return value, ensuring the compiler knows the output reference is valid only as long as the shortest input reference.

R8 — **Send:** Allows a type to be safely moved between threads. **Sync:** Allows a type to be safely referenced across threads (i.e., shared immutably). `Rc<T>` is not `Send` or `Sync` by default because its internal counter is not atomic. `Arc<T>` is thread-safe because it uses atomic operations for its reference counting, making it safe to share across threads.

R9 — Rust's async/await relies on the `Future` trait, which represents an asynchronous computation that may not be ready immediately. An `async` function returns a `Future`. The **executor** (like Tokio) is the runtime that polls these futures. It drives the state machine of the futures, resuming them only when their dependencies (like I/O) are ready. This is cooperative multitasking; the task must explicitly yield control via `.await`, unlike Go's preemptive scheduling.

R10 — `unsafe` allows direct memory manipulation, bypassing Rust's safety checks. Three things: 1) Dereferencing raw pointers. 2) Calling `unsafe` functions. 3) Accessing mutable statics. It is justified when interfacing with C libraries (FFI) or implementing highly optimized, low-level data structures where the programmer can guarantee memory safety manually.

R11 — Pattern matching uses `match` to compare a value against multiple defined patterns and execute code based on the match. `if let` is a concise way to conditionally destructure a value if it matches a single pattern. The compiler enforces **exhaustiveness**, meaning you must provide a branch for every possible variant of the enum or type being matched, preventing runtime errors from unhandled states.

R12 — `Vec<T>` is a dynamically sized, heap-allocated, growable collection. An array `[T; N]` has a fixed size `N` known at compile time and is usually stack-allocated. When `Vec` exceeds capacity, it allocates a new, larger block of memory, copies the old elements, and then adds the new element.

R13 — Rust enums are powerful algebraic data types that can hold different types of data for each variant (e.g., `enum Message { Text(String), Image(Vec<u8>) }`). `Option<T>` is an enum variant that explicitly models the absence of a value (`None`), serving as Rust's type-safe replacement for null pointers, forcing the developer to handle the `None` case explicitly.

R14 — The `impl` block defines methods for a type.
*   `&self`: Immutable borrow; read-only access.
*   `&mut self`: Mutable borrow; read and write access.
*   `self`: Takes ownership; consumes the instance.
Associated functions (like `String::new()`) are functions associated with the type but do not require an instance to be called.

R15 — A derive macro automatically implements standard traits based on the structure of a type. Examples: `Debug` (for printing), `Clone` (for copying), `PartialEq` (for equality checks), `Serialize` (for serialization). You cannot derive a trait if the type contains fields whose types do not implement that trait (e.g., if a field is a raw pointer, you cannot derive `Clone`).

R16 — `Cow<'a, T>` (Clone On Write) is an enum that holds either an owned value (`T`) or a borrowed reference (`&'a T`). It is useful when you receive data as a reference but might need to modify it. If you only read it, you use the cheap reference. If you mutate it, `Cow` clones the data internally, performs the mutation, and returns the owned version, avoiding unnecessary allocations if the data remains immutable.

R17 — The module system organizes code logically. `mod` declares a module. `use` brings items into scope. `pub` controls visibility. The file system maps to modules: a file named `foo.rs` defines the `foo` module. The Rust 2018 edition formalized the module structure, allowing modules to be defined within files and providing clearer rules for path resolution, leading to more robust and scalable code organization.

R18 — `Pin<T>` ensures that the memory location of a type `T` will not change (it cannot be moved) while it is "pinned." This is necessary for self-referential structs or for `Future`s. If a `Future` were moved, its internal state pointers would become invalid. `Unpin` is a marker trait indicating that a type is safe to move; types that do not implement `Unpin` must be pinned to maintain their internal invariants during asynchronous execution.

R19 — **Declarative Macros (`macro_rules!`):** These use pattern matching on tokens to perform textual substitution. **Procedural Macros:** These operate on the Abstract Syntax Tree (AST) of the code, allowing complex transformations (like deriving traits). **Hygiene Rules** ensure that identifiers introduced by a macro are locally scoped and do not accidentally clash with or modify identifiers in the surrounding code, maintaining code integrity.

R20 — Zero-cost abstractions mean that high-level language features compile down to highly optimized machine code with minimal runtime overhead. **Generics (Monomorphization)** achieves this by generating specialized code for each type used, eliminating runtime type checks. **Trait Static Dispatch** resolves method calls at compile time, avoiding the overhead of dynamic lookups. **Iterators** are implemented as state machines that process data sequentially without allocating intermediate collections, achieving C-like performance while maintaining high-level ergonomics.
