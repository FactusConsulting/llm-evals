**AA1**
The difference is scope and coupling. A **monolith** is a single, tightly coupled unit where all business logic resides in one deployable artifact. **Microservices** decompose the application into a collection of small, independent, loosely coupled services, each running its own process and communicating via APIs.
Problems microservices introduce:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication.
2. **Operational Overhead:** Increased complexity in deployment, monitoring, and logging across dozens of services.
3. **Data Consistency:** Managing transactions across multiple independent databases (distributed transactions).

**AA2**
**Synchronous communication** requires the caller to wait for an immediate response from the service it calls. Example: RESTful HTTP request (e.g., using `fetch` or `HttpClient`).
**Asynchronous communication** allows the caller to send a message/event and immediately continue processing without waiting for a response. The recipient processes the message later. Example: Kafka or RabbitMQ.

**AA3**
A **Reverse Proxy** sits in front of one or more servers, routing external client requests to the appropriate internal service based on rules (e.g., path, host header). Its primary function is traffic management, load balancing, and security termination.
An **API Gateway** is a specialized reverse proxy that adds business logic and abstraction layers on top of basic routing. It handles cross-cutting concerns like authentication, rate limiting, request transformation, and protocol translation before forwarding the request to the appropriate microservice.
No, an API Gateway cannot entirely replace a reverse proxy. The API Gateway *is* a specialized type of reverse proxy, but it adds significant application-level intelligence (auth, throttling) that a generic reverse proxy lacks.

**AA4**
The **Saga pattern** is a sequence of local transactions where each transaction updates the database and publishes an event to trigger the next step. If any step fails, the Saga executes compensating transactions to undo the preceding successful steps, maintaining data consistency without using traditional distributed two-phase commits.
*   **Choreography-based:** Services communicate by producing and consuming events without a central coordinator. Each service knows what to do based on the events it receives. Appropriate when the workflow is simple, decentralized, and services are highly autonomous.
*   **Orchestration-based:** A dedicated service (the orchestrator) manages the workflow, sending commands to participant services and handling the logic for compensation. Appropriate when the workflow is complex, long-running, or requires centralized visibility and control.

**AA5**
**CQRS (Command Query Responsibility Segregation)** separates the model used for updating data (Commands) from the model used for reading data (Queries). They can use different data structures, databases, and optimization strategies.
It is often paired with **Event Sourcing (ES)** because ES stores the state of the application as a sequence of immutable events. The Command side writes these events, and the Query side rebuilds optimized read models (projections) from those events.
This combination solves the problem of complex read/write requirements in a traditional CRUD model. A CRUD model forces the read and write models to be tightly coupled to the same relational schema, which often leads to performance bottlenecks when read patterns are vastly different from write patterns (e.g., complex reporting vs. simple updates).

**AA6**
The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service). It monitors calls; if failures exceed a threshold, the circuit "trips" (opens), immediately failing subsequent calls without attempting the network request, allowing the failing service time to recover.
The three states are: **Closed** (normal operation), **Open** (requests fail fast immediately), and **Half-Open** (a limited number of test requests are allowed through to check if the service has recovered).
It differs from simple retry with backoff because retry only delays the failure; the circuit breaker *stops* the failure propagation entirely when the service is known to be down. They are used together: the circuit breaker prevents overwhelming a failing service, and the retry mechanism can be used *within* the closed state for transient network glitches.

**AA8**
**Strong Consistency** guarantees that once a write operation is acknowledged, all subsequent read operations will immediately see that written value. (e.g., ACID transactions).
**Eventual Consistency** guarantees that if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value, but there is a period where reads may return stale data.
To prevent overselling inventory (a critical business invariant), you must enforce **Strong Consistency** at the point of sale/reservation.
*   **Consistency Model:** Strong Consistency (or Linearizability).
*   **Data Store:** A transactional relational database (e.g., PostgreSQL, MySQL) or a strongly consistent distributed ledger/database (e.g., CockroachDB, Spanner).
*   **Patterns:** Use pessimistic locking or atomic database transactions during the inventory decrement process. For high scale, implement a dedicated, highly consistent inventory service that acts as the single source of truth, potentially using a queue/lock mechanism to serialize reservation requests.

**AA9**
A **sidecar proxy** is a small, dedicated proxy container deployed alongside every instance of a service container within the same deployment unit (e.g., a Kubernetes Pod). It intercepts all inbound and outbound network traffic for the main application container.
In an **Istio** deployment, Envoy is the proxy deployed as the sidecar. It handles service mesh functions: traffic routing, load balancing, metrics collection, policy enforcement, and security (mTLS).
*   **Data Plane:** The set of proxies (Envoy sidecars) that handle the actual network traffic forwarding and policy enforcement.
*   **Control Plane:** The management layer (e.g., Istiod) that configures and manages the data plane proxies, pushing routing rules, security policies, and configuration to all sidecars.
mTLS between sidecars solves the problem of *untrusted network hops*. Application-level TLS secures the connection between two endpoints, but if the network itself is compromised (e.g., an attacker intercepts traffic between two services), the data is vulnerable. Sidecar mTLS ensures that *all* service-to-service communication is mutually authenticated and encrypted by the mesh infrastructure, regardless of the underlying network security.

**AA10**
The **Strangler Fig pattern** is an incremental migration technique where new functionality is built as microservices around the edges of a legacy system. Over time, the new services "strangle" the old monolith until the monolith can be safely decommissioned.
**Migration Strategy:**
1. **Identify Boundaries:** Identify a low-risk, self-contained domain within the monolith (e.g., User Profile Management).
2. **Build New Service:** Implement the new functionality (e.g., User Service) in .NET 8.
3. **Implement Facade/Routing:** Place an API Gateway in front of the monolith. Configure the gateway to route all requests for the User Profile domain to the new .NET 8 service, while all other requests continue to the monolith.
4. **Data Synchronization:** Implement a mechanism (e.g., Change Data Capture or event publishing) to keep the new service's data synchronized with the monolith's database during the transition.
5. **Iterate:** Repeat the process, strangling more domains until the monolith is only a shell or is retired.

**AA11**
The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable, and resilient software-as-a-service applications.
Six factors and their importance:
1. **Codebase:** One codebase tracked in revision control, many deploys. (Ensures version control and consistency).
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures reproducible builds in any environment).
3. **Config:** Store configuration in the environment. (Decouples configuration from code, essential for cloud deployment flexibility).
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. (Allows easy swapping of data stores without code changes).
5. **Build, Release, Run:** Strictly separate build, release, and run stages. (Enables CI/CD pipelines and immutable deployments).
6. **Processes:** Execute the application as one or more stateless processes. (Crucial for horizontal scaling; state must be externalized).

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Services only know the event contract) | Tight (Caller must know the callee's interface/endpoint) |
| **Scalability** | Excellent (Consumers can scale independently based on topic load) | Good (Vertical/Horizontal scaling of services) |
| **Debugging Complexity** | High (Tracing flow across asynchronous hops is difficult) | Low (Synchronous stack trace is clear) |
| **Ordering Guarantees** | Guaranteed within a partition/topic (if configured correctly) | Guaranteed by the request/response sequence |
| **Failure Handling** | Built-in resilience via consumer offsets/retries; dead-letter queues (DLQs). | Requires explicit client-side retry logic and circuit breakers. |
**When to choose:**
*   **Event-Driven:** When the system requires high decoupling, needs to react to state changes across many services (e.g., order fulfillment, notifications), or when high throughput/backpressure handling is critical.
*   **Request-Driven:** When an immediate, synchronous response is required (e.g., user login validation, fetching a specific resource), or when the workflow is simple and linear.

**AA13**
A **Load Balancer** distributes incoming network traffic across a group of backend servers to ensure no single server is overwhelmed, improving availability and throughput.
*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It routes traffic based on IP addresses and port numbers. It is fast because it does not inspect the application payload.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (headers, URL path, cookies) to make intelligent routing decisions.
**Use Case for Layer 7:** Routing traffic to different microservices based on the URL path (e.g., `/api/users` goes to the User Service, `/api/orders` goes to the Order Service).

**AA14**
A **Message Queue** (e.g., RabbitMQ) is a point-to-point or publish/subscribe system designed for reliable message delivery. Messages are consumed and typically *removed* from the queue once successfully processed. It prioritizes guaranteed delivery and decoupling.
A **Log-based Message Broker** (e.g., Kafka) functions as a distributed, immutable commit log. Messages are appended to topics and retained for a configurable period. Consumers read from specific offsets.
**When to pick one over the other:**
*   **Message Queue:** When you need a task to be executed *exactly once* and then discarded (e.g., processing a payment request).
*   **Log-based Broker:** When you need multiple consumers to read the same stream of events independently, or when you need to replay past events for auditing or rebuilding state (e.g., tracking all user activity).

**AA15**
A **Container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and settings. It shares the host OS kernel.
A **Virtual Machine (VM)** virtualizes the entire hardware stack, including the CPU, memory, and disk, running a full guest OS on top of a hypervisor.
Containers are popular because they offer high density, fast startup times, and portability. They avoid the overhead of running a full guest OS for every application instance, leading to smaller images and lower resource consumption.

**AA16**
A **Stateless Service** does not store any client session data or persistent state locally between requests. Every request must contain all necessary information for the service to process it. Example: A simple REST API endpoint that validates a token and returns data.
A **Stateful Service** retains data or context across multiple requests. Example: A database server, a session cache (Redis), or a message queue.
Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance, as no instance holds unique, necessary state. Scaling simply means adding more identical instances behind a load balancer.

**AA17**
An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using object-oriented paradigms (objects and classes) instead of writing raw SQL queries. It maps database tables to classes and rows to objects.
Popular ORMs: **Entity Framework (.NET)**, **Hibernate (Java)**, **SQLAlchemy (Python)**.
**Trade-offs:**
*   **ORM Pros:** Increased developer productivity, abstraction from SQL dialect, type safety.
*   **ORM Cons:** Performance overhead (the "N+1 query problem"), impedance mismatch (mapping complex object graphs to flat relational tables), and difficulty optimizing complex, highly specific queries.

**AA18**
The **Bulkhead pattern** isolates components or resources so that the failure or exhaustion of resources in one area does not cascade and bring down the entire system. It partitions resources into isolated pools.
It relates to resource isolation by preventing a single failing or overloaded dependency from consuming all shared resources (like threads or memory) needed by other, healthy services.
**Implementation Example:** If Service A calls Service B and Service C, and Service B is slow, you implement a bulkhead by assigning Service B a dedicated, limited thread pool (e.g., 10 threads). If Service B saturates its pool, subsequent calls to B fail fast, but the threads allocated for Service C remain available, preventing the entire application from blocking.

**AA19**
*   **Operational Transformation (OT):** A mathematical algorithm that transforms operations (like insertions or deletions) based on concurrent changes made by other users. It requires a central server to manage the transformation logic and maintain a canonical state.
*   **CRDTs (Conflict-free Replicated Data Types):** Data structures designed so that concurrent updates can be merged automatically and mathematically guaranteed to converge to the same state without requiring a central coordinator.
**Comparison:**
| Feature | OT | CRDTs |
| :--- | :--- | :--- |
| **Consistency** | Strong (Requires server coordination) | Eventual (Guaranteed convergence) |
| **Latency** | Higher (Requires round-trip to server for transformation) | Lower (Updates can be applied locally immediately) |
| **Complexity** | High (Complex transformation logic) | Medium (Requires specialized data structures) |
| **Offline Support** | Poor (Requires server synchronization) | Excellent (Designed for local operation and merging) |
**Choice:** I would choose **CRDTs**. Since the requirement is to support offline editing, the system must be able to accept and merge changes locally without constant server connectivity. CRDTs inherently support this by allowing local operations that are mathematically guaranteed to resolve conflicts correctly upon reconnection.

**AA20**
**Challenges in Polyglot Tracing:**
1. **Context Propagation:** Ensuring the unique trace ID and span ID are passed correctly across service boundaries, especially when services use different languages or protocols. This requires standardized headers (e.g., W3C Trace Context or B3).
2. **Sampling:** Deciding which requests to trace. **Head-based sampling** decides whether to trace at the entry point (e.g., 1 in 100 requests). **Tail-based sampling** waits until the entire trace is complete to decide if it's valuable enough to keep, offering higher fidelity but higher infrastructure cost.
3. **Storage/Querying:** Storing high-volume trace data requires specialized backends like Jaeger or Tempo, which are optimized for high-cardinality time-series data.
4. **Asynchronous Messaging:** Tracing continuity is broken when a request hands off work to a message queue.
**Ensuring Trace Continuity with Kafka:** When a request publishes a message to Kafka, the trace context (Trace ID, Parent Span ID) must be injected into the message headers. The consuming service must then extract these headers and use the existing Trace ID to start a new child span, linking the asynchronous work back to the original request flow.

**OP1**
A **Type 1 (Bare-Metal) Hypervisor** runs directly on the host hardware, managing the hardware resources and allocating them to guest VMs. It offers near-native performance. Examples: VMware ESXi, Microsoft Hyper-V.
A **Type 2 (Hosted) Hypervisor** runs as an application *on top* of a conventional host operating system (like Windows or Linux). It relies on the host OS for hardware access. Examples: VMware Workstation, Oracle VirtualBox.

**OP2**
**SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. The server sees the storage as a raw, local disk volume. Protocols: Fibre Channel (FC), iSCSI. Used when applications require high I/O performance and direct block access (e.g., high-transaction databases).
**NAS (Network Attached Storage):** A file-level storage device accessible over the standard network. The storage device itself manages the file system. Protocols: NFS, SMB/CIFS. Used when sharing files and folders across multiple users/servers (e.g., shared document repositories).

**OP3**
A **3-Tier Network Architecture** separates the network into three functional layers:
1. **Access Layer:** Where end devices (servers, workstations) connect. Handles PoE and basic connectivity.
2. **Distribution Layer:** Aggregates traffic from the Access layer. Provides policy enforcement, routing boundaries, and VLAN aggregation.
3. **Core Layer:** The high-speed backbone responsible only for fast packet switching between distribution blocks.
**Leaf-Spine (Clos) Architecture:** In modern data centers, Leaf-Spine replaces the 3-tier model. Leaf switches connect directly to servers (access), and Spine switches connect all Leaf switches.
**Problem Solved:** The 3-tier model creates bottlenecks at the Distribution layer and introduces high latency due to the required hop count (Access $\rightarrow$ Distribution $\rightarrow$ Core $\rightarrow$ Distribution $\rightarrow$ Access). Leaf-Spine provides predictable, low-latency, non-blocking paths between any two endpoints via the Spine layer, ensuring uniform bandwidth regardless of location.

**OP4**
**Architecture Design:**
*   **Node Count:** Minimum 3 nodes for quorum in a cluster.
*   **Quorum:** Achieved via the cluster manager (e.g., Corosync/Ceph monitors). A majority vote (N/2 + 1) is required for state changes.
*   **Fencing (STONITH):** Critical. Must implement fencing mechanisms (e.g., IPMI power cycling, network isolation) to ensure a failed node cannot corrupt shared storage by writing inconsistent data.
*   **Shared Storage:** Ceph is the preferred choice as it provides software-defined, distributed storage across the cluster nodes themselves, eliminating the need for external SAN/NAS dependency.
*   **Node Failure:** If a node fails, the cluster monitors detect the loss. The remaining nodes maintain quorum. Ceph automatically rebalances the data (replicas) onto the surviving nodes, ensuring data availability, provided the replication factor is maintained.

**OP5**
**VLAN Trunking:** The process of allowing traffic from multiple VLANs to traverse a single physical link (trunk).
**802.1Q Tagging:** The standard protocol used for VLAN trunking. It inserts a 4-byte tag into the Ethernet frame header, containing a specific VLAN ID (VID) that tells the receiving switch which VLAN the frame belongs to.
**Linux Configuration:** You configure the physical NIC to be part of a bridge interface. Then, you create virtual interfaces (sub-interfaces) on that bridge, each assigned a specific VLAN ID (e.g., `eth0.10`, `eth0.20`, `eth0.30`). Each sub-interface is then configured with the necessary IP address and routing rules for its respective VLAN.

**OP6**
*   **RAID 1 (Mirroring):** Duplicates data across two or more drives. High read performance, 50% capacity loss. Excellent fault tolerance.
*   **RAID 5 (Striping with Parity):** Stripes data across drives and distributes parity information. Can survive one drive failure. Good balance of performance/capacity.
*   **RAID 6 (Striping with Dual Parity):** Stripes data and distributes two independent parity blocks. Can survive two drive failures. Higher write penalty than RAID 5.
*   **RAID 10 (Mirroring + Striping):** Stripes data across mirrored sets. Excellent read/write performance and high fault tolerance (can lose multiple drives as long as they aren't in the same mirror set).
*   **RAID Z2 (ZFS):** Similar to RAID 6, using multiple parity blocks across multiple disks, offering high fault tolerance and data integrity checks (checksumming).
**Choice for Database Server (Performance, Capacity, Fault Tolerance):** **RAID 10**. While RAID 6 offers good fault tolerance, RAID 10 provides superior random I/O performance (critical for databases) because reads can be served from either mirror, and writes are faster than parity calculations.

**OP7**
**Architecture Design:**
1.  **Internal AD/DNS:** Internal DNS servers (authoritative for internal zones) are configured to forward queries for external domains to the DMZ resolvers.
2.  **Recursive Resolvers:** These are the primary servers used by clients (laptops, servers). They query external root hints and forward to authoritative servers.
3.  **Authoritative Servers:** These hold the actual zone files (e.g., `corp.local` internally, `public.com` externally).
4.  **Forwarders:** Internal resolvers forward external queries to trusted public DNS providers (e.g., Google 8.8.8.8) to reduce load on the authoritative servers.
5.  **Conditional Forwarding:** Internal DNS servers are configured to forward queries for specific domains (e.g., `vpn.partner.com`) to a specific partner's DNS server.
6.  **Split-Horizon DNS:** The internal DNS servers serve different records based on the client's location (e.g., internal clients resolve to internal IP addresses; external clients resolve to public IP addresses).
7.  **DNSSEC:** Applied only to the external, public-facing zones to cryptographically verify the authenticity of the DNS response.
**Laptop Movement:** When a laptop moves from the office (on the internal network) to the VPN, the internal DNS servers must be configured to recognize the VPN subnet and serve the appropriate internal records (Split-Horizon). The VPN gateway must be configured to route DNS requests back to the internal DNS servers.

**OP8**
The **PKI Chain of Trust** is a hierarchical structure:
1.  **Root CA:** The ultimate trust anchor. It is self-signed and kept offline (air-gapped) for maximum security. It signs the subordinate CAs.
2.  **Subordinate/Issuing CA:** These CAs are online and perform the day-to-day signing of end-entity certificates (servers, users). They are signed by the Root CA.
3.  **End-Entity Certificate:** The certificate issued to the actual resource (e.g., a web server). It is signed by the Subordinate CA.
**CRL vs OCSP:**
*   **CRL (Certificate Revocation List):** A list published periodically by the CA containing the serial numbers of all revoked certificates. Clients must download and check this list.
*   **OCSP (Online Certificate Status Protocol):** A real-time query mechanism where a client asks the CA (or an OCSP responder) directly, "Is this certificate valid?"
**Consequences of Compromise:**
*   **Compromised Subordinate CA:** High impact. An attacker can issue fraudulent certificates for any domain under that CA's scope. The damage is contained to that CA's scope, and the Root CA can revoke the subordinate CA's certificate.
*   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, its compromise means *all* certificates issued under its trust chain are untrustworthy, requiring a complete, organization-wide PKI rebuild.

**OP10**
**iDRAC/iLO/IPMI:** These are hardware management interfaces built into servers that allow administrators to remotely manage the server hardware (power cycling, viewing logs, accessing the console) independent of the operating system.
**Out-of-Band Management Criticality:** It is critical because if the OS or network stack fails, you still need a way to access the machine to diagnose the problem, reboot it, or attach storage. It provides a lifeline when the primary system is down.
**Exposure Risk:** If the IPMI interface is exposed to the internet, it becomes a massive attack vector. Attackers can use it to remotely power cycle, access the console, or potentially exploit vulnerabilities in the management firmware to gain root access to the physical server, bypassing all OS-level security controls.

**OP11**
*   **LVM (Logical Volume Manager):** A software layer that abstracts physical storage into flexible logical volumes. It allows resizing and snapshotting of volumes, but snapshots are typically block-level and can be resource-intensive.
*   **LVM-Thin:** An extension of LVM that allows for thin provisioning (allocating space only as needed). Snapshots are efficient, as they only store the *differences* from the base volume.
*   **ZFS:** A comprehensive file system and volume manager that integrates storage management, data integrity (checksumming), and volume management. It excels at snapshots, which are near-instantaneous and highly efficient because they are copy-on-write.
**Usage:**
*   **LVM:** Simple volume management where performance is not the absolute highest priority.
*   **LVM-Thin:** When you need flexible, space-efficient snapshots on top of existing LVM structures.
*   **ZFS:** For mission-critical data where data integrity (checksumming) and efficient, granular snapshots are paramount (e.g., databases, archival storage).

**OP12**
**Stretch Cluster/DR Strategy:** To survive a complete site failure, the cluster must span two geographically distant sites (Site A and Site B).
**Ceph CRUSH Rules:** CRUSH rules must be configured to understand the topology (Site A, Site B) and ensure that replicas are placed across different failure domains (i.e., at least one replica must reside in Site A and at least one in Site B).
**Monitor Placement:** Monitors must be placed in both sites, but the quorum must be carefully managed.
**Split-Brain Problem:** This occurs when network partitioning causes both sites to believe they are the sole surviving cluster, leading both to accept writes and corrupting data.
**Why 2-site Ceph is risky without a tiebreaker:** If the link between Site A and Site B fails, both sites might lose contact with the majority of the cluster. Without a tiebreaker (e.g., a third, small witness node located in a neutral third location), both sites might independently declare themselves the primary cluster, leading to divergent writes and data corruption.

**OP13**
**DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses and other network configuration parameters (subnet mask, gateway, DNS) to devices on a network.
**DORA Process:**
1.  **Discover:** Client broadcasts a DHCP Discover message to find available servers.
2.  **Offer:** DHCP server replies with a DHCP Offer, proposing an IP address and lease terms.
3.  **Request:** Client sends a DHCP Request, formally accepting the offered IP address.
4.  **Acknowledge:** DHCP server sends a DHCP ACK, confirming the lease and providing final configuration details.
**Server Unavailability:** If a Windows client's lease expires and the DHCP server is unavailable, the client will continue using its old IP address until the lease time expires or it is manually configured. Once the lease expires, the client will attempt to re-discover a server. If none is found, it will likely fail to communicate on the network until it obtains a new lease or is manually configured.

**OP14**
**Unmanaged Switch:** A plug-and-play switch that operates at Layer 2. It simply forwards frames based on MAC addresses without providing any configuration options. It is suitable for small, simple networks.
**Managed Switch:** A switch that allows administrators to configure and control network traffic flow using a CLI or GUI.
**Enterprise Features:** Managed switches provide crucial features like:
*   **VLAN Tagging/Trunking:** Segmenting broadcast domains for security and organization.
*   **QoS (Quality of Service):** Prioritizing critical traffic (like VoIP) over bulk data transfers.
*   **Port Mirroring:** Copying traffic from one port to another for monitoring/troubleshooting.
*   **Security Features:** Implementing 802.1X or port security to restrict unauthorized devices.

**OP15**
**NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.
**Criticality:** Accurate time synchronization is vital because many distributed systems rely on timestamps for ordering events, logging, and security.
**Consequences of Clock Drift:**
1.  **Log Correlation Failure:** Logs from different servers cannot be reliably correlated to reconstruct an event sequence.
2.  **Distributed Transaction Failure:** Systems relying on time-based locks or sequence numbers (like distributed databases) can fail or enter inconsistent states.
3.  **Security Issues:** Kerberos authentication and certificate validation rely heavily on synchronized time; drift can cause authentication failures.

**OP16**
*   **Physical Server:** A dedicated, tangible piece of hardware (rack-mounted server) running a bare-metal operating system.
*   **Virtual Machine (VM):** A software emulation of a physical computer, running on a hypervisor. It has its own virtual hardware and guest OS.
*   **Container:** A lightweight, isolated process that packages an application and its dependencies, sharing the host OS kernel.
**When to run on Bare Metal:** When absolute, maximum performance is required, or when the workload requires direct, low-level hardware access that virtualization layers might obscure or introduce latency to (e.g., specialized high-frequency trading applications, specific hardware acceleration tasks).

**OP17**
**UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power when utility power fails. Its role is to bridge the gap between power loss and generator startup, allowing graceful shutdown or continuous operation during the transition.
**Generator:** Provides long-term, sustained power during extended utility outages.
**Why both are needed:** The UPS handles the immediate, instantaneous failure (milliseconds), ensuring zero downtime during the switchover. The generator handles the sustained outage (minutes/hours) once the UPS battery capacity is depleted.
**ATS (Automatic Transfer Switch):** A device that monitors the utility power source. When utility power fails, the ATS automatically switches the electrical load from the utility source to the generator source. When utility power returns, it switches the load back.

**OP18**
**Active-Passive Clustering:** One node (Active) handles all the workload, while the other node (Passive/Standby) remains idle, constantly monitoring the active node. If the active node fails, the passive node takes over the workload (failover).
**Active-Active Clustering:** Both nodes actively handle portions of the workload simultaneously. This provides higher resource utilization and often better scalability, but requires more complex state synchronization.
**HA Implementation (PostgreSQL):**
1.  **Pacemaker/Corosync:** Used for cluster resource management and monitoring. Corosync handles cluster communication and membership.
2.  **Fencing (STONITH):** Essential. If the primary server fails, STONITH (Shoot The Other Node In The Head) must be used (e.g., via IPMI) to forcibly power off the failed node to prevent it from coming back online and causing data corruption (split-brain).
3.  **Virtual IPs (VIPs):** A single, floating IP address is assigned to the cluster. This VIP is managed by Pacemaker and only moves to the active node upon failover.
4.  **Failover Behavior:** Pacemaker monitors the PostgreSQL service. If the service fails on Node A, Pacemaker triggers the failover sequence: STONITH ensures Node A is isolated, the VIP is moved to Node B, and Node B starts the PostgreSQL service.

**OP19**
**3-2-1 Rule:** Maintain at least **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.
**RPO (Recovery Point Objective):** The maximum acceptable amount of data loss measured in time (e.g., 4 hours). Determines backup frequency.
**RTO (Recovery Time Objective):** The maximum acceptable downtime measured in time (e.g., 1 hour). Determines recovery speed requirements.
**Backup Types:**
*   **Full:** Copies all selected data. Slowest backup, fastest restore.
*   **Incremental:** Copies only data that has changed since the *last* backup of any type. Fastest backup, slowest restore (requires the last full + all incrementals).
*   **Differential:** Copies all data that has changed since the *last full* backup. Faster restore than incremental, slower backup than incremental.
**Deduplication:** Reduces storage footprint by identifying and storing only unique blocks of data, highly effective for backups.
**Offsite Storage:** Cloud storage (S3, Azure Blob) or tape libraries.
**Immutable Backups:** Backups that cannot be modified, deleted, or encrypted by an attacker for a set retention period, providing a critical defense against ransomware.
**Backup vs. DR:** **Backup** is the process of creating copies of data. **Disaster Recovery (DR)** is the comprehensive plan and process of restoring business operations and data availability after a catastrophic event.
**Testing Restores:** Regular, scheduled test restores are mandatory. This validates the RTO/RPO assumptions and ensures the backup chain is valid, not just that the backup job succeeded.

**OP20**
**802.1X (Port-Based Network Access Control):** A standard that controls which devices can connect to a wired network port.
*   **Supplicant:** The client device (laptop, server) requesting access.
*   **Authenticator:** The network switch/access point that enforces the policy and communicates with the server.
*   **Authentication Server:** The RADIUS server that verifies the supplicant's credentials.
**EAP Methods:**
*   **EAP-TLS:** Uses digital certificates for mutual authentication (client and server verify each other). Highest security.
*   **PEAP (Protected EAP):** Encapsulates an inner authentication method (like MS-CHAPv2) within a TLS tunnel, offering a good balance of security and ease of deployment.
**RADIUS:** The protocol used by the Authenticator to communicate authentication requests and receive authorization decisions from the Authentication Server.
**Dynamic VLAN Assignment:** Upon successful authentication, the RADIUS server sends an Access-Accept message containing vendor-specific attributes that instruct the switch to place the supplicant into a specific, authorized VLAN.
**Failed Authentication:** The switch, acting as the authenticator, places the device into a restricted, quarantined VLAN (or denies access entirely) until valid credentials are provided.
**MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., printers, IP phones). MAB allows the switch to authenticate the device based solely on its MAC address against the RADIUS server. This is less secure than 802.1X because MAC addresses are easily spoofed.
