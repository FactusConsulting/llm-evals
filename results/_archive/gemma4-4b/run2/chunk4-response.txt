**G1** — A slice is a dynamically sized, flexible view into an underlying array, while an array has a fixed size defined at compile time. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array (typically doubling the capacity), copies the existing elements to the new array, and then appends the new element. The slice header is then updated to point to this new array.

**G2** — `var x int` declares a variable `x` and initializes it to its zero value (which is `0` for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when redeclaring a variable within the same scope, or when the variable has already been declared using `var` or `:=`.

**G3** — A goroutine is a lightweight, independently executing function managed by the Go runtime, scheduled onto OS threads. It differs from an OS thread because goroutines are much smaller (starting with a small stack, often 2KB) and are managed by the Go runtime, allowing millions of them to run concurrently with minimal overhead. The Go scheduler (GMP model) maps Goroutines (G) onto OS threads (M) using a pool of operating system threads (P). The scheduler multiplexes many Gs onto a smaller set of Ps, which in turn run on Ms, efficiently utilizing CPU cores.

**G4** — Channels are typed conduits through which you can send and receive values between goroutines, providing synchronized communication. An unbuffered channel requires both the sender and receiver to be ready at the moment of communication (synchronous rendezvous). A buffered channel has a fixed capacity; sends or receives can proceed without the other party being ready, up to the buffer limit. When sending to a full buffered channel, the send operation blocks until a receiver reads a value from the channel, freeing up a slot.

**G5** — The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. This is crucial for managing the lifecycle of requests, preventing resource leaks, and ensuring timely termination.
Example:
```go
import (
    "context"
    "net/http"
    "time"
)

func makeRequestWithTimeout() {
    // Create a context that automatically cancels after 2 seconds
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel() // Always call cancel to release resources

    req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com/long-request", nil)
    client := &http.Client{}
    resp, err := client.Do(req)
    if err != nil {
        // This will catch context.DeadlineExceeded if the request takes too long
        fmt.Println("Request failed:", err)
    }
    resp.Body.Close()
}
```

**G6** — Go's interface satisfaction model is implicit: a type satisfies an interface simply by implementing all the methods defined in that interface; there is no explicit declaration required (unlike Java/C# where you must `implements` an interface). The empty interface, `interface{}`, can hold a value of any type. It is powerful because it allows for extreme flexibility (e.g., generic data structures that can hold anything). It is dangerous because it sacrifices type safety; the compiler cannot guarantee the underlying type, requiring runtime type assertions or type switches, which can lead to runtime panics if misused.

**G7** — This code is unsafe because of data races. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading `ready` and then reading `data`. Since there is no synchronization mechanism, the compiler/runtime cannot guarantee that the write operation in the goroutine is visible to the main goroutine before the loop condition is checked. The correct alternatives are: 1) Using a channel to signal completion (`<-doneChan`). 2) Using a `sync.WaitGroup` to wait for the goroutine to finish. 3) Using a `sync.Mutex` to protect access to `ready` and `data`.

**G8** — `sync.Mutex` provides exclusive locking; only one goroutine can hold the lock at a time, blocking all others. `sync.RWMutex` allows multiple readers to hold a shared lock simultaneously, but requires exclusive access for writers. Use `sync.Map` when you have a map where keys are frequently added, deleted, or updated concurrently, and you don't need complex transactional logic. Use a regular map protected by a `sync.Mutex` when reads vastly outnumber writes, or when you need fine-grained control over the map's structure, as mutex-protected maps often have lower overhead than `sync.Map` for high read/write ratios.

**G9** — Go modules manage dependencies. `go.mod` lists the required modules and their version constraints (e.g., `require github.com/pkg/errors v0.9.1`). `go.sum` contains cryptographic checksums for every dependency listed in `go.mod`, ensuring that the downloaded code has not been tampered with. `go mod tidy` cleans up the module file by adding missing dependencies and removing unused ones. Minimum Version Selection (MVS) is an algorithm that selects the highest possible version of a dependency that satisfies all specified version constraints across all required modules, ensuring dependency compatibility.

**G10** — A `defer` statement schedules a function call to be executed just before the surrounding function returns. If multiple `defer` statements exist, they execute in Last-In, First-Out (LIFO) order. A common gotcha in a loop is capturing the loop variable by reference (or closure capture). If you defer a function that references the loop variable, the deferred function will execute *after* the loop finishes, and it will use the final value of the loop variable, not the value from the iteration it was created in.

**G11** — A pointer in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`, meaning it points to no valid memory location. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12** — The `init()` function is a special function that runs automatically before the `main` function in a package. It is used for setup tasks, such as initializing global variables or registering drivers. A package can have multiple `init()` functions, and they execute sequentially in the order they appear in the source code files.

**G13** — `make` is used to initialize built-in reference types: slices, maps, and channels. It allocates and returns a pointer to the initialized data structure. `new` allocates memory for a value of a specified type and returns a pointer to the zero value of that type. `make` is for complex structures; `new` is for simple types (e.g., `new(int)` returns a pointer to a zero-value integer).

**G14** — Error handling in Go is explicit; functions typically return an `error` as the last return value. The `error` interface is a built-in interface defined as `type error interface { Error() string }`. The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain contains a specific sentinel error value. `errors.As(err, &target)` checks if the error chain contains a value that matches a specific type, allowing you to extract structured error information.

**G15** — Composite types are structures built from other types.
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be written to until initialized with `make`).
*   **Slice:** `[]Type`. Zero value: `nil` (a slice header pointing to a nil underlying array).
*   **Channel:** `chan Type`. Zero value: `nil` (a channel header pointing to a nil channel).
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.

**G16** — A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, leading to unpredictable and incorrect results. The `-race` flag enables the Go race detector, which instruments the code to detect concurrent memory accesses without synchronization.
Example Data Race: Two goroutines incrementing a shared counter without a lock.
Fix: Use `sync.Mutex`.
```go
var counter int
var mu sync.Mutex
go func() {
    mu.Lock()
    counter++
    mu.Unlock()
}()
```

**G17** — The `select` statement allows a goroutine to wait on multiple communication operations (channel sends or receives) simultaneously. It differs from `switch` because `select` is specifically designed for concurrency and channel operations. When multiple cases are ready, `select` chooses one pseudo-randomly. To implement a timeout, you use `select` alongside a `time.After` channel:
```go
select {
case msg := <-ch:
    fmt.Println("Received:", msg)
case <-time.After(5 * time.Second):
    fmt.Println("Timeout occurred")
}
```

**G18** — Escape analysis is the compiler's process of determining whether a variable's data should be allocated on the stack (fast, automatic cleanup) or the heap (slower, managed by the garbage collector). The compiler decides based on how long the variable's lifetime is and whether it needs to outlive the function call stack frame. You can inspect this using the `-m` flag during compilation. It matters for performance because stack allocation is significantly faster than heap allocation due to avoiding GC overhead and pointer indirection.

**G19** — The `reflect` package allows a program to inspect and manipulate its own structure (types, values, methods) at runtime. `reflect.Type` describes the structure of a value (e.g., its name, fields, methods). `reflect.Value` represents the actual value at runtime. Reflection incurs significant performance costs because the compiler cannot optimize calls involving reflection; it must perform dynamic lookups. Reflection is justified when building generic frameworks, serialization libraries, or ORMs where the structure must be unknown until runtime.

**G20** — The `go:embed` directive allows embedding files or directories directly into the compiled binary as byte slices. It works by specifying the path relative to the source file. For single files, directories, or file systems, you use the directive syntax: `//go:embed path/to/file` or `//go:embed path/to/dir`. Limitations include that the embedded data is static and cannot be modified at runtime. It interacts with `io/fs.FS` by providing an `fs.FS` interface implementation that allows the embedded content to be treated as a virtual file system accessible via standard I/O functions.
