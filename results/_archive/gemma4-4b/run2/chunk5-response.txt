## .NET / C#

DN1 — **Class vs Struct:** A `class` is a reference type, allocated on the heap, and supports inheritance. A `struct` is a value type, allocated on the stack (or inline), and is generally immutable and lightweight. Use a `struct` for small, simple data aggregates (like coordinates or colors) where copying the value is cheap and semantics are value-based.

DN2 — **IEnumerable<T> vs IQueryable<T>:** `IEnumerable<T>` represents an in-memory collection; operations (like `Where`) are executed locally after data is retrieved. `IQueryable<T>` represents an expression tree that describes a query. This distinction matters because `IQueryable<T>` allows the query provider (e.g., EF Core) to translate the LINQ expression into a database-specific query (SQL), executing the filtering/projection on the database server, which is vastly more efficient.

DN3 — **Async/Await, Task vs ValueTask:** `async/await` allows asynchronous code to be written in a synchronous-looking style by pausing execution until an awaited operation completes, without blocking the thread. A `Task` represents an asynchronous operation that might allocate memory for state machines. A `ValueTask<T>` is a struct that avoids heap allocation when the result can be returned synchronously (i.e., when the operation completes immediately), reducing GC pressure. Use `ValueTask` when you expect the operation to complete synchronously often, minimizing allocation overhead.

DN4 — **Dependency Injection (DI):** DI is a design pattern where components receive their dependencies from an external source (the IoC container) rather than creating them internally. The three lifetimes are:
1. **Transient:** A new instance is created every time it is requested.
2. **Scoped:** A single instance is created per scope (e.g., per HTTP request in ASP.NET Core).
3. **Singleton:** A single instance is created for the entire application lifetime.
A common bug is injecting a Scoped service (like `DbContext`) into a Singleton service. Since the Singleton lives for the entire application, it holds a reference to the Scoped instance, causing that instance to live longer than its intended scope, potentially leading to concurrency issues or incorrect state sharing across unrelated requests.

DN5 — **string vs ReadOnlySpan<char>:** `string` is an immutable, managed reference type, requiring heap allocation for any modification. `ReadOnlySpan<char>` is a stack-allocated, non-allocating view over existing character data (like a string or array). Use `Span<T>` when you need high-performance, low-allocation string/buffer manipulation, such as parsing or slicing, without creating new string objects.

DN6 — **Garbage Collector (GC):** The GC automatically manages memory by identifying and reclaiming objects that are no longer reachable by the application. It uses generations:
*   **Gen 0:** Where short-lived objects are allocated. Frequent, fast collections occur here.
*   **Gen 1:** Acts as a buffer between Gen 0 and Gen 2.
*   **Gen 2:** Where long-lived objects reside. Collections here are less frequent but more expensive.
The **Large Object Heap (LOH)** stores objects larger than a threshold (typically 85KB). LOH collections are less frequent and can cause fragmentation. `IDisposable` implements the Dispose pattern, allowing deterministic cleanup of unmanaged resources (like file handles or network sockets) *before* the GC runs, which is necessary because the GC only handles managed memory.

DN7 — **ConfigureAwait(false):** By default, `await` attempts to resume execution on the original `SynchronizationContext` (e.g., the UI thread or ASP.NET request context). `ConfigureAwait(false)` tells the runtime that the continuation does not need to resume on the original context. Use it when writing library code or high-throughput services where context switching is unnecessary, as it avoids potential deadlocks and improves performance. Do NOT use it when the continuation *must* interact with UI elements or context-specific state.

DN8 — **.NET 8/9 Features:**
*   **Primary Constructors:** Allow defining constructor parameters directly in the class signature, which can then be used for property initialization or DI injection.
*   **Collection Expressions:** Provide a concise syntax (`[1, 2, 3]`) for creating collections, simplifying initialization.
*   **FrozenDictionary:** An immutable dictionary that is optimized for read-only access, ensuring thread safety without locking overhead.
*   **Example:**
    ```csharp
    public class UserService(ILogger<UserService> logger) { /* ... */ }
    // In Program.cs:
    builder.Services.AddScoped<UserService>();
    ```

DN9 — **ObjectDisposedException in DbContext:** The likely cause is that the `DbContext` instance is being reused across multiple concurrent requests or threads without proper scoping. EF Core's `DbContext` is designed to be **scoped** (one per request). If a Singleton service holds a reference to a Scoped `DbContext`, that context might be disposed prematurely or shared incorrectly under load. The fix is to ensure the `DbContext` is registered as Scoped and injected only into services that are also Scoped (or Transient).

DN10 — **Record vs Class:** A `class` is a mutable, reference type, suitable for complex objects requiring inheritance. A `record` is designed for immutable data transfer objects (DTOs). Records automatically provide value equality (comparing contents, not references) and support non-destructive mutation (`with` expressions). A `record struct` combines the value semantics of a struct with the syntactic sugar of a record, ideal for small, immutable data carriers. Choose `record` for complex data models; choose `record struct` for small, immutable value types.

DN11 — **ref, out, in:**
*   **`ref`:** The variable must be initialized before being passed to the method. It allows the method to read and modify the original variable's value.
*   **`out`:** The variable does not need to be initialized before being passed. The method *must* assign a value to it before returning. Used when the method needs to return multiple values.
*   **`in`:** Used for passing large structs efficiently. It allows the method to read the value without copying it, but prevents the method from modifying the original variable.

DN12 — **Nullable Reference Types (NRTs):** NRTs (enabled by `#nullable enable`) allow the compiler to track potential nullability at compile time. The `?` annotation (e.g., `string?`) explicitly marks a reference type as potentially null. This differs from nullable value types (`int?`), which are structs that wrap a value type and can hold `null` because they are inherently nullable types. NRTs help eliminate `NullReferenceException`s at compile time.

DN13 — **LINQ:** LINQ (Language Integrated Query) is a set of features that allows developers to write queries against various data sources (collections, databases, XML) using a unified syntax.
*   **Method Syntax:** Uses extension methods (e.g., `list.Where(x => x > 5)`). It is generally preferred for complex logic as it is more fluent.
*   **Query Syntax:** Uses SQL-like syntax (e.g., `from x in list where x > 5`). It is often preferred for readability when translating SQL concepts.
*   **Deferred Execution:** Queries are not executed immediately upon definition. The query expression is built and only executed when the results are iterated over (e.g., in a `foreach` loop or when calling `.ToList()`).

DN14 — **Generic Constraints:** Constraints restrict the types that can be used for a generic type parameter `T`.
*   `where T : class`: T must be a reference type.
*   `where T : struct`: T must be a value type.
*   `where T : new()`: T must have a public parameterless constructor.
*   `where T : IComparable<T>`: T must implement the `IComparable<T>` interface, allowing comparisons between instances of T.
Combining constraints (e.g., `where T : class, new(), IComparable<T>`) ensures that the type `T` meets all specified requirements before the code compiles, guaranteeing that methods relying on those features will function correctly.

DN15 — **Abstract Class vs Interface:** An **abstract class** can contain both implemented methods and abstract methods, maintain state (fields), and support inheritance hierarchies. An **interface** defines a contract—it specifies *what* a class must do, but not *how*. Default interface methods (C# 8+) allow interfaces to provide default implementations, blurring the line by allowing interfaces to contain concrete logic, but they still primarily define a contract for behavior.

DN16 — **ASP.NET Core Middleware Pipeline:** The pipeline is a series of software components that process HTTP requests sequentially. Each middleware component inspects the request, performs an action (e.g., authentication, logging), and either passes the request to the next component or terminates the request/response cycle.
*   `app.Use()`: Registers middleware that processes the request/response flow (e.g., `UseAuthentication()`).
*   `app.Map()`: Maps a specific route or endpoint to a handler, often used for lightweight routing or minimal APIs.
*   `app.Run()`: Terminates the pipeline, usually used as the final endpoint handler.
Ordering is critical; middleware executes in the order it is registered. Exception handling middleware must be placed early in the pipeline to catch errors from subsequent components.

DN17 — **Channel<T>:** `Channel<T>` is a type-safe, asynchronous stream implementation in .NET, designed for producer-consumer scenarios. It is a modern, high-performance replacement for older blocking collections.
*   **Comparison to BlockingCollection<T>:** `BlockingCollection<T>` is thread-safe but synchronous and blocks threads when waiting for items. `Channel<T>` is asynchronous, using `await` to wait for items, which is non-blocking.
*   **Backpressure Example:** Using a **bounded channel** (e.g., `Channel.CreateBounded<T>(capacity)`) enforces backpressure. If the producer writes items faster than the consumer can read them, the channel fills up, and the producer's `WriteAsync()` call will asynchronously block until space becomes available, preventing memory exhaustion.

DN18 — **Source Generators:** Source Generators are compile-time code generators that inspect the syntax tree of the source code during compilation and generate new C# source files *before* the main compilation phase. They differ from reflection (runtime inspection) and IL weaving (modifying compiled IL) because they generate clean, standard C# code that the compiler consumes normally. An **incremental generator** is preferred because it only regenerates the code necessary when specific source files change, drastically improving build times compared to a standard `ISourceGenerator` which might re-run on broader changes.

DN19 — **TPL Dataflow:** TPL Dataflow provides powerful constructs for building asynchronous, data-flow pipelines.
*   **ActionBlock:** Executes an action (a delegate) asynchronously for each item received, often used for fire-and-forget processing.
*   **TransformBlock:** Receives an item, applies a transformation function to it, and outputs the result.
*   **BufferBlock:** Acts as a queue, buffering incoming items until a consumer processes them.
*   **Comparison to Channels:** Channels are fundamentally stream-based (producer $\rightarrow$ consumer), whereas TPL Dataflow is pipeline-based (a sequence of processing stages). Dataflow offers more sophisticated control over concurrency, throttling, and linking stages together using `LinkTo()`.

DN20 — **Minimal APIs:** Minimal APIs are a streamlined way to build HTTP endpoints directly in the `Program.cs` file using lambda expressions, bypassing the traditional MVC/Controller structure.
*   **Differences from Controllers:** Controllers use classes, routing attributes, and action methods; Minimal APIs use simple `app.MapGet("/endpoint", ...)` calls.
*   **Trade-offs:** Minimal APIs offer faster startup time, less boilerplate, and simpler code for small services. However, controllers offer better structure, built-in conventions, and easier separation of concerns for large, complex applications.
*   **Testability/Middleware/OpenAPI:** Testability is slightly simpler for unit testing the endpoint logic itself. Middleware integration is straightforward. OpenAPI support requires explicit configuration (e.g., using Swashbuckle) but is less automatic than in a full MVC setup.
*   **Route Groups/Endpoint Filters:** Route groups allow applying common middleware or constraints to a set of related endpoints. Endpoint filters allow intercepting the execution pipeline before or after the endpoint logic runs (e.g., for authorization checks).

## Python

P1 — **List vs Tuple, Set vs Frozenset:**
*   **List:** Mutable, ordered sequence, defined by `[]`. Allows duplicate elements.
*   **Tuple:** Immutable, ordered sequence, defined by `()`. Faster than lists and can be used as dictionary keys.
*   **Set:** Mutable collection of unique, unordered elements, defined by `{}`.
*   **Frozenset:** Immutable version of a set. Because it is immutable, it can be used as an element within another set or as a dictionary key.

P2 — **GIL (Global Interpreter Lock):** The GIL is a mutex that protects access to Python objects, ensuring that only one thread executes Python bytecode at any given time within a single process. It affects CPU-bound workloads (heavy computation) because threads cannot run truly in parallel. Workarounds include using the `multiprocessing` module (which spawns separate processes, each with its own GIL) or using C extensions (like NumPy) that release the GIL during heavy computation.

P3 — **Deepcopy vs Copy (Shallow):**
*   **Shallow Copy (`.copy()` or `copy.copy()`):** Creates a new container object, but populates it with *references* to the objects found in the original. If the original contains mutable objects (like lists), modifying those nested objects in the copy will affect the original.
*   **Deep Copy (`copy.deepcopy()`):** Creates a completely independent copy of the original object and recursively copies all nested objects.
*   **Example:** If `original = {'a': [1]}` and `shallow_copy = original.copy()`, then `shallow_copy['a'].append(2)` modifies the list in both `original` and `shallow_copy`. `deepcopy` prevents this.

P4 — **Decorators:** Decorators are syntactic sugar that allow you to wrap a function or method, modifying its behavior without permanently altering its source code. They take a function as input and return a new, enhanced function.
*   **Logging Decorator Example:**
    ```python
    import time
    from functools import wraps

    def timing_decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            start_time = time.time()
            result = func(*args, **kwargs)
            end_time = time.time()
            print(f"Function {func.__name__} executed in {end_time - start_time:.4f} seconds.")
            return result
        return wrapper

    @timing_decorator
    def slow_function(n):
        sum(i*i for i in range(n))
    ```

P5 — **Generators and Yield:** Generators are functions that return an iterator, allowing them to produce a sequence of results one at a time upon request, rather than computing and storing the entire sequence in memory at once. This is highly memory efficient for large datasets.
*   **`yield` vs `return`:** `return` terminates the function and sends a single value back. `yield` pauses the function's execution, sends a value back to the caller, and saves the function's state so it can resume from that exact point when the next value is requested.
*   **`yield from`:** Used to delegate iteration to another generator or iterable. It allows the parent generator to seamlessly pass through all values yielded by the sub-generator, simplifying complex pipeline construction.

P6 — **Asyncio Event Loop:** The event loop is the core mechanism of `asyncio`; it manages and schedules the execution of asynchronous tasks by monitoring I/O operations (like network requests) and switching between tasks when one is waiting for an external event, preventing thread blocking.
*   `asyncio.run(coro)`: Runs the top-level coroutine and manages the event loop lifecycle (starts, runs, stops).
*   `asyncio.gather(*coros)`: Runs multiple coroutines concurrently and waits for all of them to complete, returning a list of their results.
*   `asyncio.create_task(coro)`: Schedules a coroutine to run concurrently on the event loop immediately, returning a `Task` object that can be awaited later.
*   **`time.sleep()`:** This is a blocking call. If called inside an `async` function, it halts the entire event loop, preventing *all* other scheduled tasks from running, defeating the purpose of asynchronous programming. Use `await asyncio.sleep(delay)` instead, which yields control back to the event loop.

P7 — **MRO (Method Resolution Order):** MRO dictates the order in which Python searches the class hierarchy for a method or attribute. Python 3 uses the **C3 Linearization Algorithm**. This algorithm ensures a consistent, predictable inheritance order that respects the local precedence of classes while maintaining the overall hierarchy structure.
*   **Diamond Inheritance:** When a class inherits from two classes that share a common ancestor (the diamond shape), C3 ensures that the ancestor is visited only once, following the order specified in the inheritance list.
*   **Output Explanation:** `D` inherits from `B` then `C`. `B` inherits from `A`. The MRO for `D` is `(D, B, C, A, object)`. When `D().who()` is called, Python checks `D` (no `who`), checks `B` (no `who`), checks `C` (has `who` returning "C"), and executes that method.

P8 — **Metaclass:** A metaclass is the "class of a class." It controls how a class itself is created. When you define a class, Python uses its metaclass to build the class object.
*   **`__init_subclass__` vs Metaclass:**
    *   **`__init_subclass__`:** A class method defined *within* the subclass. It is called *after* the subclass has been created, allowing you to modify or validate the subclass's attributes or behavior based on its parent classes. (Use for runtime configuration/validation).
    *   **Metaclass:** Controls the *creation* process itself. It intercepts the class definition before the class object exists, allowing you to inject methods, enforce structural rules, or modify the class dictionary during construction. (Use for structural enforcement/automatic boilerplate generation).
*   **Use Case:** Use `__init_subclass__` to automatically add logging hooks to all subclasses of a base service. Use a Metaclass to enforce that every class inheriting from a base model must implement a specific set of fields.

P9 — **Multiprocessing, Threading, Concurrent.futures:**
*   **Threading:** Uses threads within a single process. Best for I/O-bound tasks (waiting for network/disk) because the GIL releases during I/O waits. Limited by the GIL for CPU-bound tasks.
*   **Multiprocessing:** Uses separate OS processes. Bypasses the GIL, allowing true parallel execution on multi-core CPUs. Best for CPU-bound tasks.
*   **Concurrent.futures:** Provides a high-level interface (`ThreadPoolExecutor` for threads, `ProcessPoolExecutor` for processes) to manage and submit tasks to the underlying executors, simplifying asynchronous execution management.
*   **Serialization:** Multiprocessing requires serialization (pickling) to pass data between processes. This overhead can be significant for large objects, but it is necessary for true parallelism.

P10 — **`__slots__`:** `__slots__` is a class attribute that explicitly declares the attributes an instance of the class will have. When defined, Python does not create a standard instance dictionary (`__dict__`) for each object.
*   **When to use:** When creating classes with many instances where memory footprint is critical (e.g., large collections of small data objects).
*   **What it prevents:** It prevents the dynamic addition of new attributes to instances after creation.
*   **Memory Impact:** It significantly reduces memory usage by replacing the flexible, dictionary-based storage with a fixed, optimized structure, leading to lower memory overhead per instance.

P11 — **Virtual Environment:** A virtual environment is an isolated Python installation containing a specific set of packages and dependencies for a project. This prevents dependency conflicts between different projects on the same machine.
*   **`venv`:** The standard, built-in module in Python 3.3+ for creating lightweight virtual environments.
*   **`virtualenv`:** A third-party package that is more feature-rich and compatible with older Python versions than `venv`.
*   **`conda`:** A package and environment manager primarily used in data science. It manages not just Python packages but also non-Python dependencies (like compilers or scientific libraries), making it broader than standard Python virtual environments.

P12 — **Comprehensions:** Comprehensions provide a concise, readable syntax for creating collections based on existing iterables.
*   **List Comprehension:** `[expression for item in iterable if condition]` (Creates a list).
*   **Dict Comprehension:** `{key: value for item in iterable if condition}` (Creates a dictionary).
*   **Set Comprehension:** `{expression for item in iterable if condition}` (Creates a set).
*   **Relation to map/filter:** Comprehensions combine the functionality of `map()` (transformation) and `filter()` (selection) into a single, cleaner syntax.
*   **Preference:** Comprehensions are generally preferred over `map()` and `filter()` because they are more Pythonic, readable, and often slightly faster due to optimized C implementation.

P13 — **== vs is:**
*   **`==`:** Checks for *equality* (value comparison). It calls the object's `__eq__` method.
*   **`is`:** Checks for *identity* (memory location comparison). It checks if two variables point to the exact same object in memory (i.e., if their `__hash__` and `__eq__` methods agree, and they are the same object).
*   **Object Interning:** Python pre-allocates and caches certain immutable objects (like small integers, e.g., -5 to 256, and short strings) to save memory. When you create `a = 10` and `b = 10`, Python often points both variables to the same cached object, causing `a is b` to be `True`.

P14 — **\*args and \*\*kwargs:**
*   **`*args`:** Collects any number of positional arguments into a tuple.
*   **`**kwargs`:** Collects any number of keyword arguments into a dictionary.
*   **Positional-only (`/`):** Arguments placed before `/` must be passed positionally and cannot be passed using keyword names (e.g., `def func(a, /, b):`).
*   **Keyword-only (`*`):** Arguments placed after `*` must be passed using keyword names (e.g., `def func(a, *, b):`). This enforces clarity and prevents ambiguity.

P15 — **Context Managers:** Context managers are objects that define the setup and teardown logic for a block of code, ensuring resources are properly acquired and released, even if errors occur.
*   **`with` statement:** The syntax used to utilize a context manager.
*   **`__enter__` / `__exit__`:** The methods implemented by the context manager class. `__enter__` runs upon entering the `with` block (returns the resource), and `__exit__` runs upon exiting (handles cleanup).
*   **`@contextmanager`:** A decorator from `contextlib` that allows you to write a context manager using a generator function. The code before `yield` is setup, and the code after `yield` is teardown.
*   **Example (Locking):** Using a `threading.Lock` as a context manager: `with lock: # critical section #` ensures the lock is acquired before the block and automatically released afterward.

P16 — **Type Hinting:** Type hinting allows developers to optionally specify the expected types for variables, function arguments, and return values. Static type checkers (like Mypy or Pyright) use these hints to perform static analysis, catching type errors before runtime.
*   **`typing.Union[A, B]`:** Indicates a variable can be of type A OR type B.
*   **`Optional[T]`:** A shorthand for `Union[T, None]`, indicating the variable can be T or None.
*   **`Literal[A, B]`:** Restricts a variable to only one of the specified literal values (e.g., `Literal["success", "fail"]`).
*   **`TypeVar`:** A placeholder for types that will be specified later, crucial for writing generic functions that maintain type safety across different types.
*   **`Protocol`:** Defines a structural type check. Instead of inheriting from a class, a class conforms to a `Protocol` if it implements the required methods/attributes, enabling duck typing with static analysis.

P17 — **Data Model (Dunder Methods):** Dunder methods (Double Underscore) are special methods that Python calls automatically to implement core language features.
*   **`__repr__` vs `__str__`:** `__repr__` (representation) should return an unambiguous, developer-friendly string that ideally allows the object to be recreated. `__str__` (string) should return a readable, end-user friendly string.
*   **`__eq__` vs `__hash__`:** `__eq__` defines equality comparison (`a == b`). `__hash__` defines how the object is mapped to an integer for use in hash-based collections (sets, dict keys).
*   **Missing `__hash__`:** If you define `__eq__` but *not* `__hash__`, Python will typically raise a `TypeError` if you try to use that object as a dictionary key or add it to a set, because the object cannot be reliably hashed.

P18 — **Descriptors:** A descriptor is an object attribute that defines how attribute access (getting, setting, deleting) behaves. It implements the descriptor protocol: `__get__`, `__set__`, and `__delete__`.
*   **Protocol:** When you access an attribute on an instance, Python checks if the attribute is a descriptor. If it is, it calls the descriptor's `__get__` method instead of simply returning the value.
*   **Usage:**
    *   **`property`:** Uses descriptors to manage attribute access (getters/setters).
    *   **`classmethod`:** Uses descriptors to ensure the method is bound to the class, not the instance.
    *   **`staticmethod`:** Uses descriptors to ensure the method is bound neither to the class nor the instance, acting as a regular function within the class namespace.

P19 — **Import System:** The import system locates and loads modules.
*   **Relative vs Absolute Imports:**
    *   **Absolute:** Imports start from the root of the package (e.g., `from my_package import module`).
    *   **Relative:** Imports reference modules relative to the current package (e.g., `from . import sibling_module`).
*   **Mechanisms:**
    *   **`sys.path`:** A list of directories Python searches when an `import` statement is encountered.
    *   **`PYTHONPATH`:** An environment variable that adds directories to `sys.path` before execution.
    *   **`__init__.py`:** Historically marked a directory as a Python package. While less strictly required in modern Python (namespace packages), it is still used to define package-level initialization logic.
    *   **Namespace Packages:** Allow multiple, unrelated packages to contribute to the same top-level namespace without being physically located in the same directory.
*   **Finder/Loader:** A **Finder** is responsible for locating a module (finding the path). A **Loader** is responsible for loading the module once found (executing the code and creating the module object).

P20 — **Dataclasses vs attrs vs Pydantic:**
*   **Dataclasses:** A standard library feature (Python 3.7+) that automatically generates boilerplate methods (`__init__`, `__repr__`, `__eq__`) for classes primarily used to hold data. They are lightweight and simple.
*   **`attrs`:** A third-party library that predates dataclasses and offers similar functionality, often with more customization options.
*   **Pydantic:** A library focused on data validation and serialization. It uses type hints heavily to enforce strict data schemas at runtime.
*   **Features:**
    *   **`__post_init__`:** A method in dataclasses called immediately after `__init__` completes, useful for derived attribute calculation.
    *   **Field Factories:** Allows defining default values that are computed dynamically rather than being static constants.
    *   **Frozen Dataclasses:** Set `frozen=True` to make the instance immutable, similar to a tuple.
    *   **Inheritance:** Dataclasses support inheritance, but careful use is needed to manage generated methods correctly.
*   **Pydantic vs Dataclasses:** Choose **Pydantic** when data *validation* is critical (e.g., API request bodies, configuration files) because it enforces types and raises clear errors if data is malformed. Choose **Dataclasses** when you simply need a lightweight, immutable container for data within your application logic where runtime validation is handled elsewhere.
