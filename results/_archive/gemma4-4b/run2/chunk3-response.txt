**T1** — Easy: What is the difference between tofu plan and tofu apply?
`tofu plan` is a dry run that compares the desired state defined in the configuration files (HCL) against the current state recorded in the state file and the actual state in the cloud provider. It outputs a detailed execution plan showing exactly what resources will be created, modified, or destroyed, but it makes no changes. `tofu apply` executes the plan, making the actual changes to the infrastructure defined by the configuration.

**T2** — Easy: What is state in OpenTofu, and why is remote state important?
The state file (`terraform.tfstate`) is a mapping that records the real-world infrastructure resources managed by OpenTofu, linking them to the configuration resources (e.g., mapping a specific AWS EC2 ID to the `aws_instance` resource block). Remote state is crucial because it stores this state file externally (e.g., S3, Azure Blob Storage), enabling collaboration among team members, providing durability against local machine failure, and allowing for state locking.

**T3** — Medium: Explain the difference between count and for_each. When is for_each preferred?
`count` creates a specified number ($N$) of identical instances, using an integer index (0, 1, 2, ...) to differentiate them. `for_each` creates instances based on the keys of a map or the elements of a set. `for_each` is preferred when the instances need a stable, meaningful identity (e.g., `web1`, `web2`) rather than a sequential index, as it maintains state stability even if the order of elements changes.

**T4** — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?
This is known as configuration drift. OpenTofu detects this drift during the `tofu plan` phase. It queries the cloud provider's API to retrieve the *actual* current configuration of the resource and compares it against the *desired* configuration in the HCL. If differences are found, OpenTofu flags them in the plan, indicating that a modification is required to bring the infrastructure back into compliance with the code.

**T5** — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
```hcl
resource "aws_instance" "web_servers" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-0abcdef1234567890"
  instance_type = "t2.micro"

  tags = {
    Name = each.key
  }
}
```

**T6** — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
**Output Values** expose data *from* the current module/root module to consumers. **`terraform_remote_state` data source** allows a module to read the state file of an *entirely separate* OpenTofu configuration. While functional, relying heavily on `terraform_remote_state` creates tight coupling and makes the configuration brittle, as the dependency is on the external state file structure. The recommended alternative is to pass necessary data explicitly using **module inputs (variables)** or to use a dedicated, shared data source (if the data is public/API-driven) rather than relying on another module's state.

**T7** — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.
The failure occurs because the dependency graph executes the `null_resource` provisioner *before* the remote execution command has completed and written the kubeconfig file, or before the resource output has been fully populated by the provider. The fix is to explicitly enforce dependency using `depends_on`. The resource that consumes the kubeconfig must explicitly list the `null_resource` (or the resource that generates the output) in its `depends_on` block.

**T8** — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
`tofu import` allows you to bring an existing, manually provisioned resource from the cloud into the OpenTofu state file without having to write the configuration code first. Its limitation is that it only records the *ID* and *current attributes* in the state; it does not define the desired configuration logic. The import block (introduced in later versions) improves this by allowing the user to define the resource type and the ID within the HCL file itself, making the import process declarative and tying the state entry directly to the configuration structure.

**T9** — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
A **variable** is a placeholder for input data that is passed into a configuration (e.g., region name, instance count). It allows the configuration to be reusable and parameterized. An **output** is a value exposed by the configuration after it has been applied (e.g., the public IP address of a created VM). Outputs allow other modules or root configurations to consume the results of the deployment.

**T10** — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
A provider is a plugin that enables OpenTofu to interact with a specific API or service (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without `tofu init`, the plan will fail because OpenTofu has not downloaded, configured, or initialized the necessary provider plugins. `tofu init` handles the downloading and configuration of these providers.

**T11** — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
The `.terraform.lock.hcl` file records the exact versions and checksums of every provider and module dependency used in the configuration. It should be committed to version control to ensure that every developer and every CI/CD pipeline uses the exact same dependency versions, preventing unexpected behavior or breakage caused by upstream provider updates.

**T12** — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
`tofu destroy` removes all infrastructure resources managed by the current state file. To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web_servers["web1"]`).

**T13** — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
A data source is a mechanism that allows OpenTofu to fetch information about existing infrastructure or external data without managing that infrastructure. Example: Using a `aws_ami` data source to look up the latest Amazon Machine Image ID for a specific region. You use it instead of a managed resource when you need to *read* configuration details (like the latest AMI or a VPC ID) but do not want OpenTofu to *manage* or control that resource's lifecycle.

**T14** — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
**Variable blocks** define external inputs that must be provided by the user or environment. **Locals** define internal, computed values within the configuration scope (module or root). You should use locals when you need to perform complex calculations, string manipulations, or define intermediate values based on existing inputs or resources, but these values do not need to be configurable by the end-user.

**T15** — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
The lifecycle block controls how OpenTofu manages a resource during updates.
*   **`create_before_destroy`**: Creates the new resource instance *before* destroying the old one. Use case: Zero-downtime database migration or VM replacement.
*   **`prevent_destroy`**: Prevents the resource from being deleted, even if a `tofu destroy` command is run. Use case: Protecting critical production resources (e.g., a primary load balancer).
*   **`ignore_changes`**: Tells OpenTofu to ignore specific attributes during updates. Use case: When an external system (like a monitoring agent) modifies a tag or metadata field that you do not want OpenTofu to revert.

**T16** — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
A moved block allows you to relocate a resource definition from its current location to a new location (e.g., moving it from one module to another) while preserving its existing state history and ID. This is critical during refactoring because it allows you to restructure your codebase without forcing OpenTofu to treat the resource as new, thus avoiding unnecessary destruction and recreation cycles.

**T17** — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
OpenTofu builds a Directed Acyclic Graph (DAG) where nodes are resources and edges represent dependencies. **Implicit dependencies** occur when one resource references an attribute of another (e.g., `subnet_id = aws_vpc.main.id`). **Explicit dependencies** are defined using `depends_on`. `depends_on` forces sequential execution, meaning the dependent resource will not start until the dependency is fully complete, regardless of whether the dependency is actually referenced. It should be used sparingly because it artificially serializes operations, preventing OpenTofu from running independent resources in parallel, which negates the speed benefits of the tool.

**T18** — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
1. **Modularization:** Break the large configuration into smaller, focused modules. *Tradeoff:* Increased complexity in managing module dependencies.
2. **State Splitting:** Separate large, independent resource groups into different state files. *Tradeoff:* Increased operational overhead (managing multiple state files).
3. **Targeted Planning:** Use `tofu plan -target=...` to only plan changes for specific components. *Tradeoff:* Requires deep knowledge of the codebase structure; not suitable for full audits.
4. **Provider Caching/Optimization:** Ensure providers are configured to cache data where possible. *Tradeoff:* Requires specific provider support and careful management of cache invalidation.

**T19** — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
State locking prevents concurrent modifications to the state file, ensuring only one operation modifies the state at a time, preventing corruption. If a lock is not released (e.g., due to a crash), the state remains locked, causing all subsequent operations to hang indefinitely. Manually breaking a lock requires administrative access to the backend service (e.g., deleting the lock key in DynamoDB or S3 metadata). The risk is extremely high: manually breaking a lock without understanding the state's current transaction can lead to severe state corruption, requiring a full state recovery or rebuild.

**T20** — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
1. **Configure Backend:** Update the `backend` block in the configuration to point to the S3 bucket and specify the DynamoDB table name for locking.
2. **Initialize:** Run `tofu init`. OpenTofu will detect the new backend configuration and prompt you to migrate the existing local state file to the remote backend.
3. **Migration:** Confirm the migration. OpenTofu uploads the local state file to S3 and registers the lock mechanism with DynamoDB. The local state file is then effectively discarded/superseded.
4. **Verification:** Run `tofu plan`. If the plan executes successfully and shows the correct resources, the migration succeeded. If it fails, check the backend configuration and permissions.

**A1** — Easy: What is the difference between an Ansible playbook, a role, and a task?
**Playbook:** The top-level YAML file that defines the entire automation workflow, specifying which hosts to target, which roles to run, and which tasks to execute. **Role:** A standardized, reusable directory structure containing related tasks, handlers, variables, and templates for a specific function (e.g., `webserver`, `database`). **Task:** A single unit of work within a playbook or role, defining a specific action to be performed on the target host (e.g., `apt: name=nginx state=present`).

**A2** — Easy: What is ansible_facts and how do you access the OS family of a target host?
`ansible_facts` is a dictionary containing gathered information about the target host (e.g., IP address, memory, OS version). You access the OS family using the Jinja2 template syntax: `{{ ansible_facts['os_family'] }}`.

**A3** — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
*   **`command`**: Executes a command directly. It is idempotent-aware (it doesn't interpret shell features like pipes or redirection). Use this for simple, atomic commands.
*   **`shell`**: Executes a command through the host's shell (e.g., Bash). It supports shell features like pipes (`|`), wildcards, and redirection. Use this for complex scripting.
*   **`raw`**: Executes a command directly without invoking the shell. It is the lowest level and should be used rarely, typically only when you need to bypass all shell interpretation.

**A4** — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
Idempotency means that running the same task multiple times yields the same result without causing unintended side effects. Ansible achieves this by using modules that check the current state before making changes.
*   **Idempotent Example:** `ansible.builtin.package: name=nginx state=present`. If Nginx is installed, Ansible does nothing; if not, it installs it.
*   **Non-Idempotent Example:** `ansible.builtin.command: echo "Hello World" >> /tmp/log.txt`. Running this task repeatedly will append "Hello World" multiple times to the file.

**A5** — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.
```yaml
- name: Install monitoring tools based on OS
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_facts['os_family'] == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_facts['os_family'] in ['Debian', 'RedHat']
```

**A6** — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
Ansible resolves variables based on a strict precedence order (highest priority listed first):
1. **`extra_vars`**: Variables passed directly on the command line (`-e`).
2. **`host_vars`**: Variables specific to a single host in the inventory.
3. **`group_vars`**: Variables specific to a group of hosts in the inventory.
4. **`role_defaults`**: Variables defined in the `defaults/main.yml` file within a role.
5. **Inventory Variables**: Variables defined directly in the inventory file.
6. **Environment Variables**: Variables set in the shell environment.

**A7** — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.
You would use the `serial` keyword in the play definition.
```yaml
- name: Deploy RKE2 Agent
  hosts: all
  serial: 3  # Only 3 hosts run concurrently before waiting for them to finish
  tasks:
    - name: Install RKE2
      ansible.builtin.shell: |
        # RKE2 installation commands here
      register: install_result
    
    - name: Wait for service to be ready
      ansible.builtin.wait_for:
        port: 6443
        host: "{{ inventory_hostname }}"
        timeout: 300
      when: install_result.rc == 0
```
The `serial: 3` ensures that only 3 hosts are processed in parallel. The `wait_for` task ensures that the deployment waits until the service is actually reachable before proceeding to the next stage.

**A8** — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
`ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible files. To encrypt a single variable without encrypting the entire file, you must use the vault mechanism when defining that specific variable in the YAML, often by referencing an encrypted variable file or using the vault command to encrypt only that specific line/block.

**A9** — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?
An inventory file defines the target hosts and groups that Ansible will manage. A **static inventory** is a manually maintained file (INI or YAML format) listing hostnames or IP addresses. A **dynamic inventory** is generated on the fly by a script or plugin that queries an external source (like AWS, VMware, or Kubernetes API) to discover and populate the list of hosts.

**A10** — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```
(Alternatively, using the `shell` module if complex piping is needed: `ansible webservers -m shell -a "df -h"`)

**A11** — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
A handler is a special task that is queued and only executed when explicitly notified by another task. The difference is that regular tasks run immediately in sequence, while handlers wait until the end of the play to run, ensuring that all necessary changes have been made before the service is restarted. You trigger a handler using the `notify:` keyword in a task.

**A12** — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
The `ansible.cfg` file is a configuration file that controls how Ansible behaves globally. It allows you to override default settings without modifying playbooks. Common settings include:
1. `inventory`: Specifies the path to the inventory file.
2. `remote_user`: Defines the default SSH user to connect as.
3. `forks`: Sets the number of parallel connections Ansible should make.

**A13** — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
The `register` keyword captures the output of a task (stdout, return code, results dictionary) into a variable. You use the registered variable in a subsequent task by referencing it using Jinja2 syntax, typically accessing the standard output: `{{ task_name.stdout }}`.

**A14** — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
*   **`import_tasks`**: Loads tasks into the current file as if they were written there. It is evaluated *before* the play starts and does not support conditional logic (`when:`). Use this for static inclusion of task sets.
*   **`include_tasks`**: Loads tasks dynamically during runtime. It supports conditional logic (`when:`), allowing you to selectively run subsets of tasks based on host facts or variables. Use this for dynamic, conditional execution.

**A15** — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
Ansible Galaxy is a community repository where users share reusable Ansible roles and collections. To install dependencies listed in a `requirements.yml` file, you run the command: `ansible-galaxy install -r requirements.yml`. This command reads the file and downloads all specified roles and collections into the local Ansible path.

**A16** — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
Connection plugins define the protocol Ansible uses to communicate with the target host.
*   **`ssh`**: The standard connection, used for remote execution over SSH. Use this for Linux/Unix servers.
*   **`local`**: Executes tasks directly on the Ansible control node itself. Use this for local file manipulation or running scripts on the machine running Ansible.
*   **`network_cli`**: Uses CLI protocols (like Telnet or SSH) to interact with network devices (routers, switches). Use this for network infrastructure automation.

**A17** — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
*   **`delegate_to: localhost`**: Forces a task to execute on the Ansible control node, even if the play is targeting remote hosts.
*   **`run_once: true`**: Ensures that the task, when delegated, executes only one time across the entire host group.
*   **Example:** To gather the IP addresses of all 50 web servers and write them to a single file on the control node:
    ```yaml
    - name: Gather IPs and write to file
      ansible.builtin.setup:
        gather_subset:
          - network
      delegate_to: localhost
      run_once: true
      register: all_ips
    - name: Write IPs to inventory file
      ansible.builtin.copy:
        content: "{{ all_ips.ansible_facts.all_hosts | join('\n') }}"
        dest: /tmp/all_hosts.txt
      delegate_to: localhost
    ```

**A18** — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).
1. **Increase `forks`**: Increase the number of parallel connections. *Tradeoff:* Higher load on the control node and target hosts.
2. **Fact Caching**: Cache gathered facts on the target hosts. *Tradeoff:* Requires persistent storage on the target hosts; initial setup complexity.
3. **Serial Batches (`serial`)**: Use small batches (e.g., `serial: 10`) instead of running all 500 at once. *Tradeoff:* Slower overall completion time, but prevents resource exhaustion on the control node.
4. **Mitogen/Tower (Orchestration)**: Use a dedicated orchestration platform. *Tradeoff:* Significant infrastructure investment and learning curve, but provides superior scaling and management.

**A19** — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.
Jinja2 is the templating engine used by Ansible.
*   **`{{ variable }}`**: Variable interpolation (outputting a value).
*   **`{% control_structure %}`**: Logic control (loops, conditionals, assignments).
*   **`{# comment #}`**: Comments that are stripped from the final output.
**Snippet:**
```nginx
upstream backend_servers {
{% for server in backend_list %}
    server {{ server.ip }}:{{ server.port }}; # Health check target: {{ server.name }}
{% endfor %}
}
```

**A20** — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.
1. **Serial Batches:** Set `serial: 1` or a small batch size (e.g., 3) to ensure only a few servers are updated at a time.
2. **Pre-Task (Registration):** Before updating a host, register it with the load balancer (LB) using the LB module.
3. **Deployment:** Run the application update tasks.
4. **Health Check:** Use the `uri` module to perform a health check against the newly updated server's endpoint.
5. **Post-Task (Verification/Rollback):** Wrap the deployment and health check in a `block/rescue` structure.
    *   If the health check succeeds, proceed to the next host.
    *   If the health check fails, the `rescue` block executes, which triggers a rollback task (e.g., reverting the application code or deregistering the failed host from the LB).
6. **Finalization:** Only after all hosts pass the health check are they fully promoted.
