## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:**
The pods are failing because the new base image (`cgr.dev/chainguard/static:latest`) defaults the container's `USER` to `root`. The cluster upgrade enforced the **Restricted Pod Security Standard (PSS)** at the namespace level. The Restricted PSS mandates that containers must run as a non-root user (`runAsNonRoot: true`) and often requires explicit user ID definitions. Since the pods only specified `runAsNonRoot: true` but did not explicitly set `runAsUser`, the container defaults to running as root (due to the image default), which violates the Restricted PSS policy. The change from Baseline to Restricted enforcement tightened the security posture, specifically by enforcing stricter non-root execution requirements that the new image default violated.

**SC1-B:**
```bash
kubectl get pods --all-namespaces -o json | jq -r '.items[] | select(.status.phase == "CrashLoopBackOff") | "\(.metadata.namespace) \(.metadata.name) | \(.spec.securityContext)"'
```

**SC1-C:**
**Immediate Fix:**
1.  **Image-level fix:** Rebuild the Go and Python microservices using a base image that explicitly sets a non-root user (e.g., `USER appuser` or using a minimal image like `distroless` that enforces non-root execution).
2.  **Manifest change:** Update the deployment manifests to explicitly set `runAsUser` to a specific non-root UID (e.g., `runAsUser: 1000`) in the `securityContext` block, overriding the image default.

**Recurrence Prevention & Rollout:**
*   **CI Pipeline Gate:** Implement a security scanning step (e.g., using Trivy or Grype) that checks the image metadata for the default `USER` directive. Furthermore, integrate a policy engine (like OPA Gatekeeper) into the CI/CD pipeline that validates the Kubernetes manifest, ensuring `securityContext.runAsNonRoot` is present *and* that `securityContext.runAsUser` is explicitly defined for all production deployments.
*   **Zero-Downtime Rollout:** Use a rolling update strategy (`maxSurge: 25%`, `maxUnavailable: 25%`) via Kubernetes Deployment objects. The new, compliant image/manifests are deployed gradually. Since the old pods are still running and healthy, the new pods will start, fail the PSS check, and crash, but the existing traffic will continue to be served by the old, healthy pods until the new pods are successfully replaced.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:**
The stale data issue arises because the cross-region replica was likely configured for **asynchronous replication**. When the primary failed, the replica was promoted *before* all Write-Ahead Log (WAL) records generated on the old primary were successfully shipped and applied to the replica. The data loss window is the time between the last successful WAL shipment and the moment the primary failed. PostgreSQL streaming replication handles WAL shipping by continuously sending WAL segments over the network. Asynchronous replication means the primary commits a transaction and acknowledges success *before* the replica confirms receipt, leading to potential data loss if the primary crashes before the WAL reaches the replica. To quantify data loss, one would check the `pg_stat_replication` view on the old primary (if accessible) or examine the WAL archive logs/replication slot status on the new primary to determine the last applied LSN (Log Sequence Number) before promotion.

**SC2-B:**
The goal is to transition the promoted replica into the primary role within Terraform state without destroying the old resources.

1.  **Import the promoted replica:** Since the promoted replica is now a standalone instance, you must import it into the state file using its new ARN/identifier.
    ```bash
    terraform import aws_db_instance.new_primary_instance <ARN_of_promoted_replica>
    ```
2.  **Update dependent resources:** Manually update all references in the Terraform code (e.g., `aws_security_group_rule`, `aws_route53_record`) to point to the new instance ARN/identifier.
3.  **Detach/Deprecate old instance:** Once all applications are confirmed pointing to the new primary, the old RDS instance can be safely deleted or marked for archival.
    ```bash
    terraform destroy -target=aws_db_instance.old_primary_instance
    ```
    *Note: The `import` command brings the resource into state; subsequent `apply` commands will manage its configuration.*

**SC2-C:**
**Architecture Design:**
*   **Connection Management:** Use **RDS Proxy** in the EU region. RDS Proxy handles connection pooling, multiplexing, and automatic failover detection, significantly reducing the load on PgBouncer and mitigating connection retry errors during transient network issues or failovers.
*   **DNS Failover:** Implement **Route53 Health Checks** targeting the primary endpoint in each region. Use weighted or failover routing policies. If the US endpoint fails the health check, traffic is automatically routed to the EU endpoint.
*   **Application Logic:** Implement **exponential backoff and jitter** in the application layer for transient database connection errors.
*   **RPO < 1 second:** This requires **Synchronous Replication**.
*   **Aurora Global Database:** Yes, I would strongly recommend Aurora Global Database. It is specifically designed for low-latency, cross-region disaster recovery, offering near-zero RPO by maintaining a dedicated, highly optimized replication channel that supports synchronous or near-synchronous replication across regions, far surpassing standard RDS cross-region read replica capabilities.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
| Blocker | Problem in K8s | Specific Solution |
| :--- | :--- | :--- |
| **1. Local Session State** | Kubernetes is ephemeral; pods are disposable. Local memory state is lost on restart/reschedule. | Externalize state to a distributed, highly available store (e.g., Redis Cluster, Hazelcast) accessible by all pods. |
| **2. Local NFS Mount (/data/uploads)** | Kubernetes storage must be provisioned via CSI drivers, not local mounts. | Implement a robust, highly available, shared storage solution (e.g., NFS CSI driver, CephFS, or cloud block storage with ReadWriteMany access). |
| **3. On-Prem Oracle 19c DB** | Kubernetes is designed for cloud-native services; direct, high-latency connection to legacy on-prem DB is brittle. | Use a dedicated, highly resilient connection layer (e.g., a dedicated cluster of stateful sets/sidecars) or migrate the data to a cloud-native managed database service. |
| **4. IBM MQ Integration** | MQ clients are often tightly coupled to specific host IPs and network configurations, making containerization difficult. | Abstract the MQ interaction using a dedicated message broker service running in Kubernetes (e.g., Kafka, RabbitMQ) that acts as a translation layer between the monolith and the mainframe MQ. |
| **5. F5 Sticky Sessions** | Kubernetes load balancing (Ingress/Service) is typically stateless by default. Sticky sessions are complex to enforce reliably across dynamic pod IPs. | Refactor the application to be truly stateless. **Necessity of ReadWriteMany:** ReadWriteMany (RWX) access mode is necessary because the monolith needs to write uploaded files to the NFS mount, and multiple replicas of the monolith (running in different pods/containers) must be able to read and write to the *same* shared file system concurrently. ReadWriteOnce (RWO) only allows a single pod to mount and write to the volume at any given time.

**SC4-C:**
**Phased Migration Plan (Strangler Fig Pattern):**

**Phase 1: Data and Session Abstraction (Strangling State)**
*   **What moves:** User session state and file uploads.
*   **Action:** Refactor the monolith to use an external, highly available Redis Cluster (for sessions) and point file uploads to the new Kubernetes NFS PVC (for uploads). The monolith remains running on bare metal, but its state dependencies are externalized.
*   **Zero-Downtime:** No traffic change. The monolith now uses the new external services while still running on the old infrastructure.
*   **Rollback:** If Redis/NFS fails, the monolith continues using its local state/NFS mount until the external service is restored.
*   **Go/No-Go:** Successful integration tests showing session persistence and file upload integrity across multiple monolith instances.

**Phase 2: Service Extraction and Traffic Shifting (Strangling Logic)**
*   **What moves:** Non-critical, stateless business logic (e.g., product catalog lookup, user profile retrieval).
*   **Action:** Extract these functions into new microservices deployed on Kubernetes. Use the F5 BIG-IP to route a small percentage (e.g., 5%) of traffic to the new Kubernetes Ingress/Service Mesh.
*   **Handling MQ:** The new microservices communicate with the mainframe via a dedicated, resilient adapter service running in Kubernetes, which handles the MQ protocol translation.
*   **Rollback:** If the new microservice fails, the F5 immediately routes 100% of traffic back to the legacy monolith.
*   **Go/No-Go:** Latency and error rate of the new microservices must match or beat the legacy monolith under load testing.

**Phase 3: Monolith Decommissioning (Final Cutover)**
*   **What moves:** Core transactional logic and the database connection.
*   **Action:** The monolith is refactored to communicate with the new microservices for all non-core functions. The final database connection is migrated (potentially via a dual-write pattern) to the new cloud-native database. The F5 is reconfigured to point 100% of traffic to the Kubernetes Ingress.
*   **Rollback:** If the new system fails, the F5 is instantly reverted to point to the legacy monolith (which is kept running in a warm standby state).
*   **Go/No-Go:** Sustained performance metrics (p99 latency, throughput) matching or exceeding the legacy baseline for 48 hours.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A:**
**Systematic Debugging Approach:**
1.  **Istio/Envoy Metrics:** Examine `istio_request_duration_milliseconds` for the `checkout-service` $\rightarrow$ `inventory-service` route. Look specifically at metrics related to proxy queuing (`envoy_server_queue_utilization`) and upstream connection pool saturation.
2.  **Kubernetes Metrics:** Check resource utilization (CPU throttling, memory pressure) on the `inventory-service` pods, even if overall usage looks low, throttling can cause latency spikes. Check `kube_pod_container_status_restarts_total`.
3.  **Application Logs:** Review logs for `inventory-service` during the 14:00-14:30 window for database connection errors, long-running query warnings, or internal thread contention.
4.  **Distributed Tracing (Jaeger/Zipkin):** Trace a request that experiences the spike. The trace will show the total time spent in the `checkout-service` call. If the time is spent *inside* the `inventory-service` span, the issue is application/DB. If the time is spent in the span *before* the call or within the sidecar proxy span, the issue is network/proxy overhead.
5.  **Envoy Specific Metrics:**
    *   **Proxy-level queueing:** High values for `envoy_server_queue_utilization` indicate the sidecar proxy is overwhelmed waiting for resources or upstream connections.
    *   **Upstream service latency:** High values for `envoy_cluster_upstream_rq_time_bucket` indicate the time spent waiting for the actual `inventory-service` to respond.

**SC5-C:**
**Architectural Solution:**
1.  **CQRS (Command Query Responsibility Segregation):** Separate the high-volume, read-heavy inventory lookups (the checkout path) from the write/reconciliation path. The reconciliation job writes to the primary database, while the checkout service reads from a dedicated, optimized read replica or a materialized view optimized for fast lookups.
2.  **Database Bulkhead Isolation:** Implement connection pooling at the application layer (or use RDS Proxy) to strictly limit the number of connections the serving pods can open to the database. This prevents the reconciliation job from exhausting the entire pool.
3.  **CronJob Scheduling:** Reschedule the reconciliation CronJob to run during off-peak hours (e.g., 03:00 UTC) or, ideally, run it against the dedicated read replica, ensuring it never contends with the live serving traffic.
4.  **Resource Governance:**
    *   **PodDisruptionBudgets (PDBs):** Define PDBs for the serving pods to ensure that during voluntary disruptions (like node maintenance), a minimum number of replicas are always available, preventing service degradation.
    *   **Resource Quotas:** Apply Resource Quotas to the namespace hosting the CronJob. This limits the total CPU/Memory the CronJob can consume, preventing it from starving the serving pods of necessary resources.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:**
**Identity and Access Layer Design:**
The core principle is to move from network-based trust (IPs) to identity-based trust (Workload Identity).

1.  **Workload Identity (SPIFFE/SPIRE):** Implement SPIFFE/SPIRE as the central identity provider. SPIRE agents run on every host (VMware, AWS EC2, Azure VM) and attest to the workload's identity (e.g., Kubernetes Service Account, AWS IAM Role). SPIRE then issues cryptographically verifiable **SVIDs (SPIFFE Verifiable Identity Documents)** to the workload.
2.  **Cloud Integration:**
    *   **AWS:** Use IAM Roles for Service Accounts (IRSA) in EKS. The SPIRE agent attests the workload, and the AWS IAM role is assumed based on the attested identity, granting temporary, least-privilege AWS permissions.
    *   **Azure:** Use Azure Managed Identities. The workload uses its Managed Identity to authenticate to Azure services, and SPIRE verifies this identity.
    *   **On-Prem:** Use the on-prem PKI infrastructure to issue certificates that SPIRE can validate, tying the workload identity to the physical host/VM.
3.  **Federation:** The SVIDs act as the universal identity token. When a workload in AWS needs to talk to a service on-prem, the AWS workload presents its SVID to the on-prem service. The on-prem service (which runs a SPIRE verifier) validates the SVID against the central SPIRE server, confirming the identity and trust chain, regardless of the underlying network location. All communication must then be secured via mutual TLS (mTLS) using the SVIDs.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:**
**Drift Source Analysis:**
1.  **Manual `tofu apply` from Laptops:** This bypasses the centralized CI/CD process, meaning the state file is updated without the required review, testing, or audit trail. This is dangerous because the local environment might have outdated assumptions, leading to unintended infrastructure changes (e.g., deleting a resource the pipeline expected to exist).
2.  **Diverged Helm Values Files:** Manual edits to values files in staging/production mean the Git repository no longer reflects the actual deployed configuration. This leads to configuration drift, where the deployed state is unknown and cannot be reliably reproduced from source control.
3.  **Direct `kubectl edit`:** This is the most dangerous form of drift. It modifies the live Kubernetes API object directly, bypassing all configuration management tools (OpenTofu, Helm). The configuration management tool (OpenTofu) will see the live state and attempt to "correct" it on the next run, potentially reverting the manual change or, worse, failing if the change is complex.

**State Locking Danger:**
If two engineers run `tofu apply` simultaneously without state locking, they both read the same state file. Both calculate their changes based on that old state. When the first engineer writes their changes, the second engineer's subsequent write overwrites the first engineer's changes, leading to **lost updates** and an inconsistent infrastructure state.

**SC7-C:**
**Drift Detection and Reconciliation:**
1.  **Scheduled Drift Detection:** Implement a nightly CI job (separate from the deployment pipeline) that runs `tofu plan` against the production environment state. If the plan output shows any changes (`Plan: X to add, Y to change, Z to destroy`), it triggers an alert (e.g., PagerDuty) detailing the drift, but *does not* automatically apply the changes.
2.  **Admission Webhook/OPA Gatekeeper:** Deploy OPA Gatekeeper to enforce policies. A policy should be written to deny any `CREATE` or `UPDATE` request to critical resources (e.g., ConfigMaps, Deployments) if the request originates from a user/service account that is *not* the CI/CD service account. This blocks direct `kubectl edit`.
3.  **Configuration Structure (Helmfile/Kustomize):** Use **Helmfile** to manage environments. Define a common base `values.yaml` for all environments. Then, use environment-specific overrides (e.g., `values-prod.yaml`) that inherit from the base. ## SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:**
**Diagnosis:**

    *   **Top Offending Metric:** Use `sum(irate(metric_name_total[5m])) by (label_name)` combined with label cardinality queries to identify which label is exploding.
2.  **Loki Drops:** **Root Cause:** Ingester saturation. The ingestion rate exceeds the capacity of the ingester pods (CPU/memory limits, or network I/O bottleneck).
    *   **Confirmation:** Check Loki ingester logs for explicit "dropping logs" messages. Check the `loki_ingester_pipelines_total` metric for dropped batches.
3.  **Tempo Timeouts:** **Root Cause:** Backend I/O bottleneck or insufficient indexing/storage capacity. Tempo relies on the backend (S3) for retrieval. If the S3 bucket is massive (14TB) and the compactor is lagging, queries must scan vast amounts of data, leading to timeouts.

4.  **Thanos Compactor Lag:** **Root Cause:** I/O saturation or insufficient resources on the compactor nodes. Compaction is an intensive disk/network operation. If the underlying storage is slow or the compactor nodes are CPU-bound, it falls behind.

**SC8-C:**
**Redesigned Observability Architecture:**
1.  **Metrics (Prometheus Replacement):** Replace Prometheus with **Mimir** (or VictoriaMetrics). Mimir is a horizontally scalable, multi-tenant Prometheus architecture designed for massive cardinality and high ingestion rates. It separates ingestion, storage, and query layers, allowing independent scaling.
2.  **Logs (Loki):** Deploy Loki in **Microservices Mode**. Instead of one large ingester cluster, deploy smaller, dedicated ingester/querier clusters per team or per application domain. This isolates load and prevents one team's peak load from affecting others.
3.  **Traces (Tempo):** Use a dedicated, highly optimized backend for Tempo, such as **Cassandra or ClickHouse**, instead of relying solely on S3 for retrieval. This allows for fast, indexed querying of trace spans, eliminating timeouts.
4.  **Governance and Cardinality Limits:**
    *   **Recording Rules:** Implement strict recording rules in Mimir to pre-aggregate high-cardinality metrics into lower-cardinality summaries (e.g., instead of tracking `http_requests_total{user_id="123"}`, record `http_requests_total{endpoint="/api/v1"}`).
    *   **Relabeling Configs:** Use Mimir's relabeling configuration to automatically drop or hash high-cardinality labels (e.g., replacing a unique `session_id` with a generic `session_hash`) before ingestion.
5.  **Chargeback Model:** Implement a **Tagging and Cost Allocation** system. Every metric, log, and trace must be tagged with a `team_id` label. Mimir/Loki/Tempo can be configured to expose usage metrics per tag. A central billing service then aggregates the storage/compute costs associated with the volume of data generated by each `team_id` tag.

## SC9 — Medium — Securing a Public-Facing API After a Breach

**SC9-A:**
| Vulnerability | OWASP Category | Blast Radius | Fix (Code/Infra) |
| :--- | :--- | :--- | :--- |
| **1. BOLA** | Broken Object Level Authorization (API1) | Attacker can view, modify, or delete *any* user's data by manipulating IDs. | **Code Fix:** Implement authorization checks in the view/serializer layer. |
| **2. Excessive Data Exposure** | Excessive Data Exposure (API3) | Attacker gains access to sensitive internal business logic, employee IDs, or PII not meant for the client. | **Code Fix:** Use serializers/DTOs to explicitly whitelist only necessary fields for the client response. |

**SC9-C:**
**Defense-in-Depth Architecture:**
1.  **API Key Migration:** Immediately rotate all compromised API keys. Implement a deprecation strategy: new consumers use OAuth2; old consumers continue using keys until a hard cutoff date.
2.  **OAuth2/JWT Implementation:** Replace API keys with OAuth2 flows. The API Gateway handles the initial token exchange (e.g., client credentials flow) and validates the short-lived JWT signature and claims before forwarding the request.
3.  **API Gateway Layer (Kong/AWS API Gateway):** Place the gateway in front of the ALB. This centralizes:
    *   **Authentication:** JWT validation.
    *   **Rate Limiting:** Enforcing quotas per authenticated user/client ID.
    *   **Request Transformation:** Stripping sensitive headers or transforming the request body before it hits the backend service.
4.  **Auditing:** Enable **CloudTrail Data Events** for the underlying database (if possible) and ensure ALB/API Gateway logs are streamed to a centralized, immutable logging system (e.g., S3/Splunk) for forensic auditing of every API access attempt.
5.  **Field-Level Encryption:** For PII fields (e.g., SSN, internal notes), use application-level encryption (e.g., AES-256) before writing to the database. The application must hold the decryption key, ensuring that even if the database is breached, the PII remains encrypted.

**Migration Strategy (API Keys to OAuth2):**
Implement a **dual-path authentication** period. The API Gateway accepts both the old API Key header *and* the new OAuth2 Bearer token. As consumers migrate, the gateway logs which authentication method is used. Once 99% of traffic uses OAuth2, the API Key validation logic is disabled, and the old keys are revoked.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
**Multi-Cluster Architecture Comparison:**

| Feature | Active-Passive (Velero) | Active-Active (Service Mesh) |
| :--- | :--- | :--- |
| **RPO/RTO Feasibility** | **RPO:** Dependent on backup frequency (e.g., 15 min). **RTO:** Minutes to hours (restore time). | **RPO:** Near Zero (Continuous sync). **RTO:** Seconds (Traffic reroute). |
| **Latency Impact (12ms)** | Minimal impact on backup/restore process. | Minimal impact on synchronous replication traffic. |
| **200TB MinIO** | Requires massive, periodic cross-region sync/copy. Slow. | Requires continuous, highly optimized replication (e.g., S3 replication features). |
| **Stateful Component Replication** | **PostgreSQL:** Patroni/Streaming (Active-Passive). **Redis:** Sentinel (Active-Passive). **RabbitMQ:** Mirroring (Active-Passive). **MinIO:** Cross-region replication (Asynchronous). | **PostgreSQL:** Synchronous Streaming (Active-Active). **Redis:** Cluster/Sentinel (Active-Active). **RabbitMQ:** Federation/Quorum Queues (Active-Active). **MinIO:** Geo-replication (Active-Active). |

**Conclusion:** To meet the strict RPO of 15 minutes and RTO of 1 hour, **Active-Active with a Service Mesh** is the superior design, as it provides near-instantaneous failover (RTO $\ll$ 1 hour) and continuous data synchronization (RPO $\ll$ 15 minutes).

**Replication Strategy Summary:**
*   **PostgreSQL:** Synchronous streaming replication managed by Patroni across sites.
*   **Redis:** Sentinel monitoring with automatic failover to the secondary cluster.
*   **RabbitMQ:** Cluster federation or queue mirroring across the two data centers.
*   **MinIO:** Utilize MinIO's built-in cross-region replication feature, configured for asynchronous replication to handle the 200TB volume.

**SC10-C:**
**Automated Failover Orchestration Sequence:**

1.  **Failure Detection:**
    *   **Monitoring:** A dedicated monitoring system (e.g., Prometheus/Alertmanager) monitors the health of the Chicago Patroni cluster via its REST API (checking `is_leader` status) and monitors the latency/health of the application endpoints.
    *   **Site Down Definition:** A site is considered "down" if the Patroni leader fails to respond to health checks for $N$ consecutive intervals (e.g., 3 minutes), *and* the application health checks fail simultaneously.
2.  **Patroni Promotion:** The monitoring system triggers the failover mechanism. Patroni's DCS (etcd) detects the leader failure and automatically initiates the promotion of the Dallas standby instance to primary.
3.  **DNS Failover (GSLB):** The GSLB (Global Server Load Balancer) detects the failure of the Chicago endpoint (via health checks) and automatically updates DNS records to point all traffic to the Dallas primary endpoint.
4.  **Stateful Component Failover:**
    *   **Redis:** Sentinel detects the primary failure and promotes the Dallas replica.
    *   **RabbitMQ:** The cluster federation mechanism automatically redirects producers/consumers to the Dallas cluster.
    *   **MinIO:** The application layer must be configured to point to the Dallas MinIO endpoint. The MinIO replication process continues to catch up asynchronously.
5.  **OpenTofu State Update:** A post-failover script runs to update the Terraform state file, changing the primary resource ARN/endpoint from Chicago to Dallas, ensuring future infrastructure changes are applied to the correct active site.

**Split-Brain Scenario Handling:**
Split-brain occurs if both sites believe they are the primary. Patroni prevents this by using the DCS (etcd). If the network partition occurs, only the site that maintains quorum with the DCS can elect a leader. If the network link fails, the minority side (losing quorum) will automatically step down, preventing divergence.

**Failing Back to Chicago:**
1.  **Recovery:** Chicago is repaired and brought back online.
2.  **Re-synchronization:** The Dallas primary initiates a replication stream back to the recovered Chicago instance, which is configured as a new standby.
3.  **Validation:** Once Chicago is fully caught up (replication lag is zero), the system runs a controlled, planned failover test (reverse of the initial failover) to promote Chicago back to primary, ensuring the process is stable before cutting over production traffic.
