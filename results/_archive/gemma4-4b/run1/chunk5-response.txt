**DN1**
The difference is that a `class` is a reference type (allocated on the heap, managed by GC) and supports inheritance, while a `struct` is a value type (allocated on the stack or inline, copied by value). You should use a `struct` for small, immutable data containers (e.g., coordinates, color values) where copying the value is cheap and you want stack allocation benefits, avoiding heap overhead.

**DN2**
`IEnumerable<T>` represents a sequence that can be iterated over lazily. It only knows *how* to iterate. `IQueryable<T>` represents an expression tree that describes a query. This distinction matters because `IEnumerable<T>` executes the query in memory (client-side evaluation), whereas `IQueryable<T>` translates the query into an expression tree that is executed by the data provider (server-side evaluation, e.g., SQL translation), allowing for efficient database filtering and projection.

**DN3**
`async/await` allows asynchronous code to be written in a synchronous-looking style. When an `await` keyword is encountered on an awaitable task, execution is suspended, control is returned to the caller, and the continuation is scheduled to resume when the awaited operation completes. A `Task` represents an asynchronous operation that might return a value or throw an exception. A `ValueTask<T>` is a struct optimized for scenarios where the operation might complete synchronously (i.e., without needing heap allocation for the state machine). Use `ValueTask<T>` when the operation is frequently synchronous or when minimizing heap allocations is critical, as it avoids the overhead of a heap-allocated `Task` object.

**DN4**
Dependency Injection (DI) is a design pattern where components receive their dependencies from an external source (the DI container) rather than creating them internally. The three lifetimes are:
1. **Transient:** A new instance is created every time it is requested.
2. **Scoped:** A single instance is created per scope (e.g., per HTTP request in ASP.NET Core).
3. **Singleton:** A single instance is created for the entire application lifetime.
A common bug is injecting a Scoped service (like `DbContext`) into a Singleton service. Since the Singleton lives for the entire application lifetime, it holds a reference to the Scoped service instance created during the first request. If the scope ends (e.g., the HTTP request finishes), the underlying resources of the Scoped service might be disposed, but the Singleton holds a stale reference, leading to `ObjectDisposedException` on subsequent requests.

**DN5**
`string` is an immutable reference type in C#. `ReadOnlySpan<char>` is a stack-allocated, memory-safe view over a contiguous block of memory (like a string's underlying characters). You use `Span<T>` (or `ReadOnlySpan<T>`) for high-performance string processing, parsing, and buffer manipulation because it avoids heap allocations and copying data when slicing or inspecting parts of a string/buffer, leading to significant performance gains.

**DN6**
The .NET GC is a generational, tracing garbage collector. It works by periodically scanning memory to identify and reclaim objects that are no longer reachable.
*   **Gen 0:** Where short-lived objects are allocated. Collections here are frequent and fast.
*   **Gen 1:** A buffer area between Gen 0 and Gen 2.
*   **Gen 2:** Where long-lived objects reside. Collections here are less frequent but more expensive.
The **Large Object Heap (LOH)** is a separate area for objects larger than a threshold (typically 85KB). Objects in the LOH are generally not compacted, which can lead to memory fragmentation. `IDisposable` implements the Dispose pattern, allowing deterministic cleanup of unmanaged resources (like file handles or network sockets) *before* the GC runs, which is necessary because the GC only manages managed memory, not external resources.

**DN7**
`ConfigureAwait(false)` tells the runtime that the continuation of the asynchronous method does not need to resume on the original synchronization context (e.g., the UI thread or ASP.NET request context).
*   **Use when:** Writing library code or high-throughput services where context switching overhead must be minimized.
*   **Do NOT use when:** Writing UI code or code that relies on specific context capture (e.g., updating a UI element), as this will prevent the continuation from running on the required thread.
This relates to `SynchronizationContext`: when `ConfigureAwait(true)` (the default), the runtime captures the current context and ensures the continuation runs there. `ConfigureAwait(false)` bypasses this capture and context restoration.

**DN8**
**Primary Constructors:** Allow defining constructor parameters directly in the class signature, which are then automatically available as read-only properties.
**Collection Expressions:** Provide a concise syntax (`[...]`, `{...}`) for creating collections.
**FrozenDictionary:** A dictionary whose contents cannot be changed after creation, offering thread-safe, immutable lookups.

*Example using Primary Constructors with DI:*
```csharp
// Service definition
public record UserService(ILogger<UserService> Logger) : IUserService;

// Registration in Program.cs
builder.Services.AddScoped<IUserService>(sp => new UserService(sp.GetRequiredService<ILogger<UserService>>()));
```

**DN9**
The likely cause is that the `DbContext` is being treated as a Singleton or is being reused across multiple concurrent requests/scopes. EF Core's `DbContext` is *not* thread-safe and must be scoped to a single unit of work (usually one HTTP request).

**DN10**
A `class` is a reference type, mutable by default, and is used for complex objects that require inheritance or identity. A `record` is a reference type designed for data transfer objects (DTOs). It automatically provides value-based equality (two records are equal if all their properties are equal) and often includes built-in `ToString()` implementations.
A `record struct` is a value type that also provides value-based equality.
*   **Choose `class`:** When identity matters (e.g., a database entity where two objects with the same data are still distinct entities).
*   **Choose `record`:** When immutability and value equality are paramount (e.g., configuration objects, DTOs).
*   **Choose `record struct`:** When you need the benefits of value semantics but require stack allocation efficiency.

**DN11**
*   **`ref`:** Passes the variable by reference. The original variable can be modified inside the method, and the change persists outside. Must be initialized before calling.
*   **`out`:** Passes the variable by reference, but the method is responsible for assigning a value to it before returning. The variable does not need prior initialization.
*   **`in`:** Passes the variable by reference, but the method is restricted from modifying the original variable. It is used for passing large structs efficiently without copying.

**DN12**
Nullable Reference Types (NRTs) use the `?` annotation (e.g., `string?`) to inform the compiler that a reference type variable might hold `null`. This is a compile-time safety feature.
Nullable Value Types (e.g., `int?`) are structs that wrap a value type and explicitly allow the value to be `null`.
The key difference is that NRTs deal with *references* (objects on the heap), while nullable value types deal with *values* (structs on the stack).

**DN13**
**LINQ (Language Integrated Query):** A set of technologies in .NET that allows querying data from various sources (collections, databases, XML) using a unified syntax.
*   **Method Syntax:** Uses extension methods on the collection (`list.Where(x => x > 5)`). More functional and fluent.
*   **Query Syntax:** Uses SQL-like syntax (`from x in list where x > 5`). More declarative and readable for SQL-like operations.
**Deferred Execution:** The query is not executed immediately upon definition. It is only executed when the results are iterated over (e.g., in a `foreach` loop or when calling `.ToList()`). This allows the query to be built up and optimized before execution.

**DN14**
Generic constraints restrict the types that can be used when instantiating a generic type.
*   `where T : class`: T must be a reference type.
*   `where T : struct`: T must be a value type.
*   `where T : new()`: T must have a public parameterless constructor.
*   `where T : IComparable<T>`: T must implement the `IComparable<T>` interface, allowing comparisons between instances of T.
You combine constraints to enforce multiple requirements simultaneously (e.g., `where T : class, new(), IComparable<T>`).

**DN15**
An **Interface** defines a contract—a set of methods and properties that implementing classes *must* adhere to. It specifies *what* a class can do. An **Abstract Class** provides a base implementation and can contain concrete methods and fields, specifying *what* a class is and providing some default behavior.
Default interface methods (C# 8+) allow interfaces to provide default implementations for methods. This blurs the line by allowing interfaces to offer concrete behavior, making them more like abstract base classes in some respects, but they still primarily define contracts.

**DN16**
The middleware pipeline is a series of software components that process HTTP requests and responses sequentially in ASP.NET Core. Each middleware component inspects the request, performs logic (authentication, logging, routing), and either passes the request to the next component or terminates the pipeline.
*   `app.Use()`: Registers middleware that processes the request/response flow (e.g., `UseAuthentication()`).
*   `app.Map()`: Maps a specific route to a handler, effectively short-circuiting the pipeline for that route.
*   `app.Run()`: Terminates the pipeline, usually used for simple, non-routing endpoints.
**Ordering matters** because the first middleware to handle the request dictates the outcome. Exception handling middleware must be placed *before* the main application logic to catch errors from downstream components.

**DN17**
`Channel<T>` is a type-safe, asynchronous stream abstraction in .NET, designed for producer-consumer scenarios. It is built on top of `System.Threading.Channels`.
**Comparison to `BlockingCollection<T>`:** `BlockingCollection<T>` is thread-safe but synchronous (blocking). `Channel<T>` is asynchronous, designed to work seamlessly with `async/await`.
**Backpressure Example:** Using a **bounded channel** (e.g., `Channel.CreateBounded<T>(capacity)`) enforces backpressure. If the producer tries to write to a full channel, the `WriteAsync` call will asynchronously await until space becomes available, preventing the producer from overwhelming the consumer.

**DN18**
**Source Generators** are compile-time code generators that run during the compilation process. They analyze the syntax tree of the source code and generate new C# source files *before* the main compilation occurs.
They differ from **Reflection** (runtime inspection) and **IL Weaving** (post-compilation modification of IL) because they operate at the source code level, providing compile-time safety and zero runtime overhead.
An **Incremental Generator** is preferred because it only regenerates the code files that are affected by changes in the source code, drastically speeding up build times compared to a standard `ISourceGenerator` which might re-run the entire analysis.

**DN19**
**TPL Dataflow** provides a library of building blocks for creating concurrent, asynchronous data processing pipelines.
*   **`ActionBlock`:** Executes an action (a side effect) asynchronously. It accepts messages and processes them sequentially or in parallel based on its concurrency limit.
*   **`TransformBlock`:** Executes a transformation function asynchronously. It takes an input message and produces an output message.
*   **`BufferBlock`:** Acts as a queue, buffering incoming messages until a consumer processes them.
**Comparison to Channels:** Channels are a simpler, lower-level stream abstraction (producer $\rightarrow$ consumer). TPL Dataflow provides higher-level, structured *pipeline topology* (e.g., Input $\rightarrow$ Transform $\rightarrow$ Filter $\rightarrow$ Output), offering built-in flow control and complex block chaining.

**DN20**
**Minimal APIs** are a lightweight, streamlined way to build HTTP endpoints in .NET using lambda expressions directly in the `Program.cs` file, bypassing the traditional MVC/Controller structure.
**Differences from Controllers:** Controllers use classes, inheritance, and attributes; Minimal APIs use functional endpoints (`app.MapGet("/weather", ...)`).
**Trade-offs:**
*   **Testability:** Minimal APIs can be slightly harder to unit test in isolation compared to traditional controllers, though testing the endpoint routing is straightforward.
*   **Middleware:** Both support middleware, but Minimal APIs integrate it more directly into the startup file.
*   **OpenAPI:** Requires explicit configuration or use of libraries (like Swashbuckle) to generate OpenAPI documentation, whereas controllers often integrate more naturally with scaffolding tools.
**Route Groups and Endpoint Filters:** Route groups allow applying common prefixes or constraints to a set of related endpoints. Endpoint filters allow injecting logic (like authorization checks or logging) that runs before or after the endpoint handler executes, regardless of the specific route.

**P1**
A **list** (`[]`) is mutable and ordered, allowing duplicate elements. A **tuple** (`()`) is immutable and ordered, often used for fixed collections of heterogeneous types.
A **set** (`set()`) is an unordered collection of unique, mutable elements. A **frozenset** (`frozenset()`) is an immutable version of a set, meaning it can be used as an element within another set or as a dictionary key.

**P2**
The **GIL (Global Interpreter Lock)** is a mutex that protects access to Python objects, ensuring that only one thread executes Python bytecode at any given time within a single process.
It affects **CPU-bound workloads** (tasks that spend most of their time executing Python code).
Workarounds include:
1.  **Multiprocessing:** Using separate processes (which have their own GIL) to achieve true parallelism.
2.  **I/O-bound tasks:** Using `asyncio` or threading for tasks that spend most of their time waiting for external resources (network, disk), as the GIL is released during I/O waits.

**P3**
**Shallow Copy:** Creates a new container object, but populates it with *references* to the objects found in the original. If the original object contains mutable objects (like lists), modifying those nested objects in the copy will also affect the original.
**Deep Copy:** Creates a completely independent copy of the original object and recursively copies all nested objects.
*Example:* If `original = [1, [2]]` and you shallow copy it, `copy[1]` still points to the same list object as `original[1]`. If you modify `copy[1]`, `original[1]` changes. A deep copy ensures the nested list is duplicated.

**P4**
Decorators are syntactic sugar in Python that allow you to wrap a function or method, modifying its behavior without permanently altering its source code. They are essentially functions that take another function as an argument and return a new function.
*Decorator logging execution time:*
```python
import time
from functools import wraps

def timer(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start_time = time.time()
        result = func(*args, **kwargs)
        end_time = time.time()
        print(f"Function {func.__name__} executed in {end_time - start_time:.4f} seconds.")
        return result
    return wrapper

@timer
def slow_function(n):
    time.sleep(n)
    return f"Done after {n}s"

slow_function(0.5)
```

**P5**
**Generators** are functions that use the `yield` keyword. Instead of building and returning an entire list in memory, a generator yields items one at a time upon request. This makes them highly memory-efficient for large datasets.
**`yield from`:** This delegates iteration to a sub-generator. It allows one generator to yield all values produced by another generator, effectively chaining generators together without needing to manually loop and yield each item.

**P6**
The **asyncio event loop** is the core mechanism in Python's `asyncio` that manages and runs asynchronous tasks concurrently. It monitors I/O operations and switches execution between tasks when one is waiting, preventing the thread from blocking.
*   `asyncio.run(coro)`: Runs the top-level coroutine and manages the event loop lifecycle.
*   `asyncio.gather(*coros)`: Runs multiple awaitables concurrently and waits for all of them to complete, returning a list of their results.
*   `asyncio.create_task(coro)`: Schedules a coroutine to run concurrently on the event loop immediately, returning a `Task` object that can be awaited later.
You cannot call `time.sleep()` inside an `async` function because `time.sleep()` is a *blocking* call. It halts the entire thread, preventing the event loop from switching to other waiting tasks, defeating the purpose of asynchronous programming. You must use `await asyncio.sleep(delay)` instead.

**P7**
**MRO (Method Resolution Order):** Defines the order in which Python searches the inheritance hierarchy to find a method or attribute.
Python 3 uses the **C3 Linearization Algorithm** (a refinement of the Diamond Problem solution) to ensure a consistent, predictable, and monotonic search order.
In the diamond inheritance example, the MRO is `D -> B -> C -> A -> object`. When `D().who()` is called, Python checks `D`, then `B`. Since `B` does not define `who`, it checks its parent, `A`. However, because C3 ensures that the path through `B` is prioritized over the path through `C` (due to the order `B, C` in `D(B, C)`), the search proceeds until it finds the implementation in `A` (if `B` didn't override it) or the first implementation encountered in the linearized path. In this specific case, the MRO is `D, B, C, A, object`. Since `B` inherits from `A` and doesn't override `who`, the search continues to `C`, which *does* override `who`, so `C`'s implementation is called. *Correction based on the provided code:* The MRO is `D, B, C, A, object`. When `D().who()` is called, it checks `D` (no method), then `B` (no method), then `C` (has `who`), so it prints `"C"`.

**P8**
A **metaclass** is the "class of a class." It controls how a class itself is created. When you define a class, Python uses the metaclass to construct that class object.
*   **`__init_subclass__`:** A class method available in Python 3.6+ that is called automatically when a class inherits from a base class. It is used for runtime configuration or modification of subclasses *after* they are defined.
*   **Metaclass:** Used to fundamentally alter the class creation process itself, often to inject methods, enforce structural rules, or modify attributes *before* the class object is finalized.
*   **Use Case (`__init_subclass__`):** Automatically adding logging hooks or validation methods to all subclasses of a base service.
*   **Use Case (Metaclass):** Creating an ORM or framework where the metaclass intercepts class definition to automatically generate database mapping metadata based on class attributes.

**P9**
*   **Threading:** Uses threads within a single process. Best for I/O-bound tasks (waiting for network/disk) because the GIL is released during I/O waits. Limited by the GIL for CPU-bound tasks.
*   **Multiprocessing:** Uses separate OS processes. Bypasses the GIL entirely, allowing true parallel execution on multiple CPU cores. Best for CPU-bound tasks.
*   **`concurrent.futures`:** A high-level interface that abstracts both `ThreadPoolExecutor` (for threading) and `ProcessPoolExecutor` (for multiprocessing), providing a unified `submit()` and `as_completed()` interface.
**Serialization Implications:** Multiprocessing requires **pickling** (serialization) to pass objects between processes. This means the objects must be serializable. Complex objects, database connections, or objects holding file handles cannot be pickled and will cause errors.

**P10**
`__slots__` is a class attribute that tells Python not to use a dynamic dictionary (`__dict__`) to store instance attributes. Instead, it reserves a fixed, predefined set of slots for attributes.
**When to use:** When creating classes with many instances where memory footprint is critical (e.g., large collections of small data objects).
**What it prevents:** It prevents the dynamic addition of new attributes to an instance after initialization.
**Memory Impact:** It significantly reduces memory usage per instance by eliminating the overhead of the instance dictionary.

**P11**
A **virtual environment** is an isolated directory containing a specific Python interpreter and its own set of installed packages. It prevents dependency conflicts between different projects.
**Why use one:** To ensure that Project A, which requires Django 2.0, does not break Project B, which requires Django 4.0, by keeping their dependencies isolated.
*   **`venv`:** The standard, built-in module for creating lightweight virtual environments in modern Python.
*   **`virtualenv`:** A third-party tool that predates `venv` and offers more advanced features, often used for older Python versions.
*   **`conda`:** A comprehensive package and environment manager (often used in data science) that manages not just Python packages but also non-Python dependencies (like compilers or specific C libraries).

**P12**
*   **List Comprehension:** `[expression for item in iterable if condition]` (Creates a list).
*   **Dict Comprehension:** `{key: value for item in iterable if condition}` (Creates a dictionary).
*   **Set Comprehension:** `{expression for item in iterable if condition}` (Creates a set).
They are generally preferred over `map()` and `filter()` because they are more concise, Pythonic, and often easier to read, especially when combining filtering and transformation in one line. `map()` applies a function to every item, while `filter()` selects items based on a predicate. Comprehensions combine both operations elegantly.

**P13**
*   **`==` (Equality Operator):** Compares the *values* of two objects. It calls the object's `__eq__` method.
*   **`is` (Identity Operator):** Compares the *identity* of two objects (i.e., whether they point to the exact same object in memory). It checks if `id(a) == id(b)`.
**Object Interning:** A memory optimization technique where Python pre-allocates and reuses immutable objects (like small integers, short strings) to save memory and speed up comparisons. Small integers (typically -5 to 256) are often interned, meaning `a is b` returns `True` because they are pointing to the same pre-existing object in memory, even if they were created separately.

**P14**
*   **`*args`:** Collects an arbitrary number of positional arguments into a tuple.
*   **`**kwargs`:** Collects an arbitrary number of keyword arguments into a dictionary.
*   **Positional-only (`/`):** Arguments placed before `/` must be passed positionally and cannot be passed by keyword (e.g., `def func(a, b, /):`).
*   **Keyword-only (`*`):** Arguments placed after `*` must be passed using their keyword name (e.g., `def func(*, c, d):`).

**P15**
**Context Managers** use the `with` statement to ensure that setup and teardown actions are executed reliably, even if errors occur.
*   **`__enter__` / `__exit__`:** The standard way. `__enter__` runs upon entering the `with` block and returns the resource. `__exit__` runs upon exiting, handling cleanup (e.g., closing files).
*   **`@contextmanager`:** A simpler, generator-based approach from the `contextlib` module. The code before `yield` is setup; the code after `yield` is teardown.
*Example (Database Connection Pool):* Instead of just closing a file, you use a context manager to acquire a connection from a pool (`__enter__`), use it, and guarantee that the connection is returned to the pool (`__exit__`), even if a query fails.

**P16**
**Type Hinting:** The practice of adding optional type annotations to variables, function arguments, and return values in Python to improve code readability and enable static analysis.
*   **`typing.Union[A, B]`:** Indicates a variable can be of type A OR type B.
*   **`Optional[T]`:** A shorthand for `Union[T, None]`, indicating the variable can be T or None.
*   **`Literal[value]`:** Restricts a variable to only accept a specific, fixed set of literal values (e.g., `Literal["read", "write"]`).
*   **`TypeVar`:** A placeholder for types that will be specified later, used to write generic functions or classes (similar to generics in C#).
*   **`Protocol`:** Defines a structural type check. Instead of inheriting from a class, a protocol specifies that any object implementing the required methods/attributes satisfies the protocol, enabling duck typing with static checks.
**Static Analysis:** Tools like Mypy or Pyright read these hints and check the code *before* runtime, flagging type mismatches (e.g., trying to add a string to an integer) without executing the code.

**P17**
**Data Model (Dunder Methods):** Special methods (prefixed and suffixed with double underscores, e.g., `__init__`) that Python calls automatically to implement core language features.
*   **`__repr__` vs `__str__`:** `__repr__` (representation) should return an unambiguous string that could ideally recreate the object (developer-focused). `__str__` (string) should return a readable, user-friendly string (end-user focused).
*   **`__eq__` vs `__hash__`:** `__eq__` defines value equality. `__hash__` defines how an object is mapped to an integer for use in hash-based collections (like sets or dict keys).
**If you define `__eq__` but not `__hash__`:** Python will issue a `TypeError` if you try to use that object as a key in a dictionary or add it to a set, because the hash value is required for efficient lookup in those structures.

**P18**
**Descriptors:** Objects that define how attribute access (getting, setting, deleting) works for other objects. They implement the descriptor protocol: `__get__`, `__set__`, and `__delete__`.
*   **Property:** Uses descriptors to allow attribute access syntax (`obj.attr`) while executing methods behind the scenes (e.g., validation logic).
*   **`classmethod`:** The class itself is passed as the first argument (`cls`) instead of the instance (`self`) when the method is called.
*   **`staticmethod`:** The method is bound to the class but does not receive either `self` or `cls` as an implicit first argument; it behaves like a regular function namespaced within the class.

**P19**
The Python import system manages how modules (files/packages) are located and loaded.
*   **Relative Imports:** Imports relative to the current package structure (e.g., `from . import utils`). Used within a package.
*   **Absolute Imports:** Imports starting from the root of the project structure (e.g., `from my_project.utils import helper`).
**Mechanisms:**
*   **`sys.path`:** A list of directories Python searches when an `import` statement is encountered.
*   **`PYTHONPATH`:** An environment variable that adds directories to `sys.path`.
*   **`__init__.py`:** Historically marked a directory as a Python package, though this is less strictly required in modern Python (namespace packages).
*   **Namespace Packages:** Allow a single package name to be split across multiple directories/packages, useful for large libraries.
**Finder and Loader:** A **Finder** is responsible for locating the module (finding the file path). A **Loader** is responsible for loading the module's code into memory and executing it.

**P20**
**Dataclasses:** A decorator (`@dataclass`) that automatically generates boilerplate methods like `__init__`, `__repr__`, `__eq__`, etc., based on type-hinted class attributes.
**Comparison:**
*   **`attrs`:** A mature, highly configurable library that predates dataclasses, offering similar functionality with more fine-grained control.
*   **Pydantic:** A data validation library that uses type hints to enforce strict data schemas, performs runtime validation, and handles serialization/deserialization (e.g., JSON parsing) automatically.
**Features:**
*   **`__post_init__`:** A method called immediately after `__init__` completes, useful for derived property calculations.
*   **Field Factories:** Allows defining default values that are computed dynamically rather than being static constants.
*   **Frozen Dataclasses:** Makes the instance immutable, similar to `typing.Final`.
*   **Inheritance:** Dataclasses support inheritance, but careful use of `__post_init__` is required to ensure base class initialization runs correctly.
**When to choose Pydantic:** Choose Pydantic when you need robust **runtime data validation** (e.g., ensuring an incoming JSON payload has a field that is actually an integer, not a string) or when you need seamless integration with serialization formats like Pydantic's built-in JSON handling. Choose dataclasses when you primarily need boilerplate reduction for simple, immutable data structures.
