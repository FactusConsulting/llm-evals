**G1**
A Go array has a fixed size defined at compile time, whereas a slice is a dynamically sized, flexible view into an underlying array. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array (typically doubling the capacity), copies the existing elements to the new array, and then adds the new element.

**G2**
`var x int` declares a variable `x` and initializes it to its zero value (which is `0` for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when declaring a variable in a scope where it has already been declared, or when you need to explicitly declare the type (e.g., `var x *int`).

**G3**
A goroutine is a lightweight, independently executing function managed by the Go runtime, not the OS. It is much cheaper than an OS thread because it requires very little stack space (starting small, growing as needed) and context switching between goroutines is handled entirely in user space by the Go scheduler. The Go scheduler (GMP model) maps M (Machine/OS thread) to N (Goroutine) using G (Goroutine). The scheduler multiplexes many goroutines onto a smaller pool of OS threads, efficiently managing concurrency.

**G4**
Channels are typed conduits through which you can send and receive values between goroutines, providing synchronized communication. An unbuffered channel requires both the sender and receiver to be ready simultaneously for the communication to proceed (synchronous). A buffered channel has a fixed capacity; sends/receives can proceed without the other party being ready until the buffer is full or empty. When sending to a full buffered channel, the sender blocks until a receiver frees up a slot.

**G5**
The `context` package is used to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. This is crucial for managing the lifecycle of concurrent operations.
Example:
```go
import (
    "context"
    "net/http"
    "time"
)

func fetchWithTimeout(url string) {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel() // Always call cancel to release resources

    req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
    client := &http.Client{}
    resp, err := client.Do(req)
    if err != nil {
        // Handle context cancellation or timeout error here
        fmt.Println("Request failed:", err)
    }
    resp.Body.Close()
}
```

**G6**
Go's interface satisfaction is implicit (structural typing). A type satisfies an interface simply by implementing all the methods defined in that interface; there is no explicit declaration required. This differs from Java/C# where interfaces often require explicit `implements` keywords. The empty interface `interface{}` (or `any` in Go 1.18+) can hold a value of *any* type. It is powerful because it allows for maximum flexibility (e.g., generic data structures), but dangerous because the compiler loses type information, requiring runtime type assertions or type switches, which can lead to runtime panics if misused.

**G7**
This code is unsafe because the write to `data` and `ready` happens concurrently with the read (`for !ready {}` and `fmt.Println(data)`). Without synchronization, the compiler cannot guarantee that the write operation has completed before the read operation begins, leading to a data race where the read might observe stale or partially written memory. The correct alternatives are using `sync.Mutex` to protect access, or using a channel to signal completion:
```go
// Using a channel for signaling
done := make(chan struct{})
go func() {
    data = "hello"
    close(done)
}()
<-done // Wait for the channel to close
fmt.Println(data)
```

**G8**
`sync.Mutex` provides exclusive locking: only one goroutine can hold the lock at a time, blocking all others. `sync.RWMutex` allows multiple readers simultaneously (`RLock`) but requires exclusive access for writers (`Lock`). Use `sync.Map` when the map keys are highly dynamic, writes are infrequent, and you want to avoid locking the entire map structure for every operation. Use a regular map with a `sync.Mutex` when reads and writes are frequent, as the mutex approach often has lower overhead than `sync.Map` for high-contention scenarios, and provides more control over locking granularity.

**G9**
Go modules manage dependencies. `go.mod` lists the required modules and their version constraints (e.g., `require github.com/pkg/errors v0.9.1`). `go.sum` contains cryptographic checksums for the exact content of every dependency version listed in `go.mod`, ensuring build reproducibility and integrity. `go mod tidy` cleans up the module file by adding missing dependencies and removing unused ones. MVS (Minimum Version Selection) is an algorithm that selects the highest possible version that satisfies all version constraints specified in the `go.mod` file, ensuring the most up-to-date, compatible code is used.

**G10**
A `defer` statement schedules a function call to be executed just before the surrounding function returns. If multiple `defer` statements exist, they execute in Last-In, First-Out (LIFO) order. A common gotcha in a loop is capturing the loop variable by reference. If you defer a function that references the loop variable, the function will execute *after* the loop finishes, and all deferred calls will reference the final value of the loop variable, not the value it held during that specific iteration.

**G11**
A pointer in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`, meaning it points to no valid memory location. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12**
The `init()` function is a special function that runs automatically before the `main` function in a package. It is used for package-level initialization logic (e.g., setting up global state). A package can have multiple `init()` functions, and they execute sequentially in the order they appear in the source code files.

**G13**
`make` is used to initialize built-in reference types: slices, maps, and channels. It allocates the underlying data structure and initializes it. `new` allocates memory for a value of a specified type and returns a pointer to the zero value of that type. It works with any type, but it only returns a pointer (`*T`), whereas `make` returns the initialized structure itself (e.g., `[]int` or `map[string]int`).

**G14**
Error handling in Go is idiomaticly done by returning an `error` type as the last return value from a function. The `error` interface is an interface defined as `type error interface { Error() string }`. The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain contains a specific sentinel error value. `errors.As(err, &target)` checks if the error chain contains a value that matches a specific type, allowing you to extract structured error data.

**G15**
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil` (an uninitialized, non-usable map).
*   **Slice:** `[]Type`. Zero value: `nil` (a slice with length 0 and capacity 0).
*   **Channel:** `chan Type`. Zero value: `nil` (an uninitialized, non-usable channel).
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values (e.g., `0` for integers, `""` for strings).

**G16**
A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, leading to unpredictable results based on the non-deterministic timing of the scheduler. The `-race` flag instruments the Go runtime to detect these data races at runtime.
Example Race:
```go
var counter int
go func() { counter++ }() // Data race
```
Fix using Mutex:
```go
var mu sync.Mutex
var counter int
go func() {
    mu.Lock()
    counter++
    mu.Unlock()
}()
```

**G17**
The `select` statement allows a goroutine to wait on multiple communication operations (channel receives or sends) simultaneously. It differs from `switch` because `select` is specifically designed for handling channel communication, whereas `switch` handles value comparisons. When multiple cases are ready, `select` chooses one pseudo-randomly. To implement a timeout, you use `select` alongside a `time.After` channel:
```go
select {
case msg := <-ch:
    fmt.Println("Received:", msg)
case <-time.After(5 * time.Second):
    fmt.Println("Timeout occurred")
}
```

**G18**
Escape analysis is the process by which the Go compiler determines whether a variable should be allocated on the stack (fast, automatic cleanup) or the heap (managed by the garbage collector). The compiler decides based on how long the variable's address needs to live and whether it is passed to functions that might outlive the current stack frame. If a variable's address escapes the function scope (e.g., returned as a pointer, stored in a global variable, or sent over a channel), it must be allocated on the heap. You can inspect this using the `-m` flag during compilation. It matters for performance because heap allocations involve GC overhead, while stack allocations are extremely fast.

**G19**
The `reflect` package allows a program to inspect and manipulate its own structure (type, fields, values) at runtime. `reflect.Type` describes the structure of a value (its kind, fields, methods), while `reflect.Value` holds the actual runtime value and allows operations on it. Reflection incurs significant performance costs because the compiler cannot optimize code paths based on the type at compile time; it must perform dynamic lookups. Reflection is justified when building generic frameworks, serialization libraries, or ORMs. Code generation is preferred for performance-critical paths.

**G20**
The `go:embed` directive allows embedding files or directories directly into the compiled binary as byte slices or file systems. It works by specifying the path relative to the source file. For single files, it embeds the content as `[]byte`. For directories or file systems, it embeds them as `fs.FS`. Limitations include the size of the binary and the complexity of runtime access if the embedded structure is large. It interacts with `io/fs.FS` by providing an in-memory file system implementation that can be passed to functions expecting an `fs.FS` interface.

**R1**
Ownership is Rust's system for managing memory without a garbage collector. It ensures that every value in Rust has a single variable that is its *owner*. The three rules are: 1) Each value has a single owner. 2) When the owner goes out of scope, the value is dropped (memory is freed). 3) Ownership can be transferred (moved) from one variable to another.

**R2**
`String` is a heap-allocated, growable, mutable, owned string type. It owns its data. `&str` is a string slice—a borrowed, immutable view into string data (which might be owned by a `String` or a string literal). Use `String` when you need to build, modify, or own the string data. Use `&str` in function signatures when you only need to read the string data without taking ownership or modifying it.

**R3**
Borrowing allows you to refer to a value without taking ownership of it. The borrow checker enforces rules to prevent data races at compile time.
*   **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously. You can have many `&T` references, but no mutable references while they exist.
*   **Mutable Reference (`&mut T`):** Allows exactly one mutable reference to the data at any given time. If a `&mut T` exists, no other references (mutable or immutable) can exist for that data.

**R4**
`Result<T, E>` is an enum representing an operation that can either succeed (`Ok(T)`) or fail (`Err(E)`). `Option<T>` is an enum representing the presence or absence of a value (`Some(T)` or `None`). The `?` operator is syntactic sugar for propagating errors or unwrapping `Option`s. If the expression it operates on is `Err(E)`, `?` immediately returns that error from the current function. If it is `Ok(T)`, it unwraps the value `T`.
Example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> Result<String, io::Error> {
    let mut file = File::open(path)?; // Propagates io::Error if file cannot be opened
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates io::Error if read fails
    Ok(contents)
}
```

**R5**
*   **`Box<T>`:** A smart pointer that allocates data on the heap. Used when you need to put a type on the heap to handle recursive types or when the size is unknown at compile time. It owns the data.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same heap data. It keeps a count; the data is dropped only when the last `Rc` goes out of scope. Used for single-threaded shared ownership.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>` but uses atomic operations for reference counting, making it safe to share across multiple threads. Used for multi-threaded shared ownership.

**R6**
Traits define shared behavior (a set of methods) that types can implement. They are similar to Go interfaces in that they define a contract. The key difference is that Rust traits are often used for static dispatch (generics), while Go interfaces are inherently dynamic.
*   **Trait Object (`dyn Trait`):** A dynamically dispatched trait object. It holds a pointer to data and a vtable, allowing you to treat different concrete types uniformly at runtime (similar to an interface variable in Go).
*   **Generic with Trait Bound (`T: Trait`):** A statically dispatched generic. The compiler generates specialized code for each concrete type used, leading to zero-cost abstractions. This is generally preferred for performance.

**R7**
This fails because the return type `&str` must live as long as the reference it returns. The compiler cannot guarantee that the shorter string (`x` or `y`) will still be valid after the `longest` function returns, as `x` and `y` are borrowed from the caller's scope.
Fix: You must introduce a lifetime parameter `'a` to tie the output reference to the input references:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

**R8**
*   **`Send`:** A marker trait indicating that a type can be safely transferred (sent) across thread boundaries.
*   **`Sync`:** A marker trait indicating that a type can be safely shared between threads (i.e., it is safe to have multiple references to it across threads).
You cannot send an `Rc<T>` across threads because its internal reference counter is not atomic, leading to race conditions when multiple threads try to increment/decrement the count simultaneously. `Arc<T>` is safe for concurrent use because its reference counting mechanism uses atomic CPU instructions, ensuring thread-safe modifications to the count.

**R9**
Rust's async/await relies on the `Future` trait. A `Future` is a trait representing a value that may not be available yet; it is a state machine that can be polled. When you `await` a future, you are essentially telling the executor: "I need this result, but if it's not ready, pause this task and poll me again later." The executor (like Tokio) is responsible for managing the task queue, polling the futures when they are ready, and driving the asynchronous execution loop. This differs from Go's goroutines because Rust's async is *cooperative multitasking* driven by an external executor, whereas Go's goroutines are managed by a preemptive scheduler within the runtime.

**R10**
`unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. Three things you can do: 1) Dereference raw pointers (`*const T`, `*mut T`). 2) Call `unsafe` functions or methods. 3) Access or modify mutable static variables. Unsafe code is justified when interfacing with C libraries (FFI), implementing highly optimized data structures (like custom memory allocators), or when the compiler cannot prove safety for a specific low-level operation.

**R11**
Pattern matching uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches. `if let` is syntactic sugar for a specific, single pattern match (e.g., `if let Some(x) = option { ... }`). The compiler enforces exhaustiveness, meaning if you match against an enum, you must provide a branch for every possible variant, or use `_` to ignore one or more.

**R12**
`Vec<T>` is a dynamically sized, heap-allocated, growable collection (a vector). An array `[T; N]` has a fixed size `N` known at compile time and is typically allocated on the stack. When `Vec` pushes elements beyond its current capacity, it allocates a new, larger contiguous block of memory (usually doubling the capacity), copies all existing elements to the new block, and then deallocates the old block.

**R13**
Enums in Rust are powerful algebraic data types that can hold data associated with each variant. Unlike C/Java enums, Rust enums can have associated data (e.g., `enum Message { Quit, Move { x: i32, y: i32 } }`). `Option<T>` is an enum variant of `Some(T)` or `None`. Rust does not have `null` because `None` is a type-safe variant of the `Option` enum, forcing the programmer to explicitly handle the absence of a value, thus eliminating null pointer dereference errors at compile time.

**R14**
The `impl` block is used to define methods and associated functions for a specific type.
*   **`&self`:** Takes an immutable reference; the method reads the data but does not change the instance.
*   **`&mut self`:** Takes a mutable reference; the method can read and modify the instance's data.
*   **`self`:** Takes ownership of the instance; the method consumes the instance, and it cannot be used afterward.
Associated functions (like `String::new()`) are functions defined within the `impl` block but do not take `self` as their first argument; they are called directly on the type name.

**R15**
A derive macro is a procedural macro that automatically implements standard traits for a struct or enum based on its definition. Examples include `#[derive(Debug)]` (allows printing via `{:?}`), `#[derive(Clone)]` (implements deep copying), `#[derive(PartialEq)]` (implements equality checks), and `#[derive(Serialize)]` (used by serialization libraries). You cannot derive a trait if the type does not meet the requirements of that trait (e.g., you cannot derive `Clone` if the type contains a non-cloneable resource like a raw file handle).

**R16**
`Cow<'a, T>` (Clone On Write) is an enum that represents data that is either borrowed (`Cow::Borrowed(&'a T)`) or owned (`Cow::Owned(T)`). It is useful when you receive data that might need modification. If you only read it, you use the borrowed version (zero allocation). If you need to modify it, `Cow` automatically clones the data into an owned version *only* when the write operation is attempted, avoiding unnecessary allocations if the data is only read.

**R17**
Rust's module system organizes code into hierarchical units.
*   **`mod`:** Declares a module, which can contain other modules or items.
*   **`use`:** Brings items from another module into the current scope, allowing you to refer to them without the full path.
*   **`pub`:** Makes an item (function, struct, module) publicly accessible outside its current module.
The file system maps to modules: a file named `foo.rs` typically defines the `foo` module. The 2018 edition introduced significant improvements, notably allowing modules to be defined in separate files using `mod foo;` and supporting more complex module structures.

**R18**
`Pin<T>` is a smart pointer wrapper that guarantees that the data it points to will not be moved in memory for the duration of its lifetime. This is crucial for self-referential structs (where a part of the struct holds a pointer to another part of the same struct) and for async/await. When a future is polled, its internal state machine must remain stable in memory; if it were moved, its internal pointers would become invalid. `Unpin` is a marker trait indicating that a type *can* be safely moved in memory.

**R19**
Rust's macro system allows metaprogramming.
*   **Declarative Macros (`macro_rules!`):** Pattern-matching macros that operate on token trees (like a sophisticated text replacement engine). They are simple and compile-time only.
*   **Procedural Macros (derive, attribute, function-like):** Macros that are actual Rust code that runs during compilation. They can inspect and transform the Abstract Syntax Tree (AST) of the code.
Hygiene rules prevent macro expansion from accidentally capturing identifiers from the surrounding scope, ensuring that generated code is isolated and correct.

**R20**
Zero-cost abstractions mean that high-level language features (like generics and iterators) compile down to machine code that is as fast as if the programmer had written the low-level, hand-optimized C code directly.
*   **Generics (Monomorphization):** The compiler generates a specific version of the code for every concrete type used, eliminating runtime overhead associated with dynamic dispatch.
*   **Iterators:** Rust's iterator trait allows chaining operations (map, filter) without allocating intermediate collections; they are lazy, executing only when requested.
*   **Trait Static Dispatch:** Similar to monomorphization, this allows the compiler to resolve method calls to the correct concrete implementation at compile time, avoiding the overhead of virtual function lookups.
