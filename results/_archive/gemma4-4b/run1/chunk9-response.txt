## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:**
The pods are failing because the Kubernetes cluster upgrade enforced the **Restricted Pod Security Standard (PSS)**, which is stricter than the previous Baseline. The failure stems from a conflict between the container image's default behavior and the PSS enforcement.
1.  **SecurityContext Interaction:** The pods specify `securityContext.runAsNonRoot: true`. This mandates that the process inside the container must run as a non-root user (UID > 0).
2.  **Image Directive Conflict:** The new base image (`cgr.dev/chainguard/static:latest`) defaults its `USER` instruction in the Dockerfile to `root` (UID 0).
3.  **PSS Enforcement:** The Restricted PSS prohibits running as root. When the Kubelet attempts to start the pod, it checks the security context. It sees `runAsNonRoot: true` but the container process is attempting to run as root (due to the image default). This mismatch violates the PSS policy, causing the kubelet to refuse to start the container, resulting in `CrashLoopBackOff`.

**SC1-B:**
```bash
kubectl get pods --all-namespaces -o json | \
jq -r '.items[] | select(.status.phase == "Running" and (.status.containerStatuses[]?.state?.waiting?.reason == "CrashLoopBackOff")) | 
  "Namespace: \(.metadata.namespace)\nPod: \(.metadata.name)\nSecurityContext: \(.spec.containers[0].securityContext | tojson)"'
```
*(Note: The `jq` filter needs adjustment to correctly target the specific container's securityContext if multiple containers exist, but this provides the general structure for extracting the required fields.)*

**SC1-C:**
**Immediate Fix (Outage Mitigation):**
1.  **Image Fix:** Rebuild the affected microservices, explicitly setting the `USER` directive in the Dockerfile to a non-root user (e.g., `USER 1000`) and ensuring the application runs under that UID.
2.  **Manifest Change (Temporary):** If immediate rebuild is impossible, temporarily modify the deployment manifest to explicitly set `securityContext.runAsUser: <non-root-uid>` to satisfy the PSS requirement, overriding the image default.

**Recurrence Prevention:**
1.  **CI Pipeline Gate:** Implement a static analysis step (e.g., using Trivy or specialized Dockerfile linters) in the CI pipeline that scans the Dockerfile for `USER root` or checks the resulting image metadata to ensure the effective user is non-root.
2.  **Deployment Strategy (Zero Downtime):** Use a **Rolling Update** strategy (default in Kubernetes Deployments). By updating the image tag in the deployment manifest and allowing Kubernetes to gradually replace old pods with new ones, the outage is contained to the replacement window, ensuring service continuity.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:**
**Stale Data Issue:** The stale data occurs because the promotion was likely **asynchronous**. PostgreSQL streaming replication ships Write-Ahead Logs (WAL) from the primary to the replica. If the primary fails before the replica has received and applied the latest WAL records, those transactions are lost. When the replica is promoted, it becomes the new primary, but it lacks the most recent committed transactions from the old primary.
**Replication Lag Implication:** High replication lag means the replica is behind the primary. Promoting it means accepting the data state at the moment the lag was measured.
**WAL Shipping:** PostgreSQL uses WAL shipping to stream transaction logs. In cross-region setups, this traffic traverses the public internet or dedicated links, introducing latency.
**Data Loss Scenarios:** Data loss occurs if the primary fails before the WAL segment containing the latest committed transactions has been successfully flushed and applied to the replica (i.e., the replica was not fully caught up).
**Quantifying Data Loss:** Check the `pg_stat_replication` view on the *old* primary (if accessible) or check the `pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()` on the *new* primary to determine the difference between the last received and last applied LSNs before the failure.

**SC2-B:**
The goal is to transition the promoted replica into the stateful infrastructure managed by Terraform without destroying the existing resources.

1.  **Import Replica into State:** Use `terraform import` to bring the promoted RDS instance into the state file.
    ```bash
    terraform import aws_db_instance.replica_instance arn:aws:rds:eu-west-1:ACCOUNT_ID:db:NEW_PRIMARY_ARN
    ```
    *(Note: The resource address `aws_db_instance.replica_instance` must match the resource block in the HCL.)*

2.  **Update Dependent Resources:** After the import, manually update the hardcoded ARN references in the Terraform configuration files (e.g., in `aws_security_group_rule` or `aws_rds_cluster_instance`) to point to the newly imported resource ID.

3.  **Detach Old Instance:** Once all applications are confirmed pointing to the new EU primary, the old US-East-1 instance can be safely detached and deleted via Terraform:
    ```bash
    terraform state rm aws_db_instance.primary_instance
    terraform apply
    ```
    *(This removes the old instance from state, allowing the subsequent `terraform destroy` or targeted deletion to proceed safely.)*

**SC2-C:**
**Architecture Design:**
*   **Connection Management:** Use **RDS Proxy** in the primary region and potentially in the DR region. RDS Proxy handles connection pooling, multiplexing, and automatic failover detection, significantly reducing the load and retry errors seen by PgBouncer.
*   **DNS Failover:** Implement **Route53 Health Checks** targeting the application endpoints in both regions. Use a weighted or latency-based routing policy that automatically shifts 100% of traffic to the healthy region upon failure detection.
*   **Application Logic:** Implement **exponential backoff and jitter** in the application's database connection logic to handle transient network issues or brief connection pool exhaustion during failover.
*   **RPO < 1 Second:** To achieve this, **Aurora Global Database** is the superior choice. It uses dedicated infrastructure and physical replication, offering near-instantaneous failover and typically achieving RPO measured in seconds or less, far surpassing standard RDS asynchronous replication capabilities.

**SC3-C:**
**Hardened CI/CD Architecture:**
1.  **Base Image Pinning:** Never use tags (`node:20-slim`). Always pin base images by their immutable **digest** (e.g., `node@sha256:abcdef123...`). This guarantees the exact content is used.
2.  **Image Signing:** Use **Cosign (Sigstore)**. After the build, the CI pipeline signs the resulting image artifact using a private key, storing the signature in the registry metadata.
3.  **Admission Control:** Deploy **Kyverno** or **OPA Gatekeeper** as a validating webhook in the cluster. Configure the policy to reject any Pod creation request unless the image reference includes a valid, trusted signature verified against the public key stored in the cluster.
4.  **SBOM Generation:** Integrate tools like Syft or Trivy into the build process to generate a **Software Bill of Materials (SBOM)** (e.g., SPDX format) for every image. Store this SBOM alongside the image in the registry.
5.  **Notary v2:** Notary v2 (or its modern successor, Sigstore) provides the cryptographic framework for signing and verifying artifacts. It ensures that the image deployed is exactly the one that passed security checks in CI, preventing runtime tampering.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
| Blocker | Problem in K8s | Specific Solution |
| :--- | :--- | :--- |
| **1. Local Session State** | Kubernetes is ephemeral. Pod restarts lose in-memory sessions, breaking sticky sessions and user experience. | Externalize state to a distributed cache (e.g., Redis Cluster) accessible by all pods. |
| **2. Local NFS Mount** | Kubernetes storage must be managed via CSI drivers. Local mounts are non-portable and non-declarative. | Provision a managed, highly available NFS/SMB volume using a CSI driver (e.g., NFS CSI) and mount it as a PVC. |
| **3. On-Prem Oracle DB** | Kubernetes is designed for cloud-native services. Direct, persistent connection to an on-prem DB introduces latency and dependency risk. | Use a dedicated, highly available database proxy (e.g., PgBouncer/ProxySQL if migrating to Postgres, or a dedicated connection pooler) running in the cluster, or use a managed cloud DB service. |
| **4. IBM MQ Integration** | MQ is a complex, proprietary messaging system requiring specific client libraries and persistent connections, which are difficult to containerize cleanly. | Introduce a dedicated **Message Broker Adapter Service** (e.g., a small microservice) running in K8s that handles the MQ connection and exposes a modern REST/gRPC interface to the monolith. |
| **5. F5 Load Balancer/Sticky Sessions** | K8s services use internal load balancing (kube-proxy) which is generally round-robin, not session-aware. | Implement an **Ingress Controller** (e.g., NGINX or HAProxy) configured with session affinity/sticky sessions based on client IP or cookie. |

**Necessity of ReadWriteMany:** The application requires multiple pods (potentially scaled replicas) to simultaneously read and write to the same shared file system (the `/data/uploads` directory). `ReadWriteMany` (RWX) is the only access mode that allows multiple nodes/pods to mount and access the volume concurrently.

**SC4-C:**
**Phased Migration Plan (Strangler Fig Pattern):**

**Phase 1: Data & State Decoupling (Shadowing)**
*   **What Moves:** Session state and file uploads.
*   **Action:** Deploy the monolith in K8s, but configure it to *read* from the new Redis/NFS storage while *writing* back to the legacy systems (dual-writing/shadowing).
*   **Traffic Split:** 0% to K8s. F5 remains the sole entry point.
*   **MQ Handling:** The K8s monolith communicates with the legacy MQ via the new Adapter Service.
*   **Go/No-Go:** Successful dual-write validation; latency parity between legacy and K8s paths.

**Phase 2: Service Extraction & Traffic Shifting**
*   **What Moves:** Read-heavy, non-critical services (e.g., product catalog lookup).
*   **Action:** Extract these services into independent microservices in K8s. Use the Ingress Controller to route a small percentage (e.g., 5%) of read traffic to the new K8s services.
*   **Traffic Split:** 5% to K8s Ingress; 95% to F5/Legacy.
*   **MQ Handling:** Critical write paths remain on the monolith.
*   **Go/No-Go:** Stable performance under 5% load; no increase in error rates on the legacy monolith.

**Phase 3: Full Cutover & Decommissioning**
*   **What Moves:** All remaining write paths and the monolith itself.
*   **Action:** Gradually increase traffic (e.g., 25%, 50%, 100%) to the K8s Ingress. Once 100% is reached, the F5 load balancer is reconfigured to point only to the K8s Ingress.
*   **MQ Handling:** The monolith is fully migrated, and the Adapter Service handles all MQ interactions.
*   **Rollback:** If any phase fails, traffic is immediately reverted to 100% on the F5/Legacy system, which remains fully operational until the K8s deployment is stable.
*   **Go/No-Go:** Sustained P99 latency matching or beating the legacy baseline for 48 hours under full load.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A:**
**Systematic Debugging Approach:**
1.  **Istio/Envoy Metrics:** Examine `istio_request_duration_milliseconds` and `envoy_cluster_upstream_rq_5xx` metrics. Look specifically at the time spent in the sidecar proxy (Envoy) vs. the time spent in the upstream service.
    *   **Proxy Queueing:** High values for `envoy_cluster_upstream_rq_pending_requests` indicate the sidecar is queuing requests because the upstream service is slow to accept them.
    *   **Upstream Latency:** High values for `istio_request_duration_milliseconds` *after* the sidecar processing time indicates the bottleneck is in the target service.
2.  **Kubernetes/Node Metrics:** Verify node resource saturation (CPU throttling, I/O wait) even if overall usage is low, as throttling can cause latency spikes.
3.  **Application Logs:** Correlate the 14:00 UTC spike time with logs from `inventory-service` to see if any specific heavy operations (like database connections) are logged.
4.  **Distributed Tracing (Jaeger/Zipkin):** Trace requests during the spike. The trace visualization will clearly show where the time is spent:
    *   If the span for the call to `inventory-service` is long, but the time spent *inside* the service span is short, the latency is likely in the network or the sidecar.
    *   If the span for the call to `inventory-service` is long, and the time spent *inside* the service span is long, the bottleneck is the application logic (database contention).

**SC5-B:**
**SQL Diagnostic Query (PostgreSQL):**
```sql
SELECT 
    a.pid AS blocking_pid, 
    a.usename AS blocking_user, 
    a.query AS blocking_query,

    pg_blocking_pids(b.pid) AS blocked_by
```

**SC5-C:**
**Architectural Solution:**
1.  **CQRS (Command Query Responsibility Segregation):** Separate the high-volume, read-heavy inventory lookups (the spike source) from the transactional write/reconciliation process. The reconciliation job writes to the primary database, while the checkout service reads from a dedicated, optimized read replica.
2.  **Read Replica for Reconciliation:** Schedule the reconciliation job to run against the read replica. This isolates the heavy locking/query load from the primary database used by live customer transactions.
3.  **Bulkhead Isolation:** Implement connection pool isolation. Use separate connection pools in the checkout-service for different types of calls (e.g., one pool for high-priority reads, one pool for background tasks). This prevents the reconciliation job's connection exhaustion from starving the critical checkout path.
4.  **CronJob Scheduling:** Adjust the CronJob to run during off-peak hours (e.g., 03:00 UTC) or, ideally, use a dedicated batch processing job that runs asynchronously and does not block the serving path.
5.  **Resource Governance:**
    *   **PodDisruptionBudgets (PDB):** Define a PDB for the serving pods to ensure that during voluntary disruptions (like node maintenance), a minimum number of checkout pods remain available.
    *   **Resource Quotas:** Apply Resource Quotas to the namespace hosting the CronJob. This limits the total CPU/Memory the job can consume, preventing it from consuming all node resources and starving the serving pods.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:**
**Identity and Access Layer Design:**
The core principle is to replace network location (IPs) with verifiable workload identity.

1.  **Workload Identity (SPIFFE/SPIRE):**
    *   **SPIRE Server:** Deployed centrally (or replicated across environments).
    *   **SPIRE Agents:** Deployed on every host/VM/Pod in vSphere, AWS, and Azure.
    *   **Attestation:** Agents attest the workload's identity (e.g., Kubernetes Service Account, AWS IAM Role, Azure Managed Identity) to the SPIRE Server.
    *   **SVID Issuance:** The SPIRE Server issues a **SPIFFE Verifiable Identity Document (SVID)**—a cryptographic certificate—to the workload. This SVID is the workload's identity.
2.  **Federation:**
    *   **AWS/Azure:** Use the native cloud identity mechanisms (IAM Roles/Managed Identities) as the initial attestation source for SPIRE.
    *   **On-Prem:** Integrate the on-prem PKI with SPIRE to attest VMs/containers.
    *   **Cross-Environment Authentication:** When a workload in AWS needs to talk to an on-prem service, the AWS workload presents its SVID. The on-prem service (which trusts the SPIRE Root CA) validates the SVID signature, confirming the caller's identity, regardless of the source IP address. This is achieved via mutual TLS (mTLS) enforced by a service mesh (like Istio).

**SC6-C:**
| Option | Cost | Bandwidth | Encryption | Failover | Zero-Trust Fit | Routing Change |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Direct Connect** | High (Port/Data) | High (Dedicated) | Physical/VPN | Manual/BGP | Excellent (Dedicated path) | Static BGP routing to TGW. |

*   **Why:** It provides the identity-centric, software-defined networking required by Zero Trust, abstracting away the underlying physical network limitations. It allows workloads to authenticate via SPIFFE/SPIRE (as designed in SC6-A) and then communicate securely over the mesh, regardless of whether they are in vSphere, AWS, or Azure.
*   **Routing Change:** The mesh handles the routing. Instead of relying solely on BGP/IP routing, the application layer routes traffic based on the verified identity of the destination service, making the underlying network topology irrelevant to the application logic.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:**
**Drift Source Analysis:**
1.  **Manual `tofu apply`:** This bypasses the entire CI/CD governance layer. The developer's local state file is used, which is not synchronized with the remote S3 state. The local apply modifies the infrastructure based on the local state, leading to divergence from the Git definition.
2.  **Diverged Helm Values:** Manual edits to values files in staging/production mean the Git repository no longer reflects the *actual* deployed state. The CI pipeline, when running `helm upgrade --values production.yaml`, will apply the Git-defined values, potentially overwriting or failing to account for the manual changes.
3.  **Direct `kubectl edit`:** This is the most dangerous form of drift. It modifies the live cluster state directly, bypassing all IaC tools (OpenTofu/Helm). The IaC tools will see the live state as different from the desired state in Git, leading to unpredictable behavior or destructive reconciliation attempts.

**State Locking Danger:**
If two engineers run `tofu apply` simultaneously without state locking, both processes read the same state file. Both calculate their changes based on the *same* initial state. When the first process writes its changes, the second process overwrites those changes with its own, leading to **lost updates** and potential resource corruption (e.g., two processes trying to modify the same resource simultaneously).

**SC7-C:**
**Drift Detection and Reconciliation:**
1.  **Scheduled Drift Detection:** Implement a scheduled CI job (e.g., nightly) that runs `tofu plan` against the production state file. If the output shows any changes (`Plan: X to add, Y to change, Z to destroy`), it triggers an alert (Slack/PagerDuty) indicating drift, but **does not apply** the changes automatically.
2.  **Admission Control (Kubernetes):** Deploy **OPA Gatekeeper** with a policy that enforces resource immutability for critical resources (e.g., ConfigMaps, Deployments). The policy checks if the resource being modified via `kubectl edit` matches the expected configuration hash derived from the Git repository. If not, the API server rejects the request.
3.  **Helm/Kustomize Structure:** Use **Helmfile** to manage environments. Define a common base chart (`base.yaml`) containing all shared configurations. Then, use environment-specific overlays (e.g., `staging/values.yaml`, `production/values.yaml`) that only override necessary parameters (e.g., replica count, resource limits). This ensures the core definition is centralized and immutable.
4.  **RBAC Enforcement:**
    *   **Kubernetes:** Create a dedicated `ci-service-account`. Grant this SA the minimum necessary permissions (`get`, `list`, `watch`, `patch`) on the target resources. Revoke all `edit` or `update` permissions from human users.

## SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:**
**Diagnosis:**
1.  **Prometheus OOM-Killed:** **Root Cause: High Cardinality.** Prometheus stores metrics as time series, and each unique combination of metric name + label set is a unique time series. 8.2 million active series is massive. High cardinality (e.g., using request IDs, user IDs, or high-cardinality labels like `instance_id` when it shouldn't) causes Prometheus to consume excessive memory storing metadata for every unique series, leading to OOM kills.
    *   **Confirmation:** Check `prometheus_tsdb_head_series` and `prometheus_tsdb_series` metrics.
    *   **Top Offender:** Use `promtool` or query the API to find metrics with the highest number of unique label combinations.
2.  **Loki Drops:** **Root Cause: Ingester Overload/Backpressure.** The ingester pods are unable to process the incoming log stream fast enough. This is often due to high volume or inefficient indexing/labeling, causing the queue to fill and drop data.
    *   **Confirmation:** Check Loki's internal metrics for queue depth and dropped log lines.
3.  **Tempo Timeouts:** **Root Cause: Inefficient Querying/Storage Backend.** Tempo relies on a backend (S3 in this case). If the queries are not optimized or the S3 access patterns are slow/throttled, retrieving traces older than 2 hours will time out.
    *   **Confirmation:** Check Tempo's query latency metrics and S3 request metrics (latency/throttling).
4.  **Thanos Compactor Lag:** **Root Cause: I/O Bottleneck/Resource Starvation.** The compactor is a heavy background job. If the underlying storage (S3) is slow, or if the Thanos sidecar/compactor pods are CPU/memory constrained, compaction falls behind, leading to stale query results.
    *   **Confirmation:** Check Thanos component logs for compaction errors and monitor the time difference between the latest ingested block and the latest compacted block.

**SC8-C:**
**Redesigned Observability Architecture:**
1.  **Metrics (Prometheus Replacement):** Replace Prometheus with **Mimir** (or VictoriaMetrics). Mimir is a horizontally scalable, multi-tenant, long-term storage solution built on Prometheus concepts. It decouples ingestion, query, and storage, allowing it to handle 50M+ series by distributing the load across many ingestion/compactor nodes.
2.  **Logs (Loki):** Deploy Loki in **Microservices Mode**. Instead of one large ingester, use smaller, dedicated ingester pods per team or per log stream. This limits the blast radius of backpressure and allows for targeted scaling.
3.  **Traces (Tempo):** Use Tempo with a dedicated, highly available, S3-backed storage backend (e.g., using a dedicated object storage service with high throughput). Ensure the Tempo query service is scaled horizontally to handle concurrent trace lookups.
4.  **Governance and Cardinality Control:**

By monitoring the volume of data ingested per `team_id`, you can generate usage reports and charge back the associated storage/compute costs.

## SC9 — Medium — Securing a Public-Facing API After a Breach

**SC9-A:**
| Vulnerability | OWASP Category | Blast Radius | Fix (Code/Infra) |
| :--- | :--- | :--- | :--- |
| **1. BOLA** | Broken Object Level Authorization (API1) | Attacker can view, modify, or delete *any* user's data by guessing IDs. | **Code Fix:** Implement authorization checks in the view/serializer layer to verify the authenticated user owns the requested resource ID. |
| **2. Data Exposure** | Excessive Data Exposure (API3) | Attacker gains access to sensitive internal business logic or employee PII. | **Code Fix:** Use serializers/DTOs to explicitly whitelist only the fields required by the client. Never return the full ORM object. |
| **3. No Rate Limiting** | Lack of Resource & Rate Limiting (API4) | Denial of Service (DoS) or mass data scraping (data exfiltration). | **Infra Fix:** Implement rate limiting at the API Gateway or ALB/WAF level. |

**SC9-C:**
**Defense-in-Depth Architecture:**
1.  **API Gateway Layer (Kong/AWS API Gateway):** Place the gateway in front of the ALB. This centralizes:
    *   **Authentication:** Offload token validation (JWT verification) from the Django app.
    *   **Rate Limiting:** Enforce global rate limits before traffic hits the backend.
    *   **Request Transformation:** Standardize headers and strip sensitive query parameters.
2.  **Authentication Migration (API Key $\rightarrow$ OAuth2/JWT):**
    *   **Migration Strategy:** Implement a **dual-auth period**. New consumers use OAuth2/JWT. Existing consumers continue using API keys, but the API Gateway is configured to accept both. A deprecation timeline is set for API keys.
    *   **JWT Implementation:** Use short-lived JWTs (e.g., 15 minutes) signed by an Identity Provider (IdP). The API Gateway validates the signature and expiration without hitting the backend.
3.  **Auditing:** Enable **CloudTrail Data Events** for the API Gateway/ALB to log every request, providing a non-repudiable audit trail of who accessed what resource and when.
4.  **Data Security:** Implement **Field-Level Encryption (FLE)** for PII fields (e.g., `internal_notes`, `created_by_employee_id`) in the database. The application layer must handle encryption/decryption using keys managed in a KMS, ensuring that even if the database is breached, the PII remains encrypted.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
**Multi-Cluster Architecture Comparison:**

| Feature | Active-Passive (Velero) | Active-Active (Service Mesh) |
| :--- | :--- | :--- |
| **RPO/RTO Feasibility** | **RPO:** Dependent on backup frequency (e.g., 15 min). **RTO:** Dependent on restore time (can be slow). | **RPO:** Near zero (continuous replication). **RTO:** Near zero (automatic traffic shift). |
| **Latency Impact (12ms)** | Minimal impact on backup/restore process, but recovery time is the bottleneck. | Minimal impact on replication, but requires robust cross-region consensus/synchronization. |
| **200TB MinIO** | Requires periodic, large-scale cross-region replication/snapshotting, which is slow. | Requires continuous, asynchronous replication between MinIO clusters. |
| **Stateful Component Replication** | **PostgreSQL:** Patroni/Streaming Replication (Asynchronous/Synchronous). **Redis:** Sentinel/Cluster replication. **RabbitMQ:** Mirroring. **MinIO:** Cross-region replication. | **PostgreSQL:** Synchronous/Asynchronous replication. **Redis:** Cluster mode. **RabbitMQ:** Federation/Mirroring. **MinIO:** Continuous replication. |

**Conclusion:** To meet RPO $\le 15$ min and RTO $\le 1$ hour reliably, **Active-Active with a Service Mesh** is superior, as it minimizes the recovery window by keeping both sites warm and ready for immediate traffic shift.

**SC10-C:**
**Automated Failover Orchestration Sequence:**

1.  **Failure Detection (Monitoring):**
    *   **Site Down:** Global monitoring (e.g., synthetic transactions, external health checks) detects failure of the Chicago site's ingress/API endpoints.
    *   **Internal Failure:** Patroni's DCS (etcd) detects the primary node is unreachable or unhealthy.
2.  **Patroni Promotion:** Patroni in Dallas detects the primary failure via the DCS and initiates an automatic promotion sequence, becoming the new primary.
3.  **Stateful Component Failover:**
    *   **PostgreSQL:** Patroni confirms promotion and updates its status in etcd.
    *   **Redis Sentinel:** Sentinel cluster detects the primary node failure and promotes the designated replica in Dallas.
    *   **RabbitMQ:** The cluster federation/mirroring mechanism automatically redirects producers/consumers to the active Dallas cluster.
    *   **MinIO:** The cross-region replication mechanism in MinIO catches up and ensures the Dallas bucket is fully synchronized and available as the primary endpoint.
4.  **DNS Failover (GSLB):** The GSLB service (e.g., AWS Route 53 Geo-routing) detects the health check failure for Chicago and automatically shifts 100% of traffic to the Dallas endpoint.
5.  **OpenTofu State Update:** A post-failover automation script runs `terraform state mv` or updates the configuration to reflect the new primary region/endpoint, ensuring future infrastructure changes target the correct active site.

**Split-Brain Handling:**
Split-brain (both sites believing they are primary) is prevented by the **Distributed Configuration Store (DCS)** (etcd). Patroni relies on the DCS quorum. If the Chicago site loses quorum, it cannot elect itself as primary, preventing it from accepting writes while Dallas is promoting.

**Failing Back:**
1.  **Recovery:** Chicago site is restored and brought back online as a standby replica, pointing to Dallas.
2.  **Synchronization:** Dallas (current primary) streams all WAL/changes back to Chicago until it is fully caught up.
3.  **Planned Switchover:** A controlled, planned switchover is executed. The GSLB is manually updated to shift traffic back to Chicago. Patroni is instructed to gracefully demote Dallas and promote Chicago.
4.  **State Update:** OpenTofu state is updated to reflect Chicago as the primary.
