**AA1**
A monolith is a single, tightly coupled application unit where all business logic resides in one codebase. Microservices are a collection of small, independent services, each running its own process and communicating via lightweight mechanisms.
Problems microservices introduce:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication.
2. **Operational Overhead:** Deploying, monitoring, and managing dozens or hundreds of independent services.
3. **Data Consistency:** Ensuring transactional integrity across multiple, independent databases (distributed transactions).

**AA2**
**Synchronous communication** requires the caller to wait for an immediate response from the called service. Example: RESTful HTTP request/response.
**Asynchronous communication** allows the caller to send a message/event and continue processing without waiting for an immediate response. Example: Kafka or RabbitMQ.

**AA3**
A **Reverse Proxy** sits in front of one or more servers, routing external client requests to the appropriate backend server based on rules (e.g., path, host header). Its primary function is traffic distribution, caching, and security termination.
An **API Gateway** sits in front of microservices, acting as a single entry point for clients. It handles cross-cutting concerns like authentication, rate limiting, request aggregation, and protocol translation, in addition to routing.
No, an API Gateway cannot entirely replace a reverse proxy. A reverse proxy is a fundamental network component for load balancing and traffic routing at L4/L7. An API Gateway *includes* reverse proxy functionality but adds significant application-layer logic (security, transformation, throttling) that a basic reverse proxy lacks.

**AA4**
The **Saga pattern** is a sequence of local transactions where each transaction updates the database and publishes an event to trigger the next step. If any step fails, the Saga executes compensating transactions to undo the preceding changes, maintaining data consistency across services.
*   **Choreography-based:** Services communicate by producing and consuming events without a central coordinator. Appropriate when the workflow is simple, decentralized, and services are highly autonomous.
*   **Orchestration-based:** A dedicated service (the orchestrator) manages the workflow, telling each participant service what local transaction to execute. Appropriate when the workflow is complex, long-running, or requires centralized monitoring and control.

**AA5**
**CQRS (Command Query Responsibility Segregation)** separates the model used for updating data (Commands) from the model used for reading data (Queries). Commands modify state; Queries retrieve state.
It is often paired with **Event Sourcing (ES)** because ES stores every change to the application state as a sequence of immutable events. The read model (Query side) is then built by projecting these events into a highly optimized, denormalized structure (e.g., a document database).
This combination solves the problem of complex read patterns in a traditional CRUD model. CRUD forces the write model to support all read needs, leading to complex joins and slow reads. CQRS/ES allows the write model to be optimized for transactional integrity, while the read model can be optimized purely for query performance, often using different data structures entirely.

**AA6**
The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service). It monitors calls; if failures exceed a threshold, the circuit "opens," immediately failing subsequent calls without attempting the network call, allowing the failing service time to recover.
The three states are: **Closed** (normal operation), **Open** (requests fail fast), and **Half-Open** (a limited number of test requests are allowed through to check if the service has recovered).
It differs from simple retry with backoff because retry attempts continue hammering a failing service, potentially exacerbating the failure (a "thundering herd"). The Circuit Breaker stops the traffic entirely. They are used together: the Circuit Breaker prevents overwhelming the service, and once the circuit is Half-Open, a limited retry mechanism (with backoff) can be used to test recovery.

**AA8**
**Strong Consistency** guarantees that once a write operation is acknowledged, all subsequent read operations, regardless of which node they hit, will immediately see that updated value.
**Eventual Consistency** guarantees that if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value, but there is a window where reads may return stale data.
To prevent overselling inventory (a critical transactional requirement), you must use **Strong Consistency**.
*   **Consistency Model:** Strong Consistency (or Linearizability).
*   **Data Store:** A strongly consistent, transactional database (e.g., PostgreSQL with strong ACID guarantees, CockroachDB, or a distributed consensus system like ZooKeeper/etcd for state management).
*   **Patterns:** Use pessimistic locking or atomic database transactions on the inventory record during the purchase flow. For high scale, use a dedicated inventory service that acts as the single source of truth for stock levels, preventing concurrent writes from different services.

**AA9**
A **sidecar proxy** is a small, dedicated network proxy container deployed alongside every service instance in a pod (in Kubernetes). It intercepts all inbound and outbound network traffic for that service.
In an Istio deployment, **Envoy** is the proxy running as the sidecar. It handles service mesh functions: traffic routing, load balancing, metrics collection, and policy enforcement.
*   **Data Plane:** The set of proxies (Envoy sidecars) that handle the actual network traffic (L4/L7 forwarding, encryption).
*   **Control Plane:** The management layer (e.g., Istiod) that configures and manages the data plane proxies, pushing routing rules, security policies, and configuration updates to them.
mTLS between sidecars solves the problem of *untrusted network hops*. Application-level TLS requires the application code to manage certificates, handshake, and encryption. Sidecar mTLS automates mutual authentication and encryption at the network layer, ensuring that only authenticated, authorized services can communicate, regardless of the application's internal logic.

**AA10**
The **Strangler Fig pattern** involves gradually replacing specific functionalities of a legacy system by building new services around it. The new services intercept calls intended for the monolith, gradually "strangling" the old functionality until the monolith can be retired.
**Migration Strategy:**
1. **Identify Boundaries:** Identify a low-risk, self-contained domain in the monolith (e.g., User Profile Management).
2. **Build New Service:** Develop the new User Profile service in .NET 8.
3. **Implement Facade/Router:** Place an API Gateway in front of the monolith. Configure the gateway to route all `/api/user/*` requests to the new .NET 8 service. All other requests continue to the monolith.
4. **Data Synchronization:** Implement a mechanism (e.g., Change Data Capture or event publishing from the monolith) to keep the new service's data store synchronized with the monolith's database during the transition.
5. **Iterate:** Repeat the process for the next domain (e.g., Order Processing).

**AA11**
The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable software-as-a-service applications.
6 Factors and why they matter:
1. **Codebase:** One codebase tracked in revision control, many deploys. (Enables CI/CD).
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures reproducible builds across environments).
3. **Config:** Store configuration in the environment. (Decouples code from environment-specific settings like database URLs, crucial for cloud portability).
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. (Allows easy swapping of services, e.g., switching from MySQL to Postgres).
5. **Build, Release, Run:** Strictly separate build, release, and run stages. (Enables immutable artifacts and reliable deployment pipelines).
6. **Processes:** Execute the application as one or more stateless processes. (Essential for horizontal scaling; state must be externalized).

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Services only know about the event contract) | Tight (Caller must know the callee's interface/location) |
| **Scalability** | Excellent (Consumers can scale independently based on topic load) | Good (Requires load balancing and service discovery) |
| **Debugging Complexity** | High (Tracing flow across asynchronous events is hard) | Low (Direct request/response chain is easy to follow) |
| **Ordering Guarantees** | Guaranteed within a partition/topic (if configured correctly) | Guaranteed by the request sequence |
| **Failure Handling** | Built-in resilience via message retention/replayability | Requires explicit retry logic and circuit breakers |

**Choice:**
*   **Choose Event-Driven:** When high decoupling, high throughput, and the ability to react to state changes across many services are paramount (e.g., IoT data ingestion, order fulfillment pipelines).
*   **Choose Request-Driven:** When an immediate, synchronous response is required for the user experience (e.g., user login validation, fetching a specific product detail page).

**AA13**
A **Load Balancer** distributes incoming network traffic across a group of backend servers to ensure no single server is overwhelmed, maximizing throughput and availability.
*   **Layer 4 (Transport Layer):** Operates based on IP addresses and TCP/UDP ports. It forwards packets to the server without inspecting the content of the request. It is fast and simple.
*   **Layer 7 (Application Layer):** Operates based on the actual content of the request (HTTP headers, URLs, cookies). It can make intelligent routing decisions based on the request path or host header.
**Use Case for L7:** Content-based routing. For example, routing `/api/v1/users` to the User Service cluster, but routing `/api/v2/billing` to the Billing Service cluster, even if they share the same IP address.

**AA14**
A **Message Queue** (e.g., RabbitMQ) is a point-to-point or publish/subscribe system designed for reliable message delivery. Messages are consumed and typically *removed* from the queue once successfully processed. It focuses on guaranteed delivery and decoupling.
A **Log-Based Message Broker** (e.g., Kafka) treats messages as an immutable, ordered log. Messages are *retained* for a configurable period, allowing multiple consumers to read the same message stream independently and replay historical data.
**When to pick one over the other:**
*   **Message Queue:** When you need a task to be executed exactly once (e.g., sending a confirmation email, processing a payment).
*   **Log-Based Broker:** When you need stream processing, historical replayability, or multiple independent services to react to the same sequence of events (e.g., tracking user activity, event sourcing).

**AA15**
A **Container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, and libraries. It virtualizes the operating system level.
A **Virtual Machine (VM)** virtualizes the entire hardware stack, including the OS kernel.
Containers are popular because they offer high density, fast startup times, and portability. They share the host OS kernel, avoiding the overhead of booting a full guest OS for every instance, making them much lighter and faster than VMs.

**AA16**
**Stateless Services** do not retain any session-specific data between requests. Every request from a client to the service must contain all the necessary information for the service to fulfill it.
**Stateful Services** retain data across multiple requests (e.g., session state, in-memory caches).
Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance, as no instance holds unique session data that needs to be maintained.
*   **Stateless Example:** A REST API endpoint that processes a calculation based on input parameters.
*   **Stateful Example:** A Redis cache server or a database connection pool.

**AA17**
An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using object-oriented paradigms (objects and classes) instead of writing raw SQL queries. It maps database tables to classes and rows to objects.
Popular ORMs: **Hibernate** (Java), **Entity Framework Core** (.NET).
**Trade-offs:**
*   **ORM Pros:** Increased developer productivity, abstraction from specific SQL dialects, improved type safety.
*   **ORM Cons:** Performance overhead (the "N+1 query problem"), impedance mismatch (the difficulty of mapping object graphs to relational tables), and difficulty in optimizing complex, highly specific queries.

**AA18**
The **Bulkhead pattern** isolates components of an application so that the failure or resource exhaustion in one component does not cascade and bring down the entire system. It partitions resources (like thread pools or connection pools) into isolated compartments.
It relates to resource isolation by ensuring that if Service A starts making slow calls to Service B, Service A's thread pool dedicated to Service B will exhaust, but the thread pool dedicated to Service C remains healthy and responsive.
**Implementation Example:** Using separate thread pools for different external dependencies. If the thread pool dedicated to the "Payment Gateway" dependency fills up due to timeouts, the thread pool dedicated to the "User Profile" dependency remains available to handle user requests, preventing a total system outage.

**AA19**
| Feature | Operational Transformation (OT) | Conflict-free Replicated Data Types (CRDTs) |
| :--- | :--- | :--- |
| **Consistency** | Strong (Requires centralized coordination/server authority) | Eventual (Converges mathematically without coordination) |
| **Latency** | Higher (Requires frequent server synchronization) | Lower (Operations can be applied locally immediately) |
| **Complexity** | High (Complex transformation algorithms needed) | Medium (Requires careful data structure design) |
| **Offline Support** | Poor (Requires synchronization upon reconnection) | Excellent (Operations are commutative and associative) |

For a system that must support **offline editing**, **CRDTs** are the superior choice. CRDTs are designed specifically for decentralized, eventually consistent systems. Because their operations are mathematically guaranteed to converge to the same state regardless of the order they are received, users can make changes offline, and when they reconnect, the system merges the changes deterministically without complex conflict resolution logic.

**AA20**
**Challenges in Polyglot Tracing:**
1. **Context Propagation:** Ensuring the unique trace ID and span ID are passed correctly across service boundaries, especially when services use different languages or protocols. Standards like **W3C Trace Context** or **B3** headers must be consistently injected and extracted by every service.
2. **Sampling Strategies:** Deciding which traces to keep. **Head-based sampling** decides whether to trace at the entry point (simple, but might miss errors deep in the trace). **Tail-based sampling** buffers all spans and decides whether to keep the trace *after* it completes, allowing for more accurate error/latency-based sampling.
3. **Storage/Querying:** Using specialized backends like **Jaeger** or **Tempo** to ingest, index, and visualize the massive volume of trace data.
4. **Asynchronous Messaging:** Tracing continuity is broken when a request hands off to a queue. To maintain continuity when passing through Kafka, the trace context (Trace ID, Parent Span ID) must be serialized and injected into the Kafka message headers. The consuming service must then extract these headers and use them to start a new child span linked to the original trace.

**OP1**
A **Type 1 (Bare-Metal) Hypervisor** runs directly on the host hardware, managing the hardware resources and allocating them to guest VMs. It has near bare-metal performance. Examples: VMware ESXi, Microsoft Hyper-V (when run natively).
A **Type 2 (Hosted) Hypervisor** runs as an application *on top* of a conventional host operating system (like Windows or Linux). It relies on the host OS for hardware access. Examples: VMware Workstation, Oracle VirtualBox.

**OP2**
**SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. Servers mount SAN storage as if it were a local disk volume. Protocols: Fibre Channel (FC), iSCSI. Used when high I/O performance and block-level access are needed (e.g., databases).
**NAS (Network Attached Storage):** A file-level storage device accessible over a standard network (LAN). It presents shared folders/files to clients. Protocols: NFS, SMB/CIFS. Used when shared file access is the primary requirement (e.g., file shares, backups).

**OP3**
**3-Tier Architecture:**
1. **Access Layer:** Connects end-user devices (PCs, phones) to the network. Handles PoE, basic switching.
2. **Distribution Layer:** Aggregates traffic from the Access layer. Provides policy enforcement, routing between VLANs, and QoS.
3. **Core Layer:** The high-speed backbone of the network. Its sole job is to move packets as fast as possible between distribution points.
**Leaf-Spine (Clos) Architecture:** Replaces the traditional hierarchy. Every Leaf switch connects to every Spine switch.
**Problem Solved:** The 3-tier model creates bottlenecks at the Distribution layer and introduces high latency because traffic often has to traverse up to the Distribution layer and back down. Leaf-Spine provides predictable, low-latency, non-blocking paths between any two endpoints, scaling horizontally by adding more spines or leaves.

**OP4**
**Architecture:**
*   **Node Count:** Minimum 3 nodes for quorum in a highly available cluster.
*   **Quorum:** Achieved via a consensus mechanism (e.g., Raft/Paxos) ensuring a majority of nodes must agree on state changes.
*   **Fencing (STONITH):** Critical mechanism to ensure a failed node cannot cause data corruption by writing to shared storage while it is technically "down." This involves forcibly powering off the node if it loses quorum.
*   **Shared Storage:** **Ceph** is ideal as it is software-defined and highly resilient, distributing data across the cluster nodes themselves.
*   **Node Failure:** If one node fails, the remaining nodes maintain quorum and continue serving traffic. Ceph automatically rebalances the lost data onto the remaining healthy nodes, maintaining data availability.

**OP5**
**VLAN Trunking:** The process of allowing traffic from multiple VLANs to traverse a single physical link (trunk).
**802.1Q Tagging:** The standard protocol used for VLAN trunking. It inserts a 4-byte tag into the Ethernet frame header, specifying the VLAN ID (VID) to which the frame belongs.
**Linux Configuration:** You configure the physical NIC (e.g., `eth0`) to be in a trunking mode (often using `802.1q` configuration). Then, you create multiple virtual interfaces (sub-interfaces) on that single physical NIC, one for each VLAN ID. For example: `eth0.10` (for VLAN 10), `eth0.20` (for VLAN 20), etc.

**OP6**
*   **RAID 1 (Mirroring):** Duplicates data across two or more drives. Excellent read performance, 50% capacity loss. Fault tolerance: Can lose all but one drive.
*   **RAID 5 (Striping with Parity):** Stripes data across drives and distributes parity information. Good balance. Fault tolerance: Can lose one drive.
*   **RAID 6 (Striping with Dual Parity):** Stripes data and uses two independent parity blocks. Fault tolerance: Can lose two drives.
*   **RAID 10 (Mirroring + Striping):** Stripes data across mirrored pairs. Excellent performance and fault tolerance. Capacity loss: 50%.
*   **RAID Z2 (ZFS):** Similar to RAID 6, using multiple parity blocks across multiple disks.
**Choice for Database Server (6 drives):** **RAID 10** or **RAID Z2**.
*   **RAID 10:** Offers the best combination of high read/write performance (due to striping) and excellent fault tolerance (can lose multiple drives, provided they aren't in the same mirror set). This is usually preferred for high-transaction databases.
*   **RAID Z2:** Offers better capacity utilization than RAID 10 while providing robust protection against two simultaneous drive failures.

**OP7**
**Architecture Design:**
1.  **Internal AD/DNS:** Internal DNS servers (Authoritative) are configured to point to the Active Directory domain controllers. They handle internal name resolution.
2.  **Recursive Resolvers:** These are the servers clients query first. They forward external queries to public DNS servers (like 8.8.8.8) and handle internal queries by forwarding to the internal authoritative servers.
3.  **Forwarders:** The recursive resolvers are configured to forward specific external queries to trusted external DNS providers.
4.  **Conditional Forwarding:** The internal DNS servers are configured to forward queries for the DMZ zone to a dedicated, highly secured authoritative server cluster in the DMZ.
5.  **Split-Horizon DNS:** The internal DNS records (e.g., `intranet.corp`) resolve to internal IPs, while the external DNS records (e.g., `corp.com`) resolve to public IPs.
6.  **DNSSEC:** Applied only to the external, public-facing zone to cryptographically verify the authenticity of the records.
**Laptop Movement:** When a laptop moves from the office (on the internal network) to the VPN, its DNS requests are intercepted by the VPN gateway, which routes them to the internal recursive resolvers, ensuring it still resolves internal names correctly.

**OP8**
**PKI Chain of Trust:**
1.  **Root CA:** The ultimate trust anchor. It is kept offline (air-gapped) and signs the subordinate CA certificate.
2.  **Subordinate/Issuing CA:** This CA is online and performs the day-to-day signing of end-entity certificates (servers, users). It is signed by the Root CA.
3.  **End-Entity Certificate:** The certificate issued to the actual resource (e.g., a web server).
The chain is verified by checking the end-entity certificate signature against the Subordinate CA certificate, and then checking the Subordinate CA certificate signature against the Root CA certificate.
**CRL vs OCSP:**
*   **CRL (Certificate Revocation List):** A list published periodically by the CA containing serial numbers of revoked certificates. Clients must download and check this list.
*   **OCSP (Online Certificate Status Protocol):** A real-time query mechanism where the client asks the CA (or an OCSP responder) directly, "Is this specific certificate valid?" (More efficient for real-time checks).
**Consequences of Compromise:**
*   **Compromised Subordinate CA:** High impact. An attacker can issue fraudulent certificates for internal services, but the damage is contained to the scope of that subordinate CA. It can be revoked and replaced relatively quickly.
*   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, if it is compromised, *every* certificate issued under its authority is untrustworthy, requiring a complete, organization-wide PKI rebuild.

For a company with 50 users per site and latency-sensitive VoIP, SD-WAN provides the best balance. It leverages the low cost of the public internet while intelligently steering latency-sensitive traffic (VoIP) over the best available path (potentially a dedicated link or optimized tunnel) and maintaining centralized policy control, which is superior to manually managing IPsec tunnels across 5 sites.

**OP10**
**iDRAC/iLO/IPMI:** These are hardware management interfaces built into servers (Dell iDRAC, HP iLO, Intregrated Platform Management Interface). They allow administrators to remotely manage the server hardware (power cycling, viewing logs, accessing the console) independent of the operating system.
**Out-of-Band Management Criticality:** It is critical because if the OS or the primary network stack fails, you still need a way to access the server to diagnose the problem, reboot it, or attach storage. It is the "emergency access" channel.
**Exposure Risk:** If the IPMI interface is exposed to the internet, it becomes a high-value target. Attackers can use it to gain full physical control over the server (e.g., forcing a reboot, accessing the console), potentially leading to data theft or denial of service, bypassing all OS-level security controls.

**OP11**
*   **LVM (Logical Volume Manager):** A software layer that abstracts physical disks into flexible logical volumes. It allows resizing and snapshotting of volumes *after* creation. Snapshot semantics are typically copy-on-write (CoW) or write-through, depending on configuration.
*   **LVM-Thin:** An extension of LVM that allows for thin provisioning, meaning you can allocate more logical space than you have physical space, and only consume physical space as data is written. Snapshot semantics are CoW.
*   **ZFS:** A comprehensive file system and volume manager. It integrates storage management, volume management, and data integrity checks (checksumming) into one system. It is highly resilient. Snapshot semantics are instantaneous, block-level copies.
**Usage:**
*   **LVM:** When you need simple, flexible volume resizing on a standard Linux setup.
*   **LVM-Thin:** When you need to over-provision storage capacity without immediately consuming physical disk space.
*   **ZFS:** When data integrity, advanced features (like automatic scrubbing), and robust, instantaneous snapshots are paramount (e.g., production databases).

**OP12**
**Strategy:** A **Stretch Cluster** configuration is required. This involves deploying the Ceph monitors and OSDs across two geographically separated data centers (sites).
**Ceph CRUSH Rules:** The CRUSH algorithm must be configured to understand the topology of both sites. Rules must be set to ensure that data replicas are placed across different failure domains (i.e., replicas must span Site A and Site B).
**Monitor Placement:** Monitors must be placed in both sites, ensuring that a majority of monitors (quorum) can still be reached even if one entire site fails.
**Network Latency:** Low latency is crucial. High latency between sites can cause split-brain scenarios because the cluster cannot quickly agree on the state of the cluster members.
**Split-Brain Problem:** This occurs when network partitioning causes two halves of the cluster to independently believe they hold the quorum and start accepting writes, leading to irreconcilable data divergence.
**2-Site Ceph Warning:** A 2-site cluster is inherently vulnerable to split-brain if the link between the sites fails, as neither side can achieve a majority quorum. A tiebreaker mechanism (like a third, small, dedicated witness node) is often required to break the tie and maintain quorum integrity.

**OP13**
**DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses, subnet masks, default gateways, and DNS server information to devices on a network.
**DORA Process:**
1.  **Discover:** Client broadcasts a DHCP Discover message to find available servers.
2.  **Offer:** Server responds with a DHCP Offer, proposing an IP address and lease terms.
3.  **Request:** Client broadcasts a DHCP Request, formally accepting the offered IP address.
4.  **Acknowledge:** Server sends a DHCP ACK, finalizing the lease assignment.
**Server Unavailability:** If a Windows client's lease expires and the server is unavailable, the client will attempt to renew the lease (DHCP Request) with the previous server. If that fails, it will eventually transition to a "limited connectivity" state, using the old IP address until it can successfully renew or obtain a new lease.

**OP14**
**Unmanaged Switch:** A simple, plug-and-play device that operates purely at Layer 2. It learns MAC addresses and forwards frames based on destination MAC, but offers no configuration, monitoring, or traffic control.
**Managed Switch:** A configurable device that allows administrators to control network traffic flow, monitor performance, and implement security policies.
**Enterprise Features:**
1.  **VLAN Support:** Segmenting broadcast domains for security and traffic isolation.
2.  **QoS (Quality of Service):** Prioritizing critical traffic (like VoIP) over less critical traffic (like bulk file transfers).
3.  **Port Security:** Limiting the number of MAC addresses allowed on a specific port to prevent unauthorized devices.
4.  **SNMP/Syslog:** Providing remote monitoring and logging capabilities for proactive troubleshooting.

**OP15**
**NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.
**Criticality:** Accurate time synchronization is vital because many distributed systems rely on timestamps for ordering events, logging, and security.
**Consequences of Clock Drift:**
1.  **Distributed Transactions:** Transactions relying on timestamps for commit ordering can fail or deadlock.
2.  **Log Analysis:** Correlating events across multiple servers becomes impossible if their clocks are skewed.
3.  **Security:** Kerberos authentication and certificate validation (which rely on time validity windows) will fail if clocks drift significantly.

**OP16**
*   **Physical Server:** A dedicated, physical piece of hardware running an operating system.
*   **Virtual Machine (VM):** A software emulation of a physical computer, running on a hypervisor. It has its own dedicated OS kernel.
*   **Container:** A lightweight, isolated process running on the host OS kernel, sharing the host's OS resources.
**Bare Metal Use Case:** You would run a workload directly on bare metal when absolute, maximum performance is required, or when the workload requires extremely low-level hardware access (e.g., specialized GPU drivers, high-frequency trading applications) where the overhead of a hypervisor or container runtime is unacceptable.

**OP17**
**UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power when utility power fails. Its role is to bridge the gap between the power failure and the generator startup, allowing graceful shutdown or continuous operation during the transition.
**Generator:** Provides long-term, sustained power during extended utility outages.
**Why both:** The UPS handles the immediate, transient failure (seconds to minutes), while the generator handles the prolonged outage (hours to days).
**ATS (Automatic Transfer Switch):** This device monitors the utility power. When utility power fails, the ATS automatically switches the load from the utility source to the generator source. When utility power returns, it switches the load back to the utility source.

**OP18**
**Active-Passive Clustering:** One server (Active) handles all the workload, while the other (Passive) remains idle, running in standby mode, constantly monitoring the active node. If the Active node fails, the Passive node takes over the workload.
**Active-Active Clustering:** Both servers actively handle portions of the workload simultaneously. This provides higher utilization and better load distribution.
**HA Implementation (Pacemaker/Corosync):**
1.  **Corosync:** Used for cluster communication and membership management, ensuring all nodes agree on the cluster state.
2.  **Pacemaker:** The resource manager that defines the services (e.g., PostgreSQL) and manages their state.
3.  **Fencing (STONITH - Shoot The Other Node In The Head):** Essential. If the active node fails but is still "alive" (e.g., network partition), STONITH uses an external mechanism (like a power controller) to forcibly shut down the potentially rogue node, preventing data corruption.
4.  **Virtual IPs (VIP):** A single, floating IP address is assigned to the service. Pacemaker ensures this VIP is only active on the node currently running the service.
**Failover Behavior:** If the active node fails, Corosync detects the failure, Pacemaker initiates the failover, STONITH ensures the failed node is isolated, and the passive node assumes ownership of the VIP and starts the PostgreSQL service.

**OP19**
**3-2-1 Rule:** Keep **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.
**RPO (Recovery Point Objective):** The maximum acceptable amount of data loss measured in time (e.g., 4 hours). Determines backup frequency.
**RTO (Recovery Time Objective):** The maximum acceptable downtime measured in time (e.g., 1 hour). Determines recovery speed/strategy.
**Backup Types:**
*   **Full:** Copies all selected data. Slowest backup, fastest restore.
*   **Incremental:** Copies only data that has changed since the *last* backup of any type. Fastest backup, slowest restore (requires the last full + all incrementals).
*   **Differential:** Copies all data that has changed since the *last full* backup. Faster restore than incremental, slower backup than incremental.
**Deduplication:** Eliminates redundant copies of data blocks, significantly reducing storage footprint.
**Offsite Storage:** Cloud storage (S3, Azure Blob) or tape libraries are used for the offsite copy.
**Immutable Backups:** Backups that cannot be modified, deleted, or encrypted by ransomware or malicious actors for a set retention period. This is the primary defense against ransomware.
**Backup vs. DR:** **Backup** is the process of creating copies of data. **Disaster Recovery (DR)** is the comprehensive plan and process of restoring business operations and data availability after a catastrophic event.
**Testing Restores:** Regular, scheduled, full-scale restore drills are mandatory to validate RTO/RPO assumptions and ensure the backup chain is viable.

**OP20**
**802.1X (Port-Based Network Access Control):** A standard that controls which devices are allowed to connect to a wired network port.
*   **Supplicant:** The client device (laptop, phone) requesting network access.
*   **Authenticator:** The network switch/port that enforces the policy and communicates with the server.
*   **Authentication Server:** The RADIUS server that validates the supplicant's credentials.
**EAP Methods:**
*   **EAP-TLS:** Uses digital certificates for mutual authentication (client proves identity to server, server proves identity to client). Highly secure.
*   **PEAP (Protected EAP):** Encapsulates an inner authentication method (like MSCHAPv2) within a TLS tunnel, providing strong authentication while being easier to deploy than full TLS.
**RADIUS:** The protocol used by the Authenticator to communicate authentication requests and responses to the Authentication Server.
**Dynamic VLAN Assignment:** Upon successful authentication, the RADIUS server instructs the switch (Authenticator) to place the supplicant into a specific VLAN, dynamically segmenting the user based on their role.
**Failed Authentication:** The switch port remains in an unauthorized state (often restricted to a quarantine VLAN or completely blocked) until valid credentials are provided.
**MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., printers, IP phones). The switch sends the device's MAC address to the RADIUS server, which checks a database to see if that MAC address is authorized for network access, bypassing the EAP handshake.
