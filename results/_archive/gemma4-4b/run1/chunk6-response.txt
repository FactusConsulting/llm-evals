## JavaScript / TypeScript

**JS1** — `var` is function-scoped and subject to hoisting (initialized as `undefined`). `let` and `const` are block-scoped. Hoisting is JavaScript's behavior of moving declarations to the top of their scope during compilation, but only the declaration is hoisted, not the assignment. `let` and `const` are subject to the Temporal Dead Zone (TDZ) until execution reaches their declaration.

**JS2** — The Event Loop is the mechanism that manages the execution of code, handling asynchronous operations. The Call Stack executes synchronous code. When an async operation (like `setTimeout` or a network request) is initiated, its callback is placed in the appropriate queue. The Event Loop continuously checks if the Call Stack is empty; if so, it moves tasks from the Microtask Queue (Promises, `queueMicrotask`) first, and then from the Macrotask Queue (I/O, `setTimeout`, `setInterval`) to the Call Stack for execution.

**JS3** — A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). Practically, it allows an inner function to access variables from its outer (parent) function even after the outer function has finished executing. The classic for loop closure bug occurs because the loop variable (`i`) is shared across all iterations; when the callbacks execute, `i` has already reached its final value. The fix is to use `let` in the loop declaration (`for (let i = 0; ...)`), which creates a new binding for `i` in each iteration.

**JS4** — A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. `async/await` is syntactic sugar built on Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()` or `try...catch` blocks around `await`. `Promise.all()` rejects immediately if *any* input promise rejects. `Promise.allSettled()` waits for *all* input promises to either fulfill or reject, returning an array of status objects describing the outcome of each.

**JS5** — A TypeScript `interface` defines a contract for an object's shape (what properties it must have). A `type` alias defines a new type based on existing types, unions, intersections, or primitives. Use `interface` when defining object shapes that might be implemented by classes (allowing declaration merging). Use `type` for unions, primitives, or complex mapped types. Discriminated unions are unions of types that share a common, literal property (the "discriminant"). This allows TypeScript to narrow the type safely using a `switch` statement on that property.

**JS6** — Prototypal inheritance means that objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. `Object.create(proto)` creates a new object whose internal `[[Prototype]]` link points directly to the provided `proto` object. ES6 classes are syntactic sugar over JavaScript's existing prototypal inheritance mechanism; they provide a cleaner, more familiar syntax for defining constructor functions and setting up prototype chains.

**JS7** — The `this` keyword refers to the object that is currently executing the function. The binding rules in priority order are: 1. `new` binding (when called with `new`). 2. Explicit binding (`.call()`, `.apply()`, `.bind()`). 3. Implicit binding (when called as a method on an object). 4. Default binding (when called globally/in strict mode, `this` is `undefined` or the global object). `bind()` returns a *new* function with the specified `this` context permanently bound; this new function can be called multiple times, but you can re-bind it to a different context.

**JS8** — `WeakRef` allows holding a weak reference to an object, meaning the garbage collector is free to reclaim the object if no strong references exist elsewhere. `FinalizationRegistry` allows registering a callback function that will be executed *after* the associated object has been garbage collected. Use them for memory management, such as cleaning up event listeners or caches associated with objects that might disappear. WeakMap keys must be objects because the garbage collector only tracks strong references; if a key were a primitive, it would always be strongly referenced, preventing the GC from ever collecting the associated value.

**JS9** — V8 optimizes JS by compiling code into machine code. **Hidden Classes** (or Shapes) allow V8 to track the structure (the sequence and types of properties) of objects. When an object's structure is consistent, V8 can use a single hidden class for fast property lookups. **Inline Caching** stores the expected type/location of an operation (like property access) directly in the machine code, avoiding repeated lookups. **Deoptimization** occurs when V8's assumptions (e.g., that an object always has a certain shape) are violated by runtime code, forcing the engine to discard the optimized machine code and revert to slower, safer interpretation. Patterns causing deoptimization include dynamically adding/deleting properties or changing the type of a variable within a tight loop.

**JS10** — Tree-shaking is a dead code elimination technique used by bundlers (like Webpack) to eliminate unused exports from modules. It works by analyzing the static `import`/`export` structure of ES Modules (ESM). ESM uses static analysis because imports are declarative (`import { func } from './module'`), allowing the bundler to trace usage paths. CommonJS (`require()`) is dynamic; since `require()` can be called conditionally or based on runtime variables, the bundler cannot statically determine which exports are used, making effective tree-shaking impossible.

**JS11** — `null` represents the intentional absence of any object value, whereas `undefined` means a variable has been declared but has not yet been assigned a value. `==` performs type coercion before comparison (e.g., `0 == false` is true), while `===` checks for strict equality, requiring both value and type to match. Nullish coalescing (`??`) returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. Optional chaining (`?.`) allows safe navigation through nested objects; if any part of the chain is `null` or `undefined`, the expression short-circuits and returns `undefined` instead of throwing an error.

**JS12** — `map()` creates a new array by applying a function to every element of the original array, returning a new array of the same length. `filter()` creates a new array containing only elements for which the provided testing function returns `true`. `reduce()` executes a reducer function on each element, resulting in a single output value. With an initial value, `reduce()` starts the accumulation process with that value, ensuring the callback runs at least once, even on an empty array. `flatMap()` maps each element using a mapping function, and then flattens the result into a new array (equivalent to `map()` followed by `flat(1)`). It is useful when a mapping function might return an array itself, and you want the final result to be a single, flat array.

**JS13** — Template literals (backticks ``) allow embedding expressions directly into strings using `${expression}`. Tagged templates allow a function to be called before the string is constructed, receiving the string parts and the interpolated values as arguments. Example: For HTML escaping, a tag function could iterate over the string parts and escape HTML entities (`&lt;`, `&gt;`) before concatenation.
```javascript
const escapeHtml = (strings, ...values) => {
  let result = '';
  strings.forEach((string, i) => {
    result += string;
    if (values[i]) {
      result += String(values[i]).replace(/[&<>"']/g, function(match) {
        return { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' }[match];
      });
    }
  });
  return result;
};
const safeHtml = escapeHtml`<h1>Hello ${'World'}!</h1>`;
```

**JS14** — Destructuring is a syntax that allows unpacking values from arrays or properties from objects into distinct variables. **Object destructuring** pulls properties out of an object (`const { name, age } = user;`). **Array destructuring** pulls elements out of an array (`const [first, second] = arr;`). Default values allow assigning a fallback if a property/element is missing (`const { age = 30 } = user;`). Renaming allows assigning the extracted value to a different variable name (`const { name: fullName } = user;`). The rest operator (`...`) collects the remaining, un-destructured properties/elements into a new array or object.

**JS15** — `for...in` iterates over the *enumerable properties* of an object, including inherited enumerable properties (though usually only own properties are desired). `for...of` iterates over the *values* of an iterable object (like Arrays, Strings, Maps). You should avoid `for...in` on arrays because it iterates over property keys (indices) as strings, and it can iterate over non-index properties added to the array object, leading to unpredictable iteration order and behavior.

**JS16** — Generics allow you to write components that can work over a variety of types while maintaining type safety. **Generic Constraints (`extends`)** restrict the types that can be used with a generic parameter, ensuring they possess certain properties or inherit from a specific type. *Example: `function identity<T extends { id: number }>(arg: T): T { return arg; }`.* **Conditional Types** allow types to be determined based on a condition. *Example: `type IsString<T> = T extends string ? true : false;`.* **Infer** is a keyword used to infer the type of a value or a function's return type based on its usage. *Example: `type MyType = Infer<SomeClass['data']>;`.*

**JS17** — The module system defines how code dependencies are managed. **CommonJS** (Node.js standard) uses synchronous `require()` to import and `module.exports` to export. **ES Modules (ESM)** use static `import` and `export` syntax. Node.js supports both; by default, `.js` files use CommonJS unless the file is explicitly treated as an ESM. Setting `"type": "module"` in `package.json` tells Node.js to treat all `.js` files in that project as ES Modules, enabling native ESM syntax.

**JS18** — TypeScript uses a structural type system, meaning that two types are considered compatible if they have the same structure (same properties with compatible types), regardless of their declared names. **Excess property checks** ensure that an object passed to a function or assigned to a type does not contain properties that are not defined in that type. They apply when assigning an object literal to a type definition. `extends` enforces that the derived type *must* have all properties of the base type. `satisfies` checks that the object *conforms* to the type structure without forcing the object to *be* that type, allowing extra properties while still verifying the required structure. Variance (in/out) defines how subtyping works for generic parameters: `in` (contravariance) means the type can accept a wider range of types; `out` (covariance) means the type can safely produce a wider range of types.

**JS19** — `Proxy` allows you to intercept fundamental operations on an object (like property lookups, assignments, function calls) by defining "traps." `Reflect` provides the standard, low-level implementations of these operations, which Proxies call. For example, to intercept assignment, you use the `set` trap in the Proxy handler. Practical example: Validation. A Proxy can intercept a property assignment (`p.age = -5`) and, within the `set` trap, throw an error if the value violates business rules, effectively enforcing validation at the object level.

**JS20** — `SharedArrayBuffer` allows multiple threads (Web Workers) to share the same block of memory, enabling high-performance, low-latency communication. `Atomics` provides methods to perform atomic operations (read-modify-write) on the integer values stored within a `SharedArrayBuffer`. This prevents race conditions. Ordering guarantees are provided by the atomic operations themselves. `Atomics.wait(typedArray, index, expectedValue)` pauses the thread until another thread calls `Atomics.notify()` on the same location, signaling a change.

## Bash

**B1** — `$@` expands to all positional parameters, treating each parameter as a separate word, preserving spaces within arguments. `*` expands to all positional parameters as a single string, separated by the first character of the `$IFS` (Internal Field Separator). `"$@"` expands to each argument quoted individually, preserving spaces. `"$*"` expands to all arguments as a single string, separated by the first character of `$IFS`.

**B2** — `set -euo pipefail` sets strict error handling:
*   `-e` (errexit): The script will exit immediately if any command exits with a non-zero status.
*   `-u` (nounset): The script will exit immediately if an unset variable is used.
*   `-o pipefail`: If any command in a pipeline fails (returns non-zero), the entire pipeline command fails, not just the last command.

**B3** — `$(command)` (Command Substitution) executes the `command` and substitutes its standard output into the current command line. `command` executes the command directly. `((expression))` performs arithmetic evaluation within Bash, treating the expression as an integer calculation. `expr` is an external utility that evaluates expressions, often requiring explicit spacing around operators.

**B4** — Process substitution (`<(command)`) runs a command and treats its standard output as a temporary file path that the current shell can read from. This is useful when a command needs to be used as an argument to another command that expects a file path. Example: `diff <(ls -l) <(ls -l sorted_files.txt)` compares the output of two separate commands as if they were two distinct files.

**B5** — Use quoting to preserve spaces and special characters: `for f in *; do ... done` is dangerous because word splitting occurs. The safe method is to use `find` combined with `while read -r` and null termination: `find . -type f -print0 | while IFS= read -r -d $'\0' f; do ... done`.

**B6** — A here document (`<<EOF`) reads input until it encounters the delimiter (`EOF`) on a line by itself, allowing multi-line input, and preserves all whitespace/newlines. A here string (`<<<`) passes a single string as standard input to a command. `<<-EOF` (here document with tab expansion) treats leading tabs in the input lines as whitespace characters rather than tabs, which is useful for cleaner indentation in multi-line scripts.

**B7** — 1. `cmd > file 2>&1`: Redirects stdout to `file`, then redirects stderr (file descriptor 2) to the same location as stdout (file descriptor 1). Both go to `file`. 2. `cmd 2>&1 > file`: Redirects stderr (2) to stdout (1), and *then* redirects stdout (1) to `file`. This means both stdout and stderr are redirected to `file`. 3. `cmd &> file`: (Bash 4+) A shorthand that redirects both stdout and stderr to `file` simultaneously. The first two differ because the order of redirection matters; in the second case, the redirection of stdout happens *after* stderr has been redirected to stdout.

**B8** — A robust lock function uses `mkdir` because it is atomic (it either succeeds completely or fails completely, preventing race conditions where two processes might try to create a file simultaneously).
```bash
lock_file() {
    local lock_dir="/tmp/my_app.lock"
    if mkdir "$lock_dir" 2>/dev/null; then
        trap 'rmdir "$lock_dir"' EXIT SIGINT SIGTERM
        echo "Lock acquired."
        # ... critical section code ...
        return 0
    else
        echo "Lock already held." >&2
        return 1
    fi
}
```
The `trap` command ensures that `rmdir` is executed upon script exit, interruption, or termination signal.

**B9** — Single quotes (`'...'`) treat everything literally; no variable expansion or command substitution occurs. Double quotes (`"..."`) allow variable expansion (`$VAR`) and command substitution (`$(cmd)`), but still respect escaping (`\"`). No quotes allow for word splitting and globbing, which is dangerous if the content contains spaces or special characters.
*Example:* `echo 'Hello $VAR'` (prints literal `$VAR`); `echo "Hello $VAR"` (substitutes value); `echo $VAR` (splits if $VAR has spaces).

**B10** — File existence: `[ -f file ]` (is a regular file), `[ -d directory ]` (is a directory), `[ -r file ]` (is readable). `[ ]` is an alias for the `test` command. `[[ ]]` is a Bash keyword that supports advanced features like regex matching (`=~`) and logical operators (`&&`, `||`) and is generally preferred for modern scripting as it handles word splitting more safely.

**B11** — `$?`: The exit status of the most recently executed foreground command (0 for success, non-zero for failure). `$$`: The Process ID (PID) of the current shell. `$!`: The PID of the most recently backgrounded command. `$#`: The number of positional arguments passed to the script/function.

**B12** — Functions are defined using `function name {}` or `name() {}`. Both are functionally equivalent in modern Bash. To return values, functions typically print the result to stdout, and the calling script captures it using command substitution: `result=$(my_function arg1)`. Bash functions do not have a formal return value mechanism like C/Java; they return an exit code (0-255).

**B13** — The `PATH` environment variable is a colon-separated list of directories that the shell searches sequentially when a command is invoked. Bash resolves commands by checking if the command name matches a file name within the directories listed in `$PATH`. A **builtin command** is implemented directly within the shell (e.g., `cd`, `echo`) and executes faster as it avoids process creation. An **external command** is an executable file located in a directory listed in `$PATH` (e.g., `ls`, `grep`). You can check if a command is a builtin using `type command`.

**B14** — `trap` allows you to specify commands to run when the shell receives a specific signal. You set handlers like `trap 'cleanup_func' EXIT` (runs when script exits), `trap 'cleanup_func' ERR` (runs on non-zero exit status), `trap 'cleanup_func' INT` (Ctrl+C), and `trap 'cleanup_func' TERM` (termination signal). When multiple signals arrive, the shell processes them according to its signal handling rules, often executing registered traps sequentially, though the exact order depends on the signal type and the shell implementation.

**B15** — `xargs` takes standard input and builds and executes command lines from it. Command substitution (`$(cmd)`) executes a command and substitutes its output as a string argument. `xargs` is superior for processing large streams of input. To handle spaces/newlines safely: `find . -type f -print0 | xargs -0 -I {} mv {} /target/`. `-0` tells `xargs` to expect null-terminated input, and `-I {}` specifies a replacement string. `-P N` runs up to N processes in parallel.

**B16** — **Arrays** store ordered lists of values (indexed numerically starting at 0). Declaration: `my_array=(val1 val2)`. Append: `my_array+=("new_val")`. Iterate: `for item in "${my_array[@]}"; do ...`. Length: `${#my_array[@]}`. **Associative Arrays** (or Hashmaps) store key-value pairs. Declaration: `declare -A my_assoc`. Access: `my_assoc[key]`. Iterate: `for key in "${!my_assoc[@]}"; do ...`. Length: `${#my_assoc[@]}`. Associative arrays are used when key lookup is required; standard arrays are used for ordered sequences.

**B17** — A **subshell** (`(...)`) executes commands in a separate, child process. Any variable changes made inside the subshell are lost when it exits, as they do not affect the parent shell's environment. A **group command** (`{ ...; }`) executes commands in the *current* shell context. Variable changes persist. Piping into a `while` loop (`cmd | while read line; do ... done`) runs the loop in a subshell by default, meaning any variables modified inside the loop body are lost upon loop completion. To prevent this, use process substitution: `while IFS= read -r line; do ... done < <(cmd)`.

**B18** — Bash handles signals by intercepting them and executing associated trap handlers. **SIGINT** (Interrupt, Ctrl+C) is typically used for user interruption. **SIGTERM** (Terminate) is the standard, polite request for a process to shut down, allowing cleanup. **SIGHUP** (Hangup) is often sent when a controlling terminal disconnects, often used to signal configuration reload. **SIGKILL** (Kill) cannot be caught or ignored; the kernel immediately terminates the process. For graceful shutdown, use `trap` to catch `SIGTERM` and `SIGINT`, allowing the script to finish current tasks before exiting.

**B19** — This requires splitting the file, processing chunks in parallel, and merging.
```bash
# 1. Split the file into N chunks (e.g., 100 lines each)
split -l 100 large_log.txt chunk_

# 2. Process chunks in parallel (using 4 jobs)
find . -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c '
    # Processing function: reads chunk, processes, writes results
    cat {} | while IFS= read -r line; do
        echo "$(date +%s) Processed: $line" >> results_temp.log
    done
'

# 3. Merge results
cat results_temp.log > final_results.log
```
Performance trade-offs: Parallel processing speeds up I/O-bound tasks but introduces overhead from process creation and context switching. Error propagation is handled by checking the exit code of the `xargs` command; if any parallel job fails, `xargs` will typically return a non-zero status.

**B20** — Running a command normally forks a new process, and the shell continues execution. `exec command` replaces the current shell process entirely with the new command; the shell itself ceases to exist. For file descriptor manipulation, `exec 3>file` opens file descriptor 3 to `file`. `exec 3>&-` closes file descriptor 3. A **bash coprocess** allows a parent shell to communicate with a child process using named pipes (FIFOs) for bidirectional, persistent communication, unlike simple pipes which are unidirectional. Use a coprocess when you need continuous, interactive, or complex two-way data exchange between two long-running shell components.

## PowerShell

**PS1** — `Write-Output` sends objects down the pipeline, allowing them to be processed by subsequent cmdlets. `Write-Host` writes directly to the console host, bypassing the pipeline. This distinction matters because cmdlets expect objects in the pipeline; if you use `Write-Host`, the object is displayed but is not available for piping or further processing by other cmdlets.

**PS2** — The PowerShell pipeline passes objects from one cmdlet to the next. `ForEach-Object` (alias `%`) is a cmdlet designed to process objects received from the pipeline. The `foreach` statement is a language construct used to iterate over collections (arrays, lists) *within* a script block or function, not typically for pipeline processing. Use `ForEach-Object` when processing pipeline input; use `foreach` when iterating over a local collection variable.

**PS3** — `[PSCustomObject]` creates a lightweight, dynamic object structure with named properties, ideal for creating structured output that can be easily piped and consumed by other cmdlets. `[hashtable]` is a dictionary-like collection where keys map to values, but it is less structured for pipeline consumption. Convert: `[PSCustomObject]@{Name="A"; Age=30}` is the standard way to create a structured object. You can convert a hashtable to an object using `[PSCustomObject]@{...}` or by casting if the structure is known.

**PS4** — PowerShell distinguishes between **terminating errors** (which stop the current operation, like a file not found when reading) and **non-terminating errors** (warnings or recoverable issues). `-ErrorAction` controls how errors are handled for a specific command (e.g., `Stop`, `Continue`, `SilentlyContinue`). `$ErrorActionPreference` sets the default behavior for the entire session. `try/catch` allows you to explicitly trap and handle errors based on their severity.

**PS5** — Splatting (`@params`) is the practice of passing a hashtable containing parameter names and values to a cmdlet. This allows you to define all parameters in a separate, reusable data structure, making scripts cleaner and easier to modify. Example: `Get-Service @params`, where `@params` is `$serviceParams = @{Name="Spooler"; Status="Running"}`. This differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named arguments for the cmdlet.

**PS6** — PowerShell remoting allows executing commands on remote machines. `Invoke-Command -ComputerName` executes a script block on the remote machine and returns the results to the local session. `Enter-PSSession` establishes an interactive, persistent connection to the remote machine, allowing you to run commands as if you were logged in locally. It primarily uses **WinRM** (Windows Remote Management) over HTTP/HTTPS for Windows targets, and can leverage SSH for Linux/Unix targets.

**PS7** — PowerShell's pipeline implicitly casts objects to `System.Object` when they are passed between cmdlets. When a function returns an array (`$result += "one"`), PowerShell often treats the return value as a single object containing the array, or it might return an empty collection if the array is empty. The correct pattern is to use `return $result` when `$result` is an array, or, more idiomatically, use `Write-Output $result` to explicitly push the array elements down the pipeline, ensuring each element is treated as a distinct object.

**PS8** — A `[scriptblock]` is a block of code that can be passed as an argument to a function or cmdlet. You pass a scriptblock to a remote session using `Invoke-Command -ScriptBlock { ... }`. The **double-hop problem** occurs when variables defined in the local scope need to be accessed inside a remote scriptblock; the variable is not automatically serialized. You solve this by using `Invoke-Command -ArgumentList` to explicitly pass the local variables into the remote scope, or by using `[scriptblock]::Create()` with explicit variable capture.

**PS9** — `@()` creates an empty array. `[array]` is a type accelerator that forces an object to be treated as an array. To force a single result into an array, wrap it: `@[myObject]`. Indexing into `$null` throws a terminating error. Indexing into an empty array (`$emptyArray[0]`) returns `$null` without error.

**PS10** — `-eq` (equals), `-ne` (not equals), `-like` (wildcard matching using `*` and `?`), `-match` (regex matching), `-contains` (checks if an array contains a specific element), `-in` (checks if a value is present within a list/array). Case-sensitive variants (`-ceq`, `-clike`, etc.) perform comparisons respecting character casing. The difference between `-contains` and `-in` is that `-contains` checks if a specific *value* exists in an array, whereas `-in` checks if a value matches a list of possible values (e.g., `$value -in @('A', 'B')`).

**PS11** — A PowerShell module bundles cmdlets, functions, variables, and configuration settings. A **script module (.psm1)** is a script file containing functions/cmdlets. A **manifest module (.psd1)** is a metadata file that describes the module (version, dependencies, required parameters) and points to the actual script module. A **binary module** is compiled code (e.g., C# assemblies). `Import-Module` loads the module's definitions into the current session's scope, making its contents available.

**PS12** — String interpolation allows embedding variables or expressions directly into a string using double quotes (`"..."`). Single quotes (`'...'`) treat the string literally, preventing any expansion. Expressions are included by placing them inside curly braces: `"The value is { $variable * 2 }"`. A here-string (`@"..."@`) is a multi-line string literal that preserves all formatting, including newlines, and is often used for large blocks of code or configuration.

**PS13** — `Get-Member` returns the properties, methods, and events available on an object, allowing deep inspection of object types. Properties are data fields; Methods are executable functions; NoteProperties are custom properties attached to objects. `Select-Object` is used to *select* and *shape* the output (choosing specific properties or creating calculated properties). `Where-Object` is used to *filter* the input objects based on a condition (e.g., `Where-Object {$_.Status -eq "Running"}`).

**PS14** — PowerShell classes (introduced in v5) allow object-oriented programming similar to C#. They differ from C# classes in that they are tightly integrated with the .NET framework but are designed to be used idiomatically within PowerShell. Limitations include that while they support inheritance and interfaces, the syntax and integration with the pipeline are unique to PowerShell. Use a class when you need to model a complex, stateful entity with defined behavior (e.g., a `User` object); use a function when you need a stateless operation (e.g., `Get-Service`).

**PS15** — `CmdletBinding()` is an attribute that transforms a standard function into an Advanced Function, giving it cmdlet-like behavior. It enables features like parameter validation, automatic help generation, and pipeline support. `SupportsShouldProcess` allows the cmdlet to check if the user wants to proceed with a potentially destructive action (e.g., `WhatIf`). `DefaultParameterSetName` specifies which parameter set is used if none is specified. `ValueFromPipeline` allows the cmdlet to accept input objects from the pipeline and process them iteratively. The `Begin` block runs once before processing starts; `Process` runs for each pipeline object; `End` runs once after all objects are processed.

**PS16** — The providers system allows PowerShell to treat different types of data sources (like the File System, Registry, or Certificate Store) as if they were standard objects accessible via the `Get-ChildItem` cmdlet. When you use `Get-ChildItem -Path "HKLM:\Software"`, PowerShell uses the `Registry` provider to traverse the registry hierarchy, treating keys like directories and values like files. This abstraction allows consistent syntax across disparate data sources.

**PS17** — A **runspace** is an execution context that hosts PowerShell code. A **[runspacepool]** manages a pool of runspaces, allowing for efficient reuse of execution contexts. A **[powershell]** object represents the PowerShell engine itself. For parallel execution, `ForEach-Object -Parallel` (v7+) manages the runspace pool internally, simplifying the code. Manual runspace management is necessary for complex, long-running parallel tasks where you need fine-grained control over thread lifecycle, but it is significantly more complex.

**PS18** — PSScriptAnalyzer is a static code analysis tool that enforces coding standards and best practices in PowerShell scripts. It operates by checking code against predefined **rules** (e.g., "Do not use global variables"). **Severity levels** (Error, Warning, Information) dictate the impact of a violation. You can suppress rules using `#Requires -ErrorAction SilentlyContinue` or specific analyzer comments. It integrates into CI/CD pipelines by running the analyzer as a pre-commit or build step, failing the build if critical rules are violated.

**PS19** — `$using:` scope allows variables defined in the parent scope to be accessed by child jobs (like `ForEach-Object -Parallel` or background jobs) by explicitly referencing them. `$args/-ArgumentList` is used to pass specific, defined variables into a remote session or job. Serialization limits (CLIXML depth) restrict the complexity of objects that can be passed across remoting boundaries; deeply nested or very large custom objects may fail to serialize correctly, requiring flattening or serialization to JSON/XML before transmission.

**PS20** — Desired State Configuration (DSC) is a management framework that allows you to define the desired state of a system (e.g., "IIS must be installed and running") and ensures the system remains in that state. **Configurations** define the desired state; **Resources** are the specific components that implement the state (e.g., the `Service` resource ensures a service is running). The **Local Configuration Manager (LCM)** is the engine that enforces the configuration on the target node. In modern infrastructure-as-code, DSC has largely been superseded or complemented by tools like Ansible, Chef, and Terraform, which offer broader orchestration capabilities.
