## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` is a dry run. It compares the current state with the desired configuration and outputs a list of actions (create, update, destroy) without making changes. `tofu apply` executes those actions to reach the desired state and updates the state file.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file mapping your configuration to real-world resource IDs. Remote state (stored in S3, GCS, etc.) is critical for teams because it provides a single source of truth, enables state locking to prevent concurrent modifications, and keeps sensitive data off local machines.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an index (0, 1, 2) to create multiple resources. `for_each` uses a map or set of strings to create resources. `for_each` is preferred when managing a list of resources that might change; removing an item from the middle of a `count` list causes all subsequent resources to be shifted/recreated, whereas `for_each` targets the specific key.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This is called "drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the cloud API. It detects the difference between the actual state and the configuration. It will then propose a plan to revert the manual change to match the code.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`output` values are for data within a single state file. `terraform_remote_state` allows one root module to read the state file of another. The recommended alternative is using a key-value store (e.g., AWS SSM Parameter Store, HashiCorp Vault). This decouples modules, prevents state-file dependency loops, and improves security by not exposing the entire state file.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
Provisioners run *after* the resource is created but *before* the resource is considered "complete" in the state. However, outputs are calculated based on the state. If the `null_resource` doesn't actually "store" the kubeconfig in a way Tofu can track (since `null_resource` has no attributes), the output is empty. 
**Fix:** Use a `local-exec` to write the config to a file, or better, use a `data` source or a separate module that reads the file from the VM after the provisioner has finished.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` brings existing infrastructure into the state file. Limitation: It only updates the state; you must manually write the HCL code to match. The `import` block allows you to declare the import in code, and with `-generate-config-out`, Tofu can automatically generate the HCL for the imported resource.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a parameter for the configuration. `variable` (input) allows users to pass values into a module (like a function argument). `output` exports information about created resources (like a function return value) for use by other modules or the CLI.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates Tofu code into API calls for a specific platform (e.g., AWS, Azure, Kubernetes). Running `plan` without `init` will fail because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It is the Dependency Lock File. It records the exact versions and hashes of the providers used. Committing it ensures that every environment (Dev, Stage, Prod) and every team member uses the exact same provider version, preventing "it works on my machine" bugs.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the current state file. To target a single resource, use: `tofu destroy -target=aws_instance.web[0]`.

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source fetches information from an external source (read-only). Use it when you need information about a resource you *don't* manage. Example: Using `data "aws_ami"` to find the latest official Ubuntu AMI ID instead of hardcoding it.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
`variable` blocks are for inputs provided by the user. `locals` are internal constants or computed values. Use `locals` to avoid repetition (DRY) and to perform complex transformations/interpolations that you don't want the user to have to provide manually.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block modifies resource behavior:
- `create_before_destroy`: Creates the new resource before deleting the old one (Use case: Zero-downtime SSL certificate rotation).
- `prevent_destroy`: Errors out if a destroy action is attempted (Use case: Production Databases).
- `ignore_changes`: Ignores updates to specific attributes (Use case: Tags managed by an external auto-scaling group).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells Tofu that a resource has changed its address in the code (e.g., moved into a module). Instead of Tofu seeing a "delete" and a "create," it performs a state rename, preserving the actual infrastructure.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
Tofu builds a Directed Acyclic Graph (DAG) to determine the order of operations. 
- **Implicit:** Created when one resource references another (e.g., `subnet_id = aws_subnet.main.id`).
- **Explicit:** Created using the `depends_on` meta-argument.
`depends_on` forces a strict sequence, reducing the number of resources Tofu can create in parallel. It should be used sparingly because it can hide architectural flaws and slow down deployment.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1. **State Splitting:** Break the monolith into smaller root modules (Tradeoff: More complex orchestration).
2. **Targeting:** Use `-target` for specific changes (Tradeoff: Risk of missing dependencies/drift).
3. **Refresh-only plans:** Use `-refresh-only` to update state without planning changes (Tradeoff: Extra step in workflow).
4. **Optimize Data Sources:** Reduce the number of expensive API calls in data blocks (Tradeoff: Less dynamic configuration).

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released? How do you manually break a lock, and what are the risks?**
Locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a process crashes, the lock remains "stale." You break it using `tofu force-unlock <LOCK_ID>`. The risk is that if another process *is* actually running, you may cause state corruption or duplicate resource creation.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process.**
1. Add the `backend "s3" { ... }` block to the configuration.
2. Run `tofu init`.
3. Tofu will detect the existing local state and ask: *"Do you want to copy existing state to the new backend?"*
4. Type `yes`.
5. Verify the `.tfstate` file now exists in the S3 bucket and the DynamoDB table contains the lock record.
6. Run `tofu plan` to ensure no changes are detected (confirming the migration was seamless).

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
A **task** is a single unit of work (calling a module). A **playbook** is a YAML file containing one or more "plays" that map tasks to specific hosts. A **role** is a structured directory containing tasks, handlers, variables, and templates, allowing for reusable and shareable automation.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary of system information gathered by the `setup` module at the start of a play. You access the OS family via `ansible_facts['os_family']` (e.g., "Debian" or "RedHat").

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
- `command`: Executes a binary. Safest; does not process through a shell (no pipes, no wildcards).
- `shell`: Executes via `/bin/sh`. Use when you need pipes (`|`), redirects (`>`), or environment variables.
- `raw`: Sends a raw SSH command. Use for hosts without Python installed (e.g., initial bootstrap or network switches).

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means running the same operation multiple times results in the same state without making unnecessary changes.
- **Idempotent:** `apt: name=nginx state=present` (If nginx is there, it does nothing).
- **Non-idempotent:** `shell: echo "Hello" >> /etc/motd` (Every run appends a new line).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
    state: present
  when: ansible_os_family == 'Debian'

- name: Install EPEL and htop
  package:
    name: "{{ item }}"
    state: present
  loop: ['epel-release', 'htop']
  when: ansible_os_family == 'RedHat'
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
(Lowest to Highest):
1. Role defaults
2. `group_vars/all`
3. `group_vars/<group>`
4. `host_vars/<host>`
5. `set_fact` (Dynamic)
6. `extra_vars` (Passed via `-e` at CLI - always wins).

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible?**
1. Create two inventory groups: `rke2_initial` (3 nodes) and `rke2_remaining` (47 nodes).
2. Use two separate plays in the playbook.
3. In the first play, target `rke2_initial`.
4. In the second play, target `rke2_remaining`.
5. Use the `wait_for` module in the second play to ensure the RKE2 API port (6443) is reachable on the first 3 nodes before proceeding.
6. Alternatively, use `serial: 3` if the logic is identical, but separate groups are cleaner for "initial" vs "remaining."

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` is a tool for encrypting sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'my_secret_password' --name 'db_password'`. This creates an encrypted block that can be pasted directly into a plain-text YAML file.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory is a list of managed nodes. A **static inventory** is a fixed file (INI or YAML). A **dynamic inventory** is a script or plugin that queries an API (e.g., AWS EC2) to generate the host list in real-time.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a special task that only runs if it is "notified" by another task that reported a `changed` status. It is typically used for restarting services. Trigger it using the `notify: <handler_name>` keyword in a task.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
It defines global Ansible settings. Common settings:
1. `inventory`: Path to the inventory file.
2. `remote_user`: Default SSH user.
3. `forks`: Number of parallel processes to use.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
`register` captures the output of a task into a variable.
Example:
```yaml
- shell: uptime
  register: uptime_result
- debug:
    msg: "The uptime is {{ uptime_result.stdout }}"
```

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
- `import_tasks`: Static. Processed when the playbook is parsed. Conditionals on the import are evaluated once at the start.
- `include_tasks`: Dynamic. Processed at runtime. Conditionals are evaluated every time the play reaches that task.
Use `include_tasks` when the decision to run the tasks depends on variables gathered during the play.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Ansible Galaxy is a public hub for sharing roles and collections. To install dependencies, list them in `requirements.yml` and run: `ansible-galaxy install -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins determine how Ansible communicates with the target.
- `ssh`: Standard for Linux/Unix; uses SSH to push modules.
- `local`: Runs tasks on the control node itself.
- `network_cli`: Used for network devices (Cisco, Juniper) that don't support Python; it maintains a persistent SSH session.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
- `delegate_to`: Executes the task on a different host than the current one in the loop.
- `run_once`: Executes the task only once for the entire batch of hosts.
**Example:** Updating a Load Balancer's target group.
```yaml
- name: Update LB
  uri: url="http://lb-api/add/{{ ansible_host }}"
  delegate_to: localhost
  run_once: true
```

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance.**
1. **Increase `forks`**: Increase the number of parallel processes in `ansible.cfg` (e.g., `forks = 50`).
2. **Enable Pipelining**: Reduces the number of SSH connections by executing modules without copying them to the remote first.
3. **Fact Caching**: Store gathered facts in Redis or a JSON file to avoid running `setup` on every play.
4. **Mitogen**: Use the Mitogen strategy plugin to replace Ansible's execution engine for significantly faster SSH communication.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet for an nginx upstream block.**
- `{{ }}`: Expressions (variable interpolation).
- `{% %}`: Control structures (loops, conditionals).
- `{# #}`: Comments.
**Snippet:**
```nginx
upstream backend_servers {
{% for host in groups['webservers'] %}
    # Health check for {{ host }}
    server {{ hostvars[host]['ansible_default_ipv4']['address'] }}:8080;
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible.**
1. **Serial Batches:** Set `serial: 20%` (or a fixed number like 2) to update servers in small groups.
2. **Pre-task:** Use `uri` or a LB module to remove the current batch from the Load Balancer.
3. **Deployment:** Update the application code/service.
4. **Health Check:** Use the `uri` module to poll the local app endpoint until it returns `200 OK`.
5. **Post-task:** Re-add the batch to the Load Balancer.
6. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, if a health check fails, trigger a task to revert the app version and re-add the server to the LB to maintain capacity.
