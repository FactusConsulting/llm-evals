## Kubernetes

**K1 — Easy:** A **Deployment** is for stateless applications; it manages a set of identical pods and ensures the desired number of replicas are running. A **StatefulSet** is for stateful applications; it provides guarantees about the ordering and uniqueness of pods, giving each pod a persistent identifier (e.g., `web-0`, `web-1`) and stable network identity.

**K2 — Easy:** A **ClusterIP** service creates a virtual IP. When a request hits this IP, `kube-proxy` (using iptables or IPVS) intercepts the traffic and load-balances it across the healthy Pod IPs associated with the service's selector.

**K3 — Medium:** 
- **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an admin or dynamically (the "actual" disk).
- **PersistentVolumeClaim (PVC):** A request for storage by a user (the "ticket" to get a disk).
- **StorageClass (SC):** A "profile" that defines different types of storage (e.g., SSD vs HDD) and allows for dynamic provisioning.
- **Relation:** A user creates a **PVC** $\rightarrow$ K8s looks for a matching **PV** or uses a **StorageClass** to automatically create a **PV** $\rightarrow$ the **PVC** is bound to the **PV**.

**K4 — Medium:**
1. `kubectl logs <pod>`: Check application logs for runtime crashes or unhandled exceptions.
2. `kubectl describe pod <pod>`: Check the "Events" section for OOMKilled, failed liveness probes, or image pull errors.
3. Check Environment Variables/Secrets: Ensure all required ConfigMaps or Secrets are present and correctly named.
4. Resource Limits: Check if the pod is hitting its memory limit (OOM) or CPU throttling causing timeouts.

**K5 — Medium:** **CoreDNS** provides service discovery. It allows pods to find other services using DNS names (e.g., `my-svc.namespace.svc.cluster.local`) instead of IPs. If CoreDNS pods are down, internal service discovery fails, and pods will be unable to communicate with each other via service names.

**K6 — Hard:** The scheduler uses a two-step process:
1. **Filtering (Predicates):** It removes nodes that don't meet requirements (e.g., insufficient CPU/RAM, node selector mismatch, taints without tolerations).
2. **Scoring (Priorities):** It ranks remaining nodes to find the "best" fit.
**Factors considered:**
- **Resource Fit:** Preferring nodes where the pod's request fits best (LeastRequestedPriority).
- **Inter-pod Affinity/Anti-affinity:** Placing pods together or apart based on labels.
- **Taints/Tolerations:** Ensuring pods only land on nodes they are allowed to be on.

**K7 — Hard:** 
- **Scheduling:** Yes. The node has 500Mi available (4GB - 3.5GB). The pod requests 256Mi, which fits.
- **Runtime:** If the pod uses 600Mi, it exceeds its `limits.memory` (512Mi). The Linux kernel will trigger an Out-Of-Memory (OOM) event, and Kubernetes will **OOMKill** the pod.

**K8 — Hard:** 
1. **External LB:** Receives traffic and forwards it to the Ingress Controller's NodePort.
2. **Ingress Controller (NGINX):** Receives the request, matches the Host/Path against Ingress rules.
3. **Service/Endpoints:** The controller looks up the **Service**, which points to a list of **Endpoints** (the actual Pod IPs).
4. **Routing:** The controller bypasses the Service IP and routes the traffic directly to a **Pod IP** (via iptables/IPVS or internal proxying) to reduce latency.

**K9 — Medium:** A **NetworkPolicy** is an L3/L4 firewall for pods. 
- **Default:** If no policy exists, all ingress and egress traffic is allowed.
- **Applying a policy:** Once a policy selects a pod, that pod becomes "isolated." All traffic is denied unless explicitly allowed by a rule in that or another policy.

**K10 — Medium:** 
- **RollingUpdate:** Gradually replaces old pods with new ones, ensuring zero downtime.
- **Recreate:** Kills all existing pods before starting new ones, causing downtime.
- **Choice:** Use **Recreate** when the application does not support two different versions running simultaneously (e.g., a database migration that is not backward compatible).

**K11 — Easy:** A **namespace** is a virtual cluster used to isolate resources within a single physical cluster. Default namespaces: `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

**K12 — Easy:** It provides detailed metadata and state. Three things `get pod` doesn't show:
1. **Events:** (e.g., "Successfully assigned to node X").
2. **Container Status:** (e.g., Exit Code, Restart count).
3. **Resource Limits/Requests:** The exact CPU/RAM configured.

**K13 — Easy:** A **ConfigMap** stores non-confidential configuration data in key-value pairs. Consumption methods:
1. **Environment Variables:** Injected into the container at startup.
2. **Volume Mounts:** Mounted as files in a specific directory inside the pod.

**K14 — Easy:** 
- **ClusterIP:** Internal IP; only reachable from within the cluster.
- **NodePort:** Exposes the service on a static port on every Node's IP.
- **LoadBalancer:** Provisions a cloud provider's LB to route external traffic to the NodePort/ClusterIP.

**K15 — Easy:** A **DaemonSet** ensures that all (or some) nodes run a copy of a specific pod. Use it for cluster-wide infrastructure services like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium:** 
- **Taints/Tolerations:** Taints are applied to **Nodes** to repel pods. Tolerations are applied to **Pods** to allow them to stay on tainted nodes. (Use case: Dedicating a node to GPU workloads).
- **Node Affinity:** Applied to **Pods** to attract them to specific nodes based on labels. (Use case: Ensuring a pod runs on a node in a specific availability zone).

**K17 — Medium:** An **Operator** is a custom controller that uses **Custom Resource Definitions (CRDs)** to manage a complex application. While a standard controller manages basic K8s objects, an Operator encodes "human operational knowledge" (e.g., how to perform a DB backup or a version upgrade) into code to automate the full lifecycle of a stateful app.

**K18 — Hard:** etcd uses the **Raft** consensus algorithm for strong consistency. 
- **Quorum Loss:** If a majority of nodes are lost, the cluster becomes read-only or unavailable because it cannot reach consensus on writes.
- **Recovery:** If 2/3 nodes are lost, you cannot recover via Raft. You must restore the remaining node from a recent snapshot and re-bootstrap the cluster as a single-node cluster, then add new members.

**K19 — Hard:** RBAC controls access to the K8s API.
- **Role:** Permissions within a specific namespace.
- **ClusterRole:** Permissions cluster-wide.
- **RoleBinding:** Grants a Role to a user/group in a namespace.
- **ClusterRoleBinding:** Grants a ClusterRole to a user/group cluster-wide.

**Manifests:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev-ns
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev-ns
subjects:
- kind: User
  name: "developer-user"
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:** By default, `ndots` is 5. If a pod looks up `google.com`, K8s tries appending search paths (e.g., `google.com.default.svc.cluster.local`) first. Since `google.com` has fewer than 5 dots, it triggers multiple failed internal queries before trying the absolute name.
**Fix:** Set `dnsConfig` in the pod spec to `ndots: 1`.

## Development

**D1 — Easy:** `git merge` combines branches and creates a merge commit, preserving the exact history. `git rebase` moves the entire branch to begin on the tip of the master branch, creating a linear history. **Avoid rebasing** public/shared branches, as it rewrites history and breaks other developers' local copies.

**D2 — Easy:** **TCP** is connection-oriented, reliable, and ensures ordered delivery (e.g., HTTP, SSH). **UDP** is connectionless, faster, but does not guarantee delivery or order (e.g., DNS, VoIP).

**D3 — Medium:** A **race condition** occurs when the timing or order of events affects the correctness of a program, typically when multiple threads access shared data. 
**Example:** Two threads incrementing a shared variable `count = 0`. Both read `0`, both increment to `1`, and both write `1` back. The final value is `1` instead of `2`.

**D4 — Medium:** 
- **Symmetric:** Same key for encryption and decryption (e.g., AES). Fast, but key distribution is hard.
- **Asymmetric:** Public key encrypts, private key decrypts (e.g., RSA). Slower, but solves key distribution.
- **TLS:** Uses asymmetric encryption to securely exchange a symmetric "session key," which is then used for the actual data transfer for efficiency.

**D5 — Medium:** A **layer** is a read-only snapshot of the filesystem changes made by a Dockerfile instruction. Docker caches these layers. To optimize, place **stable instructions** (installing OS packages) at the top and **frequently changing instructions** (copying source code) at the bottom to avoid rebuilding the entire image on every code change.

**D6 — Medium:** 
1. **Ingress/LB Logs:** Check if the request is even reaching the application.
2. **Pod Status:** Check for restarts or `CrashLoopBackOff` (indicates app instability).
3. **Resource Metrics:** Check for CPU/RAM spikes (indicates saturation).
4. **Downstream Dependencies:** Check logs for timeouts connecting to the Database or external APIs.

**D7 — Hard:** **CAP Theorem** states a distributed system can only provide two of three: Consistency, Availability, and Partition Tolerance.
- **CP (Consistency/Partition):** MongoDB (default). If a partition occurs, it stops accepting writes to ensure data consistency.
- **AP (Availability/Partition):** Cassandra. It allows writes during a partition, accepting that some nodes may have stale data (eventual consistency).

**D8 — Medium:** 
- **Horizontal Scaling:** Adding more machines/instances (scaling out).
- **Vertical Scaling:** Adding more CPU/RAM to an existing machine (scaling up).
- **Patterns:** Statelessness (no session data on server), Load Balancing, and Database Sharding.

**D9 — Easy:** An **environment variable** is a dynamic value available to processes in a shell. To persist it on Linux, add `export VAR_NAME=value` to the `~/.bashrc` or `~/.profile` file.

**D10 — Easy:** **JSON** is a strict, lightweight data-interchange format. **YAML** is a human-readable data serialization language.
- **JSON Advantage:** Faster parsing and universal support in browsers/APIs.
- **YAML Advantage:** Supports comments and is much easier for humans to write/read for configuration.

**D11 — Easy:** A **REST API** is an architectural style for networked applications using HTTP.
- **GET:** Retrieve a resource.
- **POST:** Create a new resource.
- **PUT:** Update/Replace an existing resource.
- **DELETE:** Remove a resource.

**D12 — Easy:** **Version pinning** is specifying the exact version of a dependency (e.g., `requests==2.25.1` instead of `requests>=2.0`). It ensures **reproducible builds** by preventing the application from breaking when a dependency releases a new, incompatible version.

**D13 — Easy:** 
- **Compiled:** Source code is translated to machine code before execution (e.g., C++, Rust).
- **Interpreted:** Source code is read and executed line-by-line by a runtime (e.g., Python, Ruby).

**D14 — Medium:** A **reverse proxy** sits in front of web servers and forwards client requests to them. A **forward proxy** sits in front of clients and forwards requests to the internet.
- **Nginx:** Used for load balancing and SSL termination.
- **HAProxy:** Used for high-performance TCP/HTTP load balancing.

**D15 — Medium:** A **deadlock** is a state where two or more threads are blocked forever, each waiting for the other to release a resource.
**Coffman Conditions:**
1. **Mutual Exclusion:** Only one process can use a resource at a time.
2. **Hold and Wait:** A process holds a resource while waiting for another.
3. **No Preemption:** Resources cannot be forcibly taken away.
4. **Circular Wait:** A closed chain of processes exists where each waits for the next.

**D16 — Hard:** **Eventual Consistency** guarantees that if no new updates are made to a data item, eventually all accesses will return the last updated value.
- **Cassandra:** Uses tunable consistency. You can specify `Consistency Level` (CL) for reads and writes.
- **Read-after-write:** To ensure this, the sum of nodes written to ($W$) and nodes read from ($R$) must be greater than the replication factor ($N$): $R + W > N$.

**D17 — Hard:** **mTLS** is TLS where both the client and server present certificates to each other.
**Handshake:**
1. Client connects to Server $\rightarrow$ Server sends its certificate.
2. Client verifies Server's certificate.
3. Server requests Client's certificate $\rightarrow$ Client sends its certificate.
4. Server verifies Client's certificate.
5. Both agree on a symmetric session key.
**Usage:** Commonly used in **Service Meshes** (Istio, Linkerd) for zero-trust internal communication.

**D18 — Hard:** A **hash table** uses a hash function to map keys to indices in an array.
- **Collision Resolution:** 
    - **Chaining:** Each index points to a linked list of entries.
    - **Open Addressing:** Finds the next empty slot (linear/quadratic probing).
- **Complexity:**
    - **Average:** $O(1)$ for insertion, lookup, and deletion.
    - **Worst:** $O(n)$ (when all keys hash to the same index).

**D19 — Hard:** A **circuit breaker** prevents a system from repeatedly trying to call a failing service.
- **Closed:** Requests flow normally.
- **Open:** Requests fail immediately without calling the service (fail-fast).
- **Half-Open:** Periodically allows a few requests to see if the service has recovered.
- **Relation:** It prevents "retry storms." While **exponential backoff** slows down retries, the circuit breaker stops them entirely to allow the failing service to recover.

**D20 — Hard:** 
- **Optimistic:** Assumes conflicts are rare. It doesn't lock; instead, it checks for changes (usually via a version number) at the time of commit. If the version changed, the transaction fails. (Use for: Low contention, high-scale web apps).
- **Pessimistic:** Assumes conflicts are likely. It locks the record immediately upon reading. (Use for: High contention, financial transactions).
- **Example:** Optimistic uses `UPDATE ... WHERE version = 1`; Pessimistic uses `SELECT ... FOR UPDATE`.
