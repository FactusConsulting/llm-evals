## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the **Restricted Pod Security Standard (PSS)** requires that a pod must not run as root. While `runAsNonRoot: true` tells Kubernetes to validate that the container does not run as root, it does not *assign* a user. The new base image (`chainguard/static`) defaults to `USER root`. Under the **Baseline** policy, this was permitted. Under **Restricted**, Kubernetes checks the image's default user; since it is root and no `runAsUser` (non-zero ID) is specified in the manifest to override it, the Pod is rejected or the container fails to start because it violates the security policy.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[0].state.waiting.reason=="CrashLoopBackOff") | [.metadata.namespace, .metadata.name, .spec.securityContext, .spec.containers[0].securityContext] | @json'
```

**SC1-C:**
*   **Image-level fix:** Update the Dockerfile to include `USER 1000` (or any non-zero UID) to ensure the image is non-root by default.
*   **Manifest fix:** Explicitly set `securityContext.runAsUser: 1000` in the Deployment spec.
*   **CI Pipeline Gate:** Integrate `kube-score` or a Kyverno CLI check in the CI pipeline to validate manifests against the Restricted PSS before merging.
*   **Rollout:** Use a `RollingUpdate` strategy with `maxUnavailable: 25%` and `maxSurge: 25%`. Since the issue is a configuration mismatch, updating the manifest and triggering a rollout will replace pods incrementally without downtime.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is caused by **asynchronous replication lag**. In cross-region RDS, WAL (Write Ahead Log) records are shipped asynchronously to avoid blocking primary writes with 85ms+ latency. If the primary fails before all WALs are shipped/applied in `eu-west-1`, the promoted replica is missing the most recent transactions. To quantify the loss, I would check the `pg_stat_replication` view on the old primary (if accessible) or compare the last committed transaction timestamp (`pg_last_xact_replay_timestamp()`) on the replica against the application logs of the primary.

**SC2-B:**
1.  **Import:** `terraform import aws_db_instance.primary <new-rds-instance-id>`
2.  **State Move:** If the resource name in code differs: `terraform state mv aws_db_instance.replica aws_db_instance.primary`.
3.  **Update Code:** Update the ARN/ID in the `.tf` files to match the promoted instance.
4.  **Apply:** Run `terraform plan` to ensure no destruction is planned, then `terraform apply`. This updates the dependent Security Groups and Route53 records to point to the new ARN.

**SC2-C:**
*   **Architecture:** Replace PgBouncer with **RDS Proxy** to handle failover more gracefully and reduce connection overhead. Use **Route53 Failover Routing** with health checks to automatically flip the CNAME to the DR region.
*   **RPO < 1s:** Standard RDS cannot guarantee this across regions. I recommend **Aurora Global Database**, which uses storage-level replication (typically < 1 second lag) rather than PostgreSQL's logical/physical streaming.
*   **Application:** Implement exponential backoff and jitter in the application's connection logic to handle the "login retry" storm during failover.

## SC3 — Container Image Supply Chain Compromise

**SC3-A:**
1.  **Containment:** Cordon the affected nodes to prevent new pods from scheduling. Use a `NetworkPolicy` to egress-block the affected pods (isolate them) rather than deleting them.
2.  **Forensics:**
    *   **Process Tree:** `kubectl exec <pod> -- ps auxf` or use `nsenter` on the node to enter the container's PID namespace.
    *   **Network:** `kubectl exec <pod> -- netstat -tupn` or capture traffic via `tcpdump` on the node's veth interface.
    *   **Filesystem:** `kubectl exec <pod> -- find /tmp -type f` and use `docker diff <container_id>` on the host to see modified files.

**SC3-B:**
```bash
#!/bin/bash
IMAGE="api-gateway:v2.4.1"
BASE_IMAGE="node:20-slim"
# Get digest of current image in ECR
LOCAL_DIGEST=$(aws ecr describe-images --repository-name $IMAGE --image-ids imageTag=latest --query 'imageDetails[0].imageDigest' --output text)
# Get digest of upstream image
REMOTE_DIGEST=$(skopeo inspect docker://docker.io/library/$BASE_IMAGE | jq -r '.Digest')

if [ "$LOCAL_DIGEST" != "$REMOTE_DIGEST" ]; then echo "DIGEST MISMATCH"; fi

# List layers and compare
docker history --no-trunc $IMAGE > layers.txt
# Compare layers.txt against a known-good build artifact
diff layers.txt known_good_layers.txt
```

**SC3-C:**
*   **Pinning:** Change `FROM node:20-slim` to `FROM node:20-slim@sha256:<hash>`.
*   **Signing:** Use **Cosign** to sign images after the Trivy scan passes.
*   **Admission Control:** Deploy **Kyverno** to block any image that lacks a valid signature from the CI key.
*   **SBOM:** Generate a CycloneDX SBOM using **Syft** during build and store it in the registry.
*   **Notary v2:** Provides the standard for signing and verifying OCI artifacts, ensuring the image pulled is exactly what was pushed.

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Sticky Sessions:** K8s pods are ephemeral. *Solution:* Move sessions to an external **Redis** cluster.
2.  **Local NFS:** Pods cannot share local disk. *Solution:* Use a **CSI driver** (e.g., AWS EFS or Azure Files) for shared storage.
3.  **Oracle 19c:** High latency/connectivity from K8s. *Solution:* Use a **Kubernetes Service of type ExternalName** or an Endpoints object to map the on-prem DB.
4.  **IBM MQ:** Legacy protocol/stateful connection. *Solution:* Deploy an **IBM MQ Client sidecar** or use a bridge to translate to a K8s-native message bus.
5.  **Monolith Size:** Long startup times cause Liveness/Readiness probe failures. *Solution:* Implement **Startup Probes** to give the JVM time to warm up.

**SC4-B:**
```hcl
variable "nfs_server" { default = "nfs.internal.com" }
variable "nfs_path"   { default = "/exports/uploads" }

resource "kubernetes_storage_class" "nfs_sc" {
  metadata { name = "nfs-csi" }
  storage_class_name = "nfs-csi"
  parameters = {
    server = var.nfs_server
    path   = var.nfs_path
  }
}

resource "kubernetes_persistent_volume" "nfs_pv" {
  metadata { name = "nfs-pv" }
  spec {
    capacity { storage = "1Ti" }
    access_modes = ["ReadWriteMany"] # Necessary because multiple pods must write uploads simultaneously
    persistent_volume_reclaim_policy = "Retain"
    csi { driver = "nfs.csi.k8s.io"; volume_handle = "nfs-vol-1" }
  }
}

resource "kubernetes_persistent_volume_claim" "nfs_pvc" {
  metadata { name = "nfs-pvc" }
  spec {
    access_modes = ["ReadWriteMany"]
    storage_class_name = "nfs-csi"
    resources { requests = { storage = "1Ti" } }
  }
}
```

**SC4-C:**
*   **Phase 1:** Deploy the monolith "as-is" in K8s but keep traffic on F5. Use F5 to route 1% of traffic to K8s Ingress.
*   **Phase 2:** Extract "Uploads" and "Session" logic into microservices. Route specific paths (`/uploads`) to K8s.
*   **Phase 3:** Migrate remaining business logic. Shift traffic 25% $\rightarrow$ 50% $\rightarrow$ 100%.
*   **Integration:** IBM MQ remains on-prem; K8s pods connect via a dedicated VPN/DirectConnect.
*   **Rollback:** Immediate DNS/F5 weight shift back to bare-metal.
*   **Metrics:** p99 latency $\le$ 2s and Error Rate $\le$ 0.1% compared to baseline.

## SC5 — Mysterious Latency Spike in Microservices

**SC5-A:**
1.  **Metrics:** Check Istio `istio_request_duration_milliseconds` (split by source/destination). Check K8s `container_cpu_usage_seconds_total`.
2.  **Tracing:** Use Jaeger to find the "gap." If the span for `checkout-service` is long but the `inventory-service` span is short, the latency is in the **Envoy sidecar or network**. If the `inventory-service` span is long, it's the **application**.
3.  **Envoy Metrics:** Compare `upstream_rq_time` (total time) vs `upstream_cx_connect_timeout` or `upstream_rq_pending_overflow` to identify queueing.

**SC5-B:**
**SQL:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid, 
       blocking_activity.query AS blocking_query, blocked_activity.query AS blocked_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_locks.pid = blocked_activity.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype 
     AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
     AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid
WHERE NOT blocked_locks.granted;
```
**Go (Circuit Breaker):**
```go
var cb = gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name: "inventory-service",
    MaxRequests: 5,
    Interval: 10 * time.Second,
    Timeout: 30 * time.Second,
})

func CallInventory() ([]byte, error) {
    body, err := cb.Execute(func() (interface{}, error) {
        return http.Get("http://inventory-service/api/stock")
    })
    return body.([]byte), err
}
```

**SC5-C:**
*   **CQRS:** Use a **Read Replica** for the reconciliation job to avoid locking the primary write table.
*   **Bulkhead:** Create two separate DB connection pools in the `inventory-service`: one for API requests (high priority) and one for background jobs (low priority).
*   **Scheduling:** Randomize CronJob start times (jitter) or move to a low-traffic window.
*   **K8s:** Set `PriorityClass` for serving pods higher than the CronJob. Use a `PodDisruptionBudget` to ensure `minAvailable: 80%` for the API.

## SC6 — Zero-Trust Network Overhaul

**SC6-A:**
*   **Identity:** Implement **SPIRE** (SPIFFE Runtime Environment). SPIRE agents on VMware, AWS, and Azure issue short-lived SVIDs (X.509 certificates) to workloads based on node/pod attributes.
*   **Federation:** Use **SPIFFE Federation**. The AWS SPIRE server and On-Prem SPIRE server exchange trust bundles. A workload in AWS presents its SVID; the on-prem service verifies it against the AWS trust bundle.
*   **Cloud Integration:** Map SPIFFE IDs to AWS IAM Roles using OIDC providers for access to S3/RDS.

**SC6-B:**
```hcl
resource "aws_ec2_transit_gateway" "main" { name = "zt-tgw" }

variable "endpoints" {
  type = list(string)
  default = ["s3", "rds", "ecr"]
}

resource "aws_vpc_endpoint" "private_links" {
  for_each = toset(var.endpoints)
  vpc_id   = aws_vpc.main.id
  service_name = "com.amazonaws.${var.region}.execute-api" # Simplified for example
  vpc_endpoint_type = "Interface"
  security_group_ids = [aws_security_group.endpoint_sg.id]
}

resource "aws_security_group" "default_deny" {
  name = "default-deny"
  vpc_id = aws_vpc.main.id
  # No ingress rules = default deny
}
```

**SC6-C:**
*   **Direct Connect:** Highest bandwidth, lowest latency, most expensive. Best for stability.
*   **ECMP VPN:** Increases bandwidth by using multiple tunnels. Cheaper, but still subject to internet jitter.
*   **Tailscale/Netbird:** Overlay mesh. Easiest to implement Zero Trust (WireGuard based).
*   **Recommendation:** **Direct Connect** for the backbone, but layer **Tailscale/Netbird** on top for the identity-based mesh.
*   **Routing:** Direct Connect requires BGP configuration; Tailscale requires installing an agent on nodes and managing a coordination server.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
1.  **Manual Apply:** Bypasses peer review and CI tests.
2.  **Diverged Values:** Leads to "it works in staging but not prod" bugs.
3.  **`kubectl edit`:** Creates "ghost" configurations that are wiped out during the next automated deploy.
*   **State Locking Danger:** Without locking, two engineers running `apply` simultaneously can cause **state corruption** (partial writes), leading to resources being orphaned or accidentally deleted.

**SC7-B:**
```yaml
stages: [validate, plan, apply]

tofu_plan:
  stage: plan
  script:
    - tofu init -backend-config="dynamodb_table=terraform-lock"
    - tofu fmt -check
    - tofu validate
    - tofu plan -out=tfplan
  artifacts:
    paths: [tfplan]

tofu_apply_prod:
  stage: apply
  environment: production
  script:
    - tofu apply tfplan
  when: manual # Manual gate for production
```

**SC7-C:**
*   **Drift Detection:** A scheduled GitLab CI job runs `tofu plan -detailed-exitcode`. If it returns `2` (drift detected), it triggers an alert.
*   **Blocking Edits:** Use **Kyverno** to deny `UPDATE` requests on `ConfigMaps` in production unless the user is the `gitlab-ci-sa` service account.
*   **Helm Structure:** Use **Helmfile** with a `common-values.yaml` and `prod-values.yaml` (overrides).
*   **RBAC:** Remove `cluster-admin` from all human users. Grant `edit` role to humans in `dev`, but only `view` in `prod`. Only the CI Service Account gets `cluster-admin` in `prod`.

## SC8 — Observability Stack Scaling Failure

**SC8-A:**
1.  **Prometheus OOM:** **High Cardinality**. Too many unique label combinations (e.g., putting `user_id` in a label) are bloating the TSDB index in RAM.
2.  **Loki Drops:** **Ingester Saturation**. The write path cannot flush chunks to S3 fast enough, or the ingester is hitting memory limits.
3.  **Tempo Timeouts:** **S3 Latency/Indexing**. Querying old traces requires scanning too many blocks from S3 without an efficient index.
4.  **Thanos Lag:** **Compactor Resource Starvation**. The compactor cannot merge blocks faster than they are created, leading to too many small files in S3.

**SC8-B:**
```bash
#!/bin/bash
PROM_URL="http://prometheus:9090"
echo "Metric | Series Count"
curl -s "$PROM_URL/api/v1/label/__name__/values" | jq -r '.data[] | .[]' | while read metric; do
  count=$(curl -s "$PROM_URL/api/v1/query?query=count({__name__=\"$metric\"})" | jq -r '.data.result[0].value[1]')
  echo "$metric | $count"
done | sort -t'|' -k2 -rn | head -n 20
```

**SC8-C:**
*   **Architecture:** Replace Prometheus with **Mimir** (horizontally scalable, separates read/write). Move Loki to **microservices mode** to scale ingesters and queriers independently.
*   **Tempo:** Use **Parquet** storage for traces to improve query performance.
*   **Governance:** Implement **Relabeling configs** to drop high-cardinality labels at the agent level.
*   **Chargeback:** Use Mimir's `tenant_id` label. Query `sum(prometheus_remote_storage_samples_total)` grouped by `tenant_id` to calculate costs per team.

## SC9 — Securing a Public-Facing API After a Breach

**SC9-A:**
1.  **BOLA (API1:2023):** User A accesses User B's data. *Fix:* Validate ownership in the view.
    ```python
    def get_object(self, queryset=None):
        obj = super().get_object()
        if obj.owner != self.request.user:
            raise PermissionDenied("Not your record")
        return obj
    ```
2.  **Excessive Data Exposure (API3:2023):** Internal fields leaked. *Fix:* Use a **Serializer** to explicitly define allowed fields.
3.  **Lack of Resources (API4:2023):** Scraping. *Fix:* Implement **Rate Limiting** (WAF or Django-ratelimit).
4.  **Security Misconfiguration (API7:2023):** Keys in logs. *Fix:* Move keys to `Authorization: Bearer <key>` header.

**SC9-B:**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {
  name  = "api-protection"
  scope = "REGIONAL"
  default_action { allow {} }

  rule {
    name     = "RateLimit"
    priority = 1
    action { block {} }
    statement { rate_based_statement { limit = 100; aggregate_key_type = "IP" } }
    visibility_config { ... }
  }

  rule {
    name     = "BlockQueryKeys"
    priority = 2
    action { block {} }
    statement { byte_match_statement { 
      field_to_match { query_string {} }
      text_transformation { priority = 0; type = "NONE" }
      positional_constraint = "CONTAINS"
      search_string = "api_key=" 
    } }
    visibility_config { ... }
  }
}
```

**SC9-C:**
*   **Defense-in-Depth:** Deploy **AWS API Gateway** for centralized throttling and JWT validation.
*   **Auth:** Transition to **OAuth2/OIDC** with short-lived JWTs.
*   **Audit:** Enable **CloudTrail Data Events** for the ALB/API Gateway.
*   **Encryption:** Use **AWS KMS** for field-level encryption of PII in PostgreSQL.
*   **Migration:** 1. Support both Header and Query keys. 2. Log "Deprecated" warnings in API responses. 3. Set a deadline and disable Query key support.

## SC10 — Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Architecture:** **Active-Active with Cilium Cluster Mesh**. Active-Passive with Velero is too slow for 200TB (RTO would be days, not 1 hour).
*   **RPO/RTO:** 12ms latency allows for **Synchronous Replication** for small metadata, but 200TB MinIO requires **Asynchronous Site Replication**. RPO 15m is achievable via MinIO's bucket replication.
*   **Stateful Strategy:**
    *   **PostgreSQL:** Patroni with synchronous standby in Dallas.
    *   **Redis:** Redis Global Datastore (Active-Passive).
    *   **RabbitMQ:** Federation plugin for cross-site queue mirroring.
    *   **MinIO:** Site-to-Site bucket replication.

**SC10-B:**
```yaml
- name: Configure Patroni
  hosts: db_nodes
  tasks:
    - template:
        src: patroni.yml.j2
        dest: /etc/patroni.yml
      notify: restart patroni
    - name: Ensure etcd is reachable
      uri: url="http://etcd-cluster:2379/health"

  handlers:
    - name: restart patroni
      service: name=patroni state=restarted
```
*(Template `patroni.yml` would include `synchronous_mode: true` and `synchronous_standby_names: '1 (dallas_node1)'`)*.

**SC10-C:**
1.  **Detection:** External health checks (Route53/GSLB) detect Chicago endpoint failure.
2.  **DNS:** GSLB updates CNAME to Dallas VIP.
3.  **Promotion:** Patroni in Dallas detects leader loss $\rightarrow$ promotes standby to Primary.
4.  **Middleware:** Redis Sentinel promotes Dallas slave; RabbitMQ switches to local queues.
5.  **Storage:** MinIO triggers a "failover" to make the Dallas bucket writable.
6.  **Split-Brain:** Use a **Quorum-based Witness** (3rd site or cloud region) to prevent both sites from claiming leadership.
7.  **Failback:** Re-introduce Chicago as a standby $\rightarrow$ sync data $\rightarrow$ perform a planned switchover during a maintenance window.
