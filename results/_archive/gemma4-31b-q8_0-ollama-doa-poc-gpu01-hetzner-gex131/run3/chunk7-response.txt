## Application Architecture

**AA1**
A **monolith** is a single, unified unit where all business logic, data access, and UI are bundled into one codebase and deployment. **Microservices** decompose the application into small, independent services that communicate over a network.
*Problems introduced by microservices:*
1. **Network Latency/Reliability:** Inter-service calls introduce overhead and potential points of failure (partial failure).
2. **Data Consistency:** Maintaining consistency across distributed databases requires complex patterns (e.g., Sagas) instead of simple ACID transactions.
3. **Operational Complexity:** Managing deployment, monitoring, and logging for 50 services is significantly harder than for one.

**AA2**
**Synchronous** communication requires the caller to wait for a response before proceeding (Request-Response). Example: **REST/HTTP**.
**Asynchronous** communication allows the caller to send a message and move on without waiting for an immediate result (Fire-and-Forget/Event-driven). Example: **RabbitMQ**.

**AA3**
A **Reverse Proxy** is a basic gateway that forwards requests to a backend server, providing load balancing and SSL termination (e.g., Nginx). An **API Gateway** is a "smart" reverse proxy that adds application-level logic: authentication, rate limiting, request transformation, and API versioning.
*Can it replace a reverse proxy?* Yes, because an API Gateway is essentially a reverse proxy with additional features. However, for simple static content delivery or basic load balancing, a lightweight reverse proxy is often more performant.

**AA4**
The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. Each local transaction updates the database and publishes an event. If a step fails, the Saga executes "compensating transactions" to undo the previous successful steps.
*   **Choreography:** Services exchange events without a central coordinator. Each service knows what to do when it hears a specific event. *Appropriate for simple workflows with few services.*
*   **Orchestration:** A central "Orchestrator" tells each service when to execute its transaction. *Appropriate for complex business logic with many steps.*

**AA5**
**CQRS** separates the data models for reading (Query) and writing (Command).
It is paired with **Event Sourcing** (storing state as a sequence of events rather than current state) because the event log serves as the "write" side, and the "read" side is a projection of those events into a materialized view.
*Problem solved:* Traditional CRUD struggles with high-read/write contention and lacks a native audit trail. CQRS/Event Sourcing allows independent scaling of reads/writes and provides a perfect historical record of every change.

**AA6**
The **Circuit Breaker** prevents a service from repeatedly trying to call a failing downstream service, avoiding cascading failures.
*States:* **Closed** (requests flow normally), **Open** (requests fail immediately), **Half-Open** (limited requests allowed to test if the service recovered).
*Difference from Retry:* A retry keeps hitting the service (potentially worsening a DDoS-like state); a Circuit Breaker stops the pressure entirely.
*Together:* Use a retry for transient network blips, wrapped inside a circuit breaker to stop retrying if the service is fundamentally down.

**AA7**
1. **Shared DB, Shared Schema:** Lowest cost, highest noisy-neighbor risk, lowest security (logical isolation via `tenant_id`). High operational simplicity.
2. **Shared DB, Separate Schema:** Medium cost, medium risk. Better security (schema-level permissions). Moderate operational complexity (migrations must run across $N$ schemas).
3. **Separate DB:** Highest cost, lowest risk, highest security (physical isolation). High operational complexity (managing $N$ database instances/backups).

**AA8**
**Strong Consistency** ensures all nodes see the same data at the same time. **Eventual Consistency** guarantees that if no new updates are made, all nodes will eventually converge.
*Inventory Architecture:* To prevent overselling, **Strong Consistency** is required.
*Stack:* A relational database (PostgreSQL/MySQL) with **ACID transactions** or a distributed DB with linearizability (e.g., CockroachDB).
*Pattern:* Use **pessimistic locking** (SELECT FOR UPDATE) or a distributed lock (Redis/Redlock) on the SKU ID during the checkout process to ensure atomic decrementing of stock.

**AA9**
A **sidecar proxy** is a helper container deployed alongside every application instance to handle networking logic. In **Istio**, **Envoy** is the sidecar that intercepts all incoming/outgoing traffic.
*   **Data Plane:** The collection of Envoy proxies handling the actual traffic.
*   **Control Plane:** The management layer (Istiod) that pushes configuration to the proxies.
*   **mTLS:** Sidecar mTLS provides transparent, mutual authentication and encryption between services without requiring the application code to manage certificates or TLS handshakes.

**AA10**
The **Strangler Fig pattern** involves incrementally replacing legacy functionality with new services until the old system is entirely gone.
*Strategy:*
1. Place an **API Gateway/Proxy** in front of the .NET Framework monolith.
2. Identify a single bounded context (e.g., "Billing").
3. Implement "Billing" in a .NET 8 microservice.
4. Update the Proxy to route `/billing` requests to the new service, while all other requests still go to the monolith.
5. Repeat for other modules until the monolith is an empty shell.

**AA11**
The **12-Factor App** is a methodology for building scalable, maintainable cloud-native apps.
*Factors:* 1. **Codebase** (one repo, many deploys), 2. **Dependencies** (explicitly declared), 3. **Config** (stored in environment), 4. **Backing services** (treated as attached resources), 5. **Build, release, run** (strictly separated stages), 6. **Processes** (stateless).
*Why:* These ensure the app is portable across environments, can scale horizontally instantly, and is easy to automate via CI/CD.

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Producer $\neq$ Consumer) | Tight (Caller must know Callee) |
| **Scalability** | High (Async, buffering) | Limited by sync chain depth |
| **Debugging** | Hard (Distributed traces needed) | Easier (Direct request/response) |
| **Ordering** | Guaranteed within partition | Sequential per request |
| **Failure** | Retries via DLQ/Offset | Immediate error to user |
*Choice:* Use Request-driven for immediate feedback (e.g., Login). Use Event-driven for background processing or high-throughput data pipelines (e.g., Order Processing).

**AA13**
A **Load Balancer** distributes incoming network traffic across multiple servers.
*   **Layer 4 (Transport):** Routes based on IP and Port (TCP/UDP). Fast, doesn't look at packet content.
*   **Layer 7 (Application):** Routes based on HTTP content (URL, Headers, Cookies).
*   **L7 Use Case:** Path-based routing (e.g., `example.com/api` $\rightarrow$ API Cluster, `example.com/static` $\rightarrow$ S3/CDN).

**AA14**
A **Message Queue** is a component that stores messages until a consumer processes them.
*   **Queue (RabbitMQ):** Messages are deleted once acknowledged. Best for "Task Queues" (work distribution).
*   **Log-based (Kafka):** Messages are appended to a log and persisted. Multiple consumers can read the same data at their own pace. Best for "Event Streaming" and audit logs.

**AA15**
A **Container** shares the host OS kernel and isolates the application process. A **VM** includes a full guest OS and runs on a hypervisor.
*Popularity:* Containers are lightweight, start in seconds, and ensure "it works on my machine" by packaging all dependencies, making them ideal for the rapid deployment cycles of microservices.

**AA16**
**Stateless** services do not store client data between requests (e.g., a Currency Converter API). **Stateful** services remember client state (e.g., a Database or a WebSocket chat server).
*Scaling:* Stateless services are easier to scale because any instance can handle any request; you simply add more replicas behind a load balancer.

**AA17**
An **ORM** maps database tables to objects in a programming language. Examples: **Entity Framework** (C#), **Hibernate** (Java).
*Trade-offs:*
*   **Pros:** Faster development, type safety, database abstraction.
*   **Cons:** "N+1" query problem, overhead/performance hit, loss of control over complex SQL optimizations.

**AA18**
The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function.
*Implementation:*
*   **Thread Pools:** Assign a dedicated thread pool to each downstream service. If Service A hangs, it exhausts its own pool but doesn't starve the threads needed for Service B.
*   **Deployment Groups:** Deploy "Critical" and "Non-Critical" services on separate hardware clusters.

**AA19**
*   **OT (Operational Transformation):** A central server transforms operations to ensure consistency. High complexity, requires a central authority.
*   **CRDTs (Conflict-free Replicated Data Types):** Data structures that merge automatically without conflicts. Lower server complexity, mathematically guaranteed convergence.
*   **Offline Support:** **CRDTs** are superior for offline editing because they allow local mutations that can be merged asynchronously without a central coordinator.

**AA20**
*Challenges:* Maintaining a "Trace ID" across different languages and protocols.
*Context Propagation:* Using headers like **W3C Trace Context** or **B3** to pass the Trace ID from service to service.
*Sampling:* **Head-based** (decide to trace at the start) vs **Tail-based** (decide to keep the trace after it finishes, e.g., only keep traces that resulted in an error).
*Kafka Continuity:* The producer injects the Trace ID into the **Kafka Record Header**. The consumer extracts this header and starts a new span linked to that parent ID.

## On-Premise Infrastructure Architecture

**OP1**
*   **Type 1 (Bare-metal):** Runs directly on hardware. Examples: **VMware ESXi, Microsoft Hyper-V**.
*   **Type 2 (Hosted):** Runs as an app on a host OS. Examples: **Oracle VirtualBox, VMware Workstation**.

**OP2**
*   **SAN (Storage Area Network):** Block-level storage. Appears as a local disk to the server. Protocols: **iSCSI, Fibre Channel**. Use for: Databases, VM disks.
*   **NAS (Network Attached Storage):** File-level storage. Appears as a network share. Protocols: **NFS, SMB/CIFS**. Use for: Shared folders, backups.

**OP3**
**3-Tier:** Core (routing), Distribution (policy/VLANs), Access (connecting endpoints).
**Leaf-Spine:** Every Leaf switch connects to every Spine switch.
*Problem solved:* 3-Tier is optimized for North-South traffic (client-to-server). Modern data centers have massive East-West traffic (server-to-server). Leaf-Spine provides predictable latency and linear bandwidth scaling.

**OP4**
*   **Architecture:** 3+ nodes to maintain **quorum** (majority vote).
*   **Fencing:** Use **STONITH** (Shoot The Other Node In The Head) via IPMI/iDRAC to ensure a failed node is powered off before its VMs are restarted elsewhere.
*   **Storage:** **Ceph** (distributed) is preferred for no single point of failure.
*   **Failure:** Node fails $\rightarrow$ Cluster detects loss of heartbeat $\rightarrow$ Quorum is checked $\rightarrow$ Fencing kills the dead node $\rightarrow$ VMs are restarted on remaining nodes.

**OP5**
**VLAN Trunking** allows a single physical link to carry traffic for multiple VLANs. **802.1Q** is the standard that adds a "tag" to the Ethernet frame to identify the VLAN ID.
*Linux Config:* Create tagged sub-interfaces:
`ip link add link eth0 name eth0.10 type vlan id 10`
`ip addr add 192.168.10.5/24 dev eth0.10` (Repeat for VLAN 20, 30).

**OP6**
*   **RAID 1:** Mirroring (High redundancy, 50% capacity).
*   **RAID 5:** Parity (1 disk fail, good read, slow write).
*   **RAID 6:** Dual Parity (2 disk fail).
*   **RAID 10:** Mirror of stripes (High perf, high redundancy, 50% capacity).
*   **RAID Z2:** ZFS version of RAID 6 (prevents write hole).
*   **Choice for DB (6 drives):** **RAID 10**. Databases require high IOPS (random writes); RAID 10 provides the best performance and safety without the parity calculation overhead.

**OP7**
*   **Internal:** AD-integrated DNS for internal name resolution.
*   **DMZ:** Separate authoritative servers for public records.
*   **Split-Horizon:** The DNS server returns different IPs for `app.company.com` depending on if the request is internal (private IP) or external (public IP).
*   **DNSSEC:** Digitally signs the external zone to prevent DNS spoofing/cache poisoning.
*   **VPN:** Laptop's DNS settings are pushed via VPN profile to use the internal recursive resolvers.

**OP8**
**Chain:** Root CA $\rightarrow$ Intermediate/Issuing CA $\rightarrow$ End-Entity Cert.
*   **Root CA:** Kept **offline** in a vault; only used to sign Intermediate CAs.
*   **Issuing CA:** Online; handles daily certificate requests.
*   **CRL vs OCSP:** CRL is a downloaded list of revoked certs; OCSP is a real-time API check.
*   **Compromise:** A compromised Sub-CA requires revoking that Sub-CA's cert. A compromised Root CA requires rebuilding the entire PKI and redistributing the Root cert to every device.

**OP9**
*   **MPLS:** High cost, guaranteed QoS, private.
*   **IPsec VPN:** Low cost, public internet, variable latency.
*   **SD-WAN:** Medium cost, software-defined, can bond MPLS and Internet.
*   **WireGuard Mesh:** Low cost, high performance, complex to manage at scale.
*   **Recommendation:** **SD-WAN**. It allows prioritizing VoIP traffic (QoS) over the best available path (MPL/Internet) and simplifies management for 5 sites.

**OP10**
**iDRAC/iLO/IPMI** are Baseboard Management Controllers (BMCs) that provide "Out-of-Band" management.
*Criticality:* Allows powering on/off, BIOS access, and OS installation remotely even if the OS is crashed.
*Internet Exposure:* Catastrophic. Attackers can gain full console access, reinstall the OS, or brick the hardware.

**OP11**
*   **LVM:** Logical Volume Manager. Allows resizing partitions. Snapshots are "Copy-on-Write" (performance drops as snapshot ages).
*   **LVM-Thin:** Over-provisions space. Snapshots are more efficient (pointers).
*   **ZFS:** Combined FS and Volume Manager. Uses "Redirect-on-Write" for near-instant, zero-cost snapshots.
*   **Use Case:** LVM for basic Linux flexibility; ZFS for data integrity (checksums) and massive snapshotting.

**OP12**
*   **Design:** 3 sites (Site A, Site B, and a Witness/Tiebreaker site).
*   **Ceph CRUSH:** Set `failure_domain` to `site`.
*   **Monitors:** Place one Monitor per site.
*   **Latency:** Requires very low RTT (typically <10ms) to avoid OSD timeouts.
*   **2-Site Problem:** Without a tiebreaker, a network partition causes "split-brain," where both sites think they are the master, leading to catastrophic data corruption.

**OP13**
**DHCP (DORA):** **D**iscover (Client $\rightarrow$ All), **O**ffer (Server $\rightarrow$ Client), **R**equest (Client $\rightarrow$ Server), **A**cknowledge (Server $\rightarrow$ Client).
*Failure:* When the lease expires and no server is found, Windows assigns an **APIPA** address (`169.254.x.x`).

**OP14**
**Unmanaged:** Plug-and-play, no configuration.
**Managed:** Supports **VLANs** (segmentation), **STP** (Spanning Tree Protocol to prevent loops), **SNMP** (monitoring), and **Port Mirroring** (for IDS/Packet capture). Essential for security and stability in enterprises.

**OP15**
**NTP (Network Time Protocol)** synchronizes clocks across the network.
*Criticality:* Kerberos authentication fails if clocks drift >5 mins. Log correlation across servers is impossible without sync.
*Drift:* Can cause database replication errors, incorrect file timestamps, and authentication failures.

**OP16**
*   **Physical:** Hardware.
*   **VM:** Hardware abstraction (Hypervisor).
*   **Container:** OS abstraction (Kernel sharing).
*   **Bare Metal Use Case:** High-performance databases (avoiding hypervisor overhead), GPU-intensive AI workloads, or the Hypervisor itself.

**OP17**
*   **UPS:** Battery backup. Provides **instant** power for seconds/minutes to prevent crashes.
*   **Generator:** Fuel-based. Provides power for **hours/days**.
*   **ATS (Automatic Transfer Switch):** Detects power loss and automatically switches the load from the utility grid to the generator.
*   **Why both?** The UPS bridges the gap between the power outage and the time it takes for the generator to start and stabilize.

**OP18**
*   **Active-Passive:** One server works, one waits.
*   **Active-Active:** Both servers handle traffic.
*   **Postgres HA:** Use **Pacemaker/Corosync** to manage a **Virtual IP (VIP)**. If the primary fails, Pacemaker uses **STONITH** to kill the primary, promotes the standby, and moves the VIP to the new primary.

**OP19**
*   **3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
*   **RPO/RTO:** RPO (Recovery Point Objective - max data loss), RTO (Recovery Time Objective - max downtime).
*   **Types:** Full (everything), Incremental (since last backup), Differential (since last full).
*   **Immutable Backups:** Use S3 Object Lock or WORM tapes to prevent ransomware from deleting backups.
*   **Backup vs DR:** Backup is about **data recovery** (getting files back). DR is about **business continuity** (getting the whole site running again).

**OP20**
**802.1X Process:**
1. **Supplicant** (Client) requests access.
2. **Authenticator** (Switch) blocks all traffic except EAP.
3. **Auth Server** (RADIUS) validates credentials.
*   **EAP-TLS:** Uses certificates (most secure).
*   **PEAP:** Uses username/password.
*   **Failure:** Device is moved to a "Guest VLAN" or port is disabled.
*   **MAB (MAC Authentication Bypass):** For printers/IoT that can't run 802.1X; the switch sends the device's MAC address to the RADIUS server to check against a whitelist.
