## Cloud Infrastructure Architecture

**CL1 — Easy: IaaS, PaaS, and SaaS**
*   **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and everything above it. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing the underlying OS or runtime. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Fully managed software delivered via a browser/API. You only manage configuration and data. *Example: Microsoft 365.*

**CL2 — Easy: Shared Responsibility Model**
The provider manages the "Security **of** the Cloud" (physical hardware, virtualization layer), and the customer manages "Security **in** the Cloud" (data, config).
*   **IaaS VMs:** Provider: Physical host/hypervisor. Customer: Guest OS, patching, firewall, apps.
*   **Managed Kubernetes (EKS/GKE):** Provider: Control plane (API server, etcd). Customer: Worker node OS (usually), pod security, network policies, apps.
*   **SaaS (M365):** Provider: Application code, infrastructure, OS. Customer: Identity/Access management, data governance.

**CL3 — Medium: VPC, Subnet, Security Group, and NACL**
*   **VPC:** An isolated virtual network in the cloud.
*   **Subnet:** A range of IP addresses in the VPC, usually tied to a specific Availability Zone.
*   **Security Group (SG):** A virtual firewall for **instances** (NIC level). It is **stateful** (if you allow inbound, outbound is automatically allowed).
*   **NACL:** A firewall for **subnets**. It is **stateless** (you must explicitly define both inbound and outbound rules).
*   **Layering:** VPC $\rightarrow$ Subnet (NACL) $\rightarrow$ Instance (SG).

**CL4 — Medium: Multi-Account Strategy**
*   **Landing Zone:** A pre-configured, secure multi-account environment (baseline).
*   **Organizational Units (OUs):** Logical groupings of accounts (e.g., Prod, Dev, Security) to apply policies.
*   **Guardrails:** Service Control Policies (SCPs) that set the maximum available permissions across accounts.
*   **Shared Networking:** Using a Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize egress/ingress and connect VPCs.
*   **Centralized Logging:** Aggregating logs (CloudTrail/Log Analytics) into a dedicated security account.
*   **Why not single-account?** Blast radius (one compromise affects all), API rate limits (throttling), and billing complexity.

**CL5 — Medium: Infrastructure as Code (IaC)**
IaC is the management of infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu:** HCL-based, cloud-agnostic, state-managed. *Use for multi-cloud or complex provider ecosystems.*
*   **Pulumi:** Uses general-purpose languages (TS, Python, Go). *Use when complex logic/loops are needed.*
*   **CloudFormation/Bicep:** Cloud-native (AWS/Azure). *Use for deep integration and "day zero" support of new services.*
*   **Crossplane:** K8s-native (CRDs). *Use to manage cloud resources via the K8s API (Control Plane approach).*

**CL6 — Medium: Cloud-Native Autoscaling**
*   **HPA (Horizontal Pod Autoscaler):** Adds/removes pods based on CPU/RAM.
*   **VPA (Vertical Pod Autoscaler):** Adjusts CPU/RAM requests/limits of existing pods.
*   **Cluster Autoscaler:** Adds/removes physical nodes to the cluster when pods cannot be scheduled.
*   **KEDA (Kubernetes Event-driven Autoscaling):** Scales pods based on external events (e.g., Kafka lag, RabbitMQ queue depth).
*   **KEDA vs HPA:** Use KEDA when scaling is driven by external metrics rather than internal resource consumption.

**CL7 — Hard: Disaster Recovery (DR) Strategy**
*   **RPO (Recovery Point Objective):** Max acceptable data loss. **RTO (Recovery Time Objective):** Max acceptable downtime.
*   **Active-Active:** Traffic split across regions. RTO $\approx$ 0. High cost.
*   **Active-Passive:** Primary region handles traffic; secondary is standby.
*   **Replication:** Sync (Zero data loss, high latency) vs Async (Potential data loss, low latency).
*   **DNS Failover:** Route53/Traffic Manager uses health checks to route traffic to the healthy region.
*   **DR Types:**
    *   **Pilot Light:** DB is synced; apps are off/minimal.
    *   **Warm Standby:** Scaled-down version of the app is always running.
    *   **Multi-site Active-Active:** Full capacity in both regions.

**CL8 — Hard: GitOps Model**
GitOps uses Git as the single source of truth for infrastructure and app state. A controller (ArgoCD/Flux) continuously reconciles the live state with the Git state.
*   **ArgoCD vs FluxCD:** ArgoCD provides a rich UI and multi-cluster management; Flux is more lightweight and "invisible" (CLI/Git-centric).
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift:** If a manual change occurs, the controller detects the difference and automatically overwrites the manual change to match Git.

**CL9 — Hard: Stateful Legacy App on K8s**
*   **StatefulSet:** Ensures stable network IDs (pod-0, pod-1) and ordered deployment/scaling.
*   **PV/PVC with Local Storage Class:** Maps pods to specific local NVMe/SSD disks for low latency.
*   **Headless Service:** Provides DNS records for individual pods rather than a single load-balanced IP.
*   **Init Containers:** Used to prepare the filesystem or wait for DB availability before the main app starts.
*   **ConfigMaps as Volume Mounts:** Mounts config files into specific paths (e.g., `/etc/app/config.yaml`).
*   **Pod Disruption Budgets (PDB):** Ensures a minimum number of replicas remain available during maintenance.

**CL10 — Medium: Identity and Workload Identity**
*   **Service Account:** An identity for a process running in a pod.
*   **Workload Identity / IRSA:** Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Why not mount credentials?** Static keys (JSON/CSV) are long-lived, easily leaked, and hard to rotate.
*   **Federation:** The cloud provider trusts the K8s cluster's OIDC provider, issuing short-lived, temporary tokens to the pod.

**CL11 — Medium: Cloud Storage Types**
*   **Object (S3/Blob):** Unstructured data, accessed via API. *Use for backups, images, logs.* (Highest durability: 11 9s).
*   **Block (EBS/Managed Disk):** Raw volumes attached to a VM. *Use for OS disks, databases.* (High performance, zonal availability).
*   **File (EFS/Azure Files):** Shared network filesystem (NFS/SMB). *Use for shared config, CMS uploads.* (Regional availability).

**CL12 — Hard: Zero-Trust K8s Architecture**
*   **Network Policies:** L3/L4 isolation (deny-all by default).
*   **Service Mesh (Istio/Linkerd):** mTLS for encrypted, authenticated L7 communication.
*   **Pod Identity:** IRSA/Workload Identity for least-privilege cloud access.
*   **Admission Controllers:** OPA/Kyverno to enforce policies (e.g., "no root containers").
*   **Image Signing:** Cosign/Notary to ensure only verified images are deployed.
*   **Runtime Security:** Falco to detect anomalous syscalls (e.g., shell in pod).
*   **Secrets:** Vault for dynamic secret injection.
*   **Difference:** Traditional security relies on a "hard shell" (perimeter); Zero Trust assumes the network is already compromised and verifies every request.

**CL13 — Easy: CDN (Content Delivery Network)**
A CDN is a distributed network of proxy servers (Edge locations) that cache content closer to the user.
*   **Services:** AWS CloudFront, Akamai, Cloudflare.
*   **CDN vs Origin:** Use a CDN to reduce latency, lower origin server load, and protect against DDoS. Serve from origin only for highly dynamic, user-specific data.

**CL14 — Easy: AZs and Regions**
*   **Region:** A geographic area (e.g., us-east-1).
*   **Availability Zone (AZ):** One or more discrete data centers within a region with redundant power/networking.
*   **Why Multi-AZ?** To protect against a single data center failure (High Availability).
*   **Zonal vs Regional:** Zonal resources (e.g., EBS volume) exist in one AZ; Regional resources (e.g., S3, Lambda) are replicated across AZs.

**CL15 — Easy: Managed Database Services**
Managed DBs (RDS, Cloud SQL) abstract the underlying server.
*   **Provider handles:** OS patching, hardware failure, automated backups, point-in-time recovery, and high-availability failover.
*   **User handles:** Database schema, query optimization, user permissions, and application-level logic.

**CL16 — Easy: Cloud Identity (IAM)**
*   **Users:** Permanent identities for people.
*   **Groups:** Collections of users for easier permission management.
*   **Roles:** Temporary identities assumed by users or services.
*   **Policies:** JSON documents defining "Who can do what on which resource."
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply by using specific resource ARNs instead of `*` (wildcards).

**CL17 — Easy: Serverless Computing**
Serverless is an execution model where the provider manages the server allocation and scaling.
*   **Comparison:** Lambda (AWS), Azure Functions, Google Cloud Functions are all event-driven FaaS.
*   **Cold Starts:** The latency incurred when a function is triggered after being idle (provider must spin up a container).
*   **Poor Fit:** Long-running processes (timeouts), apps requiring constant low-latency response, or predictable, high-volume workloads (where VMs are cheaper).

**CL18 — Medium: Kubernetes Ingress Options**
*   **Ingress Resource:** Basic L7 rules (host/path) implemented by a controller (e.g., Nginx).
*   **Gateway API:** The modern successor; provides role-based configuration (Gateway, HTTPRoute) for better scalability.
*   **Cloud LB Annotations:** Directs the Ingress controller to configure a cloud-specific LB (e.g., AWS ALB).
*   **Service Mesh Gateway:** Handles ingress with advanced mTLS and traffic splitting (e.g., Istio Gateway).
*   **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Sidecar (End-to-End mTLS).
*   **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenancy, and advanced traffic management.

**CL19 — Hard: Cost Optimization Strategy**
*   **Compute:** Use **Savings Plans/RIs** for baseline load; **Spot Instances** for stateless/batch jobs.
*   **Right-sizing:** Use metrics (CloudWatch/Azure Monitor) to downsize over-provisioned VMs/Pods.
*   **Storage:** Move old data to **S3 Intelligent-Tiering** or **Glacier/Archive**.
*   **Idle Resources:** Implement automated scripts to delete unattached EBS volumes or stop Dev environments on weekends.
*   **FinOps:** Establish a culture of cost-awareness. Use **Showback** (reporting costs to teams) and **Chargeback** (billing teams' budgets).
*   **Tools:** AWS Cost Explorer, Kubecost (for K8s), CloudHealth.

**CL20 — Hard: Multi-Cloud Strategy**
*   **Abstraction:** Use Kubernetes as the common runtime to avoid proprietary compute services.
*   **IaC:** Use Terraform/OpenTofu for a unified workflow across providers.
*   **Networking:** Site-to-Site VPN or dedicated interconnects (DirectConnect/ExpressRoute) for cross-cloud traffic.
*   **Identity:** Use an external IdP (Okta, Azure AD) via SAML/OIDC for federation.
*   **Trade-offs:** Theoretical benefit is resilience and no lock-in; real-world cost is massive operational complexity and "lowest common denominator" feature sets.
*   **Justification:** Justified for strict regulatory requirements (sovereignty) or extreme availability needs. Unnecessary for most companies where a multi-region single-cloud approach suffices.

## OT Infrastructure Architecture

**OT1 — Easy: Purdue Model (ISA-95)**
A structural model for ICS network segmentation.
*   **Level 0 (Process):** The physical equipment (sensors, actuators, motors).
*   **Level 1 (Basic Control):** PLCs, PID controllers.
*   **Level 2 (Area Supervisory):** HMIs, SCADA workstations.
*   **Level 3 (Site Operations):** Historians, site-wide control, patch management.
*   **Level 4 (Enterprise):** Corporate network, ERP, Email.

**OT2 — Easy: IT vs OT Networks**
*   **IT (Information Technology):** Focuses on **Confidentiality** (CIA triad). Fast update cycles.
*   **OT (Operational Technology):** Focuses on **Availability and Safety** (AIC triad). Slow update cycles.
*   **Patching:** Standard IT patching (rebooting) can cause physical danger or production loss. OT systems often require vendor certification for patches to maintain warranties/safety.

**OT3 — Medium: Industrial DMZ (IDMZ)**
The IDMZ is a buffer zone between Level 4 (IT) and Level 3 (OT).
*   **Traffic:** Only brokered traffic (via proxies/jump hosts). No direct L4 $\rightarrow$ L1/L2 communication.
*   **Direction:** Data should be pushed from OT to IT (e.g., Historian replication).
*   **Danger:** Direct L4 $\rightarrow$ L1 access allows a compromised corporate laptop to send a "Stop" command directly to a PLC, potentially causing physical damage.

**OT4 — Medium: OT Protocols**
1.  **Modbus TCP:** L1/L2. Simple, widely used, no security.
2.  **OPC UA:** L2/L3. Modern, secure, platform-independent data exchange.
3.  **EtherNet/IP (CIP):** L1/L2. Common in Rockwell/Allen-Bradley environments.
4.  **PROFINET:** L1/L2. High-speed, deterministic (Siemens).
5.  **MQTT:** L3/Cloud. Lightweight pub/sub for IIoT/Cloud ingestion.

**OT5 — Medium: Data Diode vs Firewall**
*   **Firewall:** Software/Hardware that filters traffic based on rules. Bi-directional.
*   **Data Diode:** Hardware that physically allows light/electrons to flow in **one direction only**.
*   **Use Case:** High-security environments (Nuclear, Power Grid) to send logs/data to IT without any possibility of an inbound attack.
*   **Limitation:** No TCP handshakes or ACKs; requires specialized proxy software to handle data integrity.

**OT6 — Medium: Cloud Data Flow Design**
*   **Flow:** PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Plant Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker (Cloud) $\rightarrow$ Analytics.
*   **Security Boundaries:**
    1.  L2/L3 Firewall (Restrict to OPC UA traffic).
    2.  IDMZ (Edge Gateway acts as the only bridge).
    3.  Cloud Firewall (Restrict MQTT ingress to the Edge Gateway's static IP).

**OT7 — Hard: IEC 62443 Zones and Conduits**
*   **Zone:** A grouping of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Design:**
    *   **Enterprise Zone (L4):** Corporate users.
    *   **IDMZ Zone:** Jump hosts, Proxy servers.
    *   **Control Zone (L2/L3):** SCADA servers, HMIs.
    *   **Field Zone (L1):** PLCs.
    *   **Safety Zone (SIS):** Isolated zone for Safety Instrumented Systems.
    *   **Conduits:** L4 $\rightarrow$ IDMZ (HTTPS/SSH), IDMZ $\rightarrow$ Control (OPC UA), Control $\rightarrow$ Field (Modbus/Profinet).

**OT8 — Hard: Network Segmentation Strategy**
*   **VLAN Design:** Create separate VLANs for each production line (Line 1, Line 2, etc.) and a separate VLAN for Management/HMIs.
*   **Firewall Placement:** Place an Industrial Firewall between the L3 site network and the L2 production VLANs.
*   **Remote Access:** Implement a Jump Host in the IDMZ with MFA and session recording.
*   **Transition:**
    1.  **Passive Phase:** Mirror traffic to a monitoring tool to map all flows.
    2.  **Permissive Phase:** Implement VLANs but use "Allow All" rules with logging.
    3.  **Enforcement Phase:** Gradually tighten rules based on observed traffic during scheduled maintenance windows.

**OT9 — Hard: SIS vs BPCS**
*   **BPCS (Basic Process Control System):** Manages day-to-day operations (e.g., keeping a tank at 50%).
*   **SIS (Safety Instrumented System):** A separate system that triggers a "Safe State" (e.g., emergency shutdown) if the BPCS fails.
*   **IEC 61511:** The international standard for functional safety in the process industry.
*   **Isolation:** SIS must be isolated to prevent "common-cause failure" (e.g., a bug in the BPCS crashing the SIS).
*   **Ransomware:** If SIS is hit, the plant cannot be safely shut down or restarted, leading to potential catastrophic physical failure (explosion/leak).

**OT10 — Medium: PLC, DCS, and SCADA**
*   **PLC (Programmable Logic Controller):** Fast, discrete control for specific machines.
*   **DCS (Distributed Control System):** Integrated system for complex, continuous processes (e.g., oil refinery).
*   **SCADA (Supervisory Control and Data Acquisition):** High-level monitoring of geographically dispersed assets.
*   **Coexistence:** Yes. A SCADA system often gathers data from multiple PLCs and a DCS.

**OT11 — Medium: Remote Access Architecture**
*   **Architecture:** User $\rightarrow$ VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (IDMZ) $\rightarrow$ Target HMI/PLC.
*   **Controls:** Session recording (video/logs), time-limited access (Just-in-Time), and approval workflows.
*   **Why no direct RDP?** Direct RDP allows lateral movement, lacks granular auditing, and exposes the HMI (often running an old OS) to corporate malware.

**OT12 — Hard: Water Facility Incident Response**
*   **Detection:** Use passive IDS (e.g., Nozomi, Claroty) to detect anomalous Modbus/S7 traffic or unauthorized PLC writes.
*   **Response:**
    1.  **Isolate:** Sever the connection between the IDMZ and L3.
    2.  **Manual Mode:** Instruct plant operators to switch to manual override/hand-control for critical valves/pumps.
    3.  **Inventory:** Verify asset integrity against the known-good baseline.
*   **Operator Role:** The operator is the "final authority." They ensure the physical process remains stable while the security team isolates the network.

**OT13 — Easy: HMI vs Engineering Workstation (EWS)**
*   **HMI:** A dashboard for operators to monitor and control the process (e.g., "Start Pump").
*   **EWS:** A specialized computer used by engineers to program the PLC, change logic, and configure the system. EWS has much higher privileges and is a primary target for attackers.

**OT14 — Easy: Historian**
A time-series database that logs process data over time.
*   **Plant Historian (L3):** High-resolution data (millisecond level), used for local troubleshooting and optimization.
*   **Enterprise Historian (L4):** Aggregated, lower-resolution data used for business reporting and KPIs.

**OT15 — Easy: Ladder Logic**
A graphical programming language used by PLCs that resembles electrical relay diagrams.
*   **Why dominant?** It was designed to be understood by electricians and plant technicians, not just software engineers, allowing for fast on-site troubleshooting.

**OT16 — Easy: RTU vs PLC**
*   **RTU (Remote Terminal Unit):** Designed for wide-area telemetry, low power, and rugged environments (e.g., a remote pipeline valve). Often uses cellular/radio.
*   **PLC:** Designed for high-speed, local control on a factory floor with high I/O density.

**OT17 — Easy: Analog vs Digital Signals**
*   **Digital:** Binary (On/Off, 0 or 1).
*   **Analog:** Continuous range (e.g., 4-20mA).
*   **Why 4-20mA?** It provides a "Live Zero." If the signal drops to 0mA, the system knows there is a **wire break** (fault), whereas 0-20mA cannot distinguish between a "zero" reading and a broken wire.

**OT18 — Medium: OT Asset Inventory**
You cannot protect what you cannot see. Inventory includes firmware versions, IP addresses, and rack slots.
*   **Passive Monitoring:** Sniffing network traffic (Safe, no impact).
*   **Active Scanning:** Sending queries to devices (Risky).
*   **Danger:** Active scanning (like Nmap) can crash legacy PLCs that cannot handle unexpected packets or high traffic volumes.

**OT19 — Hard: MITRE ATT&CK for ICS**
A framework mapping adversary tactics specifically for industrial environments.
*   **Tactics/Techniques:**
    1.  **Initial Access:** Valid Accounts (using stolen vendor credentials).
    2.  **Execution:** Scripting (running Python on an HMI).
    3.  **Persistence:** Project File Modification (altering PLC logic).
    4.  **Inhibition of Response:** Alarm Suppression (stopping the operator from seeing an error).
    5.  **Impair Process Control:** Unauthorized Command Message (sending a "Stop" command).
*   **Difference:** Focuses on physical impact (e.g., "Loss of Control") rather than just data theft.

**OT20 — Hard: Converged IT/OT SOC**
*   **Log Collection:** Use passive TAPs/SPAN ports to send traffic to an IDS; use Syslog for HMIs/Servers.
*   **SIEM Integration:** Feed OT-IDS alerts into a central SIEM (e.g., Sentinel/Splunk) but keep OT-specific dashboards.
*   **Staffing:** Pair an IT Security Analyst (threat hunting) with an OT Engineer (process context).
*   **False Positives:** Common during maintenance. Use "Maintenance Mode" flags to suppress alerts.
*   **Firmware Alert:**
    1.  **Verify:** Check the change management ticket.
    2.  **Validate:** Ask the plant operator if they performed an update.
    3.  **Respond:** If unauthorized, isolate the PLC, capture a forensic image of the logic, and restore from a known-good backup.
