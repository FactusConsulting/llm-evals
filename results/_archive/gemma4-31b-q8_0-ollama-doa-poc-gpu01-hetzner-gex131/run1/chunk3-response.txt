## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry run; it compares the current state with the configuration and shows what changes will be made without actually executing them. `tofu apply` executes the proposed changes to reach the desired state.

**T2 — Easy:** State is a JSON file that maps your configuration to real-world resources. Remote state stores this file in a shared location (e.g., S3, Terraform Cloud), enabling team collaboration, state locking (preventing concurrent changes), and improved security.

**T3 — Medium:** `count` creates resources based on an integer index (list-like). `for_each` creates resources based on a map or set of strings. `for_each` is preferred when managing sets of resources because removing an item from the middle of a `count` list causes all subsequent resources to be shifted/recreated; `for_each` identifies resources by a unique key, avoiding this.

**T4 — Medium:** This is called "drift." OpenTofu detects this during the next `plan` or `apply` by refreshing the state (querying the cloud API). It will show that the actual state differs from the configuration and will propose changes to revert the manual modification to match the code.

**T5 — Medium:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6 — Hard:** `terraform_remote_state` reads the entire state file of another project, which creates tight coupling and exposes all outputs. Output values are specific values exported by a module. The recommended alternative is using **Data Sources** (e.g., `aws_vpc`) to look up resources by tags or names, which decouples the projects.

**T7 — Hard:** Provisioners (like `remote-exec`) run *after* the resource is created but *before* the resource is considered "complete" in the state. If an output depends on a value generated by a provisioner, that value isn't available until the provisioner finishes. **Fix:** Use a separate `null_resource` with `depends_on` the VM, or better, use a cloud-init script and a data source to fetch the resulting config from the VM's metadata/disk.

**T8 — Medium:** `tofu import` brings existing infrastructure into the state file. Limitation: It only updates the state; you must manually write the HCL code to match. The `import` block (1.5+) allows you to define the import declaratively in code and can automatically generate the corresponding HCL configuration.

**T9 — Easy:** A **variable** (input) is a parameter passed into the module to make it reusable. An **output** is a return value exported by the module for use by other modules or the CLI.

**T10 — Easy:** A provider is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS, Azure). If you run `plan` without `init`, it will fail because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11 — Easy:** The `.terraform.lock.hcl` file records the exact versions and hashes of providers used. It should be committed to ensure every team member and CI/CD pipeline uses the exact same provider version, preventing "it works on my machine" bugs.

**T12 — Easy:** `tofu destroy` removes all resources managed by the current state. To target a single resource: `tofu destroy -target=aws_instance.web["web1"]`.

**T13 — Easy:** A data source allows you to fetch information from an external source (API, existing infra) without managing it. Example: Using `aws_ami` to find the latest official Ubuntu AMI ID instead of hardcoding it.

**T14 — Medium:** Variables are inputs provided at runtime. Locals are internal constants or computed values. Use locals to avoid repeating complex expressions or to organize constants that shouldn't be changed by the user.

**T15 — Medium:** The `lifecycle` block modifies resource behavior:
- `create_before_destroy`: Creates the new resource before deleting the old one (prevents downtime for DNS/Load Balancers).
- `prevent_destroy`: Errors out if a destroy action is attempted (protects production databases).
- `ignore_changes`: Ignores updates to specific attributes (e.g., ignore tags added by an external security scanner).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource has been renamed or moved into a module. It updates the state file to reflect the new address without destroying and recreating the physical resource.

**T17 — Hard:** OpenTofu builds a Directed Acyclic Graph (DAG) to determine the order of operations. **Implicit dependencies** are created when one resource references another's attribute. **Explicit dependencies** are created via `depends_on`. `depends_on` forces a strict order, reducing parallelism and potentially slowing down the apply process; it should be used only when dependencies aren't visible via attributes.

**T18 — Hard:** 
1. **State Splitting:** Break one large state into smaller, decoupled workspaces (reduces the number of resources to refresh).
2. **Targeting:** Use `-target` for specific changes (Tradeoff: risks state inconsistency).
3. **Refresh=false:** Run `tofu plan -refresh=false` (Tradeoff: ignores drift).
4. **Parallelism:** Adjust `-parallelism=N` to optimize API call concurrency (Tradeoff: may hit cloud API rate limits).

**T19 — Hard:** State locking prevents two users from modifying the state simultaneously. If a lock is stuck (e.g., CI crash), you use `tofu force-unlock <LOCK_ID>`. The risk is that if another process *is* actually running, forcing the unlock can lead to state corruption.

**T20 — Hard:** 
1. Add the `backend "s3" { ... }` block to the configuration.
2. Run `tofu init`.
3. OpenTofu will detect the local state and ask if you want to migrate it to S3.
4. Type `yes`.
5. Verify by checking the S3 bucket for the `.tfstate` file and the DynamoDB table for the lock record. Run `tofu state list` to ensure resources are still tracked.

## Ansible

**A1 — Easy:** A **task** is a single unit of work (e.g., install a package). A **playbook** is a YAML file containing one or more "plays" that map tasks to specific hosts. A **role** is a structured directory that bundles tasks, variables, files, and templates for reuse.

**A2 — Easy:** `ansible_facts` is a dictionary containing system information gathered during the "setup" phase. Access the OS family via `{{ ansible_os_family }}`.

**A3 — Medium:** 
- `command`: Safest; executes a binary directly. No shell environment (no pipes, no redirects).
- `shell`: Runs through `/bin/sh`. Supports pipes, redirects, and environment variables.
- `raw`: Bypasses Python on the target; sends a raw SSH command. Used for bootstrapping Python on a new node.

**A4 — Medium:** Idempotency means running the same operation multiple times results in the same state without making unnecessary changes. 
- **Idempotent:** `apt: name=nginx state=present` (only installs if not present).
- **Non-idempotent:** `shell: echo "Hello" >> /tmp/test.txt` (appends text every time it runs).

**A5 — Medium:**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
  when: ansible_os_family == 'Debian' or ansible_os_family == 'RedHat'

- name: Install EPEL for RedHat
  package:
    name: epel-release
    state: present
  when: ansible_os_family == 'RedHat'
```
*(Note: Using the generic `package` module handles the package manager difference).*

**A6 — Hard:** (Lowest to Highest) Role defaults $\rightarrow$ Inventory group_vars $\rightarrow$ Inventory host_vars $\rightarrow$ Playbook group_vars $\rightarrow$ Playbook host_vars $\rightarrow$ Playbook `vars` $\rightarrow$ Role vars $\rightarrow$ `set_fact` $\rightarrow$ Extra vars (`-e`).

**A7 — Hard:** 
1. Use two separate plays in the playbook.
2. Play 1: `hosts: first_three`, `serial: 1`.
3. Play 2: `hosts: remaining_nodes`.
4. In Play 2, use the `wait_for` module to ensure the RKE2 API port (6443) is open on the first 3 nodes before proceeding.

**A8 — Medium:** `ansible-vault` encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'my_password' --name 'db_password'`. This allows the rest of the vars file to remain plain text.

**A9 — Easy:** An inventory is a list of managed nodes. **Static inventory** is a fixed file (INI/YAML). **Dynamic inventory** is a script or plugin that queries an API (e.g., AWS EC2) to generate the host list in real-time.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A handler is a special task that only runs if "notified" by another task (via the `notify` keyword) and only if that task actually changed something. They typically run once at the end of the play (e.g., restarting a service after a config change).

**A12 — Easy:** `ansible.cfg` is the configuration file for Ansible's behavior. Common settings: `remote_user`, `inventory` (path to file), and `forks` (number of parallel processes).

**A13 — Easy:** `register` captures the output of a task into a variable. 
Example:
```yaml
- shell: uptime
  register: uptime_result
- debug: msg="{{ uptime_result.stdout }}"
```

**A14 — Medium:** `import_tasks` is **static** (processed when the playbook is parsed). `include_tasks` is **dynamic** (processed at runtime). Use `include_tasks` if the decision to include the file depends on a variable set by a previous task in the same play.

**A15 — Medium:** Ansible Galaxy is a public hub for sharing roles and collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:** Connection plugins define how Ansible communicates with hosts.
- `ssh`: Standard for Linux/Unix.
- `local`: Runs tasks on the control node itself.
- `network_cli`: Used for network devices (switches/routers) to maintain a persistent SSH session.

**A17 — Hard:** `delegate_to` runs a task on a host other than the current one in the loop. `run_once` ensures the task executes only once for the entire batch. 
**Example:** To update a DNS record on a local API server using the IP of a remote host:
```yaml
- name: Update DNS
  uri: url="http://dns-api/update"
  delegate_to: localhost
  run_once: true
  # Use hostvars to get the IP of the first host in the group
```

**A18 — Hard:** 
1. **Forks:** Increase `forks` in `ansible.cfg` to run tasks on more hosts in parallel.
2. **Pipelining:** Enable `pipelining = True` to reduce the number of SSH connections required.
3. **Fact Caching:** Use a Redis or JSON file cache for facts so they aren't gathered every run.
4. **Mitogen:** Use the Mitogen strategy plugin to replace the Ansible execution engine for significantly faster SSH communication.

**A19 — Hard:** 
- `{{ }}`: Variable interpolation/expressions.
- `{% %}`: Control structures (loops, conditionals).
- `{# #}`: Comments.
**Snippet:**
```jinja2
upstream backend_servers {
{% for server in backend_servers %}
    # Health check enabled for {{ server }}
    server {{ server }}:8080;
{% endfor %}
}
```

**A20 — Hard:**
1. Set `serial: 20%` (or a specific number) to process servers in batches.
2. **Pre-task:** Use `uri` or a LB module to remove the current batch from the Load Balancer.
3. **Deployment:** Update the application code/service.
4. **Health Check:** Use the `uri` module in a loop to verify the app is returning `200 OK` on the local port.
5. **Post-task:** Re-add the batch to the Load Balancer.
6. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, trigger a task to revert the app version and re-add the node to the LB to maintain availability.
