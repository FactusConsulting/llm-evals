## Application Architecture

**AA1** — A **monolith** is a single unified unit where all business logic, data access, and UI are bundled into one codebase and deployment. **Microservices** decompose the application into small, independent services communicating over a network. 
*Problems introduced by microservices:* 1. **Network Latency/Reliability** (inter-service calls can fail or slow down). 2. **Distributed Data Consistency** (managing transactions across multiple databases). 3. **Operational Complexity** (monitoring, deployment, and logging across dozens of services).

**AA2** — **Synchronous** communication requires the caller to wait for a response before proceeding (e.g., REST/HTTP). **Asynchronous** communication allows the caller to send a message and move on without waiting for an immediate result (e.g., RabbitMQ/Kafka).

**AA3** — A **Reverse Proxy** (e.g., Nginx) primarily handles request routing, load balancing, and SSL termination. An **API Gateway** (e.g., Kong, AWS API Gateway) is a specialized reverse proxy that adds "API-aware" logic: rate limiting, authentication, request transformation, and billing. 
*Can it replace a reverse proxy?* Yes, but it is often "overkill" for simple static site routing. A reverse proxy is lighter and faster for basic traffic management.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. Each local transaction updates the database and publishes an event to trigger the next step. If one step fails, the Saga executes "compensating transactions" to undo previous steps.
*   **Choreography:** Services exchange events without a central coordinator. Best for simple workflows with few services.
*   **Orchestration:** A central "orchestrator" tells participants which local transactions to execute. Best for complex business logic with many steps.

**AA5** — **CQRS** separates the data models for reading (Query) and writing (Command). It is paired with **Event Sourcing**, which stores the state of an application as a sequence of immutable events rather than just the current state. 
*Problem solved:* Traditional CRUD struggles with high read/write asymmetry and lacks a native audit trail. This combination allows for highly optimized read views (materialized views) and the ability to reconstruct state at any point in time.

**AA6** — The **Circuit Breaker** prevents a service from repeatedly trying to call a failing downstream service, avoiding cascading failures.
*   **Closed:** Requests flow normally.
*   **Open:** Requests fail immediately without calling the downstream service.
*   **Half-Open:** A limited number of requests are allowed through to test if the service has recovered.
*   *Difference from Retry:* Retries assume a transient glitch; Circuit Breakers assume a systemic failure. Use both by wrapping a retry logic inside a circuit breaker.

**AA7** — 
1. **Shared DB, Shared Schema:** Lowest cost, highest noisy-neighbor risk, lowest security (relies on `WHERE tenant_id = X`).
2. **Shared DB, Separate Schema:** Medium cost, medium risk, better security (schema-level permissions), higher migration complexity.
3. **Separate DB:** Highest cost, lowest risk, highest security (physical isolation), highest operational overhead (managing $N$ databases).

**AA8** — **Strong Consistency** ensures all nodes see the same data at the same time. **Eventual Consistency** guarantees that if no new updates are made, all nodes will eventually converge.
*Inventory Architecture:* To prevent overselling, use **Strong Consistency**. 
*Stack:* A Distributed SQL database (e.g., CockroachDB) or a traditional RDBMS (Postgres) with pessimistic locking (`SELECT FOR UPDATE`) or atomic increments. At scale, use **sharding by product ID** to avoid a single global lock.

**AA9** — A **sidecar proxy** is a helper container deployed alongside the application container in the same pod. In Istio, **Envoy** is the sidecar that intercepts all network traffic.
*   **Data Plane:** The collection of Envoy proxies handling actual traffic.
*   **Control Plane:** (Istiod) Manages and configures the proxies.
*   **mTLS:** Solves identity and encryption. Unlike app-level TLS, the sidecar handles certificate rotation and identity verification transparently, so the application code doesn't need to manage certificates.

**AA10** — The **Strangler Fig pattern** involves incrementally replacing legacy functionality with new services until the old system is "strangled" and can be removed.
*Strategy:* 1. Place an API Gateway/Proxy in front of the .NET Framework monolith. 2. Identify a single bounded context (e.g., "Payments"). 3. Build the "Payments" service in .NET 8. 4. Update the Gateway to route `/payments` traffic to the new service while everything else goes to the monolith. 5. Repeat for other modules.

**AA11** — A methodology for building portable, scalable cloud-native apps. 
*Factors:* 1. **Codebase** (one codebase, many deploys). 2. **Dependencies** (explicitly declared). 3. **Config** (stored in environment variables). 4. **Backing Services** (treated as attached resources). 5. **Build, Release, Run** (strictly separated stages). 6. **Processes** (stateless). 
*Importance:* These ensure that apps can be deployed consistently across Dev/Staging/Prod and scaled horizontally without manual intervention.

**AA12** — 
*   **Coupling:** Event-driven (Loose) vs Request-driven (Tight).
*   **Scalability:** Event-driven (High, async buffers) vs Request-driven (Limited by synchronous chain).
*   **Debugging:** Event-driven (Hard, requires tracing) vs Request-driven (Easier, linear stack trace).
*   **Ordering:** Event-driven (Guaranteed per partition in Kafka) vs Request-driven (Sequential by nature).
*   **Failure:** Event-driven (DLQs, retries) vs Request-driven (Immediate error/timeout).
*   *Choice:* Use Request-driven for immediate feedback (UI actions); Event-driven for background processing and cross-service synchronization.

**AA13** — A **Load Balancer** distributes incoming network traffic across multiple servers.
*   **Layer 4 (Transport):** Routes based on IP and Port (TCP/UDP). Fast, but "blind" to content.
*   **Layer 7 (Application):** Routes based on HTTP headers, cookies, or URL paths.
*   *Use Case:* Path-based routing (e.g., sending `/api` to a backend server and `/static` to a storage bucket).

**AA14** — A **Message Queue** is a component that stores messages until a consumer processes them.
*   **Queue (RabbitMQ):** Messages are deleted once consumed. Best for task distribution (Work Queues).
*   **Log-based (Kafka):** Messages are appended to a log and persist. Multiple consumers can read the same data at their own pace. Best for event streaming and audit logs.

**AA15** — A **Container** shares the host OS kernel and isolates the application process. A **VM** includes a full guest OS and runs on a hypervisor. 
*Popularity:* Containers are lightweight, start in seconds, and ensure "it works on my machine" by packaging all dependencies.

**AA16** — **Stateless** services do not store client data between requests (e.g., a calculator API). **Stateful** services remember client state (e.g., a database or a legacy session-based web app). 
*Scaling:* Stateless services scale horizontally easily because any instance can handle any request; stateful services require "sticky sessions" or shared external state (Redis).

**AA17** — An **ORM** maps database tables to objects in a programming language. 
*Examples:* Entity Framework (.NET), Hibernate (Java). 
*Trade-offs:* ORMs increase developer productivity and prevent SQL injection, but can produce inefficient queries ("N+1 problem") and hide the underlying database performance characteristics.

**AA18** — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function.
*Implementation:* 1. **Thread Pools:** Assign a dedicated thread pool to each downstream service call so one slow service doesn't exhaust all available threads. 2. **Deployment Groups:** Deploy critical "Checkout" services on separate hardware/clusters from "Product Review" services.

**AA19** — 
*   **OT (Operational Transformation):** Central server transforms operations to ensure consistency. High complexity, requires a central server, low latency for users.
*   **CRDTs (Conflict-free Replicated Data Types):** Data structures that merge automatically without conflicts. Lower server complexity, supports peer-to-peer, eventual consistency.
*   *Choice for Offline:* **CRDTs**, because they allow local mutations that can be merged mathematically when the client reconnects without needing a central coordinator to "transform" the history.

**AA20** — Challenges include maintaining a "Trace ID" across different languages and protocols.
*   **Context Propagation:** Using headers (W3C Trace Context or B3) to pass the Trace ID.
*   **Sampling:** **Head-based** (decide to trace at the start) vs **Tail-based** (decide to keep the trace after it finishes, e.g., only keep traces that resulted in an error).
*   **Storage:** Jaeger or Tempo index these spans for querying.
*   **Kafka:** To ensure continuity, the Trace ID must be injected into the **Kafka Record Headers**, not the message payload, allowing the consumer to extract it and start a new span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal)** runs directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V). **Type 2 (Hosted)** runs as an app on a host OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network)** provides block-level access (looks like a local disk). Uses iSCSI or Fibre Channel. Use for databases. **NAS (Network Attached Storage)** provides file-level access (looks like a network share). Uses NFS or SMB. Use for shared documents/backups.

**OP3** — **3-Tier** (Core $\rightarrow$ Distribution $\rightarrow$ Access) is designed for North-South traffic (client to server). **Leaf-Spine** is a two-tier architecture where every Leaf switch connects to every Spine switch. It solves the "East-West" traffic bottleneck (server to server) common in virtualized environments, providing predictable latency and linear scalability.

**OP4** — 
*   **Architecture:** 3+ nodes to maintain **quorum** (majority vote). 
*   **Fencing:** Use **STONITH** (Shoot The Other Node In The Head) via IPMI to ensure a failed node is truly dead before restarting VMs. 
*   **Storage:** **Ceph** (distributed) for high availability or **iSCSI** (centralized) for simplicity. 
*   **Failure:** If a node fails, the cluster detects loss of heartbeat $\rightarrow$ Fences the node $\rightarrow$ Promotes VMs to healthy nodes.

**OP5** — **VLAN Trunking** allows a single physical link to carry traffic for multiple VLANs. **802.1Q** is the standard that adds a "tag" to the Ethernet frame to identify the VLAN. 
*Linux Config:* Create tagged sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — 
*   **RAID 1:** Mirroring (High safety, 50% capacity).
*   **RAID 5:** Parity (1 disk fail, good read).
*   **RAID 6:** Dual Parity (2 disk fail).
*   **RAID 10:** Mirror of stripes (High perf, high safety, 50% capacity).
*   **RAID Z2:** ZFS version of RAID 6 (prevents write hole).
*   *Choice for DB (6 drives):* **RAID 10**. Databases require high IOPS (random writes), and RAID 10 provides the best performance and fast recovery compared to parity-based RAID.

**OP7** — 
*   **Internal:** AD-integrated DNS for internal name resolution.
*   **DMZ:** Separate authoritative servers for public records.
*   **Split-Horizon:** The same domain (e.g., `corp.com`) returns a private IP internally and a public IP externally.
*   **DNSSEC:** Digitally signs external zones to prevent cache poisoning.
*   **VPN:** Laptop uses a VPN tunnel to reach the internal recursive resolvers, overriding local DNS.

**OP8** — **Chain:** Root CA (Self-signed) $\rightarrow$ Intermediate/Issuing CA $\rightarrow$ End-entity Cert. 
*Deployment:* Root CA is kept **offline** (air-gapped). Issuing CA handles requests. **CRL** is a list of revoked certs; **OCSP** is a real-time API check. 
*Compromise:* A compromised Sub CA requires revoking that Sub CA's cert via the Root. A compromised Root CA is a total failure; every single certificate in the organization must be re-issued.

**OP9** — 
*   **MPLS:** High cost, guaranteed QoS, high reliability.
*   **IPsec VPN:** Low cost, relies on public internet, variable latency.
*   **SD-WAN:** Mid cost, software-defined overlay, dynamic path selection.
*   **WireGuard Mesh:** Low cost, high performance, complex manual management at scale.
*   *Recommendation:* **SD-WAN**. It allows prioritizing VoIP traffic (QoS) over multiple links (MPLS + Internet) and is easier to manage than a manual mesh.

**OP10** — **iDRAC/iLO/IPMI** are Baseboard Management Controllers (BMCs) that allow hardware management regardless of OS state. 
*Criticality:* Allows remote power cycling, BIOS config, and OS installation. 
*Internet Exposure:* Catastrophic. Attackers can gain full console access, reboot servers, or flash malicious firmware.

**OP11** — 
*   **LVM:** Logical Volume Manager; allows resizing partitions. Snapshots are "thick" (copy-on-write).
*   **LVM-Thin:** Allows over-provisioning of storage. Snapshots are more efficient.
*   **ZFS:** Combined FS and Volume Manager. Uses Copy-on-Write (CoW) for everything. Snapshots are near-instant and extremely space-efficient.

**OP12** — 
*   **Design:** 3 sites (Site A, Site B, and a Witness site). 
*   **Ceph:** Use **CRUSH rules** to ensure replicas are placed in different failure domains (sites). 
*   **Latency:** Must be very low (usually <10ms) to avoid write timeouts. 
*   **Split-Brain:** Prevented by requiring a majority (quorum) to commit writes. 
*   *2-Site Problem:* Without a third tiebreaker site, if the link breaks, neither site knows if the other is dead or just disconnected, leading to a "split-brain" where both might try to be primary.

**OP13** — **DHCP** assigns IP addresses. **DORA:** Discover (Client $\rightarrow$ All), Offer (Server $\rightarrow$ Client), Request (Client $\rightarrow$ Server), Acknowledge (Server $\rightarrow$ Client). 
*Failure:* When the lease expires and no server is found, Windows assigns an **APIPA** address (`169.254.x.x`).

**OP14** — **Unmanaged** is a basic plug-and-play switch. **Managed** switches allow configuration of **VLANs** (segmentation), **STP** (preventing loops), **SNMP** (monitoring), and **Port Mirroring** (for packet capture/IDS).

**OP15** — **NTP** synchronizes clocks across the network. 
*Criticality:* Essential for Kerberos authentication (which fails if clocks differ by >5 mins), log correlation for forensics, and database replication consistency. 
*Drift:* Can cause "clock skew," leading to authentication failures and corrupted distributed database transactions.

**OP16** — **Physical:** Hardware. **VM:** Hardware emulation via hypervisor. **Container:** OS-level virtualization. 
*Bare Metal Use Case:* High-performance databases (avoiding hypervisor overhead), GPU-intensive workloads, or very large RAM requirements.

**OP17** — **UPS** provides immediate battery power for minutes to bridge the gap. **Generator** provides long-term power via fuel. 
*Why both?* Generators take seconds/minutes to start; UPS prevents the server from crashing during that gap. 
*ATS:* The **Automatic Transfer Switch** detects power loss and switches the load from the utility grid to the generator.

**OP18** — **Active-Passive:** One node works, one waits. **Active-Active:** Both nodes handle traffic. 
*Postgres HA:* Use **Pacemaker/Corosync** for cluster membership. **STONITH** ensures the failed node is powered off. A **Virtual IP (VIP)** is assigned to the active node; upon failure, the VIP floats to the passive node, and the application reconnects to the same IP.

**OP19** — 
*   **3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
*   **RPO/RTO:** RPO (Recovery Point Objective) = max acceptable data loss; RTO (Recovery Time Objective) = max acceptable downtime.
*   **Types:** Full (everything), Incremental (changes since last backup), Differential (changes since last full).
*   **Protection:** Use **Immutable Backups** (WORM - Write Once Read Many) to prevent ransomware from encrypting backups.
*   **Backup vs DR:** Backup is the *copy of data*; DR is the *entire process* (people, sites, backups) to restore business operations.

**OP20** — **802.1X** provides port-level security. 
*   **Roles:** **Supplicant** (Client device), **Authenticator** (Switch), **Auth Server** (RADIUS). 
*   **EAP:** **EAP-TLS** uses certificates (most secure); **PEAP** uses usernames/passwords. 
*   **Process:** Switch blocks all traffic except EAP $\rightarrow$ RADIUS validates $\rightarrow$ RADIUS tells switch to open port and assign a **Dynamic VLAN**. 
*   **Failure:** Device is placed in a "Guest VLAN" or blocked. 
*   **MAB:** For devices without 802.1X (printers), the switch sends the device's **MAC address** to the RADIUS server as the identity.
