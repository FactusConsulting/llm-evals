## Cloud Infrastructure Architecture

**CL1 — Easy:** 
*   **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and everything above it. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing the underlying OS or runtime. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Fully managed software delivered via a browser/API. You only manage configuration and data. *Example: Microsoft 365.*

**CL2 — Easy:** 
The Shared Responsibility Model dictates that the provider is responsible for the security **of** the cloud (hardware, global infrastructure), and the customer is responsible for security **in** the cloud.
*   **IaaS VMs:** Provider handles physical host/hypervisor; you handle OS patching, firewall (SG), and apps.
*   **Managed Kubernetes (EKS/GKE):** Provider handles the Control Plane; you handle worker node patching (usually), pod security, and network policies.
*   **SaaS (M365):** Provider handles almost everything; you handle identity/access management and data governance.

**CL3 — Medium:** 
*   **VPC:** A logically isolated virtual network in the cloud.
*   **Subnet:** A range of IP addresses in the VPC, usually tied to a specific Availability Zone.
*   **Security Group (SG):** A virtual firewall for **instances** (NIC level). It is **stateful** (if you allow inbound, outbound is automatically allowed).
*   **NACL:** A firewall for **subnets**. It is **stateless** (you must explicitly define both inbound and outbound rules).
*   **Layering:** VPC $\rightarrow$ Subnet (NACL) $\rightarrow$ Instance (SG).

**CL4 — Medium:** 
*   **Landing Zone:** A pre-configured, multi-account environment based on best practices (security, logging, networking).
*   **Organizational Units (OUs):** Logical groupings of accounts (e.g., Prod, Dev, Security) to apply policies.
*   **Guardrails:** Service Control Policies (SCPs) that set the maximum available permissions across accounts.
*   **Shared Networking:** Using a Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize egress/ingress and connect VPCs/VNets.
*   **Centralized Logging:** Aggregating all CloudTrail/Log Analytics data into a dedicated security account.
*   **Single-account problems:** Blast radius (one compromise affects all), API rate limits, and billing complexity.

**CL5 — Medium:** 
IaC is the management of infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu:** HCL-based, provider-agnostic. Best for multi-cloud or general-purpose infra.
*   **Pulumi:** Uses general-purpose languages (TS, Python, Go). Best for developers who want loops/logic in infra.
*   **CloudFormation/Bicep:** Provider-specific (AWS/Azure). Best for deep integration and "day zero" support of new services.
*   **Crossplane:** K8s-native (CRDs). Best for managing cloud resources as K8s objects (Control Plane approach).

**CL6 — Medium:** 
*   **HPA:** Scales pods based on CPU/RAM metrics.
*   **VPA:** Adjusts the CPU/RAM requests/limits of existing pods.
*   **Cluster Autoscaler:** Adds/removes physical nodes from the cluster when pods cannot be scheduled.
*   **KEDA:** Event-driven autoscaling (e.g., scaling based on Kafka lag or RabbitMQ queue depth).
*   **KEDA vs HPA:** Use KEDA when the scaling trigger is an external event rather than internal resource consumption.

**CL7 — Hard:** 
*   **RPO (Recovery Point Objective):** Max acceptable data loss. **RTO (Recovery Time Objective):** Max acceptable downtime.
*   **Active-Active:** Traffic split across regions. RTO $\approx$ 0. High cost.
*   **Active-Passive:** Primary region active; secondary on standby.
*   **Replication:** Sync (Zero data loss, high latency) vs Async (Potential data loss, low latency).
*   **DNS Failover:** Route53/Traffic Manager uses health checks to route traffic to the healthy region.
*   **DR Types:** 
    *   *Pilot Light:* DB is synced; apps are off/minimal.
    *   *Warm Standby:* Scaled-down version of the app is always running.
    *   *Multi-site Active-Active:* Full capacity in both regions.

**CL8 — Hard:** 
GitOps uses Git as the single source of truth for infrastructure and app state. A controller (ArgoCD/Flux) continuously reconciles the live state with the Git state.
*   **ArgoCD:** Feature-rich UI, application-centric.
*   **FluxCD:** Lightweight, CLI-driven, highly modular.
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift:** If a manual change occurs, the controller detects the diff and automatically overwrites the manual change to match Git.

**CL9 — Hard:** 
*   **StatefulSet:** Ensures stable network IDs and ordered deployment/scaling.
*   **PV/PVC + Local Storage Class:** Maps pods to specific disks on the node for low latency.
*   **Headless Service:** Provides DNS records for individual pods (essential for clustering).
*   **Init Containers:** Handle filesystem setup or wait for DB readiness before the app starts.
*   **ConfigMaps:** Mounted as volumes to provide config files at specific paths.
*   **Pod Disruption Budgets (PDB):** Ensures a minimum number of replicas remain available during maintenance.

**CL10 — Medium:** 
*   **Service Account:** An identity for a process running in a pod.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Bad Practice:** Mounting static JSON keys in pods is dangerous because keys are long-lived and easily leaked.
*   **Federation:** The cloud provider trusts the K8s cluster's OIDC provider, issuing short-lived, rotating tokens to the pod.

**CL11 — Medium:** 
*   **Object (S3/Blob):** Unstructured data, accessed via API. High durability (11 9s), virtually infinite scale. Use for backups, media, logs.
*   **Block (EBS/Managed Disk):** Raw volumes attached to one VM. Low latency. Use for OS disks, Databases.
*   **File (EFS/Azure Files):** Shared filesystem (NFS/SMB). Multi-pod access. Use for shared config, CMS uploads.

**CL12 — Hard:** 
*   **Architecture:** 
    *   **Network Policies:** L3/L4 isolation (deny-all by default).
    *   **Service Mesh (Istio/Linkerd):** mTLS for encrypted, authenticated L7 communication.
    *   **Pod Identity:** IRSA/Workload Identity for cloud resource access.
    *   **Admission Controllers:** OPA/Kyverno to block non-compliant pods (e.g., no root).
    *   **Image Signing:** Cosign/Notary to ensure only verified images run.
    *   **Runtime Security:** Falco to detect anomalous syscalls.
    *   **Secrets:** Vault for dynamic secrets.
*   **Difference:** Traditional security relies on a "hard shell" (perimeter); Zero Trust assumes the network is already compromised and verifies every single request.

**CL13 — Easy:** 
A CDN is a distributed network of proxy servers (Edge locations) that cache content closer to users.
*   **Services:** AWS CloudFront, Akamai.
*   **Use Case:** Use a CDN for global users, static assets (JS/CSS/Images), or to protect the origin from traffic spikes. Serve directly from origin only for highly dynamic, user-specific, or low-traffic content.

**CL14 — Easy:** 
*   **Region:** A geographic area (e.g., us-east-1).
*   **Availability Zone (AZ):** One or more discrete data centers within a region with redundant power/cooling.
*   **Multi-AZ:** Protects against a single DC failure.
*   **Zonal vs Regional:** Zonal resources (e.g., EBS volume) exist in one AZ; Regional resources (e.g., S3, Lambda) are replicated across the region.

**CL15 — Easy:** 
A managed DB service abstracts the underlying server.
*   **Provider handles:** OS patching, hardware failure, automated backups, point-in-time recovery, and high-availability failover.
*   **User handles:** Database schema design, query optimization, user permissions, and application-level logic.

**CL16 — Easy:** 
*   **Users:** Permanent identities for people.
*   **Groups:** Collections of users for easier policy assignment.
*   **Roles:** Temporary identities assumed by users or services.
*   **Policies:** JSON documents defining "Who can do what on which resource."
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply by using granular policies instead of `AdministratorAccess`.

**CL17 — Easy:** 
Serverless is an execution model where the provider manages the server allocation and scaling.
*   **Comparison:** Lambda (AWS), Azure Functions, Google Cloud Functions are all event-driven and bill per execution.
*   **Cold Starts:** The latency incurred when a provider spins up a new container for a function after inactivity.
*   **Poor Fit:** Long-running processes (timeouts), apps requiring ultra-low consistent latency, or predictable, high-constant loads (where VMs are cheaper).

**CL18 — Medium:** 
*   **Ingress Resource:** L7 rules (host/path) for routing.
*   **Gateway API:** The successor to Ingress; provides role-based management (Gateway, HTTPRoute).
*   **Annotations:** Cloud-specific tweaks (e.g., `service.beta.kubernetes.io/aws-load-balancer-type`).
*   **Mesh Gateway:** Istio Ingress Gateway for advanced traffic splitting/canary.
*   **TLS Termination:** Can happen at the Cloud LB (offloading), the Ingress Controller, or the Sidecar (End-to-End mTLS).
*   **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenancy, and better standardization.

**CL19 — Hard:** 
*   **Compute:** Use Savings Plans for baseline, Spot for stateless/batch workloads, and Right-sizing (using Compute Optimizer) to reduce over-provisioned instances.
*   **Storage:** Move old data to S3 Intelligent-Tiering or Glacier Deep Archive.
*   **Idle Resources:** Implement automated scripts to delete unattached EBS volumes or orphaned Elastic IPs.
*   **FinOps:** Establish a culture of cost-awareness. Use **Showback** (reporting costs to teams) and **Chargeback** (billing costs to team budgets).
*   **Tools:** AWS Cost Explorer, Kubecost (for K8s), and tagging policies for granular visibility.

**CL20 — Hard:** 
*   **Strategy:** Use Kubernetes as the common runtime (abstraction layer) and Terraform for consistent provisioning.
*   **Networking:** Site-to-Site VPN or dedicated interconnects (DirectConnect/ExpressRoute).
*   **Identity:** OIDC/SAML federation for Single Sign-On (SSO) across clouds.
*   **Trade-offs:** Theoretical benefit is "no lock-in" and "highest availability." Real-world cost is massive operational complexity, higher egress costs, and the "lowest common denominator" problem (cannot use provider-specific "magic" features).
*   **Justification:** Justified for strict regulatory requirements or extreme risk mitigation. Unnecessary for most companies where a multi-AZ/multi-region strategy suffices.

## OT Infrastructure Architecture

**OT1 — Easy:** 
The Purdue Model (ISA-95) segments industrial networks into levels:
*   **Level 0 (Process):** The physical equipment (sensors, actuators, motors).
*   **Level 1 (Basic Control):** PLCs and PID controllers that manage L0.
*   **Level 2 (Area Supervisory):** HMIs and SCADA software for operator monitoring.
*   **Level 3 (Site Operations):** Site-wide historians, domain controllers, and manufacturing execution systems (MES).
*   **Level 4/5 (Enterprise):** Corporate IT, ERP systems, and internet access.

**OT2 — Easy:** 
*   **IT:** Focuses on Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability (CIA).
*   **OT:** Focuses on Availability $\rightarrow$ Integrity $\rightarrow$ Confidentiality (AIC) and Safety.
*   **Patching:** OT systems cannot be patched like IT because downtime can cause physical danger or massive financial loss. Patches must be validated in a test environment to ensure they don't crash the PLC/HMI.

**OT3 — Medium:** 
The IDMZ is a buffer zone that prevents direct communication between the Enterprise (L4) and the Control Zone (L3 and below).
*   **Traffic:** Only brokered traffic (e.g., a mirrored historian or a jump host). No direct L4 $\rightarrow$ L1.
*   **Danger:** Direct L4 $\rightarrow$ L1 connectivity allows a compromised corporate laptop to send a "Stop" command directly to a PLC, bypassing all supervisory controls and safety checks.

**OT4 — Medium:** 
1.  **Modbus TCP:** L1/L2 (Simple, widely used, no security).
2.  **OPC UA:** L2/L3 (Secure, object-oriented, used for vendor-neutral data exchange).
3.  **EtherNet/IP (CIP):** L1/L2 (Common in Rockwell/Allen-Bradley environments).
4.  **PROFINET:** L1/L2 (High-speed, common in Siemens environments).
5.  **MQTT:** L3 $\rightarrow$ Cloud (Lightweight pub/sub for IoT/Telemetry).

**OT5 — Medium:** 
*   **Firewall:** Software-based, bidirectional, allows/blocks based on rules.
*   **Data Diode:** Hardware-based, physically allows data to flow in **one direction only** (using light/fiber).
*   **Use Case:** Use a diode to send logs/data from a high-security OT zone to IT without any possibility of an external attacker sending a command back into the OT zone.
*   **Limitation:** No TCP handshake/acknowledgment; requires specialized protocols to ensure data delivery.

**OT6 — Medium:** 
*   **Flow:** PLC (L1) $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Plant Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Boundaries:** 
    1. Firewall between L2 and L3.
    2. IDMZ between L3 and L4.
    3. Outbound-only firewall/diode from IDMZ to Cloud.

**OT7 — Hard:** 
*   **Zone:** A grouping of assets with similar security requirements.
*   **Conduit:** A defined communication path between zones.
*   **Design:**
    *   **Enterprise Zone (L4):** Corporate users.
    *   **IDMZ:** Jump hosts, mirrored historian.
    *   **Operations Zone (L3):** SCADA servers, Engineering Workstations.
    *   **Control Zone (L2/L1):** PLCs, HMIs.
    *   **Safety Zone (L0/L1):** SIS (Safety Instrumented Systems) — isolated from all other zones.
    *   **Conduits:** L4 $\rightarrow$ IDMZ (HTTPS/SSH), IDMZ $\rightarrow$ L3 (OPC UA), L3 $\rightarrow$ L2 (Industrial Protocols).

**OT8 — Hard:** 
*   **Strategy:** Move from flat L2 to a segmented architecture.
*   **VLANs:** Create separate VLANs for each production line and a separate VLAN for management/HMIs.
*   **Firewalls:** Place an Industrial Firewall (e.g., Cisco ISA) between the SCADA server and the PLC VLANs.
*   **Remote Access:** Implement a VPN $\rightarrow$ MFA $\rightarrow$ Jump Host in the IDMZ.
*   **Transition:** Build the new segmented network in parallel. Migrate one production line at a time during scheduled maintenance windows to minimize risk.

**OT9 — Hard:** 
*   **BPCS:** Manages the normal process (e.g., keeping a tank at 50%).
*   **SIS:** A separate system that triggers a "Safe State" (e.g., emergency shutdown) if the BPCS fails.
*   **IEC 61511:** The international standard for functional safety in the process industry.
*   **Isolation:** SIS must be isolated so a failure (or attack) in the BPCS doesn't also disable the safety system.
*   **Ransomware in SIS:** Could lead to a "loss of safety function," meaning if a physical emergency occurs, the system cannot shut down, potentially leading to explosions or environmental disasters.

**OT10 — Medium:** 
*   **PLC (Programmable Logic Controller):** Fast, discrete control, handles specific machines.
*   **DCS (Distributed Control System):** Integrated system for large-scale continuous processes (e.g., oil refinery).
*   **SCADA (Supervisory Control and Data Acquisition):** High-level monitoring of geographically dispersed assets.
*   **Coexistence:** Yes. A SCADA system often acts as the "umbrella" monitoring multiple PLCs and DCS controllers.

**OT11 — Medium:** 
*   **Architecture:** User $\rightarrow$ VPN (MFA) $\rightarrow$ Jump Host (IDMZ) $\rightarrow$ Target HMI/PLC.
*   **Controls:** Session recording for auditing, time-limited (JIT) access, and strict firewall rules.
*   **RDP Danger:** Direct RDP from corporate to HMI allows lateral movement; if a corporate laptop is infected with ransomware, it can encrypt the HMI directly, blinding the operator.

**OT12 — Hard:** 
*   **Detection:** Deploy passive IDS (e.g., Nozomi, Claroty) to detect anomalous Modbus/S7 traffic.
*   **Response:** 
    1. Isolate the L3 network from L4 (kill the VPN).
    2. Verify the integrity of the PLC logic (compare checksums).
    3. Coordinate with the control room to determine if the process can be run manually.
*   **Operator Role:** The operator is the final authority on **safety**. They decide if the process is stable enough to remain online or if an emergency shutdown is required.

**OT13 — Easy:** 
*   **HMI:** A graphical interface (screen) that allows operators to monitor and control the process.
*   **Difference:** An HMI is for **operation** (start/stop, setpoints); an Engineering Workstation is for **configuration** (writing code, changing PLC logic).

**OT14 — Easy:** 
*   **Historian:** A high-performance time-series database that logs process data.
*   **Plant Historian (L3):** High-resolution data, used for real-time troubleshooting and local reporting.
*   **Enterprise Historian (L4):** Aggregated, lower-resolution data used for business KPIs and long-term trends.

**OT15 — Easy:** 
*   **Ladder Logic:** A graphical programming language that looks like electrical relay diagrams.
*   **Device:** Executed by PLCs.
*   **Dominance:** It is intuitive for electricians/technicians and is deterministic (guarantees execution time), which is critical for safety.

**OT16 — Easy:** 
*   **RTU (Remote Terminal Unit):** A ruggedized device designed for wide-area telemetry.
*   **Difference:** RTUs often have better integrated wireless comms and lower power consumption than PLCs.
*   **Environment:** Used in pipelines, power grids, or water pumping stations where assets are miles apart.

**OT17 — Easy:** 
*   **Analog:** Continuous signal (e.g., 4-20mA). **Digital:** Binary (On/Off).
*   **4-20mA vs 0-20mA:** 4mA is the "Live Zero." If the wire breaks, the signal drops to 0mA, allowing the system to distinguish between a "zero reading" (4mA) and a "broken wire" (0mA).

**OT18 — Medium:** 
*   **Asset Inventory:** A list of every device, firmware version, and IP on the network. Without it, you cannot patch or monitor what you don't know exists.
*   **Passive Monitoring:** Sniffing traffic via SPAN/TAP ports (Safe).
*   **Active Scanning:** Sending probes to devices (Dangerous).
*   **Danger:** Old PLCs have fragile TCP/IP stacks; a standard Nmap scan can cause a buffer overflow and crash the PLC, stopping production.

**OT19 — Hard:** 
*   **MITRE ATT&CK for ICS:** A matrix of adversary tactics specifically for industrial environments.
*   **Tactics/Techniques:** 
    1. *Initial Access:* Valid Accounts.
    2. *Execution:* Scripting.
    3. *Persistence:* Project File Modification.
    4. *Inhibition of Response Function:* Alarm Suppression.
    5. *Impair Process Control:* Unauthorized Command Message.
*   **Difference:** Focuses on physical impact (e.g., manipulating a valve) rather than just data theft.
*   **Use:** Map current detections to the matrix to find "blind spots" in the OT network.

**OT20 — Hard:** 
*   **Log Collection:** Use passive TAPs to send traffic to an IDS, which then sends alerts to the SIEM. Avoid polling PLCs directly.
*   **SIEM Integration:** Feed OT alerts into a central SIEM (e.g., Sentinel) but keep the OT data context.
*   **Staffing:** A hybrid team. IT analysts handle the "cyber" (logs/traffic), while OT engineers handle the "process" (what does this alarm mean for the plant?).
*   **Firmware Alert:** 
    1. Alert triggers $\rightarrow$ OT Engineer verifies if a maintenance window was scheduled.
    2. If unauthorized $\rightarrow$ Isolate the PLC $\rightarrow$ Perform forensic image of the logic $\rightarrow$ Restore from a known-good "Gold" backup.
