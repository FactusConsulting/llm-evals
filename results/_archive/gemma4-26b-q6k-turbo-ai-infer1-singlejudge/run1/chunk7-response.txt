## Application Architecture

**AA1** — A monolith is a single, unified unit where all components share memory and resources. Microservices are a collection of loosely coupled, independently deployable services. Three problems microservices introduce: 1. Network latency between calls, 2. Distributed data consistency challenges, 3. Increased operational complexity (observability/deployment).

**AA2** — Synchronous communication requires the caller to wait for a response (e.g., REST over HTTP). Asynchronous communication allows the caller to continue without waiting (e.g., sending a message via RabbitMQ).

**AA3** — An API Gateway handles application-level logic like authentication, rate limiting, and request routing/orchestration. A reverse proxy primarily focuses on load balancing and SSL termination. An API Gateway *is* a specialized reverse proxy; while it can replace a standard one, you might still use both if you need a dedicated proxy for raw performance before hitting the gateway.

**AA4** — The Saga pattern manages distributed transactions by breaking them into a sequence of local transactions. **Choreography** uses events (no central controller); appropriate for simple workflows. **Orchestration** uses a central coordinator; appropriate for complex business logic with many steps.

**AA5** — CQRS separates read models from write models. It is paired with Event Sourcing because ES provides the "source of truth" (the event log) used to build optimized read projections. This solves the problem of high-contention CRUD operations where reads and writes compete for the same database resources and schema.

**AA6** — States: **Closed** (traffic flows), **Open** (calls fail fast immediately), **Half-Open** (testing if service recovered). Unlike a retry which keeps hammering a failing service, a Circuit Breaker stops traffic to allow recovery. You use them together by wrapping a retry mechanism inside a circuit breaker so that retries only happen when the circuit is closed/half-open.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, lowest security, highest noisy-neighbor risk, easiest to manage.
2. **Separate Schema:** Medium cost/complexity, better isolation, moderate noisy-neighbor risk.
3. **Separate DB:** Highest cost, highest security, zero noisy-neighbor risk, highest operational complexity.

**AA8** — Strong consistency ensures all nodes see the same data simultaneously; eventual consistency allows temporary divergence. For inventory, I would use **Strong Consistency**. At scale, I'd use a distributed SQL database (like CockroachDB or Spanner) using Paxos/Raft consensus, or implement distributed locks with a pattern like TCC (Try-Confirm-Cancel).

**AA9** — A sidecar is a helper container running alongside the app. In Istio, Envoy acts as the proxy for every pod. The **Data Plane** consists of Envoys handling traffic; the **Control Plane** (Istio Pilot/etc.) manages configuration. mTLS solves identity and encryption between services without requiring application code changes, preventing man-in-the-middle attacks within the cluster.

**AA10** — Use the Strangler Fig pattern: 1. Place a proxy in front of the monolith. 2. Build new features as .NET 8 microservices. 3. Route specific paths from the proxy to the new services. 4. Gradually migrate old functionality until the monolith is "strangled" and can be decommissioned.

**AA11** — Codebase, Dependencies, Config, Backing Services, Build/Release/Run, Processes, Port binding, Concurrency, Disposability, Dev/Prod parity, Logs, Admin processes. They ensure apps are portable, scalable, and easy to automate in cloud environments.

**AA12** — 
*   **Kafka:** High throughput, decoupled, complex debugging, high ordering guarantees via partitions, handles failures by replaying logs. Best for stream processing.
*   **REST/gRPC:** Low latency, tightly coupled, easy debugging, strict request-response, harder failure handling. Best for immediate user feedback.

**AA13** — A load balancer distributes incoming traffic across multiple servers. **Layer 4** works at the transport level (IP/TCP). **Layer 7** works at the application level (HTTP). Use case: Routing requests based on URL path (e.g., `/api` goes to Service A, `/images` goes to Service B).

**AA14** — RabbitMQ is a traditional message queue (messages are deleted after consumption; smart broker). Kafka is a log-based broker (messages persist as an ordered log; dumb broker, smart consumer). Pick RabbitMQ for complex routing/task queues; pick Kafka for high-throughput event streaming and replayability.

**AA15** — A container shares the host OS kernel, making it lightweight and fast. A VM includes a full guest OS, making it heavy and slow. Containers are popular because they provide environment consistency and rapid scaling.

**AA16** — Stateless services don't store client context between requests (e.g., a web server); stateful services do (e.g., a database). Stateless services scale horizontally easily because any instance can handle any request.

**AA17** — An ORM maps objects in code to rows in a DB. Examples: Hibernate (Java), SQLAlchemy (Python). Trade-offs: Faster development vs. performance overhead and difficulty with highly optimized complex queries.

**AA18** — The Bulkhead pattern isolates resources so one failing component doesn't consume all system capacity. Implementation: Use separate thread pools for different downstream services or deploy critical services on dedicated hardware clusters.

**AA19** — **OT** requires a central authority to resolve conflicts but has low latency. **CRDTs** allow decentralized resolution where every node eventually converges mathematically without a central coordinator. For offline editing, I would choose **CRDTs** because they excel at merging divergent states once connectivity is restored.

**AA20** — Challenges include maintaining trace IDs across boundaries. Use **W3C Trace Context** for standardization. **Head-based sampling** decides to trace at the start; **Tail-based** decides after seeing the whole trace (better for finding errors). In Kafka, you must inject the trace context into the message headers to ensure continuity when the consumer picks up the task.

## On-Premise Infrastructure Architecture

**OP1** — Type 1 runs directly on hardware (e.g., ESXi, Xen); Type 2 runs on an OS (e.g., VirtualBox, VMware Workstation).

**OP2** — SAN provides block-level storage (Fibre Channel/iSCSI) for high performance; NAS provides file-level storage (NFS/SMB) for easy sharing.

**OP3** — Traditional 3-tier uses Core/Dist/Access. Leaf-Spine connects every leaf switch to every spine switch, providing predictable latency and massive east-west bandwidth, solving the bottleneck of traditional hierarchical models.

**OP4** — Requires $\ge$ 3 nodes for quorum. Shared storage (Ceph/iSCSI) allows VMs to migrate. Fencing (STONITH) is required to kill a "zombie" node during failure. If a node fails, Corosync detects loss of heartbeat, fencing triggers, and the cluster restarts affected VMs on healthy nodes.

**OP5** — VLAN trunking carries multiple VLANs over one link using **802.1Q** tags. In Linux, you configure this via sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — RAID 1 (Mirror), 5 (Parity, 1 drive loss), 6 (Double parity, 2 drives), 10 (Striped mirror), Z2 (ZFS double parity). For a database server with 6 drives, I'd choose **RAID 10** for the best balance of high IOPS performance and fault tolerance.

**OP7** — Use **Split-horizon DNS** to serve different IPs to internal vs external users. The DMZ uses authoritative servers; internal clients use recursive resolvers. Laptops moving between office/VPN trigger DHCP updates or conditional forwarding based on their current network location.

**OP8** — Root CA (offline/self-signed) $\rightarrow$ Subordinate CA (issues certs) $\rightarrow$ End Entity. CRL/OCSP checks validity. A compromised subordinate is localized; a compromised root destroys the entire trust chain.

**OP9** — MPLS (reliable/expensive); IPsec VPN (cheap/internet dependent); SD-WAN (flexible/managed); WireGuard (fast mesh). For latency-sensitive VoIP across small sites, I recommend **SD-WAN** due to its ability to prioritize traffic and optimize paths.

**OP10** — Out-of-band management allows hardware control even if the OS is dead. If exposed to the internet, an attacker can gain full physical-level control over your servers via IPMI commands.

**OP11** — LVM (standard block), LVM-Thin (space-efficient snapshots), ZFS (Copy-on-Write filesystem with integrated volume management). LVM-Thin and ZFS provide much more efficient snapshotting than standard LVM.

**OP12** — Requires low RTT (<5ms). Use Ceph CRUSH rules to ensure replicas are in different failure domains. 2-site setups need a "witness" node at a 3rd site to prevent split-brain (where both sites think they are primary because they lost contact).

**OP13** — DORA: Discover $\rightarrow$ Offer $\rightarrow$ Request $\rightarrow$ Acknowledge. If the server is down and lease expires, the client falls back to APIPA (169.254.x.x) and loses network access.

**OP14** — Managed switches allow VLANs, SNMP, Spanning Tree, and security policies; unmanaged are simple plug-and-play devices for home use.

**OP15** — NTP synchronizes clocks. Clock drift causes authentication failures (Kerberos/certificates), log correlation issues, and database replication errors in distributed clusters.

**OP16** — Physical = full hardware power; VM = isolated OS; Container = shared kernel efficiency. Run on bare metal when you need zero virtualization overhead or extreme deterministic performance.

**OP17** — UPS provides short-term battery backup; Generator provides long-term power. An ATS automatically switches the load from mains to generator during an outage.

**OP18** — Active-Passive has one standby; Active-Active shares load. In HA with Pacemaker/Corosync, Corosync manages membership, while Pacemaker handles resource movement. Fencing (STONITH) ensures a failed node cannot write data after failover.

**OP19** — 3-2-1: 3 copies, 2 media types, 1 offsite. RPO is max allowable data loss; RTO is max allowable downtime. Immutable backups protect against ransomware. Backup is copying data; Disaster Recovery is the entire process of restoring service.

**OP20** — Supplicant (client), Authenticator (switch), Auth Server (RADIUS). EAP-TLS uses certificates (strong); PEAP uses passwords (weaker). MAB allows non-802.1X devices (like printers) to connect based on their MAC address.
