## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking (e.g., AWS EC2). You manage OS and apps. **PaaS (Platform as a Service):** Provides a platform for deployment without managing underlying infrastructure (e.g., Heroku or Azure App Service). You manage only code/data. **SaaS (Software as a Service):** Fully managed software delivered over the web (e.g., M365 or Salesforce). You manage only configuration/users.

**CL2** — The model defines who manages what. 
* **IaaS VMs:** Provider manages hardware/virtualization; you manage OS, middleware, data, and apps. 
* **Managed Kubernetes:** Provider manages control plane; you manage worker nodes (partially) and workloads. 
* **SaaS (M365):** Provider manages everything; you manage identity and data access settings.

**CL3** — A **VPC** is your private network. A **Subnet** is a range of IP addresses within that VPC. A **Security Group (SG)** acts as a firewall at the instance level (stateful), while a **NACL** acts as a firewall at the subnet level (stateless). They layer such that traffic must pass through both. **Stateful filtering (SG)** remembers connection state (if inbound is allowed, outbound is automatically allowed); **Stateless filtering (NACL)** requires explicit rules for both directions.

**CL4** — A **Landing Zone** is a pre-configured multi-account environment. **Organizational Units (OUs)** group accounts by function (Prod, Dev). **Guardrails** are SCPs (Service Control Policies) that restrict actions. **Shared Networking** uses Transit Gateway or Hub-and-Spoke to centralize egress/ingress. **Centralized Logging** aggregates logs into a security account. A single-account approach is problematic due to "blast radius" (one error affects everything), lack of isolation, and difficulty in scaling permissions.

**CL5** — IaC automates infrastructure provisioning via code. 
* **Terraform/OpenTofu:** Declarative, provider-agnostic, industry standard. Use for general infra.
* **Pulumi:** Uses general-purpose languages (Python, TS). Use when developers want to use familiar logic.
* **CloudFormation/Bicep:** Cloud-native (AWS/Azure). Use for deep integration with specific cloud services.
* **Crossplane:** Kubernetes-native; manages cloud resources as K8s objects. Use for GitOps-driven platform engineering.

**CL6** — **HPA** scales pods based on CPU/RAM. **VPA** adjusts pod resource requests/limits. **Cluster Autoscaler** adds/removes nodes to the cluster. **KEDA** provides event-driven autoscaling (e.g., scale based on Kafka lag). Use KEDA over HPA when you need to scale based on external metrics rather than just resource utilization.

**CL7** — **RPO (Recovery Point Objective)** is max data loss allowed; **RTO (Recovery Time Objective)** is max downtime allowed. 
* **Active-Passive:** Primary site handles traffic; secondary sits idle or in standby. 
* **Active-Active:** Both sites serve traffic simultaneously. 
* **Replication:** Sync (zero data loss, high latency) vs Async (low latency, potential data loss). 
* **DNS Failover:** Route53 health checks redirecting traffic. 
* **DR Types:** *Pilot Light* (minimal core services running); *Warm Standby* (scaled-down version of full environment ready); *Multi-site Active-Active* (full capacity in both regions).

**CL8** — GitOps uses Git as the "single source of truth." **ArgoCD** and **FluxCD** synchronize the cluster state with Git. Secrets are handled via **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault/AWS SM), or direct **Vault** integration. If manual drift occurs, the GitOps controller detects the mismatch and automatically overwrites the manual change to match the Git repository ("self-healing").

**CL9** — Use a **StatefulSet** for stable network IDs and ordered deployment. Provision **PVs/PVCs** using a **Local Storage Class** for low latency. A **Headless Service** provides direct pod IP addressing. Use **Init Containers** to prepare filesystems. Mount **ConfigMaps** as volumes for specific paths. Implement **Pod Disruption Budgets (PDB)** to ensure availability during maintenance.

**CL10** — A **Service Account** is K8s identity; **Workload Identity** maps that K8s identity to a Cloud IAM role. **IRSA** is AWS's implementation of this mapping. Mounting long-lived credentials (JSON keys) in pods is bad because they can be stolen and leaked. **Workload Identity Federation** solves this by using OIDC tokens to exchange K8s identity for short-lived cloud credentials, eliminating static secrets.

**CL11** — **Object (S3):** Unstructured data, high scale, via API. **Block (EBS):** Low-latency, attached to single instances. **File (EFS):** Shared filesystem for multiple instances. Object storage has highest durability ($11 \times 9$s); Block/File have higher availability but lower scalability.

**CL12** — Traditional security relies on a "crunchy exterior" (perimeter). Zero Trust assumes the network is compromised. Design: **Network Policies** (micro-segmentation), **Service Mesh with mTLS** (identity-based encryption), **Admission Controllers** (policy enforcement like Kyverno), **Image Signing** (provenance), **Runtime Security** (Falco detecting anomalies), and **Pod Identity**. It moves security from the IP level to the Workload/Identity level.

**CL13** — A **CDN** caches content at edge locations closer to users. Works via DNS redirection to the nearest PoP (Point of Presence). Examples: **CloudFront (AWS)** or **Azure Front Door**. Use a CDN when you need low latency for global users or to offload origin server load; serve directly if content is highly dynamic/private and changes per request.

**CL14** — **Regions** are geographic areas; **Availability Zones (AZs)** are isolated data centers within regions. Deploy across multiple AZs for high availability against local failures. **Zonal resources** exist in one AZ (e.g., EBS); **Regional resources** span all AZs in a region (e.g., S3, VPC).

**CL15** — Managed DBs handle patching, backups, scaling, and high availability. On a VM, *you* do everything. The provider handles hardware, OS patching, automated snapshots, and multi-AZ failover orchestration.

**CL16** — **IAM Users:** People/Apps. **Groups:** Collections of users. **Roles:** Temporary identities assumed by entities. **Policies:** JSON documents defining permissions. **Least Privilege:** Granting only the minimum permission required for a task. Apply it by using granular policies instead of `AdministratorAccess`.

**CL17** — Serverless runs code in response to events without managing servers. Examples: **Lambda**, **Azure Functions**, **GCF**. **Cold Starts** occur when an idle function must spin up a new container instance, causing latency. Use serverless for intermittent/event-driven tasks; avoid if you need consistent low-latency or long-running processes.

**CL18** — **Ingress Resource:** Standard K8s API for L7 routing. **Gateway API:** Next-gen, expressive, role-oriented (Infrastructure vs App dev). **Cloud LB Annotations:** Uses cloud-specific settings on Ingress. **Service Mesh Gateway:** Handles complex mTLS/routing. TLS terminates at the Load Balancer or Ingress Controller. Use **Gateway API** over Ingress for better separation of concerns and advanced traffic splitting.

**CL19** — 
* **Optimization:** Use **Reserved Instances/Savings Plans** for predictable loads; **Spot Instances** for stateless/fault-tolerant workloads. 
* **Right-sizing:** Match instance size to actual usage. 
* **Storage Tiering:** Move old data to S3 Glacier/Archive. 
* **FinOps:** Implement tagging for **Showback/Chargeback** (allocating costs to specific teams). 
* **Tools:** AWS Cost Explorer, Azure Cost Management, CloudHealth.

**CL20** — Multi-cloud avoids lock-in but adds complexity. Strategy: Use **Kubernetes** as a common runtime, **Terraform** for IaC, and **Identity Federation** (OIDC) across clouds. Connect via **VPN or Interconnect**. It is justified if you need high availability across providers or regulatory compliance, but often unnecessary due to "lowest common denominator" syndrome where you can't use provider-specific innovations.

## OT Infrastructure Architecture

**OT1** — The Purdue Model segments industrial networks. 
* **Level 0:** Physical process (sensors/actuators). 
* **Level 1:** Basic Control (PLCs). 
* **Level 2:** Area Supervisory (HMIs/SCADA). 
* **Level 3:** Site Operations (Historians/MES). 
* **Level 4/5:** Enterprise/Cloud (ERP/Internet).

**OT2** — IT focuses on Data Confidentiality; OT focuses on Process Availability/Safety. You cannot apply standard IT patching because OT systems are sensitive to latency/jitter, and unexpected reboots can cause physical damage or safety hazards.

**OT3** — An **IDMZ** sits between Level 3 and Level 4. It acts as a buffer so no direct connection exists between the enterprise and control zones. Only specific, inspected traffic (e.g., data from Historian to ERP) should pass through proxies in the IDMZ. Direct L4 $\to$ L1 connectivity is dangerous because it bypasses all segmentation, allowing malware to jump directly into critical controls.

**OT4** — 
1. **Modbus TCP:** Level 1-2 (Legacy/Simple). 
2. **OPC UA:** Level 2-3 (Modern interoperability). 
3. **EtherNet/IP:** Level 1-2 (Industrial Ethernet). 
4. **PROFINET:** Level 1-2 (Real-time automation). 
5. **MQTT:** Level 3+ (Edge-to-cloud telemetry).

**OT5** — A **Data Diode** is hardware that allows data to flow only one way (physically impossible for return signal), providing absolute isolation. A **Firewall** is software-based and bidirectional; if misconfigured, it can be bypassed. Use a diode when protecting high-consequence safety systems where zero inbound risk is required.

**OT6** — Data Flow: Sensor $\to$ PLC $\to$ OPC UA Server $\to$ Edge Gateway $\to$ MQTT Broker $\to$ Cloud Ingestion. Security boundaries are placed at the **IDMZ** and between the **Edge Gateway** and the external network.

**OT7** — **IEC 62443** defines **Zones** (groupings of assets with similar security needs) and **Conduits** (the communication paths between zones). 
* *Model:* [Corporate Zone] $\leftrightarrow$ Conduit $\leftrightarrow$ [IDMZ] $\leftrightarrow$ Conduit $\leftrightarrow$ [SCADA/HMI Zone] $\leftrightarrow$ Conduit $\leftrightarrow$ [PLC/Control Zone]. Safety Systems (SIS) should be in their own isolated zone.

**OT8** — Segment via **VLANs** per production line. Place **Industrial Firewalls** between lines and between OT/IT. Use managed switches with ACLs. For remote access, use a **Jump Host** in the IDMZ with MFA. Transition strategy: Implement "Monitor Mode" first to map traffic before enforcing blocking rules to avoid downtime.

**OT9** — **BPCS** controls the process; **SIS** is an independent layer designed to prevent catastrophic failure (e.g., explosions). **IEC 61511** governs functional safety. SIS must be isolated because if ransomware hits the BPCS, it could manipulate setpoints; if it reaches the SIS, it can disable the emergency shutdown, leading to physical disaster.

**OT10** — **PLC:** Single device for logic control. **DCS:** Distributed system for large-scale complex processes. **SCADA:** Supervisory system for geographically dispersed assets. They coexist: SCADA supervises multiple DCS or PLC clusters.

**OT11** — Remote access requires a **Jump Host** in the IDMZ, mandatory **MFA**, full **Session Recording**, and strictly **Time-limited** windows. Direct RDP to an HMI is unacceptable as it provides an unmonitored, direct path into the control loop from the IT network.

**OT12** — **Detection:** Use OT-specific IDS/Anomaly detection. **Response:** Isolate compromised segments via firewalls, initiate incident response protocols, coordinate with operators to move to "Safe State." The **Plant Operator's** role is critical: they decide whether to continue production or perform an emergency shutdown based on process stability.

**OT13** — An **HMI** allows operators to interact with the process (visualize data). An **Engineering Workstation** is used by engineers to program PLCs/logic.

**OT14** — A **Historian** records time-series process data. A **Plant Historian (L3)** stores high-resolution local data; an **Enterprise Historian (L4)** aggregates summarized data for business analytics.

**OT15** — **Ladder Logic** is a graphical programming language executed by a **PLC**. It remains dominant because it is intuitive for electricians/engineers and highly reliable for sequential logic.

**OT16** — An **RTU** is designed for long-distance telemetry in harsh environments (e.g., remote pipelines) with low power/bandwidth. A **PLC** is more robust for localized, high-speed factory automation.

**OT17** — **Analog signals** represent continuous values. **4-20mA** is preferred over 0-20mA because if the wire breaks, the signal drops to 0mA, which can be immediately detected as a "fault" rather than a valid reading of zero.

**OT18** — Asset inventory is foundational because you cannot protect what you don't know exists. Use **Passive Monitoring** (sniffing traffic) to avoid disruption. **Active Scanning** is dangerous in OT because legacy devices may crash when receiving unexpected packets or high volumes of traffic.

**OT19** — **MITRE ATT&CK for ICS** focuses on physical process impact. 
* *Tactics:* Inhibit Response Function, Impair Process Control, etc. 
* *Techniques:* Brute force, Firmware modification. 
It differs from Enterprise by focusing on the *physical consequence*. It helps identify gaps where an attacker could manipulate hardware directly.

**OT20** — Design: Collect logs via passive taps $\to$ SIEM. Integrate with IT SOC but use **OT-specific rules** (e.g., unauthorized PLC write). Staffing requires both IT analysts and OT engineers. For firmware alerts: Treat as critical; verify with operators before any remote action. False positives are handled through baseline tuning.
