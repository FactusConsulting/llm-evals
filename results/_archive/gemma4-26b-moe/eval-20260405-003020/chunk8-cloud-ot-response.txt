## Cloud Infrastructure Architecture

**CL1**
*   **IaaS (Infrastructure as a Service):** Provides raw computing resources (VMs, storage, networking). You manage the OS, middleware, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying OS/runtime. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Provides a complete software product managed by the provider. *Example: Microsoft 365.*

**CL2**
The provider is responsible for the security **of** the cloud (physical hardware, global infrastructure); the customer is responsible for security **in** the cloud (data, configurations, IAM).
*   **IaaS VMs:** Provider handles physical host/hypervisor; Customer handles OS patching, firewall rules, and application security.
*   **Managed Kubernetes:** Provider handles Control Plane availability/scaling; Customer handles worker node configurations, pod security, and application code.
*   **SaaS (M365):** Provider handles almost everything (infrastructure, OS, app code); Customer handles identity/access management and data classification.

**CL3**
*   **VPC (Virtual Private Cloud):** An isolated logical network in the cloud.
*   **Subnet:** A range of IP addresses within a VPC used to segment resources.
*   **Security Group (SG):** A virtual firewall for **instances** (e.g., VMs/Pods). It is **stateful** (if you allow inbound traffic, outbound response is automatically allowed).
*   **NACL (Network ACL):** A firewall for **subnets**. It is **stateless** (you must explicitly define both inbound and outbound rules).
*   **Layering:** Traffic hits the NACL first (subnet boundary), then the Security Group (resource boundary).

**CL4**
*   **Landing Zone:** A pre-configured, multi-account environment following best practices for security and compliance.
*   **Organizational Units (OUs):** Logical groupings of accounts (e.g., Prod, Dev, Security) to apply hierarchical policies.
*   **Guardrails:** Service Control Policies (SCPs) or Azure Policies that set boundaries on what accounts can do.
*   **Shared Networking:** Using a Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize inspection and connectivity between VPCs/VNets.
*   **Centralized Logging:** Aggregating logs (CloudTrail, Flow Logs) into a dedicated security account.
*   **Single-Account Problem:** Lack of blast radius isolation, difficulty in applying granular permissions, and hitting resource limits (quotas).

**CL5**
*   **IaC:** Managing and provisioning infrastructure through machine-readable definition files rather than manual processes.
*   **Terraform/OpenTofu:** Declarative, provider-agnostic, uses HCL. Best for multi-cloud/complex orchestration.
*   **Pulumi:** Uses general-purpose languages (Python, Go). Best for developers wanting programmatic logic.
*   **CloudFormation/Bicep:** Cloud-native, deep integration with AWS/Azure. Best for single-cloud, "set and forget" infra.
*   **Crossplane:** Kubernetes-native IaC. Best for managing cloud resources via K8s APIs/CRDs.

**CL6**
*   **HPA (Horizontal Pod Autoscaler):** Scales the number of **pods** based on CPU/RAM or custom metrics.
*   **VPA (Vertical Pod Autoscaler):** Adjusts the **CPU/RAM requests/limits** of existing pods.
*   **Cluster Autoscaler:** Scales the number of **nodes** in the cluster when pods cannot be scheduled.
*   **KEDA (Kubative Event-Driven Autoscaling):** Scales pods based on **external events** (e.g., RabbitMQ queue length, Kafka lag).
*   **KEDA vs HPA:** Use KEDA when scaling depends on something other than resource metrics (e.g., "scale to zero" when a queue is empty).

**CL7**
*   **RPO (Recovery Point Objective):** Max acceptable data loss. **RTO (Recovery Time Objective):** Max acceptable downtime.
*   **Active-Active:** Traffic flows to both regions simultaneously. Lowest RTO/RPO, highest cost.
*   **Active-Passive:** One region is standby. Higher RTO/RPO, lower cost.
*   **Replication:** *Sync* (zero data loss, high latency) vs. *Async* (potential data loss, low latency).
*   **DNS Failover:** Route53/Traffic Manager redirects traffic to the healthy region.
*   **DR Types:**
    *   **Pilot Light:** Minimal version of environment (DB only) is running; others are provisioned on failover.
    *   **Warm Standby:** A scaled-down but functional version of the environment is always running.
    *   **Multi-site Active-Active:** Full capacity in both regions; seamless failover.

**CL8**
*   **GitOps:** Using Git as the "Single Source of Truth" for infrastructure and app state.
*   **ArgoCD vs FluxCD:** ArgoCD provides a powerful UI and multi-cluster management; FluxCD is more lightweight, CLI-driven, and follows a "pull" model more strictly.
*   **Secrets:** Never store raw secrets in Git. Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (pulls from AWS Secrets Manager/Vault), or **Vault** directly.
*   **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and automatically overwrites the manual change to match the Git state.

**CL9**
*   **StatefulSet:** Ensures pods have stable, unique network identifiers and persistent storage mapping.
*   **PV/PVC + Local Storage:** Use a `Local` StorageClass for low-latency NVMe/SSD; PVCs bind to specific PVs.
*   **Headless Service:** Provides direct Pod IPs via DNS for peer discovery (essential for stateful clusters).
*   **Init Containers:** Run setup scripts (e.g., permission changes on mounted volumes) before the main app starts.
*   **ConfigMaps:** Mounted as volumes to place files at specific paths (e.g., `/etc/app/config.yaml`).
*   **Pod Disruption Budget (PDB):** Ensures a minimum number of pods remain available during voluntary disruptions (e.g., node upgrades).

**CL10**
*   **Service Account:** A K8s identity for processes within a pod.
*   **Workload Identity / IRSA:** A mechanism to map a K8s Service Account to a Cloud IAM Role.
*   **Why not mount credentials?** Mounting static IAM keys in a pod is a massive security risk (leakage, hard to rotate).
*   **Workload Identity Federation:** Uses OIDC to allow the cloud provider to trust the K8s cluster. The pod exchanges a K8s token for a short-lived cloud IAM token, eliminating static secrets.

**CL11**
*   **Object (S3/Blob):** Unstructured data (images, backups). Highly durable ($11 \times 9$s). Use for massive scale/web content.
*   **Block (EBS/Managed Disk):** Raw volumes attached to VMs. Low latency. Use for databases or OS drives.
*   **File (EFS/Azure Files):** Shared filesystem (NFS/SMB). Use for shared config or legacy apps needing a shared drive.
*   **Durability/Availability:** Object is highest durability; Block is highest performance/low latency; File is optimized for concurrent access.

**CL12**
*   **Zero-Trust Architecture:** "Never trust, always verify."
*   **Components:**
    *   **Network Policies:** L3/L4 pod-to-pod isolation.
    *   **Service Mesh (mTLS):** L7 identity and encryption between services.
    *   **Pod Identity:** Using Workload Identity instead of secrets.
    *   **Admission Controllers:** Enforcing policies (e.g., "no root containers") via OPA/Kyverno.
    *   **Image Signing:** Ensuring only trusted images run (Cosign).
    *   **Runtime Security:** Detecting anomalous behavior (Falco).
*   **Difference:** Traditional security relies on a "hard shell" (perimeter) and "soft center." Zero-trust assumes the perimeter is already breached and secures every single interaction.

**CL13**
*   **CDN:** A distributed network of proxy servers that cache content closer to users.
*   **How it works:** User requests content $\rightarrow$ DNS routes to nearest Edge Location $\rightarrow$ Edge serves cached content or fetches from Origin.
*   **Services:** AWS CloudFront, Azure Front Door.
*   **When to use:** Use CDN for static assets (JS, CSS, Images) or to reduce latency/DDoS risk. Serve directly from origin only for highly dynamic, non-cacheable, or low-traffic internal APIs.

**CL14**
*   **Region:** A geographic area containing multiple Availability Zones.
*   **Availability Zone (AZ):** One or more isolated data centers with independent power/cooling.
*   **Why multi-AZ?** To protect against a single data center failure (fire, power outage).
*   **Zonal vs. Regional:** Zonal resources (e.g., an EBS volume) exist in one AZ. Regional resources (e.g., S3, IAM) are distributed across the entire region.

**CL15**
*   **Managed DB:** A service where the provider manages the database engine.
*   **Provider handles:** Hardware, OS patching, DB engine patching, automated backups, high availability/failover, and physical scaling.
*   **Self-managed VM:** You must manually handle all the above, plus OS hardening and complex replication setups.

**CL16**
*   **IAM User:** A permanent identity for a person/app.
*   **IAM Group:** A collection of users for easier permission management.
*   **IAM Role:** A temporary identity assumed by a user or service (no long-term credentials).
*   **IAM Policy:** A JSON document defining permissions (Allow/Deny).
*   **Least Privilege:** Giving a user/service *only* the permissions required to perform its task. Apply via granular policies and regular access reviews.

**CL17**
*   **Serverless:** An execution model where the provider manages the server allocation and scaling.
*   **Comparison:** Lambda (AWS), Functions (Azure), Cloud Functions (GCP). They are functionally similar but differ in trigger types and ecosystem integration.
*   **Cold Starts:** The latency incurred when the provider spins up a new container instance to handle a request. Matters for latency-sensitive apps.
*   **Poor Fit:** Long-running processes (e.g., video encoding), heavy stateful apps, or workloads with extremely high, constant traffic where provisioned servers are cheaper.

**CL18**
*   **Ingress Resource:** Standard K8s API for L7 routing rules.
*   **Gateway API:** The modern successor to Ingress; provides more expressive, role-oriented configuration (separating infra from routing).
*   **Cloud LB Annotations:** Using annotations to trigger a cloud provider's Load Balancer (e.g., AWS NLB) to act as the Ingress.
*   **Service Mesh Ingress:** Using a mesh (Istio) to handle entry into the cluster.
*   **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Service Mesh sidecar.
*   **Gateway API vs Ingress:** Use Gateway API for better separation of concerns (Platform Eng vs App Dev) and more advanced routing capabilities.

**CL19**
*   **Optimization:**
    *   **RI/Savings Plans:** Commit to usage for lower rates (good for steady state).
    *   **Spot/Preemptible:** Use spare capacity for massive discounts (good for stateless/batch).
    *   **Right-sizing:** Matching instance size to actual utilization.
    *   **Storage Tiering:** Moving old data to S3 Glacier/Archive.
    *   **FinOps:** Implementing a culture of cost accountability.
*   **Tools/Process:** Implement tagging (for chargeback), AWS Cost Explorer/Azure Cost Management, and automated "janitor" scripts to kill idle resources.

**CL20**
*   **Strategy:** Use Kubernetes (abstraction), Terraform (IaC), and OIDC (Identity) to minimize provider-specific code.
*   **Networking:** Use VPN or dedicated interconnects (DirectConnect/ExpressRoute) for cross-cloud communication.
*   **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs.
*   **Justification:** Justified for extreme availability requirements or regulatory compliance. Unnecessary if the goal is simply "not being locked in," as the cost of abstraction often outweighs the benefit.

## OT Infrastructure Architecture

**OT1**
The Purdue Model segments industrial networks into levels:
*   **Level 0:** Physical process (sensors, motors, actuators).
*   **Level 1:** Basic Control (PLCs, RTUs).
*   **Level 2:** Area Supervisory Control (HMIs, SCADA).
*   **Level 3:** Site Operations (Historians, MES).
*   **Level 4/5:** Enterprise/Business (ERP, IT networks).

**OT2**
*   **IT:** Focuses on Confidentiality, Integrity, and Availability (CIA). High change frequency.
*   **OT:** Focuses on Availability, Integrity, and Safety (AIS). High uptime requirements.
*   **Patching:** You cannot patch OT systems like IT because a reboot or a software change can cause physical instability, equipment damage, or safety hazards.

**OT3**
*   **IDMZ:** A buffer zone between IT and OT.
*   **Traffic:** Only highly inspected, proxied traffic (e.g., data from Historian to ERP) should cross.
*   **Danger:** Direct L4-to-L1 connectivity allows a compromised IT workstation to send malicious commands directly to a PLC, bypassing all safety controls.

**OT4**
1.  **Modbus TCP:** Level 1/2 (Fieldbus/Control).
2.  **OPC UA:** Level 2/3 (Supervisory/Interoperability).
3.  **EtherNet/IP (CIP):** Level 1/2 (Control/I/O).
4.  **PROFINET:** Level 1/2 (Real-time Control).
5.  **MQTT:** Level 3/4 (IIoT/Cloud connectivity).

**OT5**
*   **Data Diode:** A hardware device that allows data to flow in only one direction (physical light/fiber isolation). Use for sending data from OT to IT without any possibility of return.
*   **Firewall:** Software-based; allows bidirectional traffic based on rules.
*   **Limitation:** Firewalls can be misconfigured or hacked; Data Diodes are physically incapable of bidirectional communication.

**OT6**
*   **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway (with firewall/diode) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud.
*   **Security:** Place the primary boundary at the IDMZ between the Historian (L3) and the Edge Gateway.

**OT7**
*   **Zone:** A logical grouping of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Model:**
    *   **Zone 1:** SIS (Highest isolation).
    *   **Zone 2:** PLCs/Control.
    *   **Zone 3:** SCADA/HMI.
    *   **Zone 4:** Corporate.
    *   **Conduits:** All communication between these must pass through a firewall/inspection point.

**OT8**
*   **Strategy:** Segment by production line using VLANs.
*   **Architecture:** Use Industrial Managed Switches. Place a firewall between the Plant Floor (L2) and the IDMZ (L3).
*   **Remote Access:** Use a Jump Host in the IDMZ with MFA.
*   **Transition:** Use "Monitor Mode" on switches first to map traffic before enforcing blocking rules to avoid production downtime.

**OT9**
*   **SIS:** Independent system designed to prevent catastrophic failure (e.g., emergency shutdown).
*   **BPCS:** The system that actually runs the process.
*   **IEC 61511:** The standard for functional safety in the process industry.
*   **Isolation:** SIS must be isolated so a compromise of the BPCS (via ransomware) cannot disable the safety shutdown mechanism. If SIS is hit, the plant loses its "last line of defense."

**OT10**
*   **PLC:** Small, rugged controller for local logic (Level 1).
*   **DCS (Distributed Control System):** Large-scale, integrated system for entire plants (Level 2).
*   **SCADA:** Supervisory system for monitoring/controlling geographically dispersed assets (Level 2/3).
*   **Coexistence:** Yes, they often work together (SCADA monitors the DCS/PLCs).

**OT11**
*   **Architecture:** Remote user $\rightarrow$ VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (in IDMZ) $\rightarrow$ HMI/Engineering Workstation.
*   **Why not RDP to HMI?** It bypasses all segmentation, provides no audit trail, and exposes the most critical control interfaces directly to the IT network.

**OT12**
*   **Detection:** Deploy passive IDS (e.g., Dragos, Nozomi) to monitor traffic without injecting packets.
*   **Response:** Isolate the compromised segment via firewall rules. Coordinate with operators to move the process to a "Safe State."
*   **Operator Role:** The operator is the ultimate authority; they decide if the process can continue or must be manually shut down for safety.

**OT13**
*   **HMI:** A visual interface for operators to monitor and control the process.
*   **Engineering Workstation:** A specialized PC used to program PLCs and configure the control system.

**OT14**
*   **Historian:** A database that records time-series process data.
*   **Importance:** Essential for troubleshooting, regulatory compliance, and optimization.
*   **Difference:** Plant Historian (L3) is for real-time/local control; Enterprise Historian
