### SC1
**SC1-A:** The pods are failing because the `Restricted` Pod Security Standard (PSS) requires that all containers run as a non-root user. While `runAsNonRoot: true` is set, the new Chainguard base image defaults to `USER root`. In `Baseline` mode, Kubernetes allows the container to run as root if the manifest doesn't explicitly forbid it. In `Restricted` mode, the admission controller enforces that a non-zero `runAsUser` must be specified in the `securityContext`. Since the images lack a `USER` directive and the manifests lack `runAsUser`, the Kubelet attempts to run the process as root, which violates the `Restricted` policy.

**SC1-B:**
```bash
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level:** Rebuild images to include a specific non-root user (e.g., `USER 1000`).
*   **Manifest:** Add `securityContext.runAsUser: 1000` to the Pod or Container spec.
*   **CI Gate:** Implement a `conftest` or `kyverno` policy check in the pipeline to validate that `runAsUser` is explicitly defined.
*   **Rollout:** Perform a `kubectl rollout restart deployment/<name>` for each service. Since it's a K8s deployment, the rolling update strategy will replace old pods with new ones, maintaining availability as long as `maxUnavailable` is configured.

### SC2
**SC2-A:** Stale data occurs because RDS Cross-Region Read Replicas use **asynchronous replication**. There is a physical delay (replication lag) between the primary WAL (Write Ahead Log) being written in `us-east-1` and applied in `eu-west-1`. If the primary fails, any WAL segments not yet shipped to the replica are lost. To quantify the loss, check the `ReplicaLag` metric in CloudWatch and inspect the last applied LSN (Log Sequence Number) on the replica vs. the old primary.

**SC2-B:**
1.  **Identify new ARN:** Get the ARN of the promoted instance.
2.  **Import:** `tofu import aws_db_instance.primary <new-arn>`
3.  **Update Code:** Replace the old hardcoded ARN with a variable or the new ARN in the Terraform files.
4.  **State Manipulation:** If the resource name in code must stay the same, use `tofu state rm aws_db_instance.old_instance` first, then `tofu import`.
5.  **Dependency Update:** Run `tofu plan` to ensure Security Groups and Route53 records are being updated to point to the new ARN rather than being recreated.

**SC2-C:**
*   **Architecture:** Use **Amazon Aurora Global Database**. It uses storage-level replication with latency typically < 1 second, providing much lower RPO than standard RDS.
*   **Connection:** Use **RDS Proxy** to handle connection pooling and provide a stable endpoint during failover.
*   **DNS:** Use **Route53 CNAME/Alias records** with health checks to point to the database endpoint; automate the record update via Lambda during failover.
*   **App Logic:** Implement exponential backoff and jitter in the application's connection logic.
*   **RPO < 1s:** Aurora Global Database is the only way to achieve this reliably across regions.

### SC4
**SC4-A:**
1.  **Sticky Sessions:** K8s Services are load-balanced per request. **Solution:** Use an Ingress Controller (NGINX/Istio) with session affinity enabled.
2.  **Local File Storage:** Pods are ephemeral. **Solution:** Migrate `/data/uploads` to a Persistent Volume (PV) using a CSI driver (e.g., EFS or NFS).
3.  **Oracle/Mainframe Connectivity:** K8s pods need stable egress. **Solution:** Use a dedicated Egress Gateway or VPN/DirectConnect to reach on-prem resources.
4.  **Memory-based Sessions:** Pod restarts wipe sessions. **Solution:** Externalize sessions to Redis or Memcached.
5.  **Monolith Size:** Large startup times cause Liveness/Readiness probe failures. **Solution:** Tune `initialDelaySeconds` and optimize the JVM startup.

     AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid

JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid

**SC6-C:**

### SC7
**SC7-A:**
*   **Manual Tofu:** Causes "State Drift." If an engineer changes a resource manually, the next `tofu apply` might destroy/recreate it to match the code.
*   **Helm Divergence:** Makes environments non-reproducible. A "fix" in Prod might not exist in Staging, leading to failed deployments.
*   **Kubectl Edit:** Bypasses GitOps. The "Source of Truth" is no longer Git.
*   **No Locking:** If two engineers run `apply` simultaneously, the state file can become corrupted, leading to orphaned resources or complete state loss.

**SC7-B:**
```yaml
image: hashicorp/opentofu:latest

stages:
  - validate
  - plan
  - apply

validate:
  stage: validate
  script:
    - tofu fmt -check
    - tofu validate

plan:
  stage: plan
  script:
    - tofu plan -out=tfplan
  artifacts:
    paths: [tfplan]

apply:
  stage: apply
  script:
    - tofu apply tfplan
  when: manual
  environment: production
  # Backend configuration in tofu.tfvars would include:
  # backend "s3" { bucket = "my-state"; dynamodb_table = "tofu-lock" }
```

**SC7-C:**
*   **Drift Detection:** Schedule a GitLab CI job (`cron`) that runs `tofu plan -detailed-exitcode`. If it exits with `2` (drift detected), alert the team.
*   **Admission Control:** Use **Kyverno** to block `kubectl edit` on critical resources (e.g., `policy: validate, rule: deny-edit-configmap`).
*   **Structure:** Use **Helmfile** to define a base `values.yaml` and environment-specific `values-prod.yaml` overrides.
*   **RBAC:** In AWS, remove `AdministratorAccess` from developer roles; grant `AdministratorAccess` only to the GitLab Runner IAM Role. In K8s, use RBAC to restrict `edit` permissions to the CI ServiceAccount.
