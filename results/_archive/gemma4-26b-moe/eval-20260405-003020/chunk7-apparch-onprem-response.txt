## Application Architecture

**AA1** — A **monolith** is a single, unified unit where all components (UI, business logic, data access) are tightly coupled and deployed together. **Microservices** decouple these into independent, loosely coupled services communicating over a network.
*3 Problems introduced by microservices:* 1. **Network Latency/Complexity:** Inter-service calls add overhead. 2. **Distributed Consistency:** Managing transactions across databases is difficult. 3. **Observability:** Tracing a single request across many services is harder.

**AA2** — **Synchronous:** The caller sends a request and waits (blocks) for a response (e.g., REST/HTTP). **Asynchronous:** The caller sends a message and continues its work without waiting for an immediate response (e.g., RabbitMQ/AMQP).

**AA3** — A **Reverse Proxy** (e.g., Nginx) sits in front of servers to handle load balancing, SSL termination, and caching. An **API Gateway** (e.g., Kong, AWS API Gateway) adds application-level concerns like authentication, rate limiting, request transformation, and service discovery.
An API Gateway *can* replace a reverse proxy for external traffic, but a reverse proxy is often still used internally for low-level load balancing or as a lightweight entry point to the gateway itself.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. If one fails, "compensating transactions" undo the previous successful steps.
*   **Choreography:** Services exchange events without a central controller. Best for simple workflows with low coupling.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows where state management is critical.

**AA5** — **CQRS** separates the models for updating data (Commands) from the models for reading data (Queries). It is paired with **Event Sourcing** because Event Sourcing stores the state as a sequence of immutable events, which provides a perfect "audit log" to rebuild the read models.
*Problem solved:* It eliminates contention between reads and writes and allows for highly optimized, specialized read views that traditional CRUD (which uses the same model for both) cannot provide.

**AA6** — The **Circuit Breaker** prevents a system from repeatedly trying an operation that is likely to fail.
*   **Closed:** Requests flow normally; failures are tracked.
*   **Open:** The breaker "trips" after a threshold; requests fail immediately without hitting the service.
*   **Half-Open:** After a timeout, a limited number of requests are allowed through to see if the service has recovered.
*Difference:* A **retry with backoff** attempts to fix a transient error by trying again. A **Circuit Breaker** stops the attempts entirely to allow a failing service time to recover and to prevent "cascading failures." You use them together by wrapping a retry logic *inside* a circuit breaker.

**AA7** —
1. **Shared DB, Shared Schema:** *Lowest cost, highest density, lowest complexity.* However, it has the *highest security risk* (data leakage via bugs) and *highest noisy-neighbor risk* (one tenant's heavy query slows everyone).
2. **Shared DB, Separate Schema:** *Medium cost/complexity.* Better isolation than shared schema, but still shares the same DB engine resources (CPU/RAM).
3. **Separate DB per Tenant:** *Highest cost and operational complexity.* Provides the *highest security* and *lowest noisy-neighbor risk* because resources are physically isolated.

**AA8** — **Strong consistency** ensures all reads see the latest write immediately. **Eventual consistency** guarantees that if no new updates are made, eventually all accesses will return the last updated value.
*Architecture:* To prevent overselling, you need **Strong Consistency**.
*Stack:* Use a relational database (e.g., PostgreSQL) or a distributed KV store with linearizability (e.g., etcd/FoundationDB).
*Pattern:* Use **Distributed Locking** (e.g., Redlock via Redis) or **Atomic Increments/Conditional Updates** (e.g., `UPDATE inventory SET count = count - 1 WHERE id = X AND count > 0`) to ensure the decrement is atomic at the database level.

**AA9** — A **sidecar proxy** is a helper process running alongside a service in the same network namespace (e.g., a Pod). In **Istio**, **Envoy** acts as the sidecar (Data Plane) that intercepts all traffic. The **Control Plane** (IstioD) manages and distributes configuration/policies to the Envoy proxies.
*mTLS:* Application-level TLS secures the payload, but **mTLS between sidecars** provides automated certificate management, identity verification, and encryption of the *connection itself* without the application ever needing to handle certificates.

**AA10** — The **Strangler Fig pattern** involves placing a proxy in front of the monolith and gradually routing specific functionalities to new microservices until the monolith is "strangled" and can be decommissioned.
*Strategy:* 1. Identify a low-risk bounded context (e.g., "Notification Service"). 2. Build the new service in .NET 8. 3. Use an API Gateway/Reverse Proxy to route `/api/notifications` to the new service while all other traffic goes to the .NET Framework monolith. 4. Repeat for other modules.

**AA11** — 1. **Codebase:** One codebase per app (avoids massive monorepos). 2. **Dependencies:** Explicitly declare/isolate dependencies (prevents "it works on my machine"). 3. **Config:** Store config in the environment (allows same build in Dev/Prod). 4. **Builds:** One build/release pipeline (ensures consistency). 5. **Processes:** Run as one or more stateless processes (allows easy scaling). 6. **Disposability:** Fast startup/shutdown (enables rapid scaling/recovery).

**AA12** —
*   **Coupling:** Kafka is loosely coupled (producer doesn't know consumer); REST is tightly coupled (caller needs consumer address).
*   **Scalability:** Kafka scales via partitions; REST scales via load balancers.
*   **Debugging:** REST is easier (trace a single request); Kafka is harder (tracing asynchronous flows).
*   **Ordering:** Kafka provides ordering within a partition; REST has no inherent ordering.
*   **Failure:** Kafka provides durability (messages stay in log); REST requires the caller to handle retries.
*   *Choice:* Use **REST/gRPC** for real-time, request-response interactions (e.g., UI fetching a profile). Use **Kafka** for high-throughput, asynchronous workflows (e.g., processing orders, telemetry).

**AA13** — A **Load Balancer** distributes incoming network traffic across multiple servers.
*   **Layer 4 (Transport):** Routes based on IP and TCP/UDP ports. Fast, but "blind" to content.
*   **Layer 7 (Application):** Routes based on HTTP headers, cookies, or URL paths.
*   *Use Case:* Routing `example.com/images` to one server and `example.com/api` to another.

**AA14** — A **Message Queue** (RabbitMQ) is designed for "point-to-point" delivery where messages are deleted once consumed. A **Log-based Broker** (Kafka) is a distributed append-only log where messages persist and can be replayed by multiple consumers at different offsets.
*Pick RabbitMQ* for complex routing and task queuing. *Pick Kafka* for high-throughput event streaming and data replayability.

**AA15** — A **container** is an isolated user-space environment sharing the host OS kernel. A **VM** includes a full guest OS and runs on a hypervisor.
*Popularity:* Containers are lightweight, start instantly, and ensure "environment parity" (the same container runs on a laptop as in production), making them perfect for microservices.

**AA16** — **Stateless:** Does not store client data locally; every request contains all info needed (e.g., a REST API). **Stateful:** Stores data locally (e.g., a database or a session-heavy legacy app).
*Scaling:* Stateless services are easier to scale because any instance can handle any request; you just add more instances behind a load balancer.

**AA17** — An **ORM** maps database tables to programming objects. Examples: **Hibernate** (Java), **Entity Framework** (.NET).
*Trade-offs:* ORMs increase developer productivity and provide abstraction, but they can generate highly inefficient SQL and make complex joins/optimizations difficult compared to raw SQL.

**AA18** — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, the others continue to function (like compartments in a ship).
*Implementation:* 1. **Thread Pools:** Assign a dedicated thread pool to a specific downstream service so that if that service hangs, it only exhausts its own pool, not the entire application's thread pool. 2. **Deployment Groups:** Run critical services on separate hardware/clusters.

**AA19** — **OT** relies on a central server to transform operations to maintain consistency; it is complex to implement but handles high latency well. **CRDTs** are data structures that can be updated independently and merged without conflict; they are mathematically guaranteed to converge.
*Choice:* For **offline editing**, I would choose **CRDTs**. They allow users to make changes locally without a connection and merge them seamlessly once they reconnect, without needing a central server to "rebase" their changes.

**AA20** —
*   **Challenges:** Maintaining a single Trace ID across different protocols (HTTP to Kafka) and languages.
*   **Context Propagation:** Using headers (W3C Trace Context or B3) to pass the Trace ID.
*   **Sampling:** *Head-based* (decide at the start) vs. *Tail-based* (decide after the trace completes, useful for keeping only "error" traces).
*   **Kafka Continuity:** You must inject the trace context into the **Kafka Message Headers**. The consumer then extracts these headers to continue the span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., VMware ESXi, Xen). **Type 2 (Hosted):** Runs as an application on a host OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network):** Block-level storage (looks like a local disk) connected via Fibre Channel or iSCSI. Used for databases/VMs. **NAS (Network Attached Storage):** File-level storage (looks like a network folder) via NFS or SMB. Used for file sharing.

**OP3** — **3-Tier:** Core, Distribution, Access. **Leaf-Spine:** A two-tier architecture where every Leaf switch connects to every Spine switch.
*Problem solved:* Leaf-Spine provides predictable, low-latency "any-to-any" connectivity and scales horizontally much better than the hierarchical 3-tier model, which often suffers from bottlenecks at the core.

**OP4** —
*   **Architecture:** Minimum 3 nodes for quorum.
*   **Quorum/Fencing:** Use a "QDevice" or external witness to prevent split-brain. Use **STONITH** (Shoot The Other Node In The Head) via IPMI to fence a failed node.
*   **Storage:** **Ceph** is preferred for high availability as it is distributed.
*   **Failure:** If one node fails, the remaining two maintain quorum, and Ceph re-replicates data to maintain the desired redundancy level.

**OP5** — **VLAN Trunking** allows multiple VLANs to travel across a single physical link. **802.1Q** adds a "tag" to the Ethernet frame header to identify the VLAN.
*Linux Config:* Use `ip link add link eth0 name eth0.10 type vlan id 10` to create sub-interfaces for different VLANs.

**OP6** —
*   **RAID 1:** Mirroring (High safety, 50% capacity).
*   **RAID 5:** Parity (Good capacity/perf, can lose 1 drive).
*   **RAID 6:** Double Parity (Can lose 2 drives).
*   **RAID 10:** Mirroring + Striping (Best perf/safety, high cost).
*   **RAID Z2:** ZFS equivalent of RAID 6.
*   *Choice:* For a **database**, I would choose **RAID 10**. It provides the best write performance (no parity calculation overhead) and the fastest rebuild times, which is critical for database integrity.

**OP7** —
*   **Internal:** AD-integrated DNS for local resource resolution.
*   **DMZ:** Isolated DNS servers for public services.
*   **Split-Horizon:** Different DNS responses for internal vs. external queries for the same domain.
*   **DNSSEC:** Digitally signs records to prevent spoofing.
*   **Workflow:** A laptop on VPN uses the VPN's DNS settings (Conditional Forwarders) to reach internal AD DNS. When moving to the office, it uses DHCP to get local DNS settings.

**OP8** — **Chain of Trust:** Root CA signs Subordinate CA $\rightarrow$ Subordinate CA signs End-Entity.
*   **Deployment:** Root CA is kept **offline** (air-gapped). Subordinate CAs are online to issue certs.
*   **Revocation:** **CRL** is a list of revoked certs; **OCSP** is a real-time query for a specific cert's status.
*   **Compromise:** A compromised **Subordinate CA** is bad but can be revoked by the Root. A compromised **Root CA** is catastrophic; the entire PKI must be rebuilt from scratch.

**OP9** —
*   **MPLS:** High cost, high reliability, low latency, very secure, but rigid.
*   **IPsec VPN:** Low cost, uses public internet, variable latency/jitter.
*   **SD-WAN:** Software-defined, manages multiple paths (MPLS + Internet), highly flexible.
*   **WireGuard:** Extremely fast/secure, but requires manual mesh management.
*   *Recommendation:* **SD-WAN**. It can use a cheap internet link for general traffic and a reliable MPLS link for VoIP, dynamically switching based on real-time latency/jitter measurements.

**OP10** — **iDRAC/iLO/IPMI** are out-of-band management tools that allow remote access to hardware (power, BIOS, console) even if the OS is crashed.
*Criticality:* It allows remote recovery without physical presence.
*Risk:* If exposed to the internet, attackers can gain full hardware control, wipe drives, or brick the server.

**OP11** — **LVM:** Logical volume management for flexible partitioning. **LVM-Thin:** Allows over-provisioning of space. **ZFS:** A combined file system and volume manager with built-in RAID and data integrity.
*Snapshots:* LVM/LVM-Thin use "Copy-on-Write" (COW). ZFS uses "Redirect-on-Write" (more efficient for performance).

**OP12** —
*   **Strategy:** A **Stretch Cluster** spans two sites.
*   **Ceph:** Use **CRUSH rules** to ensure replicas are placed in different physical racks/sites.
*   **Latency:** Requires very low latency (usually <5ms) for synchronous replication.
*   **Split-Brain:** If the link between sites breaks, both sites might think they are the "master."
*   *Tiebreaker:* A 2-site cluster needs a **third site** (a lightweight witness/quorum node) to decide which site stays alive.

**OP13** — **DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge.
*Failure:* If the DHCP server is down, the client will eventually self-assign an **APIPA** address (169.254.x.x), which provides no network connectivity.

**OP14** — **Unmanaged:** Plug-and-play, no configuration. **Managed:** Allows configuration of VLANs, Spanning Tree, Port Security, and SNMP.
*Enterprise Importance:* Managed switches are essential for **VLAN segmentation** (security) and **Spanning Tree Protocol** (preventing loops).

**OP15** — **NTP** synchronizes clocks.
*Criticality:* Essential for log correlation (forensics) and security protocols (Kerberos/SSL).
*Drift:* If clocks drift, authentication (Kerberos) will fail, and distributed databases may suffer from data corruption or incorrect transaction ordering.

**OP16** — **Physical:** Hardware. **VM:** Hardware + Hypervisor + Guest OS. **Container:** Hardware + Host OS + Container Engine.
*Bare Metal:* Use for workloads requiring extreme performance/low latency (e.g., high-frequency trading, massive databases) where hypervisor overhead is unacceptable.

**OP17** — **UPS** provides immediate battery power for short-term outages (minutes). **Generator** provides long-term power (hours/days).
*ATS (Automatic Transfer Switch):* Detects power loss and automatically switches the load from the utility to the generator.

**OP18** — **Active-Passive:** One node is standby. **Active-Active:** Both nodes process traffic.
*PostgreSQL HA:* Use **Pacemaker/Corosync** to manage the cluster. **STONITH** (fencing) ensures the failed node is truly dead before the standby takes over. A **Virtual IP (VIP)** is used; the VIP moves from the failed node to the healthy node so the application doesn't need a config change.

**OP19** —
*   **3-2-1 Rule:** 3 copies of data, 2 different media, 1 offsite.
*   **RPO/RTO:** RPO (how much data you can lose); RTO (how long it takes to recover).
*   **Immutable Backups:** Backups that cannot be deleted or changed (essential for ransomware protection).
*   **Backup vs. DR:** Backup is the *copy of the data*; Disaster Recovery is the *entire plan/process* to restore operations.
*   *Testing:* You must perform regular **restoration drills**; a backup is useless if it cannot be restored.
