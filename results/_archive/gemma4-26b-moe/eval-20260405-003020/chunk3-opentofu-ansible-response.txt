## OpenTofu / Terraform

**T1:** `tofu plan` performs a "dry run" by refreshing state and comparing it against the current configuration to determine the execution plan. `tofu apply` executes the actions proposed in the plan to reach the desired state.

**T2:** State is a JSON file mapping real-world resources to your configuration. Remote state (e.g., S3) is critical for team collaboration, providing a "single source of truth," enabling state locking to prevent corruption, and keeping sensitive data out of local files.

**T3:** `count` uses an integer to create multiple instances, making it difficult to manage individual resource attributes if one is removed (it causes index shifts). `for_each` uses a map or set, allowing you to address each resource by a unique key. `for_each` is preferred when resources are not strictly identical or when you need to add/remove items without re-indexing others.

**T4:** OpenTofu detects "drift" during the next `plan` or `apply`. It refreshes the state by querying the cloud provider's API. If the real-world resource differs from the state, OpenTofu marks the resource for update or replacement to match the configuration.

**T5:**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

**T6:** `terraform_remote_state` reads the state file of another workspace. Output values are the mechanism used to expose data. The recommended alternative is to pass outputs from one module as inputs to another via the root module. This promotes better encapsulation and avoids tight coupling to the internal state structure of other modules.

**T7:** `null_resource` with `remote-exec` is a "provisioner," which runs during the *apply* phase. If a dependent resource requires an output from that `null_resource`, but the output is only calculated *after* the provisioner finishes, the dependency graph might attempt to resolve the output before the value is actually written to the state. **Fix:** Use a `provisioner "local-exec"` to write the kubeconfig to a file, or better, use a data source or a resource that natively supports the output to ensure the dependency is explicitly linked in the graph.

**T8:** `import` brings existing infrastructure under management by mapping a real ID to a resource address in code. **Limitations:** It doesn't generate code (pre-1.5) and requires manual configuration matching. The `import` block (1.5+) allows you to define imports in code, enabling `tofu plan` to show exactly what will happen and facilitating easier automation/refactoring.

**T9:** A **variable** (input) is a parameter used to customize configurations (e.g., instance size). An **output** is a value exported by a module or configuration to be used by other modules or displayed to the user.

**T10:** A provider is a plugin that enables OpenTofu to interact with specific APIs (AWS, Azure, etc.). If you run `plan` without `init`, OpenTofu will fail because it hasn't downloaded the necessary provider binaries to the `.terraform` directory.

**T11:** It contains the dependency lock for providers, ensuring all team members and CI/CD pipelines use the exact same provider versions. Committing it ensures reproducible environments and prevents "it works on my machine" issues caused by provider updates.

**T12:** `tofu destroy` removes all resources managed by the current configuration. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

**T13:** A data source allows you to fetch information from existing infrastructure that is *not* managed by your current OpenTofu code. **Example:** Fetching an existing VPC ID or an AMI ID created by a different team/project.

**T14:** `variables` are external inputs provided to the module. `locals` are internal, temporary values used to simplify expressions or avoid repetition within the module. Use `locals` for complex logic or derived values that should not be changed by the user.

**T15:** 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for minimizing downtime).
- `prevent_destroy`: Stops OpenTofu from destroying a resource (useful for critical databases).
- `ignore_changes`: Tells OpenTofu to ignore specific attribute updates (useful when an external process, like an Autoscaler, modifies a resource).

**T16:** The `moved` block allows you to rename a resource or move it into a module in the code without OpenTofu thinking the old resource was deleted and a new one created. It updates the state file to reflect the new address.

**T17:** OpenTofu builds a Directed Acyclic Graph (DAG) to determine the order of operations. **Implicit dependencies** are created when one resource references an attribute of another. **Explicit dependencies** are created using `depends_on`. `depends_on` forces a strict ordering, which can reduce parallelism (as OpenTofu cannot run those resources simultaneously). Use it sparingly to avoid unnecessary bottlenecks.

**T18:** 
1. **Break into smaller workspaces/states:** Reduces the size of the graph to process. (Tradeoff: Complexity in managing cross-state dependencies).
2. **Use `-refresh=false`:** Skips the API calls to refresh state. (Tradeoff: Plan might be inaccurate if drift occurred).
3. **Targeted applies:** Only run what is needed. (Tradeoff: Risk of missing dependencies).
4. **Optimize provider usage:** Minimize data sources that call slow APIs. (Tradeoff: Requires code refactoring).

**T19:** State locking prevents two users/processes from modifying state simultaneously, preventing corruption. If a lock is not released (e.g., CI crash), the state remains locked. You can manually break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually running, force-unlocking can lead to state corruption or resource duplication.

**T20:** 
1. Configure the `backend "s3"` block in your code.
2. Run `tofu init`. OpenTofu will detect the local state and ask if you want to migrate it to the remote backend.
3. Type `yes`. OpenTofu copies the local `.tfstate` to S3 and updates the configuration.
4. **Verify:** Check the S3 bucket for the state file and run `tofu plan` to ensure no unexpected changes are detected.

## Ansible

**A1:** A **task** is a single action. A **playbook** is a collection of plays (mapping hosts to tasks). A **role** is a structured way to bundle tasks, variables, files, and templates for reuse.

**A2:** `ansible_facts` is a dictionary of system information gathered by Ansible. Access OS family via `{{ ansible_os_family }}`.

**A3:** 
- `command`: Executes a command on the remote node. Does not process Jinja2 or shell variables.
- `shell`: Executes a command through a shell (`/bin/sh`), allowing pipes, redirects, and environment variables.
- `raw`: Bypasses the Python requirement; sends raw SSH commands. Use this for bootstrapping systems without Python.

**A4:** Idempotency means running a task multiple times results in the same state without extra changes. 
- **Idempotent:** `apt: name=nginx state=present` (installs only if missing).
- **NOT Idempotent:** `shell: echo "config_line" >> /etc/file` (appends the line every single time).

**A5:**
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel and htop for RedHat
  block:
    - name: Install EPEL
      yum: name=epel-release state=present
    - name: Install htop
      yum: name=htop state=present
  when: ansible_os_family == "RedHat"
```

**A6:** (Lowest to Highest) `role defaults` < `inventory group_vars` < `inventory host_vars` < `playbook vars` < `set_fact` < `extra_vars`.

**A7:** Use `serial: 3` in the playbook to process 3 hosts at a time. Use `wait_for` in a task to ensure the RKE2 service is listening on a specific port before proceeding to the next batch.

**A8:** `ansible-vault` encrypts files/variables. To encrypt a single variable in a file, you must encrypt the entire file, but you can use a variable file containing only that secret. Alternatively, use `ansible-vault encrypt_string` to generate an encrypted string to paste into a plain YAML file.

**A9:** An **inventory** defines the hosts/groups Ansible manages. **Static** is a hardcoded file (INI/YAML). **Dynamic** uses a script or plugin to query a cloud provider (AWS/GCP) for the current list of hosts.

**A10:** `ansible webservers -m shell -a "df -h"`

**A11:** A **handler** is a special task that only runs if a task notifies it (via `notify`). It is used for actions that should only happen if a change occurred (e.g., restarting Nginx after a config change).

**A12:** `ansible.cfg` configures Ansible behavior. Common settings: `inventory` (path to inventory), `remote_user` (default user), and `forks` (number of parallel processes).

**A13:** `register` saves the output of a task into a variable. You can then use that variable in a subsequent task using `when: result_var.rc == 0`.

**A14:** `import_tasks` is **static** (processed at playbook parsing time). `include_tasks` is **dynamic** (processed when the task is reached). Use `include_tasks` if you need to use a variable to determine which file to include or if you need to apply a `when` condition to the inclusion itself.

**A15:** Ansible Galaxy is a public repository for roles and collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16:** 
- `ssh`: Default; uses SSH to run Python modules.
- `local`: Runs the module on the control node itself.
- `network_cli`: Used for network devices (switches/routers) that don't have Python; it simulates a CLI user.

**A17:** `delegate_to` runs a task on a different host than the one in the current play. `run_once` ensures a task runs only once for the whole play. 
**Example:** To register a node in a load balancer:
```yaml
- name: Register node in LB
  shell: /usr/bin/register_lb {{ ansible_host }}
  delegate_to: localhost
  run_once: false
```

**A18:** 
1. **Forks:** Increase `forks` in `ansible.cfg` to run more tasks in parallel. (Tradeoff: Higher CPU/RAM usage on control node).
2. **Pipelining:** Enable `pipelining = True` to reduce SSH connections. (Tradeoff: Requires `requiretty` to be disabled on target).
3. **Fact Caching:** Use Redis/Memcached to store facts. (Tradeoff: Complexity in managing the cache).
4. **Mitogen:** Use the Mitogen plugin for highly optimized SSH execution. (Tradeoff: Can occasionally conflict with specific custom modules).

**A19:** 
- `{{ }}`: Expression (prints value).
- `{% %}`: Statement (logic like loops/conditionals).
- `{# #}`: Comment.

**Template Snippet:**
```jinja2
upstream myapp {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; # Health check: {{ server.status }}
{% endfor %}
}
```

**A20:** 
1. **Serial:** Set `serial: 1` or `serial: 20%` to process servers in batches.
2. **Pre-task:** Use `uri` module to remove the server from the Load Balancer.
3. **Deployment:** Perform the app update.
4. **Health Check:** Use `uri` module to hit the local app endpoint and wait for a `200 OK`.
5. **Post-task:** Re-add the server to the Load Balancer.
6. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, use tasks to revert the code version and re-register the server to the LB.
