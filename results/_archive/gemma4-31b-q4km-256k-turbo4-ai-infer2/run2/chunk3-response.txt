## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry run that compares the current state with the desired configuration and lists the actions (create, modify, destroy) it will take. `tofu apply` actually executes those actions to reach the desired state.

**T2 — Easy:** State is a JSON file that maps your configuration to real-world resources. Remote state is critical for teams because it allows multiple engineers to share a single "source of truth," prevents state conflicts via locking, and keeps sensitive data off local machines.

**T3 — Medium:** `count` creates resources based on an integer index (list). `for_each` creates resources based on a map or set of keys. `for_each` is preferred because removing an item from the middle of a `count` list causes all subsequent resources to be shifted/recreated; `for_each` identifies resources by key, making additions/removals stable.

**T4 — Medium:** This is called "drift." OpenTofu detects this during the `plan` phase by refreshing the state against the actual cloud API. It will show that the resource has changed and will attempt to "correct" the resource back to the configuration defined in your code during the next `apply`.

**T5 — Medium:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6 — Hard:** `terraform_remote_state` reads the entire state file of another project, which is powerful but creates tight coupling and exposes all state data. Output values are specific, intentional exports. The recommended alternative is to use a "Data Source" for specific shared resources or a dedicated "State Store" (like a SSM Parameter Store or HashiCorp Consul) to decouple the producer and consumer.

**T7 — Hard:** `null_resource` provisioners run *during* the apply phase, but the resource is considered "created" as soon as the provisioner starts. If the output depends on a value generated *inside* the `remote-exec` script, that value isn't natively returned to the Tofu state. **Fix:** Have the `remote-exec` script write the kubeconfig to a file or a cloud secret (like AWS Secrets Manager), then use a `data` source or a separate resource to read that value.

**T8 — Medium:** `tofu import` brings existing infrastructure into the state file. Limitation: The CLI command is imperative and requires you to manually write the HCL code to match the resource. The `import` block (1.5+) is declarative; it allows you to define the import in code, and Tofu can automatically generate the corresponding HCL configuration.

**T9 — Easy:** A variable (input) is a parameter passed into the module to make it reusable. An output is a value returned by the module to be used by other modules or the user.

**T10 — Easy:** A provider is a plugin that translates Tofu HCL into API calls for a specific platform (e.g., AWS, Azure). If you run `plan` without `init`, Tofu will fail because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11 — Easy:** The `.terraform.lock.hcl` ensures that every environment uses the exact same version of a provider. It should be committed to version control to prevent "it works on my machine" bugs caused by different provider versions.

**T12 — Easy:** `tofu destroy` deletes all resources managed by the state file. To target a single resource: `tofu destroy -target=aws_instance.my_vm`.

**T13 — Easy:** A data source fetches information from an existing resource not managed by the current Tofu project. Example: Using `aws_ami` to find the latest Amazon Linux 2 image ID instead of hardcoding a specific ID.

**T14 — Medium:** Variables are inputs provided at runtime. Locals are internal constants or computed values. Use locals to avoid repeating the same complex expression multiple times within a module (DRY).

**T15 — Medium:** The `lifecycle` block controls resource behavior:
- `create_before_destroy`: Creates the new resource before deleting the old one (prevents downtime).
- `prevent_destroy`: Errors out if a destroy is attempted (safety for DBs).
- `ignore_changes`: Ignores drift on specific attributes (e.g., ignore tags added by an external security scanner).

**T16 — Medium:** A `moved` block allows you to rename a resource or move it into a module in the code without Tofu thinking you want to delete the old resource and create a new one. It updates the state address mapping.

**T17 — Hard:** Tofu builds a Directed Acyclic Graph (DAG). Implicit dependencies are created when one resource references another's attribute. Explicit dependencies use `depends_on`. `depends_on` forces a strict order, reducing parallelism because Tofu must wait for the dependency to be fully complete before starting the next, even if no data is shared.

**T18 — Hard:** 
1. **State Splitting:** Break the monolith into smaller states (e.g., network, db, app). *Tradeoff: More complex management.*
2. **Targeted Plans:** Use `-target` for specific changes. *Tradeoff: Risk of state drift.*
3. **Refresh False:** Use `-refresh=false` to skip API checks. *Tradeoff: Plan may be inaccurate.*
4. **Parallelism:** Adjust `-parallelism=N`. *Tradeoff: May hit API rate limits.*

**T19 — Hard:** State locking prevents concurrent modifications. If a CI pipeline crashes, the lock remains. You manually break it using `tofu force-unlock <lock-id>`. The risk is that if a process is *actually* still running, you may cause state corruption by allowing a second concurrent write.

**T20 — Hard:** 
1. Add the `backend "s3"` block to the configuration.
2. Run `tofu init`.
3. Tofu detects the local state and asks to migrate it to S3.
4. Confirm the migration.
5. Tofu uploads the local `.tfstate` to S3 and configures DynamoDB for locking.
6. Verify by running `tofu state list` to ensure all resources are still tracked.

## Ansible

**A1 — Easy:** A **Task** is a single unit of work (e.g., install a package). A **Playbook** is a list of plays (mapping hosts to tasks). A **Role** is a structured bundle of tasks, variables, handlers, and templates for a specific function (e.g., "nginx_webserver").

**A2 — Easy:** `ansible_facts` is a dictionary of system information gathered by the `setup` module. Access OS family via: `{{ ansible_facts['os_family'] }}`.

**A3 — Medium:** 
- `command`: Most secure; doesn't process shell variables/wildcards.
- `shell`: Runs through `/bin/sh`; allows pipes, redirects, and environment variables.
- `raw`: Bypasses Python; used for systems without Python installed (e.g., network switches).

**A4 — Medium:** Idempotency means running a task multiple times results in the same state without changing the system after the first run. 
- **Idempotent:** `apt: name=vim state=present` (checks if installed first).
- **Non-idempotent:** `shell: echo "hello" >> /tmp/log` (appends every time).

**A5 — Medium:**
```yaml
- name: Install htop
  package:
    name: "{{ (ansible_os_family == 'Debian') | ternary('htop', 'epel-release') }}"
  when: ansible_os_family in ['Debian', 'RedHat']
# Note: For RedHat, a second task for htop would be needed or a loop.
```

**A6 — Hard:** Precedence (Lowest to Highest): Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ Playbook vars $\rightarrow$ `set_fact` $\rightarrow$ Extra vars (`-e`).

**A7 — Hard:** 
- Use `serial: 3` in the play to process in batches.
- Use `groups` in inventory to separate "initial" and "remaining" nodes.
- Use the `wait_for` module to ensure the RKE2 API port (6443) is open on the first 3 nodes before proceeding to the rest.

**A8 — Medium:** `ansible-vault` encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'my_password' --name 'db_password'`. This allows you to keep the rest of the vars file in plain text.

**A9 — Easy:** An inventory is a list of managed hosts. **Static** is a hardcoded file (`hosts.ini`). **Dynamic** is a script or plugin that queries an API (e.g., AWS EC2) to generate the host list in real-time.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`.

**A11 — Easy:** A handler is a task that only runs if "notified" by another task that reported a "changed" status. It is used for actions like restarting a service after a config change. Triggered via the `notify: <handler_name>` keyword.

**A12 — Easy:** `ansible.cfg` configures Ansible's behavior. Common settings: `inventory` (path to hosts file), `remote_user` (default SSH user), and `forks` (number of parallel processes).

**A13 — Easy:** `register` captures the output of a task into a variable. 
Example: 
`shell: uptime` $\rightarrow$ `register: uptime_result`. 
Next task: `debug: msg="{{ uptime_result.stdout }}"`.

**A14 — Medium:** `import_tasks` is static (parsed at startup); `include_tasks` is dynamic (parsed at runtime). Use `include_tasks` when the decision to run the tasks depends on a variable determined during the play.

**A15 — Medium:** Ansible Galaxy is a community hub for roles. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:** Connection plugins define how Ansible talks to the host.
- `ssh`: Standard for Linux.
- `local`: Runs on the control node.
- `network_cli`: Specialized for network devices (SSH but handles prompt-based shells).

**A17 — Hard:** `delegate_to` runs a task on a different host; `run_once` ensures the task runs only once per play. 
**Example:** After deploying a VM, use `delegate_to: localhost` and `run_once: true` to update a central DNS record using the IP gathered from the remote host.

**A18 — Hard:** 
1. **Forks:** Increase `forks` in `ansible.cfg` to process more hosts in parallel.
2. **Pipelining:** Enable `pipelining = True` to reduce SSH connections.
3. **Fact Caching:** Use Redis or Jsonfile to avoid running `setup` every time.
4. **Mitogen:** Use the Mitogen plugin to replace the SSH transport for massive speed gains.

**A19 — Hard:** 
- `{{ }}`: Variable interpolation.
- `{% %}`: Control logic (loops, conditionals).
- `{# #}`: Comments.
**Snippet:**
```jinja2
{% for server in backend_servers %}
# Health check: enabled
server {{ server.name }} {{ server.ip }}:80;
{% endfor %}
```

**A20 — Hard:** 
1. Set `serial: 20%` to update in batches.
2. **Pre-task:** Use `uri` or a LB module to remove the host from the load balancer.
3. **Update:** Deploy the app.
4. **Health Check:** Use `uri` module to verify the app is responding 200 OK.
5. **Post-task:** Add host back to LB.
6. **Rollback:** Wrap the update in a `block`. In the `rescue` section, trigger a task to redeploy the previous version and alert the team.
