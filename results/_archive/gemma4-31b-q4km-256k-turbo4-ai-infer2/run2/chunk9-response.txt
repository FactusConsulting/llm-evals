## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the **Restricted Pod Security Standard (PSS)** requires that pods must not run as root. While the manifest specifies `runAsNonRoot: true`, the container image `chainguard/static:latest` defaults to `USER root`. In the `Baseline` policy, Kubernetes allows the container to start even if the image defaults to root, as long as the runtime doesn't explicitly forbid it. In `Restricted`, the admission controller and the Kubelet enforce that the container *actually* runs as a non-root user. Since no `runAsUser` is specified in the `securityContext`, the container attempts to start as the image default (root), which violates the `runAsNonRoot: true` constraint, leading to a failure at the runtime level.

**SC1-B:**
```bash
kubectl get pods -A | grep CrashLoopBackOff | awk '{print $1, $2}' | xargs -L1 sh -c 'kubectl get pod -n $1 $2 -o jsonpath="{.metadata.namespace} {.metadata.name} {.spec.securityContext}"'
```
*(Note: For a cleaner JSON output of the securityContext specifically:)*
```bash
kubectl get pods -A -o json | jq '.items[] | select(.status.containerStatuses[0].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:**
*   **Image-level fix:** Update the Dockerfile to include `USER 1000` (or any non-zero UID) to ensure the image does not default to root.
*   **Manifest change:** Explicitly set `securityContext.runAsUser: 1000` in the Pod spec to override any image defaults and satisfy the Restricted PSS.
*   **CI Pipeline Gate:** Implement a policy engine like **Kyverno** or **OPA Gatekeeper** that rejects any deployment to production namespaces if `runAsUser` is missing or set to 0.
*   **Rollout:** Perform a **RollingUpdate** (maxSurge: 25%, maxUnavailable: 0) to ensure new pods are healthy before terminating old ones, preventing downtime.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is caused by **asynchronous replication lag**. In cross-region RDS, WAL (Write Ahead Log) records are shipped asynchronously to avoid latency penalties on the primary. During the outage, the replica in `eu-west-1` was likely behind the primary. Promoting it creates a "split" where data not yet shipped from `us-east-1` is lost. To quantify the loss, I would check the `pg_stat_replication` view (on the old primary if accessible) or compare the `last_wal_receive_lsn` on the new primary against the last known LSN of the old primary.

**SC2-B:**
1.  **Import:** `terraform import aws_db_instance.primary.arn <new_eu_west_1_arn>`
2.  **State Manipulation:** Use `terraform state mv` to rename the resource if the logical name changed.
3.  **Update Code:** Update the `aws_db_instance` block in HCL to match the new region and instance ID.
4.  **Dependencies:** Update the `aws_route53_record` to point to the new endpoint.
5.  **Apply:** Run `terraform apply -target=aws_db_instance.primary` to reconcile without destroying other resources.

**SC2-C:**
*   **Architecture:** Replace PgBouncer with **RDS Proxy** for better native integration with RDS failover (faster DNS/connection handling).
*   **DNS:** Use **Route53 Health Checks** with a CNAME failover policy to automatically route traffic to the DR region.
*   **RPO < 1s:** Use **Aurora Global Database**. It uses storage-level replication (physical) rather than logical/streaming, typically achieving RPO < 1 second.
*   **Recommendation:** Yes, Aurora Global Database is recommended because it handles the replication at the storage layer, reducing the overhead on the DB engine and providing significantly faster failover (RTO) and lower RPO than standard RDS replicas.

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Sticky Sessions:** K8s pods are ephemeral. *Solution:* Move sessions to an external **Redis** cluster.
2.  **Local NFS:** Pods move across nodes. *Solution:* Use a **CSI driver** (e.g., AWS EFS or Azure Files) for shared storage.
3.  **Oracle 19c:** Heavyweight, non-cloud native. *Solution:* Use an **ExternalName Service** to point to the on-prem DB until it can be migrated to RDS/Cloud.
4.  **IBM MQ:** Tight coupling. *Solution:* Deploy an **IBM MQ Operator** on K8s or use a sidecar proxy for connectivity.
5.  **Local Memory State:** App assumes persistence. *Solution:* Refactor to be **stateless** or use stateful sets with persistent volumes.

**SC4-B:**
```hcl
resource "storage_class" "nfs" {
  storage_provisioner = "nfs.csi.k8s.io"
  parameters = {
    server = var.nfs_server
    path = var.nfs_path
  }
}
resource "kubernetes_persistent_volume_claim" "uploads" {
  metadata { name = "uploads-pvc" }

    access_modes = ["ReadWriteMany"] # Necessary because multiple pods need concurrent write access to uploads
    storage_class_name = storage_class.nfs.metadata[0].name
    resources { requests = { storage = var.capacity } }
  }
}
```

**SC4-C:**
*   **Phase 1 (Edge):** Move the Ingress/ALB to K8s. Route 10% of traffic to a "read-only" version of the app in K8s, proxying writes back to the monolith.
*   **Phase 2 (Feature):** Move specific modules (e.g., Uploads) to K8s. Use the F5 to split traffic by URL path.
*   **Phase 3 (Full):** Move the core app. Use a **Canary deployment**.
*   **Integration:** IBM MQ remains external; K8s pods connect via a Service.
*   **Rollback:** DNS switch back to F5 BIG-IP.
*   **Metrics:** p99 latency, error rate (5xx), and session drop rate.

## SC5 — Mysterious Latency Spike in Microservices

**SC5-A:**
*   **Approach:** Check **Jaeger** spans for `checkout-service` $\rightarrow$ `inventory-service`. If the span for `inventory-service` is long, the issue is in the app. If the gap *between* the services is long, it's the network/mesh.
*   **Envoy Metrics:** Check `upstream_rq_time` (total time) vs `upstream_cx_connect_timeout`. If `upstream_rq_time` is high but the app logs show fast processing, the request is queuing in the Envoy buffer.
*   **Logs:** Look for "connection pool exhausted" or "timeout" in `inventory-service`.

**SC5-B:**
**SQL Diagnostic:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid, 
       blocking_locks.query AS blocking_query, blocked_locks.query AS blocked_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_act ON blocked_locks.pid = blocked_act.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype 
     AND blocking_locks.database = blocked_locks.database
JOIN pg_catalog.pg_stat_activity blocking_act ON blocking_locks.pid = blocking_act.pid
WHERE NOT blocked_locks.granted;
```
**Go Circuit Breaker:**
```go
cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{Name: "inventory-service"})

    return httpClient.Get("http://inventory-service/api/stock")
```

**SC5-C:**
*   **CQRS:** Use a **Read Replica** for the reconciliation job so it doesn't lock the primary write table.
*   **Bulkheads:** Create separate connection pools for "API requests" and "Admin/Cron jobs" in the DB.
*   **Scheduling:** Offset the CronJob to a low-traffic window or use a queue-based reconciliation.
*   **K8s:** Set a `PriorityClass` for the serving pods and a lower priority for the CronJob. Use a `ResourceQuota` to limit the CronJob's CPU/RAM so it cannot starve the API pods.

## SC6 — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:**
*   **Identity:** Deploy **SPIRE** (SPIFFE Runtime Environment). Each workload gets a SVID (SPIFFE Verifiable Identity Document) via a local agent.
*   **Federation:** Use **OIDC Federation**. AWS workloads use IAM roles to exchange an AWS token for a SPIFFE SVID. Azure workloads use Managed Identities.
*   **Cross-Env Auth:** A service in AWS presents its SVID; the on-prem service validates the SVID against the SPIRE trust bundle. No shared secrets are used; trust is based on the root CA of the SPIRE federation.

**SC6-B:**
```hcl
resource "aws_vpc_endpoint" "endpoints" {
  for_each = var.services # e.g., ["s3", "rds", "ecr"]
  vpc_id = aws_vpc.main.id
  service_name = "com.amazonaws.${var.region}.${each.value}"
  vpc_endpoint_route_table_ids = [aws_route_table.private.id]
  private_dns_enabled = true
}
resource "aws_security_group" "default_deny" {
  vpc_id = aws_vpc.main.id
  # No ingress rules = default deny
}
```

**SC6-C:**
*   **Direct Connect:** Highest cost, lowest jitter, highest bandwidth. Best for stability.
*   **ECMP VPN:** Lower cost, but subject to internet jitter.
*   **Mesh (Tailscale/Netbird):** Easiest to deploy, provides an overlay network (WireGuard), fits Zero Trust perfectly as it handles identity-based routing.
*   **Recommendation:** **Direct Connect** for the backbone, with a **Mesh overlay** for service-to-service identity. Routing changes: Move from static routes to BGP for Direct Connect.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
*   **Manual Apply:** Bypasses Git, making the repo a "lie."
*   **Diverged Values:** Leads to "it works in staging but not prod" bugs.
*   **Kubectl Edit:** Changes are invisible to the audit trail.
*   **State Locking:** Without locking, two engineers running `apply` simultaneously can corrupt the state file (race condition), leading to resources being deleted or duplicated.

**SC7-B:**
```yaml
stages: [validate, plan, apply]
tofu_plan:
  stage: plan
  script:
    - tofu init -backend-config="dynamodb_table=lock-table"
    - tofu plan -out=tfplan
  artifacts:
    paths: [tfplan]
workflow:
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
tofu_apply:
  stage: apply
  when: manual
  script:
    - tofu apply tfplan
```

**SC7-C:**
*   **Drift Detection:** Schedule a GitLab CI job to run `tofu plan -detailed-exitcode` every hour. If it returns `2` (drift detected), trigger an alert.
*   **Blocking:** Use **Kyverno** to block `UPDATE` or `PATCH` requests to ConfigMaps/Deployments unless the user is the CI service account.
*   **Structure:** Use **Helmfile** with a `common-values.yaml` and `prod-values.yaml` (overrides).
*   **RBAC:** Remove `cluster-admin` from humans; assign a `Role` with `update` permissions only to the CI ServiceAccount.

## SC9 — Securing a Public-Facing API After a Breach

**SC9-A:**
1.  **BOLA:** (API1:2023) User A accesses User B's data. *Fix:* Check ownership in the view/query.
    ```python
    def get_object(self, obj):
        if obj.owner != self.request.user:
            raise PermissionDenied("Not your record")
        return super().get_object(obj)
    ```
2.  **Data Exposure:** (API3:2023) Internal fields leaked. *Fix:* Use a **Serializer** to explicitly define allowed fields.
3.  **Rate Limiting:** (API4:2023) Resource exhaustion. *Fix:* Implement `throttling` in Django or WAF rate limits.
4.  **API Keys in URL:** (API7:2023) Log leakage. *Fix:* Move keys to `Authorization: Bearer <key>` header.

**SC9-B:**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {
  # Rate limit: 100 req / 5 min
  rule {
    name = "RateLimit"
    statement { rate_limit { limit = 100 } }
    action { block {} }
  }
  # Block API key in query string
  rule {
    name = "NoKeyInUrl"
    statement { byte_match { field = "query_string", positional_constraint = "contains", search_string = "api_key=" }
    action { block {} }
  }
  # Geo-block
  rule {
    name = "GeoBlock"
    statement { not { geo_match { country_codes = var.allowed_countries } }
    action { block {} }
  }
}
```

**SC9-C:**
*   **Defense-in-Depth:** Deploy **Kong** as an API Gateway to handle JWT validation and rate limiting before requests hit the ALB.
*   **Auth Migration:** Implement a "Grace Period" where the API accepts both API keys (header) and JWTs. Log a warning for API key usage. After 30 days, disable API keys.
*   **Encryption:** Use **AWS KMS** for field-level encryption of PII (e.g., `email`, `ssn`) in the database.

## SC10 — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Architecture:** **Active-Passive with Cilium Cluster Mesh**. This allows the DR cluster to be "warm."
*   **RPO/RTO:** 12ms latency is low enough for **Synchronous Replication** for PG (RPO=0). 200TB MinIO requires **Site Replication** (asynchronous), which may exceed 15m RPO unless bandwidth is saturated.
*   **Stateful Strategy:**
    *   **PostgreSQL:** Patroni with synchronous standby in Dallas.
    *   **Redis:** Sentinel with cross-site replication.
    *   **RabbitMQ:** Federation/Shovel for queue mirroring.
    *   **MinIO:** Site-to-site bucket replication.

**SC10-B:**

**SC10-C:**
1.  **Detection:** Use a **Quorum-based monitor** (e.g., Consul) to avoid false positives.
2.  **Sequence:** 
    *   $\rightarrow$ GSLB updates DNS to Dallas.
    *   $\rightarrow$ Patroni promotes Dallas PG to Primary.
    *   $\rightarrow$ Redis Sentinel promotes Dallas replica.
    *   $\rightarrow$ RabbitMQ Federation switches to local queues.
3.  **Split-Brain:** Use **Fencing** (STONITH) or a majority-vote in etcd to ensure only one site is primary.
4.  **Failback:** Re-sync Chicago as a standby $\rightarrow$ verify lag $\rightarrow$ controlled switch-over during maintenance window.
