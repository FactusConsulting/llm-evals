## Cloud Infrastructure Architecture

**CL1 — Easy:** 
*   **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing the underlying OS/runtime. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Fully managed software delivered via web/API. *Example: Microsoft 365.*

**CL2 — Easy:** 
The provider manages the "Cloud" (hardware, virtualization, global infra); the customer manages "in the Cloud" (data, config).
*   **IaaS VMs:** Provider: Hypervisor/Hardware. Customer: Guest OS, Patching, Apps.
*   **Managed K8s (EKS/GKE):** Provider: Control Plane. Customer: Worker node configuration, Pods, Network Policies.
*   **SaaS (M365):** Provider: Almost everything. Customer: Identity/Access management and the data itself.

**CL3 — Medium:** 
*   **VPC:** An isolated virtual network.
*   **Subnet:** A range of IP addresses within a VPC.
*   **Security Group (SG):** Instance-level firewall (stateful).
*   **NACL:** Subnet-level firewall (stateless).
*   **Layering:** VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ SG.
*   **Stateful (SG):** Remembers request/response; if traffic is allowed in, the return traffic is automatically allowed.
*   **Stateless (NACL):** Each packet is evaluated independently; you must define both inbound and outbound rules.

**CL4 — Medium:** 
*   **Landing Zone:** A standardized multi-account environment (governance, networking, identity).
*   **OUs:** Logical groupings of accounts for policy application.
*   **Guardrails:** Service Control Policies (SCPs) that set maximum permission boundaries.
*   **Shared Networking:** Hub-and-Spoke (Azure) or Transit Gateway (AWS) centralizes egress/ingress and connects VPCs.
*   **Centralized Logging:** Aggregating logs (CloudTrail/Activity Logs) into a dedicated security account.
*   **Single-account problem:** Blast radius (one compromise affects all), quota limits, and "noisy neighbor" billing.

**CL5 — Medium:** 
IaC is managing infrastructure via machine-readable definition files.
*   **Terraform/OpenTofu:** Cloud-agnostic, HCL-based, state-file driven. Best for multi-cloud.
*   **Pulumi:** Uses general-purpose languages (TS, Python). Best for developers.
*   **CloudFormation/Bicep:** Provider-specific. Best for deep integration/day-zero support.
*   **Crossplane:** K8s-native (CRDs). Best for managing infra as K8s resources.

**CL6 — Medium:** 
*   **HPA:** Scales pods based on CPU/RAM.
*   **VPA:** Adjusts pod resource requests/limits.
*   **Cluster Autoscaler:** Adds/removes nodes to the cluster.
*   **KEDA:** Event-driven scaling (e.g., scale based on Kafka lag or RabbitMQ queue depth).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external metrics not natively available to the K8s metrics server.

**CL7 — Hard:** 
*   **RPO (Recovery Point Objective):** Max acceptable data loss. **RTO (Recovery Time Objective):** Max acceptable downtime.
*   **Active-Active:** Traffic split across regions; zero RTO. Requires sync replication (high latency) or conflict resolution.
*   **Active-Passive:** Primary region active; secondary on standby.
*   **Replication:** Sync (no data loss, slow) vs Async (potential loss, fast).
*   **DNS:** Route53/Traffic Manager for health-check based failover.
*   **DR Tiers:** 
    *   *Pilot Light:* DB is synced; apps are off.
    *   *Warm Standby:* Apps are running at minimum scale.
    *   *Multi-site:* Full capacity in both regions.

**CL8 — Hard:** 
GitOps uses Git as the single source of truth.
*   **ArgoCD vs FluxCD:** ArgoCD provides a powerful UI and "push/pull" feel; Flux is more lightweight and "invisible" (pull-only).
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift:** The controller detects the difference between Git and the cluster; it automatically overwrites manual changes to match Git (self-healing).

**CL9 — Hard:** 
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC:** Use a `Local` storage class for low-latency NVMe disks.
*   **Headless Service:** Provides DNS for individual pods (e.g., `pod-0.service.ns`).
*   **Init Containers:** Handle filesystem setup or config checks before the app starts.
*   **ConfigMaps:** Mounted as volumes to specific paths.
*   **PDB (Pod Disruption Budget):** Ensures a minimum number of pods remain available during maintenance.

**CL10 — Medium:** 
*   **Service Account:** Identity for a pod within K8s.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role.
*   **Why not static credentials?** Hardcoded keys leak; they don't rotate and are hard to audit.
*   **Federation:** Uses OIDC to exchange a K8s token for a short-lived cloud token, eliminating the need for long-lived secrets.

**CL11 — Medium:** 
*   **Object (S3):** Key-value store. High durability (11 9s), scalable. Use for images, logs, backups.
*   **Block (EBS):** Low-latency, attached to one VM. Use for OS disks, databases.
*   **File (EFS):** Shared network filesystem (NFS/SMB). Use for shared config or CMS uploads.

**CL12 — Hard:** 
*   **Architecture:** Network Policies (L3/4 isolation) $\rightarrow$ Service Mesh (mTLS for L7 encryption/auth) $\rightarrow$ Pod Identity (Workload Identity).
*   **Governance:** OPA/Kyverno for policy enforcement; Image signing (Cosign) for provenance.
*   **Runtime:** Falco for anomaly detection (e.g., shell in pod).
*   **Vs Perimeter:** Traditional security trusts everything inside the wall; Zero Trust assumes the network is compromised and verifies every single request.

**CL13 — Easy:** 
A CDN caches content at "Edge" locations closer to users.
*   **Services:** CloudFront, Akamai.
*   **Use case:** Use a CDN for static assets (JS, CSS, Images) to reduce latency and origin load; serve from origin for dynamic, user-specific data.

**CL14 — Easy:** 
*   **Region:** A geographic area (e.g., us-east-1).
*   **AZ:** One or more discrete data centers within a region.
*   **Multi-AZ:** Protects against a single DC failure.
*   **Zonal vs Regional:** Zonal resources (e.g., EBS) exist in one AZ; Regional resources (e.g., S3, Lambda) are replicated across AZs.

**CL15 — Easy:** 
Managed DBs (RDS) automate patching, backups, failover, and scaling. In a VM, you must manually handle OS updates, DB installation, backup scripts, and manual replication setup.

**CL16 — Easy:** 
*   **Users:** Individual people. **Groups:** Collections of users. **Roles:** Temporary identities assumed by users/services. **Policies:** JSON documents defining permissions.
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply via granular IAM policies rather than `AdministratorAccess`.

**CL17 — Easy:** 
Serverless is event-driven compute where the provider manages all scaling and infrastructure.
*   **Cold Start:** Latency when a function is invoked after being idle (provider spins up a new container).
*   **Poor fit:** Long-running processes (timeouts), predictable high-constant load (cheaper on VMs), or requirements for custom OS kernels.

**CL18 — Medium:** 
*   **Ingress:** Basic L7 routing. **Gateway API:** Modern, role-based (Infrastructure vs. Application) API. **Annotations:** Cloud-specific tweaks (e.g., ALB settings). **Mesh Ingress:** Advanced traffic splitting/canary.
*   **TLS:** Terminated at the LB (Edge) or passed through to the pod (End-to-End).
*   **Gateway API vs Ingress:** Gateway API is more expressive, supports better traffic splitting, and separates concerns between the cluster admin and the app developer.

**CL19 — Hard:** 
*   **Commitments:** RIs/Savings Plans for predictable load; Spot for fault-tolerant batch jobs.
*   **Right-sizing:** Using metrics to downsize over-provisioned VMs.
*   **Storage:** S3 Intelligent-Tiering to move old data to Glacier automatically.
*   **FinOps:** Tagging resources by project/team $\rightarrow$ Cost Explorer $\rightarrow$ Chargeback (billing the team) or Showback (reporting cost).
*   **Tools:** AWS Cost Explorer, Kubecost for K8s.

**CL20 — Hard:** 
*   **Strategy:** Use K8s as the common runtime; Terraform for consistent IaC; VPN/DirectConnect for cross-cloud networking.
*   **Identity:** Use OIDC/SAML federation to avoid duplicating users.
*   **Trade-offs:** Theoretical benefit is resilience and leverage; reality is massive operational overhead and "lowest common denominator" feature sets.

*   **Justified:** Regulatory requirements (sovereignty) or extreme risk aversion. Otherwise, usually unnecessary complexity.

## OT Infrastructure Architecture

**OT1 — Easy:** 
The Purdue Model segments industrial networks.
*   **L0 (Process):** Physical sensors/actuators.
*   **L1 (Basic Control):** PLCs, PID controllers.
*   **L2 (Area Control):** HMIs, SCADA local.
*   **L3 (Site Operations):** Historians, site-wide control.
*   **L4 (Business/IT):** ERP, Corporate email.

**OT2 — Easy:** 
IT focuses on Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability. OT focuses on Availability $\rightarrow$ Safety $\rightarrow$ Integrity. Patching OT is dangerous because a reboot can stop a physical process, cause equipment damage, or create safety hazards.

**OT3 — Medium:** 
The IDMZ is a buffer. Only proxied, inspected traffic (e.g., via a jump host or data diode) should cross. Direct L4 $\rightarrow$ L1 is dangerous because a compromised corporate laptop could send a "Stop" command directly to a PLC, causing physical catastrophe.

**OT4 — Medium:** 
1. **Modbus TCP:** L1/L2 (Simple, unauthenticated).
2. **OPC UA:** L2/L3 (Secure, structured data).
3. **EtherNet/IP:** L1/L2 (High-speed control).
4. **PROFINET:** L1/L2 (Real-time deterministic).
5. **MQTT:** L3/Cloud (Pub/Sub, lightweight).

**OT5 — Medium:** 
*   **Data Diode:** Hardware that physically allows data to flow in only one direction (using light/optics).
*   **Firewall:** Software-based, bidirectional.
*   **Use case:** Use a diode for high-security telemetry (L3 $\rightarrow$ L4) where you must guarantee no one can send commands back into the plant. Limitation: No return path (no ACKs/handshakes).

**OT6 — Medium:** 
PLC $\rightarrow$ OPC UA Server (L2) $\rightarrow$ Plant Historian (L3) $\rightarrow$ Edge Gateway (IDMZ) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud.
*   **Boundaries:** Firewall between L3 and IDMZ; Firewall between IDMZ and L4.

**OT7 — Hard:** 
*   **Zone:** A group of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Design:** 
    *   Zone 1: SIS (Isolated).
    *   Zone 2: Control (PLCs/HMIs).
    *   Zone 3: Site Ops (Historian/SCADA).
    *   Zone 4: Corporate.
    *   Conduits: Strictly filtered via firewalls.

**OT8 — Hard:** 
*   **Segmentation:** Create VLANs per production line. Place a firewall between the lines and the SCADA server.
*   **Architecture:** Use a collapsed core or distributed switch architecture.
*   **Remote Access:** VPN $\rightarrow$ MFA $\rightarrow$ Jump Host $\rightarrow$ Target.
*   **Transition:** Implement "Passive Monitoring" first to map traffic, then apply "Permit" rules, then "Deny" all others.

**OT9 — Hard:** 
*   **BPCS:** Handles normal operations. **SIS:** Handles emergency shutdowns (Safety).
*   **IEC 61511:** Standard for functional safety.
*   **Isolation:** SIS must be isolated so a failure/attack on the BPCS doesn't disable the safety system.
*   **Ransomware in SIS:** Could prevent a safety shutdown during a crisis, leading to explosions or leaks.

**OT10 — Medium:** 
*   **PLC:** Local, fast, logic-based.
*   **DCS:** Integrated, plant-wide, centralized control.
*   **SCADA:** Wide-area monitoring and control.
*   **Coexistence:** Yes; SCADA often sits on top of PLCs and DCS.

**OT11 — Medium:** 
Architecture: Corporate $\rightarrow$ VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (Bastion) $\rightarrow$ Target HMI.
*   **Why no direct RDP?** RDP is a primary vector for lateral movement; without a jump host, an attacker has a direct path to the control layer.

**OT12 — Hard:** 
*   **Detection:** Use passive IDS (e.g., Nozomi/Claroty) to detect anomalous Modbus/S7 traffic.
*   **Response:** 
    1. Isolate the compromised L3 segment.
    2. Verify SIS integrity.
    3. Coordinate with operators to ensure the process is in a "Safe State."
*   **Operator Role:** The operator is the final authority; they can switch to manual control if the digital system is untrusted.

**OT13 — Easy:** 
*   **HMI:** A dashboard for operators to monitor and control the process.
*   **Eng Station:** A specialized PC used to program PLCs and change logic. HMIs are for *operation*; Eng Stations are for *configuration*.

**OT14 — Easy:** 
A Historian is a time-series database for process data.
*   **Plant Historian (L3):** High-resolution, real-time, used for local troubleshooting.
*   **Enterprise Historian (L4):** Aggregated, lower resolution, used for business KPIs and long-term trends.

**OT15 — Easy:** 
Ladder Logic is a graphical language that mimics electrical relay circuits. It is dominant because it is intuitive for electricians/technicians and is highly deterministic.

**OT16 — Easy:** 
*   **RTU:** Designed for wide-area, low-power, telemetry (e.g., pipelines).
*   **PLC:** Designed for local, high-speed, complex logic (e.g., assembly line).
*   **Deployment:** Use RTUs for remote sites with limited bandwidth/power.

**OT17 — Easy:** 
*   **Analog:** Continuous signal (voltage/current). **Digital:** On/Off.
*   **4-20mA:** 4mA is the "Live Zero." If the wire breaks, the signal drops to 0mA, allowing the system to distinguish between a "low reading" (4mA) and a "broken wire" (0mA).

**OT18 — Medium:** 
Inventory is the foundation because you cannot protect what you don't know exists.
*   **Passive:** Mirroring traffic (SPAN/TAP) to identify assets.
*   **Active:** Polling devices.
*   **Danger:** Active scanning can crash old PLCs by sending malformed packets or overloading their limited network stacks.

**OT19 — Hard:** 
*   **Tactics:** 
    1. *Initial Access* (e.g., Valid Accounts).
    2. *Execution* (e.g., Scripting).
    3. *Persistence* (e.g., Firmware modification).
    4. *Inhibit Response Function* (e.g., Disabling alarms).
    5. *Impair Process Control* (e.g., Modifying PLC logic).
*   **Difference:** Focuses on physical impact (e.g., "Loss of Control") rather than just data theft.

**OT20 — Hard:** 
*   **Collection:** Use SPAN ports/TAPs to send traffic to a SIEM without interrupting the process.
*   **Triage:** IT analysts handle the "how" (network), OT engineers handle the "what" (process impact).
*   **Firmware Alert:** Immediate verification: Check the PLC's checksum/hash and coordinate with the plant floor to see if a scheduled maintenance change occurred.
