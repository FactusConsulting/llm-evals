## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` is a dry run; it compares the current state with the configuration and shows what changes will be made without actually executing them. `tofu apply` executes the changes to reach the desired state, updating the real-world infrastructure and the state file.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file that maps your configuration to real-world resources. Remote state (stored in S3, GCS, etc.) is critical for teams to ensure a single source of truth, prevent concurrent modifications via state locking, and avoid keeping sensitive data on local machines.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an integer to create multiple resources (indexed by 0, 1, 2...). `for_each` uses a map or set to create resources (indexed by keys). `for_each` is preferred when resources are not identical or when you need to add/remove items from the middle of a list; `count` causes resource recreation/shifting if an item is removed from the middle of the list.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This is called "drift." OpenTofu detects this during the `plan` phase by refreshing the state (querying the cloud API). It compares the actual state of the resource with the state file and the configuration. `tofu plan` will show the drift and propose a change to revert the resource back to the configuration's desired state.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
`terraform_remote_state` reads the entire state file of another project to extract values. Output values are specific values exported by a module. The recommended alternative is using a "shared state" approach or a dedicated "data" module/service (like AWS SSM Parameter Store or HashiCorp Consul) to decouple modules and avoid the security risk of giving a module read access to an entire state file.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
Provisioners run *during* the resource creation phase, but outputs are calculated *after* the resource is fully created. If the output relies on a file created by `remote-exec`, the output may be empty if the resource isn't fully "complete" in the state's eyes. **Fix:** Use a `local-exec` or a separate resource to read the file from the remote host via SSH/SCP, or use a `data` source to read the resulting config file after the `null_resource` is finished.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` brings existing infrastructure into the state file. Limitation: It does not generate the HCL code; you must write the code manually to match the imported state. The `import` block (1.5+) allows you to declare the import in code, and `tofu plan` can then generate the necessary HCL configuration automatically.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is an input parameter for a module. An `input variable` allows users to customize the deployment (e.g., `region`). An `output` is a return value (e.g., the IP of a created VM) that can be seen by the user or used by other modules.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates OpenTofu HCL into API calls for a specific platform (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, it will fail because the necessary provider plugins have not been downloaded to the `.terraform` directory.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It is the dependency lock file that records the exact versions of providers used. It should be committed to ensure that every team member and the CI/CD pipeline use the exact same provider versions, preventing "it works on my machine" bugs.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all resources managed by the current state. To target a single resource, use `tofu destroy -target=aws_instance.my_vm`.

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source is a read-only query to fetch information from an existing resource. Example: Use a data source to fetch the latest Amazon Linux 2 AMI ID instead of hardcoding a specific AMI ID in a managed resource.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are inputs provided by the user. Locals are internal constants or computed values. Use locals for DRY (Don't Repeat Yourself) logic, such as concatenating a project name and environment to create a naming convention, which shouldn't be changed by the user.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block modifies resource behavior:
- `create_before_destroy`: Creates the new resource before deleting the old one (use case: zero-downtime VM replacement).
- `prevent_destroy`: Errors out if a destroy is attempted (use case: production databases).
- `ignore_changes`: Ignores drift on specific attributes (use case: ignoring tags added by an external security scanner).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells OpenTofu that a resource has changed its address (e.g., moved from root to a module). This allows OpenTofu to update the state file's mapping without destroying the actual physical resource.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
OpenTofu builds a Directed Acyclic Graph (DAG). **Implicit** dependencies occur when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit** dependencies are defined via `depends_on`. `depends_on` forces a strict order, reducing parallelism and slowing down the apply process. It should be used sparingly because implicit dependencies are cleaner and more maintainable.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1. **State Splitting:** Break the monolith into smaller states (e.g., network, db, app). *Tradeoff: More complex management/cross-state dependencies.*
2. **Targeting:** Use `-target` for specific changes. *Tradeoff: Risk of missing side-effect changes.*
3. **Refresh Disable:** Use `-refresh=false` to skip API calls. *Tradeoff: Plan may be based on stale data.*
4. **Provider Optimization:** Use specific provider versions or optimize the network/VPN. *Tradeoff: Minimal impact compared to state splitting.*

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released? How do you manually break a lock, and what are the risks?**
Locking prevents two users from modifying state simultaneously. If a process crashes, the lock remains. You can break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If you unlock while another process is actually running, you risk state corruption or conflicting infrastructure changes.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend. Describe the step-by-step process.**
1. Add the `backend "s3" { ... }` block to the configuration.
2. Run `tofu init`.
3. OpenTofu will detect the change and ask if you want to migrate the local state to the remote backend. Confirm "yes".
4. OpenTofu uploads the local `.tfstate` to S3 and configures DynamoDB for locking.
5. Verify by running `tofu plan`; it should show "No changes" if the migration was successful.

## Ansible

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
A **task** is a single unit of work (e.g., install a package). A **playbook** is a YAML file containing one or more "plays" (mapping tasks to hosts). A **role** is a structured bundle of tasks, variables, files, and templates that can be reused across different playbooks.

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary of system information gathered at the start of a play. Access the OS family via `ansible_facts['os_family']` (e.g., "Debian" or "RedHat").

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
- `command`: Executes a command without a shell (safe, no pipes/redirects). Use for simple binaries.
- `shell`: Executes through `/bin/sh` (supports pipes, wildcards). Use when shell features are needed.
- `raw`: Bypasses Python on the target; sends raw SSH commands. Use for bootstrapping Python on a new host.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means running the task multiple times results in the same state without changing the system after the first run.
- **Idempotent:** `apt: name=nginx state=present` (if nginx is there, it does nothing).
- **NOT Idempotent:** `shell: echo "config_line" >> /etc/motd` (adds the line every time the playbook runs).

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
  when: ansible_os_family == 'Debian'

- name: Install EPEL and htop on RedHat
  package:
    name: "{{ item }}"
  with_items: ['epel-release', 'htop']
  when: ansible_os_family == 'RedHat'
```
*(Note: Usually split into two tasks for clarity, but can be handled via a loop with conditionals).*

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
(Lowest to Highest): Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ `set_fact` $\rightarrow$ Extra vars (`-e`). Extra vars always win.

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible?**
1. Use `serial: 3` in the play to process in batches.
2. Define a specific group for the first 3 nodes in the inventory.
3. Use a `wait_for` task to ensure the RKE2 API (port 6443) is reachable before proceeding to the rest of the nodes.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'my_secret_password'` and paste the resulting encrypted block into the YAML file.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory is a list of managed hosts. **Static** is a fixed file (INI/YAML). **Dynamic** is a script or plugin that queries an API (e.g., AWS EC2) to generate the host list in real-time.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a task that only runs if "notified" by another task. Unlike regular tasks, they run at the end of the play. Trigger them using the `notify: handler_name` keyword in a task.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
It configures Ansible's behavior. Common settings: `inventory` (path to hosts file), `remote_user` (default SSH user), and `forks` (number of parallel processes).

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
`register` captures the output of a task into a variable.
Example:
```yaml
- shell: uptime
  register: uptime_result
- debug: msg="{{ uptime_result.stdout }}"
```

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other?**
`import_tasks` is static (parsed at startup); the tasks are "inlined" into the play. `include_tasks` is dynamic (parsed at runtime); it allows for conditional inclusion of tasks based on variables determined during the play.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Ansible Galaxy is a community hub for sharing roles/collections. Create a `requirements.yml` listing the roles, then run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types?**
Connection plugins define how Ansible talks to the host.
- `ssh`: Standard for Linux (requires Python).
- `local`: Runs tasks on the control node.
- `network_cli`: Specialized for network devices (switches/routers) that don't support Python.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example.**
`delegate_to` runs a task on a different host than the current target. `run_once` ensures the task runs only once for the entire batch.
**Example:** To update a DNS record on a local DNS server using the IP of a remote web server:
```yaml
- name: Update DNS
  uri: url="http://dns-server/api"
  delegate_to: localhost
  run_once: true
```

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify 4 strategies to improve performance.**
1. **Increase Forks:** Increase `forks` in `ansible.cfg` to run more parallel processes.
2. **Pipelining:** Enable `pipelining = True` to reduce the number of SSH connections.
3. **Fact Caching:** Use Redis or JSON file caching for `ansible_facts` to avoid gathering facts every run.
4. **Mitogen:** Use the Mitogen plugin to replace Ansible's SSH execution logic with a more efficient protocol.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet.**
- `{{ }}`: Expression/Variable interpolation.
- `{% %}`: Control logic (loops, if-statements).
- `{# #}`: Comments.
**Snippet:**
```jinja2
upstream backend {
{% for server in backend_servers %}
    # Health check for {{ server }}
    server {{ server }};
{% endfor %}
}
```

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers.**
1. Set `serial: 1` (or a small batch size).
2. **Pre-task:** Use `uri` module to check current health.
3. **LB Task:** Remove the current host from the Load Balancer.
4. **Deploy:** Update the application code/service.
5. **Health Check:** Use `uri` module to verify the app is responding on the local port.
6. **LB Task:** Add the host back to the Load Balancer.
7. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, trigger a rollback to the previous version if the health check fails.
