## SC1 — Broken Deployments After Cluster Upgrade

**SC1-A:** The pods are failing because the cluster upgraded to the **Restricted Pod Security Standard (PSS)**. Under the "Baseline" policy, `runAsNonRoot: true` is a request, but the pod can still start if the image defaults to root. Under "Restricted," Kubernetes requires that the pod **must not** run as root. Because the `chainguard/static` image defaults to `USER root` and the manifest lacks an explicit `runAsUser` (non-root ID), the Kubelet rejects the pod because it cannot guarantee the process will run as a non-root user.

**SC1-B:**
```bash
kubectl get pods -A | grep CrashLoopBackOff | awk '{print $2 " " $1}' | xargs -n2 sh -c 'kubectl get pod $1 -n $2 -o json | jq ".spec.securityContext, .spec.containers[].securityContext"'
```

**SC1-C:**
*   **Image-level fix:** Update the Dockerfile to include `USER 1000` (or any non-zero UID).
*   **Manifest fix:** Explicitly set `securityContext.runAsUser: 1000` and `runAsNonRoot: true`.
*   **CI Gate:** Integrate `kube-linter` or `conftest` (OPA) in the pipeline to fail builds if `runAsUser` is missing when `runAsNonRoot` is true.
*   **Rollout:** Use a `RollingUpdate` strategy with a `maxUnavailable: 25%` to ensure availability while the updated manifests propagate.

## SC2 — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data is due to **asynchronous replication lag**. In cross-region setups, the primary sends WAL (Write Ahead Log) records to the replica, but the primary doesn't wait for acknowledgment. If the primary fails, any WAL records not yet shipped to `eu-west-1` are lost. To quantify the loss, I would check the `pg_stat_replication` view (on the old primary if accessible) or compare the `last_wal_receive_lsn` on the promoted replica against the last known LSN of the primary.

**SC2-B:**
1.  **Import:** `terraform import aws_db_instance.primary.id <new_rds_arn>`
2.  **State Update:** Use `terraform state mv` if the resource name changed.
3.  **Code Update:** Update the HCL to reference the new ARN and update the Route53 CNAME record to point to the new endpoint.
4.  **Apply:** Run `terraform apply -target=aws_route53_record.db_endpoint` to update DNS without touching the DB instance itself.

**SC2-C:**
*   **Architecture:** Replace PgBouncer with **RDS Proxy** for native AWS failover handling and better connection pooling. Use **Route53 Application Recovery Controller (ARC)** for health-check-based DNS failover.
*   **RPO < 1s:** Use **Aurora Global Database** with "Managed Planned Failover" or "Synchronous Replication" (though sync across regions kills write latency). Aurora Global DB uses storage-level replication which is significantly faster than PG streaming.
*   **Recommendation:** Aurora Global Database is recommended because it provides a unified storage layer and faster RPO/RTO than standard RDS cross-region replicas.

## SC3 — Container Image Supply Chain Compromise

**SC3-A:** 
1.  **Containment:** Cordon the affected nodes. Use `kubectl label` to mark pods as "compromised" and isolate them via a NetworkPolicy that denies all egress/ingress.
2.  **Forensics:** 
    *   **Process Tree:** `kubectl exec <pod> -- ps auxf` or use `nsenter` on the host node to enter the container namespace.
    *   **Network:** `kubectl exec <pod> -- netstat -tulpn` or `ss -atp`.
    *   **Filesystem:** Use `kubectl cp` to pull `/tmp/.x` and run `sha256sum` on it. Use `find / -mmin -60` to find recently modified files.

**SC3-B:**
```bash
# Simplified logic: Compare digest of local image base vs upstream
BASE_IMAGE="node:20-slim"
LOCAL_DIGEST=$(docker inspect api-gateway:v2.4.1 --format='{{.RootFS.Layers}}')
REMOTE_DIGEST=$(docker pull $BASE_IMAGE && docker inspect $BASE_IMAGE --format='{{.Id}}')
if [ "$LOCAL_DIGEST" != "$REMOTE_DIGEST" ]; then echo "Base image mismatch!"; fi
# Layer analysis: docker history api-gateway:v2.4.1 | grep "dl" # Look for unexpected layers
```

**SC3-C:**
*   **Signing:** Use **Cosign** to sign images in CI.
*   **Admission:** Use **Kyverno** to block any image not signed by the company's private key.
*   **Pinning:** Use `node@sha256:...` instead of `node:20-slim`.
*   **SBOM:** Generate a CycloneDX SBOM using **Syft** and scan it with **Trivy**.
*   **Notary v2:** Provides the framework for the signature metadata and trust root, ensuring the image hasn't been tampered with between the registry and the cluster.

## SC4 — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
1.  **Sticky Sessions:** K8s pods are ephemeral. **Solution:** Move sessions to an external Redis cluster.
2.  **Local NFS:** Pods move nodes. **Solution:** Use a CSI driver for NFS or migrate to S3/Azure Files.
3.  **Oracle DB:** Heavyweight/External. **Solution:** Use a K8s `ExternalName` service or a Service of type `ClusterIP` with an endpoint pointing to the Oracle IP.
4.  **IBM MQ:** Legacy protocol. **Solution:** Deploy an MQ Client sidecar or use a dedicated MQ bridge.
5.  **Monolith Size:** Memory/CPU spikes. **Solution:** Set aggressive `requests` and `limits` and tune JVM heap (`-Xmx`) to be 75% of the container limit.

**SC4-B:**
```hcl
resource "storage_class" "nfs" {
  storage_provisioner = "nfs.csi.k8s.io"
  parameters = { server = var.nfs_server, path = var.nfs_path }
}
resource "kubernetes_persistent_volume_claim" "uploads" {
  metadata { name = "uploads-pvc" }
  spec {
    access_modes = ["ReadWriteMany"] # Necessary because multiple pods must write/read shared uploads
    storage = var.capacity
    storage_class_name = storage_class.nfs.metadata[0].name
  }
}
```

**SC4-C:**
*   **Phase 1:** Deploy the app in K8s; route 1% of traffic via F5 (Canary).
*   **Phase 2:** Migrate IBM MQ integration to a K8s-based bridge.
*   **Phase 3:** Full DNS cutover to K8s Ingress.
*   **Traffic Split:** Use F5 as the global LB, splitting traffic between the legacy VM pool and the K8s Ingress pool.
*   **Rollback:** Flip DNS/F5 weight back to 100% legacy.
*   **Metrics:** p99 latency and 5xx error rates.

## SC5 — Mysterious Latency Spike in Microservices

**SC5-A:**
1.  **Approach:** Check Jaeger traces for the `checkout` $\rightarrow$ `inventory` span. If the span is long but the `inventory` app logs show fast processing, the delay is in the Envoy sidecar or network.
2.  **Envoy Metrics:** Check `upstream_rq_time` (total) vs `upstream_cx_connect_timeout`. High `upstream_rq_time` with low app latency indicates queueing in the proxy or connection pool exhaustion.

**SC5-B:**
**SQL:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid, 
       blocking_activity.query AS blocking_query, blocked_activity.query AS blocked_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_locks.pid = blocked_activity.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype 
  AND blocking_locks.database = blocked_locks.database AND blocking_locks.relation = blocked_locks.relation
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid
WHERE NOT blocked_locks.granted;
```
**Go (Circuit Breaker):**
```go
cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{Name: "inventory-service"})
body, err := cb.Execute(func() (interface{}, error) {
    return http.Get("http://inventory-service/api/stock")
})
```

**SC5-C:**
*   **CQRS:** Use a Read Replica for the reconciliation job to avoid locking the primary write table.
*   **Bulkheads:** Create separate DB connection pools for "User Checkout" and "Admin Reconciliation."
*   **Scheduling:** Move the CronJob to 02:00 UTC.
*   **K8s:** Set a `PriorityClass` for the checkout-service and a lower one for the CronJob; use a `ResourceQuota` to ensure the CronJob cannot consume all node CPU.

## SC6 — Zero-Trust Network Overhaul

**SC6-A:** Implement **SPIFFE/SPIRE**. Each workload gets a SVID (X.509 cert). AWS workloads use IAM roles to bootstrap SPIRE; Azure uses Managed Identities. Federation is achieved by having a common Trust Bundle (Root CA) shared across all environments, allowing a service in AWS to verify the SVID of a service on-prem via the SPIRE agent.

**SC6-B:**
```hcl
resource "aws_vpc_endpoint" "endpoints" {
  for_each = var.services # ["s3", "rds", "ecr"]
  vpc_id = aws_vpc.main.id
  service_name = "com.amazonaws.${var.region}.${each.value}"
  vpc_endpoint_type = "Interface"
  subnet_ids = var.private_subnets
  security_group_ids = [aws_security_group.endpoint_sg.id]
}
```

**SC6-C:**
*   **Direct Connect:** Highest bandwidth, lowest jitter, most expensive. Fits Zero Trust by providing a stable pipe for encrypted mTLS traffic.
*   **ECMP VPN:** Cheaper, but unpredictable latency.
*   **Mesh (Tailscale/Netbird):** Best for Zero Trust. It creates an overlay network where identity is baked into the tunnel.
*   **Recommendation:** Direct Connect for the backbone, but use a Mesh (WireGuard-based) for the identity layer to decouple security from the physical network.

## SC7 — CI/CD Pipeline Causing Production Drift

**SC7-A:**
1.  **Manual Apply:** Bypasses CI tests and peer review; creates "hidden" state.
2.  **Diverged Values:** Leads to "it works in staging but not in prod" bugs.
3.  **Kubectl Edit:** Bypasses GitOps; the next `tofu apply` will overwrite these changes, causing unexpected outages.
**Risk:** Without state locking, two engineers running `apply` simultaneously can corrupt the state file, leading to resource duplication or accidental deletion.

**SC7-B:**
```yaml
stages: [validate, plan, apply]
tofu_plan:
  stage: plan
  script: [tofu fmt -check, tofu validate, tofu plan -out=tfplan]
  artifacts: [tfplan]
tofu_apply_prod:
  stage: apply
  when: manual
  script: [tofu apply tfplan]
  environment: production
```
*State locking is configured in the `backend "s3"` block using `dynamodb_table = "terraform-lock"`.

**SC7-C:**
*   **Drift Detection:** A scheduled GitLab job runs `tofu plan -detailed-exitcode`. If it returns `2` (drift detected), it alerts the team.
*   **Blocking Edit:** Use a **Kyverno** policy to deny `UPDATE` requests on ConfigMaps in the `production` namespace unless the user is the CI service account.
*   **Helm:** Use **Helmfile** to define a `common-values.yaml` and environment-specific `prod-values.yaml`.
*   **RBAC:** Remove `cluster-admin` from humans; assign `view` only. CI SA gets `edit`.

## SC8 — Observability Stack Scaling Failure

**SC8-A:**
1.  **Prometheus OOM:** High cardinality (too many unique label combinations). Check `prometheus_tsdb_head_series`.
2.  **Loki Drops:** Ingester saturation. Check `loki_ingester_push_requests_total` and S3 write latency.
3.  **Tempo Timeouts:** Querying raw traces over large time ranges without indexing. Check `tempo_query_duration_seconds`.
4.  **Thanos Lag:** Compactor cannot keep up with the volume of blocks. Check `thanos_compactor_blocks_processed_total`.

**SC8-B:**
```bash
# Get top 20 metrics by series count
curl -s "http://prom:9090/api/v1/query?query=count_values(metric_name)" | \
jq '.data.result' | sort -rnk2 | head -n 20 | awk '{print $1, $2}'
```

**SC8-C:**
*   **Mimir/VictoriaMetrics:** These scale horizontally by separating ingestion from querying.
*   **Loki Microservices:** Deploy `ingester`, `querier`, and `distributor` as separate deployments to scale independently.
*   **Tempo:** Use the S3 backend for all blocks and implement "Trace ID" indexing.
*   **Governance:** Implement **Recording Rules** to aggregate high-cardinality metrics into lower-cardinality ones. Use `relabel_configs` to drop unnecessary labels.
*   **Chargeback:** Use `prometheus_tsdb_head_series` per namespace to bill teams based on the number of series they generate.

## SC9 — Securing a Public-Facing API After a Breach

**SC9-A:**
1.  **BOLA (API1:2023):** User A accesses User B's data. **Fix:** Override `get_object` in DRF to check `request.user == obj.owner`.
2.  **Excessive Data Exposure (API3:2023):** Internal fields leaked. **Fix:** Use a dedicated `Serializer` that explicitly lists allowed fields.
3.  **Lack of Resources (API4:2023):** Scraping. **Fix:** Implement rate limiting via `Django Rest Framework` throttling or WAF.
4.  **Security Misconfig (API7:2023):** Keys in URL. **Fix:** Move keys to `Authorization: Bearer <key>` header.

**SC9-B:**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {
  # Rate limit: 100 req / 5 min
  rule {
    name = "RateLimit"
    statement { rate_based_statement { limit = 100 } }
    action { block {} }
  }
  # Block API key in query string
  rule {
    name = "NoKeyInUrl"
    statement { byte_match_statement { 
      field_to_match { query_string {} } 
      positional_constraint = "CONTAINS" 
      search_string = "api_key=" 
    } }
    action { block {} }
  }
}
```

**SC9-C:**
*   **Auth:** Transition to **OAuth2/JWT** (OpenID Connect).
*   **Gateway:** Deploy **Kong** to handle JWT validation and global rate limiting before the request hits the ALB.
*   **Audit:** Enable CloudTrail "Data Events" for the ALB to log every request.
*   **Migration:** Support both API keys and JWTs for a 30-day window. Log a warning in the response header for API key users: `Warning: API keys are deprecated`.

## SC10 — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
*   **Architecture:** **Active-Passive with Cilium Cluster Mesh**. This allows pods in Dallas to reach services in Chicago via a flat network.
*   **RPO/RTO:** 12ms latency allows for **Synchronous Replication** for PG (RPO=0). 200TB MinIO requires **Site Replication** (asynchronous), meaning RPO will be minutes.
*   **Stateful Strategy:** PG (Streaming), Redis (Sentinel), RabbitMQ (Federation), MinIO (Bucket Replication).

**SC10-B:**
```yaml
- name: Configure Patroni
  template:
    src: patroni.yml.j2
    dest: /etc/patroni.yml
  notify: restart_patroni
- name: Set Sync Replication
  postgresql_conf:
    name: "synchronous_standby_names"
    value: "dalas_node_1"
```

**SC10-C:**
1.  **Detection:** External health checks (Route53/GSLB) detect Chicago is down.
2.  **DNS:** GSLB updates CNAME to Dallas.
3.  **Promotion:** Patroni promotes Dallas PG to Primary.
4.  **State:** Sentinel promotes Dallas Redis. RabbitMQ federation switches to local queues.
5.  **Split-Brain:** Use a **Quorum** (3rd site or witness node) to prevent two primaries.
6.  **Failback:** Re-sync Chicago as a replica $\rightarrow$ verify lag $\rightarrow$ scheduled switch-back during maintenance window.
