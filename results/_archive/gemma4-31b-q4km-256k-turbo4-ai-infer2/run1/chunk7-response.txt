## Application Architecture

**AA1**: A **monolith** is a single unified codebase and deployment unit. **Microservices** break the application into small, independent services. 
*Problems introduced by microservices:* 1. **Distributed Complexity**: Harder to debug and trace requests across services. 2. **Data Consistency**: Managing transactions across multiple databases (no ACID across services). 3. **Operational Overhead**: Managing deployment, monitoring, and networking for N services instead of one.

**AA2**: **Synchronous** communication requires the caller to wait for a response (e.g., REST/gRPC). **Asynchronous** communication is "fire-and-forget" or event-based; the caller doesn't wait for the result (e.g., RabbitMQ/Kafka).

**AA3**: A **Reverse Proxy** handles basic request routing, SSL termination, and load balancing. An **API Gateway** provides higher-level business logic: authentication, rate limiting, request transformation, and API composition. A Gateway can replace a proxy, but often they are used together (Proxy for L4/L7 traffic, Gateway for API management).

**AA4**: The **Saga pattern** manages distributed transactions via a sequence of local transactions with compensating transactions for failures. 
*   **Choreography**: Services exchange events; each service knows what to do when it sees an event. (Best for simple, decoupled flows).
*   **Orchestration**: A central "orchestrator" tells services what to do. (Best for complex business workflows with many steps).

**AA5**: **CQRS** separates the data model for writing (Commands) from the model for reading (Queries). It is paired with **Event Sourcing** (storing state as a series of events) because the "read model" can be built by projecting those events. This solves the problem of complex read queries slowing down write performance in traditional CRUD.

**AA6**: The **Circuit Breaker** prevents a system from repeatedly trying to call a failing service. 
*   **States**: *Closed* (requests flow), *Open* (fails fast immediately), *Half-Open* (tests if service is back). 
*   **Difference**: Retry with backoff handles *transient* glitches; Circuit Breaker handles *systemic* failure. Use both to handle short blips (retry) while preventing total collapse (circuit breaker).

**AA7**: 
1. **Shared DB/Schema**: Lowest cost, lowest security, highest noisy-neighbor risk.
2. **Shared DB/Sep Schema**: Mid cost, better security (schema-level permissions), mid noisy-neighbor.
3. **Separate DB**: Highest cost, highest security, lowest noisy-neighbor risk.

**AA8**: **Strong consistency** ensures all reads return the latest write immediately. **Eventual consistency** allows temporary divergence. 
*   **Inventory System**: Requires **Strong Consistency**. 
*   **Architecture**: Use a relational database with ACID transactions or a distributed consensus store (e.g., Etcd or CockroachDB) using a "Linearizable" consistency level to prevent overselling.

**AA9**: A **sidecar** is a helper container running alongside the app. In Istio, **Envoy** is the sidecar (Data Plane) that handles actual traffic; **Istio** is the Control Plane that manages Envoy's config. **mTLS** between sidecars provides identity-based encryption and authentication without the application needing to manage certificates.

**AA10**: The **Strangler Fig** pattern involves incrementally replacing a monolith by wrapping it in a proxy. 
*   **Strategy**: 1. Place a proxy (API Gateway) in front of the .NET Framework monolith. 2. Identify a specific feature (e.g., "Billing"). 3. Build "Billing" as a .NET 8 microservice. 4. Route "Billing" traffic to the new service via the proxy. 5. Repeat until the monolith is empty.

**AA11**: **12-Factor App** is a set of cloud-native best practices. 
*   *Factors*: 1. Codebase (one per app), 2. Dependencies (explicitly declared), 3. Config (stored in environment), 4. Backing services (treated as attached resources), 5. Port binding (self-contained), 6. Processes (stateless). 
*   *Importance*: Ensures portability, scalability, and ease of deployment across environments.

**AA12**: 
*   **Kafka (Event-driven)**: Loose coupling, high scalability, harder to debug, ordering guaranteed per partition, failure handled via offsets. (Choose for streaming/async pipelines).
*   **REST/gRPC (Request-driven)**: Tight coupling, simpler debugging, no ordering guarantees, failure handled via timeouts/retries. (Choose for immediate request-response).

**AA13**: A **Load Balancer** distributes traffic across servers. 
*   **L4 (Transport)**: Routes based on IP/Port (fast). 
*   **L7 (Application)**: Routes based on HTTP headers, cookies, or URL paths. 
*   *Use case*: Routing `/api/users` to one service and `/api/orders` to another.

**AA14**: A **Message Queue** (RabbitMQ) deletes messages once consumed. A **Log-based Broker** (Kafka) persists messages, allowing multiple consumers to replay the log. Pick RabbitMQ for simple task queues; Kafka for event streaming and data replay.

**AA15**: A **container** shares the host OS kernel; a **VM** includes a full guest OS. Containers are popular because they are lightweight, start in seconds, and ensure "it works on my machine" consistency.

**AA16**: **Stateless** services store no client data locally (e.g., a calculator API). **Stateful** services remember client state (e.g., a database). Stateless services scale horizontally easily because any instance can handle any request.

**AA17**: An **ORM** maps database rows to language objects (e.g., Hibernate for Java, Entity Framework for C#). 
*   *Trade-offs*: ORMs increase developer productivity and portability but can introduce performance overhead ("N+1 query problem") compared to raw SQL.

**AA18**: **Bulkheads** isolate resources so a failure in one area doesn't exhaust resources for others. 
*   *Implementation*: Use separate thread pools for different downstream services. If the "Payment" service hangs, the "Catalog" service's thread pool remains available, keeping the rest of the app responsive.

**AA19**: **OT (Operational Transformation)** requires a central server to resolve conflicts. **CRDTs** allow decentralized merging via mathematical rules. 
*   *Offline Support*: **CRDTs** are superior for offline editing because they allow local changes to merge seamlessly without a central coordinator.

**AA20**: **Challenges**: Context propagation requires passing a `TraceID` through every hop. 
*   **Sampling**: Head-based (decide at start) vs Tail-based (decide after the trace is complete). 
*   **Kafka**: Trace continuity is ensured by injecting the trace context into the Kafka message headers, which the consumer extracts to continue the span.

## On-Premise Infrastructure Architecture

**OP1**: **Type 1 (Bare-metal)** runs directly on hardware (e.g., VMware ESXi, Proxmox/KVM). **Type 2 (Hosted)** runs on top of an OS (e.g., VirtualBox, VMware Workstation).

**OP2**: **SAN (Storage Area Network)** provides block-level storage via iSCSI or Fibre Channel (high performance, looks like a local disk). **NAS (Network Attached Storage)** provides file-level storage via NFS or SMB (shared folders).

**OP3**: **3-Tier** (Core $\rightarrow$ Distribution $\rightarrow$ Access) is hierarchical. **Leaf-Spine** is a flat topology where every leaf connects to every spine. It solves the "East-West" traffic bottleneck, providing predictable latency and massive bandwidth for server-to-server communication.

**OP4**: **Architecture**: 3+ nodes for quorum. **Shared Storage**: Ceph (distributed) or iSCSI (centralized). **Fencing**: STONITH (Shoot The Other Node In The Head) prevents two nodes from writing to the same disk. If a node fails, the cluster detects the loss of heartbeat and migrates VMs to healthy nodes.

**OP5**: **VLAN Trunking** allows multiple VLANs to travel over one physical link using **802.1Q** tags. On Linux, you create tagged sub-interfaces (e.g., `ip link add link eth0 name eth0.10 type vlan id 10`).

**OP6**: 
*   **RAID 1**: Mirroring. **RAID 5**: Parity (1 drive fail). **RAID 6**: Double parity (2 drive fail). **RAID 10**: Mirror + Stripe. **RAID Z2**: ZFS double parity. 
*   **Choice**: **RAID 10** for a database server to maximize IOPS and provide redundancy.

**OP7**: **Architecture**: Internal AD DNS for internal resolution; separate authoritative servers for the public zone. **Split-horizon** ensures internal users get internal IPs and external users get public IPs. **VPN**: The laptop receives a DNS suffix via DHCP/VPN config to resolve internal names.

**OP8**: **Chain**: Root CA (Offline/Air-gapped) $\rightarrow$ Subordinate CA $\rightarrow$ End-entity. **CRL** is a list of revoked certs; **OCSP** is a real-time check. 
*   **Compromise**: A Sub CA compromise affects one branch; a Root CA compromise destroys the entire trust anchor for the organization.

**OP9**: 
*   **MPLS**: High cost, guaranteed QoS. **VPN**: Low cost, unpredictable. **SD-WAN**: Flexible, software-defined. **WireGuard**: High performance, peer-to-peer. 
*   **Recommendation**: **SD-WAN** for 50 users/site with VoIP, as it allows prioritizing voice traffic (QoS) over multiple internet links.

**OP10**: **iDRAC/iLO/IPMI** are Out-of-Band (OOB) management interfaces. They allow power control and console access even if the OS is crashed. If exposed to the internet, an attacker can gain full hardware-level control of the server.

**OP11**: **LVM** provides flexible volume management. **LVM-Thin** allows over-provisioning (virtual size > physical). **ZFS** is a combined FS/Volume manager with Copy-on-Write (CoW). ZFS snapshots are near-instant and highly efficient due to CoW.

**OP12**: **Stretch Cluster**: Requires a 3rd site (witness) to prevent split-brain. **Ceph CRUSH** rules must be set to ensure replicas are placed in different sites. 2-site Ceph is dangerous because if the link breaks, neither site has a majority (quorum), causing the storage to go read-only.

**OP13**: **DORA**: Discover $\rightarrow$ Offer $\rightarrow$ Request $\rightarrow$ Acknowledge. If the server is unavailable, Windows clients assign themselves an **APIPA** address (169.254.x.x).

**OP14**: **Unmanaged** is a basic plug-and-play switch. **Managed** allows VLANs, Spanning Tree Protocol (STP) to prevent loops, SNMP monitoring, and Port Mirroring for traffic analysis.

**OP15**: **NTP** synchronizes clocks. Drift causes: 1. Kerberos authentication failures (time skew), 2. Log correlation failure, 3. Cluster heartbeat timeouts leading to unnecessary failovers.

**OP16**: **Physical**: Bare metal. **VM**: Hardware abstraction. **Container**: OS abstraction. Use **Bare Metal** for workloads requiring maximum I/O, direct GPU access, or very low latency (e.g., high-frequency trading).

**OP17**: **UPS** provides immediate battery power for short-term gaps. **Generator** provides long-term power via fuel. **ATS** (Automatic Transfer Switch) detects power loss and switches the load from the utility grid to the generator.

**OP18**: **Active-Passive**: One standby. **Active-Active**: Both process load. 
*   **PostgreSQL HA**: Use **Pacemaker/Corosync** to manage a Virtual IP (VIP). If the primary fails, Pacemaker uses **STONITH** to kill the failed node and moves the VIP to the standby.

**OP19**: **3-2-1 Rule**: 3 copies, 2 different media, 1 offsite. **RPO** (how much data loss is okay), **RTO** (how long to be down). **Immutable backups** (WORM) prevent ransomware from deleting backups. **Backup** is a copy of data; **DR** is the plan to restore the entire business function.

**OP20**: **802.1X**: **Supplicant** (Device) $\rightarrow$ **Authenticator** (Switch) $\rightarrow$ **Auth Server** (RADIUS). **EAP-TLS** uses certificates; **PEAP** uses passwords. **MAB** allows non-802.1X devices (printers) to connect by whitelisting their MAC address.
