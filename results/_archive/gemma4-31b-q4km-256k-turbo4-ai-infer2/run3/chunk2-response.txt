## Kubernetes

**K1 — Easy:** A **Deployment** is used for stateless applications; it manages a set of identical pods and ensures the desired number of replicas are running. A **StatefulSet** is for stateful applications; it provides stable, unique network identities (e.g., `pod-0`, `pod-1`) and stable persistent storage that persists across pod rescheduling.

**K2 — Easy:** A **ClusterIP** service provides a stable internal virtual IP. When a request hits this IP, `kube-proxy` (via iptables or IPVS) intercepts the traffic and load-balances it across the current set of healthy pod IPs associated with that service's selector.

**K3 — Medium:** 
- **PersistentVolume (PV):** A piece of storage in the cluster (the actual "disk").
- **PersistentVolumeClaim (PVC):** A user's request for storage (the "ticket").
- **StorageClass (SC):** A template that defines the "type" of storage (e.g., SSD vs HDD) and allows for dynamic provisioning.
- **Relation:** A user creates a PVC $\rightarrow$ K8s looks for a matching PV or uses a StorageClass to dynamically provision a PV $\rightarrow$ The PVC binds to the PV.

**K4 — Medium:** 
1. `kubectl logs <pod>`: Check application logs for runtime crashes or panic messages.
2. `kubectl describe pod <pod>`: Check "Events" for OOMKilled, failed probes, or scheduling issues.
3. Check **Liveness/Readiness probes**: Ensure the app isn't being killed because it's taking too long to start.
4. Check **Resource Limits**: Verify if the pod is hitting its memory limit (OOMKilled).

**K5 — Medium:** CoreDNS provides service discovery. It allows pods to resolve service names (e.g., `my-svc.default.svc.cluster.local`) to internal IPs. If CoreDNS pods are down, internal DNS resolution fails, and pods will be unable to communicate with other services via name, though IP-based communication still works.

**K6 — Hard:** The scheduler uses a two-step process:
1. **Filtering (Predicates):** Removes nodes that don't meet requirements (e.g., insufficient CPU/RAM, Taints, NodeSelector).
2. **Scoring (Priorities):** Ranks remaining nodes to find the "best" fit.
**Factors:** Resource fragmentation (LeastRequested), Image locality (node already has the image), and Node Affinity/Anti-affinity.

**K7 — Hard:** **Yes, it will be scheduled.** Total requested is $3.5\text{GB} + 256\text{Mi} \approx 3.75\text{GB}$, which is less than 4GB. However, if the pod uses 600Mi at runtime, it exceeds its `limits.memory` (512Mi) and will be **OOMKilled** by the kernel.

**K8 — Hard:** 
External LB $\rightarrow$ Ingress Controller (NGINX Pod) $\rightarrow$ Ingress Resource (Rules) $\rightarrow$ Service (Virtual IP) $\rightarrow$ Endpoints (List of Pod IPs) $\rightarrow$ `kube-proxy` (iptables/IPVS) $\rightarrow$ Target Pod.

**K9 — Medium:** A NetworkPolicy is an L3/L4 firewall for pods. If no policy exists, all traffic is allowed (default allow). Once a policy is applied to a pod, that pod becomes "isolated," and only traffic explicitly allowed by the policy is permitted.

**K10 — Medium:** **RollingUpdate** replaces pods gradually to ensure zero downtime. **Recreate** kills all existing pods before starting new ones. Use **Recreate** when the application cannot support two different versions running simultaneously (e.g., a database migration that changes the schema).

**K11 — Easy:** A namespace is a virtual partition within a cluster. Default namespaces: `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

**K12 — Easy:** `kubectl describe pod` provides detailed metadata. It shows: 1. Pod Events (e.g., Pulling image), 2. Container exit codes/restarts, 3. Volume mount details.

**K13 — Easy:** A ConfigMap stores non-confidential configuration. A pod can consume it as: 1. Environment variables, 2. Mounted files in a volume.

**K14 — Easy:** 
- **ClusterIP:** Internal only.
- **NodePort:** Exposes service on a static port on every Node IP.
- **LoadBalancer:** Provisions a cloud provider LB that routes to the NodePort.

**K15 — Easy:** A DaemonSet ensures a copy of a pod runs on *every* node (or a subset). Use it for infrastructure agents like Fluentd (logging), Prometheus Node Exporter, or CNI plugins.

**K16 — Medium:** 
- **Taints/Tolerations:** Taints are on nodes (repel pods). Tolerations are on pods (allow them to stay on tainted nodes). *Use case: Taint GPU nodes so only GPU-enabled pods land there.*
- **Node Affinity:** Pods "prefer" or "require" certain nodes. *Use case: Ensure a pod runs in a specific availability zone.*

**K17 — Medium:** An Operator is a custom controller that uses Custom Resource Definitions (CRDs) to manage complex applications. It encodes "operational knowledge" (e.g., how to backup a DB) into code. It differs from a standard controller by managing domain-specific application state, not just K8s primitives.

**K18 — Hard:** etcd uses the **Raft** consensus algorithm (Strong Consistency). If quorum is lost (e.g., 2/3 nodes fail), the cluster becomes read-only or unresponsive. To recover from 2/3 loss, you must restore from a snapshot backup to a new cluster or a single-member cluster.

**K19 — Hard:** RBAC links Users/Groups to Permissions. 
- **Role/ClusterRole:** Defines *what* can be done (verbs) on *which* resources.
- **RoleBinding/ClusterRoleBinding:** Links the Role to the User.
**Manifests:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: {namespace: my-ns, name: pod-reader}
rules: [{apiGroups: [""], resources: ["pods", "pods/log"], verbs: ["get", "list", "watch"]} ]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: {namespace: my-ns, name: read-pods-binding}
subjects: [{kind: User, name: dev-user}]
roleRef: {kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io}
```

**K20 — Hard:** `ndots:5` causes the resolver to append search suffixes (e.g., `.default.svc.cluster.local`) five times before trying the absolute name. This causes excessive DNS queries. **Fix:** Set `dnsConfig` in the pod spec to `ndots: 1` or use fully qualified domain names (ending in a dot).

## Development

**D1 — Easy:** `merge` preserves history and creates a merge commit. `rebase` rewrites history by moving the branch base to the latest commit, creating a linear history. **Avoid rebasing** public/shared branches as it rewrites history and breaks other developers' clones.

**D2 — Easy:** **TCP** is connection-oriented, reliable, and ordered (HTTP, SSH). **UDP** is connectionless, faster, and allows packet loss (DNS, VoIP).

**D3 — Medium:** A race condition occurs when the outcome depends on the non-deterministic timing of threads. **Example:** Two threads incrementing a shared variable `count++` simultaneously; both read `10`, both increment to `11`, and the final result is `11` instead of `12`.

**D4 — Medium:** **Symmetric:** One key for both encryption/decryption (AES). **Asymmetric:** Public key encrypts, private key decrypts (RSA). **TLS:** Asymmetric encryption is used for the initial handshake to securely exchange a symmetric session key, which is then used for the actual data transfer.

**D5 — Medium:** A layer is a read-only snapshot of the filesystem. Docker caches layers; if a line in the Dockerfile hasn't changed, Docker reuses the cached layer. **Best Practice:** Put stable instructions (OS, dependencies) at the top and frequently changing code at the bottom to maximize cache hits.

**D6 — Medium:** 
1. **Logs:** Check application logs for unhandled exceptions.
2. **Health Checks:** Check if the app is failing Liveness/Readiness probes.
3. **Resources:** Check for OOMKills or CPU throttling.
4. **Upstream:** Check if a downstream dependency (DB, API) is timing out.

**D7 — Hard:** **CAP Theorem:** A distributed system can only provide two of three: Consistency, Availability, and Partition Tolerance.
- **CP (Consistency/Partition):** MongoDB/etcd (will stop accepting writes if quorum is lost).
- **AP (Availability/Partition):** Cassandra/DynamoDB (allows writes during partition, resolves conflicts later).

**D8 — Medium:** **Horizontal:** Adding more machines (requires statelessness and a Load Balancer). **Vertical:** Adding more CPU/RAM to one machine. **Patterns:** Stateless architecture, externalized session management (Redis), and service discovery.

**D9 — Easy:** An environment variable is a dynamic value available to a process. To persist on Linux, add `export VAR=value` to `~/.bashrc` or `~/.profile`.

**D10 — Easy:** **JSON** is a strict, lightweight data format. **YAML** is a human-readable superset of JSON. **JSON Advantage:** Faster parsing/standardization. **YAML Advantage:** Readability and support for comments.

**D11 — Easy:** A REST API is an architectural style for network services. 
- **GET:** Retrieve data.
- **POST:** Create new resource.
- **PUT:** Update/Replace resource.
- **DELETE:** Remove resource.

**D12 — Easy:** Version pinning is specifying an exact version (e.g., `1.4.2` instead of `^1.4.0`). It ensures that every build uses the exact same dependency versions, preventing "it works on my machine" bugs caused by silent updates.

**D13 — Easy:** **Compiled:** Translated to machine code before execution (Go, Rust). **Interpreted:** Executed line-by-line by a runtime (Python, Ruby).

**D14 — Medium:** A **Reverse Proxy** sits in front of servers and handles requests for them. A **Forward Proxy** sits in front of clients to hide them. 
- **NGINX:** Used for load balancing.
- **HAProxy:** Used for high-performance traffic routing.

**D15 — Medium:** A deadlock is a state where two or more processes are waiting for each other to release resources. **Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** Eventual consistency means that if no new updates are made, all replicas will eventually converge to the same value. **Cassandra** handles this via tunable consistency: `ONE` (fast, low consistency), `QUORUM` (majority), or `ALL` (slow, high consistency). Read-after-write is achieved by ensuring $R + W > N$ (where $R$=read nodes, $W$=write nodes, $N$=replication factor).

**D17 — Hard:** **mTLS** requires both client and server to present certificates. **Handshake:** Server sends cert $\rightarrow$ Client verifies $\rightarrow$ Client sends its cert $\rightarrow$ Server verifies $\rightarrow$ Symmetric key established. Commonly used in **Service Meshes** (Istio/Linkerd) for zero-trust security.

**D18 — Hard:** A hash table uses a hash function to map keys to array indices. 
- **Collision Resolution:** **Chaining** (linked lists at each index) or **Open Addressing** (finding the next empty slot).
- **Complexity:** Average: $O(1)$ for all. Worst: $O(n)$ if all keys hash to the same index.

**D19 — Hard:** A **Circuit Breaker** prevents a failing service from overloading the system. 
- **Closed:** Traffic flows normally.
- **Open:** Service is failing; requests fail immediately without hitting the service.
- **Half-Open:** Periodically allows a few requests to see if the service has recovered.
It prevents "retry storms" by failing fast rather than waiting for timeouts.

**D20 — Hard:** 
- **Optimistic:** Assume no conflict; check for changes at the end (e.g., using a `version` column). If the version changed, the update fails. Use for low-contention environments.
- **Pessimistic:** Lock the record immediately (e.g., `SELECT FOR UPDATE`). Use for high-contention environments where conflicts are frequent.
