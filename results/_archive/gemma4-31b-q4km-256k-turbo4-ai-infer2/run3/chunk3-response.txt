## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry run that compares the current state with the desired configuration and shows what changes will be made. `tofu apply` actually executes those changes to reach the desired state.

**T2 — Easy:** State is a JSON file that maps your configuration to real-world resources. Remote state (stored in S3, GCS, etc.) is critical for team collaboration, as it provides a single source of truth and enables state locking to prevent concurrent modifications.

**T3 — Medium:** `count` creates resources based on an integer index (list). `for_each` creates resources based on a map or set of keys. `for_each` is preferred because removing an item from the middle of a `count` list causes all subsequent resources to be shifted and potentially recreated; `for_each` targets specific keys, avoiding this.

**T4 — Medium:** This is called "drift." OpenTofu detects this during the `plan` phase by refreshing the state against the actual cloud API. It will show a diff and attempt to revert the manual change to match the code during the next `apply`.

**T5 — Medium:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345"
  instance_type  = "t3.micro"
  tags = { Name = each.key }
}
```

**T6 — Hard:** `terraform_remote_state` reads the state file of another project, while `outputs` are values exported by the current module. The recommended alternative is to use a shared "data" module or a dedicated state management tool (like a Key-Value store) to avoid tight coupling between different state files.

**T7 — Hard:** `null_resource` provisioners run during the apply phase, but the output is calculated based on the resource's state. If the provisioner fails or hasn't finished, the output is empty. **Fix:** Use a `local-exec` or a dedicated provider that manages the lifecycle, or use a `depends_on` chain ensuring the resource is fully created before the output is accessed.

**T8 — Medium:** `tofu import` brings existing infrastructure into the state file. Limitation: The CLI command is imperative and requires manual state mapping. The `import` block (1.5+) is declarative, allowing you to define the import in code, which enables version control and automatic code generation.

**T9 — Easy:** A variable is an input parameter for a module. An `input variable` allows users to customize the deployment; an `output` is a return value used to export information (like an IP address) for other modules or the user.

**T10 — Easy:** A provider is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS, Azure). If you run `plan` without `init`, OpenTofu will fail because the necessary provider binaries have not been downloaded.

**T11 — Easy:** The `.terraform.lock.hcl` file locks the specific versions of providers used. It should be committed to version control to ensure that every team member and the CI/CD pipeline use the exact same provider versions, preventing "it works on my machine" bugs.

**T12 — Easy:** `tofu destroy` deletes all resources managed by the state. To target a single resource: `tofu destroy -target=aws_instance.web[0]`.

**T13 — Easy:** A data source is a read-only query of existing infrastructure. Use it when you need information about a resource you didn't create in the current project (e.g., fetching the latest Amazon Linux 2 AMI ID).

**T14 — Medium:** Variables are external inputs; locals are internal constants or computed values. Use locals to avoid repeating the same complex expression multiple times throughout your code (DRY principle).

**T15 — Medium:** The `lifecycle` block modifies resource behavior:
- `create_before_destroy`: Creates the new resource before deleting the old one (essential for zero-downtime updates).
- `prevent_destroy`: Prevents the resource from being deleted (safety for DBs).
- `ignore_changes`: Ignores drift on specific attributes (e.g., ignore tags managed by an external security tool).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module. This allows you to refactor your code without OpenTofu thinking the old resource was deleted and a new one was created.

**T17 — Hard:** OpenTofu builds a Directed Acyclic Graph (DAG) to determine the order of operations. **Implicit dependencies** occur when one resource references another's attribute. **Explicit dependencies** use `depends_on`. `depends_on` forces a strict sequence, reducing parallelism and slowing down the apply process; it should be used only when a dependency isn't detectable via attributes.

**T18 — Hard:** 
1. **State Splitting:** Break the monolith into smaller states/workspaces (reduces API calls per plan).
2. **Targeting:** Use `-target` for specific changes (skips unrelated resources).
3. **Refresh Optimization:** Use `-refresh=false` if you know the state is current.
4. **Provider Optimization:** Reduce the number of data sources or use cached data.
*Tradeoff:* Splitting increases management complexity; targeting can lead to inconsistent states.

**T19 — Hard:** State locking prevents two people from modifying the state simultaneously. If a crash occurs, the lock remains. You manually break it with `tofu force-unlock <lock-id>`. **Risk:** If you unlock while another process is actually running, you risk state corruption.

**T20 — Hard:** 
1. Update the `backend` block to S3/DynamoDB.
2. Run `tofu init`.
3. OpenTofu will detect the backend change and prompt to migrate the local state to S3.
4. Confirm migration.
5. Verify by running `tofu state list` to ensure all resources are present in the remote state.

## Ansible

**A1 — Easy:** A **playbook** is a YAML file containing one or more "plays" (the overall workflow). A **role** is a reusable package of tasks, variables, and templates. A **task** is a single unit of action (e.g., "install nginx").

**A2 — Easy:** `ansible_facts` is a dictionary of system information gathered at the start of a play. Access OS family via: `ansible_facts['os_family']` (e.g., "Debian" or "RedHat").

**A3 — Medium:** 
- `command`: Most secure; does not execute through a shell (no pipes/wildcards).
- `shell`: Executes through `/bin/sh`, allowing pipes, redirects, and environment variables.
- `raw`: Bypasses Python on the target; used for bootstrapping Python or managing devices without Python.

**A4 — Medium:** Idempotency means running a task multiple times results in the same state without changing the system if it's already correct. 
- **Idempotent:** `apt: name=nginx state=present` (won't reinstall if already there).
- **Not Idempotent:** `shell: echo "config" >> /etc/myapp.conf` (appends the line every time).

**A5 — Medium:**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'epel-release' }}"
  when: ansible_os_family in ['Debian', 'RedHat']
- name: Install htop on RedHat
  package:
    name: htop
  when: ansible_os_family == 'RedHat'
```
*(Alternatively, use a list of packages with a conditional variable).*

**A6 — Hard:** Precedence (lowest to highest): Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ Playbook vars $\rightarrow$ `set_fact` $\rightarrow$ Extra vars (`-e`). `extra_vars` always wins.

**A7 — Hard:** 
- Use `serial: 3` to process in batches.
- Define a group `[first_batch]` and `[remaining_nodes]` in inventory.
- Use the `wait_for` module to ensure the RKE2 API port (6443) is open on the first 3 nodes before proceeding to the rest.

**A8 — Medium:** `ansible-vault` encrypts sensitive data. To encrypt a single variable: use `ansible-vault encrypt_string 'my_password' --name 'db_password'`. This allows you to keep the rest of the YAML file in plain text.

**A9 — Easy:** An inventory is a list of managed hosts. **Static** is a fixed file (INI/YAML). **Dynamic** is a script or plugin that queries a cloud provider (AWS/Azure) to generate the host list in real-time.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`.

**A11 — Easy:** A handler is a task that only runs if "notified" by another task that reported a "changed" status. Trigger it using the `notify: handler_name` keyword in a task.

**A12 — Easy:** `ansible.cfg` configures Ansible's behavior. Common settings: `remote_user` (default SSH user), `inventory` (path to host file), and `forks` (number of parallel processes).

**A13 — Easy:** `register` captures the output of a task into a variable. 
Example: `shell: uptime register: uptime_result`. Use it later: `debug: msg="{{ uptime_result.stdout }}"`.

**A14 — Medium:** `import_tasks` is static (processed at parse time); `include_tasks` is dynamic (processed at runtime). Use `include_tasks` when the decision to include the file depends on a variable or condition evaluated during the play.

**A15 — Medium:** Ansible Galaxy is a community hub for roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:** Connection plugins define how Ansible talks to the host. 
- `ssh`: Standard for Linux.
- `local`: Runs on the control node.
- `network_cli`: Specialized for network devices (switches/routers) that don't support full shell access.

**A17 — Hard:** `delegate_to` runs a task on a host other than the current one in the loop. `run_once` ensures the task runs only once for the entire batch. 
*Example:* Use `delegate_to: localhost` and `run_once: true` to update a central DNS record using the IP of the first host in the current group.

**A18 — Hard:** 
1. **Forks:** Increase `forks` in `ansible.cfg` to increase parallelism.
2. **Pipelining:** Enable `pipelining = True` to reduce SSH connections.
3. **Fact Caching:** Use Redis or JSON file caching to avoid gathering facts every run.
4. **Mitogen:** Use the Mitogen plugin to replace the SSH transport for massive speed gains.
*Tradeoff:* Higher forks increase CPU/RAM load on the control node.

**A19 — Hard:** 
- `{{ }}`: Variable interpolation.
- `{% %}`: Control logic (loops/conditionals).
- `{# #}`: Comments.
```jinja2
upstream backend {
  {# Health check enabled #}
  {% for server in backend_servers %}
  server {{ server }};
  {% endfor %}
}
```

**A20 — Hard:** 
1. Set `serial: 1` (or a small percentage).
2. **Pre-task:** Use `uri` module to check health.
3. **Task:** Remove server from Load Balancer $\rightarrow$ Update App $\rightarrow$ Health check with `uri` module.
4. **Post-task:** Add server back to LB.
5. **Rollback:** Wrap the update in a `block`. In the `rescue` section, trigger a task to revert the app version and alert the admin.
