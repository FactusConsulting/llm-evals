## Kubernetes

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** manages stateless applications where pods are interchangeable; any pod can replace another without maintaining identity or specific ordering. A **StatefulSet** manages stateful applications (like databases) where each pod has a unique, persistent identifier (e.g., `web-0`, `web-1`), stable network identity, and dedicated persistent storage.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
The `ClusterIP` provides a virtual IP address reachable only within the cluster. The `kube-proxy` component on each node maintains iptables/IPVS rules that intercept traffic sent to this virtual IP and perform Network Address Translation (NAT) to forward the request to the IP of a healthy pod selected by the Service's selector.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage provisioned by an administrator (the "physical" resource).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user (the "ticket"). It specifies size and access modes.
*   **StorageClass:** Defines different types of storage (e.g., SSD vs. HDD) and allows for dynamic provisioning. 
*   **Relationship:** A user creates a PVC; if a matching **StorageClass** exists, it dynamically provisions a PV. If not, the PVC waits for a manually created PV that meets its requirements.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps.**
1.  Check logs using `kubectl logs <pod_name> --previous` to see why the previous instance crashed.
2.  Run `kubectl describe pod <pod_name>` to check for events like OOMKills or failed liveness/readiness probes.
3.  Verify configuration integrity by checking ConfigMaps and Secrets mounted to the pod.
4.  Inspect resource limits (CPU/Memory) to ensure the application isn't being throttled or killed due to memory exhaustion.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS provides internal service discovery, allowing pods to resolve names like `my-service.default.svc.cluster.local`. If CoreDNS pods are down, internal service discovery fails—pods will be unable to communicate with each other via service names, though they may still reach each other via direct IP addresses.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**
The scheduler uses a two-step process:
1.  **Filtering (Predicates):** It eliminates nodes that don't meet requirements (e.g., insufficient CPU/RAM, taints without tolerations).
2.  **Scoring (Priorities):** It ranks remaining nodes based on factors such as:
    *   **Resource Balance:** Preferring nodes with more free resources to avoid hotspots.
    *   **Image Locality:** Preferring nodes that already have the container image cached.
    *   **Pod Affinity/Anti-affinity:** Ensuring pods stay near or away from specific peers.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
Yes, it will be scheduled because only **requests** are used for scheduling decisions ($3.5\text{GB} + 256\text{Mi} < 4\text{GB}$). If it tries to use $600\text{Mi}$, the Kubernetes **OOMKiller** will terminate the process because it exceeds its defined limit of $512\text{Mi}$.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller.**
1.  External Load Balancer receives traffic and forwards it to the NodePort/LoadBalancer IP of the Ingress Controller.
2.  The **NGINX Ingress Controller** receives the request, matches the Host/Path against rules in the Ingress resource.
3.  The Controller identifies the target **Service**.
4.  `kube-proxy` (via iptables/IPVS) routes the packet from the Service's virtual IP to the specific Pod IP found in the **Endpoints** object.
5.  The packet reaches the application container inside the Pod.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A NetworkPolicy acts as a firewall for pods, controlling ingress/egress traffic at the L3/L4 level. By default, all namespaces are "open" (allow all). When you apply a policy selecting specific pods, those pods become isolated based on the policy; if they aren't explicitly allowed in the new policy, their traffic will be dropped.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old pods with new ones, ensuring zero downtime but potentially running two versions of an app simultaneously.
*   **Recreate:** Kills all existing pods before starting new ones, causing downtime. 
*   **Choose Recreate:** Use it when the application cannot handle two different versions running at once (e.g., a database schema change that isn't backward compatible).

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A Namespace is a virtual cluster within a physical cluster used to partition resources and provide logical isolation. The default namespaces are `default`, `kube-system` (for system components), and `kube-public`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
It provides detailed metadata about a specific resource. It shows:
1.  Events (e.g., "Pulling image", "Failed scheduling").
2.  Container status details (e.g., Restart counts, specific exit codes).
3.  Resource usage/limits vs actual requests.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A ConfigMap stores non-confidential key-value pairs. Pods consume them via:
1.  **Environment Variables:** Injecting keys as environment variables into the container.
2.  **Volume Mounts:** Mounting the ConfigMap as a file in a directory (useful for config files like `nginx.conf`).

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Internal only; provides an IP reachable inside the cluster.
*   **NodePort:** Exposes the service on a specific port across all nodes' external IPs.
*   **LoadBalancer:** Provisions a cloud provider's load balancer to route external traffic to the service.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A DaemonSet ensures that one copy of a pod runs on every node (or a subset of nodes) in the cluster. Use it for infrastructure tasks like log collection (`fluentd`), monitoring agents (`Prometheus Node Exporter`), or networking plugins. Use a **Deployment** for standard application scaling where pods can live on any available node.

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each.**
*   **Taints/Tolerations:** A "repellent" mechanism. Taints are applied to Nodes to repel pods; Tolerations allow specific pods to stay there. *Use Case:* Keeping pods off master nodes.
*   **Node Affinity:** An "attraction" mechanism. It tells a Pod which nodes it *prefers* or *must* run on. *Use Case:* Ensuring a high-memory app only runs on instances with NVMe drives.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An Operator is a custom controller that encodes human operational knowledge into software. While a standard controller manages generic resources (like Deployments), an Operator manages complex stateful apps (like a Postgres Cluster). It solves the problem of automating manual operations like backups, failovers, and version upgrades for complex systems.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
Etcd uses the **Raft consensus algorithm**, providing strong consistency. Quorum requires $n/2 + 1$ nodes to be healthy ($>50\%$). If quorum is lost, the cluster becomes read-only or unavailable. To recover from losing 2 out of 3 nodes, you must restore data from a backup onto new nodes and manually re-initialize the cluster members.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
RBAC defines permissions based on "Who" can do "What".
*   **Role:** Permissions within a specific namespace.
*   **ClusterRole:** Permissions across the whole cluster.
*   **RoleBinding:** Binds a Role to a user/group in a namespace.
*   **ClusterRoleBinding:** Binds a ClusterRole to a user/group globally.

*Manifest:*
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev-ns
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-read-only
  namespace: dev-ns
subjects:
- kind: User
  name: developer-user
  user: "dev-user"
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
The `ndots` setting determines how many dots are in a domain name before the resolver tries to append the search path (e.g., `svc.cluster.local`). If `ndots` is high (default 5), a query like `google.com` might be tried as `google.com.default.svc.cluster.local`, etc., causing multiple failed lookups before succeeding. Fix this by setting `ndots: 1` or specifically defining the `nameservers` in the `dnsConfig` section of the Pod's `spec`.

## Development

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
*   **Merge:** Combines two branches by creating a new "merge commit" that joins histories. It preserves the chronological history exactly.
*   **Rebase:** Moves the base of your branch to a new starting point, rewriting history to appear linear.
*   **Avoid Rebase:** Never rebase commits on a public/shared branch because it rewrites history and will cause conflicts for other collaborators.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP:** Connection-oriented, guarantees delivery and order via handshakes and acknowledgments. *Examples:* HTTP, SSH.
*   **UDP:** Connectionless, sends packets without verifying receipt (faster). *Examples:* DNS, VoIP/Streaming.

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A race condition occurs when the output depends on the timing/sequence of uncontrollable events (e.g., multiple threads accessing shared memory).
*Example (Python):* Two threads try to increment `counter += 1` simultaneously. Since `+=` is not atomic, both might read the value `5`, add 1, and write back `6`, resulting in one lost increment instead of `7`.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric:** Same key for encryption/decryption (Fast).
*   **Asymmetric:** Public key encrypts; Private key decrypts (Slow but secure key exchange).
*   **TLS Usage:** Asymmetric encryption is used during the **handshake** to securely exchange a "session key." Once established, Symmetric encryption uses that session key for the actual data transfer.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
Each instruction in a Dockerfile (`RUN`, `COPY`) creates a new immutable layer. If an instruction changes, all subsequent layers must be rebuilt. Best practice: Place instructions that change frequently (like copying source code) at the bottom of the file and stable dependencies (installing packages) at the top to maximize cache hits.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check.**
1.  Check Load Balancer logs (to see if it's reaching the app or failing before).
2.  Monitor Resource Utilization (CPU/Memory spikes causing crashes).
3.  Check Downstream Dependencies (Is a database or third-party API timing out?).
4.  Review Application Logs (Look for specific stack traces or connection pool exhaustion errors).

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
CAP states a distributed system can only provide two of three: Consistency, Availability, Partition Tolerance.
*   **CP (Consistency + Partition):** **Etcd** or **HBase**. They prioritize data being correct across nodes even if some nodes are unreachable.
*   **AP (Availability + Partition):** **Cassandra** or **DynamoDB**. They ensure the system stays up and accepts writes even if consistency is temporarily "eventual."

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical:** Adding more power (RAM/CPU) to an existing server.
*   **Horizontal:** Adding more machines to the cluster.
*   **Patterns:** Load Balancing, Database Sharding, Microservices architecture, and Stateless design.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An env var is a dynamic value used by processes (e.g., `PATH`). To persist it in Linux, add an export command to your shell configuration file (e.g., `.bashrc` or `.zshrc`) like `export API_KEY="secret"`.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
JSON is a lightweight, language-independent data format using braces `{}`. YAML is a human-friendly superset of JSON using indentation. 
*   **Advantage:** JSON is faster for machine parsing; YAML is much easier for humans to read/write as config files.

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
REST is an architectural style for building networked applications via standard HTTP.
*   **GET:** Retrieve data (Read).
*   **POST:** Create new resource.
*   **PUT:** Update existing resource (Replace entire object).
*   **DELETE:** Remove a resource.

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
Version pinning specifies exact versions (e.g., `requests==2.25.1`). It ensures that every developer and CI environment installs the same library version, preventing "it works on my machine" errors caused by automatic updates.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled:** Source code is translated into machine code before execution (Fast). *Examples:* C++, Go.
*   **Interpreted:** Code is executed line-by-line or bytecode at runtime (Flexible). *Examples:* Python, Ruby.

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
*   **Reverse Proxy:** Sits in front of web servers to handle requests (Load balancing/Security). Examples: **Nginx**, **HAProxy**. Use Case: Load balancing traffic across 10 app instances.
*   **Forward Proxy:** Sits in front of clients to hide their identity/filter content. Example: A corporate VPN or a censorship bypass tool.

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A deadlock is when processes are stuck waiting for resources held by each other. Coffman Conditions:
1.  Mutual Exclusion (Resource cannot be shared).
2.  Hold and Wait (Process holds one resource while requesting another).
3.  No Preemption (Resources cannot be forcibly taken away).
4.  Circular Wait (A chain of processes exists where each waits for the next).

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
Eventual consistency means that if no new updates are made, eventually all accesses will return the last updated value. Cassandra handles this via "Tunable Consistency": you can choose `ONE` (fastest, low consistency), `QUORUM` (majority nodes agree), or `ALL` (highest consistency, slowest). For read-after-write, using `QUORUM` on both reads and writes ensures the latest data is returned.

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
mTLS requires *both* parties to present certificates. 
Handshake: Server sends its cert $\rightarrow$ Client verifies; Client sends its cert $\rightarrow$ Server verifies. Both exchange keys. This establishes a two-way trust. It is standard in **Service Mesh** architectures (like Istio) to secure pod-to-pod communication.

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
A Hash Table uses a hash function to map keys to array indices. 
*   **Chaining:** Store multiple items in a linked list at one index.
*   **Open Addressing:** Find the next empty slot (Linear/Quadratic probing).
*   **Complexity:** Average $O(1)$ for all operations; Worst Case $O(n)$ if many collisions occur.

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
Circuit Breaker stops requests to a failing service to prevent "cascading" failure across the system.
*   **Closed:** Normal operation; requests pass through.
*   **Open:** Service failed; fail fast immediately without trying.
*   **Half-Open:** Allow a few test requests to see if the service recovered.
It complements **Retries with Exponential Backoff**, which ensures that retries don't overwhelm a struggling service by increasing wait times between attempts.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features.**
*   **Optimistic:** Assume no conflict will happen. Check version numbers before writing. Use when contention is low (e.g., `UPDATE ... WHERE version = 5`). Good for high-scale web apps.
*   **Pessimistic:** Lock the record so others can't touch it. Use when contention is high or data integrity is critical (e.g., `SELECT FOR UPDATE` on a bank balance).
