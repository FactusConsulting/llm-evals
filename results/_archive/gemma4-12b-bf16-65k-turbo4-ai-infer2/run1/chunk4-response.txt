## Go Questions

**G1 — Easy: What is the difference between a slice and an array in Go? What happens when you append to a slice that has reached its capacity?**
An **array** has a fixed length and size; its elements are stored in a contiguous block of memory. A **slice** is a descriptor containing a pointer to an underlying array, a length, and a capacity. When `append` is called on a slice at full capacity, Go allocates a new, larger underlying array (usually doubling the capacity), copies the existing elements over, and returns a new slice header pointing to this new array.

**G2 — Easy: Explain the difference between `var x int` and `x := 0`. When can you NOT use `:=`?**
`var x int` declares a variable with its zero value (`0`). `x := 0` uses short variable declaration, which infers the type from the right side. You cannot use `:=` outside of function bodies or when declaring a variable that already exists in the scope.

**G3 — Medium: What is a goroutine, and how does it differ from an OS thread? What is the role of the Go scheduler (GMP model)?**
A **goroutine** is a lightweight thread managed by the Go runtime, not the OS. They have much smaller stacks (starting at ~2KB) compared to OS threads (~MBs). The **GMP model** consists of **G**oroutines, **M**achines (OS threads), and **P**rocessors (logical contexts/resources). The scheduler maps Gs onto Ms via Ps to multiplex many goroutines across fewer OS threads efficiently.

**G4 — Medium: Explain how channels work in Go. What is the difference between a buffered and unbuffered channel? What happens when you send to a full buffered channel?**
Channels are typed conduits for communication between goroutines. An **unbuffered channel** blocks the sender until a receiver is ready (and vice versa). A **buffered channel** allows sending without blocking as long as there is space in the buffer. If a buffered channel is full, the sender blocks until a receiver removes an item.

**G5 — Medium: What is the context package used for? Write a minimal example of using context.WithTimeout to cancel a long-running HTTP request.**
The `context` package carries deadlines, cancellation signals, and request-scoped values across API boundaries.
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel() // Ensure resources are freed
req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
```

**G6 — Medium: Explain Go's interface satisfaction model. How does it differ from Java/C# interfaces? What is the empty interface interface{} (or any) and why is it both powerful and dangerous?**
Go uses **implicit satisfaction**: a type satisfies an interface by implementing its methods; no explicit declaration is needed. In Java/C#, you must explicitly declare implementation (`implements`). The `any` (empty interface) can hold any value, making it powerful for generic handling but dangerous because it bypasses type safety, requiring reflection or type assertions which can cause runtime panics.

**G7 — Hard: Explain Go's memory model regarding goroutine visibility. Why is the following unsafe, and what are the correct alternatives?**
The code has a **data race**. Because there is no synchronization (like a Mutex or Channel), the compiler/CPU might reorder instructions or cache variables in registers, meaning the main loop might never see `ready = true`. Correct alternatives include using a `sync.WaitGroup`, a channel to signal completion, or protecting access with a `sync.Mutex`.

**G8 — Hard: What is the difference between sync.Mutex and sync.RWMutex? When would you use sync.Map vs a regular map with a mutex? What are the performance trade-offs?**
A `Mutex` allows only one goroutine at a time; `RWMutex` allows multiple concurrent readers OR one writer. Use `sync.Map` for cases where keys are stable, entries are mostly read, or many goroutines write to disjoint sets of keys. A standard map + Mutex is usually faster for high-write workloads on small maps due to less internal overhead than `sync.Map`.

**G9 — Medium: How do Go modules work. What is the difference between go.mod and go.sum? What does go mod tidy do, and what is the Minimum Version Selection (MVS) algorithm?**
Go Modules manage dependencies via `go.mod`. `go.mod` defines requirements; `go.sum` stores cryptographic hashes for integrity. `go mod tidy` removes unused and adds missing dependencies. **MVS** ensures that if different packages require different versions of the same library, Go selects the *lowest* version that satisfies all constraints.

**G10 — Medium: What is a defer statement? In what order do multiple defers execute? What is a common gotcha with defer in a loop?**
`defer` schedules a function call to run immediately before the surrounding function returns. They execute in **LIFO** (Last-In, First-Out) order. A common gotcha is using `defer` inside a loop (e.g., closing a body); it won't execute until the entire function finishes, potentially exhausting file descriptors or memory.

**G11 — Easy: What is a pointer in Go? What is the zero value of a pointer? How do you create a pointer to a struct literal?**
A pointer holds the memory address of a value. The zero value is `nil`. You can create one from a struct literal using the address-of operator: `p := &MyStruct{Field: 1}`.

**G12 — Easy: Explain Go's init() function. When does it run? Can a package have multiple init() functions, and if so, in what order do they execute?**
`init()` runs automatically before `main()`. A package can have multiple `init()` functions; they execute in the order they appear in the source code files within that package. Package-level initializations happen first, then all `init()` calls.

**G13 — Easy: What is the difference between make and new in Go? What types does each work with?**
`new(T)` allocates memory for type T and returns a pointer (`*T`). It only initializes memory to its zero value. `make(T)` allocates and **initializes** memory for slices, maps, and channels (types that require internal structure setup).

**G14 — Easy: How does error handling work in Go? What is the error interface, and what is the idiomatic pattern for checking errors? How do errors.Is and errors.As differ from ==?**
Errors are values returned as the last return value. The `error` interface is an alias for `error` (a method `Error() string`). Idiomatically: `if err != nil { ... }`. `errors.Is` checks if an error wraps a specific target; `errors.As` checks if an error can be cast into a specific custom error type. Use these instead of `==` because wrapped errors won't match via direct equality.

**G15 — Easy: What are Go's built-in composite types (map, slice, channel, struct)? What is the zero value of each?**
- Map: Zero value is `nil` (not usable until `make`).
- Slice: Zero value is `nil` (length 0).
- Channel: Zero value is `nil` (blocking on send/receive).
- Struct: All fields set to their respective zero values.

**G16 — Medium: What is a race condition in Go? How does the -race flag work? Give an example of a data race and show how to fix it with sync.Mutex or a channel.**
A race condition occurs when two goroutines access the same memory concurrently and at least one is a write. The `-race` flag uses instrumentation to detect unsynchronized concurrent memory access during execution.
*Example:* Two goroutines incrementing `count++`. Fix: Wrap the increment in `mu.Lock()` / `mu.Unlock()`.

**G17 — Medium: Explain Go's select statement. How does it differ from a switch? What happens when multiple cases are ready? How do you implement a timeout with select?**
`select` blocks until one of its communication operations (send/receive) can proceed; `switch` evaluates expressions. If multiple cases are ready, one is chosen **pseudo-randomly**. Timeout is implemented using `time.After(duration)` inside a `select`:
```go
select {
case res := <-ch: // handle result
case <-time.After(1 * time.Second): // handle timeout
}
```

**G18 — Hard: What is escape analysis in Go? How does the compiler decide whether to allocate on the stack or the heap? How can you inspect escape analysis decisions, and why does it matter for performance?**
Escape analysis determines if a variable's lifetime exceeds the scope of the function. Variables that don't "escape" stay on the stack (fast). Those that do move to the heap (requires GC). You can inspect this via `go build -gcflags="-m"`. It matters because heap allocation and subsequent Garbage Collection increase latency and CPU usage.

**G19 — Hard: Explain Go's reflection package (reflect). What is reflect.Type vs reflect.Value? What are the performance costs, and when is reflection justified vs code generation?**
Reflection allows inspecting and manipulating types at runtime. `reflect.Type` describes the structure/metadata; `reflect.Value` represents the actual data. Reflection is slow due to dynamic dispatch and lack of compiler optimizations. Use it only when necessary (e.g., JSON encoders); otherwise, use Code Generation (like Protobuf) for better performance.

**G20 — Hard: What is the go:embed directive? How does it work for single files, directories, and file systems? What are the limitations, and how does it interact with io/fs.FS?**
`//go:embed` allows compiling static assets into the binary. Single files or whole directories (with a `Filelist`) can be embedded. Limitations include not being able to embed from outside the project root. It integrates with `io/fs`, allowing you to treat embedded content as an `fs.FS` object.

## Rust Questions

**R1 — Easy: What is ownership in Rust? Explain the three ownership rules.**
Ownership is Rust’s memory management system. Rules: 1. Each value has a variable called its owner. 2. There can only be one owner at a time. 3. When the owner goes out of scope, the value is dropped (freed).

**R2 — Easy: What is the difference between String and &str? When would you use each in function signatures?**
`String` is an owned, heap-allocated string that can grow. `&str` is a "string slice"—a pointer + length—representing a view into some existing string data. Use `String` when you need to own/mutate data; use `&str` for read-only parameters to allow both types of inputs.

**R3 — Medium: Explain borrowing and the borrow checker. What are the rules for shared (&T) and mutable (&mut T) references?**
Borrowing allows using a value without taking ownership. The Borrow Checker enforces: 1. You can have unlimited shared references (`&T`). 2. OR exactly one mutable reference (`&mut T`) at a time. 3. You cannot have both simultaneously. This prevents data races at compile time.

**R4 — Medium: What is a Result<T, E> and an Option<T>? How does the ? operator work? Write a function that reads a file and returns its contents or an error.**
`Option<T>` handles presence/absence (like null safety); `Result<T, E>` handles success/failure. The `?` operator returns early if an error occurs, unwrapping the successful value otherwise.
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    let content = std::fs::read_to_string(path)?; // Returns Err immediately if failed
    Ok(content)
}
```

**R5 — Medium: Explain the difference between Box<T>, Rc<T>, and Arc<T>. When would you use each?**
- `Box<T>`: Single owner on the heap. Use for large types or recursive types.
- `Rc<T>`: Reference counted pointer for multiple owners in a single thread.
- `Arc<T>`: Atomic reference counted; safe to share across threads.

**R6 — Medium: What are traits in Rust? How do they compare to Go interfaces? What is a trait object (dyn Trait) vs a generic with a trait bound (T: Trait)?**
Traits define shared behavior. Like Go interfaces, but explicit. **Trait objects (`dyn Trait`)** use dynamic dispatch (vtable), allowing heterogeneous collections of different types implementing the same trait. **Generics with bounds (`T: Trait`)** use monomorphization (static dispatch), generating specific code for every type used, which is faster but increases binary size.

**R7 — Hard: Explain lifetimes in Rust. Why does the following fail to compile, and how do you fix it?**
Lifetimes ensure references don't outlive their data. The example fails because the compiler doesn't know if `x` or `y` lives longer; it can't guarantee that the returned reference remains valid. Fix by adding lifetime annotations:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str { ... }
```

**R8 — Hard: What is Send and Sync in Rust? Why can't you send an Rc<T> across threads? What makes Arc<T> safe for concurrent use?**
- `Send`: Type can be moved between threads.
- `Sync`: Type can be accessed from multiple threads simultaneously.
`Rc<T>` is not `Send`/`Sync` because its internal reference count is updated using non-atomic operations, leading to race conditions. `Arc<T>` uses atomic instructions to update counts safely.

**R9 — Hard: Explain how Rust's async/await works under the hood. What is a Future? What is the role of the executor (e.g., Tokio)? How does this differ from Go's goroutines?**
Rust futures are **state machines** polled by an executor. They do nothing unless "polled." Unlike Goroutines (which are preemptive and managed by the runtime), Rust's async is cooperative and zero-cost; it doesn't allocate a stack per task but requires an external library like **Tokio** or **async-std** as the executor to drive them to completion.

**R10 — Medium: What is unsafe in Rust? Give 3 things you can do in an unsafe block that you can't do in safe Rust. When is unsafe justified?**
Unsafe allows bypassing some compiler checks. You can: 1. Dereference raw pointers (`*const T`). 2. Call FFI functions (C code). 3. Access mutable static variables. Unsafe is justified for low-level systems programming (OS kernels, drivers) where performance requirements necessitate direct hardware access.

**R11 — Easy: What is pattern matching in Rust? How does match differ from if let? What does the compiler enforce about exhaustiveness?**
`match` is an expression that must cover all possible patterns (exhaustiveness); otherwise, it fails to compile. `if let` is a shorthand for when you only care about one specific pattern. The compiler ensures every branch of a `match` covers all inputs of the type.

**R12 — Easy: What is the difference between Vec<T> and an array [T; N]? How does Vec manage memory when elements are pushed beyond its current capacity?**
An array has a fixed size at compile time. A `Vec` is heap-allocated and grows dynamically. When capacity is exceeded, `Vec` reallocates by finding a new memory block (usually doubling the old capacity), copying existing elements, and freeing the old block.

**R13 — Easy: What are enums in Rust, and how do they differ from enums in C or Java? What is the Option<T> enum, and why does Rust not have null?**
Rust enums can hold data (Algebraic Data Types). Unlike C/Java where enums are just integers, Rust enums can be complex structures. `Option<T>` represents "some value" or "none." Rust lacks `null` because `Option` forces developers to handle the empty case explicitly at compile time, preventing NullPointerExceptions.

**R14 — Easy: Explain the impl block. What is the difference between methods that take &self, &mut self, and self? What are associated functions (e.g., String::new())?**
The `impl` block defines functionality for a type. 
- `&self`: Immutable borrow of instance.
- `&mut self`: Mutable borrow of instance.
- `self`: Consumes ownership of the instance (moves it).
Associated functions don't take `self` as an argument; they are like static methods.

**R15 — Easy: What is the derive macro? Give examples of commonly derived traits (Debug, Clone, PartialEq, Serialize). When can you NOT derive a trait?**
Derive macros automatically implement common traits via procedural macros. You cannot derive a trait if any of its internal fields do not also implement that trait (or if the trait requires manual logic, like certain thread-safety requirements).

**R16 — Medium: What is Cow<'a, T> (clone on write)? When is it useful? Give an example where it avoids unnecessary allocations compared to always cloning.**
`Cow` stands for "Clone on Write." It allows holding either borrowed data (`&T`) or owned data (`T`). If you only read the data, no allocation occurs. Only when you need to modify/mutate the value does it clone the data into an owned version. Useful in parsers where most inputs remain unchanged.

**R17 — Medium: Explain Rust's module system. What is the difference between mod, use, and pub? How does the file system map to modules, and what changed between Rust 2015 and 2018 editions?**
- `mod`: Declares a module.
- `use`: Brings items into scope.
- `pub`: Makes items accessible outside the current module.
In 2015, modules were strictly tied to files. In 2018, the module tree became more flexible; you can define nested modules within one file or split them across files more freely using `mod`.

**R18 — Hard: What is the Pin<T> type and why is it needed? How does it relate to self-referential structs and async/await? What is Unpin?**
`Pin` ensures that a value cannot be moved in memory once pinned. This is required for types containing pointers to their own internal fields (self-referential). Async functions generate such structures. If they move, those internal pointers become invalid. `Unpin` is a marker trait indicating that a type *can* be safely moved (most types are `Unpin`).

**R19 — Hard: Explain Rust's macro system. What is the difference between declarative macros (macro_rules!) and procedural macros (derive, attribute, function-like)? What are hygiene rules?**
Declarative macros (`macro_rules!`) are pattern-matching replacements. Procedural macros are "macros as programs" that take tokens and return new tokens. Hygiene refers to how macros handle variable names—ensuring that variables defined inside a macro don't accidentally collide with variables in the surrounding scope.

**R20 — Hard: What are zero-cost abstractions in Rust? Explain how iterators, generics (monomorphization), and trait static dispatch achieve performance comparable to hand-written C while providing high-level ergonomics.**
Zero-cost means you only pay for what you use; higher-level constructs compile down to the same machine code as manual implementations. **Monomorphization** generates specific versions of generic functions at compile time, removing runtime overhead. Iterators are compiled into efficient loops without intermediate allocations or dynamic checks.
