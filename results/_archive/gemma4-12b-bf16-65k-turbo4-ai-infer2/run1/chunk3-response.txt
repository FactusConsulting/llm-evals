## OpenTofu / Terraform

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` is a dry-run operation that generates an execution plan, showing what changes will be made (create, update, delete) without actually modifying infrastructure. `tofu apply` executes those actions to reach the desired state defined in the configuration.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a JSON file that maps real-world resources to your configuration. Remote state is critical because it acts as a single source of truth for teams/CI pipelines, enables state locking to prevent concurrent modifications, and ensures consistency across different environments.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` uses an index (0, 1, 2...) to create multiple resources; if you remove an item from the middle of a list, indices shift, causing unintended recreations. `for_each` uses a map or set of keys, making it much more stable for refactoring. `for_each` is preferred whenever creating multiple instances of a resource where each instance has unique attributes.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?**
This creates "configuration drift." During the next `tofu plan`, OpenTofu performs a refresh by querying the cloud provider's API. It compares the actual state with the desired config and proposes a plan to revert the manual changes back to the defined code.

**T5 — Medium: Write a minimal OpenTofu snippet.**
```hcl
resource "null_resource" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  # Logic here...
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
The `terraform_remote_state` data source reads the entire state file of another workspace/module. The recommended alternative is passing outputs as variables into child modules (composition). This is cleaner because it reduces coupling; the module only cares about inputs, not where they come from.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
Provisioners are executed during the resource creation phase, but the output might not be populated until the provisioner finishes. If downstream resources depend on this output in the same run, they may see an empty value. **Fix:** Use a local variable or a separate "output" step using a specialized provider (like a Kubernetes provider) that can natively read the config once created.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
Import brings existing infrastructure into the state file. The CLI command requires manual mapping for every single resource. The `import` block allows you to declare imports directly in your code, making them version-controlled and easier to manage alongside configuration changes.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A variable is a parameter for your configuration. An input variable is provided by the user/CI to customize the module's behavior; an output is a value returned by the module after execution (e.g., a Load Balancer IP).

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that translates HCL into API calls for specific platforms (AWS, GCP, etc.). If you skip `tofu init`, the plan will fail because the necessary binaries/plugins haven't been downloaded or initialized.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
It locks the versions of providers used in the project. Committing it ensures that all team members and CI environments use identical provider versions, preventing "it works on my machine" errors caused by automatic updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` removes all managed resources. To target one specifically: `tofu destroy -target=resource_type.name`.

**T13 — Easy: What is a data source in OpenTofu? Give an example.**
A data source fetches information about existing infrastructure that you don't manage via Tofu. Example: Fetching the ID of an existing VPC or an AMI ID from a public registry.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
Variables are inputs provided by users; Locals are internal constants/logic defined within the module. Use locals to simplify complex expressions (e.g., combining multiple strings) or to store values derived from other outputs within the same module.

**T15 — Medium: What is the lifecycle block in a resource? Explain create_before_destroy, prevent_destroy, and ignore_changes with a use case for each.**
- `create_before_destroy`: Used when replacing a resource would cause downtime (e.g., creating a new DB before deleting the old one).
- `prevent_destroy`: A safety check to stop accidental deletion of critical infra (e.g., production DBs).
- `ignore_changes`: Prevents Tofu from trying to "fix" changes made by external processes (e.g., auto-scaling group sizes).

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block tells Tofu that a resource has changed its address in the code (e.g., moving it into a sub-module). It updates the state file mapping without forcing a recreation of the physical resource.

**T17 — Hard: Explain how OpenTofu's dependency graph works. Difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
Implicit dependencies are created automatically when one resource references an attribute of another. Explicit dependencies use `depends_on`. `depends_on` forces a strict order but limits parallelism; it should be used only when there is no direct data link between resources but a logical ordering requirement exists.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies.**
1. **State Splitting:** Break large states into smaller ones (Prod/Dev, Network/App) to reduce the scope of each plan.
2. **Partial Plans:** Use `-target` for specific changes during development.
3. **Data Source Optimization:** Reduce unnecessary remote lookups or switch to local caching.
4. **Module Refactoring:** Move static configurations out of modules so they aren't re-evaluated every time. *Tradeoff:* Increased complexity in managing multiple state files.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released? How do you manually break a lock, and what are the risks?**
Locking prevents two people from running apply simultaneously. If a CI job crashes, the lock remains "stuck." You can break it via backend commands (e.g., `terraform force-unlock`). Risk: If another process actually was writing to state while you broke the lock, the state file could become corrupted.

**T20 — Hard: Describe how to migrate an existing project from local state to S3 + DynamoDB.**
1. Add the `backend "s3"` block with DynamoDB table info.
2. Run `tofu init`. Tofu will detect the change and ask to migrate the state.
3. Confirm migration by checking the S3 bucket/DynamoDB table.
4. Verify that `tofu plan` shows no changes for existing resources.

## Ansible

**A1 — Easy: Difference between playbook, role, and task?**
Task: A single action (e.g., install a package). Role: A reusable group of tasks, variables, and files. Playbook: A list of plays that map hosts to roles or tasks.

**A2 — Easy: What is ansible_facts and how do you access the OS family?**
Ansible facts are system metadata gathered during setup. Access the OS family using `ansible_os_family` (e.g., RedHat, Debian).

**A3 — Medium: Explain difference between command, shell, and raw modules.**
- `command`: Basic execution; doesn't support pipes/redirects. Safest.
- `shell`: Runs through `/bin/sh`; supports pipes/variables. Use when needed but riskier.
- `raw`: Executes without Python on target. Used for initial bootstrap where Python isn't installed yet.

**A4 — Medium: How does Ansible handle idempotency? Give an example.**
Ansible checks if the desired state matches current state before acting. Idempotent: `apt: name=nginx state=present`. NOT idempotent: `shell: echo "data" >> /file` (appends every time it runs).

**A5 — Medium: Write an Ansible task for htop installation.**
```yaml
- name: Install htop based on OS
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'epel-release,htop' }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```
*(Note: For a cleaner approach, use separate tasks with `when` conditions or different roles).*

**A6 — Hard: Explain variable precedence order.**
Highest to lowest priority: Extra vars (`-e`), Host vars, Group vars, Role defaults, Inventory variables. `set_fact` usually has very high priority as it updates facts during runtime.

**A7 — Hard: Deploy RKE2 agent on 50 nodes; first 3 must complete first.**
Use `serial: 3` in the playbook. To ensure health check completion between batches, add a `wait_for` task at the end of the play that checks the service status before moving to the next batch.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file?**
Ansible Vault encrypts files/variables. To encrypt only one variable, create a dedicated vault file for secrets and include it via `vars_files`, rather than trying to partially encrypt a shared file (which is difficult).

**A9 — Easy: What is an Ansible inventory file? Static vs Dynamic?**
An inventory lists managed hosts. Static is a manual list of IPs/hostnames. Dynamic pulls host data from cloud providers (AWS/GCP) using plugins.

**A10 — Easy: Ad-hoc command for disk space.**
`ansible webservers -m shell -a "df -h"`

**A11 — Easy: What is a handler? How do you trigger it?**
Handlers are tasks triggered by a change (e.g., restarting a service after config update). Triggered using the `notify` keyword in a task. They run once at the end of the play unless re-notified.

**A12 — Easy: What is ansible.cfg used for? Name 3 settings.**
It configures Ansible's behavior. Common settings: `remote_interpreter`, `forks`, `inventory`.

**A13 — Easy: What is register?**
Register saves the output of a task into a variable. Example: `register: result`. You then access it as `result.stdout`.

**A14 — Medium: include_tasks vs import_tasks.**
`import_tasks`: Static; processed when the playbook is parsed (faster, but no loops). `include_tasks`: Dynamic; processed during execution (allows for loops and conditionals).

**A15 — Medium: What is Ansible Galaxy? requirements.yml?**
Galaxy is a repository for sharing roles. Use `ansible-galaxy install -r requirements.yml` to automate installation from that file.

**A16 — Medium: Connection plugins: ssh, local, network_cli.**
- `ssh`: Standard remote execution via SSH.
- `local`: Runs tasks on the control node itself.
- `network_cli`: Used for network devices (e.g., switches) using Netconf/Telnet instead of standard SSH.

**A17 — Hard: delegate_to and run_once.**
`delegate_to: localhost` runs a task on your machine while still having access to target host facts. `run_once` ensures only one host in a group executes the task. **Example:** Updating a global Load Balancer entry based on IPs gathered from 20 nodes—gather data from all hosts, then use `delegate_to: localhost` with `run_once` to update the LB once.

**A18 — Hard: Performance strategies for 500 hosts.**
1. Increase `forks` (parallelism).
2. Enable Pipelining (`pipelining = True`) to reduce SSH overhead.
3. Fact Caching (Redis/Memcached) to avoid re-gathering facts every time.
4. Mitogen plugin (faster execution engine). *Tradeoff:* Cache staleness or increased memory usage.

**A19 — Hard: Jinja2 templating.**
`{{ }}` is for expressions; `{% %}` are logic blocks (if/for); `{# #}` are comments.
```jinja2
# Upstream block example
{% for server in backend_servers %}
upstream web_servers {
    server {{ server.ip }}:80; # Health check active
}
{% endfor %}
```

**A20 — Hard: Zero-downtime rolling deployment strategy.**
Use `serial: 1` (or small batch size). Use a `pre_tasks` block to remove the host from the Load Balancer using the `uri` module to verify health. Run the deploy task. In a `rescue` block, if it fails, run a rollback task that reverts the version and puts the node back into rotation.
