## Application Architecture

AA1 — **Monolith vs. Microservices:** A monolith is a single unified unit where all components share memory and resources; microservices decompose functionality into independent services. **Problems introduced by microservices:** 1) Distributed system complexity (network latency, partial failures), 2) Operational overhead (deployment pipelines, monitoring for many units), and 3) Data consistency challenges across distributed databases.

AA2 — **Sync vs. Async Communication:** Synchronous communication requires the requester to wait for a response before proceeding (e.g., HTTP REST); Asynchronous communication allows the requester to continue immediately after sending a message (e.g., RabbitMQ or Kafka). Example Sync: gRPC/REST; Example Async: Apache Kafka.

AA3 — **API Gateway vs. Reverse Proxy:** A reverse proxy sits in front of web servers to handle load balancing/SSL termination. An API Gateway adds logic like authentication, rate limiting, request transformation, and orchestration. An API Gateway *can* perform most functions of a reverse proxy, but they are not identical because an API Gateway is specifically designed for application-level routing and policy enforcement rather than just simple traffic forwarding.

AA4 — **Saga Pattern:** Manages distributed transactions by breaking them into local transactions with compensating actions if one fails.
**Choreography:** Each service produces events that trigger others (decentralized, good for simple workflows).
**Orchestration:** A central "orchestrator" tells each service what to do (easier to track, avoids cyclic dependencies). Use Orchestration for complex flows; Choreography for high-volume, decoupled tasks.

AA5 — **CQRS & Event Sourcing:** CQRS separates read models from write models. It's paired with Event Sourcing where every state change is stored as a sequence of events. This solves the problem of scaling reads independently of writes and provides a perfect audit log/history of how state was reached—something traditional CRUD cannot easily replicate without heavy overhead.

AA6 — **Circuit Breaker:** Prevents a system from repeatedly trying to execute an operation likely to fail. States: Closed (normal), Open (failure detected, block requests), Half-Open (test if service recovered). Difference: Retries can overwhelm a failing service; Circuit Breakers stop the flow entirely until it stabilizes. You use both together when you want to retry transient blips but have a circuit breaker to prevent cascading failures during prolonged outages.

AA7 — **Multi-tenant Isolation Models:** 
1. **Shared DB/Schema:** Lowest cost, highest noisy-neighbor risk, easiest to manage at scale.
2. **Separate Schema:** Better security isolation than shared schema, moderate complexity in migrations.
3. **Separate Database:** Highest security, best isolation, highest cost/operational effort. Best for "Enterprise" tier tenants.

AA8 — **Consistency Models:** Strong consistency ensures all nodes see same data simultaneously; Eventual consistency allows temporary divergence. For inventory that must never oversell: Use **Strong Consistency**. Architecture: Distributed SQL database (e.g., CockroachDB or Google Spanner) using Paxos/Raft consensus protocols with a reservation pattern (locking items during checkout).

AA9 — **Sidecar Proxy & Service Mesh:** A sidecar is a helper container running alongside the app container. Envoy acts as the proxy handling L7 traffic. Data Plane = actual proxies moving packets; Control Plane = management of policies/configs. mTLS between sidecars solves identity and encryption without requiring developers to bake TLS logic into every individual application's code.

AA10 — **Strangler Fig Pattern:** Incrementally replace functionality by wrapping legacy calls. Strategy: Identify a small edge feature (e.g., User Profile), build it in .NET 8 microservice, use an API Gateway to route requests to either the new service or the old monolith based on the endpoint path. Repeat until the monolith is empty.

AA11 — **12-Factor App:** Key factors include: Codebase, Dependencies, Config, Backing Services, Build/Release/Run stages, Port binding, Concurrency, Statelessness, Logs, Environment Parity, Disposability, Dev/Prod Parity. These matter because they ensure apps are portable, scalable, and resilient in cloud environments like Kubernetes.

AA12 — **Event vs. Request Architecture:**
**Request (REST/gRPC):** Low latency, easier debugging, strong coupling. Good for synchronous UI actions.
**Event (Kafka):** High throughput, high decoupling, complex ordering guarantees, harder to debug "trace" flows. Good for background processing/analytics. Choose Event when you need massive scale and can tolerate eventual consistency; choose Request for immediate user feedback.

AA13 — **Load Balancer:** Distributes incoming traffic across multiple servers. Layer 4 balances at the transport layer (IP/Port); Layer 7 balances at the application layer (URL paths, headers). Use Case for L7: Routing `/api/v1` to one cluster and `/images` to another.

AA14 — **Message Queue vs. Log Broker:** RabbitMQ (Queue) deletes messages once consumed (good for task distribution). Kafka (Log-based) retains messages as an append-only log (good for replayability and stream processing). Pick MQ for simple job queues; pick Kafka for high-throughput data streams or event sourcing.

AA15 — **Container vs. VM:** A container shares the host OS kernel; a VM includes a full guest OS. Containers are popular because they start faster, use fewer resources, and provide consistent environments from dev to production.

AA16 — **Stateless vs. Stateful:** Stateless services don't store client context between requests (e.g., a web server), making them easy to scale horizontally by just adding more instances. Stateful services maintain state (e.g., a database or a gaming session). Scaling stateful services requires complex sharding or replication logic.

AA17 — **ORM:** Maps objects in code to tables in a DB. Examples: Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs increase developer velocity and prevent SQL injection but can lead to "N+1" query problems and poor performance on complex joins compared to optimized raw SQL.

AA18 — **Bulkhead Pattern:** Isolates elements of an application so that if one fails, others continue. Implementation: Use separate thread pools for different service calls so that a slow third-party API doesn't exhaust all threads available for internal tasks. Or, deploy critical components into physically separate deployment groups/clusters.

AA19 — **OT vs. CRDTs:** OT relies on a central server to sequence operations (complex logic); CRDTs allow local updates that eventually merge mathematically without coordination. For offline support, choose **CRDTs** because they are designed specifically for peer-to-peer synchronization where nodes may be disconnected for long periods.

AA20 — **Distributed Tracing Challenges:** Context propagation is hard across polyglot stacks (need W3C Trace Context headers). Sampling strategies: Head-based (decide at start) vs Tail-based (keep trace until end, then decide whether to save based on errors/latency). To ensure continuity through Kafka, the producer must inject trace IDs into message headers, which the consumer then extracts and continues.

## On-Premise Infrastructure Architecture

OP1 — **Hypervisor Types:** Type 1 runs directly on hardware (e.g., VMware ESXi, Proxmox VE). Type 2 runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

OP2 — **SAN vs. NAS:** SAN provides block-level storage over a dedicated network (Fibre Channel/iSCSI), used for high-performance DBs. NAS provides file-level storage over standard Ethernet (NFS/SMB), used for shared filesystems.

OP3 — **Network Architecture:** 3-tier (Core, Distribution, Access) creates bottlenecks in East-West traffic. Leaf-Spine architecture connects every leaf switch to every spine switch, providing predictable latency and massive bandwidth for modern data center workloads.

OP4 — **Proxmox HA Cluster:** Need $\ge$ 3 nodes for quorum. Use Ceph as shared storage (replicated blocks). Fencing: STONITH (Shoot The Other Node In The Head) via IPMI to prevent split-brain. If a node fails, Corosync detects loss of heartbeat; if quorum is maintained, the VM restarts on another node using the shared Ceph volume.

OP5 — **VLAN Trunking:** Allows multiple VLANs over one physical link by adding tags to frames. 802.1Q is the standard tagging protocol. On Linux, use `ip link` or `nmcli` to create sub-interfaces (e.g., eth0.10, eth0.20) assigned to specific bridge ports.

OP6 — **RAID Types:** RAID 1 (Mirror), RAID 5 (Parity - 1 drive failure), RAID 6 (Double Parity - 2 failures), RAID 10 (Mirror+Striped), RAID Z2 (ZFS equivalent of RAID 6). For a DB server with 6 drives, choose **RAID 10** because it offers the best balance of high IOPS and fast rebuild times compared to parity-based RAIDs.

OP7 — **DNS Architecture:** Internal DNS uses recursive resolvers for local lookups. DMZ has its own authoritative servers. Split-horizon ensures internal users see private IPs while external users see public IPs. When moving from Office to VPN, the client's DNS settings switch to the VPN's recursive resolver via DHCP/VPN config.

OP8 — **PKI Chain:** Root CA signs Subordinate CA; Subordinate CA issues end-entity certs. CRL lists revoked certs; OCSP provides real-time status. Compromised Subordinate = only those certificates are at risk. Compromised Root = entire trust chain is broken; must revoke root and re-issue everything.

OP9 — **WAN Consolidation:** MPLS (Reliable but expensive), IPsec (Cheap but variable latency), SD-WAN (Best of both: manages multiple paths intelligently), WireGuard (Fast mesh). Recommendation: **SD-WAN**. It handles VoIP quality over standard internet links efficiently while managing costs across sites.

OP10 — **Out-of-Band (OOB) Management:** iDRAC/iLO provide access even if the OS hangs or the NIC fails. Critical for remote recovery. If exposed to the internet without a firewall/VPN, an attacker can gain hardware-level control, potentially bricking the server or stealing data via the management console.

OP11 — **LVM vs. LVM-Thin vs. ZFS:** LVM is logical volume management (flexible resizing); LVM-Thin allows over-provisioning (thin provisioning like a VM disk). ZFS is a combined filesystem and volume manager with built-in RAID and snapshots. Snapshots in LVM-Thin are "Copy-on-Write" pointers; ZFS uses native CoW.

OP12 — **Stretch Cluster / DR:** To survive site failure, use 3 sites (or 2 sites + a lightweight witness node in a 3rd location) to maintain quorum. Ceph CRUSH rules must be configured to ensure replicas are on different physical sites. Latency between sites must be low (<10ms ideally) for synchronous replication; otherwise, use asynchronous replication which risks RPO > 0.

OP13 — **DHCP DORA:** Discover (Client), Offer (Server), Request (Client), Acknowledge (Server). If DHCP is down and lease expires, Windows clients enter an "APIPA" state (169.254.x.x), allowing local network communication but no internet/gateway access.

OP14 — **Managed vs. Unmanaged Switch:** Managed switches allow VLANs, Link Aggregation (LACP), SNMP monitoring, and QoS. These are essential for enterprise environments to segment traffic, prioritize VoIP, and monitor port health.

OP15 — **NTP & Clock Drift:** NTP synchronizes clocks via UDP. In clusters, drift causes issues with distributed locks, log correlation, and Kerberos authentication (which fails if clocks differ by $>5$ minutes).

OP16 — **Physical vs. VM vs. Container:** Physical = raw hardware performance. VM = OS-level isolation. Container = Process-level isolation. Run directly on bare metal when you need maximum IOPS/GPU throughput or have a workload that requires specific kernel tuning not available in virtualized layers.

OP17 — **UPS vs. Generator:** UPS provides immediate battery power for the few seconds/minutes needed to safely shut down systems during a power flick; Generators provide long-term power. ATS automatically detects power loss and starts the generator, switching the load from the UPS/Grid to the Generator.

OP18 — **Active-Passive vs. Active-Active:** Active-Passive: One node is standby (lower cost, simpler failover). Active-Active: Both nodes serve traffic (higher complexity, better utilization). Pacemaker/Corosync handles HA by using Corosync for heartbeats and Pacemaker to manage resources. STONITH ensures that a "zombie" node is physically powered off before another takes over its IP/Storage to prevent data corruption.

OP19 — **Backup & Recovery:** 3-2-1 Rule: 3 copies of data, 2 different media types, 1 offsite. RPO (Recovery Point Objective) defines max allowed data loss time; RTO (Recovery Time Objective) defines max downtime. Immutable backups (WORM storage) protect against ransomware. Backup = copying data; Disaster Recovery = the plan/process to restore operations after a catastrophe.

OP20 — **802.1X NAC:** Supplicant (Client device), Authenticator (Switch/AP), Authentication Server (RADIUS/ISE). EAP-TLS uses certificates (secure); PEAP uses usernames/passwords. Dynamic VLANs assign users to specific segments based on identity. MAB allows devices like printers (no supplicant) to be authenticated via their MAC address in the RADIUS database.
