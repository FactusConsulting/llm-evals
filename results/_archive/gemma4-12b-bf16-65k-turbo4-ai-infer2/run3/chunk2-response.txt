## Kubernetes

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** is used for stateless applications where any pod instance is interchangeable; they are managed as a collective group with random identifiers. A **StatefulSet** is used for stateful applications (like databases) where each pod requires a unique, persistent identity (e.g., `pod-0`, `pod-1`), stable network identifiers, and dedicated persistent storage that persists even if a pod is rescheduled.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
Traffic hits the Service's virtual IP. The `kube-proxy` component on each node manages rules (via `iptables` or `IPVS`) that intercept this traffic. These rules perform load balancing across the healthy backend Pod IPs listed in the Service’s **Endpoints** object.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage provisioned by an administrator (the "physical" resource).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user (the "ticket"). It specifies size and access modes.
*   **StorageClass:** Defines different types of storage (SSD, HDD, etc.) and allows for dynamic provisioning. 
**Relationship:** A user creates a PVC $\rightarrow$ the cluster looks for a matching PV or uses a StorageClass to automatically create a new PV $\rightarrow$ the PV is bound to the PVC.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps.**
1.  **Check Logs:** Run `kubectl logs <pod_name>` to see application-level errors (e.g., missing env vars, DB connection failures).
2.  **Describe Pod:** Run `kubectl describe pod <pod_name>` to check for events like OOMKills, failed liveness probes, or scheduling issues.
3.  **Resource Check:** Compare memory/CPU limits vs. actual usage; if it hits the limit, it will be OOMKilled.
4.  **Configuration Audit:** Verify ConfigMaps, Secrets, and environment variables are correctly injected into the container.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to the DNS resolution if the CoreDNS pods are down?**
CoreDNS provides internal service discovery (resolving `service-name.namespace.svc.cluster.local`) and external name resolution. If CoreDNS is down, pods cannot resolve any hostnames, breaking both internal microservice communication and external API calls.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on.**
The scheduler uses a two-step process:
1.  **Filtering (Predicates):** It eliminates nodes that don't meet requirements (e.g., insufficient CPU/RAM, taints without matching tolerations, port conflicts).
2.  **Scoring (Priorities):** It ranks remaining nodes based on factors like **Least Requested Resources** (spreading load), **Node Affinity**, and **Image Locality**. The highest score wins.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
*   **Scheduling:** Yes. The scheduler only considers **Requests** for scheduling decisions. $4\text{GB} - 3.5\text{GB} = 0.5\text{GB}$ ($512\text{Mi}$) available. Since $256\text{Mi} < 512\text{Mi}$, it fits.
*   **Runtime:** If usage hits $600\text{Mi}$, the container will be **OOMKilled** because its limit is set to $512\text{Mi}$. Limits are enforced by the Kubelet/Container Runtime.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller.**
External Request $\rightarrow$ External Load Balancer (Cloud LB) $\rightarrow$ Ingress Controller Pod (NGINX) $\rightarrow$ Ingress Rules (matches Host/Path) $\rightarrow$ Service IP $\rightarrow$ `kube-proxy` (iptables/IPVS rules on node) $\rightarrow$ Endpoints list $\rightarrow$ Target Pod IP.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A NetworkPolicy acts as a firewall for pods, controlling ingress and egress traffic at the IP/Port level. By default, all namespaces allow all traffic (Allow All). Applying a policy restricts traffic only to those specifically allowed or selected by selectors; any traffic not explicitly permitted is dropped.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old pods with new ones (ensures zero downtime).
*   **Recreate:** Kills all existing pods before starting new ones (causes downtime).
Choose **Recreate** if the application cannot handle two versions running simultaneously (e.g., shared database schema conflicts or singleton resource locks).

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A Namespace provides logical isolation within a single physical cluster. Default namespaces include `default`, `kube-system` (for system components), and `kube-public`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
It provides detailed metadata about the pod's state. It shows: 1) **Events** (restarts, scheduling errors), 2) **Container Statuses** (Ready/Running status per container), and 3) **Node Information** (which node it's on).

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A ConfigMap stores non-confidential key-value pairs. Pods consume them via:
1.  **Environment Variables:** Injected into the container environment.
2.  **Volume Mounts:** Mounted as files inside the container filesystem.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Internal only; reachable only from within the cluster.
*   **NodePort:** Exposes the service on a specific port across every node's IP.
*   **LoadBalancer:** Provisions an external cloud load balancer to route traffic to the service.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A DaemonSet ensures that exactly one copy of a pod runs on every node in the cluster. Use it for infrastructure tasks like log collection (`Fluentd`), monitoring agents (`Prometheus Node Exporter`), or networking plugins.

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints/Tolerations:** A "repellent" mechanism. Nodes have Taints (keep pods away); Pods have Tolerations (allow them onto tainted nodes). *Use Case:* Dedicated GPU nodes with a taint so only ML jobs can run there.
*   **Affinity:** A "preference." Pods have Affinity rules to choose specific nodes based on labels. *Use Case:* Ensuring high-availability by spreading pods across different Availability Zones.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An Operator is a custom controller that-manages complex stateful applications using Custom Resource Definitions (CRDs). While a standard controller handles generic logic (e.g., "ensure 3 replicas"), an Operator contains domain-specific knowledge (e.g., "how to perform a rolling upgrade of a Postgres database cluster").

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
Etcd uses the **Raft consensus algorithm**. If quorum ($n/2 + 1$) is lost, the cluster becomes read-only or stops accepting writes; no new pods can be scheduled or updated. To recover from losing 2 out of 3 nodes, you must restore data from a backup onto a new node and manually reconfigure the cluster to recognize the new member as part of the quorum.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
RBAC defines permissions for users/service accounts. **Role** = Namespace scope; **ClusterRole** = Cluster wide. **RoleBinding** links a Role to a user in a namespace; **ClusterRoleBinding** links a ClusterRole (or Role) across the whole cluster.
*Manifests:*
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: dev }
rules:
- { apiGroups: [""], resources: ["pods", "pods/log"], verbs: ["get", "list", "watch"] }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: dev-reader-binding, namespace: dev }
subjects: [{ kind: User, name: "dev-user", user: "dev-user" }]
roleRef: { kind: Role, name: pod-reader, apiGroup: "" }
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how would you fix it using dnsConfig in the pod spec.**
The `ndots` setting determines how many dots are in a domain before Kubernetes tries to resolve it as an internal name. If `ndocs=5`, a query like `google.com` (one dot) triggers multiple search path attempts (e.g., `google.com.default.svc.cluster.local`) before failing and trying the actual external IP. Fix this by setting `dnsConfig` with a lower `ndots` value or providing a specific `nameservers` list in the Pod spec.

## Development

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
Merge combines histories while preserving the original commit structure; Rebase rewrites history by moving commits onto a new base. **Avoid rebasing public branches** because rewriting shared history causes significant conflicts for other collaborators.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
TCP is connection-oriented, reliable, and ensures ordered delivery (e.g., HTTP, SSH). UDP is connectionless, faster, but does not guarantee delivery/order (e.g., DNS, VoIP).

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A race condition occurs when two threads access shared data simultaneously, and the final result depends on the timing of execution. *Example:* Two threads incrementing a global variable `counter++`. If both read "5" at the same time, they both write back "6", losing one increment.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
Symmetric uses one key for both enc/dec (AES); Asymmetric uses a Public Key to encrypt and a Private Key to decrypt (RSA/ECC). In TLS, Asymmetric encryption is used during the handshake to securely exchange a temporary Symmetric session key, which is then used for the actual high-speed data transfer.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
Each instruction in a Dockerfile creates a read-only layer. Caching works from top to bottom; if you change an early line, all subsequent layers must be rebuilt. **Best Practice:** Place stable instructions (installing OS packages) at the top and frequently changing ones (copying source code) at the bottom.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check.**
1.  Check Load Balancer logs for backend health status.
2.  Check Pod resource usage (CPU/Memory spikes causing throttling).
3.  Check upstream dependencies (is a downstream DB or service failing?).
4.  Check connection pool limits on the application server.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
CAP states a distributed system can only guarantee two out of three: Consistency, Availability, Partition Tolerance.
*   **CP Example:** HBase or MongoDB (prioritize consistency during network partitions).
*   **AP Example:** Cassandra or DynamoDB (prioritize availability even if data is temporarily inconsistent).

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
Vertical = adding more power to an existing machine (more RAM/CPU). Horizontal = adding more machines. Patterns enabling horizontal scaling include **Statelessness**, **Load Balancing**, and **Database Sharding**.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An env var is a dynamic value used by processes. To persist it in a shell session, add `export VAR_NAME=value` to your `.bashrc` or `.zshrc` file.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
JSON is a strict key-value format; YAML is an indentation-based superset of JSON. Advantage: JSON is faster for machines to parse; YAML is much easier for humans to read/write manually.

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
REST is an architectural style for networked applications. 
*   **GET:** Retrieve data.
*   **POST:** Create new resource.
*   **PUT:** Update entire existing resource.
*   **DELETE:** Remove a resource.

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
Version pinning specifies exact versions (e.g., `requests==2.25.1`) rather than ranges (`>=2.0`). It ensures that every developer and CI environment installs identical dependencies, preventing "it works on my machine" bugs caused by silent updates.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
Compiled languages are translated into machine code before execution (C++, Go). Interpreted languages are executed line-by-line or via bytecode at runtime (Python, Ruby).

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
A Reverse Proxy sits in front of web servers to handle load balancing/SSL termination; a Forward Proxy sits in front of clients to hide their identity/filter content. Common Reverse Proxies: **NGINX** (Load Balancing) and **HAProxy** (High-performance Layer 4 switching).

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A deadlock is when processes wait indefinitely for resources held by each other. The Coffman conditions are: 1) Mutual Exclusion, 2) Hold and Wait, 3) No Preemption, 4) Circular Wait.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
Eventual consistency means that if no new updates are made, all replicas will eventually converge. Cassandra handles this with "Tunable Consistency": you can choose `ONE` (fastest), `QUORUM` ($n/2 + 1$), or `ALL`. To ensure read-after-write, one would typically use `QUORUM` for both reads and writes.

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process.**
mTLS requires *both* client and server to present certificates. Handshake: Client sends Hello $\rightarrow$ Server sends Cert $\rightarrow$ Client verifies Server cert $\rightarrow$ Client sends its own Cert $\rightarrow$ Server verifies Client cert $\rightarrow$ Both exchange keys via Diffie-Hellman $\rightarrow$ Encrypted session begins. Used heavily in **Service Meshes** (e.g., Istio).

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
A hash table maps keys to array indices using a hash function. 
*   **Chaining:** Store multiple items in a linked list at each index.
*   **Open Addressing:** Find the next empty slot (Linear Probing).
Complexity: Average $O(1)$, Worst Case $O(n)$ (when many collisions occur).

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures.**
It stops requests to a failing service to allow it to recover. 
*   **Closed:** Normal operation; requests pass through.
*   **Open:** Service failed; fail fast immediately without trying.
*   **Half-Open:** Allow a limited number of test requests to see if the service has recovered. It relates to retries by preventing "retry storms" where constant retries overwhelm a struggling system.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example.**
*   **Optimistic:** Assume no conflict; check version on write before committing. Use for low contention (e.g., web apps with row versioning/timestamps).
*   **Pessimistic:** Lock the record so others cannot access it until done. Use for high contention or critical financial transactions (e.g., `SELECT FOR UPDATE`).
