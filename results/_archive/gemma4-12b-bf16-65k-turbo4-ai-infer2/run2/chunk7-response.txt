## Application Architecture

**AA1 — Easy:** A monolith is a single unified unit where all components share memory and resources. Microservices decompose an application into small, independent services communicating over a network. **3 problems introduced by microservices:** 1) Network latency/overhead between calls, 2) Complexity of distributed transactions (data consistency), and 3) Operational complexity in monitoring and deployment.

**AA2 — Easy:** Synchronous communication requires the requester to wait for a response before proceeding (e.g., REST/HTTP). Asynchronous communication allows the sender to continue without waiting for an immediate response (e.g., Message Queues like RabbitMQ or Kafka).

**AA3 — Medium:** An API Gateway acts as a single entry point that handles request routing, rate limiting, authentication, and protocol translation. A reverse proxy sits in front of a web server to handle load balancing and SSL termination. While an API Gateway *can* perform many functions of a reverse proxy, it cannot replace it entirely because high-performance proxies are optimized for raw throughput at scale, whereas Gateways focus on logic/orchestration.

**AA4 — Medium:** The Saga pattern manages distributed transactions by breaking them into local transactions. In **Choreography**, each service produces events that trigger actions in other services (decentralized). In **Orchestration**, a central controller tells participants what to do. Choreography is better for simple workflows; Orchestration is preferred for complex business processes with many steps where visibility is required.

**AA5 — Medium:** CQRS separates read and write operations into different models. It is paired with Event Sourcing because when every change is stored as an immutable event stream, you can project those events into different "read" views. This solves the problem of complex joins and performance bottlenecks in traditional CRUD systems when data needs to be served in multiple formats simultaneously.

**AA6 — Medium:** The Circuit Breaker prevents a failing service from causing a cascading failure. States: 1) Closed (normal), 2) Open (failure detected, requests fail fast), 3) Half-Open (testing if the service has recovered). A retry with backoff handles transient blips; a circuit breaker handles systemic failures. You use both together so that retries happen only during minor hiccups while the circuit opens during sustained outages.

**AA7 — Hard:**
1.  **Shared DB/Schema:** Lowest cost, highest risk of noisy neighbors, lowest isolation. Good for low-security, high-volume small tenants.
2.  **Separate Schema per Tenant:** Balanced approach. Better security/isolation than row-level, but harder to manage migrations across hundreds of schemas. Moderate cost.
3.  **Separate Database:** Highest isolation, easiest to scale independently, most expensive, hardest to manage at massive scale. Best for enterprise clients requiring strict compliance.

**AA8 — Hard:** Eventual consistency means all replicas will eventually converge, but may return stale data temporarily. Strong consistency ensures all reads see the latest write immediately. For inventory (no overselling): Use **Strong Consistency**. Architecture: A relational database (PostgreSQL) or a distributed SQL DB (CockroachDB/Spanner) using ACID transactions. Pattern: Distributed locking or "Reservation" pattern where stock is reserved in a transaction before order processing.

**AA9 — Medium:** A sidecar proxy runs alongside an application container to handle networking logic (mTLS, logging). In Istio, Envoy handles the **Data Plane** (actual traffic), while Istio's control plane manages configuration and policy distribution. mTLS between sidecars solves identity verification; it ensures that only authorized services can talk to each other regardless of network location, which application-level TLS struggles with due to certificate management overhead at the app level.

**AA10 — Medium:** The Strangler Fig pattern involves building new functionality in microservices and gradually routing traffic away from the monolith until the old system is "strangled." Strategy: 1) Identify a small edge capability (e.g., User Profile). 2) Build this as a .NET 8 service. 3) Place an API Gateway in front to route `/profile` requests to the new service and everything else to the legacy monolith. 4) Repeat for more modules.

**AA11 — Medium:** The 12-Factor App methodology provides best practices for cloud-native apps. Factors include: 1) Codebase (one repo per app), 2) Dependencies (explicitly declared), 3) Config (env vars), 4) Backing Services (treat DBs as attached resources), 5) Build/Release/Run (separation of stages), 6) Concurrency (scale via process count). These matter because they ensure portability across environments and allow independent scaling.

**AA12 — Hard:**
*   **Kafka (Event):** Loose coupling, high throughput, handles spikes well, complex debugging (tracing events), guarantees ordering within partitions. Best for async workflows like analytics or order processing.
*   **REST/gRPC (Request):** Tight coupling, lower latency, easier to debug (linear flow), strict request-response. Best for UI interactions where immediate feedback is needed. Choose Kafka when you need "fire and forget" or multi-consumer fan-out; choose gRPC for low-latency internal communication.

**AA13 — Easy:** A load balancer distributes incoming traffic across multiple servers to prevent any single server from becoming a bottleneck. Layer 4 balances at the transport layer (TCP/UDP - IP + Port). Layer 7 balances at the application layer (HTTP/HTTPS - URL path, headers, cookies). Use Case: Routing requests based on URL paths (e.g., `/api` vs `/images`).

**AA14 — Easy:** A message queue stores messages until consumed by a worker (RabbitMQ). A log-based broker (Kafka) treats messages as an append-only log of events that can be replayed. Pick RabbitMQ for simple task distribution (worker queues); pick Kafka for high-throughput stream processing and data replayability.

**AA15 — Easy:** A container shares the host OS kernel but isolates the application process (lightweight). A VM includes a full guest OS (heavy). Containers are popular because they provide consistent environments, start instantly, and allow higher density per host compared to VMs.

**AA16 — Easy:** Stateless services do not store client context between requests (easier to scale horizontally because any instance can handle any request). Stateful services maintain state (e.g., a game session or a database). Example: A web API is stateless; a WebSocket connection is stateful.

**AA17 — Easy:** An ORM maps object-oriented code to relational tables. Examples: Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs increase developer productivity and safety but can lead to "N+1" query problems and less efficient SQL than hand-tuned raw SQL.

**AA18 — Medium:** The Bulkhead pattern partitions resources so that if one part fails, others continue. In microservices, this prevents a slow service from consuming all threads in a shared pool. Implementation: Use separate thread pools for different downstream dependencies or deploy critical services into isolated deployment groups/clusters to limit blast radius.

**AA19 — Hard:**
*   **OT:** Transforms operations based on concurrent edits (Google Docs style). High complexity, requires central server coordination.
*   **CRDTs:** Data structures that merge automatically without conflict. Lower latency, better offline support as they don't require a central coordinator for every step.
*   **Choice:** For **offline editing**, CRDTs are superior because they allow local mutations that converge mathematically when the client reconnects without needing complex transformation logic against a specific history of operations.

**AA20 — Hard:** Challenges include high volume (sampling is needed) and context loss across async boundaries. Context propagation uses headers (W3C Trace Context) to pass IDs. Sampling strategies: Head-based (decide at start), Tail-based (keep trace until end - better for finding errors). Storage: Jaeger/Tempo. To ensure continuity through Kafka, you must inject the trace ID into the message header; the consumer then extracts it to start its own span linked to the producer's span.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** Type 1 hypervisors run directly on hardware (e.g., VMware ESXi, Microsoft Hyper-V). Type 2 hypervisors run on an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2 — Easy:** SAN (Storage Area Network) provides block-level access over a dedicated network (Fibre Channel/iSCSI); used for high-performance DB clusters. NAS (Network Attached Storage) provides file-level access (NFS/SMB); used for shared files.

**OP3 — Medium:** 3-tier (Core, Distribution, Access) was designed for hierarchical traffic flow. Leaf-Spine is preferred in modern DCs because every leaf connects to every spine, providing predictable latency and massive east-west bandwidth. It solves the "bottleneck" problem of traditional spanning tree protocols where many links are blocked.

**OP4 — Medium:** Proxmox Cluster: Minimum 3 nodes for quorum (to avoid split-brain). Fencing: STONITH (Shoot The Other Node In The Head) via IPMI or PDU power cycling. Shared Storage: Ceph (highly scalable), iSCSI (block level), or NFS (file level). On failure: If a node dies, the VM automatically restarts on another node; if it's a storage node, Ceph handles replication.

**OP5 — Medium:** VLAN trunking allows multiple VLANs to travel across one physical link using 802.1Q tags. To configure a single NIC on 3 VLANs in Linux, you use **Sub-interfaces** (e.g., `eth0.10`, `eth0.20`, `eth0.30`) with separate IP addresses assigned to each virtual interface.

**OP6 — Medium:** RAID 1 (Mirror - High redundancy/Low capacity), RAID 5 (Parity - Good balance), RAID 6 (Double Parity - Higher safety), RAID 10 (Mirror+Stripe - Best performance/redundancy), RAID Z2 (ZFS equivalent of RAID 6). For a DB server with 6 drives: Choose **RAID 10**. It provides the best write performance and high fault tolerance for random I/O workloads typical of databases.

**OP7 — Hard:** Architecture: Internal DNS servers provide local records + forwarders to public DNS. DMZ has its own authoritative zone. Split-horizon ensures internal IPs aren't leaked to the internet. VPN clients get "Conditional Forwarding" to reach internal zones. When moving from Office to VPN, the client switches from the office recursive resolver to the VPN tunnel's gateway. DNSSEC adds cryptographic signatures to prevent cache poisoning.

**OP8 — Hard:** Chain: Root CA -> Subordinate CA -> End Entity. The Root CA is kept offline in a vault. CRL (Certificate Revocation List) lists revoked certs; OCSP (Online Certificate Status Protocol) queries status in real-time. A compromised subordinate CA allows an attacker to issue fake certificates for your domain; a compromised root CA compromises the entire trust anchor of the organization.

**OP9 — Hard:** MPLS (Expensive, reliable), IPsec (Cheap, variable latency), SD-WAN (Smart routing over any path), WireGuard Mesh (Low overhead, peer-to-peer). Recommendation: **SD-WAN**. It combines the reliability of private paths with the cost-savings of the internet while providing built-in features like jitter buffering and path steering specifically designed for VoIP.

**OP10 — Medium:** iDRAC/iLO/IPMI are Out-of-Band (OOB) management interfaces that work even if the OS is crashed or the NIC is down. They allow remote power control, console access, and hardware monitoring. If exposed to the internet without a firewall/VPN, an attacker can gain full physical control of the server's hardware.

**OP11 — Medium:** LVM provides logical volume management on block devices. LVM-Thin allows over-provisioning (allocating more space than exists physically). ZFS is a combined file system and volume manager. Use LVM for standard flexibility, LVM-Thin for high-density VM storage, and ZFS for data integrity (checksumming) and advanced snapshots. Snapshots in LVM-Thin are "Copy-on-Write" but consume space as changes occur; ZFS snapshots are nearly instantaneous and highly efficient.

**OP12 — Hard:** Stretch Cluster: 3 nodes across sites + a "Witness" node at a third site to maintain quorum. Ceph CRUSH rules must be configured to ensure replicas are distributed across different sites. Network latency between sites must be <10ms for synchronous replication. Split-brain occurs if the link breaks; the witness decides which side stays up. Why 2-site Ceph is bad? Without a 3rd location for a tiebreaker, both sides might think they are the primary, leading to data corruption.

**OP13 — Easy:** DHCP assigns IPs automatically. DORA: Discover, Offer, Request, Acknowledge. If the server is down, Windows clients will use an APIPA address (169.254.x.x), which is a self-assigned non-routable IP.

**OP14 — Easy:** Managed switches support VLANs, QoS, SNMP monitoring, and Link Aggregation (LACP). These are critical for segmenting traffic, prioritizing voice/video, and managing network health remotely. Unmanaged switches are simple plug-and-play devices with no configuration capability.

**OP15 — Easy:** NTP synchronizes clocks. Accurate time is vital because many protocols (Kerberos, LDAP) and logs rely on precise timestamps to validate authentication tokens or sequence events during troubleshooting. Clock drift can cause Kerberos authentication failures in Active Directory environments.

**OP16 — Easy:** Physical Server = Hardware only. VM = Emulated hardware running a Guest OS. Container = Isolated process sharing the Host OS kernel. Run directly on bare metal when you need maximum performance (e.g., high-frequency trading, heavy DBs) where hypervisor overhead is unacceptable.

**OP17 — Easy:** UPS provides immediate battery power during a power dip; Generator provides long-term power during a blackout. You need both: UPS handles the "gap" while the generator starts up. ATS automatically detects power loss and switches the load from the utility grid to the generator.

**OP18 — Medium:** Active-Passive: One node works, one waits. Active-Active: Both handle traffic simultaneously. For PostgreSQL HA using Pacemaker/Corosync: Use Corosync for cluster heartbeat, Pacemaker for resource management, STONITH to ensure that if a node fails, it is physically powered off so it doesn't try to claim the Virtual IP (VIP). Failover happens when the VIP moves to the healthy node.

**OP19 — Hard:** 3-2-1 Rule: 3 copies of data, 2 different media types, 1 offsite. RPO (Recovery Point Objective - how much data can we lose?) vs RTO (Recovery Time Objective - how fast must we be back?). Full backups are baseline; Incremental only saves changes since last backup. Deduplication reduces storage footprint. Immutable backups (WORM) prevent ransomware from deleting your backups. Backup = copying data; Disaster Recovery = the plan/process to restore operations after a catastrophe.

**OP20 — Hard:** 802.1X uses a Supplicant (client), Authenticator (switch), and Auth Server (RADIUS). EAP-TLS provides certificate-based auth; PEAP uses usernames/passwords over an encrypted tunnel. RADIUS handles the backend logic. Dynamic VLANs allow the switch to put a user in a specific VLAN based on their credentials. MAB allows devices like printers (which have no supplicant) to authenticate via their MAC address against a whitelist.
