## Kubernetes

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** is used for stateless applications where pods are interchangeable; any pod can be replaced by another with the same configuration. A **StatefulSet** is used for stateful applications (like databases) where each pod has a unique, persistent identity (e.g., `pod-0`, `pod-1`), stable network identifiers, and dedicated persistent storage that persists across restarts.

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
The Service provides a stable virtual IP (VIP). When traffic hits this VIP, **kube-proxy** (running on every node) intercepts the packet using `iptables` or `IPVS` rules. It then performs load balancing (usually random or round-robin) to forward the request to one of the backend Pod IPs listed in the Service's Endpoints object.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
- **StorageClass**: Defines the "flavor" of storage available (e.g., SSD, HDD, Provisioner types). It acts as a blueprint.
- **PersistentVolume (PV)**: A piece of storage provisioned by an administrator or dynamically created by a StorageClass. It is the actual resource.
- **PersistentVolumeClaim (PVC)**: A user's request for storage (size, access mode). 
*Relationship:* A user creates a PVC; the cluster uses the StorageClass to automatically provision a PV that satisfies the PVC requirements.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps.**
1.  **Check Logs:** Run `kubectl logs <pod_name>` to see application-level errors/stack traces.
2.  **Describe Pod:** Run `kubectl describe pod <pod_name>` to check for events like OOMKilled, FailedScheduling, or ImagePullBackOff.
3.  **Resource Limits:** Check if the pod is hitting memory/CPU limits causing it to be killed.
4.  **Liveness/Readiness Probes:** Verify if the probes are failing due to incorrect port/path configurations or slow startup times.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS is the cluster's internal DNS server. It resolves service names (e.g., `my-svc.default.svc.cluster.local`) and external domain names. If CoreDNS is down, pods will fail to resolve other services within the cluster and cannot reach any external APIs via hostnames. Internal communication using IP addresses would still work, but hostname-based discovery fails.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on.**
The scheduler follows two main phases:
1.  **Filtering (Predicates):** The scheduler eliminates nodes that don't meet requirements (e.g., insufficient CPU/RAM, Taints without Tolerations, NodeSelector mismatches).
2.  **Scoring (Priorities):** Remaining nodes are scored based on factors like:
    *   **LeastRequestedPriority:** Preferring nodes with more free resources.
    *   **ImageLocality:** Preferring nodes that already have the container image downloaded.
    *   **Affinity/Anti-affinity:** Ensuring pods stay together or apart as requested by the user.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
- **Scheduling:** Yes, it will be scheduled. Scheduling is based on *Requests*. $3.5\text{GB} + 256\text{MB}$ is less than $4\text{GB}$.
- **Runtime:** If it hits $600\text{Mi}$, it stays running because its limit is $512\text{Mi}$. However, since $600 > 512$, the Kubelet will trigger an **OOMKill** (Out Of Memory Kill) once it exceeds the $512\text{Mi}$ limit.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller.**
1.  External LB receives the request and forwards it to the **Ingress Controller's** NodePort/LoadBalancer IP.
2.  The **NGINX Ingress Controller** matches the Host/Path against the **Ingress Resource** rules.
3.  The Controller identifies the target **Service**.
4.  The Controller looks up the **Endpoints** object for that Service to get actual Pod IPs.
5.  Traffic is routed from the Controller directly to the **Pod IP**. (*Note: kube-proxy handles internal routing if the controller doesn't route directly to pods*).

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A NetworkPolicy is a firewall for pods, controlling ingress/egress traffic at the L3/L4 layers. By default, all pods are "open" (allow all traffic). When you apply a policy selecting specific pods, those pods become isolated; they will only allow traffic explicitly permitted by the new policy (default deny logic applies once a policy is attached).

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies.**
- **RollingUpdate**: Gradually replaces old pods with new ones. It ensures zero downtime but might result in two versions of the app running simultaneously.
- **Recreate**: Kills all existing pods before starting new ones. This causes downtime but ensures only one version of the app is active at any time. Choose **Recreate** when the application does not support concurrent versioning or has strict singleton requirements (e.g., some legacy databases).

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A Namespace is a virtual cluster within a physical cluster used to partition resources and provide isolation between teams/projects. Default namespaces include `default`, `kube-system` (system components), `kube-public`, and `kube-node-nginux`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name 3 pieces of information it shows that `kubectl get pod` does not.**
It provides detailed metadata about a specific resource's state. Information included that `get` doesn't show:
1.  **Events:** A chronological log of recent actions (e.g., "Pulled image", "Failed scheduling").
2.  **Container Status:** Specific states like `Running`, `Waiting`, or `Terminated` with exit codes.
3.  **Resource Usage/Limits:** Shows specifically which limits were set vs. current requests.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A ConfigMap stores non-confidential configuration data. Pods consume them via:
1.  **Environment Variables:** Injecting values directly into the container's environment.
2.  **Volume Mounts:** Mounting the ConfigMap as a file in a directory inside the container.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
- **ClusterIP**: Internal IP only; reachable only from within the cluster.
- **NodePort**: Exposes the service on a specific port on every Node's IP (reachable externally).
- **LoadBalancer**: Provisions an external cloud load balancer that routes traffic to the service (standard for production public access).

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A DaemonSet ensures that all (or some) nodes run exactly one copy of a pod. Use a DaemonSet for infrastructure tasks like log collection (`fluentd`), monitoring agents (`Prometheus Node Exporter`), or networking plugins where you need a presence on every node regardless of scale.

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case.**
- **Taints/Tolerations**: A "repulsion" mechanism. Nodes have Taints; Pods must have Tolerations to be scheduled there. *Use Case:* Keeping pods off GPU nodes unless they specifically need them.
- **Node Affinity**: An "attraction" mechanism. Pods have rules specifying which nodes they prefer/require. *Use Case:* Ensuring a web server runs only in a specific Availability Zone.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller?**
An Operator is a method of packaging human operational knowledge into software. While a standard Controller handles simple loops (e.g., "ensure 3 replicas"), an Operator manages complex stateful logic (e.g., "how to perform a database failover," "how to backup data"). It uses Custom Resource Definitions (CRDs) to define these custom behaviors.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens if quorum is lost? Recovery for 2 out of 3 nodes lost?**
etcd uses the **Raft consensus algorithm**, providing strong consistency. If quorum is lost (majority cannot agree), the cluster becomes read-only or stops accepting writes, preventing split-brain scenarios. To recover from losing 2 out of 3 nodes permanently: You must force a new cluster member with a new ID and manually reset the cluster's membership via `etcdctl` to establish a new quorum.

**K19 — Hard: Describe how Kubernetes RBAC works. Write manifests for read-only access to pods/logs in one namespace.**
RBAC maps identities (Users/ServiceAccounts) to permissions (Roles).
- **Role**: Permissions within a Namespace.
- **ClusterRole**: Permissions across the whole Cluster.
- **RoleBinding**: Links Role to User in a Namespace.
- **ClusterRoleBinding**: Links ClusterRole to User globally.

*Manifest:*
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-ns
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: my-ns
  name: read-only-binding
subjects:
- kind: User
  name: developer-user
  user: "dev_user"
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io/v1
```

**K20 — Hard: Explain how `ndots` causes excessive DNS queries and fix via `dnsConfig`.**
By default, Kubernetes sets `ndots: 5`. When resolving a name like `google.com`, the resolver tries appending each part of the domain with the cluster's search paths (e.g., `google.com.default.svc.cluster.local`) before trying the actual name. This creates many failed lookups for every single request. To fix this, use `dnsConfig` in the Pod spec to set `ndots: 1` or provide a specific `nameservers` list to reduce unnecessary searching.

## Development

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
Merge combines two branches by creating a new commit that joins histories. Rebase moves the entire base of your branch to a new starting point, resulting in a linear history. **Avoid rebasing** on public shared branches; it rewrites history, which can cause major conflicts for other developers working on those commits.

**D2 — Easy: Explain the difference between TCP and UDP.**
- **TCP**: Connection-oriented, guarantees delivery, ensures order, uses error correction/retransmission. *Protocols:* HTTP, SSH.
- **UDP**: Connectionless, faster, no guarantee of delivery or order. *Protocols:* DNS, VoIP/Streaming.

**D3 — Medium: What is a race condition? Give an example.**
A race condition occurs when the output of a program depends on the unpredictable timing of events (e.g., threads). Example: Two threads try to increment a counter simultaneously without locking. Both read "5", both add 1, and write back "6" instead of the expected "7".

**D4 — Medium: Symmetric vs Asymmetric encryption. How are they used together in TLS?**
- **Symmetric**: Same key for encryption/decryption (fast).
- **Asymmetric**: Public/Private key pair (slower but allows secure exchange).
*In TLS:* Asymmetric encryption is used during the initial handshake to securely exchange a symmetric session key. Once established, symmetric encryption handles the actual data transfer for speed.

**D5 — Medium: What is a container image layer? How does caching affect Dockerfile best practices?**
Each command in a Dockerfile creates a new layer. If a line changes, all subsequent layers must be rebuilt. Best practice: Place commands that change frequently (like `COPY . .`) at the bottom of the file and stable dependencies (`RUN apt install...`) at the top to maximize cache hits.

**D6 — Medium: REST API returning HTTP 503 intermittently. Describe checks.**
1.  Check Load Balancer logs (is it failing before reaching the app?).
2.  Check Application Logs (are there internal errors or timeouts?).
3.  Check Resource Utilization (CPU/Memory spikes on the server).
4.  Check Upstream Dependencies (is a database or third-party API timing out?).

**D7 — Hard: Explain CAP theorem. Give examples.**
CAP states a distributed system can only provide two of three: Consistency (all nodes see same data), Availability (every request gets a response), Partition Tolerance (system works despite network failure).
- **CP Example:** HBase / etcd (Consistency over availability during partition).
- **AP Example:** Cassandra / DynamoDB (Availability over consistency during partition).

**D8 — Medium: Horizontal vs Vertical scaling. What patterns enable horizontal scaling?**
- **Vertical**: Adding more power (CPU/RAM) to an existing machine. Limited by hardware ceilings.
- **Horizontal**: Adding more machines to the pool.
*Patterns:* Statelessness, Load Balancing, Database Sharding, and Asynchronous Messaging.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An env var is a dynamic value used by processes. To persist it in Linux, add `export VAR_NAME=value` to your shell profile file (e.g., `.bashrc`, `.zshrc`, or `/etc/environment`).

**D10 — Easy: JSON vs YAML. Name one advantage of each.**
- **JSON**: Lightweight, standard for web APIs. Advantage: Faster parsing/native support in most languages.
- **YAML**: Human-readable, supports comments. Advantage: Much easier for humans to write complex configurations.

**D11 — Easy: What is a REST API? Explain GET, POST, PUT, DELETE.**
REST is an architectural style using HTTP methods.
- **GET**: Retrieve data (Read).
- **POST**: Create new resource.
- **PUT**: Update/Replace existing resource.
- **DELETE**: Remove a resource.

**D12 — Easy: What is version pinning? Why is it important?**
Version pinning specifies the exact version of a dependency (e.g., `requests==2.25.1`). It ensures reproducible builds; without it, a minor update in a library could break your build unexpectedly during deployment.

**D13 — Easy: Compiled vs Interpreted language.**
- **Compiled**: Source code is translated into machine code before execution (Fast runtime). *Examples:* C++, Rust.
- **Interpreted**: Code is executed line-by-line by an interpreter (Easier development). *Examples:* Python, Ruby.

**D14 — Medium: Reverse proxy vs Forward proxy.**
- **Forward Proxy**: Sits in front of clients (users) to hide their identity or filter access. Example: Corporate web filters.
- **Reverse Proxy**: Sits in front of servers to balance load and provide security. Examples: NGINX, HAProxy. Use case: Load balancing traffic across multiple backend app servers.

**D15 — Medium: What is a deadlock? Four Coffman conditions.**
A deadlock is when two processes are waiting for each other to release resources. The four conditions required:
1. Mutual Exclusion (Resource can't be shared).
2. Hold and Wait (Process holds one resource while waiting for another).
3. No Preemption (Resources cannot be forcibly taken).
4. Circular Wait (Chain of processes waiting on each other).

**D16 — Hard: Eventual consistency. How does Cassandra handle read-after-write?**
Eventual consistency means that given enough time without updates, all replicas will converge. Cassandra handles this via "Tunable Consistency." You can choose levels like `ONE` (fastest, low consistency), `QUORUM` (majority must agree), or `ALL` (slowest, highest consistency).

**D17 — Hard: What is mTLS? Explain the handshake.**
mTLS requires both client and server to present certificates. 
*Handshake:* Client sends certificate $\rightarrow$ Server verifies it; Server sends its cert $\rightarrow$ Client verifies it. Both exchange keys using asymmetric encryption to establish a symmetric session key. Used in Service Mesh (Istio/Linkerd) to secure pod-to-pod communication.

**D18 — Hard: Hash table internals.**
A hash table maps keys to indices using a hash function.
- **Chaining**: Each bucket contains a linked list of entries with the same hash.
- **Open Addressing**: If a collision occurs, find the next available slot (Linear Probing, Quadratic Probing).
*Complexity:* Average $O(1)$ for Insert/Lookup/Delete. Worst case $O(n)$ if many collisions occur at one index.

**D19 — Hard: Circuit Breaker pattern.**
Prevents a failing service from causing a cascade failure by stopping requests to a known-failing service.
- **Closed**: Requests flow normally.
- **Open**: Requests fail immediately without hitting the backend.
- **Half-Open**: Allows a limited number of test requests to see if the service has recovered.
It works with *Retries* (which can overwhelm a struggling system) and *Exponential Backoff* (waiting longer between retries) to allow the system time to recover.

**D20 — Hard: Optimistic vs Pessimistic concurrency control.**
- **Optimistic**: Assume no conflict; check for changes only at commit time (e.g., Versioning/Timestamps). Best for high-read, low-write systems.
- **Pessimistic**: Lock the record so others cannot access it until finished (e.g., `SELECT FOR UPDATE`). Best for high-contention environments where conflicts are frequent.
