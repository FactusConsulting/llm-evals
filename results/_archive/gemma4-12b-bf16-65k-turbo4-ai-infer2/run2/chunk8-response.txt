## Cloud Infrastructure Architecture

**CL1 — Easy:**
IaaS (Infrastructure as a Service): Provider provides VMs, storage, and networking; you manage OS and apps (e.g., AWS EC2). 
PaaS (Platform as a Service): Provider manages OS/runtime; you manage code/apps (e.g., Google App Engine). 
SaaS (Software as a Service): Provider manages everything; you use the software (e.g., Microsoft M365).

**CL2 — Easy:**
The Shared Responsibility Model defines who is responsible for security/maintenance.
- **IaaS VMs:** Provider handles physical hardware/virtualization; You handle OS, patching, and data.
- **Managed Kubernetes:** Provider handles the Control Plane; You handle worker nodes, pods, and container images.
- **SaaS (M365):** Provider handles almost everything except your data and identity management.

**CL3 — Medium:**
- **VPC:** A private virtual network in the cloud.
- **Subnet:** A range of IP addresses within a VPC.
- **Security Group:** A stateful firewall at the instance level (allows inbound/outbound).
- **NACL:** A stateless firewall at the subnet level (filters all traffic entering/leaving).
*Layering:* NACL filters first $\rightarrow$ Subnet $\rightarrow$ Security Group $\rightarrow$ Instance.
*Stateful vs Stateless:* Stateful remembers connection states (if port X is open for inbound, it's automatically allowed for outbound); Stateless requires explicit rules for both directions.

**CL4 — Medium:**
A **Landing Zone** is a pre-configured multi-account environment with established governance. 
- **OUs:** Organize accounts by function (Prod, Dev, Shared Services).
- **Guardrails:** Automated policies (SCP/Azure Policy) to enforce compliance.
- **Shared Networking:** Transit Gateway (AWS) or Hub-and-Spoke (Azure) connects VPCs/VNets via a central hub.
- **Centralized Logging:** Aggregating logs from all accounts into one "Log Archive" account.
*Single-account risk:* Leads to blast radius issues, lack of isolation, difficult permission management, and hitting service limits.

**CL5 — Medium:**
Infrastructure as Code (IaC) manages infrastructure via configuration files.
- **Terraform/OpenTofu:** Cloud-agnostic, stateful, HCL language. Best for multi-cloud.
- **Pulumi:** Uses general programming languages (Python, Go). Best for complex logic.
- **CloudFormation/Bicep:** Provider-specific. Best for deep integration with AWS/Azure native features.
- **Crossplane:** Kubernetes-native IaC. Best if you want to manage cloud resources directly via K8s APIs.

**CL6 — Medium:**
- **HPA:** Scales pods based on CPU/RAM metrics.
- **VPA:** Adjusts the size of existing pods (restarts them).
- **Cluster Autoscaler:** Adds/removes physical nodes when pods can't fit.
- **KEDA:** Event-driven autoscaling (e.g., scale based on RabbitMQ queue length or Kafka lag).
*Use KEDA over HPA:* When scaling needs to be triggered by external events rather than just resource utilization.

**CL7 — Hard:**
Strategy: Multi-region Active-Active setup. 
- **RPO/RTO:** Target RPO $\approx$ 0 (near real-time), RTO < minutes.
- **Architecture:** Active-Active (traffic split across regions) vs Active-Passive (failover only).
- **Database:** Synchronous replication (low latency penalty) for zero data loss; Asynchronous for high performance.
- **DNS:** Route53/Traffic Manager health checks and weighted routing.
- **State Management:** Global session handling (Redis/DynamoDB Global Tables).
- **Cost:** High cost due to redundant resources in both regions.
*DR Types:* Pilot Light (minimal core components running); Warm Standby (scaled down version ready to scale up); Multi-site Active-Active (full capacity in both, highest cost/resiliency).

**CL8 — Hard:**
GitOps is the practice of using Git as the "Source of Truth" for infrastructure state.
- **ArgoCD vs FluxCD:** ArgoCD uses a pull model with a UI/Dashboard; FluxCD is more lightweight and focuses on automated reconciliation.
- **Secrets:** Sealed Secrets (encrypted secrets stored in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
- **Drift:** If manual changes occur, the controller detects the difference between the live state and Git and automatically reverts the environment back to the Git configuration.

**CL9 — Hard:**
Architecture Design:
1.  **StatefulSet:** Ensures stable network IDs and persistent storage mapping.
2.  **PV/PVC:** Use `local` storage class for low-latency NVMe disks attached to specific nodes.
3.  **Headless Service:** Provides direct pod IP access without load balancing.
4.  **Init Containers:** Handle pre-startup tasks like config file generation or DB migrations.
5.  **ConfigMaps:** Mounted as volumes at specific paths (`/etc/app/config`).
6.  **PDBs:** Ensure minimum available pods during updates to prevent downtime.

**CL10 — Medium:**
- **Service Account:** Identity for an application running inside K8s.
- **Workload Identity / IRSA:** Maps a K8s service account directly to a Cloud IAM Role (e.g., AWS IAM). This allows the Pod to assume permissions without needing static keys.
*Why mounting credentials is bad:* Static keys can be stolen from logs or compromised containers. 
*Solution:* Workload Identity Federation provides short-lived, rotating tokens tied to the pod's identity.

**CL11 — Medium:**
- **Object Storage (S3):** Unstructured data, virtually infinite scale, high durability ($99.999999999\%$). Best for images, backups, logs.
- **Block Storage (EBS):** Virtual hard drives attached to VMs. High performance, low latency. Best for databases.
- **File Storage (EFS):** Shared filesystem accessible by multiple instances simultaneously. Best for content management systems.

**CL12 — Hard:**
Zero Trust Architecture:
- **Network Policies:** Default deny all; allow only specific microservice communication.
- **Service Mesh (Istio/Linkerd):** Provides mTLS between pods and observability.
- **Pod Identity:** Use IRSA/Workload Identity so each pod has its own unique permission set.
- **Admission Controllers:** OPA Gatekeeper or Kyverno to enforce "no root" or "signed image only" policies.
- **Runtime Security:** Falco to detect anomalous syscalls in real-time.
- **Secrets:** HashiCorp Vault with CSI driver injection.
*Difference:* Traditional security focuses on a "hard shell" (Firewall); Zero Trust assumes the network is already breached and verifies every single request internally.

**CL13 — Easy:**
A CDN caches content at edge locations closer to users. It works by intercepting requests and serving cached copies from nearby servers. 
- **Services:** AWS CloudFront, Azure CDN.
- **Use Case:** Use a CDN for static assets (images, JS) or high-traffic websites to reduce latency and origin load. Serve directly if data is highly dynamic/personalized per user.

**CL14 — Easy:**
- **Regions:** Geographic areas (e.g., us-east-1).
- **Availability Zones (AZs):** Isolated locations within a region with independent power/cooling.
Deploy across AZs to protect against local hardware failures.
- **Zonal vs Regional:** Zonal resources (like some disks) are tied to one AZ; Regional resources (like S3 buckets or Load Balancers) span multiple AZs automatically.

**CL15 — Easy:**
Managed DB services automate: Patching, automated backups, High Availability (Multi-AZ failover), and scaling. Running on a VM requires you to manage OS updates, manual replication setup, and manual failover logic.

**CL16 — Easy:**
- **Users:** People. **Groups:** Collections of users. **Roles:** Permissions assigned to identities. **Policies:** JSON documents defining permissions.
*Least Privilege:* Grant only the minimum permissions required to perform a task. Apply by using Roles instead of Users for applications and scoping policies to specific actions (e.g., `s3:GetObject` rather than `s3:*`).

**CL17 — Easy:**
Serverless is execution of code without managing servers. 
- **Cold Starts:** The delay when a function starts after being idle because the provider must spin up a container. Matters for latency-sensitive apps.
- **Poor Fit:** Long-running processes (e.g., heavy video encoding) or tasks requiring very low/consistent sub-millisecond latency.

**CL18 — Medium:**
- **Ingress Resource:** Standard K8s object for external access.
- **Gateway API:** Newer standard providing more expressive routing/traffic management features.
- **Cloud LB Annotations:** Specific instructions for AWS ALB/NLB behavior.
- **Service Mesh Ingress:** Handles traffic at Layer 7 with advanced retries/circuit breaking.
*TLS Termination:* Can happen at the Load Balancer, the Ingress Controller, or the Pod itself. Gateway API is preferred over Ingress for complex multi-tenant routing and standardized lifecycle management.

**CL19 — Hard:**
Strategy:
1.  **Commitment:** Use Reserved Instances/Savings Plans for steady-state workloads; Spot instances for batch processing.
2.  **Right-sizing:** Analyze CPU/RAM utilization to downsize oversized VMs.
3.  **Storage Tiering:** Move old data to S3 Intelligent-Tiering or Glacier.
4.  **FinOps:** Implement "Showback" (reporting costs to teams) and "Chargeback" (billing teams directly).
5.  **Tools:** CloudHealth, AWS Cost Explorer, or Azure Cost Management. Establish a monthly review cadence with engineering leads.

**CL20 — Hard:**
Multi-cloud strategy:
- **Abstraction:** Use Kubernetes as the common runtime across both clouds.
- **IaC:** Terraform allows managing both providers via one tool.
- **Networking:** Site-to-Site VPNs or dedicated interconnects (DirectConnect/ExpressRoute).
- **Identity:** Identity Federation (OIDC) to sync identities between clouds.
*Trade-offs:* Multi-cloud increases complexity, latency, and operational overhead significantly. 
*Justification:* Only justified for extreme regulatory requirements, high availability (avoiding provider outage), or specific feature needs not available on one platform. Otherwise, it is unnecessary complexity.

## OT Infrastructure Architecture

**OT1 — Easy:**
The Purdue Model defines levels of industrial automation hierarchy.
- Level 0: Physical Process (Sensors, Actuators).
- Level 1: Basic Control (PLCs, DCS controllers).
- Level 2: Area Control (HMIs, SCADA systems).
- Level 3: Site Manufacturing Operations (Historians, MES).
- Level 4: Business Planning (Enterprise IT network).
- Level 5: Enterprise Network (Internet, Corporate Office).

**OT2 — Easy:**
IT focuses on Data Confidentiality/Integrity; OT focuses on Safety and Availability (Uptime). You cannot apply standard patching because many OT devices have limited resources, lack modern OS support, and require "zero downtime" updates where a reboot could cause physical damage or safety risks.

**OT3 — Medium:**
An **IDMZ** acts as a buffer between the corporate network and the production floor.
- **Allowed Traffic:** Specific protocols (e.g., OPC UA) from Level 3 to Level 4 for data collection.
*Danger:* Direct connectivity allows an attacker to move laterally from a compromised office laptop directly into a PLC that controls a turbine or valve.

**OT4 — Medium:**
1.  Modbus TCP: Level 1 & 2 (Legacy industrial protocol).
2.  OPC UA: Level 2 & 3 (Standardized communication).
3.  EtherNet/IP: Level 1 & 2 (Common in Rockwell environments).
4.  PROFINET: Level 1 & 2 (Common in Siemens environments).
5.  MQTT: Level 3+ (Used for cloud ingestion via Edge Gateways).

**OT5 — Medium:**
A **Data Diode** is a hardware device allowing data to flow in only one direction physically. A firewall is software-based and can be misconfigured or bypassed. Use a diode when you need absolute assurance that no traffic can enter the OT environment (e.g., pushing logs out of a high-security zone). Limitation: It cannot allow two-way communication (like a request/response handshake).

**OT6 — Medium:**
Flow: Sensors $\rightarrow$ PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (Protocol conversion) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*Security Boundaries:* Place an IDMZ between the local gateway and the cloud; use a Data Diode or strict Firewall at the edge gateway to ensure outbound-only connectivity.

**OT7 — Hard:**
IEC 62443 defines security zones based on risk profile and conduits as the paths between them.
- **Zone:** Grouping of assets with similar security requirements.
- **Conduit:** The controlled path (firewall/diode) connecting zones.
*Design:* Zone 1: Corporate Network; Zone 2: Engineering Workstations; Zone 3: SCADA/Historian; Zone 4: PLCs; Zone 5: SIS. Conduits connect these via firewalls, ensuring only specific protocols move between levels.

**OT8 — Hard:**
Strategy:
1.  **VLANs:** Segment by function (PLC VLAN, HMI VLAN, Historian VLAN).
2.  **Firewalls:** Place industrial firewalls between Level 2 and Level 3.
3.  **Switch Architecture:** Use managed switches for Layer 3 routing and port security.
4.  **Remote Access:** Via Jump Host in the IDMZ with MFA.
5.  **Transition:** Implement "Parallel Infrastructure" where new segments are built alongside old ones, migrating one production line at a time during scheduled maintenance windows.

**OT9 — Hard:**
SIS is designed to take the process to a safe state in an emergency (e.g., pressure relief); BPCS handles day-to-day control. IEC 61511 governs SIS safety standards. SIS must be isolated because if ransomware hits the SIS, it could disable safety shutdowns, leading to physical explosions or environmental disasters. It must be air-gapped from IT to prevent remote exploitation.

**OT10 — Medium:**
- **PLC:** Small, dedicated controller for logic/motion.
- **DCS:** Distributed Control System; large scale, integrated system for complex processes (Refineries).
- **SCADA:** Supervisory system for geographically dispersed assets.
*Coexistence:* Yes, they often coexist (a DCS might manage the main plant while PLCs handle specific sub-processes).

**OT11 — Medium:**
Architecture: Corporate Network $\rightarrow$ VPN Gateway $\rightarrow$ IDMZ Jump Host $\rightarrow$ OT Network.
Requirements: Multi-Factor Authentication (MFA), session recording (for auditing), and time-limited access (only when needed). RDP directly to HMI is unacceptable as it exposes the HMI's OS vulnerabilities to the entire corporate network.

**OT12 — Hard:**
Plan:
1.  **Detection:** Deploy passive IDS (like Dragos or Claroty) on Level 3 switches.
2.  **Inventory:** Maintain a real-time asset inventory to identify what was touched.
3.  **Response:** Isolate the compromised vendor segment immediately via firewall rules.
4.  **Coordination:** Notify operators in the control room before any automated isolation that could trip a process.
5.  **Operator Role:** The operator remains the final authority—they must verify if an action is "safe" before allowing security teams to isolate systems.

**OT13 — Easy:**
An **HMI** provides a graphical interface for human operators to monitor/control processes (buttons, gauges). It differs from an Engineering Workstation because the workstation contains software tools to program PLCs and change logic; the HMI only displays current status and allows setpoint changes.

**OT14 — Easy:**
A **Historian** is a database optimized for time-series data (tags over time). Plant Historians (Level 3) store high-frequency raw sensor data for local operations. Enterprise Historians (Level 4) aggregate this data for long-term business analytics and reporting.

**OT15 — Easy:**
Ladder Logic mimics electrical relay diagrams. It is executed by **PLCs**. It remains dominant because it is intuitive for electricians and maintenance staff who are familiar with physical wiring schematics rather than complex programming languages like C++.

**OT16 — Easy:**
An **RTU** is designed for remote communication over low-bandwidth links (radio, cellular). A PLC is designed for high-speed local control in a factory. RTUs are used in oil fields or water pumping stations where distances are vast and bandwidth is limited.

**OT17 — Easy:**
Analog signals represent continuous values (pressure, temperature). 4-20mA is preferred over 0-20mA because if a wire breaks, the signal drops to 0mA (indicating a fault); at 0-20mA, a broken wire might look like a valid "zero" reading, causing confusion.

**OT18 — Medium:**
Asset inventory is the foundation of security; you cannot protect what you don't know exists.
*Tools:* Passive monitoring (listening to traffic) is safest. Active scanning (pinging/Nmap) can crash older PLCs that have fragile TCP stacks. Use passive discovery first to build the map.

**OT19 — Hard:**
MITRE ATT&CK for ICS focuses on physical impact.
Tactics: 1. Inhibit Response Function (e.g., block safety alarms), 2. Impair Process Control (e.g., change setpoints), 3. Loss of View (block HMI data), 4. Persistence, 5. Initial Access.
Difference: Enterprise matrix focuses on stealing data; ICS matrix focuses on manipulating physical processes. Assessment involves mapping current controls against these specific industrial techniques.

**OT20 — Hard:**
Design:
1.  **Log Collection:** Use an OT-aware sensor (passive) to mirror traffic from switches to a collector. Do not install agents on PLCs.
2.  **SIEM Integration:** Send logs to a central SIEM but use a unidirectional gateway or proxy to ensure no "write" commands go back into the OT network.
3.  **Staffing:** Need both IT analysts (for log analysis) and OT engineers (to verify if a PLC's behavior is actually abnormal).
4.  **Firmware Alert:** If unauthorized firmware changes are detected, immediately notify the plant manager. The operator must confirm if it was a planned update by a vendor before initiating emergency shutdown procedures.
