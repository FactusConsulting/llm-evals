## Kubernetes

**K1 — Easy:** A **Deployment** is for stateless applications; pods are interchangeable, and it manages rolling updates. A **StatefulSet** is for stateful applications; it provides stable network identifiers (pod-0, pod-1), ordered deployment/scaling, and stable persistent storage per pod.

**K2 — Easy:** A **ClusterIP** service creates a virtual IP. `kube-proxy` (via iptables or IPVS) intercepts traffic to this virtual IP and load-balances it across the set of pods matching the service's label selector.

**K3 — Medium:** A **PersistentVolume (PV)** is a piece of storage in the cluster (the actual disk). A **PersistentVolumeClaim (PVC)** is a request for storage by a user. A **StorageClass** is a template that allows for dynamic provisioning of PVs. **Relation:** A user creates a PVC $\rightarrow$ the StorageClass automatically provisions a PV $\rightarrow$ the PVC binds to that PV.

**K4 — Medium:** 
1. `kubectl logs <pod>`: Check application logs for runtime crashes or stack traces.
2. `kubectl describe pod <pod>`: Check "Events" for OOMKilled, failed probes, or scheduling issues.
3. Check Resource Limits: Verify if the pod is hitting memory limits (OOM).
4. Check Config/Secrets: Ensure all required environment variables and secrets are present and correct.

**K5 — Medium:** **CoreDNS** provides service discovery; it maps service names (e.g., `my-svc`) to ClusterIPs. If CoreDNS pods are down, pods cannot resolve internal service names, causing all internal network communication via DNS to fail.

**K6 — Hard:** The scheduler uses a two-step process:
1. **Filtering (Predicates):** Removes nodes that don't meet requirements (e.g., insufficient CPU/RAM, Taints).
2. **Scoring (Priorities):** Ranks remaining nodes.
**Factors:** Resource availability (least requested), Node Affinity/Anti-affinity, and Pod Topology Spread Constraints.

**K7 — Hard:** **Yes**, it will be scheduled because $3.5\text{GB} + 256\text{Mi} < 4\text{GB}$. However, if the pod uses $600\text{Mi}$ at runtime, it exceeds its **limit** ($512\text{Mi}$) and will be **OOMKilled** by the kubelet.

**K8 — Hard:** External LB $\rightarrow$ Ingress Controller (NGINX) $\rightarrow$ Ingress Rule (Host/Path) $\rightarrow$ Service $\rightarrow$ Endpoints (Pod IPs). The Ingress Controller bypasses the Service's virtual IP and sends traffic directly to the **Endpoints** (Pod IPs) using the routing rules managed by the controller, though `kube-proxy`/iptables are used for standard Service traffic.

**K9 — Medium:** A **NetworkPolicy** is an L3/L4 firewall for pods. By default, all pods in a namespace are "non-isolated" (allow all). Once a NetworkPolicy selects a pod, that pod becomes "isolated," and only traffic explicitly allowed by the policy is permitted.

**K10 — Medium:** **RollingUpdate** replaces pods gradually to ensure zero downtime. **Recreate** kills all existing pods before starting new ones. Choose **Recreate** when the application cannot handle two different versions running simultaneously (e.g., during a breaking database schema migration).

**K11 — Easy:** A **namespace** is a logical partition of cluster resources. Default namespaces include `default`, `kube-system` (system components), `kube-public` (publicly visible), and `kube-node-lease`.

**K12 — Easy:** It provides detailed state and metadata. It shows: **Events** (scheduling/pulling errors), **Container Status** (exit codes, restart counts), and **Volume Mounts**.

**K13 — Easy:** A **ConfigMap** stores non-confidential configuration. Consumption methods: 1. Injected as **environment variables**. 2. Mounted as **files** in a volume.

**K14 — Easy:** 
- **ClusterIP:** Internal IP only (default).
- **NodePort:** Exposes service on a static port on every Node IP.
- **LoadBalancer:** Provisions a cloud provider LB that routes to the NodePort.

**K15 — Easy:** A **DaemonSet** ensures one pod runs on every node (or a subset of nodes). Use it for infrastructure services like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium:** **Taints** are applied to nodes to repel pods; **Tolerations** are applied to pods to allow them to stay on tainted nodes. **Node Affinity** attracts pods to specific nodes. 
- **Taint/Toleration Use Case:** Dedicating GPU nodes to only GPU-enabled workloads.
- **Affinity Use Case:** Ensuring a pod runs on a node with an SSD.

**K17 — Medium:** An **Operator** is a custom controller that uses Custom Resource Definitions (CRDs) to manage complex, stateful applications. It encodes "human operational knowledge" into code to automate tasks like backups, upgrades, and failovers for specific apps (e.g., a Postgres Operator).

**K18 — Hard:** etcd uses the **Raft** consensus algorithm (strong consistency). If quorum ($(n/2)+1$) is lost, the cluster becomes read-only or unavailable. Recovery requires restoring from a snapshot to a new etcd cluster and updating the API server to point to the new endpoints.

**K19 — Hard:** **Role** is namespace-scoped; **ClusterRole** is cluster-wide. **RoleBinding** links a user to a Role; **ClusterRoleBinding** links a user to a ClusterRole.
```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: {namespace: my-ns, name: pod-reader}
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: {namespace: my-ns, name: read-pods-binding}
subjects: [{kind: User, name: dev-user}]
roleRef: {kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io}
```

**K20 — Hard:** `ndots:5` causes the resolver to try multiple internal search paths (e.g., `svc.cluster.local`) before trying the external domain. This creates excessive DNS queries. **Fix:** Set `dnsConfig` in the pod spec to `ndots: 1` or use a Fully Qualified Domain Name (FQDN) ending with a dot (e.g., `google.com.`).

## Development

**D1 — Easy:** **Merge** preserves history by creating a merge commit. **Rebase** rewrites history by moving the branch tip to the latest commit of the target branch, creating a linear history. Avoid rebasing **public/shared branches** as it rewrites commit hashes and breaks other developers' histories.

**D2 — Easy:** **TCP** is connection-oriented and reliable (guarantees delivery/order); examples: HTTP, SSH. **UDP** is connectionless and faster (no guarantees); examples: DNS, VoIP.

**D3 — Medium:** A **race condition** occurs when multiple threads access shared data concurrently and the final result depends on the timing of execution. **Example:** Two threads incrementing a shared integer `count++` simultaneously; both read `10`, both increment to `11`, and write back `11` instead of `12`.

**D4 — Medium:** **Symmetric** uses one key for both encryption and decryption (AES). **Asymmetric** uses a public key for encryption and a private key for decryption (RSA). **TLS:** Asymmetric encryption is used to securely exchange a symmetric session key, which is then used for the actual data transfer.

**D5 — Medium:** A **layer** is a read-only snapshot of the filesystem changes. Docker caches layers; if a line in the Dockerfile hasn't changed, Docker reuses the cached layer. **Best Practice:** Order instructions from least-changing (OS/Dependencies) to most-changing (Source Code) to maximize cache hits.

**D6 — Medium:** 
1. **Logs:** Check application logs for timeouts or crashes.
2. **Resources:** Check for CPU/Memory spikes (OOM/Throttling).
3. **Dependencies:** Check if the database or downstream API is timing out.
4. **Infrastructure:** Check Load Balancer/Ingress health and connection limits.

**D7 — Hard:** **CAP Theorem:** A distributed system can only provide two of Consistency, Availability, and Partition Tolerance. 
- **CP (Consistency/Partition):** MongoDB (defaults to consistency; if a primary fails, the system is unavailable until a new one is elected).
- **AP (Availability/Partition):** Cassandra (allows reads/writes during partitions, resolving conflicts later).

**D8 — Medium:** **Horizontal scaling** adds more machines (nodes); **Vertical scaling** adds more resources (CPU/RAM) to one machine. **Patterns:** Statelessness (no local session state), Load Balancing, and Database Sharding.

**D9 — Easy:** An **environment variable** is a dynamic value stored by the OS. To persist it on Linux, add `export VAR_NAME=value` to `~/.bashrc` or `~/.zshrc`.

**D10 — Easy:** **JSON** is a strict, lightweight data format (faster for machines). **YAML** is a human-readable format that supports comments and complex nesting. **JSON Advantage:** Ubiquity/Parsing speed. **YAML Advantage:** Readability/Configuration friendliness.

**D11 — Easy:** **REST** is an architectural style for network APIs. 
- **GET:** Retrieve data.
- **POST:** Create new resource.
- **PUT:** Update/Replace resource.
- **DELETE:** Remove resource.

**D12 — Easy:** **Version pinning** is specifying an exact version of a dependency (e.g., `1.4.2` instead of `^1.4.0`). It ensures **reproducible builds**, preventing a new dependency release from breaking the application unexpectedly.

**D13 — Easy:** **Compiled** languages are translated to machine code before execution (C++, Rust). **Interpreted** languages are read and executed by a runtime (Python, JavaScript).

**D14 — Medium:** A **forward proxy** handles requests from clients to the internet. A **reverse proxy** handles requests from the internet to internal servers. 
- **Nginx:** Used for Load Balancing/SSL termination.
- **HAProxy:** Used for high-performance TCP/HTTP load balancing.

**D15 — Medium:** A **deadlock** is a state where two or more threads are blocked forever, each waiting for the other to release a resource. **Coffman Conditions:** 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** **Eventual Consistency** means that if no new updates are made, all replicas will eventually converge to the same value. **Cassandra** handles this via **Tunable Consistency**: `ONE` (fastest, low consistency), `QUORUM` (majority of nodes must agree), `ALL` (strongest consistency, slowest).

**D17 — Hard:** **mTLS** requires both client and server to present certificates. **Handshake:** Server sends cert $\rightarrow$ Client verifies server cert $\rightarrow$ Client sends its own cert $\rightarrow$ Server verifies client cert $\rightarrow$ Both derive a session key. Commonly used in **Service Meshes** (e.g., Istio) for zero-trust security.

**D18 — Hard:** A **hash table** uses a hash function to map keys to array indices. 
- **Collision Resolution:** **Chaining** (linked lists at each index) or **Open Addressing** (finding the next empty slot).
- **Complexity:** Average: $O(1)$ for insert/lookup/delete. Worst: $O(n)$ (if all keys hash to the same bucket).

**D19 — Hard:** A **Circuit Breaker** prevents a failing service from crashing the whole system. 
- **Closed:** Normal operation; requests pass.
- **Open:** Failure threshold reached; requests fail immediately.
- **Half-Open:** Periodically tests if the service has recovered.
It prevents cascade failures. **Exponential backoff** complements this by increasing the wait time between retries to avoid overwhelming the recovering service.

**D20 — Hard:** **Optimistic:** Assumes no conflict; checks for changes (e.g., via version numbers) at commit time. Use for low-contention data. **Pessimistic:** Locks the resource immediately. Use for high-contention data. 
- **Example:** Optimistic uses **MVCC/Row Versioning**; Pessimistic uses `SELECT ... FOR UPDATE` to lock a row.
