## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry run that compares the current state against the configuration and shows what changes will be made. `tofu apply` actually executes those changes to reach the desired state.

**T2 — Easy:** State is a JSON file mapping your configuration to real-world resource IDs. Remote state (e.g., in S3) is critical for team collaboration, as it provides a single source of truth and prevents multiple users from modifying the same infrastructure simultaneously.

**T3 — Medium:** `count` creates resources based on an integer index (list). `for_each` creates resources based on a map or set of keys. `for_each` is preferred because removing an item from the middle of a `count` list causes OpenTofu to shift indices, potentially leading to the destruction and recreation of unrelated resources.

**T4 — Medium:** This is called "drift." OpenTofu detects this during the `plan` phase by refreshing the state against the actual cloud API. It will show that the resource has drifted and will propose a change to revert the manual modification back to the configuration's defined state.

**T5 — Medium:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6 — Hard:** `terraform_remote_state` reads the state file of a completely separate project. Output values are for the current module's consumers. The recommended alternative is to use a shared "Data" module or a dedicated state-sharing backend (like a Key-Value store or a specialized API) to avoid tight coupling between different state files.

**T7 — Hard:** This happens because `null_resource` provisioners run *during* the apply phase, but outputs are evaluated *after* the resource is created. If the output depends on a value generated by the `remote-exec` script, that value isn't available until the script finishes. **Fix:** Use a `local-file` resource to write the kubeconfig to disk, and have the output reference that file, or use a dedicated provider (like the Kubernetes provider) instead of a `null_resource`.

**T8 — Medium:** `tofu import` brings existing cloud resources into the state file. Limitation: You must manually write the HCL code to match the resource. The `import` block (1.5+) allows you to define the import declaratively in code, and OpenTofu can automatically generate the corresponding HCL configuration.

**T9 — Easy:** A variable (input) is a parameter passed into the module (like a function argument). An output is a value returned by the module (like a function return value) for use by other modules or the user.

**T10 — Easy:** A provider is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS, Azure). If you run `plan` without `init`, OpenTofu will fail because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11 — Easy:** The `.terraform.lock.hcl` file records the exact versions and hashes of providers used. It should be committed to ensure that every team member and the CI/CD pipeline use the exact same provider versions, preventing "it works on my machine" bugs.

**T12 — Easy:** `tofu destroy` deletes all resources managed by the current state. To target a single resource: `tofu destroy -target=aws_instance.web[0]`.

**T13 — Easy:** A data source fetches information from an existing resource not managed by the current OpenTofu project. Example: Using `aws_ami` to find the latest official Ubuntu AMI ID instead of hardcoding it.

**T14 — Medium:** Variables are input parameters (external). Locals are internal constants or computed values. Use locals to avoid repeating the same complex expression multiple times within a module (DRY principle).

**T15 — Medium:** The `lifecycle` block modifies resource behavior:
- `create_before_destroy`: Creates the new resource before deleting the old one (prevents downtime).
- `prevent_destroy`: Errors out if a destroy action is attempted (safety for DBs).
- `ignore_changes`: Ignores specific attributes (e.g., ignore tags added by an external security scanner).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource has been renamed or moved to a different module. This allows the state to be updated without the resource being destroyed and recreated.

**T17 — Hard:** OpenTofu builds a Directed Acyclic Graph (DAG) to determine the order of operations. Implicit dependencies are created via references (e.g., `vpc_id = aws_vpc.main.id`). Explicit dependencies use `depends_on`. `depends_on` forces a strict order, which reduces parallelism and slows down the apply process; it should only be used when a dependency isn't detectable via references.

**T18 — Hard:** 
1. **State Splitting:** Break the monolith into smaller, independent state files (workspaces/modules) to reduce the graph size.
2. **Targeting:** Use `-target` for specific updates (though risky for long-term use).
3. **Refresh Optimization:** Use `-refresh=false` if you know the state is current.
4. **Provider Optimization:** Use more efficient providers or reduce the number of data source calls.

**T19 — Hard:** State locking prevents concurrent modifications. If a process crashes, the lock remains. You manually break it using `tofu force-unlock <lock-id>`. The risk is that if another process *is* actually running, you may cause state corruption by allowing two simultaneous writes.

**T20 — Hard:** 
1. Update the `backend` block in the HCL to point to S3 and DynamoDB.
2. Run `tofu init`. OpenTofu will detect the change and ask to migrate the state.
3. Confirm the migration. OpenTofu copies the local `terraform.tfstate` to S3.
4. Verify by running `tofu state list` to ensure all resources are present in the remote state.

## Ansible

**A1 — Easy:** A **task** is a single unit of work (e.g., install a package). A **playbook** is a YAML file containing one or more "plays" (mapping hosts to tasks). A **role** is a structured bundle of tasks, variables, files, and templates that can be reused across different playbooks.

**A2 — Easy:** `ansible_facts` is a dictionary containing system information gathered at the start of a play. Access the OS family via `ansible_facts['os_family']` (e.g., "Debian" or "RedHat").

**A3 — Medium:** 
- `command`: Safest; doesn't process shell variables or pipes.
- `shell`: Runs through `/bin/sh`, allowing pipes, redirects, and environment variables.
- `raw`: Bypasses Python entirely; used for devices without Python installed.

**A4 — Medium:** Idempotency means running the same task multiple times results in the same state without changing the system after the first run. 
- **Idempotent:** `apt: name=nginx state=present` (won't reinstall if already there).
- **NOT Idempotent:** `shell: echo "config" >> /etc/motd` (appends every time).

**A5 — Medium:**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'epel-release' }}"
  when: ansible_os_family == 'RedHat' # Simplified; usually requires two tasks or a loop.
# Better approach:
- name: Install htop
  package:
    name: htop
  when: ansible_os_family == 'Debian'
- name: Install EPEL and htop
  package:
    name: "{{ item }}"
  loop: ['epel-release', 'htop']
  when: ansible_os_family == 'RedHat'
```

**A6 — Hard:** (Lowest to Highest) Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ Playbook vars $\rightarrow$ Role vars $\rightarrow$ Extra vars (`-e`). `set_fact` creates a variable at runtime that generally overrides most other levels.

**A7 — Hard:** Use `serial: 3` in the play to process in batches. Use a separate group for the first 3 nodes. Use the `wait_for` module to ensure the RKE2 API port (6443) is open on the first 3 nodes before the remaining 47 nodes begin their tasks.

**A8 — Medium:** `ansible-vault` encrypts sensitive data. To encrypt a single variable, use `ansible-vault encrypt_string 'my_password'` and paste the resulting encrypted block directly into the YAML vars file.

**A9 — Easy:** An inventory is a list of managed nodes. **Static:** A hardcoded file (INI/YAML). **Dynamic:** A script or plugin that queries an API (e.g., AWS EC2) to generate the host list in real-time.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A handler is a task that only runs if "notified" by another task that reported a "changed" status. Trigger it using the `notify: handler_name` keyword in a task.

**A12 — Easy:** `ansible.cfg` defines global settings. Common settings: `inventory` (path to hosts file), `remote_user` (default SSH user), and `forks` (parallelism).

**A13 — Easy:** `register` captures the output of a task into a variable. 
Example: 
```yaml
- shell: uptime
  register: uptime_result
- debug: msg="{{ uptime_result.stdout }}"
```

**A14 — Medium:** `import_tasks` is static (processed at parse time); `include_tasks` is dynamic (processed at runtime). Use `include_tasks` when the task list depends on a variable evaluated during the play.

**A15 — Medium:** Ansible Galaxy is a community hub for roles/collections. Use a `requirements.yml` file listing the roles, then run `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:** Connection plugins determine how Ansible talks to the host.
- `ssh`: Standard for Linux/Unix.
- `local`: Runs tasks on the control node.
- `network_cli`: Specialized for network devices (switches/routers) that don't support full Python.

**A17 — Hard:** `delegate_to` runs a task on a different host than the current one. `run_once` ensures the task executes only once for the entire batch. 
*Example:* Use `run_once: true` and `delegate_to: localhost` to update a DNS record on a local API server using the IP of the first host in the group.

**A18 — Hard:** 
1. **Forks:** Increase `forks` in `ansible.cfg` to process more hosts in parallel.
2. **Pipelining:** Enable `pipelining = True` to reduce SSH operations.
3. **Fact Caching:** Use Redis or JSON files to cache `ansible_facts` so they aren't gathered every run.
4. **Mitogen:** Use the Mitogen plugin to replace the SSH execution engine for massive speed gains.

**A19 — Hard:** 
- `{{ }}`: Variable interpolation.
- `{% %}`: Control logic (loops/conditionals).
- `{# #}`: Comments.
```jinja2
upstream backend_servers {
{% for server in backend_servers %}
  # Health check enabled for {{ server }}
  server {{ server }}:8080;
{% endfor %}
}
```

**A20 — Hard:** 
1. Set `serial: 25%` (or a specific number) to update in batches.
2. **Pre-task:** Use `uri` module to check health of the node.
3. **Task:** Deploy app $\rightarrow$ use `uri` to verify the new version is healthy.
4. **LB Integration:** Use `delegate_to: lb_host` to remove the node from the load balancer before updating and re-add it after.
5. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, trigger a task to revert the app version and notify the team.
