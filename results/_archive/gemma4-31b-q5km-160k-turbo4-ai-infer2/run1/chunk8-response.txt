## Cloud Infrastructure Architecture

**CL1**
*   **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and software. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing the underlying OS. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Fully managed software delivered via web/API. *Example: Microsoft 365.*

**CL2**
*   **IaaS VMs:** Provider manages hardware/hypervisor; you manage OS, patching, and apps.
*   **Managed Kubernetes (EKS/GKE):** Provider manages the Control Plane; you manage worker node configuration and the pods.
*   **SaaS (M365):** Provider manages everything; you manage data, users, and configuration settings.

**CL3**
*   **VPC:** An isolated virtual network.
*   **Subnet:** A range of IP addresses in a VPC.
*   **Security Group (SG):** Instance-level firewall (Stateful: if request is allowed in, response is automatically allowed out).
*   **NACL:** Subnet-level firewall (Stateless: must explicitly define both inbound and outbound rules).
*   **Layering:** VPC $\rightarrow$ Subnet $\rightarrow$ SG. Traffic hits NACL first, then the SG.

**CL4**
*   **Landing Zone:** A pre-configured multi-account environment with baseline security/governance.
*   **OUs:** Logical groupings of accounts for policy application.
*   **Guardrails:** Service Control Policies (SCPs) that set maximum permission boundaries.
*   **Shared Networking:** Hub-and-Spoke (Central VPC for egress/firewalls) using Transit Gateway (AWS) or Virtual WAN (Azure).
*   **Centralized Logging:** Aggregating logs (CloudTrail/Activity Logs) into a dedicated security account.
*   **Single-account problem:** Blast radius (one compromise affects all), billing complexity, and quota limits.

**CL5**
*   **Terraform/OpenTofu:** Provider-agnostic, HCL-based. Best for multi-cloud.
*   **Pulumi:** Uses general-purpose languages (TS, Python). Best for developers who want loops/logic.
*   **CloudFormation/Bicep:** Cloud-native (AWS/Azure). Best for deep integration and "day zero" feature support.
*   **Crossplane:** K8s-native (CRDs). Best for managing infra as K8s objects.

**CL6**
*   **HPA:** Scales pods based on CPU/RAM.
*   **VPA:** Adjusts pod resource requests/limits.
*   **Cluster Autoscaler:** Adds/removes nodes to the cluster.
*   **KEDA:** Event-driven scaling (e.g., scaling based on RabbitMQ queue length).
*   **KEDA vs HPA:** Use KEDA when scaling depends on external events rather than just resource consumption.

**CL7**
*   **RPO (Recovery Point Objective):** Max acceptable data loss. **RTO (Recovery Time Objective):** Max acceptable downtime.
*   **Active-Active:** Traffic split across regions; zero downtime, highest cost.
*   **Active-Passive:** Failover to secondary region; some downtime, lower cost.
*   **Replication:** Sync (no data loss, high latency) vs Async (potential data loss, low latency).
*   **DR Types:**
    *   *Pilot Light:* DB is synced; apps are off.
    *   *Warm Standby:* Scaled-down version of app is always running.
    *   *Multi-site Active-Active:* Full capacity in both regions.

**CL8**
*   **GitOps:** Git is the single source of truth. A controller (ArgoCD/Flux) synchronizes the cluster state to match Git.
*   **ArgoCD vs FluxCD:** ArgoCD provides a rich UI; Flux is more lightweight/CLI-driven.
*   **Secrets:** Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault.
*   **Drift:** The controller detects the manual change and automatically overwrites it to match the Git state.

**CL9**
*   **StatefulSet:** Ensures stable network IDs and ordered deployment.
*   **PV/PVC:** Use a `local-storage` storage class for low latency.
*   **Headless Service:** Provides DNS for individual pods (pod-0, pod-1).
*   **Init Containers:** Handle filesystem setup or config downloads before the app starts.
*   **ConfigMaps:** Mounted as volumes to specific paths.
*   **PDB:** Ensures a minimum number of pods remain available during maintenance.

**CL10**
*   **Service Account:** Identity for a pod within K8s.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Why avoid credentials in pods:** Static keys are easily leaked and hard to rotate.
*   **Solution:** Workload Identity provides short-lived, automatically rotated tokens.

**CL11**
*   **Object (S3):** Unstructured data, highly durable, accessed via API. Use for backups/images.
*   **Block (EBS):** Low-latency, attached to one VM. Use for OS disks/Databases.
*   **File (EFS):** Shared filesystem (NFS/SMB). Use for shared content across multiple pods.

**CL12**
*   **Zero Trust:** "Never trust, always verify."
*   **Components:** NetworkPolicies (L3/4 isolation), Service Mesh (mTLS for L7 encryption/auth), OPA/Kyverno (Policy enforcement), Falco (Runtime anomaly detection).
*   **Difference:** Traditional security relies on a "hard shell" (firewall); Zero Trust assumes the network is already compromised and verifies every request.

**CL13**
*   **CDN:** A distributed network of edge servers that cache content closer to the user.
*   **Services:** CloudFront (AWS), Akamai.
*   **Use case:** Use a CDN for static assets (JS, CSS, Images) to reduce latency and origin server load.

**CL14**
*   **Region:** A geographic area (e.g., us-east-1).
*   **AZ:** One or more isolated data centers within a region.
*   **Multi-AZ:** Protects against a single DC failure.
*   **Zonal vs Regional:** Zonal resources (e.g., EBS) exist in one AZ; Regional resources (e.g., S3, Lambda) are replicated across AZs.

**CL15**
*   **Managed DB:** A database where the provider manages the underlying VM and DB engine.
*   **Provider handles:** OS patching, hardware failure, automated backups, and high availability (failover).
*   **User handles:** Schema design, query optimization, and access control.

**CL16**
*   **IAM Users:** Permanent identities for people.
*   **Groups:** Collections of users.
*   **Roles:** Temporary identities assumed by users or services.
*   **Policies:** JSON documents defining "Who can do what."
*   **Least Privilege:** Granting only the minimum permissions required to perform a task.

**CL17**
*   **Serverless:** Event-driven compute where the provider manages all scaling and allocation.
*   **Cold Start:** Latency when a function is invoked after being idle (provider must spin up a container).
*   **Poor fit:** Long-running processes, predictable high-constant load, or apps requiring specialized OS kernels.

**CL18**
*   **Ingress:** L7 routing (Host/Path).
*   **Gateway API:** Modern, role-based evolution of Ingress (more flexible).
*   **LB Annotations:** Cloud-specific tweaks (e.g., AWS ALB settings).
*   **TLS Termination:** Can happen at the Load Balancer (Edge) or at the Pod (End-to-End).
*   **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-team management, and advanced traffic splitting.

**CL19**
*   **Savings:** Reserved Instances (1-3 yr commitment), Savings Plans (flexible spend), Spot (up to 90% off, can be reclaimed).
*   **Optimization:** Right-sizing (downsizing over-provisioned VMs), S3 Intelligent-Tiering (auto-moves old data to cheaper tiers).
*   **FinOps:** Implementing a culture of cost accountability.
*   **Visibility:** Tagging resources by team/project and using Cost Explorer/Azure Cost Management for chargeback.

**CL20**
*   **Strategy:** Use Kubernetes as the common runtime abstraction. Use Terraform for consistent IaC.
*   **Networking:** Site-to-Site VPN or DirectConnect/ExpressRoute.
*   **Identity:** Use OIDC/SAML federation.
*   **Trade-offs:** Multi-cloud increases operational complexity and cost.
*   **Justification:** Justified for regulatory requirements (sovereignty) or extreme risk mitigation. Unnecessary for most mid-size companies.

## OT Infrastructure Architecture

**OT1**
*   **Purdue Model:** A framework for segmenting ICS networks.
*   **Level 0:** Physical Process (Sensors/Actuators).
*   **Level 1:** Basic Control (PLCs/PACs).
*   **Level 2:** Area Supervisory Control (HMIs/SCADA).
*   **Level 3:** Site-wide Operations (Historians/Site Management).

**OT2**
*   **IT vs OT:** IT prioritizes Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability. OT prioritizes Availability $\rightarrow$ Integrity $\rightarrow$ Confidentiality (Safety first).
*   **Patching:** OT systems cannot be patched like IT because downtime can cause physical danger or production loss; patches require rigorous testing in a staging environment.

**OT3**
*   **IDMZ:** A buffer zone between IT (L4) and OT (L3).
*   **Traffic:** Only specific, proxied traffic (e.g., Historian replication) should cross.
*   **Danger:** Direct L4 $\rightarrow$ L1 connectivity allows a compromised corporate laptop to directly send "Stop" commands to a PLC, potentially causing physical catastrophe.

**OT4**
*   **Modbus TCP:** L1/L2 (Simple, no security).
*   **OPC UA:** L2/L3 (Secure, object-oriented).
*   **EtherNet/IP:** L1/L2 (Common in Rockwell/Allen-Bradley).
*   **PROFINET:** L1/L2 (Common in Siemens).
*   **MQTT:** L3/Cloud (Lightweight, pub/sub).

**OT5**
*   **Data Diode:** Hardware that physically allows data to flow in only one direction (optical).
*   **Firewall:** Software-based rules (can be misconfigured or bypassed).
*   **Use Case:** Use a diode to send data from OT to IT without any possibility of a return path (absolute isolation).

**OT6**
*   **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Plant Historian $\rightarrow$ Edge Gateway (Protocol conversion) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Boundaries:** Firewall between L3 and IDMZ; Firewall between IDMZ and L4.

**OT7**
*   **Zone:** A grouping of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Design:**
    *   Zone 1: SIS (Isolated).
    *   Zone 2: PLCs/Control.
    *   Zone 3: SCADA/Historian.
    *   Zone 4: Engineering Workstations.
    *   Zone 5: Corporate IT.
    *   Conduits: Strictly controlled via firewalls.

**OT8**
*   **Strategy:** Implement VLANs per production line.
*   **Architecture:** L3 Switch $\rightarrow$ Industrial Firewalls $\rightarrow$ L2 Access Switches.
*   **Remote Access:** VPN $\rightarrow$ MFA $\rightarrow$ Jump Host in IDMZ.
*   **Transition:** Build the new segmented network in parallel, migrate one line at a time during planned maintenance windows.

**OT9**
*   **BPCS:** Manages the normal process.
*   **SIS:** A separate system that triggers a safe shutdown if the BPCS fails.
*   **IEC 61511:** The standard for functional safety of SIS.
*   **Isolation:** SIS must be isolated so a failure/attack on the BPCS doesn't disable the safety system.
*   **Ransomware:** If SIS is hit, the plant loses its "safety net," requiring an immediate manual emergency shutdown.

**OT10**
*   **PLC:** Small, fast, handles specific logic (e.g., a conveyor belt).
*   **DCS:** Integrated system for complex, large-scale processes (e.g., oil refinery).
*   **SCADA:** Supervisory system for wide-area assets (e.g., water pipelines).
*   **Coexistence:** Yes, SCADA often supervises multiple PLCs and DCS controllers.

**OT11**
*   **Architecture:** Corporate $\rightarrow$ VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (IDMZ) $\rightarrow$ OT Asset.
*   **Controls:** Session recording (audit trail) and time-limited access.
*   **RDP Danger:** Direct RDP allows lateral movement; if the corporate network is breached, the attacker has a direct path to the HMI.

**OT12**
*   **Detection:** Deploy passive IDS (e.g., Dragos, Nozomi) to detect anomalous PLC traffic.
*   **Response:** Isolate the L3 network from L4; keep L1/L2 running.
*   **Coordination:** IT handles the network; the Plant Operator decides if the process is safe to continue.
*   **Operator Role:** The operator is the final authority on whether to shut down the physical process.

**OT13**
*   **HMI:** A screen providing a visual interface for operators to monitor/control the process.
*   **Difference:** HMI is for *operation*; an Engineering Workstation is for *programming/configuring* the PLCs.

**OT14**
*   **Historian:** A time-series database for process data.
*   **Plant Historian (L3):** High-resolution, real-time data for local operations.
*   **Enterprise Historian (L4):** Aggregated, lower-resolution data for business reporting.

**OT15**
*   **Ladder Logic:** A graphical language mimicking electrical relay circuits.
*   **Execution:** Executed by PLCs.
*   **Dominance:** It is intuitive for electricians/technicians who are not software engineers.

**OT16**
*   **RTU:** Remote Terminal Unit; designed for wide-area, low-power, often wireless telemetry.
*   **PLC:** Designed for high-speed, local control.
*   **Environment:** RTUs are used in pipelines, water grids, and remote substations.

**OT17**
*   **Analog:** Continuous signal (e.g., 4-20mA).
*   **Digital:** Binary (On/Off).
*   **4-20mA:** Preferred because 0mA indicates a "wire break" (fault), whereas 4mA indicates a valid "zero" reading.

**OT18**
*   **Asset Inventory:** Knowing exactly what is on the network (Vendor, Firmware, IP).
*   **Techniques:** Passive (SPAN/Mirror ports) or Active (Polling).
*   **Danger:** Active scanning (e.g., Nmap) can crash old PLCs by sending unexpected packets to fragile network stacks.

**OT19**
*   **MITRE ATT&CK for ICS:** Focuses on physical impact.
*   **Tactics:**
    1.  *Initial Access:* Valid Accounts.
    2.  *Inhibit Response Function:* Disabling alarms.
    3.  *Impair Process Control:* Modifying PLC logic.
    4.  *Persistence:* Creating backdoor accounts.
    5.  *Discovery:* Scanning for Modbus devices.
*   **Difference:** Enterprise focuses on data theft; ICS focuses on process disruption/physical damage.

**OT20**
*   **Collection:** Use passive TAPs/SPAN ports to send traffic to an OT-IDS $\rightarrow$ SIEM.
*   **Staffing:** IT analysts handle the SIEM; OT engineers validate if the alert is a real process anomaly or a cyber attack.
*   **Firmware Alert:**
    1.  Verify with the plant operator (was this a scheduled change?).
    2.  If unauthorized, isolate the PLC.
    3.  Perform a forensic dump of the PLC logic to compare against the known-good baseline.
