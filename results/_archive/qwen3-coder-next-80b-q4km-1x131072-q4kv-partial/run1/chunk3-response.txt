## **OpenTofu / Terraform (20 questions)**

**T1 — Easy:**  
`tofu plan` generates and displays an execution plan (what changes will be made) without applying them. `tofu apply` executes the plan — creating, updating, or destroying resources — and writes the new state. Plan is read-only; apply is destructive (unless `-refresh-only` or `-destroy` flags are used).

**T2 — Easy:**  
State is the JSON file (`terraform.tfstate`) that stores the current state of managed infrastructure (resource IDs, attributes, metadata). Remote state (e.g., S3 + DynamoDB) enables team collaboration, state locking, and secure access control. Local state is file-based and not shared — risky for teams.

**T3 — Medium:**  
`count` creates multiple *identical* resources using an integer (e.g., `count = 3`). `for_each` creates resources from a map or set, allowing unique per-resource configuration (e.g., `for_each = toset(["web1", "web2"])`). `for_each` is preferred when resources need distinct names/IDs or when the collection is dynamic (e.g., derived from data sources).

**T4 — Medium:**  
OpenTofu detects drift via `tofu plan` (compares state vs. real-world state via provider API calls). If mismatched, it proposes changes to reconcile (e.g., recreate or update). On `apply`, it applies the plan. Manual changes outside OpenTofu cause drift — plan will show corrective actions.

**T5 — Medium:**  
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])

  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = {
    Name = each.key
  }
}
```

**T6 — Hard:**  
`terraform_remote_state` data source reads *entire* state from another module/backend — but it’s static and doesn’t support module outputs directly. Outputs in the source module are only exposed if explicitly exported via `terraform_remote_state`.  
**Recommended alternative**: Use module outputs directly (e.g., `module.vpc.vpc_id`) — this enforces explicit interfaces, enables validation, and supports dependency tracking. Avoid `terraform_remote_state` for cross-module data sharing.

**T7 — Hard:**  
The `null_resource` with `remote-exec` provisioner runs *after* the resource is created, but its output is only available *after* the provisioner succeeds. However, the kubeconfig output is declared *before* the provisioner completes — so on first apply, the output is empty or undefined.  
**Fix**: Use `triggers` in `null_resource` to ensure it only runs when needed, and add a `depends_on` in dependent resources to the `null_resource`. Better: Use a data source (e.g., `aws_ssm_parameter`) to fetch kubeconfig *after* cluster is ready, or use `local-exec` with retry logic.

**T8 — Medium:**  
`tofu import` imports existing infrastructure into state (e.g., `tofu import aws_instance.web i-12345`). Limitations:  
- Only imports state — no config is generated.  
- Requires manual config writing.  
- Fails if resource type or ID is invalid.  
The `import` block (v1.5+) allows declarative import in config (e.g., `import { to = aws_instance.web id = "i-12345" }`). Improvements:  
- Integrated into plan/apply.  
- Supports `for_each`, `count`, and `depends_on`.  
- Enables version-controlled import definitions.

**T9 — Easy:**  
A `variable` defines an input parameter (like a function argument). An `output` exposes values from the module (like a return value). Variables are *inputs* to the module; outputs are *exports*.

**T10 — Easy:**  
A `provider` configures a cloud/API (e.g., `aws`, `azurerm`) — defines credentials, region, etc. Running `tofu plan` without `tofu init` fails: `init` downloads providers, initializes backends, and sets up the working directory. Plan requires initialized state.

**T11 — Easy:**  
`.terraform.lock.hcl` records exact provider versions used (via `required_providers`). Committing it ensures reproducible builds across environments and CI/CD. Prevents accidental provider upgrades.

**T12 — Easy:**  
`tofu destroy` destroys *all* resources in the state. To target a single resource: `tofu destroy -target=aws_instance.web`. Use with caution — bypasses dependency ordering.

**T13 — Easy:**  
A `data` source reads existing infrastructure (read-only). Use when you need to reference external or pre-existing resources (e.g., `data "aws_ami" "ubuntu"` to find the latest Ubuntu AMI) instead of creating new ones.

**T14 — Medium:**  
`variable` defines *external* inputs (from CLI, env, or `.tfvars`). `locals` define *internal* computed values (e.g., `locals { full_name = "${var.first}-${var.last}" }`). Use `locals` for DRY, reusable expressions — avoid polluting the module interface.

**T15 — Medium:**  
`lifecycle` block modifies resource behavior:  
- `create_before_destroy = true`: Create new before destroying old (e.g., for load-balanced services).  
- `prevent_destroy = true`: Block accidental deletion (e.g., for critical DBs).  
- `ignore_changes = [...]`: Ignore changes to specific attributes (e.g., `ignore_changes = [tags["LastModified"]]` to avoid constant diffs).

**T16 — Medium:**  
`moved` block renames or relocates resources/modules in state *without* recreating them (e.g., `moved { from = aws_instance.old to = aws_instance.new }`). Prevents `destroy + recreate` during refactoring.

**T17 — Hard:**  
OpenTofu builds a dependency graph to determine resource order.  
- *Implicit*: Dependencies inferred from references (e.g., `ami = data.aws_ami.id`).  
- *Explicit*: `depends_on` forces ordering (e.g., `depends_on = aws_s3_bucket.logs`).  
`depends_on` can reduce parallelism — only use when needed (e.g., for side effects like waiting for a service). Overuse slows plans/applies.

**T18 — Hard:**  
Strategies to reduce plan time:  
1. **State sharding**: Split state (e.g., per environment/team) — tradeoff: harder to cross-resource references.  
2. **Use `-parallelism=10` (lower than default)** — tradeoff: slower apply, but less API throttling.  
3. **Enable state caching** (e.g., `TF_STATE_CACHE_DIR`) — tradeoff: stale state if not synced.  
4. **Use `tofu plan -detailed-exitcode` + skip unnecessary modules** — tradeoff: manual orchestration.  
Bonus: Use `tofu validate` in CI instead of full plan; upgrade to latest OpenTofu (performance improvements).

**T19 — Hard:**  
State locking (e.g., DynamoDB) prevents concurrent `apply`s. If a lock isn’t released (e.g., crash), the lock remains until timeout (default: 2 mins for DynamoDB). To manually break:  
- `tofu force-unlock <LOCK_ID>` (requires lock ID from error).  
**Risks**: If another process is still running, force-unlock may cause state corruption or partial updates.

**T20 — Hard:**  
Steps to migrate local state to S3 + DynamoDB:  
1. Create S3 bucket (versioned) and DynamoDB table (for locking).  
2. Add backend config to `backend.tf`:  
   ```hcl
   terraform {
     backend "s3" {
       bucket         = "my-tf-state"
       key            = "prod/terraform.tfstate"
       region         = "us-east-1"
       dynamodb_table = "my-terraform-lock"
     }
   }
   ```  
3. Run `tofu init -migrate-state` — prompts to copy local state to S3.  
4. Verify: `tofu state list` shows resources; check S3 bucket for state file.  
5. Confirm lock table works: `tofu apply -lock-timeout=10s` (should succeed).  
**Note**: Backup state before migration.

## **Ansible (20 questions)**

**A1 — Easy:**  
- **Task**: Single action (e.g., `copy`, `service`).  
- **Playbook**: Sequence of plays (tasks + hosts + vars).  
- **Role**: Reusable, structured collection of tasks, handlers, vars, templates (in `tasks/`, `handlers/`, etc.).

**A2 — Easy:**  
`ansible_facts` is a dict of auto-discovered host info (OS, IP, etc.). Access OS family via `ansible_os_family` (e.g., `"Debian"` or `"RedHat"`).

**A3 — Medium:**  
- `command`: Runs a binary *without* shell (no pipes, `|`, `&&`). Safer.  
- `shell`: Runs via `/bin/sh` — supports shell features.  
- `raw`: Bypasses module subsystem (no Python needed) — for very old hosts or `chroot`.  
Use `command` by default; `shell` for shell features; `raw` only when needed (e.g., bootstrapping Python).

**A4 — Medium:**  
Idempotency: Running a task multiple times yields same result.  
- **Idempotent**: `apt: name=htop state=present` — installs only if missing.  
- **Not idempotent**: `shell: echo "hello" > /tmp/file` — overwrites every time. Fix with `copy` or `lineinfile`.

**A5 — Medium:**  
```yaml
- name: Install htop (Debian) or epel-release + htop (RHEL)
  package:
    name: "{{ ['htop'] if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
```

**A6 — Hard:**  
Precedence (lowest → highest):  
1. `role_defaults`  
2. `group_vars/all`  
3. `host_vars/all`  
4. `inventory vars`  
5. `playbook vars`  
6. `set_fact` / `register`  
7. `include_vars`  
8. `set_stats`  
9. `extra_vars` (CLI `-e`) — *highest priority*  
Note: `host_vars` > `group_vars`; `extra_vars` > all.

**A7 — Hard:**  
Use `serial: "3"` in play to deploy first 3 nodes, then use `wait_for` to confirm they’re ready before proceeding. Example:  
```yaml
- hosts: rke2_agents
  serial: "3"
  tasks:
    - name: Deploy RKE2 agent
      include_role:
        name: deploy_rke2_agent
    - name: Wait for node to be ready
      uri:
        url: "https://{{ inventory_hostname }}:6443/healthz"
        status_code: 200
      register: health
      until: health.status == 200
      retries: 30
      delay: 10
```
Then use `serial: "100%"` for remaining nodes.

**A8 — Medium:**  
`ansible-vault` encrypts files/variables. To encrypt a *single variable* in a vars file:  
1. Use `ansible-vault encrypt_string 'mysecret' --name 'db_password'`  
2. Paste output into vars file:  
   ```yaml
   db_password: !vault |
     $ANSIBLE_VAULT;1.1;AES256...
   ```  
Only the value is encrypted — file remains readable.

**A9 — Easy:**  
Inventory defines hosts/groups.  
- **Static**: INI/YAML file (e.g., `/etc/ansible/hosts`).  
- **Dynamic**: Script/program that generates inventory at runtime (e.g., cloud plugins).

**A10 — Easy:**  
```bash
ansible webservers -m shell -a "df -h"
```

**A11 — Easy:**  
A **handler** is a task that only runs when notified (e.g., restart service on config change). Triggered via `notify: restart nginx`. Differs from regular tasks: handlers run once at end of play, only if notified.

**A12 — Easy:**  
`ansible.cfg` configures Ansible behavior. Common settings:  
- `forks = 10`  
- `host_key_checking = False`  
- `remote_user = admin`  
- `log_path = /var/log/ansible.log`

**A13 — Easy:**  
`register` captures task output into a variable. Example:  
```yaml
- shell: uptime
  register: uptime_result
- debug:
    msg: "Uptime: {{ uptime_result.stdout }}"
```

**A14 — Medium:**  
- `import_tasks`: Static — tasks are *inlined* at parse time (before play starts). Conditionals evaluated at parse time.  
- `include_tasks`: Dynamic — tasks loaded at runtime. Conditionals evaluated at runtime.  
Use `import_tasks` for static, reusable task lists; `include_tasks` for runtime decisions (e.g., `when`).

**A15 — Medium:**  
Ansible Galaxy is a hub for roles/collections. Use `requirements.yml`:  
```yaml
roles:
  - name: geerlingguy.docker
collections:
  - community.general
```  
Install with: `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:**  
Connection plugins define how Ansible connects to hosts:  
- `ssh`: Default — uses SSH.  
- `local`: Runs tasks on control node (e.g., `connection: local`).  
- `network_cli`: For network devices (e.g., Cisco) — uses CLI over SSH.  
Use `local` for localhost tasks; `network_cli` for network gear.

**A17 — Hard:**  
`delegate_to: localhost` runs task on control node. `run_once: true` runs once per batch. Example:  
```yaml
- name: Get remote IP
  shell: hostname -I
  register: remote_ip
  delegate_to: "{{ inventory_hostname }}"

- name: Register IP on control node
  debug:
    msg: "Remote IP: {{ remote_ip.stdout }}"
  run_once: true
```

**A18 — Hard:**  
Strategies to improve performance:  
1. **Increase `forks`** — parallelize hosts. Tradeoff: API throttling.  
2. **Enable `pipelining = True`** — reduces SSH ops. Tradeoff: requires `requiretty` disabled on target.  
3. **Cache facts** (`fact_caching = jsonfile`, `fact_caching_connection = /tmp/ansible_facts`) — avoids re-gathering. Tradeoff: stale facts if host changes.  
4. **Use Mitogen** (`strategy = mitogen_linear`) — speeds SSH. Tradeoff: adds dependency, may break some modules.

**A19 — Hard:**  
- `{{ }}`: Expression output (e.g., `{{ var }}`).  
- `{% %}`: Control structures (e.g., `{% for %}`, `{% if %}`).  
- `{# #}`: Comments (ignored).  
**Template snippet**:  
```nginx
upstream backend {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; {# health check: /health #}
{% endfor %}
}
```

**A20 — Hard:**  
Rolling deployment with load balancer integration:  
```yaml
- hosts: webservers
  serial: "20%"  # 4 servers per batch
  pre_tasks:
    - name: Remove from load balancer
      uri:
        url: "http://lb/api/deregister?host={{ inventory_hostname }}"
        method: POST
      delegate_to: localhost

  tasks:
    - name: Deploy app
      copy:
        src: app.tar.gz
        dest: /opt/app/
      notify: restart app

  post_tasks:
    - name: Wait for app health
      uri:
        url: "http://localhost:8080/health"
        status_code: 200
      register: health
      until: health.status == 200
      retries: 10
      delay: 5

    - name: Re-add to load balancer
      uri:
        url: "http://lb/api/register?host={{ inventory_hostname }}"
        method: POST
      delegate_to: localhost

  handlers:
    - name: restart app
      systemd:
        name: myapp
        state: restarted

  rescue:
    - name: Rollback on failure
      debug:
        msg: "Rolling back {{ inventory_hostname }}..."
      run_once: true
    - name: Re-add to LB (rollback)
      uri:
        url: "http://lb/api/register?host={{ inventory_hostname }}"
        method: POST
      delegate_to: localhost
      run_once: true
```
