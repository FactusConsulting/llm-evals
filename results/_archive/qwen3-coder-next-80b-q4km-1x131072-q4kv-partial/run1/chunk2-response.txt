N1 — K1 — Easy:  
**Deployment** manages stateless pods with identical replicas, supports rolling updates, and does not guarantee pod identity or stable network identifiers. **StatefulSet** manages stateful applications, provides stable, unique network identities (e.g., `pod-0`, `pod-1`), ordered, graceful scaling and deletion, and persistent storage per pod (via PVCs). StatefulSets are used for databases, consensus systems, etc.

N2 — K2 — Easy:  
A **ClusterIP Service** exposes the app internally using a virtual IP (ClusterIP) assigned by Kubernetes. Traffic is routed via **kube-proxy**, which uses iptables (or IPVS) rules to load-balance requests across matching pod IPs (from Endpoints). No direct pod IP exposure; traffic is NAT’d.

N3 — K3 — Medium:  
- **PersistentVolume (PV)**: Cluster-wide storage resource (e.g., NFS, EBS), provisioned by admin.  
- **PersistentVolumeClaim (PVC)**: Request for storage by a user/pod; binds to a matching PV.  
- **StorageClass**: Defines *classes* of storage (e.g., fast SSD vs. HDD), enables dynamic provisioning.  
**Relationship**: PVCs request storage of a specific StorageClass; if `storageClassName` is set and no PV exists, the provisioner (e.g., CSI driver) creates a PV dynamically. PVC binds to PV with matching access modes and capacity.

N4 — K4 — Medium:  
Troubleshooting CrashLoopBackOff:  
1. `kubectl logs <pod>` — check app logs for errors.  
2. `kubectl describe pod <pod>` — inspect events, restart counts, exit codes.  
3. Check container exit code: `kubectl get pod -o jsonpath='{.status.containerStatuses[0].state.waiting.reason}'`.  
4. Verify resource limits (OOMKilled? `kubectl describe node`).  
5. Validate config (e.g., missing env vars, invalid configmaps/secrets).  
6. Try running container locally with same args/config.

N5 — K5 — Medium:  
**CoreDNS** provides DNS resolution for services and pods within the cluster (e.g., `service.namespace.svc.cluster.local`). Pods query CoreDNS for service discovery.  
If CoreDNS pods are down:  
- Service DNS lookups fail → pods cannot resolve services → apps fail to connect.  
- External DNS may still work if `/etc/resolv.conf` points to upstream DNS (but internal resolution breaks).

N6 — K6 — Hard:  
Scheduler uses a **two-phase** process:  
1. **Filtering (Predicates)**: Eliminate nodes that don’t meet requirements (e.g., resource不足, node affinity/anti-affinity, taints/tolerations, volume constraints).  
2. **Scoring (Priorities)**: Rank remaining nodes using weights and functions.  
**Factors considered**:  
- Resource fit (CPU/memory requests vs. available)  
- Pod affinity/anti-affinity (e.g., co-locate with other pods or avoid)  
- Topology spread (e.g., spread across zones/hosts)  
- Inter-pod affinity (e.g., same node for low-latency)  
- Minimum available replicas for topology-aware scheduling.

N7 — K7 — Hard:  
- **Scheduling**: Kubernetes only considers *requests* (not limits) for scheduling. Node has 4GB total, 3.5GB requested → 0.5GB free. Pod requests 256Mi → fits (256Mi < 512Mi free). ✅ Scheduled.  
- **Runtime**: If pod uses 600Mi > limit (512Mi), OOMKilled by kernel → pod restarts (CrashLoopBackOff likely). Limits enforce hard memory cap.

N8 — K8 — Hard:  
Request flow:  
1. External client → **Cloud LB** (e.g., AWS ELB) → routes to ingress controller’s NodePort/LoadBalancer Service.  
2. **NGINX Ingress Controller** (Deployment with Service of type LoadBalancer/NodePort) receives request, matches Ingress rule (host/path), forwards to backend **Service** (ClusterIP).  
3. **Service** uses kube-proxy (iptables/IPVS) to select an **Endpoint** (pod IP).  
4. kube-proxy NATs traffic to pod IP.  
5. Pod receives HTTP request.  
*Note*: TLS termination may happen at LB or Ingress controller (depending on config).

N9 — K9 — Medium:  
**NetworkPolicy**: Controls pod-to-pod and external traffic at L3/L4 (IP/port).  
- **Default (no policy)**: All ingress/egress allowed (open).  
- **Apply policy selecting pods**: Only traffic matching *ingress* and *egress* rules is allowed for those pods; others are denied.  
*Note*: Policies are additive; multiple policies can apply to same pod.

N10 — K10 — Medium:  
- **RollingUpdate**: Gradually replaces old pods with new ones (e.g., 25% max surge, 25% max unavailable). Minimizes downtime.  
- **Recreate**: Terminates all old pods *before* creating new ones → downtime.  
**Use Recreate** when:  
- Stateful apps that can’t run multiple versions simultaneously (e.g., DB migration).  
- Shared resources (e.g., single write endpoint).  
- Cost-sensitive (fewer pods running concurrently).

N11 — K11 — Easy:  
**Namespace**: Logical partition for resources (e.g., dev, prod). Enables multi-tenancy and resource quotas.  
**Default namespaces**:  
- `default`  
- `kube-system`  
- `kube-public`  
- `kube-node-lease` (K8s 1.13+)

N12 — K12 — Easy:  
`kubectl describe pod` shows detailed status:  
1. Events (e.g., `FailedScheduling`, `Pulling`, `Started`)  
2. Container statuses (ready, restart count, last state)  
3. Pod IP, node, QoS class  
4. Volumes, mounts, resource requests/limits  
5. Conditions (e.g., Ready, ContainersReady)  
`kubectl get pod` only shows name, ready, status, restarts, age.

N13 — K13 — Easy:  
**ConfigMap**: Stores non-sensitive config as key-value pairs.  
Pods can consume it via:  
1. **Environment variables**: `envFrom: configMapRef` or `valueFrom.configMapKeyRef`  
2. **Volume mount**: `volumes.configMap.name`, mounted as file (e.g., `/etc/config`)  
3. (Less common) Command/args substitution (via `$(VAR)` in container args).

N14 — K14 — Easy:  
- **ClusterIP**: Internal-only (cluster IP), default.  
- **NodePort**: Exposes on `<NodeIP>:<NodePort>` (30000–32767), external access via any node.  
- **LoadBalancer**: Provisions external LB (cloud provider), maps to NodePort + ClusterIP.

N15 — K15 — Easy:  
**DaemonSet**: Ensures *one pod per node* (e.g., logging, monitoring agents).  
Use instead of Deployment when:  
- Need node-local functionality (e.g., `fluentd`, `node-exporter`).  
- Pods must run on *all* or *selected* nodes (via node selector/tolerations).

N16 — K16 — Medium:  
**Taints**: Node-level labels that repel pods unless they have matching **tolerations**.  
**Tolerations**: Pod-level permission to schedule on tainted nodes.  
**vs. Node Affinity**:  
- Taints/tolerations = *prevent scheduling* (negative constraint).  
- Node affinity = *prefer scheduling* (positive constraint).  
**Use cases**:  
- Taint: Dedicate node for GPU workloads (`node.kubernetes.io/instance-type=gpu` + `NoSchedule`).  
- Node affinity: Prefer pods to run in same zone (`topologyKey: topology.kubernetes.io/zone`).

N17 — K17 — Medium:  
**Operator**: Custom controller + CRDs that encapsulates domain-specific knowledge to manage an app (e.g., etcd-operator, Prometheus Operator).  
**Differs from standard controller** (e.g., Deployment controller) by:  
- Managing *complex stateful apps* (backup, failover, upgrades).  
- Using application-aware logic (e.g., quorum checks).  
**Solves**: Manual ops (e.g., scaling DBs, rolling restarts), reduces toil, enables self-healing.

N18 — K18 — Hard:  
**etcd consistency**: Strong (linearizable) reads/writes via Raft consensus.  
**If quorum lost** (e.g., 2/3 down in 3-node cluster):  
- Cluster becomes *unavailable* for writes (and reads, unless read-quorum=false).  
- API server pods crash-loop (can’t reach etcd).  
**Recovery (2/3 lost)**:  
1. Stop API servers.  
2. On remaining node: `etcdctl snapshot restore` (if backup exists) OR manually rebuild cluster (see [etcd docs](https://etcd.io/docs/latest/op-guide/recovery/)).  
3. Best practice: Regular snapshots + disaster recovery plan.

N19 — K19 — Hard:  
**RBAC**: Role-based access control using:  
- **Role/ClusterRole**: Define permissions (rules: verbs + resources).  
- **RoleBinding/ClusterRoleBinding**: Bind role to users/groups/service accounts.  
**For read-only access to pods/logs in one namespace (`dev`)**:  
```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

N20 — K20 — Hard:  
**ndots** in `/etc/resolv.conf` (default: 5) tells resolver to try absolute query *first* if domain has ≥ ndots dots.  
**Problem**: For `www.google.com` (2 dots < 5), pod queries:  
1. `www.google.com.dev.svc.cluster.local`  
2. `www.google.com.svc.cluster.local`  
3. `www.google.com.cluster.local`  
4. `www.google.com` (finally external)  
→ 4+ queries → slow.  
**Fix**: Set `ndots: 1` in pod spec’s `dnsConfig`:  
```yaml
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "1"
```
Now `www.google.com` (1 dot) → absolute query first → 1 query.

D1 — Easy:  
**`git merge`**: Creates a merge commit combining histories (preserves branching structure).  
**`git rebase`**: Replays commits on top of target branch (linear history).  
**Avoid rebasing**: Public/shared branches (e.g., `main`) — rewrites history → conflicts for others. Use only on local/unpushed branches.

D2 — Easy:  
**TCP**: Connection-oriented, reliable, ordered, flow-controlled. Protocols: HTTP, SSH, SMTP.  
**UDP**: Connectionless, unreliable, no ordering, low overhead. Protocols: DNS, DHCP, VoIP (RTP).

D3 — Medium:  
**Race condition**: Incorrect behavior due to timing of concurrent access to shared resources.  
**Example (Python)**:  
```python
counter = 0
def increment():
    global counter
    for _ in range(100000):
        counter += 1  # Not atomic: read-modify-write
```
Two threads → final `counter < 200000` (lost updates).

D4 — Medium:  
**Symmetric encryption**: Same key for encrypt/decrypt (e.g., AES). Fast, but key distribution hard.  
**Asymmetric encryption**: Public/private key pair (e.g., RSA). Slow, but solves key exchange.  
**TLS uses both**:  
1. Asymmetric (RSA/ECDH) for key exchange (to agree on session key).  
2. Symmetric (AES-GCM) for bulk data encryption (faster).

D5 — Medium:  
**Container image layer**: Immutable filesystem diff (e.g., `RUN apt-get install`). Layers stack to form final image.  
**Layer caching**: Docker caches layers; if Dockerfile line changes, all subsequent layers rebuild.  
**Best practices**:  
- Place infrequent changes (e.g., `COPY .`) *after* frequent changes (e.g., `RUN pip install`).  
- Use `.dockerignore` to avoid unnecessary cache invalidation.

D6 — Medium:  
HTTP 503 (Service Unavailable) checks:  
1. Backend service health: `curl localhost:8080/health` on app pod.  
2. Load balancer/ingress config: misrouting? TLS errors?  
3. Resource exhaustion: CPU/memory pressure → OOM/restarts.  
4. Dependency failures: DB connection pool exhausted? Redis down?  
5. Circuit breaker open? (Check logs/metrics)  
6. DNS resolution issues (if external service).

D7 — Hard:  
**CAP theorem**: In distributed systems, can’t guarantee all three:  
- **C**onsistency (all nodes see same data)  
- **A**vailability (every request succeeds)  
- **P**artition tolerance (system works despite network failures)  
**CP example**: etcd, ZooKeeper — prioritize consistency (block reads during partition).  
**AP example**: DynamoDB, Cassandra (with eventual consistency) — return stale data during partition.

D8 — Medium:  
**Vertical scaling**: Add more power (CPU/RAM) to existing node. Limited by hardware.  
**Horizontal scaling**: Add more nodes (e.g., pods, servers).  
**Enabling patterns**:  
- Stateless services (no per-node state)  
- Load balancing (e.g., ingress, DNS round-robin)  
- Shared storage (e.g., S3, NFS)  
- Database sharding/replication.

D9 — Easy:  
**Environment variable**: Key-value pair affecting process behavior (e.g., `PATH`, `HOME`).  
**Persist on Linux**: Add to shell config (e.g., `echo 'export MY_VAR=value' >> ~/.bashrc`), then `source ~/.bashrc`.

D10 — Easy:  
**JSON**: Lightweight data interchange format (key-value, arrays).  
**YAML**: Human-readable superset of JSON (uses indentation, no quotes needed).  
**Advantages**:  
- JSON: Native in most languages, fast parsing.  
- YAML: More readable, supports comments (e.g., Kubernetes configs).

D11 — Easy:  
**REST API**: State transfer over HTTP, using resources (URLs) and methods.  
- **GET**: Retrieve resource (idempotent, safe).  
- **POST**: Create resource (non-idempotent).  
- **PUT**: Replace resource (idempotent).  
- **DELETE**: Remove resource (idempotent).

D12 — Easy:  
**Version pinning**: Lock dependencies to exact versions (e.g., `requests==2.28.1`).  
**Importance**: Ensures reproducible builds (no surprise upgrades), avoids breaking changes, aids debugging.

D13 — Easy:  
**Compiled language**: Source → machine code *before* runtime (e.g., C, Go, Rust).  
**Interpreted language**: Executed line-by-line by interpreter (e.g., Python, JavaScript, Ruby).  
*(Note: Modern languages often use hybrid models, e.g., Java → bytecode → JIT.)*

D14 — Medium:  
**Forward proxy**: Client → proxy → server (client configures proxy to hide identity).  
**Reverse proxy**: Client → proxy → server (server configures proxy to hide internal topology).  
**Examples**:  
- Forward: Squid (web caching), Tor.  
- Reverse: NGINX (load balancing), Cloudflare (DDoS protection).

D15 — Medium:  
**Deadlock**: Two or more processes wait indefinitely for resources held by each other.  
**Coffman conditions** (all must hold):  
1. Mutual exclusion  
2. Hold and wait  
3. No preemption  
4. Circular wait  
Prevention: Break one condition (e.g., resource ordering).

D16 — Hard:  
**Eventual consistency**: After updates, replicas converge to same state *eventually* (no guarantee on timing).  
**Cassandra**: Uses tunable consistency (e.g., `ONE`, `QUORUM`, `ALL`).  
- **Read-after-write**: Use consistency level ≥ write consistency (e.g., write `QUORUM`, read `QUORUM`).  
- **Tunable levels**:  
  - `ALL`: Strongest (all nodes)  
  - `QUORUM`: >50% nodes  
  - `ONE`: Fastest (one node)  
- Also uses **hinted handoff**, **read repair**.

D17 — Hard:  
**mTLS**: Mutual TLS — both client and server authenticate each other via certificates.  
**Handshake**:  
1. ClientHello → ServerHello (exchange randoms, cipher suites).  
2. Server sends cert + `CertificateVerify` (signs handshake).  
3. Client verifies server cert.  
4. Client sends cert + `CertificateVerify`.  
5. Server verifies client cert.  
6. Key exchange (e.g., ECDHE), then encrypted handshake.  
**Use cases**: Service-to-service auth (e.g., Istio mTLS), API gateways, database connections.

D18 — Hard:  
**Hash table**: Maps keys → indices via hash function.  
**Collision resolution**:  
- **Chaining**: Store colliding items in linked list/array at index.  
- **Open addressing**: Probe for next empty slot (linear/quadratic probing, double hashing).  
**Complexity**:  
- Average: O(1) insert/lookup/delete  
- Worst: O(n) (e.g., all keys hash to same index, or full table in open addressing).

D19 — Hard:  
**Circuit breaker**: Prevent cascade failures by failing fast when downstream service is unhealthy.  
**States**:  
- **Closed**: Normal operation; requests pass through.  
- **Open**: Failure threshold exceeded; requests fail immediately (no downstream call).  
- **Half-open**: Test if service recovered (allow limited requests).  
**Relation to retries**:  
- Circuit breaker *stops* retries when open.  
- Retry + exponential backoff used in *closed* state to handle transient failures.

D20 — Hard:  
**Pessimistic concurrency**: Assume conflicts → lock early (e.g., `SELECT FOR UPDATE`).  
**Optimistic concurrency**: Assume no conflict → check at commit (e.g., row versioning, `WHERE version = old_version`).  
**When to choose**:  
- Pessimistic: High contention, short transactions (e.g., inventory updates).  
- Optimistic: Low contention, long reads (e.g., user profiles).  
**Examples**:  
- Pessimistic: `BEGIN; SELECT * FROM accounts WHERE id=1 FOR UPDATE; UPDATE ...`  
- Optimistic: `UPDATE accounts SET balance=100 WHERE id=1 AND version=5;` (if 0 rows updated → retry).
