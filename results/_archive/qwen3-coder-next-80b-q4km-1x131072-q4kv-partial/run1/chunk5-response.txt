DN1 — Easy: What is the difference between class and struct in C#? When should you use a struct?  
**Answer**: Classes are reference types (allocated on heap, passed by reference); structs are value types (allocated on stack or inline in containing type, passed by copy). Structs are immutable by default (unless fields are mutable), have no inheritance (implicitly sealed), and derive from `ValueType`. Use structs for small, immutable, value-like data (e.g., `Point`, `Color`) where copying overhead is acceptable and identity isn’t important. Avoid structs for large data (>16 bytes), mutable types, or types requiring polymorphism.

DN2 — Easy: Explain the difference between IEnumerable<T> and IQueryable<T>. Why does this distinction matter for database queries?  
**Answer**: `IEnumerable<T>` executes queries *in-memory* (client-side), enumerating over an in-memory collection. `IQueryable<T>` represents a *query expression tree* that can be translated to another language (e.g., SQL) and executed *on the data source* (e.g., database). Using `IEnumerable<T>` on an EF Core `DbSet<T>` (which implements `IQueryable<T>`) forces client-side evaluation (e.g., `.Where(x => CustomMethod(x))`), causing performance issues. Always use `IQueryable<T>` for database queries until materialization (`.ToList()`, `.AsEnumerable()`).

DN3 — Medium: How does async/await work in C#? What is a Task vs a ValueTask? When should you use ValueTask?  
**Answer**: `async/await` is syntactic sugar over state machines that suspend/resume execution at `await` points without blocking threads. `Task` represents an asynchronous operation (often heap-allocated). `ValueTask` is a lightweight struct wrapper that can represent either a completed operation (with result) or a `Task`, avoiding heap allocation when the operation completes synchronously. Use `ValueTask` for high-frequency APIs (e.g., I/O, caching) where most calls complete synchronously. Avoid returning `ValueTask` from public APIs unless performance-critical, as it complicates reuse (e.g., `.ContinueWith()` doesn’t work directly).

DN4 — Medium: Explain dependency injection in .NET. What are the three service lifetimes (Transient, Scoped, Singleton), and what is a common bug when injecting a Scoped service into a Singleton?  
**Answer**: DI in .NET resolves dependencies via constructor injection using an `IServiceProvider`. Lifetimes:  
- **Transient**: New instance per resolution (e.g., `services.AddTransient<IMyService, MyService>()`).  
- **Scoped**: One instance per request scope (e.g., per HTTP request in ASP.NET Core; `services.AddScoped<...>`).  
- **Singleton**: One instance for the app lifetime (`services.AddSingleton<...>`).  
**Bug**: Injecting a Scoped service into a Singleton causes the Scoped service to behave like a Singleton (captured at first resolution), violating scope semantics and causing thread-safety issues or stale state. Fix by injecting `IServiceProvider` and resolving scoped services per request (e.g., via `scope.ServiceProvider.GetRequiredService<T>()` in middleware/controllers).

DN5 — Medium: What is the difference between string and ReadOnlySpan<char> for string processing? When would you use Span<T> and why?  
**Answer**: `string` is immutable and heap-allocated; `ReadOnlySpan<char>` is a stack-only, ref-like view over contiguous memory (e.g., substring of a string, array, or unmanaged buffer) without copying. `Span<T>` is its mutable counterpart (but `string` itself remains immutable). Use `ReadOnlySpan<char>`/`Span<T>` for high-performance, zero-allocation string/array operations (e.g., parsing, trimming, searching). Avoid `string.Substring()` in hot paths—use `str.AsSpan().Slice(...)`. Note: `Span<T>` cannot escape to heap (no fields, no async locals), so use `Memory<T>` for async scenarios.

DN6 — Medium: Explain how the .NET garbage collector works. What are generations (Gen 0, 1, 2)? What is the Large Object Heap? What is IDisposable and why do you need it if you have a GC?  
**Answer**: GC manages memory via generational collection:  
- **Gen 0**: Short-lived objects (new allocations); collected frequently.  
- **Gen 1**: Promoted from Gen 0; intermediate.  
- **Gen 2**: Long-lived objects (survivors); collected least often (full GC).  
**LOH**: Objects ≥85,000 bytes go here; not compacted (causes fragmentation), collected only in full GCs.  
**IDisposable**: GC only reclaims *managed* memory. `IDisposable` cleans up *unmanaged resources* (files, handles, network connections) deterministically via `Dispose()`. Without it, resources leak until finalization (non-deterministic). Use `using` or `try/finally` to ensure cleanup.

DN7 — Hard: What is the difference between ConfigureAwait(false) and the default behavior? When should you use it, and when should you NOT? How does this relate to SynchronizationContext?  
**Answer**: By default, `await` captures the current `SynchronizationContext` (e.g., UI thread in WPF/WinForms, or ASP.NET request context pre-.NET 6) and resumes on it. `ConfigureAwait(false)` *suppresses* capture, resuming on any thread pool thread. Use `ConfigureAwait(false)` in library code (to avoid deadlocks and improve throughput) and in ASP.NET Core (where `SynchronizationContext` is null by default, so it’s redundant but harmless). **Do NOT use** in UI code where you need to update UI elements (must resume on UI thread). In ASP.NET Core 2.1+, `SynchronizationContext` is null, so default behavior already avoids context capture—but `ConfigureAwait(false)` is still recommended for libraries for compatibility.

**Answer**:

DN9 — Hard: You have a .NET API that works fine under low load but throws ObjectDisposedException on the DbContext under high concurrency. Diagnose the likely cause and explain the fix. How does EF Core's DbContext lifetime interact with DI scoping?  
**Answer**: Likely cause: `DbContext` is registered as **Singleton** (or incorrectly shared across requests). `DbContext` is *not thread-safe* and must be scoped per request. Under high concurrency, one request disposes its `DbContext`, while another still uses it.  
**Fix**: Register `DbContext` as **Scoped** (`services.AddDbContext<MyContext>(options => ...)` does this by default). Ensure no manual caching of `DbContext` instances. In background services, create a new scope:  
```csharp
using var scope = _serviceProvider.CreateScope();
var context = scope.ServiceProvider.GetRequiredService<MyContext>();
```

DN10 — Medium: What is the difference between record and class in C#? What about record struct? When would you choose each?  
**Answer**:  
- **Record** (`record class`): Reference type with value-based equality (`==`, `GetHashCode()`), immutable by default (init-only properties), and `with` expression for non-destructive mutation.  
- **Record struct** (`record struct`): Value type variant—same semantics but stack-allocated, no inheritance (implicitly sealed), and `with` works.  
Use `record` for immutable data models (DTOs, domain objects) where equality matters. Use `record struct` for small, immutable value-like types (e.g., `Point`, `Money`). Avoid records for large or mutable data.

DN11 — Easy: What is the difference between ref, out, and in parameter modifiers in C#? When would you use each?  
**Answer**:  
- `ref`: Pass by reference; variable must be assigned before use. Allows reading/writing.  
- `out`: Pass by reference; variable need not be assigned before, but *must* be assigned in method. Used for multiple return values.  
- `in`: Pass by reference (read-only); variable must be assigned before, but method cannot modify it. Used for performance (avoids copying large structs).  
Example: `void Swap(ref int a, ref int b)`, `bool TryParse(string s, out int result)`, `void Process(in ReadOnlySpan<char> span)`.

DN12 — Easy: Explain nullable reference types in C# (the ? annotation and #nullable enable). How do they differ from nullable value types (int?)?  
**Answer**: Nullable Reference Types (NRTs, C# 8+) annotate reference types with `?` (e.g., `string?`) to indicate null is allowed. `#nullable enable` enables warnings (e.g., assigning null to non-nullable `string`). NRTs are *compile-time only*—no runtime change.  
Nullable value types (`int?`) are `Nullable<T>` structs (runtime feature), allowing null for value types. NRTs apply to *reference types*; `T?` for value types is shorthand for `Nullable<T>`.

DN13 — Easy: What is LINQ? Explain the difference between method syntax (list.Where(...)) and query syntax (from x in list where ...). What is deferred execution?  
**Answer**: LINQ (Language Integrated Query) provides composable query operations over collections.  
- **Method syntax**: Chain extension methods (e.g., `.Where()`, `.Select()`).  
- **Query syntax**: SQL-like syntax (e.g., `from x in list where x > 0 select x`), compiled to method syntax.  
**Deferred execution**: Queries (e.g., `Where`, `Select`) return `IEnumerable<T>`/`IQueryable<T>` without executing—execution happens on enumeration (e.g., `foreach`, `.ToList()`). Immediate execution methods: `.ToList()`, `.Count()`, `.First()`.

DN14 — Easy: What are generic constraints in C#? Explain where T : class, where T : struct, where T : new(), and where T : IComparable<T>. When would you combine multiple constraints?  
**Answer**: Constraints restrict generic type arguments:  
- `where T : class` — reference type.  
- `where T : struct` — non-nullable value type.  
- `where T : new()` — public parameterless constructor.  
- `where T : IComparable<T>` — implements interface.  
Combine for precision: `where T : class, IComparable<T>, new()` (e.g., factory pattern requiring constructor + interface). Constraints enable safe use of members (e.g., `new T()` or `x.CompareTo(y)`).

DN15 — Easy: What is the difference between abstract class and interface in C#? How did default interface methods (C# 8+) change this distinction?  
**Answer**:  
- **Abstract class**: Can have state (fields), constructors, access modifiers, and partial implementation. Supports single inheritance.  
- **Interface**: Traditionally only signatures (no state), multiple inheritance allowed.  
**DMI (C# 8+)**: Interfaces can now have default implementations (`void M() { ... }`), static members, and private virtual methods. This blurs the line—interfaces can now provide *behavior*, not just contracts. Use abstract classes for shared state/constructor logic; interfaces for contracts (especially when multiple inheritance needed).

DN16 — Medium: Explain the middleware pipeline in ASP.NET Core. What is the difference between app.Use(), app.Map(), and app.Run()? How does ordering matter, and how does exception handling middleware work?  
**Answer**: Middleware components form a pipeline: each handles request, then optionally calls next middleware.  
- `app.Use()`: Adds middleware (takes `Func<HttpContext, Func<Task>, Task>`).  
- `app.Map()`: Branches pipeline based on path (e.g., `/api` → separate middleware).  
- `app.Run()`: Terminates pipeline (no `next` delegate); use only at end.  
**Ordering matters**: Middleware executes top-to-bottom on request, bottom-to-top on response. Exception handling (e.g., `UseExceptionHandler`) must be *first* to catch downstream errors.  
Example: `UseExceptionHandler` → `UseAuthentication` → `UseAuthorization` → `UseRouting` → `UseEndpoints`.

DN17 — Medium: What is Channel<T> in .NET? How does it compare to BlockingCollection<T>? Give an example of using bounded channels for producer-consumer backpressure.  
**Answer**: `Channel<T>` (System.Threading.Channels) is a modern, async-friendly, lock-free producer-consumer queue. Supports unbounded (`Channel.CreateUnbounded<T>()`) or bounded (`Channel.CreateBounded<T>(new BoundedChannelOptions { FullMode = BoundedChannelFullMode.Wait })`) channels.  
**vs BlockingCollection<T>**: `Channel<T>` is async-first (uses `ReadAsync`, `WaitToWriteAsync`), more efficient, and avoids blocking threads. `BlockingCollection<T>` uses `IProducerConsumerCollection` and blocks threads (e.g., `Add`, `Take`).  
**Backpressure example**:  
```csharp
var channel = Channel.CreateBounded<string>(new BoundedChannelOptions(10) 
{ FullMode = BoundedChannelFullMode.Wait });
// Producer: await channel.Writer.WriteAsync(data);
// Consumer: await foreach (var item in channel.Reader.ReadAllAsync()) { ... }
```

DN18 — Hard: Explain Source Generators in .NET. How do they differ from reflection and IL weaving? What is an incremental generator, and why is it preferred over ISourceGenerator?  
**Answer**: Source Generators (C# 9+/Roslyn) run during compilation to inspect code and emit *additional source files* (e.g., `System.Text.SourceGenerators`, `MinVer`). They enhance performance (no runtime reflection) and tooling (compile-time errors).  
**vs reflection**: Generators avoid runtime overhead (no `GetTypeInfo()`, `InvokeMember()`).  
**vs IL weaving**: Generators work at source level (safe, IDE-aware); IL weaving modifies compiled binaries (risky, tooling unaware).  
**Incremental generators** (C# 11+): Part of `Microsoft.CodeAnalysis.IncrementalGenerators` (preview). They process only *changed* syntax/semantic data, enabling faster incremental builds. `ISourceGenerator` processes all source every time—less efficient. Incremental generators are preferred for large projects.

DN19 — Hard: What is the System.Threading.Tasks.Dataflow library (TPL Dataflow)? Explain ActionBlock, TransformBlock, and BufferBlock. How does it compare to System.Threading.Channels for pipeline processing?  
**Answer**: TPL Dataflow (System.Threading.Tasks.Dataflow) provides dataflow blocks for building pipeline architectures.  
- **ActionBlock<T>**: Consumes items (e.g., `async` action).  
- **TransformBlock<TInput, TOutput>**: Processes and outputs transformed items.  
- **BufferBlock<T>**: Stores items for later consumption (FIFO queue).  
Blocks link via `LinkTo()` and `Post()`/`SendAsync()`.  
**vs Channels**: TPL Dataflow is higher-level (built-in backpressure, branching, buffering), ideal for complex pipelines (e.g., ETL). Channels are lower-level, simpler, and more performant for basic producer-consumer. Use TPL Dataflow for orchestration; Channels for lightweight async queues.

DN20 — Hard: What are Minimal APIs in .NET? How do they differ from controller-based APIs? What are the trade-offs in terms of testability, middleware, and OpenAPI support? How do route groups and endpoint filters work?  
**Answer**: Minimal APIs (ASP.NET Core 6+) define endpoints directly with lambdas (`app.MapGet("/todo", () => ...)`), reducing boilerplate vs controllers.

P1 — Easy: What is the difference between a list and a tuple? What about a set vs a frozenset?  
**Answer**:  
- **List**: Mutable, ordered, allows duplicates (`[1, 2]`).  
- **Tuple**: Immutable, ordered, allows duplicates (`(1, 2)`).  
- **Set**: Mutable, unordered, unique elements (`{1, 2}`).

P2 — Easy: Explain the GIL (Global Interpreter Lock). What types of workloads does it affect, and what are the workarounds?  
**Answer**: GIL is a mutex protecting Python’s memory management—only one thread executes Python bytecode at a time. Affects **CPU-bound** multi-threaded workloads (e.g., numeric computation), causing no speedup from threading.  
**Workarounds**:  
- Use `multiprocessing` (separate processes, each with GIL).  
- Use C extensions (e.g., NumPy, Cython) that release GIL during computation.  
- Use async I/O for I/O-bound tasks (GIL released during I/O waits).

P3 — Medium: What is the difference between deepcopy and copy? Give an example where shallow copy causes unexpected behavior.  
**Answer**:  
- `copy.copy(obj)`: Shallow copy—copies top-level object, but nested objects are *references*.  
- `copy.deepcopy(obj)`: Deep copy—recursively copies all nested objects.  
**Example**:  
```python
import copy
a = [[1, 2], [3, 4]]
b = copy.copy(a)
b[0][0] = 99
print(a)  # [[99, 2], [3, 4]] — shallow copy shares inner lists!
```

P4 — Medium: Explain Python decorators. Write a decorator that logs the execution time of any function.  
**Answer**: Decorators wrap functions to modify behavior (syntax: `@decorator`). They’re higher-order functions returning a wrapper.  
**Timing decorator**:  
```python
import time
from functools import wraps

def timing(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

@timing
def slow_func():
    time.sleep(0.1)
```

P5 — Medium: What are generators and yield? How do they differ from returning a list? What is yield from?  
**Answer**: Generators are functions that yield values lazily (one at a time) via `yield`, producing an iterator. Memory-efficient for large/ infinite sequences.  
**vs list**: Returning a list materializes all items at once; generators compute on-demand.  
`yield from iterable` delegates to another generator/iterable (e.g., `yield from range(3)` yields 0,1,2).

P6 — Medium: Explain Python's asyncio event loop. What is the difference between asyncio.run(), asyncio.gather(), and asyncio.create_task()? Why can't you call time.sleep() inside an async function?  
**Answer**:  
- **Event loop**: Runs async tasks cooperatively (yields control on `await`).  
- `asyncio.run(coro)`: Runs top-level coroutine (creates loop, runs, closes).  
- `asyncio.gather(*coros)`: Runs multiple coroutines concurrently, returns list of results.  
- `asyncio.create_task(coro)`: Schedules coroutine as a task (returns `Task`), runs in background.  
**`time.sleep()` blocks the thread**, starving the event loop. Use `await asyncio.sleep()` instead.

P7 — Hard: Explain Python's MRO (Method Resolution Order). What algorithm does Python 3 use? What happens with diamond inheritance, and why does the following print what it does?  
```python
class A:
    def who(self): return "A"
class B(A):
    pass
class C(A):
    def who(self): return "C"
class D(B, C):
    pass
print(D().who())
```  
**Answer**: MRO defines method lookup order. Python 3 uses **C3 linearization** (monotonic, preserves local precedence).  
For `D(B, C)`: MRO = `[D, B, C, A, object]`.  
`D().who()` → `B.who()` (not defined) → `C.who()` → `"C"`.  
C3 ensures `C` appears before `A` (since `C` inherits from `A`, and `C` is listed before `A` in `D`’s bases).

P9 — Hard: Explain the difference between multiprocessing, threading, and concurrent.futures in Python. When would you use each? What are the serialization implications of multiprocessing (pickling)?  
**Answer**:  
- **Threading**: Shared memory, limited by GIL—good for I/O-bound tasks.

P10 — Medium: What is __slots__? When should you use it, and what does it prevent? What is the memory impact?  
**Answer**: `__slots__` reserves space for fixed attributes, avoiding per-instance `__dict__`. Reduces memory and speeds attribute access.  
**Prevents**: Dynamic attribute creation (e.g., `obj.x = 1` fails if `x` not in `__slots__`), `__weakref__` (unless added to `__slots__`).  
**Use**: For many small instances (e.g., `Point` in a grid). Memory savings: ~30–50% per instance.  
Example:  
```python
class Point:
    __slots__ = ('x', 'y')
    def __init__(self, x, y): self.x, self.y = x, y
```

P16 — Medium: What is type hinting in Python? Explain typing.Union, Optional, Literal, TypeVar, and Protocol. How does mypy or pyright use these for static analysis?  
**Answer**: Type hints (PEP 484) annotate types for static analysis (no runtime effect).

P17 — Medium: Explain Python's data model (dunder methods). What are __repr__ vs __str__, __eq__ vs __hash__, and __getattr__ vs __getattribute__? What happens if you define __eq__ but not __hash__?  
**Answer**:  
- `__repr__`: Unambiguous representation (for developers); `__str__`: User-friendly (for `str()`).  
- `__eq__`: Equality; `__hash__`: Hash for dict/set. If `__eq__` is defined, `__hash__` is set to `None` (object becomes unhashable) unless explicitly defined.  
- `__getattr__`: Called only if attribute not found via normal lookup.  
- `__getattribute__`: Called for *every* attribute access (override carefully).  
**Rule**: If `__eq__` is defined, redefine `__hash__` (or set to `None`) to avoid inconsistent hashing.

P20 — Hard: What is dataclasses and how does it compare to attrs and Pydantic? Explain __post_init__, field factories, frozen dataclasses, and how dataclasses interacts with inheritance. When would you choose Pydantic over dataclasses?  
**Answer**:  
- **dataclasses** (stdlib): Auto-generates `__init__`, `__repr__`, etc.  
- **attrs**: More features (validators, converters, slots), works on older Python.  
- **Pydantic**: Adds validation, serialization (JSON), and type coercion (via `BaseModel`).  
- `__post_init__`: Custom logic after `__init__`.  
- **Field factories**: `field(default_factory=list)` for mutable defaults.  
- **Frozen**: `@dataclass(frozen=True)` makes instances immutable.  
- **Inheritance**: Subclasses inherit fields; override with `field(repr=False)`.  
**Choose Pydantic** for:  
- Input validation (e.g., API payloads).  
- Serialization/deserialization (e.g., JSON ↔ model).  
- Complex type coercion (e.g., string → datetime).
