SC1-A  
The pods fail because the Restricted Pod Security Standard (PSS) enforces `runAsNonRoot: true` *and* requires that the container image’s `USER` directive be non-root. Previously, under Baseline PSS, `runAsNonRoot` was optional. With Restricted enforcement, if `runAsUser` is not explicitly set, Kubernetes expects the image’s `USER` to be non-root. The Chainguard `static:latest` image now defaults to `USER root`, violating this requirement. Even though `runAsNonRoot: true` is set in `securityContext`, Kubernetes *does not* override the image’s `USER` directive — it only validates that the effective user is non-root *at runtime*. Since the container starts as root and no `runAsUser` is specified to drop privileges, the pod is rejected by the admission controller (or fails to start properly if admission is permissive but runtime enforcement is strict). The CrashLoopBackOff occurs because the container fails to initialize (e.g., due to permission errors when writing to protected paths like `/etc/passwd` or `/var/run`), causing repeated restarts.

SC1-B  
```bash
kubectl get pods --all-namespaces -o json | jq -r '.items[] | select(.status.containerStatuses[0].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, pod: .metadata.name, securityContext: .spec.securityContext}'
```

SC1-C  
**Immediate fix**: Patch affected Deployments to add `runAsUser: 1000` (or a known non-root UID matching Chainguard’s expected user) to `securityContext`. Example:  
```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
```  
Rebuild images with explicit non-root `USER` (e.g., `USER cgr` or `USER 1000:1000`) in Dockerfile — Chainguard images support `--digest`-pinned base images with known UIDs.  

**Prevention**:  
- **CI gate**: Add a pre-push check using `docker inspect` to verify the image’s `User` field is non-root:  
  ```bash
  USER_ID=$(docker inspect --format='{{.Config.User}}' image:tag | cut -d: -f1)
  [[ "$USER_ID" == "root" || -z "$USER_ID" ]] && exit 1
  ```  
- Use Kyverno or OPA Gatekeeper to enforce `runAsNonRoot` *and* require `runAsUser` or validate image `USER` via admission webhook.  
- Pin Chainguard images by digest (e.g., `cgr.dev/chainguard/static@sha256:...`) to avoid tag drift.  

**Rollout without downtime**:  
1. Create new Deployment with fixed `securityContext` and image.  
2. Use `kubectl rollout pause`, update image/manifest, then `kubectl rollout resume`.  
3. Alternatively, use a canary rollout (e.g., with Flagger) to shift 5% → 25% → 100% traffic while monitoring error rates and latency.

SC2-A  
Promoting a cross-region read replica causes **asynchronous replication lag**, meaning WAL segments may not have shipped before promotion. PostgreSQL’s async replication (default) allows the primary to commit without waiting for replica acknowledgment. Thus, writes committed *after* the last shipped WAL but *before* promotion are lost. Data loss window = replication lag at promotion time (often seconds to minutes across regions). To quantify:  
- Check `pg_stat_replication` on primary (before promotion) for `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn`.  
- On replica: `pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()`.  
- After promotion: `pg_current_wal_lsn()` vs. `pg_last_xact_replay_timestamp()` to estimate lag.  
The stale data issue arises because clients may read from replicas *before* promotion that were lagging, or because the new primary has not yet replayed all WAL up to the promotion point — but more critically, **clients reconnecting to the new primary may not realize data is stale** if they expect strong consistency. Async replication provides no guarantee of durability across regions.

SC2-C  
**Architecture improvements**:  
- **RDS Proxy vs PgBouncer**: Use **RDS Proxy** (AWS-native) for connection pooling + TLS termination + automatic failover support. It integrates with IAM auth and handles DNS failover transparently. PgBouncer is lighter but requires manual failover orchestration.  
- **Route53 DNS failover**: Configure health checks on the RDS endpoint (via Lambda that queries `SELECT 1`). Use primary/secondary record sets with failover routing policy.  
- **Application retry logic**: Implement exponential backoff with jitter, circuit breakers (e.g., Resilience4j), and *read-after-write consistency checks* (e.g., include timestamp in response and validate client-side).  
- **RPO < 1s**: Use **Aurora Global Database** — it uses low-latency replication (typically <1s) with synchronous commit across regions for the primary cluster. Standard RDS async replication cannot guarantee RPO < 1s across regions.  
**Recommendation**: Yes — Aurora Global Database is superior for cross-region DR due to its synchronous replication to secondary region (with async fallback), faster failover (<1 min), and integrated DNS failover via RDS Proxy. It also supports global read replicas with minimal lag.

SC4-A  
**Top 5 blockers**:  
1. **Sticky sessions & local session state**: Kubernetes pods are ephemeral; local memory sessions break on pod restart.  
   → *Fix*: Use Redis for session storage (stateful Redis cluster), and configure Ingress to use `sessionAffinity: ClientIP` *or* JWT-based stateless auth.  
2. **NFS `/data/uploads`**: Local NFS is not Kubernetes-native; CSI drivers needed.  
   → *Fix*: Use `nfs.csi.k8s.io` CSI driver with `ReadWriteMany` access mode (see SC4-B).  
3. **Oracle 19c on-prem**: Not cloud-native; scaling, backups, HA are manual.  
   → *Fix*: Use Oracle RAC or migrate to Amazon RDS for Oracle (with cross-region DR), or keep on-prem but use StatefulSet with headless service + PVCs.  
4. **IBM MQ integration**: Synchronous, blocking, and not cloud-native.  
   → *Fix*: Use IBM MQ on-prem with TLS + IAM auth, or migrate to Amazon MSK (Kafka) for async decoupling.  
5. **F5 BIG-IP load balancing**: Not compatible with Kubernetes Ingress natively.  
   → *Fix*: Use NGINX Ingress Controller or AWS ALB Ingress Controller with custom annotations.

**Why `ReadWriteMany`?** Multiple pods (e.g., replicas of the monolith) must mount the same volume simultaneously to access uploaded files — `ReadWriteOnce` would only allow one pod.

SC5-A  
**Debugging approach**:  
1. **Istio metrics**: Check `istio_requests_total`, `istio_request_duration_seconds`, `istio_tcp_connections_opened_total`. Filter by `destination_service="inventory-service"`.  
2. **Envoy proxy metrics**: Look at `envoy_cluster_upstream_rq_pending`, `envoy_cluster_upstream_rq_timeout`, `envoy_cluster_upstream_rq_retry`. High pending = queueing; high timeout = upstream slow.  
3. **Application logs**: `kubectl logs <inventory-pod>` around 14:00 UTC — look for DB connection errors.  
4. **Jaeger/Zipkin**: Trace `checkout-service → inventory-service`. Identify latency spike in `inventory-service/handleRequest`.  
5. **Kubernetes metrics**: `container_cpu_usage_seconds_total`, `container_memory_usage_bytes` — rule out resource pressure.  
6. **Database metrics**: Check PostgreSQL `pg_stat_activity` for long-running queries at 14:00 UTC.  

**Distinguish proxy vs app latency**:  
- If `istio_request_duration_seconds` ≈ `envoy_cluster_upstream_rq_time` + `application_latency`, then app is slow.  
- If `envoy_cluster_upstream_rq_time` spikes but `application_latency` (from app logs) is flat, then Envoy is queuing (e.g., due to connection pool exhaustion).  

SC5-B  
**PostgreSQL lock query**:  
```sql
SELECT 
  l.pid AS locker_pid,
  l.mode,
  l.granted,
  a.query AS current_query,
  a.state,
  w.wait_event_type,
  w.wait_event,
  w.pid AS waiter_pid
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
LEFT JOIN pg_locks w ON NOT l.granted AND w.transactionid = l.transactionid AND w.pid != l.pid
WHERE l.relation = 'stock_levels'::regclass
ORDER BY l.pid;
```

SC5-C  
**Architectural solution**:  
- **CQRS**: Separate read (inventory-service) and write (reconciliation) paths. Reconciliation writes to a *dedicated read replica* or materialized view.  
- **Read replica**: Run reconciliation job against a read replica (with `pg_stat_statements` disabled to reduce overhead).  
- **Bulkhead isolation**: Use separate DB connection pools for serving vs. batch jobs (e.g., via `pgbouncer` pools: `pool_mode = transaction` with different `max_client_conn`).  
- **CronJob scheduling**: Move reconciliation to off-peak (e.g., 02:00 UTC) or use `concurrencyPolicy: Forbid` + `activeDeadlineSeconds`.  

**Kubernetes controls**:  
- **PodDisruptionBudget**: Ensure `minAvailable: 80%` for inventory-service pods.  
- **Resource quotas**: Limit CronJob’s `resources.limits.cpu/memory` to prevent starvation.  
- **PriorityClass**: Assign `system-cluster-critical` to serving pods, `batch` to CronJob.

SC6-A  
**Identity layer design**:  
- **SPIFFE/SPIRE**: Deploy SPIRE server in AWS (EKS), with agents on-prem (via VM agent) and Azure (via AKS). Use SPIFFE SVIDs for workload identity.  
- **Federation**:  
  - AWS → IAM roles for service accounts (IRSA) + SPIRE identity mapping.

  - On-prem → PKI (e.g., HashiCorp Vault PKI) issuing SPIFFE IDs.  
- **Cross-environment auth**: Use SPIRE’s `federates_with` configuration to establish trust bundles. A workload in AWS can authenticate to on-prem by validating SVID signed by a common root CA (e.g., Vault).  
- **No shared secrets**: All auth via mTLS (SPIFFE IDs in certificates) + JWT assertions for human access.

SC10-A  
**Multi-cluster architecture**:  
- **Active-passive (Velero)**:  
  - RPO/RTO: **RPO = backup interval** (e.g., 15 min), **RTO = backup time + restore time** (200TB MinIO → ~30–60 min). *Meets RPO/RTO only if backups are frequent*.  
  - Replication: PostgreSQL (sync), Redis (AOF + RDB), RabbitMQ (federation), MinIO (site replication).  
- **Active-active (Istio/Cilium)**:  
  - RPO/RTO: **RPO = replication lag** (12ms latency → ~100ms sync lag), **RTO = failover time** (~30s). *Meets RPO/RTO if using synchronous replication*.  
  - Replication: PostgreSQL (Patroni sync), Redis (Cluster + AOF), RabbitMQ (mirrored queues), MinIO (site replication).  

**Recommendation**: **Active-passive with Velero + synchronous DB replication** for regulatory compliance (zero data loss). Use Velero for CRDs, PVCs, and MinIO snapshots.

SC10-C  
**Failover orchestration**:  
1. **Detection**:  
   - Monitor: `pg_is_in_recovery()`, `patroni_state`, `minio_health`.  
   - "Site down" = 3 consecutive failures to reach Chicago services (HTTP + TCP).  
2. **Failover sequence**:  
   - Stop traffic to Chicago (DNS TTL=30s, GSLB health check fails).  
   - Patroni: `patronictl failover --force` (promotes Dallas).  
   - Redis: Sentinel auto-failover (if quorum met).  
   - RabbitMQ: Federation catch-up (if using `federation_link`), else queue mirroring.  
   - MinIO: `mc admin replicate add` to sync.  
3. **Split-brain prevention**:  
   - Use `synchronous_commit=on` + `synchronous_standby_names` to ensure only one primary.  
   - Use etcd for DCS lock (Patroni).  
4. **Failback**:  
   - After Chicago recovery: demote Dallas to standby, promote Chicago.  
   - Use `patronictl reinit` to rebuild Chicago from scratch if needed.  
5. **State sync**:  
   - Run `tofu import` for new primary resources.  
   - Use `tofu state mv` to update references.  
   - Validate with `tofu plan -detailed-exitcode`.
