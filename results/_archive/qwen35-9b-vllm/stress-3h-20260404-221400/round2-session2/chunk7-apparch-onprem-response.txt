AA1 — Easy: A monolith is a single, unified codebase deployed as one unit, while microservices decompose an application into small, independent services communicating over a network. Three concrete problems microservices introduce: 1) Distributed transactions (complexity of consistency), 2) Network latency and failure points (services can fail independently), 3) Operational complexity (deploying, monitoring, and scaling many services vs one).

AA2 — Easy: Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST, gRPC). Asynchronous communication involves fire-and-forget or publish-subscribe patterns where the caller does not wait (e.g., Message Queues like RabbitMQ, Kafka).

AA3 — Medium: An API Gateway handles business logic (auth, rate limiting, aggregation), while a reverse proxy handles traffic routing and SSL termination. An API Gateway cannot replace a reverse proxy entirely because proxies often need to operate at lower layers (L4) for performance and load balancing, whereas gateways focus on L7 logic.

AA4 — Medium: The Saga pattern manages long-running transactions across services by breaking them into local transactions. Choreography uses events to trigger the next step (decoupled, hard to debug). Orchestration uses a central coordinator to manage steps (coupled, easier to manage). Choreography is appropriate for loosely coupled systems; orchestration for complex workflows requiring rollback control.

AA5 — Medium: CQRS separates read and write operations into different models. It is paired with Event Sourcing (state is a log of events) to solve the problem of read/write performance mismatch and to provide a complete audit trail, which traditional CRUD models lack.

AA6 — Medium: The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failures exceed threshold, stop calls), Half-Open (test if service recovered). It differs from retry with backoff because it stops attempts entirely when the service is dead, whereas retry keeps hammering it. Use both: retry for transient glitches, circuit breaker for persistent failures.

AA7 — Hard:
1. **Shared DB, Shared Schema:** Lowest cost, highest operational complexity, high noisy-neighbor risk, lower security (data leakage via SQL injection).
2. **Shared DB, Separate Schema:** Medium cost, better isolation, moderate ops complexity.
3. **Separate DB per Tenant:** Highest cost, best security/performance, lowest noisy-neighbor risk, highest ops complexity (provisioning/backup).
*Recommendation:* Use separate DBs for high-security/enterprise tenants; shared schema for low-cost SaaS.

AA8 — Hard: Eventual consistency allows data to converge over time; strong consistency guarantees immediate visibility of updates. For inventory (never oversell), strong consistency is required. Architecture: Use a transactional database (e.g., PostgreSQL) with optimistic locking or a distributed lock (e.g., Redis/Zookeeper) to ensure atomicity. At scale, use a dedicated inventory service with a strong consistency store, avoiding eventual consistency for the critical path.

AA9 — Hard: A sidecar proxy runs alongside a service to handle networking. In Istio, Envoy is the sidecar (data plane) handling traffic, while Istiod is the control plane managing configuration. mTLS between sidecars solves service-to-service authentication without requiring app-level TLS changes, enabling zero-trust security within the mesh.

AA10 — Medium: The Strangler Fig pattern migrates legacy systems by incrementally routing new traffic to new services. Strategy: Place an API Gateway in front of the .NET Framework monolith. Identify a small feature (e.g., "User Profile"), implement it in .NET 8, and route that traffic to the new service. Gradually expand the feature set until the monolith is fully decommissioned.

AA11 — Medium: The 12-Factor App methodology defines best practices for cloud-native apps. Six factors: 1) Codebase (versioned), 2) Dependencies (explicit), 3) Config (env vars), 4) Services (treat as resources), 5) Build/Release/Run (separation), 6) Dev/Prod parity. They matter for portability, scalability, and security.

AA12 — Hard: **Event-Driven (Kafka):** Decoupled, high scalability, complex debugging, ordering via partitions, async failure handling. **Request-Driven (REST/gRPC):** Tight coupling, easier debugging, synchronous failure, immediate ordering. Choose Event-Driven for event sourcing, decoupled pipelines, or high throughput. Choose Request-Driven for real-time user interactions and simple CRUD.

AA13 — Easy: A load balancer distributes incoming traffic across servers. Layer 4 (TCP/UDP) balances based on IP/Port (fast). Layer 7 (HTTP/HTTPS) balances based on URL/Headers (routing). Layer 7 is required for path-based routing (e.g., `/api` vs `/static`) or SSL termination.

AA14 — Easy: A message queue (RabbitMQ) is typically point-to-point with short-lived messages. A log-based broker (Kafka) is pub/sub with durable, replayable logs. Pick RabbitMQ for task queues (e.g., email sending). Pick Kafka for event streams (e.g., user activity logs).

AA15 — Easy: A container packages code and dependencies with a shared OS kernel. A VM includes a full OS. Containers are popular for microservices due to higher density, faster startup times, and easier portability across environments.

AA16 — Easy: Stateless services do not store data in memory (e.g., Web Server), making them easy to scale horizontally. Stateful services store data (e.g., Database), making scaling harder. Stateless services allow any instance to handle any request.

AA17 — Easy: An ORM maps database tables to object classes. Examples: Hibernate (Java), SQLAlchemy (Python). Trade-offs: ORMs reduce boilerplate and prevent SQL injection but can suffer from performance overhead and "N+1" query issues compared to raw SQL.

AA18 — Medium: The Bulkhead pattern isolates resources (threads, memory) to prevent one failure from exhausting all resources. Example: Allocate separate thread pools for database connections and external API calls. If the API pool is exhausted, the DB pool remains available.

AA19 — Hard: **OT (Operational Transformation):** Server-side conflict resolution, complex, requires online connection. **CRDTs:** Client-side mathematically guaranteed convergence, supports offline editing. Choose CRDTs for offline support because they allow local edits to be merged automatically without server intervention, ensuring consistency eventually.

AA20 — Hard: Distributed tracing requires propagating a Trace ID (W3C Trace Context) via headers. Sampling (head-based) reduces storage costs. Storage (Jaeger/Tempo) aggregates spans. For async messaging (Kafka), the producer must inject the Trace ID into message headers, and the consumer must extract it to continue the trace, ensuring continuity across the broker.

OP1 — Easy: Type 1 (Bare-metal) runs directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) runs on top of an OS (e.g., VMware Workstation, VirtualBox).

OP2 — Easy: SAN (Storage Area Network) provides block-level storage (iSCSI, Fibre Channel) for high-performance DBs. NAS (Network Attached Storage) provides file-level storage (NFS, SMB) for general file sharing. Use SAN for databases; NAS for file servers.

OP3 — Medium: 3-tier (Core/Distribution/Access) separates traffic layers. Leaf-Spine (flat mesh) connects every leaf to every spine, solving the latency and scalability bottlenecks of 3-tier by providing equal path latency and higher bandwidth.

OP4 — Medium: Proxmox HA requires 3+ nodes for quorum. Use Ceph or iSCSI for shared storage. Fencing (STONITH) prevents split-brain. If a node fails, the cluster detects the loss, fences the failed node, and promotes a surviving node to take over the VMs.

OP5 — Medium: VLAN trunking allows multiple VLANs over a single link using 802.1Q tags. On Linux, configure the physical NIC as a bridge or use `ip link add` to create VLAN interfaces (e.g., `ip link add link eth0 type vlan id 10`).

OP6 — Hard: RAID 1 (Mirror), 5 (Striping+Parity), 6 (Double Parity), 10 (Striping+Mirror), Z2 (ZFS Mirror+Parity). For 6 drives balancing performance/capacity/fault tolerance: RAID 10 (4 drives usable, high perf) or ZFS RAID-Z2 (4 drives usable, better capacity efficiency). ZFS is preferred for modern DBs due to data integrity features.

OP7 — Hard: DNS Architecture: Recursive resolvers (ISP) query authoritative servers (AD/DMZ). Split-horizon: Internal clients query internal zone, external query public. DNSSEC signs zones. When a laptop moves, DHCP updates the DNS record, or split-horizon ensures the correct view based on the client's source IP.

OP8 — Hard: PKI Chain: Root CA (offline) -> Subordinate CA -> End-entity. CRL (Certificate Revocation List) is a static list; OCSP is dynamic. Compromised Subordinate: Revoke certs issued by that CA. Compromised Root: Revoke all subordinate certs and re-issue root.

OP9 — Hard: MPLS (High cost, reliable, low latency). IPsec (Low cost, internet risk). SD-WAN (Balanced, easy management). WireGuard (Simple mesh). For 50 users/VoIP: SD-WAN is recommended for balancing cost, reliability, and latency management over the internet.

OP10 — Medium: iDRAC/iLO/IPMI are Out-of-Band Management interfaces (BMC). Critical for remote reboot/console access without OS. Exposing to the internet is a severe security risk (brute force attacks, remote code execution).

OP11 — Easy: LVM (Block level), LVM-Thin (Space efficient), ZFS (File system with features). Snapshots: LVM (copy-on-write), Thin (metadata), ZFS (native, fast). Use ZFS for file storage with snapshots; LVM for block storage.

OP12 — Hard: Stretch Cluster: Place Ceph monitors in different sites. CRUSH rules ensure data replicas are spread. 2-site Ceph is risky without a tiebreaker (3rd site) because if one site fails, the other might lose quorum (split-brain). Use a 3rd site or a cloud-based tiebreaker.

OP13 — Easy: DHCP DORA: Discover, Offer, Request, Ack. If server unavailable and lease expires, the client cannot renew and assigns itself an APIPA address (169.254.x.x), losing network connectivity.

OP14 — Easy: Managed switches support VLANs, QoS, and ACLs. Unmanaged switches are plug-and-play. Managed switches are required for enterprise security, traffic prioritization, and segmentation.

OP15 — Easy: NTP synchronizes system clocks. Critical for log correlation, Kerberos authentication, and database replication. Drift causes authentication failures and data inconsistency.

OP16 — Easy: Physical (Bare metal), VM (OS layer), Container (App layer). Run on bare metal for low latency, high security (crypto), or when hypervisor overhead is unacceptable.

OP17 — Easy: UPS provides instant backup power; Generators provide long-term power. ATS switches between utility, UPS, and generator. UPS bridges the gap until the generator starts.

OP18 — Medium: Active-Passive (one active, one standby); Active-Active (both active). Pacemaker/Corosync: Use STONITH (fencing) to ensure only one node writes to shared storage. VIP floats to the active node. On failure, the standby takes the VIP.

OP19 — Hard: 3-2-1 Rule: 3 copies, 2 media types, 1 offsite. RPO (max data loss), RTO (max downtime). Types: Full (slow, complete), Incremental (fast, partial), Differential (medium). Immutable backups prevent ransomware. Backup = data copy; DR = full system recovery capability.

OP20 — Hard: 802.1X: Supplicant (client), Authenticator (switch), Auth Server (RADIUS). EAP-TLS (certs), PEAP (password). Fail auth = port blocked. MAB (MAC Auth Bypass) allows devices without supplicants (printers) to authenticate via MAC address.
