## Cloud Infrastructure Architecture

**CL1**
**IaaS** (Infrastructure as a Service) provides virtualized computing resources (VMs, storage, networks) where the user manages the OS and applications. *Example:* AWS EC2. **PaaS** (Platform as a Service) provides a managed runtime environment (database, container orchestration) where the user manages only the application code. *Example:* Google App Engine. **SaaS** (Software as a Service) delivers fully managed software applications over the internet. *Example:* Salesforce.

**CL2**
**Shared Responsibility Model:** The provider secures the cloud infrastructure; the customer secures what they put in the cloud.
*   **IaaS VMs:** Provider secures physical hardware, hypervisor, and network. Customer secures OS, data, and applications.
*   **Managed Kubernetes:** Provider secures the control plane (API server, etcd). Customer secures the worker nodes, pods, and application data.
*   **SaaS (M365):** Provider secures the entire stack (servers, OS, app logic). Customer secures user identities, data classification, and access policies.

**CL3**
**VPC:** Logical isolation of network resources within a cloud region. **Subnet:** A range of IP addresses within a VPC, defining where resources reside. **Security Group:** Stateful firewall attached to an instance (allows inbound, allows return traffic). **NACL:** Stateless firewall attached to a subnet (rules applied to all traffic entering/leaving the subnet).
**Layering:** VPC contains Subnets; Subnets have NACLs; Instances have Security Groups.
**Stateful vs Stateless:** Security Groups track connection state (if you allow inbound, return traffic is allowed). NACLs do not; if you block inbound, return traffic is also blocked unless explicitly allowed.

**CL4**
**Multi-Account Strategy:**
*   **Landing Zone:** Pre-provisioned foundational resources (IAM, networking, logging) to accelerate account creation.
*   **Organizational Units (OUs):** Hierarchical grouping of accounts for policy application (e.g., Dev, Prod, Finance).
*   **Guardrails:** SCPs (Service Control Policies) or RBAC to prevent non-compliant actions (e.g., no public S3 buckets).
*   **Shared Networking:** Hub-and-Spoke (Transit Gateway/Azure Hub) centralizes routing and security inspection.
*   **Centralized Logging:** Aggregating logs (CloudTrail, VPC Flow Logs) into a central SIEM for audit.
**Single-Account Problem:** Limits scalability, creates security silos, complicates billing, and restricts isolation for compliance.

**CL5**
**IaC:** Managing infrastructure via code rather than manual clicks.
*   **Terraform/OpenTofu:** Declarative, state-based, multi-cloud. Best for complex, multi-cloud environments.
*   **Pulumi:** Declarative/Imperative using general-purpose languages (Python, Go). Best for teams with strong coding backgrounds.
*   **CloudFormation/Bicep:** Native AWS/Azure templates. Best for single-cloud, deep integration with native services.
*   **Crossplane:** Kubernetes-native, manages cloud resources as K8s CRDs. Best for K8s-centric organizations.

**CL6**
**HPA:** Scales pod count based on CPU/Memory metrics. **VPA:** Scales pod resource requests/limits (requires restart). **Cluster Autoscaler:** Adds/removes nodes based on pod demand. **KEDA:** Scales based on external events (queue depth, HTTP requests).
**KEDA vs HPA:** Use KEDA when load is driven by external events (e.g., message queue backlog) rather than CPU usage, allowing for zero-pod scaling during idle periods.

**CL7**
**DR Strategy:**
*   **RPO/RTO:** RPO (Recovery Point Objective) = max data loss; RTO (Recovery Time Objective) = max downtime.
*   **Active-Active:** Workloads run in both regions (highest cost, lowest RTO). **Active-Passive:** Workloads run in primary, failover to secondary (lower cost, higher RTO).
*   **DB Replication:** Sync (zero RPO, high latency) vs Async (RPO > 0, low latency).
*   **DNS Failover:** Route53/Traffic Manager directs traffic to healthy region.
*   **State Management:** Use stateless services (Redis Cluster) or distributed DBs (DynamoDB) to avoid state sync issues.
*   **Cost:** Active-Active is most expensive; Pilot Light is cheapest.
*   **DR Types:** **Pilot Light:** Minimal resources ready (fast startup, high RTO). **Warm Standby:** Partial resources running (medium cost/RTO). **Multi-site Active-Active:** Full resources in both (high cost, lowest RTO).

**CL8**
**GitOps:** Infrastructure/App state is defined in Git; controllers (CD) reconcile the cluster to match Git.
*   **ArgoCD:** K8s-native, UI-focused, supports multiple apps. **FluxCD:** Operator-based, Helm-centric, often used in CI/CD pipelines.
*   **Secrets:** Use Sealed Secrets (encrypted in Git) or External Secrets Operator (fetches from Vault/AWS Secrets Manager).
*   **Drift:** If manual changes occur, the controller detects the difference and reverts the cluster to the Git state (or prompts for approval).

**CL9**
**Stateful K8s Architecture:**
*   **StatefulSet:** Ensures stable network IDs and persistent storage for pods.
*   **PV/PVC:** Use `LocalPath` StorageClass for low-latency local storage.
*   **Headless Service:** Provides DNS entries for individual pods (e.g., `pod-0.service`).
*   **Init Containers:** Run setup scripts (e.g., creating directories) before the main app starts.
*   **ConfigMaps:** Mount config files as volumes into specific paths.
*   **Pod Disruption Budgets:** Ensure a minimum number of pods are running during voluntary disruptions (e.g., node maintenance).

**CL10**
**Service Account:** K8s identity for pods. **Workload Identity:** K8s identity mapped to cloud IAM (e.g., AWS IRSA). **IRSA:** AWS-specific binding of K8s SA to IAM Role.
**Mounting Creds:** Bad practice because credentials are static, hard to rotate, and if leaked, the pod has full access.
**Workload Identity:** Solves this by allowing the pod to assume a cloud IAM role dynamically via the K8s API, eliminating the need for static credential files.

**CL11**
**Object Storage (S3/Blob):** Unstructured data, API access, high durability (99.999999999%). Use for backups, media, logs. **Block Storage (EBS/Disk):** Attached to VM, low latency, high IOPS. Use for OS, databases. **File Storage (EFS/Files):** Shared file system, NFS/SMB protocol. Use for shared app data.
**Guarantees:** Object is most durable; Block is most performant; File is most accessible for shared workloads.

**CL12**
**Zero Trust K8s:**
*   **Network Policies:** Default deny all traffic between pods.
*   **Service Mesh (Istio/Linkerd):** Enforces mTLS between services.
*   **Pod Identity:** Bind K8s pods to cloud identities.
*   **Admission Controllers (OPA/Kyverno):** Enforce policies (e.g., no privileged containers) at deploy time.
*   **Image Signing:** Verify images via Cosign/Notary.
*   **Runtime Security (Falco):** Detect anomalous behavior (e.g., unexpected process execution).
*   **Secrets:** Use external vaults, never store in env vars.
**Difference:** Traditional perimeter trusts internal traffic; Zero Trust verifies every request regardless of origin.

**CL13**
**CDN:** Network of edge servers caching content closer to users.
**How:** Caches static assets at edge nodes; fetches from origin on cache miss.
**Services:** AWS CloudFront, Azure CDN.
**Use Case:** Use CDN for static assets (images, CSS) to reduce latency and origin load. Use direct origin for dynamic content or private data requiring strict access control.

**CL14**
**Region:** Geographic area with multiple Availability Zones (e.g., us-east-1). **AZ:** Isolated data centers within a region with independent power/network.
**Deploy Across AZs:** Ensures High Availability (HA) against zone failure.
**Zonal vs Regional:** Zonal resources (e.g., EC2) are in one AZ; Regional resources (e.g., S3, RDS Multi-AZ) span AZs for redundancy.

**CL15**
**Managed Database:** Service like RDS/Cloud SQL.
**Provider Tasks:** Patching, backups, failover, scaling, monitoring, security patching.
**User Tasks:** Schema design, data management, query optimization, application connectivity.

**CL16**
**IAM:** **Users** (people), **Groups** (collections of users), **Roles** (permissions), **Policies** (JSON rules).
**Least Privilege:** Grant only the permissions necessary for a specific task. Apply via policies attached to roles/users, avoiding admin access by default.

**CL17**
**Serverless:** Event-driven compute without managing servers.
**Comparison:** AWS Lambda (Node/Python), Azure Functions (Durable), GCF (Node/Go).
**Cold Starts:** Latency on first invocation due to initialization. Matters for latency-sensitive apps.
**Poor Fit:** Long-running processes, stateful workloads, or high/consistent CPU requirements.

**CL18**
**Ingress Options:**
*   **Ingress Resource:** K8s API object, managed by controller.
*   **Gateway API:** K8s standard (RFC 9426), supports more features (HTTPRoute).
*   **Cloud LB:** Managed L7 load balancer (e.g., ALB) with annotations.
*   **Service Mesh:** Envoy-based ingress gateways (e.g., Istio).
**TLS:** Terminated at Cloud LB (offloads K8s) or Ingress Controller (K8s manages certs).
**Gateway API:** Use for multi-tenant, complex routing, or when adhering to K8s standards over vendor-specific annotations.

**CL19**
**Cost Optimization:**
*   **Commitments:** Savings Plans/RI for steady workloads. **Spot:** For fault-tolerant batch workloads.
*   **Right-sizing:** Use CloudWatch/Compute Optimizer to match instance size to usage.
*   **Storage Tiering:** Move infrequent data to S3 Glacier/Archive.
*   **Idle Detection:** Use tools to find unused resources (e.g., unattached EBS).
*   **FinOps:** Culture of cost ownership. **Showback/Chargeback:** Allocate costs to teams/projects.
*   **Tools:** AWS Cost Explorer, CloudHealth, Datadog.

**CL20**
**Multi-Cloud Strategy:**
*   **Abstraction:** Use K8s as the runtime and Terraform for IaC to avoid vendor lock-in.
*   **Networking:** AWS Direct Connect/Azure ExpressRoute + Transit Gateway peering or SD-WAN.
*   **Identity:** OIDC federation between clouds (e.g., AWS IAM Identity Center <-> Azure AD).
*   **Trade-offs:** Higher complexity, cost, and latency vs. risk mitigation and compliance.
*   **Justification:** Use when compliance requires it or for specific regional latency needs. Avoid if single-cloud meets 90% of needs (complexity often outweighs benefits).

## OT Infrastructure Architecture

**OT1**
**Purdue Model (ISA-95):** Hierarchical architecture for industrial automation.
*   **Level 0:** Physical Process (Sensors/Actuators).
*   **Level 1:** Basic Process Control (PLCs, DCS).
*   **Level 2:** Supervisory Control (SCADA, HMI).
*   **Level 3:** Enterprise Control (MES, ERP).
*   **Level 4:** Business/Management (ERP, Supply Chain).
*   **Level 5:** IT/Corporate (Office IT).

**OT2**
**IT vs OT:** IT focuses on data availability and confidentiality; OT focuses on safety, reliability, and uptime.
**Patching:** IT patches are frequent and can be done remotely. OT patches require downtime, testing, and can disrupt safety functions, making standard IT practices unsafe.

**OT3**
**IDMZ:** Demilitarized Zone separating IT (L3/L4) from OT (L1/L2).
**Traffic:** IT can initiate requests to IDMX (e.g., for updates), but OT cannot initiate to IT.
**Direction:** L4/L3 -> IDMX -> L2/L1.
**Danger:** Direct L4 to L1 connectivity bypasses security layers, allowing ransomware to reach critical control systems directly.

**OT4**
**Protocols:**
1.  **Modbus TCP:** L1 (PLC-to-PLC/PLC-to-HMI).
2.  **OPC UA:** L1/L2 (Secure, platform-independent data exchange).
3.  **EtherNet/IP:** L1 (Rockwell automation, CIP protocol).
4.  **PROFINET:** L1 (Siemens automation, real-time).
5.  **MQTT:** L2/L3 (Lightweight messaging for SCADA/Analytics).

**OT5**
**Data Diode:** Hardware device allowing data flow in only one direction (e.g., OT to IT).
**Firewall:** Bidirectional filtering.
**Use:** Use diodes for critical data export (e.g., telemetry to cloud) where return traffic is impossible or prohibited.
**Limitation:** Cannot block malicious inbound traffic; only prevents outbound data leakage.

**OT6**
**Data Flow:** PLC -> Historian/OPC UA Server -> Edge Gateway (Protocol translation) -> MQTT Broker -> Cloud Ingestion.
**Security Boundaries:**
*   **PLC to Historian:** Physical or VLAN isolation.
*   **Edge to Cloud:** Firewall with strict egress rules.
*   **OT to IT:** IDMX (Industrial DMZ) with deep packet inspection.

**OT7**
**Zones/Conduits:**
*   **Zone:** Logical boundary of assets with similar risk/function.
*   **Conduit:** Connection between zones (firewall/IDS).
**Plant Model:**
*   **Zone 1:** Corporate Network (IT).
*   **Zone 2:** Engineering Workstations (IT/OT boundary).
*   **Zone 3:** SCADA Servers/DMZ.
*   **Zone 4:** PLCs/SIS (Control).
**Conduits:** Firewalls between zones, IDS at Zone 3/4 boundary.

**OT8**
**Segmentation Strategy:**
*   **VLANs:** Separate VLANs per production line and function (Engineering, SCADA, PLC).
*   **Firewalls:** Layer 3 firewalls between VLANs (Zone-based).
*   **Switches:** Managed Layer 3 switches for routing.
*   **Vendor Access:** Jump host with MFA and session recording.
*   **Transition:** Phased migration (one line at a time) or parallel run to ensure production continuity.

**OT9**
**SIS vs BPCS:** SIS (Safety Instrumented System) overrides BPCS (Basic Process Control) to shut down equipment in emergencies.
**IEC 61511:** Functional Safety standard for SIS.
**Isolation:** SIS must be isolated (air-gapped or strict firewall) to prevent ransomware from locking safety systems.
**Consequence:** If ransomware reaches SIS, it could prevent safe shutdown, leading to physical damage or environmental hazards.

**OT10**
**PLC:** Programmable Logic Controller (discrete control, local). **DCS:** Distributed Control System (continuous process, complex, centralized). **SCADA:** Supervisory Control and Data Acquisition (monitoring, wide area).
**Usage:** PLC for simple machines; DCS for refineries/chemical plants; SCADA for utilities/water.
**Coexistence:** Yes, PLCs/DCS at L1, SCADA at L2.

**OT11**
**Remote Access:**
*   **Jump Host:** Bastion host for all access.
*   **MFA:** Mandatory for all sessions.
*   **Session Recording:** Audit all actions.
*   **Vendor Access:** Time-limited, ticket-based, via jump host.
*   **RDP to HMI:** Unacceptable because it exposes the control interface directly to the internet/corporate network.

**OT12**
**Detection/Response:**
*   **Monitoring:** IDS (e.g., Snort/Suricata) for protocol anomalies.
*   **Inventory:** Know all assets (IP, firmware, function).
*   **Response:** Isolate affected segment (firewall rule), notify control room.
*   **Operator Role:** Safety first. Operators decide if shutdown is needed; IT handles containment.
*   **Safe Ops:** Maintain manual control if automated systems are compromised.

**OT13**
**HMI:** Human-Machine Interface (touchscreen/panel) for operators to monitor/control processes.
**Role:** Real-time visualization and manual override.
**Difference:** Engineering Workstation is for configuration, debugging, and offline engineering; HMI is for live operation.

**OT14**
**Historian:** Time-series database storing process data (tags, trends).
**Importance:** Compliance, analysis, troubleshooting.
**Plant Historian (L3):** Stores operational data for the plant. **Enterprise Historian (L4):** Aggregates data from multiple plants for business analysis.

**OT15**
**Ladder Logic:** Programming language resembling relay logic diagrams.
**Device:** PLC.
**Dominance:** Familiarity for electricians, ease of debugging, and hardware support.

**OT16**
**RTU:** Remote Terminal Unit (serial, harsh environment, remote sites). **PLC:** Programmable Logic Controller (Ethernet, factory floor).
**Deployment:** RTUs for pipelines/remote oil/gas; PLCs for factory automation.

**OT17**
**Analog Signals:** Continuous values (4-20mA, 0-10V).
**4-20mA vs 0-20mA:** 4-20mA allows "live zero" (0mA means broken wire, 4mA means 0% value). 0-20mA cannot distinguish between a zero value and a broken wire. 4-20mA is preferred for noise immunity and fault detection.

**OT18**
**Asset Inventory:** List of all OT assets (IP, firmware, function). Foundation for security.
**Discovery:** Passive (sniffing traffic) is safe. Active (ping/scans) can crash devices or trigger safety logic.
**Risk:** Active scanning in OT can cause downtime or safety hazards.

**OT19**
**MITRE ATT&CK for ICS:** Framework for adversary tactics/techniques in industrial environments.
**Tactics/Techniques:**
1.  **Reconnaissance:** T1590 (Network Services Discovery).
2.  **Execution:** T1059 (Command and Scripting Interpreter).
3.  **Persistence:** T1503 (Registry Run Keys).
4.  **Privilege Escalation:** T1548 (Abuse Elevation Control Mechanism).
5.  **Exfiltration:** T1048 (Exfiltration Over C2 Protocol).
**Difference:** Enterprise ATT&CK focuses on IT; ICS includes industrial protocols and safety systems.
**Usage:** Map observed behaviors to techniques to identify gaps in detection.

**OT20**
**Converged SOC:**
*   **Log Collection:** Syslog/CEF from OT assets (firewalls, IDS) without impacting real-time ops.
*   **SIEM:** Correlate IT and OT logs.
*   **OT Rules:** Detect protocol anomalies (e.g., unexpected Modbus commands).
*   **Staffing:** Hybrid team (IT analysts + OT engineers).
*   **False Positives:** High noise in OT; tune rules to reduce alerts.
*   **Firmware Alert:** Quarantine the asset, verify integrity with vendor, patch if safe, do not reboot immediately if safety-critical.
