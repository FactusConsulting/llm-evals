## Application Architecture (20 questions)

**AA1**
A monolith is a single, unified codebase deployed as one unit. Microservices decompose the application into independent services communicating over a network.
Three concrete problems microservices introduce:
1.  **Network Latency:** Inter-service communication adds overhead compared to in-process calls.
2.  **Distributed Transactions:** Maintaining data consistency across services requires complex patterns (e.g., Sagas) instead of ACID transactions.
3.  **Operational Complexity:** Managing multiple deployments, versions, and dependencies increases CI/CD and monitoring overhead.

**AA2**
Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST, gRPC). Asynchronous communication involves fire-and-forget or callback patterns where the caller does not wait (e.g., Message Queues like RabbitMQ, Event Bus like Kafka).

**AA3**
An API Gateway handles business logic (auth, rate limiting, aggregation, transformation). A reverse proxy handles network-level routing, SSL termination, and load balancing.
An API Gateway cannot entirely replace a reverse proxy. While they overlap, a reverse proxy is often required for high-performance L4 routing, direct TCP/UDP passthrough, and lower-level SSL termination that a high-level Gateway might not handle efficiently.

**AA4**
The Saga pattern manages long-running transactions across distributed services by breaking them into local transactions.
*   **Choreography:** Services publish events; other services react. Decoupled but hard to trace and manage.
*   **Orchestration:** A central coordinator tells services what to do. Easier to manage and rollback, but introduces a single point of coordination.
*   **Usage:** Choreography for loosely coupled systems; Orchestration for complex workflows requiring strict control.

**AA5**
CQRS separates the read (Query) and write (Command) models into different stores or logic. It is paired with Event Sourcing (storing state as a sequence of events) to reconstruct state.
This combination solves the performance mismatch of traditional CRUD (where reads and writes share the same index) and provides a complete audit trail and scalability for read-heavy workloads.

**AA6**
The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service.
Three states: **Closed** (normal operation), **Open** (fail fast, no calls), **Half-Open** (testing if service recovered).
It differs from simple retry because retry keeps hammering a failing service. Use both together: Retry for transient errors (e.g., 503), Circuit Breaker to stop retrying once failure threshold is exceeded.

**AA7**
1.  **Shared DB, Shared Schema:**
    *   *Cost:* Lowest.
    *   *Security:* Low (data leakage risk).
    *   *Ops:* Low.
    *   *Noisy Neighbor:* High (one tenant slows others).
2.  **Shared DB, Separate Schema:**
    *   *Cost:* Medium.
    *   *Security:* Medium.
    *   *Ops:* Medium (schema management).
    *   *Noisy Neighbor:* Low.
3.  **Separate DB per Tenant:**
    *   *Cost:* High.
    *   *Security:* High (logical isolation).
    *   *Ops:* High (provisioning/backup).
    *   *Noisy Neighbor:* None.

**AA8**
Strong consistency guarantees immediate visibility of updates across all nodes. Eventual consistency allows temporary divergence.
For inventory (never oversell), **Strong Consistency** is required.
*   **Data Store:** Relational DB (PostgreSQL) or Strongly Consistent NoSQL (Cassandra with Tunable Consistency).
*   **Patterns:** Use distributed locks (Redis/Zookeeper) or optimistic locking (versioning) to ensure atomic updates.

**AA9**
A sidecar proxy is a lightweight process running alongside a service to handle networking. In Istio, Envoy is the sidecar.
*   **Data Plane:** Envoy handles traffic (L7/L4).
*   **Control Plane:** Istiod manages Envoy configuration.
*   **mTLS:** Solves service-to-service authentication without requiring app code changes, enabling zero-trust security within the mesh.

**AA10**
The Strangler Fig pattern migrates functionality incrementally.
*   **Strategy:** Wrap the legacy .NET Framework monolith behind an API Gateway. Route new features to .NET 8 microservices. Gradually route legacy endpoints to the new services as they are built. Finally, retire the monolith.

**AA11**
The 12-Factor App methodology defines best practices for building cloud-native apps.
Six factors:
1.  **Codebase:** One codebase tracked in VCS.
2.  **Dependency:** Explicitly declared and isolated.
3.  **Config:** Config in environment variables, not code.
4.  **Backing Services:** Treat attached resources (DB) as attached resources.
5.  **Build, Release, Run:** Strict separation of concerns.
6.  **Process:** Run app as one or more stateless processes.
They matter for portability, scalability, and security in cloud environments.

**AA12**
*   **Event-Driven (Kafka):** Decoupled, high scalability, complex debugging, eventual ordering, async failure handling. Choose for pipelines/aggregations.
*   **Request-Driven (REST/gRPC):** Tight coupling, lower scalability, easy debugging, strong ordering, sync failure handling. Choose for APIs/real-time interactions.

**AA13**
A load balancer distributes incoming traffic across multiple servers.
*   **Layer 4:** Operates on TCP/UDP (IP/Port).
*   **Layer 7:** Operates on HTTP/HTTPS (URL/Headers).
*   **L7 Use Case:** Routing `/api` to backend A and `/static` to CDN based on content.

**AA14**
A message queue (RabbitMQ) is typically point-to-point or pub-sub with low latency and acknowledgments. A log-based broker (Kafka) is append-only, high throughput, and replayable.
*   **Pick MQ:** For task queues where order and delivery guarantee are critical.
*   **Pick Kafka:** For event streaming, analytics, and replayability.

**AA15**
A container packages code and dependencies into a lightweight unit sharing the host OS kernel. A VM includes a full guest OS.
Containers are popular for microservices due to higher density, faster startup times, and easier portability across environments compared to VMs.

**AA16**
Stateless services do not store data in memory (e.g., Web Servers). Stateful services store data (e.g., Databases).
Stateless services scale horizontally easily because any instance can handle any request. Stateful services require sticky sessions or complex replication to scale.

**AA17**
An ORM maps database tables to object classes (e.g., Hibernate for Java, Entity Framework for .NET).
Trade-offs: ORMs offer productivity and safety but can suffer from performance issues (N+1 queries) and abstraction leaks compared to raw SQL.

**AA18**
The Bulkhead pattern isolates resources (threads, CPU, memory) to prevent a failure in one part of the system from exhausting resources for others.
*   **Example:** Implement separate thread pools for database connections and external HTTP calls. If the external API fails, the DB thread pool remains available.

**AA19**
*   **OT:** Server-side conflict resolution, real-time, complex logic, no offline support.
*   **CRDTs:** Client-side conflict resolution, eventual consistency, simpler, supports offline editing.
*   **Choice:** CRDTs are chosen for offline editing because they allow local changes to be merged automatically without server intervention.

**AA20**
Challenges include context propagation (injecting Trace ID via W3C Trace Context headers), sampling (head-based for cost, tail-based for debugging), and storage (Jaeger/Tempo).
*   **Async/Kafka:** Trace ID must be injected into message headers. Consumers must propagate the ID to downstream services to maintain continuity.

## On-Premise Infrastructure Architecture (20 questions)

**OP1**
*   **Type 1 (Bare-metal):** Hypervisor runs directly on hardware (e.g., VMware ESXi, Xen).
*   **Type 2 (Hosted):** Hypervisor runs as an application on an OS (e.g., VMware Workstation, VirtualBox).

**OP2**
*   **SAN (Storage Area Network):** Block-level storage (e.g., iSCSI, Fibre Channel). Used for databases requiring direct disk access.
*   **NAS (Network Attached Storage):** File-level storage (e.g., NFS, SMB). Used for file sharing and backups.

**OP3**
A 3-tier architecture has Core (routing), Distribution (aggregation), and Access (servers).
Leaf-Spine is preferred in modern DCs because it provides equal latency between any two leaf nodes and eliminates broadcast domains, solving the scalability and latency bottlenecks of hierarchical 3-tier designs.

**OP4**
*   **Nodes:** Minimum 3 for quorum.
*   **Quorum:** Majority voting (2/3) to prevent split-brain.
*   **Fencing:** STONITH (Shoot The Other Node In) to isolate failed nodes.
*   **Storage:** Ceph (preferred for HA) or iSCSI/NFS (shared storage).
*   **Failure:** Cluster detects failure, re-balances resources, and fails over services.

**OP5**
VLAN trunking allows multiple VLANs over a single link. 802.1Q adds a 4-byte tag to Ethernet frames.
*   **Linux Config:** Use `ip link add link eth0 name eth0.10 type vlan id 10` to create sub-interfaces for each VLAN.

**OP6**
*   **RAID 1:** Mirror (2x capacity, high perf).
*   **RAID 5:** Striping + 1 parity (N-1 capacity).
*   **RAID 6:** Striping + 2 parity (N-2 capacity).
*   **RAID 10:** Mirror + Stripe (N/2 capacity, high perf).
*   **RAID Z2:** ZFS equivalent of RAID 6.
*   **Choice:** RAID 6 or ZFS RAID-Z2 for 6 drives. Best balance of capacity (4 usable drives) and fault tolerance (survive 2 drive failures).

**OP7**
*   **Recursive:** ISP resolver.
*   **Authoritative:** Internal/DMZ servers.
*   **Split-Horizon:** Internal clients query internal DNS; external query public.
*   **DNSSEC:** Signs zones to prevent spoofing.
*   **Laptop Move:** DHCP updates DNS records; Split-horizon ensures correct view based on source IP (Office vs. VPN).

**OP8**
*   **Chain:** Root CA (offline) -> Subordinate CA -> End Entity.
*   **CRL:** List of revoked certs (polling). OCSP: Real-time check.
*   **Compromise:** Root CA compromise revokes all certs (catastrophic). Subordinate compromise revokes only certs issued by that subordinate.

**OP9**
*   **MPLS:** High cost, reliable, low latency.
*   **IPsec:** Low cost, internet risk, variable latency.
*   **SD-WAN:** Smart routing, cost-effective, reliable.
*   **WireGuard:** Simple, mesh, high security.
*   **Recommendation:** SD-WAN for 50 users/site with VoIP (balance of cost, reliability, and latency).

**OP10**
iDRAC/iLO/IPMI are Out-of-Band Management interfaces (BMC).
Critical for remote reboot, console access, and hardware monitoring.
Exposing to the internet is a severe security risk (brute force attacks, remote code execution).

**OP11**
*   **LVM:** Logical volumes on physical disks.
*   **LVM-Thin:** Pool-based storage (overhead).
*   **ZFS:** Filesystem + Storage pool (integrity, compression).
*   **Snapshots:** LVM (copy-on-write), ZFS (efficient, integrated).
*   **Usage:** LVM for simple VM storage; ZFS for file servers/DBs needing integrity.

**OP12**
*   **Stretch Cluster:** Ceph clusters spanning two sites.
*   **CRUSH Rules:** Define data placement affinity.
*   **Latency:** Requires low latency (<10ms) for replication.
*   **Split-Brain:** Without a tiebreaker (3rd site), a network partition causes data loss. 2-site Ceph is bad without a tiebreaker.

**OP13**
DHCP assigns IP addresses. DORA: **D**iscover, **O**ffer, **R**equest, **A**cknowledge.
If unavailable, Windows clients use APIPA (169.254.x.x) and cannot communicate with the network.

**OP14**
*   **Unmanaged:** Plug-and-play, no config.
*   **Managed:** VLANs, QoS, ACLs, Port Security.
*   **Importance:** Managed switches are required for enterprise security and traffic prioritization.

**OP15**
NTP synchronizes system clocks.
Drift causes SSL certificate validation failures, log correlation issues, and cluster consensus failures (e.g., in Kubernetes or databases).

**OP16**
*   **Physical:** Bare metal hardware.
*   **VM:** Full OS abstraction.
*   **Container:** App abstraction.
*   **Bare Metal:** Used for high-performance DBs or workloads where hypervisor overhead is unacceptable.

**OP17**
*   **UPS:** Battery backup for short-term power loss (minutes).
*   **Generator:** Fuel-based for long-term power loss (hours).
*   **ATS:** Automatically switches power source between utility, UPS, and generator.

**OP18**
*   **Active-Passive:** One node serves, one standby.
*   **Active-Active:** Both nodes serve traffic.
*   **Pacemaker/Corosync:** Manages fencing (STONITH) to prevent split-brain. Virtual IPs (VIP) float to the active node.

**OP19**
*   **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite.
*   **Backup vs DR:** Backup is data protection; DR is business continuity (infrastructure + data recovery).
*   **Strategy:** Full/Diff/Inc backups, deduplication, immutable backups (WORM) for ransomware, regular restore testing.

**OP20**
*   **Roles:** Supplicant (Client), Authenticator (Switch), Auth Server (RADIUS).
*   **EAP:** EAP-TLS (Certificate-based), PEAP (Password).
*   **Failure:** Port is blocked until auth succeeds.
*   **MAB:** Authenticates devices (printers) using MAC address if 802.1X supplicant is missing.
