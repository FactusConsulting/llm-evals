T1 — Easy: What is the difference between tofu plan and tofu apply?
`tofu plan` calculates the execution plan and displays what changes will be made without applying them. `tofu apply` executes the plan, making the actual changes to the infrastructure and updating the state file.

T2 — Easy: What is state in OpenTofu, and why is remote state important?
State is a JSON file tracking the mapping between infrastructure resources and Terraform-managed objects. Remote state is important for team collaboration (preventing concurrent modifications), security (keeping state out of local machines), and portability (allowing state to be moved between environments).

T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?
`count` uses an index (0, 1, 2...) and creates resources in a list. `for_each` uses a map or set of keys and creates resources keyed by those values. `for_each` is preferred when resource uniqueness matters (e.g., names) or when you want to avoid index-based logic errors.

T4 — Medium: What happens if you manually change a resource outside of OpenTofu? How does OpenTofu detect and handle this?
This is called "drift." OpenTofu detects it during `tofu plan` by comparing the state file against the actual cloud resources. It handles it by proposing a `refresh` to update the state or suggesting a `destroy/recreate` to fix the resource.

T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).
```hcl
resource "aws_instance" "web_servers" {
  for_each = toset(["web1", "web2", "web3"])
  ami      = "ami-12345678"
  instance_type = "t2.micro"
  tags = {
    Name = each.key
  }
}
```

T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?
`terraform_remote_state` reads the *state file* of another Terraform run to access resources. `output` values are just values defined in a module. The recommended alternative is using a shared state backend (if modules are in the same workspace) or a dedicated data source module to avoid coupling root modules to specific state files, which improves modularity and testing.

T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix.
**Why:** `remote-exec` runs during resource creation, but the output is often empty or unavailable until the provisioner finishes, causing dependent resources to fail immediately.
**Fix:** Use `local-exec` provisioner to write the kubeconfig to a file path, then use a `file` data source or `template_file` provider in the dependent resource to read that file path.

T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?
`tofu import` copies an existing cloud resource into the state file. Limitations include schema mismatches and inability to import complex resources easily. The `import` block (1.5+) allows declarative import configuration within the code, making it easier to manage and version control compared to the CLI command.

T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?
A variable is an input value passed to a module or configuration. An `output` is a value exposed by a module or configuration that can be consumed by other modules or the root configuration.

T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?
A provider is a plugin that interacts with a specific cloud API (e.g., AWS, Azure). If you run `tofu plan` without `tofu init`, Terraform fails because the provider binaries are not downloaded and configured.

T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?
It locks provider versions to ensure consistency across environments. It should be committed to prevent "dependency drift" where different environments use different provider versions, causing plan failures or security issues.

T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?
`tofu destroy` removes all resources managed by the state. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.
A data source reads existing infrastructure or data without managing it. Use it when the resource already exists (e.g., `aws_ami` to find an existing AMI) or when you need to query external data (e.g., `aws_caller_identity`).

T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?
`locals` are computed values within a module. `variables` are inputs. Use `locals` for derived values (e.g., concatenating strings) to avoid passing unnecessary inputs to modules.

T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.
`lifecycle` controls resource behavior. `create_before_destroy` ensures zero downtime for stateful resources (e.g., load balancers). `prevent_destroy` protects resources from accidental deletion (e.g., production DB). `ignore_changes` prevents drift on specific attributes (e.g., tags managed externally).

T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?
`moved` tells Terraform that a resource has been renamed or moved to a new address. It helps Terraform update the state file to match the new path without deleting and recreating the underlying resource.

T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?
The graph orders resources based on references. Implicit dependencies are inferred from resource references (e.g., `aws_instance.id`). Explicit dependencies use `depends_on`. `depends_on` forces execution order, reducing parallelism. Use sparingly because it can slow down plans and applies unnecessarily.

T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.
1. `tofu plan -refresh=false`: Skips cloud API calls. Tradeoff: Might miss drift.
2. `tofu plan -target=...`: Plans only specific resources. Tradeoff: Doesn't show full plan.
3. `tofu state rm`: Removes unused resources from state. Tradeoff: Loses tracking of those resources.
4. `tofu workspace`: Split state into workspaces. Tradeoff: More complex state management.

T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?
Locking prevents concurrent state modifications. If a lock is not released, subsequent runs fail. Manual break depends on the backend (e.g., delete the lock file in S3/DynamoDB). Risk: Concurrent state corruption or data loss if multiple users apply simultaneously.

T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.
1. Create new backend config in `backend` block.
2. Run `tofu state pull` to download existing state to local.
3. Run `tofu init` with the new backend configuration.
4. Run `tofu state push` to upload state to the new backend.
5. Verify by running `tofu state list` and checking the remote backend console.

A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?
A playbook is a collection of plays (tasks executed on hosts). A role is an organized structure of tasks, handlers, vars, and files. A task is a single action (e.g., install a package).

A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?
`ansible_facts` is a dictionary of system information gathered by Ansible. Access OS family via `ansible_facts['os_family']`.

A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?
`command` runs a binary without shell parsing. `shell` runs a command with shell parsing (e.g., pipes). `raw` runs a command without privilege escalation (no sudo). Use `command` for binaries, `shell` for scripts/pipes, `raw` for unprivileged execution.

A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.
Ansible checks if a task needs to run before executing. `yum install httpd` is idempotent (only installs if missing). `echo "hello"` is not idempotent (always runs).

A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?
Priority (highest to lowest): `--extra-vars` > `host_vars` > `group_vars` > `role defaults` > `role vars` > `role files`. `set_fact` is runtime and overrides everything.

A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?
`ansible-vault` encrypts content. To encrypt a single variable, use `ansible-vault encrypt_string` and paste the output into the variable, or use `ansible-vault create` for the whole file. For single variable, use `ansible-vault encrypt_string` and assign the encrypted string to the variable.

Inventory lists hosts and groups. Static inventory is a file (e.g., `hosts.ini`). Dynamic inventory is generated by a script/API (e.g., cloud provider).

A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?
A handler runs only if notified by a task. Regular tasks run unconditionally or based on conditions. Trigger via `notify: handler_name` in a task.

A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.
Configures Ansible behavior. Settings: `inventory`, `forks`, `timeout`.

A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?
`register` stores task output in a variable. Use it in subsequent tasks via `{{ registered_variable.stdout }}` or `{{ registered_variable.rc }}`.

A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?
`include_tasks` is dynamic (evaluated at runtime), allowing conditionals. `import_tasks` is static (evaluated at compile time), no conditionals. Use `include` for conditional inclusion.

A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?
Ansible Galaxy is a repository of roles/collections. Use `ansible-galaxy install -r requirements.yml` to install from a file listing roles/collections.

A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?
Connection plugins define how Ansible talks to hosts. `ssh` for remote Linux hosts. `local` for control node tasks. `network_cli` for network devices (e.g., Cisco IOS).

A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.
`delegate_to: localhost` runs task on control node. `run_once: true` runs once per group. Example: Gather facts on remote host, then run a task on localhost to process those facts.
