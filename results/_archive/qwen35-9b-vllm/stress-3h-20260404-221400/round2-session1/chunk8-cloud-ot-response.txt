**CL1**
IaaS (Infrastructure as a Service) provides virtualized computing resources (servers, storage, networking) without managing the underlying hardware. Example: AWS EC2. PaaS (Platform as a Service) provides a platform allowing developers to build and run applications without managing infrastructure. Example: Azure App Service. SaaS (Software as a Service) delivers software applications over the internet on a subscription basis. Example: Microsoft 365.

**CL2**
The Shared Responsibility Model defines security boundaries. For IaaS VMs, the provider secures the physical infrastructure and hypervisor; the customer secures the OS, data, and applications. For managed Kubernetes, the provider secures the control plane (API server, etcd); the customer secures the worker nodes, workloads, and network policies. For SaaS (e.g., M365), the provider manages the entire stack including application security; the customer manages identity, data, and usage policies.

**CL3**
A VPC is a logical isolation boundary for resources. A subnet is a range of IP addresses within a VPC. A Security Group (SG) is a stateful firewall attached to an instance (allows return traffic automatically). A Network ACL (NACL) is a stateless firewall attached to a subnet (must explicitly allow return traffic). Layering: VPC contains Subnets; Subnets have NACLs; Instances have SGs. Stateful filtering (SG) remembers connection state; Stateless filtering (NACL) evaluates every packet independently.

**CL4**
A Landing Zone provides a standardized, secure foundation for cloud accounts. Organizational Units (OUs) group accounts for policy management. Guardrails enforce compliance (e.g., via SCPs). Shared networking uses a Hub-and-Spoke model (Transit Gateway/Azure Hub) to connect accounts. Centralized logging aggregates logs (e.g., CloudTrail) for visibility. A single-account approach is problematic due to resource limits, billing complexity, security scope, and lack of isolation between workloads.

**CL5**
Infrastructure as Code (IaC) manages infrastructure via code. Terraform/OpenTofu uses a declarative state file (HCL) and is provider-agnostic. Pulumi uses a programming language (TypeScript/Python) for IaC. CloudFormation/Bicep are native, declarative tools for AWS/Azure respectively. Crossplane uses Kubernetes Custom Resources to manage cloud infrastructure. Choose Terraform for multi-cloud; Pulumi for developer preference; Native tools for deep provider integration; Crossplane for K8s-native operations.

**CL6**
HPA scales the number of pods based on metrics (CPU/Memory). VPA scales pod resource requests/limits. Cluster Autoscaler adds/removes nodes based on pod demand. KEDA scales based on external events (e.g., queue depth, HTTP requests). Use KEDA over HPA when load is driven by external events rather than resource utilization, allowing for more efficient scaling of event-driven workloads.

**CL7**
RPO (Recovery Point Objective) is data loss tolerance; RTO (Recovery Time Objective) is downtime tolerance. Active-Active replicates data and traffic to both regions (high cost, high resilience). Active-Passive keeps one region active (lower cost). Pilot Light (cold standby) spins up resources only on failure. Warm Standby (partial active) keeps resources running at reduced capacity. Multi-site Active-Active (hot standby) runs full capacity in both regions. Cost increases significantly with Active-Active.

**CL8**
GitOps uses Git as the single source of truth for infrastructure and application state. ArgoCD and FluxCD are controllers that sync cluster state to Git. Secrets are managed via Sealed Secrets, External Secrets Operator, or HashiCorp Vault integration. If manual changes drift from Git, the controller detects the difference and automatically reverts the cluster to the Git state (self-healing).

**CL9**
Use a StatefulSet for ordered, stable pod identities. Use a Local Persistent Volume (LocalPath) for low-latency local storage. Use a Headless Service for DNS-based service discovery (no load balancing). Use Init Containers to prepare the filesystem or fetch config. Mount ConfigMaps as volumes for config files. Use Pod Disruption Budgets to ensure availability during voluntary scaling or maintenance.

**CL10**
A Service Account is a K8s identity for pods. Workload Identity (e.g., Azure/AKS) binds K8s identities to cloud identities. IRSA (IAM Roles for Service Accounts) is an AWS-specific implementation of Workload Identity. Mounting cloud credentials in a pod is bad practice because it requires rotating secrets and risks exposure. Workload Identity federation allows pods to assume cloud roles without storing credentials.

**CL11**
Object storage (S3/Blob) stores unstructured data (files) with high durability (11 9s) and availability (99.999999999%). Block storage (EBS/Managed Disk) provides low-latency disk access for VMs (99.99% availability). File storage (EFS/Azure Files) provides shared file systems for multiple nodes (99.9% availability). Use Object for data lakes/media; Block for databases/VMs; File for shared app data.

**CL12**
Zero Trust assumes no implicit trust. Implement Network Policies (deny-all default), Service Mesh (mTLS for pod-to-pod), Pod Identity, Admission Controllers (OPA/Kyverno), Image Signing (Cosign), Runtime Security (Falco), and Secrets Management (Vault). This differs from perimeter security by verifying identity and context for every request, rather than trusting traffic inside the network boundary.

**CL13**
A CDN caches content at edge locations closer to users to reduce latency. Services: AWS CloudFront, Azure CDN. Use a CDN for static assets (images, CSS) and high-traffic content to reduce origin load. Serve content directly from the origin for dynamic, personalized content where caching is not beneficial or security is critical.

**CL14**
Regions are geographic areas with data centers. Availability Zones (AZs) are isolated locations within a region with independent power/network. Deploy across AZs for High Availability (HA) to survive zone failures. Zonal resources are restricted to one AZ; Regional resources span multiple AZs.

**CL15**
A managed database service (e.g., RDS, Cloud SQL) abstracts database administration. The provider handles patching, backups, high availability (multi-AZ), and scaling. Running on a VM requires the user to manage OS, database software, patches, backups, and HA configuration manually.

**CL16**
Cloud Identity services include Users (individuals), Groups (collections), Roles (permissions), and Policies (rules). The Principle of Least Privilege means granting only the minimum permissions necessary to perform a task. Apply this by using Roles with scoped policies and avoiding attaching users directly to resources where possible.

**CL17**
Serverless computing executes code in response to events without managing servers. AWS Lambda, Azure Functions, and Google Cloud Functions are examples. Cold starts occur when a function is invoked for the first time or after inactivity, causing latency. Serverless is a poor fit for long-running processes or latency-sensitive applications requiring consistent performance.

**CL18**
Ingress resources manage external access to K8s services. Gateway API is the newer, standard K8s API for Ingress. Cloud Load Balancer annotations delegate traffic to the cloud provider's L7 LB. Service Mesh ingress gateways handle mTLS and traffic policies. TLS termination occurs at the Cloud LB (offloading K8s) or at the Ingress Controller (K8s handles TLS). Use Gateway API for multi-tenant environments or when strict standardization is required.

**CL19**
Cost optimization involves Reserved Instances/Savings Plans (commitment discounts), Spot/Preemptible instances (variable cost), Right-sizing (matching resources to load), Storage Tiering (moving infrequent data to cheaper storage), and Idle Resource detection. FinOps practices include tagging resources and implementing showback/chargeback models. Tools: AWS Cost Explorer, CloudHealth, or Azure Cost Management.

**CL20**
Multi-cloud strategy uses abstraction layers (Kubernetes) to unify runtime, Terraform for portable IaC, and Direct Connect/ExpressRoute for networking. Identity federation (OIDC) allows single sign-on. Trade-offs include higher complexity and cost vs. vendor lock-in avoidance and resilience. Multi-cloud is justified for compliance requirements or avoiding single-vendor outages; it is unnecessary complexity if workloads are identical and one provider is sufficient.

**OT1**
The Purdue Model (ISA-95) defines security zones for industrial automation. Level 0: Field Devices (sensors/actuators). Level 1: Basic Process Control System (PLCs/Controllers). Level 2: Supervisory Control and Data Acquisition (SCADA/HMI). Level 3: Enterprise Control System (MES). Level 4: Business/Enterprise Systems (ERP). Level 5: IT/Corporate Network.

**OT2**
IT networks prioritize data availability and confidentiality; OT networks prioritize safety and reliability. Standard IT patching (remote updates, reboots) can cause downtime or destabilize critical control systems. OT systems often run legacy hardware that cannot be patched or rebooted without risking physical safety or production loss.

**OT3**
An Industrial DMZ (IDMZ) separates IT and OT networks. Traffic flows from OT to IT (e.g., data export) are allowed; traffic from IT to OT (e.g., remote control) is restricted or heavily filtered. Direct connectivity from Level 4 (IT) to Level 1 (Control) is dangerous because it exposes critical control systems to IT vulnerabilities (e.g., malware, phishing) without an intermediate security boundary.

**OT4**
1. Modbus TCP: Operates at Level 1 (Control). 2. OPC UA: Operates at Level 1 and 2 (Control/Supervisory). 3. EtherNet/IP (CIP): Operates at Level 1 (Control). 4. PROFINET: Operates at Level 1 (Control). 5. MQTT: Operates at Level 2 and 3 (Supervisory/Enterprise) for telemetry.

**OT5**
A data diode allows traffic in only one direction (e.g., OT to IT), physically or logically preventing return traffic. A firewall allows bidirectional traffic based on rules. Use a hardware data diode for critical data export where no return path is needed (e.g., sending production data to the cloud). The limitation is the inability to send commands or updates back to the OT environment.

**OT6**
Data flow: PLCs push data to a Historian (Level 1). The Historian exports data to an Edge Gateway (Level 2). The Gateway pushes data via MQTT to a Cloud Ingestion service (Level 3/4). Security boundaries are placed at the Edge Gateway (DMZ) to prevent direct cloud access from OT devices and to filter traffic before it leaves the plant.

**OT7**
A Zone is a network segment containing assets with similar security requirements. A Conduit is a connection between zones (e.g., firewall, gateway). Zone-and-Conduit Model: Zone 1 (Corporate/IT), Zone 2 (Engineering), Zone 3 (SCADA/Supervisory), Zone 4 (PLCs/Field). Conduits connect Zone 1-2, 2-3, and 3-4 with strict firewall rules. SIS is often in a separate, isolated zone.

**OT8**
Strategy: Segment the flat Layer 2 network into VLANs per production line and function (Engineering, SCADA, PLCs). Place firewalls between VLANs. Use Layer 3 switches for routing. Remote vendor access uses a Jump Host with MFA. Transition without stopping production by migrating line-by-line or using parallel networks with gradual cutover.

**OT9**
SIS (Safety Instrumented Systems) stops processes to prevent hazards; BPCS (Basic Process Control System) manages normal operations. IEC 61511 defines the functional safety lifecycle. The SIS network must be air-gapped or isolated because a ransomware attack on the BPCS could be used to disable safety systems, leading to catastrophic physical damage or loss of life.

**OT10**
A PLC is for discrete control in smaller systems. A DCS is for continuous process control in large plants. A SCADA system monitors and controls geographically dispersed assets. They can coexist; PLCs often feed data to a SCADA system, which feeds to a DCS or Enterprise system.

**OT11**
Remote access should use a Jump Host (Bastion) with MFA and session recording. Vendor access is time-limited and restricted to specific assets. RDP directly to an HMI is unacceptable because it bypasses security controls, exposes the HMI to the internet, and prevents audit trails of operator actions.

**OT12**
Detection: Use IDS/IPS and anomaly detection to identify lateral movement. Response: Isolate the compromised network segment logically (not physically if possible) to prevent spread. Notify the control room immediately. Coordination: IT isolates the threat; OT operators maintain safe operations (manual overrides if needed). The plant operator's role is safety first, ensuring physical safety over IT containment.

**OT13**
An HMI is the interface for operators to monitor and control the process. An Engineering Workstation is used for configuration, design, and maintenance of the control system. The HMI is for runtime operation; the Engineering Workstation is for development and tuning.

**OT14**
A historian stores time-series process data (tags, values, timestamps). It is important for trend analysis, compliance, and troubleshooting. A Plant Historian (Level 3) stores operational data for the plant. An Enterprise Historian (Level 4) aggregates data from multiple plants for business analysis.

**OT15**
Ladder Logic is a programming language resembling relay logic diagrams. It is executed by PLCs. It remains dominant because industrial electricians and engineers are trained on it, and it is intuitive for representing physical control logic.

**OT16**
An RTU (Remote Terminal Unit) is a ruggedized controller for remote locations, often using serial communication. A PLC is typically used in local control rooms with Ethernet. Deploy RTUs in harsh environments (oil/gas, mining) where Ethernet infrastructure is unavailable or unreliable.

**OT17**
Analog signals represent continuous values (e.g., pressure, temperature). 4-20mA is preferred over 0-20mA because it provides a "live zero" (4mA indicates a valid signal, 0mA indicates a broken wire), improving fault detection and noise immunity.

**OT18**
Asset inventory is the foundation of OT security, identifying what needs protection. Tools include passive network monitoring (sniffing traffic) and active scanning (pinging). Active scanning is dangerous because it can disrupt real-time control loops or trigger safety systems.

**OT19**
MITRE ATT&CK for ICS maps adversary tactics to industrial environments. Tactics include: Reconnaissance (e.g., T1590.001 - Industrial Protocol Enumeration), Execution (e.g., T1190.001 - Industrial Protocol Exploitation), Persistence (e.g., T1590.002 - Industrial Device Persistence), Privilege Escalation (e.g., T1590.003 - Industrial Device Privilege Escalation), and Exfiltration (e.g., T1590.004 - Industrial Data Exfiltration). It differs from Enterprise ATT&CK by focusing on industrial protocols and safety impacts.

**OT20**
Log collection uses agents or syslog to capture OT logs without impacting performance. SIEM integrates these logs with IT logs. OT-specific rules detect anomalies (e.g., unexpected protocol commands). Staffing requires OT engineers to triage alerts, as IT analysts may not understand process safety implications. For unauthorized firmware changes, verify the integrity (hash), isolate the device, and consult the vendor before restoring.
