G1 — Slices are dynamic views into arrays (length and capacity), while arrays are fixed-size value types. Appending to a slice checks capacity; if exceeded, the underlying array is reallocated (copied) to a larger buffer, and the slice header is updated.

G2 — `var x int` declares a variable with a zero value (0) but does not initialize it in the declaration line. `x := 0` is a short declaration that initializes `x` to 0. You cannot use `:=` in global scope (package level) or if a variable with the same name already exists in the current scope.

G3 — A goroutine is a lightweight thread managed by the Go runtime (M:N scheduling), whereas an OS thread is a heavy kernel resource (1:1). The GMP model consists of G (goroutine), M (machine/OS thread), and P (processor/worker). The scheduler maps Gs to Ps, and Ps to Ms, allowing thousands of goroutines to run on fewer OS threads.

G4 — Channels allow communication between goroutines. Unbuffered channels block until a sender and receiver are ready simultaneously. Buffered channels store up to `N` values. Sending to a full buffered channel blocks the sender until space is available.

G5 — The `context` package manages request-scoped values (cancellation, deadlines, values).
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
resp, err := http.Get(ctx, "https://example.com")
```

G6 — Go uses duck typing (implicit satisfaction), whereas Java/C# require explicit interface declarations. `interface{}` (or `any` in Go 1.18+) accepts any type, enabling generic-like flexibility but sacrificing compile-time type safety, leading to runtime panics if type assertions fail.

G7 — This is unsafe due to a data race: `ready` and `data` are shared without synchronization. The main thread may read `data` before the goroutine writes it. Correct alternatives: use `sync.Mutex` to protect writes/reads, `sync.WaitGroup` to wait for completion, or `atomic.Bool`/`atomic.Value` for visibility.

G8 — `sync.Mutex` allows only one writer; `sync.RWMutex` allows multiple readers but exclusive writers. `sync.Map` is optimized for concurrent reads with sparse writes (no locking for reads), whereas a regular map with a mutex is better for high write contention or dense data.

G9 — Go modules manage dependencies. `go.mod` declares the module path and requirements; `go.sum` stores checksums for security. `go mod tidy` cleans up unused dependencies and updates versions. MVS (Minimum Version Selection) picks the lowest version satisfying all constraints.

G10 — `defer` schedules a function call to run when the surrounding function exits. Multiple defers execute in LIFO (Last-In, First-Out) order. A common gotcha is capturing loop variables in a deferred function, causing all closures to share the same variable value.

G11 — A pointer holds the memory address of a value (`*T`). The zero value is `nil`. To create a pointer to a struct literal: `var p *MyStruct = &MyStruct{Field: "value"}`.

G12 — `init()` runs before `main()` to initialize package-level variables. A package can have multiple `init()` functions (e.g., in different files); they execute in alphabetical order of the filename.

G13 — `make` initializes slices, maps, and channels (allocating underlying storage). `new` allocates zeroed memory and returns a pointer (`new(T)` is `&T{}`). `make` does not work for pointers or structs directly.

G14 — Errors implement the `error` interface (`Error() string`). The idiomatic check is `if err != nil`. `errors.Is` checks if an error wraps a specific target error; `errors.As` type-asserts an error to a specific type.

G15 — Composite types: `map[K]V` (zero: `nil`), `slice` (zero: `nil`), `channel` (zero: `nil`), `struct` (zero: fields set to their zero values).

G16 — A race condition occurs when two goroutines access shared data concurrently without synchronization. The `-race` flag uses a thread sanitizer to detect unsynchronized access. Fix: protect shared data with `sync.Mutex` or use channels for communication.

G17 — `select` handles multiple channel operations like a switch. If multiple cases are ready, one is chosen randomly. To implement a timeout, use a `select` with a `time.After` case alongside channel operations.

G18 — Escape analysis determines if a variable lives on the stack or heap. If a variable is referenced outside the function (e.g., stored in a map or returned), it escapes to the heap. Inspect with `go build -gcflags="-m"`. It matters because heap allocation incurs GC overhead.

G19 — `reflect.Type` describes a type; `reflect.Value` holds the data. Reflection is slow due to dynamic dispatch and indirection. It is justified for configuration, serialization, or generic-like behavior where generics aren't available, but code generation is preferred for performance.

G20 — `go:embed` embeds files at compile time. It supports single files, directories, and file systems (`io/fs.FS`). Limitations include path resolution (must be relative to the package) and inability to embed external URLs.

R1 — Ownership ensures memory safety. Rules: 1. Each value has a single owner. 2. When the owner goes out of scope, the value is dropped. 3. You can have multiple references, but only one mutable reference at a time.

R2 — `String` is an owned, heap-allocated UTF-8 string. `&str` is a borrowed slice of UTF-8 bytes. Use `String` when you need to own the data; use `&str` for function arguments to avoid unnecessary copies.

R3 — Borrowing allows accessing data without ownership. Immutable references (`&T`) allow reading; mutable (`&mut T`) allow writing. Rules: no aliasing (two mutable refs), no mutable ref while immutable ref exists.

R4 — `Result<T, E>` holds success (`Ok`) or failure (`Err`). `Option<T>` holds `Some` or `None`. `?` propagates errors/panics.
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)?
}
```

R5 — `Box<T>` is a heap-allocated pointer (single owner). `Rc<T>` is a thread-local reference-counted pointer. `Arc<T>` is a thread-safe reference-counted pointer. Use `Box` for single ownership on heap; `Rc` for single-thread sharing; `Arc` for multi-thread sharing.

R6 — Traits define behavior. Go interfaces are dynamic (vtable); Rust traits are static (monomorphized) unless using `dyn Trait`. `dyn Trait` enables dynamic dispatch (like Go); `T: Trait` enables static dispatch (generics).

R7 — This fails because `x` and `y` have independent lifetimes, but the return type references one of them. Fix:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

R8 — `Send` means a type can be moved across threads; `Sync` means it can be shared. `Rc<T>` is not `Send` because ref counts are not atomic. `Arc<T>` uses atomic ref counts, making it `Send` and `Sync`.

R9 — Rust async uses state machines (Futures) rather than OS threads. A `Future` is a type that yields a value later. An executor (e.g., Tokio) drives these futures. Unlike Go goroutines, Rust async tasks are cooperative and lightweight, avoiding OS thread overhead.

R10 — `unsafe` blocks allow undefined behavior. Examples: dereferating raw pointers (`*const T`), reading from pointers (`ptr::read`), or calling FFI (`extern "C"`). Justified when interfacing with C or when performance requires bypassing safety checks.

R11 — `match` is exhaustive (must cover all cases). `if let` is partial. The compiler enforces that `match` covers all possible enum variants; otherwise, it fails to compile.

R12 — `Vec<T>` is a growable heap array. `[T; N]` is a fixed-size stack array. When `Vec` capacity is exceeded, it allocates a larger buffer and copies elements (usually doubling capacity).

R13 — Rust enums are tagged unions (data + tag). C/Java enums are typically just integer constants. `Option<T>` is an enum with `Some(T)` and `None`. Rust has no null; `Option` replaces it to prevent null pointer dereferences.

R14 — `impl` defines methods for a type. `&self` borrows immutably; `&mut self` borrows mutably; `self` takes ownership. Associated functions (e.g., `String::new`) take `&Self` or no self and are called on the type itself.

R15 — `derive` generates code for traits. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. You cannot derive if the type contains fields that don't implement the trait or if the trait requires custom logic not covered by the default implementation.

R16 — `Cow<'a, T>` (Clone on Write) holds a reference if immutable, or a clone if mutable. Useful for avoiding allocations when processing strings that are mostly borrowed (e.g., `Cow::Borrowed`).

R17 — `mod` declares a module; `use` imports items; `pub` makes items public. Files map to modules (filename `foo.rs` -> `foo` module). Rust 2018 changed path resolution to allow `mod foo;` to find `foo.rs` or `foo/mod.rs`.

R18 — `Pin<P>` prevents a type from being moved, ensuring references inside it remain valid. Needed for self-referential structs or async tasks where the type might be moved (breaking the reference). `Unpin` allows moving a pinned type.

R19 — Declarative macros (`macro_rules!`) are text substitution. Procedural macros (derive, attribute, function) are Rust code that generates code. Hygiene rules ensure macros don't pollute the global namespace (e.g., `!` is special).

R20 — Zero-cost abstractions mean high-level code compiles to the same machine code as hand-written low-level code. Iterators are specialized at compile time (monomorphization). Generics are specialized (no virtual dispatch). Traits use static dispatch (no vtable lookup) when used with generics.
