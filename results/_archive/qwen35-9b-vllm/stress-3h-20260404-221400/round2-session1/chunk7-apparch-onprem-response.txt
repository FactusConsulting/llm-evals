AA1 — Easy: A monolith is a single codebase deployed as one unit, while microservices are modular, independently deployable services communicating via APIs. Three concrete problems microservices introduce: 1) Distributed transactions (complexity of consistency), 2) Network latency and failure points (inter-service communication), 3) Operational complexity (orchestrating deployments, monitoring, and debugging across many services).

AA2 — Easy: Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/gRPC). Asynchronous communication involves fire-and-forget or callback patterns where the caller does not wait (e.g., Message Queues like RabbitMQ/Kafka).

AA3 — Medium: An API Gateway handles business logic (auth, rate limiting, transformation), while a reverse proxy handles traffic routing and SSL termination. An API Gateway cannot entirely replace a reverse proxy because the reverse proxy often sits at the network edge (L4) for load balancing and SSL offloading, whereas the Gateway sits at the application layer (L7).

AA4 — Medium: The Saga pattern manages long-running transactions across services by breaking them into local transactions. Choreography involves services publishing events that trigger the next step (decentralized). Orchestration involves a central coordinator telling services what to do (centralized). Choreography is better for loosely coupled systems; Orchestration is better for complex workflows requiring rollback control.

AA5 — Medium: CQRS separates read and write operations into different models. It is paired with Event Sourcing to store state as a sequence of events. This combination solves the problem of read/write performance mismatches and complex query requirements that a traditional CRUD model (single shared state) cannot handle efficiently at scale.

AA6 — Medium: Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failures detected, calls blocked), Half-Open (testing recovery). It differs from retry with backoff because it stops calling entirely when failure is persistent. Use both together: Retry for transient errors, Circuit Breaker to stop retrying when the service is dead.

AA7 — Hard:
1. **Shared DB, Shared Schema:** Lowest cost, highest operational complexity, high noisy-neighbor risk, lower security (data leakage via SQL injection).
2. **Shared DB, Separate Schema:** Medium cost, better isolation, moderate ops complexity, better security than #1.
3. **Separate DB:** Highest cost, best isolation/security, highest ops complexity (provisioning/backup), lowest noisy-neighbor risk.
*Recommendation:* Start with #1 for MVP, move to #2 or #3 as scale/security requirements increase.

AA8 — Hard: Eventual consistency allows data to converge over time; strong consistency guarantees immediate visibility. For inventory (never oversell), strong consistency is required. Architecture: Use a distributed database (e.g., PostgreSQL with row-level locking) or a transactional message queue (e.g., Kafka with transactional outbox) combined with optimistic locking or distributed locks (Redis/Zookeeper) to prevent concurrent writes from exceeding stock.

AA9 — Hard: A sidecar proxy runs alongside the application to handle networking. In Istio, Envoy is the sidecar. Data plane = Envoy (handles traffic); Control plane = Istiod (manages Envoy config). mTLS between sidecars solves the problem of managing TLS certificates in application code; it enables zero-trust service-to-service communication without app changes.

AA10 — Medium: The Strangler Fig pattern migrates legacy systems by gradually routing new functionality to new services. Strategy: Place an API Gateway in front of the .NET Framework monolith. Identify a feature (e.g., "User Profile"), implement it in .NET 8, and update the Gateway to route that feature to the new service. Repeat until the monolith is fully decomposed.

AA11 — Medium: 12-Factor App is a methodology for building cloud-native apps. 6 Factors: 1) Codebase (versioned), 2) Dependencies (explicit), 3) Config (env vars), 4) Backing Services (treated as resources), 5) Build/Release/Run (distinct phases), 6) Dev/Prod Parity (same environment). They matter for portability, scalability, and security.

AA12 — Hard: **Event-Driven (Kafka):** Decoupled, high scalability, complex debugging, eventual ordering, async failure handling. **Request-Driven (REST/gRPC):** Tight coupling, lower scalability, easier debugging, strong ordering, sync failure handling. Choose Event-Driven for audit trails, decoupling, and high throughput. Choose Request-Driven for real-time user interactions and simple APIs.

AA13 — Easy: A load balancer distributes traffic across servers. Layer 4 (TCP/UDP) balances based on IP/Port. Layer 7 (HTTP/HTTPS) balances based on content/URL. Layer 7 is required when routing traffic based on URL paths (e.g., `/api` to backend, `/static` to CDN).

AA14 — Easy: A message queue (RabbitMQ) supports point-to-point and pub/sub with guaranteed delivery. A log-based broker (Kafka) is append-only, high-throughput, and supports replay. Pick RabbitMQ for transactional messaging (e.g., order processing). Pick Kafka for event streaming and analytics (e.g., user activity logs).

AA15 — Easy: A container packages code and dependencies with a lightweight OS layer (shares host kernel). A VM includes a full OS and hypervisor. Containers are popular for microservices because they are lightweight, start faster, and use fewer resources than VMs.

AA16 — Easy: Stateless services do not store data in memory (e.g., Web Servers). Stateful services store data (e.g., Databases). Stateless services scale horizontally because any instance can handle any request without coordination.

AA17 — Easy: An ORM maps database tables to object classes. Examples: Entity Framework (.NET), Hibernate (Java). Trade-offs: ORMs improve productivity and safety but can lead to performance issues (N+1 queries) and reduced SQL flexibility compared to raw SQL.

AA18 — Medium: The Bulkhead pattern isolates resources (threads, CPU, memory) to prevent one failure from exhausting system resources. Example: Allocate separate thread pools for database connections and external API calls. If the external API fails, the DB thread pool remains available.

AA19 — Hard: **OT:** Server-side conflict resolution, complex, requires connectivity. **CRDTs:** Client-side, mathematically guaranteed convergence, supports offline. CRDTs are chosen for offline editing because they allow local changes to be merged automatically when connectivity is restored without complex server-side reconciliation.

AA20 — Hard: Distributed tracing propagates context (TraceID/SpanID) via headers (W3C Trace Context). Sampling: Head-based (start of request) vs Tail-based (end of request). Storage: Jaeger/Tempo. Async messaging: Correlate spans using message headers. Kafka continuity: Use consumer group IDs or custom headers to link producer and consumer spans, ensuring the trace continues across the broker.

OP1 — Easy: Type 1 (Bare-metal) runs directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) runs on top of an OS (e.g., VMware Workstation, VirtualBox).

OP2 — Easy: SAN (Storage Area Network) provides block storage (iSCSI, Fibre Channel) for high-performance DBs. NAS (Network Attached Storage) provides file storage (NFS, SMB) for file sharing. Use SAN for databases; NAS for general file storage.

OP3 — Medium: 3-tier (Core, Distribution, Access) separates traffic layers. Leaf-Spine is preferred in modern DCs because it provides equal path latency and higher scalability (non-blocking) compared to the hierarchical bottleneck of 3-tier.

OP4 — Medium: Proxmox HA cluster needs 3+ nodes for quorum. Use Ceph for shared storage (preferred over iSCSI/NFS for HA). Fencing (STONITH) prevents split-brain. On node failure, the cluster reboots the failed node or promotes a standby, and storage remains accessible via remaining nodes.

OP5 — Medium: VLAN trunking carries multiple VLANs over a single link using 802.1Q tags. On Linux, use `ip link add link eth0 name eth0.10 type vlan id 10` to create a sub-interface for VLAN 10 on a single NIC.

OP6 — Hard: RAID 1 (Mirror), 5 (Striping+Parity), 6 (2 Parity), 10 (Striping+Mirror), Z2 (ZFS Mirror+RAIDZ2). For 6 drives DB: RAID 10 or ZFS RAIDZ2. RAID 10 offers best performance but lowest capacity (50%). ZFS RAIDZ2 offers better capacity (4 drives usable) with good fault tolerance (2 drive failure). Choose ZFS RAIDZ2 for capacity/perf balance.

OP7 — Hard: **Architecture:** Recursive resolvers (ISP) query internal authoritative servers. Internal AD handles internal DNS. DMZ hosts public services. Split-horizon: Internal zone (AD) vs External zone (Public). DNSSEC signs external zones. **Laptop Move:** DHCP updates DNS suffix; Split-horizon ensures internal names resolve via internal servers even when on VPN, while public names resolve via external.

OP8 — Hard: **Chain:** Root CA (offline) -> Subordinate CA -> End Entity. **CRL:** List of revoked certs (polling). **OCSP:** Real-time check. **Templates:** Define cert attributes. **Auto-enrollment:** Clients request certs automatically. **Consequences:** Compromised Subordinate = Revoke that cert. Compromised Root = Revoke all certs, rebuild PKI (catastrophic).

OP9 — Hard: **MPLS:** Reliable, expensive, managed. **IPsec:** Cheap, internet risk. **SD-WAN:** Smart routing, cost-effective, reliable. **WireGuard:** Simple mesh, high security. **Recommendation:** SD-WAN for 50 users/site + VoIP. It balances cost, latency (optimization), and reliability better than raw IPsec or expensive MPLS.

OP10 — Medium: iDRAC/iLO/IPMI are out-of-band management interfaces (remote console). Critical for rebooting/fixing servers without physical access. Exposing to internet is a severe security risk (unauthorized access, RCE, hardware theft).

OP11 — Medium: **LVM:** Logical volumes on physical disks. **LVM-Thin:** Space-efficient snapshots. **ZFS:** Filesystem + storage features. **Snapshots:** LVM (Copy-on-write), Thin (Instant), ZFS (Instant, integrated). Use ZFS for simplicity and features; LVM for legacy compatibility.

OP12 — Hard: **Stretch Cluster:** 2 sites, 3 nodes (1 per site + 1 tiebreaker). **CRUSH:** Distributes data across sites. **Latency:** High latency between sites slows replication. **Split-Brain:** If network partitions, cluster thinks both sites are alive. **2-site Ceph:** Bad without tiebreaker because if one site dies, the other cannot reach quorum, causing data loss or unavailability.

OP13 — Easy: DHCP assigns IPs. DORA: Discover (Client), Offer (Server), Request (Client), Ack (Server). No server: Client gets APIPA (169.254.x.x). Lease expires: Client renews; if no server, reverts to APIPA.

OP14 — Easy: Managed switch allows VLANs, QoS, ACLs. Unmanaged is plug-and-play. Managed switches are critical for enterprise security (segmentation) and traffic prioritization (VoIP).

OP15 — Easy: NTP synchronizes time. Critical for log correlation, SSL cert validation, and database replication. Drift causes replication lag, failed auth (certs), and incorrect log analysis.

OP16 — Easy: Physical: Dedicated hardware. VM: Virtualized OS. Container: Virtualized app layer. Run on bare metal for high-performance DBs or latency-sensitive workloads where hypervisor overhead is unacceptable.

OP17 — Easy: UPS provides battery backup (minutes). Generator provides long-term power (hours/days). ATS switches power source from Grid to Generator automatically. Both needed for continuous uptime.

OP18 — Medium: Active-Passive: One active, one standby. Active-Active: Both process traffic. **Pacemaker:** Manages resources. **Corosync:** Heartbeat. **STONITH:** Fencing (power off failed node). **VIP:** Virtual IP moves to active node on failover.

OP19 — Hard: **3-2-1:** 3 copies, 2 media types, 1 offsite. **RPO/RTO:** Recovery Point/Time Objectives. **Types:** Full (base), Incremental (diff since last), Differential (diff since last full). **Dedup:** Reduces storage. **Immutable:** Prevents ransomware deletion. **Backup vs DR:** Backup = Data copy; DR = System recovery (infrastructure + data).

OP20 — Hard: **802.1X:** Supplicant (Client), Authenticator (Switch), Auth Server (RADIUS). **EAP:** EAP-TLS (Cert), PEAP (Password). **RADIUS:** Transmits auth. **Fail Auth:** Port drops. **MAB:** MAC Authentication Bypass for devices without supplicants (e.g., printers) by checking MAC address against a whitelist.
