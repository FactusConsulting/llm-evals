T1 — Easy: `tofu plan` calculates the execution plan and shows what changes will be made without applying them. `tofu apply` executes the plan and makes the changes to the infrastructure.

T2 — Easy: State is a JSON file that tracks the real-world resources managed by OpenTofu. Remote state is important for team collaboration (prevents overwrites), security (keeps state out of local repos), and consistency (single source of truth).

T3 — Medium: `count` creates a list of resources indexed by integer (0, 1, 2). `for_each` creates resources indexed by a map or set (key-value pairs). `for_each` is preferred when resources need unique identifiers or when the number of resources is dynamic based on a set of keys.

T4 — Medium: If a resource is changed outside OpenTofu (drift), `tofu plan` detects the difference and shows it as an update or delete. `tofu apply` can fix the drift by recreating the resource or updating it to match the state, depending on the configuration.

T5 — Medium:
```hcl

  for_each = toset(["web1", "web2", "web3"])
  triggers = {
    name = each.value
  }
}
```

T6 — Hard: `terraform_remote_state` reads the *state file* of another module, coupling the module to the state structure. `output` values read the *output values* of another module. The recommended alternative is using `output` values from the module itself. Why? It decouples the module from the state file, making refactoring and moving modules easier.

T7 — Hard: The `remote-exec` provisioner runs *after* the resource is created. If a dependent resource reads the output immediately, it fails because the provisioner hasn't finished. Fix: Use `local-exec` to copy the generated kubeconfig to a known location (e.g., `~/.kube/config`), then read that file in the dependent resource.

T8 — Medium: `terraform import` is a CLI command to import existing resources. It requires knowing the resource ID. The `import` block (1.5+) allows declarative definition of import targets in code, improving readability and allowing version control of import configurations.

T9 — Easy: A variable is an input value passed to a module or configuration. An output is a value returned from a module or configuration. Variables are used to configure; outputs are used to share results.

T10 — Easy: A provider is a plugin that interacts with a cloud API. If you run `tofu plan` without `tofu init`, the providers are not downloaded, and the plan will fail with an error about missing providers.

T11 — Easy: `.terraform.lock.hcl` is a lock file that records the exact versions of providers used. It should be committed to version control to prevent "dependency drift" where different environments use different provider versions.

T12 — Easy: `tofu destroy` removes all resources managed by the state. You target a single resource using `tofu destroy -target=resource_type.resource_name`.

T13 — Easy: A data source reads information about existing resources (e.g., AWS account ID). Use it when the resource exists but is not managed by OpenTofu (e.g., reading an existing VPC ID).

T14 — Medium: `locals` are computed values within a module. `variables` are inputs. Use `locals` for derived values (e.g., concatenating strings) that don't need to be passed in from outside.

T15 — Medium: `lifecycle` controls resource behavior. `create_before_destroy` ensures HA during updates. `prevent_destroy` protects critical resources from accidental deletion. `ignore_changes` prevents specific attributes from being updated by OpenTofu (e.g., tags managed externally).

T16 — Medium: A `moved` block tells OpenTofu that resources have been renamed or moved in the codebase without needing to recreate them. It helps migrate state during refactoring without downtime.

T17 — Hard: The dependency graph is a Directed Acyclic Graph (DAG). Implicit dependencies are inferred from resource references (e.g., `aws_instance.id`). Explicit dependencies use `depends_on`. `depends_on` reduces parallelism by forcing specific order, used sparingly to avoid unnecessary serialization.

T18 — Hard: Strategies: 1. `refresh=false` (skip state refresh). 2. `target` (plan specific resources). 3. `state` filtering (ignore specific resources). 4. `parallelism` (TF 1.5+ allows parallel plans). Tradeoffs: `refresh=false` risks drift; `target` limits scope; `state` filtering requires careful management.

T19 — Hard: State locking prevents concurrent modifications. If a lock is not released (crash), the state is locked. Manually break with `terraform force-unlock <id>`. Risk: Concurrent modifications can corrupt state or cause data loss.

T20 — Hard: Migration: 1. `terraform init` with new S3 backend config. 2. `terraform state push` (moves local state to new backend). 3. `terraform init` (on new backend, if not done). 4. Verify with `terraform state list`. The existing state file is moved to the new backend; local state is cleared.

A2 — Easy: `ansible_facts` contains OS and system information. Access the OS family using `ansible_os_family` (e.g., `RedHat`, `Debian`).

A3 — Medium: `command` runs a binary without shell interpretation. `shell` allows shell features (pipes, redirection). `raw` runs commands without any interpretation (no shell, no escaping). Use `raw` for performance or when shell syntax is dangerous.

A4 — Medium: Idempotency means running the task twice has the same effect as running it once. Idempotent: `file` module (creates file if missing). Not Idempotent: `command` module (runs every time).

A8 — Medium: `ansible-vault` encrypts files. To encrypt a single variable, use `ansible-vault encrypt_string` and paste the encrypted string into the `vars` file.

A9 — Easy: An inventory file lists hosts and groups. Static inventory is a text file. Dynamic inventory uses a script/API to generate the list (e.g., cloud provider).

A10 — Easy: `ansible webservers -m df -a /` or `ansible webservers -m disk_usage`.

A11 — Easy: A handler is a task that runs only if notified. It differs from a regular task which runs unconditionally. Triggered using `notify: handler_name`.

A12 — Easy: `ansible.cfg` configures Ansible behavior. Common settings: `inventory`, `forks` (parallelism), `timeout`.

A13 — Easy: `register` stores the output of a task in a variable. Use it in subsequent tasks with `{{ registered_var }}` or `when: registered_var.status == 'ok'`.

A14 — Medium: `include_tasks` is runtime (dynamic), allowing conditionals on the task itself. `import_tasks` is compile time (static). Use `include_tasks` when the task list depends on runtime variables.

A15 — Medium: Ansible Galaxy is a repository for roles/collections. Use `requirements.yml` to list dependencies, then run `ansible-galaxy install -r requirements.yml`.

A16 — Medium: Connection plugins define how Ansible connects. `ssh` for remote Linux/Windows. `local` for control node. `network_cli` for network devices (Cisco, Juniper).

A17 — Hard: `delegate_to` runs a task on a different host. `run_once` runs a task once per play. Example: Gather facts on remote host, then run a task on `localhost` using `delegate_to: localhost` and `run_once: true`.

A18 — Hard: Strategies: 1. Increase `forks`. 2. Enable `pipelining` (reduces SSH overhead). 3. Use `fact_caching` (reduces fact gathering). 4. Use `mitogen` (forks processes). Tradeoffs: `forks` increases load; `pipelining` reduces security slightly; `fact_caching` adds complexity.

A19 — Hard: `{{ }}` outputs variables. `{% %}` controls flow (loops, if). `{# #}` comments. Snippet:

```jinja
}
{% endfor %}
```

A20 — Hard: Use `serial: 1` (or batches) to deploy one by one. `pre_tasks` update load balancer. `post_tasks` update load balancer. Use `block` for the app deployment and `rescue` to rollback if health checks fail.
