**AA1**
A monolith is a single, unified application with a shared codebase and database, deployed as one unit. Microservices decompose the application into small, independent services that communicate over a network.
Three concrete problems microservices introduce:
1.  **Network Latency:** Services communicate over the network (TCP/HTTP) instead of in-process function calls, adding latency.
2.  **Distributed Transactions:** Maintaining data consistency across multiple services requires complex patterns (e.g., Sagas) rather than standard ACID transactions.
3.  **Operational Complexity:** Debugging, monitoring, and deploying distributed systems is significantly harder than managing a single monolith.

**AA2**
Synchronous communication involves a request-response pattern where the caller waits for the callee to return a result (e.g., HTTP/REST, gRPC). Asynchronous communication involves sending a message without waiting for a response; the caller continues processing (e.g., Message Queues like RabbitMQ, Pub/Sub systems like Kafka).

**AA3**
An API Gateway is a specialized reverse proxy that handles business logic (authentication, rate limiting, aggregation, transformation). A reverse proxy is a general-purpose L4/L7 traffic router (SSL termination, load balancing).
An API Gateway can technically replace a reverse proxy if it handles all routing and SSL termination, but it is often not recommended for high-performance L4 routing. A dedicated reverse proxy (like HAProxy or Nginx) is preferred for raw performance and L4 load balancing, while the Gateway handles L7 logic.

**AA4**
The Saga pattern manages long-running transactions across distributed services by breaking them into local transactions.
*   **Choreography:** Services publish events; other services subscribe and react. No central coordinator.
*   **Orchestration:** A central coordinator tells services what to do and manages compensation (rollback) logic.
*   **Usage:** Choreography is better for loosely coupled systems; Orchestration is better for complex workflows requiring strict control and easier rollback management.

**AA5**
CQRS separates the Command (write) and Query (read) models into different stores or logic paths. It is paired with Event Sourcing (storing state as a sequence of events) to reconstruct read models.
This combination solves the problem of read/write performance mismatch and schema evolution. Traditional CRUD models force the read model to match the write model, which can be slow for complex queries or difficult to change without breaking writes.

**AA6**
The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service.
*   **States:** Closed (normal), Open (failures detected, calls blocked), Half-Open (testing if service recovered).
*   **Difference from Retry:** Retry attempts to fix transient errors; Circuit Breaker stops calling a permanently failing service to save resources.
*   **Usage:** Use both together: Retry with backoff for transient errors, but if failures persist, trip the Circuit Breaker to stop retrying.

**AA7**
1.  **Shared DB, Shared Schema:**
    *   *Cost:* Lowest.
    *   *Security:* Low (data leakage risk).
    *   *Complexity:* Low.
    *   *Noisy Neighbor:* High (one tenant's load affects others).
2.  **Shared DB, Separate Schema:**
    *   *Cost:* Medium.
    *   *Security:* Medium (logical isolation).
    *   *Complexity:* Medium (schema management).
    *   *Noisy Neighbor:* Medium.
3.  **Separate DB per Tenant:**
    *   *Cost:* Highest.
    *   *Security:* High (physical isolation).
    *   *Complexity:* High (provisioning/management).
    *   *Noisy Neighbor:* None.

**AA8**
Strong consistency guarantees immediate visibility of updates across all nodes. Eventual consistency allows temporary divergence.
For an inventory system that must *never* oversell, **Strong Consistency** is required.
*   **Architecture:** Use a strongly consistent distributed database (e.g., CockroachDB, DynamoDB with strong consistency, or a centralized PostgreSQL instance).
*   **Patterns:** Implement optimistic locking or distributed locking (e.g., Redis/Zookeeper) to ensure only one transaction can reserve stock at a time. Avoid sharding inventory data unless using a consistent hashing strategy with strong consistency guarantees.

**AA9**
A sidecar proxy is a lightweight process running alongside a service (in the same container/Pod) to handle networking, security, and observability.
*   **Envoy/Istio:** Envoy is the sidecar (data plane). Istio is the control plane that configures Envoy.
*   **Data Plane:** Handles traffic flow (L4/L7). Control Plane: Manages configuration and policies.
*   **mTLS:** Solves the problem of managing TLS certificates for every service-to-service call. Application-level TLS requires code changes; sidecar mTLS handles encryption transparently at the network level.

**AA10**
The Strangler Fig pattern migrates legacy systems by incrementally routing new functionality to new services while keeping old functionality active.
*   **Strategy:**
    1.  Deploy a new .NET 8 service for a specific feature (e.g., "User Profile").
    2.  Update the API Gateway to route "User Profile" requests to the new service.
    3.  Gradually migrate other features (e.g., "Orders") to new services.
    4.  Once a feature is fully migrated, remove the legacy code path from the monolith.
    5.  Repeat until the monolith is fully decomposed.

**AA11**
The 12-Factor App methodology provides best practices for building cloud-native apps.
Six key factors:
1.  **Codebase:** One codebase tracked in VCS.
2.  **Dependencies:** Explicitly declared and isolated.
3.  **Config:** Config stored in environment variables, not code.
4.  **Backing Services:** Treat all external services (DB, cache) as attached resources.
5.  **Bail Early:** Fail fast on errors.
6.  **Dev/Prod Parity:** Keep environments similar to reduce surprises.
They matter because they ensure portability, scalability, and security across different cloud providers.

**AA12**
*   **Coupling:** Event-driven (Kafka) is loosely coupled; Request-driven (REST) is tightly coupled.
*   **Scalability:** Kafka scales horizontally better for throughput; REST scales well for latency.
*   **Debugging:** Event-driven is harder (asynchronous, replayability); Request-driven is easier (request/response logs).
*   **Ordering:** Kafka guarantees ordering per partition; REST guarantees order per request.
*   **Failure:** Event-driven allows retry/replay; REST requires immediate handling.
*   **Choice:** Use Kafka for audit trails, batch processing, and decoupled microservices. Use REST for real-time user interactions and simple CRUD.

**AA13**
A load balancer distributes incoming traffic across multiple servers.
*   **Layer 4 (Transport):** Operates on IP/Port (TCP/UDP). Fast, stateless.
*   **Layer 7 (Application):** Operates on HTTP/HTTPS content (Host, Path, Headers).
*   **Use Case:** Layer 7 is required when routing traffic based on URL paths (e.g., `/api` to Service A, `/static` to CDN) or handling SSL termination.

**AA14**
A message queue (RabbitMQ) supports point-to-point and pub/sub with guaranteed delivery and low latency. A log-based broker (Kafka) is append-only, high-throughput, and supports replayability.
*   **Pick Queue:** For task queues (e.g., sending emails) where message order and delivery guarantee are critical.
*   **Pick Broker:** For event streaming (e.g., user activity logs) where high throughput and replayability are critical.

**AA15**
A container packages code and dependencies into a lightweight unit that shares the host OS kernel. A VM includes a full guest OS.
Containers are popular for microservices because they are lighter (faster startup, lower memory footprint), allow higher density, and simplify deployment consistency across environments.

**AA16**
Stateless services do not store data in memory (e.g., Web Servers, API Gateways). Stateful services store data (e.g., Databases, Caches).
Stateless services are easier to scale horizontally because any instance can handle any request without coordination. Stateless example: Nginx. Stateful example: PostgreSQL.

**AA17**
An ORM maps database tables to object classes. Examples: Hibernate (Java), Entity Framework (.NET).
*   **Trade-offs:** ORMs increase productivity and reduce SQL injection risk but can lead to performance issues (N+1 queries) and vendor lock-in. Raw SQL offers maximum performance and control but requires manual maintenance.

**AA18**
The Bulkhead pattern isolates resources (threads, CPU, memory) to prevent one failure from exhausting shared resources.
*   **Relation:** It ensures that a failure in one service (e.g., high DB load) doesn't starve other services (e.g., HTTP processing).
*   **Implementation:** Configure separate thread pools for different operations (e.g., one pool for DB calls, one for external API calls). Or deploy separate instances of a service for different tenants.

**AA19**
*   **OT:** Server-side conflict resolution. Requires online connectivity. Complex to implement.
*   **CRDTs:** Client-side conflict resolution. Converges eventually. Supports offline editing.
*   **Comparison:** CRDTs have higher complexity in implementation but better offline support. OT is better for real-time collaboration with high latency tolerance.
*   **Choice:** Choose **CRDTs** for a system that must support offline editing because they allow the client to make changes locally and merge them automatically when connectivity is restored without server intervention.

**AA20**
*   **Context Propagation:** Use W3C Trace Context headers (trace-id, parent-id) to link requests across services.
*   **Sampling:** Head-based (sample at start) vs Tail-based (sample based on error rate). Tail-based saves storage.
*   **Storage:** Jaeger/Tempo store spans for querying.
*   **Async/Messaging:** In Kafka, propagate headers to the producer. Consumers read headers and add them to the new span.
*   **Continuity:** Ensure the consumer reads the trace context from the message headers and sets it as the parent ID for the new span.

**OP1**
Type 1 (Bare-metal) runs directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) runs as an app on a host OS (e.g., VMware Workstation, VirtualBox).
Type 1 is used for production servers; Type 2 is used for development/testing.

**OP2**
SAN (Storage Area Network) provides block-level storage (e.g., iSCSI, Fibre Channel). NAS (Network Attached Storage) provides file-level storage (e.g., NFS, SMB).
*   **Use SAN:** For databases requiring raw disk performance and low latency.
*   **Use NAS:** For file sharing, backups, and media storage.

**OP3**
A 3-tier architecture has Core (routing), Distribution (aggregation), and Access (servers).
Leaf-Spine is preferred in modern data centers because it provides a flat network topology.
*   **Problem Solved:** 3-tier can create bottlenecks at the distribution layer and limit scalability. Leaf-Spine ensures every leaf connects to every spine, minimizing latency and maximizing bandwidth.

**OP4**
*   **Node Count:** Minimum 3 nodes for quorum.
*   **Quorum:** Majority vote (2/3) required to make decisions.
*   **Fencing:** STONITH (Shoot The Other Node In) prevents split-brain by isolating failed nodes.
*   **Shared Storage:** Ceph (distributed) is preferred over iSCSI/NFS for HA.
*   **Failure:** If a node fails, the cluster detects it, fences the node, and services failover to remaining nodes.

**OP5**
VLAN trunking allows multiple VLANs over a single link. 802.1Q adds a 4-byte tag to Ethernet frames.
*   **Linux Config:** Use `ip link add link eth0 name eth0.10 type vlan id 10` for each VLAN. Assign IPs to the VLAN interfaces (e.g., `eth0.10`).

**OP6**
*   **RAID 1:** Mirror (2x capacity, high perf).
*   **RAID 5:** Striping + 1 parity (N-1 capacity).
*   **RAID 6:** Striping + 2 parity (N-2 capacity).
*   **RAID 10:** Mirror + Stripe (N/2 capacity, high perf).
*   **RAID Z2:** ZFS Mirror + Parity (similar to RAID 6 but optimized for ZFS).
*   **Choice:** **RAID Z2** (or RAID 10). With 6 drives, RAID Z2 gives 4 usable drives (good capacity/perf balance) and tolerates 2 drive failures. RAID 10 gives 3 usable drives but higher cost.

**OP7**
*   **Architecture:** Recursive resolvers (ISP) query authoritative servers. Internal DNS uses Active Directory. DMZ hosts public services.
*   **Split-Horizon:** Internal clients query internal zone; external clients query public zone.
*   **DNSSEC:** Signs public zone data to prevent spoofing.
*   **Laptop Move:** DHCP updates DNS suffix. Split-horizon ensures the laptop queries the correct server based on the domain (e.g., `internal.corp.com` vs `www.google.com`).

**OP8**
*   **Chain:** Root CA (offline) -> Subordinate CA (online) -> End Entity (Server cert).
*   **CRL vs OCSP:** CRL is a list of revoked certs (periodic check). OCSP is real-time status check.
*   **Templates:** Define cert attributes (key size, validity).
*   **Consequences:** Compromised Subordinate = revoke that cert. Compromised Root = revoke all certs issued by that root (catastrophic).

**OP9**
*   **MPLS:** High cost, high reliability, low latency.
*   **IPsec:** Low cost, variable latency, internet risk.
*   **SD-WAN:** Medium cost, high reliability, dynamic path selection.
*   **WireGuard:** Low cost, simple, fast, but less enterprise management.
*   **Recommendation:** **SD-WAN**. Balances cost and latency for VoIP. MPLS is overkill for 50 users; IPsec risks latency jitter.

**OP10**
iDRAC/iLO/IPMI are out-of-band management interfaces allowing remote server control (power, console) independent of the OS.
*   **Criticality:** Allows recovery if the OS is dead.
*   **Risk:** Exposing to the internet allows attackers to brute-force access, pivot to the network, or steal data.

**OP11**
*   **LVM:** Block-level management.
*   **LVM-Thin:** Space-efficient virtual volumes.
*   **ZFS:** File system with built-in compression, encryption, and replication.
*   **Snapshots:** LVM (copy-on-write block), Thin (metadata), ZFS (native file-level).
*   **Choice:** Use ZFS for file storage (better features), LVM for block storage (DBs).

**OP12**
*   **Strategy:** Place monitors in different sites. Use CRUSH rules to distribute data.
*   **Latency:** High latency between sites can cause timeouts.
*   **Split-Brain:** If monitors lose contact with one site, they may think the other site is dead.
*   **2-Site Ceph:** Bad without a tiebreaker (3rd site) because monitor quorum loss can cause data unavailability or corruption.

**OP13**
DHCP assigns IP addresses. DORA: Discover (Client), Offer (Server), Request (Client), Ack (Server).
*   **Unavailable Server:** Client uses APIPA (169.254.x.x).
*   **Lease Expires:** Client renews. If renewal fails, it uses APIPA.

**OP14**
Managed switches allow configuration (VLANs, QoS, ACLs). Unmanaged switches are plug-and-play.
*   **Enterprise Features:** VLAN segmentation, Port Security, QoS (traffic prioritization), SNMP monitoring.

**OP15**
NTP synchronizes system clocks.
*   **Criticality:** SSL certificate validation, log correlation, database replication consistency.
*   **Drift:** Can cause authentication failures, log analysis errors, and database replication lag.

**OP16**
*   **Physical:** Bare metal hardware.
*   **VM:** OS abstraction layer.
*   **Container:** App abstraction layer.
*   **Bare Metal:** Use for high-performance workloads (HPC, low-latency DBs) where virtualization overhead is unacceptable.

**OP17**
UPS provides immediate backup power (minutes). Generator provides long-term power (hours/days).
*   **Role:** UPS bridges the gap until the generator starts.
*   **ATS:** Automatically switches power source from Grid to Generator and back.

**OP18**
Active-Passive: One server active, one standby. Active-Active: Both servers process load.
*   **Pacemaker/Corosync:** Manages cluster state.
*   **Fencing (STONITH):** Physically isolates a failed node (e.g., power off) to prevent split-brain.
*   **VIP:** Virtual IP floats between nodes during failover.

**OP19**
*   **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Recovery Point Objective (data loss limit), Recovery Time Objective (downtime limit).
*   **Types:** Full (complete), Incremental (changes since last), Differential (changes since last full).
*   **Immutable:** Prevents ransomware from encrypting backups.
*   **Backup vs DR:** Backup is data copy; DR is restoring the entire system (infrastructure + data).

**OP20**
*   **Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
*   **EAP:** EAP-TLS (Certificate-based), PEAP (Password-based).
*   **RADIUS:** Protocol for authentication.
*   **Fail:** Port is blocked (no network access).
*   **MAB:** If supplicant fails, switch authenticates based on MAC address (fallback).
