CL1 — Easy: IaaS (Infrastructure as a Service) provides virtualized hardware (compute, storage, network) without managing the OS. Example: AWS EC2. PaaS (Platform as a Service) provides a runtime environment (OS, middleware) for applications. Example: Google App Engine. SaaS (Software as a Service) delivers fully managed software over the internet. Example: Salesforce.

CL2 — Easy: The Shared Responsibility Model defines security boundaries. For IaaS VMs, the provider secures the physical infrastructure and hypervisor; you secure the OS, data, and applications. For managed Kubernetes, the provider secures the control plane and infrastructure; you secure the workloads, policies, and data. For SaaS (e.g., M365), the provider manages the entire stack including data and security; you manage user access and identity.

CL3 — Medium: A VPC is a logical isolation boundary. A subnet is a range of IP addresses within a VPC. A Security Group (SG) is a stateful firewall attached to an instance (allows in, allows return). A Network ACL (NACL) is a stateless firewall attached to a subnet (allows in, must explicitly allow return). Layering: VPC > Subnet > NACL > SG. Stateful filtering (SG) remembers connection state; Stateless filtering (NACL) requires explicit rules for both directions.

CL4 — Medium: A Landing Zone provides a standardized, secure foundation for multi-account environments. Organizational Units (OUs) group accounts for policy management. Guardrails enforce compliance (e.g., no public S3 buckets). Shared networking uses a Hub-and-Spoke model (Transit Gateway/Azure Hub) to connect accounts. Centralized logging aggregates logs (e.g., CloudTrail) for audit. Single-account approaches are problematic due to resource limits, security isolation risks, and difficulty in scaling/multi-tenancy.

CL5 — Medium: IaC manages infrastructure via code. Terraform/OpenTofu uses a declarative state file; best for multi-cloud and complex state management. Pulumi uses programming languages (Python/TS); best for teams with strong dev skills. CloudFormation/Bicep are native provider tools; best for simple, single-provider projects. Crossplane manages infrastructure as Kubernetes resources; best for K8s-native teams.

CL6 — Medium: HPA scales pod count based on CPU/Memory. VPA scales pod resource requests based on usage. Cluster Autoscaler adds/removes nodes based on pod demand. KEDA scales based on external events (e.g., queue depth). Use KEDA over HPA when load is driven by external events (e.g., message processing) rather than resource utilization, allowing for zero-pod scaling.

CL7 — Hard: DR strategy depends on RPO (data loss) and RTO (downtime). Active-Active replicates data and traffic to both regions (lowest RTO, highest cost). Active-Passive keeps one region active (lower cost). Database replication: Sync (zero RPO) vs Async (higher RPO). DNS failover (Route53) directs traffic. State management requires consistent hashing or shared storage. Pilot Light (cold), Warm Standby (partial), Multi-site Active-Active (full). Multi-site is most resilient but most expensive.

CL8 — Hard: GitOps stores infrastructure/app manifests in Git, using a controller to sync the cluster to the repo. ArgoCD is K8s-native with a UI; FluxCD is lightweight, often used with Helm/Kustomize. Secrets are handled via Sealed Secrets (encrypted in repo) or External Secrets Operator (fetches from Vault). Manual changes cause drift; the GitOps controller detects and automatically reverts the cluster to match Git state.

CL9 — Hard: Use a StatefulSet for stable pod identities and storage. Use a Local Persistent Volume (LocalPath) for low-latency local storage. Use a Headless Service for DNS-based service discovery (no load balancing). Use Init Containers to prepare the filesystem. Mount ConfigMaps as volumes for config files. Use Pod Disruption Budgets to ensure availability during scaling.

CL10 — Medium: A Service Account is a K8s identity. Workload Identity (GCP/Azure) maps K8S SA to cloud IAM. IRSA (AWS) maps K8S SA to IAM Role. Mounting cloud credentials in a pod is bad because it exposes long-lived keys and requires rotation. Workload Identity federation allows the pod to assume the role dynamically without storing keys.

CL11 — Medium: Object storage (S3/Blob) is for unstructured data (files, backups); high durability (11 9s), availability varies. Block storage (EBS/Disk) is for databases/VMs; high IOPS, lower durability. File storage (EFS/Azure Files) is for shared file systems; lower performance, high availability. Use Object for data lakes, Block for DBs, File for shared app data.

CL12 — Hard: Zero Trust assumes no trust by default. Network Policies restrict pod-to-pod traffic. Service Mesh (Istio) enforces mTLS. Pod Identity authenticates workloads. Admission Controllers (OPA) enforce policy. Image signing verifies container integrity. Runtime security (Falco) detects anomalies. Unlike perimeter security, Zero Trust verifies every request regardless of origin.

CL13 — Easy: A CDN caches content at edge locations closer to users. It works by storing copies of static assets. Services: AWS CloudFront, Azure CDN. Use a CDN for high-traffic static content (images, video) to reduce latency and origin load. Serve directly from origin for dynamic content or low-traffic scenarios.

CL14 — Easy: A Region is a geographic area with multiple Availability Zones (AZs). AZs are isolated datacenters within a region. Deploy across AZs for High Availability (HA) to survive zone failures. Zonal resources exist in one AZ; Regional resources span multiple AZs.

CL15 — Easy: Managed DBs (RDS, Cloud SQL) abstract infrastructure management. The provider handles patching, backups, failover, and scaling. You manage data, schema, and application connectivity. Running on a VM requires manual patching, backup management, and HA configuration.

CL16 — Easy: IAM Users are humans; Roles are permissions attached to users/groups/services. Policies define permissions. Principle of Least Privilege means granting only the minimum permissions required. Apply it by using specific policies, avoiding admin roles, and using temporary credentials (STS).

CL17 — Easy: Serverless executes code in response to events without managing servers. AWS Lambda, Azure Functions, GCP Functions are examples. Cold starts occur when a function is invoked for the first time (latency). Serverless is poor for long-running processes, high I/O, or strict latency requirements.

CL18 — Medium: Ingress resource is a K8s API object. Gateway API is the standard for Ingress (more flexible). Cloud LB annotations use provider-specific rules. Service Mesh ingress gateways handle mTLS and traffic management. TLS termination happens at the Cloud LB (offload) or Ingress Controller (sidecar). Use Gateway API for multi-protocol support and advanced routing.

CL19 — Hard: Cost optimization: Commit to Reserved Instances/Savings Plans for steady workloads. Use Spot/Preemptible for fault-tolerant batch workloads. Right-size instances based on usage. Tier storage (Archive for cold data). Detect idle resources. Implement FinOps (culture, visibility). Use Showback (cost visibility) or Chargeback (billing) to allocate costs to teams.

CL20 — Hard: Multi-cloud strategy uses abstraction layers (Kubernetes, Terraform) to avoid lock-in. Networking uses Interconnect/VPN. Identity uses federation (OIDC/SAML). Trade-offs: Higher cost, complexity, and latency. Multi-cloud is justified for compliance, risk mitigation, or specific regional requirements, not just for "avoiding lock-in" without a strategic reason.

OT1 — Easy: The Purdue Model (ISA-95) defines 7 levels of enterprise control. Level 0: Physical Process. Level 1: Basic Control (PLCs). Level 2: Supervisory Control (SCADA). Level 3: Enterprise Control (MES). Level 4: Business Planning (ERP). Level 5: Management. Level 6: Enterprise Management.

OT2 — Easy: IT networks prioritize data availability and confidentiality. OT networks prioritize safety and reliability. Standard IT patching is risky in OT because it can cause downtime or safety hazards. OT systems often run legacy firmware that cannot be patched without validation.

OT3 — Medium: An IDMX (Industrial DMZ) separates IT and OT networks. Traffic flows from IT to OT (e.g., queries) and OT to IT (e.g., logs). Direct connectivity from Level 4 (IT) to Level 1 (Control) is dangerous because a compromise in IT could directly impact physical safety and equipment.

OT4 — Medium: Modbus TCP (L2/L3, L1/2): Simple, industrial. OPC UA (L2/L3, L2/3): Secure, semantic data. EtherNet/IP (L2/L3, L1/2): Rockwell automation. PROFINET (L2/L3, L1/2): Siemens automation. MQTT (L3, L2/3): Pub/Sub messaging for IoT/SCADA.

OT5 — Medium: A data diode allows traffic in only one direction (e.g., OT to IT). A firewall allows bidirectional traffic. Use a hardware data diode for critical data export where return traffic is impossible or prohibited. Limitation: No return traffic, requires specific hardware.

OT6 — Medium: Data flow: PLC -> Historian/OPC UA Server -> Edge Gateway -> MQTT Broker -> Cloud Ingestion. Security boundaries: Edge Gateway to Cloud (Firewall), OT to IT (DMZ). Ensure the edge gateway is hardened and the cloud ingestion is authenticated.

OT7 — Hard: Zones are logical network boundaries; Conduits are connections between zones. Zone 1: Corporate Network. Zone 2: Engineering Workstations. Zone 3: SCADA Servers. Zone 4: PLCs/SIS. Conduits connect zones (e.g., Zone 2 to Zone 3 via firewall).

OT8 — Hard: Segment network using VLANs per production line and function. Place firewalls between zones (e.g., between VLANs). Use Layer 3 switches for routing. For transition, run parallel networks and migrate line-by-line to avoid production stoppage.

OT9 — Hard: SIS (Safety Instrumented Systems) overrides BPCS for safety (e.g., emergency shutdown). IEC 61511 defines SIS requirements. SIS must be isolated to prevent malicious shutdowns. If ransomware reaches SIS, it could cause catastrophic physical damage or environmental release.

OT10 — Medium: PLCs are for discrete control (simple logic). DCS is for continuous process control (complex, integrated). SCADA is for monitoring and control over wide areas. They coexist: PLCs/DCS at Level 1, SCADA at Level 2.

OT11 — Medium: Remote access requires a Jump Host (bastion), MFA, and session recording. Vendor access requires tickets and time limits. RDP directly to an HMI is unacceptable because it bypasses security controls and exposes the control system directly to the internet.

OT12 — Hard: Detection: Use IDS/NetFlow monitoring. Inventory: Know all assets. Response: Isolate network segments, notify control room. Operator role: Ensure safety first (manual shutdown if needed), not IT-led. Do not isolate if it risks safety.

OT13 — Easy: An HMI allows operators to monitor and control the process. It differs from an Engineering Workstation, which is used for configuration, logic editing, and maintenance, not real-time operation.

OT14 — Easy: A historian stores time-series process data. It is important for trend analysis and compliance. Plant Historian (Level 3) stores operational data. Enterprise Historian (Level 4) aggregates data for business analysis.

OT15 — Easy: Ladder Logic is a graphical programming language resembling relay logic. It is executed by a PLC. It remains dominant due to operator familiarity and ease of troubleshooting compared to text-based languages.

OT16 — Easy: An RTU is a ruggedized controller for remote locations (serial communication). A PLC is for local control (Ethernet). Deploy RTUs in harsh, remote environments (oil/gas pipelines) where PLCs are impractical.

OT17 — Easy: Analog signals are continuous (4-20mA, 0-10V). Digital signals are discrete (0/1). 4-20mA is preferred over 0-20mA because it allows detection of a broken wire (0mA indicates fault).

OT18 — Medium: Asset inventory is the foundation of OT security. Use passive monitoring (sniffing traffic) to discover assets without impact. Active scanning (ping/port scan) is dangerous as it can disrupt real-time control operations.

OT19 — Hard: MITRE ATT&CK for ICS maps adversary tactics to OT environments. Tactics: Reconnaissance (e.g., T1590), Execution (e.g., T1591), Persistence (e.g., T1592). It differs from Enterprise ATT&CK by focusing on industrial protocols and safety. Use it to identify gaps in detection rules.

OT20 — Hard: Converged SOC collects logs (Syslog/NetFlow) without impacting operations. Integrate with SIEM. Use OT-specific rules (e.g., protocol anomalies). Staffing requires OT engineers to triage alerts. False positives are high due to legacy noise. For unauthorized firmware changes: Verify integrity, isolate device, rollback to known good image.
