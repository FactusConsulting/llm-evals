AA1 — Monoliths consist of a single codebase and database, deployed as one unit. Microservices decompose the application into independent services with their own data stores. Three problems microservices introduce: 1. Distributed transactions (complexity of consistency), 2. Network latency and failure points (inter-service communication), 3. Operational complexity (deployment, monitoring, and debugging across many services).

AA2 — Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST, gRPC). Asynchronous communication involves fire-and-forget or callback patterns where the caller does not wait (e.g., Message Queues like RabbitMQ, Kafka, or Webhooks).

AA3 — An API Gateway handles business logic (auth, rate limiting, aggregation, transformation), while a reverse proxy primarily handles routing, SSL termination, and load balancing. An API Gateway cannot entirely replace a reverse proxy because reverse proxies often operate at Layer 4 (TCP/UDP) for performance, whereas gateways operate at Layer 7 (HTTP). However, a gateway can often handle Layer 7 routing, but Layer 4 load balancing is usually handled by a dedicated proxy or LB.

AA4 — The Saga pattern manages long-running transactions across services by breaking them into smaller steps. Choreography involves services publishing events that trigger the next step (decoupled, hard to manage). Orchestration involves a central coordinator telling services what to do (coupled, easier to manage). Choreography is appropriate for loosely coupled systems; Orchestration is better for complex workflows requiring rollback coordination.

AA5 — CQRS separates read and write operations into different models. It is paired with Event Sourcing (storing state as a sequence of events) to allow reads to be optimized for specific queries while writes remain simple. This solves the problem of read/write performance mismatches and complex query requirements that a traditional CRUD model cannot handle efficiently.

AA6 — The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failures exceed threshold, calls fail fast), Half-Open (testing if service recovered). It differs from simple retry because it stops retrying when the service is dead. Use both together: Retry with backoff for transient errors, but open the circuit if failures persist to protect the system.

AA7 — 1. Shared DB/Schema: Lowest cost, highest noisy-neighbor risk, lowest security (row-level isolation). 2. Shared DB/Separate Schema: Medium cost, better isolation, higher ops complexity. 3. Separate DB: Highest cost, best security/isolation, highest ops complexity. Trade-offs: Cost decreases from 3 to 1; Security/Isolation increases from 1 to 3; Ops Complexity increases from 1 to 3; Noisy-neighbor risk decreases from 1 to 3.

AA8 — Strong consistency guarantees immediate visibility of updates; eventual consistency allows temporary divergence. For inventory oversell prevention, strong consistency is required. Architecture: Use a distributed database with strong consistency (e.g., ScyllaDB with strong read, or DynamoDB with strong consistency) or implement a centralized locking mechanism (e.g., Redis/Zookeeper) with optimistic locking to ensure atomic updates across services.

AA9 — A sidecar proxy is a lightweight process running alongside a service to handle networking. In Istio, Envoy acts as the sidecar. The Control Plane manages configuration and policies; the Data Plane (Envoy) handles traffic. mTLS between sidecars solves service-to-service authentication without requiring application code changes, whereas application-level TLS requires every service to manage certificates and endpoints.

AA10 — The Strangler Fig pattern migrates legacy systems by gradually routing new functionality to new services. Strategy: Deploy an API Gateway in front of the .NET Framework monolith. Initially, route all traffic to the monolith. Incrementally, add new endpoints to the Gateway that forward to new .NET 8 microservices. Slowly retire old endpoints on the monolith until it is fully decommissioned.

AA11 — The 12-Factor App methodology defines best practices for cloud-native apps. Six factors: 1. Codebase (versioned), 2. Dependencies (explicit), 3. Config (environment variables), 4. Backing Services (treat as external resources), 5. Build/Release/Run (separation of concerns), 6. Processes (stateless, scale out). They matter for portability, scalability, and security in cloud environments.

AA12 — Event-driven (Kafka) offers high decoupling, scalability, and replayability but has higher debugging complexity and eventual consistency. Request-driven (REST/gRPC) offers synchronous interaction, easier debugging, and strong consistency but tighter coupling. Choose Event-driven for audit trails, decoupled pipelines, and high throughput. Choose Request-driven for real-time user interactions and transactional integrity.

AA13 — A load balancer distributes incoming traffic across multiple servers. Layer 4 (Transport) balances based on IP/Port (TCP/UDP). Layer 7 (Application) balances based on content (HTTP headers, URLs). Layer 7 is required when routing traffic to different backend services based on URL paths or hostnames (e.g., API vs Web UI).

AA14 — A message queue (RabbitMQ) supports point-to-point and pub/sub with message lifecycle management (acknowledgments). A log-based broker (Kafka) is append-only, high-throughput, and supports replay. Pick RabbitMQ for task queues where message delivery guarantees are critical. Pick Kafka for event streaming, auditing, and high-volume data pipelines.

AA15 — A container packages code and dependencies with a lightweight OS layer (shared host kernel). A VM includes a full guest OS and hardware virtualization. Containers are popular for microservices because they are lightweight, start faster, and allow higher density compared to VMs.

AA16 — Stateless services do not store data in memory (e.g., Web Servers), making them easy to scale horizontally. Stateful services store data (e.g., Databases), making scaling harder. Stateless services allow instant scaling by adding more instances; stateful services require data replication or sharding.

AA17 — An ORM maps database tables to object classes (e.g., Hibernate for Java, Entity Framework for .NET). Trade-offs: ORMs simplify development and reduce SQL injection risk but can suffer from performance issues (N+1 queries) and lack of control compared to raw SQL for complex queries.

AA18 — The Bulkhead pattern isolates resources (threads, CPU, memory) to prevent one failure from exhausting system resources. Example: Implement separate thread pools for database connections and HTTP client calls. If the HTTP pool is exhausted due to a downstream failure, the DB pool remains available for other requests.

AA19 — Operational Transformation (OT) resolves conflicts server-side and requires online connectivity. CRDTs resolve conflicts client-side and support offline editing. CRDTs are chosen for offline editing because they allow local changes to be merged automatically when connectivity is restored without server intervention.

AA20 — Distributed tracing requires propagating a Trace ID and Span ID across services (W3C Trace Context). Sampling reduces storage costs. Storage (Jaeger/Tempo) aggregates spans. For async messaging (Kafka), trace continuity is ensured by injecting headers into the producer and extracting them in the consumer to link the producer and consumer spans.

OP1 — Type 1 (Bare-metal) hypervisors run directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) run on top of an OS (e.g., VMware Workstation, VirtualBox). Type 1 is for production servers; Type 2 is for development/testing.

OP2 — SAN (Storage Area Network) provides block-level storage (e.g., iSCSI, Fibre Channel) used for databases. NAS (Network Attached Storage) provides file-level storage (e.g., NFS, SMB) used for file sharing. Use SAN for performance-critical databases; use NAS for general file storage.

OP3 — A 3-tier architecture has Core, Distribution, and Access layers. Leaf-Spine is preferred in modern data centers because it provides equal path latency and higher scalability (linear scaling) compared to the hierarchical bottleneck of the 3-tier core layer.

OP4 — A Proxmox HA cluster needs 3+ nodes for quorum. Use Ceph for shared storage (preferred over iSCSI/NFS for HA). Fencing (STONITH) is critical to prevent split-brain during node failure. If a node fails, the cluster detects the loss, fences the failed node, and promotes a surviving node to take over the virtual machines.

OP5 — VLAN trunking allows multiple VLANs over a single link using 802.1Q tags. On Linux, configure a physical interface (e.g., eth0) and create VLAN sub-interfaces (e.g., `ip link add link eth0 name eth0.10 type vlan id 10`). The server can then assign IPs to these sub-interfaces to belong to multiple VLANs.

OP6 — RAID 1 (Mirror), 5 (Striping+Parity), 6 (2 Parity), 10 (Striping+Mirror), Z2 (ZFS Mirror+RAIDZ2). For 6 drives balancing performance, capacity, and fault tolerance: RAID 10 or ZFS RAIDZ2. RAID 10 offers best performance but lower capacity (50%). ZFS RAIDZ2 offers better capacity efficiency with similar fault tolerance (tolerates 2 drive failures).

OP7 — DNS architecture: Recursive resolvers (clients), Authoritative servers (AD), Forwarders (ISP), Conditional forwarding (DMZ). Split-horizon DNS directs internal queries to internal servers and external queries to public servers. When a laptop moves to VPN, the DHCP client updates the DNS suffix or the split-horizon logic routes the query to the appropriate zone based on the client's IP.

OP8 — PKI Chain: Root CA (offline) -> Subordinate/Issuing CA -> End-Entity Certificates. CRL (Certificate Revocation List) is a periodic list; OCSP (Online Certificate Status Protocol) provides real-time checks. Compromised Subordinate CA: Revoke certs issued by that CA. Compromised Root CA: Revoke all certs in the hierarchy, requiring re-enrollment.

OP9 — MPLS (High cost, reliable, low latency), IPsec (Low cost, variable latency), SD-WAN (Flexible, cost-effective, low latency), WireGuard (Simple, fast). For 50 users/site with VoIP: SD-WAN is recommended. It balances cost, reliability, and latency better than MPLS, and is easier to manage than IPsec mesh.

OP10 — iDRAC/iLO/IPMI are out-of-band management interfaces allowing remote server control (power, console) independent of the OS. Critical for troubleshooting. Exposing IPMI to the internet is a severe security risk, allowing attackers to gain root access to the hardware.

OP11 — LVM manages logical volumes on physical disks. LVM-Thin provides space efficiency (overcommitment). ZFS is a filesystem with integrated storage management. Snapshots: LVM (copy-on-write, slower), Thin (metadata-based, fast), ZFS (native, fastest). Use LVM for simple VM storage, Thin for high-density VMs, ZFS for file servers/databases requiring data integrity.

OP12 — A stretch cluster spans two sites. Ceph CRUSH rules must ensure data replicas are spread across sites. Monitor placement must be distributed (one per site). 2-site Ceph is risky because if one site loses all monitors, the cluster may lose quorum (split-brain). A tiebreaker (3rd site or cloud monitor) is required to prevent data loss.

OP13 — DHCP DORA: Discover (client), Offer (server), Request (client), Ack (server). If the server is unavailable, the client cannot renew. If the lease expires without renewal, the client uses APIPA (169.254.x.x) and cannot access the network.

OP14 — Managed switches allow configuration (VLANs, QoS, ACLs). Unmanaged switches are plug-and-play. Managed switches are required in enterprises for traffic segmentation, security policies, and Quality of Service (QoS) for critical traffic like VoIP.

OP15 — NTP synchronizes system clocks. Accurate time is critical for log correlation, SSL certificate validation, and distributed consensus (e.g., databases). Clock drift can cause authentication failures, log analysis errors, and cluster consensus splits.

OP16 — Physical server = bare metal. VM = OS virtualization. Container = OS-level isolation. Run workloads on bare metal for maximum performance, lowest latency, or when hypervisor overhead is unacceptable (e.g., high-frequency trading, specialized DBs).

OP17 — UPS provides immediate backup power (minutes) to bridge to a generator. Generators provide long-term power. ATS (Automatic Transfer Switch) switches the load from the grid to the UPS, then to the generator, and back to the grid automatically.

OP18 — Active-Passive: One server active, one standby. Active-Active: Both serve traffic. For PostgreSQL HA with Pacemaker/Corosync: Configure a Virtual IP (VIP) floating between nodes. Use STONITH (fencing) to ensure only one node writes to the shared storage during failover. If the active node fails, the standby takes the VIP.

OP19 — 3-2-1 Rule: 3 copies, 2 media types, 1 offsite. RPO (Recovery Point Objective) = max data loss. RTO (Recovery Time Objective) = max downtime. Backup = data copy; DR = full system recovery. Test restores regularly. Immutable backups (WORM) prevent ransomware from encrypting backups.

OP20 — 802.1X: Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP-TLS uses certificates; PEAP uses passwords. RADIUS validates credentials. Dynamic VLAN assignment assigns the port to a VLAN based on the user. If auth fails, the port is blocked (blacklisted). MAB (MAC Authentication Bypass) allows devices without 802.1X (like printers) to authenticate based on their MAC address.
