## Cloud Infrastructure Architecture

CL1 — Easy: **IaaS** provides virtualized hardware (compute, storage, network) where you manage the OS and apps (e.g., AWS EC2). **PaaS** provides a platform for developing/deploying apps without managing infrastructure (e.g., AWS Elastic Beanstalk). **SaaS** delivers software over the internet (e.g., Microsoft 365).

CL2 — Easy: **Shared Responsibility Model**:
*   **IaaS VMs**: Provider manages physical hardware, hypervisor, and network; you manage OS, middleware, runtime, data, and apps.
*   **Managed Kubernetes**: Provider manages control plane (nodes, networking, API server); you manage workloads, pods, and application data.
*   **SaaS (M365)**: Provider manages everything (infrastructure, platform, application); you manage user access, data, and security policies.

CL3 — Medium: **VPC** is a logical isolation boundary. **Subnet** is a range of IP addresses within a VPC. **Security Group** is a stateful firewall attached to instances (allows/ denies traffic per port). **NACL** is a stateless firewall attached to subnets (rules applied to traffic entering/leaving the subnet). **Layering**: VPC > Subnet > NACL > Security Group. **Stateful**: Security Groups remember connection state (return traffic allowed automatically). **Stateless**: NACLs must explicitly allow return traffic.

CL4 — Medium: **Multi-account strategy**:
*   **Landing Zone**: Pre-provisioned foundation (accounts, networking, logging).
*   **Organizational Units (OUs)**: Hierarchical grouping of accounts for policy application.
*   **Guardrails**: SCPs (AWS) or Policy-as-Code (Azure) to enforce compliance.
*   **Shared Networking**: Transit Gateway (AWS) or Hub-and-Spoke (Azure) for centralized routing.
*   **Centralized Logging**: Centralized S3/Log Analytics bucket for all account logs.
*   **Single-account problem**: Limits isolation, scaling, and compliance; creates single point of failure for billing/identity.

CL5 — Medium: **IaC**:
*   **Terraform/OpenTofu**: Declarative, state-based, multi-cloud. Best for complex, multi-cloud infra.
*   **Pulumi**: Declarative using modern languages (Python/TS). Best for teams with strong coding skills.
*   **CloudFormation/Bicep**: Native provider tools. Best for single-provider deep integration.
*   **Crossplane**: Kubernetes-native, manages cloud resources as K8s CRDs. Best for K8s-centric orgs.

CL6 — Medium: **Autoscaling**:
*   **HPA**: Scales pods based on CPU/Memory.
*   **VPA**: Scales pod resource requests/limits (usually for optimization, not runtime scaling).
*   **Cluster Autoscaler**: Adds/removes nodes based on pod demand.
*   **KEDA**: Scales based on external events (queue depth, HTTP requests).
*   **KEDA vs HPA**: Use KEDA for event-driven workloads (e.g., processing messages in a queue) where CPU is not the primary driver.

CL7 — Hard: **DR Strategy**:
*   **RPO/RTO**: Define max data loss (RPO) and max downtime (RTO).
*   **Active-Active vs Passive**: Active-Active (load balanced across regions) vs Active-Passive (failover).
*   **DB Replication**: Sync (zero RPO) vs Async (low RPO).
*   **DNS Failover**: Route53/Traffic Manager switches traffic to healthy region.
*   **State Management**: Use stateless services (Redis Cluster) or consistent snapshots.
*   **DR Types**: **Pilot Light** (minimal resources, spin up on failover). **Warm Standby** (partial resources, scaled up). **Multi-site Active-Active** (full resources, load balanced).
*   **Cost**: Active-Active is most expensive; Pilot Light is cheapest.

CL8 — Hard: **GitOps**:
*   **Model**: Infrastructure/App state defined in Git repo; CD tool syncs cluster to Git.
*   **ArgoCD vs FluxCD**: ArgoCD is K8s-native, Flux is Helm-based. ArgoCD has better UI/UX.
*   **Secrets**: Use Sealed Secrets (encrypt in Git) or External Secrets Operator (sync from Vault).
*   **Drift**: If manual change occurs, GitOps tool detects drift and auto-reverts or alerts for review.

CL9 — Hard: **Stateful K8s**:
*   **StatefulSet**: Ensures stable network IDs and persistent storage.
*   **PV/PVC**: Use Local Persistent Volume (LocalPath) for low latency.
*   **Headless Service**: DNS resolution for stable pod IPs (e.g., svc-0, svc-1).
*   **Init Containers**: Mount config files before main app starts.
*   **ConfigMaps**: Mount as volumes for config files.
*   **Pod Disruption Budget**: Ensures availability during node maintenance.

CL10 — Medium: **Identity**:
*   **Service Account**: K8s identity for pods.
*   **Workload Identity**: Cloud-native binding (e.g., GCP/Azure) to map K8s SA to cloud IAM.
*   **IRSA**: AWS specific (IAM Roles for Service Accounts).
*   **Mounting Creds**: Bad practice due to credential rotation risks and secret leakage.
*   **Workload Identity**: Solves this by allowing pods to assume cloud IAM roles without storing secrets.

CL11 — Medium: **Storage**:
*   **Object (S3/Blob)**: Files/Blobs, high durability (99.999999999%), no latency SLA. Use for backups, static assets.
*   **Block (EBS/Managed Disk)**: VM disks, high IOPS, low latency. Use for OS/App data.
*   **File (EFS/Azure Files)**: Shared file system, NFS/SMB protocol. Use for shared app data.
*   **Guarantees**: Object is most durable; Block/File has higher availability SLAs for I/O.

CL12 — Hard: **Zero Trust K8s**:
*   **Network Policies**: Default deny all traffic.
*   **Service Mesh (mTLS)**: Istio/Linkerd for encrypted service-to-service comms.
*   **Pod Identity**: Bind identity to workload.
*   **Admission Controllers**: OPA/Kyverno for policy enforcement (e.g., no privileged containers).
*   **Image Signing**: Notary/Cosign for supply chain security.
*   **Runtime Security**: Falco for anomaly detection.
*   **Difference**: Traditional relies on perimeter (firewall); Zero Trust verifies every request regardless of location.

CL13 — Easy: **CDN**:
*   **Definition**: Network of edge servers caching content closer to users.
*   **Services**: AWS CloudFront, Azure CDN.
*   **Use Case**: Use CDN for static assets (images, CSS) to reduce latency. Use origin for dynamic content requiring real-time processing.

CL14 — Easy: **AZ/Region**:
*   **Region**: Geographic location (e.g., us-east-1).
*   **AZ**: Isolated data centers within a region (power/network).
*   **Multi-AZ**: Deploy across AZs for HA (survives AZ failure).
*   **Zonal vs Regional**: Zonal resources (e.g., EC2) are in one AZ; Regional resources (e.g., S3) are replicated across AZs.

CL15 — Easy: **Managed DB**:
*   **Service**: RDS, Cloud SQL, Azure SQL.
*   **Provider Tasks**: Patching, backups, HA (multi-AZ), scaling, monitoring.
*   **User Tasks**: Schema design, query optimization, app connectivity.

CL16 — Easy: **IAM**:
*   **Users**: Human identities. **Roles**: Permissions for users/services. **Groups**: Collection of users. **Policies**: JSON rules defining permissions.
*   **Least Privilege**: Grant only permissions necessary for the task. Apply via IAM Policies (e.g., `Allow` only `s3:GetObject`).

CL17 — Easy: **Serverless**:
*   **Definition**: FaaS (Function as a Service), pay per execution.
*   **Comparison**: Lambda (AWS), Functions (Azure), Cloud Functions (GCP).
*   **Cold Starts**: Latency on first invocation. Matters for latency-sensitive apps.
*   **Poor Fit**: Long-running processes, stateful apps, high sustained throughput.

CL18 — Medium: **Ingress**:
*   **Ingress Resource**: K8s API object for external access.
*   **Gateway API**: New K8s standard, more flexible (HTTPRoute).
*   **Cloud LB Annotations**: Direct K8s to Cloud LB (e.g., ALB).
*   **Service Mesh**: Ingress Gateway (e.g., Istio) for mTLS/traffic control.
*   **TLS**: Terminated at Cloud LB (Edge) or Ingress Controller (Sidecar).
*   **Gateway API**: Use for advanced routing (canary, retries) and standard compliance.

CL19 — Hard: **Cost Optimization**:
*   **Pricing**: Savings Plans (flexible) > Reserved Instances (fixed). Spot for fault-tolerant workloads.
*   **Right-sizing**: Use CloudWatch metrics to match instance size.
*   **Storage Tiering**: Move infrequent data to S3 Glacier/Archive.
*   **Idle Detection**: Use tools (AWS Compute Optimizer) to find unused resources.
*   **FinOps**: Culture of cost ownership.
*   **Showback/Chargeback**: Allocate costs to teams via tags.
*   **Tools**: AWS Cost Explorer, Azure Cost Management.

CL20 — Hard: **Multi-cloud**:
*   **Strategy**: Use K8s as abstraction layer (EKS/AKS). Use Terraform for IaC portability.
*   **Networking**: AWS Direct Connect/Azure ExpressRoute + Interconnect (e.g., Cloud Router).
*   **Identity**: Federation (OIDC/SAML) between clouds.
*   **Trade-offs**: Multi-cloud adds complexity (network latency, tooling).
*   **Justification**: Avoid lock-in, compliance requirements, or specific provider features. Unnecessary if single cloud meets needs.

## OT Infrastructure Architecture

OT1 — Easy: **Purdue Model (ISA-95)**:
*   **Level 0**: Physical Process (Sensors/Actuators).
*   **Level 1**: Basic Process Control (PLCs/Controllers).
*   **Level 2**: Supervisory Control (SCADA/HMI).
*   **Level 3**: Enterprise Control (MES/ERP).
*   **Level 4**: Business Management (ERP/Finance).
*   **Level 5**: Enterprise Management (Strategic).

OT2 — Easy: **IT vs OT**:
*   **IT**: Focus on data availability, confidentiality, and speed.
*   **OT**: Focus on safety, reliability, and uptime.
*   **Patching**: IT patches frequently; OT patches risk unplanned downtime or safety hazards.

OT3 — Medium: **DMZ (IDMZ)**:
*   **Role**: Buffer between IT (Level 3/4) and OT (Level 1/2).
*   **Traffic**: IT -> OT (Allowed: specific queries, e.g., historian access). OT -> IT (Allowed: logs/alerts only).
*   **Danger**: Direct L4-L1 connectivity allows IT threats to reach control systems directly.

OT4 — Medium: **Protocols**:
*   **Modbus TCP**: Level 1/2 (Simple, serial-based).
*   **OPC UA**: Level 2/3 (Secure, platform-independent).
*   **EtherNet/IP**: Level 1/2 (Industrial Ethernet, CIP).
*   **PROFINET**: Level 1/2 (High performance, deterministic).
*   **MQTT**: Level 2/3 (Lightweight, pub/sub, often for telemetry).

OT5 — Medium: **Data Diode**:
*   **Concept**: Hardware firewall allowing traffic only in one direction (e.g., OT to IT).
*   **Use**: Critical telemetry data where return traffic is impossible (e.g., preventing malware from OT to IT).
*   **Limitation**: Cannot block bi-directional threats; requires physical separation.

OT6 — Medium: **Data Flow**:
*   **Flow**: PLC -> Historian (Local) -> Edge Gateway -> MQTT Broker -> Cloud Ingestion.
*   **Boundaries**: Security boundary at Edge Gateway (IDMZ). OT data never touches IT network directly.

OT7 — Hard: **Zones/Conduits**:
*   **Zone**: Logical boundary (e.g., Corporate, Engineering, SCADA, PLC).
*   **Conduit**: Connection between zones (e.g., Firewall, Diode).
*   **Model**: Zone 1 (Corporate), Zone 2 (Engineering), Zone 3 (SCADA), Zone 4 (PLC), Zone 5 (SIS). Conduits connect adjacent zones with strict rules.

OT8 — Hard: **Segmentation**:
*   **VLAN**: Separate VLANs per production line/function.
*   **Firewall**: Between VLANs (e.g., between Engineering and PLC).
*   **Switch**: Layer 3 switches for routing between VLANs.
*   **Remote Access**: Jump host with MFA.
*   **Transition**: Shadow VLANs (mirror traffic) before moving devices to new VLANs.

OT9 — Hard: **SIS vs BPCS**:
*   **SIS**: Safety Instrumented System (IEC 61511), stops process on hazard.
*   **BPCS**: Basic Process Control, manages normal operation.
*   **Isolation**: SIS must be isolated to prevent ransomware from disabling safety.
*   **Impact**: Ransomware on SIS = Plant shutdown (safety risk).

OT10 — Medium: **PLC vs DCS vs SCADA**:
*   **PLC**: Discrete control, small scale, rugged.
*   **DCS**: Continuous control, large scale, integrated.
*   **SCADA**: Monitoring/Remote control, distributed.
*   **Coexistence**: Yes, often used together (e.g., DCS for process, SCADA for monitoring).

OT11 — Medium: **Remote Access**:
*   **Architecture**: Jump host (bastion), MFA, Session Recording.
*   **Vendor Access**: Time-limited, ticket-based.
*   **RDP to HMI**: Unacceptable (direct access to control interface).

OT12 — Hard: **Incident Response**:
*   **Detection**: IDS/Anomaly detection on network traffic.
*   **Inventory**: Know all assets (IPs, protocols).
*   **Response**: Isolate network segment, notify control room.
*   **Operator Role**: Manual override if automation fails; ensure safety first.
*   **Coordination**: IT supports OT, OT operators manage process.

OT13 — Easy: **HMI**:
*   **Definition**: Interface for operators to monitor/control machines.
*   **Role**: Visualize process data, send commands.
*   **Difference**: Engineering Workstation is for configuration/debugging; HMI is for runtime operation.

OT14 — Easy: **Historian**:
*   **Definition**: Time-series database for process data.
*   **Importance**: Trend analysis, compliance, troubleshooting.
*   **Plant vs Enterprise**: Plant (Level 3, operational data), Enterprise (Level 4, business metrics).

OT15 — Easy: **Ladder Logic**:
*   **Definition**: Programming language resembling relay logic.
*   **Device**: PLC.
*   **Dominance**: Familiarity for electricians, legacy systems, ease of debugging.

OT16 — Easy: **RTU vs PLC**:
*   **RTU**: Remote, harsh environment, simple I/O.
*   **PLC**: Local, complex logic, industrial control.
*   **Deployment**: RTUs for pipelines/remote sites; PLCs for factories.

OT17 — Easy: **Signals**:
*   **Analog**: 4-20mA (Current), 0-10V (Voltage).
*   **Digital**: On/Off states.
*   **4-20mA Preference**: Allows "live zero" check (0mA = broken wire). 0-20mA cannot distinguish between 0mA signal and broken wire.

OT18 — Medium: **Asset Inventory**:
*   **Foundation**: Security cannot protect what you don't know.
*   **Tools**: Passive (sniffing) vs Active (ping/scanning).
*   **Active Scanning**: Dangerous (DoS, triggers safety systems). Use passive where possible.

OT19 — Hard: **MITRE ATT&CK for ICS**:
*   **Framework**: Maps adversary tactics/techniques to ICS.
*   **Tactics**: e.g., T1190 (Exploit Public-Facing App), T1059 (Command and Scripting Interpreter).
*   **Difference**: Enterprise ATT&CK is general IT; ICS includes industrial-specific techniques (e.g., T1200 - Industrial Protocol Manipulation).
*   **Assessment**: Compare current controls against matrix to find gaps.

OT20 — Hard: **Converged SOC**:
*   **Log Collection**: Syslog/Modbus over secure channel (no impact on real-time).
*   **SIEM**: Integrate OT logs with IT logs.
*   **Rules**: OT-specific (e.g., unexpected protocol changes).
*   **Staffing**: Mix of IT analysts (logs) and OT engineers (context).
*   **False Positives**: High due to process variance.
*   **Firmware Alert**: Verify intent (is it a scheduled update?). If malicious, isolate device and patch.
