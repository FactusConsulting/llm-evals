## Application Architecture (20 questions)

**AA1**
A monolith is a single application with a unified codebase and database. Microservices decompose the app into independent services communicating via APIs.
**3 Concrete Problems:**
1.  **Distributed Complexity:** Debugging and tracing across services is harder than in a single process.
2.  **Network Latency:** Inter-service communication introduces latency and failure points (network partitions) that don't exist in a monolith.
3.  **Operational Overhead:** Managing multiple deployments, versions, and infrastructure components increases CI/CD and monitoring complexity.

**AA2**
**Synchronous:** Caller waits for a response (Request-Response). Example: HTTP/REST, gRPC.
**Asynchronous:** Caller sends a message and continues without waiting. Example: Message Queues (RabbitMQ), Event Bus (Kafka).
**Difference:** Sync blocks the caller; Async decouples the producer and consumer.

**AA3**
An **API Gateway** handles business logic (auth, rate limiting, aggregation, transformation). A **Reverse Proxy** handles traffic routing, SSL termination, and load balancing.
**Can Gateway replace Reverse Proxy?** No. While they overlap, a reverse proxy often handles Layer 4 (TCP/UDP) routing and performance optimization (connection pooling) that a high-level API Gateway might not handle efficiently. A Gateway is application-layer focused; a Proxy is transport-layer focused.

**AA4**
The **Saga pattern** manages long-running transactions across services without a distributed transaction manager (2PC).
**Choreography:** Services publish events; others react. Decoupled but hard to manage rollback logic.
**Orchestration:** A central coordinator tells services what to do. Easier to manage rollback but introduces a single point of coordination.
**Appropriateness:** Use Choreography for loosely coupled, event-driven systems. Use Orchestration for complex workflows requiring strict control.

**AA5**
**CQRS** separates Read (Query) and Write (Command) models.
**Paired with Event Sourcing:** Writes are stored as an event log; reads are projected from this log.
**Problem Solved:** Traditional CRUD struggles with read performance (denormalization) and complex query requirements. CQRS allows optimizing the read model for specific queries while keeping the write model simple, solving the "write-heavy vs read-heavy" bottleneck.

**AA6**
**Circuit Breaker** prevents cascading failures by stopping calls to a failing service.
**Three States:**
1.  **Closed:** Normal operation.
2.  **Open:** Failures detected; calls fail immediately.
3.  **Half-Open:** Testing if service recovered; limited calls allowed.
**Difference from Retry:** Retry keeps hammering a failing service. Circuit Breaker stops the hammering.
**Usage Together:** Use Retry with backoff for transient errors, but wrap it in a Circuit Breaker to stop retrying if failures persist.

**AA7**
1.  **Shared DB, Shared Schema:**
    *   *Cost:* Lowest. *Security:* Low (row-level isolation). *Ops:* Low. *Noise:* High.
2.  **Shared DB, Separate Schema:**
    *   *Cost:* Medium. *Security:* Medium (schema isolation). *Ops:* Medium. *Noise:* Medium.
3.  **Separate DB per Tenant:**
    *   *Cost:* Highest. *Security:* High (physical isolation). *Ops:* High (many DBs). *Noise:* None.
**Recommendation:** Start with Shared Schema for cost, move to Separate Schema for security, or Separate DB for enterprise-grade isolation.

**AA8**
**Eventual Consistency:** Data converges over time. **Strong Consistency:** Data is identical across all nodes immediately.
**Inventory Oversell:** Requires Strong Consistency.
**Architecture:** Use a centralized inventory service with a strong-consistency database (e.g., PostgreSQL with row-level locking or a dedicated inventory DB). Do not rely on distributed caching (Redis) for the final count without a locking mechanism. Use optimistic locking or distributed locks (Redisson) to prevent concurrent writes from exceeding stock.

**AA9**
A **Sidecar Proxy** runs alongside a service to handle cross-cutting concerns (traffic, security).
**Envoy/Istio:** Envoy is the sidecar (Data Plane). Istiod is the control plane that configures Envoy.
**Data Plane:** Envoy handles actual traffic. **Control Plane:** Istiod manages configuration.
**mTLS Problem:** Application-level TLS requires code changes. Sidecar mTLS handles encryption between services automatically, simplifying security and enabling zero-trust without app redeployment.

**AA10**
**Strangler Fig:** Incrementally migrate functionality from legacy to new system.
**Strategy:**
1.  Wrap legacy .NET Framework app behind an API Gateway.
2.  Identify a small module (e.g., "User Service").
3.  Build .NET 8 microservice for that module.
4.  Route traffic for that module to the new service via the Gateway.
5.  Repeat until all modules are migrated, then retire the legacy app.

**AA11**
**12-Factor App:** Methodology for building cloud-native apps.
**6 Factors:**
1.  **Codebase:** Versioned in one repo.
2.  **Dependency:** Explicitly declared.
3.  **Config:** Externalized (Env Vars).
4.  **Backing Services:** Treated as attached resources.
5.  **Build, Release, Run:** Strict separation.
6.  **Process:** Stateless (scale horizontally).
**Importance:** Ensures portability, scalability, and ease of deployment across environments.

**AA12**
**Event-Driven (Kafka):** Decoupled, high throughput, complex debugging, eventual ordering, async failure handling.
**Request-Driven (REST/gRPC):** Coupled, lower throughput, easy debugging, synchronous ordering, immediate failure handling.
**Choice:** Use Event-Driven for audit trails, decoupled systems, and high-scale data ingestion. Use Request-Driven for real-time user interactions and simple CRUD operations.

**AA13**
A **Load Balancer** distributes traffic across servers.
**Layer 4:** Operates on IP/Port (TCP/UDP). Fast, stateless.
**Layer 7:** Operates on HTTP/HTTPS (Headers, Host). Can route based on URL path.
**L7 Use Case:** Routing `/api/v1` to Service A and `/api/v2` to Service B.

**AA14**
**Message Queue (RabbitMQ):** Point-to-point or Pub/Sub, low latency, guaranteed delivery.
**Log-based Broker (Kafka):** Append-only log, high throughput, replayable, eventual consistency.
**Choice:** Pick RabbitMQ for transactional, low-latency messaging. Pick Kafka for event streaming, analytics, and replayability.

**AA15**
A **Container** packages code and dependencies with a lightweight OS layer (shared kernel). A **VM** virtualizes hardware with a full OS.
**Difference:** Containers are lighter, start faster, and share the host kernel. VMs are isolated at the hardware level.
**Popularity:** Containers offer high density, fast scaling, and portability (Docker/Kubernetes) ideal for microservices.

**AA16**
**Stateless:** No server memory dependency (e.g., Web Server). Easy to scale horizontally because any instance can handle any request.
**Stateful:** Depends on server memory (e.g., Database, Cache). Hard to scale horizontally.
**Example:** Stateless = Nginx. Stateful = PostgreSQL.

**AA17**
**ORM:** Maps database tables to object classes.
**Examples:** Hibernate (Java), Entity Framework (.NET).
**Trade-offs:** ORMs increase productivity but can lead to performance issues (N+1 queries) and abstraction leaks. Raw SQL offers maximum performance and control but requires more maintenance.

**AA18**
**Bulkhead Pattern:** Isolates resources (threads, CPU, memory) to prevent one failure from exhausting system resources.
**Relation:** Ensures that a failure in one service (e.g., DB) doesn't starve other services (e.g., HTTP).
**Implementation:** Use separate thread pools for different operations (e.g., one pool for DB calls, one for external API calls). Or deploy separate instances of a service for different tenants.

**AA19**
**OT (Operational Transformation):** Server-side conflict resolution. Real-time, low latency, complex logic.
**CRDTs:** Client-side conflict resolution. Supports offline editing, simpler logic, eventual consistency.
**Comparison:** OT is harder to implement and debug. CRDTs are easier and support offline.
**Choice:** Choose **CRDTs** for offline editing support because they allow the client to make changes locally and merge them later without complex server-side coordination.

**AA20**
**Challenges:** Context propagation across languages, sampling overhead, storage costs, async correlation.
**Propagation:** Use W3C Trace Context (TraceID, SpanID) injected into headers.
**Sampling:** Head-based (decide at start) vs Tail-based (decide at end). Head-based saves storage.
**Storage:** Jaeger/Tempo store spans for querying.
**Async/Kafka:** Use headers to carry TraceID/ParentID through the message. The consumer creates a child span using the parent ID from the message headers to ensure continuity.

## On-Premise Infrastructure Architecture (20 questions)

**OP1**
**Type 1 (Bare-metal):** Hypervisor runs directly on hardware (e.g., VMware ESXi, Xen).
**Type 2 (Hosted):** Hypervisor runs on top of an OS (e.g., VMware Workstation, VirtualBox).
**Difference:** Type 1 is for production servers; Type 2 is for development/testing.

**OP2**
**SAN (Storage Area Network):** Block-level storage (e.g., iSCSI, Fibre Channel). Used for databases requiring direct disk access.
**NAS (Network Attached Storage):** File-level storage (e.g., NFS, SMB). Used for file sharing, backups.
**Protocols:** SAN uses iSCSI/FC. NAS uses NFS/SMB.

**OP3**
**3-Tier:** Core (Routing), Distribution (Aggregation), Access (Servers). Hierarchical.
**Leaf-Spine:** Flat fabric. Every leaf connects to every spine.
**Problem Solved:** Leaf-spine eliminates bottlenecks and latency issues inherent in hierarchical 3-tier designs, allowing linear scaling and equal path latency.

**OP4**
**Architecture:** 3+ nodes (odd number for quorum). Shared storage (Ceph preferred for HA).
**Quorum:** Majority of nodes must be alive.
**Fencing:** STONITH (Shoot The Other Node In) prevents split-brain.
**Failure:** If a node fails, others detect loss of quorum. If storage is shared, Ceph replicates data. If storage is local, VMs failover to other nodes.

**OP5**
**VLAN Trunking:** Carries multiple VLANs over a single link.
**802.1Q:** Adds a 4-byte tag to Ethernet frames.
**Linux Config:**
1.  Create VLAN interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.
2.  Assign IPs: `ip addr add 192.168.10.1/24 dev eth0.10`.
3.  Repeat for other VLANs.

**OP6**
**RAID Types:**
*   **RAID 1:** Mirror (2 drives).
*   **RAID 5:** Striping + 1 Parity (3+ drives).
*   **RAID 6:** Striping + 2 Parity (4+ drives).
*   **RAID 10:** Mirror + Stripe (4+ drives).
*   **RAID Z2:** ZFS Mirror + Parity (4+ drives).
**Choice:** For 6 drives and a DB, choose **RAID 10** or **ZFS RAID-Z2**. RAID 10 offers best performance (no parity calculation). ZFS offers data integrity (checksums).

**OP7**
**Architecture:**
*   **Recursive Resolvers:** ISP or internal DNS servers.
*   **Authoritative Servers:** Host internal zones (AD) and DMZ zones.
*   **Split-Horizon:** Internal clients query internal DNS; External clients query public DNS.
*   **DNSSEC:** Sign external zones to prevent spoofing.
*   **Movement:** Laptop moves via DHCP. Split-horizon handles the switch based on the client's domain suffix or IP range.

**OP8**
**Chain:** Root CA (Offline) -> Subordinate CA (Issuing) -> End Entity (Server).
**CRL vs OCSP:** CRL is a list of revoked certs (periodic). OCSP is real-time check.
**Compromise:**
*   **Root CA:** All certs issued by this org are compromised. Must revoke all.
*   **Subordinate CA:** Only certs issued by this subordinate are compromised. Revoke specific certs.

**OP9**
**Comparison:**
*   **MPLS:** High cost, high reliability, low latency.
*   **IPsec:** Low cost, internet risk, variable latency.
*   **SD-WAN:** Smart routing, cost-effective, good reliability.
*   **WireGuard:** Simple, fast crypto, mesh complexity.
**Recommendation:** **SD-WAN** or **MPLS**. For 50 users with VoIP, SD-WAN offers the best balance of cost and latency management (QoS) compared to MPLS.

**OP10**
**iDRAC/iLO/IPMI:** Out-of-band management interfaces (remote access to server hardware).
**Importance:** Allows rebooting, OS install, and hardware monitoring without physical access.
**Risk:** Exposing to the internet allows attackers to brute-force access, potentially taking control of the physical server.

**OP11**
**LVM:** Block-level volume management.
**LVM-Thin:** Space-efficient (overcommitment).
**ZFS:** File system with built-in compression, snapshots, and checksums.
**Snapshots:** LVM (Copy-on-Write), LVM-Thin (Instant), ZFS (Instant, integrated).
**Choice:** Use ZFS for databases requiring integrity and fast snapshots. Use LVM for simple block storage needs.

**OP12**
**Stretch Cluster:** Ceph across 2 sites.
**Problem:** 2-site Ceph is risky without a tiebreaker (3rd site). If one site loses all nodes, the cluster loses quorum (split-brain).
**Design:** Use CRUSH rules to ensure monitors are spread across sites. Use a tiebreaker (3rd site or cloud) to maintain quorum.

**OP13**
**DHCP:** Dynamic Host Configuration Protocol.
**DORA:** Discover, Offer, Request, Acknowledge.
**Unavailable:** Client gets APIPA address (169.254.x.x). Windows client lease expires = no IP, no network access.

**OP14**
**Managed Switch:** Configurable (VLANs, QoS, ACLs).
**Unmanaged Switch:** Plug-and-play.
**Enterprise Features:** Managed switches provide traffic segmentation (VLANs), security (ACLs), and performance optimization (QoS).

**OP15**
**NTP:** Network Time Protocol.
**Importance:** Critical for log correlation, SSL certificate validation, and distributed system consistency.
**Drift Consequences:** Cluster lock ordering issues, failed SSL handshakes, incorrect log analysis.

**OP16**
**Physical:** Bare metal hardware. **VM:** OS abstraction. **Container:** App abstraction.
**Bare Metal:** Use for high-performance DBs, latency-sensitive workloads, or when hypervisor overhead is unacceptable.

**OP17**
**UPS:** Battery backup for short-term power loss (minutes).
**Generator:** Long-term power (hours/days).
**ATS:** Automatically switches load from Utility -> UPS -> Generator.
**Role:** UPS bridges the gap until the generator starts.

**OP18**
**Active-Passive:** One server active, one standby.
**Active-Active:** Both servers handle load.
**Pacemaker/Corosync:** Manages cluster state.
**Fencing (STONITH):** Physically disconnects a failed node (e.g., power off) to prevent split-brain.
**Failover:** VIP floats to the active node. If active fails, standby takes VIP.

**OP19**
**Strategy:**
*   **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite.
*   **RPO/RTO:** Define max data loss and downtime.
*   **Types:** Full (weekly), Incremental (daily), Differential (daily).
*   **Immutable Backups:** Protect against ransomware.
*   **Backup vs DR:** Backup = Data copy. DR = System recovery (infrastructure + data).
*   **Testing:** Regular restore drills.

**OP20**
**802.1X:** Port-based access control.
**Roles:** Supplicant (Client), Authenticator (Switch), Authentication Server (RADIUS).
**Methods:** EAP-TLS (Certificate), PEAP (Password).
**Failure:** Access denied (port blocked).
**MAB:** MAC Authentication Bypass. Switch checks MAC address against a whitelist if 802.1X fails.
