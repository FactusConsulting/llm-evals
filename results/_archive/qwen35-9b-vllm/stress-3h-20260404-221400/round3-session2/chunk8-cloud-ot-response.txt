CL1 — Easy: IaaS (Infrastructure as a Service) provides virtualized computing resources (VMs, storage, networks) without managing hardware. Example: AWS EC2. PaaS (Platform as a Service) provides a platform for developing and running apps without managing infrastructure. Example: Google App Engine. SaaS (Software as a Service) delivers software over the internet. Example: Salesforce.

CL2 — Easy: The Shared Responsibility Model divides security duties. For IaaS VMs, the provider secures the physical infrastructure and hypervisor; you secure the OS, data, and applications. For managed Kubernetes, the provider secures the control plane and node infrastructure; you secure the workloads, policies, and data. For SaaS (e.g., M365), the provider manages the entire stack including data and security; you manage user access and identity.

CL3 — Medium: A VPC is a logical isolation boundary. A subnet is a range of IP addresses within a VPC. A Security Group (SG) is a stateful firewall attached to instances. A Network ACL (NACL) is a stateless firewall attached to subnets. Layering: VPC contains Subnets; Subnets have NACLs; Instances have SGs. Stateful filtering (SG) remembers connection state (return traffic allowed automatically); Stateless filtering (NACL) evaluates every packet independently.

CL4 — Medium: A Landing Zone provides a standardized foundation for multi-account environments. Organizational Units (OUs) group accounts for policy management. Guardrails enforce compliance (e.g., via SCPs). Shared networking uses a Transit Gateway (AWS) or Hub-and-Spoke (Azure) to connect accounts. Centralized logging aggregates logs (e.g., CloudTrail) into a central bucket. Single-account approaches are problematic due to resource limits, security isolation risks, and difficulty in scaling/multi-tenancy.

CL5 — Medium: IaC manages infrastructure via code. Terraform/OpenTofu uses a declarative state file; best for multi-cloud portability. Pulumi uses programming languages (Python/TS); best for complex logic. CloudFormation/Bicep are native AWS/Azure tools; best for deep provider integration. Crossplane uses Kubernetes CRDs; best for managing cloud resources as K8s objects. Choose based on team skills and ecosystem needs.

CL6 — Medium: HPA scales pod count based on CPU/Memory. VPA scales pod resource requests. Cluster Autoscaler adds/removes nodes. KEDA scales based on external events (e.g., queue depth). Use KEDA over HPA when scaling should be driven by specific events (e.g., message queue length) rather than general resource utilization, allowing for more granular, event-driven scaling.

CL7 — Hard: DR strategy depends on RPO (data loss) and RTO (downtime). Active-Active replicates workloads across regions; Active-Passive keeps one active. Database replication: Sync (zero RPO) vs Async (low RPO). DNS failover (Route53) directs traffic. State management requires consistent hashing or shared storage. Pilot Light (minimal standby), Warm Standby (partial resources), Multi-site Active-Active (full redundancy). Active-Active is most resilient but most expensive.

CL8 — Hard: GitOps uses Git as the source of truth for infrastructure/app state. ArgoCD and FluxCD sync cluster state to Git. Secrets are managed via Sealed Secrets (encrypted in Git) or External Secrets Operator (fetching from Vault). Manual changes cause drift; the GitOps controller detects drift and automatically reverts the cluster to match Git state.

CL9 — Hard: Use a StatefulSet for ordered, stable pod identities. Use Local Persistent Volumes (LocalPath) for low-latency local storage. Use a Headless Service for DNS-based service discovery (pod-to-pod). Use Init Containers to prepare the filesystem. Mount ConfigMaps as volumes for config files. Use Pod Disruption Budgets to ensure availability during scaling.

CL10 — Medium: A Service Account is a K8s identity. Workload Identity binds a K8s SA to a cloud IAM role (e.g., AWS IRSA). Mounting cloud credentials in a pod is bad because it exposes long-lived keys to the pod context. Workload Identity federation allows the pod to assume the role dynamically without storing keys, reducing attack surface.

CL11 — Medium: Object storage (S3/Blob) stores files as objects; high durability, no file system. Block storage (EBS/Disk) is raw disks for OS/DBs; high IOPS. File storage (EFS/Files) is shared file systems for apps. Durability: Object (99.999999999%), Block (99.99%), File (99.99%). Use Object for archives/media, Block for DBs/OS, File for shared app data.

CL12 — Hard: Zero Trust K8s requires denying all traffic by default. Network Policies enforce pod-to-pod isolation. Service Mesh (Istio) enforces mTLS. Pod Identity binds workloads to identities. Admission Controllers (OPA) enforce policies. Image signing (Notary) prevents bad images. Runtime security (Falco) detects anomalies. Unlike perimeter security, Zero Trust verifies identity and context for every request, regardless of location.

CL13 — Easy: A CDN caches content at edge locations closer to users. It works by storing copies of static assets globally. Services: AWS CloudFront, Azure CDN. Use a CDN for static assets (images, CSS) to reduce latency and origin load. Use the origin directly for dynamic content requiring real-time processing.

CL14 — Easy: A Region is a geographic area with multiple Availability Zones (AZs). An AZ is an isolated location with independent power/network. Deploy across AZs for High Availability (HA) to survive zone failures. Zonal resources are tied to one AZ; Regional resources span all AZs.

CL15 — Easy: A managed database (RDS/Cloud SQL) handles patching, backups, failover, and scaling. Running on a VM requires you to manage OS, database engine updates, backups, and HA configuration manually. Managed services reduce operational overhead and risk.

CL16 — Easy: IAM Users are humans; Groups organize users; Roles are permissions policies. Least Privilege means granting only the minimum permissions required for a task. Apply it by using roles with specific policies rather than admin access, and regularly auditing permissions.

CL17 — Easy: Serverless executes code in response to events without managing servers. Lambda/Functions/Cloud Functions are examples. Cold starts occur when a function is invoked after inactivity, causing latency. Serverless is poor for long-running processes, high I/O, or strict latency requirements where cold starts are unacceptable.

CL18 — Medium: Ingress resource is a K8s API object. Gateway API is the standard for Ingress. Cloud Load Balancer annotations configure K8s Ingress to use external LBs. Service Mesh ingress gateways handle traffic at the sidecar level. TLS termination: Ingress/Gateway terminates at the edge; Service Mesh terminates at the sidecar (mTLS). Use Gateway API for multi-protocol support and standardization.

CL19 — Hard: Cost optimization: Commit to Reserved Instances/Savings Plans for steady workloads; use Spot/Preemptible for fault-tolerant batch workloads. Right-size instances based on usage. Tier storage (S3 Intelligent-Tiering/Archive) for infrequent access. Detect idle resources (unattached EBS). Implement FinOps practices (culture, governance). Use Showback (cost visibility) or Chargeback (billing) to allocate costs to teams. Tools: AWS Cost Explorer, CloudHealth.

CL20 — Hard: Multi-cloud strategy uses abstraction layers (Kubernetes, Terraform) to avoid lock-in. Networking via Direct Connect/ExpressRoute/VPN. Identity via SAML/OIDC federation. Trade-offs: Higher complexity, cost, and latency. Multi-cloud is justified for compliance, risk avoidance, or specific regional requirements; it is unnecessary complexity if a single cloud meets all needs.

OT1 — Easy: The Purdue Model (ISA-95) defines 7 levels of industrial automation. Level 0: Physical Process. Level 1: Basic Control (PLCs). Level 2: Supervisory Control (SCADA). Level 3: Enterprise Operations (MES). Level 4: Business Planning (ERP). Level 5: Business Management. Level 6: Corporate.

OT2 — Easy: IT networks prioritize data availability and confidentiality; OT networks prioritize safety and reliability. Standard IT patching is risky in OT because it can disrupt critical processes or cause safety hazards. OT patching requires rigorous testing, scheduling during maintenance windows, and often requires vendor approval.

OT3 — Medium: An IDMZ (Industrial DMZ) separates IT and OT networks. It allows controlled traffic (e.g., SCADA to IT for monitoring) while blocking direct IT-to-OT access. Direct connectivity from Level 4 (IT) to Level 1 (Control) is dangerous because a breach in IT could directly compromise safety systems or plant operations.

OT4 — Medium: Modbus TCP (L1): Simple, serial-based protocol for PLCs. OPC UA (L1/L2): Secure, platform-independent data exchange. EtherNet/IP (L1): Real-time industrial Ethernet. PROFINET (L1): High-performance Ethernet for automation. MQTT (L2/L3): Lightweight messaging for IoT/Supervisory systems.

OT5 — Medium: A data diode allows traffic in only one direction (e.g., OT to IT). A firewall allows bidirectional traffic with rules. Use a hardware data diode when data must flow from OT to IT (e.g., telemetry) but no return traffic is allowed to prevent malware injection. Limitation: No return communication.

OT6 — Medium: Data flow: PLC -> Historian (L1) -> Edge Gateway (L2) -> MQTT Broker (L2) -> Cloud Ingestion (L3). Security boundaries: Firewall between Edge and Cloud; IDMZ between OT and IT. Ensure the edge gateway is hardened and the cloud ingestion uses secure protocols (e.g., MQTT over TLS).

OT7 — Hard: IEC 62443 defines Zones (network boundaries) and Conduits (connections). Zone: A network boundary containing assets with similar security requirements. Conduit: A connection between zones. Model: Zone 1 (Corporate/IT), Zone 2 (Engineering), Zone 3 (SCADA), Zone 4 (PLCs/SIS). Conduits connect these zones via firewalls/gateways.

OT8 — Hard: Segmentation: VLANs per production line and function (Engineering, SCADA, PLC). Firewalls between VLANs. Switches: Industrial hardened, managed. Remote access: Via Jump Host/DMZ, not direct. Transition: Parallel run new network, migrate assets one by one, keep old network active until verified.

OT9 — Hard: SIS (Safety Instrumented Systems) stops processes in emergencies; BPCS (Basic Process Control) manages normal operations. IEC 61511 defines safety lifecycle. SIS must be isolated (air-gapped) to prevent cyber attacks from disabling safety functions. If ransomware reaches SIS, it could cause physical damage or environmental disasters.

OT10 — Medium: PLC: Discrete control, simple logic, local. DCS: Continuous control, complex, distributed. SCADA: Monitoring, wide area, supervisory. They can coexist: PLCs/DCS control the process; SCADA monitors and displays data.

OT11 — Medium: Remote access: Use a Jump Host (bastion) with MFA. Record sessions. Vendor access requires tickets and time limits. RDP directly to an HMI is unacceptable because it bypasses security controls and exposes the control system directly to the internet/corporate network.

OT12 — Hard: Detection: IDS/Anomaly detection on OT traffic. Inventory: Know all assets. Response: Isolate affected segment, notify control room (Safety First). Operator role: Monitor plant status, execute safe shutdown procedures if needed, not to troubleshoot the cyber incident.

OT13 — Easy: HMI (Human-Machine Interface) allows operators to monitor and control machinery. It differs from an Engineering Workstation, which is used for configuration, design, and maintenance, not real-time operation.

OT14 — Easy: A historian stores time-series process data. It is important for trend analysis and compliance. Plant Historian (L3) stores operational data for the plant. Enterprise Historian (L4) aggregates data from multiple plants for business analysis.

OT15 — Easy: Ladder Logic is a programming language resembling relay logic diagrams. It executes on PLCs. It remains dominant due to operator familiarity, ease of debugging, and hardware support.

OT16 — Easy: RTU (Remote Terminal Unit) is for remote, harsh environments (pipelines) with serial comms. PLCs are for local industrial environments with bus comms. Deploy RTUs where physical access is difficult or communication is long-distance/serial.

OT17 — Easy: Analog signals are continuous (4-20mA, 0-10V). Digital signals are discrete (0/1). 4-20mA is preferred over 0-20mA because it allows "live zero" (0mA indicates a fault, not a valid reading) and has better noise immunity over long distances.

OT18 — Medium: Asset inventory is the foundation of OT security. Tools: Passive monitoring (sniffing traffic) is safe; Active scanning (ping/port scan) can disrupt operations and is dangerous. Use passive discovery to avoid impacting real-time control.

OT19 — Hard: MITRE ATT&CK for ICS maps adversary tactics to OT environments. Tactics: Reconnaissance (e.g., T1595), Execution (e.g., T1059), Persistence (e.g., T1504), Privilege Escalation (e.g., T1078), Exfiltration (e.g., T1041). It differs from Enterprise ATT&CK by including OT-specific techniques (e.g., PLC manipulation). Use it to assess gaps by mapping current controls to required mitigations.

OT20 — Hard: Converged SOC: Collect OT logs (Syslog, Modbus) via agents or passive taps to SIEM. Use OT-specific detection rules (e.g., abnormal PLC behavior). Staffing: Hybrid IT/OT analysts. False positives: High in OT due to legitimate process changes. Firmware alert: Verify integrity, isolate device, patch offline, then restore.
