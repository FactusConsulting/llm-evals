## Cloud Infrastructure Architecture

**CL1**
**IaaS (Infrastructure as a Service):** You manage OS, middleware, data, and apps; provider manages hardware/virtualization. *Example:* AWS EC2.
**PaaS (Platform as a Service):** Provider manages infrastructure + runtime; you manage apps/data. *Example:* Google App Engine.
**SaaS (Software as a Service):** Provider manages everything; you use the software via interface. *Example:* Microsoft 365.

**CL2**
**Shared Responsibility Model:** Security is shared.
*   **IaaS VMs:** Provider secures physical host, hypervisor, and network. You secure OS, apps, data, and IAM.
*   **Managed Kubernetes:** Provider secures control plane (nodes, API server). You secure workloads (pods, secrets, network policies).
*   **SaaS (M365):** Provider secures the entire stack (servers, apps, data). You manage user identity, access policies, and data retention.

**CL3**
**VPC:** Logical isolation of network resources within a cloud region.
**Subnet:** IP range within a VPC (e.g., public vs. private).
**Security Group:** Stateful firewall attached to instances (allows inbound, allows return traffic).
**NACL:** Stateless firewall attached to subnets (rules apply to all traffic entering/leaving subnet).
**Layering:** VPC contains Subnets; Subnets have NACLs; Instances have Security Groups.
**Stateful vs Stateless:** SG tracks connection state (if you allow Inbound, Outbound is auto-allowed). NACL does not (must explicitly allow both directions).

**CL4**
**Multi-Account Strategy:**
*   **Landing Zone:** Pre-provisioned foundational services (IAM, Networking, Logging) for new accounts.
*   **Organizational Units (OUs):** Group accounts by function (Prod, Dev, Finance) for policy inheritance.
*   **Guardrails:** SCPs (Service Control Policies) to prevent non-compliant resources (e.g., no public S3 buckets).
*   **Shared Networking:** Hub-and-Spoke (Transit Gateway/Azure Hub) centralizes routing and security.
*   **Centralized Logging:** Aggregates logs (CloudTrail, VPC Flow Logs) into a single account for analysis.
**Single-Account Problem:** Limits isolation, creates single point of failure, complicates billing/permissions, and restricts scaling.

**CL5**
**IaC:** Managing infrastructure via code rather than manual clicks.
*   **Terraform/OpenTofu:** Declarative, multi-cloud, state-based. Best for complex, multi-cloud infra.
*   **Pulumi:** Programmatic (Python/TS), uses native SDKs. Best for teams with strong coding skills.
*   **CloudFormation/Bicep:** Native AWS/Azure. Best for single-cloud, deep integration with provider features.
*   **Crossplane:** K8s-native control planes. Best for managing cloud resources as K8s CRDs.

**CL6**
**HPA:** Scales pod count based on CPU/Memory metrics.
**VPA:** Scales pod resource requests/limits (CPU/RAM) based on usage.
**Cluster Autoscaler:** Adds/removes nodes based on pending pods.
**KEDA:** Scales based on external events (queue depth, HTTP requests).
**KEDA vs HPA:** Use KEDA when scaling should be driven by event volume (e.g., message queue backlog) rather than resource saturation, allowing for more granular, event-driven scaling.

**CL7**
**DR Strategy:**
*   **RPO/RTO:** Define max data loss (RPO) and max downtime (RTO).
*   **Active-Active:** Workloads run in both regions (high cost, high resilience). Active-Passive: Workloads in primary, standby in secondary.
*   **DB Replication:** Sync (zero RPO, high latency) vs Async (low RPO, low latency).
*   **DNS Failover:** Route53/Traffic Manager directs traffic to healthy region.
*   **State:** Shared state (hard to replicate) vs Local state (easier to replicate).
*   **DR Types:**
    *   **Pilot Light:** Minimal resources (DB standby, no app instances). Fast recovery, low cost.
    *   **Warm Standby:** Partial resources (scaled-down app). Faster recovery, higher cost.
    *   **Multi-site Active-Active:** Full resources in both regions. Highest cost, highest resilience.

**CL8**
**GitOps:** Infrastructure/App state defined in Git repo; CD tool syncs cluster to Git.
*   **ArgoCD:** K8s-native, UI-heavy, sync loop.
*   **FluxCD:** Operator-based, Helm-native, lightweight.
*   **Secrets:** Use Sealed Secrets (encrypted in Git) or External Secrets Operator (fetch from Vault).
*   **Drift:** If manual change occurs, GitOps controller detects drift and reverts cluster to Git state (or alerts).

**CL9**
**Stateful App Design:**
*   **StatefulSet:** Ensures stable pod identities and ordering.
*   **Local PV/PVC:** Use `LocalPathProvisioner` for low-latency local storage.
*   **Headless Service:** DNS-based service discovery for specific pod IPs (no load balancing).
*   **Init Containers:** Run setup scripts (e.g., create directories) before main app starts.
*   **ConfigMaps:** Mount config files as volumes to specific paths.
*   **Pod Disruption Budget:** Ensures minimum pods are running during voluntary disruptions (e.g., node maintenance).

**CL10**
**Service Account:** K8s identity for pods.
**Workload Identity:** Maps K8s SA to cloud IAM (e.g., AWS IRSA, Azure AAD).
**IRSA:** AWS-specific implementation of Workload Identity.
**Mounting Creds:** Bad practice because credentials are static, hard to rotate, and if leaked, the pod has full access.
**Workload Identity:** Solves this by using the pod's identity to assume a cloud role dynamically, keeping secrets out of the pod.

**CL11**
**Object Storage (S3/Blob):** Unstructured data, API access, high durability (11 9s). Use for backups, media, logs.
**Block Storage (EBS/Disk):** Attached to VM, low latency, high IOPS. Use for OS, DBs.
**File Storage (EFS/Files):** Shared file system, NFS/SMB protocol. Use for shared app data.
**Guarantees:** Object (99.999999999% durability), Block (99.99% availability), File (99.99% availability).

**CL12**
**Zero Trust K8s:**
*   **Network Policies:** Default deny all traffic between pods.
*   **Service Mesh (Istio):** Enforces mTLS between services.
*   **Pod Identity:** Bind identity to workload (e.g., IRSA).
*   **Admission Controllers (OPA/Kyverno):** Enforce policies (e.g., no privileged containers).
*   **Image Signing:** Verify images via Cosign/Notary.
*   **Runtime Security (Falco):** Detect anomalous behavior (e.g., shell in container).
*   **Secrets:** Use external vault (Vault/Sealed Secrets).
**Difference:** Traditional model trusts internal network; Zero Trust verifies every request regardless of location.

**CL13**
**CDN:** Network of edge servers caching content closer to users.
**How:** Caches static assets at edge nodes; serves from cache if hit, fetches from origin if miss.
**Services:** AWS CloudFront, Azure CDN.
**Use Case:** Use CDN for static assets (images, CSS) to reduce latency. Use origin for dynamic/private content requiring auth.

**CL14**
**Region:** Geographic area with multiple Availability Zones (e.g., us-east-1).
**AZ:** Isolated data centers within a region (power, network).
**Deploy Across AZs:** Ensures High Availability (HA) against zone failure.
**Zonal vs Regional:** Zonal resources (e.g., NAT Gateway) are single-AZ. Regional resources (e.g., Load Balancer) span AZs.

**CL15**
**Managed DB:** Service like RDS/Cloud SQL.
**Provider Tasks:** Patching, backups, scaling, failover, monitoring, hardware maintenance.
**VM Self-Managed:** You handle all above tasks (OS updates, patching, backups, HA configuration).

**CL16**
**IAM:** Users (people), Groups (collections), Roles (permissions), Policies (rules).
**Least Privilege:** Grant only permissions necessary for the task.
**Application:** Use Roles for services, Groups for users, avoid Admin access unless absolutely required.

**CL17**
**Serverless:** Event-driven compute without managing servers.
**Comparison:** Lambda (AWS), Functions (Azure), Cloud Functions (GCP) are similar but differ in ecosystem and cold start behavior.
**Cold Starts:** Latency on first invocation due to provisioning. Matters for latency-sensitive apps.
**Poor Fit:** Long-running processes, high sustained throughput (reserved capacity is cheaper), stateful apps.

**CL18**
**Ingress Options:**
*   **Ingress Resource:** K8s API object, managed by controller.
*   **Gateway API:** New K8s standard, supports more protocols (HTTP/2, gRPC).
*   **Cloud LB:** Managed by provider (e.g., ALB), often easier to configure.
*   **Service Mesh:** Envoy-based, handles mTLS and traffic splitting.
**TLS:** Terminated at Cloud LB (Edge) or Ingress Controller (Ingress).
**Gateway API:** Use for multi-protocol support and standardization across clusters.

**CL19**
**Cost Optimization:**
*   **Commitments:** Savings Plans/RIs for steady workloads.
*   **Spot/Preemptible:** For fault-tolerant batch workloads (cheaper).
*   **Right-sizing:** Use CloudWatch/Advisor to match instance size to usage.
*   **Storage Tiering:** Move infrequent data to Glacier/Archive.
*   **Idle Detection:** Terminate unused resources.
*   **FinOps:** Tagging resources, cost allocation tags, showback/chargeback models.
*   **Tools:** AWS Cost Explorer, CloudHealth, Datadog.

**CL20**
**Multi-Cloud Strategy:**
*   **Abstraction:** Use K8s as runtime, Terraform for IaC.
*   **Networking:** AWS Direct Connect/Azure ExpressRoute + Transit Gateway peering.
*   **Identity:** OIDC federation between clouds.
*   **Trade-offs:** Higher complexity/cost vs. resilience/compliance.
*   **Justification:** Required for compliance (e.g., data sovereignty) or avoiding single-vendor lock-in. Unnecessary if one cloud meets all needs.

## OT Infrastructure Architecture

**OT1**
**Purdue Model (ISA-95):** Hierarchical architecture for industrial automation.
*   **Level 0:** Physical Process (Sensors/Actuators).
*   **Level 1:** Basic Process Control (PLCs, DCS).
*   **Level 2:** Supervisory Control (SCADA, HMI).
*   **Level 3:** Enterprise Control (MES, ERP).
*   **Level 4:** Business Management (ERP, Finance).
*   **Level 5:** IT/Management (Corporate IT).

**OT2**
**IT vs OT:** IT focuses on data availability and confidentiality; OT focuses on safety, reliability, and uptime.
**Patching:** IT patches frequently; OT patching requires downtime, testing, and risk assessment. Applying IT patches directly can crash critical control systems or cause safety hazards.

**OT3**
**IDMZ (Industrial DMZ):** Buffer zone between IT (L3/L4) and OT (L1/L2).
**Traffic:** Allowed from L4 to L2 (e.g., ERP to SCADA). Blocked from L2 to L4 (SCADA to ERP).
**Direction:** Generally L4 -> L2 allowed (monitoring), L2 -> L4 blocked (control).
**Direct L4 to L1:** Dangerous because it bypasses supervision, introduces latency, and exposes critical control systems directly to corporate vulnerabilities.

**OT4**
**Protocols:**
1.  **Modbus TCP:** L1 (PLC-to-PLC or PLC-to-HMI).
2.  **OPC UA:** L1/L2 (Secure, platform-independent data exchange).
3.  **EtherNet/IP (CIP):** L1 (Industrial Ethernet, Allen-Bradley).
4.  **PROFINET:** L1 (Siemens, real-time Ethernet).
5.  **MQTT:** L2/L3 (Lightweight messaging for IoT/SCADA).

**OT5**
**Data Diode:** Hardware device allowing data flow in only one direction (e.g., OT to IT).
**Firewall:** Bidirectional filtering.
**Use Diode:** When exporting data from OT to IT/Cloud where return traffic is never allowed (prevents malware from entering OT).
**Limitation:** No return traffic; cannot block specific bidirectional threats.

**OT6**
**Data Flow:** PLC -> Historian (L1) -> Edge Gateway (L2) -> MQTT Broker (DMZ) -> Cloud Ingestion (L3).
**Security Boundaries:**
*   **L1 to Edge:** Firewall/IDS.
*   **Edge to Cloud:** DMZ with strict egress rules.
*   **Cloud:** VPC with private subnets for ingestion.

**OT7**
**Zones:** Logical network boundaries (e.g., Corporate, Engineering, SCADA, PLC).
**Conduits:** Connections between zones (e.g., Firewall, Data Diode).
**Plant Model:**
*   **Zone 1 (Corporate):** IT, Email.
*   **Zone 2 (Engineering):** Workstations, Design.
*   **Zone 3 (SCADA):** Servers, Historian.
*   **Zone 4 (Control):** PLCs, SIS.
*   **Conduits:** Firewall between Zone 1-2, 2-3, 3-4.

**OT8**
**Segmentation Strategy:**
*   **VLANs:** Separate VLANs per production line and function (Engineering, SCADA, PLC).
*   **Firewalls:** Place firewalls between VLANs (L2-L3 segmentation).
*   **Switches:** Layer 3 switches for routing between VLANs.
*   **Vendor Access:** Jump host (bastion) with MFA; no direct access to OT VLANs.
*   **Transition:** Phased approach (segment one line at a time) or parallel run to ensure safety.

**OT9**
**SIS vs BPCS:** SIS (Safety Instrumented System) stops processes to prevent hazards; BPCS (Basic Process Control) optimizes production.
**IEC 61511:** Standard for functional safety lifecycle.
**Isolation:** SIS must be isolated (air-gapped or strict firewall) to prevent ransomware from locking safety systems.
**Ransomware Impact:** If SIS is compromised, operators may be forced to shut down production to ensure safety, causing massive financial loss.

**OT10**
**PLC:** Programmable Logic Controller (discrete control, local).
**DCS:** Distributed Control System (continuous process, complex, centralized).
**SCADA:** Supervisory Control and Data Acquisition (monitoring, wide area).
**Coexistence:** Yes. PLC/DCS at L1 (control), SCADA at L2 (supervision).

**OT11**
**Remote Access:**
*   **Jump Host:** Centralized access point.
*   **MFA:** Mandatory for all access.
*   **Session Recording:** Log all sessions for forensics.
*   **Vendor Access:** Time-limited, specific scope.
*   **No RDP to HMI:** HMIs are critical; direct access increases risk of malware injection and crashes.

**OT12**
**Detection/Response:**
*   **Monitoring:** IDS (e.g., Snort) on OT traffic, anomaly detection (baseline behavior).
*   **Inventory:** Know all assets (IPs, protocols).
*   **Response:** Isolate affected segment (firewall rule), notify control room.
*   **Operator Role:** Operators verify if safety is compromised; they may need to manually override or shut down systems if cyber threat impacts safety.
*   **Safety First:** Containment cannot compromise physical safety.

**OT13**
**HMI:** Human-Machine Interface (touchscreen/panel) for operators to monitor/control processes.
**Role:** Real-time visualization and manual intervention.
**Difference:** Engineering Workstation is for configuration, programming, and maintenance (not for real-time control).

**OT14**
**Historian:** Time-series database storing process data (tags, trends).
**Importance:** Data retention for analysis, compliance, and troubleshooting.
**Plant Historian (L3):** Stores operational data for the plant.
**Enterprise Historian (L4):** Aggregates data from multiple plants for corporate analysis.

**OT15**
**Ladder Logic:** Programming language resembling electrical relay logic (rungs).
**Device:** PLC.
**Dominance:** Familiarity for electricians, ease of debugging, hardware support, and simplicity for discrete control.

**OT16**
**RTU:** Remote Terminal Unit (serial, harsh environment, remote sites).
**PLC:** Programmable Logic Controller (Ethernet, local control, complex logic).
**Deployment:** RTUs for remote pipelines/fields; PLCs for factory floors.

**OT17**
**Analog Signals:** Continuous values (Voltage/Current).
**4-20mA vs 0-20mA:** 4-20mA allows "live zero" (0mA means broken wire, 4mA means 0% value). 0-20mA cannot distinguish between 0% value and broken wire.
**Preference:** 4-20mA is more robust against noise and allows fault detection.

**OT18**
**Asset Inventory:** List of all OT devices (IP, type, firmware). Foundation for security.
**Discovery:** Passive (sniffing traffic) vs Active (ping/scans).
**Active Scanning Risk:** Can trigger DoS, crash devices, or cause safety issues. Passive is preferred.

**OT19**
**MITRE ATT&CK for ICS:** Framework for adversary tactics/techniques in OT.
**5 Tactics:**
1.  **Reconnaissance:** (e.g., T1595 - Active Scanning).
2.  **Execution:** (e.g., T1190 - Exploit Public-Facing Application).
3.  **Persistence:** (e.g., T1505 - Server Software Component).
4.  **Privilege Escalation:** (e.g., T1548 - Abuse Elevation Control Mechanism).
5.  **Defense Evasion:** (e.g., T1070 - Obfuscated Logs).
**Difference:** Enterprise ATT&CK focuses on IT; ICS focuses on industrial protocols and safety.
**Assessment:** Map current controls to techniques to find gaps.

**OT20**
**Converged SOC:**
*   **Log Collection:** Syslog/SNMP from OT assets (non-intrusive).
*   **SIEM:** Centralize logs (e.g., Splunk, QRadar).
*   **OT Rules:** Detect protocol anomalies (e.g., unexpected Modbus commands).
*   **Staffing:** IT analysts for IT logs, OT engineers for OT context.
*   **False Positives:** High in OT due to normal process variations; tune rules.
*   **Firmware Alert:** Verify intent (is it a scheduled update?). If unauthorized, isolate the device and investigate before patching.
