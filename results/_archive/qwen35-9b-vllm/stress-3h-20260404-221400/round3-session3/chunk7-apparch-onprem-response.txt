AA1 — Easy: A monolith is a single codebase deployed as one unit, while microservices are independent services communicating over a network. Three concrete problems microservices introduce: 1) Distributed transactions (complexity of 2PC/Saga vs ACID), 2) Network latency and failure points (inter-service calls fail), 3) Operational complexity (deploying/updating multiple services vs one).

AA2 — Easy: Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST, gRPC). Asynchronous communication involves fire-and-forget or callback patterns where the caller does not wait (e.g., Message Queues like RabbitMQ, Kafka).

AA3 — Medium: An API Gateway handles business logic (auth, rate limiting, aggregation), while a reverse proxy handles traffic routing and SSL termination. An API Gateway cannot replace a reverse proxy entirely because proxies are often lighter, perform better at L4 routing, and are required for load balancing at the transport layer before the application logic is reached.

AA4 — Medium: The Saga pattern manages long-running transactions across services by breaking them into local transactions. Choreography uses events to trigger the next step (services react to events), while Orchestration uses a central coordinator to manage steps. Choreography is better for decoupled systems; Orchestration is better for complex workflows requiring rollback control.

AA5 — Medium: CQRS separates read and write operations into different models. It is paired with Event Sourcing (state is a log of events) to solve the read/write performance mismatch and provide a complete audit trail. Traditional CRUD struggles with read scaling and complex query optimization compared to optimized read models.

AA6 — Medium: Circuit Breaker prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failures, block calls), Half-Open (testing recovery). It differs from retry with backoff because it stops attempts entirely when failure is persistent. Use both together: Retry for transient errors, Circuit Breaker for persistent failures.

AA7 — Hard: 1. Shared DB/Schema: Lowest cost, highest noisy-neighbor risk, lowest security (row-level isolation). 2. Shared DB/Separate Schema: Medium cost, better isolation, moderate ops. 3. Separate DB: Highest cost, best security/performance, lowest noisy-neighbor risk, highest ops complexity.

AA8 — Hard: Eventual consistency allows data to converge over time; Strong consistency guarantees immediate visibility. For inventory (never oversell), use Strong Consistency (or Linearizable). Architect with a distributed lock (e.g., Redis/Zookeeper) or optimistic locking (DB versioning) on a strong-consistency store (e.g., PostgreSQL, DynamoDB with strong consistency).

AA9 — Hard: A sidecar proxy runs alongside a service to handle networking. In Istio, Envoy is the sidecar (data plane) handling traffic, while Istiod is the control plane managing policies. mTLS between sidecars solves service-to-service authentication without requiring app-level TLS changes, enabling zero-trust internal communication.

AA10 — Medium: The Strangler Fig pattern migrates functionality incrementally. Strategy: Wrap the legacy .NET Framework monolith behind an API Gateway. Build new .NET 8 microservices for specific features. Route specific API endpoints from the Gateway to the new services. Gradually shift traffic until the legacy monolith is retired.

AA11 — Medium: 12-Factor App is a methodology for building cloud-native apps. 6 Factors: 1) Codebase (versioned), 2) Dependencies (explicit), 3) Config (env vars), 4) Backing Services (treated as resources), 5) Build/Release/Run (separation), 6) Processes (stateless). They matter for portability, scalability, and security.

AA12 — Hard: Event-driven (Kafka) offers decoupling and high scalability but has higher debugging complexity and eventual consistency. Request-driven (REST/gRPC) offers tight coupling and synchronous guarantees but scales less elastically. Choose Event-driven for pipelines/logs; Request-driven for user-facing APIs requiring immediate feedback.

AA13 — Easy: A load balancer distributes traffic across servers. Layer 4 (TCP/UDP) balances based on IP/Port. Layer 7 (HTTP/HTTPS) balances based on content/URL. Layer 7 is required when routing traffic based on URL paths (e.g., /api vs /static) or SSL termination.

AA14 — Easy: A message queue (RabbitMQ) supports point-to-point/pub-sub with acknowledgments for task processing. A log-based broker (Kafka) is append-only, optimized for replayability and high throughput. Pick RabbitMQ for task queues; pick Kafka for event streams/audit logs.

AA15 — Easy: A container packages code and dependencies with a shared OS kernel, while a VM includes a full OS. Containers are popular for microservices due to higher density, faster startup times, and easier portability across environments.

AA16 — Easy: Stateless services do not store data in memory (e.g., Web Server), making them easy to scale horizontally. Stateful services store data (e.g., Database). Stateless services scale easily because any instance can handle any request without coordination.

AA17 — Easy: An ORM maps database tables to object classes (e.g., Hibernate for Java, Entity Framework for .NET). Trade-offs: ORMs offer productivity and safety but can suffer from performance issues (N+1 queries) and lack of control compared to raw SQL.

AA18 — Medium: The Bulkhead pattern isolates resources (threads, memory) to prevent one failure from exhausting shared resources. Example: Implement separate thread pools for database connections and HTTP requests. If the DB pool is exhausted, HTTP requests remain available.

AA19 — Hard: OT (Operational Transformation) resolves conflicts server-side (complex, requires history). CRDTs resolve conflicts client-side using mathematical properties (simpler, supports offline). CRDTs are chosen for offline editing because they guarantee convergence without server intervention and handle disconnected states better.

AA20 — Hard: Distributed tracing propagates context (TraceID/SpanID) via headers (W3C Trace Context). Sampling reduces storage costs. Storage (Jaeger/Tempo) aggregates spans. For Kafka, trace continuity is ensured by injecting headers into the message and extracting them on the consumer side to link producer and consumer spans.

OP1 — Easy: Type 1 (Bare-metal) runs directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) runs on top of an OS (e.g., VMware Workstation, VirtualBox).

OP2 — Easy: SAN (Storage Area Network) provides block-level storage (iSCSI, Fibre Channel) for high-performance DBs. NAS (Network Attached Storage) provides file-level storage (NFS, SMB) for general file sharing. Use SAN for databases; NAS for file servers.

OP3 — Medium: 3-tier (Core/Distribution/Access) creates a hierarchy that can bottleneck traffic. Leaf-Spine (flat topology) connects every leaf to every spine, solving the bottleneck and providing equal latency for all servers.

OP4 — Medium: Design a 3-node Proxmox cluster with Ceph or iSCSI shared storage. Ensure 2/3 quorum. Use STONITH (fencing) to prevent split-brain. If a node fails, the remaining nodes maintain quorum and take over VMs.

OP5 — Medium: VLAN trunking carries multiple VLANs over a single link using 802.1Q tags. On Linux, configure a bridge or use the `vlan` module: `ip link add link eth0 type vlan id 100`, `ip link add link eth0 type vlan id 200`, etc., then assign IPs to the VLAN interfaces.

OP6 — Hard: RAID 1 (Mirror), 5 (Striping+Parity), 6 (Striping+2Parity), 10 (Stripe+Mirror), Z2 (ZFS Mirror+Parity). For 6 drives DB: RAID 6 or ZFS RAID-Z2. They offer the best balance of capacity (4 usable drives), fault tolerance (survive 2 drive failures), and performance.

OP7 — Hard: DNS architecture: Primary/Secondary servers for redundancy. Forwarders to AD for internal resolution. Split-horizon: Internal zone for AD, External zone for public. DNSSEC signs external zones. When a laptop moves, DHCP updates DNS suffix or split-horizon rules route internal queries to AD and external to public resolvers.

OP8 — Hard: PKI Chain: Root CA (offline) -> Subordinate CA -> End-entity cert. CRL (list of revoked certs) vs OCSP (real-time check). Compromised Subordinate: Revoke certs issued by that CA. Compromised Root: Revoke all certs in the hierarchy, causing massive disruption.

OP9 — Hard: MPLS (expensive, reliable, low latency), IPsec (cheap, internet risk), SD-WAN (balanced, dynamic routing), WireGuard (simple mesh). For 50 users/VoIP: SD-WAN is recommended for balancing cost, reliability, and latency management over the internet.

OP10 — Medium: iDRAC/iLO/IPMI are out-of-band management interfaces. Critical for remote reboot/console access without OS. Exposing IPMI to the internet is a severe security risk (brute force attacks, hardware control).

OP11 — Medium: LVM (logical volumes), LVM-Thin (space efficient), ZFS (file system + storage). Snapshots: LVM (copy-on-write), Thin (metadata), ZFS (native, fast). Use LVM for simple VMs, Thin for high density, ZFS for file storage/VMs requiring data integrity.

OP12 — Hard: Stretch cluster across 2 sites requires Ceph CRUSH rules to place monitors and data. High latency risks split-brain. 2-site Ceph is bad without a tiebreaker because monitor quorum loss can cause data unavailability or corruption. Use a 3rd site or tiebreaker for safety.

OP13 — Easy: DHCP assigns IPs via DORA (Discover, Offer, Request, Ack). If server is unavailable, Windows clients use APIPA (169.254.x.x). If lease expires without renewal, the client stops using the IP.

OP14 — Easy: Managed switches allow VLANs, QoS, and ACLs. Unmanaged switches are plug-and-play. Managed switches are required in enterprises for traffic control, security segmentation, and performance optimization.

OP15 — Easy: NTP synchronizes system clocks. Critical for cluster consistency (logs, replication, certificates). Clock drift causes replication failures, certificate validation errors, and log correlation issues.

OP16 — Easy: Physical server (bare metal), VM (OS layer), Container (App layer). Run on bare metal for maximum performance, lowest latency, or strict compliance/security requirements where virtualization overhead is unacceptable.

OP17 — Easy: UPS provides instant backup power; Generator provides long-term power. ATS switches power from grid to UPS to generator automatically. You need both for continuous uptime during grid outages.

OP18 — Medium: Active-Passive (one active, one standby); Active-Active (both active). For PostgreSQL HA: Use Pacemaker/Corosync. Configure STONITH (fencing) to stop the old node before starting the new one. Move Virtual IP (VIP) to the active node on failover.

OP19 — Hard: 3-2-1 rule (3 copies, 2 media, 1 offsite). RPO (max data loss), RTO (max downtime). Types: Full, Incremental, Differential. Deduplication saves space. Immutable backups prevent ransomware. Backup = data copy; DR = full system recovery capability.

OP20 — Hard: 802.1X: Supplicant (client), Authenticator (switch), Auth Server (RADIUS). EAP-TLS (certs) vs PEAP (password). Fail auth = port blocked. MAB (MAC Auth Bypass) allows devices without supplicants (printers) to authenticate via MAC address.
