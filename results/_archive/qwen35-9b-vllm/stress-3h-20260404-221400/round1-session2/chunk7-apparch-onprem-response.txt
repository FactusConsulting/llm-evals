AA1 — Easy: A monolith is a single application with a shared codebase and database. Microservices are independent services communicating over a network. Three concrete problems microservices introduce: 1. Distributed latency (network calls are slower than local calls), 2. Distributed data consistency (managing transactions across services is complex), 3. Operational complexity (orchestration, monitoring, and deployment of many services vs one).

AA2 — Easy: Synchronous communication involves a request-response pattern where the caller waits for a reply (e.g., HTTP/REST, gRPC). Asynchronous communication involves fire-and-forget or callback patterns where the caller does not wait (e.g., Message Queues like RabbitMQ, Pub/Sub systems like Kafka).

AA3 — Medium: An API Gateway handles business logic (auth, rate limiting, aggregation), while a reverse proxy handles traffic routing and SSL termination. An API Gateway cannot replace a reverse proxy entirely because proxies often need to sit closer to the edge for performance (L4 routing), whereas gateways sit at the application layer (L7). Conversely, a reverse proxy cannot replace a gateway because it lacks business logic capabilities.

AA4 — Medium: The Saga pattern manages long-running transactions across services without distributed locks. Choreography-based sagas use events where services react to changes (e.g., Order Service publishes "OrderCreated", Inventory Service listens). Orchestration-based sagas use a central coordinator that tells services what to do. Choreography is better for decoupled systems; Orchestration is better for complex workflows requiring rollback coordination.

AA5 — Medium: CQRS separates read and write operations into different models. It is paired with Event Sourcing (storing state as a sequence of events) to reconstruct state. This combination solves the problem of read/write performance mismatch and complex query requirements that a traditional CRUD model cannot handle efficiently at scale.

AA6 — Medium: The Circuit Breaker pattern prevents cascading failures by stopping calls to a failing service. States: Closed (normal), Open (failures exceed threshold, stop calls), Half-Open (test if service recovered). It differs from simple retry because it stops calling entirely during failure. Use both together: retry transient errors, but open the circuit if failures persist.

AA7 — Hard:
1. **Shared DB, Shared Schema:** Low cost, high operational complexity (locking), high noisy-neighbor risk, lower security (data leakage risk).
2. **Shared DB, Separate Schema:** Medium cost, medium complexity, medium noisy-neighbor risk, better security (schema isolation).
3. **Separate DB per Tenant:** High cost, low complexity (tenant isolation), low noisy-neighbor risk, highest security.

AA8 — Hard: Strong consistency is required to prevent overselling. At scale, this is challenging. Architecture: Use a strong-consistency data store (e.g., CockroachDB or DynamoDB with strong consistency) or a centralized inventory service with optimistic locking (Redis + DB). Avoid distributed transactions (2PC) due to performance. Use a single source of truth for inventory counts.

AA9 — Hard: A sidecar proxy runs alongside the application to handle networking/security. In Istio, Envoy is the sidecar. Data plane handles traffic flow; Control plane manages Envoy configuration. mTLS between sidecars solves service-to-service authentication without requiring application code changes, unlike application-level TLS which requires certificate management in the app.

AA10 — Medium: The Strangler Fig pattern migrates legacy systems incrementally. Strategy: 1. Place an API Gateway in front of the .NET Framework monolith. 2. Extract specific functionality (e.g., "Billing") into a new .NET 8 microservice. 3. Update the Gateway to route "Billing" traffic to the new service. 4. Repeat until the monolith is fully decomposed.

AA11 — Medium: 12-Factor App methodology: 1. Codebase, 2. Dependencies, 3. Config, 4. Backing Services, 5. Build/Run/Deploy, 6. Processes, 7. Concurrency, 8. Disposals, 9. Dev/Prod, 10. Logs, 11. Admin. They matter for cloud-native deployments because they ensure portability, scalability, and security across environments.

AA12 — Hard: Event-driven (Kafka) offers high scalability and decoupling but has higher debugging complexity and eventual consistency. Request-driven (REST/gRPC) offers synchronous guarantees and easier debugging but tighter coupling. Choose Event-driven for event sourcing/decoupled pipelines; Request-driven for real-time user interactions requiring immediate responses.

AA13 — Easy: A load balancer distributes traffic across servers. Layer 4 (Transport) balances based on IP/Port (TCP/UDP). Layer 7 (Application) balances based on content (HTTP headers/URLs). Layer 7 is required for routing specific API endpoints to different microservices.

AA14 — Easy: A message queue (RabbitMQ) supports point-to-point and pub/sub with guaranteed delivery. A log-based broker (Kafka) is append-only, high-throughput, and supports replayability. Pick RabbitMQ for task queues (e.g., email sending); pick Kafka for event streams (e.g., analytics, event sourcing).

AA15 — Easy: A container packages code with dependencies in a lightweight OS environment (shared kernel). A VM includes a full OS. Containers are popular for microservices because they are lightweight, start faster, and allow higher density than VMs.

AA16 — Easy: Stateless services do not store data in memory (e.g., Web Server). Stateful services store data (e.g., Database). Stateless services are easier to scale horizontally because any instance can handle any request.

AA17 — Easy: An ORM maps database tables to object classes. Examples: Entity Framework (.NET), Hibernate (Java). Trade-offs: ORMs improve development speed but can lead to performance issues (N+1 queries) and reduced SQL flexibility compared to raw SQL.

AA18 — Medium: The Bulkhead pattern isolates resources (threads, CPU, memory) to prevent one failure from exhausting all resources. Example: Implement separate thread pools for database connections and external API calls. If the API pool is exhausted, the DB pool remains available.

AA19 — Hard: OT resolves conflicts server-side and requires connectivity. CRDTs resolve conflicts client-side and converge eventually. CRDTs support offline editing better because they allow local changes to be merged later without server intervention. Choose CRDTs for offline support.

AA20 — Hard: Distributed tracing propagates context (TraceID/ParentID) via headers (W3C Trace Context). Sampling reduces storage load. Tracing interacts with async messaging by correlating producer/consumer spans. For Kafka, inject headers into messages (e.g., `x-b3-traceid`) and extract them in consumers to ensure trace continuity.

OP1 — Easy: Type 1 (Bare-metal) runs directly on hardware (e.g., VMware ESXi, Xen). Type 2 (Hosted) runs on top of an OS (e.g., VMware Workstation, VirtualBox).

OP2 — Easy: SAN (Storage Area Network) provides block storage (iSCSI, Fibre Channel) for high-performance DBs. NAS (Network Attached Storage) provides file storage (NFS, SMB) for file sharing. Use SAN for databases; NAS for general file storage.

OP3 — Medium: 3-tier (Core, Distribution, Access) creates hierarchical bottlenecks. Leaf-Spine (flat topology) connects every leaf to every spine, solving scalability and latency issues by providing equal path lengths and eliminating bottlenecks.

OP4 — Medium: Proxmox HA cluster: 3+ nodes for quorum. Shared storage (Ceph preferred for HA). Fencing (STONITH) prevents split-brain. If a node fails, the cluster detects loss of quorum, fences the failed node, and promotes a healthy node to take over.

OP5 — Medium: VLAN trunking allows multiple VLANs over a single link. 802.1Q tags frames with a VLAN ID. On Linux: `ip link add link eth0 type vlan id 100`, `ip link add link eth0 type vlan id 200`, etc., then assign IPs to the interfaces.

OP6 — Medium: RAID 1 (Mirror), 5 (Striping+Parity), 6 (Dual Parity), 10 (Stripe+Mirror), Z2 (ZFS Mirror+Parity). For 6 drives DB: RAID 10 offers best performance but low capacity. ZFS RAID-Z2 offers better capacity and fault tolerance. Choose ZFS RAID-Z2 for modern Linux environments balancing capacity and safety.

OP7 — Hard: DNS Architecture: Recursive resolvers (clients), Authoritative servers (AD), Forwarders (ISP), Conditional forwarding (DMZ). Split-horizon handles internal vs external. When laptop moves to VPN, DHCP updates DNS suffix; split-horizon ensures internal names resolve via internal servers, external names via public resolvers.

OP8 — Hard: PKI Chain: Root CA (offline) -> Subordinate CA -> End-Entity Cert. CRL (list of revoked certs) vs OCSP (real-time check). Compromised Subordinate: Revoke certs, trust remains. Compromised Root: Global trust broken, all certs invalid.

OP9 — Hard: MPLS (High cost, reliable, low latency). IPsec (Low cost, internet risk). SD-WAN (Flexible, cost-effective, good latency). WireGuard (Simple, fast). For 50 users/VoIP: Recommend SD-WAN for balance of cost, reliability, and latency management.

OP10 — Medium: iDRAC/iLO/IPMI are out-of-band management interfaces. Critical for remote hardware access. Exposing IPMI to the internet is a severe security risk (brute force, remote root access).

OP11 — Medium: LVM (Logical Volumes), LVM-Thin (Space efficient), ZFS (Filesystem + Storage). Snapshots: LVM (Copy-on-write), Thin (Metadata), ZFS (Transactional). Use LVM for simple VM storage, Thin for high density, ZFS for file servers/DBs requiring data integrity.

OP12 — Hard: Stretch Cluster: Place monitors in different sites. CRUSH rules ensure data replication across sites. 2-site Ceph is risky without a tiebreaker because if both sites lose connectivity, the cluster may split-brain (think both sites are alive). Requires a third site or manual intervention.

OP13 — Easy: DHCP DORA: Discover, Offer, Request, Ack. If server unavailable, Windows client uses APIPA (169.254.x.x). Lease expires: Client sends Renew; if no response, lease expires and client re-discovers.

OP14 — Easy: Managed switch supports VLANs, QoS, ACLs. Unmanaged switch is plug-and-play. Managed switches are critical for enterprise security and traffic prioritization.

OP15 — Easy: NTP synchronizes time. Critical for log correlation, SSL certificate validation, and database replication. Drift causes replication lag, failed auth, and audit issues.

OP16 — Easy: Physical = Bare metal. VM = OS abstraction. Container = App abstraction. Run on bare metal for high-performance workloads (HFT, DB) where hypervisor overhead is unacceptable.

OP17 — Easy: UPS provides immediate backup (seconds/minutes). Generator provides long-term power. ATS switches between utility, UPS, and generator. Need both for continuous uptime.

OP18 — Medium: Active-Passive (one active). Active-Active (both active). Pacemaker/Corosync: Fencing (STONITH) ensures only one node writes to shared storage. VIP floats to active node. Failover: If active fails, passive takes VIP.

OP19 — Hard: 3-2-1 Rule (3 copies, 2 media, 1 offsite). RPO (max data loss), RTO (max downtime). Types: Full, Incremental, Differential. Dedup reduces storage. Immutable backups prevent ransomware. Backup = data copy; DR = system recovery.

OP20 — Hard: 802.1X: Supplicant (client), Authenticator (switch), Auth Server (RADIUS). EAP-TLS (certs) vs PEAP (password). Fail auth = port blocked. MAB (MAC Auth Bypass) allows devices without supplicants (printers) to authenticate via MAC address.
