CL1 — IaaS provides virtualized hardware (e.g., AWS EC2). PaaS provides a platform for application development (e.g., AWS Elastic Beanstalk). SaaS provides ready-to-use software (e.g., Salesforce).

CL2 — In IaaS, the provider manages hardware/network/storage; you manage OS/apps. In managed Kubernetes, the provider manages the control plane; you manage workloads/policies. In SaaS (M365), the provider manages everything including data and security; you manage user access and data governance.

CL3 — A VPC is a logical isolation boundary. A subnet is a range of IP addresses within a VPC. A Security Group (SG) is a stateful firewall attached to instances. A NACL is a stateless firewall attached to subnets. Layering: VPC contains Subnets; Subnets have NACLs; Instances have SGs. Stateful filtering (SG) remembers connection state; Stateless (NACL) does not.

CL4 — A Landing Zone provides a standardized foundation (networking, identity, logging). OUs organize accounts by function (Prod, Dev). Guardrails enforce policies (e.g., no public S3). Shared networking uses a Hub (Transit Gateway) connecting Spokes (accounts). Centralized logging aggregates logs (e.g., CloudTrail). Single-account approaches limit isolation, scalability, and multi-tenancy security.

CL5 — IaC defines infrastructure via code. Terraform/OpenTofu uses HCL (declarative). Pulumi uses general-purpose languages (TypeScript/Python). CloudFormation/Bicep are native provider tools (AWS/Azure). Crossplane uses Kubernetes CRDs. Choose Terraform for multi-cloud; Pulumi for developer preference; Native tools for simple single-cloud projects; Crossplane for K8s-native operations.

CL6 — HPA scales pod count based on CPU/Memory. VPA scales pod resource requests. Cluster Autoscaler adds/removes nodes. KEDA scales based on external events (e.g., Kafka messages). Use KEDA over HPA when traffic is event-driven and bursty, rather than CPU-based.

CL7 — RPO is data loss tolerance; RTO is downtime tolerance. Active-Active replicates workloads in both regions; Active-Passive keeps one active. Sync replication ensures low RPO; Async allows higher throughput. DNS failover (Route53) directs traffic. Pilot Light (cold), Warm Standby (warm), Multi-site Active-Active (hot) differ in cost and recovery speed.

CL8 — GitOps stores desired state in Git; CD tools sync the cluster. ArgoCD uses K8s controllers; Flux uses CRDs. Secrets are managed via Sealed Secrets or External Secrets Operator (integrating with Vault). Manual changes trigger a drift detection loop in the CD tool, which automatically reverts or prompts for approval.

CL9 — Use a StatefulSet for stable pod identities. Use Local Persistent Volumes (LocalPath) for low-latency storage. Use a Headless Service for DNS-based service discovery. Use Init Containers to prepare filesystem paths. Mount ConfigMaps as volumes. Use Pod Disruption Budgets to ensure availability during scaling.

CL10 — A Service Account is a K8s identity. Workload Identity binds a K8s SA to a cloud IAM role (e.g., AWS IRSA). Mounting credentials in pods is bad due to rotation risks and secret leakage. Workload Identity federation allows the pod to assume the role without storing keys.

CL11 — Object storage (S3) is for unstructured files with high durability (11 9s). Block storage (EBS) is for VM disks requiring low latency. File storage (EFS) is for shared file systems across nodes. Object is best for data lakes; Block for databases; File for shared app data.

CL12 — Zero Trust requires verifying every request. Use NetworkPolicies for pod isolation. Service Mesh (Istio) enforces mTLS. Pod Identity binds workloads to identities. Admission Controllers (OPA) enforce policies. Image signing (Cosign) prevents bad images. Runtime security (Falco) detects anomalies. This differs from perimeter security by trusting no one by default.

CL13 — A CDN caches content at edge locations to reduce latency. Services: AWS CloudFront, Azure CDN. Use a CDN for static assets (images, CSS) to reduce origin load; serve directly from origin for dynamic content requiring real-time processing.

CL14 — Regions are geographic areas with data centers. Availability Zones (AZs) are isolated data centers within a region. Deploy across AZs for High Availability (HA) to survive zone failures. Zonal resources exist in one AZ; Regional resources span multiple AZs.

CL15 — Managed databases (RDS) handle patching, backups, scaling, and HA. Running on a VM requires manual management of all these tasks, increasing operational overhead and risk of human error.

CL16 — IAM Users are individuals; Roles are permissions attached to users/groups/resources. Least Privilege means granting only the minimum permissions required. Apply it by using specific policies (e.g., `s3:GetObject` instead of `s3:*`).

CL17 — Serverless executes code in response to events without managing servers. Lambda/Functions are similar. Cold starts occur when a function is invoked after inactivity, causing latency. Poor fit for latency-sensitive or long-running tasks.

CL18 — Ingress resource is a K8s API object. Gateway API is the standard for Ingress. Cloud LB annotations delegate to the provider. Service Mesh ingress gateways handle mTLS. TLS termination at the Cloud LB offloads encryption; Ingress terminates at the K8s node. Use Gateway API for multi-cluster or advanced routing needs.

CL19 — Use Savings Plans for steady workloads; Spot for fault-tolerant batch jobs. Right-sizing reduces over-provisioning. Tiering moves infrequent data to cheaper storage. Idle detection stops unused resources. FinOps involves visibility, accountability, and optimization. Showback/Chargeback assigns costs to teams.

CL20 — Use Kubernetes as a common runtime and Terraform for IaC portability. Use private interconnects (Direct Connect/ExpressRoute) for networking. Federate identity (OIDC). Multi-cloud is justified for compliance or avoiding lock-in; unnecessary if a single cloud meets all requirements and adds complexity.

OT1 — The Purdue Model (ISA-95) defines 5 levels of automation. Level 0: Physical Process. Level 1: Basic Control (PLCs). Level 2: Supervisory Control (SCADA). Level 3: Enterprise Control (MES). Level 4: Business Planning (ERP). Level 5: Business Management.

OT2 — IT focuses on data availability and confidentiality; OT focuses on safety and reliability. Standard IT patching can cause downtime or instability in OT systems, risking physical safety or production stoppages.

OT3 — An IDMX (Industrial DMZ) separates IT and OT networks. Traffic flows from OT to IT (e.g., data export) but is restricted from IT to OT (e.g., no direct control commands). Direct connectivity from Level 4 to Level 1 bypasses security layers, increasing blast radius and risk of ransomware.

OT4 — Modbus TCP (L1), OPC UA (L1/L2), EtherNet/IP (L1), PROFINET (L1), MQTT (L2/L3). Modbus/OPC UA/EtherNet/IP/PROFINET are primarily for control (L1). MQTT is often used for telemetry and messaging (L2/L3).

OT5 — A data diode allows traffic in only one direction (e.g., OT to IT). A firewall allows bidirectional traffic. Use a data diode for critical data export where return traffic is impossible or prohibited. Limitation: No feedback or control commands can pass.

OT6 — Data flows: PLC -> Historian -> Edge Gateway -> MQTT Broker -> Cloud Ingestion. Security boundaries: Firewall between OT and DMZ; Firewall between DMZ and Cloud. The Edge Gateway acts as the choke point for data leaving the OT network.

OT7 — A Zone is a logical boundary of assets with similar risk. A Conduit is a connection between zones. Plant Model: Zone 1 (Corporate), Zone 2 (Engineering), Zone 3 (SCADA), Zone 4 (PLCs/SIS). Conduits connect zones via firewalls or DMZs.

OT8 — Segment by production line using VLANs. Place firewalls between zones (e.g., between L2 and L3). Use Layer 3 switches for routing. Vendor access via a Jumpbox in the DMZ. Transition involves parallel running the new network while monitoring stability.

OT9 — SIS protects against hazardous conditions; BPCS manages normal operations. IEC 61511 defines functional safety. SIS must be isolated to prevent malicious commands from disabling safety systems. If ransomware reaches SIS, it could cause physical damage or loss of life.

OT10 — PLCs handle discrete logic in local control. DCS handles continuous process control in large plants. SCADA monitors and controls geographically dispersed assets. They can coexist (e.g., PLCs feeding SCADA).

OT11 — Remote access requires a Jump Host (bastion host), MFA, and session recording. Vendor access is time-limited. RDP directly to an HMI is unacceptable because it bypasses security controls and exposes the control system directly to the internet.

OT12 — Detection: Use IDS/IPS and anomaly detection. Inventory: Maintain a live asset list. Response: Isolate affected segments, notify operators. Operators prioritize safety over security. Coordination: IT supports OT, but OT operators control the physical response.

OT13 — An HMI allows operators to monitor and control the process. It differs from an engineering workstation, which is used for configuration and maintenance, not real-time control.

OT14 — A historian stores time-series process data. Plant historians (L3) store operational data for the facility. Enterprise historians (L4) aggregate data for business analysis and reporting.

OT15 — Ladder logic is a programming language resembling relay logic. It executes on PLCs. It remains dominant due to operator familiarity, ease of troubleshooting, and reliability in industrial environments.

OT16 — An RTU is a ruggedized controller for remote locations, often using serial communication. PLCs are for local, complex logic with Ethernet. Deploy RTUs in harsh, remote environments (e.g., oil rigs) where PLCs are impractical.

OT17 — Analog signals (4-20mA) represent continuous values; digital signals represent discrete states. 4-20mA is preferred over 0-20mA because 0mA indicates a broken wire, whereas 0mA in 0-20mA could be a valid reading.

OT18 — Asset inventory identifies all OT devices. Passive monitoring (sniffing) is safe; active scanning (pinging) can disrupt operations or trigger alarms. Inventory is the foundation for segmentation and patching.

OT19 — MITRE ATT&CK for ICS maps adversary tactics to OT environments. Tactics: Reconnaissance (T1000), Execution (T1001), Persistence (T1002). It differs from Enterprise ATT&CK by including ICS-specific techniques (e.g., PLC manipulation). Use it to identify gaps in detection capabilities.

OT20 — Collect logs via Syslog/NetFlow without impacting operations. Integrate with SIEM. Use OT-specific rules (e.g., PLC IP changes). Staffing requires OT engineers to triage alerts. False positives are common; verify before acting. For firmware changes: verify integrity, isolate device, and patch only after validation.
