K1 — Easy: What is the difference between a Deployment and a StatefulSet?
A Deployment manages stateless applications. Pods are interchangeable, have no stable identity, and updates happen in parallel. A StatefulSet manages stateful applications. Pods have stable, unique identities (DNS names), are deployed in a specific order, and terminated in reverse order. StatefulSets also support stable storage (persistent volumes) per pod.

K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?
The Service creates a virtual IP (ClusterIP) within the cluster. kube-proxy (running on nodes) creates iptables or IPVS rules to forward traffic from the Service IP to the Pod IPs listed in the Service's Endpoints object. Traffic flows: Client -> Service IP -> kube-proxy -> Pod IP.

K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?
A PersistentVolume (PV) is a piece of storage provisioned by the admin (static or dynamic). A PersistentVolumeClaim (PVC) is a request for storage resources made by a user. A StorageClass defines the provisioner and parameters for dynamically creating PVs. Relation: StorageClass -> creates PV -> PVC binds to PV -> Pod mounts PV.

K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).
1. Check container logs (`kubectl logs <pod>`) for application errors.
2. Check pod events and status (`kubectl describe pod <pod>`) for OOMKilled or ImagePullBackOff.
3. Verify init containers are not failing (check `InitContainers` section in describe output).
4. Check resource limits (CPU/Memory) to ensure the container isn't being killed by the node's OOM killer.

K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?
CoreDNS provides DNS resolution for services, pods, and nodes within the cluster. If CoreDNS pods are down, internal service discovery fails (pods cannot resolve service names), and external ingress endpoints relying on DNS may become unreachable.

K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.
The scheduler first **filters** nodes that satisfy constraints (taints/tolerations, node selectors, resource availability). Then it **scores** the remaining nodes to rank them. Factors considered include: Node Affinity (preference for specific nodes), Taints/Tolerations (hard constraints), and Resource Requests (CPU/Memory availability).

Yes, the pod will be scheduled because the total requested memory (3.5GB + 0.25GB = 3.75GB) is less than the node's 4GB RAM. If the runtime usage exceeds the limit (600Mi > 512Mi), the container will be OOMKilled.

K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?
A NetworkPolicy controls ingress/egress traffic to/from pods. If no policy exists, the default behavior is to allow all traffic. When a policy is applied, it restricts traffic to/from the selected pods according to the rules (e.g., allowing only specific ports or sources).

K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?
RollingUpdate updates pods gradually, keeping the application available. Recreate stops all old pods before starting new ones, causing downtime. Choose Recreate for stateful applications (e.g., databases) where data integrity requires a clean shutdown and restart.

A namespace is a logical partition for resources. Default namespaces are: `default`, `kube-system`, `kube-public`, and `kube-node-lease`.

K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?
A DaemonSet ensures a copy of a pod runs on all (or a subset of) nodes. Use it for node-level tasks like logging agents (Fluentd), monitoring (Prometheus Node Exporter), or network plugins (Calico), rather than running multiple stateless app instances.

K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?
Taints (node side) push pods away; Tolerations (pod side) allow pods to ignore taints. Node Affinity (pod side) pulls pods to specific nodes based on labels. Use case: Taints for GPU nodes (only pods with tolerations can run). Affinity for placing DBs on specific hardware.

An Operator is a custom controller that manages the lifecycle of a specific application type (e.g., MySQL). Standard controllers manage generic resources (Pods, Deployments). Operators solve complex lifecycle problems (backups, upgrades, scaling) that standard controllers cannot handle.

States: Closed (normal), Open (fail fast), Half-Open (test). Prevents cascade by stopping calls to failing services. Retries occur in Half-Open state with exponential backoff to avoid overwhelming the service.

D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).
Optimistic checks for conflicts on commit (CAS). Pessimistic locks rows immediately. Choose Optimistic for high concurrency read-heavy. Choose Pessimistic for critical data integrity. Example: `SELECT ... FOR UPDATE` (pessimistic).
