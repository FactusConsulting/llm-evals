## Go (20 questions)

**G1**
Arrays are fixed-size, value types stored contiguously in memory. Slices are dynamic, reference types pointing to an underlying array with a length and capacity. When a slice reaches capacity, `append` allocates a new underlying array (usually double the size), copies the old data, and returns a new slice pointing to the new array.

**G2**
`var x int` declares a variable with a zero value (`0`) without initializing it. `x := 0` is a short declaration that initializes `x` to `0` and infers the type. You cannot use `:=` at package level (outside functions) or if the left-hand side is not a variable (e.g., `:=` cannot be used on a constant or a field of a struct).

**G3**
A goroutine is a lightweight thread of execution managed by the Go runtime. It differs from an OS thread in that it is much smaller (stack starts at 2KB) and the runtime multiplexes thousands of goroutines onto a smaller number of OS threads. The GMP model (Goroutine, Machine, Processor) manages scheduling: Gs are scheduled onto Ms, which run on Ps (OS threads).

**G4**
Channels allow safe communication between goroutines. An unbuffered channel blocks the sender until a receiver is ready. A buffered channel holds up to `N` values. Sending to a full buffered channel blocks the sender until a receiver removes a value or the buffer is empty.

**G5**
The `context` package manages cancellation, deadlines, and request-scoped values.
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
resp, err := http.Get(ctx, "https://example.com")
```
This ensures the request is cancelled if it exceeds 5 seconds.

**G6**
Go uses "duck typing" (implicit satisfaction); a type implements an interface if it has the required methods. Java/C# require explicit interface declarations. `interface{}` (or `any`) holds values of any type but requires type assertions to access them. It is powerful for generic-like behavior but dangerous because it loses type safety and performance (no inlining).

**G7**
This is unsafe due to a data race. `ready` and `data` are not atomic. The goroutine writes `ready` and `data` concurrently with the main loop reading them. The correct alternative is using `sync.WaitGroup` (if the goroutine does work) or `sync.Mutex`/`sync.Cond` to synchronize access to shared state.

**G8**
`sync.Mutex` allows only one writer. `sync.RWMutex` allows multiple concurrent readers but exclusive writers. `sync.Map` is optimized for high read concurrency with low write contention (uses a hash table with per-bucket locks), whereas a regular map with a mutex is slower for reads but consistent for writes.

**G9**
Go modules manage dependencies. `go.mod` declares the module path and required dependencies. `go.sum` stores checksums for security. `go mod tidy` cleans up unused dependencies and ensures versions match `go.mod`. MVS (Minimum Version Selection) picks the lowest version of a dependency that satisfies all constraints.

**G10**
`defer` schedules a function call to run when the surrounding function returns. Multiple defers execute in LIFO (Last-In, First-Out) order. A common gotcha is capturing loop variables; `defer` captures the variable by reference, so all defers in a loop may use the final value of the loop variable.

**G11**
A pointer holds the memory address of a value. The zero value is `nil`. To create a pointer to a struct literal: `var p *MyStruct = &MyStruct{}`.

**G12**
`init()` runs before `main()`. A package can have multiple `init()` functions (e.g., in different files). They execute in the order the files are compiled/imported.

**G13**
`make` allocates and initializes slices, maps, and channels (e.g., `make(map[string]int)`). `new` allocates zeroed memory and returns a pointer (e.g., `new(int)` returns `*int`). `make` does not work with pointers or structs directly.

**G14**
Go uses explicit error returns. The `error` interface has a single method `Error() string`. The idiomatic check is `if err != nil`. `errors.Is` checks if an error wraps a specific target error (useful for wrapped errors). `errors.As` type-asserts an error to a specific type.

**G15**
Composite types: `map[K]V` (zero: `nil`), `[]T` (slice) (zero: `nil`), `chan T` (zero: `nil`), `struct` (zero: fields set to their zero values).

**G16**
A race condition occurs when two goroutines access the same memory concurrently without synchronization. The `-race` flag enables the ThreadSanitizer to detect this. Fix: Protect shared data with `sync.Mutex` or use channels for communication.

**G17**
`select` chooses a case based on channel readiness. It differs from `switch` by handling channel operations. If multiple cases are ready, one is chosen randomly. A timeout is implemented by adding a `case <-time.After(d)` to the select statement.

**G18**
Escape analysis determines if a variable lives on the stack or heap. If a variable is referenced outside the function (e.g., stored in a global or heap-allocated struct), it escapes to the heap. Use `go build -gcflags="-m"` to inspect. It matters because heap allocation incurs GC overhead.

**G19**
`reflect.Type` represents the type metadata; `reflect.Value` represents the value. Reflection is slow and prevents inlining. It is justified for dynamic configuration or generic-like behavior before generics existed, but code generation is preferred for performance.

**G20**
`go:embed` embeds files at compile time. It supports single files, directories, and `io/fs.FS`. Limitations include no dynamic paths (must be known at compile time) and no support for external resources. It interacts with `io/fs.FS` by embedding the FS into the binary.

## Rust (20 questions)

**R1**
Ownership ensures memory safety. Rules: 1. Each value has one owner. 2. When the owner goes out of scope, the value is dropped. 3. Only one mutable reference or any number of immutable references can exist.

**R2**
`String` is an owned, heap-allocated UTF-8 string. `&str` is a borrowed slice of UTF-8. Use `String` when ownership is needed (e.g., return value). Use `&str` for function arguments to avoid unnecessary copies.

**R3**
Borrowing allows accessing data without taking ownership. Immutable references (`&T`) allow read-only access. Mutable references (`&mut T`) allow modification. Rules: No aliasing (cannot have two mutable refs or one mutable + one immutable ref at the same time).

**R4**
`Result<T, E>` represents success (`Ok(T)`) or failure (`Err(E)`). `Option<T>` represents presence (`Some(T)`) or absence (`None`). `?` propagates errors up the call stack.
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)?
}
```

**R5**
`Box<T>` is a heap-allocated pointer (single owner). `Rc<T>` is a reference-counted pointer (single thread). `Arc<T>` is an atomic reference-counted pointer (multi-thread). Use `Rc` for tree structures, `Arc` for shared state across threads.

**R6**
Traits define behavior. Rust traits are implicit (like Go) but can be explicit (`dyn Trait`). `dyn Trait` uses vtables (dynamic dispatch). `T: Trait` uses monomorphization (static dispatch), which is faster and allows inlining.

**R7**
This fails because the compiler cannot guarantee that `x` or `y` outlive the function. The return type `&str` implies a reference to one of the inputs, but the compiler doesn't know which. Fix: Return `String` (owned) or add explicit lifetimes: `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str`.

**R8**
`Send` means a type can be transferred across threads. `Sync` means it can be shared between threads. `Rc<T>` is not `Send` because its reference count is not atomic. `Arc<T>` is `Send` and `Sync` because it uses atomic reference counting.

**R9**
Rust async uses a state machine approach. `async fn` returns a `Future` trait object. An executor (e.g., Tokio) polls the Future to drive execution. Unlike Go's M:N scheduler, Rust async is often cooperative or relies on OS threads depending on the runtime.

**R10**
`unsafe` blocks allow bypassing safety checks. Examples: dereferating raw pointers, calling FFI functions, or accessing union fields. Justified when interfacing with C or when performance requires zero-overhead abstractions that the compiler cannot guarantee.

**R11**
Pattern matching (`match`) is exhaustive; the compiler enforces all cases are covered. `if let` is partial and only checks one pattern. `match` is preferred for control flow over nested `if`.

**R12**
`Vec<T>` is a growable heap array. `[T; N]` is a fixed-size stack array. When `Vec` capacity is exceeded, it reallocates to a larger buffer and copies elements.

**R13**
Rust enums are tagged unions (data + tag). C/Java enums are often just integer constants. `Option<T>` is an enum with `Some(T)` and `None`. Rust has no null; `Option` replaces it to prevent null pointer dereferences.

**R14**
`impl` defines methods for a type. `&self` borrows the instance, `&mut self` mutates it, `self` consumes it. Associated functions (e.g., `String::new`) take `&Self` or no self and are called on the type itself.

**R15**
`#[derive]` automatically implements traits. Common: `Debug`, `Clone`, `PartialEq`, `Serialize`. Cannot derive if the trait requires custom logic (e.g., `PartialEq` on complex types with custom equality logic).

**R16**
`Cow<'a, T>` (Clone on Write) holds a reference if immutable, or a clone if mutable. Useful for avoiding allocations when processing strings that might be borrowed. Example: `Cow::Borrowed(s)` avoids cloning if the string is not modified.

**R17**
`mod` defines a module. `use` imports items. `pub` makes items public. 2015 edition mapped modules to file structure strictly. 2018 edition allows path-based modules (e.g., `mod foo` in `src/foo/mod.rs`).

**R18**
`Pin<P>` prevents a value from being moved. Needed for self-referential structs (pointers to self) and async tasks (which must stay at a specific memory location). `Unpin` is a marker trait to allow moving.

**R19**
Declarative macros (`macro_rules!`) are text-based and less flexible. Procedural macros (derive, attribute, function-like) operate on ASTs and are more powerful. Hygiene rules prevent macro variables from conflicting with outer scope variables.

**R20**
Zero-cost abstractions mean high-level code compiles to code as efficient as hand-written C. Generics use monomorphization (code generation per type). Iterators use trait objects or static dispatch to avoid virtual function overhead.
