CL1 — Easy: **IaaS** (Infrastructure as a Service) provides virtualized computing resources (VMs, storage, networks) without managing hardware. Example: AWS EC2. **PaaS** (Platform as a Service) provides a platform for developing/deploying apps without managing the underlying OS. Example: Google App Engine. **SaaS** (Software as a Service) delivers software over the internet. Example: Salesforce.

CL2 — Easy: **Shared Responsibility Model**: Provider secures the cloud (infrastructure, physical security); Customer secures what they put in the cloud. **IaaS VMs**: Provider manages hardware/OS patching; Customer manages OS config, data, and apps. **Managed Kubernetes**: Provider manages control plane (nodes, networking); Customer manages workloads, policies, and data. **SaaS (M365)**: Provider manages everything (infrastructure, app, data); Customer manages user access and data retention policies.

CL3 — Medium: **VPC**: Logical isolation of network resources. **Subnet**: IP range within a VPC (Zonal or Regional). **Security Group**: Stateful firewall attached to instances (allows inbound, auto-opens outbound). **NACL**: Stateless firewall attached to subnets (rules apply to all traffic). **Layering**: VPC contains Subnets; NACL filters traffic at subnet boundary; Security Group filters at instance boundary. **Stateful**: Tracks connection state (SG). **Stateless**: No memory of connections (NACL).

CL4 — Medium: **Landing Zone**: Pre-configured foundation for multi-account environments (identity, networking, logging). **Organizational Units (OUs)**: Hierarchical grouping of accounts for policy application. **Guardrails**: SCPs (AWS) or Policies (Azure) enforcing compliance. **Shared Networking**: Hub-and-Spoke (Transit Gateway/VNet Peering) for centralized connectivity. **Centralized Logging**: Aggregating logs (e.g., CloudTrail, VPC Flow Logs) to a central account. **Single-account problem**: Billing complexity, security scope limits, scaling bottlenecks, and lack of isolation.

CL5 — Medium: **IaC** manages infrastructure via code. **Terraform/OpenTofu**: Declarative, state-based, multi-cloud. **Pulumi**: Declarative/Imperative using general-purpose languages (Python/TS). **CloudFormation/Bicep**: Native, cloud-specific (AWS/Azure). **Crossplane**: K8s-native, manages cloud resources as K8s objects. **Choice**: Terraform for multi-cloud; Pulumi for dev teams preferring code; Native for single-cloud simplicity; Crossplane for K8s-centric orgs.

CL6 — Medium: **HPA**: Scales pod count based on CPU/Memory. **VPA**: Scales pod resource requests/limits. **Cluster Autoscaler**: Adds/removes nodes based on pod demand. **KEDA**: Scales based on external events (queue depth, HTTP requests). **KEDA vs HPA**: Use KEDA for event-driven workloads (e.g., processing messages) where CPU isn't the primary load indicator, allowing zero-pod scaling.

CL7 — Hard: **DR Strategy**: Define **RPO** (data loss) and **RTO** (downtime). **Active-Active**: Traffic split across regions (high cost, high availability). **Active-Passive**: Failover to standby (lower cost). **DB Replication**: Sync (zero RPO) vs Async (low RPO). **DNS Failover**: Route53/Traffic Manager directs traffic to healthy region. **State**: Managed state (S3/DynamoDB) is easier to replicate than local state. **DR Types**: **Pilot Light** (minimal resources, long RTO); **Warm Standby** (partial resources, medium RTO); **Multi-site Active-Active** (full resources, low RTO).

CL8 — Hard: **GitOps**: Infrastructure/App state defined in Git repo; CD tool syncs cluster to Git. **ArgoCD vs FluxCD**: ArgoCD is K8s-native, Flux is CNCF (more flexible). **Secrets**: Use **Sealed Secrets** (encrypted in Git) or **External Secrets Operator** (syncs from Vault). **Drift**: If manual change occurs, GitOps controller detects mismatch and reverts cluster to Git state (or alerts).

CL9 — Hard: **StatefulSet**: Manages stable pod identities and ordering. **Local PV/PVC**: Use `LocalPathProvisioner` or `LocalStorageClass` for low-latency local disk. **Headless Service**: DNS returns multiple IPs for pod-to-pod communication. **Init Containers**: Run setup scripts before main app starts. **ConfigMaps**: Mount config files as volumes. **Pod Disruption Budget**: Ensures minimum pods are running during voluntary disruptions (e.g., node drain).

CL10 — Medium: **Service Account**: K8s identity for pods. **Workload Identity**: Maps K8s SA to cloud IAM (e.g., AWS IRSA, Azure AAD). **IRSA**: AWS-specific binding of SA to IAM Role. **Mounting Creds**: Bad practice due to rotation lag and credential leakage. **Workload Identity**: Solves this by allowing pods to assume IAM roles dynamically without storing secrets.

CL11 — Medium: **Object Storage** (S3/Blob): Files, unstructured, high durability (11 9s). Use for backups, static assets. **Block Storage** (EBS/Disk): Attached to VM, low latency. Use for DBs, OS. **File Storage** (EFS/Azure Files): Shared FS, NFS/SMB protocol. Use for shared app data. **Durability**: Object > Block > File (generally). **Availability**: Block/Block-Storage often higher SLA for single instance access.

CL12 — Hard: **Zero Trust K8s**: **Network Policies**: Default deny all. **Service Mesh (Istio)**: Enforces mTLS between services. **Pod Identity**: Identifies pods without secrets. **Admission Controllers (OPA/Kyverno)**: Enforce policies (e.g., no privileged containers). **Image Signing**: Verify images via Cosign/Notary. **Runtime Security (Falco)**: Detect anomalous behavior. **Difference**: Traditional model trusts perimeter; Zero Trust verifies every request regardless of origin.

CL13 — Easy: **CDN**: Network of edge servers caching content closer to users. **How it works**: Caches static assets at edge nodes. **Services**: AWS CloudFront, Azure CDN. **Use Case**: Use CDN for static assets (images, JS) and global traffic; serve directly from origin for dynamic content requiring low latency or security checks.

CL14 — Easy: **Region**: Geographic area with multiple data centers. **Availability Zone (AZ)**: Isolated location within a region (power/network). **Deploy across AZs**: Ensures High Availability (HA) against zone failure. **Zonal Resources**: Tied to one AZ (e.g., EC2). **Regional Resources**: Span all AZs (e.g., RDS Multi-AZ, S3).

CL15 — Easy: **Managed Database**: Service like RDS/Cloud SQL. **Provider Tasks**: Patching, backups, failover, scaling, monitoring. **User Tasks**: Schema design, query optimization, data management. **VM DB**: User handles all OS and DB maintenance.

CL16 — Easy: **IAM Users**: Individual humans. **Groups**: Collection of users. **Roles**: Permissions assigned to users/services. **Policies**: JSON documents defining permissions. **Least Privilege**: Grant only permissions necessary for the task. **Application**: Use roles for services, groups for humans, avoid admin access.

CL17 — Easy: **Serverless**: Event-driven compute without managing servers. **Comparison**: Lambda (AWS), Functions (Azure), Cloud Functions (GCP) are similar. **Cold Starts**: Latency on first invocation due to initialization. **Matter**: Critical for real-time apps. **Poor Fit**: Long-running processes, high I/O latency tolerance, or stateful workloads.

CL18 — Medium: **Ingress Resource**: K8s API for external access. **Gateway API**: New K8s standard (more flexible). **Cloud LB Annotations**: Use provider's LB (e.g., ALB). **Service Mesh**: Envoy-based ingress. **TLS Termination**: Can be at Edge (Cloud LB), Ingress Controller, or Client (mTLS). **Gateway API**: Use for multi-protocol support (HTTP/2, gRPC) and standardization across clusters.

CL19 — Hard: **Cost Optimization**: **Reserved Instances/Savings Plans**: Commitment for discounts. **Spot/Preemptible**: Cheaper, interruptible compute. **Right-sizing**: Match instance size to usage. **Storage Tiering**: Move infrequent data to Archive. **Idle Detection**: Terminate unused resources. **FinOps**: Cultural practice of cost ownership. **Showback/Chargeback**: Allocate costs to teams. **Tools**: AWS Cost Explorer, CloudHealth, Datadog.

CL20 — Hard: **Multi-Cloud Strategy**: **Abstraction**: Use K8s and Terraform to abstract cloud differences. **Networking**: AWS Direct Connect/Azure ExpressRoute + Transit Gateway. **Identity**: OIDC federation between clouds. **Trade-offs**: Complexity vs risk mitigation. **Justification**: Compliance requirements, avoiding vendor lock-in, or specific workload needs. **Unnecessary**: If single cloud meets all needs, multi-cloud adds operational overhead.

OT1 — Easy: **Purdue Model (ISA-95)**: Hierarchical architecture for industrial automation. **Level 0**: Field devices (sensors/actuators). **Level 1**: Basic Process Control System (PLCs/DCS). **Level 2**: Supervisory Control (SCADA/HMI). **Level 3**: Enterprise Operations (MES). **Level 4**: Business Planning (ERP). **Level 5**: IT/Corporate.

OT2 — Easy: **IT vs OT**: IT focuses on data availability and confidentiality; OT focuses on safety and availability (uptime). **Patching**: IT patches frequently; OT patching risks safety/uptime, requires testing and often requires downtime or specialized patches.

OT3 — Medium: **IDMZ (Industrial DMZ)**: Buffer zone between IT (L3/L4) and OT (L1/L2). **Traffic**: IT pushes commands to IDMZ; IDMZ pushes data to OT. **Direction**: L4 to L2/L3 allowed; L1 to L4 restricted. **Direct L4-L1**: Dangerous because it bypasses security controls, exposing control systems directly to corporate threats.

OT4 — Medium: **Modbus TCP**: L1, simple polling. **OPC UA**: L1/L2, secure, semantic data. **EtherNet/IP**: L1, CIP protocol. **PROFINET**: L1, real-time deterministic. **MQTT**: L2/L3, lightweight messaging for IoT/SCADA.

OT5 — Medium: **Data Diode**: Hardware enforces one-way data flow (e.g., OT to IT). **Firewall**: Bidirectional filtering. **Use Diode**: When absolute prevention of OT-to-IT data exfiltration is required (e.g., SCADA to corporate). **Limitation**: Cannot allow return traffic (commands from IT to OT).

OT6 — Medium: **Data Flow**: PLC -> **Historian** (local buffering) -> **Edge Gateway** (protocol translation) -> **MQTT Broker** -> **Cloud Ingestion**. **Security Boundaries**: Firewall at Edge Gateway; IDMZ between Broker and Cloud; No direct cloud-to-PLC connection.

OT7 — Hard: **IEC 62443 Zones**: Network boundaries based on security risk. **Conduits**: Connections between zones. **Model**: **Zone 1**: Corporate Network. **Zone 2**: Engineering Workstations. **Zone 3**: SCADA Servers. **Zone 4**: PLCs/SIS. **Conduits**: Firewall rules between zones (e.g., Zone 2 to Zone 3).

OT8 — Hard: **Segmentation**: **VLANs**: Separate production lines and functions (Engineering, SCADA, PLC). **Firewalls**: Between VLANs (L3). **Switches**: Layer 3 routing for segmentation. **Vendor Access**: Jump host with MFA. **Transition**: Use parallel network or phased migration with monitoring to avoid downtime.

OT9 — Hard: **SIS vs BPCS**: **SIS**: Safety Instrumented System (independent, fails-safe). **BPCS**: Basic Process Control (optimizes process). **IEC 61511**: Functional Safety standard. **Isolation**: SIS must be isolated to prevent ransomware from locking safety systems. **Consequence**: If SIS compromised, plant could be unsafe or shut down.

OT10 — Medium: **PLC**: Discrete control, local loops. **DCS**: Distributed control, continuous process, plant-wide. **SCADA**: Monitoring and data collection, often remote. **Coexistence**: Yes, e.g., DCS for process, SCADA for monitoring, PLCs for specific machines.

OT11 — Medium: **Remote Access**: **Jump Host**: Centralized entry point. **MFA**: Required. **Session Recording**: Audit trail. **Vendor Access**: Time-limited, specific scope. **RDP to HMI**: Unacceptable due to direct exposure of control interface to internet/corporate network.

OT12 — Hard: **Incident Response**: **Detection**: IDS/Anomaly detection on L3. **Inventory**: Know all assets. **Response**: Isolate network segment, notify control room. **Safe Ops**: Operators maintain manual control if automated systems are compromised. **Operator Role**: Critical decision-maker to ensure physical safety during cyber incident.

OT13 — Easy: **HMI**: Interface for operators to monitor/control processes. **Role**: Real-time visualization and control. **Difference**: HMI is for operators (run mode); Engineering Workstation is for engineers (config/design mode).

OT14 — Easy: **Historian**: Time-series database for process data. **Importance**: Trend analysis, compliance, troubleshooting. **Plant Historian**: Level 3 (process data). **Enterprise Historian**: Level 4 (business metrics, aggregated data).

OT15 — Easy: **Ladder Logic**: Programming language resembling relay logic. **Device**: PLC. **Dominance**: Familiarity for electricians, ease of maintenance, hardware support.

OT16 — Easy: **RTU**: Remote Terminal Unit, collects data in harsh environments. **Difference**: PLC is for logic/control; RTU is for telemetry/remote monitoring. **Environment**: RTUs used in remote pipelines/offshore; PLCs in factories.

OT17 — Easy: **Analog**: Continuous signal (4-20mA, 0-10V). **Digital**: On/Off. **4-20mA**: Preferred over 0-20mA because it allows "live zero" (0mA indicates wire break).

OT18 — Medium: **Asset Inventory**: List of all OT devices. **Foundation**: Essential for security (you can't protect what you don't know). **Discovery**: Passive (sniffing traffic) vs Active (ping/scanning). **Active Risk**: Can trigger devices or cause downtime.

OT19 — Hard: **MITRE ATT&CK for ICS**: Framework for ICS threats. **Tactics**: **Reconnaissance** (e.g., T1595), **Execution** (e.g., T1563), **Persistence** (e.g., T1564), **Privilege Escalation** (e.g., T1566), **Exfiltration** (e.g., T1567). **Difference**: Enterprise ATT&CK is general IT; ICS includes industrial-specific techniques. **Assessment**: Map current controls to tactics to find gaps.

OT20 — Hard: **Converged SOC**: **Log Collection**: Syslog/NetFlow from OT (non-intrusive). **SIEM**: Centralized analysis. **OT Rules**: Specific signatures (e.g., PLC scan cycles). **Staffing**: Mix of IT analysts and OT engineers. **False Positives**: High in OT; use thresholds. **Firmware Alert**: Quarantine device, verify change with vendor/operator before restoring.
