SC1-A
The pods fail because of a conflict between the Pod Security Standards (PSS) and the container image's default user.
1.  **Baseline vs. Restricted:** Before the upgrade, the namespace enforced **Baseline** PSS, which allows containers to run as root. After the upgrade, it enforces **Restricted** PSS.
2.  **Restricted Rules:** Restricted PSS requires `runAsNonRoot: true` and `runAsUser` to be set to a non-root UID.
3.  **The Conflict:** The manifests specify `runAsNonRoot: true` but do not set `runAsUser`. Kubernetes defaults `runAsUser` to the image's default user. The new base image (`cgr.dev/chainguard/static:latest`) defaults to `USER root`.
4.  **Result:** Kubernetes validates the pod spec against Restricted PSS. It sees `runAsNonRoot: true` but the effective `runAsUser` is 0 (root). This violates the rule that the user must be non-root, causing the pod admission to fail or the container runtime to reject the launch, resulting in `CrashLoopBackOff`.

SC2-A
1.  **Stale Data:** Promoting a cross-region read replica to primary means the new primary is a snapshot of the old primary at the time of promotion.
2.  **Replication Lag:** RDS cross-region replication is asynchronous. The replica does not have all the Write-Ahead Logs (WALs) generated on the primary since the last replication cycle.
3.  **Data Loss:** Any transactions committed on the primary after the last successful replication sync are lost. This is the "replication lag" window.
4.  **Quantification:** Check `pg_stat_replication` (if using custom PG) or RDS metrics `ReplicationLagSeconds`. In RDS, you can check the `ReplicationLag` metric or the `LastBackupTime` vs `CurrentTime` difference.
