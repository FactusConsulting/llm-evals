N1 — CL1 — Easy:  
**IaaS (Infrastructure as a Service)** provides virtualized computing resources over the internet (e.g., AWS EC2).  
**PaaS (Platform as a Service)** delivers hardware and software tools over the internet—typically for application development (e.g., AWS Elastic Beanstalk).  
**SaaS (Software as a Service)** delivers fully functional software applications over the internet on a subscription basis (e.g., Microsoft 365).  

N2 — CL2 — Easy:  
**Shared Responsibility Model** defines security boundaries between provider and customer.  
- **IaaS VMs**: Provider secures physical infrastructure, hypervisor, and region/zone; customer manages OS, apps, data, network config, IAM, and patching.  
- **Managed Kubernetes (e.g., EKS/AKS)**: Provider manages control plane; customer manages node pools, workloads, RBAC, network policies, and secrets.  
- **SaaS (e.g., M365)**: Provider handles *everything* (infrastructure to app); customer manages *only* user access, data, and configuration (e.g., MFA, DLP policies).  

N3 — CL3 — Medium:  
- **VPC (Virtual Private Cloud)**: Isolated logical network in cloud (e.g., AWS VPC).  
- **Subnet**: CIDR block within a VPC, tied to an Availability Zone.  
- **Security Group (SG)**: Stateful firewall at instance level; allows only specified inbound/outbound traffic.  
- **NACL (Network ACL)**: Stateless firewall at subnet level; evaluates rules in order; supports allow/deny.  
**Layering**: VPC > Subnets > SGs (instance) + NACLs (subnet).  
**Stateful vs Stateless**: SGs track connection state (auto-allow return traffic); NACLs do not (must explicitly allow both directions).  

N4 — CL5 — Medium:  
**Infrastructure as Code (IaC)** automates infrastructure provisioning via declarative or imperative code.  
- **Terraform/OpenTofu**: Declarative, HCL/JSON, multi-cloud, state-managed. Best for broad cloud portability.  
- **Pulumi**: General-purpose languages (Python, JS, Go), imperative/declarative hybrid. Best for dev teams comfortable with code.  
- **CloudFormation/Bicep**: Native to AWS/Azure; Bicep is more concise. Best for single-cloud, deep integration.  
- **Crossplane**: Kubernetes-native (CRDs), GitOps-friendly. Best for cloud resources managed *within* Kubernetes.  
**Choose**: Terraform for multi-cloud; Pulumi for developer velocity; CloudFormation/Bicep for native features; Crossplane for Kubernetes-centric ops.  

N5 — CL6 — Medium:  
- **HPA (Horizontal Pod Autoscaler)**: Scales *number* of pods based on CPU/memory or custom metrics (e.g., requests/sec).  
- **VPA (Vertical Pod Autoscaler)**: Adjusts *resources per pod* (CPU/memory limits/requests); may restart pods.  
- **Cluster Autoscaler**: Adds/removes *nodes* in the cluster based on pending pods.  
- **KEDA (Kubernetes Event-Driven Autoscaler)**: Scales based on *external event sources* (e.g., Kafka lag, queue depth, HTTP requests).  
**Use KEDA over HPA** when scaling depends on *external queue/event systems* (e.g., scale workers based on Azure Service Bus queue length). HPA only sees pod-level metrics.  

N6 — CL7 — Hard:  
**DR Strategy (RPO/RTO)**:  
- **RPO** (Recovery Point Objective): Max tolerable data loss (e.g., 5 min → async replication).  
- **RTO** (Recovery Time Objective): Max downtime (e.g., 30 min → active-active).  
**Active-passive**: Primary region serves traffic; secondary is warm/cold standby (async DB sync). Failover via DNS failover (Route 53 health checks).  
**Active-active**: Both regions serve traffic (e.g., multi-region DB with conflict resolution); lower RTO, higher cost/complexity.  
**DB replication**: Sync (synchronous, zero RPO, higher latency); Async (lower latency, non-zero RPO).  
**State management**: Use globally replicated state stores (e.g., DynamoDB Global Tables, Redis Cluster with Redis Cluster Mode).  
**Pilot Light**: Core DB replicated; compute cold. RTO ~hours.  
**Warm Standby**: Full app stack running in DR region (scaled down); DB async-replicated. RTO ~minutes.  
**Multi-site Active-Active**: Full traffic split; DB sync (sync or async); DNS-based routing. RTO ~seconds.  
**Cost**: Pilot < Warm < Active-Active.  

N7 — CL8 — Hard:  
**GitOps**: Declarative infrastructure/app delivery where Git is the *single source of truth*; tools continuously reconcile cluster state to Git.  
**ArgoCD vs FluxCD**:  
- **ArgoCD**: UI-rich, app-centric, supports Helm/Kustomize, syncs via server-side.  
- **FluxCD**: CLI-first, Git-agnostic (supports Helm, Kustomize), event-driven reconciliation, better for GitOps-native workflows.  
**Secrets handling**:  
- **Sealed Secrets** (Bitnami): Encrypt secrets in Git; controller decrypts at runtime.  
- **External Secrets Operator (ESO)**: Pull secrets from external vaults (e.g., AWS Secrets Manager, HashiCorp Vault).  
- **Vault**: Inject secrets via sidecar (e.g., Vault Agent) or CSI driver.  
**Drift**: Tools detect drift (ArgoCD shows “OutOfSync” status); can auto-reconcile or require manual approval. Manual changes are overwritten on next sync.  

N8 — CL9 — Hard:  
**Kubernetes architecture for legacy stateful app**:  
- **StatefulSet**: Ensures stable network identities, ordered startup/shutdown (e.g., `app-0`, `app-1`).  
- **Local PV/PVC**: Use `local` storage class with `nodeAffinity` to bind PVC to specific node for low-latency access.  
- **Headless Service** (`clusterIP: None`): Enables DNS-based pod-to-pod communication (e.g., `app-0.app-svc.namespace.svc.cluster.local`).  
- **Init Containers**: Pre-populate config files, validate paths, or run migrations before main container starts.  
- **ConfigMap as Volume Mount**: Mount config files to specific paths (e.g., `/etc/app/config.yaml`).  
- **Pod Disruption Budget (PDB)**: Ensure min available pods during maintenance (e.g., `minAvailable: 2`).  
*Note*: Local storage limits portability and complicates node failures—consider local SSD + replication or use CSI drivers (e.g., Rook-Ceph) if possible.  

N9 — CL10 — Medium:  
- **Service Account (SA)**: Kubernetes identity for pods (e.g., `default` SA).  
- **Workload Identity (GCP)**: Maps K8s SAs to GCP service accounts (no key files).  
- **IRSA (IAM Roles for Service Accounts, AWS)**: Maps K8s SAs to IAM roles via OIDC; pod assumes role via STS.  
**Avoid mounting credentials in pods** (e.g., AWS access keys in env vars) — keys are static, hard to rotate, and leak easily.  
**Workload identity federation** (e.g., AWS IRSA, GCP Workload Identity) enables short-lived, scoped tokens without long-lived keys.  

N10 — CL11 — Medium:  
- **Object Storage (S3, Blob)**: Unstructured data (e.g., logs, images); high durability (99.999999999% / 11 nines), scalable, cost-effective.  
- **Block Storage (EBS, Managed Disk)**: Low-latency, random I/O for VMs/DBs; persistent, attachable to one VM at a time (except shared disks).  
- **File Storage (EFS, Azure Files)**: POSIX-compliant NFS/SMB; shared access across multiple VMs (e.g., web servers, ML training).  
**Use cases**:  
- Object: Static assets, backups, data lakes.  
- Block: VM boot disks, databases.  
- File: Shared home dirs, app configs, ML pipelines.  
**Durability/Availability**:  
- S3: 99.999999999% durability; 99.99% (Standard), 99.9% (IA) availability.  
- EBS: 99.9% (single AZ); 99.99% (multi-AZ snapshots).  
- EFS: 99.99% (Standard), 99.999% (Infrequent Access).  

N11 — CL12 — Hard:  
**Zero-trust for K8s**:  
- **Network Policies**: Deny-all by default; allow only required pod-to-pod traffic (e.g., frontend → backend).  
- **Service Mesh (e.g., Istio)**: Enforces mTLS between pods, observability, traffic control.  
- **Pod Identity**: Use workload identity (IRSA/Workload Identity) instead of static credentials.  
- **Admission Controllers (OPA/Kyverno)**: Enforce policies (e.g., no privileged containers, required labels).  
- **Image Signing/Verification**: Use Cosign/Sigstore; enforce admission webhook to verify signatures.  
- **Runtime Security (Falco)**: Detect anomalous behavior (e.g., exec into container, file writes to sensitive paths).  
- **Secrets Management**: Use external secrets (ESO) + Vault; never store in ConfigMaps/Secrets unencrypted.  
**vs Perimeter Security**: Traditional models assume internal trust; zero-trust assumes breach, verifies *every* request, enforces least privilege, and monitors all traffic.  

N12 — CL13 — Easy:  
**CDN (Content Delivery Network)**: Distributed network of edge servers caching content closer to users, reducing latency and offloading origin.  
**How it works**: User requests → nearest edge → cache hit/miss → fetch from origin if needed.  
**Cloud CDNs**: AWS CloudFront, Azure CDN (Microsoft), Google Cloud CDN.  
**Use CDN** for static assets (images, JS, CSS), global scale, DDoS mitigation.  
**Serve directly from origin** for dynamic, personalized, or highly sensitive content (e.g., real-time APIs, user-specific data).  

N13 — CL14 — Easy:  
- **Region**: Geographical area (e.g., `us-east-1`).  
- **Availability Zone (AZ)**: Isolated data centers within a region (e.g., `us-east-1a`, `1b`, `1c`).  
**Deploy across AZs** for high availability: failure in one AZ doesn’t affect others.  
**Zonal resources**: Tied to one AZ (e.g., EC2 instance, EBS volume).  
**Regional resources**: Span multiple AZs (e.g., S3 bucket, RDS Multi-AZ DB).  

N14 — CL15 — Easy:  
**Managed DB service** (e.g., RDS, Cloud SQL): Cloud provider manages OS, patching, backups, replication, failover, scaling.  
**Provider handles**: Patching, backups, monitoring, high availability (Multi-AZ), scaling (vertical/horizontal), encryption at rest/in transit.  
**You manage**: Schema, queries, access control, application config, data.  
Running on VM: You manage *everything* (OS, DB engine, backups, HA, scaling).  

N15 — CL16 — Easy:  
- **IAM Users**: Human/service identities (long-term credentials).  
- **Groups**: Collections of users (for policy assignment).  
- **Roles**: Temporary identities assumed by users/services (e.g., EC2 instance role).  
- **Policies**: JSON documents defining permissions (attached to users/groups/roles).  
**Principle of Least Privilege (PoLP)**: Grant only necessary permissions. Apply via:  
- Fine-grained IAM policies (e.g., `s3:GetObject` on specific bucket ARN).  
- Use roles instead of long-lived keys.  
- Audit with IAM Access Analyzer.  

N16 — CL17 — Easy:  
**Serverless**: Code runs without managing servers; scales automatically, pay-per-execution.  
**Examples**: AWS Lambda, Azure Functions, GCP Cloud Functions.  
**Cold start**: Delay on first invocation after inactivity (due to runtime initialization). Matters for latency-sensitive apps (e.g., APIs with <100ms SLA).  
**Poor fit**: Long-running tasks (>15 min), stateful apps (no local disk), high-frequency low-latency APIs (cold starts dominate), or when full OS control needed.  

N17 — CL18 — Medium:  
**K8s Ingress options**:  
- **Ingress Resource**: Basic HTTP(S) routing (TLS termination at ingress controller, e.g., NGINX).  
- **Gateway API**: Next-gen, extensible, supports TCP/UDP/gRPC; more expressive than Ingress.  
- **Cloud LB Annotations** (e.g., `service.beta.kubernetes.io/aws-load-balancer`): Provisions cloud load balancer; TLS termination at LB (not in cluster).  
- **Service Mesh Ingress Gateway** (e.g., Istio Gateway): TLS termination at mesh edge; integrates with mTLS, observability.  
**TLS termination**:  
- Ingress: Usually at ingress controller (terminate TLS, forward HTTP).  
- Cloud LB: Terminate TLS at LB (offload CPU), forward HTTP to cluster.  
- Mesh Gateway: Terminate TLS, enforce mTLS to backend pods.  
**Use Gateway API** when needing advanced routing (e.g., HTTPRoute with match conditions), multi-protocol support, or future-proofing.  

N18 — CL19 — Hard:  
**Cost optimization ($80K/mo)**:  
- **RI/Savings Plans**: Commit to 1-year/3-year usage (e.g., EC2 RI, Compute SP) — up to 72% savings.  
- **Spot/Preemptible**: For fault-tolerant workloads (batch jobs, dev/test) — up to 90% off.  
- **Right-sizing**: Use Cost Explorer + Trusted Advisor; right-size based on actual usage (e.g., downsize over-provisioned EC2).  
- **Storage Tiering**: S3 Intelligent-Tiering (auto-move to IA/Archive), Glacier for backups.  
- **Idle Resource Detection**: Use AWS Cost Explorer “Idle” reports, Azure Cost Management “Underutilized” filters.  
- **FinOps Practices**: Assign cost tags, chargeback/showback (e.g., tag teams, show cost per pod), monthly reviews.  
**Tools/Processes**:  
- Tools: AWS Cost Explorer, Azure Cost Management, Kubecost, CloudHealth.  
- Processes: Tagging policy, FinOps team, budget alerts, quarterly reviews.  

N19 — CL20 — Hard:  
**Multi-cloud strategy**:  
- **Abstraction layers**: Kubernetes (common runtime), Terraform (IaC), Crossplane (cloud abstraction).  
- **Networking**: VPN, Direct Connect + ExpressRoute peering, or cloud interconnect (e.g., AWS Direct Connect to Azure ExpressRoute via third-party provider).  
- **Identity Federation**: Use Azure AD + AWS SSO (via SAML/OIDC), or Okta for unified identity.  
- **Trade-offs**: Higher complexity, cost, latency, operational overhead; vendor lock-in mitigation, regulatory compliance, best-of-breed services.  
**Justified when**: Regulatory constraints (data residency), need specific cloud services (e.g., GCP AI/ML), or disaster recovery across providers.  
**Unnecessary when**: Single cloud meets SLAs, cost/complexity outweighs benefits, or team lacks multi-cloud expertise.  

N20 — OT1 — Easy:  
**Purdue Model (ISA-95)**: Hierarchical model for industrial control systems.  
- **Level 0**: Process (sensors, actuators).  
- **Level 1**: Basic control (PLCs, RTUs, DCS controllers).  
- **Level 2**: Supervision (HMIs, SCADA clients).  
- **Level 3**: Site control (SCADA servers, historians, engineering workstations).  
- **Level 4**: Business planning & logistics (MES, ERP).  
- *(Level 5: Enterprise integration — sometimes included)*  

N21 — OT2 — Easy:  
**IT vs OT networks**:  
- **IT**: General-purpose, frequent updates, high bandwidth, security-focused (confidentiality/integrity).  
- **OT**: Real-time, deterministic, legacy protocols, availability/safety-critical.  
**Patching issues**: OT systems often run on legacy OS (e.g., Windows XP), unpatched due to downtime risk, vendor support limitations, or certification requirements. Patching can cause process instability or safety incidents.  

N22 — OT3 — Medium:  
**IDMZ (Industrial DMZ)**: Segments IT and OT networks.  
**Allowed traffic**:  
- IT → OT: Read-only historian data, limited control commands (e.g., setpoints).  
- OT → IT: Process data (e.g., historian, alarms), *no* control commands.  
**Direction**: One-way (OT → IT) for data; filtered two-way for limited control.  
**Direct IT→OT Level 1 dangerous**: Malware (e.g., Stuxnet) can propagate from IT to control systems, causing physical damage or safety hazards.  

N23 — OT4 — Medium:  
- **Modbus TCP**: Level 1/2; simple, read/write registers; used in legacy PLCs/sensors.  
- **OPC UA**: Level 1–3; secure, platform-independent, supports pub/sub; modern SCADA/HMI.  
- **EtherNet/IP (CIP)**: Level 1–2; Rockwell automation; encapsulates CIP over Ethernet.  
- **PROFINET**: Level 1–2; Siemens; real-time variants (RT, IRT).  
- **MQTT**: Level 2–3; lightweight pub/sub; used in IIoT edge-to-cloud (e.g., OPC UA → MQTT gateway).  

N24 — OT5 — Medium:  
**Data diode**: Hardware device allowing *one-way* data flow (e.g., OT → IT only); no return path.  
**Use case**: Securely export process data to cloud/analytics without risk of inbound attacks.  
**Limitation vs firewall**: No filtering, inspection, or bidirectional control; only unidirectional. Firewalls allow policy-based filtering but introduce attack surface.  

N25 — OT6 — Medium:  
**Data flow**:  
`PLCs/RTUs (L1) → OPC UA server (L1/L2) → Edge gateway (L2) → MQTT broker (L2/L3) → Historian/Cloud ingestion (L3/L4)`.  
**Security boundaries**:  
- Between L2 and L3: Firewall with strict rules (e.g., only MQTT port 8883 TLS).  
- Between L3 and L4: IDZ/DMZ with one-way data diode for cloud ingestion.  
- Edge gateway: Authenticate (mTLS), encrypt (TLS), sanitize data.  

N26 — OT7 — Hard:  
**IEC 62443 zones/conduits**:  
- **Zone**: Group of assets with same security needs.  
- **Conduit**: Communication path between zones; protected by firewalls/IDPS.  
**Manufacturing plant zones**:  
- **Zone 1**: Corporate network (IT).  
- **Zone 2**: Engineering workstations (L3).  
- **Zone 3**: SCADA servers (L3).  
- **Zone 4**: PLCs/HMIs (L1/L2).  
- **Zone 5**: SIS (air-gapped).  
**Conduits**:  
- Z1→Z2: Firewall (HTTPS, VPN).  
- Z2→Z3: Firewall (OPC UA, restricted IPs).  
- Z3→Z4: Firewall (OPC UA, read-only or limited write).  
- Z4↔Z5: None (air gap).  

N27 — OT8 — Hard:  
**Segmentation strategy**:  
- **VLANs**: Separate by function: VLAN 10 (PLCs), 20 (HMIs), 30 (SCADA), 40 (engineering), 50 (vendor remote access).  
- **Firewall**: Place between VLANs (e.g., SCADA→PLC: allow only OPC UA on port 443/502).  
- **Switches**: Managed L3 switches with ACLs; disable unused ports.  
- **Vendor access**: Dedicated VLAN with jump host, MFA, session recording, time-limited access (e.g., via PAM).  
**Transition without downtime**:  
- Phase 1: Logical segmentation (VLANs + ACLs) — no hardware changes.  
- Phase 2: Add physical firewalls.  
- Test in staging; use network taps for monitoring during cutover.  

N28 — OT9 — Hard:  
**SIS vs BPCS**:  
- **BPCS**: Controls normal operations (e.g., PLCs, SCADA).  
- **SIS**: Safety-critical shutdown (e.g., emergency depressurization); independent, fail-safe.  
**IEC 61511**: Functional safety standard for process industry (SIS lifecycle).  
**Air gap**: Prevents IT/OT cyberattacks from reaching SIS. If ransomware hits SIS:  
- May cause unnecessary shutdowns (safety) or *fail to shut down* (catastrophic).  
- Physical safety systems (e.g., mechanical interlocks) may still function, but digital overrides could be bypassed.  

N29 — OT10 — Medium:  
- **PLC**: Single-machine controller (e.g., assembly line).  
- **DCS**: Distributed control system for large, continuous processes (e.g., refineries).  
- **SCADA**: Centralized monitoring/controls over geographically dispersed assets (e.g., pipelines).  
**Coexistence**: Yes — e.g., SCADA monitors DCS/PLCs; PLCs handle local control under DCS supervision.  

N30 — OT11 — Medium:  
**Remote access architecture**:  
- **Jump host**: Bastion with MFA, session recording (e.g., Teleport, JumpCloud).  
- **No direct RDP to HMI**: HMI should not be internet-facing; use jump host + RDP over TLS.  
- **Vendor access**: Time-limited, role-based, with OT engineer present (or recorded).  
- **Why not direct RDP?**: Exposes legacy RDP vulnerabilities (e.g., BlueKeep), no audit trail, bypasses segmentation.  

N31 — OT12 — Hard:  
**Detection & response plan**:  
- **Network monitoring**: Deploy OT-specific IDS (e.g., Nozomi, Darktrace OT), flow analysis (NetFlow), anomaly detection (baseline traffic).  
- **Asset inventory**: Maintain live inventory (passive monitoring preferred).  
- **Incident response**:  
  1. Confirm threat (e.g., detect C2 traffic to vendor VPN).  
  2. Isolate compromised segment (firewall rules, VLAN shutdown).  
  3. Coordinate with control room: Ensure safe operations (manual override if needed).  
  4. Preserve evidence (forensics, logs).  
- **Operator role**: Maintain safe process state (e.g., manual control), report anomalies, follow IR playbooks.  

N32 — OT13 — Easy:  
**HMI**: User interface for operators to monitor/control processes (e.g., displays trends, alarms, allows setpoint changes).  
**vs Engineering Workstation**: HMI is for *operation*; engineering workstation is for *configuration* (e.g., programming PLCs, downloading logic).  

N33 — OT14 — Easy:  
**Historian**: Time-series database for process data (e.g., sensor readings, events).  
**Plant historian (L3)**: Local to site; high-frequency, low-latency.  
**Enterprise historian (L4)**: Aggregates plant data for reporting/analytics; lower frequency, integrated with MES/ERP.  

N34 — OT15 — Easy:  
**Ladder logic**: Graphical programming language for PLCs; resembles relay ladder diagrams.  
**Executed by**: PLC CPU.  
**Dominant because**: Intuitive for electricians, standardized (IEC 61131-3), reliable, and deeply embedded in legacy systems.  

N35 — OT16 — Easy:  
**RTU (Remote Terminal Unit)**: Device for remote monitoring/controls (e.g., pipeline valves); often uses serial (RS-232/485) or wireless (cellular, radio).  
**vs PLC**: RTUs are optimized for remote, low-power, long-distance comms; PLCs are for local, high-speed control.  
**Deploy RTUs** in remote, harsh environments (e.g., oil wells, water pumps).  

N36 — OT17 — Easy:  
**Analog signals (4–20mA, 0–10V)**: Continuous voltage/current representing process variable (e.g., 4mA = 0%, 20mA = 100%).  
**Digital signals**: On/off (e.g., pushbutton, limit switch).  
**Why 4–20mA?**:  
- Immune to voltage drop over long wires (current same everywhere).  
- “Live zero” (4mA) distinguishes signal loss (0mA) from low value (e.g., 0–3.9mA = fault).  

N37 — OT18 — Medium:  
**OT asset inventory**: Catalog of devices (PLCs, HMIs, protocols, firmware).  
**Why foundation?**: Enables vulnerability management, patching, segmentation, and incident response.  
**Discovery tools**:  
- Passive: NetFlow, Tenable.ot, Nozomi (listen to traffic).  
- Active: Nmap (risky — can crash legacy devices).  
**Avoid active scanning**: Legacy devices may not handle unexpected traffic; can cause process disruption.  

N38 — OT19 — Hard:  
**MITRE ATT&CK for ICS**: Framework for adversarial tactics/techniques in industrial environments.  
**5 tactics + examples**:  
1. **Initial Access**: Phishing (e.g., malicious email to engineer).  
2. **Execution**: Run malicious code on HMI (e.g., `cmd.exe`).  
3. **Persistence**: Modify PLC firmware.  
4. **Defense Evasion**: Disable antivirus on SCADA server.  
5. **Impact**: Manipulate setpoints to cause overpressure.  
**vs Enterprise ATT&CK**: ICS-specific tactics (e.g., “Inhibit Monitoring”, “Process Manipulation”), focuses on safety-critical systems.  
**Use for assessment**: Map detections to techniques; identify gaps (e.g., no PLC firmware integrity checks).  

N39 — OT20 — Hard:  
**Converged IT/OT SOC**:  
- **Log collection**: Use lightweight OT agents (e.g., Sysmon for Windows OT devices), NetFlow, syslog from firewalls/PLCs (non-intrusive).  
- **SIEM integration**: Normalize logs (e.g., using OpenC2, CEF); add OT context (e.g., process area, device type).  
- **OT detection rules**: e.g., “Unexpected firmware download to PLC”, “Large outbound data to cloud from Level 2”.  
- **Triage**: IT analysts triage; escalate to OT engineers for context (e.g., “Is this setpoint change normal?”).  
- **Staffing**: Hybrid team (IT security + OT engineers); OT engineers on-call.  
- **False positives**: Tune rules with OT engineers; avoid alerts on normal maintenance (e.g., firmware updates during shutdown).  
**PLC firmware alert**:  
1. Verify if authorized (check change log).  
2. If unauthorized: Isolate PLC, preserve memory dump, engage OT vendor.  
3. Assess safety impact (e.g., could firmware change cause unsafe state?).  
4. Restore from known-good image (if safe to do so).
