## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry-run that shows what changes will be made to the infrastructure without applying them. `tofu apply` executes those changes to reach the desired state defined in the configuration.

**T2 — Easy:** State is a JSON file mapping your configuration to real-world resources. Remote state stores this file in a shared location (S3, Azure Blob, etc.), which is critical for team collaboration to prevent state conflicts and ensure everyone works from the same source of truth.

**T3 — Medium:** `count` creates multiple resources based on an integer; it uses index-based identification (`[0], [1]`). `for_each` iterates over a map or set; it uses keys as identifiers. `for_each` is preferred when items may be removed from the middle of a list, as `count` would cause all subsequent resources to be shifted and recreated.

**T4 — Medium:** This is called "drift." During the next `plan` or `apply`, OpenTofu refreshes the state by querying the cloud API. It detects the difference between the actual state and the stored state and proposes a plan to revert the manual change back to the configured state.

**T5 — Medium:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type  = "t3.micro"
  tags          = { Name = each.value }
}
```

**T6 — Hard:** `terraform_remote_state` reads the entire raw state file of another project. Output values are specific variables exposed by a module. The recommended alternative is using **Data Sources** for existing resources (e.g., `data "aws_vpc"`) because reading remote state creates tight coupling; if the source state structure changes, the dependent code breaks.

**T7 — Hard:** Provisioners run *after* the resource is created but before it's marked as complete in state. If an output depends on a value generated inside a provisioner, that value isn't available until the apply finishes. Fix: Use a `null_resource` with a local file trigger or use a native provider feature/external data source to read the kubeconfig from the disk after creation.

**T8 — Medium:** `tofu import` brings existing infrastructure into state. Limitation: CLI import requires you to write the HCL code manually first. The `import` block (1.5+) allows declarative imports, enabling Tofu to generate the configuration automatically via `-generate-config`.

**T9 — Easy:** A variable is an input parameter (`variable` block) used to customize deployments. An output is a return value (`output` block) used to expose information (like an IP address) to the user or other modules.

**T10 — Easy:** A provider is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS, GCP). Running `plan` without `init` fails because providers are not yet downloaded and initialized.

**T11 — Easy:** `.terraform.lock.hcl` tracks the exact versions and hashes of providers used. It should be committed to version control to ensure all team members and CI pipelines use identical provider versions, preventing "it works on my machine" bugs.

**T12 — Easy:** `tofu destroy` deletes all managed resources in the state. To target one resource: `tofu destroy -target=aws_instance.web[0]`.

**T13 — Easy:** A data source fetches information from an existing resource not managed by the current project. Example: Using a data source to find the ID of a default VPC instead of creating a new one.

**T14 — Medium:** Variables are inputs provided at runtime; locals are internal constants/computed values. Use locals to avoid repeating complex expressions throughout your code and to keep logic centralized.

**T15 — Medium:**
- `create_before_destroy`: Creates the replacement before deleting the old one (use case: zero-downtime VM updates).
- `prevent_destroy`: Errors out if a destroy is attempted (use case: critical production databases).
- `ignore_changes`: Ignores specific attribute drift (use case: tags updated by an external auto-scaling process).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource has been renamed or moved into a module. It updates the state file without destroying and recreating the physical resource, preserving infrastructure stability during refactoring.

**T17 — Hard:** Tofu builds a Directed Acyclic Graph (DAG) to determine execution order. **Implicit dependencies** occur when one resource references another's attribute. **Explicit dependencies** use `depends_on`. `depends_on` forces sequential execution, reducing parallelism and potentially slowing down applies; it should be used only when implicit links aren't possible.

**T18 — Hard:** 
1. **Modularization**: Split large states into smaller ones to reduce the number of resources refreshed per plan. Tradeoff: More complex orchestration.
2. **Targeting**: Use `-target` for specific changes. Tradeoff: Risk of ignoring dependent side effects.
3. **Reduce Provider Calls**: Optimize data sources or avoid excessive API calls in logic. Tradeoff: Potential stale data.
4. **State Splitting/Workspaces**: Separate environments. Tradeoff: Management overhead.

**T19 — Hard:** State locking prevents concurrent writes by placing a lock on the backend (e.g., DynamoDB). If a crash occurs, the lock remains "stale." You manually break it using `tofu force-unlock <lock-id>`. The risk is that if someone *is* actually running an apply, you could corrupt the state file.

**T20 — Hard:** 
1. Update the `backend` block from `local` to `s3` with `dynamodb_table` configured.
2. Run `tofu init`. OpenTofu will detect the change and ask to migrate existing local state to S3.
3. Confirm migration. Tofu uploads the `.tfstate` to S3 and creates the initial lock entry.
4. Verify by checking the S3 bucket for the JSON file and confirming the DynamoDB table contains the lock record.

## Ansible

**A1 — Easy:** A **task** is a single action (e.g., install package). A **role** is a structured bundle of tasks, variables, and handlers for a specific function (e.g., "nginx"). A **playbook** is the top-level orchestration file mapping roles/tasks to hosts.

**A2 — Easy:** `ansible_facts` is a dictionary containing system metadata gathered at start. Access OS family via: `{{ ansible_os_family }}`.

**A3 — Medium:** 
- `command`: Simple execution; doesn't support shell operators like pipes or redirects. Safest.
- `shell`: Runs through `/bin/sh`; supports pipes, wildcards, and environment variables. Use when complex logic is needed.
- `raw`: Bypasses Python on target; sends raw SSH commands. Use for bootstrapping nodes without Python installed.

**A4 — Medium:** Idempotency means running the playbook multiple times results in the same state without unnecessary changes. 
- **Idempotent**: `apt: name=vim state=present`.
- **Not Idempotent**: `shell: echo "Hello" >> /tmp/log`. (Adds text every time it runs).

**A5 — Medium:**
```yaml
- name: Install htop based on OS
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
  when: ansible_os_family == 'Debian'

- name: Install epel for RedHat
  yum:
    name: epel-release
    state: present
  when: ansible_os_family == 'RedHat'

- name: Install htop for RedHat
  yum:
    name: htop
    state: present
  when: ansible_os_family == 'RedHat'
```
*(Note: Better handled via a role with variable files per OS).*

**A6 — Hard:** Precedence (lowest to highest): Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ Playbook vars $\rightarrow$ Extra vars (`-e`). `set_fact` is high priority and overrides most static variables.

**A7 — Hard:** 
1. Use two inventory groups: `first_batch` (3 nodes) and `remaining_nodes` (47 nodes).
2. Run the play first against `first_batch`.
3. Use `wait_for` module on the control node or agents to ensure port 6443 is open before starting the second group.
4. Alternatively, use `serial: [3, 47]` in the playbook.

**A8 — Medium:** `ansible-vault` encrypts data. To encrypt a single variable, use `ansible-vault encrypt_string 'mysecretvalue'` and paste the resulting encrypted block directly into your YAML vars file.

**A9 — Easy:** An inventory lists target hosts. **Static**: A text/INI file listing IPs/hostnames. **Dynamic**: A script or plugin that queries an API (AWS, GCP) to generate the host list in real-time.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A handler is a special task triggered by a `notify` keyword when a task reports a "changed" status. Unlike regular tasks, handlers run once at the end of the play. Triggered via: `notify: restart nginx`.

**A12 — Easy:** `ansible.cfg` configures Ansible's behavior globally. Common settings: `remote_user`, `forks` (parallelism), and `inventory` path.

**A13 — Easy:** `register` captures the output of a task into a variable.
```yaml
- shell: uptime
  register: system_uptime
- debug: msg="Uptime is {{ system_uptime.stdout }}"
```

**A14 — Medium:** `import_tasks` is static; it processes the file during playbook parsing. `include_tasks` is dynamic; it evaluates conditions and variables at runtime. Use `include_tasks` for conditional logic based on results of previous tasks.

**A15 — Medium:** Galaxy is a community hub for roles/collections. Install using a `requirements.yml`:
```yaml
roles:
  - name: geerlingg.nginx
```
Run: `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:** 
- `ssh`: Standard remote execution over SSH.
- `local`: Runs on the control node itself.
- `network_cli`: Specialized for network devices (switches) that don't support Python.

**A17 — Hard:** `delegate_to` runs a task on a different host than the current target. `run_once` executes the task only once for the entire batch. Example: Update an external DNS record on localhost with the IP gathered from one of the remote web servers.

**A18 — Hard:** 
1. **Forks**: Increase `forks = 50` in `ansible.cfg` to increase parallelism. Tradeoff: Higher CPU/RAM load on control node.
2. **Pipelining**: Enable `pipelining = True` to reduce SSH roundtrips. Tradeoff: Requires `requiretty` disabled in sudoers.
3. **Fact Caching**: Use Redis or JSON file caching for facts. Tradeoff: Potential stale data if hosts change.
4. **Mitogen**: A third-party plugin that optimizes SSH communication. Tradeoff: Compatibility issues with some modules.

**A19 — Hard:** `{{ }}` is for expressions; `{% %}` is for logic (loops, ifs); `{# #}` is for comments.
```jinja2
upstream backend {
  {# Health check enabled #}
  {% for server in backend_servers %}
    server {{ server.ip }}:80; {# Node: {{ server.name }} #}
  {% endfor %}
}
```

**A20 — Hard:** 
1. Set `serial: 20%` (or a specific number) to process servers in batches.
2. **Pre-task**: Remove current server from Load Balancer (LB).
3. **Update**: Deploy application code and restart service.
4. **Health Check**: Use the `uri` module to verify `/health` endpoint returns 200 OK.
5. **Post-task**: Re-add server to LB.
6. **Rollback**: Wrap tasks in a `block`. In the `rescue` section, trigger a rollback script or revert version and alert admins.
