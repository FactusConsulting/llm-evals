## Application Architecture

**AA1** — A **monolith** is a single unified unit where all business logic and data access reside in one codebase/process. **Microservices** decompose this into small, independent services communicating over a network. Three problems introduced by microservices: 1) **Network Latency**: Inter-service calls add overhead compared to in-memory calls. 2) **Distributed Data Consistency**: Maintaining consistency across multiple databases requires complex patterns like Sagas. 3) **Operational Complexity**: Monitoring, deploying, and debugging dozens of services is harder than managing one.

**AA2** — **Synchronous** communication requires the caller to wait for a response before proceeding (e.g., REST API call via HTTP). **Asynchronous** communication involves sending a message and continuing work without waiting for an immediate result (e.g., publishing a message to RabbitMQ).

**AA3** — An **API Gateway** provides high-level business logic (authentication, rate limiting, request transformation, orchestration), while a **reverse proxy** primarily handles routing, load balancing, and SSL termination. While a Gateway can perform reverse proxy functions, it cannot replace a low-level proxy entirely if extreme performance or simple L4 routing is required; however, in most modern stacks, the Gateway acts as the primary entry point.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. If one step fails, "compensating transactions" are triggered to undo previous steps.
*   **Choreography**: Services exchange events without a central coordinator. Appropriate for simple workflows with few services.
*   **Orchestration**: A central orchestrator tells participants what to do. Appropriate for complex workflows where centralized visibility and control are needed.

**AA5** — **CQRS** separates read operations (Queries) from write operations (Commands). It is paired with **Event Sourcing**, which stores state as a sequence of immutable events rather than current state. This combination solves the problem of auditability and allows highly optimized read views (projections) that traditional CRUD models struggle to provide at scale.

**AA6** — The **Circuit Breaker** prevents cascading failures by stopping requests to a failing service. States: **Closed** (requests flow), **Open** (fail fast immediately), **Half-Open** (test if service recovered). Unlike retry/backoff (which keeps trying), it stops traffic entirely to allow the downstream service to recover. Use both together: Circuit Breaker to stop the bleed, Retry with backoff for transient glitches before the breaker trips.

**AA7** — 
1. **Shared DB/Schema**: Lowest cost, lowest security; high noisy-neighbor risk. High operational simplicity.
2. **Shared DB/Separate Schema**: Medium cost; better logical isolation; moderate complexity in migrations. Reduced noisy-neighbor risk.
3. **Separate Database**: Highest cost, highest security; maximum isolation; high operational overhead (backup/patching $N$ databases). Zero noisy-neighbor risk.

**AA8** — **Strong consistency** ensures all clients see the same data simultaneously after a write. **Eventual consistency** guarantees that given enough time without updates, all nodes will converge. For inventory: use **strong consistency**. Architect this using an RDBMS with ACID transactions or a distributed SQL store (e.g., CockroachDB) utilizing linearizable reads and atomic decrements to prevent overselling.

**AA9** — A **sidecar proxy** is a helper process running alongside the application container. In Istio, Envoy acts as the **data plane** (handling actual traffic), while Istio's control plane manages configuration. mTLS between sidecars provides identity-based encryption and authentication at the network layer, removing the need for developers to implement TLS logic within the application code.

**AA10** — The **Strangler Fig pattern** involves incrementally replacing legacy functionality by wrapping it behind a proxy. Strategy: 1) Place a routing layer (API Gateway) in front of the .NET Framework monolith. 2) Build new features in .NET 8 microservices. 3) Route specific endpoints from the gateway to the new services. 4) Gradually migrate old endpoints until the monolith is "strangled" and can be decommissioned.

**AA11** — The **12-Factor App** methodology optimizes apps for cloud deployment. Factors include: 1) Single codebase, 2) Explicit dependencies, 3) Config in environment, 4) Backing services treated as attached resources, 5) Build/release/run separation, 6) Stateless processes. These ensure portability, scalability, and consistency across environments.

**AA12** —
*   **Coupling**: Event-driven (Kafka) is loosely coupled; Request-driven (REST) is tightly coupled.
*   **Scalability**: Kafka scales better for high throughput via partitioning. REST scales via load balancing.
*   **Debugging**: REST is easier (request $\rightarrow$ response); Kafka is harder (tracing events through queues).
*   **Ordering**: Kafka guarantees order within a partition; REST has no inherent ordering.
*   **Failure**: Kafka allows replay/retries later; REST requires immediate retry logic.
Choose Kafka for async pipelines/streaming; REST for synchronous APIs.

**AA13** — A **load balancer** distributes traffic across multiple servers. **Layer 4** balances based on IP/TCP ports (fast, simple). **Layer 7** balances based on application data like HTTP headers or URLs. Use case: Routing `/api` to one cluster and `/static` to another.

**AA14** — A **message queue** (RabbitMQ) delivers messages to consumers and deletes them once acknowledged. A **log-based broker** (Kafka) persists messages as an append-only log that can be replayed. Pick RabbitMQ for task distribution; pick Kafka for event streaming and audit logs.

**AA15** — A **container** shares the host OS kernel, while a **VM** includes a full guest OS. Containers are popular because they are lightweight, start in seconds, and ensure "it works on my machine" consistency across environments.

**AA16** — **Stateless services** do not store client data between requests (e.g., a calculation API), making them easy to scale horizontally by adding more instances behind a load balancer. **Stateful services** remember previous interactions (e.g., a database), requiring sticky sessions or external state stores to scale.

**AA17** — An **ORM** maps code objects to database tables. Examples: Hibernate (Java), Entity Framework (.NET). Trade-offs: ORMs increase developer productivity and portability but can produce inefficient SQL ("N+1 problem") compared to raw SQL's precision and performance.

**AA18** — The **Bulkhead pattern** isolates resources so one failure doesn't crash the whole system. In microservices, this means isolating thread pools per downstream service call. Example: If Service A calls B and C, give each its own dedicated thread pool. If Service B hangs, it only exhausts its own pool, leaving Service C functional.

**AA19** — **OT** requires a central server to transform operations based on context; **CRDTs** use mathematically commutative structures that merge automatically without coordination. For offline editing, choose **CRDTs** because they allow local updates that converge predictably when reconnecting without needing a central authority for every operation.

**AA20** — Challenges include maintaining trace IDs across different languages/frameworks. Use **W3C Trace Context** for standardized propagation. **Head-based sampling** decides at the start of a request; **tail-based** samples after completion (e.g., keep all errors). To ensure continuity in Kafka, inject the trace ID into the message headers; the consumer then extracts this header to continue the span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare Metal)** runs directly on hardware (e.g., VMware ESXi, Proxmox VE). **Type 2 (Hosted)** runs as an app on an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network)** provides block-level storage via iSCSI or Fibre Channel; used for high-performance databases. **NAS (Network Attached Storage)** provides file-level storage via NFS or SMB; used for shared files and backups.

**OP3** — **3-Tier** consists of Core $\rightarrow$ Distribution $\rightarrow$ Access layers. **Leaf-Spine** is preferred because it provides consistent low latency and non-blocking "East-West" traffic flow between servers, solving the bottlenecks and Spanning Tree Protocol (STP) limitations of traditional hierarchical designs.

**OP4** — Use $\ge 3$ nodes for quorum. Fencing is handled by STONITH (Shoot The Other Node In The Head) via IPMI/iDRAC. Shared storage can be Ceph (distributed), iSCSI, or NFS. During node failure, the remaining nodes detect loss of heartbeat, fence the failed node to prevent data corruption, and restart its VMs on healthy nodes.

**OP5** — **VLAN Trunking** allows multiple VLANs to traverse a single physical link using **802.1Q tagging**, which adds a tag to each frame identifying the VLAN ID. On Linux: create tagged sub-interfaces (e.g., `ip link add link eth0 name eth0.10 type vlan id 10`).

**OP6** — RAID 1 (Mirror), 5 (Parity - 1 fail), 6 (Dual parity - 2 fail), 10 (Striped mirror), Z2 (ZFS dual parity). For a DB server with 6 drives: choose **RAID 10**. It provides the best balance of high IOPS (performance) and fault tolerance without the write penalty of parity calculations found in RAID 5/6.

**OP7** — Use internal AD DNS for local resolution; use **split-horizon DNS** so external users see public IPs while internal users see private IPs. Configure recursive resolvers internally and forwarders for external queries. VPN clients are pushed internal DNS settings via the VPN tunnel. DNSSEC is applied only to the external authoritative zone.

**OP8** — Root CA $\rightarrow$ Subordinate CA $\rightarrow$ End Entity. The root remains offline for security. CRLs provide lists of revoked certs, whereas OCSP allows real-time status checks. A compromised subordinate CA requires revoking that specific branch; a compromised root CA necessitates rebuilding the entire PKI trust chain from scratch.

**OP9** — MPLS (High cost, guaranteed QoS); IPsec (Low cost, internet jitter); SD-WAN (Flexible, dynamic paths); WireGuard (Fast, modern mesh). For VoIP at 5 sites, recommend **SD-WAN**. It combines the reliability of multiple links with intelligent traffic steering to prioritize latency-sensitive voice packets over bulk data.

**OP10** — iDRAC/iLO/IPMI provides **out-of-band management**, allowing power control and console access regardless of OS state. If exposed to the internet, an attacker can gain full hardware-level control of the server, bypassing all OS security.

**OP11** — **LVM** manages logical volumes; **LVM-Thin** allows overprovisioning by allocating space on demand; **ZFS** is a combined filesystem and volume manager using Copy-on-Write (CoW). ZFS snapshots are near-instantaneous pointers; LVM snapshots are block-based and can degrade performance as they grow.

**OP12** — Use a stretch cluster with nodes across two sites and a witness node in a third site for quorum. Ceph CRUSH rules must be configured to ensure replicas are distributed across failure domains (sites). A 2-site Ceph setup without a tiebreaker risks "split-brain," where both sides think they are primary, leading to catastrophic data corruption.

**OP13** — DHCP uses **DORA**: Discover $\rightarrow$ Offer $\rightarrow$ Request $\rightarrow$ Acknowledge. When a lease expires and no server responds, Windows clients assign themselves an APIPA address (`169.254.x.x`).

**OP14** — An unmanaged switch is plug-and-play. A **managed switch** provides VLANs, Spanning Tree Protocol (STP) to prevent loops, SNMP monitoring, and port mirroring—all critical for security and network stability in enterprises.

**OP15** — NTP synchronizes system clocks. Accurate time is critical for Kerberos authentication, log correlation during troubleshooting, and database replication timestamps. Clock drift causes auth failures and corrupted transaction sequences.

**OP16** — Physical: Hardware; VM: Hypervisor abstraction; Container: OS kernel sharing. Run on bare metal when you need maximum I/O performance, direct GPU access, or have extremely high resource requirements that virtualization overhead would hinder.

**OP17** — **UPS** provides immediate battery power for short gaps; a **generator** provides long-term power. Both are needed because the generator takes time to start. The **ATS (Automatic Transfer Switch)** detects utility failure and switches the load to the generator automatically.

**OP18** — Active-Passive has one standby node; Active-Active uses both simultaneously. For PostgreSQL HA: use Pacemaker/Corosync to manage a Virtual IP (VIP). If the primary fails, Pacemaker triggers STONITH to kill the failed node and moves the VIP to the passive node to promote it to primary.

**OP19** — 3-2-1 Rule: 3 copies of data, 2 different media, 1 offsite. RPO (Recovery Point Objective) defines acceptable data loss; RTO (Recovery Time Objective) is downtime limit. Use immutable backups (WORM storage) to prevent ransomware encryption. Backup is a copy of data; DR is the comprehensive plan to restore services after a disaster.

**OP20** — 802.1X involves the **Supplicant** (client), **Authenticator** (switch), and **Auth Server** (RADIUS). EAP-TLS uses certificates; PEAP uses passwords. RADIUS assigns VLANs dynamically based on user identity. Devices failing auth are put in a guest VLAN or blocked. **MAB** allows non-802.1X devices by authenticating their MAC address against a whitelist.
