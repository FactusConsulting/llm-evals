## Cloud Infrastructure Architecture

**CL1 — Easy:** IaaS provides raw compute/storage/network (you manage OS); PaaS provides a platform for apps (you manage code); SaaS is a finished product (you manage settings). Examples: AWS EC2 (IaaS), Google App Engine (PaaS), Microsoft 365 (SaaS).

**CL2 — Easy:** The provider manages "of" the cloud (hardware, global infra); you manage "in" the cloud. For **IaaS VMs**, you handle the Guest OS and above. For **Managed Kubernetes**, the provider handles the control plane; you handle worker nodes/pods. For **SaaS**, the provider handles almost everything except identity and data access.

**CL3 — Medium:** A **VPC** is an isolated virtual network. A **Subnet** is a range of IPs within that VPC. A **Security Group** is a stateful firewall at the instance level (remembers requests). A **NACL** is a stateless firewall at the subnet level (checks every packet regardless of state). Layering: Traffic hits NACL $\rightarrow$ Subnet $\rightarrow$ Security Group $\rightarrow$ Instance.

**CL4 — Medium:** A **Landing Zone** is a pre-configured multi-account environment. **OUs** group accounts by function (Prod, Dev, Shared Services). **Guardrails** (e.g., SCPs) enforce policy across accounts. **Shared Networking** uses Hub-and-Spoke or Transit Gateway to centralize egress/ingress. Centralized logging aggregates logs into one security account for auditing. Single-account approaches are problematic due to blast radius, quota limits, and billing complexity.

**CL5 — Medium:** IaC manages infrastructure via code files. **Terraform/OpenTofu**: Cloud-agnostic, HCL based, industry standard. **Pulumi**: Uses general languages (Python, TS), better for devs. **CloudFormation/Bicep**: Vendor-specific, deep integration with AWS/Azure. **Crossplane**: K8s-native control plane managing external resources. Choose Terraform for portability; Pulumi for complex logic; Bicep/CFN for simplicity in single-cloud shops.

**CL6 — Medium:** **HPA** scales pods based on CPU/RAM metrics. **VPA** adjusts the resource requests/limits of existing pods. **Cluster Autoscaler** adds/removes nodes from the cluster. **KEDA** allows scaling based on external events (e.g., RabbitMQ queue length). Use KEDA over HPA when scaling depends on application-level triggers rather than just hardware utilization.

**CL7 — Hard:** Strategy: Active-Passive (Warm Standby) is a balanced approach. **RPO** (Data loss): Async replication for distance, Sync for zero loss (but higher latency). **RTO** (Downtime): DNS failover via Route53/Traffic Manager. State management requires global databases (Aurora Global / CosmosDB). **Pilot Light**: Minimal core services running. **Warm Standby**: Scaled-down version always running. **Multi-site Active-Active**: Zero RTO, highest cost, requires complex conflict resolution.

**CL8 — Hard:** GitOps uses Git as the "Source of Truth." A controller syncs the cluster to match Git state. **ArgoCD** provides a rich UI and pull model; **FluxCD** is more lightweight and focused on automation. Secrets are handled via **SealedSecrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault), or **Vault**. Manual drift is automatically overwritten by the controller to ensure consistency.

**CL9 — Hard:** Architecture: Use a **StatefulSet** for stable network IDs. Map **PV/PVCs** using a `local` storage class for low latency. Implement a **Headless Service** for direct pod communication. Use **Init Containers** to prepare config files. Mount **ConfigMaps** as volumes at specific paths. Set a **Pod Disruption Budget (PDB)** to ensure minimum available replicas during updates.

**CL10 — Medium:** A **Service Account** is an internal K8s identity. **Workload Identity / IRSA** maps that SA to a Cloud IAM Role. Mounting static cloud credentials (JSON keys) is bad because they expire slowly and leak easily. Workload Identity federation uses OIDC tokens for short-lived, temporary credentials issued by the provider.

**CL11 — Medium:** **Object Storage** (S3): Unstructured data, highly durable ($11\text{ nines}$), accessed via API. **Block Storage** (EBS): Low-latency disk for OS/Databases. **File Storage** (EFS): Shared network filesystem for multiple pods. Use Object for backups/assets, Block for boot disks, File for shared configs.

**CL12 — Hard:** Zero Trust Design: Replace perimeter security with "Never Trust, Always Verify." Use **Network Policies** for L3/4 isolation; **mTLS** via service mesh (Istio) for encrypted transit; **IRSA** for pod identity; **Kyverno/OPA** for admission control; **Cosign** for image signing; **Falco** for runtime anomaly detection. Unlike traditional models, trust is based on identity, not IP address or location.

**CL13 — Easy:** A CDN caches content at edge locations closer to users to reduce latency. Examples: AWS CloudFront, Azure Front Door. Use a CDN for static assets (images, JS) or global delivery; use origin servers for dynamic, personalized content that cannot be cached.

**CL14 — Easy:** **Regions** are geographic areas; **Availability Zones (AZs)** are isolated data centers within a region. Deploying across AZs prevents downtime if one DC fails. **Zonal resources** exist in one AZ; **Regional resources** span multiple AZs automatically.

**CL15 — Easy:** Managed DBs handle patching, automated backups, high availability failover, and hardware scaling. Running on a VM requires you to manually manage the OS, database installation, backup scripts, and manual replication setup.

**CL16 — Easy:** **Users** are individuals; **Groups** organize users; **Roles** are assumed identities for tasks; **Policies** define permissions. The **Principle of Least Privilege** means granting only the minimum permissions required for a task, reducing the impact of a compromised account.

**CL17 — Easy:** Serverless is event-driven compute where the provider manages all infrastructure. Lambda/Azure Functions scale automatically. **Cold starts** occur when a function wakes up after inactivity, causing initial latency. Poor fit for: long-running processes, constant heavy loads (cheaper on VMs), or apps requiring specific OS kernels.

**CL18 — Medium:** **Ingress Resource** provides basic L7 routing. **Gateway API** is the modern successor with role-based configuration. **LB Annotations** configure cloud-specific LB features. **Service Mesh Gateways** provide advanced traffic splitting. TLS termination happens at the Load Balancer or Ingress Controller. Use Gateway API for complex multi-tenant environments needing better separation of concerns.

**CL19 — Hard:** Strategy: Use **Savings Plans/RIs** for predictable baseline load; **Spot instances** for batch processing. Implement **S3 Intelligent-Tiering** to move old data to Archive. Right-size via metrics analysis. FinOps involves tagging every resource and using **Chargeback** models to bill costs back to departments. Tools: AWS Cost Explorer, Kubecost.

**CL20 — Hard:** Design: Use **Kubernetes** as the common runtime abstraction. Use **Terraform** for portable IaC definitions. Connect clouds via **VPN or Interconnect**. Federate identity via OIDC. Trade-off: Multi-cloud increases complexity and operational overhead significantly. It is justified only for extreme regulatory requirements or avoiding total vendor lock-in for mission-critical systems.

## OT Infrastructure Architecture

**OT1 — Easy:** The Purdue Model segments industrial networks into levels. **L0 (Process)**: Sensors/Actuators. **L1 (Basic Control)**: PLCs. **L2 (Area Supervisory)**: HMIs/SCADA. **L3 (Site Operations)**: Historians/Local servers. **L4 (Business Logistics)**: ERP/Corporate IT.

**OT2 — Easy:** IT focuses on Data Confidentiality; OT focuses on Availability and Safety. Standard IT patching can cause unplanned reboots of controllers, which could stop a production line or create physical safety hazards in a plant.

**OT3 — Medium:** An IDMZ acts as a buffer between L3 (OT) and L4 (IT). Only proxy traffic should cross; no direct connections. Direct L4 $\rightarrow$ L1 connectivity is dangerous because an IT breach could allow an attacker to directly manipulate hardware without oversight, potentially causing catastrophic failure.

**OT4 — Medium:** 1. **Modbus TCP**: L1/L2, simple data exchange. 2. **OPC UA**: L2/L3, secure, structured platform. 3. **EtherNet/IP**: L1/L2, high-speed control. 4. **PROFINET**: L1/L2, real-time deterministic. 5. **MQTT**: L3 to Cloud, lightweight pub/sub for telemetry.

**OT5 — Medium:** A **Data Diode** is hardware that physically allows data to flow in only one direction. Use it for extreme security where the OT network must be isolated from inbound threats. Limitation: It cannot send acknowledgments back, making standard two-way protocols like TCP difficult. Firewalls are software-based and bidirectional.

**OT6 — Medium:** Flow: Sensor $\rightarrow$ PLC $\rightarrow$ SCADA $\rightarrow$ Historian $\rightarrow$ Edge Gateway (Protocol conversion) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. Security boundaries: Place a firewall between the Historian and the Edge Gateway within the IDMZ.

**OT7 — Hard:** **Zones** group assets with similar security needs; **Conduits** are communication paths between them. Design: Corporate Zone $\xrightarrow{conduit}$ IDMZ $\xrightarrow{conduit}$ Control Zone (SCADA/PLCs). The Safety Instrumented System (SIS) should be in its own highly restricted zone with minimal conduits.

**OT8 — Hard:** Strategy: Segment by production line using VLANs. Place firewalls between L2 and L3. Implement an Industrial Switch architecture with ACLs. Remote access via Jump Host + MFA in the IDMZ. Transition: Deploy "Listen Mode" first to map traffic, then implement enforcement during planned maintenance windows to avoid unplanned downtime.

**OT9 — Hard:** **BPCS** handles normal operations; **SIS** is a separate system that triggers emergency shutdowns if limits are exceeded. IEC 61511 defines functional safety. Isolation prevents common-cause failure. If ransomware reaches the SIS, it could disable critical safety trips, leading to physical explosions or environmental disasters.

**OT10 — Medium:** **PLC**: Logic for specific machines. **DCS**: Distributed control for entire plant processes. **SCADA**: Supervisory oversight across wide areas. They coexist often: SCADA monitors multiple PLCs or acts as the top layer of a DCS.

**OT11 — Medium:** Architecture: VPN $\rightarrow$ MFA $\rightarrow$ Jump Host (Bastion) $\rightarrow$ Target HMI. Use session recording and time-limited access. RDP directly from corporate IT is unacceptable because it bypasses security layers and exposes controllers to lateral movement from IT breaches.

**OT12 — Hard:** Detection: Passive IDS (e.g., Nozomi/Claroty) for anomaly detection. Response: Isolate compromised segment via firewall rules $\rightarrow$ Failover to manual controls $\rightarrow$ Forensic analysis. The operator's role is paramount: they must ensure the process is in a "safe state" before any network isolation occurs.

**OT13 — Easy:** An **HMI** provides a visual interface for operators to monitor and control the process. An **Engineering Workstation** is used by engineers to program and configure the PLC logic; HMIs are for operation, workstations are for configuration.

**OT14 — Easy:** A **Historian** is a time-series database for process data. Plant Historians (L3) store high-resolution local data; Enterprise Historians (L4) store aggregated long-term data for business analytics. They are critical for auditing and root-cause analysis.

**OT15 — Easy:** **Ladder Logic** is a graphical language resembling electrical relay circuits, executed by PLCs. It remains dominant because it is intuitive for electricians and technicians who understand physical wiring diagrams.

**OT16 — Easy:** An **RTU** is designed for wide-area telemetry over low-bandwidth or unstable links (often solar powered). Unlike PLCs, which are localized to a plant floor, RTUs are deployed in remote sites like pipelines or water substations.

**OT17 — Easy:** Analog signals (e.g., 4-20mA) provide continuous values; digital signals are binary (On/Off). 4-20mA is preferred over 0-20mA because "Live Zero" allows detection of wire breaks: $0\text{mA} = \text{fault}$, while $4\text{mA} = \text{zero value}$.

**OT18 — Medium:** Asset inventory identifies every device on the network. Passive monitoring (sniffing traffic) is used for discovery. Active scanning is dangerous because legacy OT devices may crash when receiving unexpected packets from a vulnerability scanner.

**OT19 — Hard:** MITRE ATT&CK ICS focuses on industrial impact. Tactics include: **Initial Access** (VPN compromise), **Execution** (PLC logic change), **Persistence** (Firmware implant), **Impair Process Control** (Modify setpoints), and **Inhibit Response Function** (Disable alarms). It differs by focusing on physical consequences rather than just data theft.

**OT20 — Hard:** Design: Use SPAN ports/TAPs for passive log collection to avoid latency. Integrate with SIEM using OT-specific rules. Staffing requires IT analysts for alert triage and OT engineers for validation. An unauthorized firmware alert triggers an immediate investigation against change logs; if unapproved, isolate the PLC but only after ensuring process safety.
