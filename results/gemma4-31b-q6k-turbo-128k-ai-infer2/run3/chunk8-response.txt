## Cloud Infrastructure Architecture

**CL1 — Easy:** IaaS provides raw compute, storage, and networking; you manage the OS and apps (Example: AWS EC2). PaaS provides a platform for deployment without managing servers (Example: Google App Engine). SaaS delivers software over the web as a service (Example: Microsoft 365).

**CL2 — Easy:** The Shared Responsibility Model defines who manages which layer. For **IaaS VMs**, the provider handles hardware/virtualization; you handle the Guest OS, patching, and data. For **Managed Kubernetes (EKS/AKS)**, the provider manages the control plane; you manage worker node configuration and pods. For **SaaS (M365)**, the provider manages almost everything except your identity access and the data itself.

**CL3 — Medium:** A **VPC** is an isolated virtual network. A **Subnet** is a range of IP addresses within that VPC. A **Security Group** is a stateful firewall at the instance level (allows return traffic automatically). A **NACL** is a stateless firewall at the subnet level (must explicitly allow both inbound and outbound). Layering: Traffic hits NACL $\rightarrow$ Subnet $\rightarrow$ Security Group $\rightarrow$ Instance.

**CL4 — Medium:** A **Landing Zone** is a pre-configured multi-account environment. **Organizational Units (OUs)** group accounts by function (e.g., Prod, Dev). **Guardrails** (like AWS SCPs) enforce top-level policies. **Shared Networking** uses Hub-and-Spoke or Transit Gateway to centralize egress/ingress. Centralized logging aggregates logs into one secure account for auditing. Single-account approaches are problematic due to blast radius risk, quota limits, and billing complexity.

**CL5 — Medium:** IaC allows defining infrastructure via code. **Terraform/OpenTofu** is cloud-agnostic HCL; best for multi-cloud. **Pulumi** uses general languages (TS/Python); best for developers who want loops/logic in code. **CloudFormation/Bicep** are provider-specific; best for deep integration with one vendor. **Crossplane** turns K8s into an IaC control plane; best for "K8s-everything" strategies.

**CL6 — Medium:** **HPA** scales pods based on metrics (CPU/RAM). **VPA** adjusts the size of existing pods. **Cluster Autoscaler** adds/removes nodes from the cluster. **KEDA** provides event-driven scaling (e.g., RabbitMQ queue length). Use KEDA over HPA when you need to scale based on external events rather than resource consumption.

**CL7 — Hard:** 
*   **Strategy:** Active-Active across two regions using Global Load Balancing (Route53/Traffic Manager) for DNS failover. 
*   **Replication:** Async database replication (to avoid latency penalties), accepting a small RPO > 0. 
*   **DR Types:** **Pilot Light** (DB running, apps off), **Warm Standby** (Scaled down version always running), **Multi-site Active-Active** (Full capacity in both, zero RTO). 
*   **State:** Externalized state via distributed caches or global databases (CosmosDB/DynamoDB Global Tables). Cost increases linearly with redundancy level.

**CL8 — Hard:** GitOps uses Git as the single source of truth; controllers pull changes into the cluster. **ArgoCD** is UI-centric and application-focused; **FluxCD** is more lightweight and focused on automation. Secrets are handled via **SealedSecrets** (encrypted in Git) or **External Secrets Operator** (fetching from Vault). Manual drift is automatically corrected by the controller overwriting manual changes back to the Git state.

**CL9 — Hard:** Use a **StatefulSet** for stable network identities. Map pods to **PVs/PVCs** using a local storage class for low latency. Implement a **Headless Service** for direct pod addressing. Use **Init Containers** to prepare filesystem paths and mount **ConfigMaps** as volumes at specific paths. Define **Pod Disruption Budgets (PDB)** to ensure minimum availability during node maintenance.

**CL10 — Medium:** A **Service Account** is an identity for K8s processes. **Workload Identity/IRSA** maps that SA to a Cloud IAM Role via OIDC. Mounting static credentials (JSON keys) is bad because they leak, don't rotate easily, and provide overly broad access. Workload identity federation allows the cloud provider to trust the K8s token directly, eliminating long-lived secrets.

**CL11 — Medium:** **Object Storage** (S3): Unstructured data, highly durable, accessed via API; use for backups/media. **Block Storage** (EBS): Low-latency disk attached to one VM; use for OS/Databases. **File Storage** (EFS): Shared across multiple VMs/Pods; use for shared config or legacy app files. S3 has highest durability ($11\text{ nines}$); EBS depends on AZ replication.

**CL12 — Hard:** 
*   **Architecture:** Network Policies (L3/4 isolation), Service Mesh (Istio mTLS for L7 encryption). 
*   **Identity:** Pod identities instead of shared tokens. 
*   **Governance:** Kyverno/OPA for admission control; Cosign for image signing verification. 
*   **Runtime:** Falco for anomaly detection. 
*   **Difference:** Traditional models rely on "hard shell, soft center" (perimeter); Zero Trust assumes the network is compromised and verifies every single request regardless of location.

**CL13 — Easy:** A CDN caches content at edge locations closer to users to reduce latency and origin load. Examples: AWS CloudFront, Azure Front Door. Use a CDN when serving static assets globally or during high-traffic spikes to prevent your origin server from crashing.

**CL14 — Easy:** A **Region** is a geographic area; an **Availability Zone (AZ)** is one or more isolated data centers within that region. Deploying across multiple AZs protects against a single DC failure. Zonal resources exist in one AZ; Regional resources are replicated across several.

**CL15 — Easy:** Managed DBs handle patching, automated backups, hardware scaling, and failover automatically. If running on a VM, you must manually manage OS updates, backup scripts, replication lag, and manual failover procedures.

**CL16 — Easy:** Users are individuals; Groups are collections of users; Roles are identities assumed by entities; Policies define permissions. The **Principle of Least Privilege** means granting only the minimum permissions required for a task. Apply this by using granular IAM policies instead of broad administrator roles.

**CL17 — Easy:** Serverless is event-driven compute where the provider manages all infrastructure. Cold starts occur when a function spins up after inactivity, causing initial latency. It's a poor fit for long-running processes (timeouts), constant heavy loads (more expensive than VMs), or apps requiring low-latency consistency.

**CL18 — Medium:** **Ingress** is basic L7 routing. **Gateway API** is the modern successor providing role-based management (Infrastructure vs Application). **LB Annotations** provide cloud-specific tweaks. **Mesh Gateways** offer advanced traffic splitting/canarying. TLS termination usually happens at the Load Balancer or Ingress Controller via certificates managed by Cert-Manager. Use Gateway API for complex, multi-tenant routing needs.

**CL19 — Hard:** 
*   **Compute:** Mix Spot instances for non-critical workloads and Savings Plans for baseline load. Right-size based on actual utilization metrics. 
*   **Storage:** Move old data to S3 Glacier Instant Retrieval or Archive tiers. 
*   **Process:** Implement FinOps with "Tagging" strategies for chargeback/showback. 
*   **Tools:** AWS Cost Explorer, Kubecost for K8s granularity. Establish monthly review cycles between finance and engineering teams.

**CL20 — Hard:** 
*   **Abstraction:** Kubernetes as the common runtime; Terraform for portable IaC. 
*   **Connectivity:** Site-to-Site VPN or Dedicated Interconnects. 
*   **Identity:** OIDC Federation across providers. 
*   **Trade-off:** Theoretical benefit is resilience and no lock-in; real-world cost is massive operational overhead and "lowest common denominator" feature usage (avoiding provider-specific optimizations). Justified only for extreme regulatory requirements or critical availability.

## OT Infrastructure Architecture

**OT1 — Easy:** The Purdue Model segments industrial networks into levels: **Level 0** (Physical process - sensors/actuators), **Level 1** (Basic Control - PLCs), **Level 2** (Supervisory Control - HMIs/SCADA), **Level 3** (Site Operations - Historians/Workstations), **Level 4** (Enterprise IT).

**OT2 — Easy:** IT prioritizes Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability. OT prioritizes Availability $\rightarrow$ Integrity $\rightarrow$ Confidentiality. Standard patching can cause unplanned reboots, which in an OT environment could stop a production line or create physical safety hazards.

**OT3 — Medium:** An IDMZ acts as a buffer between L3 and L4. Only proxied traffic should cross (e.g., data from a historian mirror to the corporate network). Direct connectivity from L4 to L1 is dangerous because it allows an IT breach to directly manipulate hardware controllers without any oversight.

**OT4 — Medium:** 
1. **Modbus TCP**: L1/L2; simple request/response. 
2. **OPC UA**: L2/L3; secure, structured data exchange. 
3. **EtherNet/IP**: L1/L2; high-speed industrial control. 
4. **PROFINET**: L1; real-time deterministic communication. 
5. **MQTT**: Edge to Cloud / L3+; lightweight pub/sub for telemetry.

**OT5 — Medium:** A firewall filters packets based on rules; a **data diode** is a hardware device that physically ensures one-way flow (usually via light/optics). Use a diode when you need absolute certainty that no commands can enter a critical zone while still exporting logs. Limitation: No bidirectional handshake/acknowledgment.

**OT6 — Medium:** Flow: Sensor $\rightarrow$ PLC $\rightarrow$ SCADA Server $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (Protocol conversion) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. Security boundaries are placed at the IDMZ and the Edge Gateway using firewalls with strict allow-lists.

**OT7 — Hard:** A **Zone** is a group of assets with similar security requirements; a **Conduit** is the communication path between them. Design: SIS Zone (Isolated), Control Zone (PLCs), Supervisory Zone (SCADA), Corporate Zone. Conduits must be strictly controlled by firewalls, ensuring only necessary protocols cross zones.

**OT8 — Hard:** Implement VLANs per production line to isolate traffic. Place industrial firewalls between L2 and L3. Use a "Jump Host" in the IDMZ for vendor remote access. Transition strategy: Build parallel segmented networks during operation, then migrate PLCs one by one during scheduled maintenance windows to avoid unplanned downtime.

**OT9 — Hard:** BPCS handles normal operations; **SIS** is an independent safety layer designed to prevent catastrophes. IEC 61511 governs SIS design. Isolation prevents common mode failure. If ransomware reaches the SIS, it could disable emergency shutdown capabilities, potentially leading to explosions or environmental disasters.

**OT10 — Medium:** **PLC**: Discrete logic controller for specific machines. **DCS**: Integrated system managing entire plant processes. **SCADA**: High-level supervisory control over wide geographic areas. They often coexist: PLCs report to SCADA via a DCS backbone.

**OT11 — Medium:** Architecture: VPN $\rightarrow$ MFA $\rightarrow$ Jump Host $\rightarrow$ Target HMI. Include session recording and time-limited tokens. Direct RDP from corporate IT to HMIs is unacceptable because it bypasses security boundaries and allows lateral movement if the corporate network is breached.

**OT12 — Hard:** Detection: Passive IDS (e.g., Nozomi/Claroty) to find anomalies. Response: Isolate compromised L3 segments using firewalls while maintaining manual override in the control room. The plant operator's role is critical: they must determine if "cyber" behavior correlates with "physical" process changes and ensure safe state before isolation.

**OT13 — Easy:** An **HMI** provides a visual interface for operators to monitor and control the process. It differs from an engineering workstation; an HMI is for operation (read/setpoints), whereas an engineering station is for configuration (changing PLC code).

**OT14 — Easy:** A historian is a time-series database of process data used for auditing and optimization. **Plant Historian (L3)** stores high-resolution, real-time site data; **Enterprise Historian (L4)** aggregates summarized data across multiple sites for business reporting.

**OT15 — Easy:** Ladder logic is a graphical language mimicking electrical relay circuits, executed by PLCs. It remains dominant because it is deterministic, easy for electricians to troubleshoot, and highly reliable for simple boolean logic.

**OT16 — Easy:** An **RTU** is designed for wide-area telemetry and often has integrated radio/cellular modems. A **PLC** is optimized for local, high-speed machine control. Use RTUs for pipelines, water grids, or remote substations.

**OT17 — Easy:** Analog signals are continuous (voltage/current); digital are binary (on/off). 4-20mA is preferred over 0-20mA because if the signal drops to 0mA, you know there is a "broken wire" fault; 4mA represents the lowest valid measurement ("Live Zero").

**OT18 — Medium:** Asset inventory identifies every device on the network. Passive monitoring (sniffing traffic) is safe. Active scanning (ping/port scans) can crash legacy PLCs due to fragile TCP stacks that cannot handle unexpected packets.

**OT19 — Hard:** Tactics: Initial Access $\rightarrow$ Persistence $\rightarrow$ Inhibition of Control $\rightarrow$ Impair Process Control $\rightarrow$ Impact. Example technique: "Modify Parameter" in an HMI. Differs from IT by focusing on physical impact. Used to identify gaps where visibility into L1/L2 communication is missing.

**OT20 — Hard:** Collect logs via passive TAPs to avoid latency. Integrate with SIEM using OT-specific rules (e.g., alerting on S7 "Write" commands during non-maintenance windows). Staffing requires both SOC analysts and process engineers for triage. A firmware alert must be verified by the plant operator before isolation to prevent accidental production stops.
