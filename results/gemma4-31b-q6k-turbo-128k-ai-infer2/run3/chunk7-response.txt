## Application Architecture

**AA1** — A **monolith** is a single unified unit where all business logic is in one codebase/process. **Microservices** decompose the application into small, independent services communicating over a network. Three problems introduced by microservices: 1) **Distributed Complexity** (network latency and partial failures), 2) **Data Consistency** (difficulty maintaining transactions across services), 3) **Operational Overhead** (monitoring, deployment, and service discovery for dozens of units instead of one).

**AA2** — **Synchronous** communication requires the requester to wait for a response before proceeding (e.g., REST/HTTP or gRPC). **Asynchronous** communication involves sending a message without waiting for an immediate response (e.g., RabbitMQ or Apache Kafka).

**AA3** — A **reverse proxy** primarily handles routing, load balancing, and SSL termination. An **API Gateway** provides higher-level "business" logic such as authentication, rate limiting, request transformation, and API composition. While an API Gateway can perform reverse proxy tasks, it doesn't always replace them; often, a reverse proxy (like Nginx) sits in front of a gateway to handle raw traffic efficiently.

**AA4** — The **Saga pattern** manages distributed transactions via a sequence of local transactions with compensating actions if a step fails. **Choreography** is decentralized; services exchange events to trigger the next step. **Orchestration** uses a central coordinator to tell services when to act. Use choreography for simple workflows to avoid tight coupling; use orchestration for complex business processes where visibility and centralized control are required.

**AA5** — **CQRS** separates read operations (Queries) from write operations (Commands), allowing each to scale independently. It is paired with **Event Sourcing**, which stores state as a sequence of immutable events rather than current state. This combination solves the problem of auditability and high-performance reads by creating specialized "read projections" optimized for specific queries, unlike CRUD which forces a single data model for all access patterns.

**AA6** — A **Circuit Breaker** prevents cascading failures by stopping requests to a failing service. States: **Closed** (traffic flows), **Open** (requests fail fast immediately), and **Half-Open** (limited probes sent to check recovery). Unlike retry-with-backoff (which keeps trying), a circuit breaker stops all attempts entirely to allow the downstream service time to recover. You use both together by retrying transient errors but tripping the circuit if the error rate exceeds a threshold.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, highest noisy-neighbor risk, lowest security isolation. High operational simplicity.
2. **Separate Schema:** Medium cost, better security (schema permissions), reduced noise risk. Moderate complexity in migrations.
3. **Separate DB:** Highest cost, maximum security, zero noisy-neighbor risk. High operational complexity (managing $N$ databases).

**AA8** — **Strong consistency** ensures all clients see the same data simultaneously; **eventual consistency** guarantees that given enough time without updates, all replicas will converge. To prevent overselling inventory at scale: Use **strong consistency**. Architecturally, I would use a distributed database with ACID properties (e.g., PostgreSQL or Google Spanner) using **pessimistic locking** on the stock count for specific SKUs during checkout to ensure an atomic decrement.

**AA9** — A **sidecar proxy** is a helper process running alongside the application container. In Istio, **Envoy** acts as the **data plane** (handling actual network traffic), while Istio's control plane manages configuration and policy. mTLS between sidecars solves identity verification and encryption *transparently* across the mesh, removing the need for developers to implement TLS logic within every single polyglot service.

**AA10** — The **Strangler Fig pattern** involves incrementally replacing legacy functionality by wrapping it. Strategy: 1) Place a routing layer (proxy/gateway) in front of the .NET Framework monolith. 2) Implement new features as .NET 8 microservices. 3) Gradually migrate existing endpoints from the monolith to the new services one-by-one. Route traffic via the proxy to the new service; once fully migrated, decommission the monolith.

**AA11** — The **12-Factor App** methodology optimizes apps for cloud deployment. Factors include: 1) Single codebase, 2) Explicit dependencies, 3) Config in environment variables, 4) Backing services treated as attached resources, 5) Build $\rightarrow$ Release $\rightarrow$ Run separation, 6) Stateless processes. These ensure portability, scalability, and consistency across environments.

**AA12** — 
- **Event-driven (Kafka):** Loose coupling, high scalability, complex debugging, guaranteed ordering per partition, failure handled via offsets/retries. Choose for async pipelines or event streams.
- **Request-driven (REST/gRPC):** Tighter coupling, easier debugging, request-response latency, immediate failure feedback. Choose for synchronous APIs where an immediate answer is required.

**AA13** — A **load balancer** distributes network traffic across multiple servers. **Layer 4** balances based on IP/TCP ports (fast, no packet inspection). **Layer 7** balances based on application data (HTTP headers, URLs). Use Case: Path-based routing (e.g., sending `/api` to one cluster and `/images` to another).

**AA14** — A **message queue** (RabbitMQ) delivers messages to consumers who then delete them; it's a "point-to-point" model. A **log-based broker** (Kafka) persists messages in an append-only log that can be replayed by multiple independent consumers. Pick RabbitMQ for task queues; Kafka for real-time stream processing and event sourcing.

**AA15** — A **container** shares the host OS kernel and isolates processes; a **VM** includes a full guest OS and runs on a hypervisor. Containers are popular for microservices because they start faster, use fewer resources, and ensure environment parity from dev to production.

**AA16** — **Stateless services** do not store client data locally between requests (e.g., a REST API using JWTs); they scale horizontally easily because any instance can handle any request. **Stateful services** remember state (e.g., a Database or Redis cache), requiring sticky sessions or shared storage to scale.

**AA17** — An **ORM** maps database tables to language objects. Examples: Hibernate (Java), Entity Framework (.NET). Trade-offs: ORMs increase developer productivity and provide type safety but can introduce performance overhead ("N+1 query problem") compared to raw SQL which offers maximum optimization.

**AA18** — The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, others continue to function. Implementation: Use separate thread pools for different downstream service calls in your code, or deploy critical paths onto dedicated server clusters to prevent a surge in "low priority" traffic from starving "high priority" resources.

**AA19** — **OT** requires a central server to transform operations to maintain consistency; it is complex to implement for offline sync. **CRDTs** are mathematically designed to merge concurrently without conflicts regardless of order. For offline editing, I would choose **CRDTs** because they allow local updates that converge automatically when the client reconnects without needing a central coordinator to resolve every conflict.

**AA20** — Challenges include maintaining trace IDs across different languages/frameworks. **Context propagation** uses headers (W3C Trace Context) to pass IDs. **Head-based sampling** decides at the start of a request whether to trace; **tail-based** decides after completion based on results (e.g., only save traces with errors). To ensure continuity through Kafka, inject the trace context into the **Kafka record headers**.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare Metal)** runs directly on hardware (e.g., VMware ESXi, Proxmox/KVM). **Type 2 (Hosted)** runs as an app on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network)** provides block-level storage via protocols like iSCSI or Fibre Channel; used for high-performance DBs. **NAS (Network Attached Storage)** provides file-level storage via NFS or SMB; used for shared files and backups.

**OP3** — **3-Tier** consists of Core (routing), Distribution (policy/VLANs), and Access (device connection). **Leaf-Spine** is preferred in modern DCs because it provides predictable latency and massive "East-West" bandwidth (server-to-server), eliminating the bottlenecks found in traditional spanning-tree hierarchical designs.

**OP4** — Use $\ge 3$ nodes to maintain **quorum** (majority vote) to prevent split-brain. Implement **fencing (STONITH)** to forcibly power off a failed node. For shared storage: **Ceph** (distributed across nodes) or **iSCSI** (external array). If a node fails, the cluster detects loss of heartbeat, fences the node, and restarts VMs on healthy nodes using the shared storage.

**OP5** — **VLAN trunking** allows multiple VLANs to traverse one physical link. **802.1Q** adds a tag to each frame identifying its VLAN. On Linux, this is configured by creating tagged sub-interfaces (e.g., `ip addr add ... dev eth0.10` where `.10` is the VLAN ID).

**OP6** — RAID 1 (Mirror), 5 (Parity - 1 drive fail), 6 (Double Parity - 2 drives fail), 10 (Striped Mirror), Z2 (ZFS double parity). For a DB server with 6 drives: I would choose **RAID 10**. It provides the best balance of high IOPS (performance) and fault tolerance without the write penalty of parity calculations found in RAID 5/6.

**OP7** — Use an internal AD DNS for local resolution and a separate public zone for external services (**Split-Horizon**). Recursive resolvers handle client queries; conditional forwarders send specific domain requests to other servers. When a laptop moves from office $\rightarrow$ VPN, it should be assigned a DNS server that can resolve both internal zones via the tunnel and public zones via root hints. External zones are signed with **DNSSEC** to prevent cache poisoning.

**OP8** — The chain goes Root CA $\rightarrow$ Intermediate/Issuing CA $\rightarrow$ End Entity. Keep the **Root CA offline** to protect the master key. CRLs provide lists of revoked certs; OCSP provides real-time status checks. A compromised Sub-CA requires revoking only that intermediate's certificate; a compromised Root CA is catastrophic, requiring a complete re-issuance of all certificates across the organization.

**OP9** — MPLS (High cost, guaranteed QoS), IPsec VPN (Low cost, internet jitter), SD-WAN (Dynamic path selection over multiple links), WireGuard Mesh (Fast, modern encryption). For latency-sensitive VoIP at 5 sites: I recommend **SD-WAN**. It allows prioritizing VoIP traffic and failing over seamlessly between MPLS and Internet circuits based on real-time link quality.

**OP10** — iDRAC/iLO/IPMI are **out-of-band management** interfaces allowing remote power control and console access regardless of OS state. If exposed to the internet, an attacker could gain full hardware control, modify BIOS settings, or wipe disks without needing OS credentials.

**OP11** — **LVM** manages logical volumes with basic snapshots. **LVM-Thin** uses thin provisioning to allocate space only when written. **ZFS** integrates volume management and filesystem with atomic, copy-on-write snapshots. Use ZFS for data integrity (checksumming) and near-instantaneous snapshotting of large datasets.

**OP12** — Design a cluster where monitors are spread across sites. Use Ceph **CRUSH rules** to ensure replicas exist in different physical locations. Latency must be extremely low ($<10$ms typically). A 2-site setup is dangerous because if one site fails, the other cannot reach a majority ($\ge 3$ nodes needed), leading to "split-brain" unless a third tiebreaker node exists at a separate location.

**OP13** — DHCP works via **DORA**: Discover $\rightarrow$ Offer $\rightarrow$ Request $\rightarrow$ Acknowledge. When a Windows client's lease expires and no server is available, it assigns itself an **APIPA** address (169.254.x.x).

**OP14** — An unmanaged switch is plug-and-play; a **managed switch** allows configuration of VLANs, Spanning Tree Protocol (STP) to prevent loops, SNMP monitoring, and port mirroring for traffic analysis. Managed switches are essential for security segmentation and network visibility.

**OP15** — **NTP** synchronizes clocks across the network. Accurate time is critical for Kerberos authentication (which fails if clock skew $> 5$ mins), log correlation during troubleshooting, and cluster heartbeats. Drift can cause database corruption or false failovers in HA clusters.

**OP16** — Physical: Hardware only. VM: Virtualized hardware/OS. Container: Isolated process sharing kernel. Run on **bare metal** when you need maximum I/O performance, direct GPU access, or are running the hypervisor itself.

**OP17** — **UPS** provides immediate battery power to bridge the gap until a generator starts. A **generator** provides long-term fuel-based power. The **ATS (Automatic Transfer Switch)** detects mains failure and automatically switches the load from utility power to the generator once it reaches stable voltage.

**OP18** — Active-Passive has one standby node; Active-Active uses all nodes simultaneously. For PostgreSQL with Pacemaker/Corosync: Use a **Virtual IP (VIP)** that floats between servers. Implement **STONITH (fencing)** via IPMI to ensure a failing node is completely powered off before the passive node takes over, preventing "split-brain" data corruption.

**OP19** — Strategy: **3-2-1 rule** (3 copies, 2 media, 1 offsite). RPO defines acceptable data loss; RTO defines downtime limit. Use Full backups weekly $\rightarrow$ Incremental daily. Use **immutable backups** (WORM) for ransomware protection. Backup is the copy of data; Disaster Recovery is the comprehensive plan to restore operations at an alternate site.

**OP20** — **802.1X** involves the Supplicant (client), Authenticator (switch), and Auth Server (RADIUS). EAP-TLS uses certificates for high security; PEAP uses passwords. RADIUS assigns VLANs dynamically based on user identity. **MAB (MAC Authentication Bypass)** allows devices like printers (which can't run supplicants) by whitelisting their MAC addresses in the RADIUS server.
