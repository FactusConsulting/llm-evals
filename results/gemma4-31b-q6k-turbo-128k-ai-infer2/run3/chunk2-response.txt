## Kubernetes

**K1 — Easy:** A **Deployment** manages stateless pods; it ensures a specified number of replicas are running and handles rolling updates without identity preservation. A **StatefulSet** manages stateful pods; it provides stable, unique network identifiers and persistent storage that persists across pod rescheduling (pod-0, pod-1, etc.).

**K2 — Easy:** A ClusterIP creates a virtual IP within the cluster. Traffic sent to this IP is intercepted by `kube-proxy` (via iptables or IPVS rules), which load-balances the traffic across the healthy Pods associated with the Service's selector.

**K3 — Medium:** 
- **StorageClass**: A blueprint/template defining *how* storage should be provisioned (e.g., SSD vs HDD, cloud provider type).
- **PersistentVolume (PV)**: The actual piece of storage in the cluster (the physical resource).
- **PersistentVolumeClaim (PVC)**: A user's request for storage (size, access mode) from a StorageClass.
**Relation:** PVC requests resources $\rightarrow$ StorageClass provisions them $\rightarrow$ PV is created and bound to the PVC.

**K4 — Medium:**
1. `kubectl logs <pod>`: Check application crash logs for stack traces.
2. `kubectl describe pod <pod>`: Look at "Events" for OOMKill, failed probes, or image pull errors.
3. Check Liveness/Readiness probe configurations: Ensure they aren't too aggressive or pointing to wrong ports.
4. Resource limits check: Verify if the pod is hitting memory limits causing an OOMKill.

**K5 — Medium:** CoreDNS provides service discovery; it translates Kubernetes service names (e.g., `my-svc.default.svc.cluster.local`) into IP addresses. If CoreDNS pods are down, DNS resolution fails entirely inside the cluster, meaning pods cannot find other services by name, effectively breaking most inter-service communication.

**K6 — Hard:** 
The scheduler uses two main phases:
1. **Filtering (Predicates):** Removes nodes that don't meet requirements (e.g., insufficient CPU/RAM, Taints without Tolerations, NodeSelector mismatch).
2. **Scoring (Priorities):** Ranks remaining nodes based on a score.
**Factors considered:**
- **Resource Fit:** Prefers nodes where requested resources leave balanced headroom.
- **Image Locality:** Prefers nodes that already have the container image cached.
- **Inter-pod Affinity/Anti-affinity:** Places pods together or apart based on rules.

**K7 — Hard:** 
**Scheduling:** Yes, it will be scheduled. The scheduler checks **requests**, not limits. Since $3.5\text{GB} + 256\text{Mi}$ is less than $4\text{GB}$, there is enough room for the request.
**Runtime:** If the pod uses $600\text{Mi}$, it exceeds its `limits.memory` ($512\text{Mi}$). The Linux kernel OOM killer will terminate the process, and Kubernetes will report an `OOMKilled` status.

**K8 — Hard:** 
External LB $\rightarrow$ NGINX Ingress Controller Pod $\rightarrow$ Service Endpoints list $\rightarrow$ kube-proxy/iptables rule $\rightarrow$ Application Pod.
The Ingress controller reads the Ingress resource to map host/path to a Service. It bypasses the Service's virtual IP (ClusterIP) and routes traffic directly to the **Endpoints** (the actual Pod IPs) using load balancing logic, which are updated dynamically by the control plane via the API server.

**K9 — Medium:** A NetworkPolicy defines how groups of pods are allowed to communicate with each other. By default, if no policy exists, all ingress/egress traffic is allowed. Once a NetworkPolicy selects a pod, that pod enters "isolation mode," meaning only traffic explicitly permitted by the policy is allowed; everything else is denied.

**K10 — Medium:** 
- **RollingUpdate:** Gradually replaces old pods with new ones, ensuring zero downtime.
- **Recreate:** Kills all existing pods before creating new ones.
**Choose Recreate when:** The application does not support two different versions running simultaneously (e.g., database schema migrations that aren't backward compatible).

**K11 — Easy:** A namespace provides logical isolation for resources within a cluster. Default namespaces: `default` (user apps), `kube-system` (cluster internals), and `kube-public` (readable by everyone).

**K12 — Easy:** Used for detailed debugging. It shows:
1. **Events**: Recent lifecycle events (pulling image, scheduling, crashing).
2. **Container State**: Detailed exit codes and restart counts.
3. **Resource Limits/Requests**: Exact CPU/RAM settings applied.

**K13 — Easy:** A ConfigMap stores non-confidential configuration data in key-value pairs. Consumption methods:
1. **Environment Variables**: Injected into the container process at startup.
2. **Volume Mounts**: Mounted as files in a directory inside the pod.

**K14 — Easy:** 
- **ClusterIP**: Internal IP; only reachable from within the cluster.
- **NodePort**: Exposes the service on a static port on every Node's IP.
- **LoadBalancer**: Provisions an external cloud load balancer that routes to NodePorts.

**K15 — Easy:** A DaemonSet ensures that all (or some) Nodes run a copy of a Pod. Use it instead of a Deployment for infrastructure agents like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium:** 
- **Taints/Tolerations**: Taints are applied to *Nodes* to repel pods. Tolerations are applied to *Pods* to allow them onto tainted nodes. (Use case: Dedicating GPU nodes to specific ML workloads).
- **Node Affinity**: Applied to *Pods* to attract them to certain nodes based on labels. (Use case: Ensuring high-availability by spreading pods across different availability zones).

**K17 — Medium:** An Operator is a custom controller using Custom Resource Definitions (CRDs) to manage complex applications. While standard controllers handle generic resources (like Deployments), Operators encode "human operational knowledge" into code to automate tasks like backups, scaling, and failover for stateful apps (e.g., Postgres Operator).

**K18 — Hard:** etcd uses the **Raft consensus algorithm**, ensuring strong consistency. If quorum is lost (majority of nodes down), the cluster becomes read-only or unavailable because writes cannot be committed. To recover from losing 2 out of 3 nodes, you must restore from a recent snapshot backup to a new cluster.

**K19 — Hard:** RBAC controls access via Roles (permissions) and Bindings (assignment). `Role` is namespace-scoped; `ClusterRole` is global. `RoleBinding` links a user/group to a Role in a namespace; `ClusterRoleBinding` does so globally.

```yaml
# Read-only Pods/Logs Manifest
apiVersion: v1
kind: ServiceAccount
metadata: { name: pod-reader }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader-role }
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: pod-reader-binding }
subjects: [{ kind: ServiceAccount, name: pod-reader }]
roleRef: { kind: Role, name: pod-reader-role, apiGroup: rbac.authorization.k8s.io }
```

**K20 — Hard:** By default, pods have an `ndots: 5` setting in `/etc/resolv.conf`. When resolving `google.com`, the resolver tries appending search paths (e.g., `google.com.default.svc.cluster.local`) before trying the absolute domain. This causes multiple failed queries per request. Fix via `dnsConfig`:
```yaml
spec:
  dnsConfig:
    options:
      - name: ndots
      - value: "1"
```

## Development

**D1 — Easy:** `merge` creates a new merge commit and preserves history as it happened; `rebase` rewrites history by moving commits to a new base for a linear timeline. Avoid rebasing on public/shared branches because it forces other developers to perform complex manual merges when they pull changes.

**D2 — Easy:** **TCP** is connection-oriented, reliable, and ensures ordered delivery (HTTP, SSH). **UDP** is connectionless, faster, but does not guarantee delivery or order (DNS, DHCP).

**D3 — Medium:** A race condition occurs when two or more threads access shared data concurrently, and the final result depends on the timing of their execution. *Example:* Two threads incrementing a global counter `x = x + 1`. If both read $x=5$ simultaneously, both write back $6$, losing one increment.

**D4 — Medium:** Symmetric encryption uses one key for both encryption and decryption (fast, e.g., AES). Asymmetric uses a Public Key to encrypt and a Private Key to decrypt (slower, e.g., RSA). In TLS, asymmetric encryption is used during the handshake to securely exchange a symmetric session key, which is then used for the actual data transfer.

**D5 — Medium:** An image layer is a read-only snapshot of filesystem changes. Docker caches layers; if a line in the Dockerfile changes, all subsequent layers must be rebuilt. Best practice: Put frequently changing instructions (like `COPY . .`) at the end and static ones (installing OS packages) at the top.

**D6 — Medium:**
1. **Logs**: Check application logs for timeouts or "Service Unavailable" errors from upstream dependencies.
2. **Health Checks**: Verify if pods are restarting or failing readiness probes.
3. **Resource Metrics**: Check CPU/RAM spikes causing process throttling or OOMKills.
4. **Upstream Dependencies**: Check if an external API or database is timing out or hitting connection limits.

**D7 — Hard:** CAP Theorem states a distributed system can only provide two of three: Consistency, Availability, Partition Tolerance. 
- **CP (Consistency/Partition)**: MongoDB (default config)—stops accepting writes if it cannot maintain consistency during a partition.
- **AP (Availability/Partition)**: Cassandra—allows reads/writes during partitions, resolving conflicts later via eventual consistency.

**D8 — Medium:** Horizontal scaling adds more instances (more nodes); vertical scaling increases resources (CPU/RAM) on existing nodes. Patterns enabling horizontal scaling include statelessness (no session state stored locally), load balancing, and shared databases/caches.

**D9 — Easy:** An environment variable is a dynamic value available to a process. To persist across sessions in Linux, add `export VAR_NAME="value"` to the user's shell configuration file (e.g., `~/.bashrc` or `~/.zshrc`).

**D10 — Easy:** JSON is a strict data format based on key-value pairs; YAML is a human-readable superset of JSON using indentation. 
- **JSON Advantage**: Faster parsing by machines, ubiquitous for APIs.
- **YAML Advantage**: Easier for humans to write/read, supports comments.

**D11 — Easy:** A REST API is an architectural style for network applications using HTTP.
- **GET**: Retrieve resource.
- **POST**: Create new resource.
- **PUT**: Update/Replace resource.
- **DELETE**: Remove resource.

**D12 — Easy:** Version pinning specifies exact versions of dependencies (e.g., `requests==2.31.0`) instead of ranges (`requests>=2.0`). This ensures reproducible builds so that a project doesn't break when a dependency releases a breaking update.

**D13 — Easy:** Compiled languages are translated to machine code before execution (C++, Rust). Interpreted languages are read and executed line-by-line at runtime (Python, JavaScript).

**D14 — Medium:** A forward proxy acts on behalf of the client (hiding the client); a reverse proxy acts on behalf of the server (hiding the server).
- **Nginx**: Used as a Load Balancer to distribute traffic across servers.
- **Varnish**: Used as a Caching Proxy to serve static content faster.

**D15 — Medium:** A deadlock is a state where two or more processes are unable to proceed because each is waiting for the other to release a resource. Coffman conditions: 
1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** Eventual consistency means if no new updates are made, all accesses will eventually return the last updated value. Cassandra handles this via tunable consistency levels: `ONE` (fastest, low consistency), `QUORUM` (majority agreement), and `ALL` (strongest consistency but slowest/least available).

**D17 — Hard:** mTLS requires both client and server to present certificates. Handshake: Server sends its cert $\rightarrow$ Client verifies it against CA $\rightarrow$ Client sends its own cert $\rightarrow$ Server verifies it against CA $\rightarrow$ Both derive a symmetric session key. Commonly used in Service Meshes (Istio) for zero-trust internal communication.

**D18 — Hard:** A hash table uses a function to map keys to array indices. 
- **Collision Resolution**: Chaining (linked lists at index) vs Open Addressing (searching for next empty slot).
- **Complexity**: Average $O(1)$ for insertion, lookup, deletion; Worst case $O(n)$ if many collisions occur.

**D19 — Hard:** The circuit breaker prevents cascade failures by stopping requests to a failing service.
- **Closed**: Normal operation; traffic flows.
- **Open**: Failure threshold reached; fail fast immediately without calling the service.
- **Half-Open**: Periodically allows a few probes to see if the service has recovered.
It relates to retry policies via exponential backoff—increasing wait times between retries to avoid overwhelming a recovering system ("thundering herd").

**D20 — Hard:** 
- **Optimistic**: Assumes no conflict; checks version/timestamp upon commit. If changed, the transaction fails. Use when conflicts are rare. *Example:* `UPDATE users SET name='X' WHERE id=1 AND version=5`.
- **Pessimistic**: Locks the resource immediately so others cannot access it until released. Use when conflicts are frequent or data integrity is critical. *Example:* `SELECT * FROM orders WHERE id=1 FOR UPDATE` (locks row in SQL).
