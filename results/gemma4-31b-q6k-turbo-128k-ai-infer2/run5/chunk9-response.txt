## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:** These pods are failing because of the transition from **Baseline** to **Restricted** Pod Security Standards (PSS). In Baseline mode, Kubernetes allows containers to run as root if not specified otherwise. Restricted mode enforces that pods must not run as root. When `securityContext.runAsNonRoot: true` is set without an explicit `runAsUser`, Kubernetes checks the image's metadata. Since the new base image (`chainguard/static`) defaults its `USER` to root, the Kubelet refuses to start the container because it violates the "must not run as root" requirement. Essentially, `runAsNonRoot: true` tells K8s "ensure this doesn't run as root," but since no specific non-root UID was provided in the manifest and the image itself specifies root, the validation fails at runtime.

**SC1-B:** 
```bash
kubectl get pods -A -o json | jq '.items[] | select(.status.containerStatuses[0].state.waiting.reason == "CrashLoopBackOff") | {namespace: .metadata.namespace, name: .metadata.name, securityContext: .spec.securityContext}'
```

**SC1-C:** 
*   **Immediate Fix:** Update manifests to include an explicit `runAsUser: 1000` (or any non-zero ID) in the `securityContext`. This overrides the image default and satisfies the Restricted PSS.
*   **Image-level Fix:** Rebuild images with a non-root `USER` directive in the Dockerfile (e.g., `USER 1000`).
*   **CI Pipeline Gate:** Implement a `kube-linter` or `polaris` check in CI to flag any pod spec that lacks an explicit `runAsUser` when `runAsNonRoot` is true.
*   **Rollout Strategy:** Use a **Canary Deployment**. Deploy the fix to one namespace/service first, verify health via probes, then roll out across the cluster using a rolling update (`maxUnavailable: 25%`) to ensure zero downtime.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:** The stale data issue is caused by **asynchronous replication lag**. In standard RDS cross-region replicas, WAL logs are shipped asynchronously; there is always a delay between the primary commit and the replica application. Promoting the replica creates a "split" where some transactions committed in us-east-1 never reached eu-west-1 before the outage. Data loss occurs because those missing WAL records are gone. To quantify this, I would compare the `last_wal_receive_lsn` on the replica vs the `last_wal_flush_lsn` of the old primary (if accessible) or examine the `pg_stat_replication` view during the failover window.

**SC2-B:** 
1.  **Import promoted instance:** `terraform import aws_db_instance.primary <new_rds_identifier>`
2.  **State Manipulation:** Since the ARN changed, use `terraform state rm aws_db_instance.old_primary` followed by the import above.
3.  **Update References:** Update the HCL variable for the DB identifier/ARN. Use `terraform plan` to ensure only the reference updates occur.
4.  **Dependent Resources:** For Route53, update the CNAME record to point to the new EU endpoint. Run `terraform apply -target=aws_route53_record.api_db`. This prevents recreating the database while updating the network path.

**SC2-C:** 
*   **Architecture:** Replace PgBouncer with **RDS Proxy**. RDS Proxy handles failovers more gracefully and maintains application connections during DNS shifts.
*   **DNS Failover:** Implement Route53 Health Checks with a Failover Routing Policy; if us-east-1 is unhealthy, it automatically flips the CNAME to eu-west-1.
*   **RPO < 1s:** I strongly recommend **Aurora Global Database**. It uses storage-level replication (physical) rather than logical WAL shipping, typically achieving RPO < 1 second and significantly faster promotion times compared to standard RDS replicas.
*   **App Logic:** Implement exponential backoff retries in the connection pooler logic to handle the transient "server login retry" errors during the promotion window.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:** 
1.  **Sticky Sessions:** K8s pods are ephemeral; local memory sessions will be lost on restart/scale. *Solution:* Move session state to Redis.
2.  **Local NFS Mount:** Pods across different nodes need shared access to `/data/uploads`. *Solution:* Implement a CSI driver for NFS (e.g., `nfs-subdir-external-provisioner`).
3.  **Oracle DB Connectivity:** On-prem Oracle requires stable networking and specific drivers. *Solution:* Establish AWS Direct Connect/VPN and use ExternalName services in K8s.
4.  **IBM MQ Integration:** Legacy middleware often uses fixed IPs or proprietary protocols. *Solution:* Use a Sidecar proxy or a dedicated Gateway pod to bridge IBM MQ traffic.
5.  **Monolithic Size:** Large Java heaps can cause OOMKills if limits aren't tuned. *Solution:* Right-size resources using Vertical Pod Autoscaler (VPA) during initial migration.

**SC4-B:**
```hcl
variable "nfs_server" { default = "10.0.0.50" }
variable "export_path" { default = "/exports/uploads" }

resource "kubernetes_storage_class" "nfs_sc" {
  metadata { name = "nfs-client" }
  storage_class_name = "nfs-client"
  provisioner = "nfs.csi.k8s.io"
  parameters = { server = var.nfs_server, path = var.export_path }
}

resource "kubernetes_persistent_volume_claim" "upload_pvc" {
  metadata { name = "monolith-uploads-pvc" }
  spec {
    access_modes = ["ReadWriteMany"] # Necessary because multiple pods across nodes must write simultaneously
    resources { requests = { storage = "1Ti" } }
    storage_class_name = "nfs-client"
  }
}
```

**SC4-C:** 
*   **Phase 1: Read-Only Proxy.** Deploy the app in K8s but route only read traffic via F5 (Weight 90% Legacy / 10% K8s). Use a shared NFS mount for files.
*   **Phase 2: Feature Extraction.** Move one module (e.g., User Profile) to a new microservice; use an Ingress controller to route `/api/user` to K8s and everything else to legacy.
*   **Phase 3: Full Cutover.** Shift all traffic to K8s Ingress. IBM MQ is handled by keeping the connection open from the K8s cluster to on-prem until the mainframe is decommissioned.
*   **Rollback:** Keep the F5 configuration active; if p99 latency exceeds 2s or error rates spike, flip the DNS/F5 weight back to 100% bare metal. **Go/No-go metric:** Error rate < 0.1% and p99 $\le$ 2s over a 24h window.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A:** 
1.  **Approach:** Check Istio `envoy_cluster_upstream_rq_time` metrics. If the sidecar reports high "upstream" time but low "downstream" time, the delay is inside `inventory-service`.
2.  **Tracing:** Use Jaeger to look for spans where `checkout-service` calls `inventory-service`. If the span shows a long gap before the response starts, it's likely DB contention (waiting for a lock).
3.  **Envoy Metrics:** Compare `upstream_rq_pending_overflow` (proxy queueing) vs `upstream_rq_time` (actual service processing). High pending overflow indicates the proxy cannot send requests fast enough due to connection limits.

**SC5-B:**
*   **SQL Diagnostic:**
```sql
SELECT blocked_locks.pid AS blocked_pid, blocking_locks.pid AS blocking_pid, 
       blocked_activity.query AS blocked_query, blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_locks.pid = blocked_activity.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype 
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_locks.pid = blocking_activity.pid
WHERE NOT blocked_locks.granted;
```
*   **Go Circuit Breaker:**
```go
cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name: "inventory-service",
    MaxRequests: 5,
    Interval: 10 * time.Second,
    Timeout: 30 * time.Second,
})

body, err := cb.Execute(func() (interface{}, error) {
    return httpClient.Get("http://inventory-service/stock")
})
```

**SC5-C:** 
*   **Architecture:** Implement **CQRS**. The reconciliation job should run against a **Read Replica**, preventing locks on the primary write table used by `checkout-service`.
*   **Isolation:** Use separate DB connection pools for API traffic and background jobs (Bulkhead pattern).
*   **Scheduling:** Stagger CronJobs to avoid peak hours or use a queue-based approach where reconciliation is processed in small batches rather than one giant transaction.
*   **K8s Resources:** Set a `PriorityClass` for serving pods higher than the CronJob. Define a `PodDisruptionBudget` of $minAvailable: 2$ for the service to ensure it's never starved during node maintenance or resource contention.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:** I would implement **SPIFFE/SPIRE**. SPIRE acts as the identity control plane, issuing short-lived SVIDs (X.509 certificates) to workloads regardless of location. AWS workloads get identities via an AWS IAM OIDC provider linked to SPIRE; Azure workloads use Managed Identities federated into the same trust domain. A workload in AWS authenticates to on-prem by presenting its SVID; the on-prem service verifies this certificate against the shared SPIRE root of trust, eliminating the need for shared secrets.

**SC6-B:**
```hcl
resource "aws_ec2_transit_gateway" "main" { name = "zt-tgw" }

variable "endpoints" { default = ["s3", "rds", "ecr"] }

resource "aws_vpc_endpoint" "private_links" {
  for_each          = toset(var.endpoints)
  vpc_id           = aws_vpc.main.id
  service_name     = "com.amazonaws.${data.aws_region.current.name}.${each.value}"
  vpc_endpoint_type = "Interface"
}

resource "aws_security_group" "default_deny" {
  name = "zero-trust-sg"
  # No ingress rules defined = Default Deny All
}
```

**SC6-C:** 
*   **Direct Connect (DX):** Best for bandwidth/stability. High cost, low latency, fits ZT if combined with MACsec encryption. Routing: BGP via DX Gateway.
*   **VPN ECMP:** Cheaper, scales horizontally. Higher jitter, complex routing. Fits ZT but relies on IPsec overhead.
*   **Hybrid Mesh (Tailscale/Netbird):** Easiest deployment, uses WireGuard. Encrypts at the application layer. Perfect for ZT as it ignores network boundaries entirely.
*   **Recommendation:** **Direct Connect + Tailscale**. Use DX for the heavy data lift and a mesh overlay for identity-based access control. This separates the transport layer from the security policy.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:** 
1.  **Manual Apply:** Creates "shadow infrastructure." Dangerous because Git is no longer the source of truth; future pipeline runs may overwrite manual fixes or fail unexpectedly.
2.  **Helm Divergence:** Leads to inconsistent environments. A fix in staging might not work in production because the underlying values differ.
3.  **Kubectl Edit:** Direct state mutation bypasses validation and audit logs.
4.  **State Locking Risk:** Without locking, two engineers running `apply` simultaneously can cause **state corruption**, where one process overwrites the other's changes mid-update, potentially deleting resources that were just created.

**SC7-B:**
```yaml
stages: [validate, plan, apply]

tofu_plan:
  stage: plan
  script:
    - tofu fmt -check
    - tofu validate
    - tofu plan -out=tfplan
  artifacts: { paths: [tfplan] }

tofu_apply_prod:
  stage: apply
  environment: production
  when: manual # Manual gate for prod
  script:
    - tofu apply tfplan
  # Backend config includes dynamodb_table = "terraform-lock"
```

**SC7-C:** 
*   **Drift Detection:** Schedule a CI job every hour to run `tofu plan`. If it returns non-zero (changes detected), trigger an alert.
*   **Enforcement:** Use **Kyverno** policies to block any request to update ConfigMaps/Deployments unless the user is the CI Service Account (`user.kubernetes.io/username == 'gitlab-ci'`).
*   **Helm Structure:** Use **Kustomize** overlays; define a `base` folder for common values and environment folders (`dev`, `prod`) for specific overrides.
*   **RBAC:** Remove `edit` permissions from human users in Production AWS/K8s accounts, granting only `view` access. Only the CI pipeline's IAM role has `AdministratorAccess` or scoped write permissions.

## SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:** 
1.  **Prometheus OOM:** High cardinality (8.2M series). Prometheus stores active series in memory; too many unique label combinations exceed RAM. Check: `prometheus_tsdb_head_series`.
2.  **Loki Drops:** Ingester saturation. Likely due to high log volume per second exceeding the buffer size of the ingester pods. Check: `loki_ingester_push_requests_total`.
3.  **Tempo Timeouts:** Querying large trace sets without efficient indexing or using slow S3 reads for old data. Check: `tempo_query_duration_seconds`.
4.  **Thanos Lag:** Compactor cannot keep up with the rate of new blocks being uploaded to S3. Root cause is likely "too many small blocks" causing excessive metadata overhead.

**SC8-B:**
```bash
#!/bin/bash
# Get all metrics and count series via API
curl -s "http://prom:9090/api/v1/label/__name__/values" | jq '.data' > metrics.txt
echo "Metric Name | Series Count"
for m in $(cat metrics.txt); do
    count=$(curl -s "http://prom:9090/api/v1/query?query=count({__name%=\"$m\"})" | jq '.data.result[0].value[1]')
    echo "$m | $count"
done | sort -rnk2 | head -n 20 # Top 20 cardinality report
```

**SC8-C:** 
*   **Architecture:** Replace Prometheus with **Grafana Mimir**. It scales horizontally by splitting the write path (distributors $\rightarrow$ ingesters) from the read path (queriers).
*   **Loki:** Deploy in **Microservices Mode**, separating the `write` path into a dedicated cluster of ingesters to handle spikes without affecting queries.
*   **Tempo:** Use an S3 backend for long-term storage but implement a caching layer using Redis for recent traces.
*   **Governance:** Implement **Cardinality Quotas**. Use relabeling configs to drop high-cardinality labels (e.g., UserIDs) at the edge. Chargeback is implemented by tagging every metric with a `team_id` label and calculating total series per team via a Mimir query, billing based on total stored series.

## SC9 — Medium — Securing a Public-Facing API After a Breach

**SC9-A:** 
1.  **BOLA (API1:2023):** Violation of Object Level Authorization. *Fix:* Verify that the authenticated user owns the requested resource ID.
    ```python
    def get_object(self, queryset=None):
        obj = super().get_object()
        if obj.owner != self.request.user:
            raise PermissionDenied("Not your record")
        return obj
    ```
2.  **Excessive Data Exposure (API3:2023):** Returning internal fields. *Fix:* Use DRF Serializers to explicitly define allowed fields; never return raw DB models.
3.  **Lack of Rate Limiting (API4:2023):** Resource exhaustion/scraping. *Fix:* Implement WAF rate limits or DRF `Throttling`.
4.  **Sensitive Data in Logs (API7:2023):** Keys in URLs. *Fix:* Move keys to `Authorization` header (`Bearer <key>`).

**SC9-B:**
```hcl
resource "aws_wafv2_web_acl" "api_waf" {
  name = "api-security-acl"
  # ... rule for rate limiting 100 req / 5 min
  rule {
    name = "RateLimit"
    priority = 1
    statement { rate_based_statement { limit = 100 } }
    action { block {} }
    visibility_config { cloudwatch_metrics_enabled = true, metric_name = "RateLimit", sampled_requests_enabled = true }
  }
  # Rule to block query string API keys
  rule {
    name = "NoKeysInUrl"
    priority = 2
    statement { byte_match_statement { field = "query_string", positional_constraint = "CONTAINS", search_string = "api_key=" } }
    action { block {} }
    visibility_config { ... }
  }
}
```

**SC9-C:** 
*   **Defense-in-Depth:** Deploy **AWS API Gateway**. It handles JWT validation and throttling before the request ever hits the ALB.
*   **Auth Migration:** Implement a dual-auth window: allow both API Keys (headers only) and OAuth2 tokens for 30 days. Log all users still using API keys and send automated emails prompting them to migrate to the new `/token` endpoint. After 30 days, disable API key support.
*   **Encryption:** Use AWS KMS for envelope encryption of PII fields in PostgreSQL; decrypt only at the application layer for authorized roles.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:** I recommend an **Active-Passive approach with Warm Standby**. Active-Active is too complex given the 12ms latency (which would cause severe write contention/locking issues for Postgres). RPO of 15m is easily met via asynchronous streaming replication. RTO of 1h is achievable by pre-provisioning the K8s cluster in Dallas.
*   **PostgreSQL:** Patroni + Streaming Replication.
*   **Redis:** Redis Sentinel with cross-site replication.
*   **RabbitMQ:** Federation plugin to mirror critical queues.
*   **MinIO:** Site-to-Site bucket replication (asynchronous).

**SC10-B:**
```yaml

  tasks:

    - service: name=patroni state=restarted
  handlers:

        service: name=patroni state=restarted
# patroni.yml snippet:
# postgres:
#   parameters:
#     synchronous_commit: "on"
#     synchronous_standby_names: "dalas_node_1" # Ensures zero data loss if needed
```

**SC10-C:** 
1.  **Detection:** A quorum of monitors (e.g., Route53 Health Checks) must report Chicago down for > 60 seconds to avoid flapping.
2.  **Sequence:** 
    (1) GSLB flips DNS $\rightarrow$ Dallas. 
    (2) Patroni promotes Dallas standby to Primary. 
    (3) Redis Sentinel fails over. 
    (4) RabbitMQ Federation promoted to primary source. 
    (5) MinIO replication catch-up check.
3.  **Split Brain:** Use a **Fencing mechanism**. The failover script must call the AWS API to revoke all security group access to the Chicago cluster before promoting Dallas.
4.  **Failback:** Rebuild Chicago as a replica of Dallas, sync data, then perform a planned switchover during a maintenance window by gracefully demoting Dallas and promoting Chicago.
