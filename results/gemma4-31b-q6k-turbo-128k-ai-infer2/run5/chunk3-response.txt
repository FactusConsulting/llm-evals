## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry-run that compares the current state with the desired configuration and shows what changes will be made. `tofu apply` executes those changes to reach the desired state.

**T2 — Easy:** State is a JSON file mapping real-world resources to your configuration. Remote state stores this file in a shared location (S3, Consul, etc.), which is critical for team collaboration (preventing conflicting changes) and security (avoiding local secrets).

**T3 — Medium:** `count` creates resources based on an integer index (list); `for_each` uses a map or set of strings. `for_each` is preferred when managing collections because removing an item from the middle of a `count` list causes OpenTofu to shift indices and potentially destroy/recreate subsequent resources; `for_each` identifies resources by key, avoiding this.

**T4 — Medium:** This is called "drift." During the refresh phase of a `plan` or `apply`, OpenTofu queries the cloud API. If it finds differences between the actual state and the stored state, it marks them as updates. It handles this by proposing a change to revert the manual modification back to the configured state.

**T5 — Medium:**
```hcl
resource "aws_instance" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  tags = { Name = each.value }
}
```

**T6 — Hard:** `terraform_remote_state` reads the entire state file of another project; output values are specific variables exported via `output {}` blocks. The recommended alternative is using **Data Sources** (e.g., fetching a VPC ID by tags) or splitting into smaller modules managed by a wrapper like Terragrunt. This decouples states so that one team doesn't need read access to the full state file of another.

**T7 — Hard:** Provisioners run *after* the resource is created but before the resource is considered "complete." Since outputs are calculated after all resources in the graph are finished, dependent resources fail because they try to use an output that hasn't been finalized. **Fix:** Use a separate `null_resource` with `depends_on` and write the kubeconfig to a local file, then have subsequent resources read that file directly rather than relying on a module output during the same apply cycle.

**T8 — Medium:** `tofu import` brings existing infrastructure under management by adding it to the state file. Limitation: It only updates state, not code. You must manually write the HCL to match the imported resource. The `import` block (1.5+) allows declarative imports, meaning you can commit the import logic to Git and see what will happen via `plan` before executing.

**T9 — Easy:** A variable is an input parameter used to make configurations reusable. An **input variable** is provided by the user; an **output** is a value returned by the module for visibility or use by other modules.

**T10 — Easy:** A provider is a plugin that translates HCL into API calls for a specific platform (e.g., AWS, Azure). If you run `plan` without `init`, OpenTofu will error because the necessary provider binaries haven't been downloaded to the `.terraform/` directory.

**T11 — Easy:** This file records the exact versions of providers used. Committing it ensures "deterministic builds," ensuring every team member and CI pipeline uses the identical provider version to avoid breaking changes.

**T12 — Easy:** `tofu destroy` removes all resources managed by the configuration. To target one resource: `tofu destroy -target=aws_instance.web_server`.

**T13 — Easy:** A data source fetches information from an existing resource not managed by the current state. Example: Using `data "aws_ami"` to find the latest Ubuntu AMI ID instead of hardcoding a static ID that becomes obsolete.

**T14 — Medium:** Variables are inputs passed *into* a module. Locals are internal constants or computed values defined within the module. Use locals to eliminate repetition (DRY) and simplify complex logic that doesn't need to be changed by the end-user.

**T15 — Medium:**
- `create_before_destroy`: Creates the new resource before deleting the old one (Use case: Zero-downtime VM replacement).
- `prevent_destroy`: Errors out if a destroy is attempted (Use case: Production databases).
- `ignore_changes`: Ignores drift for specific attributes (Use case: Auto-scaling groups where the cloud modifies the desired capacity).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource was renamed or moved into/out of a module in the code, but it should remain the same physical resource in the state. This prevents the "delete then recreate" cycle during refactoring.

**T17 — Hard:** It uses a Directed Acyclic Graph (DAG). **Implicit dependencies** occur when one resource references another (`vpc_id = aws_vpc.main.id`). **Explicit dependencies** use `depends_on`. `depends_on` forces sequential execution; since OpenTofu parallelizes independent resources, overusing `depends_on` reduces performance by forcing a linear chain of creation.

**T18 — Hard:** 
1. **State Splitting:** Break one giant state into multiple smaller states (Tradeoff: More complex orchestration).
2. **`-refresh=false`**: Skip querying every single API endpoint on every plan (Tradeoff: Risk of acting on stale data/drift).
3. **Targeting**: Use `-target` for specific changes (Tradeoff: Can lead to inconsistent state if not careful).
4. **Modularization**: Move static infrastructure to separate modules so they aren't re-evaluated constantly (Tradeoff: Increased codebase complexity).

**T19 — Hard:** State locking prevents two people from running `apply` simultaneously. If a crash occurs, the lock remains. Manually break it with `tofu force-unlock <LOCK_ID>`. The risk is that if a process *is* actually still running and you unlock it, you may cause state corruption via concurrent writes.

**T20 — Hard:** 
1. Add the `backend "s3"` block to configuration.
2. Run `tofu init`.
3. OpenTofu detects local state and asks to migrate; confirm "yes."
4. OpenTofu uploads `.tfstate` to S3 and creates the DynamoDB lock table.
5. Verify by checking the S3 bucket for the file and ensuring subsequent plans show no drift. Local `.tfstate` files are typically deleted or ignored after migration.

## Ansible

**A1 — Easy:** A **playbook** is a YAML file containing one or more plays (the orchestration); a **role** is a structured bundle of tasks, variables, and handlers for reuse; a **task** is a single action (e.g., installing a package) executed on a host.

**A2 — Easy:** `ansible_facts` is a dictionary of system information gathered at the start of a play. Access OS family via `{{ ansible_os_family }}` or `{{ ansible_facts['os_family'] }}`.

**A3 — Medium:** 
- `command`: Executes a binary directly (safest, no shell features).
- `shell`: Runs through `/bin/sh` (allows pipes, redirects, environment variables).
- `raw`: Sends raw SSH strings (used when Python isn't installed on target).

**A4 — Medium:** Idempotency means running a task multiple times results in the same state without further changes. 
- **Idempotent:** `apt: name=nginx state=present`.
- **NOT Idempotent:** `shell: echo "timestamp" >> /var/log/deploy.log` (adds a line every time it runs).

**A5 — Medium:**
```yaml
- name: Install htop based on OS
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
  when: ansible_os_family == 'Debian' or ansible_os_family == 'RedHat'

# Better approach using a variable map:
- name: Install packages
  package:
    name: "{{ pkg_list[ansible_os_family] }}"
  vars:
    pkg_list: { 'Debian': ['htop'], 'RedHat': ['epel-release', 'htop'] }
```

**A6 — Hard:** Precedence (lowest to highest): Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ Playbook vars $\rightarrow$ Extra vars (`-e`). `set_fact` is dynamic and overrides most, but extra-vars always win.

**A7 — Hard:** 
1. Create two groups in inventory: `initial_nodes` (3) and `remaining_nodes`.
2. Use `serial: 3` for the first play targeting `initial_nodes`.
3. In the second play for `remaining_nodes`, use a task with the `wait_for` module checking for the RKE2 port (6443) on one of the initial nodes before proceeding.

**A8 — Medium:** `ansible-vault` encrypts secrets. To encrypt a single variable: use `ansible-vault encrypt_string 'mysecretpassword' --name-of-variable`. This allows you to keep the rest of the YAML file plain text while only the value is encrypted.

**A9 — Easy:** An inventory lists target hosts. **Static**: A flat `.ini` or `.yml` file. **Dynamic**: A script or plugin that queries an API (like AWS EC2 tags) to generate the host list at runtime.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A handler is a special task that runs only if notified by another task via the `notify` keyword, and it only runs once at the end of the play. Triggered when a task reports a status of `changed`.

**A12 — Easy:** `ansible.cfg` defines global settings. Common settings: `remote_user` (default SSH user), `forks` (parallelism), `host_key_checking = False` (skip SSH fingerprint prompts).

**A13 — Easy:** `register` captures the output of a task into a variable. 
Example:
```yaml
- shell: uptime
  register: system_uptime
- debug: msg="The uptime is {{ system_uptime.stdout }}"
```

**A14 — Medium:** `import_tasks` is static (processed during parsing); `include_tasks` is dynamic (processed during execution). Use `include_tasks` for conditional loading (`when`) because they are evaluated at runtime; imports are processed before any tasks run.

**A15 — Medium:** Ansible Galaxy is a community hub for roles/collections. Install using a `requirements.yml`:
```yaml
# requirements.yml
roles:
  - name: geerlingguy.nginx
collections:
  - name: community.general
```
Run: `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:** Connection plugins handle how Ansible talks to hosts.
- `ssh`: Standard remote execution via SSH.
- `local`: Runs on the control node itself.
- `network_cli`: Maintains persistent connections for network devices that don't support standard shells.

**A17 — Hard:** `delegate_to` runs a task on a different host than the current target. `run_once` executes the task once per play regardless of host count. 
Example: Update an external DNS record on localhost based on the IP gathered from a remote server:
```yaml
- name: Update DNS
  uri: url="http://dns-api/update?ip={{ ansible_default_ipv4.address }}"
  delegate_to: localhost
  run_once: true
```

**A18 — Hard:** 
1. **Forks**: Increase `forks = 50` in `ansible.cfg` to increase parallelism (Tradeoff: Higher CPU/RAM load on control node).
2. **Pipelining**: Enable `pipelining = True` to reduce number of SSH operations (Tradeoff: Requires `requiretty` disabled on targets).
3. **Fact Caching**: Use Redis or JSON file caching so facts aren't re-gathered every run (Tradeoff: Stale data if system changes).
4. **Mitogen**: Replace the SSH transport with Mitogen for massive speed gains (Tradeoff: Third-party dependency, potential compatibility issues).

**A19 — Hard:** Jinja2 uses `{{ }}` for expressions, `{% %}` for logic/loops, and `{# #}` for comments.
Snippet:
```jinja2
upstream backend_servers {
    {% for server in servers %}
    # Health check enabled for {{ server }}
    server {{ server }};
    {% endfor %}
}
```

**A20 — Hard:** 
1. Set `serial: 20%` to process nodes in batches.
2. **Pre-task**: Task using `uri` module to remove current host from Load Balancer (LB) API.
3. **Deploy**: Update application code/service.
4. **Health Check**: Loop `uri` module calls until app returns 200 OK.
5. **Post-task**: Re-add host to LB.
6. **Rollback**: Wrap deployment in a `block`. In the `rescue` section, trigger a rollback task (e.g., revert symlink to previous version) and notify administrators.
