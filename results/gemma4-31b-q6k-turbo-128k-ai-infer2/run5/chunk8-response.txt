## Cloud Infrastructure Architecture

**CL1**: **IaaS** (Infrastructure as a Service) provides raw compute, storage, and networking; user manages OS and apps (e.g., AWS EC2). **PaaS** (Platform as a Service) provides a framework for developers to build/deploy apps without managing underlying servers (e.g., Google App Engine). **SaaS** (Software as a Service) delivers fully managed software over the web (e.g., Microsoft 365).

**CL2**: The Shared Responsibility Model defines who is responsible for security "of" the cloud vs "in" the cloud.
- **IaaS VMs**: Provider handles hardware/hypervisor; User handles Guest OS, patching, and firewall config.
- **Managed Kubernetes**: Provider handles Control Plane; User handles Worker Node configuration and Pod security.
- **SaaS (M365)**: Provider handles almost everything (app, infra); User handles data, identity access, and configuration.

**CL3**: A **VPC** is an isolated virtual network. A **Subnet** is a range of IP addresses within that VPC. A **Security Group** is a stateful instance-level firewall (remembers requests). A **NACL** is a stateless subnet-level firewall (must define both inbound and outbound rules). Layering: Traffic hits NACL $\rightarrow$ Subnet $\rightarrow$ Security Group $\rightarrow$ Instance.

**CL4**: A **Landing Zone** is a pre-configured multi-account environment. **OUs** group accounts by function or business unit. **Guardrails** (like AWS SCPs) set maximum permission boundaries. **Shared Networking** uses a Hub-and-Spoke model via Transit Gateway to centralize egress/ingress. **Centralized Logging** aggregates logs into a dedicated security account for auditing. Single-account approaches are problematic due to "blast radius" (one compromise affects all), quota limits, and billing complexity.

**CL5**: IaC manages infrastructure through machine-readable definition files. 
- **Terraform/OpenTofu**: Cloud-agnostic, HCL-based; best for general purpose across providers.
- **Pulumi**: Uses general languages (Python, TS); best for developers who want loops/logic in infra.
- **CloudFormation/Bicep**: Provider-specific; deepest integration with their respective clouds.
- **Crossplane**: K8s-native control plane; treats cloud resources as K8s objects. Use Crossplane when you want the cluster to manage its own external dependencies.

**CL6**: **HPA** scales pods based on CPU/RAM metrics. **VPA** adjusts pod resource requests/limits. **Cluster Autoscaler** adds/removes nodes to the cluster. **KEDA** allows scaling based on external events (e.g., Kafka lag). Use KEDA over HPA when scaling depends on business logic or event queues rather than just hardware utilization.

**CL7**: Strategy: Active-Active across two regions using Global Load Balancing (Route53) for DNS failover. Database replication should be asynchronous for distance to avoid latency penalties, accepting a small RPO. 
- **Pilot Light**: Minimal core services running; data replicated; scale up during disaster.
- **Warm Standby**: Scaled-down version of full stack always running.
- **Multi-site Active-Active**: Full capacity in both sites serving traffic simultaneously. Cost increases linearly with redundancy level.

**CL8**: GitOps uses Git as the single source of truth for infrastructure and app state. **ArgoCD** is highly visual/UI-driven; **FluxCD** is more lightweight/CLI-focused. Secrets are handled via **SealedSecrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault), or **Vault** directly. Manual drift is detected by the controller, which either alerts the user or automatically overwrites manual changes to match Git.

**CL9**: Architecture: Use a **StatefulSet** for stable network IDs. Map pods to **PVs** using a **Local Storage Class** for low latency. A **Headless Service** provides direct pod IPs for the application's internal clustering. Use **Init Containers** to prepare filesystem paths and **ConfigMaps** mounted as volumes for configuration files. Implement **Pod Disruption Budgets (PDB)** to ensure minimum available replicas during node maintenance.

**CL10**: A **Service Account** is an identity for processes inside K8s. **Workload Identity / IRSA** maps that K8s account to a Cloud IAM Role. Mounting static credentials (JSON keys) is bad because they are long-lived and easily leaked. Workload Identity federation solves this by exchanging short-lived OIDC tokens for temporary cloud credentials.

**CL11**: 
- **Object (S3/Blob)**: Unstructured data; highly durable ($11\text{ nines}$); used for backups, images, logs.
- **Block (EBS/Managed Disk)**: Low-latency read/write; attached to one VM; used for OS boots and DB data files.
- **File (EFS/Azure Files)**: Shared access via NFS/SMB; used for shared config or legacy app mounts.

**CL12**: Zero Trust replaces perimeter security with "never trust, always verify." Components: **Network Policies** for L4 isolation $\rightarrow$ **mTLS (Istio/Linkerd)** for encrypted pod-to-pod auth $\rightarrow$ **Admission Controllers (OPA/Kyverno)** to block non-compliant pods $\rightarrow$ **Cosign** for image signing $\rightarrow$ **Falco** for runtime anomaly detection. Unlike traditional models, it assumes the network is already compromised.

**CL13**: A CDN caches content at edge locations closer to users to reduce latency. Examples: CloudFront, Akamai. Use a CDN when serving static assets globally or protecting origin servers from high traffic spikes; serve directly only for dynamic, personalized, or low-traffic internal content.

**CL14**: A **Region** is a geographic area containing multiple isolated **Availability Zones (AZs)**. Deploying across AZs protects against a single data center failure. **Zonal resources** exist in one AZ (e.g., an EBS volume); **Regional resources** span multiple AZs (e.g., S3 buckets).

**CL15**: Managed DB services automate patching, backups, hardware provisioning, and failover. Compared to running on a VM, the provider handles the operational overhead of the database engine installation and OS maintenance, leaving the user to manage schema design and query optimization.

**CL16**: **Users** are individuals; **Groups** organize users; **Roles** are identities assumed by people or apps; **Policies** define permissions. The **Principle of Least Privilege** means granting only the minimum permissions required for a task. Apply this by using granular IAM policies instead of "AdministratorAccess."

**CL17**: Serverless executes code in response to events without managing servers. Cold starts occur when a function hasn't been used recently, causing latency during initialization. It is a poor fit for long-running processes (timeouts) or workloads with high, constant traffic where dedicated instances are cheaper.

**CL18**: **Ingress** provides L7 routing via a resource object. **Gateway API** is the modern successor providing role-based configuration and better expressiveness. **LB Annotations** pass cloud-specific settings directly to the load balancer. TLS termination usually happens at the Load Balancer or Ingress Controller. Use Gateway API for complex routing requirements across multiple teams/namespaces.

**CL19**: Strategy: Move from On-Demand $\rightarrow$ **Savings Plans/RIs** for baseline loads. Use **Spot Instances** for stateless batch jobs. Implement **S3 Intelligent-Tiering** for data lifecycle management. Right-size based on CloudWatch metrics. Establish **FinOps** reviews monthly. Use **Chargeback** (billing departments) to drive accountability. Tools: AWS Cost Explorer, Kubecost.

**CL20**: Design: Use **Kubernetes** as the common runtime abstraction and **Terraform** for portable IaC. Connect clouds via **VPN or Interconnect**. Federate identity using OIDC. Trade-off: Theoretical "no lock-in" vs real-world complexity of managing two sets of APIs and higher egress costs. Justified only for extreme regulatory mandates or critical availability needs; otherwise, it's unnecessary complexity.

## OT Infrastructure Architecture

**OT1**: The Purdue Model segments industrial networks into levels:
- **Level 0 (Process)**: Physical sensors and actuators.
- **Level 1 (Basic Control)**: PLCs and PID controllers.
- **Level 2 (Area Supervisory)**: HMIs and SCADA workstations.
- **Level 3 (Site Operations)**: Plant historians and site-wide control.
- **Level 4/5 (Enterprise)**: Corporate IT network and business systems.

**OT2**: IT prioritizes Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability. OT prioritizes **Availability $\rightarrow$ Safety $\rightarrow$ Integrity**. Standard IT patching is dangerous in OT because a reboot can stop a physical process, cause equipment damage, or create safety hazards if not timed with plant shutdowns.

**OT3**: An IDMZ prevents direct communication between the corporate network (L4) and the control zone (L3). Only proxy traffic (e.g., historian replication) should cross. Direct L4 to L1 connectivity is dangerous because a compromised office laptop could send "Stop" commands directly to a PLC, bypassing all security controls.

**OT4**: 
1. **Modbus TCP**: L1/L2 (Simple device comms).
2. **OPC UA**: L2/L3 (Secure, platform-independent data exchange).
3. **EtherNet/IP**: L1/L2 (Common in Rockwell environments).
4. **PROFINET**: L1 (High-speed deterministic control).
5. **MQTT**: L3 to Cloud (Lightweight pub/sub for telemetry).

**OT5**: A **Firewall** uses software rules to allow/block bidirectional traffic. A **Data Diode** is hardware that physically allows data to flow in only one direction. Use a diode for high-security zones where no inbound signal must ever enter (e.g., nuclear core monitoring). Limitation: No TCP handshakes; requires specialized protocols since there are no ACKs.

**OT6**: Flow: Sensor $\rightarrow$ PLC $\rightarrow$ SCADA Historian $\rightarrow$ Edge Gateway (Protocol conversion Modbus$\to$MQTT) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. Security boundaries: Firewall between L2 and L3, and an IDMZ before the cloud gateway.

**OT7**: A **Zone** is a group of assets with similar security requirements. A **Conduit** is the communication path between them. Design: Corporate Zone $\rightarrow$ Conduit $\rightarrow$ IDMZ $\rightarrow$ Conduit $\rightarrow$ Control Zone (SCADA/PLCs) $\rightarrow$ Isolated Conduit $\rightarrow$ Safety Zone (SIS). The SIS should be logically or physically isolated from all other zones.

**OT8**: Strategy: Segment by production line using VLANs. Place firewalls at the boundary of each line and between L2 and L3. Implement a "Jump Host" in the IDMZ for vendor access via MFA. Transition: Start with passive mirroring (SPAN ports) to map traffic, then implement "Permit All" logging rules, and finally move to strict enforcement during scheduled maintenance windows.

**OT9**: **BPCS** manages normal operations; **SIS** is a separate system that triggers emergency shutdowns if parameters exceed safe limits. IEC 61511 governs safety lifecycle. Isolation prevents common-mode failure; if ransomware hits BPCS, the SIS must remain functional to safely shut down the plant. If SIS is compromised, the plant loses its final layer of protection against catastrophe.

**OT10**: **PLC** (Local logic/fast), **DCS** (Integrated plant-wide control/complex), **SCADA** (Supervisory over wide areas). Use PLC for simple machines, DCS for complex chemical plants, SCADA for pipelines/utilities. They coexist: PLCs act as local controllers reporting up to a SCADA system.

**OT11**: Architecture: VPN $\rightarrow$ Multi-Factor Authentication (MFA) $\rightarrow$ Jump Host (Bastion) $\rightarrow$ Target Asset. Session recording and time-limited tokens are required. Direct RDP from corporate IT is unacceptable because it exposes vulnerable HMI software directly to the broader network.

**OT12**: Detection: Deploy an IDS looking for abnormal Modbus function codes or unauthorized IP addresses in L3. Response: Isolate the affected segment via firewall rules while maintaining "fail-safe" process states. The plant operator's role is critical: they determine if the physical process can be safely maintained during isolation or if a manual emergency shutdown is needed.

**OT13**: An **HMI** provides a visual interface for operators to monitor and control the process. An **Engineering Workstation** is used by engineers to program the PLCs and configure the HMI screens; it has much higher privileges and specialized software.

**OT14**: A **Historian** is a high-performance database for time-series process data. Plant Historians (L3) store raw, high-resolution data for real-time analysis. Enterprise Historians (L4) store aggregated, long-term data for business reporting and KPIs.

**OT15**: Ladder Logic is a graphical language executed by PLCs that mimics electrical relay diagrams. It remains dominant because it is intuitive for electricians/technicians who understand physical wiring, making troubleshooting easier on the factory floor.

**OT16**: An **RTU** is designed for wide-area telemetry over low-bandwidth links (radio/cellular). Unlike PLCs, which are optimized for fast local loops in factories, RTUs are deployed in remote environments like oil wells or water pumping stations.

**OT17**: Analog signals vary continuously (e.g., 4-20mA); digital are binary (On/Off). 4-20mA is preferred over 0-20mA because if the signal drops to 0mA, the system knows there is a wire break (fault), whereas at 0V/0mA in a 0-range system, you cannot distinguish between "zero value" and "broken wire."

**OT18**: Asset inventory identifies every device, firmware version, and communication path. Passive monitoring (sniffing traffic) is used because active scanning (ping/port scans) can crash legacy PLCs with fragile TCP stacks, potentially causing an unplanned plant shutdown.

**OT19**: MITRE ATT&CK for ICS focuses on physical impact. Tactics: Initial Access $\rightarrow$ Execution $\rightarrow$ Persistence $\rightarrow$ Evasion $\rightarrow$ Impact. Example Technique: *Inhibit Response Function* (preventing alarms from reaching operators). It differs by focusing on process disruption rather than just data theft. Use it to map visibility gaps in OT telemetry.

**OT20**: Design: Collect logs via unidirectional gateways (data diodes) to avoid impacting real-time traffic. Integrate into SIEM using OT-specific parsers. Triage involves both IT analysts (network anomalies) and OT engineers (process context). A PLC firmware alert requires verifying against change tickets, checking hashes, and physically inspecting the hardware before taking action.
