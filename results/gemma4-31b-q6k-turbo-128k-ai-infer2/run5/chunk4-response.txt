## Go

**G1**: An **array** has a fixed size defined at compile time (`[5]int`). A **slice** is a descriptor for a contiguous segment of an array, consisting of a pointer to the underlying array, a length, and a capacity. When you `append` to a slice that has reached its capacity, Go allocates a new, larger underlying array (usually doubling the size), copies the existing elements over, and returns a new slice header pointing to this new array.

**G2**: `var x int` declares a variable with its zero value (0). `x := 0` is short-variable declaration; it infers the type and initializes the variable. You cannot use `:=` outside of functions (package level) or when declaring a variable that has already been declared in the current scope (unless at least one new variable is being introduced on the left side).

**G3**: A **goroutine** is a lightweight thread managed by the Go runtime, not the OS. While an OS thread typically has a large stack (MBs), goroutines start small (~2KB) and grow dynamically. The **GMP model** consists of: **G** (Goroutine), **M** (Machine/OS Thread), and **P** (Processor/Logical Context). P schedules Gs onto Ms, allowing M's to be reused and Gs to be moved between threads (work stealing) for efficiency.

**G4**: Channels are typed conduits for communication. An **unbuffered channel** blocks the sender until a receiver is ready (synchronous). A **buffered channel** allows sending values without a corresponding receiver until the buffer is full. When you send to a full buffered channel, the goroutine blocks until a value is received from the channel.

**G5**: The `context` package manages request lifecycles, cancellation signals, and deadlines across API boundaries.
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
_, err := http.DefaultClient.Do(req) // Returns error if timeout expires
```

**G6**: Go uses **implicit satisfaction**. If a type implements all methods defined in an interface, it satisfies that interface automatically; no `implements` keyword is needed. Java/C# use explicit implementation. `interface{}` (or `any`) can hold any value. It is powerful because it enables generic-like behavior but dangerous because it bypasses compile-time type safety, requiring runtime type assertions or switches.

**G7**: This code has a **data race**. There is no synchronization ensuring that the write to `ready` is visible to the main loop's read. The compiler or CPU might cache `ready` in a register, leading to an infinite loop. Correct alternatives: Use a `sync.Mutex`, a `channel`, or `atomic.Value`/`atomic.Bool`.

**G8**: `sync.Mutex` provides exclusive locking. `sync.RWMutex` allows multiple concurrent readers OR one writer, which improves performance for read-heavy workloads. `sync.Map` is optimized for two cases: when entries are written once but read many times, or when multiple goroutines read/write disjoint sets of keys. A regular map with a mutex is generally faster for most common use cases due to lower overhead and better type safety.

**G9**: Go modules manage dependencies via `go.mod` (defines module path and requirements) and `go.sum` (contains cryptographic checksums for reproducibility). `go mod tidy` adds missing module requirements and removes unused ones. **MVS (Minimum Version Selection)** selects the *lowest* version of a dependency that satisfies all constraints, providing stability over "latest" versions.

**G10**: `defer` schedules a function call to run immediately before the surrounding function returns. Multiple defers execute in **LIFO (Last-In-First-Out)** order. Common gotcha: using a loop variable inside a defer; since the closure captures the reference, by the time the defer runs, the loop may have finished, and you'll see the final value of the variable instead of the value at the time of the call.

**G11**: A pointer stores the memory address of a value. The zero value of a pointer is `nil`. To create a pointer to a struct literal: `p := &User{Name: "Alice"}`.

**G12**: `init()` functions are called automatically when a package is initialized. They run after variable initialization but before `main()`. A package can have multiple `init()` functions across different files; they execute in the order the files are presented to the compiler (lexical order).

**G13**: `make` is used only for slices, maps, and channels; it initializes them and returns a usable object. `new(T)` allocates zeroed memory for any type `T` and returns a pointer (`*T`).

**G14**: Go uses explicit return values for errors. The `error` interface has one method: `Error() string`. Idiomatic pattern: `if err != nil { return ..., err }`. `errors.Is` checks if an error wraps a specific target (deep check), while `errors.As` attempts to cast an error to a specific type. `==` only works for sentinel errors and does not handle wrapped errors.

**G15**: 
- **Slice**: `nil`
- **Map**: `nil`
- **Channel**: `nil`
- **Struct**: All fields set to their respective zero values.

**G16**: A race condition occurs when two or more goroutines access shared data concurrently and at least one access is a write. `-race` enables the runtime race detector (using ThreadSanitizer).
Example fix:
```go
var mu sync.Mutex
var count int
// Fix: wrap in mutex
mu.Lock()
count++
mu.Unlock()
```

**G17**: `select` lets a goroutine wait on multiple communication operations. Unlike `switch`, it blocks until one of its cases can proceed. If multiple are ready, one is chosen pseudo-randomly. Timeout implementation:
```go
select {
case res := <-ch: // success
case <-time.After(1 * time.Second): // timeout
}
```

**G18**: Escape analysis determines if a variable can be allocated on the stack or must "escape" to the heap. The compiler puts variables on the heap if they are referenced after the function returns or are too large for the stack. Use `go build -gcflags="-m"` to inspect decisions. Heap allocation increases GC pressure; minimizing escapes improves performance.

**G19**: `reflect` allows inspecting types and values at runtime. `reflect.Type` describes the type's structure; `reflect.Value` represents the actual data. Reflection has high overhead due to dynamic dispatch and boxing. It is justified for generic libraries (e.g., JSON encoders) where code generation would lead to excessive boilerplate.

**G20**: `go:embed` allows embedding files/folders into binary binaries. Single files use `//go:embed file.txt`. Directories use `//go:embed folder/*`. It populates a `string`, `[]byte`, or an `embed.FS` (which implements `io/fs.FS`). Limitations include only allowing static paths relative to the source file.

## Rust

**R1**: Ownership ensures memory safety without a garbage collector. Rules: 1) Each value has a variable called its owner. 2) There can only be one owner at a time. 3) When the owner goes out of scope, the value is dropped.

**R2**: `String` is a heap-allocated, growable, owned string. `&str` is a borrowed "slice" (a pointer and length) referring to some existing string data. Use `&str` in function signatures for read-only access to maximize flexibility (it accepts both `&String` and literals).

**R3**: Borrowing lets you reference data without taking ownership. **Shared references (`&T`)** allow multiple readers but no writers. **Mutable references (`&mut T`)** allow exactly one writer and no other readers. The borrow checker enforces these rules at compile time to prevent data races.

**R4**: `Option<T>` represents optionality (`Some(T)` or `None`). `Result<T, E>` handles errors (`Ok(T)` or `Err(E)`). The `?` operator unwraps an `Ok`/`Some` value or returns the error/none immediately from the current function.
```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path) // Returns Result
}
```

**R5**: 
- `Box<T>`: Single ownership, heap allocation. Used for recursive types or moving large data.
- `Rc<T>`: Reference counted, single-threaded shared ownership.
- `Arc<T>`: Atomic Reference Counted; thread-safe version of `Rc`. Use when sharing data across threads.

**R6**: Traits define shared behavior (similar to interfaces). Unlike Go's implicit satisfaction, Rust requires explicit implementation (`impl Trait for Type`). A **trait object (`dyn Trait`)** uses dynamic dispatch (vtable), while a **generic bound (`T: Trait`)** uses monomorphization (static dispatch), which is faster but increases binary size.

**R7**: Lifetimes ensure references don't outlive their data. The provided code fails because the compiler doesn't know if the returned reference points to `x` or `y`, and thus cannot guarantee it remains valid. Fix:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

**R8**: `Send` indicates a type can be transferred between threads. `Sync` indicates a type can be referenced by multiple threads safely. `Rc<T>` isn't `Send`/`Sync` because its internal counter is not atomic; incrementing it from two threads would cause a race condition. `Arc<T>` uses atomic operations for the counter, making it thread-safe.

**R9**: Rust async is "pull-based." A `Future` is a state machine that does nothing until polled. An **executor** (like Tokio) polls futures to drive them to completion. Unlike Go's goroutines (which are managed by a runtime scheduler with preemptive-like behavior), Rust's async is cooperative—the future must yield control back to the executor via `.await`.

**R10**: `unsafe` allows bypassing some compiler checks. You can: 1) Dereference raw pointers. 2) Call unsafe functions (FFI). 3) Access/modify mutable static variables. It is justified when implementing low-level primitives (e.g., `Vec`) or interfacing with C code where safety cannot be proven at compile time.

**R11**: Pattern matching (`match`) allows exhaustive branching based on data structure. `if let` is syntactic sugar for a match with only one interesting case. The compiler enforces exhaustiveness; if you miss a variant of an enum in a `match`, the code will not compile.

**R12**: `Vec<T>` is a growable heap array; `[T; N]` is a fixed-size stack array. When a `Vec` exceeds capacity, it allocates a new larger buffer (usually doubling), copies elements over, and frees the old memory.

**R13**: Enums in Rust are "sum types" (can hold data per variant), unlike C enums which are just integers. `Option<T>` is an enum (`Some(T)` or `None`). Rust avoids nulls by forcing developers to explicitly handle the `None` case via pattern matching.

**R14**: `impl` blocks define methods for a type.
- `&self`: Immutable borrow (read-only).
- `&mut self`: Mutable borrow (modify state).
- `self`: Consumes ownership (moves the object).
Associated functions (e.g., `String::new()`) do not take `self` and act like static methods.

**R15**: `derive` automatically implements traits. Common ones: `Debug` (printing), `Clone` (duplicating), `PartialEq` (equality), `Serialize` (via Serde). You cannot derive a trait if the type contains fields that don't implement that trait.

**R16**: `Cow<'a, T>` (Clone on Write) allows a value to be either borrowed or owned. It avoids allocation by using a reference until modification is required, at which point it clones the data into an owned version. Useful for string processing where most inputs aren't modified.

**R17**: `mod` declares a module; `use` brings paths into scope; `pub` makes items visible. In 2015, modules were strictly tied to file structure (`mod.rs`). Since 2018, you can use `module_name.rs` alongside a folder of the same name.

**R18**: `Pin<T>` prevents a value from being moved in memory. This is critical for self-referential structs (where a pointer points to another field in the same struct). Async futures are often self-referential; without pinning, moving the future would invalidate internal pointers. `Unpin` is a marker trait for types that are safe to move.

**R19**: **Declarative macros** (`macro_rules!`) are pattern-based substitutions. **Procedural macros** act as compiler plugins: `derive` adds traits, `attribute` modifies existing items, and function-like macros generate new code. Hygiene ensures macros don't accidentally capture variables from the surrounding scope.

**R20**: Zero-cost abstractions mean "what you don't use, you don't pay for." Iterators are optimized into loops via LLVM. Generics use **monomorphization**, generating specialized versions of functions for each type used, allowing the compiler to inline calls and optimize them exactly like hand-written C.
