## Application Architecture

**AA1**: A **monolith** is a single unified unit where all business logic is in one codebase/process. **Microservices** decompose the application into small, independent services communicating over a network. Three problems introduced by microservices: 1) **Distributed Complexity** (tracing requests across services), 2) **Data Consistency** (managing distributed transactions/eventual consistency), 3) **Operational Overhead** (deploying and monitoring dozens of separate artifacts instead of one).

**AA2**: **Synchronous** communication requires the caller to wait for a response before proceeding (e.g., REST API call via HTTP). **Asynchronous** allows the caller to send a message and move on without waiting for an immediate result (e.g., publishing a message to RabbitMQ). Example technologies: Sync $\rightarrow$ gRPC; Async $\rightarrow$ Apache Kafka.

**AA3**: An **API Gateway** provides high-level business routing, authentication, rate limiting, and protocol transformation. A **Reverse Proxy** primarily handles load balancing, SSL termination, and request forwarding. While an API Gateway can perform reverse proxy functions, it usually doesn't replace them entirely because a dedicated reverse proxy (like Nginx or HAProxy) often sits at the very edge for raw performance and L4/L7 traffic management before hitting the gateway.

**AA4**: The **Saga pattern** manages distributed transactions through a sequence of local transactions with compensating actions if a step fails. **Choreography** is decentralized; services exchange events and decide their own next steps. **Orchestration** uses a central coordinator ("orchestrator") to tell services when to act. Use choreography for simple workflows to avoid bottlenecks; use orchestration for complex business logic where visibility and centralized control are required.

**AA5**: **CQRS** separates read models from write models to optimize performance independently. It is paired with **Event Sourcing** (storing state as a series of immutable events) because Event Sourcing provides the "source of truth" that CQRS read-models consume to build their projections. This solves the CRUD problem where a single database schema must serve both heavy writes and complex queries, which often leads to locking issues and poor query performance.

**AA6**: A **Circuit Breaker** prevents a system from repeatedly trying to execute an operation that is likely to fail. States: **Closed** (requests flow), **Open** (fail fast immediately), **Half-Open** (test if service recovered). Unlike retry-with-backoff (which keeps trying), a circuit breaker stops all traffic to a failing service to allow it to recover. You use both together by retrying transient errors first, but tripping the circuit breaker if the error rate exceeds a threshold.

**AA7**: 
1. **Shared DB/Schema**: Lowest cost, lowest security (logical isolation only), high noisy-neighbor risk, low operational complexity.
2. **Separate Schema**: Medium cost, better security (schema permissions), medium noisy-neighbor risk, moderate complexity.
3. **Separate DB**: Highest cost, highest security (physical isolation), zero noisy-neighbor risk, high operational complexity (managing many DB instances).

**AA8**: **Strong consistency** ensures all clients see the same data simultaneously; **eventual consistency** guarantees that given enough time without updates, all clients will eventually converge. To prevent overselling inventory at scale: Use **strong consistency**. Architecturally, I would use a distributed ACID database (e.g., CockroachDB or PostgreSQL with strict locking) and implement the **Reservation Pattern**, where items are temporarily locked in a "pending" state before final checkout to ensure atomic decrements.

**AA9**: A **sidecar proxy** is a helper process running alongside an application container. In Istio, **Envoy** acts as the sidecar handling all network traffic. The **Data Plane** consists of these proxies; the **Control Plane** (Istiod) manages their configuration. mTLS between sidecars solves identity verification and encryption for every internal hop without requiring the application code to handle certificates/handshakes.

**AA10**: The **Strangler Fig pattern** involves incrementally replacing legacy functionality by wrapping it with new services. Strategy: 1) Place a routing layer (API Gateway) in front of the .NET Framework monolith. 2) Identify a specific bounded context (e.g., "Billing"). 3) Build the Billing service in .NET 8. 4) Route only billing-related requests to the new service via the gateway. 5) Repeat until the monolith is empty and can be decommissioned.

**AA11**: The **12-Factor App** methodology optimizes apps for cloud deployment. Factors include: 1) Single codebase, 2) Explicit dependencies, 3) Config in environment variables, 4) Backing services treated as attached resources, 5) Build $\rightarrow$ Release $\rightarrow$ Run separation, 6) Stateless processes. These matter because they ensure portability across environments and enable horizontal scaling.

**AA12**: 
*   **Coupling**: Kafka (Loose - producer doesn't know consumer); REST (Tight).
*   **Scalability**: Kafka (High throughput async); REST (Request-response latency limited).
*   **Debugging**: REST (Easier trace); Kafka (Harder; requires event tracking).
*   **Ordering**: Kafka (Guaranteed per partition); REST (No inherent order).
*   **Failure**: REST (Immediate error); Kafka (Consumer retries from offset).
Choose Kafka for high-volume data streams/event sourcing; choose REST/gRPC for low-latency synchronous APIs.

**AA13**: A **load balancer** distributes traffic across multiple servers. **Layer 4** operates at the transport layer (TCP/UDP), routing based on IP and port. **Layer 7** operates at the application layer, routing based on HTTP headers or URL paths. Use case for L7: Routing `/api/users` to one service and `/api/orders` to another.

**AA14**: A **message queue** allows asynchronous communication between services. **RabbitMQ** is a traditional queue where messages are pushed to consumers and deleted after acknowledgment. **Kafka** is a distributed log where messages persist and consumers pull data by tracking their "offset." Pick RabbitMQ for simple task queues; pick Kafka for real-time stream processing or when you need to replay historical events.

**AA15**: A **container** shares the host OS kernel and isolates processes via namespaces/cgroups. A **VM** includes a full guest OS running on a hypervisor. Containers are popular for microservices because they start in seconds, use fewer resources, and ensure environment parity from dev to prod.

**AA16**: **Stateless** services store no client session data locally (e.g., an API that reads all state from a DB). **Stateful** services remember previous interactions (e.g., a database or a WebSocket server). Stateless services scale horizontally easily because any instance can handle any request without needing shared memory or sticky sessions.

**AA17**: An **ORM** maps database tables to language objects. Examples: Hibernate (Java), Entity Framework (.NET). Trade-offs: ORMs increase developer productivity and prevent SQL injection but can produce inefficient queries ("N+1 problem") compared to raw SQL's precision and performance.

**AA18**: The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, others continue to function. Implementation: Use separate thread pools for different service clients (so a slow "Payment" service doesn't exhaust threads needed for "Catalog"). Alternatively, deploy critical paths on separate hardware clusters.

**AA19**: **OT** relies on a central server to transform operations to maintain consistency; **CRDTs** use mathematically mergeable data types where conflicts are resolved automatically by the logic itself. CRDTs provide eventual consistency with lower latency and better offline support because they don't require a central coordinator to resolve merges. I would choose **CRDTs** for offline editing.

**AA20**: Challenges include maintaining trace IDs across polyglot boundaries. **Context propagation** uses headers (W3C Trace Context) to pass `traceId` between services. **Head-based sampling** decides at the start of the request whether to trace; **tail-based** decides after completion based on errors/latency. For Kafka continuity, inject the trace context into the message header during production and extract it in the consumer to link the asynchronous spans.

## On-Premise Infrastructure Architecture

**OP1**: **Type 1** runs directly on bare metal (e.g., VMware ESXi, Microsoft Hyper-V). **Type 2** runs as an application on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2**: **SAN (Storage Area Network)** provides block-level access (iSCSI, Fibre Channel); used for high-performance DBs or VM disks. **NAS (Network Attached Storage)** provides file-level access (NFS, SMB); used for shared folders and general file storage.

**OP3**: **3-Tier** consists of Core $\rightarrow$ Distribution $\rightarrow$ Access layers. **Leaf-Spine** is a two-tier architecture where every leaf switch connects to every spine switch. It solves the bottleneck of Spanning Tree Protocol (STP) and optimizes "East-West" traffic (server-to-server), which is dominant in modern virtualized data centers.

**OP4**: Cluster: $\ge 3$ nodes for quorum. Quorum ensures only one partition can make decisions. Fencing (**STONITH**) uses IPMI/iLO to hard-reboot failing nodes to prevent split-brain. Shared storage options include Ceph (distributed) or iSCSI (central array). On failure: The cluster detects loss of heartbeat $\rightarrow$ fences the node $\rightarrow$ restarts VMs on healthy nodes using the shared disk image.

**OP5**: **VLAN Trunking** allows multiple VLANs to traverse a single physical link via **802.1Q tagging**, adding a tag to each frame identifying its VLAN. In Linux, this is configured by creating tagged sub-interfaces (e.g., `ip link add link eth0 name eth0.10 type vlan id 10`).

**OP6**: RAID 1 (Mirror), RAID 5 (Parity - 1 drive fail), RAID 6 (Double parity - 2 drive fail), RAID 10 (Striped mirrors), ZFS RAIDZ2 (similar to R6 but avoids write holes). For a DB server with 6 drives: **RAID 10**. It provides the best balance of high IOPS (performance) and fault tolerance without the parity calculation overhead of RAID 5/6.

**OP7**: Architecture: Internal AD servers act as recursive resolvers for clients. Split-horizon DNS ensures internal users get private IPs while external users get public IPs for the same hostname. External zones use DNSSEC for authenticity. When a laptop moves to VPN, conditional forwarding sends requests for `.internal` domains to the corporate DNS servers over the tunnel.

**OP8**: Chain: Root CA $\rightarrow$ Subordinate CA $\rightarrow$ End Entity. The root stays offline; subordinates issue certificates. CRLs are lists of revoked certs; OCSP provides real-time status checks. A compromised subordinate requires revoking that specific branch's certificates; a compromised root destroys all trust in the entire PKI hierarchy.

**OP9**: MPLS (High cost, guaranteed QoS), IPsec VPN (Low cost, internet jitter), SD-WAN (Dynamic path selection), WireGuard Mesh (Fast, modern encryption). Recommendation for VoIP: **SD-WAN**, as it allows prioritizing voice traffic (QoS) across multiple paths (MPLS + Internet) to ensure low latency.

**OP10**: Out-of-band management (**iDRAC/iLO**) is a dedicated hardware chip allowing remote power and console access regardless of OS state. If exposed to the internet, an attacker can gain full BIOS/OS control or wipe the server remotely.

**OP11**: **LVM** manages logical volumes on disks. **LVM-Thin** allows overprovisioning by allocating space only when written. **ZFS** is a combined filesystem and volume manager with Copy-on-Write (CoW). Snapshots: LVM uses block snapshots; Thin uses pointer-based snapshots; ZFS uses near-instant CoW snapshots.

**OP12**: Design: Use Ceph with CRUSH rules ensuring replicas are spread across sites. Monitor placement must be odd ($\ge 3$) across both sites plus a third "tiebreaker" site. A 2-site Ceph cluster without a tiebreaker risks total loss of quorum if one site fails, meaning neither side can safely write data.

**OP13**: DHCP DORA process: **Discover** (Client $\rightarrow$ All), **Offer** (Server $\rightarrow$ Client), **Request** (Client $\rightarrow$ Server), **Acknowledge** (Server $\rightarrow$ Client). When the server is unavailable after lease expiry, Windows clients assign themselves an APIPA address (`169.254.x.x`).

**OP14**: An **unmanaged switch** is plug-and-play with no configuration. A **managed switch** provides VLANs, STP to prevent loops, Port Mirroring for monitoring, and SNMP for remote management—all critical for security and troubleshooting in enterprises.

**OP15**: **NTP** synchronizes clocks via UDP. Accurate time is critical for Kerberos authentication (which fails if drift $> 5\text{min}$), log correlation during forensics, and database replication consistency. Drift causes "clock skew," leading to auth failures or corrupted transaction orders.

**OP16**: Physical (Bare metal) vs VM (Hypervisor abstraction) vs Container (OS kernel sharing). Run on bare metal when you need maximum IOPS, direct hardware access (GPU/FPGA), or have workloads where hypervisor overhead creates unacceptable latency.

**OP17**: **UPS** provides immediate battery power; a **generator** provides long-term fuel-based power. You need both because generators take seconds/minutes to start; the UPS bridges that gap. The **ATS** automatically switches from utility power to generator power.

**OP18**: Active-Passive: One node works, one waits. Active-Active: Both process traffic. For PostgreSQL HA: Use **Pacemaker** as the cluster manager and **Corosync** for membership. A Virtual IP (VIP) floats between nodes. If the primary fails, Pacemaker uses STONITH to fence the old primary and promotes the standby.

**OP19**: Strategy: **3-2-1 rule** (3 copies, 2 media types, 1 offsite). RPO defines acceptable data loss; RTO defines downtime limit. Use incremental backups daily and fulls weekly. Immutable backups use WORM storage or S3 Object Lock to prevent ransomware encryption. Backup is recovering specific files; DR is restoring an entire site's functionality.

**OP20**: 802.1X involves the **Supplicant** (client device), **Authenticator** (switch), and **Auth Server** (RADIUS). EAP-TLS uses certificates; PEAP uses credentials. RADIUS assigns a dynamic VLAN based on user identity. Devices without 802.1X support (printers) use **MAB**, where the switch allows access based solely on the MAC address.
