## Kubernetes

**K1 — Easy:** A **Deployment** is used for stateless applications where pods are interchangeable; it manages replicas and rolling updates. A **StatefulSet** is for stateful applications (e.g., databases) providing stable network identifiers (pod-0, pod-1) and persistent storage mapping that persists across rescheduling.

**K2 — Easy:** A ClusterIP service provides a virtual IP. `kube-proxy` (via iptables or IPVS) intercepts traffic sent to this VIP and load-balances it across the Pod IPs listed in the Service's **Endpoints** object.

**K3 — Medium:** 
- **PersistentVolume (PV):** The actual piece of storage (the "disk").
- **PersistentVolumeClaim (PVC):** A request by a user for storage (the "ticket").
- **StorageClass (SC):** A template/profile that allows dynamic provisioning of PVs based on PVC requests.
*Relation:* A PVC asks for resources from an SC $\rightarrow$ the SC provisions a PV $\rightarrow$ the PVC binds to that PV.

**K4 — Medium:** 
1. `kubectl logs <pod>`: Check application crash logs/stack traces.
2. `kubectl describe pod <pod>`: Look at the "Events" section for OOMKill, failed probes, or image pull errors.
3. Check Liveness/Readiness probe configurations (too aggressive?).
4. Verify resource limits vs. actual usage (is it hitting memory limits immediately?).

**K5 — Medium:** CoreDNS provides internal service discovery ($\text{service.namespace.svc.cluster.local}$). If CoreDNS pods are down, DNS resolution fails; pods cannot find other services by name, effectively breaking most inter-service communication.

**K6 — Hard:** The scheduler uses two main phases:
1. **Filtering (Predicates):** Eliminates nodes that can't host the pod (e.g., insufficient CPU/RAM, Taints without Tolerations).
2. **Scoring (Priorities):** Ranks remaining nodes using weights.
*Factors considered:* Resource availability (LeastRequestedPriority), Image locality (preferring nodes where images already exist), and Node Affinity rules.

**K7 — Hard:** Yes, it will be scheduled. Available RAM is $4\text{GB} - 3.5\text{GB} = 500\text{MB}$. Since requests.memory ($256\text{Mi}$) $\approx 262\text{MB}$, there is enough room. However, if it uses $600\text{Mi}$ at runtime, it exceeds its limit of $512\text{Mi}$ and will be **OOMKilled**.

**K8 — Hard:** External LB $\rightarrow$ Ingress Controller Pod (NGINX) $\rightarrow$ NGINX reads Ingress Rules $\rightarrow$ Maps request to a Service $\rightarrow$ Looks up associated Endpoints (Pod IPs) $\rightarrow$ `kube-proxy`/iptables routes traffic directly to the specific Application Pod IP.

**K9 — Medium:** A NetworkPolicy is an L3/L4 firewall for pods. By default, all pods in a namespace are "non-isolated" (all traffic allowed). Once a NetworkPolicy selects a pod, that pod becomes isolated; only traffic explicitly permitted by the policy is allowed; everything else is denied.

**K10 — Medium:** **RollingUpdate** replaces pods gradually to ensure zero downtime. **Recreate** kills all existing pods before starting new ones. Choose Recreate when the application cannot handle two different versions running simultaneously (e.g., during a breaking database schema migration).

**K11 — Easy:** A namespace provides a mechanism to isolate groups of resources within a single cluster. Default namespaces: `default`, `kube-system` (cluster internals), and `kube-public`.

**K12 — Easy:** Used for detailed debugging. It shows information not found in `get`: 
1. Lifecycle Events (Warning/Normal messages).
2. Container status details (Restart counts, Exit codes).
3. Volume mount paths and Resource limits.

**K13 — Easy:** A ConfigMap stores non-confidential configuration data. Consumption methods:
1. Injected as environment variables.
2. Mounted as files in a volume.

**K14 — Easy:** 
- **ClusterIP:** Internal IP only; accessible only inside the cluster.
- **NodePort:** Exposes service on a static port across every Node's IP.
- **LoadBalancer:** Provisions a cloud provider LB that routes traffic to a NodePort $\rightarrow$ ClusterIP.

**K15 — Easy:** A DaemonSet ensures one copy of a pod runs on all (or selected) nodes. Use it instead of a Deployment for infrastructure agents like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium:** 
- **Taints/Tolerations:** Taints are applied to *nodes* to repel pods. Tolerations are applied to *pods* to allow them onto tainted nodes. Case: GPU nodes (tainted so only GPU-enabled pods land there).
- **Affinity:** Pods "prefer" certain nodes based on labels. Case: Database pods preferring SSD-backed nodes.

**K17 — Medium:** An Operator is a custom controller using Custom Resource Definitions (CRDs) to automate complex, stateful applications. Unlike standard controllers (which manage generic objects), Operators encode human operational knowledge (e.g., how to perform a DB backup or scale a cluster) into code.

**K18 — Hard:** etcd uses the Raft consensus algorithm (Strong Consistency). If quorum ($n/2 + 1$) is lost, the cluster becomes read-only or unavailable. To recover from losing 2 out of 3 nodes, you must restore the remaining node from a snapshot and reconfigure it as a single-node cluster before adding new members.

**K19 — Hard:** RBAC maps Subjects $\rightarrow$ RoleBindings $\rightarrow$ Roles. `Role` is namespace-scoped; `ClusterRole` is global. `RoleBinding` grants permissions within a namespace; `ClusterRoleBinding` grants them globally.

```yaml
# Read-only access for developer in 'dev' namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""] # core group
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
- kind: User
  name: "developer-user"
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard:** By default, Kubernetes pods have an `ndots` value of 5. For external domains (e.g., `google.com`), the resolver tries several internal search paths first ($\text{google.com.ns.svc...}$, $\text{google.com.svc...}$) before trying the absolute domain. This causes multiple failed queries per request. Fix via `dnsConfig`:
```yaml
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "1"
```

## Development

**D1 — Easy:** **Merge** creates a new commit combining two branches, preserving history exactly as it happened. **Rebase** rewrites history by moving commits to a new base, creating a linear timeline. Avoid rebasing public/shared branches because it alters commit IDs and disrupts other developers' histories.

**D2 — Easy:** **TCP** is connection-oriented and reliable (guarantees delivery). Protocols: HTTP, SSH. **UDP** is connectionless and fast (no guarantee of delivery). Protocols: DNS, VoIP.

**D3 — Medium:** A race condition occurs when the outcome depends on the non-deterministic timing or order of execution of multiple threads accessing shared data. *Example:* Two threads incrementing a global variable `count++` simultaneously; both read 10, both add 1, both write back 11, losing one increment.

**D4 — Medium:** **Symmetric:** One key for encryption and decryption. **Asymmetric:** Public key encrypts, private key decrypts. In TLS: Asymmetric encryption is used during the handshake to securely exchange a symmetric session key, which is then used for bulk data transfer due to its speed.

**D5 — Medium:** An image layer is a read-only filesystem change recorded in the Dockerfile. Caching works from top down; if a layer changes, all subsequent layers are invalidated. Best practice: Put stable instructions (OS install) at the top and frequently changing code (`COPY . .`) at the bottom.

**D6 — Medium:**
1. Check Load Balancer/Ingress logs (is it reaching the pod?).
2. Check Pod health/CPU/Memory usage (resource exhaustion?).
3. Check downstream dependencies (DB latency or timeouts?).
4. Check connection pool limits (exhausted DB connections?).

**D7 — Hard:** CAP Theorem states you can only have two of Consistency, Availability, and Partition Tolerance. 
- **CP (Consistency):** MongoDB/HBase (refuses requests if consistency cannot be guaranteed).
- **AP (Availability):** Cassandra/DynamoDB (returns the best available version of data even if not perfectly consistent).

**D8 — Medium:** **Horizontal scaling** adds more instances (nodes); **Vertical scaling** increases resources (RAM/CPU) on one instance. Horizontal scaling is enabled by statelessness, load balancing, and database sharding.

**D9 — Easy:** An environment variable is a dynamic value stored by the OS used by processes. To persist across sessions on Linux, add `export VAR_NAME="value"` to `~/.bashrc` or `/etc/environment`.

**D10 — Easy:** JSON is a strict, machine-optimized format; YAML is a human-readable superset of JSON. Advantage: JSON has universal parser support; YAML supports comments and complex nesting with less syntax noise.

**D11 — Easy:** A REST API is an architectural style for network applications using HTTP. 
- **GET:** Retrieve resource.
- **POST:** Create new resource.
- **PUT:** Update/Replace existing resource.
- **DELETE:** Remove resource.

**D12 — Easy:** Version pinning specifies exact versions of dependencies (e.g., `requests==2.25.1`). It ensures reproducible builds so that a project doesn't break when a dependency releases a breaking update.

**D13 — Easy:** **Compiled** languages are translated to machine code before execution (C++, Rust). **Interpreted** languages are read line-by-line at runtime (Python, JavaScript).

**D14 — Medium:** A **forward proxy** acts on behalf of clients (hides client identity). A **reverse proxy** acts on behalf of servers (protects server identity). Examples: Nginx (load balancing), HAProxy (high availability/SSL termination).

**D15 — Medium:** A deadlock is a state where two or more processes are unable to proceed because each is waiting for the other to release a resource. Coffman conditions: 1. Mutual Exclusion, 2. Hold and Wait, 3. No Preemption, 4. Circular Wait.

**D16 — Hard:** Eventual consistency means all replicas will eventually converge to the same value if no new updates occur. Cassandra handles this via tunable consistency levels ($R+W > N$). Levels include `ONE` (fastest, least consistent) and `QUORUM` (majority agreement).

**D17 — Hard:** mTLS requires both client and server to present certificates. Handshake: Server sends cert $\rightarrow$ Client verifies it against CA $\rightarrow$ Client sends its own cert $\rightarrow$ Server verifies it against CA $\rightarrow$ Both derive a symmetric session key. Commonly used in Service Meshes (Istio) for zero-trust networking.

**D18 — Hard:** Hash tables use a hash function to map keys to array indices. Collision resolution: **Chaining** (linked lists at index) or **Open Addressing** (probing for next empty slot).
*Complexity:* Average $O(1)$ for insertion/lookup/deletion; Worst case $O(n)$ when many collisions occur.

**D19 — Hard:** A circuit breaker prevents cascading failures by stopping requests to a failing service. States: **Closed** (normal), **Open** (fail fast immediately), **Half-Open** (test with few requests). It relates to retry policies by ensuring retries don't overwhelm a struggling system (using exponential backoff).

**D20 — Hard:** 
- **Optimistic:** Assume no conflict; check version/timestamp at commit time. Use for low contention (e.g., row versioning `WHERE version = x`).
- **Pessimistic:** Lock the resource immediately. Use for high contention/critical data (e.g., `SELECT FOR UPDATE` in SQL).
