## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry run that compares the current state with the desired configuration and shows what changes will be made. `tofu apply` actually executes those changes to reach the desired state.

**T2 — Easy:** State is a JSON file mapping your code's resource addresses to real-world cloud IDs. Remote state stores this file in a shared location (S3, Consul, etc.), which is critical for team collaboration, preventing state conflicts via locking, and ensuring a single source of truth.

**T3 — Medium:** `count` creates resources based on an integer index; `for_each` uses a map or set. `for_each` is preferred because removing an item from the middle of a `count` list causes a shift in indices, leading to unnecessary destruction/recreation of subsequent resources. `for_each` identifies resources by unique keys, avoiding this issue.

**T4 — Medium:** This is called "drift." During the next `plan`, OpenTofu refreshes the state by querying the cloud API. It detects the difference between the actual state and the stored state. By default, it will propose changing the resource back to match the configuration defined in the code.

**T5 — Medium:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-xxxxxx"
  instance_type = "t3.micro"
  tags = { Name = each.value }
}
```

**T6 — Hard:** `terraform_remote_state` reads the entire state file of another project, which can be slow and exposes too much data. Output values are specific exported variables. The recommended alternative is using **Provider Data Sources** (e.g., fetching a VPC ID via `data "aws_vpc"`) or a shared Key-Value store. This decouples modules and reduces dependency on raw state files.

**T7 — Hard:** Provisioners run during the creation phase; outputs are evaluated after resources are created. If an output depends on a value generated *inside* a `remote-exec` script, that value isn't available until the apply finishes. **Fix:** Use a separate resource for the logic (like a cloud-init script) or use a `null_resource` with a trigger, ensuring the dependent resource uses a `data` source to fetch the kubeconfig from the disk/API rather than relying on a Tofu output variable.

**T8 — Medium:** `tofu import` maps existing infrastructure into the state file. Its limitation is that it doesn't generate the HCL code; you must write the code manually first. The `import` block (1.5+) allows declarative imports in code, allowing you to `plan` the import and see exactly how the state will change before committing.

**T9 — Easy:** A variable is an input parameter used to make configurations reusable. An output is a return value exported by a module for visibility or for use by other modules.

**T10 — Easy:** A provider is a plugin that translates OpenTofu code into API calls for a specific platform (e.g., AWS, Azure). Running `plan` without `init` fails because the necessary provider binaries have not been downloaded to the `.terraform` directory.

**T11 — Easy:** It is a dependency lock file that records the exact versions and hashes of providers used. Committing it ensures every team member and CI pipeline uses identical provider versions, preventing "it works on my machine" bugs.

**T12 — Easy:** `tofu destroy` deletes all resources managed by the current state. To target one resource: `tofu destroy -target=aws_instance.web[0]`.

**T13 — Easy:** A data source fetches information from an existing resource not managed by the current project. Example: Using a data source to find the latest Amazon Linux 2 AMI ID instead of hardcoding a static ID.

**T14 — Medium:** Variables are inputs provided at runtime; locals are internal constants or computed values defined within the module. Use locals to avoid repeating complex expressions or to simplify logic that doesn't need to be changed by the user.

**T15 — Medium:**
- `create_before_destroy`: Creates the new resource before deleting the old one (prevents downtime for critical services).
- `prevent_destroy`: Errors out if a destroy is attempted (safety for databases).
- `ignore_changes`: Ignores drift for specific attributes (e.g., ignoring tags updated by an external auto-scaling group).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource has been renamed or moved into a module without changing its physical existence in the cloud. This prevents Tofu from destroying and recreating the resource during refactoring.

**T17 — Hard:** The dependency graph is a Directed Acyclic Graph (DAG). **Implicit dependencies** occur when one resource references another's attribute. **Explicit dependencies** use `depends_on`. `depends_on` forces sequential execution, reducing parallelism. It should be used sparingly because it can create bottlenecks and hide architectural flaws.

**T18 — Hard:** 
1. **State Splitting:** Break one giant state into smaller, layered states (Network $\rightarrow$ App $\rightarrow$ DB). Tradeoff: More complex orchestration.
2. **`-refresh=false`**: Skip refreshing every single resource. Tradeoff: Risk of acting on stale data.
3. **Targeting**: Use `-target` for specific changes. Tradeoff: Can lead to inconsistent state over time.
4. **Reduce Data Sources**: Minimize expensive API calls in the root module. Tradeoff: Less dynamic configuration.

**T19 — Hard:** State locking prevents concurrent writes by placing a lock (e.g., in DynamoDB). If a crash occurs, the lock persists. You manually break it using `tofu state force-unlock <lock-id>`. The risk is that if you unlock while someone else *is* actually applying, you will corrupt the state file.

**T20 — Hard:** 
1. Update the `backend` block from `local` to `s3` with DynamoDB config.
2. Run `tofu init`. OpenTofu detects the change and prompts to migrate existing local state to S3.
3. Type `yes` to confirm migration.
4. Verify via `tofu state list` to ensure all resources are present and check the S3 bucket for the `.tfstate` file.

## Ansible

**A1 — Easy:** A **task** is a single unit of work (one module call). A **role** is a structured bundle of tasks, variables, and handlers. A **playbook** is the top-level YAML file that maps hosts to roles/tasks.

**A2 — Easy:** `ansible_facts` is a dictionary containing system information gathered at start. Access OS family via `{{ ansible_distribution_family }}` or `{{ ansible_os_family }}`.

**A3 — Medium:** 
- `command`: Executes a binary; safest as it doesn't process through a shell (no pipes/wildcards).
- `shell`: Runs through `/bin/sh`; allows pipes, redirects, and environment variables.
- `raw`: Bypasses Python on target; used for bootstrapping nodes without Python installed.

**A4 — Medium:** Idempotency means running a task multiple times results in the same state without changing anything after the first run. 
- **Idempotent:** `apt: name=nginx state=present`.
- **NOT Idempotent:** `shell: echo "config" >> /etc/myapp.conf` (appends every time).

**A5 — Medium:**
```yaml
- name: Install htop based on OS
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
  when: ansible_os_family == 'Debian'

- name: Install EPEL and htop for RedHat
  package:
    name: "{{ item }}"
  loop: ["epel-release", "htop"]
  when: ansible_os_family == 'RedHat'
```

**A6 — Hard:** Precedence (lowest to highest): Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ Playbook vars $\rightarrow$ Extra vars (`-e`). `set_fact` is highly prioritized as it happens during runtime.

**A7 — Hard:** Use `serial: 3` in the play header to process only 3 nodes at a time. To ensure they complete before others, use separate plays or an inventory group for the first 3, then a second play for the rest using `wait_for` to check that the RKE2 API port (6443) is open on those first 3 nodes.

**A8 — Medium:** `ansible-vault encrypt_string 'mysecretvalue'` allows you to encrypt just one value. You can then place this encrypted string directly into a plain YAML file.

**A9 — Easy:** An inventory lists target hosts. **Static** inventories are text/INI files; **Dynamic** inventories are scripts or plugins that query cloud APIs (AWS, GCP) to generate host lists in real-time.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A handler is a special task triggered by a `notify` keyword. It runs once at the end of the play if any task notified it changed something. Regular tasks run every time based on order.

**A12 — Easy:** `ansible.cfg` configures global behavior. Common settings: `remote_user`, `forks` (parallelism), and `host_key_checking = False`.

**A13 — Easy:** `register` captures the output of a task into a variable. Use it later with a conditional:
```yaml
- shell: uptime
  register: uptime_result
- debug: msg="{{ uptime_result.stdout }}"
```

**A14 — Medium:** `import_tasks` is static (processed during parsing); `include_tasks` is dynamic (evaluated at runtime). Use `include_tasks` when you need conditionals (`when`) to decide whether to load the file.

**A15 — Medium:** Ansible Galaxy is a community hub for roles/collections. Install via `ansible-galaxy install -r requirements.yml`, where the YAML lists the role names and versions.

**A16 — Medium:** 
- `ssh`: Standard remote execution over SSH.
- `local`: Runs tasks on the control node itself.
- `network_cli`: Specialized for network devices that don't support full Python shells, maintaining a persistent connection.

**A17 — Hard:** `delegate_to` runs a task on a different host than the current target; `run_once` executes only once per batch. **Example:** To update a Load Balancer API from localhost using an IP gathered from a remote server:
```yaml
- name: Register node in LB
  uri: url="http://lb/api" method=POST body="ip={{ ansible_default_ipv4.address }}"
  delegate_to: localhost
  run_once: true # Only one call needed if logic allows, or remove run_once to do it per node
```

**A18 — Hard:** 
1. **Forks**: Increase `forks = 50` in `ansible.cfg` (increases parallelism). Tradeoff: Higher CPU/RAM load on control node.
2. **Pipelining**: Enable `pipelining = True` to reduce SSH round trips. Tradeoff: Requires specific sudo settings.
3. **Fact Caching**: Use Redis or JSON file caching for facts. Tradeoff: Stale data risk.
4. **Mitogen**: A third-party plugin that optimizes execution. Tradeoff: Compatibility issues with some modules.

**A19 — Hard:** `{{ }}` is for expressions/variables; `{% %}` is for control flow (loops/ifs); `{# #}` are comments.
```jinja2
upstream backend {
  {% for server in backend_servers %}
    # Health check enabled for {{ server }}
    server {{ server }};
  {% endfor %}
}
```

**A20 — Hard:** 
1. Set `serial: 20%` (or a fixed number) for rolling batches.
2. **Pre-task**: Task using `uri` module to remove the host from LB.
3. **Update**: Deploy app code and restart service.
4. **Health Check**: Loop with `uri` module checking `/health` endpoint until 200 OK.
5. **Post-task**: Re-add host to LB.
6. **Rollback**: Wrap update tasks in a `block`. In the `rescue` section, trigger a rollback play or revert version and notify admin.
