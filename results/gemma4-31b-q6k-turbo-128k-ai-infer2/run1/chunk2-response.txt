## Kubernetes

**K1 — Easy:** A **Deployment** manages stateless pods where any pod can replace another without loss of state. A **StatefulSet** manages pods with unique, persistent identities (stable network IDs and dedicated storage per pod), ensuring ordered deployment and scaling.

**K2 — Easy:** A ClusterIP service provides a stable virtual IP. Traffic sent to this IP is intercepted by `kube-proxy` (via iptables or IPVS rules), which load-balances the traffic across the set of healthy Pods associated with the Service's selector (the Endpoints list).

**K3 — Medium:** 
- **PersistentVolume (PV):** The actual piece of storage in the cluster (e.g., an AWS EBS volume).
- **PersistentVolumeClaim (PVC):** A user's request for storage (size, access mode).
- **StorageClass (SC):** A "template" used for dynamic provisioning.
**Relation:** A PVC requests storage from a StorageClass $\rightarrow$ SC automatically provisions a PV $\rightarrow$ PVC binds to that PV.

**K4 — Medium:**
1. `kubectl logs <pod>`: Check application crash logs/stack traces.
2. `kubectl describe pod <pod>`: Look at the "Events" section for OOMKill, failed probes, or image pull errors.
3. Check Resource Limits: Verify if memory limits are too low causing OOMKilled.
4. Validate Probes: Ensure liveness/readiness probe thresholds aren't too aggressive.

**K5 — Medium:** CoreDNS provides service discovery via DNS names (e.g., `my-svc.namespace.svc.cluster.local`). If CoreDNS pods are down, internal service resolution fails; pods cannot find other services by name and must use IP addresses directly.

**K6 — Hard:** 
The scheduler uses two main phases:
1. **Filtering (Predicates):** Removes nodes that don't meet requirements (e.g., insufficient CPU/RAM, taints without tolerations, node selectors).
2. **Scoring (Priorities):** Ranks remaining nodes based on factors like resource balance (least requested), image locality (image already exists on node), and affinity rules.
**Factors considered:** Requested resources vs available capacity, Taints/Tolerations, Pod Anti-Affinity.

**K7 — Hard:** 
**Scheduling:** Yes. Scheduling is based on *requests*. $3.5\text{GB} + 256\text{Mi}$ fits within the $4\text{GB}$ limit.
**Runtime:** The pod will be **OOMKilled**. Kubernetes enforces memory limits strictly; if a process exceeds its `limits.memory` ($512\text{Mi}$), the kernel kills it immediately.

**K8 — Hard:** 
External LB $\rightarrow$ Ingress Controller (NGINX) $\rightarrow$ NGINX evaluates Host/Path rules $\rightarrow$ Maps request to a Service $\rightarrow$ Looks up the Service's Endpoints (Pod IPs) $\rightarrow$ Traffic routed via kube-proxy/iptables directly to the Application Pod IP.

**K9 — Medium:** A NetworkPolicy is an L3/L4 firewall for pods. By default, all traffic is allowed. Once a NetworkPolicy selects a pod, that pod becomes "isolated"; only traffic explicitly permitted by the policy is allowed; everything else is denied.

**K10 — Medium:** 
- **RollingUpdate:** Gradually replaces old pods with new ones (zero downtime).
- **Recreate:** Kills all existing pods before starting new ones.
**Choose Recreate when:** You cannot have two versions of the app running simultaneously (e.g., during a database schema migration that isn't backward compatible).

**K11 — Easy:** A namespace provides a scope for names and a mechanism to divide cluster resources between multiple users/teams. Default namespaces: `default`, `kube-system` (cluster components), `kube-public`.

**K12 — Easy:** Used for detailed debugging. It shows:
1. **Events:** Recent lifecycle events (pulling image, scheduling failures).
2. **Container Status:** Exit codes and restart counts.
3. **Resource Limits/Requests:** The actual configured constraints.

**K13 — Easy:** A ConfigMap stores non-confidential configuration data in key-value pairs. Consumption methods:
1. Mounted as files in a volume.
2. Injected as environment variables.

**K14 — Easy:** 
- **ClusterIP:** Internal only.
- **NodePort:** Exposes service on a static port on every Node IP.
- **LoadBalancer:** Provisions an external cloud LB that routes traffic to NodePorts.

**K15 — Easy:** A DaemonSet ensures one copy of a pod runs on all (or selected) nodes. Use case: Log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium:** 
- **Taints/Tolerations:** Taints are applied to *nodes* to repel pods; Tolerations are applied to *pods* to allow them onto tainted nodes. Case: GPU node taints so only GPU-enabled pods land there.
- **Affinity:** Pods "prefer" or "require" certain nodes based on labels. Case: Spreading replicas across different availability zones for high availability.

**K17 — Medium:** An Operator is a custom controller using Custom Resource Definitions (CRDs) to automate complex, stateful applications. It differs from standard controllers by encoding domain-specific operational knowledge (e.g., how to perform a database backup or version upgrade automatically).

**K18 — Hard:** etcd uses the Raft consensus algorithm (Strong Consistency). If quorum ($n/2 + 1$) is lost, the cluster becomes read-only or unavailable. To recover if 2 of 3 nodes are permanently lost, you must restore from a snapshot to a new single-node cluster and then re-scale the membership.

**K19 — Hard:** RBAC defines who can do what in the cluster. `Role` (namespace scope), `ClusterRole` (cluster wide), `RoleBinding` (links user to Role), `ClusterRoleBinding` (links user to ClusterRole).
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: dev, name: pod-reader }
rules: [{ apiGroups: [""], resources: ["pods", "pods/log"], verbs: ["get", "list", "watch"] }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: dev, name: read-pods-binding }
subjects: [{ kind: User, name: developer-user }]
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
```

**K20 — Hard:** The `ndots:5` default causes pods to try several search suffixes (e.g., `.default.svc.cluster.local`) before trying the absolute domain for external queries, causing multiple failed DNS lookups per request. 
**Fix:** Use `dnsConfig` in Pod spec:
```yaml
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "1"
```

## Development

**D1 — Easy:** **Merge** creates a new commit joining two histories; **Rebase** rewrites history by moving commits onto a new base. Avoid rebasing public branches as it changes commit hashes and disrupts other developers' local copies.

**D2 — Easy:** TCP is connection-oriented, reliable, and ensures ordered delivery (HTTP, SSH). UDP is connectionless, faster, but does not guarantee delivery or order (DNS, VoIP/Streaming).

**D3 — Medium:** A race condition occurs when the outcome of a program depends on the non-deterministic timing of events (usually multi-threading). Example: Two threads incrementing a shared variable `count++` without a lock; both read `1`, both add `1`, and write back `2` instead of `3`.

**D4 — Medium:** Symmetric uses one key for encryption/decryption (AES); Asymmetric uses a Public Key to encrypt and a Private Key to decrypt (RSA). In TLS, asymmetric encryption is used during the handshake to securely exchange a symmetric session key, which is then used for bulk data transfer due to its speed.

**D5 — Medium:** An image layer is a read-only filesystem snapshot created by each instruction in a Dockerfile. Caching works from top down; if a layer changes, all subsequent layers are invalidated. **Best practice:** Put stable instructions (OS install) at the top and frequently changing code at the bottom.

**D6 — Medium:** 
1. Check Application Logs: Look for timeouts or dependency errors.
2. Health Checks: Verify if pods are restarting or failing liveness probes.
3. Downstream Dependencies: Check if the database or external APIs are slow/down.
4. Resource Saturation: Monitor CPU/RAM usage for spikes causing request queuing.

**D7 — Hard:** CAP Theorem states you can only have two of Consistency, Availability, and Partition Tolerance. 
- **CP (Consistency/Partition):** MongoDB/HBase (stops writes if it cannot guarantee consistency during partition).
- **AP (Availability/Partition):** Cassandra/DynamoDB (allows reads/writes during partition, resolving conflicts later).

**D8 — Medium:** Horizontal scaling adds more instances (more nodes); Vertical scaling increases resources (CPU/RAM) on one instance. Patterns enabling horizontal scaling include statelessness, load balancing, and distributed caching (Redis).

**D9 — Easy:** An environment variable is a dynamic value stored by the OS used to configure software behavior. To persist on Linux: add `export VAR_NAME=value` to `~/.bashrc` or `/etc/environment`.

**D10 — Easy:** JSON is a strict data format; YAML is a superset of JSON that allows indentation-based nesting and comments. Advantage JSON: Faster parsing/standardized. Advantage YAML: Much easier for humans to read and edit manually.

**D11 — Easy:** A REST API uses HTTP methods to manipulate resources. 
- **GET:** Retrieve resource.
- **POST:** Create new resource.
- **PUT:** Update/Replace existing resource.
- **DELETE:** Remove resource.

**D12 — Easy:** Version pinning specifies an exact version of a dependency (e.g., `requests==2.25.1`). This ensures reproducible builds so that CI/CD pipelines don't break when a library author releases a breaking update.

**D13 — Easy:** Compiled languages are translated to machine code before execution (C++, Rust); Interpreted languages are read line-by-line at runtime (Python, JavaScript).

**D14 — Medium:** A forward proxy represents the client; a reverse proxy represents the server. Reverse proxies provide load balancing, SSL termination, and caching. Examples: Nginx (web serving), HAProxy (high-performance load balancing).

**D15 — Medium:** A deadlock is a state where two or more processes are blocked forever, each waiting for the other to release a resource. Coffman conditions: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait.

**D16 — Hard:** Eventual consistency guarantees that if no new updates are made, all replicas will eventually converge to the same value. Cassandra handles this via "Tunable Consistency" using Quorum ($R+W > N$). Levels include ONE (fastest, least consistent) and ALL (slowest, most consistent).

**D17 — Hard:** mTLS requires both client and server to present X.509 certificates. Handshake: Server sends cert $\rightarrow$ Client verifies against CA $\rightarrow$ Client sends its own cert $\rightarrow$ Server verifies against CA $\rightarrow$ Symmetric key exchange. Commonly used in Service Meshes (Istio/Linkerd) for zero-trust networking.

**D18 — Hard:** Hash tables use a hash function to map keys to array indices. 
- **Collision Resolution:** Chaining (linked lists at index) or Open Addressing (probing for next empty slot).
- **Complexity:** Average $O(1)$ for insertion, lookup, deletion; Worst case $O(n)$ when many collisions occur.

**D19 — Hard:** A circuit breaker prevents cascading failures by stopping requests to a failing service. 
- **Closed:** Normal operation.
- **Open:** Fails fast immediately without calling the service.
- **Half-Open:** Periodically allows a few requests to check if the service recovered.
It complements retry policies by preventing "retry storms" via exponential backoff.

**D20 — Hard:** 
- **Optimistic:** Assumes no conflict; checks version/timestamp at commit time. Use for low contention. Example: Row versioning (`UPDATE ... WHERE version = 5`).
- **Pessimistic:** Locks resource immediately. Use for high contention. Example: `SELECT FOR UPDATE` in SQL which locks rows until transaction ends.
