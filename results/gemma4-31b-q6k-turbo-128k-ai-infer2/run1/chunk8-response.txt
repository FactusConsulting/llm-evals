## Cloud Infrastructure Architecture

**CL1**: **IaaS** provides raw compute/storage/network (e.g., AWS EC2); **PaaS** provides a platform to deploy apps without managing OS (e.g., Heroku or Azure App Service); **SaaS** delivers software over the web (e.g., Salesforce).

**CL2**: In **IaaS**, the provider manages hardware/virtualization; you manage the Guest OS, patches, and app. In **Managed K8s**, the provider manages the control plane; you manage worker nodes (usually) and pods. In **SaaS**, the provider manages everything except your data and configuration settings.

**CL3**: A **VPC** is an isolated virtual network. A **Subnet** is a range of IPs within that VPC. A **Security Group** is a stateful firewall at the instance level (allows return traffic automatically). A **NACL** is a stateless firewall at the subnet level (must explicitly define both inbound and outbound rules). Layering: $\text{VPC} \rightarrow \text{Subnet} \rightarrow \text{NACL} \rightarrow \text{SG}$.

**CL4**: A **Landing Zone** is a pre-configured multi-account environment. **OUs** group accounts for policy application. **Guardrails** (like SCPs) prevent prohibited actions globally. **Shared Networking** uses a Hub-and-Spoke model via Transit Gateway to centralize egress/ingress. **Centralized Logging** aggregates logs into one secure account. Single-account approaches are problematic due to blast radius (one compromise affects all), quota limits, and billing complexity.

**CL5**: IaC defines infrastructure in code. **Terraform/OpenTofu** use HCL; they are cloud-agnostic and industry standard. **Pulumi** allows general languages (Python/TS). **CloudFormation/Bicep** are provider-specific and deeply integrated. **Crossplane** manages infra as K8s resources. Choose Terraform for versatility, Pulumi for developer experience, or Bicep/CFn for deep native integration.

**CL6**: **HPA** scales pods based on CPU/RAM metrics. **VPA** adjusts the resource requests/limits of existing pods. **Cluster Autoscaler** adds/removes nodes from the cluster. **KEDA** provides event-driven scaling (e.g., scaling based on RabbitMQ queue length). Use KEDA over HPA when scaling depends on external events rather than internal pod metrics.

**CL7**: Strategy: Active-Active across two regions with async DB replication (to avoid latency) and Route53 health checks for DNS failover. 
*   **Pilot Light**: Core data is synced; app servers are off until needed.
*   **Warm Standby**: Scaled-down version of the app is always running.
*   **Multi-site Active-Active**: Full capacity in both regions serving traffic.
RPO (Recovery Point Objective) defines acceptable data loss; RTO (Recovery Time Objective) defines acceptable downtime. Cost increases linearly with readiness level.

**CL8**: GitOps uses a Git repo as the single source of truth. **ArgoCD** offers a powerful UI and pull-based sync; **FluxCD** is more lightweight and Kubernetes-native. Secrets are handled via **SealedSecrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault/AWS SM), or direct **Vault** integration. Manual drift is detected by the controller, which automatically overwrites manual changes to match the Git state.

**CL9**: Architecture: Use a **StatefulSet** for stable network IDs. Map **PVCs** to a **Local Storage Class** for low-latency disk access. A **Headless Service** allows pods to be reached individually. Use **Init Containers** for startup ordering/checks. Mount **ConfigMaps** as volumes at specific paths. Implement **Pod Disruption Budgets (PDB)** to ensure minimum available replicas during updates.

**CL10**: A **Service Account** is an identity for K8s processes. **Workload Identity/IRSA** maps that SA to a Cloud IAM Role using OIDC tokens. Mounting static credentials (JSON keys) is bad because they are long-lived and easily leaked. Workload identity provides short-lived, rotating tokens, reducing the attack surface.

**CL11**: **Object Store** (S3): Unstructured data, highly scalable, accessed via API. **Block Store** (EBS): Low latency, attached to one VM, behaves like a hard drive. **File Store** (EFS): Shared network mount across multiple VMs. Durability is typically $99.999999999\%$ (11 nines) for object storage; availability depends on regional replication settings.

**CL12**: Architecture: Deny-all default **Network Policies**, **mTLS** via Istio/Linkerd for encrypted pod-to-pod traffic, **Kyverno** for policy enforcement, **Cosign** for image signing, and **Falco** for runtime anomaly detection. Unlike perimeter security ("hard shell, soft center"), Zero Trust assumes the network is compromised and verifies every single request regardless of origin.

**CL13**: A CDN caches content at edge locations closer to users to reduce latency. Examples: AWS CloudFront, Azure Front Door. Use a CDN for static assets (images, JS, CSS) or global delivery; serve from origin for dynamic, personalized, or private data.

**CL14**: A **Region** is a geographic area containing multiple isolated **Availability Zones (AZs)**. Deploying across AZs protects against datacenter failure. **Zonal resources** exist in one AZ; **Regional resources** are replicated across multiple AZs by the provider.

**CL15**: Managed DBs handle hardware provisioning, OS patching, automated backups, and high-availability failover. Running on a VM requires you to manage all these manually, including manual backup scripts and complex clustering setups.

**CL16**: **Users** are individuals; **Groups** organize users; **Roles** are assumed identities for temporary access; **Policies** define permissions. The **Principle of Least Privilege** means granting only the minimum permissions required for a task. Apply this using granular IAM policies instead of broad "Admin" roles.

**CL17**: Serverless is event-driven compute where the provider manages scaling and allocation. Cold starts occur when a function wakes up after inactivity, causing initial latency. Poor fit for long-running processes (timeouts), apps with constant heavy load (expensive), or those requiring specialized hardware/OS kernels.

**CL18**: **Ingress** is the standard L7 resource; **Gateway API** is its successor providing better role separation and flexibility. Cloud annotations configure LB settings. Service Mesh gateways provide advanced traffic splitting. TLS termination usually happens at the Load Balancer or Ingress Controller. Use Gateway API for multi-tenant clusters or complex routing requirements.

**CL19**: Strategy: Move from On-Demand $\rightarrow$ **Savings Plans/RIs** for predictable loads; use **Spot instances** for stateless batch jobs. Implement **S3 Intelligent-Tiering** to move old data to Archive automatically. Right-size based on actual utilization metrics. FinOps process: Tagging resources $\rightarrow$ Cost visibility dashboards $\rightarrow$ Monthly review meetings. Showback reports costs per team; Chargeback bills them directly.

**CL20**: Architecture: Use **Kubernetes** as a common runtime across clouds. Use **Terraform** for portable IaC definitions. Connect via **VPN or Interconnect**. Federate identity using OIDC. Trade-off: You avoid vendor lock-in but lose "best-of-breed" native features by sticking to the lowest common denominator. Justified only for extreme regulatory mandates or critical availability needs where one cloud provider's total failure is an unacceptable risk.

## OT Infrastructure Architecture

**OT1**: The Purdue Model segments industrial networks into levels:
*   **Level 0 (Process)**: Sensors, actuators, motors.
*   **Level 1 (Basic Control)**: PLCs and PID controllers.
*   **Level 2 (Area Supervisory)**: HMIs and SCADA workstations.
*   **Level 3 (Site Operations)**: Historians and site-wide control.
*   **Level 4/5 (Enterprise)**: Corporate IT network and business systems.

**OT2**: IT focuses on Confidentiality ($\text{CIA}$); OT focuses on Availability and Safety ($\text{AS}$). Standard IT patching can cause unexpected reboots or crashes in legacy PLC firmware, which could lead to physical equipment damage or safety hazards.

**OT3**: An IDMZ acts as a buffer; no direct traffic should go from L4 $\rightarrow$ L1. Only specific data flows (e.g., historian replication) are allowed via proxies. Direct connectivity is dangerous because it allows an IT-based attack (like ransomware) to directly manipulate physical hardware without oversight.

**OT4**: 
1. **Modbus TCP**: L1/L2 (Simple device communication).
2. **OPC UA**: L2/L3/L4 (Secure, platform-independent data exchange).
3. **EtherNet/IP**: L1/L2 (Industrial Ethernet for CIP).
4. **PROFINET**: L1/L2 (Real-time deterministic control).
5. **MQTT**: Edge to Cloud / L3+ (Lightweight pub/sub for telemetry).

**OT5**: A **Data Diode** is a hardware device that physically ensures one-way data flow (optical isolation). Use it when you need to send logs out of a high-security zone without any possibility of inbound attacks. Limitation: No bidirectional handshake or acknowledgment possible.

**OT6**: Flow: PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (Protocol conversion/Filtering) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. Security boundaries should be placed at the IDMZ and between the Edge Gateway and the cloud endpoint using TLS and certificate-based authentication.

**OT7**: A **Zone** is a group of assets with similar security requirements; a **Conduit** is the communication path between them. Design: Corporate Network $\xrightarrow{\text{conduit}}$ IDMZ $\xrightarrow{\text{conduit}}$ Control Zone (SCADA/PLCs) $\xrightarrow{\text{conduit}}$ Safety Zone (SIS isolated from all others).

**OT8**: Strategy: Implement VLANs per production line. Place firewalls between IT/OT and Level 3/Level 2. Deploy an Industrial Switch architecture with managed switches. Remote access via Jump Host + MFA in the DMZ. Transition: Start with "Transparent Mode" firewalls to map traffic, then move to "Enforce Mode" gradually during maintenance windows.

**OT9**: **BPCS** handles normal process control; **SIS** is a separate system that triggers safety shutdowns if parameters exceed limits. IEC 61511 defines functional safety. SIS must be isolated so that a failure or cyber attack on the BPCS cannot disable the safety trips. Ransomware reaching the SIS could prevent emergency shutdowns, leading to catastrophic physical failure.

**OT10**: **PLC** (Programmable Logic Controller): Discrete logic for specific machines. **DCS** (Distributed Control System): Integrated plant-wide control for complex processes. **SCADA** (Supervisory Control and Data Acquisition): High-level monitoring over wide areas. They coexist: PLCs report data up to SCADA systems.

**OT11**: Architecture: VPN $\rightarrow$ Multi-Factor Authentication (MFA) $\rightarrow$ Jump Server (Bastion) $\rightarrow$ Target Asset. Use session recording for auditing. Direct RDP from corporate networks is unacceptable because it exposes HMI vulnerabilities directly to IT threats.

**OT12**: Detection: Deploy an IDS looking for abnormal Modbus/S7 writes. Response: Isolate the compromised segment via firewall rules $\rightarrow$ Failover to manual operator controls $\rightarrow$ Forensic analysis of jump host logs. The plant operator's role is to maintain process stability while IT isolates the network threat.

**OT13**: An **HMI** provides a visual interface for operators to monitor and control the process. An **Engineering Workstation** is used by programmers to configure PLC logic and system parameters; it has much higher privileges than an HMI.

**OT14**: A historian is a time-series database for process data. **Plant Historian (L3)** stores high-resolution, real-time local data for operations. **Enterprise Historian (L4)** aggregates summarized data for business analytics and reporting.

**OT15**: Ladder Logic is a graphical language mimicking electrical relay circuits. It is executed by PLCs. It remains dominant because it is intuitive for electricians and ensures deterministic execution of logic.

**OT16**: An **RTU** (Remote Terminal Unit) is designed for wide-area telemetry and often includes integrated radio/cellular modems. Use RTUs for pipelines or power grids where assets are miles apart; use PLCs for localized factory floor control.

**OT17**: Analog signals vary continuously (e.g., 4-20mA); digital signals are binary (On/Off). 4-20mA is preferred over 0-20mA because $0\text{mA}$ indicates a wire break (fault), whereas $4\text{mA}$ represents the lowest valid reading ("live zero").

**OT18**: Asset inventory identifies every device on the network. Passive monitoring (sniffing traffic) is safe. Active scanning can be dangerous in OT as sending unexpected packets to an old PLC can cause it to crash or reboot, stopping production.

**OT19**: MITRE ATT&CK ICS focuses on physical impact. Tactics: Initial Access $\rightarrow$ Execution $\rightarrow$ Persistence $\rightarrow$ Evasion $\rightarrow$ Impair Process Control. Example technique: "Modify Parameter" (changing a setpoint). It differs from IT by focusing on industrial protocols and physical outcomes. Used to map defensive gaps against known adversary behaviors.

**OT20**: Design: Passive Taps $\rightarrow$ SIEM integration with OT-specific rules (e.g., "Unauthorized S7 Write"). Staff: Hybrid team of IT analysts and OT engineers for triage. Firmware alert handling: Verify if there was a scheduled maintenance window; if not, treat as high priority, isolate the PLC, and verify firmware hashes via out-of-band methods.
