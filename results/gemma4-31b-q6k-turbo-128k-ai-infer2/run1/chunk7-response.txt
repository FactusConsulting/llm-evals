## Application Architecture

**AA1 — Easy:** A **monolith** is a single, unified unit where all business logic and data access reside in one codebase/process. **Microservices** break this into small, independent services communicating over a network. Three problems introduced by microservices: 1) Distributed complexity (network latency/failures), 2) Data consistency challenges (distributed transactions), 3) Operational overhead (monitoring, deployment, and orchestration of many units).

**AA2 — Easy:** **Synchronous** communication requires an immediate response before proceeding (e.g., REST via HTTP). **Asynchronous** communication allows the sender to continue without waiting for a response (e.g., Message queuing via RabbitMQ).

**AA3 — Medium:** An **API Gateway** provides high-level application concerns like authentication, rate limiting, and request routing. A **reverse proxy** focuses on lower-level traffic management like load balancing and SSL termination. While an API Gateway can perform reverse proxy tasks, it cannot always replace a dedicated reverse proxy if extreme low-latency L4 performance or specific caching strategies are required; however, in most modern stacks, the Gateway acts as the primary entry point encompassing both roles.

**AA4 — Medium:** The **Saga pattern** manages distributed transactions across multiple services using a sequence of local transactions with compensating actions for failures.
*   **Choreography:** Services exchange events without a central coordinator. Appropriate for simple workflows where decoupling is priority.
*   **Orchestration:** A central "orchestrator" tells participants when to execute their transaction. Appropriate for complex business logic requiring strict coordination.

**AA5 — Medium:** **CQRS** separates read operations (Queries) from write operations (Commands), allowing each to scale independently. It is paired with **Event Sourcing**, which stores state as a sequence of immutable events rather than current snapshots. This combination solves the problem of auditability and historical reconstruction that traditional CRUD models lose by overwriting data.

**AA6 — Medium:** The **Circuit Breaker** prevents a system from repeatedly trying to call a failing service. 
1. **Closed:** Requests flow normally. 2. **Open:** Request fails immediately without calling the service. 3. **Half-Open:** Periodically tests if the service has recovered. 
Unlike retry/backoff (which keeps hammering the server), it stops traffic entirely to allow recovery. Use them together: use Circuit Breakers to stop systemic failure, and retries within the application for transient glitches before the breaker trips.

**AA7 — Hard:**
1. **Shared DB, Shared Schema:** Lowest cost; high noisy-neighbor risk; lowest security isolation (relies on `WHERE tenant_id = X`).
2. **Shared DB, Separate Schema:** Moderate cost; better security; moderate operational complexity (migrations must be run per schema).
3. **Separate Database:** Highest cost; highest security; eliminates noisy-neighbor at the DB level; highest operational complexity (managing hundreds of connections/backups).

**AA8 — Hard:** **Strong consistency** ensures all clients see the same data simultaneously; **eventual consistency** guarantees that given enough time, all nodes will converge. To prevent overselling inventory: I would use **strong consistency**. Architecture: A distributed SQL database (e.g., CockroachDB or PostgreSQL with strict locking) using a **pessimistic locking pattern** or an atomic "decrement where quantity > 0" operation in a single ACID transaction. At scale, I would shard by product ID to localize locks.

**AA9 — Hard:** A **sidecar proxy** is a helper process running alongside a service instance. In Istio, Envoy handles the network traffic. The **Data Plane** consists of these sidecars forwarding requests; the **Control Plane** manages configuration and policy. mTLS between sidecars solves identity verification and encryption without requiring application code changes, providing transparent zero-trust networking.

**AA10 — Medium:** The **Strangler Fig pattern** involves incrementally replacing legacy functionality by wrapping it in a routing layer. Strategy: Place a reverse proxy/gateway in front of the .NET Framework monolith. Identify one bounded context (e.g., "Billing"), build it as a .NET 8 microservice, and update the gateway to route "/billing" requests to the new service while everything else goes to the monolith. Repeat until the monolith is empty.

**AA11 — Medium:** The **12-Factor App** is a set of best practices for cloud-native apps. Factors include: 1) Codebase (one codebase, many deploys), 2) Dependencies (explicitly declared), 3) Config (stored in environment), 4) Backing services (treated as attached resources), 5) Build, release, run (strict separation), 6) Processes (stateless). These ensure portability, scalability, and consistency across environments.

**AA12 — Hard:**
*   **Coupling:** Kafka = Loose (producer doesn't know consumer); REST = Tight (caller needs endpoint).
*   **Scalability:** Kafka scales via partitions; REST scales via load balancing instances.
*   **Debugging:** REST is easier (request/response trace); Kafka is harder (event chains).
*   **Ordering:** Kafka guarantees order within a partition; REST has no inherent ordering.
*   **Failure Handling:** Kafka allows replaying events; REST requires retries/DLQs.
Choose Kafka for high-throughput asynchronous pipelines; choose REST/gRPC for immediate request-response interactions.

**AA13 — Easy:** A **load balancer** distributes traffic across multiple servers. **Layer 4 (L4)** balances based on IP and TCP/UDP ports. **Layer 7 (L7)** balances based on application data (HTTP headers, URLs). Use case: Routing `/api/v1` to one cluster and `/api/v2` to another.

**AA14 — Easy:** A **message queue** (RabbitMQ) typically deletes messages once consumed. A **log-based broker** (Kafka) persists messages in an append-only log, allowing multiple consumers to read the same data at their own pace. Pick RabbitMQ for simple task queues; pick Kafka for event streaming and replayable history.

**AA15 — Easy:** A **container** shares the host OS kernel and isolates processes via namespaces/cgroups. A **VM** includes a full guest OS running on a hypervisor. Containers are popular because they start faster, use fewer resources, and ensure "it works on my machine" consistency.

**AA16 — Easy:** **Stateless services** do not store client data between requests (e.g., a calculator API); **stateful services** remember previous interactions (e.g., a database or session cache). Stateless services scale horizontally easily because any instance can handle any request without needing local state synchronization.

**AA17 — Easy:** An **ORM** maps database tables to objects in code. Examples: Entity Framework (.NET), Hibernate (Java). Trade-offs: ORMs increase developer productivity and portability but can introduce performance overhead ("N+1 query problem") compared to raw SQL's precision.

**AA18 — Medium:** The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, others continue to function. In microservices, this means isolating resource pools. Implementation: Use separate thread pools for different downstream service calls or deploy critical services onto dedicated hardware clusters to prevent a single slow dependency from consuming all system threads.

**AA19 — Hard:** **OT** relies on a central server to transform operations to maintain order; **CRDTs** allow concurrent updates that merge mathematically without conflicts. CRDTs provide better offline support and lower latency as they don't require a central coordinator for every keystroke. For a system supporting offline editing, I would choose **CRDTs**.

**AA20 — Hard:** Challenges include maintaining the "Trace ID" across polyglot boundaries. Context propagation uses headers like **W3C Trace Context**. Sampling strategies: **Head-based** decides at start; **Tail-based** decides after completion based on errors/latency. Storage is handled by tools like Jaeger. To ensure continuity in Kafka, the producer must inject the trace context into the Kafka record headers, which the consumer then extracts to resume the span.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** **Type 1 (Bare Metal)** runs directly on hardware (e.g., VMware ESXi, Proxmox). **Type 2 (Hosted)** runs atop an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2 — Easy:** **SAN (Storage Area Network)** provides block-level access via Fibre Channel or iSCSI; used for high-performance DBs. **NAS (Network Attached Storage)** provides file-level access via NFS or SMB; used for shared files/backups.

**OP3 — Medium:** **3-Tier** consists of Core (routing), Distribution (policy), and Access (device connection) layers. **Leaf-Spine** is a two-tier architecture where every leaf connects to every spine. It solves "East-West" traffic bottlenecks common in modern virtualized DCs where servers talk more to each other than to external clients.

**OP4 — Medium:** Use $\ge 3$ nodes for quorum. Shared storage can be **Ceph** (distributed hyperconverged), **iSCSI**, or **NFS**. Fencing (**STONITH**) ensures that if a node becomes unresponsive, it is forcibly powered off to prevent data corruption. Upon failure, the cluster detects loss of heartbeat, fences the failed node, and restarts its VMs on healthy nodes using the shared storage.

**OP5 — Medium:** **VLAN Trunking** allows multiple VLANs to traverse a single physical link using **802.1Q tagging** (adding a tag to the Ethernet frame). On Linux: create sub-interfaces like `ip addr add ... dev eth0.10` (where .10 is the VLAN ID) after ensuring the physical NIC is configured as a trunk.

**OP6 — Medium:** RAID 1 (Mirror), RAID 5 (Parity), RAID 6 (Double Parity), RAID 10 (Striped Mirrors), ZFS RaidZ2 (similar to RAID 6 but avoids write holes). For a DB server with 6 drives: I would choose **RAID 10**. It provides the best balance of high IOPS (performance) and fault tolerance without the parity calculation overhead of RAID 5/6.

**OP7 — Hard:** Internal AD handles internal resolution; DMZ servers are authoritative for public zones. **Split-horizon DNS** serves different IPs for the same hostname depending on whether the request comes from inside or outside the network. External zones use **DNSSEC** for signing. When a laptop moves to VPN, DHCP assigns it an internal DNS resolver that uses conditional forwarders to route requests back to the corporate core.

**OP8 — Hard:** Root CA $\to$ Subordinate CA $\to$ End Entity. The root stays offline for security. CRLs provide lists of revoked certs; OCSP provides real-time status. A compromised subordinate CA requires revoking only that sub-CA's certificate via the root. A compromised root CA is catastrophic, requiring a complete re-issue of all certificates in the organization.

**OP9 — Hard:**
*   **MPLS:** High cost, guaranteed QoS/latency, complex setup.
*   **IPsec VPN:** Low cost, internet-dependent, higher jitter.
*   **SD-WAN:** Flexible, manages multiple paths, centralized control.
*   **WireGuard Mesh:** Extremely fast, secure, but manual management at scale.
For VoIP (latency sensitive), I recommend **SD-WAN**. It allows prioritizing VoIP traffic over MPLS while using IPsec as backup, ensuring low jitter and high reliability.

**OP10 — Medium:** Out-of-band (OOB) management (iDRAC/iLO) provides hardware-level access regardless of OS state. Critical for remote power cycling or BIOS config. If exposed to the internet, an attacker can gain full console access, bypass OS passwords, and potentially flash malicious firmware.

**OP11 — Medium:** **LVM** provides flexible volume resizing. **LVM-Thin** allows overprovisioning storage. **ZFS** is a combined filesystem/volume manager with copy-on-write. LVM snapshots are block-based; ZFS snapshots are pointer-based and nearly instantaneous without performance degradation. Use ZFS for data integrity (checksums) and rapid snapshotting.

**OP12 — Hard:** A stretch cluster requires Ceph monitors in both sites plus a third "tiebreaker" site to maintain quorum. CRUSH rules must be configured to ensure replicas are distributed across sites. Network latency must typically be $< 5\text{ms}$. Two-site Ceph is dangerous because if the link breaks, both sides may think they are the master (**split-brain**), leading to catastrophic data corruption.

**OP13 — Easy:** DHCP uses **DORA**: Discover $\to$ Offer $\to$ Request $\to$ Acknowledge. If the server is unavailable after lease expiry, Windows clients assign themselves an **APIPA** address ($169.254.x.x$).

**OP14 — Easy:** An unmanaged switch is plug-and-play. A **managed switch** allows VLAN configuration, Spanning Tree Protocol (STP) to prevent loops, SNMP monitoring, and port mirroring—all essential for security and stability in enterprise networks.

**OP15 — Easy:** NTP synchronizes clocks via UDP. Critical for Kerberos authentication (which fails if clocks drift $> 5$ mins), log correlation, and database replication consistency. Drift can cause "clock skew," resulting in rejected auth tokens or out-of-order transaction logs.

**OP16 — Easy:** Physical = Bare hardware; VM = Hardware abstraction; Container = OS process isolation. Run on bare metal when you need maximum I/O performance, direct GPU access, or avoid hypervisor overhead (e.g., high-frequency trading or massive DBs).

**OP17 — Easy:** **UPS** provides immediate battery power during a dip/outage. A **generator** provides long-term power using fuel. You need both because generators take time to start; the UPS bridges that gap. The **ATS** automatically switches from utility power to generator power once it's online.

**OP18 — Medium:** Active-Passive: one standby server takes over on failure. Active-Active: both serve traffic. For PostgreSQL HA with Pacemaker/Corosync: Use a Virtual IP (VIP) that floats between nodes. If the primary fails, Corosync detects it, STONITH fences the old primary, and Pacemaker promotes the standby and moves the VIP to it.

**OP19 — Hard:** **3-2-1 Rule**: 3 copies of data, 2 different media, 1 offsite. RPO (how much data loss is acceptable), RTO (how fast must we recover). Types: Full $\to$ Incremental (changes since last backup). Use deduplication for disk efficiency and immutable S3 buckets/Tape for ransomware protection. Backup = copying data; DR = the holistic plan to restore business operations.

**OP20 — Hard:** 802.1X uses a **Supplicant** (device), **Authenticator** (switch), and **Auth Server** (RADIUS). EAP-TLS uses certificates; PEAP uses passwords. RADIUS assigns VLANs dynamically based on user identity. Failed devices are put in a "Guest" or "Quarantine" VLAN. **MAB** allows access by checking the MAC address against a whitelist for devices like printers that cannot run an 802.1X supplicant.
