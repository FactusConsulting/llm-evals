## OpenTofu / Terraform

**T1 — Easy:** `tofu plan` is a dry run that compares the current state with the desired configuration and shows what changes will be made. `tofu apply` actually executes those changes to reach the desired state.

**T2 — Easy:** State is a JSON file mapping your configuration to real-world resources. Remote state stores this file in a shared location (S3, Consul, etc.), which is critical for team collaboration, preventing state corruption via locking, and providing a single source of truth.

**T3 — Medium:** `count` creates resources based on an integer index; `for_each` uses a map or set of strings as keys. `for_each` is preferred when managing lists where items might be removed from the middle; removing an item in `count` shifts indices, causing Tofu to destroy and recreate subsequent resources.

**T4 — Medium:** This is called "drift." During the refresh phase of a plan or apply, OpenTofu queries the cloud API. If the actual state differs from the stored state, it detects the drift and proposes a plan to revert the manual change back to the configured state.

**T5 — Medium:**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-xxxxxx"
  instance_type = "t3.micro"
  tags = { Name = each.value }
}
```

**T6 — Hard:** `terraform_remote_state` reads the entire state file of another project, while output values are specific exported variables. The recommended alternative is using **data sources** for existing infrastructure (e.g., `data "aws_vpc"`) or utilizing a shared module wrapper that passes outputs as inputs, reducing tight coupling between separate state files.

**T7 — Hard:** Provisioners run *after* resource creation but do not return data into the Tofu state natively. Because the output depends on a value generated by a provisioner (which isn't in the state), the first apply sees an empty string. **Fix:** Use a `local-exec` provisioner to write the kubeconfig to a local file, then use a `local_file` data source or a specialized provider to read it back into a variable.

**T8 — Medium:** `tofu import` maps existing cloud resources into your state file. Limitation: It only updates state; you must manually write the HCL code to match. The **import block (1.5+)** allows declarative imports; you define the import in code and run plan/apply to generate the configuration automatically.

**T9 — Easy:** A **variable** is an input parameter used to customize configurations. An **output** is a value exposed by a module after application, useful for displaying info or passing data to other modules.

**T10 — Easy:** A provider is a plugin that translates Tofu code into API calls for a specific platform (e.g., AWS, Azure). If you run `plan` without `init`, Tofu will error because the necessary provider binaries have not been downloaded.

**T11 — Easy:** This is the dependency lock file. It records the exact versions and hashes of providers used. Committing it ensures all environments (Dev, CI, Prod) use identical provider versions, preventing "it works on my machine" bugs.

**T12 — Easy:** `tofu destroy` removes all managed infrastructure. To target one resource: `tofu destroy -target=aws_instance.web[0]`.

**T13 — Easy:** A data source fetches information about resources *not* managed by your current Tofu project. Example: Using a data source to get the latest Amazon Linux 2 AMI ID instead of hardcoding a static ID.

**T14 — Medium:** Variables are external inputs; locals are internal constants/computed values. Use locals for DRY logic—calculating a common tag map or concatenating strings—so you don't repeat complex expressions throughout the module.

**T15 — Medium:**
- `create_before_destroy`: Creates new resource before deleting old (prevents downtime during updates).
- `prevent_destroy`: Errors out if a destroy is attempted (safety for DBs).
- `ignore_changes`: Ignores drift for specific attributes (e.g., ignoring tags updated by an auto-scaling group).

**T16 — Medium:** A `moved` block tells OpenTofu that a resource has changed its address in the code (e.g., moved into a module) without changing the actual cloud resource. This prevents Tofu from destroying and recreating the resource.

**T17 — Hard:** The dependency graph is a Directed Acyclic Graph (DAG). **Implicit dependencies** occur when one resource references another (`vpc_id = aws_vpc.main.id`). **Explicit dependencies** use `depends_on`. `depends_on` forces a strict order, reducing parallelism because Tofu must wait for the target to finish completely, even if no data is shared. It should be used sparingly as it can hide architectural flaws.

**T18 — Hard:** 
1. **State Splitting:** Break one giant state into smaller components (Network, App, DB) $\rightarrow$ reduces API calls per plan.
2. **`-refresh=false`**: Skip querying the cloud; uses stored state $\rightarrow$ faster but risks missing drift.
3. **Targeting**: Use `-target` for specific changes $\rightarrow$ fast, but risky as it ignores dependencies.
4. **Parallelism Tuning**: Adjust `-parallelism=N` $\rightarrow$ speeds up apply, but may hit Cloud API rate limits.

**T19 — Hard:** State locking prevents concurrent writes that would corrupt the state file. If a crash occurs, the lock remains in the backend (e.g., DynamoDB). Manually break with `tofu force-unlock <lock-id>`. Risk: If someone *is* actually running an apply and you unlock it, you will likely cause catastrophic state corruption.

**T20 — Hard:** 
1. Update `backend` block from `local` to `s3` with DynamoDB table details.
2. Run `tofu init`. Tofu detects existing local state and asks if you want to migrate.
3. Confirm "yes" to upload the `.tfstate` to S3.
4. Verify by checking the S3 bucket for the file and confirming the DynamoDB table contains the lock entry during a subsequent plan.

## Ansible

**A1 — Easy:** A **playbook** is the top-level YAML file defining the workflow; a **role** is a structured package of tasks/vars/templates for a specific function; a **task** is a single unit of execution (a module call).

**A2 — Easy:** `ansible_facts` are system properties gathered at start. Access OS family via `{{ ansible_distribution_family }}` or `{{ ansible_os_family }}`.

**A3 — Medium:** 
- `command`: Simple execution; doesn't support shell features like pipes or redirects.
- `shell`: Full shell environment (supports pipes, variables, wildcards).
- `raw`: Bypasses Python on target; sends raw SSH commands (used for bootstrapping targets without Python).

**A4 — Medium:** Idempotency means running a task multiple times results in the same state without changing anything after the first run. 
- **Idempotent:** `apt: name=nginx state=present`.
- **NOT Idempotent:** `shell: echo "Hello" >> /tmp/log.txt` (appends every time).

**A5 — Medium:**
```yaml
- name: Install htop based on OS
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
  when: ansible_os_family == 'Debian'
- name: Install EPEL and htop for RedHat
  yum:
    name: ['epel-release', 'htop']
    state: present
  when: ansible_os_family == 'RedHat'
```

**A6 — Hard:** Precedence (lowest to highest): Role defaults $\rightarrow$ Group vars $\rightarrow$ Host vars $\rightarrow$ Playbook vars $\rightarrow$ Extra vars (`-e`). `set_fact` is high priority as it happens at runtime during execution.

**A7 — Hard:** Use two separate plays in one playbook. First play targets a group `[seed]` with 3 nodes. Second play targets `[agents]`, but uses `serial: 10` or similar. To ensure the first 3 are fully ready, use a task with the `wait_for` module checking for the RKE2 port (6443) before starting the second play.

**A8 — Medium:** `ansible-vault` encrypts files/strings. For a single variable, use `ansible-vault encrypt_string 'mysecretpassword'` and paste the resulting encrypted block into your plain YAML vars file.

**A9 — Easy:** An inventory lists target hosts. **Static**: A text/INI file listing IPs/hostnames. **Dynamic**: A script or plugin that queries an API (AWS, GCP) to generate the host list on the fly.

**A10 — Easy:** `ansible webservers -m shell -a "df -h"`

**A11 — Easy:** A handler is a special task triggered by a `notify` keyword. It only runs if the calling task reports a "changed" status and only runs once at the end of the play. Triggered via `notify: restart nginx`.

**A12 — Easy:** `ansible.cfg` provides global configuration. Common settings: `remote_user`, `inventory` path, and `forks` (number of parallel processes).

**A13 — Easy:** The `register` keyword saves the output of a task into a variable. Use it in subsequent tasks using conditional logic: `when: result.changed`.

**A14 — Medium:** `import_tasks` is static (processed when playbook is parsed); `include_tasks` is dynamic (evaluated during execution). Use `include_tasks` for conditionals; otherwise, `import_tasks` conditions are evaluated only once at start.

**A15 — Medium:** Ansible Galaxy is a community hub for roles/collections. Install them using a `requirements.yml` file:
```yaml
roles:
  - { name: geerlingguy.nginx }
```
Run with `ansible-galaxy install -r requirements.yml`.

**A16 — Medium:** Connection plugins handle communication. 
- `ssh`: Standard remote execution.
- `local`: Runs on control node.
- `network_cli`: Used for network devices that don't support Python; manages persistent SSH sessions to avoid repeated logins.

**A17 — Hard:** `delegate_to` runs a task on a different host than the current target; `run_once` ensures the task executes exactly once per batch. Example: Update an external Load Balancer from localhost based on a remote IP:
```yaml
- name: Register in LB
  uri: url="http://lb/api" method=POST body="ip={{ ansible_host }}"
  delegate_to: localhost
  run_once: true
```

**A18 — Hard:** 
1. **Forks**: Increase `-f` (e.g., `--forks 50`) to increase parallelism.
2. **Pipelining**: Enable `pipelining = True` in `ansible.cfg` to reduce SSH round trips.
3. **Fact Caching**: Use Redis or JSON file caching to avoid gathering facts every run.
4. **Mitogen**: Install Mitogen for Ansible to replace the SSH execution engine with a more efficient one.

**A19 — Hard:** `{{ }}` is for variable interpolation, `{% %}` for logic (loops/ifs), and `{# #}` for comments.
Snippet:
```jinja2
upstream backend {
 {# Health check enabled #}
 {% for server in backend_servers %}
   server {{ server.ip }}:{{ server.port }};
 {% endfor %}
}
```

**A20 — Hard:** 
1. Set `serial: 2` (batch size).
2. **Pre-task**: Remove host from LB using `uri` module.
3. **Update**: Deploy app code.
4. **Health Check**: Use `uri` module to poll `/health` until 200 OK.
5. **Post-task**: Re-add host to LB.
6. **Rollback**: Wrap update tasks in a `block`. In the `rescue` section, trigger a rollback task that reverts the version and re-adds the node to the LB before failing the play.
