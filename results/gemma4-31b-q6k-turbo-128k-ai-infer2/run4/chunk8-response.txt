## Cloud Infrastructure Architecture

**CL1 — Easy:** IaaS (Infrastructure as a Service) provides raw compute, storage, and networking (User manages OS/Apps); PaaS (Platform as a Service) provides a framework for developers to build apps without managing the underlying OS; SaaS (Software as a Service) is a fully managed application delivered over the web. 
- **IaaS:** AWS EC2.
- **PaaS:** Azure App Service / Google App Engine.
- **SaaS:** Microsoft 365 / Salesforce.

**CL2 — Easy:** The Shared Responsibility Model defines who is responsible for security tasks.
- **IaaS VMs:** Provider handles hardware/hypervisor; User handles Guest OS, patching, firewall, and data.
- **Managed Kubernetes:** Provider handles Control Plane (API server, etcd); User handles Worker Node configuration, Pod security, and Application code.
- **SaaS (M365):** Provider handles almost everything including infrastructure and app logic; User handles identity management, data access permissions, and device endpoints.

**CL3 — Medium:** 
- **VPC:** An isolated virtual network boundary in the cloud.
- **Subnet:** A range of IP addresses within a VPC used to group resources.
- **Security Group (SG):** A stateful firewall at the instance level (controls traffic to specific NICs).
- **NACL:** A stateless firewall at the subnet level.
- **Layering:** Traffic hits NACL first $\rightarrow$ then Security Group.
- **Stateful vs Stateless:** Stateful (SG) remembers connection state; if an inbound request is allowed, the return traffic is automatically allowed. Stateless (NACL) requires explicit rules for both inbound and outbound directions.

**CL4 — Medium:** 
- **Landing Zone:** A pre-configured multi-account environment with baseline security and networking.
- **Organizational Units (OUs):** Logical groupings of accounts for policy application.
- **Guardrails:** Service Control Policies (SCPs) that set maximum available permissions across accounts.
- **Shared Networking:** Hub-and-Spoke architecture using Transit Gateway (AWS) or Azure Virtual WAN to centralize egress/ingress.
- **Centralized Logging:** Aggregating all CloudTrail/Activity logs into a dedicated "Log Archive" account for auditing.
- **Single Account Problems:** Blast radius (one compromise affects everything), quota limits, billing complexity, and lack of isolation between Dev/Prod environments.

**CL5 — Medium:** IaC allows managing infrastructure via code files rather than manual console clicks.
- **Terraform/OpenTofu:** HCL-based, provider-agnostic, industry standard for general cloud resources. Use when needing cross-cloud portability.
- **Pulumi:** Uses general languages (Python, TS). Use when complex logic/loops are needed in infra definition.
- **CloudFormation/Bicep:** Native to AWS/Azure. Use for deep integration with one specific provider's ecosystem.
- **Crossplane:** K8s-native control plane. Use when you want to manage cloud resources as K8s Custom Resources (CRDs).

**CL6 — Medium:** 
- **HPA:** Scales pods based on CPU/RAM usage.
- **VPA:** Adjusts the resource requests/limits of existing pods.
- **Cluster Autoscaler:** Adds/removes physical nodes from the cluster.
- **KEDA:** Event-driven autoscaling using external metrics (e.g., RabbitMQ queue length or Prometheus queries).
- **KEDA vs HPA:** Use KEDA when scaling is driven by business events (queue depth) rather than just hardware utilization.

**CL7 — Hard:** 
- **Strategy:** Active-Active across two regions for zero RTO; Async database replication (to avoid latency penalties), Route53 Health Checks for DNS failover.
- **State Management:** Global databases (Aurora Global / CosmosDB) or distributed caches.
- **DR Types:**
    - **Pilot Light:** Minimal critical services running; others are dormant but configured. Low cost, higher RTO.
    - **Warm Standby:** Scaled-down version of full stack always running. Moderate cost, low RTO.
    - **Multi-site Active-Active:** Full capacity in both regions serving traffic. Highest cost, near-zero RTO/RPO.

**CL8 — Hard:** GitOps uses a Git repository as the single source of truth. A controller (ArgoCD/FluxCD) continuously synchronizes the live state to match Git.
- **Comparison:** ArgoCD provides a powerful UI and visual diffs; FluxCD is more lightweight and "invisible."
- **Secrets:** Handled via Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault/AWS SM), or HashiCorp Vault directly.
- **Drift:** If someone makes a manual change, the GitOps operator detects the difference and automatically overwrites the manual change to revert it back to the Git state.

**CL9 — Hard:** 
- **Architecture:** Use a **StatefulSet** for stable network IDs and ordered deployment.
- **Storage:** Local Persistent Volumes (PV) with a local storage class for low latency.
- **Networking:** Headless Service for direct pod addressing.
- **Configuration:** Init containers to prepare filesystem paths; ConfigMaps mounted as volumes at specific paths.
- **Availability:** Pod Disruption Budgets (PDB) to ensure minimum available replicas during node drains.

**CL10 — Medium:** 
- **Service Account:** An identity for processes running inside K8s.
- **Workload Identity / IRSA:** Mapping a K8s Service Account to a Cloud IAM Role using OIDC.
- **Bad Practice:** Mounting static JSON keys into pods creates secret leakage risks and rotation overhead.
- **Federation Solution:** The cloud provider trusts the K8s cluster's OIDC issuer; the pod exchanges its token for short-lived temporary credentials.

**CL11 — Medium:** 
- **Object Storage (S3/Blob):** Unstructured data, highly scalable, accessed via API. Best for images, logs, backups. High durability ($11\text{ nines}$).
- **Block Storage (EBS/Managed Disk):** Low-latency disks attached to one VM. Best for OS boots, databases. Durability depends on snapshots.
- **File Storage (EFS/Azure Files):** Shared network filesystems (NFS/SMB). Best for shared app config or legacy CMS. Regional availability.

**CL12 — Hard:** 
- **Architecture:** Network Policies (L3/4 isolation) $\rightarrow$ Service Mesh with mTLS (Encryption + Auth between services) $\rightarrow$ Pod Identity (IRSA) $\rightarrow$ Admission Controllers (OPA/Kyverno for policy enforcement) $\rightarrow$ Image Signing (Cosign) $\rightarrow$ Runtime Security (Falco for anomaly detection).
- **Difference:** Traditional perimeter security relies on a "hard shell" (Firewall); Zero Trust assumes the internal network is already compromised and verifies every single request regardless of origin.

**CL13 — Easy:** A CDN caches content at edge locations closer to users to reduce latency. Examples: AWS CloudFront, Akamai. Use a CDN when serving static assets globally; serve from origin only for dynamic, personalized, or highly volatile data.

**CL14 — Easy:** 
- **Region:** Geographic area containing multiple AZs.
- **Availability Zone (AZ):** One or more isolated data centers within a region.
- **Multi-AZ Deployment:** Protects against a single DC failure (power/cooling outage).
- **Zonal vs Regional:** Zonal resources exist in one AZ; Regional resources are replicated across several AZs automatically by the provider.

**CL15 — Easy:** Managed DBs handle operational overhead like OS patching, automated backups, hardware failover, and basic scaling. The user focuses solely on schema design, indexing, and query optimization.

**CL16 — Easy:** 
- **Users:** Individual identities. **Groups:** Collections of users. **Roles:** Identities assumed by services or people temporarily. **Policies:** JSON documents defining permissions.
- **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply this by using Roles instead of Users and avoiding `AdministratorAccess` policies.

**CL17 — Easy:** Serverless is event-driven compute where the cloud provider manages all infrastructure. Examples: AWS Lambda, Azure Functions. **Cold Starts** occur when a function is invoked after being idle, causing latency while the environment initializes. Poor fit for long-running tasks (>15 mins) or high-constant load where VMs are cheaper.

**CL18 — Medium:** 
- **Ingress Resource:** Basic L7 routing rules.
- **Gateway API:** Modern, role-based evolution of Ingress with better support for complex traffic splitting.
- **LB Annotations:** Direct integration (e.g., creating an AWS ALB).
- **Mesh Gateways:** Entry points that handle mTLS termination before passing traffic into the mesh.
- **TLS Termination:** Usually happens at the Load Balancer or Ingress Controller; Gateway API allows more granular control over which service terminates TLS. Use Gateway API for multi-tenant clusters.

**CL19 — Hard:** 
- **Compute:** Reserved Instances/Savings Plans for baseline load; Spot instances for fault-tolerant batch jobs. Right-size based on actual utilization metrics.
- **Storage:** S3 Intelligent-Tiering to move old data to Archive automatically.
- **FinOps:** Implement "Tagging" policies for every resource $\rightarrow$ Cost Explorer dashboards per team $\rightarrow$ Showback (reporting cost) and Chargeback (billing back to department budgets).
- **Visibility:** Kubecost for K8s granularity; Cloud native budget alerts.

**CL20 — Hard:** 
- **Strategy:** Kubernetes as a common runtime abstraction layer; Terraform for portable IaC definitions. Networking via Site-to-Site VPN or Dedicated Interconnect. Identity Federation using OIDC.
- **Trade-offs:** Theoretical benefit is resilience/no lock-in; real-world trade-off is massive operational complexity, higher networking costs, and inability to use provider-specific high-value features.
- **Justification:** Justified only for extreme regulatory requirements or critical availability needs where one cloud's total regional failure is an unacceptable risk.

## OT Infrastructure Architecture

**OT1 — Easy:** The Purdue Model segments industrial networks into levels:
- **Level 0 (Process):** Physical sensors, actuators, motors.
- **Level 1 (Basic Control):** PLCs, PID controllers.
- **Level 2 (Area Supervisory):** HMIs, local SCADA consoles.
- **Level 3 (Site Operations):** Plant historians, site-wide SCADA servers.
- **Level 4 (Enterprise):** Corporate IT network, ERP systems.

**OT2 — Easy:** IT focuses on Confidentiality $\rightarrow$ Integrity $\rightarrow$ Availability. OT focuses on Availability $\rightarrow$ Safety $\rightarrow$ Reliability. Standard IT patching can cause unplanned reboots or crashes in legacy PLC software, which could lead to physical equipment damage or safety hazards.

**OT3 — Medium:** An IDMZ acts as a buffer between the corporate network (L4) and the plant floor (L3). Only proxy/broker traffic should cross; no direct L4 $\rightarrow$ L1 connectivity is allowed because it would allow an IT breach to directly manipulate hardware without any supervisory oversight.

**OT4 — Medium:** 
1. **Modbus TCP:** L1/L2 (Simple device communication).
2. **OPC UA:** L2/L3/L4 (Secure, platform-independent data exchange).
3. **EtherNet/IP:** L1/L2 (High-speed control logic).
4. **PROFINET:** L1/L2 (Real-time deterministic control).
5. **MQTT:** Edge to Cloud / L3+ (Lightweight telemetry).

**OT5 — Medium:** A firewall uses software rules to filter two-way traffic. A data diode is a hardware device that physically allows light/electrons to flow in only one direction. Use diodes for high-security exports (e.g., sending logs out of a nuclear plant). Limitation: No "handshake" or acknowledgment possible from the receiver.

**OT6 — Medium:** Flow: PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (Protocol conversion) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. Security boundaries are placed at the IDMZ (between L3 and L4) and the cloud edge via API Gateways with strict authentication.

**OT7 — Hard:** 
- **Zone:** Group of assets with similar security requirements. **Conduit:** The communication path between zones.
- **Design:** Corporate Zone $\xrightarrow{Firewall}$ Supervisory Zone (SCADA/Historian) $\xrightarrow{Firewall}$ Control Zone (PLCs) $\xrightarrow{Airgap/Isolation}$ Safety Instrumented System (SIS) Zone. Engineering workstations reside in their own zone with strictly timed access conduits.

**OT8 — Hard:** 
- **Strategy:** Implement VLANs per production line; place Industrial Firewalls between Level 2 and Level 3. Replace flat switches with managed switches supporting port security.
- **Remote Access:** VPN $\rightarrow$ MFA $\rightarrow$ Jump Host in IDMZ.
- **Transition:** Parallel build of new network segments $\rightarrow$ Mirror traffic to test rules $\rightarrow$ Cutover during planned maintenance windows to avoid unplanned downtime.

**OT9 — Hard:** BPCS handles normal operations; SIS is a separate, independent system that triggers a "safe state" if limits are exceeded. IEC 61511 defines functional safety for these systems. Isolation prevents common cause failure. If ransomware reaches the SIS, it could disable emergency shutdowns, potentially leading to catastrophic physical explosions or leaks.

**OT10 — Medium:** 
- **PLC:** Logic controller for specific machines/small tasks.
- **DCS:** Integrated system for complex, large-scale plant control.
- **SCADA:** Supervisory software for wide-area monitoring and control.
They coexist: PLCs act as the local "brains," reporting up to SCADA for visualization.

**OT11 — Medium:** Architecture: Corporate Network $\rightarrow$ Firewall $\rightarrow$ Jump Host (Bastion) in IDMZ $\rightarrow$ MFA $\rightarrow$ Target HMI. Session recording and time-limited access are mandatory. Direct RDP from corporate IT is unacceptable because it bypasses auditing and exposes critical HMIs to general IT malware.

**OT12 — Hard:** 
- **Detection:** Use passive IDS (e.g., Nozomi/Claroty) to detect anomalous protocol behavior.
- **Response:** Coordinate with the Control Room operator first—safety takes precedence over isolation. Isolate compromised segments via firewall rules while ensuring a human operator has manual override of all valves/switches.
- **Operator Role:** The operator ensures process stability; they decide if isolating a network segment will cause a dangerous physical state.

**OT13 — Easy:** An HMI provides a visual interface for operators to monitor and control the process. An Engineering Workstation is used by engineers to program the PLC logic or change system configurations.

**OT14 — Easy:** A historian is a time-series database that logs every sensor value over time. Plant Historian (L3) stores high-resolution data for local troubleshooting; Enterprise Historian (L4) stores aggregated, long-term data for business analytics.

**OT15 — Easy:** Ladder Logic is a graphical programming language mimicking electrical relay circuits. It's executed by PLCs. It remains dominant because it is intuitive for electricians and highly deterministic in execution.

**OT16 — Easy:** An RTU (Remote Terminal Unit) handles wide-area telemetry and often operates on low power/solar. PLCs are designed for fast, localized control within a plant. Use RTUs for pipelines, water grids, or remote substations.

**OT17 — Easy:** Analog signals vary continuously (e.g., 4-20mA); Digital are binary (On/Off). 4-20mA is preferred over 0-20mA so that if a wire breaks (0mA), the system can distinguish between "zero reading" (4mA) and "system failure" (0mA).

**OT18 — Medium:** Asset inventory identifies all devices, firmware versions, and communication paths. Passive monitoring (sniffing traffic) is used to discover assets safely. Active scanning is dangerous because old OT stacks may crash when receiving unexpected packets (like an Nmap scan).

**OT19 — Hard:** MITRE ATT&CK for ICS focuses on physical impact. Tactics: Initial Access $\rightarrow$ Execution $\rightarrow$ Persistence $\rightarrow$ Inhibition of Control $\rightarrow$ Impair Process Control. Example technique: "Modify Parameter" to change a temperature setpoint. Differs from IT by focusing on the *physical* consequence rather than just data theft.

**OT20 — Hard:** 
- **SOC Design:** Passive Taps $\rightarrow$ SIEM integration. Rules focus on protocol anomalies (e.g., S7 Write command during non-maintenance hours).
- **Staffing:** Hybrid team; IT analysts handle alerts, but OT engineers validate them.
- **Firmware Alert:** High priority alert $\rightarrow$ Cross-reference with Change Management logs $\rightarrow$ If unplanned, isolate device immediately and initiate forensic image capture.
