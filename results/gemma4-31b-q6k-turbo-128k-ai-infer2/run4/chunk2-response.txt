## Kubernetes

**K1 — Easy:** A **Deployment** manages stateless pods that are interchangeable. If a pod dies, it's replaced by an identical one. A **StatefulSet** manages pods with unique, persistent identities (e.g., `pod-0`, `pod-1`) and stable network identifiers, ensuring ordered deployment, scaling, and termination.

**K2 — Easy:** A ClusterIP service provides a single virtual IP. When traffic hits this IP, the `kube-proxy` (via iptables or IPVS) intercepts the request and load-balances it across the set of healthy Pods matching the service's label selector.

**K3 — Medium:** 
- **PersistentVolume (PV):** The actual storage resource (the "disk") in the cluster.
- **PersistentVolumeClaim (PVC):** A user's request for storage (the "ticket").
- **StorageClass (SC):** A template used to dynamically provision PVs based on specific parameters (e.g., SSD vs HDD).
**Relation:** A PVC requests resources from a StorageClass; the SC then automatically creates a PV and binds it to that PVC.

**K4 — Medium:** 
1. `kubectl logs <pod>`: Check application crash logs/stack traces.
2. `kubectl describe pod <pod>`: Look at the "Events" section for OOMKilled, failed probes, or image pull errors.
3. Check Liveness/Readiness probe configurations to see if they are killing the pod prematurely.
4. Verify environment variables, secrets, and config maps are correctly mounted and valid.

**K5 — Medium:** CoreDNS provides service discovery via DNS. It allows pods to find other services using names instead of IPs. If CoreDNS is down, internal DNS resolution fails ($\text{service.namespace.svc.cluster.local}$ will not resolve), effectively breaking communication between microservices.

**K6 — Hard:** The scheduler uses a two-step process:
1. **Filtering (Predicates):** Eliminates nodes that don't meet requirements (e.g., insufficient CPU/RAM, taints without tolerations, node selector mismatch).
2. **Scoring (Priorities):** Ranks remaining nodes based on factors like resource balance (least requested) and affinity rules.
**Factors considered:** Resource requests vs available capacity, Taints/Tolerations, Pod Anti-Affinity/Node Affinity.

**K7 — Hard:** 
- **Scheduling:** Yes. The node has $0.5\text{GB}$ free ($4\text{GB} - 3.5\text{GB}$). Since the request is only $256\text{Mi}$, it fits within the available capacity.
- **Runtime:** If the pod uses $600\text{Mi}$, it exceeds its `limits.memory` of $512\text{Mi}$. The Linux kernel OOM killer will terminate the container with an **OOMKilled** status.

**K8 — Hard:** 
External LB $\rightarrow$ NGINX Ingress Controller Pod $\rightarrow$ reads Ingress Rules $\rightarrow$ maps to Service $\rightarrow$ looks up Endpoints (the actual IPs of healthy pods) $\rightarrow$ traffic is routed directly to a Pod IP via iptables/IPVS (bypassing the Service virtual IP for efficiency).

**K9 — Medium:** A NetworkPolicy is an L3/L4 firewall for pods. By default, if no policy exists, all pods in a namespace can communicate with each other and external pods (**Allow All**). Once any NetworkPolicy selects a pod, that pod becomes "isolated," and only explicitly allowed traffic is permitted.

**K10 — Medium:** 
- **RollingUpdate:** Gradually replaces old pods with new ones, ensuring zero downtime.
- **Recreate:** Kills all existing pods before starting new ones.
**Choose Recreate when:** The application does not support multiple versions running simultaneously (e.g., during a database schema migration where two different app versions would corrupt data).

**K11 — Easy:** A namespace provides a scope for names and a way to partition cluster resources. Default namespaces: `default` (user apps), `kube-system` (cluster internals), `kube-public` (visible to everyone).

**K12 — Easy:** It shows detailed state and events. Three things it shows that `get` doesn't: 
1. Lifecycle Events (e.g., Pulling image, Started container).
2. Container status details (Exit codes, Restart counts).
3. Volume mount paths and Resource limits.

**K13 — Easy:** A ConfigMap stores non-confidential configuration key-value pairs. Consumption methods:
1. As environment variables injected into the container.
2. As files mounted as a volume in the filesystem.

**K14 — Easy:** 
- **ClusterIP:** Internal only; accessible only within the cluster.
- **NodePort:** Exposes service on a static port on every Node IP.
- **LoadBalancer:** Provisions an external cloud LB that routes traffic to the NodePort/ClusterIP.

**K15 — Easy:** A DaemonSet ensures that a copy of a specific pod runs on all (or selected) nodes. Use instead of Deployment for infrastructure services like log collectors (Fluentd) or monitoring agents (Prometheus Node Exporter).

**K16 — Medium:** 
- **Taints/Tolerations:** Taints are applied to *nodes* to repel pods; Tolerations are applied to *pods* to allow them onto tainted nodes. Case: Dedicated GPU nodes (tainted so general apps don't land there).
- **Affinity:** Pods "prefer" or "require" certain node labels. Case: Ensuring high availability by spreading pods across different Availability Zones (`topologyKey`).

**K17 — Medium:** An Operator is a custom controller using Custom Resource Definitions (CRDs) to manage complex applications. Unlike standard controllers, Operators encode human operational knowledge (e.g., how to perform a database backup or version upgrade) into code to automate lifecycle management.

**K18 — Hard:** etcd uses the Raft consensus algorithm (strong consistency). If quorum is lost (majority of nodes down), the cluster becomes read-only or unavailable. To recover from losing 2 out of 3 nodes, you must restore the remaining node from a recent snapshot and reconfigure it as a single-node cluster before adding new members.

**K19 — Hard:** RBAC links Users $\rightarrow$ Roles via Bindings. `Role` is namespace-scoped; `ClusterRole` is global. `RoleBinding` binds a Role to a user in one namespace; `ClusterRoleBinding` applies globally.
**Manifest for Read-Only access in namespace `dev`:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: dev }
rules: [{ apiGroups: [""], resources: ["pods", "pods/log"], verbs: ["get", "list", "watch"] }]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: read-pods-binding, namespace: dev }
subjects: [{ kind: User, name: developer-user }]
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
```

**K20 — Hard:** By default, Kubernetes sets `ndots: 5`. This means any DNS query with fewer than 5 dots is treated as internal first. A request for `google.com` triggers queries like `google.com.default.svc.cluster.local`, then `google.com.svc.cluster.local`, etc., before trying the external resolver. **Fix:** Set `dnsConfig` in Pod spec to `ndots: 1`.

## Development

**D1 — Easy:** `merge` creates a merge commit and preserves history exactly as it happened. `rebase` rewrites history by moving commits onto a new base for a linear timeline. Avoid rebasing public shared branches because it forces other developers to perform complex manual merges of their local histories.

**D2 — Easy:** TCP is connection-oriented and reliable (guarantees delivery/order); UDP is connectionless and fast (no guarantees). 
- **TCP:** HTTP, SSH.
- **UDP:** DNS, VoIP/Streaming.

**D3 — Medium:** A race condition occurs when multiple threads access shared data concurrently and the final outcome depends on the timing/interleaving of execution. Example: Two threads incrementing a global counter `x = x + 1` without a lock; both read `10`, both calculate `11`, and write back `11` instead of `12`.

**D4 — Medium:** Symmetric uses one key for encryption/decryption (AES). Asymmetric uses a Public Key to encrypt and a Private Key to decrypt (RSA). In TLS, asymmetric encryption is used during the handshake to securely exchange a symmetric "session key," which is then used for the actual data transfer due to its speed.

**D5 — Medium:** An image layer is a read-only filesystem delta created by each instruction in a Dockerfile. Caching skips layers that haven't changed. Best practice: Put infrequently changing instructions (OS install) at the top and frequently changing ones (source code copy) at the bottom to maximize cache hits.

**D6 — Medium:** Order of checks:
1. Load Balancer logs: Is it a timeout or an explicit response from the app?
2. App Health Checks: Are pods restarting or failing readiness probes?
3. Resource Metrics: Check CPU/RAM spikes causing latency or crashes.
4. Downstream Dependencies: Check if a database or external API is timing out.

**D7 — Hard:** CAP Theorem states a distributed system can only provide two of three: Consistency, Availability, Partition Tolerance. 
- **CP (Consistency):** MongoDB/HBase (will refuse requests if they cannot guarantee consistency during a partition).
- **AP (Availability):** Cassandra/DynamoDB (returns the best available version of data even if not perfectly consistent).

**D8 — Medium:** Horizontal scaling adds more instances; Vertical scaling increases resources (CPU/RAM) on one instance. Patterns enabling horizontal scaling include statelessness (no session state on server), load balancing, and database sharding.

**D9 — Easy:** An environment variable is a dynamic value stored by the OS used for configuration. To persist across sessions in Linux, add `export VAR_NAME="value"` to your shell profile file (e.g., `~/.bashrc` or `~/.zshrc`).

**D10 — Easy:** JSON is a strict, machine-optimized format using braces `{}`. YAML is a human-readable superset of JSON using indentation. 
- **JSON Advantage:** Faster parsing speed and universal support.
- **YAML Advantage:** Readability and support for comments.

**D11 — Easy:** A REST API uses HTTP methods to manage resources. 
- **GET:** Retrieve resource.
- **POST:** Create new resource.
- **PUT:** Update/Replace existing resource.
- **DELETE:** Remove resource.

**D12 — Easy:** Version pinning is specifying an exact version of a dependency (e.g., `requests==2.31.0`) rather than a range. This ensures reproducible builds so that a library update doesn't introduce breaking changes into production unexpectedly.

**D13 — Easy:** Compiled languages are translated to binary before execution; Interpreted languages are read line-by-line at runtime.
- **Compiled:** C++, Rust.
- **Interpreted:** Python, JavaScript.

**D14 — Medium:** A forward proxy acts on behalf of the client (anonymity/filtering); a reverse proxy acts on behalf of the server (load balancing/security). 
- **NGINX:** Used as a Load Balancer or SSL terminator.
- **HAProxy:** High-performance TCP/HTTP load balancer for high-traffic apps.

**D15 — Medium:** A deadlock is a state where two or more processes are unable to proceed because each is waiting for the other to release a resource. Coffman conditions: 
1. Mutual Exclusion. 2. Hold and Wait. 3. No Preemption. 4. Circular Wait.

**D16 — Hard:** Eventual consistency means data will eventually be identical across all nodes if no new updates occur. Cassandra handles this via tunable consistency levels ($R+W > N$). Levels include `ONE` (fastest), `QUORUM` (majority agreement), and `ALL` (strongest consistency but lowest availability).

**D17 — Hard:** mTLS requires both client and server to present certificates. Handshake: Server sends cert $\rightarrow$ Client verifies it; then Client sends its own cert $\rightarrow$ Server verifies it. Once mutual trust is established, they negotiate a symmetric session key. Commonly used in Service Meshes like Istio for zero-trust networking.

**D18 — Hard:** A hash table uses a function to map keys to array indices. Collision resolution:
- **Chaining:** Each index holds a linked list of entries.
- **Open Addressing:** Finds the next empty slot (linear/quadratic probing).
**Complexity:** Average $O(1)$ for insertion, lookup, deletion. Worst case $O(n)$ if many collisions occur.

**D19 — Hard:** The circuit breaker prevents cascading failures by stopping requests to a failing service.
- **Closed:** Normal operation; traffic flows.
- **Open:** Failure threshold reached; fails fast immediately without calling the service.
- **Half-Open:** Periodically allows a few probes to see if the service has recovered.
It complements retry policies by ensuring retries don't overwhelm a struggling system (using exponential backoff).

**D20 — Hard:** 
- **Optimistic:** Assumes no conflict; checks version at commit time (e.g., MVCC or row versions). Use when contention is low. Example: `UPDATE ... WHERE version = 5`.
- **Pessimistic:** Locks the resource immediately so others cannot access it. Use for high-contention critical data. Example: `SELECT FOR UPDATE` in SQL.
