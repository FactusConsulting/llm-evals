## Application Architecture

**AA1 — Easy:** A **monolith** is a single, unified deployable unit where all business logic resides in one codebase. **Microservices** decompose the application into small, independent services organized around business capabilities. Three problems microservices introduce: 1) Distributed system complexity (network latency, partial failures), 2) Data consistency challenges (lack of ACID transactions across services), and 3) Operational overhead (monitoring, deployment, and service discovery for dozens of units instead of one).

**AA2 — Easy:** **Synchronous communication** requires the requester to wait for a response before proceeding (e.g., REST via HTTP or gRPC). **Asynchronous communication** involves sending a message without expecting an immediate response, allowing the sender to continue processing (e.g., RabbitMQ or Apache Kafka).

**AA3 — Medium:** A **reverse proxy** primarily handles request routing, load balancing, and SSL termination (e.g., Nginx). An **API Gateway** provides higher-level business logic at the edge, such as authentication, rate limiting, request transformation, and API composition. While an API Gateway can perform reverse proxy tasks, it doesn't always replace them; often, a reverse proxy sits in front of a gateway for raw performance, or the gateway incorporates proxy functionality internally.

**AA4 — Medium:** The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions, each with a corresponding "compensating transaction" to undo changes if a later step fails.
*   **Choreography:** Services exchange events without a central coordinator. Appropriate for simple workflows where decoupling is priority.
*   **Orchestration:** A central orchestrator tells services when to execute their local transactions. Appropriate for complex workflows requiring centralized visibility and control.

**AA5 — Medium:** **CQRS** separates read operations (Queries) from write operations (Commands), using different data models for each. It is paired with **Event Sourcing**, which stores state as a sequence of immutable events rather than current snapshots. This combination solves the limitation of traditional CRUD where high-read loads conflict with heavy writes, providing a perfect audit log and the ability to reconstruct state at any point in time.

**AA6 — Medium:** The **Circuit Breaker** prevents cascading failures by stopping requests to a failing service. States: **Closed** (traffic flows normally), **Open** (requests fail fast immediately), and **Half-Open** (limited traffic allowed to test if the service recovered). Unlike retry-with-backoff (which keeps trying), the Circuit Breaker stops all attempts entirely for a timeout period. Use both together by retrying only when the circuit is Closed or Half-Open.

**AA7 — Hard:** 
1.  **Shared DB/Schema:** Lowest cost, highest noisy-neighbor risk, lowest security isolation. High operational simplicity.
2.  **Separate Schema:** Moderate cost, better security (schema-level permissions), reduced noise risk. Higher migration complexity.
3.  **Separate DB:** Highest cost, maximum security and isolation, zero noisy-neighbor risk. Highest operational complexity (managing $N$ databases).

**AA8 — Hard:** **Strong consistency** ensures all clients see the same data simultaneously; **eventual consistency** guarantees that given enough time without updates, all replicas will converge. To prevent overselling inventory: use **strong consistency**. I would architect this using a distributed database with ACID properties (e.g., PostgreSQL) or a NoSQL store with linearizability (e.g., DynamoDB with strong consistent reads). At scale, I would shard by `product_id` so that locks are localized to specific shards, ensuring atomic decrements of stock levels.

**AA9 — Hard:** A **sidecar proxy** is a helper process running alongside an application container. In Istio, **Envoy** acts as the sidecar handling all network traffic. The **data plane** consists of these proxies; the **control plane** manages their configuration. mTLS between sidecars solves identity verification at the infrastructure level, removing the need for developers to implement TLS logic within the application code itself.

**AA10 — Medium:** The **Strangler Fig pattern** involves incrementally replacing legacy functionality with new services until the old system is gone. Strategy: 
1. Place a routing layer (API Gateway/Proxy) in front of the .NET Framework monolith. 
2. Implement new features in .NET 8 microservices. 
3. Route specific endpoints from the proxy to the new services while keeping others pointed at the monolith. 
4. Gradually migrate existing endpoints one-by-one until the monolith is "strangled" and can be decommissioned.

**AA11 — Medium:** The **12-Factor App** is a methodology for building cloud-native apps. Factors include: 1) Codebase (one repo), 2) Dependencies (explicitly declared), 3) Config (stored in environment), 4) Backing services (treated as attached resources), 5) Build, release, run (strict separation), 6) Processes (stateless). These ensure portability, scalability, and consistency across environments.

**AA12 — Hard:** 
*   **Coupling:** Kafka = Loose; REST/gRPC = Tight.
*   **Scalability:** Kafka handles massive throughput via partitioning; REST scales by adding instances behind a LB.
*   **Debugging:** REST is easier (request/response); Kafka requires distributed tracing to follow an event chain.
*   **Ordering:** Kafka guarantees order per partition key; REST has no inherent ordering.
*   **Failure:** REST uses retries; Kafka uses offsets and Dead Letter Queues (DLQs).
Choose Kafka for asynchronous data pipelines/event streams; choose gRPC/REST for low-latency request-response interactions.

**AA13 — Easy:** A **load balancer** distributes network traffic across multiple servers. **Layer 4 (L4)** balances based on IP and TCP/UDP ports. **Layer 7 (L7)** balances based on application content (HTTP headers, URLs). L7 is required for path-based routing (e.g., sending `/api` requests to one cluster and `/static` to another).

**AA14 — Easy:** A **message queue** (RabbitMQ) delivers messages to consumers and deletes them once acknowledged. A **log-based broker** (Kafka) appends messages to a persistent log that can be replayed from any offset. Pick RabbitMQ for complex task queuing with flexible routing; pick Kafka for high-throughput stream processing or when you need the ability to "replay" history.

**AA15 — Easy:** A **container** shares the host OS kernel and isolates processes via namespaces/cgroups; a **VM** includes a full guest OS running on a hypervisor. Containers are popular because they start in seconds, use fewer resources, and ensure the environment is identical from dev to production.

**AA16 — Easy:** **Stateless services** do not store client data between requests (e.g., an API using JWTs); **stateful services** remember previous interactions (e.g., a database or a cache). Stateless services scale horizontally easily because any instance can handle any request without needing local session state. Example: Web Frontend (stateless), Redis (stateful).

**AA17 — Easy:** An **ORM** maps object-oriented code to relational tables. Examples: Hibernate (Java), Entity Framework (.NET). Trade-offs: ORMs increase developer productivity and safety but introduce performance overhead and may generate inefficient SQL ("N+1 query problem") compared to raw SQL.

**AA18 — Medium:** The **Bulkhead pattern** isolates elements of an application into pools so that if one fails, others continue to function. In microservices, this prevents a single slow service from consuming all available threads in the system. Implementation: Use separate thread pools for different downstream dependencies or deploy critical paths onto dedicated hardware clusters.

**AA19 — Hard:** **OT** requires a central server to transform operations based on current state; **CRDTs** use mathematically commutative structures where order doesn't matter. CRDTs provide better offline support and lower latency as they don't require a central coordinator for conflict resolution. For a Google Docs clone with offline editing, I would choose **CRDTs**.

**AA20 — Hard:** Challenges include maintaining trace IDs across polyglot stacks. Context propagation is handled via headers (**W3C Trace Context**). **Head-based sampling** decides at the start whether to trace; **tail-based sampling** keeps traces only if they meet criteria (e.g., errors). Storage tools like **Jaeger/Tempo** index these spans. To ensure continuity through Kafka, the trace context must be injected into the Kafka record headers by the producer and extracted by the consumer.

## On-Premise Infrastructure Architecture

**OP1 — Easy:** **Type 1 (Bare-metal)** runs directly on hardware (ESXi, Xen); **Type 2 (Hosted)** runs atop an OS (VirtualBox, VMware Workstation).

**OP2 — Easy:** **SAN (Storage Area Network)** provides block-level storage over Fibre Channel or iSCSI; used for databases. **NAS (Network Attached Storage)** provides file-level storage over NFS or SMB; used for shared files/backups.

**OP3 — Medium:** **3-tier architecture** uses Core $\rightarrow$ Distribution $\rightarrow$ Access layers. Modern data centers prefer **Leaf-Spine** because it provides a non-blocking fabric with predictable latency for "East-West" traffic (server-to-server), eliminating the bottlenecks and Spanning Tree Protocol (STP) limitations of 3-tier designs.

**OP4 — Medium:** Use at least 3 nodes to maintain **quorum**. Shared storage can be **Ceph** (distributed across nodes) or external **iSCSI/NFS**. If a node fails: the cluster detects loss of heartbeat $\rightarrow$ triggers **fencing (STONITH)** to ensure the failed node is powered off $\rightarrow$ VMs are automatically restarted on remaining healthy nodes using the shared storage.

**OP5 — Medium:** **VLAN trunking** allows multiple VLANs to traverse a single physical link via **802.1Q tagging**, where each packet is tagged with a VLAN ID. On Linux, you configure this by creating sub-interfaces: `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6 — Medium:** RAID 1 (Mirror), 5 (Parity - $n-1$), 6 (Double Parity - $n-2$), 10 (Striped Mirrors), Z2 (ZFS double parity). For a database server with 6 drives, I would choose **RAID 10**. It provides the best balance of high IOPS (performance) and fault tolerance without the write penalty of parity calculations found in RAID 5/6.

**OP7 — Hard:** Use internal AD DNS for local resolution; split-horizon DNS ensures public users see only DMZ records while internals see all resources. External zones use DNSSEC for integrity. Recursive resolvers handle external queries; conditional forwarders route specific domain requests to other servers. When a laptop moves to VPN, DHCP pushes new DNS settings that tunnel traffic back to the internal authoritative servers.

**OP8 — Hard:** The chain starts at an offline **Root CA** $\rightarrow$ signs an **Issuing CA** $\rightarrow$ which signs end-entity certs. CRLs provide lists of revoked certs; OCSP allows real-time checks. A compromised Sub CA requires revoking its certificate via the Root; a compromised Root CA is catastrophic, requiring a full re-issue of every single certificate in the organization.

**OP9 — Hard:** MPLS (High cost, guaranteed QoS); IPsec VPN (Low cost, internet dependent); SD-WAN (Flexible, software-defined routing); WireGuard Mesh (Fast, modern). For 50 users per site with VoIP, I recommend **SD-WAN**. It provides the reliability of multiple transports (Internet + LTE) and critical Quality of Service (QoS) tagging to prioritize latency-sensitive voice traffic over general data.

**OP10 — Medium:** Out-of-band management (**iDRAC/iLO**) allows hardware control (power on/off, console access) regardless of OS state. This is critical for recovering crashed servers. If exposed to the internet, it's a critical vulnerability allowing attackers total physical-level control of the server.

**OP11 — Medium:** **LVM** manages logical volumes; **LVM-Thin** allows overprovisioning (allocating more than exists); **ZFS** combines FS and volume management with Copy-on-Write (CoW). ZFS snapshots are near-instant and highly efficient due to CoW, whereas LVM snapshots can degrade performance as they grow.

**OP12 — Hard:** Use a stretch cluster across sites with a third "witness" node in a separate location to maintain quorum. Ceph CRUSH rules must be configured to ensure replicas are distributed across different sites. Latency must typically stay below 5ms. A 2-site Ceph setup without a tiebreaker risks **split-brain**, where both sides think they are primary, leading to catastrophic data corruption.

**OP13 — Easy:** DHCP uses **DORA**: Discover $\rightarrow$ Offer $\rightarrow$ Request $\rightarrow$ Acknowledge. When the server is unavailable and the lease expires, Windows clients assign themselves an **APIPA address** ($169.254.x.x$).

**OP14 — Easy:** An unmanaged switch is plug-and-play. A **managed switch** provides VLANs, Spanning Tree Protocol (STP), SNMP monitoring, and port mirroring—essential for security, traffic segmentation, and troubleshooting in enterprises.

**OP15 — Easy:** **NTP** synchronizes clocks via network packets. Accurate time is critical for Kerberos authentication (which fails if drift $> 5\text{min}$), log correlation during forensics, and database replication consistency.

**OP16 — Easy:** Physical = Hardware; VM = Virtualized hardware on hypervisor; Container = Isolated process sharing kernel. Run workloads on bare metal when you need maximum IOPS (DBs), direct GPU access, or are running the hypervisors themselves.

**OP17 — Easy:** A **UPS** provides immediate battery power for short outages; a **generator** provides long-term fuel-based power. You need both because generators take seconds/minutes to start; the UPS bridges that gap. The **ATS (Automatic Transfer Switch)** detects power loss and switches from utility to generator automatically.

**OP18 — Medium:** Active-Passive has one standby server; Active-Active shares load. For PostgreSQL HA: use **Pacemaker/Corosync** to manage a **Virtual IP (VIP)**. If the primary fails, Pacemaker triggers **STONITH** (fencing) to kill the failed node, then moves the VIP to the passive node to promote it to primary.

**OP19 — Hard:** Use the **3-2-1 rule**: 3 copies of data, 2 different media, 1 offsite. RPO defines acceptable data loss; RTO defines recovery time. I would use Full backups weekly $\rightarrow$ Incremental daily. Implement deduplication to save space. Immutable backups (S3 Object Lock or air-gapped tape) protect against ransomware. Backup is the *copy* of data; Disaster Recovery is the *entire plan* to restore operations at a secondary site.

**OP20 — Hard:** **802.1X** uses three roles: **Supplicant** (client), **Authenticator** (switch), and **Auth Server** (RADIUS). EAP-TLS uses certificates for high security; PEAP uses passwords. RADIUS assigns VLANs dynamically based on user identity. Devices that fail auth are put in a "Guest" VLAN or blocked. **MAB (MAC Authentication Bypass)** allows devices like printers (which can't run supplicants) by validating their MAC address against a whitelist in the RADIUS server.
