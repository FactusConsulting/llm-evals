## OpenTofu / Terraform

**T1** — `tofu plan` is a read-only operation that performs a refresh of the state and compares the current configuration against the real-world infrastructure to create an execution plan. `tofu apply` executes that plan to reach the desired state.

**T2** — State is a JSON file that maps your configuration to real-world resources and tracks metadata. Remote state is critical for team collaboration (shared source of truth), state locking (preventing concurrent writes), and security (storing sensitive data outside local machines).

**T3** — `count` uses an integer index (0, 1, 2...), making it difficult to remove items from the middle without shifting indices. `for_each` uses a map or set of strings, allowing you to add/remove specific items without affecting others. `for_each` is preferred for managing collections of resources where identity matters.

**T4** — This is "configuration drift." During the next `plan`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy between the real-world state and the state file, then proposes changes (e.g., an update or a recreation) to bring the resource back in line with the configuration.

**T5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

**T6** — `terraform_remote_state` reads the entire state file of another workspace, which can expose sensitive data and creates tight coupling. Output values are cleaner but require the other workspace to be a separate run. The recommended alternative is using **Module Outputs** passed directly between parent/child modules, or using a dedicated **Service Discovery/KV store** (like Consul) for decoupled architectures.

**T7** — The `null_resource` is being evaluated, but the `remote-exec` provisioner runs during the *apply* phase, not the *plan* phase. If the output is calculated based on the result of that provisioner, the value isn't available until the resource is fully created. **Fix:** Use a `local-exec` to write the kubeconfig to a file, or better, use a native provider/resource that manages the cluster state rather than relying on provisioners.

**T8** — `import` brings existing infrastructure under Tofu management. Limitations: It doesn't generate code (historically) and requires manual state manipulation. The `import` block (1.5+) allows you to define the import in code, making it declarative, easier to review in PRs, and allows `tofu plan` to show exactly what will happen before the import is finalized.

**T9** — A `variable` is an input parameter used to make configurations dynamic. An `output` is a return value used to expose information (like an IP address) to the user or other modules.

**T10** — A provider is a plugin that translates Tofu code into API calls for a specific platform (AWS, Azure, etc.). If you run `plan` without `init`, Tofu will fail because it hasn't downloaded the necessary provider binaries to the `.terraform` directory.

**T11** — It is the dependency lock file that records the exact versions and hashes of providers used. It should be committed to ensure all team members and CI/CD pipelines use identical provider versions, preventing "it works on my machine" issues.

**T12** — `tofu destroy` removes all resources managed by the current state. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

**T13** — A data source allows you to fetch information from existing infrastructure that is *not* managed by your current Tofu code. **Example:** Fetching an existing VPC ID or an AMI ID created by a different team.

**T14** — `variables` are external inputs (passed via CLI, `.tfvars`, or env vars). `locals` are internal constants/expressions used to simplify code or avoid repetition. Use `locals` for complex logic or derived values that should not be changed by the user.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime updates).
- `prevent_destroy`: Stops Tofu from destroying a resource (useful for production databases).
- `ignore_changes`: Tells Tofu to ignore updates to specific attributes (useful when external processes, like Auto Scaling, modify a resource).

**T16** — The `moved` block allows you to rename a resource or move it into a module within your code. It tells Tofu: "This new address in the code is actually the same as this old address in the state," preventing the resource from being destroyed and recreated during refactoring.

**T17** — The graph is a Directed Acyclic Graph (DAG). **Implicit dependencies** are created when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are created via `depends_on`. `depends_on` forces a strict order, reducing parallelism. It should be used sparingly because it can unnecessarily slow down execution by preventing independent resources from being created simultaneously.

**T18** — 
1. **State Splitting:** Break a monolithic state into smaller, decoupled states (Tradeoff: increased complexity in managing cross-state dependencies).
2. **Targeted Refactoring:** Use `moved` blocks to avoid massive refreshes (Tradeoff: requires careful planning).
3. **Reduce Refreshing:** Use `-refresh=false` (Tradeoff: risks acting on stale data).
4. **Increase Parallelism:** Adjust `-parallelism=n` (Tradeoff: can hit API rate limits).

**T19** — State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a CI pipeline crashes, the lock remains in the backend (e.g., DynamoDB). You can manually break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually still running, force-unlocking can lead to state corruption or resource duplication.

**T20** — 
1. Ensure the new S3 bucket and DynamoDB table exist.
2. Update the `backend` block in your `.tf` files.
3. Run `tofu init -migrate-state`. Tofu will detect the change and ask to copy the state from local to S3.
4. Confirm the migration.
5. **Verify:** Run `tofu plan`. If it shows "No changes," the migration was successful and the state is correctly mapped.

## Ansible

**A1** — A **task** is a single action (e.g., "install nginx"). A **playbook** is a collection of plays that map tasks to hosts. A **role** is a structured, reusable way to bundle tasks, variables, files, and templates into a single unit.

**A2** — `ansible_facts` is a dictionary of system information gathered by Ansible. Access the OS family via `ansible_facts['os_family']` (or `ansible_os_family`).

**A3** — `command`: Executes a command without a shell environment (most secure, no pipes/redirects). `shell`: Executes via `/bin/sh` (allows pipes, redirects, and environment variables). `raw`: Executes via a raw SSH connection without needing Python on the target (used for bootstrapping).

**A4** — Idempotency means running a task multiple times results in the same state without extra changes. 
- **Idempotent:** `apt: name=nginx state=present` (if installed, does nothing).
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file.txt` (appends every time it runs).

**A5**
```yaml
- name: Install htop
  package:
    name: "{{ 'epel-release' if ansible_os_family == 'RedHat' else '' }} htop"
    state: present
  when: ansible_os_family == 'RedHat' or ansible_os_family == 'Debian"
```
*(Note: A cleaner way is using two separate tasks with `when` clauses).*

**A6** — Order (lowest to highest): `role defaults` < `inventory group_vars` < `inventory host_vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process hosts in batches of 3. To ensure the first 3 are "ready," use a `wait_for` task or a health check task within the play. If the first batch fails, the playbook stops.

**A8** — `ansible-vault` encrypts files. To encrypt a single variable, you typically use a separate `vars` file that is encrypted, or use the `!vault` directive in a template/variable file (though this is more advanced). Most commonly, users encrypt the entire file containing the secret.

**A9** — An **inventory** is a list of managed hosts. **Static** is a hardcoded file (INI/YAML). **Dynamic** is a script or plugin that queries a cloud provider (AWS/GCP) to get the current list of hosts.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **handler** is a special task that only runs when "notified" by another task that reported a `changed` status. It is used for actions like "restart service" only when a config file changes. Trigger it using `notify: handler_name`.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory` (path to inventory), `remote_user` (default user), and `forks` (number of parallel processes).

**A13** — `register` saves the output of a task into a variable. You can then use that variable in a `when` clause or a `debug` task (e.g., `when: result.rc == 0`).

**A14** — `import_tasks` is **static** (processed at playbook parsing time). `include_tasks` is **dynamic** (processed during runtime). Use `include_tasks` if you need to use a variable to determine which file to include; use `import_tasks` for better performance and error checking during parsing.

**A15** — **Ansible Galaxy** is a public repository for roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16** — **ssh**: Standard connection via SSH (most common). **local**: Runs tasks on the control node itself. **network_cli**: Used for network devices (switches/routers) that don't have Python.

**A17** — `delegate_to` runs a task on a different host than the current one. `run_once` ensures a task runs only once for the entire play. 
**Example:**
```yaml
- name: Get remote IP
  set_fact:
    remote_ip: "{{ ansible_default_ipv4.address }}"
- name: Register IP on localhost
  shell: "echo {{ remote_ip }} >> local_log.txt"
  delegate_to: localhost
  run_once: true
```

**A18** — 
1. **Forks:** Increase `forks` in `ansible.cfg` (Tradeoff: higher CPU/RAM usage on control node).
2. **Pipelining:** Enable `pipelining = True` (Tradeoff: requires `requiretty` to be disabled in SSH).
3. **Fact Caching:** Use Redis/JSON for facts (Tradeoff: complexity in managing the cache).
4. **Mitogen:** Use the Mitogen plugin (Tradeoff: significantly faster but can occasionally conflict with complex custom modules).

**A19** — `{{ }}` is for expressions/variables. `{% %}` is for control logic (loops/ifs). `{# #}` is for comments.
```jinja2
upstream myapp {
{% for server in backend_servers %}
    server {{ server.ip }}:{{ server.port }}; # Health check: {{ server.status }}
{% endfor %}
}
```

**A20** — 
1. Use `serial: 1` or `serial: 20%` to control batch size.
2. **Pre-task:** Use `uri` module to tell the Load Balancer to remove the host from rotation.
3. **Deploy:** Perform the application update.
4. **Health Check:** Use `uri` module to poll the local app endpoint until it returns `200 OK`.
5. **Post-task:** Re-add the host to the Load Balancer.
6. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, trigger a task to revert the version and re-add the host to the LB.
