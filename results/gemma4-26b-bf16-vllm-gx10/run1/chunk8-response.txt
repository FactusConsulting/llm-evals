### Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and apps. *Ex: AWS EC2.* **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying OS/runtime. *Ex: Azure App Service.* **SaaS (Software as a Service):** Fully managed software delivered over the web. *Ex: Google Workspace.*

**CL2** — The provider is responsible for the "Security **of** the Cloud" (physical hardware, global infrastructure); the customer is responsible for "Security **in** the Cloud" (data, configurations).
* **IaaS VMs:** Provider handles hardware/hypervisor; You handle OS, patching, and apps.
* **Managed Kubernetes:** Provider handles Control Plane; You handle worker nodes (partially), pods, and network policies.
* **SaaS (M365):** Provider handles almost everything; You handle identity, access, and data governance.

**CL3** — **VPC:** A private isolated network. **Subnet:** A range of IP addresses within a VPC. **Security Group (SG):** A virtual firewall for *instances* (stateful). **NACL:** A firewall for *subnets* (stateless). They layer as: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ SG $\rightarrow$ Instance. **Stateful (SG):** If you allow inbound traffic, outbound response is automatically allowed. **Stateless (NACL):** You must explicitly define both inbound and outbound rules for traffic to flow.

**CL4** — **Landing Zone:** A pre-configured, multi-account environment with baseline security/compliance. **OUs (Organizational Units):** Logical groupings of accounts (e.g., Prod, Dev, Security). **Guardrails:** Automated policies (SCPs in AWS) to prevent non-compliant actions. **Shared Networking:** Using a Hub-and-Spoke (Transit Gateway/Azure Virtual WAN) to centralize inspection and connectivity. **Centralized Logging:** Aggregating all logs into a dedicated security account. **Single-account problem:** Blast radius is too large; difficulty in applying granular permissions; lack of isolation for billing and compliance.

**CL5** — **IaC:** Managing infrastructure via machine-readable files.
* **Terraform/OpenTofu:** Declarative, provider-agnostic, massive ecosystem. *Use for: Multi-cloud/General purpose.*
* **Pulumi:** Uses general-purpose languages (Python, TS). *Use for: Dev-heavy teams wanting complex logic.*
* **CloudFormation/Bicep:** Native to AWS/Azure. *Use for: Deepest integration with specific cloud features.*
* **Crossplane:** Kubernetes-native IaC. *Use for: Managing cloud resources via K8s APIs/GitOps.*

**CL6** — **HPA:** Scales pods based on CPU/RAM. **VPA:** Adjusts pod resource requests/limits. **Cluster Autoscaler:** Adds/removes VM nodes to the cluster. **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag or RabbitMQ queue depth). **KEDA vs HPA:** Use KEDA when scaling needs to be triggered by external event sources rather than just resource metrics.

**CL7** — **RPO (Recovery Point Objective):** Max data loss allowed. **RTO (Recovery Time Objective):** Max downtime allowed.
* **Active-Active:** Traffic split across regions; zero/near-zero RTO/RPO; highest cost.
* **Active-Passive:** One region idle; failover required; moderate RTO/RPO.
* **Replication:** **Sync** (no data loss, high latency) vs **Async** (low latency, potential data loss).
* **DNS:** Route53/Traffic Manager handles health checks and redirects traffic.
* **DR Types:** **Pilot Light** (minimal core services running, DB live); **Warm Standby** (scaled-down version of full stack running); **Multi-site Active-Active** (full capacity in both).

**CL8** — **GitOps:** Using Git as the "Single Source of Truth" for desired state. **ArgoCD vs FluxCD:** ArgoCD has a powerful UI and multi-tenant features; FluxCD is lightweight, CLI-driven, and follows a "pull" model more strictly. **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from AWS SM/Vault), or **Vault** (dynamic injection). **Drift:** GitOps controllers detect the difference and automatically overwrite manual changes to match the Git state.

**CL9** — Use a **StatefulSet** to ensure stable network IDs and ordered deployment. Use **Local Persistent Volumes (PV)** with a **Local Storage Class** for low-latency disk access. Use a **Headless Service** for direct pod-to-pod communication. Use **Init Containers** to prepare the filesystem or download configs. Mount **ConfigMaps** as volumes to specific paths. Implement **Pod Disruption Budgets (PDB)** to ensure a minimum number of replicas remain available during maintenance.

**CL10** — **Service Account:** K8s identity for pods. **Workload Identity/IRSA:** A mechanism to map a K8s Service Account to a Cloud IAM Role. **Bad Practice:** Mounting long-lived static credentials (JSON keys) in pods is a massive security risk if the pod is compromised. **Workload Identity Federation:** Uses OIDC to allow the cloud provider to trust the K8s cluster, exchanging a short-lived K8s token for a temporary cloud IAM token.

**CL11** — **Object (S3/Blob):** Unstructured data (images, logs). High durability ($11 \times 9$s), high latency. **Block (EBS/Disk):** Raw volumes for OS/Databases. Low latency, high IOPS. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB) for multiple instances. **Guarantees:** Object is most durable; Block is most performant for single-node; File is best for shared state.

**CL12** — **Zero-Trust:** "Never trust, always verify." **Architecture:** **Network Policies** (L3/L4 isolation), **Service Mesh (Istio/Linkerd)** for mTLS (L7 identity/encryption), **Pod Identity** (no static keys), **Admission Controllers** (enforce policies like "no root containers"), **Image Signing** (Cosign/Notary), **Runtime Security** (Falco to detect anomalous syscalls), **Secrets Management** (Vault). **Difference:** Traditional security relies on a "hard shell" (perimeter); Zero-Trust assumes the perimeter is breached and secures every individual request/identity.

**CL13** — **CDN:** A distributed network of proxy servers that caches content closer to users. **How:** User requests $\rightarrow$ Edge Location $\rightarrow$ Cache Hit (fast) or Cache Miss (fetch from origin). **Services:** AWS CloudFront, Azure Front Door. **When:** Use CDN for static assets (JS, CSS, Images) or global low-latency delivery; use Origin directly for highly dynamic, non-cacheable, or private data.

**CL14** — **Region:** A geographic area (e.g., us-east-1). **AZ (Availability Zone):** One or more discrete data centers within a region. **Why Multi-AZ:** To protect against a single data center failure (power, cooling, networking). **Zonal:** Tied to one AZ (e.g., EBS). **Regional:** Available across all AZs in a region (e.g., S3, IAM).

**CL15** — **Managed DB:** A service where the provider manages the engine. **Provider handles:** Patching, backups, hardware provisioning, high availability/failover, and scaling. **You handle:** Schema design, query optimization, and access control.

**CL16** — **IAM Users:** Individual people/apps. **Groups:** Collections of users. **Roles:** Temporary identities assumed by entities. **Policies:** JSON documents defining permissions. **Least Privilege:** Granting only the minimum permissions required to perform a task. **Application:** Use Roles instead of Users, use fine-grained IAM policies, and audit with Access Analyzer.

**CL17** — **Serverless:** Computing model where the provider manages the server lifecycle. **Comparison:** Lambda (AWS), Functions (Azure), Cloud Functions (GCP). **Cold Start:** Latency incurred when a function is invoked after being idle (container spin-up). **Poor fit:** Long-running processes, high-performance computing (HPC), or applications requiring constant, predictable low latency.

**CL18** — **Ingress Resource:** Standard K8s API for L7 routing. **Gateway API:** The modern successor; more expressive, separates roles (Infra vs App). **Cloud LB Annotations:** Uses cloud-specific settings to provision a provider LB. **Service Mesh Ingress:** Uses a mesh gateway (e.g., Istio) for advanced L7 features. **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Service Mesh. **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenant environments, and better separation of concerns.

**CL19** — **Strategy:**
* **Compute:** Use **Reserved Instances/Savings Plans** for baseline; **Spot** for stateless/batch; **Right-sizing** via tools like AWS Compute Optimizer.
* **Storage:** Move old data to **S3 Glacier/Archive**; use **Intelligent-Tiering**.
* **FinOps:** Implement **Tagging** for cost allocation. Use **Showback** (reporting costs to teams) or **Chargeback** (billing teams directly).
* **Tools:** AWS Cost Explorer, CloudHealth, or Kubecost for K8s.

**CL20** — **Strategy:** Use **Kubernetes** as the abstraction layer to make workloads portable. Use **Terraform** for infrastructure. Use **Identity Federation** (OIDC) to bridge IAM. Use **VPN/Direct Connect** for inter-cloud networking. **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs. **Justification:** Necessary for extreme regulatory compliance or massive scale; unnecessary for most companies where "single-cloud with multi-region" suffices.

### OT Infrastructure Architecture

**OT1** — **Purdue Model:** A framework for ICS security.
* **Level 0:** Physical process (sensors, actuators).
* **Level 1:** Basic Control (PLCs, RTUs).
* **Level 2:** Area Supervisory Control (HMIs, SCADA).
* **Level 3:** Site Operations (Historians, MES).
* **Level 4/5:** Enterprise/Business (ERP, Internet).

**OT2** — **IT:** Focuses on Data Confidentiality/Integrity. **OT:** Focuses on Availability/Safety. **Patching:** You cannot patch OT systems like IT because reboots can cause physical damage, loss of production, or safety hazards.

**OT3** — **IDMZ:** A buffer zone between IT and OT. **Traffic:** Only highly inspected, proxied traffic (e.g., data from Historian to ERP). **Direction:** Usually "Push" from OT to IT. **Danger:** Direct L4 $\rightarrow$ L1 connectivity allows a compromised laptop in the office to send malicious commands directly to a PLC, bypassing all monitoring.

**OT4** — 1. **Modbus TCP:** Level 1/2 (Fieldbus/Control). 2. **OPC UA:** Level 2/3 (Supervisory/Integration). 3. **EtherNet/IP:** Level 1/2 (Control). 4. **PROFINET:** Level 1/2 (Real-time Control). 5. **MQTT:** Level 3/4 (Edge-to-Cloud/IIoT).

**OT5** — **Data Diode:** Hardware that allows data to flow in only one direction (physically impossible to go back). **Firewall:** Software-based, bidirectional, rule-based. **Use Diode:** For high-security environments (Nuclear/Water) where data must leave but no commands can enter. **Limitation:** Firewalls allow bidirectional communication (needed for many protocols); Diodes break standard TCP handshakes without specialized proxies.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway (converts to MQTT) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. **Security:** Place the IDMZ between the Historian and the Edge Gateway; use a firewall to restrict the Gateway to only outbound MQTT traffic.

**OT7** — **Zone:** A grouping of assets with similar security requirements. **Conduit:** A communication path between zones. **Model:**
* **Zone 1:** SIS (Highest security, isolated).
* **Zone 2:** PLCs/Control.
* **Zone 3:** SCADA/HMI.
* **Zone 4:** Engineering Workstations.
* **Zone 5:** Corporate.
* **Conduits:** Strictly controlled firewalls/unidirectional gateways between each zone.

**OT8** — **Strategy:** Segment by production line using **VLANs**. Place **Industrial Firewalls** between lines and between the plant and the IT network. Use **Managed Switches** with port security. **Remote Access:** Use a secure Jump Host in the IDMZ with MFA. **Transition:** Use "Monitor Mode" on switches first to map traffic before enforcing blocking rules to avoid production downtime.

**OT9** — **SIS:** Independent system that shuts down the process if it becomes unsafe. **BPCS:** The system that runs the day-to-day process. **IEC 61511:** Standard for functional safety. **Isolation:** SIS must be isolated so a compromise of the BPCS (which is more connected) cannot disable the safety shutdown. **Ransomware on SIS:** Could prevent a safe shutdown during an emergency, leading to explosions or environmental catastrophe.

**OT10** — **PLC:** Small, logic-based controller for specific tasks. **DCS (Distributed Control System):** Large-scale, integrated system for complex continuous processes (e.g., oil refinery). **SCADA:** Supervisory system for geographically dispersed assets. **Coexistence:** Yes, SCADA often supervises multiple PLCs/DCS units.

**OT11** — **Architecture:** Users connect to a VPN $\rightarrow$ Jump Host in IDMZ $\rightarrow$ MFA $\rightarrow$ Session Recording. **Why not RDP to HMI:** Direct RDP exposes the HMI (a critical control asset) to the entire corporate network, making it a target for lateral movement and brute force.

**OT12** — **Plan:** 1. **Detection:** Deploy OT-IDS (e.g., Nozomi/Claroty) to find anomalous traffic. 2. **Inventory:** Verify all assets via passive monitoring. 3. **Response:** Isolate the compromised VPN segment. 4. **Coordination:** Alert the Control Room immediately. 5. **Safety:** The **Plant Operator** has the final authority; they decide if the process must be manually shut down for safety, regardless of IT security needs.

**OT13** — **HMI:** A dashboard for operators to monitor/control the process. **Engineering Workstation:** A high-privilege machine used to program PLCs and change logic. HMIs are for *operation*; Engineering Workstations are for *configuration*.

**OT14** — **Historian:** A database that records time-series process data. **Importance:** Essential for troubleshooting, regulatory compliance, and optimization. **Plant Historian (L3):** High-resolution, local, real-time. **Enterprise Historian (L4):** Aggregated, lower-resolution, used for business analytics.

**OT15** — **Ladder Logic:** A graphical programming language resembling electrical relay diagrams. **Device:** PLC. **Dominance:** It is intuitive for electricians/engineers trained in electrical circuits and is highly deterministic.

**OT16** — **RTU (Remote Terminal Unit):** Designed for long-distance, low-bandwidth, harsh environments (e.g., remote pipelines). **Difference:** PLCs are better for high-speed, local logic; RTUs are better for telemetry and wide-area communication.

**OT17** — **Analog:** Continuous signal (4-20mA). **Digital:** Discrete (On/Off). **4-20mA vs 0-20mA:** 4-20mA allows for "Live Zero." If the signal is 0mA, you know there is a wire break (fault). If it were 0-20mA, 0mA could just mean a valid "zero" reading.

**OT18** — **Inventory:** You cannot protect what you don't know exists. **Techniques:** **Passive Monitoring** (sniffing traffic) is safe. **Active Scanning** (Nmap/Ping) is **dangerous** because old OT devices can crash when receiving unexpected packets or high volumes of traffic.

**OT19** — **MITRE ATT&CK for ICS:** 1. **Inhibit Response Function** (e.g., disabling an alarm). 2. **Impair Process Control** (e.g., changing setpoints). 3. **Loss of Safety** (e.g., disabling SIS). 4. **Impair Process Safety** (e.g., manipulating sensors). 5. **Damage to Property** (e.g., over-pressurizing a tank). **Difference:** It focuses on physical consequences/process impact rather than just data theft.

**OT20** — **SOC Design:** 1. **Collection:** Use passive TAPs/SPAN ports to avoid latency. 2. **Integration:** Feed OT-IDS alerts into a SIEM. 3. **Rules:** Look for "New PLC," "Logic Download," or "Unauthorized Protocol." 4. **Triage:** IT analysts handle network alerts; OT engineers must validate if the alert is a physical process anomaly. 5. **Firmware Alert:** Treat as a critical incident; immediately isolate the PLC and verify the physical state of the process with the operator.
