## Application Architecture

**AA1** — A **Monolith** is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. **Microservices** decompose the application into small, independent services communicating over a network.
*   **3 Problems of Microservices:** 1. Network latency/unreliability; 2. Distributed data consistency (no ACID across services); 3. Operational complexity (observability, deployment, service discovery).

**AA2** — **Synchronous:** The caller waits for a response before proceeding (e.g., HTTP/REST). **Asynchronous:** The caller sends a message and continues without waiting for an immediate result (e.g., RabbitMQ/AMQP).

**AA3** — An **API Gateway** is an application-level entry point that handles routing, authentication, rate limiting, and protocol translation. A **Reverse Proxy** (like Nginx) primarily handles load balancing and SSL termination. An API Gateway *can* replace a reverse proxy for many web use cases, but it cannot replace a low-level reverse proxy used for specialized TCP/UDP load balancing or high-performance static file serving.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. If one fails, "compensating transactions" undo the previous steps.
*   **Choreography:** Services exchange events without a central controller. Best for simple workflows with few services.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows with many steps.

**AA5** — **CQRS** separates read (Query) and write (Command) models. It is paired with **Event Sourcing** (storing state as a sequence of events) because the event log provides the "source of truth" to rebuild the read models. This solves the problem of "impedance mismatch" and allows highly optimized, scalable read views that traditional CRUD (which uses a single model for both) cannot provide.

**AA6** — The **Circuit Breaker** prevents a system from repeatedly trying an operation that is likely to fail.
*   **States:** 1. **Closed** (requests flow); 2. **Open** (requests fail immediately); 3. **Half-Open** (limited requests allowed to test recovery).
*   **Difference:** Retry with backoff handles *transient* errors; Circuit Breaker handles *persistent* failures to prevent cascading failure. Use them together by wrapping a retry logic inside a circuit breaker.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, highest density, lowest complexity. Highest security risk (data leakage) and highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Moderate cost/complexity. Better security (schema-level permissions), moderate noisy-neighbor risk.
3. **Separate DB:** Highest cost and operational complexity. Highest security (physical isolation) and lowest noisy-neighbor risk.

**AA8** — **Strong Consistency** ensures all reads see the latest write. To prevent overselling:
*   **Model:** Strong Consistency.
*   **Data Store:** Relational DB (PostgreSQL/MySQL) with ACID properties or a distributed SQL DB (CockroachDB/Spanner).
*   **Patterns:** Use **Pessimistic Locking** (SELECT FOR UPDATE) or **Atomic Increments** at the database level to ensure inventory cannot drop below zero.

**AA9** — A **Sidecar Proxy** is a helper process running alongside a service to handle networking. In **Istio**, **Envoy** is the sidecar (Data Plane) that intercepts all traffic; **Istio Control Plane** (istiod) manages and pushes configurations to Envoy. **mTLS** between sidecars solves the problem of "identity" and "encryption in transit" without requiring the application code to manage certificates or trust.

**AA10** — **Strangler Fig Pattern:** Incrementally replace functionality.
*   **Strategy:** 1. Place an API Gateway/Proxy in front of the .NET Framework monolith. 2. Identify a single bounded context (e.g., "Billing"). 3. Build "Billing" as a new .NET 8 microservice. 4. Update the Gateway to route "Billing" traffic to the new service while everything else goes to the monolith. 5. Repeat until the monolith is "strangled."

**AA11** — **12-Factor App:** 1. **Codebase** (one repo per app); 2. **Dependencies** (explicitly declare); 3. **Config** (store in environment); 4. **Backing services** (treat as attached resources); 5. **Build, release, run** (strict separation); 6. **Processes** (stateless); 7. **Port binding** (self-contained); 8. **Concurrency** (scale via process model); 9. **Disposability** (fast startup/shutdown); 10. **Dev/prod parity** (keep environments similar). These ensure portability, scalability, and automation in cloud environments.

**AA12** — 
*   **Event-Driven (Kafka):** High decoupling, massive scalability, high debugging complexity, strict ordering (within partitions), complex failure handling (dead letter queues). Use for: asynchronous workflows, data pipelines.
*   **Request-Driven (REST/gRPC):** Tight coupling, lower scalability (synchronous blocking), easier debugging, no inherent ordering, simpler failure handling (immediate error). Use for: real-time user interactions, synchronous CRUD.

**AA13** — A **Load Balancer** distributes traffic across multiple servers. **Layer 4 (L4)** operates at the Transport layer (TCP/UDP) using IP/Port. **Layer 7 (L7)** operates at the Application layer (HTTP/HTTPS) using headers/cookies/URLs. **L7 Use Case:** Routing traffic to different microservices based on the URL path (e.g., `/api/users` vs `/api/orders`).

**AA14** — A **Message Queue** (RabbitMQ) is designed for task distribution; once a message is consumed, it is typically deleted. A **Log-based Broker** (Kafka) is an append-only log; messages persist and can be replayed by multiple consumers. Pick **RabbitMQ** for complex routing/task queues; pick **Kafka** for high-throughput stream processing and event replayability.

**AA15** — A **Container** is an isolated user-space process sharing the host OS kernel. A **VM** includes a full guest OS and a hypervisor. Containers are popular because they are lightweight, start instantly, and ensure "it works on my machine" consistency across environments.

**AA16** — **Stateless:** Does not store client data between requests (e.g., a REST API). **Stateful:** Stores data locally (e.g., a database or a session-heavy app). Stateless services scale horizontally easily because any instance can handle any request; stateful services require complex synchronization or "sticky sessions."

**AA17** — **ORM** maps database tables to programming objects. Examples: **Hibernate** (Java), **Entity Framework** (C#). **Trade-offs:** ORMs increase developer productivity and security (SQL injection protection) but can introduce performance overhead and "N+1" query problems compared to optimized raw SQL.

**AA18** — **Bulkhead Pattern** isolates elements into pools so that if one fails, others continue. In microservices, this prevents a single failing service from consuming all system resources. **Implementation:** Use separate **thread pools** for different downstream service calls so that a slow service only exhausts its own pool, or use **separate deployment groups** (clusters) to ensure a failure in one domain doesn't impact another.

**AA19** — **OT** requires a central server to sequence operations; high complexity but low latency for users. **CRDTs** allow decentralized, peer-to-peer updates that mathematically resolve to the same state; lower complexity for distributed systems and superior **offline support** because changes can be merged whenever the user reconnects without a central authority. **Choice:** CRDTs for offline support.

**AA20** — **Challenges:** Maintaining a single trace ID across different languages and protocols. **Context Propagation:** Passing IDs via headers (W3C Trace Context/B3). **Sampling:** *Head-based* (decide at start) vs *Tail-based* (decide after seeing the whole trace, better for catching errors). **Asynchronous:** To ensure continuity in Kafka, the producer must inject the trace context into the **Kafka Message Headers**, and the consumer must extract it to start a child span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., VMware ESXi, Xen). **Type 2 (Hosted):** Runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network):** Block-level storage, high performance, used for databases/VM disks. Protocols: Fibre Channel, iSCSI. **NAS (Network Attached Storage):** File-level storage, easier to share files. Protocols: NFS, SMB/CIFS.

**OP3** — **3-Tier:** Core $\rightarrow$ Distribution $\rightarrow$ Access. **Leaf-Spine:** Every Leaf switch connects to every Spine switch. It solves the "east-west" traffic bottleneck in modern data centers by providing predictable, low-latency, non-blocking paths between servers.

**OP4** — **Architecture:** $\ge$ 3 nodes for quorum. **Quorum:** Ensures a majority of nodes agree on state to prevent split-brain. **Fencing:** (e.g., STONITH) kills a rogue node to protect data. **Storage:** Ceph (distributed/software-defined) is preferred for high availability. **Failure:** If a node fails, the cluster detects loss of heartbeat, fencing occurs, and VMs are restarted on remaining nodes using the shared storage.

**OP5** — **VLAN Trunking:** Carrying multiple VLANs over a single link. **802.1Q:** Adds a tag to the Ethernet frame header to identify the VLAN. **Linux Config:** Use `ip link add link eth0 name eth0.10 type vlan id 10` to create sub-interfaces.

**OP6** — **RAID 1:** Mirroring. **RAID 5:** Parity (1 drive loss). **RAID 6:** Double parity (2 drive loss). **RAID 10:** Mirroring + Striping (high perf/fault tolerance). **RAID Z2:** ZFS equivalent of RAID 6. **Choice:** **RAID 10** for a database; it provides the best IOPS (performance) and fastest rebuild times/fault tolerance.

**OP7** — **Architecture:** 
*   **Internal AD:** Uses internal DNS for domain resources. 
*   **DMZ:** Uses authoritative servers for public records. 
*   **Split-Horizon:** Same domain name (e.g., `corp.com`) resolves to internal IPs for employees and public IPs for the internet. 
*   **DNSSEC:** Adds digital signatures to prevent spoofing. 
*   **Movement:** A laptop on VPN uses **Conditional Forwarders** to reach internal DNS; when moving to the office, it uses local **Recursive Resolvers**.

**OP8** — **Chain:** Root CA $\rightarrow$ Subordinate/Issuing CA $\rightarrow$ End-entity. **Deployment:** Root CA is kept **offline** to prevent total compromise. Subordinate CAs handle daily requests. **CRL/OCSP:** Methods to check if a cert is revoked. **Compromise:** A compromised Subordinate CA can issue fake certs for its scope; a compromised Root CA invalidates the *entire* organization's trust.

**OP9** — **Recommendation:** **SD-WAN**. It provides the best balance of cost (uses internet) and reliability/performance (intelligent path selection for VoIP) with centralized management. **MPLS** is more reliable/low-latency but much more expensive. **WireGuard** is highly secure/fast but harder to manage at scale for 250 users.

**OP10** — **iDRAC/iLO/IPMI:** Out-of-band management interfaces that allow hardware control (power, BIOS) even if the OS is crashed. **Criticality:** Allows remote recovery without physical presence. **Risk:** If exposed to the internet, attackers can gain full control of the hardware/server.

**OP11** — **LVM:** Logical volume management (standard). **LVM-Thin:** Allows over-provisioning and fast snapshots. **ZFS:** Integrated file system/volume manager with copy-on-write. **Snapshots:** LVM/LVM-Thin use COW/pointers; ZFS uses COW (extremely robust and efficient). Use ZFS for data integrity; LVM for simple disk management.

**OP12** — **Strategy:** A **Stretch Cluster** across two sites. **Ceph:** Use **CRUSH rules** to ensure replicas are placed in different sites. **Monitors:** Must have an odd number (e.g., 3 or 5) to maintain quorum. **Latency:** Requires very low latency (usually $<5$ms RTT). **Split-brain:** If sites lose connectivity, both might try to be "primary." **2-site issue:** Without a 3rd site (tiebreaker/witness), the cluster cannot reach a majority decision during a partition.

**OP13** — **DORA:** **D**iscover (client), **O**ffer (server), **R**equest (client), **A**cknowledge (server). If the server is unavailable and the lease expires, the client assigns itself an **APIPA** address (169.254.x.x), losing network connectivity.

**OP14** — **Unmanaged:** Plug-and-play, no configuration. **Managed:** Supports VLANs, Spanning Tree (STP), SNMP, Port Security, and QoS. Essential for security, segmentation, and troubleshooting in enterprises.

**OP15** — **NTP:** Network Time Protocol. **Criticality:** Essential for log correlation, Kerberos authentication (which fails if clocks drift $>5$ mins), and database transaction ordering. **Drift:** Can cause cluster consensus failures and broken security handshakes.

**OP16** — **Physical:** Hardware. **VM:** Hardware + Guest OS. **Container:** Hardware + Host OS + Isolated Process. **Bare Metal:** Use for high-performance workloads (e.g., massive databases, high-frequency trading) where hypervisor overhead is unacceptable.

**OP17** — **UPS:** Provides immediate battery power for short durations (minutes) to allow graceful shutdown. **Generator:** Provides long-term power (hours/days). **ATS:** Automatically switches the power source from utility to generator when a failure is detected.

**OP18** — **Active-Passive:** One node works, one waits. **Active-Active:** Both nodes work (requires complex state sync). **PostgreSQL HA:** Use **Pacemaker/Corosync** to manage a **Virtual IP (VIP)**. If the primary fails, Corosync detects it, Pacemaker uses **STONITH** (fencing) to ensure the old primary is dead, and then moves the VIP and the DB service to the standby node.

**OP19** — **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite. **RPO/RTO:** RPO (how much data you can lose); RTO (how long it takes to recover). **Types:** Full (all), Incremental (changes since last backup), Differential (changes since last full). **Strategy:** Use **Immutable Backups** (WORM) to prevent ransomware from deleting them. **Testing:** A backup is useless unless you perform regular **Restore Drills**. **Backup vs DR:** Backup is data preservation; DR is the entire process of restoring service/infrastructure.

**OP20** — **802.1X:** 1. **Supplicant** (client device); 2. **Authenticator** (switch); 3. **Authentication Server** (RADIUS). **Methods:** **EAP-TLS** (certificate-based, most secure) vs **PEAP** (username/password). **Process:** Switch asks device for credentials $\rightarrow$ Switch forwards to RADIUS $\rightarrow$ RADIUS validates $\rightarrow$ RADIUS tells switch to allow access and assigns a **Dynamic VLAN**. **Failure:** Device is moved to a "Guest" or "Quarantine" VLAN. **MAB:** For "dumb" devices (printers), the switch identifies them by MAC address and allows them based on a pre-approved list.
