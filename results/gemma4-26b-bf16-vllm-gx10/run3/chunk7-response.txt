## Application Architecture

**AA1** — A **Monolith** is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. **Microservices** decompose the application into small, independent services communicating over a network.
*   **3 Problems of Microservices:** 1. Network latency/unreliability; 2. Distributed data consistency (no ACID across services); 3. Operational complexity (observability, deployment, service discovery).

**AA2** — **Synchronous:** The caller waits for a response before proceeding (e.g., HTTP/REST). **Asynchronous:** The caller sends a message and continues without waiting (e.g., RabbitMQ/AMQP).

**AA3** — An **API Gateway** handles application-level concerns (auth, rate limiting, request transformation, orchestration). A **Reverse Proxy** (like Nginx) primarily handles network-level concerns (SSL termination, load balancing, caching). An API Gateway *can* replace a reverse proxy for most web traffic, but it is often less performant for raw TCP/UDP proxying or simple static file serving.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. If one fails, "compensating transactions" undo the previous steps.
*   **Choreography:** Services exchange events without a central controller. Best for simple workflows with few services.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows with many steps.

**AA5** — **CQRS** separates read (Query) and write (Command) models. It is paired with **Event Sourcing** (storing state as a sequence of events rather than current state) because the event log provides the perfect source of truth to rebuild specialized read models. This solves the problem of "impedance mismatch" where a single schema is inefficient for both complex writes and high-performance reads.

**AA6** — The **Circuit Breaker** prevents a system from repeatedly trying an operation that is likely to fail.
*   **States:** 1. **Closed** (requests flow); 2. **Open** (requests fail immediately); 3. **Half-Open** (limited requests allowed to test recovery).
*   **Difference:** Retry with backoff handles *transient* errors; Circuit Breaker handles *persistent* failures to prevent cascading failure. Use them together by wrapping a retry logic inside a circuit breaker.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, highest density, lowest complexity. Highest security risk (data leakage) and highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Moderate cost/complexity. Better security (schema-level permissions), moderate noisy-neighbor risk.
3. **Separate DB:** Highest cost and operational complexity. Highest security (physical isolation) and lowest noisy-neighbor risk.

**AA8** — **Strong Consistency** ensures all reads see the latest write. For inventory: Use a **Relational Database** (PostgreSQL/MySQL) with **ACID** properties. Use **Pessimistic Locking** (SELECT FOR UPDATE) or **Distributed Locks** (Redis/Etcd) to ensure only one process can decrement a specific SKU at a time. At scale, use **Sharding** by ProductID to distribute the load while maintaining local ACID.

**AA9** — A **Sidecar** is a helper process running alongside the main application container. In **Istio**, **Envoy** acts as the sidecar (Data Plane) to intercept all traffic. The **Control Plane** (Istiod) manages configuration and distributes it to Envoys. **mTLS** between sidecars solves the problem of "identity" and "encryption in transit" without requiring the application code to manage certificates or trust.

**AA10** — The **Strangler Fig** pattern involves placing a proxy in front of the monolith and gradually routing specific routes to new microservices.
*   **Strategy:** 1. Deploy an API Gateway/Proxy in front of the .NET Framework monolith. 2. Identify a low-risk bounded context (e.g., "Notifications"). 3. Build it in .NET 8. 4. Update the Proxy to route `/notifications` to the new service. 5. Repeat until the monolith is "strangled."

**AA11** — 1. **Codebase** (one repo per service); 2. **Dependencies** (explicitly declared); 3. **Config** (stored in environment); 4. **Backing Services** (treated as attached resources); 5. **Build/Release/Run** (strict separation); 6. **Processes** (stateless); 7. **Port Binding** (self-contained); 8. **Concurrency** (scale via process model); 9. **Disposability** (fast startup/shutdown); 10. **Dev/Prod Parity**. These ensure portability, scalability, and automation in cloud environments.

**AA12** — 
*   **Kafka (Event-driven):** High decoupling, massive scalability, high debugging complexity, strong ordering (per partition), complex failure handling (retries/DLQs). Use for: Data pipelines, async workflows.
*   **REST/gRPC (Request-driven):** Tight coupling, lower scalability (synchronous), easier debugging, no inherent ordering, simple failure handling (immediate error). Use for: Real-time UI interactions, synchronous CRUD.

**AA13** — A **Load Balancer** distributes traffic across multiple servers. **Layer 4** (Transport) uses IP/Port (fast, no packet inspection). **Layer 7** (Application) uses HTTP headers/cookies/paths (slower, intelligent). **Use Case:** Routing `/api` to one service and `/static` to another.

**AA14** — A **Message Queue** (RabbitMQ) is designed for "point-to-point" delivery where messages are deleted once consumed. A **Log-based Broker** (Kafka) is a persistent append-only log where messages stay after consumption, allowing "replayability." Pick RabbitMQ for complex routing/task queues; pick Kafka for high-throughput stream processing and event replay.

**AA15** — A **Container** shares the host OS kernel, making it lightweight and fast. A **VM** includes a full guest OS, making it heavy and slow. Containers are popular because they provide environment consistency and high density for microservices.

**AA16** — **Stateless:** Does not store client data locally (e.g., a REST API). **Stateful:** Stores data locally (e.g., a Database). Stateless services scale horizontally easily because any instance can handle any request by fetching state from a shared backend.

**AA17** — An **ORM** maps database tables to programming objects. Examples: **Hibernate** (Java), **Entity Framework** (C#). **Trade-offs:** ORMs increase developer productivity and security (SQLi protection) but can produce inefficient queries and hide performance bottlenecks compared to raw SQL.

**AA18** — The **Bulkhead** pattern isolates elements into pools so that if one fails, others continue. **Implementation:** 1. **Thread Pools:** Assign a specific thread pool to each downstream service call so one slow service doesn't exhaust all application threads. 2. **Deployment Groups:** Run critical services on separate hardware/clusters so a resource leak in one doesn't crash the other.

**AA19** — **OT** requires a central server to sequence operations; high complexity, low latency for local edits, but hard to implement offline. **CRDTs** allow decentralized merging; lower complexity for conflict resolution, excellent offline support, but higher memory overhead. **Choice:** **CRDTs** for offline support, as they allow users to merge changes mathematically without a central authority's immediate mediation.

**AA20** — **Challenges:** Maintaining context across different languages and protocols. **Context Propagation:** Using headers (W3C Trace Context or B3) to pass `trace_id`. **Sampling:** *Head-based* (decide at start) vs *Tail-based* (decide after seeing the whole trace, better for catching errors). **Async/Kafka:** To ensure continuity, the producer must inject the trace context into the **Kafka Message Headers**, and the consumer must extract it to start a child span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., VMware ESXi, Proxmox). **Type 2 (Hosted):** Runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network):** Block-level storage, high speed, used for databases/VM disks (Protocols: Fibre Channel, iSCSI). **NAS (Network Attached Storage):** File-level storage, easier to manage, used for shared files/media (Protocols: NFS, SMB/CIFS).

**OP3** — **3-Tier:** Core $\rightarrow$ Distribution $\rightarrow$ Access. **Leaf-Spine:** Every Leaf switch connects to every Spine switch. It solves the "east-west" traffic bottleneck in modern DCs by providing predictable, low-latency, non-blocking paths between servers.

**OP4** — **Architecture:** $\ge$ 3 nodes for quorum. **Quorum:** Ensures a majority of nodes agree on state. **Fencing:** (STONITH) kills a non-responsive node to prevent data corruption. **Storage:** Ceph (distributed/highly available) is preferred. **Failure:** If a node fails, the cluster detects loss of heartbeat, fences the node, and the remaining nodes take over the VMs/services using the shared storage.

**OP5** — **VLAN Trunking:** Carrying multiple VLANs over a single link. **802.1Q:** Adds a tag to the Ethernet frame header to identify the VLAN. **Linux Config:** Use `ip link add link eth0 name eth0.10 type vlan id 10` to create sub-interfaces.

**OP6** — **RAID 1** (Mirror), **5** (Parity, 1 drive loss), **6** (Double parity, 2 drive loss), **10** (Mirror + Stripe, high perf/fault tolerance), **Z2** (ZFS equivalent of RAID 6). **Choice:** **RAID 10** for a database. It provides the best IOPS (performance) and fastest rebuild times/fault tolerance for high-write workloads.

**OP7** — **Architecture:** 
*   **Internal:** AD-integrated DNS for local resources. 
*   **DMZ:** Authoritative servers for public zones. 
*   **Split-Horizon:** Same domain name, different IP results based on source (Internal vs External). 
*   **DNSSEC:** Adds digital signatures to prevent spoofing. 
*   **Flow:** Laptop on Office uses internal resolvers; on VPN, it uses internal resolvers via tunnel; moving to home, it uses public DNS (but cannot resolve internal names unless VPN is active).

**OP8** — **Chain:** Root CA $\rightarrow$ Intermediate/Subordinate CA $\rightarrow$ End-entity. 
*   **Deployment:** Root CA is kept **offline**; Subordinate CA is online to issue certs. **CRL/OCSP** check if certs are revoked. **Auto-enrollment** via GPO/SCEP. 
*   **Compromise:** A compromised **Subordinate CA** only affects its branch; a compromised **Root CA** invalidates the entire PKI hierarchy and requires manual re-trusting of all devices.

**OP9** — **MPLS:** High cost, high reliability, low latency, complex. **IPsec VPN:** Low cost, relies on internet stability. **SD-WAN:** High flexibility, manages multiple paths (MPLS + Internet), easiest management. **WireGuard:** High performance, simple, but lacks enterprise management. **Recommendation:** **SD-WAN** to combine MPLS (for VoIP) and Internet (for general traffic) to optimize cost and reliability.

**OP10** — **iDRAC/iLO/IPMI:** Hardware-level remote management. **Criticality:** Allows access even if the OS is crashed or the server is powered off. **Risk:** If exposed to the internet, attackers can gain full control of the hardware, reinstall OSs, or wipe data.

**OP11** — **LVM:** Logical volume management (flexible resizing). **LVM-Thin:** Allows over-provisioning and instant snapshots. **ZFS:** Integrated filesystem/volume manager with copy-on-write and massive data integrity features. **Snapshots:** LVM/Thin use COW/metadata; ZFS uses COW (extremely efficient and robust).

**OP12** — **Strategy:** A **Stretch Cluster** across two sites. **Ceph:** Use CRUSH rules to ensure replicas are placed in different sites. **Requirements:** Extremely low latency (<5-10ms RTT) is required for synchronous replication. **Split-brain:** If sites lose connectivity, both might try to be "primary." **Tiebreaker:** A 3rd site (or a lightweight witness node) is required to maintain quorum and prevent split-brain.

**OP13** — **DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge. If the server is unavailable and the lease expires, the client falls back to **APIPA** (169.254.x.x), losing network connectivity.

**OP14** — **Unmanaged:** Plug-and-play, no configuration. **Managed:** Supports VLANs, Spanning Tree (STP), SNMP, Port Security, and QoS. Essential for security and traffic segmentation in enterprises.

**OP15** — **NTP:** Network Time Protocol. **Criticality:** Essential for log correlation, Kerberos authentication (time-sensitive), and distributed database consistency. **Drift:** Can cause authentication failures or "out of order" events in distributed systems.

**OP16** — **Physical:** Bare metal. **VM:** Hardware abstraction. **Container:** OS abstraction. **Bare Metal Use Case:** High-performance computing (HPC), massive databases, or workloads requiring direct access to specialized hardware (GPUs/FPGA) without hypervisor overhead.

**OP17** — **UPS:** Provides immediate battery power for short durations (minutes) to allow graceful shutdown. **Generator:** Provides long-term power (hours/days). **ATS:** Automatically switches the load from utility power to the generator once it stabilizes.

**OP18** — **Active-Passive:** One node works, one waits. **Active-Active:** Both nodes handle traffic. **PostgreSQL HA:** Use **Pacemaker/Corosync** to manage a **Virtual IP (VIP)**. If the primary fails, Corosync detects it, Pacemaker uses **STONITH** to fence the failed node, and then moves the VIP and the DB service to the standby node.

**OP19** — **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite. **RPO/RTO:** RPO (how much data loss is acceptable); RTO (how much downtime is acceptable). **Types:** Full (all), Incremental (changes since last backup), Differential (changes since last full). **Strategy:** Use **Immutable Backups** (WORM) to prevent ransomware from deleting them. **Testing:** A backup is useless unless you perform regular **Restore Drills**. **Backup vs DR:** Backup is data preservation; DR is the entire process of restoring service/infrastructure.

**OP20** — **802.1X:** 
*   **Roles:** **Supplicant** (Client), **Authenticator** (Switch), **Authentication Server** (RADIUS). 
*   **Methods:** **EAP-TLS** (Certificates, most secure) vs **PEAP** (Username/Password). 
*   **Flow:** Switch asks client for credentials $\rightarrow$ Switch forwards to RADIUS $\rightarrow$ RADIUS validates $\rightarrow$ RADIUS tells Switch to allow/deny and assigns a **Dynamic VLAN**. 
*   **Failure:** Device is placed in a "Guest" VLAN or blocked. 
*   **MAB:** For "dumb" devices (printers), the switch checks the MAC address against a whitelist in RADIUS.
