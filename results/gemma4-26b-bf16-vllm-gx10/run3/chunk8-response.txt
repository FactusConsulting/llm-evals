## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and apps. *Ex: AWS EC2.* **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying OS/runtime. *Ex: Google App Engine.* **SaaS (Software as a Service):** Fully managed software delivered over the web. *Ex: Microsoft 365.*

**CL2** — The provider is responsible for the "Security **of** the Cloud" (physical hardware, global infrastructure); the customer is responsible for "Security **in** the Cloud" (data, configurations).
* **IaaS VMs:** Provider handles hardware/hypervisor; You handle OS, patching, and apps.
* **Managed Kubernetes:** Provider handles Control Plane; You handle worker nodes, pods, and network policies.
* **SaaS (M365):** Provider handles almost everything; You handle identity, access, and data governance.

**CL3** — **VPC:** A private isolated network. **Subnet:** A range of IP addresses within a VPC. **Security Group (SG):** A virtual firewall for *instances* (stateful). **NACL:** A firewall for *subnets* (stateless). They layer as: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ SG $\rightarrow$ Instance. **Stateful (SG):** If you allow inbound traffic, outbound response is automatically allowed. **Stateless (NACL):** You must explicitly define both inbound and outbound rules for traffic to flow.

**CL4** — **Landing Zone:** A pre-configured, multi-account environment with foundational security/networking. **OUs (Organizational Units):** Logical groupings of accounts (e.g., Prod, Dev). **Guardrails:** Automated policies (SCPs in AWS) to prevent non-compliant actions. **Shared Networking:** Using a Hub-and-Spoke (Transit Gateway/Azure Virtual WAN) to centralize inspection and connectivity. **Centralized Logging:** Aggregating all logs into a dedicated security account. **Single-account problem:** Blast radius is too large; difficult to implement granular permissions; hard to separate billing/compliance.

**CL5** — **IaC:** Managing infrastructure via machine-readable files.
* **Terraform/OpenTofu:** Declarative, provider-agnostic, massive ecosystem. *Use for: Multi-cloud/General purpose.*
* **Pulumi:** Uses general-purpose languages (Python, TS). *Use for: Dev-heavy teams wanting complex logic.*
* **CloudFormation/Bicep:** Native to AWS/Azure. *Use for: Deepest integration with specific cloud features.*
* **Crossplane:** Kubernetes-native IaC. *Use for: Managing cloud resources via K8s APIs/GitOps.*

**CL6** — **HPA:** Scales pods based on CPU/RAM/Custom metrics. **VPA:** Adjusts pod resource requests/limits (CPU/RAM) based on usage. **Cluster Autoscaler:** Adds/removes VM nodes to the cluster. **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag or RabbitMQ queue depth). **KEDA vs HPA:** Use KEDA when scaling is triggered by external event sources rather than just resource utilization.

**CL7** — **RPO (Recovery Point Objective):** Max data loss allowed. **RTO (Recovery Time Objective):** Max downtime allowed.
* **Active-Active:** Traffic split across regions; zero/near-zero RTO/RPO; highest cost.
* **Active-Passive:** One region idle; higher RTO/RPO; lower cost.
* **Replication:** **Sync** (no data loss, high latency) vs **Async** (low latency, potential data loss).
* **DNS:** Route53/Traffic Manager routes users to the healthy region.
* **State:** Replicate DBs and use global object storage.
* **DR Tiers:** **Pilot Light** (minimal core services running); **Warm Standby** (scaled-down version of full stack); **Multi-site Active-Active** (full capacity in both).

**CL8** — **GitOps:** Using Git as the "Single Source of Truth" for desired state. **ArgoCD vs FluxCD:** ArgoCD has a powerful UI and multi-tenancy; FluxCD is lightweight, CLI-driven, and follows a "pull" model more strictly. **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from AWS SM/Vault), or **Vault**. **Drift:** GitOps controllers detect the difference between Git and the cluster and automatically "reconcile" (overwrite) the manual change to match Git.

**CL9** — **StatefulSet:** Ensures stable network IDs and ordered deployment. **PV/PVC with Local Storage:** Uses `local` storage class for low-latency NVMe/SSD. **Headless Service:** Provides direct Pod IPs for peer discovery. **Init Containers:** Run setup scripts/prep files before the main app starts. **ConfigMaps:** Mounted as volumes to specific paths. **Pod Disruption Budget (PDB):** Ensures a minimum number of replicas remain available during maintenance.

**CL10** — **Service Account:** K8s identity for pods. **Workload Identity/IRSA:** A mechanism to map a K8s Service Account to a Cloud IAM Role. **Bad Practice:** Mounting long-lived static credentials (JSON keys) in pods is a massive security risk (leakage/rotation issues). **Federation:** Uses OIDC to allow the cloud provider to trust the K8s cluster, issuing short-lived, temporary tokens directly to the pod.

**CL11** — **Object (S3/Blob):** Unstructured data (images, logs). High durability ($11$ 9s), high latency. **Block (EBS/Disk):** Raw volumes for OS/DBs. Low latency, attached to one instance. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB). Multiple instances can mount simultaneously.

**CL12** — **Zero-Trust:** "Never trust, always verify." **Architecture:** **Network Policies** (L3/L4 isolation), **Service Mesh (Istio/Linkerd)** for mTLS (L7 encryption/identity), **Pod Identity** (no static keys), **Admission Controllers** (enforce policies like "no root containers"), **Image Signing** (Cosign), **Runtime Security** (Falco detects anomalous syscalls), **Secrets Management** (Vault). **Difference:** Traditional security relies on a "hard shell" (perimeter); Zero-Trust assumes the network is already compromised and secures every individual interaction.

**CL13** — **CDN:** A distributed network of proxy servers that caches content closer to users. **How:** User requests $\rightarrow$ Edge Location $\rightarrow$ Cache Hit (fast) or Cache Miss (fetch from origin). **Services:** CloudFront, Azure Front Door. **Use Case:** Use CDN for static assets (JS, CSS, Images) to reduce latency/origin load; serve directly from origin only for highly dynamic, non-cacheable, or low-traffic private data.

**CL14** — **Region:** A geographic area (e.g., US-East-1). **AZ (Availability Zone):** One or more discrete data centers within a region. **Why Multi-AZ:** To protect against data center failure (power/cooling/network). **Zonal:** Tied to one AZ (e.g., EBS). **Regional:** Available across all AZs in a region (e.g., S3, IAM).

**CL15** — **Managed DB:** A service where the provider manages the engine. **Provider handles:** Patching, backups, hardware provisioning, high availability/failover, and scaling. **You handle:** Schema design, query optimization, and user access.

**CL16** — **IAM:** **Users** (people), **Groups** (collections of users), **Roles** (temporary identities for services/users), **Policies** (JSON docs defining permissions). **Least Privilege:** Granting only the minimum permissions required to perform a task. **Application:** Use Roles instead of Users, use fine-grained IAM policies, and audit with Access Analyzer.

**CL17** — **Serverless:** Running code without managing servers. **Comparison:** Lambda (AWS), Functions (Azure), Cloud Functions (GCP). **Cold Start:** Latency incurred when a function is invoked after being idle (container spin-up). **Poor Fit:** Long-running processes (e.g., video encoding), high-performance computing, or applications requiring constant low-latency connections.

**CL18** — **Ingress:** Standard K8s resource for L7 routing. **Gateway API:** The evolution of Ingress; more expressive, role-oriented (Infra vs App dev). **Cloud LB Annotations:** Uses cloud provider LBs (ALB/NLB) via Ingress controller. **Service Mesh Ingress:** Uses a mesh gateway (Istio) for advanced L7 features. **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Sidecar (mTLS). **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenant environments, and better separation of concerns.

**CL19** — **Strategy:**
* **Commitment:** Use **Reserved Instances/Savings Plans** for predictable baseline load.
* **Flexibility:** Use **Spot Instances** for stateless/batch workloads (up to 90% savings).
* **Efficiency:** **Right-sizing** (matching instance size to actual usage) and **Storage Tiering** (moving old data to S3 Glacier).
* **Governance:** **FinOps** (culture of cost accountability), **Showback** (reporting costs to teams), **Chargeback** (billing teams for their usage).
* **Tools:** AWS Cost Explorer, Azure Cost Management, Kubecost (for K8s).

**CL20** — **Strategy:** Use **Kubernetes** as the abstraction layer to make workloads portable. Use **Terraform** for infrastructure. Use **Identity Federation** (OIDC) so identities work across clouds. Use **VPN/Interconnect** for private cross-cloud networking. **Trade-offs:** Multi-cloud increases complexity, latency, and egress costs. **Justification:** Necessary for extreme regulatory compliance or massive scale/resiliency; unnecessary for most companies where "single-cloud with multi-region" suffices.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** A framework for ICS security segmentation.
* **Level 0:** Physical process (sensors, actuators).
* **Level 1:** Basic Control (PLCs, RTUs).
* **Level 2:** Area Supervisory Control (HMIs, SCADA).
* **Level 3:** Site Operations (Historians, MES).
* **Level 4/5:** Enterprise/Business (ERP, Internet).

**OT2** — **IT:** Focuses on Data Confidentiality/Integrity. **OT:** Focuses on Availability/Safety. **Patching:** You cannot patch OT systems like IT because reboots can cause physical damage, process instability, or safety hazards.

**OT3** — **IDMZ:** A buffer zone between IT and OT. **Traffic:** Only highly inspected, proxied traffic (e.g., data from Historian to ERP). **Direction:** Usually "Push" from OT to IT. **Danger:** Direct L4 $\rightarrow$ L1 connectivity allows an attacker on the business network to directly manipulate physical hardware.

**OT4** — 1. **Modbus TCP:** Level 1/2 (Fieldbus/Control). 2. **OPC UA:** Level 2/3 (Supervisory/Integration). 3. **EtherNet/IP:** Level 1/2 (Control). 4. **PROFINET:** Level 1/2 (Real-time control). 5. **MQTT:** Level 3/4 (Edge-to-Cloud/IIoT).

**OT5** — **Data Diode:** Hardware-based, physically allows data to flow in only one direction (unidirectional). **Firewall:** Software-based, bidirectional (though restricted). **Use Case:** Use a diode for high-security environments (nuclear/water) where you must ensure zero possibility of inbound commands. **Limitation:** Firewalls allow two-way communication (needed for many protocols); diodes break standard TCP handshakes.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway (converts to MQTT) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. **Security:** Place the IDMZ between the Historian and the Edge Gateway; use a firewall to restrict the Gateway to outbound-only connections.

**OT7** — **Zone:** A grouping of assets with similar security requirements. **Conduit:** A communication path between zones. **Model:**
* **Zone 1 (Safety):** SIS (Highest isolation).
* **Zone 2 (Control):** PLCs/HMIs (Isolated via conduit from Zone 3).
* **Zone 3 (Supervisory):** SCADA/Historian (Isolated via IDMZ conduit from Zone 4).
* **Zone 4 (Corporate):** Business network.

**OT8** — **Strategy:** Implement **VLANs** to segment production lines. Place **Industrial Firewalls** between lines and between the plant and IT. Use **Managed Switches** with port security. **Remote Access:** Use a secure Jump Host in the IDMZ with MFA. **Transition:** Use a "Parallel Build" approach—install new network gear alongside the old, migrate one line at a time during scheduled maintenance windows.

**OT9** — **SIS:** Independent system designed to take the process to a safe state if the BPCS fails. **IEC 61511:** Standard for functional safety in the process industry. **Isolation:** SIS must be isolated to prevent a single failure (or cyberattack) from disabling both control and safety. **Ransomware on SIS:** Could prevent a safe shutdown during an emergency, leading to catastrophic physical explosion or environmental release.

**OT10** — **PLC:** Logic controller for specific machines (Level 1). **DCS (Distributed Control System):** Integrated system for large, continuous processes (e.g., oil refinery) (Level 2). **SCADA:** Supervisory system for geographically dispersed assets (e.g., pipelines) (Level 2/3). **Coexistence:** Yes, they often coexist in large plants.

**OT11** — **Architecture:** Users connect to a VPN $\rightarrow$ Jump Host in IDMZ $\rightarrow$ MFA $\rightarrow$ Session Recording. **Why not RDP to HMI:** Direct RDP exposes the HMI (and the process) to the entire corporate network, bypassing all segmentation and inspection.

**OT12** — **Plan:** 1. **Detection:** Deploy OT-IDS (e.g., Nozomi/Claroty) to find anomalies. 2. **Inventory:** Verify all assets via passive monitoring. 3. **Response:** Isolate the compromised VPN segment. 4. **Coordination:** Alert the Control Room immediately. 5. **Safety:** The **Plant Operator** is the ultimate authority; they decide if the process must be manually shut down for safety, regardless of IT's response.

**OT13** — **HMI:** A dashboard for operators to monitor/control the process. **Difference:** An HMI is for *operation*; an Engineering Workstation is for *programming/configuring* the PLCs.

**OT14** — **Historian:** A database that records time-series process data. **Importance:** Essential for troubleshooting, regulatory compliance, and optimization. **Plant Historian (L3):** High-resolution, local. **Enterprise Historian (L4):** Aggregated, lower-resolution, used for business analytics.

**OT15** — **Ladder Logic:** A graphical programming language resembling electrical relay diagrams. **Device:** PLC. **Dominance:** It is intuitive for electricians/engineers trained in electrical schematics and is highly deterministic.

**OT16** — **RTU:** Designed for long-distance, low-bandwidth, or remote environments (e.g., solar-powered telemetry). **Difference:** RTUs are more rugged and better at handling various serial protocols; PLCs are better for high-speed, complex logic in a factory.

**OT17** — **Analog:** Continuous signal (4-20mA). **Digital:** Discrete (On/Off). **4-20mA vs 0-20mA:** 4-20mA allows for "Live Zero." If the signal is 0mA, you know there is a wire break; if it's 4mA, the sensor is simply reading zero.

**OT18** — **Inventory:** You cannot protect what you don't know exists. **Techniques:** **Passive Monitoring** (sniffing traffic) is safe. **Active Scanning** (Nmap/Ping) is **dangerous** because it can crash older, fragile OT devices/PLCs.

**OT19** — **MITRE ATT&CK for ICS:** 1. **Inhibit Response Function** (e.g., disabling alarms). 2. **Impair Process Control** (e.g., changing setpoints). 3. **Loss of Safety** (e.g., disabling SIS). 4. **Impair Process Safety** (e.g., manipulating sensors). 5. **Inhibit Control** (e.g., DoS on PLC). **Difference:** It focuses on physical consequences/process impact rather than just data theft.

**OT20** — **SOC Design:** 1. **Collection:** Use passive TAPs/SPAN ports to avoid latency. 2. **Integration:** Send OT logs to a SIEM via an IDMZ. 3. **Rules:** Look for "New Device," "Unauthorized Protocol," or "Logic Change." 4. **Triage:** IT analysts handle network alerts; OT engineers handle process-impact alerts. 5. **Firmware Alert:** Treat as a critical incident; verify with the plant engineer if a maintenance window was scheduled. If not, initiate emergency isolation protocols.
