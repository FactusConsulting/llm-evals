## OpenTofu / Terraform

**T1** — `tofu plan` is a read-only operation that performs a refresh of the state and compares it against the configuration to create an execution plan. `tofu apply` executes the actions proposed in the plan to reach the desired state.

**T2** — State is a JSON file mapping your configuration to real-world resources. Remote state is critical for team collaboration (shared source of truth), state locking (preventing concurrent writes), and security (storing sensitive data outside local machines).

**T3** — `count` uses an integer index (0, 1, 2...), making it difficult to remove items from the middle without shifting indices. `for_each` uses a map or set of strings, allowing you to add/remove specific items without affecting others. `for_each` is preferred for collections of resources where identity matters.

**T4** — This is "configuration drift." During the next `plan`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy between the actual cloud state and the state file, then proposes changes (e.g., an update or a recreation) to bring the resource back in line with the code.

**T5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

**T6** — `terraform_remote_state` reads the entire state file of another workspace, which can expose sensitive data and creates tight coupling. Output values are cleaner but require the other module to be in the same state or accessible via a provider. The recommended alternative is passing outputs as variables to modules or using a dedicated "Service Discovery" pattern (like SSM Parameter Store or Consul) to decouple state lifecycles.

**T7** — The `null_resource` is being evaluated, but the `remote-exec` provisioner runs during the *apply* phase, not the *plan* phase. If the output is calculated based on a file created by that provisioner, the value doesn't exist yet during the initial dependency resolution. **Fix:** Use a `local_file` resource or a data source that waits for the resource to be ready, or ensure the output is derived from a resource attribute rather than a side-effect of a provisioner.

**T8** — `import` brings existing infrastructure under Tofu management. Limitations: It doesn't generate code (in older versions) and requires manual state manipulation. The `import` block (1.5+) allows you to define imports in code, making them declarative, easier to review in PRs, and allowing `tofu plan` to show exactly what will happen before the import is finalized.

**T9** — A `variable` is an input parameter used to make configurations dynamic. An `output` is a return value used to expose information (like an IP address) to the user or other modules.

**T10** — A provider is a plugin that translates Tofu code into API calls for a specific platform (AWS, Azure, etc.). If you run `plan` without `init`, Tofu will fail because it hasn't downloaded the necessary provider binaries to the `.terraform` directory.

**T11** — It is the dependency lock file that records the exact versions and hashes of providers used. It should be committed to ensure all team members and CI/CD pipelines use identical provider versions, preventing "it works on my machine" issues.

**T12** — `tofu destroy` removes all resources managed by the current state. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

**T13** — A data source allows you to fetch information from existing infrastructure that is *not* managed by your current Tofu code. Example: Fetching an existing VPC ID or an AMI ID created by a different team.

**T14** — `variables` are external inputs (passed by the user). `locals` are internal constants/expressions (defined within the module). Use `locals` to avoid repetition (DRY) and to perform complex logic/transformations on input variables.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime updates).
- `prevent_destroy`: Stops Tofu from destroying a resource (useful for production databases).
- `ignore_changes`: Tells Tofu to ignore updates to specific attributes (useful when external processes, like Auto Scaling, modify a resource).

**T16** — The `moved` block allows you to rename a resource or move it into a module within your code. It tells Tofu: "This new address in the code actually refers to this existing object in the state," preventing the resource from being destroyed and recreated during refactoring.

**T17** — The graph is a Directed Acyclic Graph (DAG). **Implicit dependencies** occur when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are defined via `depends_on`. `depends_on` forces a specific order but limits parallelism because Tofu cannot execute those resources simultaneously. It should be used sparingly as it can significantly slow down execution.

**T18** — 
1. **State Splitting:** Break the monolith into smaller, decoupled state files (reduces the graph size). *Tradeoff: Increased complexity in managing cross-state dependencies.*
2. **Targeted Plans:** Use `-target` for specific changes. *Tradeoff: Risk of missing side effects/dependencies.*
3. **Reduce Refresh:** Use `-refresh=false` if you know the state is current. *Tradeoff: Risk of planning against stale data.*
4. **Increase Parallelism:** Use `-parallelism=n` (default is 10). *Tradeoff: May hit API rate limits of the provider.*

**T19** — State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a CI pipeline crashes, the lock remains in the backend (e.g., DynamoDB). You can break it using `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually still running, force-unlocking can lead to state corruption or resource duplication.

**T20** — 
1. Ensure the new S3 bucket and DynamoDB table exist.
2. Update the `backend` block in your `.tf` files.
3. Run `tofu init`. Tofu will detect the change and ask if you want to migrate the state.
4. Type `yes`. Tofu will copy the local `.tfstate` to S3 and initialize the lock.
5. **Verify:** Run `tofu plan`. If it shows "No changes," the migration was successful and the state is correctly mapped.

## Ansible

**A1** — A **task** is a single action (e.g., install a package). A **playbook** is a collection of plays that map tasks to hosts. A **role** is a structured, reusable way to bundle tasks, variables, files, and templates.

**A2** — `ansible_facts` is a dictionary of system information gathered by Ansible. Access the OS family via `ansible_facts['os_family']` (or `ansible_os_family`).

**A3** — `command`: Executes a command without a shell environment (most secure, no pipes/redirects). `shell`: Executes via `/bin/sh` (allows pipes, redirects, and environment variables). `raw`: Executes via raw SSH without needing Python on the target (used for bootstrapping).

**A4** — Idempotency means running a task multiple times results in the same state without extra changes. 
- **Idempotent:** `apt: name=nginx state=present` (if installed, does nothing).
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file.txt` (appends every time it runs).

**A5**
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install htop on RedHat
  package:
    name: "{{ item }}"
    state: present
  loop: [epel-release, htop]
  when: ansible_os_family == "RedHat"
```

**A6** — (Lowest to Highest): `role defaults` < `inventory group_vars` < `inventory host_vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process hosts in batches of 3. To ensure the first 3 are "ready," use a `wait_for` task or a health check task within the play. If the first batch fails, the playbook stops.

**A8** — `ansible-vault` encrypts files. To encrypt a single variable, you cannot do it within a standard YAML file easily; you must either encrypt the whole file or use a separate encrypted file and include it via `vars_files`.

**A9** — An **inventory** is a list of managed hosts. **Static** is a hardcoded file (INI/YAML). **Dynamic** is a script or plugin that queries a cloud provider (AWS/GCP) to get a real-time list of hosts.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **handler** is a special task that only runs if notified by another task that reported a `changed` status. You trigger it using the `notify` keyword in a task.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory` (path to inventory), `remote_user` (default SSH user), and `forks` (number of parallel processes).

**A13** — `register` saves the output of a task into a variable. You use it in a subsequent task via `when: variable_name.rc == 0` or `debug: var=variable_name`.

**A14** — `import_tasks` is **static** (processed at playbook parsing time). `include_tasks` is **dynamic** (processed during runtime). Use `include_tasks` if you need to use a variable to determine which file to load or if you need to apply conditionals to the inclusion itself.

**A15** — **Ansible Galaxy** is a public repository for roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16** — **ssh**: Standard remote execution via SSH (default). **local**: Executes tasks on the control node itself. **network_cli**: Used for network devices (switches/routers) that don't have Python; it uses specialized CLI commands.

**A17** — `delegate_to` runs a task on a different host than the current one. `run_once` ensures a task runs only once for the entire play. 
*Example:* 
```yaml
- name: Get remote IP
  set_fact:
    remote_ip: "{{ ansible_default_ipv4.address }}"
- name: Register IP in local file
  lineinfile:
    path: /tmp/ips.txt
    line: "{{ remote_ip }}"
  delegate_to: localhost
  run_once: false # Run for each host to collect all IPs
```

**A18** — 
1. **Forks:** Increase `forks` in `ansible.cfg` to run more tasks in parallel. *Tradeoff: Higher CPU/RAM usage on control node.*
2. **Pipelining:** Enable `pipelining = True` in `ansible.cfg` to reduce SSH connections. *Tradeoff: May break some `sudo` configurations.*
3. **Fact Caching:** Use Redis/JSON files to cache facts so they aren't re-gathered every time. *Tradeoff: Risk of using stale data.*
4. **Mitogen:** Use the Mitogen plugin for a highly optimized SSH execution engine. *Tradeoff: Requires installing a plugin on the control node.*

**A19** — `{{ }}` is for expressions/variables. `{% %}` is for control logic (loops/ifs). `{# #}` is for comments.
```jinja2
upstream backend_servers {
{% for server in backend_list %}
    server {{ server.ip }}:{{ server.port }}; # Health check: {{ server.status }}
{% endfor %}
}
```

**A20** — 
1. Set `serial: 1` or `serial: 5` to process in batches.
2. **Pre-task:** Use `uri` module to check health; if unhealthy, stop.
3. **Task:** Remove server from Load Balancer (e.g., via API task).
4. **Task:** Update application code/restart service.
5. **Post-task:** Use `uri` module to verify the local server is healthy.
6. **Post-task:** Re-add to Load Balancer.
7. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, write tasks to revert the code and re-add the server to the LB.
