## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage OS and apps. *Ex: AWS EC2.* **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing OS/runtime. *Ex: Google App Engine.* **SaaS (Software as a Service):** Fully managed software delivered over the web. *Ex: Microsoft 365.*

**CL2** — The provider is responsible for the "Security **of** the Cloud" (hardware, global infra); the customer is responsible for "Security **in** the Cloud" (data, config).
* **IaaS VMs:** Provider handles physical host/hypervisor; You handle OS, patching, and apps.
* **Managed K8s:** Provider handles Control Plane; You handle worker nodes (partially), pods, and network policies.
* **SaaS (M365):** Provider handles almost everything; You handle identity, access, and data governance.

**CL3** — **VPC:** A private isolated network. **Subnet:** A range of IP addresses within a VPC. **Security Group (SG):** A virtual firewall for *instances* (stateful). **NACL:** A firewall for *subnets* (stateless). They layer as: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ SG $\rightarrow$ Instance. **Stateful (SG):** If you allow inbound traffic, outbound response is automatically allowed. **Stateless (NACL):** You must explicitly define both inbound and outbound rules for traffic to flow.

**CL4** — **Landing Zone:** A pre-configured, multi-account environment with baseline security/compliance. **OUs (Organizational Units):** Logical groupings of accounts (e.g., Prod, Dev, Security). **Guardrails:** Automated policies (SCPs in AWS) to prevent non-compliant actions. **Shared Networking:** Using a Hub-and-Spoke (Transit Gateway/Azure Virtual WAN) to centralize inspection and connectivity. **Centralized Logging:** Aggregating all logs into a dedicated security account. **Single-account problem:** Blast radius is too large; difficult to implement granular billing/access; hard to scale security boundaries.

**CL5** — **IaC:** Managing infrastructure via machine-readable files.
* **Terraform/OpenTofu:** Declarative, provider-agnostic, massive ecosystem. *Use for: Multi-cloud/General purpose.*
* **Pulumi:** Uses general-purpose languages (Python, TS). *Use for: Dev-heavy teams wanting logic/loops.*
* **CloudFormation/Bicep:** Native to AWS/Azure. *Use for: Deepest integration with specific cloud features.*
* **Crossplane:** K8s-native IaC (Control Plane approach). *Use for: Managing cloud resources via K8s APIs.*

**CL6** — **HPA:** Scales pods based on CPU/RAM/Custom metrics. **VPA:** Adjusts pod resource requests/limits (CPU/RAM) based on usage. **Cluster Autoscaler:** Adds/removes VM nodes to the cluster. **KEDA:** Event-driven autoscaling (e.g., scale based on RabbitMQ queue depth). **Use KEDA over HPA** when scaling depends on external event sources (queues, streams) rather than just resource utilization.

**CL7** — **RPO (Recovery Point Objective):** Max data loss allowed. **RTO (Recovery Time Objective):** Max downtime allowed.
* **Active-Active:** Traffic split across regions; zero RTO/RPO; highest cost.
* **Active-Passive:** One region idle; failover required; moderate RTO/RPO.
* **DB Replication:** **Sync** (no data loss, high latency) vs **Async** (low latency, potential data loss).
* **DNS Failover:** Route53/Traffic Manager redirects traffic to the healthy region.
* **State:** Must be replicated or externalized (e.g., Global DynamoDB).
* **DR Types:** **Pilot Light** (minimal core services running); **Warm Standby** (scaled-down version of full stack); **Multi-site Active-Active** (full capacity in both).

**CL8** — **GitOps:** Using Git as the "Single Source of Truth" for desired state. **ArgoCD vs FluxCD:** ArgoCD provides a powerful UI and multi-cluster management; FluxCD is lightweight, CLI-driven, and follows a more "Git-native" modular approach. **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from AWS SM/Vault), or **Vault** (direct injection). **Drift:** GitOps controllers detect the difference and automatically overwrite manual changes to match the Git state (self-healing).

**CL9** — **StatefulSet:** Ensures stable network IDs and ordered deployment. **PV/PVC with Local Storage:** Uses `local` storage class for low-latency NVMe/SSD. **Headless Service:** Provides direct Pod IPs for peer discovery. **Init Containers:** Pre-populate/configure files before the main app starts. **ConfigMaps:** Mounted as volumes to specific paths. **Pod Disruption Budget (PDB):** Ensures a minimum number of replicas remain available during maintenance.

**CL10** — **Service Account:** K8s identity for pods. **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role. **Bad Practice:** Mounting long-lived static credentials (JSON keys) in pods risks theft and requires manual rotation. **Workload Identity Federation** solves this by using OIDC to exchange a short-lived K8s token for a temporary cloud IAM token, eliminating static secrets.

**CL11** — **Object (S3/Blob):** Unstructured data (images, logs). High durability ($11 \times 9$s), high latency. **Block (EBS/Disk):** Raw volumes for OS/DBs. Low latency, attached to one instance. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB). Multiple instances can mount simultaneously.

**CL12** — **Zero-Trust:** "Never trust, always verify."
* **Network Policies:** L3/L4 pod-to-pod isolation.
* **Service Mesh (Istio/Linkerd):** L7 security with mTLS for all service communication.
* **Pod Identity:** Using IRSA/Workload Identity instead of keys.
* **Admission Controllers:** OPA/Kyverno to enforce policies (e.g., "no root containers").
* **Image Signing:** Cosign/Notary to ensure only trusted images run.
* **Runtime Security:** Falco to detect anomalous syscalls.
* **Difference:** Traditional security relies on a "hard shell" (perimeter); Zero-Trust assumes the perimeter is breached and secures every individual request/identity.

**CL13** — **CDN:** A distributed network of proxy servers that caches content closer to users. **How:** User requests $\rightarrow$ Edge location $\rightarrow$ Cache hit (fast) or Cache miss (fetch from origin). **Services:** CloudFront, Akamai. **Use CDN** for static assets (JS, CSS, Images) to reduce latency and origin load. **Use Origin** for highly dynamic, personalized data that cannot be cached.

**CL14** — **Region:** A geographic area (e.g., us-east-1). **AZ (Availability Zone):** One or more discrete data centers within a region. **Why multi-AZ:** To protect against a single data center failure (power, cooling). **Zonal:** Tied to one AZ (e.g., EBS). **Regional:** Available across all AZs in a region (e.g., S3, IAM).

**CL15** — **Managed DB:** A service where the provider manages the underlying infrastructure. **Provider handles:** Patching, backups, hardware provisioning, high availability/failover, and scaling. **You handle:** Schema design, query optimization, and user access.

**CL16** — **IAM Users:** Individual people/apps. **Groups:** Collections of users. **Roles:** Temporary identities assumed by users/services. **Policies:** JSON documents defining permissions. **Least Privilege:** Granting only the minimum permissions required to perform a task. **Application:** Use Roles instead of Users, use fine-grained IAM policies, and audit with Access Analyzer.

**CL17** — **Serverless:** Computing where the provider manages the server lifecycle. **Comparison:** Lambda (AWS), Functions (Azure), Cloud Functions (GCP). **Cold Start:** Latency incurred when a function is invoked after being idle (container spin-up). **Poor fit:** Long-running processes, high-performance computing (HPC), or applications requiring constant, predictable low latency.

**CL18** — **Ingress:** Standard K8s resource for L7 routing. **Gateway API:** The successor to Ingress; more expressive, role-oriented (Infra vs App dev). **Cloud LB Annotations:** Uses cloud-specific settings to provision a provider LB. **Service Mesh Ingress:** Uses a mesh gateway (e.g., Istio) for advanced L7 routing/mTLS. **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Service Mesh. **Use Gateway API** when you need advanced routing (canary, header-based) without bloating Ingress resources.

**CL19** — **Strategy:**
* **Compute:** Use **Reserved Instances/Savings Plans** for baseline; **Spot** for stateless/batch; **Right-sizing** via tools like AWS Compute Optimizer.
* **Storage:** Move old data to **S3 Glacier/Archive**.
* **FinOps:** Implement **Tagging** for cost allocation. Use **Showback** (reporting) and **Chargeback** (billing departments).
* **Tools:** CloudHealth, Kubecost, or native tools (AWS Cost Explorer).
* **Process:** Monthly reviews, automated alerts for budget spikes, and "Unit Cost" tracking.

**CL20** — **Strategy:** Use **Kubernetes** as the abstraction layer to make workloads portable. Use **Terraform** for infra. Use **Identity Federation** (OIDC) to bridge IAM. **Networking:** Site-to-site VPN or dedicated interconnects (DirectConnect/ExpressRoute). **Trade-offs:** Multi-cloud increases complexity, operational overhead, and egress costs. **Justification:** High regulatory requirement for exit strategy or extreme availability. **Unnecessary:** When a single provider's multi-region capability satisfies the SLA.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** A framework for segmenting ICS networks.
* **Level 0:** Physical process (sensors, actuators).
* **Level 1:** Basic Control (PLCs, RTUs).
* **Level 2:** Area Supervisory Control (HMIs, SCADA).
* **Level 3:** Site Operations (Historians, MES).
* **Level 4/5:** Enterprise/Business (ERP, Internet).

**OT2** — **IT:** Focuses on Data Confidentiality/Integrity. **OT:** Focuses on Availability/Safety. **Patching:** Standard IT patching can cause unexpected reboots or latency, which in OT can lead to physical damage or loss of life.

**OT3** — **IDMZ:** A buffer zone between IT and OT. **Traffic:** Only strictly defined, inspected traffic (e.g., Historian data replication) should cross. **Direction:** Usually "Push" from OT to IT. **Danger:** Direct L4 $\rightarrow$ L1 connectivity allows an attacker on the corporate network to directly manipulate physical hardware.

**OT4** — 1. **Modbus TCP:** Level 1/2 (Fieldbus/Control). 2. **OPC UA:** Level 2/3 (Supervisory/Integration). 3. **EtherNet/IP:** Level 1/2 (Control). 4. **PROFINET:** Level 1 (Real-time Control). 5. **MQTT:** Level 3/4 (Edge-to-Cloud/IIoT).

**OT5** — **Data Diode:** Hardware-based, physically allows data to flow in only one direction (unidirectional). **Firewall:** Software-based, bidirectional (though restricted). **Use Diode:** For high-security environments (Nuclear/Water) where data must leave but nothing can enter. **Limitation:** No "handshake" or acknowledgment possible; harder to manage.

**OT6** — **Flow:** PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway (converts to MQTT) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion. **Security:** Place the IDMZ between the Historian and the Edge Gateway; use a firewall to restrict the Gateway to outbound-only connections.

**OT7** — **Zone:** A grouping of assets with similar security requirements. **Conduit:** A communication path between zones. **Model:**
* **Zone A (Corporate):** ERP/Email.
* **Zone B (Engineering):** Workstations.
* **Zone C (Control):** SCADA/Historian.
* **Zone D (Process):** PLCs.
* **Zone E (Safety):** SIS (Highest isolation).
* **Conduits:** Strictly controlled firewalls/diodes between each zone.

**OT8** — **Strategy:**
1. **VLANs:** Segment by production line.
2. **Firewalls:** Place at the boundary of each line and the IDMZ.
3. **Switching:** Managed switches with port security.
4. **Remote Access:** Via a Jump Host in the IDMZ with MFA.
5. **Transition:** Use "Monitor Mode" on switches first to map traffic, then implement "Enforcement Mode" during scheduled maintenance windows to avoid downtime.

**OT9** — **SIS:** Independent system to prevent catastrophic failure (e.g., emergency shutdown). **BPCS:** The system that runs the day-to-day process. **IEC 61511:** Standard for functional safety in the process industry. **Isolation:** SIS must be isolated so a compromise of the BPCS (via ransomware) cannot disable the safety shutdown mechanism. **Ransomware on SIS:** Could prevent a safe shutdown during an emergency, leading to explosion/leak.

**OT10** — **PLC:** Small, logic-based controller for specific tasks. **DCS (Distributed Control System):** Large-scale, integrated system for complex continuous processes (e.g., oil refinery). **SCADA:** Supervisory system for geographically dispersed assets. **Coexistence:** Yes, SCADA often supervises multiple PLCs/DCSs.

**OT11** — **Architecture:** Users connect to a VPN $\rightarrow$ Jump Host (in IDMZ) $\rightarrow$ MFA $\rightarrow$ Session Recording. **Why not RDP to HMI:** Direct RDP bypasses all segmentation, exposes the HMI to the internet/corporate network, and lacks auditability.

**OT12** — **Plan:**
1. **Detection:** Deploy OT-IDS (e.g., Nozomi/Claroty) to find anomalous traffic.
2. **Inventory:** Verify all assets via passive monitoring.
3. **Response:** Isolate the compromised VPN segment; switch to manual/local control if possible.
4. **Coordination:** Notify the Control Room immediately.
5. **Operator Role:** The operator is the ultimate authority; they decide if the process must be "tripped" (shut down) for safety.

**OT13** — **HMI:** A dashboard for operators to visualize and interact with the process. **Difference:** An HMI is for *monitoring/control*; an Engineering Workstation is for *programming/configuring* the PLCs.

**OT14** — **Historian:** A database that stores time-series process data. **Importance:** Essential for auditing, troubleshooting, and optimization. **Plant Historian (L3):** High-resolution, local. **Enterprise Historian (L4):** Aggregated, low-resolution, used for business KPIs.

**OT15** — **Ladder Logic:** A graphical programming language resembling electrical relay diagrams. **Device:** PLC. **Dominance:** It is intuitive for electricians/enginehold engineers and maps directly to physical electrical logic.

**OT16** — **RTU:** Designed for long-distance, low-bandwidth, harsh environments (e.g., remote pipelines). **Difference:** RTUs are more rugged and better at telemetry/radio comms; PLCs are better for high-speed, complex local logic.

**OT17** — **Analog:** Continuous signal (4-20mA). **Digital:** On/Off (0 or 1). **4-20mA vs 0-20mA:** 4mA provides a "live zero." If the wire breaks, the signal drops to 0mA, allowing the system to distinguish between a "zero reading" and a "broken wire."

**OT18** — **Inventory:** You cannot protect what you don't know exists. **Techniques:** **Passive Monitoring** (sniffing traffic) is safe. **Active Scanning** (Nmap/Ping) is **dangerous** because old OT devices can crash when receiving unexpected packets.

**OT19** — **MITRE ATT&CK for ICS:**
1. **Inhibit Response Function:** (e.g., disabling an alarm).
2. **Impair Process Control:** (e.g., changing setpoints).
3. **Loss of Safety:** (e.g., disabling SIS).
4. **Inhibit Control:** (e.g., DoS on a PLC).
5. **Impair Process Safety:** (e.g., manipulating sensor data).
**Difference:** Focuses on physical impact/process disruption rather than just data theft. Use it to map your visibility gaps (e.g., "Can we detect a setpoint change?").

**OT20** — **SOC Design:**
* **Collection:** Use passive TAPs/SPAN ports to avoid latency.
* **Integration:** Send OT logs to a dedicated SIEM instance.
* **Rules:** Focus on "Impossible" transitions (e.g., PLC programming mode enabled during production).
* **Staffing:** Hybrid teams; IT analysts handle the network, OT engineers validate the process impact.
* **False Positives:** High in OT due to legacy protocols; require "tuning" based on known process cycles.
* **Firmware Alert:** Treat as a **Critical Incident**. Do not automate a shutdown; escalate to the Plant Operator to verify if the change was authorized maintenance.
