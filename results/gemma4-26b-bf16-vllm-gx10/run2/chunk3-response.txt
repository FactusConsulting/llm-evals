## OpenTofu / Terraform

**T1** — `tofu plan` is a dry run that performs a refresh of the state and compares it against the configuration to show what actions (create, update, delete) will be taken. `tofu apply` executes those actions to reach the desired state.

**T2** — State is a JSON file mapping your configuration to real-world resources. Remote state is critical for team collaboration (shared source of truth), state locking (preventing concurrent writes), and security (storing sensitive data outside local machines).

**T3** — `count` uses an integer index (0, 1, 2...), making it difficult to remove items from the middle without shifting indices. `for_each` uses a map or set of strings, allowing you to add/remove specific items without affecting others. `for_each` is preferred for managing collections of distinct resources.

**T4** — This is "configuration drift." During the next `plan` or `apply`, OpenTofu refreshes the state by querying the provider API. It detects the discrepancy and proposes an action (e.g., modifying the VM back to the configured state or recreating it) to align reality with the code.

**T5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

**T6** — `terraform_remote_state` reads the entire state file of another workspace, which can expose sensitive data and creates tight coupling. Output values are cleaner but require the other module to be in the same state or accessible via a provider. The recommended alternative is passing outputs as variables between modules or using a dedicated Service Discovery/KV store (like Consul) to decouple lifecycles.

**T7** — The `null_resource` is being evaluated, but the `remote-exec` provisioner runs during the *apply* phase, whereas outputs are calculated during the *plan/apply* transition. If the output depends on a file created by the provisioner, it may not exist yet. **Fix:** Use a `local_file` resource or a `data` source that waits for the file, or better, use a specialized provider/resource that natively manages the cluster rather than a `null_resource`.

**T8** — `import` brings existing infrastructure under Tofu management. Limitations: It doesn't generate code (historically) and requires manual state manipulation. The `import` block (1.5+) allows you to declare the import in code, making it declarative, easier to review in PRs, and allows `tofu plan` to show exactly what will happen before the import is finalized.

**T9** — A `variable` is an input parameter used to make configurations dynamic. An `output` is a return value used to export information (like an IP address) to the CLI or other modules.

**T10** — A provider is a plugin that translates Tofu code into API calls for a specific platform (AWS, Azure, etc.). If you run `plan` without `init`, Tofu will fail because it hasn't downloaded the necessary provider binaries.

**T11** — It is the dependency lock file that records the exact versions and hashes of providers used. It should be committed to ensure all team members and CI/CD pipelines use identical provider versions, preventing "works on my machine" issues.

**T12** — `tofu destroy` removes all resources managed by the current state. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

**T13** — A data source allows you to fetch information from existing infrastructure not managed by your current Tofu code. **Example:** Using a `data "aws_ami"` block to find the latest Ubuntu image ID instead of hardcoding it.

**T14** — `variables` are external inputs (provided by users/CI). `locals` are internal constants/expressions used to simplify code or avoid repetition. Use `locals` for complex logic or derived values that should not be changed by the user.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (useful for zero-downtime).
- `prevent_destroy`: Stops Tofu from destroying a resource (useful for production databases).
- `ignore_changes`: Tells Tofu to ignore updates to specific attributes (useful when an external process, like an Autoscaling Group, modifies a resource).

**T16** — The `moved` block allows you to rename a resource or move it into a module within your code. It tells Tofu: "This new address in the code is actually the same as this old address in the state," preventing a destroy/recreate cycle.

**T17** — The graph is a Directed Acyclic Graph (DAG). **Implicit dependencies** are created when one resource references an attribute of another (e.g., `vpc_id = aws_vpc.main.id`). **Explicit dependencies** are created via `depends_on`. `depends_on` forces sequential execution, reducing parallelism. It should be used sparingly because it can significantly slow down execution and often indicates a missing implicit dependency.

**T18** — 
1. **State Splitting:** Break the monolith into smaller, independent state files (Tradeoff: increased complexity in managing cross-state dependencies).
2. **Targeted Plans:** Use `-target` (Tradeoff: risky, can lead to inconsistent state).
3. **Reduce Refreshing:** Use `-refresh=false` (Tradeoff: plan might be inaccurate if drift exists).
4. **Increase Parallelism:** Adjust `-parallelism` (Tradeoff: can hit API rate limits).

**T19** — State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a CI pipeline crashes, the lock remains in the backend (e.g., DynamoDB). You can break it with `tofu force-unlock <LOCK_ID>`. **Risk:** If another process is actually running, force-unlocking can lead to state corruption.

**T20** — 
1. Ensure the new S3 bucket and DynamoDB table exist.
2. Update the `backend` block in your `.tf` files.
3. Run `tofu init -migrate-state`.
4. Tofu will detect the change and ask to copy the existing state to the new backend.
5. **Verify:** Check the S3 bucket for the `.tfstate` file and run `tofu plan` to ensure no unexpected changes are detected.

## Ansible

**A1** — A **Task** is a single action (e.g., install a package). A **Playbook** is a collection of plays that map hosts to tasks. A **Role** is a structured way to bundle tasks, variables, files, and templates for reuse.

**A2** — `ansible_facts` is a dictionary of system information gathered by Ansible. Access the OS family via `ansible_facts['os_family']` (or `ansible_os_family`).

**A3** — 
- `command`: Executes a command without a shell environment (most secure, no pipes/redirects).
- `shell`: Executes via `/bin/sh` (allows pipes, redirects, and environment variables).
- `raw`: Executes via SSH without needing Python on the target (used for bootstrapping).

**A4** — Idempotency means running a task multiple times results in the same state without extra changes. 
- **Idempotent:** `apt: name=nginx state=present` (if installed, does nothing).
- **NOT Idempotent:** `shell: echo "hello" >> /tmp/file` (appends "hello" every single time).

**A5**
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install htop on RedHat
  package:
    name: "{{ item }}"
    state: present
  loop: [epel-release, htop]
  when: ansible_os_family == "RedHat"
```

**A6** — (Lowest to Highest): `role defaults` < `inventory group_vars` < `inventory host_vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process hosts in batches of 3. To ensure the first 3 are "ready," use a `wait_for` task or a health check task within the play. If the first batch fails, the playbook stops.

**A8** — `ansible-vault` encrypts files. To encrypt a single variable, you can use the `!vault` tag in a YAML file or use a separate encrypted vars file and include it via `include_vars`.

**A9** — An **Inventory** is a list of managed hosts. **Static** is a hardcoded file (INI/YAML). **Dynamic** is a script or plugin that queries a cloud provider (AWS/GCP) to get the current list of hosts.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **Handler** is a special task that only runs if notified by another task that reported a `changed` status. You trigger it using the `notify` keyword in a task.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory` (path to inventory), `remote_user` (default user), and `forks` (number of parallel processes).

**A13** — `register` saves the output of a task into a variable. You can then use that variable in a `when` conditional or a `debug` task.

**A14** — `import_tasks` is **static** (processed at playbook parsing time). `include_tasks` is **dynamic** (processed during runtime). Use `include_tasks` if you need to use a variable to determine which file to load or if you need conditional logic on the inclusion itself.

**A15** — **Ansible Galaxy** is a hub for sharing roles/collections. Use a `requirements.yml` file listing the roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16** — 
- `ssh`: Standard connection via SSH (default).
- `local`: Runs tasks on the control node itself.
- `network_cli`: Used for network devices (switches/routers) that don't have Python.

**A17** — `delegate_to` runs a task on a different host than the current one. `run_once` ensures a task runs only once for the entire play. 
**Example:** 
```yaml
- name: Register service in Consul
  uri: url=http://consul/register
  delegate_to: localhost
  run_once: true
```

**A18** — 
1. **Forks:** Increase `forks` in `ansible.cfg` (Tradeoff: higher CPU/RAM usage on control node).
2. **Pipelining:** Enable `pipelining = True` (Tradeoff: requires `requiretty` to be disabled in SSH).
3. **Fact Caching:** Use Redis/JSON for facts (Tradeoff: complexity in managing cache).
4. **Mitogen:** Use the Mitogen plugin (Tradeoff: third-party dependency, highly efficient).

**A19** — `{{ }}` is for expressions/variables. `{% %}` is for control logic (loops/ifs). `{# #}` is for comments.
```jinja2
upstream backend_servers {
{% for host in backend_list %}
  server {{ host.ip }}:8080; # Health check: {{ host.status }}
{% endfor %}
}
```

**A20** — 
1. **Serial:** Set `serial: 4` (processes 4 servers at a time).
2. **Pre-task:** Use `uri` module to remove the host from the Load Balancer.
3. **Deploy:** Update the application.
4. **Post-task:** Use `uri` module to perform a health check on the local app.
5. **Success:** Re-add to Load Balancer.
6. **Rollback:** Wrap the deployment in a `block`. In the `rescue` section, use the previous version's configuration to restore the failed node and re-add it to the LB.
