## Application Architecture

**AA1** — A **Monolith** is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. **Microservices** decompose the application into small, independent services communicating over a network.
*   **3 Problems of Microservices:** 1. Network latency/unreliability; 2. Distributed data consistency (no ACID across services); 3. Operational complexity (observability, deployment, service discovery).

**AA2** — **Synchronous:** The caller waits for a response before proceeding (e.g., HTTP/REST). **Asynchronous:** The caller sends a message and continues without waiting for an immediate result (e.g., RabbitMQ/AMQP).

**AA3** — An **API Gateway** handles application-level concerns (auth, rate limiting, request transformation, orchestration). A **Reverse Proxy** handles network-level concerns (SSL termination, load balancing, caching). An API Gateway *can* replace a reverse proxy for most web traffic, but it cannot replace a low-level proxy used for specialized TCP/UDP load balancing or high-performance packet routing.

**AA4** — The **Saga pattern** manages distributed transactions by a sequence of local transactions. If one fails, "compensating transactions" undo the previous steps.
*   **Choreography:** Services exchange events without a central controller. Best for simple workflows with few services.
*   **Orchestration:** A central "orchestrator" tells services what to do. Best for complex workflows with many steps.

**AA5** — **CQRS** separates read (Query) and write (Command) models. It is paired with **Event Sourcing** (storing state as a sequence of events) because the event log provides the perfect source of truth to rebuild specialized read models. This solves the problem of "impedance mismatch" where a single schema cannot efficiently handle both complex writes and high-performance, diverse read requirements.

**AA6** — The **Circuit Breaker** prevents a system from repeatedly trying an operation that is likely to fail.
*   **States:** 1. **Closed** (requests flow); 2. **Open** (requests fail immediately); 3. **Half-Open** (limited requests allowed to test recovery).
*   **Difference:** Retry with backoff attempts to fix transient errors; Circuit Breaker stops the bleeding when a service is down. Use them together by wrapping a retry logic *inside* a circuit breaker.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, highest density, lowest complexity. Highest security risk (data leakage) and highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Moderate cost/complexity. Better security (schema-level permissions), moderate noisy-neighbor risk.
3. **Separate DB:** Highest cost and operational complexity. Highest security (physical isolation) and lowest noisy-neighbor risk.

**AA8** — **Strong Consistency** ensures all reads see the latest write. For inventory: Use a **Relational Database** (PostgreSQL/MySQL) with **ACID** properties. Use **Pessimistic Locking** (SELECT FOR UPDATE) or **Distributed Locks** (Redis/Etcd) to ensure only one process can decrement a specific SKU at a time. At scale, use **Sharding** by ProductID to distribute the load while maintaining local ACID.

**AA9** — A **Sidecar** is a helper process running alongside the app container. In **Istio**, **Envoy** is the sidecar (Data Plane) that intercepts all traffic. **Istio Control Plane** (Istiod) manages configuration and distributes it to Envoys. **mTLS** between sidecars solves the problem of "identity" and "encryption in transit" without requiring the application code to manage certificates or trust.

**AA10** — **Strangler Fig:** Incrementally replace functionality. 
*   **Strategy:** 1. Place an API Gateway/Proxy in front of the .NET Framework monolith. 2. Identify a single bounded context (e.g., "Identity"). 3. Build that context in .NET 8. 4. Route traffic for that specific endpoint to the new service via the Gateway. 5. Repeat until the monolith is "strangled" and can be decommissioned.

**AA11** — 1. **Codebase** (one repo per app); 2. **Dependencies** (explicitly declared); 3. **Config** (stored in environment); 4. **Backing Services** (treated as attached resources); 5. **Build/Release/Run** (strict separation); 6. **Processes** (stateless/one per instance); 7. **Port Binding** (self-contained); 8. **Concurrency** (scale via process model); 9. **Disposability** (fast startup/shutdown); 10. **Dev/Prod Parity** (keep environments similar). These ensure portability, scalability, and automation in cloud environments.

**AA12** — 
*   **Kafka (Event-driven):** High decoupling, massive scalability, high debugging complexity, strong ordering (per partition), complex failure handling (retries/DLQs). Use for: Data pipelines, async workflows.
*   **REST/gRPC (Request-driven):** Tight coupling, lower scalability (synchronous), easier debugging, no inherent ordering, simple failure handling (immediate error). Use for: Real-time UI interactions, synchronous queries.

**AA13** — A **Load Balancer** distributes traffic across multiple servers. **Layer 4 (Transport):** Routes based on IP/Port (TCP/UDP). **Layer 7 (Application):** Routes based on HTTP headers, cookies, or URL paths. **Use Case:** Routing `/api/v1` to one service and `/images` to another.

**AA14** — A **Message Queue** (RabbitMQ) is designed for task distribution; once a message is consumed, it is typically deleted. A **Log-based Broker** (Kafka) is an append-only log; messages persist and can be replayed by multiple consumers. Pick RabbitMQ for complex routing/task management; pick Kafka for high-throughput stream processing and event replay.

**AA15** — A **Container** is an isolated user-space process sharing the host OS kernel. A **VM** includes a full guest OS and a hypervisor. Containers are popular because they are lightweight, start instantly, and provide consistent environments across dev/prod.

**AA16** — **Stateless:** Does not store client data locally (e.g., a REST API). **Stateful:** Stores data locally (e.g., a Database). Stateless services scale horizontally easily because any instance can handle any request by fetching state from a shared backend.

**AA17** — **ORM** maps database tables to programming objects. Examples: **Hibernate** (Java), **Entity Framework** (C#). **Trade-offs:** ORMs increase developer productivity and security (SQLi protection) but can introduce performance overhead and "N+1" query problems compared to optimized raw SQL.

**AA18** — **Bulkhead pattern** isolates elements into pools so that if one fails, others continue. **Implementation:** 1. **Thread Pools:** Assign a specific thread pool to each downstream service so one slow service doesn't exhaust all application threads. 2. **Deployment Groups:** Run critical services on separate hardware/clusters so a resource leak in one doesn't crash the other.

**AA19** — **OT** requires a central server to sequence operations; high complexity, low latency for local edits, but struggles with high-latency/offline. **CRDTs** allow decentralized merging without a central server; lower complexity for merging, excellent offline support, but higher memory overhead. **Choice:** **CRDTs** for offline support, as they allow local state to diverge and merge mathematically without needing a server to "bless" every operation.

**AA20** — **Challenges:** Maintaining context across different languages and protocols. 
*   **Context Propagation:** Passing IDs (W3C Trace Context/B3) in headers. 
*   **Sampling:** **Head-based** (decide at start) vs **Tail-based** (decide after trace completes, e.g., keep all errors). 
*   **Storage:** Jaeger/Tempo. 
*   **Kafka:** To ensure continuity, the producer must inject the trace context into the **Kafka Message Headers**, and the consumer must extract it to start a child span.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1 (Bare-metal):** Runs directly on hardware (e.g., VMware ESXi, Xen). **Type 2 (Hosted):** Runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network):** Block-level storage (e.g., iSCSI, Fibre Channel). Used for databases/VM disks. **NAS (Network Attached Storage):** File-level storage (e.g., NFS, SMB). Used for shared files/media.

**OP3** — **3-Tier:** Core $\rightarrow$ Distribution $\rightarrow$ Access. **Leaf-Spine:** Every Leaf switch connects to every Spine switch. It solves the "East-West" traffic bottleneck by providing predictable, low-latency, non-blocking paths between servers.

**OP4** — **Architecture:** $\ge$ 3 nodes for quorum. **Quorum:** Ensures a majority of nodes agree on state. **Fencing:** (STONITH) kills a non-responsive node to prevent data corruption. **Storage:** Ceph (distributed) is preferred for HA. **Failure:** If a node fails, the cluster detects loss of heartbeat, fences the node, and restarts its VMs on surviving nodes using the shared storage.

**OP5** — **VLAN Trunking:** Carrying multiple VLANs over one link. **802.1Q:** Adds a tag to the Ethernet frame header. **Linux Config:** Use `ip link add link eth0 name eth0.10 type vlan id 10`.

**OP6** — **RAID 1** (Mirror), **5** (Parity, 1 drive loss), **6** (Double parity, 2 drive loss), **10** (Mirror + Stripe), **Z2** (ZFS double parity). **Choice:** **RAID 10** for a database. It provides the best write performance and fastest rebuild times, which is critical for database integrity.

**OP7** — **Architecture:** 
*   **Internal:** AD-integrated DNS for local resources. 
*   **DMZ:** Authoritative servers for public zones. 
*   **Split-Horizon:** Same domain name, different IP results based on source (Internal vs External). 
*   **DNSSEC:** Digitally signs records to prevent spoofing. 
*   **Movement:** A laptop on VPN uses **Conditional Forwarders** to resolve internal AD names via the VPN tunnel; on-site, it uses local **Recursive Resolvers**.

**OP8** — **Chain:** Root CA $\rightarrow$ Intermediate/Subordinate CA $\rightarrow$ End-entity. 
*   **Deployment:** Root CA is kept **offline**; Subordinate CA is online to issue certs. **CRL/OCSP** check revocation status. 
*   **Compromise:** A compromised **Subordinate CA** only affects its branch; a compromised **Root CA** invalidates the entire PKI and requires manual re-trusting of a new root on all devices.

**OP9** — **Recommendation:** **SD-WAN**. It provides the best balance: uses cheap internet (IPsec) but manages it like MPLS with application-aware routing (prioritizing VoIP) and much lower management complexity than manual VPN meshes.

**OP10** — **IPMI/iDRAC/iLO:** Out-of-band management via a dedicated NIC. **Criticality:** Allows hardware control (power, BIOS) even if the OS is crashed. **Risk:** If exposed to the internet, attackers can gain full hardware control, wipe disks, or install firmware rootkits.

**OP11** — **LVM:** Logical volume management (standard). **LVM-Thin:** Allows over-provisioning and fast snapshots. **ZFS:** Integrated volume manager and filesystem with copy-on-write. **Snapshots:** LVM/LVM-Thin use COW; ZFS uses COW. Use ZFS for data integrity/large pools; LVM for standard Linux disk management.

**OP12** — **Strategy:** A **Stretch Cluster** across two sites. 
*   **Ceph:** Use **CRUSH rules** to ensure replicas are placed in different sites. 
*   **Tiebreaker:** You need a 3rd site (or a lightweight witness node) to maintain **Quorum**. 
*   **Split-brain:** Without a tiebreaker, both sites might think they are the "master," leading to data corruption. 2-site Ceph is bad because if the link breaks, neither side has a majority.

**OP13** — **DORA:** **D**iscover, **O**ffer, **R**equest, **A**cknowledge. If the server is unavailable and the lease expires, the client assigns itself an **APIPA** address (169.254.x.x), losing network connectivity.

**OP14** — **Unmanaged:** Plug-and-play, no configuration. **Managed:** Supports VLANs, Spanning Tree (STP), SNMP, and Port Security. Essential for segmenting traffic and troubleshooting in enterprises.

**OP15** — **NTP:** Network Time Protocol. **Criticality:** Essential for log correlation, Kerberos authentication (time drift causes login failures), and database transaction ordering. Clock drift in a cluster can cause split-brain or failed consensus.

**OP16** — **Physical:** Hardware. **VM:** Hardware + Guest OS. **Container:** Hardware + Host OS + Isolated Process. **Bare Metal:** Use for high-performance workloads (e.g., massive databases, high-frequency trading) where hypervisor overhead is unacceptable.

**OP17** — **UPS:** Provides immediate battery power for short durations (minutes) to allow graceful shutdown. **Generator:** Provides long-term power (hours/days). **ATS:** Automatically switches the load from utility power to the generator once it stabilizes.

**OP18** — **Active-Passive:** One node works, one waits. **Active-Active:** Both nodes work (requires complex state sync). 
*   **PostgreSQL HA:** Use **Pacemaker/Corosync** to manage a **Virtual IP (VIP)**. If the primary fails, Corosync detects it, Pacemaker uses **STONITH** to fence the failed node, and then moves the VIP and starts the Postgres service on the standby node.

**OP19** — **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite. 
*   **RPO/RTO:** RPO (how much data you lose); RTO (how long it takes to recover). 
*   **Types:** Full (all), Incremental (changes since last backup), Differential (changes since last full). 
*   **Ransomware:** Use **Immutable Backups** (WORM - Write Once Read Many). 
*   **Backup vs DR:** Backup is the *data*; Disaster Recovery is the *process/infrastructure* to restore service.

**OP20** — **802.1X:** 
*   **Roles:** **Supplicant** (Client), **Authenticator** (Switch), **Auth Server** (RADIUS). 
*   **Methods:** **EAP-TLS** (Certificates, most secure) vs **PEAP** (Username/Password). 
*   **Dynamic VLAN:** RADIUS sends a VLAN ID to the switch upon success. 
*   **Failure:** Port is blocked or moved to a "Guest" VLAN. 
*   **MAB:** The switch checks the device's MAC address against a whitelist in RADIUS for devices (like printers) that can't run an 802.1X supplicant.
