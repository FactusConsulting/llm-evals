## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking. You manage the OS and apps. *Ex: AWS EC2.* **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing the underlying OS/runtime. *Ex: Google App Engine.* **SaaS (Software as a Service):** Fully managed software delivered over the web. *Ex: Microsoft 365.*

**CL2** — The provider is responsible for the "Security **of** the Cloud" (physical hardware, global infrastructure). The customer is responsible for "Security **in** the Cloud" (data, identity, configurations).
* **IaaS VMs:** Provider manages hardware/hypervisor; You manage OS, patching, and apps.
* **Managed Kubernetes:** Provider manages control plane and nodes; You manage pods, network policies, and app security.
* **SaaS (M365):** Provider manages almost everything (app, OS, infra); You manage user access, data classification, and device compliance.

**CL3** — **VPC:** A private, isolated virtual network. **Subnet:** A range of IP addresses within a VPC used to group resources. **Security Group (SG):** A virtual firewall for *instances* (stateful). **NACL:** A firewall for *subnets* (stateless).
* **Layering:** Traffic enters the VPC $\rightarrow$ hits the Subnet (NACL) $\rightarrow$ hits the Instance (SG).
* **Stateful (SG):** If you allow inbound traffic, the return outbound traffic is automatically allowed.
* **Stateless (NACL):** You must explicitly define both inbound and outbound rules for traffic to flow.

**CL4** — **Landing Zone:** A pre-configured, multi-account environment following best practices. **OUs (Organizational Units):** Logical groupings of accounts (e.g., Prod, Dev, Security). **Guardrails:** Automated policies (SCP/Azure Policy) to prevent non-compliant actions. **Shared Networking:** Using a Hub-and-Spoke (Transit Gateway/Azure Virtual WAN) to centralize inspection and connectivity. **Centralized Logging:** Aggregating all logs into a dedicated, locked-down account.
* **Why not single-account?** A single account creates a massive blast radius, lacks granular permission boundaries, makes cost attribution difficult, and complicates compliance/auditing.

**CL5** — **IaC:** Managing infrastructure via machine-readable definition files.
* **Terraform/OpenTofu:** Declarative, provider-agnostic, massive ecosystem. *Use for: Multi-cloud/general infra.*
* **Pulumi:** Uses general-purpose languages (Python, Go). *Use for: Dev-heavy teams wanting complex logic.*
* **CloudFormation/Bicep:** Native to AWS/Azure respectively. *Use for: Deepest integration with specific cloud features.*
* **Crossplane:** Kubernetes-native IaC. *Use for: Managing cloud resources via K8s APIs/GitOps.*

**CL6** — **HPA:** Scales number of pods based on CPU/RAM. **VPA:** Increases/decreases CPU/RAM of existing pods. **Cluster Autoscaler:** Adds/removes VM nodes to the cluster. **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag or RabbitMQ queue depth).
* **KEDA vs HPA:** Use KEDA when scaling needs to be driven by external event sources (queues, streams) rather than just resource utilization.

**CL7** — **RPO (Recovery Point Objective):** Max data loss allowed. **RTO (Recovery Time Objective):** Max downtime allowed.
* **Active-Active:** Traffic split across two regions; zero downtime; highest cost.
* **Active-Passive:** One region is standby; failover required; moderate cost.
* **Database:** **Sync** (no data loss, high latency) vs **Async** (low latency, potential data loss).
* **DNS:** Route53/Traffic Manager routes users to the healthy region.
* **DR Types:** **Pilot Light** (minimal core services running); **Warm Standby** (scaled-down version of full stack); **Multi-site Active-Active** (full capacity in both).

**CL8** — **GitOps:** Using Git as the "Single Source of Truth" for infrastructure/apps.
* **ArgoCD vs FluxCD:** ArgoCD provides a powerful UI and multi-tenant features; FluxCD is more lightweight and follows a "pull" model more strictly.
* **Secrets:** Never store raw secrets in Git. Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (pulls from AWS Secrets Mgr/Vault), or **HashiCorp Vault**.
* **Drift:** If a manual change occurs, the GitOps controller detects the mismatch and automatically overwrites the manual change to match the Git state.

**CL9** — **Architecture:**
* **StatefulSet:** Ensures stable network IDs and ordered deployment/scaling.
* **PV/PVC with Local Storage:** Use a `Local Persistent Volume` class for low-latency, direct-attached SSDs.
* **Headless Service:** Allows direct pod-to-pod communication via DNS (essential for distributed databases).
* **Init Containers:** Used to prepare the filesystem or download config files before the main app starts.
* **ConfigMaps:** Mounted as volumes to place files at specific paths.
* **Pod Disruption Budget (PDB):** Ensures a minimum number of pods remain available during voluntary disruptions (e.g., node upgrades).

**CL10** — **Service Account:** A K8s identity for processes. **Workload Identity/IRSA:** A mechanism to map a K8s Service Account to a Cloud IAM Role.
* **Why not mount credentials?** Hardcoding/mounting long-lived secret keys in a pod is a massive security risk; if the pod is compromised, the keys are stolen.
* **Workload Identity Federation:** Uses OIDC to allow the K8s cluster to exchange a short-lived token for a cloud IAM token, eliminating the need for static secrets.

**CL11** — **Object (S3/Blob):** Unstructured data (images, logs). High durability ($11$ nines), high latency. **Block (EBS/Managed Disk):** Raw volumes for OS/DBs. Low latency, attached to one VM. **File (EFS/Azure Files):** Shared filesystem (NFS/SMB) accessible by many VMs.
* **Durability/Availability:** Object storage is most durable; Block is most performant; File is most collaborative.

**CL12** — **Zero-Trust:** "Never trust, always verify."
* **Implementation:** **Network Policies** (L3/L4 isolation), **Service Mesh (Istio/Linkerd)** for mTLS (identity-based encryption), **Admission Controllers** (to block non-compliant pods), **Image Signing** (Cosign), **Runtime Security (Falco)** to detect anomalous syscalls.
* **Difference:** Traditional security relies on a "hard shell" (perimeter) and "soft center." Zero-trust assumes the network is already breached and secures every individual workload/request.

**CL13** — **CDN:** A distributed network of proxy servers that caches content closer to users. **Services:** AWS CloudFront, Azure Front Door.
* **Use CDN:** For static assets (images, JS, video) to reduce latency and origin load.
* **Use Origin:** For highly dynamic, personalized data that cannot be cached or for low-traffic internal tools.

**CL14** — **Region:** A geographic area containing multiple AZs. **AZ:** One or more discrete data centers with redundant power/cooling.
* **Why multi-AZ?** To protect against a single data center failure.
* **Zonal vs Regional:** A Zonal resource (e.g., EBS) lives in one AZ; a Regional resource (e.g., S3) is replicated across the entire region.

**CL15** — **Managed DB:** Provider handles patching, backups, high availability, and scaling.
* **Vs VM:** On a VM, you manage the OS, DB installation, backups, and manual failover. On a managed service, you only manage the schema and queries.

**CL16** — **IAM:** **Users** (people), **Groups** (collections of users), **Roles** (temporary identities for services/users), **Policies** (JSON docs defining permissions).
* **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply via granular IAM policies and regular access reviews.

**CL17** — **Serverless:** Running code without managing servers (event-driven).
* **Comparison:** Lambda (AWS), Functions (Azure), Cloud Functions (GCP).
* **Cold Starts:** Latency when a function is invoked after being idle (the provider must spin up a container).
* **Poor Fit:** Long-running processes, high-performance computing, or applications requiring constant low-latency response.

**CL18** — **Ingress:** Standard K8s resource for L7 routing. **Gateway API:** The modern successor; more expressive and role-oriented. **Cloud LB Annotations:** Triggers a cloud provider LB (e.g., ALB) to sit in front of the cluster. **Service Mesh Ingress:** Uses a mesh gateway (e.g., Istio) for advanced L7 routing/mTLS.
* **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Service Mesh Gateway.
* **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenant environments, and better separation of concerns between infra and app teams.

**CL19** — **Strategy:**
* **Savings:** Use **Reserved Instances/Savings Plans** for predictable workloads; **Spot Instances** for stateless/batch jobs.
* **Optimization:** **Right-sizing** (matching instance size to usage), **Storage Tiering** (moving old data to S3 Glacier), **Idle Detection** (finding unused VMs).
* **FinOps:** Implement **Showback** (reporting costs to teams) or **Chargeback** (billing teams directly).
* **Tools:** AWS Cost Explorer, Azure Cost Management, CloudHealth.

**CL20** — **Multi-Cloud Strategy:**
* **Abstraction:** Use **Kubernetes** as the common runtime and **Terraform** for IaC.
* **Networking:** Use **VPN/DirectConnect/ExpressRoute** to link clouds.
* **Identity:** Use **OIDC/SAML Federation** so users have one identity across clouds.
* **Trade-offs:** Multi-cloud increases complexity and cost (egress fees, skill gaps) but prevents vendor lock-in and provides extreme resilience.
* **Justification:** Only justified for massive scale, regulatory requirements, or specific regional availability. For most, it is unnecessary complexity.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** A framework for ICS security.
* **Level 0:** Physical process (sensors, actuators).
* **Level 1:** Basic control (PLCs, RTUs).
* **Level 2:** Area supervisory control (HMIs, SCADA).
* **Level 3:** Site-wide operations (Historians, MES).
* **Level 4/5:** Enterprise/Corporate (ERP, Internet).

**OT2** — **IT:** Focuses on Data Confidentiality. **OT:** Focuses on Process Availability and Safety.
* **Patching:** Standard IT patching can cause unexpected reboots or latency, which in OT can lead to physical damage or safety hazards.

**OT3** — **IDMZ:** A buffer zone between IT and OT.
* **Traffic:** Only strictly defined, inspected traffic (e.g., data from Historian to ERP) should cross.
* **Danger:** Direct L4-to-L1 connectivity allows a compromised corporate laptop to send malicious commands directly to a PLC, bypassing all monitoring.

**OT4** — 1. **Modbus TCP:** Level 1/2 (Field/Control). 2. **OPC UA:** Level 2/3 (Supervisory/Integration). 3. **EtherNet/IP:** Level 1/2 (Control). 4. **PROFINET:** Level 1/2 (Control). 5. **MQTT:** Level 3/Cloud (Data transport/IIoT).

**OT5** — **Data Diode:** A hardware device that allows data to flow in only one direction (physical light/fiber isolation). **Firewall:** Software-based, allows bidirectional traffic based on rules.
* **Use Diode:** When you need absolute physical assurance that no signal can return to the OT network (e.g., sending sensor data to the cloud).
* **Limitation:** A diode cannot handle "handshakes" or bidirectional protocols (like TCP) without specialized proxies.

**OT6** — **Flow:** Sensor $\rightarrow$ PLC $\rightarrow$ OPC UA Server $\rightarrow$ Historian $\rightarrow$ Edge Gateway (converts to MQTT) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
* **Boundaries:** Place the IDMZ between the Historian/Gateway and the Corporate network.

**OT7** — **Zones:** Groupings of assets with similar security requirements. **Conduits:** The communication paths between zones.
* **Model:** [Corporate Zone] $\rightarrow$ (Conduit: Firewall) $\rightarrow$ [IDMZ] $\rightarrow$ (Conduit: Firewall) $\rightarrow$ [SCADA Zone] $\rightarrow$ (Conduit: VLAN/Firewall) $\rightarrow$ [PLC/SIS Zone].

**OT8** — **Strategy:**
1. **Audit:** Map all assets via passive monitoring.
2. **VLANs:** Segment by production line (Line 1 VLAN, Line 2 VLAN, etc.).
3. **Firewalls:** Place industrial firewalls between lines and between SCADA and PLCs.
4. **Remote Access:** Use a Jump Host in the IDMZ with MFA.
5. **Transition:** Use "Parallel Implementation"—build the new network alongside the old, then migrate one line at a time during scheduled downtime.

**OT9** — **SIS:** Independent system designed to take a process to a safe state if the BPCS fails. **IEC 61511:** Standard for functional safety in the process industry.
* **Isolation:** SIS must be isolated to prevent a single failure (or cyber attack) from disabling both control and safety.
* **Ransomware:** If it reaches the SIS, it could prevent a safe shutdown during an emergency, leading to explosions or environmental disasters.

**OT10** — **PLC:** Logic controller for specific tasks (Level 1). **DCS:** Distributed control for large, continuous processes (Level 2). **SCADA:** Supervisory system for geographically dispersed assets.
* **Coexistence:** Yes, they often work together (SCADA monitors the DCS/PLCs).

**OT11** — **Architecture:** Use a **Jump Host** in the IDMZ. Require **MFA**. Implement **Session Recording** for auditing. Use **Time-limited/Just-in-Time** access.
* **Why not RDP to HMI?** It bypasses the IDMZ, exposes the HMI directly to the IT network, and provides a direct path for lateral movement.

**OT12** — **Plan:**
1. **Detection:** Use an OT-IDS to flag unusual Modbus/S7 commands.
2. **Inventory:** Verify if the compromised VPN is accessing known assets.
3. **Response:** Isolate the Level 3 network from IT.
4. **Coordination:** Alert the operator to switch to manual control if necessary.
5. **Safety:** Ensure the process is in a "steady state" before isolating segments.
* **Operator Role:** The operator is the final authority on whether a cyber-action is safe for the physical process.

**OT13** — **HMI:** A dashboard for operators to monitor/control the process. **Engineering Workstation:** A high-privilege machine used to program PLCs and configure the system.

**OT14** — **Historian:** A database that stores time-series process data.
* **Plant Historian (L3):** Stores high-resolution, real-time data for local operations.
* **Enterprise Historian (L4):** Aggregates data from multiple plants for business analytics/KPIs.

**OT15** — **Ladder Logic:** A graphical programming language resembling electrical relay diagrams. Executed by a **PLC**.
* **Why dominant?** It is intuitive for electricians/engineers and maps directly to physical electrical logic.

**OT16** — **RTU:** Designed for long-distance, low-power, remote telemetry (e.g., oil pipelines). **PLC:** Designed for high-speed, local factory floor control.
* **Environment:** RTUs are used in remote/harsh environments (water/gas/power grids); PLCs are used in controlled factory settings.

**OT17** — **Analog:** Continuous signal (4-20mA). **Digital:** Discrete (On/Off).
* **4-20mA vs 0-20mA:** 4mA provides a "live zero." If the wire breaks, the signal drops to 0mA, allowing the system to distinguish between a "zero reading" and a "broken wire/fault."

**OT18** — **Inventory:** You cannot protect what you don't know exists.
* **Techniques:** **Passive Monitoring** (sniffing traffic) is safe. **Active Scanning** (Nmap/WMI) is dangerous because it can crash sensitive, older PLCs/IEDs.

**OT19** — **MITRE ATT&CK for ICS:**
1. **Inhibit Response Function:** (e.g., disabling an alarm).
2. **Impair Process Control:** (e.g., changing setpoints).
3. **Loss of Safety:** (e.g., disabling SIS).
4. **Inhibit Control:** (e.g., DoS on a PLC).
5. **Impair Process:** (e.g., manipulating sensor data).
* **Difference:** It focuses on physical consequences/process impact rather than just data theft. Use it to map your visibility into "Control" vs "Safety" zones.

**OT20** — **Converged SOC:**
* **Collection:** Use passive network taps/SPAN ports to avoid latency.
* **Integration:** Feed OT-IDS alerts into a central SIEM.
* **Triage:** Use OT engineers to validate if an "anomaly" is a cyber attack or just a physical process change.
* **Staffing:** IT analysts handle the "how" (malware/VPN), OT engineers handle the "what" (process impact).
* **Firmware Alert:** Treat it as a **Critical Incident**. Immediately isolate the PLC, check the last known good configuration, and involve the plant engineer to verify physical process stability before attempting a rollback.
