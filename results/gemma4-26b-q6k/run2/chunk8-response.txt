AA1 — A monolith is a single, unified unit where all business logic, UI, and data access reside in one codebase/process. Microservices decompose this into small, independent services communicating over a network. 3 problems introduced: 1) Network latency/unreliability, 2) Distributed data consistency (CAP theorem challenges), and 3) Operational complexity (observability, deployment, and service discovery).

AA2 — Synchronous: The client sends a request and waits (blocks) for a response before continuing (e.g., REST/HTTP). Asynchronous: The client sends a message/request and continues its work without waiting for an immediate response (e.g., RabbitMQ/AMQP).

AA3 — An API Gateway provides application-level logic (authentication, rate limiting, request transformation, orchestration). A reverse proxy primarily handles routing, load balancing, and SSL termination. An API Gateway cannot entirely replace a reverse proxy because proxies are often more efficient at low-level L4/L7 routing and protecting the network edge, whereas Gateways are optimized for API management.

AA4 — The Saga pattern manages distributed transactions by breaking them into a sequence of local transactions. Each local transaction updates a service and triggers the next step. 1) Choreography: Services exchange events without a central controller (best for simple workflows). 2) Orchestration: A central "orchestrator" tells services what to do (best for complex workflows).

AA5 — CQRS separates read (Query) operations from write (Command) operations. It is often paired with Event Sourcing (storing state as a sequence of events) because CQRS allows the read model to be optimized differently from the write model. This solves the problem of complex query requirements and high-concurrency contention found in traditional CRUD models.

AA6 — The Circuit Breaker prevents a system from repeatedly trying an operation that is likely to fail. States: 1) Closed (requests flow normally), 2) Open (requests fail immediately), 3) Half-Open (limited requests allowed to test recovery). It differs from retry/backoff because retry attempts to fix a transient error, while a circuit breaker stops the bleeding to prevent cascading failure. Use both by retrying a few times, then tripping the circuit if failures persist.

AA7 — 1) Shared DB/Schema: Lowest cost, highest noisy-neighbor risk, lowest security (row-level leaks), lowest complexity. 2) Shared DB/Separate Schema: Medium cost, medium security, medium complexity, medium noisy-neighbor risk. 3) Separate DB: Highest cost, highest security (physical isolation), highest complexity, lowest noisy-neighbor risk.

AA8 — Eventual consistency: Data will be consistent across all nodes given enough time. Strong consistency: Data is immediately consistent across all nodes. For inventory: Use a Strong Consistency model. Architect with a relational database (e.g., PostgreSQL) using ACID transactions, or a distributed SQL DB (e.g., CockroachDB) using consensus protocols (Raft/Paxos) to ensure a single source of truth for stock levels.

AA9 — A sidecar is a helper process running alongside the main application container. In Istio, Envoy acts as the sidecar, intercepting all network traffic. The Data Plane consists of the Envoys; the Control Plane (Istiod) manages and configures them. mTLS between sidecars solves the problem of "identity" and encryption in transit, ensuring that even if the network is compromised, service-to-service traffic is authenticated and encrypted, which application-level TLS cannot easily manage at scale.

AA10 — The Strangler Fig pattern involves placing a proxy/router in front of the monolith and routing new/migrated functionality to new services. Strategy: 1) Deploy an API Gateway/Proxy. 2) Identify a bounded context (e.g., "Billing"). 3) Build the new .NET 8 service. 4) Route "Billing" traffic to the new service via the proxy. 5) Repeat until the monolith is "strangled" and can be decommissioned.

AA11 — 1) Codebase (one repo per service), 2) Dependencies (explicitly declared), 3) Config (stored in environment), 4) Backing services (treated as attached resources), 5) Build/Release/Run (strict separation), 6) Processes (stateless). These ensure portability, scalability, and automation in cloud environments.

AA12 — Kafka (Event-driven): High scalability, loose coupling, complex debugging, guaranteed ordering within partitions, handles failures via persistence. REST/gRPC (Request-driven): Lower latency, tight coupling, easier debugging, strict request-response, harder to scale under massive bursts. Choose Kafka for asynchronous workflows/data pipelines; choose REST/gRPC for real-time, synchronous user interactions.

AA13 — A load balancer distributes incoming network traffic across multiple servers. Layer 4 (Transport): Routes based on IP/Port (TCP/UDP). Layer 7 (Application): Routes based on HTTP headers, cookies, or URL paths. Use Case: Routing `/api/v1` to one service and `/images` to another based on the URL path.

AA14 — A message queue (RabbitMQ) focuses on delivering messages to consumers and deleting them once acknowledged (point-to-point). A log-based broker (Kafka) appends messages to a persistent log that can be replayed. Pick RabbitMQ for complex routing/task queues; pick Kafka for high-throughput stream processing and event replayability.

AA15 — A container is an isolated user-space process sharing the host OS kernel. A VM includes a full guest OS and a hypervisor. Containers are popular because they are lightweight, start instantly, and provide consistent environments across dev/prod.

AA16 — Stateless: Does not store client data between requests (e.g., a REST API). Stateful: Stores session/context (e.g., a database). Stateless services are easier to scale because any instance can handle any request, allowing you to simply add more instances behind a load balancer.

AA17 — An ORM maps database tables to objects in code. Examples: Hibernate (Java), Entity Framework (.NET). Trade-offs: ORMs increase developer productivity and prevent SQL injection, but can lead to "N+1" query problems and inefficient SQL compared to hand-tuned raw SQL.

AA18 — The Bulkhead pattern isolates elements of an application into pools so that if one fails, the others continue to function. Implementation: Use separate thread pools for different downstream services so that a slow service doesn't exhaust all threads in the caller, or deploy services into separate hardware/clusters to prevent resource contention.

AA19 — OT: Centralized server resolves conflicts by transforming operations; high complexity, low latency for local edits. CRDTs: Mathematical structures that resolve conflicts locally without a central server; lower complexity for developers, better for offline support. For offline editing, choose CRDTs because they allow seamless merging of divergent states once connectivity is restored without needing a central authority to "decide" the order.

AA20 — Challenges: Maintaining a single trace ID across different protocols and languages. Context propagation: Passing headers (W3C Trace Context/B3). Sampling: Head-based (decide at start) vs Tail-based (decide after seeing the whole trace). In Kafka, ensure the producer injects trace headers into the Kafka message headers, and the consumer extracts them to continue the span.

OP1 — Type 1: Runs directly on hardware (e.g., VMware ESXi, Xen). Type 2: Runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

OP2 — SAN (Storage Area Network): Block-level storage, high speed, used for databases/VMs (Protocols: Fibre Channel, iSCSI). NAS (Network Attached Storage): File-level storage, easier to share files (Protocols: NFS, SMB/CIFS).

OP3 — 3-tier: Core (backbone), Distribution (policy/routing), Access (end-devices). Leaf-Spine: A two-tier architecture where every leaf switch connects to every spine switch. It solves the "east-west" traffic bottleneck and provides predictable latency/bandwidth in modern data centers.

OP4 — Architecture: Minimum 3 nodes for quorum. Use Ceph for shared storage. Fencing (STONITH) is required to prevent split-brain. If a node fails, the cluster uses quorum to elect a new leader; if the storage is Ceph, data remains available via replication on other nodes.

OP5 — VLAN trunking allows multiple VLANs to travel over a single link using 802.1Q tags. On Linux, use "sub-interfaces" (e.g., `eth0.10`, `eth0.20`) via `ip link` or Netplan to tag traffic for different VLAN IDs.

OP6 — RAID 1 (Mirroring), 5 (Parity, min 3 drives), 6 (Double Parity, min 4), 10 (Striped Mirrors), Z2 (ZFS double parity). For a database: Choose RAID 10 for the best balance of high IOPS and fault tolerance.

OP7 — Use Split-Horizon: Internal DNS resolves internal names; External DNS resolves public names. Use a DMZ for public servers. A laptop moving to VPN would use a conditional forwarder or a different DNS suffix to resolve internal resources via the VPN tunnel.

OP8 — Root CA (Offline) $\rightarrow$ Subordinate CA $\rightarrow$ End-entity. CRL/OCSP check if a cert is revoked. Compromised Subordinate: Only certificates issued by that CA are invalid. Compromised Root: The entire PKI is untrusted and must be rebuilt.

OP9 — For 50 users/site with VoIP: SD-WAN is the best recommendation. It provides the reliability of MPLS with the cost-effectiveness of internet, using intelligent path selection to prioritize VoIP traffic over the best available link.

OP10 — iDRAC/iLO/IPMI provides hardware-level access (power, console) regardless of OS state. It is critical for remote recovery. If exposed to the internet, attackers can gain full control of the physical server.

OP11 — LVM: Logical volume management (standard). LVM-Thin: Thin provisioning (allocates space as needed). ZFS: Combined file system and volume manager with copy-on-write. LVM snapshots are "copy-on-write" (metadata-based); ZFS snapshots are near-instant and highly efficient.

OP12 — A stretch cluster requires low latency (<5-10ms RTT). Use Ceph CRUSH rules to ensure replicas are placed across different sites. A tiebreaker (witness node) is required to prevent split-brain. 2-site Ceph is bad because if the link breaks, both sites might think they are the master, leading to data corruption.

OP13 — DORA: Discover, Offer, Request, Acknowledge. If the server is unavailable, the client will eventually fail to renew and fall back to an APIPA (Automatic Private IP Addressing) address (169.254.x.x).

OP14 — Managed switches allow configuration (VLANs, Spanning Tree, SNMP). Unmanaged are "plug-and-play." Managed switches are essential for security (port security), segmentation (VLANs), and troubleshooting.

OP15 — NTP synchronizes clocks. In a cluster, clock drift can break authentication protocols (Kerberos), cause database transaction errors, and make log correlation impossible.

OP16 — Physical: Direct hardware access (highest performance). VM: Hardware abstraction (high isolation). Container: OS abstraction (high density). Run on bare metal for high-performance computing (HPC) or massive databases where hypervisor overhead is unacceptable.

OP17 — UPS provides short-term battery power; Generator provides long-term power. An ATS switches the load from utility to generator automatically when power fails.

OP18 — Active-Passive: One node is standby. Active-Active: Both nodes handle traffic. For PostgreSQL HA: Use Pacemaker/Corosync to manage a Virtual IP (VIP). If the active node fails, STONITH (Shoot The Other Node In The Head) ensures the failed node is truly dead before the standby takes over the VIP to prevent data corruption.

OP19 — 3-2-1: 3 copies, 2 media types, 1 offsite. RPO (how much data you lose) and RTO (how long it takes to recover). Use immutable backups (WORM) to prevent ransomware from deleting them. Backup is data preservation; Disaster Recovery is the process of restoring operations.

OP20 — Supplicant (client), Authenticator (switch), Authentication Server (RADIUS). EAP-TLS uses certificates (most secure); PEAP uses passwords. MAB (MAC Authentication Bypass) allows devices like printers to connect by checking their MAC address against a whitelist if they can't perform 802.1X.
