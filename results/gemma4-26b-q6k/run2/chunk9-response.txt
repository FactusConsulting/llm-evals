## Cloud Infrastructure Architecture

**CL1**
*   **IaaS (Infrastructure as a Service):** Provides raw computing resources (VMs, storage, networking). You manage the OS, middleware, and apps. *Example: AWS EC2.*
*   **PaaS (Platform as a Service):** Provides a framework for developers to build/deploy apps without managing underlying OS/hardware. *Example: Google App Engine.*
*   **SaaS (Software as a Service):** Fully managed software delivered via web. You only manage user access/data. *Example: Microsoft 365.*

**CL2**
*   **IaaS VMs:** Provider manages hardware/virtualization; You manage OS, patching, apps, and data.
*   **Managed Kubernetes (EKS/AKS):** Provider manages Control Plane and worker node lifecycle; You manage K8s objects, networking policies, and container security.
*   **SaaS (M365):** Provider manages everything (infrastructure to app code); You manage identity (users/groups) and data configuration.

**CL3**
*   **VPC:** A private, isolated virtual network.
*   **Subnet:** A range of IP addresses within a VPC used to segment resources.
*   **Security Group (SG):** A virtual firewall for *instances* (stateful).
*   **NACL:** A firewall for *subnets* (stateless).
*   **Layering:** Traffic hits the NACL (subnet level) first, then the SG (instance level).
*   **Stateful vs. Stateless:** SGs are **stateful** (if you allow inbound traffic, outbound response is automatically allowed). NACLs are **stateless** (you must explicitly define both inbound and outbound rules).

**CL4**
*   **Landing Zone:** A pre-configured, multi-account environment following best practices.
*   **Organizational Units (OUs):** Logical groupings of accounts (e.g., Prod, Dev, Security).
*   **Guardrails:** Automated policies (SCP in AWS) to prevent non-compliant actions.
*   **Shared Networking:** Using a Hub-and-Spoke (Azure) or Transit Gateway (AWS) to centralize inspection and connectivity between VPCs/VNets.
*   **Centralized Logging:** Sending all audit logs (CloudTrail/Activity Logs) to a dedicated security account.
*   **Single-account problem:** Lack of blast radius isolation, difficulty in applying granular permissions, and "noisy neighbor" issues with resource limits/quotas.

**CL5**
*   **Terraform/OpenTofu:** Declarative, provider-agnostic (HCL). Best for multi-cloud/general infra.
*   **Pulumi:** Uses general-purpose languages (Python, TS). Best for developers who want logic/loops in code.
*   **CloudFormation/Bicep:** Native to AWS/Azure. Best for deep, immediate support of new provider features.
*   **Crossplane:** Kubernetes-native IaC. Best if you want to manage cloud resources using K8s CRDs.

**CL6**
*   **HPA:** Scales pods based on CPU/Memory.
*   **VPA:** Adjusts pod resource requests/limits (not number of pods).
*   **Cluster Autoscaler:** Adds/removes nodes to the cluster.
*   **KEDA:** Event-driven autoscaling (e.g., scale based on Kafka lag or RabbitMQ queue depth).
*   **KEDA vs HPA:** Use KEDA when scaling needs to be triggered by external event sources rather than just resource utilization.

**CL7**
*   **RPO/RTO:** RPO (Recovery Point Objective) is max data loss; RTO (Recovery Time Objective) is max downtime.
*   **Active-Active:** Traffic flows to both regions; highest availability, highest cost.
*   **Active-Passive:** One region is standby; lower cost, higher RTO.
*   **Replication:** Sync (zero data loss, high latency) vs. Async (low latency, potential data loss).
*   **DNS Failover:** Route53/Traffic Manager redirects traffic to the healthy region.
*   **State Management:** Use global databases (DynamoDB Global Tables) or replicated storage.
*   **DR Types:**
    *   **Pilot Light:** Minimal core services running (e.g., DB only); slow recovery.
    *   **Warm Standby:** Scaled-down version of the full stack; medium recovery.
    *   **Multi-site Active-Active:** Full capacity in both; near-zero recovery.

**CL8**
*   **GitOps:** Using Git as the "single source of truth" for desired state.
*   **ArgoCD vs FluxCD:** ArgoCD has a powerful UI and multi-tenancy; FluxCD is lightweight, CLI-driven, and follows a "GitOps toolkit" approach.
*   **Secrets:** Use **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (pulls from AWS SM/Vault), or **Vault** (direct injection).
*   **Drift:** GitOps controllers detect the difference and automatically "reconcile" (overwrite) the manual change to match Git.

**CL9**
*   **StatefulSet:** Ensures stable network IDs and persistent storage mapping.
*   **PV/PVC (Local Storage):** Use a `local` storage class for low-latency NVMe/SSD access.
*   **Headless Service:** Allows direct pod IP discovery for peer communication.
*   **Init Containers:** Used to prepare the filesystem or download config files before the main app starts.
*   **ConfigMaps:** Mounted as volumes to place files at specific paths.
*   **Pod Disruption Budget (PDB):** Ensures a minimum number of pods remain available during maintenance.

**CL10**
*   **Service Account:** K8s identity for a pod.
*   **Workload Identity/IRSA:** Maps a K8s Service Account to a Cloud IAM Role via OIDC.
*   **Why not mount credentials?** Hardcoding/mounting long-lived keys in pods is a massive security risk if the pod is compromised.
*   **Federation Solution:** Workload identity uses short-lived, automatically rotated tokens, eliminating the need for static secrets.

**CL11**
*   **Object (S3/Blob):** Unstructured data (images, logs). High durability, accessed via API.
*   **Block (EBS/Managed Disk):** Raw volumes for VMs/DBs. Low latency, high performance.
*   **File (EFS/Azure Files):** Shared filesystem (NFS/SMB) for multiple instances.
*   **Guarantees:** Object storage typically offers 11 nines of durability; Block/File availability depends on the specific tier/redundancy.

**CL12**
*   **Zero-Trust Architecture:**
    *   **Network Policies:** Micro-segmentation (deny-all by default).
    *   **Service Mesh (Istio/Linkerd):** mTLS for encrypted pod-to-pod communication.
    *   **Admission Controllers:** Enforce policies (e.g., "no root containers").
    *   **Image Signing:** Ensure only trusted images run (Cosign).
    *   **Runtime Security:** Falco detects anomalous syscalls.
*   **Difference:** Traditional security relies on a "hard shell" (perimeter); Zero-Trust assumes the network is already compromised and verifies every request.

**CL13**
*   **CDN:** A distributed network of proxy servers that caches content closer to users.
*   **How it works:** User requests content $\rightarrow$ DNS directs to nearest Edge Location $\rightarrow$ Edge serves cached content or fetches from origin.
*   **Services:** AWS CloudFront, Azure Front Door.
*   **When to use:** Use a CDN for static assets (images, JS, CSS) or global low-latency delivery; serve directly from origin for highly dynamic, non-cacheable data or internal-only tools.

**CL14**
*   **Region:** A geographic area (e.g., US-East-1).
*   **AZ (Availability Zone):** One or more discrete data centers within a region.
*   **Why multi-AZ?** To protect against a single data center failure (power, cooling, networking).
*   **Zonal vs. Regional:** Zonal resources (e.g., an EBS volume) live in one AZ; Regional resources (e.g., S3 or an IAM role) are available across the entire region.

**CL15**
*   **Managed DB:** A service where the provider handles the database engine.
*   **Provider Tasks:** Patching, backups, high availability (failover), scaling, and hardware maintenance.
*   **Your Tasks:** Schema design, query optimization, user access, and data modeling.

**CL16**
*   **IAM User:** A permanent identity for a person/app.
*   **Group:** A collection of users with shared permissions.
*   **Role:** A temporary identity assumed by a user or service.
*   **Policy:** A JSON document defining permissions.
*   **Least Privilege:** Granting only the minimum permissions required to perform a task. Apply it by using granular IAM policies and regular access reviews.

**CL17**
*   **Serverless:** Running code without managing servers (FaaS).
*   **Comparison:** AWS Lambda, Azure Functions, and Google Cloud Functions are functionally similar but differ in trigger types and integration depth.
*   **Cold Start:** The latency incurred when a function is invoked after being idle (container spin-up).
*   **Poor Fit:** Long-running processes, high-performance computing, or workloads with extremely predictable, constant traffic (where VMs are cheaper).

**CL18**
*   **Ingress Resource:** Standard K8s object for HTTP routing.
*   **Gateway API:** The modern successor; more expressive and role-oriented (Infrastructure vs. App dev).
*   **Cloud LB Annotations:** Uses cloud-specific settings to provision a provider LB.
*   **Service Mesh Ingress:** Uses a mesh gateway (e.g., Istio) for advanced traffic management.
*   **TLS Termination:** Can happen at the Cloud LB, the Ingress Controller, or the Service Mesh.
*   **Gateway API vs Ingress:** Use Gateway API for complex routing, multi-tenant environments, and better separation of concerns.

**CL19**
*   **Optimization:**
    *   **RI/Savings Plans:** Commit to usage for lower rates.
    *   **Spot:** Use spare capacity for massive discounts (non-critical/stateless).
    *   **Right-sizing:** Matching instance size to actual utilization.
    *   **Storage Tiering:** Moving old data to S3 Glacier/Archive.
    *   **FinOps:** Implementing a culture of cost accountability.
*   **Tools:** AWS Cost Explorer, Azure Cost Management, CloudHealth.
*   **Processes:** Implement **Showback** (reporting costs to teams) or **Chargeback** (billing teams directly) to drive accountability.

**CL20**
*   **Multi-Cloud Strategy:**
    *   **Abstraction:** Use Kubernetes to provide a consistent runtime.
    *   **IaC:** Use Terraform to manage both providers.
    *   **Networking:** VPN or Direct Connect/ExpressRoute between clouds.
    *   **Identity:** Use OIDC/SAML for federated identity.
*   **Trade-offs:** Multi-cloud increases complexity and operational overhead significantly.
*   **Justification:** Only justified for extreme high availability, regulatory requirements, or avoiding specific vendor lock-in for a core product. For most, it is unnecessary complexity.

## OT Infrastructure Architecture

**OT1**
*   **Purdue Model:** A structural model for ICS security.
*   **Level 0:** Physical process (sensors, actuators).
*   **Level 1:** Basic control (PLCs, RTUs).
*   **Level 2:** Supervisory control (HMIs, SCADA).
*   **Level 3:** Site operations (Historians, MES).
*   **Level 4/5:** Enterprise/Business network (ERP, Internet).

**OT2**
*   **Difference:** IT focuses on Data Confidentiality; OT focuses on Process Availability and Safety.
*   **Patching:** Standard IT patching can cause unexpected reboots or latency, which in OT can lead to physical damage or safety hazards.

**OT3**
*   **IDMZ:** A buffer zone between IT and OT.
*   **Traffic:** Only specific, inspected traffic (e.g., data from Historian to ERP) should cross.
*   **Danger:** Direct connectivity allows a compromised IT workstation to send malicious commands directly to a PLC, bypassing all supervisory controls.

**OT4**
*   **Modbus TCP:** Level 1/2 (Control/Supervisory).
*   **OPC UA:** Level 2/3 (Supervisory/Site Ops).
*   **EtherNet/IP:** Level 1/2 (Control).
*   **PROFINET:** Level 1 (Control).
*   **MQTT:** Level 3/4 (Site Ops/Cloud/Enterprise).

**OT5**
*   **Data Diode:** A hardware device that allows data to flow in only one direction (physically).
*   **Use Case:** Sending logs from OT to IT without any possibility of an inbound attack.
*   **Limitation:** Unlike a firewall, it cannot handle bidirectional handshakes (TCP), making it difficult to use for standard protocols without specialized proxies.

**OT6**
*   **Flow:** Sensor $\rightarrow$ PLC $\rightarrow$ OPC UA Server $\rightarrow$ Edge Gateway (converts to MQTT) $\rightarrow$ MQTT Broker $\rightarrow$ Cloud Ingestion.
*   **Security Boundaries:** Place a firewall/IDMZ between the Edge Gateway and the Cloud, and a strict boundary between the PLC/SCADA network and the Gateway.

**OT7**
*   **Zone:** A grouping of assets with similar security requirements.
*   **Conduit:** The communication path between zones.
*   **Model:**
    *   **Zone 1:** Corporate (IT).
    *   **Zone 2:** Engineering Workstations.
    *   **Zone 3:** SCADA/Historian.
    *   **Zone 4:** PLCs.
    *   **Zone 5:** SIS (Safety Instrumented Systems) - highly isolated.
    *   **Conduits:** Firewalls/unidirectional gateways between these zones.

**OT8**
*   **Strategy:**
    *   **VLANs:** Segment by production line.
    *   **Firewalls:** Place at the boundary of each line and the SCADA network.
    *   **Transition:** Use "Transparent Mode" firewalls (Layer 2) to inspect traffic without changing IP schemes, minimizing downtime.
    *   **Remote Access:** Use a secure Jump Host in the IDMZ with MFA.

**OT9**
*   **SIS vs BPCS:** SIS is the "emergency brake" (safety); BPCS is the "driver" (process control).
*   **IEC 61511:** Standard for functional safety in the process industry.
*   **Isolation:** If SIS is connected to BPCS/IT, a ransomware attack could disable safety functions while simultaneously attacking the process, leading to catastrophic physical failure.

**OT10**
*   **PLC:** Small, logic-based controller for specific tasks (Level 1).
*   **DCS:** Distributed control system for large, continuous processes (Level 2).
*   **SCADA:** Supervisory system for geographically dispersed assets (Level 2/3).
*   **Coexistence:** Yes, they often work together (SCADA monitors the DCS/PLCs).

**OT11**
*   **Architecture:** Jump host in the IDMZ $\rightarrow$ MFA $\rightarrow$ Session Recording $\rightarrow$ Time-limited access.
*   **Why not RDP?** Direct RDP allows lateral movement and lacks the granular control/logging required to prevent an attacker from jumping from a laptop to a critical HMI.

**OT12**
*   **Plan:**
    *   **Detection:** Deploy OT-specific IDS (e.g., Nozomi/Claroty) to monitor for anomalous industrial protocols.
    *   **Response:** Isolate the compromised VPN segment; switch to manual/local control if necessary.
    *   **Coordination:** Notify the plant operator immediately.
    *   **Operator Role:** The operator is responsible for the physical safety of the plant; they decide if the process must be "tripped" (shut down) to prevent physical damage.

**OT13**
*   **HMI:** A dashboard for operators to monitor and control the process.
*   **Difference:** An HMI is for *operation*; an Engineering Workstation is for *programming* and configuring the PLCs/controllers.

**OT14**
*   **Historian:** A database that stores time-series process data.
*   **Importance:** Essential for troubleshooting, regulatory compliance, and trend analysis.
*   **Plant vs. Enterprise:** Plant Historian (Level 3) stores high-resolution, real-time data; Enterprise Historian (Level 4) stores aggregated, long-term data for business decisions.

**OT15**
*   **Ladder Logic:** A graphical programming language resembling electrical relay diagrams.
*   **Device:** Executed by a PLC.
*   **Why dominant?** It is intuitive for electricians and engineers trained in traditional electrical schematics.

**OT16**
*   **RTU:** A device used for remote telemetry, often in harsh/remote environments.
*   **Difference:** PLCs are better for high-speed, complex logic; RTUs are better for low-power, long-distance communication (e.g., cellular/radio) and wide-area monitoring.

**OT17**
*   **Analog vs Digital:** Analog is a continuous signal (4-20mA); Digital is discrete (On/Off).
*   **4-20mA vs 0-20mA:** 4-20mA is preferred because a "live zero" (4mA) allows the system to distinguish between a "zero reading" and a "broken wire" (0mA).

**OT18**
*   **Inventory:** You cannot protect what you cannot see.
*   **Techniques:** **Passive monitoring** (sniffing traffic) is safe; **Active scanning** (pinging/probing) is dangerous because it can crash older, fragile OT devices.

**OT19**
*   **MITRE ATT&CK for ICS:**
    *   **Inhibit Response Function:** (e.g., disabling an alarm).
    *   **Impair Process Control:** (e.g., changing setpoints).
    *   **Damage to Property:** (e.g., over-pressurizing a tank).
    *   **Loss of View:** (e.g., freezing the HMI screen).
    *   **Impair Process Safety:** (e.g., disabling the SIS).
*   **Difference:** It focuses on physical consequences and industrial protocols rather than just data theft.

**OT20**
*   **SOC Design:**
    *   **Log Collection:** Use passive network taps to avoid impacting real-time traffic.
    *   **Integration:** Feed OT IDS alerts into a central SIEM.
    *   **Staffing:** Use IT analysts for network/OS alerts and OT engineers to validate if a "process anomaly" is a real threat or just a mechanical issue.
    *   **Firmware Alert:** Treat it as a critical incident. Isolate the PLC, verify the firmware hash against the vendor, and check for unauthorized engineering workstation access.
