## JavaScript / TypeScript (20 questions)

**JS1** — `var` is function-scoped and subject to hoisting (initialized as `undefined`). `let` and `const` are block-scoped. `const` requires initialization and cannot be reassigned. Hoisting is JavaScript's behavior of moving declarations to the top of their scope during compilation, but only the declaration, not the assignment.

**JS2** — The Event Loop is the mechanism that monitors the call stack and queues to manage asynchronous operations in JavaScript. The **Call Stack** executes synchronous code. When an async operation (like `setTimeout` or a Promise resolution) completes, its callback is placed in the **Macrotask Queue** (e.g., I/O, timers). Microtasks (like Promise resolutions) are placed in the **Microtask Queue**. The Event Loop continuously checks: if the Call Stack is empty, it first drains the entire Microtask Queue before pulling the next task from the Macrotask Queue.

**JS3** — A closure is the ability of a function to remember and access variables from its lexical scope even after that outer function has finished executing. *Example:* A counter function factory. The classic for loop closure bug occurs when using `var` in a loop; all iterations reference the *same* variable, so they all print the final value. The fix is to use `let` (which creates a new binding for each iteration) or pass the index as an argument to an IIFE.

**JS4** — A **Promise** is an object representing the eventual completion (or failure) of an asynchronous operation. **Async/await** is syntactic sugar built on Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()` or `try...catch` around `await`. With `async/await`, `try...catch` is the standard mechanism. `Promise.all()` rejects immediately if *any* input promise rejects. `Promise.allSettled()` waits for *all* input promises to either fulfill or reject, returning an array describing the outcome of each.

**JS5** — A **Type** describes the shape of data at compile time and can be used for primitive types, unions, and intersections. It is a compile-time construct. An **Interface** is a contract that an object must adhere to; it describes the shape of an object. While they often overlap, interfaces can be used to describe object shapes, whereas types are more versatile (e.g., defining unions or tuples). **Discriminated Unions** are unions where one member has a unique literal property (the "discriminant"). This allows TypeScript to narrow the type safely using a `switch` statement on that property.

**JS6** — Prototypal inheritance means objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. `Object.create(proto)` creates a new object whose internal `[[Prototype]]` link points directly to the specified `proto` object. ES6 classes are primarily syntactic sugar over JavaScript's existing prototypal inheritance mechanism; they provide a cleaner, more familiar syntax for defining constructor functions and prototype chains.

**JS7** — The `this` keyword refers to the object that is currently executing the function. The 4 binding rules (in priority order) are: 1. **New binding** (when using `new`). 2. **Explicit binding** (using `.call()`, `.apply()`, or `.bind()`). 3. **Implicit binding** (when a function is called as a method of an object). 4. **Default binding** (when called globally/in strict mode, `this` is `undefined` or the global object). `bind()` returns a *new* function with the context permanently set; this new function can be bound again, but subsequent bindings will override the previous ones.

**JS8** — **WeakRef** holds a weak reference to an object. If the object is garbage collected, the `WeakRef` automatically becomes "dereferenced" (i.e., accessing it returns `undefined`) without preventing GC. **FinalizationRegistry** allows you to register a callback function that will be executed *after* an object has been garbage collected. They are used to perform cleanup tasks on objects without creating memory leaks. WeakMap keys must be objects because primitives (like strings or numbers) are compared by value, meaning multiple references to the same primitive would map to the same key, defeating the purpose of tracking specific object instances.

**JS9** — V8 optimizes JS by compiling code into machine code. **Hidden Classes** (or Shapes) allow V8 to quickly identify objects with the same structure (same property order/names) and reuse optimized internal representations for them. **Inline Caching** stores the type/shape of an object at the call site, allowing subsequent calls with the same type to skip type checks. **Deoptimization** occurs when V8's assumptions (based on hidden classes or inline caches) are violated (e.g., a property is added dynamically, or the object structure changes), forcing the engine to discard the optimized machine code and revert to slower, safer interpretation. Patterns causing deoptimization include dynamic property addition/deletion, or frequent changes in object structure.

**JS10** — **Tree-shaking** is a form of dead code elimination performed by bundlers (like Webpack) during the build process. It works by analyzing the static `import`/`export` structure of ES Modules. Because ES Modules are static, the bundler can trace which exported functions/variables are actually imported and used, discarding the unused code. CommonJS (`require()`) is dynamic; since `require('module')` can be called conditionally or based on runtime variables, the bundler cannot statically determine all dependencies, making effective tree-shaking impossible.

**JS11** — `null` represents the intentional absence of any object value (a deliberate assignment of "no value"). `undefined` means a variable has been declared but has not yet been assigned a value. `==` performs type coercion before comparison (e.g., `null == undefined` is true). `===` performs strict equality, checking both value and type without coercion. **Nullish coalescing (`??`)** returns the right-hand operand only if the left-hand operand is `null` or `undefined`. **Optional chaining (`?.`)** allows safe navigation through nested object properties without throwing an error if an intermediate property is `null` or `undefined`.

**JS12** — **`map()`** creates a new array by applying a function to every element in the calling array, returning a new array of the same length. **`filter()`** creates a new array containing only the elements for which the provided testing function returns `true`. **`reduce()`** executes a reducer function on each element, resulting in a single output value. With an initial value, `reduce()` starts the accumulation process with that value. **`flatMap()`** is useful when you need to map over an array and then flatten the result by one level. It combines the functionality of `map()` followed by `flat(1)`.

**JS13** — **Template literals** (backticks `` ` ``) allow for embedded expressions (`${expression}`) and multi-line strings, making string construction cleaner. **Tagged templates** allow a function to intercept and process the string parts and expressions within a template literal. The function receives the string parts (as an array) and the evaluated expressions (as subsequent arguments). *Example:* A function `sqlTag` could take the string parts and arguments, safely escaping them before constructing a parameterized SQL query string.

**JS14** — **Destructuring** is a syntax that allows unpacking values from arrays or properties from objects into distinct variables. **Object destructuring** pulls properties out of an object (e.g., `const { name, age } = user;`). **Array destructuring** pulls elements out of an array (e.g., `const [first, second] = arr;`). **Default values** allow assigning a fallback if a property/element is missing (e.g., `const { age = 30 } = user;`). **Renaming** allows assigning the extracted value to a different variable name (e.g., `const { name: fullName } = user;`). The **rest operator (`...`)** collects all remaining properties/elements into a new array or object.

**JS15** — **`for...in`** iterates over the *enumerable properties* of an object, including inherited ones (unless filtered). **`for...of`** iterates over the *values* of an iterable object (like Arrays, Maps, Sets). You should avoid `for...in` on arrays because it iterates over keys (indices) as strings, and it can iterate over non-index properties added to the array object, leading to unpredictable behavior.

**JS16** — **Generics** allow you to write reusable code that can work over a variety of types rather than a single one. **Generic Constraints (`extends`)** restrict the types that can be used with a generic type parameter, ensuring they possess certain properties (e.g., `function identity<T extends { length: number }>(arg: T): T`). **Conditional Types** allow types to be determined based on a condition (e.g., `T extends string ? string : number`). **`infer`** is used within conditional types to capture a type that matches a pattern (e.g., `type MyArray<T> = T[]`).

**JS17** — The **Module System** defines how code dependencies are managed. **CommonJS** (Node.js standard) uses synchronous `require()` to load modules and `module.exports` to expose them. **ES Modules (ESM)** use static `import`/`export` syntax, which is asynchronous and designed for static analysis. Node.js supports both; using `"type": "module"` in `package.json` tells Node.js to treat `.js` files as ESM, enabling `import`/`export`.

**JS18** — TypeScript uses a **Structural Type System**, meaning type compatibility is determined by whether an object *has* the required shape, not by whether it explicitly declares that it implements an interface (duck typing). **Excess property checks** warn when an object passed to a function has properties that the function's parameter type does not define. They apply when strict checks are enabled. **`extends`** implies inheritance/structural compatibility. **`satisfies`** asserts that an object conforms to a type *without* allowing the type to narrow the object's structure (useful for type checking literals). **Variance** describes how subtyping relates to parameter types: `in` (contravariant) means the type can be used as an input parameter; `out` (covariant) means it can be used as an output return type.

**JS19** — **Proxy** allows you to create an object that wraps another object and intercepts fundamental operations (like property lookups, assignments, function calls) via "traps." **Reflect** provides methods that mirror the built-in operations that Proxies intercept (e.g., `Reflect.get()`, `Reflect.set()`). *Example:* A validation proxy can intercept a `set` trap. If `proxy.age = -5` is called, the `set` trap fires, the proxy logic checks if `-5` is valid, and either allows the assignment or throws an error before the underlying object is modified.

**JS20** — **SharedArrayBuffer** provides a way to share raw binary data memory between different execution contexts (like Web Workers). **Atomics** provides low-level, atomic operations on the data within the `SharedArrayBuffer`. This ensures that operations like incrementing a counter happen indivisibly, preventing race conditions. **Web Workers** communicate by sharing this memory buffer. **Ordering guarantees** ensure that memory operations are visible across threads in a defined sequence. `Atomics.wait()` pauses a thread until a specific memory location changes, and `Atomics.notify()` wakes up waiting threads.

## Bash (20 questions)

**B1** — `$@` expands to all positional parameters, with each parameter quoted separately (e.g., `"$1" "$2"`). `*` expands to all positional parameters as a single string, with the characters separated by the first character of the `$IFS` variable. `"$@"` ensures that arguments containing spaces are treated as distinct arguments. `"$*"` treats all arguments as one single string.

**B2** — `set -e`: Exit immediately if a command exits with a non-zero status. `set -u`: Treat unset variables as an error and exit immediately. `set -o pipefail`: Causes a pipeline to return the exit status of the last command to exit with a non-zero status, rather than just the final command.

**B3** — `$(command)` (Command Substitution) executes the command and substitutes its standard output into the current command line. `` `command` `` (Backticks) is the older, deprecated form of command substitution, functionally identical but harder to nest. `((expression))` performs arithmetic evaluation within Bash. `expr` is an external utility that evaluates expressions, often requiring explicit spacing around operators.

**B4** — Process substitution (`<(command)`) runs a command in a subshell and makes its standard output available as a temporary file path that the current shell can read from. This is useful when a command needs to be treated as a file argument. *Example:* `diff <(ls -1) <(ls -2)` compares the output of two separate `ls` commands as if they were two distinct files.

**B5** — Use quoting: `for f in *; do ... done` or, more robustly, use `find` with `-print0` and `while IFS= read -r -d $'\0' f; do ... done`. The `for f in $(ls)` approach is dangerous because `ls` splits filenames based on the `$IFS` variable (usually space, tab, newline), causing filenames with spaces to be incorrectly parsed into multiple arguments.

**B6** — A **here document (`<<EOF`)** reads multiple lines of input until it encounters the delimiter (`EOF`) on a line by itself. A **here string (`<<<`)** passes a single line of input to a command. `<<-EOF` (here document with a leading tab) allows leading tabs in the input lines to be stripped, which is useful for configuration files where indentation matters.

**B7** — 1. `cmd > file 2>&1`: Redirect stdout to `file`, then redirect stderr (2) to the same location as stdout (1, which is now `file`). **Result: Both stdout and stderr go to `file`.** 2. `cmd 2>&1 > file`: Redirect stderr (2) to stdout (1), *then* redirect stdout (1) to `file`. **Result: Both stdout and stderr go to `file`.** 3. `cmd &> file`: (Bash 4+) Redirects both stdout and stderr to `file` simultaneously. The first two are functionally equivalent in modern Bash, but the order matters conceptually: in (1), the redirection of stderr happens *after* stdout is established; in (2), stderr is redirected *before* stdout is redirected to the final file.

**B8** — A robust lock function uses `mkdir` because it is atomic (it either succeeds completely or fails completely, preventing race conditions where two processes might try to create a file simultaneously).
```bash
lock_file() {
    local lock_dir="/tmp/my_app.lock"
    if mkdir "$lock_dir" 2>/dev/null; then
        trap "rmdir '$lock_dir'" EXIT TERM INT
        echo "Lock acquired."
        # Critical section code here
        return 0
    else
        echo "Lock already held." >&2
        return 1
    fi
}
```
`mkdir` is preferred because the operation is atomic at the filesystem level, whereas file creation (`touch`) can be interrupted between checking existence and creating the file.

**B9** — **Single quotes (`'...'`)**: Literal interpretation. No variable expansion or command substitution occurs. **Double quotes (`"..."`)**: Allows variable expansion (`$VAR`) and command substitution (`$(cmd)`), but still treats most characters literally. **No quotes**: Word splitting and pathname expansion occur. *Example:* `echo $VAR` (expands), `echo 'hello world'` (literal), `echo hello world` (splits into two arguments).

**B10** — File existence: `[ -f file ]` (is a regular file), `[ -d dir ]` (is a directory). Readability: `[ -r file ]`. `[ ]` is an alias for the `test` command. `[[ ]]` is a Bash keyword offering extended features like regex matching (`=~`) and better handling of word splitting, making it generally safer and more powerful than `[ ]`.

**B11** — `$?`: Exit status of the most recently executed foreground command (0 is success). `$$`: The Process ID (PID) of the current shell. `$!`: The PID of the most recently backgrounded command. `$#`: The number of positional arguments passed to the current script/function. *Use Case:* `$?` for error checking; `$$` for PID logging; `$!` to wait for a background job; `$#` to validate input count.

**B12** — Functions are defined using `name() { ... }` or `function name { ... }`. Both are functionally equivalent in modern Bash. To return values, functions typically print the result to standard output, and the caller captures it using command substitution: `result=$(my_function arg1)`.

**B13** — The **PATH** environment variable is a colon-separated list of directories that the shell searches sequentially when a command is invoked without a full path. Bash resolves commands by checking each directory in `$PATH` for an executable file matching the command name. A **builtin command** is part of the shell itself (e.g., `cd`, `echo`) and runs internally without spawning a new process. An **external command** is a separate executable file found in a directory listed in `$PATH`. You can check this using `type command_name`.

**B14** — `trap` allows you to specify commands to run when the shell receives a specific signal. You set handlers like `trap 'cleanup_function' EXIT` (runs on normal exit), `trap 'cleanup_function' INT` (Ctrl+C), `trap 'cleanup_function' TERM` (termination signal), and `trap 'cleanup_function' ERR` (non-zero exit status). Execution order is generally based on the signal received, but handlers registered for the same signal execute sequentially.

**B15** — **Command substitution** (`$(cmd)`) runs a command and substitutes its output. **`xargs`** takes standard input and builds and executes command lines from it. To handle spaces/newlines safely, use `find ... -print0 | xargs -0 ...`. `-0` tells `xargs` to expect null-terminated input. `-P N` runs up to $N$ processes in parallel, significantly speeding up I/O-bound tasks.

**B16** — **Arrays** store ordered lists of values (indexed numerically starting at 0). Declaration: `my_array=(item1 item2)`. Append: `my_array+=("new_item")`. Iterate: `for item in "${my_array[@]}"; do ... done`. Length: `${#my_array[@]}`. **Associative arrays** (Bash 4+) store key-value pairs (like a hash map). Declaration: `declare -A my_assoc`. Access: `my_assoc[key]`. Iterate: `for key in "${!my_assoc[@]}"; do ... done`. They are fundamentally different in structure and access method.

**B17** — A **subshell (`(...)`)** executes commands in a separate, isolated process. Any variables modified inside the subshell are lost when it exits. A **group command (`{ ...; }`)** executes commands in the *current* shell process, but they are grouped together. Variables modified inside a group command persist in the parent shell. Piping into a `while` loop (`while read line; do ... done < file`) runs the loop in a subshell, meaning any variable changes made inside the loop body are lost when the loop finishes.

**B18** — Bash handles signals by intercepting them and executing associated handlers (traps). **SIGINT** (Interrupt, Ctrl+C) is usually handled by the shell. **SIGTERM** (Terminate) is the standard, polite request to shut down. **SIGHUP** (Hangup) is often sent when a controlling terminal closes. **SIGKILL** (Kill) cannot be caught or ignored; the kernel terminates the process immediately. For graceful shutdown, use `trap` to catch `SIGTERM` and `SIGINT`, allowing background processes to finish before exiting.

**B19** — This requires splitting the file, processing chunks in parallel, and merging.
1. **Split:** `split -l 10000 logfile.log chunk_` (splits into 10k lines).
2. **Process:** `find . -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c 'process_chunk "$@"' _ {}` (Processes 4 chunks in parallel).
3. **Merge:** `cat chunk_*` (or use a dedicated merge tool if processing modified the files).
*Trade-offs:* Parallelism increases throughput but adds overhead (process creation, I/O contention). Error propagation is hard; you must check the exit code of the `xargs` command, or have the processing function explicitly write error markers to a shared log file.

**B20** — **`exec`** replaces the current shell process image with a new command, meaning the shell itself is replaced; it does not spawn a child process. This is used for resource management. `exec 3>file` opens file descriptor 3 and redirects it to `file`. `exec 3>&-` closes file descriptor 3. A **coprocess** allows a parent shell to communicate with a child process using named pipes (FIFOs) for bidirectional, persistent communication, unlike simple pipes which are unidirectional. Use a coprocess when you need continuous, interactive, two-way communication with a background task.

## PowerShell (20 questions)

**PS1** — **`Write-Output`** sends objects down the pipeline, allowing subsequent cmdlets to process them. This is the standard, pipeline-friendly way. **`Write-Host`** writes directly to the console host, bypassing the pipeline. This is useful for immediate user feedback but prevents the output from being captured or piped further.

**PS2** — The **PowerShell pipeline** passes objects from the output stream of one cmdlet to the input stream of the next. **`ForEach-Object`** (alias `%`) is a cmdlet designed to process objects coming *through* the pipeline. The `foreach` statement is a language construct used for iterating over collections (arrays, lists) *within* a script block or function, not typically for pipeline processing.

**PS3** — **`[PSCustomObject]`** creates a lightweight, dynamic object with properties defined at runtime, ideal for structured output that needs to flow through the pipeline. **`[hashtable]`** is a key-value collection, similar to a dictionary, where you access values via keys (e.g., `$ht['Key']`). You convert a hashtable to a PSCustomObject using `[PSCustomObject]@{...}` or by piping it through `Select-Object -Property @{N='Key'; E={$_.Key}}`.

**PS4** — PowerShell distinguishes between **Terminating Errors** (which stop the current operation, like a cmdlet failing to connect) and **Non-Terminating Errors** (which are warnings or recoverable issues). `-ErrorAction Stop` forces a non-terminating error to become terminating. `$ErrorActionPreference` sets the default behavior for the current scope. `try/catch` blocks catch terminating errors. If an error is non-terminating, it will be added to the automatic `$Error` variable, but the script execution will continue unless `$ErrorActionPreference` is set to `Stop`.

**PS5** — **Splatting (`@params`)** is a technique where you pass a hashtable containing parameter names as keys and values as values to a cmdlet. This allows you to define all parameters in a separate variable, making scripts cleaner and easier to reuse. *Example:* `Get-Service @params` where `@params = @{Name="Spooler"; Status="Running"}`. This differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named arguments for the cmdlet.

**PS6** — **PowerShell Remoting** allows execution of PowerShell commands on remote machines. **`Invoke-Command -ComputerName`** executes a script block on the remote machine and returns the results to the local session. **`Enter-PSSession`** establishes an interactive, persistent session on the remote machine, allowing you to run commands as if you were logged in locally. It primarily uses **WinRM** (Windows Remote Management) on Windows, and can leverage SSH for Linux/Unix targets.

**PS7** — The issue arises because when a function returns an empty array (`@()`), PowerShell treats the return value as `$null` in many contexts, or it might return an empty collection that doesn't satisfy the expected object structure. When you append to an empty array (`$result += "one"`), PowerShell often has to re-evaluate the entire array structure, leading to performance issues and sometimes unexpected type casting. The correct pattern is to use the pipeline: `return "one"`, or use `[System.Collections.Generic.List[string]]` for mutable collections, or simply return the collection directly if it's populated.

**PS8** — A **`[scriptblock]`** is a block of code that can be passed as an argument to a cmdlet or function. A **function** is a named, reusable block of code that can accept parameters and return values. You pass a scriptblock to a remote session using the `-ScriptBlock` parameter of `Invoke-Command`. The **double-hop problem** occurs when variables defined locally need to be accessed inside a remote scriptblock; they are not automatically serialized. This is solved by using `-ArgumentList` to explicitly pass variables, or by using `Invoke-Command -ScriptBlock { ... } -ArgumentList $localVar` and accessing it as `$args[0]` remotely.

**PS9** — **`@()`** creates an empty array object. **`[array]`** is a type accelerator used to explicitly cast a variable to an array type. To force a single result into an array, wrap it: `@[my_single_value]`. Indexing `$null` throws a terminating error. Indexing an empty array (`@()`) returns `$null` without error.

**PS10** — **`-eq`** (equals), **`-ne`** (not equals), **`-like`** (wildcard matching using `*` and `?`), **`-match`** (regex matching), **`-contains`** (checks if a specific item exists in an array), **`-in`** (checks if a value exists within a list of values). The case-sensitive variants (`-ceq`, `-clike`, etc.) enforce case sensitivity. **`-contains`** checks if the *entire item* is present in the collection; **`-in`** checks if the *value* matches any element in the collection.

**PS11** — A **module** is a container for cmdlets, functions, variables, and other resources. A **script module (`.psm1`)** is a script file that defines the module's content. A **manifest module (`.psd1`)** is a metadata file that describes the module (version, dependencies, required PowerShell version). A **binary module** contains compiled code. `Import-Module` loads the module's definitions into the current session's scope, making its contents available.

**PS12** — **String interpolation** allows embedding variables or expressions directly into a string using double quotes (`"`). The difference is that double quotes allow expansion, while single quotes (`'...'`) treat everything literally. Expressions are included by placing them inside curly braces: `"The value is $($variable * 2)"`. A **here-string (`@"`...`"@`)** allows multi-line strings that support interpolation, similar to template literals in JS.

**PS13** — **`Get-Member`** returns a list of properties and methods available on an object. **Properties** are data fields (e.g., `Name`). **Methods** are executable functions associated with the object (e.g., `.ToString()`). **NoteProperties** are properties that are not standard members but are attached via attributes. **`Select-Object`** is used to *select* and *shape* the output (choosing which properties to display). **`Where-Object`** is used to *filter* the input objects based on a condition.

**PS14** — PowerShell classes (v5+) are object-oriented constructs that allow defining custom types. They are heavily inspired by C# but are not a direct implementation of C# classes. Limitations include less strict enforcement of interfaces compared to C#, and constructor logic can be more complex. You use a **class** when you need to model a complex entity with state and behavior (e.g., a `User` object). You use a **function** when you need a reusable piece of logic that operates on input data without maintaining persistent state.

**PS15** — **`CmdletBinding()`** is an attribute that transforms a standard function into an Advanced Function, giving it built-in features like parameter validation, common parameters (`-Verbose`, `-ErrorAction`), and pipeline support. **`SupportsShouldProcess`** enables the `-WhatIf` parameter. **`DefaultParameterSetName`** specifies which parameter set is used if none is explicitly chosen. **`ValueFromPipeline`** allows the function to accept input objects via the pipeline. **Begin/Process/End blocks** define lifecycle stages: `Begin` runs once before processing starts; `Process` runs for each incoming object; `End` runs once after all objects are processed.

**PS16** — **Providers** are mechanisms that allow PowerShell cmdlets (like `Get-ChildItem`) to interact with various data sources using a unified interface. The `FileSystem` provider interacts with local drives. The `Registry` provider allows you to treat registry keys like directories (e.g., `Get-ChildItem HKCU:\Software`). The `Certificate` provider accesses certificate stores. This abstraction allows `Get-ChildItem` to work seamlessly across disparate systems.

**PS17** — **Runspaces** are isolated environments where PowerShell code executes. A **`[runspace]`** is a single execution context. A **`[runspacepool]`** manages a collection of runspaces, allowing for efficient reuse and parallel execution. A **`[powershell]`** object is the wrapper used to interact with a runspace. **`ForEach-Object -Parallel` (v7+)** handles the runspace management internally, abstracting the complexity. Manual management involves creating a `RunspacePool`, creating runspaces from it, and explicitly managing the job lifecycle.

**PS18** — **PSScriptAnalyzer** is a static code analysis tool that checks PowerShell scripts against a set of predefined best practices and coding standards. **Rules** are specific checks (e.g., "Do not use global variables"). **Severity levels** (e.g., Error, Warning, Information) dictate how critical the violation is. **Custom rules** allow organizations to define their own standards. Rules can be suppressed using `#Requires -ErrorAction SilentlyContinue` or specific analyzer directives. It integrates into CI/CD by running as a pre-commit or build step, failing the build if critical rules are violated.

**PS19** — **`$using:` scope** is used when passing variables to background jobs or parallel loops; it serializes the variable's *value* into the job's context at the time of job creation. **`$args/-ArgumentList`** is used when explicitly passing arguments to a remote session or script block. Serialization limits (CLIXML depth) restrict the complexity of objects that can be passed across process boundaries (like remoting or jobs). Complex, deeply nested objects may fail serialization, requiring you to flatten the data structure before passing it.

**PS20** — **Desired State Configuration (DSC)** is a management framework that enables you to define the *desired state* of a system (e.g., "IIS must be installed and running") rather than writing procedural steps to achieve it. **Configurations** define the desired state. **Resources** are the specific components that enforce that state (e.g., the `WindowsFeature` resource). The **Local Configuration Manager (LCM)** is the engine on the target node that pulls the configuration and ensures the resources match the desired state. In modern IaC, DSC is often superseded or complemented by tools like Ansible, Chef, or Terraform, which offer broader orchestration capabilities.
