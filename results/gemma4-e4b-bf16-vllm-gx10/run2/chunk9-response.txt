## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:**
The pods are failing because the Kubernetes cluster upgrade enforced the **Restricted Pod Security Standard (PSS)** at the namespace level, which is stricter than the previous **Baseline** standard.
1.  **SecurityContext Interaction:** The pods specify `securityContext.runAsNonRoot: true`. This mandates that the process inside the container must run as a non-root user (UID $\neq 0$).
2.  **Image Directive Conflict:** The new base image (`cgr.dev/chainguard/static:latest`) defaults its `USER` directive in the Dockerfile to `root` (UID 0).
3.  **Failure Mechanism:** When the pod starts, the Kubelet checks the Pod Security Policy (or PSS admission controller). It sees the pod requires non-root execution (`runAsNonRoot: true`), but the container image is configured to run as root (`USER root`). The admission controller rejects the pod creation or causes the container runtime to fail the startup, resulting in the pod entering `CrashLoopBackOff`.
4.  **Change from Baseline to Restricted:** The Baseline profile allows running as root if explicitly configured, but the Restricted profile strictly forbids running as root unless specific, highly restrictive exceptions are met, effectively enforcing the `runAsNonRoot` requirement against the image's default behavior.

**SC1-B:**
```bash
kubectl get pods --all-namespaces -o json | \
jq -r '.items[] | select(.status.phase == "Pending" or .status.phase == "Running" and (.status.containerStatuses[]?.state?.waiting?.reason == "CrashLoopBackOff")) | 
  "Namespace: \(.metadata.namespace)\nPod: \(.metadata.name)\nSecurityContext: \(.spec.containers[0].securityContext)"'
```
*(Note: The `jq` command assumes the CrashLoopBackOff status is reflected in the container status, which is the most reliable way to query this via JSON output.)*

**SC1-C:**
**Immediate Outage Fix:**
1.  **Image-Level Fix:** Rebuild the affected microservices, explicitly setting the `USER` directive in the Dockerfile to a non-root user (e.g., `USER 1000`) that matches the UID expected by the security context, or ensure the base image is configured to default to a non-root user.
2.  **Manifest Change:** In the Kubernetes deployment manifests, explicitly define `securityContext.runAsUser` to a specific, non-root UID (e.g., `runAsUser: 1000`) to override any potentially ambiguous defaults, ensuring compliance with the Restricted PSS.
3.  **CI Pipeline Gate:** Implement a static analysis step (e.g., using Trivy or Hadolint) in the CI pipeline that scans the Dockerfile. This gate must fail the build if: a) the `USER` instruction is set to `root`, or b) the image does not explicitly define a non-root user that satisfies the required `runAsNonRoot: true` policy.

**Zero-Downtime Rollout:**
Use a rolling update strategy via `kubectl rollout restart deployment/<service-name>` or by updating the image tag in the deployment manifest. Kubernetes will gradually replace old pods with new, compliant pods, ensuring that the service remains available throughout the transition, provided the new pods pass readiness checks.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:**
**Stale Data Issue:** The stale data occurs because the promotion of the read replica to primary was likely **asynchronous**. PostgreSQL streaming replication sends Write-Ahead Log (WAL) records from the primary to the replica. If the primary fails before the replica has received and applied the latest WAL records, those transactions are lost. When the replica is promoted, it becomes the new primary, but it lacks the most recent committed transactions from the old primary, leading to data inconsistency.
**Replication Lag Implication:** High replication lag means the replica is significantly behind the primary. Promoting it means accepting the data state *at the moment of promotion*, which is inherently stale relative to the last successful write on the original primary.
**WAL Shipping:** PostgreSQL ships WAL segments over the network. In cross-region setups, this relies on network latency and bandwidth. If the network connection degrades or the primary crashes before flushing the WAL to the replica, the data is lost.
**Data Loss Scenarios:** Data loss occurs if the primary crashes before the WAL segment containing the latest committed transaction has been successfully received and flushed to the replica's disk.
**Quantifying Data Loss:** Check the `pg_stat_replication` view on the *old* primary (if accessible) or check the WAL position difference between the promoted replica and the last known good state on the old primary. Specifically, check the `flush_lsn` vs. `write_lsn` on the replica just before promotion.

**SC2-B:**
The goal is to transition the promoted replica into the stateful management of Terraform without destroying the existing infrastructure.

1.  **Importing the Replica:** Since the promoted replica is now a standalone instance, you must import it into the state file, treating it as a new, managed resource.
    ```bash
    # Assuming the promoted replica's ARN is known and it's the target resource type
    terraform import aws_db_instance.new_primary <ARN_of_promoted_replica>
    ```
2.  **Updating Dependent Resources:** After the import, you must update the configuration blocks in your Terraform code (`.tf` files) to reference the newly imported resource ID/ARN.
3.  **Detaching the Old Instance:** Once the new primary is stable and all applications are pointing to it, you can safely destroy the old, failed primary instance.
    ```bash
    terraform destroy -target=aws_db_instance.old_primary
    ```
4.  **Updating References:** Manually update all dependent resources (Security Groups, Route53 records, Parameter Groups) in the Terraform code to point to the new primary's identifiers, then run `terraform apply`.

**SC2-C:**
**Architecture Design:**
*   **Connection Management:** Use **RDS Proxy** in the primary region (us-east-1) and configure the application to point to the proxy endpoint. For the DR region (eu-west-1), use PgBouncer *in front of* the promoted instance, but ensure the application logic is aware of the failover. RDS Proxy handles connection pooling and failover transparently for the application layer, which is superior to PgBouncer in a cloud-managed failover scenario.
*   **DNS Failover:** Implement **Route53 Health Checks** targeting the application endpoints in both regions. Configure a weighted or failover routing policy. If the US endpoint fails health checks, traffic automatically shifts to the EU endpoint.
*   **Application Logic:** Implement **client-side retry logic** with exponential backoff and jitter in the application code. This handles transient network issues or brief connection pool exhaustion during the switchover.
*   **RPO < 1 Second:** To achieve this, you must use **Synchronous Replication** or a service designed for near-zero RPO.
*   **Aurora Global Database vs. RDS:** **Aurora Global Database** is strongly recommended. It is specifically designed for cross-region, low-latency disaster recovery, offering near-instantaneous failover and significantly lower RPO/RTO compared to standard RDS cross-region read replicas, as it manages the replication stream more aggressively and reliably.

## SC3 — Medium — Container Image Supply Chain Compromise

**SC3-A:**
**Immediate Incident Response Steps:**
1.  **Containment:** Isolate the affected pods immediately to prevent further malicious activity or data exfiltration. Do **not** delete them.
    *   *Kubernetes Command:* Use `kubectl cordon` on the nodes hosting the pods, and then `kubectl scale deployment/<service> --replicas=0` (if possible without causing immediate service failure, otherwise proceed to forensic capture).
2.  **Forensic Evidence Capture (Before Killing):**
    *   **Process Tree:** `kubectl exec -it <pod-name> -- ps auxww` (Capture the full process tree).
    *   **Network Connections:** `kubectl exec -it <pod-name> -- netstat -tulnp` or `ss -tulnp` (Capture active connections).
    *   **Filesystem Diff:** Use a tool like `tar` or `rsync` to copy the entire container filesystem from the running container to a host volume for later analysis: `kubectl cp <pod-name>:/ <host-directory>`.
3.  **Post-Capture Action:** Once evidence is secured, terminate the pods (`kubectl delete pod <pod-name>`) and redeploy from a known-good image.

**SC3-C:**
**Hardened CI/CD Pipeline Architecture:**
1.  **Base Image Pinning:** Never use mutable tags (`:latest`, `:20-slim`). Always pin base images by their immutable **digest** (e.g., `node@sha256:xyz...`).
2.  **Image Signing (Cosign/Sigstore):** After a successful build, the image must be cryptographically signed using Cosign. The signature is stored alongside the image in the registry.
3.  **SBOM Generation:** Generate a Software Bill of Materials (SBOM) using tools like Syft during the build phase. This SBOM lists every dependency and its exact version/digest.
4.  **Admission Control Enforcement:** Deploy an admission controller (e.g., **Kyverno** or **OPA Gatekeeper**) in the cluster. This controller is configured to:
    *   **Verify Signature:** Reject any pod deployment whose image does not possess a valid signature from the trusted signing key.
    *   **Verify SBOM:** Optionally, check the deployed image's manifest against the expected SBOM to ensure no unauthorized layers were added post-build.
5.  **Notary v2:** Notary v2 (or its modern implementation via Sigstore) provides the framework for content trust. It ensures that the *identity* of the image creator and the *integrity* of the image have been verified before deployment, preventing tampering between the build server and the cluster.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
| Blocker | Problem in K8s | Proposed Solution |
| :--- | :--- | :--- |
| **Local Session State** | Kubernetes is ephemeral; pods are rescheduled, losing in-memory sessions. | Externalize state to a distributed, highly available store like Redis Cluster or Hazelcast, accessible by all pods. |
| **Local NFS Mount (/data/uploads)** | Standard K8s volumes are often ephemeral or tied to a single node unless using specific CSI drivers. | Migrate to a cloud-native, highly available, shared file storage solution (e.g., AWS EFS, Azure Files, or a dedicated NFS CSI driver). |
| **On-Prem Oracle 19c DB** | Requires complex networking, driver management, and stateful persistence outside the K8s control plane. | Use a dedicated StatefulSet with a robust CSI driver for persistent storage, or, preferably, migrate the database to a managed cloud service (RDS/Cloud SQL) and use a service endpoint. |
| **IBM MQ Integration** | MQ clients are often tightly coupled to specific host IPs and require complex network configuration (VPN/Firewall rules) that don't map well to ephemeral Pod IPs. | Introduce an abstraction layer (e.g., a dedicated MQ Gateway microservice running in K8s) that handles the MQ connection, decoupling the monolith from the MQ client libraries. |
| **Sticky Sessions (F5)** | Kubernetes load balancing (Service/Ingress) is generally stateless by default. | Externalize session state (as above) or use an Ingress controller that supports session affinity based on cookies/headers, though externalizing state is the superior long-term fix. |

**SC4-B:**

**ReadWriteMany Necessity:** `ReadWriteMany` (RWX) is necessary because the monolith application, when scaled horizontally (multiple pods), needs to write to the same shared file system (`/data/uploads`) concurrently from any pod instance. `ReadWriteOnce` (RWO) only allows a single node/pod to mount and write to the volume at a time, which breaks horizontal scaling.

**SC4-C:**
**Phased Migration Plan (Strangler Fig Pattern):**

*   **Phase 1: Data & State Decoupling (Shadowing/Read-Only):**
    *   **Move:** Externalize session state (to Redis) and file uploads (to EFS/S3). The monolith continues to run on bare metal but now reads/writes to the new external services.
    *   **Cutover:** No traffic change. This phase validates the new state management layer.
    *   **Rollback:** Revert application configuration to use local memory/NFS.
    *   **Go/No-Go:** Successful read/write operations to external services without performance degradation.
*   **Phase 2: Service Extraction (Strangling the Edge):**
    *   **Move:** Extract the least coupled functionality (e.g., user profile lookup, static content serving) into new microservices running in Kubernetes.
    *   **Cutover:** Use the F5 BIG-IP to route a small percentage (e.g., 5%) of traffic for the extracted functionality to the new Kubernetes Ingress. The monolith handles the rest.
    *   **Rollback:** Revert the F5 routing rule to send 100% of traffic back to the monolith.
    *   **Go/No-Go:** Latency and error rates for the extracted functionality remain within 10% of the legacy system's baseline.
*   **Phase 3: Core Migration & Decommissioning:**
    *   **Move:** Migrate the core business logic (e.g., order processing) into K8s services. The IBM MQ integration is replaced by the MQ Gateway microservice.
    *   **Cutover:** Gradually shift 100% of traffic via the Ingress/Service Mesh from the F5 to the K8s Ingress.
    *   **Rollback:** If critical errors occur, revert the Ingress routing to point 100% back to the legacy F5/Monolith.
    *   **Go/No-Go:** Sustained P99 latency below 2 seconds for 48 hours under peak load, and zero critical errors reported.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A:**
**Systematic Debugging Approach:**
1.  **Metrics Examination (Grafana/Prometheus):**
    *   **Istio/Envoy:** Check `istio_request_duration_milliseconds` for the `checkout-service` $\rightarrow$ `inventory-service` route. Look specifically at the 99th percentile latency histogram buckets.
    *   **Sidecar Proxy:** Examine Envoy metrics for connection pool saturation, request queue depth (`outbound_rq_queue_depth`), and upstream connection failures. High queue depth suggests the sidecar is waiting for the upstream service to accept connections.
    *   **Application:** Check CPU/Memory usage *within* the `inventory-service` pod during the spike.
2.  **Distributed Tracing (Jaeger/Zipkin):**
    *   Trace a request that experiences the 3.5s latency. The trace waterfall will visually show where the time is spent.
    *   If the time is spent *inside* the `inventory-service` span, the issue is application logic/database.
    *   If the time is spent *between* the spans (in the network/proxy overhead), the issue is the sidecar or network path.
3.  **Specific Envoy Metrics:** To distinguish proxy queueing from upstream latency:
    *   **Proxy Queueing:** High values for `envoy_cluster_upstream_rq_queue_depth` indicate the sidecar is buffering requests because the upstream service is too slow to accept them.
    *   **Upstream Latency:** High values for `envoy_cluster_upstream_rq_time_total` (time spent waiting for the upstream service to respond) indicate the service itself is slow.

**SC5-B:**
**SQL Diagnostic Query (PostgreSQL):**

**SC5-C:**
**Architectural Solution:**
1.  **CQRS (Command Query Responsibility Segregation):** Separate the write path (inventory updates, reconciliation) from the read path (checkout queries). The reconciliation job writes to a dedicated, highly optimized write database, while the checkout service reads from a denormalized, eventually consistent read replica optimized for fast lookups.
2.  **Read Replica for Reconciliation:** Run the heavy reconciliation CronJob against the dedicated read replica, ensuring it does not contend for locks or resources on the primary transactional database used by the checkout service.
3.  **Bulkhead Isolation:** Implement connection pool isolation. The checkout service should use one connection pool dedicated to serving user requests, and the reconciliation job (if it must run on the primary) should use a completely separate, smaller pool, preventing resource exhaustion in the serving path.
4.  **CronJob Scheduling:** Reschedule the reconciliation job to run during off-peak hours (e.g., 03:00 UTC) or use a staggered, incremental update approach instead of a single massive batch job.
5.  **Resource Governance:**
    *   **PodDisruptionBudgets (PDBs):** Define PDBs for the serving pods (`checkout-service`) to ensure that during voluntary disruptions (like node maintenance), a minimum number of replicas remain available.
    *   **Resource Quotas:** Apply strict `ResourceQuota` limits to the namespace hosting the CronJob. This prevents the reconciliation job from consuming excessive CPU/Memory, thereby starving the serving pods.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:**
**Identity and Access Layer Design:**
The core principle is to move from network-based trust (IPs) to **cryptographically verifiable workload identity**.

1.  **Workload Identity (SPIFFE/SPIRE):**
    *   **SPIFFE (Secure Production Identity Framework for Everyone):** Defines a standard for workload identity (SVIDs).
    *   **SPIRE:** Acts as the Certificate Authority (CA) and agent. SPIRE agents run on every host (VMware, AWS EC2, Azure VM). They attest to the workload's environment (e.g., "This pod is running in AWS Account X, on Node Y") and issue a short-lived X.509 certificate (SVID) to the workload.
2.  **Environment Integration:**
    *   **AWS:** SPIRE agents attest to the EC2 instance metadata, which can be linked to the associated IAM Role. The SVID is issued based on this verified role.
    *   **Azure:** SPIRE agents attest to the Managed Identity assigned to the VM/Pod.
    *   **On-Prem (VMware):** SPIRE agents attest to the hypervisor/VM metadata or use integration with the on-prem PKI to verify host identity.
3.  **Federation:** The SVIDs are the universal identity. When a workload in AWS needs to talk to a service on-prem:
    *   The AWS workload presents its SVID to the on-prem service endpoint.
    *   The on-prem service (which is also running a SPIRE agent/verifier) validates the SVID against the central SPIRE server's trust bundle.
    *   If valid, the service trusts the identity, not the source IP. This requires mutual TLS (mTLS) enforced by a service mesh (like Istio/Linkerd) that uses the SVIDs for authentication.

**SC6-C:**
| Option | Cost | Bandwidth | Encryption | Failover | Zero-Trust Fit | Routing Change |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Direct Connect** | High (Port/Data Transfer) | High (Dedicated) | Managed by AWS/Customer | Manual/DNS | Excellent (Dedicated path) | Static routing via BGP to TGW. |

*   **ECMP VPN:** Requires configuring multiple VPN connections to the TGW and ensuring the routing tables are configured to use ECMP paths for redundancy.
*   **Tailscale/Netbird:** Requires installing the client on every host/VM and joining the unified mesh network. Routing is handled automatically by the overlay network, bypassing traditional VPC/VPN routing tables for service-to-service communication.

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:**
**Drift Source Analysis:**
1.  **Manual `tofu apply` from Laptops:** This bypasses the centralized, audited pipeline. The developer's local state file (if they used one) or the state they manually updated is not synchronized with the central S3 state, leading to the pipeline's view of reality being outdated.
2.  **Diverged Helm Values:** When values files are edited manually outside Git, the Git repository no longer reflects the *actual* state of the cluster. Subsequent pipeline runs will attempt to reconcile the cluster state back to the Git definition, potentially causing unexpected changes or failing if the manual change was necessary.
3.  **Direct `kubectl edit`:** This is the most dangerous. It modifies the live cluster state directly, bypassing *all* IaC tooling (OpenTofu/Helm). The IaC tool believes the resource is in state X, but the cluster is in state Y.

**State Locking Danger:**
If two engineers run `tofu apply` simultaneously without state locking, both processes read the same state file, calculate their changes based on that old state, and then attempt to write their changes back. The second process to write will **overwrite and discard** the changes made by the first process, leading to silent data loss or configuration rollback.

## SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:**
**Symptom Diagnosis:**
1.  **Prometheus OOM-Killed:** **Root Cause:** High Cardinality. Prometheus stores metrics as time series, and each unique combination of metric name + label set is a unique time series. 8.2 million active series is too much for a single node's memory, especially if labels are highly granular (e.g., `user_id`, `request_id`).
    *   **Confirmation:** Check `prometheus_tsdb_head_series` metric. Identify the top offending metrics by querying the API for series counts per metric name.
2.  **Loki Ingester Drops:** **Root Cause:** Ingestion Rate Exceeds Processing Capacity. The volume of logs (events/second) is overwhelming the ingester pods' ability to process, index, and forward them to storage.
    *   **Confirmation:** Check Loki metrics for `ingester_dropped_logs_total`.
3.  **Tempo Timeouts:** **Root Cause:** Backend Storage Latency/Capacity. Tempo relies on the backend (S3 in this case) for trace storage. If the S3 bucket is slow, or if the compaction process is lagging, queries waiting for data retrieval will time out.
    *   **Confirmation:** Check Tempo query latency metrics and S3 API call latency metrics.
4.  **Thanos Compactor Lag:** **Root Cause:** I/O Bottleneck or Insufficient Resources. Compaction is an intensive disk/CPU operation. If the underlying storage (or the Thanos sidecar's resources) cannot keep up with the incoming data rate (500GB/week), it falls behind.
    *   **Confirmation:** Check Thanos component metrics for `compaction_duration_seconds` and the lag between the latest ingested block and the latest compacted block.

**SC9-C:**
**Defense-in-Depth Architecture:**
1.  **Authentication Migration:**
    *   **API Gateway:** Place an API Gateway (e.g., Kong, AWS API Gateway) in front of the ALB. This gateway handles the initial request validation.
    *   **Key Rotation:** Immediately revoke all existing API keys.
    *   **OAuth2 Implementation:** Migrate consumers to use OAuth2. The API Gateway is configured to validate JWTs issued by an Identity Provider (IdP). The JWT payload contains user/client identity claims, replacing the need for static API keys.
2.  **Centralized Control:** The API Gateway enforces rate limiting, schema validation, and authentication *before* the request ever hits the ALB or the Django application, drastically reducing the attack surface.
3.  **Auditing:** Enable **CloudTrail Data Events** for the underlying database (if applicable) and ensure the API Gateway logs all authentication attempts and access patterns to CloudWatch for compliance auditing.
4.  **Data Protection:** Implement **Field-Level Encryption (FLE)** for PII fields (e.g., `internal_notes`) in the database. The application layer must handle the encryption/decryption using keys managed by a KMS, ensuring that even if the database is breached, the PII is unreadable without the application's key.

**Migration Strategy (API Keys to OAuth2):**
Implement a **dual-mode compatibility layer** in the API Gateway. For a transition period:
*   If the request contains an old API Key in the header/query, the Gateway validates it against a legacy key store and issues a short-lived, internal JWT token.
*   If the request contains a valid JWT, it proceeds normally.
This allows existing consumers to continue working while new consumers are onboarded to the OAuth2 flow.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
**Multi-Cluster Architecture Comparison:**

| Feature | Active-Passive (Velero) | Active-Active (Service Mesh) |
| :--- | :--- | :--- |
| **RPO/RTO Feasibility** | **RPO:** Dependent on backup frequency (e.g., 15 min). **RTO:** Dependent on restore time (can be slow for 200TB). | **RPO:** Near Zero (Continuous replication). **RTO:** Near Zero (Traffic shift). |
| **Latency Impact (12ms)** | Minimal impact on backup/restore process itself, but recovery time is the bottleneck. | Manageable. Service mesh handles routing across the latency boundary. |
| **200TB MinIO** | Requires a massive, asynchronous backup/restore operation, likely exceeding the 1-hour RTO. | Requires continuous, synchronous/asynchronous cross-site replication setup for MinIO. |
| **Stateful Component Replication** | PostgreSQL: Patroni/Streaming. Redis: Sentinel/Replication. RabbitMQ: Mirroring. MinIO: Replication. | PostgreSQL: Synchronous/Asynchronous Streaming. Redis: Cluster Mode. RabbitMQ: Federation. MinIO: Cross-Region Replication. |

**Conclusion:** To meet the strict RPO (15 min) and RTO (1 hr) requirements, **Active-Active with a Service Mesh** is the superior design, as it minimizes recovery time by eliminating the need for a full restore.

**Replication Strategy:**
*   **PostgreSQL:** Patroni configured for **Synchronous Replication** across sites (if latency allows, or near-synchronous with quorum management) to ensure zero data loss on failover.
*   **Redis:** Use **Redis Cluster Mode** with cross-datacenter replication enabled, or use Sentinel with a highly available quorum spanning both sites.
*   **RabbitMQ:** Configure **Queue Mirroring** across the clusters, ensuring messages are mirrored to the DR site before acknowledgment.
*   **MinIO:** Configure **Cross-Region Replication (CRR)** on the MinIO buckets, ensuring data is continuously copied to the Dallas site.

**SC10-C:**
**Automated Failover Orchestration Sequence:**

1.  **Failure Detection:**
    *   **Monitoring:** A dedicated external monitoring system (e.g., Prometheus/Alertmanager, or a dedicated health check service) monitors the primary site's health.
    *   **Site Down Definition:** "Site Down" is defined as the failure of the primary Patroni cluster to respond to health checks *and* the failure of the GSLB/DNS health checks to resolve the primary endpoint for a sustained period (e.g., 5 minutes).
2.  **Patroni Promotion:** The monitoring system triggers the failover mechanism (often via an API call to Patroni or by waiting for Patroni's internal quorum loss detection). Patroni in Dallas detects the loss of the Chicago primary and automatically promotes the Dallas replica to primary.
3.  **Stateful Component Failover:**
    *   **Redis:** Sentinel detects the primary failure and promotes the designated replica in Dallas.
    *   **RabbitMQ:** The cluster manager detects the primary site loss and initiates queue mirroring/federation to ensure consumers connect to the active Dallas cluster.
    *   **MinIO:** The CRR mechanism ensures the Dallas bucket is up-to-date. The application configuration must be updated to point to the Dallas endpoint.
4.  **DNS Failover (GSLB):** The GSLB (e.g., AWS Route 53 Failover Routing) detects the primary endpoint failure and automatically shifts all traffic resolution to the Dallas endpoint.
5.  **OpenTofu State Update:** **This is the most complex step.** The failover orchestration must trigger a script that runs `terraform import` or updates the configuration to reflect the new primary's ARN/endpoint, followed by a `terraform apply` to update dependent infrastructure (e.g., load balancer targets, DNS records) to point to Dallas.

**Split-Brain Handling:**
Split-brain (both sites believing they are primary) is prevented by **Patroni's Distributed Configuration Store (DCS - etcd)**. Patroni requires a quorum (majority) of the DCS nodes to elect a primary. If the Chicago site loses quorum (e.g., network partition isolates it), it cannot elect or maintain primary status, forcing it into a standby/read-only mode, thus preventing simultaneous writes.

**Failback Procedure:**
1.  **Chicago Recovery:** Once Chicago is stable, it is brought back online as a *new standby* replica, pointing to the current Dallas primary.
2.  **Data Sync:** Allow Chicago to fully catch up via streaming replication.
3.  **Planned Switchover:** Schedule a maintenance window. Initiate a controlled, planned switchover (not a failover). The Dallas primary initiates a graceful handover to Chicago, which is promoted to primary.
4.  **DNS Update:** Update GSLB to point traffic back to Chicago.
5.  **Terraform Update:** Update the IaC state to reflect Chicago as the new primary.
