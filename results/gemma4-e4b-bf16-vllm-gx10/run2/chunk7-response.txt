## Application Architecture Answers

**AA1**
A **monolith** is a single, tightly coupled, indivisible unit where all business logic (UI, business services, data access) resides in one codebase and is deployed as one artifact. **Microservices** decompose an application into a collection of small, independent, loosely coupled services, each running its own process and communicating via lightweight mechanisms.

Three concrete problems microservices introduce that monoliths don't have:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication failures.
2. **Operational Overhead:** Increased complexity in deployment, monitoring, logging, and tracing across dozens or hundreds of services.
3. **Data Consistency:** Managing transactions across multiple independent databases (distributed transactions).

**AA2**
**Synchronous communication** requires the calling service to wait for an immediate response from the called service before continuing its own execution. *Example Technology: REST/HTTP (e.g., using `fetch` or `HttpClient`).*
**Asynchronous communication** allows the calling service to send a message/event and immediately continue processing without waiting for a response. The recipient processes the message when it is available. *Example Technology: Kafka or RabbitMQ.*

**AA3**
An **API Gateway** acts as a single entry point for all clients, handling cross-cutting concerns like authentication, rate limiting, request routing, and protocol translation before forwarding requests to the appropriate backend microservice. A **Reverse Proxy** sits in front of one or more servers, primarily to forward client requests to the correct internal server, often handling SSL termination and basic load balancing.

An API Gateway *can* replace a reverse proxy entirely, but it is usually more than that. A reverse proxy's core function (routing traffic to internal services) is a subset of the API Gateway's functionality. The API Gateway adds crucial business logic layers (security policies, throttling, aggregation) that a basic reverse proxy lacks.

**AA4**
The **Saga pattern** is a sequence of local transactions where each transaction updates the database within a single service and publishes an event to trigger the next step in the sequence. If any local transaction fails, the Saga executes compensating transactions to undo the preceding changes, maintaining data consistency across the distributed system.

*   **Choreography-based Sagas:** Services communicate by producing and consuming events without a central coordinator. Each service knows what to do based on the events it receives. *Appropriate when:* the workflow is simple, decentralized, and services are highly autonomous.
*   **Orchestration-based Sagas:** A dedicated service (the Orchestrator) manages the workflow, telling each participant service what local transaction to execute via commands. *Appropriate when:* the workflow is complex, long-running, or requires centralized visibility and control over the entire process.

**AA5**
**CQRS (Command Query Responsibility Segregation)** separates the model used for updating data (Commands) from the model used for reading data (Queries). Commands change state; Queries retrieve state.

It is often paired with **Event Sourcing (ES)** because ES stores the state of an entity not as its current snapshot, but as a sequence of immutable domain events. The read model (Query side) is then built by projecting these events into a highly optimized, denormalized structure (e.g., a specific SQL table or document store).

This combination solves the problem of **read/write scaling mismatch** inherent in traditional CRUD. In CRUD, the same database structure must efficiently handle complex writes (updates) and complex reads (reporting/UI views). CQRS/ES allows you to optimize the write model for transactional integrity and the read model for query performance independently.

**AA6**
The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a remote service that is down or overloaded). It monitors calls; if failures exceed a threshold, it "trips" the circuit, immediately failing subsequent calls without attempting the network request, allowing the failing service time to recover.

The three states are:
1. **Closed:** Normal operation. Requests pass through. Failures are counted.
2. **Open:** The circuit is tripped. All requests fail immediately (fast-fail) without hitting the downstream service. After a timeout, it moves to Half-Open.
3. **Half-Open:** A limited number of test requests are allowed through. If they succeed, the circuit closes; if they fail, it returns to Open.

It differs from a simple retry with backoff because **retries** assume the failure is transient and try again, potentially hammering an already struggling service. The **Circuit Breaker** assumes the failure is systemic and *stops* the traffic entirely to give the service breathing room. They are used together: the Circuit Breaker prevents cascading failures, and within the Closed state, retries with backoff can handle minor, transient network hiccups.

**AA7**
| Model | Cost | Security | Operational Complexity | Noisy-Neighbor Risk |
| :--- | :--- | :--- | :--- | :--- |
| **1. Shared DB, Shared Schema** | Lowest | Lowest (Requires strict application-level enforcement) | Lowest | Highest (One bad query affects all tenants) |
| **2. Shared DB, Separate Schema** | Low | Medium (Database permissions isolate tenants) | Medium (Schema management overhead) | Medium (Resource contention within the DB instance) |
| **3. Separate DB per Tenant** | Highest | Highest (Strongest isolation boundary) | Highest (Managing N databases) | Lowest (Resource isolation at the DB level) |

**Trade-offs Summary:**
*   **Cost:** Model 1 $\ll$ Model 2 $<$ Model 3.
*   **Security:** Model 3 $>$ Model 2 $>$ Model 1.
*   **Operational Complexity:** Model 1 $\ll$ Model 2 $<$ Model 3.
*   **Noisy-Neighbor Risk:** Model 3 $\ll$ Model 2 $<$ Model 1.

**AA8**
**Strong Consistency** guarantees that once a write operation is acknowledged, all subsequent read operations, regardless of which replica they hit, will immediately see that written value. **Eventual Consistency** guarantees that if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value, but there is a window where reads might return stale data.

To prevent overselling inventory (a critical business invariant), **Strong Consistency** is required for the inventory decrement operation.
*   **Consistency Model:** Strong Consistency (or Linearizability).
*   **Data Store:** A strongly consistent, transactional database (e.g., PostgreSQL with strong ACID guarantees, CockroachDB, or a distributed ledger).
*   **Patterns:** Use pessimistic locking or atomic database transactions during the checkout/inventory update process. For high scale, use a consensus algorithm (like Raft or Paxos) managed by the data store itself to ensure all replicas agree on the state before confirming the sale.

**AA9**
A **sidecar proxy** is a secondary container deployed alongside the main application container within the same Kubernetes Pod. It intercepts all inbound and outbound network traffic for the application container.

In an **Istio deployment**, Envoy is the proxy deployed as the sidecar. It handles all service-to-service communication. The **Data Plane** consists of these Envoy proxies, which intercept and manage the actual network traffic (L4/L7). The **Control Plane** (e.g., Istiod) configures these proxies, pushing routing rules, security policies, and telemetry settings down to the data plane.

**mTLS (Mutual TLS)** between sidecars solves the problem that application-level TLS often only authenticates the *server* to the *client*. With mTLS enforced by the sidecar mesh, *both* the client service and the server service must present and validate cryptographic certificates issued by the mesh CA. This provides **mutual authentication** and ensures that only authorized services within the mesh can communicate, regardless of the underlying network segmentation.

**AA10**
The **Strangler Fig pattern** is an incremental migration strategy where a new system (the microservices) is built around a legacy system (the monolith). New functionality is built in the microservices, and traffic is gradually rerouted away from the monolith to the new services until the monolith can be safely "strangled" and retired.

**Migration Strategy (Monolith $\rightarrow$ Microservices):**
1.  **Identify Seams:** Identify a bounded context within the monolith that is relatively self-contained (e.g., User Profile Management).
2.  **Implement Facade/Routing:** Place an API Gateway in front of the monolith. Initially, all traffic routes to the monolith.
3.  **Extract Service:** Re-implement the User Profile functionality as a new, independent .NET 8 microservice.
4.  **Redirect Traffic:** Configure the API Gateway to route `/api/users/*` requests to the new microservice, while all other requests still go to the monolith.
5.  **Data Synchronization:** Implement a mechanism (e.g., Change Data Capture or event publishing from the monolith) to keep the new microservice's data store synchronized with the monolith's database during the transition.
6.  **Iterate:** Repeat the process for the next bounded context until the monolith is empty.

**AA11**
The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable, and resilient software-as-a-service applications.

Six factors and their importance:
1. **Codebase:** One codebase tracked in revision control, many deploys. (Ensures consistency across environments.)
2. **Dependencies:** Explicitly declare and isolate dependencies. (Ensures portability; avoids "it works on my machine.")
3. **Config:** Store configuration in the environment. (Decouples code from deployment environment, crucial for cloud elasticity.)
4. **Backing Services:** Treat backing services (databases, caches) as attached resources. (Allows swapping out a MySQL instance for a cloud-managed one without code changes.)
5. **Build, Release, Run:** Strictly separate these stages. (Allows for immutable artifacts and repeatable deployments.)
6. **Processes:** Execute the application as one or more stateless processes. (Essential for horizontal scaling; any instance can handle any request.)

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Temporal decoupling) | Tight (Synchronous dependency) |
| **Scalability** | Excellent (Consumers scale independently) | Good (Requires load balancing, but scaling is coupled to request volume) |
| **Debugging Complexity** | High (Tracing event flow across time/services is hard) | Lower (Direct request/response chain is easier to follow) |
| **Ordering Guarantees** | Guaranteed within a partition/topic. | Guaranteed by the request/response sequence. |
| **Failure Handling** | Built-in retry/replay mechanisms via broker retention. | Requires explicit client-side retry logic (e.g., Circuit Breaker). |

**When to Choose:**
*   **Event-Driven:** Choose when services need to react to state changes in other services, when high throughput/decoupling is paramount, or when you need to build complex workflows from disparate events (e.g., order fulfillment).
*   **Request-Driven:** Choose when an immediate response is required to complete a user interaction (e.g., login validation, fetching a specific user profile).

**AA13**
A **load balancer** is a device or software that distributes incoming network traffic across a group of backend servers (a server farm) to ensure no single server becomes a bottleneck, thereby maximizing throughput and availability.

*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It makes routing decisions based on IP addresses and port numbers. It is fast because it does not inspect the content of the packet.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (headers, URLs, cookies) to make routing decisions.

**Use Case for Layer 7:** Routing traffic based on the URL path (e.g., sending `/api/v1/users` to Service A and `/api/v2/products` to Service B, even if they share the same IP/port).

**AA14**
A **message queue** (e.g., RabbitMQ) is a system designed for point-to-point or publish/subscribe messaging where messages are consumed and *removed* from the queue once successfully processed by a consumer. It focuses on reliable delivery of discrete tasks.

A **log-based message broker** (e.g., Kafka) functions as a distributed, immutable commit log. Messages are appended to topics and are *retained* for a configurable period, allowing multiple consumers to read the same message stream at different times or speeds.

**When to Pick Which:**
*   **Message Queue:** Pick when you need guaranteed, single consumption of a task (e.g., processing a payment request once).
*   **Log-Based Broker:** Pick when you need stream processing, replayability, or when multiple independent services need to react to the same stream of events (e.g., tracking all user activity).

**AA15**
A **container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and settings. It shares the host operating system's kernel.

A **Virtual Machine (VM)** virtualizes the entire hardware stack, including the CPU, memory, disk, and network interfaces, running its own complete Guest OS on top of a hypervisor.

Containers are popular for microservices because they offer **high density** (many more containers than VMs on the same hardware) and **fast startup times** because they do not need to boot an entire operating system.

**AA16**
A **stateless service** is one that does not retain any session-specific data between client requests. Every request from the client must contain all the necessary information for the service to fulfill it.
A **stateful service** is one that retains data or session context between requests (e.g., user session data, in-memory caches).

Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance of the service without worrying about whether that specific instance holds the necessary session context.
*   **Stateless Example:** A REST API endpoint that processes a calculation based on input parameters.
*   **Stateful Example:** A Redis cache server or a traditional relational database instance.

**AA17**
An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using the paradigm of object-oriented programming (i.e., manipulating objects in code) rather than writing raw SQL strings.

*   **Popular ORMs:** Hibernate (Java), SQLAlchemy (Python).
*   **Trade-offs:**
    *   **ORM Pros:** Increased developer productivity, database portability (switching SQL dialects is easier), type safety.
    *   **ORM Cons:** Performance overhead (the ORM might generate inefficient SQL), the "impedance mismatch" (mapping complex object graphs to flat relational tables can be awkward), and abstraction can hide performance bottlenecks.

**AA18**
The **Bulkhead pattern** isolates components of an application so that the failure or resource exhaustion in one component does not cascade and bring down the entire system. It partitions resources (like thread pools or connection pools) into isolated compartments, much like watertight compartments in a ship.

It relates to resource isolation by ensuring that if Service A starts consuming all its allocated resources (e.g., all its threads waiting on a slow dependency), those resources are contained within Service A's bulkhead, leaving the resources allocated to Service B untouched and operational.

**Implementation Example:** If Service A calls Service B and Service C, you would implement separate, limited thread pools for the calls to B and C. If Service B becomes slow, it will only exhaust the threads in its dedicated pool, allowing the threads dedicated to calling Service C to remain available.

**AA19**
*   **Operational Transformation (OT):** A mathematical algorithm that transforms concurrent edits made to the same document into a consistent state. It requires a central server to manage the transformation logic and sequence of operations.
    *   *Consistency:* Strong (if managed correctly by the server).
    *   *Latency:* Moderate (requires constant server round-trips).
    *   *Complexity:* High (the transformation logic itself is mathematically complex).
    *   *Offline Support:* Poor (requires complex state merging upon reconnection).
*   **CRDTs (Conflict-free Replicated Data Types):** Data structures designed so that concurrent updates can be merged mathematically without requiring coordination or central authority. They are inherently commutative and associative.
    *   *Consistency:* Eventual (converges to the same state eventually).
    *   *Latency:* Low (updates can be applied locally immediately).
    *   *Complexity:* Medium (implementing the correct data structure is complex, but the merging logic is simpler than OT).
    *   *Offline Support:* Excellent (updates are stored locally and merged upon reconnection).

**Choice:** I would choose **CRDTs**. For a system that *must* support offline editing, the ability to apply changes locally and merge them deterministically later is non-negotiable. OT fundamentally relies on a central authority to order and transform operations correctly.

**AA20**
**Challenges in Polyglot Tracing:**
1.  **Context Propagation:** Ensuring that the unique trace ID and span ID are passed correctly across service boundaries, regardless of the language or communication protocol used.
2.  **Sampling:** Deciding which requests to trace. If you trace everything, storage costs explode.
3.  **Storage/Querying:** Storing high-volume trace data and providing an efficient way to reconstruct the entire request path.
4.  **Asynchronous Continuity:** Maintaining the trace context when the request flow is broken by a message broker.

**Solutions:**
*   **Context Propagation:** Use standardized headers like **W3C Trace Context** or B3 headers. The application code in *every* service must be instrumented to read these headers on ingress and inject them into outgoing requests/messages.
*   **Sampling:**
    *   **Head-based:** A decision (e.g., sample 1 in 100 requests) is made at the very first service entry point. Simple, but might miss critical errors that occur deep in the trace.
    *   **Tail-based:** All traces are collected, and a decision is made *after* the trace completes (e.g., sample all traces that resulted in a 5xx error). More accurate but requires significant buffering/storage.
*   **Storage/Querying:** Tools like **Jaeger** or **Tempo** are used to ingest, index, and visualize the trace data based on the propagated IDs.
*   **Asynchronous Continuity (Kafka):** When a service publishes an event to Kafka, the trace context (Trace ID, Parent Span ID) must be injected into the **message headers** of the Kafka record. The downstream consumer service must then read these headers upon consumption and use them to create a new child span linked to the original trace.

## On-Premise Infrastructure Architecture Answers

**OP1**
A **Type 1 (Bare-Metal) Hypervisor** runs directly on the host hardware, managing the hardware resources and allocating them to Guest VMs. It has minimal overhead. *Examples: VMware ESXi, Microsoft Hyper-V (when run directly on hardware).*
A **Type 2 (Hosted) Hypervisor** runs as an application *on top of* a conventional host operating system (like Windows or Linux). It relies on the host OS to manage hardware access. *Examples: VMware Workstation, Oracle VirtualBox.*

**OP2**
**SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. The server sees the storage as a raw, local disk volume. *Use Case: High-performance transactional databases.* *Protocols: Fibre Channel (FC), iSCSI.*
**NAS (Network Attached Storage):** A file-level storage device accessible over a standard network. The storage device itself manages the file system. *Use Case: File sharing, backups.* *Protocols: NFS, SMB/CIFS.*

**OP3**
**3-Tier Architecture:**
1.  **Access Layer:** Connects end-user devices (PCs, phones) to the network. Handles PoE, basic switching.
2.  **Distribution Layer:** Aggregates traffic from the Access layer. Provides policy enforcement, routing boundaries, and redundancy between access blocks.
3.  **Core Layer:** The high-speed backbone of the network. Its sole job is fast, reliable packet switching between distribution blocks.

**Leaf-Spine (Clos) Architecture:** This modern design replaces the hierarchical 3-tier model. It uses two layers: **Leaf** switches (connecting servers/endpoints) and **Spine** switches (forming the high-speed backbone). Every Leaf connects to every Spine.

**Problem Solved:** The 3-tier model creates bottlenecks at the Distribution layer and limits east-west traffic (server-to-server communication) speed. Leaf-Spine provides predictable, low-latency, non-blocking paths between any two endpoints, allowing for massive horizontal scaling of bandwidth.

**OP4**
**Architecture:**
*   **Node Count:** Minimum of 3 nodes for quorum.
*   **Quorum:** Achieved via Corosync/Pacemaker consensus mechanism. A majority (N/2 + 1) must agree on the cluster state.
*   **Fencing (STONITH):** Critical. Must implement fencing (e.g., IPMI/iDRAC commands) to ensure that if a node appears "alive" but is actually partitioned (split-brain), it can be forcibly powered off to prevent data corruption.
*   **Shared Storage Options:**
    *   **Ceph:** Distributed, software-defined storage. Excellent for scale-out and high availability across nodes.
    *   **iSCSI/NFS:** Traditional block/file sharing, requiring a dedicated storage array or server.
*   **Node Failure:** If a node fails, the remaining nodes maintain quorum. The cluster manager (Pacemaker) detects the failure, marks the node as down, and automatically migrates the virtual machines/services running on the failed node to the remaining healthy nodes, utilizing the shared storage.

**OP5**
**VLAN Trunking:** The process of allowing traffic from multiple VLANs to traverse a single physical link (trunk port) between two network devices (e.g., switch to switch, or switch to server).

**802.1Q Tagging:** This is the standard protocol used for trunking. It inserts a 4-byte tag into the Ethernet frame header. This tag contains a **VLAN ID (VID)**, which tells the receiving switch exactly which VLAN the frame belongs to, allowing the switch to correctly process the frame even though it traveled over a single physical wire.

**Linux Configuration:** This requires creating multiple network interfaces (or using VLAN sub-interfaces) on the single physical NIC.
1.  Create VLAN interfaces: `ip link add link eth0 name eth0.10 type vlan id 10` (for VLAN 10).
2.  Repeat for VLAN 20, 30, etc.
3.  Assign IP addresses and bring up each sub-interface: `ip addr add 192.168.10.5/24 dev eth0.10` and `ip link set eth0.10 up`.

**OP6**
*   **RAID 1 (Mirroring):** Duplicates data across two or more drives. High read performance, 50% capacity loss. Excellent fault tolerance (can lose N-1 drives).
*   **RAID 5 (Striping with Parity):** Stripes data across drives and distributes parity information. Can tolerate the failure of **one** drive. Good balance of performance and capacity.
*   **RAID 6 (Striping with Dual Parity):** Stripes data and distributes two independent parity blocks. Can tolerate the failure of **two** drives. Higher write penalty than RAID 5.
*   **RAID 10 (Mirroring + Striping):** Stripes data across mirrored sets. Offers the best combination of performance and fault tolerance, as it can survive multiple drive failures as long as they are not in the same mirrored pair.
*   **RAID Z2 (ZFS):** ZFS's implementation of RAID 6. Provides dual parity protection.

**Choice for Database Server (6 drives):** **RAID 10**. While RAID 6 offers better capacity utilization, RAID 10 provides superior **write performance** (crucial for databases) and faster rebuild times, which is critical when a drive fails. With 6 drives, RAID 10 (3 mirrored pairs) offers excellent redundancy and speed.

**OP7**
**DNS Architecture Design:**
1.  **Internal Resolvers (Recursive):** Placed inside the corporate network. These servers query external/authoritative DNS servers on behalf of internal clients. They are configured to forward internal queries to the internal AD DNS servers.
2.  **Internal Authoritative Servers:** These servers host the records for the internal domains (e.g., `corp.local`). They are authoritative for the internal zone.
3.  **DMZ Authoritative Servers:** These servers host the public-facing records (e.g., `company.com`). They are authoritative for the external zone.
4.  **Forwarders:** The internal resolvers are configured to forward external queries (e.g., `google.com`) to trusted external DNS providers (like 8.8.8.8).
5.  **Conditional Forwarding:** The internal resolvers are configured to forward queries for `corp.local` to the internal AD servers, while forwarding all other queries to the external forwarders.
6.  **Split-Horizon DNS:** The internal DNS servers serve different records based on the client's location/IP. Internal clients resolve to internal IPs; external clients resolve to public IPs.
7.  **DNSSEC:** Applied only to the **external zone** (`company.com`) to cryptographically sign records, ensuring data integrity for external users.

**Laptop Movement:** When a laptop moves from the office (internal IP) to the VPN (which routes traffic through the corporate network), the internal resolvers handle the query. Because the laptop is now on the internal network segment, the DNS server resolves the internal hostname to the correct internal IP address, maintaining seamless access.

**OP8**
**PKI Chain of Trust:**
1.  **Root CA (Offline):** The ultimate trust anchor. It is kept offline (air-gapped) and highly secured. It signs the subordinate CA certificate.
2.  **Subordinate/Issuing CA:** This CA is online and performs the day-to-day signing of end-entity certificates (e.g., for servers or users). It is trusted because it was signed by the Root CA.
3.  **End-Entity Certificate:** The certificate issued to the actual resource (e.g., `webserver.corp.com`). It is signed by the Subordinate CA.

**CRL vs OCSP:**
*   **CRL (Certificate Revocation List):** A list published periodically by the CA containing the serial numbers of all revoked certificates. Clients must download and check this list. (Can be slow/stale).
*   **OCSP (Online Certificate Status Protocol):** A real-time query service where a client asks the CA, "Is certificate X valid right now?" (Faster, more immediate).

**Certificate Templates & Auto-Enrollment:** Templates define the rules (key usage, validity period, subject fields) for different types of certificates. Auto-enrollment allows client machines to automatically request and receive certificates from the Issuing CA without manual intervention, usually via Group Policy Objects (GPO) in Active Directory.

**Consequences of Compromise:**
*   **Compromised Subordinate CA:** High impact. An attacker can issue fraudulent certificates for any service under that CA's scope. The damage is contained to the scope of that subordinate CA, and it can be revoked/replaced without touching the Root CA.
*   **Compromised Root CA:** Catastrophic. If the Root CA key is compromised, the entire trust chain is broken. Every certificate issued by every subordinate CA becomes untrustworthy, requiring a complete, organization-wide PKI rebuild.

**OP9**
| Feature | MPLS | IPsec VPN over Internet | SD-WAN | WireGuard Mesh |
| :--- | :--- | :--- | :--- | :--- |
| **Cost** | Very High (Carrier dependent) | Low to Medium (Internet + VPN hardware) | Medium (Optimized internet usage) | Very Low (Software-defined) |
| **Reliability** | Very High (Carrier SLA) | Medium (Dependent on ISP quality) | High (Intelligent path selection) | Medium to High (Peer-to-peer resilience) |
| **Latency** | Low (Guaranteed QoS) | Variable (Internet jitter) | Low (Optimizes paths) | Low (Simple, fast crypto) |
| **Management Complexity** | Low (Carrier managed) | Medium (Tunnel configuration) | Medium (Centralized controller) | Low (Simple peer configuration) |
| **Security Posture** | High (Private network) | High (Encrypted tunnels) | High (Encrypted tunnels + policy) | High (Modern, strong crypto) |

**Recommendation:** **SD-WAN**. For 50 users per site with latency-sensitive VoIP, SD-WAN provides the best balance. It leverages cheaper, high-bandwidth internet connections while intelligently steering VoIP traffic over the path with the lowest latency and jitter, offering better reliability and QoS than standard IPsec VPNs, all while being more cost-effective than MPLS.

**OP10**
**iDRAC/iLO/IPMI:** These are **Baseboard Management Controllers (BMC)**. They are dedicated, low-level hardware interfaces embedded on the server motherboard that allow administrators to manage the server hardware (power cycling, viewing sensor data, accessing the console) *independent* of the main operating system.

**Out-of-Band Management Criticality:** It is critical because if the OS crashes, the network stack fails, or the server is powered off, you lose all remote access. IPMI allows you to "wake up" the server, view the boot process, or reboot it even when the OS is completely unresponsive.

**Internet Exposure Risk:** If the IPMI interface is exposed to the internet, it becomes a massive, high-privilege attack vector. An attacker could gain root access to the BMC, allowing them to remotely power cycle, dump BIOS/firmware, or potentially compromise the entire physical host without ever needing to breach the OS firewall.

**OP11**
*   **LVM (Logical Volume Manager):** A software layer that abstracts physical disks into flexible logical volumes. It allows for resizing and managing storage volumes dynamically *after* the OS is running. Snapshot semantics are typically **crash-consistent** (the state at the moment the snapshot command was issued).
*   **LVM-Thin:** An extension of LVM that allows for thin provisioning—allocating storage space only as it is actually written to, rather than pre-allocating the entire volume size. Snapshot semantics are also generally crash-consistent.
*   **ZFS:** A complete file system and volume manager. It manages storage pools, volumes, and datasets. Its snapshot semantics are **transactional/application-consistent** because ZFS tracks data changes at the block level, allowing for near-perfect point-in-time recovery.

**When to Use:**
*   **LVM:** When you need simple, flexible volume resizing on existing hardware without adopting a full new file system.
*   **LVM-Thin:** When you need to over-provision storage capacity without consuming physical disk space immediately.
*   **ZFS:** When data integrity, advanced features (checksumming, self-healing), and application-consistent snapshots are paramount (e.g., critical databases).

**OP12**
**Stretch Cluster/DR Strategy:** To survive a complete site failure, the cluster must span two geographically distant sites (Site A and Site B).

**Ceph CRUSH Rules:** CRUSH rules must be configured to understand the topology (Site A vs. Site B). The rules must ensure that data replicas are placed across different failure domains (i.e., replicas must be placed in different physical sites).
**Monitor Placement:** Monitors must be distributed across both sites, ensuring that a majority of monitors remain available even if one entire site goes offline.
**Network Latency:** This is the biggest challenge. High latency between sites severely impacts the performance of consensus algorithms (like Raft used by Ceph Monitors) and can lead to timeouts and instability.
**Split-Brain Problem:** This occurs when network partitioning causes nodes in Site A and Site B to lose contact with each other, leading both sides to believe they are the sole authority.
**Why 2-Site Ceph is Bad Without Tiebreaker:** Without a tiebreaker (like a quorum witness or fencing mechanism), if the link between Site A and Site B fails, both sites might independently elect a new primary or start accepting writes, leading to data divergence (split-brain). A tiebreaker ensures only one side can achieve quorum and continue operations.

**OP13**
**DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses, subnet masks, default gateways, and DNS server information to devices on a network.

**DORA Process:**
1.  **Discover:** Client broadcasts a DHCP Discover message to find available DHCP servers.
2.  **Offer:** DHCP servers respond with a DHCP Offer, proposing an available IP address and configuration.
3.  **Request:** The client formally requests the offered IP address from the chosen server.
4.  **Acknowledge (ACK):** The server sends a DHCP ACK, finalizing the lease agreement.

**Server Unavailable:** If the DHCP server is unavailable and a Windows client's lease expires, the client will attempt to renew the lease using the old parameters. If renewal fails, the client will eventually revert to using its **static configuration** (if one was previously set) or, if no configuration is known, it will enter a state of **APIPA (Automatic Private IP Addressing)**, assigning itself an address in the 169.254.x.x range, making it unable to communicate outside its local subnet.

**OP14**
**Unmanaged Switch:** A plug-and-play device that operates purely at Layer 2 (Data Link). It learns MAC addresses and forwards frames based on those addresses. It has no configuration interface and provides basic connectivity.

**Managed Switch:** A sophisticated Layer 2/Layer 3 device that allows administrators to configure its behavior via a CLI or GUI.

**Enterprise Features:** Managed switches provide:
*   **VLAN Support (802.1Q):** Essential for segmenting broadcast domains.
*   **QoS (Quality of Service):** Prioritizing critical traffic (like VoIP) over bulk data transfers.
*   **Port Security:** Limiting the number of MAC addresses allowed on a port to prevent unauthorized device connection.
*   **SNMP Monitoring:** Allowing network management systems to poll the switch for status, errors, and utilization.

**OP15**
**NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.

**Criticality:** Accurate time synchronization is vital because many distributed systems rely on timestamps for ordering events, logging, and security.
**What Goes Wrong:**
1.  **Log Correlation:** If servers have different times, correlating logs across multiple services to trace a single user request becomes impossible.
2.  **Distributed Transactions/Clustering:** In clustered databases or distributed locks, time skew can cause transactions to be processed out of order, leading to data corruption or deadlock failures.
3.  **Security:** Kerberos authentication and certificate validation rely heavily on synchronized time to prevent replay attacks.

**OP16**
*   **Physical Server:** The actual, tangible hardware machine (CPU, RAM, NICs).
*   **Virtual Machine (VM):** A software emulation of a physical computer, running its own full operating system, isolated by a hypervisor.
*   **Container:** A lightweight, isolated process environment that shares the host OS kernel.

**When to Run on Bare Metal:**
1.  **Extreme Performance Needs:** Workloads requiring direct, low-level access to hardware resources (e.g., high-frequency trading, specialized GPU computing) where the hypervisor overhead is unacceptable.
2.  **Hypervisor/Storage Infrastructure:** Running the hypervisor itself (e.g., ESXi) or specialized storage appliances where the OS needs direct hardware control.
3.  **Minimal Footprint:** When the application is extremely small and the overhead of even a minimal OS/container runtime is deemed wasteful.

**OP17**
**UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power when utility power fails. Its role is to bridge the gap between the power outage and the generator starting up, ensuring graceful shutdown or continuous operation during the transition.

**Generator:** Provides long-term, sustained power during extended outages.

**Why Both:** The UPS handles the *instantaneous* failure (milliseconds), while the generator handles the *prolonged* failure (hours/days).

**ATS (Automatic Transfer Switch):** This is the electromechanical device that monitors the utility power. When utility power fails, the ATS automatically signals the generator to start and then switches the facility's electrical load from the utility feed to the generator feed. When utility power returns, the ATS switches the load back to the utility.

**OP18**
**Active-Passive Clustering:** One node (Active) handles all the workload, while the other node (Passive/Standby) remains powered on but idle, constantly monitoring the Active node. If the Active node fails, the Passive node takes over the workload.
**Active-Active Clustering:** Both nodes actively handle portions of the workload simultaneously. This provides higher resource utilization and better load distribution.

**PostgreSQL HA Implementation (Pacemaker/Corosync):**
1.  **Corosync:** Provides the cluster communication and membership service, ensuring all nodes agree on who is alive.
2.  **Pacemaker:** The cluster resource manager that monitors the state of the PostgreSQL service.
3.  **Virtual IPs (VIPs):** A floating IP address is configured. Pacemaker ensures this VIP is only assigned to the node currently running the PostgreSQL service.
4.  **Fencing (STONITH):** This is crucial. If the Active node fails, Pacemaker must use STONITH (e.g., sending a power-off command via IPMI) to ensure the failed node cannot come back online and try to claim the VIP or write to the shared storage, which would cause data corruption.
5.  **Failover Behavior:** If the Active node fails, Corosync detects the loss of heartbeat. Pacemaker initiates the failover: it fences the old node, moves the VIP to the Passive node, and starts the PostgreSQL service on the Passive node.

**OP19**
**3-2-1 Rule:** Maintain **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.

**RPO/RTO:**
*   **RPO (Recovery Point Objective):** The maximum acceptable amount of data loss measured in time (e.g., 1 hour). Dictates backup frequency.
*   **RTO (Recovery Time Objective):** The maximum acceptable downtime after a disaster (e.g., 4 hours). Dictates recovery speed and infrastructure readiness.

**Backup Types:**
*   **Full:** Copies all selected data. Slowest backup, fastest restore.
*   **Incremental:** Copies only data that has changed since the *last* backup of any type. Fastest backup, slowest restore (requires the last full + all subsequent incrementals).
*   **Differential:** Copies all data that has changed since the *last full* backup. Faster restore than incremental, slower backup than incremental.

**Deduplication:** Reduces storage footprint by identifying and storing only unique blocks of data, regardless of how many times they appear across different files or backups.

**Storage Tiers:**
*   **Disk:** Fast, used for short-term operational backups.
*   **Tape:** Slowest, highest archival density, used for long-term, cold storage.
*   **Cloud Offsite:** Used for the required offsite copy (e.g., AWS S3 Glacier).

**Immutable Backups:** Backups written to storage that cannot be modified or deleted for a set retention period. This is the primary defense against ransomware, as the attacker cannot encrypt or delete the recovery points.

**Testing Restores:** The most critical step. Regularly schedule test restores to a segregated environment to validate that the RTO/RPO targets are actually achievable with the current backup procedures.

**Backup vs. Disaster Recovery (DR):**
*   **Backup:** The process of creating copies of data to protect against data loss (e.g., accidental deletion, corruption).
*   **Disaster Recovery (DR):** The comprehensive plan and infrastructure designed to restore *business operations* after a catastrophic event (e.g., fire, site failure), which includes restoring data *and* getting applications running.

**OP20**
**802.1X (Port-Based Network Access Control):** A standard that controls which devices are allowed to connect to a wired network port. It enforces authentication *before* granting network access.

**Roles:**
*   **Supplicant:** The client device (laptop, IP phone) requesting access.
*   **Authenticator:** The network access device (the switch) that enforces the policy and relays authentication messages.
*   **Authentication Server:** The central authority (usually RADIUS) that verifies the supplicant's credentials.

**EAP Methods:**
*   **EAP-TLS:** The most secure method. Requires both the supplicant and the server to present and validate digital certificates.
*   **PEAP (Protected EAP):** A tunnel-based method where the server authenticates using a certificate, and then the client authenticates using username/password *inside* that secure tunnel.

**RADIUS:** The protocol used by the Authenticator (switch) to communicate authentication requests, credentials, and authorization decisions to the Authentication Server.

**Dynamic VLAN Assignment:** After successful authentication, the RADIUS server can instruct the switch (via RADIUS attributes) to place the supplicant onto a specific VLAN (e.g., placing a guest device on VLAN 99, while an employee lands on VLAN 10).

**Failed Authentication:** If a device fails authentication, the switch, based on policy, will typically place the port into an **unauthorized/quarantine VLAN** (a "black hole" VLAN) that has no access to production resources, effectively isolating the threat.

**MAB (MAC Authentication Bypass):** Used for devices that cannot run an 802.1X supplicant (e.g., printers, IP cameras). MAB allows the switch to use the device's **MAC address** as its identity credential and sends this MAC address to the RADIUS server for validation against a pre-approved list.
