## Kubernetes Answers

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** manages stateless applications, ensuring a specified number of identical, interchangeable replicas are running. Pods managed by a Deployment have no stable identity. A **StatefulSet** manages stateful applications, providing stable, unique network identifiers and persistent storage to each pod (e.g., database primary/replica).

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
A ClusterIP Service exposes a stable internal IP address within the cluster. It uses `kube-proxy` (which typically runs iptables or IPVS rules on each node) to intercept traffic destined for the Service's ClusterIP and redirect it to one of the healthy backing Pods selected via the Service's selector.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator or dynamically. It is a cluster resource representing the actual storage capacity (e.g., an AWS EBS volume).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a namespace resource that requests a specific amount and access mode of storage.
*   **StorageClass:** A class of storage that defines "how" the PV should be provisioned (e.g., fast SSD, standard HDD). It allows for dynamic provisioning.
*   **Relation:** A PVC requests storage based on criteria (size, access mode). The StorageClass dictates *how* that storage is created. The Kubernetes control plane then binds the PVC to an available or newly provisioned PV that matches the PVC's requirements.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**
1.  **Check Pod Events/Status:** Run `kubectl describe pod <name>` to see the reason for the crash and recent events.
2.  **Check Logs:** Run `kubectl logs <name>` (and potentially `kubectl logs <name> --previous`) to see the application-level error that caused the crash.
3.  **Check Configuration/Image:** Verify the container image tag is correct and that the necessary ConfigMaps/Secrets are mounted and accessible.
4.  **Check Resource Limits:** Verify the pod's resource requests/limits are reasonable and that the node has sufficient capacity (check node resource usage).

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS acts as the cluster's internal DNS service. It resolves service names (e.g., `my-service.my-namespace.svc.cluster.local`) to the corresponding ClusterIPs and handles internal cluster DNS lookups. If CoreDNS pods are down, internal DNS resolution fails. Pods will be unable to resolve other services within the cluster by name, leading to connection timeouts or failures when attempting to communicate with other microservices.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**
The scheduler uses a two-phase process:
1.  **Filtering (Predicates):** The scheduler first filters out all nodes that *cannot* run the pod based on hard constraints. Examples include: checking if the node has enough available CPU/Memory, checking for required taints/tolerations, or checking node selectors.
2.  **Scoring (Priorities):** From the remaining viable nodes, the scheduler scores them based on various preferences. The node with the highest score is chosen.
*   **Specific Factors:**
    1.  **Resource Availability:** How much CPU/Memory is left on the node.
    2.  **Node Affinity/Anti-Affinity:** Whether the pod prefers or avoids specific nodes/zones.
    3.  **Least Requested Priority:** Preferring nodes that are less utilized to spread the load evenly.

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
**Scheduling:** Yes, it will likely be scheduled, provided the scheduler only checks against *requested* resources. The node has $4\text{GB} - 3.5\text{GB} = 0.5\text{GB}$ available. The pod requests $256\text{Mi}$, which is less than $0.5\text{GB}$.
**Runtime Behavior:** If the pod uses $600\text{Mi}$ at runtime, it will exceed its defined `limits.memory` of $512\text{Mi}$. Kubernetes will enforce this limit, and the container runtime (like containerd) will terminate the container, resulting in the pod entering a `OOMKilled` state.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.**
1.  **External LB:** The request first hits an external Load Balancer (managed by the cloud provider or an external tool) which routes traffic to the NodePorts exposed by the Ingress Controller Pods.
2.  **Ingress Controller:** The request arrives at an NGINX Ingress Controller Pod running on a node. The controller reads the Ingress resource rules (host/path matching) and routes the traffic internally.
3.  **Service:** The Ingress Controller forwards the request to the ClusterIP Service associated with the application.
4.  **Endpoints:** The Service object maintains an Endpoints object, which is a list of the actual IP addresses of the healthy application Pods.
5.  **kube-proxy/iptables:** `kube-proxy` on the node intercepts traffic destined for the Service's ClusterIP. It uses iptables rules to perform DNAT (Destination Network Address Translation), rewriting the destination IP/port to the IP and port of one of the healthy Pods listed in the Endpoints object. The request finally reaches the application Pod.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A **NetworkPolicy** defines rules about how groups of pods are allowed to communicate with each other and with external network endpoints.
**Default Behavior:** If no NetworkPolicy exists in a namespace, the default behavior is "allow all" ingress and egress traffic.
**Applying a Policy:** When a NetworkPolicy is applied, the default behavior *changes* to "deny all" ingress and egress for the selected pods, unless explicitly allowed by a rule within that policy.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old Pods with new Pods one by one (or in batches), ensuring that a minimum number of old and new versions are running concurrently. This minimizes downtime.
*   **Recreate:** Terminates all existing Pods of the deployment, waits for them to terminate, and then creates all new Pods. This causes a brief period of downtime.
*   **When to choose Recreate:** When the application is highly sensitive to partial traffic during an update, or when the new version requires a complete, clean state initialization that cannot tolerate running alongside the old version.

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A **Namespace** is a mechanism to partition cluster resources across multiple virtual clusters within a single physical cluster. It provides scope isolation for names, resources, and policies.
**Default Namespaces:** Typically, `default`, `kube-system` (for cluster components), and sometimes `kube-public` and `kube-node-lease` are created.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
`kubectl describe pod <name>` provides a detailed status report on the pod, including events, resource requests, and configuration details.
**Information not shown by `kubectl get pod`:**
1.  **Events:** A chronological log of actions taken on the pod (e.g., scheduling attempts, image pull failures).
2.  **Detailed Status Conditions:** Specific reasons for pending/running states (e.g., `Reason: ImagePullBackOff`).
3.  **Container/Volume Details:** Detailed configuration, mounted volumes, and resource limits for each container within the pod.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A **ConfigMap** is an API object used to store non-confidential configuration data (like environment variables, configuration files, or command-line arguments) in key-value pairs, decoupling configuration from the application image.
**Consumption Methods:**
1.  **As Environment Variables:** Injecting keys/values directly into the container's environment variables.
2.  **As Mounted Files:** Mounting the ConfigMap as a volume inside the container, where each key becomes a file in the specified directory.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Exposes the Service on an internal IP address only, reachable from within the cluster.
*   **NodePort:** Exposes the Service on a specific port on *every* Node's IP address. This allows external access via `<NodeIP>:<NodePort>`.
*   **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes traffic to the Service's nodes, providing a stable, external IP address.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A **DaemonSet** ensures that a copy of a Pod runs on *every* (or a selected subset of) eligible nodes in the cluster.
**When to use:** When you need a service that must run locally on every node for infrastructure tasks, such as logging agents (Fluentd/Logstash), node monitoring agents (Prometheus Node Exporter), or network plugins (CNI).

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints:** A property applied to a Node that repels Pods. They act as a "no entry" sign.
*   **Tolerations:** A property applied to a Pod that allows it to be scheduled onto a Node that has a matching taint.
*   **Difference from Affinity:** Taints/Tolerations are about *repulsion* (preventing scheduling), whereas Node Affinity is about *preference* (guiding scheduling).
*   **Use Case (Taint/Toleration):** Isolating a GPU node by tainting it (`dedicated=gpu:NoSchedule`), allowing only GPU-requiring pods to tolerate that taint.
*   **Use Case (Affinity):** Ensuring a database pod is always scheduled on nodes within the same availability zone as its replicas.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An **Operator** is a method of packaging, deploying, and managing a complex application (like a database cluster) using custom controllers.
**Difference from Controller:** A standard controller watches the desired state (e.g., "I want 3 replicas") and reconciles the current state to match it. An Operator extends this by embedding *human operational knowledge* (e.g., "When the primary database fails, promote the replica, update the connection string, and run a failover script").
**Problem Solved:** It automates complex, domain-specific operational tasks that go beyond simple declarative state management, allowing users to manage stateful applications as easily as stateless ones.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
Kubernetes uses **Raft consensus algorithm** for etcd, which enforces **strong consistency**. This means that once a write is committed, all subsequent reads will see that write.
**Quorum Loss:** If the etcd quorum (majority, e.g., 2 out of 3) is lost, the cluster cannot achieve consensus. The API server cannot write or update the cluster state, effectively halting all configuration changes and potentially causing instability or read-only mode.
**Recovery (2/3 lost):** If 2 out of 3 nodes are permanently lost, the cluster loses its quorum and cannot function correctly. Recovery requires restoring the cluster state using a backup taken *before* the loss, and then re-establishing a new quorum with a minimum of 3 nodes.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
**RBAC Flow:** RBAC defines *who* (Subject) can do *what* (Verb) on *which* resources (Resource) within a specific scope.
*   **Role:** Defines permissions (e.g., `get`, `list` pods) scoped to a single Namespace.
*   **ClusterRole:** Defines permissions scoped across the entire cluster (e.g., `view secrets` cluster-wide).
*   **RoleBinding:** Binds a Role to a Subject (User/Group) within a specific Namespace.
*   **ClusterRoleBinding:** Binds a ClusterRole to a Subject cluster-wide.
**Manifests (Read-only Pods/Logs in `dev` namespace):**
```yaml
# 1. Define the permissions (Role)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# 2. Bind the permissions to a user/group (RoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-reader-binding
  namespace: dev
subjects:
- kind: User
  name: developer-user # Replace with actual user/group
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
**The Problem (ndots):** The `ndots` value in `/etc/resolv.conf` specifies the maximum number of dots a hostname can contain before the system stops trying to resolve it as a short hostname (i.e., stops trying to resolve it against the local search domains). If `ndots` is set too low (e.g., 1), and the pod tries to resolve an external domain like `api.service.com`, the system might first try to resolve it as `api.service.com.svc.cluster.local` (if the cluster search domain is appended), leading to unnecessary, slow queries against the cluster DNS before finally hitting the external resolver.
**The Fix (dnsConfig):** By using `dnsConfig` in the Pod spec, you can explicitly override the DNS settings. You can set `options` to control `ndots` or, more commonly for external resolution, explicitly define the `nameservers` to point directly to reliable external DNS servers (like 8.8.8.8) and ensure the `searches` list is minimal or empty.

## Development Answers

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
*   **Merge:** Combines the histories of two branches by creating a new "merge commit." It preserves the exact history of both branches.
*   **Rebase:** Rewrites history by taking the commits from one branch and reapplying them one-by-one onto the tip of another branch. It creates a linear history.
*   **Avoid Rebasing:** You should **never** rebase commits that have already been pushed to a shared, public repository, as this rewrites history and causes major synchronization issues for collaborators.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP (Transmission Control Protocol):** Connection-oriented, reliable, ordered delivery. It uses a three-way handshake to establish a connection and guarantees packet delivery via acknowledgments and retransmissions. (Protocols: HTTP/1.1, FTP).
*   **UDP (User Datagram Protocol):** Connectionless, unreliable, best-effort delivery. It sends packets without establishing a connection or guaranteeing order/delivery. (Protocols: DNS, VoIP/SIP).

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A **race condition** occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data.
**Example (Conceptual/Pseudocode):** Two threads try to increment a shared counter variable initialized to 0.
1. Thread A reads counter (0).
2. Thread B reads counter (0).
3. Thread A calculates $0 + 1 = 1$ and writes 1 back.
4. Thread B calculates $0 + 1 = 1$ and writes 1 back.
The expected result is 2, but due to the interleaving, the final result is 1.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is very fast.
*   **Asymmetric Encryption (Public-Key):** Uses a pair of keys: a public key (shared widely for encryption) and a private key (kept secret for decryption). It is computationally intensive.
*   **TLS Usage:** TLS uses both. First, the client and server use **asymmetric encryption** (via RSA or ECDH) to securely exchange a unique, ephemeral **symmetric session key**. Once the session key is established, all subsequent bulk data transfer is encrypted using the much faster **symmetric encryption**.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
A **container image layer** is a read-only, immutable filesystem layer that stores the changes made during the build process (e.g., installing packages, copying files). Layers are stacked on top of each other.
**Caching Impact:** Docker caches layers based on the instruction and its context. If an instruction (like `RUN apt-get update`) hasn't changed, Docker reuses the cached layer, speeding up builds.
**Best Practice:** Place instructions that change infrequently (like installing base OS dependencies) *before* instructions that change frequently (like copying application source code). This maximizes cache hits.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**
1.  **Application Logs (Deep Dive):** Check the application logs for the specific time of the 503. Is it an internal service dependency failure, thread exhaustion, or resource exhaustion? (This identifies the root cause).
2.  **Resource Utilization (CPU/Memory):** Check the hosting environment (Kubernetes/VM) metrics for the API pods. Is the CPU spiking to 100% or is memory usage hitting limits, causing throttling or OOMKills?
3.  **Dependency Health:** Check the health and latency of any downstream services the API relies on (databases, caches, other microservices). A 503 often means the API couldn't reach its dependencies.
4.  **Load Balancer/Ingress Metrics:** Check the ingress controller/LB metrics to see if the traffic is being distributed correctly or if the upstream health checks are failing prematurely.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
The **CAP Theorem** states that a distributed data store can only guarantee two out of three properties simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest write), and **Partition Tolerance** (the system continues to operate despite arbitrary message loss or failure of part of the network).
*   **CP Example (Consistency over Availability):** Traditional relational databases (like PostgreSQL clusters configured for strong consistency). If a network partition occurs, the system will refuse writes or reads on the minority side of the partition to prevent data divergence.
*   **AP Example (Availability over Consistency):** Cassandra or DynamoDB. If a network partition occurs, nodes continue to accept reads and writes on both sides, ensuring the service remains available, but data might temporarily diverge until the partition heals (eventual consistency).

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) of an *existing* single server instance. (Easier, but has hard limits).
*   **Horizontal Scaling (Scaling Out):** Adding *more* instances (replicas) of the application behind a load balancer. (More resilient, theoretically limitless).
*   **Patterns for Horizontal Scaling:** Statelessness (the application instance doesn't store session data locally), Microservices architecture, and using distributed caching layers (like Redis).

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An **environment variable** is a dynamic named value that can affect the way running processes will behave on a computer. They are used to pass configuration data to applications without hardcoding it.
**Persistence:** To set a variable to persist across shell sessions on Linux, you must add the export command to your shell's startup file, typically `~/.bashrc` or `~/.zshrc`.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
*   **JSON (JavaScript Object Notation):** A lightweight data-interchange format using key-value pairs and arrays.
    *   *Advantage:* Extremely fast to parse in most programming languages.
*   **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that uses indentation to denote structure.
    *   *Advantage:* Highly readable and concise for configuration files (like Kubernetes manifests).

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
A **REST API** (Representational State Transfer) is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources.
*   **GET:** Retrieves a resource or a collection of resources (Safe and Idempotent).
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource (Not Idempotent).
*   **PUT:** Replaces an entire resource at a known URI with the provided data (Idempotent).
*   **DELETE:** Removes the specified resource (Idempotent).

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
**Version pinning** is the practice of explicitly locking a dependency to a specific, exact version number (e.g., `library@1.2.3`) rather than using a range (e.g., `library@^1.2.0`).
**Importance:** It ensures **reproducible builds**. If you don't pin versions, a future update to a dependency might introduce breaking changes, causing your build to fail unexpectedly, even if your own code hasn't changed.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled Language:** Source code is translated entirely into machine code (an executable file) by a compiler *before* execution. This results in faster runtime performance. (Examples: C++, Go).
*   **Interpreted Language:** Source code is read and executed line-by-line by an interpreter program at runtime. This allows for faster development cycles but can be slower at runtime. (Examples: Python, JavaScript).

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
*   **Reverse Proxy:** Sits in front of one or more web servers. It intercepts client requests and forwards them to the appropriate backend server. The client never knows the backend server's identity.
*   **Forward Proxy:** Sits in front of a client (user). It intercepts requests from the client and forwards them to the internet on behalf of the client (often used for anonymity or filtering).
*   **Servers & Use Cases:**
    *   **NGINX:** Used for load balancing across multiple application servers.
    *   **HAProxy:** Used for high-availability traffic distribution and advanced health checking.

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A **deadlock** is a situation where two or more competing actions are waiting for the other to finish, resulting in a permanent standstill.
**Coffman Conditions:**
1.  **Mutual Exclusion:** At least one resource must be held in a non-sharable mode (only one process can use it at a time).
2.  **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3.  **No Preemption:** A resource cannot be forcibly taken away from a process; it must be released voluntarily.
4.  **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
**Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. There is a window of time where different replicas might return stale data.
**Cassandra Handling:** Cassandra uses mechanisms like **read repair** and **anti-entropy repair** (e.g., Merkle trees) to propagate updates across nodes asynchronously.
**Tunable Consistency Levels:** Users specify the required consistency level per operation (read or write). Examples include:
*   **ONE:** Only one replica needs to respond (fastest, least consistent).
*   **QUORUM:** A majority of replicas must respond (balances speed and consistency).
*   **ALL:** All replicas must respond (slowest, most consistent).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
**mTLS** requires *both* the client and the server to present and validate cryptographic certificates during the TLS handshake, ensuring both parties are authenticated.
**Handshake Process:**
1.  Client initiates connection.
2.  Server sends its certificate to the client.
3.  Client verifies the server's certificate against its trusted CAs.
4.  **Client sends its certificate to the server.**
5.  Server verifies the client's certificate against its trusted CAs.
6.  If both validations pass, they proceed to exchange keys and establish the symmetric session.
**Use Case:** Service-to-service communication in a Zero Trust network architecture (e.g., securing internal microservice mesh traffic).

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an underlying array.
**Collision Resolution:**
*   **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hash to that index.
*   **Open Addressing:** If a collision occurs, the algorithm probes for the next available empty slot in the main array according to a defined sequence (e.g., linear probing, quadratic probing).
**Time Complexity:**
*   **Average Case (Good Hash Function):** $O(1)$ for insertion, lookup, and deletion.
*   **Worst Case (All keys hash to the same bucket):** $O(n)$ for all operations (effectively degrades to searching a linked list).

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
The **Circuit Breaker** pattern prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a failing downstream service), thereby preventing resource exhaustion and cascading failures.
**States:**
1.  **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the breaker trips to Open.
2.  **Open:** Requests are immediately rejected without attempting the call (failing fast). After a timeout, the breaker moves to Half-Open.
3.  **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker closes; if they fail, it returns to Open.
**Relation to Retries/Backoff:** Circuit breakers act as a *macro* defense. Retries and exponential backoff are *micro* defenses used *within* the Closed state to handle transient errors gracefully before the breaker trips.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**
*   **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data *before* modification, preventing other transactions from reading or writing it until the lock is released. (High safety, lower concurrency).
    *   *Example:* Using `SELECT ... FOR UPDATE` in SQL.
*   **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read. If it has, the transaction fails and must be retried. (High concurrency, requires retry logic).
    *   *Example:* Using a version column (e.g., `version_number`) in the table; the `UPDATE` statement includes a `WHERE version_number = [original_version]`.
