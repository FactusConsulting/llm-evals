## OpenTofu / Terraform Answers

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` calculates and displays the changes that will be made to the infrastructure (what will be created, modified, or destroyed) without actually applying them. `tofu apply` executes the changes detailed in the plan, provisioning or modifying the real infrastructure based on the configuration.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a file that maps the resources defined in your configuration code to the actual resources provisioned in the real world (e.g., mapping a logical resource name to its unique cloud ID). Remote state (e.g., S3, Terraform Cloud) is crucial because it allows teams to collaborate safely, provides a single source of truth for the infrastructure state, and enables state locking to prevent concurrent modifications.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` creates multiple instances of a resource based on an integer value. It uses an index (e.g., `count.index`) to differentiate instances. `for_each` creates multiple instances based on the elements of a map or set. It uses the key/value of the iteration as the identifier. `for_each` is preferred when you need to reference specific instances by a meaningful key (like a hostname or environment name) rather than a numerical index, as it makes resource referencing more robust to reordering.

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?**
OpenTofu detects this drift during the `tofu plan` phase. It compares the desired state defined in the configuration against the actual state retrieved from the cloud provider API. If a difference is found, OpenTofu reports a "drift" or "change" in the plan, indicating that the configuration needs to be updated to match the manual change, or the manual change needs to be reverted to match the configuration.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
resource "aws_instance" "web" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-0abcdef1234567890" # Example AMI
  instance_type = "t2.micro"

  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
**Output Values:** Outputs are designed to expose data *from* the current module *to* consumers (like the root module). They are generally used for simple, final values.
**`terraform_remote_state` Data Source:** This is used to read the state file of *another*, separately managed remote state backend.
**Recommended Alternative:** The recommended alternative is to use **Module Outputs** combined with **Module Inputs**. If Module A creates a resource and Module B needs its ID, Module A should output the ID, and Module B should consume it as an input variable. This keeps dependencies explicit and manageable within the module structure, whereas `terraform_remote_state` couples modules tightly to specific state file locations.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
The failure occurs because OpenTofu's dependency graph executes resources in parallel by default. The `null_resource` with `remote-exec` runs its provisioner *after* the resource is created, but the output value is only populated *after* the provisioner successfully completes. If a dependent resource tries to read this output immediately, it reads the initial, empty value.
**Fix:** Explicitly enforce the dependency using `depends_on`. The dependent resource must explicitly list the `null_resource` in its `depends_on` block to ensure it only runs after the remote execution has finished and the output has been populated.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` allows you to bring existing, manually created infrastructure resources under the management of your configuration without first writing the configuration code.
**Limitations:** It only imports the *current state* of the resource; it does not automatically generate the corresponding HCL configuration code.
**Improvement (Import Block):** The import block (e.g., `resource "aws_instance" "example" { ... } import = ["i-12345"]`) allows you to define the resource block *and* specify the import ID in one place. This is superior because it immediately associates the existing resource ID with the resource block definition, making the configuration immediately usable for subsequent `plan`/`apply` operations, rather than relying on a separate CLI command.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A **variable** (input) is a placeholder defined in the configuration that accepts external values (e.g., from CLI flags, `.tfvars` files, or environment variables) to make the configuration reusable. An **output** is a value exposed *from* a module or root configuration to other parts of the system, allowing consumers to retrieve data generated by the infrastructure (e.g., a public IP address).

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that enables OpenTofu to interact with a specific API or service (e.g., AWS, Azure, Kubernetes). If you run `tofu plan` without `tofu init`, OpenTofu will fail because it has not downloaded or initialized the necessary provider plugins specified in the configuration.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
The `.terraform.lock.hcl` file records the exact, specific versions of every provider and module dependency that OpenTofu downloaded during `tofu init`. It should be committed to version control to ensure that every developer or CI/CD pipeline running the code uses the *exact same* dependency versions, preventing "works on my machine" issues caused by upstream provider updates.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` tears down all infrastructure resources managed by the current state file. To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web["web1"]`).

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source is a block that fetches information about existing infrastructure or external data that is *not* managed by the current configuration.
**Example:** You need to provision a new EC2 instance, but you need to reference the latest Amazon Linux AMI ID. Instead of hardcoding the AMI ID (which changes frequently), you use a `data "aws_ami"` source to dynamically look up the latest official AMI ID for your region.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
**Variables** are inputs that come from *outside* the configuration (user input). **Locals** are variables defined *inside* the configuration block to store intermediate values, perform calculations, or simplify complex expressions *within* the configuration itself.
**When to use locals:** Use locals when you need to derive a value based on other variables or resources *within* the same module, or when you want to abstract complex logic (like constructing a complex tag map) without exposing that logic as an input variable.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block allows fine-grained control over how OpenTofu manages a resource during updates.
*   **`create_before_destroy`:** Creates a new replacement resource *before* destroying the old one. **Use Case:** Database migrations or critical services where downtime must be avoided during replacement.
*   **`prevent_destroy`:** Prevents the resource from being destroyed by any operation (`apply` or `destroy`). **Use Case:** Critical infrastructure components (like a primary load balancer) that should never be accidentally deleted.
*   **`ignore_changes`:** Tells OpenTofu to ignore specific attributes when calculating drift or applying changes. **Use Case:** When an external system (like a monitoring agent) modifies a tag or metadata field that you do not want OpenTofu to manage or revert.

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
A `moved` block is used during configuration refactoring. It explicitly tells OpenTofu how to map an old resource address to a new resource address. When you rename a resource or move it between modules, you use the `moved` block to inform the state file that the *identity* of the resource remains the same, even though its address in the code has changed. This prevents OpenTofu from treating the resource as deleted and recreated, thus preserving its state and avoiding downtime.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
The dependency graph maps out the execution order of all resources.
*   **Implicit Dependency:** Occurs when one resource references an attribute of another resource (e.g., `resource_b.id` is used in `resource_a`). OpenTofu automatically infers this dependency.
*   **Explicit Dependency:** Defined using `depends_on = [resource_x]`. This forces an execution order regardless of attribute references.
**Impact on Parallelism:** Explicit dependencies force sequential execution. If you use `depends_on` unnecessarily, you artificially constrain the graph, preventing OpenTofu from running independent resources concurrently, which slows down the plan/apply time. It should be used sparingly, only when implicit dependencies are insufficient (e.g., when a resource needs to exist before another resource is *created*, but doesn't need its attributes).

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1.  **Modularization:** Break large configurations into smaller, focused modules. *Tradeoff:* Increases complexity in managing module dependencies and state boundaries.
2.  **Targeted Operations:** Use `tofu plan -target=module.resource` to only plan changes for specific, small sections of the infrastructure. *Tradeoff:* Reduces safety; you risk missing drift in untargeted resources.
3.  **State Splitting/Isolation:** Separate unrelated infrastructure components into different state files/workspaces. *Tradeoff:* Increases operational overhead (more state files to manage) but drastically reduces the scope of each plan.
4.  **Provider Configuration Optimization:** Ensure providers are configured efficiently (e.g., using specific regions, limiting API calls). For very large deployments, consider using tools that cache provider metadata. *Tradeoff:* Requires deep knowledge of the specific provider's API limitations.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**
State locking ensures that only one operation modifies the state file at a time, preventing corruption from concurrent runs. It is typically implemented via a backend mechanism (like DynamoDB for S3).
**If a lock is not released:** The state file becomes locked indefinitely. Any subsequent `tofu plan` or `tofu apply` will fail immediately with a "state is locked" error.
**Manually Breaking a Lock:** You must use the backend-specific CLI command (e.g., `aws dynamodb delete-item` if using DynamoDB).
**Risks:** Manually breaking a lock bypasses safety checks. If the previous operation *did* partially succeed before crashing, breaking the lock and running a new apply could lead to state corruption or resource duplication.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.**
1.  **Configure New Backend:** Update the `backend` block in the root configuration to point to the S3 bucket and DynamoDB table.
2.  **Initialize with Migration:** Run `tofu init`. OpenTofu will detect the existing local state and prompt you to migrate it to the new remote backend. Confirm the migration.
3.  **State File Handling:** The local state file is uploaded to S3, and the remote state file is created/updated. The local file can then be safely deleted.
4.  **Verification:** Run `tofu plan`. If the plan runs successfully and shows no changes (or only the expected changes), the migration was successful, and the configuration is now using the remote state and locking mechanism.

## Ansible Answers

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
*   **Task:** The smallest unit of work in Ansible. It is a specific instruction telling Ansible what to do (e.g., `apt: name=nginx state=present`).
*   **Playbook:** A YAML file that defines a set of plays. A play is a set of tasks that Ansible executes against a group of hosts defined in the inventory. Playbooks are the primary execution files.
*   **Role:** A standardized, reusable structure for organizing related tasks, handlers, variables, and templates. Roles promote best practices and modularity, allowing complex configurations to be broken down logically (e.g., a `webserver` role).

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary containing gathered information about the target host, such as OS version, memory, network interfaces, etc., collected during the initial fact-gathering phase. To access the OS family, you would typically use `ansible_facts['os_family']`.

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
*   **`command`:** Executes a command directly. It is generally safer as it does not interpret shell features (like pipes `|` or redirects `>`). Use this for simple, non-shell-dependent commands.
*   **`shell`:** Executes a command through the host's shell (e.g., `/bin/sh`). Use this when you need shell features like piping, environment variable expansion, or redirection.
*   **`raw`:** Executes a command directly on the remote machine without invoking the shell interpreter. Use this when you need maximum control over the execution environment, often for low-level system interaction, but it is less portable than `command`.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means that running the same task multiple times will result in the same system state without causing unintended side effects after the first successful run. Ansible achieves this by using modules that check the current state before making changes.
*   **Idempotent Example:** `ansible.builtin.package`: If the package is already installed, the module reports "ok" and makes no changes.
*   **Non-Idempotent Example:** `ansible.builtin.command: cmd=echo "Hello" >> /tmp/log.txt`: Running this command repeatedly will append "Hello" to the log file every time, changing the state each time.

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS family
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
Ansible resolves variables based on a strict precedence order, where later sources override earlier ones. The general order (highest priority listed last) is:
1.  **Role Defaults:** Variables defined within the `defaults/main.yml` of a role.
2.  **Inventory Variables:** Variables defined in `group_vars/` or `host_vars/`.
3.  **Extra Variables:** Variables passed via the command line (`-e`).
4.  **Set Fact:** Variables set dynamically during runtime using `set_fact`.

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**
1.  **Inventory Grouping:** Divide the 50 nodes into two groups: `initial_batch` (3 nodes) and `remaining_nodes` (47 nodes).
2.  **Serial Execution:** Use the `serial` keyword in the play definition to control batch size.
3.  **Structure:**
    *   Run the play targeting `initial_batch` with `serial: 1` (or `serial: 3` if you want them to run concurrently but wait for all 3).
    *   Run a second play targeting `remaining_nodes` with `serial: 1` (or a larger number).
    *   *Note on `wait_for`*: `wait_for` is used to wait for a service/port to become available *after* a task runs, not to control the execution flow between batches. The `serial` keyword handles the batching requirement.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible files.
To encrypt a single variable without encrypting the whole file, you must use the vault syntax directly within the variable definition in your YAML file, typically using the `vault:` prefix or by ensuring the variable is loaded via a vault-encrypted file. For a single variable, you would typically use a vault-encrypted file (`vars/secrets.yml`) and reference the variable in your playbook, ensuring the vault password is provided during execution.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory file lists the hosts (servers) that Ansible will manage, grouping them logically.
*   **Static Inventory:** A manually maintained file (INI or YAML format) where you list every host and its associated groups.
*   **Dynamic Inventory:** A script or plugin that connects to a source (like AWS, Azure, or a CMDB) at runtime to generate the inventory list. This is preferred for large, ephemeral cloud environments.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a special task designed to perform cleanup or post-configuration actions (like restarting a service).
**Difference:** Handlers are *not* run immediately when they are defined. They are only executed when explicitly "notified" by another task that has made a change.
**Triggering:** A task notifies a handler using the `notify:` keyword (e.g., `service_task: ... notify: restart_nginx`).

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
`ansible.cfg` is a configuration file that controls how Ansible behaves globally across all playbooks.
**Common Settings:**
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Sets the default SSH user to connect as.
3.  `host_key_checking`: Controls whether Ansible verifies the host's SSH key.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
The `register` keyword captures the entire return value (stdout, stderr, status, etc.) of a task and stores it in a variable.
**Usage:** You access the captured data in subsequent tasks using dot notation on the registered variable (e.g., `{{ result.stdout }}`).

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
*   **`import_tasks`:** Reads tasks from a file *before* the play starts. It is treated as a static inclusion.
*   **`include_tasks`:** Reads tasks from a file *during* the play execution. It is dynamic.
**Conditional Evaluation:** `include_tasks` allows for conditional execution (using `when:` clauses) on the included tasks, as it runs during the play. `import_tasks` executes all tasks in the file immediately upon loading, making conditional logic more complex or impossible to apply cleanly to the included file itself.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Ansible Galaxy is a community repository where users share reusable Ansible content (roles and collections).
To use a `requirements.yml` file, you run the command `ansible-galaxy install -r requirements.yml`. This command reads the file, which lists the required roles/collections and their specific versions, and downloads/installs them into the local Ansible dependency cache.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins define the mechanism Ansible uses to connect to the target host.
*   **`ssh` (Default):** Connects over SSH to a remote machine. Used for managing standard Linux/Unix servers.
*   **`local`:** Executes tasks directly on the Ansible control node itself. Used for tasks that don't require remote access (e.g., running local scripts).
*   **`network_cli`:** Connects to network devices (routers, switches) using CLI protocols (like Telnet or SSH). Used for infrastructure automation outside of traditional OS management.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
*   **`delegate_to`:** Allows a task normally targeted at a remote host to be executed on a different host, including the control node (`localhost`).
*   **`run_once`:** Ensures that a task, even if targeted at multiple hosts, is executed only one time across the entire managed group.
**Practical Example:** You gather the IP addresses of all web servers using a task registered as `web_ips`. You then use a task that runs only once (`run_once: true`) and delegates to the control node (`delegate_to: localhost`) to update a central configuration file (like a firewall rule list) using the gathered IPs:
```yaml
- name: Update central firewall config
  ansible.builtin.lineinfile:
    path: /etc/firewall/whitelist.conf
    line: "{{ item }}"
  loop: "{{ web_ips.results | map(attribute='ansible_facts.inetaddr') | list }}"
  delegate_to: localhost
  run_once: true
```

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).**
1.  **Increase `forks`:** Increase the number of parallel connections Ansible makes. *Tradeoff:* Can overwhelm the target hosts or the control node's resources if set too high.
2.  **Pipelining:** Allows Ansible to send tasks to multiple hosts simultaneously, rather than waiting for one host to finish its entire play before starting the next. *Tradeoff:* Can increase complexity and might not be suitable for highly sequential tasks.
3.  **Fact Caching:** Cache the gathered facts (`ansible_facts`) on the target hosts or a central server. *Tradeoff:* Requires setup (e.g., using `fact_caching` module) and introduces a slight delay for cache invalidation.
4.  **Mitogen/Parallel Execution:** Use external tools or advanced Ansible features to manage execution across multiple control nodes simultaneously. *Tradeoff:* Significantly increases infrastructure complexity and operational overhead.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
Jinja2 is the templating engine used by Ansible.
*   **`{{ variable }}`:** Used for **printing** the value of a variable (output).
*   **`{% statement %}`:** Used for **logic** control structures (loops, conditionals, assignments).
*   **`{# comment #}`:** Used for **comments** within the template that are stripped out during rendering.
**Snippet:**
```nginx
upstream backend_servers {
    # Backend Server 1 (Primary)
    server {{ backend_servers.0.ip }}:{{ backend_servers.0.port }} weight=3;
    
    # Backend Server 2 (Secondary)
    server {{ backend_servers.1.ip }}:{{ backend_servers.1.port }} weight=1;
    
    # Backend Server 3 (Backup)
    server {{ backend_servers.2.ip }}:{{ backend_servers.2.port }} backup;
}
```
*(Assuming `backend_servers` is a list of dictionaries passed into the template.)*

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.**
1.  **Serial Batches:** Use `serial: 2` (or similar) in the play to ensure only 2 servers are updated at a time, leaving the rest active behind the load balancer.
2.  **Pre-Task (Deregister):** Before updating a batch, use a task to deregister the current batch of servers from the load balancer (e.g., using the `uri` module to call the LB API).
3.  **Update Task:** Deploy the new code/configuration to the batch.
4.  **Health Check:** Immediately after deployment, use the `uri` module to perform a health check against the newly updated servers. If the check fails, trigger the `rescue` block.
5.  **Post-Task (Register):** If the health check passes, register the servers back into the load balancer.
6.  **Rollback Strategy:** Wrap the deployment logic in a `block`/`rescue` structure. If the health check fails (or any task in the block fails), the `rescue` block executes, which runs a task to immediately redeploy the *old* configuration onto the affected servers and re-registers them, ensuring minimal downtime.
