## Go Answers

**G1** — An array in Go has a fixed size determined at compile time (e.g., `[5]int`). A slice is a dynamically sized, flexible view into an underlying array. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array, copies the existing elements, and then appends the new element(s).

**G2** — `var x int` declares a variable `x` and initializes it to its zero value (which is `0` for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when redeclaring a variable within the same scope, or when assigning to a variable that was already declared using `var` or `:=`.

**G3** — A goroutine is a lightweight, independently executing function managed by the Go runtime. It differs from an OS thread because goroutines are multiplexed onto a smaller number of OS threads by the Go scheduler, requiring significantly less memory overhead (typically a few KB stack vs. MBs for an OS thread). The Go scheduler (GMP model) maps Goroutines (G) onto OS threads (M) using a pool of logical processors (P). It handles scheduling, context switching, and cooperative multitasking, allowing millions of goroutines to run efficiently.

**G4** — Channels are typed conduits through which you can send and receive values between goroutines, enabling safe communication. An **unbuffered channel** requires both the sender and receiver to be ready at the moment of communication (synchronous rendezvous). A **buffered channel** can hold a specified number of values without blocking the sender until the buffer is full. When sending to a full buffered channel, the sender goroutine blocks until another goroutine receives a value, freeing up space in the buffer.

**G5** — The `context` package is used to carry deadlines, cancellation signals, and other request-scoped values across API boundaries and between goroutines. This is crucial for managing the lifecycle of concurrent operations.
Minimal example:
```go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	// Create a context that automatically cancels after 2 seconds
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel() // Always call cancel to release resources

	// Simulate a long-running request
	done := make(chan string)
	go func() {
		select {
		case <-time.After(5 * time.Second):
			done <- "Request completed successfully"
		case <-ctx.Done():
			done <- "Request cancelled by context timeout"
		}
	}()

	result := <-done
	fmt.Println(result)
}
```

**G6** — Go's interface satisfaction is implicit (structural typing). A type satisfies an interface simply by implementing all the methods declared in that interface; there is no explicit `implements` keyword. This differs from Java/C# where interfaces must be explicitly declared and implemented. The empty interface `interface{}` (or `any` in Go 1.18+) can hold a value of *any* type. It is powerful because it allows for maximum flexibility (e.g., generic functions accepting any type). It is dangerous because using it requires type assertion or type switching to use the underlying value, which can panic if the assertion is incorrect.

**G7** — This code is unsafe due to data races. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading `ready` and then reading `data`. The Go memory model guarantees that writes are visible to other goroutines *only* if synchronization primitives (like channels or mutexes) are used. The loop `for !ready {}` spins indefinitely, potentially reading a stale value of `ready` before the write is visible, leading to a deadlock or reading an uninitialized/stale `data`.
Correct alternatives:
1. **Channel:** Send a signal on a channel when done: `done := make(chan bool); go func() { data = "hello"; ready = true; done <- true }(); <-done`.
2. **Mutex:** Use a `sync.Mutex` to protect both writes and reads.

**G8** — `sync.Mutex` provides exclusive locking: only one goroutine can hold the lock at a time (read or write). `sync.RWMutex` allows multiple readers to hold the lock simultaneously (`RLock`/`RUnlock`), but requires exclusive access for writers (`Lock`/`Unlock`).
Use `sync.Map` when you need a concurrent map where keys are frequently added, deleted, or updated by many goroutines, and you want to avoid locking the entire map for every operation. Use a regular map with a mutex when reads vastly outnumber writes, as the overhead of `sync.Map` might be higher than using an `RWMutex` around a standard map. Performance trade-offs: `RWMutex` is faster for read-heavy workloads; `sync.Map` is optimized for concurrent access patterns but can have higher overhead for simple, sequential access.

**G9** — Go modules manage dependencies. `go.mod` lists the required modules and their required versions (the dependency graph). `go.sum` contains cryptographic checksums for the exact content of every dependency listed in `go.mod`, ensuring that downloaded dependencies haven't been tampered with. `go mod tidy` cleans up the `go.mod` and `go.sum` files by adding missing dependencies and removing unused ones. MVS (Minimum Version Selection) is an algorithm used by Go to select the highest possible version of a dependency that satisfies all version constraints specified in the module graph, ensuring compatibility while allowing for updates.

**G10** — A `defer` statement schedules a function call to be executed just before the surrounding function returns. Multiple defers execute in Last-In, First-Out (LIFO) order. A common gotcha in a loop is capturing the loop variable by reference (or closure capture). If you defer a function that uses the loop variable, the deferred function will execute *after* the loop finishes, and it will use the final value of the loop variable, not the value from the iteration it was defined in.

**G11** — A pointer in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12** — The `init()` function is a special function that runs automatically before the `main` function (or before any other code in the package) is executed. It runs exactly once per package. A package *can* have multiple `init()` functions, and they execute sequentially in the order they appear in the source code files.

**G13** — `make` is used to initialize built-in reference types (slices, maps, channels). It allocates and initializes the underlying data structure. `new` allocates memory for a value of a specified type and returns a pointer to the zero-initialized value of that type. `make` works with slices, maps, and channels; `new` works with any type.

**G14** — Error handling in Go is explicit, not exception-based. The `error` interface is the standard interface that any type can implement to signal an error (it requires only one method: `Error() string`). The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain wraps a specific sentinel error value. `errors.As(err, &target)` checks if the error chain contains a value that matches a specific type, allowing you to extract structured error details.

**G15** — **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be written to until initialized). **Slice:** `[]Type`. Zero value: `nil` (a nil slice, length 0, capacity 0). **Channel:** `chan Type`. Zero value: `nil` (cannot be used until initialized). **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.
**G16** — A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization mechanism. The `-race` flag instruments the Go runtime to detect these unsynchronized memory accesses at runtime. Example: Two goroutines incrementing a shared counter without a mutex. Fix: Wrap the increment operation in a `sync.Mutex.Lock()`/`Unlock()` block, or use atomic operations/channels for communication.

**G17** — The `select` statement waits on multiple communication operations (channel sends/receives). It differs from `switch` because `select` is specifically designed for concurrency and blocking on channel operations. When multiple cases are ready, `select` chooses one pseudo-randomly. To implement a timeout, you include a `case <-time.After(duration):` case in the `select` block.

**G18** — Escape analysis is a compiler optimization that determines whether a variable's data should be allocated on the stack (fast, automatic cleanup) or the heap (slower, requires garbage collection). The compiler analyzes the variable's lifetime and whether it might "escape" the function's scope. If a variable's address is returned from a function or stored in a structure that outlives the function call, it must escape to the heap. You can inspect this using compiler flags (e.g., `-gcflags=-m`). It matters because stack allocation is significantly faster than heap allocation.

**G19** — Reflection allows a program to examine and manipulate its own structure (types, fields, methods) at runtime. `reflect.Type` describes the structure of a value (its kind, fields, methods). `reflect.Value` holds the actual runtime value and allows you to invoke methods or access fields. Reflection incurs significant performance costs because the compiler cannot optimize calls through reflection as effectively as static calls. It is justified when dynamic behavior is required (e.g., ORMs, serialization libraries), but code generation is preferred for performance-critical paths.

**G20** — The `go:embed` directive allows embedding files or directories directly into a Go binary as assets. It works by instructing the compiler to read the specified path and embed its contents into a variable of type `embed.FS` (or similar). For single files, you specify the path; for directories, you specify the root directory. Limitations include file size limits imposed by the build system and the fact that the embedded content is static at compile time. It interacts with `io/fs.FS` by providing an implementation of that interface, allowing standard Go I/O functions to read the embedded assets as if they were on the filesystem.

## Rust Answers

**R1** — Ownership is Rust's system for managing memory without a garbage collector. It ensures that every piece of data has a single, clear owner at any given time. The three rules are: 1. Each value in Rust has a variable that’s called its owner. 2. There can only be one owner at a time. 3. When the owner goes out of scope, the value is dropped (memory is freed).

**R2** — `String` is a heap-allocated, growable, mutable UTF-8 string type (owned data). `&str` is a string slice—a borrowed, immutable view into string data, which might be stored on the stack or in the heap. Use `String` when you need to own, modify, or build a string. Use `&str` in function signatures when you only need to read the string data without taking ownership or modifying it, as it avoids unnecessary heap allocations.

**R3** — Borrowing allows you to refer to data without taking ownership. The borrow checker enforces rules to prevent data races at compile time. **Shared reference (`&T`)**: Allows multiple immutable references to the same data simultaneously. **Mutable reference (`&mut T`)**: Allows only one mutable reference to the data at any given time. The core rule is: you can have *either* one mutable reference *or* any number of immutable references, but not both simultaneously.

**R4** — `Result<T, E>` is an enum representing an operation that might succeed (`Ok(T)`) or fail (`Err(E)`). `Option<T>` is an enum representing a value that might be present (`Some(T)`) or absent (`None`). The `?` operator is syntactic sugar for propagating errors or unwrapping `Option`s. If the expression it operates on is `Err(E)` or `None`, it immediately returns that error or `None` from the current function.
File reading example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> Result<String, io::Error> {
    let mut file = File::open(path)?; // Propagates io::Error if file not found
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates io::Error if read fails
    Ok(contents)
}
```

**R5** — **`Box<T>`**: A smart pointer that allocates data on the heap, giving the type a known, fixed size at compile time. Used for recursive types or when you need to put a trait object on the stack. **`Rc<T>` (Reference Counted)**: Allows multiple owners of the same data on the heap. It uses reference counting for automatic memory management. **`Arc<T>` (Atomic Reference Counted)**: Similar to `Rc<T>` but uses atomic operations, making it safe to share ownership across multiple threads. Use `Box` for single heap allocation; `Rc` for single-threaded shared ownership; `Arc` for multi-threaded shared ownership.

**R6** — Traits define shared behavior (like interfaces). They specify a set of methods that a type must implement. They are similar to Go interfaces in that they define a contract. A **trait object (`dyn Trait`)** is a dynamically dispatched pointer (like `Box<dyn Trait>`) that holds any type implementing the trait, allowing for runtime polymorphism. A **generic with a trait bound (`T: Trait`)** is statically dispatched; the compiler generates specialized code for every concrete type used, resulting in zero runtime overhead.

**R7** — This fails because the compiler cannot guarantee that the returned reference (`&str`) will remain valid as long as the caller uses it. The lifetime of the returned reference is tied to the shorter of the two input references (`x` or `y`). If the function returns a reference to `x`, but `x` goes out of scope before the caller, the reference becomes a dangling pointer.
Fix: We must annotate the function signature with a lifetime parameter, ensuring the output reference lives as long as the shorter of the two inputs:
```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

**R8** — **`Send`**: A marker trait indicating that a type can be safely transferred (sent) ownership across thread boundaries. **`Sync`**: A marker trait indicating that a type can be safely referenced across thread boundaries (i.e., `&T` where `T: Sync` is safe to share between threads). You cannot send an `Rc<T>` across threads because its internal reference count is not atomic, leading to race conditions during counting. `Arc<T>` is safe for concurrent use because its internal reference count uses atomic operations, ensuring thread-safe increments and decrements.

**R9** — Rust's async/await is built on the concept of `Future`s. A `Future` is a trait representing a value that *might* be available at some point in the future. When you `.await` a future, you are essentially pausing the current task until the future completes, yielding control back to the executor. The **executor** (like Tokio) is the runtime environment responsible for polling these futures. It manages the state machines of the futures and drives them forward when they are ready (e.g., when I/O completes). This differs from Go's goroutines because Rust futures are *cooperative* (they must explicitly yield control via `.await`), whereas Go's goroutines are managed preemptively by the scheduler.

**R10** — `unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. Three things you can do: 1. Dereference raw pointers (`*const T`, `*mut T`). 2. Call `unsafe` functions or methods. 3. Access or modify mutable static variables. Unsafe code is justified when interfacing with C libraries (FFI), implementing highly optimized data structures, or when the programmer can mathematically prove that the safety invariants will be maintained.

**R11** — Pattern matching uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches. `if let` is syntactic sugar used to conditionally destructure a value if it matches a specific pattern, but it only handles one case. `match` is exhaustive; the compiler forces you to handle *every* possible variant of the enum or pattern, preventing runtime errors from unhandled states.

**R12** — `Vec<T>` is a dynamically sized, heap-allocated, growable collection. An array `[T; N]` has a fixed size $N$ known at compile time and is typically allocated on the stack. When `Vec<T>` is pushed beyond its current capacity, it allocates a new, larger contiguous block of memory (often doubling the capacity), copies all existing elements to the new location, and then deallocates the old memory.

**R13** — Rust enums are powerful because they can hold data associated with each variant (they are sum types). Unlike C/Java enums (which are usually just integer constants), Rust enums can be complex data structures. `Option<T>` is an enum with two variants: `Some(T)` (contains a value) and `None` (contains no value). Rust avoids null by using `Option<T>`, forcing the programmer to explicitly handle the absence of a value at compile time, eliminating null pointer dereference errors.

**R14** — An `impl` block defines methods and associated functions for a specific type. **`&self`**: Borrows the instance immutably; methods can read the data but not change it. **`&mut self`**: Borrows the instance mutably; methods can read and modify the data. **`self`**: Takes ownership of the instance; the method consumes the instance. Associated functions (like `String::new()`) are functions associated with the type but do not take `self` as an argument; they are called using the type name.

**R15** — A derive macro is a procedural macro that automatically implements standard traits for a struct or enum based on its definition. Examples: `#[derive(Debug)]` allows printing the struct nicely; `#[derive(Clone)]` implements deep copying; `#[derive(PartialEq)]` implements equality checks. You cannot derive a trait if the type contains fields that do not implement the required trait (e.g., you cannot derive `Clone` if one of your fields is a raw pointer or a type that doesn't implement `Clone`).

**R16** — `Cow<'a, T>` (Clone On Write) is a smart pointer that can hold either an owned value (`T`) or a borrowed reference (`&'a T`). It is useful when you frequently receive data that you might need to modify, but often don't. If you only read the data, it uses the cheap reference (`&'a T`). If you attempt to modify it, `Cow` automatically clones the data into an owned `T` internally, allowing the modification to proceed safely. This avoids unnecessary allocations when the data is only read.

**R17** — Rust's module system organizes code into hierarchical units. `mod` declares a module (which can be a file or a block). `use` brings items from other modules into the current scope to avoid fully qualified paths. `pub` makes items accessible outside the current module. The file system maps to modules: a file named `foo.rs` typically defines the `foo` module. The major change in Rust 2018 was the introduction of the `lib.rs` and `main.rs` files as the primary entry points for library and binary crates, respectively, standardizing the module structure.

**R18** — `Pin<T>` is a wrapper that guarantees that a value `T` will not be moved in memory after it has been pinned. This is crucial for types that contain self-references (where a part of the struct points back to another part of the same struct) or for async/await futures. If a future is moved in memory while it is suspended, its internal state (which might hold a reference to its own location) becomes invalid. `Unpin` is a marker trait indicating that a type *can* be safely moved in memory.

**R19** — **Declarative macros (`macro_rules!`)** are pattern-matching macros that operate on tokens (like a sophisticated `switch` statement). They are simple and compile-time only. **Procedural macros** (derive, attribute, function-like) are complex macros written as Rust code that run during compilation. They can inspect and transform the Abstract Syntax Tree (AST). **Hygiene rules** prevent macro expansions from accidentally capturing or interfering with identifiers defined by the user in the surrounding code, ensuring that macro-generated code is isolated and safe.

**R20** — Zero-cost abstractions mean that high-level language features (like generics or iterators) compile down to machine code that is as fast as if the programmer had written the equivalent low-level code by hand. **Generics** achieve this via **monomorphization**: the compiler generates a specific version of the code for every concrete type used, avoiding runtime type checks. **Trait static dispatch** (using generics) resolves method calls at compile time, similar to C++ templates. **Iterators** provide a clean, composable interface that often compiles down to highly optimized loops, avoiding intermediate allocations.
