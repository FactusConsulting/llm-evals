## JavaScript / TypeScript (20 questions)

**JS1** — `var` is function-scoped and subject to hoisting (initialized as `undefined`). `let` and `const` are block-scoped. `const` requires initialization and cannot be reassigned. Hoisting is JavaScript's behavior of moving declarations to the top of their scope during compilation, but only the declaration, not the assignment.

**JS2** — The Event Loop is the mechanism that monitors the call stack and queues to manage asynchronous operations in JavaScript. The **Call Stack** executes synchronous code. When an async operation (like `setTimeout` or a Promise resolution) completes, its callback is placed into the **Macrotask Queue** (e.g., `setTimeout`, I/O). Microtasks (e.g., Promise resolutions, `queueMicrotask`) are prioritized and are processed entirely from the **Microtask Queue** *after* the current synchronous code finishes but *before* the Event Loop checks the Macrotask Queue again.

**JS3** — A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). Practically, it allows an inner function to access variables from its outer function even after the outer function has finished executing. The classic for loop closure bug occurs because the loop variable (`i`) is shared across all iterations; when the callbacks execute, `i` has reached its final value. The fix is to use `let` in the loop declaration (`for (let i = 0; ...)`), which creates a new binding for `i` in each iteration.

**JS4** — A **Promise** is an object representing the eventual completion (or failure) of an asynchronous operation. **`async/await`** is syntactic sugar built on top of Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()`, while with `async/await`, standard `try...catch` blocks are used. **`Promise.allSettled()`** waits for *all* promises to either fulfill or reject, returning an array of status objects describing the outcome of each. **`Promise.all()`** rejects immediately if *any* of the input promises reject.

**JS5** — A **Type** describes the shape of data at runtime and compile time (e.g., `string`, `number`, or a union/intersection). An **Interface** is a compile-time construct used primarily for defining the "shape" of an object, often used for contracts. You use **Interfaces** when defining public APIs or contracts that objects must adhere to. You use **Types** for more complex type manipulation, aliases, or when defining unions/tuples. **Discriminated Unions** are unions where one member has a unique, literal property (the "discriminant"). This allows TypeScript to narrow the type safely using a `switch` statement on that property.

**JS6** — Prototypal inheritance means that objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. **`Object.create(proto)`** creates a new object whose internal `[[Prototype]]` link points directly to the object passed as `proto`. ES6 classes are primarily syntactic sugar over JavaScript's existing prototypal inheritance mechanism; they provide a cleaner, more familiar syntax for developers coming from class-based languages, but under the hood, they still rely on prototype chains.

**JS7** — The `this` keyword refers to the object that is currently executing the function. The 4 binding rules in priority order are: 1. **`new` binding** (when used with a constructor). 2. **Explicit binding** (`.call()`, `.apply()`, `.bind()`). 3. **Implicit binding** (when a function is called as a method of an object). 4. **Default binding** (when called globally/in strict mode, `this` is `undefined` or the global object). `bind()` returns a *new* function with the specified `this` context permanently bound to it. Yes, you can re-bind the returned function, but it's generally redundant.

**JS8** — **`WeakRef`** provides a weak reference to an object. If the object is no longer strongly referenced anywhere else, the garbage collector can reclaim it, and the `WeakRef` will automatically become "dereferenced." **`FinalizationRegistry`** allows you to register a callback function that will be executed *after* the associated object has been garbage collected. You use them to perform cleanup tasks (like removing listeners or closing resources) without preventing the object from being collected. WeakMap keys must be objects because primitives (like strings or numbers) are compared by value, which would prevent the garbage collector from ever seeing the key as "unreferenced."

**JS9** — V8 optimizes JS by compiling code into highly efficient machine code. **Hidden Classes** (or Shapes) allow V8 to represent objects with the same structure (same property order/types) using a single internal structure, enabling fast property lookups. **Inline Caching (IC)** stores the type and location of an object's property access directly at the call site. If the next access matches the cached type, it's extremely fast. **Deoptimization** occurs when V8's assumptions (like an object always having a certain shape) are violated at runtime (e.g., adding a new property to an object that was previously optimized). Coding patterns causing deoptimization include dynamic property addition/deletion, or frequent changes in object structure.

**JS10** — **Tree-shaking** is a dead code elimination technique used by bundlers (like Webpack/Rollup) to eliminate unused exports from modules during the build process. It works effectively with **ES Modules** because `import`/`export` syntax is static; the bundler can statically analyze the dependency graph to see exactly which exports are imported and used. **CommonJS** (`require`/`module.exports`) is harder to shake because `require()` is dynamic—you can conditionally require modules based on runtime logic, making static analysis impossible.

**JS11** — **`null`** represents the intentional absence of any object value (a deliberate assignment of "no value"). **`undefined`** means a variable has been declared but has not yet been assigned a value. `==` performs type coercion before comparison (e.g., `0 == false` is true). `===` performs strict equality, checking both value and type without coercion (e.g., `0 === false` is false). **Nullish coalescing (`??`)** returns the right-hand operand only if the left-hand operand is `null` or `undefined`. **Optional chaining (`?.`)** allows you to safely access deeply nested properties without explicitly checking if each intermediate property exists, returning `undefined` if any part of the chain is nullish.

**JS12** — **`map()`** creates a new array by applying a function to every element in the calling array, returning a new array of the same length. **`filter()`** creates a new array containing only the elements for which the provided testing function returns `true`. **`reduce()`** executes a reducer function on each element, resulting in a single output value. With an initial value, `reduce()` starts the accumulation process with that value. **`flatMap()`** is useful when you need to map over an array and then flatten the result by one level. It combines the functionality of `map()` followed by `flat(1)`.

**JS13** — **Template literals** (backticks `` ` ``) allow for embedded expressions (`${expression}`) and multi-line strings, making string construction cleaner. **Tagged templates** allow a function to intercept and process the string parts and expressions within a template literal. The function receives the array of string segments and the array of interpolated values. Example: For HTML escaping, the tag function would iterate over the string segments and escape HTML special characters (`<` to `&lt;`, etc.) before joining them back together.

**JS14** — **Destructuring** is a syntax that allows you to unpack values from arrays or properties from objects into distinct variables. **Object destructuring** pulls properties out of an object (`const { name, age } = user;`). **Array destructuring** pulls elements out of an array (`const [first, second] = arr;`). **Default values** allow you to assign a fallback value if a property/element is missing (`const { age = 30 } = user;`). **Renaming** allows you to assign the extracted value to a different variable name (`const { name: fullName } = user;`). The **rest operator (`...`)** collects the remaining, un-destructured properties/elements into a new array or object.

**JS15** — **`for...in`** iterates over the *enumerable properties* of an object, including inherited ones (though usually only own properties are intended). **`for...of`** iterates over the *values* of an iterable object (like Arrays, Maps, Sets). You should avoid `for...in` on arrays because it iterates over keys (indices) as strings, and it can iterate over non-index properties added to the array object, leading to unpredictable iteration order and behavior.

**JS16** — **Generics** allow you to write reusable code that can work over a variety of types rather than a single one. **Generic Constraints (`extends`)** restrict the types that can be used with a generic type parameter, ensuring they possess certain properties (e.g., `function identity<T extends { length: number }>(arg: T): T`). **Conditional Types (`T extends U ? X : Y`)** allow you to define a type that resolves to one type or another based on a condition. **`infer`** is used within conditional types to *capture* a type from a complex structure (e.g., inferring the type of the element inside an array).

**JS17** — The **Module System** defines how code dependencies are managed. **CommonJS** (Node.js standard) uses synchronous `require()` to load modules and `module.exports` to expose them. **ES Modules (ESM)** use static `import`/`export` syntax, which is asynchronous and designed for static analysis. Node.js supports both; using `.mjs` or setting `"type": "module"` in `package.json` forces ESM behavior. The `"type": "module"` field tells Node.js to treat `.js` files in that package as ES Modules by default, enabling native `import`/`export`.

**JS18** — TypeScript uses a **Structural Type System**, meaning two types are considered compatible if they have the same structure (the same members with compatible types), regardless of whether they explicitly declare inheriting from each other. **Excess Property Checks** ensure that an object passed to a function or assigned to a type does not contain properties that are *not* defined in that type. They apply when the structure is being checked against a defined type. **`extends`** enforces that the derived type *must* have all members of the base type. **`satisfies`** checks that the type *conforms* to the shape of the type argument, but it does not enforce that the type *is* that shape; it's used for type-checking objects against a shape without altering the object's actual type. **Variance** describes how subtyping relationships behave with generics: `in` (contravariant) means the type can be used as an input parameter (e.g., `string` can be used where `object` is expected). `out` (covariant) means the type can be used as an output return value (e.g., `string` can be returned where `object` is expected).

**JS19** — **Proxy** is an object that wraps another object (the target) and allows you to intercept fundamental operations performed on that target, such as property lookups, assignments, function calls, etc., via "traps" (e.g., `get`, `set`, `apply`). **Reflect** is an API that provides methods to perform these operations in a standardized, reflective way, often used *inside* a Proxy handler to perform the actual operation after interception. Example: For validation, you can use the `set` trap in a Proxy to check if a new value meets certain criteria before allowing the assignment to the target object.

**JS20** — **`SharedArrayBuffer`** is a low-level memory buffer that can be shared between multiple execution contexts (like Web Workers). **`Atomics`** provides methods to perform atomic operations (operations that complete entirely without interruption) on the integer values stored within a `SharedArrayBuffer`. Web Workers communicate by sharing this memory block. **Ordering guarantees** ensure that memory operations appear to happen in a specific sequence across all threads. **`Atomics.wait(typedArray, index, expectedValue)`** pauses the thread until another thread calls `Atomics.notify()` on the same location, provided the value at that index still matches `expectedValue`.

## Bash (20 questions)

**B1** — **`$@`** expands to all positional parameters, with each parameter quoted separately (e.g., if arguments are "a b", `$@` expands to `"a" "b"`). **`$*`** expands to all positional parameters as a single string, separated by the first character of the `$IFS` variable (usually space). **`"$@"`** (quoted) is the safe way to iterate over arguments, preserving spaces in arguments. **`"$*"`** (quoted) treats all arguments as one single string.

**B2** — `set -euo pipefail` enforces strict scripting behavior:
*   **`-e` (errexit):** The script will exit immediately if any command exits with a non-zero status.
*   **`-u` (nounset):** The script will exit immediately if an unset variable is used.
*   **`-o pipefail`:** If any command in a pipeline fails (returns non-zero), the entire pipeline command fails, rather than just returning the status of the last command.

**B3** — **`$(command)`** (Command Substitution) executes the `command` and substitutes its standard output into the current command line. **`command`** executes the command directly. **`$((expression))`** performs arithmetic evaluation within Bash. **`expr`** is an external utility that evaluates expressions; it is generally slower and requires more quoting than Bash's built-in arithmetic expansion.

**B4** — **Process substitution (`<(command)`)** runs a command and makes its standard output available as a temporary file path that the current shell can read from, allowing it to be used as an argument to another command that expects a file. This is useful when a command needs to be treated like a file but its output is generated dynamically. Example: `diff <(ls -1) <(ls -1 | sort)` compares the output of two separate `ls` commands as if they were files.

**B5** — You must use quoting and globbing patterns carefully. The safe way is to use a `while read` loop combined with `find` and `xargs -0`:
`find . -name "* *" -print0 | while IFS= read -r -d $'\0' f; do echo "Processing $f"; done`
`for f in *` is dangerous because if a filename is `My File.txt`, the loop iterates over `My` and `File.txt` separately.

**B6** — A **here document (`<<EOF`)** reads multiple lines of input until it encounters the delimiter (`EOF`) on a line by itself. A **here string (`<<<`)** passes a single string as standard input to a command. **`<<-EOF`** (with a leading hyphen) allows leading tabs in the here document content to be treated as spaces (i.e., it strips leading tabs from the input lines).

**B7** — 1. `cmd > file 2>&1`: Redirect stdout to `file`, then redirect stderr (2) to the same place stdout (1) is currently going (`file`). **Result: Both stdout and stderr go to `file`.**
2. `cmd 2>&1 > file`: Redirect stderr (2) to stdout (1), *then* redirect stdout (1) to `file`. **Result: Both stdout and stderr go to `file`.** (Note: In modern shells, these often behave identically if the redirection order is correct, but the conceptual difference is crucial: in (1), the redirection happens sequentially; in (2), the target of stderr is set *before* the final stdout redirection).
3. `cmd &> file`: This is a shorthand (Bash 4+) that redirects both stdout and stderr to `file` simultaneously.

**B8** — A robust lock function uses `mkdir` because it is atomic (it either succeeds completely or fails completely, preventing race conditions where two processes might try to create a file simultaneously).
```bash
lock_file() {
    local lock_dir="/tmp/mylock_$$"
    if mkdir "$lock_dir" 2>/dev/null; then
        echo "Lock acquired in $lock_dir"
        trap "rmdir $lock_dir" EXIT TERM INT
        # Script logic here
    else
        echo "Could not acquire lock." >&2
        return 1
    fi
}
```
The `trap` ensures that `rmdir` is called upon normal exit (`EXIT`), interruption (`INT`), or termination (`TERM`).

**B9** — **Single quotes (`'...'`)**: Literal interpretation. No variable expansion, no command substitution. Example: `echo 'Hello $USER'` outputs `Hello $USER`. **Double quotes (`"..."`)**: Allows variable expansion (`$VAR`) and command substitution (`$(cmd)`), but prevents word splitting and glob expansion. Example: `echo "Hello $USER"` expands the variable. **No quotes**: Enables both variable expansion *and* word splitting/pathname expansion. Example: `echo $USER` might split if `$USER` contained spaces.

**B10** — File existence: `[ -f file ]` (is a regular file), `[ -d dir ]` (is a directory). Readability: `[ -r file ]`. **`[ ]` (test)** is an external command. **`[[ ]]`** is a Bash keyword/builtin that offers extended features like regex matching (`=~`) and better handling of word splitting, making it generally preferred in modern scripts.

**B11** — **`$?`**: Exit status of the most recently executed foreground command (0 for success). **`$$`**: The Process ID (PID) of the current shell. **`$!`**: The PID of the most recently backgrounded command. **`$#`**: The number of positional arguments passed to the current script/function.

**B12** — Functions are defined using `name() { ... }` or `function name { ... }`. Both are functionally equivalent in modern Bash. To return values, functions typically print the result to standard output, and the calling script captures it using command substitution: `result=$(my_function arg1)`. The function itself returns an exit code (0-255) via `return N`.

**B13** — **`PATH`** is an environment variable containing a colon-separated list of directories where the shell searches for executable commands. Bash resolves commands by iterating through the directories listed in `$PATH` until it finds an executable file matching the command name. A **builtin** command is part of the shell itself (e.g., `cd`, `echo`) and runs internally without spawning a new process. An **external command** is a separate executable file found in a directory listed in `$PATH` (e.g., `grep`, `ls`). You can check using `type command_name`.

**B14** — **`trap`** allows you to specify commands to run when the shell receives a specific signal. You set handlers like `trap 'cleanup_function' EXIT` (runs on normal exit), `trap 'cleanup_function' INT` (runs on Ctrl+C), `trap 'cleanup_function' TERM` (runs on termination signal), and `trap 'cleanup_function' ERR` (runs if a command fails). When multiple signals arrive, the shell processes them sequentially based on its internal signal handling logic, but handlers are executed in the order they are trapped.

**B15** — **Command substitution (`$(cmd)`)** executes a command and substitutes its output. **`xargs`** takes standard input and builds and executes command lines from it. The difference is that `xargs` is designed to efficiently batch inputs into arguments for a command, whereas substitution is for simple string replacement. To handle spaces/newlines safely: `find . -name "*.log" -print0 | xargs -0 -I {} mv {} {}.bak`. **`xargs -P N`** runs up to $N$ processes in parallel, significantly speeding up I/O-bound tasks.

**B16** — **Bash Arrays** are indexed numerically (0, 1, 2...). Declaration: `my_array=(item1 item2)`. Append: `my_array+=("new_item")`. Iterate: `for item in "${my_array[@]}"; do ...`. Length: `${#my_array[@]}`. **Associative Arrays** (requires `declare -A`) map string keys to values. Declaration: `declare -A map`. Set: `map[key]="value"`. Iterate: `for key in "${!map[@]}"; do echo "$key=${map[$key]}"; done`. They are used for dictionary-like structures.

**B17** — A **subshell (`(...)`)** executes commands in a separate, isolated process. Any variables set or modified inside the subshell are lost when it exits. A **group command (`{ ...; }`)** executes commands in the *current* shell environment. Variables modified inside the group persist. Piping into a `while` loop (`command | while read line; do ... done`) runs the loop in a subshell by default, meaning any variables modified inside the loop body are lost when the loop finishes, as the subshell exits.

**B18** — Bash handles signals by intercepting them and executing a handler (if one is trapped) or by terminating the process. **SIGINT** (Interrupt, Ctrl+C) is usually handled gracefully. **SIGTERM** (Terminate) is the standard request for a process to shut down gracefully. **SIGHUP** (Hangup) is often sent when a controlling terminal closes, used to signal configuration reload. **SIGKILL** (Kill) cannot be caught or ignored; the kernel terminates the process immediately. For graceful shutdown, use `trap` to catch `SIGTERM` and `SIGINT`, allowing background processes to finish before the main script exits.

**B19** — This requires splitting the file, processing chunks in parallel, and merging.
1. **Split:** `split -l 10000 large_log.log chunk_` (splits into 10k lines).
2. **Process:** `find . -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c 'process_chunk "$@"' _ {}` (Processes 4 chunks in parallel).
3. **Merge:** `cat chunk_*_processed > final_log.log`.
**Trade-offs:** Parallelism increases throughput for I/O-bound tasks but adds overhead from process creation and context switching. Error propagation is tricky; you must check the exit code of the `xargs` command or check the return status of the function executed by `bash -c`.

**B20** — **`exec`** replaces the current shell process image with a new command, meaning the shell itself is replaced; it does not spawn a child process. This is useful for resource management. `exec 3>file` opens file descriptor 3 and redirects it to `file`. `exec 3>&-` closes file descriptor 3. A **coprocess** allows a parent shell to communicate with a child process using named pipes (FIFOs) without the child process needing to be a background job. You use it when you need bidirectional, persistent communication channels between two related processes within the same shell session.

## PowerShell (20 questions)

**PS1** — **`Write-Output`** sends objects down the pipeline, allowing subsequent cmdlets to process them. This is the standard, pipeline-friendly way. **`Write-Host`** writes directly to the console host, bypassing the pipeline. This is useful for simple, immediate user feedback (like progress messages) but the output cannot be captured or piped further.

**PS2** — The **PowerShell pipeline** passes objects from the output stream of one cmdlet to the input stream of the next. **`ForEach-Object`** (alias `%`) is a cmdlet designed to process objects coming *through* the pipeline. **`foreach` statement** is a language construct used to iterate over a collection (like an array or list) that is already loaded into a variable in memory. Use `ForEach-Object` when processing streaming input; use `foreach` when iterating over a known, finite collection.

**PS3** — **`[PSCustomObject]`** creates a lightweight, dynamic object structure with named properties, ideal for structured output that can be easily piped and consumed by other cmdlets. **`[hashtable]`** is a key-value store, similar to a dictionary, where access is done via keys (e.g., `$ht['Key']`). Use `[PSCustomObject]` for structured data intended for the pipeline; use `[hashtable]` for temporary, associative data storage within a script block. Conversion: `[PSCustomObject]@{Key = $ht.Value}` or `$ht | ConvertTo-Json | ConvertFrom-Json`.

**PS4** — PowerShell distinguishes between **Terminating Errors** (which stop the current operation, like a cmdlet failing to find a resource) and **Non-Terminating Errors** (which are warnings or informational messages that allow the script to continue). **`-ErrorAction`** controls how a specific command handles errors (e.g., `Stop`, `Continue`, `SilentlyContinue`). **`$ErrorActionPreference`** sets the default behavior for *all* commands in the current scope. **`try/catch`** allows you to explicitly trap and handle terminating errors, overriding the default `$ErrorActionPreference` for the block.

**PS5** — **Splatting (`@params`)** is a technique where you pass a hashtable containing parameter names as keys and values as values to a cmdlet. This allows you to dynamically build and pass complex sets of parameters without hardcoding them. Example: `$params = @{Path = "C:\Logs"; LogLevel = "Error"}`. `Get-Service @params`. This differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named arguments for the target cmdlet.

**PS6** — **PowerShell Remoting** allows management of remote computers. **`Invoke-Command -ComputerName`** executes a script block on a remote machine, returning the results to the local session. **`Enter-PSSession`** establishes an interactive, persistent connection to the remote machine, allowing you to run commands *as if* you were logged into that machine. It primarily uses **WinRM (Windows Remote Management)** on Windows. While SSH is used for PowerShell Core/7+ on Linux/macOS, WinRM is the standard protocol for Windows-to-Windows remoting.

**PS7** — The issue arises because when a function returns an empty array (`@()`), PowerShell often treats the return value as `$null` in certain contexts, or the pipeline might not correctly interpret the empty collection. When you append to an empty array (`$result += "one"`), PowerShell often has to re-evaluate the entire array, which is inefficient. The correct pattern is to use the pipeline or initialize the array correctly: `return @("one")` or `return "one"`. If the function returns nothing, it returns `$null`, which is distinct from an empty array.

**PS8** — A **`[scriptblock]`** is a block of code that can be passed as an argument to a cmdlet or function. A **function** is a named, reusable block of code that can accept parameters and return values. You pass a scriptblock to a remote session using the `-ScriptBlock` parameter of `Invoke-Command`. The **double-hop problem** occurs when trying to pass complex, non-serializable objects (like active session objects) across remote boundaries. This is solved by using `Invoke-Command -ArgumentList` to pass simple data types, or by using CredSSP for more complex authentication/session management.

**PS9** — **`@()`** creates an empty array object. **`[array]`** is a type accelerator used to explicitly cast a variable to an array type. To force a single result into an array, wrap it: `@[my_string]`. Indexing `$null` throws a terminating error. Indexing an empty array (`$emptyArray[0]`) returns `$null` without error.

**PS10** — **`-eq`** (equals), **`-ne`** (not equals), **`-like`** (wildcard matching, uses `*` and `?`), **`-match`** (regex matching), **`-contains`** (checks if a specific item exists in an array), **`-in`** (checks if a value exists within a list of values). The case-sensitive variants (`-ceq`, `-clike`, etc.) perform the same comparison but require an exact case match. **`-contains`** checks if the *entire item* is present in the collection; **`-in`** checks if the item matches any of the values provided in the list.

**PS11** — A **PowerShell module** is a collection of cmdlets, functions, variables, and data that can be imported into a PowerShell session to extend functionality. A **script module (`.psm1`)** is a script file containing functions/cmdlets. A **manifest module (`.psd1`)** is a metadata file that describes the module (version, dependencies, required PowerShell version). A **binary module** contains compiled code (like DLLs). `Import-Module` loads the module's definitions into the current session's scope, making its contents available.

**PS12** — **String interpolation** allows embedding variable values directly into a string using double quotes. Example: `"The user is $username."`. Single quotes (`'...'`) treat everything literally. Double quotes (`"..."`) allow expansion. To include expressions, wrap them in curly braces: `"The result is $($variable * 2)."`. A **here-string (`@"...@"`)** allows multi-line strings where the content is treated literally (like single quotes), but it supports variable expansion if double quotes are used around the entire block.

**PS13** — **`Get-Member`** returns the properties and methods available on an object. It is the primary tool for introspection. **Properties** are data fields (values). **Methods** are executable functions associated with the object. **NoteProperties** are properties that are not standard object properties but are attached via the `[System.Management.Automation.PSObject]` structure. **`Select-Object`** is used to *choose* which properties to display or rename. **`Where-Object`** is used to *filter* objects based on a condition applied to their properties.

**PS14** — PowerShell classes (introduced in v5) allow object-oriented programming. They are similar to C# classes but are built on top of the .NET framework. Limitations include that they are not as strictly typed as C# classes, and while they support inheritance, the ecosystem is often more functional. You use a **class** when you need to model a complex entity with state and behavior (e.g., a `User` object). You use a **function** when you need a reusable piece of logic that operates on input data without maintaining persistent state.

**PS15** — **`CmdletBinding()`** is an attribute that transforms a standard function into an advanced function, giving it built-in features like parameter validation, pipeline support, and error handling. **`SupportsShouldProcess`** enables the `-WhatIf` parameter, allowing the cmdlet to simulate actions without actually executing them. **`DefaultParameterSetName`** specifies which parameter set is used if none is explicitly chosen. **`ValueFromPipeline`** allows the cmdlet to accept input objects from the pipeline and assign them to a parameter. **Begin/Process/End blocks** define lifecycle stages: `Begin` runs once before processing starts; `Process` runs for each incoming object; `End` runs once after all objects are processed.

**PS16** — **Providers** are mechanisms that allow PowerShell cmdlets (like `Get-ChildItem`) to interact with various data sources using a unified interface. The **FileSystem Provider** interacts with local drives. The **Registry Provider** allows you to treat registry keys like folders/files (e.g., `Get-ChildItem HKCU:\Software`). The **Certificate Provider** accesses certificate stores. The **Environment Provider** accesses environment variables. This abstraction allows `Get-ChildItem` to work consistently across disparate systems.

**PS17** — A **`[runspace]`** is an execution context that hosts PowerShell code. A **`[runspacepool]`** manages a pool of runspaces to handle concurrent requests efficiently. A **`[powershell]`** object is the executable instance. **Thread safety** is managed by ensuring that shared resources are accessed safely, often by using runspaces. **`ForEach-Object -Parallel` (v7+)** uses the runspace pool internally to execute script blocks concurrently across multiple threads/processes. Manual runspace management is used for fine-grained control over resource allocation and lifecycle.

**PS18** — **PSScriptAnalyzer** is a static code analysis tool that checks PowerShell scripts against a defined set of best practices and coding standards. It enforces rules (e.g., "Always use `[CmdletBinding()]`," "Avoid using global variables"). **Severity levels** (e.g., Error, Warning, Information) dictate how critical the violation is. **Custom rules** allow organizations to define their own specific standards. Rules can be suppressed using `#Requires -ErrorAction SilentlyContinue` or specific analyzer directives. It integrates into CI/CD by running as a pre-commit or build step, failing the build if critical rules are violated.

**PS19** — **`$using:` scope** is used when passing variables into background jobs or parallel operations. It serializes the variable's *value* at the time the job starts, ensuring the remote/parallel job gets a snapshot of the data. **`$args/-ArgumentList`** is used for passing parameters to remote sessions (`Invoke-Command`). **Serialization limits (CLIXML depth)** restrict the complexity of objects that can be passed across the WinRM boundary. Deeply nested objects or objects containing complex, non-serializable references can fail to transfer, leading to errors or data loss.

**PS20** — **Desired State Configuration (DSC)** is a management framework that allows administrators to define the *desired state* of a system (e.g., "IIS must be installed," "Registry key X must equal Y") and ensures the system remains in that state. **Configurations** define the desired state. **Resources** are the specific components that implement the state logic (e.g., the `Service` resource ensures a service is running). The **Local Configuration Manager (LCM)** is the engine on the target node that reads the configuration and applies the necessary resources to achieve the desired state. In modern IaC, DSC has been largely superseded by tools like Ansible, Chef, and Terraform, which offer broader orchestration capabilities.
