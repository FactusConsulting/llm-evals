## OpenTofu / Terraform Answers

**T1 — Easy: What is the difference between tofu plan and tofu apply?**
`tofu plan` calculates the difference between the desired state defined in the configuration files and the current state recorded in the state file. It outputs an execution plan showing exactly what actions (create, update, delete) will be taken without making any changes. `tofu apply` executes the actions detailed in the plan, modifying the infrastructure to match the configuration.

**T2 — Easy: What is state in OpenTofu, and why is remote state important?**
State is a file that maps the resources defined in your configuration to the real-world infrastructure objects created by the provider (e.g., mapping a resource block to a specific AWS EC2 instance ID). Remote state (e.g., stored in S3 or Azure Blob Storage) is crucial because it allows teams to collaborate safely, provides a single source of truth for the infrastructure state, and enables state locking to prevent concurrent modifications that could corrupt the infrastructure.

**T3 — Medium: Explain the difference between count and for_each. When is for_each preferred?**
`count` creates a list of identical resources based on a numeric value. It is best for creating multiple instances of the *same* resource type where the identity doesn't matter (e.g., 3 identical load balancers). `for_each` creates a map or set of resources, where each instance is uniquely identified by a key (string or map). `for_each` is preferred when the resources need unique identifiers or when you need to manage different configurations for each instance (e.g., creating VMs named `web1`, `web2`, `web3`).

**T4 — Medium: What happens if you manually change a resource outside of OpenTofu (e.g., modify a VM in the cloud console)? How does OpenTofu detect and handle this?**
OpenTofu detects this drift during `tofu plan`. It compares the configuration's desired state against the actual state retrieved from the cloud provider API. If a manual change is detected, OpenTofu will report a difference, showing that the resource's current state does not match the configuration. By default, `tofu apply` will attempt to reconcile this drift, often by reverting the manual change to match the configuration, or by prompting the user if the change is significant.

**T5 — Medium: Write a minimal OpenTofu snippet that creates 3 identical VMs using for_each over a toset(["web1", "web2", "web3"]).**
```hcl
resource "aws_instance" "web_servers" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-0abcdef1234567890"
  instance_type = "t2.micro"

  tags = {
    Name = each.key
  }
}
```

**T6 — Hard: Explain the difference between terraform_remote_state data source and output values when sharing data between root modules. What is the recommended alternative and why?**
**Output Values:** Outputs are designed to expose values *from* the current module to consumers (other modules or the root module). They are generally used for exposing final, derived values.
**`terraform_remote_state` Data Source:** This data source is used to read the state file of *another*, separately managed remote state backend.
**Recommended Alternative:** The recommended alternative is to use **Module Outputs** combined with **Module Inputs**. If Module A creates a resource and Module B needs its ID, Module A should output the ID, and Module B should consume it as an input variable. This keeps dependencies explicit and avoids coupling modules to the state file of another module, leading to cleaner, more portable, and less brittle infrastructure code.

**T7 — Hard: You have a module that provisions an RKE2 cluster. The kubeconfig output depends on a null_resource with a provisioner "remote-exec". The dependent resources fail because the output is empty on first apply. Explain why and how to fix it.**
The failure occurs because OpenTofu's dependency graph evaluates outputs *before* the provisioner script within the `null_resource` has successfully executed and populated the output value. Provisioners run *during* the resource lifecycle, not before the output is read.
**Fix:** The correct fix is to use an **explicit dependency** via `depends_on`. The resource that consumes the kubeconfig must explicitly list the `null_resource` (or the resource that generates the kubeconfig) in its `depends_on` block. This forces OpenTofu to wait for the provisioner to complete successfully before attempting to read the output.

**T8 — Medium: What is terraform import (or tofu import), and what are its limitations? How does the import block (1.5+) improve on the CLI command?**
`tofu import` allows you to bring existing, manually created infrastructure resources under the management of your OpenTofu configuration without having to write the configuration code first.
**Limitations:** It only imports the *state* of the resource; it does not generate the corresponding HCL configuration code. You still need to write the configuration manually afterward.
**Improvement (Import Block):** The import block (e.g., `resource "aws_instance" "example" { ... } import = ["i-12345"]`) allows you to define the resource block *and* specify the import ID in one place. This is superior because it immediately links the configuration to the state, making the code self-documenting and easier to manage than relying solely on a separate CLI command.

**T9 — Easy: What is a variable in OpenTofu, and what is the difference between variable (input) and output?**
A **variable** (input) is a placeholder defined in the configuration that allows users to pass dynamic values into the module or root configuration at runtime (e.g., `var.instance_type`). An **output** is a value exposed *from* a module or resource that can be consumed by other parts of the configuration (e.g., `output "instance_id" { value = aws_instance.example.id }`). Inputs define what the module needs; outputs define what the module provides.

**T10 — Easy: What is a provider in OpenTofu? What happens if you run tofu plan without running tofu init first?**
A provider is a plugin that enables OpenTofu to interact with a specific API or service (e.g., AWS, Azure, Kubernetes). It contains the logic to read, create, update, and delete resources for that service. If you run `tofu plan` without `tofu init`, OpenTofu will fail because it has not downloaded the necessary provider plugins specified in the configuration, and thus cannot communicate with the target API.

**T11 — Easy: What is the .terraform.lock.hcl file, and why should it be committed to version control?**
The `.terraform.lock.hcl` file records the exact, specific versions (including checksums) of every provider and module dependency that OpenTofu downloaded during `tofu init`. It should be committed to version control to ensure **reproducibility**. If it is not committed, different team members or CI/CD pipelines might download slightly different, potentially incompatible versions of providers, leading to "works on my machine" issues.

**T12 — Easy: What does tofu destroy do, and how do you target a single resource for destruction?**
`tofu destroy` tears down all infrastructure resources managed by the current state file. To target a single resource, you use the `-target` flag followed by the resource address (e.g., `tofu destroy -target=aws_instance.web_servers["web1"]`).

**T13 — Easy: What is a data source in OpenTofu? Give an example of when you would use one instead of a managed resource.**
A data source is a block that allows OpenTofu to fetch information about existing infrastructure that is *not* managed by the current configuration. It reads data from the provider's API.
**Example:** You want to launch a new EC2 instance, but you need to use the latest Amazon Linux AMI ID. Instead of hardcoding the AMI ID (which changes frequently), you use a `data "aws_ami"` source to dynamically fetch the latest official AMI ID for your region.

**T14 — Medium: Explain the difference between locals and variable blocks. When should you use locals instead of input variables?**
**Variables** are external inputs provided by the user or defined globally to configure the module (e.g., `var.environment = "staging"`). **Locals** are internal, computed values defined *within* a module or configuration block to simplify expressions, reuse complex logic, or derive values from inputs (e.g., `locals { region_name = var.aws_region }`).
**When to use locals:** Use locals when you need to perform transformations, calculations, or create aliases based on existing inputs *within* the scope of the configuration, rather than needing the value to be configurable externally.

**T15 — Medium: What is the lifecycle block in a resource? Explain the create_before_destroy, prevent_destroy, and ignore_changes options with a use case for each.**
The `lifecycle` block controls how OpenTofu manages the resource during updates.
*   **`create_before_destroy`:** Ensures a new replacement resource is created *before* the old one is destroyed. **Use Case:** Database migrations or critical services where downtime must be avoided during replacement.
*   **`prevent_destroy`:** Prevents the resource from being deleted via `tofu destroy` or `tofu apply`. **Use Case:** Production databases or critical network components that should never be accidentally removed.
*   **`ignore_changes`:** Tells OpenTofu to ignore specific attributes when calculating drift or applying changes. **Use Case:** When an external system (like a monitoring agent) modifies a tag or metadata field that you do not want OpenTofu to manage or revert.

**T16 — Medium: What is a moved block in OpenTofu, and how does it help when refactoring module structure without destroying and recreating resources?**
The `moved` block (introduced in later versions) allows you to explicitly tell OpenTofu that a resource address has changed during a refactoring operation (e.g., moving a resource from one module to another, or renaming it). By using `moved`, you instruct the state file to map the old resource address to the new one, allowing you to refactor the HCL code without triggering a destructive replacement of the underlying cloud resource.

**T17 — Hard: Explain how OpenTofu's dependency graph works. What is the difference between implicit and explicit dependencies? How does depends_on affect parallelism, and why should it be used sparingly?**
The dependency graph is a directed acyclic graph (DAG) that OpenTofu builds to determine the correct order of operations.
*   **Implicit Dependency:** Occurs when one resource references an attribute of another resource (e.g., `aws_instance.a.id` is used in `aws_security_group.b.ingress`). OpenTofu automatically infers this dependency.
*   **Explicit Dependency:** Defined using `depends_on = [resource_address]`. This forces an ordering even if no attribute reference exists.
**Impact on Parallelism:** Explicit dependencies force sequential execution. If you use `depends_on` unnecessarily, you artificially constrain the DAG, preventing OpenTofu from running independent resources concurrently, which slows down the apply process. It should be used sparingly, only when implicit dependencies are insufficient.

**T18 — Hard: You have an OpenTofu codebase with 200+ resources and tofu plan takes over 10 minutes. Identify at least 4 strategies to reduce plan time and explain the tradeoffs of each.**
1.  **Modularization:** Break the large codebase into smaller, focused modules. *Tradeoff:* Increases complexity in managing module dependencies and state boundaries.
2.  **Targeted Operations:** Use `tofu plan -target=...` to only plan changes for specific, affected components. *Tradeoff:* Requires deep knowledge of the infrastructure and can lead to state drift if targets are missed.
3.  **State Splitting/Isolation:** Separate resources into different state files (e.g., one state for networking, one for compute). *Tradeoff:* Increases operational overhead (managing multiple state files) but drastically reduces the scope of each plan/apply.
4.  **Provider Configuration Optimization:** Ensure providers are configured efficiently (e.g., using specific regions, caching credentials). *Tradeoff:* Requires careful configuration tuning and might limit flexibility.

**T19 — Hard: Explain the OpenTofu state locking mechanism. What happens if a lock is not released (e.g., a CI pipeline crashes mid-apply)? How do you manually break a lock, and what are the risks?**
State locking ensures that only one operation (plan or apply) can modify the state file at any given time, preventing race conditions. It is typically implemented via a backend feature (like DynamoDB in S3).
**If a lock is not released:** The state file becomes locked indefinitely. Any subsequent `tofu plan` or `tofu apply` will fail immediately with a "state is locked" error.
**Manually Breaking a Lock:** You use the backend-specific CLI command (e.g., `aws dynamodb delete-item` or a specific backend command) to force the lock release.
**Risks:** Manually breaking a lock is dangerous. If the previous operation was mid-way through an apply, the state file is inconsistent, and forcing the lock release allows a new operation to proceed on corrupted state, leading to infrastructure corruption.

**T20 — Hard: You need to migrate an existing OpenTofu project from a local state backend to an S3-compatible remote backend with state locking via DynamoDB. Describe the step-by-step process, including what happens to the existing state file and how to verify the migration succeeded.**
1.  **Configure New Backend:** Update the `backend` block in the configuration to point to the S3 bucket and DynamoDB table.
2.  **Initialize with Migration:** Run `tofu init -migrate`. This command reads the local state, uploads it to the new remote backend, and creates the necessary lock mechanism.
3.  **Verify State:** Run `tofu state list` to confirm all resources are present in the remote state.
4.  **Test Operations:** Run `tofu plan` and `tofu apply`. If these succeed and the state is correctly updated in S3, the migration is successful.
5.  **Cleanup:** Once verified, the local state file can be safely deleted.

## Ansible Answers

**A1 — Easy: What is the difference between an Ansible playbook, a role, and a task?**
*   **Task:** The smallest unit of work in Ansible. It is a specific instruction telling Ansible what to do (e.g., "install nginx," "copy this file"). Tasks are defined within playbooks or roles.
*   **Playbook:** A YAML file that defines a set of plays. A play describes a set of tasks to be executed against a specific group of hosts defined in the inventory. It is the primary execution file.
*   **Role:** A standardized, reusable structure for organizing related tasks, handlers, variables, and templates. Roles promote best practices and modularity, allowing complex deployments to be broken down logically (e.g., a `webserver` role).

**A2 — Easy: What is ansible_facts and how do you access the OS family of a target host?**
`ansible_facts` is a dictionary containing gathered information about the target host system (OS version, memory, network interfaces, etc.), collected automatically by Ansible during the initial connection phase. To access the OS family, you would typically use the `ansible_facts['os_family']` variable in a task or template.

**A3 — Medium: Explain the difference between command, shell, and raw modules. When would you use each?**
*   **`command` module:** Executes a command directly. It is generally safer as it does not interpret shell features (like pipes `|` or redirects `>`). Use this for simple, non-shell-dependent commands.
*   **`shell` module:** Executes commands through the system's shell (e.g., `/bin/sh`). Use this when you need shell features like piping, environment variable expansion, or redirection.
*   **`raw` module:** Executes a command directly on the remote machine without Ansible's abstraction layer. It is the lowest level and should be used sparingly, usually only when interacting with very specific, non-standard remote APIs or tools.

**A4 — Medium: How does Ansible handle idempotency? Give an example of a task that is idempotent and one that is NOT.**
Idempotency means that running the same task multiple times will result in the same system state without causing unintended side effects after the first successful run. Ansible achieves this by using modules that check the current state before making changes.
*   **Idempotent Example:** Using the `ansible.builtin.package` module to install `nginx`. If Nginx is already installed, the module reports "ok" and makes no changes.
*   **Non-Idempotent Example:** Using the `ansible.builtin.command` module to run `echo "hello" >> /tmp/log.txt`. If run twice, the file will contain "hello" twice.

**A5 — Medium: Write an Ansible task that installs htop only on Debian-based systems and epel-release + htop on RedHat-based systems using a single task file.**
```yaml
- name: Install htop based on OS family
  ansible.builtin.package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else ['epel-release', 'htop'] }}"
    state: present
  when: ansible_os_family in ['Debian', 'RedHat']
```

**A6 — Hard: Explain Ansible's variable precedence order. Where do group_vars, host_vars, extra_vars, role defaults, and set_fact land in priority?**
Ansible resolves variables based on a strict precedence order, where later sources override earlier ones. The general order (highest priority listed last) is:
1.  **Role Defaults:** Variables defined within the `defaults/main.yml` of a role.
2.  **Inventory Variables:** Variables defined in `group_vars/` or `host_vars/`.
3.  **Extra Variables:** Variables passed at runtime via the `-e` flag or `extra_vars` in the command line.
4.  **Set Fact/Register:** Variables set dynamically during playbook execution using `set_fact` or registered variables.

**A7 — Hard: You need to deploy an RKE2 agent on 50 nodes. The first 3 nodes must complete before the rest start. How do you structure this in Ansible? Cover: serial, inventory groups, and wait_for.**
1.  **Inventory Grouping:** Divide the 50 nodes into two groups: `initial_batch` (3 nodes) and `remaining_nodes` (47 nodes).
2.  **Serial Execution:** Use the `serial` keyword in the play definition to control batch size.
3.  **Structure:**
    *   Run the play targeting `initial_batch` with `serial: 3`.
    *   After the first play completes, run a second play targeting `remaining_nodes` with `serial: 1` (or a larger number if desired, but the first batch must finish).
    *   *Note on `wait_for`*: `wait_for` is used to wait for a service to become available *after* deployment, not to control the start order of subsequent plays. The `serial` keyword controls the execution flow across hosts.

**A8 — Medium: What is ansible-vault? How do you encrypt a single variable inside a vars file without encrypting the entire file?**
`ansible-vault` is a tool used to encrypt sensitive data (passwords, API keys) within Ansible files.
**Encrypting a single variable:** You can use the vault command to encrypt only the specific line or variable definition within a file, leaving the rest of the file unencrypted. For example, you can use `ansible-vault encrypt var_name=secret_value --vault-password-file ~/.vault_pass`. This ensures that only the sensitive data is protected, while configuration details remain readable.

**A9 — Easy: What is an Ansible inventory file? What is the difference between a static inventory and a dynamic inventory?**
An inventory file defines the hosts (servers) that Ansible will manage and groups them logically.
*   **Static Inventory:** A manually maintained file (INI or YAML format) where you list every host and assign it to a group (e.g., `[webservers]\nweb1.example.com`).
*   **Dynamic Inventory:** A script or plugin that connects to a source (like AWS, Azure, or a CMDB) at runtime to fetch the current list of hosts and their metadata. This is essential for cloud environments where hosts are constantly being created or destroyed.

**A10 — Easy: How do you run a single ad-hoc Ansible command to check disk space on all hosts in the webservers group?**
```bash
ansible webservers -m ansible.builtin.command -a "df -h"
```

**A11 — Easy: What is a handler in Ansible, and how does it differ from a regular task? How do you trigger a handler?**
A handler is a special task that is only executed when explicitly notified by another task.
**Difference:** Regular tasks run sequentially as part of the play flow. Handlers are deferred; they wait until the entire play finishes (or until they are notified) and then run, ensuring that tasks complete before service restarts occur.
**Triggering:** A task triggers a handler using the `notify` keyword (e.g., `notify: restart nginx`). The handler definition itself is placed in the `handlers/main.yml` file of the role or playbook.

**A12 — Easy: What is the ansible.cfg file used for? Name at least 3 settings commonly configured there.**
The `ansible.cfg` file is a configuration file that controls how Ansible behaves globally across all runs. It allows users to override default settings without modifying playbooks.
**Common Settings:**
1.  `inventory`: Specifies the path to the inventory file.
2.  `remote_user`: Sets the default SSH user to connect as.
3.  `host_key_checking`: Controls whether Ansible verifies the host keys during connection.

**A13 — Easy: What is the register keyword in Ansible, and how do you use the registered variable in a subsequent task?**
The `register` keyword captures the entire return value (stdout, stderr, status, etc.) of a task and stores it in a variable.
**Usage:** If a task is registered as `my_result`, you can access its output in a subsequent task using Jinja2 templating, such as `{{ my_result.stdout }}` or `{{ my_result.rc }}` (return code).

**A14 — Medium: Explain the difference between include_tasks and import_tasks. When would you use one over the other, and how does this affect conditional evaluation?**
*   **`import_tasks`:** Reads tasks from a file but **does not** merge the task file into the current play's execution context. It executes the imported tasks as a separate, self-contained unit.
*   **`include_tasks`:** Reads tasks from a file and **merges** them directly into the current play's execution flow.
**Conditional Evaluation:** `include_tasks` allows the imported tasks to inherit the current play's variables and conditions, meaning they can be conditionally evaluated based on the context of the calling play. `import_tasks` runs the imported tasks in isolation, making conditional inheritance more complex.

**A15 — Medium: What is Ansible Galaxy, and how do you use a requirements.yml file to install roles and collections from it?**
Ansible Galaxy is a community repository where users share reusable Ansible content (roles and collections).
**Using `requirements.yml`:** You create a `requirements.yml` file listing the required roles/collections and their sources (e.g., GitHub, Ansible Galaxy). You then run `ansible-galaxy install -r requirements.yml`. This downloads and installs the necessary dependencies into a local cache, making them available for use in your playbooks.

**A16 — Medium: Explain how Ansible connection plugins work. What is the difference between ssh, local, and network_cli connection types? When would you use each?**
Connection plugins define the mechanism Ansible uses to communicate with the target host.
*   **`ssh` (Default):** Uses SSH to connect to a remote machine. Used for managing standard Linux/Unix servers.
*   **`local`:** Executes tasks directly on the Ansible control node itself. Used for tasks that don't require remote access (e.g., running local scripts, managing the control machine).
*   **`network_cli`:** Connects to network devices (routers, switches) using command-line protocols (like Telnet or SSH CLI). Used for network automation where standard OS modules are insufficient.

**A17 — Hard: Explain how Ansible's delegate_to and run_once work. Give a practical example where you need to run a task on the control node (localhost) once, using data gathered from a remote host.**
*   **`delegate_to`:** Allows a task normally intended for a remote host to be executed on a different host, specified by the `delegate_to` keyword. You can delegate to a specific host, a group, or `localhost`.
*   **`run_once`:** When used with `delegate_to: localhost`, it ensures that the task runs only one time across the entire set of hosts targeted by the play, even if multiple hosts are in the group.
**Practical Example:** You gather the IP addresses of all web servers using a loop and register them. You then use `delegate_to: localhost` and `run_once: true` to run a script on the control node that updates a central DNS record using the collected list of IPs.

**A18 — Hard: You need to manage a fleet of 500 hosts and Ansible playbook runs take over 30 minutes. Identify at least 4 strategies to improve performance and explain the tradeoffs (cover: forks, pipelining, fact caching, and mitogen or similar).**
1.  **Increase `forks`:** Increase the number of concurrent connections Ansible makes. *Tradeoff:* Puts more load on the control node and the target hosts; too high can cause connection saturation.
2.  **Pipelining:** Allows Ansible to send tasks to multiple hosts simultaneously, rather than waiting for one host to finish all tasks before starting the next. *Tradeoff:* Can increase complexity in error handling and state management.
3.  **Fact Caching:** Use a persistent cache (e.g., Redis, JSON file) to store gathered facts. *Tradeoff:* Requires setting up and maintaining a cache backend; if the cache is stale, the deployment might be based on old system information.
4.  **Mitogen/Parallel Execution:** Using tools like Mitogen allows for true parallel execution of entire plays across multiple control nodes. *Tradeoff:* Significantly increases infrastructure complexity and requires robust coordination between control nodes.

**A19 — Hard: Explain how Ansible Jinja2 templating works. What is the difference between {{ }}, {% %}, and {# #}? Write a template snippet that generates an nginx upstream block from a list of backend servers with health check comments.**
Jinja2 is the templating engine Ansible uses.
*   **`{{ variable }}`:** Used for **printing** the value of a variable (output).
*   **`{% statement %}`:** Used for **logic** control flow (loops, conditionals, assignments).
*   **`{# comment #}`:** Used for **comments** within the template that are stripped out during rendering.
**Snippet:**
```nginx
upstream backend_servers {
    # Backend Server 1 (Primary)
    server {{ backend_servers.0.ip }}:{{ backend_servers.0.port }} weight=3;
    
    # Backend Server 2 (Secondary)
    server {{ backend_servers.1.ip }}:{{ backend_servers.1.port }} weight=1;
    
    # Backend Server 3 (Backup)
    server {{ backend_servers.2.ip }}:{{ backend_servers.2.port }} backup;
}
```
*(Assuming `backend_servers` is a list variable containing dictionaries with `ip` and `port` keys.)*

**A20 — Hard: Describe how to implement a zero-downtime rolling deployment of a web application across 20 servers using Ansible. Cover: serial batches, pre/post tasks for load balancer registration, health checks with uri module, and rollback strategy on failure using block/rescue.**
1.  **Serial Batches:** Use `serial: 5` in the play to deploy to 5 servers at a time, ensuring only a small fraction of the fleet is down at any moment.
2.  **Pre-Task (Deregister):** Before updating the application on a batch, use a task to deregister the current batch of servers from the load balancer (LB) using the `uri` module (or cloud provider module).
3.  **Deployment Task:** Run the application update tasks.
4.  **Health Check:** Immediately after deployment, use the `uri` module to perform a health check against the newly updated servers. If the check fails, the playbook execution should halt.
5.  **Post-Task (Register):** If the health check passes, use a task to register the updated batch of servers back into the LB.
6.  **Rollback Strategy:** Wrap the entire deployment sequence (Steps 2-5) within a `block`/`rescue` structure. If any task within the `block` fails (e.g., health check fails), the `rescue` block executes, which contains tasks to immediately revert the application on the affected servers and re-register them with the LB, ensuring minimal downtime.
